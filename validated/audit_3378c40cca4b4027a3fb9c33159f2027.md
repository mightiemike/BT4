### Title
Unbounded full-table iteration in list/pagination RPC handlers allows cheap per-request CPU/disk amplification - ([File: chainbase/src/main/java/org/tron/core/db/common/iterator/StoreIterator.java])

### Summary
Several gRPC/HTTP handlers (`ListWitnesses`, `GetAssetIssueList`, `ListExchanges`, and the "paginated" variants that internally call `getAllAssetIssues()`/`getAllExchanges()`) iterate the entire underlying LevelDB/RocksDB column via `StoreIterator.hasNext()`/`next()` before applying any offset/limit, meaning the DB-scan cost of a single request scales with total table size regardless of the requested page size. This lets an unprivileged network client trigger disproportionate CPU/I/O cost per cheap, feeless read request.

### Finding Description
`StoreIterator` (`chainbase/src/main/java/org/tron/core/db/common/iterator/StoreIterator.java:30-65`) walks the full keyspace via `dbIterator.seekToFirst()`/`hasNext()`/`next()` with no built-in bound — it is a raw wrapper with no cap on the number of entries visited.

This iterator is used by `AssetIssueStore.getAllAssetIssues()` (`chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java:34-38`) and `ExchangeStore.getAllExchanges()` (`chainbase/src/main/java/org/tron/core/store/ExchangeStore.java:31-38`), both of which do `Streams.stream(iterator()).collect(...)` — a full-table materialization with no pagination applied at the DB layer.

Critically, even the "paginated" API `AssetIssueStore.getAssetIssuesPaginated(offset, limit)` (`chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java:61-63`) calls `getAllAssetIssues()` first (full scan + full list materialization + sort), and only *afterward* slices the list to `ASSET_ISSUE_COUNT_LIMIT_MAX`. The size cap therefore only bounds the *response*, not the *cost of computing it* — the offset/limit parameters do not reduce the DB iteration work at all.

These are reachable from unprivileged, unauthenticated clients via:
- gRPC: `WalletSolidityApi.getAssetIssueList`/`getPaginatedAssetIssueList`, `listWitnesses`, `listExchanges`/`getPaginatedExchangeList` in `framework/src/main/java/org/tron/core/services/RpcApiService.java:393-441, 2023-2037`.
- HTTP: `GetPaginatedAssetIssueListServlet`, `GetPaginatedExchangeListServlet`, `ListWitnessesServlet`, `ListExchangesServlet` in `framework/src/main/java/org/tron/core/services/http/`.

These endpoints require no signed transaction, no fee, no bandwidth/energy payment, and no privileged role — a plain TCP/HTTP connection to the node's public API port suffices.

Existing mitigations do not close this gap:
- `RateLimiterServlet` (HTTP, `framework/src/main/java/org/tron/core/services/http/RateLimiterServlet.java:103-152`) and `RateLimiterInterceptor` (gRPC, `framework/src/main/java/org/tron/core/services/ratelimiter/RateLimiterInterceptor.java:95-123`) apply a default QPS-based rate limiter (`DefaultBaseQqsAdapter`/`QpsStrategy.DEFAULT_QPS_PARAM`) per endpoint and a global limiter. These bound *requests per second*, not the *cost per request*. If the underlying table (asset issues, exchanges, witnesses, proposals) is large, each individual request — even one that passes the QPS check — still performs an O(N) scan, so the per-request cost is not "metered" by the rate limiter at all. An attacker operating within the allowed QPS (or opening N concurrent connections, each independently rate-limited) can still sustain O(QPS × N) DB scans/sec.
- There is no per-request cap on iteration depth independent of the eventual response size; the only caps found (`ASSET_ISSUE_COUNT_LIMIT_MAX`, `PROPOSAL_COUNT_LIMIT_MAX`) bound output length, not I/O work, and for `ProposalStore` iteration is actually avoided (it uses direct key lookups via `calculateDbKey`, not a full scan) — but `AssetIssueStore` and `ExchangeStore` do not have that optimization.

### Impact Explanation
This is a DoS-via-RPC-API class issue: sustained CPU and disk I/O amplification proportional to on-chain table size (asset issues, exchanges, witnesses) per cheap/free read request, degrading node responsiveness for all API consumers. It does not lead to fund loss, key leak, or consensus divergence — the impact is scoped to availability/service degradation of the queried node's API layer.

### Likelihood Explanation
Feasible for any unprivileged client with only a network connection to the node's public gRPC/HTTP port; no fee, signature, or special permission required. The attacker is still bound by the existing per-endpoint/global QPS rate limiters, so the practical severity depends on the configured QPS limits and the size of the target tables (in the current live TRON mainnet, asset-issue/exchange table sizes are moderate, limiting real-world blast radius) — this reduces likelihood from "trivial mass DoS" to "moderate resource-amplification within already-rate-limited request budgets." Opening multiple concurrent connections/IPs can multiply the effect since the default rate limiters are commonly per-IP/per-channel rather than a single global hard cap (confirmed default adapter is QPS-based, not a hard concurrency cap), but I could not fully verify from the available code the exact global limiter semantics/config defaults for production deployments, so real-world exploitability additionally depends on node-operator rate-limiter configuration, which was not fully traced here.

### Recommendation
- Push offset/limit into the DB iteration itself (e.g., use `dbIterator.seek()`+bounded iteration count) instead of materializing the full table then slicing, for `AssetIssueStore.getAssetIssuesPaginated`, `ExchangeStore.getAllExchanges`, and any handler backing `ListWitnesses`/`GetAssetIssueList`/`ListExchanges`.
- Add a hard maximum iteration count to `StoreIterator`-based full-table reads used by unauthenticated RPC/HTTP handlers, independent of the enforced response-size cap.
- Consider adding request-cost-aware limiting (e.g., based on estimated table size) rather than pure QPS-based limiting for these full-scan endpoints.

  @Override
  public boolean hasNext() {
    if (close.get()) {
      return false;
    }

    boolean hasNext = false;
    // true is first item
    try {
      if (first) {
        dbIterator.seekToFirst();
        first = false;
      }

      if (!(hasNext = dbIterator.hasNext())) { // false is last item
        close();
      }
    } catch (Exception e) {
      logger.error(e.getMessage(), e);
      try {
        close();
      } catch (Exception e1) {
        logger.error(e1.getMessage(), e1);
      }
    }

    return hasNext;
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
