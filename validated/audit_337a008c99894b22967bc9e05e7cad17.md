## Analysis

The Gelato finding is a **cost accounted before/without the actual work that can be abused** pattern: a fee is fixed based on a coarse pre-computed estimate, while the subsequent step that is actually attacker-influenced is unbounded, letting the attacker pay a small fixed cost while forcing disproportionate work/resource consumption on the victim system.

The closest reachable analog in Agave, within the allowed AccountsDB/index scope, is the **secondary index (program-id / SPL-token owner / SPL-token mint) reverse-mapping**, which does an unbounded linear scan per insert and never prunes historical associations for a still-live account. ### Title
Unbounded, O(n²) growth of secondary-index reverse mappings from repeated attacker-controlled SPL-token owner/mint field changes - (File: accounts-db/src/accounts_index/secondary.rs)

### Summary
`SecondaryIndex::insert()` (used to maintain the `program_id`, `spl_token_owner`, and `spl_token_mint` secondary indexes) stores, per account pubkey, a `Vec<Pubkey>` of every distinct "outer key" (owner/mint) that account has ever been associated with, and de-duplicates via a linear `Vec::contains()` scan on every single insert. Nothing prunes historical entries from this reverse-index Vec while the account stays alive — pruning only happens when the account's primary-index entry is fully purged (dead key). An unprivileged user who repeatedly changes a token account's embedded owner (e.g., via `SetAuthority`) across separate slots forces `update_secondary_indexes`/`SecondaryIndex::insert` to append to this Vec every time, at O(n) cost per call, for O(n²) total CPU as well as unbounded memory retained by the reverse index, for the price of n ordinary transaction fees.

### Finding Description
`update_secondary_indexes()` unpacks the SPL-token owner/mint fields directly from raw, attacker-supplied account data and calls `self.spl_token_owner_index.insert(owner_key, pubkey)` (and similarly for mint/program-id) on every account write: [4](#0-3) 

`SecondaryIndex::insert()` maintains a `reverse_index: DashMap<Pubkey, RwLock<Vec<Pubkey>>>` keyed by the account (`inner_key`), whose value is a list of every distinct outer key (owner/mint) ever observed for that account: [1](#0-0) [2](#0-1) 

The comment at the top of the struct explicitly documents the assumption baked into this data structure: it assumes the case of an inner key mapping to multiple different outer keys "is rare," which is why an `O(n)`-scanned `Vec` was chosen over a `HashSet`: [1](#0-0) 

This assumption mirrors the flawed assumption in the Gelato report (fixed gas-overhead constants for ERC20/native transfers): the code sizes/optimizes for the "typical" case while leaving the adversarial case (attacker deliberately triggering the "rare" branch repeatedly) completely unbounded. An account's owner/mint embedded fields are fully attacker-controlled content within data the attacker's own transactions write (e.g. repeated `SetAuthority` calls on an SPL token account they control, or any account whose owning program lets the caller freely rewrite the indexed byte range across successive slots). Each such write is a normal, cheap transaction, but each corresponding `insert()` call is unbounded in cost because it must linear-scan the ever-growing `outer_keys` Vec: [5](#0-4) 

Crucially, these accumulated stale (owner, account) mappings are **not pruned** as the account's data changes across slots while it stays alive. Removal only happens via `purge_secondary_indexes_by_inner_key_if()`, which is invoked only when the account's key is fully removed from the primary accounts index (a "dead key"), i.e. never while the account is being actively kept alive by the attacker: [6](#0-5) [7](#0-6) 

### Impact Explanation
On any validator/RPC node running with `--account-index program-id|spl-token-owner|spl-token-mint` enabled, an attacker can force:
- Unbounded memory growth in the in-memory `reverse_index` DashMap entry for a single account (a `Vec<Pubkey>` that only ever grows).
- Superlinear (O(n²)) CPU cost in `SecondaryIndex::insert()`'s `outer_keys.contains(key)` scan, growing with every additional distinct owner/mint value the attacker cycles through.
- This CPU/memory cost is entirely disproportionate to the fixed, cheap transaction fees paid to trigger it (each triggering transaction is an ordinary account-data write), analogous to the Gelato report's disproportionate resource consumption relative to fee collected.

### Likelihood Explanation
Likelihood is limited to deployments that enable the optional secondary account indexes (common on RPC-serving nodes that support `getProgramAccounts`/`getTokenAccountsByOwner` scans by owner/mint). Any account owner able to issue transactions that alter the tracked byte ranges of an account they own (e.g., SPL Token `SetAuthority` to change owner) can trigger the vulnerable path with ordinary, unprivileged transactions across a moderate number of slots.

### Recommendation
Bound and/or deduplicate the reverse-index growth for `SecondaryIndex`:
- Replace `Vec<Pubkey>` with a `HashSet<Pubkey>` (or equivalent O(1)-lookup structure) for `reverse_index` entries to remove the O(n) `contains()` scan cost, and/or
- Impose a hard cap on the number of distinct outer keys tracked per inner key, evicting/pruning the oldest association once the cap is reached (mirroring the "hard cap" mitigation applied to the original Gelato report), and/or
- Actively unlink the previous owner/mint association for an account when it is updated to a new value in a later slot, instead of only pruning on full key removal from the primary index.

### Proof of Concept
1. Start a node with `--account-index spl-token-owner` enabled.
2. Create a single SPL token account `A` controlled by attacker keypair.
3. In a loop, for `i in 0..N`, submit (in separate, successive rooted slots) a `SetAuthority` instruction on `A` that installs a fresh, unique authority/owner pubkey `owner_i`.
4. Each of these N cheap transactions triggers `update_secondary_indexes` → `SecondaryIndex::insert(owner_i, A)`, which appends to `reverse_index[A]`'s Vec and performs an O(i) `contains()` scan, yielding O(N²) total CPU work and an O(N)-sized permanently retained Vec for a single account, entirely for the price of N ordinary transaction fees, since no compaction of `reverse_index[A]` ever happens while `A` remains alive in the primary index.

    /// Inserts `inner_key` into `key`'s map.
    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }

        // explicitly drop the locks so we don't hold them while reporting metrics
        drop(outer_keys);
        drop(reverse_index_entry);

    pub(crate) fn update_secondary_indexes(
        &self,
        pubkey: &Pubkey,
        account: &impl ReadableAccount,
        account_indexes: &AccountSecondaryIndexes,
    ) {
        if account_indexes.is_empty() {
            return;
        }

        let account_owner = account.owner();
        let account_data = account.data();

        if account_indexes.contains(&AccountIndex::ProgramId)
            && account_indexes.include_key(account_owner)
        {
            self.program_id_index.insert(account_owner, pubkey);
        }
        // Note because of the below check below on the account data length, when an
        // account hits zero lamports and is reset to AccountSharedData::Default, then we skip
        // the below updates to the secondary indexes.
        //
        // Skipping means not updating secondary index to mark the account as missing.
        // This doesn't introduce false positives during a scan because the caller to scan
        // provides the ancestors to check. So even if a zero-lamport account is not yet
        // removed from the secondary index, the scan function will:
        // 1) consult the primary index via `get(&pubkey, Some(ancestors), max_root)`
        // and find the zero-lamport version
        // 2) When the fetch from storage occurs, it will return AccountSharedData::Default
        // (as persisted tombstone for snapshots). This will then ultimately be
        // filtered out by post-scan filters, like in `get_filtered_spl_token_accounts_by_owner()`.

        self.update_spl_token_secondary_indexes::<spl_generic_token::token::Account>(
            &spl_generic_token::token::id(),
            pubkey,
            account_owner,
            account_data,
            account_indexes,
        );
        self.update_spl_token_secondary_indexes::<spl_generic_token::token_2022::Account>(
            &spl_generic_token::token_2022::id(),
            pubkey,
            account_owner,
            account_data,
            account_indexes,
        );
    }

    fn purge_secondary_indexes_for_dead_keys<'a>(
        &self,
        removed_keys: impl IntoIterator<Item = &'a Pubkey>,
    ) {
        if self.account_indexes.is_empty() {
            return;
        }
        for key in removed_keys {
            // Purging secondary entries for a key that is still alive in the primary index
            // would leave a live account invisible to secondary-index scans
            debug_assert!(
                !self.accounts_index.contains(key),
                "key removed from the primary index must not be present: {key}"
            );
            self.accounts_index.purge_secondary_indexes_by_inner_key_if(
                key,
                &self.account_indexes,
                || !self.accounts_cache.contains_pubkey(key),
            );
        }
    }
