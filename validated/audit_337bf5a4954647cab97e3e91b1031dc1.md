### Title
Non-embedded app OAuth session cookie is not scoped per shop by default, enabling cross-tenant session fixation - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
For non-embedded apps, `shopify.auth.callback` writes the `shopify_app_session` cookie with a hard-coded default path of `/` unless the app opts in to the `cookiePath` config option. Because the cookie name and path are identical for every shop, an OAuth completion for one shop silently overwrites the previously-authenticated session cookie for a different shop in the same browser, exactly like the sandwich pattern in the reported bug: a shared piece of state (an auction/cookie) that a second, less-trusted party can complete mid-flow to clobber the first party's expected outcome.

### Finding Description
`begin()` and `callback()` in `oauth.ts` set the OAuth state cookie and, at the end of a successful OAuth callback, the session cookie: [1](#0-0) 

The `cookiePath` resolves to `'/'` by default (`config.cookiePath ?? '/'`), so every shop's session cookie is written to the exact same name/path. This is explicitly documented as a known collision: [2](#0-1) 

The CHANGELOG confirms the impact and that it was previously unmitigated (fix is opt-in, not default): [3](#0-2) 

A regression test also encodes the vulnerable default as expected behavior — `cookiePath` not configured results in `path: '/'`: [4](#0-3) 

Just as the lender could sandwich a borrower by mutating `auctionLength` mid-flow to seize collateral, an attacker can induce a victim's browser to complete (or begin) OAuth for an attacker-controlled/second shop, silently overwriting the `shopify_app_session` cookie that the victim's legitimate session for their own shop depends on. Since `validateWithAuthCodeFlow` in `shopify-app-express` derives `shop` from `session?.shop` when no explicit `shop` query parameter is present, and only redirects to re-auth when a `shop` query param mismatches the loaded session, the victim's tab silently continues operating under the new (attacker-influenced) shop/session context with no explicit warning to the user: [5](#0-4) 

### Impact Explanation
This allows session fixation/cross-tenant confusion for non-embedded apps using the default configuration: a merchant/customer who has an app session open for their own shop can have it silently overwritten by a second OAuth flow (their own second tab, or one an attacker lures them into via a link/iframe for an attacker-controlled shop), causing subsequent actions/data submitted by the victim in the original tab to be associated with the wrong shop/session. This is analogous to the reported lender-sandwich bug: a mutable shared piece of state (cookie/session, analogous to `auctionLength`) is not validated against the caller's expected value before being trusted, letting a second, less-trusted party silently redirect the outcome of the first party's in-flight operation.

### Likelihood Explanation
Requires only an unprivileged actor (single merchant/customer opening a second OAuth flow, or being tricked via a link) and default (undocumented-as-required) configuration — no privileged access, leaked secret, or MITM needed. It is realistic for any non-embedded, multi-shop-capable Shopify app that has not explicitly set `cookiePath`.

### Recommendation
Make cookie scoping mandatory (not opt-in) for non-embedded apps that could plausibly serve multiple shops from the same domain, or, at minimum, bind the session lookup to a validated `shop` parameter present in the request itself rather than trusting `session?.shop` when a mismatch could indicate cookie collision. Consider defaulting `cookiePath` to something shop-derived when `isEmbeddedApp` is `false`, or emitting a hard warning/error at startup if multi-shop support is enabled without a distinct `cookiePath`.

### Proof of Concept
1. Deploy a non-embedded app without setting `cookiePath` (default `'/'`).
2. Victim completes OAuth for `shop-a.myshopify.com` in Tab 1 — `shopify_app_session` cookie is set to `offline_shop-a...` at path `/`.
3. Attacker gets the victim to open a link/iframe in Tab 2 that begins and completes OAuth for `shop-b.myshopify.com` (attacker's own store, or any shop the victim is induced to authorize).
4. The browser's `shopify_app_session` cookie is overwritten to `offline_shop-b...` because both cookies share the same name and path (`/`).
5. Victim returns to Tab 1 and continues interacting with the app; requests now resolve `session.shop === shop-b`, silently operating under a different shop context than the victim intended — confirmed by the test at `oauth.test.ts:725-760` showing the default path is always `/` regardless of shop.

  /**
   * The path to use for the OAuth session cookie in non-embedded apps.
   *
   * By default the cookie is written with `path: '/'`, making it domain-wide.
   * This means that when a user authenticates multiple shops in separate tabs,
   * each OAuth callback overwrites the previous cookie, causing all tabs to use
   * the most-recently-authenticated shop.
   *
   * Set this to a string or a function returning a string to scope the cookie to
   * a URL path prefix that is unique per shop. The browser will then maintain
   * one cookie per shop and deliver only the matching one per request.
   *
   * **Requirement:** the configured path must match the actual URL structure of
   * your app — e.g. if each shop lives under `/shops/:shop/`, use that prefix.
   * The library cannot derive this automatically.
```

**File:** packages/apps/shopify-api/CHANGELOG.md (L129-150)
```markdown
- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
```
