### Title
Deposit Refund Misdirection in Meta Transactions Enables Relayer Fund Drain via Malicious DelegateAction - (File: runtime/runtime/src/actions.rs)

### Summary

In nearcore's meta transaction (NEP-366 `DelegateAction`) implementation, when an inner action receipt fails on the receiver's shard, the attached deposit refund is routed to the `predecessor_id` of the inner receipt (the user/sender, e.g. Alice), not to the relayer who actually paid for the deposit. An unprivileged user can exploit this by crafting a `DelegateAction` with a large deposit attached to an inner action designed to fail, causing the relayer to permanently lose the deposit while the user receives it.

### Finding Description

`apply_delegate_action` in `runtime/runtime/src/actions.rs` constructs the inner receipt with `predecessor_id = sender_id` (Alice):

```rust

        ...

``` [1](#0-0) 

The comment immediately below acknowledges the problem:

> "If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction. … Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit." [2](#0-1) 

When the inner receipt fails on the receiver's shard, `refund_unspent_gas_and_deposits` computes:

```rust
let deposit_refund = if result.result.is_err() { total_deposit } else { Balance::ZERO };
```

and routes it to `receipt.balance_refund_receiver()`, which is the `predecessor_id` of the inner receipt — Alice — not the relayer who funded the deposit. [3](#0-2) 

The protocol documentation explicitly confirms this broken invariant:

> "But what if the transaction fails execution on Bob's shard? At this point, the predecessor is `Alice` and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard." [4](#0-3) 

The broken invariant is: **the party who paid for the deposit (the relayer, `signer_id`) does not receive the deposit refund when the inner action fails; instead it goes to the user (Alice, `predecessor_id` of the inner receipt)**. This is a structural mismatch in the refund routing that the protocol itself acknowledges but does not fix.

### Impact Explanation

An unprivileged user (Alice) can drain an arbitrary amount of NEAR from a relayer's account:

1. Alice crafts a `DelegateAction` with a large NEAR deposit (e.g. 100 NEAR) attached to an inner `FunctionCall` that is guaranteed to fail (e.g. calling a non-existent method, or a method that panics).
2. Alice sends this `SignedDelegateAction` to a relayer.
3. The relayer submits the outer transaction on-chain, paying for all gas and the deposit from its own balance.
4. The outer receipt executes successfully on Alice's shard (the `DelegateAction` signature and nonce are valid).
5. The inner receipt fails on the receiver's shard.
6. The deposit refund (100 NEAR) is sent to Alice (`predecessor_id` of the inner receipt), not the relayer.
7. The relayer loses 100 NEAR plus gas costs. Alice gains 100 NEAR.

This attack can be repeated with fresh nonces, draining the relayer's balance. The deposit amount is bounded only by the relayer's own balance, not by any protocol limit. The impact is **loss of funds** for the relayer and **unauthorized balance gain** for Alice.

### Likelihood Explanation

The likelihood is **medium**. The attack requires:
- A relayer that accepts `DelegateAction`s from untrusted users (the intended use case for general-purpose relayers).
- Alice to craft a `DelegateAction` with a deposit-bearing inner action that will fail.

No privileged access, validator role, or special permissions are required. Alice is a fully unprivileged user. The nearcore protocol provides no on-chain mechanism for the relayer to prevent this — the only mitigation is off-chain verification by the relayer, which is not enforced by the protocol. General-purpose relayers (the intended audience for NEP-366) are the primary target.

### Recommendation

The deposit refund routing for meta transactions should be corrected at the protocol level. When an inner receipt spawned by a `DelegateAction` fails, the deposit refund should be sent to the `signer_id` of the inner receipt (the relayer), not the `predecessor_id` (Alice). This requires either:

1. Introducing a dedicated `deposit_refund_receiver` field in `ActionReceipt` that `apply_delegate_action` sets to the relayer's account ID, or
2. Tracking the original deposit payer through the receipt chain and routing refunds accordingly.

The comment in `apply_delegate_action` acknowledges the problem but defers responsibility to relayer implementors. A protocol-level fix is needed because off-chain verification cannot prevent race conditions (Alice can reduce her balance or cause the inner action to fail after the relayer has already verified the action).

Step 3: Relayer wraps it in a transaction:
  Transaction {
    signer_id:   "relayer.near",
    receiver_id: "alice.near",

  - Signature valid ✓, nonce valid ✓, sender matches ✓

      receiver_id:    "bob.near"

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

    // Generate a new receipt from DelegateAction.
    let new_receipt = Receipt::V0(ReceiptV0 {
        predecessor_id: sender_id.clone(),
        receiver_id: delegate_action.receiver_id().clone(),
        receipt_id: CryptoHash::default(),

        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: action_receipt.signer_id().clone(),
            signer_public_key: action_receipt.signer_public_key().clone(),
            gas_price: action_receipt.gas_price(),
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: delegate_action.get_actions(),
        }),
    });

    // Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas.
    // If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction.
    // Gas is refunded to the signer, this is Relayer.
    // Some contracts refund the deposit. Usually they refund the deposit to the predecessor and this is sender_id/Sender from DelegateAction.
    // Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit.

    let prepaid_send_fees = total_prepaid_send_fees(&apply_state.config, action_receipt.actions())?;
    let required_cost = receipt_required_cost(apply_state, &new_receipt)?;
    // This gas will be burnt by the receiver of the created receipt.
    // Compute costs of that are not relevant at this point, the "used" gas is
    // only reserved for execution later, potentially on a different shard.
    result.gas_used = result.gas_used.checked_add_result(required_cost.gas)?;
    // This gas was prepaid on Relayer shard. Need to burn it because the receipt is going to be sent.
    // gas_used is incremented because otherwise the gas will be refunded. Refund function checks only gas_used.
    result.gas_used = result.gas_used.checked_add_result(prepaid_send_fees.gas)?;
    result.gas_burnt = result.gas_burnt.checked_add_result(prepaid_send_fees.gas)?;
    result.compute_usage = safe_add_compute(result.compute_usage, prepaid_send_fees.compute)?;
    result.new_receipts.push(new_receipt);

    Ok(())
}

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
