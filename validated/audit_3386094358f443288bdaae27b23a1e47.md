**Rationale:**

The premise conflates a test-only simulation helper with the production executor-to-storage commit path. `apply_write_set` only exists in test/simulation utilities — e.g. `aptos-transaction-simulation/src/state_store.rs` and `aptos-move/e2e-tests/src/executor.rs` — where it is explicitly used to feed a `WriteSet` (already produced by VM execution) back into an in-memory `FakeExecutor`/state store for testing purposes. [1](#0-0) 

In production, ledger commit goes through `ChunkExecutorTrait`/`ChunkExecutor`, which either (a) executes transactions with the real VM (`enqueue_chunk_by_execution` → `DoGetExecutionOutput::by_transaction_execution`) so the write set is always the deterministic output of Move bytecode execution, or (b) applies already-computed `TransactionOutputListWithProofV2` only after verifying the accumulator/ledger-info proof against a validator-signed `LedgerInfoWithSignatures` (`enqueue_chunk_by_transaction_outputs`). [2](#0-1) [3](#0-2) 

There is no code path by which an unprivileged transaction, package, API call, or view can supply an arbitrary/manipulated `ValidatorInfo` write set that substitutes for the VM's actual computation. The `ValidatorSet`/`ValidatorInfo` values committed at epoch boundary are generated exclusively inside `aptos_framework::stake` by `generate_validator_info`/`refresh_validator_set_in_place`, which derives voting power and config purely from on-chain `StakePool`/`ValidatorConfig` resources at that state version — the Move VM session record (`ChangeSet`) is the sole source of the write set, and there's no user-facing mechanism to inject a different one into the block/chunk pipeline. [4](#0-3) [5](#0-4) 

The cited "analogous path" (`execution/executor/src/tests/mock_vm/mod.rs`) is test/mock-only code and is explicitly excluded by the review scope rules. Since the actual production handoff (`ChunkExecutorInner::commit_chunk_impl` → `db.writer.save_transactions`) only ever commits the `ExecutedChunk` output that itself derives from either genuine VM execution or a proof-verified output list bound to a signed ledger info, there is no unprivileged path to corrupt the committed `ValidatorSet` with data diverging from the true VM result. [6](#0-5)
