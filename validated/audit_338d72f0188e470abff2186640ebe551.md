### Title
Division by zero on `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` due to unenforced `assert` - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides by `totalEnergyWeight` and guards this only with a Java `assert`, which is disabled by default in production (JVMs run without `-ea`). If `totalEnergyWeight` becomes `0`, this results in an `ArithmeticException` (hardened path) or produces `NaN`/`Infinity` (double-math path), analogous to the reported Notional issue where a value that "should" be positive (per contract/comment) is not actually enforced to be positive at the point of division.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` reads `totalEnergyWeight` from `DynamicPropertiesStore` and immediately divides by it: [1](#0-0) 

The only safety check is `assert totalEnergyWeight > 0;`, which is a no-op at runtime unless the JVM is started with `-ea` (assertions are disabled by default in Java, including in typical production `java-tron` deployments). If `totalEnergyWeight` is `0`:
- In the hardened path (`hardenResourceCalculation()` true), `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`.
- In the legacy double-math path, `totalEnergyLimit / totalEnergyWeight` produces `Infinity`/`NaN` rather than throwing, silently corrupting energy accounting.

Contrast this with the sibling implementation `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`, which explicitly checks `totalEnergyWeight <= 0` / `== 0` and returns `0` instead of dividing: [2](#0-1) 

This shows the codebase itself recognizes `totalEnergyWeight` can be zero (e.g., before any TRX is frozen for energy on a fresh chain, or transiently during reward/weight recalculations) and defends against it in one place, but not in `RepositoryImpl`, which is the path used by the VM/native contract resource logic (`Repository` interface, used by `VMActuator`, `DelegateResourceProcessor`, `UnDelegateResourceProcessor`, etc.).

### Impact Explanation
If `totalEnergyWeight` is `0` and the hardened resource calculation path is enabled (`allowHardenResourceCalculation`), any call path through `RepositoryImpl.calculateGlobalEnergyLimit` throws an unhandled `ArithmeticException`. Since this is invoked from smart-contract execution / resource-delegation flows reachable by any ordinary account (an unprivileged user simply calling a contract or delegating/undelegating energy resources triggers energy limit calculation), this can cause transaction execution to fail unexpectedly or, if triggered deep in block-processing logic without proper exception handling, potentially destabilize node processing for that code path. This matches the reported bug class' "invalid-state/halt" impact category, since it turns a purely arithmetic assumption failure (never checked at runtime) into a crash of the affected computation path.

### Likelihood Explanation
`totalEnergyWeight` is a globally tracked, protocol-maintained value (sum of frozen balances for energy across the network) rather than user input, so it is unlikely to be exactly zero on a mature mainnet. However, it is plausible on fresh/private/test networks before genesis freezes are applied, or transiently through the "new reward" logic that `EnergyProcessor` explicitly checks for (`allowNewReward() && totalEnergyWeight <= 0`). The fact that the codebase already needed to add that explicit zero-check in `EnergyProcessor` demonstrates this is a recognized, reachable condition — but the `RepositoryImpl` counterpart was not updated with the same protection.

### Recommendation
Add an explicit zero/non-positive check for `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit`, mirroring the guard already present in `EnergyProcessor.calculateGlobalEnergyLimitV2`, returning `0` (or otherwise handling this case) instead of relying on an `assert` that is disabled in production:

```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
if (totalEnergyWeight <= 0) {
  return 0;
}
```

### Proof of Concept
1. Deploy/operate a `java-tron` node in a state where `DynamicPropertiesStore.getTotalEnergyWeight()` returns `0` (e.g., freshly initialized network prior to any energy freezes, or a state achievable via the `allowNewReward` transition that `EnergyProcessor` already guards against).
2. Trigger any code path that calls `RepositoryImpl.calculateGlobalEnergyLimit(accountCapsule)` — e.g., through a smart contract call handled by `VMActuator`, or through `DelegateResourceProcessor`/`UnDelegateResourceProcessor`, which reference the same `Repository` methods: [3](#0-2) 
3. With `allowHardenResourceCalculation` enabled, the `BigInteger.divide(BigInteger.ZERO)` at line 981 throws `ArithmeticException`, since assertions (`assert totalEnergyWeight > 0;`) are not enforced by default in a standard production JVM run.
