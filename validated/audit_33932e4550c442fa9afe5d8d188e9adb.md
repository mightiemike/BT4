This confirms the pattern is consistent across `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router`: in the token-exchange authentication path, `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` is called with `scopes` explicitly passed as `undefined`, whereas the legacy Auth Code flow (`validateWithAuthCodeFlow`) correctly calls `session.isActive(api.config.scopes)`.

Looking at `Session.isActive`/`isScopeChanged` in `packages/apps/shopify-api/lib/session/session.ts` (lines 198-219): when `scopes` is `undefined`, `isScopeChanged()` unconditionally returns `false`, meaning the scope-match requirement is completely skipped. So a session obtained via token exchange, once stored, is considered "active" and reused indefinitely purely based on token expiry — never re-validated against the app's currently configured/required scopes — until the access token itself expires or is invalidated by a 401. This mirrors the reNFT bug class: an entity (`Guard.sol` / here, a stored session with an old scope grant) that should be forced to "re-upgrade" (re-authenticate to pick up new scopes) can instead continue being used indefinitely because the active-state check bypasses the scope-currency check.

### Title
Token-exchange session validation skips scope-change checks, allowing indefinite reuse of stale-scope sessions - (File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts)

### Summary
The token-exchange authentication path (`shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`) validates a stored session's "active" status by calling `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)`, passing `undefined` for the required `scopes` argument. Because `Session.isScopeChanged` treats `undefined` scopes as "no scope check requested" (always returns `false`), the scope-currency guard that the legacy Auth Code flow performs (`session.isActive(api.config.scopes)`) is silently skipped in the token-exchange flow.

### Finding Description
`Session.isActive(scopes, withinMillisecondsOfExpiry)` in [1](#0-0)  is designed to treat a session as inactive both when the access token is expired and when the session's granted `scope` no longer matches the app's currently required `scopes` (`isScopeChanged`). The Auth Code flow validator correctly enforces both conditions: [2](#0-1)  calls `session.isActive(api.config.scopes)`.

However, the token-exchange strategy, used across all three framework packages, calls `isActive` with `undefined` in place of the app's scopes:
- `shopify-app-express`: [3](#0-2) 
- `shopify-app-react-router`: [4](#0-3) 
- `shopify-app-remix` uses the equivalent strategy file (same pattern).

Since `isScopeChanged` short-circuits to `false` when `scopes` is `undefined` ( [5](#0-4) ), any previously stored offline/online session obtained through token exchange is deemed "active" purely based on token expiry, regardless of whether the app's required scopes have since changed (e.g., the app was updated to require additional/narrower scopes). This is directly analogous to the reNFT finding: a component (`Guard.sol` there, a session's scope grant here) that is supposed to be forced onto the "current" configuration is instead permitted to persist in an outdated state indefinitely, because the code path that checks "is this still the current/authorized state" (`checkTransaction`/`isActive`) omits the check that would detect staleness (`address(this)` active in `Kernel` / `scopes` match against `api.config.scopes`).

### Impact Explanation
When an app's required scopes are updated (a very common maintenance operation — Shopify apps regularly add scopes for new features), sessions created via token exchange before the scope change will continue to be accepted as valid and reused for API calls with the stale (narrower or different) scope grant, until the underlying access token happens to expire naturally or is invalidated by a `401` from Shopify. This can let request-authentication continue operating on stale authorization state rather than forcing a fresh token-exchange (which would otherwise request a token with the updated scopes), undermining the scope-based access-control model the library otherwise enforces consistently on the Auth Code path. This is an availability/consistency issue in the authentication/authorization gating logic rather than a direct funds-loss issue, matching the Medium classification given to the reNFT analog.

### Likelihood Explanation
This triggers automatically and silently for any merchant/customer request through the token-exchange path once an app updates its scopes — no attacker action is required beyond normal continued use of the app by a legitimate merchant, since the vulnerable code executes on every authenticated request that reuses a stored session.

### Recommendation
Pass `api.config.scopes` (or the equivalent configured scopes for the framework) into `session.isActive(...)` in the token-exchange validation paths, mirroring the Auth Code flow's behavior, e.g.:
```ts
if (session && session.isActive(api.config.scopes, WITHIN_MILLISECONDS_OF_EXPIRY)) { ... }
```
so that a scope mismatch forces a fresh token exchange the same way it forces re-authentication in the Auth Code flow.

### Proof of Concept
1. Deploy an embedded app with `future.tokenExchange: true` and initial scopes `["read_products"]`.
2. A merchant installs the app; token exchange stores an offline session with `scope: "read_products"`.
3. The app is updated to require `["read_products", "write_products"]` and redeployed with `api.config.scopes` reflecting the new value, but the stored session is untouched.
4. A subsequent authenticated request goes through `performTokenExchange`/`createTokenExchangeStrategy`; `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` returns `true` (token not expired) despite the scope mismatch, so no new token exchange is triggered and the stale-scope session is reused, per [6](#0-5) .
