### Title
Hardcoded scale assumption in `MAX_OBSOLETE_ACCOUNTS_FILE_SIZE` silently forces expensive full-archive rebuilds instead of cheap fastboot - ([File: runtime/src/snapshot_utils.rs])

### Summary
`runtime/src/snapshot_utils.rs` hardcodes a cap on the size of the per-bank-snapshot obsolete-accounts file based on a fixed assumption about per-entry byte cost and total account-count scale of the network. Like the `DEFAULT_ANTE`/`CONSTRAINT_ANTE_MAX` constants in the referenced report — sized for an assumed price/scale that silently becomes wrong as real-world conditions change — this constant is sized for an assumed obsolete-entry ratio/format overhead that can become wrong as the ledger's account churn and format evolve, with no governance/override mechanism to correct it. When the assumption breaks, the validator is forced onto the disproportionately expensive code path (full archive restore) instead of the cheap one (fastboot from local disk).

### Finding Description
The obsolete-accounts fastboot file size limit is derived from a fixed, in-code guess about future network scale and per-entry size: [1](#0-0) 

This constant is used both when writing the file during snapshot generation (`serialize_obsolete_accounts`) and when reading it back during fastboot (`deserialize_obsolete_accounts`): [2](#0-1) 

If the actual obsolete-accounts file on disk exceeds `MAX_OBSOLETE_ACCOUNTS_FILE_SIZE` — because the real per-entry encoding size grew (e.g. serde/wincode format changes), or because a node accumulated more obsolete entries than the "5% of 10 billion accounts" assumption anticipated (e.g. sustained heavy account-write churn on a single node between clean/shrink passes) — `deserialize_obsolete_accounts` returns a hard error rather than any graceful degradation: [3](#0-2) 

This error is not recoverable in-place: an honest node hitting this limit cannot load its own local (and otherwise perfectly valid) fastboot snapshot state, and `try_load_bank_forks_from_snapshot` must fall back to restoring from a full snapshot archive: [4](#0-3) 

There is no configuration flag or governance-style override to raise `MAX_OBSOLETE_ACCOUNTS_FILE_SIZE`; it is a hardcoded constant baked into the binary, exactly the pattern the external report calls out as high risk (a numeric assumption about scale/magnitude that is reasonable "at the time of writing" but becomes wrong later, with no adjustable knob).

### Impact Explanation
Hitting this limit forces an honest, correctly-functioning validator to discard its fast local snapshot directory and instead download/extract a full snapshot archive and fully rebuild storages/accounts index from scratch — a dramatically more expensive CPU, disk I/O, and (if downloading from a peer) network operation compared to fastboot. This matches the accepted "disproportionate storage and CPU cost" impact class: a node that should restart in seconds is instead forced into a multi-minute/hour cold-start path purely because a hardcoded scale assumption from the past no longer matches present conditions.

### Likelihood Explanation
The constant's own doc comment shows it was deliberately derived from present-day assumptions ("5% of 10 billion accounts", "24 bytes per entry") without any adjustment mechanism, so as the network's total account count or the actual bytes-per-entry serialization overhead grows (or as heavy account-write churn on a specific node produces more obsolete entries between clean passes than anticipated), the fixed 12 GiB ceiling can eventually be exceeded on entirely honest nodes during normal operation, not just via attack.

### Recommendation
Make the obsolete-accounts file size limit configurable (similar to other size limits like `MAX_SNAPSHOT_DATA_FILE_SIZE`) or derive it dynamically from the actual number of tracked storages/obsolete entries at serialization time, rather than a single hardcoded assumption baked in at compile time. At minimum, add a CLI/config override so operators are not stuck with an outdated hardcoded ceiling as the network scales, mirroring the report's recommendation to make the analogous economic constant governable instead of hardcoded.

### Proof of Concept
The existing unit tests already demonstrate the failure mode directly — shrinking the limit causes both the serialize and deserialize paths to hard-fail: [5](#0-4) [6](#0-5) 

The same failure occurs in production whenever `obsolete_accounts_file_metadata.len() > MAX_OBSOLETE_ACCOUNTS_FILE_SIZE` is true for a real, honestly-generated snapshot, forcing the fallback path shown in `try_load_bank_forks_from_snapshot`.

fn deserialize_obsolete_accounts(
    bank_snapshot_dir: impl AsRef<Path>,
    maximum_obsolete_accounts_file_size: u64,
) -> Result<SerdeObsoleteAccountsMap> {
    let obsolete_accounts_path = bank_snapshot_dir
        .as_ref()
        .join(snapshot_paths::SNAPSHOT_OBSOLETE_ACCOUNTS_FILENAME);
    let obsolete_accounts_reader = ReadAdapter::new(large_file_buf_reader(
        &obsolete_accounts_path,
        AUX_SNAPSHOT_FILE_READ_BUF_SIZE,
        &IoSetupState::default(),
    )?);
    // If the file is too large return error
    let obsolete_accounts_file_metadata = fs::metadata(&obsolete_accounts_path)?;
    if obsolete_accounts_file_metadata.len() > maximum_obsolete_accounts_file_size {
        let error_message = format!(
            "too large obsolete accounts file to deserialize: '{}' has {} bytes (max size is \
             {maximum_obsolete_accounts_file_size} bytes)",
            obsolete_accounts_path.display(),
            obsolete_accounts_file_metadata.len(),
        );
        return Err(IoError::other(error_message).into());
    }
