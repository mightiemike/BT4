### Title
Direct nonce mutation in `perform_pre_validation_stage` before subsequent checks can fail, corrupting gateway/mempool validation state - (File: crates/blockifier/src/transaction/account_transaction.rs)

### Summary
`AccountTransaction::perform_pre_validation_stage` calls `Self::handle_nonce`, which increments the account nonce directly on the passed-in state, *before* the fee-bound and proof-fact checks that can fail and return an `Err`. In the block-building/production path this is safe because `execute()` always wraps `execute_raw` (and thus `perform_pre_validation_stage`) in a `TransactionalState` that is explicitly `abort()`-ed on any error. However, in the gateway's stateful validation path, `StatefulValidator::perform_validations` calls `tx.perform_pre_validation_stage(self.state(), &tx_context)` directly on the validator's own `CachedState` with **no surrounding transactional wrapper and no `abort()` on failure**.

### Finding Description
In `crates/blockifier/src/transaction/account_transaction.rs`: [1](#0-0) 
`perform_pre_validation_stage` calls `handle_nonce` first, which — on a valid nonce — performs `state.increment_nonce(address)` immediately: [2](#0-1) 
Only *after* this mutation does the function run `check_fee_bounds`, `verify_can_pay_committed_bounds`, and `validate_proof_facts`, any of which can return `Err` and abort the function — but the nonce increment has already been committed to the `state` object passed in.

This mirrors the audited pattern exactly: state is mutated before a check that can fail, so a failing validation still leaves the mutated state in place unless something explicitly reverts it.

In the normal transaction-execution path (`ExecutableTransaction::execute`), this is safe because a fresh `TransactionalState` is created and explicitly `abort()`-ed on any error: [3](#0-2) 

But `StatefulValidator::perform_validations`, used by the gateway to validate a submitted transaction before mempool admission, calls `perform_pre_validation_stage` directly on `self.state()` (the validator's live `CachedState`) with no such wrapper: [4](#0-3) 
`self.state()` returns the raw `CachedState` backing the whole validator instance: [5](#0-4) 

If `perform_pre_validation_stage` fails at `check_fee_bounds`/`verify_can_pay_committed_bounds`/`validate_proof_facts` (all of which run *after* the nonce increment), the `Err` propagates out of `perform_validations` via `?` with no rollback of the already-incremented nonce in `self.state()`.

### Impact Explanation
This corrupts the state used by the stateful validator's `CachedState` for the remainder of its lifetime. Concretely, in the gateway's `run_validate_entry_point`, a fresh `StatefulValidator::create(state, block_context)` is built per validated transaction from a freshly-fetched `CachedState`: [6](#0-5) 
so within the gateway's own request flow the impact is limited to a single validation call and does not persist across different gateway requests. However, the same `StatefulValidator` API is also exposed directly for reuse in `crates/native_blockifier/src/py_validator.rs`, where a single long-lived `PyValidator`/`StatefulValidator` instance is created once and then `perform_validations` is called repeatedly across many separate incoming transactions on the *same* state: [7](#0-6) 
In that reused-validator scenario, a submitted transaction that fails only due to insufficient fee bounds (not nonce or signature) will leave the account's nonce permanently incremented in the validator's cached state, causing subsequent validations of that account's legitimately-nonced transactions to be rejected as having an "invalid nonce" (since the tracked nonce has silently advanced without the corresponding transaction ever executing). This can be triggered by any unprivileged transaction sender submitting a transaction with a valid signature/nonce but insufficient fee/resource bounds, resulting in that account being effectively unable to get further transactions validated until the discrepancy is discovered — a mempool-admission liveness/DoS issue for the affected account, matching the "unauthorized state mutation before validation completes" bug class of the reported issue.

### Likelihood Explanation
Medium. Reaching the vulnerable code path requires only submitting an ordinary Invoke transaction with a correct nonce/signature but insufficient fee bounds — fully reachable by any unprivileged transaction sender via the gateway/mempool validation flow. The actual persistence of the corrupted state depends on whether the specific caller of `StatefulValidator` reuses one instance/state across multiple transactions (as is done in `native_blockifier`'s `PyValidator`) rather than recreating it per transaction (as the Rust gateway currently does).

### Recommendation
In `perform_pre_validation_stage`, reorder or otherwise guard the check so the nonce is only incremented after all static/fee checks that can fail have succeeded, or wrap the call in a `TransactionalState` that is `abort()`-ed on `Err` inside `StatefulValidator::perform_validations` (and any other caller, e.g. `py_validator.rs`), mirroring the pattern already used by `ExecutableTransaction::execute`.

### Proof of Concept
1. Instantiate (or reuse) a `StatefulValidator` over a `CachedState` with a known account nonce `N`.
2. Submit an `AccountTransaction` (Invoke, V1/V3) with `nonce = N` and a valid signature, but with `resource_bounds`/`max_fee` below the minimal required amount (as covered by `check_fee_bounds`).
3. Call `perform_validations`; observe it returns `Err(TransactionPreValidationError::TransactionFeeError(...))`.
4. Query `state.get_nonce_at(address)` on the same underlying `CachedState` (e.g. via `StatefulValidator::get_nonce`) — the nonce has already advanced to `N+1` despite the transaction being rejected, matching the existing unit-test assertion pattern already documented for the execute path: [8](#0-7) 
which confirms nonce increment happens on `handle_nonce` success regardless of later stage outcome — the difference being that in the `StatefulValidator` path there is no `abort()` to revert it.

    // Note that nonce is incremented during these checks.
    pub fn perform_pre_validation_stage<S: State + StateReader>(
        &self,
        state: &mut S,
        tx_context: &TransactionContext,
    ) -> TransactionPreValidationResult<()> {
        let tx_info = &tx_context.tx_info;
        Self::handle_nonce(state, tx_info, self.execution_flags.strict_nonce_check)?;

        if self.execution_flags.charge_fee {
            self.check_fee_bounds(tx_context)?;

            verify_can_pay_committed_bounds(state, tx_context).map_err(Box::new)?;
        }

        self.validate_proof_facts(&tx_context.block_context, state)?;

        Ok(())
    }

    fn handle_nonce(
        state: &mut dyn State,
        tx_info: &TransactionInfo,
        strict: bool,
    ) -> TransactionPreValidationResult<()> {
        if tx_info.is_v0() {
            return Ok(());
        }

        let address = tx_info.sender_address();
        let account_nonce = state.get_nonce_at(address)?;
        let incoming_tx_nonce = tx_info.nonce();
        let valid_nonce = if strict {
            account_nonce == incoming_tx_nonce
        } else {
            account_nonce <= incoming_tx_nonce
        };
        if valid_nonce {
            return Ok(state.increment_nonce(address)?);
        }
        Err(TransactionPreValidationError::InvalidNonce {
            address,
            account_nonce,
            incoming_tx_nonce,
        })
    }

pub trait ExecutableTransaction<U: UpdatableState>: Sized {
    /// Executes the transaction in a transactional manner
    /// (if it fails, given state does not modify).
    fn execute(
        &self,
        state: &mut U,
        block_context: &BlockContext,
    ) -> TransactionExecutionResult<TransactionExecutionInfo> {
        log::debug!("Executing Transaction...");
        let mut transactional_state = TransactionalState::create_transactional(state);
        let concurrency_mode = false;
        let execution_result =
            self.execute_raw(&mut transactional_state, block_context, concurrency_mode);

        match execution_result {
            Ok(value) => {
                transactional_state.commit();
                log::debug!("Transaction execution complete and committed.");
                Ok(value)
            }
            Err(error) => {
                log::debug!("Transaction execution failed with: {error}");
                transactional_state.abort();
                Err(error)
            }
        }
    }

    pub fn perform_validations(&mut self, tx: AccountTransaction) -> StatefulValidatorResult<()> {
        // Deploy account transaction should be fully executed, since the constructor must run
        // before `__validate_deploy__`. The execution already includes all necessary validations,
        // so they are skipped here.
        // Declare transaction should also be fully executed - otherwise, if we only go through
        // the validate phase, we would miss the check that the class was not declared before.
        match tx.tx {
            ApiTransaction::DeployAccount(_) | ApiTransaction::Declare(_) => self.execute(tx),
            ApiTransaction::Invoke(_) => {
                let tx_context = Arc::new(self.tx_executor.block_context.to_tx_context(&tx));
                tx.perform_pre_validation_stage(self.state(), &tx_context)?;
                if !tx.execution_flags.validate {
                    return Ok(());
                }

                // `__validate__` call.
                let (_optional_call_info, actual_cost) = self.validate(&tx, tx_context.clone())?;

                // Post validations.
                PostValidationReport::verify(
                    &tx_context,
                    &actual_cost,
                    tx.execution_flags.charge_fee,
                )?;

                Ok(())
            }
        }
    }
