### Title
`afterAuth` hook failure during token exchange causes an authenticated session to be rejected with a 500, denying access despite a valid session token - ([File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts])

### Summary
`performTokenExchange` completes the OAuth token exchange (validating the session token and obtaining/storing an access token) and then invokes the developer-configured `afterAuth` hook. If that hook throws for any reason unrelated to the validity of the session or request, the middleware discards the already-successful authentication result and returns a `500 Internal Server Error` instead of calling `next()`, blocking the legitimate, already-authenticated request. [1](#0-0) 

### Finding Description
`performTokenExchange` decodes the session token, exchanges it for an offline (and optionally online) access token, stores the resulting session, and only then runs `callAfterAuthHook`, which wraps the user-supplied `config.hooks.afterAuth` callback. [2](#0-1) [3](#0-2) 

If `afterAuth` throws (e.g. it tries to register webhooks and Shopify's API is briefly unavailable, or it performs any unrelated business logic that fails), the surrounding `try/catch` treats this as a fatal error for the whole request and responds `500`, never calling `next()`:
```
try {
  await callAfterAuthHook(config, newSession, sessionToken);
} catch (error) {
  logger.error(`Error in afterAuth hook: ${error}`);
  res.status(500).send('Internal Server Error');
  return;
}
``` [4](#0-3) 

At this point the session token has already been verified as authentic and the access token has already been exchanged and persisted via `config.sessionStorage.storeSession(offlineSession)`. [5](#0-4)  The `afterAuth` hook is an auxiliary, app-defined side effect (e.g. webhook registration) that has no bearing on the correctness or authenticity of the incoming request — exactly analogous to the CSR module's fee-distribution step in `PostTxProcessing`, which is unrelated to the validity of the underlying transaction but is allowed to revert it anyway. Here, an unrelated failure in `afterAuth` is allowed to revert (reject) an otherwise valid, already-authenticated request.

Additionally, `callAfterAuthHook` runs through `IdempotentPromiseHandler.handlePromise`, which marks the `sessionToken` identifier as "already attempted" before the hook resolves and only clears it after a fixed TTL (60 seconds), rather than clearing it on failure. [6](#0-5)  This means a failing `afterAuth` hook cannot be safely retried for the same token within that window, compounding the outage for that request/token.

### Impact Explanation
A transient or unrelated failure in an app's `afterAuth` hook causes a fully authenticated request (valid session token, valid access token already stored) to be rejected with `500`, rather than proceeding to the actual route handler. This is a denial-of-service of the authentication middleware for otherwise legitimate merchant/session requests, triggered any time a fresh offline (or online) token must be exchanged — i.e., whenever no active stored session exists yet, which happens on first install and after session expiry/rotation. The app owner's business logic (webhook registration, external calls, etc.) becomes a single point of failure for the authentication path itself.

### Likelihood Explanation
This occurs whenever `config.hooks.afterAuth` is configured (a common and documented pattern for registering webhooks) and that hook throws for any reason not related to the request's authenticity — including transient network/API failures on Shopify's own webhook registration endpoints. No attacker action is required; it is a reliability/availability flaw reachable by normal merchant traffic during routine token-exchange flows.

### Recommendation
Do not let failures in `afterAuth` (or other post-authentication side-effect hooks) affect the response to the already-authenticated request. Log the error and still call `next()` so the request proceeds normally, consistent with how the library's webhook processing intentionally always responds to Shopify even if a handler throws. Consider surfacing `afterAuth` failures asynchronously (e.g., via retries or monitoring) instead of coupling them to the request/response lifecycle of `performTokenExchange`.

### Proof of Concept
1. Configure a Shopify Express app with `hooks.afterAuth` that calls `shopify.registerWebhooks({session})` (the documented pattern for token exchange). [7](#0-6) 
2. Simulate `afterAuth` throwing (e.g. Shopify's webhook registration GraphQL call returns a transient 5xx, or any exception in developer code inside the hook).
3. Send a request with a valid, freshly-issued session token requiring a new offline token exchange (no active stored session yet).
4. Observe that `performTokenExchange` completes the token exchange and stores the session, but then returns `500 Internal Server Error` and never calls `next()`, per [4](#0-3) , denying the legitimate request despite a valid, already-persisted session.

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }

  private async clearStaleIdentifiers() {
    this.identifiers.forEach((date, identifier, map) => {
      if (Date.now() - date > IDENTIFIER_TTL_MS) {
        map.delete(identifier);
      }
    });
  }
