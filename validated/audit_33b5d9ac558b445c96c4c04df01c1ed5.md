### Title
Missing `ALLOW_CANCEL_ALL_UNFREEZE_V2` Feature-Toggle Check in TVM `cancelAllUnfreezeV2` Path Allows Bypass of Committee Gate - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/CancelAllUnfreezeV2Processor.java`)

### Summary
`CancelAllUnfreezeV2Contract` is a committee-gated feature: it can only be used once the `ALLOW_CANCEL_ALL_UNFREEZE_V2` proposal has been approved, which is enforced via `DynamicPropertiesStore.supportAllowCancelAllUnfreezeV2()`. The normal transaction-level actuator, `CancelAllUnfreezeV2Actuator.validate()`, correctly checks this toggle before allowing execution, but the equivalent smart-contract/TVM-facing code path, `CancelAllUnfreezeV2Processor.validate()`, omits this check entirely. This mirrors the Mochi finding, where `withdrawLock()` failed to verify the `lockCrv` toggle before performing a state-changing operation.

### Finding Description
`CancelAllUnfreezeV2Actuator.validate()` (used when a regular transaction of type `CancelAllUnfreezeV2Contract` is broadcast) explicitly requires the feature toggle to be enabled: [1](#0-0) 

However, the corresponding TVM native-contract processor, invoked when a smart contract calls the `cancelAllUnfreezeV2()` precompiled/native opcode, performs no such check: [2](#0-1) 

The processor's `validate()` only checks that the repository is non-null, that the address is valid, and that the account exists — it never calls `repo.getDynamicPropertiesStore().supportAllowCancelAllUnfreezeV2()`. Compare this to sibling processors such as `FreezeBalanceV2Processor`/`UnfreezeBalanceV2Processor`, which gate similarly-versioned functionality via `supportUnfreezeDelay()`... but `CancelAllUnfreezeV2Processor` has no analogous gate for its own dedicated toggle at all.

`supportAllowCancelAllUnfreezeV2()` is defined as: [3](#0-2) 

This flag is meant to represent whether the committee has enabled the `CancelAllUnfreezeV2` feature (via the `ALLOW_CANCEL_ALL_UNFREEZE_V2` proposal), which also requires `UNFREEZE_DELAY_DAYS` to already be non-zero: [4](#0-3) 

Since the TVM entry point (`Program.cancelAllUnfreezeV2`, referenced 11 times in `Program.java`) instantiates and calls `CancelAllUnfreezeV2Processor` directly, a smart contract can invoke this state-mutating opcode before the committee formally enables `ALLOW_CANCEL_ALL_UNFREEZE_V2`, or on any network/fork where the toggle has intentionally been left disabled, bypassing the intended feature gate.

### Impact Explanation
This lets unprivileged smart-contract callers exercise `cancelAllUnfreezeV2` functionality (which cancels pending unfreeze requests and re-locks funds as frozen resource, affecting global bandwidth/energy/TRON-power weight accounting) through the TVM path even when the feature has not been enabled by governance for ordinary transactions. This is a state/accounting-divergence issue: normal `CancelAllUnfreezeV2Contract` transactions are blocked pre-activation, but contract-invoked calls are not, creating inconsistent enforcement of the network-wide feature flag and letting resource/weight state mutate outside the committee-controlled rollout window.

### Likelihood Explanation
Reachability requires only deploying/calling a smart contract that exercises the corresponding TVM native contract call for `cancelAllUnfreezeV2` (an unprivileged, publicly available capability once the underlying opcode is registered) — no special permissions are needed. The only gating condition is whether the opcode itself is enabled at the VM/fork level, which is separate from the `ALLOW_CANCEL_ALL_UNFREEZE_V2` dynamic property being asserted in `validate()`.

### Recommendation
Add `if (!repo.getDynamicPropertiesStore().supportAllowCancelAllUnfreezeV2()) { throw new ContractValidateException(...); }` to `CancelAllUnfreezeV2Processor.validate()`, mirroring the check already present in `CancelAllUnfreezeV2Actuator.validate()`, so both the transaction and TVM native-contract paths enforce the same committee-controlled feature toggle.

### Proof of Concept
1. On a network/state where `ALLOW_CANCEL_ALL_UNFREEZE_V2` has not been enabled (`getAllowCancelAllUnfreezeV2() == 0`), submitting a standalone `CancelAllUnfreezeV2Contract` transaction fails validation with "Not support CancelAllUnfreezeV2 transaction, need to be opened by the committee" as enforced in `CancelAllUnfreezeV2Actuator.validate()` (lines 130-133).
2. If the TVM opcode invoking `Program`'s `cancelAllUnfreezeV2` handler (which constructs a `CancelAllUnfreezeV2Processor` and calls its `validate`/`execute`) is reachable, the same account state, when driven through a contract call instead of a top-level transaction, passes `CancelAllUnfreezeV2Processor.validate()` unconditionally (lines 27-42) — it never inspects `supportAllowCancelAllUnfreezeV2()` — and proceeds to `execute()`, mutating `unfrozenV2` lists and total resource weights, contrary to the governance gate.
