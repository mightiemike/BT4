This is a direct analog to the CBridge bug class: the `register` function accepts `given_deposit >= required_deposit` but only needs `required_deposit`, yet on the successful (`Entry::Vacant`) path it never refunds the excess — the entire `given_deposit` is retained by the `AddressRegistrar` contract, which has no withdraw/owner method to recover it.

### Title
Excess attached deposit is permanently trapped (not refunded) in `AddressRegistrar::register` - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar::register` function only validates that the attached deposit is *at least* the required storage cost, but on the successful registration path it never refunds the difference between what was attached and what was actually required, unlike the failure/collision path which does refund the full deposit.

### Finding Description
`register` computes `required_deposit` from the storage bytes needed to store the address mapping, then checks `given_deposit < required_deposit` to reject underpayment [1](#0-0) . If the deposit is sufficient and the address slot is `Entry::Vacant`, the mapping is inserted and the function returns without ever transferring back the surplus (`given_deposit - required_deposit`) [2](#0-1) . This is inconsistent with the `Entry::Occupied` (collision) branch, which explicitly refunds the *entire* `given_deposit` back to the caller because no storage was written [3](#0-2) . The comment "Transfer the deposit back to the caller since no storage was updated" only appears in the failure branch, confirming the success branch was never intended to keep more than `required_deposit`, yet it silently does.

Reachability: `register` is a `#[payable]` public method, callable by any account via a standard `FunctionCall` transaction with an attached deposit — this is exactly the kind of unprivileged, single-transaction path the report targets. It is also invoked internally by the `WalletContract`'s `address_check_callback`/eth-emulation flow when handling ETH base-token transfers routed through this registrar.

### Impact Explanation
Any signer who attaches more NEAR than the exact storage cost when calling `register` permanently loses the excess: it becomes part of the `AddressRegistrar` contract's own account balance. The contract exposes no `withdraw`, `owner`, or admin method to move that balance out [4](#0-3) , so the funds are effectively frozen forever — worse than the original CBridge finding, where the excess could at least be recovered by any party. This is a concrete, transaction-triggered loss/freezing of user funds.

### Likelihood Explanation
High likelihood: overpayment is the natural/default behavior for any caller (human or contract) that doesn't compute the exact per-byte storage cost precisely (e.g., attaching a round NEAR amount, or reusing a generic "storage deposit" constant). The existing test suite even attaches deposits far larger than required (`NearToken::from_near(3)` vs. an actual requirement on the order of 0.0003 NEAR) and explicitly asserts the caller is *not* refunded the excess in the success case [5](#0-4) , and a similar pattern appears in `test_register_without_deposit`, where an exact deposit is used only because the test controls it precisely [6](#0-5) .

### Recommendation
In the `Entry::Vacant` success branch of `register`, compute `refund = given_deposit.checked_sub(required_deposit)` and, if non-zero, issue a `promise_batch_action_transfer` back to `env::predecessor_account_id()`, mirroring the refund logic already present in the `Entry::Occupied` branch. Alternatively, panic if `given_deposit != required_deposit` (exact-match requirement), consistent with the mitigation pattern recommended in the referenced CBridge report (changing `>=`/`<` checks to strict equality where no refund path exists).

### Proof of Concept
1. Call `AddressRegistrar::register({"account_id": "alice.near"})` attaching `NearToken::from_near(3)` (or any amount greater than the actual per-byte storage cost, which is on the order of `~0.0003` NEAR for a short account id).
2. The call succeeds, returns the computed address, and inserts the mapping (`Entry::Vacant` branch).
3. Observe that the caller's balance decreased by the full `3 NEAR` attached deposit, not just the storage cost — this matches the assertion in `test_caller_refunds`: `pre_tx_account_balance - post_tx_account_balance >= deposit_amount` for the success case [5](#0-4) .
4. There is no method on `AddressRegistrar` to withdraw the excess NEAR now sitting in the contract's account, so those funds are permanently lost to the caller and unrecoverable by anyone.

/// Test asserting the address registrar requires a deposit.
#[tokio::test]
async fn test_register_without_deposit() -> anyhow::Result<()> {
    let TestContext { worker, address_registrar, .. } = TestContext::new().await?;

    let method = "register";
    let args = br#"{"account_id": "birchmd.near"}"#;
    let result = address_registrar.call(method).args(args.to_vec()).transact().await?;
    assert!(result.is_failure(), "Call without deposit must fail");

    let pre_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    let deposit_amount = NearToken::from_yoctonear(320000000000000000000);
    let result = worker
        .root_account()?
        .call(address_registrar.id(), method)
        .args(args.to_vec())
        .deposit(deposit_amount)
        .transact()
        .await?;

    let output: Option<String> = result.json()?;
    assert_eq!(output.as_deref(), Some("0x4bfcff9a964925adf801c866f6ada98bd7ec40ca"));
    let post_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    assert!(
        post_tx_account_balance.as_yoctonear() - pre_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );
