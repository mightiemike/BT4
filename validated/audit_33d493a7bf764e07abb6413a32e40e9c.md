### Title
Missing negative/staleness validation on LINK/ETH price feed in VRF v2 fee estimation - (File: core/services/vrf/v2/listener_v2_log_processor.go)

### Summary
The VRF v2 off-chain listener reads the LINK/ETH aggregator via `latestRoundData()`-equivalent (`LatestRoundData`) to estimate the LINK cost of fulfilling a request paid in LINK, but only checks that the returned answer is exactly zero, and never checks that it is positive or that the round is fresh (non-stale), unlike the sequencer/staleness guidance Chainlink itself documents for consumers of price feeds.

### Finding Description
In `estimateFee`, the LINK/ETH price is fetched directly from the aggregator and its `Answer` field is passed straight into `EstimateFeeJuels` with no positivity or staleness check: [2](#0-1) 

`EstimateFeeJuels` only guards against an exact-zero price (`Cmp(big.NewInt(0)) == 0`), which does not catch a negative `Answer` (a corrupted/misbehaving aggregator round can return a negative int256) or a stale round whose `UpdatedAt`/`AnsweredInRound` indicates outdated data: [3](#0-2) 

If `weiPerUnitLink` were negative, the division in `EstimateFeeJuels` (`numerator.Quo(numerator, weiPerUnitLink)`) would silently produce a negative `costJuels`, and no staleness metadata (`UpdatedAt`, `AnsweredInRound`) from the round is ever inspected, matching the reported bug class ("missing check for price > 0" and "price staleness not checked").

### Impact Explanation
This estimate is used purely off-chain by the VRF listener to decide fee-related behavior when a request is paid in LINK; it is not the source of truth for on-chain payment (the VRF coordinator contract performs its own payment calculation on-chain). Consequently, a corrupted/stale LINK/ETH feed read here would primarily cause the node to make an incorrect internal cost estimate (potentially skipping fulfillable requests or misjudging fee suitability), rather than a direct fund-loss or unauthorized on-chain action. This limits the impact relative to the High-impact framing in the original report, which concerned protocol-level minting/redeeming decisions.

### Likelihood Explanation
Low — requires the external LINK/ETH Chainlink aggregator itself to report a negative or stale round, which is an edge case dependent on aggregator misbehavior/compromise, not something triggerable by an unprivileged user of the chainlink node.

### Recommendation
In `estimateFee` (`core/services/vrf/v2/listener_v2_log_processor.go`), validate the round data before use: reject non-positive `Answer` (not just zero), and reject rounds whose `UpdatedAt` exceeds a configured heartbeat/staleness threshold for the specific LINK/ETH feed, mirroring the `TokenPriceStalenessThreshold` pattern already used in the CCIP `FeeQuoter` ( [4](#0-3) ).

### Proof of Concept
Not independently reproducible from static analysis alone — would require simulating an aggregator contract returning `Answer < 0` (or a stale `UpdatedAt`) to the `lsn.aggregator.LatestRoundData` call in `estimateFee` and observing that `EstimateFeeJuels` does not reject it (only the `== 0` case is rejected), given the code paths cited above.

**Caveat:** Given the constrained impact (off-chain estimate only, not an on-chain trust-boundary bypass) and the low likelihood, this finding is a weak analog and may not meet the report's threshold for a valid, high-confidence finding — flagging this uncertainty explicitly since I could not trace all downstream consumers of `estimateFee`'s return value within the available tool budget to confirm whether it gates any privileged/unsafe transaction submission.

// EstimateFeeJuels estimates the amount of link needed to fulfill a request
// given the callback gas limit, the gas price, and the wei per unit link.
// An error is returned if the wei per unit link provided is zero.
func EstimateFeeJuels(callbackGasLimit uint32, maxGasPriceWei, weiPerUnitLink *big.Int) (*big.Int, error) {
	if weiPerUnitLink.Cmp(big.NewInt(0)) == 0 {
		return nil, errors.New("wei per unit link is zero")
	}
	maxGasUsed := big.NewInt(int64(callbackGasLimit + GasProofVerification))
	costWei := maxGasUsed.Mul(maxGasUsed, maxGasPriceWei)
	// Multiply by 1e18 first so that we don't lose a ton of digits due to truncation when we divide
	// by weiPerUnitLink
	numerator := costWei.Mul(costWei, big.NewInt(1e18))
	costJuels := numerator.Quo(numerator, weiPerUnitLink)
	return costJuels, nil
}
