### Title
Permanent loss of bridged funds when a CEA (contract) recipient doesn't implement `executeUniversalTx` after a successful PRC20 deposit - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
For `isCEA` inbounds whose recipient is a deployed smart contract, `ExecuteInboundFundsAndPayload` first mints (deposits) PRC20 tokens to the recipient address and commits that state change, then separately calls `executeUniversalTx` on the recipient. If the recipient contract doesn't implement `executeUniversalTx` (or otherwise reverts), the already-minted tokens are permanently stranded: the codebase explicitly disables the automatic `INBOUND_REVERT` path for `isCEA` failures, and the manual `RESCUE_FUNDS` path is only eligible when the deposit itself (the first `PcTx`) failed — not when the deposit succeeded but the subsequent contract call failed.

### Finding Description
In `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, for a non-UEA `isCEA` recipient with contract code (`isSmartContract=true`), the deposit runs unconditionally on the outer `sdkCtx` and is committed: [1](#0-0) 

Only *after* this committed deposit does the code attempt to call `executeUniversalTx` on the recipient contract, wrapped in a `CacheContext` that only protects the fee-deduction step — the deposit itself is outside that cache and stays committed regardless of the outcome of this call: [2](#0-1) 

If the recipient contract does not implement `executeUniversalTx` (wrong selector) or otherwise reverts, `contractErr != nil` and the `PcTx` for this step is marked `"FAILED"`, but the function still returns `nil` — no revert outbound is created: [3](#0-2) 

This is a deliberate design choice, called out explicitly in the code: "isCEA failures never create an INBOUND_REVERT outbound": [4](#0-3) 

The only alternative recovery mechanism, `AttachRescueOutboundFromReceipt`, explicitly requires the *deposit itself* (i.e., `PcTx[0]`) to have failed for CEA inbounds — it is not triggered when the deposit succeeded and only the follow-up contract call failed: [5](#0-4) 

The same pattern (deposit commits, then a best-effort contract call that can fail without any refund) recurs in `execute_inbound_gas_and_payload.go`.

### Impact Explanation
Any user (or dApp acting on a user's behalf) submitting a cross-chain deposit through the gateway controls the `Inbound.recipient` and `isCEA` fields. If that recipient is set to a smart contract that does not implement the `executeUniversalTx(...)` interface (e.g., a plain token contract, DEX pool, or any unrelated deployed contract), the PRC20 tokens are minted into that contract's balance with no way for the protocol to retrieve them: no automatic `INBOUND_REVERT` is generated (explicitly excluded for `isCEA`), and the manual rescue path requires the deposit to have failed, which it did not. The funds are effectively permanently locked in a contract that has no protocol-level awareness of or entitlement to them — a direct analog to the C4 M-08 "funds lost when the receiver doesn't implement the expected interface" bug class, except here the loss is unconditional and unrecoverable rather than merely reverting the transaction.

### Likelihood Explanation
This requires no privileged access or validator collusion — it is triggered purely by an ordinary user's inbound deposit with attacker/user-controlled `recipient` and `isCEA=true` parameters. It can happen accidentally (a user or wallet UI mis-specifying a recipient) or be intentionally exploited to strand funds sent to a victim (e.g., a phishing dApp instructing a user to bridge funds to a recipient address that looks like a UEA but is actually a contract lacking the interface). Given deposits are honestly voted in by honest Universal Validators (in scope), and the destination-side failure is deterministic and permanent, likelihood of triggering and impact severity are both high.

### Recommendation
- Wrap the PRC20 deposit and the `executeUniversalTx` call for `isCEA` smart-contract recipients in the same cache context, so a failed `executeUniversalTx` call also discards the deposit, consistent with the non-CEA `FUNDS_AND_PAYLOAD` path.
- Alternatively, when the deposit succeeds but `executeUniversalTx` fails for a smart-contract CEA recipient, create an `INBOUND_REVERT` outbound (or make the deposit's `PcTx[0]` reflect the overall failure so the existing `RESCUE_FUNDS` path becomes eligible).
- Ensure the rescue-eligibility check in `AttachRescueOutboundFromReceipt` also covers the case where the deposit succeeded but the subsequent contract call failed, not just a failed first `PcTx`.

### Proof of Concept
1. Attacker/user submits (or a validator honestly observes/votes) an `Inbound` with `TxType=FUNDS_AND_PAYLOAD`, `isCEA=true`, `Amount>0`, and `Recipient` set to the address of an already-deployed contract on Push Chain that has bytecode but does not implement `executeUniversalTx` (e.g., a generic ERC20 or any unrelated contract).
2. Once 2/3+ Universal Validators vote the inbound (honest validators, in-scope), `ExecuteInboundFundsAndPayload` runs: `depositPRC20` mints tokens to `Recipient` and commits (`x/uexecutor/keeper/execute_inbound_funds_and_payload.go:89-100`).
3. `isSmartContract=true` path calls `CallExecuteUniversalTx` on `Recipient`; since the recipient contract lacks the function/selector, the EVM call reverts, `contractErr != nil` (`execute_inbound_funds_and_payload.go:240-274`).
4. The `PcTx` is recorded as `FAILED`, function returns `nil`. No `INBOUND_REVERT` outbound is created (explicitly excluded for `isCEA`).
5. `AttachRescueOutboundFromReceipt`'s rescue eligibility check for CEA fails because `PcTx[0]` (the deposit) is `"SUCCESS"`, not `"FAILED"` (`create_outbound.go:247-250`), so rescue is also unavailable.
6. Result: PRC20 tokens are permanently minted into a contract with no interface to use, move, or return them — permanent loss of user funds with no code path to recovery.
