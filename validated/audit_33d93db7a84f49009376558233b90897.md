## Title
Reachable division-by-zero DoS in `RepositoryImpl.calculateGlobalEnergyLimit()` when `totalEnergyWeight` is zero - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()` divides by `totalEnergyWeight` and only guards the zero-denominator case with a Java `assert` statement, which is a no-op in production (assertions are disabled by default unless the JVM is started with `-ea`). This mirrors the Backd `KeeperGauge._calcTotalClaimable()` bug class: a state (`totalEnergyWeight == 0`) that the code assumes cannot occur is not actually prevented from occurring, and when it does occur the division throws `ArithmeticException`, crashing/reverting execution wherever the function is invoked.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit()`: [1](#0-0) 

only checks `assert totalEnergyWeight > 0;` before dividing:
```
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
assert totalEnergyWeight > 0;
if (hardenResourceCalculation()) {
  return BigInteger.valueOf(energyWeight)
      .multiply(BigInteger.valueOf(totalEnergyLimit))
      .divide(BigInteger.valueOf(totalEnergyWeight))
      .longValueExact();
}
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```
This is *not* the same protection used in the sibling implementation `EnergyProcessor.calculateGlobalEnergyLimit()`, which explicitly checks the flag/value and short-circuits to `0`: [2](#0-1) 

and its V2 counterpart, which properly guards with `if (totalEnergyWeight == 0) { return 0; }`: [3](#0-2) 

Assertions in Java are disabled by default at runtime unless `-ea` is passed to the JVM; standard production deployments (and the default `java -jar` invocation for a full node) run with assertions off. Consequently, `assert totalEnergyWeight > 0` provides **no runtime protection** in a production java-tron node — exactly the analog of the Backd finding where a critical invariant (`perPeriodTotalFees[i] != 0`) was assumed but never actually enforced, allowing a division-by-zero DoS once the assumption is violated.

`totalEnergyWeight` is a globally shared, mutable accounting variable adjusted by ordinary user actions (freeze/unfreeze energy, delegate/undelegate resources), via the same mechanisms used by `FreezeBalanceActuator`, `UnfreezeBalanceActuator`, `FreezeBalanceV2Actuator`, `UnfreezeBalanceV2Actuator`, `DelegateResourceActuator`, `UnDelegateResourceActuator`, and their native-contract processors (all reference `addTotalEnergyWeight`/`saveTotalEnergyWeight` per the repo-wide grep of `RepositoryImpl.java`, `ContractState.java`, and the actuator/native-contract files). If all energy-freezing accounts on the chain (or on a private/side/consensus-test network) unfreeze their energy — an ordinary, unprivileged sequence of transactions — `totalEnergyWeight` can reach `0`. Once it does, any subsequent call into `calculateGlobalEnergyLimit()` for an account that still has legacy (`getAllFrozenBalanceForEnergy() >= TRX_PRECISION`) frozen energy balance recorded (e.g. residual state or a race where the weight/balance accounting diverges) triggers an integer or `BigInteger` "divide by zero" exception.

### Impact Explanation
`ArithmeticException` (integer divide, or `BigInteger.divide` throwing `ArithmeticException: BigInteger divide by zero`) thrown from a repository/state-accounting helper used during TVM execution (`RepositoryImpl`/`ContractState`, reachable from `VMActuator`) is not a normal, recoverable contract-level revert — it is an unexpected Java exception surfacing from core resource-limit accounting code. Depending on where the exception is caught (or not caught) up the call stack, this can:
- Cause smart-contract calls that indirectly trigger energy-limit computation to fail unpredictably for all users touching the affected account/global state, effectively halting a legitimate, previously-working operation (a state/halt class impact).
- Produce inconsistent behavior/divergence between nodes if assertions are enabled on some nodes (throwing `AssertionError` in the `assert` line itself) and not others (proceeding to the unguarded division and throwing `ArithmeticException`), which is a consensus-divergence risk class.

This satisfies the "invalid-state/divergence/halt" impact category required by the analog rules.

### Likelihood Explanation
Likelihood is moderate: it requires the network-wide `totalEnergyWeight` accounting to hit exactly zero, which is unusual on Tron mainnet (given its large validator/staking base) but plausible on smaller networks (private chains, testnets, or side-chains built on this codebase) and is reachable purely through sequences of ordinary, unprivileged freeze/unfreeze/delegate transactions — no privileged role is required, unlike the original Backd report which required the `InflationManager`'s `kill()`/`advanceEpoch()`. The reliance on a disabled-by-default `assert` for correctness (rather than an explicit runtime check) is the root design flaw that makes this a real latent bug, independent of how often the zero-weight state is reached in practice.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit()` with an explicit runtime check that short-circuits to `0` (matching the pattern already used in `EnergyProcessor.calculateGlobalEnergyLimit()` / `calculateGlobalEnergyLimitV2()`):
```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
if (totalEnergyWeight <= 0) {
  return 0;
}
```
so the guard is actually enforced in production builds regardless of the `-ea` JVM flag.

### Proof of Concept
1. Deploy/operate a java-tron node without `-ea` (default production configuration).
2. Drive the chain (or a private/test network built from this codebase) into a state where `DynamicPropertiesStore.getTotalEnergyWeight()` returns `0` — e.g., by having all accounts that froze balance for energy submit `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`/`UnDelegateResourceActuator` transactions until the global total energy weight counter reaches zero.
3. Trigger any TVM/actuator code path that calls `RepositoryImpl.calculateGlobalEnergyLimit(accountCapsule)` for an account whose `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` (reachable via ordinary contract execution/energy-limit queries in `VMActuator`/`ContractState`, per the call sites found in `actuator/src/main/java/org/tron/core/vm/program/ContractState.java` and `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`).
4. Because `assert totalEnergyWeight > 0;` is disabled at runtime, execution proceeds to `.divide(BigInteger.valueOf(totalEnergyWeight))` (hardened path) or `totalEnergyLimit / totalEnergyWeight` (double path), both of which throw `ArithmeticException` for a zero denominator, causing the calling operation to fail unexpectedly.

*Note:* Full confirmation of exact reachability from external, unprivileged transactions (i.e., a concrete sequence of transactions guaranteed to zero out `totalEnergyWeight` on live Tron mainnet) would require deeper tracing of `DynamicPropertiesStore` weight-accounting invariants across all freeze/unfreeze/delegate code paths, which was not fully completed within the available tool budget — this should be verified with a live/testnet reproduction before treating likelihood as more than moderate.
