### Title
Renderer-Accessible HTTP Cache serves stale/cross-origin-tainted cached responses without freshness or CORS/ORB/CORP revalidation - ([File: services/network/public/cpp/shared_http_cache_client.cc])

### Summary
The new "Renderer-Accessible HTTP Cache" lets a renderer process read cached HTTP responses (images/scripts/styles/fonts) directly from an isolated SQLite database via `sqlite_vfs`, bypassing IPC to the network service on cache hits. `DatabaseBackend::ParseAndDecode()` reconstructs a `URLResponseHead` and body straight from the stored pickle and serves it to the caller with no check that the entry is still fresh, and no re-application of the security decisions (CORS, ORB, CORP, SRI) that would normally be made by the network service pipeline for the *current* request. This is structurally the same defect as the audited oracle bug: data that was valid/authorized under a past context (a past `roundId`/fetch) is reused as if it were the current, re-validated answer, without checking that the "round" (here: freshness lifetime and security mode) still matches.

### Finding Description
`DatabaseBackend::ParseAndDecode()` in `services/network/public/cpp/shared_http_cache_client.cc` explicitly documents the missing checks: [1](#0-0) 

It then unconditionally builds a `URLResponseHeadPtr` from the cached headers and hands the decoded body back to the caller: [2](#0-1) 

`SharedHttpCacheClientImpl::Find()` only gates entry into this path on `IsRequestEligibleForSharedHttpCacheLookup()`, which merely checks scheme/method/destination/load-flags — it performs no per-request CORS mode, credentials mode, or origin comparison against what was true when the entry was written: [3](#0-2) [4](#0-3) 

This is the same root-cause pattern as the `wstETHChainlinkOracle._calculateAnswer()` bug: the consumer trusts a previously-recorded value (Chainlink `answer`/`roundId` in the original report; here, a cached `URLResponseHead`/body keyed only by URL) without re-validating that the value is still "current" for the present caller/context — no check of `answeredInRound >= roundId` there, no check of freshness lifetime or of CORS/ORB/CORP applicability here. The accompanying browser test file (`content/browser/network/renderer_accessible_http_cache_browsertest.cc`) confirms the feature is specifically exercised with cross-origin ACAO/CORP test resources (`acao_wildcard.js`, `acao_origin.js`, `corp_same_origin.js`, `corp_cross_origin.js`), i.e. resources whose cacheability/exposure to a given requesting origin depends on response headers evaluated by CORS/CORP/ORB machinery that this fast path skips: [5](#0-4) 

### Impact Explanation
If a response was written to the shared cache in one security context (e.g., fetched with `Access-Control-Allow-Origin: https://a.test`, or with a `Cross-Origin-Resource-Policy: same-origin` header, under one requesting origin/CORS mode) and a later request for the *same URL* is made by a different, less-privileged origin whose request would normally be blocked or its body opaque-filtered by CORS/ORB/CORP in the network service, the cache-hit fast path in `ParseAndDecode()` returns the full response head and decoded body directly to the renderer with no re-check of these policies. That is a cross-origin resource disclosure / CORS-ORB bypass (reading response bytes an attacker's origin should never see), which matches the "SOP bypass / cross-origin disclosure" acceptance bar. It would also let a stale, already-invalidated resource be served indefinitely to any page requesting that URL, since freshness (`Cache-Control`/`Expires`/`Age`) is never checked on this path either.

### Likelihood Explanation
The lookup happens for the common `kImage`/`kScript`/`kStyle`/`kFont` subresource destinations on ordinary `https://` GET requests — i.e., every page load can trigger it, and no special flags/policies are required. The TODOs make explicit that the security checks are simply not implemented yet (`crbug.com/473666511`), i.e. this is a currently-shipping gap in a code path reachable purely from web content making a subresource request whose URL happens to match a prior cross-origin-restricted or CORP-restricted cache entry.

### Recommendation
Before returning a `Response` from `DatabaseBackend::ParseAndDecode()`/`FindResource()`, revalidate: (1) freshness per `Cache-Control`/`Expires`/`Age`/`Date` and fall back to network validation instead of serving directly if stale, and (2) re-apply CORS (mode/credentials/ACAO), Cross-Origin-Resource-Policy, and ORB filtering for the *current* request's origin and mode, exactly as the network service's normal `URLLoader`/`CorsURLLoader` path would, rejecting or opaque-filtering the cached response when it does not match. This mirrors the audit's fix of validating `answeredInRound >= roundId` before trusting a cached oracle value — here, validating current request context/time against the stored entry's authorization/freshness before trusting the cached body.

### Proof of Concept
Not independently exploitable/verifiable in this ask-only session (no build/runtime access). Conceptually:
1. Site `https://a.test` causes a `<script>` (or `<img>`) fetch of `https://cross.test/resource.js` returned with `Access-Control-Allow-Origin: https://a.test` (or `Cross-Origin-Resource-Policy: same-origin`), which gets written to the shared SQLite cache per `IsRequestEligibleForSharedHttpCacheWrite()`.
2. A different, unrelated origin `https://evil.test` later requests the same URL `https://cross.test/resource.js` as a subresource. `IsRequestEligibleForSharedHttpCacheLookup()` only checks method/scheme/destination/load-flags, so the lookup proceeds.
3. `DatabaseBackend::FindResource()`/`ParseAndDecode()` returns the full cached body/headers straight to `evil.test`'s renderer without re-checking ACAO/CORP for the `evil.test` origin, per the missing-checks TODO at `services/network/public/cpp/shared_http_cache_client.cc:260-262`, disclosing response bytes evil.test should not receive.

bool IsRequestEligibleForSharedHttpCacheLookup(const ResourceRequest& request) {
  if (!IsRequestEligibleForSharedHttpCacheWrite(request)) {
    return false;
  }

  // Requests that bypass the HTTP cache (e.g. shift-reload) or force cache
  // validation (e.g. reload) must not be read directly from the cache without
  // network validation.
  if (request.load_flags &
      (net::LOAD_BYPASS_CACHE | net::LOAD_VALIDATE_CACHE)) {
    return false;
  }

  // Revalidation requests cannot be served directly from the shared cache
  // without network validation.
  if (request.is_revalidating || request.revalidation_etag.has_value() ||
      request.revalidation_last_modified.has_value()) {
    return false;
  }

  return true;
}
