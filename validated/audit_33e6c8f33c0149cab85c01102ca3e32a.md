### Title
Front-runnable `Factory.initialize()` grants attacker ownership of the UEA Factory system contract - (File: x/uexecutor/keeper/genesis.go)

### Summary
The `ue` module's Factory contract (deployed at the reserved address `0x00000000000000000000000000000000000000eA`) is deployed at genesis with bytecode and EIP-1967 proxy/implementation storage slots set directly, but its `Ownable` owner is left unset. The contract's `initialize(address initialOwner)` function follows the OZ `Initializable` pattern with no other access control, so any externally-owned account can call it in a normal transaction after chain start and become the Factory's owner.

### Finding Description
`deployFactoryEA` runs during `InitGenesis` and deploys three pieces: the Factory implementation, the `ProxyAdmin`, and the Factory `ERC1967`-style proxy, using `SetAccount`/`SetCode`/`SetState` to directly inject bytecode and storage [5](#0-4) . The `ProxyAdmin`'s owner slot is explicitly initialized to `PROXY_ADMIN_OWNER_ADDRESS_HEX` at genesis [3](#0-2) , proving the team is aware that owner state must be pinned during genesis for security-critical contracts.

However, the Factory implementation contract exposes `initialize(address initialOwner)` [4](#0-3) , and no equivalent direct storage write sets the Factory's owner during `deployFactoryEA`. The only place `initialize` is actually invoked is in test helper code, called manually right after genesis in the same test flow [6](#0-5) . There is no analogous call anywhere in the production module wiring (`InitGenesis`, `BeginBlock`, module `RegisterServices`, etc. — confirmed by exhaustive grep for `"initialize"` across the repo, which only matches the ABI definition and the test helper).

This exactly mirrors the reported bug class: a proxy/implementation contract following the unguarded OZ `Initializable` pattern is deployed in one step (genesis) but its `initializer`-gated setup call is expected to happen in a separate, later step. Because genesis in a live chain is not an atomic multicall bundled with a subsequent `initialize` transaction, the window between block 1 (first block where the contract is live and reachable by ordinary users) and whenever/if the deployer submits their own `initialize` transaction is front-runnable by any unprivileged account watching the mempool.

Once an attacker becomes Factory owner via `initialize(attackerAddress)`, they gain access to every `onlyOwner`-style admin function exposed by the Factory ABI, most critically:
- `setUEAProxyImplementation(address)` — lets the attacker point every future UEA proxy at an attacker-controlled implementation [7](#0-6) .
- `registerNewChain` / `registerUEA` — lets the attacker register malicious chain/VM implementation mappings used when the `ue` module auto-deploys UEAs for inbound users [8](#0-7) .

Every unprivileged user's inbound transaction that requires a not-yet-deployed UEA calls `DeployUEAV2` → `CallFactoryToDeployUEA` → `factory.deployUEA(...)` [9](#0-8) , which is reached automatically from ordinary deposit/payload flows (`ExecuteInboundGas`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`, `ExecutePayload`) whenever `isDeployed == false` [10](#0-9) [11](#0-10) . If the attacker has swapped in a malicious `UEA_PROXY_IMPLEMENTATION`, every new UEA deployed after the takeover would execute attacker-controlled logic, exposing every future depositor's UEA (and the funds routed through `depositPRC20`/autoswap into it) to the attacker.

### Impact Explanation
This is a chain-wide, unprivileged, front-runnable takeover of the system contract that gates deployment and behavior of every Universal Executor Account (UEA) — the smart-account abstraction that all cross-chain inbound users rely on to hold and route funds on Push Chain. A successful takeover lets the attacker redirect UEA proxy implementation logic, letting them drain or hijack funds deposited into any newly deployed UEA thereafter (PRC20 deposits, gas swaps, universal payload execution). This satisfies "unauthorized UEA... execution," "unauthorized module-originated EVM execution," and "stealing/draining... of user or protocol-controlled funds" from the allowed impact list.

### Likelihood Explanation
Likelihood depends entirely on operational timing: if the legitimate deployer's `initialize(owner)` transaction is bundled with genesis or executed before the chain accepts any other transactions, the window doesn't exist. But nothing in the scoped code enforces this atomically — `deployFactoryEA` in `InitGenesis` never calls `initialize`, so the operational safety entirely depends on off-chain deployment discipline, exactly the scenario the external report calls out as unsafe. Any external, unprivileged actor monitoring the very first blocks after mainnet genesis (or a fresh testnet/localnet spin-up) can race to call `initialize` on `0x...ea` before the operator does.

### Recommendation
- Set the Factory owner directly via genesis storage write (as already done for `ProxyAdmin`) instead of relying on a subsequent `initialize()` call, eliminating the race entirely.
- Alternatively, if `initialize()` must remain callable post-genesis, restrict it via a module-only precompile-gated call, or make the deployment/initialization atomic within the same `InitGenesis` execution using a direct `DerivedEVMCall` in the same code path that deploys the bytecode.
- Add invariant/consistency checks (e.g., an integration test similar to `TestDeploySystemContracts_ReportEveryProxyAdminOwner`) that asserts the Factory's `Ownable` owner slot is non-zero and equals the expected admin address immediately after genesis, failing loudly if it is not.

### Proof of Concept
1. Start a fresh Push Chain node from genesis; `InitGenesis` runs `deployFactoryEA`, placing bytecode/proxy/impl at `0x00000000000000000000000000000000000000eA` with no owner set.
2. Before the legitimate operator's `initialize(operatorAddress)` transaction is included in a block, an attacker submits an ordinary EVM transaction calling `Factory.initialize(attackerAddress)` at the same address.
3. Because `initialize()` uses the unguarded `initializer` modifier (no `onlyOwner`/`onlyModule` gate) as shown in the ABI [4](#0-3) , this succeeds and the attacker becomes owner.
4. The attacker then calls `setUEAProxyImplementation(maliciousImpl)` [7](#0-6) , redirecting every future UEA proxy to attacker-controlled logic.
5. Any subsequent inbound deposit for a new sender triggers `DeployUEAV2` → deploys a UEA proxy pointing at the malicious implementation [12](#0-11) , after which the attacker's implementation controls that user's funds routed through `depositPRC20`/swap logic.

func deployFactoryProxy(ctx context.Context, evmKeeper types.EVMKeeper) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	proxyAddress := common.HexToAddress(types.FACTORY_PROXY_ADDRESS_HEX)
	proxyAdminOwner := common.HexToAddress(types.PROXY_ADMIN_ADDRESS_HEX)
	factoryImplAddress := common.HexToAddress(types.FACTORY_IMPL_ADDRESS_HEX)

	// Compute the code hash from the runtime bytecode
	codeHash := crypto.Keccak256(types.ProxyRuntimeBytecode)

	// Create the EVM account object
	evmAccount := statedb.Account{
		Nonce:    1,             // to prevent tx nonce=0 conflicts
		Balance:  new(uint256.Int), // zero balance by default
		CodeHash: codeHash,      // link to deployed code
	}

	// Set the EVM account with the factory proxy contract
	err := evmKeeper.SetAccount(sdkCtx, proxyAddress, evmAccount)
	if err != nil {
		panic("failed to set factory proxy contract account: " + err.Error())
	}

	// Store the runtime bytecode linked to the code hash
	evmKeeper.SetCode(sdkCtx, codeHash, types.ProxyRuntimeBytecode)

	// Update proxyAdmin Slot with the proxyAdmin owner address (left padded to 32 bytes)
	evmKeeper.SetState(sdkCtx, proxyAddress, types.PROXY_ADMIN_SLOT, common.LeftPadBytes(proxyAdminOwner.Bytes(), 32))

	// Update proxyImplementation Slot with the factory implementation address (left padded to 32 bytes)
	evmKeeper.SetState(sdkCtx, proxyAddress, types.PROXY_IMPLEMENTATION_SLOT, common.LeftPadBytes(factoryImplAddress.Bytes(), 32))
}

// CallFactoryToDeployUEA deploys a new UEA using factory contract
// Returns deployment response or error if deployment fails
func (k Keeper) CallFactoryToDeployUEA(
	ctx sdk.Context,
	from, factoryAddr common.Address,
	universalAccount *types.UniversalAccountId,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: deployUEA",
		"factory", factoryAddr.Hex(),
		"chain_namespace", universalAccount.ChainNamespace,
		"chain_id", universalAccount.ChainId,
		"owner", universalAccount.Owner,
	)

	abi, err := types.ParseFactoryABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse factory ABI")
	}

	abiUniversalAccount, err := types.NewAbiUniversalAccountId(universalAccount)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal account")
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,        // who is sending the transaction
		factoryAddr, // destination: FactoryV1 contract
		big.NewInt(0),
		nil,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"deployUEA",
		abiUniversalAccount,
	)
}
