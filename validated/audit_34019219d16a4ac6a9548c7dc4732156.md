**Rationale:**

The `PanicError`/`code_invariant_error` message text (built via `{:?}` Debug formatting in `third_party/move/move-vm/types/src/delayed_values/error.rs` and `types/src/error.rs`) never reaches the consensus-committed `TransactionInfo`. Tracing the exact path:

1. `VMOutput::try_materialize_into_transaction_output` converts a `PanicError` into `VMStatus::error(StatusCode::DELAYED_FIELD_OR_BLOCKSTM_CODE_INVARIANT_ERROR, Some(e.to_string()))`, which is returned as an `Err(VMStatus)` from the function — it is not embedded into a `TransactionOutput`. [1](#0-0) 

2. The same holds at the block-executor level: a `PanicError::CodeInvariantError(err_msg)` is mapped to `VMStatus::Error { status_code: DELAYED_FIELD_OR_BLOCKSTM_CODE_INVARIANT_ERROR, message: Some(err_msg), .. }`, which is only propagated as a fatal `Result::Err` from `execute_block`, causing a fallback to sequential execution or a full block discard — never a per-transaction committed output carrying the message. [2](#0-1) 

3. When the block-executor falls back and ultimately discards, transactions are discarded using only the `StatusCode` (`CommittedOutput::discard(error_code)`), not any message string. [3](#0-2) 

4. Crucially, the object that actually gets hashed and stored in the ledger accumulator, `TransactionInfo` (`TransactionInfoV0`/`V1`), stores a `status: ExecutionStatus` field, not a `VMStatus`. `ExecutionStatus::MiscellaneousError` only carries `Option<StatusCode>` — a bare enum discriminant, with no arbitrary message text. [4](#0-3) [5](#0-4) 

5. The conversion from `VMStatus` to the committed `TransactionStatus`/`ExecutionStatus` (`TransactionStatus::from_vm_status`) discards the message entirely and keeps only the `StatusCode`. [6](#0-5) 

Since only the `StatusCode` enum discriminant (a fixed, deterministic value determined by the code path taken, not by Debug-formatted data ordering) is embedded in `ExecutionStatus`/`TransactionInfo`, any non-determinism in the `{:?}`-formatted message string of a `PanicError` cannot propagate into the hashed, consensus-committed transaction info. The free-text message is only used in transient, non-consensus contexts: `println!`/`tracing::error!` logging, the `anyhow::Result<..., VMStatus>` error path that aborts/falls back execution, and the API's separate, non-hashed `vm_status: String` field in `api/types/src/transaction.rs` (used for human-readable display, not for ledger hashing). No unprivileged input path exists by which this message text corrupts committed state, proof material, or an authenticated response bound to a ledger root/version.
