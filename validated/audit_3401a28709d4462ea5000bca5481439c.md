### Title
`handle_poison_microblock` accepts any two same-key-signed microblock headers as "proof of fork" without verifying they actually conflict, enabling wrongful coinbase slashing/theft - (File: stackslib/src/chainstate/stacks/db/transactions.rs)

### Summary
`StacksChainState::handle_poison_microblock` (the consensus-critical, Clarity-invoked state transition executed for every `PoisonMicroblock` transaction) only checks that `mblock_header_1` and `mblock_header_2` recover to the same signer pubkey hash and that this pubkey hash is not yet matured; it never checks that the two headers actually collide (same `sequence`/`prev_block` with differing content). Because *every* microblock in a single anchored block's stream is signed by the *same* microblock private key, any two non-conflicting, honestly-published microblocks (e.g., real seq 0 and seq 1, never forked) satisfy `check_microblock_header_signer` and will be recorded as a valid poison report, wrongfully slashing an honest miner's coinbase.

### Finding Description
The claimed equality is: *a poison report accepted by `handle_poison_microblock` == a genuine double-signature/equivocation event where `mblock_header_1` and `mblock_header_2` are two microblocks the miner actually broadcast at a colliding sequence number as part of a real fork.*

Tracing `handle_poison_microblock`: [1](#0-0) 
only calls `check_microblock_header_signer`, which merely recovers each header's pubkey and requires `pkh1 == pkh2`: [2](#0-1) 

No comparison is ever made between `mblock_header_1` and `mblock_header_2` on `sequence`, `prev_block`, or `tx_merkle_root`. The subsequent maturity check only bounds `height` vs `current_height`: [3](#0-2) 
and the report-bookkeeping logic only ever inspects `mblock_header_1.sequence`, never validating it against `mblock_header_2.sequence`: [4](#0-3) 

Critically, since every microblock in one anchored block's stream is signed with the *same* microblock private key (the `microblock_pubkey_hash` in that block's header applies to the whole stream — see `mine_next_microblock`/`make_next_microblock_from_txs` which reuse `self.miner_privkey`/`miner_key` for every sequence number): [5](#0-4) 
`pkh1 == pkh2` is trivially true for *any two* microblocks from the same, entirely honest, non-forked stream (e.g. seq 0 and seq 1).

The actual conflict check (`sequence`, `prev_block`, `version` must match between the two headers) exists **only** in the mempool admission path, `will_admit_mempool_tx`, which is not a consensus rule: [6](#0-5) 
The consensus-level transaction-execution path that actually invokes `handle_poison_microblock` during block processing performs no such check before calling into it: [7](#0-6) 

**Attacker's exact input:** any two legitimately-signed, honestly-published `StacksMicroblockHeader`s from the *same* anchored block's microblock stream — obtainable by any unprivileged party over P2P/RPC (e.g., via `getmicroblocks_confirmed`) — with differing `sequence`/`tx_merkle_root`/`prev_block` but the *same* signer, regardless of whether the miner ever actually equivocated.

**Exploit flow:** attacker constructs `TransactionPayload::PoisonMicroblock(header_seq_i, header_seq_j)` from two real, non-conflicting, already-canonical microblocks of a target miner's stream, self-mines/includes it directly in a block (bypassing mempool checks entirely, since `will_admit_mempool_tx`'s conflict check is not re-enforced at block-processing time), and `handle_poison_microblock` accepts it as if it were proof of an equivocation, recording `insert_microblock_poison` for that miner's pubkey hash/height.

**Why existing guards fail:** the guard that would prevent this (headers must share `sequence`/`prev_block` and differ, i.e. `PoisonMicroblocksDoNotConflict`) is implemented only as a mempool heuristic in `blocks.rs`, not as part of the actual state-transition logic in `transactions.rs::handle_poison_microblock`, which is the function that determines consensus-critical reward slashing at block-maturation time (`find_mature_miner_rewards`): [8](#0-7) 

### Impact Explanation
When a mature poison report exists for a miner's key/height, `find_mature_miner_rewards` redirects a fraction of that miner's coinbase to the "reporter" and burns/punishes the miner's remaining reward: [9](#0-8) 
Since the poison report can be fabricated from two entirely honest, non-conflicting microblocks, an attacker can cause an honest miner's block reward to be wrongfully slashed and stolen — matching the Critical category "block-reward theft/double-payment/loss". This is deterministically reproducible network-wide (every node applies the same consensus rule and will accept the same bogus poison transaction), so it is not merely a local inconsistency but a chain-wide wrongful reward transfer.

### Likelihood Explanation
No special preconditions are needed beyond obtaining two already-public microblock headers of a target miner's real stream, which are broadcast/relayed openly over P2P/RPC. The attacker needs no majority stake, no signer role, and no key of their own beyond an address to receive the reporter's commission; they only pay the normal transaction fee (which can be minimal). This is fully repeatable against any miner who has produced multiple microblocks in a stream (i.e., virtually every miner), and it requires no equivocation or bad behavior by the victim miner at all.

### Recommendation
In `handle_poison_microblock` (`stackslib/src/chainstate/stacks/db/transactions.rs`), before accepting a report, enforce that the two headers actually constitute a genuine equivocation: require `mblock_header_1.sequence == mblock_header_2.sequence`, `mblock_header_1.prev_block == mblock_header_2.prev_block`, and `mblock_header_1 != mblock_header_2` (differing signature/tx_merkle_root), mirroring the check already present in `will_admit_mempool_tx`'s `PoisonMicroblocksDoNotConflict` logic, and reject the transaction (as invalid) if this invariant does not hold — moving that check from mempool-only heuristic into the consensus-critical execution path.

### Proof of Concept
Rust integration test (based on existing test infra in `stackslib/src/chainstate/stacks/db/transactions.rs`, e.g. `test_poison_microblock` style tests around lines 5509-5597):
1. Set up a chainstate, insert a real microblock pubkey hash at height 1 via `insert_microblock_pubkey_hash`.
2. Using `make_signed_microblock` (or the miner's real key), construct two **legitimately sequential, non-conflicting** microblocks: `mblock_seq0` (`sequence=0`, real `prev_block`) and `mblock_seq1` (`sequence=1`, `prev_block == mblock_seq0.block_hash()`), both signed by the same real miner key, simulating an honest, non-forked stream (assert they do NOT share `sequence` or `prev_block`).
3. Build `TransactionPayload::PoisonMicroblock(mblock_seq0.header, mblock_seq1.header)`, sign it with an arbitrary reporter key, and submit it directly via `StacksChainState::process_transaction` (bypassing `will_admit_mempool_tx`).
4. Assert equality-left: `StacksChainState::get_poison_microblock_report(&mut conn, 1)` returns `Some((reporter_addr, 0))` — i.e., the network state now records a slash.
5. Assert equality-right (ground truth): no actual fork/equivocation occurred — `mblock_seq0.header.sequence != mblock_seq1.header.sequence` and `mblock_seq0.header.prev_block != mblock_seq1.header.prev_block`.
6. The two sides mismatch (report accepted vs. no real equivocation), proving the broken equality. Optionally extend to `find_mature_miner_rewards` to show the honest miner's coinbase is reduced and paid to the attacker/reporter address.
