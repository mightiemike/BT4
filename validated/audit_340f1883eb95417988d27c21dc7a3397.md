### Title
Unbounded Iteration Over All Voters in `Wallet.getPaginatedNowWitnessList()` / `countVote()` — Public API DoS via Cheap Vote Spam - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
The Rigor finding describes an unbounded loop over an attacker-growable list (`tasks[]`) inside `projectCost()`, which is called from public-facing functions (`lendToProject()`, `toggleLendingNeeded()`), causing those calls to run out of gas as the list grows. The same bug class exists in java-tron's `Wallet.getPaginatedNowWitnessList()`, which internally calls `countVote()` — a helper that iterates over the *entire* `VotesStore` (every account that voted in the current epoch) with no cap, even though the function is meant to return a bounded, paginated slice of witnesses.

### Finding Description
`getPaginatedNowWitnessList(offset, limit)` caps the number of *witnesses returned* via `WITNESS_COUNT_LIMIT_MAX`, but before it does any pagination it must first compute up-to-date vote counts by calling `countVote(votesStore)`: [1](#0-0) 

`countVote()` iterates the full `VotesStore` database using an unbounded `Iterator`, processing every `VotesCapsule` (i.e., every account that cast a vote this epoch) regardless of how large that set is: [2](#0-1) 

The size of `VotesStore` is directly controlled by unprivileged users: any account can vote for a witness via `VoteWitnessActuator`, which writes a new entry into `VotesStore` for every distinct voting address, and this store is only cleared during the periodic `doMaintenance()` cycle (every voting cycle, e.g. every few hours), which itself performs the same unbounded per-voter iteration: [3](#0-2) 

Because freezing/voting only requires a small amount of TRX to be frozen for TRON Power, an attacker can cheaply create a very large number of distinct voting accounts within a single epoch, causing `VotesStore` to grow to an arbitrarily large size. This directly mirrors the Rigor pattern: an unprivileged actor inflates a state collection (`tasks[]` there, `VotesStore` here) that is then iterated in full — without any bound — inside a function meant to be safely callable (`projectCost()`/`lendToProject()` there, `countVote()`/`getPaginatedNowWitnessList()` here).

`getPaginatedNowWitnessList` is exposed as a public, unauthenticated read API on both full nodes and solidity nodes: [4](#0-3) 

### Impact Explanation
Every call to this API — which any external client can invoke repeatedly and without cost (it is a query, not a transaction) — forces the node to iterate the entirety of `VotesStore`. As the attacker-controlled voter set grows, per-call latency and CPU/DB-read cost grow linearly and unboundedly. Because this can be triggered by unauthenticated HTTP/gRPC clients at will, and the underlying state (`VotesStore`) can be inflated cheaply by an unprivileged attacker, this can degrade full node responsiveness or exhaust node resources — an availability/DoS impact on a public read path, analogous to the `lendToProject()`/`toggleLendingNeeded()` gas-exhaustion DoS in the original report (there, an unbounded loop over an attacker-inflatable list blocked a publicly callable function).

### Likelihood Explanation
Likelihood is moderate-to-high: voting is a normal, low-cost, unprivileged operation, and creating many distinct voting addresses (each holding minimal frozen TRON Power) is inexpensive relative to the potential to force expensive full-store scans on every node serving this API for the remainder of the epoch. The attack does not require any privileged role, contract bug, or off-chain trust assumption — only ordinary `FreezeBalance(V2)`/vote transactions repeated across many accounts.

### Recommendation
- Cap the number of `VotesCapsule` entries processed by `countVote()` per call, or maintain vote deltas incrementally (e.g., update an aggregate vote-count structure on each vote transaction rather than recomputing from a full store scan on every query).
- Alternatively, only recompute unresolved vote deltas lazily/incrementally and cache the result, invalidating on the next maintenance cycle instead of rescanning `VotesStore` on every API call.
- Consider adding a hard maximum on the number of distinct new votes counted per epoch, with proper aggregation instead of full re-iteration.

### Proof of Concept
1. Create N distinct accounts, each freezing the minimum TRON Power required to vote (`FreezeBalanceV2Contract` with `TRON_POWER` resource).
2. Have each account cast a vote for any witness via `VoteWitnessContract`, producing N entries in `VotesStore`.
3. Repeatedly call the public `/wallet/getpaginatednowwitnesslist` (or gRPC `GetPaginatedNowWitnessList`) API.
4. Observe that `countVote()` scans all N `VotesStore` entries on every single call — as N grows (e.g., into the hundreds of thousands, feasible cheaply on a testnet or via many low-balance accounts), each API call's cost grows correspondingly, since the store is only cleared at the next maintenance cycle boundary.

**Note on verification limits:** I was not able to determine the exact minimum TRON Power/frozen-balance cost required to cast a valid vote (which determines the practical cost-per-fake-voter for the attacker) within the indexed portion of the codebase, nor the precise maintenance cycle interval constant. A Devin session with full repository access would be needed to pin down these exact economic parameters for a complete cost/impact analysis.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }
