### Title
`check_pox_bitvector` allows a miner to bypass PoX bitvector/reward-set consistency checks by submitting a block-commit with an empty `treatment` vector - (File: `stackslib/src/chainstate/nakamoto/mod.rs`)

### Summary
`check_pox_bitvector` (nakamoto/mod.rs:4882-4966) is intended to verify that the Nakamoto block header's `pox_treatment` bitvector is consistent with the miner's own `LeaderBlockCommitOp.treatment` field and the active reward set. The function short-circuits to `Ok(())` whenever `tenure_block_commit.treatment.is_empty()`, a condition fully controlled by the attacker since `treatment` is derived from their own Bitcoin block-commit transaction.

### Finding Description
The equality this function is supposed to enforce is: for every rewarded PoX address `A`, `block_header.pox_treatment[index(A)]` (the bits declared in the Stacks block header) must agree with `tenure_block_commit.treatment[A]` (the reward/punish decision the miner made on the burnchain for that address). This equality is the sole content of the loop at [1](#0-0) .

Before that loop is even reached, the function has an early return: [2](#0-1) 

Since `tenure_block_commit` is the attacker's own `LeaderBlockCommitOp`, parsed directly from the attacker's Bitcoin transaction, `treatment` is attacker-supplied data. Submitting a block-commit whose `treatment` vector is empty (as opposed to explicitly zero-filled/burn-marked) causes `check_pox_bitvector` to return `Ok(())` unconditionally for that tenure, before ever consulting `active_reward_set` or the block header's `pox_treatment` bitvector. This means: (1) the block header's `pox_treatment` bits are never cross-checked against the block-commit's on-chain reward/punish declaration, and (2) every Nakamoto block mined in that tenure can carry an arbitrary `pox_treatment` bitvector with no validation, since the check operates per-tenure using the tenure's block-commit `treatment`.

### Impact Explanation
This is a minority-triggerable static-validation divergence: a single miner with a winning sortition (their own BTC, their own slot) can, for the whole tenure they win, set `header.pox_treatment` inconsistently with the burnchain-committed reward/punish decisions without the chainstate ever detecting or rejecting it. This corrupts downstream PoX-unlock/reward bookkeeping tied to that bitvector, which matches the "High" category (reward mis-payment/bookkeeping divergence, static-validation bypass triggerable by a minority miner) rather than a chain split, since the check being bypassed is a Stacks-level (not burnchain-consensus) validation and does not, on its own, cause two honest followers to disagree on chain tip acceptance — both would accept the same (inconsistently-treated) block.

### Likelihood Explanation
Preconditions: the attacker only needs to win a single sortition (control one miner slot with their own BTC) and construct their `LeaderBlockCommitOp` with an empty `treatment` field, which is entirely within their control as the transaction author. No majority stake, no signer collusion, no privileged role required. This is repeatable every time the attacker wins a tenure.

### Recommendation
Remove the `treatment.is_empty()` early-return short-circuit in `check_pox_bitvector`, or replace it with a check that empty `treatment` is only valid when the active reward set has no PoX reward addresses to treat (i.e., merge this case into the existing `active_reward_set.rewarded_addresses() == None` branch rather than bypassing on the attacker-controlled `treatment` field). If `treatment` is empty but `active_reward_set.rewarded_addresses()` is `Some(non-empty)`, the block should be rejected as invalid (`InvalidStacksBlock`) rather than accepted with `Ok(())`.

### Proof of Concept
Rust integration test plan:
1. Set up a Nakamoto chainstate with an active `RewardSet` containing at least one rewarded PoX address (`active_reward_set.rewarded_addresses()` returns `Some(vec![addr])`).
2. Construct a `LeaderBlockCommitOp` for the tenure with `treatment = vec![]` (attacker fully controls this as it's their own burnchain transaction).
3. Construct a Nakamoto block header for that tenure whose `pox_treatment` `BitVec` marks `addr`'s index as rewarded (`1`), while a second block in the same tenure marks the same index as punished (`0`) — an internally inconsistent declaration.
4. Call `check_pox_bitvector(&block_bitvec, &tenure_block_commit, &active_reward_set)` for both blocks and assert both return `Ok(())` despite `active_reward_set` containing `addr` and the bitvectors disagreeing with each other and with any reasonable reward/punish semantics.
5. Assert equality-under-test: before the fix, `block_header.pox_treatment[index(addr)]` is never compared against the block-commit's reward/punish declaration for `addr` (since `treatment` is empty, there is nothing to compare against, yet the check still reports success). After applying the recommended fix (treating empty `treatment` as invalid when `rewarded_addresses()` is non-empty), the same call should return `Err(ChainstateError::InvalidStacksBlock(..))`.
