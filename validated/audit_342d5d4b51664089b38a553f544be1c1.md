### Title
`check_pox_pre_waterfall` treats any block-commit as "descended from the PoX anchor" whenever `parent_vtxindex == 0`, letting a non-descendant commit wrongly punish PoX reward recipients - (`stackslib/src/chainstate/burn/operations/leader_block_commit.rs`)

### Summary
`LeaderBlockCommitOp::check_pox_pre_waterfall()` computes `descended_from_anchor` by OR-ing three conditions, one of which (`maybe_shadow_parent`) is a cheap heuristic that assumes the commit is legitimate whenever `parent_vtxindex == 0`, deferring the real verification to a later, unrelated check that does not actually enforce the assumption when it is false.

### Finding Description
In `check_pox_pre_waterfall`, the anchor-descent equality check is short-circuited: [1](#0-0) 

```
let directly_descended_from_anchor = ...
let maybe_shadow_parent = epoch_id.supports_shadow_blocks()
    && self.parent_block_ptr != 0
    && self.parent_vtxindex == 0;
let descended_from_anchor = directly_descended_from_anchor
    || maybe_shadow_parent
    || tx.descended_from(...)?;
```

The comment states the assumption explicitly: "the block validation logic will check that the parent block is indeed a shadow block, and that `self.parent_block_ptr` points to the shadow block's tenure's burnchain block." [2](#0-1) 

That deferred check is `NakamotoChainState::validate_shadow_parent_burnchain`, which is a no-op whenever the parent turns out **not** to be a shadow block: [3](#0-2) 

```
let Some(parent_header) = staging_db.get_nakamoto_block_header(&block.header.parent_block_id)? else {
    return Ok(());
};
if !parent_header.is_shadow_block() {
    return Ok(());
}
```

So the only place that is supposed to confirm the `maybe_shadow_parent` heuristic silently succeeds precisely in the case it should be catching: a normal (non-shadow) parent. There is no check anywhere that rejects a `LeaderBlockCommitOp` for having `parent_vtxindex == 0` when its parent is *not* a shadow block. `parent_vtxindex` is simply the burnchain transaction index of the referenced parent block-commit and is fully attacker-controlled — a miner only needs the previous commit they build on to occupy vtxindex 0 in its Bitcoin block (e.g. by broadcasting it alone, or via normal chance in low-traffic blocks), which requires no majority hash power or privileged access.

`check_pox` (and `check_pox_pre_waterfall`) is called on every node processing the burnchain as part of consensus-critical `LeaderBlockCommitOp::check()`, so all honest nodes compute the same (incorrect) `descended_from_anchor = true` deterministically — this is not a node-disagreement bug, but a uniformly-applied bypass of the anchor-descent proof.

### Impact Explanation
With `descended_from_anchor` falsely forced to `true`, a miner who is **not** actually building on the correct PoX reward-cycle anchor can:
- Submit an all-burn commit and have it recorded as `Treatment::Punish` for the legitimate PoX recipients [4](#0-3) , diverting stacker rewards to burn even though the commit does not legitimately descend from the anchor block that would justify punishment.
- Alternatively submit outputs matching the reward set and have them recorded as `Treatment::Reward` [5](#0-4)  without the expensive/legitimate `tx.descended_from()` proof.

This is a reward-mispayment bug bounded to PoX payouts within a reward cycle — the equality that should hold ("this commit's ancestry chain actually reaches the recorded PoX anchor") is broken by any single minority miner crafting `parent_vtxindex = 0`.

### Likelihood Explanation
`parent_vtxindex` is chosen by referencing an existing block-commit at a given burnchain height/index; any miner can pick a parent block-commit that happens to sit at burnchain-tx-index 0 (trivial in low-competition blocks, or when they mine that Bitcoin block themselves), triggering `maybe_shadow_parent` without ever constructing an actual shadow block. No majority stake or privileged role is required — a single minority miner suffices.

### Recommendation
`maybe_shadow_parent` must not be trusted at the burn-operation `check_pox` layer unless it is actually corroborated there (e.g., by querying whether the parent commit's referenced tenure is truly a shadow tenure at check time), or `validate_shadow_parent_burnchain` must be made to reject (not silently accept) commits whose `parent_vtxindex == 0` but whose parent is not a shadow block. The heuristic should be replaced by an actual verification at the point it is used to decide `descended_from_anchor`, rather than being deferred to a check that only fires when the parent legitimately is a shadow block.

### Proof of Concept
1. Attacker (any minority miner) submits `LeaderBlockCommitOpA` whose resulting Bitcoin transaction lands at `vtxindex = 0` in block `H` (achievable by mining that Bitcoin block themselves or broadcasting when the mempool is otherwise empty).
2. In a later Bitcoin block, attacker submits `LeaderBlockCommitOpB` with `parent_block_ptr = H`, `parent_vtxindex = 0`, referencing `OpA`, but `OpA`'s tenure is a normal (non-shadow) tenure that does *not* descend from the current PoX reward-cycle anchor block.
3. During sortition processing, `check_pox_pre_waterfall` evaluates `maybe_shadow_parent = true` (since `epoch_id.supports_shadow_blocks()` and `parent_vtxindex == 0`), forcing `descended_from_anchor = true`.
4. If `OpB` uses all-burn outputs and `allow_nakamoto_punishment` is set for the epoch, the legitimate PoX reward-set recipients are recorded as `Treatment::Punish` even though `OpB` never legitimately proved descent from the anchor.
5. Later, `validate_shadow_parent_burnchain` is invoked when the corresponding Nakamoto block is validated; since the parent header is not actually a shadow block, it returns `Ok(())` without flagging the inconsistency, so the fraudulent Treatment stands.
