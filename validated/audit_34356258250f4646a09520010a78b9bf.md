## Title
Zero-output rounding in the "taker == maker" branch of `matchSingleOrder` silently zeroes a resting maker order without the zero-receive guard that exists elsewhere - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
This is an analog of the Rubicon `swap`/`route.length-1` bug class: a code path that computes a "received amount" via integer division, allows that amount to be `0`, and — unlike the sibling branch that explicitly guards against this — proceeds to fully consume the order and mark it `INACTIVE`, causing the order owner to receive nothing for the tokens they contributed.

### Finding Description
`MarketSellAssetActuator.matchSingleOrder` computes `takerBuyTokenQuantityRemain` and then branches into three cases depending on how it compares to the maker's remaining sell quantity: `taker == maker`, `taker < maker`, and `taker > maker`.

In the `taker == maker` branch, `makerBuyTokenQuantityReceive` is computed via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)` — a truncating integer division that can legitimately round down to `0` for small quantities or unfavorable ratios [1](#0-0) . Immediately after, regardless of whether `makerBuyTokenQuantityReceive` is `0`, the code sets `makerOrderCapsule.setSellTokenQuantityRemain(0)` and calls `MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore)`, fully closing out the maker's order [2](#0-1) .

This is the exact analog of the Rubicon flaw: a divide/rounding operation that can yield `0` is not checked before the state-mutating "consume the entire order" action is taken.

The codebase itself demonstrates awareness of this exact hazard: in the sibling `taker > maker` branch, the same `multiplyAndDivide` computation for `makerBuyTokenQuantityReceive` is explicitly checked for `== 0`, and if so the maker's remaining sell tokens are returned via `returnSellTokenRemain` instead of being consumed [3](#0-2) . The code comment even reasons about why the zero case "would not happen" for that specific branch, based on the relationship between `sellQuantity` and `buyQuantity` in that ratio — but this reasoning is branch-specific and is never applied/re-derived for the `taker == maker` branch, where `makerSellRemainQuantity` is bounded by `takerBuyTokenQuantityRemain` rather than by the maker's own order size, so the same "at least one token" argument does not obviously transfer.

If `makerBuyTokenQuantityReceive == 0` in the equal-quantities branch, execution continues to `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` (adding `0` value) and the order is persisted as fully closed with `orderStore.put(...)` [4](#0-3) .

### Impact Explanation
The maker order was placed and fully funded (its sell-side tokens escrowed) in an earlier `MarketSellAssetContract` transaction, executed by the actuator's `execute` path that reduces the owner's asset/TRX balance and stores the order [5](#0-4) . The maker has no ability to intervene at match time — matching is triggered by an unrelated taker's transaction reaching this code path. If the taker's remaining sell amount happens to exactly equal the maker's remaining sell amount (the `taker == maker` condition) and the resulting `multiplyAndDivide` truncates to `0`, the maker's entire remaining order is consumed and marked `INACTIVE` while `makerBuyTokenQuantityReceive` (what the maker gets credited) is `0`. This is a direct, permanent loss of the maker's escrowed assets with no corresponding token or TRX credited back — an accounting corruption reachable purely from a broadcast transaction (an ordinary taker sell order) with no privileged access required.

### Likelihood Explanation
This requires: (1) an existing resting maker order at a price ratio where `makerBuyQuantity * makerSellRemainQuantity` truncates to `< makerSellQuantity` under integer division, and (2) a taker order whose computed `takerBuyTokenQuantityRemain` exactly equals the maker's `sellTokenQuantityRemain`, triggering the `taker == maker` branch specifically (as opposed to `taker > maker`, which already has the guard). This is a narrower trigger condition than the Rubicon original (which required only a 1-user mistake), since it needs precise quantity equality plus a rounding-to-zero ratio; it is not trivial to hit by accident, but is fully controllable/craftable by an adversarial taker who chooses `sellTokenQuantity`/`buyTokenQuantity` to target a specific victim maker order and quantity match. I was unable to fully verify within the available context whether the `taker == maker` condition, combined with a rounding-to-zero ratio, is actually reachable given the invariants maintained elsewhere in order creation/validation (e.g., minimum quantity checks in `MarketSellAssetActuator`'s `validate()`), so this should be confirmed with concrete numeric test vectors before treating it as confirmed-exploitable.

### Recommendation
Add the same zero-guard used in the `taker > maker` branch to the `taker == maker` branch: check `if (makerBuyTokenQuantityReceive == 0)` before mutating `makerOrderCapsule`'s state, and if so, return the maker's remaining sell tokens via `MarketUtils.returnSellTokenRemain` instead of zeroing and closing the order. Alternatively, centralize the "receive amount == 0" handling into `MarketUtils` so all three branches share one enforced invariant rather than relying on branch-specific manual reasoning that can silently miss a case, mirroring the Rubicon-recommended fix of enforcing a structural precondition (`route.length > 1`) rather than trusting downstream math to "just work out."

### Proof of Concept
Conceptual PoC (concrete numeric vectors not fully derived from available context):
1. User A places a maker `MarketSellAssetContract` selling asset X with `sellTokenQuantity = S`, `buyTokenQuantity = B`, chosen so that for some future `makerSellRemainQuantity = R` (with `R < S`), `multiplyAndDivide(R, B, S) == 0` (i.e., `R * B < S`).
2. User B (taker) places a `MarketSellAssetContract` on the opposite side such that the computed `takerBuyTokenQuantityRemain` (via `multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity)`) exactly equals `R`, forcing the `taker == maker` branch in `matchSingleOrder`.
3. On match, `makerBuyTokenQuantityReceive = multiplyAndDivide(R, B, S) = 0`, yet `makerOrderCapsule.setSellTokenQuantityRemain(0)` and `updateOrderState(..., INACTIVE, ...)` execute unconditionally, closing User A's order.
4. `addTrxOrToken(makerOrderCapsule, 0)` credits User A nothing, and their escrowed `R` units of asset X are lost with no return path taken (unlike the guarded `taker > maker` branch) [6](#0-5) .
