Contract-creation DoS via front-running predictable deployment address - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`VMActuator.create()` derives the address for a new smart contract deterministically from the transaction's raw-data hash and owner address, then rejects deployment if any account already exists at that address. Since the transaction ID/hash is computed only from `raw_data` (not the signature), the resulting contract address is fully computable by anyone who observes the pending, unconfirmed `CreateSmartContract` transaction (e.g. in the node's pending pool / broadcast network), before it is packed into a block. This mirrors the reported Morpho Blue bug class: a market/contract creation whose resulting identifier is deterministic and can be pre-empted by any observer once the parameters (or raw transaction) are visible, causing the legitimate creation transaction to permanently fail with a "already exists" style guard.

### Finding Description
The contract address for `CreateSmartContract` is computed as: [1](#0-0) 

which hashes `txRawDataHash || ownerAddress`. `txRawDataHash` is the transaction ID, itself computed purely from `raw_data` (excluding signatures): [2](#0-1) 

Because signatures are excluded, any node or peer that receives the broadcast (unconfirmed) transaction — via the anonymous gRPC/HTTP `BroadcastTransaction` API or P2P propagation — can compute the resulting `contractAddress` immediately, without needing the private key or waiting for block confirmation.

`VMActuator.create()` then enforces a "must not already exist" guard before deploying: [3](#0-2) 

An attacker who observes the pending deployment transaction can quickly submit a competing, unprivileged transaction (e.g. a simple TRX transfer, or another account-creating operation) that causes an `AccountCapsule` to be created at the precomputed `contractAddress` before the original deployment transaction is confirmed. Once any account exists at that address, `rootRepository.getAccount(contractAddress) != null` evaluates to true and the legitimate `CreateSmartContract` transaction is rejected with `ContractValidateException("Trying to create a contract with existing contract address...")`, consuming the deployer's fee/bandwidth/energy for a failed transaction and blocking the intended deployment. This is the exact analog of the Morpho Blue market-creation front-run: a deterministic, non-secret identifier gates a "must not already exist" state-transition check, and an attacker who observes it before finalization can grief the creator.

### Impact Explanation
This is a Denial-of-Service on contract deployment, an unprivileged actuator state-transition path reachable from any anonymous broadcast transaction. Impact is Medium: the victim's deployment transaction fails, wasting fees/bandwidth and delaying (not permanently blocking — see below) legitimate contract deployment. It does not lead to fund loss, key disclosure, or consensus divergence, but it is a genuine resource-and-availability griefing vector triggerable by anyone monitoring the mempool/P2P layer.

### Likelihood Explanation
Medium likelihood: the attack requires the attacker to observe the specific pending deployment transaction (via P2P gossip or a public full node's pending pool) before it is included in a block, and then race a transaction into an earlier block slot with a bribe/priority — feasible on TRON given predictable block production and public visibility of pending transactions, but it does require timing precision and repeated retries if the victim simply resubmits with different `raw_data` (which changes `txRawDataHash` and thus the target address).

### Recommendation
Do not gate contract creation solely on the deterministic, pre-computable address derived from public transaction fields. Options include: incorporating a value unknown to observers until inclusion (e.g., using account nonce/sequence at execution time rather than a value derivable purely from the pending transaction), or treating a pre-existing plain (non-contract) account at the target address the way `Program.createContractImpl` already does for internal `CREATE`/`CREATE2` calls — i.e., upgrading a non-contract account in place instead of unconditionally rejecting — rather than hard-failing the top-level deployment in `VMActuator.create()`.

### Proof of Concept
1. Attacker monitors the network/pending-pool for a broadcast `CreateSmartContract` transaction from victim address `O`.
2. Attacker computes `contractAddress = sha3omit12(txRawDataHash || O)` using `WalletUtil.generateContractAddress` logic (`chainbase/src/main/java/org/tron/common/utils/WalletUtil.java:39-52`) — all needed inputs (`raw_data` bytes, owner address) are visible in the unsigned-portion of the pending transaction.
3. Attacker submits any transaction that results in an `AccountCapsule` being created at `contractAddress` (e.g., a TRX transfer to that address) with sufficient fee/priority to be included in an earlier block than the victim's transaction.
4. When the victim's `CreateSmartContract` transaction executes, `VMActuator.create()` (`actuator/src/main/java/org/tron/core/actuator/VMActuator.java:355-361`) finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException`, causing the deployment to fail and consuming the victim's fee/energy.

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);

    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

  }
