## Analysis Result



### Title
Permissionless `deploy_from_zero` allows any unprivileged caller to seize a victim's precomputed contract address before the victim deploys it - (File: crates/blockifier/src/execution/syscalls/syscall_base.rs)

### Summary
The `deploy` syscall supports a `deploy_from_zero` flag that, when set, computes the deployed contract's address **without binding it to the caller's own contract address**. This is functionally analogous to the Opus `abbot.deposit()` flaw: a shared resource identifier (a contract address, like a trove) can be permissionlessly claimed/written to by any caller, not just its intended owner, letting an attacker redirect an outcome (address ownership) that a victim assumed only they could produce.

### Finding Description
In `execute_syscall_base::deploy`, the deployer address used for address calculation is zeroed out whenever `deploy_from_zero` is true: [1](#0-0) 

The same pattern exists in the Starknet OS Cairo implementation of both the current and deprecated deploy syscalls: [2](#0-1) [3](#0-2) 

Because `get_contract_address`/`calculate_contract_address` is a pure function of `(salt, class_hash, constructor_calldata, deployer_address)`, once `deployer_address` is forced to zero, **the resulting address depends only on values that are entirely public and guessable/known ahead of time** (class hash, salt, calldata) — not on who actually submits the deploying transaction. Any account contract on the network can call any other deployed contract that itself calls `deploy(..., deploy_from_zero=True)` (or any contract can invoke this syscall directly), and if it wins the race, it takes over the address that a victim intended to deploy to later using the exact same `(salt, class_hash, calldata)` triple (a common counterfactual-wallet pattern). There is no ownership or authorization check tying this deployment path to a specific caller, exactly mirroring the Opus `deposit()` issue of a permissionless action on a resource that should be exclusive to its intended owner.

### Impact Explanation
If a victim (or a wallet-deployment flow) precomputes an address via `deploy_from_zero` semantics with a known `(class_hash, salt, calldata)` before funding or actually deploying it, any unprivileged attacker who observes the parameters (they are necessarily public, since the victim must publish/communicate them to receive funds or trigger later deployment) can deploy a malicious constructor to that exact address first. This results in unauthorized account takeover of the address and permanent loss/freezing of any funds sent to it, satisfying the "unauthorized account action" / "concrete loss or permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood is bounded by the fact that this requires knowledge of the exact `(class_hash, salt, calldata)` ahead of time and a race to submit before the legitimate deployment — an inherent, long-documented characteristic of `deploy_from_zero` in Starknet rather than a newly introduced coding defect. It is reachable by any unprivileged transaction sender with no special access, consistent with the Opus finding's own "low likelihood, but real" characterization (which was still rated Medium severity).

### Recommendation
Discourage or gate use of `deploy_from_zero` for flows where a specific address must be exclusively reserved for a particular deployer; alternatively, require the caller's identity to be bound into the salt/calldata for such flows, or emit a race-safety warning/guard so higher-layer account-deployment tooling incorporates deployer-specific entropy by default.

### Proof of Concept
1. Victim computes a wallet address using `deploy_from_zero=True` with `(class_hash=C, salt=S, calldata=D)` intending to fund it and deploy later.
2. Victim shares/publishes this address so third parties can send funds to it (a common "predict your future address, fund it now, deploy later" UX pattern).
3. Attacker observes the public `(C, S, D)` triple (necessarily known since it determines the published address) and submits an `invoke` transaction from **any of their own contracts** calling `deploy(class_hash=C, contract_address_salt=S, constructor_calldata=D, deploy_from_zero=True)` before the victim's real deployment transaction lands.
4. Per `deployer_address_for_calculation = ContractAddress::default()` in `syscall_base.rs:401-403`, the resulting contract address is identical regardless of who called `deploy`, so the attacker's transaction claims the address first, running attacker-controlled constructor logic there and taking control of any funds subsequently sent to that address.
