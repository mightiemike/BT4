### Title
Unbounded Memory Allocation via Unvalidated Array Size in Deprecated Syscall Felt-Array Reading - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The deprecated (Cairo 0) syscall handler reads a felt-array size directly as an arbitrary felt from Cairo VM memory and converts it to a `usize` without validating it against the actual amount of available/remaining VM memory before passing it to a range-read routine that allocates a `Vec` sized to the declared count.

### Finding Description
`read_felt_array` in the deprecated syscall path reads the array size as a raw felt value (`felt_from_ptr`) rather than deriving it from two real pointers, and only special-cases `Felt::ZERO`: [1](#0-0) 

That size is converted with `usize::try_from(array_size.to_biguint())?` and immediately forwarded to `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)` — a call whose cost/allocation is proportional to `size`, with no upper bound check against the actual segment length or remaining calldata: [2](#0-1) 

This is unlike the equivalent function in the current (non-deprecated) syscall hint processor, which derives the array length from the difference between two real relocatable pointers (`array_data_end_ptr - array_data_start_ptr`), bounding the size to what actually exists in the segment: [3](#0-2) 

Because the deprecated variant trusts a felt value that originates from data the executing (attacker-deployed or attacker-invoked) Cairo 0 contract places in VM memory (e.g., calldata/array-size fields used when handling deprecated syscall requests such as calldata for `call_contract`/`library_call`, event keys/data, or L1 message payloads), any transaction sender that deploys or calls a Cairo 0 class can supply a large size felt (up to `usize::MAX`, i.e. up to ~2^64-1) and trigger `get_integer_range` to attempt to construct a vector for that many entries before any bounds failure is possible.

### Impact Explanation
A single transaction invoking a Cairo 0 (deprecated) contract can force the executing sequencer node to attempt an enormous heap allocation while processing that transaction, exhausting node memory. Since this happens during mempool/block execution on every honest node re-executing or validating the same transaction (including the Starknet OS re-execution during proving), it can crash or degrade every node that processes it — a network-wide availability impact consistent with a network unable to confirm new transactions, rather than a benign resource-only slowdown.

### Likelihood Explanation
Deprecated Cairo 0 classes and calls to them remain permitted on Starknet mainnet/sequencer, so the vulnerable path is reachable directly from any account without special privileges: declare/deploy or call an existing Cairo 0 contract crafted to place a large size felt where the deprecated syscall handler expects an array length, then invoke it in a normal transaction.

### Recommendation
Bound the declared array size in `read_felt_array` (deprecated_syscalls/hint_processor.rs) against a sane maximum (e.g., the actual remaining VM memory/segment size, or the protocol's maximum calldata/array length) before calling `felt_range_from_ptr`/`vm.get_integer_range`, mirroring the pointer-difference approach already used in the non-deprecated syscall implementation, or reject the request early with a clear execution error if the declared size exceeds that bound.

### Proof of Concept
A Cairo 0 contract can be crafted so that, when invoked via a deprecated syscall (e.g. `library_call`/`call_contract` on a legacy class, or via emitting an event/L1 message), the felt at the expected "array size" slot is set to a very large value (e.g., `2^62`) while the actual data segment is empty/small. When `read_felt_array` executes for that request, `usize::try_from` succeeds, and `felt_range_from_ptr` invokes `vm.get_integer_range` with that huge size, attempting to allocate/scan a vector sized accordingly, consuming excessive memory/CPU on the executing node for a single, low-cost transaction.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
