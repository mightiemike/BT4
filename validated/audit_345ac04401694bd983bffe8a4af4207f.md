### Title
Empty-but-present signer set makes zero signer signatures satisfy the Nakamoto block approval threshold — ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
The bug class in the report — a threshold that is silently computed as `0` before real participation exists, letting an unprivileged party satisfy it trivially — has a concrete analog in the Nakamoto signer-weight approval logic, where a reward set whose signer list is present but empty (`Some(vec![])`) causes `total_weight == 0`, `threshold == 0`, and therefore a block with **zero signer signatures** passes `verify_signer_signatures`.

### Finding Description
`NakamotoBlockHeader::verify_signer_signatures` computes the approval threshold purely as a percentage of `total_weight`: [1](#0-0) 

and the threshold formula: [2](#0-1) 
`compute_voting_weight_threshold(0)` returns `0`. If `total_weight_signed` starts at `0` (i.e., no signatures at all, or all signatures fail to map to a valid public key and are simply not counted) and `threshold == 0`, the check `total_weight_signed < threshold` is `0 < 0 = false`, so the function returns `Ok(0)` — the block is treated as validly signed with **no real signer approval**.

The guard against this is `reward_set.signers().is_none()`, which only rejects a `None` signer list, not an empty-but-`Some` one: [3](#0-2) 
`total_signing_weight()` similarly only errors on `None`, not on an empty `Some(vec![])`: [4](#0-3) 

An empty-but-`Some` signer list is reachable through `make_signer_set`, which returns `Some(signer_set)` even when every candidate's weight rounds down to `0` and is filtered out — it only returns `None` if the *input* `entries` slice was empty to begin with: [5](#0-4) 
The PoX-4 path `pox_4_compute_and_update_signers` passes this signer_set through directly into the constructed `RewardSet` without any additional empty-set check: [6](#0-5) 
By contrast, the newer PoX-5 path explicitly guards against this with `if signer_set.is_empty() { ... return Err(...) }`, indicating the maintainers are aware this state is dangerous and must be rejected: [7](#0-6) 
Later, when the reward set is read back for use in Nakamoto block/signature validation, the only defensive check is `reward_set.signers().is_none()`, which again does **not** catch the empty-but-`Some` case: [8](#0-7) 
There is a separate `is_empty()` check, but it only runs in `OnChainRewardSetProvider::get_reward_set` (used for the epoch-2.x style reward-set retrieval path), not in the Nakamoto-specific `read_reward_set_at_calculated_block`/`get_reward_set_nakamoto` path used at block-validation time: [9](#0-8) 

### Impact Explanation
If a reward cycle's PoX-4 stacking pool ends up with every stacker's stacked amount below the per-slot threshold (all weights floor to `0`), `make_signer_set` produces an empty `Vec` wrapped in `Some(...)`, and this construction happens without the PoX-5-style explicit rejection. If such a reward set is written and used for a Nakamoto reward cycle, `verify_signer_signatures` will accept a block header carrying an empty `signer_signature` vector (or garbage signatures that fail to resolve to any of the zero entries in the reward set) as validly signed, because `0 >= 0`. This breaks the fundamental equality that a Nakamoto block must be approved by supermajority signer weight — an **invalid block would be accepted network-wide** with no real signer participation, which is Critical-class impact per the given severity taxonomy (invalid block accepted network-wide).

### Likelihood Explanation
This requires a specific, narrow, unprivileged-triggerable pre-condition: a reward cycle where the PoX-4 computed per-slot threshold causes every stacker's weight to floor to zero (e.g., very low aggregate stacked amounts relative to reward-slot count, or a cycle transitioning from little/no participation). No signer key, admin key, or majority collusion is required — the "attacker" is simply the natural state of the network (or a set of small stackers) at a given cycle boundary. The explicit fix already present in the PoX-5 path (`if signer_set.is_empty() { return Err(...) }`) but absent from the PoX-4 path and from the `read_reward_set_at_calculated_block` re-validation confirms this is a real, previously-recognized-but-incompletely-patched gap rather than a purely theoretical one.

### Recommendation
Add the same `signer_set.is_empty()` rejection used in `pox_5_compute_and_update_signers` to `pox_4_compute_and_update_signers`, and additionally harden `read_reward_set_at_calculated_block` (and any other Nakamoto reward-set consumption path) to reject `reward_set.signers().map_or(true, |s| s.is_empty())` rather than only `is_none()`. As defense in depth, `NakamotoBlockHeader::compute_voting_weight_threshold` and/or `verify_signer_signatures` should explicitly reject `total_weight == 0` as an error rather than silently computing a `0` threshold.

### Proof of Concept
1. Construct a `RewardSetV0` (or drive PoX-4 reward-set computation) such that `signers = Some(vec![])` — reachable via `make_signer_set` when all `RawRewardSetEntry` amounts are non-empty but each individually floors to `weight == 0` against the chosen `threshold`.
2. Call `NakamotoBlockHeader::verify_signer_signatures(&reward_set, epoch_id)` on a header with `signer_signature = vec![]`.
3. Observe: `reward_set.signers()` is `Some(&vec![])` (passes the `is_none()` check); `total_signing_weight()` returns `Ok(0)`; `compute_voting_weight_threshold(0)` returns `Ok(0)`; loop over `self.signer_signature` does nothing; final check `0 < 0` is `false`; function returns `Ok(0)` — i.e. the block is accepted as validly signed with zero signer participation.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

    pub fn make_signer_set(
        threshold: u128,
        entries: &[RawRewardSetEntry],
    ) -> Option<Vec<NakamotoSignerEntry>> {
        let Some(first_entry) = entries.first() else {
            // entries is empty: there's no signer set
            return None;
        };
        // signing keys must be all-or-nothing in the reward set
        let expects_signing_keys = first_entry.signer.is_some();
        for entry in entries.iter() {
            if entry.signer.is_some() != expects_signing_keys {
                panic!("FATAL: stacking-set contains mismatched entries with and without signing keys.");
            }
        }
        if !expects_signing_keys {
            return None;
        }

        let mut signer_set = BTreeMap::new();
        for entry in entries.iter() {
            let signing_key = entry
                .signer
                .expect("BUG: signing keys should all be set in reward-sets with any signing keys");
            if let Some(existing_entry) = signer_set.get_mut(&signing_key) {
                *existing_entry += entry.amount_stacked;
            } else {
                signer_set.insert(signing_key, entry.amount_stacked);
            };
        }

        let mut signer_set: Vec<_> = signer_set
            .into_iter()
            .filter_map(|(signing_key, stacked_amt)| {
                let weight = u32::try_from(stacked_amt / threshold)
                    .expect("CORRUPTION: Stacker claimed > u32::max() reward slots");
                if weight == 0 {
                    return None;
                }
                Some(NakamotoSignerEntry {
                    signing_key,
                    stacked_amt,
                    weight,
                })
            })
            .collect();
