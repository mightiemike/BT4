### Title
Signature-encoding malleability bypasses per-address de-duplication in `ValidateMultiSign`, allowing a single authorized key to be counted multiple times toward `permission.getThreshold()` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompile de-duplicates recovered signers by comparing the *exact byte concatenation* of `recoveredAddr + sign`, not just `recoveredAddr`. When a recovered address is already present in `executedSignList` but the concatenated bytes differ (e.g. due to different padding bytes fetched by `extractSigArray`, or ECDSA signature malleability), the loop falls through instead of skipping, and re-adds the same key's weight to `totalWeight`. This lets an attacker with a single valid low-weight key satisfy a higher `permission.getThreshold()`.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute`: [1](#0-0) 

```java
long totalWeight = 0L;
List<byte[]> executedSignList = new ArrayList<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  if (weight == 0) { return Pair.of(true, DATA_FALSE); }
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
if (totalWeight >= permission.getThreshold()) {
  return Pair.of(true, dataOne());
}
```

The de-duplication intent is: if `recoveredAddr` was already seen, skip only if this *exact* signature (`sign`) was already seen; otherwise call `MUtil.checkCPUTime()` (a CPU-time budget check for repeated ECDSA recoveries) and **fall through to weight accumulation anyway**. This means: any two byte-distinct signature encodings that both recover to the same address will each contribute weight, instead of being treated as duplicates of the same key.

The attacker-controlled byte-difference vector is the raw signature bytes fed into `recoverAddrBySign`: [2](#0-1) 
`recoverAddrBySign` builds `Rsv.fromSignature(sign)` and calls `SignUtils.fromComponents`/`signatureToAddress` [3](#0-2) 
which only uses the r/s/v components internally. `extractSigArray` copies a fixed-length window (`SIG_LENGTH` bytes) directly out of the raw calldata under full attacker control: [4](#0-3) 
If `SIG_LENGTH` is larger than the 65 bytes actually consumed for r/s/v, an attacker can vary the unused trailing/padding bytes to produce two byte-distinct `sign` arrays that both recover to the identical address (they hash to different `merge(recoveredAddr, sign)` results but pass through `recoverAddrBySign` identically). Independently, standard ECDSA signature malleability (`s` vs `n - s` with adjusted recovery id `v`) also yields two distinct valid `(r,s,v)` byte encodings recovering to the same address for a single private key, unless canonical low-S enforcement blocks it (not confirmed from the reviewed code paths).

This bypasses the invariant that `totalWeight` should reflect distinct authorized keys, and inflates `totalWeight` past `permission.getThreshold()` using only one real key.

Note: This check in `TransactionCapsule.checkWeight`, used for on-chain transaction multi-sig validation, has its own separate (and correct) address-based de-dup via `addMap` keyed by base58-encoded address: [5](#0-4) 
That protects normal transaction signing but is a **separate code path** — it does not protect the `ValidateMultiSign`/`BatchValidateSign` TVM precompiles, which have their own (flawed) de-dup logic.

### Impact Explanation
Any smart contract that relies on `ValidateMultiSign` (address `0x...a`, TVM precompile) to gate privileged actions (fund release, permission checks, governance actions) can be tricked into believing a multi-sig threshold was met when only a single authorized key (with weight below threshold) actually approved. This is an unauthorized-state-change / asset-movement class impact: dependent contracts that release TRX/TRC20 or perform privileged operations upon `dataOne()` can be triggered without genuine multi-party authorization — directly matching "unauthorized asset movement" in the TRON bounty impact classes.

### Likelihood Explanation
- Attacker precondition: control of one key with weight `w < threshold` in the target account's permission — a normal, non-privileged setup (e.g., attacker's own multi-sig account or a shared permission they are legitimately a partial signer of).
- Attacker needs only to construct calldata to the `ValidateMultiSign` precompile from a smart contract call — fully attacker-controlled, no special node config, no MITM, no privileged role.
- Cost is limited to normal TVM energy per signature (`ENGERYPERSIGN = 1500` per entry, up to `MAX_SIZE = 5` signatures), which is cheap.
- Feasibility depends on whether `SIG_LENGTH` allows attacker-controlled padding beyond the 65 bytes consumed by `Rsv.fromSignature`, and/or whether ECDSA signature validation in `ECKey.ECDSASignature`/`SM2.SM2Signature` rejects the malleable `(r, n-s, v')` variant. These specific validation details were not confirmed within available context and should be verified directly against `Rsv.fromSignature` and `ECDSASignature.validateComponents`/canonical-S enforcement before treating this as fully proven exploitable; however, the core loop logic (fallthrough instead of `continue` when merged bytes differ) is confirmed present and is a genuine logic defect regardless of which byte-difference vector is used to trigger it.

### Recommendation
Change the de-duplication to key strictly on `recoveredAddr`, not on the concatenated `sign+addr` bytes:
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  continue; // always skip weight accumulation for an already-seen address
}
...
executedSignList.add(recoveredAddr); // no need to track merged sign bytes at all
```
Remove the `MUtil.checkCPUTime()`/fallthrough branch that allows repeated weight accumulation for an address already present in `executedSignList`. Apply the equivalent fix in `BatchValidateSign` if it shares similar logic. Additionally, confirm/enforce canonical low-S signatures in `ECDSASignature.validateComponents` to remove the ECDSA malleability vector, and confirm `extractSigArray`/`Rsv.fromSignature` do not silently ignore attacker-controlled trailing padding bytes.

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,

    }
