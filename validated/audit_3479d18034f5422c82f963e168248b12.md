### Title
Transaction backup restore accepts write-sets whose hash is never checked against the accumulator-committed `state_change_hash` - ([File: storage/backup/backup-cli/src/backup_types/transaction/restore.rs])

### Summary
When restoring a transaction backup, `LoadedChunk::load` reads `(txn, aux_info, txn_info, events, write_set)` tuples from an untrusted backup file and only calls `TransactionListWithProofV2::verify()`, which cryptographically checks the transaction hash and event root hash against the accumulator-anchored `TransactionInfo`, but never checks the `write_set` bytes against `TransactionInfo::state_change_hash`. The unverified `write_set` is then persisted directly to `WriteSetDb` and, in `kv_replay` mode, is fed into `state_store.calculate_state_and_put_updates` to reconstruct the actual state tree/state values that a restored full node serves.

### Finding Description
`LoadedChunk::load` at [1](#0-0)  deserializes `write_sets` straight from the backup chunk file, separately from the `txn_list_with_proof` structure used for cryptographic verification.

The verification call at [2](#0-1)  only builds a `TransactionListWithProofV2` from `txns`, `event_vecs`, and `txn_infos` — the `write_sets` vector is completely outside this structure and is never passed through `verify()`.

`TransactionListWithProof::verify` at [3](#0-2)  checks: version continuity, transaction-hash vs `txn_info.transaction_hash()`, the `TransactionInfo` accumulator proof against `ledger_info`, and event hashes vs `txn_info.event_root_hash()`. It never touches `txn_info.state_change_hash()` nor cross-checks it with any write-set hash.

`TransactionInfo` does carry a `state_change_hash` field that is supposed to be `CryptoHash::hash(write_set)`, as produced canonically during normal execution in [4](#0-3) . But nothing in the restore path recomputes `CryptoHash::hash(&write_set)` from the loaded `write_set` and compares it to `txn_info.state_change_hash()`.

The unverified write sets then flow to disk via `save_transactions_impl`, which writes them into `WriteSetDb` and — in the kv-replay branch — uses them to recompute state values and the state tree via `state_store.calculate_state_and_put_updates`: [5](#0-4) . This is exactly the code path invoked by `save_transactions_and_replay_kv` in [6](#0-5)  and driven from `replay_kv` in `TransactionRestoreBatchController`.

The accumulator/ledger-info proof only binds the `TransactionInfo` struct (a set of hashes) to the ledger root; it never binds the raw `write_set` bytes supplied in the backup file to anything authenticated, because the code path that would have made that binding (a hash comparison against `state_change_hash`) is missing.

### Impact Explanation
A backup file is normally treated as untrusted/replaceable data (fetched from arbitrary `BackupStorage`, e.g., S3, GCS, or any configured backend) that is supposed to be validated by cryptographic proofs before being trusted. Because the write-set hash is never checked, an attacker who can supply or tamper with a backup chunk file (compromised backup storage, MITM on backup transport, or a malicious/buggy custom `BackupStorage` implementation) can substitute an arbitrary `WriteSet` for any transaction while keeping the `Transaction` and `TransactionInfo` untouched (since those are the only fields checked). The restored node will:
- Persist the wrong `WriteSet` into `WriteSetDb` permanently (durable ledger data corruption), and
- In `kv_replay` mode, use the forged write set to compute state values/state tree that is served to clients as authenticated state, silently diverging from the value any validator actually computed.

This is a hard state-commitment integrity failure: the restored ledger's write-set-derived state can differ from the correct VM result while still appearing "verified" because the proof check that was supposed to cover this exact field is absent.

### Likelihood Explanation
Likelihood is moderate-to-high in specific but realistic deployments: any operator restoring a node or bootstrapping via `db-restore`/backup-cli from a backup storage they do not fully trust (or whose storage layer can be tampered with) is exposed. Because `write_set` is a byte blob that is trivial to swap in a chunk file without needing to forge any signature, and the exploit requires no privileged validator/consensus role — only control over the backup artifact being restored — this is a realistic, unprivileged root cause matching the state-integrity scope (restore path, write-set integrity, silent divergence from correct VM/committed state).

### Recommendation
In `LoadedChunk::load` (and any other place `write_sets` are loaded from backup, e.g., `restore_handler.save_transactions*`), after deserializing each `write_set`, recompute `CryptoHash::hash(&write_set)` and assert it equals the corresponding `txn_info.state_change_hash()` before accepting the chunk — mirroring the transaction-hash and event-root-hash checks already done in `TransactionListWithProof::verify`. Ideally, extend `TransactionListWithProofV2`/`TransactionOutputListWithProofV2` verification itself to take an optional write-set list and perform this check centrally, so all restore/replay code paths get the protection automatically rather than relying on each caller to remember it.

### Proof of Concept
1. Take a valid transaction backup chunk file (containing `(txn, aux_info, txn_info, events, write_set)` bcs records).
2. For one record, replace `write_set` with an attacker-chosen `WriteSet` (e.g., one that credits an arbitrary account with a large `AptosCoin` balance), leaving `txn`, `aux_info`, `txn_info`, and `events` untouched.
3. Run `db-restore` (or `TransactionRestoreController`) with `kv_only_replay`/`replay_from_version` pointed at this manifest, using a `BackupStorage` implementation that serves the tampered chunk file.
4. Observe: `LoadedChunk::load`'s call to `txn_list_with_proof.verify(...)` succeeds (it never inspects `write_sets`), the tampered write set is written to `WriteSetDb`, and in kv-replay mode `state_store.calculate_state_and_put_updates` recomputes state values/state tree using the forged write set — producing a state root/state values that silently diverge from the value the original VM execution produced, yet is served as authenticated state by the restored node.

Note: I was unable to execute this end-to-end in this environment (no filesystem/terminal access to run `db-restore`); the finding is based on static tracing of the verification and persistence code paths shown above. This should be reproduced/confirmed by a Devin session with terminal access if independent runtime confirmation is desired.

    pub fn verify(
        &self,
        ledger_info: &LedgerInfo,
        first_transaction_version: Option<Version>,
    ) -> Result<()> {
        // Verify the first transaction versions match
        ensure!(
            self.get_first_transaction_version() == first_transaction_version,
            "First transaction version ({:?}) doesn't match given version ({:?}).",
            self.get_first_transaction_version(),
            first_transaction_version,
        );

        // Verify the lengths of the transactions and transaction infos match
        ensure!(
            self.proof.transaction_infos.len() == self.get_num_transactions(),
            "The number of TransactionInfo objects ({}) does not match the number of \
             transactions ({}).",
            self.proof.transaction_infos.len(),
            self.get_num_transactions(),
        );

        // Verify the transaction hashes match those of the transaction infos
        self.transactions
            .par_iter()
            .zip_eq(self.proof.transaction_infos.par_iter())
            .map(|(txn, txn_info)| {
                let txn_hash = txn.committed_hash();
                ensure!(
                    txn_hash == txn_info.transaction_hash(),
                    "The hash of transaction does not match the transaction info in proof. \
                     Transaction hash: {:x}. Transaction hash in txn_info: {:x}.",
                    txn_hash,
                    txn_info.transaction_hash(),
                );
                Ok(())
            })
            .collect::<Result<Vec<_>>>()?;

        // Verify the transaction infos are proven by the ledger info.
        self.proof
            .verify(ledger_info, self.get_first_transaction_version())?;

        // Verify the events if they exist.
        if let Some(event_lists) = &self.events {
            ensure!(
                event_lists.len() == self.get_num_transactions(),
                "The length of event_lists ({}) does not match the number of transactions ({}).",
                event_lists.len(),
                self.get_num_transactions(),
            );
            event_lists
                .into_par_iter()
                .zip_eq(self.proof.transaction_infos.par_iter())
                .map(|(events, txn_info)| verify_events_against_root_hash(events, txn_info))
                .collect::<Result<Vec<_>>>()?;
        }

        Ok(())
    }
