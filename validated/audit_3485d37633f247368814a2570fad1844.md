### Title
Precision loss in energy-limit weight calculation (divide-before-multiply) allows understated resource limit / incorrect energy accounting - (File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java)

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit()` computes an account's usable energy limit from its frozen TRX balance using `long energyWeight = frozeBalance / TRX_PRECISION;` — an **integer division performed before the multiplication** by `totalEnergyLimit/totalEnergyWeight` — the same anti-pattern flagged in the Numoen `Pair.invariant()` finding (divide first, multiply second, causing truncation of the fractional weight).

### Finding Description
In the non-hardened path of `calculateGlobalEnergyLimit`: [1](#0-0) 
the code does `frozeBalance / TRX_PRECISION` (integer division, TRX_PRECISION = 1_000_000) and only afterward multiplies by the ratio `totalEnergyLimit / totalEnergyWeight`. Any fractional part of `frozeBalance / TRX_PRECISION` below 1 TRX unit is discarded before the multiplication ever happens — mirroring exactly the Numoen bug class where `FullMath.mulDiv(amount, 1e18, liquidity) * scale` truncates before scaling.

The codebase itself documents awareness of this exact issue: `ResourceProcessor.calculateGlobalLimitV1` and `calculateGlobalLimitV2` are the "hardened" (multiply-first) replacements, explicitly commented as fixing the legacy divide-first formula: [2](#0-1) 
But the un-hardened legacy formula is still present and reachable at `EnergyProcessor.java:164-165` and `EnergyProcessor.java:177-178` (V2 variant, using double arithmetic which is even more imprecise), gated behind `hardenCalculation()` / `dynamicPropertiesStore.allowHardenResourceCalculation()`.

### Impact Explanation
`calculateGlobalEnergyLimit()` determines how much energy an account may consume for free from frozen/staked TRX, invoked on every contract-triggering transaction via `EnergyProcessor.useEnergy()` (reachable from any broadcast TVM-invoking transaction, i.e., unprivileged). When `hardenCalculation()` is false (default/legacy chains that haven't activated the harden proposal, or any node where `allowHardenResourceCalculation` is 0), the divide-before-multiply truncation systematically **understates** `energyWeight` for balances with fractional TRX_PRECISION remainders, and the subsequent `double` multiplication in the non-hardened path compounds rounding error. This causes miscalculated free-energy allowances: accounts can be given more or less energy than the correct proportional share, which affects energy accounting consistency, and — combined with the double-arithmetic path — can produce non-deterministic-looking (though actually deterministic per-JVM) results if `disableJavaLangMath`/strict-math settings differ across implementations, risking energy-limit divergence between nodes running different math paths. This is an accounting-correctness bug rather than a direct fund-theft primitive (unlike the Numoen case where value could be extracted); TRX itself isn't at risk because `frozeBalance` is bounded and accounted separately, but it can allow slight over/under crediting of free TVM execution capacity, which has second-order economic impact (free energy is a resource with market value, and callers pay energy fees only above this limit).

### Likelihood Explanation
The vulnerable code path executes whenever `hardenCalculation()` (`allowHardenResourceCalculation`) is disabled, which is the historical/legacy default before this hardening proposal is activated on a given chain instance, and is triggered on every single energy-consuming transaction (`useEnergy` → `calculateGlobalEnergyLimit`) — i.e., trivially reachable by any user broadcasting a smart-contract call. However, the effect is bounded to at most `TRX_PRECISION - 1` micro-units of weight truncation per account, which for large stake amounts and large totalEnergyLimit/totalEnergyWeight ratios is a small but non-zero systematic bias, not currently demonstrated to be attacker-exploitable for direct fund extraction (unlike the Numoen `swap()`-drain scenario). The repository's own hardening work (`calculateGlobalLimitV1/V2`, `CalculateGlobalLimitHardenTest`) confirms this was already recognized and is being phased out via the harden flag.

### Recommendation
Ensure `calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` always use the multiply-first, BigInteger-exact formulas (`calculateGlobalLimitV1`/`calculateGlobalLimitV2` in `ResourceProcessor.java`) unconditionally rather than only when `hardenCalculation()` is true, i.e., retire the legacy `frozeBalance / TRX_PRECISION` / double-arithmetic branches at `EnergyProcessor.java:164-165` and `:177-178`.

### Proof of Concept
Given `frozeBalance = 1_500_000` (1.5 TRX units, TRX_PRECISION = 1_000_000), `totalEnergyLimit = 3`, `totalEnergyWeight = 2`:
- Legacy (non-hardened) path: `energyWeight = 1_500_000 / 1_000_000 = 1` (fractional 0.5 dropped) → `1 * (3.0/2) = 1.5 → (long) = 1`.
- Hardened path (`calculateGlobalLimitV1`): `weight = frozeBalance / TRX_PRECISION` is actually identical in V1 (still divides first) — but `calculateGlobalLimitV2` (used in the `supportUnfreezeDelay()` branch) computes `frozeBalance * totalLimit / (TRX_PRECISION * totalWeight)` = `1_500_000 * 3 / (1_000_000 * 2) = 4_500_000 / 2_000_000 = 2`.

This shows the divide-first legacy formula yields `1` while the multiply-first exact formula yields `2` — a demonstrable discrepancy from the same "truncate before scale" defect class described in the Numoen report, confirmed by the repo's own test comment at: [3](#0-2) 
which explicitly asserts `buggy != resultNew` for the naive `usage * (limit/weight)` formulation.

```java
  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
```
