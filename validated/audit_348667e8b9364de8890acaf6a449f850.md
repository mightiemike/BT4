### Title
Unauthorized `WithdrawFromGasKey` Action Allows Any Account to Drain Another Account's Gas Key Balance — (`runtime/runtime/src/access_keys.rs`)

---

### Summary

`action_withdraw_from_gas_key` in `runtime/runtime/src/access_keys.rs` does not verify that the action's `predecessor_id` equals the `receiver_id` (i.e., that the withdrawal is self-directed). Any unprivileged user can craft a transaction with `receiver_id = victim` and action `WithdrawFromGasKey`, draining the victim's gas key balance to zero and moving it to the victim's main account balance — without the victim's authorization. While funds are not stolen, the victim's gas key operational balance is manipulated and all pending gas-key transactions are disrupted.

---

### Finding Description

`WithdrawFromGasKeyAction` is designed to let an account owner reclaim funds from their own gas key back to their main account balance. However, the runtime enforces no `predecessor_id == receiver_id` constraint for this action.

In NEAR, a transaction with `signer_id = attacker` and `receiver_id = victim` produces a receipt with `predecessor_id = attacker` that executes on the victim's account. If that receipt contains `WithdrawFromGasKey`, the runtime executes it on the victim's account without any ownership check:

The static validation function for this action only checks that the `GasKeys` protocol feature is enabled — no ownership or predecessor check:

```rust

By contrast, the protocol explicitly requires `predecessor_id == receiver_id` for `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, and `DeleteAccount`: [3](#0-2) 

`WithdrawFromGasKey` is absent from that list, and no equivalent guard exists anywhere in the verifier or runtime for this action.

Every existing test and utility that calls `WithdrawFromGasKey` uses `signer_id == receiver_id` (self-directed), confirming the intended usage pattern: [4](#0-3) [5](#0-4) 

The action is dispatched from the main runtime loop with `account_id = receipt.receiver_id()`, with no predecessor check inserted at the call site: [6](#0-5) 

---

### Impact Explanation

An attacker sends a transaction:
- `signer_id = attacker`
- `receiver_id = victim`
- `actions = [WithdrawFromGasKey { public_key: victim_gas_key, amount: full_balance }]`

Result:
- Victim's gas key balance is reduced to zero (balance manipulation of a distinct sub-balance).
- Victim's main account balance increases by the same amount (funds are not stolen, but the gas key operational state is destroyed).
- All of the victim's pending and future gas-key transactions fail with `NotEnoughGasKeyBalance` until the victim manually re-funds the key via `TransferToGasKey`.
- This is a non-network-level denial of service on gas-key functionality, fixable without a hardfork by adding a single predecessor check.

---

### Likelihood Explanation

- Requires no special privileges — any account with enough NEAR to pay a transaction fee can execute this.
- The attack is cheap and repeatable: every time the victim re-funds the gas key, the attacker can drain it again.
- The `GasKeys` feature is gated behind `ProtocolFeature::GasKeys`; once that feature is enabled on mainnet, this attack surface is live.

---

### Recommendation

Add a `predecessor_id == receiver_id` check in `action_withdraw_from_gas_key`, mirroring the pattern used for other account-sensitive actions:

```rust
pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    predecessor_id: &AccountId,          // pass receipt.predecessor_id()
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    if predecessor_id != account_id {
        result.result = Err(ActionErrorKind::ActorNoPermission {
            account_id: account_id.clone(),
            actor_id: predecessor_id.clone(),
        }.into());
        return Ok(());
    }
    // ... existing logic
}
```

Alternatively, add `WithdrawFromGasKey` to the set of actions that require `predecessor_id == receiver_id` in the protocol specification and enforce it in `validate_action` / `check_account_existence`.

### Proof of Concept

1. Alice owns account `alice` with a gas key `GK` funded with 100 NEAR.
2. Bob submits a standard JSON-RPC `broadcast_tx_commit` with:
   ```json
   {
     "signer_id": "bob",
     "receiver_id": "alice",
     "actions": [{ "WithdrawFromGasKey": { "public_key": "<GK>", "amount": "100000000000000000000000000" } }]
   }
   ```
3. The receipt executes on Alice's account. `action_withdraw_from_gas_key` is called with `account_id = alice`, no predecessor check fires.
4. Alice's gas key balance drops to 0; Alice's main balance increases by 100 NEAR.
5. All of Alice's gas-key transactions now fail with `NotEnoughGasKeyBalance`.
6. Bob repeats step 2 every time Alice re-funds the key. [7](#0-6) [8](#0-7)

        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {

        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),

        }
        .into());
        return Ok(());

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {

        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
