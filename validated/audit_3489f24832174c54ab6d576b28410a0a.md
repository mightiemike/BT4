Unbounded, non-deduplicated per-shop session-ID array growth in `KVSessionStorage` causes DoS of session lookup/auth flows - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
`KVSessionStorage.addShopIds` appends a session ID to the per-shop index array on every `storeSession` call without checking whether the ID is already present, unlike the equivalent Redis implementation which explicitly deduplicates. Because `storeSession` is re-invoked on ordinary, unprivileged authentication paths (token exchange on every expired/near-expiry session), the per-shop array can grow without bound and is later loaded/parsed/iterated in full by `findSessionsByShop` and rewritten in full by `addShopIds`/`removeShopIds`, degrading and eventually breaking session lookup for that shop — mirroring the classic "array updates are not constant time" bug class (unbounded push + full linear scan/rewrite).

### Finding Description
`KVSessionStorage.storeSession` stores the session blob and then calls `addShopIds`: [1](#0-0) 

`addShopIds` unconditionally concatenates the new ID(s) onto the existing array and rewrites the whole JSON blob, with no de-duplication check: [2](#0-1) 

Compare this to `RedisSessionStorage.addKeyToShopList`, which guards against duplicates: [3](#0-2) 

`storeSession` is not a one-time operation confined to initial installation — it is re-invoked on the normal, unprivileged token-exchange authentication path whenever a request lacks an active session (including sessions "within expiry"): [4](#0-3) 

Because the offline session ID is deterministic per shop, every one of these re-exchanges calls `addShopIds(shop, [sameOfflineSessionId])` again, appending a duplicate entry to the shop's index array each time, with the array size growing linearly with the number of token-exchange/re-auth events for that shop (App Bridge routinely refreshes session tokens, and any 401/invalid-token response also triggers this path via `respondToInvalidSessionToken`).

Downstream, `findSessionsByShop` reads the entire ID array and does a `Promise.all` load over every entry (including all duplicates), and `removeShopIds`/`addShopIds` each read-modify-write the entire array on every session store/delete: [5](#0-4) [6](#0-5) 

This satisfies the reported bug class exactly: an array that grows without bound (never deduplicated/bounded) while being fully scanned/rewritten/loaded on every subsequent operation.

### Impact Explanation
As the per-shop ID array grows, every `storeSession`, `deleteSession`, and `findSessionsByShop` call for that shop becomes progressively slower (linear read + full JSON re-serialization + `Promise.all` fan-out of KV `get`s for duplicate IDs). This directly degrades and can eventually break the authentication path (`AppInstallations.includes`/`AppInstallations.delete` and `findSessionsByShop` consumers, and the token-exchange session store), producing a denial-of-service against session lookups for the affected shop. Cloudflare KV values also have a hard size ceiling (25 MiB); sustained unbounded appends can eventually cause writes to the shop index key to fail outright, permanently breaking session persistence/lookup for that shop until manually repaired.

### Likelihood Explanation
This requires no privileged access — it is triggered purely by normal embedded-app traffic: App Bridge refreshes session tokens roughly every minute, and any transient 401/invalid-session-token response re-triggers `TokenExchangeStrategy.authenticate`'s "no valid session" branch, each of which calls `storeSession` and therefore `addShopIds` again with the same offline session ID. A single active merchant session over time, or an attacker deliberately forcing repeated re-authentication (e.g., by invalidating/expiring their own session or replaying old-but-still-valid session tokens), will steadily grow the array. This is a realistic, low-effort, entirely unprivileged trigger.

### Recommendation
In `KVSessionStorage.addShopIds`, deduplicate before writing, mirroring the Redis adapter's pattern:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```
More broadly, enforce a codebase policy (as recommended in the underlying report) that any array acting as an index be either bounded or deduplicated, and add a regression test asserting that repeated `storeSession` calls with the same session ID do not grow `findSessionsByShop`'s result count.

### Proof of Concept
1. Configure an embedded app with `KVSessionStorage` as `sessionStorage`.
2. As a normal merchant, load the app; `TokenExchangeStrategy.authenticate` runs because no session exists, calling `storeSession(offlineSession)` → `addShopIds(shop, [offlineSession.id])`.
3. Force the "no valid session" branch to re-run repeatedly (e.g., wait past `WITHIN_MILLISECONDS_OF_EXPIRY`, or trigger repeated `respondToInvalidSessionToken` 401 responses, or simply reload the embedded app iframe multiple times in quick succession, which is standard App Bridge behavior) — each iteration calls `storeSession` with the same deterministic offline `session.id`.
4. Inspect the KV value at key `shop:<shop-domain>`: it now contains N duplicate copies of the same session ID, where N equals the number of token-exchange invocations.
5. Call `findSessionsByShop(shop)`: it performs N redundant `loadSession` KV reads instead of 1, and this cost grows unboundedly with continued normal usage, eventually causing timeouts/failures in `AppInstallations.includes`/`delete` and in `findSessionsByShop` consumers, or hitting the KV per-value size cap on the index key itself.
