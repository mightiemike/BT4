### Title
Precision Loss in Legacy Vote-Reward Calculation via Divide-Before-Multiply in `MortgageService.computeReward` (Old Algorithm Path) - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a witness's cycle reward by first dividing `userVote` by `totalVote` into a `double`, then multiplying that ratio by `totalReward`. This is the same "divide-before-multiply" precision-loss pattern described in the `FluxToken.sol::getClaimableFlux` report: the correct order to preserve maximum precision is `userVote * totalReward / totalVote`, but the code instead performs the division first (losing precision in the intermediate ratio) and only then multiplies, before truncating to `long` via `reward +=`.

### Finding Description
In the legacy ("old") reward algorithm path used for cycles before `newRewardAlgorithmEffectiveCycle`, per-voter reward is computed as: [1](#0-0) 

```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```

This mirrors exactly the bug class in the report: division is performed before multiplication (`userVote/totalVote` computed first), rather than `userVote * totalReward / totalVote`. Because `double` has only ~52 bits of mantissa, and TRON balances/vote counts can be large (`long`), the early division step discards precision that the later multiplication cannot recover, and the final implicit `double -> long` narrowing (via `reward +=`) truncates any fractional remainder toward zero. The mathematically correct integer computation `(userVote * totalReward) / totalVote` (as used consistently elsewhere in the codebase for the *new* reward algorithm, e.g. `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)` in the same file) is provably more precise and is exactly the "multiply first" fix the report recommends.

This routine is reached by any account holder calling `withdrawReward`/`queryReward` through `MortgageService`, which is invoked from voting/reward actuators reachable by ordinary, unprivileged transactions: [2](#0-1) [3](#0-2) 

The dispatch to the vulnerable old-algorithm path is conditioned only on `beginCycle < newAlgorithmCycle`: [3](#0-2) 

Notably, the codebase already demonstrates awareness of this exact bug class elsewhere: for resource/energy accounting, a "hardened" `BigInteger`-based replacement was specifically added with a docstring stating it fixes double-precision loss from computing `((double) frozeBalance / TRX_PRECISION) * ((double) totalLimit / totalWeight)` (divide-then-multiply) by instead multiplying first and dividing last: [4](#0-3) 
No equivalent hardening/BigInteger fix exists for the legacy vote-reward `voteRate` calculation in `MortgageService.computeReward(long, List)`.

### Impact Explanation
Because reward is calculated as `voteRate * totalReward` where `voteRate` is a lossy `double` ratio, voters can receive slightly less TRX allowance than the exact proportional share `userVote * totalReward / totalVote` would yield. The lost fraction is not returned to the voter and is not tracked/redistributed elsewhere, resulting in a small but real "freezing"/loss of rewards for affected voters for every cycle computed via the old algorithm. This matches the reported impact category of "permanent freezing" of a proportional share of rewards due to precision loss, applied here to on-chain TRX voting rewards rather than an off-chain Solidity token.

### Likelihood Explanation
The vulnerable path executes automatically and unconditionally whenever `computeReward(beginCycle, endCycle, accountCapsule)` is invoked for any cycle range that includes cycles prior to `newRewardAlgorithmEffectiveCycle` (i.e., any voter whose reward-accrual window spans old-algorithm cycles). This is triggered by ordinary `withdrawReward`/`queryReward` calls, which any account can invoke without special privileges. On networks/chains where `newRewardAlgorithmEffectiveCycle` has already passed all cycles, this code path is dormant for future cycles but remains load-bearing for historical cycle computations whenever accounts finally withdraw/query old, unclaimed rewards — this can happen at any time an account with old pending votes interacts with the reward system, making the likelihood of triggering the calculation moderate-to-high, though the resulting discrepancy per call is small (bounded by floating-point precision limits relative to `long` reward magnitudes).

### Recommendation
Replace the floating-point divide-then-multiply computation with an integer/`BigInteger` multiply-then-divide, consistent with the pattern already used for the new reward algorithm and for `ResourceProcessor.calculateGlobalLimitV2`:

```java
// before
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;

// after
reward += BigInteger.valueOf(userVote)
    .multiply(BigInteger.valueOf(totalReward))
    .divide(BigInteger.valueOf(totalVote))
    .longValueExact();
```

This eliminates the early lossy division and only truncates once, at the very end, preserving maximal precision — mirroring the fix already applied for `calculateGlobalLimitV2` and the new-algorithm Vi-based reward computations in the same class.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
