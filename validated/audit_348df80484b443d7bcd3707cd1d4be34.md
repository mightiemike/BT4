### Title
`store_account_and_update_capitalization` computes capitalization delta from a non-write-cache load, allowing a stale/wrong-version balance to silently corrupt `Bank::capitalization` - (File: `runtime/src/bank.rs`)

### Summary
`Bank::store_account_and_update_capitalization` reads the "old" version of an account via `get_account_with_fixed_root_no_cache`, which is documented to explicitly skip the read-only cache population path, and then computes the capitalization delta from that read before calling `store_account`. This mirrors the ELFI class of bug: an aggregate/derived value (capitalization, analogous to the pool's borrowing rate) is updated using a value that is not guaranteed to reflect the very latest state at the time of the state-changing write, rather than being derived transactionally from the same store operation.

### Finding Description
`get_account_with_fixed_root_no_cache` at [1](#0-0)  calls `load_with_fixed_root_do_not_populate_read_cache`, which invokes `AccountsDb::load` with `PopulateReadCache::False` [2](#0-1) . This still goes through the normal `do_load` path (write cache first, then read-only cache, then storage) so under single-threaded/serial use it will report the correct current version. However, `store_account_and_update_capitalization` performs the pattern of (1) load old account, (2) compute lamport diff and mutate `self.capitalization` via `fetch_add`/`fetch_sub`, and (3) only afterward call `self.store_account(pubkey, new_account)`: [3](#0-2) 

This is structurally identical to the ELFI bug pattern: the capitalization delta (an aggregate derived quantity, analogous to the borrowing rate derived from `baseTokenBalance`) is computed from a *separately read* prior state rather than atomically as part of the same store operation that changes the balance. Any caller invoking `store_account_and_update_capitalization` concurrently for the *same pubkey* (or with a concurrent flush/clean that changes what "old" resolves to) can compute an incorrect `old_account.lamports()` baseline, causing `self.capitalization` to drift from the true sum of the ledger's lamports — a silent capitalization divergence. This is different from `commit_transactions`' `update_bank_hash_stats`, which is fed directly from the accounts actually being stored (`&to_store`), not from a separately-issued read of "prior" state.

### Impact Explanation
`Bank::capitalization` is a consensus-relevant, exposed value included in a bank's hash computation and RPC-visible supply/`get_supply` figures. A silent drift between `capitalization` and the true summed lamports of all accounts is a capitalization divergence, one of the explicitly accepted bug classes ("hash/capitalization divergence", "silent balance change"). Because `store_account_and_update_capitalization` is used for balance-affecting book-keeping paths (e.g., precompile account burn/replace via `burn_and_purge_account`/`add_precompiled_account_with_owner` at [4](#0-3) , and other internal reward/administrative flows), an incorrect capitalization baseline would propagate into snapshot capitalization fields and any consensus/verification code path that recomputes and compares capitalization (`calculate_capitalization_at_startup_from_index`), producing an honest-node snapshot-vs-replay mismatch if the concurrently-read "old" value differs from what is truly committed.

### Likelihood Explanation
This is a narrow, internal (non-transaction) code path rather than one reachable directly from unprivileged user transactions, so the reachable trigger conditions are limited to whatever internal callers invoke `store_account_and_update_capitalization` concurrently for the same key, or interleave it with other writers to the same account outside of normal `Bank::store_accounts` (which serializes through the stakes-cache/lt-hash pipeline). I was not able to fully confirm from the indexed code whether any caller of `store_account_and_update_capitalization` can race with a competing writer of the same pubkey in production replay ordering (replay is generally single-threaded per bank for a given pubkey's sequence of writes), which would make the practical likelihood low absent such a race. This uncertainty is a gap in my analysis given the available index; a full audit of all call sites and their execution contexts (e.g., during epoch-boundary reward distribution, feature activation) would be needed to confirm actual concurrent-write reachability.

### Recommendation
Compute the capitalization delta atomically with the store, e.g. by having `store_account_and_update_capitalization`/`store_account` return the previous account state directly from the same store operation (as `update_index_for_flush`/`upsert` already do via `reclaims`), rather than issuing a separate `get_account_with_fixed_root_no_cache` read beforehand. This removes the window in which the "old" value used for the capitalization diff can diverge from the value actually being replaced by the subsequent store, closing the analog of the ELFI "stale aggregate/rate" class of bug.

### Proof of Concept
Not able to construct a concrete reproducing PoC from the available indexed code alone: doing so requires confirming (from `runtime/src/bank.rs` and its callers, which could not be fully retrieved from the index within the given search budget) a code path where two writers can call `store_account_and_update_capitalization` for the *same* `pubkey` concurrently, or where a flush/clean can retarget which slot `get_account_with_fixed_root_no_cache` resolves to between the read and the subsequent `store_account` call. A Devin session with full repository access would be needed to enumerate all call sites of `store_account_and_update_capitalization` and check for concurrent-invocation patterns before this can be escalated from a structural pattern match to a proven, exploitable divergence.

    /// Technically this issues (or even burns!) new lamports,
    /// so be extra careful for its usage
    pub(crate) fn store_account_and_update_capitalization(
        &self,
        pubkey: &Pubkey,
        new_account: &AccountSharedData,
    ) {
        let old_account_data_size = if let Some(old_account) =
            self.get_account_with_fixed_root_no_cache(pubkey)
        {
            match new_account.lamports().cmp(&old_account.lamports()) {
                std::cmp::Ordering::Greater => {
                    let diff = new_account.lamports() - old_account.lamports();
                    trace!("store_account_and_update_capitalization: increased: {pubkey} {diff}");
                    self.capitalization.fetch_add(diff, Relaxed);
                }
                std::cmp::Ordering::Less => {
                    let diff = old_account.lamports() - new_account.lamports();
                    trace!("store_account_and_update_capitalization: decreased: {pubkey} {diff}");
                    self.capitalization.fetch_sub(diff, Relaxed);
                }
                std::cmp::Ordering::Equal => {}
            }
            old_account.data().len()
        } else {
            trace!(
                "store_account_and_update_capitalization: created: {pubkey} {}",
                new_account.lamports()
            );
            self.capitalization
                .fetch_add(new_account.lamports(), Relaxed);
            0
        };

        self.store_account(pubkey, new_account);

        // If the new account has zero lamports, that means it is being closed.
        let new_account_data_size = if new_account.lamports() == 0 {
            0
        } else {
            new_account.data().len()
        };
        self.calculate_and_update_accounts_data_size_delta_off_chain(
            old_account_data_size,
            new_account_data_size,
        );
    }
