## Title
Stale `is_v2` snapshot in `OverlayStateProvider` causes trie-table type/encoding mismatch on the shared `AccountsTrie`/`StoragesTrie` MDBX table - (File: `crates/storage/storage-overlay/src/provider.rs`)

### Summary
`reth` implements a v1→v2 storage migration in which the on-disk `AccountsTrie`/`StoragesTrie` MDBX tables are reinterpreted with a different key/subkey encoding: legacy `StoredNibbles`/`StoredNibblesSubKey` (65-byte, 1 nibble/byte) versus packed `PackedStoredNibbles`/`PackedStoredNibblesSubKey` (33-byte, 2 nibbles/byte), exposed as separate `Table` types (`tables::AccountsTrie`/`tables::StoragesTrie` vs `PackedAccountsTrie`/`PackedStoragesTrie`) that share the **same underlying MDBX table name** [1](#0-0) . This is structurally identical to the reported Slither finding: one raw storage location (here, one MDBX table) is written and read using two different type/encoding schemes selected by a runtime flag, and the underlying storage engine has no way to detect a mismatch.

### Finding Description
The correct encoding to use is determined by `StorageSettingsCache::cached_storage_settings().is_v2()`, and the codebase's own convention (`reth_trie_db::with_adapter!`) is to check this **live, at the point of use**, for every trie cursor factory construction [2](#0-1) . This pattern is used consistently for state-root computation and trie writes (`write_trie_updates_sorted`, `compute_state_root`, `LatestStateProviderRef::state_root`, the merkle stage, etc.) [3](#0-2) [4](#0-3) .

However, `OverlayStateProvider` breaks this pattern: `OverlayStateProviderFactory::database_provider_ro` reads `is_v2` **once** when constructing the provider and stores it as a plain `bool` field, rather than re-checking `cached_storage_settings()` at read time: [5](#0-4) 

That cached `self.is_v2` boolean is then used to pick the trie-cursor adapter for every subsequent read through that provider instance: [6](#0-5) 

Meanwhile, `write_trie_updates_sorted` (invoked by the merkle/execution stages and by `v1→v2` migration finalization) determines the encoding via a **fresh** read of `cached_storage_settings()` on every call [3](#0-2) , and the `reth db migrate-v2` command flips `StorageSettings` to v2 in a live transaction and commits it [7](#0-6) .

If an `OverlayStateProvider` (or an `OverlayStateProviderFactory` whose `state_trie_overlay_cache` and constructed providers can outlive a storage-settings flip) is created/held with `is_v2 = false` and the node then completes the v1→v2 migration (or vice-versa in any code path that snapshots settings once and reuses the provider across the flip), the overlay provider will keep decoding the (now-repacked) `AccountsTrie`/`StoragesTrie` bytes with the stale adapter: e.g., interpreting 33-byte packed nibble keys as 65-byte legacy `StoredNibblesSubKey`, or vice versa. Because `Encode`/`Decode` for these key types is a pure byte-reinterpretation with no self-describing tag (`StoredNibbles::decode`/`PackedStoredNibbles::decode` both blindly call `from_compact` on whatever bytes MDBX returns) [8](#0-7) , this produces garbage `Nibbles`/`BranchNodeCompact` values instead of a decode error in most cases (the layouts are different lengths and the "nibble length" byte is at a different offset), silently corrupting the recovered trie shape.

### Impact Explanation
This breaks the "state read differs from committed post-state" / "state root differs from a full recompute" equality class. An `OverlayStateProvider` that decodes the trie under the wrong encoding will build a `TrieCursor` walk over corrupted nibble paths and branch masks, producing a `state_root`/`state_root_with_updates` that is wrong relative to a correct (freshly-checked) recompute of the same on-disk state, e.g. via `LatestStateProviderRef::state_root` (which uses `with_adapter!` fresh) or the merkle stage's independent recompute. A wrong state root produced by an execution/proof/overlay path that diverges from the canonical recompute is a High/Critical-class defect (self-consistency break within a single node, and if propagated into a produced block, a reth-built block that would be rejected by other clients).

### Likelihood Explanation
This requires the `is_v2` snapshot to actually go stale relative to a live migration or settings flip while an `OverlayStateProvider`/`OverlayStateProviderFactory` instance created before the flip is still being used for reads — i.e., it is a narrow, operational-timing window (during `reth db migrate-v2`, or any other path where storage settings are updated on a live `ProviderFactory` while overlay providers persist), not attacker-triggerable via a single malicious transaction. I could not fully trace every call site that constructs/reuses `OverlayStateProviderFactory` across a live settings flip within the tool-call budget, so I cannot confirm a concrete reachable trigger sequence (e.g., whether the engine tree keeps a long-lived `OverlayStateProviderFactory` across the v1→v2 migration boundary) — this needs further verification with the full codebase/tests to establish a certain reachable path.

### Recommendation
- Make `OverlayStateProvider`'s trie-cursor selection call `self.provider().cached_storage_settings().is_v2()` live at read time (matching the `with_adapter!` convention used elsewhere) instead of caching a `bool` snapshot at construction.
- Alternatively, invalidate/rebuild all outstanding `OverlayStateProviderFactory`/`OverlayStateProvider` instances (and their `state_trie_overlay_cache`) whenever `StorageSettingsCache::set_storage_settings_cache` changes the v1/v2 flag, so no reader can hold a stale encoding assumption about the shared `AccountsTrie`/`StoragesTrie` table.
- Longer term, consider giving `PackedAccountsTrie`/`PackedStoragesTrie` and the legacy tables a self-describing on-disk tag (e.g., a version byte) so a decode-time mismatch fails loudly (`DatabaseError::Decode`) instead of silently producing a structurally-plausible but wrong `Nibbles`/`BranchNodeCompact`.

### Proof of Concept
Not independently verified end-to-end due to tool budget; the mechanism is demonstrated by code inspection:
1. Construct `OverlayStateProviderFactory` and call `database_provider_ro()` while `cached_storage_settings().is_v2() == false`; the returned `OverlayStateProvider` stores `is_v2 = false` [5](#0-4) .
2. While holding that provider, run `reth db migrate-v2` (or otherwise flip `StorageSettings` to v2 and `write_trie_updates`) so the `AccountsTrie`/`StoragesTrie` MDBX tables now contain packed (33-byte) entries.
3. Call `state_root`/`account_trie_cursor` on the previously-created `OverlayStateProvider`; it uses `LegacyKeyAdapter` (`tables::AccountsTrie`, `StoredNibbles`/`StoredNibblesSubKey`) to decode bytes that were written as `PackedStoredNibbles`/`PackedStoredNibblesSubKey`, producing corrupted nibble paths/branch masks and a wrong root, diverging from a fresh recompute via `LatestStateProviderRef::state_root`, which always re-checks `cached_storage_settings()` live [9](#0-8) .

        Self: 'a;

        = InMemoryTrieCursor<'a, Box<dyn TrieStorageCursor + Send + 'a>>
    where
        Self: 'a;

    fn account_trie_cursor(&self) -> Result<Self::AccountTrieCursor<'_>, DatabaseError> {
        let overlay = self.state_trie_overlay(true).map_err(into_database_error)?;
        let cursor: Box<dyn TrieCursor + Send> = if self.is_v2 {
            Box::new(DatabaseAccountTrieCursor::<_, PackedKeyAdapter>::new(

            Box::new(DatabaseAccountTrieCursor::<_, LegacyKeyAdapter>::new(
                self.provider().tx().cursor_read::<tables::AccountsTrie>()?,
            ))
        };
        Ok(InMemoryTrieCursor::new_account(cursor, &overlay.input().nodes))
    }
