### Title
Anyone can grief `DeleteKey`/`DeleteAccount` by inflating a victim's gas-key balance via unrestricted `TransferToGasKey` - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
`action_transfer_to_gas_key` credits `gas_key_info.balance` on the receiver account's gas key without checking that the receipt's predecessor is the account owner. `action_delete_key`/`action_delete_account` reject the operation with `GasKeyBalanceTooHigh` whenever `gas_key_info.balance` (or the account's summed gas-key balance) exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR). An attacker can therefore send a `TransferToGasKey` receipt to a victim's gas key, front-run/precede the victim's `DeleteKey`/`DeleteAccount` transaction, and permanently block it — the same "balance used as a completion/permission gate that anyone can perturb" pattern described in the external report (`isLiquidationActive` griefed via a dust transfer).

### Finding Description
`action_transfer_to_gas_key` looks up the access key on `account_id` (the receipt's receiver) and adds `action.deposit` to `gas_key_info.balance`, with no actor/permission check tying the caller to the account owner: [3](#0-2) 

Compare this to the set of actions that the runtime restricts to `predecessor_id == receiver_id` (self-only, administrative actions): `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`. `TransferToGasKey`/`WithdrawFromGasKey` are documented separately and are not in that self-only set: [4](#0-3) [5](#0-4) 

Meanwhile, `delete_gas_key` (invoked from `action_delete_key`) and `action_delete_account`'s gas-key-burn accounting both hard-fail if the balance exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN`: [6](#0-5) [7](#0-6) 

Because any account can send a transaction/receipt containing a `TransferToGasKey` action targeting an arbitrary victim account's public key (the action only requires the key to exist and be a gas key — it does not require `predecessor_id == account_id`), an attacker holding no privileges on the victim account can push the gas key's balance above 1 NEAR, causing every subsequent `DeleteKey` (for that key) or `DeleteAccount` (which sums all gas-key balances) issued by the legitimate owner to fail with `GasKeyBalanceTooHigh`. This exactly parallels the report's bug class: a balance value used as a gating condition for a privileged operation ("is liquidation finished" / "can this key/account be deleted") can be manipulated by an unrelated third party sending funds to the relevant location, permanently (or repeatedly) blocking the intended operation.

### Impact Explanation
This is a griefing/denial-of-service vector reachable purely from a single submitted transaction/receipt by any signer: the victim's own account/key management (deleting a gas key or deleting the account entirely) becomes permanently blocked as long as the attacker keeps topping up the gas key with tiny deposits above the 1 NEAR burn threshold. Since `DeleteAccount` requires clearing the account, this can permanently freeze an account's ability to self-delete (frozen state transition), and force the owner to instead call `WithdrawFromGasKey` first — which is itself gate-able similarly if the attacker keeps re-funding it, or is otherwise limited by amount thresholds. At minimum this is a state-transition-blocking, transaction-triggered griefing bug affecting availability of account cleanup for any account with a gas key, satisfying "permanently frozen funds"/"invalid state transition rejection" categories for gas-key balances that legitimately should have been withdrawable/burnable.

### Likelihood Explanation
High reachability: `TransferToGasKey` is a plain action available to any signer/relayer targeting any receiver with a known public key that holds a gas key (gas keys and their public keys can be discovered via RPC `view_access_key_list`). No special privilege, staking, or validator status is required — an ordinary RPC caller submitting a transaction is sufficient. The griefing cost is minimal (attacker just needs to fund slightly over 1 NEAR total across the target's gas keys, one time, and it stays blocked unless the owner withdraws it back below the threshold first).

### Recommendation
Restrict `TransferToGasKey` (and consider `WithdrawFromGasKey`) to self-only actions, i.e. require `predecessor_id == receiver_id` in the actor-permission check (the same list that already includes `AddKey`/`DeleteKey`/`Stake`/`DeployContract`/`DeleteAccount`), unless third-party funding of gas keys is an explicitly intended feature — in which case the `GasKeyBalanceTooHigh` gate in `delete_gas_key`/`action_delete_account` should not treat "balance too high" as an unconditional failure that blocks deletion; instead, any balance above the burn threshold should be automatically refunded/burned rather than rejecting the whole action, so a third party cannot use it to lock the owner out of deleting their own key/account.

### Proof of Concept
1. Victim `alice.near` adds a `GasKeyFullAccess`/`GasKeyFunctionCall` access key `PK` (a "gas key") to her account.
2. Attacker `eve.near` submits a transaction with a single `TransferToGasKey { public_key: PK, deposit: 2 NEAR }` action, receiver `alice.near` — this succeeds because `action_transfer_to_gas_key` performs no actor/permission check against the predecessor (see `runtime/runtime/src/access_keys.rs:257-288`), and `TransferToGasKey` is not restricted to `predecessor_id == receiver_id` per `docs/RuntimeSpec/Actions.md:26-35`.
3. `alice.near` now attempts `DeleteKey { public_key: PK }` (or `DeleteAccount`). `delete_gas_key`/`action_delete_account` computes `gas_key_info.balance` (2 NEAR) `> GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR) and returns `ActionErrorKind::GasKeyBalanceTooHigh`, aborting the deletion (`runtime/runtime/src/access_keys.rs:93-111`, `runtime/runtime/src/actions.rs:330-379`).
4. Eve repeats step 2 whenever Alice tries to withdraw the balance below the threshold, indefinitely blocking Alice from deleting the key/account.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
