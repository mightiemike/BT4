### Title
Unhandled `receiver_shard_id()` error causes chunk-processing panic on stale `GlobalContractDistribution` receipts - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` calls `receiver_shard_id()` on every delayed receipt and unconditionally `.unwrap()`s the `Result`. For `GlobalContractDistribution` receipts, `receiver_shard_id()` returns `Err(EpochError::ShardingError)` whenever the receipt's `target_shard` cannot be resolved to a shard in the current layout — a state that a resharding-crossing delayed receipt can still reach even with the existing `resolve_to_current_shard` fallback. This mirrors CVE-2018-12479's bug class: a value that is attacker/environment-influenced (a stale shard/target id carried in a receipt, analogous to a "crafted request id") is not defensively validated before being unwrapped, causing a crash instead of a graceful error, which halts chunk production (DoS) for every honest node applying that chunk.

### Finding Description
`Receipt::receiver_shard_id()` at [1](#0-0)  returns `Ok(shard_id)` for ordinary receipts by direct account-to-shard mapping, but for `ReceiptEnum::GlobalContractDistribution` receipts it must resolve a `target_shard` value that may be from an arbitrarily old shard layout (the receipt may have sat in the delayed-receipt queue across multiple resharding events). It attempts `shard_layout.resolve_to_current_shard(target_shard)`, and only if that lookup succeeds does it return `Ok`; otherwise it returns `Err(EpochError::ShardingError(...))`.

That fallible result is called from `receipt_filter_fn` in `DelayedReceiptQueueWrapper`, used both when popping receipts for processing and when peeking the delayed queue: [2](#0-1) 

The call site unconditionally unwraps:
```
let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
```
If `resolve_to_current_shard` cannot map the stale `target_shard` (e.g., because the shard's split-history bookkeeping does not go back far enough, the shard was merged/removed via a different resharding path, or any other layout-history gap not covered by the split-history lookup), this `.unwrap()` panics inside `process_receipts` → `process_delayed_receipts` → `pop()`/`peek_iter()`, which is on the hot path of applying every chunk: [3](#0-2) 

An existing regression test in the repo demonstrates the exact reachable scenario and explicitly documents the panic outcome as the "vulnerability" it guards against: [4](#0-3) 

The test constructs the condition by having an unprivileged account (`user0`) submit an ordinary `DeployGlobalContract` transaction, then saturating the shard's compute budget with normal transactions so the resulting `GlobalContractDistribution` receipt is pushed to the delayed-receipt queue and survives two sequential resharding events before being drained — all of which are actions reachable purely from a stream of user-submitted, protocol-valid transactions with no validator or network privilege required. The test's own comment states: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations."* While the specific two-resharding-generation case is now handled via `resolve_to_current_shard`, the underlying design defect remains: `receiver_shard_id()` is `Result`-returning specifically because target-shard resolution across resharding history *can* fail, yet the only consumer in the delayed-receipt hot path (`receipt_filter_fn`) discards that possibility with `.unwrap()` rather than propagating the error. Any layout-history edge case beyond what `resolve_to_current_shard` currently covers (e.g., additional resharding generations, non-split layout transitions, or GC of split-history data before a heavily delayed receipt drains) reaches the same unwrap panic.

### Impact Explanation
A panic inside `process_delayed_receipts`/`pop()`/`peek_iter()` occurs while applying a chunk — this is consensus-critical code executed by every validator/chunk-producer applying that shard's state transition. A panic here crashes the node process (or aborts chunk application), which for all honest nodes processing the same chunk produces a transaction-triggered halt of chunk/block production on the affected shard — a concrete, reachable DoS impact consistent with the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Reaching this bug requires only standard user capabilities already demonstrated as sufficient in this codebase: (1) deploy a global contract (any account can do this), and (2) cause the resulting distribution receipt to become delayed and outlive the shard-layout history depth that `resolve_to_current_shard` can traverse — achievable by generating enough compute-saturating transactions across enough resharding cycles, similar to the regression test's own construction. This does not require validator, network, or leaked-key privilege; it is purely a function of transaction volume and timing relative to resharding events, both attacker-influenceable by any unprivileged sender given sustained gas budget.

### Recommendation
Do not `.unwrap()` the `Result` from `receiver_shard_id()` in `receipt_filter_fn` (and any other delayed-queue consumer). Propagate the `EpochError` up through `pop()`/`peek_iter()` as a proper `RuntimeError`/`Result`, and decide on a safe, deterministic fallback behavior for unresolvable stale `target_shard` values (e.g., treat as "not this shard" and keep in the delayed queue, or drop with an explicit, audited invariant) rather than crashing chunk application. Add fuzz/property tests that push `GlobalContractDistribution` receipts through arbitrarily many resharding generations (including non-split transitions and GC of split-history) to ensure `resolve_to_current_shard` failure paths never reach an unwrap in the hot path.

### Proof of Concept
The existing test demonstrates the reachable construction end-to-end (deploy global contract as unprivileged user → saturate shard compute to delay the receipt → drive two resharding events → drain queue) and asserts that the chain does not stall, i.e., it is a regression guard against exactly this panic path: [5](#0-4) 

Note: I could not fully verify the exact boundary conditions under which `resolve_to_current_shard` (in `core/primitives/src/shard_layout/v3.rs` / `mod.rs`) fails versus succeeds beyond two resharding generations, since I was not able to read that function's implementation within the available tool budget — this is the key remaining uncertainty for pinpointing the precise minimal trigger beyond what the existing regression test already covers.

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
