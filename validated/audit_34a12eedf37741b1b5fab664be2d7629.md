### Title
Webhook shop-domain is not covered by the HMAC signature, allowing cross-tenant session hijacking via forged `X-Shopify-Shop-Domain` header - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
Shopify webhook requests are authenticated in this library by validating an HMAC over the raw request body only. The `X-Shopify-Shop-Domain` header that identifies *which* shop the webhook belongs to is never included in the signed data, yet it is trusted as-is and used to look up and hand out that shop's stored offline access token. Any party who can obtain one valid (body, HMAC) pair signed with the app's shared secret — e.g. by installing the app on their own store and triggering a webhook — can replay that exact body/HMAC to the app's webhook endpoint while swapping in a victim shop's domain in the header, causing the handler to authenticate the request as the victim shop and construct an admin API client from the victim's real access token.

### Finding Description
The root cause mirrors the reported bug class: an authentication artifact (here, the webhook HMAC) is not bound to the specific "destination" it should authorize (here, the target shop domain), so it can be replayed in a context different from the one it was issued for.

- `validateHmacFromRequestFactory` computes/verifies the HMAC solely over `rawBody`, using the app's single shared `apiSecretKey`. Nothing about the shop domain, host, or destination is part of the signed material: [1](#0-0) 

- `checkWebhooksHeaders`/`checkEventsHeaders` read the `domain` straight from the unauthenticated `X-Shopify-Shop-Domain` header and pass it through as trusted data once the (domain-agnostic) HMAC check succeeds: [2](#0-1) 

- `authenticateWebhookFactory` (shopify-app-remix / shopify-app-react-router) then uses that unauthenticated `check.domain` value directly to load the shop's stored offline session and build a live admin API client, without re-validating that the domain in the header matches anything cryptographically bound to the signed body: [3](#0-2) 

Because the app's `apiSecretKey` is shared across every shop that installs the app, a merchant who installs the app on their own store receives genuine, correctly-HMAC'd webhook deliveries for their own shop. They can capture one such `(rawBody, X-Shopify-Hmac-Sha256)` pair and resend it directly to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop that also has the app installed. `validateHmacFromRequestFactory` will report the HMAC as valid (it never looked at the domain), and `ensureValidOfflineSession(params, check.domain)` will load the victim's real, stored offline access token and construct an authenticated `admin` client scoped to the victim shop.

### Impact Explanation
This breaks the isolation between tenants (shops) of a multi-tenant Shopify app: a low-privileged actor (any merchant able to install the app) can trigger the app's webhook business logic as if it were running against a different, victim shop, with a genuine admin API client authorized by the victim's real access token. Depending on what the app's webhook handlers do with `admin`/`session` (e.g., create orders, modify products, issue refunds, write app-specific data), this can lead to unauthorized cross-tenant data access or mutation using the victim's credentials — a direct analog of the reported "cross-chain token reuse" issue, but manifesting as cross-tenant session use.

### Likelihood Explanation
The attack requires only: (1) the attacker's own installation of the app (a normal, unprivileged action any merchant can take), (2) the ability to capture one legitimate webhook HTTP request sent to the app (trivial if the attacker controls the app's webhook receiving infrastructure, or captures via app logs/proxy), and (3) the ability to send an arbitrary HTTP POST with a spoofed header to the app's public webhook route — no additional secrets or privileged access are required. The webhook endpoint is a plain public HTTP endpoint with no additional binding of body-to-domain, so likelihood is high wherever such an endpoint is internet reachable.

### Recommendation
Bind the shop domain (and ideally webhook id / topic / timestamp) into the authenticated material rather than trusting the `X-Shopify-Shop-Domain` header on its own. Concretely:
- Verify that the shop domain claimed in the header is a domain the app actually expects for this specific delivery, e.g. by also validating it against the `X-Shopify-Webhook-Id` uniqueness/idempotency tracking per shop, or
- Where possible, incorporate the domain into a canonical string that is checked against Shopify-documented invariants (e.g., cross-check the domain in the body payload for topics that include shop identifiers) before using it to look up and hand out a session/access token.
- At minimum, treat `check.domain` as untrusted for authorization decisions until corroborated by data already tied to the verified body (e.g., a `shop_id`/`shop_domain` field embedded in the payload itself for topics where Shopify includes it), rather than passing it directly into `ensureValidOfflineSession`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures/observes a webhook subscription (e.g. `orders/create`).
2. Attacker triggers an event (e.g., creates an order) on their own shop, causing Shopify to POST a webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` header computed over the raw body using the app's shared secret, and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this exact `(rawBody, X-Shopify-Hmac-Sha256)` pair (e.g. via a proxy in front of their own receiving endpoint, or by re-pointing DNS/host temporarily to capture the raw request before it reaches the real app).
4. Attacker resends the identical body and HMAC header directly to the app's public webhook URL, replacing only `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (a shop that also installed the app).
5. `validateHmacFromRequestFactory` validates successfully (HMAC only checked `rawBody`), `checkWebhooksHeaders` returns `domain: 'victim-shop.myshopify.com'`, and `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, which loads the victim's real stored offline session/access token and returns an authenticated `admin` client for `victim-shop`, which the app's webhook handler then acts upon.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
