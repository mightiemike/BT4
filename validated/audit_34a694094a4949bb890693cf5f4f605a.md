### Title
Optional price-feed update lets a caller selectively skip the Pyth update to execute borrow/liquidation at a stale, more favorable cached price - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` accepts an *optional* list of Pyth price-update payloads on price-sensitive entry points. If the caller supplies `none`, `write-feeds` is a no-op and the transaction proceeds using whatever price is already cached, as long as it is within `max-staleness`. Because the caller — not the protocol — decides whether to push the freshest off-chain price on-chain before the action executes, the same actor can choose the more favorable of "stale-but-still-fresh-enough" vs. "true current" price for their own borrow, collateral, or liquidation call, exactly mirroring the Flatmoney H-6 keeper price-selection bug.

### Finding Description
`write-feeds` processes an `(optional (list 3 (buff 8192)))` of Pyth update payloads and explicitly does nothing when `none` is passed, "for backward compatibility": [1](#0-0) 

Downstream, price validity is enforced only by a staleness/monotonicity window, not by requiring the truly latest price: [2](#0-1) 

`price-resolve` accepts any price whose timestamp delta from `stacks-block-time` is `<= max-staleness` and whose timestamp is `>= last-update-time`; it does not require the timestamp to equal the current time or force the caller to supply an update at all: [3](#0-2) 

The identical pattern exists in the local-testing mirror: [4](#0-3) [5](#0-4) 

Because the feed-update step is optional and happens in the *same transaction* just before the health/LTV/liquidation math runs, the caller effectively controls whether the on-chain price is refreshed to the true current market price or left at whatever value is already cached (which remains legal as long as it is inside `max-staleness`, e.g. up to several minutes old per asset). This is the same root cause as H-6: the party who benefits from choosing a price is also the party who decides whether the price gets updated before the guarded logic (health check / debt calculation / liquidation) executes on that price.

### Impact Explanation
An actor can:
- Omit the price update (`feeds: none`) when borrowing so that a stale, higher collateral valuation (still inside the staleness window) is used to borrow more debt than the true collateral value supports, directly extracting excess funds and risking protocol insolvency.
- Omit the price update when triggering their own liquidation-avoidance action, or supply/withhold an update around a liquidation to bias the collateral/debt price used in the health-factor check that "changes what it checked" between validation and effect within the same call.

Since debt/collateral valuation directly drives how much a user can borrow or how a liquidation settles, this can result in direct theft of protocol funds or protocol insolvency, satisfying the in-scope Critical impact category.

### Likelihood Explanation
Any caller of the affected public functions is free to build the transaction with `feeds: none` or with feeds for unrelated assets, since `write-feeds` silently accepts `none`. No special privilege, keeper role, or DAO action is required — the caller of `borrow`/liquidation-related entry points is the same account that decides whether the oracle gets refreshed, making this trivially reachable by any user, limited only by the size of the `max-staleness` window per asset.

### Recommendation
Require that a price update be supplied and consumed whenever the resolved price is not already the freshest available for the specific feed(s) used in the transaction's valuation, rather than allowing `none`/omitted updates to silently fall back to a stale-but-legal cached price. At minimum, tighten `max-staleness` and/or force `write-feeds` to be mandatory (non-optional) for any code path that computes LTV, borrow limits, or liquidation eligibility, removing the caller's ability to choose whether the price is refreshed before the guarded check runs.

### Proof of Concept
1. Attacker observes the on-chain cached Pyth price for a collateral asset is currently higher than the true off-chain market price, but the age of that cached price is still `<= max-staleness` (see `oracle-timestamp-fresh`, [6](#0-5) ).
2. Attacker calls the borrow (or other price-sensitive) entry point in `v0-4-market.clar`, passing `feeds: none` so `write-feeds` performs no update ( [1](#0-0) ).
3. `price-resolve`/`price-multi-resolve` then values the attacker's collateral using the stale, inflated cached price because it still passes the `oracle-timestamp-fresh` check ( [3](#0-2) ).
4. The health/LTV computation approves a larger borrow than the true collateral value supports; the debt is issued in the same transaction before any subsequent price update can correct the valuation.
5. Once the true (lower) price is eventually pushed on-chain by another party, the position is already under-collateralized, leaving the protocol/LPs to absorb the shortfall — analogous to the Flatmoney H-6 scenario where the party controlling whether the oracle updates chooses the price that benefits them.

(Note: I was unable to enumerate every one of the ~9 additional call sites of `write-feeds` inside `v0-4-market.clar` within the available tool budget; the analysis is based on the confirmed optional/no-op semantics of `write-feeds` and the staleness-window-based `price-resolve` logic shared by both the mainnet and local-testing market contracts. A full Devin session with repo access would be needed to enumerate every entry point that wires an optional `feeds` parameter through to `write-feeds`.)

```text
;; If list is provided, folds over it and updates all feeds
;; If list is none, does nothing (allows for backward compatibility)
(define-private (write-feeds (feeds (optional (list 3 (buff 8192)))))
  (match feeds
    entries (fold write-feed entries (ok true))
    (ok true)))
```

```text
(define-private (oracle-price-legal (p uint))
  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))
```

```text
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```
