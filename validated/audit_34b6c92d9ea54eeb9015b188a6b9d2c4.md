### Title
Hardcoded, unupdatable Address Registrar dependency in the immutable Eth Wallet Contract can permanently break address-check transfers for all ETH-implicit accounts - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Eth Wallet Contract that every ETH-implicit account is created with hardcodes the account ID of an "Address Registrar" contract at compile time via `include_str!`, and this code is deployed globally under an immutable `CodeHash` reference used by all ETH-implicit accounts on the network. There is no mechanism for an ETH-implicit account to update this dependency, analogous to `UXDToken`'s immutable `controller` address that cannot be changed if the controller becomes unusable.

### Finding Description
The `ADDRESS_REGISTRAR_ACCOUNT_ID` is baked into the WASM at build time via `include_str!("ADDRESS_REGISTRAR_ACCOUNT_ID")`, and used at runtime to look up whether an address corresponds to a named account before completing certain base-token transfers: [1](#0-0) [2](#0-1) 

This WASM is the same code deployed once globally by `code_hash` for every ETH-implicit account created on the network: [3](#0-2) [4](#0-3) 

Global-contract deployment by `CodeHash` is explicitly documented as making the contract immutable, unlike `AccountId` mode which allows an owner to upgrade it: [5](#0-4) 

ETH-implicit accounts cannot add a full-access key, delete their account, or otherwise replace their contract code — the wallet contract itself explicitly rejects adding a full-access key, and the docs confirm these accounts "cannot be deleted, nor can a full access key be added": [6](#0-5) [7](#0-6) 

Consequently, if the specific account referenced by `ADDRESS_REGISTRAR_ACCOUNT_ID` (`address-map.near`) becomes unusable — deleted, taken over, redeployed with an incompatible interface, or otherwise stops responding correctly — every ETH-implicit account's `rlp_execute` calls that require an address check will permanently fail, with no way for any individual account holder to fix, redeploy, or point their account at a replacement registrar, since the dependency is compiled into an immutable, globally-shared contract: [8](#0-7) 

This is structurally the same root cause as the reported `UXDToken` issue: a critical dependency address is fixed/immutable with no update path, so if that dependency becomes compromised or unavailable, dependent functionality becomes permanently unusable.

### Impact Explanation
The affected code path is scoped to `EOABaseTokenTransfer` transactions carrying `address_check: Some(_)` (used to guard against sending funds to an address that actually maps to a named account). If the hardcoded registrar becomes unusable, this specific transfer path fails for every ETH-implicit account network-wide, permanently, since the dependency cannot be changed post-deployment. This is a protocol-level, permanent denial-of-service for a category of user-initiated fund transfers reachable by any unprivileged transaction signer using an ETH-implicit account — not a full freeze of all wallet-contract functionality (plain `Transfer`, `FunctionCall`, and `ERC20Transfer` actions do not depend on the registrar), but it does constitute a permanently broken/frozen transaction path with no user-side remediation, matching the "permanently frozen funds"/"transaction-triggered halt" class of impact for that specific flow.

### Likelihood Explanation
Likelihood depends entirely on whether `address-map.near` (the hardcoded registrar account) ever becomes compromised, deleted, or redeployed incompatibly. The report explicitly notes the wallet-contract implementation is currently marked "Must not use in production!" in its own README, and I was not able to fully confirm the current production/mainnet activation status of `EthImplicitGlobalContract` for this exact code path versus the legacy magic-bytes contract; this should be verified further before treating this as an active mainnet exposure. [9](#0-8) 

### Recommendation
Avoid hardcoding the address-registrar account ID directly into the immutable, globally-shared wallet contract WASM. Consider deploying the wallet contract global contract under `GlobalContractDeployMode::AccountId` (allowing a controlled, transparent upgrade path) rather than `CodeHash`, or add an explicit, governed mechanism (e.g., a well-audited on-chain config account with a timelock/multisig) that can be updated to repoint the registrar dependency if it ever becomes compromised or unavailable, rather than relying on a permanently baked-in account ID.

### Proof of Concept
1. An ETH-implicit account is created, which is assigned `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))` — an immutable, hash-addressed global contract (`runtime/runtime/src/actions.rs:255-269`).
2. That global contract's compiled WASM contains a hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID = "address-map.near"` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:27`, `ADDRESS_REGISTRAR_ACCOUNT_ID` file).
3. A user submits an `rlp_execute` transaction representing an `EOABaseTokenTransfer` with `address_check: Some(address)`; the contract cross-calls `address-map.near::lookup` (`lib.rs:417-432`).
4. If `address-map.near` becomes unusable (deleted/redeployed/compromised), this call returns `PromiseResult::Failed`, and `address_check_callback` unconditionally returns a failure response (`lib.rs:141-148`).
5. Because the ETH-implicit account's contract is immutable (global by code hash) and the account cannot obtain a full-access key or be deleted (`lib.rs:484-487`; `docs/DataStructures/Account.md:119-122`), there is no way for the affected account owner to route around the broken registrar dependency — this transfer path is permanently broken for every existing and future ETH-implicit account on the network.
