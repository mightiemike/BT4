### Title
Exchange reserve can be driven to exactly 0 via repeated `ExchangeTransactionActuator` calls, permanently locking `ExchangeInjectActuator`/`ExchangeWithdrawActuator` for the exchange creator - (File: `ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction` only rejects the resulting balance when it goes negative, and only when `hardenedCalc` is true; it never rejects a resulting balance of exactly `0`. Any unprivileged account holding a small amount of one of the exchanged tokens can repeatedly call `ExchangeTransactionActuator` to shrink the smaller-side reserve down to exactly `0`, after which `ExchangeInjectActuator`/`ExchangeWithdrawActuator` permanently reject all future calls — including from the legitimate exchange creator — with "the exchange has been closed", with no recovery path in the reviewed code.

### Finding Description
`ExchangeCapsule.transaction` computes `newFirstTokenBalance`/`newSecondTokenBalance` and only guards against negative results, and only under `hardenedCalc`: [1](#0-0) 
This means a resulting balance of exactly `0` is always accepted, regardless of whether `allowHardenExchangeCalculation` is enabled or not.

Every read/write path into the exchange (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`) independently gates on: [2](#0-1) [3](#0-2) [4](#0-3) 

Because `ExchangeTransactionActuator.execute` calls `exchangeCapsule.transaction(...)` and persists the result unconditionally as long as it doesn't throw (`hardenedCalc` only bars `< 0`, not `== 0`): [5](#0-4) 
an unprivileged attacker holding a nonzero balance of either exchanged token can broadcast a sequence of `ExchangeTransactionContract` transactions, each selling the token on the side with the smaller reserve, using the AMM's floor/truncating integer math (`(long) issuedSupply`, `setScale(0, RoundingMode.DOWN)` in `ExchangeProcessor`/`SafeExchangeProcessor`) to whittle the opposing reserve down until the last transaction's computed `buyTokenQuant` exactly equals the remaining balance, yielding a resulting balance of `0`. This passes the actuator's `doValidate()` (which only rejects `<0`/`==0` *before* the trade, not the *post-trade* result) and the capsule's own `hardenedCalc` guard (`< 0`, not `<= 0`).

Once either `firstTokenBalance` or `secondTokenBalance` reaches `0`, every subsequent call to `ExchangeInjectActuator.doValidate` and `ExchangeWithdrawActuator.doValidate` throws `ContractValidateException("... the exchange has been closed")` unconditionally for *any* caller, including the legitimate creator, and there is no actuator or mechanism found in the codebase to reset/recreate a zero-balance exchange.

### Impact Explanation
This is a permanent Denial of Service against the exchange creator: legitimate `ExchangeInjectActuator`/`ExchangeWithdrawActuator` calls become permanently unusable for that exchange, locking any remaining reserve on the non-drained side and any future liquidity operations, with no recovery mechanism identified. This matches a DoS-via-protocol-implementation impact class (permanent loss of function/asset lock for a legitimate market participant), not merely a griefing nuisance.

### Likelihood Explanation
Preconditions are minimal: any account holding a small nonzero balance of one exchanged token can act, no special permission or state is required beyond the exchange existing. The attack is deterministic and repeatable — the attacker simply needs to keep selling the token on the smaller-reserve side in decreasing increments (dictated by the AMM's floor/truncation behavior) until the last trade computes an exact drain to `0`. Cost is limited to standard transaction fees/bandwidth and the value of tokens sold into the pool (partially recovered as the opposite token via the trade), making this economically inexpensive to execute against low-liquidity exchanges, which are common for user-created markets.

### Recommendation
Change the invariant in `ExchangeCapsule.transaction` to reject `newFirstTokenBalance <= 0 || newSecondTokenBalance <= 0` unconditionally (not just under `hardenedCalc`, and not just `< 0`), so a trade that would exhaust a reserve to exactly zero is rejected before being committed. Additionally, consider adding an explicit, permission-gated "close/reset exchange" recovery path so a creator is not left permanently locked out if a zero-balance state is ever reached through other means (e.g., pre-hardening chain history).
