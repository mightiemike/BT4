### Title
Missing `as-contract?` Authorization Context in `send-underlying()` Breaks Withdrawals for USDC/USDH Vaults - (File: mainnet/contracts/vault/v0-vault-usdc.clar / mainnet/contracts/vault/v0-vault-usdh.clar)

### Summary
`send-underlying()` in the USDC and USDH vault contracts calls the external SIP-010 token's `transfer` function with `current-contract` as the sender argument, but does **not** wrap the call in `as-contract?`. Every SIP-010 `transfer` implementation enforces `(asserts! (is-eq tx-sender sender) ...)`. Since the call is not impersonated via `as-contract?`, `tx-sender` remains the original transaction signer (a depositor calling `redeem`, or `market.clar` calling `system-borrow`), which never equals `current-contract` (the vault). The token contract therefore rejects the transfer every time, exactly analogous to the H-02 report's misuse of transfer authorization semantics (a caller attempting to move funds it is not authorized, under the token's own rules, to move).

### Finding Description
Compare the working and broken implementations:

Working pattern (`v0-vault-stx.clar`): [1](#0-0) 

```
(define-private (send-underlying (amt uint) (account principal))
  (begin
    (try! (as-contract? ((with-stx amt))
      (try! (contract-call? .wstx transfer amt tx-sender account none))
      true))
    (ok true)))
```

Here, `as-contract?` makes `tx-sender` (inside the block) equal to `current-contract`, so the `.wstx` token's `(is-eq tx-sender sender)` check passes.

Broken pattern (`v0-vault-usdc.clar`): [2](#0-1) 

Broken pattern (`v0-vault-usdh.clar`): [3](#0-2) 

Both call `(contract-call? <token> transfer amount current-contract account none)` directly, with no `as-contract?` wrapper. The transaction's real `tx-sender` (the user calling `redeem`, or ultimately the vault's caller through `market.clar` calling `system-borrow`) is not `current-contract`. The external SIP-010 token (`usdcx` / `usdh-token-v1`) will reject this call because the `sender` parameter (`current-contract`) does not match `tx-sender`.

This is used by:
- `redeem()`, which burns the user's `zft` shares and then calls `send-underlying` to pay out the underlying asset: [4](#0-3) 
- `system-borrow()`, which mutates debt-accounting state (`principal-scaled`, `total-borrowed`) before calling `send-underlying`: [5](#0-4) 

Since `try!` on the failing `contract-call?` reverts the whole transaction (single-transaction atomicity, no partial state committed), `redeem()` for USDC/USDH will always fail after burning the shares fails atomically together — but the intended withdrawal path itself is permanently non-functional, meaning deposited/underlying funds behind these two vaults can never be redeemed by their rightful owners through the normal flow.

### Impact Explanation
Because `send-underlying` cannot ever satisfy the SIP-010 token's ownership check, every `redeem()` call against the USDC and USDH vaults reverts, and every `system-borrow()` call (used by `market.clar` to disburse borrowed USDC/USDH to borrowers) reverts as well. This permanently strands the underlying USDC and USDH tokens locked in these two vaults — depositors cannot withdraw their principal/yield, and borrowers cannot draw down debt in these assets. This lands in the "permanent freezing of funds" impact category (freezing of the underlying vault liquidity, not just unclaimed yield).

### Likelihood Explanation
This will trigger deterministically on the very first `redeem()` or `system-borrow()` call for the USDC or USDH vault — no adversarial conditions or race are needed; it is a straightforward, always-reachable code path.

### Recommendation
Wrap the outbound `transfer` call in `as-contract?` with the appropriate `with-ft` post-condition, matching the pattern already used in `v0-vault-stx.clar` / `v0-vault-ststx.clar` / `v0-vault-ststxbtc.clar`:

```clarity
(define-private (send-underlying (amount uint) (account principal))
  (begin
    (try! (as-contract? ((with-ft 'SP120SBRBQJ00MCWS7TM5R8WJNTTKD5K0HFRC2CNE.usdcx "*" amount))
      (try! (contract-call? 'SP120SBRBQJ00MCWS7TM5R8WJNTTKD5K0HFRC2CNE.usdcx transfer amount tx-sender account none))
      true))
    (ok true)))
```
(analogously for `v0-vault-usdh.clar`).

### Proof of Concept
1. Deploy/initialize `v0-vault-usdc.clar` and deposit USDC via `deposit()` (this succeeds because `receive-underlying` correctly has `tx-sender == account` since the depositor is the real `tx-sender`).
2. Call `redeem(amount, min-out, recipient)` as the depositor.
3. Execution reaches `(try! (send-underlying inkind recipient))`, which internally calls `(contract-call? 'SP120SBRBQJ00MCWS7TM5R8WJNTTKD5K0HFRC2CNE.usdcx transfer inkind current-contract recipient none)`.
4. The `usdcx` SIP-010 contract's `transfer` implementation checks `(asserts! (is-eq tx-sender sender) err-not-token-owner)`. Since `tx-sender` is the depositor's principal (not the vault's `current-contract`), the assertion fails and the call returns an error.
5. `try!` propagates the error, and the entire `redeem` transaction reverts — the user's shares are never burned and no underlying is transferred, but critically, redemption is now permanently impossible through this path for all users, freezing all USDC deposited in the vault. The same failure occurs for `system-borrow()`, blocking all USDC/USDH borrowing.
