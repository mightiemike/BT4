### Title
Dynamic energy penalty factor lets an attacker inflate a victim's contract-call energy fee via prior on-chain activity, with no way for the caller to cap the fee - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
The TVM's "dynamic energy" mechanism computes a per-contract energy-cost multiplier (`contextContractFactor`) from cumulative energy usage recorded against that contract in a shared, contract-scoped state object. This factor is applied uniformly to every subsequent caller's opcode costs until the next cycle transition recalculates it. Exactly like the AlgebraPool bug where the swap fee state set by an earlier transaction in the same block dictates the fee paid by a later, unrelated flashloan call, here the energy multiplier set by earlier heavy contract usage dictates the energy fee paid by a later, unrelated `TriggerSmartContract` call to the same contract — and the caller has no way to specify a maximum fee they are willing to pay.

### Finding Description
When dynamic energy is enabled (`ALLOW_DYNAMIC_ENERGY`), `VM.play()` fetches a multiplicative `factor` once per call via `program.updateContextContractFactor()` and then applies it as a penalty to every opcode's energy cost for the remainder of that execution: [1](#0-0) [2](#0-1) 

`updateContextContractFactor()` reads/writes a shared `ContractStateCapsule` keyed only by the contract address (not by caller or transaction), and calls `catchUpToCycle()` to roll the stored energy-usage counter and factor forward: [3](#0-2) 

`catchUpToCycle()` increases the persisted `energyFactor` whenever the accumulated `energyUsage` for that contract exceeded `DYNAMIC_ENERGY_THRESHOLD` in the prior cycle, and decays it otherwise: [4](#0-3) 

Every execution against that contract then reports its energy usage back into the same shared counter via `addContextContractUsage()`: [5](#0-4) 

Because the factor for a given cycle is derived purely from the *previous* cycle's aggregate usage on that contract, any account can drive up a target contract's `energyFactor` ahead of time (by repeatedly invoking energy-heavy paths on it) so that when a victim's transaction is broadcast and executed in a later block/cycle against the same contract, it is charged energy at the inflated multiplier — a materially different (higher) fee than the caller could predict from the contract's normal energy cost table. As in the reported analog, the caller of `TriggerSmartContract` has no field to bound the acceptable energy multiplier/fee; `TransactionCapsule`/`TriggerSmartContractActuator` simply executes at whatever factor is currently persisted for the target contract.

### Impact Explanation
A user submitting a smart-contract call transaction (via the public gRPC/HTTP `TriggerSmartContract` broadcast path) can be forced to burn substantially more TRX in energy fees than expected, since the multiplier is state that a third party can manipulate ahead of the victim's transaction with no consent or bound from the victim. Unlike the source report where LPs merely gain fee revenue, here the excess energy fee is paid in TRX (via `ReceiptCapsule.payEnergyBill`) and burned/paid to the fee pool or blackhole, so the victim suffers a direct monetary loss with no compensating benefit. This is a resource/fee-accounting griefing/DoS vector against specific contract callers rather than a fund-theft bug.

### Likelihood Explanation
Exploitation requires the attacker to interact with the same target contract enough to push its cumulative per-cycle energy usage above `DYNAMIC_ENERGY_THRESHOLD`, and this only manifests as an increase at cycle boundaries determined by `dps.getCurrentCycleNumber()`, whose granularity ties into the consensus maintenance/voting cycle machinery (`MaintenanceManager`, `MortgageService`) rather than being trivially "the very next block." I was not able to fully confirm within the available index how frequently `getCurrentCycleNumber()` advances relative to block production, so the exact "front-run within one block" timing window from the original report could not be verified end-to-end; the underlying design flaw (fee multiplier state shared across unrelated callers, no caller-specified cap) is nonetheless clearly present and reachable from ordinary transaction broadcast.

### Recommendation
- Scope the dynamic-energy factor state (or at least allow an opt-out/cap) at the granularity of the caller/transaction rather than purely the destination contract, or
- Allow transaction senders to specify a maximum acceptable energy price/factor for a call, causing the transaction to fail rather than silently pay an inflated fee, mirroring the two mitigations proposed in the original report (max-fee parameter, or a flat/bounded fee model) applied to `Program.updateContextContractFactor()` / `ContractStateCapsule.catchUpToCycle()`.

### Proof of Concept
1. Attacker repeatedly calls energy-intensive functions on target contract `C` such that `ContractStateCapsule.getEnergyUsage()` for `C` exceeds `DynamicEnergyThreshold` in the current cycle (see `catchUpToCycle`, `ContractStateCapsule.java:110-120`).
2. At the next cycle rollover, `contractStateCapsule.getEnergyFactor()` for `C` increases (bounded by `DynamicEnergyMaxFactor`).
3. A victim then submits an unrelated `TriggerSmartContract` transaction calling `C`; `VM.play()` reads the now-inflated `factor` via `updateContextContractFactor()` and applies the increased penalty to every opcode (`VM.java:62-79`), so the victim's `ReceiptCapsule.payEnergyBill` charges energy fee at the manipulated rate — with no parameter in the transaction to reject execution above an acceptable fee.   public long updateContextContractFactor() {
```java
    ContractStateCapsule contractStateCapsule =
        contractState.getContractState(getContextAddress());

    if (contractStateCapsule == null) {
      contractStateCapsule = new ContractStateCapsule(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber());
      contractState.updateContractState(getContextAddress(), contractStateCapsule);
    } else {
      if (contractStateCapsule.catchUpToCycle(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber(),
          VMConfig.getDynamicEnergyThreshold(),
          VMConfig.getDynamicEnergyIncreaseFactor(),
          VMConfig.getDynamicEnergyMaxFactor(),
          VMConfig.allowStrictMath(),
          VMConfig.disableJavaLangMath())) {
        contractState.updateContractState(getContextAddress(), contractStateCapsule
        );
      }
    }
    contextContractFactor = contractStateCapsule.getEnergyFactor()
        + Constant.DYNAMIC_ENERGY_FACTOR_DECIMAL;
    return contextContractFactor;
  }
```

```java
  public boolean catchUpToCycle(
      long newCycle, long threshold, long increaseFactor, long maxFactor,
      boolean useStrictMath, boolean disableMath
  ) {
    long lastCycle = getUpdateCycle();

    // Updated within this cycle
    if (lastCycle == newCycle) {
      return false;
    }

    // Guard judge and uninitialized state
    if (lastCycle > newCycle || lastCycle == 0L) {
      reset(newCycle);
      return true;
    }

    final long precisionFactor = DYNAMIC_ENERGY_FACTOR_DECIMAL;

    // Increase the last cycle
    // fix the threshold = 0 caused incompatible
    if (getEnergyUsage() > threshold) {
      lastCycle += 1;
      double increasePercent = 1 + (double) increaseFactor / precisionFactor;
      this.contractState = ContractState.newBuilder()
          .setUpdateCycle(lastCycle)
          .setEnergyFactor(min(
              maxFactor,
              (long) ((getEnergyFactor() + precisionFactor) * increasePercent) - precisionFactor,
              disableMath))
          .build();
    }
```
