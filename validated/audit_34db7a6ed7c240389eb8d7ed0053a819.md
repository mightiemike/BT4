### Title
Cross-Workflow Request-ID Squatting Enables Denial-of-Service in HTTP Trigger Handler - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
The gateway's `httpTriggerHandler` deduplicates in-flight HTTP trigger requests using a single, gateway-instance-wide map keyed only by the client-supplied `requestID` string, with no binding to the calling workflow, workflow owner, or authenticated key. Any authenticated caller (i.e., any party who can produce a valid `req.Auth` for *any* workflow) can pre-occupy an arbitrary `requestID` value before a legitimate user submits a request with that same ID for a different, unrelated workflow, causing the victim's request to be rejected. This mirrors the reported `createOffer` front-running pattern: a user-supplied identifier is checked for prior existence in a global namespace, and whoever claims it first wins, blocking everyone else — regardless of whether the claimant has any legitimate relationship to the resource being IDed.

### Finding Description
`httpTriggerHandler.callbacks` is declared as a single map shared across the entire handler instance: [1](#0-0) 

`HandleUserTriggerRequest` processes the request through validation (`validatedTriggerRequest`), workflow resolution (`resolveWorkflowID`), authorization (`authorizeRequest`), and rate limiting (`checkRateLimit`) — all scoped to the *caller's own* `workflowID` — before reaching `setupCallback`: [2](#0-1) 

`setupCallback` is where the collision check actually happens, and it is keyed purely on `requestID`, independent of `workflowID` or the authenticated key: [3](#0-2) 

Because the `requestID` namespace is global rather than scoped per-workflow/per-owner, the check `if _, found := h.callbacks[requestID]; found` at line 401 behaves exactly like `require(s_offers[offerId].creationDate == 0, ...)` in the reported `TunnlTwitterOffers.createOffer` bug: whoever successfully calls `setupCallback` first with a given ID "owns" it until the callback resolves or is reaped, and any other party — including one with no relationship to the victim's workflow — is rejected with a `jsonrpc.ErrConflict` ("requestID … has already been used"), confirmed by the existing test at `http_trigger_handler_test.go:316-354`, which simply asserts the second caller with the same `requestID` fails, without checking that the two callers even target the same workflow.

An attacker only needs valid authentication for *some* workflow they control (this is a routine, low-privilege capability — any workflow owner can register a trivial workflow and sign requests to it via `WorkflowMetadataHandler.Authorize`), not any privilege over the victim's workflow, to submit `HandleUserTriggerRequest` calls that squat on chosen `requestID` values. Once squatted, that ID remains blocked for other users' completely unrelated workflow executions until `reapExpiredCallbacks` clears it (bounded by `CleanUpPeriodMs`), or until the squatting attacker's own callback resolves.

### Impact Explanation
This is a availability/multi-tenancy isolation break in the gateway's core request dispatch path: an authenticated-but-unprivileged party can deny other tenants' HTTP-triggered workflow executions by squatting shared `requestID`s, even though request IDs are meant to be caller-chosen (e.g., idempotency keys, batch job identifiers, or predictable sequence numbers used by legitimate integrators). The impact is amplified because the check occurs after `authorizeRequest`/`checkRateLimit` succeed for the attacker's own workflow — i.e., the attacker pays only their own rate-limit budget, not the victim's — and the collision detection deliberately has no per-tenant scoping, unlike `checkRateLimit`, which explicitly scopes by `workflowID`/`workflowOwner` via `contexts.WithCRE`. This is a direct availability/trust-boundary violation analogous to the reported medium-severity finding: no funds are directly at risk, but legitimate workflow executions can be reliably blocked by an unrelated, low-cost caller.

### Likelihood Explanation
Likelihood is moderate-to-high in practice wherever request IDs are predictable or reused by convention (sequential counters, timestamp-based IDs, deterministic idempotency keys derived from external system IDs) — a common pattern for HTTP trigger integrations. Any workflow owner able to submit signed requests to the gateway can attempt this without any special permission beyond owning one workflow, and the attack requires no on-chain transaction or gas cost, only a JSON-RPC call to the gateway.

### Recommendation
Scope the in-flight request deduplication key to the tuple of `(workflowID, workflowOwner, requestID)` (or the authorized key) rather than `requestID` alone, so that a `requestID` collision is only rejected when it collides with an in-flight request for the *same* workflow/owner. This preserves the intended idempotency semantics per-caller while eliminating the cross-tenant squatting vector, mirroring the report's recommendation to bind the user-chosen identifier to the legitimate submitter before enforcing uniqueness.

### Proof of Concept
1. Attacker registers/owns a trivial workflow `W_attacker` and obtains valid signed auth for it via the normal onboarding flow (as exercised by `createTestPrivateKey`/`createTestJWTToken` in `http_trigger_handler_test.go`).
2. Attacker sends `HandleUserTriggerRequest` with `req.ID = "shared-id-123"` targeting `W_attacker`; this succeeds and populates `h.callbacks["shared-id-123"]` (per `setupCallback`, `http_trigger_handler.go:397-421`).
3. Victim (unrelated tenant), owning workflow `W_victim`, sends `HandleUserTriggerRequest` with the same `req.ID = "shared-id-123"` targeting `W_victim`.
4. `setupCallback` finds `"shared-id-123"` already present in the shared map and rejects the victim's request with `jsonrpc.ErrConflict` ("requestID: shared-id-123 has already been used…"), exactly as demonstrated for the same-workflow case in the existing `t.Run("duplicate request ID", ...)` test at `http_trigger_handler_test.go:316-354` — except here the two callers target entirely different, unrelated workflows, proving the collision domain is global rather than per-tenant.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

	// (N+F)//2 + 1 threshold where N = number of nodes, F = number of faulty nodes
	threshold := (len(h.donConfig.Members)+h.donConfig.F)/2 + 1
	agg, err := aggregation.NewIdenticalNodeResponseAggregator(threshold)
	if err != nil {
		return nil, errors.New("failed to create response aggregator: " + err.Error())
	}

	doneCh := make(chan struct{})
	h.callbacks[requestID] = savedCallback{
		Callback:           callback,
		requestStartTime:   requestStartTime,
		createdAt:          time.Now(),
		responseAggregator: agg,
		doneCh:             doneCh,
	}
	return doneCh, nil
}
