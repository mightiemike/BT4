### Title
Sequencer never validates the real L1 fee paid for `L1_HANDLER` transactions — fee check is bypassed with a hardcoded `Fee(1)` - (File: crates/apollo_transaction_converter/src/transaction_converter.rs)

### Summary
When a validating/proposing node converts a consensus-received `L1_HANDLER` transaction into an executable transaction, it discards the real fee the caller paid on L1 for the `LogMessageToL2` message and substitutes a hardcoded `Fee(1)`. The only guard inside blockifier's L1-handler execution path is `paid_fee != Fee(0)`, so this hardcoded constant trivially satisfies the "fee paid" check regardless of how much (if anything beyond dust) was actually deposited on L1 to cover L2 execution.

### Finding Description
An `L1HandlerTransaction` carries no fee field in its own hash preimage ("No fee in l1 handler transaction" — [1](#0-0) ). Instead, the fee actually paid on L1 is meant to be tracked out-of-band as `paid_fee_on_l1`, taken from the L1 `LogMessageToL2` event's `fee` field when scraped directly from L1: [2](#0-1) .

However, the actual sequencer path that a proposer/validator uses to turn a **consensus-received** `L1_HANDLER` transaction into something executable does not use this real value at all — it hardcodes `Fee(1)`: [3](#0-2) 

This constant is then fed straight into `blockifier`'s post-execution enforcement, which only checks that the fee is non-zero — it does not compare it to the actual computed resource cost: [4](#0-3) 

Because `Fee(1) != Fee(0)`, this check always passes, no matter what the real L1 sender paid (or didn't pay). Combined with the enormous `l1_handler_max_amount_bounds` used to gate execution instead (`l1_gas`/`l1_data_gas`/`l2_gas` all set to `10000000000`, i.e. effectively unbounded in practice): [5](#0-4) , an `L1_HANDLER` transaction can legally consume resources up to those very high caps while the "fee paid" check is a no-op.

The same TODO exists in the RPC/simulation path as well (`Fee(1)` used for simulated fee estimation) confirming this is a known, unaddressed placeholder rather than a deliberate design choice tied to real payment: [6](#0-5) .

This is the direct analog of the Optimism M-11 report: on L1, an ETH bridging/L1→L2 message sender pays some `msg.value` amount to `sendMessageToL2` (test helper shows this is an arbitrary nonzero value, not derived from resource cost): [7](#0-6) . The sequencer is expected to use that fee to gate how much L2 execution work it is willing to perform on the caller's behalf — but in the consensus/validator path this linkage is completely severed by the hardcoded `Fee(1)` substitution.

### Impact Explanation
Any unprivileged L1 message sender can trigger a large, expensive L1-to-L2 handler execution (bounded only by the very permissive `l1_handler_max_amount_bounds`) while the sequencer's internal accounting always treats the transaction as if a nominal, non-zero fee were paid — the check never verifies proportionality to the real L1 payment. This lets an attacker force sequencers (proposers and all honest validating nodes, since this conversion path is shared code) to spend disproportionate L2 execution/blockifier resources per L1 message without being economically deterred, mirroring the "gasless"/underpaid bridging DoS class described in the report: expensive-to-process blocks that are not adequately compensated.

### Likelihood Explanation
High reachability: any external account can call the L1 core contract's `sendMessageToL2` (or equivalent) to create an `L1_HANDLER` transaction that every sequencer node must pick up via `ProposeTransactionProvider`/`ValidateTransactionProvider` and convert via `TransactionConverter`; the vulnerable hardcoded-fee code path is unconditionally exercised for every consensus L1Handler transaction, with no privileged role or special conditions required.

### Recommendation
Propagate the real `paid_fee_on_l1` value (sourced from the L1 `LogMessageToL2` event, as already done in `apollo_l1_events`/`papyrus_base_layer`) through the consensus `L1Handler` transaction representation into `convert_consensus_l1_handler_to_internal_l1_handler`, removing the `Fee(1)` placeholder. Additionally, strengthen the blockifier check in `l1_handler_transaction.rs` to compare `paid_fee_on_l1` against the actual computed receipt fee (as the existing comment/error message already implies it should), rather than only checking non-zero.

### Proof of Concept
1. An attacker calls the Starknet core contract's L1→L2 messaging entry point with a negligible `msg.value` (as low as covering the on-chain event emission) and a calldata payload targeting an L1-handler entry point that performs expensive computation/storage writes.
2. The L1 event is scraped and turned into a consensus `L1_HANDLER` transaction; when a proposer/validator processes it, `convert_consensus_l1_handler_to_internal_l1_handler` assigns it `paid_fee_on_l1 = Fee(1)` regardless of the real (negligible) L1 payment: [3](#0-2) .
3. Blockifier executes the transaction up to `l1_handler_max_amount_bounds` and only verifies `paid_fee_on_l1 != Fee(0)`, which trivially passes: [8](#0-7) .
4. The transaction is included in the block despite the sequencer having no verified economic compensation proportional to the L2 resources consumed.

**Note on limitations:** I was unable to fully trace, within the tool budget, how the `ConsensusTransaction::L1Handler` variant carries (or fails to carry) the originally-scraped `paid_fee_on_l1` field all the way from `apollo_l1_events`/L1 provider into the `ConsensusTransaction` struct consumed by `transaction_converter.rs` — it's possible the real fee is simply not represented at all in that struct today, which would make the hardcoded `Fee(1)` a structural consequence rather than a discardable value. Confirming this exactly would require inspecting `starknet_api::consensus_transaction::ConsensusTransaction` and its `L1Handler` variant definition in full, which I could not retrieve before the tool budget was exhausted.

pub async fn send_message_to_l2(
    starknet_core_contract: &StarknetL1Contract,
    l1_handler: &L1HandlerTransaction,
) -> TransactionReceipt {
    const PAID_FEE_ON_L1: U256 = U256::from_be_slice(b"paid"); // Arbitrary value.

    let l2_contract_address = l1_handler.contract_address.0.key().to_hex_string().parse().unwrap();
    let l2_entry_point = l1_handler.entry_point_selector.0.to_hex_string().parse().unwrap();

    // The calldata of an L1 handler transaction consists of the L1 sender address followed by
    // the transaction payload. We remove the sender address to extract the message
    // payload.
    let payload =
        l1_handler.calldata.0[1..].iter().map(|x| x.to_hex_string().parse().unwrap()).collect();
    let msg = starknet_core_contract.sendMessageToL2(l2_contract_address, l2_entry_point, payload);

    msg
        // Sets a non-zero fee to be paid on L1.
        .value(PAID_FEE_ON_L1)
        // Sends the transaction to the Starknet L1 contract. For debugging purposes, replace
        // `.send()` with `.call_raw()` to retrieve detailed error messages from L1.
        .send().await.expect("Transaction submission to Starknet L1 contract failed.")
        // Waits until the transaction is received on L1 and then fetches its receipt.
        .get_receipt().await.expect("Transaction was not received on L1 or receipt retrieval failed.")
}
