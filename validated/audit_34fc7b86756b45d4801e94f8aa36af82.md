### Title
tokenExchange never validates that the requested `shop` matches the session token's `dest` claim, allowing cross-tenant session/token binding - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary
`tokenExchange` calls `decodeSessionToken(config)(sessionToken)` purely to validate the JWT's signature/expiry/audience, but discards the returned payload and never compares its `dest` claim to the caller-supplied `shop` argument. The function then builds the outbound `/admin/oauth/access_token` request and the resulting local `Session` object using the caller-supplied `shop` (via `sanitizeShop`), not the shop embedded in the validated token, breaking the intended binding between "who the token proves you are" and "which shop the resulting session gets filed under."

### Finding Description
In `tokenExchange`: [1](#0-0) 
the decoded/validated payload from `decodeSessionToken` is never used again — `decodeSessionToken` only checks the HS256 signature, `exp`/`nbf`, and (optionally) `aud === config.apiKey`: [2](#0-1) 
It does not check `dest` at all. `sanitizeShop` only validates the *format* of the `shop` string (regex for `*.myshopify.com` etc.), with no relationship to the token: [3](#0-2) 
The resulting session is created with `shop: cleanShop` (the caller-supplied value), not the shop derived from the token's `dest`: [4](#0-3) 

Critically, this is not merely a hypothetical host-app misuse: the library's own published documentation demonstrates sourcing `shop` from the raw, attacker-controlled request query string, completely decoupled from the session token: [5](#0-4) 
This confirms the vulnerable pattern is the library's own recommended usage, not an app-level bug — any consumer that follows the documented example (or any multi-tenant router that derives `shop` from a request parameter while token comes from a header) is exposed. Note that the "safe" official framework packages (`shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`) do NOT follow this pattern — they derive `shop` from `payload.dest` before calling `tokenExchange`, e.g.: [6](#0-5) 
but the core `shopify-api` library itself provides no defense-in-depth check and its own docs recommend the unsafe pattern.

### Impact Explanation
If an app follows the documented API contract (shop from request, token from header/param, independently), an attacker can request token exchange with `shop=victimshop.myshopify.com` while supplying their own validly-signed session token (`dest` = attackershop.myshopify.com). The library will POST the attacker's JWT as `subject_token` to `https://victimshop.myshopify.com/admin/oauth/access_token`, and whatever result Shopify's backend returns gets stored locally in a `Session` keyed to `victimshop.myshopify.com` (`createSession({..., shop: cleanShop})`). This breaks TENANT_ISOLATION at the library level: the local session store can end up associating a shop key with a token that never went through validated ownership of that shop, or at minimum leaks the attacker's own session token to a foreign shop endpoint. This maps to Shopify's bounty class of cross-tenant/session-isolation issues.

### Likelihood Explanation
Requires only an unprivileged caller who possesses their own valid session token (any authenticated merchant/user of the attacker's own installed shop) and a code path (the library's documented usage pattern) that passes an independently-sourced `shop` value. No secrets, no privileged role, and no MITM are needed — it directly follows the library's own reference documentation.

### Recommendation
In `tokenExchange`, use the `dest` claim from the already-decoded, verified JWT payload as the source of truth for the shop domain (as the official framework packages already do), and either ignore the caller-supplied `shop` or throw if it doesn't match `sanitizeShop(config)(new URL(payload.dest).hostname, true)`. Update the documentation example to stop sourcing `shop` from `req.query.shop` independently of the token.

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };

export function sanitizeShop(config: ConfigInterface) {
  return (shop: string, throwOnInvalid = false): string | null => {
    let shopUrl = shop;
    const domainsRegex = [
      'myshopify\\.com',
      'shopify\\.com',
      'myshopify\\.io',
      'shop\\.dev',
    ];

    // Add domains from transformations (both source and target)
    if (config.domainTransformations) {
      domainsRegex.push(...getTransformationDomains(config));
    }

    const shopUrlRegex = new RegExp(
      `^[a-zA-Z0-9][a-zA-Z0-9-_]*\\.(${domainsRegex.join('|')})[/]*$`,
    );

    const shopAdminRegex = new RegExp(
      `^admin\\.(${domainsRegex.join('|')})/store/([a-zA-Z0-9][a-zA-Z0-9-_]*)$`,
    );

    const isShopAdminUrl = shopAdminRegex.test(shopUrl);
    if (isShopAdminUrl) {
      shopUrl = shopAdminUrlToLegacyUrl(shopUrl) || '';
    }

    const sanitizedShop = shopUrlRegex.test(shopUrl) ? shopUrl : null;
    if (!sanitizedShop && throwOnInvalid) {
      throw new InvalidShopError('Received invalid shop argument');
    }

    if (sanitizedShop && config.domainTransformations) {
      return applyDomainTransformations(sanitizedShop, config);
    }

    return sanitizedShop;
  };
