### Title
Wallet Contract permanently absorbs attached deposit on pre-promise transaction validation failures - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point is `#[payable]`, allowing any relayer/caller to attach a NEAR deposit. When the submitted RLP transaction fails parsing/validation inside `inner_rlp_execute` before a cross-contract promise is created, the error is converted into a successful `ExecuteResponse` value rather than a failed receipt, so the protocol-level automatic deposit refund never triggers, and the contract has no mechanism to return or use the attached deposit.

### Finding Description
`rlp_execute` ( [1](#0-0) ) calls `inner_rlp_execute`, which captures `env::attached_deposit()` into an `ExecutionContext` and wraps it in `CallerDeposit` ( [2](#0-1) ). If transaction parsing fails with a `User` error or other non-relayer error, the function returns `Err(err)` directly without creating any `Promise` ( [3](#0-2) ). Back in `rlp_execute`, this `Err(e)` (for non-`Relayer` errors) is turned into `PromiseOrValue::Value(e.into())` ( [4](#0-3) ) — a *successful* method return from the runtime's perspective. Because the receipt succeeds, `refund_unspent_gas_and_deposits`/`Receipt::new_balance_refund` (only triggered on receipt failure per `runtime/runtime/src/lib.rs:1402-1407`) is never invoked, and the `CallerDeposit`-based manual refund logic in `rlp_execute_callback` ( [5](#0-4) ) is also unreachable since no promise/callback chain was started at all. The deposit thus becomes part of the Wallet Contract account's own NEAR balance permanently, with no `withdraw` or self-refund capability exposed anywhere in the contract ( [6](#0-5) ).

### Impact Explanation
Any relayer or caller who attaches a NEAR deposit to `rlp_execute` alongside a transaction that fails early validation (malformed RLP, invalid signature encoding, unsupported action type, etc.) permanently loses that deposit into the eth-implicit account's balance, since eth-implicit/Wallet Contract accounts cannot have a full-access key added (per `docs/DataStructures/Account.md:121`) and there is no method to move out stray NEAR balance not tied to an in-flight transaction. This is a fund-loss/frozen-funds condition reachable by any unprivileged external caller (relayer) attaching a deposit, matching the "value permanently stuck" impact class.

### Likelihood Explanation
Likelihood is moderate: it requires a caller to attach a deposit to `rlp_execute` while submitting a transaction that fails parsing/validation before promise dispatch — plausible for buggy/malicious relayers, or via user error, but not the primary designed usage pattern (most legitimate uses pass validation and reach the promise-based refund path tested by `test_caller_refunds`, `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs:170-229`).

### Recommendation
In `rlp_execute`, when `inner_rlp_execute` returns `Err(e)` and `env::attached_deposit()` is non-zero, issue a `Promise::new(predecessor_account_id).transfer(deposit)` (or equivalent `promise_batch_action_transfer`) to refund the caller before returning `PromiseOrValue::Value(e.into())`, mirroring the refund logic already present in `rlp_execute_callback`.

### Proof of Concept
1. A relayer calls `rlp_execute(target, tx_bytes_b64)` on a deployed Wallet Contract account, attaching a nonzero NEAR deposit via `#[payable]`.
2. `tx_bytes_b64` is crafted to be a malformed/unparsable RLP payload (or otherwise triggers `internal::parse_rlp_tx_to_action` to return `Err(Error::User(_))`), per `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:347-393`.
3. `inner_rlp_execute` returns `Err(err)` without creating any `Promise`.
4. `rlp_execute` converts this into `PromiseOrValue::Value(e.into())`, returning a successful `ExecuteResponse{success: false, ...}` as the receipt's success value — no failed receipt, no refund receipt generated.
5. Query the Wallet Contract account balance: the attached deposit remains there permanently, with no method available to extract it.
