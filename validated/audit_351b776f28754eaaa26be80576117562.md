Based on the investigation, there's a structurally similar issue in `createContractImpl` in the TVM contract creation path, where an existing on-chain account object is partially "re-initialized" as a contract without fully resetting its prior state fields — analogous to the LPP metadata re-initialization issue (partial overwrite of a struct's fields while leaving stale fields from before).

### Title
Pre-funded/legacy account reused as new contract account without fully clearing stale resource/vote state - (actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.createContractImpl()` decides whether an address being targeted by `CREATE`/`CREATE2` "already has a contract" via `existingAccount != null` and, only under the `allowTvmConstantinople` feature flag, a stricter `isContractExist()` check. When the target address corresponds to a pre-existing plain account (e.g. one that has previously received a TRX/TRC10 transfer, votes, frozen balance, or delegated resources), the code does not always fully reset that account's state before allowing it to become the account backing a freshly created contract.

### Finding Description [1](#0-0) 

In the `allowTvmConstantinople()` branch, if `existingAccount != null` but `contractAlreadyExists` is false (i.e. an account exists at the target address but is not itself already a deployed contract), the code mutates the *existing* `AccountCapsule` object in place:
```
} else if (!contractAlreadyExists) {
  existingAccount.updateAccountType(AccountType.Contract);
  existingAccount.clearDelegatedResource();
  deposit.updateAccount(newAddress, existingAccount);
}
```
Only `clearDelegatedResource()` is invoked; other economically meaningful fields carried over from the pre-existing account (votes, frozen balance/TronPower, latest consume/operation timestamps, resource usage counters) are not shown to be reset in this path, and are therefore preserved into the new contract account.

In the legacy (non-Constantinople) branch, the situation is worse: no `updateAccountType`/reset call happens at all — the code only creates the `ContractCapsule` (bytecode/ABI metadata record) and adjusts balance:
```
} else {
  deposit.createAccount(newAddress, "CreatedByContract", Protocol.AccountType.Contract);
  ...
  deposit.createContract(newAddress, new ContractCapsule(newSmartContract));
  long oldBalance = deposit.getBalance(newAddress);
  deposit.addBalance(newAddress, oldBalance);
}
```
This is the same class of bug as the LPP metadata issue: a storage record intended to represent a freshly-initialized entity is instead built on top of an existing record, and only a subset of that record's fields are explicitly cleared/overwritten, leaving unrelated but security-relevant fields (resource accounting, voting power, frozen balances) unintentionally carried forward.

### Impact Explanation
An attacker who can predict a future contract address (deterministic for `CREATE2`, and computable for ordinary `CREATE` if the deploying account's nonce/tx hash is known/controllable) can pre-fund that address, delegate resources to it, vote with it, or freeze balance on it as a normal account, then trigger contract creation at that address. Depending on the exact fields left uncleared, this could let the resulting contract inherit unearned TronPower/votes or resource-usage state that was never validated as belonging to a contract, corrupting energy/bandwidth accounting or vote tallying — a resource/reward accounting corruption reachable purely through ordinary contract-call transactions (`CREATE`/`CREATE2`), not requiring any privileged actor.

### Likelihood Explanation
Reachability is high in principle — contract creation via `CREATE`/`CREATE2` is available to any unprivileged account, and CREATE2 addresses are deterministically predictable, so pre-funding/pre-voting an address before deployment is directly controllable by an attacker. However, I could not fully verify (due to tool/read failures in this session) the complete set of fields covered by `AccountCapsule.clearDelegatedResource()` versus what other fields (votes, frozen v2 balances, latest timestamps) remain uncleared, nor the exact behavior of `isContractExist()`. This uncertainty means the concrete exploitability (which specific accounting field is stale and how it can be abused) is not fully confirmed from the available code excerpts, and would need direct inspection of `AccountCapsule.clearDelegatedResource()`/`updateAccountType()` and `isContractExist()` to confirm.

### Recommendation
When converting a pre-existing account into a contract account (in both the Constantinople and legacy branches), fully reset all resource-accounting and governance fields (votes, TronPower/frozen balances V1 and V2, delegated resource in both directions, usage/consume timestamps) rather than only clearing delegated resource, or reject contract creation entirely if the target address has any non-default account state.

### Proof of Concept
Not executable in this session — would require constructing a `CREATE2` deployment where the target address is first pre-funded/voted/frozen as a normal account (using `AccountCapsule` setters analogous to `freezeV2`/`vote` operations), then verifying via `AccountStore` state after deployment whether stale fields (votes/frozen balances) survive the contract-creation path in `Program.createContractImpl()`. This requires a running node/test harness (e.g. `FreezeV2Test`/`Create2Test` style tests already present in the repo) to confirm, which is outside the scope of static analysis performed here.
