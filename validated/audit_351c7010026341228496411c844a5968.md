### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery/replay - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
The Solidity `bps()` bug lets an attacker inject an extra value at the end of `calldata` that is used for the security-relevant action (token transfer) while a *different* value is used for the actual computation, because the two values are never checked against each other. The `shopify-app-js` webhook validation pipeline has the same class of bug: the HMAC only covers `rawBody`, but the `domain` (shop) that gets used to look up/create the session and attribute the payload is taken from an **unsigned header** and is trusted without being tied to the HMAC-validated body.

### Finding Description
`validateHmacFromRequestFactory` computes the HMAC exclusively over `rawBody`: [1](#0-0) 

`validateFactory` then separately extracts the `domain` (and `topic`, `apiVersion`, `webhookId`) straight from request headers with `checkWebhooksHeaders`/`checkEventsHeaders`, without ever binding those header values into the HMAC computation: [2](#0-1) 

The `domain` field returned as part of the "valid" result is then used, unquestioned, to select which shop's offline session to load and use for API calls in every framework adapter: [3](#0-2) 

Because Shopify webhooks for **all** shops installed on an app are signed with the same `apiSecretKey` (the app's shared secret, not a per-shop secret), the HMAC over `rawBody` is valid for a given body/HMAC pair *regardless of which shop's domain header accompanies it*. This is structurally identical to the `bps()` flaw: the "computation" (HMAC validation) is performed on one piece of data (`rawBody`), while the "action" (selecting which tenant's session/admin client to use, and what shop the payload is attributed to) is driven by a different, unauthenticated piece of data (`X-Shopify-Shop-Domain` header) that is never cross-checked against what was actually signed.

An unprivileged single merchant that owns their own app installation receives legitimate webhooks with a valid `hmac` for their own shop's body. They can capture such a `(rawBody, hmac)` pair and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to point at a **different (victim) shop** that is also installed on the same app. `validateHmacFromRequestFactory` will report `valid: true` (it only checked `rawBody` against `hmac`, and does not care what shop sent it), and `checkWebhooksHeaders`/`checkEventsHeaders` will happily accept the attacker-controlled `domain` value, causing:
- `ensureValidOfflineSession(params, check.domain)` to load/create the **victim's** offline session and admin client, and
- the attacker's own webhook payload (`rawBody`) to be delivered to the app's webhook handler tagged as belonging to the victim shop. [4](#0-3) [5](#0-4) 

### Impact Explanation
This is a confused-deputy / cross-tenant issue: an attacker with their own legitimate (paid or free) app install can forge webhook deliveries that the app processes as if they originated from a victim shop. Depending on what the app's webhook handlers do with the `shop`/`domain` field (e.g., updating per-shop billing state, toggling settings, writing/deleting data keyed by shop, triggering emails, or acting through the victim's `admin` client using the victim's real access token while fed attacker-controlled body content), this can lead to data corruption, unauthorized actions performed against a victim shop's Admin API, or state confusion between tenants. The severity is app-handler-dependent but the platform-level flaw (unsigned domain header trusted for tenant selection) is the same class of issue as the Sherlock report: "computations are done using data that was never validated against what was actually authenticated."

### Likelihood Explanation
Reachable by any unprivileged actor who can install the app on at least one shop (or observe one legitimate webhook delivery) and can send a single crafted HTTP POST to the app's public webhook endpoint — no privileged access, no leaked secret, and no MITM is required, since the app secret key is shared across all shops using the app and the domain header is never bound to the signature.

### Recommendation
Bind the shop/domain (and other routing-relevant headers such as topic, api-version, webhook-id) into the HMAC-covered material, or otherwise cryptographically verify that the `X-Shopify-Shop-Domain` header corresponds to a shop that the signed `rawBody` actually originated from (e.g., include shop domain in the signed payload check, or independently verify domain ownership against the session store keyed by a value derived from the signature). At minimum, document/enforce that `checkWebhooksHeaders`/`checkEventsHeaders` in `packages/apps/shopify-api/lib/webhooks/validate.ts` must not treat `domain` as trusted routing input for tenant/session selection unless it is included in the signed payload.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives (or triggers) a legitimate webhook, capturing `rawBody` and its valid `X-Shopify-Hmac-Sha256` value (both are computed from data controllable/observable by the attacker's own shop).
2. Attacker sends:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: <topic>
X-Shopify-Shop-Domain: victim-shop.myshopify.com   <-- forged, not part of HMAC
X-Shopify-Hmac-Sha256: <hmac valid for attacker's rawBody>
X-Shopify-Webhook-Id: ...
X-Shopify-Api-Version: ...

<attacker's rawBody>
```
3. `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts:168-201`) validates `hmac` against `rawBody` only — passes.
4. `checkWebhooksHeaders` (`packages/apps/shopify-api/lib/webhooks/validate.ts:99-134`) extracts `domain: 'victim-shop.myshopify.com'` from the unsigned header — accepted.
5. `authenticate()` in `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts:52` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading the victim's session/admin client while processing the attacker's payload.

**Uncertainty**: I could not fully trace what every app's webhook `callback` handler does with `domain`/`session` (that is app-specific business logic outside this repo), so the concrete end-impact (data write, billing manipulation, etc.) depends on the consuming app. The root-cause gap in the shared library — unsigned `domain` header trusted for session/tenant selection — is confirmed directly in the cited files.

import {BasicParams} from '../types';

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
