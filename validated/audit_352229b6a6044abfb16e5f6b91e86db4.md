### Title
`ensure_match_transaction_info()` silently skips validation of `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, allowing replay-verify to accept a corrupted/divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the authenticated cross-check used by replay/verify tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a locally re-executed `TransactionOutput` matches the trusted, previously-committed `TransactionInfo` pulled from the ledger/accumulator. It validates status, gas, write-set hash, and event-root hash, but the function's own code comment admits it does **not** validate `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields carried on `TransactionInfo`. [1](#0-0) 

### Finding Description
`TransactionInfoV1` carries `hot_state_checkpoint_hash` and the newly repurposed `position_state_checkpoint_hash` field, both of which are authenticated (covered by `BCSCryptoHash`/inclusion in the transaction accumulator) roots of the hot state and the "native position" (trading-native) state tree respectively. [2](#0-1) 

These roots are produced during normal execution by `DoLedgerUpdate::assemble_transaction_infos`, which plumbs `hot_state_checkpoint_hashes` and `position_state_checkpoint_hashes` computed in `DoStateCheckpoint::run` / `compute_position_checkpoint` into the `TransactionInfo` builder. [3](#0-2) [4](#0-3) 

However, when tooling needs to *verify* that re-execution reproduces the exact committed ledger state (`replay_on_archive`, CLI simulate/validate paths), it relies solely on `ensure_match_transaction_info()`, which checks only `status`, `gas_used`, `write_set_hash` (== `state_change_hash`), and `event_root_hash`: [5](#0-4) 

The function's own inline comment documents the gap explicitly:

```rust
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [6](#0-5) 

This means: if the locally recomputed `position_state_checkpoint_hash` (or `hot_state_checkpoint_hash`) diverges from the value bound in the trusted `TransactionInfo` (e.g. due to a bug in `compute_position_checkpoint`'s SMT extension logic, an execution-vs-storage schema mismatch, or a corrupted persisted position summary), the divergence is never surfaced — `ensure_match_transaction_info` reports a full match anyway, because the checkpoint-hash fields are simply not part of the comparison.

### Impact Explanation
This breaks the core "committed state must match VM re-execution result" invariant for the position/hot-state checkpoint roots specifically. `replay_on_archive` and equivalent verification tools are the last line of defense used to detect state-divergence bugs (including hard-fork-class divergences) between the trusted on-chain accumulator and re-execution. Because the position-state root (guarded by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature) and hot-state root are excluded from the check, a bug that corrupts the position/hot-state Merkle root during commit, restore, or replay would go undetected by the tool whose entire purpose is to catch exactly this class of bug. This is a proof/root-binding gap on an authenticated, accumulator-embedded value — falling squarely in the "wrong accumulator root ... accepted as valid" and "hard-fork-only divergence during commit/replay" impact categories.

### Likelihood Explanation
The gap is deterministic and code-documented (not speculative): any actual divergence in the position/hot-state root computation — whether from a real executor bug, a storage bug in `sharded_jmt_state`/`state_summary`, or a restore-path bug — is guaranteed to slip past `ensure_match_transaction_info`, because the check for those two fields simply does not exist. The trigger condition is limited to configurations where `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / hot-state roots are enabled, and the comment explicitly flags this as a pre-condition ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), indicating the feature may already be enabled or on a path to being enabled while this validation gap remains open.

### Recommendation
Extend `ensure_match_transaction_info()` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on the `TransactionInfo` and when the corresponding roots are computed locally), returning an error on mismatch just as is done for `write_set_hash`/`event_root_hash`, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any network where replay-verify is relied upon as an integrity gate.

### Proof of Concept
Not independently reproducible from static analysis alone — this finding is a verification-logic gap rather than a data-corruption bug with a concrete triggering input. Confirming exploitability would require constructing a scenario (e.g., via a fuzzed/malformed persisted position-state summary or a targeted bug in `compute_position_checkpoint`) that produces a wrong `position_state_checkpoint_hash` and demonstrating that `aptos-move/cli/src/commands.rs` / `storage/db-tool/src/replay_on_archive.rs` report success despite the divergence; this requires runtime/test-harness access beyond what static code review can provide here. I flag this as a documented, self-admitted logic gap in `ensure_match_transaction_info`, not a fully executed exploit.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
