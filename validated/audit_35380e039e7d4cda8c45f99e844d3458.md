## Finding: Duplicate-tenure-block detection uses a weaker, non-equivalent predicate in the v1 signer path than in v2, allowing double-counted signer weight to certify two conflicting tenure-start blocks

### Summary
The stacks-signer chainstate validation logic that rejects a second, competing tenure-change block for a tenure that a signer has already helped certify differs between the v1 and v2 signer protocol implementations. `validate_tenure_change_payload` in v2 treats a block as a duplicate if it has been *locally or globally* signed (`get_last_signed_block`), while the v1 implementation only treats a block as a duplicate if it has been *globally* accepted (`get_last_globally_accepted_block`), i.e. confirmed by the node. This creates a window, prior to global confirmation, in which v1-protocol signers do not recognize an already (locally) signed tenure-start block as a conflict and can sign a second, competing tenure-change block for the same tenure — letting the same honest signer weight be double-counted across two mutually exclusive blocks, each of which can independently reach the 70% signing threshold.

### Finding Description
The consensus-critical invariant enforced by `check_nakamoto_tenure`/tenure-change validation is that at most one tenure-start block can be certified per tenure (`TenureChangeCause::BlockFound` must uniquely identify the tenure) [1](#0-0) . This invariant is enforced socially by the signer set: `validate_tenure_change_payload` must reject a second proposal for a tenure that has already been signed.

The v2 path checks against `get_last_signed_block`, which covers blocks that are *either* locally or globally accepted: [2](#0-1) 

The v1 path instead checks against `get_last_globally_accepted_block`, which only covers blocks the *node* has confirmed processing (via a `NewBlock` event), not blocks the signer has merely locally accepted/signed: [3](#0-2) 

This divergence is explicitly documented as intentional version-skew behavior, with the comment noting the v1 count is strictly narrower than v2's: [4](#0-3) 

Because `mark_locally_accepted` fires for a signer once it has independently observed ≥70% signing weight over StackerDB gossip — before the node has processed/confirmed the block — there is a real window where a block is "signed" (from the network's perspective) but not yet "globally accepted." [5](#0-4) 

A malicious or Byzantine miner that has legitimately won the current tenure's sortition can craft two distinct tenure-change blocks (A and B) for the same tenure and selectively propose them to different signer subsets. v2 signers, once they have signed A (or observed it reach the local acceptance threshold), reject B via `DuplicateBlockFound`. v1 signers, however, only reject a competing proposal once the *node* has confirmed A, which requires the node to actually receive and process A's signatures — an event that can lag behind or be raced against B's proposal. During that gap, v1 signers can validate and sign B as well, contributing their weight toward B's own 70% threshold, while that same weight was already spent (from the v2 signers' perspective) supporting A. The system-wide accounting that assumes a signer's weight is spent on at most one block per tenure is violated: v1-protocol signer weight is silently double-counted across two mutually-exclusive blocks.

### Impact Explanation
This breaks the equality that "a signature threshold reached for a Nakamoto tenure-start block is unique per tenure and backed by disjoint signer weight." If enough v1-protocol signer weight double-signs, both block A and block B can independently reach the reported 70% approval threshold and be broadcast/relayed as valid, fully-signed Nakamoto blocks for the same tenure. This is a minority-triggerable signer/validation divergence between honest signers, producing a temporary tip disagreement (nodes that receive A vs. B diverge on their canonical tip) until the fork resolves — matching the "High" severity bucket (minority-triggerable static-validation divergence / temporary tip disagreement) in scope for this repo's signer boot/validation logic.

### Likelihood Explanation
Exploitation requires only: (1) a miner that has already won the current tenure's sortition (an ordinary, unprivileged, and frequent occurrence — no admin/majority needed), (2) a live mixed-protocol-version signer set (explicitly a supported and tested configuration, per `supported_signer_protocol_version` and the dedicated v1/v2 modules), and (3) network-level timing to deliver a second proposal to v1 signers before the node confirms the first. All three preconditions are realistic during any signer-protocol upgrade rollout window.

### Recommendation
Make `validate_tenure_change_payload` in the v1 chainstate path use the same duplicate-detection predicate as v2 (`get_last_signed_block`, i.e., locally *or* globally accepted), so that any signer — regardless of protocol version — refuses to sign a second competing tenure-change block once it, or its peers, have already signed one for that tenure. Alternatively, gate mixed v1/v2 operation so that duplicate-block protection is computed from a version-independent, canonical predicate shared by both code paths.

### Proof of Concept
1. Stand up a Nakamoto testnet with a mixed signer set: some signers running the v1 protocol module, others v2 (as exercised by `signer_waits_for_validation_before_signing`-style multi-signer harnesses [6](#0-5) ).
2. As the winning miner for tenure T, construct two distinct tenure-change block proposals A and B, both citing tenure T as `tenure_consensus_hash`.
3. Broadcast A first; wait until it crosses the local signing threshold for a subset of v2 signers (`mark_locally_accepted`) but before the node emits a `NewBlock` event confirming it.
4. Broadcast B to the v1-protocol signers. Because `validate_tenure_change_payload` (v1) only consults `get_last_globally_accepted_block`, and A has not yet been globally accepted, v1 signers do not detect a duplicate and proceed to validate/sign B.
5. Observe that B accumulates enough weight (from v1 signers plus any v2 signers that have not yet observed A) to independently cross the 70% `compute_voting_weight_threshold`, producing two conflicting, fully-signed blocks for tenure T.
