### Title
Leader-key consumption is never checked in block-commit validation, allowing one VRF key to back multiple commits - ([File: stackslib/src/chainstate/burn/operations/leader_block_commit.rs])

### Summary
`LeaderBlockCommitOp::check_common` in `stackslib/src/chainstate/burn/operations/leader_block_commit.rs` only verifies that a referenced leader key exists at `(key_block_ptr, key_vtxindex)` via `get_leader_key_at`, but never calls `SortitionHandleTx::is_leader_key_consumed` (defined in `stackslib/src/chainstate/burn/db/sortdb.rs`) to check whether that key has already backed a prior accepted commit on the fork. This breaks the intended invariant that each registered leader key can be consumed by at most one commit.

### Finding Description
The equality that should hold is: **for a given fork, `count(LeaderBlockCommitOp referencing key K)` accepted == 1** (a leader key is consumed exactly once). 

Tracing the code:
- `check_common` (`stackslib/src/chainstate/burn/operations/leader_block_commit.rs:1167-1232`) looks up the key with `tx.get_leader_key_at(leader_key_block_height, self.key_vtxindex.into(), &tx_tip)` and only errors if the key is *absent* (`BlockCommitNoLeaderKey`). It never checks `is_leader_key_consumed`. [1](#0-0) 
- `SortitionHandleTx::is_leader_key_consumed` (`stackslib/src/chainstate/burn/db/sortdb.rs:1437-1466`) exists specifically to answer "has this key already been consumed by a subsequent commit on this fork's history," reading the `vrf_key_status` MARF key, but it is exercised only in unit tests (`stackslib/src/chainstate/burn/db/sortdb.rs:7909-7954`) — no production call site invokes it from the block-commit validation path. [2](#0-1) 
- `LeaderKeyRegisterOp::check` (`stackslib/src/chainstate/burn/operations/leader_key_register.rs:213-234`) only prevents *re-registering* the same VRF public key (`has_VRF_public_key`), which is orthogonal to consumption by a commit. [3](#0-2) 
- `get_consumed_leader_keys` (`stackslib/src/chainstate/burn/db/sortdb.rs:1318-1348`), used post-sortition to record consumption for winners, is only invoked for the block-commit(s) that actually win a sortition round — it does not gate acceptance of competing candidate commits during validation, so nothing stops two (or more) commits from referencing the very same `(key_block_ptr, key_vtxindex)` in the same or different burn blocks and both being accepted as valid candidates. [4](#0-3) 

**Attacker's exact input**: the attacker registers one `LeaderKeyRegisterOp` (one Bitcoin tx, minority cost), then broadcasts two (or more) `LeaderBlockCommitOp`s that both set `key_block_ptr`/`key_vtxindex` to point at that same registered key — either in the same burn block (to get two independent candidate slots in the same sortition round) or across two different sortition rounds/forks (to reuse the same key indefinitely without re-registering).

**Why existing guards fail**: `check_common` validates key *existence*, not *consumption*; `is_leader_key_consumed` is dead code from the perspective of the commit-acceptance path (only referenced by tests as of this snapshot).

### Impact Explanation
This lets a single, minority-stake miner effectively claim multiple independent candidate slots in the burn distribution/sortition using only one registered VRF key, rather than the intended one-key-one-commit relationship. Since the sortition winner is chosen probabilistically weighted by burn amount among *all* valid candidates, having multiple simultaneously-valid candidates backed by the same key increases the attacker's effective chance of winning a round relative to honest participants who must register (and pay for) a fresh key per attempt, and it allows key reuse across otherwise-unrelated tenures, undermining the freshness assumption tied to each VRF key. This matches "High – a minority-triggerable sortition/VRF ... divergence" in the stated severity rubric.

### Likelihood Explanation
The only precondition is broadcasting one Bitcoin `LeaderKeyRegisterOp` (cost of one on-chain tx) and then two or more `LeaderBlockCommitOp`s referencing the same key pointer fields — entirely within a single minority participant's control, requiring no majority stake, no signer collusion, and no privileged role. This is directly and repeatably testable by constructing two `LeaderBlockCommitOp`s with identical `key_block_ptr`/`key_vtxindex` and checking both pass `check_common`.

### Recommendation
Add a consumption check to `check_common` (or an earlier stage of `LeaderBlockCommitOp::check`) that calls `tx.is_leader_key_consumed(&register_key)` after resolving the referenced key, and rejects the commit (e.g., a new `op_error::BlockCommitLeaderKeyAlreadyConsumed`) if the key has already been consumed by an earlier accepted commit on the same fork. Ensure this check is fork-aware (per `sortition_id`/chain tip) so that consumption on one fork does not incorrectly block use on a sibling fork where the key is still fresh, consistent with the existing fork-handling in `is_leader_key_consumed` and `get_consumed_leader_keys`.

### Proof of Concept
Rust integration test plan (extending the existing test harness in `stackslib/src/chainstate/burn/operations/leader_block_commit.rs` tests and `sortdb.rs` tests):
1. Set up a `SortitionDB` and append a burn block containing one `LeaderKeyRegisterOp` (`key_1`) — mirror the pattern used in `stackslib/src/chainstate/burn/db/sortdb.rs:7806-7823`.
2. Construct `block_commit_a` referencing `key_1.block_height`/`key_1.vtxindex`, and call `block_commit_a.check_common(...)` (or the public `check`/`check_and_add_ops` equivalent) — assert `Ok(())`.
3. Simulate `block_commit_a` being accepted/appended as a chain-tip snapshot (consuming `key_1`).
4. Construct `block_commit_b` (different `txid`, same or later burn height) also referencing `key_1.block_height`/`key_1.vtxindex`, and call its `check_common(...)` against the same fork tip.
5. **Assertion on both sides of the equality**: before the fix, assert `block_commit_b.check_common(...) == Ok(())` (demonstrating the bug — the key is consumed twice); after applying the recommended fix, assert `block_commit_b.check_common(...) == Err(op_error::BlockCommitLeaderKeyAlreadyConsumed)` (or equivalent), confirming `is_leader_key_consumed(&key_1)` becomes `true` after step 3 and is honored by `check_common`.

    /// The burn DB should have a key for each candidate; otherwise the candidate would not have

    pub fn get_consumed_leader_keys(
        &mut self,
        parent_tip: &BlockSnapshot,
        block_candidates: &[LeaderBlockCommitOp],
    ) -> Result<Vec<LeaderKeyRegisterOp>, db_error> {
        // get the set of VRF keys consumed by these commits
        let mut leader_keys = vec![];
        for candidate in block_candidates.iter() {
            let leader_key_block_height = candidate.key_block_ptr as u64;
            let leader_key_vtxindex = candidate.key_vtxindex as u32;
            let leader_key = self
                .get_leader_key_at(
                    leader_key_block_height,
                    leader_key_vtxindex,
                    &parent_tip.sortition_id,
                )?
                .unwrap_or_else(|| {
                    panic!(
                        "FATAL: no leader key for accepted block commit {} (at {},{})",
                        &candidate.txid, leader_key_block_height, leader_key_vtxindex
                    )
                });

            leader_keys.push(leader_key);
        }

        Ok(leader_keys)
    }

    pub fn is_leader_key_consumed(
        &mut self,
        leader_key: &LeaderKeyRegisterOp,
    ) -> Result<bool, db_error> {
        if leader_key.block_height >= BLOCK_HEIGHT_MAX {
            return Err(db_error::BlockHeightOutOfRange);
        }
        let chain_tip = self.context.chain_tip.clone();

        let key_status =
            match self.get_indexed(&chain_tip, &db_keys::vrf_key_status(&leader_key.public_key))? {
                Some(status_str) => {
                    if status_str == "1" {
                        // key is still available
                        false
                    } else if status_str == "0" {
                        // key is consumed
                        true
                    } else {
                        panic!("Invalid key status string {}", status_str);
                    }
                }
                None => {
                    // never before seen
                    false
                }
            };

        Ok(key_status)
    }
