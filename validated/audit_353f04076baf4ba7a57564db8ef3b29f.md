Confirmed: `GlobalContractDeployMode::AccountId` deploys are keyed only by `account_id` — `initiate_distribution` computes `GlobalContractIdentifier::AccountId(account_id.clone())` with no code-hash binding [1](#0-0) , and the same owner can call `DeployGlobalContractAction` again later with different bytecode; `apply_distribution_current_shard` simply overwrites the trie value at the `GlobalContractCode{AccountId}` key as long as the nonce is fresh, with no check against any previously committed code [2](#0-1) .

### Title
Deterministic accounts referencing a mutable `GlobalContractIdentifier::AccountId` do not commit to fixed code, breaking the "fixed code and fixed initial state" invariant - (File: `runtime/runtime/src/deterministic_account_id.rs`, `runtime/runtime/src/global_contracts.rs`, `core/primitives/src/utils.rs`)

### Summary
NEP-616 deterministic accounts are documented and designed around the invariant that a `0s…` account ID is a full commitment to "fixed code and fixed initial state" [3](#0-2) . The account ID is derived by hashing the `DeterministicAccountStateInit`, whose `code` field is a `GlobalContractIdentifier` that can be either `CodeHash(CryptoHash)` (immutable, content-addressed) or `AccountId(AccountId)` (a mutable pointer to whatever code that account last deployed) [4](#0-3) . When `AccountId` is used, the deterministic account's identity commits only to the *identifier*, not to any hash of the actual bytecode, and `use_global_contract`/`action_deploy_global_contract` allow the identifier owner to redeploy different code under that same `AccountId` at any later point (subject only to a freshness nonce, not a content check) [5](#0-4) [6](#0-5) . This is structurally the same "duplicated state that must stay in sync but is only validated in one code path, not the other" pattern as the DInterest report: `DeterministicStateInitAction`/`UniversalStateInitAction` validate that `receiver_id == derive_*_account_id(state_init)` at creation time (`InvalidDeterministicStateInitReceiver`/`InvalidUniversalStateInitReceiver`) [7](#0-6) [8](#0-7) , but there is no corresponding check anywhere that binds the account's *behavior* (the code that `AccountId`-mode global contract identifier resolves to) to anything immutable, so the "fixed code" half of the invariant is never actually enforced.

### Finding Description
`derive_near_deterministic_account_id` computes the account id by Borsh-encoding the whole `DeterministicAccountStateInit` (which contains `code: GlobalContractIdentifier`) and hashing it [9](#0-8) . When `code = GlobalContractIdentifier::AccountId(publisher)`, the hash commits to `publisher`'s account id string — not to any snapshot of the WASM `publisher` had deployed at account-creation time. `use_global_contract` sets `AccountContract::GlobalByAccount(id)` on the account so that at call time the runtime resolves code by looking up the *current* trie entry for `TrieKey::GlobalContractCode{ AccountId(id) }` [10](#0-9) . That trie entry is not append-only or hash-checked: `apply_distribution_current_shard` simply `state_update.set(trie_key, global_contract_data.code().to_vec())`, keyed by `GlobalContractCodeIdentifier::AccountId(account_id)`, gated only by a monotonically-increasing nonce that the same account controls via `initiate_distribution`/`increment_nonce` [11](#0-10) [12](#0-11) . Nothing in `action_validation.rs`'s deterministic/universal state-init validation, nor in the deterministic-account creation path, checks that the referenced `AccountId`-identified global contract's code is pinned or will remain unchanged after the deterministic account is created — the validation only checks the *receiver id ↔ state_init hash* relationship [13](#0-12) , exactly mirroring `setInterestOracle`'s checked relationship in the original report while the corresponding "other half" of the invariant (code immutability) is left unchecked anywhere, including at deterministic-account creation.

### Impact Explanation
Any unprivileged account can deploy a global contract in `AccountId` mode, let users/relayers/dApps create deterministic accounts whose id is derived from `code = GlobalContractIdentifier::AccountId(that_account)` and fund/use them trusting the documented "fixed code" guarantee, and later redeploy different code to the same `AccountId` identifier. Every existing deterministic account bound to that identifier then silently starts executing different logic — this is a state-transition/behavior change that is invisible from the account id and from the original state-init payload the user validated. Depending on the new code, this can move funds unauthorizedly out of every account using that identifier (e.g. change a "vault" contract's withdraw logic to drain balances to an attacker-controlled address), which matches "concrete unauthorized value movement" from the accepted-impact list.

### Likelihood Explanation
Reachable entirely through ordinary transactions from any unprivileged signer: `DeployGlobalContractAction` (to publish/republish code), `DeterministicStateInitAction`/`UniversalStateInitAction` (to create deterministic accounts pointing at that identifier), and normal `FunctionCall`s to those accounts. No validator, network, or operator privilege is required, and the mismatch is a design/validation gap rather than a race condition, so it is deterministically reproducible once a victim protocol/dApp adopts `GlobalContractIdentifier::AccountId` for a deterministic account it advertises as having fixed behavior.

### Recommendation
- Short term: document loudly (and/or add a protocol-level restriction) that `DeterministicAccountStateInit`/`UniversalStateInit` should disallow `GlobalContractIdentifier::AccountId` for the `code` field, or require that once a deterministic account is created referencing an `AccountId` identifier, that identifier's code becomes frozen (e.g., reject further `DeployGlobalContractAction`s to an `AccountId` that already has one or more deterministic accounts bound to it, or require deterministic/universal accounts to only reference `GlobalContractIdentifier::CodeHash`, which is truly content-addressed and immutable).
- Long term: avoid basing "fixed code" security claims on a duplicated/mutable reference (`AccountId`) instead of a single canonical, content-addressed commitment (`CodeHash`), consistent with the original report's long-term advice to avoid duplicated state that can drift out of sync.

### Proof of Concept
1. Attacker account `A` calls `DeployGlobalContractAction{ code: benign_wasm, deploy_mode: AccountId }` from account `A` — this creates `GlobalContractIdentifier::AccountId(A)` pointing at `benign_wasm` (see `test-loop-tests/src/tests/deterministic_account_id.rs` `deploy_global_contract` helper usage) [14](#0-13) .
2. A user computes `state_init = DeterministicAccountStateInitV1{ code: GlobalContractIdentifier::AccountId(A), data }`, derives `det_account = derive_near_deterministic_account_id(state_init)`, and sends `DeterministicStateInitAction{ state_init, deposit }` to `det_account` — this passes the `InvalidDeterministicStateInitReceiver` check since `det_account` was correctly derived [15](#0-14) . The user deposits funds and interacts with `det_account`, trusting `benign_wasm`'s logic.
3. Later, `A` calls `DeployGlobalContractAction{ code: malicious_wasm, deploy_mode: AccountId }` again. `initiate_distribution`/`apply_distribution_current_shard` overwrite the `GlobalContractCode{AccountId(A)}` trie entry with `malicious_wasm`, gated only by the nonce that `A` itself controls [11](#0-10) [12](#0-11) . No check anywhere rejects this because `det_account` already exists and is bound to `AccountId(A)`.
4. Every subsequent `FunctionCall` to `det_account` now executes `malicious_wasm`, even though `det_account`'s id was supposedly "fully defined by its initial state" — allowing the attacker to redirect balances/withdrawals to themselves.

        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

        }

    let is_nonce_fresh = check_and_update_nonce(global_contract_data, &identifier, state_update)?;
    if !is_nonce_fresh {
        return Ok(0);
    }

    let config = apply_state.config.wasm_config.clone();
    let trie_key = TrieKey::GlobalContractCode { identifier };
    let code_len = global_contract_data.code().len() as u64;
    state_update.set(trie_key, global_contract_data.code().to_vec());

            code_hash,
        ));
    }

/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}
