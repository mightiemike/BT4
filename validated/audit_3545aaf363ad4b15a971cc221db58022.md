### Title
Unchecked subtraction of obsolete/tombstone byte counts in `AccountStorageReader::new` can underflow and corrupt snapshot storage streaming - ([File: accounts-db/src/account_storage_reader.rs])

### Summary
`AccountStorageReader::new` computes the number of "alive" bytes to stream out of an account storage file (used when writing/streaming accounts storages into a snapshot archive/dir) by subtracting an "obsolete bytes" quantity, and optionally a tombstone-bytes quantity, from the storage's total byte length, using plain unchecked `usize` subtraction. This mirrors the M-20 pattern of computing `balanceAfter - reservedFunds` style deltas where the subtracted term can exceed the base value.

### Finding Description
In `AccountStorageReader::new`: [1](#0-0) 

```rust
let num_total_bytes = storage.accounts.len();
let mut num_alive_bytes = num_total_bytes - storage.get_obsolete_bytes(snapshot_slot);
...
if tombstones_filter == TombstonesFilter::Exclude {
    let tombstone_stored_size = storage.accounts.calculate_stored_size(0);
    let tombstone_offsets = storage.tombstone_offsets_read_lock();
    num_alive_bytes -= tombstone_offsets.len() * tombstone_stored_size;
    ...
}
```

Both subtractions are plain `-`/`-=` operations on `usize`, not `saturating_sub`/`checked_sub`. This is the same bug class flagged in the external report: computing a "before/after" (here, "total minus excluded") quantity by subtracting a value that is assumed to always be smaller, without validating that invariant. If `storage.get_obsolete_bytes(snapshot_slot)` ever returns a value equal to or exceeding `num_total_bytes` (e.g., due to stale/duplicate obsolete-account bookkeeping, a snapshot_slot argument that causes over-counting, or tombstones being double counted since tombstones are themselves obsolete-marked accounts and could be included in both `get_obsolete_bytes` and the separate tombstone subtraction), the subtraction underflows. In a release build (the default for validator binaries, where overflow checks are compiled out), this silently wraps to a value near `usize::MAX` rather than panicking, which is even more dangerous than a panic because it would then be used as the declared length (`len()`) of the reader and consumed by `io::copy` in the streaming/serialization path.

This reader is directly used when producing the byte stream for account storage files, as seen in `copy_append_vecs`/`account_storages_to_stream`-style consumers: [2](#0-1) 

An incorrect (wrapped) `num_alive_bytes` would cause `reader.len()` to no longer match the actual data written by `Read::read`, which explicitly loops based on `num_total_bytes` and the excluded-account list: [3](#0-2) 

If `len()` (used elsewhere to size output buffers/allocate files, e.g. in tests at line 355/486/497) diverges from the real emitted length, downstream snapshot files can be truncated, malformed, or (if wrapped to a huge number) trigger enormous/invalid allocation requests.

### Impact Explanation
An honest node computing/serializing account storages for a snapshot (full or incremental) could produce a corrupted or malformed storage file whose declared length disagrees with its actual content, potentially causing the resulting snapshot to fail verification on load (`reconstruct_single_storage`/`AccountsFile::new_from_file`/`new_for_startup`) or, in a panic-enabled build, a node panic on the subtraction underflow itself. This falls into the "honest-node snapshot generation/rebuild mismatch" and "node panic" categories called out as acceptable impact classes.

### Likelihood Explanation
This requires the invariant `get_obsolete_bytes(snapshot_slot) <= storage.accounts.len()` (and no double-counting between obsolete bytes and tombstone bytes) to always hold. I was not able to fully verify, within the remaining budget, whether `get_obsolete_bytes` and the tombstone-offset bookkeeping in `account_storage_entry.rs` / `obsolete_accounts.rs` are guaranteed by construction to never overlap or overcount (e.g., whether tombstones are always a subset already reflected inside `get_obsolete_bytes`, which would make the second subtraction double-count tombstone bytes and underflow deterministically whenever `TombstonesFilter::Exclude` is used together with any obsolete-but-not-tombstone bytes). This is a real gap in my analysis — confirming exploitability requires tracing exactly how `mark_accounts_obsolete`, `batch_insert_tombstone_offsets`, and `get_obsolete_bytes` interact, which I could not complete before this session ended.

### Recommendation
Replace the unchecked subtractions in `AccountStorageReader::new` with `saturating_sub`/`checked_sub`, and add a debug assertion (or explicit error) validating that `storage.get_obsolete_bytes(snapshot_slot) + tombstone_bytes <= storage.accounts.len()` before computing `num_alive_bytes`. This mirrors the sherlock recommendation of avoiding order-dependent subtraction that assumes a strict ordering that may not always hold; using saturating arithmetic (or explicit validated invariants) prevents silent wraparound in release builds and converts programming errors into detectable panics/errors in debug/test builds instead of corrupting snapshot data silently.

### Proof of Concept
I could not construct a concrete PoC within this session because it requires confirming, from `accounts-db/src/account_storage_entry.rs` and `accounts-db/src/obsolete_accounts.rs`, a code path where `get_obsolete_bytes(snapshot_slot)` (plus, under `TombstonesFilter::Exclude`, the tombstone byte count) can exceed `storage.accounts.len()` for a given storage/slot combination — e.g., verifying whether tombstones are already included inside `get_obsolete_bytes`'s accounting, which would make the two subtractions overlap and always risk underflow whenever any tombstones exist. This should be validated with a background Devin session that has full repository access to trace `mark_accounts_obsolete`, `batch_insert_tombstone_offsets`, and `get_obsolete_bytes` end-to-end and, if the overlap is confirmed, write a unit test reproducing the underflow.

impl<'a, R: FileBufRead<'a>> Read for AccountStorageReader<'_, R> {
    fn read(&mut self, buf: &mut [u8]) -> io::Result<usize> {
        let mut total_read = 0;
        let buf_len = buf.len();

        while total_read < buf_len {
            let next_excluded_account = self.sorted_excluded_accounts.last();
            let file_offset = self.reader.get_file_offset() as usize;
            if let Some(&(excluded_start, excluded_size)) = next_excluded_account
                && file_offset == excluded_start
            {
                let skip_len = excluded_size.min(self.num_total_bytes - excluded_start);
                self.reader.consume_or_skip(skip_len);
                self.sorted_excluded_accounts.pop();
                continue;
            }

            // Cannot read beyond the end of the buffer
            let bytes_left_in_buffer = buf_len.saturating_sub(total_read);

            // Cannot read beyond the next excluded account or the end of the file
            let bytes_to_read_from_file = if let Some((excluded_start, _)) = next_excluded_account {
                excluded_start.saturating_sub(file_offset)
            } else {
                self.num_total_bytes.saturating_sub(file_offset)
            };

            let bytes_to_read = bytes_left_in_buffer.min(bytes_to_read_from_file);

            let read_size = self.reader.read(&mut buf[total_read..][..bytes_to_read])?;

            if read_size == 0 {
                break; // EOF
            }

            total_read += read_size;
        }

        Ok(total_read)
    }
