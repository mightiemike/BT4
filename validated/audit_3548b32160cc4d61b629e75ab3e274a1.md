### Title
`has_in_flight_tx` lock in the NEAR Wallet Contract can be left permanently `true` if the `rlp_execute_callback` receipt fails, bricking the wallet forever - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (the eth-implicit account contract that lets Ethereum-signed transactions be relayed as NEAR actions) uses a boolean lock, `has_in_flight_tx`, to serialize execution: `rlp_execute` refuses to start a new transaction while a previous one is still in flight, and the lock is only cleared inside `#[private]` callback methods (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`) that run *after* the dispatched cross-contract promise resolves. This is structurally identical to the reported `frontrunLock` bug: a lock is set eagerly and is expected to be cleared by a subsequent asynchronous callback, but nothing guarantees that the callback actually completes successfully. [1](#0-0) 

### Finding Description
`rlp_execute` sets `has_in_flight_tx = true` before returning a `Promise`, and the invariant documented on the struct says the flag "must be `true` when a mutable method... returns a promise and `false` otherwise": [2](#0-1) 

The flag is only reset inside the `#[private]` callback that is chained via `.then(...)` onto the dispatched action promise, e.g. `rlp_execute_callback`: [3](#0-2) 

For the generic/default action path (arbitrary NEAR `FunctionCall`/`Transfer`/`AddKey`/`DeleteKey` actions decoded from the Ethereum transaction), the callback's static gas budget is a *fixed* constant, `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas), independent of how much data the called `target` contract might return: [4](#0-3) 

By contrast, the other two branches (`address_check_callback`, `nep_141_storage_balance_callback`) explicitly widen the callback gas budget with `.saturating_add(action.gas())`, showing the authors were aware that callback gas needs can scale with the inner action — but this compensation is missing for the generic `FunctionCall` path: [5](#0-4) [6](#0-5) 

On NEAR, a function-call receipt's storage writes are only committed to the trie if the receipt finishes execution successfully; if the WASM execution traps (e.g., out-of-gas while reading a large `PromiseResult` payload via `env::promise_result(0)`), **all** state mutations performed during that receipt — including the `self.has_in_flight_tx = false;` write at the top of `rlp_execute_callback` — are discarded, and the callback's `ExecutionOutcome` is recorded as failed. Because `target` is an attacker-influenceable/arbitrary account (derived from the Ethereum transaction's `to` field/action), a malicious or colluding target contract can be crafted to return an oversized `success_value` from its `FunctionCall`, causing the retrieval/return of that payload inside `rlp_execute_callback` to exceed the fixed 5 Tgas budget. The callback then fails entirely (out of gas) before its state changes commit, leaving `has_in_flight_tx` stuck at `true` in the persisted contract state forever, exactly mirroring the "the callback never completes, so the lock never clears" root cause in the LooksRare `frontrunLock` report.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, `rlp_execute` unconditionally short-circuits every future call with "transaction already in progress": [7](#0-6) 

This permanently disables the wallet contract for its owner — no further Ethereum-emulated transactions (transfers, function calls, access-key management) can ever be relayed through it again. Because the wallet contract holds/controls the account's funds and access keys, this is a permanent freeze of the account's ability to move funds or manage keys — a concrete, unauthorized-value-movement-adjacent, "permanently frozen funds" outcome triggered entirely by a single transaction routed through the wallet contract by an unprivileged relayer/user.

### Likelihood Explanation
The trigger is reachable by any account that can submit an RLP-encoded transaction to `rlp_execute` targeting an account under attacker control (or a contract the attacker can influence to return large data), which is the normal, permissionless entry point of the wallet contract. No validator/node privilege or malicious peer is required — only crafting a `target` contract whose method returns an oversized value under the generic action path, which uses only the fixed `RLP_EXECUTE_CALLBACK_GAS` budget rather than a size-scaled one. This makes the likelihood non-trivial, though the exact gas parameters (per-byte cost of reading a promise result vs. the max allowed return payload size) determine whether 5 Tgas is provably insufficient in the worst case; that precise gas-cost arithmetic was not independently confirmed against the runtime's parameter tables in this analysis.

### Recommendation
- Ensure the callback gas budget for the generic/default action branch also accounts for the worst-case size of data the target contract could return (mirror the `.saturating_add(action.gas())` pattern used in the other two branches, or scale by the maximum receipt/return-value size), so the callback cannot run out of gas while reading `promise_result`.
- Add a recovery mechanism (e.g., a way to reset `has_in_flight_tx` if the associated promise/receipt is provably no longer pending, or a timeout-based unlock similar to NEAR's own `PromiseYieldTimeout` mechanism used elsewhere in the protocol) so a failed/under-funded callback cannot brick the wallet permanently.

### Proof of Concept
1. Deploy an attacker-controlled contract `evil.near` whose method, when called, is written to return the maximum-allowed data size in its `PromiseResult` (a large byte blob), while requiring minimal actual gas to execute itself.
2. Craft/sign an Ethereum transaction whose decoded NEAR action is a `FunctionCall` to `evil.near`'s method, with the `gas` field on the inner action left small (so the outer action succeeds cheaply) — the important constraint being that the callback's gas is the fixed `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas), not scaled to the return payload.
3. Submit this transaction to the wallet contract's `rlp_execute`. `has_in_flight_tx` is set to `true`, and `action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))` is scheduled with only `RLP_EXECUTE_CALLBACK_GAS` static gas.
4. When `evil.near`'s call succeeds and returns its oversized payload, `rlp_execute_callback` is invoked; reading/propagating that payload via `env::promise_result(0)` consumes gas beyond the allotted 5 Tgas, the callback receipt fails with `FunctionCallError::HostError(GasExceeded)` (or similar), and none of its state writes — including `self.has_in_flight_tx = false` — are committed.
5. Any subsequent call to `rlp_execute` now returns `"transaction already in progress"` forever, permanently freezing the wallet contract's ability to process transactions.

(Note: this analysis was unable to independently verify from the parameter YAML the exact per-byte gas cost for `promise_result`/register reads versus the maximum allowed return-value size, which would be needed to confirm the 5 Tgas budget is provably exceedable in the worst case; this should be validated numerically before treating the PoC as fully deterministic.)

    #[payable]
    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
