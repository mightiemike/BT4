No vulnerability found for this question.

**Reasoning:**

The exclusion is explicit, documented, and intentional legacy behavior, not a bug introduced by faulty accounting logic.

- `AbstractResourceWriteOp::is_aggregator_v1_delta()` is `true` only for the `AggregatorChangeV1::MaterializedDelta` case — i.e. an aggregator that already existed in storage *before* this transaction, was only touched via `add`/`sub` operations, and was never read or newly created in the transaction: `if is_write(&id) { AggregatorChangeV1::Write(value) } else { AggregatorChangeV1::MaterializedDelta(value) }` [1](#0-0) .
- The `AbstractResourceWriteOp::is_aggregator_v1_delta` doc comment states explicitly that this flag "keep[s] legacy (none) metadata" and is "excluded from storage-fee charging and write-set size/count accounting... For compatibility, this behavior is maintained," confirming this is deliberate, long-standing legacy semantics rather than an accidental omission [2](#0-1) .
- `VMChangeSet::num_write_ops` and `write_set_size_iter` filter out entries where `is_aggregator_v1_delta()` is true, and the code comments reiterate "Legacy aggregator V1 deltas excluded. They were never part of the write set iterator" [3](#0-2) .
- `UserSessionChangeSet::num_write_ops`/`write_set_size_iter` simply delegate to the underlying `VMChangeSet`/`ModuleWriteSet` implementations, so the exclusion flows through unchanged into `check_change_set` [4](#0-3) , and `check_change_set` enforces `max_write_ops_per_transaction`/`max_bytes_all_write_ops_per_transaction` strictly over what `write_set_size_iter`/`num_write_ops` report [5](#0-4) .

This matches Aptos's historical (pre-refactor) aggregator V1 design, where delta-only writes were tracked and merged separately from the regular write set and were never subject to the write-op count/size caps — gas for the add/sub itself is charged at the native-call level during execution, independent of the final write materialization, so this exclusion does not let an attacker get "free" or uncapped writes beyond what the transaction's gas budget already bounds. The final committed value is still correctly materialized and written to storage; only the legacy accounting bucket differs, which is consistent with mainnet's existing, intended behavior rather than a newly introduced state-corrupting bug. Since the review standard requires unprivileged input to corrupt committed state, proof material, or bindings — and here the write set that is actually committed is correct and deterministic, just categorized per long-documented legacy rules — this does not meet the bar for a valid finding.
