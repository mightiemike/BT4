### Title
`TransactionOutput::ensure_match_transaction_info` never validates `state_checkpoint_hash` (or hot-state/position-state checkpoint hashes), letting replay-verify accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the authenticated-invariant check used by offline replay/verification tooling to confirm that freshly re-executed transaction results match the `TransactionInfo` that is bound into the transaction accumulator (and thus committed on mainnet). The function checks `status`, `gas_used`, the write-set hash, and the event-root hash, but it never compares the recomputed `state_checkpoint_hash` (nor `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the expected `TransactionInfo`. The code even documents this gap in a `TODO(trading-native)` comment, but the comment understates the scope: the base `state_checkpoint_hash` field — the field bound to the actual state Merkle root — is skipped unconditionally, not only the new trading-native fields. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` is defined on `TransactionOutput` and is the sole comparator used by both `db-tool`'s `replay_on_archive` (mainnet archive replay-verification) and the CLI diff tooling, to assert that a freshly executed `TransactionOutput` matches an authoritative, already-committed `TransactionInfo`. [2](#0-1) 

The function's checks are limited to:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (`CryptoHash::hash(self.write_set())`) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()` [3](#0-2) 

It never reads or compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` against any locally recomputed state root. The developers' own comment confirms the gap exists and is currently unaddressed: [4](#0-3) 

This function is invoked directly by `replay_on_archive.rs`'s `execute_and_verify`, which re-executes historical transactions from an on-disk/backup archive with `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` as the pass/fail gate for the whole verification run: [5](#0-4) 

The state-checkpoint hash is exactly the authenticated commitment to the resulting Jellyfish Merkle / state-summary root produced during `DoStateCheckpoint::run`, and is what downstream consumers (light clients, state-sync bootstrap, backup/restore proofs) rely on as the binding proof of ledger state at a version: [6](#0-5) 

Because `ensure_match_transaction_info` never checks this field, any local divergence between the archived/authoritative state root and a freshly recomputed one (e.g., from a state-application bug, a JMT computation regression, an incorrect write-set replay, or a hard-fork-only behavior change) is silently invisible to this verifier. The replay tool will report "verification passed" purely because the write-set bytes, events, gas, and status matched, even though the resulting state commitment is wrong.

### Impact Explanation
This breaks the state/proof-integrity invariant that "committed state must differ, and any divergence must be provably detected during replay/verification" required by the State-Integrity Gate. `replay_on_archive` and the CLI diff commands are the primary automated tools operators and auditors use to assert that a node/archive's historical execution matches consensus-committed results. A silent skip of the state-root comparison means:
- A subtle state-application or JMT-root computation bug (hard-fork-only divergence) would not be caught by replay-verify, even though write sets and events match.
- Confidence in "verified" archives/backups derived from this tool is misplaced: an authenticated state-commitment field is effectively unauthenticated in this code path.
- This is precisely the category of impact the gate calls out: "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong accumulator root ... accepted as valid" — here, the state-checkpoint root can be wrong yet accepted as valid because it is simply not compared.

The severity is High: it does not corrupt live mainnet consensus state by itself, but it removes a critical safety net that is depended upon to detect state divergence bugs before they cause real consensus/hard-fork problems, and it does so silently (no error, no warning) for every replay-verify invocation and CLI diff invocation.

### Likelihood Explanation
This is not a probabilistic bug — it fires deterministically on every call to `ensure_match_transaction_info`, in every replay-verify run over any archived version range, and in the CLI's diff subcommands. It requires no adversarial or privileged behavior; any underlying state-computation defect (regardless of cause) is guaranteed to bypass this check, because the state-checkpoint fields are structurally absent from the comparison, not merely tolerant of small deviations.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash` (and, when applicable/available, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) against the corresponding fields on the expected `TransactionInfo`, failing verification (as the write-set/event checks already do) on any mismatch. Until this is done, `replay_on_archive` and CLI diff tooling should not be treated as validating full state-commitment integrity, and this limitation should be explicitly surfaced to operators (e.g., via a warning at tool startup) rather than only documented in a source comment.

### Proof of Concept
Conceptual PoC (cannot be executed without a live archive/environment):
1. Take any historical version range with a state checkpoint transaction.
2. Introduce (or naturally hit) a bug that alters the computed state Merkle root at that version while leaving the write set, events, gas, and status of the transaction itself unchanged (e.g., a bug in `ProvableStateSummary::update`/`LedgerStateSummary::update` root aggregation, unrelated to per-key write-op hashing).
3. Run `storage/db-tool/src/replay_on_archive.rs`'s verify path (`execute_and_verify` → `ensure_match_transaction_info`) over that range.
4. Observe that verification reports success despite the state_checkpoint_hash being wrong, because lines 2159–2196 of `types/src/transaction/mod.rs` never assert on `txn_info.state_checkpoint_hash()`. [1](#0-0) [7](#0-6)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
