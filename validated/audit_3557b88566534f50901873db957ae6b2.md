### Title
Panic (DoS) in Solana `DecodeDestExecDataToMap` from malformed `TokenAmounts.DestExecData` propagates through `decodeExecDataSui` - ([File: core/capabilities/ccip/ccipsolana/extradatacodec.go])

### Summary
`decodeExecDataSui` in `core/capabilities/ccip/ocrimpls/sui_contract_transmitter.go` calls `codec.DecodeTokenAmountDestExecData` for every token amount in the (attacker-influenced) execute report message, without any length/format pre-validation of `DestExecData`. When the source-chain family resolves to the Solana codec, `ccipsolana.ExtraDataDecoder.DecodeDestExecDataToMap` calls `binary.BigEndian.Uint32(destExecData)` directly with no length check, which panics with an index-out-of-range error if `destExecData` is fewer than 4 bytes.

### Finding Description
`decodeExecDataSui` iterates `message.TokenAmounts` and calls: [1](#0-0) 
for each token amount, passing `tokenAmount.DestExecData` and the source chain selector straight into `codec.DecodeTokenAmountDestExecData`. This dispatches (via `ExtraDataCodecRegistry`/`ExtraDataCodecMap`, keyed by source chain family) to a per-family `SourceChainExtraDataCodec` implementation: [2](#0-1) 

For a Solana-family source chain, the implementation is: [3](#0-2) 
`binary.BigEndian.Uint32` reads bytes `[0:4]` from the slice with no bounds check beforehand. Unlike the Aptos decoder, which explicitly checks `des.Remaining() != 4` before reading, or the EVM decoder, which uses `abiDecodeUint32` (ABI-decode, which errors gracefully on malformed input), the Solana `DecodeDestExecDataToMap` has no length guard at all. If an attacker-crafted CCIP message (e.g., from a malicious/compromised token pool or crafted message on the Solana source chain) sets `TokenAmounts[i].DestExecData` to fewer than 4 bytes, this call panics instead of returning an error.

Because `decodeExecDataSui` and its caller `SuiExecCallDataFunc` do not recover from panics, and this is invoked from the OCR3 transmit path (`ccipTransmitter.Transmit` → `toEd25519CalldataFn` → `decodeExecDataSui`), the panic propagates up through the transmitter goroutine. Reasoning by the "invariant" stated in the prompt — chain-specific validation must reject malformed data rather than propagate it — this codec fails that invariant for Solana-sourced dest exec data.

### Impact Explanation
A crafted/malformed `DestExecData` (under 4 bytes) reaching a Sui offramp execute-report pipeline whose source chain family resolves to Solana will cause an unrecovered panic in the node's OCR3 transmit goroutine, rather than a rejected/errored decode. This is a denial-of-service on the CCIP execute plugin transmission path for the affected chain lane — it can prevent execution of the given report (and potentially any subsequent OCR round using the same code path) until the node process crashes/restarts or the report is dropped, which is a real availability/integrity risk for CCIP execution completion, matching a "misreporting/execution DoS" bounty category. It does not itself cause unauthorized fund movement, since the panic aborts before `SubmitTransaction` is reached — so the "attacker-controlled map is embedded and submitted unchecked" part of the audited question does not hold for Solana; the actual observed defect is a crash/DoS, not silent corruption reaching `SubmitTransaction`.

### Likelihood Explanation
The precondition matches the prompt: an unprivileged party can craft a message on the source chain (e.g., via a malicious/compromised token pool implementation controlling `destExecData` encoding, or a permissionless message with attacker-chosen extra data fields depending on how strictly upstream/onchain validation constrains `DestExecData` length) that includes a `TokenAmounts[].DestExecData` under 4 bytes. Reaching the OCR3 execute report pipeline for CCIP requires this message to be committed and included in an execute report by the CCIP offchain plugin, which does not appear (from the reviewed code) to pre-validate `DestExecData` length against the expected 4-byte format before it reaches `decodeExecDataSui`. This makes the bug reachable through the normal onramp → commit → execute plugin path, without any node-operator or key-compromise privilege.

### Recommendation
Add an explicit length check in `ccipsolana.ExtraDataDecoder.DecodeDestExecDataToMap` before calling `binary.BigEndian.Uint32`, mirroring the Aptos decoder's `des.Remaining() != 4` check, e.g.:
```go
if len(destExecData) != 4 {
    return nil, fmt.Errorf("dest exec data invalid length: %d, should be 4 bytes", len(destExecData))
}
```
Additionally, consider wrapping calls to third-party/codec decode functions in the OCR3 transmit path (`decodeExecDataSui`, `SuiExecCallDataFunc`) with panic recovery so that any similar defensive gaps in other chain-family codecs degrade to an error rather than crashing the transmitter goroutine/node.

### Proof of Concept
Unit/fuzz test target: `ccipsolana.ExtraDataDecoder.DecodeDestExecDataToMap` and integration through `decodeExecDataSui`.

1. Unit test:
```go
func TestDecodeDestExecDataToMap_ShortInput_ShouldNotPanic(t *testing.T) {
    d := ccipsolana.ExtraDataDecoder{}
    require.NotPanics(t, func() {
        _, err := d.DecodeDestExecDataToMap([]byte{0x01, 0x02}) // < 4 bytes
        require.Error(t, err)
    })
}
```
Current behavior: this panics with "runtime error: index out of range" inside `binary.BigEndian.Uint32`.

2. Fuzz test:
```go
func FuzzDecodeDestExecDataToMap(f *testing.F) {
    f.Add([]byte{})
    f.Add([]byte{0x01})
    f.Fuzz(func(t *testing.T, data []byte) {
        d := ccipsolana.ExtraDataDecoder{}
        defer func() {
            if r := recover(); r != nil {
                t.Fatalf("panic on input %x: %v", data, r)
            }
        }()
        _, _ = d.DecodeDestExecDataToMap(data)
    })
}
```
Expected assertion: no panic for any input length; short/malformed input should return a non-nil error.

	destExecData cciptypes.Bytes,
	sourceChainSelector cciptypes.ChainSelector,
