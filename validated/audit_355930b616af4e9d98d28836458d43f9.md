### Title
Stale contract-class cache can serve an undeclared V0 class, causing execution divergence between sequencer nodes - (File: crates/blockifier/src/state/state_reader_and_contract_manager.rs)

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` re-validates that a *Cairo1* class returned from the global `ContractClassManager` cache is actually declared in the canonical state before trusting the cache hit, explicitly because the cache "might contain a declared class from a reverted block." The same re-validation is **not** performed for Cairo0 (`RunnableCompiledClass::V0`) classes, even though the cache is shared across block-building attempts (including discarded/reverted proposals) and across view calls, exactly mirroring the Balancer report's pattern of trusting a cached value that can silently diverge from ground truth.

### Finding Description
`ContractClassManager` (`crates/blockifier/src/state/contract_class_manager.rs`, `native_class_manager.rs`) wraps a `GlobalContractCache` that is created once per batcher process and shared by both block production and view calls (`crates/apollo_batcher/src/batcher.rs:1747-1761`: "Block production and view calls share one class cache"). It is also reused across separate proposal-building attempts within the batcher's block builder.

In `get_compiled_from_class_manager`: [1](#0-0) 

the code explicitly acknowledges that a cache hit does not guarantee the class is declared in the authoritative state (`self.state_reader.is_declared`) because the entry could have been populated while executing a proposal/block that was later reverted or discarded, and only re-checks this for the non-`V0` (Cairo1) branch. For `RunnableCompiledClass::V0(_)`, the function returns the cached class immediately with no re-validation against `is_declared`.

This is structurally identical to the Balancer bug: a value (pool tokens / "is this class declared") that can legitimately change or never have been finalized is cached once, and later code paths trust the cache without re-verifying against current canonical state — except here the omission is asymmetric (V1 is protected, V0 is not), which is itself evidence this is an accidental gap rather than a deliberate design choice.

Populating the cache with a class that ends up not being declared is reachable from an ordinary flow: the block builder executes transactions (including `Declare` transactions for V0 classes) speculatively while building a proposal; `set_and_compile` is called as soon as the class is fetched/compiled, before the proposal is known to be accepted by consensus. If that proposal round is aborted/rejected (e.g., a competing proposal wins, or the round times out) the class hash remains warm in the shared `ContractClassManager` even though it was never actually declared in committed state. A subsequent transaction (submitted by any unprivileged account) referencing that same V0 class hash (e.g., via `deploy_syscall`) will then hit the warm cache and successfully retrieve a "declared" V0 class from `get_compiled_from_class_manager`, bypassing the `is_declared` check that `CachedState`/the base state reader would otherwise enforce.

### Impact Explanation
If a node with the stale cache entry executes a transaction (e.g., a deploy of a contract with an undeclared V0 class hash) successfully while another honest node — one that never cached that speculative class, or whose cache was evicted/cleared — rejects the same transaction with `StateError::UndeclaredClassHash`, the two nodes compute different transaction outcomes and therefore different state diffs/roots for the same block. This is a state-root / block-hash divergence between honest nodes, which is a Medium/High-severity correctness bug for a sequencer (the class of impact explicitly listed as acceptable: "honest-node divergence" / "wrong committed root or block hash").

### Likelihood Explanation
Likelihood is moderate: it requires (1) a Cairo0 declare to be executed once during proposal building without the proposal being finalized (a normal occurrence under contention/timeouts in consensus), and (2) a follow-up transaction referencing the same class hash before the cache entry is evicted (cache is LRU with a configurable but often large size, and persists across proposal rounds and view calls for the lifetime of the process). No privileged access is needed — only ordinary `Declare`/`Invoke`/`deploy_syscall` transactions from a standard account are involved.

### Recommendation
Apply the same `is_declared` re-validation currently done for the `RunnableCompiledClass::V1`/native branch to the `RunnableCompiledClass::V0` branch in `get_compiled_from_class_manager`, so that every cache hit — regardless of Cairo version — is confirmed against the canonical `state_reader.is_declared` before being trusted, or clear/scope the `ContractClassManager` cache per block-building attempt so entries from discarded proposals cannot leak into subsequent execution.

### Proof of Concept
1. Batcher begins building proposal A; it includes a `Declare` transaction for a Cairo0 class `C` with hash `h`. During speculative execution, `contract_class_manager.set_and_compile(h, ...)` caches `C`.
2. Proposal A is discarded (e.g., consensus round change) before being committed; class `h` was never actually recorded as declared in canonical/committed state.
3. A different (or the same) account later submits an `Invoke` transaction that calls `deploy_syscall` with `class_hash = h` (without ever having a successful, committed `Declare` for `h`).
4. On the node whose shared `ContractClassManager` still has `h` cached from step 1, `get_compiled_from_class_manager` hits the cache, takes the `RunnableCompiledClass::V0(_) => {}` branch (no `is_declared` check), and returns the class successfully — the deploy succeeds and is included in the block's state diff.
5. On a node without that stale cache entry (e.g., fresh process, evicted entry, or independent validating node), the same call goes to `state_reader.get_compiled_classes(h)`, which fails with `UndeclaredClassHash`, and the transaction reverts/fails differently.
6. The two nodes now disagree on the resulting state diff/root for the block containing this transaction.

    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }
