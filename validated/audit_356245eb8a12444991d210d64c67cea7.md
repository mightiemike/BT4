### Title
Governance-toggled dual exchange-calculation path allows an `ExchangeTransactionContract` to silently bypass Manager-level exchange-transaction handling - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
The fork introduces a "hardened" bancor-style exchange calculation path (`SafeExchangeProcessor`, BigDecimal-based) alongside the legacy `ExchangeProcessor` (double-based), selected at runtime by the `AllowHardenExchangeCalculation` dynamic parameter via `allowHarden()` [1](#0-0) . `Manager` contains a helper `isExchangeTransaction(Transaction)` whose result flips depending on this same flag: with hardening disabled it correctly classifies an `ExchangeTransactionContract` as an exchange transaction, but with hardening enabled it returns `false` for the identical transaction, as demonstrated by the fork's own test [2](#0-1) .

### Finding Description
This mirrors the Tigris `addToPosition()` bug class: a security-relevant classification/limit is enforced correctly on one code path but is silently skipped on an alternate, attacker-reachable path. In Tigris, closing normally enforced the +500% PnL cap while `addToPosition()` did not; here, whatever logic in `Manager` gates on `isExchangeTransaction(...)` is only applied when `AllowHardenExchangeCalculation == 0`. Once the chain (via proposal) enables hardening — or if it is left enabled — `isExchangeTransaction` returns `false` for genuine `ExchangeTransactionContract` transactions [3](#0-2) , meaning any special handling keyed on that classification (e.g., transaction-type–specific validation, accounting, or bookkeeping performed elsewhere in `Manager`) is bypassed for exchange trades executed through `ExchangeTransactionActuator`/`ExchangeCapsule.transaction(...)` [4](#0-3) [5](#0-4) .

**Verification gap:** I could not retrieve the actual method body of `isExchangeTransaction` in `Manager.java` in this session (only the package declaration line was returned), so I cannot cite the exact downstream logic that is skipped when the flag flips. This is the same class of "alternate path skips an enforced check" as the reference report, but I cannot prove the concrete asset/consensus impact without seeing what `isExchangeTransaction`'s caller actually gates.

### Impact Explanation
If `isExchangeTransaction` gates something like per-transaction-type re-validation, replay/duplicate protection, or resource/fee accounting specific to exchange trades, then enabling hardened calculation (a chain-wide governance parameter, not privileged per-user) would cause every `ExchangeTransactionContract` broadcast by any anonymous account to skip that logic — a systemic, non-privileged bypass matching the "cap enforced on one path but not another" pattern from the reference report. Given the uncertainty above, I cannot assert a specific asset-corruption or consensus-divergence outcome with the same confidence as the confirmed code paths.

### Likelihood Explanation
`AllowHardenExchangeCalculation` is read directly from `DynamicPropertiesStore` and consulted on every `ExchangeTransactionActuator.execute`/`validate` call [6](#0-5) , so once the flag is set to `1` (via a passed proposal, per `ProposalUtil`/`ProposalService` references found alongside this flag), the bypass is triggered on every single ordinary, anonymous `ExchangeTransactionContract` broadcast — no privileged actor or race condition is required.

### Recommendation
Manually inspect `Manager.java`'s `isExchangeTransaction` and its call site(s) to confirm what check/accounting step is conditioned on it, and ensure that step is applied consistently regardless of `AllowHardenExchangeCalculation`. If it protects against a cap, replay, or accounting invariant, that invariant should be enforced unconditionally rather than being tied to the calculation-mode flag — analogous to Tigris's fix of enforcing the max-PnL check identically on `addToPosition`, `addMargin`, and normal close paths.

            Transaction.Contract.newBuilder()

    java.lang.reflect.Method m = Manager.class.getDeclaredMethod(
        "isExchangeTransaction", Transaction.class);
    m.setAccessible(true);

    // Default: hardened disabled (==0) -> contract is treated as exchange
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
    Assert.assertTrue("Exchange tx must be detected when hardened disabled",
        (boolean) m.invoke(dbManager, exchange));

    // Hardened enabled -> bypass returns false
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);
    Assert.assertFalse("Exchange tx must be bypassed when hardened enabled",
        (boolean) m.invoke(dbManager, exchange));

    // Reset
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
  }

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
