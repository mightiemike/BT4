### Title
Starknet OS `replace_class` syscall omits declared-class validation, causing state/root divergence from Blockifier - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
An unprivileged account can call `replace_class_syscall` with an arbitrary, undeclared `class_hash`. The Blockifier (execution engine that actually builds/commits blocks) rejects this by fetching the compiled class and reverting the transaction if it is not declared. The Starknet OS Cairo program, which re-executes transactions to produce the block's proof/commitment, has this validation explicitly missing (marked with a `TODO`), and unconditionally writes the new (possibly undeclared) `class_hash` into `contract_state_changes`.

### Finding Description
In the Blockifier, `replace_class` first ensures the class is declared before mutating state: [1](#0-0) 
This is verified by a test that asserts an undeclared class hash causes an `"is not declared"` error and the class hash is *not* replaced: [2](#0-1) 

In the Starknet OS's Cairo re-implementation of the same syscall, the equivalent check is missing — explicitly called out by a `TODO` comment — and the function proceeds to unconditionally update the contract's `class_hash` in `contract_state_changes`: [3](#0-2) 

The same gap exists in the deprecated (Cairo0) syscall path: [4](#0-3) 

This is directly analogous to the reported bug class: an ID (here, `class_hash`, analogous to `proposalId`) that references an entity which may not exist is not validated before a state mutation is performed and committed, even though the "correct"/reference implementation (Blockifier here, the smart-contract's own state elsewhere) would have rejected/reverted the action.

### Impact Explanation
The Starknet OS is responsible for re-executing every transaction in a block to derive the state diff that is committed to the Patricia tries and ultimately the block's state root/hash, and it is also the program executed by provers to attest block correctness. If a transaction invokes `replace_class_syscall` with an undeclared class hash:
- The Blockifier (used by the sequencer while building the block) will revert the `__execute__` call for that undeclared class hash, producing one set of side effects (only fee charged, no class hash change, and a revert flag).
- The Starknet OS, when re-executing the same call to build/verify the state diff and prove the block, will *not* revert on this condition and will happily write the new (undeclared) class hash into `contract_state_changes`, producing a different state diff for that contract than the Blockifier produced.

This is a **root cause of honest-node/state divergence**: the sequencer's committed state (from the Blockifier) and the state re-derived/proved by the OS disagree on this contract's class hash after the transaction. Depending on how strictly the OS's re-derived control flow is cross-checked against the sequencer's hinted outcome, this can lead to an incorrect state root/commitment being proven as valid, or to the network being unable to reach consensus on the correct state, satisfying the "wrong committed root or block hash, honest-node divergence" impact criterion.

### Likelihood Explanation
Triggering the divergent path requires nothing more than an ordinary account contract that calls `replace_class_syscall` (a standard, unprivileged Starknet syscall available to any Cairo contract) with a `class_hash` value that has never been declared. This requires no special privileges, no protocol-level trust, and can be done by any user submitting a normal transaction with such a contract.

### Recommendation
Implement the same "class must be declared" check in the Starknet OS's `execute_replace_class` (and its deprecated counterpart in `deprecated_execute_syscalls.cairo`) that the Blockifier already performs, i.e., read/verify the compiled class for `class_hash` via `contract_class_changes`/declared-classes dictionary before performing the `dict_update` on `contract_state_changes`, and fail/revert consistently with the Blockifier's behavior if the class is not declared. This resolves the `TODO(Yoni, 1/1/2026)` and eliminates the execution divergence.

### Proof of Concept
1. Deploy any Cairo1 contract that calls `replace_class_syscall(class_hash)` on external invocation (e.g., the existing test helper `test_replace_class`, see [5](#0-4) ).
2. Submit an invoke transaction calling this entry point with `class_hash` set to an arbitrary value that has never been declared on-chain (e.g., `felt!(1234)`), analogous to the `undeclared_class_hash` Blockifier test scenario at [2](#0-1) .
3. The Blockifier reverts the `__execute__` call (per the cited test), so the sequencer's block includes the transaction as reverted, with no class hash change for the contract, only fee deduction.
4. When the Starknet OS re-executes the same transaction (e.g., during proving/re-execution verification), `execute_replace_class` in `syscall_impls.cairo` skips the declared-class check (per the cited `TODO`) and unconditionally updates `contract_state_changes` with the undeclared class hash — producing a state diff for the contract that differs from what the Blockifier actually committed, demonstrating the divergence.
