### Title
DoS: Attacker May Front-Run `AssetIssueContract` (Create Token) With The Same Asset `Name` Causing The Victim's Transaction To Revert - (`actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java`)

### Summary
When `AllowSameTokenName` is disabled (`getAllowSameTokenName() == 0`), `AssetIssueActuator.validate()` rejects any `AssetIssueContract` (token creation) transaction whose `name` field already exists in the `AssetIssueStore`. Because the asset name is a global, first-come-first-served unique key checked purely against on-chain state at validation time, an attacker observing a pending `AssetIssueContract` transaction in the mempool can broadcast a competing transaction with the same `name` and a higher fee/priority so it gets included first, causing the victim's original transaction to fail validation and revert with `"Token exists"`. This mirrors the Joyn `createSplit()` `merkleRoot`-as-salt front-running issue, where a public, attacker-observable, single-use identifier is used as an exclusivity key.

### Finding Description
In `AssetIssueActuator.validate()`: [1](#0-0) 
the uniqueness check `assetIssueStore.get(assetIssueContract.getName().toByteArray()) != null` is performed against the asset `name` supplied by the transaction itself. This `name` is visible in the broadcast transaction/mempool before it is confirmed on-chain, just like the `merkleRoot` in the original report is visible in the mem pool before `createSplit()` is mined.

An attacker can:
1. Observe a pending `AssetIssueContract` transaction with a desired `name` from a legitimate user.
2. Broadcast their own `AssetIssueContract` transaction using the identical `name` (with different `ownerAddress`, `totalSupply`, etc.) and a higher energy fee / faster propagation so it is packed into a block first.
3. Because `assetIssueStore` is keyed by `name` under legacy (`AllowSameTokenName == 0`) semantics, the attacker's transaction succeeds and stores the name first, as seen in `execute()`: [2](#0-1) 
4. The victim's original transaction then fails the `"Token exists"` check and reverts.

This is functionally analogous to the reported bug class: a publicly-visible, attacker-front-runnable value (`name` here, `merkleRoot` in Joyn) is used as the sole exclusivity/identity key for a one-time creation operation, allowing an attacker to squat on it and force the legitimate creator's transaction to permanently fail for that value, forcing them to retry with a different value with no guarantee against repeated front-running.

### Impact Explanation
A victim attempting to issue a token under a specific, meaningful name (e.g. a brand name) can be repeatedly denied service: every time they broadcast their `AssetIssueContract` transaction, an attacker can front-run it with the same name, consuming that unique identifier and forcing the victim's transaction to revert. This is a availability/DoS impact on the `CreateAssetIssue` transaction type and can also be leveraged for name-squatting/griefing against specific projects, since asset names are business-meaningful and non-fungible once claimed.

### Likelihood Explanation
Exploitability requires only the ability to observe a pending transaction (which is generally straightforward for any mempool-observing/full node participant) and to submit a competing broadcast transaction — no privileged role, leaked key, or malicious peer/node behavior is needed. However, this legacy uniqueness check only applies when `AllowSameTokenName == 0`; on networks/chains where this dynamic parameter has been switched to `1` (as on current TRON mainnet), asset names are no longer required to be unique and this specific path is not exercised. The vulnerability is therefore latent but real in any deployment/private chain still operating with `AllowSameTokenName == 0`.

### Recommendation
- Do not rely on a user-supplied, mempool-visible field (`name`) as the sole exclusivity key for a one-shot resource claim under `AllowSameTokenName == 0` semantics.
- Consider binding the uniqueness key to the transaction sender (e.g., include `ownerAddress` in the uniqueness check/key), or require a commit-reveal scheme so the desired `name` is not revealed before the claiming transaction is finalized.
- If the legacy `AllowSameTokenName == 0` mode is deprecated/unused on mainnet, ensure this code path cannot be re-enabled without addressing the front-running weakness.

### Proof of Concept
1. Ensure `AllowSameTokenName == 0` (legacy mode).
2. Victim broadcasts `AssetIssueContract` transaction A with `name = "BRAND"`.
3. Attacker observes transaction A in the mempool and broadcasts `AssetIssueContract` transaction B with the same `name = "BRAND"` and a higher fee/priority.
4. Transaction B is processed first; `AssetIssueActuator.execute()` stores the asset under key `"BRAND"`: [2](#0-1) 
5. Transaction A is then processed and fails `validate()` with `"Token exists"`: [1](#0-0) 
6. The victim's original intended asset name is now permanently unavailable to them, and the attack can be repeated for any subsequent name they choose.
