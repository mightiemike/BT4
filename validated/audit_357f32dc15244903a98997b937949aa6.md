**Analysis:** `authenticateFlowFactory` in `packages/apps/shopify-app-remix/src/server/authenticate/flow/authenticate.ts` validates the HMAC signature via `api.flow.validate` and looks up the offline session, then returns a `FlowContext` to the app's route handler [1](#0-0) . It does not itself execute any business-logic side effects — it authenticates the request and hands control back to the host app's action handler.

Delivery-id (webhook/event ID) deduplication is explicitly documented as the *app developer's* responsibility, not something the library performs. The `webhookId` field is documented as "the idempotency key — useful to keep track of which events your app has already processed" [2](#0-1) , and the same pattern applies to Flow/events deliveries. Enforcing at-most-once processing requires persistent, app-specific state (e.g., a database of processed IDs) that a stateless authentication library cannot own — the library's job ends at cryptographic verification of the request's authenticity, which it does correctly.

Since replay-detection/idempotency is a host-app responsibility by design (and documented as such), and not a flaw in the library's authentication logic, this does not meet the bar of "a bug in this library" per the rules (which explicitly reject issues that are "a bug in the host app rather than in this library" or "best-practice cleanup without exploitable impact").
