### Title
Un-timeweighted reward snapshot in `calculate-rewards` lets a staker join immediately before distribution and claim a full period's yield - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`calculate-rewards` in the PoX-5 signer/staking contract distributes the whole half-cycle's freshly-accrued sBTC rewards (`gross-accrued-rewards`) proportionally to whatever `cycle-staked-ustx` (the *current* `get-total-shares-staked-for-cycle`) is at the moment the function is called, rather than to a time-weighted stake held throughout the period. This mirrors the reported MakerDAO bug class: reward accrual keyed off a discrete "drip" snapshot that does not require the beneficiary to have held the position for the period being compensated.

### Finding Description
`calculate-rewards` computes: [1](#0-0) 
using `cycle-staked-ustx` read live at call time, and updates the global `rewards-per-token-for-cycle` accumulator by `accrued-rewards-per-ustx = (stx-staker-rewards * PRECISION) / cycle-staked-ustx`: [2](#0-1) 

A staker's claimable amount is `earned = shares * (rpt - rptPaid) + pending`, and `rptPaid` is only updated by `settle-rewards`/`settle-staker-rewards`, which snapshot the staker's `rewards-per-token-settled` to whatever the *current* accumulator value is at the moment they register/change stake: [3](#0-2) [4](#0-3) 

When a new staker joins via `add-staker-to-signer-for-cycle`, their `staker-rewards-per-token-settled-for-cycle` is initialized to the *signer's current* `rewards-per-token-for-cycle` (pre-accrual value), and their `shares` are added into `total-shares-staked-for-cycle` immediately: [5](#0-4) 

Because the accumulator (`rpt`) only updates when `calculate-rewards` is invoked — an unprivileged, permissionless call gated only by "has a new half-cycle closed" and a reentrancy guard, not by a minimum holding duration — a staker who enters right before that call is included in `cycle-staked-ustx` used to compute the accrual for the *entire* elapsed half-cycle, exactly like a MakerDAO attacker joining the `pot` right before `drip()`.

### Impact Explanation
An attacker can (1) call `register-for-bond`/stake in the closing half-cycle, (2) immediately call the public, unprivileged `calculate-rewards`, capturing a full period's worth of `accrued-rewards-per-ustx` diluted only by their instantaneous share of `cycle-staked-ustx`, then (3) unstake and reclaim their principal. This siphons yield from other, genuinely time-committed stakers/signers — a reward mis-payment bounded to the fee/reward pool (sBTC yield), matching the "High - poison or reward mis-payment bounded to fees" category, and is triggerable by a single unprivileged actor.

### Likelihood Explanation
Likelihood depends on whether `register-for-bond`/`unstake-sbtc` impose a lockup or cooldown before shares are creditable/withdrawable, and whether `calculate-rewards`'s cadence (only once per half-cycle, gated by `calculation-height > last-calc`) can realistically be raced by an attacker's own stake+claim+unstake sequence within the same or an adjacent block. I could not confirm the presence/absence of a minimum lockup in `register-for-bond`/`unstake-sbtc` within the available context, so likelihood is uncertain without further code review.

### Recommendation
Require rewards to accrue based on a time-weighted stake (e.g., checkpointed balances across the accrual interval, or a minimum bonding duration before a staker's shares count toward `cycle-staked-ustx` in `calculate-rewards`), rather than a snapshot of instantaneous shares at the moment `calculate-rewards`/`drip`-equivalent is invoked.

### Proof of Concept
Conceptual (not executed): In the last block before a half-cycle's `calculate-rewards` becomes callable, attacker calls `register-for-bond`/stake STX to become a signer/staker for the closing cycle; attacker (or anyone) then calls `calculate-rewards`, which credits `rewards-per-token-for-cycle` based on the just-joined attacker's share of `cycle-staked-ustx`; attacker calls `claim-rewards` to withdraw sBTC, then unstakes — extracting yield for a period during which they held no real economic exposure. Verifying exact call ordering/lockup constraints requires deeper reading of `register-for-bond` and `unstake-sbtc`, which was not completed.

(define-private (settle-rewards
        (signer principal)
        (reward-cycle uint)
        (bond-index (optional uint))
    )
    (let (
            (shares (get-signer-shares-staked-for-cycle signer reward-cycle bond-index))
            (rewards-per-token (get-rewards-per-token-for-cycle reward-cycle bond-index))
            (earned (compute-earned-rewards
                shares
                rewards-per-token
                (get-signer-rewards-per-token-settled-for-cycle signer reward-cycle bond-index)
                (get-signer-unclaimed-rewards-for-cycle signer reward-cycle bond-index)
            ))
        )
        (map-set signer-unclaimed-rewards-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            earned
        )
        (map-set signer-rewards-per-token-settled-for-cycle {
            reward-cycle: reward-cycle,
            bond-index: bond-index,
            signer: signer,
        }
            rewards-per-token
        )
        (if (> shares u0)
            (map-set signer-rewards-per-token-for-cycle {
                signer: signer,
                reward-cycle: reward-cycle,
                bond-index: bond-index,
            }
                rewards-per-token
            )
            true
        )
        {
            earned: earned,
            rewards-per-token: rewards-per-token,
