### Title
Front-runnable asset-name squatting permanently blocks legitimate TRC10 token issuance - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
The `AssetIssueActuator` (handles `AssetIssueContract`, the transaction type used to create TRC10 tokens) enforces global uniqueness of the token `name` field by checking a shared key-value store before allowing creation, when `AllowSameTokenName` is disabled. Because the uniqueness check binds the caller-chosen `name` to whichever transaction is mined first, an unprivileged attacker can observe a pending legitimate issuance in the mempool and front-run it with an identical `name`, permanently denying the original issuer that name — the same "unique identifier bound to first-writer" bug class as the Folks Finance `accountId` DoS.

### Finding Description
`AssetIssueActuator.validate()` performs this check: [1](#0-0) 

If `dynamicStore.getAllowSameTokenName() == 0` and an entry already exists in `assetIssueStore` keyed by the raw `name` bytes, the transaction reverts with `"Token exists"`. The store write happens in `execute()`: [2](#0-1) 

The key used for `assetIssueStore` is derived directly from the user-supplied `name` (`assetIssueCapsule.createDbKey()`), exactly like the Folks Finance `accountId` being used verbatim as the `accounts` mapping key. Since `name` is chosen by the caller and there is no commit-reveal, escrow, or per-owner namespacing at this stage, any address can observe a pending `AssetIssueContract` transaction in the mempool, extract its `name`, and submit a competing `AssetIssueContract` with the same `name` and a higher fee/priority. If the attacker's transaction is included first, the store entry is claimed under the attacker's own asset/ID, and the legitimate user's transaction reverts with `"Token exists"` when it is later processed — the exact same front-running/first-writer race described in the external report.

This is confirmed as the intended, tested behavior: the regression test `IssueSameTokenNameAssert` demonstrates that a second `AssetIssueContract` with a name already present in `assetIssueStore` fails validation with `"Token exists"`, regardless of which account owns the existing entry: [3](#0-2) 

Additionally, `execute()` also enforces that each account may only issue one asset ever (`accountCapsule.setAssetIssuedName(...)`), verified by `assetIssueNameTest`: [4](#0-3) 

so the squatted asset name can never be reclaimed by the legitimate issuer through a retry with the same account, compounding the griefing effect — once squatted with `name = X`, no account can ever successfully issue a TRC10 token called `X` again while `AllowSameTokenName == 0`.

### Impact Explanation
This lets an unprivileged attacker permanently deny a specific token name to its intended issuer at the cost of only the network's `AssetIssueFee` (a fixed protocol fee, not "free" like the Folks Finance case, but still trivially affordable and requires no special privilege or technical sophistication). The impact is griefing/DoS on token-issuance functionality: legitimate projects can be blocked from issuing their intended TRC10 token name, and the namespace collision is irreversible under the `AllowSameTokenName == 0` mode because the store entry and the one-time-issuance flag on the attacker's account are both permanent.

The severity is bounded by the fact that `AllowSameTokenName` is a `DynamicPropertiesStore`-controlled chain parameter set via committee proposal; I was unable to determine from the indexed code whether this parameter is currently forced to `1` (same-name allowed, disabling the vulnerable branch) on the live java-tron mainnet/testnet used in this repo's default configuration — the search for its default value in `DynamicPropertiesStore.java` did not return results within the indexed content. If `AllowSameTokenName` is `0` (or can be set to `0`) on any reachable network, the vulnerable code path is live and exploitable exactly as described.

### Likelihood Explanation
Exploitation only requires mempool observation and submission of a competing transaction with a higher fee/energy or faster propagation — a standard front-running technique with no special access requirements, mirroring the attacker capability assumed in the original report. The only cost is the standard `AssetIssueFee`, making the attack cheap and repeatable against any pending `AssetIssueContract` transaction.

### Recommendation
Introduce a commit-reveal scheme for asset-name reservation, or bind name reservation to the submitting account at proposal time with a cooling-off period, so that observing a pending transaction's `name` in the mempool does not allow immediate front-running. Alternatively, since the same-token-name-required mode (`AllowSameTokenName == 0`) is a legacy compatibility path, consider deprecating/disabling it entirely in favor of the `AllowSameTokenName == 1` mode where uniqueness is enforced by internally generated `id` rather than user-chosen `name`, eliminating the front-runnable shared key.

### Proof of Concept
1. Set `AllowSameTokenName = 0` (legacy mode).
2. Legitimate user A broadcasts `AssetIssueContract` with `name = "MYTOKEN"`.
3. Attacker observes A's pending transaction in the mempool, extracts `name = "MYTOKEN"`, and broadcasts their own `AssetIssueContract` with the same `name`, using a higher fee to get mined first.
4. Attacker's transaction succeeds; `assetIssueStore` now maps `"MYTOKEN"` to the attacker's `AssetIssueCapsule`, as verified by `SameTokenNameCloseAssetIssueSuccess`: [5](#0-4) 
5. A's transaction is then processed and reverts with `ContractValidateException("Token exists")` per the check at lines 210-214, exactly reproducing the `IssueSameTokenNameAssert` failure path: [6](#0-5) 
6. A can never issue a TRC10 token named `"MYTOKEN"` again, and (per the one-asset-per-account rule) cannot retry issuance under the same account for any name once this attempt is committed/rejected in a way that consumes their one-time issuance slot, depending on transaction ordering.
