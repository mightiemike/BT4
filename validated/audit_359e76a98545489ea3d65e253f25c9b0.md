### Title
`ensure_match_transaction_info` Silently Skips State-Checkpoint Root Comparison, Letting `replay-verify` Accept a Diverged State Root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-comparison routine used by the `db-tool replay_on_archive` verifier to confirm that a freshly re-executed transaction matches the archived, LedgerInfo-proven `TransactionInfo`. It checks status, gas used, write-set hash, and event-root hash, but the code explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that authenticate the Merkle root of world state. This mirrors the reported bug class: an invariant/equality check that is supposed to bind two representations of the same committed quantity but silently omits a component, so the check can "pass" even though the values it is meant to protect have diverged.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  verifies execution status, gas used, write-set hash (`state_change_hash`), and event-root hash against the archived `TransactionInfo`, but the function's own inline comment admits the gap: [2](#0-1) 

This comparator is the sole per-transaction integrity check used by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes archived transactions and calls it directly: [3](#0-2) 

`TransactionOutput` (the re-executed VM output) never carries a `state_checkpoint_hash` field at all — that value only exists on the archived `TransactionInfo` after the state-checkpoint/Merkle-tree recomputation done in the full executor pipeline (`DoStateCheckpoint::run`, `do_state_checkpoint.rs`). Because `replay_on_archive` never recomputes or independently supplies a state-checkpoint hash for comparison, an execution divergence that produces the correct write-set hash and event hash but a different resulting state tree (root hash) — e.g., a bug in JMT update logic, an incorrect state-key hashing path, a hot-state or position-state root mis-derivation, or a non-deterministic Move VM code path — would pass this "authenticated" replay verification with no error.

By contrast, the block/chunk executor's own internal check, `LedgerUpdateOutput::ensure_transaction_infos_match` (used in `ChunkResultVerifier`), compares full `TransactionInfo` structs (which do include `state_checkpoint_hash`), so this integrity gap is specific to the archive-replay tool, not the live consensus/execution commit path.

### Impact Explanation
`replay-verify` (via `replay_on_archive`) is the tool operators/auditors use to confirm historical mainnet blocks replay to the exact committed ledger state — it is one of the primary defenses for detecting a state-divergence (hard-fork-class) bug after a VM/framework upgrade. Because the checkpoint-hash fields are excluded from the comparison, a real state-root divergence bug (which would corrupt durable ledger data or diverge from validator consensus) could exist and go completely undetected by this verification tool, giving false confidence that historical replay is correct. This directly matches the "Hard-fork-only divergence during commit, replay ... proof verification" and "authenticated API ... bound to the wrong version, object, or proof context" impact categories, since the verifier is meant to bind re-executed output to the authenticated (LedgerInfo-signed) state root and currently does not.

### Likelihood Explanation
The gap is not currently exploitable by an external unprivileged attacker to corrupt live consensus state (the live execution/commit path retains full `TransactionInfo` equality checks elsewhere), so it does not itself let a malicious party alter committed state. Its severity is as a detection/verification blind spot: any latent state-divergence bug (from any source) will not be caught by `replay-verify`, undermining the safety net meant to catch state-commitment corruption before/after mainnet incidents. Likelihood of the *underlying* corruption depends on other bugs; likelihood that *this checker fails to catch it* is 100% by design, as acknowledged in the code's own comment.

### Recommendation
Extend `ensure_match_transaction_info` (or `replay_on_archive`'s verifier) to compute/require the state (and, when enabled, hot-state and position-state) checkpoint hashes from re-executed output and compare them against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` before declaring a replayed transaction "matched." This likely requires wiring a `DoStateCheckpoint`-equivalent (or a lighter, replay-only state-summary) into `replay_on_archive.rs` so state-checkpoint versions have their computed roots verified before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and generally for `replay-verify` to be a meaningful state-integrity check.

### Proof of Concept
Not applicable as classic PoC exploit code — this is a verification-logic gap, not directly triggerable state corruption. Demonstration path:
1. Hypothesize/introduce a bug that alters the resulting state tree (e.g., a bad JMT key derivation) while leaving gas, status, event hashes, and write-set hash bytewise identical (or simply have any state-root-affecting non-determinism that doesn't touch the write-set structure hashed by `state_change_hash`).
2. Run `db-tool replay-on-archive` over the affected version range.
3. Observe `ensure_match_transaction_info` returns `Ok(())` for the affected transaction because it never inspects `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` — confirmed by reading the function body at [1](#0-0)  and its sole caller at [3](#0-2) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
