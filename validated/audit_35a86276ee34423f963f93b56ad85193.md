### Title
`CalculateGasCost` double-divides `baseFee` by 1e18, zeroing the effective gas price and letting UEA payload execution run gas-free — ([File: x/uexecutor/keeper/fees.go])

### Summary
`CalculateGasCost` in `x/uexecutor/keeper/fees.go` unwraps `baseFee` (an `sdkmath.LegacyDec`) by calling `baseFee.BigInt()` and then dividing the result by `1e18` again [1](#0-0) . `LegacyDec.BigInt()` already returns the correct integer value of the decimal (i.e., a plain integer number of the smallest `upc` unit, e.g. a base fee of `1000000000` as configured in genesis/app.toml) — it does **not** need a second `/1e18` unscaling. Since realistic base-fee values (gwei-scale, e.g. `1e9`) are far smaller than `1e18`, the extra division truncates the result to `0` via Go integer division, in the same way the WooFi `gamma` calculation rounds to `0` when the notional trade value is tiny relative to the coefficient.

### Finding Description
`CalculateGasCost` is used to compute the gas fee charged to a UEA after a `UniversalPayload` is executed, called from `DeductGasFeesFromReceipt` [2](#0-1) , which is itself invoked from both the direct `ExecutePayload` message handler and `ExecutePayloadV2` (used by inbound `GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` flows) [3](#0-2) [4](#0-3) .

Genesis/testnet configs set `feemarket.base_fee` as `"1000000000.000000000000000000"` (a `Dec` whose *value* is `1e9`, i.e., 1 gwei-equivalent in `aupc`/`upc`, since `upc` is configured as the 18-decimal EVM denom) [5](#0-4) . `baseFee.BigInt()` correctly yields this integer (`1e9`). The code then divides this already-correct value by `1e18` a second time under the mistaken assumption that the `Dec`'s internal 18-decimal fixed-point representation needs unwrapping [1](#0-0) . Because `1e9 / 1e18 = 0` under integer division, `baseFeeBig` becomes `0`. This zeroed value is then used both for the `maxFeePerGas` validation (which trivially always passes since any non-negative `maxFeePerGas` is ≥ 0) and as `effectiveGasPrice`, making `gasCost = effectiveGasPrice * gasUsed = 0` regardless of how much gas the payload consumed [6](#0-5) . `DeductGasFeesFromReceipt` then treats `gasCost.Sign() <= 0` as a no-op, and no fee is ever deducted or burned [7](#0-6) .

This is a direct analog to the M-5 report: a decimal-scaling round-down turns the "price" (here, gas price) to exactly zero, and every subsequent trade/execution proceeds at that zero rate — an unprivileged user can trigger it on every single `ExecutePayload`/`GAS_AND_PAYLOAD` call by simply submitting normal transactions, with no special conditions required (unlike the WooFi case which needed a dust-sized swap; here the bug is deterministic given typical gas-price magnitudes).

### Impact Explanation
Any unprivileged user invoking `MsgExecutePayload` (or triggering `GAS_AND_PAYLOAD`/`FUNDS_AND_PAYLOAD` inbound execution) causes their UEA to execute arbitrary EVM calls of any gas cost while paying **zero** protocol gas fee via `DeductAndBurnFees`/burn path [8](#0-7) . This breaks the fee/gas accounting invariant that execution gas must be charged and burned proportional to `gasUsed × effectiveGasPrice`. Concretely this is unauthorized economic loss/permanent under-collection of protocol fees for every universal payload execution, and — combined with unlimited free EVM execution — an economic-DoS vector: an attacker can flood the chain with heavy payload calls at zero marginal cost, since the standard Cosmos ante-level tx fee (charged separately for the wrapping Cosmos transaction) is unrelated to the actual UEA-side gas consumed by the module-originated `DerivedEVMCall`.

### Likelihood Explanation
High. This does not require an edge-case dust amount like the WooFi bug — it triggers deterministically whenever `baseFee` (in its natural gwei-scale magnitude) is less than `1e18`, which is virtually always true for any sane gas-price configuration. Every call to `ExecutePayload`/payload-bearing inbound flows is affected, and no privileged access is needed — an ordinary user submitting a normal `MsgExecutePayload` triggers it.

### Recommendation
Remove the erroneous second division by `1e18` in `CalculateGasCost`; use `baseFee.BigInt()` (or `baseFee.TruncateInt().BigInt()`) directly as the integer `upc` base fee value without an additional unscale step. Add a regression test asserting that for realistic base-fee magnitudes (e.g. `1e9`–`1e12`), `CalculateGasCost` returns a non-zero, correctly proportional gas cost for non-trivial `gasUsed`.

### Proof of Concept
1. Configure `feemarket.params.base_fee = "1000000000.000000000000000000"` (1 gwei-equivalent), matching genesis defaults in `scripts/test_node.sh`/`testnet/core/setup/setup_genesis_validator.sh`.
2. Call `k.CalculateGasCost(baseFee, maxFeePerGas, maxPriorityFeePerGas, gasUsed)` with `gasUsed = 1_000_000` and any `maxFeePerGas ≥ 0`.
3. Trace: `baseFeeBig := baseFee.BigInt()` → `1000000000`; `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` → `0`; `effectiveGasPrice = 0`; `gasCost = 0 * 1000000 = 0`.
4. In `DeductGasFeesFromReceipt`, `gasCost.Sign() <= 0` is true → function returns `nil` without calling `DeductAndBurnFees` — no funds are moved and no coins are burned, despite `receipt.GasUsed = 1_000_000` [7](#0-6) .
5. This can be verified end-to-end by executing any `MsgExecutePayload` against a deployed UEA on a standard test/genesis setup and observing the UEA's `upc` balance is unchanged before/after execution regardless of `gasUsed`.

	coin := sdk.NewCoin(pchaintypes.BaseDenom, amt)

	k.Logger().Debug("deducting and burning fees",
		"from", from.String(),
		"gas_cost", gasCost.String(),
		"denom", pchaintypes.BaseDenom,
	)

	err := k.bankKeeper.SendCoinsFromAccountToModule(ctx, from, types.ModuleName, sdk.NewCoins(coin))
	if err != nil {
		return err
	}

	return k.bankKeeper.BurnCoins(ctx, types.ModuleName, sdk.NewCoins(coin))
}
