### Title
`citrea_network_to_chain_id` is not injective — `Nightly` and `TestNetworkWithForks` both map to chain_id `5665`, breaking the cross-network replay guard on `BatchProofMethodId` upgrades - (File: `crates/light-client-prover/src/circuit/mod.rs`)

### Summary
`citrea_network_to_chain_id` is documented as existing specifically "to prevent cross network replay attacks" on method-id upgrade inscriptions, but it maps `Network::Nightly` and `Network::TestNetworkWithForks` to the identical value `5665`. Any `BatchProofMethodIdBody` signed with `chain_id = 5665` for one of these networks passes the chain_id gate in `run_l1_block` unchanged on the other, and — since the compiled-in fallback security-council pubkeys for both networks in `initial_values.rs` default to the exact same 5 hex keys when the corresponding env vars are unset — the same 3-of-5 signature set verifies on both.

### Finding Description
Binding claimed by the code comment: `citrea_network_to_chain_id(A) != citrea_network_to_chain_id(B)` for all distinct `Network` variants `A != B`. Actual implementation: [1](#0-0) 

shows `Network::Nightly => 5665` and `Network::TestNetworkWithForks => 5665` — the binding is false for this pair.

The chain_id gate in the light client circuit is: [2](#0-1) 

`circuit_chain_id = citrea_network_to_chain_id(network)` is compared only by value, so a body constructed and signed with `chain_id = citrea_network_to_chain_id(Network::TestNetworkWithForks)` (5665) is indistinguishable from one signed with `chain_id = citrea_network_to_chain_id(Network::Nightly)` (5665) — both pass on a light client prover instantiated with `network = Network::Nightly`, and vice versa.

Signature verification (`verify_method_id_security_council`, called with `msg = batch_proof_method_id.body.serialize()`) is purely a function of message bytes and the compiled-in `initial_da_pubkeys` array for the running binary's network — it has no independent per-network binding beyond the `chain_id` field inside `msg`. The default fallback pubkey constants for the two networks are identical hex values (same commented private keys) when the corresponding `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_{1..5}` env vars are not set at guest-binary compile time: [3](#0-2) [4](#0-3) 

Under that (default/unmodified) configuration, a `BatchProofMethodIdBody{method_id, activation_l2_height, chain_id:5665}` signed by the council for a `TestNetworkWithForks` deployment produces an inscription whose bytes are also fully valid against a `Nightly`-configured light client prover's `verify_method_id_security_council` call, because `msg` bytes match and the pubkeys match.

Existing guards that fail to stop this: the `activation_l2_height` monotonicity check (`crates/light-client-prover/src/circuit/mod.rs:539`) only rejects non-increasing heights, not cross-network origin; the chain_id check itself is the guard that is broken; there is no additional binding (e.g., DA network id, genesis hash) inside `BatchProofMethodIdBody` to disambiguate the two networks.

### Impact Explanation
If exploited, this allows a `BatchProofMethodId` upgrade legitimately authorised (signed by the 3-of-5 security council) for `TestNetworkWithForks` to be replayed as a valid, accepted method-id upgrade on `Nightly` (or vice versa), matching the Critical category "a sequencer commitment or method-id upgrade accepted that was never authorised." The attacker does not need council keys — they only need to observe a publicly inscribed `DataOnDa::BatchProofMethodId` payload for one network and re-inscribe the identical bytes on the Bitcoin chain monitored by the other network's light client prover (inscription/fee cost is the only requirement, which is within the attacker's allowed capability). This is repeatable for every future method-id upgrade inscribed on either network as long as the code and default keys remain unchanged.

### Likelihood Explanation
The chain_id collision itself is unconditional and present in shipped code today — no configuration is needed to trigger the `5665 == 5665` collision; a `cargo test` immediately proves it. Full weaponization into a signature replay additionally requires the two networks to share (or an attacker to otherwise obtain) matching council pubkeys, which is true for the compiled-in defaults in `initial_values.rs` unless the corresponding env vars are overridden per network at build time. Since `TestNetworkWithForks` is explicitly documented as a testing-purpose network likely built with the same default/test keys as local `Nightly` dev builds, this precondition is plausible in non-production deployments, and the underlying chain_id defect applies regardless of key configuration.

### Recommendation
Assign a unique `chain_id` constant to each of the five `Network` variants (`Mainnet`, `Testnet`, `Devnet`, `Nightly`, `TestNetworkWithForks`) with no overlap, and add a compile-time or unit-test assertion enforcing injectivity of `citrea_network_to_chain_id` across all variants so future additions cannot silently reintroduce a collision.

### Proof of Concept
```rust
// crates/light-client-prover/src/circuit/mod.rs (test module)
use sov_rollup_interface::Network;
use crate::circuit::citrea_network_to_chain_id;

#[test]
fn chain_id_is_injective_across_networks() {
    let networks = [
        Network::Mainnet,
        Network::Testnet,
        Network::Devnet,
        Network::Nightly,
        Network::TestNetworkWithForks,
    ];
    for i in 0..networks.len() {
        for j in (i + 1)..networks.len() {
            assert_ne!(
                citrea_network_to_chain_id(networks[i]),
                citrea_network_to_chain_id(networks[j]),
                "chain_id collision between {:?} and {:?}",
                networks[i],
                networks[j]
            );
        }
    }
}
```
This test fails today because `citrea_network_to_chain_id(Network::Nightly) == citrea_network_to_chain_id(Network::TestNetworkWithForks) == 5665`, confirming the broken binding.
