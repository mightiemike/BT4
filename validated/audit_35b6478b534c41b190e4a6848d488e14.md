### Title
Unpaginated `GetAssetIssueListServlet` allows O(N) unbounded response/work scaling with total on-chain TRC10 count - ([File: framework/src/main/java/org/tron/core/services/http/GetAssetIssueListServlet.java])

### Finding Description
`GetAssetIssueListServlet.doGet` calls `wallet.getAssetIssueList()` with no offset/limit parameters, unlike the sibling `GetPaginatedAssetIssueListServlet`, which requires explicit `offset`/`limit`. [1](#0-0) 
`Wallet.getAssetIssueList()` ultimately reads the entire `AssetIssueStore`/`AssetIssueV2Store` and serializes every stored `AssetIssueCapsule` into the response, so the work performed (store iteration + protobuf/JSON serialization) and the response payload size scale linearly with the total number of TRC10 tokens ever issued on the chain, with no cap.

An attacker can grow that store by issuing new TRC10 tokens via `AssetIssueActuator`. However, issuance is neither free nor unlimited per account: `AssetIssueActuator.validate()` rejects issuance if the account already owns an issued asset ("An account can only issue one asset") and requires the owner to have a balance ≥ `calcFee()` = `dynamicStore.getAssetIssueFee()`, a nonzero TRX fee burned/sent to the blackhole on execution. [2](#0-1) [3](#0-2) 

So mass issuance requires funding and controlling N distinct accounts and paying the asset-issue fee N times — this is real on-chain cost, not free.

Additionally, every HTTP servlet including `GetAssetIssueListServlet` extends `RateLimiterServlet`, which enforces a per-endpoint rate limiter (`IRateLimiter`) plus a `GlobalRateLimiter` before invoking the underlying servlet logic, throttling how often any single client (or aggregate) can invoke the endpoint. [4](#0-3) 

### Impact Explanation
If the total number of issued TRC10 tokens grows very large, each call to `/wallet/getassetissuelist` does more CPU/memory/serialization work and returns a larger payload than the paginated equivalent. Repeated invocation by a client that has capacity within the configured rate limits could increase load on the full node's HTTP tier, in principle degrading responsiveness of other HTTP endpoints served by the same node (e.g., `broadcasttransaction`), though impact is bounded by, and shared with, node-level QPS/global rate limiting.

### Likelihood Explanation
Exploitability is materially constrained by two existing guards that the audit prompt's premise does not fully account for:
1. Growing `N` requires paying the on-chain `AssetIssueFee` per token and funding a distinct account per token (one-issue-per-account restriction), making large-scale store growth a real, non-negligible on-chain cost rather than free/underpriced work.
2. `RateLimiterServlet`'s per-endpoint and global rate limiters throttle repeated calls to this specific servlet, which is the primary lever the described exploit needs to inflict sustained load.

Given these guards, this is a genuine design inconsistency (missing pagination relative to `GetPaginatedAssetIssueListServlet`) but not a free, unauthenticated, unbounded DoS primitive — it requires sustained financial investment to grow `N` and is bounded by rate limiting for repeated exploitation.

### Recommendation
Add default pagination (or a hard cap on returned entries) to `GetAssetIssueListServlet`/`Wallet.getAssetIssueList()` matching the bounds already enforced by `getPaginatedAssetIssueList`, and consider a stricter dedicated rate-limiter/QPS budget for this specific unpaginated endpoint given its unbounded response size.

### Proof of Concept
Integration test plan (illustrative, requires a test `AssetIssueStore`):
1. Populate a test `AssetIssueStore` directly with N synthetic `AssetIssueCapsule` entries (e.g., N = 10,000, 50,000, 100,000).
2. Invoke `Wallet.getAssetIssueList()` repeatedly and measure wall-clock latency/memory allocation vs. N, and compare against `Wallet.getPaginatedAssetIssueList(offset, limit)` with fixed `limit`.
3. Assert that `getAssetIssueList()` latency/memory grows ~linearly (or worse) with N while the paginated call remains ~constant regardless of N — confirming the missing-pagination gap, while separately noting (via code inspection of `AssetIssueActuator` and `RateLimiterServlet`) that scaling N and repeated invocation both carry real economic/rate-limit costs to the attacker.
