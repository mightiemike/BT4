### No vulnerability found for this question.

The code at `stackslib/src/chainstate/stacks/db/transactions.rs:821-841` correctly implements the intended ordering logic. When a stored report `(reporter=A, seq=S_low)` exists and a new report arrives with `mblock_header_1.sequence = S_high > S_low`, the condition `mblock_header_1.sequence < seq` evaluates to `false`, so execution falls into the `else` branch, which explicitly keeps `(reporter, seq)` = `(A, S_low)` unchanged and does **not** call `insert_microblock_poison` [1](#0-0) . The returned tuple `(reporter_principal, reported_seq)` is `(A, S_low)`, matching the claimed invariant that the first/lower-sequence reporter's record is never overwritten by a later, higher-sequence (worse) report.

The equality the question posits as violated — "stored (reporter, seq) after processing == earliest-sequence, first valid reporter, never overwritten by a later/worse report" — actually holds both before and after processing the attacker's second transaction: before, it's `(A, S_low)`; after, it remains `(A, S_low)`. Only a genuinely *lower* sequence than the stored one triggers an overwrite via the `if mblock_header_1.sequence < seq` branch [2](#0-1) , which is the correct behavior (a lower sequence proves an earlier fork point and legitimately entitles that reporter to the commission). There is no path by which a higher-sequence report can overwrite a lower-sequence one, so the described attack does not succeed.
