### Title
Wallet Contract can be permanently locked (`has_in_flight_tx` never reset) if an attacker-controlled token contract's callback response causes the callback to trap - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`WalletContract::nep_141_storage_balance_callback` resets the reentrancy-guard flag `has_in_flight_tx = false` as its first in-WASM statement, but that assignment is only *persisted* to state if the callback function returns without a host-level failure (panic/trap/out-of-gas). Because the `token_id` in this callback is the attacker-controllable `target` account from `rlp_execute`, an attacker can deploy a malicious "token" contract that responds to `storage_balance_of` with a payload engineered to abort execution of the callback (e.g. via `serde_json::from_slice` stack-overflow on deeply nested JSON, or gas exhaustion) before the function returns. This causes the whole receipt — including the in-memory `has_in_flight_tx = false` write — to be discarded, leaving the wallet permanently stuck with `has_in_flight_tx == true`. Since `rlp_execute` unconditionally rejects further calls while this flag is `true`, and no non-`#[private]` method exists to reset it, the wallet becomes permanently unusable.

### Finding Description
`WalletContract::rlp_execute` enforces a single-in-flight-transaction invariant using the boolean field `has_in_flight_tx` [1](#0-0) . It is set to `true` before dispatching a promise chain and is only cleared inside `#[private]` callback methods [2](#0-1) .

For ERC-20 style emulated transfers, `inner_rlp_execute` schedules a call to the attacker-supplied `target` account's `storage_balance_of` method, chained to `nep_141_storage_balance_callback` [3](#0-2) . Inside that callback, `has_in_flight_tx` is reset first, then the raw bytes returned by the *externally controlled* `token_id` contract are parsed with `serde_json::from_slice` [4](#0-3) .

This mirrors the Curve `emergencyExit` bug class exactly: a critical protective/cleanup state transition (there: `_lockVault()`; here: `has_in_flight_tx = false`) is only durable if a subsequent step that depends on an *externally controlled* contract completes successfully. In Solidity, an entire transaction reverts atomically on failure. In NEAR, the analogous atomicity unit is the receipt/function-call action: per the runtime spec, "a receipt whose result is `Err` triggers `state_update.rollback()`, discarding all state changes from the receipt" [5](#0-4) . Thus if the callback function itself panics/traps (rather than returning an `Err`/`ExecuteResponse` value) partway through — e.g., a WASM stack-overflow trap while recursively parsing a maliciously deep/large JSON payload returned by the attacker's fake token contract — the entire in-memory state of the function call, including the earlier `has_in_flight_tx = false` assignment, is rolled back and never committed.

Because `has_in_flight_tx` can only be reset inside `#[private]` methods, which cannot be invoked directly by any external account (only via a callback the contract itself scheduled), there is no recovery path once the flag is stuck at `true`. Every future call to `rlp_execute` — the sole entry point for the wallet's Ethereum-style transaction execution — will immediately short-circuit and fail [6](#0-5) .

### Impact Explanation
Any unprivileged caller of `rlp_execute` (e.g. a malicious or compromised relayer, or the account owner tricked into signing a transfer to a hostile "token") can supply an attacker-deployed contract as `target`/`token_id` for an ERC20Transfer-kind transaction. If that contract's `storage_balance_of` response is engineered to trap the callback (stack overflow via deep JSON nesting, or an oversized payload that exhausts the callback's gas budget before `has_in_flight_tx = false` can be persisted), the victim's `WalletContract` becomes permanently locked: `rlp_execute` will forever reject subsequent Ethereum-style transactions with "transaction already in progress." This effectively freezes the wallet's ability to move funds through its primary interface — a permanent denial-of-service / frozen-funds condition triggered by a single unprivileged transaction, satisfying the "permanently frozen funds" / "transaction-triggered halt" criteria.

### Likelihood Explanation
The attack requires only a single RLP-encoded ERC20Transfer-style transaction naming an attacker-controlled `target` contract; no privileged access, validator collusion, or network-level assumptions are needed. `serde_json`'s recursive-descent parser is known to be susceptible to stack exhaustion on deeply nested input, so producing a payload that traps the WASM guest during `nep_141_storage_balance_callback` is a well-understood technique, making exploitation practically feasible. Its practicality still depends on the exact gas/stack limits configured for `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` and the wasmer/near-vm stack-depth limits, which were not independently verified in this pass.

### Recommendation
- Move the persistence of `has_in_flight_tx = false` so it is guaranteed to happen independent of any parsing of untrusted external contract responses — e.g., perform the reset and commit it via a dedicated always-succeeding step, or wrap the untrusted-payload parsing in a way that cannot abort the whole receipt (bound the input size/depth explicitly before calling `serde_json::from_slice`, or use a non-recursive/streaming JSON parser with an explicit depth limit).
- Add a hard cap on the response size accepted from `storage_balance_of` before attempting deserialization.
- Provide a recovery mechanism (e.g., a timeout-based or owner-triggered reset of `has_in_flight_tx`) so that an unexpected callback failure cannot permanently brick the wallet.

### Proof of Concept
1. Attacker deploys `MaliciousToken` contract exposing `storage_balance_of(account_id)` that returns a byte string encoding deeply nested JSON arrays (e.g., `"[[[[[...]]]]]"` thousands of levels deep) or otherwise oversized to exhaust `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`.
2. Attacker (or a relayer using the wallet owner's access key) calls `rlp_execute(target = MaliciousToken, tx_bytes_b64 = <ERC20Transfer tx>)` on the victim's `WalletContract` [7](#0-6) .
3. `inner_rlp_execute` schedules `MaliciousToken::storage_balance_of` → `.then(nep_141_storage_balance_callback)` and sets `has_in_flight_tx = true` [3](#0-2) .
4. `nep_141_storage_balance_callback` executes: `has_in_flight_tx = false` is set in-memory, then `serde_json::from_slice(&value)` is invoked on the malicious payload and traps (stack overflow / OOG) [4](#0-3) .
5. The function call action fails with a host error; per rollback semantics the whole receipt's state changes (including the flag reset) are discarded [5](#0-4) , leaving on-chain `has_in_flight_tx == true`.
6. All subsequent `rlp_execute` calls on the victim wallet immediately return `"Error: transaction already in progress, please try again later."` forever, with no available reset path.

                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();

            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)

                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }

        }
