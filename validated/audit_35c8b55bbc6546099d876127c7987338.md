## Analysis

This maps to a real analog in the NEAR Wallet Contract. The external report's bug class — a value/asset that is expected to be forwarded/handled through a specific callback path gets silently dropped whenever execution takes a different branch than the one the developer accounted for — is reproduced in `WalletContract`'s meta-transaction refund logic.

### Title
Caller deposit is permanently unrefundable when the address-registrar or NEP-141 `storage_balance_of` intermediate promise fails or returns unexpected data - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` tracks any NEAR deposit attached by an external caller in a `CallerDeposit { account_id, yocto_near }` value, whose sole purpose is to be refunded back to the caller if the wrapped cross-contract call ultimately fails [1](#0-0) . That refund is only ever issued inside `rlp_execute_callback`, in its `PromiseResult::Failed` branch [2](#0-1) . However, `caller_deposit` is threaded through two earlier, intermediate callbacks — `address_check_callback` (used for `EOABaseTokenTransfer` targeting eth-implicit accounts) and `nep_141_storage_balance_callback` (used for emulated ERC-20 transfers) — and both callbacks contain early-return branches that discard `caller_deposit` entirely instead of forwarding it to a refund path.

### Finding Description
`inner_rlp_execute` builds a multi-step promise chain for two transaction kinds:
- `EOABaseTokenTransfer` with `address_check: Some(address)`: first calls the address registrar, then `address_check_callback`, which if successful chains into `action_to_promise(...).then(rlp_execute_callback(caller_deposit))` [3](#0-2) .
- `ERC20Transfer`: first calls `storage_balance_of` on the token contract, then `nep_141_storage_balance_callback`, which if successful chains into a transfer promise `.then(rlp_execute_callback(caller_deposit))` [4](#0-3) .

In both intermediate callbacks, several branches return `PromiseOrValue::Value(...)` directly, terminating the promise chain without ever creating a refund transfer to `caller_deposit.account_id`:
- `address_check_callback`: on `PromiseResult::Failed` (registrar call fails) and on JSON deserialize failure of the registrar's response [5](#0-4) , and on the "target already a named account" branch [6](#0-5) .
- `nep_141_storage_balance_callback`: on `PromiseResult::Failed` and on deserialize failure of `storage_balance_of`'s response [7](#0-6) , and on the "action is not a FunctionCall" branch [8](#0-7) .

In every one of these paths, the `caller_deposit` parameter received by the callback is simply dropped (it is an unused function parameter at that point) — the NEAR balance the caller attached to their original `FunctionCall` action (and which was already deposited onto the Wallet Contract's own account balance by the runtime when the receipt executed) is never scheduled for a transfer back to the caller. Contrast this with `rlp_execute_callback`, which is the *only* place that actually issues `env::promise_batch_action_transfer` to refund the caller [9](#0-8) ; the test `test_caller_refunds` explicitly asserts this exact refund invariant holds only for the flows that reach that function [10](#0-9) .

This is the direct analog of the TrueFi bug: a value (there, a reward token; here, a refundable deposit) is correctly handled along the "expected" happy path but is silently lost whenever an intermediate, attacker- or environment- influenced step (the address registrar contract, or an NEP-141 token's `storage_balance_of` response format) does not behave exactly as hardcoded/assumed.

### Impact Explanation
Any external caller (a relayer, or any account other than the wallet's own account, per `CallerDeposit::new`'s check that `predecessor_account_id != current_account_id` [11](#0-10) ) that submits an RLP-encoded `EOABaseTokenTransfer` to an eth-implicit target, or an emulated ERC-20 transfer, while attaching a NEAR deposit, permanently loses that deposit whenever:
- the address registrar's `lookup` call fails for any reason (e.g., insufficient gas, congestion, contract error), or returns anything the callback fails to deserialize, or
- the target NEP-141 token's `storage_balance_of` call fails or returns an unexpected format, or the wrapped action is not itself a `FunctionCall` when the receiver is unregistered.

The deposited NEAR balance is retained by the Wallet Contract account indefinitely with no code path to reclaim it on behalf of the caller — a concrete case of permanently frozen/unrecoverable funds triggered by ordinary (non-adversarial) external cross-contract-call failure modes.

### Likelihood Explanation
This is reachable by any unprivileged transaction signer calling `rlp_execute` on a deployed Wallet Contract with a nonzero attached deposit, targeting either (a) an eth-implicit account (forcing the address-registrar check path) or (b) an ERC-20 emulation transfer whose receiver is not yet storage-registered with the token contract. Address-registrar/token-contract call failures are not exotic — they can arise from ordinary gas exhaustion, temporary unavailability, or a token contract simply not implementing `storage_balance_of` in the exact expected shape — making this easily triggerable without any privileged or adversarial network position.

### Recommendation
`address_check_callback` and `nep_141_storage_balance_callback` should forward `caller_deposit` into a refund transfer (mirroring the logic in `rlp_execute_callback`'s `Failed` branch) on every early-return / error branch, rather than silently discarding it. Consider factoring the refund logic into a shared helper invoked from all three callbacks' failure paths so future modifications to the promise chain can't reintroduce this gap.

### Proof of Concept
1. Deploy a `WalletContract` and have it target `EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), .. }` where `address` is not registered in the address registrar, but simulate/force the registrar `lookup` call itself to fail (e.g., by giving it insufficient attached gas via `ADDRESS_CHECK_CALLBACK_GAS`/`REGISTRAR_LOOKUP_GAS` starvation, or by having the registrar temporarily unavailable).
2. Submit `rlp_execute` from an external account (`predecessor_account_id != current_account_id`) with a nonzero attached deposit.
3. Observe that `address_check_callback` returns `ExecuteResponse { success: false, error: Some("Call to Address Registrar contract failed") }` [12](#0-11)  without ever issuing a refund transfer, unlike the refund performed by `rlp_execute_callback`'s `Failed` branch [13](#0-12) .
4. Verify via account balance queries that the caller's attached deposit remains in the Wallet Contract's balance and is never transferred back, contradicting the invariant demonstrated in `test_caller_refunds` [14](#0-13)  for the code paths that do reach `rlp_execute_callback`.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
