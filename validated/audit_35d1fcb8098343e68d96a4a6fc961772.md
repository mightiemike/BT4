Confirmed: `WithdrawExpireUnfreezeProcessor` — the native-contract path reachable from TVM smart-contract execution — omits the `supportUnfreezeDelay()` gate that the ordinary actuator enforces for the same operation.

### Title
Missing `supportUnfreezeDelay()` feature-flag check in `WithdrawExpireUnfreezeProcessor` allows bypass of committee-controlled unfreeze-delay gating via smart contract - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java)

### Summary
The withdraw-of-expired-unfreeze-balance operation exists in two parallel code paths in java-tron: the ordinary transaction actuator `WithdrawExpireUnfreezeActuator` and the TVM-reachable native contract `WithdrawExpireUnfreezeProcessor` (invoked from `Program.withdrawExpireUnfreeze()` when a smart contract calls the corresponding precompile). The actuator gates the whole operation behind a committee-controlled dynamic parameter, `supportUnfreezeDelay()`, but the native-contract processor performs the identical state mutation without that check, exactly mirroring the reported bug class where a gating flag ("unlockAvailable"/feature flag) is enforced in some entry points but missing in others that perform the same underlying withdrawal.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` explicitly requires the feature to be enabled by the committee before allowing the withdrawal: [1](#0-0) 

However `WithdrawExpireUnfreezeProcessor.validate()`, which is the code path exercised when a smart contract calls the corresponding TVM native contract, never checks `supportUnfreezeDelay()` at all: [2](#0-1) 

This processor is directly reachable from any deployed/broadcast contract transaction through `Program.withdrawExpireUnfreeze()`, which constructs the same `WithdrawExpireUnfreezeParam`, calls `processor.validate()` then `processor.execute()`, and commits the repository changes: [3](#0-2) 

Because the committee flag `supportUnfreezeDelay` is meant to gate the entire "expire-unfreeze withdrawal" functionality (analogous to the `unlockAvailable` flag in the reference report gating SUP withdrawal), and one of the two code paths implementing that functionality omits the check, any account with pending `UnFreezeV2` entries can bypass the gate simply by triggering the withdrawal via a smart contract call (TVM `withdrawExpireUnfreeze` opcode/precompile) instead of a normal `WithdrawExpireUnfreezeContract` transaction.

### Impact Explanation
If the committee disables/has not enabled `AllowUnfreezeDelay` (i.e., `supportUnfreezeDelay()` is false) — for instance to pause or roll back the unfreeze-delay feature — users can still withdraw their expired-unfreeze balances by routing the same call through a smart contract, defeating the intended protocol-level control. This breaks the guarantee that the committee-controlled flag fully governs the feature's availability, i.e., "users break key functionality" gated by a chain parameter, matching the impact class of the referenced report (unauthorized state transition bypassing an intended gate).

### Likelihood Explanation
Reachability is straightforward: any user can deploy or call a trivial contract to invoke the `withdrawExpireUnfreeze` TVM native contract, without special privileges, as long as they have `UnFreezeV2` entries whose `unfreezeExpireTime` has passed. No malicious peer, leaked key, or privileged actor is required — it's directly reachable from a normal broadcast transaction that triggers contract execution.

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check to `WithdrawExpireUnfreezeProcessor.validate()` that already exists in `WithdrawExpireUnfreezeActuator.validate()`, throwing a `ContractValidateException` when the feature is not enabled, so both entry points enforce the same gating condition.

### Proof of Concept
1. Committee sets `AllowUnfreezeDelay` to disabled (`supportUnfreezeDelay()` returns false).
2. A user has pending `UnFreezeV2` entries whose `unfreezeExpireTime` has already passed (e.g., from a prior `UnfreezeBalanceV2` when the feature was enabled, or seeded state).
3. User deploys/calls a smart contract that internally triggers the `withdrawExpireUnfreeze` native contract (via `Program.withdrawExpireUnfreeze()`), instead of broadcasting a `WithdrawExpireUnfreezeContract` transaction.
4. `WithdrawExpireUnfreezeProcessor.validate()` performs no `supportUnfreezeDelay()` check and succeeds; `execute()` credits the account balance and clears the expired `UnFreezeV2` entries, even though the feature is supposed to be disabled at the protocol level.

  public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");
    }
    try {
      LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
  }
