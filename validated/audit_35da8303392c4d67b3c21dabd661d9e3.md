### Title
Reentrancy in `liquidate` via attacker-supplied `<ft-trait>` allows double seizure of collateral before position state is updated - (File: `mainnet/contracts/market/v0-4-market.clar`, function `liquidate`)

### Summary
`liquidate` computes the borrower's health check, LTV, and all liquidation amounts from position/mask data fetched once at the top of the function, then performs external calls through caller-supplied `<ft-trait>` contracts (`debt-ft`, `collateral-ft`) before the borrower's debt/collateral state in `market-vault` is fully committed. This mirrors the Juicebox `distributePayoutsOf` pattern: checks are computed, then an externally-controlled token transfer executes, and only afterward are the effects (mask update, scaled-debt removal, collateral removal) applied — violating checks-effects-interactions and allowing a reentrant call to observe stale, pre-liquidation state.

### Finding Description
In `liquidate` [1](#0-0) , the position, mask, LTV, and health check (`asserts! (>= current-ltv ltv-liq-partial) ERR-HEALTHY`) are all computed from `get-liquidation-position`/`get-full-position` fetched at function entry, before any external interaction occurs.

After the checks pass, the function performs:
1. `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` — this drives an external call through the caller-supplied `debt-ft` `<ft-trait>` parameter [2](#0-1) .
2. Only afterward does it call `.v0-market-vault debt-remove-scaled` and `.v0-market-vault collateral-remove` to commit the position's updated debt/collateral state [3](#0-2) .

Inside `collateral-remove` in the vault, the map state (`insert updated-entry`) is updated before `send-tokens` is called [4](#0-3) , and `send-tokens` again calls out through the caller-supplied `<ft-trait>` (`collateral-ft`) to the `recipient` [5](#0-4) .

Because `debt-ft`/`collateral-ft` are trait parameters chosen by the caller (the liquidator), the liquidator can pass a malicious FT contract whose `transfer` implementation calls back into `liquidate` for the same borrower. At the point of the first external call (`vault-system-repay`, step 1 above), the borrower's `market-vault` registry entry (mask), scaled debt, and collateral maps have **not yet** been updated for this liquidation — `debt-remove-scaled`/`collateral-remove` only run afterward. A reentrant `liquidate` call on the same borrower therefore recomputes health-check, LTV, and liquidation amounts (`calc-liquidation-params`, `process-debt-asset`, `process-collateral-asset`) from the same stale, pre-liquidation position data, allowing collateral to be seized (via a second `collateral-remove` from the vault) beyond what a single, correctly-sequenced liquidation would permit for the debt actually being repaid. This is precisely analogous to the Juicebox report's core flaw: an external transfer to caller-influenced code executes before the effects that the checks were meant to guard are finalized, letting the guarded values be reused with a call that changes what they measured.

### Impact Explanation
A liquidator can use a malicious `debt-ft` (or `collateral-ft`) token contract to reenter `liquidate` on the same borrower while the position's debt/collateral state is still pre-liquidation, seizing collateral beyond the amount justified by the debt actually repaid, or draining collateral disproportionately relative to the socialized bad debt. This is direct theft of user (borrower) collateral / protocol insolvency risk — a Critical impact.

### Likelihood Explanation
Exploitability depends on `debt-ft`/`collateral-ft` being fully attacker-controlled trait parameters passed directly by the liquidator (confirmed in the function signature), which is a normal, expected path for any market participant calling `liquidate` — no privileged access, DAO compromise, or flashloan-specific mechanics are required. The main precondition is that the reentrant call must reach `liquidate` again before the outer call's `debt-remove-scaled`/`collateral-remove` land, which the current code allows since those effects are only applied after the first external call in the sequence.

### Recommendation
Apply checks-effects-interactions consistently in `liquidate`: fully commit all borrower debt/collateral state changes (mask update, `debt-remove-scaled`, `collateral-remove` bookkeeping) in `market-vault` *before* invoking `vault-system-repay` or `send-tokens`, or introduce an explicit reentrancy guard (a `var-set in-liquidation`-style flag, as already used for `in-flashloan`) around `liquidate` to prevent any reentrant call from executing until the outer call completes.

### Proof of Concept
1. Attacker deploys a malicious FT contract implementing the `ft-trait` for use as `debt-ft`, whose `transfer` function calls back into `liquidate` for the same `borrower`.
2. Attacker calls `liquidate(borrower, collateral-ft, malicious-debt-ft, debt-amount, ...)` on an eligible position.
3. `liquidate` computes health-check/LTV/liquidation amounts from the (unmodified) position, then calls `vault-system-repay`, which triggers `malicious-debt-ft`'s `transfer` callback.
4. Inside the callback, attacker calls `liquidate` again for the same `borrower`, before `debt-remove-scaled`/`collateral-remove` from step 2/3 have committed — the reentrant call recomputes the same (still pre-liquidation) health check/amounts and seizes collateral a second time via its own `collateral-remove` call.
5. Both calls' `collateral-remove` invocations succeed, resulting in collateral seized twice against debt that was (at most) reduced once, before the outer call's own effects are applied — net over-seizure of borrower collateral.

Note: the exact internal implementation of `vault-system-repay` was not retrieved during this investigation (only its call sites were located), so the precise point at which the external `debt-ft` transfer callback fires relative to `market`-level bookkeeping could not be fully confirmed from the indexed contents; this should be verified directly in the full `v0-4-market.clar` / `market.clar` source before treating the PoC as conclusively reproducible.

(define-public (collateral-remove (account principal) (amount uint) (ft <ft-trait>) (asset-id uint) (recipient principal))
  (let ((states (var-get pause-states))
        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
        (remaining (try! (remove-user-collateral user-id asset-id amount)))
        (updated-mask (if (is-eq remaining u0)
                        (mask-update mask asset-id true false) ;; collateral, remove
                        mask))
        (updated-entry (merge entry (refresh updated-mask))))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-remove states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (insert updated-entry)
    (try! (send-tokens ft amount recipient))
    
    (print {
      action: "collateral-remove",
      caller: contract-caller,
      data: {
        account: account,
        recipient: recipient,
        asset-id: asset-id,
        amount: amount,
        updated-collateral-amount: remaining,
        mask-before: mask,
        mask-after: updated-mask
      }
    })
    
    (ok remaining)))
