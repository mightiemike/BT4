### Title
`DeleteAccount` action does not validate that `beneficiary_id` refers to an existing (or self) account, permanently burning the account's balance - (File: runtime/runtime/src/actions.rs)

### Summary
Just as `MainToken.set_mint_multisig()` in the reference report accepts an unchecked/zero address and can permanently lose a privileged pointer, `action_delete_account` in nearcore accepts an attacker- or user-supplied `beneficiary_id` on `DeleteAccountAction` with no validation that the account exists, and unconditionally routes the account's remaining balance to it via a system "refund" receipt. If the target does not exist, the funds are irrecoverably burned rather than returned to the signer.

### Finding Description
`DeleteAccountAction { beneficiary_id: AccountId }` is a fully user-controlled field, reachable from any signer via a simple transaction containing a `DeleteAccount` action, or via a contract call using `promise_batch_action_delete_account`. When executed, `action_delete_account` pays out the account's balance like this: [1](#0-0) 

This uses `Receipt::new_balance_refund`, which builds a system-predecessor ("refund") receipt: [2](#0-1) 

Crucially, refund receipts are exempt from account-creation semantics — `check_account_existence` explicitly disallows creating an account via a refund-shaped `Transfer` action, confirmed by the test `refund_may_not_create_universal_account`: [3](#0-2) 

If a refund receipt's execution fails (e.g., because `beneficiary_id` doesn't exist), the runtime does **not** re-refund the sender — it burns the deposit outright: [4](#0-3) 

Unlike `Transfer`, `DeleteAccountAction` has no dedicated action-validation check ensuring `beneficiary_id` exists, is a valid non-implicit account, or differs from the account being deleted. A test comment in the codebase itself corroborates the danger: "The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" (in practice: burned, not returned) — [5](#0-4) . The action-level documentation only lists `InvalidAccountId`, `DeleteActionMustBeFinal`, and `DeleteAccountStaking` as validation errors for `DeleteAccountAction` — no existence check for `beneficiary_id`: [6](#0-5) 

### Impact Explanation
Any account holder (or any contract acting on a user's behalf via `promise_batch_action_delete_account`) can permanently destroy an account's entire remaining NEAR balance by specifying a nonexistent (e.g., mistyped) `beneficiary_id`. This is a **permanent freezing/loss of funds**: the deleted account's balance is neither transferred to the intended beneficiary nor returned to the signer — it is unconditionally burned in `other_burnt_amount`. This is directly analogous to the referenced bug class (unchecked/zero-like target address on an irreversible state-changing operation causing permanent loss), reachable purely by a single unprivileged transaction or a smart-contract-issued batch action, with concrete, permanent value loss.

### Likelihood Explanation
High likelihood of accidental triggering: a single typo in an `AccountId` string (a common, easy-to-make mistake, e.g. `.near` vs `.testnet`, or wrong sub-account) when constructing a `DeleteAccountAction`/`promise_batch_action_delete_account` call results in complete, irreversible loss of the deleted account's balance. No special privileges, timing, or race conditions are required — deletion and burn happen deterministically and atomically within the same chunk-processing flow.

### Recommendation
Add a validation step (either in `action_validation.rs`/`validate_actions` or at execution time in `action_delete_account`) requiring that `beneficiary_id`:
1. Is not equal to the account being deleted (self-burn edge case), and
2. Refers to an existing, initialized account before the delete is allowed to proceed — otherwise fail the action with a clear `ActionErrorKind` (e.g., `BeneficiaryDoesNotExist`) rather than silently generating a doomed refund receipt that later gets burned.

Alternatively, change the failure path for the generated balance-refund receipt so that when the beneficiary does not exist, the balance is returned to the original account owner/predecessor instead of being burned — but a strict existence check on `beneficiary_id` before deletion is the safer fix.

### Proof of Concept
1. Submit a transaction from account `alice.near` containing a single action:
   `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "typo-nonexistent.near".parse().unwrap() })`.
2. Runtime executes `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`), which unconditionally emits `Receipt::new_balance_refund(&"typo-nonexistent.near", account_balance)` and deletes `alice.near`.
3. When the refund receipt executes against `typo-nonexistent.near`, `check_account_existence` rejects the `Transfer` because refund receipts cannot create accounts, producing `AccountDoesNotExist` and a failed `result.result`.
4. Because `receipt.predecessor_id().is_system()` and `result.result.is_err()`, the deposit is added to `stats.balance.other_burnt_amount` (`runtime/runtime/src/lib.rs:1047-1054`) instead of being returned to `alice.near` — the entire balance is permanently burned.

Note: I was unable to fully inspect the exact validate-action-level DeleteAccountAction branch inside `action_validation.rs` (search results returned matches but the specific branch body wasn't retrieved before the tool budget ran out); if it turns out there already is an existence/self-beneficiary check there, that would need to be re-confirmed via a fresh code read.

## DeleteAccountAction

```rust
pub struct DeleteAccountAction {
    /// The remaining account balance will be transferred to the AccountId below
    pub beneficiary_id: AccountId,
}
```

**Outcomes**:

- The account, as well as all the data stored under the account, is deleted and the tokens are transferred to `beneficiary_id`.

### Errors

**Validation Error**:

- If `beneficiary_id` is not a valid account id, the following error will be returned

```rust
/// Invalid account ID.
InvalidAccountId { account_id: AccountId },
```

- If this action is not the last action in the action list of a receipt, the following error will be returned

```rust
/// The delete action must be a final action in transaction
DeleteActionMustBeFinal
```

- If the account still has locked balance due to staking, the following error will be returned

```rust
/// Account is staking and can not be deleted
DeleteAccountStaking { account_id: AccountId }
```

**Execution Error**:

- If state or storage is corrupted, a `StorageError` is returned.
