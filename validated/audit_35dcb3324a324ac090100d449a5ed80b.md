### Title
Interest accrual clock (`last-update`) is only advanced when the index changes, allowing accrual state to desynchronize from real elapsed time - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
In every `v0-vault-*` contract's `accrue` function, the data-var `last-update` (the accrual clock) is only written when the computed `index`/`lindex` actually differ from the previous stored values. If the computed next index equals the current index (e.g. rounding to the same value over a very short elapsed interval, or interest computed as zero due to `mul-div-down` truncation), `last-update` is left untouched even though a full `accrue` invocation completed and returned `(ok {...})` as if state were current.

### Finding Description
`accrue` in the vault contracts reads `pause-states`, `index`, and `lindex`, and — when accrual isn't paused — computes `next` (new borrow index) and `nliq` (new liquidity index) via `next-index` / `next-liquidity-index`, which are time-dependent functions using `stacks-block-time` and the previously stored `last-update`. [1](#0-0) 

The update of `last-update` is explicitly gated behind an equality check:
```clarity
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
```
This means: whenever the freshly computed `next`/`nliq` happen to equal the previously stored `idx`/`lidx` (a real possibility given integer-division rounding in `next-index`/`next-liquidity-index` over short time deltas, or zero-rate periods), the clock is *not* advanced, while the function still returns `(ok {index: next, lindex: nliq})` to every caller (`system-borrow`, `deposit`, `redeem`, market callers, etc.) as a successful accrual. Every subsequent call to `accrue` will then recompute the elapsed time from the stale `last-update`, silently accumulating a growing backlog of un-recorded time between the true current block time and the last time the index actually moved.

This is the "clock advanced only on change" pattern: a timestamp meant to represent "when did we last observe/settle state" is mutated conditionally on a value comparison rather than unconditionally on every successful execution path, causing the clock to drift out of sync with the block time it is supposed to track.

### Impact Explanation
Because interest-rate accrual (`next-index`) and liquidity-index growth (`next-liquidity-index`) are computed from the delta between `stacks-block-time` and `last-update`, an accrual clock that lags behind real elapsed time understates the interest actually owed during periods where per-call recomputation produces no observable index delta. Depending on the growth-rate function's shape, this can result in permanently lost/uncaptured interest accrual for lenders (frozen/lost yield) since the "missing" time delta is never applied — once `last-update` finally does move forward (on a call where index changes), the intervening un-recorded elapsed time is discarded rather than compounded, because `next-index`/`next-liquidity-index` are computed strictly off `(stacks-block-time - last-update)` for the *next* call, not off the true un-recorded backlog. This lands on the in-scope impact class of **temporary/permanent freezing of unclaimed yield** for vault depositors, since accrued-but-unrecorded interest for that time window is not credited to the liquidity index and thus never distributed to zToken holders.

### Likelihood Explanation
This can occur under ordinary usage without any attacker action: any sequence of rapid `accrue`-triggering calls (deposit/redeem/borrow/repay) within intervals short enough, or under low/zero effective rates, where `mul-div-down`-based index growth rounds down to the previous stored index, will skip the `last-update` write. Given `accrue` is invoked on essentially every state-changing vault operation, this scenario is reachable in normal high-frequency operation, not just a contrived edge case.

### Recommendation
Always write `last-update` to `stacks-block-time` whenever `accrue`'s non-paused branch executes, regardless of whether `index`/`lindex` changed value, so the clock never falls behind the block time it is meant to track:
```clarity
(var-set last-update stacks-block-time)
```
unconditionally at the end of the non-paused accrual branch.

### Proof of Concept
1. Vault has `index = I0`, `lindex = L0`, `last-update = T0`.
2. Two `accrue`-triggering operations (e.g. two small `deposit`s) occur at `T0 + Δ1` and then `T0 + Δ2`, where `Δ1` is small enough that `next-index`/`next-liquidity-index` compute `next == I0` and `nliq == L0` due to integer-division truncation in `mul-div-down`.
3. In the first call, `(is-eq idx next)` and `(is-eq lidx nliq)` are both true → the `or` condition is false → `last-update` is **not** updated (remains `T0`), even though the call returns `(ok {index: I0, lindex: L0})` successfully.
4. At `T0 + Δ2`, `accrue` is called again; it still computes elapsed time as `(T0+Δ2) - T0` (correct so far, self-healing in this case) — however, if in the interim any deposit/redeem/borrow that reads the *unaccrued* index for its own share-price or scaled-debt conversion occurred using the stale `index`/`lindex` (e.g. `convert-to-assets-preview`, `get_available_assets`, or `total-debt`), those calls used index/lindex values that were valid at `T0` while additional real elapsed time (`Δ1`) had already passed but was not reflected, understating accrued interest for that window.
5. Because the growth functions are computed strictly from `(stacks-block-time - last-update)` rather than from an accumulated unaccounted backlog, once `last-update` finally advances, the `Δ1` window's proportional interest that rounded to zero is never separately recovered - it is permanently absent from the liquidity index growth, resulting in under-accrued yield relative to true elapsed time across the vault's lifetime.
