### Title
Ledger-tool `run_final_hash_calc()` can race with the still-running `AccountsBackgroundService`, causing stale/incorrect hash-verification results or a panic - (File: `runtime/src/bank.rs`, `ledger/src/blockstore_processor.rs`)

### Summary
`Bank::run_final_hash_calc()` force-flushes the write cache and then walks the accounts index to (re)compute the accounts lattice hash for verification. This is explicitly documented as unsafe to run concurrently with flush/clean/shrink operations, yet the call site in `blockstore_processor::process_blockstore_from_root` invokes it without first stopping the `AccountsBackgroundService` (ABS), unlike the sibling "create-snapshot" code path in `ledger-tool`, which explicitly joins/stops ABS first "to avoid" this exact race.

### Finding Description
`AccountsDb::calculate_accounts_lt_hash_at_startup_from_index` is annotated "NOT safe to call concurrently with flush operations" [1](#0-0) . It is reached via `Bank::run_final_hash_calc` → `Bank::verify_accounts`, which force-flushes the cache and then reads the accounts index/storage while ABS may still be concurrently flushing, cleaning, and shrinking storages in the background: [2](#0-1) [3](#0-2) 

The `--run-final-accounts-hash-calculation` ledger-tool flag documents this exact hazard in its own help text: "Final hash calculation could race with accounts background service tasks and assert." [4](#0-3) 

`process_blockstore_from_root` calls `bank.run_final_hash_calc()` directly at the end of replay, with no call to stop/join the `AccountsBackgroundService` beforehand: [5](#0-4) 

Contrast this with the "create-snapshot" command in `ledger-tool`, which recognizes the identical hazard for flush/clean and explicitly calls `accounts_background_service.join().unwrap()` before performing the (implicit) flush/clean operations of snapshot creation: [6](#0-5) 

`LoadAndProcessLedgerOutput` itself documents that ABS is deliberately *not* joined by default because some of its operations are long-running and "don't respond to the exit flag," leaving it up to each caller to decide whether to stop ABS before doing something unsafe with it running: [7](#0-6) 

This is the AccountsDB-storage/hashing analog of the ParticlePositionManager bug: a documented invariant ("this operation must not run while the background service is active") exists, but one specific call path (`run_final_hash_calc`, gated by `--run-final-accounts-hash-calculation`) does not enforce it, while a structurally similar path (create-snapshot) does. Just as the paused/unpaused ParticlePositionManager allowed `closePosition`/`addPremium` to execute during a state where they should have been blocked, `run_final_hash_calc` executes a hash-verification routine during a state (ABS actively running) where the code's own comments say it is unsafe.

### Impact Explanation
If ABS concurrently flushes/cleans/shrinks storages while `calculate_accounts_lt_hash_at_startup_from_index` walks the accounts index and storages, the computed lattice hash can be computed over an inconsistent view of storage vs. index (accounts being relocated by shrink, or purged by clean, mid-scan), leading to either:
- A spurious mismatch between calculated and expected accounts lt hash, causing `verify_accounts` to report a false failure ("Verifying accounts failed: accounts lattice hashes do not match") even though the ledger/state is actually correct, or
- An index-vs-storage race triggering an assert/panic in the accounts-db read path (as literally warned about in the CLI help text: "could race... and assert"), taking down the ledger-tool process.

This is a node panic / incorrect-verification-result class of issue, matching the "node panic" and "hash divergence" acceptance criteria; it does not compromise consensus safety of a running validator (this path is only reachable via a ledger-tool debug flag), but it does produce concretely wrong or crashing behavior for anyone using `--run-final-accounts-hash-calculation` while other accounts-db background work is in flight.

### Likelihood Explanation
`process_blockstore_from_root` always spins up `AccountsBackgroundService` before replay (per `LoadAndProcessLedgerOutput`'s own comment about it running "several long running operations" in the background) [7](#0-6) , and `run_final_hash_calc()` is invoked immediately at the end of replay in the same function without an intervening join/stop [5](#0-4) . Because ABS's clean/shrink loop runs on fixed intervals (`CLEAN_INTERVAL`/`SHRINK_INTERVAL`) independent of the caller, there is a realistic window where ABS is mid-flush/clean/shrink exactly when `--run-final-accounts-hash-calculation` triggers the hash walk. The bug is only user/operator-triggered (requires the specific CLI flag) and self-admittedly known ("could race... and assert" in the help text itself), so likelihood is moderate — it depends on timing but is not contrived, and the codebase's own documentation confirms the hazard is real and currently unmitigated on this path.

### Recommendation
Before calling `bank.run_final_hash_calc()` (or more generally, before calling `verify_accounts`/`calculate_accounts_lt_hash_at_startup_from_index`), stop and join the `AccountsBackgroundService`, mirroring the pattern already used in the create-snapshot command (`accounts_background_service.join().unwrap()`). Concretely, in `blockstore_processor::process_blockstore_from_root`, thread the `AccountsBackgroundService`/`AbsStatus` handle into scope and call `.status().stop()` followed by joining, or restructure so `run_final_hash_calc` is only invoked after the service has been torn down, exactly as done for `create-snapshot`.

### Proof of Concept
Not directly executable as a PoC in this read-only review; the race is demonstrated by the codebase's own contradictory handling of the same hazard:
1. `AccountsDb::calculate_accounts_lt_hash_at_startup_from_index` explicitly documents "NOT safe to call concurrently with flush operations" (`accounts-db/src/accounts_db.rs:4646`).
2. The `--run-final-accounts-hash-calculation` flag help text acknowledges "Final hash calculation could race with accounts background service tasks and assert" (`ledger-tool/src/main.rs:1171-1178`).
3. `process_blockstore_from_root` calls `bank.run_final_hash_calc()` with ABS still running and un-joined (`ledger/src/blockstore_processor.rs:2000-2023`).
4. The sibling `create-snapshot` command in the same binary treats the identical hazard (flush+clean racing with ABS) as serious enough to require `accounts_background_service.join().unwrap()` before proceeding (`ledger-tool/src/main.rs:2186-2190`), showing the missing guard on the `run_final_hash_calc` path is an inconsistency/omission rather than an accepted design choice.
