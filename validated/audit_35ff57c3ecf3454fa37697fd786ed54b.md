### Title
Arbitrary pre-installed binary execution via attacker-controlled `pluginConfig.command` in OCR2 generic-plugin job specs - ([File: plugins/registrar.go])

### Summary
An authenticated user holding only the 'edit' role can submit an OCR2 `pluginType = "plugin"` job spec via the `createJob` GraphQL mutation and fully control the `command` field of `pluginConfig`. This value flows unchecked (aside from a mere existence check) through `validateGenericPluginSpec` and `RegisterLOOP`/`NewCmdFactory` into `exec.Command`, letting the job creator dictate which pre-existing executable on the node's `PATH` the chainlink node process spawns, along with a fully attacker-controlled environment for that subprocess.

### Finding Description
The `createJob` GraphQL mutation is gated only by `authenticateUserCanEdit`, which permits any role except `View`/`Run` [1](#0-0) . For `job.OffchainReporting2` specs it calls `validate.ValidatedOracleSpecToml`, which for `pluginType = "plugin"` dispatches to `validateGenericPluginSpec` [2](#0-1) .

In `validateGenericPluginSpec`, the `command` used to launch the LOOP plugin comes directly from the attacker-supplied `pluginConfig.command`; it only falls back to an operator env var if the field is empty: [3](#0-2) 

The only gate is `exec.LookPath(command)`, which merely verifies the named program exists and is executable somewhere on `PATH` (or as an absolute/relative path) — it performs no allow-listing of which binaries are permitted to be used as a plugin command. The resolved command (and attacker-supplied `EnvVars`) is then passed to `rc.RegisterLOOP(plugins.CmdConfig{Cmd: command, Env: envVars})` [4](#0-3) .

`RegistrarConfig.RegisterLOOP` forwards the `CmdConfig` unmodified to `NewCmdFactory` [5](#0-4) , which builds the actual OS command with no allow-list check whatsoever: [6](#0-5) 

Note that `cmd.Env` is built solely from `lcfg.Env` (attacker-controlled `EnvVars`) plus the registered loop's env config, replacing rather than inheriting the process environment — giving the attacker full control of the environment of the spawned process as well. The same unguarded `command` field is used again at actual job-runtime in `Delegate.newServicesGenericPlugin`, which explicitly notes it skips validation because "that happens as part of creating the job" [7](#0-6) , so both the validation-time and run-time code paths execute the attacker-chosen binary with attacker-chosen environment.

There is no allow-list of permitted commands anywhere in the codebase gating this flow (confirmed via repo-wide search for allow-list/whitelist mechanisms tied to LOOP plugin commands); the design intends `CL_<PLUGIN>_CMD` operator env vars to select the binary, but a job spec's explicit `command` field silently overrides that operator-controlled default.

### Impact Explanation
An Edit-role user — who is only supposed to be able to manage job specs, not arbitrary processes — can cause the node's own process to `exec()` any executable already present on the container/host `PATH` (e.g. `sh`, `bash`, `python3`, `curl`, `psql`, cloud CLI tools) with a fully attacker-controlled environment (`EnvVars`), for both the one-shot `plugin.ValidateConfig` validation run and the persistent job's runtime LOOP process. This is a privilege escalation/process-execution primitive beyond the intended scope of the 'edit' role, and can be leveraged for data exfiltration, credential/metadata access (e.g. invoking a cloud CLI already installed in the image), or as a stepping stone toward further compromise, depending on what binaries happen to exist in the deployed image.

### Likelihood Explanation
Feasible and repeatable with only an authenticated session holding 'edit' (not admin) role — precisely the precondition stated. The only constraint is that the target command must already exist on the node's `PATH`/be locatable via `exec.LookPath`; most production container images bundle a shell and various utilities, making this broadly exploitable in practice.

### Recommendation
Enforce that the executable used for a LOOP plugin command is always derived from operator-side configuration (the `CL_<PLUGIN>_CMD` env var / an explicit allow-list of permitted plugin names to binary paths) and never take the executable path directly from job-spec input (`pluginConfig.command`). If per-job override of the command is required, restrict it to admin-only job creation, and validate the resolved command against an explicit operator-maintained allow-list rather than merely checking that the path exists via `exec.LookPath`.

### Proof of Concept
1. Add an integration test in `core/services/ocr2/validate/validate_test.go` (or a GraphQL resolver test similar to `TestResolver_CreateJob`) that:
   - Authenticates a session with `sessions.UserRoleEdit`.
   - Submits a `createJob` mutation / calls `ValidatedOracleSpecToml` with a TOML spec: `pluginType = "plugin"`, `pluginConfig.PluginName = "poc"`, `pluginConfig.OCRVersion = 2`, `pluginConfig.Command = "/usr/bin/id"` (or any benign binary guaranteed present, e.g. `"echo"`).
   - Supplies a fake `plugins.RegistrarConfig` (as in `plugins/cmd_test.go`'s pattern) whose `RegisterLOOP` captures the `CmdConfig.Cmd`/`Env` passed to it, or use the real `NewRegistrarConfig` and assert that `exec.Command` is invoked with `Cmd == "/usr/bin/id"`.
2. Assert that job creation succeeds (no allow-list error raised) and that the captured `CmdConfig.Cmd` equals the attacker-supplied value, proving the node would spawn that exact binary.
3. Additionally assert (via code inspection/test) that `validateGenericPluginSpec` and `newServicesGenericPlugin` contain no check comparing `command` against any operator-configured allow-list — only the `exec.LookPath` existence check.

```go
// NewCmdFactory is helper to ensure synchronization between the loop registry and os cmd to exec the LOOP
func NewCmdFactory(register func(id string) (*RegisteredLoop, error), lcfg CmdConfig) (func() *exec.Cmd, error) {
	registeredLoop, err := register(lcfg.ID)
	if err != nil {
		return nil, fmt.Errorf("failed to register %s LOOP plugin: %w", lcfg.ID, err)
	}
	return func() *exec.Cmd {
		cmd := exec.Command(lcfg.Cmd) //#nosec G204 -- we control the value of the cmd so the lint/sec error is a false positive
		cmd.Env = append(cmd.Env, lcfg.Env...)
		cmd.Env = append(cmd.Env, registeredLoop.EnvCfg.AsCmdEnv()...)
		return cmd
	}, nil
```
