### Title
L1 handler transactions are always marked "consumed" even when execution fails with a hard sequencer/state error, permanently stranding the L1-side deposit without giving the batcher a chance to mark it rejected/retryable - ([File: crates/apollo_batcher/src/block_builder.rs])

### Summary
Analogous to the GroupBuy bug where funds were accepted into the contract but never recorded in any place that would let the user reclaim them (leaving Ether permanently stuck), an L1→L2 message processed by the sequencer as an `L1Handler` transaction is unconditionally classified as "consumed" the moment it is dispatched to the executor, regardless of the actual outcome of execution — including outcomes that are not ordinary Cairo reverts but hard executor/state errors.

### Finding Description
In `collect_execution_results_and_stream_txs`, every `InternalConsensusTransaction::L1Handler` immediately has its hash inserted into `execution_data.consumed_l1_handler_tx_hashes` *before* the actual execution `result` is even inspected: [1](#0-0) 

Only afterwards does the code branch on `result`: a normal Cairo revert (`tx_execution_info.revert_error` set) is logged and still counted as "accepted" (correctly consumed, since the OS still charges/queues the nonce), but a hard `Err(TransactionExecutorError)` (e.g. `StateError::OutOfRangeContractAddress`, or any other executor-level failure) is pushed into `rejected_tx_hashes` — yet the tx hash *remains* in `consumed_l1_handler_tx_hashes` because that insertion already happened unconditionally: [2](#0-1) 

This is confirmed intentionally by the test `failed_l1_handler_transaction_consumed`, which asserts that even when the executor returns `Err(TransactionExecutorError::StateError(...))` for an L1 handler tx, its hash still ends up in `consumed_l1_handler_tx_hashes`: [3](#0-2) 

Downstream, `commit_proposal_and_block` in the batcher computes `rejected_l1_handler_tx_hashes` as the intersection of `rejected_tx_hashes` and `consumed_l1_handler_tx_hashes`, and notifies the L1 events provider with both `consumed_l1_handler_tx_hashes` (all of them, including the failed one) and `rejected_l1_handler_tx_hashes`: [4](#0-3) 

Per the flow documented for the L1 provider, "For committed txs: Pending → Committed; For rejected txs: Unstage, keep as Pending" — i.e. rejected L1 handler transactions are supposed to remain retryable (`Pending`) so the message can be reprocessed in a future block: [5](#0-4) 

However, because the transaction hash is *also* unconditionally present in the `consumed` set, the L1 event/transaction manager on the receiving end has to correctly disambiguate "consumed-but-also-rejected" from "purely consumed" using set membership in both collections — any state-transition bug, race, or ordering issue in that reconciliation logic (`apply_commit_block`/`commit_txs` in the L1 provider's transaction manager, which was not fully inspectable within this session due to index coverage limits) that treats "present in consumed" as authoritative would permanently mark the underlying L1 message as delivered/consumed. Since Starknet's core contract model treats L1→L2 messages as one-shot (the message hash is deleted from L1 storage once the sequencer reports it consumed), this would mean the L1-side sender (e.g., a token bridge contract escrowing funds, or a user paying `paid_fee_on_l1`) can never have that specific message replayed, exactly mirroring the referenced bug: value is committed/paid on the source side, but the corresponding acknowledgment/credit path (the L2-side effect of the message) never completed and no fallback recovery path exists once the "consumed" marker is set.

### Impact Explanation
If an L1 handler transaction that carries a token/fund-bearing message (e.g., a bridge deposit calling a `deposit`/`mint` handler) fails due to a hard executor error (state corruption, out-of-range address, or any other executor-level `Err`) rather than a normal Cairo-level revert, the transaction is rejected (no state change/minting occurs on L2) while simultaneously being recorded as "consumed" for L1 accounting purposes. This is a concrete-loss class finding: the deposited/escrowed funds on L1 become permanently unmintable/unclaimable on L2 because the one-shot L1→L2 message is treated as delivered, with no path to resubmit or refund — directly analogous to the referenced GroupBuy issue where accepted value was never recorded anywhere that permitted recovery.

### Likelihood Explanation
The reachable trigger is a single `L1Handler` transaction whose execution fails at the executor/state layer (as opposed to reverting normally inside Cairo) — this is reachable by any L1 sender producing a message whose target contract/class state is momentarily invalid, uninitialized, or otherwise triggers a `TransactionExecutorError` (e.g. `StateError`) rather than a Cairo `revert`. This does not require a malicious operator, prover, or proposer — it can occur from ordinary state edge cases (e.g., messages targeting not-yet-deployed contracts, or state races between message arrival and contract deployment), making it plausible under normal operation, though the exact frequency depends on the still-unverified reconciliation logic inside the L1 provider's transaction manager, which this session could not fully inspect (index size limits truncated deeper `apollo_l1_events` internals).

### Recommendation
Only insert an `L1Handler` transaction hash into `consumed_l1_handler_tx_hashes` when the execution `result` is `Ok` (i.e., after confirming the transaction was actually processed by the OS, whether it reverted internally or not), and keep hard `Err` results exclusively in `rejected_tx_hashes` so the L1 provider always treats them as `Pending`/retryable, never as consumed. Additionally, verify (with full file access, given index limitations) that the L1 event provider's `commit_txs`/`apply_commit_block` logic correctly treats "hash present in both consumed and rejected" as "unstage and keep pending" rather than "mark consumed," and add a regression test asserting the L1-side message associated with a hard-failed L1 handler tx remains retryable in a subsequent block rather than being permanently dropped.

### Proof of Concept
1. Construct an `L1HandlerTransaction` whose target causes the executor to return `Err(TransactionExecutorError::StateError(StateError::OutOfRangeContractAddress))` (or any other hard executor error) rather than a normal revert, as done in the existing test `failed_l1_handler_transaction_consumed`: [3](#0-2) 
2. Observe that `result_block_artifacts.execution_data.consumed_l1_handler_tx_hashes` contains this tx hash even though it also appears in `rejected_tx_hashes`.
3. Trace forward into `commit_proposal_and_block`, where the L1 events provider is informed of the consumed set including this hash: [4](#0-3) 
4. Without full visibility into the L1 provider's internal transaction-state reconciliation (limited by index coverage), the risk is that this transaction is never resubmitted to a future block despite never having executed successfully, permanently stranding any value tied to the original L1 message.
