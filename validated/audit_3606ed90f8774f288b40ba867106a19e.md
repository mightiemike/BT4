### Title
Global-contract owner can silently rug-pull every account that "uses" an `AccountId`-mode global contract - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
NEP's `GlobalContractDeployMode::AccountId` lets an owner account publish a contract that other accounts reference by account id rather than by immutable code hash. Any account that later calls `UseGlobalContract` with `GlobalContractIdentifier::AccountId(owner)` permanently binds its `AccountContract` to `AccountContract::GlobalByAccount(owner)` — a live pointer, not a pinned code hash. The owner account can redeploy arbitrary new code under the same account id at any time; this instantly and irreversibly changes the executable code run in every subscriber account's context, with no additional consent, timelock, or notification to those subscribers.

### Finding Description
`use_global_contract` (runtime/runtime/src/global_contracts.rs:76-109) resolves `GlobalContractIdentifier::AccountId(id)` into `AccountContract::GlobalByAccount(id.clone())` [1](#0-0) , which is a reference by account id, not by a fixed code hash. `action_deploy_global_contract` (global_contracts.rs:25-63) allows the owning account to redeploy code under the same `GlobalContractDeployMode::AccountId` identifier at will [2](#0-1) ; the only access-control check applied is `check_actor_permissions`, which merely requires the transaction's actor to equal the deploying account itself (`Action::DeployGlobalContract(_) ... if actor_id != account_id => ActorNoPermission`) [3](#0-2)  — there is no restriction preventing that owner from later redeploying malicious code. The redeployment then propagates via `initiate_distribution`/`GlobalContractDistributionReceipt` to every shard (global_contracts.rs:143-171), and is picked up transparently by any account whose `AccountContract` still resolves via `GlobalByAccount(owner)` — the docs explicitly state this is intentional: "This allows the owner to update the contract for all its users" [4](#0-3) . Once malicious code is live, any `FunctionCall` receipt sent to a subscriber account executes that new code under the subscriber's own `current_account_id`, so it can issue promises (e.g. `Transfer`) that move the subscriber account's NEAR balance to an attacker-controlled account without any additional signature or access key from the victim — exactly analogous to the Graph `BridgeEscrow.approveAll()` issue where a privileged party can unilaterally redirect custody of funds it does not itself own.

### Impact Explanation
This is a Medium-severity, protocol-acknowledged trust concentration: an `AccountId`-mode global contract owner effectively becomes a "governor" over the balances of every account that opted into `UseGlobalContract` for that identifier. If the owner key is compromised, sold, or the owner turns malicious, it can push a backdoored contract update that drains NEAR from every subscriber account the next time a function call triggers execution — this is unauthorized value movement out of accounts that never directly authorized the new code, mirroring the reported analog where the Governor could `approveAll()` arbitrary spenders over escrowed funds.

### Likelihood Explanation
Likelihood is non-trivial but bounded by the same caveat the sponsor raised in the original report: this is intentional design to allow contract upgrades, and any account choosing `UseGlobalContract(AccountId(...))` implicitly trusts that owner's continued good behavior/key custody. Still, unlike the `CodeHash` mode (immutable, cryptographically pinned), the `AccountId` mode gives subscribers no way to detect or block an upcoming malicious update, and no on-chain mechanism exists (timelock, allowlist, opt-out) to protect already-subscribed accounts from a future rug — a single compromised or malicious owner key can affect an unbounded number of subscriber accounts across all shards in one transaction.

### Recommendation
Provide subscriber accounts a way to pin trust more precisely and reduce blast radius: (1) allow `UseGlobalContract` callers to pin a specific code hash *snapshot* of an `AccountId`-mode contract rather than always tracking the latest version, or provide a mechanism to migrate a `GlobalByAccount` reference to an explicit `CodeHash` reference locally; (2) consider a timelock/notice period before an `AccountId`-mode redeploy takes effect for existing subscribers, giving them a window to `UseGlobalContract` away or otherwise react; (3) at minimum, strongly document in the docs and in RPC/wallet UX that `UseGlobalContract(AccountId(...))` grants the named owner account perpetual, unilateral code-update authority over the calling account's execution logic and, transitively, its NEAR balance.

### Proof of Concept
1. Account `owner` deploys a benign contract via `DeployGlobalContractAction { deploy_mode: AccountId }` (see `test_global_contract_update`, test-loop-tests/src/tests/global_contracts.rs:71-97, which already demonstrates redeployment/update semantics) [5](#0-4) .
2. Victim accounts `v1`, `v2`, ... call `UseGlobalContract { contract_identifier: AccountId(owner) }`, setting `AccountContract::GlobalByAccount(owner)` on their own accounts (global_contracts.rs:95-98).
3. `owner` redeploys new code under the same `AccountId` mode containing a function such as `drain(target: AccountId)` that issues `Promise::new(target).transfer(env::account_balance())`.
4. Any relayer/attacker sends a `FunctionCall` receipt invoking `drain` against `v1`/`v2`; because the account's contract now resolves to the malicious code via the live `GlobalByAccount(owner)` pointer, the call executes with `v1`'s/`v2`'s own balance and transfers it to the attacker, with no signature from `v1`/`v2` required for that specific redeploy.
