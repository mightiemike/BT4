## Finding: Unauthorized UEA Execution via `IsCEA` Recipient Bypass — Gas Billed to Victim's UEA - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
The `IsCEA=true` inbound path lets an attacker name **any already-deployed UEA** as `Recipient`, completely decoupled from the depositing `Sender`. That `Recipient` is then handed to `ExecutePayloadV2` → `CallUEAExecutePayload`, invoked with `evmFrom = ueModuleAddr` (the trusted `uexecutor` module EVM address). Per the module's own documented authorization model, calls where `evmFrom == UNIVERSAL_EXECUTOR_MODULE` are the one case where the UEA contract's owner-signature check is not the attacker-facing gate — that gate is only guaranteed to fire "since `evmFrom != UNIVERSAL_EXECUTOR_MODULE`" [1](#0-0) . In the non-CEA path this is safe because the target `ueaAddr` is deterministically derived *from the same `Sender`* that the module is executing on behalf of [2](#0-1) . The `IsCEA` path breaks that binding: `ueaAddr` comes straight from attacker-controlled `Recipient`, checked only for "is this address a deployed UEA" via `CallFactoryGetOriginForUEA`, with **no relationship whatsoever to `Sender`** [3](#0-2) .

### Finding Description
1. Attacker performs a real deposit on a source chain (e.g. Sepolia gateway) with `TxType_FUNDS_AND_PAYLOAD`, `IsCEA=true`, `Sender=attacker`, `Recipient=<victim's already-deployed UEA address>`, and an arbitrary `UniversalPayload.Data`/`VerificationData` of the attacker's choosing.
2. Honest Universal Validators faithfully observe and vote this real event via `MsgVoteInbound`; nothing about the event is forged — it is exactly what happened on-chain, so honest-validator finalization converges normally.
3. `ValidateForExecution` only requires that `Recipient` be a non-empty valid hex address when `IsCEA` is set — it does not tie `Recipient` to `Sender` [4](#0-3) .
4. `ExecuteInboundFundsAndPayload` resolves `ueaAddr = Recipient` and only checks `isUEA` via `CallFactoryGetOriginForUEA`, again with no linkage to `Sender`'s origin [3](#0-2) .
5. `ExecutePayloadV2` is invoked with `evmFrom = ueModuleAddr` against the victim's UEA and the attacker's payload/`VerificationData` [5](#0-4) , which calls `CallUEAExecutePayload` [6](#0-5) .
6. Because the sender is the trusted `UNIVERSAL_EXECUTOR_MODULE` address, the owner-signature check inside the UEA contract that would otherwise block an unauthorized third party does not act as the gate here (per the documented rule that this check is guaranteed only for non-module `evmFrom`) [7](#0-6) . The attacker's arbitrary calldata therefore executes as the victim's UEA.
7. `DeductGasFeesFromReceipt` then bills the resulting gas cost against the victim UEA's native `upc` balance, burning it from the victim's account rather than the attacker's [8](#0-7) .

This violates the invariant that gas should be billed only to the account whose authorized call incurred it, and lets an attacker force unauthorized EVM execution as any deployed UEA of their choosing.

### Impact Explanation
- Direct native-balance drain of the victim's UEA (gas billed for calls the victim never authorized).
- Unauthorized execution as the victim's UEA — if the payload targets a PRC20/DEX/other contract where the UEA holds approvals or balances, the attacker can trigger transfers, approvals, or other state changes attributable to the victim's account.
- The `deposit` step (PRC20 mint into the victim's UEA) happens first and is uncorrelated with the attacker's payload, so the attacker doesn't even need to spend real value beyond gas/dust to grief a target — repeatable griefing against any known deployed UEA.

### Likelihood Explanation
High: it requires only an ordinary source-chain deposit transaction crafted by an unprivileged attacker, no validator or admin collusion, and validators need only relay the true observed event (honest-validator assumption holds).

### Recommendation
Bind the `IsCEA` `Recipient` to the `Sender`'s authorization the same way the non-CEA path does, or require `VerificationData` to be validated as a genuine owner signature regardless of `evmFrom`. At minimum, the module-trusted no-signature-check exception should never be reachable with an attacker-chosen `ueaAddr` that isn't cryptographically tied to the observed `Sender`.

### Proof of Concept
1. Deploy/identify a victim UEA `V` that already holds `upc` and/or token approvals.
2. From an attacker-controlled EOA on a supported source chain, submit a deposit/gateway event with `TxType_FUNDS_AND_PAYLOAD`, `IsCEA=true`, `Sender=attacker`, `Recipient=V`, `UniversalPayload.Data=<attacker-chosen calldata>`.
3. Drive the event through the normal 3-of-N honest validator `MsgVoteInbound` quorum.
4. Observe `ExecuteInboundFundsAndPayload` executes the payload against `V` and `DeductGasFeesFromReceipt` decrements `V`'s `upc` balance — confirm via `GetBalance` before/after, matching the pattern already exercised in `test/integration/uexecutor/inbound_cea_smart_contract_test.go:315-352` for the smart-contract analogue, but here targeting an unrelated pre-existing UEA rather than a contract the attacker "should" be allowed to invoke.

**Uncertainty note:** the actual owner-signature enforcement logic lives in the external `UEA_EVM.sol`/`UEA_SVM.sol` contracts (in the separate `push-chain-core-contracts` repo), which are not present in this repository's index. This assessment relies on the explicit behavioral description in `x/uexecutor/README.md` stating the signature check is guaranteed only when `evmFrom != UNIVERSAL_EXECUTOR_MODULE`; I could not directly inspect the Solidity source to confirm the exact bypass condition for `evmFrom == UNIVERSAL_EXECUTOR_MODULE`. Confirming this against the actual contract bytecode/source is recommended before treating this as fully proven.

```markdown
The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**

#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.

func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}

	gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
	if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
		return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
	}

	recipientAccAddr := sdk.AccAddress(recipient.Bytes())
	balance := k.bankKeeper.GetBalance(sdkCtx, recipientAccAddr, pchaintypes.BaseDenom)

	if err := k.DeductAndBurnFees(ctx, recipientAccAddr, gasCost); err != nil {
		return fmt.Errorf("insufficient gas: required %s upc, available %s upc, gas_used %d, from %s: %w",
			gasCost.String(), balance.Amount.String(), receipt.GasUsed, recipient.Hex(), err)
	}
```
