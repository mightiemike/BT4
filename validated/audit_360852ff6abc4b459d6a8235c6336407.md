### Title
Fixed-gas callback in the NEAR Wallet Contract can revert on out-of-gas, permanently freezing `has_in_flight_tx` and locking the account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract (NEP-518) that hosts ETH-implicit accounts uses a boolean flag `has_in_flight_tx` to serialize execution of `rlp_execute` calls, resetting it to `false` as the very first statement of every callback (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`). All of the promise chains that lead into `rlp_execute_callback` attach a **fixed** static gas budget (`RLP_EXECUTE_CALLBACK_GAS = Gas::from_tgas(5)`) regardless of how large the return value of the called action turns out to be.

### Finding Description
Every code path that calls `rlp_execute` and dispatches a Near action sets `has_in_flight_tx = true` before returning a `Promise`, and relies on the *following* callback to reset it back to `false`: [1](#0-0) 

The terminal callback that finally clears the flag is `rlp_execute_callback`, and its first statement is the reset: [2](#0-1) 

Crucially, `action_to_promise(...).then(ext.rlp_execute_callback(...))` schedules this callback with a **hard-coded** gas allowance: [3](#0-2) [4](#0-3) 

`rlp_execute_callback` copies the entire successful `PromiseResult::Successful(value)` into `ExecuteResponse.success_value` and returns it (which requires allocating, copying, and borsh/JSON-serializing that buffer): [5](#0-4) 

On NEAR, if a function-call receipt exceeds its attached/prepaid gas, the entire execution — including *all* state writes performed earlier in that same function — is rolled back, and only the base "function call" outcome (failure) is committed. Because the reset `self.has_in_flight_tx = false;` happens inside `rlp_execute_callback` itself, an out-of-gas failure in that callback reverts the reset along with everything else in the callback. The underlying action that was called by the promise chain (the `FunctionCall`/`Transfer` etc. issued via `action_to_promise`) has *already executed and committed as a separate receipt* before the callback runs, so the side effects of the user's intended action are not rolled back — only the wallet contract's own bookkeeping (`has_in_flight_tx` reset) is lost. This leaves `has_in_flight_tx == true` permanently.

Since `rlp_execute` unconditionally rejects any further call while `has_in_flight_tx` is `true`: [6](#0-5) 
there is no recovery path once the flag is stuck: every subsequent `rlp_execute` call for that ETH-implicit account will be rejected forever, effectively bricking the account.

The size of the value returned by an arbitrary contract that the wallet's `FunctionCall` action targets is attacker-influenced: any account the wallet interacts with (e.g., a token contract, or any callee chosen through the signed Ethereum-style transaction's `target`/`FunctionCall` action) can return an oversized successful value, or otherwise be crafted so the resulting downstream borsh/JSON serialization of `ExecuteResponse` inside the fixed 5 Tgas budget runs out of gas.

### Impact Explanation
If a user routes a `FunctionCall` action through the Wallet Contract to an account that returns a sufficiently large or gas-costly response, the `rlp_execute_callback` can exceed its statically allotted 5 Tgas, causing that callback receipt to fail with an out-of-gas error. Since the `has_in_flight_tx = false` reset is the first statement of the same function whose overall execution then fails, the reset is rolled back and the flag remains `true` indefinitely. The account can never successfully call `rlp_execute` again (it always short-circuits with "transaction already in progress"), which permanently freezes the ETH-implicit account from further use through the intended protocol — a denial-of-service that matches the "permanently frozen funds" / halt category, reachable purely by a normal transaction/contract-call from an unprivileged actor (the account owner interacting with an adversarial or buggy target contract), with no admin key, leaked key, or validator involvement required.

### Likelihood Explanation
Likelihood depends on whether it is actually possible, under NEAR's real per-byte/per-instruction gas costs, to exceed a 5 Tgas budget while just copying/serializing a `PromiseResult::Successful` payload and constructing the small `ExecuteResponse` struct. I was not able to fully confirm the exact numeric feasibility (i.e., the maximum allowed promise-return-value size versus the per-byte gas cost of borsh/JSON serialization at that size) within the available search tools, so this should be treated as a plausible but not fully proven root cause — it hinges on the callback being under-provisioned relative to worst-case return-value sizes, which is a known anti-pattern class in NEAR contracts (fixed-gas callback + attacker-influenced payload size).

### Recommendation
Scale `RLP_EXECUTE_CALLBACK_GAS` (and the derived `ADDRESS_CHECK_CALLBACK_GAS` / `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) to account for the maximum possible return-value size instead of using a fixed constant, or make `has_in_flight_tx` recovery not depend on this specific callback completing (e.g., a separate, minimal-gas final step whose only job is to clear the flag, or a timeout/self-healing mechanism that allows a legitimate user to force-clear a stuck flag after enough blocks have passed).

### Proof of Concept
1. Deploy the Wallet Contract for an ETH-implicit account `A`, and deploy/target a contract `B` (attacker- or third-party-controlled) whose method returns a value near the maximum allowed promise-return size.
2. From `A`, sign (and have a relayer submit) an RLP-encoded Ethereum transaction whose `FunctionCall` action targets `B`'s large-return method.
3. `inner_rlp_execute` → `action_to_promise` schedules the call to `B` then chains `rlp_execute_callback` with the fixed `RLP_EXECUTE_CALLBACK_GAS`.
4. `B`'s call succeeds and returns the large payload; `rlp_execute_callback` runs, sets `has_in_flight_tx = false`, but then runs out of gas while copying/serializing the large `success_value` into `ExecuteResponse`.
5. The callback receipt fails with an out-of-gas error, rolling back the `has_in_flight_tx = false` write; the flag is now stuck at `true`.
6. Any subsequent call to `rlp_execute` on account `A` immediately returns `"Error: transaction already in progress, please try again later."` and never succeeds again, permanently freezing the account.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
