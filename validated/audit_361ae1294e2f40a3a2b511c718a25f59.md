### Title
`replay_on_archive`'s per-transaction verification skips state-checkpoint/hot-state/position-state root comparison, letting divergent commit state pass replay verification - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by the `db-tool replay-on-archive` / replay-verify tooling to confirm that locally re-executed transaction outputs match the authenticated `TransactionInfo` recorded on-chain (the accumulator leaf). It explicitly omits comparison of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — fields that represent the authenticated Merkle roots of the ledger's state / hot-state / native-position state at that version. This is an acknowledged gap (the code contains a `TODO(trading-native)` comment stating exactly this), and it means replay verification can report success even when locally-recomputed state roots diverge from the on-chain committed roots.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  checks transaction status, gas used, write-set hash (`state_change_hash`), and event root hash against the archived `TransactionInfo`, but does not check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`: [2](#0-1) 

These three fields are exactly the fields that carry the authenticated Sparse-Merkle/Jellyfish state roots for the regular state tree, hot state tree, and native-position state tree, as defined on `TransactionInfoV1`: [3](#0-2) .

This comparator is the sole state-root check used by `db-tool`'s `replay_on_archive::Verifier::execute_and_verify`, which re-executes archived transactions with the real VM and calls `ensure_match_transaction_info` against the archived, ledger-committed `TransactionInfo` to flag divergence: [4](#0-3) . Because the checkpoint-hash fields are never included in that comparison, if VM execution logic or state-checkpoint computation diverges from the historically-committed values (e.g. after a code change, a non-deterministic bug in state-checkpoint materialization, or introduction of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state features), the replay tool will still report the transaction as "matching," even though the locally-computed state root differs from the authenticated on-chain root.

This differs from the equivalent commit-time and proof-verification code paths, which do bind proofs to `state_checkpoint_hash`/accumulator leaf hashes directly (e.g. `TransactionInfoWithProof::verify` via `verify_transaction_info`, which hashes the whole `TransactionInfo` including checkpoint hashes): [5](#0-4) . So while accumulator-proof verification itself is not broken (the leaf hash includes all fields), the dedicated regression/replay-integrity tool that is supposed to be the last line of defense for catching state divergence bugs before/after a hard fork silently ignores exactly the fields that matter most for detecting state-commitment corruption.

### Impact Explanation
Replay-verify is the primary tool operators and Aptos Labs use to confirm that a proposed VM/execution change reproduces the exact historical ledger state before it is shipped to mainnet validators. If a change corrupts state-checkpoint hash computation (state root, hot-state root, or the newer native-position state root) without also corrupting the write-set hash, event root, gas, or status, `replay_on_archive` would report a clean pass. This is precisely a "hard-fork-only divergence during commit/replay" risk item in scope: a bug that changes committed ledger state without being caught by the designated proof-integrity tooling, potentially reaching mainnet nodes and causing consensus/state divergence that is discovered only after the fact.

### Likelihood Explanation
The likelihood of the code path being exercised is high in the sense that it runs on every replay-verify invocation, but the likelihood of an actual state-root bug slipping through depends on there being an independent bug elsewhere (in state-checkpoint materialization) that changes the checkpoint hash but not the write-set/event data. The comment in the code itself acknowledges this exact scenario is a live concern ("even when the authenticated position state root diverges from local execution"), especially before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, which is an active in-progress feature per the surrounding `execution_output.rs` config flags [6](#0-5) .

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` against the locally-computed roots (when locally available/applicable), or thread through the corresponding checkpoint-hash computation so replay tooling fails loudly on any state-root divergence before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or any future state-root-bearing feature.

### Proof of Concept
Not independently exploitable as an on-chain attack (it requires an additional bug that changes checkpoint hash computation); the concrete verifiable defect is the code path itself:
1. `storage/db-tool/src/replay_on_archive.rs` re-executes transactions and calls `ensure_match_transaction_info` (lines 392–397).
2. `ensure_match_transaction_info` (types/src/transaction/mod.rs lines 2139–2204) never reads `expected_txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`.
3. Constructing a `TransactionOutput` whose write set, events, gas, and status match `expected_txn_info` exactly, but whose independently-computed state/hot-state/position-state checkpoint hash differs (simulate by mutating the state-checkpoint materialization logic or hand-crafting an `TransactionInfoV1` with a different `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` than what local execution would produce) results in `ensure_match_transaction_info` returning `Ok(())`, i.e. replay-verify reports success despite state-root divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

/// Verifies that a given `transaction_info` exists in the ledger using provided proof.
fn verify_transaction_info(
    ledger_info: &LedgerInfo,
    transaction_version: Version,
    transaction_info: &TransactionInfo,
    ledger_info_to_transaction_info_proof: &TransactionAccumulatorProof,
) -> Result<()> {
    ensure!(
        transaction_version <= ledger_info.version(),
        "Transaction version {} is newer than LedgerInfo version {}.",
        transaction_version,
        ledger_info.version(),
    );

    let transaction_info_hash = transaction_info.hash();
    ledger_info_to_transaction_info_proof.verify(
        ledger_info.transaction_accumulator_hash(),
        transaction_info_hash,
        transaction_version,
    )?;

    Ok(())
}
