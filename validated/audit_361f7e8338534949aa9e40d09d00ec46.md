### Title
Wallet Contract pays the relayer fee unconditionally before the target/action is validated, allowing fund loss even when the relayer is banned - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
In the ETH-implicit `WalletContract`, `inner_rlp_execute` fires an independent, un-gated `Transfer` promise that pays the relayer's requested fee *before* it is known whether the underlying action will even be attempted, let alone succeed. This is analogous to the reported Teller `CollateralEscrowV1` bug, where the escrow's internal accounting (`collateral._amount -= _amount`) was updated unconditionally even though the asset transfer (`transferFrom`) could silently fail — here the wallet unconditionally moves value (the fee) to the relayer even when the corresponding user action is subsequently rejected/banned.

### Finding Description
`inner_rlp_execute` decodes the user's signed Ethereum transaction and, for `EOABaseTokenTransfer` and `ERC20Transfer` emulation kinds, immediately creates and fires a fee-refund promise to the relayer (`context.predecessor_account_id`) as soon as `fee` is non-zero: [1](#0-0) 

This code block runs unconditionally for *both* variants of `EOABaseTokenTransfer` (with or without `address_check`), because the match only destructures `fee` via `..`. When `address_check` is `Some(address)`, the actual action is not sent directly — instead a lookup promise to the address registrar is scheduled and continues in `address_check_callback`: [2](#0-1) 

`address_check_callback` can determine the relayer supplied an invalid `target` (a faulty relayer) and instead of running the user's action, it schedules `create_ban_relayer_promise`, which deletes the relayer's key and returns a failure response: [3](#0-2) [4](#0-3) 

Because the fee-refund promise at lines 381-384 is created via `env::promise_batch_create`/`env::promise_batch_action_transfer` as a **separate, independent** promise (not chained with `.then()` off of the main action promise), it executes regardless of whether the subsequent lookup/callback determines the relayer is faulty and bans it. There is no mechanism to cancel or claw back this fee transfer once the later callback discovers the transaction should not proceed. The wallet's balance is debited for the relayer's fee even though: (a) the relayer is proven to be at fault and banned, and (b) the user's intended action (the base-token/ERC-20 transfer) never executes.

This mirrors the reported bug's root cause exactly: an accounting/value-moving step that is not conditioned on the actual success/validity of the corresponding operation, resulting in value loss with no automatic recovery path — the fee once sent to the relayer is not refunded to the wallet.

### Impact Explanation
Any transaction relayed through the Wallet Contract that includes a non-zero fee and requires an `address_check` (i.e., `target` is ambiguous / another eth-implicit account) results in the wallet unconditionally transferring the fee to the relayer *before* legitimacy of the relay is confirmed. If the relayer supplies an invalid `target`/mismatched address (whether maliciously or in error), the relayer is banned, the user's intended action is never carried out, yet the wallet has already lost the fee amount to the relayer with no refund — a concrete, unauthorized/unconditional value movement out of the user's wallet, unrecoverable through this transaction flow. Because `rlp_execute` is reachable by any relayer/RPC caller (not privileged), this is directly triggerable by an unprivileged actor.

### Likelihood Explanation
Likelihood is Medium: it requires a relay transaction with a non-zero fee that goes through the `address_check` path (target is another eth-implicit account) and where the registrar lookup subsequently classifies the relayer as faulty (banned). This is achievable by any relayer sending a malformed or misconfigured `target`, or as a side effect of relayer bugs, and does not require any privileged access — only a single `rlp_execute` call.

### Recommendation
Chain the relayer fee-refund promise off of the outcome of the underlying action (or defer its creation until after the target/`address_check` validation succeeds and the action promise is confirmed to have been scheduled), so that the fee is only paid when the corresponding action is actually attempted/succeeds. Alternatively, only create the fee-refund promise from within `rlp_execute_callback`/`address_check_callback` after confirming the relayer was not banned and the action promise did not fail.

### Proof of Concept
1. A relayer submits `rlp_execute(target, tx_bytes_b64)` where the decoded Ethereum transaction is an `EOABaseTokenTransfer` (or `ERC20Transfer`) with a non-zero `fee` and a `target` that is itself an eth-implicit account (so `address_check: Some(address)` is set by `parse_rlp_tx_to_action`).
2. `inner_rlp_execute` executes lines 374-385: since `fee` is non-zero and `predecessor_account_id != current_account_id`, it immediately fires `env::promise_batch_create` + `env::promise_batch_action_transfer(refund_promise, fee)` to the relayer.
3. Separately, it schedules the address-registrar lookup promise chained to `address_check_callback`.
4. In `address_check_callback`, the registrar reports that `target`'s address maps to an existing named account (i.e., the relayer picked the wrong `target`), so the code path at lines 161-173 creates `create_ban_relayer_promise`, deleting the relayer's key and returning `success: false`.
5. Result: the relayer's key is banned and the user's base-token/ERC-20 transfer never executes, but the fee transfer from step 2 already completed — the wallet's balance is permanently reduced by `fee` with no compensating action and no refund path in this call.

fn create_ban_relayer_promise(current_account_id: AccountId) -> Promise {
    let pk = env::signer_account_pk();
    Promise::new(current_account_id).delete_key(pk).function_call_weight(
        "ban_relayer".into(),
        Vec::new(),
        NearToken::from_yoctonear(0),
        Gas::from_tgas(1),
        GasWeight(1),
    )
}
