### Title
Receipt Size Limit Bypassed via `promise_return` and `value_return` Post-Validation Mutation — (`runtime/runtime/src/lib.rs`)

### Summary

The `max_receipt_size` invariant (4 MiB) can be violated by an unprivileged user through two execution paths in `process_action_receipt`. In both cases, a receipt passes `validate_receipt(..., NewReceipt)` at creation time, but is then mutated to exceed the limit before being emitted — with no re-validation. The nearcore team acknowledges this as an open bug (issue #12606) and has added a workaround (`ValidateReceiptMode::ExistingReceipt`) to prevent crashes, but the root cause is unfixed.

---

### Finding Description

**Path 1 — `promise_return` (action receipt mutation)**

In `runtime/runtime/src/lib.rs`, when a contract calls `promise_return(C)` and the parent receipt has non-empty `output_data_receivers`, the runtime appends those receivers directly to receipt C's `output_data_receivers` field after C has already been validated: [1](#0-0) 

Receipt C was validated at creation time with an empty `output_data_receivers`. After `extend_from_slice`, each appended `DataReceiver` adds ~70 bytes (two `AccountId`s + a `CryptoHash`). If C was crafted to be exactly at `max_receipt_size`, the mutation pushes it over the limit with no re-check.

**Path 2 — `value_return` (data receipt creation)**

When a contract returns a value and the parent receipt has `output_data_receivers`, a `DataReceipt` is created wrapping the full return value: [2](#0-1) 

`validate_data_receipt` only checks `max_length_returned_data` (4 MiB), not the total borsh-serialized receipt size: [3](#0-2) 

A return value of exactly 4 MiB produces a `DataReceipt` whose envelope (predecessor/receiver/receipt IDs) pushes the total borsh size above `max_receipt_size`.

**Acknowledged workaround, not a fix**

The `ValidateReceiptMode::ExistingReceipt` variant was added specifically because these oversized receipts reach the delayed-receipt queue and must be tolerated: [4](#0-3) 

The size check in `validate_receipt` is only applied for `NewReceipt` mode: [5](#0-4) 

---

### Impact Explanation

An oversized receipt bypasses the `max_receipt_size` protocol invariant. The receipt is serialized, merkle-proven, and stored in every node's trie. A receipt of, say, 8 MiB (two `output_data_receivers` appended to a max-size receipt) is processed by every shard node that receives it. This constitutes **contract execution flow breakage** (the size-limit guard is defeated) and a **non-network-level denial-of-service** (nodes must allocate and process unbounded receipt payloads, fixable without a hardfork by re-validating after mutation).

---

### Likelihood Explanation

Any user who can deploy a contract can trigger this. The test suite already contains a working end-to-end reproducer: [6](#0-5) [7](#0-6) 

---

### Recommendation

1. **Re-validate after mutation**: after `extend_from_slice` on `output_data_receivers` in the `promise_return` path, call `validate_receipt(..., NewReceipt)` on the mutated receipt and abort with an `ActionError` if it now exceeds `max_receipt_size`.
2. **Validate total DataReceipt size**: when constructing a `DataReceipt` from a return value, check `borsh::object_length(&new_receipt) <= max_receipt_size` before emitting it, not just `data.len() <= max_length_returned_data`.
3. Once the root cause is fixed, `ValidateReceiptMode::ExistingReceipt` can be tightened to enforce the size limit on all receipts.

---

### Proof of Concept

```
1. Deploy a contract that implements:
   - method1: creates promise A → promise_then → B, returns promise A
   - method2 (called as A): creates promise C with args sized to
     (max_receipt_size - base_receipt_size) bytes, calls promise_return(C)

2. Call method1. The DAG becomes [C → B].
   Receipt C passes validate_receipt(NewReceipt) at creation (size == max_receipt_size).
   When method2 executes, the runtime appends B's data_receiver to C's
   output_data_receivers, making C's borsh size > max_receipt_size.
   No re-validation occurs. C is emitted, stored, and processed.

3. Confirm via assert_oversized_receipt_occurred() that a receipt above
   max_receipt_size appears in the chain — as the existing test already does.
``` [8](#0-7) [9](#0-8)

    /// Used for validating new receipts that were just created.
    /// More strict than `OldReceipt` mode, which has to handle older receipts.
    NewReceipt,

    ///    to handle them gracefully until the receipt size limit bug is fixed.

    ExistingReceipt,

fn validate_data_receipt(
    limit_config: &LimitConfig,
    receipt: &DataReceipt,
) -> Result<(), ReceiptValidationError> {
    let data_len = receipt.data.as_ref().map(|data| data.len()).unwrap_or(0);
    if data_len as u64 > limit_config.max_length_returned_data {
        return Err(ReceiptValidationError::ReturnedValueLengthExceeded {
            length: data_len as u64,
            limit: limit_config.max_length_returned_data,
        });
    }
    Ok(())
}
