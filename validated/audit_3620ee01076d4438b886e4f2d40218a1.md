### Title
Replay-verify comparator (`ensure_match_transaction_info`) never checks the state-checkpoint / hot-state / position-state Merkle roots against the authenticated `TransactionInfo` — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole comparator used by `db-tool`'s archive replay-verify (`storage/db-tool/src/replay_on_archive.rs`) and by `aptos-debugger`'s mismatch reporting to decide whether a locally re-executed transaction output matches the authenticated (backed-up/archived) `TransactionInfo`. It checks status, gas, the write-set hash (`state_change_hash`) and the event root hash, but never compares the `state_checkpoint_hash` (nor `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) fields of `TransactionInfo` against the locally computed values.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  and checks only status, gas, write-set hash and event root hash. Its own inline comment acknowledges the gap: [2](#0-1) 

This function is the exact comparator invoked by the archive replay tool to decide "replay success/failure" per chunk: [3](#0-2) 

and by the debugger's mismatch printer: [4](#0-3) 

The `state_checkpoint_hash` field is the committed state-Merkle-tree root produced by `DoStateCheckpoint`/state-checkpoint transactions and is bound into the accumulator via `TransactionInfo` construction — see how it is populated during normal ledger update (`assemble_transaction_infos`) at [5](#0-4) . It is the value that ultimately proves the JMT/state root at a version. Because `ensure_match_transaction_info` skips it entirely, a replay session using `db-tool::replay_on_archive` (or the debugger's comparison utility) will report a transaction as fully verified even if the locally computed state root diverges from the archived, ledger-info-signed `TransactionInfo.state_checkpoint_hash` — as long as the write set, events, gas and status happen to match. This can occur on any state-computation divergence that does not manifest in the write set itself (e.g. divergent JMT/hot-state root derivation logic, a hard-fork-only bug in state root assembly, or storage-side corruption of the checkpoint hash path) while leaving the raw write set unaffected.

### Impact Explanation
Archive/backup replay-verify is the primary tooling operators and auditors use to assert that an archived ledger's committed state matches what independent re-execution produces — i.e., to catch state divergence, hard forks, or storage/replay corruption. Because the state-checkpoint (and hot-state/position-state) root is never verified, an operator running `replay_on_archive` gets a false "PASS" even when the authenticated state root has silently diverged from local re-execution. This directly undermines the "authenticated response/version-root binding" and "replay/restore must not reinterpret committed data into a different ledger state" invariants called out in the state-integrity gate, since the tool designed to catch exactly this kind of divergence structurally cannot.

### Likelihood Explanation
This does not require an attacker; it is a latent gap in the verification logic that is always present whenever the write set (and hence `state_change_hash`) itself is unaffected by a state-root computation bug or storage bug (e.g., a corrupted/incorrect state-checkpoint hash computed by `DoStateCheckpoint`, a hot-state root regression, or a native "position state" root bug — the comment explicitly names `COMPUTE_TRADING_NATIVE_STATE_ROOTS` as an upcoming feature this gap would silently pass). Since the checking function is a shared, general-purpose utility (used unconditionally, not just under a feature flag), the gap is live today for every replay-verify run, regardless of which optional features are enabled.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) between the locally computed output and the `TransactionInfo` from the archive/proof, failing verification on any mismatch, before enabling any feature (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that depends on this comparator for correctness.

### Proof of Concept
Not independently exploitable by an external attacker (no privileged/untrusted-input trigger); the finding is a structural verification gap demonstrated directly by the code and its own acknowledging comment:
1. Corrupt or diverge state-checkpoint-hash computation in a way that leaves the transaction's write set, events, gas, and status unchanged (e.g., a bug in `DoStateCheckpoint`'s root assembly, or in JMT/hot-state root computation).
2. Run `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which calls `ensure_match_transaction_info` at [6](#0-5) .
3. Observe that replay reports success (`Ok(None)`) despite the state root being wrong, because `state_checkpoint_hash` is never compared.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
