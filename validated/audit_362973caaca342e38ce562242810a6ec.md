**On the "CPU amplification" claim:** `FastByteComparisons.compareTo` operates on fixed-length TRON addresses (21 bytes), not attacker-controlled variable-length data. [1](#0-0) 
The comparison loop terminates at `min(length1, length2)` and is O(21) regardless of byte prefix similarity — there is no pathological worst case distinct from the best case for fixed 21-byte addresses; "long common prefixes" do not change the asymptotic or practical cost since the loop always runs to completion for equal-length arrays anyway. [2](#0-1) 
The claim about "30-byte shared prefixes" is inapplicable since TRON addresses are a fixed 21 bytes, so an attacker cannot construct longer comparison inputs to amplify cost.

**On the "double-processing" / "one-time-settlement" claim:** `UnfreezeBalanceProcessor.validate` explicitly checks that the delegated resource has a positive frozen balance before allowing execute to proceed: [3](#0-2) 
After `execute` runs once, it zeroes out the balance via `setFrozenBalanceForBandwidth(0, 0)` / `setFrozenBalanceForEnergy(0, 0)` and persists the update with `repo.updateDelegatedResource(key, delegatedResourceCapsule)`.

    private enum PureJavaComparer implements Comparer<byte[]> {
      INSTANCE;

      @Override
      public int compareTo(byte[] buffer1, int offset1, int length1,
          byte[] buffer2, int offset2, int length2) {
        // Short circuit equal case
        if (buffer1 == buffer2 &&
            offset1 == offset2 &&
            length1 == length2) {
          return 0;
        }
        int end1 = offset1 + length1;
        int end2 = offset2 + length2;
        for (int i = offset1, j = offset2; i < end1 && j < end2; i++,
            j++) {
          int a = (buffer1[i] & 0xff);
          int b = (buffer2[j] & 0xff);
          if (a != b) {
            return a - b;
          }
        }
        return length1 - length2;
      }
