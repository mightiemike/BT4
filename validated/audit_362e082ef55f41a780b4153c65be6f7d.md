### Title
Attacker-triggered dust deposit to old TSS address races the independent balance re-query in fund-migration signing verification, causing signing-hash mismatch and blocking/permanently stalling fund migration - ([File: universalClient/tss/sessionmanager/sessionmanager.go], [File: universalClient/chains/evm/tx_builder.go])

### Summary
The reported bug is a class of "attacker manipulates a balance-derived amount by racing an unprivileged, publicly-callable balance mutation against the protocol's own balance snapshot." Push Chain's TSS fund-migration flow reproduces the same fragile pattern: the sweep amount is derived from a live `GetBalance` query of a well-known public address (the old TSS EVM address), taken independently by the coordinator and by every session-manager verifier, rather than from one canonical, agreed-upon snapshot.

### Finding Description
When a fund migration is initiated, the coordinator builds the signing request by querying the *live* balance of the old TSS address: [1](#0-0) 
This flows into `GetFundMigrationSigningRequest`, which computes `maxTransfer = balance - gasCost - l1GasFee` and bakes it into `TSSFundMigrationAmount`, which becomes part of the TSS signing hash: [2](#0-1) 

Independently, every other Universal Validator's `SessionManager` re-derives the same signing request to verify the coordinator's proposal, calling `builder.GetFundMigrationSigningRequest(ctx, migrationFundData, req.Nonce)` with `Balance` left nil so it performs its own fresh `GetBalance` RPC call against the source chain: [3](#0-2) 

Because each participant queries live chain state at a different wall-clock moment (and potentially against a different RPC node), the old TSS address's balance is not a value the protocol pins to a specific, agreed block height for this purpose. The old TSS address is derivable by anyone from `OldTssPubkey`, which is emitted publicly in the `FundMigrationInitiatedEvent`: [4](#0-3) 

An unprivileged external attacker can therefore send an arbitrary small amount (dust) to the old TSS address on the external chain at any point after migration initiation and before/during the TSS signing ceremony. Any validator whose `GetBalance` call lands after the attacker's transfer computes a different `maxTransfer` (and thus a different `SigningHash`) than the coordinator (or than other validators who queried earlier), causing `verifyFundMigrationSigningRequest` to reject the coordinator's proposal: [5](#0-4) 

This mirrors the H-7 pattern precisely: a value used for a privileged/protocol "claim" operation (here, the sweep amount used for TSS-cosigning) is derived from an externally-influenceable, unprivileged balance mutation with no commitment to a fixed snapshot, so the attacker can repeatedly and freely deny the operation from succeeding.

### Impact Explanation
This is a repeatable, free, unprivileged denial-of-service against the fund-migration flow that is not network-level: an attacker sends a single tiny on-chain transfer to a publicly-known address on the source chain. If the attacker times/repeats this dust transfer for every migration attempt, the migration for that chain can be indefinitely blocked because signers keep disagreeing on the signing hash. Since fund migration exists specifically to move all remaining protocol/user funds out of the old TSS key before/after a TSS key rotation, and outbound is already disabled for that chain during migration (per `InitiateFundMigration`'s precondition checks), an attacker can strand protocol/user funds at the old TSS address indefinitely — a form of permanent freezing of protocol-controlled funds, matching the in-scope impact category. This is comparable in class (not necessarily severity) to the H-7 finding: an unprivileged, cost-free front-run of a balance-diff computation permanently denies a legitimate value-moving operation.

### Likelihood Explanation
Likelihood is high for the DoS/griefing effect: the old TSS address is discoverable from the on-chain `FundMigrationInitiatedEvent` (or from historical `TssKeyHistory`), sending a dust transaction on an external EVM chain is cheap and requires no special access, and the signing ceremony's multi-party nature only needs ONE validator's balance query to diverge from the coordinator's for the hash-mismatch rejection to fire. However, whether this results in true "permanent" fund loss versus a "retry" that eventually succeeds during a quiet window depends on operational retry logic not fully traced here (I was not able to confirm whether/how the coordinator retries a failed migration signing round, nor whether it eventually pins to a "finalized" block balance the way nonce lookups do via `useFinalized`). That mitigating detail is uncertain from the code reviewed.

### Recommendation
Pin the fund-migration balance to a single, deterministic value at protocol level instead of having each participant independently query "live" balance:
- Have the coordinator query balance at a specific, agreed block height (e.g., the finalized height at migration-initiation time), and encode that height (or the balance itself, authenticated) into the on-chain `FundMigrationInitiatedEventData` so all validators derive an identical value without a fresh RPC race.
- Alternatively, sweep the *entire* current balance at broadcast time (as Aura/Convex's recommended fix does — "use the entire balance instead of a before/after diff") rather than pre-computing a fixed amount that must match bit-for-bit across independently-timed queries.
- Add a bounded retry/backoff and a "settle-and-retry once" step when hash mismatches occur so a single dust transaction cannot indefinitely block migration.

### Proof of Concept
1. Observe (or await) an on-chain `FundMigrationInitiatedEvent` for chain `eip155:X`, extracting `OldTssPubkey` and deriving the old TSS EVM address via `DeriveEVMAddressFromPubkey`. [6](#0-5) 
2. As soon as migration initiates, submit a plain native-token transfer of 1 wei (or any small amount) to the old TSS address on the source chain.
3. The coordinator (or the first validator) queries the balance and builds `TSSFundMigrationAmount`/`SigningHash` at time T0 (before the dust lands). [7](#0-6) 
4. A different validator's `SessionManager.verifyFundMigrationSigningRequest` queries the balance at time T1 (after the dust lands), computing a different `maxTransfer`/`SigningHash`. [8](#0-7) 
5. The hash comparison fails, signing is rejected with `"fund migration signing hash mismatch"`, and the migration round fails. [5](#0-4) 
6. Repeat step 2 for each subsequent migration attempt to keep the funds stuck at the old TSS address.

// buildFundMigrationTransaction parses event data and returns the signing
// request for sweeping old-TSS funds to the current TSS. If claimedAmount is
// non-nil, the balance is reconstructed as amount + gas + L1 instead of
// queried from chain — used by the ACK verify path to rebuild the hash
// deterministically without racing a successful sweep.
func (c *Coordinator) buildFundMigrationTransaction(ctx context.Context, eventData []byte, assignedNonce *uint64, claimedAmount *big.Int) (*common.UnsignedSigningReq, error) {
	if assignedNonce == nil {
		return nil, fmt.Errorf("assigned nonce is required for fund migration transaction")
	}
	var migrationData utsstypes.FundMigrationInitiatedEventData
	if err := json.Unmarshal(eventData, &migrationData); err != nil {
		return nil, fmt.Errorf("unmarshal fund migration event data: %w", err)
	}
	oldTSSAddr, err := DeriveEVMAddressFromPubkey(migrationData.OldTssPubkey)
	if err != nil {
		return nil, fmt.Errorf("derive old TSS address: %w", err)
	}
	currentTSSAddr, err := DeriveEVMAddressFromPubkey(migrationData.CurrentTssPubkey)
	if err != nil {
		return nil, fmt.Errorf("derive current TSS address: %w", err)
	}
	if c.chains == nil {
		return nil, fmt.Errorf("chains manager not configured")
	}
	client, err := c.chains.GetClient(migrationData.Chain)
	if err != nil {
		return nil, fmt.Errorf("get client for chain %s: %w", migrationData.Chain, err)
	}

func (tb *TxBuilder) GetFundMigrationSigningRequest(ctx context.Context, data *common.FundMigrationData, nonce uint64) (*common.UnsignedSigningReq, error) {
	fromAddr := ethcommon.HexToAddress(data.From)
	toAddr := ethcommon.HexToAddress(data.To)

	if data.GasPrice == nil || data.GasPrice.Sign() == 0 {
		return nil, fmt.Errorf("gas price must be provided for fund migration")
	}
	if data.GasLimit == 0 {
		return nil, fmt.Errorf("gas limit must be provided for fund migration")
	}

	var balance *big.Int
	if data.Balance != nil {
		balance = new(big.Int).Set(data.Balance)
	} else {
		queried, err := tb.rpcClient.GetBalance(ctx, fromAddr)
		if err != nil {
			return nil, fmt.Errorf("failed to get balance of %s: %w", data.From, err)
		}
		balance = queried
	}

	maxTransfer, err := computeFundMigrationTransfer(balance, data.GasPrice, data.GasLimit, data.L1GasFee)
	if err != nil {
		return nil, err
	}

	tb.logger.Debug().
		Str("from", data.From).
		Str("to", data.To).
		Str("balance", balance.String()).
		Str("gas_price", data.GasPrice.String()).
		Uint64("gas_limit", data.GasLimit).
		Str("l1_gas_fee", l1GasFeeString(data.L1GasFee)).
		Str("transfer_amount", maxTransfer.String()).
		Msg("building fund migration tx")

	tx := types.NewTransaction(
		nonce,
		toAddr,
		maxTransfer,
		data.GasLimit,
		data.GasPrice,
		nil, // no calldata for simple transfer
	)

	signer := types.NewEIP155Signer(big.NewInt(tb.chainIDInt))
	txHash := signer.Hash(tx).Bytes()

	// TSSFundMigrationAmount rides alongside Nonce in the req — both are signing-time-decided
	// values that must reach broadcast unchanged so the signed tx is reproduced exactly.
	return &common.UnsignedSigningReq{
		SigningHash:            txHash,
		Nonce:                  nonce,
		TSSFundMigrationAmount: new(big.Int).Set(maxTransfer),
	}, nil
}
