### Title
Deterministic Contract Address Formula Allows Permissionless Squatting/Front-Running of Counterfactual Account Addresses - (File: `crates/starknet_api/src/core.rs`, `crates/blockifier/src/execution/syscalls/syscall_base.rs`)

### Summary
Starknet's contract address derivation is fully deterministic: `contract_address = f(salt, class_hash, constructor_calldata, deployer_address)`. For `DeployAccountTransaction`, `deployer_address` is hardcoded to `ContractAddress::ZERO` [1](#0-0) . Crucially, the exact same formula with the exact same zero deployer address is reachable by *any* unprivileged contract via the plain `deploy` syscall when `deploy_from_zero=true` [2](#0-1) . Since `salt`, `class_hash`, and `constructor_calldata` for a not-yet-deployed account are public/predictable (this is the entire point of "counterfactual" account addresses used to fund an account before it deploys itself), any third party can pre-compute the future account address and deploy an arbitrary contract to that exact address first, permanently blocking the legitimate `DeployAccountTransaction` from ever succeeding at that address.

### Finding Description
The contract address is computed the same way regardless of which mechanism triggers the deployment:
- `DeployTransactionTrait`/`CalculateContractAddress` used by `DeployTransaction`/`DeployAccountTransaction` always uses `DEPLOYER_ADDRESS = ContractAddress(PatriciaKey::ZERO)` [1](#0-0) .
- The generic `deploy` syscall (reachable from any Cairo contract via an ordinary `invoke` transaction) computes `deployer_address_for_calculation = ContractAddress::default()` whenever the caller passes `deploy_from_zero = true` [2](#0-1) . The same logic exists in the deprecated syscall path [3](#0-2)  and in the Starknet OS Cairo implementation used for re-execution/proving [4](#0-3) .

Because both paths converge on the identical `calculate_contract_address(salt, class_hash, constructor_calldata, ContractAddress::ZERO)` formula, an attacker who observes/predicts the `(salt, class_hash, constructor_calldata)` tuple a user intends to use for a future `DeployAccountTransaction` (this data is typically public — SDKs derive `salt` from a public key, and the account class hash/constructor calldata are standard/well-known) can invoke `deploy_syscall(class_hash, salt, constructor_calldata, deploy_from_zero=true)` from any already-deployed contract they control. This deploys *some* contract (even an empty/junk one) to the exact address the victim's future account is supposed to occupy.

Once an address has a non-zero class hash recorded in state, any subsequent attempt to deploy to it fails, as demonstrated by the existing test `test_deploy` (`available_for_deployment=false` → `"Deployment failed:"`) [5](#0-4) . This means the legitimate `DeployAccountTransaction` for the victim's intended address will subsequently revert/fail every time it is submitted — the address is now permanently squatted.

This directly mirrors the reported bug class: a deterministic identifier (there, an object ID; here, a contract address) is derived off-chain/predictably from inputs the eventual "owner" chooses, but nothing on the sequencer/protocol level prevents an unrelated, unprivileged party from reaching the same identifier first through an alternate permissionless code path (there, `payDividendFromEntity`; here, the generic `deploy` syscall with `deploy_from_zero`), permanently precluding the legitimate use of that identifier.

### Impact Explanation
Starknet's standard account-abstraction UX relies on counterfactual deployment: users (or paymasters/dApps) transfer funds to a precomputed account address *before* that account is deployed, then submit `DeployAccountTransaction` to actually deploy it (charging deployment/first-tx fees from the pre-funded balance) — this pattern is directly exercised in this codebase's own test helpers (`add_fund_address_tx_with_default_amount` followed by a `DeployAccountTransaction` targeting the same precomputed address) [6](#0-5) . If an attacker squats that address beforehand via the `deploy` syscall, the funds already sent to the precomputed address become permanently inaccessible: the real account's constructor (and thus its signature-validation logic and owner key material) can never be deployed there since the address slot is already occupied by the attacker's contract. This is a concrete, permanent freezing-of-funds condition reachable purely by an unprivileged transaction sender using a standard syscall, matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Exploitation requires no special privilege — only knowledge of the victim's future `(class_hash, contract_address_salt, constructor_calldata)`, which is by design public/predictable for counterfactual deployment flows (e.g., deterministic salts derived from public keys, well-known account class hashes, and standard constructor calldata). The attacking transaction is a single ordinary `invoke` call to any already-deployed contract's `deploy_syscall` wrapper (as exercised by the codebase's own test contracts, e.g. `test_deploy`) [7](#0-6) , requiring only enough gas to pay for the syscall — a trivial and cheap operation to front-run any specific, valuable, targeted account address.

### Recommendation
- Consider whether the `deploy` syscall's `deploy_from_zero` option should be restricted or whether `deployer_address_for_calculation` for `deploy_from_zero=true` should incorporate additional entropy (e.g., a component of the caller's context) so a generic contract call cannot land on the exact same address space reserved for zero-deployer (account) deployments.
- Alternatively/complementarily, document and mitigate at the wallet/SDK level: encourage funding flows that do not send value to a not-yet-deployed address computed from fully public/guessable parameters, or require salts to include additional unpredictable/private entropy known only to the intended owner until deployment time.
- This is a protocol-design-level tradeoff (similar to Ethereum's CREATE2 front-running concerns) and needs an explicit risk-acceptance decision, but should at minimum be documented so client/SDK implementers avoid patterns where meaningful value is exposed to squatting before deployment.

### Proof of Concept
1. Off-chain, compute the future account address for a target user: `addr = calculate_contract_address(salt, account_class_hash, constructor_calldata, ContractAddress::ZERO)`, using the same public `salt`/`class_hash`/`calldata` conventions the target's wallet SDK will use (this mirrors the codebase's own test helper pattern) [8](#0-7) .
2. From any already-deployed attacker-controlled contract, submit an ordinary `invoke` transaction calling `deploy_syscall(account_class_hash, salt, constructor_calldata, deploy_from_zero=true)` (as the `test_deploy` entry point does) [7](#0-6) . Blockifier will compute `deployer_address_for_calculation = ContractAddress::default()` and deploy to the identical `addr` [2](#0-1) .
3. The target user later submits their intended `DeployAccountTransaction` with the same `salt`/`class_hash`/`constructor_calldata`. Its `calculate_contract_address()` yields the same `addr`, which now already has a non-zero class hash — the deployment fails, matching the `"Deployment failed:"` behavior already covered by the existing test suite for occupied addresses [5](#0-4) , and any funds pre-sent to `addr` remain permanently stranded.

impl<T: DeployTransactionTrait> CalculateContractAddress for T {
    /// Calculates the contract address for the contract deployed by a deploy account transaction.
    /// For more details see:
    /// <https://docs.starknet.io/architecture-and-concepts/smart-contracts/contract-address/>
    fn calculate_contract_address(&self) -> StarknetApiResult<ContractAddress> {
        // When the contract is deployed via a deploy-account transaction, the deployer address is
        // zero.
        const DEPLOYER_ADDRESS: ContractAddress = ContractAddress(PatriciaKey::ZERO);
        calculate_contract_address(
            self.contract_address_salt(),
            self.class_hash(),
            self.constructor_calldata(),
            DEPLOYER_ADDRESS,
        )
    }
