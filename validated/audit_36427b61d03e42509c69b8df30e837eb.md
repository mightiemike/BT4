### Title
Global-contract distribution nonce is permanently advanced even when the deploying receipt fails or is rolled back, causing legitimate redeploys to be silently dropped - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`initiate_distribution` in `action_deploy_global_contract` writes an incremented "distribution nonce" directly to `state_update` via `increment_nonce`/`set_nonce`, independent of the `ActionResult` (`result.new_receipts`) that actually carries the corresponding `GlobalContractDistributionReceipt`. If the action later in the same receipt causes the receipt to fail (`ActionResult::set_error`, which clears `new_receipts`), or the receipt/transaction is otherwise rejected and its state changes discarded, the nonce write to state can still diverge from the receipt that was supposed to consume it — the "resource" (the nonce slot and the intended distribution) is allocated/incremented but the corresponding distribution receipt is never actually sent, i.e. never freed/used, permanently and irrecoverably stranding that nonce value. ### Finding Description
`action_deploy_global_contract` (runtime/runtime/src/global_contracts.rs:25) charges storage cost from the account and then calls `initiate_distribution`, which computes the global contract identifier, calls `increment_nonce` (which reads the current stored nonce and immediately `set_nonce`s the incremented value into `state_update`), and then pushes a `GlobalContractDistributionReceipt` carrying that nonce into `result.new_receipts`: [2](#0-1) 

The nonce write happens via `state_update.set(...)` (through `set_nonce`), a direct, unconditional trie write, not gated behind the success of the whole action/receipt the way `result.new_receipts` is. `ActionResult::set_error` (runtime/runtime/src/lib.rs:535) explicitly documents that on a later action failure within the same receipt, `new_receipts` is cleared to avoid "receipt-scoped state that would otherwise leak across the failure boundary" — but this comment and the discard logic only covers the `ActionResult` fields, not writes already staged into `state_update` by a *prior successful* action such as `action_deploy_global_contract`.

Because `apply_action` is called once per action within a multi-action receipt (runtime/runtime/src/lib.rs:571), and `Action::DeployGlobalContract` writes to `state_update` unconditionally as soon as it runs (before any later action in the same receipt fails), a receipt with `[DeployGlobalContract, X]` where `X` fails afterward will have already staged the nonce increment into `state_update`. The intended companion object of that increment — the `GlobalContractDistributionReceipt` that must arrive with the matching nonce to write the code into the trie via `apply_distribution_current_shard`/`check_and_update_nonce` (runtime/runtime/src/global_contracts.rs:191-269) — lives only in `result.new_receipts`, which is discarded by `set_error` when the receipt fails.

This is the direct structural analog of the reported bug class: an object/counter is allocated ("mlx4_srq_alloc") on one code path, but the corresponding cleanup/undo ("mlx4_srq_free") that should happen together with it on the error path is missing — here, the nonce increment (the "resource") is committed to persistent state unconditionally, but the receipt meant to "consume" that nonce and actually complete the deployment is dropped on failure, with no code path that decrements/restores the nonce.

### Impact Explanation
Once the nonce for a given `GlobalContractIdentifier` (by code hash or by account id) is advanced past a value for which no distribution ever completed, any subsequent legitimate `DeployGlobalContract` attempt with a lower or equal "fresh" nonce is permanently treated as stale by `check_and_update_nonce` (`incoming_nonce < stored_nonce` → rejected). This can permanently prevent an account from (re)deploying a global contract under `GlobalContractDeployMode::AccountId`, since every new deploy from that account starts its own `initiate_distribution` call, which reads-and-increments the *same* stored nonce (`TrieKey::GlobalContractNonce`) — a value that can be bumped arbitrarily by an attacker triggering the failure path repeatedly (e.g., pairing `DeployGlobalContract` with an action that reliably fails, such as insufficient gas/balance for the next action) without the corresponding distribution ever landing. This causes state divergence between the intended protocol invariant ("every nonce increment corresponds to exactly one committed distribution") and reality, and results in a form of permanently frozen functionality: an account's global-contract slot becomes unusable for future legitimate updates, and the excess nonce increments are irrecoverable garbage in state that no operation can decrement.

### Likelihood Explanation
This is reachable by an unprivileged contract deployer/transaction signer with a single crafted transaction: submit a batch receipt containing `Action::DeployGlobalContract` followed by any action that is made to fail deterministically (e.g., a `FunctionCall` action with the wrong receiver/permission, or one that runs out of attached gas) in the same receipt. Because `check_actor_permissions`/action ordering rules allow at least some multi-action batches (as documented in the codebase's own test suite around "actions before init fail gracefully" and rollback tests), a signer only needs the ability to submit a multi-action transaction, which is standard capability of any account. No validator, network, or privileged access is required.

### Recommendation
`initiate_distribution`'s nonce increment must be tied to the same commit/rollback boundary as the rest of the receipt's effects. Either (a) defer the `increment_nonce`/`set_nonce` write until it is known the whole receipt will succeed (e.g., stage it in `ActionResult` alongside `new_receipts` and only flush it to `state_update` when the receipt is not going to be discarded by `set_error`), or (b) make `set_error` (or the receipt-level rollback path in `apply_action_receipt`) explicitly roll back any global-contract-nonce writes made by actions processed earlier in the same failed receipt, mirroring how `new_receipts`/`validator_proposals`/burnt amounts are already cleared. Additionally, consider whether `TrieUpdate`'s existing prepare/commit/rollback semantics (used elsewhere, e.g., in `apply_distribution_current_shard`'s explicit `state_update.commit(...)`) should be applied consistently here so an uncommitted nonce write is naturally discarded on receipt failure instead of leaking into the final state.

### Proof of Concept
1. Attacker deploys account `attacker.near` with sufficient balance.
2. Attacker submits a transaction from `attacker.near` to `attacker.near` containing actions: `[DeployGlobalContract{code, deploy_mode: AccountId}, FunctionCall{... gas too low to succeed, or a call guaranteed to panic}]`.
3. `apply_action` processes `DeployGlobalContract` first: `action_deploy_global_contract` succeeds, calling `initiate_distribution`, which calls `increment_nonce` — this writes the incremented nonce for `GlobalContractIdentifier::AccountId(attacker.near)` directly to `state_update`, and stages a `GlobalContractDistributionReceipt` in `result.new_receipts`.
4. `apply_action` then processes the second action, which fails; the receipt overall fails and `set_error` clears `result.new_receipts` for the *whole receipt's* aggregated `ActionResult` — the distribution receipt carrying the incremented nonce is never sent, but the nonce write already staged into `state_update` from step 3 persists into the finalized state (since it was written directly, not through the `ActionResult` that gets cleared).
5. Repeating this batch N times advances the stored nonce by N with zero successful distributions.
6. Attacker (or the legitimate owner) now issues a normal, single-action `DeployGlobalContract{AccountId}` transaction that would have succeeded before — its resulting distribution receipt carries `nonce = stored_nonce_before + 1`, but if further such failed batches race ahead of it, or if the account's true redeploy nonce sequence is bypassed this way, the account's global contract slot can be pushed into a nonce state that legitimate future deploys can never catch up to being treated as "fresh" (`incoming_nonce < stored_nonce` guard in `check_and_update_nonce`), permanently blocking further global contract updates from that identifier.

*Note: I was not able to fully trace whether `apply_action_receipt`'s outer receipt-processing loop discards uncommitted `TrieUpdate` writes on receipt failure via a `state_update.rollback()`/prepare-checkpoint mechanism (the tool budget was exhausted before locating that exact rollback call), so it is not 100% confirmed from code alone whether the nonce write actually survives receipt failure or is already rolled back by the surrounding infrastructure. This is the key remaining uncertainty for definitively confirming exploitability; a background agent with full repository access should verify the `TrieUpdate` checkpoint/rollback behavior in `runtime/runtime/src/lib.rs`'s `apply_action_receipt` around action failure before treating this as a confirmed, unmitigated vulnerability.*

```rust
fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}
```
