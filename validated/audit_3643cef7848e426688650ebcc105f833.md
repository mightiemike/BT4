### Title
Unclamped negative `remainWindowSize` in `ResourceProcessor.increaseV2` corrupts `WindowSizeV2` bandwidth/energy accounting - ([File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java])

### Summary
In `increaseV2` (lines 133-188), `remainWindowSize = oldWindowSizeV2 - (now - lastTime) * WINDOW_SIZE_PRECISION` is computed without any lower-bound clamp, then fed into the `newWindowSize` weighted-average formula and stored via `accountCapsule.setNewWindowSizeV2`. Because `oldWindowSizeV2` can be smaller than `oldWindowSize * WINDOW_SIZE_PRECISION` (its own theoretical max) after prior delegation/blend operations, a sufficiently large but still "in-window" idle gap (`now - lastTime`) lets `remainWindowSize` go negative while still taking the non-zero-`remainUsage` code path, producing a negative or otherwise corrupted `newWindowSize` value persisted to account state.

### Finding Description
`increaseV2` first computes `remainUsage = getUsage(averageLastUsage, oldWindowSize)` [1](#0-0) . If the idle gap is large enough that `lastTime + oldWindowSize <= now`, `averageLastUsage` is forced to `0`, `remainUsage` becomes `0`, and the method takes the early-return branch that resets the window to the safe maximum (`this.windowSize * WINDOW_SIZE_PRECISION`), avoiding the bug.

However, when `lastTime + oldWindowSize > now` (i.e., the account is idle but still technically "inside" the plain `oldWindowSize` in block units), decay is applied and `remainUsage` stays non-zero, so execution falls through to: [2](#0-1) 
Here `remainWindowSize = oldWindowSizeV2 - (now - lastTime) * WINDOW_SIZE_PRECISION` has no `max(..., 0)` clamp — unlike `min(newWindowSize, this.windowSize * WINDOW_SIZE_PRECISION, ...)` applied to the upper bound on line 184. Because `oldWindowSizeV2` is a *scaled* windowed average that can be smaller than `oldWindowSize * WINDOW_SIZE_PRECISION` (e.g., after a prior `unDelegateIncreaseV2` blend with a shorter receiver window), it is possible for `(now - lastTime) * WINDOW_SIZE_PRECISION` to exceed `oldWindowSizeV2` while still satisfying `now - lastTime < oldWindowSize` (the gating condition for the non-zero branch). In that case `remainWindowSize` is negative, and it directly multiplies `remainUsage` in the `newWindowSize` numerator, which can drive the final `newWindowSize` negative (especially when the new `usage` in the same call is small, e.g. a trivial freeze/delegate/consume), and this negative value is persisted via `accountCapsule.setNewWindowSizeV2(resourceCode, newWindowSize)`.

Notably, the sibling method `unDelegateIncreaseV2` explicitly clamps the analogous quantities: `remainOwnerWindowSizeV2 = remainOwnerWindowSizeV2 < 0 ? 0 : remainOwnerWindowSizeV2;` and the same for the receiver [3](#0-2) . This shows the developers were aware that windowSizeV2-derived deltas can go negative and require clamping — but the equivalent clamp is missing in `increaseV2`.

### Impact Explanation
A negative or corrupted `WindowSizeV2` value is written into persistent account state used by future `increaseV2`/`recovery` calls as `oldWindowSizeV2`, and factors into bandwidth/energy limit and usage recovery math throughout `ResourceProcessor`. This corrupts faithful resource metering for the affected account (self, or a delegation receiver whose windowSizeV2 is blended in via `unDelegateIncreaseV2`), leading to under- or over-metered bandwidth/energy limits — a state-accounting corruption bug (TRON bounty class: "asset/accounting corruption" / state corruption via the protocol implementation), not a direct fund theft.

### Likelihood Explanation
Preconditions: `supportAllowCancelAllUnfreezeV2` must be enabled (mainnet-default post-fork feature, not a special node config) and the account's `WindowSizeV2` must have been previously blended to a value below `oldWindowSize * WINDOW_SIZE_PRECISION` (achievable via normal delegate/undelegate resource operations, which are ordinary unprivileged actions). The attacker needs only: (1) freeze/delegate once to establish usage and a shrunk `WindowSizeV2`, (2) remain idle for a specific number of blocks (bounded, computable from `oldWindowSizeV2` and `WINDOW_SIZE_PRECISION`), (3) issue any trivial resource-consuming transaction. All steps use ordinary funded-account transactions with normal fees; no special privilege or non-default config is required. This is repeatable and only requires reproducing the exact timing window found via the `increase()`/`increaseV2()` arithmetic — no signature/permission checks intervene since this logic runs unconditionally during normal resource accounting on any transaction the account submits.

### Recommendation
Clamp `remainWindowSize` to a non-negative value before using it in the weighted-average computation, mirroring the existing pattern in `unDelegateIncreaseV2`:
```java
long remainWindowSize = oldWindowSizeV2 - (now - lastTime) * WINDOW_SIZE_PRECISION;
remainWindowSize = remainWindowSize < 0 ? 0 : remainWindowSize;
```
Add regression tests asserting `newWindowSize >= 0` and `newWindowSize <= windowSize * WINDOW_SIZE_PRECISION` across randomized `lastTime`/`now`/`oldWindowSizeV2` combinations, including cases where `oldWindowSizeV2 < oldWindowSize * WINDOW_SIZE_PRECISION`.

### Proof of Concept
```java
// JUnit-style PoC targeting ResourceProcessor.increaseV2
@Test
public void testIncreaseV2RemainWindowSizeCanGoNegative() {
  dbManager.getDynamicPropertiesStore().saveAllowCancelAllUnfreezeV2(1);
  dbManager.getDynamicPropertiesStore().saveUnfreezeDelayDays(14);

  // Simulate a prior blend (e.g. via unDelegateIncreaseV2) that left
  // WindowSizeV2 below oldWindowSize * WINDOW_SIZE_PRECISION.
  long oldWindowSize = 28800L;                     // plain block-unit window
  long shrunkWindowSizeV2 = 1000L * WINDOW_SIZE_PRECISION; // « oldWindowSize * PRECISION
  long lastUsage = 1_000_000L;
  long lastTime = 10000L;
  // choose delta so that: delta < oldWindowSize (non-zero remainUsage branch)
  //                       but delta * PRECISION > shrunkWindowSizeV2
  long delta = 1500L;
  long now = lastTime + delta;

  ownerCapsule.setNewWindowSize(ResourceCode.ENERGY, oldWindowSize);
  ownerCapsule.setNewWindowSizeV2(ResourceCode.ENERGY, shrunkWindowSizeV2);
  ownerCapsule.setLatestConsumeTimeForEnergy(lastTime);
  ownerCapsule.setEnergyUsage(lastUsage);

  processor.increaseV2(ownerCapsule, ResourceCode.ENERGY,
      lastUsage, /*usage=*/1L, lastTime, now);

  long newWindowSize = ownerCapsule.getWindowSizeV2(ResourceCode.ENERGY);
  Assert.assertTrue("newWindowSize must not be negative, got " + newWindowSize,
      newWindowSize >= 0);
}
```
Expected (buggy) result: `newWindowSize` computed from the code path is negative, failing the assertion, confirming that `increaseV2` can write a corrupted `WindowSizeV2` into account state.
