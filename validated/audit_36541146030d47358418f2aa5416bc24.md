## Finding: `TransactionOutput::ensure_match_transaction_info` accepts checkpoint hash divergence in chunk replay verification

### Title
Transaction replay verification does not validate state-checkpoint / hot-state / position-state root hashes against the authenticated `TransactionInfo` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the routine used by chunk execution, replay-verify tooling, and the Aptos debugger/CLI to confirm that a locally re-executed transaction produces the same result as the authenticated on-chain `TransactionInfo` embedded in a proof. It validates status, gas used, write-set hash, and event root hash, but **explicitly skips validation of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`**, as flagged by its own inline `TODO`.

### Finding Description [1](#0-0) 

The function checks:
- `status`
- `gas_used`
- `write_set` hash vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

then explicitly stops, with the comment: [2](#0-1) 

> "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This function is invoked from the real commit/verification paths, not just tests: [3](#0-2) 
and also from `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`, and `storage/db-tool/src/replay_on_archive.rs`.

The `state_checkpoint_hash` is precisely the field meant to bind a `TransactionInfo` to the resulting Jellyfish Merkle / state-summary root produced by applying the write set — the exact invariant class called out in the task ("accumulator root hash accepted as valid," "state that differs from correct VM result," "proof-bearing responses bound to right root"). Because this comparator does not check it, any divergence between the locally computed state root (from `DoStateCheckpoint`/state summary) and the value embedded in the authenticated `TransactionInfo` from a synced ledger will not be surfaced by this check.

### Impact Explanation
If the locally computed state-checkpoint root ever diverges from the authenticated `TransactionInfo.state_checkpoint_hash` (e.g., due to a bug in a new feature such as the "trading-native"/position-state code path referenced in the comment, a JMT restore bug, or a non-deterministic execution bug), replay-verify tooling and chunk executor validation used as a safety net will **not detect it** and will report success. This is a genuine proof/commitment-integrity gap: state that differs from the correct VM result can be silently accepted as validated, defeating the purpose of `ensure_match_transaction_info` as an integrity check on synced/replayed chunks.

### Likelihood Explanation
This is a real, un-guarded gap in already-shipped code — it is not a hypothetical: the TODO explicitly states the tool "can report a successful replay even when the authenticated position state root diverges from local execution." It is gated behind the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag context per the comment, meaning today the checkpoint hash comparison for this code path is a known, deliberate omission awaiting completion. Its current impact is real for any state-checkpoint bug for the standard state checkpoint hash too, since none of the three fields are checked at all (not just the position-state-specific one) — the code checks none of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s locally computed `state_checkpoint_hash` (and, once available, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) against `txn_info.state_checkpoint_hash()` (and the corresponding fields), returning an error on mismatch exactly as done for the write-set and event root hash checks, before enabling any feature that depends on these being trustworthy (e.g., `COMPUTE_TRADING_NATIVE_STATE_ROOTS`).

### Proof of Concept
Not independently exploitable as a state-corruption primitive by itself (it is a missing detection, not a state-mutation bug); the concrete demonstration is the code path itself:
1. Run replay-verify/chunk-executor with a locally computed state root that differs from the on-chain `TransactionInfo.state_checkpoint_hash` for a given transaction (e.g., by injecting a divergent local state root in a test).
2. Observe that `ensure_match_transaction_info` returns `Ok(())` because it never reads `self`'s computed checkpoint hash or compares it to `txn_info.state_checkpoint_hash()`.
3. Downstream tooling (`replay_on_archive`, `aptos-debugger`) reports the replay as matching despite the ledger-state divergence.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
```
