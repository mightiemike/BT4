### Title
`stringifyQueryForAppProxy` uses delimiter-less key/value concatenation, allowing HMAC parameter-substitution forgery - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
`stringifyQueryForAppProxy` builds the string that is HMAC-signed for app-proxy requests by concatenating `key=value` pairs with **no separator** between them. Because query values are not restricted from containing `=` or other characters, two structurally different parameter sets (different key/value splits) can serialize to an identical string and therefore produce an identical HMAC, letting an attacker substitute a forged parameter set for a legitimately-signed one.

### Finding Description
`stringifyQueryForAppProxy` in [1](#0-0)  sorts entries by key and concatenates them as `${acc}${key}=${value}` with no delimiter between pairs. This string is then fed into `generateLocalHmac` [2](#0-1)  and compared against the request's `signature` in `validateHmac` [3](#0-2) .

Because the query object passed in is already parsed by the standard `&`/`=` URL-query parser before reaching this function, an attacker can choose a value that itself contains `key=value`-shaped text (URL-encoded `=` decodes fine inside a value). For example:

- Set A: `{a: '1', b: '2', shop: 's', timestamp: 't'}` → sorted keys `a,b,shop,timestamp` → string `a=1b=2shop=stimestamp=t`
- Set B: `{a: '1b=2', shop: 's', timestamp: 't'}` (only 3 real keys, `b` absorbed into `a`'s value) → sorted keys `a,shop,timestamp` → string `a=1b=2shop=stimestamp=t`

Both produce the identical string, hence the identical HMAC/`signature`. `validateHmac` only checks `safeCompare(signature, localHmac)`; it never verifies that the actual parsed key set matches what Shopify originally signed. `normalizeQuery` [4](#0-3)  only guards against duplicate single-value params (`hmac`, `shop`, `signature`, `timestamp`), not against this boundary-shifting collision on arbitrary keys such as `logged_in_customer_id` or app-specific business parameters. Consequently, an attacker who has observed one legitimately Shopify-signed app-proxy request can send a direct HTTP request straight to the app's proxy endpoint (these endpoints are ordinary public URLs, not restricted to Shopify's infrastructure) with a differently-structured, colliding query and the same `signature` value; the app treats it as authentic even though the real parsed fields (e.g., a customer-identity or business parameter) differ from what Shopify actually signed.

### Impact Explanation
This allows app-proxy request/parameter forgery without knowledge of `apiSecretKey`: an attacker can present a colliding, differently-structured parameter set (potentially altering or dropping identity-bearing fields such as `logged_in_customer_id` or other business parameters that were merged/split across the boundary) while still passing `validateHmac`. Depending on how the host app trusts these fields, this can enable customer impersonation or unauthorized-parameter injection under a valid-looking Shopify signature — corresponding to Shopify's "authentication/authorization bypass via signature forgery" bounty class.

### Likelihood Explanation
The attacker needs no secret and no privileged role — only visibility into one legitimately-signed app-proxy request (trivially obtained by visiting their own app-proxy URL as an anonymous/logged-in customer) and the ability to send a direct HTTP request to the app's public proxy endpoint with a crafted colliding query string. Constructing a collision is deterministic and repeatable (demonstrated below), requiring only that a value be allowed to contain `=` and adjacent characters that mimic a following `key=value`.

### Recommendation
Use an unambiguous, injective serialization for the app-proxy HMAC input, e.g. join sorted `key=value` pairs with an explicit separator (`&`), and/or percent-encode both keys and values before concatenation so no value can produce characters that mimic a `key=` boundary. Ensure the join method matches what Shopify actually computes (Shopify's app-proxy signature format should be verified against the documented algorithm), and add a check that rejects unexpected characters (e.g., `=`) inside decoded values used for signing where feasible.

### Proof of Concept
```ts
import {generateLocalHmac} from '../hmac-validator';
import {testConfig} from '../../__tests__/test-config'; // use repo's existing config test helper

test('stringifyQueryForAppProxy allows colliding param sets to produce the same HMAC', async () => {
  const config = testConfig();
  const genHmac = generateLocalHmac(config);

  // Set A: two distinct params "a" and "b"
  const queryA = {shop: 's', timestamp: 't', a: '1', b: '2'};
  // Set B: single param "a" whose value absorbs what was "b=2" in set A
  const queryB = {shop: 's', timestamp: 't', a: '1b=2'};

  const hmacA = await genHmac(queryA, 'appProxy');
  const hmacB = await genHmac(queryB, 'appProxy');

  // Both concatenate to "a=1b=2shop=stimestamp=t"
  expect(hmacA).toBe(hmacB);
});
```
This confirms that a `signature` computed by Shopify for query set A will also `validateHmac`-pass for the structurally different, attacker-crafted query set B.

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}

export function generateLocalHmac(config: ConfigInterface) {
  return async (
    params: AuthQuery,
    signator: HMACSignator = 'admin',
  ): Promise<string> => {
    const {hmac: _hmac, signature: _signature, ...query} = params;

    const queryString =
      signator === 'admin'
        ? stringifyQueryForAdmin(query)
        : stringifyQueryForAppProxy(query);

    return createSHA256HMAC(config.apiSecretKey, queryString, HashFormat.Hex);
  };
}

export function validateHmac(config: ConfigInterface) {
  return async (
    query: HmacQuery,
    {signator}: {signator: HMACSignator} = {signator: 'admin'},
  ): Promise<boolean> => {
    const normalizedQuery = normalizeQuery(query, signator);

    if (signator === 'admin' && !normalizedQuery.hmac) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain an HMAC value.',
      );
    }

    if (signator === 'appProxy' && !normalizedQuery.signature) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain a signature value.',
      );
    }

    validateHmacTimestamp(normalizedQuery);

    const hmac =
      signator === 'appProxy'
        ? normalizedQuery.signature
        : normalizedQuery.hmac;
    const localHmac = await generateLocalHmac(config)(
      normalizedQuery,
      signator,
    );

    return safeCompare(hmac as string, localHmac);
  };
}

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
