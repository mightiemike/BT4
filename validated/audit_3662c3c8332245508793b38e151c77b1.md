### Title
`WithdrawFromGasKey` nested inside a `Delegate` action bypasses the pending-transaction-queue's gas-key balance tracking, allowing overdraft/double-spend of a gas key's funded balance before the fix at `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` - (File: `chain/client/src/pending_transaction_queue.rs`)

### Summary
The `PendingTransactionQueue`/`PendingTxSession` mechanism tracks in-flight (not-yet-applied) balance and gas-key commitments so that concurrently-submitted transactions in the same chunk-production window cannot collectively overdraw an account or a gas key. This tracking scans only the *top-level* actions of a transaction for `Action::WithdrawFromGasKey`. When a `WithdrawFromGasKey` action is nested inside an `Action::Delegate` (meta-transaction) payload instead of being a top-level action, the queue never records it, so the gas key's tracked "available" balance stays artificially high while the actual balance is drained. This is directly analogous to the Perennial `Market.update()` collateral-removal bug: an action that moves value out immediately, without going through the validation/accounting path that all other value-affecting actions are required to go through, letting a user exploit a stale/incomplete accounting view to extract more value than should be available.

### Finding Description
`PendingTxSession::check_pending` computes `paid_from_gas_key` from `snapshot.pending_gas_key_cost` (queue-wide) plus `session_gas_key_withdrawals` (this session), and the session-local scan only looks at `tx.transaction.actions()` at the top level: [1](#0-0) 

The same top-level-only scan is used when a chunk's transactions are folded into the queue's aggregate state: [2](#0-1) 

A `Delegate` action, however, carries an inner `DelegateAction` with its own nested `actions` list, which is executed as a separate receipt on the sender's account once the outer meta-transaction is processed (`apply_delegate_action` in `runtime/runtime/src/actions.rs`). If that nested list contains `Action::WithdrawFromGasKey`, the outer transaction (as submitted to and admitted by the queue) shows no `WithdrawFromGasKey` action at all, so `chunk_data.gas_key_costs` / `session_gas_key_withdrawals` never account for the pending drain — even though the receipt this delegate spawns will, when it later executes, subtract the withdrawal amount from the gas key's real balance via `action_withdraw_from_gas_key` in `runtime/runtime/src/access_keys.rs`.

The nearcore maintainers themselves documented this exact hole as the rationale for a dedicated protocol fix: [3](#0-2) 

And the deliberately-designed host-function omission confirms the intended invariant that gas-key-draining actions must be visible to the queue only via top-level transaction actions: [4](#0-3) 

The regression test that exists specifically to characterize this hole demonstrates the exploit end-to-end: a `Delegate` action wrapping a `WithdrawFromGasKey` is admitted and executes successfully pre-upgrade, draining the gas key balance, and is only rejected once `RejectWithdrawFromGasKeyInDelegate` is active: [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who controls a gas key with a funded balance can submit multiple `Delegate` transactions in the same chunk-production window, each nesting a `WithdrawFromGasKey` action against the same gas key. Because the pending-transaction-queue's accounting never records these nested withdrawals as pending cost, the queue continues to admit further transactions (including regular gas-key transactions) against the same key as if its balance were untouched. This can result in the gas key's balance being drawn down beyond what the runtime's ephemeral (in-chunk) checks would otherwise have permitted had the withdrawal been visible — i.e., unauthorized/duplicated value movement out of the gas key relative to the balance the admission layer believed was committed, undermining the very "available_gas_key_balance = balance - pending" invariant that `verify_and_charge_gas_key_tx_ephemeral` relies on (`runtime/runtime/src/verifier.rs:579-594`). This is a concrete accounting-bypass/value-extraction vector reachable purely by an unprivileged transaction signer submitting ordinary signed meta-transactions — no validator or network-level privilege required.

### Likelihood Explanation
This is trivially triggerable: it requires only that an account create/fund a gas key (`AddKey` + `TransferToGasKey`, both ordinary user actions) and then submit a `SignedDelegateAction` whose inner action list contains `WithdrawFromGasKey`, which any full-access-key holder can construct and sign. No special timing, race condition beyond ordinary concurrent tx submission, or validator collusion is needed — the regression test confirms it executes successfully under normal conditions pre-fix. The condition is gated behind the `GasKeys` and `DelegateV2`/meta-transaction features being live, which are part of mainline protocol progression (not SPICE-exclusive; the accompanying `pending_transaction_queue.rs` withdrawal-tracking test is `cfg_attr(not(feature = "protocol_feature_spice"), ...)`-gated, but the vulnerable code path itself — `check_pending`'s top-level-only action scan and `apply_delegate_action`'s nested-action execution — is general runtime/client logic, not restricted to SPICE validators; the exploit is initiated by an ordinary transaction signer, not a validator or peer).

### Recommendation
Harden the pending-transaction-queue accounting (and the corresponding action-validation layer) so that `WithdrawFromGasKey` actions nested inside `Delegate`/`DelegateV2` payloads are either (a) recursively scanned and included in `gas_key_costs`/`session_gas_key_withdrawals` accounting exactly like top-level actions, or (b) rejected outright at admission time, mirroring what `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` already implements via `ActionsValidationError::WithdrawFromGasKeyNotAllowedInDelegate` in `runtime/runtime/src/action_validation.rs`. Ensure this fix (and its activation protocol version) is deployed and enforced network-wide before any protocol version window in which gas keys, delegate actions, and the vulnerable pending-transaction-queue logic can coexist unpatched.

### Proof of Concept
1. Attacker account `alice` adds a gas-key access key via `AddKey` with `AccessKey::gas_key_full_access(..)`.
2. Attacker funds the gas key via `TransferToGasKey` with some balance `B`.
3. Attacker builds a `DelegateAction` whose `actions` field contains a single `WithdrawFromGasKey { public_key: gas_key, amount: B }`, signs it with `alice`'s full access key producing a `SignedDelegateAction`, and wraps it in an outer `Action::Delegate` transaction (as shown in `delegated_withdraw_tx` in `test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs:26-54`).
4. Attacker submits several such `Delegate` transactions concurrently in the same chunk-production window (or repeatedly before execution catches up). Because `PendingTxSession::check_pending` (`chain/client/src/pending_transaction_queue.rs:576-585`) only scans top-level actions, none of these nested withdrawals are added to `session_gas_key_withdrawals`, so `paid_from_gas_key` under-reports the true pending drain, and each transaction is admitted as if the gas key still has its full balance.
5. When the delegate receipts execute, `action_withdraw_from_gas_key` (`runtime/runtime/src/access_keys.rs`) subtracts the withdrawal from the gas key's real on-chain balance for each admitted transaction, resulting in a total drain exceeding what the admission-time accounting believed was outstanding — as directly confirmed by the existing regression test asserting the withdrawal succeeds and drains the balance pre-fix (`test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs:112-137`).
