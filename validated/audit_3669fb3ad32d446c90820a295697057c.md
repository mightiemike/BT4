### Title
Blockifier's `deploy` syscall omits the reserved-contract-address check enforced by the Starknet OS, allowing a sequencer to accept and commit deployments the OS will later reject - ([File: crates/blockifier/src/execution/execution_utils.rs])

### Summary
The Starknet OS explicitly forbids deploying a contract to one of the protocol-reserved addresses (`ORIGIN_ADDRESS`, `BLOCK_HASH_CONTRACT_ADDRESS`, `ALIAS_CONTRACT_ADDRESS`, `RESERVED_CONTRACT_ADDRESS`) via an `assert_not_zero` guard in `deploy_contract.cairo`. The blockifier (the sequencer's native execution engine, used both to build and to validate blocks before OS re-execution) has no equivalent check when handling the `deploy` syscall, so it will happily accept, execute, and commit a deployment whose computed address collides with one of these reserved values. This is analogous to the reported issue where a `require` check in one code path (`initiateBridgeERC721`) is not mirrored in another reachable path (the default constructor), letting a caller reach a state (`address(0)`) that downstream logic assumed was impossible.

### Finding Description
The Starknet OS's `deploy_contract` function asserts that the target address is not one of four reserved addresses before mutating state: [1](#0-0) 

This check exists only in the Cairo OS program. The Rust-side execution engine (`blockifier`), which is what the sequencer actually runs when building/validating a block via the `deploy` syscall, computes the deployed address and then only checks that the address is *currently unoccupied* — it never checks that the address avoids the reserved set: [2](#0-1) 

Both syscall entry points (Cairo0 deprecated syscall and the current VM syscall) compute `deployed_contract_address` via `calculate_contract_address` and pass it straight into `execute_deployment`/`ConstructorContext` with no reserved-address filtering: [3](#0-2) [4](#0-3) 

`calculate_contract_address` itself only range-checks the felt via `ContractAddress::try_from` (Patricia key domain check), not the OS's reserved-address exclusion set: [5](#0-4) 

Separately, `ContractAddress::validate()` does implement a "reserved address" exclusion (rejecting `<= BLOCK_HASH_TABLE_ADDRESS`), but it is only invoked by the gateway on `sender_address` for `Declare`/`Invoke` transactions — never on syscall-computed deployment addresses: [6](#0-5) [7](#0-6) 

Because `constructor_calldata` and `contract_address_salt` are fully attacker-controlled inputs to the `deploy` syscall, an unprivileged transaction sender can grind salt/calldata values (a Pedersen hash pre-image search) until `calculate_contract_address` lands on one of the four reserved addresses. The blockifier will accept this as a normal deployment, execute the constructor, and mark the block as valid, while the Starknet OS — invoked later during proving/re-execution — will hit the `assert_not_zero` and fail.

### Impact Explanation
This produces a genuine honest-node/OS divergence: blockifier (used for both block-building on the sequencer and state-transition validation) commits state that the Starknet OS's `deploy_contract` guard forbids. When the block is later re-executed/proven by the Starknet OS (needed for state commitment/proving pipeline), the proof generation for that block fails, since the reserved-address assertion trips. This can render a block unprovable, i.e., the network becomes unable to finalize/confirm that block's state transition — a concrete "network unable to confirm new transactions" outcome, consistent with the accepted impact categories (wrong committed root / inability to prove — honest-node divergence between blockifier execution and Starknet OS re-execution).

### Likelihood Explanation
The only obstacle to reaching a reserved-address collision is finding calldata/salt values whose Pedersen-hash-based `calculate_contract_address` result (mod `L2_ADDRESS_UPPER_BOUND`) equals one of a handful of reserved felts. This is a search over a large output space (not simply guessable), but it is a single, unprivileged, deterministic offline computation — a brute-force/grinding search for a preimage landing on one of ~4 target values out of the address domain — reachable purely by submitting one `invoke`/`deploy_account`/syscall transaction with attacker-chosen `salt`/`constructor_calldata`. No special privileges, node compromise, or network-level attack is required; it's a standard tx-crafting exercise, similar in spirit to `deploy_from_zero` grinding tests already present in the codebase (e.g. `to_unavailable_address` test). The main uncertainty is the computational cost of the grinding search, which the report itself does not need to bound since finding *any one* of the 4 target values is sufficient and Pedersen hashing is fast to compute offline.

### Recommendation
Add the same reserved-address exclusion check that the Starknet OS enforces (`ORIGIN_ADDRESS`, `BLOCK_HASH_CONTRACT_ADDRESS`, `ALIAS_CONTRACT_ADDRESS`, `RESERVED_CONTRACT_ADDRESS`) directly inside blockifier's `execute_deployment` (or immediately after computing `deployed_contract_address` in both the deprecated and current `deploy` syscall handlers), so that the sequencer rejects such deployments with a normal execution error, exactly mirroring what the OS Cairo program checks. This keeps the two execution paths (blockifier and Starknet OS) consistent and prevents blocks containing such deployments from ever being built.

### Proof of Concept
1. An attacker submits an `invoke` transaction that calls the `deploy` syscall (directly, or via any account contract exposing a deploy helper) with attacker-chosen `contract_address_salt` and `constructor_calldata`, grinding these values offline until:
   `calculate_contract_address(salt, class_hash, constructor_calldata, deployer_address) == RESERVED_CONTRACT_ADDRESS` (or one of `ORIGIN_ADDRESS`/`BLOCK_HASH_CONTRACT_ADDRESS`/`ALIAS_CONTRACT_ADDRESS`).
2. Blockifier's `deploy` (in `syscall_base.rs` / `hint_processor.rs`) computes this address, finds it unoccupied (`current_class_hash == ClassHash::default()`), and proceeds to run the constructor and call `state.set_class_hash_at`, succeeding — see `crates/blockifier/src/execution/execution_utils.rs:325-356`.
3. The transaction is included in a block by the sequencer's Batcher/BlockBuilder.
4. When the Starknet OS later re-executes/proves this block, `deploy_contract.cairo`'s `assert_not_zero` at lines 45-49 trips because `contract_address` matches one of the reserved constants, causing OS execution/proof generation for that block to fail — a divergence between the sequencer's accepted block and the provable state transition. pub fn calculate_contract_address(
    salt: ContractAddressSalt,
    class_hash: ClassHash,
    constructor_calldata: &Calldata,
    deployer_address: ContractAddress,
) -> Result<ContractAddress, StarknetApiError> {
    let constructor_calldata_hash = Pedersen::hash_array(&constructor_calldata.0);
    let contract_address_prefix = format!("0x{}", hex::encode(CONTRACT_ADDRESS_PREFIX));
    let address = Pedersen::hash_array(&[
        Felt::from_hex(contract_address_prefix.as_str()).map_err(|_| {
            StarknetApiError::OutOfRange { string: contract_address_prefix.clone() }
        })?,
        *deployer_address.0.key(),
        salt.0,
        class_hash.0,
        constructor_calldata_hash,
    ]);
    let (_, address) = address.div_rem(&L2_ADDRESS_UPPER_BOUND);

    ContractAddress::try_from(address)
}
