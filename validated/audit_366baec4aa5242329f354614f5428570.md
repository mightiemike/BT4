### Title
Floor-vs-Ceiling Threshold Mismatch Between Signer Global-State Agreement and Nakamoto Block Signing Threshold - ([File: libsigner/src/v0/signer_state.rs])

### Summary
This is a rounding-boundary analog of the reported bug class ("a comparison performed against a value computed one way, while the actual effect uses a value computed a different way, causing an equality mismatch"). Here, the same constant `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` is used to define two different "have we reached the required weight?" checks, but the two implementations round the threshold in opposite directions, so the exact same total signer weight can be judged "sufficient" by one code path and "insufficient" by the other.

### Finding Description
The core Nakamoto block-approval threshold is computed with ceiling division in `NakamotoBlockHeader::compute_voting_weight_threshold`: [1](#0-0) 
```
let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
u32::try_from((total_weight * threshold) / 10 + ceil)...
```
This is the value used by `verify_signer_signatures` to decide whether a Nakamoto block header has enough accumulated signer weight to be considered validly signed by the network: [2](#0-1) 

The signer-side `GlobalStateEvaluator::reached_agreement`, which uses the *same* `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` constant to decide global-state agreement (active signer protocol version, global burn view, current miner, and tx-replay-set consensus), uses plain floor (truncating integer) division instead: [3](#0-2) 
```
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight) >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}
```

For any `total_weight` where `(total_weight * threshold) % 10 != 0` (i.e., the threshold is not an exact multiple), `compute_voting_weight_threshold` rounds up while `reached_agreement`'s inline computation rounds down. Example: `total_weight = 13`, threshold = 7 (70%): `13*7/10 = 9` (both compute floor 9), `compute_voting_weight_threshold` adds `ceil=1` → `10`; `reached_agreement` uses `9` directly (no ceiling term) → a vote weight of exactly `9` is judged "agreement reached" by the signer's global-state evaluator, while the same weight of `9` would be judged *insufficient* to satisfy the Nakamoto block-header signature threshold in `verify_signer_signatures`.

This is used across `determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, and `determine_global_state` (current miner / tx-replay-set), all of which gate signer behavior (e.g., which miner a signer treats as "current," which protocol version messages it will parse/act on, which transaction-replay set it enforces): [4](#0-3) [5](#0-4) 

### Impact Explanation
At an exact boundary weight, a minority of signers (holding the boundary weight, e.g. 9/13) is enough to make `GlobalStateEvaluator` believe "global agreement" is reached on a burn view / current-miner / protocol version / tx-replay-set — even though that same weight would not be enough to actually get a Nakamoto block signed under `verify_signer_signatures`'s ceiling-based threshold. Signers acting on a premature "global state" determination can diverge from signers/nodes still requiring the stricter ceiling threshold for block signature verification, producing a temporary tip/view disagreement among signers about the current miner or replay set. This maps to the "temporary tip disagreement" / "minority-triggerable... divergence" category of High impact under the given rubric, since it is triggered purely by weight distribution arithmetic at specific totals, not by a majority coalition.

### Likelihood Explanation
Triggering requires only that the total signer weight distribution land on a value where `(total_weight * 7) % 10 != 0` (the common case — most `total_weight` values are not exact multiples of 10/gcd), and that update weights accumulate to exactly the floor-threshold value before reaching the ceiling-threshold value. This is a naturally-occurring arithmetic edge case, not an adversarial exploit requiring special crafted inputs beyond ordinary variance in reward-cycle signer weights, so it is plausible to occur in ordinary operation given diverse weight distributions across reward cycles.

### Recommendation
Factor out a single shared threshold-computation function (the ceiling-based one already in `NakamotoBlockHeader::compute_voting_weight_threshold`) and have `GlobalStateEvaluator::reached_agreement` (and `reached_disagreement`) call it instead of re-implementing the division inline, ensuring both consensus-critical and signer-side agreement checks always agree bit-for-bit on the same total weight.

### Proof of Concept
1. Configure a reward set with 3 signers of weights `[9, 3, 1]` (`total_weight = 13`).
2. `NakamotoBlockHeader::compute_voting_weight_threshold(13)` → `13*7/10 = 9`, remainder `91 % 10 = 1 != 0` → `ceil = 1` → threshold = `10`.
3. `GlobalStateEvaluator::reached_agreement(9)` → `9 >= 13*7/10 = 9` → `true` (agreement reached with weight 9).
4. A block signed only by the weight-9 signer subset would be rejected by `verify_signer_signatures` (needs 10), yet the same weight-9 subset is treated by the signer's `GlobalStateEvaluator` as having reached "global agreement" on burn view / current miner / protocol version — a verified inconsistency in the threshold arithmetic between the two call sites, confirmed by direct code inspection of both functions.

Note: I was unable to fully trace every downstream consumer of `GlobalStateEvaluator::reached_agreement` inside `stacks-signer` (e.g., how "current miner" state feeds into actual block-signing decisions) within the available search budget; a full confirmation of end-to-end chain-split reachability (versus a signer-software-only disagreement) would benefit from deeper tracing in `stacks-signer/src/v0/`.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

    /// Determine what the maximum signer protocol version that a majority of signers can support
    pub fn determine_latest_supported_signer_protocol_version(&self) -> Option<u64> {
        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
            *entry += weight;
        }
        // find the highest version number supported by a threshold number of signers
        let mut protocol_versions: Vec<_> = protocol_versions.into_iter().collect();
        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }

    /// Determine what the global burn view is if there is one
