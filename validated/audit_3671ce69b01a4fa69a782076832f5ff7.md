### Title
Divergent tronPower ceiling check between `VoteWitnessActuator.validate()` and `VoteWitnessProcessor.execute()` during the `AllowNewResourceModel=1 / UnfreezeDelay=0` fork window - ([File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java] / [File: actuator/src/main/java/org/tron/core/vm/nativecontract/VoteWitnessProcessor.java])

### Summary
`VoteWitnessActuator.validate()` selects `getAllTronPower()` whenever `supportAllowNewResourceModel()` is true, while `VoteWitnessProcessor.execute()` only selects `getAllTronPower()` when **both** `supportUnfreezeDelay()` and `supportAllowNewResourceModel()` are true, otherwise falling back to `getTronPower()`. In the fork window where `AllowNewResourceModel=1` but `UnfreezeDelay=0`, the two code paths compute a different voting-power ceiling for identical account state and identical vote input.

### Finding Description
`VoteWitnessActuator.validate()`: [1](#0-0) 
uses `getAllTronPower()` as soon as `supportAllowNewResourceModel()` is true, regardless of `supportUnfreezeDelay()`.

`VoteWitnessProcessor.execute()` (reached from the TVM native-contract vote path, called from `Program.java`): [2](#0-1) 
requires **both** `supportUnfreezeDelay()` and `supportAllowNewResourceModel()` to be true before using `getAllTronPower()`; otherwise it uses the smaller `getTronPower()`.

During the window `AllowNewResourceModel=1, UnfreezeDelay=0`:
- Ordinary broadcast `VoteWitnessContract` transactions (validated via `VoteWitnessActuator.validate()`) are checked against the larger `getAllTronPower()` ceiling.
- The same vote submitted through a TVM native vote precompile call (which reaches `VoteWitnessProcessor.execute()` directly, bypassing `VoteWitnessActuator.validate()` per the referenced call sites in `Program.java`) is checked against the smaller `getTronPower()` ceiling.

Since `getAllTronPower()` is expected to be `>= getTronPower()` (it aggregates both the legacy and new resource-model frozen balances), an account can pass the ceiling check on the actuator path with a total vote sum that would be rejected on the processor path for the exact same account state — the two independently-validating code paths do not agree on acceptance for identical input during this fork window. This violates the determinism invariant that identical vote input must yield identical acceptance/rejection irrespective of which internal path (regular contract vs. TVM native contract) it traverses.

None of the existing generic protections (`DecodeUtil.addressValid`, signature/permission checks, size limits, other fork gates) address this specific mismatch because both checks are gated purely by the two dynamic-property flags whose combination is the actual root cause.

### Impact Explanation
This allows an account, during the narrow transitional window where `AllowNewResourceModel` is enabled ahead of `UnfreezeDelay`, to obtain a larger effective voting-power ceiling by submitting votes through the ordinary actuator path than would be permitted through the TVM native-contract vote path (or vice versa depending on which flag rollout order actually occurs on the network). This is an accounting/state-consistency defect (inflated/deflated vote-power enforcement) rather than a fund-theft or RCE bug; it falls under "unauthorized state change" / accounting inconsistency in the vote/witness accounting subsystem. It does not cause cross-node consensus divergence by itself, since all fully-validating nodes run identical code and would agree on the (inconsistent) result for a given transaction type — the impact is limited to inconsistent enforcement between the two call paths rather than chain forks.

### Likelihood Explanation
Exploitation requires the network to actually be in the specific fork-gate state `AllowNewResourceModel=1 && UnfreezeDelay=0`, which is set via committee/witness-controlled `ChainParameters` proposals, not by the attacker. An ordinary funded account or contract caller cannot create this window itself; it can only be present transiently during a real hard-fork rollout sequence if the two related proposals are activated at different times. Whether this window ever actually occurs on a live network depends on the mainnet/testnet rollout schedule of these two specific proposals, which could not be fully confirmed from the available index (no direct evidence found of how/when `UnfreezeDelay` and `AllowNewResourceModel` are toggled relative to each other in production). If the window does occur, exploitation cost for an attacker is just normal transaction/energy fees — no privileged access is needed to submit either a standard vote transaction or a contract call reaching `VoteWitnessProcessor`.

### Recommendation
Make the tronPower-selection condition identical in both `VoteWitnessActuator.validate()` and `VoteWitnessProcessor.execute()` — either gate both on `supportAllowNewResourceModel()` alone, or gate both on `supportUnfreezeDelay() && supportAllowNewResourceModel()`, so the same input produces the same accept/reject decision on both code paths.

### Proof of Concept
JUnit outline mirroring `voteWitnessWithoutEnoughOldTronPowerAfterNewResourceModel` in `framework/src/test/java/org/tron/core/actuator/VoteWitnessActuatorTest.java`:

```java
// Setup: dynamicStore.setAllowNewResourceModel(1); dynamicStore.setUnfreezeDelay(0);
// Account has getTronPower() = X, getAllTronPower() = Y, with X < voteSum <= Y

// Path 1: actuator
VoteWitnessActuator actuator = new VoteWitnessActuator();
actuator.setChainBaseManager(...);
actuator.setAny(buildVoteContract(voteSum));
boolean actuatorAccepted;
try {
  actuator.validate(); // uses getAllTronPower() -> Y >= voteSum -> passes
  actuatorAccepted = true;
} catch (ContractValidateException e) {
  actuatorAccepted = false;
}

// Path 2: VoteWitnessProcessor (simulating TVM native call)
VoteWitnessProcessor processor = new VoteWitnessProcessor();
boolean processorAccepted;
try {
  processor.execute(buildVoteWitnessParam(voteSum), repository); // uses getTronPower() -> X < voteSum -> throws
  processorAccepted = true;
} catch (ContractExeException e) {
  processorAccepted = false;
}

// Assert divergence
assertTrue(actuatorAccepted);
assertFalse(processorAccepted); // FAILS the determinism invariant: same input, different outcomes
```
