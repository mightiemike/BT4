### Title
Off-by-one boundary allows a PoisonMicroblock report to be accepted by `handle_poison_microblock` in the exact block where it is already too late for `find_mature_miner_rewards` to see it - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`handle_poison_microblock` accepts a report whenever `height + MINER_REWARD_MATURITY < current_height` is false, i.e. it also accepts the exact boundary case `height + MINER_REWARD_MATURITY == current_height`. But `find_mature_miner_rewards` for the block at that same `height` is invoked at `reward_height = tip_stacks_height - MINER_REWARD_MATURITY` on the very same `current_height`/`tip_stacks_height`, and that lookup happens *before* any transaction of that block (including the PoisonMicroblock tx itself) is executed. The report accepted "just in time" by the transaction-validity check is therefore never observed by the reward-maturation lookup for that height, so the offending miner keeps the full, unpunished coinbase for that block while the reporter's commission is silently dropped.

### Finding Description
The claimed equality is: *reporter commission paid == a report accepted as valid by `handle_poison_microblock` for that exact `reward_height`*.

- In `handle_poison_microblock` (`stackslib/src/chainstate/stacks/db/transactions.rs:770-803`), the maturity guard is:
```
if height.checked_add(MINER_REWARD_MATURITY) < current_height { reject }
```
i.e. `height + MINER_REWARD_MATURITY == current_height` is *accepted*, and the report is written via `insert_microblock_poison(mblock_pubk_height, ...)` keyed on `mblock_pubk_height == height` (`transactions.rs:806-855`).

- In `find_mature_miner_rewards` (`stackslib/src/chainstate/stacks/db/accounts.rs:985-1041`), the lookup is:
```
let reward_height = tip_stacks_height - MINER_REWARD_MATURITY;
StacksChainState::get_poison_microblock_report(clarity_tx, reward_height)
```
When `tip_stacks_height == current_height` for the block currently being appended, `reward_height == height` — the same key used above. However `find_mature_miner_rewards`/`calculate_matured_miner_rewards` is invoked *before* the block's own transactions are processed: in `stackslib/src/chainstate/stacks/db/blocks.rs:5099-5120` (and similarly in `stackslib/src/chainstate/nakamoto/mod.rs:4671-4683`), the matured-reward calculation runs against `clarity_tx` immediately after the block-begin, prior to executing any of that block's own transactions.

Consequently, if a PoisonMicroblock transaction naming the exact boundary height is included in the same block where `height + MINER_REWARD_MATURITY == current_height`, `handle_poison_microblock` will accept and record it (because the strict `<` comparison does not reject the equal case), but `get_poison_microblock_report(clarity_tx, reward_height)` — invoked earlier in that same block's processing to decide the reward payout — will find nothing, because the `insert_microblock_poison` write for this transaction has not happened yet in program order. No existing guard (`check_tenure_tx`, `validate_*_static`, MARF hashing, etc.) intercepts this because both operations are legitimate, deterministic reads/writes of Clarity key/value state performed in a fixed, but incorrectly-ordered-relative-to-each-other, sequence.

Attacker's exact input: a PoisonMicroblock transaction referencing two conflicting microblock headers signed by the same pubkey hash whose registration height satisfies `height + MINER_REWARD_MATURITY == current_height` for the block into which the transaction is mined.

### Impact Explanation
The bug is fully deterministic — every honest node executes transactions in the same order and reaches the identical (wrong) outcome, so there is no chain split, no non-reproducible state root, and no invalid-block-accepted/valid-block-rejected divergence. The concrete effect is a reward mis-payment bounded to a single block/tenure's coinbase commission: the reporter who should have received `poison_microblock_commission(coinbase)` gets nothing, and the offending miner's coinbase for that one block is not slashed despite a validly-recorded double-sign report existing in chain state. This matches the "High - a poison or reward mis-payment bounded to fees" category, not the Critical chain-split/theft-of-outside-funds category, since the mis-payment is confined to the punishment/commission mechanism for exactly one poisoned height and does not touch unrelated accounts, the MARF root, or sortition/VRF state.

### Likelihood Explanation
Triggering requires a PoisonMicroblock transaction to land specifically in the one block where `height + MINER_REWARD_MATURITY == current_height`. Any unprivileged participant who detects a fork can craft this transaction; no majority stake, signer key, or node-operator privilege is needed — it only requires timing the transaction's inclusion (or waiting for natural inclusion via a full mempool) to that exact tenure. This is a narrow one-block window per offending microblock-pubkey-hash rather than a persistently repeatable exploit, and a rational reporter has every incentive to submit *earlier* (any earlier block also satisfies the maturity check and would correctly pay out), so the loss more plausibly manifests as an unintentional race (report arrives just barely too late) than a deliberately profitable attacker action — though a miner wishing to evade punishment for their own double-sign, if they can influence which block ultimately includes the incriminating report (e.g., by delaying propagation/relay of the report by one tenure), can exploit it to escape docking of that one coinbase.

### Recommendation
Change the guard in `handle_poison_microblock` (`stackslib/src/chainstate/stacks/db/transactions.rs`) to reject the boundary case that can never be observed by `find_mature_miner_rewards`, i.e. use `<=` instead of `<`:
```rust
if height.checked_add(MINER_REWARD_MATURITY) <= current_height { reject }
```
so the accepted window for `handle_poison_microblock` exactly matches the window in which `find_mature_miner_rewards` will still query `get_poison_microblock_report` for that height before it matures.

### Proof of Concept
Rust integration test plan (in `stackslib/src/chainstate/stacks/tests/accounting.rs` style, using the existing `TestPeer` harness):
1. Mine a tenure at height `H` whose block uses microblock pubkey hash `PK`, and craft a forked-microblock pair signed by `PK`.
2. Advance the chain to height `H + MINER_REWARD_MATURITY` (the exact boundary), and include a `PoisonMicroblock(mblock_header_1, mblock_header_2)` transaction referencing `PK` in the block at this height.
3. Assert side A: the transaction is accepted (`handle_poison_microblock` returns `Ok`, receipt shows no error) — confirm via the resulting tx receipt/result value containing `height == H`.
4. Assert side B: after this block is appended, query `StacksChainState::get_matured_miner_payment` (or inspect `MinerReward`/`calculate_miner_reward`'s punished flag) for the miner of block `H`, and assert the miner's coinbase was **not** docked and the reporter's account balance did **not** increase by `poison_microblock_commission(coinbase)`.
5. Show the equality violation: assert `get_poison_microblock_report(clarity_tx, reward_height=H)` returned `None` at the time `find_mature_miner_rewards` was invoked for tip height `H + MINER_REWARD_MATURITY`, despite the PoisonMicroblock transaction at that same height having been accepted by `handle_poison_microblock`.
6. As a control, repeat with the same report submitted one block earlier (`height + MINER_REWARD_MATURITY == current_height - 1`) and show the commission *is* correctly paid, proving the divergence is specific to the exact boundary block.
