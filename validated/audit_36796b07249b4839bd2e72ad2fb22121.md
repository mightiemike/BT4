### Title
Unbounded `UniversalTx.OutboundTx` growth from a single user-controlled EVM payload enables per-vote linear-scan cost blowup - (File: `x/uexecutor/keeper/create_outbound.go`, `x/uexecutor/keeper/msg_vote_outbound.go`)

### Summary
`VotingEscrow.MAX_DELEGATES` (external report) is a hard-cap-that-isn't-low-enough on an unbounded array populated by unprivileged user actions, which later gets iterated in security-critical functions (`transferFrom`, `withdraw`, `merge`, `_mint`), eventually exceeding block gas limits and permanently locking funds. The Push Chain analog is `UniversalTx.OutboundTx`, an append-only slice that grows once per `UniversalTxOutboundEvent` log emitted by the `UniversalGatewayPC` contract during a single EVM execution, with **no cap on how many such events one payload/inbound execution can emit**. Every later `MsgVoteOutbound` call by every Universal Validator does a full linear scan of `utx.OutboundTx` (`x/uexecutor/keeper/msg_vote_outbound.go:45-51`) and a full read/decode/append/re-encode of the entire `UniversalTx` record (`x/uexecutor/keeper/create_outbound.go:339-406`, `k.UpdateUniversalTx`). An unprivileged caller of `MsgExecutePayload` (gasless, "any user" per `x/uexecutor/README.md:204`) can therefore inflate a single UTX's `OutboundTx` array arbitrarily, making all subsequent voting/finalization on that UTX's outbounds increasingly expensive for every validator, mirroring the delegate-array DOS pattern.

### Finding Description
`x/uexecutor/keeper/create_outbound.go:16-105` (`BuildOutboundsFromReceipt`) scans **every log** in an EVM receipt for `UniversalTxOutboundEvent` emitted by the fixed `UniversalGatewayPC` address, and for each matching log builds and appends one `*types.OutboundTx` to a slice with no upper bound: [1](#0-0) 

That unbounded `outbounds` slice is then appended into the persisted `UniversalTx.OutboundTx` array via `attachOutboundsToUtx`, again with no size check: [2](#0-1) 

This is reachable by an ordinary, unprivileged user through `MsgExecutePayload`, which "any user" may submit gaslessly and which drives `ExecutePayloadV2` → `CallUEAExecutePayload` → an arbitrary EVM call on the user's own UEA (`x/uexecutor/keeper/execute_payload.go`, `x/uexecutor/keeper/evm.go`). If the payload's target contract logic (or the UEA's called contract) can be made to invoke the `UniversalGatewayPC` withdraw/outbound entry point repeatedly within one EVM call — bounded only by the EVM `gasLimit` the caller supplies in the payload, not by any Cosmos-side count limit — the resulting receipt can carry many `UniversalTxOutboundEvent` logs, each becoming a new `OutboundTx` entry appended to the same `UniversalTx.OutboundTx` slice via `AttachOutboundsToExistingUniversalTx` (`x/uexecutor/keeper/create_outbound.go:144-155`), called from the inbound-payload execution paths (`execute_inbound_funds_and_payload.go`, `execute_inbound_gas_and_payload.go`).

Once `OutboundTx` is large, every later `MsgVoteOutbound` from every Universal Validator must:
1. Fully unmarshal the `UniversalTx` (which now embeds N `OutboundTx` entries),
2. Linearly scan `utx.OutboundTx` to find the target outbound (`msg_vote_outbound.go:45-51`),
3. Re-marshal and persist the whole record again via `k.UpdateOutbound`. [3](#0-2) 

This is structurally identical to the `VotingEscrow` bug: a cheap, unprivileged, single action (delegating minimal-value locks / here, emitting N outbound events in one EVM call) inflates an array that is iterated by a different, later, otherwise-honest operation (moving delegates on transfer/withdraw / here, voting on any one of the N outbounds), and the cost of that later operation scales with the attacker-chosen N rather than with anything the later caller controls.

### Impact Explanation
If N can be pushed high enough (via `gasLimit`/complex reentrant-style calls into the gateway inside a single payload execution), every subsequent `MsgVoteOutbound` transaction for any outbound in that UTX becomes proportionally expensive (read + full re-marshal + linear scan of a large protobuf-encoded slice), and in the worst case can approach or exceed the Cosmos block gas limit for ordinary UV votes, stalling finalization of that UTX's outbounds — funds routed through those outbounds (destination-chain releases, refunds) remain in `PENDING` and cannot be observed/finalized, which is a fund-freezing/DOS condition on user-controlled state reachable without any privileged or malicious-validator assumption. It also inflates the on-chain `UniversalTx` blob size, increasing state-growth and per-block processing cost for the chain generally.

Impact is bounded by whatever practical limit exists on how many outbound-emitting calls a single EVM execution invoked via `MsgExecutePayload`/`ExecutePayloadV2` can make within its declared `gasLimit` — this repository does not appear to enforce any additional cap on the number of `UniversalTxOutboundEvent`s per receipt or per UTX, so the bound is effectively the EVM per-call gas limit, which is a much cheaper constraint on the attacker than the cost it later imposes on every UV vote.

### Likelihood Explanation
Reachability requires only a standard, unprivileged user submitting `MsgExecutePayload` with a payload/contract that emits many gateway outbound events in one call — no validator collusion, no admin/governance action, and no external chain compromise is needed. The exact number of events achievable per call (and whether the gateway/UEA contract logic permits a loop of outbound-triggering calls within one transaction) could not be fully verified from this repository, since the `UniversalGatewayPC`/UEA Solidity contracts live in a separate repository (`push-chain-core-contracts`) referenced only by address/ABI here. This uncertainty affects the achievable magnitude of N, not the underlying missing-cap defect in the Go keeper code, which is confirmed.

### Recommendation
- Enforce an explicit maximum on the number of `OutboundTx` entries (and/or `UniversalTxOutboundEvent` logs processed) attachable to a single `UniversalTx` in `BuildOutboundsFromReceipt` / `attachOutboundsToUtx`, rejecting or truncating with a clear error once the cap is exceeded, analogous to reducing `MAX_DELEGATES`.
- Alternatively/additionally, avoid indexing outbounds by linear scan over `utx.OutboundTx` in `VoteOutbound`; maintain a direct `outboundId -> index` or separate keyed collection so per-vote cost stays O(1) regardless of how many outbounds a UTX accumulates.
- Cap or meter the number of outbound-producing gateway calls one `MsgExecutePayload`/inbound execution can make per receipt, independent of the EVM `gasLimit` value the payload sender controls.

### Proof of Concept
Not independently reproducible from this repository alone: exploitation depends on the Solidity `UniversalGatewayPC`/UEA contract logic (external `push-chain-core-contracts` repo) allowing a single EVM call to emit many `UniversalTxOutboundEvent` logs. The Go-side defect — unbounded append to `UniversalTx.OutboundTx` in `attachOutboundsToUtx` and linear-scan lookup in `VoteOutbound` with no size cap — is directly confirmed by the cited code; a concrete PoC would additionally require the EVM contract bytecode to demonstrate the maximum achievable N per transaction.

func (k Keeper) attachOutboundsToUtx(
	ctx sdk.Context,
	utxId string,
	outbounds []*types.OutboundTx,
	revertMsg string, // revert msg if the outbound is for a inbound revert
) error {

	if len(outbounds) == 0 {
		return nil
	}
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {

		for _, outbound := range outbounds {

			utx.OutboundTx = append(utx.OutboundTx, outbound)

			// Compute signature expiry deadline for the destination chain.
			var signingDeadline int64
			if chainCfg, err := k.uregistryKeeper.GetChainConfig(ctx, outbound.DestinationChain); err == nil {
				if chainCfg.TssSigningDeadline != nil && *chainCfg.TssSigningDeadline > 0 {
					signingDeadline = ctx.BlockTime().Unix() + int64(chainCfg.TssSigningDeadline.Seconds())
				}
			}

			// Write to pending outbounds index (inside UpdateUniversalTx closure for atomicity)
			if err := k.PendingOutbounds.Set(ctx, outbound.Id, types.PendingOutboundEntry{
				OutboundId:      outbound.Id,
				UniversalTxId:   utxId,
				CreatedAt:       ctx.BlockHeight(),
				SigningDeadline: signingDeadline,
			}); err != nil {
				return fmt.Errorf("failed to set pending outbound index for %s: %w", outbound.Id, err)
			}
