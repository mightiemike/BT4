### Title
Unchecked `storeSession` return value in OAuth/token-exchange auth flows causes silent session-persistence failures and re-authentication DoS - (File: packages/apps/shopify-app-express/src/auth/auth-callback.ts, packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts, packages/apps/shopify-app-express/src/helpers/invalidate-access-token.ts, packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts)

### Summary
`SessionStorage.storeSession()` is explicitly documented to return `Promise<boolean>`, "returns `true` if successfully stored, `false` otherwise" [1](#0-0) , exactly the same "call may fail without throwing / returns a success flag" contract as the `.call{value:...}("")` construct in the referenced GroupBuy report. Every authentication-critical call site in this repo (`await ...storeSession(...)`) discards that boolean and unconditionally proceeds as if the persistence succeeded.

### Finding Description
The `SessionStorage` interface's `storeSession` is a fallible operation by design — the reference implementation and docs show it can legitimately return `false` on write failure instead of throwing [2](#0-1) .

However, in every authentication/authorization-critical path in the OAuth and Token Exchange flows, the return value is ignored:

- OAuth callback, after obtaining and about to trust a freshly-issued access token: [3](#0-2) 

- Token exchange middleware, persisting freshly exchanged offline/online tokens: [4](#0-3) 

- Access-token invalidation on a 401 from Shopify (used to force re-auth after a stale/rotated token): [5](#0-4) [6](#0-5) 

- Remix/React Router Token Exchange strategy, same unchecked pattern: [7](#0-6) 

In each case the code sets `res.locals.shopify.session` / returns the in-memory `Session` object and treats the request as authenticated **for the current request only**, without verifying that the session was durably persisted. If the underlying storage adapter returns `false` (e.g., a custom or misbehaving `SessionStorage` implementation, or a storage backend under load that fails a write without raising an exception), the code has no way of detecting or reacting to that failure.

### Impact Explanation
- In `authCallback`, if `storeSession` silently fails after OAuth completes, the current request proceeds (webhooks may be registered, `afterAuth` hook fires) as though the shop is now installed, but no session exists in storage for subsequent requests. Every following request for that shop will fail to `loadSession`, forcing the app back into the OAuth-begin/redirect loop — a persistent Denial-of-Service of the authentication handler for that merchant until the storage issue self-resolves or the shop reinstalls.
- In `performTokenExchange` / the Token Exchange `authenticate()` strategy, silent failure to persist the freshly exchanged offline/online access token means the next request will find no active session and re-run the full token exchange against Shopify's `/admin/oauth/access_token` endpoint on every single request, needlessly generating new tokens/leaking previous ones as orphaned, and could trigger Shopify-side rate limiting on the OAuth token endpoint — again degrading/DoS-ing the authentication path.
- In `invalidateAccessToken`, if the write clearing `session.accessToken` fails silently, the caller's forced re-auth message is still sent, but the stale/potentially-revoked access token remains persisted in storage; because nothing surfaces the failure, operators have no signal that a shop's session state is inconsistent.

This does not require a privileged actor: it is triggered purely by transient/failing storage behavior encountered during normal, anonymous OAuth/token-exchange request handling — matching the "DoS of an auth handler" acceptance criterion. Severity is bounded because it does not directly grant an attacker cross-tenant access or a forged session; it is a resilience/availability gap in the authentication pipeline caused by ignoring a documented fallible return value, analogous in root cause (not checking success of a state-changing call) to the referenced GroupBuy finding, though lower in severity since ETH loss vs. session write is not a direct fund-loss equivalent.

### Likelihood Explanation
Likelihood depends entirely on the concrete `SessionStorage` implementation in use. The interface contract explicitly allows non-throwing `false` returns on failure [1](#0-0) , and the maintained example implementation demonstrates this exact pattern (returning `false` on write error rather than throwing) [8](#0-7) . Any app using a custom adapter (or a bundled adapter under a transient failure condition that its `try/catch` maps to `false` rather than a rethrow, e.g. the Drizzle/SQLite/session-storage adapters' `deleteSession`/`deleteSessions` `catch` blocks returning `false`) is exposed. No attacker action is required to trigger the underlying condition — it manifests purely from ordinary storage-layer failures during normal authentication traffic.

### Recommendation
Check the boolean returned by `storeSession` (and `deleteSession`/`deleteSessions`) at every call site in the authentication/token-exchange flows, and fail the request (e.g., respond with a 500 and avoid marking the request as authenticated, or retry) if persistence did not succeed, instead of silently continuing as though the session is durable. Apply this to `auth-callback.ts`, `perform-token-exchange.ts`, `invalidate-access-token.ts` (all three framework packages: `shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`), and the Token Exchange / Auth Code Flow strategies.

### Proof of Concept
1. Configure a custom `SessionStorage` (or use a bundled adapter during a failure window) whose `storeSession` returns `false` on a transient write error instead of throwing (this is an explicitly supported, documented behavior per `implementing-session-storage.md`).
2. Complete OAuth (`shopify.auth.callback`) or a Token Exchange request as an anonymous merchant/browser hitting the app's `/auth/callback` or `/auth` (token-exchange) endpoint while the storage backend is failing writes.
3. Observe that `authCallback` / `performTokenExchange` / `TokenExchangeStrategy.authenticate` proceed to treat the current request as authenticated (webhooks registered, `afterAuth` hook invoked, response sent) even though `storeSession` returned `false`.
4. On the very next request for the same shop, `loadSession` returns `undefined` because nothing was persisted, forcing the app back into the OAuth/token-exchange handshake — repeating indefinitely while the storage failure persists, effectively denying legitimate use of the authentication handler for that shop.

Note: I was not able to fully verify the internal failure-return behavior of every bundled `SessionStorage` adapter (e.g., DynamoDB, MongoDB, Prisma, KV) within the available index; some of these files may return `false` under different conditions than shown for Redis/Drizzle/SQLite. If precise verification of a specific adapter's failure semantics is needed, a full read via a Devin session would be required.

  public async storeSession(session: Session): Promise<boolean> {
    try {
      const lines = this.readLines();

      let found = false;

      // process each line
      for (let i = 0; i < lines.length; i++) {
        // split the line by comma into columns
        const columns = lines[i].split(',');
        // check if the id column matches (second column is value of 'id')
        if (columns[1] === session.id) {
          // if the session id already exists, update the line
          lines[i] = session.toPropertyArray().join(',');
          found = true;
          break;
        }
      }

      if (!found) {
        // if the session id does not exist, add a new line
        lines.push(session.toPropertyArray().join(','));
      }

      try {
        this.writeLines(lines);
        return true;
      } catch (err) {
        // error on write
        return false;
      }
    } catch (err) {
      // error on read
      return false;
    }
  }
