### Title
Unmetered O(n) asset-map copy/merge cost during SUICIDE breaks FAITHFUL_METERING - ([File: actuator/src/main/java/org/tron/core/vm/utils/MUtil.java])

### Summary
`MUtil.transferAllToken()` performs two full `Protocol.Account.Builder` clones plus a `forEach` merge over the entire TRC10 asset map of the self-destructing contract, but the SUICIDE opcode is charged a fixed energy cost independent of how many distinct token balances the contract holds. An attacker can cheaply accumulate many distinct TRC10 token balances on a contract and then trigger SUICIDE, causing CPU/heap work proportional to the asset-map cardinality while paying a constant, size-independent energy fee.

### Finding Description
`transferAllToken` is invoked as part of the SUICIDE opcode handling. It builds `fromBuilder`/`toBuilder` full copies of both accounts via `toBuilder()` [1](#0-0) , calls `toAccountCap.importAllAsset()` (which itself rebuilds the entire asset map from `AccountAssetStore.getAllAssets`) [2](#0-1) , and then iterates every entry of `fromAccountCap.getAssetMapV2()` to merge balances into `toBuilder`, mutating both protobuf builders per token.

The SUICIDE opcode's metered cost, however, is a fixed constant regardless of asset-map size:
- `getSuicideCost` returns a constant `SUICIDE = 0`.
- `getSuicideCost2` adds `NEW_ACCT_CALL` (25000) only if the destination is a "dead" (non-existent) account, otherwise 0.
- `getSuicideCost3` (post fair-energy-adjustment fork) returns `SUICIDE_V2 = 5000`, plus `NEW_ACCT_CALL` if the destination account doesn't exist yet.

None of these cost functions consult the size of `fromAccountCap.getAssetMapV2()` [3](#0-2) . This is corroborated by the existing unit test `testSuicideCost`, which asserts only the fixed values `{0, 25000, 30000, 5000}` regardless of any asset holdings on the account [4](#0-3) .

Because `importAllAsset()` and the merge loop scale with the number of distinct TRC10 token IDs a contract has ever received, and there is no per-account cap on that count found in `AccountCapsule`/`AssetUtil` (only `ASSET_ISSUE_COUNT_LIMIT_MAX`, which bounds a listing-query page size, not per-account holdings) [5](#0-4) , an attacker who first funds a contract with many distinct token balances (a one-time, roughly linear-cost setup via ordinary TRC10 transfers) can subsequently trigger a single SUICIDE call whose CPU/allocation cost is O(n) while the billed SUICIDE energy remains O(1).

### Impact Explanation
This is a metering/accounting gap (FAITHFUL_METERING violation): the actual node-side work (two full `Account.Builder` copies plus an O(n) map merge) is not reflected in the energy charged for the SUICIDE opcode. Repeating this across many independently deployed, pre-funded contracts within a single block can accumulate disproportionate heap churn and CPU time relative to the energy actually billed for those transactions, contributing to block-processing latency spikes. This matches the "DoS via the TRON protocol implementation" bounty class, scoped to processing-latency/stall rather than crash or fund loss.

### Likelihood Explanation
Preconditions require only an unprivileged account: deploy a contract, fund it with N distinct TRC10 token balances via ordinary transfers (paying normal bandwidth/fee costs), then call a SUICIDE-triggering function that itself stays within a small, fixed energy budget. This is entirely achievable by a normal funded account without special privileges, and is repeatable across as many contracts as bandwidth/energy for the *setup* transactions and *SUICIDE-triggering* transactions allow within a block. The main mitigating factor is that block-level bandwidth/energy limits still bound the total number of transactions per block, and the setup cost (accumulating N distinct token balances) is paid up front and is not free — but the SUICIDE-time cost itself is disproportionate to what is billed at destruct-time, which is the actual finding.

### Recommendation
Make the SUICIDE cost functions (`getSuicideCost`, `getSuicideCost2`, `getSuicideCost3`) account for the size of the from-account's asset map (e.g., charge a per-token energy fee proportional to `fromAccountCap.getAssetMapV2().size()`), similar to how `LOG`/`MCOPY` costs scale with data size in `EnergyCost.java`. Alternatively, cap the number of distinct TRC10 tokens a single account may hold, or avoid building two full protobuf `Account.Builder` copies in `transferAllToken` in favor of an incremental/streaming merge that doesn't require doubling memory for the whole map.

  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
