### No vulnerability found for this question.

**Reasoning:** The premise that `expected_burn`/`tenure_burn_chain_tip` is read from "the current tenure_burn_chain_tip" or a live/racing burnchain tip is incorrect. Tracing the actual call path:

- `get_expected_burns` resolves `expected_burn` by looking up the `BlockSnapshot` keyed on a *fixed* `burn_view_consensus_hash` taken from the block's own `TenureChange` payload (or, if no tenure change, from the parent block's already-recorded `total_burns()`), via `SortitionDB::get_block_snapshot_consensus`. [1](#0-0) 

- Likewise, `validate_nakamoto_tenure_snapshot` (called from `validate_normal_nakamoto_block_burnchain`) resolves `tenure_burn_chain_tip` by looking up the snapshot for the block's `header.consensus_hash` — again a fixed key, not "the current burnchain tip" — and then checks that this snapshot is on the canonical fork relative to whatever the current tip happens to be. [2](#0-1) 

- `common_validate_against_burnchain` then compares `self.header.burn_spent` against this fixed `expected_burn`. [3](#0-2) 

`BlockSnapshot` rows in the sortition DB are written once, atomically, when a burnchain block finishes processing (`Burnchain::from_block_ops` / snapshot commit), and `total_burn` for a given `consensus_hash` never changes afterward — there is no "intermediate" partially-committed state visible to readers through `get_block_snapshot_consensus`, since a consensus hash only exists once the corresponding sortition block has fully committed. A concurrent, later-arriving burnchain block produces a *different* `consensus_hash`/snapshot; it does not mutate the earlier snapshot that the in-flight Nakamoto block's `burn_view_consensus_hash` points to.

So the equality `self.header.burn_spent == expected_burn` is evaluated against an immutable historical record selected by a hash that is part of the block payload itself, not against a moving "current tip." Node A and Node B, both having processed the referenced sortition, will read the identical `total_burn` value regardless of when (t0 vs t1) they query it, and regardless of any later burnchain blocks that may have since arrived. If a node hasn't yet processed the referenced sortition, `get_block_snapshot_consensus` returns `None` and the call fails closed with `NoSuchBlockError`/`InvalidStacksBlock`, not a divergent Ok result. [4](#0-3) 

Existing tests confirm this determinism explicitly: a tenure's `burn_spent` stays pinned to its election sortition's total burn even after a newer sortition becomes canonical. [5](#0-4) 

The claimed race (two nodes computing different `expected_burn` for the same block due to a "concurrent burnchain block finishing committing") does not correspond to any actual code path — the lookup key is a specific historical consensus hash, not the live tip, so there is no non-determinism to exploit.

    pub(crate) fn get_expected_burns<SH: SortitionHandle>(
        sort_handle: &SH,
        chainstate_conn: &Connection,
        block: &NakamotoBlock,
    ) -> Result<Option<u64>, ChainstateError> {
        let burn_view_ch = if let Some(tenure_payload) = block.get_tenure_tx_payload() {
            &tenure_payload.burn_view_consensus_hash
        } else {
            // if there's no new tenure for this block, the burn total should be the same as its parent
            let parent_burns_opt =
                Self::get_block_header(chainstate_conn, &block.header.parent_block_id)?
                    .map(|parent| parent.anchored_header.total_burns());
            return Ok(parent_burns_opt);
        };
        let burn_view_sn =
            SortitionDB::get_block_snapshot_consensus(sort_handle.sqlite(), burn_view_ch)?
                .ok_or_else(|| {
                    warn!("Could not load expected burns -- no such burn view";
                          "burn_view_consensus_hash" => %burn_view_ch
                    );
                    ChainstateError::NoSuchBlockError
                })?;
        Ok(Some(burn_view_sn.total_burn))
    }

    fn validate_nakamoto_tenure_snapshot(
        db_handle: &SortitionHandleConn,
        block: &NakamotoBlock,
    ) -> Result<BlockSnapshot, ChainstateError> {
        // find the sortition-winning block commit for this block, as well as the block snapshot
        // containing the parent block-commit.  This is the snapshot that corresponds to when the
        // miner begain its tenure; it may not be the burnchain tip.
        let consensus_hash = &block.header.consensus_hash;

        let sort_tip = SortitionDB::get_canonical_burn_chain_tip(db_handle)?;

        // burn chain tip that selected this commit's block (the tenure sortition)
        let Some(tenure_burn_chain_tip) =
            SortitionDB::get_block_snapshot_consensus(db_handle, consensus_hash)?
        else {
            warn!("No sortition for {}", consensus_hash);
            return Err(ChainstateError::InvalidStacksBlock(
                "No sortition for block's consensus hash".into(),
            ));
        };

        // tenure sortition is canonical
        let Some(ancestor_sort_id) = get_ancestor_sort_id(
            db_handle,
            tenure_burn_chain_tip.block_height,
            &sort_tip.sortition_id,
        )?
        else {
            // not canonical
            warn!("Invalid consensus hash: snapshot is not canonical"; "consensus_hash" => %consensus_hash);
            return Err(ChainstateError::InvalidStacksBlock(
                "No sortition for block's consensus hash -- not canonical".into(),
            ));
        };
        if ancestor_sort_id != tenure_burn_chain_tip.sortition_id {
            // not canonical
            warn!("Invalid consensus hash: snapshot is not canonical"; "consensus_hash" => %consensus_hash);
            return Err(ChainstateError::InvalidStacksBlock(
                "No sortition for block's consensus hash -- not canonical".into(),
            ));
        };

        Ok(tenure_burn_chain_tip)
    }
