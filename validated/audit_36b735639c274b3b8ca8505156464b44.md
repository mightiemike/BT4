### Title
Unprotected balance subtraction in `ExchangeCapsule.transaction()` allows exchange pool corruption when the bancor-formula result is erroneous - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The default (non-hardened) code path of `ExchangeCapsule.transaction()` computes a swap output (`buyTokenQuant`) using floating-point bancor-style math in `ExchangeProcessor`, then subtracts it from the pool balance without any bounds/sanity check, mirroring the reported Swapnet-lite pattern where an unchecked value from a rate/quantity computation is subtracted unprotected, corrupting subsequent state.

### Finding Description
`ExchangeCapsule.transaction()` obtains `buyTokenQuant` from `Processor.exchange()` and then, in the **non-hardened** branch (the default unless the `AllowHardenExchangeCalculation` proposal is active), performs a raw subtraction with no validation: [1](#0-0) 

The value being subtracted, `buyTokenQuant`, comes from `ExchangeProcessor.exchange()`, which relies on `Math.pow`-based bancor formulas involving divisions and exponentiation on `double`s derived directly from attacker/user-controlled pool balances and trade quantities: [2](#0-1) 

Because these are unchecked `double` operations (no `SafeExchangeProcessor`-style `BigDecimal`/`addExact` protection), extreme or edge-case inputs (very small `newBalance`, near-zero `supply` after large trades, or precision loss during the `1_000_000_000_000_000_000L` supply mutation) can drive `issuedSupply`/`exchangeBalance` to `NaN`, `Infinity`, or a large negative double. When cast to `long`, this yields `0`, `Long.MIN_VALUE`, or a wildly incorrect quantity — directly analogous to `_getExchangeRate` returning `0` in the Swapnet-lite report.

That erroneous `buyTokenQuant` is then used in the unprotected subtraction (`secondTokenBalance - buyTokenQuant` or `firstTokenBalance - buyTokenQuant`) in the non-hardened branch shown above, with **no check** that the resulting balance is non-negative — the negativity check `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))` only applies when `hardenedCalc` is `true`: [3](#0-2) 

This corrupted pool balance is then persisted via `Commons.putExchangeCapsule(...)` in `ExchangeTransactionActuator.execute()`, permanently poisoning the exchange's state and all future swap calculations against it — exactly the "perpetuating the problem" failure mode described in the report (a bad computed value feeds back into state used for future rate/quant computations): [4](#0-3) 

The only guard in `ExchangeTransactionActuator.doValidate()` is a lower-bound check (`anotherTokenQuant < tokenExpected`), which does not protect against negative/overflowed balances or an unexpectedly enormous payout: [5](#0-4) 

### Impact Explanation
Reaching `ExchangeCapsule.transaction()` via `ExchangeTransactionActuator` requires only broadcasting an ordinary `ExchangeTransactionContract` — no privileged role is needed, and pool sizes/quantities can be shaped over time via public `ExchangeCreate`/`ExchangeInject` operations. A corrupted (negative, overflowed, or grossly incorrect) exchange balance directly corrupts on-chain TRX/TRC10 asset accounting for that exchange pair and can be exploited to drain the pool of the "another token" or brick the market for all future participants — an accounting corruption / DoS via protocol implementation, matching the accepted impact classes.

### Likelihood Explanation
The non-hardened path is the **default** behavior (it only becomes hardened when the `AllowHardenExchangeCalculation` proposal, tracked in `DynamicPropertiesStore`/`ProposalUtil`, has been activated on the network) [6](#0-5) . Triggering the floating-point edge cases requires carefully chosen extreme pool balances/quantities, which is feasible for an attacker who can create and fund exchanges and iteratively probe values, but I could not fully verify the exact numeric thresholds at which `Maths.pow`/`MathWrapper.pow` produce `NaN`/`Infinity`/overflowing casts, since `MathWrapper.java` was not found in the indexed codebase — this needs closer numeric analysis or a live test harness to construct a concrete failing input.

### Recommendation
Apply the same protection used by `SafeExchangeProcessor`/`hardenedCalc` unconditionally (or at minimum validate `buyTokenQuant` is within `[0, buyTokenBalance]` and reject/throw before mutating and persisting `ExchangeCapsule` state) rather than gating the negative-balance check behind `hardenedCalc` only, mirroring the report's suggestion to branch/guard on an erroneous computed value before using it in unprotected arithmetic.

### Proof of Concept
Not able to construct a concrete numeric PoC from static analysis alone — this requires exercising `ExchangeProcessor.exchange()` with edge-case pool balances/quantities (e.g., extremely large `sellTokenQuant` relative to `balance`, or repeated trades driving `supply` toward zero) to confirm a `NaN`/`Infinity`/overflow cast occurs, then confirming the resulting `buyTokenQuant` produces a negative `newFirstTokenBalance`/`newSecondTokenBalance` in the non-hardened branch of `ExchangeCapsule.transaction()`. I recommend a Devin session with test/REPL access to `ExchangeProcessorTest`-style harnesses (as already present in `framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorTest.java`) to fuzz for a concrete failing input before treating this as confirmed-exploitable.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
