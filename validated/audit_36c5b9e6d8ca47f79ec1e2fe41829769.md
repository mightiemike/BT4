### Title
Webhook HMAC Validation Does Not Bind the Signed Body to the Claimed Shop Domain, Enabling Cross-Tenant Webhook Replay - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
The bug class in the report is: a resource is accepted because it satisfies a *coarse* check (matching `owner`/`mint`) instead of a check that *cryptographically or deterministically binds* it to the specific identity it claims to represent — allowing an attacker-controlled resource with a merely "valid-looking" property to be substituted for the legitimate one and drain/starve the real resource. The same structural flaw exists in shopify-app-js's webhook HMAC validation: the signature only covers the raw request body, never the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header that the rest of the pipeline trusts to select *which merchant's* offline session and data the webhook applies to.

### Finding Description
`validateHmacFromRequestFactory` computes and checks the HMAC strictly over `rawBody` and compares it to the `hmac` header value: [1](#0-0) 

Nothing in this check incorporates the shop-domain header, topic, or webhook id into the signed material — those are read out of the request separately after the HMAC has already been judged `valid`: [2](#0-1) 

Downstream, `authenticateWebhookFactory` (and the equivalent Express/Remix middlewares) unconditionally trusts `check.domain` (i.e., the `X-Shopify-Shop-Domain` header) to look up and act on that shop's offline session, without any additional binding between the signed body and the claimed domain: [3](#0-2) 

Because a merchant who has legitimately installed the app receives their own webhooks signed with the app's shared `apiSecretKey` (the same secret is used for every shop using the app, not a per-shop secret), that merchant possesses a body+HMAC pair that is cryptographically valid but is not bound to their shop identity. Nothing prevents them from replaying that exact `rawBody`/`hmac` pair while swapping the `X-Shopify-Shop-Domain` header to a victim shop's domain — the validator will still return `valid: true` because it never inspects the domain header as part of the signed content.

### Impact Explanation
Similar to the `vault_gkhan_account` finding, where a coarse check (`owner`, `mint`) let an attacker substitute a "phantom" resource for the canonical one and drain/lock the legitimate one, this flaw lets a single malicious merchant with a validly-signed webhook impersonate a different shop's webhook delivery. Depending on the topic handled by the app (e.g. `app/uninstalled`, `shop/redact`, billing-related topics), this can:
- Trigger deletion/invalidation of another shop's offline session or app data (DoS of that shop's access to the app).
- Cause the app to process attacker-controlled payload data under the victim shop's `session`/`admin` context returned from `authenticate.webhook`, corrupting or misattributing data cross-tenant.

### Likelihood Explanation
Any merchant who installs the app (an unprivileged, ordinary customer of the app — not a privileged internal actor) can capture one legitimately-signed webhook delivery to their own shop and replay it with a forged domain header against the app's public webhook endpoint. No secret material needs to be leaked; the merchant already legitimately possesses a valid `(rawBody, hmac)` pair for their own shop.

### Recommendation
Bind the webhook's claimed identity to the signed content instead of trusting an unsigned header:
- Include the `X-Shopify-Shop-Domain` (and ideally `X-Shopify-Webhook-Id`/`X-Shopify-Topic`) values as part of the HMAC input, or
- Cross-check the domain header against an out-of-band verified identifier (e.g., look up the destination shop by the `webhookId` via the Admin API, or require that the offline session for `check.domain` was created via a prior verified OAuth/token-exchange flow whose secret material is per-shop) before trusting the header to select which shop's session/data to act on.

### Proof of Concept
1. Merchant A installs the app and legitimately receives a webhook, e.g.:
   - `rawBody = '{"id": 123}'`
   - Headers include `X-Shopify-Hmac-Sha256: <valid hmac over rawBody>`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Topic: app/uninstalled`.
2. Merchant A captures this exact request and re-sends it to the app's `/webhooks` endpoint, changing only `X-Shopify-Shop-Domain` to `shop-b.myshopify.com` (a victim shop that also has the app installed).
3. `shopify.webhooks.validate` / `validateHmacFromRequestFactory` recomputes the HMAC over the unchanged `rawBody` and finds it matches the unchanged `X-Shopify-Hmac-Sha256` header — validation succeeds (`valid: true`, `domain: 'shop-b.myshopify.com'`).
4. `authenticateWebhookFactory` proceeds to call `ensureValidOfflineSession(params, 'shop-b.myshopify.com')` and executes the `app/uninstalled` handler against shop B's session, e.g. deleting shop B's stored offline session — a denial of service against a shop the attacker never controlled.
