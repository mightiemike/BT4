### Title
NullPointerException in `RepositoryImpl.commitCodeCache`/other commit* methods when `Value.create` is given an empty/null byte[] while `VMConfig.allowMultiSign()` is false - (File: actuator/src/main/java/org/tron/core/vm/repository/Value.java)

### Finding Description
`Value`'s private constructor only assigns `this.type` when `value != null`; when `value == null` it only sets `this.type = new Type(Type.UNKNOWN)` inside an `if (VMConfig.allowMultiSign())` branch, leaving `this.type` as its default `null` when the flag is disabled. [1](#0-0) 

`Value.create(byte[] value, int type)` normalizes any empty (`length == 0`) or `null` byte array to `null` before invoking that constructor: [2](#0-1) 

`RepositoryImpl.saveCode` unconditionally stores whatever code bytes it receives (including empty arrays) via `Value.create(code, Type.CREATE)`: [3](#0-2) 

During `commit()`, `commitCodeCache` (and every other `commit*Cache` method for accounts, contracts, contract state, dynamic properties, delegated resources, votes, delegation, delegated-resource-index) calls `value.getType().isDirty() || value.getType().isCreate()` without a null check: [4](#0-3) 

If `VMConfig.allowMultiSign()` returns `false` at the time the `Value` object is constructed, `value.getType()` is `null`, and this call throws a `NullPointerException`, aborting `commit()` mid-way for that cache (and any caches processed after it, since `commit()` calls each `commit*Cache` sequentially). [5](#0-4) 

An empty code array reaching `saveCode` is a realistic, unprivileged-attacker-reachable condition: a deployed contract whose constructor/init code legitimately returns zero-length runtime code (e.g., a contract that performs `return(0,0)` or self-destructs during construction) is valid EVM/TVM behavior, not an error condition, so it is not rejected upstream before reaching `saveCode`.

### Impact Explanation
An uncaught `NullPointerException` during `commit()` breaks the deterministic state-commit sequence of the child `Repository` to its parent (or to the underlying stores at the top level). Because `commit()` processes caches in a fixed order and `commitCodeCache` runs early, an NPE there prevents subsequent `commit*Cache` calls (accounts, contracts, delegated resources, votes, delegation, delegated-resource index) from executing, leaving state changes for balances, delegated resource bookkeeping, and votes uncommitted for that repository layer. Depending on where the exception propagates, this can manifest as a transaction/block-processing failure or state divergence between nodes if the flag's effective value differs across nodes at the time of execution.

### Likelihood Explanation
This requires: (1) `VMConfig.allowMultiSign()` to be `false` (default before the corresponding chain parameter/proposal is enabled — relevant for private/consortium chains, freshly bootstrapped networks, or historical replay before the proposal activation height); and (2) an unprivileged user deploying/calling a contract whose constructor returns zero-length code, which is straightforward and requires no special privileges — any account can submit a `CreateSmartContract` with init bytecode ending in `RETURN` with size 0. Given these two conditions, the bug is deterministically reproducible every time such a deployment occurs.

### Recommendation
Fix `Value`'s constructor so `type` is never left `null`: always assign a `Type` object (e.g., default to `Type.NORMAL` or the requested `type`) regardless of `VMConfig.allowMultiSign()`, or make `Value.getType()` return a non-null default. Additionally, add defensive null checks in all `commit*Cache` methods in `RepositoryImpl` before calling `value.getType()`.

### Proof of Concept
```java
// Java unit test in actuator/src/test/java/org/tron/core/vm/repository/ValueNpeTest.java
@Test
public void testEmptyCodeValueCausesNpeOnCommit() {
  // Simulate VMConfig.allowMultiSign() == false (disabled multisign chain parameter)
  // e.g. via ConfigLoader/VMConfig test setter that forces allowMultiSign to false

  RepositoryImpl repo = RepositoryImpl.createRoot(storeFactory);
  byte[] address = randomAddress();
  byte[] emptyCode = new byte[0]; // legitimate zero-length runtime code from a CREATE

  repo.saveCode(address, emptyCode);

  // Expect commit() to complete without NPE and codeCache Value.getType() to be non-null
  assertDoesNotThrow(repo::commit);
}
```
Expected (buggy) result: `commit()` throws `NullPointerException` at `RepositoryImpl.commitCodeCache` line `value.getType().isDirty()` because `Value.getType()` is `null` for the empty-code `Value` object. A fuzz/invariant harness generating `CreateSmartContract`/`TriggerSmartContract` payloads that yield empty init-code returns should assert `commit()` never throws and every cached `Value`'s `getType()` is non-null.
