## Analysis: Unbounded `PendingInbounds` Scan in `AfterBallotTerminal` Triggered by Batch Ballot Expiry

### Title
Unbounded O(n) `PendingInbounds.Walk` Triggered Per-Ballot in `EndBlocker` Batch Expiry Enables Quadratic-Cost DoS - (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
The Knox bug class is an unbounded loop over attacker-inflatable state executed synchronously and reachable without special privilege. The Push Chain analog is `afterInboundBallotTerminal` in `x/uexecutor/keeper/ballot_hooks.go`, which performs a full linear `Walk` over the entire `PendingInbounds` collection every time a single inbound ballot terminates, in order to locate the owning entry by scanning every variant of every pending entry.

### Finding Description
`RecordInboundVote` (`x/uexecutor/keeper/inbound.go` L27-88) creates a `PendingInboundEntry` the first time any validator votes on a given inbound `utx_key`, and this is invoked from `VoteInbound` (`x/uexecutor/keeper/msg_vote_inbound.go` L18-75) for every distinct source-chain event that gets observed. Because `utx_key = sha256(source_chain:tx_hash:log_index)` [1](#0-0) , an ordinary unprivileged user can trigger arbitrarily many *distinct* pending inbound entries simply by submitting many low-value cross-chain deposit transactions on a supported external source chain — this is exactly "ordinary user deposits ... alone" per the allowed-impact scope, no validator or admin collusion required (validators only relay/observe what genuinely happened on-chain).

Ballots for these entries are voted on and, if not resolved by validators before `BlockHeightExpiry`, are expired in a batch by `ExpireBallotsBeforeHeight` (`x/uvalidator/keeper/ballot.go` L320-364), which is driven automatically by `x/uvalidator/abci.go`'s `EndBlocker` — no privileged trigger needed. That function iterates all currently active ballots and, for each one past its expiry height, calls `k.MarkBallotExpired`, which in turn synchronously invokes the `BallotHooks.AfterBallotTerminal` callback (`x/uvalidator/keeper/ballot.go` L200-211).

For `INBOUND_TX` ballots, this callback is `afterInboundBallotTerminal` (`x/uexecutor/keeper/ballot_hooks.go` L72-143), which — because ballot IDs are one-way digests and cannot be reverse-mapped to their owning entry — performs a **full `Walk` over the entire `PendingInbounds` map**, and for each entry linearly scans its `Variants` slice looking for a matching `BallotId`: [2](#0-1) 

If an attacker seeds `N` distinct low-value cross-chain deposits within roughly the same expiry window (default `DefaultExpiryAfterBlocks`, `x/uexecutor/types/constants.go`), and validators fail to reach quorum on any of them before expiry (e.g. because the destination chain / payload is deliberately malformed so nothing finalizes, or simply because they are submitted in a burst near the expiry deadline), then a single `EndBlocker` invocation of `ExpireBallotsBeforeHeight` will call `MarkBallotExpired` up to `N` times, and **each** of those calls performs an independent O(N) `Walk` over `PendingInbounds` inside `afterInboundBallotTerminal`. This yields O(N²) synchronous, in-consensus work executed inside a single block's `EndBlocker`, entirely attacker-seeded and requiring no privileged actor.

This is structurally identical to the Knox bug class: an unbounded loop over an attacker-inflatable collection, executed as part of normal (here: automatic, block-driven) processing, with the potential to make block processing arbitrarily expensive as the attacker grows `N`.

### Impact Explanation
If enough low-cost source-chain deposits are queued to expire in the same window, the resulting O(N²) `EndBlocker` cost can materially degrade or stall block production for all validators simultaneously (since `EndBlocker` logic is deterministic and executed identically by every honest node) — a network-wide, non-privileged, in-scope DoS ("denial of service only when it is not network-level and is reachable without privileged control" — this is node/consensus-level slow-down, not merely a network-layer issue, and requires no privileged actor). Because `PendingOutbounds` explicitly documents that ballot expiry does **not** trigger removal (to avoid double-pay risk), and `PendingInbounds` cleanup is the only removal path proportional to `N`, an attacker can keep the collection large indefinitely by continuing to submit cheap deposits, sustaining the attack.

### Likelihood Explanation
The cost to an attacker is bounded by the gas/fees for many small deposit transactions on an inexpensive external source chain — cheap relative to the effect of imposing O(N²) validator-side computation. No special access, validator key, or governance action is required; a normal user (or Sybil of low-value UEA/CEA deposits) can populate `PendingInbounds` at will. The only constraint is causing many ballots to expire near-simultaneously, which is achievable by submitting a burst of deposits within one expiry window and ensuring they don't reach quorum (e.g., targeting a chain/asset pairing that's disabled or malformed post-submission, or simply timing submission at the tail end of the expiry window across many entries).

### Recommendation
- Avoid the reverse O(n) scan entirely: maintain a secondary index keyed by `ballotID -> utxKey` (populated in `RecordInboundVote` alongside the existing entry) so `afterInboundBallotTerminal` can do an O(1) lookup instead of walking all of `PendingInbounds`.
- Bound per-block hook-driven work: cap the number of ballot expirations processed (and therefore hooks fired) per `EndBlocker` invocation, deferring the remainder to subsequent blocks.
- Consider rate-limiting/bonding requirements on inbound observation creation (e.g., minimum value thresholds already discussed for the Knox `minSize` analog) to make flooding `PendingInbounds` economically costly.

### Proof of Concept
Conceptual sequence (would need to be validated in an integration/simulation test against `x/uvalidator/abci.go`'s `EndBlocker` and `x/uexecutor/keeper/ballot_hooks.go`):
1. Attacker submits `N` distinct low-value cross-chain deposit transactions on a supported external chain within the same `DefaultExpiryAfterBlocks` window, each producing a unique `(source_chain, tx_hash, log_index)` triple and hence a unique `utx_key`/`PendingInboundEntry`.
2. Validators observe and vote via `VoteInbound`, populating `N` entries in `PendingInbounds` (`RecordInboundVote`), but quorum is not reached for any of them (attacker can make destination-side details slightly divergent per validator, or simply rely on natural asynchrony/expiry timing).
3. At the shared expiry height, `x/uvalidator`'s `EndBlocker` calls `ExpireBallotsBeforeHeight`, which calls `MarkBallotExpired` for each of the `N` ballots in the same block.
4. Each `MarkBallotExpired` call fires `AfterBallotTerminal` → `afterInboundBallotTerminal`, each performing a full `Walk` over the (still size-`N`) `PendingInbounds` collection — `N` walks of size `N`, i.e., O(N²) work in one `EndBlocker` execution.
5. Increasing `N` demonstrates unbounded, attacker-controlled growth in per-block computation, mirroring the Knox `_previewWithdraw`/`_redeemMax` DoS pattern but on Push Chain's ballot-finalization/EndBlocker path. [3](#0-2) [4](#0-3)

	}

// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}

	// Close iterator explicitly before mutation phase to release the IAVL snapshot
	iter.Close()

	if len(toExpire) > 0 {
		k.Logger().Debug("expiring stale ballots", "count", len(toExpire), "current_height", currentHeight)
	}

	// Phase 2: expire collected ballots (safe — iterator is closed)
	for _, id := range toExpire {
		if err := k.MarkBallotExpired(ctx, id); err != nil {
			return err
		}
	}

	return nil
}
