**Analysis:** The `Usage.items`/`bytes` fields in `state_storage.move` are populated by the native `get_state_storage_usage_only_at_epoch_beginning`, which calls the resolver's `get_usage()` [1](#0-0) , itself backed by the incrementally-maintained `StateStorageUsage` counter in `storage/storage-interface/src/state_store/state.rs`.

That counter is updated via `update_usage`/`usage_delta_for_shard`, which computes item/byte deltas directly from the actual write ops applied to state (`Creation`/`Modification`/`Deletion`) by reading the prior occupied/vacant status of each touched key from the state cache or overlay before applying the delta [2](#0-1) . This mechanism is key-agnostic: a table entry is just another `StateKey`, and its creation/deletion is accounted for exactly like any other resource — one item added on occupied-write, one item removed on occupied-to-vacant transition — with an explicit invariant assertion (`expect_old_slot`) that every updated key must have been read and recorded in the cache, or the code panics rather than silently drifting [3](#0-2) .

Because usage is derived transactionally from the same write-set that produces the JMT leaves (each occupied `StateSlot` corresponds 1:1 to a committed leaf, and each vacant slot to an absent leaf), rapid churn of table entries within a block does not desynchronize `items`/`bytes` from the JMT leaf count — the delta computation is invoked once per net write-set entry regardless of how many intermediate creates/deletes occurred, and the accounting tests (`test_usage_delta_new_occupied_key`, `test_usage_delta_deletion_removes_item`, `test_update_usage_sums_deltas`) confirm the sums stay consistent [4](#0-3) . There is no code path where `on_new_block`'s snapshot read of usage can diverge from the true committed leaf count due to unprivileged table-entry churn; the theorized divergence is not supported by the actual accounting design, which is derived from write-set deltas rather than an independently-drifting counter.

fn native_get_usage(
    context: &mut SafeNativeContext,
    _ty_args: &[Type],
    _args: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    assert!(_ty_args.is_empty());
    assert!(_args.is_empty());

    context.charge(STATE_STORAGE_GET_USAGE_BASE_COST)?;

    let ctx = context.extensions().get::<NativeStateStorageContext>();
    let usage = ctx.resolver.get_usage().map_err(|err| {
        PartialVMError::new(StatusCode::VM_EXTENSION_ERROR)
            .with_message(format!("Failed to get state storage usage: {}", err))
    })?;

    Ok(smallvec![Value::struct_(Struct::pack(vec![
        Value::u64(usage.items() as u64),
        Value::u64(usage.bytes() as u64),
    ]))])
}

    fn usage_delta_for_shard<'kv>(
        cache: &StateCacheShard,
        overlay: &LayeredMap<HashValue, StateSlot>,
        updates: &HashMap<&'kv StateKey, StateUpdateRef<'kv>>,
    ) -> (i64, i64) {
        let mut items_delta: i64 = 0;
        let mut bytes_delta: i64 = 0;
        for (k, v) in updates {
            let state_value_opt = match v.state_op.as_state_value_opt() {
                Some(value_opt) => value_opt,
                None => continue,
            };

            let key_size = k.size();
            if let Some(value) = state_value_opt {
                items_delta += 1;
                bytes_delta += (key_size + value.size()) as i64;
            }

            // n.b. all updated state items must be read and recorded in the state cache,
            // otherwise we can't calculate the correct usage.
            let old_slot = Self::expect_old_slot(overlay, cache, k);
            if old_slot.is_occupied() {
                items_delta -= 1;
                bytes_delta -= (key_size + old_slot.size()) as i64;
            }
        }
        (items_delta, bytes_delta)
    }
