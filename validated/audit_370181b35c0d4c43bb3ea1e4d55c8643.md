## Analog Found

### Title
Front-runnable Bancor-style Exchange lacks meaningful slippage protection because callers fully control the `expected` minimum-output parameter - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
Java-tron's on-chain Bancor-style token exchange (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract`) prices trades purely from two on-chain reserve balances stored in `ExchangeCapsule`. Any unprivileged account can submit an `ExchangeTransactionContract` and self-supply the `expected` (minimum received) value, exactly mirroring the `AutoPxGlp::compound`/`PirexGmx::depositGlp` pattern where a caller-supplied `_minUsdg`/`_minGlp` is the only guard against price manipulation, and can be set to a value that is technically non-zero but economically meaningless.

### Finding Description
`ExchangeTransactionContract` carries a caller-chosen `expected` field [1](#0-0) , which is used in `ExchangeTransactionActuator.doValidate()` as the sole slippage protection: the only bound enforced is `tokenExpected <= 0` must throw, and the executed swap amount must simply be `>= tokenExpected` [2](#0-1) . There is no protocol-level floor tied to real economic value (e.g., 1 unit of an 18-decimal-equivalent TRC10 token is virtually zero), exactly like the `_minUsdg`/`_minGlp` == 1 case described in the external report.

The trade price itself is derived solely from the two mutable on-chain reserves (`firstTokenBalance`/`secondTokenBalance`) tracked in `ExchangeCapsule.transaction()` [3](#0-2) . Those reserves can be shifted by any account issuing `ExchangeInjectContract`/`ExchangeWithdrawContract` calls (also unprivileged, ordinary user-callable, per the wallet client helper methods) immediately before/after a victim's `ExchangeTransactionContract` lands in the same block, exactly as GMX's `GlpManager`/`Vault` price is manipulable in the referenced report. Since the swap execution and validation happen in `execute`/`doValidate` using the exchange's current reserve state at execution time [4](#0-3) , a front-run reserve shift combined with a caller-set `expected=1` allows the trade to execute at an arbitrarily bad price for the trader while still satisfying validation.

### Impact Explanation
A dApp/wallet integrator (or a malicious relayer/aggregator building the transaction on a user's behalf) that sets `expected` too low — or a user who blindly accepts a wallet default of `1` — has no on-chain protection against reserve manipulation via front-running `ExchangeInjectContract`/`ExchangeWithdrawContract`/other `ExchangeTransactionContract` calls. This directly parallels "compounded assets may be lost" in the original report: token value can be extracted from an unwitting swap because the only guard (`expected`) is fully attacker/caller-controllable and not tied to any independent price reference. This is a genuine unprivileged-user accounting/market impact (loss of funds in a public exchange primitive), not a theoretical or trusted-role-only issue.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a victim transaction with a low/degenerate `expected` value (common if wallets/dApps set minimal slippage guards or if the flow is automated/integrated without proper UI validation) and (b) an attacker able to observe the pending transaction and inject a manipulating trade beforehand (front-running via mempool/block proposer ordering, which is a realistic capability on any blockchain with a visible transaction pool). No special privileges are needed by the attacker — `ExchangeInjectContract`, `ExchangeWithdrawContract`, and `ExchangeTransactionContract` are all plain user-signed contracts.

### Recommendation
- Do not rely solely on caller-supplied `expected` as the only protection; consider adding a protocol-level minimum relative slippage bound (e.g., percentage-based) rather than allowing an absolute value as low as `1`.
- Consider rate-limiting or time-weighting reserve changes (e.g., TWAP-like smoothing) for `ExchangeCapsule` pricing so that a single-block `Inject`/`Withdraw` cannot drastically move the price used by a same-block `ExchangeTransactionContract`.
- Document/enforce wallet-level guidance that `expected` must be computed from a realistic minimum-received threshold, and consider warning/rejecting `expected` values that are implausibly small relative to the trade `quant` and current exchange reserves.

### Proof of Concept
1. Attacker observes a pending `ExchangeTransactionContract` from Victim with `token_id=X`, `quant=Q`, `expected=1` (or any negligible value) targeting `exchange_id=E`.
2. Attacker submits `ExchangeInjectContract`/`ExchangeWithdrawContract` for `exchange_id=E` (or a large `ExchangeTransactionContract`) to shift `firstTokenBalance`/`secondTokenBalance` [5](#0-4)  before Victim's transaction is packed into the block.
3. Victim's `ExchangeTransactionActuator.execute()` computes `anotherTokenQuant` from the now-manipulated reserves via `ExchangeCapsule.transaction()` [6](#0-5) , and passes validation because `anotherTokenQuant >= 1` is trivially true [7](#0-6) .
4. Attacker reverses the reserve shift (e.g., withdraw/inject back or execute the opposite-direction swap) to capture the spread, leaving Victim's swap executed at a manipulated, unfavorable price.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
