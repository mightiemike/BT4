### Title
Witness commission ("brokerage") changes take effect for the entire next reward cycle with no timelock, letting a witness front-run reward distribution and starve voters of rewards - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
`UpdateBrokerageActuator` lets the account controlling a Super Representative (witness) change its "brokerage" (commission) percentage — the split between what the witness owner keeps and what is distributed to its voters — at any block, with no delay, queue, or minimum-notice mechanism, up to 100%.

### Finding Description
`UpdateBrokerageActuator.execute()` writes the new brokerage value directly to the "default" (`cycle = -1`) slot for the witness with no restriction other than a `0–100` range check performed in `validate()`: [1](#0-0) [2](#0-1) 

The stored default value is later "snapshotted" into the concrete cycle record used for reward accounting. This happens in `MaintenanceManager.doMaintenance()`, which runs whenever a maintenance/epoch boundary is crossed: it reads the witness's *current* default brokerage and copies it forward into the record for `nextCycle`: [3](#0-2) 

`MortgageService.payReward()` (which is invoked for both block rewards and transaction-fee rewards) looks up the brokerage rate for the account's `currentCycleNumber` and immediately splits the reward, sending `brokerageAmount` to the witness owner's allowance and only the remainder to the voter-reward pool for that cycle: [4](#0-3) 

Because `doMaintenance()` reads whatever the "default" brokerage value is *at the exact moment the maintenance boundary is crossed*, a witness owner can submit an `UpdateBrokerageContract` transaction in the block(s) immediately preceding the maintenance boundary, setting brokerage to `100`. That value is snapshotted into `nextCycle`'s brokerage record before any voter has a chance to react (unstake/unvote), and it then governs 100% of that witness's reward split for the entire following cycle. Unlike the pre-fix Celo `Validators.updateCommission`, java-tron does add one layer of indirection (writes go to a "default" slot, and only the per-cycle snapshot matters for payouts) — but there is no minimum notice period, timelock, or queuing between when the owner sets the value and when it is committed into the effective cycle record. The commit happens atomically at the very next maintenance cycle change, which can be triggered by a single block, giving voters no reliable advance warning.

### Impact Explanation
A witness owner can capture up to 100% of both block rewards and transaction-fee rewards earned by their SR for an entire cycle, denying the SR's voters their expected share of the reward, matching the reward-misallocation/accounting-integrity impact class described in the H02 report. Since witness registration and voting are permissionless (any account can freeze TRX to vote and any account can register as a witness), the affected voters are ordinary unprivileged users of the network's staking/reward mechanism.

### Likelihood Explanation
Likelihood is moderate-to-high in principle: any existing SR owner (a role obtainable by anyone who registers via `WitnessCreateContract`) can execute this without any other privilege, and the exploit only requires timing a single transaction correctly relative to the known, deterministic `nextMaintenanceTime`. However, the attack yields a one-cycle windfall for the malicious SR at the cost of its own future vote count/reputation (voters would presumably un-vote once they notice), which somewhat limits repeated abuse but does not prevent a single profitable extraction event just before a maintenance boundary.

### Recommendation
Introduce an explicit delay for brokerage changes analogous to the Celo fix: queue the new brokerage value in `UpdateBrokerageActuator.execute()` and only allow it to become the value copied into a cycle's snapshot after it has been pending for a minimum number of blocks/cycles (e.g., require it to have been set at least one full cycle before the maintenance boundary that would apply it), rather than always using whatever the default value happens to be at the instant `doMaintenance()` runs.

### Proof of Concept
1. Attacker controls an already-active SR/witness account `W` (obtainable permissionlessly by registering + being voted into the active set).
2. Shortly before `consensusDelegate.getNextMaintenanceTime()` is reached (deterministic and publicly known), `W` broadcasts `UpdateBrokerageContract{owner_address: W, brokerage: 100}`.
3. `UpdateBrokerageActuator.execute()` stores `brokerage=100` in the "default" (`cycle=-1`) key for `W` [1](#0-0) .
4. The next block crosses the maintenance boundary; `MaintenanceManager.doMaintenance()` runs and copies the current default (100) into `nextCycle`'s brokerage record for `W` [3](#0-2) .
5. For the entirety of `nextCycle`, every `payBlockReward`/`payTransactionFeeReward` call for `W` routes 100% of the reward to `W`'s own allowance via `adjustAllowance(witnessAddress, brokerageAmount)`, leaving `0` for the voter reward pool (`delegationStore.addReward`) [4](#0-3) .
6. Voters who staked/voted for `W` withdraw `0` rewards for that cycle when calling `withdrawReward`, despite having contributed voting power.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
