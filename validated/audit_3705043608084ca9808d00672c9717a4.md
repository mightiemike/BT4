## Title
Unbounded, unbounded duplicate-ID growth in `KVSessionStorage`'s shop→session index enables session-lookup Denial-of-Service - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
The Sherlock finding describes an unbounded array (`DepositManager`'s deposit list) that is repeatedly appended to without limits, so a legitimate-looking action performed at high volume causes downstream loops over that array to blow the gas limit and brick refunds. The same "append-without-dedupe/bound, then iterate-all-on-read" pattern exists in the Cloudflare KV session-storage adapter shipped in `shopify-app-js`: every call to `storeSession()` unconditionally pushes the session id onto a per-shop index array, and `findSessionsByShop()` later iterates and fetches every id in that array with no upper bound.

### Finding Description
`KVSessionStorage.storeSession()` always calls `addShopIds(session.shop, [session.id])` regardless of whether that session id is already indexed: [1](#0-0) 

`addShopIds()` blindly concatenates the new id onto the existing list with no de-duplication check: [2](#0-1) 

Contrast this with the Redis adapter shipped in the same monorepo, which explicitly guards against duplicates before pushing: [3](#0-2) 

`storeSession` is invoked on essentially every authenticated request path where the current session is not active, both in the offline-token-exchange strategy used by `shopify-app-remix`/`shopify-app-react-router`: [4](#0-3) 

and the equivalent Express middleware: [5](#0-4) 

Because the offline session id is deterministic (`offline_${shop}`), repeated invocations of this path for the same shop (e.g., app uninstall/reinstall cycles, forced 401→`invalidateAccessToken`→re-exchange cycles, or short-lived tokens when `expiringOfflineAccessTokens` is enabled) each append a duplicate entry to the shop's KV index array with no cap. This index array is later fully iterated in `findSessionsByShop()`: [6](#0-5) 

`findSessionsByShop` itself is invoked from `AppInstallations.includes()`/`delete()` (used to check/act on install status) and from the token-exchange/OAuth flows: [7](#0-6) 

As the index grows unbounded, every subsequent `findSessionsByShop` call fans out one KV `get` per (duplicated) id via `Promise.all`, so the cost of session lookups grows linearly and unboundedly with the number of times the shop went through this re-authentication path — directly analogous to the unbounded-array/for-loop DoS root cause in the H-7 report, just realized as unbounded KV read fan-out/latency instead of EVM gas.

### Impact Explanation
A shop that repeatedly triggers this code path (self-uninstall/reinstall, forced session invalidation, or naturally through expiring offline tokens) causes its own shop-index array in KV storage to grow without bound. Because `findSessionsByShop`/`AppInstallations.includes()`/`.delete()` iterate and fetch every entry, this degrades (and can eventually exhaust CPU-time/request budgets on platforms like Cloudflare Workers, where this adapter is designed to run) the session-lookup and app-installation-check logic, which is on the critical path of every authenticated/OAuth/token-exchange request for that app deployment — a resource-exhaustion/DoS condition affecting a shared app backend, not just the triggering shop.

### Likelihood Explanation
This requires no privileged access — a single merchant repeatedly going through the normal (or intentionally repeated) OAuth/token-exchange re-authentication flow for their own shop is sufficient to keep appending to the same array, since `storeSession` is called on every request where the session is not currently active, with no de-duplication guard in the KV adapter (unlike the Redis adapter in the same repo, which does guard against this).

### Recommendation
Add the same de-duplication check used in `RedisSessionStorage.addKeyToShopList` to `KVSessionStorage.addShopIds` (only push the id if `!shopIds.includes(id)`), and/or bound the number of ids tracked per shop, mirroring the fix pattern applied to the analogous unbounded-array issue in the reference report.

### Proof of Concept
1. Configure a Worker app using `KVSessionStorage`.
2. For a given shop, repeatedly force the offline session to be considered inactive (e.g., trigger `invalidateAccessToken` via a simulated 401, or enable `expiringOfflineAccessTokens` and let short-lived tokens lapse) and re-hit the authenticated endpoint so `token-exchange.ts`'s `authenticate()` runs the `storeSession(offlineSession)` branch each time: [4](#0-3) 
3. Inspect the KV entry at `shop:<shop>`; observe the id array growing by one duplicate entry (`offline_<shop>`) per iteration with no cap, per `addShopIds`: [2](#0-1) 
4. Call `findSessionsByShop(shop)` or `AppInstallations.includes(shop)` and observe the number of KV `get` calls/latency scale linearly with the accumulated duplicate count, with no upper bound enforced anywhere in the adapter.

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    const sessionIds = await this.namespace.get<string[]>(
      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );
  }

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }

  async includes(shopDomain: string): Promise<boolean> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      for (const session of shopSessions) {
        if (session.accessToken) return true;
      }
    }
    return false;
  }

  async delete(shopDomain: string): Promise<void> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      await this.sessionStorage.deleteSessions!(
        shopSessions.map((session: Session) => session.id),
      );
    }
  }
