### Title
Wallet Contract eth-implicit accounts can be permanently bricked by a malicious/oversized cross-contract response - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The `WalletContract` (near-wallet-contract, used to give eth-implicit accounts NEAR/NEP-141 "ERC-20"-style transfer semantics) protects itself against concurrent execution with a `has_in_flight_tx` boolean flag that is only ever cleared to `false` inside its own private callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). `rlp_execute` unconditionally refuses to start a new transaction whenever this flag is `true` [1](#0-0) . This is structurally analogous to OpenQ's `DepositManagerV1`/`ClaimManagerV1` pattern where a single mandatory external call must succeed for the state machine to unlock — except here the "malicious ERC20" is any attacker-controlled or adversarial NEP-141 token / target contract that the wallet is asked to call.

### Finding Description
Whenever `rlp_execute` dispatches an emulated ERC-20 transfer or an arbitrary FunctionCall action, it chains a `.then(...)` callback (`nep_141_storage_balance_callback` or `rlp_execute_callback`) that is responsible for resetting `has_in_flight_tx = false` as its very first statement [2](#0-1) [3](#0-2) .

nearcore's runtime documents that "a receipt whose result is `Err` triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting" — i.e. **all state writes made during a failing receipt, including ones made before the point of failure, are discarded** [4](#0-3) . This applies even to failures caused entirely by protocol-level checks rather than contract logic — e.g. `TotalPromiseInputSizeExceeded`, which fires when the combined size of a receipt's input `PromiseResult` data exceeds `max_receipt_total_input_size` (an `ActionErrorKind` enforced before/around the callback's own execution) [5](#0-4) [6](#0-5) .

Because the callback receipt's promise input includes the return value of the previous cross-contract call, an attacker-controlled contract that the wallet is instructed to call as the `target`/token (e.g. via an emulated ERC-20 `transfer`, or any generic `Action::FunctionCall` routed through `rlp_execute_callback`) can return an oversized payload from that call. When the size of that returned data exceeds the receipt input-size limit, the callback receipt fails at the protocol level with `TotalPromiseInputSizeExceeded` before/independent of the callback's own logic completing normally, so the `self.has_in_flight_tx = false;` write made at the top of `rlp_execute_callback`/`nep_141_storage_balance_callback` is rolled back along with everything else in that receipt.

Once this happens, `has_in_flight_tx` remains permanently `true` in the wallet contract's persisted state. Every subsequent call to `rlp_execute` — the sole entry point for using the eth-implicit account — is rejected with `"transaction already in progress, please try again later"` [7](#0-6) . There is no other method on `WalletContract` that can reset the flag (`ban_relayer` also resets it, but is only reachable via the same promise chain, which never fires). The wallet's own doc comment even states the flag is an invariant that "must be `true` ... and `false` otherwise" with no described recovery path [8](#0-7) .

The existing test `test_insufficient_gas` demonstrates the contract's designers assumed any failure prior to promise creation is safely rolled back and leaves the contract "still usable afterwards" [9](#0-8)  — but this assumption does not hold for failures that occur *inside* the async callback receipt itself (after `has_in_flight_tx = true` has already been durably committed by the initiating receipt), because such a failure rolls back the callback's own `has_in_flight_tx = false` write, not the initiating one.

### Impact Explanation
This produces **permanently frozen funds**, one of the explicitly accepted impact classes: every $NEAR balance and every NEP-141 token balance held by the eth-implicit account becomes permanently inaccessible, since `rlp_execute` is the only way to move funds out of (or interact with) the wallet contract, and it is unconditionally gated by the stuck flag. This mirrors the OpenQ analog exactly: a single interaction with an adversarial/malicious external contract (playing the role of the malicious ERC20 token) bricks the entire account and locks the funds indefinitely, with no expiry or recovery mechanism (unlike the OpenQ bounty, which at least unlocks at expiry — here there is no unlock condition at all).

### Likelihood Explanation
Reachable by a single unprivileged actor: the account owner (or a relayer holding a function-call access key restricted to `rlp_execute`, which is the documented normal operating mode for this contract) simply signs/relays an RLP transaction whose `target` is a contract they (or an attacker who tricks them) control, and that contract returns an oversized value from the invoked method. No validator, network, or node compromise is required — this is purely a consequence of external, attacker-influenced call data size versus the protocol's fixed receipt input-size limit, exactly the class of interaction OpenQ's bug report calls out ("any malicious user can fund/interact ... and prevent winners from withdrawing").

### Recommendation
- Do not rely solely on a state flag that is written before making an outbound call and cleared only inside the eventual callback; instead ensure `has_in_flight_tx` clearing is resilient to any callback failure mode, e.g. by moving the flag-clearing logic to a wrapping mechanism that is guaranteed to run regardless of whether the inner promise/receipt succeeds, fails, or is rejected by protocol-level limits (e.g., a lower-gas/lower-risk "finally" callback that only touches the flag and nothing else, so it cannot itself hit `TotalPromiseInputSizeExceeded`).
- Alternatively, bound/validate the size of data returned by the called `target` contract before chaining it into the callback that also carries the state-unlocking write, or restructure so the flag reset does not depend on successfully processing potentially attacker-sized promise results.
- Add a permissionless recovery/timeout path (e.g., an owner or time-gated "force unlock" method) so a stuck `has_in_flight_tx` can eventually be cleared even if the above mitigations miss an edge case.

### Proof of Concept
1. Deploy `WalletContract` as the code for an eth-implicit account (as in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/emulation.rs`), following the pattern of `test_erc20_emulation` [10](#0-9) .
2. Deploy a malicious "token"/target contract whose function (invoked as the `target` of an RLP-encoded emulated ERC-20 transfer, or any plain `FunctionCall` action) returns a value sized to exceed `max_receipt_total_input_size` when included as the callback's `input_data_ids` (this is precisely the scenario exercised by `test_promise_input_size_limit_fails_callback`, showing such a callback fails with `ActionErrorKind::TotalPromiseInputSizeExceeded`) [11](#0-10) .
3. Sign and relay an RLP transaction via `rlp_execute` targeting this malicious contract. `inner_rlp_execute` sets `has_in_flight_tx = true` and chains `.then(ext.rlp_execute_callback(...))` [12](#0-11) .
4. The malicious contract's call succeeds and returns the oversized payload; the subsequent `rlp_execute_callback` receipt fails at the protocol level with `TotalPromiseInputSizeExceeded` before its logic durably resets `has_in_flight_tx`.
5. Call `rlp_execute` again with any valid transaction (e.g. a simple $NEAR transfer as in `test_simultaneous_transactions` [13](#0-12) ): it is rejected forever with `"Error: transaction already in progress, please try again later."`, and no further method can unstick it — the wallet and its funds are permanently frozen.

*(Note: I was unable to fully verify the precise byte threshold of `max_receipt_total_input_size` from the index in this pass — a background Devin session with full repo access would be needed to confirm the exact value in `core/parameters/src/vm.rs` and reproduce the PoC end-to-end.)*

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

        .enable_rpc()
        .add_user_account(&account, Balance::from_near(100))

        env.rpc_node().tx_deploy_contract(&account, near_test_contracts::rs_contract().to_vec());

    // Two callee contracts each return 2.5 MiB (individually below `max_length_returned_data`
    // = 4 MiB, so each data receipt is valid), joined into a single callback whose
    // combined promise inputs (~5 MiB) exceed the 4 MiB limit.

    let callee_gas = 110_000_000_000_000u64;

    let args = serde_json::json!([
        {
            "create": {
                "account_id": account,
                "method_name": "return_large_value",
                "arguments": {"value_size": value_size},
                "amount": "0",
                "gas": callee_gas,
            },
            "id": 0,
        },
        {
            "create": {
                "account_id": account,
                "method_name": "return_large_value",
                "arguments": {"value_size": value_size},
                "amount": "0",
                "gas": callee_gas,
            },
            "id": 1,
        },
        {"and": [0, 1], "id": 2},
        {
            "then": {
                "promise_index": 2,
                "account_id": account,
                "method_name": "return_large_value",
                "arguments": {"value_size": 0},
                "amount": "0",
                "gas": callback_gas,
            },
            "id": 3,
            // Return the callback promise so the transaction's final status
            // reflects the callback receipt's outcome.
            "return": true,
        },
    ]);

    let call_tx = env.rpc_node().tx_call(
        &account,
        &account,
        "call_promise",
        serde_json::to_vec(&args).unwrap(),
        Balance::ZERO,
        Gas::from_teragas(300),
    );
    let outcome = env.rpc_runner().execute_tx(call_tx, Duration::seconds(10)).unwrap();

    assert_matches!(
        &outcome.status,
        FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
            kind: ActionErrorKind::TotalPromiseInputSizeExceeded { .. },
            ..
        })),
        "callback with oversized combined promise inputs should fail"
    );

async fn test_insufficient_gas() -> anyhow::Result<()> {

        &target.parse().unwrap(),

        action,
        &wallet_sk,
    );

    let error = wallet_contract
        .inner
        .call(crate::tests::RLP_EXECUTE)
        .args_json(serde_json::json!({
            "target": target,
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_gas::NearGas::from_tgas(7))
        .transact()
        .await
        .unwrap()
        .raw_bytes()
        .unwrap_err();

        error.to_string().contains("Exceeded the prepaid gas."),
        "Error should be that there was not enough gas"
    );

    // But the contract is still usable afterwards.
    utils::deploy_and_call_hello(&worker, &wallet_contract, &wallet_sk, 0).await?;

    Ok(())
}

async fn test_simultaneous_transactions() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

        utils::create_signed_transaction(0, receiver_account.id(), Wei::zero(), action, &wallet_sk);
    let wallet_method_call_1 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));
    let wallet_method_call_2 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));

    let near_transaction = wallet_contract
        .inner
        .as_account()
        .batch(wallet_contract.inner.id())
        .call(wallet_method_call_1)
        .call(wallet_method_call_2)
        .transact()
        .await?;

    let result: ExecuteResponse = near_transaction.json()?;

    assert!(!result.success);

    assert_eq!(final_receiver_balance.as_yoctonear() - initial_receiver_balance.as_yoctonear(), 1,);

    Ok(())
}
