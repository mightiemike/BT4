### Title
Confirmed-height ordering of `DataOnDa::BatchProofMethodId` allows a later-height inscription to permanently block an earlier, validly-signed council upgrade - (File: `crates/light-client-prover/src/circuit/mod.rs`)

### Summary
`run_l1_block` accepts any relayed `BatchProofMethodId` blob whose embedded 3-of-5 signatures verify, with no requirement on which Bitcoin transaction/sender delivered it, because authorization lives entirely in `body`+`signatures_with_index` rather than `blob.sender()`. The single monotonicity guard (`activation_l2_height <= last_activation_height → continue`) assumes bodies are confirmed on L1 in increasing `activation_l2_height` order, but nothing in the DA layer enforces that order, so an unprivileged party can get a higher-height, previously-signed body confirmed before a lower-height one and permanently suppress the lower-height, fully-authorized upgrade.

### Finding Description
Binding claimed: for every council-signed `BatchProofMethodIdBody{method_id, activation_l2_height, chain_id}` that passes `verify_method_id_security_council`, `BatchProofMethodIdAccessor::get()` after processing == the full set of such signed bodies (one insertion per valid signed body).

Code path:
- `run_l1_block` iterates `da_txs` in the order blobs are extracted from the L1 block(s) [1](#0-0) .
- For `DataOnDa::BatchProofMethodId`, there is no `blob.sender()` check at all (unlike `Complete`, `Aggregate`, `SequencerCommitment`), by design, since the security-council public keys are embedded in the signed body rather than being the DA tx sender [2](#0-1) .
- Insertion is gated only by comparing the new body's height to `last_activation_height`, the height of the *last inserted* entry: `if batch_proof_method_id.body.activation_l2_height <= last_activation_height { continue; }` [3](#0-2) .
- If the signatures verify, the body is inserted unconditionally via `BatchProofMethodIdAccessor::insert` [4](#0-3) .
- `BatchProofMethodIdAccessor::insert` itself performs no sorting/validation - it just appends `(height, method_id)` to a `Vec` and blindly relies on caller ordering [5](#0-4) .
- Later, `process_complete_proof` looks up the applicable method id for a given L2 height via `binary_search_by_key` over that same vector, which requires it to remain sorted by ascending activation height [6](#0-5) .

Because Bitcoin has no notion of "nonce order" for independent reveal transactions, an attacker who has observed the bytes of a validly-signed, higher-height body `H2` (e.g., seen in mempool, or previously broadcast for later application) can copy that exact `body`+`signatures_with_index` payload into their own OP_FALSE OP_IF reveal transaction, funded from any wallet, and pay a higher fee to get it mined in an earlier L1 block than the genuine, lower-height body `H1`. When `run_l1_block` processes the L1 blocks in chain order:
1. `H2`'s block is processed first: `H2 <= last_activation_height` is false (assuming `last_activation_height < H1 < H2`), signatures verify, `BatchProofMethodIdAccessor::insert(H2, ...)` runs, `last_activation_height` becomes `H2`.
2. `H1`'s block is later processed: `H1 <= last_activation_height (H2)` is true, so the genuine `H1` body is skipped via `continue`, and it can never be inserted afterward since heights only increase monotonically going forward.

No existing guard prevents this: `blob.sender()` is irrelevant here by design, `verify_method_id_security_council` only checks the signature validity of the body content (not confirmation order), and there is no cross-body ordering commitment (e.g., a "previous activation height" or sequence field) tying `H1`'s and `H2`'s validity to each other's confirmation order.

### Impact Explanation
The genuinely authorized `H1` upgrade is permanently dropped from the light client's `BatchProofMethodIdAccessor` state. Any batch prover that (correctly, per the public council schedule) starts using the new method id at L2 height `H1` will produce batch proofs that the light client prover verifies against the wrong (stale, pre-`H1`) method id for the `[H1, H2)` L2-height range (per the `binary_search_by_key` fallback logic), causing `Z::verify` to fail and those complete/aggregate proofs to be permanently rejected. This makes a true state transition unprovable to the light client for that range - matching the Critical category "a true one made unprovable" - and affects every honest light client prover and any batch prover relying on the intended upgrade schedule, since the LCP JMT state (and thus consensus over authorized method ids) is shared network-wide. The attack costs only Bitcoin inscription/mining fees and is repeatable whenever the council pre-signs/publishes future-height updates before earlier ones are confirmed.

### Likelihood Explanation
Preconditions: `Network::Nightly` (or any live network using this circuit), the attacker must be able to observe the exact bytes of a validly-signed higher-height body before the lower-height body is confirmed (plausible if council pre-signs/publishes upgrade proposals for transparency, or if a higher-height tx sits in mempool). The attack requires no privileged keys - only a wallet, BTC for fees, and public knowledge of a previously-signed message. It's fully attacker-controlled which block their copycat transaction lands in via fee bidding, since Bitcoin provides no other ordering guarantee for reveal transactions.

### Recommendation
Do not gate insertion solely on comparison to the last-inserted entry's height. Instead, either (a) require each `BatchProofMethodIdBody` to explicitly commit to the previous authorized entry (e.g., a monotonically increasing sequence number or the hash/height of the immediately preceding council-authorized body) as part of the signed message, so that a later body cannot be validly confirmed without also implying acceptance of all earlier ones, or (b) buffer/sort all `BatchProofMethodId` bodies observed for a given L1 block (or window) by `activation_l2_height` before applying the monotonicity check and insertion, and/or maintain method ids keyed by height in a way that permits later insertion of a smaller-but-still-valid height as long as it doesn't collide, rather than relying on `.last()`.

### Proof of Concept
In `crates/light-client-prover/src/tests/mod.rs`, add a test that:
1. Constructs two `BatchProofMethodIdBody` values `body_h1 { activation_l2_height: H1, method_id: M1, chain_id }` and `body_h2 { activation_l2_height: H2, method_id: M2, chain_id }` with `H1 < H2`, both signed by the same 3 of 5 authority keys (`verify_method_id_security_council` passes for both).
2. Calls `run_l1_block` (or the native input-building wrapper) for a first L1 block containing only the `H2` blob, then a second L1 block containing only the `H1` blob (simulating the attacker's earlier-mined copy of `H2` followed by the genuine, later-mined `H1`).
3. Asserts:
   - `BatchProofMethodIdAccessor::get(&mut working_set)` contains `(H2, M2)` after step 1.
   - After step 2, `BatchProofMethodIdAccessor::get(&mut working_set)` does **not** contain `(H1, M1)` — i.e., the binding "every validly council-signed body is inserted" is violated even though `verify_method_id_security_council(body_h1.serialize(), signatures_with_index_h1)` independently returns `true`.

    /// Inserts a new batch proof method id into the LCP state
    ///
    /// # Arguments
    /// * `activation_l2_height` - The L2 block height at which the method id is activated
    /// * `method_id` - The method id to store
    /// * `working_set` - Mutable reference to the working set for storage access
    pub fn insert(activation_l2_height: u64, method_id: [u32; 8], working_set: &mut WorkingSet<S>) {
        let key = Self::key();
        let mut method_ids = Self::get(working_set).unwrap_or_default();
        method_ids.push((activation_l2_height, method_id));
        let value: StorageValue = borsh::to_vec(&method_ids)
            .expect("Batch proof method ids serialization should not fail")
            .into();
        working_set.set(&key, value);
    }
