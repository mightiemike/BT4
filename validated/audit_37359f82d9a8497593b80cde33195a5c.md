### Title
Unbounded-depth recursion in `bytecode_hash_node` when hashing a declared Sierra→CASM class can crash the sequencer process (analog of CVE-2018-15871) - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
The CVE describes a decompiler (`decompileSingleArgBuiltInFunctionCall`) that dereferences invalid memory while walking an attacker-supplied, structurally malformed bytecode tree, crashing the process. The sequencer contains a structurally analogous pattern: `bytecode_hash_node` recursively walks an attacker-influenced `NestedIntList` (`bytecode_segment_lengths`) that describes how a declared class's CASM bytecode is segmented, with no bound on recursion depth. This walk runs **in the sequencer/gateway process itself** (not inside the resource-limited compiler subprocess), so a sufficiently deep/skewed segment tree can exhaust the native call stack and crash the node process handling the `DECLARE` transaction.

### Finding Description
When a `DECLARE` transaction is submitted, the gateway compiles the Sierra program to CASM inside a subprocess that is explicitly resource-limited (CPU time, memory) and whose crashes/signals are caught and converted into a `CompilationError` — see `crates/apollo_compilation_utils/src/compiler_utils.rs` (`compile_with_args`, `format_compiler_error`) and `crates/apollo_compile_to_casm/src/compiler.rs`. This isolation is a deliberate mitigation for compiler crashes.

However, once the subprocess returns its JSON output, the resulting `CasmContractClass` is deserialized and its compiled-class hash is computed **directly in the calling (unsandboxed) sequencer process**: [1](#0-0) 

The hash computation recurses over the `bytecode_segment_lengths` field (`NestedIntList`) that the compiler produced, mirroring the contract's function/branch structure: [2](#0-1) 

`bytecode_hash_node` recurses once per nesting level of the segment tree with **no depth limit or iterative fallback**. The Cairo/Starknet-OS documentation of this same algorithm confirms segmentation is per-function *and* per-branch, i.e., arbitrarily deep for a program with deeply nested branches: [3](#0-2) 

A declarer fully controls the Sierra source (subject only to `max_bytecode_size`, `max_contract_class_object_size`, and allowed-libfuncs checks performed in `StatelessTransactionValidator`): [4](#0-3) 

None of these checks bound the *depth* of nested branching/function structure that the compiler will encode into `bytecode_segment_lengths` — only the total serialized size and byte-code length are capped. A contract composed of a long, deeply nested chain of `if/else` branches (or many nested function calls) can therefore produce a segment tree whose depth is proportional to the number of nested branches rather than to `log(bytecode_size)`, while total bytecode size stays under the size cap. Note also that `crates/blockifier/src/execution/casm_hash_estimation.rs` explicitly assumes and asserts only shallow ("at most one level of") segmentation for its cost model, implying that deeper segment structures are an atypical/edge case not accounted for elsewhere in the code either: [5](#0-4) 

This is the direct analog of the libming bug class: a recursive parser/serializer that walks an untrusted, attacker-shaped tree structure without a depth guard, causing an out-of-bounds/invalid memory access (native stack overflow → SIGSEGV) instead of a graceful error.

### Impact Explanation
Unlike the Sierra→CASM compilation step, which is explicitly sandboxed in a subprocess with CPU/memory rlimits so that crashes are converted into `CompilationError`s (see `compiler_utils.rs`), the hash computation over the *returned* `CasmContractClass` executes back in the caller's process (the gateway, and later the batcher/blockifier and full nodes re-validating the block). A crash here (stack-overflow abort) takes down the node process handling the declare transaction directly, rather than being contained and reported as a compilation failure. Because every honest node runs the identical hashing code on the identical declared class (during gateway admission, block building, and OS re-execution/state commitment), a single malicious `DECLARE` transaction could reproducibly crash every node that processes it — a `Sierra to CASM compilation and class hashing` path explicitly in scope. If exploitable, this halts transaction processing on affected nodes, i.e. a network unable to confirm new transactions.

### Likelihood Explanation
The reachable trigger — an unprivileged account submitting a single `DECLARE` transaction with a specially crafted, deeply-branching Cairo/Sierra contract — requires no special privileges beyond declaring a class, which is exactly the surface CVE-2018-15871 targeted (any input causing a decompiler/parser to walk untrusted structure). The main uncertainty is quantitative: I could not verify from the indexed code (i) the exact maximum achievable nesting depth of `bytecode_segment_lengths` produced by the external `cairo-lang-starknet-classes` compiler for a program within `max_bytecode_size`/`max_contract_class_object_size` limits, nor (ii) the actual thread stack size configured for the gateway/batcher process, both of which determine whether the crash is practically achievable. These depend on the `cairo-lang-starknet-classes` crate's segmentation algorithm, which is outside this repo's indexed sources, so this should be treated as a plausible but unconfirmed structural weakness rather than a proven crash.

### Recommendation
- Convert `bytecode_hash_node` (and its Cairo-OS analogs `bytecode_hash_node` in `blake_compiled_class_hash.cairo` / `poseidon_compiled_class_hash.cairo`) to an explicit iterative (work-stack based) traversal instead of native recursion, removing any dependence on the native call stack for depth.
- Alternatively/additionally, enforce an explicit maximum nesting depth for `bytecode_segment_lengths` as part of stateless/stateful declare validation, rejecting classes whose segment tree exceeds a safe bound, consistent with the existing `max_bytecode_size`/`max_contract_class_object_size` checks in `stateless_transaction_validator.rs`.
- Run the compiled-class-hash computation for declare transactions inside the same resource-isolated context as the Sierra→CASM compilation (or with a bounded/guarded stack), so a crash there is caught and surfaced as a compilation/validation error rather than terminating the hosting process.

### Proof of Concept
Conceptual (not executed, since exploitability depends on the external Sierra compiler's segmentation behavior, which is outside the indexed sources):
1. Author a Cairo 1 contract whose body consists of a very long chain of deeply nested `if`/`else` branches (or deeply nested function calls), keeping total compiled bytecode under `max_bytecode_size`/`max_contract_class_object_size` (see `crates/apollo_gateway/src/stateless_transaction_validator.rs`).
2. Submit it as a `DECLARE` transaction to a node's gateway `add_tx`. The gateway's `SierraCompiler` compiles it in the sandboxed subprocess (which succeeds, since it is a valid, size-bounded program) and returns a `CasmContractClass` with a deeply nested `bytecode_segment_lengths`.
3. `SierraCompiler::compile` then calls `executable_class.hash(&HashVersion::V2)` in-process (`crates/apollo_compile_to_casm/src/lib.rs:69`), which recurses through `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs:111-132`) once per nesting level.
4. If the resulting recursion depth exceeds the process's native stack capacity, the gateway process crashes/aborts while handling this single transaction, and every other honest node performing the same hash computation (gateway admission, block building, OS re-execution) would crash identically on the same declared class.

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

    fn validate_sierra_version(
        &self,
        sierra_program: &[Felt],
    ) -> StatelessTransactionValidatorResult<()> {
        // Any patch version is valid. (i.e. when check version for upper bound, we ignore the Z
        // part in a version X.Y.Z).
        let mut max_sierra_version = self.config.max_sierra_version;
        max_sierra_version.0.patch = usize::MAX;

        let sierra_version = VersionId::from_sierra_program(sierra_program)?;
        if self.config.min_sierra_version <= sierra_version && sierra_version <= max_sierra_version
        {
            return Ok(());
        }

        Err(StatelessTransactionValidatorError::UnsupportedSierraVersion {
            version: sierra_version,
            min_version: self.config.min_sierra_version,
            max_version: self.config.max_sierra_version,
        })
    }

    fn validate_class_length(
        &self,
        contract_class: &starknet_api::state::SierraContractClass,
    ) -> StatelessTransactionValidatorResult<()> {
        if contract_class.sierra_program.len() > self.config.max_contract_bytecode_size {

                contract_bytecode_size: contract_class.sierra_program.len(),

        let contract_class_object_size = serde_json::to_string(&contract_class)
            .expect("Unexpected error serializing contract class.")

            return Err(StatelessTransactionValidatorError::ContractClassObjectSizeTooLarge {
                contract_class_object_size,
                max_contract_class_object_size: self.config.max_contract_class_object_size,
