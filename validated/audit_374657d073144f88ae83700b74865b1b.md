Based on my investigation, I've confirmed the strongest analog in java-tron. `ExchangeCreateActuator.doValidate()` mirrors the "insufficient validation of pool creation parameters" bug class: it lets any account create an AMM pool (`Exchange`/`ExchangeV2`) pairing two arbitrary tokens without enforcing any cross-token invariants — no check that the two `AssetIssueContract` tokens share compatible precision/decimals, and no check that the token pair doesn't already have an existing pool for the same pair. This is analogous to the Napier report's concern that a pool factory must validate relationships between the constituent tokens (maturity, decimals ≤ 18, underlying match) rather than trusting the caller.

### Title
Missing validation of decimal/precision compatibility and duplicate-pair checks in `ExchangeCreateActuator` allows creation of economically-broken AMM pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
`ExchangeCreateActuator` allows any account to create a TRX-based bonding-curve exchange pool (`ExchangeCapsule`) pairing any two TRC10 tokens (or TRX) it merely needs sufficient balance of, with no on-chain verification that the two tokens have compatible decimal precision, and no restriction preventing the same token pair from being created multiple times as separate, disconnected liquidity pools with independent, arbitrary initial ratios.

### Finding Description
`doValidate()` in `ExchangeCreateActuator` only checks: address validity, fee/balance sufficiency, that token ids are well-formed numbers (when `allowSameTokenName==1`), that the two token ids differ, that balances are positive and under `getExchangeBalanceLimit()`, and that the creator holds enough of each token. [1](#0-0) 
There is no check on the `precision` field of either token's `AssetIssueContract` (which can independently range 0–6, per `AssetIssueActuator`'s own validation), and no check that the token pair isn't already backing another pool. [2](#0-1) 
The bonding-curve math in `ExchangeCapsule.transaction()` / `ExchangeProcessor` / `SafeExchangeProcessor` treats the two token balances as directly comparable raw integer quantities with no decimal normalization. [3](#0-2) 
Because the creator freely picks the initial `firstTokenBalance`/`secondTokenBalance` ratio and TRON allows unlimited duplicate pools for the same pair (no uniqueness enforced anywhere in `ExchangeCreateActuator` or `ExchangeStore`/`ExchangeV2Store`), a malicious creator can seed a pool with a ratio wildly divorced from the token's true precision/value (e.g., pairing a 6-decimal token against a 0-decimal token at a 1:1 raw-unit ratio), then use `ExchangeTransactionActuator`/`MarketSellAssetActuator`-adjacent flows to trade against the mispriced pool. This is directly analogous to the reported Napier issue where a pool factory that fails to enforce "tokens must share decimals/maturity/underlying" invariants leads to unexpected behavior once liquidity or trades interact with the pool.

### Impact Explanation
An attacker-created pool with a mismatched decimal ratio does not by itself steal funds — attackers only trade against liquidity they or others voluntarily deposited — but it can be leveraged to mislead other users interacting with `wallet/getexchangesbypair`, `wallet/getpaginatedexchangelist`, or wallet UIs that don't independently verify token precision, causing them to inject or trade at an economically incorrect rate and lose value. Because the actuator runs as a normal user-broadcastable `ExchangeCreateContract`, this is reachable by any account with minimal TRX. Actual value loss depends on other users trusting/using the mispriced pool, so severity is bounded compared to a direct fund-drain bug.

### Likelihood Explanation
The path is trivially reachable: any account can broadcast an `ExchangeCreateContract` transaction (or call `createExchangeAndReturnId`/similar wallet RPC) supplying arbitrary token pairs and balances, subject only to already-owned balances and the `getExchangeBalanceLimit()` cap. No special permissions, on-chain governance, or malicious peer/node behavior is required — a single unprivileged, self-funded actor is sufficient to create a mispriced pool.

### Recommendation
Add on-chain validation in `ExchangeCreateActuator.doValidate()` to: (1) reject pool creation when the two tokens' `precision` values differ beyond an accepted tolerance (or require callers to normalize the reported balances against `AssetIssueCapsule.getPrecision()`), and (2) enforce uniqueness of the (firstTokenId, secondTokenId) pair (independent of ordering) so duplicate/competing pools for the same asset pair cannot be created, matching the underlying invariant the Napier report calls out for Napier's `PoolFactory`.

### Proof of Concept
1. Attacker issues (or already owns) Token A with `precision=6` and Token B with `precision=0` via `AssetIssueActuator` (validated only for `0 <= precision <= 6`, no cross-token relationship enforced: `actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java:176-181`).
2. Attacker broadcasts `ExchangeCreateContract` with `firstTokenId=A`, `secondTokenId=B`, `firstTokenBalance=1_000_000` (i.e. 1 unit of A accounting for its precision) and `secondTokenBalance=1_000_000` (i.e. 1,000,000 raw units of B, since B has 0 decimals) — `doValidate()` only checks balances/limits, not the precision mismatch: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java:183-228`.
3. `execute()` persists an `ExchangeCapsule` with this skewed 1:1,000,000 raw ratio with no re-validation against token decimals: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java:104-116`.
4. Any subsequent `ExchangeTransactionActuator` trade against this pool uses `ExchangeCapsule.transaction()`, which operates purely on the raw stored balances, producing an exchange rate 10^6 times off from the tokens' true relative value, misleading counterparties who don't independently check underlying decimals.
