### Title
Rounding-down precision loss in `MortgageService.computeReward` (old reward algorithm) causes users to receive less voting reward than owed - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
The legacy (pre-VI) SR-vote reward computation in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` performs division before multiplication when calculating a user's share of a cycle's witness reward: `voteRate = (double) userVote / totalVote` followed by `reward += voteRate * totalReward`. Because `voteRate` is first rounded to double precision and the accumulator `reward` is a `long`, the multiply-after-divide ordering (plus the implicit `double`→`long` narrowing) systematically loses precision, mirroring the exact bug class described in the external Alchemix report where `claimableFlux` rounds down because multiplication is applied to an already-divided intermediate value. [2](#0-1) 

### Finding Description
`MortgageService` maintains two reward algorithms: a VI-based (BigInteger, multiply-then-divide) algorithm used for cycles at/after `newAlgorithmCycle`, and a legacy algorithm used for cycles before that boundary, invoked via `getOldReward`: [4](#0-3) 

When `dynamicPropertiesStore.allowOldRewardOpt()` is not enabled, `getOldReward` iterates every cycle in the range and calls the legacy per-cycle `computeReward(cycle, votes)`:
```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;
    reward += voteRate * totalReward;
  }
  return reward;
}
``` [2](#0-1) 

This is the same "multiplication on the result of division" anti-pattern flagged in the external report: `voteRate` (userVote/totalVote) is computed and rounded to a finite-precision `double` first, and only then multiplied by `totalReward`. For large `totalReward`/`totalVote` values, the double representation cannot retain full precision, and the summed `voteRate * totalReward` value is implicitly narrowed to `long`, truncating any fractional remainder. Doing the mathematically equivalent `userVote * totalReward / totalVote` (multiply first, divide once) would retain full integer precision and never lose more than 1 unit to floor rounding, whereas the double-based division-first approach can lose materially more due to floating-point representation error, especially when accumulated across many cycles.

This computation is reachable from a fully anonymous, unprivileged path: any account holder can broadcast a `WithdrawBalanceContract` transaction, processed by `WithdrawBalanceActuator.execute()`, which unconditionally calls `mortgageService.withdrawReward(...)`: [1](#0-0) 
`withdrawReward` and `queryReward` both call the private `computeReward(beginCycle, endCycle, accountCapsule)` overload, which delegates to `getOldReward` for any cycle span before `newAlgorithmCycle`: [5](#0-4) [6](#0-5) 

### Impact Explanation
The bug causes permanent under-crediting of voting rewards (`allowance`) to SR voters for any cycles processed by the legacy algorithm. Because `adjustAllowance` is only ever called with the truncated `reward` value, the shortfall is never recovered — it is effectively burned/frozen rather than distributed, matching the "Permanent freezing of unclaimed yield" impact category from the source report. The magnitude scales with `totalReward` and the number of cycles/voters affected, and is compounded across every user who ever calls `withdrawReward`/`queryReward` while old-algorithm cycles remain unprocessed (e.g., on networks/deployments where `allowOldRewardOpt`/the VI algorithm hasn't taken effect for the full history, or accounts with an old, un-migrated `beginCycle`).

### Likelihood Explanation
The vulnerable code path is exercised automatically and unconditionally by any account withdrawing/querying rewards whose vote history spans cycles prior to `newAlgorithmCycle` while `allowOldRewardOpt` is disabled — no special privilege, timing, or attacker action is required; it is a deterministic computation error triggered by ordinary, anonymous `WithdrawBalanceContract` transactions.

### Recommendation
Refactor `computeReward(long cycle, List<Pair<byte[], Long>> votes)` to perform the multiplication before the division, ideally using integer/`BigInteger` arithmetic (consistent with the VI-based algorithm's approach) instead of `double`:
```java
long reward = 0;
for (Pair<byte[], Long> vote : votes) {
  ...
  long userVote = vote.getValue();
  reward += Math.multiplyHigh(userVote, totalReward) ...; // or BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward)).divide(BigInteger.valueOf(totalVote)).longValueExact();
}
```
This mirrors the fix pattern in the external report (group multiplication before division) and eliminates both the floating-point precision loss and the truncating `double`→`long` narrowing.

### Proof of Concept
Given `totalVote = 3`, `userVote = 1`, `totalReward = 10` (a case that does not divide evenly):
- Current code: `voteRate = 1.0/3 = 0.3333333333333333` (finite double approximation), `reward += 0.3333333333333333 * 10 = 3.333333333333333` → truncated to `3` when accumulated/returned as `long`.
- Correct multiply-first approach: `userVote * totalReward / totalVote = 10 / 3 = 3` (same result in this simple case, but for adversarially chosen large `totalReward`/`totalVote` combinations near `Long.MAX_VALUE`/`double` precision limits — e.g. `totalReward` in the range of tens of trillions of sun with `totalVote` values that are not exact powers matching double's 52-bit mantissa — the double-based `voteRate * totalReward` diverges from the exact integer result by more than the guaranteed single-unit floor-rounding error of the multiply-then-divide approach, systematically under-crediting the voter's `reward`).   private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }
