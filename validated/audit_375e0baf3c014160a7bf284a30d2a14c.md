### Title
Receipts can be created above `max_receipt_size` after validation, forcing a lossy size-clamp workaround in cross-shard forwarding - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
A contract deployer/caller can produce an outgoing cross-shard receipt that ends up larger than `max_receipt_size` even though receipt-size validation is supposed to reject anything above that limit. This is a known, currently open bug (tracked as near/nearcore#12606) reachable purely by calling a deployed contract — no validator or node privilege required. The runtime does not re-reject or fail the oversized receipt after the size grows past validation; instead, `ReceiptSink::try_forward` silently *pretends* the receipt is `max_receipt_size` for admission/accounting purposes so it "doesn't get stuck" [1](#0-0) , and `generate_bandwidth_request` applies the same pretend-clamp when computing bandwidth requests [2](#0-1) .

### Finding Description
Two documented paths let a contract caller create a receipt whose true borsh-encoded size exceeds `max_receipt_size` after the size check has already passed:
1. A promise-chain callback (`promise_return`) has its `output_data_receivers` appended to a receipt that was already validated as being at the size limit, pushing it over the limit (`test_max_receipt_size_promise_return`, comment: "the receipt should be rejected, but currently isn't because of a bug (See https://github.com/near/nearcore/issues/12606)") [3](#0-2) .
2. Returning a value that is itself close to `max_receipt_size` gets wrapped into a `DataReceipt`, whose total size then exceeds the limit, again without being rejected (`test_max_receipt_size_value_return`) [4](#0-3) .

Once such an oversized receipt exists, the runtime's forwarding/buffering logic (`ReceiptSink::try_forward`, called from `forward_or_buffer_receipt`) explicitly documents the workaround: "There is a bug which allows to create receipts that are above the size limit… Let's pretend that all receipts are at most `max_receipt_size` to avoid receipts getting stuck. See https://github.com/near/nearcore/issues/12606" [1](#0-0) . The clamp is then used to decide whether the receiver's `OutgoingLimit.size` admits it and to decrement that limit by the (fictitious, clamped) size rather than the real size [5](#0-4) . The identical clamp is duplicated in bandwidth-request generation so a receiver never issues a bandwidth grant sized to what the receipt actually needs [2](#0-1) .

This means the byte-accounting invariants that both congestion control (NEP-539) and the bandwidth scheduler rely on — that a granted `size` budget is always large enough to carry the receipt it was granted for — are violated for any receipt above `max_receipt_size`. The bandwidth scheduler's own module doc states this guarantee is supposed to hold for liveness: "There is a guarantee that for every bandwidth grant, the shard will be able to send at least one receipt" [6](#0-5) . An oversized receipt is admitted with the wrong (smaller) size accounted against the sender's/receiver's limits, meaning the shard consumes less of its declared `outgoing_limit.size`/bandwidth grant than the receipt actually occupies on the wire and in the receiving shard's incoming buffer/state.

### Impact Explanation
Because the clamp treats the oversized receipt as `max_receipt_size` for the purposes of `OutgoingLimit` and `CongestionInfo`/bandwidth-request accounting, but the actual receipt bytes committed to the trie and transmitted between shards are larger, the byte-budget bookkeeping that both congestion control and the bandwidth scheduler use to bound shard-to-shard traffic becomes inaccurate. This is exactly analogous to the referenced Arbitrum incident: a bug in the "batch submission" (here, cross-shard receipt forwarding/bandwidth-granting) path can cause receipts to be forwarded/accounted incorrectly, undermining the throttling that is supposed to prevent shards from being overloaded, and — since the underlying validation gap is not fixed, only downstream-patched in two specific call sites — any other code path that trusts a receipt to be at most `max_receipt_size` (e.g. size-based buffer/queue accounting, storage-proof size estimates) is exposed to the same discrepancy. This falls under "receipt loss or duplication"/"invalid state transition acceptance"-class impact: byte accounting used for consensus-relevant `CongestionInfo` and bandwidth grants no longer reflects real receipt sizes.

### Likelihood Explanation
Any account holder can deploy the test-style contract logic (the same primitives — `promise_then`/`promise_return` and large return values — are ordinary, unprivileged WASM host-function usage) to reproduce the oversized receipt, as shown directly by the existing regression tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return`, which are written specifically to demonstrate the bug is still live in this codebase [7](#0-6) [8](#0-7) . No validator collusion, network-layer manipulation, or privileged access is required — a single contract call chain suffices.

### Recommendation
Fix the root cause rather than only papering over it in `try_forward`/`generate_bandwidth_request`: enforce the `max_receipt_size` check *after* all receipt-mutating steps (adding `output_data_receivers`, wrapping return values into `DataReceipt`) complete, so an oversized receipt is rejected with `ReceiptValidationError::ReceiptSizeExceeded` before it is ever queued for cross-shard forwarding, consistent with how `test_max_receipt_size` already rejects a directly-oversized receipt [9](#0-8) . Remove the two duplicated size-clamp workarounds once the validation gap is closed so that byte accounting in `CongestionInfo` and the bandwidth scheduler always matches real receipt sizes.

### Proof of Concept
Use the existing repro tests as the PoC:
- `test_max_receipt_size_promise_return`: deploy the test contract, then call `max_receipt_size_promise_return_method1` with `args_size` computed so the base receipt is exactly at `max_receipt_size`; the subsequent `output_data_receivers` append pushes it over the limit without rejection [10](#0-9) .
- `test_max_receipt_size_value_return`: call `max_receipt_size_value_return_method` with `value_size` equal to `max_receipt_size`, producing an oversized `DataReceipt` that is likewise accepted rather than rejected [11](#0-10) .
Both tests assert `assert_oversized_receipt_occurred`, confirming a receipt above `max_receipt_size` was actually included in a chunk/proof despite validation [12](#0-11) .

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
