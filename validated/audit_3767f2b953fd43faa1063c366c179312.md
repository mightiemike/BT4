### Title
Unbounded internal-transaction accumulation in `Wallet.callConstantContract()` allows disproportionate response-size DoS via free constant calls - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.callConstantContract()` unconditionally copies every `InternalTransaction` produced during a constant-call VM execution into the `TransactionExtention` response via `builder.addInternalTransactions(...)`, with no cap tied to response size, count, or actual energy charged. Because `triggerconstantcontract` is a free, unauthenticated read-only RPC call (no broadcast, no fee deduction), an attacker can craft a view function with many cheap `CALL`-family opcodes to precompiles/self to make the node serialize an arbitrarily large internal-transaction list while paying nothing beyond a bounded VM energy budget.

### Finding Description
The call chain is: `TriggerConstantContractServlet.doPost()` → `Wallet.triggerConstantContract()` → `Wallet.callConstantContract()` [1](#0-0)  → `VMActuator.validate()/execute()` which runs the TVM and populates `ProgramResult` via `Program.addInternalTx()` for every internal `CALL`/`CREATE` [2](#0-1) , stored unboundedly in `ProgramResult.internalTransactions` [3](#0-2) .

Critically, `callConstantContract()` copies **all** of `result.getInternalTransactions()` into the gRPC/HTTP response builder unconditionally: [4](#0-3) 
This is different from the block-execution path `TransactionUtil.buildTransactionInfoInstance()`, which gates the same copy behind `CommonParameter.getInstance().isSaveInternalTx()` (default `false`) [5](#0-4) . For constant calls, no such gate exists — the internal transactions are always serialized into the response regardless of the `vm.saveInternalTx` config.

The only resource bound on the VM execution is `maxEnergyLimitForConstant` (default 100,000,000, floor-clamped to 3,000,000) [6](#0-5) [7](#0-6) , further reducible if the transaction sets a `feeLimit` [8](#0-7) , but this bound governs execution steps, not response payload size or object-count. Since each low-level `CALL` (e.g., to a cheap precompile or self) costs a small, roughly fixed amount of energy relative to the 3M–100M energy budget, an attacker can fit a very large number of `CALL` opcodes in a single constant call, each producing one `InternalTransaction` entry that gets serialized (hash, sender, recipient, call-value info, note, etc.) into the HTTP/gRPC response, independent of the fact that constant calls incur **no actual fee** (no broadcast, no TRX deducted) — the attacker pays nothing for the resulting memory/serialization cost imposed on the node.

None of the standard checks (`TransactionCapsule.validateSignature`, permission checks, `ForkController` gates, bandwidth/energy accounting for real transactions) apply here because `triggerconstantcontract` is explicitly a local, non-broadcast, feeless read call — this is expected TRON behavior, but it means the response-size cost is entirely decoupled from any economic disincentive.

### Impact Explanation
This falls under "DoS via RPC-API": a full node with `vm.supportConstant=true` (required for `triggerconstantcontract`/`eth_call` to function at all — a standard, commonly-enabled configuration for RPC-serving nodes) can be made to allocate and serialize a response containing a very large number of `InternalTransaction` protobuf messages per single, free HTTP POST. Repeated concurrent requests amplify memory pressure and CPU spent on protobuf serialization and JSON conversion (`Util.printTransactionExtention`), potentially degrading or crashing the RPC/HTTP service for that node. This does not corrupt chain state or consensus, and is scoped to node/API availability degradation, not fund loss or key leakage.

### Likelihood Explanation
- Preconditions: `vm.supportConstant=true` (needed for the endpoint to work at all — not an unusual hardening deviation, it's required for basic dApp read functionality).
- Attacker needs no funded account, no signature, no special permission — `triggerconstantcontract` accepts unauthenticated/unsigned requests since it never broadcasts a transaction.
- Cost to attacker: effectively zero (no fee deducted for constant calls); only the cost of writing/deploying the target contract once (which does cost energy/bandwidth for the one-time `CreateSmartContract`, or the attacker could target any existing contract's fallback/view function that internally loops with calls, if one exists).
- Fully repeatable: attacker can call the same crafted contract's function unlimited times, and `RateLimiterServlet` throttling on this endpoint (if configured) limits request rate, but does not limit the per-request payload size explosion.
- The `TriggerConstantContractServletTest.testManyFlatFieldsDoesNotOverflowStack` test shows awareness of large-request-body DoS on this servlet's input side [9](#0-8) , but there is no equivalent protection on the *output* side (internal-transaction list growth) that I could find.

### Recommendation
In `Wallet.callConstantContract()`, cap the number/size of internal transactions copied into the response — e.g., respect `vm.saveInternalTx`/`vm.saveFeaturedInternalTx` config flags as done in `TransactionUtil.buildTransactionInfoInstance()`, and/or enforce a hard maximum count (or serialized byte-size limit) on `result.getInternalTransactions()` before calling `builder.addInternalTransactions(...)`, truncating or rejecting the response (with a clear error) when exceeded, at `framework/src/main/java/org/tron/core/Wallet.java:3184-3185`.

### Proof of Concept
Conceptual PoC (cannot be fully executed without a running node, but the code path is deterministic):

1. Deploy a contract with a `view` function such as:
```solidity
function spam() external view returns (bool) {
    for (uint i = 0; i < N; i++) {
        address(0x1).staticcall(""); // cheap precompile call, generates 1 internal tx each
    }
    return true;
}
```
2. Choose `N` such that total energy stays within `maxEnergyLimitForConstant` (e.g., 3,000,000 default floor / small per-call cost ⇒ tens of thousands of internal transactions fit).
3. POST to `/wallet/triggerconstantcontract`:
```json
{
  "owner_address": "<any address, unsigned>",
  "contract_address": "<deployed address>",
  "function_selector": "spam()",
  "visible": true
}
```
4. Expected observation: `TransactionExtention.internal_transactions` list length in the response scales linearly with `N`, `energyUsed` stays within the constant-call budget (no fee charged since not broadcast), and response payload size grows proportionally to `N × (~100+ bytes per InternalTransaction)`.

JUnit-level assertion sketch (using existing test infra in `framework/src/test/java/org/tron/common/runtime/VMActuatorMockTest.java` style):
```java
// Deploy contract with N internal CALL opcodes, execute via VMActuator(true)
VMActuator vmActuator = new VMActuator(true);
vmActuator.validate(context);
vmActuator.execute(context);
ProgramResult result = context.getProgramResult();
assertTrue(result.getInternalTransactions().size() == N);
assertTrue(result.getEnergyUsed() <= CommonParameter.getInstance().getMaxEnergyLimitForConstant());
// Then verify Wallet.callConstantContract copies all N entries into builder unconditionally
```
Verifying the exact per-`CALL` energy cost to compute a precise maximum `N` requires inspecting `actuator/src/main/java/org/tron/core/vm/EnergyCost.java` in full, which was not fully retrievable through the available index — this detail should be confirmed by a full read of that file before finalizing exact PoC numbers.

    if (triggerSmartContract.getContractAddress().isEmpty()) { // deploy contract

      long feeLimit = trxCap.getFeeLimit();

      byte[] contractAddress = triggerSmartContract.getContractAddress().toByteArray();
      if (contractStore.get(contractAddress) == null) {
        throw new ContractValidateException("Smart contract is not exist.");
      }
    }
    return callConstantContract(trxCap, builder, retBuilder, isEstimating);
