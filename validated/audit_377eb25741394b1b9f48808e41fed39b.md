### Title
CPU DoS via forced full-store sort in `AssetIssueStore.getAssetIssuesPaginated` regardless of requested `limit` - ([File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java])

### Summary
`GetPaginatedAssetIssueListServlet` (`/wallet/getpaginatedassetissuelist`) passes attacker-controlled `offset`/`limit` straight into `Wallet.getAssetIssueList(offset, limit)`, which calls `AssetIssueStore.getAssetIssuesPaginated`. That method always loads the entire asset store via `getAllAssetIssues()` and sorts the full list with `List.sort()` before applying the `ASSET_ISSUE_COUNT_LIMIT_MAX` clamp, so the requested `limit` cannot reduce the cost of the call.

### Finding Description
The private helper in `AssetIssueStore` performs, on every call:
1. `getAllAssetIssues()` — a full DB iteration collecting every `AssetIssueCapsule` into a `List` [1](#0-0) .
2. An unconditional `assetIssueList.sort(...)` over that entire list, comparing asset names as UTF-8 strings [2](#0-1) .
3. Only after the sort is `limit` clamped to `ASSET_ISSUE_COUNT_LIMIT_MAX` and the sublist extracted [3](#0-2) .

This is reachable unauthenticated via `GetPaginatedAssetIssueListServlet.doGet`/`doPost`, which parses `offset`/`limit` from the request and forwards them unchanged into `wallet.getAssetIssueList(offset, limit)` [4](#0-3) . There is no size/limit validation prior to the sort — even `limit=1` still forces the full-store sort. The only mitigation present is `RateLimiterServlet`, which throttles request *rate* (QPS/global) but does nothing to bound the *cost* of an individual permitted request [5](#0-4) . Thus a small number of permitted requests per second, each triggering an O(n log n) sort over the full asset-issue set, can consume significant CPU as the store grows.

### Impact Explanation
This matches a DoS via RPC-API impact class: an unauthenticated client can force repeated, unavoidable O(n log n) sorts of the entire on-chain asset-issue dataset on a hot HTTP endpoint, degrading node responsiveness/CPU availability for legitimate API consumers. It does not achieve RCE, key leakage, or state corruption — the impact is scoped to computational resource exhaustion on full/solidity node HTTP API processes.

### Likelihood Explanation
The endpoint requires no authentication, no fee/energy payment (it's a query HTTP endpoint, not a transaction), and no special account privileges — any anonymous client can send `offset=0&limit=1` (or any value) repeatedly. The only friction is the QPS-based `RateLimiterServlet`, which limits requests per second/IP but not cost per request, so the attack is fully repeatable within whatever QPS the limiter allows, and cost scales with the size of the asset-issue store rather than the requested page size.

### Recommendation
Cap the record set that must be sorted independent of requested `limit`/`offset` sanity, e.g., reject or clamp `offset`/`limit` before hitting the store (as `GetPaginatedAssetIssueListServlet` already does not), and/or maintain a persistently sorted index (e.g., store assets pre-sorted by name/order, or use a `TreeMap`/sorted secondary index) so pagination doesn't require re-sorting the entire dataset on each call. At minimum, validate `limit`/`offset` bounds and consider caching the sorted list with invalidation on asset-issue creation instead of re-sorting per request.

### Proof of Concept
```java
// JUnit-style benchmark inside chainbase test module
@Test
public void testPaginationCostIndependentOfLimit() {
  AssetIssueStore store = ...; // populated with N (e.g. 100_000) AssetIssueCapsule entries

  long start1 = System.nanoTime();
  List<AssetIssueCapsule> tiny = store.getAssetIssuesPaginated(0, 1);
  long tinyCost = System.nanoTime() - start1;

  long start2 = System.nanoTime();
  List<AssetIssueCapsule> full = store.getAssetIssuesPaginated(0, Long.MAX_VALUE);
  long fullCost = System.nanoTime() - start2;

  // Assert cost of tiny limit request is not meaningfully smaller than full request,
  // proving the sort (O(n log n) over all N assets) dominates regardless of limit.
  assertTrue(tinyCost > fullCost * 0.8);
}
```
Request-level reproduction: repeatedly `GET /wallet/getpaginatedassetissuelist?offset=0&limit=1` (or `limit=9223372036854775807`) against a node with a large asset-issue set and observe CPU usage scaling with total asset count rather than the requested `limit`.
