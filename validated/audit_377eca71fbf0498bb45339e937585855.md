### Title
Unbounded, permissionlessly-growable iteration over `VotesStore`/`WitnessStore` inside mandatory consensus maintenance path with no CPU/size budget - ([File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java])

### Summary
The Sherlock report describes a Chainlink VRF callback (`fulfillRandomWords`) whose cost scales with a parameter (`AGENTS_TO_WOUND_PER_ROUND_IN_BASIS_POINTS`) that can grow unboundedly, so the mandatory, must-not-revert callback exceeds the coordinator's fixed 2,500,000 gas limit and permanently reverts, DoSing the protocol. The structural bug class is: **mandatory, deterministic, must-succeed logic whose cost scales with a permissionlessly-growable, unbounded input, executed with no per-call resource budget.**

In java-tron, ordinary smart-contract execution (TVM) is explicitly protected against this class of bug: every transaction has both an energy limit and a CPU time budget enforced with `Program.checkCPUTimeLimit`, `OutOfTimeException`, `OutOfEnergyException`, and `maxCpuTimeOfOneTx` [1](#0-0) [2](#0-1) . However, the consensus-critical maintenance path that runs automatically on every witness node every `maintenanceTimeInterval` (default 6 hours) has **no such budget at all**.

### Finding Description
`MaintenanceManager.applyBlock()` unconditionally calls `doMaintenance()` whenever a block's timestamp crosses the maintenance boundary [3](#0-2) . `doMaintenance()` in turn calls `countVote(votesStore)`, which iterates the **entire** `VotesStore` — one entry per account that has voted since the previous cycle — and for each entry iterates that account's full vote list:

Any unprivileged account can permissionlessly add itself to `VotesStore` by calling `VoteWitnessActuator`/`VoteWitnessProcessor` (`vote`), each vote transaction touching up to `MAX_VOTE_NUMBER` (30) witnesses per account [5](#0-4) . There is **no bound on the total number of distinct voting accounts**, and thus no bound on the size of `VotesStore` or on the work `countVote()` must perform.

Unlike a normal transaction, this maintenance logic:
- Is executed **unconditionally inside block application** by every full node/witness, not inside the TVM, so it is **not subject to `checkCPUTimeLimit`, energy metering, or `OutOfTimeException`** the way ordinary contract calls are [6](#0-5) .
- Must complete deterministically and identically on every node for consensus to proceed — there is no "revert" escape valve; if it becomes disproportionately slow, it directly threatens block production/propagation timing (`blockProducedTimeOut`, default 50% of the block interval) [7](#0-6) .
- Also drives `IncentiveManager.reward()` and `MortgageService.payStandbyWitness()` / `withdrawReward()`, whose per-account reward computation (`computeReward`) also loops the full votes list of accounts with no size cap [8](#0-7) [9](#0-8) .

This mirrors the VRF pattern precisely: a fixed external constraint (VRF's 2.5M gas ceiling / java-tron's block interval and `blockProducedTimeOut`) versus an internal computation whose cost is controlled by a parameter (permissionless account count / vote count) that has no protocol-level cap, executed as mandatory, must-succeed logic.

### Impact Explanation
If `VotesStore` grows large enough (e.g., via a sustained low-cost campaign of many accounts each casting a vote), `doMaintenance()`'s per-cycle cost grows roughly linearly with the number of distinct voters, with no circuit breaker. Because this runs inside `applyBlock()` on the critical path for every witness and full node at every maintenance boundary, sufficiently large growth could cause witnesses to consistently miss their `blockProducedTimeOut` window during maintenance blocks, causing systemic missed slots/slowed block production across the network at that boundary — a network-wide liveness degradation rather than an isolated transaction failure. This is analogous to the Medium-severity DoS/liveness impact accepted in the referenced report (no unauthorized fund movement, but a break of a core, deterministic protocol guarantee — “the maintenance cycle must complete promptly”).

### Likelihood Explanation
Reachability is high: voting is a fully permissionless, low-cost, unprivileged-user action (`VoteWitnessContract`), and the number of unique voting accounts is bounded only by economic cost to the attacker (creating accounts and casting minimal votes), not by protocol logic. The severity of impact depends on how large `VotesStore` must grow before `doMaintenance()` materially threatens block timing on production hardware, which is not proven here (no PoC/benchmark was run against this java-tron path) — so likelihood should be treated as plausible-but-unconfirmed rather than demonstrated.

### Recommendation
- Add an explicit time/iteration budget check inside `doMaintenance()`/`countVote()` analogous to `checkCPUTimeLimit`, with graceful, deterministic degradation instead of unmetered execution.
- Consider paginating/batching maintenance-cycle vote counting and reward computation across multiple blocks rather than requiring completion within a single maintenance block, or cap the number of `VotesStore` entries processed per cycle.
- Benchmark `doMaintenance()` cost against a `VotesStore` sized to a realistic worst-case adversarial voter count to confirm whether current cost stays safely below `blockProducedTimeOut` margins, and add monitoring/alerting for maintenance-cycle duration.

### Proof of Concept
No concrete PoC was executed against java-tron in this analysis (this environment has no execution access). The theoretical PoC path is:
1. Programmatically create N accounts (N large, e.g. hundreds of thousands), fund each minimally, and have each cast a `VoteWitnessContract` vote for one witness, populating `VotesStore` with N entries.
2. Advance the chain to the next `maintenanceTimeInterval` boundary and measure the wall-clock duration of `MaintenanceManager.doMaintenance()` (specifically `countVote()`) inside `applyBlock()`.
3. Compare against `blockProducedTimeOut` (default 50% of block interval) to determine at what N the maintenance cycle begins to threaten timely block production, mirroring how the Sherlock PoC measured `fulfillRandomWords()` gas usage against the VRF coordinator's fixed 2,500,000 gas ceiling.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }
