### Title
Unbounded growth of an account's `AssetV2` map lets any unprivileged user degrade bandwidth accounting and self-destruct token transfer for a victim account - ([File: chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java])

### Summary
`AccountCapsule` stores every TRC10 token an account has ever held in an unbounded `asset`/`assetV2` map (`putAssetV2`, see `AccountCapsule.addAssetAmountV2` at `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java:733-765`). Any unprivileged user can grow this map for a victim address simply by sending a minimal amount of many distinct existing TRC10 tokens to it via ordinary `TransferAssetContract` transactions — no admin/privileged role is required, mirroring the `addPool`-style "attacker-controlled unbounded array" bug class from the report. This map is then iterated on hot, frequently-triggered code paths: `BandwidthProcessor.updateUsage` (invoked for essentially every transaction touching the account, e.g. `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java:47-78`) and `MUtil.transferAllToken` (invoked on smart-contract `SELFDESTRUCT`, `actuator/src/main/java/org/tron/core/vm/utils/MUtil.java:28-41`).

### Finding Description
`AccountCapsule.addAssetAmountV2` unconditionally adds a new entry to the account's asset map whenever a new token type is received, with no cap on the number of distinct tokens an account may hold: [1](#0-0) 

Because thousands of TRC10 tokens already exist on-chain (issuable by anyone who pays the `AssetIssueFee`, see `AssetIssueActuator.calcFee`), an attacker does not even need to issue new tokens — they only need to acquire a minimal balance of many already-issued tokens and transfer 1 unit of each to the victim address via the standard, permissionless `TransferAssetContract`/`TransferAssetActuator` path. Each transfer adds one more entry to the victim's `assetV2` map, which has no maximum-size check anywhere in `AssetIssueActuator`, `TransferAssetActuator`, or `AccountCapsule`.

This growing map is then iterated in at least two places that are reachable in normal, non-privileged operation:

1. `BandwidthProcessor.updateUsage(AccountCapsule)` iterates the account's entire `assetMapV2` (plus the legacy `assetMap` when same-token-name mode is active) every time bandwidth usage needs to be recalculated for that account: [2](#0-1) 
This method is called from numerous places across `Wallet.java`, delegate/undelegate actuators, and `Program.java`, i.e., essentially any operation that queries or updates the account's resource state.

2. `MUtil.transferAllToken`, invoked when a smart contract self-destructs (`SELFDESTRUCT`) and needs to move all its token balances to an inheritor address, iterates the *entire* `assetMapV2` of the destructing contract account: [3](#0-2) 

Both operations scale linearly (or worse, given map rebuilds via protobuf builders) with the number of distinct tokens the account holds, and there is no limit analogous to `UNFREEZE_MAX_TIMES` (used to bound the `UnFreezeV2` list in `UnfreezeBalanceV2Actuator`, `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java:44,179-182`) protecting the asset map.

### Impact Explanation
Growing this map imposes escalating CPU/memory cost on every subsequent call to `BandwidthProcessor.updateUsage` for the targeted account, and on `SELFDESTRUCT` execution if the account is a contract. Since `updateUsage` is invoked on nearly every transaction the account participates in (transfers, freezes, delegations, resource queries), a sufficiently large asset map degrades block-processing performance for transactions touching that specific account and can make `SELFDESTRUCT`/self-destruct-driven token transfer prohibitively expensive or push it toward exceeding the transaction's energy/time budget. This does not immediately brick the entire chain's core functionality (unlike a truly global iterated array as in the `addPool` report, since `asset` maps are per-account, not chain-wide), which lowers the severity relative to the original finding, but it is a genuine underpriced-computation / targeted-DoS vector against a specific account with no cost proportional to the actual damage caused (transferring 1 unit of a token is very cheap bandwidth-wise, while causing an ever-growing map that must be rebuilt/iterated repeatedly afterward).

### Likelihood Explanation
Likelihood is higher than the original report's "requires a malicious/erring admin" scenario, since no privileged role is needed at all — any account holder can perform this using standard `TransferAssetContract` calls against thousands of already-issued TRC10 tokens on mainnet. The main friction is that many distinct token types must be acquired first (via exchange/purchase or by issuing new ones, each issuance costing the `AssetIssueFee`), but this is an entirely permissionless, repeatable action rather than a rare admin mistake.

### Recommendation
Introduce an explicit cap on the number of distinct asset entries (`assetV2`/legacy `asset`) an account may accumulate, enforced in the token-receiving path (`AccountCapsule.addAssetAmountV2` / `TransferAssetActuator` validation), analogous to the `UNFREEZE_MAX_TIMES` bound already used for `UnFreezeV2` lists. Alternatively, redesign per-account asset accounting to avoid iterating the full map in `BandwidthProcessor.updateUsage` and `MUtil.transferAllToken` (e.g., lazy/on-demand accounting per token rather than eager iteration of all held tokens).

### Proof of Concept
1. Attacker acquires a minimal balance (e.g., `1` unit) of `N` distinct, already-issued TRC10 tokens (thousands exist on mainnet).
2. For each token, attacker submits a `TransferAssetContract` transaction sending `1` unit to victim address `V`. Each such transfer succeeds via the standard, unbounded `AccountCapsule.addAssetAmountV2` path (`chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java:733-765`), adding one entry to `V`'s `assetV2` map with no size check.
3. After repeating this `N` times (N can be arbitrarily large, bounded only by attacker's token acquisition cost/time), `V`'s `assetV2` map has `N` entries.
4. Any subsequent transaction involving `V` invokes `BandwidthProcessor.updateUsage(V)`, which iterates all `N` map entries (`chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java:66-78`), incurring cost proportional to `N` on every such transaction going forward.
5. If `V` is instead a smart contract, triggering `SELFDESTRUCT` invokes `MUtil.transferAllToken`, which likewise iterates all `N` entries (`actuator/src/main/java/org/tron/core/vm/utils/MUtil.java:34-37`), increasing the cost/energy required to self-destruct proportionally to `N`.

  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }
