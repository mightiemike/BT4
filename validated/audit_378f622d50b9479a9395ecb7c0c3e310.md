### Title
Missing Root/Anchor Validation Against On-Chain Note-Commitment History in `VerifyMintProof`/`VerifyTransferProof`/`VerifyBurnProof` Precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The reported bug is that `withdrawBySnapshot()` accepts an `extraProof.root` that is never checked against the trusted `massExitBlock.blockRid` — only internal consistency of the proof is checked, not consistency with the canonical chain state. The same bug class exists in java-tron's Shielded TRC-20 precompiled contracts: `VerifyMintProof`, `VerifyTransferProof`, and `VerifyBurnProof` accept a caller-supplied `anchor` (merkle root) that is validated only for internal zk-SNARK proof consistency via `librustzcashSaplingCheckSpend`, but is **never checked against the actual, on-chain history of note-commitment tree roots** that the shielded TRC-20 contract is supposed to represent.

### Finding Description
In the native shielded-transaction path, `ShieldedTransferActuator.validate()` explicitly checks that any spend's `anchor` is a real, previously-recorded merkle root: [1](#0-0) 

This is the equivalent of validating `extraProof.root` against `massExitBlock.blockRid` in the reported bug — it binds the caller-supplied root to a canonical, previously-existing chain state.

However, the Shielded TRC-20 precompiled contracts (`VerifyMintProof`, `VerifyTransferProof`, `VerifyBurnProof`), which are the TVM-level primitives that back the on-chain `ShieldedTRC20` contract's `mint`/`transfer`/`burn` entry points, perform no such check. In `VerifyBurnProof.execute()`, the `anchor` is taken directly from caller-supplied `data` and passed straight into the zk-SNARK verification call: [2](#0-1) 

The same pattern appears in `VerifyTransferProof`, where `anchor[i]` values extracted from the ABI-encoded input are fed straight into `SaplingCheckSpendTask` without any lookup against a persisted root/anchor history: [3](#0-2) 

The only state that is threaded through these precompiles is the `frontier`/`leafCount` pair — an incremental-merkle-tree "frontier" representation that is itself supplied by the caller (the calling Solidity contract) as raw bytes and updated via `insertLeaves()`: [4](#0-3) 

Nothing in `VerifyProof`/`insertLeaves` or the `VerifyMintProof`/`VerifyTransferProof`/`VerifyBurnProof` classes checks that the presented `anchor` corresponds to a root that this `frontier` state (or any historical state of it) has ever actually produced. The zk-SNARK check (`librustzcashSaplingCheckSpend`) only proves that *some* note with the claimed nullifier/commitment is consistent with the *claimed* anchor via the supplied merkle path inside the proof — it does not prove that the claimed anchor is a root the chain/contract has legitimately committed to. Because the `anchor` is fully attacker-controlled input data (part of `data` in `execute(byte[] data)`), an attacker who controls both sides of a note (their own spending key, rcm, and path) can generate a self-consistent zk-SNARK proof for an anchor that was never actually part of the ShieldedTRC20 contract's real note-commitment tree — i.e., they can prove membership in a merkle tree of their own construction and present its root as `anchor`. Since the precompile trusts the proof-internal consistency instead of checking the anchor against the contract's real historical set of valid roots, this validation must instead be enforced entirely by the calling Solidity `ShieldedTRC20` contract (root history tracking) — outside the scope of this repository, so if that Solidity contract fails to maintain/verify against a root history (as the reported bridge bug shows can happen), the precompile provides no defense-in-depth.

### Impact Explanation
If the higher-layer `ShieldedTRC20` Solidity contract (not present in this repository, but the one these precompiles are explicitly designed to serve) fails to independently track and check a root/anchor history — exactly the class of omission described in the reported finding — an attacker can fabricate a spend/burn proof against an arbitrary self-chosen anchor that was never actually part of the pool's real commitment tree, and successfully pass `VerifyTransferProof`/`VerifyBurnProof`. This allows minting spend authorization out of thin air, i.e., draining the shielded pool's backing TRC-20 tokens without ever having deposited them — a direct accounting/settlement forgery, analogous in class and severity to draining a bridge contract during a mass exit.

### Likelihood Explanation
Likelihood is contingent on the calling Solidity contract's root-history enforcement. Since the precompile itself performs zero cross-checking against any persisted root set, the security of the whole flow rests entirely on Solidity-side bookkeeping that is external to and unverifiable at this layer, and the reported bug's root cause (skipping root binding to trusted history) demonstrates that such external checks are exactly the kind of validation prone to being missed. Any ShieldedTRC20-style contract that (like `withdrawBySnapshot()`) relies on the precompile's return value alone, without independently maintaining/consulting a root history, is directly exploitable.

### Recommendation
Require the anchor/root passed into `VerifyMintProof`, `VerifyTransferProof`, and `VerifyBurnProof` to be checked against a maintained, append-only history of valid roots (equivalent to `merkleContainer.merkleRootExist()` used by `ShieldedTransferActuator`), either by exposing a root-history precompile/oracle that the TVM contract must call, or by having the precompile itself validate the anchor against the frontier-derived root set it manages. At minimum, document and enforce (via a required precompile check) that any consuming contract must verify the anchor's presence in an on-chain-maintained root history before minting/transferring/burning value.

### Proof of Concept
1. Attacker calls `mint()` via `VerifyMintProof` with amount X, receiving a valid note into a merkle tree of their choosing (not the real contract tree) — or simply constructs their own independent incremental merkle tree offline with a note they fully control (own `sk`, `rcm`, value).
2. Attacker computes a valid merkle path/anchor `A'` for their self-constructed tree containing that note, and generates a valid Sapling spend zk-SNARK proof binding note → `A'`.
3. Attacker calls `VerifyBurnProof.execute(data)` (or `VerifyTransferProof`) supplying `anchor = A'`, the crafted spend proof, and a `nullifier`.
4. `librustzcashSaplingCheckSpend` returns `true` because the proof is internally consistent for `A'`, even though `A'` was never actually a root produced by the real, on-chain frontier/leafCount progression of the `ShieldedTRC20` contract: [5](#0-4) 
5. If the calling Solidity contract does not separately verify `A'` is a historically valid root (mirroring the missing `extraProof.root` vs. `massExitBlock` check in the original report), the burn/transfer succeeds and the attacker extracts real TRC-20 value they never legitimately deposited.
