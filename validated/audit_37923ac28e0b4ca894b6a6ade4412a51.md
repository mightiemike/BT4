## Finding: Relayer fee paid unconditionally regardless of transaction execution outcome

### Title
Relayer fee is paid out before the underlying wallet action's success is verified, allowing fee extraction on failed transactions - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Sherlock report flags that `transfer()`/return values for ERC-20 transfers are not checked, letting code proceed as if a transfer succeeded when it may have silently failed. The `near-wallet-contract` (Near's Ethereum-emulation wallet, callable by any account submitting an RLP-encoded transaction to `rlp_execute`) has the analogous defect: it pays out the relayer's fee via an unconditional native `Transfer` action *before* it is known whether the emulated action (ERC-20 transfer, base-token transfer, or generic Near action) will actually succeed.

### Finding Description
In `inner_rlp_execute`, once the transaction is parsed successfully, the code unconditionally schedules a fee refund to `context.predecessor_account_id` (the caller of `rlp_execute`, i.e. the relayer) whenever the fee is non-zero: [1](#0-0) 

This `refund_promise` is created and fired independently of the `promise` that will actually carry out the user's intended action (base transfer, ERC-20 `ft_transfer`, or generic function call), which is only built afterward in the `match transaction_kind { ... }` block: [2](#0-1) 

The eventual success/failure of that action is only checked later in `rlp_execute_callback`, and even then only the attached `caller_deposit` is refunded on failure — the relayer's fee transfer has no such rollback: [3](#0-2) 

Because the fee transfer is a separate, immediately-dispatched native `Transfer` receipt (not chained via `.then()` to the outcome of the main action), the wallet pays the "relayer fee" regardless of whether the emulated action (e.g. an NEP-141 `ft_transfer` that panics due to insufficient token balance, an unregistered receiver, or any other cross-contract failure) actually completes. This mirrors the reported bug class of "acting as if a transfer succeeded without checking its actual result" — except here it directly costs the wallet owner real $NEAR.

### Impact Explanation
Any account (not necessarily an honest relayer) can call `rlp_execute` with a validly signed transaction of a victim's wallet and, being `predecessor_account_id`, will receive the fee refund immediately, even if the underlying action later fails for reasons unrelated to the relayer (e.g., the wallet's token balance is insufficient for the ERC-20 transfer amount, causing `ft_transfer` to fail). The wallet owner's nonce is consumed (so no retry) and the wallet loses the fee in $NEAR without receiving the paid-for service. This is unauthorized value movement out of the wallet contract triggered purely by a submitted transaction/RPC call.

### Likelihood Explanation
This requires only that a user's wallet contract have a non-zero fee tx, and that the eventual emulated action fails (e.g. insufficient token balance for the exact transfer amount, or the target rejecting the call) — situations that a relayer or attacker who has the signed transaction bytes (which are broadcast/relayed publicly) can trivially trigger by simply resubmitting them once the wallet's token balance is no longer sufficient, or racing to submit before the intended relayer.

### Recommendation
Do not fire the relayer fee refund promise independently of the outcome of the main action. Instead, chain the fee payment as a callback that only executes/keeps the transfer if `rlp_execute_callback` observes `PromiseResult::Successful`, or roll the fee transfer back (similar to the existing `caller_deposit` refund logic) if the main promise fails.

### Proof of Concept
1. User signs an Ethereum-style ERC-20 transfer transaction via their wallet contract with `max_fee_per_gas * gas_limit` non-zero (i.e. `tx_fee > 0`), intending to transfer more NEP-141 tokens than currently held (or targeting a receiver that will cause `ft_transfer`/`storage_deposit` to fail).
2. Any account calls `rlp_execute(target, tx_bytes_b64)` on the wallet contract, becoming `predecessor_account_id`.
3. `inner_rlp_execute` (`lib.rs:367-385`) immediately creates and fires `refund_promise` transferring `fee` yoctoNEAR to the caller.
4. The main promise chain (`storage_balance_of` → `ft_transfer`/`storage_deposit`) subsequently fails because of insufficient token balance or other cross-contract error.
5. `rlp_execute_callback` reports `success: false` and refunds only the `caller_deposit` (if any) — the fee already sent to the caller in step 3 is never returned.
6. Result: the wallet lost `fee` yoctoNEAR with no successful action performed, and the caller (who need not be the intended relayer) profited unconditionally.

                    .parse()

            };

            address_registrar.lookup(address).then(ext.address_check_callback(

        TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => {
            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }

            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
