### Title
Unbounded witness-created proposal backlog can stall `ProposalController.processProposals()` during maintenance - (File: `framework/src/main/java/org/tron/core/consensus/ProposalController.java`)

### Summary
Any account that becomes a witness candidate (a permissionless action, not requiring election to the active top-27 set) can call `ProposalCreateActuator` an unbounded number of times with zero fee, inflating `latestProposalNum`. Every maintenance cycle, `ProposalController.processProposals()` walks backward from `latestProposalNum` through every unprocessed proposal, calling `processProposal()` (which mutates and re-persists each capsule) for every PENDING-but-expired entry it finds. This is analogous to the reported Morph `Gov.sol` issue where an unbounded, attacker-inflatable proposal count causes an expensive iteration in consensus-critical code executed by every node.

### Finding Description
`ProposalCreateActuator.validate()` only requires that the owner address exists in `chainBaseManager.getWitnessStore()` [1](#0-0) . Witness-store membership is obtained via `WitnessCreateContract`, a permissionless registration that does not require being an elected/active witness — any staker with the requisite fee can register. `calcFee()` for proposal creation returns `0` [2](#0-1) , and there is no cooldown or per-account limit on proposal creation — each call simply increments `currentProposalID`/`latestProposalNum` and stores a new capsule [3](#0-2) .

During every maintenance period, `ProposalController.processProposals()` iterates backward from `latestProposalNum` to `1`, fetching each proposal from the `ProposalStore` and only stopping when it reaches a proposal that `hasProcessed()` (state `APPROVED`/`DISAPPROVED`) [4](#0-3) . For every unprocessed, expired proposal encountered it invokes `processProposal()`, which reads active witnesses, computes approvals, and re-writes the capsule to the store, potentially also driving `ProposalService.process()` for approved ones [5](#0-4) . This scan executes synchronously in the consensus/maintenance path on every full node, with no gas metering or execution-time bound, similar in shape to the `Gov.sol` pruning loop from the referenced report — the number of iterations is proportional to attacker-controlled proposal creation volume rather than to any bounded governance parameter.

### Impact Explanation
If a witness candidate floods the network with a very large number of `ProposalCreateContract` transactions within a single maintenance window (all sharing similarly-computed expiration times, since expiration is derived from `maintenanceTimeInterval`/`proposalExpireTime` rather than attacker-chosen), the next `processProposals()` invocation must scan and process the entire backlog on every full node simultaneously. This is a network-wide, consensus-path resource-consumption issue (disk I/O and CPU per node, executed in lock-step at maintenance time), which could slow block/maintenance processing for all nodes — a DoS on protocol implementation rather than an isolated RPC endpoint issue.

### Likelihood Explanation
Becoming a witness candidate only requires standard, unprivileged staking/registration (paying the witness-creation fee); it does not require being one of the elected active-27 witnesses. Combined with the zero fee and lack of any creation-rate limiting on `ProposalCreateContract`, an attacker only needs sufficient bandwidth/energy for the transactions themselves to inflate the proposal count arbitrarily, making this feasible for any account willing to pay the one-time witness registration cost.

### Recommendation
Introduce a cooldown or per-witness rate limit on `ProposalCreateContract` (as suggested in the referenced report for `Gov.sol`), and/or bound the number of outstanding PENDING proposals `processProposals()` will process per maintenance cycle, so that scan cost cannot grow unbounded with attacker-controlled proposal creation.

### Proof of Concept
Not executed; behavior inferred from code paths cited above (`ProposalCreateActuator.validate()`/`execute()` and `ProposalController.processProposals()`). A concrete PoC would require a testnet witness account issuing a large batch of `ProposalCreateContract` transactions and measuring `processProposals()` execution time at the next maintenance boundary — this was not verified in this analysis.

  public void processProposals() {
    long latestProposalNum = manager.getDynamicPropertiesStore().getLatestProposalNum();
    if (latestProposalNum == 0) {
      logger.info("latestProposalNum is 0, return");
      return;
    }

    long proposalNum = latestProposalNum;

    ProposalCapsule proposalCapsule = null;

    while (proposalNum > 0) {
      try {
        proposalCapsule = manager.getProposalStore()
            .get(ProposalCapsule.calculateDbKey(proposalNum));
      } catch (Exception ex) {
        logger.error("", ex);
        proposalNum--;
        continue;
      }

      if (proposalCapsule.hasProcessed()) {
        logger
            .info("Proposal has processed, id:[{}], skip it and before it",
                proposalCapsule.getID());
        //proposals with number less than this one, have been processed before
        break;
      }

      if (proposalCapsule.hasCanceled()) {
        logger.info("Proposal has canceled, id:[{}], skip it", proposalCapsule.getID());
        proposalNum--;
        continue;
      }

      long currentTime = manager.getDynamicPropertiesStore().getNextMaintenanceTime();
      if (proposalCapsule.hasExpired(currentTime)) {
        processProposal(proposalCapsule);
        proposalNum--;
        continue;
      }

      proposalNum--;
      logger.info("Proposal has not expired, id:[{}], skip it", proposalCapsule.getID());
    }
    logger.info("Processing proposals done, oldest proposal[{}]", proposalNum);
  }

    List<ByteString> activeWitnesses = this.manager.getWitnessScheduleStore().getActiveWitnesses();
    if (proposalCapsule.hasMostApprovals(activeWitnesses)) {
