### Title
Replay-verify's `ensure_match_transaction_info` never checks `state_checkpoint_hash`, letting state-root divergence pass as a successful replay — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole integrity check used by the archive replay-verify tool to confirm that locally re-executed transactions produced the exact same committed ledger state as what is recorded on-chain. The function checks status, gas used, the write-set hash, and the event-root hash, but it never compares the recomputed `state_checkpoint_hash` (or `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the expected value from the authenticated `TransactionInfo`. As a result, a divergence in the actual state Merkle root — the primary signal that a replay or historical execution has produced an incorrect ledger state — is silently ignored by the one code path whose job is to detect exactly that.

### Finding Description
`ensure_match_transaction_info` is defined here: [1](#0-0) 

It compares:
- `self.status()` vs `expected_txn_status`
- `self.gas_used()` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- recomputed `event_root_hash` vs `txn_info.event_root_hash()`

It never touches `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.maybe_position_state_checkpoint_hash()`. The comment left in the code by the original author explicitly acknowledges this: [2](#0-1) 

The state_checkpoint_hash is the accumulator/Jellyfish-Merkle-derived commitment to the *entire resulting state* after a checkpoint boundary (computed separately from the write-set hash, which only commits to that one transaction's deltas). It is produced during ledger update in `assemble_transaction_infos`: [3](#0-2) 

This is the only field in `TransactionInfo` that binds a transaction to the *cumulative* state root rather than just that transaction's own write set/events. Skipping it in the verification comparator means the comparator can never detect a scenario where the write set and events match but the resulting global state tree (JMT) has diverged — e.g. from a bug in state-merkle update, a schema/versioning mismatch during restore, or a chunk executor miscomputing state roots.

`execute_and_verify` in the archive replay tool calls exactly this function as its pass/fail gate for each replayed transaction: [4](#0-3) 

If replay succeeds, the tool reports the version range as "verified" with no error, even though it has structurally never checked that the state root it locally computed equals the state root actually committed to the ledger/accumulator at that version.

### Impact Explanation
Replay-verify (`aptos-db-tool replay-on-archive`) exists specifically to catch state-commitment bugs and hard-fork-only divergence by fully re-executing history against an archived DB and confirming the recomputed ledger state matches what was actually committed. Because the one check that would catch a state-root mismatch is absent, any bug in the executor/storage stack that corrupts the accumulated state tree while still producing byte-identical write sets/events for the replayed transaction (or where the divergence is entirely in the state-merkle commitment layer rather than the write set itself, such as a corrupted state value read pre-image, a hot-state checkpoint discrepancy, or an incorrect state-checkpoint computed during a chunk boundary) will go completely undetected. This directly undermines the "authenticated ledger version/root binding" invariant this tool is relied upon to enforce, and it is the exact class of bug ("hard-fork-only divergence during commit, replay, restore, or proof verification" going undetected) called out as in-scope.

### Likelihood Explanation
This is not an attacker-triggered exploit against consensus; it is a structural gap in an internal verification tool that node operators and the Aptos team rely on to catch exactly this class of bug before/after upgrades. The likelihood of the underlying state-root divergence occurring is separate from this bug, but whenever it does occur, this comparator is guaranteed to miss it because the check is categorically absent from the code, not merely misconfigured.

### Recommendation
Add explicit `ensure!` checks in `ensure_match_transaction_info` comparing the recomputed `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the values in the expected `TransactionInfo`, mirroring the pattern already used for `state_change_hash` and `event_root_hash`. This requires threading the replay tool's locally computed state-checkpoint hash (currently only produced inside `do_state_checkpoint.rs` / `do_ledger_update.rs`) into `TransactionOutput` or into the comparator's call site so it can be validated per-transaction/per-checkpoint rather than skipped entirely.

### Proof of Concept
1. In the replay-verify tool (`storage/db-tool/src/replay_on_archive.rs`), replay a version range where the archived `TransactionInfo` has a given `state_checkpoint_hash`.
2. Force (or naturally hit, via any latent state-merkle/storage bug) a scenario where the locally re-executed transaction produces the identical `write_set`/`events`/`gas_used`/`status` as expected, but where the downstream JMT/accumulator ends up computing a different overall state root than the archived one (e.g., by mutating an unrelated leftover leaf, or replaying with a subtly different `state_view_at_version` base).
3. Observe that `execute_and_verify` -> `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) returns `Ok(())` because none of its `ensure!` checks reference `state_checkpoint_hash`, so the tool reports the chunk as successfully verified despite the actual state root diverging from the authenticated ledger.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
