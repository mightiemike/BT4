### Title
Unbounded, non-deduplicated array growth in `KVSessionStorage.addShopIds` enables shop-scoped session-storage DoS - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage` maintains, per shop, a JSON array of session IDs (`shop:<shop>` key) that is grown on every `storeSession` call via `addShopIds`. Unlike the Redis and DynamoDB adapters in the same package family, this method does not check whether the ID already exists before appending, and there is no upper bound on the array size. Any code path that re-invokes `storeSession` with the same (deterministic) session id — most notably the offline session id `offline_${shop}` used throughout the token-exchange/OAuth flows — causes the per-shop array to grow by one duplicate entry every time, with no cap analogous to Alchemix's `MAX_DELEGATES`.

### Finding Description
`storeSession` always calls `addShopIds(session.shop, [session.id])`, which does: [1](#0-0) 

There is no `includes()`/dedup check here, in contrast to the Redis adapter's equivalent `addKeyToShopList`, which explicitly guards against duplicates: [2](#0-1) 

Offline sessions use a deterministic, shop-scoped id (`offline_${shop}`) generated by `getOfflineId`: [3](#0-2) 

The token-exchange authentication strategy (used by `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router`) calls `sessionStorage.storeSession(offlineSession)` any time a valid, active offline session isn't currently present in storage: [4](#0-3) 

Because `addShopIds` blindly concatenates instead of deduplicating, each such re-store operation appends another copy of `offline_${shop}` (or the deterministic online id `${shop}_${userId}` for embedded apps) to the shop's KV array, permanently growing it. This mirrors the Alchemix root cause: an array associated with a single logical key (there, a delegate's token list; here, a shop's session-id list) that is allowed to grow without a cap or duplicate check, eventually degrading or breaking operations that must iterate/serialize the whole array.

### Impact Explanation
`findSessionsByShop` iterates the entire array and issues one KV `get` per (now duplicated) id: [5](#0-4) 

As the array grows, `findSessionsByShop` and every subsequent `storeSession`/`deleteSession` call (which read-modify-write the same JSON blob) become progressively more expensive, and the value is subject to Cloudflare KV's 25 MiB value-size limit. Once that limit is hit, `namespace.put` for the shop key begins failing, breaking `storeSession` for that shop going forward — a denial of service against the app's authentication/session-storage layer for that shop, affecting all of its users (merchant staff and app-proxy/customer sessions alike), not just the actor who triggered it.

### Likelihood Explanation
This is reachable by any actor able to repeatedly cause the offline (or online) session to be re-exchanged/re-stored while the KV adapter is in use — e.g., a customer/merchant staff member whose stored session is deleted, expires, or is otherwise treated as inactive between requests, or an actor deliberately forcing repeated token-exchange calls with a valid session token. No secret disclosure, MITM, or elevated privilege is required; it only requires normal, repeatable interaction with an authentication endpoint backed by `shopify-app-session-storage-kv`.

### Recommendation
Update `KVSessionStorage.addShopIds` to deduplicate before storing, mirroring the Redis adapter's check, e.g. only append `id` if `!shopIds.includes(id)`, and consider bounding the maximum tracked session-id count per shop (pruning stale entries during `findSessionsByShop`/`storeSession`) to avoid unbounded growth analogous to `MAX_DELEGATES`.

### Proof of Concept
1. Configure an app with `KVSessionStorage` and enable offline-token based `performTokenExchange`.
2. Repeatedly send authenticated requests with a valid session token while ensuring the stored offline session for the shop is treated as inactive/missing before each request (e.g., have the KV entry for `offline_${shop}` deleted, expired, or simulate storage read failures).
3. Each request triggers `exchangeToken` → `config.sessionStorage.storeSession(offlineSession)` → `addShopIds(shop, ['offline_<shop>'])`.
4. Inspect the `shop:<shop>` KV key after N iterations — it will contain N duplicate `offline_<shop>` entries, growing linearly and without limit, eventually approaching Cloudflare KV's per-value size limit and causing `storeSession`/`findSessionsByShop` failures for that shop.

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
