## Title
Unhandled `unwrap()` panic on stale `GlobalContractDistribution` receipts across multiple legacy shard splits causes a transaction-triggered chain halt - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally `.unwrap()`s the result of `Receipt::receiver_shard_id()` on every receipt popped from the delayed-receipt queue. For `GlobalContractDistribution` receipts, `receiver_shard_id()` can return `Err(EpochError::ShardingError(..))` when the receipt's `target_shard` predates the shard's split history and cannot be resolved to a shard in the current layout. Under legacy (non-`ShardLayoutV3`) resharding, this resolution is limited to a single generation, so a `GlobalContractDistribution` receipt that stays delayed (e.g. due to shard congestion) across two or more shard-splitting protocol upgrades becomes permanently unresolvable, and popping it from the delayed queue panics every node applying that shard's chunk.

### Finding Description
`Receipt::receiver_shard_id` handles `GlobalContractDistribution` receipts specially: if the receipt's stored `target_shard` no longer exists in the current shard layout, it calls `shard_layout.resolve_to_current_shard(target_shard)` and returns an `Err(EpochError::ShardingError(...))` if that fails [1](#0-0) .

`ShardLayout::resolve_to_current_shard` only performs full-history resolution for `ShardLayoutV3` (dynamic resharding). For `V0`/`V1`/`V2` layouts (i.e. legacy/static resharding, still the production path today), it falls back to `get_children_shards_ids`, which is explicitly documented and implemented to support only a single split generation [2](#0-1) . If two (or more) shard-splitting layout transitions occur while the receipt is delayed, this lookup returns `None`, propagating an `Err` all the way up.

That `Err` is fatal at the call site: `DelayedReceiptQueueWrapper::receipt_filter_fn` calls `.unwrap()` directly on `receiver_shard_id(&shard_layout)`:
```
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
``` [3](#0-2) 

This filter is invoked on every receipt popped from the delayed queue during ordinary chunk application (`DelayedReceiptQueueWrapper::pop`), which runs deterministically as part of `Runtime::apply` → `process_delayed_receipts` for every honest validating/tracking node [4](#0-3) .

The engineering team's own test acknowledges this gap explicitly, noting the mitigation (full split-history tracking) exists only for `ShardLayoutV3`:
```
// The fix only works with V3 shard layouts (dynamic resharding).
// With static resharding, the shard layout doesn't maintain a full split history.
``` [5](#0-4) 
and the corresponding test comment describes the exact crash: *"processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations."* [6](#0-5) 

A user can attacker-control the receipt's genesis condition entirely from a single submitted transaction: deploying a global contract creates a `GlobalContractDistributionReceiptV1/V2` with `target_shard` set to the deployer's current shard [7](#0-6) , and an attacker can keep that receipt (and any of its shard-hop forwards) stuck in the delayed queue by continuously saturating the target shard's compute budget with ordinary function calls, exactly as demonstrated in the existing regression test [8](#0-7) . If that shard then undergoes two (legacy/static) shard-splitting layout transitions while the receipt remains delayed, all nodes attempting to apply the chunk that drains the delayed queue for that shard will hit the `unwrap()` panic.

### Impact Explanation
A panic inside `Runtime::apply` during ordinary delayed-receipt draining is not an isolated node failure — every honest node validating or tracking that shard executes the identical deterministic code path and will panic identically when it reaches the same delayed receipt. This produces a synchronized crash loop across the network for that shard, i.e. a transaction-triggered halt of chain progress, matching the accepted impact category (a transaction that reliably prevents block/chunk finalization). It is directly analogous to the reported Argo Workflows bug class: an ordinary, low-privilege, low-cost action (submit + clean up daemon workflows / here, deploy a global contract + keep it congested) reliably drives a crash across the controller/validator fleet.

### Likelihood Explanation
Triggering requires: (1) a single `DeployGlobalContract` action from any account (no special privilege), (2) sustained shard congestion (cheap, achievable with self-calls burning gas, as already demonstrated by the project's own PoC-style regression test), and (3) two legacy shard-splitting layout changes occurring while the receipt is delayed. Because `ShardLayoutV3`/dynamic resharding is a newer feature and legacy static (`V2`) shard-layout transitions are still part of the supported migration path (used e.g. during bootstrapping dynamic resharding, per `docs/architecture/how/dynamic_resharding.md`), the precondition of "two static-resharding generations while a receipt is congested-delayed" is realistic on any network still performing/migrating through static resharding events, and the condition is entirely attacker-triggerable on the delay side.

### Recommendation
Do not `.unwrap()` the result of `receiver_shard_id()` in `receipt_filter_fn`; propagate the error through `pop()`'s `Result` instead of panicking. Additionally, extend split-history tracking (or an equivalent fallback) to legacy `V0`/`V1`/`V2` shard layouts so `resolve_to_current_shard` can resolve receipts across multiple generations, or reject/redirect `GlobalContractDistribution` receipts whose `target_shard` cannot be resolved (e.g., drop with a logged/metric warning) rather than allowing an unrecoverable state to reach `apply()`.

### Proof of Concept
The project's own regression test reproduces the exact scenario (deploy global contract → congest target shard → force two shard splits → drain delayed queue) and documents that, absent the `ShardLayoutV3` full-history fix, this panics in `receipt_filter_fn`: [9](#0-8) . The same sequence performed against a shard layout that has not migrated to `ShardLayoutV3` (i.e. still using `V2`/static resharding across two splits) is not covered by the fix and remains exploitable per the code path cited above.
