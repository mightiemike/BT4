### Title
CEA inbound path lets an unprivileged source-chain contract execute arbitrary calldata against any deployed UEA, bypassing UEA-owner signature authorization - (File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go)

### Summary
`ExecuteInboundFundsAndPayload` (and the analogous `ExecuteInboundGasAndPayload`) calls `ExecutePayloadV2` with `evmFrom = ueModuleAddr` whenever `Inbound.IsCEA == true` and `Inbound.Recipient` resolves to a deployed UEA. Per `x/uexecutor/README.md`, when `evmFrom == UNIVERSAL_EXECUTOR_MODULE`, the UEA contract's `executeUniversalTx` skips ECDSA/Ed25519 signature verification of `VerificationData` (that check is only guaranteed for `evmFrom != UNIVERSAL_EXECUTOR_MODULE`). For the non-CEA path this is safe because `ueaAddr` is deterministically derived from `Inbound.Sender` (the entity that actually authored the observed source-chain transaction). For the CEA path, however, `Recipient` (and thus `ueaAddr`) is an attacker-controlled field with no binding to `Inbound.Sender`, and `UniversalPayload`/`VerificationData` are likewise fully attacker-controlled. Nothing in the scoped code verifies that the CEA-originating contract/sender is authorized to act on behalf of the targeted UEA's owner.

### Finding Description
This is the native analog of the external H-01 report: Alligator's `isValidProxySignature` trusted a self-supplied "authority chain" without validating the chain was actually rooted in a legitimate signer, letting an attacker forge authorization by setting `authority[0] = self`. In Push Chain, the equivalent authorization gate is the `evmFrom == UNIVERSAL_EXECUTOR_MODULE` check inside `UEA_EVM.sol`/`UEA_SVM.sol`'s `executeUniversalTx`, documented in [1](#0-0) . That check exists to let the module execute pre-authorized (i.e., sender-derived) payloads without a redundant signature, but it implicitly trusts every call the module makes as already-authorized.

The CEA branch of `ExecuteInboundFundsAndPayload` breaks that trust assumption: [2](#0-1) 

Here `ueaAddr` comes directly from the attacker-suppliable `Inbound.Recipient` field, gated only by "is this address a deployed UEA" (`CallFactoryGetOriginForUEA`) — not by any relationship to `Inbound.Sender` or any registry-level allowlist of trusted CEA senders/gateways per chain.

Regardless of the isCEA/non-CEA branch taken, execution then unconditionally proceeds to: [3](#0-2) 

`ExecutePayloadV2` is invoked with `evmFrom = ueModuleAddr` (the module account), the attacker-chosen `ueaAddr`, the attacker-chosen `UniversalPayload` (arbitrary `To`/`Data`/`Value`), and the attacker-chosen `VerificationData` (which integration tests show is routinely left empty for CEA inbounds, e.g. `VerificationData: ""`) [4](#0-3) .

Because honest Universal Validators only attest to *what actually happened on the source chain* — and an attacker fully controls what a contract they deploy/call on that source chain emits — an unprivileged attacker can cause a genuine, honestly-observed event whose `Recipient` names a victim's UEA and whose `UniversalPayload.Data` is arbitrary calldata (e.g., an ERC20/PRC20 `transfer`/`approve` call). Once 2/3+ honest UVs vote it in (`VoteInbound`/ballot finalization, which validates only that the event was truthfully observed, not that the payload is authorized by the UEA owner), the module executes it via `ExecutePayloadV2` with the module's own address as `evmFrom`, which — per the documented contract behavior — bypasses the UEA owner's signature check entirely. The `Recipient` UEA is never proven to belong to, or have consented to control by, `Inbound.Sender`/the CEA contract.

### Impact Explanation
This directly maps to the "Push Chain Allowed Impact Gate": unauthorized UEA execution and unauthorized draining/transfer of user-controlled funds. An attacker who has never interacted with the victim's UEA, does not control the victim's private key, and holds no privileged role (not a validator, not the UEA owner) can cause the `uexecutor` module to execute arbitrary EVM calldata as/through the victim's UEA — e.g. transferring out the UEA's PRC20 or native balances — with zero cryptographic authorization from the UEA owner. This is a full compromise of the per-account authorization invariant that the rest of the module (and its own README) claims is enforced via `Signer`/owner-signature binding.

### Likelihood Explanation
Likelihood is high in principle: the only requirement is that the attacker can deploy or otherwise trigger a contract call on some chain configured in `x/uregistry` with `IsInboundEnabled = true`, emitting a gateway-style event that the Push Chain relayer parses as `IsCEA = true` with an arbitrary `Recipient`/`UniversalPayload`. No relayer-side or Cosmos-side allowlist of "which source-chain senders/contracts may act as a CEA on behalf of which UEA" was found in the reviewed code (`x/uregistry` chain/token config carries no such CEA-sender binding, and `execute_inbound_funds_and_payload.go` performs no `Sender`-to-`Recipient` relationship check). This assessment is based on the code paths and documentation reviewed above; I was not able to fully inspect `universalClient/chains/common/event_processor.go` or the actual EVM/SVM UEA contract source (external repo, not indexed here) within the remaining tool budget, so I cannot rule out an additional allowlist/gating mechanism enforced purely at the relayer or gateway-contract level that would need to be bypassed as well. This uncertainty should be resolved before treating the finding as fully confirmed.

### Recommendation
- Require that a CEA inbound's `Recipient` (target UEA) be provably linked to an owner/CEA-relationship that the actual UEA owner registered in advance (e.g., an on-chain allowlist stored per-UEA of permitted CEA source-chain sender addresses), analogous to fixing Alligator by validating `proxy == proxyAddress(authority[0], proxyRules)`.
- Alternatively, never allow the module to call `ExecutePayloadV2`/`executeUniversalTx` with the trust-bypassing `evmFrom == UNIVERSAL_EXECUTOR_MODULE` path when `Inbound.IsCEA == true`; instead always require and verify real `VerificationData` (owner signature or precompile-based `verifyTxHash` proof) for CEA-originated payload executions, regardless of `evmFrom`.
- Add a registry-level (`x/uregistry`) explicit binding between a chain's approved CEA gateway/sender addresses and permitted target semantics, and enforce it inside `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` before invoking `ExecutePayloadV2`.

### Proof of Concept
Conceptual PoC (cannot be executed without the external `UEA_EVM.sol` source and a full devnet, which are outside this repo's indexed content):
1. Attacker deploys a trivial contract on a supported chain (e.g. `eip155:11155111`) that emits the standard gateway inbound event, setting: `Sender = attacker's own address`, `Recipient = victimUeaAddress` (a real, already-deployed UEA discoverable from public UEA factory events), `Amount = "0"`, `IsCEA = true`, `UniversalPayload = {To: <PRC20 token address>, Data: encode("transfer", attacker, victimUeaBalance)}`, `VerificationData = ""`.
2. Honest Universal Validators observe this real on-chain event and submit `MsgVoteInbound` with matching data (they are honestly reporting what occurred), as in the test harness pattern: [5](#0-4) .
3. The ballot finalizes (2/3+ honest votes), producing a `UniversalTx`; `ExecuteInboundFundsAndPayload` runs the `IsCEA` branch, resolves `ueaAddr = victimUeaAddress` via `CallFactoryGetOriginForUEA` (succeeds because it is a real deployed UEA), skips deposit (amount is 0), and unconditionally calls `ExecutePayloadV2(ueModuleAddr, victimUeaAddress, maliciousPayload, "")`.
4. If, as documented, the UEA contract skips signature verification when `msg.sender == UNIVERSAL_EXECUTOR_MODULE`, the malicious `transfer` calldata executes as/through the victim's UEA, moving its PRC20 balance to the attacker — without the attacker ever having possessed the UEA owner's key or any privileged role.

Verifying step 4 with certainty requires reading `UEA_EVM.sol`'s `executeUniversalTx` (external `push-chain-core-contracts` repo, not available in this index) to confirm the exact bypass condition as stated in the README.

#### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**

#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
