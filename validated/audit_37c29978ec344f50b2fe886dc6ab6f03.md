### Title
Replay-verify's `ensure_match_transaction_info` never checks the authenticated `state_checkpoint_hash`, allowing a divergent state root to pass replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function that replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, and the chunk executor's replay-verify path) uses to confirm that locally re-executed transaction results match the authenticated `TransactionInfo` that is already committed in the accumulator (and therefore bound to a signed `LedgerInfo`). It checks status, gas used, write-set hash, and event root hash, but it never compares the locally computed state (or hot-state / position-state) checkpoint root against `txn_info.state_checkpoint_hash()` (and the analogous hot/position fields). A `TODO` left directly in the code confirms the comparator "ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution," but the same gap applies to the base `state_checkpoint_hash` field that is used unconditionally today, not only to the not-yet-enabled trading-native fields.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates a `TransactionOutput` against a `TransactionInfo` pulled from an authenticated backup/proof stream. It asserts:
- `status == expected_txn_status`
- `gas_used == txn_info.gas_used()`
- `write_set_hash == txn_info.state_change_hash()`
- `event_root_hash == txn_info.event_root_hash()`

It never reads or compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` against any value computed from local re-execution. This is the exact function used by the primary replay-verify command in [2](#0-1) , which is specifically the "state-integrity" tool: it re-executes transactions read from a backup and is supposed to catch any divergence between local execution and the authenticated ledger, including a wrong state root.

Because the state (Sparse-Merkle / JMT) root hash is the single most sensitive, non-directly-observable commitment in `TransactionInfo` — it is not independently reconstructible from the write set alone the way the write-set hash or event hash are — omitting it from the comparator means a bug in state-checkpoint computation (e.g., in `DoStateCheckpoint`, JMT construction, or the ProvableStateSummary hashing path in [3](#0-2) ) that silently produces the wrong `state_checkpoint_hash` would never be flagged by replay-verify, even though replay-verify's entire purpose is to detect exactly this class of state-commitment corruption.

### Impact Explanation
The state checkpoint hash is what state-proof and state-sync consumers ultimately trust as the root of the account/resource tree at a given version (it flows into the accumulator via `TransactionInfo` and is bound to the signed `LedgerInfo`). If the state-checkpoint hash computation diverges from the correct VM result — through a code bug in checkpoint construction, a JMT/SMT node-key or diffing regression, or (as the code's own TODO calls out) once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/position-state roots are enabled — replay-verify will still report "success" because `ensure_match_transaction_info` silently accepts any state_checkpoint_hash. This defeats the primary safety net (`testsuite/replay-verify`) that mainnet operators rely on to catch state-divergence bugs before/after upgrades, letting a wrong committed state root go undetected across the fleet. This matches the "Committed state that differs from the correct VM result… accepted as valid" and "authenticated API… output bound to the wrong version/proof" impact classes in the state-integrity gate.

### Likelihood Explanation
This is not an externally triggerable exploit by itself; it is a proof-integrity/verification gap that becomes impactful whenever any other component (execution, JMT construction, or future features like `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) produces an incorrect state root. Given that replay-verify is the designated safety net for exactly such divergence bugs, the likelihood of this gap mattering is tied to the likelihood of a state-computation bug elsewhere — which the codebase's own `TODO` comment acknowledges is an anticipated risk for the trading-native feature. The comparator is unconditionally missing this check today regardless of feature flags, so the weakness exists on every replay-verify run, not just when trading-native roots are enabled.

### Recommendation
Extend `ensure_match_transaction_info` to also compare a locally recomputed `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the corresponding fields of the passed-in authenticated `TransactionInfo`, failing verification on mismatch just as it does today for the write-set and event root hashes. This requires threading the locally computed checkpoint hash(es) into the callers (`replay_on_archive.rs`, chunk executor's replay path, `aptos-debugger`, `aptos-move/cli`) alongside `expected_write_set`/`expected_events`, matching what the in-code TODO already recommends before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Proof of Concept
Not independently exploitable as a standalone PoC — it is a missing check. Demonstration path:
1. Introduce (or trigger) any bug that causes the state-checkpoint root computed during local re-execution in `DoStateCheckpoint::run` to differ from the historically committed `state_checkpoint_hash` in the backup's `TransactionInfo` (write set, events, gas, and status all remain correct).
2. Run `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::run`, which calls `execute_and_verify` → `ensure_match_transaction_info` ( [4](#0-3) ).
3. Observe that `ensure_match_transaction_info` ( [1](#0-0) ) returns `Ok(())` and the tool reports no failed transactions, despite the state root being wrong.

**Confidence/uncertainty**: I could not fully trace all call sites (`aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`) due to the final-iteration limit, so I cannot confirm whether any of those callers independently re-validate the state-checkpoint hash through a separate mechanism that would mitigate this gap for their specific workflows. The `replay_on_archive.rs` and `chunk_executor` call sites, however, clearly rely solely on `ensure_match_transaction_info` for this validation.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
