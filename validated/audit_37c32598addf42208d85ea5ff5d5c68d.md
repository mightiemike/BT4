### Title
Deposits are unconditionally removed from `DepositDataMempool` even when their `BridgeDeposit` system transaction fails during real inclusion, permanently losing the Bitcoin-side deposit without minting cBTC - ([File: crates/sequencer/src/runner.rs])

### Summary
`process_sys_txs` (crates/sequencer/src/runner.rs:1617-1706) applies each fetched deposit as an isolated system transaction and silently skips (`continue`) any deposit whose call reverts with `EvmSystemTransactionNotSuccessful`, excluding it from the returned `all_txs`. However, the caller subsequently calls `remove_deposits(&deposit_data)` (crates/sequencer/src/runner.rs:636-643) using the original, unfiltered `deposit_data` list that was fetched from the mempool and fed into `populate_deposit_system_events`, not the actually-applied subset. This means any deposit that fails during real block inclusion — whether due to gas exhaustion, contract-state drift since the `eth_call` admission check, or any other on-chain revert — is deleted from the mempool exactly as if it had succeeded.

### Finding Description
Binding: `cBTC minted by SYSTEM_SIGNER Bridge deposit == deposit removed from DepositDataMempool`. This binding is broken.

Path:
1. Attacker calls `citrea_sendRawDepositTransaction` with an ABI-valid but gas-heavy blob. `send_raw_deposit_transaction` (crates/sequencer/src/rpc.rs:330-388) admits it into the mempool as long as `evm.get_call` succeeds against `BlockId::pending()` — a point-in-time check with no guarantee about the state or accumulated gas at future real inclusion.
2. On block production, `fetch_deposits` returns a batch, which is turned into `SystemEvent::BridgeDeposit` events via `populate_deposit_system_events` (runner.rs:1596) and processed one-by-one in `process_sys_txs` (runner.rs:1617-1706), each with its own fixed `SYSTEM_TX_GAS_LIMIT` (`crates/evm/src/evm/system_events.rs:15`) and own checkpoint.
3. If a deposit's system transaction fails (`StateTransitionError::ModuleCallError(L2BlockModuleCallError::EvmSystemTransactionNotSuccessful)`), the code explicitly reverts the checkpoint and `continue`s (runner.rs:1685-1697), excluding that deposit's RLP tx from `all_txs`. Crucially, `process_sys_txs` returns only `(Vec<RlpEvmTransaction>, WorkingSet)` — it does not report which specific deposits from the batch succeeded or failed.
4. After block production, the caller calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` (runner.rs:636-643) using the same `deposit_data` variable originally fetched/passed in — not filtered by whichever deposits actually landed in `all_txs`. `remove_deposits` (crates/sequencer/src/deposit_data_mempool.rs:79-109) removes every entry in `deposit_data` from `accepted_deposit_txs` unconditionally by `calc_tx_id` match.

The result: a deposit whose Bridge call reverted during real inclusion (never emitting a `Deposit` event, never crediting cBTC) is nonetheless purged from the mempool as though it succeeded, with no retry path. This can be triggered by an attacker submitting a gas-heavy or state-dependent deposit blob in the same fetch batch as a victim's legitimate deposit, or even by naturally-occurring reverts (e.g., a deposit becoming invalid between admission-time `eth_call` and inclusion-time execution due to unrelated Bridge contract state changes in the interim).

Existing guards do not catch this: the admission-time `eth_call` at `BlockId::pending()` (rpc.rs:346-353) cannot predict the exact state/gas context at actual inclusion; `process_sys_txs`'s per-tx checkpoint/revert logic correctly prevents state corruption but throws away the success/failure signal needed by the caller to correctly update the deposit mempool.

### Impact Explanation
A legitimate depositor's Bitcoin funds are moved into Clementine's presigned vault UTXO on the Bitcoin side, but the corresponding cBTC mint on Citrea is dropped from the mempool without being retried, and there is no mechanism to resubmit it (the deposit data can be resubmitted by the depositor via RPC again if they notice, but nothing on-chain records the failure or refunds/relists it automatically). This matches the "funds permanently frozen" Critical impact category since the Bitcoin-side value has moved but the L2 credit vanishes silently. This is repeatable per fetch batch and per L2 block, and any attacker able to submit a deposit blob that reliably reverts during real inclusion (crafted gas cost, or exploiting Bridge-contract state dependent on prior events in the same batch) can target it against a victim deposit sharing the same fetch window.

### Likelihood Explanation
The attacker only needs unauthenticated access to `citrea_sendRawDepositTransaction`, which any unprivileged actor has. Crafting a deposit blob that passes the admission-time `eth_call` but reverts at inclusion time requires knowledge of `SYSTEM_TX_GAS_LIMIT` (fixed, public constant) and some engineering of the `moveTx` vin/vout structure to shift gas cost near the boundary, or simply exploiting any legitimate on-chain revert condition in the Bridge contract that changes between admission and inclusion. No BTC funds need to be spent by the attacker to trigger the mempool removal bug itself (the attacker's own crafted deposit does not need a real Bitcoin transaction to demonstrate the mempool-removal defect, though a full end-to-end proof of lost cBTC would require a real victim deposit).

### Recommendation
Change `process_sys_txs` to return per-deposit success/failure information (e.g., a `Vec<(Deposit, bool)>` or the set of deposits that were actually applied), and have the caller call `remove_deposits` only with the subset that succeeded. Failed deposits should remain in `DepositDataMempool` for retry in a subsequent block, or be explicitly logged/reported so operators can investigate rather than being silently and permanently dropped.

### Proof of Concept
```
cargo test -p citrea-sequencer deposit_removed_on_failed_inclusion -- --nocapture
```
Plan:
1. Construct two `Deposit` blobs: `deposit_ok` (a normal valid deposit) and `deposit_fail` (crafted so that `evm.get_call` at `BlockId::pending()` succeeds during `send_raw_deposit_transaction`, but the Bridge contract call reverts during actual `apply_l2_block_txs` execution in `process_sys_txs`, e.g. by relying on contract state that changes between admission and inclusion, or a gas-boundary condition).
2. Add both via `DepositDataMempool::add_deposit_tx`.
3. Run one simulated block production cycle invoking `apply_system_events` → `process_sys_txs`, asserting `deposit_fail`'s RLP transaction is absent from the returned `all_txs` (confirming it was not applied/no `Deposit` event emitted).
4. Assert that after the block-production path calls `remove_deposits(&deposit_data)` with the original fetched batch, `deposit_fail` is no longer present in `DepositDataMempool::fetch_deposits`, despite never having emitted a `Deposit` log — demonstrating the binding `cBTC minted == deposit removed from mempool` is broken.
