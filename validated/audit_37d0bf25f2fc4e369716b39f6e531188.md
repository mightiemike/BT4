Confirmed: `CallerDeposit` tracks external caller's attached deposit specifically so it can be refunded "if the cross-contract call fails" [1](#0-0) , and `rlp_execute_callback`'s `PromiseResult::Failed` arm does perform that refund [2](#0-1) . However, both `address_check_callback` and `nep_141_storage_balance_callback` have their own `PromiseResult::Failed` arms that return a failure `ExecuteResponse` **without** issuing that same refund [3](#0-2) [4](#0-3) . This is exactly the analog to the Camelot/Uniswap issue: code paths built on an assumed external-contract interface (NEP-141/NEP-145 `storage_balance_of`, or the address-registrar `lookup`) that, when the assumption breaks (call fails because the target isn't behaving as expected), leave user funds unrecovered instead of degrading gracefully like the "happy path" callback does.

### Title
Wallet Contract loses attached caller deposit on ERC-20/registrar pre-flight call failure - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Wallet Contract's ERC-20 transfer emulation and eth-implicit address-check paths make an intermediate cross-contract call (`storage_balance_of` on the token contract, or `lookup` on the address registrar) before performing the user's requested action. Both intermediate callbacks (`nep_141_storage_balance_callback`, `address_check_callback`) refund the external caller's attached NEAR deposit on success paths that route to `rlp_execute_callback`, but neither refunds it when the intermediate call itself fails (`PromiseResult::Failed`), unlike `rlp_execute_callback` which does refund on failure of the final action.

### Finding Description
`CallerDeposit` exists specifically to let the contract "refund the caller's deposit if the cross-contract call fails" [1](#0-0) . It is only populated for external (non-self) callers who attach a nonzero deposit to `rlp_execute` [5](#0-4) , meaning a relayer/caller other than the wallet owner. This deposit accompanies actions such as emulated ERC-20 transfers (`EthEmulationKind::ERC20Transfer`) which build a two-hop promise: `storage_balance_of` → `nep_141_storage_balance_callback` [6](#0-5) , and emulated cross-wallet base-token transfers (`address_check: Some(...)`) which build `lookup` → `address_check_callback` [7](#0-6) .

In the terminal callback, `rlp_execute_callback`, the `PromiseResult::Failed` branch explicitly refunds `caller_deposit` back to the external caller's `account_id` [2](#0-1) . This confirms the intended invariant: whenever a promise chain started by an external caller's deposit ends in failure, that deposit must come back.

But the two intermediate callbacks break this invariant on their own `PromiseResult::Failed` arm:
- `address_check_callback`: if the registrar `lookup` call fails, it returns an error `ExecuteResponse` and drops `caller_deposit` on the floor — it is never passed anywhere for a refund [8](#0-7) .
- `nep_141_storage_balance_callback`: if the token contract's `storage_balance_of` call fails, it likewise returns an error and drops `caller_deposit` [9](#0-8) .

This mirrors the report's root cause pattern: code was written assuming the external contract being probed (a Uniswap-V3-shaped pool / here, a NEP-141-compliant token or the trusted registrar) will behave a certain way, and the failure-handling code path added for the "happy path" contract calls (`rlp_execute_callback`) was not replicated for the newly introduced pre-flight/interface-probe calls. Any token contract that reverts, is paused, does not implement `storage_balance_of` at all, runs out of gas, or otherwise fails that specific call — a very plausible occurrence for arbitrary ERC-20-emulated NEP-141 tokens a relayer might route a user's transaction through — causes the attached deposit to be silently forfeited instead of refunded.

### Impact Explanation
This is a concrete, transaction-triggered loss of funds for an external caller (typically a relayer paying/pre-funding a transfer on behalf of the eth-implicit account, or a caller attaching value for a fee/registrar check). Since the deposit is not tracked or moved elsewhere on this failure branch, and the wallet contract's balance simply absorbs it, the funds become permanently stuck relative to the caller who sent them — a real value-movement bug (unauthorized retention of the caller's NEAR), not merely a UX revert like the original Camelot report. Given the wallet contract is a global contract deployed to control every ETH-implicit account, this affects any relayer/caller who attaches a deposit and whose target ERC-20 token or the address registrar fails that specific intermediate call.

### Likelihood Explanation
Reaching this path requires only a single, ordinary transaction: an external (non-owner) account calling `rlp_execute` on an eth-implicit account's wallet contract with a nonzero attached deposit for an ERC-20-emulated transfer (or a cross-wallet base-token transfer requiring an address-registrar lookup), targeting a token/registrar interaction that fails. Test coverage (`test_caller_refunds`) demonstrates the refund mechanism exists and is expected end-to-end but only exercises the final-call failure path, not the intermediate-callback failure path [10](#0-9) , so a failing `storage_balance_of`/`lookup` call is a realistic, easily triggered scenario (e.g. any non-standard or paused token, or simply targeting an account that isn't a NEP-141 contract).

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, mirror the refund logic used in `rlp_execute_callback`'s `PromiseResult::Failed` arm: when the intermediate call fails, issue `env::promise_batch_create`/`promise_batch_action_transfer` to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the error `ExecuteResponse`.

### Proof of Concept
1. Deploy the Wallet Contract as the global contract for an eth-implicit account `A` (as in `test_wallet_contract_interaction` / `TestContext`) [11](#0-10) .
2. Have an external account `C` (not `A`) call `A.rlp_execute(target, tx_bytes_b64)` with an attached deposit, where the RLP-encoded Ethereum transaction's calldata matches `ERC20_TRANSFER_SELECTOR` and `target` is some account ID that does **not** implement NEP-141's `storage_balance_of` (e.g., a plain contract or non-existent account) [12](#0-11) .
3. `inner_rlp_execute` builds the `storage_balance_of` → `nep_141_storage_balance_callback` promise chain and forwards `caller_deposit` (populated from `C`'s attached deposit since `C != A`) [6](#0-5) .
4. The `storage_balance_of` call fails (method not found / execution error) since `target` is not a NEP-141 contract.
5. `nep_141_storage_balance_callback` hits `PromiseResult::Failed`, returns `success: false` with an error message, and never refunds `caller_deposit` to `C` [9](#0-8) .
6. `C`'s attached deposit remains on the wallet contract's account balance permanently, unlike the symmetric scenario in `test_caller_refunds` where a final-action failure does trigger a refund [13](#0-12) .

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
