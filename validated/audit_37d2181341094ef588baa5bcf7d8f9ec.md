### Title
Front-runnable self-escalation of `Active` permission via `AccountPermissionUpdateContract` re-authorization race - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
An account owner can grant a delegate ("Bob") an `Active` permission whose operations bitmap includes the `AccountPermissionUpdateContract` bit, letting Bob broadcast `AccountPermissionUpdateContract` transactions on the owner's behalf. Because `AccountPermissionUpdateActuator` validates that bit against the broad, governance-controlled `AvailableContractType` whitelist rather than the intentionally-restricted default `ActiveDefaultOperations` set, this self-referential capability is legally grantable. Once granted, Bob can front-run the owner's attempt to revoke him by first adding a colluding key ("Eve") with the same self-update capability; after the owner's revocation lands, Bob uses Eve's key to re-grant himself, exactly mirroring the reported Drips `Caller.authorize()`/`unauthorize()` race.

### Finding Description
`AccountPermissionUpdateActuator.checkPermission()` validates an `Active` permission's `operations` bitmap against `dynamicStore.getAvailableContractType()`: [1](#0-0) 

The default `AVAILABLE_CONTRACT_TYPE` value only excludes `ClearABIContract`/`UpdateBrokerageContract` (id 48/49), so `AccountPermissionUpdateContract` (id 46) *is* included as an "available" operation, as demonstrated by the test that reproduces this exact bitmap: [2](#0-1) 

In contrast, the *default* operations automatically assigned to a freshly created `Active` permission (`getActiveDefaultOperations`) deliberately excludes `AccountPermissionUpdateContract`, as shown by the companion test that explicitly skips that contract type when building the expected bitmap: [3](#0-2) [4](#0-3) 

This divergence shows the protocol designers treat "the ability to rewrite one's own permission structure" as a distinct, sensitive right — but nothing in `checkPermission()`'s validation prevents an owner (voluntarily or unknowingly) from manually constructing a custom `Active` permission with that bit set anyway, since it passes the `AvailableContractType` check.

Signature/permission enforcement for a broadcast transaction only checks that the signer's `Active` permission's operations bitmap contains the bit for the target contract type — it does not forbid `AccountPermissionUpdateContract` specifically: [5](#0-4) [6](#0-5) 

`AccountPermissionUpdateActuator.execute()` then unconditionally overwrites the account's Owner/Witness/Active permission set with whatever the transaction specifies, with no check that the new state preserves the pre-existing keys: [7](#0-6) 

Attack flow (analog of the Drips `authorize()`/`unauthorize()` race):
1. Alice (owner) grants Bob an `Active` key whose `operations` bitmap includes `AccountPermissionUpdateContract`.
2. Alice later decides to revoke Bob and broadcasts an `AccountPermissionUpdateContract` transaction removing Bob's key.
3. Bob sees this pending transaction and front-runs it (higher energy/fee bribery to the block-producing witness) with his own `AccountPermissionUpdateContract` transaction that adds a colluding key Eve to the same `Active` permission, also carrying the `AccountPermissionUpdateContract` bit.
4. Alice's revocation executes, removing Bob.
5. Bob, now controlling Eve's key, broadcasts another `AccountPermissionUpdateContract` transaction (signed via Eve) re-adding himself to the `Active` permission — regaining his authority indefinitely, exactly as in the original report.

### Impact Explanation
An account owner attempting to revoke a misbehaving delegate can be perpetually thwarted by that delegate re-granting itself authority through a planted accomplice key, enabling continued unauthorized fund transfers/voting/etc. on the owner's account. Because `execute()` does not validate that the new Owner permission retains original keys, a delegate with this bit can go further than the original report and directly overwrite the account's Owner permission in a single transaction, resulting in full account/asset takeover rather than mere transient re-authorization.

### Likelihood Explanation
This requires the owner to have granted an `Active` permission that includes the `AccountPermissionUpdateContract` operation bit — which is not the default, but is explicitly permitted by validation (`getAvailableContractType()` includes it) with no additional guardrail or warning distinguishing it from ordinary operations like transfers or voting. Any tooling, multisig setup script, or naive "grant all contract types" convenience flow that copies from `AvailableContractType` instead of `ActiveDefaultOperations` would silently create this exposure. Once created, exploitation only requires the malicious delegate to observe the pending revocation transaction in the mempool and out-bid it, which is standard front-running.

### Recommendation
- In `AccountPermissionUpdateActuator.checkPermission()`, disallow the `AccountPermissionUpdateContract` bit from ever being set in an `Active` permission's `operations`, regardless of `getAvailableContractType()`, mirroring the exclusion already applied to `getActiveDefaultOperations()`.
- Alternatively/additionally, require that `AccountPermissionUpdateContract` transactions can only be signed using `permissionId == 0` (the Owner permission), never an `Active` permission, closing the self-referential escalation path entirely.
- Consider validating in `execute()`/`validate()` that a new Owner permission is not silently replaced without meeting a distinct, stricter threshold, to prevent single-transaction takeover even if an `Active` key is ever granted this capability.

### Proof of Concept
1. Owner creates account with an `Active` permission whose `operations` byte array sets bit 46 (`AccountPermissionUpdateContract`) alongside normal bits — this passes `AccountPermissionUpdateActuator.checkPermission()` because bit 46 is part of `getAvailableContractType()` (see `checkAvailableContractTypeCorrespondingToCode` test at lines 919-948) and is added as a key belonging to "Bob".
2. Bob signs and broadcasts an `AccountPermissionUpdateContract` transaction using `permission_id` referencing that `Active` permission, adding "Eve" as an additional key with the same `AccountPermissionUpdateContract` bit — accepted per `TransactionCapsule.checkPermission`/`checkPermissionOperations` (lines 635-645, 468-496).
3. Owner broadcasts an `AccountPermissionUpdateContract` transaction (signed with Owner permission) removing Bob's key.
4. Whichever transaction lands first in the block is irrelevant to the outcome as long as Bob's addition of Eve is not itself removed; after Owner's revoke executes, Bob signs a new `AccountPermissionUpdateContract` transaction via Eve's key, re-adding his own key to the `Active` permission — `AccountPermissionUpdateActuator.execute()` (lines 41-52) applies this unconditionally, restoring Bob's authority.
