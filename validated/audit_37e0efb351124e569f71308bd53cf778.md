### Title
`queryDelegatableResource` TVM precompile can report a max-delegatable size larger than what `DelegateResourceContract` actually accepts, breaking on-chain integrations - (File: `actuator/src/main/java/org/tron/core/vm/utils/FreezeV2Util.java`)

### Summary
The external report describes PoolTogether's `Vault.maxDeposit`/`maxMint` returning an upper bound that is not actually constrained by the real acceptance limit of the wrapped ERC4626 vault, so callers relying on the "max" value can have their subsequent `deposit`/`mint` calls revert. java-tron has a directly analogous pattern in its Freeze v2 TVM precompile: `FreezeV2Util.queryDelegatableResource` [1](#0-0)  is exposed to any smart contract via `PrecompiledContracts.java` as the advertised "maximum bandwidth/energy an account can delegate", but it computes remaining usage with a different formula than the one actually enforced by `DelegateResourceActuator`/`DelegateResourceProcessor` when the delegation is executed.

### Finding Description
`queryDelegatableResource` computes the delegatable amount as `frozenV2Resource - v2NetUsage`, where the usage is obtained via `Repository.getAccountNetUsageBalanceAndRestoreSeconds` [2](#0-1) , which recovers usage with the pure-function `recover()` and converts it to a TRX-balance figure with `usageToBalance()`: [3](#0-2) 

In contrast, the actuator/precompile-execution path that actually performs the delegation (`DelegateResourceActuator.doValidate` and its TVM twin `DelegateResourceProcessor.validate`) computes the equivalent quantity differently: it calls `BandwidthProcessor.updateUsageForDelegated()` (which persists/re-derives `netUsage` via the stateful `increase()`/window-resize logic in `ResourceProcessor`) and then converts that usage to a balance inline with its own arithmetic ordering: [4](#0-3) [5](#0-4) 

The two code paths differ in: (1) which recovery function is used (`recover()`/read-only vs `increase()`/`updateUsageForDelegated()` which can change window sizing state per `ResourceProcessor.increase`) [6](#0-5) , and (2) the exact multiply/divide order and rounding when converting bandwidth "usage" into TRX-balance units (`usageToBalance` vs the actuator's inline `netUsage * TRX_PRECISION * (weight/limit)` expression). Because these are two independently maintained, non-identical numeric formulas computing the conceptually same "how much can I still delegate" value, they are not guaranteed to agree bit-for-bit — the precompile's advertised maximum is not provably bounded by (and can exceed) the real maximum enforced by the validate() path that will actually execute the delegation.

### Impact Explanation
`queryDelegatableResource` is a public, unprivileged-callable TVM precompile intended for on-chain contracts (staking automation, DeFi resource-delegation aggregators, wallets) to determine how much bandwidth/energy an account can safely delegate before calling `delegateResource`. If the query overstates the real limit relative to `DelegateResourceActuator`/`DelegateResourceProcessor.validate`, any contract or transaction that delegates the full amount reported by the query will have its `ContractValidateException` ("delegateBalance must be less than or equal to available FreezeBandwidthV2/EnergyV2 balance") thrown at execution, wasting the caller's energy/fee and breaking automated integrations built on top of the query — the same class of impact (integration breakage due to an unconstrained/incorrect "max" oracle) described in the source report, and a concrete on-chain settlement/invalid-state divergence between an advertised limit and an enforced limit.

### Likelihood Explanation
The divergence is deterministic and depends only on chain configuration flags (`allowHardenResourceCalculation`, `supportUnfreezeDelay`, `disableJavaLangMath`, `hardenResourceCalculation`) and account state (concurrent usage/window-size drift between the two code paths), not on any privileged action — any unprivileged account/contract with frozen-for-bandwidth/energy V2 balance and non-zero usage can trigger a scenario where `queryDelegatableResource` and the actuator's real limit diverge, since the two implementations are separately maintained duplicate formulas rather than sharing a single source of truth.

### Recommendation
Make `queryDelegatableResource` call the exact same usage-recovery and balance-conversion logic used by `DelegateResourceActuator`/`DelegateResourceProcessor` (e.g., extract a single shared helper for "available frozen-V2 balance for delegation" and have both the precompile query and the actuator/processor call it), so the reported maximum can never exceed what a subsequent `delegateResource` call will actually accept.

### Proof of Concept
Not independently reproduced in this analysis — the divergence is demonstrated analytically from the two independent implementations:
- Query path: `FreezeV2Util.queryDelegatableResource` → `Repository.getAccountNetUsageBalanceAndRestoreSeconds` → `usageToBalance` [1](#0-0) 
- Enforcement path: `DelegateResourceActuator.doValidate` / `DelegateResourceProcessor.validate` → `BandwidthProcessor.updateUsageForDelegated` → inline balance formula [4](#0-3) 

A definitive PoC would require constructing an account/state combination (e.g., a specific `windowSize`/`newWindowSize` mismatch produced by `supportUnfreezeDelay` window-resizing in `ResourceProcessor.increase`) and computing both formulas to show a numeric mismatch; this was not executed against a live node/test harness in this analysis, so the exact magnitude of divergence is unverified and should be validated with unit tests comparing both code paths under matching account states.

  public Pair<Long, Long> getAccountNetUsageBalanceAndRestoreSeconds(AccountCapsule accountCapsule) {
    long now = getHeadSlot();

    long netUsage = accountCapsule.getNetUsage();
    long latestConsumeTime = accountCapsule.getLatestConsumeTime();
    long accountWindowSize = accountCapsule.getWindowSize(Common.ResourceCode.BANDWIDTH);

    if (now >= latestConsumeTime + accountWindowSize) {
      return Pair.of(0L, 0L);
    }

    long restoreSlots = latestConsumeTime + accountWindowSize - now;

    long newNetUsage = recover(netUsage, latestConsumeTime, now, accountWindowSize);

    long totalNetLimit = getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = getTotalNetWeight();

    long balance = usageToBalance(newNetUsage, totalNetWeight, totalNetLimit);

    return Pair.of(balance, restoreSlots * BLOCK_PRODUCED_INTERVAL / 1_000);
  }

  private long usageToBalance(long usage, long totalWeight, long totalLimit) {
    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(usage)
          .multiply(BigInteger.valueOf(totalWeight))
          .multiply(BigInteger.valueOf(TRX_PRECISION))
          .divide(BigInteger.valueOf(totalLimit))
          .longValueExact();
    }
    return (long) ((double) usage * totalWeight / totalLimit * TRX_PRECISION);
  }

    long averageLastUsage;
    long averageUsage;
    if (hardenCalculation()) {
      BigInteger biPrecision = BigInteger.valueOf(precision);
      BigInteger biWindowSize = BigInteger.valueOf(windowSize);
      averageLastUsage = divideCeilExact(
          BigInteger.valueOf(lastUsage).multiply(biPrecision), biWindowSize);
      averageUsage = divideCeilExact(
          BigInteger.valueOf(usage).multiply(biPrecision), biWindowSize);
    } else {
      averageLastUsage = divideCeil(lastUsage * precision, windowSize);
      averageUsage = divideCeil(usage * precision, windowSize);
    }

    if (lastTime != now) {
      assert now > lastTime;
      if (lastTime + windowSize > now) {
        long delta = now - lastTime;
        double decay = (windowSize - delta) / (double) windowSize;
        averageLastUsage = round(averageLastUsage * decay,
            this.disableJavaLangMath());
      } else {
        averageLastUsage = 0;
      }
    }
    averageLastUsage += averageUsage;
    return getUsage(averageLastUsage, windowSize);
  }
