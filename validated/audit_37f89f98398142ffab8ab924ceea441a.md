### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by the HMAC signature, allowing cross-tenant admin session confusion via webhook replay - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The GitLab report's root cause was that a value trusted to route a request into a privileged execution context (the Redis queue command) was not protected by the same integrity check as the rest of the payload, letting an attacker who could inject unsanitized data control routing/behaviour outside the validated channel. The same *class* of bug — trusting an unsigned "routing" value while only the body/payload is integrity-checked — exists in the webhook authentication path of `shopify-app-js`: the shop-identifying header used to select which shop's offline access token/session to use is never covered by the webhook HMAC.

### Finding Description
`validateHmacFromRequestFactory` in [1](#0-0)  computes and checks the HMAC over `rawBody` only, using the header named by `hmacHeaderName`. No other header — including the shop-identifying `X-Shopify-Shop-Domain` (or the events equivalent) — is included in the signed data.

`checkWebhooksHeaders`/`checkEventsHeaders` in [2](#0-1)  only requires the `domain` header to be *present*; it never verifies that `domain` corresponds to whatever shop actually produced the signed body. The webhook is considered `valid: true` as long as the HMAC-over-body check succeeds, regardless of what the `domain` header says.

`authenticateWebhookFactory` in `shopify-app-remix`/`shopify-app-react-router` then uses this **unsigned** value directly to select which shop's offline session/access token to attach to the request: [3](#0-2)  calls `ensureValidOfflineSession(params, check.domain)`, which loads/creates the offline session for that (attacker-controlled) shop string via [4](#0-3) , and then builds an authenticated `admin` client bound to that session's access token for the handler to use.

Because a merchant who has legitimately installed the app can freely obtain valid `(rawBody, hmac)` pairs for their **own** shop (every webhook Shopify sends them is HMAC'd with the app's shared client secret, not a per-shop secret), that merchant can replay one of their own legitimately-signed webhook deliveries to the app's webhook endpoint while substituting a different shop's domain in the unsigned `X-Shopify-Shop-Domain` header. The HMAC check still passes (it never looked at the header), `check.domain` becomes the victim shop, and the webhook handler executes with the **victim's** offline session/admin client while processing the **attacker's** payload content — a confused-deputy / cross-tenant session misuse.

### Impact Explanation
An unprivileged, low-cost actor (any merchant who can install the app on their own store and thus receive real webhooks) can cause the app to invoke its webhook business logic using another (victim) shop's offline access token, while supplying attacker-chosen payload content. Depending on what the app's webhook handlers do with `admin`/`session` (e.g., write to Shopify resources, trigger side effects, update stored data keyed by shop), this can lead to cross-tenant data corruption, unauthorized actions taken against a victim shop's store via that shop's real access token, or information disclosure if handler responses/logs echo victim-shop resources back to the attacker-controlled flow.

### Likelihood Explanation
Moderate-to-high: exploitation only requires the attacker to install the target app on any shop they control (a normal, unprivileged action), capture one legitimate webhook delivery to their own endpoint (or simply record the `rawBody` + valid HMAC pair, since replays are same-body/same-hmac), and re-POST it to the app's webhook endpoint with a modified `X-Shopify-Shop-Domain` (or `shopify-events-domain`) header pointing at a known/target shop. No secret, credential leak, or MITM is required — only knowledge of another installed shop's domain (often guessable/public, e.g. `victim.myshopify.com`).

### Recommendation
Bind the shop domain (and other routing-relevant headers such as topic/webhook id) into the value that is actually HMAC-verified, or independently cross-check that the shop identified by `check.domain` matches a shop for which this exact `(rawBody, hmac)` pair could only have been produced (e.g., by additionally validating against Shopify's webhook-specific verification APIs that scope by shop, or by deriving the shop from data embedded/verified inside the signed payload rather than an unsigned header). At minimum, document and enforce that `authenticateWebhookFactory` must not trust `check.domain` for session/token selection without further authorization, and consider rejecting mismatches where the same `(rawBody, hmac)` was already seen for a different shop within a validity window (replay detection).

### Proof of Concept
1. Install the target app (using `shopify-app-remix`/`shopify-app-react-router`) on attacker-owned shop `attacker.myshopify.com`; Shopify sends a real webhook `POST /webhooks` with body `B`, `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` using the app's shared secret), and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture `(B, H)`.
3. Replay: `POST /webhooks` with the same body `B`, same `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `webhooks.validate` in [5](#0-4)  returns `valid: true` because only `B`/`H` are checked; `domain` is taken verbatim from the forged header.
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, "victim.myshopify.com")`, loading `victim`'s offline session/access token and invoking the registered webhook handler with `session`/`admin` scoped to the victim shop, processing attacker-supplied body `B`.

function getRequiredHeader(
  headers: Headers,
  headerName: string,
  missingHeaders: string[],
): string | undefined {
  const value = getHeader(headers, headerName);
  if (!value) {
    missingHeaders.push(headerName);
  }
  return value;
}

import {BasicParams} from '../types';

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
