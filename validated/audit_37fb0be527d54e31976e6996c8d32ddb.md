### Title
LDAP Bind DN constructed with RFC4515 filter-escaping instead of RFC4514 DN-escaping enables DN injection, combined with unchecked empty password allowing potential unauthenticated-bind auth bypass - (File: core/sessions/ldapauth/ldap.go)

### Summary
`ldapAuthenticator.CreateSession` and `TestPassword` build the LDAP **Bind DN** using `ldap.EscapeFilter`, which only escapes RFC 4515 search-filter metacharacters (`*`, `(`, `)`, `\`, NUL) and does **not** escape RFC 4514 DN metacharacters such as comma, `+`, quotes, `<`, `>`, `;`. Because a raw comma in `sr.Email` is a DN component separator, an attacker can inject additional RDN components into the constructed Bind DN. This is compounded by the fact that `sr.Password` is never checked for emptiness before `conn.Bind` is called, which under RFC 4513 can trigger an "unauthenticated bind" on servers that accept empty-password binds as success.

### Finding Description
In `CreateSession` (`core/sessions/ldapauth/ldap.go:406-408`):
```go
escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
``` [1](#0-0) 
`ldap.EscapeFilter` is designed for RFC 4515 search-filter contexts, not RFC 4514 distinguished-name construction, yet the resulting `searchBaseDN` here is used directly as the Bind DN (identity being authenticated as), not as a filter. The same mismatch exists in `TestPassword`: [2](#0-1) 

Because commas are unescaped, `sr.Email` such as `admin-uid,ou=SomeNestedOU` produces a Bind DN of `uid=admin-uid,ou=SomeNestedOU,<UsersDN>,<BaseDN>` — a different, attacker-influenced DN path rather than the literal requested identity's own DN. The reachable target set is still restricted to descendants of the fixed, non-attacker-controlled suffix (`UsersDN`, `BaseDN`), since that suffix is appended after the injected value; it is not possible to redirect the Bind DN to an arbitrary, unrelated branch of the directory.

Separately, `sr.Password` is passed straight to `conn.Bind` with no check that it is non-empty: [3](#0-2) 
The unauthenticated-caller entry point is `SessionsController.Create`, which JSON-binds `sr` and forwards it unchecked to `CreateSession`: [4](#0-3) 
No validation rejects an empty `sr.Password`. Per RFC 4513 §5.1.2, a bind with a non-empty DN and a zero-length password is defined as an "unauthenticated bind," and depending on server configuration this can return a success result without validating any secret. Combined with the DN-injection primitive above, this raises the possibility of a crafted DN plus empty password producing a Bind "success" for a target identity without possessing valid credentials.

After a Bind "success," the code calls `l.FindUser(ctx, escapedEmail)` (line 416) — reusing the same filter-escaped, comma-containing string — to look up group membership for role assignment, so a successfully redirected bind could, in principle, propagate into an elevated role assignment.

### Impact Explanation
If the target LDAP server accepts unauthenticated (empty-password) binds as successful, and the injected DN happens to resolve to an existing higher-privileged account nested under the configured Users container, an attacker could obtain a valid Chainlink session without knowing the target's password, potentially assuming an elevated role (up to Admin) and thereby full node control (blockchain keys, job/workflow management). This matches the "LDAP authentication bypass / privilege escalation" impact category.

### Likelihood Explanation
Exploitability is conditional and not a guaranteed universal bypass:
- Requires `WebServer.AuthenticationMethod=ldap` (given as precondition).
- Requires the target LDAP server to actually accept empty-password/unauthenticated binds as success — this is server/config dependent, not solely a Chainlink code defect, though the application should defensively reject empty passwords regardless.
- The attacker cannot redirect the Bind DN to an arbitrary branch of the directory; they can only inject additional RDN components in front of the fixed `UsersDN`/`BaseDN` suffix, so a real, walkable nested-OU/object structure matching the injected path must exist under that container for the DN to resolve to a genuine higher-privileged entry.
- No repo-visible check currently blocks either the comma-based DN injection or the empty-password bind, so the code-level weaknesses themselves are real and directly verifiable in `core/sessions/ldapauth/ldap.go`.

### Recommendation
1. In `CreateSession` and `TestPassword`, reject empty (or whitespace-only) `sr.Password` before calling `conn.Bind`, since an empty password should never be treated as a valid credential.
2. Replace `ldap.EscapeFilter` with proper RFC 4514 DN-value escaping (escape `,`, `+`, `"`, `\`, `<`, `>`, `;`, leading `#`/space, trailing space) when constructing `searchBaseDN`/Bind DN values — filter-escaping must be reserved only for filter construction (as already correctly done in `FindUser`/`validateUsersActive`).
3. After building the Bind DN, validate that it does not contain an unexpected number of RDN components (i.e., verify the DN parses to exactly the expected `BaseUserAttr=value` RDN prepended to the fixed `UsersDN,BaseDN` suffix) before calling `conn.Bind`.

### Proof of Concept
Unit test plan for `core/sessions/ldapauth`:
1. Mock `LDAPClient`/`LDAPConn` to capture the DN string passed to `Bind`.
2. Call `CreateSession(ctx, sessions.SessionRequest{Email: "victim,ou=Admins", Password: ""})`.
3. Assert that the captured Bind DN equals `"uid=victim,ou=Admins,<UsersDN>,<BaseDN>"` (proving comma injection alters DN structure) rather than being rejected/escaped.
4. Assert that `conn.Bind` is invoked with an empty password string, confirming no guard exists to prevent unauthenticated-bind attempts.
5. Fuzz `sr.Email` with LDAP/DN metacharacter payloads (`,`, `+`, `"`, `\`, `<`, `>`) and assert the resulting `searchBaseDN` always contains exactly one RDN component derived from the input (i.e., the fix must make injected metacharacters part of the escaped value, not structural DN separators).

func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()

		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials

	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}
