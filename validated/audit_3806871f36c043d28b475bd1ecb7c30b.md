### Title
Missing slippage protection in `ExchangeInjectActuator` / `ExchangeWithdrawActuator` enables sandwich attacks on TRC10 Bancor-style exchange liquidity operations - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
java-tron's built-in Bancor-style TRC10 exchange (`ExchangeInjectContract` / `ExchangeWithdrawContract`) computes the paired-token amount required/returned purely from the current on-chain pool ratio at execution time, with no user-supplied minimum/maximum bound. This is the exact analog of the reported `PositionManager` issue: deposits/withdrawals that mint or redeem a pool-derived amount without a `minAmountOut`-style guard are sandwichable.

### Finding Description
`ExchangeInjectActuator.execute()` reads the current `firstTokenBalance`/`secondTokenBalance` from the `ExchangeCapsule` and derives `anotherTokenQuant` proportionally to the live ratio: [1](#0-0) 

The same pattern (deriving `anotherTokenQuant` from the live pool ratio at execution time) exists in `ExchangeWithdrawActuator.execute()`: [2](#0-1) 

The protobuf definitions confirm neither contract carries any bound on the resulting counter-token amount — only `owner_address`, `exchange_id`, `token_id`, and `quant` are present: [3](#0-2) 

By contrast, the trading path `ExchangeTransactionContract` explicitly carries an `expected` field, and `ExchangeTransactionActuator.doValidate()` enforces it (`anotherTokenQuant < tokenExpected` reverts): [4](#0-3) [5](#0-4) 

This asymmetry means the "swap" path is slippage-protected while the "inject liquidity" (deposit-analog) and "withdraw liquidity" (withdraw-analog) paths are not. An attacker who observes a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction in the mempool can:
1. Front-run it with their own `ExchangeTransactionContract` swap to skew `firstTokenBalance`/`secondTokenBalance` (the Bancor-relay ratio),
2. Let the victim's inject/withdraw execute at the manipulated ratio, causing the victim to pay more of the paired token per unit injected (or receive less of the paired token per unit withdrawn) than intended,
3. Back-run with a reverse swap to restore the ratio and pocket the difference, extracting value from the victim with no bound the victim could have set to prevent it.

### Impact Explanation
Victims lose value proportional to pool depth and attacker capital — this is a direct, capital-extraction accounting impact on any TRC10 exchange pool participant performing inject/withdraw operations, matching the "underpriced-public-work"/settlement manipulation impact class. Since exchange pools are attacker-creatable (any user can create an `ExchangeCreateContract` and any unprivileged user can inject/withdraw), this is reachable by any user, not a trusted role.

### Likelihood Explanation
Likelihood is Medium: it requires an attacker to monitor the mempool for pending inject/withdraw transactions and possess enough capital to move the pool ratio meaningfully within the same block window (front-run + back-run), which is standard, well-documented MEV/sandwich tooling on account-model chains like TRON.

### Recommendation
Add an explicit min/max bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring the `expected` field already present on `ExchangeTransactionContract`), and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`'s `doValidate()`/`execute()` — e.g., reject the transaction if the computed `anotherTokenQuant` exceeds a caller-specified maximum (for inject) or falls below a caller-specified minimum (for withdraw), analogous to the existing `tokenExpected` check in `ExchangeTransactionActuator`.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from victim for exchange pool `(A, B)` injecting `X` of token `A`.
2. Attacker submits an `ExchangeTransactionContract` selling a large amount of `A` for `B` (or vice versa) to shift `firstTokenBalance`/`secondTokenBalance`, exploiting the ratio computation in `ExchangeCapsule.transaction()`: [6](#0-5) 
3. Victim's inject executes, computing `anotherTokenQuant` off the now-skewed `secondTokenBalance`/`firstTokenBalance` ratio in `ExchangeInjectActuator.execute()` — victim is forced to contribute more of token `B` than at the pre-attack ratio, since there is no user-supplied bound to reject an unfavorable ratio.
4. Attacker submits a reverse `ExchangeTransactionContract` to restore the ratio and realize profit from the ratio round-trip, since `ExchangeTransactionActuator` allows this (the swap path itself is correctly slippage-protected for the attacker's own transaction via `expected`, but nothing protects the victim's inject/withdraw).

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
