### Title
Front-runnable global VRF-key uniqueness check lets any unprivileged party block a miner's leader-key registration - (File: `stackslib/src/chainstate/burn/operations/leader_key_register.rs`)

### Summary
`LeaderKeyRegisterOp::check()` enforces VRF-public-key uniqueness globally across a fork, keyed **only** by the raw public-key bytes and with no binding to the sender/miner who registered it. Because the raw VRF public key is broadcast in the clear inside the Bitcoin transaction's `OP_RETURN` payload before it confirms, any unprivileged third party can copy those bytes verbatim and get a competing `LeaderKeyRegisterOp` mined first (or at a lower `vtxindex` in the same burn block). The victim's own, byte-identical registration is then rejected as a duplicate, exactly mirroring the Fraxlend `_deployFirst` salt-squatting pattern where a shared, attacker-copyable identifier is used to permanently block the honest party's operation.

### Finding Description
`LeaderKeyRegisterOp::check()` rejects a leader-key registration solely because the VRF public key bytes were seen before on the fork: [1](#0-0) 

The uniqueness check is a pure MARF lookup on the public-key bytes, with no relation to `apparent_sender`, `consensus_hash`, or any other identity/ownership binding: [2](#0-1) 

The index entry that makes a key "already used" is written for every `LeaderKeyRegisterOp` processed in a block, again keyed only by the raw key bytes: [3](#0-2) 

Within a single burn block, an additional pre-filter keeps only the first (lowest-`vtxindex`) occurrence of a given VRF public key and silently drops every later occurrence — again with no sender check: [4](#0-3) 

Because `LeaderKeyRegisterOp` is a plain Bitcoin transaction, the VRF public key it commits to is visible in the Bitcoin mempool (or even just observable once broadcast) before it is mined. This is the direct analog of the Fraxlend `deployedPairsBySalt`/`deployedPairsByName` bug: a globally-unique identifier that the honest party must reveal in the clear, and that any unprivileged attacker can copy byte-for-byte and race to claim first, permanently barring the honest party's identical registration on that fork (`op_error::LeaderKeyAlreadyRegistered`).

Before-state: miner A has broadcast (but not yet confirmed) a `LeaderKeyRegisterOp` committing VRF public key `K`.
After-state: attacker B, an unprivileged party with no stake, weight, or special role, copies `K` verbatim into their own `LeaderKeyRegisterOp` and gets it mined first (higher fee / RBF, or same block with lower `vtxindex`). `has_VRF_public_key(K)` now returns `true` when A's transaction is processed, so `check()` returns `LeaderKeyAlreadyRegistered` and A's registration is dropped from the accepted-ops set.

### Impact Explanation
This is a minority-triggerable (in fact zero-weight-required) attack on the leader-key registration step of sortition: any single unprivileged party can unilaterally deny a specific miner's chosen VRF key from ever being validly registered on a fork, forcing that miner to generate a fresh keypair and wait out the maturity window before they can again attempt block commits. This matches the High-severity bucket for "a minority-triggerable sortition/VRF ... divergence": it lets an attacker who controls none of the burn weight and needs no majority manipulate which VRF keys are eligible to participate in sortition, targeting a specific competitor. All nodes apply the rule deterministically and agree on the outcome, so this does not itself split the chain or misappropriate STX rewards, but it directly corrupts the intended one-miner-per-key sortition-eligibility invariant that VRF key registration is supposed to guarantee, at zero cost/risk to the attacker (a small BTC fee) and with no privileged position required.

### Likelihood Explanation
The precondition is only that the attacker observe another party's pending `LeaderKeyRegisterOp` in the Bitcoin mempool (or otherwise learn the VRF public key before confirmation) and get a copy of it mined at an equal or earlier position. This requires no stake, no signer weight, no majority, and no access to any private key — it is a standard front-running race achievable by any Bitcoin user, directly analogous to the Fraxlend `_name="public"` salt-squatting front-run described in the external report.

### Recommendation
Bind VRF-key uniqueness (and/or the `filter_block_VRF_dups` tie-break) to the registering `apparent_sender`/consensus-hash identity rather than to the bare public-key bytes alone, or require the registration to commit to a value derived from sender-specific data (e.g., hash the VRF public key together with the sender's address) so that copying the raw public key bytes from someone else's pending transaction cannot collide with, or pre-empt, their registration.

### Proof of Concept
1. Miner A generates VRF keypair `(sk, K)` and broadcasts `LeaderKeyRegisterOp_A` committing `K` to the Bitcoin network; the transaction is visible, unconfirmed, in the mempool.
2. Attacker B (no stake, no signer weight) observes the raw payload of `LeaderKeyRegisterOp_A`, extracts `K` per the wire format documented in [5](#0-4) 
and crafts `LeaderKeyRegisterOp_B` committing the identical `K`, with a higher fee (or via RBF) so it confirms first, or in the same burn block at a lower `vtxindex`.
3. When the burn block is processed, `filter_block_VRF_dups` (same-block case) or `LeaderKeyRegisterOp::check()` -> `has_VRF_public_key` (cross-block case) causes `LeaderKeyRegisterOp_A` to be rejected/dropped with `op_error::LeaderKeyAlreadyRegistered`, exactly as exercised by the existing unit test: [6](#0-5) 
4. Miner A's key `K` never becomes a validly registered leader key on this fork; any future block commit A intends to build referencing `K` fails to resolve a leader key at that `(block_height, vtxindex)`, forcing A to generate a new VRF keypair and re-register, losing mining opportunity for that window — all triggered unilaterally by an unprivileged, zero-weight attacker.

impl StacksMessageCodec for LeaderKeyRegisterOp {
    /*
        Wire format:

        0      2  3              23                       55                      75        80
        |------|--|---------------|-----------------------|-----------------------|---------|
         magic  op consensus hash   proving public key      block-signing hash160    memo
                   (ignored)                                                       (ignored)

         Note that `data` is missing the first 3 bytes -- the magic and op have been stripped.
         `block-signing hash160` is new to Nakamoto, and is contained within the first 20 bytes of `memo`
    */
    fn consensus_serialize<W: Write>(&self, fd: &mut W) -> Result<(), codec_error> {
        write_next(fd, &(Opcodes::LeaderKeyRegister as u8))?;
        write_next(fd, &self.consensus_hash)?;
        fd.write_all(&self.public_key.as_bytes()[..])
            .map_err(codec_error::WriteError)?;
        let memo = match self.memo.len() {
            l if l <= 25 => self.memo.get(0..),
            _ => self.memo.get(0..25),
        }
        .expect("FATAL: improper memo serialization");
        fd.write_all(&memo).map_err(codec_error::WriteError)?;
        Ok(())
    }

    /// Verify that there are no duplicate VRF keys registered.
    /// If a key was registered more than once, take the first one and drop the rest.
    /// checked_ops must be sorted by vtxindex
    /// Returns the filtered list of blockstack ops
    pub fn filter_block_VRF_dups(
        mut checked_ops: Vec<BlockstackOperationType>,
    ) -> Vec<BlockstackOperationType> {
        debug!("Check Blockstack transactions: reject duplicate VRF keys");
        assert!(Burnchain::ops_are_sorted(&checked_ops));

        let mut all_keys: HashSet<VRFPublicKey> = HashSet::new();
        checked_ops.retain(|op| {
            if let BlockstackOperationType::LeaderKeyRegister(data) = op {
                if all_keys.contains(&data.public_key) {
                    // duplicate
                    warn!(
                        "REJECTED({}) leader key register {} at {},{}: Duplicate VRF key",
                        data.block_height, &data.txid, data.block_height, data.vtxindex;
                        "consensus_hash" => %data.consensus_hash
                    );
                    false
                } else {
                    // first case
                    all_keys.insert(data.public_key.clone());
                    true
                }
            } else {
                // preserve
                true
            }
        });

        checked_ops
    }
