### Title
CPU-heavy Sapling proof verification (`checkProof`) executes in `ShieldedTransferActuator.validate()` with no signature/fee cost for pure shielded (z2z) transactions, enabling cheap CPU-exhaustion DoS - (`actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
For a shielded-to-shielded `ShieldedTransferContract` (no `transparentFromAddress`), `TransactionCapsule.validateSignature` requires **zero** ECDSA signatures and performs no account/balance checks, so an attacker can broadcast an unbounded stream of syntactically valid but cryptographically bogus shielded transactions at near-zero cost. Each is routed through `Manager.processTransaction` into `ShieldedTransferActuator.validate()`, which invokes the CPU-expensive native `JLibrustzcash.librustzcashSaplingCheckSpend/CheckOutput/FinalCheck` calls before any `shieldedTransactionFee` is actually deducted (fee deduction happens only in `execute()`, which never runs when `validate()` throws).

### Finding Description
`ShieldedTransferActuator.validate()` computes `fee = calcFee(...)` but only uses it as a value for later balance-delta arithmetic; the fee is never actually charged in `validate()` [1](#0-0) . After cheap structural checks (`checkSender`, `checkReceiver`, nullifier/anchor checks limited to ≤1 spend and ≤2 receives per protocol limits [2](#0-1) ), `validate()` calls `checkProof()`, which runs the full native Groth16/Sapling verification pipeline for every spend and receive description and a final binding-signature check [3](#0-2) . Only on success is `fee` actually deducted, inside `execute()` [4](#0-3) , which is never reached for invalid proofs.

Critically, `TransactionCapsule.validateSignature` special-cases `ShieldedTransferContract`: if there is no transparent-from address (i.e., a pure shielded z2z transfer), the method requires the signature list to be **empty** and returns `true` immediately — no cryptographic signature check, no account lookup, no balance/permission check at all [5](#0-4) . This means an anonymous attacker with no funded account and no keys can construct an unlimited number of such transactions, fill the spend/output descriptions with syntactically valid-but-bogus (e.g., zeroed or random) zk-SNARK proof bytes, and pass `validateSignature` trivially in `Manager.pushTransaction` before entering `processTransaction` and reaching the CPU-heavy `checkProof` [6](#0-5) [7](#0-6) .

Because `validate()` (and therefore `checkProof`) executes before `execute()`/fee deduction, and because no fee or resource cost is incurred for a rejected (invalid-proof) transaction beyond whatever `consumeBandwidth` charges for raw transaction bytes, the attacker pays only for transaction bandwidth points/bytes — not for the disproportionately expensive native cryptographic verification work performed in `checkProof`. This breaks the metering-faithfulness invariant: CPU cost is not bounded by a fee proportional to the attacker's chosen invalid-proof volume.

I was not able to fully confirm from the retrieved code how `BandwidthProcessor.consume()` handles the zero-length owner-address case for pure shield transactions (i.e., whether free-bandwidth-pool consumption applies with no per-account debit, making the attack even cheaper) — this should be verified directly in `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`.

### Impact Explanation
This is a DoS via the TRON protocol implementation / RPC-API: attackers can flood `broadcastTransaction` (and consequently the transaction relay/mempool and block-packing paths) with cheap, deliberately-invalid shielded transactions that each force multiple native Sapling proof verifications (up to 1 `CheckSpend` + 2 `CheckOutput` + 1 `FinalCheck` per tx). Because verification runs inside the synchronized/locked section of `pushTransaction` (`transactionLock`/`synchronized(this)`) [8](#0-7) , this can serialize and stall processing of other pending transactions (transfers, votes, unfreeze, proposals) sharing the same lock, degrading node availability for legitimate users.

### Likelihood Explanation
- Preconditions: public RPC node with shielded transactions enabled (`supportShieldedTransaction`), which is a normal/default-enabled feature on public full nodes serving shielded transfers.
- Attacker capability: fully unprivileged — no account, no funds, no keys required, since pure z2z transactions need zero signatures.
- Cost: essentially the bandwidth-byte cost of building/sending each transaction (a few hundred bytes each), no shielded-transaction fee is ever actually charged for a failing proof.
- Repeatability: trivially scriptable, unlimited transaction generation (only anchors/nullifier uniqueness need be locally consistent to pass earlier structural checks, no need to correspond to a real note).

### Recommendation
- Charge (or pre-reserve) the `shieldedTransactionFee`/`shieldedTransactionCreateAccountFee` before performing the expensive `checkProof` native calls, or require a minimum bond/fee-bearing bandwidth cost proportional to the number of Spend/Receive descriptions prior to invoking `librustzcashSaplingCheckSpend/CheckOutput/FinalCheck`.
- Apply a lightweight structural/format pre-check and a per-IP/per-connection rate limiter (e.g., extend `RateLimiterInterceptor`/`RateLimiterServlet` or add a dedicated limiter) specifically for `ShieldedTransferContract` broadcasts, independent of the general RPC rate limiter.
- Consider requiring a minimal signature or proof-of-funds mechanism even for pure shielded transactions (e.g., anti-spam fee escrowed via bandwidth/energy prior to verification) so CPU cost tracks paid fee.
- Re-audit `TransactionCapsule.validateSignature`'s zero-signature bypass for shielded-only transfers to ensure it isn't exploitable to also bypass other resource-accounting assumptions elsewhere.

```java
@Test
public void benchmarkInvalidProofFloodCost() throws Exception {
  dbManager.getDynamicPropertiesStore().saveAllowShieldedTransaction(1);
  int N = 200;
  long start = System.currentTimeMillis();
  for (int i = 0; i < N; i++) {
    ZenTransactionBuilder builder = new ZenTransactionBuilder(wallet);
    // Pure shielded z2z: no transparentFromAddress -> no signature required
    // 1 SpendDescription (garbage proof bytes) + 2 ReceiveDescriptions (garbage proof bytes)
    ShieldedTransferContract badContract = buildContractWithBogusProofs(); // craft manually via protobuf builder
    TransactionCapsule tx = wrapContract(badContract); // no .sign() call

    Contract contract = tx.getInstance().getRawData().getContract(0);
    ShieldedTransferActuator actuator = new ShieldedTransferActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setContract(contract).setTx(tx);
    try {
      actuator.validate(); // triggers librustzcashSaplingCheckSpend/CheckOutput/FinalCheck, always fails
    } catch (ContractValidateException expected) {
      // expected: proof invalid, e.g. "librustzcashSaplingCheckSpend error"
    }
  }
  long elapsed = System.currentTimeMillis() - start;
  long feeCharged = 0; // execute() never runs -> no shieldedTransactionFee actually deducted
  // Assert: elapsed time scales with N * (native proof verification cost),
  // while feeCharged stays 0 and TransactionCapsule.validateSignature required 0 signatures.
  Assert.assertEquals(0, feeCharged);
  System.out.println("N=" + N + " invalid shielded validate() calls took " + elapsed + " ms, fee paid=0");
}
```
Expected result: wall-clock time grows roughly linearly with `N` (dominated by native Sapling verification), while the fee actually collected from the attacker remains `0`, and no RPC-layer rate limiter specific to `ShieldedTransferContract` throttles this volume — demonstrating the metering-faithfulness violation.

```java
      throws ContractValidateException {
    if (!shieldedTransferContract.getTransparentFromAddress().isEmpty()

      throw new ContractValidateException("ShieldedTransferContract error, more than 1 senders");
```

```java
    if (!isVerified) {
      //Do not support multi contracts in one transaction
      Transaction.Contract contract = this.getInstance().getRawData().getContract(0);
      if (contract.getType() != ContractType.ShieldedTransferContract) {
        validatePubSignature(accountStore, dynamicPropertiesStore);
      } else {  //ShieldedTransfer
        byte[] owner = getOwnerAddress();
        if (!ArrayUtils.isEmpty(owner)) { //transfer from transparent address
          validatePubSignature(accountStore, dynamicPropertiesStore);

          if (this.transaction.getSignatureCount() > 0) {

          }
        }
      }
      isVerified = true;
    }
    return true;
  }
```
