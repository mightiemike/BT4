### Title
Deleting an account with a mistaken/non-existent `beneficiary_id` permanently burns the account's balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` lets any account owner delete their account and route the remaining balance to an arbitrary `beneficiary_id`. The validation layer only checks that `beneficiary_id` is a syntactically well-formed `AccountId` — it never checks that the account exists or is reachable. If the beneficiary account does not exist, the balance-refund receipt generated by the deletion fails with `AccountDoesNotExist`, and because it is a system-predecessor "refund" receipt, its failure causes the deposited balance to be permanently burned rather than returned to anyone. This mirrors the Gearbox report's pattern: a single unchecked parameter (`beneficiary_id` acting like `to`) lets an unprivileged caller irrecoverably destroy their own funds by mistake, with no recommended guard in place.

### Finding Description
`validate_delete_action` only validates that `beneficiary_id` is a syntactically valid account ID; it performs no existence check: [1](#0-0) 

`action_delete_account` then unconditionally converts the account's remaining balance into a `Receipt::new_balance_refund` addressed to that unchecked `beneficiary_id`, before removing the account: [2](#0-1) 

Balance-refund receipts are constructed with `predecessor_id == "system"` (a "refund" receipt per the runtime spec), and the runtime's docs state explicitly: "If the execution of a refund fails, the refund amount is burnt": [3](#0-2) 

This is implemented in the apply loop: for any receipt whose predecessor is `system`, a failed execution result adds the entire deposit to `other_burnt_amount` instead of generating any further refund or bounce-back: [4](#0-3) 

A `Transfer` action targeting a named account that doesn't exist fails with `AccountDoesNotExist` (as shown for ordinary transfers), and implicit account creation is explicitly disallowed for refund receipts, so a refund can never fall back to creating the destination account: [5](#0-4) 

Because `beneficiary_id` is never checked against account existence at either validation or execution time, a user who deletes their account with a typo'd, unused, or otherwise non-existent `beneficiary_id` (the `to = address(0)` analog from the report) causes the entirety of their remaining balance to be silently, permanently burned.

### Impact Explanation
The deleting account's full remaining NEAR balance is irrecoverably destroyed (added to `other_burnt_amount`/total supply burn) rather than transferred to any account. This is a direct, transaction-triggered, permanent loss of funds reachable by any ordinary unprivileged signer executing a single `DeleteAccount` action — no privileged role, network condition, or malicious peer is required.

### Likelihood Explanation
Likelihood is non-trivial: `beneficiary_id` is a free-form user-supplied `AccountId` with no existence check at signing time, submission time, or execution time. Any typo, use of an unregistered/expired sub-account, or reuse of a beneficiary ID that was deleted between wallet UI construction and transaction execution will silently burn all funds instead of failing the whole transaction atomically or refunding the caller.

### Recommendation
Before executing the delete, verify that `beneficiary_id` corresponds to an existing account (or reject `beneficiary_id == account_id` / non-existent IDs at `validate_delete_action`/`action_delete_account`), analogous to the report's recommendation to reject `to == address(0)`. Alternatively, make the delete action fail atomically (not commit the account removal) if the beneficiary account does not exist, instead of burning the deposit via the refund-failure path.

### Proof of Concept
1. Account `alice.near` holds `N` NEAR and has no locked stake.
2. `alice.near` signs and submits a transaction with a single `DeleteAccount { beneficiary_id: "nonexistent.near" }` action, where `nonexistent.near` has never been created.
3. `validate_delete_action` accepts the action (format is valid) — `runtime/runtime/src/action_validation.rs:447-451`.
4. `action_delete_account` removes `alice.near` and enqueues `Receipt::new_balance_refund("nonexistent.near", N)` — `runtime/runtime/src/actions.rs:380-387`.
5. The refund receipt executes with `predecessor_id == "system"`; the inner `Transfer` fails with `AccountDoesNotExist` because the receiver never existed and refunds cannot trigger implicit account creation.
6. Per `runtime/runtime/src/lib.rs:1047-1055`, the failed system-receipt deposit `N` is added to `other_burnt_amount` — permanently removed from total supply, credited to no account.
