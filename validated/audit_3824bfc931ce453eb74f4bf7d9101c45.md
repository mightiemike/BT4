Based on my investigation, I found a concrete, code-provable gap: `TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs` never validates the state-checkpoint hash (the JMT/state root) against the `TransactionInfo` it is supposed to authenticate.

### Title
`TransactionOutput::ensure_match_transaction_info` never verifies the state-checkpoint (state root) hash, letting replay/verification tools accept a divergent state root as matching - ([File: types/src/transaction/mod.rs])

### Summary
`ensure_match_transaction_info` is the function used by replay-verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to check that a freshly re-executed `TransactionOutput` matches the `TransactionInfo` recorded/authenticated on the accumulator for that version. It checks `status`, `gas_used`, `write_set_hash` (vs `state_change_hash`), and `event_root_hash`, but it never compares the computed `state_checkpoint_hash` for the version against `txn_info.state_checkpoint_hash()`. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` computes and checks three hashes explicitly (status/gas, write-set hash, event root hash) but the state-checkpoint hash field is completely absent from the comparison logic: [2](#0-1) 
The function even carries a `TODO(trading-native)` comment admitting the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling ... can report a successful replay even when the authenticated ... state root diverges from local execution": [3](#0-2) 
This function is the actual proof-integrity check used by `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which drives production replay-verification of archived/backed-up ledger history: it re-executes transactions and calls `ensure_match_transaction_info` per-transaction against `expected_txn_infos` pulled from the trusted backup/accumulator-verified `TransactionInfo` list. [4](#0-3) 
The `TransactionInfo.state_checkpoint_hash` is the field that anchors the JMT/global state root for a version and is what state-proof verification (`get_state_value_with_proof_by_version_ext`, `ensure_state_checkpoint_hash`, restore/backup manifest checks) ultimately relies on. Since this comparator silently skips it, a divergence between the locally re-executed state root and the archived, ledger-committed state root at that version is not detected by this code path.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result... must not be silently accepted" invariant for the replay/verification tooling: an operator or automated CI pipeline running `replay-on-archive` (or the equivalent debugger/CLI commands) to audit historical state integrity of an archived DB would get a false "match" even if the actual state root diverged (e.g., due to a bug in an upgrade, a hard-fork mismatch, or corrupted archive data that nonetheless kept correct write-set/event/gas fields). This is a proof-integrity gap in the tooling that is explicitly relied upon to catch exactly this class of divergence, meaning genuine ledger state corruption or non-determinism affecting only the state root (not the write-set hash itself, which can happen since the state_checkpoint_hash also folds in hot-state/position roots per the surrounding code) can pass verification undetected.

### Likelihood Explanation
This is not a hypothetical: the code has a standing `TODO` acknowledging the exact scenario. It requires no attacker action to trigger; it is a latent gap in every invocation of `ensure_match_transaction_info` across all three call sites. It's most consequential once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any scenario where state root and write-set hash could diverge independently) is exercised, but the check is missing unconditionally, not just under that feature flag.

### Recommendation
Add a comparison in `ensure_match_transaction_info` (types/src/transaction/mod.rs) between the state checkpoint hash of the locally re-executed transaction output for the given version (as tracked by the caller's `StateCheckpointOutput`/`LedgerUpdateOutput`) and `txn_info.state_checkpoint_hash()`, along with the hot-state and position-state checkpoint hashes when applicable, before returning `Ok(())`. Note that `TransactionOutput` itself does not carry the state-checkpoint hash (it's computed at the ledger-update/checkpoint layer, not per-output), so this requires either threading the checkpoint hash into the comparator's signature or performing the check at the call sites (`replay_on_archive.rs`, `aptos_debugger.rs`, `cli/commands.rs`) using `DoStateCheckpoint`/`DoLedgerUpdate` output.

### Proof of Concept
Not independently exploitable as a state-corrupting attack (this is a verification-omission bug, not a consensus-commit bug); the concrete reproduction is: run replay-on-archive against an archive whose stored `TransactionInfo.state_checkpoint_hash` values do not match what re-execution would produce (e.g., by hand-editing a backup or simulating a state-root divergence while keeping write_set/events/gas identical) and observe that `ensure_match_transaction_info` at `types/src/transaction/mod.rs:2139-2203` returns `Ok(())`, causing `replay_on_archive.rs`'s `execute_and_verify` to report success for that transaction.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
