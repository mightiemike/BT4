## Root cause analysis

`getEmbeddedAppUrl` extracts the `host` query parameter and passes it to `buildEmbeddedAppUrl`, which calls `sanitizeHost` and then directly string-interpolates the base64-decoded value into the redirect URL: [1](#0-0) 

`sanitizeHost` only validates the parsed `URL().hostname` of the decoded value against an allow-listed domain suffix regex — it never validates the rest of the string (path/query/fragment), and it returns the original *raw* base64 `host` string, not a normalized one: [2](#0-1) 

Because only `.hostname` is checked, an attacker can construct a decoded host value such as `test.myshopify.com/<arbitrary-bytes-including-CR-LF>`. The `new URL()` call used for validation stops parsing the "host" component at the first `/`, so `.hostname` still resolves to `test.myshopify.com` and passes the allow-list check, while everything after the `/` (including literal `\r\n` bytes, since `atob()`/`decodeHost` does no encoding) is completely unchecked. `buildEmbeddedAppUrl` then re-decodes the same raw base64 string and concatenates it verbatim into the final URL: [3](#0-2) 

This final string is returned as the redirect target and used verbatim by consumers such as `redirectToShopifyOrAppRoot` in shopify-app-remix/shopify-app-react-router, or `res.redirect(embeddedUrl + req.path)` in the documented Express integration: [4](#0-3) 

## Practical exploitability caveat

However, the practical severity of the "CRLF header split" scenario is significantly limited:

- The domain-suffix check is anchored (`\.(myshopify\.com|...)$`), so the actual `hostname` used by any real URL/HTTP parser (browser, Node `URL`, Express) can never be redirected to an attacker-controlled domain — only the *path* portion of an otherwise-legitimate `*.myshopify.com`/`*.shopify.com` URL can be attacker-influenced. This rules out true open-redirect/SSRF to arbitrary hosts.
- Actually delivering literal `\r\n` bytes to the wire as an HTTP header value requires that whatever code eventually calls `res.setHeader('Location', …)` / `res.redirect(...)` does not reject control characters. Node's built-in `http` module (since Node 8) throws `ERR_INVALID_CHAR` for `\r`/`\n` in header values, and Express's `res.location()` runs the URL through `encodeurl`. This means, in the standard shopify-app-express/remix/react-router integrations running on Node, the literal CRLF would typically be rejected or encoded by the runtime/framework before it ever reaches a raw socket — i.e., the actual "header splitting" impact depends on a downstream component's behavior, not solely on this library.

This distinguishes the bug from a directly-exploitable open redirect/SSRF: the library-level flaw (validating only `.hostname` while blindly reusing the entire raw decoded string, including a completely unchecked path segment) is real and worth fixing, but the specific "CRLF response splitting to break header integrity" impact requires an additional downstream weakness (a raw HTTP server/consumer that does not enforce Node's/Express's built-in CRLF rejection) that is outside the scope of this library and cannot be confirmed to exist within `shopify-app-js` itself.

### Title
Unvalidated path segment in `host` param allows path/content injection into embedded-app redirect URL - (File: `packages/apps/shopify-api/lib/auth/get-embedded-app-url.ts`)

### Summary
`sanitizeHost` in `shop-validator.ts` validates only the `hostname` component of the base64-decoded `host` parameter, ignoring everything after the first `/`, `?`, or `#`. `buildEmbeddedAppUrl` then reuses the full raw decoded string (including any attacker-controlled path/query bytes, e.g. literal CR/LF) to build the final redirect URL returned by `getEmbeddedAppUrl`.

### Finding Description
An attacker crafts a `host` query param whose base64-decoded value is e.g. `test.myshopify.com/%0d%0a<injected-bytes>` (or raw `\r\n` bytes, since `decodeHost` is a plain `atob()` with no encoding). `sanitizeHost` (`packages/apps/shopify-api/lib/utils/shop-validator.ts:52-90`) builds a `URL` object from the decoded string only to read `.hostname`; the host component parsing stops at the `/`, so `.hostname` is `test.myshopify.com`, which passes the allow-listed suffix regex — the payload after `/` is never inspected. `sanitizeHost` then returns the **original untouched base64 string**. `buildEmbeddedAppUrl` (`get-embedded-app-url.ts:44-53`) decodes that same base64 string again and interpolates it directly into `https://${decodedHost}/apps/${config.apiKey}` with no further validation or encoding, propagating the attacker-controlled bytes (including raw CR/LF) into the returned URL string, which is then used as a redirect target by consumers like `redirectToShopifyOrAppRoot`.

### Impact Explanation
Because the hostname suffix check is anchored to Shopify-owned domains, the attacker cannot redirect victims to a fully attacker-controlled host — this is not a classic open redirect/SSRF to an arbitrary origin. The realistic impact is limited to injecting an attacker-chosen path/query onto an otherwise-legitimate `*.myshopify.com` URL, and only becomes a true header-splitting/response-injection issue if a downstream HTTP layer fails to reject/encode CR/LF in header values (Node's `http` module and Express's `encodeurl`-based `res.location()` normally do reject/encode such bytes), which could not be confirmed as broken anywhere in this repository.

### Likelihood Explanation
Low-to-moderate. Any unauthenticated caller can supply an arbitrary base64 `host` value, and the missing path/query validation is trivially reachable. But full exploitation into an observable open-redirect/header-splitting bug requires a downstream component that does not enforce standard HTTP header sanitization, which is not demonstrated within `shopify-app-js`.

### Recommendation
Validate and reconstruct the redirect URL from the parsed `URL` object's `hostname` only (rebuild `https://${hostname}/apps/${apiKey}` instead of reusing the raw decoded string), and/or reject any decoded `host` value containing a path, query, fragment, or control characters in `sanitizeHost`.

```typescript
export function sanitizeHost(config: ConfigInterface) {
  return (host: string, throwOnInvalid = false): string | null => {
    const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;

    let sanitizedHost = base64regex.test(host) ? host : null;
    if (sanitizedHost) {
      const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);

      const originsRegex = [
        'myshopify\\.com',
        'shopify\\.com',
        'myshopify\\.io',
        'spin\\.dev',
        'shop\\.dev',
      ];

      if (config.domainTransformations) {
        const hostTransformationDomains = config.domainTransformations
          .filter((t) => t.includeHost !== false)
          .flatMap((t) =>
            getTransformationDomains({
              ...config,
              domainTransformations: [t],
            }),
          );
        originsRegex.push(...hostTransformationDomains);
      }

      const hostRegex = new RegExp(`\\.(${originsRegex.join('|')})$`);
      if (!hostRegex.test(hostname)) {
        sanitizedHost = null;
      }
    }
    if (!sanitizedHost && throwOnInvalid) {
      throw new InvalidHostError('Received invalid host argument');
    }

    return sanitizedHost;
  };
```
