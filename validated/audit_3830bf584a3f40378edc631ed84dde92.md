### Title
Manual, per-actuator LRU cache invalidation for `ContractCapsule` risks consensus divergence when a mutation site forgets to invalidate it - ([File: actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java])

### Summary
`RepositoryImpl` maintains contract state (`ContractCapsule`, including `consumeUserResourcePercent`, `originEnergyLimit`, code hash) both in a per-transaction `contractCache` and, critically, in what appears to be a separate, longer-lived LRU cache that is explicitly invalidated via the static method `RepositoryImpl.removeLruCache(...)` [1](#0-0) [2](#0-1) . Both `UpdateSettingContractActuator` and `UpdateEnergyLimitContractActuator` write directly to `ContractStore` and then call `RepositoryImpl.removeLruCache(contractAddress)` to keep the cache consistent with the store.

### Finding Description
This is structurally the same bug class as the OtterSec report: a cached representation of on-chain executable/contract state (analogous to the cached ELF in `ExtendProgramData`) is not guaranteed to be flushed/invalidated whenever the underlying account data is mutated. Here, invalidation is not automatic on write to `ContractStore`; instead, each actuator that bypasses the normal `Repository.updateContract()` path must remember to call the static `RepositoryImpl.removeLruCache()` helper itself [3](#0-2) . Normal TVM execution flows read/write contract state through `RepositoryImpl.getContract()`/`updateContract()`, which populate `contractCache` and are committed via `commitContractCache()` [4](#0-3) [5](#0-4) [6](#0-5) . But `UpdateSettingContractActuator`/`UpdateEnergyLimitContractActuator` write to `ContractStore` directly, sidestepping that cache path, and instead rely on an explicit manual "flush" call to a separate LRU cache referenced from `VMActuator` and `Program.java` as well [7](#0-6) .

This pattern is fragile by construction: it depends on every current and future call site that mutates `ContractStore` outside the `Repository` cache/commit lifecycle to remember to invalidate the LRU cache. I was not able to fully inspect the internal implementation and thread-safety guarantees of `RepositoryImpl.removeLruCache()` itself within the available tool budget, so I cannot confirm whether the invalidation is atomic with respect to concurrent reads from other in-flight transaction executions (e.g. via `Program.getCodeHashAt`/`getContractState` reading cached `ContractCapsule` fields) [8](#0-7) .

### Impact Explanation
If any code path updates a deployed contract's `ContractCapsule` fields (e.g. `consumeUserResourcePercent`, `originEnergyLimit`, code hash) without invalidating the LRU cache — whether due to a future missed call site, a race between the store write and the cache eviction, or a code path that reads the cache before invalidation completes — different nodes (or the same node across sequential blocks) could use stale vs. fresh contract metadata during TVM execution. Since `consumeUserResourcePercent` and `originEnergyLimit` directly influence energy accounting split between caller and contract owner during contract execution, a stale cached value being used by one executor while another uses the updated value would produce divergent energy/fee deductions for the same transaction — a state root / consensus divergence.

### Likelihood Explanation
The likelihood is moderate: the invalidation calls are currently present at both known mutation sites (`UpdateSettingContractActuator`, `UpdateEnergyLimitContractActuator`), so no active exploit path was proven in this pass. The risk is a latent one: the design pattern of "cache must be manually invalidated in every writer" is exactly the anti-pattern flagged in the source report, and it only takes one missed or improperly-ordered invalidation (in current or future code) to reintroduce the class of bug described. I was unable to verify the full `RepositoryImpl.removeLruCache()` implementation and its concurrency guarantees to rule out a race condition, which is a gap in this analysis.

### Recommendation
Eliminate the manual dual-cache-invalidation pattern: route all writes to contract account data (`ContractStore`) exclusively through `Repository.updateContract()`/`commit()` so that cache consistency is enforced structurally rather than by convention. If a separate LRU cache is required for performance, tie its invalidation directly to `ContractStore.put()` (e.g., inside the store or a wrapping decorator) rather than requiring each actuator to remember to call `RepositoryImpl.removeLruCache()`. Additionally, verify (or add) synchronization guarantees so that no concurrent TVM execution can observe the cache in the window between the store write and the cache invalidation.

### Proof of Concept
Not independently constructed — this finding is based on static code-path analysis of the two known cache-invalidation call sites and the shared `RepositoryImpl` cache/commit machinery; I could not fully trace the runtime concurrency behavior of `RepositoryImpl.removeLruCache()` within the available investigation budget to build a concrete divergence PoC.

  private void commitContractCache(Repository deposit) {
    contractCache.forEach(((key, value) -> {
      if (value.getType().isDirty() || value.getType().isCreate()) {
        if (deposit != null) {
          deposit.putContract(key, value);
        } else {
          ContractCapsule contractCapsule = new ContractCapsule(value.getValue());
          if (!abiStore.has(key.getData())) {
            abiStore.put(key.getData(), new AbiCapsule(contractCapsule));
          }
          getContractStore().put(key.getData(), contractCapsule);
        }
      }
    }));
  }

  public byte[] getCodeHashAt(DataWord address) {
    byte[] tronAddr = address.toTronAddress();
    AccountCapsule account = getContractState().getAccount(tronAddr);
    if (account != null) {
      ContractCapsule contract = getContractState().getContract(tronAddr);
      byte[] codeHash;
      if (contract != null) {
        codeHash = contract.getCodeHash();
        if (ByteUtil.isNullOrZeroArray(codeHash)) {
          byte[] code = getCodeAt(address);
          codeHash = Hash.sha3(code);
          contract.setCodeHash(codeHash);
          getContractState().updateContract(tronAddr, contract);
        }
      } else {
        codeHash = Hash.sha3(new byte[0]);
      }
      return codeHash;
    } else {
      return EMPTY_BYTE_ARRAY;
    }
