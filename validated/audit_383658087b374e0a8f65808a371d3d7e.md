### Title
Unprivileged dust-transfer griefing on `GetFundMigrationSigningRequest` stalls fund migration and can permanently freeze TSS-controlled funds - (File: universalClient/chains/evm/tx_builder.go)

### Summary
`GetFundMigrationSigningRequest` computes the fund-migration sweep amount from a live `balanceOf`-style query (`rc.GetBalance`) of the old TSS address, exactly like the reported `_getPoolBalance` pattern that trusts a raw on-chain balance instead of an internally tracked value. [1](#0-0)  Because any unprivileged actor can send native tokens to the (publicly derivable) old TSS address at will, the "balance" this function reads is attacker-influenceable and non-deterministic across independent observers — the same structural flaw as the Stargate report, applied to TSS coordination instead of pool accounting.

### Finding Description
`GetFundMigrationSigningRequest` builds the sweep transaction as `balance - gasCost - l1GasFee`, where `balance` is fetched live from the chain unless explicitly supplied. [2](#0-1)  This function is called twice independently by different actors at different times:

1. By the coordinator, when building the initial signing setup (`balance` queried live, `claimedAmount == nil`). [3](#0-2) 
2. By every participant validator, independently, to *verify* the coordinator's signing hash before signing — again querying live balance from its own RPC node. [4](#0-3) 

The code comment explicitly assumes stability: "the balance at signing time will equal the balance at broadcast time" because outbound is disabled and no pending outbounds remain. [5](#0-4)  That assumption only holds if nobody else can change the old TSS address's balance — but the address is a public, permissionless native-token recipient. Any external, unprivileged attacker can send a dust transfer to the old TSS address on the source chain between the moment the coordinator computes its `balance`/`signingHash` and the moment each honest participant validator independently recomputes it for verification (`verifyFundMigrationSigningRequest`, comparing hashes byte-for-byte). [6](#0-5) 

Because different validators use different RPC providers/endpoints (`executeWithFailover`) and query at different wall-clock times, a single well-timed dust transfer causes the coordinator's `signingReq.SigningHash` (built from the old balance) to differ from what honest participants recompute (built from the new, dust-inflated balance). The hash-mismatch check then rejects the ACK. [7](#0-6)  Since the migration sweeps the *entire* balance every time (no internal ledger of "funds that belong to the protocol" separate from `balanceOf`), any attacker who can afford trivial gas on the source chain can repeat this indefinitely to keep the balance in flux and prevent any two honest validators from ever agreeing on the same signing hash.

### Impact Explanation
`InitiateFundMigration` enforces that outbound must be disabled and no pending outbounds exist before migration starts, and blocks starting a second migration while one is pending for the same chain. [8](#0-7)  If the migration can be perpetually stalled by dust-transfer griefing, the funds held at the compromised/rotated-out old TSS address can never be swept to the current TSS key, and outbound for that chain remains disabled for the duration — this is a form of permanent freezing of protocol/user funds reachable purely through unprivileged external transactions, not through any admin, validator, or key-compromise assumption.

### Likelihood Explanation
Exploitation requires only: (1) observing the public `FundMigrationInitiated` event (which contains `OldTssPubkey`, from which the address is deterministically derivable) [9](#0-8) , and (2) sending a trivial native-token transfer to that address on the source chain at any point while migration signing is in progress. No special access, timing precision beyond "somewhere in the multi-second signing window," or validator collusion is needed. This is a low-cost, repeatable griefing vector fully within reach of a single unprivileged attacker.

### Recommendation
Do not let live `balanceOf`/`GetBalance` results at variable observation times determine the swept amount independently at each party. Instead, have the chain (via the `FundMigrationInitiated` event, which is agreed upon by consensus) pin a canonical balance snapshot (e.g., the balance observed and voted on by validators at initiation, similar to how gas price/gas limit/L1 fee are already baked into the event) so that the coordinator and every participant derive the *same* signing hash from a value fixed at ballot time rather than from independent live RPC calls. Alternatively/additionally, require the coordinator's chosen balance/amount to be attested to and voted on by validators before being used to build the signing hash, the same way `TxHash` is voted on in `VoteFundMigration`.

### Proof of Concept
1. Admin disables outbound for chain `eip155:X` and calls `InitiateFundMigration`, emitting `FundMigrationInitiated` with `OldTssPubkey`. [10](#0-9) 
2. Attacker derives the old TSS address from `OldTssPubkey` (public) and sends 1 wei of native token to it right as validators begin verifying the coordinator's signing setup.
3. The coordinator already computed `signingHash` from `balance_A` (pre-dust). [11](#0-10) 
4. One or more honest participant validators independently query `GetBalance` after the dust lands, getting `balance_B = balance_A + 1`, and recompute a different `signingHash`. [12](#0-11) 
5. `verifyFundMigrationSigningRequest` rejects due to hash mismatch, and/or `VerifySignedData`/ACK verification rejects a returning signature for the same reason. [13](#0-12) 
6. Attacker repeats step 2 on each retry attempt, indefinitely preventing quorum convergence on a single signing hash.

**Uncertainty / what I could not fully verify:** I did not find (or was not able to locate within index limits) any additional bound, retry backoff, or fallback mechanism beyond `checkExpiredSessions`'s generic session-expiry retry logic that would mitigate a sustained griefer; nor could I confirm whether ballot-level nonce assignment (`assignFundMigrateNonce`) changes the address-balance race window in a way that reduces the attack surface. A Devin session with full repo access and the ability to run the fund-migration integration tests would be needed to confirm the exact reproduction timing and whether any existing safeguard (not surfaced in the indexed code) already neutralizes this.

	fromAddr := ethcommon.HexToAddress(data.From)
	toAddr := ethcommon.HexToAddress(data.To)

	if data.GasPrice == nil || data.GasPrice.Sign() == 0 {
		return nil, fmt.Errorf("gas price must be provided for fund migration")
	}
	if data.GasLimit == 0 {
		return nil, fmt.Errorf("gas limit must be provided for fund migration")
	}

	var balance *big.Int
	if data.Balance != nil {
		balance = new(big.Int).Set(data.Balance)
	} else {
		queried, err := tb.rpcClient.GetBalance(ctx, fromAddr)
		if err != nil {
			return nil, fmt.Errorf("failed to get balance of %s: %w", data.From, err)
		}
		balance = queried
	}

	maxTransfer, err := computeFundMigrationTransfer(balance, data.GasPrice, data.GasLimit, data.L1GasFee)
	if err != nil {
		return nil, err
	}
