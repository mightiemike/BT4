Based on my investigation, I found a genuine analog: `l1_handler_message_hash` in `starknet_api::hash` panics via `.expect()` on empty calldata, reachable from an L1 message with an empty payload.

### Title
Sequencer panic (DoS) via empty-payload L1-to-L2 message triggering `.expect()` in `l1_handler_message_hash` - ([File: crates/starknet_api/src/hash.rs])

### Summary
`l1_handler_message_hash` unwraps `calldata.0.split_first()` with `.expect(...)`, assuming the calldata always contains at least the prepended L1 `from_address` element. An L1 message with a zero-length payload produces `L1HandlerTransaction` calldata that, depending on the code path used to hash/verify it, can be empty, causing an unrecoverable panic (process crash) analogous to the NATS `.expect()`/panic-on-attacker-input pattern (CWE-476-class reachable crash) described in the report.

### Finding Description
`L1HandlerTransaction::calc_msg_hash` calls `l1_handler_message_hash`, which does:
```rust
let (from_address, payload) =
    calldata.0.split_first().expect("Invalid calldata, expected at least from_address");
``` [1](#0-0) 

This function assumes calldata is never empty because normally the L1 sender address is always prepended, as seen in the canonical constructor:
```rust
impl From<EventData> for L1HandlerTransaction {
    fn from(mut event_data: EventData) -> Self {
        let payload = Arc::make_mut(&mut event_data.payload.0);
        payload.insert(0, event_data.from_address.into());
        ...
``` [2](#0-1) 

However, `Calldata`/`L1HandlerTransaction` derive `Deserialize` and carry no non-empty invariant — this is explicitly acknowledged elsewhere in the codebase:
```rust
pub fn payload_size(&self) -> usize {
    // The calldata includes the "from" field, which is not a part of the payload.
    // `saturating_sub` guards the empty-calldata case (which would otherwise underflow to
    // `usize::MAX` in release): `L1HandlerTransaction` derives `Deserialize` and `Calldata`
    // has no non-empty invariant.
    self.tx.calldata.0.len().saturating_sub(1)
}
``` [3](#0-2) 

This comment confirms that other code in the same struct was specifically hardened (with `saturating_sub`) against empty calldata, but `l1_handler_message_hash` was not similarly hardened and still uses a panicking `.expect()` on the same untrusted invariant.

### Impact Explanation
If `l1_handler_message_hash`/`calc_msg_hash` is invoked on an `L1HandlerTransaction` whose calldata is empty (e.g., a deserialized/constructed L1 handler transaction that never went through the `EventData -> L1HandlerTransaction` prepending path, or any consumer that builds/receives an L1 handler transaction with empty payload), the sequencer process panics. Since Rust panics abort the current thread/process (depending on panic strategy), this can crash the node processing L1 messages, an availability impact (DoS) matching CWE-476-class "reachable panic on attacker/external input" cited in the NATS advisory.

### Likelihood Explanation
The likelihood depends on whether any reachable code path constructs or deserializes an `L1HandlerTransaction` with empty calldata before calling `calc_msg_hash`/`l1_handler_message_hash`. The `L1ToL2Message`/`EventData` conversions I found always prepend the sender address, so the primary L1-scraper path appears safe. However, because `Calldata`/`L1HandlerTransaction` implement `Deserialize` with no non-empty invariant enforced at the type level (per the comment above), any additional deserialization entry point (e.g. RPC, JSON-RPC `l1_handler` message tooling, or future/other integration code) that builds an `L1HandlerTransaction` directly from external data without guaranteeing the from-address prefix would trigger the panic. I was not able to fully confirm within the indexed code whether an unprivileged/external caller can currently reach `calc_msg_hash` with attacker-controlled empty calldata bypassing the prepending step — this would require deeper tracing of all callers of `calc_msg_hash`/`l1_handler_message_hash` across the full repository, which the current index does not fully expose.

### Recommendation
Replace the panicking `.expect()` in `l1_handler_message_hash` with a `Result`-returning fallible check (mirroring the `saturating_sub` guard pattern already used in `L1HandlerTransaction::payload_size`), so that empty calldata produces a graceful error rather than a process panic, regardless of which caller reaches this function.

### Proof of Concept

use starknet_api::transaction::fields::Calldata;
use starknet_api::transaction::L1HandlerTransaction;
use starknet_api::core::{ContractAddress, EntryPointSelector, Nonce};
use starknet_api::core::patricia_key;
use starknet_types_core::felt::Felt;
use std::sync::Arc;

let tx = L1HandlerTransaction {
    contract_address: ContractAddress(patricia_key!(1_u8)),
    entry_point_selector: EntryPointSelector(Felt::ONE),
    nonce: Nonce(Felt::ZERO),
    calldata: Calldata(Arc::new(vec![])), // empty calldata: no non-empty invariant enforced
    ..Default::default()
};

// Panics: "Invalid calldata, expected at least from_address"
let _ = tx.calc_msg_hash();

/// Calculating the message hash of L1 -> L2 message.
/// For more info: <https://docs.starknet.io/documentation/architecture_and_concepts/Network_Architecture/messaging-mechanism/#structure_and_hashing_l1-l2>
pub fn l1_handler_message_hash(
    contract_address: &ContractAddress,
    nonce: Nonce,
    entry_point_selector: &EntryPointSelector,
    calldata: &Calldata,
) -> L1L2MsgHash {
    let (from_address, payload) =
        calldata.0.split_first().expect("Invalid calldata, expected at least from_address");

    let mut encoded = Vec::new();
    encoded.extend(from_address.to_bytes_be());
    encoded.extend(contract_address.0.key().to_bytes_be());
    encoded.extend(nonce.to_bytes_be());
    encoded.extend(entry_point_selector.0.to_bytes_be());

    let payload_length_as_felt =
        Felt::from(u64::try_from(payload.len()).expect("usize should fit in u64"));
    encoded.extend(payload_length_as_felt.to_bytes_be());

    for felt in payload {
        encoded.extend(felt.to_bytes_be());
    }

    let mut keccak = Keccak256::default();
    keccak.update(&encoded);
    L1L2MsgHash(keccak.finalize().into())
