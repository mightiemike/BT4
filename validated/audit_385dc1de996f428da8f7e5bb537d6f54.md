### Title
Quadratic-blowup regex processing of attacker-controlled Cairo0 class ABI/program strings in hinted class hash computation - ([File: crates/starknet_os/src/hints/class_hash/hinted_class_hash.rs])

### Summary
`compute_cairo_hinted_class_hash` (called from `compute_deprecated_class_hash` for any deprecated Cairo0 class) runs `add_backward_compatibility_space` on the full re-serialized JSON of an attacker-declared contract's `program`/`abi`. This function applies four `Regex`es with nested `replace_all` calls (one `replace_all` invoking another `replace_all` inside its match closure) over attacker-controlled string content, analogous to the Bref/Riverline advisory pattern of unbounded slow string transforms on attacker-supplied header text during event-driven request handling. [1](#0-0) 

### Finding Description
`add_backward_compatibility_space` is invoked from `compute_cairo_hinted_class_hash` whenever a declared Cairo0 contract has no `compiler_version` field (i.e., an older-style program) as part of computing the "hinted class hash": [2](#0-1) 

Inside the function, `value_regex` matches `"value": "(.*?)"` non-greedily across the *entire serialized JSON string* (which embeds the attacker-supplied `abi`, `program.identifiers`, `program.attributes`, etc.), and for each match, `paren_regex.replace_all` is run on the captured inner text, which in turn runs `pair_regex.replace_all` in a nested closure per parenthesized group: [3](#0-2) 

Because `value_regex`'s capture group `(.*?)` is unbounded and applied per `"value": "..."` occurrence, and the inner `paren_regex`/`pair_regex` re-scan the captured substring on every outer match, an attacker who crafts a Cairo0 declare transaction with many nested/degenerate `"value"` strings containing large numbers of parenthesis groups and colon-separated tokens can force this code path into work that scales far worse than linearly with the crafted content size (nested regex re-scans over the same data), mirroring the CVE-2024-29186 bug class where a slow string transform over attacker-controlled request-body content causes disproportionate CPU cost per request.

This is reachable purely by an unprivileged declarer: `compute_deprecated_class_hash` → `compute_cairo_hinted_class_hash` is executed both by the Starknet OS during block re-execution of Declare (Cairo0) transactions and by the hint processor when validating a declared class's hash, meaning the cost is paid by the sequencer/prover for every relevant block containing such a Declare, not just once at submission time. [4](#0-3) 

### Impact Explanation
An attacker submitting a single crafted Cairo0 `Declare` transaction (with a maliciously structured `program`/`abi` containing degenerate `"value"`/parenthesis/colon patterns, within otherwise-legal size limits) can force disproportionately expensive nested regex processing on the sequencer and, more critically, on the Starknet OS re-execution/proving path, which recomputes this hash for every block containing the transaction. Excess CPU consumption on this path can degrade block production throughput or, in aggregate proving/re-execution contexts, threaten timely block finalization — a network-availability concern (CWE-400) rather than a state-correctness one.

### Likelihood Explanation
Reaching this code requires only an unprivileged account submitting a standard Cairo0 (deprecated) `Declare` transaction; no special privileges, staking, or operator/proposer role is needed. However, I could not fully verify (within tool budget) the exact upper bound on ABI/program field sizes enforced by gateway validation for deprecated Cairo0 declares (the stateless validator code I found, `validate_class_length`/`validate_declare_tx` in `crates/apollo_gateway/src/stateless_transaction_validator.rs`, appears to target Sierra/Cairo1 `SierraContractClass` size and bytecode limits — it is unclear whether/how equivalent size caps constrain deprecated Cairo0 `abi`/`program` string content specifically). This uncertainty affects how large an attacker-controlled payload can realistically reach this regex path, and thus the practical severity of the slowdown.

### Recommendation
- Bound the total size and nesting complexity of the `abi`/`program` content passed into `add_backward_compatibility_space`, or reject Cairo0 declares whose serialized JSON exceeds a strict size limit before this transform runs.
- Replace the nested nested-`replace_all` regex approach with a single-pass, linear-time parser (as recommended by the original advisory: validate/bound the parsed substrings before performing further processing on them) to avoid quadratic behavior on crafted inputs.
- Add a fuzz/perf test that measures wall-clock time of `add_backward_compatibility_space` against adversarially constructed `abi`/`program` strings with many nested parenthesis/colon groups, to confirm the actual complexity class and set a hard timeout or size-based rejection.

pub fn compute_cairo_hinted_class_hash(
    contract_class: &ContractClass,
) -> Result<Felt, HintedClassHashError> {
    // Serialize to Value, sort all objects by keys for deterministic output, then to bytes.
    // The sorting is necessary because serde_json with `preserve_order` feature enabled
    // maintains insertion order instead of sorting keys.
    // TODO(Meshi): Compute hinted hashes when loading serialized contracts from storage, before
    // deserializing, to avoid back-and-forth serde.
    let contract_value = serde_json::to_value(contract_class)?;
    let sorted_contract_value = sort_json_value(contract_value);
    let contract_definition_vec = serde_json::to_vec(&sorted_contract_value)?;
    let contract_definition: CairoContractDefinition<'_> =
        serde_json::from_slice(&contract_definition_vec)?;

    let mut string_buffer = vec![];

    let mut ser = serde_json::Serializer::with_formatter(&mut string_buffer, PythonJsonFormatter);
    contract_definition.serialize(&mut ser)?;

    let mut raw_json_output = String::from_utf8(string_buffer)?;
    if contract_definition.program.compiler_version.is_none() {
        add_backward_compatibility_space(&mut raw_json_output);
    }

    let mut keccak_writer = KeccakWriter::default();
    keccak_writer
        .write_all(raw_json_output.as_bytes())
        .expect("writing to KeccakWriter never fails");

    let KeccakWriter(hash) = keccak_writer;
    Ok(truncated_keccak(<[u8; 32]>::from(hash.finalize())))
}

pub fn add_backward_compatibility_space(input: &mut String) {
    let cairo_regex = Regex::new(r#""cairo_type"\s*:\s*"\(([^"]*)\)""#).unwrap();
    let value_regex = Regex::new(r#""value"\s*:\s*"(.*?)""#).unwrap();
    let paren_regex = Regex::new(r"\(([^()]+)\)").unwrap();
    let pair_regex = Regex::new(r"([^:\s,]+):\s*([^,\s)]+)").unwrap();

    // Fix cairo_type, which must be a single type (either a simple type or a tuple).
    *input = cairo_regex
        .replace_all(input, |caps: &regex::Captures<'_>| {
            let inner = &caps[1];
            let fixed = pair_regex.replace_all(inner, "$1 : $2");
            format!("\"cairo_type\": \"({fixed})\"")
        })
        .into_owned();

    // Fix only (key: value) pairs inside (...) in "value".
    *input = value_regex
        .replace_all(input, |caps: &regex::Captures<'_>| {
            let raw_value = &caps[1];
            let fixed = paren_regex
                .replace_all(raw_value, |paren_caps: &regex::Captures<'_>| {
                    let inner = &paren_caps[1];
                    let fixed_inner = pair_regex.replace_all(inner, "$1 : $2");
                    format!("({fixed_inner})")
                })
                .into_owned();
            format!("\"value\": \"{fixed}\"")
        })
        .into_owned();
}
