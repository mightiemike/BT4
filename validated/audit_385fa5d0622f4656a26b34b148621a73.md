### Title
Standby witness allowance uses updated vote count before pay-per-vote reward is finalized for the ending cycle - ([File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java])

### Summary
The reported Timeless bug is a "state mutated before reward accrual" class of bug: `Gate.claimYieldAndEnter` mints tokens to the Gate contract (increasing its balance) before accruing yield for it, so the newly-minted balance improperly participates in the yield-per-token delta computed for the whole elapsed period, over-crediting the recipient. The same "mutate state, then compute period reward using the *already-mutated* state" pattern is reachable in `MaintenanceManager.doMaintenance()`.

### Finding Description
`doMaintenance()` first accumulates each witness's `Vi` (reward-per-vote accumulator) for the *closing* cycle using the vote count that was in effect during that cycle: [1](#0-0) 

It then applies the new votes cast during the closing cycle directly onto the same `WitnessCapsule.voteCount` field and persists it: [2](#0-1) 

Immediately after, `incentiveManager.reward(newWitnessAddressList)` is invoked to distribute the **standby-witness allowance for the cycle that just ended**, but it reads `consensusDelegate.getWitness(address).getVoteCount()` — which has *already* been mutated by the `countWitness.forEach` block above to include the brand-new votes for the *next* cycle: [3](#0-2) 

This is structurally identical to the Gate.sol issue: a reward computation (`totalPay * voteCount / voteSum`) is performed using an account/witness aggregate value (`voteCount`) that was mutated (increased/decreased by new votes) immediately beforehand, in the very same maintenance pass, instead of using the vote-count snapshot that was actually in force during the period being rewarded. Compare this with the correctly-ordered `delegationStore.setWitnessVote(nextCycle, ...)` call at the very end of the method, which intentionally stores the *new* vote count only for `nextCycle`, confirming that the codebase's own intended invariant is "current-cycle reward must use current-cycle (pre-update) vote count, next-cycle vote count is stored separately for future use." `IncentiveManager.reward` breaks that invariant by consuming the live, already-updated `witnessCapsule.getVoteCount()`.

### Impact Explanation
Any account that casts a large new vote (or unvotes) right before a maintenance boundary can shift the just-closed cycle's `WITNESS_127`/standby allowance distribution in its favor or against other standby witnesses, because the payout ratio `voteCount / voteSum` used by `IncentiveManager.reward` is computed from vote totals that already include votes that should only count starting next cycle. This causes incorrect reward/asset accounting for standby witnesses (a form of the "wrong yield/reward accumulation" bug class), diverting allowance value between witnesses that would otherwise not be entitled to it. This is a live/production consensus-layer accounting path invoked on every maintenance cycle (`Manager.processBlock` -> `consensus.applyBlock` -> `MaintenanceManager.doMaintenance`).

### Likelihood Explanation
This path executes automatically once per maintenance cycle for every network participant, requiring no special privilege — any voter broadcasting a `VoteWitnessContract` transaction close to the maintenance boundary can influence the outcome. However, this only affects the *old* reward algorithm's standby-witness payout path (`IncentiveManager.reward`, gated by `!allowChangeDelegation()`); on networks/cycles where `allowChangeDelegation()` is true (the "new" delegation reward algorithm, which is the actual reward path exercised by `MortgageService`/`VoteRewardUtil`/`RewardViCalService`), `IncentiveManager.reward` returns immediately and is not exploitable. So likelihood is limited to chains/periods still running the legacy standby-reward algorithm.

### Recommendation
Snapshot each witness's `voteCount` for the cycle being rewarded **before** applying `countWitness` deltas, and pass that snapshot (not the live, mutated `WitnessCapsule`) into `IncentiveManager.reward`, mirroring the `Vi`-accumulation call that correctly precedes the vote-count mutation.

### Proof of Concept
Not independently verified with a live testnet run; this is inferred purely from code-path/order analysis of `MaintenanceManager.doMaintenance()` and `IncentiveManager.reward()`. A concrete PoC would require reproducing the legacy (`allowChangeDelegation() == false`) reward algorithm state on a devnet, casting/removing large votes for a standby witness in the block immediately preceding a maintenance boundary, and comparing the resulting `WITNESS_127` allowance split against the value expected from the pre-vote-change vote distribution.

  public void reward(List<ByteString> witnesses) {
    if (consensusDelegate.allowChangeDelegation()) {
      return;
    }
    if (witnesses.size() > WITNESS_STANDBY_LENGTH) {
      witnesses = witnesses.subList(0, WITNESS_STANDBY_LENGTH);
    }
    long voteSum = 0;
    for (ByteString witness : witnesses) {
      voteSum += consensusDelegate.getWitness(witness.toByteArray()).getVoteCount();
    }
    if (voteSum <= 0) {
      return;
    }
    long totalPay = consensusDelegate.getWitnessStandbyAllowance();
    for (ByteString witness : witnesses) {
      byte[] address = witness.toByteArray();
      long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay
          / voteSum));
      AccountCapsule accountCapsule = consensusDelegate.getAccount(address);
      accountCapsule.setAllowance(accountCapsule.getAllowance() + pay);
      consensusDelegate.saveAccount(accountCapsule);
    }
  }
