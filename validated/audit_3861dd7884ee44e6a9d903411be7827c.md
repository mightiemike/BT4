### Title
Missing sanity check after non-hardened Exchange (Bancor) balance update permanently corrupts pool reserves - ([File: actuator/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes new bancor-style reserve balances for a TRC10/TRX exchange pool and writes them back to the `Exchange` record, but the post-update sanity check that a resulting balance must be non-negative is only executed when `hardenedCalc` is `true`. When the exchange runs in its default (non-hardened) mode, an updated record with a negative `firstTokenBalance`/`secondTokenBalance` is accepted and persisted, corrupting the last stored state of the exchange for all future trades — directly analogous to the reported class of bug: "lack of sanity checks after record update" that lets an incorrect record permanently poison subsequent validation/matching logic.

### Finding Description
`ExchangeCapsule.transaction()` [1](#0-0)  computes `newFirstTokenBalance`/`newSecondTokenBalance` using either the hardened `SafeExchangeProcessor` or the legacy `ExchangeProcessor` (bancor formula using floating-point `Math.pow`), and only guards against negative resulting balances when `hardenedCalc` is `true`: [2](#0-1) 

`ExchangeTransactionActuator.doValidate()` calls `exchangeCapsule.transaction(...)` for validation and again in `execute()` for the mutating call, gated by `allowHarden()` [3](#0-2) [4](#0-3) . The only other checks performed by `doValidate()` are that the *current* (pre-trade) balances are non-zero and that the post-trade balance stays under an upper `balanceLimit`; there is no lower-bound / non-negative check on the computed reserves when the hardened path is disabled: [5](#0-4) .

Because the legacy `ExchangeProcessor` performs its math with `double` arithmetic and `Math.pow` [6](#0-5) , extreme or edge-case inputs (very large `sellTokenQuant` relative to the pool, or repeated/rounding-driven precision loss) can drive `buyTokenQuant` above the actual reserve, producing a negative `newFirstTokenBalance`/`newSecondTokenBalance` that is written back into the store unchecked via `Commons.putExchangeCapsule(...)` [7](#0-6) . Once persisted, this corrupted record is not caught by `doValidate()`'s zero-balance guard (`firstTokenBalance == 0`), since a negative value is not zero — future trades against the pool will operate on a permanently poisoned reserve, similar to how the mETH oracle's last record could be poisoned by an update that skips inter-record consistency checks.

This is directly reachable by any unprivileged account broadcasting an `ExchangeTransactionContract` transaction (`ExchangeTransactionActuator`), unlike the original mETH finding, which required a privileged `ORACLE_MODIFIER_ROLE` holder — making this java-tron analog exploitable without any special privilege.

### Impact Explanation
A corrupted (negative) reserve balance for an Exchange (TRC10 <-> TRX or TRC10 <-> TRC10 bancor pool) breaks price computation for all subsequent `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` operations against that pool, since the bancor formulas in `ExchangeProcessor`/`ExchangeCapsule.transaction()` assume non-negative reserves. This can permanently deny/lock the exchange (denial of service for that market) or, depending on subsequent computation paths, allow a trader to extract disproportionate value at other participants' expense, mirroring the reported accounting-corruption/exchange-rate-manipulation impact.

### Likelihood Explanation
Exploitability depends on being able to construct trade parameters (pool reserves and `sellTokenQuant`) that push the bancor computation past reserve limits under floating point arithmetic — this requires precise crafting but is achievable by any account able to fund the trade, with no special role required. The hardened path (`SafeExchangeProcessor` plus the `hardenedCalc` non-negative check) exists specifically to prevent this, and is gated behind the `AllowHardenExchangeCalculation` dynamic property, so any network where that property is not yet enabled remains exposed.

### Recommendation
Apply the same non-negative-balance sanity check unconditionally (not only under `hardenedCalc`) in `ExchangeCapsule.transaction()`, i.e., always reject the update if `newFirstTokenBalance < 0 || newSecondTokenBalance < 0`, regardless of the hardened/legacy processor path. Consider also validating that consecutive Exchange record updates preserve accounting invariants (e.g., that both first and second token balances remain positive) before persisting the record, and prioritize enabling `AllowHardenExchangeCalculation` network-wide.

### Proof of Concept
Exact numeric inputs that trigger the negative-balance branch under the legacy `ExchangeProcessor`'s floating point/`Math.pow`-based bancor formula could not be confirmed from static code review alone; this would require dynamic testing (e.g., extending `ExchangeCapsuleTest`/`ExchangeTransactionActuatorTest`, which already contain analogous "overflow"/"precision" test scaffolding at [8](#0-7) ) to brute-force or analytically derive an input where `buyTokenQuant` computed by `ExchangeProcessor.exchange()` exceeds the counter-reserve, causing `secondTokenBalance - buyTokenQuant < 0` (or vice versa) in the non-hardened `ExchangeCapsule.transaction()` path [9](#0-8) , then submitting that as an `ExchangeTransactionContract` and confirming the persisted `ExchangeCapsule` balance goes negative and is accepted without a `ContractValidateException`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
