### Title
Uncaught `TypeError` in `sanitizeHost` when base64 `host` decodes to bytes containing forbidden URL host code points - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` validates the base64 charset of `host` but never validates or catches errors from decoding it and feeding it into `new URL()`. Because `decodeHost` uses `atob`, which produces a raw byte string (not sanitized UTF-8/URL-safe text), an attacker can craft a base64 `host` value that decodes into characters forbidden in URL hosts (e.g. NUL, `@`, `\`, `#`, `?`, whitespace). The WHATWG `URL` parser throws a `TypeError: Invalid URL` for such input, and since `sanitizeHost` has no try/catch around `new URL(...)`, that exception propagates uncaught out of the function instead of being converted into an `InvalidHostError` or a `null` return.

### Finding Description
`sanitizeHost` in [1](#0-0) . `decodeHost` is a thin wrapper over `atob`: [2](#0-1) . `atob` decodes base64 into a binary string where each character is an arbitrary byte value 0x00–0xFF — it performs no UTF-8 or URL-safety validation. Any byte sequence is valid base64 input as long as it satisfies the charset regex `^[0-9a-zA-Z+/]+={0,2}$`, which only constrains the *encoded* text, not the decoded bytes.

If the decoded bytes contain a WHATWG "forbidden host code point" (NUL, TAB, LF, CR, space, `#`, `/`, `:`, `<`, `>`, `?`, `@`, `[`, `\`, `]`, `^`, `|`) positioned in the host portion of the constructed URL string, Node's `URL` constructor throws `TypeError: Invalid URL` synchronously. This is uncaught in `sanitizeHost`.

This function is called directly from request-handling code paths without a wrapping try/catch, e.g. `validateShopAndHostParams` in the Remix and React Router adapters: [3](#0-2) , and from `buildEmbeddedAppUrl`/`getEmbeddedAppUrl`: [4](#0-3) . None of these call sites wrap the call in try/catch either, so an uncaught `TypeError` propagates up through the embedded-admin auth route, crashing/erroring the request handler with an unhandled exception instead of the intended graceful `InvalidHostError`/redirect-to-login behavior.

The existing test suite [5](#0-4) , confirming this input class is untested and unhandled.

### Impact Explanation
This matches the "DoS in an authentication handler" impact class from the rules. Any unprivileged HTTP client can send a single crafted `host` query parameter to any embedded-admin auth route (e.g. the `authenticate.admin`/login/callback routes in `shopify-app-remix`, `shopify-app-react-router`, or a call to `getEmbeddedAppUrl`) and cause an unhandled `TypeError` to be thrown during request processing. Depending on the host framework's error handling this can crash the process (unhandled promise rejection) or, at minimum, produce a 500 error instead of the expected sanitized `null`/`InvalidHostError` behavior, violating the stated invariant that destination allowlisting must never throw unhandled errors on attacker input.

### Likelihood Explanation
Fully reachable with default configuration and no privileges: the attacker only needs to base64-encode a byte sequence containing a forbidden host code point (e.g. bytes for `"@"` or NUL) and pass it as `host=` on any embedded-admin request. This is trivially scriptable/fuzzable and 100% reproducible — no secrets, signatures, or race conditions required.

### Recommendation
Wrap the `new URL(...)` call in `sanitizeHost` in a try/catch, treating any parse failure as an invalid host (returning `null` or throwing `InvalidHostError` when `throwOnInvalid` is set), consistent with how `sanitizeShop` handles invalid input via regex testing rather than exception-prone parsing. Alternatively, validate that the decoded bytes form valid UTF-8 and contain no forbidden host code points before constructing the `URL`.

### Proof of Concept
```javascript
// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('sanitizeHost does not throw on malicious decoded host bytes', () => {
  const shopify = shopifyApi(testConfig());

  // decodes to "my-shop.myshopify.com/admin@evil" -> contains '@' which is a
  // forbidden host code point once placed in the URL host portion
  const maliciousHost = Buffer.from(
    'my-shop.myshopify.com\x00/admin',
  ).toString('base64');

  // This currently throws an uncaught TypeError ("Invalid URL") instead of
  // returning null or throwing InvalidHostError.
  expect(() => shopify.utils.sanitizeHost(maliciousHost)).not.toThrow(TypeError);
});
```
Expected (current buggy) behavior: `new URL('https://my-shop.myshopify.com\x00/admin')` throws `TypeError: Invalid URL`, which escapes `sanitizeHost` uncaught, failing the assertion above and crashing any caller (e.g. `validateShopAndHostParams`) that does not itself wrap the call in try/catch.
