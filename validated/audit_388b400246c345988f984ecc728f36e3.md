This confirms a well-documented, acknowledged design gap in the bandwidth scheduler's handling of the *sender-side* missing chunk case: the `max_shard_bandwidth` incoming cap on a receiver shard is a hard invariant the protocol is supposed to enforce, but it can be exceeded through perfectly ordinary, unprivileged user activity once a chunk is missed anywhere on the sender path — matching the LooksRare bug class (a hard per-round/per-shard cap that holds under the "happy path" check-then-act sequence but breaks once an intervening, non-attacker-controlled state change — pause/unpause there, a missed chunk here — reopens the admission window before the cap can be re-enforced).### Title
Bandwidth scheduler's `max_shard_bandwidth` incoming-receipt cap can be exceeded when a sender-side chunk is missed, causing unbounded incoming-receipt accumulation and oversized state witnesses - (File: `runtime/runtime/src/bandwidth_scheduler/scheduler.rs`)

### Summary
The bandwidth scheduler is designed to enforce a hard per-shard invariant: no shard should ever receive more than `max_shard_bandwidth` bytes of receipts at a given height [1](#0-0) . This is analogous to LooksRare's `MAXIMUM_NUMBER_OF_DEPOSITS_PER_ROUND` invariant. Just as that cap was checked at the "close the round" boundary but not re-enforced on every entry path once a pause/unpause created a gap, the NEAR bandwidth scheduler only prevents cap violation for the *receiver-missing-chunk* case, but explicitly does **not** prevent it for the *sender-missing-chunk* case, which the code comments themselves acknowledge as unresolved.

### Finding Description
`calculate_is_link_allowed` blocks a link only when the **receiver's** last chunk was missing (`receiver_status.last_chunk_missing`) or when the **sender's** last chunk was missing at the height the grant is being computed for [2](#0-1) . This only stops the scheduler from granting bandwidth for the height at which the sender/receiver chunk is missing — it cannot prevent receipts that were already sent by the sender at a prior (non-missing) height, and are simply queued in transit, from arriving at the receiver once the sender's chunk resumes.

The module doc explicitly states the unresolved gap: when chunks are missing on the **sender's** shard, receipts already forwarded before the miss are only delivered whenever the sender's chunk finally resumes — which "could be arbitrarily far into the future" — and in the meantime other (unaffected) shards continue to legitimately receive fresh bandwidth grants and keep sending receipts to the same receiver. When the delayed batch and the fresh batch land in the same or nearby heights, the receiver can receive more bytes than `max_shard_bandwidth` in a single window [3](#0-2) .

This is not a hypothetical: it is asserted directly by an in-repo (currently `#[ignore]`d) test that documents the violated invariant:

```
// Incoming max_shard_bandwidth is not respected! When a chunk is missing, the receipts that
// were sent previously will arrive later and they can mix with other incoming receipts, and the
// receiver can receive more than max_shard_bandwidth of receipts :/
// TODO(bandwidth_scheduler) - prevent shard from having too many incoming receipts
assert!(summary.max_incoming > summary.max_shard_bandwidth);
``` [4](#0-3) 

The protocol spec for cross-shard congestion also flags this as an open, unmitigated design gap: "the receiving shard could receive more receipts than it should. This is harder to deal with, the current version of bandwidth scheduler doesn't have a mechanism to prevent that." [5](#0-4) 

The trigger event ("sender chunk missing") is not itself attacker-controlled, but — exactly like the LooksRare bug where the trigger was an admin pause outside the depositor's control — once that condition occurs, ordinary, unprivileged user transactions on unrelated shards are sufficient to push the receiver shard's incoming receipt volume past the hard cap the protocol was designed to enforce.

### Impact Explanation
`max_shard_bandwidth` exists specifically to bound the size of the incoming receipt backlog that ends up embedded in `ChunkStateWitness`, and the state-witness size budget is built assuming this bound holds (the whole `outgoing_receipts_usual_size_limit`/`outgoing_receipts_big_size_limit` accounting in the witness-size doc assumes bandwidth-scheduler enforcement) [6](#0-5) . If a receiver shard accumulates receipts beyond the modeled cap, the resulting `ChunkStateWitness` can grow beyond the ~21 MiB design budget, risking outsized witnesses that are costly/slow to distribute and validate, and, depending on downstream hard limits, could contribute to chunk-validation failures or state-root divergence between honest nodes computing congestion/bandwidth state under different assumptions about incoming volume.

### Likelihood Explanation
Missing chunks are a routine occurrence on NEAR (temporary validator unavailability, network jitter) and require no malicious action — they are explicitly modeled and tested with a 10% probability in the linked simulation test [7](#0-6) . Once a sender-side miss occurs, the condition is triggered purely by continued, unprivileged cross-shard transaction activity from other shards — no coordination or special privilege needed, mirroring the LooksRare scenario where ordinary depositors (not the pausing admin) completed the invariant violation.

### Recommendation
Implement the improvement already outlined in the module's own "Future improvements" section: track, for a receiver shard, how much bandwidth was already granted-but-not-yet-delivered by senders currently missing chunks, and withhold new grants to that receiver from other senders until the backlog is accounted for, or cap total incoming bytes across a rolling window rather than per-height-grant only [8](#0-7) .

### Proof of Concept
The existing (currently disabled) integration test already reproduces and asserts the violation end-to-end: run a multi-shard scenario with `missing_chunk_probability(0.1)` for 2000 heights and observe `summary.max_incoming > summary.max_shard_bandwidth`, i.e., a receiver shard received more incoming receipt bytes in a window than the configured `max_shard_bandwidth` invariant permits [9](#0-8) .

//! ## Missing chunks
//!
//! Special care has to be taken to handle missing chunks. When a chunk is missing, it doesn't
//! process the receipts that were sent to it at previous heights. If other shards keep sending
//! receipts to the shard with missing chunks, these receipts will accumulate and the size of
//! incoming receipts can grow into infinity. This would also mean that the state witness for the
//! next chunk would be huge, which would cause problems.
//!
//! Bandwidth scheduler handles this using a simple rule - if the last chunk was missing on some
//! shard, don't send any receipts to this shard, it still hasn't processed the previous ones.
//! This rule is enough to ensure that a shard doesn't send too much to another shard that has
//! missing chunks.
//!
//! The situation is worse when the chunks are missing on the sender shard. Receipts sent during
//! previous chunk's application are received when the next non-missing chunk on the sender shard
//! appears. This could be arbitrarily far into the future and in the meantime other shards could
//! send receipts to the same receiver, and the receiver could receive more receipts than it should.
//! This is harder to deal with, the current version of bandwidth scheduler doesn't have a mechanism
//! to prevent that.
//!
//! Future improvements:
//! a) Add proper handling of missing chunks on sender shard. The scheduler could look at how much
//!    was granted on other senders which have missing chunks and forbid producing too many receipts
//!    to a receiver.
//!
//! b) It's a bit wasteful to not send anything when a chunk is missing. We could track how much a
//!    shard already sent to the shard with missing chunks at previous heights, and allow to send
//!    receipts to it, but make sure that their total size doesn't exceed the grant that was given when
//!    the chunk wasn't missing. This would improve bandwidth utilization in scenarios with many
//!    missing chunks.

    /// Decide if it's allowed to send receipts on the link, based on shard statuses.
    /// Makes sure that receipts are not sent to fully congested shards or shards with missing chunks.
    fn calculate_is_link_allowed(
        sender_index: ShardIndex,
        receiver_index: ShardIndex,
        shards_status: &ShardIndexMap<ShardStatus>,
    ) -> bool {
        let Some(receiver_status) = shards_status.get(&receiver_index) else {
            // Receiver shard status unknown - don't send anything on the link, just to be safe.
            return false;
        };

        if receiver_status.last_chunk_missing {
            // The chunk was missing, receipts sent previously were not processed.
            // Don't send anything to avoid accumulation of incoming receipts on the receiver shard.
            return false;
        }

        let sender_status_opt = shards_status.get(&sender_index);
        if let Some(sender_status) = sender_status_opt {
            if sender_status.last_chunk_missing {
                // The chunk on sender's shard is missing. Don't grant any bandwidth on links from a shard
                // that is missing and won't send out anything at this height.
                // Bandwidth scheduler calculates outgoing bandwidth for chunks that are currently
                // being applied. The sender's chunk is not being applied right now, so it wouldn't
                // send out any receipts, it'd be wasteful to grant bandwidth on this link.
                return false;
            }
        }
