### Title
Local-admin role hijack via email-based lookup precedence over authenticated LDAP bind identity - ([File: core/sessions/ldapauth/ldap.go])

### Finding Description
In `CreateSession`, the attacker-supplied `sr.Email`/`sr.Password` is used to `conn.Bind` against a DN built from that email [1](#0-0) . Immediately after, the *same* email string is passed to `l.FindUser(ctx, escapedEmail)` to determine the role for the new session [2](#0-1) .

Inside `FindUser`, the very first thing done is an unconditional, case-insensitive lookup against the local `users` table; if a row matches, that row (and its `Role`) is returned immediately, with **no verification whatsoever that the caller actually authenticated as that local admin** (no password check, no comparison against the bind DN) [3](#0-2) . The function never checks whether the credential that produced a successful bind belongs to the LDAP-verified identity or to an unrelated local admin row that merely shares the same email string.

Because `returnErr` is only set when the LDAP bind fails or `FindUser` errors, a successful bind combined with a local-table hit leaves `returnErr == nil`, so the `localLoginFallback` path (which does perform a real password check via `utils.CheckPasswordHash`) is never invoked [4](#0-3) . The resulting session is persisted with `foundUser.Role` (the local admin's role) and `isLocalUser=false`, meaning the session appears to be a legitimately LDAP-authenticated session, while the granted role was never checked against the group membership of the DN that was actually bound, nor was the local admin's password ever verified [5](#0-4) .

The invariant that is violated: role assignment must bind to the identity that was actually authenticated (the bind DN's LDAP group membership), not to a secondary email-string lookup performed after the fact.

### Impact Explanation
If any local `users` table row's email matches (case-insensitively) the email of an LDAP-bindable account that a lower-privileged user controls, that user is granted the local row's role — up to Admin — purely by successfully binding with their own (non-admin) LDAP credentials. This is a full privilege escalation to Admin without ever presenting or matching the local admin's actual password.

### Likelihood Explanation
This requires a specific precondition: the local `users` table (used for CLI/bootstrap admin accounts) contains an email that coincides, case-insensitively, with the login (`uid`) of an LDAP account the attacker controls. This is plausible in deployments where the CLI bootstrap admin email is a well-known/default value (e.g., an operator-configured admin email) that also happens to exist, or can be provisioned/guessed, as an LDAP-bindable identity — but it does depend on this email overlap existing, which is an operational/configuration condition outside pure attacker control. The code-level defect (unconditional local-table precedence with no cross-check to the authenticated bind identity) is unconditionally present regardless of whether this precondition is currently met in any given deployment.

### Recommendation
In `FindUser`/`CreateSession`, do not let a local `users` table match short-circuit role resolution for an LDAP bind. Specifically:
- Only consult the local `users` table fallback when the LDAP bind/directory lookup did not resolve the identity (as is already done later in `FindUser` at the "no LDAP entries found" branch), not unconditionally first.
- In `CreateSession`, only treat a user as "local" (and grant a local role) when the local password was actually verified via `localLoginFallback`; never assign a local table's role based purely on a successful LDAP bind plus an email string match.
- Consider requiring exact (not case-folded) email matching between the bind DN and any local-table role source, and log/alert on such email collisions between local and directory identities.

### Proof of Concept
Integration test in `core/sessions/ldapauth`:
1. Configure a fake LDAP server (via the existing `LDAPClient`/mock conn used in tests) so that binding as `attacker@example.com` with password `attackerpass` succeeds, and the group search for that email returns only the "Read" group.
2. Seed the local `users` table with a row `email='Attacker@example.com'`, `role='admin'`, `hashed_password=<unrelated hash>`.
3. Call `CreateSession(ctx, sessions.SessionRequest{Email: "attacker@example.com", Password: "attackerpass"})`.
4. Assert that the returned session's role (as stored in `ldap_sessions.user_role`) is `UserRoleView`/`UserRoleRead` (matching the actual LDAP group), and specifically assert it is **not** `UserRoleAdmin`, unless `localLoginFallback`'s password check against the local admin's `hashed_password` was actually performed and succeeded.
