Based on my research, I found a credible analog: a reserved "bootstrap" sender address that is intended only for genesis/bootstrap class declarations, but for which I could not find any explicit gateway-side denylist preventing an ordinary declare-transaction sender from using it.

### Title
Unauthorized use of the reserved `BOOTSTRAP` declarer address bypasses `__validate_declare__`, fee charge, and nonce enforcement - (File: crates/starknet_api/src/executable_transaction.rs)

### Summary
The protocol defines a hardcoded, publicly-known "bootstrap" sender address (`ContractAddress::from(0x424f4f545354524150_u128)`, the felt-encoding of the string `"BOOTSTRAP"`) that is meant to let the sequencer itself declare core classes at genesis without running `__validate_declare__`, charging a fee, or bumping a nonce. [1](#0-0) 
Neither the gateway's declare-authorization check nor its stateless validation appears to explicitly reject a transaction whose `sender_address` equals this reserved constant, i.e., the special-case bypass in transaction execution is reachable through the normal, permissionless `add_tx` transaction-submission path.

### Finding Description
The bootstrap short-circuit is implemented identically in both the Rust blockifier and the Starknet OS Cairo program:
- Rust: `AccountTransaction::execute_raw` checks `tx.is_bootstrap_declare(charge_fee)` and, if true, skips `perform_pre_validation_stage` (nonce/fee pre-checks) and the whole validate/execute/fee-charge flow, running only `run_execute` to record the class declaration. [2](#0-1) 
- Cairo OS: the same condition (`sender_address == 'BOOTSTRAP' and tx_info.nonce == 0 and tx_info.version == 3`, with `max_possible_fee == 0`) skips `check_and_increment_nonce` and the `__validate_declare__` call entirely, directly writing the class-hash → compiled-class-hash mapping. [3](#0-2) 

`is_bootstrap_declare` is defined purely in terms of `sender_address`, `nonce`, and `charge_fee` — it performs no additional authentication of *who* is allowed to submit such a transaction: [4](#0-3) 

On the gateway side, the only declare-specific authorization gate is `check_declare_permissions`, which is skipped entirely unless the operator has configured `authorized_declarer_accounts`. Its default value is `None`, and `is_authorized_declarer` explicitly treats `None` as "any address is authorized": [5](#0-4) [6](#0-5) 

The default/most deployment configs I found ship with `authorized_declarer_accounts` unset (`#is_none: true`), meaning any account can submit a `Declare` transaction, including one using `sender_address = bootstrap_address()`: [7](#0-6) [8](#0-7) 

Stateless validation (`StatelessTransactionValidator::validate`) also has no check preventing the bootstrap address as a declare sender; it only validates the address format, empty deployment/paymaster data, resource bounds, sizes, and DA modes — none of which single out or reject the reserved constant: [9](#0-8) 

This mirrors the reported bug class: a normal, unprivileged "write"/"send" operation (submitting a `Declare` RPC transaction) is able to reach an admin/operator-only code path (the no-validation, no-fee, no-nonce bootstrap declare branch) because the authorization boundary between "ordinary declarer" and "the bootstrap identity" is not enforced.

### Impact Explanation
If an external, unprivileged account can successfully trigger the `is_bootstrap_declare` branch, it could:
- Declare a class while completely bypassing `__validate_declare__` (no signature/account-based authorization at all) and nonce enforcement — an unauthorized account action performed under the identity of the protocol-reserved `BOOTSTRAP` account.
- Front-run/squat specific class hashes that a legitimate genesis bootstrap sequence would need to declare, since the OS enforces `prev_value=0` (a class hash may be declared only once) — this could disrupt or permanently block legitimate chain-bootstrap declarations for well-known deterministic class hashes (e.g., standard account/token classes), a freezing-style impact on network initialization.

### Likelihood Explanation
This is uncertain and I was not able to fully confirm end-to-end exploitability in the time available. The bootstrap branch additionally requires `!charge_fee` (`execution_flags.charge_fee == false`), which is derived from `enforce_fee(executable_tx, only_query)`; I could not locate and inspect the exact logic of `enforce_fee` to determine whether an externally-submitted, non-query `Declare` V3 transaction can ever have `charge_fee == false` while still passing the gateway's `validate_resource_bounds` stateless check (which rejects zero resource bounds when `validate_resource_bounds` is enabled). If `enforce_fee` unconditionally returns `true` for real (non-query) V3 declares reaching consensus/execution, the bypass would only be reachable via internally-generated bootstrap transactions (as in the `generate_bootstrap_declare` test helper), which would make this non-exploitable by an ordinary sender and reduce the severity substantially. [10](#0-9) 

### Recommendation
- Explicitly reject any incoming `Declare` transaction (or any transaction at all) whose `sender_address` equals `DeclareTransaction::bootstrap_address()` at the gateway's stateless/declare-permission check, regardless of `authorized_declarer_accounts` configuration, unless the transaction is produced/injected through a trusted, internal bootstrap-only path (not the public `add_tx` entry point).
- Audit `enforce_fee` to confirm whether `charge_fee == false` is reachable for any externally-submitted transaction, and if so, tie the bootstrap fee-exemption to an explicit internal/administrative flag rather than to the sender address alone.

### Proof of Concept
Not fully verified end-to-end given open questions about `enforce_fee`. Conceptually: craft an `RpcTransaction::Declare(V3)` with `sender_address = DeclareTransaction::bootstrap_address()` (`0x424f4f545354524150`), `nonce = 0`, and resource bounds/fee parameters mirroring those used by `generate_bootstrap_declare` (`ValidResourceBounds::create_for_testing_no_fee_enforcement()`), and submit it through the public gateway `add_tx`. If it is admitted and `charge_fee` resolves to `false` during execution, the class is declared without `__validate_declare__`, fee, or nonce checks, exactly as exercised by the existing test `test_bootstrap_declare`. [11](#0-10)

    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

fn test_bootstrap_declare(
    block_context: BlockContext,
    #[case] declare_tx: DeclareTransaction,
    #[case] hash_version: HashVersion,
) {
    let class_info = calculate_class_info_for_testing(
        FeatureContract::Empty(CairoVersion::Cairo1(RunnableCairo1::Casm)).get_class(),
    );
    let contract_class = class_info.contract_class();
    let mut executable_declare = ApiExecutableDeclareTransaction {
        tx: declare_tx.clone(),
        tx_hash: TransactionHash::default(),
        class_info,
    };

    // Update compiled_class_hash in V3 declare txs to match the contract class with the given hash
    // version.
    if let DeclareTransaction::V3(tx) = &mut executable_declare.tx {
        if let ContractClass::V1((casm, _)) = &contract_class {
            tx.compiled_class_hash = casm.hash(&hash_version);
        }
    }
    let compiled_class_hash = executable_declare.tx.compiled_class_hash();
    let declare_account_tx = AccountTransaction::new_for_sequencing(
        ApiExecutableTransaction::Declare(executable_declare),
    );

    let mut state = CachedState::from(DictStateReader::default());
    let res = declare_account_tx.execute(&mut state, &block_context).unwrap();

    // Check declaration.
    assert_eq!(
        state.get_compiled_class_hash(declare_tx.class_hash()).unwrap(),
        compiled_class_hash
    );

    // Ensure the only change is the class declaration: no fees, nonce bump, etc.
    assert_eq!(res, TransactionExecutionInfo::default());
    assert_eq!(
        state.to_state_diff().unwrap().state_maps,
        StateMaps {
            compiled_class_hashes: HashMap::from([(declare_tx.class_hash(), compiled_class_hash)]),
            declared_contracts: HashMap::from([(declare_tx.class_hash(), true)]),
            ..Default::default()
        }
    );
}
