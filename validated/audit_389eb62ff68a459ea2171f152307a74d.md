### Title
ExchangeWithdrawContract has no minimum-output ("expected") slippage protection, unlike ExchangeTransactionContract - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawContract` lets a bancor-style exchange's creator withdraw liquidity by specifying only the `token_id` and `quant` to withdraw; the "another token" amount returned is computed at execution time from the current pool ratio, with no user-supplied minimum-acceptable-amount field, unlike the sibling `ExchangeTransactionContract` which has an explicit `expected` field enforced at validation time.

### Finding Description
The `ExchangeWithdrawContract` protobuf message only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum-output parameter: [1](#0-0) 

In `ExchangeWithdrawActuator.execute`, the `anotherTokenQuant` (the counter-asset amount paid out to the withdrawer) is derived purely from the exchange pool balances that exist *at execution time* using the constant-ratio formula, and this value is paid out unconditionally: [2](#0-1) 

The only checks in `doValidate()` guard against balances being drained to zero and against BigDecimal rounding "precision loss" (the `allowHarden`/`"Not precise enough"` check) — neither of these protects the user against the pool ratio moving between the time the transaction is signed/broadcast and the time it is executed in a block: [3](#0-2) 

Contrast this with `ExchangeTransactionContract`/`ExchangeTransactionActuator`, which does carry a user-specified `expected` field, and explicitly reverts if the actual output is below what the user expected: [4](#0-3) [5](#0-4) 

This is directly analogous to the Yearn `YearnTokenAdapter.unwrap()` bug: the hardcoded `MAXIMUM_SLIPPAGE` (10,000/100%) means the withdraw call has no protection against unfavorable price movement and unconditionally accepts whatever amount the underlying mechanism returns. Here, `ExchangeWithdrawActuator` has the analogous gap: no `expected`/`minAmountOut` parameter exists at all for withdrawals, whereas the trade-path (`ExchangeTransactionContract`) does have this protection, showing the protocol designers recognized the need for slippage protection in one path but omitted it in the other.

### Impact Explanation
An exchange creator submitting `ExchangeWithdrawContract` has no way to bound the amount of counter-asset they will receive. Between broadcast and block inclusion, other market participants can execute `ExchangeTransactionContract` trades against the same `exchange_id` to shift the first/second token balance ratio (front-running/sandwiching the pending withdrawal), causing the withdrawer to receive significantly less counter-asset value than they intended, with the withdrawal still executing successfully (no revert). This is a concrete loss-of-funds / value-extraction vector against the exchange creator, matching the "underpriced-public-work"/settlement-impact category since a state-changing settlement occurs without any way for the initiator to bound their loss.

### Likelihood Explanation
Any account that is the creator of a Bancor-style exchange pair can trigger a withdrawal via `ExchangeWithdrawContract`, and any user can submit `ExchangeTransactionContract` trades to move the pool ratio before the withdraw transaction is packed into a block — this requires no privileged role, only normal wallet/API access and awareness of pending transactions (e.g. via mempool observation), making the attack practically executable rather than theoretical.

### Recommendation
Add an `expected`/minimum-output field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()`, reverting with a clear error (e.g. "another token amount less than expected") if the computed `anotherTokenQuant` falls below the caller-specified minimum.

### Proof of Concept
1. User A creates an exchange pair and later submits `ExchangeWithdrawContract{exchange_id, token_id=firstTokenID, quant=X}` expecting to receive `Y` of the second token, based on the pool ratio visible when they signed the transaction (see ratio computation in `ExchangeWithdrawActuator.execute`, lines 74-89): [6](#0-5) 
2. Before A's transaction is included in a block, an attacker submits an `ExchangeTransactionContract` trade against the same exchange, shifting `firstTokenBalance`/`secondTokenBalance` unfavorably for A.
3. A's `ExchangeWithdrawContract` executes successfully (no revert possible since there is no `expected` field to check against), and A receives an `anotherTokenQuant` far lower than `Y`, with the loss realized permanently and no slippage-based recourse — see the absence of any bound check comparable to `ExchangeTransactionActuator`'s `anotherTokenQuant < tokenExpected` guard: [5](#0-4)
