### Title
`ValidateMultiSign` precompile double-counts a single signer's weight via duplicate-address dedup bypass - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Finding Description
The `ValidateMultiSign` precompile is reachable by any unprivileged smart contract via a normal `staticcall`/`call` to the precompile address, passing an arbitrary victim `address`, `permissionId`, `dataHash`, and an attacker-supplied array of signature byte strings [1](#0-0) .

The weight-accumulation loop is the root cause: [2](#0-1) 

For each signature, `recoveredAddr` is derived and then `sign` is redefined as `merge(recoveredAddr, sign)`. The de-duplication logic only skips the current entry (`continue`) if the *exact byte-for-byte* merged value (`recoveredAddr || rawSignatureBytes`) was already recorded in `executedSignList`. If `recoveredAddr` was already seen but the raw signature bytes differ even slightly (different padding, trailing bytes, or an ECDSA-malleable `(r, n-s)` re-encoding that still recovers to the same address), the code does **not** skip the entry — it only invokes `MUtil.checkCPUTime()` (a CPU/DoS throttle, not a security check) and then falls straight through to `TransactionCapsule.getWeight(permission, recoveredAddr)` and `totalWeight += weight`, adding the same signer's weight a second time.

Because the dedup key is the raw signature bytes rather than the canonical recovered address, an attacker who holds only **one** valid signature from **one** authorized key of the victim's permission can:
1. Derive a second, byte-distinct but validly-recovering signature for the same message/key (e.g., via ECDSA `s -> n-s` malleability with adjusted recovery id, or by appending/altering non-significant padding bytes if the recovery routine tolerates it).
2. Submit `sigs = [sigA, sigA_variant]` to `ValidateMultiSign`.
3. Both entries recover to the same `recoveredAddr`, but since the merged byte arrays differ, the `continue` path is never taken, and `totalWeight` is incremented twice for the same key.
4. If `2 * weight(signerA) >= permission.getThreshold()`, the precompile returns "valid" even though only one authorized signer actually cooperated.

This defeats the invariant that no unprivileged actor can satisfy a multi-signature threshold without independently obtaining signatures from distinct authorized keys.

### Impact Explanation
`ValidateMultiSign` is used by contracts to authorize privileged actions gated on a victim account's permission threshold (e.g., custom multisig-gated contract logic, escrow, exchange-related authorization flows referenced in the prompt). If a contract trusts this precompile's boolean result to authorize a transfer or state change, an attacker with a single leaked/observed signature (many Tron signatures are publicly visible on-chain) can spoof satisfaction of a `threshold>1` permission, enabling unauthorized execution of victim-gated logic without collecting independent signer approvals.

### Likelihood Explanation
Preconditions match realistic conditions: any account with an Active permission of `keysCount>1`, `threshold>1` is a candidate, and permission/signature data (including a valid signature captured from a prior broadcast transaction referencing that permission) is public on-chain. The attacker needs no privileged access — only the ability to deploy and call a contract, which is unrestricted. The exploit is deterministic and repeatable given one authentic signature and a signature-malleability/padding transform.

### Recommendation
Change the de-duplication key in the `ValidateMultiSign`/`BatchValidateSign` loops from raw-signature-byte equality to `recoveredAddr` equality only: once `recoveredAddr` has been recorded, always `continue` (skip weight accumulation) regardless of whether the exact signature bytes match, removing the `checkCPUTime()`-then-fall-through path that permits re-adding weight for an address already counted.

### Proof of Concept
Java unit test (JUnit, similar in structure to `ValidateMultiSignContractTest.java`):
```java
@Test
public void testDuplicateAddressDoubleCountsWeight() {
  // Setup: victim account with Active permission, threshold=6, two keys each weight=3
  Permission permission = buildPermission(threshold=6,
      keys=[keyA(weight=3), keyB(weight=3)]);
  AccountCapsule victim = buildAccount(permission);
  deposit.putAccount(victim);

  byte[] hash = computeHash(victimAddress, permissionId, data);
  byte[] sigA = ECKey.fromPrivate(privA).sign(hash).toByteArray(); // valid sig from keyA
  byte[] sigAVariant = malleateOrRepad(sigA); // same recoveredAddr, different raw bytes

  byte[] rawInput = encodeValidateMultiSignInput(
      victimAddress, permissionId, data, new byte[][]{sigA, sigAVariant});

  Pair<Boolean, byte[]> result = new ValidateMultiSign().execute(rawInput);

  // Expected (fixed) behavior: totalWeight should equal weight(keyA)=3 < threshold(6)
  // => result should be DATA_FALSE
  assertArrayEquals(PrecompiledContracts.DATA_FALSE, result.getRight());

  // Current (vulnerable) behavior: totalWeight = 3+3 = 6 >= threshold(6)
  // => result incorrectly returns dataOne() (true), demonstrating the bug
}
```
Fuzz/invariant extension: generate many `(sigA, sigA_variant)` pairs (paddings, malleable `s` transforms, redundant leading zero bytes) that all recover to the same address, and assert `totalWeight` computed by `ValidateMultiSign.execute` never exceeds the sum of *unique* `recoveredAddr` weights, regardless of raw-byte variation or insertion order.
