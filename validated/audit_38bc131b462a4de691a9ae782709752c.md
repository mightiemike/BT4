### Title
Unregistered/UNRECOGNIZED `Contract.type` causes uncaught `NullPointerException` in `ActuatorFactory.getActuatorByContract` instead of a graceful `ContractValidateException` - (File: `actuator/src/main/java/org/tron/core/actuator/ActuatorFactory.java`)

### Summary
`ActuatorFactory.getActuatorByContract` calls `TransactionFactory.getActuator(contract.getType())` and immediately invokes `clazz.newInstance()` without checking for `null`, unlike the equivalent code path in `ActuatorCreator.getActuatorByContract`, which explicitly null-checks the returned class and throws a `ContractValidateException`. A transaction whose `Contract.type` decodes to `ContractType.UNRECOGNIZED` (an enum value never registered in `TransactionFactory.actuatorMap`) will make `getActuator()` return `null`, producing an uncaught `NullPointerException`.

### Finding Description
`TransactionFactory.actuatorMap` (chainbase/src/main/java/org/tron/core/actuator/TransactionFactory.java) is only populated through `register()` calls performed reflectively by `TransactionRegister.registerActuator()` for concrete `AbstractActuator` subclasses, plus two static hard-coded entries. [1](#0-0) 

`ActuatorFactory.getActuatorByContract` fetches the actuator class for `contract.getType()` and directly calls `clazz.newInstance()` with no null check: [2](#0-1) 

By contrast, `ActuatorCreator.getActuatorByContract` — which serves the same purpose — explicitly checks for `null` and throws `ContractValidateException`: [3](#0-2) 

Because `Protocol.Transaction.Contract.ContractType` is a protobuf enum, any wire value not corresponding to a known enum constant deserializes to `ContractType.UNRECOGNIZED`, which is never present as a key in `actuatorMap`. `ActuatorFactory.createActuator` only catches `IllegalAccessException`/`InstantiationException` around the call, so a `NullPointerException` thrown from `clazz.newInstance()` on a `null` class reference propagates uncaught: [4](#0-3) 

`ActuatorFactory` is referenced from `framework/src/main/java/org/tron/core/Wallet.java`, indicating it is reachable from the transaction-processing/broadcast code path in that class, in contrast to `RuntimeImpl` (TVM execution path), which uses the safer `ActuatorCreator.getINSTANCE().createActuator(...)` API instead.

I was not able to fully confirm within the available tool budget whether `Wallet.java`'s broadcast/push-transaction flow performs a `validateContractType`-style pre-check (a match for `validateContractType` was found in `Wallet.java`) that filters out `UNRECOGNIZED`/unmapped contract types before reaching `ActuatorFactory.createActuator`. If such a check does not cover every code path that invokes `ActuatorFactory.createActuator`, the NPE described above is reachable from attacker-supplied transactions.

### Impact Explanation
If reachable, this is a Denial-of-Service via the TRON protocol implementation: an unprivileged, ordinary funded account (or even an anonymous submitter, depending on whether signature/fee checks occur before or after actuator instantiation) can repeatedly submit malformed transactions to crash or destabilize the RPC worker thread handling `broadcastTransaction`, since the resulting `NullPointerException` is not converted into the intended `ContractValidateException`.

### Likelihood Explanation
The precondition is that the malformed transaction reaches `ActuatorFactory.createActuator` rather than only `ActuatorCreator.createActuator`. This is a genuine code inconsistency (confirmed by direct comparison of the two classes) and represents a real defect regardless of the exact call path taken in `Wallet.java`, but I could not fully verify the runtime reachability/ordering of checks in `Wallet.java`'s broadcast path with the tools available, so exploitability from an external RPC call could not be conclusively confirmed within this session.

### Recommendation
Add the same null-check and typed-exception handling used in `ActuatorCreator.getActuatorByContract` to `ActuatorFactory.getActuatorByContract`:
```java
Class<? extends Actuator> clazz = TransactionFactory.getActuator(contract.getType());
if (clazz == null) {
  throw new ContractValidateException("not exist contract " + contract);
}
```
and ensure `ActuatorFactory.createActuator` propagates/handles this exception the same way `ActuatorCreator.createActuator` does, rather than only catching `IllegalAccessException`/`InstantiationException`.

### Proof of Concept
```java
// JUnit-style PoC illustrating the code-level defect
@Test
public void testUnregisteredContractTypeThrowsNPE() {
  Protocol.Transaction.Contract contract = Protocol.Transaction.Contract.newBuilder()
      .setTypeValue(9999) // out-of-range ordinal -> ContractType.UNRECOGNIZED
      .build();
  Protocol.Transaction.raw raw = Protocol.Transaction.raw.newBuilder()
      .addContract(contract)
      .build();
  Protocol.Transaction tx = Protocol.Transaction.newBuilder().setRawData(raw).build();
  TransactionCapsule capsule = new TransactionCapsule(tx);

  // Expected: ContractValidateException (handled) — actual: NullPointerException
  ActuatorFactory.createActuator(capsule, chainBaseManager);
}
```
Because `TransactionFactory.getActuator(ContractType.UNRECOGNIZED)` returns `null`, `clazz.newInstance()` in `ActuatorFactory.getActuatorByContract` throws `NullPointerException`, which is not caught by the surrounding `catch (IllegalAccessException | InstantiationException e)` block in `ActuatorFactory.createActuator`.
