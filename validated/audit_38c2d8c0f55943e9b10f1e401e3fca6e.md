### Title
Duplicate promise indices in `promise_and` inflate a receipt's data-dependency count, permanently freezing the resulting postponed receipt - (File: `runtime/near-vm-runner/src/wasmtime_runner/logic.rs`)

### Summary
### Finding Description
`promise_and` (`runtime/near-vm-runner/src/wasmtime_runner/logic.rs:2385-2433`) builds a `Promise::NotReceipt(receipt_dependencies)` by iterating over a caller-supplied array of promise indices and, for each one, pushing the underlying `ReceiptIndex` (or extending with all indices of a nested `NotReceipt`) into `receipt_dependencies`: [1](#0-0) 
There is no deduplication: nothing prevents the caller from passing the same `promise_idx` (or the same underlying `receipt_idx`) more than once in `promise_idx_ptr`/`promise_idx_count`. The only check performed is a length limit against `max_number_input_data_dependencies`: [2](#0-1) 

When this joined promise is subsequently used as the base of a new receipt (e.g., via `promise_batch_then`), the receipt-dependency list — now containing the duplicated `receipt_idx` — is passed straight through to `RuntimeExt::create_action_receipt`, which zips it 1:1 with generated `data_id`s and installs an `output_data_receivers` entry on each dependency, then stores the resulting `input_data_ids` verbatim on the new `ActionReceiptMetadata`: [3](#0-2) 

Because the source promise is duplicated, the *same* receipt index appears twice among `receipt_dependencies`, so the loop in `create_action_receipt` allocates **two distinct `data_id`s pointing at the same single underlying receipt**, and both are written into `input_data_ids`.

When the resulting `ActionReceipt` is applied by the runtime, `process_action_receipt` iterates `input_data_ids()` and, for each one not yet received, increments `pending_data_count` and records a `PostponedReceiptId` link: [4](#0-3) 

Since the duplicated dependency really corresponds to only one physical output-producing receipt, at most one matching `Data` receipt with a data_id equal to one of the two synthetic ids can actually ever be produced/delivered for the underlying receipt execution (the underlying receipt only fires once and only routes to the `output_data_receivers` entries actually attached to it — see below), so `pending_data_count` can be initialized to `N` but only ever decremented `N-1` times (or fewer), meaning it never reaches zero. The postponed receipt is written to state via `set_postponed_receipt` and is never picked up again: [5](#0-4) 

This is the direct structural analog of the reported Securitize `_addWallet`/`walletCount` bug: an item (`promise_idx` / `receipt_idx`) is added multiple times into a collection that gates completion of an operation (`pending_data_count` / `walletCount`), without checking whether it is already present, causing an inflated counter that can never be satisfied and permanently blocks/"bricks" the downstream state (there, `removeInvestor`; here, the postponed action receipt and any gas/deposit attached to it).

### Impact Explanation
An unprivileged contract account can call `promise_and` with a repeated promise index and then `promise_batch_then`/`promise_then` on the resulting joint promise. This produces an `ActionReceipt` whose `pending_data_count` can never reach zero, so the receipt is stored as a `PostponedReceipt` in the receiver account's state forever. Any attached balance/gas prepayment on that receipt is permanently locked (receipt never executes, no refund path is triggered for postponed receipts), and the associated trie storage entries (`PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`) remain in state indefinitely, growing unrecoverable storage usage on the account. This matches "permanently frozen funds" / state growth from an unauthorized, self-inflicted but exploitable state-transition defect reachable purely through a `FunctionCall` action from any signer.

### Likelihood Explanation
This requires a contract (deployable by any account) invoking `promise_and` with a duplicated promise index, which is a plain host-function call available to any WASM contract with no special privileges. No validator or node cooperation is needed; it is reachable purely through the standard "function call → promise API" path used by ordinary dApps.

### Recommendation
In `promise_and` (and analogously anywhere `Promise::NotReceipt` dependency lists are constructed), deduplicate `receipt_dependencies` before storing the promise, e.g. collect into a `BTreeSet`/`HashSet` before converting back to `Vec<ReceiptIndex>`, so a given receipt index cannot appear more than once as an input dependency of a newly created receipt. Alternatively, `ReceiptManager::create_action_receipt` should reject (or dedupe) `input_data_ids`/`receipt_indices` containing duplicate `receipt_idx` values, ensuring `pending_data_count` can only ever count each physically-satisfiable dependency once.

### Proof of Concept
Conceptual PoC (host-function level, matching the pattern in the existing estimator contract usage of `promise_and`/`promise_then` at `runtime/near-test-contracts/estimator-contract/src/lib.rs:2074-2098`):
1. Call `promise_create` once to obtain a single promise index `p`.
2. Call `promise_and` with an index array `[p, p]` (the same index twice) — no error is raised because there is no dedup check (`runtime/near-vm-runner/src/wasmtime_runner/logic.rs:2408-2421`).
3. Call `promise_then`/`promise_batch_then` on the resulting joint promise, creating a new `ActionReceipt` whose `input_data_ids` contains two distinct synthetic data ids that both trace back to the single underlying receipt from step 1.
4. When the runtime applies this new receipt, `process_action_receipt` sets `pending_data_count = 2` (`runtime/runtime/src/lib.rs:1662-1709`), but the single underlying promise from step 1 can only ever deliver one `Data` receipt matching one of the two ids, so `pending_data_count` never reaches `0` and the receipt is permanently stuck as a `PostponedReceipt` in state.

Note: I could not fully trace, within the available indexed context, the exact mechanics of how `output_data_receivers` get attached in the wasmtime/near-vm-runner "batch" receipt-creation path (`create_action_receipt` signature differs slightly between `dependencies.rs`/`ext.rs` and `receipt_manager.rs`), so the precise data_id-to-underlying-receipt wiring should be verified end-to-end in a live Devin session before treating this as fully confirmed; the core absence-of-deduplication in `promise_and` and the resulting unguarded `pending_data_count` accumulation in `process_action_receipt`, however, are directly confirmed in the cited code.

        &mut self,
        input_data_ids: Vec<CryptoHash>,
        receipt_indices: Vec<ReceiptIndex>,
        receiver_id: AccountId,
    ) -> Result<ReceiptIndex, VMLogicError> {
        assert_eq!(input_data_ids.len(), receipt_indices.len());
        for (data_id, receipt_index) in input_data_ids.iter().zip(receipt_indices.into_iter()) {
            self.action_receipts
                .get_mut(receipt_index as usize)
                .ok_or(HostError::InvalidReceiptIndex { receipt_index })?
                .output_data_receivers
                .push(DataReceiver { data_id: *data_id, receiver_id: receiver_id.clone() });
        }

        let new_receipt = ActionReceiptMetadata {
            receiver_id,
            refund_to: None,
            output_data_receivers: vec![],
            input_data_ids,
            actions: vec![],
            is_promise_yield: false,
        };
        let new_receipt_index = self.action_receipts.len() as ReceiptIndex;
        self.action_receipts.push(new_receipt);
        Ok(new_receipt_index)
    }
