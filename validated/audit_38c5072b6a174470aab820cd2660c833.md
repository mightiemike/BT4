### Title
Inconsistent gas-key fee calculation between send and exec paths for ML-DSA-65 public keys - (File: runtime/runtime/src/config.rs)

### Summary
`gas_key_send_pk_len` in [1](#0-0)  chooses between `public_key.len()` (wire-encoded length) and `public_key.trie_id_len()` (on-trie/storage length) depending on whether `config.wasm_config.fix_ml_dsa_cost_charging` is enabled, mirroring the audit's pattern where one code path (`swap.rs`) applies a specific high-confidence adjustment while another path (`pool::get_swap_fees`) uses a broader/different criterion for the same fee decision.

### Finding Description
For ED25519 and SECP256K1 keys, `len()` and `trie_id_len()` are identical [2](#0-1) , but for `MLDSA65` keys they diverge sharply: `len()` returns 1 + the full 1953-byte ML-DSA-65 public key, while `trie_id_len()` returns 1 + a 32-byte hash. The send fee for `TransferToGasKey`/`WithdrawFromGasKey` actions is computed via `gas_key_send_pk_len`, which — when `fix_ml_dsa_cost_charging` is disabled — deliberately uses the *storage-sized* `trie_id_len()` (33 bytes) instead of the *wire-sized* `len()` (1953 bytes), a comment explicitly labeling this "the (incorrect) existing behavior" preserved only for protocol-consensus reasons [1](#0-0) . Separately, a regression test documents the complementary defect on the exec/storage-fee side: "the pre-execution / refund path priced the key on `trie_id_len()` (33 bytes) while the host path reserved the exec fee on `len()` (1953)... the extra reserved gas was neither burnt nor refunded, so total supply silently dropped" [3](#0-2) . This is structurally identical to the audit's bug class: two different code paths compute a fee/cost for the same value based on inconsistent criteria (wire length vs. storage length), producing either under-charging (send fee) or supply leakage (exec/refund mismatch).

### Impact Explanation
When the inconsistency is live (i.e., prior to/without `FixMlDsaCostCharging` being active for a given protocol version), a transaction signer creating an ML-DSA-65 gas key via `TransferToGasKey`/`WithdrawFromGasKey` is charged a send fee based on 33 bytes instead of the true 1953-byte wire cost — a large gas under-charge relative to actual resource consumption/bandwidth. The complementary exec-side divergence documented in the regression test caused reserved gas to be neither burnt nor refunded, directly reducing total token supply accounting integrity, which maps to the "state-root divergence" / "supply inflation-or-loss" class of acceptable impacts.

### Likelihood Explanation
This is directly reachable by any unprivileged transaction signer submitting a `TransferToGasKey` or `WithdrawFromGasKey` action with an ML-DSA-65 public key — no validator, operator, or privileged role is required, satisfying the reachable-actor constraint.

### Recommendation
Ensure `gas_key_send_pk_len` and the exec/storage fee path use the same length metric consistently once `FixMlDsaCostCharging` is the sole behavior (i.e., confirm the feature is unconditionally enabled at/above the network's live protocol version, and that no supported chain can still run with it disabled), and add supply-conservation tests across all ML-DSA-65 gas-key action paths analogous to `test_gas_key_add_key_conserves_supply` for `TransferToGasKey`/`WithdrawFromGasKey`.

/// Public-key byte length for a gas-key SEND (transmission) fee computation.
fn gas_key_send_pk_len(config: &RuntimeConfig, public_key: &PublicKey) -> usize {
    if config.wasm_config.fix_ml_dsa_cost_charging {
        // This is the proper value - send fee should be based on how many bytes
        // the key occupies on the wire, not in storage.
        public_key.len()
    } else {
        // Preserve the (incorrect) existing behavior if the fix is not enabled.
        // Otherwise, we would break protocol consensus.
        public_key.trie_id_len()
    }
}
