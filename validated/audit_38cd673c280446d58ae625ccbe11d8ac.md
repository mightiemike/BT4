## Title
Signature malleability enables multisig threshold bypass via weight double-counting in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract accepts a caller-supplied array of ECDSA signatures and sums the weight of the accounts that produced them to compare against a permission threshold. Signature validity is checked via `ECDSASignature.validateComponents()` in `ECKey.java`, which does not enforce the canonical low-`s` form, so every signature is malleable (both `(r, s)` and `(r, N-s)` recover to the same address). The precompile's duplicate-detection logic keys off the raw signature bytes rather than the recovered address alone, so an attacker can submit a signature and its malleable twin to have the *same* signer's weight counted twice, bypassing the intended multisig threshold with fewer real signers than required.

### Finding Description
`ECDSASignature.validateComponents()` only checks that `r` and `s` are within `[1, SECP256K1N)`; it does not reject signatures where `s > HALF_CURVE_ORDER` [1](#0-0) . A canonicalization helper `toCanonicalised()` exists in the same class but is never invoked by the validation path used in the precompile [2](#0-1) . As a result, for any valid signature `(r, s, v)` from key `K`, the malleable counterpart `(r, N-s, v')` is also accepted as valid by `recoverAddrBySign` and resolves to the exact same address `K` [3](#0-2) .

In `ValidateMultiSign.execute`, the code attempts to prevent a signer's weight from being counted more than once, but the guard is keyed on the exact signature bytes, not solely on the recovered address:

```java
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;   // only skips when the identical signature bytes repeat
    }
    MUtil.checkCPUTime();   // otherwise just a CPU-time check, no skip
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
``` [4](#0-3) 

If `recoveredAddr` was already seen but the current `sign` bytes differ (which is trivially achievable via signature malleability: flip `s` to `N-s` and adjust `v`), the `continue` is skipped, `MUtil.checkCPUTime()` runs (a rate-limit-style check, not a duplicate-prevention check), and the same address's weight is added to `totalWeight` a second time.

This mirrors the root cause of the referenced report exactly: a library/verification routine that does not check for non-malleability (`validateComponents()` vs Solady's `SignatureCheckerLib`), combined with application logic that treats a signature (or a value derived from it) as a unique, single-use credential (here, "one signature per required signer slot" for multisig threshold accounting) rather than deduplicating strictly by recovered signer identity.

### Impact Explanation
`ValidateMultiSign` is a reachable precompiled contract at a fixed TVM address, callable by any smart contract (and thus by any unprivileged user deploying/invoking such a contract) to check on-chain permission/multisig thresholds for an account. By supplying one real signature plus its computed malleable twin, an attacker holding only a single key with weight `w` can cause the precompile to report `totalWeight = 2w`, satisfying thresholds that were designed to require multiple independent signers (e.g., `threshold = 2w` intended to require two distinct keys of weight `w`, or `w+something`). This is a concrete authorization/threshold-bypass primitive: it allows spoofing multi-party approval with a single private key, undermining any contract logic that relies on this precompile to gate privileged actions.

### Likelihood Explanation
Exploitation requires only: (1) one valid ECDSA signature over the target hash from a real permission key, and (2) computing the standard secp256k1 malleable variant `(r, N-s)` with adjusted recovery id — a well-known, mechanical transformation requiring no additional secret knowledge. Any account/contract that uses `ValidateMultiSign` for permission checks is affected, and the precompile is unconditionally reachable from user-supplied contract bytecode. No privileged role or race condition is needed.

### Recommendation
Enforce canonical (low-`s`) signatures in `ECDSASignature.validateComponents()` (or call `toCanonicalised()`/reject if `s > HALF_CURVE_ORDER` before further processing) so that only one of the two malleable variants is ever considered valid. Additionally, in `ValidateMultiSign.execute`, deduplicate strictly by `recoveredAddr` (skip immediately once an address has contributed weight) rather than by the combined `sign`/address byte array, so weight can never be counted twice for the same signer regardless of which malleable signature variant is supplied.

### Proof of Concept
1. Choose account `A` with permission requiring `threshold = 2 * w`, where key `K` (address `addrK`) has weight `w` and there is only one such key available to the attacker.
2. Attacker signs the target `hash` (as computed by the precompile: `Sha256Hash.hash(address || permissionId || data)`) with `K`, obtaining `sig1 = (r, s, v)`.
3. Attacker computes the malleable twin `sig2 = (r, N-s, v')` (flip `s` mod curve order `N`, adjust recovery id) — this still recovers to `addrK` via `recoverAddrBySign`.
4. Attacker calls `ValidateMultiSign` with `signatures = [sig1, sig2]`.
5. In the loop: for `sig1`, `addrK` is added with weight `w` (`totalWeight = w`). For `sig2`, `recoveredAddr == addrK` is already in `executedSignList`, but `sign` (merged bytes) differs from the previously stored one, so the inner `continue` is skipped; `weight = w` is added again (`totalWeight = 2w`).
6. `totalWeight (2w) >= threshold (2w)` returns `true` (`dataOne()`), even though only one real signer participated — the multisig requirement is bypassed.

    public ECDSASignature toCanonicalised() {
      if (s.compareTo(HALF_CURVE_ORDER) > 0) {
        // The order of the curve is the number of valid points that
        // exist on that curve. If S is in the upper
        // half of the number of valid points, then bring it back to
        // the lower half. Otherwise, imagine that
        //    N = 10
        //    s = 8, so (-8 % 10 == 2) thus both (r, 8) and (r, 2)
        // are valid solutions.
        //    10 - 8 == 2, giving us always the latter solution,
        // which is canonical.
        return new ECDSASignature(r, CURVE.getN().subtract(s));

        return this;
      }
    }

  private static byte[] recoverAddrBySign(byte[] sign, byte[] hash) {
    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }
