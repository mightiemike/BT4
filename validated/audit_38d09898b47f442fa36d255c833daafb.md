### Title
Unbounded Recursion in `bytecode_hash_node` During Compiled Class Hash Computation Can Crash the Sierra Compiler / OS Re-execution Process - (File: crates/starknet_api/src/contract_class/compiled_class_hash.rs)

### Summary
`bytecode_hash_node` in `starknet_api`'s compiled-class-hash computation recurses over the `bytecode_segment_lengths` tree (`NestedIntList`) that ships inside a `CasmContractClass`, with no maximum recursion-depth guard. [1](#0-0) 
This tree is produced by the Sierra→CASM compiler based on the nested branch/segment structure of the submitted program and is only bounded by the (relatively large) `max_bytecode_size` limit, not by nesting depth. This function is invoked in-process (outside the resource-isolated compiler subprocess) right after Sierra→CASM compilation to compute the executable class hash for every `Declare` transaction. [2](#0-1) 

### Finding Description
When a class is declared, `SierraCompiler::compile` runs the Sierra→CASM compilation in a separate, resource-limited subprocess (CPU/memory bounded) via `compile_with_args`/`ResourceLimits`. [3](#0-2) 
Immediately afterward, the *result* (`CasmContractClass`) is hashed **in the main process**, with no sandboxing or resource limit:
```
let executable_class_hash = executable_class.hash(&HashVersion::V2);
``` [4](#0-3) 

`hash()` calls `hash_inner`, which calls `bytecode_hash`, which calls `bytecode_hash_node` recursively over the compiler-emitted `bytecode_segment_lengths` (`NestedIntList`) tree:
```rust
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where H: StarkHash, NL: HashableNestedIntList {
    if node.is_leaf() {
        ...
    } else {
        let inner_nodes = node.iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        ...
    }
}
``` [1](#0-0) 

There is no depth limit or iterative rewrite of this traversal — recursion depth is exactly the depth of the `NestedIntList` tree, which is a segment tree the compiler builds from the nested control-flow (functions/branches) of the submitted Cairo/Sierra program. Because only `max_bytecode_size` (total instruction count) is enforced, not the *nesting depth* of the segment tree, an attacker can structure a Sierra program (e.g. via deeply nested match/if branches or deeply nested function-call chains compiled into skippable segments) so that the segment tree is a long, thin chain rather than a balanced/shallow tree, driving recursion depth into the thousands while staying within the byte-size budget. This directly mirrors the reported bug class: a size guard exists, but no depth guard bounds the recursive descent, and the recursive function itself performs the unguarded traversal.

The same code path (`HashableCompiledClass::hash` / `bytecode_hash_node`) is also used by:
- Gateway compiled-class-hash verification when validating a `Declare` transaction (`starknet_api::executable_transaction` / `blockifier::execution::contract_class`), matching declared `compiled_class_hash` against the actual compiled class.
- Starknet OS re-execution tooling (`blockifier_reexecution::compile::sierra_to_versioned_contract_class_v1`), which compiles classes fetched from chain history in-process (explicitly not process-isolated, per its own doc comment) and then hashes them the same way. [5](#0-4) 

None of these call sites impose a depth limit on the recursive hash walk before invoking it.

### Impact Explanation
A stack overflow in `bytecode_hash_node` triggers an unrecoverable Rust abort (stack overflow signal), crashing the process performing the hash. Because this hashing runs outside the sandboxed compiler subprocess:
- In the `SierraCompiler` component (used by the gateway/sequencer to compile and hash every declared class), a crash here takes down the compiler service handling all pending declarations — a network-wide denial of service against new `Declare` transaction processing, not merely resource exhaustion of the isolated compile subprocess.
- In Starknet OS re-execution tooling, the same unguarded recursion can crash re-execution/verification processes.

This satisfies the "network unable to confirm new transactions" bar (the shared sierra-compiler service crashing halts declare-transaction throughput sequencer-wide) rather than being a merely local/contained resource-only issue, since the crash occurs in the un-sandboxed parent process, not inside the CPU/memory-limited child compiler process.

### Likelihood Explanation
Reachable directly from an unprivileged class declarer: any account can submit a `Declare` (v3) transaction with an adversarially crafted Sierra program engineered to produce a deeply, linearly nested bytecode segment structure while remaining under `max_bytecode_size`. The compilation itself succeeds (it is resource-bounded and isolated), but the subsequent, unguarded hash computation in the parent process is what is vulnerable. No special privileges, timing, or race conditions are required — a single malicious declare transaction suffices if a sufficiently deep segment tree can be produced within size limits.

### Recommendation
- Convert `bytecode_hash_node` (and `bytecode_hash`) to an explicit iterative/stack-based traversal instead of native recursion, so recursion depth is not dictated by attacker-influenced input structure.
- Alternatively, enforce and validate a maximum nesting depth for `bytecode_segment_lengths` immediately after compilation (before hashing), rejecting classes whose segment tree exceeds a safe depth bound, consistent with the existing `max_bytecode_size` check.
- Ensure this validation/guard is applied uniformly at all call sites that hash a `CasmContractClass` in-process: `apollo_compile_to_casm::SierraCompiler::compile`, gateway compiled-class-hash verification, and `blockifier_reexecution::compile::sierra_to_versioned_contract_class_v1`.

### Proof of Concept
1. Construct (or compile from a crafted Cairo/Sierra source) a Sierra program whose control-flow/branch structure causes the Sierra→CASM compiler to emit a `bytecode_segment_lengths` `NestedIntList` that is a long chain of single-child `Node` wrappers (depth in the thousands), while total bytecode size remains under `max_bytecode_size` (`DEFAULT_MAX_BYTECODE_SIZE`, configured in `apollo_sierra_compilation_config::config`).
2. Submit this class via a `Declare` transaction to the sequencer's gateway/`SierraCompiler`.
3. Compilation completes in the sandboxed subprocess; the returned `CasmContractClass` is then hashed via `HashableCompiledClass::hash` in the (un-sandboxed) parent process.
4. `bytecode_hash_node`'s recursive descent into `bytecode_segment_lengths` matches the crafted depth, exhausting the call stack and crashing the compiler/gateway process with a stack overflow — a `SIGSEGV`/fatal runtime error, not a catchable `Result` error.

Note: I could not execute this PoC or directly inspect the external `cairo-lang-sierra-to-casm` crate's segment-tree generation logic to empirically confirm the maximum achievable nesting depth for a given `max_bytecode_size`; that logic lives in the `cairo-lang-sierra-to-casm` dependency (not indexed in this repository), so the precise depth-to-size ratio achievable should be verified experimentally by a Devin session with full repository/dependency access before treating this as fully confirmed exploitable at scale.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

/// Compile a SierraContractClass to a versioned ContractClass V1 (casm) in-process, using the
/// Sierra→Casm compiler as a library. The classes compiled here are fetched from the chain, so
/// unlike the sequencer gateway (which compiles user-submitted classes in a resource-limited
/// subprocess), no process isolation is needed.
pub fn sierra_to_versioned_contract_class_v1(
    sierra_contract: SierraContractClass,
) -> StateResult<(ContractClass, SierraVersion)> {
    let sierra_version = SierraVersion::extract_from_program(&sierra_contract.sierra_program)
        .map_err(|err| {
            StateError::StateReadError(format!("Failed to extract Sierra version: {err}"))
        })?;
    let contract_class_for_compilation = into_contract_class_for_compilation(&sierra_contract);
    let extracted_sierra_program =
        contract_class_for_compilation.extract_sierra_program(false).map_err(|err| {
            StateError::StateReadError(format!("Failed to extract the Sierra program: {err}"))
        })?;
    // Re-execution must accept any class the network accepted; do not restrict to the audited
    // libfuncs list.
    extracted_sierra_program
        .validate_version_compatible(ListSelector::ListName("all".to_string()))
        .map_err(|err| {
            StateError::StateReadError(format!("Sierra program version validation failed: {err}"))
        })?;
    let casm_contract_class = CasmContractClass::from_contract_class(
        contract_class_for_compilation,
        extracted_sierra_program,
        // Add pythonic hints, as the sequencer does when compiling declared classes.
        true,
        // Generous bound; declared classes already passed the network's bytecode-size limit.
        10 * DEFAULT_MAX_BYTECODE_SIZE,
    )
    .map_err(|err| {
        StateError::StateReadError(format!("Failed to compile Sierra to Casm: {err}"))
    })?;

    Ok((ContractClass::V1((casm_contract_class, sierra_version.clone())), sierra_version))
}
