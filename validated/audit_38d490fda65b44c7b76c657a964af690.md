### Title
Quadratic-complexity bouncer state tracking allows transaction-induced sequencer slowdown - (File: crates/blockifier/src/bouncer.rs)

### Summary
`Bouncer::try_update`, invoked once per transaction during block building/validation, computes marginal contributions by diffing the transaction's touched state/storage/class-hash sets against block-wide accumulator sets (`state_changes_keys`, `visited_storage_entries`, executed class hashes) that grow monotonically over the block. Each of these diff/count operations is proportional to the *accumulated* set size, not just the current transaction's contribution, so per-block cost is quadratic in the number of transactions/distinct keys touched.

### Finding Description
In `Bouncer::try_update`, for every transaction the bouncer:
- computes `tx_state_changes_keys.difference(&self.state_changes_keys)` — a diff against the full accumulated state-changes key set,
- computes `self.get_executed_class_hashes()` which **clones every key** out of the accumulated `class_hash_to_casm_hash_computation_gas` map, then diffs it against the transaction's executed class hashes,
- computes `tx_execution_summary.visited_storage_entries.difference(&self.visited_storage_entries).count()` — a diff/count against the accumulated `visited_storage_entries` set. [1](#0-0) 

`get_executed_class_hashes` explicitly clones all keys of the growing map on every call: [2](#0-1) 

After the diff, `update()` extends the accumulated sets (`visited_storage_entries`, `state_changes_keys`, `class_hashes_to_migrate`) so they keep growing across the block: [3](#0-2) 

Because these accumulated sets grow by O(1) per transaction (up to the block's resource limits) and each transaction's `try_update` call does O(size-of-accumulated-set) work (set difference/clone over `HashSet`/`HashMap` keys), the total per-block cost across N transactions is O(N²) rather than O(N). An attacker who is simply a normal transaction sender can maximize this by submitting many transactions that each touch distinct, previously-unseen storage keys/class hashes (e.g., writing to N different storage slots or invoking N different declared classes), maximizing the marginal set sizes and the accumulator size the diff must scan against on each subsequent call.

This directly parallels the Suricata CVE-2026-31933 bug class: a legitimate, unprivileged input stream (packets there; transactions here) triggers an internal accumulator-based inspection routine whose per-item cost scales with the size of state accumulated so far, producing quadratic total cost and CPU-based slowdown of the processing engine (stream inspection there; block building/validation in the sequencer here).

### Impact Explanation
`Bouncer::try_update` runs inline in both the sequential (`transaction_executor.rs`) and concurrent (`worker_logic.rs::commit_tx`) block-building/validation paths, i.e., on the hot path for every proposed and validated block. An attacker submitting a sequence of transactions engineered to maximize distinct touched storage keys/class hashes per block can inflate this to quadratic-time bouncer bookkeeping, slowing down block proposal and validation. Because both proposers and validators run this same code, a legitimate-looking but adversarially-crafted transaction set can degrade sequencer throughput network-wide (affecting the validator's ability to keep up with proposal timeouts), which is a network-unable-to-confirm-new-transactions-class impact, matching the "High" severity of the CVE analog.

### Likelihood Explanation
Any unprivileged transaction sender can submit a set of transactions that read/write many distinct storage keys and declare/invoke many distinct classes within a single block (bounded only by the block's existing bouncer capacity limits on state-changes/class-hash weights, not by the cost of the accumulator bookkeeping itself). No special privileges, ordering control, or contract deployment are required beyond ordinary transaction sending — this makes the likelihood high, limited mainly by how many distinct keys/classes fit under the existing per-block weight caps.

### Recommendation
Avoid re-scanning/cloning the full accumulated sets on every transaction. Track marginal-cost bookkeeping incrementally (e.g., maintain running counts, or use data structures that support O(marginal) insert-and-check, such as checking new-key membership as elements are added rather than diffing full sets each time). Specifically, replace `HashSet::difference` calls against `self.visited_storage_entries` / `self.state_changes_keys` with direct membership checks on the incoming keys only, and change `get_executed_class_hashes()` to avoid cloning the whole key set on every call (e.g., pass a reference or maintain a persistent `HashSet<ClassHash>` incrementally updated instead of derived fresh each time from the gas-computation map).

### Proof of Concept
1. Build a block/proposal containing N transactions, each writing to a distinct, previously-untouched storage key (or declaring/invoking a distinct class), while staying within the bouncer's configured weight limits (`BouncerConfig`).
2. For each transaction i, `Bouncer::try_update` is called; internally it performs `self.get_executed_class_hashes()` (clone of i-1 already-tracked class hashes) and `HashSet::difference`/`.count()` over `self.visited_storage_entries` / `self.state_changes_keys`, each sized O(i).
3. Summed over N transactions, total bouncer bookkeeping cost is O(N²), measurable as increasing marginal per-transaction latency in block building/validation as N grows, even though each transaction's actual execution work is O(1).
4. Because this same code path runs for both the proposer (`transaction_executor.rs`) and validator (`worker_logic.rs::commit_tx`) [4](#0-3) , the crafted transaction batch can degrade both proposal creation time and validator confirmation time for the same block.

    fn update(
        &mut self,
        tx_weights: TxWeights,
        tx_execution_summary: &ExecutionSummary,
        state_changes_keys: &StateChangesKeys,
    ) {
        let bouncer_weights = &tx_weights.bouncer_weights;
        let err_msg = format!(
            "Addition overflow. Transaction weights: {bouncer_weights:?}, block weights: {:?}.",
            self.get_bouncer_weights()
        );
        self.accumulated_weights.bouncer_weights = self
            .accumulated_weights
            .bouncer_weights
            .checked_add(tx_weights.bouncer_weights)
            .expect(&err_msg);
        self.accumulated_weights
            .casm_hash_computation_data_sierra_gas
            .extend(tx_weights.casm_hash_computation_data_sierra_gas);
        self.accumulated_weights
            .casm_hash_computation_data_proving_gas
            .extend(tx_weights.casm_hash_computation_data_proving_gas);
        self.visited_storage_entries.extend(&tx_execution_summary.visited_storage_entries);
        // Note: cancelling writes (0 -> 1 -> 0) will not be removed, but it's fine since fee was
        // charged for them.
        // Also, `get_patricia_update_resources` relies on this property - each cell must
        // be counted at most once as modified.
        self.state_changes_keys.extend(state_changes_keys);
        self.accumulated_weights.class_hashes_to_migrate.extend(tx_weights.class_hashes_to_migrate);
    }
