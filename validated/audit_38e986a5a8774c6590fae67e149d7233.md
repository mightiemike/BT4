### Title
Pre-authentication Stack-Overflow Denial of Service via Unbounded JSON Recursion in JSON-RPC Message Parsing - ([File: chain/jsonrpc-primitives/src/message.rs])

### Summary
The NEAR JSON-RPC server deserializes every inbound HTTP POST body on `/` into a `WireMessage`/`Message` via `serde_json::de::from_slice`, before any method routing, parameter validation, transaction signature check, or authentication takes place. Because `Message`/`Broken` carry raw `serde_json::Value` fields (`params`, `id`, `Broken::Unmatched(Value)`), the JSON value tree is parsed with `serde_json`'s default recursive-descent `Value` deserializer, which has no configured recursion-depth limit. A deeply nested JSON array/object body (e.g. `[[[[[...]]]]]` repeated tens of thousands of times) will recurse until the parser thread's stack is exhausted, crashing the whole `neard` process with a SIGSEGV/abort — this is exactly the bug class described in the referenced MongoDB advisory (BIT-mongodb-2025-6710 / CVE-2025-6710): unbounded JSON-parsing recursion causing pre-authentication stack overflow and server crash.

### Finding Description
`from_slice`/`from_str` in `chain/jsonrpc-primitives/src/message.rs` parse the wire body directly with `serde_json::de::from_slice(s)` into `WireMessage` (`Message` or `Broken`): [1](#0-0) 

`WireMessage` is `#[serde(untagged)]` over `Message` and `Broken`, and `Broken::Unmatched(Value)` / `Request.params: Value` / `Notification.params: Value` are plain `serde_json::Value` fields: [2](#0-1) [3](#0-2) 

`serde_json`'s `Value` deserializer is a naive recursive-descent parser: for each level of array/object nesting it makes a nested recursive call with no depth counter or bound, so sufficiently deep nesting drives the call stack past its limit regardless of the overall payload size.

The only guard on the request body before this deserialization happens is a raw byte-count limit (`RequestBodyLimitLayer`, default 10 MiB, `limits_config.json_payload_max_size`): [4](#0-3) 

10 MiB is vastly more than what is required to overflow a typical thread stack via nested `[` characters (a stack overflow via `serde_json::Value` recursion is achievable with only a few hundred KB of nesting, well under any reasonable size cap), so the byte-size limit provides no real mitigation against this recursion-depth attack. There is no depth limit, no iterative/streaming parser, and no `#[serde(deny_unknown_fields)]`-style structural cap that would reject deeply nested `params`/`id`/unmatched bodies before recursive parsing begins.

Per the RPC architecture documentation, this parsing happens in `rpc_handler()` before `process()`/`process_request()`/`process_request_internal()`, i.e. before method routing, before `RpcRequest::parse()`, and before any transaction-signature or access-key check: [5](#0-4) 

This means **any unauthenticated network caller** who can reach the public JSON-RPC endpoint (port 3030 by default, no credential/API key required) can trigger the crash with a single POST request — squarely matching "pre-authorization" reachability required by the rules (RPC caller path).

### Impact Explanation
A stack overflow in Rust is not a catchable `panic!` — it triggers an immediate process abort (SIGSEGV/SIGILL depending on platform), which crashes the entire `neard` process, not just the RPC handler task. On a validator node this means an unauthenticated remote party can force a full node/validator crash with a single, cheap HTTP request, without spending any gas, submitting a signed transaction, or holding an access key. Since the JSON-RPC server, ViewClientActor, ClientActor and consensus components run in the same process, this can be used to repeatedly crash arbitrary validator or RPC nodes that expose the endpoint, degrading network liveness/availability. This is a genuine transaction/RPC-triggered halt of an individual node, matching the accepted impact class ("transaction-triggered halt").

### Likelihood Explanation
High likelihood: the attack requires no authentication, no valid account, no signed transaction, and no special network position — just an HTTP POST to the public `/` RPC endpoint with a crafted body. Any RPC node that is publicly reachable (the default node configuration) is exposed. The payload is deterministic and inexpensive to construct/repeat.

### Recommendation
- Configure `serde_json::Deserializer` (or equivalently wrap `Value`'s recursive descent) with an explicit recursion-depth limit before deserializing untrusted RPC bodies in `chain/jsonrpc-primitives/src/message.rs::from_slice`/`from_str`, rejecting inputs whose JSON nesting exceeds a small, safe bound (e.g. tens of levels) with a `Broken::SyntaxError`/parse error instead of recursing.
- Alternatively/additionally, pre-scan the raw bytes for maximum bracket/brace nesting depth prior to invoking `serde_json`, rejecting oversized nesting cheaply.
- Consider running JSON parsing of untrusted RPC bodies on a dedicated thread with a bounded stack and catching the overflow via `std::thread` with a size limit plus a supervisory restart, so a single malicious body cannot take down the whole process — though a hard recursion-depth cap on parsing is the primary fix.
- Apply the same treatment to any other place `serde_json::Value`/`serde_json::from_slice`/`from_str` is used to parse untrusted, externally-supplied payloads before authentication (e.g. `Params::parse` in `chain/jsonrpc/src/api/mod.rs`, which also calls `serde_json::from_value` on attacker-controlled `params`).

### Proof of Concept
Send a single POST request to the JSON-RPC endpoint (`http://<node>:3030/`) with a body consisting of deeply nested JSON arrays, e.g.:

```
POST / HTTP/1.1
Host: <node>:3030
Content-Type: application/json
Content-Length: <N>

[[[[[[[[[[ ... (repeated tens/hundreds of thousands of times) ... ]]]]]]]]]]
```

This body is well under the default 10 MiB `json_payload_max_size` limit but exceeds the recursion depth `serde_json`'s `Value` deserializer can safely handle on the RPC-serving thread's stack. `rpc_handler()` calls into `near_jsonrpc_primitives::message::from_slice` (`chain/jsonrpc-primitives/src/message.rs:262-264`), which calls `serde_json::de::from_slice(s)` on the raw body before any authentication, routing, or signature verification, causing unbounded recursive descent and a stack-overflow crash of the `neard` process.

```rust
#[derive(Debug, Clone, PartialEq, serde::Deserialize)]
#[serde(untagged)]
pub enum Broken {
    /// It was valid JSON, but doesn't match the form of a JSONRPC 2.0 message.
    Unmatched(Value),
    /// Invalid JSON.
    #[serde(skip_deserializing)]
    SyntaxError(String),
}

impl Broken {
    /// Generate an appropriate error message.
    ///
    /// The error message for these things are specified in the RFC, so this just creates an error
    /// with the right values.
    pub fn reply(&self) -> Message {
        match *self {
            Broken::Unmatched(_) => Message::error(RpcError::parse_error(
                "JSON RPC Request format was expected".to_owned(),
            )),
            Broken::SyntaxError(ref e) => Message::error(RpcError::parse_error(e.clone())),
        }
    }
}

/// A trick to easily deserialize and detect valid JSON, but invalid Message.
#[derive(serde::Deserialize)]
#[serde(untagged)]
pub enum WireMessage {
    Message(Message),
    Broken(Broken),
}
```

```markdown
### Request Processing Pipeline

When a POST request arrives at `/`:

1. **`rpc_handler()`** - Deserializes the body into a JSON-RPC `Message`. Calls `JsonRpcHandler::process()`.
2. **`process()`** - Validates it's a `Request`, extracts `id`, delegates to `process_request()`.
3. **`process_request()`** - Metrics wrapper (timing, request count, error count per method). Delegates to `process_request_internal()`.
4. **`process_request_internal()`** - Core routing. Tries in order:
   - Adversarial requests (only with `test_features` cargo feature).
   - `process_basic_requests_internal()` - matches method name against known RPC methods.
   - Special `"query"` branch with sub-type metrics tracking.
   - Returns `method_not_found` if no match.
5. **`process_method_call()`** - Generic helper: parses params via `R::parse()`, invokes handler, serializes result, converts errors.
6. **HTTP status code mapping** in `rpc_handler()`: 200 (success), 400 (validation), 408 (timeout), 422 (UNKNOWN_BLOCK behind head), 500 (internal).
```
