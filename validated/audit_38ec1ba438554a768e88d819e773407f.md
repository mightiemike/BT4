### Title
Exchange trades can be permanently blocked by the fixed `ExchangeBalanceLimit` config, mirroring the `spend_limit` DoS pattern - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
`ExchangeTransactionActuator#doValidate` enforces a chain-wide `ExchangeBalanceLimit` on the resulting pool balance of a `bancor`-style exchange, reverting any `ExchangeTransactionContract` that would push either token's pool balance above this fixed threshold. This mirrors the reported Anchor bug class: an admin-configured cap unrelated to the user's actual entitlement (their token balance / the pool's real liquidity) can permanently block an otherwise-legitimate, unprivileged user operation.

### Finding Description
In `doValidate()`, once the token/TRX quantity is validated, the actuator computes the resulting pool balance and compares it to a fixed, governance-set limit: [1](#0-0) 

```java
long balanceLimit = dynamicStore.getExchangeBalanceLimit();
long tokenBalance = (Arrays.equals(tokenID, firstTokenID) ? firstTokenBalance
    : secondTokenBalance);
tokenBalance = addExact(tokenBalance, tokenQuant);
if (tokenBalance > balanceLimit) {
  throw new ContractValidateException("token balance must less than " + balanceLimit);
}
```

This is functionally analogous to the Anchor `distributor_contract#spend()` check: `if (config.spend_limit < amount) { revert }`. In both cases, a fixed threshold set independently of the user's actual balance/entitlement can prevent a legitimate, unprivileged-user transaction from succeeding. In the Anchor case it blocks claiming already-earned rewards; in java-tron's case it blocks trading into an exchange pool whose balance has organically grown (through normal trading activity) past the configured cap. Once one side of an exchange pool nears `ExchangeBalanceLimit`, any user attempting to sell that token into the pool (pushing the balance further over the limit) will have their transaction permanently rejected at validation, regardless of how much liquidity the pool otherwise has — the user has real tokens and the exchange has real capacity to fulfill the trade computed via `exchangeCapsule.transaction(...)`, but the fixed limit still causes a revert.

Unlike a legitimate slippage/anti-overflow safeguard that scales with actual usage, this limit is a single global constant applied to all exchanges, so any exchange pool that organically accumulates balance (e.g., a popular/heavily traded pair) can become permanently unable to accept further deposits of the token that is near/at the limit — a systemic, not just edge-case, denial of service for ordinary traders.

### Impact Explanation
This does not cause loss of principal or theft, but it produces a **liveness/availability failure for unprivileged users**: legitimate `ExchangeTransactionContract` calls revert with "token balance must less than X" once a pool's balance approaches the fixed `ExchangeBalanceLimit`, even though the trade is otherwise valid and the exchange has sufficient counter-liquidity. This can permanently trap users' ability to sell that particular token into the exchange (their funds remain in their own account, but the intended swap can never execute through this path), which is the same class of impact judged Medium in the Anchor report ("loss of yield"/"inability to complete a legitimate on-chain action due to a static limit").

### Likelihood Explanation
This is reachable by any unprivileged user submitting a normal `ExchangeTransactionContract` transaction — no special privileges are required. The condition (pool balance approaching the fixed limit) is a natural, foreseeable consequence of an actively-traded exchange pair over time, making this a practically reachable, not merely theoretical, scenario, matching the "Medium — mitigated in practice by choosing a large limit but still a real bug" characterization from the original report.

### Recommendation
- Consider removing the fixed global `ExchangeBalanceLimit` check, or
- Make the limit configurable per-exchange (proportional to the pool's own scale) rather than a single global constant, or
- Allow partial-amount trades / provide a governance mechanism to raise the limit for specific exchanges once it is approached, so legitimate trading is not permanently blocked.

### Proof of Concept
1. Create an exchange pair (`ExchangeCreateActuator`) and inject balances (`ExchangeInjectActuator`) such that one token's pool balance is close to `dynamicStore.getExchangeBalanceLimit()` (default value defined in `DynamicPropertiesStore`, adjustable via proposal).
2. As an ordinary user, call `ExchangeTransactionContract` to sell an amount of that token into the pool such that `tokenBalance (pool) + tokenQuant (sold) > balanceLimit`.
3. Observe `doValidate()` throws `ContractValidateException("token balance must less than " + balanceLimit)` at: [2](#0-1) 
even though the user holds sufficient token balance (confirmed by the preceding balance checks) and the trade would otherwise be valid per `exchangeCapsule.transaction(...)`. This confirms an unprivileged user's legitimate swap is permanently rejected purely due to the fixed global limit, not due to any lack of funds or liquidity — the same root-cause pattern as the referenced `spend_limit` finding.
