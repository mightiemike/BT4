### Title
Session-Storage/Decode Errors Leaked Verbatim to Unauthenticated Callers in `validateAuthenticatedSession` - (File: `packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts`)

### Summary
The `shopify-app-express` request-authentication middleware `validateWithAuthCodeFlow` catches errors thrown while resolving the current session id and while loading the session from the configured `sessionStorage` backend, and forwards the raw `error.message` directly to the HTTP response body with no sanitization.

### Finding Description
When a request reaches the auth-code-flow branch of `validateAuthenticatedSession`, the middleware first calls `api.session.getCurrentId({...})` to derive a session id from the request's cookie/Authorization header, then calls `config.sessionStorage.loadSession(sessionId)`. Both calls are wrapped in `try/catch` blocks that, on failure, send the caught exception's `.message` straight back to the client: [1](#0-0) 

and the generic fallback path: [2](#0-1) 

This middleware runs on every request that needs authentication — it is the request-authentication entry point itself, so it is reachable by an anonymous caller who has not yet established a valid session (they only need to supply *some* cookie/session-id or `Authorization: Bearer` value, valid or not, to trigger the `loadSession` call). Because `config.sessionStorage` is pluggable (Postgres, SQLite, MongoDB via Prisma, Drizzle, etc.), any backend-specific exception — a database driver error, a parameterization/type-coercion failure, a "table does not exist" error, etc. — propagates unmodified into the HTTP response.

This is directly analogous to the reported class of bug: raw backend/database error strings (potentially including engine internals, storage identifiers, and diagnostic details) are handed to an untrusted, unauthenticated client through an authentication-adjacent code path, rather than being sanitized and logged server-side only. Note that the sibling token-exchange path in the same package handles this correctly by returning a generic `'Internal Server Error'` and logging details server-side: [3](#0-2) 

which highlights that the auth-code-flow branch is the inconsistent, vulnerable one.

The existing test suite confirms this is intentional current behavior, not a hypothetical: a mocked storage error message ("Storage error") is asserted to be returned verbatim in the response body: [4](#0-3) 

### Impact Explanation
- Discloses session-storage backend technology and internal error semantics (e.g., SQL error text, table/column names, Prisma/driver-specific codes) to an unauthenticated caller, enabling backend fingerprinting.
- Assists attackers in crafting more precise probing/injection payloads against the session storage layer by giving direct feedback on malformed session-id inputs.
- Because this occurs in the authentication middleware itself, it affects every route protected by `validateAuthenticatedSession`, maximizing exposure surface across an app.
- Severity is bounded (no direct data exfiltration or auth bypass), consistent with the "Medium" rating of the original analog finding.

### Likelihood Explanation
Any anonymous HTTP request carrying a cookie or `Authorization: Bearer` header that causes `getCurrentId` or `sessionStorage.loadSession` to throw (e.g., malformed/oversized session id, backend transient failures, unexpected data types) will trigger this path without requiring prior authentication or any privileged access, making this readily reachable by unauthenticated actors.

### Recommendation
- In `validateWithAuthCodeFlow` (and `handleSessionError`), stop sending `error.message` to the client. Return a generic message (e.g., `'Internal Server Error'`) with a correlation/trace id, matching the pattern already used in `performTokenExchange`.
- Log the full error (including `error.message`/stack) only server-side via `config.logger.error`, as is already done immediately before the vulnerable `res.send` calls.
- Audit other session-storage adapters (Prisma, PostgreSQL, Drizzle, etc.) for similar patterns where raw driver errors could bubble up to HTTP responses instead of being caught and sanitized.

### Proof of Concept
1. Configure a `shopify-app-express` app with any `sessionStorage` implementation reachable over a live connection (e.g., PostgreSQL).
2. As an unauthenticated client, send a request to a protected route with a crafted/invalid session cookie or `Authorization: Bearer <malformed-token>` header such that `config.sessionStorage.loadSession(sessionId)` throws (e.g., simulate a backend error/timeout, or supply a session id value that causes the storage driver to raise a type/parse error).
3. Observe the HTTP 500 response body contains the raw exception message from the storage layer, e.g. `res.send(error.message)` at [5](#0-4) , exactly as demonstrated by the existing unit test that asserts the client receives `'Storage error'` verbatim: [4](#0-3) .

      res.status(401);

      break;
