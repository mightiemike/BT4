## Analysis

I investigated the ZetaChain bug class — "an observer/handler only recognizes a specific direct/top-level call pattern and silently ignores an equivalent indirect path, leaving a depositor's attached funds permanently stuck with no refund mechanism." I searched nearcore's receipt/runtime pipeline (which handles all cross-contract calls explicitly through typed receipts, so there is no EVM-style "hidden internal transaction" analog there) and then found a much closer analog in the `near-wallet-contract` (NEP EVM-emulation wallet contract), which decodes attached Ethereum-style RLP transactions the same way ZetaChain decodes the `data` field of an EVM transfer to determine what to do with attached funds.

In `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`, `rlp_execute` is `#[payable]`, so any deposit attached by an external caller is credited to the wallet contract's balance as soon as the receipt executes successfully (i.e., as long as the method doesn't panic). `inner_rlp_execute` builds `CallerDeposit` up front [1](#0-0)  so that if the *cross-contract call it dispatches* later fails, the caller is refunded via `rlp_execute_callback` [2](#0-1) , and I confirmed this refund path is tested by `test_caller_refunds` [3](#0-2) .

However, when the RLP-transaction parsing itself fails (`parse_rlp_tx_to_action` returns `Err`), `inner_rlp_execute` returns the error immediately, and the outer `rlp_execute` returns `PromiseOrValue::Value(e.into())` (a normal, non-panicking success at the protocol level) without ever creating a refund promise for `caller_deposit`: [4](#0-3) 

Because the method returns a `Value` (not a panic), the NEAR protocol's automatic deposit-refund mechanism (which only refunds when the whole receipt/action fails, per `refund_unspent_gas_and_deposits`) does **not** trigger — that mechanism only fires on `ActionError`/receipt failure, not on a "logical" failure returned as a normal value [5](#0-4) . The `caller_deposit` local computed at line 345 is simply dropped on this path, so any NEAR tokens an external, unprivileged caller attaches to a `rlp_execute` call that fails to parse (bad nonce, bad signature, bad chain id, wrong `target`, etc. — anything surfaced as `Error::User`, `Error::Relayer`, or `Error::AccountId`) become permanently stuck in the wallet contract, exactly mirroring the ZetaChain pattern of "decoder/observer doesn't recognize this input path, so the attached funds are silently absorbed instead of refunded."

I was not able to fully verify inside this session which exact subset of `parse_rlp_tx_to_action`'s error branches are reachable with a non-zero attached deposit (I located the function in `internal.rs` and the `Error` enum in `error.rs`/`types.rs` but ran out of tool iterations before reading their full bodies), so I cannot enumerate every concrete user input that triggers each error variant, or confirm whether any early call-site validation prevents deposits from reaching parse failures. This should be confirmed by reading `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs` (`parse_rlp_tx_to_action`) and `.../src/error.rs` in full before treating this as conclusively exploitable.

### Title
Deposit permanently locked in NEAR Wallet Contract when RLP transaction parsing fails - (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` is `#[payable]` and tracks an external caller's attached deposit via `CallerDeposit` so it can be refunded if the resulting cross-contract call fails. But when the *inner RLP-transaction decoding* itself fails (before any promise is even created), the function returns `PromiseOrValue::Value(e.into())` directly, discarding `caller_deposit` without issuing any refund.

### Finding Description
`inner_rlp_execute` computes `caller_deposit` from the attached deposit at the very start [1](#0-0) , then calls `internal::parse_rlp_tx_to_action`. If parsing fails with any `Error` variant, the function immediately returns `Err(err)` without touching `caller_deposit` [6](#0-5) .

Back in `rlp_execute`, this error is converted straight into a value response: [4](#0-3) 

Only the `Ok(promise)` branch propagates `caller_deposit` forward through the promise chain to `rlp_execute_callback`, which is the only place a refund `Promise::new(...).transfer(...)` is actually created [2](#0-1) . Because the method call completes without panicking, NEAR's protocol-level deposit-refund path (`refund_unspent_gas_and_deposits`, triggered only on receipt/action failure) never activates [5](#0-4) , so the deposit stays credited to the wallet contract's account balance with no code path that returns it to the original caller.

This is directly analogous to the ZetaChain finding: a component that decodes an embedded payload to decide how to route/refund attached value has an "unrecognized input" branch that silently swallows the transferred value instead of failing safe or refunding it.

### Impact Explanation
Any unprivileged external account calling `rlp_execute` with a non-zero attached deposit and a malformed/rejected RLP payload (any parse-time `Error`) loses that deposit permanently to the wallet contract — a direct, unauthorized, and irreversible loss of user funds with no code path to reclaim them (the funds are not burned or refunded, they simply become part of the wallet contract's balance, unlinked from the depositor). This matches the "permanently frozen/locked funds" impact category.

### Likelihood Explanation
Reachable by any regular NEAR account (no special privilege) simply by calling `rlp_execute` with a deposit and any RLP payload that fails to decode/validate — e.g., wrong nonce, invalid signature, disallowed target, or any other condition mapped to `Error::User`/`Error::Relayer`/`Error::AccountId` in `parse_rlp_tx_to_action`. Since relayers routinely submit third-party-constructed transactions on behalf of users, a malformed payload combined with an attached deposit (intentional or accidental) is plausible in normal operation, not just a contrived adversarial input.

### Recommendation
In `rlp_execute`, on any `Err(e)` returned from `inner_rlp_execute` where a non-zero deposit was attached (i.e., `caller_deposit` is `Some`), issue a refund `Promise` to the caller before returning the `ExecuteResponse`, mirroring the logic already present in `rlp_execute_callback`. Ensure `caller_deposit` is threaded out of `inner_rlp_execute`'s error path (not just its success path) so this refund can be constructed uniformly for every failure branch, including the `Error::Relayer`-with-access-key ban-relayer branch.

### Proof of Concept
1. Deploy the `near-wallet-contract` for an owner address.
2. From an external NEAR account (not the wallet owner, not using an access key on the wallet), call `rlp_execute(target, tx_bytes_b64)` attaching a deposit (e.g., 3 NEAR), where `tx_bytes_b64` encodes an RLP transaction that fails parsing/validation (e.g., wrong nonce or invalid signature so `parse_rlp_tx_to_action` returns `Err(Error::User(_))` or `Err(Error::Relayer(_))`).
3. Observe the call returns successfully (`ExecuteResponse{success:false,...}`) rather than panicking.
4. Check the caller's balance: the attached deposit is not returned; check the wallet contract's balance: it increased by the deposit amount, and there is no subsequent transaction/promise that transfers it back to the caller — the funds are stuck.

(This flow parallels `test_caller_refunds` in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs`, which only exercises the *cross-contract-call failure* refund path, not the *parse failure* path, and would need to be extended to demonstrate the missing refund.)

#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,

    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;

    );
