### Title
`replay_on_archive` verification tool skips state-checkpoint hash comparison, letting silently-diverging state roots pass as "verified" replay - ([File: types/src/transaction/mod.rs])

### Summary
The `db-tool replay-on-archive` verification path (`storage/db-tool/src/replay_on_archive.rs`) re-executes historical transactions and validates the VM output against the archived `TransactionInfo` via `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs`). That function only compares `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash. It never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, and the code contains an explicit `TODO` acknowledging this gap. This means the archive-replay verifier can report success for a chunk whose locally-computed state (or hot-state / position-state) root diverges from the authenticated on-chain root, undermining the integrity guarantee the tool is meant to provide.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by replay-verification tooling to assert that locally re-executed VM output matches the trusted, previously-committed `TransactionInfo` (the leaf that is hashed into the transaction accumulator and ultimately signed by validators in the `LedgerInfo`). [1](#0-0) 

The function validates:
- `status` vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- `write_set_hash` (`CryptoHash::hash(self.write_set())`) vs. `txn_info.state_change_hash()`
- `event_root_hash` vs. `txn_info.event_root_hash()`

It explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that exist on `TransactionInfoV0`/`TransactionInfoV1` and represent the Sparse-Merkle/Jellyfish state root(s) at that version: [2](#0-1) [3](#0-2) 

This comparator is invoked directly by the `db-tool replay-on-archive` verifier's `execute_and_verify` routine, which is the entire purpose of the tool (to detect state divergence between archived ledger data and independent VM re-execution): [4](#0-3) 

Because `state_checkpoint_hash` (and the newer position/hot-state roots) are never diffed, a bug in write-op-to-state-value conversion, in `StateStore` commit logic, in the Jellyfish Merkle Tree batch update, or in the position/hot-state root computation, that produces a *state root* different from the one archived/agreed upon by consensus, would not be caught by this tool as long as the write set, events, gas, and status still match. The verifier would report "no failed transactions" even though the actual state root (used to serve state proofs and to gate later restores) is wrong.

### Impact Explanation
`state_checkpoint_hash` is the field bound into the `TransactionInfo` leaf hashed into the transaction accumulator and covered by validator signatures; it is what state proofs (`get_state_value_with_proof_by_version`, backup/restore manifests, `TransactionInfoWithProof` verification, etc.) are ultimately anchored to. A verification tool that silently skips this check provides false assurance that replayed state matches the authenticated ledger. This is precisely the "authenticated proof/response bound to the wrong version/root" and "hard-fork-only divergence during... replay... not caught" class of issue called out in scope: a bug elsewhere in the state-commit pipeline (e.g., in write-op conversion, SMT/JMT batch update, or the newer position-state/hot-state root computation) could silently corrupt the durable state root, and this is the specific tool meant to catch such regressions during replay-verify — but it structurally cannot, because the comparator omits the very hash it should check. This directly weakens the operational integrity backstop for a hard fork or state divergence, which is high severity for a mainnet-facing verification tool, though it is a detection gap rather than a live path that itself corrupts consensus-critical state.

### Likelihood Explanation
The gap is guaranteed to manifest whenever the underlying state-commit path diverges from the archived data at a version that does not coincide with a state-checkpoint boundary comparison — the code itself documents this as a known limitation via the inline TODO ("this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution"). No attacker interaction is required; it is a latent correctness gap that would only be exercised if a separate state-commit bug exists, but when it does, this verifier is guaranteed to miss it.

### Recommendation
In `ensure_match_transaction_info` (`types/src/transaction/mod.rs`), additionally recompute and compare the state-checkpoint hash (and, where applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against `txn_info`'s values whenever the transaction is a checkpoint boundary, gating this on the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag as the existing TODO suggests, before enabling that flag's replay-verify usage. Ensure `replay_on_archive.rs` supplies (or the executor computes) the necessary in-memory state trees to perform this comparison at chunk boundaries.

### Proof of Concept
No exploit is required to demonstrate this — it is a static code-inspection finding: the comparator's implementation and its own inline TODO comment at lines 2197-2202 of `types/src/transaction/mod.rs` confirm that `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` are excluded from the equality checks performed in `ensure_match_transaction_info`, and `storage/db-tool/src/replay_on_archive.rs` (lines 392-397) shows this is the sole correctness check used by the replay-verify tool for each replayed transaction. Constructing a live divergence would require an independent state-commit bug (out of scope to fabricate here); the finding is that, were one to exist, this tool would not detect it.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
