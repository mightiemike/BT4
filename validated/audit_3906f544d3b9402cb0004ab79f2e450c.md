## Title
Stale/undeclared Cairo0 (deprecated) contract classes are trusted across execution contexts via the global class cache without revalidating declaration state — (File: `crates/blockifier/src/state/state_reader_and_contract_manager.rs`)

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` serves classes from a process-wide, cross-block `GlobalContractCache` (`contract_class_manager`). For Cairo1 classes it explicitly revalidates that the class is *still declared* in the current canonical state before trusting the cached entry, because the authors acknowledge the cache can hold "a declared class from a reverted block". For Cairo0 (deprecated) classes this revalidation is entirely skipped, so once a Cairo0 class is populated into the shared cache from any non-committed execution context (a reverted block, an aborted speculative/concurrent transaction, or a rejected re-declare), it will be served as a valid compiled class forever afterward, in any other state/context, even though it was never actually declared in that context's canonical state.

### Finding Description
In `get_compiled_from_class_manager`: [1](#0-0) 

The branch handling `RunnableCompiledClass::V0(_) => {}` performs no check at all, whereas the non-V0 (Cairo1) branch calls `self.state_reader.is_declared(class_hash)` specifically because "existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)". The `FetchCompiledClasses::is_declared` contract itself documents that it only supports Cairo1: "Cairo 0 classes always return `false`" — which is presumably *why* the check was omitted for V0, but the omission means no equivalent safety net exists for V0 at all.

The cache in question, `GlobalContractCache` / `RawClassCache`, is explicitly a shared, long-lived, cross-execution cache: "Thread-safe LRU cache for contract classes ... optimized for inter-language sharing" [2](#0-1) , populated via `contract_class_manager.set_and_compile(class_hash, compiled_class.clone())` on every cache miss regardless of whether the read happened in a committed, reverted, or aborted execution context [3](#0-2) .

Compounding this, Cairo0 declares are special-cased to skip the "already declared" check entirely for backward compatibility, writing the class straight into state without verifying prior declaration status: [4](#0-3) 

This is the same bug class as CVE-2023-0386: a capability/artifact (there, a setuid+capability file; here, a "declared and runnable" class binding) established in one context that should not be trusted outside it (a nosuid mount / a reverted-or-aborted execution) is carried, unchecked, into a different privileged context (another mount / a different, canonical block state) because the code path that would normally re-validate the capability against the new context's actual permission table (`declared_contracts` in `StateMaps`) is missing for this specific variant (Cairo0).

### Impact Explanation
Blockifier supports concurrent/optimistic execution where transactions are speculatively run and can be aborted and retried (`crates/blockifier/src/concurrency/worker_logic.rs`, `versioned_state.rs`); it is also possible for a produced block to be discarded/reverted. Any of these flows can cause a Cairo0 class's CASM to be fetched from base storage and inserted into the shared `GlobalContractCache` without the associated declare transaction ever being finalized in `declared_contracts`. Because the V0 branch of `get_compiled_from_class_manager` never re-checks the current state's declaration status, any subsequent call to `get_compiled_class(class_hash)` for that class hash — in an unrelated block, from an unrelated caller, potentially on some but not all sequencer/replica processes depending on their individual cache contents — will succeed and return a runnable class, even though the class is not declared in that context's committed state. This can let a contract execute logic under a class hash that per protocol rules should be rejected with `UndeclaredClassHash`, producing execution results (and therefore state diffs / state roots) that diverge from an honest node whose cache does not happen to hold the stale entry (or that re-executes independently, e.g., during Starknet OS re-execution or state re-execution used for proving) — i.e., a state root/committed-root divergence between otherwise-honest executions.

### Likelihood Explanation
Reaching this requires only ordinary, unprivileged actions: submitting a Declare (or Deprecated Declare, V0/V1) transaction whose class ends up read once (fetched into the shared cache) but whose declaration is not durably committed (e.g., transaction reverted/rejected during re-validation after concurrent execution, or included in a discarded/rebuilt block) followed by a later reference to the same class hash without a valid on-chain declaration. No operator/proposer/prover privilege is needed — a single crafted transaction sequence from an ordinary sender/declarer suffices, and the divergent behavior depends only on per-process cache state, which is inherently variable across sequencer/full-node instances.

### Recommendation
Apply the same declaration-revalidation logic used for Cairo1 classes to Cairo0/deprecated classes. Extend `FetchCompiledClasses::is_declared` (or add an analogous, symmetric check) to also support Cairo0 classes so that `get_compiled_from_class_manager` can verify, on every cache hit, that the class hash is actually present in the current context's `declared_contracts`/class state before returning a cached `RunnableCompiledClass::V0`, matching the invariant already enforced for V1.

### Proof of Concept
1. Configure a sequencer node using `StateReaderAndContractManager` with a populated `GlobalContractCache` shared across executions (default runtime configuration).
2. Trigger a scenario where a Cairo0 class is read into the cache without its declare being durably committed — e.g., submit a Declare V0/V1 transaction for class `C` that gets included in a speculative/concurrent execution pass and is subsequently aborted (via `worker_logic::validate`/`delete_writes`), or gets included in a block that is later discarded/rebuilt — such that `get_compiled_from_class_manager` executes its cache-miss path and calls `contract_class_manager.set_and_compile(C, ...)` (`crates/blockifier/src/state/state_reader_and_contract_manager.rs:88-91`) even though `C` never lands in the canonical `declared_contracts` map.
3. In a fresh, unrelated state/context that has never declared `C` (verify via `state_reader.is_declared(C)` returning false, or absence from `declared_contracts`), call `get_compiled_class(C)`.
4. Because the `RunnableCompiledClass::V0(_) => {}` branch performs no revalidation (`state_reader_and_contract_manager.rs:74`), the call returns `Ok(runnable_class)` instead of `Err(StateError::UndeclaredClassHash(C))`, allowing execution of an undeclared class in a context where other nodes without the stale cache entry would correctly reject it.
