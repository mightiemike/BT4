### No vulnerability found for this question.

**Analysis supporting this conclusion:**

The equality the question claims can be broken — "leader_key.public_key passed to check_normal_coinbase_tx == the VRF public key registered by the SAME apparent_sender/miner that produced tenure_change_payload.pubkey_hash" — is enforced by construction, not by independent lookups that could diverge.

In `validate_normal_nakamoto_block_burnchain`, both the miner-signature-check input (`miner_pubkey_hash160`) and the VRF-check input (`leader_key.public_key`) are derived from the **same single `leader_key` record**, fetched exactly once: [1](#0-0) 

That is: `leader_key = db_handle.get_leader_key_at(block_commit.key_block_ptr, block_commit.key_vtxindex)`, and then both `miner_pubkey_hash160 = leader_key.interpret_nakamoto_signing_key()` and `leader_key.public_key` (the VRF key) come from this one struct instance, passed together into `validate_normal_against_burnchain` [2](#0-1) . There is no code path where `check_tenure_tx`'s `pubkey_hash` and `check_normal_coinbase_tx`'s `leader_vrf_key` are sourced from two different `LeaderKeyRegisterOp` records — they are always two fields of the identical registration.

Additionally, the `block_commit` that supplies `key_block_ptr`/`key_vtxindex` is itself resolved deterministically to a single fork: `validate_nakamoto_tenure_snapshot` first resolves `tenure_burn_chain_tip` from `block.header.consensus_hash` and explicitly checks that this snapshot's `sortition_id` matches the ancestor snapshot at the same height along the canonical fork rooted at `db_handle`'s tip (via `get_ancestor_sort_id`), rejecting the block if not canonical [3](#0-2) . Only after this canonicality check does the code fetch `block_commit` via `db_handle.get_block_commit_by_txid(&tenure_burn_chain_tip.sortition_id, ...)`, which is keyed by the specific `sortition_id` of that canonical snapshot, not a bare `(block_height, vtxindex)` pair that could collide across forks [4](#0-3) . The subsequent `get_leader_key_at` call is made on the same `db_handle` (a `SortitionHandleConn` already scoped to this canonical fork), so it cannot resolve a leader key registered on a divergent fork sharing coincidental `(block_height, vtxindex)` coordinates.

Given this, the premise of the question — that `tenure_change_payload.pubkey_hash` (verified by `check_tenure_tx`/`check_miner_signature`) and the VRF key used by `check_normal_coinbase_tx` could belong to two unrelated registrants — cannot occur, because both are read from the same `leader_key` object that is itself resolved deterministically to the single canonical fork identified by the block's own `consensus_hash`. I was unable to inspect the full internal implementation of `SortitionHandleConn::get_leader_key_at` in `stackslib/src/chainstate/burn/db/sortdb.rs` within the available tool budget, but the surrounding call sites and the mandatory canonicality check in `validate_nakamoto_tenure_snapshot` make a fork-crossing key substitution structurally impossible through this path.

            SortitionDB::get_block_snapshot_consensus(db_handle, consensus_hash)?
        else {
            warn!("No sortition for {}", consensus_hash);

                "No sortition for block's consensus hash".into(),
            ));
        };

        // tenure sortition is canonical
        let Some(ancestor_sort_id) = get_ancestor_sort_id(
            db_handle,
            tenure_burn_chain_tip.block_height,

        else {

            warn!("Invalid consensus hash: snapshot is not canonical"; "consensus_hash" => %consensus_hash);

            warn!("Invalid consensus hash: snapshot is not canonical"; "consensus_hash" => %consensus_hash);

            ));
        };
