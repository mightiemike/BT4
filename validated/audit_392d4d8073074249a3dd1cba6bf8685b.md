### Title
Deposit Refund Misdirection in Meta-Transaction (`DelegateAction`) Execution Sends Relayer-Paid Deposits to Sender on Failure - (`File: runtime/runtime/src/actions.rs`)

### Summary

When `apply_delegate_action` constructs the inner action receipt spawned from a `DelegateAction`, it sets `predecessor_id` to the DelegateAction `sender_id` (Alice). The deposit-refund path in `refund_unspent_gas_and_deposits` unconditionally uses `receipt.balance_refund_receiver()`, which resolves to `predecessor_id` when no `refund_to` override is present. Because the relayer — not Alice — paid the attached deposit, any failure of the inner receipt on the receiver's shard causes the full deposit to be credited to Alice rather than returned to the relayer who funded it. An unprivileged user can exploit this by crafting a `DelegateAction` with a large attached deposit that is guaranteed to fail, draining the relayer's NEAR balance into their own account.

### Finding Description

**Receipt construction in `apply_delegate_action`**

`apply_delegate_action` (`runtime/runtime/src/actions.rs:422–491`) builds the inner receipt as a `Receipt::V0` with `ReceiptEnum::Action(ActionReceipt {...})`:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),          // Alice — DelegateAction sender
    receiver_id: delegate_action.receiver_id(), // Bob
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id(),  // Relayer
        ...
    }),
});
``` [1](#0-0) 

The `predecessor_id` is Alice; the `signer_id` is the relayer. The relayer's balance was debited for the full deposit when the outer transaction was converted to a receipt.

**Deposit refund routing**

`refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs:1163–1298`) issues the deposit refund to `receipt.balance_refund_receiver()`:

```rust
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(),
        deposit_refund,
    ));
}
``` [2](#0-1) 

`balance_refund_receiver()` returns `refund_to` if set, otherwise `predecessor_id`:

```rust
pub fn balance_refund_receiver(&self) -> &AccountId {
    self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
}
``` [3](#0-2) 

Because the inner receipt is `Receipt::V0 / ReceiptEnum::Action` (not `ActionReceiptV2`), `refund_to()` always returns `&None`:

```rust
pub fn refund_to(&self) -> &Option<AccountId> {
    match self.receipt() {
        ReceiptEnum::Action(_) | ... => &None,
        ReceiptEnum::ActionV2(r) | ... => &r.refund_to,
    }
}
``` [4](#0-3) 

Therefore `balance_refund_receiver()` always returns `predecessor_id` = Alice for the inner receipt, regardless of who paid the deposit.

**Protocol documentation confirms the broken invariant**

The nearcore architecture documentation explicitly acknowledges this:

> "But what if the transaction fails execution on Bob's shard? At this point, the predecessor is `Alice` and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a **financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard.**" [5](#0-4) 

The code comment in `apply_delegate_action` also acknowledges this:

> "If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction." [6](#0-5) 

### Impact Explanation

The relayer pays the deposit when the outer transaction is converted to a receipt (balance deducted from the relayer's account). When the inner receipt fails on the receiver's shard, the deposit is refunded to Alice (`predecessor_id`), not the relayer (`signer_id`). The relayer suffers a permanent net loss equal to the attached deposit. Alice gains that same amount. This is a direct, protocol-enforced balance transfer from the relayer to Alice triggered by a user-controlled failure.

**Broken invariant:** The entity whose balance was debited for a deposit must receive the refund when the action fails. In meta-transactions, the relayer is debited but Alice is refunded.

**Corrupted value:** `deposit_refund` (the full `total_deposit` of the inner receipt's actions) is credited to Alice's account instead of the relayer's account. [7](#0-6) 

### Likelihood Explanation

Any unprivileged user (Alice) who can create a `DelegateAction` can trigger this. The attack requires:
1. Alice crafts a `DelegateAction` with a large `deposit` attached to a `FunctionCall` targeting a receiver that will reject the call (e.g., a non-existent method, a contract that panics, or a receiver with no contract).
2. Alice submits the `SignedDelegateAction` to a relayer.
3. The relayer, unable to guarantee the call will succeed at execution time (contract state can change between submission and execution), submits the outer transaction.
4. The inner receipt fails; Alice receives the deposit.

The attack is repeatable and scales linearly with the deposit size. The nearcore documentation explicitly identifies this as a "financial incentive" for users to exploit.

### Recommendation

In `apply_delegate_action`, construct the inner receipt using `ReceiptEnum::ActionV2(ActionReceiptV2 { refund_to: Some(relayer_id), ... })` where `relayer_id` is the outer receipt's `predecessor_id` (the relayer). This ensures that on failure, the deposit refund is routed back to the relayer who paid it, not to Alice.

Alternatively, the `predecessor_id` of the inner receipt could be set to the relayer, but this would break the `predecessor_id` semantics that contracts rely on to verify the caller identity (Alice must appear as `predecessor_id` for the inner receipt to function correctly). The `refund_to` field in `ActionReceiptV2` was designed precisely for this override use case. [8](#0-7) 

### Proof of Concept

**Actors:**
- `relayer.near` — submits the meta-transaction, pays all costs
- `alice.near` — crafts the `DelegateAction`, receives the stolen deposit
- `bob.near` — receiver of the inner action (no contract deployed, so any function call fails)

**Steps:**

1. Alice creates a `DelegateAction`:
   ```
   DelegateAction {
       sender_id: "alice.near",
       receiver_id: "bob.near",
       actions: [FunctionCall { method: "any", deposit: 100 NEAR, gas: 30 TGas }],
       nonce: ...,
       max_block_height: ...,
       public_key: alice_key,
   }
   ```
2. Alice signs it and sends it to the relayer off-chain.
3. The relayer wraps it in a transaction (signer = `relayer.near`, receiver = `alice.near`) and submits it. The relayer's balance is debited for the 100 NEAR deposit plus gas.
4. On Alice's shard, `apply_delegate_action` creates the inner receipt:
   - `predecessor_id = alice.near`
   - `signer_id = relayer.near`
   - deposit = 100 NEAR
5. The inner receipt is routed to Bob's shard. `bob.near` has no contract; the function call fails.
6. `refund_unspent_gas_and_deposits` issues:
   - Deposit refund → `balance_refund_receiver()` = `predecessor_id` = **`alice.near`** ← 100 NEAR
   - Gas refund → `signer_id` = `relayer.near` ← unspent gas value
7. Alice's balance increases by 100 NEAR. The relayer's balance decreases by 100 NEAR (net of gas refund).

The existing test `test_gas_key_refund` in `test-loop-tests/src/tests/gas_keys.rs` demonstrates the deposit-refund-to-predecessor behavior in a non-meta-transaction context, confirming the refund routing logic is as described. [9](#0-8)
