### Title
Cost model's `allocated_accounts_data_size` only inspects top-level instructions, letting CPI'd System Program allocations bypass `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` accounting - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` walks only `transaction.program_instructions_iter()` (top-level instructions) and only recognizes `SystemInstruction::CreateAccount`/`Allocate`/etc. when the *top-level* `program_id` is the System Program. If an attacker deploys a custom SBF program that CPIs into the System Program's `Allocate`/`CreateAccount` instructions, the top-level program id seen by the cost model is the attacker's program (not `system_program::id()`), so `calculate_account_data_size_on_instruction` returns `SystemProgramAccountAllocation::None` and the transaction's `allocated_accounts_data_size` is computed as 0 even though real account growth occurs at execution time.

### Finding Description

and aggregated per-transaction here: [2](#0-1) 
Both `calculate_cost` (pre-execution, used for banking-stage scheduling admission) and `calculate_cost_for_executed_transaction` (used for post-execution accounting) invoke this same top-level-only walk: [3](#0-2) 

This value feeds `CostTracker::try_add`, which is the sole gate that enforces `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (`WouldExceedAccountDataBlockLimit`): [4](#0-3) 
This same `try_add`/cost-tracker mechanism is invoked both during block production and, per the `apply_cost_tracker_during_replay` feature, during block replay/validation via `check_block_cost_limits` in `runtime/src/transaction_execution.rs`: [5](#0-4) 

Meanwhile, the *actual* real per-account data growth is tracked independently at the `TransactionContext`/`TransactionAccounts` level via `update_accounts_resize_delta`/`can_data_be_resized`, which correctly captures growth regardless of call depth (CPI included), because it's invoked from every account-data resize path: [6](#0-5) 
That real, accurate resize delta is rolled up into `Bank::accounts_data_size_delta_on_chain` post-execution: [7](#0-6) 
— but this real accounting value is never compared against `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`; that block-level limit is only checked against the pre-execution, top-level-only cost-model estimate in `CostTracker::try_add`.

So there are two separate mechanisms:
1. Per-transaction hard cap (`can_data_be_resized`, `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`) — this is enforced correctly at the account/resize level and does account for CPI, capping any single transaction's total account growth.
2. Per-block soft cap (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` via `CostTracker`) — this is enforced only against the cost model's static, top-level-only estimate, which is blind to CPI'd allocations.

An attacker deploying a program that CPIs into `system_instruction::allocate`/`create_account` therefore causes every such transaction to report `allocated_accounts_data_size == 0` to the cost tracker, while still growing real account data up to the per-transaction cap. A leader (or, under `apply_cost_tracker_during_replay`, a replaying validator) can pack many such transactions into one block, each contributing 0 to the tracked `allocated_data_size` counter but real bytes to `accounts_data_size_delta_on_chain`, systematically exceeding the intended 100MB-per-block growth budget without tripping `WouldExceedAccountDataBlockLimit`.

### Impact Explanation
This is a metering/resource-exhaustion issue (METERING_TOTALITY invariant violation): accounts-db can grow substantially beyond the advertised `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100,000,000 bytes) per block, since CPI'd allocations are invisible to the admission-control accounting: [8](#0-7) 
This maps to Solana's resource-exhaustion / DoS bounty category (uncharged, unbounded-relative-to-spec accounts-db growth), not to a funds-loss or consensus-halt bug, since the per-transaction cap still bounds any single transaction and no signature/lamport/consensus invariant is broken.

### Likelihood Explanation
The attack requires only deploying an ordinary SBF program (unprivileged) that CPIs `system_instruction::allocate`/`create_account`, and submitting many such transactions. No special permissions, validator access, or feature-gate bypass are needed; the gap exists in `calculate_account_data_size_on_instruction`'s top-level-id check, which is a static, general property of the code, and is trivially and repeatably reachable by any attacker with enough fee-paying capacity.

### Recommendation
`calculate_allocated_accounts_data_size` should inspect all instructions reachable from a transaction, not just top-level ones, when statically estimating account-data growth — e.g., either walk instructions recursively where CPI targets are staticaly known, or (more robustly) switch the block-level enforcement to use the actual post-execution `accounts_resize_delta` (already computed per-transaction, CPI-inclusive) instead of/in addition to the static top-level estimate when enforcing `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`.

### Proof of Concept
Bank integration test:
1. Deploy an SBF program that, given a target account and space, issues a CPI `system_instruction::allocate(target, MAX_PERMITTED_DATA_LENGTH)` (or `create_account`).
2. Build and sanitize a transaction whose only top-level instruction invokes this custom program (no top-level `system_program::id()` instruction).
3. Assert `CostModel::calculate_cost(&tx, &feature_set).allocated_accounts_data_size() == 0`.
4. Execute the transaction against a `Bank` and assert the target account's on-chain data length equals `MAX_PERMITTED_DATA_LENGTH` (i.e., real growth occurred) and `bank.load_accounts_data_size_delta_on_chain()` increased by that amount.
5. Repeat with N such transactions packed into one "block" through the normal banking/cost-tracker admission path, and show `CostTracker::try_add` never returns `WouldExceedAccountDataBlockLimit` even though cumulative real growth (`accounts_data_size_delta_on_chain`) exceeds `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`.

    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }

    pub(crate) fn update_accounts_resize_delta(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        let accounts_resize_delta = self.resize_delta.get();
        self.resize_delta.set(
            accounts_resize_delta.saturating_add((new_len as i64).saturating_sub(old_len as i64)),
        );
        Ok(())
    }

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
