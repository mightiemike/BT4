### Title
Unprivileged growth of `PendingOutbounds` can DoS the O(n) `HasPendingOutboundsForChain` check gating TSS fund migration - (File: x/uexecutor/keeper/pending_outbound_query.go)

### Summary
The CoreDAO finding is a class of "unbounded array grown by an unprivileged actor, later walked in a gas-bound loop that becomes inoperable." The Push Chain analog is `PendingOutbounds`, a `Map` that any unprivileged user can grow via repeated, gasless `MsgExecutePayload` calls, and which is later walked in full (`O(n)`) by `Keeper.HasPendingOutboundsForChain` — a check invoked from `x/utss`'s admin-gated `MsgInitiateFundMigration` handler.

### Finding Description
`PendingOutbounds` entries are created whenever an EVM receipt contains a `UniversalTxOutboundEvent` log emitted by the `UniversalGatewayPC` contract, decoded and appended in `BuildOutboundsFromReceipt`: [1](#0-0) 

This path is reachable directly by any unprivileged account through `MsgExecutePayload` (gasless — any caller, authenticated purely by the UEA's own signature check), which calls the UEA, then attaches any outbound events found in the receipt via `CreateUniversalTxFromReceiptIfOutbound`: [2](#0-1) 

Each successful call that triggers the gateway's withdraw path creates a new `PendingOutbounds` entry that is never removed until UVs vote it to `OBSERVED`/`PASSED` — and the module's own docs state ballot expiry deliberately does **not** remove `PendingOutbounds` entries ("Auto-refund risks double-pay ... there is no safe automatic resolution"): [3](#0-2) 

Later, `HasPendingOutboundsForChain` performs a full, unbounded `Walk` over the entire `PendingOutbounds` collection, joining against `UniversalTx` on every iteration, explicitly documented as "O(n) but only called during admin-initiated migration": [4](#0-3) 

This function is invoked from `x/utss`'s `MsgInitiateFundMigration` handler (`x/utss/keeper/msg_initiate_fund_migration.go`), which is the gate that determines whether TSS funds can be safely migrated off a chain to a new TSS key. If an unprivileged attacker inflates `PendingOutbounds` with a large number of stuck/never-finalized entries (e.g., cheap outbound withdrawals of low-value or dust PRC20 balances, repeated across many separate gasless `MsgExecutePayload` transactions — each transaction's own gas cost is paid from the attacker's UEA balance, not the Cosmos fee, and can be kept arbitrarily small per call), the `Walk` executed inside the (in-consensus) `MsgInitiateFundMigration` transaction can grow large enough to exceed the block gas limit, causing that transaction to always fail and rendering fund migration permanently inoperable for that chain — directly mirroring the CoreDAO `turnRound()` DoS pattern (unbounded attacker-grown array walked in a gas-bound loop).

### Impact Explanation
Blocking `MsgInitiateFundMigration` prevents Push Chain from ever safely rotating/migrating TSS-controlled funds off a compromised or refreshed key for the affected chain, which is a core security control of the crosschain protocol (TSS coordination is explicitly in scope). This is a genuine denial-of-service of a privileged administrative safety mechanism, triggered purely by unprivileged action, with no existing bound (no `MaxPendingOutbounds`-style cap analogous to CoreDAO's `CANDIDATE_COUNT_LIMIT` fix).

### Likelihood Explanation
Moderate. The attacker needs a funded UEA and the ability to repeatedly trigger successful outbound-emitting payload executions; each individual withdraw likely requires nonzero PRC20 balance/some gas cost from the attacker's own UEA, so building enough entries to exceed a block's gas limit during the `Walk` requires sustained, but not privileged, effort. It also requires an admin to actually attempt `MsgInitiateFundMigration` on the targeted chain while the backlog exists — the impact (blocking migration) is not immediate but persists once the state is inflated.

### Recommendation
- Cap `PendingOutbounds` growth per chain (or add a global limit with rejection/queuing when exceeded), analogous to CoreDAO's `CANDIDATE_COUNT_LIMIT`.
- Convert `HasPendingOutboundsForChain` to use a secondary index keyed by destination chain (rather than a full O(n) walk over all pending outbounds joined against `UniversalTx`), so the check's cost scales with entries for that chain only, not total system-wide pending outbounds.
- Consider adding a maximum age / minimum-amount threshold enforcement, or a paginated/bounded-iteration migration-check design so the check cannot be starved by attacker-inflated backlog.

### Proof of Concept
1. Attacker deploys/funds a UEA with minimal native gas balance and a nonzero balance of some low-value PRC20 token.
2. Attacker repeatedly submits gasless `MsgExecutePayload` transactions whose payload calls the UniversalGatewayPC withdraw function for a small amount of the PRC20 token, targeting the chain intended to later undergo TSS fund migration.
3. Each successful call adds a new entry to `PendingOutbounds` (via `BuildOutboundsFromReceipt` → `CreateUniversalTxFromReceiptIfOutbound`) that stays PENDING indefinitely (per the documented no-auto-cleanup design).
4. After accumulating a sufficiently large number of entries, an admin's `MsgInitiateFundMigration` for that chain triggers `HasPendingOutboundsForChain`, whose full `Walk` over all `PendingOutbounds` (joined with `UniversalTx` lookups) exceeds the block gas limit, causing the migration transaction to fail deterministically and blocking TSS fund migration for that chain.

Note: I was unable to directly inspect `x/utss/keeper/msg_initiate_fund_migration.go`'s exact gas-cost characteristics or confirm the precise minimum economic cost per attacker-created `PendingOutbounds` entry (e.g., minimum withdrawal amount enforcement in the Gateway contract) within the available indexed context — this would need to be validated in the full repository to precisely quantify attacker cost versus block-gas-exceeding entry count.

### `PendingOutbounds`

- **Created** by chain code at outbound creation in `create_outbound.go` —
  BEFORE any validator vote. The chain knows the outbound exists because it
  generated the destination-chain transaction itself; validators are tasked
  with observing whether/how it landed.
- **Keyed** by deterministic chain-derived `outbound_id`.
- **Variant-aware:** validator votes append `OutboundObservationVariant`s as
  they arrive (`RecordOutboundVote` inside `VoteOutbound`). Multiple variants
  per outbound indicate validator divergence on the destination-chain
  observation (different `success`/`tx_hash`/`error_msg`/`gas_fee_used`).
- **Removed ONLY when validators reach consensus** (existing inline
  `PendingOutbounds.Remove` in `msg_vote_outbound.go` on `PASSED`).
- **Ballot expiry does NOT remove the entry** — this is intentional. The
  destination chain already received (or did not receive) the outbound; the
  user's funds are already in flight. Auto-refund risks double-pay (if the
  outbound actually landed), auto-retry risks double-delivery, and there is
  no safe automatic resolution. Operators investigate stuck outbounds via
  the per-variant audit trail (which validators voted what observation) plus
  separate `x/uvalidator` ballot status queries; resolution is governance-
  driven, not chain-driven.

// HasPendingOutboundsForChain checks if there are any pending outbounds for a given chain.
// It walks PendingOutbounds and joins against UniversalTx to check destination_chain.
// Returns true on first match. This is O(n) but only called during admin-initiated migration.
func (k Keeper) HasPendingOutboundsForChain(ctx context.Context, chain string) (bool, error) {
	var found bool
	err := k.PendingOutbounds.Walk(ctx, nil, func(outboundId string, entry types.PendingOutboundEntry) (bool, error) {
		utx, exists, err := k.GetUniversalTx(ctx, entry.UniversalTxId)
		if err != nil {
			return true, err
		}
		if !exists {
			return false, nil
		}
		for _, ob := range utx.OutboundTx {
			if ob.DestinationChain == chain && ob.Id == outboundId {
				found = true
				return true, nil // stop walking
			}
		}
		return false, nil
	})
	if err != nil {
		return false, err
	}
	return found, nil
}
