Looking at the external bug's two invariants — (1) off-by-one in a threshold comparison (`>=` vs `>`) and (2) missing limit on number of actions — I need to check nearcore's runtime for analogous mismatches between spec and implementation.

### Title
Delegate Action Expiry Check Uses `>` Instead of `>=`, Allowing Execution One Block Beyond Spec-Defined Deadline — (`File: runtime/runtime/src/actions.rs`)

### Summary

The runtime spec states that a `DelegateAction` must be rejected when `block_height >= max_block_height`. The implementation uses a strict `>` comparison, so a delegate action is accepted and executed at the block whose height exactly equals `max_block_height`. This is a direct spec/implementation mismatch of the same off-by-one class as the external report.

### Finding Description

`docs/RuntimeSpec/Actions.md` line 402 specifies the expiry condition as:

> "If the current block is **equal or greater than** `max_block_height`" → `DelegateActionExpired`

The implementation in `apply_delegate_action` (`runtime/runtime/src/actions.rs:435`) is:

```rust
if apply_state.block_height > delegate_action.max_block_height() {
    result.result = Err(ActionErrorKind::DelegateActionExpired.into());
    return Ok(());
}
```

The guard uses `>` (strictly greater than), not `>=`. Consequently, when `block_height == max_block_height`, the condition is `false`, the action is **not** rejected, and execution continues normally — the opposite of what the spec mandates.

The test `test_delegate_action_max_height` only exercises `max_block_height + 1` (strictly greater), never the equal case, so the off-by-one is untested and undetected. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation

A `DelegateAction` is a signed meta-transaction: the user (sender) signs a payload that includes `max_block_height` as a TTL bound, and a relayer submits it. The user's intent is that the action becomes invalid at block `max_block_height`. Because the implementation uses `>` instead of `>=`, a relayer can withhold the action and submit it exactly at block `max_block_height`, one block beyond the user's intended deadline. Any state changes (token transfers, key additions, contract calls) encoded in the delegate action's inner actions are then applied against the user's account at a block the user explicitly intended to be out-of-range.

The nonce mechanism prevents the same delegate action from being replayed a second time, but it does not prevent the single execution at the boundary block. The user's only mitigation is to set `max_block_height = intended_last_valid_block - 1`, which contradicts the documented spec. [4](#0-3) [5](#0-4) 

### Likelihood Explanation

Triggering the boundary condition requires a relayer to time submission precisely to the block at `max_block_height`. This is feasible: block production is deterministic and predictable, and a relayer who has received a signed delegate action can observe the chain and submit at the exact boundary block. The user has no on-chain recourse once the signed payload is in the relayer's hands. [2](#0-1) 

### Recommendation

Change the comparison from strict `>` to `>=` to match the specification:

```rust
// Before (wrong):
if apply_state.block_height > delegate_action.max_block_height() {

// After (correct, matches spec):
if apply_state.block_height >= delegate_action.max_block_height() {
```

Add a test case where `apply_state.block_height == delegate_action.max_block_height` and assert `DelegateActionExpired` is returned. [1](#0-0) 

### Proof of Concept

1. User creates and signs a `DelegateAction` with `max_block_height = N` (intending it to expire at block `N`).
2. User hands the signed payload to a relayer.
3. Relayer waits until the chain reaches block `N`.
4. At block `N`, the relayer submits the delegate action.
5. The runtime evaluates `apply_state.block_height > delegate_action.max_block_height()` → `N > N` → `false` → action is **not** expired.
6. `validate_delegate_action_key` runs, nonce is valid (not yet consumed), and the inner actions (e.g., `Transfer`, `FunctionCall`) execute against the user's account.
7. The user's funds or account state are modified at a block the user explicitly intended to be the expiry boundary. [6](#0-5) [2](#0-1)
