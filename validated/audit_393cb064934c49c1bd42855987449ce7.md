### Title
Failed deposits are unconditionally removed from `DepositDataMempool`, permanently freezing the corresponding BTC - (File: `crates/sequencer/src/runner.rs`)

### Summary
`produce_l2_block_inner` fetches a batch of deposits from `DepositDataMempool` via `fetch_deposits` and later calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using that same original, unfiltered batch, regardless of whether each individual deposit actually succeeded in `process_sys_txs`. Any deposit that fails to apply (out-of-gas, EVM revert, or any other `EvmSystemTransactionNotSuccessful` cause) is skipped/reverted in `process_sys_txs` but is still removed from the mempool at the end of block production, so it is never retried and the corresponding Bitcoin deposit can never be minted.

### Finding Description
The claimed binding is: `deposit ∈ DepositDataMempool after block production` `==` `NOT(deposit successfully applied to BridgeWrapper::deposit)`. Tracing the code shows this binding is broken.

`produce_l2_block_inner` fetches deposits with `fetch_deposits` [1](#0-0)  and stores them in the local `deposit_data` variable. This same variable, unmodified, is passed into `dry_run_transactions` → `produce_and_run_system_transactions` → `process_sys_txs` [2](#0-1) .

Inside `process_sys_txs`, each deposit is turned into a system transaction and applied via `self.stf.apply_l2_block_txs`. If it fails with `EvmSystemTransactionNotSuccessful`, the working set is reverted and the loop simply `continue`s without adding the transaction to `all_txs` — i.e., there is no state change, the deposit is not applied, and it is silently dropped from the returned transaction list: [3](#0-2) .

Crucially, no record is kept of which deposits in the original `deposit_data` batch actually succeeded — `dry_run_transactions`/`produce_and_run_system_transactions` returns only `all_txs`/`(all_txs, l1_fee_failed_txs, senders)`, with no per-deposit success flag propagated back to `produce_l2_block_inner`.

At the end of block production, the code unconditionally removes the *entire original* `deposit_data` batch from the mempool: [4](#0-3) . `DepositDataMempool::remove_deposits` computes `calc_tx_id` for each deposit in the passed slice and removes matching entries from both `accepted_deposit_txs` and `pending_deposits` unconditionally [5](#0-4) .

Thus any deposit that fails during `process_sys_txs` for any reason (gas exhaustion during ABI decode/SPV verification loop with an attacker-crafted maximal-size Merkle `proof`/`witness`, a state-dependent gas cost difference between the RPC-time `eth_call` simulation and actual block-time execution, or any other revert) is removed from the mempool exactly as if it had succeeded. Since Solidity reverts undo all state including `processedTxIds`, the deposit is never marked as processed on-chain, yet it disappears from the sequencer's only tracking structure (`accepted_deposit_txs`/`pending_deposits`) for retry. There is no other mechanism in the codebase that re-queues or retries a failed deposit.

### Impact Explanation
This results in the Critical impact category "funds permanently frozen": a real Bitcoin deposit, whose funds are already locked in the bridge multisig on the Bitcoin side, becomes permanently unmintable on Citrea because the sequencer's only reference to it (the `DepositDataMempool` entry) is deleted after a failed apply attempt, without the corresponding `BridgeWrapper::deposit` state change ever taking effect. This is not limited to attacker-controlled deposits — any deposit (including honest depositors') that happens to fail during `process_sys_txs` due to gas variance, contract-state-dependent reverts, or any other transient condition is silently and permanently dropped. The bug is deterministic and repeatable across every L2 block/every deposit batch that experiences any deposit-application failure.

### Likelihood Explanation
Preconditions: any deposit blob accepted into the mempool via `citrea_sendRawDepositTransaction` (which only requires that the `eth_call` simulation at submission time succeeds) that subsequently fails when actually applied during block production. This can be triggered without any privileged role — an attacker (or even an honest user, unintentionally) submits a deposit whose gas usage is borderline relative to `SYSTEM_TX_GAS_LIMIT`, or crafts inputs (e.g., maximal witness/Merkle proof sizes) that push gas usage over the limit specifically at production time due to state differences (cold/warm storage access, differing base state between simulation and production), causing `EvmSystemTransactionNotSuccessful`. Cost is limited to the on-chain Bitcoin transaction fee needed to create the deposit UTXO plus normal RPC submission; no privileged keys or majority hashrate are required. The failure mode is fully reproducible in a `cargo test` using the sequencer runner logic.

### Recommendation
Track which deposits from the fetched `deposit_data` batch were actually included in `all_txs` (successfully applied) during `process_sys_txs`/`produce_and_run_system_transactions`, and only pass that successfully-applied subset to `remove_deposits`. Deposits that fail to apply must remain in `DepositDataMempool` (or be explicitly requeued) so they can be retried in a later block instead of being unconditionally removed alongside successful ones.

### Proof of Concept
`cargo test` plan (new integration test in `crates/sequencer/src/runner.rs` or a sequencer test module):
1. Populate `DepositDataMempool` with two deposit blobs: `deposit_ok` (valid, applies successfully) and `deposit_fail` (crafted so `apply_l2_block_txs` returns `EvmSystemTransactionNotSuccessful`, e.g., a receiver contract that reverts, or a gas-limit-exceeding oversized witness/proof).
2. Call `fetch_deposits` to obtain both, then invoke `produce_and_run_system_transactions` (or the full `produce_l2_block_inner` flow) with both deposits in a single batch.
3. Assert that only `deposit_ok`'s system transaction appears in the returned `all_txs`, and that `deposit_fail` triggered the revert-and-continue path in `process_sys_txs` with `*nonce` decremented.
4. After block production completes and `remove_deposits(&deposit_data)` is invoked with the original two-deposit batch, assert on `DepositDataMempool` state: `deposit_ok` is correctly absent (success), but assert `deposit_fail` is **still present** in `accepted_deposit_txs`/`pending_deposits` for retry.
5. Show the current code fails this last assertion — `deposit_fail` is removed despite never having been applied to `BridgeWrapper::deposit`, proving the binding `retained_in_mempool == NOT(applied_successfully)` is violated.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
