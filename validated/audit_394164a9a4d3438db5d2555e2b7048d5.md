### Title
`ExchangeInjectActuator` unguarded `long` multiplication overflows despite `BigInteger`-safe validation, causing legitimate liquidity injections to revert - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
The Sherlock report describes `Vault::_calcDeposit()` computing `depositAmount * bal * totalSupply` with full-precision primitives, which overflows for low-priced tokens even though the mathematically correct result would fit, causing deposits to revert. The same bug class — a primitive-precision multiplication that overflows even though the true (BigInteger) result is valid and within all enforced limits — exists in `ExchangeInjectActuator`, where `doValidate()` computes the exchange amount safely with `BigInteger` but `execute()` recomputes it with raw `long` arithmetic (`multiplyExact`), which can overflow and throw, aborting a transaction that was accepted at validation time.

### Finding Description
In `doValidate()`, the "another token" amount is computed with full `BigInteger` precision, avoiding any overflow: [1](#0-0) 

This value is checked against `dynamicStore.getExchangeBalanceLimit()` and account balances, and the transaction is accepted if it passes: [2](#0-1) 

However, `execute()` independently re-derives the exact same quantity using **unbounded-precision-unsafe primitive `long` arithmetic** instead of the `BigInteger` path used in validation: [3](#0-2) 

`multiplyExact(secondTokenBalance, tokenQuant)` (or `multiplyExact(firstTokenBalance, tokenQuant)`) computes the full numerator product before dividing by the other balance — exactly the same overflow-prone pattern as `Vault::_calcDeposit()`'s `depositAmount * bal * totalSupply`. Because `firstTokenBalance`/`secondTokenBalance` can independently be as large as `dynamicStore.getExchangeBalanceLimit()` (a governance-tunable cap that is not bounded to `sqrt(Long.MAX_VALUE)`), and `tokenQuant` can also be large (bounded only by the same balance limit and the injector's own asset balance), the intermediate product `secondTokenBalance * tokenQuant` can exceed `Long.MAX_VALUE` (~9.22e18) even when the final quotient `anotherTokenQuant` (after dividing by `firstTokenBalance`) is small and well within the balance limit — precisely the scenario the Sherlock report describes for low-valued/high-supply tokens.

Since the `BigInteger`-based `doValidate()` path never overflows, such a transaction passes validation. But at `execute()` time, the primitive `multiplyExact` throws `ArithmeticException`, which is caught and converted into `ContractExeException`, failing the transaction after it was accepted into a block: [4](#0-3) 

This is a genuine divergence between the validation and execution arithmetic paths — analogous to `Vault::_calcDeposit()`'s failure to downscale precision before multiplying.

### Impact Explanation
A legitimate `ExchangeInjectContract` that correctly passes on-chain validation can still fail at execution due to arithmetic overflow, wasting the transaction's block slot/bandwidth and causing the exchange-liquidity injection to fail non-deterministically depending on token balances — the same "missed favorable action, wasted resources" impact class described in the report. Unlike `ExchangeWithdrawActuator`, which already performs its execute-time calculation with `BigInteger` (see `bigFirstTokenBalance`/`bigSecondTokenBalance` usage), `ExchangeInjectActuator`'s `execute()` was not hardened the same way, creating an inconsistency between the two related actuators.

### Likelihood Explanation
Only the pool creator can call `ExchangeInjectActuator` (enforced by `doValidate()`'s creator check), which somewhat narrows the actor set, but exchange creation itself is fully permissionless — any account can call `ExchangeCreateActuator` and become a creator of its own pool. Reaching the overflow only requires the two token balances in the pool and injected quantity to be large enough that their product exceeds `Long.MAX_VALUE`, which is plausible for low-decimal/high-supply TRC10/TRC20-mirrored tokens injected into a pool that has grown near `dynamicStore.getExchangeBalanceLimit()`.

### Recommendation
Replace the raw `multiplyExact`/`floorDiv` computation in `ExchangeInjectActuator.execute()` (lines 73–80) with the same `BigInteger`-based calculation already used in `doValidate()` (or reuse a single shared helper), so that the execution-time result cannot diverge from — or fail relative to — the validated result, consistent with how `ExchangeWithdrawActuator.execute()` already computes its value via `BigInteger`.

### Proof of Concept
1. Two accounts each create/inject into an exchange pool until `firstTokenBalance` and `secondTokenBalance` both approach `dynamicStore.getExchangeBalanceLimit()` (e.g., ~1e15–1e18 depending on configured limit).
2. Creator submits `ExchangeInjectContract` with `tokenID = firstTokenID` and a `tokenQuant` such that `secondTokenBalance * tokenQuant > Long.MAX_VALUE` while `secondTokenBalance * tokenQuant / firstTokenBalance` (the true `anotherTokenQuant`) remains small and within `balanceLimit` and the creator's own balances.
3. `doValidate()` computes `anotherTokenQuant` via `BigInteger` — succeeds, passes all checks (lines 215–256).
4. `execute()` calls `multiplyExact(secondTokenBalance, tokenQuant)` (line 73–74) — throws `ArithmeticException` because the intermediate product overflows `long`, even though the final validated quantity was safe.
5. The exception is caught and rethrown as `ContractExeException` (lines 107–111), and the transaction fails despite having passed validation — mirroring the `Vault::_calcDeposit()` overflow-revert behavior from the source report.
