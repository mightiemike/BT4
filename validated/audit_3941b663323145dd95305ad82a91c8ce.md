## Analysis

The external report's bug pattern is a **fee-classification bypass**: an attacker controls which "kind" of operation the system believes it is executing (by manipulating an external/attacker-controlled value), and the fee-charging logic only fires for one classification branch while the economically-equivalent operation slips through an unfeed branch.

The closest reachable analog in this nearcore tree is in the **NEAR wallet contract** (`runtime/near-wallet-contract`), which lets any unprivileged caller (a "relayer") submit an RLP-encoded Ethereum transaction on behalf of an eth-implicit account and have it translated into a Near action.

### Finding Description

`parse_rlp_tx_to_action` computes a `tx_fee` meant to compensate whichever relayer submits the transaction: [1](#0-0) 

That `tx_fee` is only attached to the returned `TransactionKind` — and therefore only actually paid to the relayer in `inner_rlp_execute` — when the classification comes out as `EthEmulationKind::EOABaseTokenTransfer` or `EthEmulationKind::ERC20Transfer`: [2](#0-1) 

The classification itself is decided purely by matching the first 4 bytes of `tx.data` (a value the transaction's signer controls) in `parse_tx_data`: [3](#0-2) [4](#0-3) 

If the selector is `FUNCTION_CALL_SELECTOR`, the payload is decoded into a generic `Action::FunctionCall { receiver_id, method_name, args, gas, yocto_near }` and classified as `ParsableTransactionKind::NearNativeAction`, which becomes `TransactionKind::NearNativeAction` — a branch that carries **no fee at all**, per the match in `parse_rlp_tx_to_action`: [5](#0-4) 

Only if the selector falls through to `eth_emulation::try_emulation` (the ERC‑20 emulation path) does the resulting `EthEmulationKind::ERC20Transfer{ fee, .. }` retain and forward `tx_fee` for actual payment to the relayer.

### Impact Explanation

Because `receiver_id`/`method_name`/`args` in the `FUNCTION_CALL_SELECTOR` branch are fully attacker(signer)-controlled, the wallet owner can encode an economically-identical NEP-141 token transfer (e.g. `method_name = "ft_transfer"`, `args` = the transfer JSON, targeting any NEP-141 contract as `receiver_id`/`target`) as a `NearNativeAction` instead of letting it fall into the `ERC20Transfer` emulation path. This is functionally the same value-moving operation the `ERC20Transfer` fee was designed to compensate, but it completely avoids attaching/sending `tx_fee` to the relayer — the fee computed at line 59-64 is silently discarded once the `NearNativeAction` branch is taken. A relayer that expects to be compensated (per the design comment at lines 54-58) for shepherding the user's fee‑bearing transaction is instead given zero payment for relaying what is, in effect, an ERC-20/NEP-141 transfer. This is a direct analog of the ZRX finding: the attacker manipulates which classification branch of the fee logic is taken (there: `boughtERC20Amount` counterfeit signal; here: the 4-byte selector) so that a value-transfer that should carry a fee is instead classified into a fee-free branch.

### Likelihood Explanation

Any account that owns/controls a wallet-contract deployment can construct such a transaction unilaterally — no special privileges, no reliance on malicious peers/validators, and it is reachable directly through the contract's public `rlp_execute` entry point that any relayer (or the owner itself acting as relayer) submits as an ordinary FunctionCall transaction.

### Recommendation

Compute and attach `tx_fee` uniformly based on the *semantic effect* of the decoded action (e.g., whenever the resulting action is a value transfer/NEP-141 transfer-equivalent call), rather than gating fee payment purely on which raw ABI selector matched. Alternatively, require that any `FunctionCall` action whose target/method matches a known fungible-token transfer interface be forced through the `ERC20Transfer` classification (and its associated fee), instead of allowing it to be encoded as an unfeed `NearNativeAction`.

### Proof of Concept

1. As the eth-implicit wallet owner, encode an Ethereum transaction whose `data` begins with `FUNCTION_CALL_SELECTOR` and ABI-encodes `(receiver_id = "<nep141-token>.near", method_name = "ft_transfer", args = <json for a transfer>, gas, yocto_near = 0)`, with `target = "<nep141-token>.near"`.
2. Submit this via `rlp_execute` through any relayer. `validate_tx_relayer_data` and `parse_tx_data` classify it as `TransactionKind::NearNativeAction` (`internal.rs:83-86`, `244-256`).
3. `inner_rlp_execute`'s fee-forwarding branch (`lib.rs:374-385`) only fires for `EOABaseTokenTransfer`/`ERC20Transfer`, so no `promise_batch_action_transfer` refund is created for the relayer even though `tx_fee` was computed from `max_fee_per_gas * gas_limit`.
4. The FT transfer executes normally (equivalent economic effect to an `ERC20Transfer`), but the relayer receives none of the compensation the fee mechanism was designed to provide.

fn parse_tx_data(
    target: &AccountId,
    tx: &NormalizedEthTransaction,
    fee: NearToken,
    context: &ExecutionContext,
) -> Result<(Action, ParsableTransactionKind), Error> {
    if tx.data.len() < 4 {
        return Err(Error::User(UserError::InvalidAbiEncodedData));
    }
    match &tx.data[0..4] {
        FUNCTION_CALL_SELECTOR => {
            let (receiver_id, method_name, args, gas, yocto_near): (String, _, _, _, _) =
                ethabi_utils::abi_decode(&FUNCTION_CALL_SIGNATURE, &tx.data[4..])?;
            if target.as_str() != receiver_id.as_str() {
                return Err(Error::Relayer(RelayerError::InvalidTarget));
            }
            if yocto_near >= MAX_YOCTO_NEAR {
                return Err(Error::User(UserError::ExcessYoctoNear));
            }
            Ok((
                Action::FunctionCall { receiver_id, method_name, args, gas, yocto_near },
                ParsableTransactionKind::NearNativeAction,
            ))
