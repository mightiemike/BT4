## Finding: CEA recipient contracts are forced to pay attacker-chosen gas costs on inbound payload execution, with no consent or cap

### Title
Attacker-controlled `gas_limit`/execution cost in `UniversalPayload` drains a CEA recipient contract's PC balance without its consent - (File: `x/uexecutor/keeper/fees.go`, `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
The external report describes the maker buyer being forced to reimburse gas cost at whatever `tx.gasprice` the executor happens to use, with no cap the buyer controls. Push Chain's CEA (Custom Execution Account, `IsCEA=true`) inbound flow reproduces the same class of bug in a stronger form: the entity billed for gas — the recipient smart contract's own on-chain `upc` balance — never sets or approves any of the parameters that determine how much it will be billed. Those parameters (`gas_limit`, `max_fee_per_gas`, `max_priority_fee_per_gas`, calldata) are entirely supplied by the unprivileged external sender of the cross-chain inbound message.

### Finding Description
When an inbound is `IsCEA=true` with `TxType_FUNDS_AND_PAYLOAD` or `TxType_GAS_AND_PAYLOAD`, the executor calls `executeUniversalTx` on the recipient contract via `CallExecuteUniversalTx`, then bills the *recipient contract's own* `upc` balance for the resulting gas cost: [1](#0-0) 

The billed amount comes from `DeductGasFeesFromReceipt`, which computes `gasCost = effectiveGasPrice * gasUsed` and burns it from the recipient's account: [2](#0-1) 

`effectiveGasPrice` is derived from the current network base fee, and the only bound applied is that `maxFeePerGas >= baseFee` (a floor check, not a ceiling on the attacker): [3](#0-2) 

Crucially, `gas_limit`, `max_fee_per_gas`, `max_priority_fee_per_gas`, and `data` all originate from `UniversalPayload`, which is populated from the inbound event on the *source chain* — fully controlled by whoever submits the deposit+payload, not by the CEA contract owner: [4](#0-3) 

`ValidateBasic`/`ValidateForExecution` only check that these fields are well-formed non-negative integers — there is no upper bound on `gas_limit`, no per-chain/per-contract cap, and no mechanism for the CEA contract to opt into or reject a specific gas budget: [5](#0-4) 

The gas limit is then passed straight through to the real EVM execution with no independent cap: [6](#0-5) 

### Impact Explanation
An unprivileged external attacker can submit repeated cross-chain inbound messages (deposits of arbitrarily small/zero amount plus a payload) targeting any CEA-configured recipient contract, each carrying a large attacker-chosen `gas_limit` and calldata engineered to consume close to that limit (e.g., invoking an expensive but otherwise harmless path on the target, or simply wasting gas inside the call). Each such inbound causes `DeductGasFeesFromReceipt` to burn `gasUsed * baseFee` worth of `upc` from the victim contract's own balance — funds the contract owner never approved a cap for. Repeating this drains the victim contract's native PC gas reserve to zero, which is a real, permanent loss of protocol/user-controlled funds triggered purely by ordinary, unprivileged inbound submission — matching the "unauthorized burn" / "gas fee accounting corruption" impact categories in scope.

### Likelihood Explanation
High. No privileged role, validator collusion, or TSS/oracle manipulation is required — an attacker only needs to submit a normal cross-chain deposit event with a crafted `UniversalPayload` to a CEA recipient, which is the intended, user-reachable entry point for CEA payload execution. The vote/ballot finalization by honest UVs does not validate or bound the payload's gas parameters before execution.

### Recommendation
- Require the CEA recipient contract to explicitly opt in to (or register) a maximum gas price/limit it is willing to pay per inbound execution, similar to the report's recommended `maxGasCost` parameter, rather than trusting the attacker-supplied `UniversalPayload.GasLimit`/`MaxFeePerGas`.
- Enforce a protocol-wide or per-chain ceiling on `gas_limit` in `UniversalPayload.ValidateBasic`/`ValidateForExecution` for CEA-routed executions.
- Consider billing gas costs from a bonded/staked deposit associated with the *sender* of the inbound (or from a pre-funded escrow) rather than debiting the recipient contract's balance unconditionally.

### Proof of Concept
1. Deploy/registry a CEA contract as recipient for a supported source chain (per `x/uregistry` token/chain config), and fund it with `upc`.
2. As an unprivileged attacker, submit a source-chain deposit event (or the corresponding inbound vote path once validators observe it) with `IsCEA=true`, `TxType_GAS_AND_PAYLOAD`, `Amount="0"`, and `UniversalPayload{ GasLimit: "<very large>", Data: "<calldata designed to consume near GasLimit>", MaxFeePerGas: "<sufficiently high>", ... }`.
3. Once 2/3 quorum of UVs vote the inbound (a routine, non-privileged process for any valid on-chain event), `ExecuteInboundGasAndPayload`/`ExecuteInboundFundsAndPayload` executes `CallExecuteUniversalTx` against the CEA contract and then calls `DeductGasFeesFromReceipt`, burning `gasUsed * baseFee` upc from the CEA contract's balance.
4. Repeat with new zero/low-value deposits to progressively drain the CEA contract's `upc` balance without its consent. [7](#0-6)

func (k Keeper) DeductGasFeesFromReceipt(
	ctx context.Context,
	sdkCtx sdk.Context,
	recipient common.Address,
	receipt *evmtypes.MsgEthereumTxResponse,
	universalPayload *types.UniversalPayload,
) error {
	if receipt == nil || receipt.GasUsed == 0 {
		return nil
	}
	if universalPayload == nil {
		return nil
	}

	abiPayload, err := types.NewAbiUniversalPayload(universalPayload)
	if err != nil {
		return fmt.Errorf("failed to parse payload for gas deduction: %w", err)
	}

	baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)
	if baseFee.IsNil() {
		return fmt.Errorf("base fee not found")
	}

	gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
	if err != nil {
		return fmt.Errorf("failed to calculate gas cost: %w", err)
	}
	if gasCost.Sign() <= 0 {
		return nil
	}

	gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
	if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
		return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
	}

	recipientAccAddr := sdk.AccAddress(recipient.Bytes())
	balance := k.bankKeeper.GetBalance(sdkCtx, recipientAccAddr, pchaintypes.BaseDenom)

	if err := k.DeductAndBurnFees(ctx, recipientAccAddr, gasCost); err != nil {
		return fmt.Errorf("insufficient gas: required %s upc, available %s upc, gas_used %d, from %s: %w",
			gasCost.String(), balance.Amount.String(), receipt.GasUsed, recipient.Hex(), err)
	}

// CallExecuteUniversalTx calls executeUniversalTx on a smart-contract recipient.
// This is used for isCEA inbounds whose recipient is a deployed contract (not a UEA).
func (k Keeper) CallExecuteUniversalTx(
	ctx sdk.Context,
	recipientAddr common.Address,
	sourceChain string,
	ceaAddress []byte,
	payload []byte,
	amount *big.Int,
	prc20AssetAddr common.Address,
	txId [32]byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	recipientABI, err := types.ParseRecipientContractABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse recipient contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		recipientABI,
		ueModuleAccAddress,
		recipientAddr,
		big.NewInt(0),
		nil,
		true,
		false,
		true,
		&nonce,
		"executeUniversalTx",
		sourceChain,
		ceaAddress,
		payload,
		amount,
		prc20AssetAddr,
		txId,
	)
