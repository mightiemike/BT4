### Title
Exchange (Bancor-style AMM) becomes permanently frozen once either token reserve reaches zero, locking creator/user funds - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The TRX/TRC10 Exchange (Bancor-formula AMM) actuators unconditionally reject `ExchangeTransactionContract`, `ExchangeWithdrawContract`, and `ExchangeInjectContract` transactions once either of the exchange's two token reserves reaches exactly zero. Any unprivileged user can drive a reserve to zero purely through normal, permitted trading via `ExchangeTransactionActuator`, after which the exchange is permanently closed with no recovery path, freezing the creator's remaining reserve and preventing anyone from injecting new liquidity or withdrawing funds.

### Finding Description
`ExchangeTransactionActuator.doValidate()` and `ExchangeWithdrawActuator.doValidate()` both contain the same guard: [1](#0-0) [2](#0-1) 

which reverts every subsequent call once `firstTokenBalance == 0 || secondTokenBalance == 0`. This is the exact same "check that permanently disables downstream state transitions once a value hits an extreme (zero)" pattern from the reported bug class, except the trigger here is the AMM's own internal reserve balance rather than an external price oracle.

The reserve balances are mutated on every successful trade in `ExchangeCapsule.transaction()`: [3](#0-2) 

The Bancor curve implemented in `ExchangeProcessor.exchangeFromSupply`/`exchangeToSupply` is theoretically asymptotic (never fully drains a reserve), but the computation is done in double-precision floating point and then truncated to `long`: [4](#0-3) 

Because `Maths.pow` uses floating-point math, for reserves that are small enough (or after enough successive drain trades against one side), the truncation/rounding error can cause the computed `buyTokenQuant` to equal or exceed the full remaining reserve, driving one of `firstTokenBalance`/`secondTokenBalance` to exactly `0`. From that point forward:
- `ExchangeTransactionActuator` (further trades) reverts via the same "exchange has been closed" check.
- `ExchangeInjectActuator` (adding liquidity to reopen the pool) reverts on the identical check.
- `ExchangeWithdrawActuator` — the only path for the exchange creator to reclaim their remaining reserve of the *other* token — also reverts on the identical check.

No committee/proposal parameter or admin actuator was found that can reset an exchange's reserve balances or bypass this check, so once triggered the state is unrecoverable through any documented on-chain path.

### Impact Explanation
Once a reserve hits zero, the exchange is permanently bricked: the creator's remaining balance of the non-zero token, and any TRX/TRC10 previously injected into the pool, becomes permanently locked in the `ExchangeStore`/`ExchangeV2Store` capsule with no actuator able to move it out. This is reachable by any unprivileged account simply broadcasting `ExchangeTransactionContract` transactions (a standard, permissionless transaction type), so it directly causes asset lock/loss for the exchange creator without requiring any privileged role — matching the "permanent lock/freeze state created through reachable user action" and "asset/accounting corruption" criteria.

### Likelihood Explanation
Reaching exactly zero requires either favorable floating-point rounding behavior in `ExchangeProcessor` for adversarially chosen quantities, or (more reliably) reserves that are already small (e.g., a low-liquidity exchange, or one that has already been drained close to zero by legitimate trading) where the remaining integer/long truncation of the double-precision Bancor computation returns a value equal to the full remaining balance. Because trade quantities and reserve sizes are fully attacker-controlled inputs to `ExchangeTransactionContract`, an attacker can iteratively probe/trade to search for the exact input that produces `buyTokenQuant == remaining reserve`, making this practically triggerable rather than purely theoretical.

### Recommendation
Add a dedicated recovery/close-out path (e.g., allow the exchange creator to withdraw remaining balance of the non-zero token even when the other side is zero), and/or change the reserve check in `ExchangeWithdrawActuator` to only block withdrawal of the token whose balance is actually zero rather than blocking withdrawal of the *other* token as well. Additionally, consider using `SafeExchangeProcessor`/exact (non-floating-point) arithmetic consistently so a reserve cannot round down to exactly zero through normal trading, and add a floor (minimum reserve) enforcement in `ExchangeCapsule.transaction()` similar to constant-product AMMs' minimum-liquidity protections.

### Proof of Concept
1. `ExchangeCreateActuator` creates an exchange with a small `firstTokenBalance`/`secondTokenBalance` (creator-chosen, no floor enforced beyond `>0`).
2. Attacker (unprivileged) repeatedly broadcasts `ExchangeTransactionContract` selling the counter-token, driving `firstTokenBalance` (or `secondTokenBalance`) down via `ExchangeCapsule.transaction()` -> `ExchangeProcessor.exchange()`.
3. Due to double-precision truncation in `exchangeFromSupply`/`exchangeToSupply` (`(long) exchangeBalance`), a final trade computes `buyTokenQuant` equal to the entire remaining reserve, setting it to `0` (see `ExchangeCapsule.java:160-166`, which only rejects negative balances, not exact zero).
4. Any subsequent `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` referencing this exchange ID now reverts at the `firstTokenBalance == 0 || secondTokenBalance == 0` check in the respective actuator's `doValidate()`.
5. The exchange creator can never withdraw the remaining balance of the non-zero token, permanently locking those funds.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
