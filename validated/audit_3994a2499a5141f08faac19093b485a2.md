## Title
Stale-fee recalculation in `MarketCancelOrderActuator` can block users from canceling exchange orders after a governance fee change - (`File: actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java`)

### Summary
`MarketCancelOrderActuator` charges the *current* `MARKET_CANCEL_FEE` governance parameter when a user cancels an open TRC10 market order, rather than the fee that was in effect (or reserved) when the order was created. Since `MARKET_CANCEL_FEE` is a chain parameter that the committee can change at any time via a proposal, a user who placed an order under one fee regime can be forced to pay a different, possibly higher, fee at cancellation time — and if their current balance can't cover it, the cancellation transaction reverts, leaving their locked sell-side assets stuck in the order book. This mirrors the Superfluid `cancelProgram()` bug class: an amount that should be fixed at creation time is instead recomputed from a mutable governance parameter at a later settlement/cancellation step.

### Finding Description
When a user places an order via `MarketSellAssetActuator.execute()`, a fee is charged based on the *current* `MARKET_SELL_FEE`: [1](#0-0) 

The order itself does not persist any fee-related field — `MarketOrderCapsule` only stores the sell/buy token amounts, remaining quantity, owner, and state; no snapshot of the fee context is stored.

Later, when the user calls `MarketCancelOrderActuator` to cancel that same (possibly long-lived, unmatched) order, the fee actually charged is recomputed from the *current* `MARKET_CANCEL_FEE`, fetched fresh from `DynamicPropertiesStore` at cancellation time: [2](#0-1) 

This fee is deducted from the owner's balance in `execute()`: [3](#0-2) 

and is enforced as a precondition in `validate()`, where insufficient balance causes an outright revert: [4](#0-3) 

`MARKET_CANCEL_FEE` is a committee-governed parameter, validated with a wide allowed range `[0, 10_000_000_000]` SUN and can be updated at any time via a proposal: [5](#0-4) 

and applied immediately to `DynamicPropertiesStore` once the proposal passes: [6](#0-5) 

Because the order was created and left resting in the order book potentially for a long time (no expiration mechanism for unmatched orders), any committee-driven increase of `MARKET_CANCEL_FEE` that occurs while the order is outstanding will retroactively apply to that order's cancellation, even though the user had no ability to anticipate or budget for the new fee when they locked their assets into the order.

### Impact Explanation
An unprivileged market participant places a sell order, locking their TRX/TRC10 balance into `MarketOrderCapsule` state (`transferBalanceOrToken`). If governance later raises `MARKET_CANCEL_FEE` (a legitimate, permitted governance action within the documented range) and the user's spendable TRX balance at cancellation time is below the new fee, `MarketCancelOrderActuator.validate()` throws `ContractValidateException("No enough balance !")` and the cancellation reverts. The user cannot retrieve their locked sell-token remainder (`MarketUtils.returnSellTokenRemain`) until they top up their balance to cover the new, unanticipated fee — an invalid-state/DoS condition on order cancellation and a real, concrete accounting divergence from the fee regime the user transacted under. This is a genuine, unprivileged-user-facing impact (temporary fund lock / inability to exit a position), consistent with the "incorrect recalculation using mutable governance parameters causing revert" bug class described in the source report.

### Likelihood Explanation
`MARKET_CANCEL_FEE` changes require a passed committee proposal, so likelihood is bounded by governance activity, but the report's own precedent (Superfluid case is "acknowledged, won't fix" due to being a real but governance-triggered edge case) applies equally here: any legitimate parameter adjustment while orders remain outstanding in the order book (there is no enforced expiry on resting orders) will trigger this divergence for any user whose balance is fee-constrained at cancellation time.

### Recommendation
Snapshot the applicable cancel fee (or an equivalent reserved amount) in `MarketOrderCapsule` at order-creation time, and have `MarketCancelOrderActuator.calcFee()` read that stored value instead of re-querying the live `MARKET_CANCEL_FEE` from `DynamicPropertiesStore`. This guarantees cancellation cost is fixed and predictable at order placement, independent of subsequent governance changes.

### Proof of Concept
1. User calls `MarketSellAssetActuator` to place a sell order; `MARKET_SELL_FEE` is charged and the order rests unmatched in the book (`MarketOrderCapsule`, no fee data stored).
2. Committee proposes and passes a `MARKET_CANCEL_FEE` increase via `ProposalService` (allowed range up to `10_000_000_000` SUN, per `ProposalUtil`).
3. User's spendable balance is less than the new `MARKET_CANCEL_FEE` (e.g., they only kept enough to cover the fee at time of order placement).
4. User calls `MarketCancelOrderActuator`; `validate()` recomputes `calcFee()` from the new, higher `MARKET_CANCEL_FEE`, finds `ownerAccount.getBalance() < fee`, and reverts with `"No enough balance !"`, leaving the order's locked assets inaccessible until the user acquires more TRX.
