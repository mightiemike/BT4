## Finding

### Title
Replay-verify integrity check skips state-checkpoint root comparison, letting a diverged state root pass verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative "does the freshly-computed VM output match the persisted, ledger-committed `TransactionInfo`" check used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`). The function validates status, gas used, write-set hash, and event-root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that bind a transaction to the authenticated global state (Sparse-Merkle/Jellyfish-Merkle) root.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` computes and checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but then explicitly returns `Ok(())` with a code comment acknowledging the gap:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

`storage/db-tool/src/replay_on_archive.rs::execute_and_verify` re-executes historical transactions and calls exactly this function as its sole per-transaction correctness gate before treating a replayed chunk as verified: [3](#0-2) 

The `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields on `TransactionInfo` are precisely the values that summarize the Sparse-Merkle/JMT/position-state roots produced by `DoStateCheckpoint::run` (see the checkpoint-hash construction and the trading-native root path guarded by `execution_output.compute_trading_native_state_roots`) [4](#0-3)  and are assembled into the on-chain `TransactionInfo`/accumulator leaf by `assemble_transaction_infos` [5](#0-4) . These fields are the authenticated binding between a transaction and the ledger's global state root that clients ultimately trust via `TransactionInfoWithProof`/`StateProof` verification.

Because `ensure_match_transaction_info` never re-derives or compares these root hashes, a discrepancy that affects only the state/hot-state/position-state Merkle root computation (e.g., a bug in state-tree update logic, hot-state summary construction, or the newer position-state summary path) while leaving individual write-ops, events, gas and status unchanged, will not be detected by replay-verify. The tool will report a "successful replay" for a chunk whose actual computed state root diverges from the state root that is durably committed and served in authenticated API responses/state proofs.

### Impact Explanation
This breaks the "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" and "Hard-fork-only divergence during commit, replay, restore" integrity pivots. Replay-verify (`db-tool replay-on-archive`) exists specifically so that operators/auditors can prove that an archived, backed-up, or historical ledger segment's state matches what real execution would produce. If a bug elsewhere silently produces a wrong state-checkpoint root (state, hot-state, or the newer position-state tree used for trading-native features), this verification path will not surface it, giving false assurance that the state is bit-for-bit correct when the authenticated Merkle root actually diverges. That directly threatens confidence in Merkle proof integrity for anything anchored to that root (state proofs, restore manifests, epoch snapshots) and is the kind of undetectable state divergence that would only surface as a hard-fork-class disagreement between nodes/tools trusting different roots for the same version.

### Likelihood Explanation
The gap is not theoretical — it is explicitly documented by the maintainers as a known, currently-unmitigated hole tied to the upcoming `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature, meaning the state-root verification is scheduled to matter more as the position-state tree rolls out, while the check has not yet been added. Today it already blinds `replay_on_archive`, the CLI's transaction replayer, and `aptos-debugger` to any bug that corrupts only checkpoint-hash computation without altering the write set/event data. Triggering it does not require a malicious/privileged actor — a benign implementation bug in checkpoint-hash derivation (state, hot-state, or position-state) is sufficient, and it would go unnoticed by anyone relying on replay-verify for state-integrity assurance.

### Recommendation
Extend `ensure_match_transaction_info` to also compare (when both sides carry a value) `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against independently-recomputed checkpoint roots for the replayed range, and fail loudly on mismatch — exactly as the existing TODO instructs, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in production.

### Proof of Concept
1. In a local replay-verify run, use `storage/db-tool/src/replay_on_archive.rs` to replay a chunk of transactions from an `AptosDB`.
2. Inject (or simulate via a fault in a checkpoint-computation dependency) a bug that makes `DoStateCheckpoint::run` (`execution/executor/src/workflow/do_state_checkpoint.rs`) compute an incorrect `state_summary`/`hot state` root while leaving write-ops, events, gas, and status unchanged for the affected transactions.
3. Run `execute_and_verify`; observe that `ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) returns `Ok(())` because it never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, so `replay_on_archive` reports the chunk as successfully verified despite the diverging authenticated state root.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
