### Title
Unbounded growth of never-expiring ballots causes O(n) full-set scan on every new ballot creation, degrading/DoS-ing inbound, outbound, TSS, and fund-migration finalization - ([File: x/uvalidator/keeper/ballot.go])

### Summary
The Gov.sol bug is a class of "unbounded list growth + full iteration on every state-changing action → resource exhaustion." The closest reachable analog in this repo is `x/uvalidator`'s generic ballot machine: `CreateBallot` unconditionally calls `ExpireBallotsBeforeHeight`, which does a full linear walk of the shared `ActiveBallotIDs` set (used by inbound, outbound, chain-meta, TSS, and fund-migration ballots alike) every single time any module creates a new ballot [1](#0-0) , [2](#0-1) . Combined with `DefaultExpiryAfterBlocks` being set to `100_000_000` blocks (effectively disabling expiry "for ~19 years"), any ballot that never reaches quorum stays in `ActiveBallotIDs` forever [3](#0-2) .

### Finding Description
`CreateBallot` is invoked (via `GetOrCreateBallot`) on the first vote for every distinct observation - inbound, outbound, chain-meta, TSS event, or fund migration - and before storing the new ballot it always calls `ExpireBallotsBeforeHeight`, which iterates the entire `ActiveBallotIDs` key set, doing a `k.Ballots.Get` for each entry [4](#0-3) [2](#0-1) .

Ballot IDs are content-addressed hashes of the observation (`hex(marshal(Inbound))` for inbound, and a canonicalized digest that includes `Success`/`ErrorMsg`/`GasFeeUsed` for outbound observations) [5](#0-4) . Because validators independently observe and marshal external-chain events, any divergence among honest validators (timing differences, differing decoded gas fee, etc.) produces **multiple distinct ballot IDs ("variants") for the same logical event**, splitting votes across ballots that individually may never reach the 2/3+1 threshold [6](#0-5) .

Normally, a stuck ballot would eventually be swept via `MarkBallotExpired` once its `BlockHeightExpiry` passes. However, `DefaultExpiryAfterBlocks = 100_000_000` (~19 years at 6s blocks) means ballots are, in practice, never auto-expired [7](#0-6) . The presence of a dedicated one-off upgrade handler (`app/upgrades/purge-expired-outbounds`) whose sole job is to manually walk all pending outbounds and delete stale/expired ballots confirms that ballot accumulation without automatic pruning is an already-observed operational problem in this codebase [8](#0-7) .

An ordinary, unprivileged user does not need to compromise or bribe a validator to trigger this: simply sending many genuine but distinctly-formed deposit/crosschain-transfer transactions on an external source chain generates many `Inbound` observations for honest Universal Validators to vote on gaslessly via `MsgVoteInbound` [9](#0-8) . If any subset of these fail to converge to quorum (e.g., because they intentionally straddle edge-case decode paths, or simply arrive faster than the network can reach consensus on identical byte-for-byte payloads), they remain `PENDING` and accumulate permanently in the shared `ActiveBallotIDs` set (never expiring, never finalizing). Every subsequent `CreateBallot` call — for *any* ballot type, including unrelated TSS key-rotation or fund-migration ballots — must scan this ever-growing, un-prunable set, driving vote/finalization processing time toward O(n²) over the life of the chain, exactly mirroring the Gov.sol "prune all previous proposals on every new one" root cause.

### Impact Explanation
This is a state-machine-level resource-exhaustion vector reachable purely from unprivileged, ordinary crosschain deposit activity (no validator/admin/relayer compromise required). As the shared `Ballots`/`ActiveBallotIDs` collection grows unboundedly, block-processing time for `MsgVoteInbound`, `MsgVoteOutbound`, TSS-event votes, and fund-migration votes increases without bound, threatening to delay or effectively halt honest-validator finalization of inbound/outbound crosschain transactions system-wide — a denial of service on core universal-execution flows, not merely a query-path inconvenience. This falls within the allowed in-scope category "denial of service... reachable without privileged control" tied to honest-validator finalization paths.

### Likelihood Explanation
Medium. The trigger (spamming an external chain with many low-value crosschain deposits to create numerous distinct `Inbound`/`Outbound` observation variants) is within reach of any unprivileged actor and costs only the source-chain gas fee. Whether ballots regularly fail to converge to quorum in practice (given honest validators generally decode identically) is uncertain and would need empirical confirmation; the report should be read as flagging a **design-level missing safeguard** (no ballot cap, no periodic active-set pruning independent of per-observation expiry, and expiry effectively disabled by a 100M-block constant) rather than a proven, easily reproducible single-transaction exploit.

### Recommendation
- Reintroduce a bounded, meaningfully short `DefaultExpiryAfterBlocks` (or a per-ballot-type configurable expiry) instead of the effectively-infinite `100_000_000` value, so stuck/non-converging ballots are reclaimed in a timely manner.
- Decouple ballot expiry sweeping from `CreateBallot`'s hot path: run it in `EndBlocker`/`BeginBlocker` with a bounded batch size (cap the number of ballots examined per block) instead of a full unbounded walk triggered synchronously by every new ballot creation.
- Consider capping the number of concurrently active (non-finalized) ballots or rate-limiting new-variant creation per source chain/utx key to prevent unbounded fan-out from divergent validator observations.

### Proof of Concept
Not independently reproduced (index/tooling limits prevented running the chain locally). The reasoning path demonstrated from source:
1. `CreateBallot` unconditionally calls `ExpireBallotsBeforeHeight`, which iterates all of `ActiveBallotIDs` [1](#0-0) .
2. `DefaultExpiryAfterBlocks = 100_000_000` means ballots practically never satisfy `ballot.BlockHeightExpiry <= currentHeight` [7](#0-6) , so nothing is ever pruned from this walk.
3. Distinct/divergent `Inbound`/`OutboundObservation` byte encodings from honest validators create distinct ballot IDs (variants) that individually may never reach the 2/3+1 threshold [6](#0-5) , leaving them permanently `PENDING`/active.
4. A background Devin session with a local devnet could confirm this by seeding thousands of divergent inbound/outbound ballot variants and measuring `CreateBallot` latency growth over time.

// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
