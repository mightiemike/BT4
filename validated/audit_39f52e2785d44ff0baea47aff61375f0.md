### Title
Deleting an account with a beneficiary that does not exist permanently burns the account's balance - ([File: runtime/runtime/src/actions.rs])

### Summary
`DeleteAccountAction` only validates that `beneficiary_id` is a syntactically well-formed `AccountId`; it never checks that the beneficiary account actually exists. When the account is deleted, its balance is unconditionally forwarded as a system "balance refund" receipt to `beneficiary_id`. If that account does not exist, the refund receipt fails, and — per protocol design — a failed refund is *burnt*, not returned to anyone. This is the direct analog of the Solidity report: an unvalidated "receiver" parameter is used to move funds, and by the time the mistake is discovered the source of funds has already been irreversibly destroyed (the account is deleted before/atomically with the doomed transfer, just like the vault tokens were burnt before the withdrawal address was validated).

### Finding Description
`validate_delete_action` only performs a syntax check on `beneficiary_id`, with no existence check: [1](#0-0) 

`action_delete_account` uses the account's current balance as a "pay out to beneficiary" and pushes a system balance-refund receipt targeting `delete_account.beneficiary_id`, then immediately (in the same, unconditional flow) removes the account and clears its state: [2](#0-1) 

`Receipt::new_balance_refund` builds this payout as a refund receipt (`predecessor_id = "system"`), i.e. a receipt kind that is explicitly barred from creating an account: [3](#0-2) 

`implicit_creation_allowed` guarantees that a refund receipt can never implicitly create the receiving account, regardless of account type: [4](#0-3) 

This is confirmed by a dedicated test showing that a refund receipt sent to a non-existent account fails with `AccountDoesNotExist` and does not create the account: [5](#0-4) 

And per protocol documentation, a failed refund's funds are burnt outright, not returned to the sender or anyone else: [6](#0-5) 

Put together: a user (or a contract acting on the user's behalf via `promise_batch_action_delete_account`) submits a `DeleteAccount` action with a `beneficiary_id` that is a valid-looking but non-existent account (analogous to a "burn"/zero address — e.g. a typo'd account name, an account that expired/was never registered, or one the user mistakenly believes exists). Validation passes because only syntax is checked: [1](#0-0) 
The deleting account is removed from state regardless of the beneficiary's status — the "burn" of the source account's funds already happened by construction (its state is gone) before the transfer to the invalid receiver can even be attempted: [7](#0-6) 
The subsequent balance-refund receipt to the non-existent beneficiary then fails and is burnt, exactly mirroring the reported bug class where tokens are destroyed before the receiver is validated, with no way to recover them afterward.

### Impact Explanation
This is a self-inflicted but real and permanent loss-of-funds bug: any NEAR balance held by the deleted account is irrecoverably burnt if `beneficiary_id` does not correspond to an existing account. There is no recourse — the deleting account no longer exists, and refund failures are burnt per protocol design rather than bounced back. This matches "permanently frozen funds"/unauthorized value destruction from a single, unprivileged transaction (a `DeleteAccount` action or a `promise_batch_action_delete_account` host call), reachable by any transaction signer or any contract executing on a user's behalf (e.g., wallet/relayer contracts that construct delete-account actions programmatically from user-supplied beneficiary strings).

### Likelihood Explanation
Likelihood is Medium: it requires the caller to supply an incorrect/non-existent `beneficiary_id`, which is a plausible operator/user error (typo in account id, referencing an account that was itself deleted or never created, or a stale beneficiary address from off-chain state) — directly analogous to the "receiver=address(0)" mistake class in the source report. No malicious third party is required; only the deleting account's owner (or a contract acting on their behalf) needs to make the mistake, and NEAR's validation of `DeleteAccountAction` does not catch it because it only checks the account-id syntax, not existence.

### Recommendation
Before removing the account's state in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account (or otherwise ensure the deletion+payout is atomic/reversible on beneficiary-missing failure) rather than unconditionally deleting the account and only discovering the beneficiary's absence afterward in a fire-and-forget refund receipt whose failure burns the funds. At minimum, surface this hazard prominently in wallet/tooling UX and consider making `check_account_existence`/`action_delete_account` fail the whole action (refusing the deletion) when `beneficiary_id` does not exist, instead of deleting the source account and then burning the payout.

### Proof of Concept
1. Account `alice.near` holds a nonzero balance and submits a transaction with a single `DeleteAccountAction { beneficiary_id: "typo-account.near" }`, where `typo-account.near` does not exist on-chain.
2. `validate_delete_action` accepts the action because `typo-account.near` is a syntactically valid `AccountId`. [1](#0-0) 
3. `action_delete_account` runs: it computes `account_balance = account_ref.amount()`, pushes `Receipt::new_balance_refund(&"typo-account.near", account_balance)`, then calls `remove_account` and sets `*account = None`, permanently deleting `alice.near`. [2](#0-1) 
4. The generated balance-refund receipt is processed against `typo-account.near`. Because it is a refund receipt, it is barred from creating the missing account (`implicit_creation_allowed` returns `false` for `is_refund`), so it fails with `AccountDoesNotExist`. [4](#0-3) 
5. Per protocol rules, the failed refund's deposit is burnt rather than returned to `alice.near` (which no longer exists) or anyone else. [6](#0-5) 
6. Net effect: `alice.near`'s entire balance is permanently destroyed with no recovery path, exactly analogous to the reported "receiver = address(0)" fund-loss pattern.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;

    /// This should be used for token refunds instead of gas refunds.
    /// It doesn't refund the allowance of the access key. For gas refunds use `new_gas_refund`.
    pub fn new_balance_refund(receiver_id: &AccountId, refund: Balance) -> Self {
        Receipt::V0(ReceiptV0 {
            predecessor_id: "system".parse().unwrap(),
            receiver_id: receiver_id.clone(),
            receipt_id: CryptoHash::default(),
            receipt: ReceiptEnum::Action(ActionReceipt {
                signer_id: "system".parse().unwrap(),
                signer_public_key: PublicKey::empty(KeyType::ED25519),
                gas_price: Balance::ZERO,
                output_data_receivers: vec![],
                input_data_ids: vec![],
                actions: vec![Action::Transfer(TransferAction { deposit: refund })],
            }),
        })
    }
