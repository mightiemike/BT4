### Title
Deposits that fail during system-tx execution are permanently removed from the deposit mempool without retry, freezing funds - (File: crates/sequencer/src/runner.rs)

### Summary
`process_sys_txs` correctly reverts and skips a deposit whose actual on-chain execution fails, without adding it to `all_txs` [1](#0-0) . However, the caller unconditionally calls `remove_deposits(&deposit_data)` on the entire fetched deposit batch after block production, with no filtering for which deposits actually succeeded [2](#0-1) . `process_sys_txs`'s return value gives the caller no way to know which of `deposit_data` failed, so any deposit that fails execution (for any reason, transient or not) is silently and permanently dropped from `DepositDataMempool`, never retried.

### Finding Description
The binding that must hold is: `deposit successfully executed on L2 (present in all_txs) == deposit removed from DepositDataMempool.accepted_deposit_txs`. Tracing the code shows this equality is broken.

In `process_sys_txs`, when `apply_l2_block_txs` returns `EvmSystemTransactionNotSuccessful` for a deposit event, the working set is reverted and the loop `continue`s — the corresponding `sys_tx_rlp` is never pushed to `all_txs` [3](#0-2) . This is exercised by the existing unit test showing a second identical deposit call fails with `EvmSystemTransactionNotSuccessful` [4](#0-3) .

`process_sys_txs`'s return type is `(Vec<RlpEvmTransaction>, WorkingSet)` — it does not report which entries of the input `deposit_data: &[Deposit]` succeeded versus failed [5](#0-4) . Yet at block-commit time, the caller calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the same, unfiltered `deposit_data` slice that was originally fetched from the mempool via `fetch_deposits` [2](#0-1) . `remove_deposits` computes `calc_tx_id` for every entry passed to it and removes matches from `accepted_deposit_txs`/`pending_deposits` unconditionally [6](#0-5) .

The result: any deposit blob that is admitted via `citrea_sendRawDepositTransaction` (which only performs a best-effort `eth_call` against `BlockId::pending()` [7](#0-6) ) and later fails during actual system-tx execution against the finalized `l2_block_info` state is nonetheless removed from the mempool as if it had succeeded. This can happen for reasons entirely independent of malice — e.g., the `BitcoinLightClient` inclusion proof state (`setBlockInfo`) required by `verifyInclusion` not yet being in the exact state assumed at pending-simulation time, or any other legitimate state divergence between the `BlockId::pending()` snapshot used at RPC-admission time and the state actually committed when `process_sys_txs` executes the deposit. Once dropped, `fetch_deposits`/`accepted_deposit_txs` no longer contains the deposit, and there is no other path in the codebase that re-adds a `Deposit` blob to `DepositDataMempool` after this point — the corresponding Bitcoin-side `moveTx` deposit never mints cBTC.

The specific causal mechanism proposed in the question (a `witnessRoots[blockHash]` collision causing simulation-pass/execution-fail asymmetry) requires a SHA-256 preimage/collision and is not a demonstrable, in-scope attack vector; that part of the hypothesis is rejected as infeasible. However, the underlying concern the question raises — "is the underlying Deposit blob re-added to mempool for retry, or lost forever?" — is answered by the code: it is lost forever, regardless of *why* the execution-time failure occurred, because `remove_deposits` is called on the full unfiltered batch.

### Impact Explanation
Any deposit whose on-chain execution fails at inclusion time after being admitted via `citrea_sendRawDepositTransaction`'s pending-state `eth_call` check is permanently purged from the sequencer's `DepositDataMempool` without being included in a block and without ever being retried. If the underlying Bitcoin `moveTx` was otherwise valid, the corresponding BTC deposit permanently fails to mint cBTC — user funds are frozen with no automatic recovery path in this codebase (Critical, matches "funds permanently frozen"). This is repeatable for every deposit that experiences a pending-vs-execution state divergence, and affects any full node/sequencer running this exact logic, not just a single instance.

### Likelihood Explanation
No special privilege is required: the flow uses the public, unauthenticated deposit submission RPC and depends only on normal sequencer timing behavior (asynchronous system-event vs. deposit-mempool admission, as acknowledged by the RPC's own best-effort `eth_call` check against `BlockId::pending()`). No attacker action beyond normal deposit submission is strictly needed to trigger the drop — it is a latent correctness gap in `process_sys_txs`/`remove_deposits` interaction that can manifest during ordinary operation whenever pending-state simulation and actual execution-state diverge for any deposit.

### Recommendation
Have `process_sys_txs` (and `produce_and_run_system_transactions`) return which of the input deposits actually succeeded (e.g., a `Vec<Deposit>` of successfully-applied deposits, derived by tracking `is_deposit` success per iteration) and only call `remove_deposits` with that successful subset. Deposits that failed execution should remain in `accepted_deposit_txs` (or be explicitly re-queued) so they are retried in a subsequent block rather than silently discarded.

```rust
#[test]
fn test_failed_deposit_is_not_lost_if_execution_fails_after_fetch() {
    // 1. Add a deposit to the mempool and fetch it (simulating admission that
    //    passed eth_call against BlockId::pending()).
    let mut mempool = DepositDataMempool::new();
    let deposit = hex::decode(DEPOSIT1).unwrap();
    assert!(mempool.add_deposit_tx(deposit.clone()).unwrap());
    let fetched = mempool.fetch_deposits(10);

    // 2. Simulate runner.rs's process_sys_txs behavior: the deposit fails at
    //    actual execution time (EvmSystemTransactionNotSuccessful), so it is
    //    never added to `all_txs`.
    let successfully_included: Vec<Deposit> = vec![]; // nothing succeeded

    // 3. Current buggy behavior in runner.rs calls remove_deposits(&deposit_data)
    //    with the *original* fetched slice, not `successfully_included`:
    let removed = mempool.remove_deposits(&fetched); // BUG: uses unfiltered `fetched`
    assert_eq!(removed, 1);
    assert_eq!(mempool.accepted_deposit_txs.len(), 0); // deposit is now gone forever

    // Assert the binding that SHOULD hold instead:
    // count(deposits executed successfully) == count(deposits removed from mempool)
    assert_eq!(successfully_included.len(), 0);
    // With the fix, removed should equal successfully_included.len() == 0,
    // and the deposit should still be retrievable via fetch_deposits for retry:
    // assert_eq!(mempool.fetch_deposits(10).len(), 1);
}
```
This test demonstrates that `remove_deposits` is invoked on the full fetched batch rather than the subset that actually succeeded in `process_sys_txs`, confirming the deposit is dropped forever instead of being retried.

```rust
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });
```
