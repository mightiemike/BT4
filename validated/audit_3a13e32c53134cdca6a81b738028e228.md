## Finding: Resource‑usage ceiling rounding in `ResourceProcessor.increase`/`increaseV2` causes systematic overcharge of bandwidth/energy accounting

### Title
Ceiling-rounded average usage calculation causes users to be systematically overcharged for bandwidth/energy consumption - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
The external report describes a class of bug where a resource-consumption/interest formula is computed with coarse rounding (ceiling per unit) such that any partial excess above a whole unit gets billed as a full additional unit, systematically overcharging the user. java-tron's `ResourceProcessor` (parent of `BandwidthProcessor` and `EnergyProcessor`) contains the same rounding pattern in its `increase`/`increaseV2` methods, which are invoked on every transaction that consumes bandwidth or energy.

### Finding Description
`ResourceProcessor.increase` and `increaseV2` compute a windowed moving average of resource usage using `divideCeil`/`divideCeilExact`, which always rounds the quotient **up**: [1](#0-0) [2](#0-1) 

Both terms of the average — the carried-over `averageLastUsage` and the newly added `averageUsage` — are rounded up independently before being summed: [3](#0-2) 

The same ceiling logic is duplicated in `increaseV2` (used for `UnfreezeDelay`/V2 resource accounting): [4](#0-3) 

This is directly analogous to the reported bug: like the loan's late-interest calculation that rounds any partial day up to a full day, `divideCeil` rounds any non-zero remainder of `usage * precision / windowSize` up to the next integer. Because this occurs on *every* bandwidth/energy consumption update (`EnergyProcessor.useEnergy`, `BandwidthProcessor.consumeBandwidthForCreateNewAccount`, `useAccountNet`, etc. — all reachable from an ordinary broadcast transaction), the reported "average usage" is persistently inflated above the true value, exactly like the loan protocol's periodic interest being rounded up to the next full day for any partial overdue period.

### Impact Explanation
Because the computed `newEnergyUsage`/`newNetUsage` is inflated by the ceiling rounding, accounts appear to have consumed more of their free/frozen resource limit than they actually have. This can cause:
- A transaction to be pushed over the account's free bandwidth/energy limit earlier than it should, forcing `useTransactionFee`/fee payment in TRX (burned or sent to blackhole) that would not have been required under exact accounting: [5](#0-4) 
- Systematic loss of user funds/resource availability across the network, since every energy/bandwidth-consuming transaction goes through this rounding path.

This is comparable in class/severity to the reported bug (low severity, systemic overcharge due to rounding rather than an exploitable single-shot loss), but it is reachable from any ordinary broadcast transaction rather than a privileged actor.

### Likelihood Explanation
High likelihood of occurrence (triggered on virtually every transaction that consumes bandwidth/energy), but the magnitude of each individual overcharge is small (bounded by rounding to the next unit of `precision`), consistent with the "Low" severity classification given to the analogous external report. The client's philosophy in the original report — acknowledging the rounding but not viewing it as high risk — would likely apply here too, since `hardenCalculation()`/`allowHardenResourceCalculation` (BigInteger-based path) exists but still preserves the same ceiling-rounding semantics for backward compatibility.

### Recommendation
Where feasible, avoid ceiling-rounding both terms of the moving-average sum independently; instead perform the addition using higher precision (e.g., keep the running sum in an accumulator before final truncation), or defer rounding to strictly the final division step so that fractional remainders can offset rather than always inflate.

### Proof of Concept
1. Call `ResourceProcessor.increase(lastUsage, usage, lastTime, now, windowSize)` (as done internally by `EnergyProcessor.useEnergy` / `BandwidthProcessor.consumeBandwidthForCreateNewAccount`) with `lastUsage` and `usage` values chosen such that `lastUsage * precision % windowSize != 0` and `usage * precision % windowSize != 0`.
2. Observe that `divideCeil` rounds each term up independently: [2](#0-1) 
3. Compare the resulting `newUsage` to the mathematically exact (non-rounded) average; the ceiling-rounded result will always be ≥ the exact value, and can push an account over its bandwidth/energy limit, triggering `useTransactionFee` (TRX fee charge) in cases where the exact accounting would not have required it.
