### Title
`AddressRegistrar::register` locks excess attached deposit with no refund path - (File: runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs)

### Summary
The `AddressRegistrar::register` method is a `#[payable]` public contract method that requires the caller to attach at least `required_deposit` (the storage cost of the new mapping). When the mapping is newly created (the `Entry::Vacant` branch), any deposit amount attached in excess of `required_deposit` is silently kept by the contract and never refunded to the caller, unlike the `Entry::Occupied` (collision) branch a few lines below, which explicitly refunds the full `given_deposit` back to `predecessor_account_id`.

### Finding Description
`register` computes `required_deposit` from the storage bytes needed and compares it against `given_deposit = env::attached_deposit()`: [1](#0-0) 

It only panics if `given_deposit < required_deposit`; it never checks or refunds the case `given_deposit > required_deposit`. In the success path (`Entry::Vacant`), the deposit is simply absorbed into the contract's balance with no transfer action created: [2](#0-1) 

Contrast this with the collision path, which explicitly builds a refund promise for the entire attached deposit because "no storage was updated": [3](#0-2) 

Because NEAR's runtime automatically credits `attached_deposit` to the receiving contract's balance before code executes (per the Economics API semantics), any yoctoNEAR sent above `required_deposit` becomes part of the contract balance and there is no method in this contract (no `withdraw`, no owner-only sweep) to move it back out. A search of the wallet-contract/address-registrar crates confirms no such recovery function exists.

This mirrors the reported Solidity bug class exactly: a payable entry point validates a minimum required payment (`msg.value >= price` / `given_deposit < required_deposit`) but performs no refund of the surplus when the operation succeeds, permanently locking the excess.

### Impact Explanation
Any account that calls `register` (directly via a signed `FunctionCall` transaction, or indirectly through the NEAR Wallet Contract's ETH-emulation flow when checking/registering an address before a base-token transfer) and attaches more than the exact storage cost permanently loses the excess. There is no way for the caller or anyone else to recover it — this is a direct, unauthorized loss/freezing of user funds triggered by an ordinary, unprivileged transaction. This satisfies the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: since `register` is `#[payable]` and does not document/enforce an exact deposit amount, any caller (including the wallet-contract's own cross-contract call flow, or a naive integrator attaching a round/buffer amount like 1 NEAR "to be safe") will overpay whenever the computed storage cost is not attached precisely. Because the bug requires no adversarial conditions — just a normal call with `given_deposit > required_deposit` — it is trivially and repeatedly triggerable by any RPC caller.

### Recommendation
In the `Entry::Vacant` success branch of `register`, compute `surplus = given_deposit.checked_sub(required_deposit)` and, if non-zero, issue a `promise_batch_action_transfer` back to `env::predecessor_account_id()` for the surplus amount, exactly as already done in the `Entry::Occupied` branch. Alternatively, require an exact-deposit match and panic on overpayment, forcing callers to compute the precise cost.

### Proof of Concept
1. An externally owned NEAR account submits a `FunctionCall` transaction to the `AddressRegistrar` contract calling `register("alice.near")` with `deposit = required_storage_cost + 1_000_000 yoctoNEAR` (an intentional overpayment), where `required_storage_cost` is `env::storage_byte_cost() * (20 + len("alice.near"))` as computed at [4](#0-3) .
2. Since `"alice.near"`'s derived address has not been registered before, the `Entry::Vacant` branch executes at [5](#0-4) , inserting the mapping and returning `Some(address)` — no transfer/refund action is created.
3. Querying the caller's account balance before and after the call shows a balance decrease equal to the full `deposit` (required cost + surplus), while querying the `AddressRegistrar` contract's balance shows it increased by the full deposit amount, including the surplus.
4. There is no subsequent method (`withdraw`, admin sweep, etc.) in the contract that can return the surplus `1_000_000 yoctoNEAR` to the original caller or any account — the funds are permanently locked in the contract's balance.
