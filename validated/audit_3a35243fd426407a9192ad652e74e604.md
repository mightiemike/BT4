### Title
Birthday-attack collision on truncated Keccak256 `target` verification allows relayer to redirect ETH-implicit-account (Wallet Contract) actions to an attacker-controlled account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point accepts a caller-supplied `target: AccountId` argument alongside a user-signed, RLP-encoded Ethereum transaction. When the transaction's `to` field does not exactly match the current account or a parseable eth-implicit address, the only authorization that the supplied `target` account is the one the user actually intended is a **truncated-hash equality check**: `to == account_id_to_address(target)`, where `account_id_to_address` takes only the last 20 bytes of a 256-bit Keccak256 digest. This is structurally identical to the Panoptic `validateCallback()` finding: a 256→160-bit truncation used as an *authorization* check instead of an exact/canonical identity check, which is subject to a birthday-attack collision search (~2^80 work) rather than requiring a full 2^160 preimage break.

### Finding Description
`account_id_to_address` truncates a Keccak256 hash to 20 bytes and is used to validate the caller-provided `target`: [1](#0-0) 

This function is the sole authorization mechanism for the "other Near account" case in `validate_tx_relayer_data`: [2](#0-1) 

`parse_target` classifies `target` into `CurrentAccount`, `EthImplicit(address)` (checked by exact string/address equality), or `OtherNearAccount` — and it is exactly the `OtherNearAccount` branch (the common case: sending funds/tokens to a normal named NEAR account such as `alice.near`) that falls through to the truncated-hash-only check: [3](#0-2) 

`rlp_execute` is a public, unrestricted entry point: any predecessor account (a relayer, which need not hold any access key on the wallet) can call it, supplying an arbitrary `target` together with a previously-observed, user-signed RLP transaction: [4](#0-3) 

Once `target_kind` resolves to `OtherNearAccount` and passes the hash check, `target` is used directly as the receiver of the resulting Near action (`Transfer`/`FunctionCall`, including NEP-141 `ft_transfer` for emulated ERC-20 transfers), with no further validation against the user's original intent: [5](#0-4) [6](#0-5) 

Because Near account IDs allow up to 64 lowercase alphanumeric characters (plus `-`, `_`, `.`), the space of valid account-ID strings vastly exceeds 2^160. By the pigeonhole principle, for any fixed 20-byte hash value there are ~2^(N-160) account-ID strings whose Keccak256 digest truncates to it (analogous to the audit's derivation of Uniswap pool addresses). A relayer who wants to redirect a legitimate user transfer does not need to break a single specific hash (a 2^160 preimage problem); instead, it can pre-compute a large set of self-controlled candidate account IDs (e.g., cheaply created sub-accounts under an account it owns) and their `account_id_to_address` hashes, then wait for/relay any signed Ethereum-style transaction whose `to` field collides with one of them — a birthday-search problem solvable in roughly 2^80 total hash operations across both sets, exactly the class of attack described in the Panoptic report.

Note: the exact same truncated-hash pattern (`keccak256(x)[12..32]`) also underlies `derive_eth_implicit_account_id` (`core/primitives/src/utils.rs:474-480`), `derive_near_deterministic_account_id` (`:482-492`), and the address-registrar contract (`runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs:114-119`), but those are *naming/identity derivation* schemes (equivalent in security posture to how Ethereum itself derives addresses) rather than *authorization* checks gating fund movement to an attacker-chosen destination — the wallet-contract `target` check is the one place this pattern is used to authorize where value/actions actually go.

### Impact Explanation
If exploited, a malicious or compromised relayer could redirect a legitimate NEAR-token transfer, NEP-141 (`ft_transfer`) token transfer, or `FunctionCall` action initiated through a Wallet Contract (ETH-implicit account) to an account it controls instead of the account the signing user intended, resulting in unauthorized value movement/theft of funds intended for a different recipient. This matches "concrete unauthorized value movement" from an unprivileged, permissionless caller (a meta-transaction relayer), satisfying the Medium/High impact bar.

### Likelihood Explanation
Exploitability requires performing ~2^80 hash operations across two sets (attacker-controlled candidate account IDs vs. observed `to` values from real signed transactions being relayed) — the same order of magnitude computation the original report calculated as "expensive today but increasingly feasible," and it does not require breaking any cryptographic signature or key. The relayer role is explicitly modeled in this codebase as untrusted/"faulty" (the contract has ban-relayer logic for detected misbehavior), but detection there is limited to protocol-format violations, not to birthday-collision redirection of `OtherNearAccount` targets, which passes all existing validation. Likelihood is bounded mainly by the same computational cost discussed in the source report, and by the fact that `EthImplicit` targets are exempt from this weakness (only `OtherNearAccount`, the common real-world "send to a named account" case, is affected).

### Recommendation
Do not use a truncated-hash equality as the authorization proof for `target`. Options:
1. Require the relayer/off-chain resolution to be verifiable on-chain against a canonical registry (the existing Address Registrar already stores `address -> account_id`; require a registrar-confirmed round trip for all `OtherNearAccount` targets, not just the two other TargetKind cases that already do so via `address_check`), or
2. Encode enough of the target's canonical identity (not merely a 160-bit hash) into the Ethereum transaction payload/signature so that no truncation-driven collision is possible, or
3. Widen the comparison to the full 256-bit hash (or otherwise avoid truncation) for any check gating fund-recipient selection, consistent with the mitigation recommended in the source report ("query on-chain authoritative state instead of relying on a truncated/derived comparison").

### Proof of Concept
1. Attacker creates many cheap sub-accounts under an account they control, e.g. `x00001.attacker.near`, `x00002.attacker.near`, …, and computes `account_id_to_address(sub_account_id)` for each (as defined in `internal.rs:202-207`).
2. Attacker (acting as an unprivileged relayer) monitors/collects signed Ethereum-style RLP transactions intended for `rlp_execute` on various ETH-implicit accounts (Wallet Contracts), whose `to` field is a 20-byte address representing an intended recipient account (`internal.rs:332`).
3. When any observed `to` value collides with one of the attacker's precomputed sub-account hashes (statistically expected once ~2^80 total hash operations have been performed across the two sets, per the birthday-attack math in the source report), the attacker calls `rlp_execute(target = <colliding sub_account>, tx_bytes_b64 = <the legitimately signed tx>)`.
4. `validate_tx_relayer_data` (`internal.rs:318-368`) computes `parse_target` → `OtherNearAccount`, checks `to == account_id_to_address(target)` — which now passes — and returns `Ok(target_kind)`.
5. `inner_rlp_execute` (`lib.rs:412-472`) builds the corresponding `Transfer`/`FunctionCall`/`ft_transfer` action against `target` (the attacker's sub-account) instead of the account the user actually intended, moving the user's tokens to the attacker.

```rust
/// Coverts any Near account ID into a 20-byte address by taking the last 20 bytes
/// of the keccak256 hash.
pub fn account_id_to_address(account_id: &AccountId) -> Address {
    let hash = keccak256(account_id.as_bytes());
    let mut result = [0u8; 20];
    result.copy_from_slice(&hash[12..32]);
    result.into()
}
```

```rust
fn parse_target(target: &AccountId, current_address: Address) -> TargetKind<'_> {
    match extract_address(target) {
        Ok(address) => {
            if address == current_address {
                TargetKind::CurrentAccount
            } else {
                TargetKind::EthImplicit(address)
            }
        }
        Err(_) => TargetKind::OtherNearAccount(target),
    }
}
```
