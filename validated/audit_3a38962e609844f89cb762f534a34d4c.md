### Title
Unbounded native-stack recursion in compiled-class-hash computation over attacker-shaped bytecode segment tree - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
`bytecode_hash_node` recursively walks the `bytecode_segment_lengths` tree of a compiled class to compute the compiled-class hash. This recursion runs on the native Rust call stack (unlike Cairo-VM execution, which is step-bounded and stack-simulated on the heap), and its depth is dictated by the segment-tree shape produced from a declarer-supplied Sierra program. No depth limit is enforced anywhere in this path.

### Finding Description
`bytecode_hash_node` in [1](#0-0)  recurses once per level of the `HashableNestedIntList` segment structure with no depth check:
```
} else {
    let inner_nodes = node.iter_children().map(|child| bytecode_hash_node::<H, NL>(iter, child)).collect_vec();
    ...
}
```
This is invoked from `bytecode_hash` / `hash_inner` [2](#0-1)  which is called by `HashableCompiledClass::hash` [3](#0-2) .

Critically, this hash computation is executed **outside** the resource-limited compiler subprocess. The subprocess wrapper `ResourceLimits`/`compile_with_args` bounds only the actual Sierra→CASM compilation step:
```rust
let executable_class = self.compiler.compile(class)?;      // sandboxed subprocess, CPU/mem limited
let executable_class_hash = executable_class.hash(&HashVersion::V2); // runs in-process, unbounded
``` [4](#0-3) 

The `bytecode_segment_lengths` field is a `NestedIntList` produced by the Sierra→CASM compiler based on the nesting of a declared contract's control-flow structure (branches/functions). The gateway's declare path directly compiles and hashes attacker-supplied Sierra as part of ordinary transaction admission — see the tx-submission flow: `GW->>CM: add_class(SierraContractClass)` → `CM->>Compiler: compile(RawClass)` , and `apollo_gateway/src/gateway.rs` shows the compilation step runs during ordinary `add_tx_inner` for `RpcTransaction::Declare`, gated only by a concurrency semaphore (`declare_compilation_semaphore`), not by segment-depth limits [5](#0-4) . There is no validation anywhere in `StatelessTransactionValidator::validate_declare_tx` [6](#0-5)  that bounds the resulting segment-tree recursion depth — only Sierra version, overall size, and entry-point ordering are checked.

This is structurally the same bug class as CVE-2020-12243: attacker-controlled input drives unbounded recursive evaluation of a nested structure with no depth cap, causing native stack exhaustion and process crash (vs. OpenLDAP's nested LDAP filter booleans crashing `slapd`).

Separately, `NestedFeltCounts::new_inner` in `blockifier/src/execution/contract_class.rs` even documents this exact class-of-bug's mitigation via a hard `assert!(segmentation_depth <= 1, ...)` [7](#0-6) , confirming the codebase's own expectation that segment depth should be bounded — yet `bytecode_hash_node` in `starknet_api`, used on the hot declare path, enforces no such bound.

### Impact Explanation
If a crafted Sierra program compiles to CASM with a sufficiently deep `bytecode_segment_lengths` tree (achievable by writing deeply/lexically nested conditional branches within the `max_bytecode_size` budget), computing `executable_class_hash` will recurse thousands of native frames deep. Given typical Rust default stack sizes (unless raised, as is explicitly done for `native_blockifier`'s recursive entry-point handling via `RUST_MIN_STACK` [8](#0-7) , but not evidently for the Sierra-compiler component), this can stack-overflow and crash the process handling the declare request. Because this hashing happens synchronously in the gateway/sierra-compiler request path for every declare transaction, a single malicious declare can crash the serving component, denying declare (and potentially other colocated) transaction processing — a network-availability impact ("network unable to confirm new transactions") consistent with the required impact bar.

### Likelihood Explanation
Medium-High: an unprivileged account can submit a `Declare` transaction; the only friction is producing a Sierra program whose compiled CASM has an unusually deep nested branch/segment structure within existing size limits, and paying for compilation resources (bounded to 40 concurrent compilations per gateway, but a single crashing request is sufficient). No signature/balance verification is needed before this hashing occurs since it happens during class conversion prior to full stateful validation in `add_tx_inner` [5](#0-4) .

### Recommendation
Enforce an explicit maximum recursion/segment-tree depth check (mirroring the `assert!(segmentation_depth <= 1)` invariant already present in `blockifier/src/execution/contract_class.rs`) inside `bytecode_hash_node`/`bytecode_hash` in `starknet_api::contract_class::compiled_class_hash`, rejecting (with a normal error, not a panic) any `bytecode_segment_lengths` structure whose depth exceeds the compiler's documented invariant before recursing. Alternatively, convert the recursive walk to an explicit iterative/worklist algorithm so recursion depth is independent of segment nesting, and/or ensure this hashing step also executes with a bounded stack / inside the already-sandboxed compiler subprocess rather than in the gateway/sierra-compiler's main process.

### Proof of Concept
1. Author a Cairo1 contract whose body contains deeply, lexically nested conditional branches (e.g., programmatically generate `N` levels of nested `if`/`match` arms) sized to stay within `max_bytecode_size` but maximizing nesting depth (rather than breadth) of the resulting CASM control flow.
2. Submit it as the `contract_class` of an `RpcDeclareTransaction::V3`.
3. The gateway's `convert_rpc_tx_to_internal_and_executable_txs` invokes the Sierra→CASM compiler (sandboxed, succeeds) and then calls `executable_class.hash(&HashVersion::V2)` in-process [4](#0-3) , which recurses via `bytecode_hash_node` proportional to the crafted nesting depth, exhausting the native stack and crashing the serving process before any fee/signature check completes.

/// Computes the hash of the bytecode according to the provided segment structure.
/// The function iterates over the bytecode, partitioning it into segments as described
/// by the `HashableNestedIntList`. For each segment, it recursively computes a hash
/// using the provided `StarkHash` implementation. The final result is a hash representing the
/// entire bytecode structure, as required by Starknet's contract class hash computation.
fn bytecode_hash<H, NL>(bytecode: &[Felt], bytecode_segment_lengths: &NL) -> Felt
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    let mut bytecode_iter = bytecode.iter().copied();
    let (len, bytecode_hash) =
        bytecode_hash_node::<H, NL>(&mut bytecode_iter, bytecode_segment_lengths);
    assert_eq!(len, bytecode.len());
    bytecode_hash
}
```

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
```
