## Title
Silent underflow reset in `PendingTransactionQueue`'s custom checked-subtraction macro can permanently corrupt per-account pending-balance/nonce accounting used for transaction admission - (File: chain/client/src/pending_transaction_queue.rs)

### Summary
`chain/client/src/pending_transaction_queue.rs` implements a hand-rolled "safe subtraction" helper, `checked_sub_or_default!`, that is the direct analog of the external report's untested custom SafeMath library: a custom arithmetic-safety wrapper, used to maintain balance/count accounting (`paid_from_balance`, `access_key_tx_count`, `deploy_tx_count`, gas-key costs) that gates transaction admission, with no test coverage of its failure branch.

### Finding Description
The macro is defined as: [1](#0-0) 

Unlike the rest of the codebase's arithmetic (which uses `.checked_add()/.checked_sub()` combined with `.ok_or_else(...)?` to propagate a hard error, per the project's own style guidance on arithmetic overflow handling: [2](#0-1) ), this macro instead swallows the failure: it fires a `debug_assert!` (compiled out entirely in release builds) and then silently substitutes `Default::default()` (i.e. `0`) for the result.

It is used to update the account/nonce/gas-key aggregates that back `PendingConstraints` (`paid_from_balance`, `paid_from_gas_key`, `max_nonce`), which are consumed directly by the runtime's balance/nonce validation on both the transaction-admission (chunk-production) path and the RPC-submission path: [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

The queue's own internal invariant checks are also downgraded to debug-only assertions rather than hard errors, e.g. the duplicate-block-hash guard on `add_chunk_transactions`: [7](#0-6) 

Because `debug_assert!` is a no-op in release (production) builds, if this invariant is ever violated at runtime — e.g. the same `block_hash`'s chunk transactions get added twice (a re-processing/reorg edge case), or `remove_certified_chunk_by_block_hash` interacts with the per-chunk maps in a way the code's authors did not anticipate — the second `add_chunk_transactions` call silently overwrites `self.chunks[block_hash]`, causing the account/nonce/gas-key totals in `pending_accounts` / `pending_nonces` / `pending_gas_key_costs` to be double-counted while only a single chunk entry remains to ever be subtracted back out on certification. The result is a permanent residual in `paid_from_balance` (and related counters) that is never removed, because the corresponding `self.chunks` entry for that `block_hash` has already been consumed. No test in the file's `#[cfg(test)] mod tests` exercises the failure branch of `checked_sub_or_default!`, nor a duplicate-block-hash re-add scenario, so this invariant violation and its silent-corruption consequence are completely untested — exactly the "untested custom SafeMath" bug class from the report.

### Impact Explanation
This accounting feeds `PendingConstraints.paid_from_balance`/`max_nonce`, which the runtime treats as authoritative for balance/nonce checks on **both** the chunk-production admission path (`chain/chain/src/runtime/mod.rs`, `check_pending`) and the RPC `submit_transaction`/`can_verify_and_charge_tx` path (`chain/client/src/rpc_handler.rs`). A silently corrupted (understated) `paid_from_balance` would let the ephemeral verifier believe more balance is available than actually is, permitting acceptance of transactions that should have been rejected for insufficient funds across multiple in-flight uncertified chunks (the exact double-spend-across-pending-chunks scenario this queue exists to prevent per NEP-611). Conversely, a corrupted (overstated, permanently-residual) `paid_from_balance`/counter — the more likely outcome of the double-add-then-single-remove scenario described above — permanently and incorrectly reduces the account's *apparent* available balance and inflates its access-key/deploy counters forever, since the residual can never be subtracted back out. This can permanently block legitimate future transactions from that account (funds effectively frozen from the protocol's perspective, without any way for the account owner to clear it short of a node restart/queue `clear()`), which matches the "permanently frozen funds" impact category.

### Likelihood Explanation
The failure mode requires hitting one of the invariant violations guarded only by `debug_assert!` (e.g. duplicate `block_hash` re-insertion, or a queue entry already removed on `is_zero()` while other chunk contributions still reference the same account/nonce scope). These are edge cases around reorgs/re-processing of chunks feeding this Spice-only pending-transaction-queue (`spice_pending_transaction_queue_enabled`), not requiring a malicious validator — they can be triggered by ordinary chain-reorg conditions interacting with normal transaction submission. However, I could not fully trace, within the remaining tool budget, the exact call sites in `chain/client/src/client.rs` / `chunk_producer.rs` that invoke `add_chunk_transactions` and `clear()`/`remove_certified_chunk_by_block_hash` to confirm whether a genuine double-add or premature-removal is reachable in the current control flow, or whether upstream guards (e.g. only calling `add_chunk_transactions` once per newly-accepted block) already make the debug-only assertion effectively unreachable in practice. This is the primary source of uncertainty in this finding.

### Recommendation
Replace `checked_sub_or_default!`'s silent `Default::default()` fallback with a hard error (propagate a `Result`/abort chunk production or reject the RPC call) rather than continuing with corrupted accounting, and promote the duplicate-`block_hash` guard in `add_chunk_transactions` from `debug_assert!` to a checked, always-enforced condition. Add explicit unit tests that exercise the underflow/duplicate-insertion branches (not just the happy path currently covered in the file's test module) to verify the queue's behavior under invariant violations, consistent with the codebase's own documented policy of never silently tolerating arithmetic/invariant failures on the consensus-adjacent path.

/// Checked subtraction that falls back to `Default::default()` on underflow,
/// logging an error and firing a debug_assert so tests catch the invariant violation.
macro_rules! checked_sub_or_default {
    ($a:expr, $b:expr, $msg:expr) => {
        match ($a).checked_sub($b) {
            Some(v) => v,
            None => {
                debug_assert!(false, $msg);
                tracing::error!(target: "client", $msg);
                Default::default()
            }
        }
    };
}

        let Some(chunk_data) = self.chunks.remove(block_hash) else {
            tracing::debug!(
                target: "client",
                ?block_hash,
                "chunk not found in pending transaction queue during removal"
            );
            return;

        // Reverse per-account aggregates.
        for (account_id, chunk_account) in &chunk_data.accounts {
            if let Some(total_account) = self.pending_accounts.get_mut(account_id) {
                total_account.subtract(chunk_account);
                if total_account.is_zero() {

                if entry.is_empty() {
                    self.pending_nonces.remove(scope);
                }

**File:** docs/practices/style.md (L260-301)
```markdown
### Arithmetic integer operations

Use methods with an appropriate overflow handling over plain arithmetic operators (`+-*/%`) when
dealing with integers.

```
// GOOD
a.wrapping_add(b);
c.saturating_sub(2);
d.widening_mul(3);   // NB: unstable at the time of writing
e.overflowing_div(5);
f.checked_rem(7);

// BAD
a + b
c - 2
d * 3
e / 5
f % 7
```

If you’re confident the arithmetic operation cannot fail,
`x.checked_[add|sub|mul|div](y).expect("explanation why the operation is safe")` is a great
alternative, as it neatly documents not just the infallibility, but also *why* that is the case.

This convention may be enforced by the `clippy::arithmetic_side_effects` and
`clippy::integer_arithmetic` lints.

**Rationale:** By default the outcome of an overflowing computation in Rust depends on a few
factors, most notably the compilation flags used. The quick explanation is that in debug mode the
computations may panic (cause side effects) if the result has overflowed, and when built with
optimizations enabled, these computations will wrap-around instead.

For nearcore and neard we have opted to enable the panicking behavior regardless of the
optimization level. By doing it this we hope to prevent accidental stabilization of protocol
mis-features that depend on incorrect handling of these overflows or similarly scary silent bugs.
The downside to this approach is that any such arithmetic operation now may cause a node to crash,
much like indexing a vector with `a[idx]` may cause a crash when `idx` is out-of-bounds. Unlike
indexing, however, developers and reviewers are not used to treating integer arithmetic operations
with the due suspicion. Having to make a choice, and explicitly spell out, how an overflow case
ought to be handled will result in an easier to review and understand code and a more resilient
project overall.
```
