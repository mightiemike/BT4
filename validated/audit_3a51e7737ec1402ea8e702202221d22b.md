### Title
Unbounded native recursion in `bytecode_hash_node` during compiled-class-hash verification can stack-overflow the sequencer - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
The janino advisory (CVE-2023-33546) is a classic "attacker-controlled recursive structure walked by an unbounded native recursive function → stack overflow / DoS" bug class. The analogous pattern in this codebase is `bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs`, which recurses over a `HashableNestedIntList` (backed by `cairo_lang_starknet_classes::NestedIntList`) with no depth bound, using genuine Rust call-stack frames rather than the Cairo VM's heap-simulated stack.

### Finding Description
`bytecode_hash_node` walks the bytecode-segment tree recursively: [1](#0-0) 

This is invoked from `hash_inner`/`HashableCompiledClass::hash`, which computes the compiled-class hash from a `CompiledClassV1`'s `bytecode_segment_felt_sizes` (`NestedFeltCounts`) whenever the sequencer needs to (re)compute/verify a declared class's compiled class hash: [2](#0-1) 

Unlike the corresponding Cairo-language implementations used inside the Starknet OS (`hash_entry_points_inner`, `bytecode_hash_internal_node` in `blake_compiled_class_hash.cairo` / `poseidon_compiled_class_hash.cairo`), whose recursion executes inside the Cairo VM where the "stack" is a heap-backed memory segment bounded by the step/gas limit, this Rust-side recursion consumes the real OS thread stack. The codebase is explicitly aware that unbounded native recursion during class-hash-related computation is a stack-overflow risk — see the comment and stack pre-allocation logic for Cairo Native execution: [3](#0-2) 

and the `RUST_MIN_STACK` sizing explicitly tied to `MAX_ENTRY_POINT_RECURSION_DEPTH`: [4](#0-3) 

However, no equivalent guard (depth counter, iterative rewrite, or `RUST_MIN_STACK` sizing tied to segment nesting depth) was found protecting `bytecode_hash_node`'s recursion over `NestedIntList`. Because `bytecode_segment_felt_sizes`/`NestedIntList` structure is derived from a Sierra-to-CASM compilation of an attacker-declared class, an attacker who controls the Sierra program submitted in a `Declare` transaction could, in principle, cause the compiler to emit (or could otherwise cause the sequencer to construct) a deeply/pathologically nested segment tree that is walked natively at hash-verification time.

### Impact Explanation
If reachable with sufficient nesting depth, this would crash the sequencer process handling declare/class-hash verification with a native stack overflow, causing a denial of service to the sequencer executing or re-executing that transaction (e.g., during declare validation, execution, casm-hash migration in `map_class_hash_to_casm_hash_computation_resources`, or Starknet OS re-execution paths that consult compiled-class hashes). A crash during block building/re-execution could stall the sequencer from confirming new transactions, which is in-scope impact per the validation criteria.

### Likelihood Explanation
This is **uncertain/unverified** rather than proven: I was not able to confirm within the available index (1) the exact code path in `crates/apollo_compile_to_casm` / `cairo_lang_starknet_classes` that produces `NestedIntList` from a Sierra program to determine whether nesting depth is naturally bounded by compiler logic (e.g., segment sizes tied to bytecode length, which is itself capped), nor (2) a concrete transaction-level trigger that lets a declarer directly control the segment nesting depth independent of bytecode size/step limits. Given the sequencer's own compiler builds the `NestedIntList` (not the attacker directly), the achievable nesting depth may be implicitly capped by existing bytecode-size limits (e.g., max contract class size), which would significantly reduce or eliminate real-world exploitability. This should be treated as a **candidate/likely-benign** finding pending confirmation of compiler-side depth bounds.

### Recommendation
- Verify whether `cairo_lang_starknet_classes`' Sierra→CASM segment-generation logic bounds nesting depth relative to existing contract-class-size limits.
- If unbounded, convert `bytecode_hash_node` (and the analogous cairo-side recursive helpers if they are ever executed off the Cairo VM) to an iterative, explicit-stack implementation, or enforce an explicit maximum nesting-depth check before recursing, returning a graceful error on classes whose segment tree exceeds the configured depth limit.
- Ensure any RUST_MIN_STACK sizing assumptions documented for entry-point recursion also account for compiled-class-hash computation paths.

### Proof of Concept
Not constructed — I could not confirm without further investigation (compiler internals for `NestedIntList` generation) whether an attacker-controlled Sierra program can force sufficiently deep nesting to overflow the default Rust stack. A concrete PoC would require crafting a Sierra program whose compiled CASM bytecode segment structure nests to a depth on the order of the default stack's frame capacity (typically tens of thousands of frames) and declaring it via a `Declare` transaction, then observing whether `bytecode_hash_node`'s recursion depth scales with attacker input independent of other resource limits.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

/// Trait for types that can be hashed as a Starknet compiled class.
/// Used to abstract over different contract class representations.
pub trait HashableCompiledClass<EH: EntryPointHashable, NL: HashableNestedIntList>: Sized {
    fn get_hashable_l1_entry_points(&self) -> &[EH];
    fn get_hashable_external_entry_points(&self) -> &[EH];
    fn get_hashable_constructor_entry_points(&self) -> &[EH];
    fn get_bytecode(&self) -> Vec<Felt>;
    fn get_bytecode_segment_lengths(&self) -> Cow<'_, NL>;

    /// Returns the compiled class hash using the specified hash version.
    fn hash(&self, hash_version: &HashVersion) -> CompiledClassHash {
        match hash_version {
            HashVersion::V1 => hash_inner::<Poseidon, EH, NL>(self),
            HashVersion::V2 => hash_inner::<Blake2Felt252, EH, NL>(self),
        }
    }
}

/// Computes the compiled class hash for a given hashable class using the specified hash algorithm.
fn hash_inner<H, EH, NL>(hashable_class: &impl HashableCompiledClass<EH, NL>) -> CompiledClassHash
where
    H: StarkHash,
    EH: EntryPointHashable,
    NL: HashableNestedIntList,
{
    let external_funcs_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_external_entry_points());
    let l1_handlers_hash = entry_point_hash::<H, EH>(hashable_class.get_hashable_l1_entry_points());
    let constructors_hash =
        entry_point_hash::<H, EH>(hashable_class.get_hashable_constructor_entry_points());

    let bytecode_hash = bytecode_hash::<H, NL>(
        &hashable_class.get_bytecode(),
        &*hashable_class.get_bytecode_segment_lengths(),
    );

    // Compute total hash by hashing each component on top of the previous one.
    CompiledClassHash(H::hash_array(&[
        *COMPILED_CLASS_V1,
        external_funcs_hash,
        l1_handlers_hash,
        constructors_hash,
        bytecode_hash,
    ]))
}
