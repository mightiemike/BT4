## Finding

Based on the report's bug class — a "safeguard" that looks present because of shared naming/structure, but is silently weaker in one code path due to an inherited/duplicated implementation that wasn't updated — the closest reproducible analog in this repo is a divergence between the v1 and v2 `SortitionsView::validate_tenure_change_payload` implementations in the signer's duplicate-tenure-block guard.

### Title
Stale duplicate-tenure-block guard in `SortitionsView` v1 lets a rogue miner get two conflicting tenure-start blocks approved by different signers - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`stacks-signer` maintains two parallel implementations of `validate_tenure_change_payload`, one for each signer state-machine protocol version. The `DuplicateBlockFound` safeguard — meant to stop a miner from getting a second, different tenure-start block signed for the same tenure — was hardened in the v2 path but the v1 path still uses the older, weaker check, even though both are still live code paths selected by the signer's active protocol version.

### Finding Description
In `stacks-signer/src/chainstate/v2.rs`, `validate_tenure_change_payload` looks up the tenure's already-approved block with `get_last_signed_block`, which returns a block that is either `LocallyAccepted` or `GloballyAccepted`: [1](#0-0) 

In `stacks-signer/src/chainstate/v1.rs`, the equivalent function still uses `get_last_globally_accepted_block`, which only sees blocks that have already crossed the network-wide signing threshold: [2](#0-1) 

The DB layer makes the semantic gap explicit — `get_last_signed_block` intentionally includes `LocallyAccepted` blocks precisely because "a pre-commit does not put a signature over the block and may be safely superseded", whereas `get_last_globally_accepted_block`/`get_last_accepted_block` do not carry that guarantee for locally-accepted-but-not-yet-global blocks: [3](#0-2) 

A regression test explicitly documents that using `get_last_globally_accepted_block` for this check is the bug that was fixed for v2 — the exact code still present in v1 today: [4](#0-3) 

And the project's own CHANGELOG records this as a fix, without noting it was scoped to only one of the two active check paths: [5](#0-4) 

This mirrors the WardenPledge report's failure mode exactly: two conceptually identical safeguards, implemented separately, where one retained the weaker/buggy behavior after the other was hardened — invisible to anyone reasoning only about the "fixed" path.

### Impact Explanation
A minority-controlled miner (no majority or signer collusion required — only control of the mining key for one tenure) can:
1. Propose tenure-start block A. Some v1-protocol signers locally-accept it (sign it) but it has not yet reached the 70% global-acceptance threshold (e.g. some signers are slow, offline, or the miner deliberately withholds broadcasting enough signatures).
2. Propose a second, different tenure-start block B for the *same* tenure. For any v1-protocol signer, `validate_tenure_change_payload` calls `get_last_globally_accepted_block`, which returns `None` (block A is only locally accepted, not global), so the `DuplicateBlockFound` guard does not fire, and block B passes validation and can be signed by other signers.

The result is two different tenure-start blocks each carrying valid signer signatures from different subsets of the v1 signer set — a validation verdict on which block is legitimate that two (sets of) nodes disagree on, i.e. a signer-set/tip disagreement bounded to the affected tenure. This is exactly the "validation verdict two nodes disagree on" / "temporary tip disagreement" category called out as an in-scope High-impact analog.

### Likelihood Explanation
Likelihood is High for signers still running the v1 state-machine protocol version: the trigger requires only an unprivileged miner controlling a single tenure and timing two block proposals before the first reaches the 70% weight threshold — no signer collusion, no majority, and no operator/admin key is needed. The v2 path is unaffected because it already checks `get_last_signed_block`.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` to use `SignerDb::get_last_signed_block` (as v2 does) instead of `get_last_globally_accepted_block`, so the `DuplicateBlockFound` guard also covers locally-accepted-but-not-yet-global blocks for v1-protocol signers. Alternatively, since v1 is a superseded/legacy path, confirm whether it can be retired entirely rather than patched in parallel with v2, to avoid this class of drift recurring.

### Proof of Concept
1. Set up a signer running the v1 state-machine protocol version (`SortitionsView` v1).
2. Miner proposes tenure-start block A for consensus hash `CH`; have a subset of v1 signers locally-accept/sign it (do not let it reach the 70% weight threshold — e.g. withhold responses from enough signers, matching the existing regression test setup in `check_tenure_change_rejects_when_locally_accepted_block_exists`, but run it against `v1::SortitionsView::validate_tenure_change_payload` instead of v2).
3. Miner proposes a second tenure-start block B, also for `CH`, to the remaining v1 signers.
4. Observe that `validate_tenure_change_payload` in `v1.rs` calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, finds `None` (block A is only locally accepted), and does not return `RejectReason::DuplicateBlockFound` — block B is accepted for signing, producing two independently-signed, conflicting tenure-start blocks for the same tenure.

    /// Return the last signed block in a tenure (identified by its consensus hash).
    /// A block is considered signed if it is locally or globally accepted. Blocks that
    /// have only been pre-committed are excluded, because a pre-commit does not put a
    /// signature over the block and may be safely superseded by a competing proposal.
    ///
    /// This answers "what is the tenure's signed tip?", a different question from
    /// [`SignerDb::has_signed_block_in_tenure`]'s "does a signature bind us to this tenure?",
    /// which is why the predicates deliberately differ on rejected blocks (see there).
    pub fn get_last_signed_block(
        &self,
        tenure: &ConsensusHash,
    ) -> Result<Option<BlockInfo>, DBError> {
        let query = "SELECT block_info FROM blocks WHERE consensus_hash = ?1 AND state IN (?2, ?3) ORDER BY stacks_height DESC LIMIT 1";
        let args = params![
            tenure,
            &BlockState::GloballyAccepted.to_string(),
            &BlockState::LocallyAccepted.to_string(),
        ];
        let result: Option<String> = query_row(&self.db, query, args)?;

        try_deserialize(result)
    }
