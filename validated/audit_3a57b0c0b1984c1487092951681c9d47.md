### Title
Tombstone stored-size assumption (`calculate_stored_size(0)`) can diverge from actual on-disk tombstone size, corrupting `AccountStorageReader` byte-skip alignment - (File: accounts-db/src/account_storage_reader.rs)

### Summary
`AccountStorageReader::new` computes a fixed `tombstone_stored_size` via `storage.accounts.calculate_stored_size(0)` for every offset in `tombstone_offsets`, hard-coding the assumption that "tombstones are zero-lamport accounts, which store no data." Nothing in the shrink path that creates tombstones enforces that a zero-lamport single-ref account actually has zero data length, so an attacker who leaves non-zero data on a zero-lamport account can make the assumed tombstone size diverge from the real physical record size written to disk.

### Finding Description
In `accounts_db.rs::load_accounts_index_for_shrink`, an account is classified as a tombstone candidate purely based on `stored_account.is_zero_lamport() && ref_count == 1`: [1](#0-0) 
There is no check that the account's `data_len` is zero. `stored_account` is pushed verbatim (`tombstones.push(*stored_account)`), and later `shrink_storage`/`store_tombstones` writes these tombstones to the new storage via `write_accounts_to_storage`, which persists whatever data length the source account actually has: [2](#0-1) 

Meanwhile, `AccountStorageReader::new` computes the skip size for every tombstone offset using a single fixed value derived from a zero-length account: [3](#0-2) 
and `Read::read` uses that fixed size to decide how many bytes to skip when it reaches a tombstone offset: [4](#0-3) 

If the true on-disk tombstone record is larger than `calculate_stored_size(0)` (because the source zero-lamport account retained non-zero `data_len`), the reader under-skips at that offset, leaving the read cursor misaligned with the next account/tombstone boundary for the remainder of the file. All subsequent excluded-offset comparisons (`file_offset == excluded_start`) will fail to match real boundaries, and the output byte stream for that storage file will contain garbage/misaligned account records for everything following the malformed tombstone.

An unprivileged attacker fully controls whether a zero-lamport account retains non-zero data: Solana's account model does not force `data_len` to zero when `lamports` reaches zero (there is no runtime-enforced "zero out data on zero-lamport" rule; only `is_zero_lamport()` — a lamports check — gates tombstone creation). By self-owning a program (or simply not clearing data before draining lamports) an attacker can produce a zero-lamport, single-ref, non-empty-data account, get it shrunk into a tombstone while it's newer than the latest full snapshot (`can_purge_zero_lamport_single_ref == false`), and have it retained in storage as a tombstone with non-zero-size stored bytes.

### Impact Explanation
This affects `TombstonesFilter::Exclude`, used specifically for full snapshot archiving (`snapshots/src/archive.rs`): [5](#0-4) 
A misaligned/corrupted `AppendVec` byte stream written into the full snapshot archive would break deserialization of that storage file on rebuild (parsing failures, panics, or spurious/garbage accounts being read back), which can propagate into hash/capitalization mismatches on snapshot reload — matching the "honest-node snapshot-vs-replay mismatch" / storage-corruption bounty category.

### Likelihood Explanation
Requires: (1) attacker creates a zero-lamport account that is the sole reference (`ref_count == 1`) with non-zero `data_len`; (2) that slot is shrunk while newer than the latest full snapshot slot (so `can_purge_zero_lamport_single_ref == false`, forcing the account to be carried forward as a tombstone rather than dropped); (3) a full snapshot is later taken from that storage. All three steps are reachable through the normal write/shrink pipeline (`shrink_storage` → `shrink_collect` → `store_tombstones`) without any privileged access, though it depends on validator-controlled shrink/snapshot timing, making exploitation timing-dependent but not infeasible for a patient attacker across many accounts/slots.

### Recommendation
Do not assume a fixed zero-length stored size for tombstones. Either (a) enforce that only true zero-data-length zero-lamport accounts are ever converted to tombstones (assert/filter on `data_len == 0` in `load_accounts_index_for_shrink`/`shrink_collect` before pushing to `tombstones`), or (b) have `AccountStorageReader::new` compute each tombstone's actual stored size from the storage's per-offset data length (as is already done for `obsolete_accounts` via `calculate_stored_size(*len)`) instead of hardcoding `calculate_stored_size(0)` for all tombstone offsets.

### Proof of Concept
Rust integration test plan (in `accounts-db/src/accounts_db/tests/impl.rs` style, extending `test_shrink_converts_zero_lamport_single_ref_account_to_tombstone`):
1. Create a zero-lamport account with non-zero data (`AccountSharedData::new(0, /*data_len=*/64, &owner)`) as the sole reference in a slot.
2. Set `latest_full_snapshot_slot` older than that slot so the zero-lamport single-ref account is not purgeable and must be carried forward as a tombstone.
3. Force shrink (`shrink_slot_forced`) and confirm via `new_storage.num_tombstones() == 1` that the account became a tombstone, and independently verify (e.g., via `storage.accounts.get_account_data_lens`) that the on-disk stored size for that offset exceeds `storage.accounts.calculate_stored_size(0)`.
4. Construct an `AccountStorageReader` with `TombstonesFilter::Exclude`, read the full output into a buffer, and assert that:
   - `reader.len()` bytes are produced without I/O errors, and
   - Re-parsing the output bytes as an `AppendVec`/`AccountsFile` and comparing recovered accounts (pubkeys/offsets) against a naive re-scan of the live accounts index for the same slot yields a mismatch (extra/garbage/missing accounts), demonstrating the skip-length miscomputation corrupts the output stream.
