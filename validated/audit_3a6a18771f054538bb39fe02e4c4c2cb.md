### Title
Webhook HMAC validation binds only rawBody, allowing cross-tenant session confusion via forged `X-Shopify-Shop-Domain` header replay - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
`validateHmacFromRequestFactory` computes and checks the webhook HMAC solely against `rawBody`, never incorporating the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers into the signed material. Because a single `apiSecretKey` signs webhooks for every shop installed on the app, an attacker who controls one installed shop can capture one of their own legitimately-signed `(rawBody, hmac)` pairs and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop, causing the app to treat the payload as an authentic webhook for the victim.

### Finding Description
`validateHmacFromRequestFactory` (packages/apps/shopify-api/lib/utils/hmac-validator.ts:168-201) reads the `hmac` header and calls `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` [1](#0-0) , which recomputes `createSHA256HMAC(config.apiSecretKey, rawBody, format)` and does a `safeCompare` [2](#0-1) . No header value (domain, topic, webhook id) is folded into the HMAC input.

`validateFactory` in packages/apps/shopify-api/lib/webhooks/validate.ts calls this HMAC check, and only *after* it passes does it separately extract `domain`, `topic`, `webhookId` directly from the (unauthenticated w.r.t. binding) request headers via `checkWebhooksHeaders` [3](#0-2) . These header values are returned as `valid: true` fields but are never cryptographically tied to the `rawBody`/`hmac` pair that was verified.

Downstream, `authenticateWebhookFactory` in both shopify-app-remix and shopify-app-react-router uses `check.domain` (the raw header value) to resolve the session: `ensureValidOfflineSession(params, check.domain)` [4](#0-3) , which calls `createOrLoadOfflineSession`, deriving `offlineSessionId = api.session.getOfflineId(shop)` and loading that session from storage [5](#0-4) .

Exploit flow:
1. Attacker installs the target app on their own shop ("shopA") — a normal, unprivileged action.
2. Shopify sends attacker a legitimate webhook for shopA: `rawBody` + `X-Shopify-Hmac-Sha256` computed with the shared `apiSecretKey`, plus `X-Shopify-Shop-Domain: shopA.myshopify.com`.
3. Attacker replays that exact `rawBody` and `hmac` to the app's `/webhooks` endpoint, but sets `X-Shopify-Shop-Domain: shopB.myshopify.com` (victim).
4. `validateHmacFromRequestFactory` only checks `rawBody` vs `hmac` — this still passes because neither value changed.
5. `checkWebhooksHeaders` returns `domain: 'shopB.myshopify.com'` as part of the "valid" result.
6. The host app frameworks (`shopify-app-remix`/`shopify-app-react-router`) load shopB's offline session and hand the attacker-supplied payload/context to the app's webhook handler tagged as if it originated from shopB, with `session`/`admin` client bound to the victim shop.

This breaks the tenant-isolation invariant that a verified webhook request should resolve to the session of the exact shop that signed it — instead it resolves to whatever domain header the attacker supplies, since domain is not part of the signed data.

### Impact Explanation
This allows cross-tenant webhook forgery: an app's webhook handler will run business logic (e.g., processing `orders/create`, `app/uninstalled`, GDPR-style topics, or app-specific automation) attributing attacker-controlled data to a victim shop's session, and the handler is handed a live `admin` API client authenticated as the victim. Depending on what the app's webhook handlers do (write to DB keyed by shop, trigger side effects, call Admin API mutations using the victim's access token), this can cause data corruption, unauthorized state changes, or information disclosure scoped to the victim tenant. This matches Shopify's "cross-tenant data/state access" bounty impact class.

### Likelihood Explanation
Preconditions: attacker needs only to install the app on one shop they control (a normal customer action) and passively capture one webhook delivery — no secret leakage, no privileged role, and no dependency on any Shopify internal behavior. The victim shop domain is guessable (it's simply `*.myshopify.com`, often discoverable or brute-forceable) and no additional secret is required to forge the header. The attack is trivially repeatable for every webhook the attacker's own shop receives. Actual impact strength depends on what host-app webhook handlers do with the `domain`/`session`, but the library itself provides no binding to prevent the confusion, and both `shopify-app-remix` and `shopify-app-react-router` are built directly on top of this unbound `check.domain` value.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-verified material, or otherwise cryptographically bind the header values used for session resolution to the same signed request that carries the `X-Shopify-Hmac-Sha256` value — for example, by validating that the `domain` header matches a shop the current session/webhook subscription was registered for, or by rejecting/flagging replay by tracking `X-Shopify-Webhook-Id` as a one-time-use nonce. At minimum, document that `validateFactory`'s HMAC check does not guarantee the returned `domain` is authentic, and ensure `ensureValidOfflineSession` cannot be driven by unauthenticated header data without additional verification (e.g., cross-check against a known/registered shop list, or verify the shop actually has this webhook subscription active with matching `webhookId`).

### Proof of Concept
```ts
import request from 'supertest';
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';
import {getTestExpressApp, headers, hmac} from './utils';

describe('cross-tenant webhook domain spoof', () => {
  it('accepts shopA-signed rawBody replayed with shopB domain header', async () => {
    const shopify = shopifyApi(testConfig());
    const app = getTestExpressApp(shopify);

    const rawBody = '{"foo": "bar"}'; // captured from shopA's legitimate webhook
    const validHmac = hmac(shopify.config.apiSecretKey, rawBody); // captured from shopA's webhook

    const response = await request(app)
      .post('/webhooks')
      .set(headers({
        hmac: validHmac,
        domain: 'shopB-victim.myshopify.com', // forged, was shopA.myshopify.com originally
      }))
      .send(rawBody)
      .expect(200);

    // HMAC check passes (rawBody unchanged) and domain is trusted as shopB
    expect(response.body.data).toMatchObject({
      valid: true,
      domain: 'shopB-victim.myshopify.com',
    });
  });
});
```
Expected result: the assertion passes, demonstrating that `validateFactory`/`validateHmacFromRequestFactory` treats the replayed request as a valid webhook for `shopB-victim.myshopify.com` despite the HMAC having been generated for a different shop's original delivery, and that host frameworks would subsequently load shopB's offline session via `check.domain`.

export async function createOrLoadOfflineSession(
  {api, config, logger}: BasicParams,
  shop: string,
) {
  if (config.distribution === AppDistribution.ShopifyAdmin) {
    logger.debug('Creating custom app session from configured access token', {
      shop,
    });
    return api.session.customAppSession(shop);
  } else {
    logger.debug('Loading offline session from session storage', {shop});
    const offlineSessionId = api.session.getOfflineId(shop);
    const session = await config.sessionStorage!.loadSession(offlineSessionId);

    return session;
  }
