## Analog Vulnerability Found

The Tigris `mint()` bug is a **check-effect-interaction violation**: state is read, an external call is made, and the code that follows the external call commits new storage state using data that was captured *before* the interaction, instead of the up-to-date result. The closest analog in shopify-app-js is in the Express token-exchange middleware, `performTokenExchange`.

### Title
Stale-session capture across external calls corrupts session storage on token-exchange error path - (File: `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`)

### Summary
`performTokenExchange` hoists a reference to the *pre-exchange* session (`sessionToInvalidate`) before performing external network calls (`exchangeToken`, i.e. `api.auth.tokenExchange`) and invoking the app's `afterAuth` hook. If any of those subsequent operations throws an `HttpResponseError` with code 401, the top-level `catch` block calls `invalidateAccessToken(sessionToInvalidate, config)`, which persists the *stale, pre-exchange* session object (with `accessToken` nulled) back into session storage — overwriting the fresh, valid session that was already stored moments earlier in the same request.

### Finding Description
The function captures `sessionToInvalidate` immediately after loading the session from storage, before any interaction with Shopify's token endpoint: [1](#0-0) 

It then performs the check-interaction: exchanges the offline (and optionally online) access token, and **stores the new, valid session**: [2](#0-1) 

Only after these external calls and successful stores does it invoke the app-provided `afterAuth` hook: [3](#0-2) 

If that hook throws (e.g. it calls the Admin API, such as `registerWebhooks`, and Shopify returns 401), execution falls into the outer `catch`, which re-uses the **old, pre-exchange** `sessionToInvalidate` object — not the freshly obtained `newSession` — and persists it with `accessToken` cleared: [4](#0-3) 

`invalidateAccessToken` unconditionally overwrites the session-storage record keyed by the same `session.id`: [5](#0-4) 

Because the offline session id is derived deterministically from the shop (`api.session.getOfflineId(shop)`), it is shared by all requests for that shop, so this final store clobbers the just-persisted valid session with stale, invalidated data — effects are committed using pre-interaction data instead of the interaction's true result, exactly mirroring the `initId`/`_limitOrders` clobbering pattern in the reference report.

### Impact Explanation
A single request through the token-exchange path can permanently corrupt the shop's persisted offline session: the record that was just correctly refreshed gets overwritten with a copy that has `accessToken: undefined`, forcing every subsequent request for that shop to be treated as unauthenticated and re-enter the exchange flow. This is a self-inflicted denial of service on the authentication handler for the shop, triggerable without any privileged access — merely by causing (or having occur) a 401 anywhere downstream of the token exchange within the same request (e.g. from the app's own `afterAuth` webhook registration call).

### Likelihood Explanation
The precondition (a pre-existing, previously-stored offline session with a non-empty `accessToken`, i.e. an already-installed shop) is common. A 401 from `afterAuth` is plausible whenever an app registers webhooks or calls the Admin API from that hook and the token/scope is transiently invalid — this is entirely within reach of a single merchant/customer-triggered request, requiring no elevated privileges, matching the "DoS of an auth handler" acceptance criterion.

### Recommendation
Do not persist `sessionToInvalidate` (the pre-interaction snapshot) after external calls have potentially replaced it. Instead:
- Track whether a new session was already successfully stored during this request, and if so, invalidate/update that object (or reload the current record from storage) rather than the stale pre-exchange copy, or
- Scope the invalidation to only trigger when the exchange itself (not a later, unrelated hook failure) returned 401, and otherwise let 401s from `afterAuth` be handled without mutating the just-established session.

### Proof of Concept
1. Shop has a previously stored offline session with a stale/expired `accessToken` (`sessionToInvalidate` captured at line 77).
2. `performTokenExchange` successfully exchanges a fresh offline (and online) access token and stores it (lines 94-116) — storage now holds a valid session.
3. The app's `afterAuth` hook (invoked at line 124) makes an Admin API call that returns an `HttpResponseError` with code 401 (e.g., a webhook topic requires a scope not yet granted).
4. Execution reaches the outer `catch` (line 150); since `sessionToInvalidate.accessToken` was truthy, `invalidateAccessToken(sessionToInvalidate, config)` is called, storing the **old** session (accessToken cleared) under the same session id, overwriting the valid session stored in step 2.
5. All subsequent requests for the shop see an inactive/invalid offline session and are forced to redo the exchange, indefinitely reproducing the same failure if `afterAuth` keeps failing — a persistent DoS of the shop's authenticated session state.

import {Session} from '@shopify/shopify-api';

import {AppConfigInterface} from '../config-types';

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
}
