### Title
Global signer state agreement uses a weaker floor-rounded 70% threshold than the block-approval ceiling threshold, letting sub-quorum weight dictate global miner/burn-view/protocol-version state - ([File: libsigner/src/v0/signer_state.rs])

### Summary
The bug report describes `SpeedJumpIrm` computing `avgBorrowRate` incorrectly because a rounding-to-zero special case (`linearVariation == 0`) is checked against the wrong intermediate value, so a value that "looks like zero" after truncation silently substitutes a different formula than intended. The structural analog in this repo is a **mismatch between two different roundings of the same nominal 70% supermajority threshold**: one path rounds up (ceil), the other rounds down (floor), so the two code paths can disagree about whether the same vote weight clears "70%".

### Finding Description
`NakamotoBlockHeader::compute_voting_weight_threshold` computes the minimum weight required for block acceptance/pre-commit/rejection decisions using explicit ceiling rounding: [1](#0-0) 

```rust
pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
    let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
    let total_weight = u64::from(total_weight);
    let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
    u32::try_from((total_weight * threshold) / 10 + ceil)...
}
```

This is used everywhere block-level consensus decisions are made: pre-commit tallying, signature-threshold tallying, and rejection-threshold tallying in `stacks-signer/src/v0/signer.rs` (`handle_block_pre_commit`, `store_and_process_block_signature`, block rejection handling) and in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`: [2](#0-1) [3](#0-2) 

Separately, `GlobalStateEvaluator::reached_agreement` (used to determine the *global signer state* — burn view, active miner, protocol version, tx-replay set — from all peers' `StateMachineUpdate`s) computes the same nominal 70% using **floor** division, with no ceiling correction: [4](#0-3) 

```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}
```

Both functions purport to check "does this vote weight reach ≥70% of `total_weight`?", but they use different rounding rules on the exact same constant `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD`. When `total_weight * threshold` is not a multiple of 10, the two functions disagree at the boundary:

- `compute_voting_weight_threshold(total_weight)` = `ceil(total_weight * 7 / 10)`
- `reached_agreement` minimum passing weight = `floor(total_weight * 7 / 10)`

Example: `total_weight = 11` → `total_weight*7 = 77`. `compute_voting_weight_threshold` returns `8` (ceil(7.7)=8, i.e. requires ≥8/11 ≈ 72.7%). `reached_agreement(7)` returns `true` (floor(7.7)=7, i.e. accepts 7/11 ≈ 63.6%). This exact discrepancy is exercised by the existing test `test_compute_voting_weight_threshold`, which explicitly checks the ceiling behavior of the block-approval function: [5](#0-4) 

but `GlobalStateEvaluator`'s own boundary test only pins the floor-rounded semantics of `reached_agreement`/`reached_disagreement` in isolation, without cross-checking against `compute_voting_weight_threshold`'s ceiling semantics: [6](#0-5) 

`reached_agreement` gates `determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, `determine_global_state` (current miner/tenure view), and the tx-replay-set majority-prefix search: [7](#0-6) [8](#0-7) 

So at a total signer weight where `total_weight * 7` is not divisible by 10, a coalition holding strictly less than the intended 70% supermajority (as low as `floor(total_weight*7/10)/total_weight`, e.g. 63.6% at `total_weight=11`) can force the local signer's belief about the global burn view / current miner / protocol version / replay set, while the same weight would be rejected as insufficient by the block pre-commit/signature/rejection threshold check elsewhere in the same signer.

### Impact Explanation
This is a minority-triggerable divergence between two supposedly-identical 70% supermajority checks used by the signer set. A coalition below the true 70% bar (but above the floor-rounded bar) can unilaterally fix the "global state" (miner/tenure/burn-view/protocol-version/replay-set) that individual signers rely on for chainstate consistency checks (`check_block_against_signer_db_state`), even though that same weight would fail to reach the pre-commit/signature threshold needed to actually get a block signed. This produces a temporary, minority-triggerable disagreement in what different parts of the signer logic consider "70% agreed", which can manifest as inconsistent local decisions across the signer set (e.g., a subset of signers believing a different miner/tenure is canonical than what would actually be needed to sign/reject a block) — a temporary tip/decision disagreement bounded to the affected reward cycle, consistent with the High-severity category ("signer weight below threshold... temporary tip disagreement").

### Likelihood Explanation
Triggering requires only that `total_weight * NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` not be a multiple of 10 (very common, since `total_weight` is the sum of arbitrary signer weights derived from stacked amounts) and that an adversarial or naturally-occurring coalition hold weight in the narrow band between the floor and ceil thresholds. No majority coordination, no privileged key, and no admin action is required — it is a pure arithmetic inconsistency reachable by any subset of signers whose combined weight lands in that band.

### Recommendation
Make `GlobalStateEvaluator::reached_agreement` (and `reached_disagreement`) use the exact same rounding rule as `NakamotoBlockHeader::compute_voting_weight_threshold` (ceiling division), or better, have `reached_agreement` call `compute_voting_weight_threshold` directly so there is a single source of truth for the 70% supermajority computation across the codebase.

### Proof of Concept
1. Construct a signer set with `total_weight = 11` (e.g., 11 signers of weight 1 each, or any weight distribution summing to 11).
2. `NakamotoBlockHeader::compute_voting_weight_threshold(11)` returns `8` — confirmed by the ceiling logic and existing test pattern in `stackslib/src/chainstate/nakamoto/tests/mod.rs`.
3. Call `GlobalStateEvaluator::reached_agreement(7)` with `total_weight = 11`: `u64::from(7) >= (11 * 7) / 10 = 77/10 = 7` → `7 >= 7` → `true`.
4. A coalition of signers totaling weight `7` (63.6% of `11`, below the intended 70%) thus causes `determine_global_state`/`determine_global_burn_view`/`determine_latest_supported_signer_protocol_version` to report "agreement reached" on their preferred burn view/miner/protocol version, while the identical weight `7` would fail `compute_voting_weight_threshold`'s requirement of `8` for actually signing or rejecting a block — demonstrating the two "70%" checks diverge for the same input.

    /// Determine what the maximum signer protocol version that a majority of signers can support
    pub fn determine_latest_supported_signer_protocol_version(&self) -> Option<u64> {
        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
            *entry += weight;
        }
        // find the highest version number supported by a threshold number of signers
        let mut protocol_versions: Vec<_> = protocol_versions.into_iter().collect();
        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }

    /// Determine what the global burn view is if there is one

#[test]
/// Locks the joint behavior of `reached_agreement` and `reached_disagreement`
/// at a single `total_weight`:
///   - agreement: `>=` 70% (inclusive)
///   - disagreement: `>` 30% (strict)
///   - three regions: [0, 30%] neither, (30%, 70%) disagreement only,
///     [70%, total] both
///
/// Walking 0, 30%, 30%+1, 70%-1, 70% catches a flipped inequality on either
/// side and any drift between the two threshold constants. Also pins the
/// "agreement implies disagreement" relation, which holds as long as the
/// agreement threshold sits above the disagreement one.
fn thresholds_partition_weight_space() {
    let evaluator = evaluator_with_total_weight(1_000_000_000);

    // 0%: neither.
    assert!(!evaluator.reached_agreement(0));
    assert!(!evaluator.reached_disagreement(0));

    // Exactly 30%: strict `>`, so not yet disagreement.
    assert!(!evaluator.reached_agreement(300_000_000));
    assert!(!evaluator.reached_disagreement(300_000_000));

    // One unit past 30%: gap region, disagreement only.
    assert!(!evaluator.reached_agreement(300_000_001));
    assert!(evaluator.reached_disagreement(300_000_001));

    // One unit below 70%: still in the gap.
    assert!(!evaluator.reached_agreement(699_999_999));
    assert!(evaluator.reached_disagreement(699_999_999));

    // Exactly 70%: agreement (`>=`), and disagreement still holds since 70% > 30%.
    assert!(evaluator.reached_agreement(700_000_000));
    assert!(evaluator.reached_disagreement(700_000_000));
}
