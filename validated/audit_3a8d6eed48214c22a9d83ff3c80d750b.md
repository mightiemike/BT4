## Title
Inconsistent rounding direction in TRC10 Market order matching causes value leakage from fully-filled maker orders to takers - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

## Summary
`MarketSellAssetActuator.matchSingleOrder` uses the same floor-rounding helper, `MarketUtils.multiplyAndDivide`, for two calculations that require opposite rounding directions: the amount the **taker** receives, and the amount the **maker** receives when their entire remaining order is consumed. Both are floored, which silently underpays the maker whenever the remaining/full-quantity ratio isn't an exact integer, letting the taker keep the rounding remainder. This mirrors the reported Sudoswap `ICurve` issue where the same rounding direction was (incorrectly) applied to both buy and sell calculations instead of rounding in favor of the party being fully settled.

## Finding Description
`MarketUtils.multiplyAndDivide` always performs a floor division: [1](#0-0) 

This single, always-round-down primitive is used for two conceptually different quantities inside `matchSingleOrder`:

1. What the **taker** may buy given their remaining sell quantity (rounding down here is safe — it under-delivers to the taker, protecting the counterparty): [2](#0-1) 

2. What the **maker** receives in return for giving up their *entire* remaining sell quantity (the "taker == maker" and "taker > maker" branches): [3](#0-2) [4](#0-3) 

In these branches, `makerOrderCapsule.setSellTokenQuantityRemain(0)` — the maker's full remaining balance is consumed — while `makerBuyTokenQuantityReceive` is computed by flooring `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity`. Because the maker gives up *all* of their remaining tokens, fairness requires this quotient to be rounded up (ceiling) — any fractional remainder belongs to the maker. Instead it is rounded down, and the taker's own remaining sell balance is only reduced by that floored amount (see `subtractExact(takerOrderCapsule.getSellTokenQuantityRemain(), makerBuyTokenQuantityReceive)`), meaning the taker keeps the fractional surplus that should have gone to the maker.

The existing dev comment even acknowledges the precision issue exists ("Accuracy problem"), and a corresponding test class documents (but does not fix) this behavior: [5](#0-4) 

Concrete example: maker order `sell A : buy B = 100 : 33`, with `sellTokenQuantityRemain = 7` (a partially filled order). A taker whose order fully consumes this maker order triggers:
`makerBuyTokenQuantityReceive = floor(7 * 33 / 100) = floor(2.31) = 2`
The fair value is `2.31`; the maker receives `2`, and the taker's sell-side balance is reduced only by `2` instead of the fair `2.31`, letting the taker keep the surplus `0.31` B for free.

## Impact Explanation
Every match that fully consumes a maker's remaining order with a non-exact `sellRemain * buyQty / sellQty` ratio silently transfers value from the maker (who is presumed fully settled, `sellTokenQuantityRemain = 0`) to the taker. This is a systemic, protocol-level accounting shortfall reachable by any unprivileged account placing/matching TRC10 market orders (`MarketSellAssetActuator`), analogous to the reported AMM curve issue where value leaks from pair creators/liquidity providers to traders due to inconsistent rounding direction. Repeated or scaled trading (especially involving low-decimal or high-value tokens) compounds the loss to makers and erodes trust in on-chain market fairness/state accounting.

## Likelihood Explanation
High: this occurs automatically on ordinary, unprivileged `MarketSellAssetContract` transactions whenever a maker order is fully filled with a non-integer-dividing remaining ratio — no special conditions, admin roles, or attacker crafting beyond normal order placement are required. The magnitude per trade is small (rounding-error scale) but is deterministic and systematically biased in one direction (favoring takers), rather than randomly distributed.

## Recommendation
Use ceiling (round-up) division instead of floor when computing the amount owed to a maker whose full remaining order is being consumed (`makerBuyTokenQuantityReceive` in the "taker == maker" and "taker > maker" branches of `matchSingleOrder`), while keeping floor division for quantities computed on behalf of the taker/protocol side (`takerBuyTokenQuantityRemain`). This ensures the fully-settled party never receives less than their fair share, consistent with the general AMM/market best practice of rounding in favor of the side being fully and irrevocably settled.

## Proof of Concept
1. Create a maker sell order for token A→B with ratio `sellTokenQuantity = 100`, `buyTokenQuantity = 33` (via `MarketSellAssetActuator`).
2. Partially fill it so `sellTokenQuantityRemain = 7` (e.g., through a smaller matching taker order).
3. Submit a taker order (opposite pair) large enough to fully consume the remaining `7` A tokens (`takerBuyTokenQuantityRemain >= makerOrderCapsule.getSellTokenQuantityRemain()`), landing in the "taker == maker" or "taker > maker" branch of `matchSingleOrder`.
4. Observe: `makerOrderCapsule.getSellTokenQuantityRemain()` becomes `0` (maker fully settled), but `makerBuyTokenQuantityReceive = floor(7*33/100) = 2` is credited to the maker via `addTrxOrToken`, while the taker's own `sellTokenQuantityRemain` is reduced only by `2` (not the fair `2.31`), letting the taker retain the extra fractional value that rightfully belonged to the maker.
