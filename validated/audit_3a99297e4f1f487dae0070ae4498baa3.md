### Title
Unbounded recursive stack growth in `get_recursive_transaction_results` reachable via `tx`/`EXPERIMENTAL_tx_status` JSON-RPC - (File: chain/chain/src/chain.rs)

### Summary
`get_recursive_transaction_results` walks the execution-outcome tree of a transaction using native (non-tail) Rust recursion, one stack frame per receipt in the chain, with no depth cap [4](#0-3) . It is invoked by `get_partial_transaction_result_option`/`get_final_transaction_result`, which back the `ViewClientActor`'s `TxStatus`/`TxStatusRequest` handlers [5](#0-4) [6](#0-5) , which in turn service the public `tx`/`EXPERIMENTAL_tx_status`/`send_tx`/`broadcast_tx_commit` JSON-RPC methods through `tx_status_common`/`tx_status_fetch` [7](#0-6) [8](#0-7) .

### Finding Description
Every recursive call in `get_recursive_transaction_results` adds a stack frame for each `receipt_id` produced along the execution chain of a transaction, with the depth of recursion bounded only by the number of chained (sequential) cross-contract-call receipts that a transaction/its descendants have generated over the transaction's lifetime, not by any explicit limit [9](#0-8) . This is functionally identical in shape to the trust-dns-server bug class: a chain of linked records (there: additional MX/SRV targets; here: chained receipt IDs) is walked with plain recursion and no depth guard, so a sufficiently long chain overflows the thread stack.

The codebase elsewhere explicitly recognizes and defends against exactly this class of bug: `get_subtree_size` in `trie_recording.rs` was rewritten to a `VecDeque`-based BFS "to avoid any potential stack overflows" [10](#0-9) , and the `ReceiptToTx` handler enforces a hard `MAX_DEPTH=1000` with a dedicated `DepthExceeded` error [3](#0-2) . `get_recursive_transaction_results`, which walks a structurally similar chain (in the opposite direction — receipt children rather than receipt-to-originating-tx parents), has no such guard.

### Impact Explanation
An unbounded stack overflow triggered by a remote/unprivileged JSON-RPC caller crashes the querying node process (validator or RPC node, since `ViewClientActor` runs inside the full node binary, not an isolated sandbox). A stack-overflow abort in a validator process constitutes a transaction-triggered halt/DoS of that validator's participation in consensus and of any RPC serving built on the same binary, satisfying the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Exploitability requires the attacker to actually cause a very long *sequential* chain of receipts to be produced and executed on-chain (each cross-contract call spawns one receipt whose `receipt_ids` link forward), then query `tx`/`EXPERIMENTAL_tx_status`/`send_tx` for that transaction hash. Because promise/cross-contract-call chains span multiple blocks (each hop is a separate receipt executed in a following block/chunk) and are only bounded by the caller's willingness to pay gas across many transactions/blocks over time, an attacker with no special privileges can incrementally build an arbitrarily long chain and then issue a single RPC query to trigger the recursive walk. However, I could not fully verify from static inspection alone the exact number of hops needed to exhaust a typical thread stack (dependent on frame size of `ExecutionOutcomeWithIdView`/`Vec` operations and platform stack size), nor whether any upstream congestion-control or gas-refund mechanism effectively caps the maximum practically achievable chain length before the node would already be stalled by other limits. This uncertainty should be resolved with an actual reproduction before treating severity as fully confirmed.

### Recommendation
Rewrite `get_recursive_transaction_results` as an iterative (worklist/queue-based) traversal, mirroring the fix already applied to `get_subtree_size` in `core/store/src/trie/trie_recording.rs`, and/or impose an explicit maximum traversal depth (analogous to the `MAX_DEPTH=1000` used for `ReceiptToTx`) with a graceful error returned to the RPC caller instead of unbounded native recursion.

### Proof of Concept
1. Deploy a contract exposing a self-recursive cross-contract-call method (the codebase's own test contract already demonstrates such chained calls, see `max_self_recursion_delay`/`internal_recurse` in `runtime/near-test-contracts/test-contract-rs/src/lib.rs`) [11](#0-10) .
2. Repeatedly trigger the chained cross-contract call over many blocks so that the persisted execution-outcome chain for a single originating transaction grows to many thousands of linked receipts (bounded only by total gas spent across many submitted transactions, not by any single-block/gas-based recursion-depth check like the ~56–221 depth seen in `slow_test_self_delay`, since that limit is per-receipt gas budget, not a global chain-length cap) [12](#0-11) .
3. Call the `tx` / `EXPERIMENTAL_tx_status` JSON-RPC endpoint for the originating transaction hash, causing `tx_status_common` → `tx_status_fetch` → `TxStatus` → `get_partial_transaction_result_option` → `get_recursive_transaction_results` to recurse once per receipt in the chain [7](#0-6) [13](#0-12) .
4. Observe stack exhaustion/process abort on the serving node once the chain length exceeds the thread's stack capacity.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    async fn tx_status_fetch(
        &self,
        tx_info: near_jsonrpc_primitives::types::transactions::TransactionInfo,
        finality: near_primitives::views::TxExecutionStatus,
        fetch_receipt: bool,
    ) -> Result<
        near_jsonrpc_primitives::types::transactions::RpcTransactionResponse,
        near_jsonrpc_primitives::types::transactions::RpcTransactionError,
    > {
        // If the request times out before any poll completes we report that we never got a
        // usable status; each poll that keeps us waiting replaces this with a better cause.
        let mut timeout_error_cause = TimeoutErrorCause::default();

        let poll_tx_status = async {
            // Create a new watch::Receiver to watch for new blocks. Mark the current block as seen.
            let mut new_block_watcher = self.block_notification_watcher.clone();
            new_block_watcher.mark_unchanged();

            loop {
                match self.tx_status_fetch_single(&tx_info, &finality, fetch_receipt).await {
                    ControlFlow::Break(outcome) => break outcome,
                    ControlFlow::Continue(cause) => timeout_error_cause = cause,
                }
                new_block_watcher.changed().await.map_err(|_| {
                    RpcTransactionError::InternalError {
                        debug_info: "block notification channel closed".to_string(),
                    }
                })?;
            }
        };

        // The polling loop returns on its own once it reaches the requested finality or hits a
        // definitive error; only a timeout falls through to `unwrap_or_else`.
        self.clock
            .timeout(self.polling_config.polling_timeout, poll_tx_status)
            .await
            .unwrap_or_else(|_| {
                self.tx_status_on_timeout(&tx_info, fetch_receipt, timeout_error_cause)
            })
    }

#[unsafe(no_mangle)]
pub unsafe fn recurse() {
    input(0);
    if register_len(0) != size_of::<u64>() as u64 {
        panic()
    }
    let mut data = [0u8; size_of::<u64>()];
    read_register(0, data.as_mut_ptr());
    let n = u64::from_le_bytes(data);
    let res = internal_recurse(n);
    let data = res.to_le_bytes();
    value_return(data.len() as u64, data.as_ptr() as u64);
}

/// Rust compiler is getting smarter and starts to optimize my deep recursion.
/// We're going to fight it with a more obscure implementations.
#[unsafe(no_mangle)]
#[inline(never)]
fn internal_recurse(n: u64) -> u64 {
    if n <= 1 {
        n
    } else {
        let a = internal_recurse(n - 1) + 1;
        if a % 2 == 1 { (a + n) / 2 } else { a }
    }
}
