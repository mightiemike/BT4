## Title
Missing zero-shares check in `deposit` allows silent loss of deposited funds due to floor-rounding in share conversion - (File: `mainnet/contracts/vault/v0-vault-stx.clar`, and identically in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
All six v0 vaults compute the number of vault shares (`inkind`) to mint for a deposit using floor division in `convert-to-shares-preview`, but unlike `redeem`, the `deposit` function never asserts that the computed share amount is non-zero. This is the exact same rounding-to-zero bug class described in the WUSDA report: a depositor can transfer real underlying tokens into the vault and receive zero shares in return, permanently losing their funds to the benefit of other shareholders (i.e. of `assets`), with no revert protecting them.

### Finding Description
`convert-to-shares-preview` performs a floor division: [1](#0-0) 

This is invoked by `deposit`, and the returned `inkind` (shares to mint) is only checked against the caller-supplied `min-out` for slippage — there is no `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` guard: [2](#0-1) 

Compare this to `redeem` in the same contract, which explicitly guards against a zero output with `ERR-OUTPUT-ZERO`: [3](#0-2) 

Because `mul-div-down` truncates, whenever `amount * total-supply-preview < total-assets-preview` (i.e. the deposit is smaller than the current price-per-share), `inkind` evaluates to `u0`. Since the default `min-out` supplied by an unaware caller is `u0`, the slippage check `(>= inkind min-out)` trivially passes with `inkind = u0`. The deposit then proceeds: `receive-underlying` pulls the full `amount` of the depositor's tokens into the vault, `ft-mint? zft inkind recipient` mints zero shares, and `assets` is increased by the full `amount` — permanently socializing the depositor's underlying tokens to all other existing shareholders with no shares issued in return.

This is identical in every v0 vault, since they share the same `convert-to-shares-preview`/`deposit` pattern: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

Note that share price (`total-assets-preview / total-supply-preview`) is not static: interest continuously accrues into `total-assets`/`total-assets-preview` via `accrue`/`total-debt`, while `total-supply` only grows when new shares are minted. Over time the price-per-share naturally drifts above 1, making rounding-to-zero on small deposits an ordinary, not merely adversarial, occurrence — no flash loan or second party is required to trigger it, this is a single-transaction bug in `deposit` itself.

### Impact Explanation
A depositor whose deposit rounds to zero shares transfers real underlying tokens (STX/sBTC/stSTX/stSTXbtc/USDC/USDH) into the vault and receives nothing representing ownership of them; the value is absorbed into `assets` and thus effectively redistributed to all other existing shareholders. This is a direct, permanent loss of the depositor's principal — theft of user funds at rest, matching the Critical impact category.

### Likelihood Explanation
No privileged access or multi-party interaction is required — a single depositor calling `deposit` with `min-out` left at the safe-looking default of `u0` (as most integrators/UIs would do to avoid unnecessary reverts) and an amount below the current price-per-share is sufficient. Because vault share price increases monotonically with accrued interest, the window in which small deposits round to zero widens over the vault's lifetime, making this increasingly likely to be hit as vaults mature and as smaller deposit amounts (in base units, given 6/8-decimal underlying assets) are used.

### Recommendation
Add the same zero-output guard used in `redeem` to `deposit` in all six v0 vault contracts:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed before `receive-underlying`/`ft-mint?` are executed, so that a deposit that would mint zero shares reverts instead of silently consuming the depositor's tokens.

### Proof of Concept
1. Vault has been running long enough that `total-assets-preview` has grown relative to `total-supply-preview` due to accrued interest (e.g. `ts = 1_000_000`, `ta = 2_000_000_000` in base units — price-per-share = 2000).
2. A user calls `deposit` with `amount = 1` (smallest unit of underlying) and `min-out = u0` (the default a naive integrator/UI would pass).
3. `convert-to-shares-preview` computes `inkind = mul-div-down(1, 1_000_000, 2_000_000_000) = 0`, per [1](#0-0) .
4. All `asserts!` in `deposit` pass: `amount > u0` ✓, `inkind (0) >= min-out (0)` ✓, cap check ✓ — none of them catch `inkind == 0`, per [8](#0-7) .
5. `receive-underlying` pulls the user's 1 unit of underlying into the vault; `ft-mint? zft 0 recipient` mints zero shares to the user; `assets` is incremented by 1, per [9](#0-8) .
6. The user's deposited token is now irrecoverably part of the vault's `assets`, benefiting all other shareholders proportionally, while the depositor holds zero shares and has no claim on it.

```text
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```
