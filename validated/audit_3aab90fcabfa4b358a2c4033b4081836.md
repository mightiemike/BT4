### Title
Outbound event parser and observation builder collapse FINALIZE/REVERT/RESCUE outcomes into an identical `Success=true` vote, corrupting outbound ballot content - ([File: universalClient/chains/evm/event_parser.go], [File: universalClient/chains/common/event_processor.go])

### Summary
`ParseEvent` dispatches `EventTypeFinalizeUniversalTx`, `EventTypeRevertUniversalTx`, and `EventTypeFundsRescued` (as well as `EventTypeExecuteUniversalTx`) to the same `parseOutboundObservationEvent` function, which only ever extracts `TxID`/`UniversalTxID` from `Topics[1]`/`Topics[2]` and produces an identical `store.Event{Type: store.EventTypeOutbound, EventData: {TxID, UniversalTxID}}` with no field recording which of the three semantically distinct outcomes occurred. [1](#0-0) [2](#0-1) 

Downstream, the honest UniversalClient's `buildOutboundObservation` reconstructs the `OutboundObservation` (the actual ballot content voted via `MsgVoteOutbound`) purely from this data plus the raw tx hash, and it **hardcodes `Success: true` and `ErrorMsg: ""` unconditionally**, with no branch on which vault/gateway method emitted the log: [3](#0-2) 

Since the ballot key is `sha256(utxId:outboundId:marshal(observedTx))` and `observedTx` for finalize, revert, and rescue outcomes is built identically (`Success:true`, same `BlockHeight`/`TxHash`/`GasFeeUsed` derivation), the produced ballot content cannot distinguish a genuine successful finalize from a revert or a funds-rescue for the same outbound. [4](#0-3) [5](#0-4) 

### Finding Description
The `x/uexecutor` design explicitly documents that `OutboundObservation.Success` is the field UVs vote on to record whether the destination-chain outbound landed, and that different `success`/`tx_hash`/`error_msg` observations should produce different ballot variants: [6](#0-5) [7](#0-6) 

However, the honest UniversalClient never actually derives `Success`/`ErrorMsg` from which vault event fired (`finalizeUniversalTx` = success, `revertUniversalTx` = revert, `fundsRescued` = rescue-after-revert-failure). All three are parsed through the identical `parseOutboundObservationEvent` code path and voted with `Success: true` always. This is a genuine bug in the honest-validator client code (not a malicious-validator scenario) that is exercised automatically whenever a real revert or rescue happens on the destination chain — an outcome an attacker can often force by causing the outbound's destination call to fail (e.g., a recipient contract that reverts, or another condition that triggers the vault's revert/rescue path instead of its finalize path).

Because every honest UV runs the same client code, this does not cause cross-validator disagreement (no ballot-forking among honest nodes), but it does cause the entire honest validator set to converge on and vote a **factually wrong** ballot: an outbound whose funds were actually reverted or rescued back to the vault gets voted and finalized as `Success: true`/`OBSERVED`, exactly matching the semantics of a genuine successful finalize.

### Impact Explanation
`VoteOutbound` transitions `outbound.OutboundStatus` to `Status_OBSERVED` on ballot finalization based on this `Success:true` observation, without any downstream code path aware that the underlying event was actually a revert or a rescue. This means the chain's canonical `UniversalTx`/`OutboundTx` state records a delivered outbound for a transaction whose funds never actually reached the intended destination (they were reverted or rescued back into the vault). This corrupts the canonical UniversalTx outbound-status accounting and can suppress or bypass the revert/refund flow that should return funds to the user, resulting in funds becoming effectively lost/unaccounted-for from the user's perspective (recorded as delivered while sitting unreturned in the vault) — a material accounting-corruption and potential fund-loss impact within the "Required Impacts" scope (corruption of canonical UniversalTx state / revert destination / unauthorized-refund-adjacent accounting failure).

### Likelihood Explanation
This does not require any malicious validator, node, or TSS participant — it is a deterministic bug in the honest client code that fires on ordinary, unprivileged-attacker-reachable conditions: any outbound whose destination-chain execution fails (attacker can often induce this, e.g., by controlling or reverting in a recipient contract), triggering the vault's `revertUniversalTx` or `fundsRescued` path instead of `finalizeUniversalTx`. Every honest UV independently derives the same wrong `Success:true` observation, so the ballot reaches quorum with certainty, not merely with probability.

### Recommendation
`ParseEvent` should carry the specific `eventType` (finalize vs revert vs rescue) into the resulting `store.Event`'s payload, and `buildOutboundObservation` must derive `Success`/`ErrorMsg` from that event type (e.g., `Success=true` only for `finalizeUniversalTx`, `Success=false` with an appropriate `ErrorMsg` for `revertUniversalTx`/`fundsRescued`) instead of hardcoding `Success: true` for every outbound-observation event.

### Proof of Concept
1. Emit two EVM logs with identical `Topics[1]` (txID) and `Topics[2]` (universalTxID) but different underlying event signatures, once processed as `EventTypeFinalizeUniversalTx` and once as `EventTypeRevertUniversalTx`.
2. Call `ParseEvent(log, EventTypeFinalizeUniversalTx, ...)` and `ParseEvent(log, EventTypeRevertUniversalTx, ...)` — both return a `store.Event` with `Type: store.EventTypeOutbound` and identical `EventData` (`{TxID, UniversalTxID}`); nothing distinguishes them. [8](#0-7) 
3. Feed each resulting event into `EventProcessor.buildOutboundObservation` — both produce `OutboundObservation{Success: true, ErrorMsg: "", TxHash: ..., GasFeeUsed: ...}`, with no field reflecting that one came from a revert and the other from a finalize. [9](#0-8) 
4. Both observations, when identical in `TxHash`/`GasFeeUsed`, hash to the same `GetOutboundBallotKey(utxId, outboundId, observedTx)`, merging a finalize vote and a revert vote onto the same ballot variant.

// buildOutboundObservation builds an OutboundObservation from event metadata and parsed outbound data
func (ep *EventProcessor) buildOutboundObservation(event *store.Event, outboundData *OutboundEvent) (*uexecutortypes.OutboundObservation, error) {
	// Extract txHash from EventID (format: "txHash:logIndex" or "signature:logIndex")
	txHash := ""
	parts := strings.Split(event.EventID, ":")
	if len(parts) > 0 {
		txHash = parts[0]
	}

	// Convert txHash to hex format if it's in base58
	txHashHex, err := ep.base58ToHex(txHash)
	if err != nil {
		ep.logger.Warn().
			Str("tx_hash", txHash).
			Err(err).
			Msg("failed to convert txHash to hex, using original value")
		txHashHex = txHash
	}

	gasFeeUsed := "0"
	if outboundData.GasFeeUsed != "" {
		gasFeeUsed = outboundData.GasFeeUsed
	}

	observation := &uexecutortypes.OutboundObservation{
		Success:     true,
		BlockHeight: event.BlockHeight,
		TxHash:      txHashHex,
		ErrorMsg:    "",
		GasFeeUsed:  gasFeeUsed,
	}

	return observation, nil
