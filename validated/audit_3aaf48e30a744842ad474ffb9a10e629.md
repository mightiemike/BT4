### Title
Unvalidated `beneficiary_id` in `DeleteAccount` Action Causes Permanent Token Burn - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_delete_account` transfers an account's entire remaining balance to a caller-supplied `beneficiary_id` without ever checking that this account exists (or can be implicitly created). If the target does not exist, the resulting refund receipt fails and the tokens are permanently burnt rather than returned to anyone — directly analogous to the reported `setValidatorAddress` issue where an unvalidated recipient address can cause funds to be irrecoverably lost.

### Finding Description
When a `DeleteAccountAction` is executed, `action_delete_account` unconditionally queues a system-style refund receipt carrying the deleted account's entire balance to `delete_account.beneficiary_id`, with no check that this account currently exists: [1](#0-0) 

The only validations documented/enforced for `DeleteAccountAction` are format validity of `beneficiary_id`, that delete is the final action, and that the account isn't staking — none of them confirm the beneficiary account exists: [2](#0-1) 

The balance transfer is created via `Receipt::new_balance_refund`, which is a system-predecessor ("refund") receipt. Refund receipts are specifically exempted from implicit-account creation, so a `Transfer` to a non-existent named account (or an implicit account type refunds cannot create) fails with `AccountDoesNotExist`: [3](#0-2) [4](#0-3) 

This is confirmed by an existing unit test asserting that a refund to a missing account is rejected and does not create the account: [5](#0-4) 

When a refund receipt (`predecessor_id().is_system()`) fails, the runtime does not create a further recovery receipt — it simply burns the deposited amount into `other_burnt_amount`: [6](#0-5) 

This burn-on-failed-refund behavior is explicitly documented as intended for refunds in general: [7](#0-6) 

Combining these: the source account is deleted (irreversibly removing its state), the balance-transfer receipt is generated as a refund receipt, and if `beneficiary_id` does not exist, that receipt's execution fails and the entire balance is permanently burnt with no path to recovery — the same class of unrecoverable-fund-loss described in the external report ("Lack of `newAddress` validation ... tokens could be locked in the contract forever").

### Impact Explanation
Any unprivileged transaction signer who submits a `DeleteAccountAction` with a typo'd, malformed-but-valid-format, or otherwise non-existent `beneficiary_id` (including one that cannot be implicitly created because the transfer is a refund, not a normal transfer) causes their entire account balance to be permanently and unrecoverably burnt from total supply. There is no confirmation step, no fallback to the predecessor, and no recovery mechanism — this is a direct, protocol-level permanent loss of user funds triggered by a single transaction.

### Likelihood Explanation
High likelihood: any account holder (or a relayer submitting a meta-transaction on their behalf) can trigger this simply by submitting a `DeleteAccountAction` naming a `beneficiary_id` that does not exist on-chain — no special privileges, races, or validator/network cooperation required. This can happen accidentally (typo) or be deliberately exploited to permanently destroy funds (e.g., in griefing scenarios via relayed/meta transactions where a relayer or intermediary chooses the beneficiary).

### Recommendation
Add an existence check (and/or an implicit-creation allowance check) for `beneficiary_id` before executing `action_delete_account`, rejecting the action with `AccountDoesNotExist` (or a dedicated error) up front if the account cannot receive the refund, instead of deleting the source account and later burning the balance on a failed refund receipt.

### Proof of Concept
1. Create/own an account `alice.near` holding balance `B`.
2. Submit a transaction from `alice.near` to itself containing `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent123456789.near" })` where the beneficiary account does not exist.
3. `action_delete_account` deletes `alice.near` and queues `Receipt::new_balance_refund(&"nonexistent123456789.near", B)` [1](#0-0) .
4. The refund receipt (system predecessor) executes a `Transfer` to the nonexistent beneficiary; `check_account_existence` rejects it with `AccountDoesNotExist` because refunds cannot implicitly create accounts [4](#0-3) .
5. Because the failing receipt's predecessor is `system`, the runtime burns the entire deposit `B` into `other_burnt_amount` instead of refunding it anywhere [6](#0-5) .
6. Balance `B` is permanently gone from total supply with no recovery path.

```rust
/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
```

```markdown
Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
```
