### Title
Unbounded growth of the shared `IdempotentPromiseHandler.identifiers` map allows a single app user to DoS the `afterAuth` hook execution for all tenants during token-exchange/OAuth-callback authentication - (File: `packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts`)

### Summary
The reported analog in the original finding is a shared, unbounded state structure that legitimate low-cost requests can flood, causing a downstream confirmation step to become unusable for everyone relying on it. In `shopify-app-js`, the `IdempotentPromiseHandler` used by the token-exchange auth strategies (Remix, React Router, and Express packages) plays a similar role: it is a single, process-wide instance shared across *all* shops/tenants on an app deployment, keyed by an attacker/user-supplied `sessionToken` string, with cleanup that is O(n) over the whole map on every single call.

### Finding Description
`IdempotentPromiseHandler` stores every `identifier` (the raw session token JWT) it sees in an in-memory `Map`, and only removes entries once they are older than a 60-second TTL, and only during a full `forEach` scan performed inside every `handlePromise` call: [1](#0-0) 

This handler is instantiated exactly once per app config, not per shop or per request, and is shared globally across the whole running app instance: [2](#0-1) 

It is invoked on the authenticated request path used to complete token exchange and fire the `afterAuth` hook, keyed on the raw session token that is used to authenticate the request: [3](#0-2) [4](#0-3) [5](#0-4) 

Every embedded-app page load or App Bridge fetch generates a fresh, uniquely-`jti`'d session token that Shopify signs for the authenticated merchant/user. Because the map key is the entire token string (never re-used, always unique per issuance), any single authenticated app user (merchant staff, or online-token customer/collaborator user) can repeatedly hit an authenticated route (e.g. reloading the embedded app or replaying App Bridge session-token fetches) to generate a continuous stream of unique identifiers. Each request:
1. Adds a new entry to the shared `identifiers` Map (`isPromiseRunnable`).
2. Performs a full `Map.forEach` scan of all currently-tracked identifiers across *every tenant* in `clearStaleIdentifiers`, even though the TTL window is only 60 seconds — so during a burst the map can still grow to the size of "requests in the last 60 seconds" for the *entire app instance*, not just for the flooding shop.

Because the handler and its map are shared process-wide, a single unprivileged/single-merchant actor sustaining a request flood degrades this shared confirmation/cleanup loop for concurrently-authenticating shops.

### Impact Explanation
While this is not an on-chain gas-limit revert like the referenced report, the structural analog holds: cheap, repeatable, attacker-controlled entries accumulate in a single shared unbounded/loosely-bounded collection that a common code path scans in full on every invocation. Under sustained flooding by one merchant/user, the shared `identifiers` map and its per-call `forEach` scan add increasing CPU and memory overhead to the token-exchange/`afterAuth` authentication path for all shops served by that app instance, which can delay or effectively deny the completion of the authenticated request pipeline (session persistence + `afterAuth` hook, which often performs billing checks, webhook registration, and app setup) for other tenants sharing the same Node process.

### Likelihood Explanation
Any authenticated app user (a single merchant or an online-token holder for their own shop) can trigger this without any special privilege — simply causing repeated App Bridge/session-token refreshes or automating repeated calls to an authenticated route drives the map growth; no cross-tenant secret or forged credentials are required.

### Recommendation
Bound the `identifiers` map independent of wall-clock TTL (e.g. enforce a maximum map size with eviction, or use a per-shop/tenant-scoped handler instance instead of one shared globally across all tenants), and avoid a full-map scan on every call — e.g. use a scheduled/periodic sweep or a data structure (like an ordered map/queue) that allows O(1) expiry of the oldest entries instead of `Array.forEach`/`Map.forEach` over the entire collection on each request.

### Proof of Concept
1. Deploy a multi-tenant embedded app using `shopify-app-remix` (or `-express`/`-react-router`) with `useOnlineTokens` or token-exchange enabled.
2. As a single authenticated merchant/user, script repeated requests to an authenticated route, each carrying a freshly obtained (unique `jti`) session token from App Bridge/`getSessionToken()`.
3. Observe that each request adds a new entry to the shared `IdempotentPromiseHandler.identifiers` map (`packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts`), and that `clearStaleIdentifiers` performs a full scan of that shared map on every request from any tenant, showing measurable CPU/memory overhead growth that is proportional to the flooding tenant's request rate but affects the shared process handling all tenants.

```typescript
const IDENTIFIER_TTL_MS = 60000;

export class IdempotentPromiseHandler {
  protected identifiers: Map<string, number>;

  constructor() {
    this.identifiers = new Map<string, number>();
  }

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }

  private async clearStaleIdentifiers() {
    this.identifiers.forEach((date, identifier, map) => {
      if (Date.now() - date > IDENTIFIER_TTL_MS) {
        map.delete(identifier);
      }
    });
  }
```
