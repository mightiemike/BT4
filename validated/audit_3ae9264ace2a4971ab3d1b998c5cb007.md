### Title
Governance proposals mutating `WITNESS_STANDBY_ALLOWANCE`/reward-affecting dynamic properties take effect immediately and are applied retroactively to votes accrued over the entire just-completed maintenance cycle - (File: `consensus/src/main/java/org/tron/consensus/dpos/IncentiveManager.java`)

### Summary
`IncentiveManager.reward()` distributes the full `WITNESS_STANDBY_ALLOWANCE` pool proportionally across votes that standby witnesses accumulated over an entire maintenance cycle, but the allowance value it reads is whatever is currently stored in `DynamicPropertiesStore` at the moment maintenance runs, with no snapshot taken at the start of the cycle. Because proposal-driven changes to that value are applied synchronously and take effect immediately once approved, a parameter change approved during the cycle is used to pay out rewards for the entire, already-elapsed cycle, not just for votes going forward.

### Finding Description
`ProposalController.processProposals()` -> `ProposalService.process()` writes new values for governance parameters such as `WITNESS_STANDBY_ALLOWANCE` and `WITNESS_PAY_PER_BLOCK` directly into `DynamicPropertiesStore` as soon as a proposal expires and has enough approvals: [1](#0-0) [2](#0-1) 

Separately, `MaintenanceManager.applyBlock()` triggers `doMaintenance()` at the maintenance boundary, which counts votes accumulated by standby witnesses over the entire cycle and then calls `incentiveManager.reward(newWitnessAddressList)`: [3](#0-2) 

`IncentiveManager.reward()` reads `consensusDelegate.getWitnessStandbyAllowance()` at the moment of distribution and divides that pool according to `voteCount`, which is the cumulative vote count gathered over the whole cycle just ended: [4](#0-3) 

Because both the proposal-parameter mutation and the reward distribution happen as part of the same maintenance-time processing (block reaching `nextMaintenanceTime`), any governance change to `WITNESS_STANDBY_ALLOWANCE` (or similarly `WITNESS_PAY_PER_BLOCK`, which feeds `payReward()`/brokerage math in `MortgageService`) that becomes effective in that maintenance cycle is applied to the vote weight accumulated for the *entire preceding cycle*, not merely to future distributions. This mirrors the reported bug class: an admin-controlled parameter that feeds a reward-accounting formula is mutated without first "settling"/paying out rewards for the time period already elapsed under the old parameter value.

### Impact Explanation
If `WITNESS_STANDBY_ALLOWANCE` is increased or decreased via a passed proposal, standby witnesses (and their voters, indirectly, since this allowance flows into witness account allowance/reward pools) receive a payout computed with the new rate applied to votes and activity that occurred entirely under the old rate. This causes incorrect (either inflated or deflated) TRX reward issuance for a period that has already passed, which is an accounting/consensus-relevant reward-correctness defect, not merely a UX inconvenience, since it changes the amount of TRX minted/allocated to accounts.

### Likelihood Explanation
Triggering this requires only that a normally-functioning on-chain governance proposal (any account/witness participating in the proposal-and-approval process, which itself is a permissionless flow reachable via broadcast `ProposalCreateContract`/`ProposalApproveContract` transactions) passes and expires during a maintenance interval in which standby-witness rewards are also being computed. Since this is normal governance operation (not a privileged bypass), and maintenance/reward computation happens automatically every cycle, the condition can occur under ordinary conditions whenever a relevant proposal happens to expire around a maintenance boundary — this is a systemic timing/ordering issue rather than a rare edge case.

### Recommendation
Snapshot cycle-relevant reward parameters (e.g. `WITNESS_STANDBY_ALLOWANCE`) at the start of a maintenance cycle and use that snapshot for `IncentiveManager.reward()` during that cycle's payout, only allowing newly-approved proposal values to take effect starting with the *next* cycle — analogous to how `DelegationStore`/`MortgageService` already defers `brokerage` changes to `nextCycle` rather than applying them to the currently-accruing cycle: [5](#0-4) [6](#0-5) 

### Proof of Concept
1. Standby witness `W` accrues votes over maintenance cycle `N` (votes counted via `countVote(votesStore)` in `MaintenanceManager.doMaintenance()`). [7](#0-6) 
2. Near the end of cycle `N`, a `ProposalCreateContract` raising `WITNESS_STANDBY_ALLOWANCE` gathers enough SR approvals and its `expirationTime` falls within cycle `N`.
3. When the block whose timestamp reaches `nextMaintenanceTime` is applied, `ProposalController.processProposals()` immediately commits the new, higher `WITNESS_STANDBY_ALLOWANCE` value via `ProposalService.process()`. [2](#0-1) 
4. In the very same maintenance pass, `IncentiveManager.reward()` distributes the now-inflated `totalPay` across all votes standby witnesses accumulated over the whole of cycle `N`, even though that vote-earning activity occurred entirely under the old (lower) allowance. [8](#0-7) 

Full confirmation of the exact call ordering between `ProposalController.processProposals()` and `MaintenanceManager.doMaintenance()` within `Manager`'s per-block maintenance dispatch could not be completely traced with the available index (the orchestrating method in `framework/src/main/java/org/tron/core/db/Manager.java` that sequences these two calls was not fully retrievable); a Devin session with full repository access should confirm the precise ordering to fully validate whether the proposal commit and the reward payout occur in the same maintenance-time transaction/block.

  public void reward(List<ByteString> witnesses) {
    if (consensusDelegate.allowChangeDelegation()) {
      return;
    }
    if (witnesses.size() > WITNESS_STANDBY_LENGTH) {
      witnesses = witnesses.subList(0, WITNESS_STANDBY_LENGTH);
    }
    long voteSum = 0;
    for (ByteString witness : witnesses) {
      voteSum += consensusDelegate.getWitness(witness.toByteArray()).getVoteCount();
    }
    if (voteSum <= 0) {
      return;
    }
    long totalPay = consensusDelegate.getWitnessStandbyAllowance();
    for (ByteString witness : witnesses) {
      byte[] address = witness.toByteArray();
      long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay
          / voteSum));
      AccountCapsule accountCapsule = consensusDelegate.getAccount(address);
      accountCapsule.setAllowance(accountCapsule.getAllowance() + pay);
      consensusDelegate.saveAccount(accountCapsule);
    }
  }
