### Title
Post-validation mutation of receipt size bypasses `max_receipt_size` enforcement, causing congestion/bandwidth accounting to operate on out-of-bound values - (File: runtime/runtime/src/verifier.rs, runtime/runtime/src/congestion_control.rs)

### Summary
`validate_receipt`/`validate_action_receipt` in `runtime/runtime/src/verifier.rs` enforce the `max_receipt_size` bound only once, at the moment a new receipt is validated with `ValidateReceiptMode::NewReceipt`. Later mutations to that same receipt (appending `output_data_receivers`, attaching a large returned value via `promise_return`/`value_return`) are not re-validated, so the receipt that actually gets persisted, forwarded, and accounted for by congestion control and the bandwidth scheduler can be larger than `max_receipt_size`. Instead of re-enforcing the bound at every consumption site, the downstream congestion/bandwidth code "pretends" the receipt is within bounds by clamping it, which is exactly the flawed pattern described in the report: validation performed at one call site, but other call sites that consume the same (now different) value skip validation and instead proceed as if it were valid.

### Finding Description
`validate_receipt` (`runtime/runtime/src/verifier.rs:681-696`) checks `receipt_size > limit_config.max_receipt_size` only `if mode == ValidateReceiptMode::NewReceipt`. [1](#0-0) 

This call is invoked exactly once, right after a new receipt is produced from action execution, inside `apply_action_receipt` in `runtime/runtime/src/lib.rs`: [2](#0-1) 

However, a receipt created via `receipt_manager.rs` (e.g. through `promise_return`/`create_action_receipt`, or via `value_return` populating a `Data` receipt in `function_call.rs`) can have its `output_data_receivers` or payload mutated/grown *after* it was validated as a "new receipt", as documented directly in the code comment and confirmed by the dedicated regression test: [3](#0-2) 

Once this happens, the receipt on the wire is larger than `max_receipt_size`, yet no other code path re-validates it. Downstream, the congestion-control forwarding logic explicitly does not enforce the bound — it just clamps the size used for bookkeeping/admission decisions and forwards or buffers the oversized receipt anyway: [4](#0-3) 

The same clamp-instead-of-reject pattern is applied again when generating bandwidth requests (`generate_bandwidth_requests`, referenced at `runtime/runtime/src/congestion_control.rs:503,561` in the module's own documentation) and is explicitly tracked as a known, only partially mitigated issue: [5](#0-4) 

This is structurally identical to the `OracleUniGeoDistribution` bug: the bound (`max_receipt_size` / usable-tick range) is validated correctly at one call site (`floorPriceToRick`'s validated call in `isValidParams` / `validate_receipt`'s `NewReceipt` check), but other call sites that consume the same underlying value after it can change (`query`/`computeSwap`/`cumulativeAmount0/1` / congestion admission, buffering, bandwidth-request generation) do not re-validate and instead let out-of-range values flow through, with only a "pretend it's in range" clamp as a stopgap.

### Impact Explanation
An oversized receipt (larger than the protocol's `max_receipt_size`) can be forwarded across shards and persisted in outgoing/delayed receipt buffers despite congestion-control code assuming all receipts are bounded by `max_receipt_size` for its gas/size accounting. Because the clamp only affects the *admission* comparison and not the actual bytes stored/transmitted, `CongestionInfo`'s `receipt_bytes`/buffered-gas bookkeeping and the bandwidth scheduler's per-link grants are computed against a value that understates the true payload size. This can let state/witness-affecting data flow through channels sized under the assumption of a strict per-receipt cap, risking state-witness size-limit violations and unbounded resource usage on receiving shards, or divergent behavior if any node path treats size as authoritative while another doesn't (receipts stuck/duplicated across resharding boundaries, oversized-storage-proof edge cases). This is transaction-triggered (an ordinary contract call that emits `promise_return` or a large `value_return`), reachable by any contract deployer/caller, and the codebase itself acknowledges it as a live, only-mitigated bug (issue #12606) rather than a fully fixed one.

### Likelihood Explanation
High likelihood of triggering the underlying condition: it requires no privileged access, just a contract that issues a `FunctionCall` whose returned/attached data is appended to `output_data_receivers` after the receipt's initial `NewReceipt` validation — exactly what the existing regression tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` construct. [6](#0-5) [7](#0-6) 
The severity of downstream consequences (state-witness/bandwidth accounting divergence vs. mere availability degradation) depends on interactions with congestion control internals that were not fully traceable from the index alone (see caveat below).

### Recommendation
Re-validate (or recompute and enforce) `max_receipt_size` on the *final* receipt object at every point where a receipt is committed to storage/buffers/forwarding (`ReceiptSinkV2::try_forward`, `buffer_receipt`, `generate_bandwidth_requests`) rather than relying solely on the single `NewReceipt`-mode check performed immediately after receipt construction and before subsequent mutation (`output_data_receivers` append, `value_return` attachment). Alternatively, make receipt construction append-then-validate atomic so no consumer ever observes a receipt whose true size exceeds the validated bound, removing the need for the "pretend it's `max_receipt_size`" clamp in `congestion_control.rs`.

### Proof of Concept
1. Deploy a contract and call a method that issues a cross-contract promise chain where an intermediate promise appends to `output_data_receivers` after receipt creation, or returns a value near `max_receipt_size`, as done in `test_max_receipt_size_promise_return` / `test_max_receipt_size_value_return`. [8](#0-7) 
2. Observe (via `assert_oversized_receipt_occurred`) that the resulting incoming/forwarded receipt exceeds `max_receipt_size` and is still processed by `try_forward`/congestion accounting rather than rejected, because `validate_receipt`'s size check was only applied before the mutation and is never re-applied at the forwarding/bandwidth-accounting call sites. [9](#0-8) 

**Uncertainty:** The exact downstream state-root-divergence or fee-bypass consequence of the oversized-receipt clamp (beyond the "receipt stuck forever" availability concern the code comment mentions) could not be fully confirmed from the indexed code alone — deeper tracing through `bootstrap_congestion_info`, `outgoing_metadatas`, and the bandwidth-request generation math (`runtime/runtime/src/congestion_control.rs:503-570`) would be needed to determine whether the size mismatch can be leveraged for concrete value movement versus only availability/accounting skew.

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
