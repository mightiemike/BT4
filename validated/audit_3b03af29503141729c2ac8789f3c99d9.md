### Title
Meta Transaction Deposit Refund Misdirection Allows Sender to Drain Relayer's Attached Deposit — (`runtime/runtime/src/actions.rs`)

---

### Summary

In `apply_delegate_action`, the inner receipt spawned from a `DelegateAction` has its `predecessor_id` set to `sender_id` (Alice/the user), not to the relayer who actually paid for the attached deposit. When that inner receipt fails at the receiver's shard, the runtime's deposit-refund path sends the full attached deposit back to `predecessor_id` — Alice — rather than to the relayer who funded it. An unprivileged user can deliberately craft a `DelegateAction` with a large attached deposit targeting a call that is guaranteed to fail, causing the relayer to lose the deposit while the user gains it.

---

### Finding Description

**Step 1 — Inner receipt creation with wrong predecessor**

In `apply_delegate_action` the new receipt is built as:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // Alice, NOT the relayer
    receiver_id: delegate_action.receiver_id().clone(),
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(), // relayer
        ...
        actions: delegate_action.get_actions(),
    }),
});
``` [1](#0-0) 

The code comment immediately below this block acknowledges the consequence:

> "If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction. Gas is refunded to the signer, this is Relayer." [2](#0-1) 

**Step 2 — Deposit refund routing on failure**

When the inner receipt fails at the receiver's shard, `refund_unspent_gas_and_deposits` computes:

```rust
let deposit_refund = if result.result.is_err() { total_deposit } else { Balance::ZERO };
```

and then emits:

```rust
result.new_receipts.push(Receipt::new_balance_refund(
    receipt.balance_refund_receiver(),
    deposit_refund,
));
``` [3](#0-2) [4](#0-3) 

**Step 3 — `balance_refund_receiver` resolves to Alice**

```rust
pub fn balance_refund_receiver(&self) -> &AccountId {
    self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
}
``` [5](#0-4) 

Because the inner receipt uses `ReceiptEnum::Action` (not `ActionV2`), `refund_to()` always returns `&None`:

```rust
ReceiptEnum::Action(_) | ... => &None,
``` [6](#0-5) 

So `balance_refund_receiver()` falls back to `predecessor_id()`, which is Alice. The relayer's deposit is transferred to Alice.

**Step 4 — The relayer paid, not Alice**

The relayer is the transaction signer. Gas and deposit are charged from the relayer's account during `verify_and_charge_transaction`. The gas refund correctly returns to `signer_id` (the relayer):

```rust
result.new_receipts.push(Receipt::new_gas_refund(
    &action_receipt.signer_id(),   // relayer
    gas_balance_refund,
    action_receipt.signer_public_key().clone(),
));
``` [7](#0-6) 

But the deposit refund goes to Alice. The split is asymmetric and exploitable.

The architecture documentation explicitly acknowledges this as a live design flaw:

> "But what if the transaction fails execution on Bob's shard? At this point, the predecessor is Alice and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard." [8](#0-7) 

---

### Impact Explanation

An unprivileged user (Alice) can drain an arbitrary amount of NEAR from any relayer that accepts `DelegateAction`s with attached deposits. The relayer's account balance decreases by the deposit amount; Alice's account balance increases by the same amount. There is no cap on the deposit size other than the relayer's own balance. The attack requires no privileged access, no special contract deployment, and no validator cooperation.

---

### Likelihood Explanation

Meta transactions are a live, default-enabled protocol feature (NEP-366). Any relayer that accepts `DelegateAction`s containing `FunctionCall` or `Transfer` actions with non-zero deposits is exposed. The attack is trivially repeatable: Alice can submit many such actions in parallel across multiple relayers. The only friction is that Alice must find a relayer willing to relay her action, which is the normal use case for meta transactions.

---

### Recommendation

The inner receipt created in `apply_delegate_action` should use `ReceiptEnum::ActionV2` with the `refund_to` field set to the relayer (`action_receipt.signer_id()`), so that deposit refunds on failure are routed to the party who paid for them, while `predecessor_id` remains `sender_id` (Alice) to preserve correct `predecessor_account_id()` semantics inside the contract:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // keep for contract call semantics
    receiver_id: delegate_action.receiver_id().clone(),
    receipt: ReceiptEnum::ActionV2(ActionReceiptV2 {
        signer_id: action_receipt.signer_id().clone(),
        signer_public_key: action_receipt.signer_public_key().clone(),
        refund_to: Some(action_receipt.signer_id().clone()), // relayer receives deposit refund
        gas_price: action_receipt.gas_price(),
        output_data_receivers: vec![],
        input_data_ids: vec![],
        actions: delegate_action.get_actions(),
    }),
});
``` [9](#0-8)

### Proof of Concept

**Setup**: Relayer account `relayer.near` (balance: 100 NEAR). User account `alice.near` (balance: 0 NEAR). Contract `bob.near` has no deployed code.

1. Alice creates and signs a `DelegateAction`:
   - `sender_id`: `alice.near`
   - `receiver_id`: `bob.near`
   - `actions`: `[FunctionCall { method_name: "nonexistent", deposit: 50_NEAR, gas: 100TGas }]`
   - `nonce`: valid nonce from Alice's access key

2. Alice sends the signed `DelegateAction` to the relayer off-chain.

3. The relayer wraps it in a transaction (signer: `relayer.near`, receiver: `alice.near`) and submits it. The relayer's account is charged 50 NEAR (deposit) + gas cost.

4. On Alice's shard, `apply_delegate_action` creates an inner receipt:
   - `predecessor_id = alice.near`
   - `receiver_id = bob.near`
   - `actions = [FunctionCall { deposit: 50_NEAR, ... }]`

5. On Bob's shard, the function call fails (`MethodNotFound` — no contract deployed). `refund_unspent_gas_and_deposits` computes `deposit_refund = 50_NEAR` and calls `Receipt::new_balance_refund(receipt.balance_refund_receiver(), 50_NEAR)`. `balance_refund_receiver()` returns `alice.near`.

6. **Result**: `relayer.near` balance: ~50 NEAR (lost 50 NEAR + gas). `alice.near` balance: 50 NEAR (gained 50 NEAR). Net theft: 50 NEAR per iteration.

The attack is repeatable with fresh nonces and can be parallelized across multiple relayers simultaneously.
