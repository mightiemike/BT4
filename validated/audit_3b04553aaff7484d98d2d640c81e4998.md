### Title
Unbounded `triggerConstantContract` amplification via `ak`/`nk` in `ScanShieldedTRC20NotesByIvkServlet` bypasses HTTP-level rate limiting - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`ScanShieldedTRC20NotesByIvkServlet` is guarded only by `RateLimiterServlet`, which throttles HTTP requests/IP-QPS but has no knowledge of the number of VM `triggerConstantContract` executions a single request can trigger internally. When `ak`/`nk` are supplied, `Wallet.queryTRC20NoteByIvk` calls `isShieldedTRC20NoteSpent` (which runs a full constant-contract VM execution) once per note successfully decrypted within the requested block range, so a single rate-limited HTTP request can cause dozens of VM invocations.

### Finding Description
The servlet extends `RateLimiterServlet`, whose `service()` method only gates on HTTP request counts via `IRateLimiter`/`GlobalRateLimiter` before delegating to `super.service()` [1](#0-0) . It has no concept of the downstream compute cost of the request.

`doGet`/`doPost` forward directly to `wallet.scanShieldedTRC20NotesByIvk(...)`, passing through attacker-controlled `ak`/`nk` with no ownership or ivk-derivation check [2](#0-1) .

`queryTRC20NoteByIvk` bounds the block range to `endNum - startNum <= 1000` [3](#0-2) , then iterates every log of every transaction in that range, calling `getNoteTxFromLogListByIvk` for each note-producing log [4](#0-3) .

`getNoteTxFromLogListByIvk` attempts `Note.decrypt(cenc, ivk, epk, cm)`; only if decryption succeeds (i.e., the note plaintext is present) and `ak`/`nk` are non-empty does it call `isShieldedTRC20NoteSpent`, which builds and runs a real `triggerConstantContract` VM execution per note [5](#0-4) [6](#0-5) .

Note decryption is authenticated (ChaCha20/Poly1305-style), so an arbitrary self-generated `ivk` that was never used to encrypt the notes in the target range will fail to decrypt with overwhelming probability — the "any self-generated ivk, no ownership needed" premise in the question does **not** let an attacker amplify against arbitrary victim logs. However, the check is only cryptographic, not an authorization/ownership proof tied to a signed request: an attacker can cheaply mint their own real shielded notes once (paying normal on-chain fees), and their own `ivk` will reliably decrypt those notes on every subsequent scan. From that point, every HTTP request that includes the block range containing those notes plus their own `ak`/`nk` will trigger one `triggerConstantContract` VM execution per owned note, and this can be repeated indefinitely at the HTTP rate-limit's allowed cadence with no additional on-chain cost. The rate limiter counts only the HTTP call, not the internal VM work, so the per-request compute cost (bounded loosely by 1000-block range × logs × notes) is effectively unpriced beyond the one-time cost of creating the notes.

### Impact Explanation
This is a compute-amplification / underpriced-work issue: a single rate-limit-compliant HTTP request can induce many VM `triggerConstantContract` executions (bounded by the number of shielded notes the attacker controls within the queried ≤1000-block range), and the attacker can replay the same request at the HTTP rate limit indefinitely for near-zero marginal cost. Sustained at scale (many notes × high request rate × concurrent servlet instances such as OnPBFT/OnSolidity variants, which reuse the same `doGet`/`doPost`) this can materially increase full node CPU/VM load, degrading availability for other API consumers — a scoped denial-of-service via amplification that defeats the HTTP request-counting rate limiter's cost-control assumption.

### Likelihood Explanation
Feasibility is real but requires an upfront, non-trivial precondition: the attacker must first create (mint) a batch of real shielded notes in the target contract to guarantee their own `ivk` decrypts many notes in a given block range — decryption cannot be forced against arbitrary/other users' notes due to the authenticated encryption. Once notes exist, the exploit is fully repeatable and cheap (only HTTP calls, no further on-chain transactions), and is reachable by any unprivileged user via the public `/wallet/scanshieldedtrc20notesbyivk` HTTP endpoint or gRPC equivalent.

### Recommendation
- Charge/limit cost proportional to actual internal work, not just HTTP request count: e.g., bound or rate-limit the number of `isShieldedTRC20NoteSpent` (constant-contract) invocations performed per request or per identity/IP within a time window, independent of the outer HTTP rate limiter.
- Reduce the maximum allowed block range specifically when `ak`/`nk` are supplied (since this path is far more expensive per block than the ivk-only decrypt path).
- Consider caching/batching nullifier lookups (e.g., a single batched contract call for multiple nullifiers) instead of one `triggerConstantContract` per note.
- Add a dedicated cost-aware limiter (e.g., token bucket keyed on estimated VM executions) in `RateLimiterServlet` or as an additional guard in `queryTRC20NoteByIvk` for the `ak`/`nk` branch.

### Proof of Concept
Integration test plan (JUnit, extending `WalletMockTest`/`ScanShieldedTRC20NotesServletTest` patterns already in the repo):

2. Mock `Note.decrypt` to return `Optional.of(fakeNote)` for all N logs (simulating notes actually owned/created by the attacker's `ivk`).
3. Spy `Wallet` and stub/count invocations of the private `isShieldedTRC20NoteSpent` (or verify `triggerConstantContract`/`createTransactionCapsule` call count via Mockito `verify(times(N))`) when calling `wallet.scanShieldedTRC20NotesByIvk(start, end, contract, ivk, ak, nk)` with non-empty `ak`/`nk`.
4. Assert that the number of internal VM-trigger invocations equals N per single call, and that this scales linearly with the number of attacker-controlled notes/logs in range, while the HTTP-facing `RateLimiterServletTest` shows the request itself is accepted under normal per-endpoint QPS limits (i.e., one permit for N internal executions).
5. Compare wall-clock time for repeated identical calls with N=1 vs N=1000 logs at the same QPS budget to demonstrate the amplification factor.

    // chooses blocking or non-blocking semantics based on rate.limiter.apiNonBlocking.
    boolean perEndpointAcquired = rateLimiter == null || rateLimiter.acquirePermit(runtimeData);
    boolean acquireResource = perEndpointAcquired && GlobalRateLimiter.acquirePermit(runtimeData);

    String contextPath = req.getContextPath();
    String url = Strings.isNullOrEmpty(req.getServletPath())
        ? MetricLabels.UNDEFINED : contextPath + req.getServletPath();
    // int64_as_string is honored only on GET requests (URL query). POST is intentionally
    // unsupported because reading the body here would consume request.getReader() and
    // break downstream servlets that read it themselves.
    if ("GET".equalsIgnoreCase(req.getMethod())) {
      JsonFormat.setInt64AsString(Util.getInt64AsString(req));
    }
    try {
      resp.setContentType("application/json; charset=utf-8");

      if (acquireResource) {

            MetricKeys.Histogram.HTTP_SERVICE_LATENCY, url);
        super.service(req, resp);
        Metrics.histogramObserve(requestTimer);
      } else {
        resp.getWriter()
            .println(Util.printErrorMsg(new IllegalAccessException("lack of computing resources")));
      }
