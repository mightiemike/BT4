### Title
L1Handler transactions bypass congestion-based fee pricing and hold priority block space, enabling cheap block-stuffing DOS - (File: `crates/apollo_batcher/src/transaction_provider.rs`, `crates/blockifier/src/transaction/l1_handler_transaction.rs`)

### Summary
Analogous to the Aleo `split`-transaction issue (a transaction type with a fixed, congestion-independent fee that can be used to cheaply stuff blocks), `L1Handler` transactions in this sequencer are admitted into every proposed block ahead of ordinary mempool transactions via a dedicated `L1` phase, and their fee-sufficiency check is a trivial nonzero check rather than one that tracks network congestion or the mempool's dynamic gas-price/tip market.

### Finding Description
`ProposeTransactionProvider::get_txs` always services the `L1` phase first, pulling up to `max_l1_handler_txs_per_block` `L1Handler` transactions and appending them to the block *before* any mempool (fee-market) transactions are considered: [1](#0-0) 

`L1Handler` transactions never go through `apollo_mempool`'s `FeeTransactionQueue`/fee-escalation mechanism (the mempool p2p protocol doc explicitly states it does not carry `L1Handler` transactions at all): [2](#0-1) 

At execution time, the only fee sufficiency check performed for an `L1Handler` transaction is that `paid_fee_on_l1 != Fee(0)` — there is no comparison against the actual/dynamic gas price, congestion state, or any EIP-1559-style base fee: [3](#0-2) 

Compounding this, `create_tx_info` for `L1HandlerTransaction` sets `max_fee: Fee::default()` (i.e., `Fee(0)`), so the standard fee-type/version-based checks that other transaction types are subject to are trivially bypassed for this type: [4](#0-3) 

Because `L1Handler` transactions are (a) reserved a dedicated slice of every block (`max_l1_handler_txs_per_block`), (b) never subject to the mempool's tip/gas-price ordering or fee-escalation logic, and (c) only required to present a nonzero `paid_fee_on_l1` regardless of how congested the network is, an L1 message sender can cheaply flood the L1-handler slot of blocks at a fixed near-zero cost per transaction, independent of demand. This mirrors the Aleo `split` bug class exactly: a transaction category whose admission cost does not respond to congestion, allowing attackers to occupy scarce block space cheaply while other transaction types (invoke/declare/deploy_account) pay dynamically increasing tips/gas prices during congestion.

### Impact Explanation
The `L1` phase is serviced unconditionally at the start of every proposed block up to `max_l1_handler_txs_per_block`, meaning this reserved capacity is consumed regardless of the fee paid, as long as it is nonzero. During periods of high demand where honest users are paying escalating tips to get transactions included via the mempool's `FeeTransactionQueue`, an attacker can still guarantee inclusion of `L1Handler` transactions in the L1 slot at negligible cost, crowding out legitimate transaction throughput for the fraction of block capacity reserved for L1 handlers, and potentially delaying time-sensitive operations (e.g., liquidations, bridge finalization) that rely on this channel — directly analogous to the funds-at-risk/liveness scenario described in the source report.

### Likelihood Explanation
Reaching this path requires only sending a message from L1 to the Starknet core contract (an L1 message sender action explicitly listed as an unprivileged, in-scope actor) that will produce an `L1Handler` transaction with a small nonzero `paid_fee_on_l1`. No sequencer/validator/proposer privilege is required — the actor only needs to interact with the L1 bridge/core contract, which is a normal, permissionless action. This makes the analog readily reachable, though the "cost" of triggering it is bounded by L1 gas costs for each `LogMessageToL2`-style call, somewhat limiting the attack's throughput compared to a pure L2 mempool spam vector.

### Recommendation
- Make `L1Handler` admission fee-aware: require `paid_fee_on_l1` (or the equivalent value paid via the L1 message) to scale with the current L2 gas price / congestion signal (e.g., the `apollo_consensus_orchestrator` dynamic gas price mechanism already present in this codebase), rather than only checking `paid_fee_on_l1 != Fee(0)`.
- Reconsider whether `max_l1_handler_txs_per_block` should be a hard, unconditionally-serviced reservation, or should compete with mempool transactions based on effective price once network congestion crosses a threshold.
- Remove or tighten the `TODO(Arni)` nonzero-only fee check in `l1_handler_transaction.rs`, replacing it with a real fee-sufficiency check tied to the `l1_handler_max_amount_bounds`/gas price so that the fee is meaningfully bound to resource cost and congestion, not just non-zero.

### Proof of Concept
1. An attacker repeatedly calls the L1 core contract's `sendMessageToL2` (or equivalent) function targeting an L2 contract's `l1_handler` entrypoint, paying only the minimal nonzero `paid_fee_on_l1` amount.
2. Each resulting `L1Handler` transaction reaches the `ProposeTransactionProvider` in the `L1` phase and is included in the block regardless of L2 network congestion, per `get_txs`: [5](#0-4) 
3. During execution, `execute_raw` only rejects the transaction if `paid_fee_on_l1 == Fee(0)`; any nonzero value passes regardless of the block's actual/target gas price: [6](#0-5) 
4. By repeating this up to `max_l1_handler_txs_per_block` times per block, the attacker consistently occupies the reserved L1-handler block capacity across consecutive blocks at a fee that never rises with demand, unlike ordinary mempool transactions which must pay increasing tips to enter the `priority_queue` in `FeeTransactionQueue`: [7](#0-6) 

Note: I was unable to fully trace the exact value substituted for `paid_fee_on_l1` when an `L1Handler` transaction is first constructed from a raw L1 event (`apollo_l1_events`/`papyrus_base_layer`) within the tool budget available; I confirmed only that on the consensus-conversion path this value is currently hardcoded to `Fee(1)` with an explicit TODO to "put real value in `paid_fee_on_l1`" [8](#0-7) , which — if representative of the value used during proposal as well — would make the described attack even cheaper than implied above.

    async fn get_txs(&mut self, n_txs: usize) -> TransactionProviderResult<NextTxs> {
        assert!(n_txs > 0, "The number of transactions requested must be greater than zero.");
        let mut txs = vec![];
        if self.phase == TxProviderPhase::L1 {
            let n_l1handler_txs_to_get =
                min(self.max_l1_handler_txs_per_block - self.n_l1handler_txs_so_far, n_txs);
            let mut l1handler_txs = self.get_l1_handler_txs(n_l1handler_txs_to_get).await?;
            self.n_l1handler_txs_so_far += l1handler_txs.len();

            // Determine whether we need to switch to mempool phase.
            let no_more_l1handler_in_provider = l1handler_txs.len() < n_l1handler_txs_to_get;
            let reached_max_l1handler_txs_in_block =
                self.n_l1handler_txs_so_far == self.max_l1_handler_txs_per_block;
            if no_more_l1handler_in_provider || reached_max_l1handler_txs_in_block {
                self.phase = TxProviderPhase::Mempool;
            }

            txs.append(&mut l1handler_txs);
            if txs.len() == n_txs {
                return Ok(txs);
            }
        }
