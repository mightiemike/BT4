## Finding: `ensure_match_transaction_info` skips checkpoint-hash validation, allowing corrupted state roots to pass replay/verification checks

### Summary
`aptos-types`'s `TransactionOutput::ensure_match_transaction_info` — the function used by `aptos move replay` tooling to confirm a locally re-executed `TransactionOutput` matches an authenticated `TransactionInfo` pulled from the accumulator-proven ledger — validates status, gas, write-set hash, and event-root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is the exact same bug *class* as the SelfLiquidate report: a value that should participate in an integrity check (the "collateral"/state root a party is entitled to rely on) is silently excluded from the computation/verification, so a divergent value is accepted as correct.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (`CryptoHash::hash(self.write_set())`) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but the function returns `Ok(())` right after a `TODO` comment that explicitly says the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)" — meaning `txn_info.state_checkpoint_hash()`, `.hot_state_checkpoint_hash()`, and `.position_state_checkpoint_hash()` are never compared against anything computed from the locally re-executed state. [2](#0-1) 

The `TransactionInfo` (`TransactionInfoV0`/`V1`) carries `state_checkpoint_hash` as the authenticated Sparse-Merkle-Tree root of world state at that version, protected under the ledger's `TransactionAccumulator`. [3](#0-2) 

Because this hash is skipped in `ensure_match_transaction_info`, any tool that relies on this function to validate replay correctness (confirmed callers are in `aptos-move/cli/src/commands.rs`, i.e., the `aptos move replay` CLI subcommand path) will report success even if the locally computed state root diverges from the authenticated on-chain root — as long as the write set, events, gas, and status happen to match. A write set can hash-match (state_change_hash is just a hash of the write ops) while the *resulting* SMT root diverges from consensus if there is any nondeterminism or divergence in how the local executor derives/accumulates the state tree from that same write set (e.g., differing state view/base tree, or a local state-sync bug), since that computation is entirely separate from the write set itself and is exactly what `state_checkpoint_hash` is meant to catch.

### Impact Explanation
This breaks the "authenticated API and state-view output must stay bound to the right ledger version/root" invariant from the proof-and-storage pivots: a replay/verification pass which is supposed to authenticate that a node's storage/state matches the canonical, accumulator-proven ledger can silently accept a divergent state root. In a hard-fork/divergence scenario (execution non-determinism, storage schema/format bugs, or corrupted restore), this tool would fail to catch the divergence because it only checks the write-set hash and event root, not the actual Merkle state root that the write set is applied against. This matches the required "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category, and the "authenticated API or state-view output bound to the wrong version, object, or proof context" category, since a downstream consumer would trust that replay-verify passing means the state root is verified when it is not.

### Likelihood Explanation
This is a real, currently-existing gap (not speculative) — it's explicitly documented in-code with a TODO acknowledging the exact hole, gated behind not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature work. It is a code-level integrity gap in a validation routine used by the CLI replay path. Likelihood is limited by the fact that it requires: (1) a pre-existing execution/storage divergence to actually exist for this gap to matter, and (2) the affected tool's role is validation/debugging (`aptos move replay`), not consensus-critical block processing — the block-commit path (`do_ledger_update.rs`, `assemble_transaction_infos`) independently recomputes `state_checkpoint_hash` and includes it in the committed `TransactionInfo`/accumulator, so mainnet consensus integrity itself isn't directly broken by this gap. The exposure is specifically that *tooling meant to detect* a divergence (replay-verify) would under-report it.

### Recommendation
Extend `ensure_match_transaction_info` to also compare locally-computed `state_checkpoint_hash` (and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` when applicable) against `txn_info`'s corresponding fields, passing in the locally-computed checkpoint hash(es) as an additional parameter, before returning `Ok(())`.

### Proof of Concept
Not applicable as a live network exploit — this is a verification-tooling logic gap, demonstrable by unit test: construct a `TransactionOutput`/`TransactionInfo` pair whose `write_set`, `events`, `gas_used`, and `status` all match, but whose local state application would produce a different `state_checkpoint_hash` than `txn_info.state_checkpoint_hash()`; `ensure_match_transaction_info` returns `Ok(())` despite the mismatch.

**Caveat on confidence:** I was unable to fully trace the runtime call sites of `ensure_match_transaction_info` beyond `aptos-move/cli/src/commands.rs` (file too large to fully inspect in the remaining budget), so I cannot confirm every consumer of this comparator or whether any consensus-critical/state-sync path (versus only the CLI replay tool) depends on it. If a consensus-relevant path also uses it, the severity assessment above should be revisited upward.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
