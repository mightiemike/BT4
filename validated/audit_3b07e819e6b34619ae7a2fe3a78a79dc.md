### Title
Missing `TokenConfig.Enabled` validation lets minting/bridging continue for admin-disabled tokens - (File: `x/uexecutor/keeper/handler.go`)

### Summary
This is the Push Chain analog of GMX M-37 ("no market enabled validation in Swap/CreateAdl"). Push Chain's `x/uregistry` module defines a per-token `Enabled` flag intended to gate whether a token can be minted/bridged, but the inbound-execution code path that mints PRC20s never checks it.

### Finding Description
`TokenConfig` carries an `enabled` field explicitly documented as "Whether this token is enabled for minting/bridging": [1](#0-0) 

The admin can flip this flag off via `MsgUpdateTokenConfig` / `MsgRemoveTokenConfig` (e.g., to halt bridging of a compromised, depegged, or exploited token) as documented in `x/uregistry/README.md`: [2](#0-1) 

However, the core mint path `depositPRC20` — invoked from `ExecuteInboundFunds`, `ExecuteInboundGas`, `ExecuteInboundFundsAndPayload`, and `ExecuteInboundGasAndPayload` — only calls `GetTokenConfig` to fetch the native representation and never inspects `tokenConfig.Enabled`: [3](#0-2) 

`GetTokenConfig` in `x/uregistry/keeper` performs no enabled check either — it is a pure lookup: [4](#0-3) 

By contrast, the chain-level `ChainEnabled.IsInboundEnabled` / `IsOutboundEnabled` flags **are** consistently enforced at every relevant chokepoint: `VoteInbound`, `MsgExecutePayload`, `BuildOutboundsFromReceipt` (outbound creation), and the TSS `verifyOutboundSigningRequest`: [5](#0-4) [6](#0-5) [7](#0-6) 

This demonstrates the module deliberately implements an "enabled" gate pattern for chains, but the equivalent per-token gate is absent from the execution/minting logic — exactly the GMX M-37 bug class (activity — here, minting — executes for a "disabled" registry entry because the enabled check was omitted from the hot path, even though the type explicitly carries the flag for that purpose).

### Impact Explanation
Because `IsChainInboundEnabled` is chain-scoped, not token-scoped, disabling a single token on an otherwise-enabled chain does not stop inbound votes/UTX creation or PRC20 minting for that token. Any unprivileged user who deposits the disabled asset on the source chain and has it observed/voted by honest Universal Validators will still have `depositPRC20` mint the PRC20 representation, defeating the intended admin control. This is an unauthorized-mint / accounting-corruption class impact (PRC20 supply against a token the admin explicitly declared unsafe to mint), reachable purely through the ordinary user deposit → honest-UV-vote → execution pipeline, matching the in-scope "corruption of PRC20 ... accounting ... token mapping" and "unauthorized mint" impact categories.

### Likelihood Explanation
Likelihood is moderate: it requires the admin to have disabled a specific token (a normal operational action, e.g. incident response to a depeg/exploit on the source-chain asset) while the underlying chain remains inbound-enabled. Once that state exists, exploitation requires no special access — a normal deposit on the source chain plus standard honest-validator voting triggers the mint. No malicious validator, relayer, or privileged actor is needed.

### Recommendation
Add a token-enabled check analogous to the existing chain-enabled checks, at minimum inside `depositPRC20` (and ideally as early as inbound-vote finalization for immediate rejection), e.g.:
```go
tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
if err != nil {
    return nil, err
}
if !tokenConfig.Enabled {
    return nil, fmt.Errorf("token %s on chain %s is disabled for minting/bridging", assetAddr, sourceChain)
}
```
This should be applied consistently across `ExecuteInboundFunds`, `ExecuteInboundGas`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`, and the outbound `GetTokenConfigByPRC20` lookup in `create_outbound.go`, mirroring the enforcement pattern already used for `ChainEnabled`.

### Proof of Concept
1. Admin calls `MsgUpdateTokenConfig` to set `Enabled: false` for USDC on `eip155:11155111`, while the chain's `ChainEnabled.IsInboundEnabled` remains `true`.
2. An attacker (or any ordinary user) deposits USDC on the source-chain gateway as usual.
3. Honest Universal Validators observe the event and submit `MsgVoteInbound` (this succeeds — `IsChainInboundEnabled` only checks the chain flag, per `x/uexecutor/keeper/msg_vote_inbound.go`).
4. Quorum is reached, `ExecuteInboundFunds` runs, which calls `depositPRC20` — this only calls `GetTokenConfig` (no `Enabled` check) and successfully mints the PRC20 to the recipient's UEA, per `x/uexecutor/keeper/handler.go`.
5. Result: PRC20 is minted for a token the admin explicitly disabled, silently bypassing the intended control — analogous to GMX's disabled-market Swap/CreateAdl execution.

Note: I was not able to fully trace `GetTokenConfigByPRC20`'s usage in the outbound path (`create_outbound.go`) for a matching `Enabled` check within the available iterations; if it also omits the check, the same class of issue would apply symmetrically to outbound/withdrawal flows. Recommend verifying that path as well in a full session.

```go
func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
```
