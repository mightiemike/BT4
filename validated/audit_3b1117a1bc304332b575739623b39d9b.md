### Title
App Proxy signature verification vulnerable to key/value boundary collision due to unescaped, undelimited concatenation - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
`stringifyQueryForAppProxy`, used to build the canonical string that is HMAC'd to validate Shopify App Proxy requests, concatenates sorted `key=value` pairs with **no delimiter and no escaping**. This is structurally identical to the LibMuon `abi.encodePacked` hash-collision bug: because there is no separator between fields, two different sets of (key, value) pairs can serialize to the exact same canonical string, allowing an attacker to capture Shopify's legitimate signature for one payload and replay it for a different, more privileged parsed payload (e.g. a different `logged_in_customer_id`).

### Finding Description
`generateLocalHmac` selects the canonicalization strategy by `signator`: [2](#0-1) 

For `signator: 'admin'`, `stringifyQueryForAdmin` uses `ProcessedQuery`, which is backed by `URLSearchParams` and joins fields with `&`, percent-encoding both keys and values — this makes it collision-resistant, since a literal `&`/`=` inside a value is escaped and cannot be mistaken for a field boundary: [3](#0-2) 

For `signator: 'appProxy'` (used for all app-proxy/storefront-triggered requests), `stringifyQueryForAppProxy` instead does a raw, unescaped concatenation with **no separator at all** between `key=value` pairs: [4](#0-3) 

`validateHmac` then simply recomputes this canonical string from the parsed query object and compares HMACs: [5](#0-4) 

Because keys are sorted alphabetically and pairs are glued together with nothing between them, the exact same byte string can be produced by two *different* underlying key sets whenever one field's attacker-controlled value happens to contain the literal substring `<otherKey>=<otherValue>`. For example, `{extra: 'xlogged_in_customer_id=999', path_prefix, shop, timestamp}` produces the identical canonical string as `{extra: 'x', logged_in_customer_id: '999', path_prefix, shop, timestamp}` (since `logged_in_customer_id` sorts before `path_prefix`/`shop`/`timestamp` alphabetically). Only `hmac`, `shop`, `signature`, and `timestamp` are protected against this kind of ambiguity via `APP_PROXY_SINGLE_VALUE_PARAMS`, which merely blocks *duplicate occurrences* of those four keys — it does nothing to prevent one key's value from masquerading as `<otherKey>=<value>` when that other key is a different, unprotected field such as `logged_in_customer_id` or `path_prefix`: [6](#0-5) [7](#0-6) 

This is used directly by `shopify-app-remix`'s and `shopify-app-react-router`'s `authenticate.public.appProxy`, whose documented usage pattern is to trust `searchParams.get("logged_in_customer_id")` for identifying the calling customer once `validateAppProxyHmac` returns true: [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker who can get Shopify to sign one app-proxy request with attacker-chosen custom query-parameter values (any custom app-defined param is passed straight through to the app proxy URL by the storefront and forwarded/signed by Shopify verbatim) can craft that value to embed a spoofed `logged_in_customer_id=<victim id>` (or other unprotected field) substring. The attacker then replays that same signature against a *differently-parsed* request where `logged_in_customer_id` is a real, standalone query key equal to the victim's ID. `validateHmac` recomputes an identical canonical string and accepts the forged request, causing the app to believe the request originates from `logged_in_customer_id=<victim>` even though Shopify never actually signed a request on behalf of that customer. Any app that uses `logged_in_customer_id` (or other unprotected app-proxy fields such as `path_prefix`) from the query for authorization or personalization — as the official documentation for `authenticate.public.appProxy` recommends — is exposed to customer impersonation / cross-tenant data exposure via a single unauthenticated storefront-triggered request, without needing the app's API secret.

### Likelihood Explanation
Exploitation requires only an attacker-controlled custom query parameter, which is a standard, expected part of app-proxy URLs (apps commonly forward extra query params to their proxy endpoint), plus one legitimately-triggered app-proxy hit to obtain a valid Shopify signature over the crafted payload, and one direct forged HTTP request to the app's proxy endpoint replaying that signature with the reinterpreted parameters. No secret material, privileged role, or MITM is needed — this is reachable from a single anonymous/customer-level HTTP interaction, matching the required scope.

### Recommendation
Change `stringifyQueryForAppProxy` to use an unambiguous, escaped/delimited encoding just like `stringifyQueryForAdmin`/`ProcessedQuery` (e.g. percent-encode keys/values and join with `&`), or otherwise ensure that no two distinct key/value structures can ever serialize to the same canonical string. If backward compatibility with Shopify's own app-proxy signing scheme must be preserved (Shopify itself concatenates without delimiters for legacy reasons), the safest option is to validate against Shopify's documented canonicalization *and* additionally reject/normalize custom parameter values that contain unescaped `=` characters resembling key boundaries, or to independently re-derive privileged fields (`logged_in_customer_id`, `path_prefix`) only from a fixed, well-known parameter set that cannot be shadowed by arbitrary custom parameter values.

### Proof of Concept
1. App accepts a custom app-proxy query parameter, e.g. `extra`, and forwards it unchanged in proxy links (a common pattern; the app never restricts customer-supplied param names/values).
2. Attacker (unauthenticated) triggers a legitimate app-proxy request with `extra=xlogged_in_customer_id=999&path_prefix=/apps/app&shop=shop.myshopify.com&timestamp=T` (no real `logged_in_customer_id` key present because attacker is not logged in). Shopify computes and returns:
   `signature = HMAC(secret, "extra=xlogged_in_customer_id=999path_prefix=/apps/appshop=shop.myshopify.comtimestamp=T")`.
3. Attacker sends a forged request directly to the app's proxy endpoint (bypassing Shopify) with distinct, separately-parsed parameters: `extra=x&logged_in_customer_id=999&path_prefix=/apps/app&shop=shop.myshopify.com&timestamp=T&signature=<captured signature>`.
4. `validateHmac`/`stringifyQueryForAppProxy` recomputes the exact same canonical string `"extra=xlogged_in_customer_id=999path_prefix=/apps/appshop=shop.myshopify.comtimestamp=T"` from the new key set, `safeCompare` succeeds, and `authenticateAppProxyFactory` treats the request as valid: [10](#0-9) 
5. The app's loader, following the documented pattern, reads `searchParams.get("logged_in_customer_id")` as `"999"` and treats the request as originating from customer `999`, even though Shopify never signed a request on that customer's behalf.

function stringifyQueryForAdmin(query: AuthQuery): string {
  const processedQuery = new ProcessedQuery();
  Object.keys(query)
    .sort((val1, val2) => val1.localeCompare(val2))
    .forEach((key: string) => processedQuery.put(key, query[key]));

  return processedQuery.stringify(true);
}

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
