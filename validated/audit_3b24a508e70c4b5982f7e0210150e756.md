### Title
Unhandled `RuntimeError::UnexpectedIntegerOverflow` causes a hard node panic instead of graceful state-transition failure - (File: chain/chain/src/runtime/mod.rs)

### Summary
`Runtime::apply` (the top-level chunk state-transition function) can return `RuntimeError::UnexpectedIntegerOverflow` from many checked-arithmetic call sites throughout the runtime (validator reward accounting, gas/deposit refund accounting, and congestion-control gas/byte bookkeeping). The chunk-application caller in `chain/chain/src/runtime/mod.rs` treats this error class as unrecoverable and `panic!`s the process rather than surfacing it as a normal `Error`, exactly mirroring the Notional pattern where an arithmetic-underflow assumption violation aborts a critical state-update path instead of being handled gracefully.

### Finding Description
`Runtime::apply` builds/updates several `u128`/`u64` accumulators using `checked_add`/`checked_sub`, converting any arithmetic failure into `RuntimeError::UnexpectedIntegerOverflow(reason)`:
- `CongestionInfo::remove_receipt_bytes`, `remove_delayed_receipt_gas`, `remove_buffered_receipt_gas` (and their `add_*` counterparts) in `core/primitives/src/congestion_info.rs:245-321` subtract exact amounts from congestion accumulators when receipts leave the delayed/buffered/memory-tracked pools. [1](#0-0) [2](#0-1) 
- `update_validator_accounts` in `runtime/runtime/src/lib.rs:1751-1793` computes `locked.checked_add(reward)`, `locked.checked_sub(max(max_of_stakes, last_proposal))`, and `locked.checked_sub(return_stake)`, each mapped to `RuntimeError::UnexpectedIntegerOverflow` on failure. [3](#0-2) 

Whatever the exact trigger (congestion-tracking mismatch, reward/stake accounting edge case, etc.), the caller that drives chunk application does not attempt any graceful recovery:
```
RuntimeError::UnexpectedIntegerOverflow(reason) => {
    panic!("RuntimeError::UnexpectedIntegerOverflow {reason}")
}
``` [4](#0-3) 
This line is explicitly annotated `// TODO(#2152): process gracefully`, i.e., the developers are aware this is a known gap rather than a considered design choice — the same class of "we assumed monotonicity/ordering and didn't account for the exception" root cause identified in the Notional report, where a decreasing external value broke a `checked_sub` invariant and reverted (there, at the function level; here, at the node-process level via `panic!`).

### Impact Explanation
`RuntimeError` is not a benign, recoverable outcome — a panic inside `Runtime::apply` crashes the node process that hit it. Because `Runtime::apply` is invoked identically by every chunk producer/validator applying the same chunk, if the state that trips the overflow/underflow condition is reachable deterministically (i.e., it is not a divergent/adversarial computation but a consequence of legitimate protocol accounting under specific conditions), all honest nodes computing that chunk hit the same panic and crash simultaneously, halting chunk production/validation for that shard. This is strictly more severe than the Notional analog (which blocked only specific actions like liquidations/settlements for one protocol) — here it can halt block/chunk progress for an entire shard, a transaction/receipt-triggered halt as defined in the validation criteria.

### Likelihood Explanation
The likelihood hinges on whether any of the `checked_add`/`checked_sub` operations feeding into `RuntimeError::UnexpectedIntegerOverflow` can actually fail under a legitimate (non-malicious-validator) receipt/transaction sequence — e.g., a congestion-info counter (`buffered_receipts_gas`, `delayed_receipts_gas`, `receipt_bytes`) being decremented by an amount that doesn't exactly match what was previously added due to a bookkeeping edge case in `runtime/runtime/src/congestion_control.rs`. I was not able to fully trace and validate every call site of `add_*`/`remove_*` congestion accounting functions and their invariant guarantees within the tool budget available, so I cannot assert with certainty that a specific transaction sequence triggers the underflow today. What is certain and verifiable is the architectural defect: **any** `UnexpectedIntegerOverflow` anywhere in the apply path is treated as fatal via `panic!`, with an open TODO acknowledging this should be handled gracefully instead. Given the breadth of code paths that can produce this error (validator rewards/stake return, congestion bookkeeping, gas/deposit refund arithmetic), and that congestion accounting is updated on every ordinary cross-shard receipt forward/buffer/drain cycle triggered by regular user transactions, the reachable attack surface is broad enough to warrant a Medium/High-severity fix even without a fully reproduced PoC.

### Recommendation
- Change `chain/chain/src/runtime/mod.rs` to convert `RuntimeError::UnexpectedIntegerOverflow` into a recoverable `Error` (as already done for `RuntimeError::StorageError`) rather than `panic!`, completing the acknowledged `TODO(#2152)`.
- Audit every `checked_add`/`checked_sub` in `core/primitives/src/congestion_info.rs` and `runtime/runtime/src/lib.rs::update_validator_accounts` to confirm the subtracted amounts can never legitimately exceed the accumulator (i.e., prove the invariant rather than merely assume it, as flagged by the comment "should always be <= gas_purchase_price, otherwise receiver_reward might underflow" in `runtime/runtime/src/lib.rs:1040-1042`), and add regression tests for boundary/near-overflow congestion states.
- Where an invariant is truly guaranteed by construction, use `.expect("reason")` with a clear proof-of-safety comment (per the project's own style guide) instead of a fallible path that still panics via a different mechanism; where it is not guaranteed, saturate/clamp and record the discrepancy rather than halting chunk application.

### Proof of Concept
A concrete transaction-only reproduction was not obtained within the available investigation; the finding is based on static analysis of the code paths above. To construct a PoC, a future investigation should:
1. Identify a receipt/action sequence that causes a shard's `buffered_receipts_gas`/`delayed_receipts_gas`/`receipt_bytes` congestion counters to be decremented (`remove_buffered_receipt_gas`/`remove_delayed_receipt_gas`/`remove_receipt_bytes`, `core/primitives/src/congestion_info.rs:256-321`) by more than was previously added for the corresponding receipt, e.g. via edge cases in receipt re-buffering, forwarding, or resizing in `runtime/runtime/src/congestion_control.rs`.
2. Confirm the resulting `RuntimeError::UnexpectedIntegerOverflow` propagates to `Runtime::apply`'s caller and observe the `panic!` at `chain/chain/src/runtime/mod.rs:368`.
