Based on the investigation, I found a strong analog to the reported bug class in the NEAR Wallet Contract.

### Title
Wallet Contract relayer-ban check uses `signer_account_id` (transaction originator) instead of `predecessor_account_id` (actual caller), allowing relayer misbehavior to escape detection - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The `rlp_execute` entrypoint of the Wallet Contract (used for ETH-implicit accounts to have relayers submit NEAR transactions on their behalf) captures `predecessor_account_id` correctly for most of its logic (e.g., `CallerDeposit`, refund routing), but the security-critical decision of whether to ban a misbehaving relayer is gated on `env::signer_account_id()` rather than `predecessor_account_id`, exactly mirroring the Starknet report's confusion between `tx.origin` (signer) and `msg.sender` (predecessor/caller).

### Finding Description
`rlp_execute` records the immediate caller as `predecessor_account_id` at the top of the function: [1](#0-0) 

but the branch that decides whether a faulty relayer should be banned compares the *original transaction signer* to the current account, not the predecessor: [2](#0-1) 

In NEAR, `signer_account_id` is the account that signed the original transaction (`tx.signer_id`, equivalent to `tx.origin` in the Starknet/EVM analogy), while `predecessor_account_id` is the immediate caller of the current receipt (equivalent to `msg.sender`), as documented in the runtime context model: [3](#0-2) 
and exposed via the two distinct host functions `signer_account_id` and `predecessor_account_id`: [4](#0-3) [5](#0-4) 

The docs even flag this exact class of bug generically: "Currently we conflate `originator_id` and `sender_id` in our code base." [6](#0-5) 

For a `FunctionCallPermission`-restricted access key added specifically for `rlp_execute` (as set up in the wallet-contract flow), the relayer normally is both signer and predecessor when it directly signs and sends the transaction, so `signer_account_id == predecessor_account_id` in the common path. However, when the call reaches the wallet contract via an intermediate hop — e.g., a delegate/meta-transaction (`DelegateAction`) is relayed by a third-party relayer, or another contract forwards the call as a cross-contract call — `predecessor_account_id` (the account that actually invoked `rlp_execute`) can diverge from `signer_account_id` (the original transaction signer). In such cases the `env::signer_account_id() == current_account_id` check can be satisfied or bypassed incorrectly relative to who actually caused the relayer error, because the check should be testing "did I (the wallet) call myself" via the predecessor, not "did I sign the outer transaction."

### Impact Explanation
`ban_relayer` is a `#[private]` self-call that revokes the current in-flight-transaction relayer's access key, a protective mechanism intended to stop a misbehaving relayer from repeatedly attempting invalid transactions against the wallet. If the ban condition is evaluated against the wrong identity (`signer_account_id` instead of `predecessor_account_id`), the contract could either:
- Fail to trigger the ban when it should (a genuinely malicious/faulty relayer using an access key continues to be trusted), or
- Trigger the ban incorrectly in scenarios where the transaction path involves an intermediate predecessor that isn't the actual relayer whose key should be revoked.

Either outcome undermines the wallet's key-revocation defense that protects users' ETH-implicit accounts from a compromised or malfunctioning relayer, which can lead to continued unauthorized fund movement attempts or loss of the intended protection (frozen/funds-at-risk scenario), consistent with the "unauthorized value movement" / "invalid state transition acceptance" impact classes for this scan.

### Likelihood Explanation
Reachable directly by an unprivileged relayer/RPC caller: any account holding a `FunctionCall` access key scoped to `rlp_execute` on the wallet-contract account can submit transactions and control whether it is the direct predecessor or arrives via a different call path (e.g., via `DelegateAction`, since the wallet contract flow already integrates with function-call access keys and meta-transaction-style relaying is a first-class NEAR feature). The condition is exercised on every relayer-error path of `rlp_execute`, so it is easily triggerable without any privileged access.

### Recommendation
Change the relayer-ban condition in `rlp_execute` to compare `predecessor_account_id` (already captured) against `current_account_id`, consistent with the rest of the function's use of `predecessor_account_id` for caller-sensitive logic (e.g., `CallerDeposit::new`, refund routing). Audit all other usages of `env::signer_account_id()` in the wallet contract and any other in-repo contracts/runtime logic where an access-control or accounting decision should be based on the immediate caller (`predecessor_id`) rather than the original transaction signer (`signer_id`), per the documented and known conflation risk between these two concepts.

### Proof of Concept
1. Deploy the Wallet Contract as a global contract for an ETH-implicit account, as done in the existing test harness. [7](#0-6) 
2. Register a relayer access key restricted to `rlp_execute` on the eth-implicit account. [8](#0-7) 
3. Construct a call path to `rlp_execute` where the immediate predecessor differs from the original transaction signer (e.g., relay through a `DelegateAction`/meta-transaction or an intermediary contract that forwards the call), while an RLP-encoded Ethereum transaction is crafted to trigger a `Error::Relayer` condition inside `inner_rlp_execute`.
4. Observe that the ban decision at `Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id` evaluates the wrong identity: it does not correctly identify "self-call" (predecessor == current account) which is what should gate whether `ban_relayer` is invoked, since a genuine relayer error must be attributed to the account that directly invoked the contract (`predecessor_account_id`), not the original signer of a possibly multi-hop transaction.
5. Confirm the divergence by comparing `env::signer_account_id()` and `env::predecessor_account_id()` values captured at lines 106-107 versus the check at line 121. [9](#0-8) 

**Note on completeness**: I was unable to fully trace, within the available tooling, whether NEAR's `DelegateAction`/meta-transaction receipt construction actually produces a case where `predecessor_account_id != signer_account_id` at the exact point `rlp_execute` executes (i.e., confirming a concrete divergent scenario end-to-end through `action_delegate` in `runtime/runtime/src/actions.rs`, which I could not locate/read completely due to tool-call limits). This is the piece needed to fully prove the exploitability path; a Devin agent with full repository access should verify `action_delegate`'s receipt construction (`signer_id`/`predecessor_id` fields) to confirm whether a genuine mismatch is reachable through supported call patterns (e.g., meta-transactions or contract-to-contract relaying) before treating this as conclusively exploitable versus a defense-in-depth/code-smell issue.

pub fn signer_account_id(ctx: &mut Ctx, _memory: &mut [u8], register_id: u64) -> Result<()> {
    ctx.result_state.gas_counter.pay_base(base)?;

    if ctx.context.is_view() {
        return Err(
            HostError::ProhibitedInView { method_name: "signer_account_id".to_string() }.into()
        );
    }
    ctx.registers.set(
        &mut ctx.result_state.gas_counter,
        &ctx.config.limit_config,
        register_id,
        ctx.context.signer_account_id.as_bytes(),
    )
}
