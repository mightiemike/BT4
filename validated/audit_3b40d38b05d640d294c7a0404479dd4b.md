## Title
Permanent Denial-of-Service on account deployment via deterministic contract-address squatting - (File: `crates/blockifier/src/execution/execution_utils.rs`)

## Summary
`DeployAccount` transactions and the `deploy` syscall compute the target contract address deterministically via `calculate_contract_address(salt, class_hash, constructor_calldata, deployer_address)` [1](#0-0) . For `DeployAccount` transactions the `deployer_address` is hard-coded to zero [2](#0-1) , and the `deploy` syscall lets any already-deployed contract request the same zero-deployer computation via `deploy_from_zero: true` [3](#0-2) . Address "availability" is validated only by checking that the current class hash at that address is zero, exactly analogous to the reported bug's `balanceOf(pair) == 0` check with no origin/ownership validation [4](#0-3) .

## Finding Description
The same class of vulnerability described in the external report — a permissionless actor pre-empting a resource whose identifying parameters are publicly knowable, using a naive "is it empty" check instead of an origin check — is reachable in the sequencer through account/contract address squatting:

1. A user intending to deploy an account precomputes their future address from `(salt, class_hash, constructor_calldata, deployer_address=0)`. This address is, by design, publicly known ahead of time (users are told to fund this address before submitting the `DeployAccount` transaction), and/or becomes visible once the `DeployAccount` transaction enters the mempool.
2. Any attacker who already controls a deployed contract can call the `deploy` syscall with `deploy_from_zero = true` and the *same* `salt`, `class_hash`, and `constructor_calldata`. The syscall computes `deployer_address_for_calculation = ContractAddress::default()` — identical to the victim's target address — and deploys an arbitrary class there [5](#0-4) .
3. This syscall is permitted in normal execution; it is only rejected during the `Validate` execution phase [6](#0-5) , so any ordinary invoke transaction can trigger it.
4. `execute_deployment` only checks whether the current class hash at the target address is `ClassHash::default()`; it never verifies that the address was "reserved" for or expected to belong to the victim's account. If the attacker's write lands first, the check fails and `StateError::UnavailableContractAddress` is returned [4](#0-3) .
5. When the legitimate `DeployAccount` transaction is later executed, it reaches the identical address-availability check and reverts with the same `UnavailableContractAddress` error, as confirmed by the existing negative-flow test for "deploy to an existing address" [7](#0-6) .

Because the address is a pure function of `(salt, class_hash, constructor_calldata)` with a fixed zero deployer, the victim cannot "retry" at the same address — the account can never be deployed there. This is the same root cause pattern as the reported issue: public pre-image of a deterministic resource identifier + unrestricted third-party ability to create/occupy that resource + a validation that checks "is it untouched" rather than "did the legitimate party create it."

## Impact Explanation
Any single unprivileged contract call (an ordinary invoke transaction executing the `deploy` syscall) can permanently deny deployment of a specific, chosen account address. Since users are commonly instructed to send funds to their precomputed account address *before* submitting the `DeployAccount` transaction (to pay for the deployment fee), an attacker can:
- Grief a targeted user by permanently blocking their account from ever being deployed at the expected address once its parameters are known (via mempool observation or public key disclosure), and
- Potentially capture funds sent to that pre-funded address by deploying a contract of the attacker's choosing (with a constructor the attacker controls) at that exact address, since the attacker — not the intended owner — decides what code and state end up there.

This constitutes both permanent freezing/loss of funds and denial of service for legitimate account creation, satisfying the "concrete loss or permanent freezing of funds" and "network unable to confirm [that] transaction" criteria.

## Likelihood Explanation
The attack requires only: (1) an already-deployed attacker-controlled contract capable of invoking the `deploy` syscall, and (2) knowledge of the victim's `(salt, class_hash, constructor_calldata)`. These parameters are frequently public by protocol design (precomputed addresses are shared to allow pre-funding) or become visible in the mempool before inclusion — mirroring the exact information-leakage vector in the original report. No special privileges, race conditions beyond simple transaction ordering/fee bidding, or protocol bugs elsewhere are needed.

## Recommendation
When validating deploy availability, do not rely solely on "class hash is zero" as a proxy for "this address is free for the intended deployer." Consider:
- Restricting `deploy_from_zero` (or the entire `deploy` syscall with a zero-equivalent deployer) so that an arbitrary caller cannot mimic the reserved `DeployAccount` address space, or
- Binding the reserved address space for `DeployAccount` transactions to a namespace that ordinary `deploy` syscalls (with `deploy_from_zero=true`) cannot collide into, e.g. by incorporating a distinguishing domain separator/prefix specific to `DeployAccount` transactions into the address hash so that syscall-based deployments can never target the same address space.

## Proof of Concept
1. Compute `victim_address = calculate_contract_address(salt, class_hash, constructor_calldata, ContractAddress::default())` — the same formula used for `DeployAccount` [8](#0-7) .
2. From any deployed attacker contract, invoke the `deploy` syscall with `class_hash`, `contract_address_salt = salt`, `constructor_calldata = constructor_calldata`, `deploy_from_zero = true`. This lands at the identical `victim_address` and succeeds provided the class hash there is still `ClassHash::default()` [3](#0-2) .
3. Submit (or wait for) the victim's `DeployAccount` transaction with the matching `salt`/`class_hash`/`constructor_calldata`.
4. Observe it revert with `TransactionExecutionError::ContractConstructorExecutionFailed(... StateError::UnavailableContractAddress ...)`, exactly as reproduced in the existing test `test_fail_deploy_account_to_an_existing_address`-style flow [7](#0-6) . The victim's account can never be deployed at that address again.

pub fn calculate_contract_address(
    salt: ContractAddressSalt,
    class_hash: ClassHash,
    constructor_calldata: &Calldata,
    deployer_address: ContractAddress,
) -> Result<ContractAddress, StarknetApiError> {
    let constructor_calldata_hash = Pedersen::hash_array(&constructor_calldata.0);
    let contract_address_prefix = format!("0x{}", hex::encode(CONTRACT_ADDRESS_PREFIX));
    let address = Pedersen::hash_array(&[
        Felt::from_hex(contract_address_prefix.as_str()).map_err(|_| {
            StarknetApiError::OutOfRange { string: contract_address_prefix.clone() }
        })?,
        *deployer_address.0.key(),
        salt.0,
        class_hash.0,
        constructor_calldata_hash,
    ]);
    let (_, address) = address.div_rem(&L2_ADDRESS_UPPER_BOUND);

    ContractAddress::try_from(address)
}

    /// Calculates the contract address for the contract deployed by a deploy account transaction.
    /// For more details see:
    /// <https://docs.starknet.io/architecture-and-concepts/smart-contracts/contract-address/>
    fn calculate_contract_address(&self) -> StarknetApiResult<ContractAddress> {
        // When the contract is deployed via a deploy-account transaction, the deployer address is
        // zero.
        const DEPLOYER_ADDRESS: ContractAddress = ContractAddress(PatriciaKey::ZERO);
        calculate_contract_address(
            self.contract_address_salt(),
            self.class_hash(),
            self.constructor_calldata(),
            DEPLOYER_ADDRESS,
        )
    }
}
