### Title
`WithdrawFromGasKey` nested in a `Delegate` action drains a gas key that the SPICE pending-transaction queue still counts as funded — ([File: runtime/runtime/src/action_validation.rs])

### Summary
The reported HopeLend incident is a contract-logic bug where an attacker/frontrunner extracted value that legitimate accounting did not expect, and the extracted value was then used to bribe a block producer/validator to guarantee inclusion. The closest reachable analog in nearcore is a gas-accounting/admission-control gap: a `WithdrawFromGasKey` action nested inside a `Delegate` action drains a gas key's balance in a way that the SPICE `PendingTransactionQueue` admission logic does not observe, because that queue only inspects the *outer* transaction's top-level actions to compute gas-key balance commitments. A relayer (an unprivileged transaction signer) can exploit this to admit multiple transactions against a gas key balance that has already been withdrawn, similar in spirit to the HopeLend flaw where state used for a critical check was stale/bypassable, enabling a value-extraction opportunity a chunk/block producer could subsequently be bribed to include.

### Finding Description
`Action::WithdrawFromGasKey`, when executed, subtracts from a gas key's balance and credits the owning account (`action_withdraw_from_gas_key`, `runtime/runtime/src/access_keys.rs:290-334`). Normally the SPICE pending-transaction queue tracks `pending_gas_key_costs` per gas key including "WithdrawFromGasKey amounts" (comment at `chain/client/src/pending_transaction_queue.rs:102`) so admission control can reject transactions that would overspend an uncertified gas key.

However, this tracking is keyed off the *outer* transaction's actions. A `WithdrawFromGasKey` action can also be nested inside a `Delegate`/`DelegateV2` action's inner action list (`DelegateAction.actions: Vec<NonDelegateAction>`, see `docs/RuntimeSpec/Actions.md:340-361`), and until `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` is enabled, `validate_delegate_action` (`runtime/runtime/src/action_validation.rs:222-248`) does **not** reject such nested actions:

```
if mode == ValidateReceiptMode::NewReceipt
    && ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(current_protocol_version)
    && actions.iter().any(|action| matches!(action, Action::WithdrawFromGasKey(_)))
{
    return Err(ActionsValidationError::WithdrawFromGasKeyNotAllowedInDelegate);
}
```

The in-code comment on the feature itself confirms the root cause explicitly (`core/primitives-core/src/version.rs:461-465`):
> "Reject a `WithdrawFromGasKey` action nested inside a delegate action. The SPICE pending transaction queue scans only the top level actions of a transaction for `WithdrawFromGasKey`, so a nested one drains a gas key that the queue still counts as funded."

The behavior is confirmed live in `test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs:112-137`: pre-upgrade, a `Delegate` action wrapping `WithdrawFromGasKey` executes successfully and drains the gas key, exactly the hole the later protocol feature closes.

Per `core/primitives-core/src/version.rs:622`, `RejectWithdrawFromGasKeyInDelegate` activates only at protocol version **87**, while `EnforcePerReceiptStorageProofLimit` (**86**) is the stable, currently-active protocol version in this tree per `protocol-model/spec/runtime-execution.md:3` ("Protocol version: 86 (stable)"). This means on the live/stable protocol version in this codebase, the fix is **not yet active**, and the vulnerable admission gap is exploitable.

### Impact Explanation
This affects the SPICE architecture's pending-transaction queue, which exists to bound how much of an account's/gas-key's balance can be pre-committed across uncertified chunks before execution/certification catches up (the whole point of `P_MAX` and `pending_gas_key_costs` in `chain/client/src/pending_transaction_queue.rs`). If a gas key's committed balance can be silently drained via a nested `WithdrawFromGasKey` inside a `Delegate` action without the queue accounting for it, subsequent transactions that rely on the (now-stale) "funded" balance can be admitted and reach execution, later failing at runtime with `NotEnoughGasKeyBalance`/insufficient-balance errors, or in constructions where multiple such transactions are chained across blocks before certification, this undermines the admission invariant that the queue is designed to guarantee (no more work admitted than the account/gas key can actually pay for). This is a chunk/transaction-admission integrity issue reachable purely from a signed transaction submitted by any account holding (or delegating on behalf of) a gas key — no validator or operator privilege required.

### Likelihood Explanation
High reachability: the only requirements are (1) an account with a gas key (a normal, permissionless `AddKey` with `AccessKey::gas_key_full_access`), and (2) submitting a `Delegate` action whose inner `actions` list contains `WithdrawFromGasKey`, signed with a plain access key (gas keys themselves cannot sign V1 delegate actions, but the outer/relayer flow shown in the test file works with a normal signer). The existing test `test_reject_delegated_gas_key_withdraw_protocol_upgrade` proves the exploit works exactly as described pre-upgrade. Because the fixing feature (`RejectWithdrawFromGasKeyInDelegate`) is gated to protocol version 87 while the tree's stable protocol version is 86, the vulnerable code path is what ships/runs today in this codebase.

### Recommendation
Backport/accelerate activation of `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` to the currently active stable protocol version (or otherwise make `validate_delegate_action`'s nested-action check for `WithdrawFromGasKey` unconditional, independent of protocol-version gating) so that the admission-time gap between the pending-transaction queue's balance tracking and actual on-chain execution cannot be exploited while the fix sits in a not-yet-active future protocol version. Additionally, ensure `PendingTransactionQueue` recursively inspects nested/delegate actions (not just top-level ones) for any action type capable of mutating a gas key's balance, rather than relying solely on rejecting the nested action at validation time, to defend in depth against similar future action nestings.

### Proof of Concept
Use the existing exploit reproduction already present in the codebase, which is a faithful PoC for the pre-fix behavior:
- `test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs:26-54` (`delegated_withdraw_tx`) builds a `Delegate` action wrapping `WithdrawFromGasKey` targeting the sender's own gas key, signed by the sender's plain key, submitted by an unrelated `relayer`.
- `test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs:112-137` shows that on the pre-fix protocol version, this transaction is admitted and executes successfully, and the gas key balance is drained by `WITHDRAW_AMOUNT`, confirming the runtime honors the nested withdrawal while (per the code comments) the SPICE pending-transaction queue never accounted for it at admission time. pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
