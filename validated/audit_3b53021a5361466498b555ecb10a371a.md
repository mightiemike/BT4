### Title
CREATE2 Contract Deployment Permanently Fails if Target Address Is Pre-occupied (DoS via Address Squatting) - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
Analogous to the Uniswap `createPair` issue (which reverts if a trading pair address is already taken by an attacker), java-tron's TVM `CREATE`/`CREATE2` contract-creation logic in `createContractImpl` unconditionally reverts if the computed target address already has contract code/nonce, and there is no fallback path — meaning an attacker who front-runs a deterministic `CREATE2` deployment can permanently block the legitimate deployer from ever deploying to that address.

### Finding Description
`Program.createContractImpl` computes `newAddress` deterministically (via `TransactionUtil.generateContractAddress` for `CREATE`, and via a salt+codehash scheme for `CREATE2`, exposed through `OperationActions`/`WalletUtil`). It then checks whether an account/contract already exists there: [1](#0-0) 

If `VMConfig.allowTvmConstantinople()` is active, `contractAlreadyExists` is derived via `isContractExist(existingAccount, getContractState())`. Regardless of the exact predicate, once `contractAlreadyExists` is `true`, the code path never creates the new contract and instead forces a hard failure: [2](#0-1) 

This causes `stackPushZero()` and the internal transaction to be rejected: [3](#0-2) 

Because `CREATE2` addresses are deterministic (`keccak256(0xff, sender, salt, codehash)`), any contract or dApp relying on deterministic deployment (e.g., a factory that computes a pool/pair address in advance, mirroring the Uniswap/Radiant `initializePool` pattern) is exposed to the exact same front-running class of bug described in the external report: an attacker observing an anonymous, unconfirmed transaction in the mempool (or simply predicting the salt/bytecode used by a well-known factory) can broadcast their own transaction that creates *any* account or contract at that computed address first (e.g., via a plain TRX transfer that creates an account, or their own `CREATE2` call with attacker-controlled salt targeting the same resulting address). Once occupied, `contractAlreadyExists` becomes permanently `true`, and every subsequent legitimate deployment attempt to that address will always fail with `BytecodeExecutionException` — there is no "deploy if not exists" fallback, and no way to recover the address without changing the salt/bytecode (which may not be an option for protocols relying on cross-chain address parity).

### Impact Explanation
This is a Denial-of-Service vector against protocols that depend on deterministic contract addresses for cross-chain consistency or two-phase factory patterns (analogous to Uniswap/Balancer pool factories). A malicious actor can permanently block a specific, predictable contract deployment on java-tron by squatting the target address first, forcing the protocol to redeploy with different parameters/salt (breaking any assumptions of deterministic addressing across chains) or migrate their entire deployment strategy. This does not directly cause fund loss or consensus divergence, but it is a legitimate availability/deployment-integrity issue reachable by any anonymous account able to broadcast a transaction, matching the "DoS via ... protocol implementation" acceptance criteria.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to know (or predict) the salt/bytecode/sender combination that a target deployer intends to use before the deployer's transaction confirms — exactly the same precondition as the original Uniswap report ("during deployment on a new chain," or when the deploy transaction is visible in the mempool prior to confirmation). No special privileges are required; only the ability to submit an ordinary TVM transaction with a computed `CREATE`/`CREATE2` call or account-creating transfer.

### Recommendation
Where a `CREATE2`-based deployment is expected to be idempotent or resistant to address squatting, consider allowing redeployment to detect and gracefully handle a pre-existing but "empty" address, or emit/return the existing contract rather than reverting when the codehash/state indicates the address was never meaningfully used (mirroring EIP-684 semantics more strictly, and clarifying `isContractExist`'s exact definition). At minimum, this should be documented as a known limitation so integrators building deterministic factories on java-tron (in the spirit of Uniswap/Balancer-style pool helpers) are aware that address squatting can permanently block their deployment path.

### Proof of Concept
Conceptual PoC (cannot be executed without live index access to `isContractExist`/`WalletUtil` full source, which the available index does not fully expose):
1. Victim protocol computes a deterministic `CREATE2` address `A` for a factory contract using `sender`, `salt`, and `codehash` of their pool/router bytecode, and broadcasts a deployment transaction referencing `A`.
2. Attacker observes the pending transaction (or independently predicts `sender`/`salt`/`codehash`, e.g. from known deployer conventions) and broadcasts a competing transaction that creates any account/contract at address `A` first (e.g. a trivial TRX transfer to `A`, or their own `CREATE2` call producing the same address).
3. When the victim's original transaction executes, `Program.createContractImpl` finds `existingAccount != null` / `contractAlreadyExists == true` and takes the failure branch shown at `Program.java:907-911`, permanently reverting the intended deployment for that specific address.

Due to index size limits, the full implementation of `isContractExist` and the CREATE2 salt/address derivation in `WalletUtil.java` / `OperationActions.java` was not retrievable in this session; a Devin session with full repository access would be needed to confirm the exact conditions under which `contractAlreadyExists` evaluates `true` for a "squatted but never actually deployed" address.
