### Title
Exception fully-qualified class names leaked to unauthenticated API clients via error messages - (File: framework/src/main/java/org/tron/core/services/RpcApiService.java, framework/src/main/java/org/tron/core/Wallet.java, framework/src/main/java/org/tron/core/services/http/TriggerSmartContractServlet.java)

### Summary
Multiple public-facing gRPC and HTTP API handlers in java-tron catch generic `Exception`/`RuntimeException` and echo `e.getClass() + " : " + e.getMessage()` (or `e.getMessage()` alone from library exceptions) directly back to the caller in the response payload, exposing internal implementation details (fully-qualified Java class names, underlying library exception types, and raw exception text) to any unauthenticated network caller.

### Finding Description
Several handlers in the public wallet/API surface catch broad exception types and place the raw exception class and message into the response returned to the client: [1](#0-0) [2](#0-1) [3](#0-2) 

These catch blocks build the response with `ByteString.copyFromUtf8(e.getClass() + " : " + e.getMessage())` or similar, which is returned as the `Return.message` field / JSON `message` field to the requester — this is functionally the same bug class described in the report (leaking library/internal diagnostic info in a user-facing error, e.g. `viem@2.37.12`-style disclosure), except here it discloses Java package/class names and internal exception types (e.g., `java.lang.NullPointerException`, `com.google.protobuf.InvalidProtocolBufferException`, or java-tron internal exception classes) rather than a JS library version string. This is reachable by any unauthenticated caller of `triggerConstantContract`/`triggerContract` gRPC calls, `getTransactionApprovedList`, and the HTTP `wallet/triggersmartcontract` endpoint — all standard, unprivileged public API surfaces.

Additional low-level HTTP servlets return `e.getMessage()` directly to the writer without any sanitization at all: [4](#0-3) [5](#0-4) 

### Impact Explanation
Fully-qualified exception class names and raw library exception messages reveal internal implementation choices (which parsing/serialization libraries are in use, internal exception hierarchy, stack-derived messages) to any unauthenticated remote caller. This is reconnaissance-grade information disclosure: it can help an attacker fingerprint the exact code path/library handling a given input, correlate with known CVEs in dependencies (e.g., protobuf, guava, bouncycastle versions bundled), and refine targeted exploitation attempts against the node's public gRPC/HTTP wallet API. It does not by itself grant funds movement, consensus divergence, or accounting corruption, so the impact is confined to information disclosure/reconnaissance rather than a direct fund-loss or consensus-halting vulnerability.

### Likelihood Explanation
High likelihood of triggering: these code paths are reached by unauthenticated, standard API calls (`triggerConstantContract`, `triggerContract`, `getTransactionApprovedList`, HTTP `triggersmartcontract`) whenever malformed input causes any runtime exception (e.g., malformed permission data, VM runtime exceptions, protobuf parse errors). No special privilege is required — any external client interacting with a full node's open JSON-RPC/gRPC/HTTP wallet interface can elicit these responses simply by sending invalid transaction data or unexpected parameters.

### Recommendation
Replace `e.getClass() + " : " + e.getMessage()` and raw `e.getMessage()` echoing in all public-facing HTTP/gRPC handlers (`RpcApiService.callContract`, `Wallet.getTransactionApprovedList`, `TriggerSmartContractServlet.doPost`, and the `solidity` servlets that print `e.getMessage()` directly) with generic, category-level error messages (e.g., "Invalid transaction", "Internal error processing request") mapped from a fixed enum of user-safe error codes. Log the full exception (class, message, stack trace) server-side only via `logger.warn`/`logger.error`, and never propagate `Throwable.getClass()` or raw library exception text into the `Return.message`/JSON response body.

### Proof of Concept
1. Send a malformed `TriggerSmartContract` request to the HTTP endpoint `/wallet/triggersmartcontract` (or the gRPC `TriggerContract`/`TriggerConstantContract` RPC) with input that causes an unexpected `RuntimeException` deep in VM execution (e.g., malformed call data causing an internal decoding exception).
2. Observe the JSON/gRPC response `message` field contains text such as `"org.tron.core.vm.<SomeInternalException> : <raw message>"` per the code at [6](#0-5)  and [1](#0-0) , confirming that internal Java class names and implementation details are disclosed to an unauthenticated caller.
