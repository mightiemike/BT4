### Title
Deposits that fail inside `process_sys_txs` due to stale BitcoinLightClient state are unconditionally evicted from `DepositDataMempool` with no re-queue - ([File: crates/sequencer/src/runner.rs])

### Summary
`produce_l2_block_inner` fetches a batch of deposits from `DepositDataMempool::fetch_deposits` and unconditionally calls `remove_deposits(&deposit_data)` on that entire batch after block production, regardless of whether each individual deposit's system transaction actually succeeded inside `process_sys_txs`. Because `process_sys_txs` silently reverts and skips (`continue`) any deposit whose `Bridge.deposit` call fails with `EvmSystemTransactionNotSuccessful` (e.g., because the L1 block its Merkle proof references has not yet been recorded via `SystemEvent::BitcoinLightClientSetBlockInfo` for that l2_height), a genuinely valid but temporarily-unprovable deposit is permanently dropped from the mempool with no automatic re-submission path.

### Finding Description
The binding that must hold is: **{L1 blocks recorded in BitcoinLightClient via `SetBlockInfo` events included in `system_events` for l2_height N} ⊇ {L1 block referenced by deposit B's Merkle inclusion proof}**. This binding is checked only inside the EVM/`Bridge.deposit` call executed by `process_sys_txs`; it is never re-checked or reflected back into mempool bookkeeping.

Code path:
- `crates/sequencer/src/runner.rs:517-520` — `fetch_deposits(limit)` returns (without removing) up to `limit` deposits from the mempool. [1](#0-0) 
- `system_events` is built from `da_blocks` (`SetBlockInfo` events) first, then `populate_deposit_system_events(deposit_data)` appends the deposit events, and both are handed to `process_sys_txs`. [2](#0-1) 
- Inside `process_sys_txs`, each system event is applied via a checkpoint/revert loop. If applying a `BridgeDeposit` event fails with `EvmSystemTransactionNotSuccessful` (which is exactly what happens when `Bridge.deposit`'s Merkle-proof-against-`BitcoinLightClient` check fails because the referenced L1 block's `SetBlockInfo` was not included in this l2_height's `system_events`), the working set is reverted and the loop `continue`s to the next event — the deposit is simply skipped, not queued for retry. [3](#0-2) 
- Back in `produce_l2_block_inner`, after the block is finalized, the code removes **every** deposit in the originally-fetched `deposit_data` batch from the mempool — with no filtering based on which deposits actually succeeded inside `process_sys_txs`: [4](#0-3) 
- `remove_deposits` matches by `calc_tx_id` computed from the deposit's `moveTx` fields and deletes the entry from both `accepted_deposit_txs` and `pending_deposits`, with no distinction for success/failure and no re-insertion logic anywhere in this file or in `DepositDataMempool`. [5](#0-4) 

No guard exists that reconciles "did this specific deposit's system tx actually succeed" with "should this deposit be removed from the mempool." The two code paths (`process_sys_txs`'s per-event success/failure tracking and `produce_l2_block_inner`'s bulk `remove_deposits`) are disjoint — the former discards its per-event result information (`all_txs` only contains successfully applied txs, but `deposit_data` passed to `remove_deposits` is the original unfiltered fetch), so the binding is broken by construction, independent of the specific DA-lag trigger.

### Impact Explanation
A user who genuinely locks BTC and submits a valid deposit blob via `citrea_sendRawDepositTransaction` can have that deposit permanently evicted from the sequencer's mempool without cBTC ever being credited, if the deposit happens to be batched into an l2_height where the referenced L1 block's `SetBlockInfo` event is not yet present in `system_events` (a timing/ordering condition entirely outside the depositor's control, driven by da_blocks selection at block-production time versus mempool acceptance/simulation time). This is a permanent loss of bridged funds for the affected user — matching the "funds permanently frozen" Critical impact category. The condition is repeatable per-deposit and is not limited to double-spend races; any transient mismatch between `da_blocks` fed into a given l2_height and the L1 view when the deposit was mempool-accepted triggers the same eviction-without-retry behavior.

### Likelihood Explanation
No special privilege is required — any unprivileged party can call `citrea_sendRawDepositTransaction` with a deposit blob whose Merkle proof references an L1 block that has not yet been reflected in `BitcoinLightClient` state at the exact l2_height where the sequencer happens to batch it. This is a normal race condition inherent to the sequencer's two-stage flow (mempool-time validation vs. block-production-time `da_blocks` selection) and does not require hashrate, key compromise, or DA manipulation — only ordinary timing. Given that deposit batching runs continuously and mempool acceptance and block production are decoupled, this can occur under normal operation, not just via deliberate attacker timing.

### Recommendation
Track per-deposit success/failure results returned from `process_sys_txs` (e.g., return the set of `SystemEvent::BridgeDeposit` payloads that were actually applied successfully) and pass only that filtered subset to `DepositDataMempool::remove_deposits`, leaving failed/reverted deposits in the mempool for automatic retry in a later l2_height once the relevant `SetBlockInfo` event is available.

3. Assert the equality before: `deposit_mempool.pending_deposits` contains `calc_tx_id(B)`.
4. Assert inside `process_sys_txs` that applying `B`'s `BridgeDeposit` event returns `StateTransitionError::ModuleCallError(EvmSystemTransactionNotSuccessful)` and is skipped via the `continue` branch (lines 1678-1698).

6. Assert there is no subsequent re-queue of `B` in any later l2_height's system_events — confirming permanent loss.

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
