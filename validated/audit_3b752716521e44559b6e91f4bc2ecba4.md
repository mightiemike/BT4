## Finding: Unvalidated `to_address` in `send_message_to_l1` on L3 chains causes a sequencer panic

### Title
Unvalidated L1 message receiver on L3 chains causes a node panic during message finalization - (File: `crates/blockifier/src/execution/call_info.rs`)

### Summary
Similar to the SUI receiver-validation bug (where an unvalidated receiver address was only encoded, not checked, and later broke the withdrawal-building code), the `send_message_to_l1` syscall in this sequencer skips `EthAddress` range validation of the message `to_address` whenever the chain is configured as an L3, but a downstream code path unconditionally assumes the value is a valid `EthAddress` and panics (`.expect()`) if it is not.

### Finding Description
When a contract calls the `send_message_to_l1` syscall, the syscall handler only validates that `to_address` fits into an Ethereum address (160 bits) if the chain is *not* an L3: [1](#0-0) 

The same conditional skip exists in the deprecated (Cairo 0) syscall path: [2](#0-1) 

On an L3-configured chain, any felt value (up to ~252 bits) is accepted as `to_address` and stored unchecked in the `L1Address` wrapper as part of `MessageToL1`/`OrderedL2ToL1Message`. This is confirmed by the test suite, which explicitly asserts that execution succeeds for an out-of-`EthAddress`-range `to_address` when `is_l3` is true: [3](#0-2) 

However, when the ordered L2-to-L1 message is later converted into the API-level `MessageToL1` (used to build `CallInfo`/`TransactionExecutionInfo`, receipts, and downstream message-segment data), the conversion from `L1Address` to `EthAddress` is performed with an unconditional `.expect()`, with no is_l3 branch to skip or tolerate an invalid value: [4](#0-3) 

Because the initial validation was intentionally bypassed for L3 chains, but this later conversion has no equivalent bypass, a value that was accepted at syscall time can still fail the `try_into::<EthAddress>()` call and panic the process that is building the call info (part of block execution/finalization on the sequencer).

### Impact Explanation
Any unprivileged account can deploy a trivial contract (or use `TestContract`) and issue a single `send_message_to_l1_syscall` (or the deprecated equivalent) with a `to_address` argument larger than `2^160 - 1`, on a chain running with `ChainInfo::is_l3 = true`. The transaction's syscall succeeds (bypassing validation), but the subsequent processing that materializes the ordered L2-to-L1 message (`to_ordered_tuple`) panics via `.expect("Failed to convert L1Address to EthAddress")`. A panic during block building/execution on the sequencer is a liveness-critical bug: it can crash or halt the process handling the transaction, preventing the network from confirming new transactions/blocks — directly analogous to the "withdrawals getting stuck" impact in the SUI report, but manifesting as a sequencer crash rather than a stuck retry loop.

### Likelihood Explanation
The trigger requires only a single transaction from any unprivileged sender/contract deployer calling a permissionless syscall with an out-of-range felt argument — no special privileges, no chain-specific preconditions beyond the target chain being configured with `is_l3 = true` (a supported, documented configuration in this codebase, exercised by dedicated tests). This is a low-effort, deterministic, single-transaction attack path.

### Recommendation
Ensure `to_address` validation and later consumption are consistent: either validate/bound `to_address` uniformly regardless of `is_l3` (e.g., still require it fits some canonical L1-address-like domain, or use a non-panicking, chain-aware type conversion in `to_ordered_tuple` and elsewhere), or make the `L1Address -> EthAddress` conversion fallible (`Result`) and propagate the error instead of using `.expect()`, matching the intent of skipping strict `EthAddress` validation on L3s without introducing a panic path.

### Proof of Concept
1. Configure `ChainInfo::is_l3 = true` (as done in `test_send_message_to_l1_invalid_address`, `crates/blockifier/src/execution/syscalls/syscall_tests/send_message_to_l1.rs:91-131`).
2. From any account, invoke a contract's `send_message_to_l1_syscall` (e.g., `test_send_message_to_l1` in the test feature contract) with `to_address = 0x10000000000000000000000000000000000000000` (greater than `2^160`).
3. Execution succeeds per current test assertions (`assert!(result.is_ok(), ...)` when `is_l3`).
4. When the resulting `OrderedL2ToL1Message` is later converted via `to_ordered_tuple` (`crates/blockifier/src/execution/call_info.rs:100-116`) to build the transaction's message receipt/output, the `.expect("Failed to convert L1Address to EthAddress")` call panics because the felt does not fit in 160 bits, crashing the code path responsible for building the block/receipt.

    pub fn send_message_to_l1(&mut self, message: MessageToL1) -> SyscallResult<()> {
        if !self.context.tx_context.block_context.chain_info.is_l3 {
            EthAddress::try_from(message.to_address)?;
        }
        let ordered_message_to_l1 =
            OrderedL2ToL1Message { order: self.context.n_sent_messages_to_l1, message };
        self.l2_to_l1_messages.push(ordered_message_to_l1);
        self.context.n_sent_messages_to_l1 += 1;

        Ok(())
    }

    #[case] runnable_version: RunnableCairo1,
    #[values(true, false)] is_l3: bool,

    let test_contract = FeatureContract::TestContract(CairoVersion::Cairo1(runnable_version));
    let mut chain_info = ChainInfo::create_for_testing();
    chain_info.is_l3 = is_l3;
    let mut state = test_state(&chain_info, BALANCE, &[(test_contract, 1)]);

    let invalid_to_address = felt!("0x10000000000000000000000000000000000000000");
    let payload = vec![felt!(2019_u16), felt!(2020_u16)];
    let calldata = Calldata(
        concat(vec![
            vec![
                invalid_to_address,
                felt!(u64::try_from(payload.len()).expect("Failed to convert usize to u64.")),
            ],
            payload.clone(),
        ])
        .into(),
    );
    let entry_point_call = CallEntryPoint {
        entry_point_selector: selector_from_name("test_send_message_to_l1"),
        calldata,
        ..trivial_external_entry_point_new(test_contract)
    };
    let block_context = BlockContext::create_for_testing().with_chain_info(chain_info.clone());
    let result = entry_point_call.execute_directly_given_block_context(&mut state, block_context);

    if is_l3 {
        assert!(result.is_ok(), "Expected execution to succeed on L3 chain");

        assert!(result.is_err(), "Expected execution to fail with invalid address");
