Based on the investigation, I found a genuine structural analog to the reported "division by an unchecked total-allocation-style denominator" bug class in java-tron's energy/bandwidth accounting code — but with an important caveat about exploitability that I'll flag explicitly.

### Title
Unchecked zero-denominator division in legacy energy-limit calculation can throw/corrupt results during TVM energy metering - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit` (the legacy, pre-`supportUnfreezeDelay` path) divides by `totalEnergyWeight` while only guarding the zero/negative case when `dynamicPropertiesStore.allowNewReward()` is true; otherwise it falls through to an `assert` (a no-op unless the JVM is started with `-ea`, which is not the default for production nodes) and then performs the division regardless of whether `totalEnergyWeight` is actually zero. The identically-shaped V2 method (`calculateGlobalEnergyLimitV2`) and the analogous bandwidth method (`BandwidthProcessor.calculateGlobalNetLimit`) both have an explicit `if (totalEnergyWeight == 0) return 0;` guard, showing the missing check in the V1 path is an inconsistency rather than an intentional invariant.

### Finding Description [1](#0-0) 

The V1 path only returns 0 when `frozeBalance < TRX_PRECISION` for the *caller's* frozen balance; it never validates the network-wide `totalEnergyWeight` on the non-`allowNewReward` branch before dividing:
- If `hardenCalculation()` is enabled, division routes through `calculateGlobalLimitV1`, which internally uses `BigInteger` division — dividing by `BigInteger.ZERO` throws `ArithmeticException`.
- If hardening is disabled, the code does `(double) totalEnergyLimit / totalEnergyWeight`, which for a zero divisor produces `Infinity`/`NaN`, silently corrupting the resulting energy-limit value instead of reverting cleanly.

By contrast, the V2 counterpart used when `supportUnfreezeDelay()` is enabled explicitly guards this: [2](#0-1) 

The same asymmetry (guarded V2, unguarded/assert-only V1) exists in `BandwidthProcessor.calculateGlobalNetLimit` versus `calculateGlobalNetLimitV2`: [3](#0-2)  — here the V1 bandwidth path *does* check `totalNetWeight == 0`, making the energy path the outlier.

`RepositoryImpl.calculateGlobalEnergyLimit` (used inside TVM execution/precompiles) has the identical unguarded pattern: [4](#0-3) 

This function is invoked on every TVM energy consumption (`useEnergy`) for a smart-contract-triggering transaction: [5](#0-4) 

### Impact Explanation
`totalEnergyWeight` reflects the sum of all frozen-for-energy balances network-wide. In the intended steady state of mainnet it is non-zero, so this is not an easily attacker-triggerable condition today. However, if it were to reach zero on this legacy code path (e.g., an edge/degenerate network state, private/test chain, or a future migration bug that zeroes the aggregate before `allowNewReward` is set), any transaction that consumes energy would either throw an uncaught `ArithmeticException` (hardened math path) — causing that transaction/block processing to fail — or silently compute a corrupted (`Infinity`/`NaN`→cast) energy limit, which could let accounts bypass real energy limits (accounting corruption) rather than cleanly reverting. Because energy accounting underlies TVM contract execution universally, either outcome is systemic (block processing / DoS or resource-accounting corruption) rather than confined to a single actor.

### Likelihood Explanation
Low-to-moderate. This is not reachable purely by an unprivileged transaction under current mainnet configuration, since `totalEnergyWeight` is normally always positive once the network is bootstrapped (accounts freeze TRX for energy from genesis configuration). The condition would require the aggregate weight to actually be zero while still on the legacy (non-`supportUnfreezeDelay`) code path with `allowNewReward` disabled — a configuration state that is unlikely on a live, mature chain but is architecturally possible (e.g., private networks, fresh testnets before any freeze happens, or via a bug elsewhere that decrements the weight to zero). I could not verify from the indexed code whether any additional invariant elsewhere in the codebase makes `totalEnergyWeight == 0` truly unreachable on this exact combination of flags; this remains uncertain given index limitations on cross-referencing every genesis/config-init path.

### Recommendation
Add an explicit `totalEnergyWeight <= 0` (and analogous `totalNetWeight <= 0`) guard unconditionally — not only inside the `allowNewReward()` branch — before performing the division in `EnergyProcessor.calculateGlobalEnergyLimit` and `RepositoryImpl.calculateGlobalEnergyLimit`, returning 0 in that case, matching the pattern already used in `calculateGlobalEnergyLimitV2` and `BandwidthProcessor.calculateGlobalNetLimit`. Remove reliance on `assert` statements for production invariant enforcement since assertions are disabled by default.

### Proof of Concept
Not independently reproducible against the current indexed codebase/config without live node access to force `totalEnergyWeight` to 0 while `allowNewReward()` is false and `supportUnfreezeDelay()` is false. Conceptually: on such a chain state, call any smart contract consuming energy → `useEnergy` → `calculateGlobalEnergyLimit` → division by zero `totalEnergyWeight`, producing either an uncaught `ArithmeticException` (hardened) or `NaN`/`Infinity`-derived corrupted long (non-hardened).

    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
