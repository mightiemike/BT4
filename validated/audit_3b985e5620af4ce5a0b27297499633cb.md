### Title
Block/standby rewards for a Super Representative with zero effective votes are silently dropped and never distributed - (`chainbase/src/main/java/org/tron/core/store/DelegationStore.java`, `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
The DPoS voter-reward accounting in java-tron accumulates a witness's voter reward pool per maintenance cycle into a "Vi" accumulator (`rewardPerTokenStored`-analog) that is later used to compute each voter's share via delta-Vi. When a witness's vote count is `0` for a cycle, the accumulator update is skipped entirely instead of being deferred/carried forward with the pending reward, so any reward earned by that witness in that cycle (block reward net of brokerage) is permanently lost and can never be claimed by any voter — the exact same root cause described in the referenced Wenwin finding, where `rewardPerTokenStored` is not updated when `totalSupply == 0`.

### Finding Description
`DelegationStore.accumulateWitnessVi` is the java-tron analog of `Staking.rewardPerToken()`: [1](#0-0)

If `voteCount == 0` for a cycle, the branch simply forwards the previous `Vi` value and drops the `reward` value entirely — it is never merged into a later cycle's Vi computation. This is invoked from `MaintenanceManager.doMaintenance()`: [2](#0-1) 

The reward pool for that cycle/witness is populated earlier by `MortgageService.payReward` for every block reward and transaction-fee reward paid to a witness: [3](#0-2) 

```java
private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
}
```

`value` (the voter-share portion of the reward, after brokerage) is stored via `delegationStore.addReward(cycle, witnessAddress, value)` regardless of the witness's current vote count. It is only ever redeemed through the Vi delta at withdrawal time, in both the new and old reward algorithms:

- New algorithm: `VoteRewardUtil.computeReward` / `MortgageService.computeReward` use `deltaVi = endVi - beginVi`; if `Vi` was never bumped for the zero-vote cycle, `deltaVi.signum() <= 0` and the contribution is skipped: [4](#0-3) 
- Old algorithm: `computeReward(cycle, votes)` explicitly `continue`s when `totalVote == 0`: [5](#0-4) 

In both algorithms, once a cycle's witness reward is recorded with `voteCount == 0`, that specific reward amount can never be attributed to any voter — it is orphaned inside the accounting store forever with no withdrawal path, no burn, and no redistribution mechanism, mirroring exactly the "Locked tokens" issue from the report (the analog of `Staking.rewardPerTokenStored` never being bumped when `totalSupply == 0`).

A witness can have `voteCount == 0` for a cycle while still being a member of the previous `activeWitnesses`/standby list that produces blocks and earns rewards during that cycle: witness vote counts change continuously (any account can withdraw/clear all its votes at any time, e.g. via `VoteWitnessActuator`/TVM `vote` clearing as exercised in `VoteTest.clearVote`), but `activeWitnesses`/standby membership and vote-count snapshots used for reward distribution are only refreshed once per maintenance cycle (`doMaintenance`, default every 6 hours). If all voters unvote from a witness mid-cycle, that witness remains in the active/standby set (and keeps producing blocks / receiving standby pay) until the next maintenance, at which point `accumulateWitnessVi` is invoked with `voteCount == 0` and the reward is dropped.

### Impact Explanation
This causes silent, permanent loss of TRX/TRX-equivalent value that was intended for voter rewards: the amount recorded via `delegationStore.addReward` is bookkeeping for a future payout that will never occur, effectively vanishing from the redeemable reward pool with no recovery path (asset/accounting corruption). Although the loss for any single cycle/witness is bounded (one cycle's share of block/tx-fee/standby reward), it happens deterministically whenever the described vote-to-zero condition occurs, and there is no mitigation, withdrawal, or redistribution mechanism for it, matching the Medium-severity classification given to the original Wenwin finding.

### Likelihood Explanation
This requires no privileged access — any set of voters withdrawing/clearing their votes from a witness (a normal `VoteWitnessContract`/TVM `vote` operation) can trigger the zero-vote condition for that witness in the window between two maintenance cycles, while the witness remains part of the active/standby set from the prior snapshot and continues to accrue rewards. This is a realistic operational scenario (e.g., low-vote SRs, testnets, or vote churn near maintenance boundaries) rather than a purely theoretical corner case.

### Recommendation
When `voteCount == 0` for a cycle in `DelegationStore.accumulateWitnessVi` (and the analogous old-algorithm `computeReward` skip in `MortgageService`), do not drop the recorded `reward`. Instead, either (a) carry the un-distributed reward forward and add it to the next cycle's reward for that witness before computing delta-Vi so it is eventually distributed to whichever voters exist then, or (b) redirect it to a defined sink (e.g., burn to blackhole or the community/treasury account) instead of leaving it permanently orphaned in `delegationStore`.

### Proof of Concept
1. Witness `W` is part of the active/standby set at the start of cycle `N` and produces blocks, accumulating block/tx-fee rewards via `MortgageService.payReward` → `delegationStore.addReward(N, W, value)`.
2. During cycle `N`, all voters call `VoteWitnessContract`/TVM `vote` to clear their votes for `W`, driving `W.getVoteCount()` to `0`, but `W` remains in the active/standby list until the next maintenance (`doMaintenance` runs only every `maintenanceTimeInterval`, default 6 hours).
3. At the next maintenance, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, W, 0)` since `witness.getVoteCount()` is now `0`.
4. `accumulateWitnessVi` takes the `voteCount == 0` branch, forwarding `preVi` unchanged and discarding the `reward` retrieved via `getReward(N, W)`.
5. Any voter who previously voted for `W` (or new voters) queries/withdraws their reward via `MortgageService.queryReward`/`withdrawReward`; because `Vi` was never bumped for cycle `N`, `deltaVi` for that span is `0` for `W`, so the reward accumulated in step 1 is never paid to anyone and remains permanently unclaimable in `delegationStore`.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
