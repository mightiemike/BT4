Based on my investigation, `RewardCalculator::calculate_reward` contains a bug analogous to the reported `lpFeesTotal` issue: when `num_validators == 0`, the protocol treasury's reward is inserted into the returned `validator_reward` map, but the function returns `Balance::ZERO` as the minted amount instead of `epoch_protocol_treasury`.

### Title
Protocol treasury credited without matching minted-supply accounting when an epoch has zero validators - (File: `chain/epoch-manager/src/reward_calculator.rs`)

### Summary
`RewardCalculator::calculate_reward` always computes and inserts a nonzero `epoch_protocol_treasury` reward into the `res` (validator reward) map before checking `num_validators`. When `num_validators == 0`, it returns `(res, Balance::ZERO)` — the treasury reward stays in `res` (and will later be credited to the treasury account's balance), but the second return value, which becomes `minted_amount` and is added to `total_supply`, is forced to zero instead of `epoch_protocol_treasury`.

### Finding Description
In `chain/epoch-manager/src/reward_calculator.rs:78-87`:
```rust
let epoch_protocol_treasury = Balance::from_yoctonear(...);
res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury);
if num_validators == 0 {
    return (res, Balance::ZERO);
}
``` [1](#0-0) 
The treasury account entry is unconditionally inserted before the `num_validators == 0` short-circuit, but the second tuple element (`minted_amount`) is hard-coded to `Balance::ZERO` in that branch, discarding the treasury reward that was just computed and stored in `res`.

This `res` map (`validator_reward`) is later used by `proposals_to_epoch_info` / `apply_epoch_update_to_proposals` to bump the treasury account's stake proposal by the reward amount [2](#0-1) , and separately by `update_validator_accounts` in the runtime, which actually credits the treasury account's `amount`/`locked` balance from this same reward map [3](#0-2) . Meanwhile, `minted_amount` (the function's second return value) is what is stored on `EpochInfo` and later added to `total_supply` when validating/producing the next epoch's first block [4](#0-3) .

Because the `Balance::ZERO` short-circuit discards `epoch_protocol_treasury` from `minted_amount` while `res` (and hence the actual account credit) still contains it, the amount credited to the treasury account and the amount added to `total_supply` diverge whenever an epoch ends with zero validators.

### Impact Explanation
If `num_validators == 0` at an epoch boundary, the protocol treasury account receives a balance credit (`epoch_protocol_treasury`) that is never reflected in `total_supply`. This creates a permanent, systemic mismatch between the sum of all account balances and the chain's tracked `total_supply` — effectively unaccounted token inflation (supply-accounting divergence), which is one of the invariants nearcore explicitly checks via `verify_total_supply_checked` at block application [5](#0-4) . This mirrors the reported bug's structure: a to-be-distributed accumulator (`lpFeesTotal`/here, the treasury reward) is applied to one side of the ledger (recipient's balance) without the corresponding bookkeeping reset/adjustment on the other side (supply total), producing more value credited than accounted for.

### Likelihood Explanation
Low likelihood, exactly analogous to the original report's "requires no LP stake" precondition: mainnet networks are designed to always have at least one validator; `num_validators == 0` for a live epoch is an edge case that would require every validator to leave/unstake simultaneously (a scenario the code elsewhere treats as exceptional, e.g., `EpochError::ThresholdError`/`NotEnoughValidators` fallbacks in `chain/epoch-manager/src/lib.rs`).

### Recommendation
When `num_validators == 0`, either skip inserting the treasury reward into `res` entirely (so no balance credit occurs), or return `(res, epoch_protocol_treasury)` instead of `(res, Balance::ZERO)` so that the minted-supply accounting matches the actual credited amount:
```rust
res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury);
if num_validators == 0 {
    return (res, epoch_protocol_treasury);
}
```

### Proof of Concept
1. Construct an epoch boundary where `validator_block_chunk_stats` is empty (`num_validators == 0`), which can occur if all validators are kicked out or unstake in the same epoch, a path already handled elsewhere as a degenerate case (`EpochError::ThresholdError`/`NotEnoughValidators`).
2. `calculate_reward` computes `epoch_protocol_treasury > 0` from `total_supply * max_inflation_rate * epoch_duration * protocol_reward_rate` and inserts it into `res` at `reward_calculator.rs:84`.
3. Since `num_validators == 0`, the function returns `(res, Balance::ZERO)` at `reward_calculator.rs:86`.
4. `res` (containing the treasury credit) flows through `finalize_epoch` into the next `EpochInfo`'s `validator_reward` field, and is applied to the treasury account's actual balance via `update_validator_accounts` in the runtime.
5. The returned `Balance::ZERO` is stored as `EpochInfo::minted_amount()`, which is what gets added to `total_supply` at the next epoch's first block [6](#0-5) .
6. Result: the treasury account's balance increases by `epoch_protocol_treasury`, but `total_supply` does not, producing a persistent supply/balance-sum divergence.
