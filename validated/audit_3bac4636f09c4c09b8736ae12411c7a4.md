### Title
App proxy `logged_in_customer_id` query parameter is not protected against duplication, allowing customer-ID smuggling past HMAC validation - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
The app-proxy HMAC verification scheme concatenates sorted `key=value` pairs without any delimiter (`stringifyQueryForAppProxy`), mirroring the classic `abi.encodePacked()`-style collision problem where dynamic values are hashed without unambiguous framing. Combined with the fact that `logged_in_customer_id` is **not** included in the set of parameters that are required to be single-valued, an attacker who controls the query string reaching an app-proxy route (any storefront visitor) can inject a duplicate `logged_in_customer_id` parameter. The library's own `normalizeQuery` silently comma-merges duplicate values for the signature computation, so the resulting signature still validates, while the SDK's documented way of reading the value downstream (`URLSearchParams.get('logged_in_customer_id')`, which returns only the *first* occurrence) can return the attacker-controlled value instead of the one appended by Shopify.

### Finding Description
`validateHmac`'s app-proxy path builds the signed string with `stringifyQueryForAppProxy`, which concatenates `key=value` pairs directly with no separator between pairs: [1](#0-0) 

`APP_PROXY_SINGLE_VALUE_PARAMS` only protects `hmac`, `shop`, `signature`, and `timestamp` from being duplicated — `logged_in_customer_id` and `path_prefix` are excluded: [2](#0-1) 

For any other (non-protected) key, `normalizeQuery` merges duplicate values by joining them with a comma, in the order they appear in the query string: [3](#0-2) 

This merge behavior is exercised and accepted as valid in the test suite (e.g., `consentGiven=true,false`), confirming duplicate/array values for non-protected keys are folded into the signed string rather than rejected: [4](#0-3) 

The `authenticateAppProxyFactory` implementations in both `shopify-app-remix` and `shopify-app-react-router` only validate the signature and shop/session — they never inspect or sanitize `logged_in_customer_id`, leaving it to the app developer: [5](#0-4) 

The SDK's own published documentation instructs developers to read the value with `URLSearchParams.get('logged_in_customer_id')` after calling `authenticate.public.appProxy(request)`: [6](#0-5) 

Because `URLSearchParams.get()` returns only the first matching key, an attacker who appends a bogus `logged_in_customer_id=<victim-id>` to the storefront URL *before* Shopify appends its own trusted `logged_in_customer_id=<real-id>` can have both values pass HMAC validation (as a comma-joined signed string) while the app's documented code path reads the attacker-controlled first value as the "logged in customer" for the request.

### Impact Explanation
An unauthenticated or low-privileged customer can potentially cause the app-proxy endpoint to attribute a request to an arbitrary `logged_in_customer_id`, despite HMAC signature validation succeeding, because the field that is trusted downstream is not one of the fields whose singularity is enforced by the signature-checking code. Any app logic that gates customer-scoped data or actions on this value (as explicitly recommended by the SDK's own documentation) is exposed to cross-customer/cross-tenant data access or spoofing.

### Likelihood Explanation
Exploitability depends on: (1) whether Shopify's storefront proxy preserves duplicate query parameters and appends its own trusted value after any attacker-supplied one (positional dependency an attacker doesn't fully control), and (2) whether the app follows the SDK's documented pattern of using `URLSearchParams.get()` rather than the internally-normalized comma-merged value. This makes it a real but conditional/moderate-likelihood issue rather than a trivial one-shot bypass, since it hinges on parameter-order behavior on Shopify's side that isn't verifiable from this codebase alone.

### Recommendation
Add `logged_in_customer_id` (and `path_prefix`) to `APP_PROXY_SINGLE_VALUE_PARAMS` so `normalizeQuery` rejects requests with duplicated values for these trust-sensitive fields, consistent with the existing protection for `hmac`, `shop`, `signature`, and `timestamp`. Additionally, update the documented usage pattern to read `logged_in_customer_id` from the SDK's normalized/validated query object rather than instructing developers to call `URLSearchParams.get()` directly on the raw request URL.

### Proof of Concept
1. A malicious storefront visitor requests `/apps/my-proxy/route?logged_in_customer_id=<attacker-chosen-id>&...` where `...` represents whatever additional params the storefront naturally includes.
2. Shopify's app-proxy forwards the request to the app, appending its own trusted params, including the real `logged_in_customer_id=<real-id>`, to the query string (order depends on Shopify's proxy implementation) and signs the full parameter set (assuming Shopify's own signer performs the same alphabetical-sort + comma-merge-duplicate behavior mirrored by this library).
3. `validateHmac` (signator `appProxy`) computes `stringifyQueryForAppProxy` over the normalized query, where `logged_in_customer_id` becomes `"<attacker-chosen-id>,<real-id>"`, and the signature check passes: [7](#0-6) 
4. The app's loader, following the SDK's documented pattern, calls `new URL(request.url).searchParams.get('logged_in_customer_id')`, which returns only the first occurrence — the attacker-chosen value — despite the request having a valid signature.

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}

export function validateHmac(config: ConfigInterface) {
  return async (
    query: HmacQuery,
    {signator}: {signator: HMACSignator} = {signator: 'admin'},
  ): Promise<boolean> => {
    const normalizedQuery = normalizeQuery(query, signator);

    if (signator === 'admin' && !normalizedQuery.hmac) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain an HMAC value.',
      );
    }

    if (signator === 'appProxy' && !normalizedQuery.signature) {
      throw new ShopifyErrors.InvalidHmacError(
        'Query does not contain a signature value.',
      );
    }

    validateHmacTimestamp(normalizedQuery);

    const hmac =
      signator === 'appProxy'
        ? normalizedQuery.signature
        : normalizedQuery.hmac;
    const localHmac = await generateLocalHmac(config)(
      normalizedQuery,
      signator,
    );

    return safeCompare(hmac as string, localHmac);
  };
