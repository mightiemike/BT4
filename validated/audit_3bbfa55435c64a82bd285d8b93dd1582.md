### Title
Global contract publisher (`GlobalContractDeployMode::AccountId`) can silently rug every account referencing their contract by redeploying malicious code - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
NEAR's global-contract feature lets an account publish WASM code addressed either by immutable code hash, or by the publisher's `AccountId`. In the `AccountId` mode, any other account can adopt that code via `UseGlobalContractAction` or as the `code` of a `DeterministicStateInitAction` (NEP-616 deterministic accounts). Crucially, the publisher retains the unilateral ability to redeploy new code under the same `AccountId` identifier at any later time, and this new code is distributed to and takes effect on **every** account that references it - without any consent, notification, or on-chain approval from those accounts. This is directly analogous to the reported Astaria bug: a party that users implicitly "delegate trust" to (a vault strategist / here, a global-contract publisher) can unilaterally change the terms/logic that governs funds held by other parties, and drain them.

### Finding Description
`DeployGlobalContractAction` supports two `GlobalContractDeployMode`s: [1](#0-0) 

Documented explicitly: "Contract is deployed under the owner account id... This allows the owner to update the contract for all its users." [2](#0-1) 

The deploy path re-uses the same `GlobalContractIdentifier::AccountId(account_id)` on every redeploy and simply overwrites the stored code once the new version's nonce is higher, with no additional authorization check against the accounts that currently use it: [3](#0-2) [4](#0-3) 

Any account can bind itself to that identifier via `UseGlobalContractAction`, which just checks the code exists and rewires `AccountContract::GlobalByAccount(id)`: [5](#0-4) 

Deterministic accounts (NEP-616) go further: their code is *pinned forever* to a `GlobalContractIdentifier` chosen at account-derivation time, and the account, once seeded via `DeterministicStateInitAction`, executes with that identifier's *current* code — i.e. whatever the publisher has most recently deployed: [6](#0-5) [7](#0-6) 

This "update propagates to all users" behavior is confirmed by an in-repo test that redeploys code under the same `AccountId` and shows previously-adopting accounts pick up the new code automatically: [8](#0-7) 

Because contract code deployed on an account runs with the full authority of that account (it can call `Promise::transfer`/cross-contract calls moving that account's own NEAR/NEP-141 balances), a publisher can: (1) publish an innocuous, audited contract under `AccountId` mode; (2) wait until many unrelated deterministic/derived accounts adopt it and accumulate real user funds; (3) redeploy new code under the same identifier that adds a hidden, publisher-only "sweep" method (or unconditionally forwards deposits/balances to an attacker-controlled account); (4) call that method (or simply let normal user calls trigger the malicious logic) to drain every account still pointing at that `AccountId` identifier — all without the affected accounts ever signing a new key, approving a code hash, or being able to opt out in advance.

### Impact Explanation
This allows unauthorized, one-shot movement of NEAR balances (and any token balances the affected contracts manage) out of every account bound to the publisher's `AccountId`-mode global contract, including deterministic accounts whose code reference is immutable once created. Unlike the `CodeHash` mode (which is explicitly documented as immutable/safe), the `AccountId` mode gives the publisher persistent, unbounded, retroactive control over logic governing other accounts' funds — a systemic rug vector reachable by any account holder who chooses to publish global code, and exploitable against any account (created by any unprivileged signer) that adopts it.

### Likelihood Explanation
Likelihood is Medium: exploitation requires that at least one victim account adopt the `AccountId`-mode contract (via `UseGlobalContractAction` or deterministic-account state-init) and hold funds, and that the publisher issue a later malicious redeploy. Both actions are ordinary, permissionless transactions requiring no special privilege beyond owning the publishing account, and the redeploy-then-drain sequence is a single-actor, on-chain-only operation (no cooperation from validators, other nodes, or victims needed).

### Recommendation
- Warn/require explicit acknowledgment (or a distinct, more restrictive action) before an account references an `AccountId`-mode global contract, clearly surfacing that the publisher retains unilateral update rights over the code governing that account's funds.
- Consider adding a way for a using account to pin to a specific nonce/version of an `AccountId`-mode contract (or convert its reference to an immutable `CodeHash` snapshot) so future republishes by the identifier owner cannot silently change code already relied upon.
- For deterministic accounts specifically (NEP-616), consider disallowing `AccountId`-mode `GlobalContractIdentifier`s in `code`, since users have no way to migrate off a compromised/rug-updated reference once the deterministic account ID has been derived from it.

### Proof of Concept
1. Publisher account `pub.near` deploys a benign contract with `DeployGlobalContractAction { deploy_mode: GlobalContractDeployMode::AccountId }`.
2. Victim accounts `alice.near`, `bob.near`, and/or freshly created deterministic accounts each execute `UseGlobalContractAction { contract_identifier: GlobalContractIdentifier::AccountId("pub.near") }` (or a `DeterministicStateInitAction` whose `state_init.code` is that identifier) and deposit real NEAR/NEP-141 balances into their accounts, trusting the currently-reviewed code.
3. `pub.near` later submits a second `DeployGlobalContractAction` (same `AccountId` mode) with malicious code containing a callable method that transfers the executing account's balance to an attacker address (or a NEP-141 `ft_transfer` sweep).
4. Per `initiate_distribution`/`apply_distribution_current_shard`, the new code (with a strictly higher nonce) overwrites the previous version network-wide for that `GlobalContractIdentifier::AccountId` — `runtime/runtime/src/global_contracts.rs:143-171,191-226`.
5. `pub.near` (or anyone) calls the malicious method against `alice.near`, `bob.near`, or the deterministic accounts; because the code executes with the target account's own authority, it drains their balances — demonstrating the same "signer with discretionary power over shared terms rugs all dependents" pattern as the original Astaria finding.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

fn deploy_deterministic_account(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    state_init: &DeterministicAccountStateInit,
    result: &mut ActionResult,
    storage_usage_config: &StorageUsageConfig,
) -> Result<(), RuntimeError> {
    // Step 1: set contract code (includes storage usage accounting)
    use_global_contract(state_update, account_id, account, state_init.code(), result)?;
    if result.result.is_err() {
        return Ok(());
    }

    // Step 2: insert provided key-value pairs
    let mut required_storage_usage = account.storage_usage();
    for (key, value) in state_init.data() {
        let trie_key = TrieKey::ContractData { account_id: account_id.clone(), key: key.to_vec() };

        let value_bytes = value.len() as u64;
        let key_bytes = key.len() as u64;
        let extra_per_record_bytes = storage_usage_config.num_extra_bytes_record;

        let new_bytes = value_bytes
            .checked_add(key_bytes)
            .and_then(|acc| acc.checked_add(extra_per_record_bytes))
            .ok_or(IntegerOverflowError {})?;
        state_update.set(trie_key, value.clone());
        required_storage_usage =
            required_storage_usage.checked_add(new_bytes).ok_or(IntegerOverflowError {})?;
    }
    account.set_storage_usage(required_storage_usage);

    Ok(())
}

fn test_global_contract_update() {

                    MethodResolveError::MethodNotFound
                )),
                index: _
            }))
        );
    }

    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    for account in &use_accounts {
        // Function call should be successful after deploying rs contract
        // containing the function we call here
        env.assert_call_global_contract_success(account.clone(), account.clone());
    }
}
