## Title
`liquidate-multi` uses `map` instead of aggregated `try!`, allowing a partially-executed `liquidate` call to strand a liquidator's repaid debt without receiving collateral if a later step in the same call fails - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` calls `(ok (map call-liquidate positions))` [1](#0-0) . Because the outer function always returns `(ok ...)` regardless of the individual results, and `map` does not propagate an inner `(err ...)` to abort the whole transaction, any state mutation already committed by a `contract-call?` earlier inside a single `liquidate` invocation (specifically `vault-system-repay`, which pulls/burns the liquidator's repayment tokens) is **not rolled back** if a later step in that same `liquidate` call - `debt-remove-scaled` or `collateral-remove` on `.v0-market-vault` - subsequently fails and returns an error via `try!`.

### Finding Description
Inside `liquidate`, the sequence of state-mutating operations is:
1. `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` - liquidator's tokens are transferred/burned to repay debt [2](#0-1) .
2. `(try! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-to-remove debt-aid))` [3](#0-2) .
3. `(try! (contract-call? .v0-market-vault collateral-remove borrower coll-final collateral-ft coll-aid actual-receiver))` [4](#0-3) .

Step 1 is itself a separate `contract-call?` to a vault (e.g. `.v0-vault-usdc`), which commits its own effects (burns the liquidator's tokens) once it returns `(ok ...)`. Steps 2/3 call `.v0-market-vault`, whose `debt-remove-scaled` and `collateral-remove` each perform their own `asserts!`/`try!` guards (`ERR-INSUFFICIENT-DEBT`, `ERR-INSUFFICIENT-COLLATERAL`, `ERR-PAUSED`, `ERR-AUTH`) before mutating the registry maps [5](#0-4) [6](#0-5) . If either of those guards fails (e.g. `debt-add-scaled`/`debt-remove-scaled` desync from a concurrently-executed position in the same batch, or `market-vault`'s `pause-states` toggled by DAO mid-batch, or `ERR-INSUFFICIENT-COLLATERAL` from stale collateral bookkeeping), `liquidate` itself returns `(err ...)` via the propagating `try!`.

Normally, in a standalone `liquidate` transaction, this `(err ...)` from the top-level entry point rolls back the *entire transaction*, including the already-executed `vault-system-repay` step, preserving atomicity. However, `liquidate-multi` invokes `liquidate` indirectly through `call-liquidate` inside a `map` [7](#0-6) , and wraps the whole result list in `(ok ...)` unconditionally [8](#0-7) . Because the *outermost* entry-point function (`liquidate-multi`) returns `ok`, the overall transaction commits. The per-position `err` returned by a failing `liquidate` call is just a value inside the returned list - it does not cause a transaction-wide rollback. Whether the already-executed cross-contract `vault-system-repay` commit for that failed position persists depends on Clarity's atomicity semantics for un-propagated nested `contract-call?` results; the doc comment "Failed liquidations return error codes but don't revert entire batch" [9](#0-8)  confirms the intended (and documented) behavior is per-position independence, but the mechanism for guaranteeing that intra-`liquidate` state changes made *before* the failure point are also cleanly reverted (rather than the top-level `ok` simply papering over a partially-mutated vault/market-vault state) is not visible in this code and cannot be confirmed to be safe from this contract alone.

### Impact Explanation
If a liquidator's debt repayment (`vault-system-repay`) commits but the subsequent `debt-remove-scaled`/`collateral-remove` calls fail, the liquidator's funds used to repay debt are spent with no collateral received and no corresponding on-chain debt reduction recorded for the borrower - a stranding of the liquidator's value in a partially-executed multi-step entry point. This falls under temporary/permanent freezing of funds (liquidator capital) and potential protocol insolvency risk (debt state inconsistency between vault and market-vault bookkeeping) if such partial states can be provoked deliberately, e.g. by a DAO-controlled pause toggle mid-batch or by constructing a batch where one position's failure is engineered.

### Likelihood Explanation
This requires a specific interleaving: `liquidate-multi` executing multiple positions where one position's later step (`debt-remove-scaled`/`collateral-remove`) fails after its `vault-system-repay` step already succeeded. Realistic triggers for such a failure mid-batch (pause toggling, insufficient-collateral edge cases from rounding, or account state changes) exist but are not certain to be reachable by an unprivileged attacker without further conditions (e.g., a DAO pause action interleaved in the same block, which is out of scope per the rules unless the attacker alone can cause the desync). This significantly limits confidence that this is independently, deterministically exploitable by a single actor without additional privileged interaction, and I could not fully verify Clarity's rollback semantics for un-propagated nested `contract-call?` errors from within this codebase alone.

### Recommendation
Ensure `liquidate-multi` cannot commit an inconsistent state for a partially-completed `liquidate` call: either (a) perform each position's repay + debt-removal + collateral-removal only after confirming all steps will succeed (validate-then-execute ordering, similar to the borrow/repay functions' existing pattern of computing all post-conditions before any mutation), or (b) explicitly wrap each `liquidate` call in a construct that guarantees full atomic rollback per position (e.g. verify via testing that a failing nested `contract-call?` does fully unwind prior contract-calls within the same top-level `ok` transaction), and add regression tests exercising a forced mid-batch failure to confirm no stranded liquidator funds occur.

### Proof of Concept
1. Attacker/liquidator submits `liquidate-multi` with two positions: position A (healthy debt-removal path) and position B constructed so that `vault-system-repay` succeeds for B's debt asset but the subsequent `.v0-market-vault debt-remove-scaled` call for B fails (e.g. via a race where `scaled-to-remove` computed against a stale `curr-scaled` no longer matches after another list entry's earlier processing in the same `map`, or the pause-state flips mid-batch).
2. In `liquidate` for position B: `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` executes, burning/transferring liquidator B's repayment tokens [2](#0-1) .
3. `(try! (contract-call? .v0-market-vault debt-remove-scaled borrower scaled-to-remove debt-aid))` fails with `ERR-INSUFFICIENT-DEBT` [10](#0-9) , causing `liquidate` for position B to return `(err ...)`.
4. `call-liquidate` returns this err as a list element; `map` continues to process remaining positions [7](#0-6) .
5. `liquidate-multi` returns `(ok (list ... err ...))` [8](#0-7) , and since this is the top-level transaction return, the transaction commits - potentially retaining the already-executed `vault-system-repay` side effects for position B without the corresponding debt/collateral bookkeeping update.

Note: I was not able to fully confirm within this codebase whether Clarity's runtime guarantees a full rollback of the intra-`liquidate` state for the failed position B despite the outer `ok`, since this depends on VM-level atomicity semantics not visible in the contract source. This uncertainty should be validated with targeted integration tests (deliberately forcing a step-2/3 failure inside `liquidate-multi`) before treating this as confirmed exploitable.

```text
(define-private (remove-user-scaled-debt (user-id uint) (asset-id uint) (amount uint))
  (let ((key { id: user-id, asset: asset-id })
        (current-scaled-debt (default-to u0 (get scaled (map-get? debt key)))) ;; graceful default to u0
        (legal? (asserts! (<= amount current-scaled-debt) ERR-INSUFFICIENT-DEBT))
        (updated-scaled-debt (- current-scaled-debt amount)))
    (if (is-eq updated-scaled-debt u0)
        (map-delete debt key)
        (map-set debt key { scaled: updated-scaled-debt }))
    (ok updated-scaled-debt)))
```
