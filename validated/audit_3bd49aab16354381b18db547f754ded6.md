### Title
Native stack-overflow DoS via unbounded recursive JSON parsing of internally-tagged `RpcTransaction` at the gateway HTTP endpoint - ([File: crates/apollo_http_server/src/http_server.rs])

### Summary
The reported CVE (CVE-2018-18700) is a stack-consumption DoS caused by unbounded recursive descent parsing of an untrusted, attacker-crafted structured input (`cp-demangle.c`) with no recursion-depth guard. The sequencer has an analogous bug class: the gateway's `/gateway/add_rpc_transaction` HTTP endpoint deserializes the raw, untrusted request body directly into the internally-tagged enum `RpcTransaction` via `axum::extract::Json`, which in turn uses `serde_json`'s recursive-descent parser with no depth limit configured anywhere in the codebase.

### Finding Description
The HTTP endpoint handler decodes the request body straight into the strongly-typed, internally-tagged transaction enum before any semantic/structural validation (e.g. `StatelessTransactionValidator`) runs: [1](#0-0) 

`RpcTransaction` is declared with `#[serde(tag = "type")]`: [2](#0-1) 

For internally-tagged enums, `serde_derive` generates code that first buffers the *entire* incoming JSON value into an untyped intermediate representation (`serde::private::de::Content`) so it can inspect the `"type"` field before dispatching to the concrete variant deserializer. This buffering step recursively walks arbitrarily nested JSON arrays/objects regardless of the target field's declared (non-recursive) type — a deeply nested array anywhere in the payload (e.g. inside `calldata`, `signature`, or any other array/object field) forces the parser into deep native-stack recursion before any type mismatch is even detected.

A repo-wide search confirms there is no recursion-depth guard configured anywhere (`serde_json::Deserializer::disable_recursion_limit`, a manual JSON-depth check, or similar) protecting this path: [3](#0-2) 
Only a byte-size limit (`RequestBodyLimitLayer`/`DefaultBodyLimit`) is enforced — this bounds total payload size, not nesting depth. Because JSON nesting only costs 2 bytes per level (`[` … `]`), a request well within the configured byte limit can encode tens of thousands of nesting levels, which is enough to exceed a typical 8 MiB thread stack via the generic `Content` recursive parser, causing the worker thread (and the whole HTTP-server/gateway process, since Rust aborts on stack overflow) to crash.

This is directly analogous to the CVE's bug class: recursion depth is driven entirely by attacker-supplied structure, with the vulnerable recursive routine (serde's internal `Content` deserializer here, `d_encoding`/`d_name` there) invoked before the higher-level consumer (transaction semantics / demangled-name consumer) ever validates the input.

### Impact Explanation
A single unauthenticated HTTP POST to `/gateway/add_rpc_transaction` (or the legacy `/gateway/add_transaction` path, which also parses attacker JSON via `serde_json::from_str`) can crash the gateway/HTTP-server component of a sequencer node, halting new-transaction ingestion for that node (denial of service against transaction submission — "a network unable to confirm new transactions" if this affects the sequencing path broadly or is repeated against multiple nodes). No fee is charged and no valid transaction ever needs to be admitted, since the crash occurs during deserialization, prior to `StatelessTransactionValidator` checks.

### Likelihood Explanation
High likelihood of reachability: the endpoint is public, requires no authentication, no fee, and no valid signature — a plain HTTP POST with a small (well under any configured body-size limit), deeply-nested JSON payload suffices. The `#[serde(tag = "type")]` attribute is present on the top-level `RpcTransaction` enum, guaranteeing the vulnerable Content-buffering code path is always exercised for every submission.

### Recommendation
- Configure `serde_json`'s deserializer with an explicit recursion/nesting depth limit before/while parsing untrusted request bodies (e.g., wrap the incoming bytes with a `serde_json::Deserializer` that enforces `recursion_limit`, or pre-scan/reject payloads whose bracket/brace nesting exceeds a small bound, e.g. 32–64 levels, before calling into `serde`).
- Avoid using `axum::Json<T>` directly on internally-tagged enums for untrusted input; instead parse into `serde_json::Value` first with an explicit depth guard, or switch the wire format to an externally-tagged/adjacently-tagged representation that does not require full-content buffering.
- Add a fuzz/regression test that posts deeply nested JSON payloads (e.g. 100k `[` characters) to `add_rpc_transaction` and asserts the server returns a JSON-parse error rather than crashing.

### Proof of Concept
```
POST /gateway/add_rpc_transaction HTTP/1.1
Host: <sequencer-gateway>
Content-Type: application/json
Content-Length: <small>

{"type":"INVOKE","version":"0x3","calldata":[[[[[[[[[[ ... 100000 nested arrays ... ]]]]]]]]]],"sender_address":"0x1", ...}
```
Sending this request (well within the configured `max_request_body_size`) forces `serde`'s internally-tagged-enum `Content` deserializer to recurse once per nesting level while buffering the JSON value to locate the `"type"` discriminant, exhausting the worker thread's native stack and crashing the process — before `validate_declare_tx`/`validate_sierra_version`/calldata-length checks in `StatelessTransactionValidator` ever run.
