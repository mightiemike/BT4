### Title
Uncontrolled Memory Allocation via Unvalidated Length Field in Starknet OS Output Parsing - (File: crates/starknet_os/src/io/os_output_types.rs)

### Summary
`TryFromOutputIter` for `Vec<T>` reads an item count directly from the felt stream produced by Starknet OS execution and immediately calls `Vec::with_capacity(n_items)` before verifying that the iterator actually contains that many remaining elements [1](#0-0) . This mirrors the dr_flac.h bug class described in the external report: a length field taken from untrusted/attacker-influenced data is used to size an allocation before the corresponding payload is validated, allowing a crafted length value to trigger an oversized allocation.

### Finding Description
`try_from_output_iter` for `Vec<T>` pulls `n_items` from the next felt in the output iterator and calls `Vec::with_capacity(n_items)` with no upper bound and no check that `n_items` is consistent with the number of felts actually remaining in the iterator [2](#0-1) . The codebase already recognizes and has patched exactly this bug class elsewhere: `CairoArray::try_from` in `apollo_cairo_utils` explicitly validates the declared count against the number of remaining felts before calling `Vec::with_capacity`, with a comment stating the purpose is "to prevent a contract-controlled length felt from triggering an unbounded `Vec::with_capacity`" [3](#0-2) . The `Vec<T>` implementation for `TryFromOutputIter` in `os_output_types.rs` lacks this same guard, so a felt value used to encode a collection length (e.g., counts embedded in the OS's structured output such as messages, state diff entries, or similar repeated structures) can be set arbitrarily high relative to the true remaining data, causing an attempted allocation sized by that felt rather than by validated data length.

### Impact Explanation
`TryFromOutputIter`/`os_output_types.rs` types are used to parse the structured Starknet OS output during Starknet OS re-execution and validation flows, which is one of the explicitly in-scope sequencer paths. A node performing this parsing on a maliciously crafted or corrupted output stream (or on output influenced by a contract execution that controls a length-prefixed field) can be driven to attempt an excessive memory allocation, causing denial of service / node crash during OS output verification. This can degrade or halt a node's ability to validate blocks, aligning with "network unable to confirm new transactions" if triggered broadly.

### Likelihood Explanation
The bug is directly reachable any time `TryFromOutputIter for Vec<T>` is invoked on OS output data where the count felt is not independently bounded elsewhere before this call, and the analogous flaw was serious enough that a fix was already applied to the structurally identical `CairoArray::try_from` code path, indicating this bug class is a known and exploitable pattern within the codebase's felt-stream deserialization utilities [3](#0-2) .

### Recommendation
Apply the same fix used in `CairoArray::try_from`: before calling `Vec::with_capacity(n_items)` in `TryFromOutputIter for Vec<T>`, validate that `n_items` does not exceed the number of elements actually remaining in the iterator (or a conservative bound derived from it), returning an error otherwise [1](#0-0) .

### Proof of Concept
Construct or influence a Starknet OS output felt stream so that a count field consumed by `Vec::<T>::try_from_output_iter` is set to a very large value (e.g., close to `usize::MAX` or a value far larger than the number of felts that actually follow), while the actual number of subsequent felts is small or zero. When a node parses this output via `try_from_output_iter`, it will call `Vec::with_capacity(n_items)` with the attacker-chosen huge value before the shortage of remaining data is discovered, causing an oversized allocation attempt [2](#0-1) .

impl<T: TryFromOutputIter> TryFromOutputIter for Vec<T> {
    fn try_from_output_iter<It: Iterator<Item = Felt>>(
        iter: &mut It,
        private_keys: Option<&Vec<Felt>>,
    ) -> Result<Self, OsOutputError> {
        let n_items =
            wrap_missing_as(iter.next(), &format!("n_items of {}", std::any::type_name::<T>()))?;
        let mut items = Vec::with_capacity(n_items);
        for _ in 0..n_items {
            items.push(T::try_from_output_iter(iter, private_keys)?);
        }
        Ok(items)
    }
}
