## #Vulnerability found

### Title
Missing bounds validation for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` proposal parameters allows setting negative/unbounded fees - (File: `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`)

### Summary
`ProposalUtil.validator()` performs no range/sign check for the `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` proposal types, unlike every sibling fee parameter (`ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, `TRANSACTION_FEE`, etc.) which all enforce `value < 0 || value > LONG_VALUE` checks. This is the same bug class described in the external report: a setter for an economically critical parameter with no `require`-style validation of the input value.

### Finding Description
In `ProposalUtil.validator()` the switch statement validates almost every numeric governance parameter with an explicit range check, for example the sibling group: [1](#0-0) 

but `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` fall through to a bare `break;` with zero validation of `value`: [2](#0-1) 

Once `ProposalCreateActuator.validate()` calls this validator and the proposal is approved, `ProposalService.process()` writes the unvalidated value directly into the chain state: [3](#0-2) 

`ENERGY_FEE` is subsequently consumed as `sunPerEnergy` in `ReceiptCapsule.payEnergyBill()`, which computes `energyFee = (usage - accountEnergyLeft) * sunPerEnergy` and then does `account.setBalance(balance - energyFee)`: [4](#0-3) 

If `ENERGY_FEE` is set to a negative value (nothing in `ProposalUtil` prevents this), `energyFee` becomes negative and `balance - energyFee` *increases* every account's balance instead of debiting it for energy consumption — a direct token-supply/accounting integrity break. Likewise `EXCHANGE_CREATE_FEE` (consumed via `getExchangeCreateFee()` when creating a bancor-style exchange pair) can be set negative or to an absurdly large value with no defense, corrupting exchange-creation economics.

### Impact Explanation
This is an accounting/invalid-state issue: an unvalidated negative `ENERGY_FEE` flips a fee-debit into a balance credit for every smart-contract-calling account on the network each time the fallback "pay from account" branch of `payEnergyBill` executes, directly inflating balances/breaking tokenomics network-wide (mirroring exactly the "impact on the tokenomics of the ecosystem" called out in the external report). `EXCHANGE_CREATE_FEE` similarly lacks any bound, letting a governance mistake set an economically nonsensical (negative or extreme) fee for exchange creation.

### Likelihood Explanation
Setting these values requires a proposal to be created (any witness/account with SR privileges) and approved by ≥19 witnesses, so it is not exploitable by a fully unprivileged attacker in one step. However, unlike almost every other numeric field in the same switch statement, `ENERGY_FEE`/`EXCHANGE_CREATE_FEE` have no defensive validation at all, so a single bad proposal input (typo, malicious insider proposal, or a negative value slipping through) is sufficient to trigger network-wide incorrect accounting — there is no secondary safety net anywhere else in the code path (`ProposalService.process`, `saveEnergyFee`, `payEnergyBill` all trust the value blindly).

### Recommendation
Add the same bounds check used for the other fee-like parameters, e.g.:
```java
case ENERGY_FEE:
case EXCHANGE_CREATE_FEE: {
  if (value < 0 || value > LONG_VALUE) {
    throw new ContractValidateException(LONG_VALUE_ERROR);
  }
  break;
}
```
in `ProposalUtil.validator()` at [2](#0-1) , matching the pattern already used for `ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, etc.

### Proof of Concept
1. Craft a `ProposalCreateContract` with `parameters = { ENERGY_FEE.getCode(): -1 }` (code 11) and submit via `ProposalCreateActuator`.
2. `ProposalCreateActuator.validate()` calls `ProposalUtil.validator()`, which reaches `case ENERGY_FEE: break;` and returns successfully — no exception is thrown for the negative value (contrast with `ACCOUNT_UPGRADE_COST` at the same code path which would reject `-1`).
3. Once witnesses approve the proposal, `ProposalService.process()` executes `case ENERGY_FEE: manager.getDynamicPropertiesStore().saveEnergyFee(-1); ...` at [5](#0-4)  — a negative fee is now the network's `ENERGY_FEE`.
4. On the next smart-contract call where an account exhausts its frozen energy, `ReceiptCapsule.payEnergyBill()` computes `sunPerEnergy = -1` and `energyFee = (usage - accountEnergyLeft) * -1` (negative), then executes `account.setBalance(balance - energyFee)`, which *increases* the caller's TRX balance instead of charging it — see [4](#0-3) .
