I found a concrete, code-documented integrity gap. This is being reported as a new Aptos-native analog to the `DelFiPrice` issue: a "post"/commit path (`TransactionOutput::ensure_match_transaction_info`) that is supposed to authenticate a computed result against a trusted commitment, but silently skips part of that commitment (the state-checkpoint/state-root hashes), so `replay_on_archive` and similar tools can report success even though the locally computed state root diverges from the archived, authenticated one.

### Title
`TransactionOutput::ensure_match_transaction_info` never verifies `state_checkpoint_hash` / `hot_state_checkpoint_hash`, letting replay/restore verification silently accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the function used by replay/debugger tooling (`db-tool`'s `replay_on_archive`, `aptos-debugger`, `aptos-move/cli`) to compare a freshly re-executed `TransactionOutput` against the archived, ledger-committed `TransactionInfo`. It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** compare the state-checkpoint hash (state root) or hot-state checkpoint hash fields carried in `TransactionInfo`, even though the code has a `TODO` acknowledging this. This means the one function whose entire purpose is to authenticate a re-computed transaction result against the trusted, proof-bearing `TransactionInfo` can pass even when the state root actually diverges.

### Finding Description
`TransactionInfo` carries `state_checkpoint_hash` (and, in `V1`, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`), which is the authenticated root of ledger state at that version, bound into the transaction accumulator via `TransactionInfo::hash()` and validated by `AccumulatorProof::verify`.

`TransactionOutput::ensure_match_transaction_info` checks:
- execution status vs `txn_info.status()` [1](#0-0) 
- gas used vs `txn_info.gas_used()` [2](#0-1) 
- write-set hash vs `txn_info.state_change_hash()` [3](#0-2) 
- event-root hash vs `txn_info.event_root_hash()` [4](#0-3) 

It then returns `Ok(())` without comparing `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` at all, and the surrounding comment explicitly documents this gap: [5](#0-4) 

This function is the sole "post happened → recompute and compare the committed state" gate used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls exactly this function to decide pass/fail: [6](#0-5) 

Because the write set is compared only by its serialized hash (`state_change_hash`), and never against the resulting state root, a scenario where the write set is bit-identical but the *effective materialized state* (e.g. under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state or position-state-checkpoint features that produce additional roots not encoded in the write-set hash) diverges will not be caught. This mirrors the external report's core defect: there exist two "paths" that are supposed to keep an authenticated value consistent (write-set materialization vs. state-root commitment), but only one is checked, so the two can silently diverge without the verifier noticing.

### Impact Explanation
This is a proof/authenticated-response integrity gap in the replay/restore verification tooling: `replay_on_archive`, `aptos-debugger`, and `aptos-move/cli` rely on `ensure_match_transaction_info` as their correctness oracle. If the underlying state-root computation for a transaction diverges from what's stored in the archived `TransactionInfo` (e.g. due to a state-computation bug, hot-state/position-state-root logic bug, or a hard-fork-only divergence), replay-verification will report "success" even though the local state root does not match the authenticated ledger root. This directly satisfies the state-integrity gate's "hard-fork-only divergence during commit, replay, restore, or proof verification" and "authenticated API or state-view output bound to the wrong version/root" criteria — a wrong root can pass verification undetected, defeating the entire purpose of replay verification as a corruption/divergence detector.

### Likelihood Explanation
The gap is not theoretical guesswork — it's confirmed by the code's own `TODO` comment, which states the comparator "ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution." The trigger condition (state root divergence not reflected in the write-set hash) becomes concretely reachable once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or related hot-state/position-state-checkpoint features are enabled, since those introduce additional state-root fields (`hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) that are stored in `TransactionInfoV1` but are exactly the ones excluded from comparison.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s locally computed state-checkpoint hash(es) against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` (when present/applicable), failing verification on any mismatch, before enabling or relying on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` in replay/restore tooling.

### Proof of Concept
1. Enable a code path where state materialization (e.g. hot-state or position-state root, gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) diverges from the original execution's authenticated `state_checkpoint_hash` while producing an identical serialized write set (e.g. through a scheduling/materialization order bug in `execution/executor/src/workflow/do_state_checkpoint.rs`).
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`) over the affected version range.
3. Observe `execute_and_verify` calling `ensure_match_transaction_info`, which only checks status/gas/write-set-hash/event-root-hash [7](#0-6)  — the call returns `Ok(())` despite the divergent state-checkpoint hash, so the replay is reported as verified even though the ledger state root is wrong.

**Note on confidence**: I confirmed the missing comparison and its acknowledgment via the in-code `TODO`, and traced the single call site in `replay_on_archive.rs`. I was not able to fully verify, within the available search iterations, the exact runtime conditions under which `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-driven divergence would occur in practice (i.e., whether a genuine reachable bug currently exists in `do_state_checkpoint.rs`'s hot-state/position-state-root computation), since that flag was called out in the code as not-yet-safe-to-enable. The core finding — that the verification function itself has an incomplete authenticity check by its own admission — is confirmed directly from source.
