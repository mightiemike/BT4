## Title
Unbounded array length in deprecated syscall calldata parsing can trigger large VM memory allocation - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

## Summary
`read_felt_array` in the deprecated syscall handler reads an attacker/contract-controlled `array_size` felt directly from Cairo VM memory and converts it to a `usize` without bounding it against any actual buffer/segment size before using it to read a felt range from the VM.

## Finding Description
`read_felt_array` reads the declared length of an array (`array_size`) straight from VM memory that is populated by whatever calldata/arguments a deployed/declared Cairo 0 contract passes into a deprecated syscall (e.g., `call_contract`/library-call style calldata parsing): [1](#0-0) 

The declared `array_size` is converted to `usize` and passed to `felt_range_from_ptr`, which forwards it to `vm.get_integer_range(ptr, size)`: [2](#0-1) 

Unlike the analogous `read_felt_array` in the newer (non-deprecated) syscall hint processor, which derives the array length from the *difference between two pointers* (`array_data_end_ptr - array_data_start_ptr`) and is therefore bounded by real memory layout, the deprecated variant trusts a raw length value with no independent validation against the actual data present: [3](#0-2) 

This matches the pypdf bug class: a length field (`/Length` in the PDF case, `array_size` here) is used to drive allocation/iteration before the real extent of the underlying data is validated, so an attacker can supply a huge declared length against a tiny backing buffer.

## Impact Explanation
This is reachable only through the deprecated (Cairo 0) syscall path, which is a legacy/back-compat code path. A crafted Cairo 0 contract's deprecated syscall invocation (e.g. reading a calldata array in `call_contract`/library-call handling) can declare an arbitrarily large `array_size`, causing `get_integer_range` to attempt to allocate/read a correspondingly large range before erroring out on a missing memory cell. Depending on the underlying cairo-vm implementation of `get_integer_range` (allocation size vs. lazily reading), this can drive excessive memory allocation per transaction, which is a resource-exhaustion (CWE-770) issue rather than a fund-loss or state-divergence issue.

## Likelihood Explanation
Reachable from any transaction that invokes an entry point of a Cairo 0 (deprecated) declared class exercising this code path, so the barrier to trigger it is low — a single declare + invoke by an unprivileged account. However, the actual severity depends on cairo-vm's internal behavior for `get_integer_range` with out-of-range sizes (whether it eagerly allocates a Vec of the requested capacity or incrementally reads and fails fast), which this repo's index does not contain (it lives in the external `cairo-vm` crate, not in this repository).

## Recommendation
Bound `array_size` in `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`) against a sane maximum (e.g., the max calldata/array length already enforced elsewhere, such as `max_calldata_length` in the gateway config) before calling `felt_range_from_ptr`/`get_integer_range`, mirroring the pointer-difference approach used in the non-deprecated syscall handler.

## Proof of Concept
Not fully constructible from the indexed code alone: reproducing this requires knowing the exact behavior of `cairo-vm`'s `get_integer_range` for large `size` values (whether it pre-allocates), which is defined outside this repository. Conceptually: declare a Cairo 0 class whose deprecated syscall invocation calldata parsing sets `array_size` to a large value (e.g., close to `usize::MAX` or large enough to exceed practical memory) while providing a tiny backing memory segment, then invoke that entry point; `read_felt_array` will attempt to materialize a felt range of that declared size.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
