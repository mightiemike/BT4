### Title
Missing low-S canonicalization in `check_recover_pubkey` allows signature malleation to forge a second `StacksMicroblockHeader` for a poison report - (File: stacks-codec/src/transaction.rs)

### Summary
`StacksMicroblockHeader::check_recover_pubkey` (stacks-codec/src/transaction.rs:2598-2616) recovers the signer's public key using `StacksPublicKey::recover_to_pubkey_without_validating_low_s`, which accepts both the canonical low-S signature and its malleated high-S counterpart (`s -> n-s`, recovery id flipped) for the exact same message digest and key. Because the digest is computed only from `version, sequence, prev_block, tx_merkle_root` (signature zeroed out during hashing, see `serialize(..., true)` at lines 2585-2596), an attacker who observes any one broadcast, signed `StacksMicroblockHeader` h1 can compute a malleated `MessageSignature` and build h2' with identical content fields but a different `.signature` byte string, which still recovers to the same `Hash160` pubkey hash used by `check_microblock_header_signer` and by mempool admission (`will_admit_mempool_tx`, blocks.rs:6844-6868).

### Finding Description
The intended equality for poison-microblock evidence is: "two `StacksMicroblockHeader`s independently produced/signed by the same key at the same sequence" == proof of equivocation. The code instead only checks: (a) both headers recover to the same pubkey hash via `check_recover_pubkey`, and (b) the header byte-representations differ (`h1 != h2`, which trivially holds because `.signature` differs). It never checks that the two signatures are cryptographically independent nonces/messages rather than a low-S/high-S malleated pair of the *same* underlying ECDSA signature.

Because `recover_to_pubkey_without_validating_low_s` is used instead of the canonicalizing recovery function, non-canonical signatures are accepted as valid for the same key/message. An attacker can:
1. Take a legitimately broadcast, signed microblock header h1 (public once broadcast, per the precondition).
2. Compute the malleated signature: flip `s -> n - s`, adjust the recovery id, producing a new `MessageSignature` bytes for the exact same digest and the exact same key.
3. Construct h2' with the identical `version/sequence/prev_block/tx_merkle_root` as h1 but the malleated `.signature`.
4. Submit h1 and h2' as the two headers of a `TransactionPayload::PoisonMicroblock` transaction; both pass `check_recover_pubkey`/`check_microblock_header_signer` since low-S is not enforced, and `h1 != h2'` holds only because of the cosmetic signature-encoding difference, not because the miner produced two different messages.

This lets the attacker manufacture "two header" evidence from a miner who only ever signed and broadcast one microblock header, since the malleated variant was never independently produced by the miner's key — it is a deterministic transformation of the one signature the attacker observed.

### Impact Explanation
This is a poison-microblock false-positive: it lets an unprivileged attacker with no key material file a `PoisonMicroblock` transaction that gets admitted to the mempool (via `will_admit_mempool_tx`) and processed as valid double-sign proof against a miner who signed only one microblock. The consequence is a miner incorrectly penalized — reward/coinbase forfeiture bounded to that miner's fee/reward share and repeatable for any observed microblock header — which matches the "High: a poison or reward mis-payment bounded to fees" category rather than a chain split, since the underlying microblock content (sequence, prev_block, tx_merkle_root) is unchanged and no fork divergence between honest nodes results from this alone.

### Likelihood Explanation
The precondition is trivial for an unprivileged attacker: observing any one broadcast, valid microblock header/signature (public information) and applying standard secp256k1 signature malleability (`s -> n-s`), which requires no BTC stake, no signer weight, and no privileged role. It is fully repeatable against any miner's broadcast microblocks and requires no majority position — any single observer of a broadcast header can do this offline and then submit the crafted `PoisonMicroblock` tx.

### Recommendation
Enforce canonical low-S signatures when recovering the pubkey in `check_recover_pubkey` (use the validating recovery function, e.g. reject/normalize any signature whose `s` is not in the lower half of the curve order, consistent with what `recover_to_pubkey_without_validating_low_s` intentionally skips), for both microblock header verification and any signature checked as poison-microblock evidence. Additionally/defensively, `check_microblock_header_signer` should treat two headers with identical `version/sequence/prev_block/tx_merkle_root` as the same logical message and refuse to treat a purely signature-encoding difference as equivocation evidence.

### Proof of Concept
Rust integration test plan:
1. Generate a `StacksPrivateKey`, build a `StacksMicroblockHeader` h1 with arbitrary `version/sequence/prev_block/tx_merkle_root`, call `h1.sign(&privk)`.
2. Extract `h1.signature`, parse the secp256k1 `(r, s, recid)`, compute `s' = n - s` and flip `recid`, and build a new `MessageSignature` bytes for h2 with the same fields as h1 but `signature = malleated`.
3. Assert `h1.check_recover_pubkey().unwrap() == h2.check_recover_pubkey().unwrap()` (both recover to same `Hash160`), and `h1 != h2` (struct/byte inequality) and `h1.block_hash() != h2.block_hash()`.
4. Serialize both into a `TransactionPayload::PoisonMicroblock(h1, h2)`, run `TransactionPayload::consensus_deserialize` and feed into the poison-handling path (`check_microblock_header_signer` / `will_admit_mempool_tx` / `handle_poison_microblock`).
5. Assert that the poison-check succeeds and the miner tied to h1's pubkey hash is penalized, despite the attacker never having possessed the miner's private key and the miner having broadcast only h1 — demonstrating the false-equivocation/mis-slashing.
