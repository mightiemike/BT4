### Title
Governance flag `supportUnfreezeDelay` enforced in `DelegateResourceActuator`/`UnDelegateResourceActuator` but not validated in the equivalent TVM native-contract paths (`DelegateResourceProcessor` / `UnDelegateResourceProcessor`) - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
This is the same bug class as the JOJO `JUSDBank._withdraw()` finding: a governance/state gate (`ReserveInfo.isDepositAllowed`) is checked on one entry path (`_deposit`) but not on a functionally equivalent alternate path (`_withdraw` with `isInternal=true`) that produces the same state effect. In java-tron, `DelegateResourceActuator.validate()` and `UnDelegateResourceActuator.validate()` (the normal broadcast-transaction path) both require `dynamicStore.supportUnfreezeDelay()` to be true before allowing resource delegation/undelegation: [1](#0-0) [2](#0-1) 

However, the equivalent logic reachable from a smart contract via the `DELEGATERESOURCE`/`UNDELEGATERESOURCE` TVM opcodes uses `DelegateResourceProcessor.validate()` and `UnDelegateResourceProcessor.validate()`, neither of which checks `supportUnfreezeDelay()` — they only check `dynamicStore.supportDR()`: [3](#0-2) [4](#0-3) 

These processors are invoked directly from `Program.delegateResource()` / `Program.unDelegateResource()`, which back the `DELEGATERESOURCE`/`UNDELEGATERESOURCE` opcodes gated only by `VMConfig.allowTvmFreezeV2()`: [5](#0-4) [6](#0-5) 

### Finding Description
`supportUnfreezeDelay` (backed by the `UNFREEZE_DELAY_DAYS` chain parameter, settable via committee proposal) and `allowTvmFreezeV2` (a separate hard-fork/proposal flag gating the TVM opcode enablement) are distinct governance switches. The normal-transaction actuators for `DelegateResourceContract`/`UnDelegateResourceContract` require both `supportDR()` and `supportUnfreezeDelay()` to be true — the latter is explicitly checked with the error message `"Not support Delegate/unDelegate resource transaction, need to be opened by the committee"`. This indicates `supportUnfreezeDelay` is intended as an independent kill-switch/feature-flag for the delegate/undelegate-resource capability, separate from whether the TVM opcode set is active.

The TVM opcode implementation of the same functionality (reachable from any deployed smart contract via `DELEGATERESOURCE`/`UNDELEGATERESOURCE`), however, is gated only by `allowTvmFreezeV2`, and its validate methods in `DelegateResourceProcessor`/`UnDelegateResourceProcessor` omit the `supportUnfreezeDelay()` check entirely. If the committee ever enables `allowTvmFreezeV2` (opcode support) while `supportUnfreezeDelay` (delegate/undelegate feature) remains disabled — a state explicitly anticipated by the actuators' distinct validation — a smart contract could still delegate/undelegate frozen-v2 resources via the TVM opcode path, bypassing the intended feature gate, exactly mirroring how JUSDBank's internal-withdraw path bypassed `isDepositAllowed`.

### Impact Explanation
If this configuration state (opcode enabled, feature flag disabled) occurs, contracts could perform resource delegation/undelegation that the committee intentionally disabled at the protocol level, undermining the governance control and potentially causing unintended resource-weight/vote-power accounting changes network-wide (affecting total bandwidth/energy weight, delegated balances) while the feature is supposed to be off. This is a protocol-level governance-bypass in the native-contract/actuator layer, reachable from any deployed smart contract.

### Likelihood Explanation
Likelihood is dependent on the committee's actual configuration/rollout order for `allowTvmFreezeV2` and `supportUnfreezeDelay` (i.e., whether these two proposals are always enabled together in practice by the maintainers, or the actuators' independent checks are dead code). I could not confirm from the indexed code the actual historical/production sequencing of these two proposals, nor whether `ConfigLoader`/`ProposalService` enforce the two flags to change atomically. If they are always toggled together in practice, the exploitable window is narrow or nonexistent; if not, this is directly triggerable by any user calling a trivial contract during the misconfigured window.

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check (with the same error semantics as the actuators) inside `DelegateResourceProcessor.validate()` and `UnDelegateResourceProcessor.validate()`, so the TVM opcode path enforces the identical governance gate as the standard transaction path.

### Proof of Concept
Conceptual (root-cause based, not independently executed):
1. Assume/verify a chain state where `allowTvmFreezeV2 == 1` (opcode enabled) but `supportUnfreezeDelay() == false` (feature disabled by committee, e.g. `UNFREEZE_DELAY_DAYS` unset/zero per `DynamicPropertiesStore`).
2. Deploy any contract that invokes the `DELEGATERESOURCE` opcode via `Program.delegateResource()`.
3. Because `DelegateResourceProcessor.validate()` only checks `supportDR()` and not `supportUnfreezeDelay()`, the call succeeds and resource delegation occurs, whereas a normal `DelegateResourceContract` transaction using `DelegateResourceActuator` would be rejected with "Not support Delegate resource transaction, need to be opened by the committee".
