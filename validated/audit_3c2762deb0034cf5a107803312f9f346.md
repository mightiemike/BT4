### Title
`tokenExchange` discards the verified session-token shop claim and trusts a separately supplied `shop` parameter without cross-validation - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Summary
The Solana report's root cause is that one instruction (`borrow_collateral`) records an account identifier while a second, related instruction (`repay_sol`) is validated independently against its own account identifier — with no check that the two identifiers refer to the same position. This lets an attacker satisfy the "collateral" flow using proof tied to one position while satisfying the "repay" flow using a completely different (already-repaid) position. The shopify-app-js analog is `tokenExchange()`, which cryptographically verifies a session token but throws away the verified claims, then uses a second, independently supplied `shop` argument for the entire rest of the flow (request URL and resulting `Session.shop`) without ever checking that the two match.

### Finding Description
`tokenExchange()` in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts` takes two logically-related but separately supplied inputs: `sessionToken` (a signed JWT whose `dest` claim cryptographically identifies the shop it was issued for) and `shop` (a plain string parameter supplied by the caller). The function verifies the JWT's signature/expiry via `decodeSessionToken`, but discards the decoded payload entirely: [1](#0-0) 

It then sanitizes and uses only the caller-supplied `shop` value — never the token's own `dest` — both to build the outbound `/admin/oauth/access_token` request and to stamp the resulting `Session.shop`: [2](#0-1) 

This is structurally identical to the Solana bug: the library validates one artifact ("does this session token have a valid signature?") but never checks that it corresponds to the *other* artifact ("is `shop` the same shop the token claims to represent?"). All in-repo call sites happen to construct `shop` from the JWT's own `dest`/`aud` claims first (see `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts` and the Remix/React Router `TokenExchangeStrategy`): [3](#0-2) [4](#0-3) 

But `shopify.auth.tokenExchange()` is a public, documented API (`TokenExchangeParams` explicitly separates `shop` and `sessionToken` as independent fields), so any integrator who builds `shop` from a different source than the token itself (e.g., `req.query.shop`, a stored merchant record, or a separate header) bypasses any binding between the two. The library provides no defense-in-depth check to prevent this class of mistake, unlike `oauth.ts`'s `callback()` flow, which explicitly cross-validates the `state` nonce against the cookie via `safeCompare` before trusting the query (`validQuery`): [5](#0-4) 

### Impact Explanation
If an integration supplies `shop` from an untrusted/independent source rather than deriving it from the verified session token, the library will submit the code-exchange request to the attacker-chosen shop's domain while presenting a session token that was actually issued for a different shop, and — assuming the request succeeds — will label/store the resulting access token under the attacker-chosen shop's session ID (`getOfflineId(shop)` / `getJwtSessionId(shop, sub)`). This is a cross-tenant session-storage confusion: a valid credential minted for shop A could end up filed under shop B's session key, or vice versa, corrupting `sessionStorage` entries across tenants for apps that don't already enforce the shop/token binding themselves.

### Likelihood Explanation
Moderate-to-low. Exploitability ultimately depends on whether Shopify's `/admin/oauth/access_token` token-exchange endpoint independently rejects a `subject_token` whose issuer/`dest` does not match the shop domain in the request URL — server-side behavior that is outside this repository and that I could not verify. Within this codebase, the vulnerability is real as a missing defense-in-depth/instruction-cross-validation control: the library itself performs no binding check, and its public API shape (`{shop, sessionToken}` as independent parameters, with the decoded payload thrown away) actively invites exactly the kind of caller mistake the original Solana report demonstrates (using verified data from one context to authorize an action in a mismatched context).

### Recommendation
After decoding the session token, compare its `dest`/`iss` claim against the caller-supplied `shop` (case/scheme-normalized) and throw an `InvalidJwtError`/`InvalidShopError` on mismatch, mirroring the `safeCompare(query.state!, stateFromCookie)` pattern already used in `oauth.ts`. At minimum, derive `shop` internally from the verified payload rather than accepting it as a separate, uncorrelated parameter.

### Proof of Concept
Conceptual (cannot be executed against the live Shopify backend from this analysis):
```ts
// Attacker has a valid session token for "attacker-shop.myshopify.com"
// but supplies a different, victim shop as the `shop` parameter.
await shopify.auth.tokenExchange({
  shop: 'victim-shop.myshopify.com',      // untrusted, caller-supplied
  sessionToken: attackerShopSessionToken, // cryptographically valid, but for a different shop
  requestedTokenType: RequestedTokenType.OfflineAccessToken,
});
// token-exchange.ts never checks that decodeSessionToken(sessionToken).dest === shop,
// so the request is sent to https://victim-shop.myshopify.com/admin/oauth/access_token
// and, if it succeeds, the resulting Session is stamped with shop: 'victim-shop.myshopify.com'.

export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };
