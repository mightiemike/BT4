### Title
Sandwich-able spot-price swap quote lets an attacker steal value from gas-abstraction auto-swap deposits - (File: x/uexecutor/keeper/execute_inbound_gas.go)

### Summary
The external report's bug class is: a payout that is computed from mutable, time/state-dependent pricing at execution time, with no user-supplied minimum-payout guarantee, lets an attacker manipulate that state just before the victim's transaction lands to reduce the payout the victim actually receives. Push Chain's gas-abstraction "auto-swap" path in `x/uexecutor` reproduces this exact pattern: it fetches a spot swap quote from an on-chain Uniswap-style pool and then executes the swap with a fixed 5% slippage tolerance that the depositing user never chose and cannot protect against.

### Finding Description
When an inbound deposit needs gas-token conversion, `ExecuteInboundGas` (and the analogous `gasAndPayloadDepositAutoSwap` in `execute_inbound_gas_and_payload.go`) does the following, atomically inside a single Cosmos message handler execution (`MsgVoteInbound` finalization by a Universal Validator): [1](#0-0) 

1. `GetSwapQuote` performs a **live/spot** call to `QuoterV2.quoteExactInputSingle` on the UniversalCore Uniswap-style pool to get the current expected output amount. [2](#0-1) 
2. A minimum-out value is derived with a **hardcoded** 5% slippage buffer: `minPCOut := quote * 95 / 100`. [3](#0-2) 
3. `CallPRC20DepositAutoSwap` then executes the actual swap on-chain using that `minPCOut`. [4](#0-3) 

Because the quote is read from **spot pool reserves** rather than a manipulation-resistant price (e.g., TWAP) and the slippage tolerance is a fixed, protocol-chosen 5% rather than a value the depositing end-user can express, this is structurally the same weakness as the bond's decaying price: the "payout" (PC/WPC the depositor's PRC20 gets swapped into) depends on pool state that is *cheap to move* between the moment the quote is computed and the swap executes.

An unprivileged attacker who watches the mempool/pending `MsgVoteInbound` transactions that will trigger this auto-swap path (or simply trades opportunistically around Universal Validator vote-finalization blocks) can:
- Push the PRC20/WPC pool price in the direction that lowers the quote used for the victim's swap (front-run) before the finalizing vote lands, executing the swap through the low `minPCOut` bound.
- Immediately reverse the trade afterward (back-run), extracting the ~5% (bounded by the fixed slippage tolerance) as arbitrage profit paid for by the depositor's converted funds — a classic sandwich attack.

This is essentially the exact bug class described in the report: "the bond's payout is reduced for future purchases based on time/state that has passed," exploitable "to front-run a deposit/purchase tx and lower the victim's payout," with the same recommended fix (a caller-specified minimum payout) missing here — the minimum is hardcoded by the protocol, not chosen by the party whose funds are at risk.

### Impact Explanation
The victim (whoever's inbound deposit triggers gas-abstraction auto-swap) receives fewer PC/WPC tokens than the fair, unmanipulated market price would produce — up to the full 5% slippage tolerance per swap, extracted by the attacker. This is a direct, repeatable value-extraction against protocol/user-controlled funds routed through `depositPRC20WithAutoSwap`, satisfying the in-scope impact "corruption of PRC20 or native asset accounting" / unauthorized value drain from the deposit-and-swap flow. Because every inbound-gas deposit that needs conversion goes through this path, the attack is repeatable per inbound event, not a one-off.

### Likelihood Explanation
Likelihood is high for chains/pools with modest liquidity: the trigger event (an inbound observation reaching quorum, causing `ExecuteInboundGas`/`gasAndPayloadDepositAutoSwap` to run) is publicly observable ahead of time via pending `MsgVoteInbound` transactions in the mempool from Universal Validators, and the attack requires no privileged role — only capital to move the pool price within the 5% band and gas to trade on the same underlying Uniswap-style pool that PRC20/WPC pricing depends on. No governance/admin/validator compromise is needed; the attacker is a purely external, unprivileged actor exploiting the deterministic execution of a public flow.

### Recommendation
- Replace the spot `quoteExactInputSingle` call with a TWAP or otherwise manipulation-resistant price oracle for computing `minPCOut`.
- Reduce the fixed 5% slippage tolerance, and/or make it configurable per-token via governance-set risk parameters rather than a single hardcoded constant shared by `ExecuteInboundGas`, `gasAndPayloadDepositAutoSwap`, and the `refundUnusedGas` swap-back path.
- Where feasible, let inbound depositors (or the observed gateway event) carry an explicit acceptable-slippage/minimum-output parameter that is verified against, so users bear (and consent to) their own risk rather than a protocol-wide default that an attacker can reliably extract.
- Consider batching/atomicity techniques (e.g., committing the quote fetch and swap in the same EVM sub-call rather than round-tripping through separate `CallEVM`/`DerivedEVMCall` invocations) to shrink the window an attacker has to react, combined with the oracle fix above.

### Proof of Concept
Conceptual (no live-network PoC was run; this is inferred from code reachability and matches the reported bug class):
1. Attacker monitors the Push Chain mempool for a `MsgVoteInbound` that will finalize an inbound ballot requiring gas-abstraction auto-swap (visible because it is a normal user-submitted vote tx from a Universal Validator, and inbound observation data is public).
2. Immediately before that tx is included, attacker submits a large swap trade against the PRC20/WPC Uniswap-style pool referenced by `GetUniversalCoreQuoterAddress`/`GetSwapQuote`, moving the spot price down within the tolerance the 5% slippage buffer allows.
3. The finalizing tx executes `ExecuteInboundGas` → `GetSwapQuote` (now reads the manipulated price) → computes `minPCOut = quote*95/100` → `CallPRC20DepositAutoSwap` executes at the worse price. [5](#0-4) 
4. Attacker immediately reverses their trade in a follow-up transaction, restoring the pool price and pocketing the difference extracted from the victim's swap.

Verification of this path would require a testnet/mempool-level PoC against a live PRC20/WPC pool, which is out of scope for static code review; the above traces the exact code path and demonstrates the missing user-specified minimum-payout protection matches the report's root cause.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil

// Calls Handler Contract to deposit prc20 tokens with auto-swap.
// fee and minPCOut must be pre-computed by the caller (see GetDefaultFeeTierForToken / GetSwapQuote).
func (k Keeper) CallPRC20DepositAutoSwap(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount, fee, minPCOut *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: depositPRC20WithAutoSwap",
		"prc20", prc20Address.Hex(),
		"recipient", to.Hex(),
		"amount", amount.String(),
		"fee", fee.String(),
		"min_pc_out", minPCOut.String(),
	)
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // who is sending the transaction
		handlerAddr,        // destination: Handler contract
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20WithAutoSwap",
		prc20Address,
		amount,
		to,
		fee,
		minPCOut,
		big.NewInt(0), // deadline = 0 → contract uses its default
	)
}
