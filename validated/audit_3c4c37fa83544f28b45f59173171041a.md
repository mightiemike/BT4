### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay-verify tooling to accept a diverged state root — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a freshly re-executed transaction produces the exact same result as the transaction info that was actually committed to the accumulator on-chain. The function checks status, gas used, write-set hash, and event root hash, but it deliberately does not check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents as unresolved.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates only:
- transaction status vs `txn_info.status()`
- `gas_used()` vs `txn_info.gas_used()`
- write-set hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()`

It explicitly omits validating the state checkpoint hash, hot-state checkpoint hash, and the newer position-state checkpoint hash fields carried in `TransactionInfoV1` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`), as flagged by the inline TODO: [2](#0-1) 

These checkpoint hashes are exactly the fields that bind a `TransactionInfo` to the authenticated state-tree root produced by execution (see `assemble_transaction_infos` in the executor, which folds `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` into the `TransactionInfo` that is hashed into the accumulator): [3](#0-2) .

This comparator is consumed by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes backed-up transactions and calls `ensure_match_transaction_info` to decide pass/fail for each replayed transaction: [4](#0-3) . Because the comparator never inspects the checkpoint-hash fields, a divergence in the locally-computed state/hot-state/position-state Merkle root relative to the archived, signature-authenticated `TransactionInfo` will not be detected — the tool will report a clean replay-verify pass even though the authenticated state root diverges from local execution.

### Impact Explanation
This breaks a core proof/commitment invariant this scan targets: an authenticated proof-bearing artifact (the accumulator-committed `TransactionInfo`, which embeds the state-checkpoint root) can silently diverge from the actual re-executed state without detection by the tooling designed to catch exactly this class of divergence. In an upgrade/hard-fork or execution-change scenario (e.g., framework upgrade, VM semantics change, storage schema change), a state-root divergence introduced by a bug would not surface through `replay-verify`/`db-tool replay-on-archive`, undermining the safety net operators rely on to detect state-committing regressions before or after mainnet rollout.

### Likelihood Explanation
The gap is deterministic and always present whenever the checkpoint-hash-carrying code path (`COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `TransactionInfoV1` position-state checkpoints) is in use, since the comparator never exercises those fields regardless of input. It requires a separate root-cause bug (an actual state-checkpoint divergence) to become impactful, but the detection blind spot itself is unconditional and confirmed by the code's own TODO comment, not speculative.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields on the expected `TransactionInfo` (when present for the transaction's variant), consistent with the TODO already left in the code, before relying on `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or shipping replay-verify results as a correctness signal.

### Proof of Concept
Not applicable as a standalone exploit — this is a detection-gap finding validated purely from source: `ensure_match_transaction_info`'s field list at [5](#0-4)  omits the three checkpoint-hash fields that `TransactionInfo` builders populate at commit time [3](#0-2) , and `replay_on_archive.rs` relies solely on this comparator to certify a replay as verified [6](#0-5) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
