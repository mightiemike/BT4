### Title
Committee-controlled `ALLOW_MARKET_TRANSACTION` switch can be disabled while open TRC10 market orders exist, permanently freezing escrowed trader funds - (File: `actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java`)

### Summary
The java-tron TRC10 exchange (`MarketSellAssetActuator` / `MarketCancelOrderActuator`) is globally gated by the dynamic parameter `ALLOW_MARKET_TRANSACTION`, which is toggled through the committee proposal mechanism (`ProposalUtil`/`ProposalService`). When a trader places a sell order via `MarketSellAssetActuator`, their sell-token balance is immediately debited and escrowed as an open order in `MarketOrderStore`/`MarketPairPriceToOrderStore`. The only way to reclaim that escrowed balance is `MarketCancelOrderActuator`, whose `validate()` unconditionally checks `dynamicStore.supportAllowMarketTransaction()` before allowing the cancellation, exactly as it also gates new order creation. There is no check for outstanding/open orders before this global switch can be flipped off, and no fallback path exists to let users cancel orders once the feature is disabled.

### Finding Description
`MarketCancelOrderActuator.validate()` requires the feature flag to be enabled before a user can cancel their own order and get their escrowed sell-token quantity back: [1](#0-0) 

This mirrors the exact same gating logic used for placing new orders in `MarketSellAssetActuator`, both keyed off the single dynamic property `ALLOW_MARKET_TRANSACTION`: [2](#0-1) 

That property is a committee-governed parameter that can be flipped through the standard proposal-approval flow (`ProposalUtil`/`ProposalService`), analogous to the "protocol operator" role in the original report: [3](#0-2) 

Crucially, the code that flips `ALLOW_MARKET_TRANSACTION` off performs no check on whether the `MarketOrderStore` currently holds any active (non-`CANCELED`, non-fully-filled) orders. Since `MarketCancelOrderActuator` uses the very same flag to gate cancellation, disabling the flag while a trader has an open order (created earlier via `MarketSellAssetActuator`, which already debited their sell-token balance) makes that trader's escrowed funds permanently unrecoverable through the normal user-facing path: they cannot cancel (blocked by the flag) and cannot get the order matched either, since the same flag also blocks any new incoming `MarketSellAssetContract` that could match against it.

### Impact Explanation
This is a direct funds-lock/accounting-divergence bug that affects unprivileged traders, not the governance actors: once `ALLOW_MARKET_TRANSACTION` is disabled while open orders exist, the trader's already-debited sell-token balance is stuck in escrow in `MarketOrderStore` with no callable path to reclaim it (`MarketCancelOrderActuator` reverts with "Not support Market Transaction, need to be opened by the committee"), while the order remains listed in `MarketPairToPriceStore`/`MarketPairPriceToOrderStore`. This is the same bug class as the original report: a global operator-controlled switch disables the only exit path for a market with open user positions/orders, leaving affected users unable to recover value they've already committed to the protocol.

### Likelihood Explanation
`ALLOW_MARKET_TRANSACTION` is a standard chain parameter changeable via the committee proposal process that already exists in mainnet java-tron (it was introduced to be able to turn the TRC10 market feature on/off). Any time community governance decides to disable the market feature (e.g., due to a bug or economic decision) while users hold open orders, this freeze occurs automatically as a side effect of the existing code path — no exploit or malicious actor is required beyond normal governance operation, and the check ordering in both actuators guarantees the freeze whenever this occurs.

### Recommendation
Either:
1. Always allow `MarketCancelOrderActuator` to succeed (returning escrowed sell-token balances) regardless of the state of `ALLOW_MARKET_TRANSACTION`, so users can always exit their own open orders, or
2. Before permitting a proposal to disable `ALLOW_MARKET_TRANSACTION`, verify (or require prior cleanup of) any outstanding entries in `MarketOrderStore`/`MarketPairPriceToOrderStore`, or provide a distinct governance switch specifically for order creation vs. order cancellation so cancellation is never blocked.

### Proof of Concept
1. Trader A calls `MarketSellAssetContract` (handled by `MarketSellAssetActuator`) to sell TokenX for TokenY, creating an active order; TokenX is deducted from A's balance and held in escrow. [4](#0-3) 
2. The committee passes a proposal setting `ALLOW_MARKET_TRANSACTION` to `0` (feature disabled) — no check is performed for existing open orders in `MarketOrderStore`.
3. Trader A attempts to call `MarketCancelOrderContract` to cancel the still-active order and recover their TokenX. `MarketCancelOrderActuator.validate()` immediately reverts with `"Not support Market Transaction, need to be opened by the committee"`. [1](#0-0) 
4. Because new `MarketSellAssetContract`s are blocked by the same flag, no counter-order can arrive to match and settle A's order either, leaving A's TokenX permanently locked in the exchange escrow with no recourse until/unless the committee re-enables the flag (at which point the market state, and A's original economic intent, may have become stale or unfavorable).
