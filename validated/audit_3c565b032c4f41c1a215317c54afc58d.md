## Finding

### Title
Missing fee-sufficiency check for L1Handler transactions allows executing under-priced messages - (File: `crates/blockifier/src/transaction/l1_handler_transaction.rs`)

### Summary
The analog of the "swap with `amountOutMinimum = 0`" bug class is the fee-sufficiency check performed when the sequencer executes an `L1HandlerTransaction`. Instead of verifying that the fee paid on L1 (`paid_fee_on_l1`) actually covers the fee computed from the transaction's real L2 execution cost (`receipt.fee`), the sequencer only checks that the paid fee is non-zero, effectively disabling the intended economic protection the same way `amountOutMinimum = 0` disables slippage protection in the reported Uniswap swap.

### Finding Description
`L1HandlerTransaction::execute_raw` computes a `TransactionReceipt` (including `receipt.fee`, the actual cost of running the L1-to-L2 message handler) and then performs what is supposed to be a fee-sufficiency check: [1](#0-0) 

The check is:
```rust
let paid_fee = self.paid_fee_on_l1;
// For now, assert only that any amount of fee was paid.
// The error message still indicates the required fee.
if paid_fee == Fee(0) {
    return Err(... InsufficientFee { paid_fee, actual_fee: receipt.fee } ...);
}
```
The error type is `TransactionFeeError::InsufficientFee { paid_fee, actual_fee }`, whose documented meaning is "Actual fee exceeded paid fee on L1", implying the intended semantics is `paid_fee >= actual_fee`. However, the implementation only rejects the transaction when `paid_fee == 0`, i.e., any strictly positive `paid_fee_on_l1` (as small as `1`) passes regardless of how large `receipt.fee` (the real computed cost) is.

Unlike ordinary account transactions, L1Handler transactions do not perform any on-chain fee transfer to cover the discrepancy — `fee_transfer_call_info` is unconditionally `None` for L1Handler execution: [2](#0-1) 

So there is no mechanism to claw back the difference between `paid_fee_on_l1` and the true `receipt.fee` computed at execution time. The `paid_fee_on_l1` is fixed by the L1 message sender at the time the message is sent to L1 (at whatever L1/L2 gas price prevailed then), while `receipt.fee` is computed using the sequencer's *current* L2 gas price at execution time, which can rise substantially due to the EIP-1559-style dynamic fee market (`calculate_next_base_gas_price` in `crates/apollo_consensus_orchestrator/src/fee_market/mod.rs`), driven by ordinary network congestion or by an attacker deliberately filling blocks to push `l2_gas_used` above `gas_target`.

An unprivileged L1 message sender can therefore submit a message to L2 while committing to pay only a negligible `paid_fee_on_l1` (e.g., `1`), and later, when the L2 gas price has risen (either organically or via self-induced congestion), the sequencer will still execute and commit the L1Handler transaction (bounded only by `l1_handler_max_amount_bounds`) without recovering the true cost of the consumed L2 resources.

### Impact Explanation
This causes a concrete economic loss for the network/proposer: the sequencer performs real computational and state-diff work (bounded by `l1_handler_max_amount_bounds`, which can be sizable — e.g., 10,000,000,000 gas units per resource in some versioned constants) while collecting essentially no compensating fee, since the on-L1 payment can be arbitrarily small and there is no on-L2 fee transfer to make up the difference. This degrades the resource/fee accounting invariant that transaction fees should cover the resources consumed, analogous to the reported swap executing at an attacker-favorable price because the minimum-output/minimum-payment protection was effectively disabled.

### Likelihood Explanation
Reachable by any L1 sender submitting a message to L2 (i.e., an unprivileged, permissionless action) — no special privileges are required. The condition needed (L2 gas price rising between message submission and L2 execution) is a routine occurrence given the dynamic fee market, and can also be amplified by an attacker who fills blocks to push `l2_gas_used` above `gas_target`, directly increasing `calculate_next_base_gas_price` output for subsequent blocks.

### Recommendation
Change the L1Handler fee check in `crates/blockifier/src/transaction/l1_handler_transaction.rs` to require `paid_fee_on_l1 >= receipt.fee` (matching the documented semantics of `TransactionFeeError::InsufficientFee`) rather than merely `paid_fee_on_l1 != 0`, and revert/reject the L1Handler transaction (or, per protocol design, defer/skip inclusion) when the L1-paid fee does not cover the actual computed L2 execution cost.

### Proof of Concept
1. An L1 sender sends a message to L2 (`LogMessageToL2`) paying a minimal `paid_fee_on_l1` (e.g., `Fee(1)`).
2. Before the corresponding `L1HandlerTransaction` is included and executed on L2, the L2 gas price rises (naturally, or via an attacker submitting congestion transactions in prior blocks to push `l2_gas_used` above `gas_target`, per `calculate_next_base_gas_price`).
3. When the sequencer executes the queued L1Handler transaction, `receipt.fee` (computed from actual gas consumed at the now-higher L2 gas price) is far larger than `paid_fee_on_l1 = 1`.
4. The check at [3](#0-2)  only tests `paid_fee == Fee(0)`, which is false, so the transaction is committed and reported as successful with no fee shortfall enforcement, despite the sequencer having covered execution cost far exceeding what was paid on L1.
