## Analysis

`StateComputeResult::extension_proof()` builds the `AccumulatorExtensionProof` from `self.ledger_update_output.transaction_accumulator` (frozen subtree roots + leaf count) and `self.transaction_info_hashes()` (the leaves to append): [1](#0-0) 

`LedgerUpdateOutput` explicitly carries **two distinct accumulators**: `transaction_accumulator` and `parent_accumulator`, populated separately by the builder: [2](#0-1) 

`transaction_accumulator` is the resulting (post-block) accumulator — this is exactly what `StateComputeResult::root_hash()` returns as "the root hash of this compute result" (i.e., the block's own executed state id): [3](#0-2) 

`parent_accumulator` is the pre-block accumulator; it is used correctly elsewhere, e.g. `first_version()` derives the first version of the chunk from `parent_accumulator.num_leaves`: [4](#0-3) 

The semantics of `AccumulatorExtensionProof` require `frozen_subtree_roots`/`num_leaves` to describe the accumulator **before** the new leaves are appended, so that `verify(original_root)` reconstructs the accumulator matching `original_root` and then appends `leaves` to yield the new (post-block) tree: [5](#0-4) 

This is confirmed by how the proof is consumed by consensus/safety-rules: `parent.accumulator_extension_proof().verify(parent.block().quorum_cert().certified_block().executed_state_id())` — the proof for a given block is verified against the **certified (pre-block/parent) root**, and only after appending the block's own leaves does it yield that block's resulting tree (whose `frozen_subtree_roots()`/`num_leaves()` are then used to build the *next* block's proof): [6](#0-5) 

## Finding

`extension_proof()` sources `frozen_subtree_roots`/`num_leaves` from `transaction_accumulator` (the **post-block** accumulator, same one that yields `root_hash()`) instead of from `parent_accumulator` (the correct **pre-block** accumulator), while still appending `transaction_info_hashes()` — the current block's own leaves — on top of it. Because `parent_accumulator` exists specifically to hold the pre-block state and is used correctly elsewhere in the same file, this appears to be a field-selection mismatch in `extension_proof()`.

Consequence: for `AccumulatorExtensionProof::verify(original_root)` to satisfy `original_tree.root_hash() == original_root`, `original_root` would have to equal the block's *own* resulting root_hash (not its parent's certified root, as safety-rules expects) — and the tree it then returns is produced by re-appending the block's own transaction-info hashes a second time on top of the already-finalized accumulator. Any successful use of this malformed proof would bind an accumulator state that does not correspond to any transaction application that ever actually occurred in the VM/executor pipeline, decoupling the proof handed to consensus for commit certification from the real ledger history. Any block containing at least one committed transaction — including transactions supplied entirely by unprivileged senders — exercises this code path, since the mismatch is unconditional and does not depend on any special transaction content.

I could not fully confirm the internal wiring of `execution/executor/src/workflow/do_ledger_update.rs` (its content did not load within the available tool budget), which is the code that actually populates `transaction_accumulator` vs. `parent_accumulator` in `LedgerUpdateOutput::new`. The conclusion above rests on the field documentation/usage inferred from `root_hash()` and `first_version()` semantics rather than a direct read of that builder call. I recommend a Devin session read that file directly and add a unit test constructing `extension_proof()` and asserting `AccumulatorExtensionProof::verify` against the real parent root (as in `test_utils.rs`) to conclusively confirm or refute the mismatch before treating this as confirmed.

### Title
Possible wrong accumulator source in `StateComputeResult::extension_proof` (post-block accumulator used instead of parent) - (File: execution/executor-types/src/state_compute_result.rs)

### Summary
`extension_proof()` builds its `AccumulatorExtensionProof` "original tree" component from `ledger_update_output.transaction_accumulator` (the resulting, post-block accumulator that also backs `root_hash()`) rather than from `ledger_update_output.parent_accumulator` (the pre-block accumulator), while still appending the block's own `transaction_info_hashes()` on top.

### Finding Description
`AccumulatorExtensionProof::verify` reconstructs an "original" accumulator from the supplied `frozen_subtree_roots`/`num_leaves`, checks its root against a caller-supplied expected root, then appends `leaves` to compute the extended tree. Consensus (`safety-rules`) verifies a block's `accumulator_extension_proof()` against the *parent's* certified `executed_state_id()`, expecting the extension proof's base accumulator to be the parent (pre-block) state. `LedgerUpdateOutput` maintains a dedicated `parent_accumulator` field for exactly this purpose, used correctly by `first_version()`. `extension_proof()`, however, reads `frozen_subtree_roots`/`num_leaves` from `transaction_accumulator` — which is the same accumulator that backs `root_hash()`, i.e., the block's own resulting/post-block state — not `parent_accumulator`.

### Impact Explanation
If confirmed, this would decouple the extension proof handed to consensus for commit certification from the block's real, VM-computed transaction sequence, since the "base" of the proof would already include the block's own leaves before they are appended a second time. This could manifest either as verification failures against the true parent root (blocking legitimate commit certification) or, if some caller supplies the block's own root as the expected root, as a proof that appears to verify while representing a nonexistent ledger state.

### Likelihood Explanation
The mismatch, if real, is unconditional and triggers on any committed block with transactions — no special crafted transaction content is required, only inclusion of at least one transaction in a block, which unprivileged senders control by default.

### Recommendation
Have a Devin session inspect `execution/executor/src/workflow/do_ledger_update.rs` to confirm whether `transaction_accumulator` is indeed populated as the post-block accumulator and `parent_accumulator` as the pre-block one, then, if confirmed, change `StateComputeResult::extension_proof()` to source `frozen_subtree_roots`/`num_leaves` from `self.ledger_update_output.parent_accumulator` instead of `self.ledger_update_output.transaction_accumulator`. Add a regression test that builds a `StateComputeResult` for a non-trivial block and asserts `extension_proof().verify(parent_root_hash)` succeeds and its resulting root equals `state_compute_result.root_hash()`.

### Proof of Concept
Conceptual reproduction (to be executed/confirmed in a real session): construct a `StateComputeResult` for a block with one or more transactions via the normal executor pipeline (`ApplyExecutionOutput::run`), capture the parent's root hash (`base_view.transaction_accumulator.root_hash`), call `state_compute_result.extension_proof()`, and call `.verify(parent_root_hash)`. If the mismatch is real, this will fail the internal root-hash equality check inside `AccumulatorExtensionProof::verify` [7](#0-6) , or produce a resulting tree whose root differs from `state_compute_result.root_hash()`.
