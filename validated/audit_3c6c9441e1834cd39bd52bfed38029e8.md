Analysis of `AccountsDb::hash_account_helper` (`accounts-db/src/accounts_db.rs:4176-4209`):

The hashed byte stream is `lamports(8 bytes) || data(n bytes) || executable(1 byte) || owner(32 bytes) || pubkey(32 bytes)`, whether the data path takes the "large" branch (`data.len() > DATA_SIZE`, hashed via a separate `hasher.update(data)` call) or the "small" branch (data copied into the stack `SmallVec` buffer). blake3 is a streaming hash, so splitting `update()` calls at the `DATA_SIZE`(200)/`META_SIZE`(73) boundary does not change the resulting hash for a given logical byte sequence — this is confirmed by `test_hash_stored_account` at [1](#0-0)  which asserts the `StoredAccountInfo`-based and `AccountSharedData`-based hashing paths agree.

Regarding the collision premise: every field in the hashed message except `data` has a **fixed** byte length (lamports = 8, executable = 1, owner = 32, pubkey = 32), as seen in the `META_SIZE` constant definition at [2](#0-1) . Because only one field (`data`) is variable-length and all others are fixed-length and always appended in the same fixed order, the total message length is `8 + n + 1 + 32 + 32`, which uniquely determines `n = data.len()`. Consequently:

- Two accounts with different `data.len()` produce messages of different total length, so they cannot produce an identical byte string to hash.
- Two accounts with the same `data.len()` but different `data`, `owner`, `executable`, or `pubkey` produce byte strings that differ at some fixed position (since the field boundaries are pinned once `n` is fixed) — there is no way for `data`'s trailing bytes to be reinterpreted as part of `owner`/`pubkey`, because `owner()` and the `pubkey` argument are read directly from the account/key objects and appended verbatim, not parsed out of the `data` buffer.

This means the encoding is injective with respect to `(lamports, data, executable, owner, pubkey)` — there is no field-boundary ambiguity of the kind that plagues naive concatenation of *multiple* variable-length fields. The only way `hash_account_helper` could produce identical output for two accounts with differing observable state is an actual blake3 collision, which is a break of the underlying cryptographic hash function itself (out of scope per `SECURITY.md`'s exclusion of dependencies/cryptographic primitives).

The `DATA_SIZE`/`META_SIZE` = 200/73-byte constants only affect which code path is used to feed bytes into the streaming hasher (stack buffer vs. direct `data` slice), not the semantic content being hashed, so there is no exploitable boundary effect there either.
