Based on my investigation, I found a plausible analog: an unvalidated, attacker/contract-controlled length field is used to size a `Vec` allocation before that length is checked against actual backing memory or charged for in gas — the same "trust the header, allocate before validating" pattern as the Cloudreve pixel-bomb.

### Title
Unbounded allocation from attacker-controlled array length in deprecated (Cairo 0) syscall argument parsing causes sequencer OOM crash - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The Cairo 0 ("deprecated") syscall argument reader `read_felt_array` takes an `array_size` felt value straight from VM memory — a value fully controlled by the executing contract's own bytecode — converts it to a `usize`, and immediately passes it to `felt_range_from_ptr`, which calls the VM's range-read API to materialize a `Vec<Felt>` of that length, before any gas charge or size bound is applied to the value.

### Finding Description
`read_felt_array` in the deprecated syscall hint processor reads the `array_size` felt operand of a Cairo 0 syscall (e.g. the `calldata_size` argument of `library_call`/`call_contract`/`storage` array syscalls, or the `keys_len`/`data_len` in `emit_event`) directly from VM memory and converts it via `usize::try_from`, with no upper bound check: [1](#0-0) 

That size is handed to `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)` — the cairo-vm API that allocates a `Vec` sized to `size` before validating that the underlying segment actually contains that many populated cells: [2](#0-1) 

This is invoked unconditionally from `read_calldata`/`read_call_params`, used by every deprecated syscall that carries a calldata/array argument: [3](#0-2) 

Crucially, this parsing happens as part of *reading the syscall request*, which occurs before the syscall's linear (calldata-length-proportional) gas cost is computed and charged — the linear factor is derived from `calldata.0.len()` only *after* the array has already been fully read/allocated: [4](#0-3) 

Because `array_size` is just a felt value the Cairo 0 contract's own code writes into its memory (e.g. via a single `[ap] = <huge constant>` instruction) before invoking a syscall such as `library_call`, an attacker can construct a Cairo 0 contract whose entry point costs almost nothing in steps but declares an astronomically large `calldata_size`/`data_len`/`keys_len`. This is exactly analogous to the Cloudreve bug: a compressed representation (tiny bytecode / tiny PNG header) declares an enormous decoded size (huge array length / huge pixel dimensions), and the runtime allocates a buffer sized directly from that untrusted value before validating it against real backing data or bounding it against a sane limit, i.e. `Vec::with_capacity`/equivalent triggered by an attacker-declared size rather than actual content size.

### Impact Explanation
`Vec`/buffer allocation failures for very large requested capacities in Rust abort the process via `handle_alloc_error` (not a catchable panic in the general case), or the allocation succeeds and then the kernel OOM-killer terminates the process under memory pressure — in both cases this is a fatal, unrecoverable termination of the executing node process, not a normal `Result::Err`. Since this code path runs inside contract execution in the blockifier (used by the gateway for validation/simulation and by the sequencer for block building), a single transaction invoking a vulnerable Cairo 0 contract can crash the sequencer process handling it, halting block production and transaction confirmation for the network — a full availability loss reachable from a single unprivileged submitted transaction.

### Likelihood Explanation
Reachability requires only an ordinary `INVOKE` transaction targeting a deployed Cairo 0 class whose entry point performs a syscall (e.g. `library_call`, `emit_event`) with a size operand the contract computes internally (a hardcoded or attacker-supplied huge constant costs O(1) VM steps to write). No special privilege, no declare of new classes, and no interaction with mempool/p2p/proposer roles is needed — this is squarely in the "single submitted transaction → blockifier execution → syscalls" path explicitly in scope.

### Recommendation
Bound `array_size`/`data_len`/`keys_len` (and any other length read from VM memory before use as an allocation size) against a hard configured maximum (e.g. `SIERRA_ARRAY_LEN_BOUND`/`max_calldata_length`-style limits already used elsewhere in the codebase) *before* calling into `felt_range_from_ptr`/`get_integer_range`, and/or charge the syscall's linear gas cost for the declared size prior to performing the read so an attacker cannot get a "free" oversized allocation attempt. Consider validating the declared size against the actual known segment size (which cairo-vm can report) before allocating.

### Proof of Concept
1. Author a Cairo 0 contract whose external entry point writes a large constant (e.g. `2**40`) into the `calldata_size` operand slot for a `library_call` syscall invocation, with a real (small) `calldata` pointer.
2. Deploy this Cairo 0 class and an instance of it (Cairo 0 classes remain invocable wherever already deployed/whitelisted).
3. Submit a single `INVOKE` transaction calling that entry point.
4. During execution, `read_calldata` → `read_felt_array` → `felt_range_from_ptr` → `vm.get_integer_range` attempts to allocate a `Vec<Felt>` of `2**40` elements (32 bytes each, ~32 TB) before validating the request against actual memory content or charging gas for it, aborting/crashing the executing sequencer/gateway process. pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
```rust
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
```

```rust
pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
```
