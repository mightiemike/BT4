### Title
Single-transaction chain liquidation via `liquidate-multi` re-resolving egroup/health per entry allows over-liquidation beyond the intended cap - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` executes several independent `liquidate` calls against the same borrower inside one atomic transaction via `(map call-liquidate positions)`. Each entry in the list re-derives the borrower's mask, egroup, LTV thresholds and health status from state that has already been mutated by the previous entries in the same `map`. Because Zest prices risk per asset-combination (egroup bitmask) rather than per individual collateral factor, fully draining one collateral asset in an early entry can shift the borrower into a different, laxer egroup for the remaining entries, letting a single liquidator extract more collateral from the same borrower in one transaction than any single, atomically-evaluated health check would permit.

### Finding Description
`liquidate` computes `current-ltv`, resolves the position's `mask`/`egroup`, and derives `ltv-liq-partial`/`ltv-liq-full`/penalty parameters fresh on every call: [1](#0-0) 

The graduated liquidation factor is capped per-call at `BPS` using the mask's own thresholds: [2](#0-1) 

`liquidate-multi` runs multiple such calls, one per list entry, in a single transaction, and explicitly does not revert the whole batch if one entry fails: [3](#0-2) 

Egroup resolution is bitmask-based and selects the most-specific (smallest-superset) match for whatever collateral/debt combination the borrower currently holds: [4](#0-3) 

The protocol's own tests confirm that removing a collateral asset type (moving from a multi-asset "superset" mask to a smaller "subset" mask) causes resolution to switch to a *different* egroup with a *higher* (less conservative) LTV — this is presented as intended behavior: [5](#0-4) 

Crucially, this "future capacity must not decrease" safety check exists only in `collateral-add` (to protect *depositors* changing their own mask): [6](#0-5) 

No equivalent invariant exists inside `liquidate`/`liquidate-multi` to prevent a *liquidator* from steering the borrower's mask into a laxer egroup between successive liquidation entries of the same batch. Each `call-liquidate` invocation independently re-checks health and re-derives the liquidation factor using whatever mask remains after the prior entries' collateral removal — i.e., "a health check followed by a call that changes what it checked," repeated across a `map`/fold that does not enforce any position-wide, cross-entry liquidation cap.

### Impact Explanation
By choosing the order and target collateral of entries inside one `liquidate-multi(positions)` call, a liquidator can:
1. First liquidate against the borrower using a collateral asset whose removal collapses the borrower's mask to a subset egroup with a higher `LTV-LIQ-PARTIAL`/`LTV-LIQ-FULL`.
2. Because the mask/egroup and health are recomputed fresh for the *next* entry in the same `map`, the borrower — now resolved under the laxer egroup — is judged liquidatable (or liquidatable to a larger degree) again, even though a single atomic health snapshot taken once for the whole position would have capped the liquidator to the normal graduated percentage.
3. Repeat across further entries in the same batch, each seizing additional collateral (with liquidation penalty) that the intended single-check, capped liquidation-factor design was meant to prevent in one transaction.

This is a direct analog of the referenced Wise Lending finding, condensed into a single atomic transaction via `liquidate-multi`'s `map`, satisfying the "single-transaction" scope constraint. The result is a liquidator extracting borrower collateral in excess of the amount the protocol's graduated liquidation-factor cap (`calc-liq-factor`, `calc-liquidation-params`) is designed to allow for one health evaluation — i.e., direct theft of the borrower's collateral (funds at rest), landing in the Critical impact class.

### Likelihood Explanation
Reachable by any address (liquidation is permissionless) with no privileged access, DAO compromise, or oracle manipulation required. It relies only on: (a) a borrower holding more than one collateral asset type such that draining one changes their mask to a different, already-configured egroup with a higher LTV-LIQ threshold (an intended, existing feature of the egroup system, not a misconfiguration), and (b) `liquidate-multi` batching entries targeting the same borrower with different `collateral-ft` selections. Both conditions are ordinary, expected states of the system rather than edge-case or admin-error scenarios, making this practically exploitable whenever a liquidatable multi-collateral position exists.

### Recommendation
- In `liquidate-multi`, snapshot the borrower's mask/egroup/health once per unique borrower before processing any entries for that borrower, and cap the aggregate USD value liquidated across all entries for that borrower to the single graduated liquidation-factor limit computed from that snapshot.
- Alternatively, disallow multiple entries in the same `liquidate-multi` call from targeting the same borrower, or force a fresh, whole-position health re-check (not just a partial-order egroup re-resolution) that includes a monotonic, position-wide liquidation cap independent of which specific collateral asset is drained first.
- Consider enforcing the same "capacity must not decrease" style invariant used in `collateral-add` on collateral-removing liquidation paths as well, or explicitly forbid egroup transitions to a higher-LTV mask as a side effect of a liquidation call.

### Proof of Concept
Conceptual sequence (single Clarity transaction):
1. Borrower holds collateral `sBTC + USDC`, debt `USDC`, resolved via a "superset" egroup with LTV-LIQ-PARTIAL = X (lower/conservative, per superset invariant confirmed in `local-testing/tests/security/egroup.test.ts:201-234`).
2. Price move makes the position marginally liquidatable under the superset egroup (`current-ltv` just above `ltv-liq-partial`), capping factor to the normal small/graduated percentage.
3. Liquidator calls `liquidate-multi` with:
   - Entry 1: `{borrower, collateral-ft: USDC-collateral, debt-ft: USDC, debt-amount: X1}` — fully drains the borrower's USDC collateral, changing the borrower's mask from `sBTC+USDC coll` to `sBTC coll only`.
   - Entry 2: `{borrower, collateral-ft: sBTC, debt-ft: USDC, debt-amount: X2}` — executed in the same `map`, now resolves the borrower under the `sBTC coll + USDC debt` (subset) egroup, which per the confirmed test data uses a higher LTV-LIQ-PARTIAL/FULL, and independently re-evaluates `current-ltv`/health using the collateral state left after entry 1.
4. Because each `call-liquidate` in `liquidate-multi`'s `map` is evaluated independently against the fresh (already-mutated) state, entry 2 is processed as a legitimate liquidation against the "new" egroup, extracting further sBTC collateral (plus penalty) beyond what a single, whole-position health check taken once would have permitted.
5. All of this occurs within one transaction/block, so there is no window for the borrower or protocol to intervene between entries. [3](#0-2)

```markdown
### The Mask System

**Mask = Bitmap representing asset combination**

Example masks:
- `0b0001` = Asset 0 only
- `0b0011` = Assets 0 and 1
- `0b0111` = Assets 0, 1, 2
- `0b1111` = Assets 0, 1, 2, 3

### The Bucket System (Optimization)

**Problem:** Finding matching egroup could require checking all egroups.

**Solution:** Group egroups by "population count" (number of assets).

```
(define-map buckets (buff 1) (list 128 uint))
(define-data-var popbucket- uint u0)
```

#### How it works
1. `popbucket-` is a bitmap where bit N = "bucket N has egroups"
2. Bucket N contains egroups with N+1 assets
3. When resolving, only check relevant buckets

#### Example
- User has 3 assets -> Population count = 3
- Only check buckets with ≥3 assets
- Find smallest superset (most specific match)

### The Resolution Algorithm

```
(define-read-only (resolve (mask uint))
```

#### Steps:

1. Calculate minimum population (# of bits set in user's mask)
2. Get active buckets ≥ minimum
```
