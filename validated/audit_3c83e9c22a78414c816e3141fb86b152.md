## Analysis Result

### Title
Unvalidated Base64 length in `sanitizeHost` causes unhandled exception (DoS) in unauthenticated admin auth flow - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` validates the `host` query parameter with a base64 character-class regex that does not enforce that the string length is a multiple of 4 (i.e., it does not check for correct base64 padding/length). It then feeds the unpadded string straight into `atob()` via `decodeHost`, which throws an uncaught `DOMException`/`InvalidCharacterError` for malformed base64. This is reachable from a single anonymous HTTP request (no auth required) hitting the embedded-admin authentication entry point with a malformed `host` param, and the exception is not caught by the calling authentication wrapper, so it propagates as an unhandled error instead of a controlled 4xx response — the same bug class as the reported analog ("function can fail without any information in case of incorrect input" due to a missing length/format precondition check).

### Finding Description
`sanitizeHost` only checks the character set of `host`, not its length: [1](#0-0) 

```
const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
```

`decodeHost` is a thin wrapper around `atob`: [2](#0-1) 

`atob` (per WHATWG Base64 semantics used by Node's global `atob`) throws for strings whose length is not a multiple of 4 / that are not correctly padded. Because `base64regex` accepts any length ≥ 1 as long as the character set matches (e.g., `host=A`, `host=AB`, `host=ABCDE`), a malformed-but-regex-passing value causes `atob` to throw before any `try/catch` in `sanitizeHost` — there is none — so the exception bubbles straight up.

This function is invoked directly on unauthenticated request data in the admin auth entry point: [3](#0-2) 

which is called unconditionally for document requests inside `authenticateAdmin`: [4](#0-3) 

The surrounding `try { ... } catch (errorOrResponse)` only special-cases `Response` instances (used for intentional redirects/login flows) and otherwise just rethrows the raw error: [5](#0-4) 

So a raw `DOMException` from `atob` is never turned into a normal 400 response — it propagates as an unhandled exception out of the admin auth handler. The same `sanitizeHost`/`decodeHost` call chain is reused by `getEmbeddedAppUrl` and by the equivalent React Router package's `validateShopAndHostParams`: [6](#0-5) [7](#0-6) 

The existing test suite for `sanitizeHost` only exercises non-base64-charset strings and domain-mismatch cases, never a charset-valid-but-badly-padded string, confirming this gap was not covered: [8](#0-7) 

### Impact Explanation
An anonymous request to any embedded app's admin authentication route (the root document loader/`authenticate.admin` handler in `shopify-app-remix`/`shopify-app-react-router`) with a crafted `host` query parameter of unpadded-but-charset-valid base64 triggers an unhandled exception in the request-authentication code path before any session/shop validation completes. This is a denial-of-service vector against the app's primary auth handler: instead of returning a clean 400 (as happens for a plainly invalid host), the request crashes the handler with an uncontrolled exception, which — depending on the surrounding server framework's top-level error handling — can produce unhandled promise rejections, noisy 500s on every hit, or process-level instability under repeated requests, since every document-load request from Shopify Admin normally carries a `host` param and this can be forced arbitrarily by anyone hitting the app URL directly.

### Likelihood Explanation
Trivial to trigger: no authentication, no valid shop, no cookies, and no prior state are required — a single GET request with `?host=<n chars satisfying base64 charset, length not a multiple of 4>` is sufficient. The vulnerable code path is unconditionally reached for any embedded-app document request lacking a session token header, which is the default entry point for first-time or bookmarked/normal browser navigation to the app.

### Recommendation
In `sanitizeHost` (`packages/apps/shopify-api/lib/utils/shop-validator.ts`), tighten the base64 regex to require proper padding/length (e.g. `^(?:[0-9a-zA-Z+/]{4})*(?:[0-9a-zA-Z+/]{2}==|[0-9a-zA-Z+/]{3}=)?$`), and/or wrap the `decodeHost`/`atob` call in a `try/catch` that treats decode failures the same as a regex mismatch (returning `null` or throwing `InvalidHostError`) instead of letting the raw `DOMException` propagate. Additionally, the top-level `authenticateAdmin` catch block should not blindly rethrow non-`Response` errors originating from input sanitization; such errors should be normalized into a controlled 400 Bad Request response.

### Proof of Concept
```
GET /?shop=some-shop.myshopify.com&host=A
```
(or any `host` value whose characters all match `[0-9a-zA-Z+/]` but whose length is not a multiple of 4, e.g. `host=AB`, `host=ABCDE`)

Flow:
1. Request hits `authenticateAdmin` → no session token header present → `validateShopAndHostParams(params, request)` is called.
2. `api.utils.sanitizeHost('A')` → regex `^[0-9a-zA-Z+/]+={0,2}$` matches `'A'` → proceeds to `decodeHost('A')` → `atob('A')`.
3. `atob('A')` throws `DOMException: The string to be decoded is not correctly encoded.`
4. This exception is not a `Response`, so the outer `catch (errorOrResponse)` in `authenticateAdmin` simply rethrows it, producing an unhandled error at the framework's request boundary instead of a graceful 400 response.
