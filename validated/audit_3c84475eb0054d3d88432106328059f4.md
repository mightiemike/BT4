This confirms the design: HMAC validation in `hmac-validator.ts` computes the signature only over `rawBody` [1](#0-0) , while the shop identity (`X-Shopify-Shop-Domain` header) is read separately from headers in `checkWebhooksHeaders`/`checkEventsHeaders` and is never included in the HMAC-signed payload [2](#0-1) . Since a single app-wide `apiSecretKey` is shared across every shop that installs the app, any valid `(rawBody, hmac)` pair legitimately observed by one merchant is cryptographically valid for **any** domain value, because the domain is not bound to the signature.

### Title
Webhook Domain Header Is Not Bound to HMAC Signature, Allowing Cross-Tenant Webhook Forgery - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
`shopify.webhooks.validate` (used by `authenticateWebhookFactory` in the Express/Remix/React-Router packages) authenticates an inbound webhook solely by validating the HMAC of the raw request body against the app's shared `apiSecretKey`. The `X-Shopify-Shop-Domain` header used to select which shop's session to load is never included in the signed payload.

### Finding Description
`validateHmacFromRequestFactory` computes `createSHA256HMAC(config.apiSecretKey, rawBody, ...)` and compares it to the `X-Shopify-Hmac-Sha256` header [1](#0-0) . `validateFactory` then separately extracts `domain`, `topic`, `webhookId`, etc. purely from headers via `checkWebhooksHeaders`, with no cryptographic link between those header values and the HMAC that was verified [3](#0-2) .

`authenticateWebhookFactory` in each web framework package trusts `check.domain` unconditionally to load the shop's offline session and build an authenticated Admin/Storefront client:
```
const session = await ensureValidOfflineSession(params, check.domain);
...
const admin = adminClientFactory({params, session, ...});
``` [4](#0-3) 

Because the same `apiSecretKey` is shared across every shop that installs the app, an attacker who is a legitimate, unprivileged merchant with the app installed can capture one of their own genuine webhook deliveries (`rawBody` + valid `X-Shopify-Hmac-Sha256`), then replay that exact `rawBody`/HMAC pair to the app's webhook endpoint while substituting a different, victim shop's domain in `X-Shopify-Shop-Domain`. `validateHmacFromRequestFactory` still returns `valid: true` because it only checks the body against the shared secret, and `authenticate()` proceeds to load the victim shop's offline session and hand it (plus attacker-controlled payload) to the app's webhook handler and Admin API client.

### Impact Explanation
This lets a single unprivileged merchant/customer-facing actor forge webhook events that are processed in the context of a different tenant's offline session — a cross-tenant authorization bypass. Depending on the app's webhook handler logic, this can trigger unauthorized writes/side effects against a victim shop's data (using the victim's `admin` client scoped session) or corrupt/desync victim application state, entirely bypassing per-shop authorization boundaries the library is supposed to enforce.

### Likelihood Explanation
Exploitation only requires an attacker to control one shop that has the target app installed (to obtain one valid rawBody/HMAC pair from their own webhook traffic) and send a single crafted HTTP POST with a forged `X-Shopify-Shop-Domain` header — no secrets need to be leaked, and no privileged Shopify staff access is required, satisfying the "single merchant" unprivileged-actor bar.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the HMAC-verified material, or independently verify that the domain header value corresponds to a shop actually entitled to trigger the delivered body (e.g., by validating that the payload's own shop-identifying fields, where present, match the header, or by additionally authenticating via a per-shop webhook signing secret / mandatory webhook subscription confirmation before trusting `check.domain` to select a session).

### Proof of Concept
1. Merchant A installs the app and captures a legitimate webhook delivery: `rawBody = '{"id":123,...}'`, `X-Shopify-Hmac-Sha256 = HMAC(apiSecretKey, rawBody)` (this is visible to Merchant A because it targets their own callback URL).
2. Merchant A crafts:
```http
POST /webhooks HTTP/1.1
Host: app.example.com
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <the captured, still-valid HMAC>
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-API-Version: 2024-01
X-Shopify-Webhook-Id: <any>
Content-Type: application/json

{"id":123,...}   (unchanged rawBody)
```
3. `shopify.webhooks.validate` returns `valid: true` because only `rawBody` is HMAC-checked [5](#0-4) .
4. `authenticateWebhookFactory` loads `victim-shop.myshopify.com`'s offline session via `ensureValidOfflineSession(params, check.domain)` and invokes the app's webhook handler / Admin API client as if the event genuinely originated from the victim shop [6](#0-5) .

  headers: Headers,
  headerName: string,
  missingHeaders: string[],
