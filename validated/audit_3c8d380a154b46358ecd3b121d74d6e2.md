### Title
Cross-network replay of security-council-signed `BatchProofMethodIdBody` between `Network::Nightly` and `Network::TestNetworkWithForks` due to collapsed chain-id mapping - (File: `crates/light-client-prover/src/circuit/mod.rs`)

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the same numeric chain id `5665`, so the anti-replay check at `run_l1_block` (`circuit_chain_id != batch_proof_method_id.body.chain_id`) cannot distinguish a method-id upgrade body signed for one network from one signed for the other. Because the signed message is the serialized `BatchProofMethodIdBody` bytes (which only contain the numeric chain id, not the `Network` enum variant), a signature bundle produced and inscribed for `Nightly` verifies identically when replayed on a `TestNetworkWithForks` deployment at the same `activation_l2_height`.

### Finding Description
The intended binding, as documented directly above the function, is:
`chain_id(network) == chain_id(network')` should hold **iff** `network == network'`, i.e. the chain id gate is supposed to be unique per `Network` the council distinguished when signing.

In code:
```
pub fn citrea_network_to_chain_id(network: sov_rollup_interface::Network) -> u64 {
    match network {
        ...
        sov_rollup_interface::Network::Nightly => 5665,
        sov_rollup_interface::Network::TestNetworkWithForks => 5665,
    }
}
``` [1](#0-0) 

This breaks the invariant: `Network::Nightly != Network::TestNetworkWithForks` as enum variants, but `citrea_network_to_chain_id` maps both to `5665`.

In `run_l1_block`, the `DataOnDa::BatchProofMethodId` arm gates acceptance solely on this numeric comparison:
```
let circuit_chain_id = citrea_network_to_chain_id(network);
if circuit_chain_id != batch_proof_method_id.body.chain_id {
    log!("Method ID upgrade transactions chain ID does not match circuit chain ID");
    continue;
}
``` [2](#0-1) 

The signature check that follows, `verify_method_id_security_council`, only verifies the EIP-191 prehash of `body.serialize()` against the council public keys and signature ordering; it never re-derives or checks which `Network` the body was intended for — it only checks the raw bytes, which are identical for a body constructed with `chain_id = citrea_network_to_chain_id(Network::Nightly)` and one constructed with `chain_id = citrea_network_to_chain_id(Network::TestNetworkWithForks)`, since both equal `5665`. [3](#0-2) 

Exploit flow: an attacker who can inscribe/relay any Bitcoin transaction observes (or is handed) a council-signed `BatchProofMethodId` inscription originally produced for `Nightly` at some `activation_l2_height = H`. If a `TestNetworkWithForks` deployment exists whose `BatchProofMethodIdAccessor` last activation height is `< H`, the attacker simply relays/re-inscribes the identical bytes as a DA blob on the `TestNetworkWithForks` chain. `run_l1_block` on that chain computes `circuit_chain_id = 5665` (same as `Nightly`), the `<=` height check at line 539 passes, the chain-id check at line 545 passes (5665 == 5665), and the untouched signature bytes still verify against the same council public keys, so the method id is inserted into `BatchProofMethodIdAccessor` for `TestNetworkWithForks` — even though the council never separately produced/authorized that body for that network. [4](#0-3) 

None of the existing guards (`activation_l2_height` monotonicity check, `verify_method_id_security_council`) catch this, because both checks operate purely on the serialized body bytes and the collapsed `chain_id` integer, not on the `Network` value passed into `run_l1_block` for the deployment actually being proven.

### Impact Explanation
This matches the "method-id upgrade accepted that was never authorised" Critical category: a `BatchProofMethodId` (i.e. the RISC0/SP1 guest program identifier trusted for verifying batch proofs) becomes authoritative on `TestNetworkWithForks` without the council ever separately signing for that network. Since the batch-proof method id determines which ZK program is trusted to validate state transitions, an attacker-controlled or stale method id accepted this way could let a light client/full node accept proofs for a different (or malicious) guest program as valid, corrupting the trusted state-transition chain for that deployment. The attack is repeatable for every future council-signed `Nightly` method-id upgrade as long as `TestNetworkWithForks` remains at a lower `last_activation_height`.

### Likelihood Explanation
The code-level defect is real and matches the documented intent violation (the comment above `citrea_network_to_chain_id` explicitly states its purpose is "to prevent cross network replay attacks," yet it does not for these two variants). However, `Network::TestNetworkWithForks` is explicitly documented in `crates/sovereign-sdk/rollup-interface/src/network.rs` as "All forks from genesis to Nightly... used for testing purposes only," not as a value-bearing production deployment. [5](#0-4) 
This significantly lowers real-world likelihood/impact versus mainnet: there is no evidence in the repo of a public, value-bearing `TestNetworkWithForks` deployment sharing the production security council keys, and the rules' scope excludes purely test-configuration issues with no demonstrated path to real bridged value. If a security-council-signed `Nightly` method-id ever needed to be treated as distinct from `TestNetworkWithForks`, this mapping collapse would need fixing regardless, but the practical, in-scope exploitation against a value-bearing network is not established by the repo as-is.

### Recommendation
Give `Network::TestNetworkWithForks` its own distinct chain id (not `5665`) in `citrea_network_to_chain_id`, or better, bind the signed `BatchProofMethodIdBody` to the `Network` enum discriminant explicitly (include a `network` tag in the serialized body) rather than relying on chain-id reuse for two conceptually different network configurations.

### Proof of Concept
```
// cargo test in crates/light-client-prover
#[test]
fn cross_network_replay_nightly_vs_test_network_with_forks() {
    let body = BatchProofMethodIdBody {
        method_id: [0u32; 8],
        activation_l2_height: 100,
        chain_id: citrea_network_to_chain_id(Network::Nightly), // signed once for Nightly
    };
    let msg = body.serialize();
    let prehash = eip191_hash_message(msg);
    let (initial_pubkeys, signers) = generate_initial_pub_keys_with_signers();
    let signatures_with_index = create_valid_signatures(&signers, &prehash);
    let batch_proof_method_id = BatchProofMethodId { body, signatures_with_index };

    // Binding check: chain_id derived for both networks must differ if Network variants differ
    let nightly_id = citrea_network_to_chain_id(Network::Nightly);
    let fork_test_id = citrea_network_to_chain_id(Network::TestNetworkWithForks);
    assert_eq!(nightly_id, fork_test_id); // demonstrates the collapsed mapping (5665 == 5665)

    // Replay acceptance under both networks via run_l1_block-equivalent gate
    assert_eq!(citrea_network_to_chain_id(Network::Nightly), batch_proof_method_id.body.chain_id);
    assert_eq!(citrea_network_to_chain_id(Network::TestNetworkWithForks), batch_proof_method_id.body.chain_id);
    assert!(verify_method_id_security_council(
        initial_pubkeys,
        batch_proof_method_id.body.serialize().as_slice(),
        &batch_proof_method_id.signatures_with_index
    )); // signature verification passes identically regardless of which Network it's replayed on
}
```
This test demonstrates the equality binding (`chain_id(Nightly) == chain_id(TestNetworkWithForks)`) holds when it should not, and that the signature/chain-id gate in `run_l1_block` cannot distinguish the two networks for a body of identical bytes.

```rust
pub fn verify_method_id_security_council(
    initial_da_pubkeys: [[u8; SECURITY_COUNCIL_COMPRESSED_PUBKEY_SIZE];
        SECURITY_COUNCIL_MEMBER_COUNT],
    msg: &[u8],
    signatures_with_idx: &[([u8; SECURITY_COUNCIL_SIGNATURE_SIZE], u8);
         SECURITY_COUNCIL_SIGNATURE_THRESHOLD],
) -> bool {
    // EIP-191 prefix + keccak256 → 32-byte prehash
    let prehash = eip191_hash_message(msg);

    // Check that signature indices are within bounds
    for &(_, index) in signatures_with_idx {
        if index >= 5 {
            log!("Invalid signature index: {}", index);
            return false;
        }
    }

    // Make sure the indexes are in ascending order to prevent duplicates
    for i in 0..signatures_with_idx.len() - 1 {
        if signatures_with_idx[i].1 >= signatures_with_idx[i + 1].1 {
            log!(
                "Signature indices are not in ascending order, failing indices: {}, {}",
                signatures_with_idx[i].1,
                signatures_with_idx[i + 1].1
            );
            return false;
        }
    }

    for signature_with_idx in signatures_with_idx.iter() {
        let signature = signature_with_idx.0;
        let pubkey_idx = signature_with_idx.1;
        let const_pubkey = initial_da_pubkeys[pubkey_idx as usize];

        // ensure the inscription pubkey matches the expected constant (compressed 33B)
        let verifying_key = VerifyingKey::from_sec1_bytes(const_pubkey.as_slice())
            .expect("Initial DA pubkeys must be parsable to k256 VerifyingKey form sec1 bytes");

        let Ok(parsed_sig) = Signature::from_bytes(&signature.into()) else {
            log!("Invalid signature format");
            return false; // invalid signature format, fail
        };

        // verify prehash with the matching verifying key
        if verifying_key
            .verify_prehash(prehash.as_slice(), &parsed_sig)
            .is_err()
        {
            log!("Signature verification failed for index: {}", pubkey_idx);
            return false;
        }
    }

    true
}
