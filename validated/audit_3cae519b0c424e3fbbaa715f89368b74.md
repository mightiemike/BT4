### Title
Function-call access key allowance not tracked in the pending-transaction-queue admission path, allowing spend beyond the granted allowance during SPICE chunk-production windows - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/verifier.rs`, `chain/client/src/pending_transaction_queue.rs`)

### Summary
The external report's bug class is: a resource cap (ERC20 allowance) is checked against a stale value because the system fails to account for already-in-flight decrements before permitting another decrement, letting the cap be exceeded. The nearcore analog is the `FunctionCallPermission.allowance` cap on a restricted access key, which is deliberately designed so that "both account balance and the allowance is decreased by the same value" per transaction [1](#0-0) . During chunk preparation under the SPICE pending-transaction-queue path, the ephemeral verification re-reads the allowance from the last *certified* state and only adjusts for pending *account balance* and *gas-key* spend, never for pending allowance consumption by the same restricted key.

### Finding Description
`PendingConstraints`, the struct used to adjust ephemeral validation for transactions that are already included in uncertified pending chunks, tracks only `paid_from_balance`, `paid_from_gas_key`, `max_nonce`, and `max_bootstrap_nonce` [2](#0-1) . There is no field carrying "allowance already spent by pending, uncertified transactions signed with this restricted access key."

`check_and_compute_new_allowance`, used by `verify_and_charge_tx_ephemeral`, computes the new allowance purely from the `access_key` snapshot loaded from state and the current transaction's `total_cost` — it takes no `pending` parameter at all: [3](#0-2) 

Contrast this with the balance check in the same function, which explicitly subtracts `pending.paid_from_balance` before comparing against `total_cost`: [4](#0-3) 

The gas-key path has an equivalent, correctly-tracked mechanism: `PendingConstraints::paid_from_gas_key` accumulates pending gas-key cost and `WithdrawFromGasKey` amounts from `add_chunk_transactions`/`check_pending` in `chain/client/src/pending_transaction_queue.rs` [5](#0-4) [6](#0-5) . No analogous `paid_from_allowance` field or tracking exists for regular `FunctionCallPermission` allowance consumption anywhere in `pending_transaction_queue.rs`.

The SPICE chunk-production path explicitly uses the *last certified block's* `ChunkExtra` state root for validation while relying on `PendingConstraints` to compensate for chunks that were already produced but not yet certified: `prepare_transactions` builds a `PendingTxSession` and calls `prepare_transactions_extra` against `certified_chunk_extra.state_root()` [7](#0-6) . The same certified-state + `PendingConstraints` combination is used for RPC-time admission in `rpc_handler.rs` [8](#0-7) .

Because the allowance for a `FunctionCallPermission` key is read from that stale certified state and is never reduced by the amount already consumed by transactions from the same key sitting in earlier, uncertified pending chunks, a transaction using such a key that appears in multiple back-to-back pending (uncertified) chunks will pass the allowance check multiple times against the same, not-yet-decremented allowance value — exactly the "approve/allowance checked against a value that has not been synchronized with concurrent in-flight consumption" pattern flagged in the external report.

### Impact Explanation
The `FunctionCallPermission.allowance` exists specifically to cap how much of an account's balance a *restricted* key (e.g. one handed to an app, a session key, or a minor/limited delegate as in the docs' "Alice's parent" example [9](#0-8) ) is permitted to spend, independent of the account's total balance sufficiency (which is separately enforced and correctly pending-aware via `paid_from_balance`). If the allowance cap can be exceeded because pending, uncertified consumption from the same key is not subtracted, a holder of a deliberately-restricted key can drain more of the owner's account balance than the owner authorized, during the SPICE window between chunk production and certification. This is an unauthorized value movement out of the owner's account, beyond the explicit, protocol-documented cap — the exact analog of bypassing an ERC20 allowance limit.

### Likelihood Explanation
This requires the SPICE protocol feature and its pending-transaction-queue to be enabled (`spice_pending_transaction_queue_enabled`), and requires an account to hold a `FunctionCallPermission` access key with a finite allowance and to repeatedly submit/have admitted transactions from that key across several chunks before certification catches up — all of which is achievable by an ordinary signer holding such a key, no validator or operator privilege needed. The likelihood is bounded by how many uncertified chunks can be produced before certification (a SPICE-specific timing window), and by the fact this only affects the narrower allowance sub-cap, not overall account solvency (which remains protected).

### Recommendation
Add a `paid_from_allowance` (or similar) field to `PendingConstraints`, populate it in `PendingTxSession::check_pending`/`add_chunk_transactions` by accumulating `total_cost` for pending transactions keyed by `(signer_id, public_key)` for `FunctionCallPermission` keys (mirroring the existing `gas_key_costs` tracking), and thread this value into `check_and_compute_new_allowance` so the allowance check subtracts already-pending, uncertified consumption before permitting a new decrement — matching how `paid_from_balance` is already handled for the account-balance check.

### Proof of Concept
1. Enable the SPICE protocol feature with `spice_pending_transaction_queue_enabled = true`.
2. Account `alice` grants a `FunctionCallPermission` access key `K` to `bob` with `allowance = Some(3000)`, `receiver_id = "app"`, matching the pattern in `docs/RuntimeSpec/Scenarios/CrossContractCall.md`.
3. `bob` submits two function-call transactions signed by `K`, each with `total_cost = 2500`, in rapid succession such that both are admitted into two different chunks before the first chunk is certified.
4. For the first transaction, `prepare_transactions_extra` validates against certified state where `K.allowance == 3000`; `check_and_compute_new_allowance` succeeds (3000 - 2500 = 500), and the transaction is admitted into pending chunk N.
5. Because `PendingConstraints` has no `paid_from_allowance` accounting for `K`, when the second transaction is validated for chunk N+1 (still against the same certified state, since chunk N is not yet certified), `check_and_compute_new_allowance` again sees `K.allowance == 3000` (unmodified) and again succeeds (3000 - 2500 = 500), admitting a second transaction.
6. Net effect: `bob` has been admitted to spend `5000` total using a key whose owner-granted cap was `3000`, i.e., `2000` more than authorized, once both chunks are eventually certified and applied.

fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
