### Title
Delegated `WithdrawFromGasKey` action drains gas-key balance without updating the `PendingTransactionQueue` checkpoint, allowing pending-window gas-key overspend admission - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
The Livepeer finding describes a checkpoint/snapshot ledger (`BondingVotes`) that goes stale because a balance-mutating code path (`withdrawFees` → `updateDelegatorWithEarnings`) never calls the checkpoint-update hook. Nearcore's SPICE `PendingTransactionQueue` ("PTQ") is architecturally the same kind of side-ledger: it maintains `paid_from_gas_key` / `paid_from_balance` checkpoints used by RPC/chunk-producer admission control to validate whether a not-yet-certified transaction can be safely admitted, mirroring balance effects that haven't yet been finalized on-chain. This ledger is deliberately updated by scanning only the *top-level* actions of a transaction for `WithdrawFromGasKeyAction` [1](#0-0) , exactly as the Livepeer bug's checkpoint update was skipped for a particular balance-mutating call path.

### Finding Description
`PendingTransactionQueue::add_chunk_transactions` and `PendingTxSession::check_pending` scan `tx.actions()` (top level only) for `Action::WithdrawFromGasKey` to update `gas_key_costs` / `session_gas_key_withdrawals`, which back the `paid_from_gas_key` checkpoint returned in `PendingConstraints` [2](#0-1) . This checkpoint is what `verify_and_charge_gas_key_tx_ephemeral` relies on to bound gas-key spend across the "pending window" (admitted-but-not-yet-certified transactions) [3](#0-2) .

A `WithdrawFromGasKeyAction` nested inside a `Delegate`/`DelegateV2` meta-transaction actually mutates gas-key balance during execution, exactly like the top-level action does [4](#0-3) , but the PTQ's scan of `tx.actions()` never looks inside `DelegateAction.actions`, so this drain is invisible to the checkpoint — precisely the "balance update happens but the checkpoint used elsewhere is never touched" bug class. The codebase itself documents this exact root cause in two `ProtocolFeature` doc comments:

- `RejectDelegateV2`: "the inner nonce advances a gas key of the delegate sender and `PendingTransactionQueue` does not see it... its nonce and gas key balance commitments would miss that key" [5](#0-4) 
- `RejectWithdrawFromGasKeyInDelegate`: "the SPICE pending transaction queue scans only the top level actions of a transaction for `WithdrawFromGasKey`, so a nested one drains a gas key that the queue still counts as funded" [6](#0-5) 

A dedicated test confirms the mechanism and its pre-upgrade impact: before the mitigating protocol feature activates, a delegated `WithdrawFromGasKey` is admitted and actually drains the gas key's balance [7](#0-6) .

### Impact Explanation
Because the fix is implemented as an *admission-time rejection* (`validate_delegate_action` returns `WithdrawFromGasKeyNotAllowedInDelegate` when `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` is enabled, and `RejectDelegateV2` separately disables `DelegateV2` entirely) rather than as a fix to the PTQ's checkpoint accounting itself [8](#0-7) , the underlying stale-checkpoint defect in `PendingTransactionQueue` remains present in the code; it is only masked for the two known trigger paths (top-level `Delegate`/`DelegateV2` wrapping a `WithdrawFromGasKey`). If both `RejectDelegateV2` and `RejectWithdrawFromGasKeyInDelegate` are active at the current stable protocol version, this specific exploitation path is currently closed for newly-admitted transactions (in-flight/`ExistingReceipt` execution still tolerates it for backward compatibility, per the tests). The residual risk is architectural: any future action variant or nesting construct that can mutate gas-key balance without being visible to the PTQ's shallow, top-level-action scan would reproduce the same "unauthorized value movement" class bug — a chunk producer/RPC could admit more gas-key-funded transactions into the pending window than the account actually has balance for, since the checkpoint used for admission (`paid_from_gas_key`) undercounts real balance depletion.

### Likelihood Explanation
Low-to-Medium under the current stable protocol version, because both mitigating `ProtocolFeature`s (`RejectDelegateV2`, `RejectWithdrawFromGasKeyInDelegate`) close the only two currently-known trigger paths for a submitted transaction. I was not able to determine from the available index snippets whether `PROTOCOL_VERSION`/`STABLE_PROTOCOL_VERSION` (86, per other spec documents) is at or beyond the activation version of both features — this would need to be confirmed in `core/primitives-core/src/version.rs`'s activation table before concluding the path is fully closed. The finding is best framed as: the root-cause checkpoint gap in `PendingTransactionQueue` (a shallow, top-level-only action scan backing a balance-admission control) is real and documented by the maintainers themselves as a hole that had to be patched reactively per-action-type, rather than by making the checkpoint accounting itself complete/robust.

### Recommendation
Harden `PendingTransactionQueue`'s accounting instead of relying solely on action-type denylists: recursively scan nested `Delegate`/`DelegateV2` actions (and any future wrapping/batching action) for balance-affecting sub-actions (`WithdrawFromGasKey`, and any other action added later that mutates gas-key or account balance) when computing `paid_from_balance`/`paid_from_gas_key`, or alternatively enforce, at the type level, that no action capable of mutating a balance the PTQ tracks can ever appear inside a container action that the PTQ's scanner does not recurse into. This closes the class of bug rather than patching each newly-discovered instance with a `ProtocolFeature` rejection.

### Proof of Concept
1. On a protocol version prior to `RejectWithdrawFromGasKeyInDelegate` activation (demonstrated in the existing test), create a gas key and fund it via `TransferToGasKey`.
2. Submit a `Delegate` action whose single inner action is `WithdrawFromGasKeyAction` targeting that gas key, signed by the sender's plain access key [9](#0-8) .
3. Observe the transaction is admitted and executes successfully, draining the gas key balance by `WITHDRAW_AMOUNT`, while `PendingTransactionQueue::add_chunk_transactions`'s top-level-only scan never records this drain against `pending_gas_key_costs` [1](#0-0) .
4. Concurrently submit additional gas-key transactions relying on `paid_from_gas_key` for admission; because the checkpoint undercounts the true balance depletion, more spend than the gas key can support may be admitted into the pending (uncertified) window before the runtime's ephemeral balance check (which does see the real state) ultimately rejects execution — a race window exploitable purely via transaction submission, matching the Livepeer "stale checkpoint enables inconsistent accounting used by downstream logic" bug class.

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
}

fn validate_delegate_action(
    limit_config: &LimitConfig,
    delegate_action: VersionedDelegateActionRef<'_>,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ActionsValidationError> {
    // Check the count before `get_actions()` clones the list, so a huge
    // nested-action list can't force the allocation before being rejected.
    // Consensus-neutral: same `TotalNumberOfActionsExceeded` as the check in
    // `validate_actions_with_mode` below.
    let num_actions = delegate_action.actions().len() as u64;
    if num_actions > limit_config.max_actions_per_receipt {
        return Err(ActionsValidationError::TotalNumberOfActionsExceeded {
            total_number_of_actions: num_actions,
            limit: limit_config.max_actions_per_receipt,
        });
    }
    let actions = delegate_action.get_actions();
    // As with the `DelegateV2` removal above, receipts created before this rule
    // are still in flight and must keep executing.
    if mode == ValidateReceiptMode::NewReceipt
        && ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(current_protocol_version)
        && actions.iter().any(|action| matches!(action, Action::WithdrawFromGasKey(_)))
    {
        return Err(ActionsValidationError::WithdrawFromGasKeyNotAllowedInDelegate);
    }
