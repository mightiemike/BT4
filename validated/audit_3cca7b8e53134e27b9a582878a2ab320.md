### Title
Legacy `WriteSet` V1 payload silently reinterpreted as `V0` on decode, permanently dropping the `hotness` bucket - ([File: storage/aptosdb/src/schema/write_set/mod.rs])

### Summary
`WriteSetSchema::decode_value` contains a fallback path for pre-hot-state binaries that wrote `WriteSet::V1` bytes without the newer `extensions` field. On EOF, it parses the tail as a `LegacyWriteSetV1Payload{value, hotness}` and reconstructs the value — but wraps it in `WriteSet::V0` instead of `WriteSet::V1`. Because `WriteSetV0::hotness`/`extensions` are `#[serde(skip)]`, this in-memory value silently loses its `hotness` set the moment it is re-serialized (BCS bytes and, since `WriteSet` derives `BCSCryptoHash` over those bytes, its hash too), even though the on-disk bytes originally carried the `hotness` set under the `V1` tag.

### Finding Description
`decode_value` in [1](#0-0)  matches on `data.first() == Some(&1)` (BCS enum tag for `WriteSet::V1`), tries the current decoder, and on `Eof` (missing `extensions` field in the legacy format) falls back to:
```
let legacy: LegacyWriteSetV1Payload = bcs::from_bytes(&data[1..])?;
let mut ws = WriteSet::V0(legacy.value);
ws.add_hotness(legacy.hotness);
```
`LegacyWriteSetV1Payload` at [2](#0-1)  is exactly what the pre-migration `WriteSet::V1` variant looked like (value_writes + hotness, no extensions), i.e. the source bytes were unambiguously tagged and produced as `V1`. The decoder nonetheless reconstructs it as `WriteSet::V0` and only patches `hotness` into memory via `add_hotness`, which works because `hotness_mut()` is variant-agnostic ( [3](#0-2) ). But `WriteSetV0` marks `hotness` and `extensions` `#[serde(skip)]` ( [4](#0-3) ), so any later `bcs::to_bytes(&ws)` — used both for `ValueCodec::encode_value` (re-persisting, e.g. during compaction/backup restore) and for the `BCSCryptoHash` derive on `WriteSet` ( [5](#0-4) ) — drops `hotness` entirely and changes the byte encoding/hash relative to the originally-committed `V1` bytes.

The existing regression test only checks `decoded.as_v0() == expected.as_v0()`, a `PartialEq` comparison unaffected by `#[serde(skip)]`, so it never exercises a decode→re-encode round trip and misses this loss ( [6](#0-5) ).

### Impact Explanation
Any code path that decodes a legacy-format `WriteSet` and subsequently re-serializes or re-hashes it (DB migration/compaction rewriting the `WRITE_SET_CF`, backup/restore re-encoding into a target DB, or any replay/verification logic that recomputes a write-set-derived hash from the decoded value) will silently emit bytes that omit the `hotness` promotion set and no longer match what was originally committed. This is exactly the class of bug the task calls out: "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state." Concretely, the persisted representation of a historical write set is corrupted from `V1` (with hotness) into `V0` (without hotness) the instant it passes through this decode path and is written back out, and any hash computed over the reconstructed value diverges from the hash computed by the original executor over the true `V1` value.

### Likelihood Explanation
The fallback branch is not a hypothetical edge case — its own comment states it exists specifically because "baseline validators would write legacy format to DB" in forge-compat scenarios, meaning it is actively exercised whenever a node holds/serves data produced by pre-migration binaries (mixed-version fleets, restores from older backups, upgrades across the hot-state migration boundary). No malicious input is required; ordinary version-skew during a rolling upgrade or a backup/restore across the migration boundary triggers it.

### Recommendation
In the fallback branch, reconstruct the value with the same variant its on-disk tag indicates: build `WriteSet::V1(WriteSetV1 { value_writes: legacy.value.into_value_writes(...), hotness: legacy.hotness, extensions: Vec::new() })` instead of wrapping in `WriteSet::V0`. Additionally, extend the schema test to perform a decode → encode round trip (and compare raw bytes, not just `as_v0()`), so any variant-misclassification or field-loss regression is caught automatically.

### Proof of Concept
Not runnable within this session's remaining tool budget; the invariant break is demonstrated directly from source:
1. Encode a `WriteSetV1{value_writes, hotness: {k}, }` without an `extensions` field the way pre-migration binaries did (mirrors `test_decode_legacy_v1_fallback`'s manual construction in [7](#0-6) ).
2. Call `WriteSet::decode_value(&bytes)` — it returns `WriteSet::V0` with `hotness = {k}` in memory (per `decode_value`, [8](#0-7) ).
3. Call `bcs::to_bytes(&decoded)` (equivalently, take `decoded.hash()`) and observe the output no longer contains the `hotness` key, and differs from step 1's bytes/hash, because `WriteSetV0::hotness` is `#[serde(skip)]` ( [4](#0-3) ).

I was not able to fully trace, within the remaining budget, every concrete call site (e.g., `backup/backup_handler.rs`, `ledger_db/write_set_db.rs`) that re-encodes or re-hashes a decoded `WriteSet` to confirm an end-to-end mainnet-triggerable hash-mismatch/silent-corruption scenario; that verification would require an additional session to trace restore/replay call sites and confirm whether they compare a recomputed hash against `TransactionInfo.state_change_hash`.

    fn decode_value(data: &[u8]) -> Result<Self> {
        // TODO(HotState): we could simply use `bcs::from_bytes` for everything once the latest
        // release branch does not write LegacyWriteSetV1Payload and forge-compat test would not
        // fail in CI.
        match data.first() {
            Some(&1) => match bcs::from_bytes::<WriteSet>(data) {
                Ok(ws) => Ok(ws),
                // Legacy V1 payload lacks the trailing `extensions` field, so the new decoder
                // runs out of bytes while reading it. Any other error indicates real corruption
                // and should propagate.
                Err(bcs::Error::Eof) => {
                    let legacy: LegacyWriteSetV1Payload = bcs::from_bytes(&data[1..])?;
                    let mut ws = WriteSet::V0(legacy.value);
                    ws.add_hotness(legacy.hotness);
                    Ok(ws)
                },
                Err(e) => Err(e.into()),
            },
            _ => bcs::from_bytes::<WriteSet>(data).map_err(Into::into),
        }
    }

/// Legacy V1 bytes (variant tag 1 with `value ++ hotness`, no trailing extensions) must
/// decode via the fallback path and preserve both writes and hotness.
#[test]
fn test_decode_legacy_v1_fallback() {
    let writes = WriteSet::new(vec![(
        StateKey::raw(b"key1"),
        WriteOp::legacy_creation(b"val1".to_vec().into()),
    )])
    .unwrap();
    let hotness: BTreeSet<_> = [StateKey::raw(b"hot1"), StateKey::raw(b"hot2")]
        .into_iter()
        .collect();

    let mut bytes = vec![1u8]; // BCS variant tag for V1.
    bytes.extend(
        bcs::to_bytes(&LegacyWriteSetV1Payload {
            value: writes.as_v0().clone(),
            hotness: hotness.clone(),
        })
        .unwrap(),
    );

    let mut expected = writes;
    expected.add_hotness(hotness);
    let decoded = WriteSet::decode_value(&bytes).unwrap();
    assert_eq!(decoded.as_v0(), expected.as_v0());
}
