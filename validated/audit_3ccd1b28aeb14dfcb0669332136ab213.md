## Title
Stale/misaligned cached-hash indexing in `StorageProofCalculator`/`AccountProofCalculator` can compute a wrong state root under proof-guided caching - (`crates/trie/trie/src/proof_v2/mod.rs`)

## Summary
`next_uncached_key_range` in `crates/trie/trie/src/proof_v2/mod.rs` pulls a child's cached RLP hash out of a `BranchNodeCompact` by computing `hash_idx` as "the number of `hash_mask` bits set below this child's nibble" and then indexing `cached_branch.hashes[hash_idx]` (lines ~1101-1105). This is exactly the `Gather`-style pattern from the referenced advisory: an index is derived from one piece of state (the mask/traversal position) and used to index a *different*, independently-populated array (`hashes`) without re-validating that the two are still in agreement for the *current* traversal context (post prefix-set exclusions, deletions, or non-canonical trie shapes).

## Finding Description
The dense `hashes` vector on a `BranchNodeCompact` is populated once, in nibble order, only for children whose `hash_mask` bit is set at the time the compact node was persisted/cached. When the calculator later walks the trie guided by a *live* prefix set (representing execution-time deletions/dirtiness) it recomputes `hash_idx` purely from `hash_mask & lower_bits` — i.e., it assumes the dense position of a bit in `hash_mask` still corresponds 1:1 with the same position in `hashes`, for every candidate child, regardless of whether some earlier claimed-cached children were actually skipped/re-derived due to being in the prefix set or otherwise stale.

The repository's own test `test_cached_hash_with_deleted_leaf` (`crates/trie/trie/src/proof_v2/mod.rs:3258-3336`) documents precisely this class of bug in its comments:

> "With the bug, nibble 5 gets hashes[0] (nibble 3's hash) and nibble 8 gets hashes[1] (nibble 5's hash), producing a wrong root." [1](#0-0) [2](#0-1) 

This is the same bug shape as TFLite's `Gather`/`GatherNd`: an attacker/adversarial-state-controlled index (here, the position of a masked-out or dirtied nibble relative to the surviving `hash_mask` bits) is used to read from an array (`hashes`) whose contents were populated under a different assumption about which slots are present, producing either an out-of-bounds/garbage read or — as the code's own regression test shows — a **silently wrong hash value** pulled from the wrong dense slot. Because `hashes` is a `Vec<B256>` sized to `hash_mask.count_ones()`, a computed `hash_idx` that is off by the number of "skipped" cached children will read a *different but in-bounds* `B256` (not necessarily a panic), which is worse than a crash: it corrupts the state/storage root silently.

The `StorageProofCalculator`/`AccountProofCalculator` computations feed directly into `compute_root_hash`, which backs `overlay_multiproof_v2`/`witness` (`crates/storage/provider/src/providers/state/latest.rs:222-262`) and ultimately trie-based root computation used during block validation and witness generation. [3](#0-2) 

## Impact Explanation
If the "off-by-one/misaligned index" scenario reaches the canonical state-root computation path (not only the isolated proof/witness helpers exercised in the added regression tests), it breaks the core equality that the "Validate" rules call out explicitly: *a state root, receipts root, or balance differing from the spec*. A wrong cached hash silently substituted into a branch node changes the computed root without any error being raised, which would cause reth to either compute an incorrect state root for a block it executes (potentially rejecting a spec-valid block, or worse, accepting/committing a wrong root) or produce a corrupted multiproof/witness that a light client or another verifier would reject. This matches the "Critical" impact bar: *a state root ... differing from the spec* triggered deterministically by a specific state shape (a masked-empty/dirtied child preceding other hashed children in a `BranchNodeCompact`), not requiring any malicious peer, RPC caller, or consensus-layer cooperation — only a specific combination of trie shape and touched/deleted storage slots that can arise from perfectly ordinary transaction execution.

## Likelihood Explanation
The repository already contains three adjacent, purpose-built regression tests (`test_node_with_masked_empty_child`, `test_node_with_masked_empty_child_lower_bound_past_branch`, `test_cached_hash_with_deleted_leaf`) whose comments explicitly describe how "the bug" mis-indexes `hashes` when earlier children are masked/dirtied — indicating this exact index-alignment invariant has already broken at least once in this codebase's history and needed a targeted fix/test to catch. This shows the invariant ("dense hash_mask bit position == dense position in the cached `hashes` vec, for *every* subset of children considered during incremental/partial traversal") is fragile and re-derivable incorrectly whenever the traversal logic changes how it decides to skip a masked child (e.g., due to prefix-set dirtiness, absence proofs, or lower-bound advancement past a branch). Given how many different code paths in `next_uncached_key_range` recompute `hash_idx` from `hash_mask` bit-counting (the pattern recurs for every child considered, including cases explicitly called out in comments as "masked empty child"), a functionally similar regression is plausible if any of these edge-case branches is not fully covered by the existing tests (e.g., combinations across account *and* storage proofs, multiple dirtied children in the same branch, or when-only-some children are targets in a proof rather than an absence check).

## Recommendation
- Do not derive `hash_idx` solely from bit-counting on `hash_mask`; instead, maintain the cached branch's `hashes` alongside an explicit, defensive mapping that is validated whenever the "should use cached hash" fast path is taken, so any prefix-set exclusion of a *preceding* masked child provably cannot shift the meaning of later dense indices.
- Add an invariant check (debug assertion at minimum, and ideally a runtime check outside of debug builds given the criticality) that `hash_idx < cached_branch.hashes.len()` and that the reconstructed root using the pulled hash matches an independently recomputed subtree hash in a sampling/fuzz test across all combinations of masked/dirtied children positions (not just single-position cases).
- Expand fuzz/property testing of `StorageProofCalculator`/`AccountProofCalculator` against a reference "always recompute from scratch" trie builder for randomly generated `BranchNodeCompact` masks with randomly dirtied prefix sets, specifically targeting multiple simultaneous masked/dirty children within one branch and across branch boundaries.
- Audit all other call sites in `crates/trie/trie/src/proof_v2/mod.rs` that compute a dense index from `TrieMask::count_ones()`/`count_bits()` bit-counting against a *different* mask or vector populated at a different point in time, applying the same defensive validation.

## Proof of Concept
The existing test `test_cached_hash_with_deleted_leaf` in `crates/trie/trie/src/proof_v2/mod.rs` is itself the reproduction harness for this bug class:
1. Construct a `BranchNodeCompact` at path `[6]` with `state_mask`/`hash_mask` both set for nibbles `3, 5, 8`, and `hashes = [hash(leaf_63), hash(leaf_65), hash(leaf_68)]`.
2. Mark `key_63`'s path dirty in the prefix set (simulating a deleted leaf, as would occur naturally from execution of a transaction that clears a storage slot).
3. Request an absence proof for `key_63` via `StorageProofCalculator::storage_proof` and then `compute_root_hash`.
4. Compare against the root of a fresh trie built only from `key_65`/`key_68`.

The test's own comments state that, absent the fix, `nibble 5` incorrectly consumes `hashes[0]` (belonging to nibble 3) and `nibble 8` incorrectly consumes `hashes[1]` (belonging to nibble 5) — i.e., exactly the `Gather`-style indexing corruption described in the advisory, applied to state-root-critical cached branch hashes rather than a ML tensor. Because this fix/test currently exists only for this specific single-preceding-dirty-child configuration, replaying the same construction with **two or more** dirtied/masked preceding children in the same branch (or combining it with the "masked empty child" and "lower bound past branch" scenarios in the neighboring tests) is a reasonable next step to check whether the underlying `hash_idx` derivation is fully corrected or only patched for the originally observed case.

    fn test_cached_hash_with_deleted_leaf() {
        reth_tracing::init_test_tracing();

        // Use different values to ensure distinct leaf hashes.
        let val_3 = U256::from(111u64);
        let val_5 = U256::from(222u64);
        let val_8 = U256::from(333u64);

        // Keys under a common prefix `0x6_` to create a branch at path [6].
        // Use second byte to distinguish short keys (so they differ after position 2).
        let key_63 = B256::right_padding_from(&[0x63, 0xaa]); // nibble path: 6,3,a,a,...
        let key_65 = B256::right_padding_from(&[0x65, 0xbb]); // nibble path: 6,5,b,b,...
        let key_68 = B256::right_padding_from(&[0x68, 0xcc]); // nibble path: 6,8,c,c,...

        // Compute leaf hashes. The branch at [6] consumes 2 nibbles (the branch path [6]
        // plus the child nibble), so each leaf's short key starts at position 2.
        let leaf_hash_3 = storage_leaf_hash(&Nibbles::unpack(key_63).slice(2..), &val_3);
        let leaf_hash_5 = storage_leaf_hash(&Nibbles::unpack(key_65).slice(2..), &val_5);
        let leaf_hash_8 = storage_leaf_hash(&Nibbles::unpack(key_68).slice(2..), &val_8);

        // Build cached branch at [6] with state_mask and hash_mask bits for nibbles 3, 5, 8.
        let state_mask = TrieMask::new((1 << 3) | (1 << 5) | (1 << 8));
        let cached_branch = BranchNodeCompact::new(
            state_mask,
            TrieMask::new(0),
            state_mask, // hash_mask = state_mask (all children have cached hashes)
            vec![leaf_hash_3, leaf_hash_5, leaf_hash_8],
            None,
        );

        let storage_nodes: BTreeMap<Nibbles, BranchNodeCompact> =
            std::iter::once((Nibbles::from_nibbles([0x6]), cached_branch)).collect();

        // Compute the expected root from a fresh trie with just key_65 and key_68.
        let mut harness =
            TrieTestHarness::new([(key_65, val_5), (key_68, val_8)].into_iter().collect());
        let expected_root = harness.original_root();

        // Update the harness with a cached trie node which will reference key_63 by hash.
        harness.set_trie_nodes(storage_nodes);

        // Mark key_63 as dirty in the prefix set — in the real scenario the leaf was
        // deleted and the HashedPostState overlay masks it out.
        let mut prefix_set = PrefixSetMut::default();
        prefix_set.insert(Nibbles::unpack(key_63));

        // Request a proof for key_63 (absence proof — no leaf exists).
        // Because the prefix set marks nibble 3's child path as dirty, the cached hash for
        // nibble 3 is skipped.
        let mut targets = vec![ProofV2Target::new(key_63)];

        let trie_cursor =
            harness.trie_cursor_factory().storage_trie_cursor(harness.hashed_address()).unwrap();
        let hashed_cursor = harness
            .hashed_cursor_factory()
            .hashed_storage_cursor(harness.hashed_address())
            .unwrap();
        let mut calculator = StorageProofCalculator::new_storage(trie_cursor, hashed_cursor)
            .with_prefix_set(prefix_set.freeze());

        let proofs = calculator
            .storage_proof(harness.hashed_address(), &mut targets)
            .expect("storage_proof should succeed");
        assert_eq!(1, proofs.len());
        let got_root = calculator
            .compute_root_hash(&proofs)
            .expect("compute_root_hash should succeed")
            .expect("should produce a root hash (proof contains root node)");

        // With the bug, nibble 5 gets hashes[0] (nibble 3's hash) and nibble 8 gets
        // hashes[1] (nibble 5's hash), producing a wrong root.
        pretty_assertions::assert_eq!(
            expected_root,
            got_root,
            "Root hash should match trie without key_63; cached hash index is off when \
             an earlier hashed child has no leaves (absence proof target)"
        );
    }
