### Title
Non-embedded app OAuth session cookie is not scoped per-shop by default, causing cross-tenant session overwrite - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
In non-embedded Shopify apps, `oauth.callback()` writes the offline/online session id into a single browser-wide cookie (`shopify_app_session`) at `path: '/'` unless the app explicitly opts into a shop-scoped `cookiePath`. Because this cookie is not keyed by shop, completing OAuth for a second shop in the same browser silently overwrites the cookie that points at the first shop's session, so subsequent requests resolve to the wrong shop/session — a direct analog of the Yaxis `addToken` bug where `vaults[_token] = _vault` was overwritten without a duplicate/ownership check, corrupting the first vault's bookkeeping.

### Finding Description
The OAuth callback builds a `Session` for the shop that just completed OAuth, then persists its id into `SESSION_COOKIE_NAME` (`shopify_app_session`) using a cookie path that defaults to `'/'` for the whole app unless the app config supplies a shop-specific `cookiePath`: [1](#0-0) 

The cookie name is a single fixed constant with no shop component baked in: [2](#0-1) 

The project's own changelog confirms this is a real, previously-unmitigated defect: with the default `path: '/'`, "all shops shared a single `shopify_app_session` cookie... so authenticating a new shop would silently overwrite the previous shop's session," and the fix is an *opt-in* `cookiePath` config (function of shop) rather than a mandatory safe default: [3](#0-2) [4](#0-3) 

This is the same bug class as `addToken`'s missing duplicate/ownership check: a shared mutable "slot" (`vaults[_token]` in Yaxis, the `shopify_app_session` cookie here) is unconditionally overwritten whenever a second entity (a second vault, a second shop) claims it, with no check that the slot is already owned by a different tenant.

### Impact Explanation
Any deployment that (a) is non-embedded (`isEmbeddedApp: false`), (b) serves more than one shop from the same app instance/domain, and (c) does not set the new opt-in `cookiePath` is affected. A user/browser that authenticates shop B after shop A silently has shop A's tab now presenting shop B's session cookie on the next authenticated request, since `getCurrentSessionId`/cookie-based lookup (`cookies.getAndVerify(SESSION_COOKIE_NAME)`) trusts whichever session id is currently in the cookie: [5](#0-4) 

Because `SessionStorage.loadSession(id)` resolves purely by id (no ownership/shop cross-check against the request context), the app will load and act on the wrong shop's `Session` (including its access token), yielding cross-tenant data exposure/action-on-behalf-of-wrong-shop — comparable to the Yaxis case where the vault's value calculation broke because `vaults[_token]` pointed to a different vault.

### Likelihood Explanation
This requires no privileged access — it triggers whenever a legitimate merchant/agent completes OAuth for a second shop in the same non-embedded browser session (a normal, unprivileged workflow for agencies/consultants running the same custom or non-embedded app across multiple client stores). It is not a forged-request or MITM scenario; it is a default-configuration correctness/isolation failure reachable by ordinary OAuth completion.

### Recommendation
Make the shop-scoped cookie path (or an equivalent shop-in-cookie-name scheme) the mandatory default for non-embedded apps rather than an opt-in, e.g., always derive `cookiePath` (or the cookie name) from `session.shop` when `cookiePath` is not explicitly supplied, so two shops can never collide on the same cookie without an explicit developer override. Document prominently that leaving `cookiePath` unset in a multi-shop non-embedded deployment is unsafe.

### Proof of Concept
1. Deploy a non-embedded app (`isEmbeddedApp: false`) without setting `cookiePath`.
2. In Browser Tab 1, complete OAuth for `shop-a.myshopify.com`; note `shopify_app_session` cookie now equals `offline_shop-a.myshopify.com` (per `getOfflineId`) at `path=/`.
3. In Browser Tab 2 (same browser/cookie jar), complete OAuth for `shop-b.myshopify.com`; the callback in `oauth.ts` lines 219-230 writes the same-named cookie at `path=/`, overwriting Tab 1's cookie value with `offline_shop-b.myshopify.com`.
4. Return to Tab 1 and make an authenticated request; the app now loads and operates using shop B's session/access token instead of shop A's.

- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
```

  /**
   * The path to use for the OAuth session cookie in non-embedded apps.
   *
   * By default the cookie is written with `path: '/'`, making it domain-wide.
   * This means that when a user authenticates multiple shops in separate tabs,
   * each OAuth callback overwrites the previous cookie, causing all tabs to use
   * the most-recently-authenticated shop.
   *
   * Set this to a string or a function returning a string to scope the cookie to
   * a URL path prefix that is unique per shop. The browser will then maintain
   * one cookie per shop and deliver only the matching one per request.
   *
   * **Requirement:** the configured path must match the actual URL structure of
   * your app — e.g. if each shop lives under `/shops/:shop/`, use that prefix.
   * The library cannot derive this automatically.
   *
   * @example
   * // Static path (single-shop apps or apps with no shop-specific routing)
   * cookiePath: '/'
   *
   * @example
   * // Factory function (multi-shop non-embedded apps)
   * cookiePath: (session) => `/shops/${session.shop}/`
   *
   * @defaultValue `'/'`
   */
  cookiePath?: string | ((session: Session) => string);
```
