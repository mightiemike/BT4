### Title
Relayer fee refund is sent unconditionally before the emulated transfer's success is known, decoupling payment from delivery - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract's `inner_rlp_execute` fires an independent fee-refund promise to the relayer as soon as it parses an `EOABaseTokenTransfer`/`ERC20Transfer` action with a non-zero fee, *before* the actual transfer action's outcome is known. The fee promise is not chained to (does not depend on) the success of the main action promise, so it is paid out regardless of whether the emulated transfer subsequently fails. This is the same bug class as the reported `DssChangeRatesSpell.cast()` issue: an operation is treated as "done"/paid for based on the initiating call succeeding, without checking whether the actual intended effect (the token/NEAR transfer) completed.

### Finding Description
`inner_rlp_execute` in [1](#0-0)  creates a standalone `promise_batch_create`/`promise_batch_action_transfer` to refund the relayer's fee as soon as the transaction is parsed into `EthEmulationKind::EOABaseTokenTransfer{fee,..}` or `EthEmulationKind::ERC20Transfer{fee,..}`, *before* the main action promise (`action_to_promise(...).then(rlp_execute_callback(...))`) is even constructed and dispatched later in the same function [2](#0-1) .

This fee-refund promise is a separate receipt with no data dependency on the outcome of the main transfer/ERC20-transfer promise. Meanwhile, `rlp_execute_callback` — the callback that eventually resolves the main action — only inspects `PromiseResult::Successful`/`PromiseResult::Failed` of that separate main-action promise, and on failure only refunds the caller's *attached deposit* (`caller_deposit`), not the fee that was already sent to the relayer [3](#0-2) . There is no mechanism that claws back or withholds the fee if the underlying `ft_transfer`/native transfer action later fails (e.g., insufficient token balance causing the NEP-141 contract to panic, or gas exhaustion in a nested call).

This mirrors the reported analog precisely: the "cast" (here, sending the fee) is marked complete based on the initiating call/parse succeeding, not on the semantic success of the target operation it was supposed to compensate for.

### Impact Explanation
An unprivileged transaction signer (the EOA-emulating account owner, or any relayer submitting an RLP transaction to `rlp_execute`, which is a public/payable method reachable by any RPC caller with an access key or via `predecessor_account_id`) can cause a relayer to be paid a fee for a transfer that never actually completes. Conversely and more importantly, a malicious *relayer* who controls fee flow could construct or replay borderline transactions (e.g., transfers destined to fail due to insufficient token balance or an unregistered/rejecting receiver) to repeatedly collect the fee component while the user's intended value transfer never lands — extracting value without delivering the corresponding service. This is an unauthorized value movement / fee bypass: value (the fee, taken from the wallet-contract account's balance) moves to the relayer even though the receipt tree it was meant to compensate ends up failing and rolling back. Since the fee payment is a separate, non-atomic receipt, it survives the rollback of the failing main-action receipt (per the "commit or rollback" per-receipt semantics of `apply_action_receipt`) [4](#0-3) .

### Likelihood Explanation
Medium. Triggering a failing `ft_transfer`/transfer while the fee is still paid only requires a single RLP-encoded transaction with a non-zero `fee` field targeting an ERC20/base-token transfer whose underlying action later fails (e.g., insufficient balance, or the token contract panicking on transfer to an unexpected account). No privileged access, validator collusion, or network-level assumptions are needed — a single transaction submitted through the normal wallet-contract flow (`rlp_execute` → `inner_rlp_execute`) is sufficient to reach this code path.

### Recommendation
Do not dispatch the fee-refund promise independently at parse time. Either (a) chain the fee payment as a `.then()` continuation of the main action's promise so it only executes after the main action succeeds, or (b) defer sending the fee until `rlp_execute_callback` observes `PromiseResult::Successful` for the main action, mirroring how `caller_deposit` refunds are already gated on the `PromiseResult::Failed` branch. Document, in the interim, that the fee is currently paid regardless of the ultimate success of the emulated transfer.

### Proof of Concept
1. An eth-implicit wallet-contract account holds some NEP-141 token balance below what is required for a signed ERC-20 "transfer" RLP transaction, but the RLP transaction specifies a non-zero relayer `fee`.
2. A relayer (or the account owner acting as their own relayer) submits this RLP transaction via `rlp_execute(target, tx_bytes_b64)`.
3. `inner_rlp_execute` parses the transaction as `EthEmulationKind::ERC20Transfer{fee, ..}`, and because `fee` is non-zero and `predecessor_account_id != current_account_id`, it immediately creates and dispatches the fee-transfer promise to the relayer (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:381-384`).
4. Separately, the storage-balance check / `ft_transfer` action promise is later dispatched and eventually fails (e.g., the token contract panics due to insufficient balance), causing `rlp_execute_callback` to see `PromiseResult::Failed` and only refund the `caller_deposit` (not the fee) (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:296-311`).
5. Result: the relayer has received the fee even though the ERC-20 transfer the fee was meant to compensate for never occurred — value was moved out of the account with no corresponding successful action, matching the "return value/effect not checked before treating the action as completed" bug class from the report.
