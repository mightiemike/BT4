### Title
External Job ID hash collision due to unpadded concatenation in CCIP spec generation - ([File: core/capabilities/ccip/validate/validate.go])

### Summary
`ExternalJobID` in `core/capabilities/ccip/validate/validate.go` derives a job's unique external UUID by concatenating three variable-length, attacker/operator-influenced string fields with `fmt.Appendf(nil, "%s%s%s", ...)` and hashing the result with SHA-256, with no length-prefixing, delimiter, or per-field hashing between the components. This is the same root-cause pattern as the reported Sui `compute_digest_for_modules_and_deps` bug: concatenating variable-length inputs directly before hashing allows different tuples of inputs to produce an identical byte stream and therefore an identical digest/ID.

### Finding Description
`ExternalJobID` builds its hash preimage as: [1](#0-0) 

`CapabilityLabelledName`, `CapabilityVersion`, and `P2PKeyID` are all free-form strings taken directly from `SpecArgs`, which is populated from a TOML job spec: [2](#0-1) 

Because the three fields are concatenated with zero separator (`"%s%s%s"`), two different (name, version, keyID) tuples can produce the exact same concatenated byte sequence — e.g. `("AB","C","X")` and `("A","BC","X")` yield the identical preimage `"ABCX"`, hence the identical SHA-256 digest and identical resulting UUID via `ExternalJobID`. `NewCCIPSpecToml` uses this function to auto-populate the `ExternalJobID` field of a newly generated CCIP job spec TOML when one isn't explicitly supplied: [3](#0-2) 

This mirrors the reported bug class exactly: no padding/delimiter between concatenated variable-length items before hashing, enabling a preimage collision that breaks the "must be unique" guarantee the digest/ID was designed to provide.

### Impact Explanation
`ExternalJobID` is meant to give each CCIP capability job a stable, unique identity. Chainlink's job pipeline treats `ExternalJobID` as the canonical identity for upsert/dedup operations. If two distinct capability configurations (different labelled name/version/key split across the same total character sequence) collide to the same external job ID, spec generation/upsert logic that keys off `ExternalJobID` could silently treat a new, differently-configured spec as the same job as an existing one — leading to an unintended overwrite of an existing job's on-chain/off-chain capability binding with different capability metadata or P2P key association than intended. This is a data-integrity/job-identity tampering risk in the job/workflow ingestion path, not merely a cosmetic bug.

### Likelihood Explanation
The collision requires an attacker or operator to control at least two of the three concatenated fields (`CapabilityLabelledName`, `CapabilityVersion`) so that a boundary can be shifted between them while keeping the total byte sequence identical, and matching `P2PKeyID`. This is a targeted but low-complexity construction (as demonstrated in the PoC below) — no cryptographic break is needed, only careful string boundary placement, which is exactly the technique used in the original Sui PoC.

### Recommendation
Hash each field independently (or length-prefix each field) before combining, e.g.:
```go
h := sha256.New()
for _, f := range []string{spec.CapabilityLabelledName, spec.CapabilityVersion, spec.P2PKeyID} {
    fh := sha256.Sum256([]byte(f))
    h.Write(fh[:])
}
in := h.Sum(nil)[:16]
```
or prepend each field's length before writing it, matching the standard fix pattern for this bug class (hash-then-hash / length-prefixing), as used correctly elsewhere in the codebase, e.g. `appendLengthPrefixed` in `core/services/ocr/capregconfig/digest.go`: [4](#0-3) 

### Proof of Concept
```go
// Both produce the same preimage "ABCX" -> identical SHA-256 digest -> identical ExternalJobID
specA := validate.SpecArgs{
    CapabilityLabelledName: "AB",
    CapabilityVersion:      "C",
    P2PKeyID:               "X",
}
specB := validate.SpecArgs{
    CapabilityLabelledName: "A",
    CapabilityVersion:      "BC",
    P2PKeyID:               "X",
}
idA, _ := validate.ExternalJobID(specA)
idB, _ := validate.ExternalJobID(specB)
// idA == idB, despite specA and specB describing different capabilities/versions.
```

// NewCCIPSpecToml creates a new CCIP spec in toml format from the given spec args.
func NewCCIPSpecToml(spec SpecArgs) (string, error) {
	type fullSpec struct {
		SpecArgs
		Type          string `toml:"type"`
		SchemaVersion uint64 `toml:"schemaVersion"`
		Name          string `toml:"name"`
		ExternalJobID string `toml:"externalJobID"`
	}
	extJobID, err := ExternalJobID(spec)
	if err != nil {
		return "", fmt.Errorf("failed to generate external job id: %w", err)
	}
	marshaled, err := toml.Marshal(fullSpec{
		SpecArgs:      spec,
		Type:          "ccip",
		SchemaVersion: 1,
		Name:          fmt.Sprintf("%s-%s", "ccip", extJobID),
		ExternalJobID: extJobID,
	})
	if err != nil {
		return "", fmt.Errorf("failed to marshal spec into toml: %w", err)
	}

	return string(marshaled), nil
}

func ExternalJobID(spec SpecArgs) (string, error) {
	in := fmt.Appendf(nil, "%s%s%s", spec.CapabilityLabelledName, spec.CapabilityVersion, spec.P2PKeyID)

func appendLengthPrefixed(buf []byte, data []byte) []byte {
	var lenBytes [4]byte
	binary.BigEndian.PutUint32(lenBytes[:], uint32(len(data))) //#nosec G115 - data length will never exceed uint32 max in practice
	buf = append(buf, lenBytes[:]...)
	buf = append(buf, data...)
	return buf
