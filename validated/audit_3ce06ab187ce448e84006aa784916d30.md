## Analysis Summary

I traced the DAO-membership "unused cap" bug-class into the accounts-index/bucket-map storage layer, since that is the closest unprivileged-user analog to a *configured maximum that is only advisory and never hard-enforced at the point of insertion*.

### Title
Accounts index memory threshold (`IndexLimit::Threshold.num_bytes`) is advisory only and is never enforced at insertion time - ([File: accounts-db/src/accounts_index/bucket_map_holder.rs])

### Summary
`AccountsIndexConfig::index_limit` lets a validator operator configure `IndexLimit::Threshold(IndexLimitThreshold { num_bytes, .. })` as the memory cap for the accounts index, analogous to `DAOConfig.maxMembers` being intended as a hard cap on DAO membership [1](#0-0) . Just like `maxMembers`, this "limit" is only ever used to derive advisory `high_water_mark`/`low_water_mark` thresholds that trigger a background eviction loop; it is never checked or enforced at the point where new entries are inserted into the in-memory index [2](#0-1) .

### Finding Description
`BucketMapHolder::new()` computes `threshold_entries_per_bin` (target/high/low water marks) purely from the configured `num_bytes`, and this is only consulted by `should_evict_based_on_count` / `should_evict_based_on_free_entries`, which are advisory booleans consumed by a periodic background flush/evict loop gated by `age_ms` (400ms for `Threshold` mode) [3](#0-2) . The actual insertion path, `InMemAccountsIndex::get_or_create_index_entry_for_pubkey`, inserts unconditionally into the in-memory `HashMap` with no check against the configured byte limit before returning [4](#0-3) . `check_flush_trigger` (the function that actually decides "should we evict now") only fires based on the precomputed count/free-entry watermarks, and is itself invoked lazily/periodically rather than being a blocking gate on insert [5](#0-4) .

This mirrors the reported bug class exactly: a field explicitly documented as "The memory limit, in bytes, for the entire accounts index" [1](#0-0)  is never enforced as a hard cap at the point new entries are created — it is only used to schedule a best-effort background eviction, the same "validation only, not enforcement" pattern as `maxMembers`.

### Impact Explanation
Because insertion into the in-memory index bin is unconditional and eviction is only best-effort/periodic (400ms cadence, watermark-based, background-thread driven), a burst of new unique pubkeys created within a short window (well within normal, unprivileged transaction throughput) can push the resident set size of the accounts index substantially past the operator-configured `--accounts-index-limit` before the background evictor catches up. On validators that sized their memory allocation around the configured limit (the CLI documentation explicitly promises this bound: "the accounts index may use up to 50 GB of memory" [6](#0-5) ), this can produce disproportionate memory/CPU cost, increased GC/rehash pressure, and in the worst case contribute to OOM-driven node instability — without any single malicious/mocked-only precondition, since the only requirement is normal high-rate account creation.

### Likelihood Explanation
Likelihood is moderate: it requires no privileged access, no crafted malicious input, and no interaction with excluded areas (sBPF, Alpenglow/votor, RPC, Loader V4, snapshots). It only requires a sustained rate of new-account creation that exceeds the background eviction rate, which is governed by fixed constants (`DEFAULT_NUM_ENTRIES_OVERHEAD` / `DEFAULT_NUM_ENTRIES_TO_EVICT`) rather than any adaptive/blocking backpressure tied to the configured byte limit.

### Recommendation
Add a genuine enforcement path: either (a) block/backpressure the write path (similar to `should_write_through`) when a bin's in-memory usage already exceeds `high_water_mark` by more than the configured overhead, forcing synchronous eviction/write-through before accepting more entries, or (b) make the eviction loop's cadence and batch size adaptive to insertion rate rather than fixed constants, so the "num_bytes" limit is actually respected rather than being a soft target for a periodic background task.

### Proof of Concept
Not directly exploitable as a standalone PoC without a running validator instance; the root-cause code path can be demonstrated via unit tests already present that show insertion always succeeds and only *stats* record that a threshold was crossed, without any insertion failure/backpressure: [7](#0-6)  (`test_check_flush_trigger_high_count` shows that crossing `high_water_mark` only flips a boolean/stat — it does not stop or throttle further inserts).

---

Note: this finding is a plausible structural analog (advisory-only "limit" field) rather than a certainty of severe impact — the actual blast radius depends on operational deployment specifics (whether operators rely on `--accounts-index-limit` as a hard memory ceiling) which I cannot fully verify from the code alone.

    /// Returns true when a bin's entry count is high enough that eviction should begin.
    /// The threshold is the configured `high_water_mark`.
    pub fn should_evict_based_on_count(&self, count: usize) -> bool {
        match &self.threshold_entries_per_bin {
            None => self.is_disk_index_enabled(),
            Some(threshold_entries_per_bin) => count > threshold_entries_per_bin.high_water_mark,
        }
    }

    /// Returns true when a bin's HashMap free entries (`capacity - len`) are low
    /// enough that eviction should begin to prevent an imminent capacity doubling.
    /// The threshold is the overhead gap between `target_entries` and `high_water_mark`.
    pub fn should_evict_based_on_free_entries(&self, free_entries: usize) -> bool {
        match &self.threshold_entries_per_bin {
            None => self.is_disk_index_enabled(),
            Some(threshold_entries_per_bin) => {
                let overhead = threshold_entries_per_bin
                    .target_entries
                    .saturating_sub(threshold_entries_per_bin.high_water_mark);
                free_entries < overhead
            }
        }
    }

    fn check_flush_trigger(&self) -> bool {
        let (entries_in_bin, capacity) = {
            let map = self.map_internal.read().unwrap();
            (map.len(), map.capacity())
        };

        // Skip during initial growth: below HWM, low free entries reflect a not-yet-grown
        // table, not tombstones. If tombstones do force a doubling before len crosses HWM,
        // the count check catches it later once len grows past HWM.
        if let Some(thresholds) = &self.storage.threshold_entries_per_bin
            && capacity < thresholds.high_water_mark
        {
            return false;
        }

        let high_count_triggered = self.storage.should_evict_based_on_count(entries_in_bin);
        let low_free_entries_triggered = self
            .storage
            .should_evict_based_on_free_entries(capacity.saturating_sub(entries_in_bin));
        if !high_count_triggered && !low_free_entries_triggered {
            return false;
        }
        if low_free_entries_triggered {
            // Primary case: low free-entry headroom (typically from tombstones).
            Self::update_stat(&self.stats().evict_triggered_by_low_free_entries, 1);
        } else {
            // Backstop: bin is past the high-water mark while free-entry headroom
            // still has slack — typically because the hashmap doubled in size.
            Self::update_stat(&self.stats().evict_triggered_by_high_count, 1);
        }
        true
    }
