### Title
Contract self-destruct bypasses freeze-period lock by paying still-frozen V1 stake directly to the inheritor as spendable balance - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.transferDelegatedResourceToInheritor`, invoked from `Program.suicide`/`suicide2` when a contract self-destructs, converts the contract owner's still-locked (old-model, "V1") frozen balance for bandwidth/energy directly into liquid, spendable TRX credited to the `inheritor`/`obtainer` address, without checking whether the frozen balance's lock period (`expireTime`) has elapsed. This mirrors the reported `CollateralPool.merge` bug class: state is "merged"/transferred between accounts while the withdrawal/lock restriction attached to that state is silently dropped.

### Finding Description
When a contract calls `SUICIDE`/`SELFDESTRUCT`, `Program.suicide()`/`suicide2()` calls `transferDelegatedResourceToInheritor(owner, obtainer, repo)` (guarded by `VMConfig.allowTvmFreeze()`): [1](#0-0) 

Inside that helper, the owner's currently frozen (staked) balance for bandwidth and energy is read directly from `AccountCapsule` and added as **liquid balance** to the inheritor, with no check of the frozen entry's `expireTime` (the field that normally enforces the mandatory 3‑day freeze/lock period, `FROZEN_PERIOD`): [2](#0-1) 

Contrast this with the normal, non-suicide path for releasing frozen balance, `UnfreezeBalanceProcessor.validate`, which explicitly enforces that the freeze period must have elapsed (`frozenForEnergy.getExpireTime() > now` → reject) before any frozen amount can become spendable: [3](#0-2) 

In `transferDelegatedResourceToInheritor`, this expiry check is entirely absent — the full `frozenBalanceForBandwidth`/`frozenBalanceForEnergy` amount is unconditionally paid out as liquid balance to whatever address is chosen as `obtainer`/`inheritor` in the `SUICIDE` opcode call. The stale comment "// transfer all kinds of frozen balance to BlackHole" (while the code actually credits the attacker-controlled `inheritorAddr`) further indicates the withdrawal-restriction semantics were not carried through when this code merges/transfers the frozen-balance state between accounts, exactly analogous to `CollateralPool.merge` dropping the `child` pool's withdrawal limits when moving collateral shares to `parent`.

### Impact Explanation
An attacker can:
1. Deploy a contract, and use `FreezeBalanceContract` (old model) to freeze TRX for BANDWIDTH/ENERGY on the contract's own account (locking it for the mandatory freeze period and, since `allowTvmFreeze()`-gated flows are still present in this codebase, obtain TRON Power/bandwidth for it).
2. Immediately execute `SUICIDE`/`SELFDESTRUCT` inside the same or a later transaction, naming an address the attacker controls as beneficiary.
3. `transferDelegatedResourceToInheritor` pays out the entire still-locked frozen balance as immediately spendable TRX to that address — completely bypassing the freeze lock period that every other code path (`UnfreezeBalanceActuator`/`UnfreezeBalanceProcessor`) enforces.

This lets an attacker turn staked/locked TRX into instantly liquid, transferable funds, defeating the purpose of the mandatory freeze period underlying TRON's staking/voting-weight/resource model — a concrete accounting/invalid-state bypass, not merely theoretical.

### Likelihood Explanation
Reaching this path only requires deploying a simple contract that (a) freezes balance for itself via `FreezeBalanceContract` and (b) calls `SUICIDE`, which are both unprivileged, ordinary user operations available on TVM. The guard `VMConfig.allowTvmFreeze()` must be enabled (this is a chain parameter controlling the old V1 freeze/resource model); when active, no special permission or race condition is needed, making this practically reachable by any user of the network with that feature enabled.

### Recommendation
In `transferDelegatedResourceToInheritor` (and equivalently review `transferFrozenV2BalanceToInheritor` for the same class of issue with non-expired `unfrozenV2` entries, which are currently `clearUnfrozenV2()`'d without transfer), do not unconditionally credit spendable balance for frozen amounts whose `expireTime` has not yet passed. Either:
- Reject/disallow self-destruct while the account has non-expired frozen V1 balances, or
- Transfer the *frozen* state itself (with its original `expireTime`) to the inheritor's frozen list, rather than converting it into liquid balance, so the same withdrawal timing restrictions the protocol otherwise enforces are preserved.

### Proof of Concept
1. Attacker deploys `Attacker` contract A.
2. Attacker sends `FreezeBalanceContract` with `owner_address = A`, `resource = BANDWIDTH` (or `ENERGY`), freezing `N` TRX (locks for `FROZEN_PERIOD`, see `WithdrawBalanceActuator`/freeze constant usage) — verified enforced elsewhere by `UnfreezeBalanceProcessor.validate` at [4](#0-3) .
3. In the same block (well before `expireTime`), attacker triggers contract A's `SUICIDE`/`SELFDESTRUCT(attackerEOA)`.
4. `Program.suicide()` calls `transferDelegatedResourceToInheritor(A, attackerEOA, repo)` at [5](#0-4) , which reads `frozenBalanceForBandwidthOfOwner`/`frozenBalanceForEnergyOfOwner` and calls `repo.addBalance(inheritorAddr, ...)` unconditionally at [6](#0-5) .
5. `attackerEOA` immediately has `N` TRX of spendable balance, despite the freeze lock period never having elapsed — confirmable by comparing account balance before/after the transaction and noting `N` TRX is spendable without any elapsed `FROZEN_PERIOD` and without ever calling `UnfreezeBalanceContract`.

**Note on verification limits:** I was unable to fully confirm the exact numeric value of `FROZEN_PERIOD`/freeze duration or trace every downstream consumer of `addTotalNetWeight`/`addTotalEnergyWeight` in this pass; a Devin session with full repository access could compile a concrete integration test (similar to `framework/src/test/java/org/tron/core/actuator/WithdrawBalanceActuatorTest.java`) exercising `Program.suicide` to empirically confirm the bypass end-to-end.
