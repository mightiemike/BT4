### Title
Domain-transformation target namespace collision allows attacker-submitted shop to impersonate a transformed tenant's session ID - (File: `packages/apps/shopify-api/lib/utils/domain-transformer.ts`)

### Summary
When `domainTransformations` is configured, `getTransformationDomains` adds both the source and target domain patterns to `sanitizeShop`'s allowed `domainsRegex`, but `applyDomainTransformations` only transforms shops matching the *source* pattern and passes through anything else (including the raw target domain) unchanged. An attacker can submit a shop string that is already in the *target* domain namespace, bypassing the intended source-to-target mapping, and land on the exact same sanitized shop value—and therefore the same session key—as a legitimately transformed merchant.

### Finding Description
`sanitizeShop` (`packages/apps/shopify-api/lib/utils/shop-validator.ts:14-24`) builds `domainsRegex` by concatenating static trusted domains with `getTransformationDomains(config)`, which extracts **both** the source domain (e.g. `my\.shop\.dev`) and the target domain (e.g. `dev-api\.shop\.dev`) from each transformation's `match`/`transform` (`domain-transformer.ts:106-126`). This means `shopUrlRegex` at `shop-validator.ts:26-28` treats `shop1.dev-api.shop.dev` as a syntactically valid, trusted shop just as much as `shop1.my.shop.dev`.

After the regex check passes, `sanitizeShop` unconditionally calls `applyDomainTransformations(sanitizedShop, config)` (`shop-validator.ts:44-46`). Inside `applyDomainTransformations` (`domain-transformer.ts:22-58`):
- For `shop1.my.shop.dev`, the transformation's `match` regex (`^([a-zA-Z0-9-_]+)\.my\.shop\.dev$`) matches, and it is rewritten to `shop1.dev-api.shop.dev`.
- For `shop1.dev-api.shop.dev` submitted directly, that same `match` regex does **not** match (it only matches `.my.shop.dev` suffixes), so the loop falls through and line 57 returns the input **unchanged**: `shop1.dev-api.shop.dev`.

Both inputs therefore produce the identical sanitized output `shop1.dev-api.shop.dev`. This value flows directly into session key derivation in `packages/apps/shopify-api/lib/session/session-utils.ts`:
```
getJwtSessionId(config)(shop, userId) => `${sanitizeShop(config)(shop, true)}_${userId}`
getOfflineId(config)(shop) => `offline_${sanitizeShop(config)(shop, true)}`
``` [1](#0-0) 
Any code path that accepts an attacker/merchant-influenced `shop` value (OAuth begin/callback, token exchange, JWT `dest` claim decoding in `getCurrentSessionId`, `customAppSession`) and feeds it into these functions is affected, since `sanitizeShop` is the sole gate and it is fooled into treating the pre-transformed (target-domain) string as already-canonical.

No existing check (HMAC, JWT signature, nonce) prevents this, because the collision occurs entirely within shop-string normalization logic that both legitimate and forged shop identifiers pass through equally — the forgery is in the *shop identifier itself*, not in any signed token. A user with any ability to influence the `shop`/`dest` value used to look up/create a session (e.g., during install, token exchange, or a custom-domain embedded session) can trigger the collision.

### Impact Explanation
This breaks tenant isolation: two different logical shop identifiers are mapped to one session-storage key. This enables session/token overwrite (the attacker's install or session write clobbers or is clobbered by the legitimate transformed tenant's session) or lookup theft (the attacker's request resolves to the legitimate tenant's session/access token). This maps to Shopify's "cross-tenant data/session access" and "injection into session storage" bounty impact classes.

### Likelihood Explanation
Requires the host app to configure `domainTransformations` (a supported, documented feature, not a hardening bypass) — this is a real, intended configuration used by apps supporting custom/dev domains. Once configured, exploitation requires no privileged role: an unprivileged party only needs to cause a shop value equal to the *target* domain literal to be processed by `sanitizeShop`, which is fully deterministic and repeatable.

### Recommendation
In `applyDomainTransformations`, reject (return `null`) or explicitly detect when the input already matches a known **target** domain pattern rather than silently passing it through unchanged. Alternatively, in `getTransformationDomains`, do not add target domains to `sanitizeShop`'s accepted `domainsRegex` unless they are also validated as not colliding with a source-eligible identifier — i.e., only allow the target domain through `sanitizeShop` if it was actually produced by a transformation, not accepted as raw attacker input. The safest fix is to make transformation application idempotent-safe by short-circuiting when the shop's target-domain segment is already canonical, while ensuring the untransformed literal target string can never be equated with the transformed value of a different source segment.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/utils/__tests__/domain-transformer.test.ts (new test)
import {sanitizeShop} from '../shop-validator';
import {ConfigInterface} from '../../base-types';

const config = {
  domainTransformations: [
    {
      match: /^([a-zA-Z0-9][a-zA-Z0-9-_]*)\.my\.shop\.dev$/,
      transform: '$1.dev-api.shop.dev',
    },
  ],
} as ConfigInterface;

test('attacker-submitted target domain collides with transformed tenant shop', () => {
  const direct = sanitizeShop(config)('shop1.dev-api.shop.dev', true);
  const transformed = sanitizeShop(config)('shop1.my.shop.dev', true);

  expect(direct).toBe('shop1.dev-api.shop.dev');
  expect(transformed).toBe('shop1.dev-api.shop.dev');
  expect(direct).toBe(transformed); // collision confirmed
});
