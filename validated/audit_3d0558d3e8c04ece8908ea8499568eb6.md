### Title
Webhook shop-domain identity is not cryptographically bound to the HMAC signature, allowing cross-shop attribution of attacker-controlled webhook payloads - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts, packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
Shopify webhook authentication in this SDK verifies only that the raw request body was signed with the app's single shared `apiSecretKey`; it never verifies that the `X-Shopify-Shop-Domain` (or events-equivalent) header — the field used to decide *which merchant's offline session/access token* gets attached to the webhook — is actually tied to the entity that produced that signature. This is structurally the same class of bug as the reported "payer is not tied to msg.sender" issue: an identity field that drives privileged behavior (loading a specific shop's session) is taken from unauthenticated, unsigned request metadata rather than being bound to the cryptographic proof of origin.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC solely over `rawBody` using the app-wide `config.apiSecretKey`, and compares it against the header HMAC: [1](#0-0) 

This secret is identical for *every shop* that has the app installed — it is not per-shop. Separately, `validateFactory`/`checkWebhookHeaders` pulls the shop identity purely from the `X-Shopify-Shop-Domain` (or events `Domain`) header, with no cross-check against anything in the signed body: [2](#0-1) [3](#0-2) 

The consuming handlers then use this unauthenticated `domain`/`check.domain` value directly to look up and attach that shop's offline session (containing its access token) to the webhook context: [4](#0-3) [5](#0-4) 

Because the HMAC only proves "this body was produced by Shopify for *some* installation of this app" (using the shared app secret) rather than "for shop X specifically," an attacker who controls their own store's installation can capture a legitimately-signed `(rawBody, hmac)` pair delivered to their own endpoint (or otherwise obtain one, e.g. via a re-triggerable/idempotent webhook), then replay that exact body+HMAC to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` header value. The signature check still passes (it never inspected the domain header), and `checkWebhookHeaders` accepts whatever domain the attacker supplied, which then flows into `ensureValidOfflineSession(params, check.domain)` and into the handler as `shop`.

### Impact Explanation
An attacker with any installation of the target app can forge webhook deliveries "from" an arbitrary victim shop, causing:
- The app to load and attach the victim shop's real offline session/access token to attacker-controlled event data (`webhookContext.session`, `admin` client bound to the victim), [4](#0-3)  which is then passed to the app's registered webhook callback for further processing/business logic keyed on `shop`.
- Cross-tenant data confusion/injection: any app logic that trusts `topic`/`shop`/payload combination as authoritative (e.g., updating per-shop billing state, order records, inventory sync, deletion flows like `app/uninstalled` or `shop/redact`) can be triggered against a shop that never actually sent that event, potentially causing state corruption, unwanted data mutations via the victim's own access token, spam/DoS on the victim's tenant, or triggering destructive GDPR-style webhooks against the wrong shop.
- This mirrors the reported bug class: a field ("payer"/"shop domain") that determines whose resources/credentials get used is not tied to the actual authenticated originator of the request.

Severity should be considered Medium, similar to the original finding, since exploitation requires the attacker to already control an app installation and to obtain a validly-signed body (limiting free-form payload forgery), but it does allow real cross-tenant misattribution without needing to know the shared secret.

### Likelihood Explanation
Requires an attacker to have (or create) their own installation of the vulnerable app to obtain at least one legitimately HMAC-signed `(rawBody, hmac)` pair, and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with a custom `X-Shopify-Shop-Domain` header — both of which are trivial for any merchant/developer with an app install. No secrets need to be leaked and no privileged access is required, since the domain header is attacker-controlled while the HMAC verification path never examines it.

### Recommendation
Bind the shop identity used for session lookup to information that is actually protected by the signature, or otherwise validate it: e.g., include the shop domain in the HMAC-signed payload/canonical string, cross-verify `X-Shopify-Shop-Domain` against a shop reference embedded in the signed body, or additionally check the domain against a known/allow-listed set of shops that installed the app (with per-shop session existence not being sufficient, since any shop that ever installed will have a stored session). At minimum, do not treat `check.domain` as an authenticated value — verify it against something cryptographically tied to the specific delivery before using it to select which shop's session/access token to attach to the request context in `authenticateWebhookFactory` and `ensureValidOfflineSession`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.io`, obtaining a valid webhook subscription (e.g. `PRODUCTS_CREATE`).
2. Attacker triggers/receives a legitimately signed webhook delivery, capturing `rawBody` and the `X-Shopify-Hmac-Sha256` header value (this HMAC is valid because it's computed with the shared `config.apiSecretKey`, per `validateHmacString` in `hmac-validator.ts`).
3. Attacker replays the exact same `rawBody` + `X-Shopify-Hmac-Sha256` to the app's `/webhooks` endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.io`.
4. `validateHmacFromRequestFactory` succeeds (it only checks body vs. HMAC) [1](#0-0) ; `checkWebhooksHeaders` accepts the forged `domain` header unconditionally [3](#0-2) .
5. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` with `check.domain === 'victim-shop.myshopify.io'`, loading the victim's real offline session/access token and passing it, along with the attacker's payload, to the app's webhook handler as if it genuinely came from the victim shop [4](#0-3) .

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    rawBody,
    ...adapterArgs

      await abstractConvertRequest(adapterArgs);

      return validHmacResult;

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
