## Title
Duplicate accounts removed from capitalization/lt-hash during `generate_index` are not deducted from `storage_info` before `set_storage_count_and_alive_bytes` - stale per-storage alive-byte/count accounting - (File: accounts-db/src/accounts_db.rs)

### Summary
`AccountsDb::generate_index` (agave `accounts-db/src/accounts_db.rs`) computes several accumulator fields per storage while scanning slots — `capitalization`, `accounts_data_len`, `lt_hash`, and `storage_info` (a per-`store_id` `stored_size`/`count` map) — during the initial parallel scan in `generate_index_for_slot`. After the scan, the code explicitly walks all duplicate pubkeys (`visit_duplicate_pubkeys_during_startup`) and subtracts their contribution from `capitalization` (`total_accum.capitalization = total_accum.capitalization.checked_sub(capitalization_from_duplicates)...`) and `accounts_data_len` (`total_accum.accounts_data_len -= accounts_data_len_from_duplicates`), and mixes the duplicate lt-hash *out* of `total_accum.lt_hash`. [1](#0-0) 

However, `total_accum.storage_info` (the `StorageSizeAndCountList` populated with `stored_size`/`count` per storage during the scan, see `accum.storage_info.push((store_id, info))`) is passed unmodified into `self.set_storage_count_and_alive_bytes(total_accum.storage_info, &mut timings)` — with no corresponding subtraction of the duplicate accounts' size/count that were just removed from capitalization/accounts_data_len/lt_hash. [2](#0-1) [3](#0-2) 

This mirrors the Tigris `_handleOpenFees` bug class exactly: one derived value (`capitalization`/`accounts_data_len`/`lt_hash`) is corrected for a secondary factor (duplicate/referral fee) that is calculated once and applied to some outputs but not to a sibling output (`storage_info`) that is computed from the very same intermediate scan and is expected to be internally consistent with it.

### Finding Description
During index generation from an on-disk snapshot/storages set, each storage (AppendVec) is scanned once via `generate_index_for_slot`, accumulating per-account contributions into `capitalization`, `accounts_data_len`, `lt_hash`, and `storage_info` (`stored_size`, `count`) keyed by `store_id`. [4](#0-3) 

Because a pubkey can appear in multiple slots/storages (older, now-obsolete versions of the same account), `generate_index` performs a second pass over all "duplicate" pubkeys, and for each duplicate pubkey walks its slot list to determine which entries are stale and must be removed from the index (and from the accumulated capitalization/accounts_data_len/lt_hash), since only the newest version of the account should count toward the final capitalization and be "alive". This correction is applied to `total_accum.capitalization`, `total_accum.accounts_data_len`, and `total_accum.lt_hash`. [5](#0-4) 

`storage_info` (the per-store `stored_size`/`count`, later consumed by `set_storage_count_and_alive_bytes`) is populated during the *same* initial scan and includes the bytes/counts of every account version encountered, including the stale duplicate versions in older storages that get logically removed by the duplicate-visiting pass. Unlike capitalization/accounts_data_len/lt_hash, there is no equivalent post-scan adjustment applied to `storage_info` to remove the duplicate accounts' `stored_size`/`count` contribution from the storages that actually hold the stale (duplicate, older) versions before it is handed to `set_storage_count_and_alive_bytes`. [6](#0-5) 

The `stored_size`/`count` recorded for the *older* storages therefore reflects "an account was alive in this store" for accounts that are, immediately afterward, unref'd/reclaimed as stale duplicates by `mark_obsolete_accounts_at_startup` in the very same `generate_index` call. This is the same class of bug as the Tigris finding: `_feePaid`/`_marginAfterFees` is computed once from a formula that omits a component (referral fee) that is known and applied elsewhere in the same code path, leading two derived quantities that should be mutually consistent (position size vs. margin-after-fees; here, capitalization/accounts_data_len vs. storage alive-byte/count) to diverge.

### Impact Explanation
`set_storage_count_and_alive_bytes` seeds the "num_alive_accounts"/"num_alive_bytes" state used by `AccountsDb` shrink/clean scheduling (`is_candidate_for_shrink`, `alive_bytes_after_shrink`, `select_candidates_by_total_usage`) immediately after startup index generation. If the alive-byte/count values for older storages are overstated because they still include already-removed duplicate account bytes, shrink candidate selection and productivity checks (`is_shrinking_productive`, `should_not_shrink`) operate on inflated alive-byte figures for those storages. This can cause a validator to under-shrink storages that are, in reality, much sparser than reported, leaving dead/duplicate-account byte ranges resident on disk longer than intended — a disproportionate storage-cost outcome consistent with the accepted impact categories (in-scope: "disproportionate storage and CPU cost"). It does not directly corrupt capitalization or the bank hash (those are explicitly corrected), so it is not a balance/hash-divergence bug; the divergence is confined to the storage-usage bookkeeping that drives shrink heuristics.

### Likelihood Explanation
This code path executes on every validator startup that performs `generate_index` from snapshot-restored storages whenever there is more than one version of any account across slots — which is the common case for any node that has been running for a nontrivial period before snapshotting (accounts are almost always rewritten across multiple slots). The duplicate-visiting logic (`visit_duplicate_pubkeys_during_startup`) is exercised on essentially every startup with a nontrivial account set, so the omitted `storage_info` correction is very likely reachable, though its user-visible effect (skewed shrink timing) is subtle and cumulative rather than immediately observable.

### Recommendation
When walking duplicate pubkeys in `visit_duplicate_pubkeys_during_startup`/the surrounding fold in `generate_index`, also accumulate the `stored_size` (and count) of the stale/duplicate account entries per `store_id`, and subtract that amount from the corresponding entries in `total_accum.storage_info` before calling `self.set_storage_count_and_alive_bytes(total_accum.storage_info, &mut timings)`, mirroring the existing `checked_sub` treatment already applied to `capitalization` and `accounts_data_len`.

### Proof of Concept
Not independently reproduced in this analysis; the divergence is inferred from static code review of `generate_index`/`generate_index_for_slot` in `accounts-db/src/accounts_db.rs`, where `capitalization`, `accounts_data_len`, and `lt_hash` are explicitly corrected for duplicate accounts (lines ~6107-6112) but `storage_info` (populated at lines ~5793-5816) is passed to `set_storage_count_and_alive_bytes` at line ~6125 with no equivalent correction. A concrete repro would involve: (1) creating an account, rooting/flushing it in slot N, (2) rewriting the same account in a later slot M (creating a duplicate/stale entry in storage N), (3) restarting the node so `generate_index` runs against on-disk storages for both N and M, and (4) inspecting `AccountStorageEntry::alive_bytes()`/`count()` for storage N immediately after startup versus after a subsequent `clean_accounts` pass, to check whether storage N's alive-byte/count figures were initially overstated by the size of the stale duplicate account before clean corrects it.
