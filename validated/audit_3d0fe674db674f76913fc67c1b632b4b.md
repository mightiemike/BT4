### Title
`liquidity_cap` defined in `TokenConfig` is never read or enforced during PRC20 deposit minting - ([File: x/uexecutor/keeper/handler.go])

### Summary
`uregistry.TokenConfig.LiquidityCap` is documented as "max supply cap for this token" and is a mandatory field (`ValidateBasic` rejects an empty value), but no code path in `x/uexecutor` — the module that actually mints PRC20 supply on inbound execution — ever reads or checks it. This is the direct Push Chain analog of the Midas `RedemptionVault` bug: a cap/allowance is defined in configuration and documented as a protocol invariant, but the execution path that performs the value-creating operation (mint here, redeem there) never consults it.

### Finding Description
`TokenConfig` stores `LiquidityCap` as a required field: [1](#0-0) [2](#0-1) 

The field is explicitly documented as a per-token max-supply cap: [3](#0-2) 

However, the actual PRC20 minting path — `depositPRC20` in `x/uexecutor/keeper/handler.go` — reads `tokenConfig.NativeRepresentation` for the PRC20 contract address and calls `CallPRC20Deposit` with the raw inbound `amount`, with no reference anywhere to `LiquidityCap`: [4](#0-3) 

`CallPRC20Deposit` in turn issues a `DerivedEVMCall` to `depositPRC20Token` on the `UNIVERSAL_CORE` handler contract with the amount unmodified and unchecked against any cap: [5](#0-4) 

`ExecuteInboundFunds` (the inbound-quorum-triggered execution entrypoint for `TxType_FUNDS`) calls `depositPRC20` directly with `inbound.Amount` taken straight from the voted `Inbound` record, again with no cap check: [6](#0-5) 

The same unchecked pattern repeats in the `FUNDS_AND_PAYLOAD` execution path: [7](#0-6) 

A grep across `x/uexecutor` for any use of `LiquidityCap`/`liquidity_cap`/`totalSupply`/`maxSupply` returns no hits outside the protobuf-generated `uregistry` types — confirming the field is stored and validated on write, but never read on the mint path.

### Impact Explanation
Under an honest-validator, honest-node model, an unprivileged external attacker can deposit real funds on a source chain (e.g. real USDC on Ethereum) that exceed the `liquidity_cap` configured for that token in `uregistry`. Once Universal Validators observe and vote the inbound to quorum (an ordinary, permissionless flow reachable via `MsgVoteInbound` by any bonded UV observing a genuine on-chain event), `x/uexecutor` mints the corresponding PRC20 supply with no upper bound check, silently exceeding the registry's configured max-supply invariant.

This breaks the accounting/registry invariant the protocol itself documents and validates on write (`liquidity_cap cannot be empty`), and any downstream logic that assumes PRC20 total supply for a given token is bounded by its registry cap (liquidity provisioning, risk parameters, swap routing assumptions in `CallPRC20DepositAutoSwap`, etc.) can be silently violated. This falls under "corruption of PRC20 or native asset accounting … token mapping … or canonical UniversalTx state" in the allowed impact set, since the mint operation ignores a documented protocol-level cap that governs PRC20 supply integrity.

Unlike the original Midas bug (which enabled genuine over-redemption of a shared vault beyond an admin-set allowance with no offsetting deposit), this Push Chain analog requires the attacker to actually deposit real underlying value on the source chain to trigger minting — so it is not a direct fund-drain, but it is a direct violation of the stated invariant with no enforcement mechanism anywhere in the in-scope Go code.

### Likelihood Explanation
High reachability: the path is exercised by any ordinary `TxType_FUNDS` / `FUNDS_AND_PAYLOAD` inbound reaching UV quorum, which is the default, permissionless deposit flow of the protocol — no privileged actor is required. The only "attacker" action needed is depositing a large amount on a supported source chain, which is intentionally an unprivileged, user-facing action.

### Recommendation
In `depositPRC20` (`x/uexecutor/keeper/handler.go`) or in `ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload`, before calling `CallPRC20Deposit`/`CallPRC20DepositAutoSwap`, query the current PRC20 total supply (or track cumulative minted amount in `uexecutor` state) for the token and compare `currentSupply + amount` against `tokenConfig.LiquidityCap`. Reject or cap the deposit (and route to the existing revert/outbound path) when the configured liquidity cap would be exceeded, mirroring how the Midas fix added the missing allowance check into the redemption path.

### Proof of Concept
Not independently executable from static review alone; the analysis is a structural code-path trace showing `LiquidityCap` is validated on `MsgAddTokenConfig`/`MsgUpdateTokenConfig` but never referenced in the runtime mint path. Concretely:
1. Admin registers a token with `liquidity_cap = "1000000000000000000000000"` (1,000,000 tokens at 18 decimals) via `MsgAddTokenConfig`.
2. An unprivileged user deposits an amount on the source-chain gateway far exceeding this cap (e.g. 10,000,000 tokens), which is a legitimate, permissionless action.
3. Universal Validators observe and vote the inbound (`MsgVoteInbound`) to quorum — no privileged action.
4. `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints the full 10,000,000-token PRC20 amount with no check against the 1,000,000 `liquidity_cap`, as shown in the cited code — the field is never read.

**Caveat:** Whether the PRC20 contract itself (in the separate `push-chain-core-contracts` repository, out of scope for this index) independently enforces a supply cap at the Solidity level cannot be confirmed from this repository's indexed contents. This finding is scoped strictly to the fact that the in-scope Go/`x/uexecutor` code never reads or enforces `LiquidityCap` on the mint path, which is the direct structural analog of the reported bug class (a documented cap/allowance omitted from the value-creating operation).

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
