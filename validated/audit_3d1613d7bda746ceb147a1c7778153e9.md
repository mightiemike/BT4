## Title
`replay_on_archive` verification (`ensure_match_transaction_info`) accepts replayed transactions whose state/hot-state/position checkpoint roots diverge from the authenticated ledger - ([File: types/src/transaction/mod.rs])

## Summary
`TransactionOutput::ensure_match_transaction_info` — the comparator used by `db-tool`'s `replay_on_archive` to validate that a locally re-executed transaction matches the backup-provided, ledger-info-authenticated `TransactionInfo` — checks status, gas, write-set hash (`state_change_hash`) and event root hash, but explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`. This is called out in-code as a known TODO, but it is live, unguarded code on the verification path today.

## Finding Description
`TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs` is documented as verifying that a `TransactionOutput` matches its `TransactionInfo`: [1](#0-0) 

However at the end of the function, the code explicitly leaves out validation of the checkpoint hashes: [2](#0-1) 

`TransactionInfo` (V1) actually carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields that are meant to bind a committed transaction to a specific state Merkle root / hot-state root / position-state root: [3](#0-2) 

This comparator is the sole re-execution check used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which replays archived transactions with the VM and compares the freshly executed `TransactionOutput` against the `expected_txn_info` pulled from the (ledger-info-signed) backup: [4](#0-3) 

Because `ensure_match_transaction_info` never compares `self`'s locally computed checkpoint roots against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, a state-checkpoint transaction whose write-set hash and events happen to match, but whose resulting Jellyfish Merkle / hot-state / position-state root diverges from the authenticated value in the backup, will still pass `replay_on_archive` verification silently.

## Impact Explanation
This breaks the "committed state that differs from the correct VM result... accepted as valid" invariant: `replay_on_archive` is explicitly the tool used to independently verify that historical/archived ledger data actually matches deterministic VM re-execution. If a state root diverges (due to a storage bug, replay-path bug, or a maliciously altered archive/backup that keeps write-set/event hashes but tampers with committed state-tree contents at a checkpoint boundary), this verification path will not detect it, since it never re-derives or cross-checks the checkpoint root hashes it is meant to protect. This directly undermines the security property that "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" for anyone relying on `replay_on_archive` as an integrity guarantee (a key tool referenced by Aptos infrastructure operators / auditors for validating archive-node data).

The impact is limited to the fact that this is a verification/tooling gap rather than a live consensus-breaking bug — it does not by itself corrupt any committed state on mainnet, but it defeats an important authenticated-verification mechanism meant to catch such corruption, satisfying the "proof/replay/restore path fails to bind to the correct root" category of impact.

## Likelihood Explanation
Likelihood is moderate: the write-set hash and event root hash checks that remain in place will catch the vast majority of naive divergences, since state values feed into the write set. However, the code comment itself acknowledges a concrete scenario (`COMPUTE_TRADING_NATIVE_STATE_ROOTS` / "trading-native" state roots) where the state/hot-state/position-state checkpoint root can diverge independently of the write-set hash used in the comparison — this is precisely why the TODO exists. The bug is not theoretical; it is an explicit, currently-shipped gap gating a future feature flag, meaning any code path that produces a divergent checkpoint hash without changing the raw write-set/event hashes will go undetected today.

## Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` when locally re-computable, comparing them against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` whenever the transaction is a checkpoint boundary, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` as the comment recommends, and audit `replay_on_archive` / `db-tool` callers to ensure the additional checks are wired through with the locally computed checkpoint roots.

## Proof of Concept
Not directly exploitable as a standalone PoC without triggering the yet-to-be-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state-divergent code path; the finding is a structural verification gap demonstrated by code inspection:
1. `ensure_match_transaction_info` (lines 2139-2204) only checks `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`.
2. `replay_on_archive`'s `execute_and_verify` (lines 392-405) relies solely on this function to accept/reject a replayed transaction.
3. Any divergence confined to `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` (which are independent fields of `TransactionInfo`, not derived from the compared write-set/event hashes) is provably never checked, so `replay_on_archive` would report success (`Ok(None)`) despite the mismatch.

**Note:** I was not able to fully trace how `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are populated on the execution side (`do_state_checkpoint.rs`) versus what `TransactionOutput` exposes locally, since `TransactionOutput` itself doesn't expose those roots — confirming these are structurally impossible to check from within `ensure_match_transaction_info` today, which reinforces that this is a genuine, currently-unaddressed gap rather than an oversight caught elsewhere in the call chain. Full confirmation of exploitability under the trading-native/hot-state feature would require running/building the code, which is out of scope for this read-only analysis.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
