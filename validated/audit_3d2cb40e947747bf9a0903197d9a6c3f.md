Based on the code's own admission (a TODO comment marking a known integrity gap), I found a valid analog to the `RewardHandler` bug class: a conditional/incomplete validation that lets committed data pass a verification check that should catch corruption.

### Title
`ensure_match_transaction_info` skips validating state/hot-state/position checkpoint hashes, letting replay-verify and restore-time execution verification silently accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used to confirm that a locally re-executed transaction matches an already-committed, accumulator-proof-authenticated `TransactionInfo`. It checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that represent the Sparse-Merkle/JMT state root and native-position state root committed to the ledger accumulator. [1](#0-0) 

### Finding Description
`TransactionInfo` (both `V0` and `V1`) carries `state_checkpoint_hash` and (for `V1`) `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, all of which are part of the value hashed into the transaction accumulator leaf and thus part of the authenticated ledger commitment. [2](#0-1) 

`ensure_match_transaction_info` validates `status`, `gas_used`, `write_set` (via `state_change_hash`), and `event_root_hash`, but the code contains an explicit TODO acknowledging it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [3](#0-2) 

This function is the sole integrity gate in the following consumers, all of which re-execute transactions locally and compare against the already-committed/authenticated `TransactionInfo`:
- `ChunkExecutor::verify_execution`, used during chunk-executor-based state-sync/backup verification, which loops over freshly executed outputs and calls `txn_out.ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))`. [4](#0-3) 

- `storage/db-tool/src/replay_on_archive.rs` and `storage/db-tool/src/replay_verify.rs`, the operator-facing tools whose entire purpose is to detect execution/state divergence against an archived, trusted ledger before it becomes consensus-breaking. [5](#0-4) 

Because the state root fields are skipped, if local re-execution (during restore, chunk-executor verify-execution, or the `replay-verify`/`replay-on-archive` db-tools) produces a **different** state root — whether from a state-commit bug, a corrupted JellyfishMerkleTree/hot-state root computation, or a divergent native-position root under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` — the comparator still returns `Ok(())`. The write-set hash and event hash matching does not imply the state root matches, since the state root is derived from the full JMT/position-tree update, not solely from the transaction's own write set (it also depends on prior tree state, which is exactly the class of bug this check exists to catch).

### Impact Explanation
This breaks the "proof and storage pivot" requirement that "accumulators, Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding," and directly matches the gate's "hard-fork-only divergence during commit, replay, restore, or proof verification" impact category. A state-root-divergence bug elsewhere in the codebase (e.g., in hot-state or native-position root computation) would be silently missed by the very tooling (`replay-verify`, `replay-on-archive`, chunk-executor verify-execution) designed to catch it before it causes a chain split. Operators and auditors relying on a "successful replay" signal would have false confidence that local execution reproduces the authenticated ledger state, when in fact the state root has diverged.

### Likelihood Explanation
The gap is real and unconditional in current code — it always occurs regardless of which features are enabled, since the check for these three hash fields is entirely absent (not merely feature-gated). The comment states the intent to fix this "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying the authors are aware this is an active hole in the verification path, but the checks are still missing for the already-shipped `state_checkpoint_hash` field applicable to every checkpoint transaction on mainnet (not only the trading-native path), since `TransactionInfoV0`/`V1` state_checkpoint_hash matching is also skipped.

### Recommendation
In `ensure_match_transaction_info`, compute the locally derived state checkpoint hash (and, when applicable, hot-state and position-state checkpoint hashes) for checkpoint transactions and assert equality against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, mirroring the existing pattern used for `write_set_hash` and `event_root_hash`, before any code path (chunk-executor verify-execution, replay-verify, replay-on-archive) reports a transaction as "matched."

### Proof of Concept
1. Introduce (or trigger via an existing latent bug in) state root computation a divergence between the actual state committed on-chain (or in the backup being replayed) and what a node computes locally — e.g., a bug in hot-state root or native-position root aggregation causes a different `state_checkpoint_hash` for a given block-epilogue transaction, while the write set and events are identical.
2. Run `db-tool replay-verify` (or trigger `ChunkExecutor::verify_execution` via state sync backup verify mode) over the affected version range.
3. `ensure_match_transaction_info` is called with the locally computed `TransactionOutput` and the archived/committed `TransactionInfo`; since it never compares `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, the call returns `Ok(())` and the tool reports success.
4. The state root divergence goes undetected, even though `TransactionAccumulatorSummary::verify_consistency` (which does check the accumulator/ledger-info root) would have caught it downstream only if the mismatch alters the final accumulator root — but for purely local diagnostic/backup verification purposes, the check that is supposed to flag the exact corrupted field never fires. [6](#0-5)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
