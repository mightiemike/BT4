## Analog Found

### Title
Unauthorized UEA auto-deployment and gas-fee drain triggered by attacker-manipulable balance in `MsgExecutePayload` - (File: `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
The external report describes `GenesisGroup` gating a privileged state transition (`launch`) on `address(this).balance`, a value any unprivileged actor can force via `selfdestruct`, bypassing the intended `purchase()` authorization path. The Push Chain analog is `Keeper.ExecutePayload`, which gates the privileged auto-deployment of a victim's Universal Executor Account (UEA) purely on the raw native-token balance of the CREATE2-precomputed UEA address — a value any unprivileged user can set via an ordinary bank transfer, with no relation to actual authorization from the account owner.

### Finding Description
`ExecutePayload` computes the deterministic UEA address for a caller-supplied `universalAccountId` and, if not yet deployed, checks only: [1](#0-0) 
If the balance is non-zero, it auto-deploys the UEA on behalf of an arbitrary `universalAccountId` owner: [2](#0-1) 

The gating value (`k.bankKeeper.GetBalance(ueaAccAddr, BaseDenom)`) is exactly analogous to `address(this).balance` in `GenesisGroup`: it is externally observable, deterministically precomputable off-chain (the UEA address is CREATE2-derived), and can be set by *any* unprivileged actor sending ordinary tokens to that address — with zero relationship to the actual account owner's consent. The integration test suite explicitly acknowledges this is attacker-reachable: it labels pre-funding the precomputed address as "the attacker-grief setup" and confirms the auto-deploy path fires purely off balance: [3](#0-2) 

`MsgExecutePayload` is registered as a **gasless** message type, meaning the ante handler does not charge the caller (`evmFrom`/tx signer) transaction fees at all: [4](#0-3) 

Instead, gas cost for the payload execution attempt is deducted from the **UEA's own balance**, and per the code's own comment this happens "regardless of success/failure" of the underlying signature-authenticated call: [5](#0-4) 
The sibling `ExecutePayloadV2` path confirms the same semantics: fee deduction runs against `ueaAddr` even when `CallUEAExecutePayload` (the verification-data-gated call) fails: [6](#0-5) 

### Impact Explanation
An unprivileged attacker can:
1. Compute any victim's not-yet-deployed UEA address off-chain (deterministic CREATE2 pre-image, obtainable via the same view call `CallFactoryToGetUEAAddressForOrigin`).
2. Send a trivial amount of native token directly to that address via a normal bank transfer — no protocol permission required.
3. Submit a **gasless** `MsgExecutePayload` naming the victim's `universalAccountId` with forged/garbage `verificationData` — the attacker pays no ante-level transaction fee.
4. This forces `DeployUEAV2` to deploy the victim's UEA without their consent, and drives an authenticated-execution attempt whose gas cost is billed to the victim's UEA balance even though the signature check inside `CallUEAExecutePayload` should fail.

This is an unauthorized state transition (forced deployment) and a fund-drain vector (repeated fee deduction from a party who never signed or authorized the interaction), reachable purely through ordinary token transfers and a gasless message — falling under "unauthorized burn ... of user or protocol-controlled funds" and "unauthorized UEA ... execution" in the allowed impact scope.

### Likelihood Explanation
Moderate-to-high: no privileged role, validator collusion, or key compromise is needed. The only precondition is that the target UEA is not yet deployed (a common state for any account that hasn't yet transacted), and the attacker needs only enough native token to trigger a nonzero-balance check plus whatever gas the reverted verification path consumes. The economics of the attack (attacker pays zero ante fee due to the gasless allowlist, while the victim pays gas for an unauthorized attempt) make it repeatable and cheap.

### Recommendation
Do not use raw account balance as an authorization/trigger signal for auto-deployment. Require an explicit, authenticated event (e.g., a verified inbound deposit ballot, or a valid `verificationData` check performed *before* any deployment or fee deduction against the victim's balance) to gate `DeployUEAV2`. Additionally, ensure gas-fee deduction for a failed/forged `verificationData` attempt is not charged against the target UEA at all — instead reject the message pre-deployment, or charge only the (currently fee-exempt) message submitter.

### Proof of Concept
1. Off-chain: call the view-equivalent of `CallFactoryToGetUEAAddressForOrigin` for a target `universalAccountId` to obtain the not-yet-deployed UEA address (mirrors `test/integration/uexecutor/execute_payload_test.go` lines 246–260).
2. Send a minimal native-token transfer to that address via a standard bank `MsgSend`.
3. Submit `MsgExecutePayload` with `evmFrom` = attacker address, `universalAccountId` = victim's, and an invalid/garbage `verificationData`.
4. Observe `ExecutePayload` (msg_execute_payload.go:57-78) auto-deploys the victim's UEA, then `DeductGasFeesFromReceipt` charges gas against the victim's UEA balance despite the attacker's forged verification data, while the attacker's own `MsgExecutePayload` submission incurred no ante-level fee (per `app/txpolicy/gasless.go`).

*Note: exact deduction amounts depend on `DeductGasFeesFromReceipt`'s handling of a nil/zero-`GasUsed` receipt on signature-verification failure inside `CallUEAExecutePayload` (`x/uexecutor/keeper/evm.go` / `x/uexecutor/keeper/fees.go`), which could not be fully inspected within the available tool budget — this should be verified directly in those files to confirm the precise drained amount per attempt.*
