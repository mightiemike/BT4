### Title
`citrea_network_to_chain_id` maps `Network::Nightly` and `Network::TestNetworkWithForks` to the identical chain id (5665), defeating cross-network replay protection for `BatchProofMethodId` upgrades - (File: crates/light-client-prover/src/circuit/mod.rs)

### Summary
`citrea_network_to_chain_id` is documented as existing specifically "to prevent cross network replay attacks" for method-id upgrade transactions, but it returns `5665` for both `Network::Nightly` and `Network::TestNetworkWithForks`. Combined with the fact that the default `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` and `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` fall back to the exact same hardcoded public keys/env-vars when unset, a validly-signed `BatchProofMethodId` body produced for one network is silently accepted by the other network's light client prover.

### Finding Description
The intended binding is `citrea_network_to_chain_id(network_A) == citrea_network_to_chain_id(network_B) ⇒ network_A == network_B`. This is violated explicitly in code: [1](#0-0) 
both `Network::Nightly` and `Network::TestNetworkWithForks` map to `5665`.

In `run_l1_block`'s `DataOnDa::BatchProofMethodId` arm, the only network-binding checks are: activation height monotonicity, `circuit_chain_id == body.chain_id`, and `verify_method_id_security_council` (pure signature verification against `method_id_upgrade_authority_da_public_keys`, with no network-specific salt in the signed message beyond `chain_id`): [2](#0-1) 

`verify_method_id_security_council` itself only checks signature validity/index ordering against whatever `initial_da_pubkeys` array is passed in - it has no notion of which network it is being called for: [3](#0-2) 

The default authority key sets for Nightly and TestNetworkWithForks are literally the same constants/env-var fallbacks: [4](#0-3) [5](#0-4) 

Given these two facts together, a `BatchProofMethodId` body/signature set produced and inscribed for `Network::TestNetworkWithForks` (chain_id 5665, same council keys) is byte-for-byte a valid `BatchProofMethodId` for `Network::Nightly` as well. An attacker who observes such an inscription on one network's DA (this is public data on Bitcoin) can simply re-inscribe the identical bytes on the other network's DA - a pure "pay Bitcoin fees to inscribe a transaction" action, no privileged key needed. `run_l1_block` for the Nightly prover will pass the chain-id check (5665==5665) and the signature check (keys match), and call `BatchProofMethodIdAccessor::insert`, adopting a method-id upgrade that the council never separately authorized for Nightly.

The existing "wrong network" test only exercises `Network::Mainnet` vs `Network::Nightly` (chain ids 4114 vs 5665, correctly rejected): [6](#0-5) 
It does not cover the Nightly/TestNetworkWithForks collision, so this specific gap is untested and unguarded.

### Impact Explanation
This allows a method-id upgrade accepted on the wrong network without a matching, network-specific council authorization - the exact "method-id upgrade accepted that was never authorised" scenario. Once accepted, `BatchProofMethodIdAccessor` on the victim network is updated with a method-id/activation-height pair chosen by whichever council quorum signed for the other network, changing which `BatchProofCircuitOutput` proofs the light client circuit will subsequently accept as valid for that network. This is repeatable for every future method-id upgrade transaction as long as both networks retain the shared chain-id/key configuration, and it affects every light client prover following that network's rules identically (so it does not, by itself, cause honest-node divergence within one network - all Nightly provers would accept the replayed upgrade the same way).

### Likelihood Explanation
The bug is unconditionally present in `citrea_network_to_chain_id` regardless of configuration. However, real-world exploitability additionally depends on operational facts I could not fully verify from the repo alone: whether any live/value-bearing deployment actually runs `Network::Nightly` and `Network::TestNetworkWithForks` concurrently with non-overridden (identical) `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_*` env vars, and whether `TestNetworkWithForks` (documented in `crates/sovereign-sdk/rollup-interface/src/network.rs` as "used for testing purposes only", activated via the internal `--dev-all-forks` CLI flag in `bin/citrea/src/main.rs`) is deployed as a distinct standalone network holding bridged value versus being an ephemeral local/CI-only harness with no real BTC bridged. If both are only used in local/CI test harnesses with no real bridge deposits, the "cBTC moved" severity bar is not met even though the chain-id collision is a genuine code defect. I could not confirm from the indexed code whether any production/staging deployment runs both networks side-by-side with shared keys; the wiki/deployment configuration for actual network rollout is outside what's indexed here.

### Recommendation
Assign distinct, non-overlapping chain ids in `citrea_network_to_chain_id` for every `Network` variant, including `TestNetworkWithForks` (e.g. `5666` or any value distinct from Nightly's `5665`), so that the equality binding `citrea_network_to_chain_id(A) == citrea_network_to_chain_id(B) ⇒ A == B` holds for all variants.

```rust
use sov_rollup_interface::Network;
use citrea_light_client_prover::circuit::citrea_network_to_chain_id;

#[test]
fn test_network_chain_id_uniqueness() {
    // Binding under test: distinct networks must map to distinct chain ids
    assert_ne!(
        citrea_network_to_chain_id(Network::Nightly),
        citrea_network_to_chain_id(Network::TestNetworkWithForks),
        "Nightly and TestNetworkWithForks must not share a chain id"
    );
}
```
This assertion currently fails (`5665 == 5665`), demonstrating the broken binding. A full end-to-end PoC would extend `test_wrong_network_method_id_update_should_fail` in `crates/light-client-prover/src/tests/mod.rs` to build a `BatchProofMethodId` body with `chain_id: citrea_network_to_chain_id(Network::TestNetworkWithForks)`, sign it with `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS`, then run the circuit with `network = Network::Nightly` and the shared default key set, asserting (unlike the Mainnet-vs-Nightly case) that the upgrade is accepted (`batch_proof_method_ids.len()` increases) despite never being authorized specifically for `Nightly`.

```rust
#[test]
fn test_wrong_network_method_id_update_should_fail() {
    let db_dir = tempdir().unwrap();
    let native_circuit_runner = NativeCircuitRunner::new(db_dir.path().to_path_buf());
    let zk_circuit_runner = LightClientProofCircuit::<ZkStorage, MockDaSpec, MockZkGuest>::new();

    let light_client_proof_method_id = [1u32; 8];
    let da_verifier = MockDaVerifier {};

    let l2_genesis_state_root = [1u8; 32];
    let batch_prover_da_pub_key = [9; 32];
    let sequencer_da_pub_key = [45; 32];
    let method_id_sender = [11u8; 32];

    let block_header_1 = MockBlockHeader::from_height(1);

    // Create method id update for a different network
    let blob = create_new_method_id_tx(10, [2u32; 8], method_id_sender, Network::Mainnet);

    let input = native_circuit_runner.run(
        LightClientCircuitInput {
            previous_light_client_proof: None,
            light_client_proof_method_id,
            da_block_header: block_header_1,
            inclusion_proof: [1u8; 32],
            completeness_proof: vec![blob],
            witness: Default::default(),
        },
        l2_genesis_state_root,
        INITIAL_BATCH_PROOF_METHOD_IDS.to_vec(),
        &batch_prover_da_pub_key,
        &sequencer_da_pub_key,
        &METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS,
        Network::Nightly,
    );

    let _ = zk_circuit_runner
        .run_circuit(
            da_verifier.clone(),
            input,
            ZkStorage::new(),
            Network::Nightly,
            l2_genesis_state_root,
            INITIAL_BATCH_PROOF_METHOD_IDS.to_vec(),
            &batch_prover_da_pub_key,
            &sequencer_da_pub_key,
            &METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS,
        )
        .unwrap();
    let mut working_set = WorkingSet::new(
        native_circuit_runner
            .prover_storage_manager
            .create_final_view_storage(),
    );

    let batch_proof_method_ids =
        BatchProofMethodIdAccessor::<ProverStorage>::get(&mut working_set).unwrap();

    // didn't change
    assert_eq!(batch_proof_method_ids.len(), 1);
}
```
