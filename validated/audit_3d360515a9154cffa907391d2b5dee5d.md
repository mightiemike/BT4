## Analog Found

### Title
Deterministic chain-halting panic in `receipt_filter_fn` when a `GlobalContractDistribution` receipt's `target_shard` cannot be resolved across shard-layout resharding transitions - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
CVE-2017-9216 is a NULL-pointer dereference in `jbig2dec`'s Huffman decoder caused by insufficient validation of parser state on unusual/malformed input, crashing the process. The structurally analogous bug class in nearcore is an `unwrap()`-driven panic reached from ordinary, protocol-legal receipt processing when a helper function's `Option`/`Result` return isn't handled defensively for an edge case in the input's shape — here, a receipt whose `target_shard` predates more shard-layout history than the resolution logic can walk.

### Finding Description
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally unwraps the result of `receiver_shard_id()`: [1](#0-0) 

`Receipt::receiver_shard_id` can return `Err(EpochError::ShardingError(..))` for a `GlobalContractDistribution` receipt when its `target_shard` is not in the current shard layout and cannot be resolved to a current descendant: [2](#0-1) 

`ShardLayout::resolve_to_current_shard` explicitly documents that for `V0`/`V1`/`V2` layouts it only handles a **single generation** of resharding (falls back to `get_children_shards_ids`), unlike `V3`, which walks a cumulative split-history map: [3](#0-2) 

If a `GlobalContractDistribution` receipt (created whenever any account deploys a global contract, an action reachable by any unprivileged transaction signer) becomes stuck in the delayed receipt queue under sustained congestion and the shard layout changes across **two or more** resharding generations while it waits, `receiver_shard_id` returns `Err`, and the `.unwrap()` in `receipt_filter_fn` panics — crashing every honest node that reaches this code path in `pop()`/`peek_iter()`: [4](#0-3) 

The nearcore team is aware of this exact class of bug for the new dynamic-resharding (V3) shard layout and added a cumulative split map plus a dedicated regression test, whose comment explicitly states the mitigation is V3-only: [5](#0-4) [6](#0-5) 

Legacy `V0`/`V1`/`V2` shard layouts (used for static, protocol-version-triggered resharding) retain the single-generation limitation, so `receiver_shard_id`/`receipt_filter_fn` can still panic if a receipt sent before a static resharding is delayed long enough to span a second static resharding.

### Impact Explanation
A panic inside `DelayedReceiptQueueWrapper::pop`/`peek_iter` occurs deterministically on every validator/node applying the chunk that processes the stale receipt, since receipt processing order and content are consensus-critical and identical across honest nodes. This matches the accepted "transaction-triggered halt" impact class: the chain would stop producing blocks until the code is patched or the state is manually repaired, a availability-breaking, chain-wide failure triggered purely by ordinary transaction activity (global contract deployment plus congestion) with no attacker privilege required beyond submitting normal transactions.

### Likelihood Explanation
Reaching this requires (a) a `GlobalContractDistribution` receipt to remain in the delayed queue across two shard-layout transitions on a legacy (non-V3) layout, which requires either sustained heavy congestion on the target shard or naturally spaced static-resharding protocol upgrades combined with an unlucky in-flight receipt. This is a legacy-path/lower-probability trigger compared to the (now-mitigated) V3 dynamic-resharding case, but the code path and the unguarded `unwrap()` remain live in production for any network state still using V0/V1/V2 shard layouts, or during any future rollback/mixed-version window.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` (and any other direct callers of `receiver_shard_id` on delayed/incoming receipts) with graceful error handling — e.g., propagate the error via `Result` and treat unresolvable ancient `target_shard` receipts explicitly (log + drop or route to a fallback shard) instead of panicking, mirroring the `Err` handling already used elsewhere in the congestion-control module (e.g., `IntegerOverflowError` propagation). Extend `ShardLayoutV3`-style cumulative ancestor-tracking (or an equivalent full-history walk) to the legacy `V0`/`V1`/`V2` `resolve_to_current_shard` path so multi-generation resolution never fails.

### Proof of Concept
1. Deploy a chain using legacy (`V0`/`V1`/`V2`) static shard layouts.
2. As any account, submit a `DeployGlobalContract` action; this creates a `GlobalContractDistribution` receipt targeting the deploying account's current shard.
3. Saturate the target shard's compute budget every block (e.g., repeated `FunctionCall` burning gas) so the receipt is pushed into, and stays in, the delayed receipt queue (see `process_incoming_receipts` push-to-delayed logic referenced in `protocol-model/spec/cross-shard-congestion.md:111-121`).
4. Trigger two successive static shard-layout changes (protocol version upgrades that alter `EpochConfig::static_shard_layout`) while the receipt remains delayed.
5. Once congestion clears and the runtime pops the stale receipt via `DelayedReceiptQueueWrapper::pop`, `receiver_shard_id` returns `Err` because `resolve_to_current_shard` on the legacy layout can only resolve one generation back; `receipt_filter_fn`'s `.unwrap()` panics, crashing chunk application on every node — reproducing the exact scenario the `test_stale_global_contract_distribution_after_double_resharding` test was written to guard against, but for the legacy (non-V3) shard-layout code path that the fix does not cover.

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }

    /// Resolve any historical shard ID to a current descendant shard ID.
    /// For V3 layouts this uses the complete `shards_split_map`.
    /// For older layouts it falls back to `get_children_shards_ids` (single generation only).
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        match self {
            Self::V0(_) | Self::V1(_) | Self::V2(_) => {
                self.get_children_shards_ids(shard_id).map(|c| c[0])
            }
            Self::V3(v3) => v3.resolve_to_current_shard(shard_id),
        }
    }
