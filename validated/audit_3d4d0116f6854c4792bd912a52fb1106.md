### Title
Unauthenticated `batchProver_setCommitments` allows arbitrary overwrite of sequencer-commitment state without DA verification - (File: crates/batch-prover/src/rpc.rs)

### Summary
`BatchProverRpcServerImpl::set_commitments` writes attacker-supplied `SequencerCommitment` data directly into `ledger_db` via `put_commitment_by_index`, `put_commitment_index_by_l1`, and `put_prover_pending_commitment`, with no signature or DA-inclusion check anywhere in the call path. The shared `Auth` RPC middleware that wraps every JSON-RPC call only gates three unrelated methods, so this state-mutating call is reachable by anyone who can hit the batch-prover RPC port.

### Finding Description
The binding that should hold is: `ledger_db` sequencer-commitment entries (indexed by `commitment.index`) == commitments extracted from `DataOnDa::SequencerCommitment` blobs whose `blob.sender()` equals the configured `sequencer_da_pub_key`, as enforced in the normal ingestion path (`crates/common/src/da.rs::extract_sequencer_commitments`, and analogously `DataOnDa::SequencerCommitment` handling in `crates/light-client-prover/src/circuit/mod.rs:567-575` which explicitly checks `blob.sender().as_ref() != sequencer_da_public_key`).

`set_commitments` (`crates/batch-prover/src/rpc.rs:345-381`) bypasses this entirely: it builds a `SequencerCommitment` directly from caller-supplied `merkle_root`, `index`, `l2_end_block_number` fields and calls
```
self.context.ledger_db.put_commitment_by_index(&commitment)
self.context.ledger_db.put_commitment_index_by_l1(...)
self.context.ledger_db.put_prover_pending_commitment(commitment.index)
```
with no signature check, no DA lookup, and the docstring itself states "It overrides the commitment already if exists, so use with caution" (`crates/batch-prover/src/rpc.rs:172`).

The only cross-cutting protection is the `Auth` RPC middleware installed in `start_rpc_server` (`crates/common/src/rpc/server.rs:42-43`), implemented in `crates/common/src/rpc/auth.rs`. That middleware's `PROTECTED_METHODS` constant is `["backup_create", "backup_validate", "backup_info"]` (`crates/common/src/rpc/auth.rs:11`) — `batchProver_setCommitments` is not in this list, so `Auth::call` short-circuits to `return Box::pin(service.call(req))` (`crates/common/src/rpc/auth.rs:36-38`) with no API-key check at all, regardless of whether `RPC_API_KEY`/`rpc_config.api_key` is configured.

### Impact Explanation
An attacker reaching the batch-prover's RPC port can inject or overwrite a "pending commitment" entry with an arbitrary `merkle_root`/`l2_end_block_number` for any `index`, including indices colliding with or preceding real pending commitments. Because `put_prover_pending_commitment` marks it for proving, subsequent `prove`/`createCircuitInput` calls (or the automatic prover loop) will attempt to build circuit input for this forged commitment. However, whether this actually results in a **forged proof accepted on-chain** depends on whether `apply_l2_blocks_from_sequencer_commitments` cross-checks the commitment's `merkle_root` against the real, sequencer-signed L2 block header chain before emitting `sequencer_commitment_hashes` into `BatchProofCircuitOutput`. If that in-circuit check exists (verifying L2 headers/signatures independent of the RPC-injected value), a forged `merkle_root` would cause proving to fail rather than produce a false but ZK-valid output — I was not able to fully trace and confirm this check within the available context (`crates/sovereign-sdk/module-system/sov-modules-stf-blueprint/src/lib.rs` merkle-root usage) in the tool budget available. Independent of that, the confirmed, demonstrable impact is: **an unauthenticated JSON-RPC call mutates persistent node state** (`ledger_db` commitment/pending-commitment tables) on the batch prover, matching the High-severity category ("an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`"). This is repeatable per call and per index, and can disrupt/corrupt the prover's local commitment bookkeeping (denial-of-service-adjacent effects on proving progress are out of scope per the rules, but the state mutation itself is in scope).

### Likelihood Explanation
Precondition is simply that the batch-prover's RPC endpoint is network-reachable, which the rules state is assumed reachable ("no separate auth middleware wraps this specific method in the visible code" — confirmed true). No BTC/cBTC cost, no special role, and no prior authentication is required; a single JSON-RPC POST is sufficient. This is trivially repeatable across arbitrary indices and requires no interaction with Bitcoin at all.

### Recommendation
Add `batchProver_setCommitments` (and likely `submitFakeProof`, which is similarly unauthenticated and mutates/generates DA submissions) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`, or otherwise require the same API-key gate applied to backup endpoints. Additionally, consider binding these administrative RPC methods to a separate internal-only listener not exposed on the public RPC port, and/or validate that any manually-set commitment cannot silently propagate into a proof without being reconciled against sequencer-signed L2 blocks/DA-observed commitments.

### Proof of Concept
```rust
// cargo test in crates/batch-prover, using an in-memory/mock ledger_db and DaService
#[tokio::test]
async fn unauthenticated_set_commitments_overwrites_pending_commitment() {
    // Build RpcContext with a mock ledger_db (BatchProverLedgerOps) and mock DaService,
    // as done in existing batch-prover rpc tests.
    let ctx = build_test_rpc_context();
    let server = BatchProverRpcServerImpl::new(ctx);

    // Attacker-controlled forged commitment for an index that does not
    // correspond to anything ever inscribed as DataOnDa::SequencerCommitment
    // signed by sequencer_da_pub_key.
    let forged = SequencerCommitmentRpcParam {
        merkle_root: [0xAA; 32],
        index: U32::from(5u32),
        l2_end_block_number: U64::from(999_999u64),
    };

    // No API key / auth header is passed anywhere - the trait method takes none.
    server.set_commitments(vec![forged.clone()]).await.unwrap();

    // Binding check: ledger_db now contains a commitment at index 5 that was
    // never observed via extract_sequencer_commitments / DataOnDa::SequencerCommitment
    // with a valid sequencer_da_pub_key signer.
    let stored = ctx.ledger_db.get_commitment_by_index(5).unwrap().unwrap();
    assert_eq!(stored.merkle_root, [0xAA; 32]);
    assert_eq!(stored.l2_end_block_number, 999_999);

    // Confirm it was also marked pending for proving, i.e. it will be picked
    // up by create_circuit_input / prove without ever having existed on DA:
    let pending = ctx.ledger_db.get_prover_pending_commitments().unwrap();
    assert!(pending.contains(&5));

    // Cross-check against DA: no SequencerCommitment blob with index=5 signed
    // by sequencer_da_pub_key was ever sent via da_service.send_transaction,
    // proving the ledger_db state diverges from the DA-verified set.
}
```
This demonstrates the state-mutation (High-severity: unauthenticated JSON-RPC bypassing `Auth` and mutating node state) unambiguously. Whether it escalates to a fully-accepted forged batch proof (Critical) additionally requires tracing the merkle-root/header verification inside `apply_l2_blocks_from_sequencer_commitments`, which I could not fully confirm within the available tool budget — this should be independently verified before scoping severity beyond High.
