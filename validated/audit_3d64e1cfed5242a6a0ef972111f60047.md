## Analysis

java-tron's built-in AMM-style Exchange module implements the exact slippage mitigation the report recommends (a minimum-expected-output parameter), but only for swaps — not for liquidity provisioning or withdrawal, leaving those two operations exposed to the same "rate changes while tx is pending" risk described in the ERC4626 report.

### Title
Missing slippage/minimum-output protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` allows unfavorable execution due to pool-ratio changes between broadcast and inclusion - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeTransactionContract` (a swap against the built-in bancor-style Exchange) includes an `expected` field that is validated against the computed output before execution, protecting the trader from unfavorable price movement between signing and inclusion. `ExchangeInjectContract` (add liquidity) and `ExchangeWithdrawContract` (remove liquidity) have no equivalent field: the paired token amount is derived purely from the exchange's current on-chain balances at execution time, with no user-specified bound.

### Finding Description
`ExchangeTransactionActuator.doValidate()` explicitly checks the computed output against a user-supplied `expected` value and reverts if it is not met: [1](#0-0) 

In contrast, `ExchangeInjectActuator` computes the paired token amount (`anotherTokenQuant`) purely from the exchange's live balances at validation/execution time and has no user-provided bound to enforce a maximum contribution or minimum received ratio: [2](#0-1) 

The `ExchangeInjectContract` protobuf message itself only carries `exchange_id`, `token_id`, and `quant` — no expected/min/max field exists to be validated in the first place.

Similarly, `ExchangeWithdrawActuator` computes `anotherTokenQuant` from the live pool ratio with only a "not precise enough" rounding-drift check, not a user-declared minimum acceptable amount: [3](#0-2) [4](#0-3) 

Because Exchange pool balances can be shifted by any other account's `ExchangeTransactionContract` swap executed earlier in the same block or an intervening block (this is normal, unprivileged usage of the public Exchange), the actual paired-token amount injected or received on withdraw can differ materially from what the sender expected when constructing/broadcasting the transaction — exactly the "exchange rate change while transaction is pending" scenario the external report describes for ERC4626, but here applied to java-tron's native on-chain relay/exchange rather than an off-chain smart contract wrapper.

### Impact Explanation
An exchange creator submitting `ExchangeInjectContract` or `ExchangeWithdrawContract` can have their liquidity contribution or withdrawal executed at a materially different ratio than intended if the pool balance shifts (via ordinary swap transactions) between broadcast and block inclusion. On inject, this can force a contribution at an unfavorable ratio (effectively donating value to the pool relative to the depositor's intent); on withdraw, it can return fewer of the "another token" than the withdrawer expected. This is a fund-loss risk analogous to, but scoped to, the account performing the action — there is no cross-account fund theft, matching the Medium-severity characterization in the original report.

### Likelihood Explanation
Exploitability requires the pool ratio to move between transaction creation and inclusion — achievable by any third party issuing ordinary `ExchangeTransactionContract` swaps against the same exchange pair, which is a normal, unprivileged, permissionless action. No special access is needed to shift the ratio, only broadcasting a normal transaction, making this readily reachable in practice, though the actual loss magnitude depends on pool liquidity depth and how much the ratio is moved.

### Recommendation
Add an optional minimum/maximum bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring the `expected` field already present on `ExchangeTransactionContract`), and validate the computed `anotherTokenQuant` against it in `ExchangeInjectActuator.doValidate()` and `ExchangeWithdrawActuator.doValidate()` before allowing execution.

### Proof of Concept
1. Account A creates an exchange pair for tokens X/Y via `ExchangeCreateContract` and becomes its creator.
2. Account A signs and broadcasts `ExchangeInjectContract` intending to inject `tokenQuant` of X, expecting to also contribute roughly `anotherTokenQuant` of Y based on the pool ratio observed when the transaction was built.
3. Before A's transaction is included, any other account (unprivileged) broadcasts an `ExchangeTransactionContract` swap that shifts the X/Y balance ratio in the pool.
4. When A's `ExchangeInjectContract` executes, `ExchangeInjectActuator.execute()` recomputes `anotherTokenQuant` from the now-shifted `firstTokenBalance`/`secondTokenBalance` [5](#0-4) , forcing A to contribute a different (potentially much larger) amount of Y than intended, with no on-chain mechanism to bound or reject this deviation.
5. The same scenario applies to `ExchangeWithdrawContract`: the creator can receive less of the paired token than expected if the ratio shifts before inclusion, since only a fixed rounding-precision check exists, not a user-declared minimum output.
