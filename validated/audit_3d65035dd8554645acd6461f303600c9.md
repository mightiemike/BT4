## Analysis Result

### Title
Missing slippage protection in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` liquidity operations — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
TRON's built-in Bancor-style exchange (TRC10 AMM pools) supports liquidity add/remove via `ExchangeInjectContract` and `ExchangeWithdrawContract`. Unlike `ExchangeTransactionContract`, which includes an `expected` field enforced during validation as a minimum-output/slippage guard, neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` carries any user-supplied bound on the paired-token amount. The counter-token quantity (`anotherTokenQuant`) is computed purely from the pool's live `firstTokenBalance`/`secondTokenBalance` at execution time, exactly mirroring the `spot_lp` root cause in the external report where required tokens are derived from the current, mutable pool state with no min/max check.

### Finding Description
`ExchangeTransactionContract` explicitly protects traders via the `expected` field, validated at [1](#0-0)  which rejects the trade if the computed output is below the caller-supplied minimum.

In contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` have no equivalent field: [2](#0-1) . The actuators compute the paired token amount directly from the pool's current balances with no ceiling/floor supplied by the caller:
- Inject: [3](#0-2) 
- Withdraw: [4](#0-3) 

The underlying pool balances (`firstTokenBalance`/`secondTokenBalance`) are mutated by ordinary `ExchangeTransactionContract` trades between when a liquidity transaction is broadcast and when it is packed into a block, via `ExchangeCapsule.transaction()`: [5](#0-4) . This is the direct java-tron analog of the `spot_lp` bug class: the required counter-token amount for a liquidity operation is calculated against a pool ratio that can shift arbitrarily before execution, and the caller has no mechanism to bound the resulting exposure.

Note: only the exchange's `creatorAddress` may call inject/withdraw (enforced at [6](#0-5)  and the analogous check in `ExchangeWithdrawActuator`), but any unprivileged account can become a pool's creator by issuing `ExchangeCreateContract`, so this is not a protocol-trusted role (not SR/witness/multisig) — it is ordinary user-owned pool state, consistent with the "market/exchange" scope allowed by the rules.

### Impact Explanation
An exchange creator submitting an `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction can have the pool ratio shifted (intentionally, via front-running trades from any other unprivileged account submitting `ExchangeTransactionContract`, or unintentionally, via normal trading activity/network delay) between broadcast and execution. Because there is no minimum/maximum bound field, the creator's liquidity operation executes at whatever ratio exists at inclusion time, causing them to inject or withdraw a materially different (less favorable) counter-token amount than intended — direct accounting/value loss, matching the "underpriced-public-work"/settlement-divergence impact class.

### Likelihood Explanation
Any account can call `ExchangeTransactionContract` against the same exchange pool to move the ratio before a queued inject/withdraw transaction lands, since TRON transactions are visible pre-confirmation and exchange pool state changes are always public. This makes exploitation straightforward for an adversary monitoring the mempool/relayed transactions, requiring only ordinary user-level trade transactions — no privileged access needed.

### Recommendation
Add slippage-bound fields (e.g., `expected_another_token_min`/`expected_another_token_max` or similar) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate the calculated `anotherTokenQuant` against these bounds in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()`, mirroring the existing `expected` check already present in `ExchangeTransactionActuator` at [1](#0-0) .

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction from a pool creator in the transaction pool.
2. Attacker submits an `ExchangeTransactionContract` against the same `exchange_id` with a large `quant`, shifting `firstTokenBalance`/`secondTokenBalance` before the creator's transaction is packed, via the trade path in [5](#0-4) .
3. When the creator's inject/withdraw transaction executes, `anotherTokenQuant` is computed against the now-skewed ratio in [3](#0-2) , forcing the creator to inject/withdraw at an unfavorable, unbounded rate with no on-chain check to reject the transaction.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
