### Title
Malformed `host` query parameter causes an uncaught exception that crashes the Express process in `sanitizeHost`/`decodeHost` (`atob`) - (File: `packages/apps/shopify-api/lib/utils/shop-validator.ts`)

### Summary
`shopify-app-express`'s unauthenticated-request handling path (`ensureInstalledOnShop` → `redirectToAuth` → `clientSideRedirect`) calls `api.utils.sanitizeHost()` on the attacker-controlled `host` query parameter without any `try/catch`. `sanitizeHost` unconditionally calls `decodeHost()` (a thin wrapper around `atob`) on any string that merely matches the base64 *character-set* regex, without validating that the string has a length that is actually decodable. A one-character (or otherwise malformed-length) `host` value passes the regex but makes `atob` throw a `DOMException`. Because this throw happens synchronously inside an `async` Express middleware chain that Express never awaits/catches, it becomes an **unhandled promise rejection**, which by default terminates the Node.js process — a full application crash triggerable by a single, unauthenticated HTTP request.

### Finding Description
`sanitizeHost` in [1](#0-0)  validates `host` only against `/^[0-9a-zA-Z+/]+={0,2}$/`, a regex that matches base64 *alphabet* but does not enforce a decodable length (multiple of 4, or length%4 != 1). If the regex passes, the code immediately calls `decodeHost(sanitizedHost)`: [2](#0-1) 

`atob()` implements the WHATWG forgiving-base64 algorithm, which throws a `DOMException` when the input length modulo 4 equals 1 (e.g. a single character such as `"A"`). This throw occurs **before** the `throwOnInvalid` check further down in `sanitizeHost`, so it happens unconditionally, regardless of how the caller invoked the function.

This function is called, unguarded by any try/catch, from the unauthenticated request path in `shopify-app-express`:

- `ensureInstalledOnShop()` → when no session is found, calls `redirectToAuth({req, res, api, config})`: [3](#0-2) 
- `redirectToAuth` → for embedded requests (`embedded=1`), calls `clientSideRedirect`, which calls `sanitizeHost` directly on `req.query.host`: [4](#0-3) 

`ensureInstalledOnShop` is an `async` middleware function returned as-is to Express: [5](#0-4)  Express 4 (used throughout this codebase's middlewares) does not await or catch rejected promises returned by route/middleware handlers, so a synchronous throw inside this async call chain becomes an unhandled promise rejection at the process level rather than a normal Express error response.

The same unguarded `sanitizeHost` pattern also exists in `redirectToShopifyOrAppRoot` (`packages/apps/shopify-app-express/src/middlewares/redirect-to-shopify-or-app-root.ts:22`) and in the Remix/React Router equivalents, but those run inside framework loaders that have their own error boundaries and are less likely to crash the whole server process.

### Impact Explanation
Any anonymous visitor can trigger this by sending a single unauthenticated GET request to any route protected by `shopify.ensureInstalledOnShop()` — a standard, widely-recommended middleware in Shopify Express app templates — with `?shop=<valid-shop>&embedded=1&host=A` (or any other host value whose length is not decodable, e.g. length%4==1). This throws an uncaught exception which Node.js's default unhandled-rejection behavior turns into a full process crash, taking down the entire app for all merchants until the process is restarted — directly analogous to the reported "join route" DoS pattern (attacker-supplied malformed input reaching an unguarded code path in an authentication-adjacent HTTP handler, crashing the whole service).

### Likelihood Explanation
High. No authentication, valid session, or secret knowledge is required — only a syntactically valid shop domain and a malformed `host` value, both fully attacker-controlled URL query parameters on a route that is explicitly designed to handle pre-authentication/unauthenticated traffic (its entire purpose is to redirect users who are not yet installed/authenticated).

### Recommendation
- In `decodeHost`/`sanitizeHost`, wrap the `atob` call in a `try/catch` and treat decode failures the same as a regex mismatch (return `null` / throw `InvalidHostError` only when `throwOnInvalid` is set), instead of allowing raw `DOMException`s to propagate.
- Additionally, harden the regex to also validate that the base64 length is decodable (`length % 4 !== 1`) before calling `atob`.
- As defense in depth, wrap all Express middleware bodies that can throw synchronously (`ensureInstalledOnShop`, `redirectToAuth`, `redirectToShopifyOrAppRoot`) with `try/catch`, or use `express-async-errors`/an async wrapper so thrown/rejected errors are routed to Express's error-handling middleware instead of becoming unhandled promise rejections.

### Proof of Concept
Against an app using `shopify-app-express` with a route guarded by `shopify.ensureInstalledOnShop()` and no active session for the shop:

```
GET /any-protected-route?shop=example.myshopify.com&embedded=1&host=A HTTP/1.1
Host: your-app-host.example.com
```

`host=A` passes the base64 character-set regex in `sanitizeHost` but has length 1 (mod 4 == 1), causing `atob("A")` to throw a `DOMException` inside the async `clientSideRedirect` → `redirectToAuth` → `ensureInstalledOnShop` call chain. This becomes an unhandled promise rejection and, per Node.js default behavior, crashes the process.
