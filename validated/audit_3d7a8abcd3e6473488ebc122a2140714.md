### Title
`ensure_match_transaction_info` skips `state_checkpoint_hash` verification, letting `replay_on_archive` accept a state root divergence as valid replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness check used by the archival replay-verification tool (`storage/db-tool/src/replay_on_archive.rs`) to confirm that locally re-executed transactions reproduce the historically committed ledger state. The function's own comment admits it "ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution." This is a self-acknowledged proof-integrity gap that is live in the current comparator, not merely hypothetical.

### Finding Description
`ensure_match_transaction_info` checks four fields of the locally computed `TransactionOutput` against the trusted `TransactionInfo` pulled from a backup/archive: status, gas used, write-set hash (`state_change_hash`), and event root hash. [1](#0-0) 

It explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields of `TransactionInfo` that summarize the full Merkle root of the world state (and hot-state/position-state trees) at checkpoint boundaries: [2](#0-1) 

These checkpoint hashes are separate from `state_change_hash` (the write-set hash of the single transaction) — they represent the *cumulative* Sparse Merkle Tree root after applying all state updates up to that point, defined on `TransactionInfoV0`/`TransactionInfoV1`: [3](#0-2) [4](#0-3) 

`storage/db-tool/src/replay_on_archive.rs` uses `ensure_match_transaction_info` as the *only* per-transaction correctness gate when replaying historical transactions read from a backup and comparing them to freshly executed VM outputs: [5](#0-4) 

There is no separate accumulator-root or state-tree-root comparison performed anywhere else in this replay path (`execute_and_verify`/`verify`/`run`) — the tool loads `expected_txn_info`, `expected_event`, `expected_writeset` from backup and never independently recomputes or checks the state checkpoint root against local execution. [6](#0-5) 

Consequently, if VM/state-checkpoint computation diverges from the historically committed result in a way that only manifests in the state root (e.g. a bug in `DoStateCheckpoint`'s hot-state or position-state root computation, or any non-determinism affecting the merged Sparse Merkle Tree but not the per-transaction write set bytes themselves), the write-set hash and event hash can still match while the state checkpoint hash silently diverges. `ensure_match_transaction_info` will return `Ok(())` for such a transaction, and `replay_on_archive` will report the version as successfully verified.

### Impact Explanation
This breaks the core guarantee of replay-verification: that re-executing history from a trusted checkpoint reproduces the exact authenticated ledger state. A state-corrupting bug (or hard-fork-only divergence) confined to checkpoint/state-root computation would pass `replay_on_archive` undetected, giving false confidence that a node's/archive's historical execution is correct when the actual committed Merkle/state root has diverged. This falls squarely under "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "committed state that differs from the correct VM result... accepted as valid" in the state-integrity gate, because the verification tool that exists specifically to catch such divergence has a hole matching exactly this class of error.

### Likelihood Explanation
The gap is unconditional in the current code (not gated behind any flag for the fields it omits) and is on the single verification path used by the operational replay-verify tooling referenced in the codebase's own release/CI processes. Any historical or future bug that affects only the state-checkpoint hash computation (hot-state, position-state, or general SMT hashing) — rather than the individual write-set bytes — will not be caught by this tool. The severity of triggering it depends on a separate root-cause bug existing in checkpoint hash computation, but the detection gap itself is unconditionally present and provably exploitable by any state-root-only divergence.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash` (and, once populated, `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) between the locally computed checkpoint output and the expected `TransactionInfo`, as the existing TODO comment recommends, before any reliance on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-gated features. Ensure `replay_on_archive` and any other callers pass through and check the locally computed checkpoint hash at each checkpoint boundary against the trusted `TransactionInfo`.

### Proof of Concept
1. Introduce (hypothetically, for testing) a divergence solely in checkpoint-hash computation, e.g., a bug in `DoStateCheckpoint`'s hot-state or position-state root aggregation logic in `execution/executor/src/workflow/do_state_checkpoint.rs`, such that the final `state_checkpoint_hash` differs from the one recorded in the historical `TransactionInfo`, while all individual write ops, gas used, status, and events remain identical.
2. Run `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::run` over the affected version range.
3. Observe that `execute_and_verify` calls `ensure_match_transaction_info` [7](#0-6)  which only checks status/gas/write_set_hash/event_root_hash [8](#0-7) , so no error is returned despite the state checkpoint hash mismatch, and the tool reports the range as successfully replayed.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
