### Title
L2 gas price permanently stuck at zero once reached — self-reinforcing floor bypass in EIP-1559-style adjustment - ([File: crates/apollo_consensus_orchestrator/src/fee_market/mod.rs])

### Summary
`calculate_next_base_gas_price` implements the EIP-1559-style per-block gas price adjustment used to derive the next L2 gas price for a Starknet block. When the current price falls below the configured minimum, the function is supposed to gradually raise it back up. However, the "gradual increase" step computes the increase as a *fraction of the current price itself*, so once the price reaches exactly `0`, the increase computed is always `0`, and the price can never recover — it stays pinned at zero forever, regardless of `min_gas_price`. This mirrors the GMX/Sherlock M-20 bug class: once a price-like quantity hits zero, the mechanism that is supposed to correct/liquidate/re-anchor it stops working entirely, because all of its internal math is multiplicatively derived from the (now-zero) value.

### Finding Description
The relevant logic: [1](#0-0) 

```
if price < min_gas_price {
    let max_increase = price.0 / MIN_GAS_PRICE_INCREASE_DENOMINATOR;
    let adjusted = price.0 + max_increase;
    let adjusted_price = adjusted.min(min_gas_price.0);
    ...
    return GasPrice(adjusted_price);
}
```

If `price == GasPrice(0)`, then `max_increase = 0 / MIN_GAS_PRICE_INCREASE_DENOMINATOR = 0`, so `adjusted = 0 + 0 = 0`, and `adjusted_price = 0.min(min_gas_price.0) = 0`. The function returns `GasPrice(0)` again. Every subsequent call with `price = GasPrice(0)` reproduces the same result, so the price is a fixed point at zero — the "gradual approach toward `min_gas_price`" guarantee described in the function's own doc comment never applies once the price is exactly zero.

The descending branch (used when `gas_used <= gas_target`) can, in principle, drive `price` down toward this fixed point: `price_change` is computed as `price * gas_delta / (gas_target * gas_price_max_change_denominator)`, i.e., a fraction of the current price shrinking each block. For any `gas_price_max_change_denominator > 1`, integer-division flooring causes decay to stall at a small positive value before reaching literal zero, but for pathological/edge configurations of `gas_price_max_change_denominator` (a versioned constant, loaded from `apollo_versioned_constants/resources/orchestrator_versioned_constants_0_14_x.json`) that approach or equal `1`, an empty/near-empty block (`gas_used = 0`) subtracts the *entire* current price in a single step, landing exactly on `GasPrice(0)`.

Downstream, this zero price is fatal in a different way: `convert_to_sn_api_block_info` wraps all gas-price fields (including `l2_gas_price_fri`) in `NonzeroGasPrice::new`, which explicitly rejects zero: [2](#0-1) [3](#0-2) 

Once `self.l2_gas_price` in `sequencer_consensus_context.rs` becomes (and stays) `GasPrice(0)` due to the fixed-point bug above, `convert_to_sn_api_block_info` will begin returning `Err(StarknetApiError::ZeroGasPrice)` for every subsequent block-info conversion, since the price can never self-correct back above zero: [4](#0-3) 

### Impact Explanation
Once the L2 gas price is driven to exactly zero, it is permanently stuck there — the very mechanism intended to raise it back toward `min_gas_price` is disabled by the same zero value it's supposed to correct. Every subsequent proposer/validator that relies on `convert_to_sn_api_block_info` (and any other consumer requiring `NonzeroGasPrice`) will fail to construct valid block info from that point forward, which can prevent the network from confirming new transactions — an accepted High/Medium-severity impact per the validation criteria ("a network unable to confirm new transactions").

### Likelihood Explanation
Reaching literal zero via the "empty-block decay" path requires either (a) an unusually low `gas_price_max_change_denominator` versioned constant (not currently observed as `1` in the shipped `0_14_x` JSON constants, so likely not triggerable under current production constants) or (b) some other path setting `self.l2_gas_price` to zero directly. This makes the "reach zero" precondition uncertain under current versioned constants — I could not confirm from the indexed JSON values whether `gas_price_max_change_denominator` is ever small enough in practice to hit exactly zero in one step. However, the underlying logic flaw (once at zero, the "increase toward minimum" branch is a permanent no-op) is a genuine, unconditional code defect independent of how zero is first reached, and is inconsistent with the function's own asserted invariant that price is bounded by `min_gas_price` via gradual increase.

### Recommendation
In the "price below minimum" branch, do not derive the increase step as a fraction of the (possibly zero) current price. Use an absolute minimum step (e.g., `max(price.0 / MIN_GAS_PRICE_INCREASE_DENOMINATOR, 1)` or a step derived from `min_gas_price` instead of `price`) so that a price of zero can still climb back toward `min_gas_price` over subsequent blocks, matching the function's documented intent.

### Proof of Concept
1. Assume (via configuration or an intervening bug) `self.l2_gas_price` becomes `GasPrice(0)` for some block height, with `min_gas_price = GasPrice(N)`, `N > 0`.
2. Call `calculate_next_base_gas_price(GasPrice(0), gas_used, gas_target, GasPrice(N))`.
3. Since `price (0) < min_gas_price (N)`, the function takes the "increase" branch: `max_increase = 0 / MIN_GAS_PRICE_INCREASE_DENOMINATOR = 0`; `adjusted = 0`; `adjusted_price = 0.min(N) = 0`.
4. The function returns `GasPrice(0)` again — deterministically, for any number of subsequent calls, regardless of `gas_used`/`gas_target`.
5. Every block thereafter, `self.l2_gas_price` remains `GasPrice(0)`, and `convert_to_sn_api_block_info` (invoked per-block via `NonzeroGasPrice::new`) will error with `ZeroGasPrice` from that point on [5](#0-4) , blocking block-info construction indefinitely.
