## Analog Vulnerability Found

### Title
Missing cross-check between JWT session-token `dest` claim and caller-supplied `shop` parameter in `shopify.auth.tokenExchange()` - (File: `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`)

### Summary
The reported UStb bug is a class of vulnerability where a security-sensitive function validates one input (the caller/`msg.sender`) but never cross-checks it against a second, logically-related input (`from`) that should also satisfy the same invariant. The `tokenExchange` function in `shopify-app-js` exhibits the same pattern: it decodes and cryptographically validates the session token, but it never verifies that the token's `dest` (destination shop) claim actually matches the `shop` argument that is used to build the OAuth request sent to Shopify.

### Finding Description
`tokenExchange()` accepts two independent inputs from its caller: `shop` and `sessionToken`. [1](#0-0) 

It calls `decodeSessionToken(config)(sessionToken)` purely to validate the JWT's signature/expiry/audience — the decoded payload (which contains the trusted `dest` field identifying which shop the token was actually issued for) is discarded and never compared to the `shop` parameter. The function then builds the token-exchange request using the caller-supplied `shop` verbatim: [2](#0-1) 

The two first-party integrations in this monorepo happen to derive `shop` safely, from the token's own `dest` claim, before calling this function:
- `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts` — `const shop = new URL(payload.dest).hostname;` [3](#0-2) 
- `packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts` — `shop` comes from `validateSessionToken` → `payload.dest` [4](#0-3) 

However `shopify.auth.tokenExchange` is a documented public API (`TokenExchangeParams`) that any consumer of `@shopify/shopify-api` (custom frameworks, Cloudflare Workers, non-Remix/Express integrations) can call directly with their own derivation of `shop` — e.g. from a query string, header, or any other request-derived value — exactly analogous to how the UStb contract trusted `msg.sender`'s role but never checked that the `from` address itself held the required role.

### Impact Explanation
If a consuming application derives the `shop` value from an untrusted source (e.g., `req.query.shop`) instead of from the verified JWT `dest` claim, an attacker holding a *valid session token for their own shop* could request that the library perform a token exchange **for a shop of the attacker's choosing** (any string satisfying `sanitizeShop`). Because `client_id`/`client_secret` are the app's own static credentials and Shopify's `/admin/oauth/access_token` endpoint trusts the `subject_token`'s validity together with the `shop` in the URL, this could result in the library silently generating/persisting an access token under the wrong shop identity in the app's session storage — a cross-tenant session-storage injection primitive, matching the "session-storage injection" acceptance criterion.

### Likelihood Explanation
Low-to-moderate, similar to the original finding's judged severity: exploitation requires a consuming app to violate an implicit (but undocumented in code) invariant by not deriving `shop` from the token itself. The two reference implementations in this repo do it correctly, so real-world impact depends on third-party or custom integrations built directly on `@shopify/shopify-api`. As with the original report, the library provides no defense at the trust boundary itself — the check is left entirely to callers, with no runtime assertion tying `shop` to `payload.dest`.

### Recommendation
Inside `tokenExchange()`, after decoding the session token, assert that `new URL(payload.dest).hostname` (post `sanitizeShop`) equals the sanitized `shop` argument, and throw an `InvalidJwtError`/`InvalidShopError` on mismatch — mirroring the recommended fix in the original report of adding the missing role/identity check rather than relying on callers to enforce it correctly.

### Proof of Concept
1. A hypothetical custom integration (not shopify-app-express/remix) implements:
   ```ts
   const shop = req.query.shop; // attacker-controlled, NOT derived from the token
   const sessionToken = req.headers.authorization.replace('Bearer ', ''); // valid token for attacker-shop.myshopify.com
   const { session } = await shopify.auth.tokenExchange({ shop, sessionToken, requestedTokenType: RequestedTokenType.OfflineAccessToken });
   await sessionStorage.storeSession(session);
   ```
2. Attacker sends a valid session token issued for `attacker-shop.myshopify.com` but sets `?shop=victim-shop.myshopify.com`.
3. `tokenExchange()` only validates the JWT signature/expiry via `decodeSessionToken`, never compares `payload.dest` to `shop`, and proceeds to call `https://victim-shop.myshopify.com/admin/oauth/access_token` with the app's own `client_id`/`client_secret` and the attacker's `subject_token`.
4. If Shopify's endpoint honors this combination (subject_token valid + shop param independent), the resulting session is created/stored under `victim-shop.myshopify.com`, achieving cross-tenant session confusion — directly caused by the missing consistency check identified in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts` lines 32-54.
