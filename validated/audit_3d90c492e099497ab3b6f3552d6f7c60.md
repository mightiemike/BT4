### Title
Function-call access key allowance limit is not enforced when the key is used via a `DelegateAction` (meta-transaction), allowing the spending cap to be bypassed - (File: `runtime/runtime/src/actions.rs`)

### Summary
The `restrictedMint`/pause-bypass pattern in the reported ArrakisV2 issue — a spending/authorization restriction that is enforced on one entry path but *not* on an alternate entry path into the same state-mutating logic — has a direct analog in nearcore's function-call access-key model. A `FunctionCallPermission` access key carries an `allowance: Option<Balance>` field that is meant to cap the total `$NEAR` the key can spend on gas/fees [1](#0-0) . This cap is enforced when the key signs a normal transaction directly (`check_and_compute_new_allowance` in the verifier), but it is intentionally **not checked at all** when the same key is used to sign the inner `DelegateAction` of a meta-transaction, as explicitly documented in the project's own architecture docs [2](#0-1) .

### Finding Description
`validate_delegate_action_key` in `runtime/runtime/src/actions.rs` is the function that authorizes a `DelegateAction` against the sender's access key. It validates the nonce, checks that the permission is a `FunctionCall` permission when required, validates the action count, the zero-deposit rule, the `receiver_id` match, and the `method_names` match [3](#0-2) . Nowhere in this function (nor anywhere else in the delegate-action apply path, `apply_delegate_action`, at lines 453-535) is the key's `allowance` field read, decremented, or checked against a spend limit — unlike the direct-transaction path where `verify_and_charge_tx_ephemeral` explicitly calls the allowance check (`check_and_compute_new_allowance`) as part of authorizing the transaction (per `protocol-model/spec/accounts-keys.md`, item 4: "Allowance: `check_and_compute_new_allowance`... for a FunctionCall key with a finite allowance, subtracts total_cost"). In the meta-transaction path, all gas/fee costs are paid by the relayer, so the allowance check is simply skipped, and the key's `allowance` value in storage is left untouched.

This is confirmed both by the nearcore documentation and by the project's own test suite: `meta_tx_fn_call_access_key_insufficient_allowance` deliberately sets an access key allowance of `1 yoctoNEAR` (far less than the cost of any call) and asserts that the call **still succeeds** when routed through a meta-transaction, whereas the same call would be rejected with `NotEnoughAllowance` if signed directly [4](#0-3) .

### Impact Explanation
An account owner who issues a restricted function-call access key with a deliberately small `allowance` — the protocol's documented mechanism for bounding how much of the account's balance a given key/application/integration is allowed to spend — intends that cap to be an authorization boundary, not merely a convenience default. Any holder of that key (or any relayer colluding with/impersonating that key holder) can completely bypass the allowance cap by wrapping the same signed action in a `DelegateAction` and having any account submit it as a meta-transaction. This defeats the security guarantee the allowance field is supposed to provide: a key meant to be limited to spending, say, 0.01 NEAR on gas fees can be used an unlimited number of times through a relayer without ever being blocked, because the allowance is never decremented or checked on that path. This is the same *category* of bug as the reported ArrakisV2 issue: a value-limiting guard exists and is enforced on the "front door" (`rlp_execute`/direct tx) but is completely absent on an alternate reachable path (`burn`/`DelegateAction`) into the same privileged operation, letting an unprivileged caller circumvent an intended spending restriction.

### Likelihood Explanation
This is reachable by any single relayer-submitted meta-transaction — no validator collusion, network-layer manipulation, or privileged access is required. The relayer only needs the user's signature over a `DelegateAction` using the function-call access key (which the key holder or an entity with access to sign meta-transactions for the sender already possesses, per the intended meta-tx UX). The nearcore team is aware of and has explicitly documented this behavior as "This behavior is in the spirit of allowance limiting how much financial resources the user can use... but if someone were to limit a function access key to one trivial action by setting a very small allowance, that is circumventable by going through a relayer" [5](#0-4) , and there is a passing regression test (`meta_tx_fn_call_access_key_insufficient_allowance`) that locks in this exact bypass as expected behavior rather than as a bug to fix [6](#0-5) .

### Recommendation
If the allowance field is intended to be a hard authorization boundary (as its doc-comment states: "Allowance is a balance limit to use by this access key to pay for function call gas and transaction fees"), `validate_delegate_action_key` in `runtime/runtime/src/actions.rs` should be extended to check and decrement the key's `allowance` against some accounting of the cost attributable to the sender's key usage when processing a `DelegateAction`, mirroring `check_and_compute_new_allowance` in the direct-transaction verifier path. Alternatively, if this is accepted as intended/documented protocol behavior (as the current code and docs suggest), no code change is required, but the `FunctionCallPermission::allowance` documentation and the `AccessKeyPermissionView` returned to wallets/dApps should explicitly warn that the allowance limit does not apply to actions authorized via meta-transactions/`DelegateAction`, since this deviates from the "spending cap" mental model that most integrators reasonably assume.

### Proof of Concept
1. Alice creates a `FunctionCallPermission` access key for `bob.near`/`some_method` with `allowance = 1 yoctoNEAR` (effectively zero usable balance for gas), intending it to prevent any real transaction from that key from being processed directly.
2. Alice signs a `DelegateAction` invoking `some_method` with that key and passes it to any relayer (e.g., `alice_account()`), as in `setup_with_access_key` / `check_meta_tx_fn_call` in the test harness.
3. The relayer submits the meta-transaction; on the receiver's shard `apply_delegate_action` → `validate_delegate_action_key` authorizes the call purely based on nonce, receiver, and method-name checks — the `allowance` field is never inspected.
4. The call succeeds and the access key's `allowance` remains unchanged at `1 yoctoNEAR`, exactly as demonstrated by `meta_tx_fn_call_access_key_insufficient_allowance` [6](#0-5) . Repeating this process an arbitrary number of times shows the "restricted spending" key is unrestricted when routed through meta-transactions.

## Function access keys in meta transactions

Assume alice sends a meta transaction and signs with a function access key.
How exactly are permissions applied in this case?

Function access keys can limit the allowance, the receiving contract, and the
contract methods. The allowance limitation acts slightly strange with meta
transactions.

But first, both the methods and the receiver will be checked as expected. That
is, when the delegate action is unwrapped on Alice's shard, the access key is
loaded from the DB and compared to the function call. If the receiver or method
is not allowed, the function call action fails.

For allowance, however, there is no check. All costs have been covered by the
relayer. Hence, even if the allowance of the key is insufficient to make the call
directly, indirectly through meta transaction it will still work.

This behavior is in the spirit of allowance limiting how much financial
resources the user can use from a given account. But if someone were to limit a
function access key to one trivial action by setting a very small allowance,
that is circumventable by going through a relayer. An interesting twist that
comes with the addition of meta transactions.

    // The restriction of "function call" access keys:
    // the transaction must contain the only `FunctionCall` if "function call" access key is used
    if let Some(function_call_permission) = access_key.permission.function_call_permission() {
        if actions.len() != 1 {
            result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                InvalidAccessKeyError::RequiresFullAccess,
            )
            .into());
            return Ok(());
        }
        if let Some(Action::FunctionCall(function_call)) = actions.get(0) {
            if function_call.deposit > Balance::ZERO {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DepositWithFunctionCall,
                )
                .into());
                // Before this fix, the missing early return allowed execution
                // to fall through to the receiver_id and method_name checks,
                // which could overwrite this error with a different one.
                if ProtocolFeature::FixDelegateActionDepositWithFunctionCallError
                    .enabled(apply_state.current_protocol_version)
                {
                    return Ok(());
                }
            }
            if delegate_action.receiver_id() != &function_call_permission.receiver_id {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::ReceiverMismatch {
                        tx_receiver: delegate_action.receiver_id().clone(),
                        ak_receiver: function_call_permission.receiver_id.clone(),
                    },
                )
                .into());
                return Ok(());
            }
            if !function_call_permission.method_names.is_empty()
                && function_call_permission
                    .method_names
                    .iter()
                    .all(|method_name| &function_call.method_name != method_name)
            {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::MethodNameMismatch {
                        method_name: function_call.method_name.clone(),
                    },
                )
                .into());
                return Ok(());
            }
        } else {
            // There should Action::FunctionCall when "function call" permission is used
            result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                InvalidAccessKeyError::RequiresFullAccess,
            )
            .into());
