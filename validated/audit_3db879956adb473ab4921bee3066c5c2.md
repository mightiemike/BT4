Based on my investigation, I found a genuine analog in the sequencer's Declare-transaction execution path, but there's already a partial mitigation in the mempool layer, and a residual gap at the execution/blockifier layer. Let me lay out the analysis and finding.

### Title
Declare-transaction class-hash squatting griefing causes guaranteed-fee-loss revert for the original declarer - (File: `crates/blockifier/src/transaction/transactions.rs`)

### Summary
The Starknet `Declare` transaction's class registration is keyed solely by the deterministic `class_hash` of the submitted Sierra/CASM bytecode, with no binding to the declaring account or nonce. A griefer who can observe an honest declarer's pending transaction (in the mempool, over P2P gossip, or simply by independently computing the same class hash from public source code) can submit their own `Declare` transaction for the identical `class_hash` and get it included first. When the victim's transaction subsequently executes, `try_declare` finds the class hash already registered and reverts the transaction — yet the victim still pays the transaction fee, since only `__validate__` succeeding (not `__execute__`) is required for fee collection on Starknet. This mirrors the NFT-grief bug class: a public, deterministically-derived resource key (NFT token id / class hash) lets an unprivileged third party manipulate shared state ahead of a legitimate actor's transaction, forcing a guaranteed revert and fee loss for the victim while the griefer's cost is comparatively low (they pay only their own declare fee for the same, now-shared, class).

### Finding Description
The relevant check lives in `try_declare`: [1](#0-0) 

```
fn try_declare<S: State>(...) -> TransactionExecutionResult<()> {
    match state.get_compiled_class(class_hash) {
        Err(StateError::UndeclaredClassHash(_)) => { ... Ok(()) }
        Err(error) => Err(error)?,
        Ok(_) => {
            // Class is already declared, cannot redeclare.
            Err(TransactionExecutionError::DeclareTransactionError { class_hash })
        }
    }
}
```

This is a per-`class_hash` global uniqueness check with no relation to the sender or nonce of the transaction that ultimately wins the race — analogous to `ParticleExchange`'s `safeTransferFrom` reverting because a shared resource (the NFT) was moved by an unrelated party's transaction between submission and execution of the victim's transaction.

The mempool layer already has a *partial* mitigation for one variant of this class-hash-squatting griefing: it delays making incoming `Declare` transactions eligible for proposal (`declare_delay`), and explicitly rejects any fee-escalation replacement attempt against a delayed declare via `validate_no_delayed_declare_front_run`: [2](#0-1) 

That mechanism, however, only protects against a *replacement at the same `(address, nonce)`* — i.e., an attacker trying to bump-fee-replace the exact pending transaction. It does **not** and cannot protect against an entirely different account submitting an independent `Declare` transaction (different sender, different nonce) for the same `class_hash`. Such a transaction is fully valid at the mempool-admission level (unique nonce, its own account state) and is only rejected at execution time deep in `try_declare`, after the honest declarer's competing transaction has already been charged its fee.

### Impact Explanation
Any account that submits a `Declare` transaction for a not-yet-declared class is exposed: if the bytecode/class hash becomes visible before block inclusion (via mempool propagation, gossip, or because the source code is public/well-known — e.g. common OpenZeppelin-derived account or ERC-20 templates), any other unprivileged account can declare the same `class_hash` first. The victim's transaction then deterministically reverts in `try_declare`, and Starknet's fee model still charges the fee for a transaction whose `__validate__` succeeded even though `__execute__` reverted, resulting in a guaranteed, repeatable loss of funds (fee) for the victim with no way to recover, matching the "concrete loss of funds" bar in the validation criteria.

### Likelihood Explanation
This is trivially reachable by any unprivileged L2 account: it requires only submitting a standard `Declare` transaction for a `class_hash` observed in another pending transaction (or independently computed from public source). No special privileges, node role, or network position beyond ordinary mempool visibility is needed, and the `declare_delay`/`validate_no_delayed_declare_front_run` protections in `apollo_mempool` explicitly do not cover this cross-account race, since they only guard the specific `(address, nonce)` slot.

### Recommendation
Extend the griefing protection beyond the single `(address, nonce)` slot: track pending/delayed class hashes across all senders in `apollo_mempool` (not just per-address nonce collisions), and reject or delay-queue any newly submitted `Declare` transaction that targets a `class_hash` already pending declaration by another sender until the original is resolved. Alternatively/additionally, consider refunding or reducing the fee charged for a transaction that reverts purely due to `DeclareTransactionError` (class already declared), since the outcome is entirely predictable and outside the declarer's control once front-run.

### Proof of Concept
1. Account A crafts and broadcasts a `Declare` transaction `tx_A` for class hash `C` (nonce `n_A`).
2. Attacker B observes `tx_A` in the mempool/gossip (or independently derives `C` from known source code) and immediately submits `tx_B`, a `Declare` transaction for the same `class_hash` `C`, from an unrelated account with an unrelated valid nonce `n_B`.
3. Both `tx_A` and `tx_B` pass mempool admission (different `(address, nonce)` pairs — `validate_no_delayed_declare_front_run` and fee-escalation logic in `crates/apollo_mempool/src/mempool.rs` do not apply across different senders).
4. Whichever of `tx_A`/`tx_B` executes second reaches `try_declare` in `crates/blockifier/src/transaction/transactions.rs`, finds `state.get_compiled_class(class_hash)` already populated, and returns `TransactionExecutionError::DeclareTransactionError { class_hash }`, reverting execution.
5. The reverted transaction still consumes the sender's fee at the standard Starknet fee-charging step, since `__validate__` succeeded — the victim has lost funds for a transaction whose outcome was fully controllable by an adversary who merely resubmitted the same public bytecode first.

/// Attempts to declare a contract class by setting the contract class in the state with the
/// specified class hash.
fn try_declare<S: State>(
    tx: &DeclareTransaction,
    state: &mut S,
    class_hash: ClassHash,
    compiled_class_hash: Option<CompiledClassHash>,
) -> TransactionExecutionResult<()> {
    match state.get_compiled_class(class_hash) {
        Err(StateError::UndeclaredClassHash(_)) => {
            // Class is undeclared; declare it.
            state.set_contract_class(class_hash, tx.contract_class().try_into()?)?;
            if let Some(compiled_class_hash) = compiled_class_hash {
                state.set_compiled_class_hash(class_hash, compiled_class_hash)?;
            }
            Ok(())
        }
        Err(error) => Err(error)?,
        Ok(_) => {
            // Class is already declared, cannot redeclare.
            Err(TransactionExecutionError::DeclareTransactionError { class_hash })
        }
    }
}
