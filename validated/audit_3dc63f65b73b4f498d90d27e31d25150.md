### Title
Starknet OS `replace_class` syscall omits declared-class validation present in Blockifier, causing honest-node re-execution divergence - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo)

### Summary
The Cairo implementation of the `replace_class` syscall in the Starknet OS program (`execute_replace_class`) unconditionally updates a contract's `class_hash` in `contract_state_changes` without checking that `request.class_hash` corresponds to an actually declared (and Cairo1) contract class. This mirrors the Escher `sale.edition` bug class: a downstream state transition trusts a caller-supplied reference (a class hash / "edition" contract) without verifying it was legitimately registered through the proper mechanism (declaration via `Escher721Factory` analog = Starknet's declare-transaction/class-registration flow).

### Finding Description
Blockifier — the execution engine used during block building — enforces in `SyscallHintProcessor::replace_class` (via `syscall_base.rs`) that the class hash passed to `replace_class_syscall` must already be declared (`self.state.get_compiled_class(class_hash)?`) and must be a Cairo1 class, rejecting the call with `ForbiddenClassReplacement`/`"is not declared"` otherwise [1](#0-0) . The deprecated (Cairo0) syscall path enforces the analogous check by calling `get_compiled_class` before `set_class_hash_at` [3](#0-2) .

The Starknet OS's own Cairo re-implementation of this syscall (`execute_replace_class` in `syscall_impls.cairo`), which re-executes transactions to build the OS program's proof of the same block, performs no such check — it directly updates the `StateEntry.class_hash` for the contract with the attacker/caller-supplied `class_hash`, with an explicit TODO acknowledging the missing check [4](#0-3) . Any contract can invoke `replace_class_syscall` on itself (this is not a privileged operation — it's `self.call.storage_address`, i.e. the calling contract itself), so an ordinary transaction can pass an arbitrary, never-declared `class_hash` value.

### Impact Explanation
Because Blockifier rejects a `replace_class` call with an undeclared class hash (transaction reverts / fails), while the OS Cairo implementation accepts it and commits the (illegitimate) class hash to `contract_state_changes`, the sequencer's committed block state (built via Blockifier) and the Starknet OS's re-executed/proved state can diverge for any transaction that attempts `replace_class` with an undeclared class hash. This is exactly the class of "honest-node divergence" / "wrong committed root" bug: the OS program (which underlies proof generation and re-execution verification) would compute a different final state (and thus a different state root / block hash) than the block actually built and committed by the sequencer for the same transaction, or vice versa (accepting a state transition in the OS that the sequencer would have rejected as invalid). This can result in inability to prove correctly generated blocks, or acceptance of an invalid state transition by the OS that never should have been possible, undermining the integrity of the state root committed to L1.

### Likelihood Explanation
`replace_class_syscall` is callable by any deployed Cairo1 contract as part of ordinary `__execute__` logic — no special privilege is required, only that a contract choose to invoke the syscall on itself with a caller-controlled `class_hash` argument. Reaching the vulnerable OS code path requires only a standard invoke/transaction that performs a `replace_class` syscall passing a never-declared felt as `class_hash`. This makes the divergence trivially reachable from a single unprivileged transaction sender.

### Recommendation
Add the missing declared-class check in `execute_replace_class` in `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`, mirroring the Blockifier logic: before updating `StateEntry.class_hash`, verify that `class_hash` exists in the OS's contract-class dictionary (i.e., has a corresponding declared/compiled class, analogous to `contract_class_changes` / declared-classes tracking used elsewhere in the OS), and reject (or fail) if it is undeclared or not Cairo1, so that OS re-execution semantics exactly match Blockifier's runtime semantics.

### Proof of Concept
1. Deploy a Cairo1 contract exposing a function that calls `replace_class_syscall(class_hash)` with a caller-supplied `class_hash`.
2. Submit an invoke transaction calling that function with `class_hash = 0x1234` (a felt that was never declared on-chain).
3. In Blockifier (sequencer block-building path), this transaction reverts/fails with `"<class_hash> is not declared"`, as demonstrated by the `undeclared_class_hash` test [2](#0-1) .
4. In the Starknet OS Cairo program's `execute_replace_class`, the same call would proceed unchecked and commit `class_hash = 0x1234` into `contract_state_changes` for the contract, per the code at [4](#0-3) , producing a different resulting state/root than the sequencer's Blockifier execution would (or that Blockifier's execution engine would ever allow to succeed).
