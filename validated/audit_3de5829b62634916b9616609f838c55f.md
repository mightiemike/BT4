### Title
Unbounded gzip decompression of user-supplied Cairo0 program in `TryFrom<BroadcastedDeclareTransaction>` allows resource-exhaustion DoS via decompression bomb - (File: `crates/apollo_rpc/src/v0_8/api/mod.rs`)

### Summary
The RPC handler that converts a broadcasted `DeclareTransactionV1` (Cairo0/legacy declare, used by `simulate_transactions`/`estimate_fee`/`trace_transaction` execution paths) into an executable transaction calls `user_deprecated_contract_class_to_sn_api`, which calls `decompress_program` on the raw, user-supplied `compressed_program` field with no size or time limit.

### Finding Description
`decompress_program` base64-decodes the caller-supplied string and feeds it into a `GzDecoder`, reading to completion into an unbounded `Vec<u8>`: [1](#0-0) 

This function is reached directly from `TryFrom<BroadcastedDeclareTransaction>`, via `user_deprecated_contract_class_to_sn_api`, when handling a `BroadcastedDeclareV1Transaction` submitted by any unprivileged RPC caller: [2](#0-1) 

Unlike every other decompression path in the codebase that touches untrusted/serialized program data — `crates/starknet_api/src/compression_utils.rs`'s `decompress_with_size_limit` (bounds output to `max_size`), `crates/apollo_storage/src/compression_utils.rs`'s `decompress` (bounded by `MAX_DECOMPRESSED_SIZE = 256MB` via `zstd::bulk::decompress`), and the P2P class converter in `crates/apollo_protobuf/src/converters/class.rs` (`decode_and_decompress_with_size_limit(&value.program, MAX_CAIRO0_PROGRAM_SIZE)` with a 4MB cap) — this specific decoder has no such bound. The `// TODO(dan): add time and size limits.` comment on the line confirms the omission is unintentional/incomplete relative to the size-limited siblings.

A gzip "zip bomb" (a tiny compressed payload that expands to gigabytes) can therefore be embedded as `compressed_program` in a `DECLARE` v1 transaction sent to `starknet_estimateFee`, `starknet_simulateTransactions`, or `starknet_traceTransaction`-style RPC calls that go through this conversion path, causing the decoder to allocate and fill an unbounded `Vec<u8>` in memory, exhausting CPU and RAM on the serving node.

### Impact Explanation
This is a resource-exhaustion Denial-of-Service against the JSON-RPC serving process handling transaction simulation/estimation, matching the exact bug class of the referenced CVE-2021-37865 (unbounded decompression of attacker-controlled data leading to server-side DoS). It does not affect state commitment, block hash, consensus, or the Batcher/Blockifier execution path — it lives in the RPC layer's transaction-simulation conversion code, which is a read/simulation utility rather than part of the committed sequencer state-transition pipeline.

### Likelihood Explanation
Reachable by any unauthenticated/unprivileged client capable of calling the affected RPC methods with a crafted declare-v1 payload; requires no special privileges beyond normal RPC access.

### Recommendation
Apply the same bounded-decompression approach already used elsewhere in the codebase (`decode_and_decompress_with_size_limit` / `MAX_CAIRO0_PROGRAM_SIZE`-style limiting, or `zstd`'s bounded decompress) to `decompress_program`, capping both output size and, ideally, decompression time, before parsing the JSON program.

### Proof of Concept
Send a `DECLARE` v1 transaction to `starknet_estimateFee` / `starknet_simulateTransactions` with `contract_class.program` set to a small base64-encoded gzip bomb (e.g., a few KB compressed expanding to several GB of repeated zero bytes). `decompress_program` (`crates/apollo_rpc/src/v0_8/api/mod.rs:671-682`) will attempt to fully decompress it into memory with no cap, exhausting node memory/CPU before the subsequent `serde_json::from_reader` parse is even reached.

**Note on confidence:** I could not fully trace runtime deployment topology to confirm whether this RPC crate's execution-simulation code path runs on the same process/resources as consensus-critical components in all deployment configurations, nor whether upstream request-size limits (e.g., `apollo_http_server`'s max body size) would truncate the base64 payload size enough to bound the achievable decompression ratio in practice. This should be verified against the deployed HTTP body-size limits and the JSON-RPC method dispatch before treating this as fully exploitable in production.

pub(crate) fn decompress_program(
    base64_compressed_program: &String,
) -> Result<Program, ErrorObjectOwned> {
    base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    let compressed_data =
        base64::decode(base64_compressed_program).map_err(internal_server_error)?;
    // TODO(dan): add time and size limits.
    let mut decoder = GzDecoder::new(compressed_data.as_slice());
    let mut decompressed = Vec::new();
    decoder.read_to_end(&mut decompressed).map_err(internal_server_error)?;
    serde_json::from_reader(decompressed.as_slice()).map_err(internal_server_error)
}
