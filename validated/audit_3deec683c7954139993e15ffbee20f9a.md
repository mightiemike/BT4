### Title
Webhook HMAC verification does not bind the signature to the `X-Shopify-Shop-Domain` (or `shopify-domain`) header, allowing shop-identity spoofing analogous to unverified `PeerId`/public-key binding - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
The `GHSA-wc36-xgcc-jwpr` advisory describes a signature-verification bug class where a valid signature is accepted without checking that the signing key actually corresponds to the identity attached to the signed data — allowing an attacker to reattach a valid signature to a different identity. The webhook validation logic in `shopify-app-js` exhibits the same structural flaw: the webhook HMAC is computed and verified only over the raw request body, while the shop identity (`domain`) used for all downstream authorization decisions is taken from an unauthenticated HTTP header that is not included in the signed data.

### Finding Description
`validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` computes the local HMAC using only `rawBody`: [1](#0-0) 

`validateFactory` in `packages/apps/shopify-api/lib/webhooks/validate.ts` calls this body-only HMAC check, and only *after* it passes does it separately pull the `domain` header out of the (unauthenticated) headers via `checkWebhooksHeaders`/`checkEventsHeaders`: [2](#0-1) [3](#0-2) 

The `domain` field returned by `validate()` is never cross-checked against anything covered by the HMAC signature — it is pure header content. Because Shopify computes webhook HMACs using the app's single shared `apiSecretKey` (the same secret for *every* shop that has installed the app, not a per-shop secret), any merchant who has installed the app on their own store can capture a body+HMAC pair from a real webhook delivered to their own shop, and then replay that exact body/HMAC while substituting the `X-Shopify-Shop-Domain` header value with an arbitrary victim shop's domain. The HMAC check still passes because the header is not part of the signed content.

That forged `domain` value flows unchecked into the trust boundary: `process.ts` passes `webhookCheck.domain` directly into the app's webhook `callback` handler as the `shop_domain` argument: [4](#0-3) 

In the framework packages, `authenticateWebhookFactory` uses `check.domain` to load an offline session/access token via `ensureValidOfflineSession(params, check.domain)`, then builds an authenticated Admin API client bound to that session and passes it to the app's handler along with the attacker-controlled payload: [5](#0-4) [6](#0-5) 

This mirrors the `SignedEnvelope`/`PeerRecord` flaw exactly: a valid signature (HMAC) is accepted for "any combination" with an identity claim (the shop domain) that isn't bound to what was actually signed.

### Impact Explanation
An attacker who is a legitimate, unprivileged merchant with the app installed on their own store can:
1. Trigger a real event in their own store to obtain a genuine `(rawBody, hmac)` pair signed with the app's shared secret.
2. Replay that request to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain.
3. Cause the app to load the victim shop's stored offline session/access token (`ensureValidOfflineSession`) and invoke the app's webhook business logic as if the event legitimately originated from the victim shop, using an authenticated Admin/Storefront API client scoped to the victim.

Depending on what the app's webhook handlers do (e.g., updating victim data, revoking access, triggering side effects using attacker-controlled payload fields), this enables cross-tenant impact: unauthorized actions taken against a victim merchant's store/session using a forged shop identity, and injection of the app's internal shop/session-keyed state with attacker-controlled data.

### Likelihood Explanation
Requires only a single unprivileged actor: any merchant that installs the app on their own store. No MITM, no dependency compromise, no leaked secrets, and no elevated privileges are needed — the actor only needs to intercept/replay their own valid outbound webhook request and swap one header. The attack surface (a public webhook HTTP endpoint) is reachable by definition.

### Recommendation
Bind the shop identity to the signed content instead of trusting the `X-Shopify-Shop-Domain`/`shopify-domain` header independently:
- Include the domain/shop header (and ideally topic/api-version/webhook-id) in the HMAC input when computing/verifying the webhook signature, or
- Cross-validate the header-derived `domain` against a shop identifier embedded in the (also-signed) body payload, and reject on mismatch, or
- If Shopify's actual wire protocol does not sign these headers (this should be confirmed against Shopify's current webhook spec), enforce a secondary binding — e.g., verifying the resolved session's shop against additional out-of-band webhook metadata (webhook ID uniqueness/registration records tied to a specific shop) before trusting `check.domain` for session lookup.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook (e.g., `orders/create`) delivered with a valid `X-Shopify-Hmac-Sha256` computed over `rawBody` using the app's shared secret.
2. Attacker captures `(rawBody, hmac)` from that delivery.
3. Attacker POSTs to the app's `/webhooks` endpoint with the same `rawBody` and `hmac`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `validateHmacFromRequestFactory` verifies the HMAC successfully (body unchanged) — `packages/apps/shopify-api/lib/utils/hmac-validator.ts` lines 185-197.
5. `checkWebhooksHeaders` returns `domain: 'victim-shop.myshopify.com'` untouched from the header — `packages/apps/shopify-api/lib/webhooks/validate.ts` lines 99-134.
6. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading the victim's offline session and admin client, then invokes the app's webhook handler with the attacker's payload under the victim's identity — `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts` lines 35-102.

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

      rawBody,

      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);

      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

import {BasicParams} from '../types';

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}
