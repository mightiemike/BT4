### Title
Attacker-controlled `fund_recipient` can permanently strand outbound-revert PRC20 funds in `ABORTED` state with no escrow fallback - (File: x/uexecutor/keeper/outbound.go)

### Summary
The Wagmi Leverage bug is a direct-transfer-to-a-hostile-address pattern: repayment logic pushes funds straight to a creditor address that can make the transfer revert, and there is no fallback/escrow, so the whole flow gets stuck. The same shape exists in `x/uexecutor`'s outbound-failure recovery path: `handleFailedOutbound` re-mints bridged PRC20 tokens directly to a user-supplied `recipient` address, and if that call reverts, the outbound is simply marked `ABORTED` with no escrow or retry-to-alternate-address mechanism.

### Finding Description
When a destination-chain outbound (`FUNDS`, `GAS_AND_PAYLOAD`, `FUNDS_AND_PAYLOAD`) is voted as failed by Universal Validators, `handleFailedOutbound` computes a `recipient` for the re-mint: [1](#0-0) 

That `recipient` defaults to `outbound.Sender` but is overridden by `outbound.RevertInstructions.FundRecipient` whenever it is non-empty. `RevertInstructions.FundRecipient` is populated from `event.RevertRecipient`, an attacker-controlled field decoded from the `UniversalTxOutbound` event emitted by the user's own universal payload execution: [2](#0-1) 

The token re-mint is executed via `CallPRC20Deposit`, a `DerivedEVMCall` to `UniversalCore.depositPRC20Token(prc20, amount, to)`: [3](#0-2) 

If this EVM call fails for any reason tied to the recipient (e.g. `to` is a contract without accepting logic, is address-zero after malformed encoding, or otherwise causes the mint/transfer path in `UniversalCore`/PRC20 to revert), `handleFailedOutbound` does not fall back to an escrow or to the original sender — it immediately calls `AbortOutbound`, which sets the outbound to a terminal `ABORTED` state requiring manual/governance intervention: [4](#0-3) [5](#0-4) 

This mirrors the Wagmi Leverage flaw precisely: value is pushed to an attacker-influenced address with no escrow/try-catch-to-safe-account fallback, so a single unreceivable recipient can permanently freeze funds recovery for that outbound (funds sit un-reverted, and the automatic path can never complete without an admin).

I was not able to verify the exact Solidity implementation of `UniversalCore.depositPRC20Token` / the PRC20 contract (its source was not found in the indexed portion of the repository), so I cannot confirm with certainty whether the PRC20 mint path can actually be made to revert by an attacker choosing a specific recipient address (e.g. via a blacklist, a reverting fallback, or an invalid/zero-code-size contract check). This is the key uncertainty that determines whether the "unreceivable recipient" trigger is reachable at all.

### Impact Explanation
If the `depositPRC20Token` call can be forced to revert by the chosen recipient, an attacker can guarantee that any outbound requiring a revert-mint lands in `ABORTED` status permanently, since there is no retry-with-alternate-recipient or escrow-holding logic — matching the "Allowed Impact" criteria of permanent freezing of protocol/user funds reachable through an ordinary/attacker-influenced execution path (the payload that emits `RevertRecipient` is user-supplied). Because `AbortOutbound` explicitly states manual intervention is required, this is a genuine freezing of funds outside the normal automated flow, not merely an inconvenience.

### Likelihood Explanation
Likelihood is conditioned entirely on whether `UniversalCore.depositPRC20Token`/the PRC20 implementation can revert based on recipient identity (blacklist, non-payable contract semantics, or similar). Since the Solidity contract source was not available in the indexed codebase, I could not confirm this precondition. If the mint function is a straightforward `_mint`/balance-increment with no external call or recipient-code checks, this analog does not hold and the risk is purely hypothetical.

### Recommendation
- Verify whether `UniversalCore.depositPRC20Token` (and `depositPRC20WithAutoSwap`/`refundUnusedGas`, which share this exact recipient-controlled pattern in `applyGasRefund`) can revert based on properties of the `to` address.
- If so, wrap the mint call in a try/fallback: on failure, retry with the original inbound `Sender`, or fall back to an escrow/claimable balance recorded in module state rather than leaving the outbound permanently `ABORTED`.
- Add a query/message allowing the rightful owner to claim escrowed funds once the original recipient is confirmed non-functional, avoiding indefinite dependence on manual admin action.

### Proof of Concept
1. Attacker submits a `MsgExecutePayload` whose EVM payload calls the Universal Gateway to create an outbound withdraw event with `revertRecipient` set to an address/contract crafted so that `UniversalCore.depositPRC20Token(prc20, amount, revertRecipient)` reverts (exact mechanism depends on unverified PRC20/`UniversalCore` internals — e.g. a contract that reverts on any incoming call, if the mint path performs such a call).
2. Universal Validators observe the destination-chain leg of the outbound fail and vote it via `MsgVoteOutbound` with `success=false`.
3. `FinalizeOutbound` → `handleFailedOutbound` attempts `CallPRC20Deposit(..., recipient=revertRecipient, ...)` [6](#0-5) .
4. The call errors; `AbortOutbound` sets `Status_ABORTED` and removes the entry from `PendingOutbounds`, leaving the bridged funds neither delivered on the destination chain nor re-minted on Push Chain, pending manual operator action indefinitely.

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
