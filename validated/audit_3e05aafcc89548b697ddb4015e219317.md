### Title
Unbounded step budget in `execute_call` (JSON-RPC `starknet_call`) allows single-call resource exhaustion - (File: `crates/apollo_rpc_execution/src/lib.rs`)

### Summary
The `execute_call` function backing the `starknet_call` RPC endpoint executes an arbitrary contract entry point with `limit_steps_by_resources = false` and a Sierra-gas budget taken directly from `execution_config.default_initial_gas_cost`, without ever capping the Cairo-step budget to a "single query" bound the way the dedicated view-call helper does.

### Finding Description
`execute_call` builds an `EntryPointExecutionContext` via `EntryPointExecutionContext::new_invoke` with `limit_steps_by_resources = false`: [1](#0-0) 

Because `limit_steps_by_resources` is `false`, `EntryPointExecutionContext::max_steps` returns the raw block-wide upper bound (`versioned_constants.invoke_tx_max_n_steps` for `ExecutionMode::Execute`) instead of any per-query cap: [2](#0-1) 

Likewise, `remaining_gas` (the Sierra gas budget) is initialized from `execution_config.default_initial_gas_cost` — a whole-transaction-sized constant, flagged in the code itself with a `// TODO(yair): check if this is the correct value.` comment — rather than a bound sized for a single blocking read.

This is in direct contrast to `call_view_entry_point`, the blockifier's dedicated helper for view-only external calls, which is explicitly documented as being bounded to `VIEW_CALL_MAX_SIERRA_GAS` / `VIEW_CALL_MAX_N_STEPS` "since the caller is blocked while the call runs, so the budget is sized for a read rather than for a whole transaction," and which calls `context.cap_remaining_steps(VIEW_CALL_MAX_N_STEPS)` to enforce that: [3](#0-2) 

`execute_call` performs no analogous `cap_remaining_steps` call, so a single `starknet_call` request can synchronously run up to the entire block's step budget (and the full `default_initial_gas_cost` Sierra-gas budget) worth of computation — a budget meant for committing an entire block of transactions, not for answering one synchronous read request. This mirrors the reported `callEVM` issue where a query-time call was allowed to consume resources far beyond what a bounded read should need, because the code path responsible for queries did not apply the same tight resource cap used elsewhere (`call_view_entry_point`) for read-only calls.

### Impact Explanation
Any unprivileged caller can invoke `starknet_call` (or, transitively, `estimateFee`/simulate paths built on the same `execute_call`) against a deployed contract crafted to consume close to the block's full step budget (e.g., deep or bounded recursion, dense loops) and force the executing node to run compute proportional to `invoke_tx_max_n_steps`, per single synchronous RPC request, repeatedly and in parallel. This is a resource-exhaustion / denial-of-service vector against nodes serving `starknet_call`, directly analogous to the reported `callEVM` gas issue where query execution was not properly resource-bounded, letting attackers stall RPC/execution capacity by deploying and repeatedly calling computationally expensive contracts.

### Likelihood Explanation
The path is reachable by any external, unprivileged actor issuing a standard read-only JSON-RPC `starknet_call`/simulate request against a contract they deployed themselves — no special privileges, staking, or node-operator access are required, and this matches the report's original threat model (deploy a heavy contract, then query it repeatedly).

### Recommendation
Bound `execute_call`'s step and gas budgets the same way `call_view_entry_point` does: use a fixed, appropriately small per-query constant (e.g., something on the order of `VIEW_CALL_MAX_SIERRA_GAS` / `VIEW_CALL_MAX_N_STEPS`) instead of `default_initial_gas_cost`/`invoke_tx_max_n_steps`, and call `context.cap_remaining_steps(...)` after context construction so a single call cannot consume a whole block's worth of Cairo steps.

### Proof of Concept
1. Deploy a Cairo contract with an external entry point performing bounded but heavy recursion/looping, sized to approach `invoke_tx_max_n_steps` Cairo steps and/or `default_initial_gas_cost` Sierra gas but stay under the transaction-level bounds so it would also be usable as a real (non-view) call.
2. Repeatedly send `starknet_call` (or the batcher's `call_contract`, which is built on the same `execute_call`/`EntryPointExecutionContext::new_invoke` flow) against this contract from many concurrent unauthenticated clients.
3. Because `execute_call` grants each such synchronous call the block-sized step/gas allowance (no `cap_remaining_steps`, unlike `call_view_entry_point`), each request occupies execution resources comparable to processing an entire block, degrading or exhausting the serving node's capacity to answer further calls/transactions — reproducing the "unbounded gas in queries" DoS pattern from the original report.

    /// If fee is disabled, returns the global maximum.
    /// The bound computation is saturating (no panic on overflow).
    fn max_steps(
        tx_context: &TransactionContext,
        mode: &ExecutionMode,
        limit_steps_by_resources: bool,
    ) -> usize {
        let TransactionContext { block_context, tx_info } = tx_context;
        let BlockContext { block_info, versioned_constants, .. } = block_context.as_ref();
        let block_upper_bound = match mode {
            ExecutionMode::Validate => versioned_constants.validate_max_n_steps,
            ExecutionMode::Execute => versioned_constants.invoke_tx_max_n_steps,

            log::warn!("Failed to convert global step limit to usize: {error}.");

// Calls the specified external entry point on the contract at the given address.
// Intended for view-only entry points; any attempted state changes will be discarded.
// Bounded by VIEW_CALL_MAX_SIERRA_GAS and VIEW_CALL_MAX_N_STEPS, since the caller is blocked while
// the call runs, so the budget is sized for a read rather than for a whole transaction.
pub fn call_view_entry_point(
    state_reader: impl StateReader,
    block_context: Arc<BlockContext>,
    storage_address: ContractAddress,
    entry_point_name: &str,
    calldata: Calldata,
) -> EntryPointExecutionResult<CallInfo> {
    let mut remaining_gas = VIEW_CALL_MAX_SIERRA_GAS;

    let execute_call = CallEntryPoint {
        entry_point_type: EntryPointType::External,
        entry_point_selector: selector_from_name(entry_point_name),
        calldata,
        class_hash: None,
        code_address: None,
        storage_address,
        caller_address: ContractAddress::default(),
        call_type: CallType::Call,
        initial_gas: remaining_gas.0,
    };

    // Create a dummy transaction info, since we are not in a context of a real transaction.
    let tx_context =
        Arc::new(TransactionContext { block_context, tx_info: TransactionInfo::default() });

    let limit_steps_by_resources = false;
    let mut context = EntryPointExecutionContext::new(
        tx_context,
        ExecutionMode::Execute,
        limit_steps_by_resources,
        SierraGasRevertTracker::new(remaining_gas),
    );
    // The context starts with the block's invoke_tx_max_n_steps, sized for a whole transaction.
    context.cap_remaining_steps(VIEW_CALL_MAX_N_STEPS);

    let mut state = CachedState::new(state_reader); // Changes to it are discarded.
    execute_call.non_reverting_execute(&mut state, &mut context, &mut remaining_gas.0)
