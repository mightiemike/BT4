### Title
Unauthenticated invoke transaction bypasses `__validate__` via deploy-account skip-check, allowing griefing DoS of a victim's account nonce - ([File: crates/apollo_gateway/src/stateful_transaction_validator.rs])

### Summary
The gateway's stateful transaction validator contains a UX shortcut (`skip_stateful_validations`) that skips signature verification (`__validate__`) for an `Invoke` transaction with `nonce == 1` whenever *any* transaction for that sender address already exists in the mempool or a recent block. The check only verifies presence of an account entry, not that the submitter of the nonce-1 invoke controls the account's private key. An unprivileged attacker who observes a victim's broadcast `deploy_account` transaction (visible via mempool P2P propagation) can immediately submit a forged `Invoke` transaction at nonce 1 for that same, not-yet-deployed account. This bypasses `__validate__` at admission time and gets accepted into the mempool, occupying the account's nonce-1 slot and blocking the victim's genuine follow-up transaction — analogous to BigBlueButton's CVE-2022-41960, where insufficient authenticity verification of a client-supplied identifier let an unauthenticated party disrupt a legitimate participant's session.

### Finding Description
`GenericGateway::add_tx_inner` performs stateless validation, then calls `StatefulTransactionValidator::extract_state_nonce_and_run_validations`, which:
1. Reads the account's on-chain nonce.
2. Calls `run_pre_validation_checks`, which in turn calls `skip_stateful_validations`.
3. Calls `run_validate_entry_point`, passing the `skip_validate` flag from step 2. [1](#0-0) 

`skip_stateful_validations` only checks that `tx.nonce() == 1`, `account_nonce == 0`, and that `mempool_client.account_tx_in_pool_or_recent_block(sender_address)` returns true — i.e., *some* transaction (typically the victim's `deploy_account`) exists for that address. It performs no check that the nonce-1 invoke itself was produced by the legitimate account owner: [2](#0-1) 

When `skip_validate` is `true`, `run_validate_entry_point` builds `ExecutionFlags { validate: !skip_validate, .. }`, i.e. `validate: false`, so the blockifier's `StatefulValidator::validate` never invokes the account contract's `__validate__` entry point (no ECDSA/signature check happens): [3](#0-2) 

Because the flag only skips the *validate* call for `Invoke` transactions (see `perform_validations`, which for `Invoke` calls `tx.perform_pre_validation_stage` then conditionally calls `self.validate` only `if tx.execution_flags.validate`), a forged invoke with no correct signature sails through gateway admission: [4](#0-3) 

The transaction is then handed to `mempool_client.add_tx`, and inserted into the mempool pool/queue at `(address, nonce=1)`: [5](#0-4) 

Once occupying that `(address, nonce)` slot, any subsequent legitimate transaction from the victim at the same nonce is rejected via `validate_fee_escalation`/`validate_incoming_tx` unless it out-bids the attacker's fee (which the attacker fully controls and can set arbitrarily high, since the forged tx is never actually paid for — it will be rejected at block-execution time, not admission time): [6](#0-5) 

Only later, during actual block building/execution (where `AccountTransaction::new_for_sequencing` always sets `validate: true`), will the forged transaction fail `__validate__` and be rejected — but by then it has already occupied the nonce slot and blocked the victim, and the attacker can immediately resubmit another forged nonce-1 invoke as soon as `account_tx_in_pool_or_recent_block` remains true, repeating the griefing.

### Impact Explanation
This lets any unprivileged network participant who observes a victim's `deploy_account` broadcast (via mempool P2P gossip, which is explicitly designed to propagate transactions across nodes) deny that victim the ability to get their first post-deployment transaction accepted into the mempool, indefinitely, by repeatedly squatting the nonce-1 slot with unsigned/forged transactions. This is a denial-of-service against a specific account/user — the network becomes unable to confirm the victim's new transactions — directly matching the "no vulnerability class rejected" criteria of causing "a network unable to confirm new transactions" for the targeted account.

### Likelihood Explanation
The precondition (observing a pending `deploy_account` transaction for a target address) is trivially satisfiable: it is literally the design intent that these transactions propagate through the mempool P2P gossip protocol, and the RPC endpoint returns the tx hash to any submitter. Any node participant, or even a passive observer via public JSON-RPC / P2P topic, can extract the pending sender address, then craft and submit an arbitrary invoke calldata to the gateway's HTTP endpoint with nonce=1. No cryptographic material from the victim is required. The only friction is winning the race and potentially outbidding, but the attacker can simply repeat immediately after each rejection cycle, and the attack costs the attacker nothing since gas is never charged for a `__validate__`-skipped/execution-rejected transaction added under the fee-escalation admission model (fees are checked but not charged/settled during forged occupancy).

### Recommendation
`skip_stateful_validations` must not merely check that *some* transaction exists for the sender address; it should also verify that the specific incoming nonce-1 invoke transaction is causally tied to (e.g., signed together with, or explicitly bundled with) the legitimate `deploy_account` transaction already known to the mempool/state (for instance, by checking transaction-bundling metadata submitted atomically by the same RPC caller, or by still running a lightweight authenticity check, e.g., verifying the invoke's calldata/signature against the public key that will be set by the pending constructor). At minimum, do not fully disable `__validate__`; consider deferring, not skipping, and re-validating once the `deploy_account` is confirmed, or require that both transactions arrive in the same request/session to bind them.

### Proof of Concept
1. Victim submits a valid `deploy_account` transaction for address `A` (nonce 0) via the gateway; it propagates to the mempool and is visible via mempool P2P gossip.
2. Attacker (a completely different, unrelated account) observes address `A` from the propagated transaction.
3. Attacker crafts an arbitrary `Invoke` transaction with `sender_address = A`, `nonce = 1`, and an arbitrary (unsigned/garbage) signature, and submits it to the gateway.
4. In `extract_state_nonce_and_run_validations`, `account_nonce` for `A` is `0` (not yet deployed), `tx.nonce() == 1`; `skip_stateful_validations` calls `account_tx_in_pool_or_recent_block(A)`, which returns `true` because the victim's `deploy_account` is in the mempool — see [7](#0-6) .
5. `run_validate_entry_point` is invoked with `skip_validate = true`, so `__validate__` is never executed, and the attacker's invoke (with no valid signature) is admitted and inserted into the mempool at `(A, nonce=1)`.
6. When the victim later submits their real `Invoke` transaction at `(A, nonce=1)`, mempool admission rejects it with `MempoolError::DuplicateNonce` (or requires out-bidding the attacker's chosen fee) as shown in `validate_fee_escalation` — see [8](#0-7) .
7. The attacker's forged transaction is only rejected later, during actual block execution (when real `__validate__` finally runs and fails), and the attacker can immediately repeat steps 3–6 for the next block cycle, indefinitely denying the victim's account the ability to transact.

/// Check if validation of an invoke transaction should be skipped due to deploy_account not being
/// processed yet. This feature is used to improve UX for users sending deploy_account + invoke at
/// once.
async fn skip_stateful_validations(
    tx: &ExecutableTransaction,
    account_nonce: Nonce,
    mempool_client: SharedMempoolClient,
) -> StatefulTransactionValidatorResult<bool> {
    if let ExecutableTransaction::Invoke(ExecutableInvokeTransaction { tx, .. }) = tx {
        // check if the transaction nonce is 1, meaning it is post deploy_account, and the
        // account nonce is zero, meaning the account was not deployed yet.
        if tx.nonce() == Nonce(Felt::ONE) && account_nonce == Nonce(Felt::ZERO) {
            let account_address = tx.sender_address();
            debug!("Checking if deploy_account transaction exists for account {account_address}.");
            // We verify that a deploy_account transaction exists for this account. It is sufficient
            // to check if the account exists in the mempool since it means that either it has a
            // deploy_account transaction or transactions with future nonces that passed
            // validations.
            return mempool_client
                .account_tx_in_pool_or_recent_block(tx.sender_address())
                .await
                .map_err(|err| mempool_client_err_to_deprecated_gw_err(&tx.signature(), err))
                .inspect(|exists| {
                    if *exists {
                        debug!("Found deploy_account transaction for account {account_address}.");
                    } else {
                        debug!(
                            "No deploy_account transaction found for account {account_address}."
                        );
                    }
                });
        }

    pub fn perform_validations(&mut self, tx: AccountTransaction) -> StatefulValidatorResult<()> {
        // Deploy account transaction should be fully executed, since the constructor must run
        // before `__validate_deploy__`. The execution already includes all necessary validations,
        // so they are skipped here.
        // Declare transaction should also be fully executed - otherwise, if we only go through
        // the validate phase, we would miss the check that the class was not declared before.
        match tx.tx {
            ApiTransaction::DeployAccount(_) | ApiTransaction::Declare(_) => self.execute(tx),
            ApiTransaction::Invoke(_) => {
                let tx_context = Arc::new(self.tx_executor.block_context.to_tx_context(&tx));
                tx.perform_pre_validation_stage(self.state(), &tx_context)?;
                if !tx.execution_flags.validate {
                    return Ok(());
                }

                // `__validate__` call.
                let (_optional_call_info, actual_cost) = self.validate(&tx, tx_context.clone())?;

                // Post validations.
                PostValidationReport::verify(
                    &tx_context,
                    &actual_cost,
                    tx.execution_flags.charge_fee,
                )?;

                Ok(())
            }

    /// Validates whether the incoming transaction may replace an existing one at the same
    /// `(address, nonce)` via fee escalation, without mutating any state. Returns the existing
    /// transaction to be replaced when a valid replacement exists, `None` when there is nothing to
    /// replace, or an error when a replacement is present but not permitted.
    fn validate_fee_escalation(
        &self,
        incoming_tx_reference: TransactionReference,
    ) -> MempoolResult<Option<TransactionReference>> {
        let TransactionReference { address, nonce, .. } = incoming_tx_reference;

        self.validate_no_delayed_declare_front_run(incoming_tx_reference)?;

        if !self.config.static_config.enable_fee_escalation {
            if self.tx_pool.get_by_address_and_nonce(address, nonce).is_some() {
                return Err(MempoolError::DuplicateNonce { address, nonce });
            };

            return Ok(None);
        }

        let Some(existing_tx_reference) = self.tx_pool.get_by_address_and_nonce(address, nonce)
        else {
            // Replacement irrelevant: no existing transaction with the same nonce for address.
            return Ok(None);
        };

        if !self.should_replace_tx(&existing_tx_reference, &incoming_tx_reference) {
            info!(
                "{existing_tx_reference} was not replaced by {incoming_tx_reference} due to \
                 insufficient fee escalation."
            );
            // TODO(Elin): consider adding a more specific error type / message.
            return Err(MempoolError::DuplicateNonce { address, nonce });
        }

        Ok(Some(existing_tx_reference))
    }
