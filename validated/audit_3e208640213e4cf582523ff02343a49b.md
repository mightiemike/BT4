### Title
Missing runtime guard against zero `TotalEnergyWeight` causes divide-by-zero panic in TVM energy accounting - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides by `totalEnergyWeight` while relying solely on a Java `assert` to guarantee the denominator is non-zero. Java assertions are disabled by default in production JVMs (no `-ea` flag), so the `assert totalEnergyWeight > 0;` statement is a no-op at runtime. This is the same bug class as the reported `NativeTokenToStkXPRT`/`StkXPRTToNativeToken` issue: a share/weight-based ratio calculation that fails to defensively check for a zero denominator before dividing, and a sibling function in the same codebase (`BandwidthProcessor.calculateGlobalNetLimit`) demonstrates the correct pattern that is missing here.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` (used by TVM execution paths) computes the account's energy limit proportional to `frozeBalance / TRX_PRECISION` scaled by `totalEnergyLimit / totalEnergyWeight`: [1](#0-0) 

Note the guard is only `assert totalEnergyWeight > 0;` — no `if (totalEnergyWeight == 0) return 0;` fallback exists here at all. When `hardenResourceCalculation()` is enabled, the code takes the `BigInteger...divide(BigInteger.valueOf(totalEnergyWeight))` path, which throws `ArithmeticException: BigInteger divide by zero` unconditionally (BigInteger division always checks for zero regardless of Java assertion flags) — this exception is **not caught** anywhere in the call chain from `getAccountLeftEnergyFromFreeze` down through `VMActuator`.

Compare with the sibling function `EnergyProcessor.calculateGlobalEnergyLimit`, which has a *conditional* guard that only fires when the `allowNewReward` proposal is active: [2](#0-1) 

And the bandwidth counterpart `BandwidthProcessor.calculateGlobalNetLimit`, which — unlike both energy variants — has an **unconditional** `if (totalNetWeight == 0) return 0;` check in addition to the `allowNewReward` guard: [3](#0-2) 

This mirrors exactly the report's remediation guidance: "handle the case where the denominator is zero in the same way [a sibling function] does" — `BandwidthProcessor` already has the fix pattern; `RepositoryImpl`/`EnergyProcessor` energy-limit calculations do not consistently apply it.

`RepositoryImpl.calculateGlobalEnergyLimit` is reached from `getAccountLeftEnergyFromFreeze`, which is invoked from `VMActuator.getAccountEnergyLimitWithFixRatio`/`getAccountEnergyLimitWithFloatRatio` (energy accounting for every smart-contract call) and from `getTotalEnergyLimitWithFixRatio`/`getTotalEnergyLimitWithFloatRatio` (creator/caller energy split), all triggered by any `TriggerSmartContractContract` broadcast by an anonymous account: [4](#0-3) [5](#0-4) 

### Impact Explanation
If chain state reaches a point where `getTotalEnergyWeight()` is `0` while an account still has a non-zero frozen-for-energy balance (`frozeBalance >= TRX_PRECISION`) — a state that is plausible on freshly-initialized/private networks or during the FreezeV1→FreezeV2/`allowNewReward` migration window before the corresponding hard-fork proposal is activated — any subsequent smart-contract call touching that account's energy accounting (which happens on every `TriggerSmartContractContract` transaction) throws an uncaught `ArithmeticException`. Since this code executes inside block/transaction processing (not wrapped with a catch for `ArithmeticException` at this layer), the exception propagates and can abort transaction/block processing for all nodes executing the same transaction, producing a consensus-halting denial-of-service. Even outside the hardened path, the non-hardened `double` division silently yields `Infinity`/`NaN`, and casting that to `long` corrupts the account's energy limit (`Long.MAX_VALUE` or `0` depending on JIT/platform behavior), which is an accounting-integrity defect.

### Likelihood Explanation
The precondition (`totalEnergyWeight == 0` while some account has frozen energy balance) is a narrow chain-state condition dependent on migration/feature-flag ordering (`allowNewReward`, `supportUnfreezeDelay`) rather than something an attacker can trivially force on a fully-activated mainnet-like configuration. However, on any node/network where these proposals are not yet activated (new testnets, private chains, or during controlled feature rollout), it is directly reachable by simply calling any contract from an unprivileged, anonymous account — no special permissions required. This matches the "High" severity but state-dependent characterization of the original report.

### Recommendation
Add the same unconditional zero-check that `BandwidthProcessor.calculateGlobalNetLimit` already has to both `EnergyProcessor.calculateGlobalEnergyLimit` and `RepositoryImpl.calculateGlobalEnergyLimit`, replacing the ineffective `assert totalEnergyWeight > 0;` with an explicit `if (totalEnergyWeight <= 0) { return 0; }` guard before any division, independent of the `allowNewReward()` flag.

### Proof of Concept
1. Configure/observe a node state where `DynamicPropertiesStore.getTotalEnergyWeight()` is `0` (e.g., fresh chain before any `FreezeBalanceV2`/energy delegation activity, or a state where `allowNewReward()` is not yet enabled) while an account nonetheless has `accountCapsule.getAllFrozenBalanceForEnergy() >= TRX_PRECISION` (e.g. via a legacy V1 freeze path or a delegated-frozen-balance edge case not yet reflected in `totalEnergyWeight`).
2. Enable `allowHardenResourceCalculation` (or simply rely on the always-checked `BigInteger` divide in the hardened path).
3. Broadcast a `TriggerSmartContractContract` transaction calling any contract from that account.
4. During processing, `VMActuator.getAccountEnergyLimitWithFixRatio`/`getTotalEnergyLimitWithFixRatio` calls `rootRepository.getAccountLeftEnergyFromFreeze`/`calculateGlobalEnergyLimit` → `RepositoryImpl.calculateGlobalEnergyLimit`, which executes `BigInteger.valueOf(energyWeight).multiply(...).divide(BigInteger.valueOf(totalEnergyWeight))` with `totalEnergyWeight == 0`, throwing `ArithmeticException: / by zero`, uncaught at this layer, aborting transaction execution for the node.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
