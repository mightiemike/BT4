## Title
Missing slippage/minimum-output protection in `ExchangeInjectActuator` allows front-run "sandwich" extraction from liquidity injections - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` (adds liquidity to an existing Bancor-style TRX/TRC10 pool) computes the amount of the paired token required using the pool's *current* on-chain ratio at execution time, but — unlike `ExchangeTransactionActuator` (the swap actuator), which requires callers to supply a `tokenExpected` minimum-output bound — it provides no caller-supplied bound to protect against the ratio moving between transaction submission and execution.

### Finding Description
In `ExchangeTransactionActuator#doValidate()`, the caller supplies `tokenExpected`, and the actuator rejects the transaction if the computed output is below that bound: [1](#0-0) 

This is the java-tron analog of the `checkDeviation`-protected operations in the external report. However, `ExchangeInjectActuator#doValidate()` computes `anotherTokenQuant` purely from the pool's current `firstTokenBalance`/`secondTokenBalance` ratio and only validates that the result is `> 0` and within the global balance limit — there is no caller-supplied minimum/maximum bound on `anotherTokenQuant`: [2](#0-1) 

`ExchangeInjectActuator#execute()` then commits to whatever ratio exists in the pool at execution time: [3](#0-2) 

This is structurally identical to the reported bug class: `TalosBaseStrategy#init()` mints liquidity against the pool's current tick/price with `amount0Min`/`amount1Min` hardcoded to `0`, while sibling functions (`deposit`, `rerange`) are protected by `checkDeviation`. In java-tron, `ExchangeInjectActuator` (liquidity-add) is the sibling of `ExchangeTransactionActuator` (swap, which has `tokenExpected`) but has no equivalent minimum-output/ratio-bound field in `ExchangeInjectContract`.

`ExchangeWithdrawActuator` has a weaker, non-user-configurable check ("Not precise enough") that only bounds internal rounding error, not price movement caused by an intervening trade: [4](#0-3) 

### Impact Explanation
Because `ExchangeTransactionActuator` (the swap actuator) is callable by any unprivileged account against any exchange pool, an attacker who observes a pending `ExchangeInjectContract` in the mempool can:
1. Front-run it with an `ExchangeTransactionContract` swap that skews `firstTokenBalance`/`secondTokenBalance` unfavorably.
2. Let the victim's `ExchangeInjectContract` execute at the now-skewed ratio, causing the victim to contribute a disadvantageous mix of tokens (i.e., over-contribute the more valuable side).
3. Back-run with a reverse swap to realize the extracted value — a classic sandwich attack, with the victim absorbing the loss.

This is a genuine value-extraction path reachable purely through public, unprivileged actuators (`MarketSellAssetActuator`/exchange swap calls plus inject), not a mocked or trusted-role-only scenario — any account is allowed to submit `ExchangeTransactionContract` against any pool id.

### Likelihood Explanation
The precondition (an `ExchangeInjectContract` visible in the mempool immediately before inclusion) is the same MEV/sandwich precondition well established for AMM-style DEXs, and TRON's block-production/mempool model does not prevent transaction reordering by block producers or same-block bundling. Given how cheap swaps are (`calcFee()` for `ExchangeTransactionActuator` is `0`), the cost to an attacker executing the sandwich is low relative to potential extracted value on larger injects.

### Recommendation
Add a caller-supplied slippage bound to `ExchangeInjectContract` (e.g., `minAnotherTokenQuant`/`maxAnotherTokenQuant`) analogous to `tokenExpected` in `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator#doValidate()` before accepting the computed `anotherTokenQuant`. Consider applying the same bound-checking pattern to `ExchangeWithdrawActuator`, since its current "Not precise enough" check only guards against rounding error, not adversarial price movement.

### Proof of Concept
1. Alice (pool creator) broadcasts `ExchangeInjectContract{exchangeId, tokenId=TRX, quant=X}` intending to add liquidity at the pool's current ratio.
2. Bob (unprivileged attacker) sees Alice's pending transaction and broadcasts `ExchangeTransactionContract{exchangeId, tokenId=abc, quant=Y, expected=1}` ahead of it, shifting `firstTokenBalance`/`secondTokenBalance` (see `ExchangeTransactionActuator#execute()` mutating `exchangeCapsule` balances) — this transaction succeeds unconditionally provided `anotherTokenQuant >= expected`. [5](#0-4) 
3. Alice's `ExchangeInjectContract` then executes against the now-skewed ratio, computing `anotherTokenQuant` from the post-swap balances with no bound check on the result other than `> 0`. [6](#0-5) 
4. Bob reverses his swap after Alice's inject lands, capturing the arbitrage profit extracted from Alice's mispriced contribution.
