### Title
`TokenConfig.Enabled` is never enforced in inbound minting or outbound creation, allowing continued PRC20 minting/bridging for admin-disabled tokens - (File: x/uexecutor/keeper/handler.go)

### Summary
The Mountain Protocol USDM report describes a state flag (`blocklist`) that is meant to gate a token action but is only checked on one side (source) of the transfer, letting the other side proceed unguarded. Push Chain's `x/uregistry` registry has an analogous state flag, `TokenConfig.Enabled`, which is documented as controlling "whether this token is enabled for minting/bridging". This flag is set by the registry admin (e.g., to pause a compromised or exploited token) but is never read or enforced anywhere in the `x/uexecutor` execution paths that actually perform PRC20 minting or outbound creation.

### Finding Description
`TokenConfig.Enabled` is defined in the schema (`x/uregistry/types/types.pb.go:598-608`, `api/uregistry/v1/types.pulsar.go:5720`) with the documented purpose "Whether this token is enabled for minting/bridging". [1](#0-0) 

However, unlike `ChainConfig.Enabled` (`IsInboundEnabled`/`IsOutboundEnabled`), which is explicitly checked in `VoteInbound` [2](#0-1)  and in `BuildOutboundsFromReceipt` [3](#0-2) , `TokenConfig.Enabled` is fetched only to read `NativeRepresentation.ContractAddress` and is never inspected:

- `depositPRC20` (used by `ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload`) fetches `tokenConfig` and immediately proceeds to call `CallPRC20Deposit` (mint) without checking `tokenConfig.Enabled`. [4](#0-3) 
- `ExecuteInboundGas` fetches `tokenConfig` and proceeds to swap/deposit without an `Enabled` check. [5](#0-4) 
- `ExecuteInboundGasAndPayload` likewise fetches `tokenConfig` and mints via `gasAndPayloadDepositAutoSwap` without checking `Enabled`. [6](#0-5) 
- `BuildOutboundsFromReceipt` looks up `tokenCfg` via `GetTokenConfigByPRC20` solely to populate `ExternalAssetAddr`, again with no `Enabled` check before constructing and attaching the `OutboundTx`. [7](#0-6) 

A grep across `x/uexecutor` for any reference to `.Enabled` returns only two unrelated hits (`msg_execute_payload.go` and `msg_migrate_uea.go`, both referring to `ChainConfig.Enabled`, not `TokenConfig.Enabled`), confirming the field is dead weight from the executor's perspective.

### Impact Explanation
When a registry admin sets `TokenConfig.Enabled = false` for a token (e.g., in response to a compromised bridge, an exploited external contract, or a token that needs to be sunset), the intended effect is to stop that token from being minted/bridged onto Push Chain. Because this flag is never consulted by any inbound execution path, an ordinary unprivileged user can still submit — and honest Universal Validators will still faithfully vote and finalize — inbound events referencing the "disabled" token's `AssetAddr`, causing `depositPRC20`/`CallPRC20Deposit` to mint PRC20 tokens as if the token were still enabled. This is an unauthorized-mint condition: PRC20 supply is inflated for a token asset the protocol has explicitly marked as disabled, undermining the only admin lever meant to halt that token's bridging in an incident-response scenario. It also means outbound flows for a "disabled" token's PRC20 can still be created and drained to an external chain via `BuildOutboundsFromReceipt`.

### Likelihood Explanation
High reachability with only an ordinary, unprivileged action: the attacker does not need to control TSS, validators, or governance — they only need to trigger a genuine gateway event on the (formerly trusted, now-disabled) source-chain asset, or replay/re-observe a still-live gateway contract for that token. Universal Validators observe events truthfully per their design; the missing check lives entirely in Push Chain's own execution logic (`x/uexecutor`), so honest UVs and honest validators alone are sufficient to reproduce the issue — no privileged-actor assumption is required.

### Recommendation
Enforce `TokenConfig.Enabled` uniformly wherever a token's `NativeRepresentation` is used to mint, deposit, autoswap, or attach an outbound:
- In `depositPRC20` (`x/uexecutor/keeper/handler.go`), reject with an error (mirroring the `ChainConfig` disabled pattern) when `tokenConfig.Enabled` is `false`.
- In `ExecuteInboundGas` and `ExecuteInboundGasAndPayload`, check `tokenConfig.Enabled` before calling any deposit/auto-swap helper.
- In `BuildOutboundsFromReceipt`, check `tokenCfg.Enabled` before constructing the `OutboundTx`, alongside the existing `IsChainOutboundEnabled` check.
- Ensure the resulting UTX records a `FAILED` PCTx / revert path consistent with how a missing token config is already handled, so a disabled token behaves the same as one that doesn't exist in the registry.

### Proof of Concept
1. Registry admin adds `TokenConfig{Chain: "eip155:11155111", Address: usdcAddress, Enabled: true, NativeRepresentation: {ContractAddress: prc20USDC}}` and a corresponding enabled `ChainConfig`.
2. A user deposits funds via the source-chain gateway; Universal Validators observe and vote `MsgVoteInbound` honestly; quorum reached; PRC20 is minted to the recipient (as tested in `test/integration/uexecutor/*` inbound flows).
3. Registry admin later calls `MsgUpdateTokenConfig` to set `Enabled: false` for the same `Chain`/`Address`, intending to halt further bridging of this token (e.g., because the source-chain contract was exploited).
4. A user submits another gateway event for the same (now-disabled) `AssetAddr`; UVs observe and vote `MsgVoteInbound` honestly and quorum is reached again.
5. `ExecuteInboundFunds`/`ExecuteInboundGasAndPayload` calls `depositPRC20` → `GetTokenConfig` succeeds (the entry still exists, just disabled) → `CallPRC20Deposit` mints the PRC20 exactly as before, because `tokenConfig.Enabled` is never read. Confirm via `chainApp.EVMKeeper.CallEVM(..., "balanceOf", ...)` that the recipient's PRC20 balance increases despite the token being disabled — no test in the existing suite (`chain_enabled_test.go`, `execute_inbound_gas_test.go`, etc.) covers or blocks this case, since those tests only exercise `ChainConfig.Enabled`, not `TokenConfig.Enabled`.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
