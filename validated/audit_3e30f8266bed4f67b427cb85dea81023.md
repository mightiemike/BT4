### Title
Deterministic accounts can reference a mutable `GlobalContractIdentifier::AccountId`, breaking the "fixed code" invariant and enabling silent code takeover of every account referencing it - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
NEAR's "deterministic accounts" (NEP-616) are documented and designed as accounts whose behavior is fully and permanently pinned by their `DeterministicAccountStateInit` (code + data) — the account ID itself is a hash of that state. However, the `code` field of that state can be a `GlobalContractIdentifier::AccountId`, i.e. a *mutable* reference to a global contract that its owner may redeploy at any time. Any number of deterministic accounts that reference the same owner account's global contract share that single, owner-controlled, mutable code path. If the code-owning account is compromised, malicious, or simply upgrades its global contract, every deterministic account pointing at it — via `AccountContract::GlobalByAccount` — silently starts executing different code, without any action from the affected account holders. This is structurally the same "shared, mutable backing resource serving many independent unprivileged principals" flaw as the SwapFacility/BitcornOFT report: the safety of many downstream holders becomes only as strong as the single weakest/most-trusted upstream resource, contradicting the advertised guarantee ("fixed code").

### Finding Description
- `AccountContract::GlobalByAccount(AccountId)` is described as allowing "the owner to update the contract for all its users" [1](#0-0)  and the same wording appears in the on-chain OpenAPI schema [2](#0-1) .
- `DeterministicAccountStateInitV1.code` is typed as `GlobalContractIdentifier`, which can be either `CodeHash` (immutable) or `AccountId` (mutable) [3](#0-2) .
- Documentation for deterministic accounts explicitly promises immutability: "Deterministic accounts have a fixed code and fixed initial state associated with it" and "The account ID is derived from a `DeterministicAccountStateInit` instance," implying the code referenced is permanently bound to that ID [4](#0-3) .
- The runtime path that deploys a deterministic account's contract, `deploy_deterministic_account`, simply calls `use_global_contract` with whatever `GlobalContractIdentifier` was supplied in the state-init, with no restriction that it must be `CodeHash` (immutable) rather than `AccountId` (mutable) [5](#0-4) .
- `use_global_contract` resolves the account's `AccountContract` to `AccountContract::GlobalByAccount(id)` when an `AccountId`-mode identifier is used, and never snapshots or pins the code at that point — it only stores a pointer to "whatever code is currently registered under `id`" [6](#0-5) .
- The actual code lookup happens at call-time by the current contents of the `TrieKey::GlobalContractCode` for that identifier, which is *replaced in place* whenever the owning account calls `DeployGlobalContractAction` again with `AccountId` mode [7](#0-6) , and the propagation mechanism (`GlobalContractDistributionReceipt` / `initiate_distribution`) applies this new code across shards without any deterministic-account-specific gating [8](#0-7) .
- Nothing in `action_validation.rs`'s deterministic-state-init validation (`validate_deterministic_state_init`) restricts `code` to `CodeHash`; the only check performed is that the receiver ID matches the state-init hash, and the test suite explicitly exercises `GlobalContractIdentifier::AccountId(...)` as valid `code` for deterministic accounts [9](#0-8) , and production test-loop code deliberately builds deterministic accounts on top of `GlobalContractIdentifier::AccountId` [10](#0-9) .

This means: any user can be lured/instructed to create (or fund) a deterministic account whose `code` is `GlobalContractIdentifier::AccountId(owner)`. Many independent, unrelated users may end up depending on the exact same `owner` global-contract deployment (analogous to many `BitcornOFT` holders depending on the same shared collateral vault). If `owner`'s key is later compromised, or `owner` is a service that turns malicious/rug-pulls, or `owner`'s account is taken over via any other unrelated vulnerability, they can redeploy the global contract to arbitrary code (e.g. code that transfers out `account_balance()` to an attacker-controlled account whenever called), and **every** deterministic account across every shard that referenced `AccountId(owner)` is compromised simultaneously and non-consensually — despite each such account's ID cryptographically attesting (via the deterministic-ID hash) to a specific, believed-immutable `state_init`.

### Impact Explanation
This directly maps to "concrete unauthorized value movement" and "permanently frozen funds": a single compromised/malicious global-contract owner account can rewrite the executable logic of every deterministic account that referenced it via `AccountId` mode, and drain their balances via ordinary `FunctionCall`/`Transfer` promises issued from the new, attacker-controlled code — with the victims having no way to detect this from the account ID alone (the very thing the "deterministic account" feature promises to make verifiable/immutable). Balances held by any of these zero/low-balance deterministic accounts (a design goal of NEP-616/NEP-448) or contract-storage-fund flows through the changed code are unauthorized value movements attributable to a change nobody with a stake in those specific deterministic accounts authorized.

### Likelihood Explanation
Reachable entirely through unprivileged, ordinary transactions: `DeployGlobalContractAction` (AccountId mode) to publish/update code, `DeterministicStateInitAction` referencing that `AccountId` identifier to spin up dependent accounts, and later another `DeployGlobalContractAction` from the same owner to swap the code. No validator/node compromise, no privileged role, and no protocol bug is needed beyond the fact that the protocol permits (and even documents/test-covers) using a mutable identifier for something advertised as immutable. The likelihood of exploitation scales with adoption of `GlobalByAccount`-referenced deterministic accounts (e.g. wallet/factory patterns that use a shared owner account for code distribution) and with the compromise/incentive risk of that owner account, exactly mirroring the "operators must be highly vigilant about collateral quality" caveat in the original report.

### Recommendation
Either:
1. Disallow `GlobalContractIdentifier::AccountId` as the `code` in `DeterministicAccountStateInitV1`, restricting deterministic-account code to `CodeHash` only, so the documented "fixed code" guarantee actually holds; or
2. If `AccountId` mode must remain supported for deterministic accounts, update documentation to explicitly state that such accounts are *not* immutable and their behavior can change if the referenced owner account redeploys, and consider snapshotting/pinning the resolved code hash at `DeterministicStateInitAction` time (converting to an internal `CodeHash` reference) so future owner redeployments cannot retroactively affect already-created deterministic accounts.

### Proof of Concept
1. Owner account `alice.near` deploys a global contract in `AccountId` mode containing benign logic (`DeployGlobalContractAction{ deploy_mode: AccountId }`), as shown in the test helper flow [11](#0-10) .
2. Any unprivileged user submits `DeterministicStateInitAction` with `state_init.code = GlobalContractIdentifier::AccountId("alice.near")` and some `data`, deriving the receiver via `derive_near_deterministic_account_id`, exactly as done in `check_deterministic_state_init` [11](#0-10) . This creates account `0s...` whose `AccountContract` is `GlobalByAccount("alice.near")` via `use_global_contract` [12](#0-11) . Repeat for many users/accounts, all pointing at `alice.near`.
3. Users fund/use these deterministic accounts normally (transfers, function calls), trusting that "deterministic" implies fixed behavior.
4. `alice.near` (compromised or malicious) submits another `DeployGlobalContractAction{ deploy_mode: AccountId }` with attacker-chosen WASM that, e.g., on any call transfers the caller account's full balance to an attacker account.
5. Because every deterministic account created in step 2 resolves its code by the `AccountId` pointer at call time (not a pinned hash), the next function call/promise executed against any of them runs the attacker's new code, enabling unauthorized transfers out of all of them — with no action or consent from those account's "actor" (the original predecessor who created them, per `create_deterministic_account`'s actor-preserving design [13](#0-12) ).

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
