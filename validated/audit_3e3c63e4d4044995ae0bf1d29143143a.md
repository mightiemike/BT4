## Analysis

The Beedle bug class is: a security‑critical, monotonically‑increasing state field that gates a validation is silently reset to a "safe/default" value by a self‑triggered action that reuses the same identifier, thereby defeating the invariant the field exists to enforce. The closest reachable nearcore analog is the **access‑key nonce reset on `DeleteKey` + `AddKey` self-reuse**, which defeats the nonce‑monotonicity invariant that prevents transaction replay.

`AccessKey::nonce` is documented to be a monotonically increasing replay guard: `verify_nonce` rejects any transaction whose nonce is not strictly greater than (Monotonic) or not the exact successor of (Strict) the access key's stored nonce. [1](#0-0) 

The design explicitly anticipates the case where an access key is deleted and recreated with the *same* public key, and states that the nonce **must** be preserved to prevent replaying old transactions: [2](#0-1) 

However, `action_add_key` → `add_regular_key` does not preserve any prior nonce for the reused public key. It unconditionally seeds the new key's nonce from the current block height: [3](#0-2) [4](#0-3) 

`initial_nonce_value(h) = (h-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (1e6), while the nonce upper bound enforced elsewhere allows any nonce up to `h * ACCESS_KEY_NONCE_RANGE_MULTIPLIER - 1` to be chosen by the signer. So a key holder who has already consumed a high nonce (close to the upper bound) can, in the very same transaction batch, submit `[DeleteKey(pk), AddKey(pk, ...)]`: `DeleteKey` removes the access key row, then `AddKey` re-creates it with the same public key and a nonce reset to `(h-1)*1e6` — up to ~1e6 lower than the nonce that was just consumed. Because actions within one receipt execute sequentially against the live trie state, there is no `AddKeyAlreadyExists` conflict. [5](#0-4) 

This directly breaks the documented invariant: "Nonce monotonicity prevents replay" — `verify_nonce` rejects stale/equal nonces, and that guarantee depends on the stored nonce never decreasing for a given key. [6](#0-5) 

Because the same public key/private key pair is retained, any previously signed (and often already-broadcast, publicly visible on-chain) `SignedTransaction` whose nonce falls in the reopened window `[(h-1)*1e6, old_current_nonce)` becomes valid again — its signature still verifies, and the nonce check now passes against the lowered floor. This allows replay/double-execution of a prior action (e.g., a `Transfer`, `Stake`, or `FunctionCall`) that had already been applied once, i.e., unauthorized re-execution of a previously finalized transaction.

### Title
Access-key nonce reset via DeleteKey+AddKey self-reuse defeats nonce-monotonicity, enabling transaction replay - (`runtime/runtime/src/access_keys.rs`)

### Summary
`add_regular_key` unconditionally reseeds a newly (re-)added access key's nonce from `initial_nonce_value(block_height)` instead of preserving the previous nonce when the same public key is reused, contradicting the documented invariant and reopening a nonce window that was already consumed, in a way directly analogous to the Beedle `auctionStartTimestamp` self-reset bug.

### Finding Description
`verify_nonce` in `runtime/runtime/src/verifier.rs` enforces that a submitted transaction's nonce must be strictly greater than (Monotonic mode) the access key's currently stored nonce, which is the sole mechanism preventing replay of previously-signed transactions. The `AccessKey` documentation states that when an access key is recreated with the same public key, its nonce "should be equal to the nonce of the old access key… required to avoid replaying old transactions again." The implementation of `add_regular_key` in `runtime/runtime/src/access_keys.rs` does not honor this: it always sets `access_key.nonce = initial_nonce_value(block_height)`, i.e. `(block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, regardless of what nonce was previously consumed for that key.

Because `action_delete_key` and `action_add_key` are ordinary actions processed sequentially against live trie state within one receipt, an account holder (or a relayer/meta-tx sender acting on the account's behalf with a full-access key) can submit a single transaction containing `[DeleteKey(pk), AddKey(pk, same_permission)]`. `DeleteKey` removes the existing access key row (whose nonce reflects all transactions consumed so far, potentially near the per-height upper bound of `height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`), and the immediately following `AddKey` recreates the identical key with the nonce rolled back to `(height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`. This is exactly the Beedle pattern: a self-triggered call re-using the same identifier resets a monotonic guard field back to a "reset" baseline, defeating the very check (`RateTooHigh`/nonce-too-low) it exists to enforce.

### Impact Explanation
Any previously signed `SignedTransaction` (transfer, stake, function call, etc.) whose nonce falls inside the reopened window `[(height-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER, old_stored_nonce)` becomes valid again, because the signature still verifies (same keypair) and `verify_nonce` now compares against the lowered floor. Since past transactions and their raw bytes are visible on-chain, this permits replaying/re-executing an already-finalized state transition (e.g., a `Transfer` or `Stake` action firing a second time), i.e., unauthorized duplicate value movement, without any additional signature from the account owner beyond the one DeleteKey/AddKey transaction that triggers the reset.

### Likelihood Explanation
The primitive requires only a full-access key and a single self-submitted transaction batching `DeleteKey` followed by `AddKey` with the identical public key — an operation nowhere rejected by `validate_actions` or `action_add_key`'s `AddKeyAlreadyExists` check (since the key is removed before being re-added within the same receipt). No validator collusion, network-level attack, or privileged role is required; it is reachable from an ordinary unprivileged transaction signer.

### Recommendation
When `add_regular_key`/`action_add_key` re-adds a key for a public key that previously existed on the account within the same logical operation (or generally), preserve the maximum of the old nonce and the newly computed `initial_nonce_value(block_height)` rather than unconditionally overwriting it, consistent with the documented invariant in `docs/DataStructures/AccessKey.md`. Alternatively, disallow `AddKey` from resetting the nonce below any previously-recorded value for that `(account_id, public_key)` pair by tracking a persisted "last nonce ever used" floor independent of key deletion.

### Proof of Concept
1. Account `A` has full-access key `K` (public key `pk`) with stored nonce `N` close to the per-height upper bound (e.g., achieved by signing and submitting a transaction with a large monotonic nonce, permitted since `NonceMode::Monotonic` only requires `tx_nonce > current_nonce` and `tx_nonce < height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`).
2. `A` retains an old, already-executed `SignedTransaction` `T_old` (nonce `n_old`, where `(height-1)*1e6 <= n_old < N`) signed with `pk` — e.g., a `Transfer` transaction that already ran once.
3. `A` submits a new transaction at height `h` containing actions `[DeleteKey(pk), AddKey(pk, FullAccess)]`, signed with `pk` and nonce `> N` (passes `verify_nonce`).
4. `action_delete_key` removes the access key row for `pk`; `action_add_key` → `add_regular_key` recreates it with `nonce = initial_nonce_value(h) = (h-1)*1e6`, which is `<= n_old`.
5. Resubmit `T_old` (raw signed bytes unchanged). Signature verification succeeds (same `pk`); `verify_nonce` now sees `n_old > (h-1)*1e6 =` current stored nonce, so the transaction is accepted and its actions execute a second time — demonstrating replay of an already-finalized transaction.

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {
        add_gas_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;
    } else {
        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}
