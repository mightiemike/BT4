This confirms the equality is correctly enforced end-to-end: `validate_normal_nakamoto_block_burnchain` (nakamoto/mod.rs:2739-2817) fetches the `leader_key` bound to the winning block-commit's `key_block_ptr`/`key_vtxindex` via `db_handle.get_leader_key_at(...)` [1](#0-0)  and passes `leader_key.public_key` into `validate_normal_against_burnchain`, which calls `check_normal_coinbase_tx(vrf_public_key, &tenure_burn_chain_tip.sortition_hash)` [2](#0-1) . `check_normal_coinbase_tx` performs `VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes())` and returns `Err("Invalid Nakamoto block: leader VRF key did not produce a valid proof")` when it fails [3](#0-2) . On error, `validate_normal_nakamoto_block_burnchain` propagates the error immediately and never proceeds to insert/accept the block [4](#0-3) .

There's an existing regression test proving this exact scenario: a coinbase VRF proof correctly generated with `vrf_pubkey`/`sortition_hash` returns `Ok`, but the same header checked against an alternate, mismatched VRF public key (`vrf_alt_pubkey`) returns `Err`, and checking with a mismatched sortition hash also returns `Err` [5](#0-4) . This is deterministic (`VRF::verify` uses only public data — `Y_point`, `proof`, `alpha` — and constant-time scalar comparison) [6](#0-5) , so both node A and node B reject identically; there is no divergence and no path to "verify correctly rejects but downstream code still finalizes the sortition as won" — rejection of the block happens before any sortition/reward-set finalization step in this call chain.

Regarding the "frozen reward" branch of the question: even if a miner's coinbase carries a mismatched VRF proof, the *block* is rejected, not the *sortition*. The block-commit still won the sortition on the burnchain (that's a Bitcoin-layer fact, independent of the Stacks block's validity), and the miner simply fails to produce a valid tenure-start block; nothing in this code path "orphans" or "freezes" the sortition's winning status — it only prevents an invalid Stacks block from being accepted. The reward/burn-distribution bookkeeping is computed from the burnchain block-commits/sortition tally, not from `check_normal_coinbase_tx`, so this validation failure has no effect on that accounting.

    pub fn verify(Y_point: &VRFPublicKey, proof: &VRFProof, alpha: &[u8]) -> Result<bool, Error> {
        let H_point = VRF::hash_to_curve(Y_point, alpha);
        let s_reduced = proof.s();
        let Y_point_ed = CompressedEdwardsY(Y_point.to_bytes())
            .decompress()
            .ok_or(Error::InvalidPublicKey)?;
        if proof.Gamma().is_small_order() {
            return Err(Error::InvalidPublicKey);
        }

        let U_point = s_reduced * &ED25519_BASEPOINT_POINT - proof.c() * Y_point_ed;
        let V_point = s_reduced * &H_point - proof.c() * proof.Gamma();

        let c_prime_hashbuf = VRF::hash_points(&H_point, proof.Gamma(), &U_point, &V_point);
        let Some(c_prime) = VRF::ed25519_scalar_from_hash128(&c_prime_hashbuf) else {
            return Err(Error::InvalidHashPoints);
        };

        // NOTE: this leverages constant-time comparison inherited from the Scalar impl
        Ok(c_prime == *(proof.c()))
    }
