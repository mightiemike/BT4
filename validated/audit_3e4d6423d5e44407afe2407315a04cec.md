### Title
`replay_on_archive` never validates the state-checkpoint (JMT root) hash, so it silently accepts diverging world-state during replay verification - (File: `types/src/transaction/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole comparator used by `db-tool`'s replay-verify utility (`replay_on_archive.rs`) to confirm that a freshly re-executed transaction matches the `TransactionInfo` that was actually committed to the archived ledger. The function checks status, gas used, write-set hash, and event-root hash, but never reads or compares `TransactionInfo::state_checkpoint_hash()` — the field that carries the authoritative Sparse-Merkle/Jellyfish-Merkle world-state root for that version. As a result, replay-verify can report "PASS" for a chunk whose freshly computed state root diverges from the one actually committed on-chain, defeating the tool's purpose of catching state-divergence (including hard-fork-class) bugs.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) . It validates `status`, `gas_used`, `write_set_hash` against `state_change_hash`, and `event_root_hash`, and explicitly documents the gap: [2](#0-1) 

This comment states the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)", but the code shows that even the base `state_checkpoint_hash` — present on `TransactionInfoV0` since genesis, not just the new trading-native fields — is never read inside the function. The accessor `TransactionInfo::state_checkpoint_hash()` [3](#0-2)  is defined and documented as "The root hash of the Sparse Merkle Tree describing the world state at the end of this transaction" [4](#0-3) , yet it is not part of the match-check.

This comparator is used by `db-tool`'s archive replay-verify flow: `Verifier::execute_and_verify` re-executes historical transactions and calls `ensure_match_transaction_info` per transaction against the `expected_txn_infos` pulled from the archive DB, treating a passing check as proof of a correct replay: [5](#0-4) . Because `state_checkpoint_hash` is never compared, a transaction that produces the correct events/write-set/status/gas but a different underlying JMT root (e.g., due to a state-tree construction bug, a hidden extra/missing state write not reflected in the same-transaction write set, or non-determinism in state materialization) will pass verification undetected.

### Impact Explanation
Replay-verify against archived data is one of the primary mechanisms used to detect state-commitment divergence — precisely the "hard-fork-only divergence during commit/replay" category called out as in-scope. Since the tool never checks the one field that actually attests to the global state root, a real state-corrupting bug in the VM/executor could ship and diverge from the canonical ledger, while this tool — whose job is exactly to catch such divergence — reports success. This directly weakens the state-integrity safety net for mainnet history.

### Likelihood Explanation
This is not a hypothetical: the code path is unconditionally reached on every invocation of `replay_on_archive`, and the gap is confirmed by the author's own TODO comment acknowledging that checkpoint hashes are skipped. No adversarial input is required — the omission means any silent state-root divergence (from any cause) up to and including hard-fork-class VM bugs would go unflagged whenever this tool is relied upon for verification.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`-derived/expected `state_checkpoint_hash` (and, once enabled, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against the `TransactionInfo` under verification whenever the checkpoint hash is present (i.e., at the end of a block/state-checkpoint boundary), and update `replay_on_archive.rs`'s `execute_and_verify` to supply/compute the actual state root at each checkpoint boundary so it can be validated rather than skipped.

### Proof of Concept
1. Run `db-tool replay-on-archive` against a target archive DB range containing a block boundary transaction (one with `Some(state_checkpoint_hash)`).
2. Construct/emulate a replay in which the VM produces identical `status`, `gas_used`, `write_set` (hence identical `state_change_hash`), and `events` (hence identical `event_root_hash`) as the archived `TransactionInfo`, but where the resulting global state tree root (as would be recorded in `state_checkpoint_hash`) differs (e.g., inject a state key/value that gets applied to the SMT/JMT outside of the per-txn write set materialization, or exploit any non-determinism in state-tree assembly).
3. Observe that `ensure_match_transaction_info` at [1](#0-0)  returns `Ok(())` and `execute_and_verify` in `replay_on_archive.rs` reports no error for this chunk, even though the actual world-state root diverges from the canonical ledger.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
