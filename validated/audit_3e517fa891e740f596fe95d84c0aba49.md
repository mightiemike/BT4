## Finding: Version-5 metadata clearing is asymmetric between publish-time validation and API/runtime metadata reads

### Summary
`get_metadata_from_compiled_code` in `types/src/vm/module_metadata.rs` clears `struct_attributes`/`fun_attributes` only when `code.version() == 5`, and this cleared value is what `verify_module_metadata_for_module_publishing` uses to validate resource-group attributes at publish time. [1](#0-0)  However, the API-facing path (`MoveConverter::is_resource_group` and, transitively, `find_resource`) reads module metadata through the separate `get_metadata` function, which performs **no** such version-based clearing. [2](#0-1) [3](#0-2) 

### Finding Description
- `verify_module_metadata_for_module_publishing` obtains the metadata via `get_metadata_from_compiled_code(module)` and then iterates `metadata.fun_attributes`/`metadata.struct_attributes` to validate each `ResourceGroup`/`ResourceGroupMember`/view-function/event attribute (`is_valid_resource_group`, `is_valid_resource_group_member`, etc.). [4](#0-3) 
- If an unprivileged publisher targets a module whose serialized bytecode reports `code.version() == 5`, the returned `RuntimeModuleMetadataV1` has its `struct_attributes`/`fun_attributes` maps forcibly cleared before the validation loops run, so the `for` loops over those maps iterate zero times and the function trivially returns `Ok(())` — regardless of what attributes were actually declared (e.g., a `ResourceGroupMember` attribute pointing at an arbitrary container `StructTag`, attached to a struct lacking the `key` ability, which `is_valid_resource_group_member` would normally reject). [5](#0-4) [6](#0-5) 
- The comment on the clearing logic itself acknowledges this is a workaround ("shouldn't have existed in the first place... should have been gated in the verify module metadata"), i.e. it is documented as a known gap rather than intentional hardening. [7](#0-6) 
- Critically, the clearing only mutates the *in-memory* struct returned to the validator — it does not rewrite the bytes actually persisted on-chain. Any later reader that calls `get_metadata` (not `get_metadata_from_compiled_code`) against the same module will get back the full, unvalidated `struct_attributes`, including the bogus `ResourceGroupMember` annotation. [8](#0-7) 
- `api/types/src/convert.rs`'s `is_resource_group` and `find_resource` (via `AptosValueAnnotator`) are exactly such readers: they resolve whether a `StructTag` is a resource-group member from the module's metadata to decide whether to look up `StateKey::resource_group(&address, &group_tag)` (BCS map lookup) versus the plain `StateKey::resource(&address, tag)`. [9](#0-8) 

### Impact Explanation
For a v5-format module, publish-time validation of `ResourceGroup`/`ResourceGroupMember` attributes is a no-op, so an attacker-controlled struct can carry an attribute claiming membership in an arbitrary resource-group container that would otherwise be rejected (e.g., wrong scope, struct without `key` ability, nonexistent container tag). Any consumer that later trusts `get_metadata` (uncleared) to decide storage/lookup semantics — including the REST API's `find_resource`/`is_resource_group` — will act on that unvalidated attribute, potentially computing the wrong `StateKey` for a given `(address, tag)` pair and returning `None` or bytes extracted from an unrelated container blob, which is a misbinding of an authenticated API response to the wrong ledger object/state key.

### Likelihood Explanation
This requires an attacker to be able to publish a package whose emitted file-format version is exactly 5 while still attaching the V1 metadata section (`APTOS_METADATA_KEY_V1`) — normally the compiler only emits V1 metadata for file-format version ≥ `METADATA_V1_MIN_FILE_FORMAT_VERSION` (6), per the constant defined right above this logic. [10](#0-9)  So exploitation depends on being able to craft a module (not necessarily through the standard compiler) that reports `version() == 5` yet still carries the V1 metadata key — I was not able to confirm within the available tool budget whether the bytecode verifier or module-publishing pipeline rejects such a combination earlier (e.g., in `check_metadata_format` or the deserializer's version gating), nor whether the actual VM runtime write path for resource-group placement (`aptos-vm-types/src/resolver.rs`, `aptos-move/block-executor/src/view.rs`) consults `get_metadata` or `get_metadata_from_compiled_code`. That link is necessary to determine whether write-time placement and API read-time lookup can actually diverge (full state-integrity impact) versus this being confined to a publish-time validation bypass with the runtime/API layers still self-consistently using the uncleared metadata.

### Recommendation
- Make the clearing behavior in `get_metadata_from_compiled_code` consistent across all call sites (including `get_metadata`, which powers `api/types/src/convert.rs`), so a v5 module's `struct_attributes`/`fun_attributes` are treated as empty (or rejected outright) everywhere, not just at publish-time validation.
- Alternatively, reject modules that declare V1 metadata (`APTOS_METADATA_KEY_V1`) together with `code.version() == 5` outright in `check_metadata_format`/publish verification instead of silently clearing it for validation only.
- Verify and align the runtime resource-group placement code path (`resolver.rs`/`view.rs`/`get_resource_group_member`) with whichever metadata function is authoritative, to guarantee write-time and read-time (API) never diverge on which `StateKey` a given `(address, StructTag)` resolves to.

### Proof of Concept
Conceptual repro (not fully executed due to tool constraints):
1. Construct/publish a module whose serialized `CompiledModule` reports `version() == 5` (via `CompiledCodeMetadata`) but includes an `APTOS_METADATA_KEY_V1` metadata entry declaring a struct with `KnownAttribute::resource_group_member("0x1::some::Container")`, where the struct does **not** have the `key` ability (which `is_valid_resource_group_member` would normally reject).
2. Publish this package as an unprivileged account; observe that `verify_module_metadata_for_module_publishing` accepts it because the metadata seen by validation is cleared to empty for `version() == 5`.
3. Publish a resource of that struct type to the account (stored under whatever key the VM's actual runtime logic computes).
4. Call the REST API's resource endpoint / `find_resource(state_view, address, tag)` for that struct tag; because `is_resource_group`/`find_resource` reads via the uncleared `get_metadata`, it treats the struct as a resource-group member and looks up `StateKey::resource_group(&address, &group_tag)` instead of the actual key used by the VM, returning `None` or an unrelated container's bytes for the queried `(address, tag)`.

I could not confirm within this investigation which `StateKey` the actual VM write path uses for such a v5 module (this needs direct inspection of `aptos-vm-types/src/resolver.rs::get_resource_group_member` and `block-executor/src/view.rs`), so step 3–4's divergence is asserted based on the code paths found but not independently confirmed against the runtime placement logic.

pub fn get_metadata_from_compiled_code(
    code: &impl CompiledCodeMetadata,
) -> Option<RuntimeModuleMetadataV1> {
    if let Some(data) = find_metadata(code.metadata(), APTOS_METADATA_KEY_V1) {
        let mut metadata = bcs::from_bytes::<RuntimeModuleMetadataV1>(&data.value).ok();
        // Clear out metadata for v5, since it shouldn't have existed in the first place and isn't
        // being used. Note, this should have been gated in the verify module metadata.
        if code.version() == 5 {
            if let Some(metadata) = metadata.as_mut() {
                metadata.struct_attributes.clear();
                metadata.fun_attributes.clear();
            }
        }
        metadata
    } else if let Some(data) = find_metadata(code.metadata(), APTOS_METADATA_KEY) {
        // Old format available, upgrade to new one on the fly
        let data_v0 = bcs::from_bytes::<RuntimeModuleMetadata>(&data.value).ok()?;
        Some(data_v0.upgrade())
    } else {
        None
    }
}

pub fn verify_module_metadata_for_module_publishing(
    module: &CompiledModule,
    features: &Features,
) -> Result<(), MetaDataValidationError> {
    if features.is_enabled(FeatureFlag::SAFER_METADATA) {
        check_module_complexity(module)?;
    }

    if features.are_resource_groups_enabled() {
        check_metadata_format(module)?;
    }
    let metadata = if let Some(metadata) = get_metadata_from_compiled_code(module) {
        metadata
    } else {
        return Ok(());
    };

    let functions = module
        .function_defs
        .iter()
        .map(|func_def| {
            let func_handle = module.function_handle_at(func_def.function);
            let name = module.identifier_at(func_handle.name);
            (name, (func_handle, func_def))
        })
        .collect::<BTreeMap<_, _>>();

    for (fun, attrs) in &metadata.fun_attributes {
        for attr in attrs {
            if attr.is_view_function() {
                is_valid_view_function(module, &functions, fun)?;
            } else if attr.is_randomness() {
                is_valid_unbiasable_function(&functions, fun)?;
            } else {
                return Err(AttributeValidationError {
                    key: fun.clone(),
                    attribute: attr.kind,
                }
                .into());
            }
        }
    }

    let structs = module
        .struct_defs
        .iter()
        .map(|struct_def| {
            let struct_handle = module.struct_handle_at(struct_def.struct_handle);
            let name = module.identifier_at(struct_handle.name);
            (name, (struct_handle, struct_def))
        })
        .collect::<BTreeMap<_, _>>();

    for (struct_, attrs) in &metadata.struct_attributes {
        for attr in attrs {
            if features.are_resource_groups_enabled() {
                if attr.is_resource_group() && attr.get_resource_group().is_some() {
                    is_valid_resource_group(&structs, struct_)?;
                    continue;
                } else if attr.is_resource_group_member()
                    && attr.get_resource_group_member().is_some()
                {
                    is_valid_resource_group_member(&structs, struct_)?;
                    continue;
                }
            }
            if features.is_module_event_enabled() && attr.is_event() {
                continue;
            }
            return Err(AttributeValidationError {
                key: struct_.clone(),
                attribute: attr.kind,
            }
            .into());
        }
    }
    Ok(())
