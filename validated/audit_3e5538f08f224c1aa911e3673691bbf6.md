### Title
`getAssetIssuesPaginated` performs full-store iteration and full sort regardless of `limit`, making "paginated" asset-issue queries as expensive as full listing - ([File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java])

### Summary
`AssetIssueStore.getAssetIssuesPaginated(long offset, long limit)` internally calls `getAllAssetIssues()` (full `iterator()` scan of the entire asset-issue store) and then sorts the *entire* resulting list before slicing out `[offset, offset+limit)`. `AssetIssueV2Store` extends `AssetIssueStore` without overriding this method, so it inherits the identical unbounded behavior. The public HTTP/gRPC "paginated" endpoints therefore do full O(N) iteration + O(N log N) sort work no matter how small `limit` is.

### Finding Description
The reachable path is:
`GetPaginatedAssetIssueListServlet.doGet/doPost` → `Wallet.getAssetIssueList(offset, limit)` → `AssetIssueStore.getAssetIssuesPaginated(offset, limit)`: [1](#0-0) [2](#0-1) 

The store implementation: [3](#0-2) 

`getAssetIssuesPaginated(offset, limit)` calls the private overload with `getAllAssetIssues()` — a full stream over `iterator()` of the entire `asset-issue` (or `asset-issue-v2`) column family — collected into a `List`, then unconditionally sorts that whole list by name/order, and only *afterward* slices `[offset, min(offset+limit, size))` via `subList`. There is no early-exit, no streaming top-K selection, and no bound on the initial iteration — the `limit` argument is only applied at the very end, after all O(N) work (iteration + `List` materialization) and O(N log N) work (sort) have already been paid. This is identical in asymptotic cost to `Wallet.getAssetIssueList()` (the unpaginated endpoint), which also calls `getAllAssetIssues()` and iterates the full list: [4](#0-3) 

`AssetIssueV2Store` inherits this method verbatim with no override: [5](#0-4) 

The only guard on the servlet is `RateLimiterServlet`, which applies QPS-style (request-count) rate limiting per endpoint/IP, not cost- or size-aware throttling: [6](#0-5) 

This limiter treats a `limit=1` paginated request identically to a `limit=100000` request in terms of permitted request rate, since the acquired "permit" is not scaled by the actual O(N) work the backend will do. There is no fee, no accounting, and no auth requirement on this endpoint — it is a plain public read-only HTTP/gRPC call.

### Impact Explanation
An unprivileged attacker who repeatedly calls `/wallet/getpaginatedassetissuelist` (or the gRPC `getPaginatedAssetIssueList`) with `offset=0&limit=1` forces the node to iterate and sort the entire `asset-issue` (or `-v2`) store on every single call, identical cost to the unpaginated `getassetissuelist` endpoint. Because the per-request rate limiter is QPS-based and not proportional to `limit`, an attacker can issue many "cheap-looking" `limit=1` requests at the same rate as legitimate small requests while incurring full-list CPU/memory cost each time, amplifying resource consumption per allowed request far beyond what the rate limiter is designed to bound. This is a resource-exhaustion / denial-of-service amplification issue against a public read API, not a value-theft or consensus issue.

### Likelihood Explanation
No privileged access, signed transaction, or special setup is required — this is a plain HTTP GET/POST or gRPC call available to any external caller. The only precondition is that the asset-issue store contains a non-trivial number of entries (which happens naturally as more `AssetIssueContract`s are created on a live/public chain over time, since asset issuance itself is an unprivileged operation any account can perform, further allowing the attacker to also grow N). The behavior is fully deterministic and repeatable on every call, requiring no race condition or timing dependency.

### Recommendation
Rework `AssetIssueStore.getAssetIssuesPaginated` to avoid full materialization/sort scaled to `limit`:
- Maintain the asset list already sorted (e.g., an ordered index/secondary key by name+order) instead of sorting on every read, so retrieval can seek directly to `offset` and read only `limit` entries.
- If a full in-memory sort is unavoidable given current storage design, at minimum use a partial/selection sort (e.g., a bounded heap of size `offset+limit`) instead of `Collections.sort` on the entire list, and enforce `ASSET_ISSUE_COUNT_LIMIT_MAX` before any iteration begins where possible.
- Consider scaling `RateLimiterServlet` permits (or adding a distinct limiter) for these list-style endpoints based on estimated backend cost (e.g., current store size) rather than treating every call as equally cheap.

```java
@Test
public void paginatedLimit1CostsSameAsFullList() {
  // Populate AssetIssueStore with N (e.g., 100_000) AssetIssueCapsule entries.
  populateAssetIssueStore(assetIssueStore, 100_000);

  long t0 = System.nanoTime();
  List<AssetIssueCapsule> full = assetIssueStore.getAllAssetIssues();
  long fullCost = System.nanoTime() - t0;

  long t1 = System.nanoTime();
  List<AssetIssueCapsule> paginated = assetIssueStore.getAssetIssuesPaginated(0, 1);
  long paginatedCost = System.nanoTime() - t1;

  assertEquals(1, paginated.size());
  // Assert paginated(0,1) cost is NOT significantly cheaper than full scan+sort,
  // proving pagination provides no early-exit/streaming optimization.
  double ratio = (double) paginatedCost / fullCost;
  assertTrue("Expected paginated(limit=1) cost to be asymptotically similar to full list cost, "
      + "ratio=" + ratio, ratio > 0.5);
}
```
Expected result: `getAssetIssuesPaginated(0, 1)` takes essentially the same time as `getAllAssetIssues()` (both dominated by full iteration + full sort), confirming that `limit` provides no computational cost reduction and the "pagination" endpoint offers no defense against mass low-`limit` request flooding.

```java
  public List<AssetIssueCapsule> getAllAssetIssues() {
    return Streams.stream(iterator())
        .map(Entry::getValue)
        .collect(Collectors.toList());
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
```
