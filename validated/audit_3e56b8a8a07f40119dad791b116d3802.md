### Title
Exchange Liquidity Injection Rounds Down the Required Paired-Token Payment, Allowing Value Extraction from Pool - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes the amount of the paired token (`anotherTokenQuant`) that a liquidity provider must deposit alongside `tokenQuant` using integer division that truncates toward zero (floors for positive operands), in both `execute()` and `doValidate()`. Because this is an amount owed *into* the pool to preserve the constant-ratio invariant, rounding it down (instead of up) lets the depositor under-pay relative to the true proportional requirement, which is the exact rounding-direction defect described in the referenced report (an amount owed to the system should round up, not down, to prevent payers from remitting less than required).

### Finding Description
In `execute()`: [1](#0-0) 

`anotherTokenQuant` is derived via `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` (or the symmetric case), which truncates any fractional remainder toward zero. The same truncating computation (`BigInteger.divide`, also truncating toward zero for positive values) is used for validation and balance-limit checks in `doValidate()`: [2](#0-1) 

`anotherTokenQuant` is the amount the depositor must contribute to keep `firstTokenBalance / secondTokenBalance` constant. Any remainder from the multiplication/division is silently dropped, so the depositor contributes strictly less than the mathematically exact proportional amount whenever the division isn't exact. This mirrors the reported bug class: a value representing an amount owed *to* an accounting pool is rounded down when it should be rounded up to prevent the payer from paying less than their true share.

Contrast this with `ExchangeWithdrawActuator`, which computes the same style of ratio but is the *receiving* side (the actuator computes how much the withdrawer *gets back*, not what they owe), so flooring there is directionally correct (protects the pool, not the user): [3](#0-2) 
Inject is the mirror-image case where the truncation benefits the payer instead of the pool.

### Impact Explanation
Each `ExchangeInjectContract` broadcast by any account (the injector must be the exchange creator per the check at `ExchangeInjectActuator.java:175`) can be crafted (by choosing `tokenQuant`) so that the true required paired amount has a nonzero fractional remainder, letting the injector systematically under-contribute the second token while still increasing their proportional claim on the pool. Repeated over many injections this results in accounting/value leakage from the exchange pool (dilutes the implicit share value backing existing pool balances), which falls under "asset or accounting corruption" via exchange/market math, i.e., the reachable and in-scope impact category.

### Likelihood Explanation
The exchange creator (an authenticated but still untrusted, non-privileged network participant relative to node operators) can trigger this at will via a standard broadcast transaction, choosing arbitrary `tokenQuant` values to maximize the rounding remainder. No special access is required beyond being the exchange's creator, which any account can become via `ExchangeCreateContract`. The magnitude of loss per call is bounded (less than one unit of the paired token per call, since it's simple integer truncation) but is deterministic and repeatable.

### Recommendation
When computing `anotherTokenQuant` for injection (the value paid *into* the pool), round the division up (e.g., ceiling division: `(numerator + denominator - 1) / denominator`, or `divideCeilExact`-style handling as already used elsewhere in the codebase, e.g., `RepositoryImpl.divideCeilExact`) rather than truncating down, in both `execute()` and `doValidate()` of `ExchangeInjectActuator`, so the depositor never contributes less than the proportional amount required to preserve the pool ratio.

### Proof of Concept
1. Create an exchange pool with `firstTokenBalance = 3`, `secondTokenBalance = 10` (ratio 10/3, non-integer).
2. As the exchange creator, broadcast `ExchangeInjectContract` with `tokenId = firstTokenID`, `quant = 1`.
3. `anotherTokenQuant = floorDiv(10 * 1, 3) = 3` (exact value is `3.333...`), so the depositor contributes `3` of the second token instead of the mathematically required `3.34` (rounded up), effectively receiving pool credit for `1` first-token unit while underpaying the second token by the truncated fraction.
4. Repeating this with carefully chosen `quant` values that maximize the truncated remainder each time siphons value from the pool's implied backing ratio over many transactions. [1](#0-0) [2](#0-1)
