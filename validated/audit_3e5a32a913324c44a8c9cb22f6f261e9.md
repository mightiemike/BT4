### Title
`DelegateAction` (NEP-366 meta-transaction) signatures omit any chain-binding data, enabling cross-chain replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`, `runtime/runtime/src/actions.rs`)

### Summary
The signed payload for meta-transactions (`DelegateAction`/`DelegateActionV2`, wrapped in `SignedDelegateAction`/`VersionedSignedDelegateAction`) contains only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`. Unlike an ordinary `SignedTransaction`, which is implicitly bound to a specific chain because it references a recent `block_hash`, the `DelegateAction` signature has no genesis hash, chain id, or any other network-identifying field. On-chain replay protection relies purely on comparing `delegate_action.nonce` against the sender's locally stored access-key nonce, exactly as with cross-chain-replayable ERC20/ETH Merkle-proof claims in the reported footium issue, where the signed artifact carries no domain separator tying it to one specific chain.

### Finding Description
`DelegateAction::get_nep461_hash` (and `VersionedDelegateActionPayload::get_nep461_hash`) build the signed hash from a `SignableMessage` wrapping only the struct fields listed above: [1](#0-0) 

The `SignableMessage`/`MessageDiscriminant` scheme (NEP-461/NEP-366) tags the message type (`DelegateAction` vs `DelegateActionV2`) to stop cross-type confusion, but it never mixes in any chain-specific value such as a genesis hash or chain id: [2](#0-1) 

When the relayer submits the `SignedDelegateAction` on-chain, the only freshness/replay check performed is `validate_delegate_action_key`, which compares the action's nonce against the access key's stored nonce for that `(sender_id, public_key)` pair — a check that is entirely local to whatever chain state currently exists, with no reference to which network produced that state: [3](#0-2) 

`apply_delegate_action` verifies only the signature, expiry (`max_block_height`), and that `sender_id` matches the tx receiver — again nothing chain-specific: [4](#0-3) 

By contrast, an ordinary `SignedTransaction` includes `block_hash`, which effectively differs per chain and gives natural cross-chain replay resistance once chains diverge even slightly. `DelegateAction` has no equivalent field.

This gap is explicitly relevant in the ecosystem because nearcore ships a tool (`tools/mirror`) whose entire purpose is to take one chain's transaction/receipt history (including `Action::Delegate`/`Action::DelegateV2`) and replay it onto a second chain that was bootstrapped from the same state snapshot; the tool has to go out of its way to *remap keys* specifically to prevent a captured `SignedDelegateAction` from being valid on the mirrored chain: [5](#0-4) 

Any deployment where two NEAR-protocol chains are initialized from the same state (fork, disaster-recovery restore from a shared snapshot, or any environment that copies account/access-key state without remapping keys) would let a previously observed `SignedDelegateAction` — a value that must be transmitted off-chain to a relayer and is also publicly visible once included in a receipt/transaction on the origin chain — be resubmitted verbatim to the second chain. Since the nonce check only inspects that chain's own access-key state (which starts identical), the replayed delegate action passes nonce validation and re-executes its inner actions (e.g. `Transfer`, `FunctionCall` with deposit, `AddKey`) on the second chain, exactly mirroring the reported cross-chain Merkle-proof replay pattern.

### Impact Explanation
A successful replay causes unauthorized re-execution of the inner actions of a meta-transaction on a second chain that shares matching account/access-key state with the origin chain — e.g., duplicating a token transfer, re-adding an access key, or re-triggering a paid `FunctionCall` — without the sender's fresh authorization on that chain. This is a concrete unauthorized value movement / invalid state transition, satisfying Medium severity for cross-chain-replay bug classes, analogous to the reported footium prize-claim replay.

### Likelihood Explanation
Exploitation requires two nearcore-based chains that share matching account and access-key nonce state (fork, snapshot-based restore, or any state-preserving migration that does not remap keys) plus the attacker's ability to observe a previously broadcast/relayed `SignedDelegateAction` (which is visible in on-chain receipts and must be transmitted to a relayer off-chain). No special privilege on the target chain is needed — any unprivileged RPC caller/relayer that can submit a transaction containing `Action::Delegate`/`Action::DelegateV2` can trigger replay once such state overlap exists, matching the "single submitted transaction/RPC request" reachability bar.

### Recommendation
Bind the `DelegateAction`/`DelegateActionV2` signed payload to the target chain by including a chain-identifying value (e.g., genesis hash or a protocol-defined chain id) inside the `SignableMessage` that is hashed and signed in `get_nep461_hash`, and validate that value against the current chain's identifier in `apply_delegate_action`/`validate_delegate_action_key` before executing the inner actions.

### Proof of Concept
1. Chain A and Chain B are both instances of this nearcore codebase, initialized from the same state snapshot (e.g., a disaster-recovery restore, or any migration workflow that does not remap account keys, unlike `tools/mirror`'s key-remapping path).
2. Alice signs a `DelegateAction` (built exactly as in `create_delegate_action_receipt`/`meta_tx` helpers, e.g. `integration-tests/src/user/mod.rs` lines 287-318) transferring funds to Bob, and hands the `SignedDelegateAction` to relayer R on Chain A.
3. R wraps it in a `SignedTransaction` (`Action::Delegate`) and submits it to Chain A; `apply_delegate_action`/`validate_delegate_action_key` (`runtime/runtime/src/actions.rs` lines 453-535, 574-746) validate signature + nonce against Chain A's access key state and the transfer executes, advancing Chain A's nonce for Alice's key.
4. Because Chain B was bootstrapped from the same snapshot, Alice's access key on Chain B still has the pre-transfer nonce.
5. An attacker (or R itself) resubmits the identical `SignedDelegateAction` bytes on Chain B. `SignedDelegateAction::verify()` succeeds (same signature/public key), `max_block_height` has not passed on Chain B, and `validate_delegate_action_key` sees the nonce as valid (Chain B's state hasn't advanced), so the transfer to Bob executes a second time on Chain B without Alice's fresh authorization there.

/// A wrapper around a message that should be signed using this scheme.
///
/// Only used for constructing a signature, not used to transmit messages. The
/// discriminant prefix is implicit and should be known by the receiver based on
/// the context in which the message is received.
#[derive(BorshSerialize)]
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
#[non_exhaustive]
pub enum SignableMessageType {
    /// A delegate action, intended for a relayer to included it in an action list of a transaction.
    DelegateAction,
    /// A delegate action with gas key support, intended for a relayer to include it in an action
    /// list of a transaction.
    DelegateActionV2,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum ReadDiscriminantError {
    #[error("does not fit any known categories")]
    UnknownMessageType,
    #[error("NEP {0} does not have a known on-chain use")]
    UnknownOnChainNep(u32),
    #[error("NEP {0} does not have a known off-chain use")]
    UnknownOffChainNep(u32),
    #[error("discriminant is in the range for transactions")]
    TransactionFound,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum CreateDiscriminantError {
    #[error("nep number {0} is too big")]
    NepTooLarge(u32),
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
