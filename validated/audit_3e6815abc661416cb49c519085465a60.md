### Title
JSON-RPC `buildTransaction` silently drops the caller's TRC10 asset transfer when both `value` and `tokenId`/`tokenValue` are set for a non-contract recipient - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/types/BuildArguments.java])

### Summary
The unauthenticated JSON-RPC `buildTransaction` endpoint decides which on-chain contract type to build (`TransferContract` vs `TransferAssetContract` vs `TriggerSmartContract`) based on which of the mutually-independent fields `value` (TRX) and `tokenId`/`tokenValue` (TRC10) are populated. When the destination is a plain account (not a deployed smart contract) and the caller supplies **both** a TRX `value` and a TRC10 `tokenId`/`tokenValue`, `BuildArguments.getContractType()` silently selects `TransferContract` and the TRC10 fields are dropped entirely with no error, exactly mirroring the LineLib pattern where mixing two asset types in one call causes one of them to be silently ignored instead of raising an error.

### Finding Description
`BuildArguments.getContractType()` [1](#0-0)  branches on the destination type:
- If `to` is a deployed smart contract, `TriggerSmartContract` is used, and both `call_value` and `call_token_value`/`token_id` are correctly propagated together [2](#0-1) .
- If `to` is a plain (non-contract) account, the code checks `availableTransferAsset()`, which only returns `true` when `tokenId>0 && tokenValue>0 && paramQuantityIsNull(value)` [3](#0-2) . If `value` is non-empty (even though `tokenId`/`tokenValue` are also non-zero), this check fails, and the code falls through to `if (StringUtils.isNotEmpty(value)) { contractType = ContractType.TransferContract; }` [4](#0-3) .
- `buildTransferContractTransaction()` then builds a pure TRX `TransferContract` using only `args.parseValue()`, and `args.getTokenId()`/`args.getTokenValue()` are never read or included in the resulting transaction at all [5](#0-4) .

This means a caller (or any wallet/tooling built on top of the RPC) that intends a combined TRX + TRC10 transfer to a normal account gets a transaction that only moves the TRX; the TRC10 portion is silently discarded with no exception, no partial-success indicator, and no way for the caller to detect the omission from the response alone — it just returns a valid, signed-looking `TransferContract`. This is the same root-cause shape as the reported LineLib bug: two different asset kinds are handled by two independent code paths, and when both are supplied simultaneously, one branch's logic simply ignores the other asset instead of erroring or handling both.

### Impact Explanation
Any external caller/integrator relying on `buildTransaction` to construct combined TRX+TRC10 transfers to ordinary accounts will have their TRC10 transfer intent silently dropped. Automated systems (exchanges, custody services, bots) that build a transaction from this RPC and blindly broadcast it may believe a token transfer occurred (based on the fields they submitted) when in fact only TRX moved — this can lead to unaccounted-for/failed settlement expectations and could be leveraged to trick a counterparty into believing a TRC10 payment was sent when it was not, since the RPC gives no validation error. It does not directly corrupt the ledger (no genuine value is "locked" the way ETH gets stuck in the LineLib contract — the token balance simply never leaves the sender because the field is dropped before the transaction is even assembled), so this is a request-construction/API-correctness defect rather than a fund-lock at the protocol/consensus level.

### Likelihood Explanation
This requires no privileged access — it is reachable by any anonymous JSON-RPC client calling `buildTransaction` with a `to` address that is not a deployed smart contract and both `value` and `tokenId`/`tokenValue` populated, which is a very plausible combination for third-party integrations that don't realize `buildTransaction`'s dual-asset semantics are mutually exclusive for non-contract recipients. It's a straightforward, deterministic classification bug (not a race or timing issue), so it always reproduces under these conditions.

### Recommendation
In `BuildArguments.getContractType()`, explicitly detect the case where `to` is a non-contract account and both `value` and `tokenId`/`tokenValue` are set, and throw a `JsonRpcInvalidParamsException` (e.g., "cannot combine TRX value and TRC10 token transfer to a non-contract address in a single buildTransaction call") rather than silently choosing `TransferContract` and dropping the token fields. Alternatively, support building a combined transaction (if the underlying protocol allows attaching both) or document/reject the ambiguity explicitly so no field is silently discarded.

### Proof of Concept
1. Call the JSON-RPC `buildTransaction` method with:
   - `from`: a funded account
   - `to`: a plain (non-contract) account address
   - `value`: `"0x1f4"` (500 sun)
   - `tokenId`: `1000016`
   - `tokenValue`: `20`
2. `BuildArguments.getContractType()` evaluates `availableTransferAsset()` as `false` (because `value` is non-empty) and falls into the `TransferContract` branch [4](#0-3) .
3. `buildTransferContractTransaction()` is invoked, which builds a `TransferContract` using only `amount = args.parseValue()`; `tokenId`/`tokenValue` are never referenced [5](#0-4) .
4. The response is a valid signed-transaction JSON of type `TransferContract` moving only 500 sun; the caller's TRC10 transfer intent for `tokenId=1000016`, `amount=20` is silently absent from the built transaction, with no error returned by the API (consistent with the existing `testTransferContract`/`testTransferAssertContract` tests exercising these two branches independently but never together) [6](#0-5) .

  public ContractType getContractType(Wallet wallet) throws JsonRpcInvalidRequestException,
      JsonRpcInvalidParamsException {
    // Fail fast on bad hex / conflict before the state lookup;
    // calldataEquals relies on resolveData() having validated hex first.
    String resolvedData = resolveData();
    validateCallDataConflict();

    ContractType contractType;

    // to is null
    if (paramStringIsNull(to)) {
      // data is null
      if (paramStringIsNull(resolvedData)) {
        throw new JsonRpcInvalidRequestException("invalid json request");
      }

      contractType = ContractType.CreateSmartContract;
    } else {
      // to is not null
      byte[] contractAddressData = addressCompatibleToByteArray(to);
      BytesMessage.Builder build = BytesMessage.newBuilder();
      BytesMessage bytesMessage = build.setValue(ByteString.copyFrom(contractAddressData)).build();
      SmartContract smartContract = wallet.getContract(bytesMessage);

      // check if to is smart contract
      if (smartContract != null) {
        contractType = ContractType.TriggerSmartContract;
      } else {
        // tokenId and tokenValue: trc10, value: TRX
        if (availableTransferAsset()) {
          contractType = ContractType.TransferAssetContract;
        } else {
          if (StringUtils.isNotEmpty(value)) {
            contractType = ContractType.TransferContract;
          } else {
            throw new JsonRpcInvalidRequestException("invalid json request");
          }
        }
      }
    }

    return contractType;
  }

  private TransactionJson buildTransferContractTransaction(byte[] ownerAddress,
      BuildArguments args) throws JsonRpcInvalidParamsException, JsonRpcInvalidRequestException,
      JsonRpcInternalException {
    long amount = args.parseValue();

    TransferContract.Builder build = TransferContract.newBuilder();
    build.setOwnerAddress(ByteString.copyFrom(ownerAddress))
        .setToAddress(ByteString.copyFrom(addressCompatibleToByteArray(args.getTo())))
        .setAmount(amount);

    return createTransactionJson(build, ContractType.TransferContract, args);
  }
