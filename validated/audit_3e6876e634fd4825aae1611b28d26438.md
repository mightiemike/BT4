### Title
Missing check that transfer/account-creation destination address is not the zero-body address - (File: `common/src/main/java/org/tron/common/utils/DecodeUtil.java`)

### Summary
`DecodeUtil.addressValid` — the single validation routine used across actuators to check owner/recipient addresses — only verifies address length (21 bytes) and the network prefix byte (`0x41`); it never verifies that the remaining 20 address bytes are non-zero. This is the same bug class as the reported Gearbox issue: a caller-supplied address field is accepted as valid without excluding the "null"/zero-body address, so an unprivileged transaction can move value or create account state bound to an address that no one can plausibly control.

### Finding Description
`DecodeUtil.addressValid` performs only two checks — length and prefix byte — with no check on the remaining bytes: [1](#0-0) 

This method is the sole gatekeeper for recipient/owner addresses in multiple actuators reachable directly from broadcast transactions:
- `TransferActuator.validate()` validates `toAddress`/`ownerAddress` only via `DecodeUtil.addressValid`, and if the account doesn't exist it is silently created in `execute()`: [2](#0-1) [3](#0-2) 
- `TransferAssetActuator` has the identical pattern for `toAddress`: [4](#0-3) [5](#0-4) 
- `CreateAccountActuator.validate()` validates `accountAddress` the same way before creating the account: [6](#0-5) 

None of these paths reject an address whose 20-byte body is all zero (i.e., `0x41` followed by 20 zero bytes). Because TRON addresses are derived from public key hashes and not from an explicit "null address" sentinel, such an address is indistinguishable at the protocol layer from a normal address, but in practice it corresponds to no known/derivable private key. The system will happily register it as a `Normal` account and credit it with TRX/TRC10 balance.

### Impact Explanation
Any unprivileged user can send a normal `TransferContract` or `TransferAssetContract` transaction (or a `AccountCreateContract`) that targets the zero-body address. This will:
- Create a new on-chain account bound to an address with no known corresponding key, and
- Permanently lock any TRX/asset balance sent to it, since no one can produce a valid signature for that address.

This is analogous to the underlying bug class in the report (an address parameter that should be excluded from being the "null"/zero value is accepted and used to create account/ownership state), and results in permanent loss of user funds sent to that address, which is an asset-accounting-corruption/fund-loss issue reachable directly by any broadcast transaction.

### Likelihood Explanation
High likelihood of accidental triggering (typos, malformed clients producing all-zero address bytes) and trivial to exploit deliberately since it requires only constructing a normal `TransferContract`/`TransferAssetContract` with `toAddress = 0x41 + 20×0x00`, which passes `DecodeUtil.addressValid` unmodified.

### Recommendation
Add an explicit check in `DecodeUtil.addressValid` (or in each actuator's `validate()`) that rejects addresses whose body (bytes after the prefix) are all zero, in addition to the existing length/prefix checks, mirroring the recommended fix in the referenced report (reject the zero/null-equivalent address before using it to create or credit accounts).

### Proof of Concept
1. Craft a `TransferContract` with `owner_address` = a funded account and `to_address` = `0x41` followed by 20 zero bytes (a 21-byte array).
2. Broadcast the transaction; `TransferActuator.validate()` passes because `DecodeUtil.addressValid` only checks length/prefix.
3. `TransferActuator.execute()` creates a new `AccountCapsule` at the zero-body address and credits it with the transferred amount — funds are now bound to an address without a plausible controlling private key. [7](#0-6)

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
