### Title
Asymmetric rounding between capability spend-limit derivation and settlement causes CRE workflow billing/balance inconsistency - (File: core/services/workflows/metering/balance_store.go)

### Summary
This is analyzed as a bug-class analog to the SwapNet `FutureCash.tradeLiquidityToken` rounding issue: two quantities that are supposed to represent the "same" value (an authorized spend limit vs. the amount actually deducted from the ledger) are computed via two different, non-inverse rounding operations, allowing the locally tracked balance/limit to diverge from the true settled amount.

### Finding Description
In Chainlink's CRE workflow metering package, a capability's spend limit is derived from the local credit balance and then, after the capability executes, the actual usage is converted back into credits to deduct from that same balance. These two conversions use different rounding rules:

- `convertFromBalance` (used when deriving a spend limit to hand to a capability, e.g. gas budget) rounds gas resource conversions to 0 decimal places: `amount.Mul(rate).Round(0)` [1](#0-0) 
- `convertToBalance` (used when converting the capability's *actual* reported spend back into credits at settlement time) rounds gas conversions to `defaultDecimalPrecision` (10) decimal places: `amount.Div(rate).Round(defaultDecimalPrecision)` [2](#0-1) 

`creditToSpendingLimits` uses `ConvertFromBalance` to compute the `SpendLimit` handed to a capability (e.g., a chain-write capability's max native-gas budget) [3](#0-2) . Later, `Settle` takes the capability's self-reported spend value and runs it back through `ConvertToBalance` to determine how many credits to actually subtract from the local balance and report as `CreditsConsumed` to the billing service [4](#0-3) .

Because `Mul(...).Round(0)` and `Div(...).Round(10)` are not exact inverses of each other, a limit derived from N credits and then spent back down does not necessarily deduct exactly N credits — analogous to how SwapNet's `tokensToRemove = (collateralRequired*totalLiquidity)/totalCollateral` and the reverse `collateral = (totalCollateral*tokensToRemove)/totalLiquidity` produced different values under Solidity's truncating division. Here, the "local" balance (`balanceStore.balance`, deducted via `Minus`) can drift from what is actually reported/settled with the authoritative billing service via `SubmitWorkflowReceipt`'s `CreditsConsumed` field [5](#0-4) , since the two paths (`Deduct`'s pre-execution reservation and `Settle`'s post-execution deduction) are computed independently through asymmetric round-trip math rather than one authoritative value being reused.

### Impact Explanation
If the local spend-limit accounting and the actual credited/settled deduction diverge because of rounding, the effects are analogous to the SwapNet bug's downstream consequences: the workflow engine's tracked balance (`balanceStore.balance`) can end up higher than what is truly consumed (allowing more capability calls than the user's remaining credits should permit before `ErrInsufficientBalance` triggers), or conversely lower, causing premature switch to `metering mode`/`ErrInsufficientBalance` even when sufficient credits exist. Because a capability's `SpendLimit` (e.g., for `evm.WriteReport`) is derived from this same rounded math, and that limit is passed as authoritative metadata into `capabilities.RequestMetadata.SpendLimits` for privileged write capabilities [6](#0-5) , repeated rounding errors across many steps/executions can accumulate (as explicitly called out for the analogous protocol bug), producing sustained misreporting of consumed credits to the billing service relative to what capabilities were actually authorized/able to spend.

### Likelihood Explanation
This code path executes on every CRE workflow capability call that has metering enabled and involves a gas/resource-based spend type — i.e., it is triggered by ordinary, unprivileged workflow execution, not by a malicious node/operator. The divergence is a deterministic, systematic effect of the differing `Round(0)` vs `Round(defaultDecimalPrecision)` behavior in `convertFromBalance`/`convertToBalance`, not a rare edge case, so it will manifest whenever the arithmetic does not land on an exact round-trip value (which is generically the common case for non-power-of-ten rates).

### Recommendation
Avoid deriving a spend limit and a settlement deduction from two independently-rounded conversions of the same conceptual quantity. Prefer: (1) using a single canonical rounding precision/rule between `convertToBalance` and `convertFromBalance` so they are true inverses, or (2) instead of recomputing the settled credit amount from scratch via `ConvertToBalance` in `Settle`, cap/reconcile it directly against the previously reserved `Deduction` amount from the corresponding `ReportStep`, similar to how the SwapNet fix used the actual value returned by `_settleLiquidityToken` rather than a separately recomputed `collateralRequired`. At minimum, add unit tests asserting round-trip conversions (`ConvertFromBalance` then `ConvertToBalance`) are idempotent within an acceptable epsilon and that persistent local-balance drift cannot exceed a bounded/reconciled amount over many steps.

### Proof of Concept
Conceptual walk-through based on `balance_store.go`:
1. `NewBalanceStore(balance=10 credits, conversions={"GAS.<chainSel>": rate})` where rate is the "gas units per credit" (e.g., `230140614074074` from `metering_test.go`) [7](#0-6) .
2. `creditToSpendingLimits` calls `ConvertFromBalance("GAS...", amount)` → `amount.Mul(rate).Round(0)`, producing a whole-wei spend limit (e.g., `"1380843684444444000"` in the test) [8](#0-7) .
3. A capability spends exactly up to that wei limit; when settled, `Settle` calls `ConvertToBalance("GAS...", spentWei)` → `spentWei.Div(rate).Round(10)` [9](#0-8) .
4. Because `Round(0)` (integer wei) followed by `Div(rate).Round(10)` is not guaranteed to reproduce the original credit amount exactly (unless `rate` divides evenly), the credits actually subtracted from `balanceStore.balance` via `Minus` in `Settle`'s caller path can differ fractionally from the credits reserved in step 2 — repeated over many workflow steps, this produces the same class of accumulating balance drift described in the source report.

Note: I was not able to fully trace how (or whether) any reconciliation/cap exists between the `Deduction` recorded in `ReportStep` and the value later added to `spentCredits` in `Settle` within the given iteration budget, so the exact magnitude of exploitable drift (versus a purely cosmetic/logged discrepancy) is not fully confirmed and would benefit from deeper review of `metering.go`'s `Settle` and `FormatReport` functions and how `CreditsConsumed` is ultimately reconciled against the billing service's own ledger.

// convertToBalance converts a resource dimension amount to a credit amount.
// This method should only be used under a read lock.
func (bs *balanceStore) convertToBalance(fromResourceType string, amount decimal.Decimal) (decimal.Decimal, error) {
	rate, ok := bs.conversions[fromResourceType]
	if !ok {
		return amount, ErrResourceTypeNotFound
	}

	// Special case for gas as gas token conversions are provided in amount per credit.
	// Other rates are provided as the inverse.
	if isGasSpendType(fromResourceType) {
		if rate.IsZero() {
			return decimal.Zero, nil
		}

		return amount.Div(rate).Round(defaultDecimalPrecision), nil
	}

	return amount.Mul(rate), nil
}

// creditToSpendingLimits returns a slice of spend limits where the amount is applied to the spend types from the
// provided info. Amount should be specified in universal credits and will be converted to spend type credits within
// this function.
func (r *Report) creditToSpendingLimits(
	info capabilities.CapabilityInfo,
	capConfig *values.Map,
	amount decimal.Decimal,
) []capabilities.SpendLimit {
	if r.meteringMode {
		return []capabilities.SpendLimit{}
	}

	// no spend types results in no limits and is not a failure case
	if len(info.SpendTypes) == 0 {
		return []capabilities.SpendLimit{}
	}

	ratios, err := ratiosFromConfig(info, capConfig)
	if err != nil {
		r.switchToMeteringMode(err)

		return []capabilities.SpendLimit{}
	}

	// spend types do not have matching ratios; this is a bad configuration
	if len(info.SpendTypes) != len(ratios) {
		r.switchToMeteringMode(fmt.Errorf("%w: %d spend types and %d ratios", ErrRatiosAndTypesNoMatch, len(info.SpendTypes), len(ratios)))

		return []capabilities.SpendLimit{}
	}

	limits := []capabilities.SpendLimit{}

	for _, spendType := range info.SpendTypes {
		ratio, hasRatio := ratios[spendType]
		if !hasRatio {
			// the spend type does not exist in the ratios mapping; this is a bad configuration
			r.switchToMeteringMode(fmt.Errorf("%w: ratios missing %s spend type", ErrRatiosAndTypesNoMatch, spendType))

			return []capabilities.SpendLimit{}
		}

		// use rate card to convert capSpendLimit to native units
		spendLimit, err := r.balance.ConvertFromBalance(string(spendType), amount.Mul(ratio))
		if err != nil {
			r.switchToMeteringMode(fmt.Errorf("attempted to create spending limits [%s]: %w", spendType, err))

			return []capabilities.SpendLimit{}
		}

		formattedLimit := spendLimit.StringFixed(defaultDecimalPrecision)
		if isGasSpendType(string(spendType)) {
			formattedLimit = spendLimit.StringFixed(0)
		}

		limits = append(limits, capabilities.SpendLimit{SpendType: spendType, Limit: formattedLimit})
