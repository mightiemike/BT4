### Title
Attacker-controlled revert/refund recipient can permanently abort failed-outbound fund recovery, freezing bridged funds - (File: x/uexecutor/keeper/outbound.go)

### Summary
The GoGoPool finding is a push-payment DoS: a node operator sets `owner` to a contract that rejects native transfers, causing `cancelMinipoolByMultisig`'s `safeTransferETH` to revert and permanently block cancellation/refund. The Push Chain analog is in the outbound-finalization refund path, where the fund-recovery recipient is fully attacker-controlled (set at inbound-creation time via `RevertInstructions.FundRecipient`) and a failed "push" mint to that recipient causes the recovery flow to halt in a terminal, unrecoverable state instead of returning funds to the user.

### Finding Description
When an outbound (bridge-out) transaction is observed as failed by the universal validators, `handleFailedOutbound` in `x/uexecutor/keeper/outbound.go` attempts to "revert" by re-minting the bridged PRC20 tokens back on Push Chain to a recipient: [1](#0-0) 

The recipient is taken from `outbound.RevertInstructions.FundRecipient` if set, otherwise falls back to `outbound.Sender` — both of which are values supplied by the original, unprivileged inbound submitter/depositor and simply carried forward through `buildRevertOutbound`: [2](#0-1) 

If the `CallPRC20Deposit` (mint) call to this attacker-chosen recipient fails for any reason, the code does **not** retry, does not fall back to a pull-based claim mechanism, and does not credit the funds anywhere else. Instead it calls `AbortOutbound`, which sets the outbound to a terminal `ABORTED` status and only emits a log/event for manual intervention: [3](#0-2) [4](#0-3) 

This is reached purely through the honest-validator voting path (`VoteOutbound` → `FinalizeOutbound` → `handleFailedOutbound`), with no privileged actor involved: [5](#0-4) 

This mirrors the GoGoPool bug-class: a "push" of value to an attacker-influenced address is used as the sole path to close out a failure/cancellation state, and the attacker can make that push fail, permanently blocking normal resolution and leaving user/protocol funds in a stuck, non-refundable state (`ABORTED`, no further automatic path visible in this flow).

The same push-based pattern, with the same attacker-supplied recipient, exists in the excess-gas-refund path (`applyGasRefund`), and in the admin/inbound revert path (`RevertStuckInbound`/`handleFailedInboundValidation`) which also mints/deposits to `RevertInstructions.FundRecipient`: [6](#0-5) [7](#0-6) 

### Impact Explanation
If exploitable, this permanently freezes the user's own bridged funds (and any excess gas refund) in an `ABORTED` state with no documented on-chain path to reclaim them via a pull mechanism — a fund-freezing / denial-of-recovery condition reachable by an ordinary unprivileged user who controls the `RevertInstructions.FundRecipient` field of their own inbound. This matches the in-scope impact category of "permanent freezing... of user or protocol-controlled funds" under the Push Chain allowed-impact gate.

### Likelihood Explanation
**Uncertain / not fully confirmed.** I could not verify within the available context whether `CallPRC20Deposit`'s underlying PRC20 `deposit`/`mint` function actually invokes recipient contract code in a way that an attacker-deployed contract could force to revert (e.g., via a receiver hook, callback, or gas-griefing pattern), or whether it is a simple internal ledger `_mint` that cannot be blocked by recipient bytecode. I was not able to fully inspect `CallPRC20Deposit`'s implementation or the PRC20 contract's mint logic (`evm.go` beyond line 80, and the PRC20/UniversalCore Solidity source) before running out of iterations. If the PRC20 mint is a pure balance-ledger update with no external call to the recipient, this finding does not apply, since nothing an attacker controls at the recipient address could cause `CallPRC20Deposit` to fail (barring gas-limit tricks, which were also not verified as reachable here).

### Recommendation
1. Confirm whether `CallPRC20Deposit`/PRC20 mint can be forced to revert by adversarial recipient bytecode (check the PRC20/UniversalCore Solidity `deposit`/`mint` implementation and whether it makes any external call, hook, or has fixed/unbounded gas forwarding to the recipient).
2. If confirmed, replace the push-based recovery/refund/abort pattern with a pull-based claim: on mint failure, record a claimable balance keyed by the original inbound sender/UTX (not the attacker-adjustable `FundRecipient`), and expose a permissionless `ClaimAbortedFunds` message so the rightful owner (or a canonical, non-attacker-controlled address) can retrieve funds independent of the `RevertInstructions.FundRecipient` value.
3. Alternatively, bound the gas forwarded to the recipient during mint/deposit and treat any failure there as non-fatal to the destination bookkeeping (i.e., escrow funds under the module account rather than aborting entirely).

### Proof of Concept
Not verifiable without confirming the underlying PRC20 mint call semantics (see Likelihood Explanation). Conceptually:
1. Attacker submits an inbound with `RevertInstructions.FundRecipient` set to a malicious contract address that is designed/deployed to revert on any interaction that the PRC20 mint might trigger (if such an interaction exists).
2. The outbound created from this inbound is later observed as failed by honest universal validators via `VoteOutbound`.
3. `FinalizeOutbound` → `handleFailedOutbound` attempts `CallPRC20Deposit` to the attacker's malicious `FundRecipient`; if this call reverts, `AbortOutbound` marks the outbound `ABORTED` with no further automated recovery path, matching the "cannot cancel/refund" bug class from the source report.

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}

func (k Keeper) buildRevertOutbound(sdkCtx sdk.Context, inbound *types.Inbound) *types.OutboundTx {
	recipient := inbound.Sender
	if inbound.RevertInstructions != nil && inbound.RevertInstructions.FundRecipient != "" {
		recipient = inbound.RevertInstructions.FundRecipient
	}

	outbound := &types.OutboundTx{
		DestinationChain:  inbound.SourceChain,
		Recipient:         recipient,
		Amount:            inbound.Amount,
		ExternalAssetAddr: inbound.AssetAddr,
		Sender:            inbound.Sender,
		TxType:            types.TxType_INBOUND_REVERT,
		OutboundStatus:    types.Status_PENDING,
		Id:                types.GetOutboundRevertId(inbound.SourceChain, inbound.TxHash, inbound.LogIndex),
	}
