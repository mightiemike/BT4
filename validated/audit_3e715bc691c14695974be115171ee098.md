## Analysis

The reported bug class is precision loss in an accumulator caused by decoupling *when a value's underlying clock/checkpoint advances* from *whether that specific value actually captured meaningful change* — small increments get silently truncated away because the checkpoint moves on regardless. This class is described in the rules as "a clock advanced only on change," and it has a direct analog in the Zest vault accrual logic. [1](#0-0) 

### Title
Shared `last-update` checkpoint advances on any index change, permanently truncating liquidity-index (supplier yield) accrual - (File: mainnet/contracts/vault/v0-vault-stx.clar)

### Summary
`accrue()` maintains two independent, integer-rounded accumulators — the debt `index` (rounded up) and the supplier `lindex` (rounded down) — but both share a single `last-update` timestamp that is only advanced `(if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)`. Whenever the debt index changes but the liquidity index rounds down to no change in the same call, the shared clock is reset anyway, discarding the liquidity index's sub-unit accrued fraction forever.

### Finding Description
`next-index` and `next-liquidity-index` both derive `time-delta` from the same `last-update` variable, but apply different rounding to `calc-multiplier-delta`: the debt-side multiplier rounds up (`round-up true`), while the liquidity-side multiplier rounds down (`round-up false`) and is additionally scaled down by utilization and `(1 - reserve-factor)` via `calc-liquidity-rate`. [2](#0-1) 

Because the liquidity rate is always `<=` the borrow rate (`calc-liquidity-rate` applies `mul-bps-down` twice — once for utilization, once for `1 - reserve-factor`), and its multiplier rounds down while the debt multiplier rounds up, there is a wide, realistic parameter/time-delta space (low utilization, short block-to-block intervals) where the debt index's rounded-up multiplier ticks to a new integer value while the liquidity index's rounded-down multiplier truncates to exactly `INDEX-PRECISION` (no change). [3](#0-2) 

In `accrue()`, `index` and `lindex` are only persisted `if` they individually changed, but `last-update` — the shared baseline both accumulators measure `time-delta` from — is advanced `if either one changed`: [4](#0-3) 

When the debt index alone triggers the reset, the liquidity index's sub-threshold elapsed-time contribution (the fraction that hadn't yet accumulated enough to round up to a nonzero multiplier increment) is permanently lost — the next `next-liquidity-index()` call computes `time-delta` from the new, later `last-update`, so that discarded window can never be recovered. This is structurally identical to the referenced report's `pd_store`/`upd_twap` issue: an accumulator whose denominator/checkpoint gets reset by an unrelated event before it absorbed the small quantity it was meant to track, silently erasing precision on every occurrence. The identical pattern (shared `pause-states`/`last-update`, asymmetric rounding, and reset-on-any-change) is duplicated across every vault: `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, and `v0-vault-ststxbtc.clar`. [5](#0-4) 

The corrupted `lindex` is not merely an internal bookkeeping artifact — it is read directly by `market.clar` to price every zToken used as collateral or for redemption/health calculations, via `resolve-ztoken`, independent of the vault's own `total-assets/total-supply` share-price mechanics: [6](#0-5) 

So a `lindex` that systematically under-accrues relative to the true continuously-compounding supply rate causes zTokens to be persistently mispriced low relative to their fair redeemable value, while the debt-side index (and therefore borrower obligations and the treasury's `reserve-inc`/`treasury-lp` mint, which is derived purely from debt-delta and unaffected by this truncation) continue to grow correctly and unaffected. [7](#0-6) 

### Impact Explanation
Depositors' yield entitlement, as represented on-chain by `lindex` and consumed by `market.clar` for zToken valuation, is permanently truncated below the true accrued rate whenever this rounding-mismatch pattern is triggered — this is a **permanent loss of unclaimed yield** for suppliers (High impact). Because the effect compounds every time it recurs (each occurrence resets the checkpoint and discards the fractional window irrecoverably), an attacker who repeatedly triggers `accrue()` with short intervals under low-utilization conditions (e.g., via minimal-size `borrow`/`repay` cycles, which are single, ordinary, self-contained transactions and cost only gas) can indefinitely suppress `lindex` growth for a given vault, systematically starving all suppliers of that vault's earned interest while the debt side accrues normally.

### Likelihood Explanation
Utilization near zero (common for freshly-deployed or thinly-borrowed stablecoin/asset vaults) combined with sub-second-to-few-second block cadence is a routine, not contrived, operating condition — the interpolated base borrow rate at low utilization is commonly nonzero (curve intercept), while the utilization-scaled liquidity rate necessarily approaches zero faster, making the truncation-then-reset sequence easy to trigger repeatedly and cheaply.

### Recommendation
Track `last-update` (or an equivalent accrual checkpoint) independently per accumulator — i.e., only reset the debt-index checkpoint when the debt index changes, and only reset the liquidity-index checkpoint when the liquidity index changes — so that a change in one never discards unaccrued precision belonging to the other. Alternatively, retain the truncated remainder (e.g., carry `time-delta` forward until the liquidity multiplier is guaranteed to move) instead of resetting the shared clock unconditionally.

### Proof of Concept
1. Vault deployed with `INDEX-PRECISION = 1e12`, `SECONDS-PER-YEAR-BPS = 31536000 * 10000`, and an interest-rate curve with a nonzero base borrow rate at ~0 utilization (e.g., 200 bps) and reserve factor 1000 bps.
2. Utilization is kept near 0 (large supply, minimal debt) so `calc-liquidity-rate` (`calc-liquidity-rate` at `v0-vault-stx.clar:187-190`) yields a very small liquidity rate.
3. Attacker calls a tiny `system-borrow`/`system-repay` pair (or any action invoking `accrue()`) every ~1-2 seconds. Each call: `time-delta` is small, `calc-multiplier-delta(rate, time-delta, round-up=true)` for the debt index rounds up to a nonzero increment (`idx` changes), while `calc-multiplier-delta(liquidity-rate, time-delta, round-up=false)` rounds down to `0` (`lindex` unchanged).
4. Per `accrue()` (`v0-vault-stx.clar:851-862`), since `idx` changed, `last-update` is reset to `stacks-block-time` even though `lindex` did not change — discarding the elapsed window's fractional liquidity accrual.
5. Repeating step 3 across many blocks keeps `lindex` frozen (or growing far slower than the true compounded rate) indefinitely, while `idx` (and derived debt/treasury values) continues to grow correctly.
6. Any zToken price read via `market.clar`'s `resolve-ztoken` (`v0-4-market.clar:343-347`) for collateral valuation, redemption, or health checks reflects the stale, under-accrued `lindex`, permanently understating supplier value relative to the true continuously-compounded yield.
