### Title
Floor-rounding in `ExchangeInjectActuator#doValidate`/`execute` understates the paired-token amount required, violating proportional-injection invariant (ERC4626-style rounding-direction bug) - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
The Sherlock report flags that `AutoRoller.previewWithdraw` rounds in the wrong direction: when the protocol computes how much a user must *supply* to receive a desired output, ERC-4626 requires rounding **up** (in favor of the vault), but the code effectively rounds down/underestimates. The same rounding-direction class exists in java-tron's bonded liquidity-pool ("Exchange"/Bancor-style AMM) actuators: when computing the paired-token amount a liquidity provider must contribute to keep the pool's price ratio unchanged, the code uses floor (truncating) integer division instead of rounding up.

### Finding Description
`ExchangeInjectActuator` lets the exchange creator inject one side of a two-token pool by an arbitrary `tokenQuant`, and the protocol computes the required amount of the *other* token (`anotherTokenQuant`) needed to keep `firstTokenBalance/secondTokenBalance` constant: [1](#0-0) 

```java
if (Arrays.equals(tokenID, firstTokenID)) {
  anotherTokenID = secondTokenID;
  anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant)
      .divide(bigFirstTokenBalance).longValueExact();
  ...
```

`BigInteger.divide` truncates toward zero (floor for positive operands), so `anotherTokenQuant` is always `<=` the exact proportional amount. This same floor value is recomputed and applied in `execute()` via a `floorDiv` helper: [2](#0-1) 

Per ERC-4626 rounding conventions (cited directly in the external report), when the protocol is "calculating the amount of underlying tokens a user has to provide to receive [or match] a certain amount" of another asset, it must round **up**, favoring the pool/vault, not the depositor. Here it rounds down, so the injector systematically contributes a fraction of a token-unit less of `anotherToken` than the exact ratio requires. Both `firstTokenBalance` and `secondTokenBalance` are updated using this under-computed value, so the pool's stored price ratio (`firstTokenBalance/secondTokenBalance`) drifts slightly with every injection, always in the direction that favors the injector over the pool/other counterparties who trade against it via `ExchangeTransactionActuator`.

By contrast, the two genuinely price-critical paths — `ExchangeProcessor`/`SafeExchangeProcessor` (used by `ExchangeTransactionActuator`, reachable by any unprivileged trader) — correctly floor/truncate in the safe direction (round down when minting relay-supply and when paying out the counter-asset), matching ERC-4626's requirements for `previewDeposit`/`previewRedeem`. The bug is confined to `ExchangeInjectActuator`'s "round up" scenario, which uses the wrong (floor) rounding mode instead of ceiling division.

### Impact Explanation
Each injection understates the matching-token requirement by up to 1 unit (in the token's smallest denomination) due to integer floor division, silently shifting the pool's first/second balance ratio in favor of the injecting account. While the single-call impact is bounded to sub-unit dust, an exchange creator can repeatedly call `ExchangeInjectActuator` with crafted `tokenQuant` values (choosing quantities that maximize the truncation remainder) to accumulate a systematically favorable price skew in the pool over many transactions, at the expense of value extracted from subsequent traders on `ExchangeTransactionActuator`, or from other stakeholders relying on `getFirstTokenBalance()/getSecondTokenBalance()` (V1/V2 exchange rate) as an oracle-like reference. This is a state/accounting-drift bug rather than a fund-draining exploit in a single call, but it is a genuine violation of the intended pool invariant and directly maps to the reported rounding-direction defect.

### Likelihood Explanation
Any account that has created (or become creator of) an exchange can call `ExchangeInjectContract` freely and repeatedly — no elevated blockchain-level privilege is required, only ownership of a self-created pool, which is attainable by any account. The bug triggers deterministically on essentially every injection call where the division is inexact (very common, since `tokenQuant` is arbitrary and pool balances are also arbitrary), so likelihood of triggering the rounding defect is high; the meaningful economic impact requires repeated/deliberate exploitation to accumulate drift, which is straightforward given the actuator's unrestricted call frequency.

### Recommendation
Change the `anotherTokenQuant` calculation in both `doValidate()` and `execute()` of `ExchangeInjectActuator` to round up (ceiling division) instead of floor division, e.g. using `BigInteger` ceiling-division (`(numerator + denominator - 1) / denominator`, guarded for exactness) or `Math.ceilDiv`-equivalent logic, consistent with the ERC-4626 principle of rounding in favor of the pool/vault when computing the amount a user must supply to match a given quantity.

### Proof of Concept
1. Create an exchange pool with `firstTokenBalance = 10` and `secondTokenBalance = 3` (ratio 10:3).
2. Call `ExchangeInjectContract` with `tokenID = firstTokenID`, `tokenQuant = 1`.
3. `anotherTokenQuant = (3 * 1) / 10 = 0` (floor), so the actuator accepts an injection of `1` unit of the first token while requiring `0` units of the second token — the pool ratio moves from `10:3` (3.33) to `11:3` (3.67), a price shift entirely in favor of the injector, with no compensating contribution, purely due to floor-rounding instead of round-up.
