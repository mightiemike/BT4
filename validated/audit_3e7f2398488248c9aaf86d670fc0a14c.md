### Title
Disk-backed AccountsIndex bucket files are reused across validator upgrades without any struct-layout/version check on `IndexEntry<T>`, risking silent index corruption analogous to storage-gap corruption on upgrade - (File: `bucket_map/src/restart.rs`, `bucket_map/src/bucket_storage.rs`, `bucket_map/src/bucket.rs`)

### Summary
The Sherlock report describes Solidity contracts that persist inherited storage across an upgrade without reserving storage-gap slots, so a future upgrade that changes an intermediate contract's field layout silently shifts and corrupts the child contract's storage. The reachable analog in Agave is the `bucket_map` disk-index restart mechanism: it persists raw, `repr(C)` `IndexEntry<T>` records to files and, on the next process start, blindly reinterprets those bytes using whatever `size_of::<IndexEntry<T>>()` the *currently running binary* computes, with no on-disk record describing the actual layout/size the data was written with.

### Finding Description
`Bucket::new` computes `elem_size` from the size of the currently-compiled `IndexEntry<T>` type and tries to reuse a previous run's index bucket file via `BucketStorage::load_on_restart`: [1](#0-0) 

`load_on_restart` derives `num_elems` purely from `file_len / elem_size` (using the caller-supplied, i.e. current-build, `elem_size`) and performs no check that the file was actually written with that same element size or layout: [2](#0-1) 

The separate "restart" bookkeeping file only validates a coarse `Header` (`version`, `buckets`, `max_search`) and per-bucket `file_name`/`random`; it never records or validates the `IndexEntry<T>` layout/size that produced the associated data files: [3](#0-2) [4](#0-3) 

`IndexEntry<T>` and its nested `MultipleSlots`/`PackedStorage`/`PackedRefCount` types are `repr(C)` structs whose exact byte layout determines how pubkeys, ref-counts, and slot lists are parsed out of the mmapped bucket file: [5](#0-4) [6](#0-5) 

Just as the audited Solidity contracts relied on unreserved storage slots that a later upgrade to an intermediate contract could silently shift, this Rust code relies on an *unversioned, unchecked* binary layout of `IndexEntry<T>` that a later Agave build could silently change (e.g. reordering/adding a field, changing `RefCount`/`Slot` width, or changing generic `T`). Because `load_on_restart`'s only sanity check is that `file_len` divides evenly by the new `elem_size`, a coincidental size match (or a size that still divides evenly) would cause the file to be accepted and its bytes reinterpreted under the new layout, corrupting `key`, `ref_count`, and `slot_list` data with no error raised.

### Impact Explanation
If accepted, this leads to silently corrupted `AccountsIndex` entries after a validator software upgrade that changes `IndexEntry<T>`'s binary layout while operators keep persistent bucket-map/accounts-index directories across the upgrade (a supported, intentional operational pattern to speed up restart). Corrupted index entries (wrong pubkey/ref_count/slot_list) can cause stale or wrong-version account loads and can diverge a node's view of account state from the rest of the cluster without any panic or visible error, matching the "concrete stale or wrong-version account loads" / "silent" corruption criteria.

### Likelihood Explanation
This requires a future Agave release to change the binary layout of `IndexEntry<T>` (or its generic parameter) without bumping any compatibility marker, combined with an operator preserving on-disk bucket files across the upgrade — both realistic, non-malicious operational scenarios rather than attacker-controlled inputs. There is currently no mechanism (analogous to a storage gap) reserving room for future layout changes or detecting a layout mismatch beyond the coarse restart-file header, so the risk is structural rather than merely theoretical.

### Recommendation
Persist an explicit format/layout identifier (e.g., a hash or version constant derived from `size_of::<IndexEntry<T>>()`/its generic parameter, or an explicit schema version) inside each bucket data file's header (as is already done conceptually for the `Restart` `Header`), and have `BucketStorage::load_on_restart` reject/discard files whose stored layout identifier doesn't match the current build's expected layout, rather than relying solely on `file_len % elem_size == 0`.

### Proof of Concept
1. Run a validator build where `size_of::<IndexEntry<T>>()` is `S1`, with a persistent accounts-index/bucket-map path, and let it write bucket data files.
2. Upgrade to a new Agave build where an internal field of `IndexEntry<T>` (or `MultipleSlots`/`PackedStorage`) is reordered/resized such that the new `size_of::<IndexEntry<T>>()` is `S2`, chosen (or coincidentally arising from an unrelated change) such that the old file's length is still evenly divisible by `S2`.
3. Restart the validator with the same accounts-index/bucket-map path. `Bucket::new` → `BucketStorage::load_on_restart` (`bucket_map/src/bucket_storage.rs:226-253`) computes `num_elems = file_len/S2` and reinterprets the old `S1`-laid-out bytes as `S2`-laid-out `IndexEntry<T>` records, with no version check catching the mismatch (`bucket_map/src/restart.rs:145-177` only checks `buckets`/`max_search`/`version`, not element layout).
4. Resulting reads via `IndexEntryPlaceInBucket::get_slot_count_enum`/`read_value` (`bucket_map/src/index_entry.rs`) return garbage `key`, `ref_count`, and `slot_list` data for affected entries, silently corrupting the accounts index.

    /// load and mmap the file that is this disk bucket if possible
    pub(crate) fn load_on_restart(
        path: PathBuf,
        elem_size: NonZeroU64,
        max_search: MaxSearch,
        stats: Arc<BucketStats>,
        count: Arc<AtomicU64>,
    ) -> Option<Self> {
        let offset = Self::get_offset_to_first_data();
        let num_elems = std::fs::metadata(&path)
            .ok()
            .map(|metadata| metadata.len().saturating_sub(offset) / elem_size)?;
        if num_elems == 0 {
            return None;
        }
        let mmap = Self::map_open_file(&path, false, 0, &stats)?;
        Some(Self {
            path,
            mmap,
            cell_size: elem_size.into(),
            count,
            stats,
            max_search,
            contents: O::new(Capacity::Actual(num_elems)),
            // since we loaded it, it persisted from last time, so we obviously want to keep it present disk.
            delete_file_on_drop: false,
        })
    }

    /// loads and mmaps restart file if it exists
    /// returns None if the file doesn't exist or is incompatible or corrupt (in obvious ways)
    pub(crate) fn get_restart_file(config: &BucketMapConfig) -> Option<Restart> {
        let path = config.restart_config_file.as_ref()?;
        let metadata = std::fs::metadata(path).ok()?;
        let file_len = metadata.len();

        let expected_len = Self::expected_len(config.max_buckets);
        if expected_len as u64 != file_len {
            // mismatched len, so ignore this file
            return None;
        }

        let file = OpenOptions::new()
            .read(true)
            .write(true)
            .create(false)
            .open(path)
            .ok()?;
        let mmap = unsafe { MmapMut::map_mut(&file).unwrap() };

        let restart = Restart { mmap };
        let header = restart.get_header();
        if header.version != HEADER_VERSION
            || header.buckets != config.max_buckets as u64
            || header.max_search != config.max_search.unwrap_or(MAX_SEARCH_DEFAULT)
        {
            // file doesn't match our current configuration, so we have to restart with fresh buckets
            return None;
        }

        Some(restart)
    }
