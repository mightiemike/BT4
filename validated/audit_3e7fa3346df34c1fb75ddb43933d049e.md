## Title
Block assembler uses hardcoded `BlobParams::cancun()` instead of the chain's active blob params for the first post-Cancun-fork block, producing an `excess_blob_gas` that diverges from consensus validation — (`File: crates/ethereum/evm/src/build.rs`)

### Summary
`EthBlockAssembler::assemble_block` computes the header's `excess_blob_gas` for the first block after Cancun activates by calling a hardcoded `alloy_eips::eip7840::BlobParams::cancun()` with all-zero inputs, instead of using the chain's actual active blob params at the block's timestamp (as it correctly does for every subsequent block, and as consensus validation does for every block, including this first one). This mirrors the reported analog bug class of "calling the wrong function/parameters for a rate/param calculation," which silently produces a wrong value used downstream for equality checks.

### Finding Description
In the assembler: [1](#0-0) 

```rust
if self.chain_spec.is_cancun_active_at_timestamp(timestamp) {
    block_blob_gas_used = Some(*blob_gas_used);
    excess_blob_gas = if self.chain_spec.is_cancun_active_at_timestamp(parent.timestamp) {
        parent.maybe_next_block_excess_blob_gas(
            self.chain_spec.blob_params_at_timestamp(timestamp),
        )
    } else {
        // for the first post-fork block, both parent.blob_gas_used and
        // parent.excess_blob_gas are evaluated as 0
        Some(
            alloy_eips::eip7840::BlobParams::cancun()
                .next_block_excess_blob_gas_osaka(0, 0, 0),
        )
    };
}
```

The "normal" branch correctly derives the blob params from `self.chain_spec.blob_params_at_timestamp(timestamp)` — i.e., whichever fork (Cancun/Prague/Osaka) is actually active at the block's timestamp. The `else` branch (first post-fork block) instead hardcodes `BlobParams::cancun()` regardless of which fork is actually active, and additionally hardcodes the third argument (base fee) to `0` instead of the parent's actual base fee.

Consensus validation for the same header field does not have this special-case shortcut and always resolves the correct active params and the parent's real base fee: [2](#0-1) 

```rust
let parent_blob_gas_used = parent.blob_gas_used().unwrap_or(0);
let parent_excess_blob_gas = parent.excess_blob_gas().unwrap_or(0);
...
let parent_base_fee_per_gas = parent.base_fee_per_gas().unwrap_or(0);
let expected_excess_blob_gas = blob_params.next_block_excess_blob_gas_osaka(
    parent_excess_blob_gas,
    parent_blob_gas_used,
    parent_base_fee_per_gas,
);
```

where `blob_params` is passed in from the caller in `crates/ethereum/consensus/src/lib.rs`: [3](#0-2) 

```rust
if let Some(blob_params) = self.chain_spec.blob_params_at_timestamp(header.timestamp()) {
    validate_against_parent_4844(header.header(), parent.header(), blob_params)?;
}
```

So validation always uses `blob_params_at_timestamp(header.timestamp())` (whatever fork is active for that block — Cancun, Prague, or Osaka) and the parent's real `base_fee_per_gas`. The assembler's first-post-fork branch instead always uses Cancun's fixed `target_blob_count`/`max_blob_count`/`update_fraction` and a fake `0` base fee, even when Prague/Osaka (with different blob target/max/update-fraction values, as shown by the chain-spec parsing test) is the fork actually active at that timestamp. [4](#0-3) 

This is only latent under mainnet's default schedule (where Cancun, Prague, and Osaka activate at strictly increasing timestamps so the "first-post-fork" boundary block for Cancun is never simultaneously the activation block for a later fork). It is directly triggered on any chain spec where a later blob-schedule fork (Prague/Osaka) is configured to activate at the same timestamp as Cancun — a common pattern for devnets/test chains that enable "all forks from genesis+1", where `is_cancun_active_at_timestamp(timestamp)` and `is_prague_active_at_timestamp(timestamp)` (or Osaka) are both true for the same header.

### Impact Explanation
When triggered, the locally built block's `excess_blob_gas` (computed via the wrong, hardcoded Cancun params/zero base fee) will not match the value `validate_against_parent_4844` expects (computed via the correct active params and real parent base fee). This causes reth's own block-post-execution/header validation to reject a block that reth itself built and is broadcasting/importing — i.e., "a reth-built block that fails its own validation" per the accepted impact classes (High: reth-built blocks rejected, stalling progress until manual intervention on affected chain configurations).

### Likelihood Explanation
The bug is deterministic and always fires under a specific but realistic chain-spec configuration (multiple blob-schedule forks sharing an activation timestamp with Cancun), a pattern common for devnets/testnets and custom network configurations that reth explicitly supports via `ChainSpec`/genesis blob schedule config. It does not require a malicious actor — it is triggered purely by chain configuration and normal block building.

### Recommendation
In `crates/ethereum/evm/src/build.rs`, replace the hardcoded `alloy_eips::eip7840::BlobParams::cancun()` and zero base fee in the `else` branch with the same resolution used in the main branch and in consensus validation:
```rust
Some(
    self.chain_spec
        .blob_params_at_timestamp(timestamp)
        .unwrap_or_else(BlobParams::cancun)
        .next_block_excess_blob_gas_osaka(0, 0, parent.base_fee_per_gas().unwrap_or(0)),
)
```
so the assembler and consensus validation always agree on which blob params and which base fee value to use.

### Proof of Concept
1. Configure a `ChainSpec` where Prague (or Osaka) activates at the exact same timestamp as Cancun (e.g., both set to the same `timestamp` in the hardforks/blob schedule — a supported and non-exotic devnet configuration).
2. Build the first block after genesis (the Cancun/Prague activation boundary) via `EthBlockAssembler::assemble_block`. Because `is_cancun_active_at_timestamp(parent.timestamp)` is `false` while `is_cancun_active_at_timestamp(timestamp)` is `true`, the `else` branch fires and computes `excess_blob_gas` using `BlobParams::cancun()` with `(0,0,0)`.
3. Run `validate_against_parent_4844` (invoked from `EthBeaconConsensus::validate_header_against_parent`) on the same header/parent pair. It resolves `blob_params_at_timestamp(header.timestamp())`, which returns the Prague/Osaka params (different `target_blob_count`/`max_blob_count`/`update_fraction`) and the parent's real base fee, yielding a different `expected_excess_blob_gas`.
4. The mismatch causes `ConsensusError::ExcessBlobGasDiff`, rejecting the block reth itself just built.
