### Title
VRF-seed binding bypass via mislabeled `TenureChangeCause::Extended` on a genuine new-tenure block - ([File: stackslib/src/chainstate/nakamoto/mod.rs, stackslib/src/chainstate/nakamoto/tenure.rs])

### Summary
`NakamotoChainState::append_block` gates the VRF-seed check (`check_block_commit_vrf_seed`) purely on the boolean `is_new_tenure`, which is derived from the block's self-declared `TenureChangePayload.cause` rather than from the actual sortition outcome. `check_nakamoto_tenure`'s validation branch for `TenureChangeCause::Extended` never cross-checks the claimed `tenure_consensus_hash`/`prev_tenure_consensus_hash` against the parent block's actually-recorded ongoing tenure, so a block that is really the first block of a brand-new winning sortition can be labeled `Extended` and skip VRF-seed validation entirely.

### Finding Description
The broken equality is: `is_new_tenure` (computed as `tenure_cause.is_new_tenure()`, i.e. `true` only for `TenureChangeCause::BlockFound`) should equal "this block is actually the first block of a new winning sortition" (i.e. `block.header.consensus_hash` differs from the parent block's ongoing-tenure consensus hash because a new sortition winner was chosen).

Code path:
- `check_block_commit_vrf_seed` is only invoked `if is_new_tenure` [1](#0-0) .
- `is_new_tenure`/`tenure_cause` is taken straight from `block.try_get_tenure_change_payload().cause`, converted via `MinerTenureInfoCause::is_new_tenure()`, which returns `true` only for `BlockFound` [2](#0-1) .
- `check_nakamoto_tenure`'s cause-validation branch enforces cross-consistency with the parent's *actual* recorded tenure (`parent_tenure.tenure_id_consensus_hash`) **only** for `TenureChangeCause::BlockFound`; for `Extended` (and the SIP-034 partial-extend variants) it only checks internal self-consistency (`tenure_consensus_hash == prev_tenure_consensus_hash`), never comparing against `parent_tenure.tenure_id_consensus_hash` [3](#0-2) .
- `advance_nakamoto_tenure` also treats `Extended` as not advancing `coinbase_height`, and the outer append_block check only asserts internal consistency between `is_new_tenure` and `coinbase_height` advancing (both stay flat under the fabricated `Extended` cause, so no error is raised) [4](#0-3) [5](#0-4) .

Attacker's exact input: broadcast a real Bitcoin block-commit that legitimately wins a new sortition (fresh consensus hash, fresh VRF-derived seed), then construct a `NakamotoBlock` whose header consensus_hash is (necessarily) that new, real consensus hash, but whose `TenureChangePayload` sets `cause = TenureChangeCause::Extended` and sets both `tenure_consensus_hash` and `prev_tenure_consensus_hash` equal to that same new consensus hash (satisfying the self-consistency check at tenure.rs:797), instead of pointing `prev_tenure_consensus_hash` at the actual previous tenure as a genuine `BlockFound` would require. As posed in the question, this block still collects valid signer signatures at/above threshold.

Because `check_nakamoto_tenure`'s `Extended` branch never compares the claimed tenure identity against `parent_tenure.tenure_id_consensus_hash` (only `BlockFound` does, at tenure.rs:774-788), this fabricated tenure-change transaction validates successfully. Consequently `is_new_tenure` (as computed for the VRF gate) is `false`, and `check_block_commit_vrf_seed`/`validate_vrf_seed` at mod.rs:5176 is never called for this block, even though it is paired with a genuinely new, distinct winning block-commit whose VRF seed should have been checked against the hash of the prior tenure's VRF proof.

Existing guards checked and found insufficient for this specific path: `check_valid_consensus_hash` only verifies canonicality of a consensus hash, not that it matches the recorded tenure lineage; `check_tenure_continuity` is used only for tenure-tx-less blocks and is not exercised on this path; the coinbase-height self-consistency check at mod.rs:5198-5215 only checks `is_new_tenure` against `coinbase_height` movement — both derived from the same falsified `cause`, so they trivially agree with each other, masking the mismatch against ground truth.

### Impact Explanation
This is a High-severity, minority-triggerable divergence between a signer-approved block's declared tenure semantics and the true sortition state: the VRF-seed binding for an entire tenure is bypassed by chainstate logic that all honest nodes apply identically (deterministic, not a fork/split by itself), but it removes the cryptographic guarantee that the new tenure's leader-election seed is unbiasable/derived correctly from the prior VRF proof. This matches the "minority-triggerable sortition/VRF/static-validation divergence" High category. It also leaves no VRF proof recorded for this tenure (since `vrf_proof_opt` stays `None` under `is_new_tenure=false`), which can desynchronize `get_parent_vrf_proof` lookups for the following genuine new tenure, a secondary correctness hazard whose downstream chain-split potential could not be fully traced within available tool calls.

### Likelihood Explanation
Preconditions: attacker must win an actual Bitcoin sortition (real BTC cost, feasible for a minority miner), and must obtain signer approval (>= threshold weight) for a block whose tenure-change payload cause is falsely labeled `Extended` — the question stipulates this signature validity as a given, so this analysis does not independently verify whether the Stacks signer runtime (out of file scope here) would itself catch the cause/sortition mismatch before signing. Within `stackslib` chainstate alone, no additional gate blocks it. Repeatable once per won sortition where a cooperating/complicit or fooled signer set approves.

### Recommendation
In `check_nakamoto_tenure` (`stackslib/src/chainstate/nakamoto/tenure.rs`), for the `TenureChangeCause::Extended`/SIP-034 extend branch, additionally require `tenure_payload.tenure_consensus_hash == parent_tenure.tenure_id_consensus_hash`, i.e. that an "extend" can only continue the *actual* last recorded tenure, not silently reference a new sortition's consensus hash. Additionally, derive `is_new_tenure` for the VRF-seed gate in `append_block` from the actual sortition/tenure-lineage state (e.g., whether `block.header.consensus_hash` differs from the parent's recorded ongoing tenure id) rather than solely from the attacker/miner-supplied `cause` field.

### Proof of Concept
Rust integration test plan (extending `stackslib/src/chainstate/nakamoto/tests/node.rs` harness):
1. Build a two-tenure Nakamoto chain normally (tenure A, then win a new sortition for tenure B).
2. For tenure B's first block, construct `TenureChangePayload` with `cause = TenureChangeCause::Extended`, `tenure_consensus_hash = prev_tenure_consensus_hash = <tenure B's real consensus hash>` (not tenure A's), while `block.header.consensus_hash` is naturally tenure B's real consensus hash (tied to the real new block-commit/VRF).
3. Assert `NakamotoChainState::check_nakamoto_tenure(...)` returns `Ok(Some(_))` (i.e., wrongly validates) — compare against the equality that should hold: `tenure_payload.tenure_consensus_hash == <parent_tenure>.tenure_id_consensus_hash` (currently unchecked for Extended).
4. Feed this crafted block through `NakamotoChainState::append_block`, and assert `NakamotoChainState::check_block_commit_vrf_seed` is *not* invoked (e.g., by using a deliberately-corrupted VRF seed on the real block-commit and observing the block is still accepted), whereas an honest node applying the recommended fix would reject the tenure-change tx before reaching the VRF gate.
5. Compare processing on node A (unpatched) vs node B (patched with the `parent_tenure` cross-check) to demonstrate the divergence in acceptance/rejection of the same block.

    pub(crate) fn advance_nakamoto_tenure<SH: SortitionHandle>(
        headers_tx: &mut StacksDBTx,
        handle: &mut SH,
        block: &NakamotoBlock,
        parent_coinbase_height: u64,
        do_not_advance: bool,
    ) -> Result<u64, ChainstateError> {
        let Some(tenure_payload) = block.get_tenure_tx_payload() else {
            // no new tenure
            return Ok(parent_coinbase_height);
        };

        let coinbase_height = match tenure_payload.cause {
            TenureChangeCause::BlockFound => {
                // tenure height advances
                parent_coinbase_height
                    .checked_add(1)
                    .expect("FATAL: too many tenures")
            }
            TenureChangeCause::Extended
            | TenureChangeCause::ExtendedRuntime
            | TenureChangeCause::ExtendedReadCount
            | TenureChangeCause::ExtendedReadLength
            | TenureChangeCause::ExtendedWriteCount
            | TenureChangeCause::ExtendedWriteLength => {
                // tenure height does not advance
                parent_coinbase_height
            }
        };
