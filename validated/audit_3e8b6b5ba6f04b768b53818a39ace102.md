## Finding confirmed

### Title
Non-atomic persistence of state-merkle pruner progress lets the on-disk progress key lag behind actually-deleted JMT nodes, causing a restarted node to serve corrupted Merkle proofs for pruned versions - (File: `storage/aptosdb/src/pruner/state_merkle_pruner/mod.rs`, `storage/aptosdb/src/pruner/state_merkle_pruner/state_merkle_metadata_pruner.rs`)

### Summary
`StateMerklePruner::prune` has two branches that both physically delete Jellyfish Merkle nodes in the (possibly sharded) state-merkle DB, but only one of the two branches durably persists the corresponding progress marker. When the "fast" branch is taken - the one hit once stale-index enumeration in `StateMerkleMetadataPruner::maybe_prune_single_version` has already caught up to or exceeded `target_version` - real node deletion happens via `prune_shards`, yet only the in-memory `progress` `AtomicVersion` is advanced, never the `pruner_progress_key` row in the metadata DB. A crash/restart after this point leaves the persisted progress key pointing at an older, lower version than the version actually pruned on disk.

### Finding Description
`StateMerklePruner::prune` (`storage/aptosdb/src/pruner/state_merkle_pruner/mod.rs`, lines 57-92): [1](#0-0) 

- In the `if let Some(...)` branch, `maybe_prune_single_version` both deletes stale metadata-DB nodes and writes the new progress value to `DbMetadataSchema` in the *same* `SchemaBatch`, which is then written atomically: [2](#0-1) 
Crashing before this batch commits leaves progress unchanged (safe); crashing after leaves progress exactly consistent with what was deleted in that batch.

- In the `else` branch (triggered once `next_version` has already advanced past `target_version`, i.e., stale-index enumeration is "ahead" - a state reached routinely once pruning catches up during sustained commit throughput), `prune_shards` still physically deletes stale JMT nodes from the shard DBs for the range `[progress, target_version]`, but the subsequent `self.record_progress(target_version)` call only updates the in-process `AtomicVersion` and a metric - it performs **no disk write**: [3](#0-2) [4](#0-3) 

The only durable copy of pruner progress for this schema lives in the metadata DB's `pruner_progress_key`, written solely inside `maybe_prune_single_version`'s batch. Because the `else` branch performs no such write, if the process is killed/crashes after `prune_shards` in the `else` branch completes but before another `if` branch executes (which would refresh the key), the persisted progress is stale relative to the deletions already committed to the shard DBs.

On restart, `StateMerklePrunerManager::new` (lines 110-138) rebuilds `min_readable_version` from `get_state_merkle_pruner_progress`, which reads exactly this stale, lower on-disk value: [5](#0-4) 

The restarted node therefore believes versions up to the stale (lower) progress are still prunable/available, while the actual JMT nodes for the intervening range are already gone from the shard DBs (deleted by the pre-crash `prune_shards` call in the `else` branch). Any subsequent proof construction or state read for a version in that gap will encounter missing tree nodes.

### Impact Explanation
This is a genuine crash-consistency defect in the pruning progress bookkeeping, not an atomic commit. Because deletion and durable progress-recording are decoupled in the fast-path branch, a node that restarts at the wrong moment can end up with a persisted `min_readable_version` that understates how much state has actually been deleted. Any component that trusts `min_readable_version` (proof serving, state-sync, restore verification, epoch-ending proof queries) can then attempt to read/prove over already-deleted tree nodes, returning an incomplete or malformed Merkle proof for a version the node incorrectly still considers "readable." Since peers that did not crash at that exact instant retain a correct progress marker, this creates state-integrity divergence between nodes for identical committed history - exactly the class of bug in scope (proof-integrity / hard-fork-only divergence from restart, not from a malicious peer).

### Likelihood Explanation
Triggering the vulnerable `else` branch requires only ordinary sustained transaction throughput and pruner catch-up behavior (stale-index enumeration racing ahead of `target_version`), which is a normal condition on any node with active pruning — no special unprivileged transaction crafting is needed beyond generating enough committed write sets to keep the pruner busy. The remaining requirement is a process crash/restart at the specific window between `prune_shards` and the next durable metadata write, which happens on any real-world node restart (upgrade, OOM, crash, SIGKILL) that lands during pruner activity. This is a timing-dependent but realistic and reproducible condition, not dependent on trusted-operator error.

### Recommendation
Persist the progress update in the `else` branch atomically together with (or immediately after) the shard deletions performed by `prune_shards`, mirroring the atomic batch pattern used in `maybe_prune_single_version`. Concretely, `StateMerklePruner::prune`'s `else` branch should write the new progress value to `DbMetadataSchema` under `M::pruner_progress_key()` in the same `SchemaBatch`/write call that commits the shard deletions (or force a synchronous durable write immediately after `prune_shards` succeeds), so that on-disk progress can never lag behind physically deleted nodes.

### Proof of Concept
1. Commit enough write sets so the state-merkle pruner's stale-index cursor (`next_version` in `StateMerkleMetadataPruner`) advances past the current `target_version` at least once, forcing `maybe_prune_single_version` to return `None` and the `else` branch in `StateMerklePruner::prune` to execute (`storage/aptosdb/src/pruner/state_merkle_pruner/mod.rs` lines 82-86).
2. Kill the process immediately after `prune_shards` returns in that branch but before any further call reaches `maybe_prune_single_version`'s batch write (which is the only path that persists `pruner_progress_key`).
3. Restart the node. `StateMerklePrunerManager::new` reconstructs `min_readable_version` from the stale, lower `pruner_progress_key` value on disk via `get_state_merkle_pruner_progress`.
4. Issue a proof/state query for a version in the gap between the stale persisted progress and the actual (higher) version whose nodes were deleted by the pre-crash `prune_shards` call; observe the query fails or returns an incomplete Merkle proof due to missing JMT nodes, while a peer that did not crash at that instant still correctly reports that version as pruned.
