### Title
Receipt size limit is checked before `output_data_receivers` are appended, allowing oversized receipts to bypass `max_receipt_size` - (File: `test-loop-tests/src/tests/max_receipt_size.rs`)

### Summary
Analogous to the `GladiusOrderQuoter` issue — where an unbounded byte blob (`reason`) is accepted without checking it against a maximum size before being used further — nearcore's function-call output path validates a receipt's `max_receipt_size` limit at receipt-construction time, but then mutates the receipt afterward by appending `output_data_receivers`, so the final, wire/borsh-serialized receipt can exceed the very limit that was supposed to bound it. This is explicitly reproduced by existing regression tests referencing the tracked bug near/nearcore#12606.

### Finding Description
`value_return` in the VM logic only checks the returned blob against `max_length_returned_data` [1](#0-0) , and `LimitConfig::max_receipt_size` is meant to bound the total serialized size of any receipt produced during execution [2](#0-1) . However, the test suite in `test-loop-tests/src/tests/max_receipt_size.rs` documents that when a promise's data receipt is produced (via `promise_return`/`value_return`) and then `output_data_receivers` is subsequently attached to route the result to a callback, the resulting receipt's serialized size is computed and validated *before* `output_data_receivers` is added — so the check passes on a receipt that is still within budget, but the final receipt (with the added `output_data_receivers` field) ends up larger than `max_receipt_size`: [3](#0-2) [4](#0-3) 

Both dedicated tests (`test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return`) construct a maximum-size receipt via `return_large_value`/`max_receipt_size_promise_return_method2` and confirm that the produced data receipt or action receipt, once `output_data_receivers` is attached, is bigger than `max_receipt_size`, yet the code path does not reject it: the comment states "The receipt should be rejected, but currently isn't because of a bug" [5](#0-4) .

This mirrors the audit report's root cause exactly: a size-bounding check exists (`ReturnedValueLengthExceeded`/`ReceiptSizeExceeded`, analogous to a "maximum limit of returned bytes"), but it is applied to an earlier, incomplete version of the data, while a later field (`output_data_receivers`, analogous to unconstrained error `reason` bytes) is appended after validation and is not re-checked.

### Impact Explanation
`max_receipt_size` (4 MiB) is a protocol-level invariant relied upon elsewhere in the system: it is used as the upper bound for `max_single_grant` in the bandwidth scheduler [6](#0-5)  and is assumed by cross-shard receipt-forwarding/congestion-control logic to guarantee any single receipt can be scheduled and transmitted within one bandwidth grant. A receipt that silently exceeds `max_receipt_size` after passing the check can violate this assumption for the bandwidth scheduler and receipt storage/serialization paths, which is a transaction/contract-triggered condition (any account can call `return_large_value`-style methods with a maximally sized argument/return blob and chain a callback) — not a validator- or network-layer-only bug. Because this bypass is deterministic given the transaction contents, if any node/version handles the over-limit receipt differently in cross-shard delivery or state-witness accounting than another, this can lead to disagreement in receipt processing or bandwidth-scheduling behavior between nodes, i.e., a chunk/shard-level state-transition/validity discrepancy rather than a mere local resource issue.

### Likelihood Explanation
Likelihood is high in the sense that it is fully reachable by an ordinary function-call transaction from any signer: deploy a contract, call a method that returns a value near `max_length_returned_data`/creates a promise near `max_receipt_size`, and chain a `promise_then`/callback so `output_data_receivers` gets attached post-check. The existing tests demonstrate the exact call sequence that triggers it deterministically [7](#0-6) [8](#0-7) .

### Recommendation
Compute and enforce `max_receipt_size` on the fully-finalized receipt — i.e., after `output_data_receivers` (and any other post-construction fields) are attached — rather than on an intermediate receipt snapshot. Alternatively, reserve budget for `output_data_receivers` up front (similar to how `max_receipt_total_input_size` already reserves per-input framing overhead [9](#0-8) ) so the check performed before mutation remains a sound upper bound after mutation.

### Proof of Concept
Use the existing regression tests as the PoC skeleton: [10](#0-9) [11](#0-10) 
1. Deploy `near_test_contracts::rs_contract()`.
2. Call `max_receipt_size_promise_return_method1` (or `max_receipt_size_value_return_method`) with an `args_size`/`value_size` sized so the produced receipt is exactly at `max_receipt_size` (4_194_304 bytes) before `output_data_receivers` is attached.
3. Observe (per the test's own assertions, `assert_oversized_receipt_occurred`) that the resulting receipt on chain exceeds `max_receipt_size` despite the size check having passed.

Note: I could not locate the definition of `assert_oversized_receipt_occurred` or the exact receipt-validation function (`validate_receipt`) within the indexed portion of the codebase to pinpoint the precise line where the check is performed relative to the `output_data_receivers` mutation; this may be due to index size limits excluding some file contents. fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
