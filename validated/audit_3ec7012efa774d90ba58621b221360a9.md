### Title
`TransactionOutput::ensure_match_transaction_info` skips state-checkpoint hash validation, letting a diverged post-state root pass replay/proof verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs`) and the Aptos debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a locally re-executed `TransactionOutput` matches an authenticated `TransactionInfo` taken from chain/backup data. The function checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually commit to the resulting state tree / Merkle root. This is called out in the code itself as a known gap.

### Finding Description [1](#0-0) 

The function computes and compares:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash = CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but the trailing comment states plainly:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

`state_checkpoint_hash` is the field in `TransactionInfo` that binds a transaction's execution to the resulting Jellyfish-Merkle state root (analogous to `hot_state_checkpoint_hash` for the hot-state tree and `position_state_checkpoint_hash` for the position tree). None of these are recomputed or compared here, so `ensure_match_transaction_info` only verifies write-set *content* hash and event hash — never the derived, authenticated state root that the write set is supposed to produce.

`storage/db-tool/src/replay_on_archive.rs::execute_and_verify` re-executes historical transactions with `AptosVMBlockExecutor` and calls exactly this function to decide whether replay matches the archived, signature/proof-authenticated `TransactionInfo`: [3](#0-2) 

Because the state/hot-state/position checkpoint hashes are skipped, if local execution produces the correct write set (and thus correct `state_change_hash`/event hash) but a downstream state-tree construction/commit step diverges (e.g., a bug in Jellyfish Merkle insertion, hot-state promotion, or position-tree update that is independent of the write-set bytes themselves), `replay_on_archive` and the debugger's replay-check will report success even though the actual resulting Merkle/state root differs from the one referenced by the authenticated `TransactionInfo`/ledger info.

This is the same integrity-invariant class as the external report: a validation short-circuit ("skip checking the thing that actually matters") lets a divergent/incorrect internal value pass a gate meant to catch it — except here the missed field is a cryptographic commitment to ledger state, not an ERC-20 balance.

### Impact Explanation
This breaks the "committed state must match VM result" and "state proof must be validated against the correct root" invariants required by the State-Integrity Gate. Concretely:
- Replay-verification (used to certify that an archived/backed-up chain segment is correct, e.g., before promoting a snapshot or auditing a segment for a hard fork) can silently pass even when the state root diverges from correct VM execution, because the only fields compared are write-set hash, event hash, gas, and status — not the state/hot-state/position checkpoint hash.
- This is exactly a "hard-fork-only divergence during commit, replay, restore, or proof verification" scenario: a bug that corrupts state-tree construction without corrupting the write set itself would be undetectable by this check, meaning corrupted ledger state could be accepted as verified.
- Since `ensure_match_transaction_info` is the authoritative "does my re-execution match the trusted record" comparator used by the primary replay/debug tooling, and it is gated behind not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, the checkpoint-hash-producing code paths it's meant to protect are apparently being staged without the corresponding verification, which is a real gap today rather than a hypothetical one.

### Likelihood Explanation
Likelihood is moderate: this doesn't require an attacker action per se — it's a validation completeness bug that manifests only when there is a genuine divergence between the write set/events and the derived state root (e.g., a bug in state-checkpoint-hash computation, hot-state or position-tree update logic). The report itself documents that this must be fixed before the associated feature is turned on, indicating the authors are aware the state-root-producing code is not yet verified end-to-end by this comparator. Until `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and its associated state/hot-state/position mechanisms are fully wired up and exercised, this gap means any bug in those newer code paths would go undetected by the standard replay-verify safety net.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the given `TransactionInfo`) against the actual post-execution state/hot-state/position roots, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, as the existing TODO comment specifies. This closes the gap where write-set/event equality is treated as sufficient proof that the derived ledger state matches.

### Proof of Concept
Not independently reproducible from static analysis alone — the gap is a missing check rather than an active exploit path, and requires an actual bug in state/hot-state/position-tree construction to manifest as an undetected divergence. The concrete evidence is the code-level analysis above: `ensure_match_transaction_info` at [1](#0-0)  never reads `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` from `txn_info`, and its only two callers used for verification, [3](#0-2)  and the debugger/cli usages, rely on it as the sole pass/fail gate for replay correctness.

**Note on confidence:** I could not fully trace whether `state_checkpoint_hash` is independently validated by some *other* code path during normal consensus commit (outside `ensure_match_transaction_info`) that would make this specific comparator redundant for mainnet safety — the tool-call budget was exhausted before I could confirm that. The TODO comment itself, however, explicitly states this is a real, acknowledged gap in the replay-verify path, which is the basis for this finding.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
