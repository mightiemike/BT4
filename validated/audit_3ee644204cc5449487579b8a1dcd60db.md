The self-documented gap I found in `types/src/transaction/mod.rs` is a genuine, real integrity check gap in Aptos's own replay/verify tooling, not a restated GitHub Actions issue.

### Title
Replay-verification bypasses state/hot-state checkpoint hash comparison, allowing corrupted authenticated state roots to pass as valid replays - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole function used by chunk-executor state-sync verification, the replayer's `verify_execution`, `db-tool`'s `replay_on_archive`, and `aptos-debugger`'s mismatch printer to confirm that a locally re-executed transaction's output matches the trusted, proof-carrying `TransactionInfo`. This function checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check the state checkpoint hash / hot-state checkpoint hash / `position_state_checkpoint_hash` fields carried in `TransactionInfo`, a gap the code itself documents with a `TODO(trading-native)` comment.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  verifies four fields (status, gas, write-set hash, event root hash) but ends with an explicit comment stating the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [2](#0-1) 

This same function is the integrity gate used in three independent verification paths:
- Chunk replay verification (`verify_execution` in the chunk executor), which drives consensus-critical resync/replay correctness: [3](#0-2) 
- The archive replay tool used to validate historical ledger integrity: [4](#0-3) 
- The debugger's mismatch detection used by operators to detect divergence: [5](#0-4) 

`TransactionInfo` carries dedicated fields for the state checkpoint and (with the trading-native / hot-state feature) additional checkpoint hashes that authenticate the post-transaction state tree root, distinct from the write-set hash. Because none of the three consumers cross-check these checkpoint-hash fields, any divergence between the locally computed state/hot-state root and the authenticated `TransactionInfo`'s checkpoint hash is invisible to replay verification. This means a bug in state summary/checkpoint computation (e.g., in `do_state_checkpoint.rs` or the "trading native"/position-state summary path referenced in `execution/executor/src/block_executor/mod.rs`) could silently produce a wrong state root that is never caught by any of the standard verification tools, even though the write set and events are correct.

### Impact Explanation
This breaks the proof-and-storage-pivot invariant that "Accumulators, Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding" and that committed state must match the correct VM result. If the checkpoint/hot-state root computation diverges from consensus (a hard-fork-class bug, feature bug, or non-determinism in the new "trading native state roots" / hot-state code paths), archive replay-verify (`db-tool replay-on-archive`), chunk-executor verified replay, and the debugger mismatch detector would all report a clean, matching replay despite a corrupted state root being committed to storage. This is exactly the class of "hard-fork-only divergence during commit, replay, or proof verification" and "wrong ... state proof accepted as valid" that the state-integrity gate is scoped to catch, since it defeats the safety net meant to detect such divergence.

### Likelihood Explanation
This requires a pre-existing bug in state/hot-state checkpoint hash computation to have real-world effect (it is a verification gap, not by itself a state-corruption trigger). However, the surrounding code (`compute_trading_native_state_roots`, `ProvablePositionStateSummary`, hot-state feature flags) is clearly active, in-development functionality, i.e. exactly the kind of new consensus-affecting logic most likely to contain such a divergence bug. The comment is written by the Aptos team itself, confirming they are aware the gap exists and consider it a real risk("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges"). No privileged access is needed to trigger a divergence; it just requires a code-level bug in checkpoint computation somewhere in the executor.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `txn_info.state_checkpoint_hash()` (and, when the hot-state/trading-native features are enabled, the hot-state and `position_state_checkpoint_hash` fields) against the locally computed values before returning `Ok(())`. Until this is done, none of chunk-executor replay verification, `db-tool replay-on-archive`, or the debugger's mismatch printer can be relied upon to detect state-root corruption, only write-set/event corruption.

### Proof of Concept
Conceptual: instrument or introduce a divergence in the hot-state/position-state checkpoint hash computation (e.g., in `DoStateCheckpoint::run` or `ProvablePositionStateSummary::new_persisted`, referenced from `execution/executor/src/block_executor/mod.rs` lines 355-372) so the locally computed checkpoint hash differs from the one embedded in the trusted `TransactionInfo`, while write set and events remain identical. Run `db-tool replay-on-archive` or the chunk executor's `verify_execution` over the affected version range; because `ensure_match_transaction_info` never inspects the checkpoint hash fields, replay reports success despite the state root mismatch.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
