## Analysis: Race condition in mempool-based validation skip for invoke transactions

### Title
Time-of-check/time-of-use race condition in `skip_stateful_validations` allows invoke transaction to execute without `__validate__` signature check - (File: `crates/apollo_gateway/src/stateful_transaction_validator.rs`)

### Summary
The gateway's stateful validation decides whether to skip the account's `__validate__` entrypoint for an invoke transaction based on a transient, point-in-time check of whether a corresponding `deploy_account` transaction currently exists in the mempool. Because this check and the transaction's actual admission/execution are not atomic, the underlying mempool state that justified skipping validation can change (the `deploy_account` tx can be evicted, replaced, or expire) between the check and the time the invoke transaction is actually included, producing a decision based on stale information — the same "parameters can change while in flight" race-condition class as the reported Teller `lenderAcceptBid` bug.

### Finding Description
When the gateway processes an invoke transaction with `nonce == 1` while the account's on-chain nonce is `0`, it calls `skip_stateful_validations`, which asks the mempool whether a `deploy_account` transaction for that sender is currently `in pool or recent block` via `account_tx_in_pool_or_recent_block`: [1](#0-0) 

If this returns `true`, the gateway sets `execution_flags.validate = false` for the invoke transaction (`skip_validate` propagated into `run_validate_entry_point`), meaning the account's `__validate__` (signature check) entrypoint will not run for this transaction: [2](#0-1) 

The check itself is implemented as a simple, momentary lookup against the mempool's internal `staged`/`committed` map and pool contents: [3](#0-2) 

This decision is made once, at gateway admission time, and cached into the transaction's `ExecutionFlags`. However, the actual `deploy_account` transaction that justified skipping validation can be removed from the mempool afterward through independent code paths — for example fee-escalation replacement (`remove_replaced_tx`), capacity eviction (`handle_capacity_overflow`), or expiration (`remove_expired_txs`) — all of which run inside `add_tx`/`add_tx_inner` for unrelated, later-arriving transactions: [4](#0-3) 

In FIFO mode, the mempool additionally queues *all* transactions for execution eligibility immediately, without enforcing nonce ordering at the mempool layer: [5](#0-4) 

Because the "skip validate" decision was taken and baked into the transaction's flags before this later eviction, the invoke transaction can reach block execution with `validate: false` even though the `deploy_account` transaction it was piggy-backing on never lands in the mempool/block anymore.

### Impact Explanation
If the deploy-account precondition becomes false after the skip decision is cached, an invoke transaction can be executed with the account's `__validate__` (signature verification) entrypoint bypassed. Depending on interplay with `perform_pre_validation_stage`'s nonce check in the blockifier, this can allow a transaction to reach `__execute__` without signature verification, i.e., an unauthorized account action — the security guarantee that a transaction be authorized by the account owner is undermined for a class of transactions whose "skip validation" eligibility was determined by transient mempool contents rather than a hard, consensus-safe precondition.

### Likelihood Explanation
Reachable by an unprivileged sender: submit a `deploy_account` tx followed immediately by a dependent `invoke` tx (a common UX pattern this feature exists to support), then trigger removal of the `deploy_account` tx from the mempool (e.g., another account/sender causing capacity pressure, fee-escalation replacement, or waiting out expiration) before the `deploy_account` tx is actually included. No special privileges, only ordinary transaction submission, are required to attempt this race.

### Recommendation
Do not cache the "skip validate" decision based on a point-in-time mempool snapshot. Re-verify the deploy-account precondition (or otherwise gate `__execute__`/`__validate__` skip) at the point of actual inclusion/execution rather than only at gateway admission, or make the invoke transaction's eligibility for the queue strictly conditioned on the `deploy_account` transaction still being present/committed at commit time, not merely "was present when checked."

### Proof of Concept
1. Attacker submits `deploy_account` tx A for account `X` (nonce 0) and, immediately after, an `invoke` tx B for `X` with nonce 1.
2. Gateway processes B: `skip_stateful_validations` checks `account_tx_in_pool_or_recent_block(X)`, finds A present, returns `true` → B is marked `validate: false`.
3. Before A is included in a block, cause A to be evicted from the mempool (e.g., submit a fee-escalated replacement for A's slot from a colluding sender path, or exploit capacity eviction / expiration timing against A).
4. B, still carrying `validate: false`, is eventually pulled for execution (particularly straightforward in FIFO mode where nonce ordering is not enforced at the mempool layer) without A ever being committed, executing `__execute__` for B without having run `__validate__`.

/// Check if validation of an invoke transaction should be skipped due to deploy_account not being
/// processed yet. This feature is used to improve UX for users sending deploy_account + invoke at
/// once.
async fn skip_stateful_validations(
    tx: &ExecutableTransaction,
    account_nonce: Nonce,
    mempool_client: SharedMempoolClient,
) -> StatefulTransactionValidatorResult<bool> {
    if let ExecutableTransaction::Invoke(ExecutableInvokeTransaction { tx, .. }) = tx {
        // check if the transaction nonce is 1, meaning it is post deploy_account, and the
        // account nonce is zero, meaning the account was not deployed yet.
        if tx.nonce() == Nonce(Felt::ONE) && account_nonce == Nonce(Felt::ZERO) {
            let account_address = tx.sender_address();
            debug!("Checking if deploy_account transaction exists for account {account_address}.");
            // We verify that a deploy_account transaction exists for this account. It is sufficient
            // to check if the account exists in the mempool since it means that either it has a
            // deploy_account transaction or transactions with future nonces that passed
            // validations.
            return mempool_client
                .account_tx_in_pool_or_recent_block(tx.sender_address())
                .await
                .map_err(|err| mempool_client_err_to_deprecated_gw_err(&tx.signature(), err))
                .inspect(|exists| {
                    if *exists {
                        debug!("Found deploy_account transaction for account {account_address}.");
                    } else {
                        debug!(
                            "No deploy_account transaction found for account {account_address}."
                        );
                    }
                });
        }
    }

    Ok(false)
}
