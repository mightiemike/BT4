### Title
Wallet Contract fails to refund external caller's attached deposit when the address-registrar lookup or NEP-141 storage-balance check fails, permanently freezing user funds - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (NEP-518) accepts an attached NEAR deposit from an external, non-owner caller (typically a relayer) when invoking `rlp_execute`, and is supposed to refund that deposit if the resulting cross-contract call fails. However, this refund is only implemented in the final `rlp_execute_callback`. Two intermediate callbacks that also observe a failed promise — `address_check_callback` and `nep_141_storage_balance_callback` — return an error response without refunding the tracked `CallerDeposit`, permanently trapping the caller's attached NEAR tokens in the wallet contract.

### Finding Description
`CallerDeposit::new` records the attached deposit of any *external* (non-self) caller of `rlp_execute` so it can later be refunded if the requested action fails [1](#0-0) .

For a plain base-token transfer or generic action, the deposit-refund guarantee is honored: `rlp_execute_callback` explicitly transfers the tracked deposit back to `caller_deposit.account_id` when `env::promise_result(0)` is `PromiseResult::Failed` [2](#0-1) .

But for two other transaction kinds handled by `inner_rlp_execute`, the flow instead routes through intermediate callbacks that swallow the failure without ever refunding `caller_deposit`:

- When the target is an eth-implicit account requiring an address-registrar check, `inner_rlp_execute` schedules `address_check_callback` carrying `caller_deposit` [3](#0-2) . If the call to the registrar contract fails, `address_check_callback` simply returns an error `ExecuteResponse` and drops `caller_deposit` on the floor — no refund promise is created [4](#0-3) .
- When the target is an emulated ERC-20 transfer, `inner_rlp_execute` schedules `nep_141_storage_balance_callback`, again carrying `caller_deposit` [5](#0-4) . If the call to the token contract's `storage_balance_of` fails, the callback returns an error `ExecuteResponse` and, likewise, never issues a refund of `caller_deposit` [6](#0-5) .

In both cases the deposit that was attached to the original `FunctionCall` receipt calling `rlp_execute` has already been credited to the Wallet Contract account's balance by the NEAR runtime's normal `Transfer`/deposit-crediting mechanics before the contract logic runs; it is now indistinguishable from the account's own balance and there is no code path in the contract that can move it back out to the original caller once these branches are taken. Exactly like `UXDController`, which can `receive()` ETH but has no code path to send it back out, the Wallet Contract can *receive* an external caller's deposit through these two specific failure branches but has no corresponding refund logic, so the funds are permanently stuck in the wallet account (an eth-implicit account that only `rlp_execute` — signed by the ETH-implicit owner's secp256k1 key — can move funds from, and which has no operation to "return an arbitrary leftover deposit to a past caller").

### Impact Explanation
Any unprivileged relayer/caller who attaches a NEAR deposit while calling `rlp_execute` on someone else's ETH-implicit Wallet Contract account risks having that deposit permanently frozen if the eth-tx being relayed happens to be (a) a base-token transfer to another eth-implicit account (triggering the registrar address-check path) or (b) an emulated ERC-20 transfer (triggering the NEP-141 storage-balance-check path), and the corresponding cross-contract call to the registrar/token contract fails (e.g., insufficient gas, target contract paused/upgraded, temporary unavailability, or the registrar/token account not existing). This is a protocol-shipped contract (`near-wallet-contract`), so this is a systemic loss-of-funds bug affecting every relayer that funds transaction execution this way, not a user configuration mistake. This matches the reported class: "contract receives value but has no way to withdraw it," resulting in concretely and permanently frozen user funds.

### Likelihood Explanation
This is reachable purely from a signed NEAR `FunctionCall` transaction to `rlp_execute` with a nonzero attached deposit sent by any external account (no special privileges, validator status, or malicious peer/node behavior needed) — exactly the "relayer pays deposit" pattern demonstrated by the project's own `rlp_execute_from` test helper and `test_caller_refunds`/`test_base_token_transfer_with_relayer_refund` tests [7](#0-6) . Any transient failure of the downstream registrar/NEP-141 call (which relayers do not fully control) is sufficient to trigger permanent loss, making this readily triggerable in normal relayer operation, not merely a contrived edge case.

### Recommendation
Refund `caller_deposit` in the `PromiseResult::Failed` branches of both `address_check_callback` and `nep_141_storage_balance_callback`, mirroring the refund logic already present in `rlp_execute_callback`, so that an external caller's attached deposit is always returned whenever the requested action ultimately fails, regardless of which intermediate callback observes the failure.

### Proof of Concept
1. An eth-implicit Wallet Contract account `A` is deployed and its owner signs an Ethereum-formatted base-token-transfer transaction whose `to` is another eth-implicit address `B` that is not yet a known/verified eth-implicit account, forcing `parse_rlp_tx_to_action` to set `EOABaseTokenTransfer { address_check: Some(address), .. }`.
2. A relayer `R` (unprivileged external account) submits a NEAR `FunctionCall` to `A.rlp_execute(target, tx_bytes_b64)` with a nonzero `deposit` attached (as in `rlp_execute_from`), so `CallerDeposit::new` records `{ account_id: R, yocto_near: deposit }` [1](#0-0) .
3. `inner_rlp_execute` schedules a cross-contract call to the address-registrar contract followed by `address_check_callback(target, action, caller_deposit)` [3](#0-2) .
4. If the registrar call fails for any reason (e.g. the registrar account is temporarily unavailable, out of gas, or misconfigured), `address_check_callback` hits the `PromiseResult::Failed` branch and returns an error response without creating any refund promise for `caller_deposit` [8](#0-7) .
5. `R`'s attached deposit, already credited to `A`'s account balance by the runtime, remains there permanently: no subsequent call path in the Wallet Contract exposes a way to return it, exactly as with `UXDController`'s unrecoverable stray ETH.
