Confirmed: `check.domain` (the `X-Shopify-Shop-Domain` header) is used directly as the shop identity to load the offline session and issue an admin client, with no cryptographic link between that header and the HMAC that was actually validated.

### Title
Webhook HMAC signature omits the shop-domain header from the signed payload, allowing cross-tenant webhook forgery/replay - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
`shopify-app-js` validates inbound Shopify webhooks by computing an HMAC over the raw request body alone and comparing it to the `X-Shopify-Hmac-Sha256` header value, exactly as EIP-155 legacy transactions can be signed without binding to `chainId`. The shop-identifying header (`X-Shopify-Shop-Domain`) is never included in the signed material, so any valid `(rawBody, hmac)` pair — signed once with the app's single, app-wide `apiSecretKey` — remains valid no matter which shop domain header accompanies it on replay.

### Finding Description
`validateHmacFromRequestFactory` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` (lines 168-201) reads the raw body and the `hmac` header, then calls `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` (lines 153-162), which HMACs only `rawBody` with `config.apiSecretKey`.
<cite repo="Thankgoddavid56/shopify-app-js--004" path="packages/apps/shopify-api/lib/utils/hmac-validator.ts" start="185-197" end="185-197" />
The `apiSecretKey` is a single, app-wide secret shared across every shop that installs the app — it is not shop-specific. The domain, topic, and webhook-id headers are only checked for *presence*, not incorporated into the signature, in `checkWebhookHeaders`/`checkWebhooksHeaders` in `packages/apps/shopify-api/lib/webhooks/validate.ts`: [1](#0-0) [2](#0-1) 
Downstream, `authenticateWebhookFactory` in both `shopify-app-remix` and `shopify-app-react-router` trusts `check.domain` (sourced straight from the unauthenticated header) to look up the merchant's offline session and construct an authenticated Admin API client for that shop: [3](#0-2) 
Because the signature never binds to the domain, an attacker who can obtain one legitimately-signed `(rawBody, hmac)` pair (e.g., from a shop they themselves install the app on, or any shop-agnostic webhook topic/body) can resend that exact body and HMAC to the app's webhook endpoint while substituting a different `X-Shopify-Shop-Domain` value. The HMAC check still passes (it only ever validated the body), and the webhook handler proceeds to load session/admin context for the *forged* domain — this is the direct analog of the EIP-155 finding, where `reserved[0]==0` lets the signer drop chain-id binding from the signed data and lets a signature be replayed across an unintended context.

### Impact Explanation
An attacker with any app installation (a "single merchant" actor, not privileged) can harvest one valid `(body, hmac)` pair from their own shop's webhook deliveries and replay it against the shared webhook endpoint with a spoofed domain header for a victim shop that also has the app installed. Because `check.domain` is used unauthenticated to select the offline session and mint an Admin API client, this enables cross-tenant confusion: forged webhook events processed under another merchant's session context, and denial-of-service/data-poisoning of that merchant's webhook handler logic (e.g., triggering `orders/create`, `app/uninstalled`, or GDPR handlers against the wrong shop with attacker-chosen body content, as long as the body was originally validly signed for the attacker's own shop).

### Likelihood Explanation
The domain header is trivial for an anonymous HTTP client to control (it's not authenticated by the HMAC), and the `apiSecretKey` is intentionally shared across shops by design (there's no per-shop webhook secret in this scheme), so any existing app installer can produce inputs that satisfy this condition. The main constraint is that the replayed body's semantic content still refers to the attacker's own shop's data unless a shop-agnostic/empty-body topic is used, which somewhat limits practical exploitation but does not require any secret leakage or MITM — only standard app install access.

### Recommendation
Bind the shop domain (and preferably topic/webhook-id) into the material that is authenticated, not just checked for presence. Concretely: include the `X-Shopify-Shop-Domain` header value in the HMAC input (e.g., mimic the app-proxy signator's approach of stringifying an ordered parameter set that includes shop/domain before hashing), or, at minimum, cross-check that a successfully validated webhook's declared `domain` corresponds to the actual originating request context via an independent trust boundary (e.g., per-shop signing secrets or mTLS from the webhook relay) rather than trusting a client-suppliable header once an app-wide HMAC has passed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook (e.g., `orders/create`) with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed as `HMAC-SHA256(apiSecretKey, B)`), where `apiSecretKey` is the same value for every install of this app.
2. Attacker resends `POST /webhooks` with the exact same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and adjusts `X-Shopify-Topic`/`X-Shopify-Webhook-Id` freely, since these aren't signed either).
3. `validateHmacFromRequestFactory` recomputes `HMAC-SHA256(apiSecretKey, B)`, which still equals `H`, so `check.valid === true` and `check.domain === 'victim-shop.myshopify.com'`.
4. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, 'victim-shop.myshopify.com')`, loading the victim's stored offline session/access token and processing the attacker-controlled payload `B` as if it were an authentic event for the victim shop.
