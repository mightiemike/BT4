### Title
Unbounded `UniversalPayload.GasLimit` accepted from a gasless, unprivileged `MsgExecutePayload` allows unmetered EVM gas limits to reach `DerivedEVMCall` - (File: x/uexecutor/keeper/evm.go)

### Summary
`MsgExecutePayload` is in the gasless allowlist and can be submitted by "any" unprivileged account [1](#0-0) . Its `UniversalPayload.GasLimit` field is a free-form uint256 decimal string whose only validation is "parses as a non-negative integer" [2](#0-1) . That unbounded value is parsed straight into a `*big.Int` and handed to `DerivedEVMCall` as the EVM call's explicit gas limit with no upper-bound check against the block gas limit or any sane maximum [3](#0-2) .

### Finding Description
The report's bug class is "unbounded/invalidly-bounded parameters cause undefined behavior." The Push Chain analog is the `gas_limit` field of `UniversalPayload`, which flows through `MsgExecutePayload` (gasless, callable by "any" signer per the module's own README) into `CallUEAExecutePayload`:

```go
gasLimit := new(big.Int)
gasLimit, ok := gasLimit.SetString(universal_payload.GasLimit, 10)
if !ok {
    return nil, fmt.Errorf("invalid gas limit: %s", universal_payload.GasLimit)
}
return k.evmKeeper.DerivedEVMCall(ctx, abi, from, ueaAddr, big.NewInt(0), gasLimit, true, false, false, nil, "executeUniversalTx", abiUniversalPayload, verificationData)
``` [3](#0-2) 

`UniversalPayload.ValidateBasic` only checks that `gas_limit` parses as a non-negative big integer — there is no ceiling check (e.g., against the chain's max block gas or `math.MaxUint64`):

```go
for fieldName, value := range uintFields {
    if value != "" {
        bi, ok := new(big.Int).SetString(value, 10)
        if !ok || bi.Sign() < 0 {
            return errors.Wrapf(sdkerrors.ErrInvalidRequest, "%s must be a valid unsigned integer", fieldName)
        }
    }
}
``` [2](#0-1) 

`MsgExecutePayload` skips the normal Cosmos min-gas-price and fee-deduction ante checks entirely because it is in the gasless allowlist:

```go
GaslessMsgTypes = []string{
    ...
    sdk.MsgTypeURL(&uexecutortypes.MsgExecutePayload{}),
    ...
}
``` [4](#0-3) 

and the README explicitly documents that any account may submit it at no Cosmos-fee cost, with the actual gas billed only to the (potentially attacker-controlled/unfunded) UEA post-hoc:

> "Any account may submit the message. ... The actual EVM execution gas is deducted from this UEA's balance." [5](#0-4) 

Fee accounting only bills for `receipt.GasUsed` (actual consumption), never the caller-supplied `GasLimit`:
```go
gasCost, err := k.CalculateGasCost(baseFee, abiPayload.MaxFeePerGas, abiPayload.MaxPriorityFeePerGas, receipt.GasUsed)
``` [6](#0-5) 

This means the value that gates how much computation the EVM is *allowed* to run (`gasLimit` passed to `DerivedEVMCall`) is fully attacker-controlled and unbounded, while the value that determines what the attacker actually *pays* is decoupled and based only on real consumption. There is no cross-check anywhere in `x/uexecutor` (msg_execute_payload.go, execute_payload.go, evm.go) capping `GasLimit` to the chain's configured EVM block gas limit before it is passed into `DerivedEVMCall`.

### Impact Explanation
If the underlying `DerivedEVMCall`/EVM execution path does not itself independently clamp the caller-supplied gas limit to the consensus block gas limit (this repository does not contain that clamp — it lives in the vendored cosmos-evm fork, which was not fully inspectable here), an unprivileged, unfunded/minimally-funded attacker can submit a free (gasless) `MsgExecutePayload` with an astronomically large `gas_limit` (up to `2^256-1`) targeting any UEA, including one they do not control and cannot pay for. Because the tx is gasless, the attacker pays no Cosmos fee to attempt this, and the only enforcement gate is checking whether `receipt.GasUsed` (after execution) exceeds `abiPayload.GasLimit` — which happens only after the EVM has already run with the caller-supplied cap. This is a denial-of-service surface reachable purely by "unprivileged user actions" (submitting a whitelisted gasless message with an unbounded numeric field), matching the "denial of service ... not network-level and reachable without privileged control" allowed-impact class.

### Likelihood Explanation
Medium-to-low confidence without being able to inspect the vendored `cosmos-evm` fork's `DerivedEVMCall` implementation to confirm whether it clamps the supplied `gasLimit` to the consensus/block gas limit before execution. If it does clamp (as stock go-ethereum/cosmos-evm typically does at the block-gas-pool level), the practical DoS is bounded and this degrades to a lower-severity "no input validation" data-quality issue rather than a genuine resource-exhaustion bug. If it does not clamp for module/derived calls specifically (since `DerivedEVMCall` is a Push-Chain-fork-specific code path distinct from normal `MsgEthereumTx` block-gas accounting, per `DERIVED_TRANSACTIONS.md`), the DoS is directly reachable by any address, for free, repeatedly. This uncertainty should be resolved by inspecting the fork's `DerivedEVMCall` gas-pool integration before treating this as high severity.

### Recommendation
Add an explicit upper bound to `UniversalPayload.ValidateBasic` (and/or `MsgExecutePayload.ValidateBasic`) for `gas_limit`, `max_fee_per_gas`, and `max_priority_fee_per_gas`, e.g. capping `gas_limit` to the chain's configured EVM block gas limit (or a fixed sane ceiling such as the block gas limit minus overhead) before it is ever passed to `CallUEAExecutePayload`/`DerivedEVMCall`. Reject payloads whose `gas_limit` exceeds this bound with a clear error, mirroring the standard `MsgEthereumTx` gas-limit-vs-block-gas-limit check that would apply to a normal Ethereum transaction.

### Proof of Concept
1. Attacker (any funded-or-unfunded Cosmos account) constructs a `MsgExecutePayload` targeting an arbitrary `UniversalAccountId` (does not need to be the attacker's own UEA — the module deliberately allows `Signer != Owner`, per `x/uexecutor/README.md` lines 211-237).
2. Set `UniversalPayload.GasLimit = "115792089237316195423570985008687907853269984665640564039457584007913129639935"` (i.e. `2^256-1`), which passes `ValidateBasic` because it only checks non-negativity.
3. Submit as a gasless transaction — `MsgExecutePayload` is in `app/txpolicy/gasless.go`'s allowlist, so `MinGasPriceDecorator` and `DeductFeeDecorator` are both skipped, and the submission costs the attacker nothing.
4. `ExecutePayload` → `CallUEAExecutePayload` parses this string directly into a `*big.Int` and forwards it as the explicit `gasLimit` argument to `DerivedEVMCall` [3](#0-2) .
5. Whether this produces a practical resource-exhaustion DoS depends on whether the vendored EVM keeper's `DerivedEVMCall` independently caps the gas limit to the consensus block gas limit — this could not be confirmed from the code available in this repository and should be verified directly.

### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
