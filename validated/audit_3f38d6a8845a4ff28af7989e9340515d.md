### Title
Division-by-zero panic in energy-limit calculation via unguarded `totalEnergyWeight` denominator - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` and the legacy branch of `EnergyProcessor.calculateGlobalEnergyLimit` divide by the global state variable `totalEnergyWeight` while only "protecting" the zero case with a Java `assert` statement, which is a no-op unless the JVM is started with `-ea`. This mirrors the InfiniFi `slashIndex` bug class: a critical accounting denominator that can legitimately fall to `0` is not defensively checked before being used as a divisor, so a division-by-zero can be reached through normal execution paths (TVM energy accounting) rather than through privileged/administrative action.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` computes the account's energy limit as `totalEnergyLimit / totalEnergyWeight` (via `BigInteger.divide` when `hardenResourceCalculation()` is enabled, or via double division otherwise): [1](#0-0) 

The only guard against `totalEnergyWeight == 0` is:
```java
assert totalEnergyWeight > 0;
```
which does nothing in a production JVM (assertions are disabled by default), so execution falls through to:
```java
BigInteger.valueOf(energyWeight)
    .multiply(BigInteger.valueOf(totalEnergyLimit))
    .divide(BigInteger.valueOf(totalEnergyWeight))
    .longValueExact();
```
`BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException: BigInteger divide by 0`, exactly analogous to the Solidity panic caused by `_rewardWeight.divWadDown(slashIndex)` when `slashIndex == 0`.

The same pattern exists in the pre-`supportUnfreezeDelay` branch of `EnergyProcessor.calculateGlobalEnergyLimit`: [2](#0-1) 
Here, the explicit zero-check is only executed when `dynamicPropertiesStore.allowNewReward()` is true (`if (... && totalEnergyWeight <= 0) return 0;`); otherwise the code falls to the same no-op `assert totalEnergyWeight > 0;` before doing the division/BigInteger divide in `calculateGlobalLimitV1`.

By contrast, the bandwidth analog explicitly and unconditionally guards the same kind of denominator regardless of feature-flag state: [3](#0-2) 
and the V2 (post-`supportUnfreezeDelay`) energy path also has an unconditional guard: [4](#0-3) 

This inconsistency — where `BandwidthProcessor` and the energy V2 path were hardened with an unconditional `if (totalWeight == 0) return 0;` check but the legacy energy path and `RepositoryImpl`'s VM-facing copy were not — is the direct structural analog of the InfiniFi report: a shared "weight/index" denominator is protected in some code paths but not others, and the unprotected path can divide by zero when the denominator legitimately reaches `0` (e.g., if the total frozen balance backing energy, `totalEnergyWeight`, drops to zero because no account currently has ENERGY frozen/delegated).

### Impact Explanation
If `totalEnergyWeight` becomes `0` while the legacy (pre-`supportUnfreezeDelay`) code path is active and `hardenResourceCalculation()`/`hardenResourceCalculation` equivalent is enabled, any transaction or contract call that triggers energy accounting (`EnergyProcessor.useEnergy`, `RepositoryImpl.calculateGlobalEnergyLimit` from TVM execution via `ContractState`/`VMActuator`) throws an uncaught `ArithmeticException`. Because this computation runs during block/transaction processing on every full node, an unhandled exception here is a consensus-critical failure mode — it can crash transaction processing or block validation across the network (a DoS on the RPC/broadcast transaction path, since any user-submitted transaction touching energy accounting could trigger it), analogous to how the InfiniFi bug froze users' locked funds and reverted all `startUnwinding` calls.

### Likelihood Explanation
Reaching `totalEnergyWeight == 0` requires that the total resources frozen/delegated for ENERGY across the whole network reach zero — a state that is far more plausible on private/test networks or immediately post-genesis than on a mature mainnet with many long-standing frozen balances, and it further requires the specific combination of the legacy branch (`supportUnfreezeDelay` not yet active) together with `hardenResourceCalculation` enabled, or reaching the `RepositoryImpl` variant which has no feature-flag guard at all and only relies on the disabled `assert`. Since `assert` is unconditionally inert in production, `RepositoryImpl.calculateGlobalEnergyLimit` is unconditionally exposed whenever `totalEnergyWeight` is zero and `hardenResourceCalculation()` is on — this is a real, reachable code path, not merely a theoretical one, though the state precondition (zero total energy weight) is the main limiting factor for a live, mature mainnet.

### Recommendation
Add an unconditional `if (totalEnergyWeight <= 0) return 0;` (or equivalent explicit exception with graceful handling) before any division in `RepositoryImpl.calculateGlobalEnergyLimit` and in the legacy branch of `EnergyProcessor.calculateGlobalEnergyLimit`, mirroring the guard already present in `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2` and in `EnergyProcessor.calculateGlobalEnergyLimitV2`. Do not rely on Java `assert` statements for any invariant that affects consensus-critical arithmetic, since assertions are disabled by default in production JVMs.

### Proof of Concept
Conceptual reproduction (cannot be executed without a live node/test harness, but derivable directly from the code):
1. Configure/observe a network state where `dynamicPropertiesStore.getTotalEnergyWeight() == 0` (e.g., a fresh private network before any account freezes TRX for energy, or after all energy-frozen balances have been fully unfrozen) while still on the legacy resource-accounting path (`supportUnfreezeDelay()` false).
2. Enable `allowHardenResourceCalculation` (`hardenResourceCalculation()` returns true) — a configurable chain parameter.
3. Submit any transaction/contract call that invokes `EnergyProcessor.useEnergy` → `calculateGlobalEnergyLimit`, or any TVM execution path that calls `RepositoryImpl.calculateGlobalEnergyLimit` (via `ContractState`/`VMActuator`).
4. Because `assert totalEnergyWeight > 0;` is a no-op, execution proceeds to `calculateGlobalLimitV1`/the `BigInteger.divide(BigInteger.valueOf(0))` call, throwing `ArithmeticException`, which is unhandled at that layer and propagates up through transaction/block processing.

Note: I could not fully trace every call site (`VMActuator.java`, `ContractState.java`, `Wallet.java` calls to `calculateGlobalEnergyLimit`) due to remaining tool-call budget constraints, so the exact set of externally-triggerable entry points (e.g., whether an ordinary RPC-submitted contract call can reach `RepositoryImpl.calculateGlobalEnergyLimit` directly) should be verified with a full Devin session that can read those files in entirety and trace exception handling up the call stack (e.g., whether `VMActuator.execute` or the transaction-processing loop catches generic exceptions and only fails the single transaction versus crashing block validation).

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
