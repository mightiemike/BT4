### Title
L1-to-L2 message is unconditionally marked "consumed" even when the L1-handler transaction's execution reverts, permanently discarding the intended L1→L2 effect - (File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo, crates/apollo_batcher/src/block_builder.rs)

### Summary
An L1 message sender (an "unprivileged L1 message sender" in the threat model) submits a message to L2 via an L1 handler transaction. The sequencer commits the message as consumed regardless of whether the invoked L2 entry point actually succeeds. This is structurally the same bug class as the VUSD report: the "burn"/finalization step (message consumption) is performed unconditionally, while the "delivery" step (the entry-point invocation representing the effect the L1 sender paid for) can fail and is handled non-revertingly, with no compensating action. The result is the same as in VUSD: the user's funds/intended state change can be permanently lost with no path to retry, because the L1 message can never be resubmitted once consumed.

### Finding Description
In the Starknet OS, `execute_l1_handler_transaction` calls `consume_l1_to_l2_message` for the L1 message *before* invoking the target entry point, and the invocation itself goes through `non_reverting_select_execute_entry_point_func`: [1](#0-0) 

`non_reverting_select_execute_entry_point_func` explicitly asserts `is_reverted = 0` after running `select_execute_entry_point_func`, meaning any failure inside the invoked contract call is expected to already be excluded before this hint is reached — i.e., the decision of whether the transaction is "reverted" as a whole is made once, up front, via the `IsReverted` hint at the top of `execute_l1_handler_transaction`: [2](#0-1) [3](#0-2) 

Crucially, when `is_reverted != FALSE` (line 387), the OS **skips execution entirely but has already returned early before reaching `consume_l1_to_l2_message`** — so consumption in the OS path only happens for accepted (non-reverted) txs. However, at the blockifier/batcher layer that decides "reverted vs not", the L1 handler transaction hash is added to `consumed_l1_handler_tx_hashes` for *both* successful and failed executions, as long as the executor returns `Ok(...)` for the transaction (i.e., anything other than a hard `TransactionExecutorError`): [4](#0-3) 

This mirrors the blockifier's `L1HandlerTransaction::execute_raw`, where an internal execution error (`Err(execution_error)`) still returns `Ok(l1_handler_tx_execution_info(...))` with a `revert_error` set — the transaction is "reverted" but not rejected by the executor, so from the batcher's point of view it is neither an execution error nor a normal success; it still gets treated as "consumed": [5](#0-4) [6](#0-5) 

The existing test suite explicitly documents and asserts this behavior: even when the `TransactionExecutor` itself returns a hard `Err` for one of two L1-handler transactions, both are asserted to end up in `consumed_l1_handler_tx_hashes`: [7](#0-6) 

Once `consumed_l1_handler_tx_hashes` is committed to the L1 Provider/`TransactionManager` via `commit_block`, the transaction is marked `Committed`/`consume_tx` and can never be reproposed or resubmitted — the `TransactionManager::consume_tx` even treats double consumption as a bug (`Err`) rather than allowing replay: [8](#0-7) 

So exactly as in the VUSD case — where `burn(amount)` happens unconditionally and the payout call failure is merely logged via `WithdrawalFailed` with no refund — here the L1 message consumption happens unconditionally (or is treated as final/consumed) even when the intended on-chain effect (the L2 entry-point call, e.g. crediting a bridged asset) reverts. There is no mechanism to re-queue, refund, or resubmit the message; the L1 sender's deposit/action is permanently lost on L2 while L1 has already released/locked the corresponding value for the L1→L2 transfer.

### Impact Explanation
Any unprivileged L1 message sender (e.g., a bridge contract or user relaying an L1→L2 message, analogous to the "contract deployer"/"L1 message sender" actor class explicitly in-scope) can have their L1-to-L2 message permanently consumed without the corresponding L2 side-effect being applied, if the target L2 entry point reverts for any reason (bug in target contract, transient state issue, insufficient L2 gas bound, etc.). This is a **permanent freezing/loss of funds** scenario: the L1 side has already recorded the message as sent (and typically the L1 value/asset is locked or burned on L1 pending L2 processing), while L2 never applies the corresponding credit, and the message cannot be resubmitted because it is already marked consumed. This matches the accepted impact category: "concrete loss or permanent freezing of funds."

### Likelihood Explanation
This is not conditional on a malicious operator/proposer — it triggers for any legitimate L1→L2 message whose L2 handler reverts due to an ordinary bug, edge case, or resource-bound rejection (e.g., L1 handler L2-gas bound as seen in `l1_handler_max_amount_bounds`/`FeeCheckReport::check_all_gas_amounts_within_bounds`). Given the codebase's own test (`failed_l1_handler_transaction_consumed`) affirms and locks in this exact behavior as intended, it is a deterministic, always-reachable code path rather than a rare race condition — likelihood is high whenever any L1 handler transaction fails/reverts during normal sequencer operation.

### Recommendation
Do not mark an L1 handler transaction as "consumed" in `consumed_l1_handler_tx_hashes` when its execution reverted/failed with a `revert_error` (or hard executor error) unless the protocol design intentionally treats "consumed" as "processed but possibly reverted" and provides a separate, safe recovery path (e.g., automatic requeue, or a compensating mint/refund mechanism on L1). At minimum, distinguish between "processed and applied" vs "processed but reverted" in the OS output/consumption tracking so that reverted L1 handler transactions can be resubmitted or refunded, avoiding permanent fund loss for the L1 message sender, mirroring the VUSD recommendation to mint back on failure or move to a retry-capable design instead of a global unconditional consumption/queue-advance step.

### Proof of Concept
1. An L1 message sender sends a `LogMessageToL2` message (e.g., a bridge deposit) targeting an L2 contract entry point that transiently reverts (e.g., due to a bug, an assertion failure, or exceeding `l1_handler_max_amount_bounds`).
2. The sequencer batcher processes it as an `InternalConsensusTransaction::L1Handler`; `L1HandlerTransaction::execute_raw` returns `Ok(...)` with `revert_error: Some(...)` (per `crates/blockifier/src/transaction/l1_handler_transaction.rs:132-141`), or `TransactionExecutor` may even return a hard `Err`.
3. In `collect_execution_results_and_stream_txs`, the transaction hash is inserted into `execution_data.consumed_l1_handler_tx_hashes` unconditionally for any L1Handler tx, per `crates/apollo_batcher/src/block_builder.rs:644-649`, regardless of the branch taken in the subsequent `match result`.
4. This matches the assertion in the existing test `failed_l1_handler_transaction_consumed` (`crates/apollo_batcher/src/block_builder_test.rs:1064-1111`), which explicitly confirms that even a hard-failed L1 handler transaction ends up in `consumed_l1_handler_tx_hashes`.
5. `commit_block` propagates these hashes to the `L1EventsProvider`/`TransactionManager::consume_tx`, which marks the transaction `Committed`/`consumed` — a state from which it cannot be resubmitted (`crates/apollo_l1_events/src/transaction_manager.rs:247-272`).
6. Result: the L1 sender's intended L2 effect (e.g., crediting bridged funds) never happens, and the message can never be replayed — a permanent loss/freeze of the value associated with that L1→L2 message.

    pub fn consume_tx(
        &mut self,
        tx_hash: TransactionHash,
        consumed_at: BlockTimestamp,
        unix_now: u64,
    ) -> Result<(), BlockTimestamp> {
        self.clear_old_tx_from_consumed_queue(unix_now);

        let Some(record) = self.records.get(&tx_hash) else {
            debug!(
                "Attempted to consume an unknown transaction: {tx_hash}. This can happen if the \
                 transaction was too old to be scraped (e.g. it was created before we started \
                 scraping)."
            );
            return Ok(());
        };

        // Double consumption is a bug.
        if let Some(previously_consumed_at) = record.get_consumed_at_timestamp() {
            return Err(previously_consumed_at);
        }

        // Mark the transaction as consumed.
        self.with_record(tx_hash, |record| record.mark_consumed(consumed_at));
        Ok(())
    }
