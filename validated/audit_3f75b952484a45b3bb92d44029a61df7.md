### Title
Nested `WithdrawFromGasKey` inside a `Delegate` action bypasses the SPICE pending-transaction-queue's gas-key balance guard - (File: chain/client/src/pending_transaction_queue.rs)

### Summary
The `PendingTransactionQueue`/`PendingTxSession` machinery that gates admission of gas-key transactions into SPICE chunks tracks each gas key's committed spend by scanning only the *top-level* actions of a transaction for `Action::WithdrawFromGasKey`. A `WithdrawFromGasKey` action nested inside a `Delegate`/`DelegateV2` meta-transaction's inner action list is never counted, so the guard designed to prevent a gas key from being drained beyond its funded balance across concurrently-pending, uncertified chunks does not apply to that reachable path — the same class of bug as BakerFi's `rebalance` bypassing the vault's pause guard: a protective check exists for the "normal" call path but was not extended to a structurally equivalent nested path.

### Finding Description
`chain/client/src/pending_transaction_queue.rs`'s `add_chunk_transactions` (lines 311-320) and `PendingTxSession::check_pending` (lines 576-585) both iterate `tx.actions()`/`tx.transaction.actions()` directly and pattern-match `Action::WithdrawFromGasKey(withdraw)` to accumulate `pending_gas_key_costs` / `session_gas_key_withdrawals`, the commitments that `paid_from_gas_key` (returned in `PendingConstraints`) uses to bound how much of a gas key's balance can be committed across all uncertified chunks at once. Neither scan recurses into `Action::Delegate`/`Action::DelegateV2` payloads. A transaction whose top-level action is a `Delegate` wrapping an inner `WithdrawFromGasKey` therefore contributes zero to `pending_gas_key_costs`, even though, once the delegate is unpacked and executed by the runtime (`runtime/runtime/src/actions.rs`, `apply_delegate_action`), it does withdraw from the gas key's on-chain balance. This is exactly the class of bug described in the external report: a fee/guard mechanism (`whenNotPaused` in BakerFi; the pending-queue gas-key balance commitment here) is enforced on the "normal" direct call path but not on a semantically equivalent indirect path (meta-transaction / delegate wrapping), letting the guarded value-affecting operation execute unaccounted for.

### Impact Explanation
If unmitigated, multiple uncertified chunks could each admit a gas-key transaction alongside a delegate-wrapped `WithdrawFromGasKey` targeting the same gas key, because the pending-queue's `paid_from_gas_key` commitment would undercount the outstanding withdrawal. This can let a gas key's balance be committed/spent beyond what any single chunk-production session believes is available, i.e., a form of double-spend/overdraft of gas-key funds across the SPICE cross-shard chunk-admission pipeline — concrete unauthorized value movement. This matches the bug-class hint: a protective mechanism (analogous to `whenNotPaused`) is not applied uniformly to all reachable code paths that move value.

### Likelihood Explanation
Reachable directly by any account holding a gas key and issuing a signed meta-transaction (`Delegate`/`DelegateV2`) wrapping `WithdrawFromGasKey` — no validator, operator, or privileged role is required; it is a pure transaction-construction issue reachable by an ordinary RPC caller/transaction signer. However, this exact gap is already named and explicitly closed by `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` (`core/primitives-core/src/version.rs:461-465`, enforced in `runtime/runtime/src/action_validation.rs`, regression-tested in `test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs`), so likelihood of it being currently exploitable depends entirely on whether that protocol feature is activated at the network's current protocol version — a detail I could not fully confirm from the index (the feature-to-version mapping table beyond what was shown was not retrieved).

### Recommendation
Ensure `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` is activated at or before the protocol version this codebase runs, and/or extend `pending_transaction_queue.rs`'s `WithdrawFromGasKey` scan to recurse into `Delegate`/`DelegateV2` inner actions (mirroring how `is_deploy_like_action` already recurses into delegate actions for the deploy-exclusivity check) so the balance commitment guard covers this path defensively even if the action-level rejection is ever relaxed.

### Proof of Concept
1. Fund a gas key via `TransferToGasKey` (as in `test-loop-tests/src/tests/gas_keys.rs`).
2. Construct a signed transaction whose sole action is `Action::Delegate`/`DelegateV2` wrapping a `WithdrawFromGasKey` action for that gas key, at a protocol version predating `RejectWithdrawFromGasKeyInDelegate`'s activation.
3. Submit this delegate transaction alongside other gas-key transactions from the same key into concurrently uncertified chunks; observe that `add_chunk_transactions` (`chain/client/src/pending_transaction_queue.rs:311-320`) does not record the nested withdrawal in `pending_gas_key_costs`, so `PendingTxSession::check_pending`'s `paid_from_gas_key` constraint (lines 553-558) understates the gas key's committed spend, potentially admitting further gas-key transactions that, combined with the delegate's actual withdrawal once executed, overdraft the gas key's funded balance.
