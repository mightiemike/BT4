Based on the investigation, the relevant reachable path is the JSON-RPC HTTP endpoint, which deserializes arbitrary attacker-controlled request bodies into `serde_json::Value` via the untagged `Message` enum before any application-level validation occurs.

### Title
Unbounded Recursion in JSON-RPC Request Deserialization Causes Stack Exhaustion / Node Crash - (File: chain/jsonrpc-primitives/src/message.rs)

### Summary
The `rpc_handler` in `chain/jsonrpc/src/lib.rs` uses axum's `Json<Message>` extractor to deserialize the raw HTTP body into the `Message` enum, whose `params`/`id` fields are typed as `serde_json::Value` [1](#0-0) , and the top-level type itself is a `#[serde(untagged)]` enum [2](#0-1) . `serde_json`'s recursive-descent parser for `Value` has no built-in depth limit, so a deeply nested JSON array/object (e.g. `[[[[[...]]]]]`) causes the parser to recurse once per nesting level, exhausting the call stack, before any RPC method routing, size checks, or business logic runs [3](#0-2) .

### Finding Description
Because the deserialization happens directly on the untrusted network body via the generic `Json<Message>` axum extractor [4](#0-3) , and `Message::Request.params: Value` / `Notification.params: Value` accept arbitrary JSON without a depth cap [5](#0-4) [6](#0-5) , an attacker can submit a JSON payload consisting purely of deeply nested arrays. `serde_json`'s value deserializer recurses for every level of array/object nesting; well within a documented 10MB request body size limit (per `RPC_ARCHITECTURE.md`) an attacker can encode hundreds of thousands of nesting levels (e.g. `[` repeated N times), which is sufficient to overflow the default OS thread stack during parsing. This class of bug is directly analogous to CVE-2025-0649 (TensorFlow Serving): "Incorrect JSON input stringification ... allows for potentially unbounded recursion leading to server crash." In Rust, a stack overflow triggers an immediate process abort (SIGSEGV/guard-page trap) rather than a catchable panic, so this crashes the entire `neard` process, not just the handling task.

### Impact Explanation
Any unauthenticated RPC caller can crash a node's `neard` process with a single HTTP POST to the public JSON-RPC endpoint (default port 3030), causing denial of service. If exploited against enough validators simultaneously, this could halt block production, matching the "transaction-triggered halt" criterion (here, RPC-triggered halt reachable without any special privileges — no signed transaction, private key, or validator status required).

### Likelihood Explanation
High likelihood: the JSON-RPC endpoint is intentionally public and reachable by any external caller without authentication. No economic cost (gas, deposit) is required to send the payload, and constructing a deeply nested JSON array is trivial. The only constraint is the 10MB body size cap, which is far larger than needed for enough nesting depth to overflow a typical 8MB-or-smaller thread stack.

### Recommendation
Bound the deserialization depth before or during JSON parsing of any RPC-facing type that wraps `serde_json::Value` (e.g. `Request::params`, `Notification::params`, `Broken::Unmatched`). Options: use a depth-guarding deserializer (e.g. `serde_stacker`, which grows the stack on demand), pre-scan/reject payloads with nesting deeper than a small fixed bound, or run request body deserialization inside a dedicated worker with a bounded stack and a documented recursion limit enforced by the parser itself. Apply the same protection to the `chain/rosetta-rpc` and `chain/jsonrpc/client` deserialization paths in `chain/rosetta-rpc/src/lib.rs`/`models.rs`, which have not been individually verified here due to index truncation but are structurally similar.

### Proof of Concept
```
POST / HTTP/1.1
Host: <node>:3030
Content-Type: application/json
Content-Length: <size>

{"jsonrpc":"2.0","method":"block","id":1,"params": [[[[[[[[[[ ... 300000 nested arrays ... ]]]]]]]]]] }
```
Sending this payload causes `serde_json` to recurse once per `[`, well before reaching the 10MB body limit, overflowing the handling thread's stack and aborting the `neard` process.

**Uncertainty note:** I could not directly confirm the exact body-size-limit constant/middleware wiring in `chain/jsonrpc/src/lib.rs` (grep matched but full context for the `create_jsonrpc_app`/body-limit layer was not retrievable within the indexed excerpts) — the 10MB figure is taken from `chain/jsonrpc/RPC_ARCHITECTURE.md`, not from directly reading the middleware code. This does not affect the core recursion vulnerability, since even a much smaller body limit (KBs) would still permit sufficient nesting depth to overflow a stack.

pub enum Message {
    /// An RPC request.
    Request(Request),
    /// A response to a Request.
    Response(Response),
    /// A notification.
    Notification(Notification),
    /// A batch of more requests or responses.
    ///
    /// The protocol allows bundling multiple requests, notifications or responses to a single
    /// message.
    ///
    /// This variant has no direct constructor and is expected to be constructed manually.
    Batch(Vec<Message>),
    /// An unmatched sub entry in a `Batch`.
    ///
    /// When there's a `Batch` and an element doesn't conform to the JSONRPC 2.0 format, that one
    /// is represented by this. This is never produced as a top-level value when parsing, the
    /// `Err(Broken::Unmatched)` is used instead. It is not possible to serialize.
    #[serde(skip_serializing)]
    UnmatchedSub(Value),
}
