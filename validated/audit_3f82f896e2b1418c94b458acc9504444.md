### Title
Waterfall block-commit validation compares `PoxAddress` by full struct equality instead of canonical burnchain representation, allowing the on-chain `mainnet` tag to break a semantically-identical-address match - (File: stackslib/src/chainstate/burn/operations/leader_block_commit.rs)

### Summary
`check_pox_waterfall` validates a Nakamoto/PoX-5 (sBTC "waterfall") block-commit by comparing the parsed commit output directly against the expected `sbtc_address` using Rust's derived `PartialEq` on `PoxAddress`, rather than the canonical, consensus-safe `to_burnchain_repr()` comparison used everywhere else in the same file for this exact purpose. `PoxAddress::Addr32`/`Addr20` embed a `mainnet: bool` field that is not actually recoverable from the raw Bitcoin scriptPubKey (segwit/taproot outputs carry no network marker on-chain) and is instead supplied by the caller decoding the transaction. This mirrors the ParaSpace bug class: two representations of the same underlying value (one built from Clarity/contract state, one built from raw chain data) can diverge on an incidental field even though the real, security-relevant payload (the 32-byte witness program) is identical, and an equality check that isn't normalized to the canonical/on-chain representation then produces a spurious rejection.

### Finding Description
`PoxAddress` is defined as:
```rust
pub enum PoxAddress {
    Standard(StacksAddress, Option<AddressHashMode>),
    Addr20(bool, PoxAddressType20, [u8; 20]),
    Addr32(bool, PoxAddressType32, [u8; 32]),
}
``` [1](#0-0) 

`PoxAddress::to_burnchain_repr()` exists specifically because "certain information (e.g. the hash mode) can't be used since it's not stored [on the burnchain]", and produces a representation that intentionally excludes non-recoverable metadata (for `Addr20`/`Addr32` it only encodes the type byte and the raw hash bytes, dropping the `mainnet` bool):
```rust
pub fn to_burnchain_repr(&self) -> String {
    match *self {
        PoxAddress::Standard(ref addr, _) => format!("{:02x}-{}", &addr.version(), &addr.bytes()),
        PoxAddress::Addr20(_, ref addrtype, ref addrbytes) => format!("{:02x}-{}", addrtype.to_u8(), to_hex(addrbytes)),
        PoxAddress::Addr32(_, ref addrtype, ref addrbytes) => format!("{:02x}-{}", addrtype.to_u8(), to_hex(addrbytes)),
    }
}
``` [2](#0-1) 

This is exactly the comparison method used by the classic (pre-waterfall) PoX-output check and by the miner spend-distribution helper, both of which correctly avoid comparing the `mainnet` bool:
```rust
let search_predicate = self_commit.to_burnchain_repr();
let found = check_recipients.iter().enumerate().find(|(_, (check_commit, _))| {
    search_predicate == check_commit.to_burnchain_repr()
});
``` [3](#0-2) 
```rust
if commit_out.to_burnchain_repr() != expected_pox_addr.to_burnchain_repr() { ... }
``` [4](#0-3) 

However, `check_pox_waterfall` — the function that validates PoX-5/sBTC block-commits, introduced for the "Waterfall" reward-set path — instead compares the two `PoxAddress` values with plain `!=`, i.e., full derived struct equality including the `mainnet` field:
```rust
if self.commit_outs.get(0) != Some(&wf_info.sbtc_address) {
    warn!("Invalid waterfall block commit: unexpected output"; ...);
    return Err(op_error::BlockCommitBadOutputs);
}
``` [5](#0-4) 

The expected `sbtc_address` is constructed from Clarity/contract execution context using `is_mainnet = clarity.is_mainnet()`:
```rust
let sbtc_address = PoxAddress::Addr32(is_mainnet, PoxAddressType32::P2TR, output_key);
``` [6](#0-5) 

The actual `commit_outs[0]` comes from decoding the raw Bitcoin transaction output via `PoxAddress::try_from_bitcoin_output`, which for segwit/taproot outputs simply forwards whatever `network`/`mainnet` value was supplied by the caller when the scriptPubKey was parsed:
```rust
BitcoinAddress::Segwit(SegwitBitcoinAddress::P2TR(network, bytes_32)) => Some(
    PoxAddress::Addr32(network.is_mainnet(), PoxAddressType32::P2TR, *bytes_32),
),
``` [7](#0-6) 
and `BitcoinAddress::from_scriptpubkey` takes that network tag purely as a caller-supplied parameter (`network_id`) — it is never derived from the scriptPubKey bytes for P2WPKH/P2WSH/P2TR outputs, since Bitcoin's witness-program scripts carry no network marker on-chain:
```rust
pub fn from_scriptpubkey(network_id: BitcoinNetworkType, scriptpubkey: &[u8]) -> Option<BitcoinAddress> {
    ...
    // segwit p2tr
    Some(BitcoinAddress::Segwit(SegwitBitcoinAddress::P2TR(network_id, *witness_program)))
``` [8](#0-7) 

The codebase already contains at least one call site that hardcodes this tag independent of actual node configuration (`BitcoinNetworkType::Mainnet` regardless of the running network) when reconstructing `PoxAddress` from raw scriptPubKey bytes:
```rust
let Some(bitcoin_addr) = BitcoinAddress::from_scriptpubkey(BitcoinNetworkType::Mainnet, &pox_addr_bytes) ...
``` [9](#0-8) 

This demonstrates that the `mainnet` tag on `PoxAddress::Addr20`/`Addr32` is not a property recoverable from the burnchain output itself, and different code paths in the same codebase already disagree on how to set it. If the value used by whichever component ultimately produces `LeaderBlockCommitOp.commit_outs` (from the real Bitcoin burnchain indexer) is derived from a different assumption than `clarity.is_mainnet()` (e.g., a testnet/regtest deployment, or any code path following the pattern shown in `chain_data.rs`), `check_pox_waterfall`'s strict `PartialEq` will reject a block-commit whose real, on-chain 32-byte taproot output key exactly matches the reward-set-selected sBTC address, purely because of a metadata bit that carries no on-chain meaning.

### Impact Explanation
This breaks the equality "a committed state a node cannot reproduce" / "a validation verdict two nodes disagree on" class: if the `mainnet` tag used when constructing `commit_outs` differs from the tag baked into `wf_info.sbtc_address` (built via `clarity.is_mainnet()`), a syntactically-correct, fee-correct, PoX-eligible block-commit paying the exact correct sBTC taproot output is rejected as `BlockCommitBadOutputs`, denying that miner's sortition-eligible commit even though the underlying payment is valid. Because this only affects the metadata comparison and not the funds themselves, it maps to the High severity bucket ("minority-triggerable sortition/VRF/static-validation divergence") rather than Critical, since it manifests as validation rejection of a would-be-valid commit rather than fund theft — but it can still starve/censor a legitimate miner's commit if the two representations diverge in a given deployment (testnet/regtest most plausibly, since mainnet paths conventionally agree).

### Likelihood Explanation
Likelihood is moderate: on a homogeneously-configured mainnet deployment, both code paths are likely to be fed the same `mainnet=true` flag, so the bug would not normally trigger. The risk surfaces on non-mainnet networks (testnet/regtest, where PoX-5/Waterfall sBTC integration is actively being tested per `pox_5_integrations.rs`), and any future refactor/alternate indexer path that follows the `chain_data.rs`-style hardcoded-network pattern, or that decodes taproot commit outputs using a different network-inference rule than `clarity.is_mainnet()`. The root cause (comparing full `PoxAddress` equality instead of `to_burnchain_repr()`) is a straightforward code-review finding, not something requiring privileged access — no signer/majority/admin key is needed, only a syntactically valid block-commit whose output-address `mainnet` tag differs from the contract-derived value.

### Recommendation
In `check_pox_waterfall`, replace the direct `PoxAddress` equality check with the canonical, burnchain-derived comparison already used elsewhere in this file and in `chain_data.rs`:
```rust
if self.commit_outs.get(0).map(|a| a.to_burnchain_repr())
    != Some(wf_info.sbtc_address.to_burnchain_repr())
{
    ...
}
```
This makes the waterfall PoX check consistent with `check_pox_pre_waterfall`'s `to_burnchain_repr()`-based matching and eliminates dependence on the non-consensus-recoverable `mainnet` field.

### Proof of Concept
1. Two `PoxAddress::Addr32` values are constructed for the identical 32-byte taproot witness program but with different `mainnet` bool values — one from `pox_5_compute_and_update_signers` (`is_mainnet = clarity.is_mainnet()`) at [6](#0-5) , and one from decoding the raw block-commit output via `try_from_bitcoin_output`/`from_scriptpubkey` at [7](#0-6)  and [8](#0-7) , where the `network_id` is supplied externally by whatever burnchain-indexing path is in use (demonstrated to sometimes be hardcoded independent of actual configuration, per [9](#0-8) ).
2. `check_pox_waterfall` compares these two values with `!=` (full derived `PartialEq`, including the `mainnet` field) instead of `to_burnchain_repr()`: [5](#0-4) 
3. Because the two `mainnet` bools differ while the real witness-program bytes are identical, the comparison fails and the function returns `Err(op_error::BlockCommitBadOutputs)`, rejecting a block-commit that pays the correct sBTC recipient — exactly analogous to the ParaSpace bug where two representations of the same asset (WETH vs. NATIVE) failed an equality check causing a legitimate `buyWithCredit` call to revert.
