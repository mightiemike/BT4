This confirms the key fact needed: `DefaultExpiryAfterBlocks = 100_000_000` [1](#0-0)  means inbound/outbound/chain-meta ballots effectively never expire naturally, so `ActiveBallotIDs` only shrinks when a ballot finalizes (2/3+ threshold) — never from timeout — for the ~19-year default window.

### Title
Unbounded `ActiveBallotIDs` scan on every new ballot creation can gas-exhaust vote transactions and permanently stall inbound/outbound finalization - (File: `x/uvalidator/keeper/ballot.go`)

### Summary
`CreateBallot` unconditionally calls `ExpireBallotsBeforeHeight`, which does a full linear scan of the single, protocol-wide `ActiveBallotIDs` collection every time *any* new ballot (inbound, outbound, chain-meta, TSS, fund-migration) is created [2](#0-1) [3](#0-2) . This mirrors the Splits `distribute()` bug: an unbounded, attacker-influenceable collection is iterated inside a single atomic operation, and as that collection grows, the gas cost of that specific operation grows linearly and unboundedly, eventually causing the transaction that would make progress (here, finalizing/creating a new vote ballot) to run out of gas and revert — with no bound anywhere in the code to cap the scan size.

### Finding Description
`VoteOnBallot` → `GetOrCreateBallot` → `CreateBallot` is the single entry point every crosschain vote (`MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, `MsgVoteTssKeyProcess`, `MsgVoteFundMigration`) goes through the first time a UV votes on a *new* observation [4](#0-3) . `CreateBallot` always runs `ExpireBallotsBeforeHeight(ctx, blockHeight)` before creating the new ballot:

```
// First, expire any old ballots before this height
if err := k.ExpireBallotsBeforeHeight(ctx, blockHeight); err != nil {
``` [2](#0-1) 

`ExpireBallotsBeforeHeight` iterates the *entire* `ActiveBallotIDs` collection (unbounded, unpaginated) and, for each ID, fetches the full `Ballot` record to check its expiry height:

```go

	...
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		...
		ballot, err := k.Ballots.Get(ctx, id)
		...
		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
	...
}
``` [3](#0-2) 

`ActiveBallotIDs` is a single shared collection across all ballot types (inbound, outbound, chain-meta, TSS keygen/refresh, fund migration) [5](#0-4) . Because `DefaultExpiryAfterBlocks = 100_000_000` (~19 years) is used for all normal inbound/outbound/chain-meta ballots specifically to "disable expiry" until pruning/escape-hatch work lands [6](#0-5) , the only thing that removes an entry from `ActiveBallotIDs` under normal operation is reaching the 2/3 finalization threshold via `CheckIfFinalizingVote` → `MarkBallotFinalized` [7](#0-6) .

An unprivileged external user can grow the active-ballot set essentially without bound, purely through ordinary cross-chain usage, by triggering many distinct genuine source-chain events (e.g. many cheap dust deposits from different source addresses/tx hashes, each producing a distinct `sha256(sourceChain:txHash:logIndex)` ballot key) [8](#0-7) . Honest UVs will faithfully vote on each of these real observed events via `MsgVoteInbound`, each first vote creating a new ballot and running the full scan. Every ballot that is never voted to a 2/3 majority (e.g., because it references a chain/token that later becomes disabled, or where UVs disagree/partially vote and stop) stays PENDING in `ActiveBallotIDs` forever, since expiry is effectively disabled. As this set grows, every subsequent *new* ballot creation — including the ones needed to finalize legitimate outbounds that release user funds — pays a growing linear-scan cost inside the same atomic vote transaction. Once the accumulated active-ballot count is large enough that the scan's gas cost exceeds the `GasWanted` typically supplied for a vote tx (or, in the worst case, the block gas limit), the vote transaction fails with out-of-gas, so the ballot is never created/finalized. Because the failing operation *is* the one that would eventually clean up expired entries, there is no mechanism (short of a chain-halting upgrade) to reduce the set once it becomes too costly to scan — this is corroborated by the existence of the `purge-expired-outbounds` upgrade, which had to be shipped specifically to manually walk and clean up `PendingOutbounds`/stuck ballots via an upgrade handler because operators had no other recourse [9](#0-8) .

This is a direct structural analog of the reported bug: an unbounded loop over a collection whose size is influenced by ordinary, unprivileged usage is embedded inside a single all-or-nothing operation, so growth of that collection can push the required gas past what any single transaction can supply, permanently blocking the very state transition that funds' release depends on (inbound mint confirmation, outbound observation, TSS event finalization, fund migration).

### Impact Explanation
If `ActiveBallotIDs` grows large enough that the embedded `ExpireBallotsBeforeHeight` scan inside `CreateBallot` cannot complete within the gas budget of a UV's vote transaction, *no new ballot of any kind* can be created or finalized chain-wide — including inbound votes that mint PRC20/native funds for depositors, outbound votes that release funds cross-chain, TSS key-process votes, and fund-migration votes. Funds already deposited on source chains but awaiting inbound finalization would be permanently unconfirmed/unminted, and outbound observations needed to complete cross-chain fund releases would be permanently blocked — matching the "permanent freezing of user or protocol-controlled funds" and "consensus/state-machine divergence reachable from ordinary user deposits" impact categories. There is no owner/admin fast-path analogous to Split's `execCalls()`; the codebase's own upgrade history (`purge-expired-outbounds`) shows that unwinding a stuck ballot backlog currently requires a full chain software upgrade.

### Likelihood Explanation
Likelihood depends on Push Chain's configured consensus `MaxGas`/typical per-vote `GasWanted` versus the actual per-active-ballot iteration cost (one KV read of `Ballots` plus one `ActiveBallotIDs` iterator step each). I could not verify the exact per-vote `GasWanted` value UVs submit or the chain's configured block gas limit from the indexed code, so I cannot give a precise "N active ballots" threshold — this is analogous to the original report's "~1100 recipients" estimate, which required an on-chain benchmark to pin down. The design intentionally disabled expiry ("Set to 100M... to effectively disable expiry... Ballots should not expire without an escape hatch") [10](#0-9) , which strongly suggests the team is aware unbounded accumulation is possible but has not yet bounded the per-operation scan cost, only deferred cleanup to future work.

### Recommendation
- Decouple ballot expiry sweeping from the hot path of `CreateBallot`. Do not run `ExpireBallotsBeforeHeight` synchronously inside every new-ballot creation; instead run it as a bounded/batched job (e.g., cap the number of IDs scanned per call, or move sweeping to a periodic `BeginBlocker`/`EndBlocker` with a fixed per-block budget).
- Add an explicit cap on the number of active ballots scanned or expired per invocation, similar in spirit to the reported recommendation of validating recipient-array size up front.
- Consider indexing active ballots by expiry height (or a secondary time-ordered index) so expired ballots can be found without scanning the entire active set.
- Re-evaluate whether `DefaultExpiryAfterBlocks = 100_000_000` for inbound/outbound/chain-meta ballots is safe given `ExpireBallotsBeforeHeight`'s O(n) behavior, since it guarantees the active set can only shrink via full 2/3 consensus, never via time-based pruning.

### Proof of Concept
Conceptual reproduction (would need on-chain benchmarking to find the exact breaking point, mirroring the original report's gas benchmark):
1. Seed `ActiveBallotIDs` with a large number (N) of PENDING ballots that never reach threshold (e.g., via `CreateBallot` in a test harness, as already exercised by `TestExpireBallotsBeforeHeight_NoneSkipped` / `TestExpireBallotsBeforeHeight_MultipleExpiredAndPending`, which already demonstrate `ExpireBallotsBeforeHeight` walking all active ballots each call) [11](#0-10) .
2. Measure gas consumed by a subsequent `CreateBallot` call (or full `MsgVoteInbound` execution) as N scales, analogous to the Splits PoC's `gasBefore - gasleft()` measurement.
3. Confirm gas grows ~linearly with N and identify the N at which it exceeds typical `GasWanted` for a UV vote tx or the chain's configured block gas limit.

// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}

// CheckIfFinalizingVote inspects whether the just-cast vote pushes the ballot
// over its threshold and, if so, drives the finalization through
// MarkBallotFinalized — the single canonical write path for terminal status
// transitions, which applies CEI-style ordering on the secondary indexes.
func (k Keeper) CheckIfFinalizingVote(ctx context.Context, b types.Ballot) (types.Ballot, bool, error) {
	ballot, isFinalizing := b.IsFinalizingVote()
	if !isFinalizing {
		return b, false, nil
	}

	k.Logger().Debug("ballot reached finalization threshold",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)

	if err := k.MarkBallotFinalized(ctx, ballot.Id, ballot.Status); err != nil {
		return ballot, false, errors.Wrap(err, "failed updating finalized ballot")
	}

	k.Logger().Debug("ballot finalized",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)
	return ballot, true, nil
}
