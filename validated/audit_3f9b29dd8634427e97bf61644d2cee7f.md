## Binding

For every L2 height `h`, the light client circuit's expected batch proof method id at `h` must equal the method id the honest batch prover used to prove `h`:
`BatchProofMethodIdAccessor::get(...)` resolved-at-`h` == `method_id` used in `Z::verify(proof, &method_id, ...)` when the batch prover generated the proof for `h`.

## Trace

The accessor stores `(activation_l2_height, method_id)` pairs and only allows strictly increasing insertions: [1](#0-0) 

If a copied/replayed signed `BatchProofMethodId` body `Y` (higher activation height) is included in an earlier DA block before the genuine lower-height upgrade `X` is included, `last_activation_height` becomes `Y`. When the legitimate `X` transaction later arrives, `activation_l2_height (X) <= last_activation_height (Y)` is true, so the `continue` branch fires and `X` is silently dropped — `BatchProofMethodIdAccessor::insert` for `id_X` never happens: [2](#0-1) 

Downstream, `process_complete_proof` resolves the method id for a proof purely from `batch_proof_output_last_l2_height` via a binary search over the accessor's sorted activation-height list, taking the entry with the greatest activation height `<=` that target: [3](#0-2) 

Given the accessor now only contains `[..., (pre_X_height, id_prev), (Y, id_Y)]` (no `X` entry), any proof whose `last_l2_height` falls in `[X, Y)` resolves to `id_prev`, not `id_X`. An honest batch prover that produced a real ZK proof for that range under `id_X` (the correct, authorized-but-front-run method id) will have `Z::verify(proof, &id_prev, ...)` invoked against it, which fails, and the proof is simply skipped/logged rather than applied: [4](#0-3) 

There is no other code path that reconstructs or falls back to `id_X` — the accessor is the sole source of truth for method-id-by-height, and once `X`'s insertion is skipped, `id_X` is permanently absent from every future `get()` call, for every future L1 block indefinitely, confirmed by the accessor's append-only/monotonic design (`initialize`/`insert` only permit forward-only history): [5](#0-4) 

The existing guards (`verify_method_id_security_council`, chain-id check, monotonic-height check) only protect against forging new activation records; they do nothing to protect a value that was already correctly signed but got pre-empted by a copy of a higher-height signed body landing first, since the signature only covers `(method_id, activation_l2_height, chain_id)` with no ordering/replay-protection tie to block inclusion order: [6](#0-5) 

## Impact

For every L2 height `h ∈ [X, Y)`, the circuit-resolved method id (`id_prev`) diverges from the method id the honest prover actually used (`id_X`); the binding is broken. A genuine state transition proved under `id_X` becomes permanently unverifiable by the light client circuit and can never be re-submitted with a different, matching method id (since `id_X`'s only valid representation is what the prover already computed). This directly matches the "true transition made permanently unprovable" Critical impact category — Clementine's bridge proof (which relies on the light client proof for the L2 state root) can never mark that range of commitments as verified, permanently stalling/forking the provable L2 state root the bridge can rely on for that height range.

## Likelihood

Preconditions are exactly the antecedent "front-run" condition (a previously-broadcast, validly-signed but not-yet-included `BatchProofMethodId` body `Y` gets copied/rebroadcast into an earlier finalized block than the genuine lower-height `X` body) — this requires only Bitcoin transaction fee payment/mining ability, not any council/private key, matching the unprivileged-attacker model. Once that precondition holds, the downstream unprovability is deterministic and repeatable for every batch proof targeting `[X, Y)`.

## Recommendation

Reject/ignore method-id upgrade insertion decisions based solely on `activation_l2_height <= last_activation_height` comparisons against the *currently stored maximum*; instead validate against all previously seen (or pending) signed activation heights, or require the batch prover / accessor to retain and honor `id_X` explicitly (e.g., insert by sorted position rather than append-only-highest, or require security-council transactions to commit to the full ordered set of expected upcoming activations so a later-arriving lower height cannot be silently dropped).

    ///
    /// # Arguments
    /// * `activation_l2_height` - The L2 block height at which the method id is activated
    /// * `method_id` - The method id to store
    /// * `working_set` - Mutable reference to the working set for storage access
    pub fn insert(activation_l2_height: u64, method_id: [u32; 8], working_set: &mut WorkingSet<S>) {
        let key = Self::key();
        let mut method_ids = Self::get(working_set).unwrap_or_default();
        method_ids.push((activation_l2_height, method_id));
        let value: StorageValue = borsh::to_vec(&method_ids)
            .expect("Batch proof method ids serialization should not fail")
            .into();
        working_set.set(&key, value);
    }
