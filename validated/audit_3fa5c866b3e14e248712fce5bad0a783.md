### Title
Insufficiently robust `__execute__` invocation guard — `library_call`/`meta_tx_v0` paths do not enforce `block_direct_execute_call` — ([File: crates/blockifier/src/execution/syscalls/hint_processor.rs])

### Summary
Analogous to GHSA-mp76-7w5v-pr75 (checks that exist to restrict which "methods" can be invoked are not applied consistently across all invocation paths), the blockifier's protection against direct invocation of a contract's `__execute__` entry point (`block_direct_execute_call` / `maybe_block_direct_execute_call`) is enforced only on the `call_contract` syscall path, but not on the `library_call` syscall path or other call-dispatch paths that ultimately construct a `CallEntryPoint` with an attacker-supplied `entry_point_selector`.

### Finding Description
The sequencer added a guard, `maybe_block_direct_execute_call`, to reject calls whose target selector equals `__execute__` (`EXECUTE_ENTRY_POINT_NAME`), when the `block_direct_execute_call` versioned constant is enabled [1](#0-0) . This is invoked explicitly in the native `call_contract` syscall handler [2](#0-1)  and, in the deprecated (Cairo0) syscall handler, an equivalent inline check exists in `call_contract` [3](#0-2) , and in the OS Cairo code for the deprecated `CALL_CONTRACT_SELECTOR` handler [4](#0-3)  and in the current OS Cairo `execute_call_contract` implementation [5](#0-4) .

However, the `library_call` syscall handler — which also allows a caller to specify an arbitrary `entry_point_selector` and construct a `CallEntryPoint` of type `External` — does **not** call `maybe_block_direct_execute_call` (or any equivalent) in either the native handler [6](#0-5)  or the Cairo1 VM handler [7](#0-6) . The `meta_tx_v0` syscall explicitly requires the target selector to be `__execute__` by design (a legitimate exception documented in the code) [8](#0-7) , which shows the codebase is aware that invoking `__execute__` outside the normal transaction flow is a security-sensitive operation requiring explicit gating — yet `library_call` has no gate at all.

This mirrors the TurboBoost bug class precisely: a security check ("only these methods/selectors may be invoked this way") exists conceptually but is implemented per-entry-point rather than centrally, so an alternate code path (`library_call`) that reaches the same underlying dispatch primitive (`CallEntryPoint` construction with an attacker-controlled selector) bypasses the restriction.

### Impact Explanation
`__execute__` is normally only supposed to run after `__validate__` has authorized the specific calldata for a given transaction (this is the entire security model of Starknet account abstraction: `__validate__` gates what `__execute__` is permitted to do with a given signature/nonce). The `block_direct_execute_call` protection was introduced specifically to prevent an unrelated caller from invoking a victim account's `__execute__` directly with attacker-chosen calldata, bypassing the validate-then-execute invariant enforced by the OS/blockifier transaction flow. If `library_call` is a viable bypass of this restriction (i.e., invoking `__execute__` of a class in a delegate-call context still allows attacker-directed execution of the account's `__execute__` logic without a preceding, matching `__validate__` call for that calldata), this would allow unauthorized account actions or arbitrary invocation of `__execute__` semantics outside the protected transaction flow — a High severity issue consistent with "unauthorized account action" per the validation criteria.

### Likelihood Explanation
The vulnerability is directly reachable by any contract deployer/caller: any contract can invoke `library_call_syscall(class_hash, selector!("__execute__"), calldata)` in a single transaction, without needing privileged access, an operator, or multi-party coordination. This makes it trivially reachable from a single submitted transaction/contract call, matching the "single transaction reach" requirement.

### Recommendation
Move the `__execute__` direct-invocation guard out of the individual `call_contract` handlers and into the shared `CallEntryPoint` execution path (e.g., in `execute_inner_call` or `CallEntryPoint::execute`), so that every syscall constructing a `CallEntryPoint` with `entry_point_type == External` and an attacker-provided selector — including `library_call`, `delegate_call`, and any future dispatch mechanism — is subject to the same `block_direct_execute_call` check, unless intentionally exempted (as `meta_tx_v0` is, by design, for a different flow). Add regression tests exercising `library_call` with `__execute__` as the target selector under `block_direct_execute_call = true` to confirm the fix.

### Proof of Concept
This report is based on static code analysis; I was not able to execute the sequencer to dynamically confirm that a `library_call` to a victim account's `__execute__` produces an unauthorized action equivalent to a bypassed `call_contract` invocation (this would require confirming, at runtime, whether the OS/blockifier semantics of `library_call`'s "delegate" execution context for `__execute__` genuinely allow bypassing the `__validate__`-gates-`__execute__` invariant, or whether the storage-context difference between `call_contract` and `library_call` neutralizes the impact). Conceptually:
1. Deploy/attacker contract A calls `library_call_syscall(victim_account_class_hash, selector!("__execute__"), attacker_calldata)`.
2. Since `library_call` executes in delegate-call semantics (using contract A's own storage context but the victim class's code), and there is no `maybe_block_direct_execute_call` check, the call proceeds without the `DirectExecuteCall`/`Invalid argument` rejection that `call_contract` would produce, as demonstrated by the existing regression test only covering `call_contract` [9](#0-8)  and the Cairo1 test contract's `test_direct_execute_call`, which also exercises only `call_contract_syscall` [10](#0-9) , with no analogous `test_library_call`-based negative test.

Given the uncertainty about the exact exploitation impact through `library_call`'s storage-context semantics (verification requires either running the sequencer test-suite or expert review of the OS specification for `__execute__`'s trust boundary), this should be treated as a concrete gap in defense-in-depth that a background engineer/security reviewer should validate empirically before final triage.

    pub(crate) fn maybe_block_direct_execute_call(
        &mut self,
        selector: EntryPointSelector,
    ) -> SyscallResult<()> {
        let versioned_constants = &self.context.tx_context.block_context.versioned_constants;
        if versioned_constants.block_direct_execute_call
            && selector == selector_from_name(EXECUTE_ENTRY_POINT_NAME)
        {
            return Err(SyscallExecutionError::Revert { error_data: vec![INVALID_ARGUMENT_FELT] });
        }
        Ok(())
    }

    fn library_call(
        &mut self,
        class_hash: Felt,
        function_selector: Felt,
        calldata: &[Felt],
        remaining_gas: &mut u64,
    ) -> SyscallResult<Vec<Felt>> {
        self.pre_execute_syscall(
            remaining_gas,
            self.gas_costs().syscalls.library_call.base_syscall_cost(),
            SyscallSelector::LibraryCall,
        )?;

        let class_hash = ClassHash(class_hash);

        let wrapper_calldata = Calldata(Arc::new(calldata.to_vec()));

        let selector = EntryPointSelector(function_selector);

        let entry_point = CallEntryPoint {
            class_hash: Some(class_hash),
            code_address: None,
            entry_point_type: EntryPointType::External,
            entry_point_selector: selector,
            calldata: wrapper_calldata,
            // The call context remains the same in a library call.
            storage_address: self.base.call.storage_address,
            caller_address: self.base.call.caller_address,
            call_type: CallType::Delegate,
            initial_gas: *remaining_gas,
        };

        let error_wrapper_function =
            |e: SyscallExecutionError,
             class_hash: ClassHash,
             storage_address: ContractAddress,
             selector: EntryPointSelector| {
                e.as_lib_call_execution_error(class_hash, storage_address, selector)
            };

        Ok(self
            .execute_inner_call(entry_point, remaining_gas, class_hash, error_wrapper_function)?
            .0)
    }

    fn library_call(
        request: LibraryCallRequest,
        vm: &mut VirtualMachine,
        syscall_handler: &mut Self,
        remaining_gas: &mut u64,
    ) -> Result<LibraryCallResponse, Self::Error> {
        let entry_point = CallEntryPoint {
            class_hash: Some(request.class_hash),
            code_address: None,
            entry_point_type: EntryPointType::External,
            entry_point_selector: request.function_selector,
            calldata: request.calldata,
            // The call context remains the same in a library call.
            storage_address: syscall_handler.storage_address(),
            caller_address: syscall_handler.caller_address(),
            call_type: CallType::Delegate,
            // NOTE: this value might be overridden later on.
            initial_gas: *remaining_gas,
        };

        let retdata_segment = execute_inner_call(entry_point, vm, syscall_handler, remaining_gas)
            .map_err(|error| match error {
            SyscallExecutionError::Revert { .. } => error,
            _ => error.as_lib_call_execution_error(
                request.class_hash,
                syscall_handler.storage_address(),
                request.function_selector,
            ),
        })?;

        Ok(LibraryCallResponse { segment: retdata_segment })
    }

fn test_direct_execute_call(cairo1_type: RunnableCairo1, block_direct_execute_call: bool) {
    let test_contract = FeatureContract::TestContract(CairoVersion::Cairo1(cairo1_type));
    let contract_with_execute = FeatureContract::EmptyAccount(cairo1_type);
    let chain_info = &ChainInfo::create_for_testing();
    let mut state =
        test_state(chain_info, BALANCE, &[(test_contract, 1), (contract_with_execute, 1)]);

    let test_contract_address = *test_contract.get_instance_address(0).0.key();
    let contract_with_execute_address = *contract_with_execute.get_instance_address(0).0.key();
    let call_execute_directly_selector = selector_from_name("call_execute_directly");
    let return_result_selector = selector_from_name("return_result");

    let call_execute_directly = CallEntryPoint {
        entry_point_selector: call_execute_directly_selector,
        calldata: calldata_macro![
            // The Execute entrypoint of this contract will be called.
            contract_with_execute_address,
            // Outer calldata (passed to `execute` entrypoint)
            felt!(4_u8), // Outer calldata length.
            test_contract_address,
            return_result_selector.0,
            // Inner calldata (passed to function called by `execute` entrypoint)
            felt!(1_u8), // Inner calldata length.
            felt!(0_u8)  // Inner calldata value.
        ],
        ..trivial_external_entry_point_new(test_contract)
    };

    let mut block_context = BlockContext::create_for_testing();
    block_context.versioned_constants.block_direct_execute_call = block_direct_execute_call;
    let call_info = call_execute_directly
        .execute_directly_given_block_context(&mut state, block_context)
        .unwrap();

    if block_direct_execute_call {
        assert!(call_info.execution.failed, "Expected direct execute call to fail.");
        assert_eq!(
            format_panic_data(&call_info.execution.retdata.0),
            "0x496e76616c696420617267756d656e74 ('Invalid argument')",
        );
    } else {
        assert!(
            !call_info.execution.failed,
            "Expected direct execute call to succeed, because `block_direct_execute_call` is \
             false."
        );
    }
