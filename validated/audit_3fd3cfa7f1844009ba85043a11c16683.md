### Title
Stale Cairo0 (V0) class from the global contract cache bypasses declaration checks - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` treats a cache hit in the process-global `ContractClassManager` as sufficient proof that a class is declared for Cairo1 (V1/V1Native) classes only. For Cairo0 (V0) classes, the same "declared" re-verification is explicitly skipped, so a V0 class hash that is merely present in the shared cache is returned as-is, with no check against the canonical committed state.

### Finding Description
`get_compiled_from_class_manager` first asks the shared `ContractClassManager` cache for a runnable class by `class_hash`: [1](#0-0) 

For non-V0 classes, the code explicitly re-validates declaration via `self.state_reader.is_declared(class_hash)`, with the comment stating the reason: *"existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)"*. This proves the developers know the cache can retain entries from speculative/aborted execution paths that never became canonical.

For `RunnableCompiledClass::V0(_)`, this branch is a no-op — no re-check is performed at all: [2](#0-1) 

The `FetchCompiledClasses::is_declared` trait itself documents this asymmetry: *"Returns whether the given class hash corresponds to a declared Cairo 1 class. Cairo 0 classes always return `false`."* [3](#0-2) 

Both `ApolloReader::is_declared` and `SyncStateReader::is_declared` only check the Cairo1 declaration tables, confirming `is_declared` is structurally incapable of validating V0 classes: [4](#0-3) [5](#0-4) 

The `ContractClassManager`/`GlobalContractCache` used here is a process-wide LRU cache, shared across all block-building/re-validation/view-call activity in the node (e.g. shared between block production and view calls in the batcher, per `StorageViewStateReaderFactory::create`): [6](#0-5) [7](#0-6) 

Because entries are inserted via `set_and_compile` whenever `get_compiled_classes` is called on the underlying reader — including during speculative execution that is later discarded (e.g. an aborted/rejected proposal, or a re-execution/estimate-fee path) — a V0 class hash can end up warm in this shared cache without ever being truly declared in the finalized/committed state. Any subsequent transaction that references that class hash (e.g., via `library_call` or a deploy syscall) will get a cache hit and, because the V0 branch performs no re-validation, the sequencer will treat the class as declared and execute it, even though the canonical storage-backed state has no record of its declaration.

### Impact Explanation
If two honest nodes (or the same node across two different execution contexts) differ in whether this V0 entry is warm in their local process cache, they can diverge on whether a given class hash is declared and thus on the outcome of any call/deploy referencing it. This can lead to:
- Honest-node divergence in execution results and therefore in the computed state root / block hash for the same block.
- Effective bypass of the declare-transaction/fee requirement for Cairo0 classes, allowing use of a class that was never legitimately declared on-chain.

Both outcomes fall squarely into "wrong committed root or block hash" / "honest-node divergence", satisfying the High-severity bar.

### Likelihood Explanation
The vulnerable code path is reached purely by a state-reader cache lookup during ordinary compiled-class resolution, which is invoked for every call/deploy/library_call referencing a class hash — fully reachable from a single submitted transaction. The precondition (a V0 class hash becoming cached without a corresponding canonical declaration) requires the class to first pass through `set_and_compile` in a non-canonical execution path (e.g., discarded proposal, view call, or re-execution/estimate flow) sharing the same `ContractClassManager` instance as later block production, as suggested by `StorageViewStateReaderFactory` and by the explicit "reverted block" caching comment. I was not able to fully trace, within this investigation, the exact lifecycle guarantees of the `ContractClassManager`/cache across proposal abort/re-validation cycles in the batcher (i.e., confirm empirically that a discarded proposal's speculative class-cache writes are never rolled back before the same process later executes a different, canonical block). This should be verified directly in the batcher/proposal lifecycle code before treating this as a confirmed, immediately-exploitable bug rather than a design gap that mirrors an already-acknowledged risk for V1 classes.

### Recommendation
Apply the same `is_declared`-style verification to `RunnableCompiledClass::V0` cache hits as is already done for V1/V1Native, i.e. extend `FetchCompiledClasses::is_declared` (or add a parallel check) to also validate Cairo0 declaration against the canonical, committed state before trusting a cache hit, removing the special-cased no-op branch in `get_compiled_from_class_manager`.

### Proof of Concept
Conceptual reproduction (not verified end-to-end due to the batcher-lifecycle uncertainty noted above):
1. Submit (or have the sequencer speculatively execute, e.g. via a fee-estimation/view call or a proposal that is later discarded) a transaction that declares/uses Cairo0 class `C` with hash `H`, causing `get_compiled_from_class_manager` to call `set_and_compile(H, ...)` and populate the shared `ContractClassManager` cache — even though this execution never becomes part of the canonical committed state (e.g., the proposal round is aborted).
2. Submit a transaction to the now-canonical block-building context that performs a `library_call` (or deploys) using class hash `H`, without `H` ever being declared in the committed state.
3. `get_compiled_from_class_manager` finds `H` in the shared cache, sees it is `RunnableCompiledClass::V0`, and returns it directly with no `is_declared` check, executing code for a class that is not part of the canonical state — while a node with a cold cache (or one that discarded the cache entry) would correctly reject it with `StateError::UndeclaredClassHash`, producing state divergence.
