### Title
`DeleteAccount`'s `beneficiary_id` is not existence-checked before the balance-refund receipt is emitted, causing permanent burning of the deleted account's entire balance - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`action_delete_account` unconditionally emits a system "balance refund" receipt carrying the account's entire balance to the caller-supplied `beneficiary_id`, without checking whether that account exists. [1](#0-0)  If `beneficiary_id` is a syntactically valid but non-existent (and non-implicit) account, the resulting refund receipt fails and the entire balance is permanently burned rather than returned to anyone.

### Finding Description
`DeleteAccountAction::beneficiary_id` is only validated as a syntactically well-formed `AccountId`; there is no check that the account actually exists. [2](#0-1)  When the delete executes, `action_delete_account` pays out the account's full balance via `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` unconditionally. [1](#0-0) 

This generated receipt has `predecessor_id == "system"`, marking it as a refund receipt. [3](#0-2)  When this refund receipt is later applied as a `Transfer` action against the (possibly nonexistent) `beneficiary_id` account, `check_account_existence` only allows implicit account creation for `NearImplicit`/`EthImplicit`/`NearDeterministic` account types; a normal named account id (e.g. a typo'd or not-yet-registered `AccountId`) that does not exist causes the action to fail with `AccountDoesNotExist`. [4](#0-3) 

Critically, refund receipts are special-cased: if a refund receipt's execution fails, the deposit amount is **burned**, not returned to anyone: `if receipt.predecessor_id().is_system() { if result.result.is_err() { stats.balance.other_burnt_amount = safe_add_balance(..., total_deposit(...)) } }`. [5](#0-4)  This is also documented explicitly: "If the execution of a refund fails, the refund amount is burnt." [6](#0-5) 

The runtime test suite itself confirms this exact hazard, noting that a beneficiary must exist "otherwise the balance transfer the delete sends it would come straight back as a refund" — and per the refund semantics above, a failed refund is burned, not returned. [7](#0-6) 

This closely mirrors the reported Graph Protocol bug class: a caller-supplied "refund/beneficiary" destination that is assumed to be reachable/controllable, but if it is not (does not exist, in this case), the value is irrecoverably lost rather than returned to the sender.

### Impact Explanation
Any account holder (or a relayer executing a meta-transaction `DeleteAccount` action on behalf of a signer, per NEP-366 `Delegate`/`DelegateV2`) who submits a `DeleteAccount` action with a `beneficiary_id` that is a syntactically valid but non-existent named account permanently and irrecoverably burns their entire account balance. This is a direct, transaction-triggered permanent loss of user funds (burned, i.e. removed from total supply) with no path to recovery — matching the "permanently frozen funds" / unauthorized value destruction criteria.

### Likelihood Explanation
This is trivially reachable by any single unprivileged transaction signer calling `DeleteAccount` (directly, via a contract's `promise_batch_action_delete_account`, or via a relayed meta-transaction) and specifying a `beneficiary_id` that has not been created (e.g. a typo, a not-yet-registered sub-account, or an account that was itself deleted earlier in the same execution). There is no additional privilege or precondition required beyond controlling the account being deleted, and the failure mode (silent, permanent burn) is non-obvious to users, closely analogous to the original report's scenario of a refund destination that "exists" nominally but cannot actually receive/control the funds.

### Recommendation
Before emitting the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing account (or is an implicit/deterministic account type that can be created on the fly). If the beneficiary cannot be shown to exist/be creatable, reject the `DeleteAccount` action with a validation error (as is already done for other malformed inputs, e.g. `DeleteAccountWithLargeState`), rather than silently proceeding and later burning the funds on refund failure.

### Proof of Concept
1. Create account `alice.near` with balance `B`.
2. `alice.near` submits `SignedTransaction` with a single `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "ghost.near" })`, where `ghost.near` is a syntactically valid but never-created account.
3. `action_delete_account` executes: it removes `alice.near` and pushes `Receipt::new_balance_refund("ghost.near", B)` [1](#0-0) .
4. The refund receipt (predecessor `"system"`) is later applied. Since `ghost.near` is a Named account type that does not exist, `check_account_existence` rejects the `Transfer` action with `AccountDoesNotExist` [4](#0-3) .
5. Because the failing receipt has `predecessor_id == "system"`, the runtime burns the full deposit `B` instead of refunding it to anyone [5](#0-4) .
6. Result: `alice.near`'s entire balance `B` is permanently removed from total supply, with no recipient — an irrecoverable loss triggered by a single ordinary transaction.
