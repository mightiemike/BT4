### Title
Exchange liquidity injection (`ExchangeInjectContract`) lacks minimum-received/slippage protection, letting the paired-token amount be silently changed by pool-state shifts before execution - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` computes the "balanced" counter-token amount (`anotherTokenQuant`) purely from the exchange pool's *current* `firstTokenBalance`/`secondTokenBalance` ratio at execution time, and then deducts that computed amount directly from the submitter's account with **no user-supplied bound** on it. Any other market participant's `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` that executes earlier in the same block (or a preceding block after the user broadcasts but before their tx is packed) changes the pool ratio, so the actually-charged `anotherTokenQuant` can differ arbitrarily from what the user expected when they signed the transaction. This is the same bug class as the reported Mellow `LPIssuer.deposit` finding: a deposit/injection function derives a paired/balanced amount from a mutable external ratio, with no min/max-return check, so unprivileged, ordinary transaction ordering can cause the user to receive/pay an unpredictable, unintended outcome.

### Finding Description
In `ExchangeInjectActuator.execute`, the paired amount is derived on the fly from the live pool balances: [1](#0-0) 

and the same uncapped calculation is repeated in `doValidate`: [2](#0-1) 

Neither `execute` nor `doValidate` compares `anotherTokenQuant` against any value chosen by the transaction submitter — the only checks are `anotherTokenQuant <= 0` and an absolute `balanceLimit`, not a user-defined bound tied to the ratio at signing time. [3](#0-2) 

This is confirmed by the protobuf definition of `ExchangeInjectContract`, which only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/min-return-style field: [4](#0-3) 

By contrast, java-tron's own sibling actuator for the trading path, `ExchangeTransactionActuator`, *does* implement exactly this protection: the contract carries an `expected` field and `doValidate` explicitly rejects the transaction if the computed output is below it: [5](#0-4) [6](#0-5) 

This shows the protocol designers were aware of the "ratio can shift before execution" risk for swaps but never applied the equivalent min/max-bound protection to the liquidity-injection ("deposit") path, which is precisely the gap the external report calls out for `LPIssuer.deposit`.

### Impact Explanation
Because `ExchangeInjectContract` is reachable by any account via a normal broadcast transaction (no special permission required), and because the pool ratio can be moved by any other account's ordinary `Exchange*` transactions confirmed earlier in the same or a prior block, a user's injection can be executed against a ratio wildly different from the one they observed when they signed and broadcast the transaction. Since the actuator unconditionally debits both `tokenQuant` and the freshly recomputed `anotherTokenQuant` from the user's balance/asset holdings, the user can be forced to inject (i.e., lose) a far larger amount of the counter-token than intended, or receive a far smaller effective share of the pool than expected — a direct, unbounded value-transfer/accounting-corruption risk against the depositor, matching the "exchange/market math" category of state-transition bugs in scope.

### Likelihood Explanation
Likelihood is high: it requires no privileged role, no leaked key, and no P2P/node compromise — only ordinary, permissionless transactions from other market participants (or even accidental interleaving of unrelated trades) targeting the same `exchange_id`. Any active exchange pool with normal trading volume will regularly shift its balance ratio between the time a user constructs an `ExchangeInjectContract` and the time it is packed into a block.

### Recommendation
Add a user-supplied bound to `ExchangeInjectContract` (and the analogous `ExchangeWithdrawContract`), mirroring the `expected` field already used in `ExchangeTransactionContract`:
- Extend the protobuf message with a minimum-accepted / maximum-accepted paired-token amount field.
- In `ExchangeInjectActuator.doValidate` / `execute`, reject the transaction if the computed `anotherTokenQuant` falls outside the caller-specified bound, the same way `ExchangeTransactionActuator` rejects trades where `anotherTokenQuant < tokenExpected`.

### Proof of Concept
1. Pool for exchange pair (A, B) has balances `[1000, 1000]`.
2. User U broadcasts `ExchangeInjectContract{token_id=A, quant=100}`, expecting to also inject ~100 of B (ratio 1:1) based on the state they queried right before broadcasting.
3. Before U's transaction is packed, another account executes `ExchangeTransactionContract` that sells a large amount of A into the pool, shifting the balances to `[5000, 200]`.
4. U's `ExchangeInjectContract` now executes against the actuator logic at `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java:79-80`: `anotherTokenQuant = firstTokenBalance * tokenQuant / secondTokenBalance = 5000*100/200 = 2500`.
5. U is debited 100 of A and 2500 of B — 25x more B than they intended — with no on-chain check to prevent this, because `ExchangeInjectContract` has no `expected`/bound field and the actuator performs no comparison against user intent.
