### Title
Sierra-to-CASM/Native compiler subprocess has no wall-clock timeout, only a CPU-time `rlimit` — a malicious declare can hang the compilation worker indefinitely - (File: `crates/apollo_compilation_utils/src/compiler_utils.rs`)

### Summary
The gateway compiles every declared Sierra contract class to CASM (and optionally to native code) by spawning a subprocess and calling the blocking `Command::output()`, which waits until the child exits with no wall-clock deadline. The only enforced limits are POSIX `rlimit`s: `RLIMIT_CPU` (CPU time), `RLIMIT_FSIZE`, and `RLIMIT_AS` (virtual memory). `RLIMIT_CPU` only accounts for time the process is actually scheduled on a CPU — it does not fire while a process is blocked/sleeping/swapping/waiting on I/O. This mirrors the CVE-2023-7250 bug class: a party fully controlling the input can put the server-side worker into a state where it waits indefinitely for something that never completes, and the "watchdog" (rlimit here, timeout there) never triggers because it only measures the wrong resource.

### Finding Description
`compile_with_args` in `crates/apollo_compilation_utils/src/compiler_utils.rs` builds a `Command`, applies `ResourceLimits::apply` (which only calls `setrlimit` for CPU/FSIZE/AS via `pre_exec`, see `crates/apollo_compilation_utils/src/resource_limits/resource_limits_unix.rs`), and then calls `command.output()`, which blocks the calling thread until the child process terminates: [1](#0-0) 

`SierraToCasmCompiler::compile` (used synchronously in the gateway's declare-transaction path) and `SierraToNativeCompiler::compile` (used by the async native-compilation worker thread) both build a `ResourceLimits` from only `max_cpu_time` and `max_memory_usage` (and `max_file_size` for native), with no separate wall-clock timeout: [2](#0-1) [3](#0-2) 

`ResourceLimits` sets only `RLIMIT_CPU`, `RLIMIT_FSIZE`, `RLIMIT_AS`: [4](#0-3) 

`RLIMIT_CPU` fires a `SIGXCPU`/`SIGKILL` only after the process consumes N seconds of *actual CPU time*. If a malicious Sierra program can be crafted so that the compiler subprocess spends most of its wall-clock time blocked rather than running on-CPU (e.g., heavy paging/swap I/O near the `RLIMIT_AS` boundary, lock contention, or any other blocking condition inside the third-party compiler/cairo-native toolchain triggered by adversarial input), the CPU-time limit never triggers even though the subprocess runs indefinitely, and there is no independent wall-clock timeout in `compile_with_args` to kill it.

This is reachable by an unprivileged declare-transaction sender:
- The gateway synchronously compiles Sierra→CASM for every `Declare` transaction while holding a `declare_compilation_semaphore` permit (default `max_concurrent_declare_compilations = 40`), released only after the compilation call returns: [5](#0-4) [6](#0-5) 

- Separately, the blockifier's native compilation worker processes compilation requests from a channel strictly sequentially in a single dedicated thread; if one request never returns, every subsequent native-compilation request queues up (or the channel fills) indefinitely: [7](#0-6) 

### Impact Explanation
If an attacker can craft `N` (up to `max_concurrent_declare_compilations`, default 40) declare transactions whose Sierra payload causes the compiler subprocess to block indefinitely while consuming little CPU time, every compilation permit becomes permanently held (the permit is only released *after* `compile()` returns), and no further declare transactions can ever be admitted by that gateway instance — a persistent denial of service for an entire transaction class, until the process is restarted. The same class of input, if it also stalls the shared native-compilation worker thread, degrades Cairo-native compilation service-wide for all subsequently declared classes. This matches the "network unable to confirm new transactions" bucket (for the declare transaction type) from a single, unprivileged, submitted transaction.

### Likelihood Explanation
Medium confidence/likelihood: the mechanism (CPU-time rlimit not covering blocked/IO-wait time, and no wall-clock timeout around the blocking `Command::output()` call) is confirmed in the code. What is **not verified** from static inspection alone is whether an actual Sierra program can be constructed that reliably drives the underlying `cairo-lang`/`cairo-native` compiler binary into a long-blocked, low-CPU state (e.g., pathological swap thrashing near the `max_memory_usage` limit, or blocking behavior inside the third-party compiler toolchain). Confirming exploitability would require fuzzing/testing the actual compiler binaries with adversarial Sierra inputs under constrained memory, which is outside what can be established by code reading alone.

### Recommendation
- Wrap the compiler subprocess call with an explicit wall-clock timeout (e.g., `tokio::time::timeout` around a `spawn_blocking`, or poll/`wait_timeout` with `SIGKILL` on expiry) in `compile_with_args`, independent of `RLIMIT_CPU`.
- Ensure the permit/semaphore release and any worker-thread state cannot be starved by a single stuck compilation — kill-and-release on timeout rather than relying solely on the subprocess exiting.
- Consider disabling swap for the compiler subprocess's cgroup/container or bounding wall-clock via an external watchdog, since `RLIMIT_AS` bounds address space but not swap I/O duration.

### Proof of Concept
Not independently reproduced — a concrete PoC would require identifying (via fuzzing or targeted testing of the actual `cairo-lang` Sierra→CASM compiler and `cairo-native` compiler binaries) a Sierra program that maximizes wall-clock blocked time (I/O wait / swap thrashing / internal lock contention) relative to on-CPU time, then submitting `max_concurrent_declare_compilations` such declare transactions concurrently to exhaust `declare_compilation_semaphore` permits and observe that legitimate declares are rejected indefinitely with `TransactionLimitExceeded` even after the configured `max_cpu_time` has elapsed for each stuck compilation.

/// A struct to hold resource limits for a process.
/// Each limit is optional and can be set to `None` if not needed.
/// NOTE: This struct is fully implemented only for Unix-like systems.
pub struct ResourceLimits {
    /// A limit (in seconds) on the amount of CPU time that the process can consume.
    cpu_time: Option<RLimit>,
    /// The maximum size (in bytes) of files that the process may create.
    file_size: Option<RLimit>,
    /// The maximum size (in bytes) of the process’s virtual memory (address space).
    memory_size: Option<RLimit>,
}

impl ResourceLimits {
    pub fn new(
        cpu_time: Option<u64>,
        file_size: Option<u64>,
        memory_size: Option<u64>,
    ) -> ResourceLimits {
        ResourceLimits {
            cpu_time: cpu_time.map(|t| RLimit {
                resource: Resource::CPU,
                soft_limit: t,
                hard_limit: t,
                units: "seconds".to_string(),
            }),
            file_size: file_size.map(|x| RLimit {
                resource: Resource::FSIZE,
                soft_limit: x,
                hard_limit: x,
                units: "bytes".to_string(),
            }),
            memory_size: memory_size.map(|y| RLimit {
                resource: Resource::AS,
                soft_limit: y,
                hard_limit: y,
                units: "bytes".to_string(),
            }),
        }
    }

// transaction ingestion before the transaction's signature and balance are verified. Bound the

/// Handles compilation requests from the channel, holding the receiver end of the channel.
/// If no request is available, non-busy-waits until a request is available.
/// When the sender is dropped, the worker processes all pending requests and terminates.
fn run_compilation_worker(
    class_cache: RawClassCache,
    receiver: Receiver<CompilationRequest>,
    compiler: Arc<SierraToNativeCompiler>,
    panic_on_compilation_failure: bool,
) {
    log::info!("Compilation worker started.");
    for compilation_request in receiver.iter() {
        process_compilation_request(
            class_cache.clone(),
            compiler.clone(),
            compilation_request,
            panic_on_compilation_failure,
        )
        .unwrap_or(());
    }
    log::info!("Compilation worker terminated.");
}
