### Title
User enumeration via timing side-channel in `CreateSession` — invalid emails skip bcrypt while valid emails always incur it - ([File: core/sessions/localauth/orm.go])

### Summary
`orm.CreateSession` in `core/sessions/localauth/orm.go` returns immediately on a `FindUser` DB-lookup miss (invalid email), but for any *existing* email it always proceeds to call `utils.CheckPasswordHash` (bcrypt) before returning a failure. Because bcrypt verification is deliberately slow (tens to hundreds of ms) compared to a fast/no-row SQL lookup, an unauthenticated attacker sending POST `/sessions` requests can distinguish valid from invalid emails purely from response latency, without needing to guess the password.

### Finding Description
The relevant code is: [1](#0-0) 

Flow:
1. `o.FindUser(ctx, sr.Email)` runs `SELECT * FROM users WHERE lower(email) = lower($1)` [2](#0-1) . For a nonexistent email this returns `sql.ErrNoRows` almost immediately, and `CreateSession` returns `"", err` right away at line 145-148 — the `constantTimeEmailCompare` and `utils.CheckPasswordHash` calls are **never reached**.
2. For an *existing* email, `FindUser` succeeds, `constantTimeEmailCompare` (a cheap constant-time byte comparison) passes, and then `utils.CheckPasswordHash(sr.Password, string(user.HashedPassword))` is invoked — a bcrypt comparison that is intentionally computationally expensive (cost factor typically yields tens to hundreds of milliseconds).
3. Only after that (i.e., only for existing emails) does the code proceed to `o.GetUserWebAuthn` — an extra DB round trip — reinforcing the latency gap.

The comment in the code ("Do email and password check first to prevent extra database look up for MFA tokens leaking...") shows an awareness of one MFA-token timing leak, but it does not address the much larger and easier-to-measure bcrypt-vs-no-bcrypt latency gap between "email not found" and "email found, password check attempted." No constant-time delay, dummy bcrypt computation, or artificial padding is used to mask the "email not found" fast path from the "the password check ran" slow path.

This is reachable unauthenticated via the `SessionsController.Create` handler wired to POST `/sessions`: [3](#0-2) . The same pattern also exists in the LDAP and OIDC local-fallback authenticators (`localLoginFallback` in `core/sessions/ldapauth/ldap.go` and `core/sessions/oidcauth/oidc.go`), which similarly only reach `utils.CheckPasswordHash` once a user row is found.

No rate limiting, constant-time global response delay, or dummy-hash execution exists in this path to normalize response time for the "email not found" branch. `constantTimeEmailCompare` only protects against a comparison-level timing leak on the email string itself, not against the much larger structural timing difference caused by conditionally skipping bcrypt entirely.

### Impact Explanation
An attacker can enumerate valid Chainlink node admin/API user emails by measuring `/sessions` response latency: fast responses = email not registered, slow (bcrypt-inclusive) responses = email registered. This does not by itself grant authentication bypass or credential disclosure, but it is a real information-disclosure/account-enumeration weakness that directly enables targeted credential stuffing, password spraying, or phishing against confirmed admin accounts — a legitimate precursor step against a node's admin panel. Under Chainlink's bounty categorization this maps to a low/informational-severity information disclosure issue (account enumeration), not a direct fund-loss or node-compromise bug.

### Likelihood Explanation
Highly feasible and repeatable: the attacker only needs unauthenticated network access to POST `/sessions` repeatedly, and can average many samples to overcome network jitter, since bcrypt's cost difference is on the order of 10-100x the typical fast SQL miss. No special privileges, secrets, or race conditions are required, making this a low-effort, low-precondition side channel.

### Recommendation
Make the failure timing independent of whether the email exists:
- Always perform a bcrypt comparison against a real or dummy hash, even when the email lookup misses (e.g., use a precomputed dummy bcrypt hash for the "user not found" branch so `CheckPasswordHash` is always invoked).
- Alternatively, enforce a fixed minimum response latency for the entire `/sessions` POST failure path (padding fast paths to match the slow path).
- Apply rate-limiting/backoff per source IP and per attempted email on `/sessions` to reduce statistical feasibility of timing fuzzing.

### Proof of Concept
Fuzz/timing test plan (extending `core/sessions/localauth/orm_test.go`):
1. Create a known user via `orm.CreateUser`.
2. Loop N (e.g., 200) times calling `orm.CreateSession(ctx, sessions.SessionRequest{Email: knownEmail, Password: "wrong-password"})`, recording wall-clock duration for each call.
3. Loop N times calling `orm.CreateSession(ctx, sessions.SessionRequest{Email: "definitely-not-a-user@example.com", Password: "wrong-password"})`, recording durations.
4. Assert (e.g., via a statistical test such as Mann-Whitney U or simple mean/percentile comparison) that the two duration distributions are significantly different (mean duration for known-email path >> mean duration for unknown-email path, driven by the bcrypt call).
5. Expected result confirming the bug: known-email failure latency distribution is measurably and consistently higher (by roughly the bcrypt verification cost) than unknown-email failure latency distribution, demonstrating a reliable enumeration oracle.

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```

```go
func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}
```
