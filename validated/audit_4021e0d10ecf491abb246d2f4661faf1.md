## Title
`PinkasWUF::verify_proof` accepts an empty (zero-share) `Proof` as a trivially valid proof - ([File: crates/aptos-dkg/src/weighted_vuf/pinkas/mod.rs])

### Summary
The production weighted-VUF implementation used for on-chain randomness, `PinkasWUF` (aliased as `WVUF` in [1](#0-0) ), does not reject a `Proof` containing zero contributing player shares in `verify_proof`. The batched pairing check degenerates to a trivial pass when `proof.len() == 0`.

### Finding Description
`verify_proof` in `crates/aptos-dkg/src/weighted_vuf/pinkas/mod.rs` only guards against `proof.len() > apks.len()`, never against `proof.len() == 0`: [2](#0-1) 

With an empty proof (`proof.len() == 0`):
- `taus = get_powers_of_tau(&tau, 0)` is empty.
- `shares` (parallel map over `proof.par_iter().zip(taus.par_iter())`) is empty.
- `pis` (built by iterating `for (player, _) in proof`) is empty.
- `sum_of_taus: Scalar = taus.iter().sum()` evaluates to `Scalar::ZERO` for an empty iterator.
- `h_tau = h.mul(sum_of_taus)` is therefore the **identity element** of G1 (point at infinity), regardless of `msg`. [3](#0-2) 

The final check becomes `parallel_multi_pairing([pp.g_neg], [h_tau=identity])`, which is `pairing(g_neg, identity) = Gt::identity()`. Since the only comparison is `!= Gt::identity()`, this check passes trivially and `verify_proof` returns `Ok(())` for an empty proof — no shares, no APKs, and no cryptographic binding to `msg` are actually checked.

### Impact Explanation
This matches the exploit hypothesis in the review question: `verify_proof` does **not** reject an empty-share `Proof` before it could be handed to `derive_eval`. Any unprivileged/attacker-controlled or malformed `Proof` value with zero shares (e.g., malformed randomness share aggregation, a corrupted/replayed on-chain artifact, or a proof deserialized from an authenticated response) would be accepted as "verified" by this function alone. If any caller relies on `verify_proof` succeeding as the sole gate before treating the associated evaluation as valid randomness (or before calling `derive_eval`), this is a state-integrity concern for the on-chain randomness pipeline, since `PinkasWUF` backs `types::randomness::WVUF`. This is a violation of the intended security property described directly above the trait's `verify_proof` signature — that a verified proof implies ">33% of the stake must've contributed."

### Likelihood Explanation
I was not able to fully trace, within the available tool budget, whether `derive_eval` is ever invoked without confirming `proof.len() > 0` via some other check upstream (e.g., inside `collect_lagrange_coeffs_shares_and_rks`, or in consensus/rand call sites), nor could I locate all production call sites that invoke `verify_proof` (only benchmark and trait-definition references were found via search; consensus call sites were not found in the indexed portion of the repository). Because of this gap, I cannot conclusively confirm end-to-end mainnet impact (i.e., that a degenerate `Evaluation` actually gets treated as valid randomness on the seed-consumption path) — only that `verify_proof` itself, in isolation, incorrectly returns `Ok(())` for a zero-share proof, which is the exact defect the question asks about.

### Recommendation
Add an explicit `proof.is_empty()` check (return `Err` / `bail!`) at the start of `PinkasWUF::verify_proof` (and defensively in `BlsWUF::verify_proof` / `derive_eval` as well), before any pairing computation, so a proof with zero contributing shares can never be judged "verified."

let pp: PublicParameters = /* valid public params */;

let apks: Vec<Option<APK>> = vec![]; // no APKs known
let empty_proof: Proof = vec![];     // zero contributing shares

assert!(result.is_ok()); // BUG: passes, instead of expected Err

Given `apks.len() == 0`, the `proof.len() > apks.len()` guard (`0 > 0`) does not trigger; the pairing check then reduces to `pairing(g_neg, identity) == Gt::identity()`, which is always true — `verify_proof` incorrectly returns `Ok(())`. [4](#0-3) [3](#0-2)
