## Analysis

The Morpho report is about a class of bug: **the outer protocol layer (Morpho) omits threshold/pause checks that exist as configuration in the underlying/adjacent layer, letting user-triggered mint/borrow-like actions bypass those guardrails.** The Push Chain analog is `x/uregistry`'s `TokenConfig`, which defines exactly the same two guardrail fields — `Enabled` ("whether this token is enabled for minting/bridging") and `LiquidityCap` ("max supply cap for this token") — [1](#0-0)  but neither is read anywhere in the actual mint execution path in `x/uexecutor`.

`depositPRC20`, the function that mints the PRC20 representation for every inbound (`FUNDS`, `FUNDS_AND_PAYLOAD`, `GAS_AND_PAYLOAD`), only reads `NativeRepresentation.ContractAddress` and the amount, then unconditionally calls `CallPRC20Deposit`: [2](#0-1) 

By contrast, `x/uregistry`'s `IsChainInboundEnabled` / `IsChainOutboundEnabled` (the chain-level pause) **is** enforced in `MsgVoteInbound`/`ExecutePayload`/outbound creation, and is unit-tested for exactly this purpose [3](#0-2) . But there is no equivalent call site anywhere in the codebase that reads `TokenConfig.Enabled` or `TokenConfig.LiquidityCap` at execution time — a search across the whole repo shows `LiquidityCap` only appears in proto-generated getters, `ValidateBasic` (which just checks the string is non-empty, not that any running total respects it) [4](#0-3) , and test fixtures — never in `x/uexecutor`'s deposit/mint flow.

### Title
Missing enforcement of `TokenConfig.Enabled` and `TokenConfig.LiquidityCap` during PRC20 minting - (File: `x/uexecutor/keeper/handler.go`)

### Summary
`x/uregistry.TokenConfig` defines a token-level `Enabled` pause flag and a `LiquidityCap` max-supply threshold, analogous to Compound's `borrowGuardianPaused[cToken]` and `borrowCaps[cToken]`. Just as the report describes Morpho omitting those Compound-level checks on its own borrow path, Push Chain's `depositPRC20` (called by every `FUNDS`/`FUNDS_AND_PAYLOAD`/`GAS_AND_PAYLOAD` inbound execution) never reads either field before minting PRC20 to the recipient.

### Finding Description
`depositPRC20` fetches the `TokenConfig` solely to resolve the PRC20 contract address (`tokenConfig.NativeRepresentation.ContractAddress`) and then calls `CallPRC20Deposit`/`CallPRC20DepositAutoSwap` with the raw inbound amount — no comparison against `tokenConfig.LiquidityCap`, and no check of `tokenConfig.Enabled`. [2](#0-1)  This is called from every inbound-funds execution path: `ExecuteInboundFunds`, `ExecuteInboundFundsAndPayload`, and `ExecuteInboundGasAndPayload`. [5](#0-4) [6](#0-5) 

Meanwhile the chain-level pause (`IsChainInboundEnabled`/`IsChainOutboundEnabled`) *is* enforced and tested at `MsgVoteInbound`, `ExecutePayload`, and outbound-creation time, confirming the codebase's own design intent is that admin-set flags on `uregistry` config gate execution — yet the token-level `Enabled`/`LiquidityCap` fields are wired into `ValidateBasic` for admin messages only, never into the runtime mint path. [7](#0-6) 

### Impact Explanation
Any ordinary, unprivileged user who deposits/transfers the registered external token through the standard gateway/inbound flow causes honest Universal Validators to vote the inbound through, and the core validator's `depositPRC20` will mint the corresponding PRC20 with no regard to:
- `LiquidityCap` — the configured maximum PRC20 supply can be silently exceeded purely through normal user deposit volume, corrupting the intended PRC20 supply-accounting invariant that `uregistry` is supposed to enforce.
- `Enabled=false` — if an admin disables a token (the documented mechanism to halt minting/bridging for a token, e.g. in response to a detected issue on the source chain), users can still deposit and have PRC20 minted, because nothing in the mint path checks this flag — a pause bypass exactly mirroring the `borrowGuardianPaused` gap called out in the report.

Both are reachable purely from ordinary user deposit paths, matching the "in scope" criteria for corruption of PRC20 accounting from unprivileged action.

### Likelihood Explanation
High for the `LiquidityCap` gap: it triggers under completely normal usage (aggregate deposits exceeding the configured cap), no attacker sophistication required. The `Enabled=false` bypass requires the admin to have set the flag with intent to halt a token, at which point any user depositing that token still succeeds — also low-effort to trigger.

### Recommendation
In `depositPRC20` (and the auto-swap variant), before calling `CallPRC20Deposit`/`CallPRC20DepositAutoSwap`:
1. Reject/queue-for-revert the deposit if `tokenConfig.Enabled == false`, mirroring the existing `IsChainInboundEnabled` pattern already enforced elsewhere in `x/uexecutor`.
2. Track cumulative minted PRC20 supply per token (or query the PRC20 contract's `totalSupply`) and reject/cap the deposit if it would push supply above `tokenConfig.LiquidityCap`, mirroring Compound's `borrowCaps` check.

If, like Morpho, the team decides these checks are intentionally omitted (e.g., because the fields are meant as off-chain/admin-side signals rather than on-chain enforcement), this should be explicitly documented next to the `TokenConfig.Enabled`/`LiquidityCap` proto fields and in `x/uregistry/README.md`, since currently the README's own state-layout table implies these are enforced invariants ("liquidity cap" is presented as protocol config, not merely informational metadata). [8](#0-7) 

### Proof of Concept
1. Admin registers a `TokenConfig` with `LiquidityCap = "1000000"` (or sets `Enabled=false` after initial registration).
2. A user (or many users) submits a source-chain deposit event for that token with amount exceeding the cap (or any amount while `Enabled=false`).
3. Universal Validators observe and vote `MsgVoteInbound`; ballot passes with honest 2/3+ votes.
4. `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` executes and mints the full amount, verifiable via the resulting `PCTx` `"SUCCESS"` status and the recipient's increased PRC20 balance — with no error referencing `LiquidityCap` or `Enabled`, unlike the existing `"inbound is disabled for chain ..."` error that *is* produced when `IsChainInboundEnabled` is false. [9](#0-8)

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// ValidateBasic performs sanity checks on the TokenConfig
func (p TokenConfig) ValidateBasic() error {
	if strings.TrimSpace(p.Chain) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "chain cannot be empty")
	}

	if strings.TrimSpace(p.Address) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token contract address cannot be empty")
	}

	// Enforce a parseable address for the chain's namespace (e.g. 20-byte hex
	// for eip155, base58 for solana) so every registration lands on the
	// canonical storage key.
	if _, err := utils.CanonicalizeAddressByNamespace(p.Chain, p.Address); err != nil {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token address for chain %s: %s", p.Chain, err)
	}

	if strings.TrimSpace(p.Name) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token name cannot be empty")
	}

	if strings.TrimSpace(p.Symbol) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token symbol cannot be empty")
	}

	if p.Decimals == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "decimals must be greater than zero")
	}

	// Validate token_type is within known enum range
	if _, ok := TokenType_name[int32(p.TokenType)]; !ok {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token_type: %v", p.TokenType)
	}

	if strings.TrimSpace(p.LiquidityCap) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "liquidity_cap cannot be empty")
	}

	if p.NativeRepresentation == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "native_representation is required")
	}
	if err := p.NativeRepresentation.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid native representation")
	}

	return nil
}
