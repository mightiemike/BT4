### Title
Permanent loss-of-funds DoS in the NEAR Wallet Contract via gas-griefed async callback that leaves `has_in_flight_tx` stuck `true` - (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (used for Ethereum-style transaction emulation on NEAR-native accounts) enforces "one in-flight transaction at a time" via a boolean flag `has_in_flight_tx` that is set `true` before a cross-contract promise is dispatched and is only reset to `false` inside the async callback that resolves that promise. Because NEAR reverts *all* state writes of a receipt that fails (including out-of-gas failures), an attacker-controlled target contract can return an oversized (up to `max_length_returned_data`, 4 MiB) successful result to force the low-gas-budgeted callback to run out of gas before it can persist `has_in_flight_tx = false`. This permanently locks the wallet's owner out of `rlp_execute`, freezing all assets/actions reachable only through that wallet contract — directly analogous to the reported "loss of funds by griefing" pattern (push-callback failure blocking recovery/repayment), except here the "push" is a state-flag write instead of a token transfer.

### Finding Description
`WalletContract::rlp_execute` sets `self.has_in_flight_tx = true` and returns a `Promise` chain that is only supposed to reset the flag back to `false` inside a terminal callback: [1](#0-0) 

The generic path for arbitrary target contract actions builds the promise chain as `action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))`, where `target` is attacker/owner-chosen and `rlp_execute_callback` is allocated only `RLP_EXECUTE_CALLBACK_GAS = Gas::from_tgas(5)`: [2](#0-1) [3](#0-2) 

The callback resets the flag at its very start, then inspects the single promise result and, on success, wraps the raw returned bytes (up to `max_length_returned_data`) directly into `ExecuteResponse.success_value`: [4](#0-3) 

The NEP-141 storage-balance path has the same shape and an even smaller gas allowance for JSON deserialization of an attacker-controlled `storage_balance_of` response: [5](#0-4) [6](#0-5) 

The protocol allows any successful promise/data receipt to carry up to `max_length_returned_data` (4 MiB on the mainnet/testnet runtime configs) of return data: [7](#0-6) [8](#0-7) 

If the target's callee returns a value near this maximum, the receiving of that value into the register, copying it into the `ExecuteResponse` struct, and/or (in the NEP-141 case) `serde_json::from_slice`-parsing it, is very likely to exceed the small (5–15 TGas) budget reserved for the callback. When a receipt's execution runs out of gas (or otherwise fails), NEAR discards all state changes attempted by that receipt — this is the fundamental "all-or-nothing" state-commit semantics of receipt execution. Consequently the `self.has_in_flight_tx = false` write at the top of the callback is never committed, and the flag remains permanently `true`.

Once `has_in_flight_tx` is stuck `true`, every future call to `rlp_execute` on that wallet is rejected up front: [9](#0-8) 
and there is no owner-facing reset/recovery function in the contract — the account's Ethereum-transaction-emulation capability, and therefore any funds or approvals only reachable through it, become permanently inaccessible. This mirrors the reported bug class: a callback meant to finalize/settle state (there: debt repayment; here: releasing the in-flight lock) is coupled to an externally-influenced payload whose failure mode is unhandled, causing irreversible loss of access.

### Impact Explanation
This is a concrete, permanent denial-of-funds-access for any account using the NEAR Wallet Contract's Ethereum-transaction-emulation feature: after the griefed callback fails, the wallet can never again process an `rlp_execute` call, since the guard at the top of `rlp_execute` unconditionally rejects any call while `has_in_flight_tx` is `true`, and nothing in the contract clears it. Any balance, allowance, or in-progress operation intended to be executed via this wallet becomes frozen indefinitely — matching the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
The trigger requires only a single, unprivileged, attacker-reachable action: getting an `rlp_execute` call routed (either by the account owner themselves interacting with a hostile contract, or by any relayer submitting the owner's already-signed RLP transaction) to a `target`/`token_id` account that returns a large (up to 4 MiB) successful response from the method invoked (arbitrary method for the generic path, or `storage_balance_of` for the NEP-141 path). No special privileges, validator collusion, or network-level assumptions are needed — deploying a contract that returns an oversized value on a given method is trivial, and the `max_length_returned_data` protocol limit (4 MiB) is far larger than the ~5–15 TGas callback budgets can safely process.

### Recommendation
- Do not gate the "one transaction in flight" invariant behind a callback that must succeed under an attacker-influenced gas budget. Instead, decouple flag-clearing from payload processing: clear `has_in_flight_tx` unconditionally as the very first, minimal-gas action, or track "in-flight" status via a scheme that cannot be starved of gas by an oversized promise result (e.g., a lightweight always-succeeds callback that only clears the flag and forwards raw results, or use a fixed generous gas reservation independent of the payload size, capped strictly below the returned-value size that's actually needed).
- Bound how much of a promise's returned data is copied/deserialized by these callbacks (e.g., truncate or reject oversized results before doing further processing), rather than assuming call results are always small.
- Add an owner-controlled/administrative recovery path (e.g., a "force-clear stuck flag after N blocks with no pending receipt" mechanism) as defense-in-depth.

### Proof of Concept
1. Deploy a malicious contract `evil.near` implementing an arbitrary method (or a fake NEP-141 `storage_balance_of`) that on invocation calls `env::value_return` with a payload close to `max_length_returned_data` (4 MiB).
2. Craft/sign an Ethereum-style transaction whose action targets `evil.near` and invokes that method (for the generic path any `TransactionKind` other than the special-cased base-token/self-transfer kinds funnels through `action_to_promise(target, action)?.then(ext.rlp_execute_callback(...))`).
3. Submit `rlp_execute(target: "evil.near", tx_bytes_b64: <encoded tx>)` to the wallet contract.
4. Observe: `has_in_flight_tx` is set `true` at `lib.rs:118`; the promise to `evil.near` succeeds and returns the large payload; `rlp_execute_callback` (only `RLP_EXECUTE_CALLBACK_GAS = 5 TGas`) attempts to wrap the large value into `ExecuteResponse` and exceeds its gas allocation, failing the receipt.
5. Because the receipt failed, the `self.has_in_flight_tx = false` write at `lib.rs:280` is discarded; state persists with `has_in_flight_tx == true`.
6. Any subsequent call to `rlp_execute` on this wallet now unconditionally returns the "transaction already in progress" error at `lib.rs:97-105`, permanently, with no recovery path in the contract.

    pub fn nep_141_storage_balance_callback(
        &mut self,

        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,

        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

/// Validates given data receipt. Checks validity of the length of the returned data.
fn validate_data_receipt(
    limit_config: &LimitConfig,
    receipt: &DataReceipt,
) -> Result<(), ReceiptValidationError> {
    let data_len = receipt.data.as_ref().map(|data| data.len()).unwrap_or(0);
    if data_len as u64 > limit_config.max_length_returned_data {
        return Err(ReceiptValidationError::ReturnedValueLengthExceeded {
            length: data_len as u64,
            limit: limit_config.max_length_returned_data,
        });
    }
    Ok(())
}
