### Title
Precision-loss in legacy bandwidth/energy resource-limit formula from truncating division before multiplication - (File: `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`, `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
The externally reported sfrxEth bug is a classic "divide-then-multiply vs multiply-then-divide" precision defect: performing the integer division before the multiplication truncates a fractional component that should have survived until the final step, systematically distorting the computed value. java-tron's legacy (non-hardened) resource-limit formulas for bandwidth and energy contain the exact same bug class: they perform an early integer division (`frozeBalance / TRX_PRECISION`) before multiplying by the limit/weight ratio, discarding the fractional weight that the codebase's own "hardened" replacement (which multiplies everything first, then divides once at the end using `BigInteger`) proves should be preserved.

### Finding Description
`BandwidthProcessor.calculateGlobalNetLimit` and `EnergyProcessor.calculateGlobalEnergyLimit` compute a user's per-resource limit from their frozen TRX balance. The legacy path does:
```java
long netWeight = frozeBalance / TRX_PRECISION;
return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
``` [1](#0-0) 

and analogously:
```java
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
``` [2](#0-1) 

This truncates `frozeBalance` down to a multiple of `TRX_PRECISION` *before* applying the limit/weight ratio, discarding any fractional weight component — mathematically identical in structure to the sfrxEth bug where `frxAmount` was divided by `price_oracle` at the wrong point in the expression, distorting the final result. The codebase itself acknowledges this is wrong: it ships a "hardened" replacement, explicitly documented as fixing exactly this truncation-order problem, that multiplies everything first and divides only once at the end with exact `BigInteger` arithmetic:
```java
protected long calculateGlobalLimitV2(long frozeBalance,
    long totalLimit, long totalWeight) {
  return BigInteger.valueOf(frozeBalance)
      .multiply(BigInteger.valueOf(totalLimit))
      .divide(BigInteger.valueOf(TRX_PRECISION)
          .multiply(BigInteger.valueOf(totalWeight)))
      .longValueExact();
}
``` [3](#0-2) 

The doc comment on this method explicitly states the legacy formula's flaw: *"fractional weight (i.e. `frozeBalance < TRX_PRECISION`) is preserved through the multiplication and only truncated at the final divide, so small balances yield the same proportional result as the double-arithmetic path"* — confirming the legacy path does **not** preserve fractional weight and yields a different (incorrect) proportional result, exactly the sfrxEth-style order-of-operations defect.

The hardened path is gated behind `hardenCalculation()` / `hardenResourceCalculation()` flags read from `DynamicPropertiesStore` (controlled via a chain committee proposal, e.g. `ProposalUtil`), meaning the legacy, precision-lossy formula remains the live, default-active code path for every account computing its bandwidth/energy resource limit until/unless that proposal is passed. This computation is triggered on ordinary, unprivileged flows — any account that freezes TRX for bandwidth/energy and then broadcasts a normal transaction exercises `BandwidthProcessor`/`EnergyProcessor` limit checks. [4](#0-3) [5](#0-4) 

### Impact Explanation
The distorted resource-limit calculation affects the fairness and correctness of bandwidth/energy allocation for every network participant, since the legacy formula truncates the frozen-balance weight before applying the ratio rather than after, in exact analogy to how the sfrxEth `ethPerDerivative()` distortion overstated/understated user proceeds. This is not a fund-theft primitive by itself, but it is a systemic resource/reward-accounting inaccuracy reachable by any account via ordinary freeze + transact operations, falling within the allowed "resource and reward accounting" category. The project's own test suite (`CalculateGlobalLimitHardenTest`, `RepositoryImplHardenTest`) demonstrates concretely that the legacy and hardened formulas diverge, with one test explicitly computing a "buggy" value and asserting it differs from the correct one. [6](#0-5) 

### Likelihood Explanation
The divergence is deterministic and occurs whenever `frozeBalance` is not an exact multiple of `TRX_PRECISION` (1,000,000 sun) — a very common case for real frozen balances — and requires no privileged access; it happens automatically for any account under the legacy (default, un-hardened) code path.

### Recommendation
Enable/complete the transition to the `hardenCalculation()`/`hardenResourceCalculation()` `BigInteger`-based formulas (`calculateGlobalLimitV1`/`V2`) as the default and permanent behavior, removing reliance on the legacy divide-before-multiply double-arithmetic path, consistent with the mitigation pattern from the sfrxEth report (multiply first, divide last, with exact arithmetic).

### Proof of Concept
Given `frozeBalance = 1,999,999` (just under 2 * `TRX_PRECISION`), `totalNetLimit = 43,200,000,000`, `totalNetWeight = 2,000,000,000`:
- Legacy: `netWeight = 1,999,999 / 1,000,000 = 1` (truncated), result ≈ `1 * 21.6 = 21` (using the ratio `totalNetLimit/totalNetWeight = 21.6`).
- Hardened (`calculateGlobalLimitV2`): `BigInteger` computes `1,999,999 * 43,200,000,000 / (1,000,000 * 2,000,000,000)` ≈ `43`, roughly double the legacy result.

This mirrors the report's PoC pattern (comparing the buggy order-of-operations result against the corrected one) and is directly confirmed by the project's own divergence tests. [7](#0-6)
