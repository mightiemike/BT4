### Title
Premature dedup-cache insertion in `broadcastTransaction` permanently blocks legitimate transaction resubmission after transient failure - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.broadcastTransaction()` inserts the incoming transaction's hash into `dbManager.getTransactionIdCache()` *before* the transaction has actually been validated and accepted into the pending pool. If any later step in the same call throws (signature/contract validation, resource insufficiency, TAPOS/expiration checks, P2P broadcast failure, etc.), the transaction never gets applied, yet its ID remains locked in the cache for the cache's full TTL, permanently rejecting any legitimate resubmission of that exact transaction as a duplicate. This mirrors the reported bug class: a reuse/dedup lock is set on the first attempt rather than after successful completion, defeating retries and silently discarding a user's transaction.

### Finding Description
In `broadcastTransaction`, the cache write happens well before the transaction is pushed: [1](#0-0) 

```java
if (trxCacheEnable) {
  if (dbManager.getTransactionIdCache().getIfPresent(txID) != null) {
    ...
    return builder.setResult(false).setCode(response_code.DUP_TRANSACTION_ERROR)...
  } else {
    dbManager.getTransactionIdCache().put(txID, true);
  }
}
```

Only after this unconditional `put` does the code proceed to validate the contract, check expiration, and actually call `dbManager.pushTransaction(trx)` and broadcast to peers: [2](#0-1) 

Any exception thrown afterward — `ValidateSignatureException`, `ContractValidateException`, `ContractExeException`, `AccountResourceInsufficientException`, `TaposException`, `TooBigTransactionException`, `TransactionExpirationException`, or even a P2P broadcast shortfall (`NOT_ENOUGH_EFFECTIVE_CONNECTION`) — is caught and returned as a failure response, but the code never removes the entry it already wrote into `transactionIdCache`: [3](#0-2) 

This is analogous to the reported `bridge-withdraw` TOTP issue: the "used" marker is written on the **first attempt**, independent of whether that attempt actually succeeds, so every subsequent legitimate resubmission with the identical transaction bytes (same hash, e.g. same signature/expiration produced by a wallet or SDK retrying after a timeout) is rejected with `DUP_TRANSACTION_ERROR` even though the transaction was never applied to state or broadcast. The existing unit test `testBroadcastTransactionAlreadyExists` confirms the cache-based short-circuit behavior: [4](#0-3) 

Note that `containsTransaction`/`validateDup` in `Manager` is a *separate*, correctly-ordered duplicate check based on `TransactionCache`/`TransactionStore` (checked only once the transaction actually reaches `processTransaction`), which is not the defect here: [5](#0-4) 

The defect is specifically the early, unconditional `put` into the separate short-TTL `transactionIdCache` gate inside `broadcastTransaction`, which fires before any of the downstream validation/push/broadcast steps that can fail.

### Impact Explanation
Any client (wallet, exchange, SDK) that constructs a transaction and retries broadcasting it after a transient error (gRPC timeout, temporary "not enough effective connections", momentary resource shortage causing `AccountResourceInsufficientException`, etc.) will find every retry rejected with `DUP_TRANSACTION_ERROR`, even though the transaction was never accepted or executed. This is a reachable-from-anonymous-RPC denial-of-service against legitimate transaction submission: an unprivileged caller's own transaction can become permanently unsubmittable for the duration of the cache TTL, causing silent transaction loss ("fire and forget" broadcast APIs typically don't distinguish "already succeeded" from "blocked by stale lock"). It does not directly corrupt consensus state or leak keys, but it degrades transaction-submission availability/integrity for normal users interacting via the public broadcast RPC.

### Likelihood Explanation
The scenario requires only a transient/legitimate failure after the cache is populated — e.g., a momentary drop below `minEffectiveConnection`, a race where bandwidth/energy is briefly insufficient, or a contract validation failure on the first attempt followed by a valid resubmission of the identical, unmodified transaction (same hash). None of this requires a privileged actor, malicious peer, or special network position; it is triggerable by any normal client that retries a broadcast, making it moderately likely to occur in production under normal transient-failure conditions (matching the "Medium" likelihood of the original report).

### Recommendation
Move the `transactionIdCache.put(txID, true)` call to occur only after the transaction has been successfully validated and accepted (e.g., right before or immediately after a successful `dbManager.pushTransaction(trx)` call and successful broadcast), or wrap the current logic in a `try/finally`/`catch` that removes (`invalidate`) the `txID` entry from `transactionIdCache` whenever any exception is thrown or the broadcast otherwise fails, so that a subsequent legitimate resubmission of the same transaction is not permanently blocked.

### Proof of Concept
1. Submit a transaction via `broadcastTransaction` at a moment when `tronNetDelegate.getActivePeer()` effective-connection count is transiently below `minEffectiveConnection` (or trigger any other post-cache-insert exception path, e.g. by having insufficient bandwidth so `AccountResourceInsufficientException` is thrown from `dbManager.pushTransaction`).
2. Observe the call reaches line 564 and inserts `txID` into `transactionIdCache` before line 578/600 return the failure response — the transaction was never pushed/broadcast successfully.
3. Immediately resubmit the identical transaction bytes (same `txID`) via `broadcastTransaction`.
4. Observe the second call short-circuits at [6](#0-5)  returning `DUP_TRANSACTION_ERROR`, even though the transaction was never actually accepted into the pending pool or broadcast to peers — confirmed by the existing test pattern in `testBroadcastTransactionAlreadyExists` which shows the cache alone is sufficient to produce this response regardless of transaction execution state.

  void validateDup(TransactionCapsule transactionCapsule) throws DupTransactionException {
    if (containsTransaction(transactionCapsule)) {

    }

  private boolean containsTransaction(TransactionCapsule transactionCapsule) {
    return containsTransaction(transactionCapsule.getTransactionId().getBytes());
  }


  private boolean containsTransaction(byte[] transactionId) {
    if (transactionCache != null && !transactionCache.has(transactionId)) {
      // using the bloom filter only determines non-existent transaction
      return false;
    }

    return chainBaseManager.getTransactionStore()
        .has(transactionId);
  }
