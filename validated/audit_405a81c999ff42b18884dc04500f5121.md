## Analog validated in java-tron

### Title
Unbounded `DelegatedResourceAccountIndex` growth per address enables cheap state/query-cost griefing via public `getdelegatedresourceaccountindexv2` API - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`DelegateResourceContract` lets any account delegate as little as 1 TRX of frozen bandwidth/energy to an arbitrary number of distinct receiver addresses, with no limit on how many unique delegation relationships (and therefore index entries) an address can accumulate. Each delegation adds a permanent DB entry keyed by `V2_FROM_PREFIX/V2_TO_PREFIX + address`, and the public/solidity/PBFT `getdelegatedresourceaccountindexv2` API reconstructs the full list for an address by scanning **all** entries under that prefix, exactly the same growth+iteration pattern flagged in the report for `activeWorkerIds`.

### Finding Description
`DelegateResourceActuator.validate()` only enforces `delegateBalance >= 1 TRX` and that the receiver differ from the owner and not be a contract; it places no cap on how many distinct receiver addresses one owner can delegate to, nor how many distinct delegators one receiver can accumulate. [1](#0-0) [2](#0-1) 

Execution unconditionally records the relation via `delegateV2`, which writes two more keys to `DelegatedResourceAccountIndexStore` with no size check or deduplication limit: [3](#0-2) [4](#0-3) 

Later, when any user queries this address's delegation index (via `getDelegatedResourceAccountIndexV2`, exposed over gRPC, HTTP, Solidity-node, and PBFT-node APIs), the store performs a full **prefix scan** over the database for all keys matching that address, sorts them, and materializes the entire list into memory: [5](#0-4) 

This is functionally the same class of bug as `activeWorkerIds` in the report: a permissionless, cheap action grows an unbounded collection with no cap, and a downstream function loops/scans over the entire collection whenever it's accessed. The public endpoints that trigger this scan are wired into every full node, solidity node, and PBFT node: [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker with a trivial amount of TRX (1 TRX minimum delegation, refundable/reusable across many freshly generated receiver addresses, no requirement that receivers hold meaningful balance beyond existing as an account) can create an arbitrarily large number of delegation index entries tied to a single address. Any subsequent call to `getdelegatedresourceaccountindexv2` (or the V1 `getIndex`/`getWithPrefix` equivalent) for that address forces the serving node to scan and materialize the entire, attacker-inflated key range, consuming disproportionate CPU/IO on the public API-serving node relative to the near-zero cost paid by the attacker. Since this endpoint is exposed on every full node's public wallet API (and gRPC/PBFT/Solidity variants), this is a shared-infrastructure resource whose service quality degrades for all other API users when hit against a poisoned address, matching the "gas-grief"/DoS impact class from the report, translated to public API resource exhaustion rather than EVM gas.

### Likelihood Explanation
Low-to-medium: exploitation requires only issuing many low-value `DelegateResourceContract` transactions (bandwidth/energy cost is minimal for system contracts and the delegated TRX is recoverable by undelegating later), so it is cheap and repeatable, similar to the "unprofitable due to bond" caveat in the original report — the funds aren't lost, only temporarily locked, and gas cost for the attacker itself stays low. It requires many transactions to build a sufficiently large list to matter, and impact is confined to nodes serving the specific query (not consensus-breaking), which lowers overall severity relative to the original finding.

### Recommendation
Add either an upper bound on the number of distinct `toAccounts`/`fromAccounts` (or unique from/to prefix keys) an address may accumulate in `DelegatedResourceAccountIndexStore`, or replace the full-list reconstruction in `getWithPrefix`/`getIndex` with paginated/limited queries (similar to the existing `getPaginatedExchangeList`/`getPaginatedProposalList` patterns already present in `Wallet.java`) so that a single request cannot force an unbounded database scan.

### Proof of Concept
1. Fund an attacker account and freeze balance V2 for bandwidth/energy.
2. Generate N (e.g., 100,000) fresh receiver addresses, each with a minimal existing account.
3. Submit N `DelegateResourceContract` transactions, each delegating the minimum 1 TRX from the attacker address to a distinct receiver — validated and executed without any cap, per `DelegateResourceActuator.validate()`/`delegateResource()`.
4. Call `/wallet/getdelegatedresourceaccountindexv2` (or the gRPC/PBFT/Solidity equivalents) for the attacker address; observe the node performing a prefix scan of N entries in `DelegatedResourceAccountIndexStore.getWithPrefix()`, materializing and sorting the full list on every single request, degrading that endpoint's latency/throughput for all callers.

  public DelegatedResourceAccountIndexCapsule getIndex(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = get(address);
    if (indexCapsule != null) {
      return indexCapsule;
    }
    return getWithPrefix(FROM_PREFIX, TO_PREFIX, address);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
