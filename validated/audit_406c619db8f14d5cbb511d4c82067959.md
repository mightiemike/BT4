### Title
Constant-call path (`triggerconstantcontract`/`estimateenergy`) grants unauthenticated callers a higher energy ceiling and a separate CPU-time budget than any paid broadcast transaction can afford, enabling cheaper CPU-DoS via Stack-heavy bytecode — ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
`VMActuator.call()` builds two structurally different `ProgramInvoke` configurations depending on `isConstantCall`: broadcast calls get `energyLimit = getTotalEnergyLimit(...)` (bounded by the caller's paid `feeLimit`/`energyFee` and account resources), while constant calls get `energyLimit = maxEnergyLimit`, a fixed ceiling unrelated to any fee payment. [1](#0-0)  The CPU-time budget for the same execution is also computed via a distinct branch, `calculateCpuLimitInUs(isConstantCall, maxCpuTimeOfOneTx, cpuLimitInUsRatio, CommonParameter.getInstance().getConstantCallTimeoutMs())`, meaning constant calls are bounded by a dedicated `constantCallTimeoutMs` config value instead of the per-broadcast-tx CPU ratio. [2](#0-1)  Because `triggerconstantcontract`/`estimateenergy` require no signature and no fee (`Wallet.callConstantContract` only checks `Args.getInstance().isSupportConstant()` before running the VM), an anonymous caller can drive VM execution against this higher, fee-decoupled energy ceiling for free.

### Finding Description
`Wallet.triggerConstantContract` → `Wallet.callConstantContract` builds a `TransactionContext` and directly calls `VMActuator.validate/execute` — it does not perform `TransactionCapsule.validateSignature`, bandwidth/energy-fee deduction, or permission checks that a broadcast transaction undergoes. [3](#0-2)  This is reachable from unauthenticated HTTP (`TriggerConstantContractServlet.doPost`) and gRPC (`RpcApiService`/`RpcApiServiceOnSolidity`'s `triggerConstantContract`). [4](#0-3) [5](#0-4) 

Inside `VMActuator.call()`, the two paths diverge in `energyLimit` (fee-bounded for broadcast vs. `maxEnergyLimit` for constant) and in the CPU-time ceiling supplied to `Program` (`getConstantCallTimeoutMs()` for constant vs. the normal `maxCpuTimeOfOneTx`/ratio for broadcast). [6](#0-5)  Both `Program` instances still enforce the same hard-coded `MAX_STACK_SIZE = 1024` via `verifyStackOverflow`, so the stack-depth bound itself is identical for both paths. [7](#0-6) [8](#0-7)  The disparity is in *how much energy/CPU-time budget is available to execute Stack push/pop/swap-heavy opcodes before the interpreter loop in `VM.play` halts on `spendEnergy`/`checkCPUTimeLimit`*. [9](#0-8)  Since a constant call's energy ceiling is not fee-derived and its CPU-time ceiling is a separately configured constant, a crafted contract that loops on cheap Stack operations can consume more aggregate opcode/CPU budget per call, for free, than a signed transaction could ever purchase for the same TRX cost (theoretically $0).

I was not able to retrieve the exact default numeric values of `maxCpuTimeOfOneTx`, `constantCallTimeoutMs`, and `maxEnergyLimit` from `reference.conf`/`Args.java` within the available iterations, so I cannot mathematically confirm that `constantCallTimeoutMs` exceeds the effective broadcast-tx CPU budget in the shipped default configuration — this needs verification against `common/src/main/resources/reference.conf` and `common/src/main/java/org/tron/core/config/args/VmConfig.java`.

### Impact Explanation
If confirmed that the constant-call CPU/energy budget exceeds what a paid transaction can buy, this is a **DoS via RPC-API** vector: an anonymous client can repeatedly call `triggerconstantcontract`/`estimateenergy` against a Stack-churning contract with zero fee, tying up RPC/HTTP worker threads for longer wall-clock durations than any broadcast transaction, degrading node responsiveness. The blast radius is bounded by: the size of the RPC/HTTP worker thread pool (limits concurrency), the `HttpApiAccessInterceptor`/`RateLimiterServlet` on HTTP endpoints, and the fact that `constantCallTimeoutMs` is still a *finite* cap (execution is not unbounded, only relatively larger than the broadcast per-tx CPU budget).

### Likelihood Explanation
Preconditions: default node configuration with `vm.supportConstant=true` (default in most public/full nodes serving dApp reads), no signature or TRX cost required, and network/API access to `wallet/triggerconstantcontract`, `wallet/estimateenergy`, or the equivalent gRPC methods — all reachable by an anonymous, unprivileged actor. [10](#0-9)  Cost to attacker is effectively zero (no TRX spent, no signature needed) versus a broadcast transaction that must pay `feeLimit`/energy and bandwidth. Repeatability is high — every request is stateless and can be issued in parallel up to the RPC/HTTP thread-pool and rate-limiter thresholds.

### Recommendation
- Cap constant-call `energyLimit` to a value proportionate to (or no larger than) what an equivalent broadcast transaction could purchase with `getMaxFeeLimit()`, rather than an independent `maxEnergyLimit` constant.
- Ensure `constantCallTimeoutMs` is not larger than the effective per-transaction CPU budget used for broadcast execution (`maxCpuTimeOfOneTx` × ratio), or otherwise tie it to the same governance-controlled parameter.
- Apply/verify a dedicated rate limiter and per-IP/per-account throttling specifically for `triggerconstantcontract`/`estimateenergy` on both HTTP and gRPC surfaces, and consider a global concurrency cap for constant-call execution independent of the general RPC thread pool.

### Proof of Concept
Conceptual PoC (needs the actual default constants from `reference.conf` to quantify the gap):
1. Deploy a contract whose fallback performs a tight loop of `PUSH1`/`POP`/`DUP`/`SWAP` operations bounded only by gas, e.g. Solidity: a loop incrementing a stack-heavy computation without storage writes, run via `while(true) { uint a = 1; a; }`-style unrolled bytecode.
2. Call it once via a signed `triggerContract` broadcast transaction with `feeLimit` set to `getMaxFeeLimit()`; record wall-clock execution time and energy consumed before `OutOfEnergyException`/`OutOfTimeException`.
3. Call the same contract via unauthenticated `wallet/triggerconstantcontract` (no signature, no fee) with default `fee_limit`; record wall-clock execution time and energy consumed before halting.
4. Compare: expected assertion is that the constant-call path executes materially longer (bounded by `constantCallTimeoutMs`) and/or consumes energy far beyond what `feeLimit` from step 2 could have purchased, at zero cost to the caller — confirming the CPU-per-dollar asymmetry.

This PoC requires instrumenting/reading the actual `VmConfig`/`CommonParameter` default values (`maxCpuTimeOfOneTx`, `constantCallTimeoutMs`, `maxEnergyLimit`) to state exact numeric bounds, which I could not pull from the index in this session — a full Devin session with repo/file access would be needed to extract `common/src/main/resources/reference.conf` and confirm the concrete magnitude of the disparity before treating this as a fully proven, quantified vulnerability.

      throw new ContractValidateException("this node does not support constant");
    }

    Block headBlock;
    List<BlockCapsule> blockCapsuleList = chainBaseManager.getBlockStore()
        .getBlockByLatestNum(1);
    if (CollectionUtils.isEmpty(blockCapsuleList)) {
      throw new HeaderNotFound("latest block not found");
    } else {
      headBlock = blockCapsuleList.get(0).getInstance();
    }

    BlockCapsule headBlockCapsule = new BlockCapsule(headBlock);
    TransactionContext context = new TransactionContext(headBlockCapsule, trxCap,
        StoreFactory.getInstance(), true, false);
    VMActuator vmActuator = new VMActuator(true);

    try {
      vmActuator.validate(context);
      vmActuator.execute(context);
    } finally {
      // constant call runs on a pooled RPC worker; drop its thread-local VM config view so it
      // can never leak into a later (block/broadcast) execution on the same thread.

    }
