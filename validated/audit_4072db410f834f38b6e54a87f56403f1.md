### Title
Constant-call energy clamp is unreachable via `TriggerConstantContractServlet` — attacker always gets full `maxEnergyLimitForConstant` energy budget - ([File: framework/src/main/java/org/tron/core/services/http/TriggerConstantContractServlet.java])

### Summary
`VMActuator.validate()` only tightens `maxEnergyLimit` for constant calls when `trx.getRawData().getFeeLimit() > 0`, but `TriggerConstantContractServlet.doPost()` never reads or sets a `fee_limit` field on the transaction it builds, so `feeLimit` is always `0` for every HTTP `triggerconstantcontract` request. As a result the fee-scaled clamp is dead code on this path and every constant call is metered against the full `CommonParameter.maxEnergyLimitForConstant` (default 100,000,000), independent of the configured `getMaxFeeLimit()`/`getEnergyFee()` dynamic parameters.

### Finding Description
`VMActuator.validate()` performs the clamp: [1](#0-0) 

This is gated on `trx.getRawData().getFeeLimit() > 0`. Compare `TriggerConstantContractServlet.doPost()`, which builds the `TriggerSmartContract` request and creates the `TransactionCapsule` directly from it, with no code path reading a `fee_limit` JSON field or calling `rawBuilder.setFeeLimit(...)`: [2](#0-1) 

This is in stark contrast to the sibling `TriggerSmartContractServlet` (used for real, fee-paying broadcast-eligible calls), which explicitly extracts `fee_limit` from the JSON body and applies it to the raw transaction before calling into the wallet: [3](#0-2) 

Because `TriggerSmartContract` (the protobuf contract type) has no `fee_limit` field at all — `fee_limit` only exists on `Transaction.raw` — and the constant-contract servlet never touches `Transaction.raw.fee_limit`, the resulting `TransactionCapsule` passed into `wallet.triggerConstantContract(...)` → `callConstantContract(...)` → `VMActuator.validate()` always has `getFeeLimit() == 0`. Consequently the `if (isConstantCall && trx.getRawData().getFeeLimit() > 0)` branch never executes for HTTP `triggerconstantcontract` calls, and `maxEnergyLimit` stays at the constructor default `CommonParameter.getInstance().maxEnergyLimitForConstant`: [4](#0-3) 

No existing check compensates for this: `triggerConstantContract`/`callConstantContract` in `Wallet.java` never call `trxCap.setFeeLimit(...)` for ordinary (non-estimating) calls — that only happens inside the energy-estimation binary search (`cleanContextAndTriggerConstantContract`), a distinct code path: [5](#0-4) 

The gRPC path (`RpcApiService.callContract`) similarly relies on `createTransactionCapsule(request, ...)` without any fee-limit assignment for constant calls, so the same gap exists there: [6](#0-5) 

An unprivileged, anonymous caller can simply POST to `/wallet/triggerconstantcontract` (no signature, no funded account, no fee required since constant calls are free/read-only) targeting an energy-heavy view function, and always receive the maximum `maxEnergyLimitForConstant` execution budget — the operator-configured `getMaxFeeLimit()`/dynamic fee-scaling clamp intended to bound this budget never applies.

### Impact Explanation
This maps to **DoS via RPC-API**: every anonymous constant-call request is unconditionally metered at the maximum configured constant-call energy budget (`maxEnergyLimitForConstant`, default 100M), regardless of any lower `getMaxFeeLimit()` dynamic property the node operator intended to use to bound per-call CPU/energy cost. Since constant calls execute synchronously on RPC worker threads without any TRX cost, this maximizes the amount of VM execution (and thus CPU time / wall-clock time) an attacker can force per request, amplifying resource-exhaustion/DoS potential against `triggerconstantcontract` endpoints compared to the intended fee-scaled clamp.

### Likelihood Explanation
Trivial and fully repeatable: default JSON body for `/wallet/triggerconstantcontract` already omits `fee_limit` (the servlet doesn't even parse it), so no special attacker effort is required — this is simply the servlet's normal, unmodified behavior. No signature, no funded account, no privileged role, and no fee payment is needed since constant calls don't broadcast or consume real TRX. The attacker only needs network access to the HTTP/JSON-RPC endpoint (default node configuration).

### Recommendation
Have `TriggerConstantContractServlet.doPost()` (and the gRPC `callContract` constant-call path) parse an optional `fee_limit` from the request and apply it via `rawBuilder.setFeeLimit(...)` before invoking `wallet.triggerConstantContract`, mirroring `TriggerSmartContractServlet`. Alternatively, make the clamp in `VMActuator.validate()` unconditional for `isConstantCall`, using `min(maxEnergyLimitForConstant, getMaxFeeLimit() / getEnergyFee())` regardless of whether the caller supplied a `feeLimit`, so the operator-configured cap is always enforced rather than only when the (currently unreachable) `feeLimit > 0` condition holds.

### Proof of Concept
```java
// actuator/src/test/java/org/tron/core/actuator/VMActuatorFeeLimitClampTest.java
@Test
public void testConstantCallFeeLimitZeroBypassesClamp() throws Exception {
  // Simulate TriggerConstantContractServlet behavior: build a TriggerSmartContract
  // transaction WITHOUT setting fee_limit (as the servlet currently does).
  TransactionCapsule trxCap = buildConstantTriggerTrx(/* feeLimit not set -> defaults to 0 */);
  assertEquals(0L, trxCap.getInstance().getRawData().getFeeLimit());

  TransactionContext context = new TransactionContext(blockCap, trxCap, storeFactory, true, false);
  VMActuator vmActuator = new VMActuator(true); // isConstantCall = true
  vmActuator.validate(context);

  // Even with a low dynamic getMaxFeeLimit()/getEnergyFee(), maxEnergyLimit
  // remains at the full CommonParameter.maxEnergyLimitForConstant because the
  // clamp branch (feeLimit > 0) never triggers.
  long actualMaxEnergyLimit = getPrivateField(vmActuator, "maxEnergyLimit");
  assertEquals(CommonParameter.getInstance().getMaxEnergyLimitForConstant(), actualMaxEnergyLimit);
}
```
