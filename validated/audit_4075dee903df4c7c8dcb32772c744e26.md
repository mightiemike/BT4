### Title
Stale accrual index cache read after a same-transaction vault mutation in `liquidate` – (`local-testing/contracts/market/market.clar`, `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` caches each vault's accrual indexes per `(stacks-block-time, aid)` the first time they are read in a transaction, and every later read within the same call falls back to the cache instead of re-querying the vault [1](#0-0) . Inside `liquidate`, after this cache is populated the code calls `vault-system-repay`, which invokes the vault's `system-repay`/interest-accrual path and can move the vault's stored index, yet the very same transaction later reads `get-cached-indexes` again (used to compute `rem-borrow-index`/`other-borrow-idx`) instead of re-accruing [2](#0-1) . This is the same fundamental class as GMX's H-16 (a state check/derived-value computed at one moment is trusted again after the underlying source has moved within the same call).

### Finding Description
`accrue-and-cache` implements a "compute-once, reuse for the rest of the block/tx" pattern: on cache miss it calls `vault-accrue` and stores the returned `{index, lindex}` under key `{timestamp: stacks-block-time, aid}`; on cache hit it just returns the stored value without touching the vault again [1](#0-0) .

In `liquidate` (mirrored in `mainnet/contracts/market/v0-4-market.clar`), the debt/collateral indexes are cached early via `accrue-user-debts`/`accrue-user-collateral` [3](#0-2) . Later in the same function, `vault-system-repay` is executed to actually repay the debt asset in its vault [4](#0-3) , and immediately afterward the code reads `get-cached-indexes debt-aid` again to compute `rem-borrow-index` and `other-borrow-idx` for the "remaining debt repayable" / bad-debt bookkeeping math [5](#0-4) . Because `get-cached-indexes` only returns the value stored at the start of the transaction (the same `stacks-block-time` key), any index movement caused by `vault-system-repay`'s own accrual step is not reflected in these later reads — the value bound before the mutating call is silently reused after the mutating call, inside a single transaction. This mirrors the GMX root cause: a value is captured, an external/mutating call happens, and the earlier value is trusted again as if it were still fresh, because nothing re-validates or re-fetches it before reuse.

By contrast, `socialize-debt-asset` correctly re-derives and overwrites the cache with `vault-accrue` right after `vault-socialize-debt` mutates the vault [6](#0-5) , showing the codebase's own intended invalidation pattern — which is missing on the `liquidate` repay path for the `rem-borrow-index`/`other-borrow-idx` computations.

### Impact Explanation
`rem-borrow-index`/`other-borrow-idx` feed directly into `remaining-debt-to-repay` and `other-debt-repayable`, which gate whether `coll-final` is set to the borrower's full collateral balance and whether the position is treated as having "no collateral left" (triggering bad-debt socialization) [7](#0-6) . If the true post-repay index differs from the stale cached one, these downstream accounting decisions (how much collateral is seized, whether debt is socialized) are computed against inconsistent debt-to-collateral rounding assumptions, which can misstate the amount of debt actually cleared versus collateral actually seized during liquidation — a form of temporary/permanent misallocation of funds within the liquidation flow. I was not able to fully verify the magnitude of index drift a single `system-repay` call can produce (that requires reading the vault's `accrue`/`system-repay` implementation in detail, which I did not have iterations left to inspect), so the concrete size of the resulting discrepancy is unconfirmed.

### Likelihood Explanation
This path is exercised on every ordinary `liquidate` call where `coll-remaining > u0` or `other-coll-usd > u0` — i.e., whenever collateral isn't fully exhausted by the primary debt/collateral pair being liquidated, which is a common, non-adversarial liquidation scenario, not a crafted edge case. No malicious counterparty or special callback is required, unlike the GMX report's attacker-controlled revert payload.

### Recommendation
Have `liquidate` re-accrue (or explicitly refresh the `index-cache` entry for `debt-aid`) immediately after `vault-system-repay` completes, mirroring the invalidation already done in `socialize-debt-asset`, before any later `get-cached-indexes debt-aid` read is used for `rem-borrow-index` or `other-borrow-idx` computations.

### Proof of Concept
1. Borrower has debt in `debt-aid` and collateral split across ≥2 collateral assets, such that after seizing the targeted collateral asset (`coll-final`), `coll-remaining > u0` (other collateral still exists) — i.e., `no-collateral-left` bad-debt branch is not simply skipped.
2. Liquidator calls `liquidate(borrower, collateral-ft, debt-ft, debt-amount, ...)`.
3. Inside `liquidate`: `accrue-user-debts` populates `index-cache` for `debt-aid` at the current `stacks-block-time` [8](#0-7) .
4. `vault-system-repay debt-aid debt-to-repay ...` executes, causing the underlying vault to accrue/update its index as part of processing the repay [9](#0-8) .
5. The function then computes `rem-borrow-index`/`other-borrow-idx` via `get-cached-indexes debt-aid`, which returns the value cached in step 3, not the post-repay value from step 4 [10](#0-9) .
6. `remaining-debt-to-repay`/`other-debt-repayable` and therefore `coll-final`/`bad-debt-socialized` are computed against the stale index, producing collateral-seizure/debt-write-down amounts inconsistent with the vault's true post-repay state — all within the single `liquidate` transaction.

I could not fully confirm within available iterations whether `vault-*-system-repay`'s internal `accrue` call actually changes the stored index by a materially different amount in the same block (this depends on the vault's interest-accrual formula, which I did not have time to fully trace), so root-cause plausibility is established structurally (cache-not-invalidated pattern demonstrably present) but the exact numeric exploitability is not independently proven here.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
