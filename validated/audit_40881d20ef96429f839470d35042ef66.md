### Title
Vote reward settlement uses current vote allocation to retroactively price past cycles, allowing users to manipulate accrued rewards - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
The Plaza Finance report describes a class of bug where a periodic, discretely-settled fee/reward is computed against a stale or mismatched state snapshot, letting a user change their position immediately before settlement and thereby escape or distort their true pro-rata share. java-tron's SR voting reward mechanism has a structurally similar pattern: reward for a *range* of past cycles `[beginCycle, endCycle)` is computed using the account's **current** vote allocation rather than the vote allocation that was actually held during each of those historical cycles.

### Finding Description
`MortgageService.computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)` computes reward for the "new algorithm" cycles by taking the delta of the witness's cumulative value-index (`Vi`) between `beginCycle-1` and `endCycle-1` and multiplying it by the account's **current** vote count for that SR (`vote.getValue()` taken from `accountCapsule.getVotesList()`, i.e. present-tense data), not by a per-cycle historical vote snapshot: [1](#0-0) 

This delta-Vi approach is only mathematically correct if the user's vote allocation to that SR was constant for the whole `[beginCycle, endCycle)` range. `withdrawReward`/`queryReward` only snapshot the account's vote list into `delegationStore` at the moment `withdrawReward` is actually invoked (via `setAccountVote`), and `beginCycle`/`endCycle` bookkeeping is only advanced at that point: [2](#0-1) 

If a user goes multiple cycles without calling `withdrawReward` (which is common — many actuators only call it as a side effect), and then changes their vote allocation (via `VoteWitnessContract`/TVM `vote`) shortly before finally triggering `withdrawReward` (e.g. via `WithdrawBalanceActuator`, `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, or the TVM `withdrawReward` precompile), the entire backlog of unclaimed cycles gets priced using the *new* vote allocation instead of the allocation actually held during those cycles: [3](#0-2) [4](#0-3) 

This mirrors the root cause pattern in the external report: the accounting state used to settle a periodic obligation/benefit does not reflect the position actually held during the accrual period, so a user who changes their position immediately before the discrete settlement point can extract more reward than earned (analogous to leverage holders avoiding fees) or, depending on direction of the change, other voters bear a skewed distribution since witness-level aggregate reward (`delegationStore.getReward`/`getWitnessVi`) is fixed and independently computed, so any voter capturing a disproportionate share via this mistiming directly comes at the expense of the correctly-behaving voters' pro-rata share.

### Impact Explanation
Because SR reward pools per cycle are fixed pot values (from `payReward`/`payStandbyWitness`), if a subset of voters' `computeReward` reads an inflated (or deflated) current vote weight instead of the historical weight for past cycles, the sum of all voters' claims against a given cycle's fixed reward pot can diverge from what was actually earned. Malicious actors could sequence "increase vote to SR X" → "call withdrawReward" to claim reward for prior cycles as if they had voted with the larger allocation the whole time, extracting value that should have gone to other voters of the same SR. This is an accounting/resource-reward corruption issue reachable purely through unprivileged, broadcast transactions (`VoteWitnessContract`, `WithdrawBalanceContract`, TVM `vote`/`withdrawReward`).

### Likelihood Explanation
Likelihood is moderate: the attacker needs to accumulate multiple un-withdrawn cycles (easy — nothing forces frequent withdrawal) and then perform a vote change followed by a withdrawal in a short window, all of which are ordinary, permissionless operations available to any account holder. No special timing relative to block production or privileged access is required.

### Recommendation
Reward accrual for the pending cycle range should be computed using a per-cycle historical vote snapshot (or reward must be settled/flushed automatically whenever the vote allocation changes, not deferred until the next explicit `withdrawReward` call), so that `deltaVi * voteCount` is only ever applied over intervals where `voteCount` is verified constant. Concretely, `VoteWitnessActuator`/`VoteWitnessProcessor` and other vote-mutating paths should call `mortgageService.withdrawReward`/`VoteRewardUtil.withdrawReward` to settle and snapshot pending rewards *before* applying the new vote allocation, closing the gap between "position held" and "position used for retroactive settlement."

### Proof of Concept
Not independently reproduced here (requires a running node/testnet to demonstrate multi-cycle accrual plus a vote-change-then-withdraw sequence); the finding is based on static analysis of the referenced `computeReward` logic in `MortgageService.java` and the corresponding `VoteRewardUtil.java`, showing the settlement uses present-tense vote data for past-cycle pricing. Confidence in exploitability is bounded by not having verified whether `VoteWitnessActuator.countVoteAccount` (not fully visible in the explored snippet) independently forces a reward settlement before altering votes; if it does not, the described mistiming is directly exploitable.
