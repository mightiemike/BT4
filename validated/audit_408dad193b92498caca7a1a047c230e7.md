I found a concrete analog: `SecondaryIndex::insert` in `accounts_index/secondary.rs` runs an unbounded linear `Vec::contains()` scan on every insert, on a `Vec` documented as "rare" but which is fully attacker/workload-influenced (an inner key, e.g. an SPL token mint or owner, can legitimately map to many outer keys/pubkeys whenever accounts with that data are rewritten across slots).

### Title
Unbounded linear `Vec::contains()` scan in `SecondaryIndex::insert` causing CPU cost that scales with reverse-index fan-out - (File: accounts-db/src/accounts_index/secondary.rs)

### Summary
`SecondaryIndex::insert()` maintains a reverse index (`reverse_index: DashMap<Pubkey, RwLock<Vec<Pubkey>>>`) mapping an inner key (e.g. SPL token mint/owner or program ID) back to every outer pubkey (account) that references it. On every single insert, it performs `outer_keys.contains(key)` — an O(n) linear scan of the `Vec<Pubkey>` for that inner key — before deciding whether to push a new entry. [1](#0-0) 

This is structurally the same bug class as the reported `onlyAllowed` modifier: an unbounded, append-only list is exhaustively linear-scanned on every hot-path operation instead of using a set/map for O(1) membership checks.

### Finding Description
The comment at the type definition acknowledges the tradeoff explicitly: [2](#0-1) 

This assumes the "outer keys per inner key" fan-out is always small ("rare"). However, this is a workload-dependent assumption, not an enforced invariant. Any account holder pattern where a very large number of distinct owner pubkeys hold accounts of the same SPL token mint or SPL token owner, or the same program ID (this is the common case for `ProgramId` and can be true for popular mints), causes the reverse-index `Vec` for that single inner key to grow to be proportional to the number of accounts sharing that key — that can be very large on mainnet (millions of token accounts sharing the same mint).

Because `insert()` is called on the accounts-update hot path (`update_secondary_indexes` → `update_spl_token_secondary_indexes`/`ProgramId` insert path) every time any account matching the secondary index configuration is written, and because the `Vec::contains()` check is `O(n)` in the number of *already-inserted* outer keys for that inner key, the per-insert cost grows linearly with the size of the reverse-index entry. Since the reverse index only grows (entries are only removed when the outer key's forward-index sub-map goes empty via `remove_by_inner_key_if`), sustained account churn on a popular mint/program repeatedly re-triggers this near-`O(n)` (or effectively `O(n)` in the worst case where the key isn't already present) scan under a write lock (`RwLock<Vec<Pubkey>>`), serializing all writers of accounts referencing that inner key. [3](#0-2) 

This mirrors the reported bug precisely: an append-only, non-shrinking collection checked via full/linear iteration in a modifier-equivalent hot path, rather than a hashed/mapped structure providing O(1) lookups.

### Impact Explanation
This applies only when the validator is run with `--account-index` enabled for `program-id`, `spl-token-mint`, or `spl-token-owner` (opt-in feature, not default). When enabled, this is a disproportionate CPU cost issue: normal transaction/account processing (a legitimate, in-scope function — account storage/index maintenance) that touches accounts under a heavily-shared owner/mint/program key degrades in per-operation cost as that key's popularity grows, and each insert holds an exclusive write lock on the shared `RwLock<Vec<Pubkey>>` for the entire scan+push, serializing concurrent account updates referencing the same inner key. This does not directly corrupt state, cause hash divergence, or crash the node, but it is a legitimate "disproportionate storage/CPU cost" finding as called out in the validation criteria.

### Likelihood Explanation
Likelihood is real but bounded by scope: it requires the operator to have opted into secondary indexing (`--account-index`), and requires an inner key (mint/owner/program) referenced by a large and growing number of distinct outer pubkeys — a naturally occurring condition for popular SPL token mints or heavily used program IDs on mainnet, so no attacker action beyond normal high-volume usage is required to trigger the degradation.

### Recommendation
Replace the `SecondaryReverseIndexEntry` type (`RwLock<Vec<Pubkey>>`) with a hashed structure (e.g. `RwLock<HashSet<Pubkey>>` or `IndexSet<Pubkey>` if insertion order matters) so that the `contains()` check in `insert()` and any future existence checks are O(1) rather than O(n), removing the assumption that fan-out will always remain small.

### Proof of Concept
Not applicable in the traditional sense (no external transaction sequence is required against a smart contract); this is a structural/algorithmic complexity issue reachable purely by normal validator operation:
1. Run the validator with `--account-index spl-token-mint` (or `program-id`).
2. Have a very large number of distinct token accounts (outer keys) reference the same mint (inner key) — this is common for high-volume mints.
3. Each time any of these accounts is updated/rewritten (a normal, frequent occurrence), `SecondaryIndex::insert()` is called and executes `outer_keys.contains(key)` over the full `Vec` for that mint under a write lock, as shown at [4](#0-3) 
As the number of distinct outer keys for that mint grows, the per-insert cost and the write-lock hold time grow linearly, producing disproportionate CPU cost that scales with historical account/mint popularity rather than the size of the current update.

    /// Inserts `inner_key` into `key`'s map.
    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }
