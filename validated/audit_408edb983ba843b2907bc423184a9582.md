### Title
Receipt Size Validation Bypass Allows Oversized Receipts Past `max_receipt_size` — (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The `max_receipt_size` limit (4 MiB, meant to bound `ChunkStateWitness` size per `docs/misc/state_witness_size_limits.md`) is checked once at receipt-creation time via `validate_receipt`/`validate_action_receipt` in `runtime/runtime/src/verifier.rs`, but a receipt's `output_data_receivers` and returned data can be mutated *after* that validation passes (e.g. via `promise_return`/`ReceiptManager::create_action_receipt` appending `DataReceiver` entries in [1](#0-0) , or a function-call's returned value being wrapped into a `Data` receipt). This lets a contract-controlled receipt legitimately exceed `max_receipt_size` after passing its size check.

### Finding Description
An unprivileged contract caller can construct a promise DAG where a receipt is built up to exactly `max_receipt_size` and then further mutated (`output_data_receivers` appended, or a large return value wrapped into a `Data` receipt) so its serialized size exceeds the configured hard limit — bypassing the size gate that is supposed to bound `ChunkStateWitness` and per-shard receipt-forwarding size accounting. This is a self-acknowledged, still-open issue in the codebase itself: `runtime/runtime/src/congestion_control.rs` contains an explicit workaround comment citing the upstream bug: [2](#0-1) 

referencing `https://github.com/near/nearcore/issues/12606`. The workaround only clamps the *accounting* value used for outgoing bandwidth/congestion bookkeeping (`try_forward`); it does not reject or shrink the oversized receipt itself, and it is only exercised on the cross-shard forwarding path — it does not close the root cause in the validation path (`runtime/runtime/src/verifier.rs`, `validate_receipt`/`validate_action_receipt`) or in `ReceiptManager` where the mutation actually occurs. This is directly analogous in bug-class to CVE-2018-1000100: a size/bounds check performed too early, followed by an unchecked mutation/append that grows the buffer/structure past the validated bound.

The nearcore test suite reproduces and explicitly documents this as an unresolved bug: [3](#0-2) [4](#0-3) 

### Impact Explanation
An oversized receipt evades the size limit that exists specifically to bound `ChunkStateWitness` to ~21 MiB (per `docs/misc/state_witness_size_limits.md`). This can (a) bloat state witnesses beyond the designed cap, risking distribution/propagation issues across chunk validators, and (b) because the clamp in `try_forward` only fakes the size for admission bookkeeping while the real oversized receipt is still pushed to `outgoing_receipts`, congestion-control size accounting (`OutgoingLimit.size`) can diverge from the true byte cost being moved between shards — a bookkeeping/state-consistency defect in the cross-shard receipt path. The test suite explicitly asserts the runtime "shouldn't die" when this occurs, implying the primary designed mitigation is "don't crash," not "prevent the invalid state."

### Likelihood Explanation
High likelihood of triggering: it requires only an ordinary `FunctionCall` transaction from any account, deploying/calling a contract that builds a promise chain near the size limit and then appends an additional `output_data_receivers`/return value (as demonstrated by the existing test contract methods `max_receipt_size_promise_return_method1` and `max_receipt_size_value_return_method` used in the test suite). No validator collusion, network-layer access, or privileged position is needed — a single unprivileged RPC caller can reach it.

### Recommendation
Re-validate receipt size after all post-construction mutations (in particular after `ReceiptManager::create_action_receipt` appends `output_data_receivers`, and after return-value wrapping into `Data` receipts) rather than only at initial `validate_receipt`/`validate_action_receipt` time. Alternatively, reject the receipt (rather than silently clamping the accounting size to `max_receipt_size`) in `try_forward` in `runtime/runtime/src/congestion_control.rs` when the real serialized size exceeds the limit, and thread that rejection back into execution outcome (`ReceiptSizeExceeded`) instead of forwarding it while under-counting congestion. This effectively fixes the referenced open issue (`near/nearcore#12606`) at its root rather than only in the forwarding-admission workaround.

### Proof of Concept
The nearcore test suite already contains a working PoC pattern (not a hypothetical): deploy the standard test contract and call `max_receipt_size_promise_return_method1`/`max_receipt_size_value_return_method` with `args_size`/`value_size` computed to make the receipt exactly `max_receipt_size` before promise return, then let the return/`output_data_receivers` mutation push it over the limit: [5](#0-4) [6](#0-5) 

These tests call `assert_oversized_receipt_occurred`, which walks the chain looking for an incoming/proof receipt whose size exceeds `max_receipt_size`, confirming the bypass is real and reproducible via ordinary transaction submission.

**Note on completeness:** I was not able to fully trace every mutation site of `ActionReceiptMetadata`/`DataReceiptMetadata` after validation (e.g. exact serialization/borsh conversion point where the final on-chain `Receipt` is built from `ReceiptManager` state) within the available index; a Devin session with full repository access would be needed to pinpoint the exact borsh-serialization boundary and confirm whether additional guard checks exist elsewhere in `runtime/runtime/src/lib.rs` between receipt finalization and validation that I could not locate via search.

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
