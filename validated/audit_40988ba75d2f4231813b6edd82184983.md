Based on the analog-bug hunt, I found a concrete match: **`citrea_haltCommitments`** and **`citrea_resumeCommitments`** are unauthenticated JSON-RPC methods that mutate live sequencer state, directly matching the requested High-severity class ("an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`").

### Title
Unauthenticated `citrea_haltCommitments` / `citrea_resumeCommitments` RPC methods can halt or resume sequencer commitment submission - (File: `crates/sequencer/src/rpc.rs`)

### Summary
The sequencer's JSON-RPC `Auth` middleware only requires an API key for three methods: `backup_create`, `backup_validate`, `backup_info` [1](#0-0) . Every other registered method, including `citrea_haltCommitments` and `citrea_resumeCommitments`, is passed straight through to the underlying service with no authentication or authorization check [2](#0-1) .

### Finding Description
The `SequencerRpc` trait exposes `citrea_haltCommitments` and `citrea_resumeCommitments` as unauthenticated methods [3](#0-2) . Their implementations simply forward a `HaltCommitments`/`ResumeCommitments` message over an internal channel to the sequencer's main runner loop, with no caller identity, API key, or any other authorization check performed: [4](#0-3) 

Unlike `publish_test_block`, which explicitly checks `self.context.test_mode` before acting [5](#0-4) , `halt_commitments` and `resume_commitments` have no such gate — they run unconditionally for any caller who can reach the sequencer's RPC endpoint. The `Auth` middleware's `PROTECTED_METHODS` allowlist does not include these method names [1](#0-0) , so the request is dispatched without any credential check, matching the pattern in the external report (a state-mutating RPC accepted "without asking...for confirmation").

This is the same bug class as the StarkNet-Snap analog: a JSON-RPC entry point that changes persistent/operational node state is reachable by any party that can send an RPC request, with no confirmation, signature, or API-key requirement — as opposed to `backup_create`/`backup_validate`/`backup_info`, which the codebase's own authors clearly recognized needed protection and gated via `Auth`.

I was not able to fully trace `crates/sequencer/src/runner.rs`'s handling of `SequencerRpcMessage::HaltCommitments`/`ResumeCommitments` before running out of tool iterations, so I cannot state with certainty the full blast radius (e.g., whether halting commitments merely pauses L1 submission or also affects proof/backup scheduling) — this would need further verification by reading `crates/sequencer/src/runner.rs` end-to-end.

### Impact Explanation
If exposed on a network-reachable RPC port (the default binding is configurable via `RpcConfig::bind_host`/`bind_port`, and `api_key` is `Option<String>` — i.e., not mandatory) [6](#0-5) , any client able to reach the sequencer's RPC could unilaterally halt sequencer commitment submission to L1, or resume it, without being the sequencer operator. This can stall the rollup's L1 commitment cadence — a state-mutating, unauthenticated call directly affecting rollup liveness/operation, matching the "High" bar of "unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`."

### Likelihood Explanation
Likelihood depends entirely on network exposure of the sequencer RPC port. If the operator relies on `api_key` being set and assumes it protects "sensitive" methods generally (as it does for `backup_*`), they may not realize `citrea_haltCommitments`/`citrea_resumeCommitments` are unprotected by the same mechanism, since the omission is silent (no compile-time or config-time warning).

### Recommendation
Add `citrea_haltCommitments` and `citrea_resumeCommitments` (and any other state-mutating admin RPC methods) to the `PROTECTED_METHODS` allowlist in `crates/common/src/rpc/auth.rs`, or gate them by node role/test mode analogous to the `test_mode` check already used in `publish_test_block`.

### Proof of Concept
1. Start a sequencer node with `rpc.api_key` unset or with the RPC port exposed to an untrusted network.
2. From an arbitrary unauthenticated client, call:
```
citrea_haltCommitments
```
via the sequencer's JSON-RPC endpoint — no API key parameter required, unlike `backup_create`.
3. Observe (per [7](#0-6) ) the `HaltCommitments` message is sent to the runner unconditionally, halting sequencer commitments without any authorization.

```rust
    /// Halt sequencer commitments
    async fn halt_commitments(&self) -> RpcResult<()> {
        debug!("Sequencer: citrea_haltCommitments");
        self.context
            .rpc_message_tx
            .send(SequencerRpcMessage::HaltCommitments)
            .map_err(|e| internal_rpc_error(format!("Could not send halt commitments signal: {e}")))
    }

    /// Resume sequencer commitments
    async fn resume_commitments(&self) -> RpcResult<()> {
        debug!("Sequencer: citrea_resumeCommitments");
        self.context
            .rpc_message_tx
            .send(SequencerRpcMessage::ResumeCommitments)
            .map_err(|e| {
                internal_rpc_error(format!("Could not send resume commitments signal: {e}"))
            })
    }
```
