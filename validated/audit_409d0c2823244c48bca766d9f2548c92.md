### Title
Attacker-controlled zero-filled buffer ELF causes out-of-bounds slice panic in `SourceBuffer::new_checked_with_verified_build_hash` - ([File: runtime/src/bank/builtins/core_bpf_migration/source_buffer.rs])

### Summary
`new_checked_with_verified_build_hash` computes `end_offset` by calling `rposition` over the **entire** buffer account data (metadata + ELF) instead of only the ELF region starting at `offset`. If the attacker zero-fills the ELF portion of the buffer while the preceding bincode-encoded `UpgradeableLoaderState::Buffer` metadata's last byte happens to be zero, `end_offset` computes to a value smaller than `offset`, and the subsequent `&data[offset..end_offset]` slice operation panics with "slice index starts at ... but ends at ...".

### Finding Description
In `SourceBuffer::new_checked_with_verified_build_hash`: [1](#0-0) 

```
let offset = UpgradeableLoaderState::size_of_buffer_metadata();
let end_offset = data.iter().rposition(|&x| x != 0).map_or(offset, |i| i + 1);
let buffer_program_data = &data[offset..end_offset];
```

`rposition` scans the whole `data` slice, not `data[offset..]`. The metadata region (indices `0..offset`) is a bincode-serialized `UpgradeableLoaderState::Buffer { authority_address }`, which is `4` bytes of enum discriminant plus, when `authority_address` is `Some(pubkey)`, `1` discriminant byte + `32` pubkey bytes, exactly filling `offset` bytes with no padding. The attacker fully controls `authority_address` (it is supplied by them in the `InitializeBuffer` instruction, verified in `programs/bpf_loader/src/lib.rs` at `process_loader_upgradeable_instruction`), and fully controls the buffer's ELF payload via `Write` instructions.

If the attacker:
1. Picks any `authority_address` pubkey whose last serialized byte is `0x00` (trivially grindable, ~1/256 probability per keypair attempt), and
2. Writes all-zero bytes for the entire ELF region (`data[offset..]`),

then the last non-zero byte found by `rposition` lies strictly inside the metadata region, i.e. at some index `i < offset - 1`, so `end_offset = i + 1 < offset`. The following `&data[offset..end_offset]` then panics immediately — this happens **before** the hash comparison against `expected_hash`, so the panic is unconditional and does not depend on any hash matching.

This is a genuine indexing bug distinct from the hash-comparison logic described in the question: the empty/zero-length-ELF scenario is not what triggers the crash — a backwards slice range is what triggers it.

### Impact Explanation
A validator processing a scheduled `migrate_builtin_to_core_bpf` migration (invoked from `Bank::migrate_builtin_to_core_bpf`, `runtime/src/bank/builtins/core_bpf_migration/mod.rs`) whose `config.verified_build_hash` is `Some(..)` will panic while calling `SourceBuffer::new_checked_with_verified_build_hash`, crashing bank processing for all validators that reach the migration slot. This matches Agave's "node panic" bounty category for a reachable, attacker-inducible panic in the runtime/bank builtins module.

### Likelihood Explanation
Exploitation requires the attacker to control the specific `source_buffer_address` account referenced in the hardcoded `CoreBpfMigrationConfig` for a given feature-gated migration. In current production configurations, this address and its write authority are chosen and controlled by the Solana Foundation/Anza team ahead of the migration (the verified-build buffer is populated well before the feature-gate activates, for community review), not by an arbitrary unprivileged user. An ordinary attacker cannot originate or rewrite that specific account unless they hold its private key or the migration's designated authority key. Absent that precondition, the bug, while real at the code level and trivially reproducible in a unit test, is not reachable by a purely unprivileged attacker under the stated threat model for any currently-configured migration.

### Recommendation
Restrict the `rposition` scan to the ELF region only, e.g. `data[offset..].iter().rposition(|&x| x != 0).map_or(offset, |i| offset + i + 1)`, guaranteeing `end_offset >= offset` and eliminating the possibility of a backwards slice range regardless of metadata byte contents.

### Proof of Concept
```rust
#[test]
fn test_verified_build_hash_backwards_slice_panic() {
    let bank = create_simple_test_bank(0);
    let buffer_address = Pubkey::new_unique();

    let buffer_metadata_size = UpgradeableLoaderState::size_of_buffer_metadata();
    // Grind an authority pubkey whose last serialized byte is zero.
    let authority = loop {
        let candidate = Pubkey::new_unique();
        if candidate.to_bytes()[31] == 0 {
            break candidate;
        }
    };

    let elf_len = 64usize;
    let mut data = vec![0u8; buffer_metadata_size + elf_len];
    bincode::serialize_into(
        &mut data[..buffer_metadata_size],
        &UpgradeableLoaderState::Buffer { authority_address: Some(authority) },
    )
    .unwrap();
    // ELF region left all-zero.

    let lamports = bank.get_minimum_balance_for_rent_exemption(data.len());
    let mut account = AccountSharedData::new(lamports, data.len(), &bpf_loader_upgradeable::id());
    account.data_as_mut_slice().copy_from_slice(&data);
    bank.store_account_and_update_capitalization(&buffer_address, &account);

    // This should return an error (e.g. BuildHashMismatch), not panic.
    let result = std::panic::catch_unwind(|| {
        SourceBuffer::new_checked_with_verified_build_hash(&bank, &buffer_address, Hash::default())
    });
    assert!(result.is_err(), "expected panic due to backwards slice range");
}
```
Expected (fixed) behavior: the call returns `Err(CoreBpfMigrationError::BuildHashMismatch(..))` instead of panicking.
