Looking at java-tron's native `Exchange` module (its closest analog to a market/trading system), I can compare two withdrawal/trade paths:

- `ExchangeTransactionActuator` (buy/sell against the bancor-style AMM pool) **already has** slippage protection: the `ExchangeTransactionContract.expected` field is validated against the computed `anotherTokenQuant` and rejected if it's below the expected minimum. [1](#0-0) 
- `ExchangeWithdrawActuator` (liquidity withdrawal from the same pool, restricted to the pool's creator) has **no equivalent minimum-received parameter**. It computes `anotherTokenQuant` purely from the *current* pool ratio at execution time and transfers it without any bound check against the value the creator expected when they signed the transaction. [2](#0-1) 

### Title
Missing slippage protection in `ExchangeWithdrawActuator` withdrawal - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawActuator.execute` calculates the counter-token amount (`anotherTokenQuant`) a liquidity-pool creator receives when withdrawing from an Exchange pool strictly from the pool balances present *at execution time*, with no user-supplied minimum-acceptable-amount check, unlike its sibling `ExchangeTransactionActuator` which enforces an `expected` floor.

### Finding Description
The `ExchangeWithdrawContract` protobuf message only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum field. [3](#0-2) 

In `ExchangeWithdrawActuator.execute`, the ratio `anotherTokenQuant` paid out to the caller is computed on the fly from `firstTokenBalance`/`secondTokenBalance` read from the live `ExchangeCapsule` at the moment the transaction is executed by a block-producing witness: [4](#0-3) 

Because a signed `ExchangeWithdrawContract` transaction can sit in the mempool for some time before being packed into a block, other `ExchangeTransactionContract` trades against the same pool can execute first and shift the `firstTokenBalance`/`secondTokenBalance` ratio significantly. Since `doValidate()` re-derives `anotherTokenQuant` from the pool state at validation time as well (right before execution), there is no way for the caller to bound the amount they actually receive — the same execution-time-price dependency the external report flags for `closeTradeMarketCallback`, just applied to Ostium's collateral payout vs. java-tron's counter-token payout. [5](#0-4) 

This is in direct contrast to `ExchangeTransactionActuator`, which validates `anotherTokenQuant < tokenExpected` and reverts the transaction if the trader would receive less than they were willing to accept: [1](#0-0) 

### Impact Explanation
An Exchange-pool creator withdrawing liquidity can receive substantially less of the counter-token than they intended if trading activity against the pool moves the ratio between transaction signing and block inclusion (e.g., another user or an MEV-motivated block producer executes large trades first). Since only the pool creator can call `ExchangeWithdrawContract` [6](#0-5) , the affected party is an ordinary unprivileged account (any user who created a TRC10 exchange pool), not a trusted/privileged role. The impact is a value-loss/settlement issue: withdrawn value does not match user expectations and cannot be capped by the user.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires either natural trading volatility in that specific pool between signing and inclusion, or an adversary (or the withdrawing user's own counterparty) deliberately front-running the withdrawal with trades to shift the ratio unfavorably before the withdrawal executes. TRC10 Exchange pools are lower-traffic than Ostium's leveraged markets, but the mechanism is identical in class to the reported issue.

### Recommendation
Add a `expected`/`min_another_token_quant` parameter to `ExchangeWithdrawContract`, mirroring the pattern already used in `ExchangeTransactionContract`, and validate `anotherTokenQuant >= expected` in `ExchangeWithdrawActuator.doValidate()` before executing the withdrawal, rejecting the transaction otherwise.

### Proof of Concept
1. User A creates/owns an Exchange pool with tokens X/Y at ratio 1,000,000/2,000,000.
2. User A signs an `ExchangeWithdrawContract` withdrawing 1,000 units of X, expecting ~2,000 units of Y based on the current ratio, and broadcasts it.
3. Before A's transaction is included, other users execute large `ExchangeTransactionContract` trades against the pool that skew the ratio to 1,000,000/200,000 (heavily reduce Y relative to X).
4. A's withdrawal transaction executes later, and `anotherTokenQuant` is now recalculated at execution time from the skewed ratio, giving A only ~200 units of Y instead of the expected ~2,000 — a 90% loss — with no reverted transaction because there is no minimum-amount check comparable to `ExchangeTransactionActuator`'s `expected` field.
