### Title
`rlp_execute` silently absorbs attached NEAR deposit when the RLP payload fails to parse - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract::rlp_execute` entry point is `#[payable]` [1](#0-0) , meaning any caller can attach a NEAR deposit when invoking it. `inner_rlp_execute` computes a `CallerDeposit` (the mechanism meant to track and later refund an external caller's attached deposit) before attempting to parse the RLP-encoded Ethereum transaction, but on parsing failure it returns the error without ever using that `caller_deposit`, so no refund promise is ever created [2](#0-1) .

### Finding Description
`CallerDeposit::new` is constructed from `context.attached_deposit` right after the `ExecutionContext` is built, specifically to allow the caller's deposit to be refunded later if a downstream cross-contract call fails [3](#0-2) . However, `caller_deposit` is only ever consumed on the success path, where it is threaded through to `rlp_execute_callback`, which issues a refund transfer promise if the final cross-contract call fails [4](#0-3) .

If `internal::parse_rlp_tx_to_action` fails — which happens for any `Error::User` variant (e.g. `UnknownFunctionSelector`, `InvalidAbiEncodedData`, `ValueTooLarge`, `ExcessYoctoNear`, unsupported actions) or other non-`Ok` results — `inner_rlp_execute` immediately `return`s the error, discarding `caller_deposit` without creating any promise [5](#0-4) . Back in `rlp_execute`, this error is turned into a value response, not a panic: `Err(e) => PromiseOrValue::Value(e.into())` [6](#0-5) . `ExecuteResponse` is explicitly documented as existing so that the method "should never panic," precisely to let contract state changes persist even on error [7](#0-6) .

Because the call completes successfully (no panic), NEAR's runtime does not perform the automatic deposit refund it performs on function-call failure (as demonstrated for a genuinely failing call in `test_gas_key_refund`, where the deposit is only refunded because the function call panicked/errored at the runtime level) [8](#0-7) . Instead, the attached deposit — already credited to the wallet contract's account balance as part of applying the `FunctionCall` action — permanently remains on the wallet contract's balance, with no code path ever moving it back to the caller.

This is the direct analog of the reported `receive()` bug: a payable entry point accepts value, hits an internal branch with "no logic to route the funds," and the value is irrecoverably absorbed by the contract instead of being returned to the sender.

### Impact Explanation
Any unprivileged account (an external caller or a relayer without an access key) that calls `rlp_execute` and attaches a NEAR deposit, but supplies an RLP payload that fails to parse into a supported action/emulation (a `UserError`), permanently loses that attached deposit to the target wallet contract's balance. This is a direct, concrete loss of value for the caller with no way to recover it, matching the "permanently frozen/lost funds" criterion. Given `rlp_execute` is a core, externally reachable entry point of the wallet contract used by both relayers and direct RPC callers, this is broadly reachable and requires no special privilege.

### Likelihood Explanation
Triggering this requires only sending a single `FunctionCall` transaction to `rlp_execute` with a deposit attached and calldata that fails ABI/selector parsing (easy to construct, e.g. malformed function selector or invalid ABI-encoded args) [9](#0-8) . Since attaching a deposit alongside an already-failing call is exactly the kind of "user makes an honest mistake" scenario the original ETH `receive()` report describes, likelihood is realistic, especially from buggy front-end/relayer code that miscalculates the intended action or wrongly includes a deposit for a to-be-emulated ETH transaction.

### Recommendation
In `inner_rlp_execute`, whenever an error path returns before scheduling a promise (the `Err(err @ Error::User(_))` and `Err(err) => return Err(err)` branches, as well as any other synchronous error return in `rlp_execute`/`address_check_callback`/`nep_141_storage_balance_callback`), issue a refund transfer of `caller_deposit` back to `predecessor_account_id` before returning the error, mirroring the refund logic already present in `rlp_execute_callback`. Alternatively, have `rlp_execute` panic on early validation failures for external (non-relayer) callers so the NEAR runtime automatically refunds the attached deposit, consistent with normal FunctionCall failure semantics.

### Proof of Concept
1. Deploy the wallet contract to an eth-implicit account, as in `test_wallet_contract_interaction` / `TestContext::new` [10](#0-9) .
2. As any account (does not need to be the wallet owner or hold a function-call access key), submit a `FunctionCall` to `rlp_execute(target, tx_bytes_b64)` attaching, e.g., 1 NEAR, with `tx_bytes_b64` set to malformed/garbage RLP data such that `parse_rlp_tx_to_action` returns `Error::User(UserError::InvalidAbiEncodedData)` or `UnknownFunctionSelector` (see `test_bad_data`) [11](#0-10) .
3. Observe the transaction succeeds (returns `ExecuteResponse { success: false, ... }`), and check the wallet contract's account balance — it will be permanently increased by the attached 1 NEAR, while the caller's balance is decreased by that amount with no refund receipt ever generated, unlike the genuine-failure refund path shown in `test_gas_key_refund` [12](#0-11) .

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
