### Title
Missing Validation That `beneficiary_id != account_id` in `DeleteAccountAction` Causes Permanent Fund Loss - (File: `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/actions.rs`)

---

### Summary

`validate_delete_action` only checks that `beneficiary_id` is a syntactically valid account ID. It does not check that `beneficiary_id` differs from the account being deleted (`receiver_id`). When they are equal, `action_delete_account` enqueues a balance-refund receipt addressed to the account it is simultaneously erasing from state. That receipt arrives at a non-existent named account, the `Transfer` action fails, and because the predecessor is `"system"` the failed-refund amount is burnt rather than returned — permanently destroying the account's entire liquid balance.

---

### Finding Description

`validate_delete_action` in `runtime/runtime/src/action_validation.rs` performs only one check:

```rust
fn validate_delete_action(action: &DeleteAccountAction) -> Result<(), ActionsValidationError> {
    validate_action_account_id(&action.beneficiary_id)?;
    Ok(())
}
``` [1](#0-0) 

`validate_action_account_id` verifies only that the string is a well-formed NEAR account ID. There is no check that `beneficiary_id != receiver_id` (the account being deleted). The `receiver` parameter is available in the calling function `validate_action_with_mode` but is never forwarded to `validate_delete_action`. [2](#0-1) 

At execution time, `action_delete_account` reads the account balance, pushes a `Receipt::new_balance_refund` addressed to `delete_account.beneficiary_id`, and then calls `remove_account` to erase the account from the trie — in that order, with no equality guard:

```rust
let account_balance = account_ref.amount();
if account_balance > Balance::ZERO {
    result.new_receipts.push(
        Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)
    );
}
let remove_result = remove_account(state_update, account_id)?;
``` [3](#0-2) 

`Receipt::new_balance_refund` creates an action receipt whose `predecessor_id` is the literal string `"system"` and whose `receiver_id` is `beneficiary_id`:

```rust
pub fn new_balance_refund(receiver_id: &AccountId, refund: Balance) -> Self {
    Receipt::V0(ReceiptV0 {
        predecessor_id: "system".parse().unwrap(),
        receiver_id: receiver_id.clone(),
        ...
        actions: vec![Action::Transfer(TransferAction { deposit: refund })],
    })
}
``` [4](#0-3) 

When `beneficiary_id == account_id`, this refund receipt targets an account that `remove_account` has just deleted. The refund receipt is a `Transfer` action (not `DeleteAccount`), so it is **not** an instant receipt and is processed in a subsequent block: [5](#0-4) 

By that time the named account no longer exists. The `Transfer` action fails with `AccountDoesNotExist`. Because the predecessor is `"system"`, the deposit refund of the failed receipt is also sent to `"system"`, which is not a real account. Per the runtime's refund rules, a refund whose execution fails is **burnt**:

> "If the execution of a refund fails, the refund amount is burnt."

The entire liquid balance of the deleted account is permanently destroyed.

---

### Impact Explanation

**Loss of funds.** Any named account that submits (or is induced by a contract to submit) a `DeleteAccount` action with `beneficiary_id` equal to its own account ID will have its entire liquid balance permanently burnt. The account is deleted and the tokens vanish from total supply with no recovery path.

The corrupted value is `account_ref.amount()` — the full liquid balance — which should be credited to the beneficiary but instead becomes `tokens_burnt` via the failed-refund path.

---

### Likelihood Explanation

- **Direct user trigger**: Any account owner can craft a `DeleteAccount` transaction with `beneficiary_id = signer_id`. No privileged role is required.
- **Contract-induced trigger**: A malicious or buggy contract can call `promise_batch_action_delete_account(receipt_idx, own_account_id)` via the host function, causing the same outcome for any account that calls it.
- **No existing guard**: `validate_delete_action` has no equality check; `action_delete_account` has no equality check. The only validation is syntactic. [6](#0-5) 

---

### Recommendation

Add an equality check in `validate_delete_action`. Because `validate_delete_action` does not currently receive the `receiver_id`, the check should be added either:

1. In `validate_action_with_mode`, before delegating to `validate_delete_action`, using the already-available `receiver` parameter:

```rust
Action::DeleteAccount(a) => {
    if a.beneficiary_id == *receiver {
        return Err(ActionsValidationError::DeleteAccountBeneficiarySameAsAccount {
            account_id: receiver.clone(),
        });
    }
    validate_delete_action(a)
}
```

2. Or by passing `receiver_id` into `validate_delete_action` and performing the check there.

A matching guard should also be added in `action_delete_account` as a defence-in-depth assertion.

---

### Proof of Concept

1. Alice (`alice.near`) has a balance of 10 NEAR.
2. Alice submits a signed transaction:
   ```
   signer_id:    alice.near
   receiver_id:  alice.near
   actions:      [DeleteAccount { beneficiary_id: "alice.near" }]
   ```
3. `validate_delete_action` passes — `"alice.near"` is a valid account ID.
4. `action_delete_account` executes:
   - Reads `account_balance = 10 NEAR`.
   - Pushes `Receipt::new_balance_refund("alice.near", 10 NEAR)` into `result.new_receipts`.
   - Calls `remove_account(state_update, "alice.near")` — account deleted from trie.
5. In the next block, the refund receipt is processed with `receiver_id = "alice.near"`.
6. `alice.near` does not exist → `Transfer` fails with `AccountDoesNotExist`.
7. Deposit refund goes to `predecessor_id = "system"` → burnt.
8. **10 NEAR permanently destroyed.** Alice's balance is zero and the account is gone.
