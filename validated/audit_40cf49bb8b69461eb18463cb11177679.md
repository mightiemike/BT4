### Title
Attached native NEAR deposit permanently trapped in the Wallet Contract on intermediate cross-contract call failure - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
This is the NEAR analog of the Sherlock M-3 `FeeBuyback` finding: an unprivileged caller can attach native tokens to a contract call, and under a specific failure path those tokens become permanently stuck with no rescue mechanism. In the NEAR Wallet Contract (NEP-518), an external caller's attached `$NEAR` deposit (`CallerDeposit`) is only refunded from the single terminal callback `rlp_execute_callback`. Two other callbacks in the same execution chain — `address_check_callback` and `nep_141_storage_balance_callback` — can also terminate the flow on failure but do not contain any refund logic for `caller_deposit`, permanently trapping the attached deposit in the contract.

### Finding Description
`inner_rlp_execute` computes `CallerDeposit::new(&context)` for any external (non-self) caller who attaches a deposit (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:345`), and threads it through the multi-hop promise chains used for two transaction kinds:

- `EOABaseTokenTransfer { address_check: Some(_) }` → calls the address registrar, then `address_check_callback` (`lib.rs:412-431`).
- `ERC20Transfer` (emulated NEP-141 transfer) → calls `storage_balance_of`, then `nep_141_storage_balance_callback` (`lib.rs:433-458`).

Only the final `rlp_execute_callback` refunds the caller's deposit on failure: [1](#0-0) 

However, `address_check_callback` returns an early failure response with **no refund** when the registrar lookup fails: [2](#0-1) 

And `nep_141_storage_balance_callback` returns an early failure response with **no refund** when the `storage_balance_of` call to the token contract fails or returns malformed data: [3](#0-2) 

In both of these paths the caller's attached `$NEAR` deposit was already credited to the Wallet Contract's account balance when the outer transaction (`rlp_execute`, a `#[payable]` method) was executed. If the downstream call it depends on (address registrar lookup, or the token's `storage_balance_of`) fails — which can happen for reasons entirely outside the caller's or the wallet owner's control, e.g. the registrar/token account not existing, being out of gas, or panicking — the function returns `PromiseOrValue::Value(ExecuteResponse{success:false,...})` directly, `has_in_flight_tx` is reset to `false`, and the `CallerDeposit` captured in the closure is simply dropped. No transfer action is ever generated to return the funds, and the `WalletContract` struct exposes no rescue/withdraw method comparable to `rescueERC20()` in the referenced report. The deposit is now indistinguishable from the wallet's own balance and can never be recovered by the original caller through the contract's public interface.

### Impact Explanation
This results in permanently frozen funds for any unprivileged, external (non-owner) caller who submits an `rlp_execute` transaction with an attached `$NEAR` deposit targeting either of the two multi-hop code paths, whenever the intermediate cross-contract call fails for any reason (misconfigured/non-existent registrar or token account, running out of allotted callback gas, a panicking token contract, etc.). This is a genuine "permanently frozen funds" outcome as called out in the validation criteria, reachable purely by a normal RPC-submitted, unprivileged transaction — no validator or network-level compromise is required.

### Likelihood Explanation
Likelihood is moderate-to-high: any relayer/user can construct an eth-emulated `ERC20Transfer` targeting a token contract, or an `EOABaseTokenTransfer` with `address_check` targeting an unregistered address, and attach `$NEAR`. All it takes to trigger permanent fund loss is an intermediate call (`storage_balance_of` or the registrar `lookup`) failing — which is a normal occurrence (e.g., insufficient forwarded gas, target account not deployed, or the called contract reverting), not a rare edge case. No special privileges or races are needed to reach the vulnerable branches.

### Recommendation
Ensure the deposit-refund logic present in `rlp_execute_callback` is also executed on every early-return failure branch that can terminate the promise chain, specifically the `PromiseResult::Failed` and malformed-response branches in `address_check_callback` (`lib.rs:141-158`) and `nep_141_storage_balance_callback` (`lib.rs:203-220`). Either factor the refund into a shared helper invoked from all early-exit points, or restructure the flow so any terminal failure route unconditionally schedules the `caller_deposit` refund transfer before responding.

### Proof of Concept
1. An external (non-owner) account calls `rlp_execute` on a deployed Wallet Contract with a signed Ethereum-emulated `ERC20Transfer` transaction targeting a NEP-141 token contract, attaching a native `$NEAR` deposit as a relayer fee/value (`CallerDeposit::new` captures it since predecessor != current account, `lib.rs:181-191` in `types.rs`).
2. `inner_rlp_execute` routes this into the `ERC20Transfer` branch, dispatching a cross-contract call to `storage_balance_of` on the token account and chaining `nep_141_storage_balance_callback` with `caller_deposit` (`lib.rs:433-458`).
3. The `storage_balance_of` call fails (e.g. because the token account has since been deleted, does not implement the method, or ran out of gas).
4. `nep_141_storage_balance_callback` hits the `PromiseResult::Failed` branch (`lib.rs:203-209`) and returns `ExecuteResponse{success:false,...}` directly — no transfer is scheduled back to the caller.
5. The caller's attached `$NEAR` remains permanently on the Wallet Contract's account balance; there is no method on `WalletContract` to reclaim or rescue it.
