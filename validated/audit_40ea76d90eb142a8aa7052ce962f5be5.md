### Title
PoX reward address validation permits the burn hash (all-zero `Hash160`), silently sending a Stacker's BTC reward to an unspendable output - ([File: stackslib/src/chainstate/stacks/boot/pox-4.clar])

### Summary
`stack-stx` (and its equivalents in `pox.clar`/`pox-2.clar`/`pox-3.clar`) only validates the *version* and *hashbytes length* of a Stacker-supplied PoX reward address; it never rejects the all-zero hash that the node treats as the reserved "burn" address. When this address is later chosen by VRF as a block-commit reward recipient, the node's own `is_burn()` logic classifies the payout as a burn rather than a real payment, so the Bitcoin funds are sent to a provably-unspendable output instead of reaching the Stacker who locked up STX for that reward. This is the direct analog of the Foundation report: an address that resolves to the "null" recipient causes value to be burned instead of paid to the intended party.

### Finding Description
`minimal-can-stack-stx` in the PoX contracts only checks: [1](#0-0) 
i.e. `check-pox-addr-version` (version ≤ max) and `check-pox-addr-hashbytes` (correct buffer length for the version) — there is no assertion that `hashbytes` is non-zero. A caller can therefore submit `pox-addr = { version: 0x00 (P2PKH), hashbytes: 0x0000...00 (20 zero bytes) }` and pass validation.

On the node side, `StacksAddress::is_burn` / `PoxAddress::is_burn` define the burn address purely as "hash bytes are all zero": [2](#0-1) [3](#0-2) 

This address, once accepted into the reward set, can be chosen by the VRF-seeded selection in `pick_recipients_from_next_cycle`: [4](#0-3) 

When a miner later builds the block-commit, `calculate_paid_rewards` explicitly treats any `is_burn()` output as destroyed value rather than a payout to a recipient: [5](#0-4) 

and `LeaderBlockCommitOp::check_pox_outputs`'s "all burns" fast-path further assumes that any `is_burn()`-classified recipient set means no real Stacker is owed a payment: [6](#0-5) 

The equality that should hold is: *every address selected from a non-empty, legitimately-stacked reward-set slot must correspond to a spendable BTC output that the Stacker who locked STX for it can redeem.* Because the contract fails to reject the reserved null hash, a Stacker's real slot can decode to the same representation the node uses for "nothing to pay," breaking that equality — the BTC that should have gone to the Stacker is instead burned to an OP_RETURN-equivalent, unspendable scriptPubKey.

### Impact Explanation
This is bounded to the reward owed to the Stacker(s) who register the zero-hash address (or whoever is chosen alongside them under the "all recipients are burn" fast path) — it does not fork the chain or corrupt consensus, but it causes a real, permanent loss of a PoX reward payout, matching "a poison or reward mis-payment bounded to fees" in the High-severity bucket.

### Likelihood Explanation
This is triggerable unilaterally by any single Stacker calling `stack-stx`/`stack-extend`/`delegate-stack-stx` with a crafted `pox-addr`; no majority, admin, or other party's key is required. The only precondition is being chosen for a reward slot, which happens naturally through normal PoX participation and VRF selection over one to two reward cycles.

### Recommendation
Add an explicit rejection of the all-zero hash (and any other network-reserved unspendable pattern) in `check-pox-addr-hashbytes`/`minimal-can-stack-stx` across `pox.clar`, `pox-2.clar`, `pox-3.clar`, and `pox-4.clar`, matching the node-side `is_burn()` definition so a legitimate Stacker's PoX address can never collide with the burn-address sentinel used by `calculate_paid_rewards` and `check_pox_outputs`.

### Proof of Concept
1. A user calls `stack-stx` (or `stack-aggregation-commit`/`delegate-stack-stx`) with `pox-addr = { version: 0x00, hashbytes: 0x0000000000000000000000000000000000000000 }` (20 zero bytes) and a valid `amount-ustx`/`lock-period`; `minimal-can-stack-stx` succeeds because it never compares `hashbytes` against zero.
2. This address is registered in the reward set for the upcoming cycle via `get-reward-set-pox-address`, consumed by `get_reward_addresses_pox_2`/equivalent.
3. When the reward cycle begins, `pick_recipients_from_next_cycle` may select this slot as one of the two `OUTPUTS_PER_COMMIT` recipients.
4. A miner's block-commit sends BTC to this address; because `PoxAddress::is_burn()` returns true for it, `calculate_paid_rewards` records the amount as `burn_amt`, not as a payout to any Stacker, and the BTC lands in an unspendable output on the Bitcoin chain.
5. The Stacker who locked STX for that slot receives no BTC reward — the funds are permanently lost, exactly mirroring the address(0)-burns-royalties defect in the original report.
