### Title
Unvalidated `DeleteAccountAction.beneficiary_id` permanently burns account balance when beneficiary does not exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` lets any signer choose an arbitrary `beneficiary_id` to receive the deleted account's remaining balance. Only syntactic account-id validation is performed on this field; there is no check that the beneficiary account actually exists before the source account is destroyed and the refund receipt is dispatched. If the beneficiary does not exist, the resulting transfer is treated as a "refund" receipt, which by protocol design can never implicitly create an account, so it fails and the balance is permanently burned instead of reaching anyone.

### Finding Description
`validate_delete_action` only checks that `beneficiary_id` is a syntactically valid `AccountId`, with no existence check: [1](#0-0) 

At execution time, `action_delete_account` unconditionally pushes a `Receipt::new_balance_refund` addressed to `delete_account.beneficiary_id` for the full remaining balance, without any prior verification that the account exists: [2](#0-1) 

This generated receipt is a system-predecessor "refund" receipt. `check_account_existence` for a `Transfer` action only allows implicit account creation if `implicit_creation_allowed` returns true: [3](#0-2) 

But `implicit_creation_allowed` explicitly forbids account creation for refund receipts, unconditionally: [4](#0-3) 

So a transfer refund to a nonexistent `beneficiary_id` fails with `AccountDoesNotExist`. Because it is a refund receipt (predecessor is `system`), the runtime does not retry or re-refund it — it burns the deposit instead of crediting anyone, per the documented failure-mode invariant: "a failed refund burns its deposit into `other_burnt_amount` rather than refunding" (`runtime/runtime/src/lib.rs:929`, `:972`, documented in `protocol-model/spec/runtime-execution.md:152`). The existing integration test comment corroborates this exact behavior: "The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" is not accurate to a straightforward refund back to the sender — the sender account has already been deleted, so the amount is burned, not returned: [5](#0-4) 

This mirrors the DODORouteProxy pattern exactly: a user/relayer-controlled fee/value-recipient field is never checked for validity/reachability before the value transfer executes, so under normal-but-unvalidated conditions the value is irretrievably lost rather than delivered.

### Impact Explanation
Any account holder (or a relayer submitting a meta-transaction `DeleteAccount` action, or a contract issuing `promise_batch_action_delete_account`) can lose their entire remaining balance in a single transaction merely by specifying a `beneficiary_id` that is syntactically valid but does not correspond to an existing account (a very easy typo: any unused, never-created named account, or a near-implicit/eth-implicit/deterministic/universal id that was never funded). The funds are not returned to anyone — they become part of `other_burnt_amount`, permanently removed from total supply. This is a genuine, protocol-level "frozen/lost funds" bug reachable by an ordinary unprivileged transaction signer, with no way to recover once the delete-account receipt commits (the source account has already been removed by that point).

### Likelihood Explanation
High likelihood of unintentional occurrence: `beneficiary_id` is a free-form user-supplied string with no existence check either at transaction submission (mempool/RPC) or at execution, and typos or use of accounts that have not yet been created (e.g. a not-yet-registered named account, or copy-pasting an implicit-account id incorrectly) are easy mistakes. It could also be exploited deliberately by a malicious relayer executing meta-transactions on a victim's behalf, or scripted attacks that trick users/dApps into signing a `DeleteAccount` action whose beneficiary is intentionally invalid, silently destroying the victim's balance instead of the expected transfer.

### Recommendation
Before creating and dispatching the `balance_refund` receipt in `action_delete_account`, verify that `beneficiary_id` refers to an account that exists (or is of a type that transfers can implicitly create, and route that non-refund creation path instead of the refund path). Alternatively, disallow committing the `DeleteAccount` action (fail the whole receipt, restoring atomicity via the existing rollback mechanism) when the beneficiary account cannot be confirmed to exist, so the balance is not moved (and thus not burned) until a valid recipient is guaranteed. At minimum, avoid silently converting a failed beneficiary payout into a burn; surface it as an explicit, well-documented economic effect and consider only allowing existing-account beneficiaries, since after the source account is deleted there is no way to reissue or reroute the payment.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance and no locked stake.
2. `alice.near` submits `DeleteAccountAction { beneficiary_id: "totally-empty-account.near" }`, where `totally-empty-account.near` has never been created.
3. `validate_delete_action` accepts the action (syntactically valid id) — `runtime/runtime/src/action_validation.rs:447-451`.
4. `action_delete_account` computes `account_balance = alice.near`'s remaining amount and unconditionally emits `Receipt::new_balance_refund(&"totally-empty-account.near", account_balance)`, then deletes `alice.near` — `runtime/runtime/src/actions.rs:380-386`, `:404`.
5. The refund receipt executes a `Transfer` action against `totally-empty-account.near`. Since the receipt is `is_refund = true`, `implicit_creation_allowed` returns `false` — `runtime/runtime/src/actions.rs:929-933` — so `check_account_existence` returns `ActionErrorKind::AccountDoesNotExist` — `runtime/runtime/src/actions.rs:842-850`.
6. Per the documented failure-mode invariant, this failed refund's deposit is burned into `other_burnt_amount` rather than being returned to anyone (`runtime/runtime/src/lib.rs:929`, `:972`).
7. Result: `alice.near`'s entire balance is permanently removed from total supply, delivered to no account — a direct analog of the DODORouteProxy "fee amount will be lost" finding, but here it is the account's principal balance, not merely a fee.
