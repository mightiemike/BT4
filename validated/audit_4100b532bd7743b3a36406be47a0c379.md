### Title
Non-zero-padded `\u` escape in `PythonJsonFormatter` causes incorrect hinted class hash computation for declared Sierra/Cairo0 classes - ([File: crates/papyrus_common/src/python_json.rs])

### Summary
`PythonJsonFormatter::write_string_fragment` escapes non-ASCII characters as `\uXXXX` using the format specifier `{num:4x}`, which pads with **spaces**, not zeros, for hex values shorter than 4 digits. This diverges from the canonical Python `json.dumps()` behavior (and from any correct JSON string escaping), which always zero-pads unicode escapes to exactly 4 hex digits.

### Finding Description
`compute_cairo_hinted_class_hash` serializes a declared Cairo 0 contract's ABI/program/identifiers using a custom `serde_json::ser::Formatter` (`PythonJsonFormatter`) specifically to reproduce Python's `json.dumps()` byte-for-byte output, because the resulting bytes are Keccak-hashed to produce the "hinted class hash," which in turn feeds `compute_deprecated_class_hash` (the deprecated/Cairo0 class hash used in state commitment and the Starknet OS re-execution). [1](#0-0) 

The formatter's non-ASCII branch encodes each UTF-16 code unit and writes it with `write!(writer, r"\u{num:4x}")`, using width `4` without the zero-fill flag: [2](#0-1) 

In Rust, `{:4x}` right-pads/pads with a space by default; only `{:04x}` produces zero-padding. So any UTF-16 code unit whose hex representation is fewer than 4 digits (i.e., any Unicode scalar value below `0x1000`, which includes the vast majority of non-ASCII characters such as Latin-1 supplement, Cyrillic, Greek, CJK below U+1000, and any UTF-16 surrogate-pair low/high unit that happens to fall under that value) will be serialized as e.g. `\u  1a` (two literal space characters) instead of the correct `\u001a`. This is both invalid/divergent JSON text and — more importantly — a different byte sequence than what a reference Python `json.dumps()`-based implementation (or any spec-compliant JSON serializer) would produce for the same ABI/program content.

Because a contract declarer fully controls the ABI (and other string fields such as identifiers/attribute names) of a class being declared, an attacker can craft a Cairo 0 class whose ABI contains a non-ASCII character with code point `< 0x1000`. When the sequencer computes the hinted/deprecated class hash for this declared class, it will get a value that diverges from any implementation that escapes correctly (including the reference Python implementation this formatter was explicitly built to match, per its own doc comment "Formats a json object in the same way that python's `json.dumps()` formats").

### Impact Explanation
This is a canonicalization bug directly analogous to the reported json-sanitizer class of bug (a serializer emitting characters/sequences that do not match what an external/reference parser or consumer expects, enabling ambiguity/inconsistent interpretation of the same input). Here, the consequence in the sequencer's threat model is honest-node divergence and consensus-relevant hash mismatch: the deprecated/Cairo0 class hash is a value committed into state and re-derived by the Starknet OS during re-execution/proving. If the Rust sequencer and any other conformant implementation (or the Starknet OS's own expectations, mirrored from Python `json.dumps`) disagree on the hinted class hash for any declared class containing such characters in its ABI, this produces:
- A wrong class hash / wrong committed root for that declaration, or
- A Starknet OS re-execution mismatch (the OS recomputes the hash and it won't match what the sequencer committed), which can halt block proving/confirmation for the network.

This is reachable directly by an unprivileged contract declarer submitting a `DECLARE` (Cairo 0 style) transaction with a crafted ABI string, satisfying the "declared class" reachable-path requirement.

### Likelihood Explanation
Likelihood is straightforward: any declarer can include non-ASCII characters in ABI entry names, event names, struct/member names, or other free-text fields of a Cairo 0 contract class ABI, or in identifiers, and trigger this code path unconditionally whenever `compute_cairo_hinted_class_hash`/`compute_deprecated_class_hash` is invoked for that class. No special privileges or timing conditions are required — this triggers on ordinary code path used to validate/hash any newly declared deprecated (Cairo 0) class.

### Recommendation
Fix the format specifier to zero-pad the hex digits to exactly 4 characters, matching Python's `\uXXXX` escape convention:
```rust
write!(writer, r"\u{num:04x}")?;
```
Add a regression test asserting that non-ASCII characters with UTF-16 code units below `0x1000` produce the correctly zero-padded 4-digit hex escape, and cross-check the output against Python's `json.dumps()` for a range of code points (including surrogate pairs for values ≥ U+10000) to ensure full parity, since this formatter's entire purpose is byte-for-byte compatibility with a reference implementation feeding a consensus-critical hash.

### Proof of Concept
```rust
use papyrus_common::python_json::PythonJsonFormatter;
use serde::Serialize;
use serde_json::Serializer;

fn main() {
    // U+001A hex value < 0x1000 -> should be "\u001a"
    let s = "\u{1a}bc"; // control char just as an illustrative low-codepoint example; use any
                        // non-ASCII char whose UTF-16 unit is < 0x1000, e.g. '\u{7f}' won't work
                        // (ASCII); use e.g. 'á' (U+00E1) which is non-ASCII and < 0x1000.
    let s = "á"; // U+00E1, non-ascii, UTF-16 unit 0x00e1
    let mut buf = Vec::new();
    let mut ser = Serializer::with_formatter(&mut buf, PythonJsonFormatter);
    s.serialize(&mut ser).unwrap();
    let out = String::from_utf8(buf).unwrap();
    // BUG: produces "\u  e1" (with spaces) instead of the correct "\u00e1"
    println!("{}", out);
    assert_ne!(out, "\"\\u00e1\""); // demonstrates divergence from correct/Python output
}
```
Running this against `compute_cairo_hinted_class_hash` with a Cairo 0 class whose ABI contains `á` (or any similar character) will yield a Keccak hash of the malformed byte sequence rather than the byte sequence a spec-compliant implementation would produce, causing the resulting deprecated class hash to diverge from any other correct implementation.     fn write_string_fragment<W>(&mut self, writer: &mut W, fragment: &str) -> IOResult<()>
    where
        W: ?Sized + Write,
    {
        let mut buf = [0u16; 2];
        for ch in fragment.chars() {
            if ch.is_ascii() {
                writer.write_all(&[u8::try_from(ch).expect("ASCII fits in u8")])?;
            } else {
                let slice = ch.encode_utf16(&mut buf);
                for num in slice {
                    write!(writer, r"\u{num:4x}")?;
                }
            }
        }
        Ok(())
    }
