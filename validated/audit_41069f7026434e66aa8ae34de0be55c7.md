### Title
Legacy (non-hardened) exchange settlement path in `ExchangeCapsule.transaction` allows exchange reserves to go negative — ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The reported bug class is: a value derived from a delta calculation (`new_total_value`) is implicitly assumed to stay non-negative, and only a later fix adds an explicit non-negative clamp/check. The same pattern exists in java-tron's TRX/TRC10 exchange (bancor-style AMM) settlement code: `ExchangeCapsule.transaction()` computes new pool reserves from a floating-point `ExchangeProcessor` and only validates `newFirstTokenBalance/newSecondTokenBalance >= 0` when the optional `hardenedCalc` flag is `true`. In the default (non-hardened) path used unless the `AllowHardenExchangeCalculation` proposal has been passed, no such check exists, so a negative or otherwise corrupted reserve value can be silently written into on-chain state.

### Finding Description
`ExchangeCapsule.transaction()` computes reserve updates for TRX/TRC10 exchange pools: [1](#0-0) 

The non-hardened branch (`hardenedCalc == false`, the default unless a chain-wide proposal is passed) performs plain `long` addition/subtraction on the reserves without any overflow or non-negativity check, and directly uses the result from `ExchangeProcessor`, which performs its bancor-formula math with `double` arithmetic: [2](#0-1) 

Only when `hardenedCalc` is `true` does the code check for negative resulting balances and reject the transaction: [3](#0-2) 

The `hardenedCalc` flag is threaded from `allowHarden()`, which is gated by the `AllowHardenExchangeCalculation` dynamic property/proposal: [4](#0-3) [5](#0-4) 

`ExchangeTransactionActuator.doValidate()` calls `exchangeCapsule.transaction(...)` purely to compute `anotherTokenQuant` for the `tokenExpected` check, and separately `execute()` calls `transaction(...)` again to actually mutate reserves — in both calls, if the proposal has not been activated, `hardenedCalc` is `false`, and the double-precision bancor math result is trusted without a sanity check that either reserve remains `>= 0`. This mirrors the audited bug: a value ("total"/reserve) computed from a delta is assumed non-negative and only patched behind a conditional path, while the unconditional/default path remains exposed. `ExchangeWithdrawActuator`/`ExchangeCreateActuator` are unaffected because they use `subtractExact`/`addExact` unconditionally, but the swap actuator's reserve update logic in `ExchangeCapsule.transaction()` is not.

### Impact Explanation
If floating-point rounding in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (or a combination of extreme/edge-case reserve values and quantities) produces a `buyTokenQuant` larger than the actual pool reserve, the non-hardened path will silently store a negative `firstTokenBalance`/`secondTokenBalance` into the `Exchange` protobuf (a signed `int64`), corrupting the on-chain AMM pool state. This can be leveraged by an attacker broadcasting `ExchangeTransactionContract` transactions to drain more of a token than the pool actually holds, or to permanently corrupt the pool's reserve accounting, breaking future exchange price computations and potentially allowing further extraction of unbacked tokens — an accounting/asset corruption issue reachable directly from an anonymous broadcast transaction.

### Likelihood Explanation
Likelihood is **Low-to-Medium**: the corrupting condition requires the non-hardened path to still be active (i.e., the `AllowHardenExchangeCalculation` proposal not yet activated on the target network) and requires reserve/quantity combinations where floating-point/bancor computation error can push the computed swap amount beyond the counter-reserve. Reaching this state does not require any privileged role — any account can send `ExchangeTransactionContract` transactions — but crafting inputs that trigger the underflow reliably may require careful selection of pool reserves and repeated small trades to accumulate rounding drift.

### Recommendation
Make the non-negative reserve check unconditional in `ExchangeCapsule.transaction()` regardless of `hardenedCalc`, i.e., always validate `newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0` (and ideally always use the `SafeExchangeProcessor`/`BigDecimal` computation path) rather than gating the safety check behind an opt-in proposal.

### Proof of Concept
Conceptual reproduction (cannot be fully executed without a live node):
1. Create an `Exchange` pool via `ExchangeCreateActuator` with small/skewed reserves (e.g., `firstTokenBalance = 1`, `secondTokenBalance` very large, or vice versa) without activating `AllowHardenExchangeCalculation`.
2. Submit a sequence of `ExchangeTransactionContract` swaps chosen so that `ExchangeProcessor.exchange()`'s double-precision bancor calculation returns a `buyTokenQuant` slightly exceeding the actual opposite-side reserve (rounding/precision edge case), as illustrated by the discrepancy already documented between `ExchangeProcessor` and `SafeExchangeProcessor` in the repo's own tests: [6](#0-5) .
3. Because `hardenedCalc` is `false`, `ExchangeCapsule.transaction()` writes the resulting negative `newSecondTokenBalance` (or `newFirstTokenBalance`) directly into the `Exchange` protobuf via `setBalance(...)` without rejecting it, corrupting the pool state.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
