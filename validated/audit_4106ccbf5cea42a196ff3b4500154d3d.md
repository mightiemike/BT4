## Title
External caller's attached deposit is permanently lost when an intermediate cross-contract check fails in the NEAR Wallet Contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (`WalletContract`) tracks an external caller's attached NEAR deposit via `CallerDeposit` so it can be refunded if the emulated Ethereum action ultimately fails. This refund is correctly issued in `rlp_execute_callback` when the *final* action promise fails. However, for transaction kinds that require an intermediate cross-contract check before the final action is dispatched — `EOABaseTokenTransfer` with `address_check` (handled by `address_check_callback`) and `ERC20Transfer` (handled by `nep_141_storage_balance_callback`) — the `Failed` branch of those intermediate callbacks discards the `caller_deposit` parameter entirely and never schedules a refund transfer, leaving the caller's attached deposit stranded in the wallet contract's account balance.

### Finding Description
`inner_rlp_execute` creates a `CallerDeposit` for any external (non-self) predecessor that attaches a deposit: [1](#0-0) 

For `EOABaseTokenTransfer` transactions that require an address-registrar lookup, the deposit is threaded through to `address_check_callback`: [2](#0-1) 

But the `Failed` arm of that callback drops `caller_deposit` without ever creating a refund promise: [3](#0-2) 

The identical pattern exists for ERC-20 transfers, where `nep_141_storage_balance_callback` receives `caller_deposit` but discards it on failure of the `storage_balance_of` view call: [4](#0-3) 

By contrast, the terminal callback `rlp_execute_callback` correctly implements the refund when the final action promise fails, by issuing a `promise_batch_action_transfer` back to `CallerDeposit.account_id`: [5](#0-4) 

This confirms the refund mechanism is intentional and expected on any failure path — it is simply missing in the two intermediate "pre-check" callbacks. The attached NEAR deposit from the original `#[payable] rlp_execute` call becomes part of the wallet contract account's balance the moment the transaction is accepted; there is no automatic protocol-level refund to the original external caller because the protocol only refunds the *predecessor* of a failed receipt, and the predecessor of the internal registrar/storage-balance lookup receipts is the wallet contract itself, not the original external caller: [6](#0-5) 

This is the same bug class as the reported Astaria issue: a party has already paid in (bid/deposit) expecting either success or a refund path, but an "early exit" / intermediate abort path bypasses the refund logic, permanently trapping the funds in the contract holding them.

### Impact Explanation
Any external account (a relayer or any other on-chain caller other than the wallet owner itself) that submits a `rlp_execute` call with an attached NEAR deposit for an `EOABaseTokenTransfer` with `address_check` or for an `ERC20Transfer` will permanently lose that deposit if:
- the Address Registrar contract's `lookup` call fails (e.g., transient failure, registrar paused/upgraded, insufficient gas), or
- the token contract's `storage_balance_of` view call fails (e.g., malformed/incompatible NEP-141 token, transient failure).

In both cases `has_in_flight_tx` is reset to `false` and an `ExecuteResponse{success: false}` is returned, but the attached deposit stays in the wallet contract's balance with no code path to reclaim it for the original caller. This is a concrete, unauthorized value-loss / permanently-frozen-funds condition reachable by any transaction signer/relayer interacting with an eth-implicit account's wallet contract.

### Likelihood Explanation
This is triggerable by any unprivileged caller who is not the wallet owner (e.g., a relayer paying/forwarding fees, or any account calling `rlp_execute` directly with a deposit) whenever the downstream registrar or NEP-141 token contract call fails — a condition that can occur due to normal operational failures (gas exhaustion, contract not deployed/paused, malformed response) and does not require any malicious validator, network, or node behavior. It requires only a single transaction/RPC call from a regular account, matching the "unprivileged transaction signer" reachability bar.

### Recommendation
In the `Failed` arms of `address_check_callback` and `nep_141_storage_balance_callback`, mirror the logic in `rlp_execute_callback`: if `caller_deposit` is `Some`, issue `env::promise_batch_create` + `promise_batch_action_transfer` to refund `account_id` for `yocto_near` before returning the failure `ExecuteResponse`.

### Proof of Concept
1. Deploy the eth-implicit wallet contract for address `A`.
2. From an external (non-owner) account `R`, call `rlp_execute` with an RLP-encoded Ethereum transaction that is an `EOABaseTokenTransfer` to another eth-implicit account requiring `address_check` (or an ERC-20 `transfer`), attaching `N` yoctoNEAR as deposit.
3. Ensure the Address Registrar's `lookup` call (or the token's `storage_balance_of` call) fails — e.g., by pointing at a registrar/token account that does not implement the expected method, or that runs out of gas.
4. Observe: `address_check_callback` (or `nep_141_storage_balance_callback`) hits the `PromiseResult::Failed` arm, returns `ExecuteResponse{success:false}`, and never issues a refund transfer to `R`.
5. `R`'s balance decreased by `N` yoctoNEAR permanently; the wallet contract account's balance retains those funds indefinitely, as confirmed by the absence of any refund-transfer promise in the failing code path, in contrast with the refund logic present in `rlp_execute_callback`.

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );
