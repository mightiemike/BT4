Based on my research, I found a strong analog to the OpenSSL bug class (silent truncation/undercounting that lets unauthenticated data slip past size-based integrity limits).

### Title
Body-only transaction size accounting lets ML-DSA-65 (post-quantum) transactions smuggle unmetered bytes past `max_transaction_size`/`combined_transactions_size_limit` on pre-`PostQuantumSignatures` protocol versions - ([File: core/primitives/src/transaction.rs])

### Summary
`SignedTransaction::size_for_limits()` only counts the full wire size (body + signature) once the `PostQuantumSignatures` protocol feature is enabled; before that version gate it falls back to the legacy `get_size()`, which measures only the borsh-encoded `Transaction` body and excludes the signature entirely. [1](#0-0)  Since ML-DSA-65 signatures are ~3.3 KiB (vs. ~65 B for Ed25519), a transaction signed with an ML-DSA-65 key can carry ~3.3 KiB of data that is completely invisible to `max_transaction_size` and `combined_transactions_size_limit` accounting on any protocol version prior to `PostQuantumSignatures`, exactly mirroring the OpenSSL class of bug: a size-limited/authenticated artifact silently contains more bytes than the enforcement path accounts for, while the check still reports success.

### Finding Description
`Transaction::get_hash_and_size()` computes size from `borsh::to_vec(&self)` on the inner `Transaction` only, deliberately excluding the `Signature`. [2](#0-1)  `SignedTransaction::get_size()` returns this body-only size, while `wire_size()` adds the serialized signature length to get the true on-wire size. [3](#0-2)  `size_for_limits(protocol_version)` is the value actually checked against `max_transaction_size` in `ValidatedTransaction::check_valid_for_config` and against `combined_transactions_size_limit` when packing transactions into `ChunkStateWitness`, but it only switches to `wire_size()` starting at the `PostQuantumSignatures` protocol version - otherwise it returns the under-counting `get_size()`. [1](#0-0)  The check itself lives at: [4](#0-3) 

The project's own documentation explicitly flags this as an open "witness-honesty gap": *"`SignedTransaction::get_size()` counts only the inner `Transaction` body, so it under-counted every ML-DSA-65 tx by its ~3.3 KiB signature - including inside `combined_transactions_size_limit`... `size_for_limits(protocol_version)` selects [`wire_size()`] for the `max_transaction_size` and `combined_transactions_size_limit` gates from `PostQuantumSignatures` onward."* [5](#0-4)  This confirms the gap is real and version-gated rather than universally fixed.

### Impact Explanation
The `combined_transactions_size_limit` (and the family of state-witness size limits it belongs to) exists specifically to bound the total uncompressed size of `ChunkStateWitness` to a documented ~21 MiB budget so witnesses can be reliably distributed and validated. [6](#0-5)  If ML-DSA-65 is a supported key/signature type on a network before `PostQuantumSignatures` activates (during any rollout window, or on any deployment that pins an older protocol version while still accepting PQ key types), an attacker can pack transactions whose accounted size is under the limit but whose true wire size (and hence true witness contribution) exceeds it by ~3.3 KiB per transaction. At scale this breaks the invariant the size limits are designed to guarantee, inflating the actual `ChunkStateWitness` beyond its intended cap - the same "checks pass, but the underlying artifact is larger than what was authenticated/budgeted" failure mode as the OpenSSL advisory, applied to chunk-witness size budgeting instead of file signing.

### Likelihood Explanation
This requires only a single unprivileged actor submitting an ML-DSA-65-signed transaction from any account, no special privileges - and per the documentation the gap is `protocol_version`-gated, meaning it is currently exploitable on any network/build combination where PQ key types are already accepted but `PostQuantumSignatures` is not yet the active protocol version.

### Recommendation
Remove the protocol-version gate on `size_for_limits()` (or otherwise ensure `wire_size()` - or an equivalent signature-inclusive size - is always used for `max_transaction_size` and `combined_transactions_size_limit` accounting), independent of whether `PostQuantumSignatures` has activated, so the enforced size always matches the true wire/witness footprint of the transaction.

### Proof of Concept
1. On a network/build where PQ key types (`KeyType::MLDSA65`) can be used but `ProtocolFeature::PostQuantumSignatures.enabled(protocol_version)` is `false` for the active protocol version.
2. Create and sign a transaction using an ML-DSA-65 signer, sized so that `get_size()` (body only) is just under `max_transaction_size`/`combined_transactions_size_limit`, while `wire_size()` (body + ~3.3 KiB ML-DSA-65 signature) exceeds it - as constructed in the existing test `slow_test_combined_tx_size_limit_counts_ml_dsa_signature`, which explicitly measures this delta. [7](#0-6) 
3. Submit the transaction(s); `check_valid_for_config` accepts them because `size_for_limits` returns the smaller `get_size()` value on the pre-feature protocol version. [4](#0-3) 
4. Repeat with multiple such transactions in one chunk; the true wire/witness bytes contributed exceed `combined_transactions_size_limit` even though every individual check reported success, inflating the actual `ChunkStateWitness` beyond its designed cap.

    /// Full borsh-serialized size of the signed transaction, including the
    /// signature.
    ///
    /// [`Self::get_size`] counts only the inner `Transaction` body, omitting
    /// the signature - ~65 B for ed25519 but up to ~3.3 KiB for ML-DSA-65.
    /// Use this where the true on-wire / in-witness size matters.
    pub fn wire_size(&self) -> u64 {
        let signature_size =
            borsh::object_length(&self.signature).expect("borsh signature length") as u64;
        self.size + signature_size
    }

### Size axis (accounting done, pricing deferred)

`SignedTransaction::get_size()` counts only the inner `Transaction` body, so it
under-counted every ML-DSA-65 tx by its ~3.3 KiB signature - including inside
`combined_transactions_size_limit`, the bound on transaction bytes carried by
the `ChunkStateWitness`. `SignedTransaction::wire_size()` now returns the full
borsh length (signature included), and `size_for_limits(protocol_version)`
selects it for the `max_transaction_size` and `combined_transactions_size_limit`
gates from `PostQuantumSignatures` onward (version-gated to keep chunk
production deterministic across the boundary). The mempool counts `wire_size()`
unconditionally, since it physically buffers the signature. *Pricing* the extra
size - e.g. a per-wire-byte gas surcharge at conversion time, mirroring the
verify cost - is deferred: the accounting fix closes the witness-honesty gap on
its own, independent of any later pricing decision. A per-byte component on
`AddKey`/`DeleteKey` for the ~1952-byte pubkey they carry on the wire is in the
same deferred bucket.

## State witness size limits

Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 21MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.

The limits are:

* `max_transaction_size = 1.5 MiB`
  * All transactions must be below 1.5 MiB, otherwise they'll be considered invalid and rejected.
  * Previously was 4MiB, now reduced to 1.5MiB
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
* `max_receipt_total_input_size - 4 MiB + 640 B`
  * Hard limit on the combined size of a receipt's resolved promise inputs (the `ReceivedData` referenced by its `input_data_ids`). Receipts which exceed it fail with `TotalPromiseInputSizeExceeded` without executing their actions.
  * These inputs are read before `per_receipt_storage_proof_size_limit` starts counting, so without this limit a single receipt could pull `max_number_input_data_dependencies * max_receipt_size` (128 * 4 MiB) into the witness.
  * The limit is `max_length_returned_data` (4 MiB) plus the worst-case per-input framing overhead (128 * 5 bytes), so 4 MiB of input data always fits no matter how it's split across data receipts.
* `combined_transactions_size_limit - 4 MiB`
  * Hard limit on total size of transactions from this and previous chunk. `ChunkStateWitness` contains transactions from two chunks, this limit applies to the sum of their sizes.
