### Title
JSON-RPC parsing occurs before per-request/IP rate limiting in the Chainlink Gateway HTTP server, enabling memory-amplification DoS - (File: core/services/gateway/network/httpserver.go, core/services/gateway/gateway.go)

### Summary
The Chainlink Gateway (used by CRE/WebAPI/HTTP-trigger workflows to accept requests from unprivileged external callers) parses the full JSON-RPC request body before any request-level or per-IP rate limiting is applied, mirroring the reported bug class ("parsing before rate limiting" memory amplification).

### Finding Description
`httpServer.handleRequest` only enforces a *size* limit (`MaxRequestBytesLimiter`) before reading the body — there is no per-IP or global concurrency/parsing throttle at this layer: [1](#0-0) 

The raw bytes are then passed straight to `gateway.ProcessRequest`, which immediately performs **two** JSON decode passes (`jsonrpc2.DecodeRequest` then `codec.DecodeJSONRequest`, i.e. `json.Unmarshal` into `api.Message`) before any rate limiting is considered: [2](#0-1) 

Rate limiting is only enforced *after* this parsing and *only* inside specific downstream handlers, and only for specific methods/paths:
- The legacy WebAPI handler applies a rate limiter only when forwarding an *outgoing* node message, not on inbound user request parsing, and the inbound `HandleLegacyUserMessage` path has an explicit `// TODO: apply allowlist and rate-limiting here` marker: [3](#0-2) [4](#0-3) 
- The v2 HTTP trigger handler applies rate limiting (`checkRateLimit`) only *after* full request parsing, workflow-ID resolution, and JWT authorization: [5](#0-4) [6](#0-5) 

There is no global concurrent-parsing semaphore in the gateway HTTP path analogous to what the external report recommends — the only pre-parsing control found is `MaxRequestBytesLimiter`, a size cap, not a rate/concurrency cap: [7](#0-6) 

### Impact Explanation
Because JSON decoding happens unconditionally for every inbound HTTP request regardless of source IP, and because the only bound is a configurable byte-size cap, an attacker can send many concurrent requests (each up to the configured `GatewayIncomingPayloadSizeLimit`) that all get fully parsed into `serde/encoding`-equivalent in-memory structures (`api.Message`, nested JSON via `json.RawMessage`) before any rate limiter runs. Since `http.Server` has no built-in concurrency ceiling here (`ReadTimeout`/`WriteTimeout` only bound duration, not concurrency), and rate limiting is workflow/node/method-scoped rather than IP-scoped and applied only after parsing, an unauthenticated or low-privilege caller can drive amplified memory consumption on the gateway process, which is a shared control-plane component routing to DON nodes. This is a legitimate gateway/capability-routing trust-boundary DoS analog, not a mocked or node/peer-only issue.

### Likelihood Explanation
The gateway's HTTP endpoint is designed to accept external, unprivileged requests (CRE workflow triggers, WebAPI triggers) as documented in the HTTP Handlers V2 README, so the attack surface is directly reachable without special privileges: [8](#0-7) . The absence of pre-parsing IP/global rate limiting (only a size limiter) and the explicit "TODO: apply allowlist and rate-limiting here" comment on the legacy path indicate this gap is a known, unresolved condition rather than a defense-in-depth already covering it.

### Recommendation
1. Add an IP-based or global concurrency/rate limiter in `httpServer.handleRequest` (`core/services/gateway/network/httpserver.go`) that runs before `io.ReadAll`/JSON parsing, not just the existing byte-size cap.
2. Collapse the double-parse in `gateway.ProcessRequest` (`jsonrpc2.DecodeRequest` + `codec.DecodeJSONRequest`) or gate the second parse behind a cheap pre-check.
3. Extend rate limiting to all inbound methods/handlers uniformly (including the legacy `HandleLegacyUserMessage` path currently marked `// TODO`), not only the v2 HTTP trigger's post-auth `checkRateLimit`.
4. Consider a global semaphore bounding concurrent JSON-parsing operations across all gateway HTTP connections.

### Proof of Concept
Send many concurrent POST requests to the gateway's configured path, each near the `GatewayIncomingPayloadSizeLimit` byte cap (e.g., a few MB of nested JSON in `params`), from a single or few source IPs. Because `httpServer.handleRequest` → `gateway.ProcessRequest` fully parses every request into `api.Message`/`json.RawMessage` structures before any per-IP/global rate limiter is consulted (rate limiting for the v2 trigger path only occurs after JWT auth + workflow resolution, and is entirely absent on the legacy inbound path per the `TODO` comment), sustained concurrent submissions can amplify memory usage on the gateway process without ever tripping a per-IP throttle.

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	// TODO orgID https://smartcontract-it.atlassian.net/browse/CRE-1707
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		var errLimited limits.ErrorRateLimited
		if errors.As(err, &errLimited) {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
