### Title
Unhandled `receiver_shard_id()` error in `DelayedReceiptQueueWrapper::receipt_filter_fn` causes a receipt-triggered chunk-application panic - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The Sherlock report's root cause is that outbound cross-chain transactions are admitted into a persistent, strictly-ordered processing queue without validating that they will remain processable by the time they are actually delivered/executed, so a single bad entry blocks or crashes the whole downstream pipeline. The closest reachable analog in nearcore is `DelayedReceiptQueueWrapper::receipt_filter_fn`, which `.unwrap()`s the result of `Receipt::receiver_shard_id()` when draining the persistent delayed-receipt queue after resharding. A `GlobalContractDistribution` receipt can be admitted into the delayed queue while carrying a `target_shard` that later cannot be resolved to a shard in the current layout, and `validate_receipt()` never checks this field at admission time.

### Finding Description
`GlobalContractDistributionReceipt` carries a `target_shard: ShardId` that is used to route the receipt hop-by-hop across shards via `forward_distribution_next_shard` [1](#0-0) . This receipt is admitted into the delayed/outgoing queues without any validation of that field: `validate_receipt()` explicitly treats `GlobalContractDistribution` receipts as always valid, regardless of `NewReceipt` or `ExistingReceipt` mode [2](#0-1) .

`Receipt::receiver_shard_id()` computes the destination shard for such a receipt by first checking whether `target_shard` exists in the *current* shard layout, and if not, falling back to `shard_layout.resolve_to_current_shard(target_shard)`; if that also fails it returns `Err(EpochError::ShardingError(...))` [3](#0-2) .

The delayed-receipt queue wrapper used when draining receipts that survived a resharding event calls this same function but discards the `Result` with `.unwrap()`:
```
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
``` [4](#0-3) 

This filter is invoked from both `pop()` (used every chunk while draining the delayed queue) and `peek_iter()` [5](#0-4) . A stale `GlobalContractDistribution` receipt that sat in the delayed queue across two (or more) resharding generations can end up with a `target_shard` whose split-ancestry can no longer be traced by `resolve_to_current_shard`, causing `receiver_shard_id()` to return `Err`, which the `.unwrap()` turns into a panic during chunk application on every node processing that chunk.

This mirrors the reported bug class precisely: no validation gate exists (analogous to the missing per-chain checks for Solana/SUI/TON) at the point where the "outbound" cross-shard receipt is queued, so an admissible-but-eventually-unprocessable entry sits in a strictly-ordered FIFO queue (`DelayedReceiptQueue`, the NEAR analog of the CCTX nonce queue) and only fails when popped for delivery — except here the failure mode is worse than "blocked queue": it is an unhandled `unwrap()` panic.

A dedicated regression test in the repository (`test-loop-tests/src/tests/global_contracts_distribution.rs`) explicitly documents this exact scenario and asserts the chain does not stall after two resharding generations, indicating the maintainers are aware of this exact failure mode as a live risk area [6](#0-5) . I was not able to fully verify, within the available search budget, whether `resolve_to_current_shard` (`core/primitives/src/shard_layout/mod.rs`, `core/primitives/src/shard_layout/v3.rs`) is guaranteed to resolve *any* number of resharding generations or only a bounded number, which determines whether this panic is still reachable on the current tree or has been fully mitigated by that function's implementation. This is the key remaining uncertainty.

### Impact Explanation
If `resolve_to_current_shard` cannot always resolve an arbitrarily-aged `target_shard` (e.g., after several resharding epochs occur while a `GlobalContractDistribution` receipt is delayed, or after a chain of shard merges/splits that breaks the traceable ancestry), every validator/chunk-producer node that attempts to drain the delayed-receipt queue for the affected shard will panic in `receipt_filter_fn`. Because this code path runs deterministically on every node applying that chunk, this is a transaction/receipt-triggered chain halt for the affected shard — the exact "concrete... transaction-triggered halt" impact class permitted by the rules, not merely a resource-exhaustion or DoS issue.

### Likelihood Explanation
Triggering requires: (1) deploying a global contract (an ordinary, unprivileged action any account can perform) whose distribution receipt gets delayed/buffered long enough to survive multiple resharding events, and (2) at least two resharding generations occurring during that window. Resharding is an infrequent, protocol-scheduled event, so likelihood depends on timing relative to resharding schedules, and on whether `resolve_to_current_shard`'s ancestry walk is actually bounded in a way that fails for realistic multi-generation splits. Without confirming the depth-limits of `resolve_to_current_shard`, I can only assess this as a credible but unconfirmed path — the existence of a targeted regression test for exactly this scenario suggests the underlying risk was real enough to warrant dedicated test coverage.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` with proper error propagation (e.g., return a `Result` from the filter and propagate `RuntimeError`/`StorageInconsistentState` instead of panicking), and audit `resolve_to_current_shard` to guarantee it can resolve `target_shard` across an unbounded number of resharding generations, or alternatively validate/refresh `GlobalContractDistribution.target_shard` against the *current* shard layout each time the receipt is forwarded/dequeued rather than only at receipt-creation time.

### Proof of Concept
Not independently reproduced here (would require driving a testnet-scale multi-epoch resharding scenario). The repository's own `test_global_receipt_distribution_at_resharding_boundary`-adjacent test in `test-loop-tests/src/tests/global_contracts_distribution.rs:163-186` constructs exactly this scenario (deploy a global contract, force two shard splits while distribution receipts are still in flight/delayed, then drain the delayed queue) and its comment states the expected failure mode is a panic inside `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the stale `target_shard`.

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }
