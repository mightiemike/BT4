### Title
Stale-read race condition in `performTokenExchange` allows an anonymous requester to wipe a merchant's valid offline access token, causing repeated DoS of the auth handler - (File: `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`)

### Summary
The token-exchange middleware reads the currently stored session *before* making an external network call to Shopify's `/admin/oauth/access_token` endpoint, and only updates/invalidates the session storage record *after* that external call resolves. Just as `ConvexMasterChef`'s `deposit()`/`withdraw()` perform the reward-accounting update only after the external `safeRewardTransfer`/token call, `performTokenExchange` captures a `sessionToInvalidate` snapshot before the slow external exchange, then unconditionally writes it back on failure — overwriting whatever session state exists by the time the external call returns, regardless of concurrent updates.

### Finding Description
In `performTokenExchange`, the session is loaded from storage and hoisted into `sessionToInvalidate` before the (slow, network-bound) call to `exchangeToken`/`api.auth.tokenExchange`: [1](#0-0) 

If that external exchange later fails with an HTTP 401, the code unconditionally invalidates the *stale* snapshot captured before the call, rather than re-reading current storage state: [2](#0-1) 

`invalidateAccessToken` simply nulls the access token on the object it's given and persists it, with no compare-and-swap / version check against the storage: [3](#0-2) 

Because JavaScript/Node request handling is concurrent, two requests for the same shop (same `sessionId`, derived deterministically from `shop`/`sub`) can race:
1. Request A loads the (currently invalid/expired) session, `sessionToInvalidate = A`.
2. Request A calls `exchangeToken` (slow, external HTTP call to Shopify).
3. Meanwhile, Request B (or a legitimate offline-token refresh flow) successfully performs its own token exchange and calls `config.sessionStorage.storeSession(offlineSession)`, persisting a *valid new* access token for the same `sessionId`.
4. Request A's exchange later fails/returns 401 (e.g., because the caller manufactured an already-consumed/expired session token, or Shopify's endpoint returned a transient 401), triggering `invalidateAccessToken(sessionToInvalidate, config)`, which overwrites the *fresh, valid* session B just wrote with the stale pre-call `undefined`-accessToken object.

This is structurally identical to the reported bug class: state that should be updated atomically with (or before) the external call is instead finalized using a value captured prior to it, allowing a concurrent/racing caller to clobber the up-to-date state.

### Impact Explanation
Because `performTokenExchange` runs on the `validateAuthenticatedSession()` middleware path — reachable by an anonymous embedded-app request bearing any (even soon-to-expire or crafted) session token for the target shop — a remote, unauthenticated-beyond-app-installation actor (any user of the installed app, or anyone who can trigger repeated app-bridge/session-token requests for that shop) can repeatedly race token-exchange requests to null out the shop's persisted offline `accessToken`. This forces the merchant's app into a permanent re-authentication loop (bounce-page / 401 retry responses), denying legitimate background/offline API access until the app owner notices and manually reinstalls or the flow self-heals via a fresh successful exchange (itself racy). This matches the accepted "DoS of an auth handler" category.

### Likelihood Explanation
Triggering the race requires only the ability to send concurrent HTTP requests with a session token for the shop (something any user of an embedded app already possesses) and no privileged access; no secret leakage, MITM, or dependency issue is needed. The race window is bounded by the latency of the external `POST https://{shop}/admin/oauth/access_token` call, which is easily wide enough (tens to hundreds of ms) for concurrent requests to interleave, especially under normal app-bridge retry behavior which already fires repeated requests with the retry header on 401s.

### Recommendation
- Do not invalidate a session snapshot captured before the external call; instead, re-load the current session from storage immediately before invalidation and only clear the access token if it still matches the one that was known-stale (compare token/timestamp), or use storage-level optimistic concurrency (e.g., version/etag) so a stale write is rejected.
- Alternatively, only invalidate if the session currently in storage is still inactive/expired at invalidation time, mirroring "checks-effects-interactions": perform the read-check-write invalidation atomically (e.g., a single storage transaction) rather than across two separate awaited external calls.
- Apply the same idempotency guard already used for `afterAuth` (`config.idempotentPromiseHandler`) to the exchange-and-store sequence itself, keyed by `sessionId`, so concurrent requests for the same session serialize instead of racing.

### Proof of Concept
1. App is installed on shop `test.myshopify.com`; a stored offline session with a valid `accessToken` exists.
2. Attacker (any user with a session token for the shop, e.g. via app-bridge) fires two near-simultaneous requests to a protected route guarded by `shopify.validateAuthenticatedSession()`:
   - Request A uses a session token that will cause `exchangeToken` to eventually return 401 (e.g., a token whose backing session is concurrently invalidated/expired server-side, or by racing right as Shopify briefly 401s).
   - Request B uses a fresh, valid session token that successfully completes `exchangeToken` and calls `storeSession(offlineSession)` with a valid `accessToken`, per [4](#0-3) .
3. If Request A's `sessionToInvalidate` (loaded at step start, before B's write) resolves its failing exchange *after* B's `storeSession` call, A's catch handler calls `invalidateAccessToken(sessionToInvalidate, config)`, per [5](#0-4) , overwriting the shop's just-stored valid `accessToken` with `undefined`.
4. All subsequent legitimate requests for the shop now fail session validation and must re-run the full token-exchange/OAuth flow, denying service until another successful (and equally racy) exchange occurs.

import {Session} from '@shopify/shopify-api';

import {AppConfigInterface} from '../config-types';

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
}
