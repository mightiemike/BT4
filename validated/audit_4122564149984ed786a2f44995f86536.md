This is a genuine, self-documented gap in `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs`). The function is the sole check used by both `ChunkExecutor::verify_execution` (used during backup restore's `db-restore --verify-execution-mode`, see `execution/executor/src/chunk_executor/mod.rs:692`) and the `db-tool replay-on-archive` tool (`storage/db-tool/src/replay_on_archive.rs:392`) to confirm that a freshly re-executed `TransactionOutput` matches the historical, ledger-committed `TransactionInfo`. ### Title
Replay/restore execution-verification skips state-checkpoint root hashes, allowing divergent state roots to pass as verified — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  is the authoritative comparator used to confirm that VM re-execution reproduces the exact state committed to the ledger. It verifies transaction status, gas used, the write-set hash (`state_change_hash`), and the event root hash, but it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` between the freshly computed and the persisted/expected `TransactionInfo`. The comment directly above the `Ok(())` return acknowledges this: [2](#0-1)  states that "this comparator ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

### Finding Description
Two consumers rely on this function as their integrity gate:
- `ChunkExecutor::verify_execution`, used by execution-verified chunk application/restore paths, calls it per-transaction and treats a returned `Ok(())` as proof the replay is correct: [3](#0-2) .
- The `db-tool replay-on-archive` verifier calls it identically to decide whether a re-executed chunk is accepted or reported as a failed transaction: [4](#0-3) .

Because the function never re-derives or compares `state_checkpoint_hash` (the Sparse-Merkle-Tree root of world state after the transaction) or the newer `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields carried by `TransactionInfoV1` [5](#0-4) , a divergence in state-checkpoint computation between the historical execution and the current replay is entirely invisible to this check. The write-set hash and event-root check only prove the *transaction-level* output (write set + events) is byte-identical; they say nothing about whether the *accumulated state root* after applying that write set onto local storage matches the one originally committed and Merkle-proven in `TransactionInfo`.

### Impact Explanation
This affects the state-integrity guarantee that authenticated proof structures (state-checkpoint roots embedded in `TransactionInfo`, which is itself a leaf of the transaction accumulator) faithfully reflect the real, deterministic VM/storage result. A tool whose entire purpose is to assert "local execution reproduces the exact ledger state" can report success (`Ok(())`) while the position/hot/main state Merkle root it computed locally differs from the one embedded in the historical `TransactionInfo` and anchored by the accumulator/ledger-info signature. This directly undermines chunk-executor verified-execution and `replay-on-archive`, tools operators depend on to detect state divergence, silent forks, or storage corruption across the trading-native / hot-state feature rollout paths (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`, see feature flags at [6](#0-5) ). This matches the state-integrity gate's "authenticated API or state-view output bound to the wrong version/root" and "hard-fork-only divergence during ... replay ... verification" categories.

### Likelihood Explanation
The gap is deterministic and 100% reproducible whenever these newer feature flags are enabled and a state-root-affecting bug/regression exists anywhere in checkpoint computation (state, hot-state, or position state) — the verification tooling will not catch it, regardless of how many chunks are replayed. It requires no adversarial input; it is a missing check in a correctness/verification tool, not exploitable by an external attacker to directly corrupt consensus state, but it removes the safety net meant to catch such corruption before/after it happens.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` against locally recomputed values (when available/applicable per current feature flags), consistent with the TODO left in the code, before further enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.

### Proof of Concept
Not directly exploitable as a state-corruption PoC by itself; the flaw is in a verification/replay tool. A conceptual demonstration: construct a `TransactionOutput` whose write set and events hash-match a given `TransactionInfo`, but recompute checkpoint-stage state via `DoStateCheckpoint` with a divergent state root (e.g., a bug in the trading-native/position-state Merklization path). Feed both into `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` [4](#0-3) ; `ensure_match_transaction_info` returns `Ok(())` despite the state root mismatch, so the tool reports the chunk as successfully verified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
