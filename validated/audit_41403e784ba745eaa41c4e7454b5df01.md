### Title
`IdempotentPromiseHandler` marks the `afterAuth` hook as "already run" before confirming it succeeded, silently swallowing retries after a failure - ([File: packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts])

### Summary
`IdempotentPromiseHandler.handlePromise` records an identifier as "consumed" *before* the wrapped promise resolves. If the wrapped `afterAuth` hook throws, the identifier remains marked as run for up to 60 seconds, so a retried request with the same session token silently no-ops instead of re-running the hook or surfacing the failure — mirroring the reported pattern of an operation being marked "executed" even though it never completed successfully.

### Finding Description
The handler sets the identifier in its map synchronously, then awaits the actual work: [1](#0-0) 

`isPromiseRunnable` adds the identifier to `this.identifiers` and returns `true` on first sight, *before* `promiseFunction()` is awaited. If `promiseFunction()` subsequently throws, the `finally` block only prunes entries older than `IDENTIFIER_TTL_MS` (60000 ms) — it does not remove the identifier for the failed run. Consequently, any later call to `handlePromise` with the same identifier within that TTL window sees `isPromiseRunnable` return `false`, skips calling `promiseFunction` entirely, and resolves successfully (`return Promise.resolve()`), even though the original invocation failed.

This handler backs the OAuth/token-exchange `afterAuth` hook invocation, keyed by the raw session token (JWT) as the identifier: [2](#0-1) 

The hook itself performs security/setup-relevant work for a freshly authenticated shop (e.g., invoking the app's configured `afterAuth` callback with a live Admin API context): [3](#0-2) 

In the calling code, if `handleAfterAuthHook` throws, the caller converts it into a `500` `Response` that is thrown back to the client: [4](#0-3) 

If the client (App Bridge / browser) retries the request using the *same* still-valid session token (session tokens are short-lived but commonly reused across a small retry window), the second `handlePromise` call for that identical identifier will short-circuit: `isPromiseRunnable` returns `false`, the hook is not re-executed, and no error is thrown — the retry appears to succeed even though the app-defined `afterAuth` logic never actually completed. The exact same pattern exists in the parallel implementations used by `shopify-app-react-router` and `shopify-app-express`: [5](#0-4) [6](#0-5) 

This is directly analogous to the reported `order.func` bug: a completion/idempotency marker (`executed?`, here "identifier consumed") is set optimistically at send-time rather than being conditioned on confirmed success, so a failure downstream (bounce / thrown exception) still leaves the system believing the action occurred.

### Impact Explanation
If a merchant's `afterAuth` hook performs security- or state-critical setup (e.g., webhook registration, billing enforcement, provisioning access-scoped resources) and fails once due to a transient error, a subsequent retry with the same session token will be silently treated as already handled. The app's authentication/setup flow returns success (no error surfaced) to the request pipeline while the actual side effects of `afterAuth` never ran. This produces an inconsistent server-side state for that merchant's install — a class of application-level integrity failure reachable by a single merchant's own (unprivileged) authentication flow, without requiring a leaked secret or a privileged actor. In apps whose `afterAuth` hook enforces mandatory setup, this could functionally degrade or partially disable the app's security-relevant behavior for that shop while apparently completing authentication successfully.

### Likelihood Explanation
Exploitation requires two conditions: (1) the `afterAuth` hook must fail at least once for a given session token (e.g. a transient GraphQL/network error, as already exercised by the existing throttling handling in `webhooks/register.ts`), and (2) a retry must reuse the exact same session token before the 60-second TTL expires. Because session tokens are short-lived and app-bridge/browser retry logic can resend an identical `id_token` within seconds of a `500` response, this is a plausible, naturally occurring scenario rather than a purely theoretical one, though it is not attacker-controlled in the sense of forging identity — it manifests as a reliability/idempotency defect under normal failure conditions.

### Recommendation
- Move the identifier registration in `IdempotentPromiseHandler.isPromiseRunnable` to occur only *after* `promiseFunction()` resolves successfully, or remove the identifier immediately if the promise rejects, so failed attempts can be retried.
- Consider distinguishing "in-flight" vs "completed" state (e.g., store a `Promise` keyed by identifier so concurrent calls await the same in-flight execution, while a rejected promise is not treated as terminal success) rather than a simple has-run boolean.
- Ensure failures from `afterAuth` are surfaced consistently to callers/clients so they can decide whether to retry, and document that identical identifiers within the TTL window will not re-trigger the hook even after a prior failure, if this behavior is intentionally kept for some cases.

### Proof of Concept
1. Configure `shopify-app-remix` (or `-react-router`/`-express`) with an `afterAuth` hook that throws on its first invocation for a shop (e.g., simulate a transient GraphQL error).
2. Perform token exchange for a new session (no active offline session) using a session token `T` — `authenticate()` in `token-exchange.ts` calls `exchangeToken`, stores the offline session, then invokes `handleAfterAuthHook(newSession, request, T)`. The hook throws; the request receives a `500 Internal Server Error` (per `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts:89-105`), but `IdempotentPromiseHandler.identifiers` already contains `T` (set in `isPromiseRunnable` before the `await`).
3. Retry the identical request with the same token `T` within 60 seconds (simulating an App Bridge automatic retry on 500). Because the session is now active in storage, the outer `authenticate()` early-returns the stored session without re-invoking `handleAfterAuthHook` — **but** in cases where the caller code path re-invokes `handleAfterAuthHook` with the same `T` (e.g., concurrent duplicate requests before storage completes, or callers that key by session token across multiple call sites sharing the same `idempotentPromiseHandler` instance), `handlePromise` returns successfully without calling `promiseFunction`, silently skipping the hook logic that previously failed.
4. Assert that `config.hooks.afterAuth` was called exactly once and failed, yet the second call to `handlePromise({promiseFunction, identifier: T})` resolves without error and without invoking the hook again — demonstrating the non-executed hook is treated as executed.

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }

export async function triggerAfterAuthHook(
  params: BasicParams,
  session: Session,
  request: Request,
  authStrategy: AuthorizationStrategy,
) {
  const {config, logger} = params;
  if (config.hooks.afterAuth) {
    logger.info('Running afterAuth hook', {shop: session.shop});

    const admin = createAdminApiContext(
      session,
      params,
      authStrategy.handleClientError(request),
    );

    await config.hooks.afterAuth({
      session,
      admin,
    });
  }
