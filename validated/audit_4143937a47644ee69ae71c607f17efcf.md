### Title
Unvalidated account existence in `WithdrawRewardProcessor` causes NullPointerException DoS during TVM execution - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawRewardProcessor.java`)

### Summary
The C4 report describes a class of bug where a critical payout path fails to validate a recipient/account before using it, causing an unhandled failure that blocks fund distribution for ordinary users. The equivalent defect class in java-tron is a missing account-existence check before dereferencing account state in the TVM native "withdraw vote reward" contract, reachable by any unprivileged address invoking the corresponding TVM opcode/native contract in a normal transaction.

### Finding Description
`WithdrawRewardProcessor.validate()` only rejects genesis-witness ("guard representative") addresses; it performs no check that `ownerAddress` actually has an account in the state store [1](#0-0) .

`execute()` then calls `VoteRewardUtil.withdrawReward(ownerAddress, repo)`, which itself explicitly guards against a nonexistent account by returning early when `repository.getAccount(address)` is `null` [2](#0-1) . Immediately after that call returns, `execute()` re-fetches the account and unconditionally dereferences it without a null check:

```
AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
long oldBalance = accountCapsule.getBalance();
``` [3](#0-2) 

If `ownerAddress` has never been funded/created (a completely normal, attacker-controlled condition — e.g. a fresh, unfunded address, or any address passed as an argument to the TVM's vote/withdraw-reward native contract from a smart contract call), `repo.getAccount(ownerAddress)` returns `null` and the second line throws a `NullPointerException`. This is the same root-cause pattern as the C4 finding: a payout/reward code path assumes a value (fee recipient / account) is valid and unconditionally uses it in a state-mutating operation, without validating it first, so that a preventable, externally-triggerable condition turns a normal operation into a guaranteed failure.

Unlike the Solidity `safeTransfer` revert (a checked, catchable failure), here the failure is an unchecked `NullPointerException`, which is not declared in `execute()`'s `throws ContractExeException` signature. This exception class is not caught by any of the checked-exception handling that normally converts contract execution errors into a clean "REVERT" result, and can propagate further up the TVM/actuator call stack.

### Impact Explanation
Because this defect is inside a native contract invoked as part of ordinary TVM contract execution (not a Solidity-level `safeTransfer`), an uncaught `RuntimeException` escaping the expected `ContractExeException` handling in the executor path risks disrupting transaction/block processing rather than being cleanly reverted — a denial-of-service in the protocol implementation rather than a simple fund lock. At minimum it is a reliably triggerable execution failure in a reward-withdrawal precompile that any address (with no privileged role) can invoke through a smart contract call, matching the report's "reward accounting function can be made to fail for ordinary users" bug class.

### Likelihood Explanation
Triggering the null account condition requires no privileged action: any caller can pass an arbitrary/unfunded address as the "owner" argument into the TVM's withdraw-reward native contract from a transaction/contract call, matching the "broadcast transaction / contract call" unprivileged reachability requirement. No admin action, no key compromise, and no P2P/malicious-peer assumption is needed.

### Recommendation
Add an explicit null-check on the `AccountCapsule` returned by `repo.getAccount(ownerAddress)` in `WithdrawRewardProcessor.execute()` and return/throw a proper `ContractExeException` (mirroring the existing guard already present in `VoteRewardUtil.withdrawReward`) instead of allowing an unchecked `NullPointerException` to propagate out of native-contract execution.

### Proof of Concept
1. Deploy or use any smart contract that can invoke the TVM's "withdraw vote reward" native contract (as exercised in `VoteTest`/`RewardBalanceTest`) with an owner address that has never been assigned an `AccountCapsule` (e.g., a freshly generated, unfunded address never seen by `AccountStore`).
2. Call the withdraw-reward opcode/native contract path with that address as `ownerAddress`.
3. `WithdrawRewardProcessor.validate()` passes (address is not a guard representative) [1](#0-0) .
4. `execute()` calls `VoteRewardUtil.withdrawReward`, which returns immediately because `accountCapsule == null` [4](#0-3) .
5. `execute()` re-fetches the (still null) account and calls `.getBalance()` on it, throwing `NullPointerException` [5](#0-4) .

Note: I was not able to fully trace, within the available tool budget, the exact upstream catch site in `Program.java`/opcode dispatch that invokes `WithdrawRewardProcessor.execute()`, so I cannot confirm with certainty whether this specific `NullPointerException` is ultimately swallowed as a generic VM exception (degrading only to a reverted transaction) or whether it can escape further and affect block-level processing. This should be verified directly in the repository (particularly the native-contract dispatch code in `actuator/src/main/java/org/tron/core/vm/program/Program.java`) before relying on the "protocol-level DoS" severity claimed above.
