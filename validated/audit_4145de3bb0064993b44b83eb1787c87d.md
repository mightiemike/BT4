## Analysis

The `addPool` bug class (an admin-controlled but ever-growing array that gets fully scanned by hot-path logic, eventually exceeding gas/computation limits) has a structural analog in `x/uexecutor`'s `PendingInbounds` collection and its terminal-ballot hook.

Unlike `addPool`, growth of `PendingInbounds` is **not gated by a privileged admin call** — it grows automatically, once per unique cross-chain event, purely from unprivileged user activity on external source chains (deposits/messages into the gateway), which honest validators then vote on via `MsgVoteInbound` / `VoteInbound`.

### Title
Unbounded full-collection scan in `afterInboundBallotTerminal` allows ordinary user deposit volume to degrade/DoS inbound ballot finalization - (File: x/uexecutor/keeper/ballot_hooks.go)

### Summary
Every terminal transition of an `INBOUND_TX` ballot (`PASSED`/`REJECTED`/`EXPIRED`) triggers `afterInboundBallotTerminal`, which performs a full `h.k.PendingInbounds.Walk` over the entire `PendingInbounds` collection to locate the entry owning the finalized `ballotID` [1](#0-0) . `PendingInbounds` entries are created for every distinct source-chain event as soon as the first validator votes on it, and are only removed once all variants of that entry reach a terminal state [2](#0-1) . Because ordinary, unprivileged users control how many distinct cross-chain events exist (e.g. by submitting many cheap deposits/messages on an external chain), they can drive the size of `PendingInbounds` arbitrarily high without any admin action, and every subsequent ballot finalization pays an O(n) cost against that set.

### Finding Description
`afterInboundBallotTerminal` is registered as the `BallotHooks` implementation fired synchronously by `x/uvalidator`'s `MarkBallotFinalized`/`CheckIfFinalizingVote` path whenever an inbound ballot crosses its vote threshold or expires [3](#0-2) [4](#0-3) . The hook's own comment records the load-bearing but unenforced assumption: *"the pending set is small and transient"* [5](#0-4) . Nothing in the code enforces that assumption:

- `PendingInbounds` entries are created the moment the *first* validator votes for a given source-chain event, keyed by `utx_key = sha256(source_chain:tx_hash:log_index)` [2](#0-1) , and removed only once every variant for that key reaches a terminal ballot status [6](#0-5) .
- There is no cap on the number of concurrent, not-yet-finalized inbound events tracked in `PendingInbounds`.
- Every call to `afterInboundBallotTerminal` does a full `Walk` of the collection plus a nested scan of each entry's `Variants` slice to find the one matching `ballotID` [7](#0-6) , i.e. O(total pending entries × variants per entry) work executed **inside consensus-critical message processing**, once per finalizing/expiring ballot.
- An unprivileged attacker who controls a source chain (e.g. sends a large volume of small-value deposits/messages to the Push Chain gateway on that chain in a short window, all with distinct tx hashes/log indices) can inflate `PendingInbounds` to a large size before any of the events reach ballot quorum. Once ballots for these (or any other unrelated inbound) events begin finalizing, each finalization/expiry event pays the full linear-scan cost, and the cost compounds as more events are outstanding simultaneously.

This mirrors the `addPool` bug class: an attacker-influenced, unbounded collection that core state-machine logic (`swapGLPout`/`recoverTreasuryTokensFromGLP` there; ballot finalization here) must fully iterate, eventually threatening to exceed acceptable per-block computation and stall processing of inbound votes/finalizations chain-wide.

### Impact Explanation
If the pending set grows large enough (sustained by cheap deposit spam on any enabled external chain, requiring no protocol privilege), the per-finalization cost of `afterInboundBallotTerminal` grows unboundedly, degrading and potentially denial-of-servicing the inbound ballot finalization path for **all** users, not just the attacker's own transactions — a shared core-functionality DoS, matching the "denial of service ... reachable without privileged control" allowed-impact category.

### Likelihood Explanation
Moderate. No privileged access or malicious validator/relayer is required — only the ability to generate a large number of distinct, low-cost, valid deposit/message events on a supported external chain within a window before those events' ballots finalize (governed by `DefaultExpiryAfterBlocks` and validator vote latency) [8](#0-7) . This is bounded by external-chain gas costs, but is still fully within reach of an unprivileged attacker with modest capital, unlike the original `addPool` bug which required a malicious/erring admin.

### Recommendation
Bound `PendingInbounds` growth (e.g. cap outstanding entries per chain, or evict/refuse new votes once a size threshold is hit) and/or replace the `Walk`-based ballot-ID lookup in `afterInboundBallotTerminal` with a direct indexed lookup (e.g. store a `ballotID -> utxKey` secondary index) so the terminal hook is O(1) instead of O(n) regardless of how large `PendingInbounds` becomes.

### Proof of Concept
1. Attacker submits N distinct low-value deposit/message transactions on an enabled external source chain within a short window, each producing a unique `(source_chain, tx_hash, log_index)`.
2. Honest validators observe and vote via `MsgVoteInbound`; each unique payload creates a new `PendingInboundEntry`/variant in `PendingInbounds` before any of them reach quorum [2](#0-1) .
3. As soon as any one ballot (this batch or an unrelated pre-existing one) reaches its vote threshold or expires, `afterInboundBallotTerminal` performs a `Walk` over the now-large `PendingInbounds` collection [7](#0-6) , with cost scaling linearly with N; repeated finalizations while N stays large impose sustained additional computation on every node processing inbound votes.

```go
func (k Keeper) MarkBallotFinalized(ctx context.Context, id string, status types.BallotStatus) error {
	if status != types.BallotStatus_BALLOT_STATUS_PASSED && status != types.BallotStatus_BALLOT_STATUS_REJECTED {
		return fmt.Errorf("invalid finalization status: %v", status)
	}

	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as finalized",
		"ballot_id", id,
		"final_status", status.String(),
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.FinalizedBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = status
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, status)
	return nil
```

```go
// CheckIfFinalizingVote inspects whether the just-cast vote pushes the ballot
// over its threshold and, if so, drives the finalization through
// MarkBallotFinalized — the single canonical write path for terminal status
// transitions, which applies CEI-style ordering on the secondary indexes.
func (k Keeper) CheckIfFinalizingVote(ctx context.Context, b types.Ballot) (types.Ballot, bool, error) {
	ballot, isFinalizing := b.IsFinalizingVote()
	if !isFinalizing {
		return b, false, nil
	}

	k.Logger().Debug("ballot reached finalization threshold",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)

	if err := k.MarkBallotFinalized(ctx, ballot.Id, ballot.Status); err != nil {
		return ballot, false, errors.Wrap(err, "failed updating finalized ballot")
	}

	k.Logger().Debug("ballot finalized",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)
	return ballot, true, nil
}
```
