### Title
`TransactionOutput::ensure_match_transaction_info` omits checkpoint-hash validation, allowing replay-verification tools to accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single routine used by both `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` to authenticate that a freshly re-executed `TransactionOutput` matches the historically committed `TransactionInfo` for a given version. It checks status, gas, the write-set hash (`state_change_hash`), and the event root hash, but — by the code's own admitted `TODO(trading-native)` comment — it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the locally computed state root.

### Finding Description [1](#0-0) 

The function validates only `status`, `gas_used`, `write_set_hash` (against `txn_info.state_change_hash()`), and `event_root_hash`. It ends with: [2](#0-1) 

This comment explicitly states the state/hot-state checkpoint hash and `position_state_checkpoint_hash` — the fields that summarize the actual Sparse-Merkle-Tree state root at a checkpoint version — are never cross-checked against what the replayed execution produced. This is structurally analogous to the reported `c-kzg-4844` bug: a batch/aggregate verification routine that is supposed to bind *all* relevant committed values into its pass/fail decision, but silently drops some of them from the check, letting an invalid value slip through undetected while unrelated fields validate correctly.

Both consumers rely on this function as their sole per-transaction correctness gate: [3](#0-2) 

The replay verifier only flags a failure when `ensure_match_transaction_info` returns an `Err`; since checkpoint-hash mismatches are never inspected, a checkpoint transaction whose freshly-computed state root differs from the stored `TransactionInfo.state_checkpoint_hash` (or `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) will pass verification silently.

### Impact Explanation
This breaks a proof/storage invariant explicitly called out in scope: "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" and "Authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object." `replay_on_archive` (`db-tool replay-verify`) and the Aptos debugger are the primary tools operators and auditors use to confirm that an archived/backed-up ledger's committed data actually matches independent re-execution by the VM. Because the checkpoint-hash fields (which represent the actual global state Merkle root, not just the write-set hash) are excluded from comparison, these tools can report a "successful" replay even though the state root that would be used for subsequent state proofs, restore, and light-client verification has silently diverged from the correct VM result. This is a hard-fork-class divergence detection gap: if execution semantics ever change (intentionally or via a bug) such that the write set matches but the derived state root differs, this is precisely the class of regression these verification tools exist to catch, and they will not catch it.

The severity is tempered by two caveats I could not fully resolve given available tool budget:
1. The comment ties this gap to enabling a not-yet-active feature flag, `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (referenced in `types/src/on_chain_config/aptos_features.rs` and `storage/aptosdb/src/db/aptosdb_writer.rs`), suggesting the authors are aware this needs to be fixed before that feature ships, and that today `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` may not yet be load-bearing in the current mainnet configuration.
2. The consensus/commit-time path (`aptosdb_writer.rs`) is a separate code path from this replay/debugger verification helper; I was not able to confirm within the remaining budget whether the writer itself independently re-derives and checks the state-checkpoint hash at commit time (which would mean this gap only affects offline replay-verification tooling, not consensus safety itself).

### Likelihood Explanation
No attacker action or privilege is required — this is a pure verification-logic omission that will silently mask any accidental or malicious VM/state-computation divergence at every checkpoint transaction, every time these tools are run, as long as write-set and event hashes still match. Given the explicit acknowledging `TODO` comment in the code, this is a confirmed, already-identified gap.

### Recommendation
In `ensure_match_transaction_info`, compute the actual state checkpoint hash (and hot-state / position-state checkpoint hash, when applicable) resulting from applying `self.write_set()` to the pre-state, and assert it equals `txn_info.state_checkpoint_hash()` (and the corresponding V1 fields) whenever those fields are `Some`, before returning `Ok(())`.

### Proof of Concept
Not independently exploitable via a crafted network message (this is a local-tooling verification gap, not a consensus-accepted forgery), so no PoC is provided beyond code inspection: any replay where VM execution changes the resulting state root while preserving write-set bytes, event bytes, gas, and status (e.g., a bug in how the SMT root or hot-state root is derived from an unchanged write set) will pass `ensure_match_transaction_info` and thus `replay_on_archive`/`aptos-debugger` verification undetected, per the code paths cited above.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
