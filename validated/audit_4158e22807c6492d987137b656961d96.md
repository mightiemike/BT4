## Finding: `TransactionOutput::ensure_match_transaction_info` silently skips checkpoint-hash verification

### Title
Replay/backup-verification accepts a divergent committed state root because `ensure_match_transaction_info` never checks the state-checkpoint hashes - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-comparison routine used by replay-verify and chunk-replay tooling to confirm that a freshly re-executed `TransactionOutput` matches the `TransactionInfo` recorded/committed in the ledger (and proven by an accumulator/ledger-info signature). It checks status, gas, write-set hash, event-root hash, and transaction hash, but it explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that commit to the JMT/state-summary root produced by execution. This is called directly by the archive replay-verify tool.

### Finding Description
The function's own comment documents the gap: [1](#0-0) 

Specifically, after validating status, gas, write-set hash, and event-root hash, it returns `Ok(())` without ever comparing `self`'s (or the caller-computed) state/hot-state/position-state checkpoint hash to `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`: [2](#0-1) 

This is invoked as the sole per-transaction correctness check in the standalone replay/backup-verify tool `storage/db-tool/src/replay_on_archive.rs`, which re-executes transactions read from a backup and calls `ensure_match_transaction_info` on the freshly computed `TransactionOutput` against `expected_txn_infos` pulled from the archive: [3](#0-2) 

It is also referenced from `execution/executor/src/chunk_executor/mod.rs` and `aptos-move/cli/src/commands.rs` as part of chunk/replayer verification paths.

The state-checkpoint hash is the field that binds a `TransactionInfo` to the resulting JMT/state-summary root produced by execution (the analogous field to the accumulator root in other proof paths, e.g. `types/src/proof/definition.rs` `AccumulatorProof::verify` and `TransactionOutputListWithProof::verify`, both of which fully validate every committed field including root hashes). By contrast, `ensure_match_transaction_info` omits the corresponding check for the checkpoint hash entirely, even though this hash is present on both `self` (the recomputed output, when `transaction_info_v1`/hot-state/position-state hashes are computed, see `execution/executor/src/workflow/do_ledger_update.rs::assemble_transaction_infos`) and on `txn_info` (the archived/authenticated value).

### Impact Explanation
Because `ensure_match_transaction_info` is the terminal correctness gate for backup/archive replay-verify, a state-root divergence introduced anywhere in execution, restore, or storage-commit logic (e.g. a bug in JMT construction, hot-state promotion, or position-state summary assembly) would produce a `TransactionOutput`/state root that differs from the one recorded on-chain, yet this tool would report the replay as successful. This directly matches the "Committed state that differs from the correct VM result... accepted as valid" and "Authenticated ... output bound to the wrong version, object, or proof context" categories: the archived, signature-backed `TransactionInfo.state_checkpoint_hash` is supposed to be the authenticated commitment to state, and this verifier explicitly bypasses re-deriving/confirming it.

### Likelihood Explanation
The gap is intentionally called out in-code as a TODO ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), and `compute_trading_native_state_roots` is a currently-gated onchain config feature flag (`types/src/on_chain_config/aptos_features.rs`, `types/src/block_executor/config.rs`). This indicates the maintainers are aware of the incompleteness and it is pending activation alongside that feature, which lowers confidence that this is an as-yet-unknown, immediately exploitable defect versus known WIP scaffolding for a not-yet-enabled feature. It does not affect core consensus-time commit validation (which is enforced elsewhere via the accumulator/ledger-info signature path), only the standalone `db-tool` replay-verify and CLI verification utilities.

### Recommendation
In `TransactionOutput::ensure_match_transaction_info` (`types/src/transaction/mod.rs`), add explicit `ensure!` checks comparing the recomputed state checkpoint hash(es) against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` before returning `Ok(())`, gated appropriately so the check activates alongside `compute_trading_native_state_roots`, rather than leaving replay-verify blind to this field indefinitely.

### Proof of Concept
Not applicable as a runnable exploit — this is a code-review-confirmed logic gap: `types/src/transaction/mod.rs` lines 2196-2204 show the missing comparisons, and `storage/db-tool/src/replay_on_archive.rs` lines 392-397 show the only integrity gate invoked in the replay-verify tool relying on that incomplete function.

---
Caveat: this finding is self-acknowledged as a pending TODO in the code tied to an unreleased feature flag (`compute_trading_native_state_roots`), so it may already be tracked internally rather than being a novel unprivileged mainnet exploit; I'm flagging it because it is the strongest local, provable proof-integrity gap I found matching the requested analog (validating an insufficient/wrong subset of fields rather than the ones that actually matter), consistent with the CVX-style "checked something, but not what actually needed checking" bug class.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
