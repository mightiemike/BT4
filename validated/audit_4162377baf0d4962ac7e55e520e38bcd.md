### Title
TVM shielded-pool precompiled contracts trust caller-supplied Merkle tree state (`frontier`/`leafCount`) without validating against any persisted root history - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`VerifyMintProof`, `VerifyTransferProof`, and `VerifyBurnProof` are TVM precompiled contracts used by shielded TRC20 (ShieldedTRC20.sol-style) contracts to validate zk-SNARK spend/output proofs. Unlike the native `ShieldedTransferActuator`, which cross-checks the proof's `anchor` against a persisted, chain-maintained root history via `MerkleContainer.merkleRootExist()`, these precompiles never verify that the caller-supplied Merkle tree state (`frontier`, `leafCount`, and the derived `anchor`) corresponds to any real, previously-committed state of the shielded pool. This is the same class of bug as the Footium `changeMaxGenerationId` finding: the low-level cryptographic verification (zk-SNARK / Merkle proof math) is sound, but the caller-supplied "generation" parameter that scopes what the proof is valid against is never independently validated by the verifying component itself.

### Finding Description
In the native shielded-transfer path, `ShieldedTransferActuator.validate()` explicitly enforces that any spend's anchor is a real, previously recorded Merkle root: [1](#0-0) 

This is backed by `MerkleContainer`, which persists Merkle tree roots keyed by content, giving a canonical, chain-verifiable history of what "current" or "past" state is legitimate. See usage of `MerkleContainer`/`getMerkleTreeStore` across `Manager.java` and `ChainBaseManager.java` and tests like `MerkleContainerTest.java`.

In contrast, the TVM precompiled contracts for shielded TRC20 (used by smart contracts calling into the shielded pool via the TVM) accept `frontier` and `leafCount` directly from the calldata supplied by whatever contract invokes them, and only check internal zk proof math and per-call duplicate nullifier/commitment sets — never against any global, persisted root history: [2](#0-1) [3](#0-2) [4](#0-3) 

The `anchor` used inside `VerifyTransferProof`/`VerifyBurnProof` is only checked for internal cryptographic consistency (`librustzcashSaplingCheckSpendNew`, `FinalCheck`), never against `MerkleContainer` or any equivalent state store: [5](#0-4) 

The precompiles are wired into the TVM dispatch table and reachable by any contract call once `allowShieldedTRC20Transaction()` is enabled: [6](#0-5) 

Effectively, the entire notion of "what is the current/legitimate tree generation" for the TVM shielded-pool flow is delegated to whatever Solidity contract calls these precompiles and how it manages its own `frontier`/`leafCount` storage — exactly analogous to how `changeMaxGenerationId` in the Footium report allowed a merkle proof to validate against stale generation/season data because the verification primitive itself didn't scope the check to the "current" generation.

### Impact Explanation
If a shielded-pool wrapper contract (or any other contract with access to these precompile addresses) can be made to pass a stale or attacker-influenced `frontier`/`leafCount` (e.g., due to a bug/reentrancy/upgrade in the wrapper contract's storage handling, or if multiple contracts share/reuse tree state), the precompile will happily accept and process mint/transfer/burn proofs against that stale state, since there is no independent, chain-level cross-check of "is this really the current committed tree." This can lead to note-commitment/leaf-insertion corruption in the shielded pool's accounting (double insertion, root collisions, inconsistent balances) — an asset/accounting corruption class impact within the TVM execution and precompiled-contract layer.

### Likelihood Explanation
Exploitability depends on the correctness of the calling Solidity wrapper contract's own state management, since the precompile trusts whatever `frontier`/`leafCount` is passed in calldata. This is a design characteristic shared with the original Sapling/Zcash-style shielded pool architecture (state kept in the calling contract, not enforced by the VM), so likelihood is moderate and contingent on a flaw or inconsistency in the wrapper contract rather than a direct, self-contained java-tron RPC exploit. I could not verify within this index whether TRON's reference `ShieldedTRC20.sol` contract enforces additional guardrails (e.g., strictly incrementing `leafCount`/single-writer enforcement) that would mitigate this at the Solidity layer, since that contract's source isn't part of this repository's index.

### Recommendation
Add a chain-level cross-check in `VerifyMintProof`/`VerifyTransferProof`/`VerifyBurnProof` (or in a wrapping actuator/precompile pre-check) that validates the supplied `frontier`/`leafCount`/`anchor` against a persisted, contract-scoped tree-state record analogous to `MerkleContainer.merkleRootExist()`, rather than trusting values passed directly in calldata by the invoking contract.
