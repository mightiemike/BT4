### Title
Declare-transaction griefing via cross-account class-hash front-running - (File: crates/apollo_mempool/src/mempool.rs)

### Summary
The mempool's declare-delay griefing protection only guards against a griefer using the *same* `(address, nonce)` pair to front-run/replace a pending declare. It does not protect against a griefer submitting an independent `DeclareTransaction` from a *different* account with the *same* `class_hash` as a pending, legitimately paying declarer, causing the victim's transaction to be executed second in the same block and revert as "already declared," permanently wasting the victim's fee — the sequencer analog of the VeloGovernor "front-run with identical settings, then invalidate" griefing pattern.

### Finding Description
Declare transactions are asynchronously delayed in `Mempool::add_tx` for `declare_delay` seconds via `self.delayed_declares.push_back(...)`, specifically to give the sequencer time to detect and resolve conflicts before proposing them. [2](#0-1)  The only duplication/front-run check performed, `validate_no_delayed_declare_front_run`, keys exclusively on `tx_reference.address` and `tx_reference.nonce`: [1](#0-0) 

There is no equivalent check keyed on `class_hash` anywhere in `mempool.rs` (confirmed absent via search), meaning a griefer can observe an honest declarer's pending transaction (which is public in gossip/mempool visibility) and submit their own, cheaper `DeclareTransaction` from an unrelated, disposable account referencing the *identical* `class_hash`. Both transactions are independently valid from the mempool's perspective (different `(address, nonce)` pairs) and can be admitted and queued.

At execution time, `try_declare` in the blockifier enforces global class-hash uniqueness: the first execution in the block succeeds and declares the class; the second reverts with `TransactionExecutionError::DeclareTransactionError { class_hash }` because the class is "already declared": [3](#0-2) 

Because the block-builder/priority-queue ordering is driven by tip/fee rather than by which declarer submitted first, the griefer can pay a minimal fee (still enough to be included before the victim, e.g. by controlling nonce ordering or submission timing) so that their throwaway declare consumes the "declare-once" slot for that class hash, and the victim's legitimate, already-fee-paying declare transaction executes afterward and reverts.

### Impact Explanation
The victim's declare transaction, despite being valid, fully paying its fee, and having successfully passed mempool validation, is executed and fails on-chain due to the pre-existing class hash, per the `try_declare` logic. [4](#0-3)  Declare transaction fees are charged even upon a failing (reverted) execution outside of the specific bootstrap edge case, so the victim's account nonce is consumed and fee is spent for no useful state change — a concrete, repeatable loss of funds inflicted by an unprivileged third party with no special access, purely by racing/observing the mempool and submitting a cheap adversarial transaction. This matches the "Medium" classification pattern of the reference report: griefing that costs the victim funds/gas without directly compromising consensus safety.

### Likelihood Explanation
Any unprivileged party monitoring the public mempool/gossip network for pending `Declare` transactions can extract the `class_hash` field (it is not secret; it must be public for validation) and submit a copy declare from a fresh account. The `declare_delay` window itself (default `Duration::from_secs(1)` in test config, `20` seconds in production configs) actually widens the attack window by holding the victim's declare visibly in the `delayed_declares` queue longer before it is released to the pool/priority queue. [5](#0-4) [6](#0-5)  No collusion with sequencer operators, stakers, or provers is required — this is reachable purely through submitting standard `starknet_addDeclareTransaction` calls.

### Recommendation
Extend mempool-level duplicate detection to also key on `class_hash` for `Declare` transactions, independent of sender address/nonce: when a `DeclareTransaction` referencing a `class_hash` is already present in `delayed_declares`/`tx_pool` from a different account, either (a) reject/delay the newer duplicate-`class_hash` declare with a specific `MempoolError` (mirroring `DuplicateNonce`), or (b) prioritize the earliest-seen declare for a given `class_hash` regardless of fee/tip so a griefer cannot use a low-fee decoy to jump the class-hash "slot." Additionally, consider not charging/consuming nonce+fee for declare transactions that fail purely due to `DeclareTransactionError` (already-declared), so that even if the race occurs, the honest declarer is not financially penalized.

### Proof of Concept
1. Account A submits `DeclareTransaction` for `class_hash = C` with nonce `nA`, paying the network's expected declare fee; it is admitted to `delayed_declares` keyed on `(A, nA)`.
2. A griefer observes this pending transaction (via public mempool visibility) and, from a fresh account B (any nonce `nB`), submits its own independent `DeclareTransaction` for the same `class_hash = C`, with a lower fee/tip. `validate_no_delayed_declare_front_run` only checks `(address, nonce)` collisions and does not detect the shared `class_hash`, so B's transaction is accepted. [7](#0-6) 
3. Once both declare delays elapse, both transactions are proposed; if B's is ordered/executed first in the block, `try_declare` succeeds for B and writes `class_hash -> compiled_class_hash` into state. [8](#0-7) 
4. A's transaction then executes and hits the `Ok(_)` branch of `try_declare`, returning `TransactionExecutionError::DeclareTransactionError { class_hash: C }`, reverting A's transaction while A's fee is charged and nonce is incremented. [9](#0-8)

    /// Validates that the given transaction does not front run a delayed declare. This means in
    /// particular that no fee escalation can occur to a declare that is being delayed.
    fn validate_no_delayed_declare_front_run(
        &self,
        tx_reference: TransactionReference,
    ) -> MempoolResult<()> {
        if self.delayed_declares.contains(tx_reference.address, tx_reference.nonce) {
            return Err(MempoolError::DuplicateNonce {
                address: tx_reference.address,
                nonce: tx_reference.nonce,
            });
        }
        Ok(())
    }
