### Title
Unbounded, contract-controlled array length in `read_felt_array` allows a Denial-of-Service via oversized allocation in deprecated (Cairo 0) syscalls - (File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs)

### Summary
The Cairo-0 ("deprecated") syscall request parser reads an array length felt directly from Cairo VM memory and converts it to a `usize` without validating it against the amount of data actually available before attempting to materialize the array, mirroring the gmrtd `ReadFile` issue where an unbounded TLV length triggered excessive allocation/iteration work from untrusted input.

### Finding Description
`read_felt_array` in the deprecated syscall hint processor reads the array size as an arbitrary felt supplied by the executing (attacker/deployer-controlled) Cairo 0 bytecode, converts it to `usize`, and immediately calls `felt_range_from_ptr` to materialize a `Vec<Felt>` of that size: [1](#0-0) 

Unlike the modern (non-deprecated) syscall counterpart, whose `read_felt_array` derives the array length from `array_data_end_ptr - array_data_start_ptr` — two already-materialized pointers bounded by real Sierra-array construction — [2](#0-1) 

the deprecated variant trusts a raw length felt written by the Cairo 0 program itself (e.g. `keys_len`/`data_len` for `EmitEvent`, `payload_size` for `SendMessageToL1`, `calldata_len` for `CallContract`/`LibraryCall`/`Deploy`): [3](#0-2) [4](#0-3) 

Because a Cairo 0 contract's own bytecode writes this length into a memory cell prior to invoking the syscall (there is no VM-level guarantee that the pointed-to segment actually contains that many populated cells), a malicious contract can supply an arbitrarily large length value (bounded only by `usize::try_from(felt.to_biguint())`, i.e. up to ~2^64 on 64-bit hosts) for these fields. This flows into `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)`: [5](#0-4) 

This is the same class of vulnerability as GHSA-j49h-6577-5xwq: an untrusted, unbounded length value drives an allocation/iteration proportional to an attacker-chosen number before any content-based bound check is performed, unlike the sequencer's own hardened analogs elsewhere in the codebase (e.g. `CairoArray::try_from` explicitly validates the declared length against remaining data *before* allocating: `Vec::with_capacity(num_items)` is guarded by a check that `num_items <= num_remaining_felts`): [6](#0-5) 

I was not able to directly inspect the `cairo-vm` dependency's `get_integer_range` implementation (it lives outside this repository) to confirm whether it pre-allocates a `Vec` with the full requested capacity before validating memory presence, or whether it fails fast per-cell without a large up-front allocation. This is the key unresolved factual gap: if `get_integer_range` allocates a `Vec::with_capacity(size)` (or otherwise performs O(size) work) before discovering the first missing memory cell, then a single crafted Cairo 0 declare+invoke can force the sequencer to attempt a huge allocation (potential immediate abort/OOM) or to spend excessive CPU on a fast-failing loop, per transaction, at negligible gas cost, because the failure only manifests deep inside syscall parsing.

### Impact Explanation
If confirmed, an unprivileged transaction sender could deploy/declare and invoke a Cairo 0 contract that calls `EmitEvent`, `SendMessageToL1`, `CallContract`, `LibraryCall`, or `Deploy` with a crafted, huge `*_len`/`*_size` felt. Executing this transaction in the gateway/mempool validation or blockifier execution path would cause the sequencer process to attempt an oversized allocation or CPU-heavy loop while parsing the syscall request — potentially crashing the node process (denial of service) or causing severe resource consumption during block building/re-execution, which could stall block production (network unable to confirm new transactions) if not caught early by gas/step metering.

### Likelihood Explanation
Likelihood is moderate-to-uncertain because: (1) Cairo 0 contracts are still declarable/deployable and their entry points (including `__validate__`/`__execute__`) reach these syscall handlers directly from a single submitted transaction, so the reachability bar is low; but (2) whether this actually causes a crash depends entirely on the unverified internal behavior of `cairo_vm::VirtualMachine::get_integer_range`, which may already fail cheaply on the first out-of-range access rather than pre-allocating. Existing internal precedent (`CairoArray::try_from`'s explicit pre-allocation guard) suggests the sequencer team is aware of and has fixed this exact bug pattern in at least one other code path, but the deprecated syscall path's `read_felt_array` was not given the same treatment.

### Recommendation
Add an explicit bound check in `read_felt_array` (deprecated_syscalls/hint_processor.rs) before calling `felt_range_from_ptr`: validate the parsed `array_size` against a sane upper bound (e.g. the transaction's calldata/segment size, or a versioned-constants-configured max array length) and reject with a syscall error if exceeded — mirroring the guard already used in `apollo_cairo_utils::CairoArray::try_from`. Additionally/alternatively, confirm and, if needed, patch `cairo-vm`'s `get_integer_range` to avoid unbounded up-front allocation for unverified ranges.

### Proof of Concept
Conceptual PoC (exact behavior contingent on `cairo-vm::get_integer_range` internals, which could not be verified from this repo):
1. Write a Cairo 0 contract whose `__execute__` invokes the `send_message_to_l1` syscall (or `emit_event`) passing a `payload_size` (or `keys_len`/`data_len`) felt equal to a very large value (e.g. `2**40`) while pointing `payload_ptr` at a small, real memory segment.
2. Declare and deploy this class, then submit an invoke transaction calling `__execute__`.
3. During execution, `SendMessageToL1Request::read` / `EmitEventRequest::read` call `read_felt_array`, which converts the felt to `usize` and calls `felt_range_from_ptr(vm, payload_ptr, huge_size)` → `vm.get_integer_range(ptr, huge_size)`.
4. If `get_integer_range` performs O(size) work or a large up-front allocation before detecting the missing memory, the sequencer node executing/validating this transaction experiences excessive CPU/memory usage or crashes, per [1](#0-0)  and [5](#0-4) .

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>

}

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}
