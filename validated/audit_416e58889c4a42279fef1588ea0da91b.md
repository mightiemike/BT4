### Title
Hardcoded static gas constants in the Wallet Contract's callback chain can cause `has_in_flight_tx` to never reset, permanently freezing an ETH-implicit account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (used by every ETH-implicit account, see NEP-518) attaches **fixed, compile-time-hardcoded** gas budgets to the promises it schedules for its own callbacks, instead of relying on remaining/weighted gas. This is directly analogous to Solidity's `transfer()`/`send()` fixed 2300-gas stipend: if the actual runtime cost of executing the callback changes (e.g. due to a future protocol gas-cost parameter change), the hardcoded budget can become insufficient, causing the callback to fail with an out-of-gas error every time.

### Finding Description
The contract defines several fixed `Gas` constants used with `.with_static_gas(...)`: [1](#0-0) 

These are used, for example, to schedule the mandatory `rlp_execute_callback` after every action the wallet performs: [2](#0-1) 

`rlp_execute_callback` is the only place that resets the in-flight flag to `false`: [3](#0-2) 

`rlp_execute` refuses to process any new transaction while `has_in_flight_tx` is `true`, and this flag is set to `true` right before every promise is returned: [4](#0-3) 

On NEAR, a `FunctionCall` receipt that exhausts its `prepaid_gas` fails entirely and none of its state mutations are committed (the whole execution is rolled back), regardless of how early in the function the mutation occurred. Because `RLP_EXECUTE_CALLBACK_GAS` (and the derived `ADDRESS_CHECK_CALLBACK_GAS` / `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) are fixed `Gas::from_tgas(5)`-based constants baked into the compiled contract, they encode an assumption about the *current* cost of executing WASM, host functions, and action costs (e.g., `promise_batch_action_transfer`, `promise_result` deserialization, `function_call_base`/`function_call_byte` fees). These parameters are governed by `RuntimeConfig`/`RuntimeFeesConfig` and can be changed via a protocol upgrade. If such a change increases the effective cost of what the callback does above 5 Tgas, `rlp_execute_callback` (or the address/storage-balance callbacks that eventually call it) will always fail with `GasExceeded`, and `self.has_in_flight_tx = false` will never be durably committed.

### Impact Explanation
Since the Wallet Contract is deployed as a global contract for every ETH-implicit account, and per protocol design an ETH-implicit account "can only be used by calling the methods of the Wallet Contract. It cannot be deleted, nor can a full access key be added" (see `docs/DataStructures/Account.md`), there is no alternate recovery path once `has_in_flight_tx` is stuck at `true`. Every subsequent `rlp_execute` call — including simple transfers out of the account — will be rejected with "transaction already in progress," permanently freezing all funds held by that account. This matches the accepted impact category of permanently frozen funds triggered purely by a normal user/relayer transaction plus a protocol-level gas-cost parameter change (not requiring any malicious actor). [5](#0-4) 

### Likelihood Explanation
This requires a protocol-level change to gas cost parameters (host function costs, action costs, or WASM opcode costs) that increases the true cost of the callback logic above the hardcoded 5 Tgas budgets. Such runtime-config/gas-parameter updates do occur periodically as part of protocol upgrades (this is exactly the scenario EIP-1884 represents for Ethereum's `SLOAD` cost). Because the Wallet Contract's gas constants are fixed at compile time rather than derived from current config or a gas-weight-based allocation, any future increase silently breaks every wallet contract instance already deployed on-chain, with no way to redeploy per-account gas overrides (global contract code is shared).

### Recommendation
Avoid hardcoding fixed `Gas` amounts for the mandatory callback chain. Instead:
- Use `GasWeight`-based allocation (as already supported by `promise_batch_action_function_call_weight` / `PromiseOrValue` gas-weight mechanisms) so the callback receives a proportion of whatever gas remains, rather than an absolute fixed amount.
- Alternatively, add a safety margin well beyond current cost estimates, and/or make the constants configurable/upgradable independent of the compiled global contract code, so a future protocol gas-cost change cannot strand `has_in_flight_tx = true` permanently.
- Ensure `has_in_flight_tx` can be reset through some out-of-band/administrative recovery path (or make the flag reset unconditionally in a low-gas-cost `#[private]` panic-hook/callback) so a stuck flag does not permanently disable the account.

### Proof of Concept
1. A protocol upgrade increases `RuntimeFeesConfig`/`ExtCosts` values relevant to promise-result handling, transfer actions, or WASM execution (a normal, permissionless-to-users protocol parameter change).
2. Any user submits a `rlp_execute` transaction to their ETH-implicit account that goes through a multi-hop path (e.g., `ERC20Transfer` or `EOABaseTokenTransfer` with `address_check`), which schedules `rlp_execute_callback`/`address_check_callback`/`nep_141_storage_balance_callback` with `.with_static_gas(RLP_EXECUTE_CALLBACK_GAS)` (5 Tgas) as seen at `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:178-188` and `:412-472`.
3. Because the new gas costs make execution of the callback body exceed 5 Tgas, the callback receipt fails with `FunctionCallError::HostError(GasExceeded)`, and none of its state changes (including `self.has_in_flight_tx = false` at line 280) are committed.
4. `has_in_flight_tx` remains permanently `true`. All future `rlp_execute` calls on that account are rejected at `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:97-105`, permanently freezing the account's funds since no full access key can ever be added to an ETH-implicit account.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
