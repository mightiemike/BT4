### Title
Integer truncation in `CalculateGasCost` unwrap of `LegacyDec` base fee zeroes out gas fees for UEA payload execution when base fee drops below 1 upc - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`CalculateGasCost` unwraps the feemarket's `LegacyDec` base fee back to a raw integer `upc` amount via a hard-coded integer division `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))`. The code comment asserts this is always safe because "the base fee is always a whole number of upc," but nothing in the reachable code path enforces that invariant. If the on-chain base fee (read from the standard Cosmos EVM feemarket module) is a fractional `LegacyDec` value strictly less than `1e18` (i.e., less than 1 upc), integer division truncates it to `0`, producing `effectiveGasPrice = 0` and therefore `gasCost = 0` for that transaction's entire gas usage. `DeductGasFeesFromReceipt` then short-circuits (`gasCost.Sign() <= 0 → return nil`) and skips fee deduction entirely — the user's UEA-originated payload execution runs for free while consuming real EVM gas paid for by nobody. This mirrors the reported bug class: floor-style integer division on a value that legitimately has fractional/sub-unit magnitude, silently truncating the amount owed to zero and letting the caller obtain execution for less than the correct price, repeatable indefinitely as long as the condition holds.

### Finding Description
`CalculateGasCost` in [1](#0-0)  takes the feemarket's base fee as `sdkmath.LegacyDec` and does:
```go
baseFeeBig := baseFee.BigInt()
baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
```
This treats the base fee's internal 18-decimal-precision `big.Int` representation as if it can only ever encode whole-upc amounts. That assumption is asserted only in a comment, not enforced by any validation in the reachable path. The base fee here comes from `k.feemarketKeeper.GetBaseFee(sdkCtx)` in [2](#0-1) , i.e. the standard Cosmos EVM feemarket's EIP-1559-style base fee, which is a `Dec` that can move by fractional amounts per block according to feemarket parameters (elasticity multiplier / base-fee change denominator) and is not guaranteed to always be a multiple of `1e18`.

If `baseFee < 1e18` (sub-1-upc), the truncating `Div` yields `effectiveGasPrice = 0`, so:
```go
gasCost := new(big.Int).Mul(effectiveGasPrice, gasUsedBig) // = 0
```
Back in `DeductGasFeesFromReceipt` ( [3](#0-2) ):
```go
gasCost, err := k.CalculateGasCost(...)
...
if gasCost.Sign() <= 0 {
    return nil
}
```
No fee is deducted and no burn occurs, even though `receipt.GasUsed` may be large (e.g. an expensive UEA-executed payload). This is invoked from every user-driven universal-payload execution path (`execute_payload.go`, `execute_inbound_gas_and_payload.go`, `execute_inbound_funds_and_payload.go`, `msg_execute_payload.go` per [4](#0-3) ), all of which are reachable by an ordinary unprivileged user submitting a `UniversalPayload` for execution through their UEA.

### Impact Explanation
This corrupts gas-fee accounting: real, attacker-directed EVM execution cost (paid for by the module burning `upc` from the user) is silently reduced to zero whenever the base fee is sub-1-upc. Repeated exploitation compounds protocol loss exactly like the reference finding — an attacker can drive or wait for the base fee to sit below 1 upc (which is the network's natural resting/floor state under low demand for many EIP-1559-style fee markets) and then submit gas-consuming universal payloads for free indefinitely, draining value from the protocol's gas-accounting invariant (protocol/validators effectively subsidize execution with no fee recovered). This falls under "corruption of ... gas fee accounting" explicitly listed as in-scope impact.

### Likelihood Explanation
Likelihood depends on whether the feemarket base fee can actually fall below `1e18` (1 upc) in practice — this requires confirming feemarket module parameters (base fee minimum floor, `MinGasPrice`, elasticity settings) at genesis/params level, which I was not able to fully verify in the indexed code (feemarket params configuration wasn't found in the scoped `x/` or `app/` files beyond references in ante handlers). If the feemarket module enforces a floor of `MinGasPrice` at exactly 1 upc or above at all times, this bug path would not be reachable. Given this uncertainty, likelihood should be treated as **moderate/unconfirmed** — it is a straightforward and clearly present truncation defect in scoped code (`x/uexecutor/keeper/fees.go`), but exploitability strictly depends on external/global feemarket parameter configuration that I could not fully confirm from the indexed context.

### Recommendation
Do not silently truncate the base fee. Either:
1. Round up (`ceil`) when unwrapping `LegacyDec` to raw `upc`, matching the pattern already used elsewhere in this codebase for min-gas-price fee computation (`fee.Ceil().RoundInt()` in [5](#0-4)  and [6](#0-5) ), or
2. Assert/enforce a floor invariant on the feemarket parameters (reject/clamp base fee below `1e18`) before calling `CalculateGasCost`, or
3. Perform the whole computation in `LegacyDec` and only convert to integer `upc` at the very end with `Ceil().RoundInt()`.

### Proof of Concept
1. Assume feemarket module allows base fee to be set/decay to a `LegacyDec` value less than `1e18` (e.g., `500000000000000000` = 0.5 upc), reachable through normal EIP-1559 base-fee decay under sustained low block utilization.
2. User submits a `UniversalPayload` execution via their UEA with `GasLimit` large enough to consume, say, 500,000 gas (`receipt.GasUsed = 500000`).
3. `DeductGasFeesFromReceipt` calls `CalculateGasCost(baseFee=0.5, ...)`:
   - `baseFeeBig = 500000000000000000`
   - `baseFeeBig.Div(baseFeeBig, 1e18)` → integer division truncates `0.5` down to `0`
   - `effectiveGasPrice = 0`
   - `gasCost = 0 * 500000 = 0`
4. `gasCost.Sign() <= 0` → `DeductGasFeesFromReceipt` returns `nil` without deducting or burning any `upc`.
5. The user's payload executes on-chain consuming 500,000 gas of real compute, but the protocol collects/burns 0 fee. Repeating this transaction whenever base fee sits below 1 upc lets the attacker execute unlimited free EVM computation via UEA payloads, compounding protocol loss over each execution — directly analogous to the referenced report's repeated-underpriced-buy pattern.
