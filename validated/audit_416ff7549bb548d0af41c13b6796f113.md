### Title
`Wallet.estimateEnergy` binary search allows unauthenticated attacker to trigger O(log(maxFeeLimit)) full VM executions per single RPC/HTTP/JSON-RPC call, causing multiplicative underpriced CPU cost - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.estimateEnergy` performs a doubling search followed by a binary search over the fee/energy range `[0, dps.getMaxFeeLimit()]`, invoking `cleanContextAndTriggerConstantContract` → `callConstantContract` → `VMActuator.execute` up to `~log2(maxFeeLimit)` times per single call, each wrapped in an inner retry loop (up to `estimateEnergyMaxRetry`) that re-runs the same expensive execution on `Program.OutOfTimeException`. An attacker submitting a contract that is deliberately slow can force many of these binary-search steps to hit the timeout boundary and be retried, multiplying CPU work per unauthenticated call with zero fee charged (constant calls are not broadcast/executed on-chain and are not charged).

### Finding Description
The reachable path is `RpcApiService.estimateEnergy` / `TronJsonRpcImpl.estimateEnergy` / `EstimateEnergyServlet.doPost` → `Wallet.estimateEnergy` [1](#0-0) [2](#0-1) , gated only by `vm.estimateEnergy=true` and `vm.supportConstant=true` [3](#0-2) , both of which are attacker-controllable node-config preconditions (not authentication).

Inside `estimateEnergy`, the algorithm runs an initial probe at `high = dps.getMaxFeeLimit()`, an optional doubling step, then a binary search loop `while (low + TRX_PRECISION < high)`, each iteration calling `cleanContextAndTriggerConstantContract` → `triggerConstantContract` → `callConstantContract` → `vmActuator.execute(context)` [4](#0-3) [5](#0-4) . Each of these steps is itself wrapped in an unbounded-looking `while (true)` retry loop that catches `Program.OutOfTimeException` and decrements `retry` (bounded by `estimateEnergyMaxRetry`), re-executing the identical VM run at the same fee limit on timeout [6](#0-5) . This means total VM executions per single `estimateEnergy` call is bounded by `O(log2(maxFeeLimit)) * (estimateEnergyMaxRetry + 1)` in the worst case, each execution running up to the per-execution CPU time limit before throwing `OutOfTimeException`.

Since `callConstantContract` runs via `VMActuator(true)` in "constant" mode, execution consumes no persisted fee/bandwidth/energy from any account, and the whole call is unauthenticated (any public RPC/HTTP/JSON-RPC caller). The rate limiters present (`GlobalRateLimiter`, per-endpoint QPS/`GlobalPreemptibleAdapter`) throttle request *count*, not per-request CPU cost [7](#0-6)  — they do not compensate for a single call that internally performs `O(log(maxFeeLimit) * retries)` full VM executions of an attacker-chosen contract, each potentially running to the CPU timeout before failing.

### Impact Explanation
A single unauthenticated `estimateEnergy` call can consume CPU time equal to `O(log2(maxFeeLimit))` full VM executions of an attacker-supplied contract — each execution can be made to run close to the CPU-time limit by crafting bytecode whose runtime straddles specific energy thresholds (so many binary-search midpoints individually trip `Program.OutOfTimeException`, each retried up to `estimateEnergyMaxRetry` times). This is a materially underpriced, repeatable CPU amplification relative to a normal `triggerConstantContract`/`triggerContract` call of the same contract, which performs only one VM execution. Repeated concurrent calls from a small number of IPs (bounded only by generic QPS limits, not cost-aware) can degrade full-node responsiveness for legitimate constant-call/estimate/RPC traffic — a resource-exhaustion / DoS-class impact, not fund theft or consensus divergence.

### Likelihood Explanation
Feasible: the endpoint is public, requires only `vm.estimateEnergy` and `vm.supportConstant` (both default-relevant configuration used by full/estimate-capable nodes), and needs only bytecode-level knowledge to make a contract intentionally slow near arbitrary energy thresholds (loops gated by comparison to `msg.value`/calldata parameters, as already demonstrated by the existing `testEstimateEnergyOutOfTime` test contract in the repo test suite) [8](#0-7) . No fee/energy is charged for constant calls, and the existing rate limiters are QPS/concurrency-based, not proportional to the CPU cost incurred by an individual request, so repeated invocation is straightforward for an unprivileged caller.

### Recommendation
- Cap the total number of VM executions (including retries) performed within a single `estimateEnergy` call regardless of loop position (a single global budget across doubling + binary search + inner retries, not merely a per-step retry counter).
- Add a wall-clock/CPU budget for the entire `estimateEnergy` request (not per VM execution) and abort with an error once exceeded.
- Consider adding a dedicated, cost-aware rate limiter (e.g., `GlobalPreemptibleAdapter` with a low permit count, or CPU-time based backpressure) specifically for `EstimateEnergyServlet` / the gRPC `estimateEnergy` method and the JSON-RPC equivalent, since generic QPS limiters do not account for the amplification inherent in this specific endpoint.
- Optionally shrink the effective search domain from `dps.getMaxFeeLimit()` using a smaller, configurable initial upper bound for untrusted callers.

### Proof of Concept
Java integration test plan (extending existing `WalletTest.testEstimateEnergyOutOfTime`):
1. Deploy a contract whose execution time is a step function of an input threshold value comparable to energy amounts derivable from the fee limit passed into `triggerConstantContract` (e.g., loop count derived from `msg.value`/calldata, similar to the bytecode already used in `testEstimateEnergyOutOfTime`) [9](#0-8) .
2. Instrument/spy `VMActuator.execute` (or wrap `Wallet.callConstantContract`) to count invocations during a single `wallet.estimateEnergy(...)` call.
3. Assert that the invocation count is materially greater than 1 (i.e., `> log2(maxFeeLimit)` in the pathological case, verified against a control call using `wallet.triggerConstantContract(...)` on the same contract which should invoke `VMActuator.execute` exactly once).
4. Measure wall-clock CPU time consumed by the `estimateEnergy` call vs. a `triggerConstantContract` call of the identical contract+parameters and assert the ratio scales with `estimateEnergyMaxRetry` and the number of binary-search steps, demonstrating the multiplicative, underpriced CPU cost.
