### Title
Wallet Contract silently drops the external caller's attached deposit on registrar/storage-check failure paths - permanent fund loss ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (`near-wallet-contract`, an eth-implicit account contract that emulates Ethereum transactions on NEAR) tracks an external caller's attached deposit via `CallerDeposit` so it can be refunded if the emulated action ultimately fails. This refund is correctly performed in `rlp_execute_callback`, but two other failure branches in the same call chain — `address_check_callback` and `nep_141_storage_balance_callback` — simply return a failure `ExecuteResponse` and drop the `caller_deposit` parameter without ever generating a refund `Promise`. This is directly analogous to the reported bug class: a payment/value-receiving path that lacks the "receive/refund" handler on certain code paths, causing attached native tokens to become permanently stuck.

### Finding Description
`rlp_execute` is a `#[payable]` entrypoint [1](#0-0) . When called by an external (non-owner) relayer/caller with an attached deposit, `CallerDeposit::new` records the caller's account and yoctoNEAR amount specifically "to refund the caller's deposit if the cross-contract call fails" [2](#0-1) .

For most transaction kinds this deposit is threaded through to `rlp_execute_callback`, which does refund the caller when the final promise fails: [3](#0-2) 

However, for `EOABaseTokenTransfer` with an `address_check`, and for `ERC20Transfer`, an *intermediate* cross-contract call (address-registrar lookup, or NEP-141 `storage_balance_of`) is made first. If that intermediate call itself fails, the corresponding callback returns a failure response without ever creating a refund promise for `caller_deposit`:

- `address_check_callback`, on `PromiseResult::Failed` from the address registrar lookup: returns failure and drops `caller_deposit` [4](#0-3) .
- Same function, "Invalid target" branch (target address resolves to an existing named account and the call was made by an external relayer, not the wallet owner): again returns failure and drops `caller_deposit` [5](#0-4) .
- `nep_141_storage_balance_callback`, on `PromiseResult::Failed` from `storage_balance_of`: returns failure and drops `caller_deposit` [6](#0-5) .

Because NEAR credits an attached deposit to the receiving account's balance automatically as part of the `FunctionCall`/`Transfer` action processing (unlike EVM, where a missing `receive()` causes an outright revert and thus an automatic refund of the whole transaction), the deposit from `rlp_execute` is already part of the Wallet Contract's balance the moment the method starts executing. If none of the subsequent code paths issues a `Transfer` promise back to the caller, that NEAR remains permanently in the wallet contract's balance with no accounting or means for the original caller to reclaim it.

### Impact Explanation
Any external, unprivileged relayer/caller who calls `rlp_execute` with an attached deposit on behalf of a wallet-contract owner (e.g., to cover the emulated ERC-20 transfer fee or a base-token transfer with address verification, as used by the `EthEmulationKind::EOABaseTokenTransfer`/`ERC20Transfer` fee-forwarding logic [7](#0-6) ) permanently loses that deposit whenever:
- the address-registrar lookup call fails (e.g., registrar contract runs out of gas, is temporarily broken, or the relayer targets an existing named account), or
- the NEP-141 `storage_balance_of` call fails (e.g., a non-standard or malicious/paused token contract).

This is concrete, permanently frozen/lost funds for a legitimate transaction submitter, triggered without any malicious behavior by validators or other network participants — a single relayer's call combined with an unresponsive/failing downstream contract is sufficient.

### Likelihood Explanation
This is reachable by any relayer submitting an otherwise valid, unprivileged `rlp_execute` transaction; the triggering condition (an intermediate cross-contract call failing) is a normal, easily-inducible failure mode (gas exhaustion on the registrar/token contract, a paused or reverting NEP-141 token, or simply targeting an existing named account as `target`). No special privileges, timing races, or malicious validators are required.

### Recommendation
In `address_check_callback` (both the `PromiseResult::Failed` branch and the "Invalid target" branch) and in `nep_141_storage_balance_callback`'s `PromiseResult::Failed` branch, mirror the refund logic already present in `rlp_execute_callback`: if `caller_deposit` is `Some`, issue `env::promise_batch_create` + `env::promise_batch_action_transfer` back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the failure `ExecuteResponse`.

### Proof of Concept
1. An external relayer account `R` (not the wallet owner) calls `rlp_execute(target, tx_bytes_b64)` attaching a deposit `D`, where the decoded transaction is an `ERC20Transfer` with a non-zero relayer `fee`, so `CallerDeposit::new` records `{account_id: R, yocto_near: D}` [8](#0-7) .
2. `inner_rlp_execute` schedules a `storage_balance_of` call on the token contract followed by `nep_141_storage_balance_callback` [9](#0-8) .
3. The token contract's `storage_balance_of` call fails (e.g., token is paused, malformed, or runs out of allotted gas).
4. `nep_141_storage_balance_callback` observes `PromiseResult::Failed` and returns `ExecuteResponse { success: false, ... }` without creating any refund promise for `caller_deposit` [6](#0-5) .
5. Deposit `D`, already credited to the Wallet Contract account's balance as part of step 1's `FunctionCall` action, is never returned to `R` and remains stuck in the wallet contract indefinitely — a permanent, unrecoverable loss of `D` for the relayer.

```rust
/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
```
