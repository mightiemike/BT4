### Title
JSON-RPC response ID mismatch when attacker-supplied `req.ID` contains the internal owner/request-ID separator, triggered via `errorResponse` before owner-prefixing occurs - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
The gateway vault handler's `errorResponse` unconditionally strips everything up to and including `vaulttypes.RequestIDSeparator` from `req.ID`, assuming that separator only ever appears as part of the internal `owner::originalID` prefix stamped by `GatewayVaultRequestProcessor.authorizeAndStamp`. However, for error paths that occur *before* that stamping happens (e.g. `InvalidParamsError` from a failed param/validation check), `req.ID` is still exactly the untrusted, client-supplied value. If the attacker deliberately embeds the separator sequence in their own `req.ID`, `errorResponse` truncates the ID incorrectly, returning a JSON-RPC response whose `id` does not equal the original request `id`.

### Finding Description
In `handler.HandleJSONRPCUserMessage` (core/services/gateway/handlers/vault/handler.go:436-443), the request is passed to `h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)`. Inside `GatewayVaultRequestProcessor.ProcessRequest` → `processCreateSecretsRequest` (core/capabilities/vault/gateway_vault_request_processor.go:88-120), validation (`p.validator.ValidateCreateSecretsRequest`) happens *before* `authorizeAndStamp` is invoked. Only `authorizeAndStamp` (lines 222-255) computes `prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID` and mutates `req.ID`. If validation fails, `p.validationError(req, err)` returns an `InvalidVaultParamsError` with `req.ID` still untouched — i.e., exactly the client-supplied string.

Back in `HandleJSONRPCUserMessage`, this is caught by `vaultcap.IsInvalidVaultParamsError(err)` and forwarded via `h.sendImmediateUserResponse(ctx, req, callback, api.InvalidParamsError, err)` (handler.go:438-439), which calls `h.errorResponse(req, ...)`.

`errorResponse` (handler.go:779-784) then does:
```go
index := strings.Index(req.ID, vaulttypes.RequestIDSeparator)
if index != -1 {
    req.ID = req.ID[index+2:]
}
```
This logic is meant to strip a `owner::` prefix that only exists *after* successful authorization/stamping. But at the point an `InvalidParamsError` is raised, no such prefix exists — `req.ID` is 100% attacker-controlled. If the attacker sets `req.ID = "foo::bar"` (containing the literal separator), this code incorrectly finds the separator inside the attacker's own ID and truncates it to `"bar"`, discarding `"foo::"`. The returned JSON-RPC response's `id` field is therefore `"bar"`, not the client's original `"foo::bar"`.

This is asymmetric with `sendSuccessResponse` (handler.go:575-581), where `resp.ID` genuinely originates from the node echoing back the gateway-stamped `owner::originalID` value (stamped in `authorizeAndStamp` prior to `fanOutToVaultNodes`), so stripping there is safe by construction. The `errorResponse` path lacks that guarantee for any error raised before stamping (e.g. `InvalidParamsError`, and potentially other pre-authorization errors).

No authz, signature, or namespace check protects against this because `req.ID` is free-form client input (limited only by length ≤ 200 chars per `HandleJSONRPCUserMessage`, handler.go:407-410) and is never sanitized against containing the separator sequence.

### Impact Explanation
An unprivileged API client that crafts its own request ID with an embedded separator can receive a JSON-RPC response whose `id` does not match its `req.ID`, violating the JSON-RPC 2.0 request/response correlation invariant. In multi-tenant or pipelined gateway client libraries that match responses to pending requests purely by exact `id` equality, this can cause a response to be dropped, misrouted, or (in poorly written correlation logic) incorrectly associated with a different in-flight request from the same client. This is a client-side correlation/logic-confusion issue rather than a server-side authorization bypass or secret disclosure — the gateway itself continues to track/clean up the request by the correct internal map key (`h.activeRequests[req.ID]`), so this does not itself desynchronize the gateway's own request bookkeeping.

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: any unprivileged API client can set `req.ID` to any string of their choosing (up to 200 chars) and trigger an `InvalidParamsError` deliberately (e.g., malformed `CreateSecretsRequest` params for `MethodSecretsCreate`). No special privileges, timing, or race conditions are required — this is 100% reliable given knowledge of the separator constant, which is defined in the open-source `vaulttypes` package.

### Recommendation
Do not reuse a generic substring-search/strip heuristic on `req.ID` in `errorResponse` for pre-authorization error codes. Instead, track whether the request ID has actually been owner-prefixed (e.g., pass an explicit flag/boolean alongside the request, or only strip using the known/authoritative prefix length recorded when `authorizeAndStamp` ran) rather than blindly searching for the separator substring within attacker-controlled input. At minimum, only strip the separator using `strings.Cut` combined with confirmation that the prefix matches a previously recorded `authorizedOwner` value, not an unconditional first-match strip.

### Proof of Concept
Unit test targeting `handler.errorResponse` and `handler.sendSuccessResponse` in `core/services/gateway/handlers/vault/handler_test.go`:
```go
func TestErrorResponse_PreservesAttackerSuppliedIDWithEmbeddedSeparator(t *testing.T) {
    req := jsonrpc.Request[json.RawMessage]{
        Version: jsonrpc.JsonRpcVersion,
        ID:      "foo" + vaulttypes.RequestIDSeparator + "bar", // attacker-controlled, no owner prefix yet
        Method:  vaulttypes.MethodSecretsCreate,
    }
    payload := h.errorResponse(req, api.InvalidParamsError, errors.New("bad params"), nil)
    resp, err := (&api.JsonRPCCodec{}).DecodeRawRequest(payload.RawResponse, "")
    require.NoError(t, err)
    // FAILS today: resp.ID == "bar" instead of "foo::bar"
    require.Equal(t, req.ID, resp.ID, "response id must exactly equal original client-supplied request id per JSON-RPC 2.0")
}
```
Expected today: assertion fails, demonstrating `resp.ID` becomes `"bar"` instead of the original `"foo::bar"`, proving the ID-stripping logic in `errorResponse` incorrectly consumes attacker-controlled substrings before any owner-prefixing has occurred.
