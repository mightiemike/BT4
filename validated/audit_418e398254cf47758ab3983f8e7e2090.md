## Finding: `TransactionOutput::ensure_match_transaction_info` does not check state/hot-state/position checkpoint hashes

### Title
Replay-verification comparator skips checkpoint-hash fields, allowing a diverged state/position root to pass as a verified replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  is the authoritative comparator used by replay/verification tooling to decide whether a freshly re-executed transaction output matches the transaction info that is authenticated by the accumulator/ledger-info signature chain. It explicitly checks status, gas, write-set hash (`state_change_hash`) and event root hash, but the code contains a developer-acknowledged gap: it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` on `TransactionInfoV1`, as flagged by the inline `TODO(trading-native)` comment.

### Finding Description
The bug-class analog to the DYAD report is: a safeguard exists (`ensure_match_transaction_info`), but there is an alternate/omitted path through the same logic that never exercises the check needed to catch a divergence — analogous to `liquidate`/`move` bypassing the `idToBlockOfLastDeposit` flashloan check that only `deposit`/`withdraw` enforce.

Here, `TransactionInfoV1` carries three checkpoint-hash fields that bind the authenticated ledger state (the Jellyfish Merkle "main" state root, the hot-state root, and — new in this codebase — the native "position" state root used for on-chain trading state) [2](#0-1) . These roots are computed independently by `do_state_checkpoint.rs` during normal execution/commit [3](#0-2)  and are what a full node's proof responses (state proofs, position-state proofs) are ultimately bound to.

`ensure_match_transaction_info` is the function callers use to prove that a *locally re-executed* `TransactionOutput` reproduces a *given* `TransactionInfo` (e.g., one pulled from a signed backup/archive). Its actual body only verifies:
- status [4](#0-3) 
- gas used [5](#0-4) 
- write-set hash vs `state_change_hash` [6](#0-5) 
- event root hash [7](#0-6) 

It then returns `Ok(())` unconditionally without comparing any of the checkpoint hash fields, with the comment stating outright: *"this comparator ignores the checkpoint hashes (state/hot-state and position_state_checkpoint_hash), so replay-verify tooling (e.g. db-tool's replay_on_archive) can report a successful replay even when the authenticated position state root diverges from local execution."* [8](#0-7) 

This function is consumed by `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which re-executes archived transactions with the VM and calls `ensure_match_transaction_info` to compare fresh execution against the archived `expected_txn_info` [9](#0-8) , and also by `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`. In none of these callers is the write-set applied to a real state tree and the resulting root independently recomputed and compared to `state_checkpoint_hash`/`position_state_checkpoint_hash` — the comparator is treated as the sole gate for "does replay match."

Because the state root itself is never rebuilt and compared here, a state-commitment bug elsewhere (e.g. an incorrect JMT/position-Merkle update, an incorrect `hot_state_root_in_txn_info` computation, or corrupted historical `position_state_checkpoint_hash` data) that changes the committed root but leaves the write set and events unchanged would sail through replay-verify as a passing/matching transaction.

### Impact Explanation
This breaks the "Proof And Storage Pivots" invariant that "Accumulators, Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding" and that "replay paths ... must not reinterpret committed data into a different ledger state." Concretely:

- `replay_on_archive` / `replay_verify` tooling is the mechanism operators and the Aptos Labs pipeline use to certify that an archived (backed-up) chain history is internally consistent and matches VM execution. If the state/hot-state/position-state root recorded on-chain has silently diverged from what local re-execution would produce (due to any other bug in checkpoint-hash computation, corruption during restore, or a bit-flip in stored `TransactionInfo`), this verifier will still report success, since it never inspects those fields.
- The `position_state_checkpoint_hash` in particular authenticates the "native trading" position state root, which is used to answer authenticated state-proof queries for that subsystem. A silent divergence there is undetectable by this tool, meaning proof-bearing responses derived from a corrupted position state could go unnoticed indefinitely by the verification pipeline meant to catch exactly this class of fault.
- This is a genuine gap acknowledged in-code (not a hypothetical), so it satisfies "local code proves its own... broken state or proof invariant."

The severity is bounded by the fact that this does not, by itself, cause bad state to be *accepted into consensus* (BFT/execution correctness is enforced elsewhere by validators re-executing and comparing full `TransactionInfo` hashes against the accumulator via signature verification). The impact is specifically on the **detection/verification tooling path**, i.e., a full/verify-node or auditor could be fooled into believing an archived history/replay is fully consistent when the state-checkpoint-bound proof material has actually diverged. This is a high-impact integrity gap in the audit/replay-verify pipeline (masking corruption of committed proof roots), but it is not demonstrated here to corrupt what validators actually commit to consensus.

### Likelihood Explanation
The gap is unconditionally present — `ensure_match_transaction_info` always skips these fields regardless of feature flags — so any root-hash divergence caused by any other bug (in JMT computation, hot-state computation, or position-state computation) is guaranteed to be masked whenever this comparator is used. Likelihood of the comparator missing a genuine divergence is therefore deterministic (100%) if such a divergence exists elsewhere; the remaining question is only how likely an actual root divergence is to occur (dependent on other code paths, e.g. `do_state_checkpoint.rs`), which the report does not separately prove.

### Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (when `TransactionInfoV1`), and `txn_info.position_state_checkpoint_hash()` against independently recomputed roots at checkpoint boundaries before returning `Ok(())`, and update every caller (`replay_on_archive.rs`, `aptos_debugger.rs`, `cli/src/commands.rs`) to supply/compute the actual state roots for comparison rather than relying solely on write-set/event hash equivalence.

### Proof of Concept
No exploit transaction is required; this is a static code-review-provable gap:
1. Read `types/src/transaction/mod.rs:2139-2204` — the function body only checks status/gas/write_set_hash/event_root_hash and returns `Ok(())`.
2. Read the inline comment at lines 2197-2203, which is the developers' own acknowledgment that checkpoint hashes (including `position_state_checkpoint_hash`) are ignored and that `replay_on_archive` can report success despite divergence.
3. Read `storage/db-tool/src/replay_on_archive.rs:388-406`, showing `execute_and_verify` uses exactly this function as its pass/fail gate for chunk replay, with no supplementary state-root check anywhere else in that file.

This is sufficient to demonstrate the exact corrupted-check location and its exploitation path (a diverged committed root escaping detection by the verify tool); confirming an actual live root-divergence bug elsewhere that this masks was outside what could be traced with the available context.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
