### Title
Duplicate `input_data_ids` in `ActionReceipt` Permanently Locks Attached Deposits via Inflated `PendingDataCount` — (`runtime/runtime/src/lib.rs`)

---

### Summary

`process_action_receipt` counts each entry in `input_data_ids` toward `pending_data_count` without deduplicating, while the trie key `PostponedReceiptId[data_id]` is a single-slot map keyed only by `data_id`. When the same `data_id` appears twice, the count is inflated by 2 but only one trie link is written. The single arriving `DataReceipt` decrements the count to 1 and removes the link, leaving the count permanently above zero with no remaining link to trigger a further decrement. The `ActionReceipt` is postponed forever and any attached deposit is irrecoverably locked in state.

---

### Finding Description

`validate_action_receipt` in `runtime/runtime/src/verifier.rs` checks only that `input_data_ids.len()` does not exceed `max_number_input_data_dependencies`; it performs no uniqueness check: [1](#0-0) 

`process_action_receipt` in `runtime/runtime/src/lib.rs` iterates over every entry in `input_data_ids` and, for each entry not yet in state, increments `pending_data_count` and writes `TrieKey::PostponedReceiptId { receiver_id, data_id } → receipt_id`: [2](#0-1) 

Because `TrieKey::PostponedReceiptId` is keyed by `(receiver_id, data_id)`, a second write for the same `data_id` silently overwrites the first with the identical value. The counter, however, is incremented for every occurrence:

- `input_data_ids = [X, X]` → `pending_data_count = 2`, one trie link `PostponedReceiptId[X] = receipt_id`.

When the `DataReceipt` for `X` arrives, the runtime looks up `PostponedReceiptId[X]`, decrements the count to 1, and removes the link: [3](#0-2) 

After this, `pending_data_count = 1` but no `PostponedReceiptId[X]` link exists. No future `DataReceipt` can decrement the counter further. The `ActionReceipt` is stored as a postponed receipt indefinitely and `apply_action_receipt` is never called: [4](#0-3) 

If the receipt somehow reached `apply_action_receipt` with duplicate `input_data_ids` and all data already present, the second iteration over the same `data_id` would attempt to read `ReceivedData` that was already removed in the first iteration, triggering `StorageError::StorageInconsistentState`: [5](#0-4) 

**Attack vector.** `ActionReceipt.input_data_ids` is populated by the VM logic when a contract calls `promise_and` or `promise_then`. A malicious contract that passes the same promise index twice to `promise_and` would produce an `ActionReceipt` with a repeated `data_id`. The runtime-level validation does not prevent this: [6](#0-5) 

**Note on VM-logic reachability.** The `near-vm-logic` source files were not available in the index for this repository. It is therefore uncertain whether the VM host function for `promise_and` independently deduplicates promise indices before constructing `input_data_ids`. If it does not, the attack is directly reachable from any user-deployed contract. If it does, the runtime-level invariant is still broken for any receipt that arrives via cross-shard routing or state migration with duplicate `input_data_ids`, because the runtime's own validation never enforces uniqueness.

---

### Impact Explanation

Any deposit attached to the permanently-postponed `ActionReceipt` is locked in the trie under `TrieKey::PostponedReceipt` and `TrieKey::PendingDataCount` with no code path that can ever clear it. The signer's deposited NEAR is unrecoverable without a protocol-level state patch. This constitutes **loss of funds** and **contract execution flow breakage**.

---

### Likelihood Explanation

Likelihood is **conditional**. If the VM logic does not deduplicate promise indices in `promise_and`, any user who can deploy and call a contract (i.e., any NEAR account holder) can trigger this with a single function call. The runtime validation is the only gate and it is missing the uniqueness check. If the VM logic does deduplicate, the impact is limited to crafted receipts injected through other means (e.g., cross-shard routing bugs or future receipt-format changes), which is a lower-likelihood path.

---

### Recommendation

Add a uniqueness check for `input_data_ids` in `validate_action_receipt`:

```rust
fn validate_action_receipt(...) -> Result<(), ReceiptValidationError> {
    let ids = receipt.input_data_ids();
    if ids.len() as u64 > limit_config.max_number_input_data_dependencies {
        return Err(...);
    }
    // NEW: reject duplicate data dependencies
    let mut seen = HashSet::with_capacity(ids.len());
    for id in ids {
        if !seen.insert(id) {
            return Err(ReceiptValidationError::DuplicateInputDataId { data_id: *id });
        }
    }
    ...
}
```

Additionally, add a defensive deduplication guard in `process_action_receipt` so that even receipts that pre-date the validation fix cannot permanently lock funds:

```rust
let mut seen_data_ids = HashSet::new();
for data_id in action_receipt.input_data_ids() {
    if !seen_data_ids.insert(data_id) { continue; } // skip duplicates
    if !has_received_data(state_update, account_id, *data_id)? {
        pending_data_count += 1;
        set(state_update, TrieKey::PostponedReceiptId { ... }, receipt.receipt_id());
    }
}
```

### Proof of Concept

```
1. Deploy a contract on NEAR that, when called, executes:
      let p0 = env::promise_create("target.near", "method", b"{}", 0, 5_000_000_000_000);
      // Pass the same promise index twice to promise_and
      let combined = env::promise_and(&[p0, p0]);
      env::promise_then(combined, "target.near", "callback", b"{}", deposit, gas);

2. Call the contract with a non-zero deposit attached to the callback.

3. The runtime creates an ActionReceipt for "callback" with:
      input_data_ids = [data_id_X, data_id_X]   // same hash twice
      deposit = <attached NEAR>

4. process_action_receipt sets pending_data_count = 2 and writes
   PostponedReceiptId[data_id_X] = callback_receipt_id once.

5. The DataReceipt for data_id_X arrives (from p0's execution).
   pending_data_count decremented to 1; PostponedReceiptId[data_id_X] removed.

6. No further DataReceipt for data_id_X will ever arrive.
   pending_data_count stays at 1 forever.
   The callback ActionReceipt is permanently postponed.
   The attached deposit is permanently locked in trie state.
```
