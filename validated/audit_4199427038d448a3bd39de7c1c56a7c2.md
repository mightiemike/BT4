`accrue()` "pause pass-through" lets `system-borrow`/`system-repay`/liquidation math run against stale index/lindex, understating debt and stranding protocol value - (File: `mainnet/contracts/vault/v0-vault-stx.clar`)

### Summary
Every vault's `accrue()` function is designed to skip interest-index updates while the `accrue` pause flag is set, returning the *current* (stale) `index`/`lindex` instead of reverting. Every other vault entrypoint (`system-borrow`, `system-repay`, `deposit`, `redeem`, and by extension `market.clar`'s liquidation/health-check flow) unconditionally calls `(try! (accrue))` first and then trusts whatever index it gets back to compute debt, collateral valuation, and liquidation thresholds. Because a pause is a live, admin-toggleable, single-block condition, and the callers never check whether the "pause pass-through" path was taken, borrow/repay/liquidate calculations proceed on frozen indexes and the protocol accrues real economic drift (interest, bad-debt write-downs) that is silently dropped rather than reverted.

### Finding Description
`accrue()` in `v0-vault-stx.clar` (and duplicated in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`) is:

```
(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index)) ...)
            ...
            (ok { index: next, lindex: nliq })))))
``` [1](#0-0) 

The bug-class signature is exactly "a pause that passes through instead of reverting": when `accrue` is paused, the function returns `(ok ...)` with the *unchanged* stored `index`/`lindex` values, rather than propagating an error or blocking dependent state-changing operations. All value-bearing operations built on top of it — `system-borrow`, `system-repay`, `socialize-debt`, `deposit`, `redeem` — call `(try! (accrue))` unconditionally and use the returned `index`/`lindex` to compute debt totals, cap checks, and shares:

```
(define-public (system-borrow (amount uint) (receiver principal))
  (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      ...
      (idx (var-get index))
      (debt (total-debt))
      (scaled-amount (mul-div-up amount INDEX-PRECISION idx))
``` [2](#0-1) 

Crucially, `market.clar`'s `liquidate()` also flows through this same cached-accrual path via `accrue-and-cache` / `get-cached-indexes`, and health checks, LTV calculations, and bad-debt socialization all rely on the `index`/`lindex` obtained via this chain: [3](#0-2) [4](#0-3) 

Because `pause-states` is a single admin-controlled boolean that can be toggled at any block boundary (single-transaction, single-block scope — no separate confirmation step is required for callers to observe it), any borrow, repay, liquidation, or bad-debt socialization that executes while `accrue` is paused will:
1. Compute `debt`, `total-assets`, LTV, and liquidation penalties using the frozen `index`/`lindex` instead of the true, currently-accruing values.
2. Persist state changes (`principal-scaled`, `total-borrowed`, `assets`, obligation removal in `market-vault`) based on that stale math.
3. Never revert or flag that the pause path was taken — the caller has no way to detect it was served stale data, since `accrue()` returns `(ok {...})` in both branches with the same shape.

This matches the mitigation-relevant analog to `CollectionShutdown::execute()`: just as that function silently omits NFTs not present in a caller-supplied set (an incomplete state view used to drive an irreversible action), `accrue()`'s pause-pass-through silently omits the true, currently due index update from the value computed and durably written by every downstream operation, with no error signal distinguishing "fresh index" from "stale index."

### Impact Explanation
When `accrue` is paused (even momentarily, e.g. during a maintenance window or a DAO-scheduled parameter change) and a `system-borrow`/`system-repay`/`liquidate` transaction lands in that same window:
- Debt/interest that has genuinely accrued since `last-update` is not reflected in `index`, so borrowers can repay/be liquidated against understated debt, and lenders' `lindex`-based share value understates true assets — causing a temporary (and, if state changes are then persisted on the stale basis, effectively permanent for that accrual period) freezing/loss of yield owed to suppliers.
- `socialize-debt`-based bad-debt write-downs computed off a stale `lindex` mis-price collateral relative to real vault assets, which can leave true losses unsocialized (protocol insolvency risk) or double-counted on the next unpaused accrual.

This lands in the in-scope impact class of **temporary freezing of unclaimed yield** (suppliers' accrued interest is not reflected/credited for the paused window) and, in the liquidation path, potential **protocol insolvency** exposure if bad-debt socialization proceeds on stale indexes while real debt has grown further.

### Likelihood Explanation
`pause-states` is an operationally normal, DAO/admin-controlled toggle (the docs describe pausability as a standard feature, not an emergency-only path), so the paused window is reachable without any privilege escalation. Any user transaction (borrow, repay, liquidate) that lands while `accrue` is paused triggers this automatically — no attacker coordination or flashloan is required, purely an ordering/timing condition within normal protocol operation, matching the "pause that passes through instead of reverting" analog class explicitly permitted by the scan rules.

### Recommendation
Have `accrue()` distinguish between "pause active" and "index refreshed" in its return type (or have callers check `(get accrue states)` before trusting the returned `index`/`lindex`), and block interest-sensitive state-changing operations (`system-borrow`, `system-repay`, `socialize-debt`, liquidation-path debt calculations in `market.clar`) from proceeding while `accrue` is paused, rather than silently continuing with stale indexes. At minimum, emit and check a staleness flag so `market.clar`'s liquidation/health logic can revert if it discovers the underlying vault's accrual was paused during the same evaluation.

### Proof of Concept
1. DAO/admin sets `pause-states.accrue = true` on `vault-stx` via the appropriate pause-setter (pattern consistent with `set-pause-liquidation`/pause-state setters seen in `market.clar`) [5](#0-4) .
2. Time passes; true `next-index()`/`next-liquidity-index()` would be materially higher than stored `index`/`lindex`, i.e., real debt/assets have grown.
3. A user calls `system-borrow`/`system-repay` (or `market.clar`'s `liquidate`) on `vault-stx`. `accrue()` is invoked, sees `(get accrue states)` true, and returns `(ok { index: idx, lindex: lidx })` — the old, stale values — at line 839-841 of `v0-vault-stx.clar`.
4. `system-borrow`/`system-repay`/liquidation logic uses this stale `idx`/`lindex` to compute `scaled-amount`, `debt`, LTV, and collateral seizure, and durably writes `principal-scaled`, `total-borrowed`, `assets` based on it [6](#0-5) .
5. No revert occurs and no signal indicates the computation used stale accrual data; the discrepancy between true and stale index is never socialized once the pause window ends, and the affected users' debt/yield positions are permanently understated/overstated for that accrual window.
