### Title
Unauthenticated JSON-RPC methods can halt/resume sequencer commitment submission without any authorization check - (File: `crates/common/src/rpc/auth.rs`, `crates/sequencer/src/rpc.rs`)

### Summary
The `Auth` RPC middleware that is meant to gate privileged JSON-RPC methods behind an API key only protects a hardcoded allow-list of three method names, while the sequencer exposes state-mutating methods such as `citrea_haltCommitments` and `citrea_resumeCommitments` that are never added to that list. Any client able to reach the node's JSON-RPC port can therefore invoke these methods without presenting any credential, directly mirroring the reported bug class ("fallback"/dispatch logic that routes a privileged operation without checking sender authorization).

### Finding Description
All RPC methods on a Citrea node share a single `jsonrpsee` server and a single `RpcServiceT` middleware stack built in `start_rpc_server`: [1](#0-0) 

The `Auth` layer is the only authorization gate, and it explicitly whitelists just three method names to check against an API key, letting every other method pass straight through untouched: [2](#0-1) 

The sequencer registers `citrea_haltCommitments` and `citrea_resumeCommitments` as ordinary RPC methods on this same server, with no additional authorization check inside their handlers — they simply forward a control message to the sequencer's internal runner: [3](#0-2) [4](#0-3) 

Since `halt_commitments`/`resume_commitments` are absent from `PROTECTED_METHODS`, the `Auth` middleware treats them as public and forwards the call regardless of whether an `api_key` was configured or supplied — functionally identical to the reported issue where a dispatcher routes a call to a privileged handler without verifying the caller's authorization.

### Impact Explanation
`SequencerRpcMessage::HaltCommitments` / `ResumeCommitments` control whether the sequencer submits sequencer commitments to the L1 DA layer (consumed by `crates/sequencer/src/commitment/service.rs` and `crates/sequencer/src/runner.rs`). An unauthenticated attacker who can reach the sequencer's JSON-RPC endpoint can unilaterally halt commitment submission, stalling the rollup's proof/settlement pipeline, or resume it at an attacker-chosen time — mutating sequencer node state through an unauthenticated call, which the rules explicitly classify as High-impact ("an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`").

### Likelihood Explanation
Exploitation only requires network access to the sequencer's RPC port and a single JSON-RPC request with the method name `citrea_haltCommitments` or `citrea_resumeCommitments` — no signature, private key, or node-operator role is needed, and the bug is purely a missing-entry omission in a hardcoded list (`PROTECTED_METHODS`), not a deployment misconfiguration.

### Recommendation
Change `Auth`'s protection model from a method-name allow-list requiring opt-in, to a default-deny/opt-out model, or explicitly add all sequencer-control methods (`citrea_haltCommitments`, `citrea_resumeCommitments`, and similarly sensitive `txpool_removeTransactionsByHash`/`txpool_removeTransactionsBySender`) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`, so that any method capable of mutating sequencer/node state requires the API key by default rather than by exception.

### Proof of Concept
1. Start a Citrea sequencer node with `rpc_config.api_key` configured for protection.
2. Without supplying any API key, send a JSON-RPC request to the node's RPC endpoint: `{"jsonrpc":"2.0","method":"citrea_haltCommitments","params":[],"id":1}`.
3. Because `"citrea_haltCommitments"` is not in `PROTECTED_METHODS` (`crates/common/src/rpc/auth.rs:11`), the `Auth` layer forwards the request unchanged (`crates/common/src/rpc/auth.rs:36-38`), and `SequencerRpcServerImpl::halt_commitments` executes, sending `SequencerRpcMessage::HaltCommitments` to the sequencer runner (`crates/sequencer/src/rpc.rs:408-414`).
4. The sequencer stops submitting commitments to L1 until an equally unauthenticated `citrea_resumeCommitments` call is made, with no authorization ever checked.

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }
