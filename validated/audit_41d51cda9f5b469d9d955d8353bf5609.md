### Title
Log/state artifacts from failed top-level VM execution can survive commit when TvmOsaka is not active - (File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java)

### Summary
`OperationActions.logAction` unconditionally appends `LogInfo` to `program.getResult()` during opcode execution [3](#0-2) . When the transaction ultimately fails via an exception path caught in `VMActuator.execute`'s `catch` blocks (`JVMStackOverFlowException`, `OutOfTimeException`, generic `Throwable`), the accumulated logs and delete-accounts are only purged if the `TvmOsaka` hard fork/feature is active; otherwise they remain attached to the `ProgramResult` that is stored into the `TransactionContext` and subsequently used to build `TransactionInfo`/receipts and trigger events.

### Finding Description
Inside the normal (non-exceptional) control flow, `VMActuator.execute` correctly clears `logInfoList` and `deleteAccounts` when `result.getException() != null || result.isRevert()` [4](#0-3) . However, there is a second, structurally distinct set of failure paths: exceptions thrown directly out of `VM.play(program, OperationRegistry.getTable())` (e.g. stack overflow, CPU/time-limit exhaustion, or any other unexpected `Throwable`) bypass that in-try cleanup entirely and are caught by the `catch (JVMStackOverFlowException e)`, `catch (OutOfTimeException e)`, and `catch (Throwable e)` blocks [5](#0-4) . Each of these calls `clearExceptionResult(result)`, but that helper is gated behind `VMConfig.allowTvmOsaka()` [1](#0-0) . If `allowTvmOsaka` is not enabled on the running node/chain configuration, any `LogInfo` entries already pushed via `logAction` (and any `deleteAccounts`) before the fatal exception occurred remain in the `ProgramResult` that is set into the `TransactionContext` at line 298 and returned to callers, even though the transaction is marked failed (`result.setException(...)`, `result.setRuntimeError(...)`).

An attacker can trigger this by deploying a contract via `/wallet/deploycontract` that: emits one or more `LOG0`-`LOG4` opcodes (reaching `logAction`) early in execution, then enters a code path engineered to blow the JVM call stack (deep recursive internal calls) or exhaust the CPU/time budget, causing `VM.play` to throw `JVMStackOverFlowException` or `OutOfTimeException` rather than returning normally. After signing and broadcasting via `/wallet/broadcasttransaction`, the resulting `TransactionInfo`/receipt can carry stale log entries from a transaction whose execution did not actually commit any state (the whole transaction reverted/failed), producing a discrepancy between the "committed" TVM state (no storage/balance changes) and the published log/trigger artifacts.

### Impact Explanation
Downstream consumers—event listeners (`ContractTrigger`s built from `logInfoTriggerParser`), the `TransactionInfo.log` field returned by `/wallet/gettransactioninfobyid` and block servlets, and off-chain settlement/monitoring systems that key on emitted events—may observe logs for a transaction that did not actually change state, matching the "false spent-state decisions"/"inconsistent execution artifacts" impact category described in the target invariant. This is scoped to whichever chains/configurations have not yet activated the `allowTvmOsaka` feature; the code comments and gating strongly suggest this exact defect was identified and is being progressively patched (Osaka-only fix), meaning any environment where Osaka is not enabled remains exposed.

### Likelihood Explanation
The attacker only needs unprivileged access to deploy and broadcast a self-crafted contract that triggers `LOG*` opcodes followed by a JVM stack overflow or CPU-time exhaustion during the same top-level call — both are attacker-controllable via nested-call depth/structure and computational loops, which are exactly the "nested-call structure" and "energy" levers named in the question's attacker-controls list. It is repeatable across any transaction the attacker chooses to craft this way, on any node/network where `allowTvmOsaka` is not active.

### Recommendation
Make the log/delete-account cleanup unconditional in `clearExceptionResult`, or move the clearing logic so it always executes for any exception/failed-execution path in `VMActuator.execute`, regardless of the `allowTvmOsaka` flag, ensuring published logs/triggers always correspond to the actually committed execution branch.

  public static void logAction(Program program) {
    Stack stack = program.getStack();
    if (program.isStaticCall()) {
      throw new Program.StaticCallModificationException();
    }
    DataWord address = program.getContractAddress();

    DataWord memStart = stack.pop();
    DataWord memOffset = stack.pop();

    int nTopics = program.getCurrentOpIntValue() - Op.LOG0;

    List<DataWord> topics = new ArrayList<>();
    for (int i = 0; i < nTopics; ++i) {
      DataWord topic = stack.pop();
      topics.add(topic);
    }

    byte[] data = program.memoryChunk(memStart.intValueSafe(), memOffset.intValueSafe());

    LogInfo logInfo =
        new LogInfo(address.getLast20Bytes(), topics, data);

    program.getResult().addLogInfo(logInfo);
    program.step();
  }
