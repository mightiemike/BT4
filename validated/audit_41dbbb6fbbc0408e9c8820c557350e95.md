### Title
Unauthenticated declare-transaction path allows any sender to impersonate the privileged bootstrap identity - (File: `crates/starknet_api/src/executable_transaction.rs`)

### Summary
The Starknet OS and blockifier contain a special-case "bootstrap declare" path meant to let the sequencer operator declare initial system classes with no signature validation, no fee charge, and no nonce bump, before any account exists on-chain. Eligibility for this privileged path is determined purely from fields fully controlled by the transaction sender (`sender_address == bootstrap_address()` and `nonce == 0`) plus a locally computed `charge_fee` flag, with no cryptographic proof that the caller is the legitimate bootstrap orchestrator. This is directly analogous to the referenced Wildfly CVE-2021-3717, where an authentication mechanism intended for one legitimate local principal (`JBOSS_LOCAL_USER`) was reachable by any local user due to the challenge/identity check being placed at the wrong trust boundary.

### Finding Description
`DeclareTransaction::is_bootstrap_declare` treats any Declare v3 transaction as a privileged, unauthenticated "system bootstrap" transaction whenever three attacker-controllable/operator-controllable conditions hold: [1](#0-0) 

```
pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
    if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
        return tx.sender_address == Self::bootstrap_address()
            && tx.nonce == Nonce(Felt::ZERO)
            && !charge_fee;
    }
    false
}
```

`bootstrap_address()` is a hard-coded constant (`0x424f4f545354524150`, the ASCII encoding of "BOOTSTRAP") — not a real account contract that must be deployed and whose `__validate_declare__` can enforce ownership. `sender_address` is a plain field of the `DeclareTransactionV3` struct, freely chosen by whoever constructs the RPC transaction; nothing in the gateway rejects a normal user from setting `sender_address` to this exact constant.

When `is_bootstrap_declare` returns true, both the blockifier and the Starknet OS skip **all** account-related protections for the transaction:

- Blockifier (sequencer execution) skips `perform_pre_validation_stage` (nonce/fee checks) and the `__validate_declare__` call entirely, running only the class-declaration side effect: [2](#0-1) 

- The Starknet OS mirrors this: it checks the same three conditions in Cairo and, if satisfied, updates `contract_class_changes` for the given `class_hash` directly and returns, skipping nonce increment, `__validate_declare__`, and fee charge: [3](#0-2) 

The class declaration itself uses a one-time-write semantic (`prev_value=0` in `dict_update`), i.e. whichever transaction declares a given `class_hash` first under the bootstrap path "wins" that class hash permanently: [4](#0-3) 

The only gate preventing this from being reachable by ordinary traffic on a live chain is the sequencer-wide `charge_fee` / `validate_resource_bounds` operational flag, which is `false` only during the network's bootstrap phase (a legitimate operational window, documented as "used to improve UX"/"for starting a new Starknet system"): [5](#0-4) 

During that window, **any** unprivileged transaction sender — not just the sequencer operator's intended bootstrap orchestrator — can submit a Declare v3 transaction with `sender_address = bootstrap_address()`, `nonce = 0`, and zero/no-fee resource bounds, and have it accepted with zero signature validation and zero fee. Since there is no actual "BOOTSTRAP" account contract enforcing who may act on its behalf (the whole point of the shortcut is to skip `__validate_declare__`), the identity check is effectively a bare string/address match — the same class of flaw as the Wildfly issue, where a privileged local-only challenge could be satisfied by anyone due to the challenge being checked at the wrong scope/trust level.

### Impact Explanation
During the bootstrap window an unprivileged attacker can:
- Front-run/squat any `class_hash` the legitimate bootstrap process intends to declare (e.g., the account class, UDC, or other system contracts), permanently occupying that `class_hash -> compiled_class_hash` slot with attacker-chosen bytecode, because the on-chain declare-once semantics (`prev_value=0`) blocks any subsequent legitimate declaration of the same class hash.
- Cause the genuine bootstrap declare for that class hash to fail forever afterward, freezing correct system initialization (a permanent, unauthorized state change with no attribution, fee, or signature check) — this is an unauthorized-account-action / freezing-of-intended-state impact reachable purely from a single submitted transaction during the operationally-supported bootstrap phase.
- Do so entirely for free (no fee, no valid signature required), unlike every other transaction type in the system.

### Likelihood Explanation
The precondition (`charge_fee == false`, i.e. `validate_resource_bounds` disabled) is an intended, documented operational state used specifically "during a system bootstrap" — meaning this attack surface is open exactly at the most sensitive point in a chain's lifecycle (genesis), when the set of correctly-declared classes matters most and no other classes/accounts exist yet to detect or react to squatting. No signature, funds, or special privilege is required to exploit it once that window is open — a single crafted Declare transaction suffices.

### Recommendation
Do not rely on `sender_address == bootstrap_address()` as a stand-in for authorization. Options:
- Restrict the bootstrap-declare shortcut to a single, sequencer-injected transaction (not one submitted through the public gateway/mempool at all), e.g., only allow it to originate from a trusted internal API/batcher call, never from `apollo_gateway`'s external RPC ingestion path.
- If external submission must be supported, require a signature check against a well-known bootstrap public key (configured out-of-band by the node operator) before skipping `__validate_declare__`, rather than skipping validation unconditionally.
- Alternatively, gate the bootstrap path by block number (only valid in block 0 and only via a channel the gateway does not expose over public RPC), removing the reachability from an unprivileged external sender entirely.

### Proof of Concept
1. Configure/observe a node in bootstrap mode (`validate_resource_bounds: false`, matching `apollo_node_config` pointer target used "during a system bootstrap"): [5](#0-4) 
2. As any external client, submit an RPC `add_declare_transaction` with:
   - `sender_address = 0x424f4f545354524150` (`DeclareTransaction::bootstrap_address()`)
   - `nonce = 0`
   - `resource_bounds` set to `ValidResourceBounds::create_for_testing_no_fee_enforcement()` (or any bounds that keep `charge_fee` false in this window), matching the pattern used in `generate_bootstrap_declare()`: [6](#0-5) 
   - `class_hash`/`compiled_class_hash` for an attacker-chosen contract that collides with a `class_hash` the legitimate bootstrap process was going to declare (e.g. a known system contract's Sierra hash), with `signature` empty/arbitrary.
3. The transaction is accepted by `AccountTransaction::execute_raw` via the `is_bootstrap_declare` shortcut with no validate call and no fee: [7](#0-6)  and by the OS's mirrored check: [8](#0-7) .
4. The subsequent legitimate declaration of that same `class_hash` by the real bootstrap process fails, because `dict_update` enforces `prev_value=0` for a first-time-only declare: [4](#0-3) , permanently freezing correct genesis-time class declaration for that hash.

**Caveat / uncertainty:** I was unable to fully trace the exact conditions under which `charge_fee` (via `enforce_fee`) is `false` for a transaction submitted through the live public gateway outside of the explicit bootstrap-mode config flag (`validate_resource_bounds=false`); the tool budget was exhausted before reading `crates/blockifier/src/transaction/objects.rs::enforce_fee` in full. If in practice `charge_fee` can never be `false` for transactions accepted through the normal external RPC/gateway path (i.e., it is gated purely by trusted internal orchestration and not reachable by public submission at all), this reduces to a lower-severity design smell rather than an externally-triggerable vulnerability. A background session with full repository access should verify `enforce_fee`'s logic and how bootstrap-phase transactions are actually injected (public RPC vs. internal-only channel) to confirm real-world reachability before treating this as confirmed-exploitable.

        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {
            if tx.is_bootstrap_declare(self.execution_flags.charge_fee) {
                let mut context = EntryPointExecutionContext::new_invoke(
                    tx_context.clone(),
                    self.execution_flags.charge_fee,
                    SierraGasRevertTracker::new(GasAmount::default()),
                );
                let mut remaining_gas = 0;
                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());
