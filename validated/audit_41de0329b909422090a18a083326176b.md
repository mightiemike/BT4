### Title
Session Cookie Not Scoped Per-Shop in Non-Embedded Multi-Shop Apps Causes Cross-Tenant Session Fixation - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
The ValueToken bug class is a "shared fungible identifier used across distinct value contexts" flaw: because the same `ValueToken` doesn't encode which `cid` (closure id) it belongs to, an attacker can mint it in a low-value context and redeem it in a high-value one. The structurally identical pattern in `shopify-app-js` is the OAuth session cookie for non-embedded apps: the `shopify_app_session` cookie is written at a single, shop-agnostic `path` (default `/`), so the *same cookie slot* is shared across all shop contexts (the equivalent of "cids") in a given browser. Authenticating a second shop silently overwrites the session identity bound to the first, letting one shop's authenticated context bleed into another tab/session that believed it was still scoped to the original shop.

### Finding Description
When `callback()` completes OAuth for a non-embedded app, it signs and stores the resulting `session.id` in a cookie named `SESSION_COOKIE_NAME` (`shopify_app_session`), using a `path` that defaults to `/` regardless of which shop the session belongs to: [1](#0-0) 

The cookie value itself is just a `session.id` (e.g., `offline_{shop}`), which is then used to look up the actual session (and access token) from app-provided storage: [2](#0-1) 

Because the cookie has no shop-specific scoping by default, if a browser is used to authenticate a second shop (e.g., a user or attacker triggers `/auth?shop=shopB...`), the OAuth callback for `shopB` overwrites the single domain-wide `shopify_app_session` cookie that was previously set for `shopA`. Any tab/session still believing it operates on `shopA` will now resolve to `shopB`'s session id via `getCurrentSessionId`/`getCurrentId`, exactly like the ValueToken bug where value minted under one `cid` is redeemable in another. This is explicitly documented as intrinsic default behavior: [3](#0-2) [4](#0-3) 

The `validateWithAuthCodeFlow` middleware does perform a shop/query mismatch check, but it only protects requests that explicitly pass `?shop=`; when the app relies on the cookie-derived session (`shop = ... || session?.shop`), a mismatch is only caught if the caller supplies the original shop in the query string: [5](#0-4) 

### Impact Explanation
An attacker who can get their own OAuth flow triggered in the same browser as a victim (e.g., shared/public device, or a victim clicking an "Install for shopB" link the attacker controls while their app tab for `shopA` remains open) overwrites the victim's session cookie with the attacker-controlled shop's session id. Subsequent requests from the victim's still-open tab that rely on the cookie (rather than an explicit `shop` query param) will silently operate under the attacker's shop context/access token instead of the intended shop — a cross-tenant session-fixation condition. This can result in a merchant unknowingly performing or viewing actions against the wrong (attacker's) store, and undermines the assumption that one browser session maps to one merchant/shop.

### Likelihood Explanation
This is opt-out by default: any non-embedded, multi-shop-capable app that does not explicitly set the new `cookiePath` config is affected, since `cookiePath` defaults to `'/'`. Non-embedded apps supporting multiple shops per browser (common for admin dashboards, multi-store SaaS tools) are realistically exposed. The trigger requires only an unprivileged actor able to initiate `/auth?shop=<attacker-shop>` in the same browser context as the victim — no secrets, MITM, or privileged access are required.

### Recommendation
Require (or default to) shop-specific cookie scoping for non-embedded apps — i.e., make `cookiePath` mandatory or auto-derive a shop-specific path/cookie name (e.g., `shopify_app_session_{shop}`), rather than relying solely on documentation and an opt-in config flag. Additionally, harden `getCurrentSessionId`/`validateWithAuthCodeFlow` so that a shop mismatch between the resolved session and any shop hint in the request is enforced even when `req.query.shop` is absent, by binding the cookie itself (not just the referenced session) to the shop, similar to how `getJwtSessionId` binds embedded sessions to `shop_sub`.

### Proof of Concept
1. Configure a non-embedded, multi-shop app without setting `cookiePath` (default `'/'`).
2. Victim authenticates shop `victim-shop.myshopify.com` in Tab 1 → server sets `shopify_app_session=offline_victim-shop.myshopify.com` at `path=/`.
3. Attacker causes the same browser to complete OAuth for `attacker-shop.myshopify.com` (e.g., via a link/iframe triggering `/auth?shop=attacker-shop.myshopify.com`) → server overwrites the domain-wide cookie with `offline_attacker-shop.myshopify.com`.
4. Victim's Tab 1, which does not resend `shop=victim-shop.myshopify.com` on every request, now resolves its session via `getCurrentSessionId`/`cookies.getAndVerify(SESSION_COOKIE_NAME)` to the attacker's shop session, as shown in [2](#0-1) , silently switching the victim's authenticated tenant context.

- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
```
