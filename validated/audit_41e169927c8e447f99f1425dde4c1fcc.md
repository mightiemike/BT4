No vulnerability found for this question.

**Analysis supporting this conclusion:**

Across all three `DBPruner` implementations, the `progress() > target_version()` case is handled safely as a pure no-op, with no arithmetic wraparound and no corruption of persisted progress metadata:

- `LedgerPruner::prune` and `StateKvPruner::prune` both guard the batch loop with `while progress < target_version`. When `progress > target_version`, this is a plain unsigned comparison that evaluates to `false` immediately — the loop body (which contains the only arithmetic, `progress + max_versions as Version`) never executes, so there is no overflow/wraparound possible. `record_progress()` is inside the loop and is therefore never called, leaving the persisted min-readable-version metadata untouched. [1](#0-0) [2](#0-1) 

- `StateMerklePruner::prune` is even more explicit, with a dedicated early-return guard `if progress >= target_version { return Ok(progress); }` before any work is attempted. [3](#0-2) 

- The only place a pruner's `record_progress()` is invoked is inside these guarded loop bodies, so the described no-op path never writes a misleading min-readable-version.

Separately, the premise that `progress() > target_version()` is externally reachable via the described `saturating_sub` path does not hold. `set_target_version()` is only ever invoked through `PrunerWorker::set_target_db_version`, which explicitly refuses to lower the target: it only calls `self.pruner.set_target_version(target_db_version)` `if target_db_version > self.pruner.target_version()`. [4](#0-3) 

This means `target_version()` is monotonically non-decreasing regardless of how `latest_version` or `get_min_viable_version`'s `saturating_sub` behaves in `LedgerPrunerManager::set_pruner_target_db_version` or the analogous state-merkle manager code — a shrinking `latest_version` can at most compute a smaller `min_readable_version`, but that smaller value is simply never applied as a new target because of the `>` guard. [5](#0-4) [6](#0-5) 

So even under the hypothesized "caller bug" scenario, both (a) the `prune()` implementers correctly no-op with no panic/wraparound, and (b) the described version-accounting path in the manager cannot actually drive `target_version()` below `progress()` in the first place, since the worker enforces monotonic target growth. There is no reachable path from unprivileged transaction/API/proof input that corrupts committed state, proof material, or authenticated responses here.
