This confirms the key mechanism: for a source chain in the `solana` CAIP-2 namespace, `inbound.Sender` is canonicalized via `canonicalizeSolanaValue` [1](#0-0) , which accepts and **preserves base58-encoded Solana pubkeys as-is** — it never forces a 20-byte EVM hex form for non-EVM chains [2](#0-1) . `Inbound.Canonicalize()` explicitly routes `Sender` through this per-source-chain-namespace canonicalizer [3](#0-2) .

That same `Sender` value later becomes `OutboundTx.Sender` [4](#0-3) , and in `applyGasRefund` it is used, when `RevertInstructions.FundRecipient` is absent, as `refundRecipient`, which is force-decoded with `common.HexToAddress(refundRecipient)` [5](#0-4) . `common.HexToAddress` never errors — for a base58 Solana string it silently derives a garbage/likely-wrong 20-byte value (Go's `go-ethereum` `common.FromHex`/`HexToAddress` strips non-hex characters and right-aligns whatever hex remains, effectively producing an unrelated or zero-ish address for non-hex input). The refunded PRC20/native gas excess is then irreversibly minted to that unintended address via `CallUniversalCoreRefundUnusedGas` [6](#0-5) . The identical fallback pattern (`recipient := outbound.Sender`) also exists in the revert-outbound builder [7](#0-6) , but there the funds go back out as an `OutboundTx.Recipient` on the **source chain** through the SVM tx builder (which parses `Recipient` via `solana.PublicKeyFromBase58`, with a hex-decode fallback) [8](#0-7) , so that specific path is not necessarily broken — but the **gas-refund** path (`applyGasRefund`) unconditionally treats the recipient as a Push-Chain EVM address regardless of the outbound's destination-chain namespace, because the refund always happens on Push Chain itself via `DerivedEVMCall`, not on the destination chain.

I was not able to fully trace, in the remaining budget, whether every code path that populates `OutboundTx.Sender` for an SVM-origin, TxType_GAS/GAS_AND_PAYLOAD inbound guarantees `RevertInstructions.FundRecipient` is always set to a valid EVM hex address (which would neutralize the bug by never falling into the `outbound.Sender` fallback branch). The `event_processor.go` `constructInbound` only sets `RevertInstructions` "if revert fund recipient is present" in the event data [9](#0-8) , meaning it is optional and attacker/source-chain-event-controlled — an SVM-chain-initiated inbound that omits `revert_fund_recipient` (or a malicious/malformed source-chain event lacking it) is plausible and unprivileged.

### Title
Gas-refund fallback silently sends excess gas fee to a wrong/derived address for non-EVM-chain senders - (File: x/uexecutor/keeper/outbound.go)

### Summary
`applyGasRefund` refunds unused destination-chain gas by depositing PRC20/native value to `common.HexToAddress(refundRecipient)` on Push Chain. When `RevertInstructions.FundRecipient` is not supplied, it falls back to `outbound.Sender`, which for non-EVM source chains (e.g. Solana, CAIP-2 `solana:*`) is canonicalized and stored as a base58 string, not a 20-byte EVM hex address. `common.HexToAddress` on a non-hex string does not fail; it silently produces an incorrect derived address, permanently misdirecting the refunded gas value — directly analogous to the PoolTogether report where a domain-incompatible refund address (a value with no meaningful counterpart in the target address space) causes irrecoverable loss of the excess fee.

### Finding Description
`Inbound.Canonicalize()` normalizes `Sender` per source-chain namespace: for `eip155:*` it forces a checksummed 20-byte EVM address, but for `solana:*` (and any other non-`eip155` namespace) it simply preserves the base58 pubkey via `canonicalizeSolanaValue` [1](#0-0) [3](#0-2) . This value flows unchanged into `OutboundTx.Sender` when building outbounds for `handleFailedOutbound`/`handleSuccessfulOutbound` [4](#0-3) .

`applyGasRefund` computes the excess gas fee and, when `RevertInstructions.FundRecipient` is empty, uses `outbound.Sender` as `refundRecipient`, then unconditionally converts it with `common.HexToAddress` [10](#0-9) . This resulting `recipientAddr` is passed to `CallUniversalCoreRefundUnusedGas`, which performs a real, committed `DerivedEVMCall` on Push Chain (via `refundUnusedGas`) that mints/deposits the refunded PRC20 or swaps it to native PC token at that address [6](#0-5) . No validation exists anywhere in this path that `refundRecipient` is a well-formed EVM hex string before conversion.

### Impact Explanation
For an outbound whose originating inbound came from a non-EVM chain and did not carry `RevertInstructions.FundRecipient` (an optional field, populated only if the event carried one, per `event_processor.go`'s `constructInbound`) [9](#0-8) , the excess gas-fee refund is deposited to an address derived from garbage/truncated bytes of the base58 sender string rather than to any address the depositor controls. This is a genuine, unprivileged-triggerable, protocol-level fund-misdirection (loss) bug: the refund logic runs unconditionally for both successful and failed outbounds (`handleFailedOutbound`/`handleSuccessfulOutbound` both call `applyGasRefund`) whenever `gasFee > gasFeeUsed`, and there is no way for the affected user (an ordinary depositor on a non-EVM chain) to reclaim the misdirected value once minted.

### Likelihood Explanation
Reachable purely through ordinary user deposit flows (GAS / GAS_AND_PAYLOAD / FUNDS_AND_PAYLOAD inbound types) from any registered non-`eip155` chain, with no privileged actor required — the only condition is that the inbound/outbound-triggering event does not carry an explicit `RevertInstructions.FundRecipient`, which is optional and thus can occur under normal (non-malicious) usage as well as be deliberately omitted by an attacker-controlled source-chain event.

### Recommendation
Before converting `refundRecipient` to an EVM address in `applyGasRefund` (and in `buildRevertOutbound`'s analogous fallback), validate that the value is a syntactically valid EVM hex address; if not (e.g., the sender's source-chain namespace is non-EVM and no explicit `FundRecipient` was provided), require the refund/revert flow to derive or require an explicit Push-Chain-valid recipient (e.g., the sender's mapped UEA address) rather than blindly calling `common.HexToAddress` on an arbitrary source-chain address string. Reject or abort (mark `ABORTED` with a clear reason) instead of silently sending to a wrong/garbage address.

### Proof of Concept
1. Register a `solana:*` chain and submit an inbound of `TxType_GAS_AND_PAYLOAD` whose `RevertInstructions.FundRecipient` is empty and whose `Sender` is a base58 Solana pubkey (e.g. `EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v`).
2. Reach quorum so the UTX/outbound is created with `OutboundTx.Sender` set to that base58 string [4](#0-3) .
3. Vote the outbound as observed with `gasFeeUsed < gasFee` (see `test/integration/uexecutor/gas_fee_refund_test.go` harness) to trigger `applyGasRefund` [11](#0-10) .
4. Observe that `common.HexToAddress("EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v")` produces a deterministic but unrelated 20-byte address (no error raised), and `CallUniversalCoreRefundUnusedGas` deposits the refunded value there — unrecoverable by the original Solana depositor.

// canonicalizeSolanaValue: hex inputs lowercase (0x kept); base58 inputs are
// charset-validated and preserved as-is (base58 is case-significant —

func canonicalizeSolanaValue(s string) (string, error) {
	s = strings.TrimSpace(s)
	if body, had0x := strip0x(s); had0x && len(body)%2 == 0 && isHexString(body) {
		return "0x" + strings.ToLower(body), nil
	}
	if isBase58String(s) {
		return s, nil
	}
	return "", fmt.Errorf("invalid solana value %q: neither 0x-hex nor base58", s)
}
