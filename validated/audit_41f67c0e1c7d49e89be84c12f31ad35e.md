Found it — a genuine, self-admitted proof-integrity gap in `ensure_match_transaction_info`.

### Title
`ensure_match_transaction_info` does not validate checkpoint hashes, allowing replay-verification to accept a divergent authenticated state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant check used by replay/backup-verification tooling (e.g. db-tool's `replay_on_archive`) to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` fetched from storage/network before it is accepted as correct. It checks status, gas used, write-set hash, and event root hash, but explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`.

### Finding Description [1](#0-0) 

The comment in the code itself documents the gap: [2](#0-1) 

```rust
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
```

`ensure_match_transaction_info` validates only `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash`, but performs no comparison for `txn_info.state_checkpoint_hash()`, the `hot_state_checkpoint_hash` (V1), or `position_state_checkpoint_hash` (V1) fields against locally computed values. These fields are exactly the Merkle roots produced during commit — the world-state SMT root, the hot-state root, and the newly introduced "trading-native" position-state root (`compute_trading_native_state_roots` / `hot_state_root_in_txn_info`, wired through `do_state_checkpoint.rs` and `do_ledger_update.rs`) — that are supposed to bind an authenticated `TransactionInfo` to the exact resulting ledger state.

Because these root-hash fields are excluded from the equality check, any consumer of `ensure_match_transaction_info` (replay/verification paths, e.g. `db-tool replay-verify`, or restore validation flows that use this method to sanity-check reconstructed outputs against trusted `TransactionInfo`s) will report a **successful match** even if the locally computed state-checkpoint root, hot-state root, or position-state root differs from the authenticated one stored in the `TransactionInfo`/accumulator. This directly breaks the "authenticated API/state-view output must stay bound to the right root" invariant called out in the task's proof/storage pivots, since it lets a divergent state root pass verification silently.

### Impact Explanation
This is a proof-integrity failure: a tool or node path that relies on `ensure_match_transaction_info` to validate reconstructed/replayed transaction outputs against authenticated `TransactionInfo` (fetched via state sync, backup, or replay-verify) will not catch a mismatch in the state checkpoint, hot-state, or position-state Merkle roots. This could mask a divergence between the locally executed state and the canonical committed state — exactly the "hard-fork-only divergence during replay/restore/proof verification" and "wrong accumulator/Merkle root accepted as valid" categories called out as in-scope, since the check silently accepts a corrupted or non-canonical root as consistent with the authenticated transaction record.

### Likelihood Explanation
The gap is deterministic and unconditional — it is not behind a flag; the comparator simply never inspects these three fields regardless of `compute_trading_native_state_roots`/`hot_state_root_in_txn_info` settings, as shown by `ensure_match_transaction_info`'s early `Ok(())` return with no comparisons of those hashes. Any legitimate replay-verify run that has a real divergence in the position/hot state root (e.g. due to a bug or corruption in the position-state or hot-state code paths, both of which are new/`TODO`-marked features in this codebase per the surrounding comments) would silently pass this check instead of failing loudly.

### Recommendation
Extend `ensure_match_transaction_info` to compute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the authenticated `TransactionInfo`) against the locally computed roots, returning an error on mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state-root features are relied upon in replay-verify or restore validation.

### Proof of Concept
Not independently exploitable as a standalone PoC without a companion bug that produces a divergent position/hot-state root; the root-cause artifact is the code itself: [1](#0-0)  shows the comparator omits all three checkpoint-hash fields, and the author's own TODO comment confirms that "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution." This is directly demonstrable by constructing two `TransactionOutput`/`TransactionInfo` pairs with identical write sets/events/gas/status but different `state_checkpoint_hash` (or V1 `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) — `ensure_match_transaction_info` will return `Ok(())` for both.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
