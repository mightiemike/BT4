## Title
DeleteAccount permanently burns the entire account balance when `beneficiary_id` does not exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
The external report flags an ERC721 bridge contract using `transferFrom` instead of `safeTransferFrom`, so a token sent to a target address that cannot handle it is permanently lost. The nearcore analog is `action_delete_account`, which sends the deleted account's entire remaining NEAR balance to an attacker/user-controlled `beneficiary_id` via a system refund receipt without ever checking whether that account exists. Because refund receipts are explicitly forbidden from implicitly creating an account, and a failed refund is burned rather than returned, any signer who submits `DeleteAccount` with a beneficiary that does not exist (typo, unregistered name, or an implicit account id whose owner never created it) permanently and irrecoverably destroys their own balance.

### Finding Description
`action_delete_account` computes the account's current balance and, if positive, pushes a system-refund receipt addressed to the caller-supplied `beneficiary_id`, with no existence check on that id at all: [1](#0-0) 

That receipt is a `Receipt::new_balance_refund`, i.e. `predecessor_id == "system"`, which is the refund path handled by `check_account_existence`/`implicit_creation_allowed`. Refunds are explicitly excluded from ever creating an account, for *any* account type: [2](#0-1) [3](#0-2) 

If the target `beneficiary_id` account does not exist, this `Transfer` action inside the refund receipt fails with `AccountDoesNotExist`, and the runtime's documented refund semantics state that a failed refund's deposit is burned rather than retried or returned to anyone: [4](#0-3) 

The nearcore test suite even documents this exact hazard as intentional/expected behavior, requiring test setups to pre-create the beneficiary account specifically to avoid the funds "coming straight back as a refund" (i.e., being burned): [5](#0-4) 

This is the direct structural analog of the ERC721 bug: value is moved to a caller-chosen destination without verifying that destination can actually receive it, and failure to receive results in permanent, unrecoverable loss of the asset (NEAR balance here, an NFT there) rather than a safe rejection/rollback that preserves the asset with the original owner.

### Impact Explanation
Any account holder who signs a `DeleteAccount` action with a mistyped, unregistered, or otherwise nonexistent `beneficiary_id` permanently burns their entire account balance. This is unauthorized, irreversible value destruction reachable by a single unprivileged transaction signer — no attacker, validator, or malicious peer involvement is required, only a user error (or a malicious relayer/dApp inducing a victim to sign a delete-account transaction with a bogus beneficiary). Given `DeleteAccount` is a routine, wallet-exposed action and NEAR account balances can be arbitrarily large, this is a concrete "permanently frozen/burned funds" impact matching the medium-severity class of the reported bug.

### Likelihood Explanation
This is triggered by a completely ordinary transaction (`DeleteAccount`) that any signer can submit at will; the only precondition is supplying a `beneficiary_id` that does not currently exist on-chain (e.g. an unregistered named account, or an implicit/derived account nobody has funded yet). No special privileges, races, or protocol-version gating are needed — the behavior is present in the current code path for every account type, always (`is_refund` unconditionally disables implicit creation for all `AccountType` variants). This makes the scenario easy to trigger accidentally (typo) and trivially exploitable via social engineering or a malicious front-end that fills in the beneficiary field.

### Recommendation
Before generating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` corresponds to an existing (or otherwise safely creatable) account, and reject the `DeleteAccount` action with a clear validation error (e.g., a new `ActionErrorKind::BeneficiaryAccountDoesNotExist`) if it does not — mirroring the "verify before you send, don't rely on a fallible fire-and-forget transfer" fix recommended for `safeTransferFrom`. Alternatively, allow the refund receipt to implicitly create implicit/deterministic/universal beneficiary accounts (as ordinary sender-funded transfers already do) instead of always burning on failure, so a nonexistent-but-legitimately-derivable beneficiary id does not result in fund destruction.

### Proof of Concept
1. Attacker/careless user controls (or is a legitimate) account `victim.near` holding `N` NEAR.
2. `victim.near` signs and submits a transaction with a single `DeleteAccount { beneficiary_id: "typo-name.near" }` action, where `typo-name.near` has never been created on-chain.
3. `action_delete_account` (`runtime/runtime/src/actions.rs:380-386`) removes `victim.near`'s account and enqueues `Receipt::new_balance_refund("typo-name.near", N)`.
4. When that system refund receipt is applied, `check_account_existence`/`implicit_creation_allowed` reject the `Transfer` because it is a refund receipt (`runtime/runtime/src/actions.rs:928-933`), producing `AccountDoesNotExist`.
5. Per the documented refund semantics (`docs/RuntimeSpec/Refunds.md:10-13`), the failed refund's `N` NEAR deposit is burned into `other_burnt_amount` rather than returned to `victim.near` or held anywhere recoverable — the funds are permanently and unrecoverably destroyed.
