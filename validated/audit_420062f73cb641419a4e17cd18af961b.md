# Finding: `save_transactions_impl` Persists `PersistedAuxiliaryInfo` Without Verifying It Matches `TransactionInfo.auxiliary_info_hash`

### Summary
`save_transactions_impl` in `storage/aptosdb/src/backup/restore_utils.rs` writes `persisted_aux_info`, `txn_infos`, and `write_sets` to three independent column families in the same loop-based pass, but never computes the hash of each `PersistedAuxiliaryInfo` entry and compares it against the corresponding `TransactionInfo`'s `auxiliary_info_hash` field before committing.

### Finding Description
`save_transactions_impl` iterates over the three input slices independently and calls the low-level per-CF writers directly: [1](#0-0) 

- `PersistedAuxiliaryInfoDb::put_persisted_auxiliary_info` simply serializes and puts the given `PersistedAuxiliaryInfo` at `version` with no hash check at all: [2](#0-1) 
- `TransactionInfoDb::put_transaction_info` is invoked immediately after, on the same index, but the code never cross-references `txn_info.auxiliary_info_hash` (or equivalent field) with a hash computed from `aux_info` at index `idx`.

I confirmed there is no verification call site anywhere outside `types/src/transaction/mod.rs` (the struct/hash-computation definition itself) that ties a `PersistedAuxiliaryInfo` value back to `auxiliary_info_hash` — searches across `storage/backup/backup-cli` (the restore/backup verification code that drives calls into `save_transactions`) returned no matches for `auxiliary_info_hash`, only for unrelated symbols (`save_transactions`, `write_set_hash`, etc.). This indicates the restore/backup pipeline that feeds untrusted backup-archive data (and the KV-replay/state-sync paths that reuse `save_transactions_impl`) has no external check either — the accumulator/ledger-info verification that authenticates `TransactionInfo` entries does not extend to `PersistedAuxiliaryInfo`, because `PersistedAuxiliaryInfo` is a separate column family introduced alongside the `auxiliary_info_hash` field of `TransactionInfo` but is not itself accumulator-proven; the only authenticity guarantee available is exactly this hash-equality check, which is never performed in this code path.

### Impact Explanation
If an untrusted or corrupted backup source (or a byzantine full-node during fast-sync/restore, or a replay input) supplies a `persisted_aux_info` slice whose entries don't hash-match the `auxiliary_info_hash` embedded in the already-signed `TransactionInfo`, the restoring node will silently persist a `PersistedAuxiliaryInfo` value that is inconsistent with the authenticated `TransactionInfo`. This causes the node's committed auxiliary info (used, e.g., for `transaction_shuffler`/replay determinism or randomness-related auxiliary data depending on what `PersistedAuxiliaryInfo` encodes) to diverge from what honest validators derived, even though the transaction accumulator, transaction hash, event root, and state root all remain nominally intact. This is a state-integrity corruption of a specific, distinctly-stored piece of committed ledger data that has no cross-check protecting it.

### Likelihood Explanation
Likelihood is limited by the fact that `save_transactions_impl`/`save_transactions` are only reachable from restore and replay/state-sync code paths, which are typically operator- or protocol-driven (backup files, chunk responses). Whether an *unprivileged* actor can supply the mismatched `persisted_aux_info` slice depends on whether the backup/replay pipeline that calls into these functions performs any independent hash check upstream (in `storage/backup/backup-cli`) — I was not able to fully confirm the entirety of `storage/backup/backup-cli/src/backup_types/transaction/restore.rs` in the remaining tool budget, only that it does not reference `auxiliary_info_hash` by name. I could not verify whether the accumulator-proof verification step in that file indirectly recomputes and validates the auxiliary info hash through another abstraction. This uncertainty should be resolved before treating this as a confirmed, exploitable, unprivileged-triggerable bug.

### Recommendation
Add an explicit check inside `save_transactions_impl` (or immediately before persisting) that recomputes the hash of each `PersistedAuxiliaryInfo` entry and asserts it equals `txn_infos[idx].auxiliary_info_hash()` (however that accessor is named), returning an `AptosDbError`/`ensure!` failure on mismatch, mirroring the pattern used for `confirm_or_save_frozen_subtrees_impl`'s hash-equality check.

### Proof of Concept
Conceptually: call `save_transactions_impl` (directly, or via `save_transactions`) with:
- `txn_infos[0].auxiliary_info_hash = H1`
- `persisted_aux_info[0]` = a value whose hash is `H2 != H1`

Then assert that `save_transactions_impl` returns `Ok(())` and the value stored via `PersistedAuxiliaryInfoDb::get_persisted_auxiliary_info(first_version)` is the corrupted `persisted_aux_info[0]`, rather than the function returning an error rejecting the mismatch — demonstrating that no cross-check exists in this function as written.
