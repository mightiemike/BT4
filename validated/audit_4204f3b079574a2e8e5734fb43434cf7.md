## Analysis

The external report's root cause — the EVM layer returning `gasRemaining == 0` (or equivalently, zero gas charged) for a failed call that is *not* a genuine out-of-gas condition (stack overflow, invalid jump, invalid opcode) — has a direct structural analog in Push Chain's gas-fee accounting for module-originated/derived EVM calls.

### Title
Zero-`GasUsed` EVM receipts silently skip fee collection in `DeductGasFeesFromReceipt`, enabling free repeated EVM execution via `MsgExecutePayload` - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`DeductGasFeesFromReceipt` treats any receipt with `GasUsed == 0` as equivalent to "no EVM transaction was created" and skips fee collection entirely [1](#0-0) . This conflates two different situations: (1) a Go-level error before any EVM work happened (receipt is `nil`), and (2) a receipt that is non-`nil` but reports `GasUsed == 0` because the underlying EVM execution hit an error class that the tracer/executor doesn't bill for — exactly the stack-overflow / invalid-jump / invalid-opcode class described in the referenced minievm H-07 finding.

### Finding Description
Push Chain's `CallUEAExecutePayload` dispatches a real, committed EVM transaction from the user's derived EVM address to their UEA contract, executing arbitrary attacker-controlled `to`/`data` via `executeUniversalTx` [2](#0-1) . This flows through `DerivedEVMCall` on the forked `cosmos-evm` engine (`github.com/pushchain/evm`) [3](#0-2) .

`ExecutePayloadV2` wraps this call plus fee collection in a `CacheContext`, and explicitly documents that `DeductGasFeesFromReceipt` is a no-op "if the receipt is nil or GasUsed == 0 (EVM call produced nothing to bill)" [4](#0-3) . The actual guard is:

```go
if receipt == nil || receipt.GasUsed == 0 {
    return nil
}
``` [5](#0-4) 

This assumes `GasUsed == 0` only happens when "no EVM tx was created" (per the function doc comment on lines 95-96). That assumption is false for the exact bug class in the source report: cosmos-evm-family engines can return a non-`nil` receipt with `GasUsed == 0` after real, resource-consuming execution when the interpreter hits an error that isn't `ErrOutOfGas` (stack overflow from unbounded recursion, invalid jump destination, invalid opcode). In the original minievm code this was an explicit special-case check (`gasRemaining == 0 && err != nil && err != vm.ErrOutOfGas`) that early-returned without charging gas. Push Chain's fork of the same EVM execution lineage is exposed through the identical `DerivedEVMCall`/receipt path, and this repo's own accounting code (`fees.go`) is written to *trust* `GasUsed` as the sole billing signal, with an explicit skip-if-zero branch that has no secondary sanity check (e.g., "was `err` an EVM execution error vs a Go-level construction error").

Since the attacker fully controls the target contract deployed behind their own UEA payload `to`/`data`, they can engineer a callee that reliably trips this bug class (deep recursion to exhaust the Go call stack / interpreter stack, or an invalid jump), causing the derived tx to actually execute (consuming node CPU and possibly writing/reverting EVM state) while the resulting receipt reports `GasUsed == 0`. `DeductGasFeesFromReceipt` then charges nothing, and the outer `writeCache()` only fires when `execErr == nil` — but note the fee-skip happens independent of `execErr`, so a repeatable failure path exists at zero cost per attempt.

### Impact Explanation
This falls under the allowed impact of gas-fee accounting corruption and unprivileged denial-of-service: an attacker can repeatedly submit `MsgExecutePayload` transactions (a gasless-eligible, user-reachable message per Push Chain's gasless whitelist policy note in the codebase) that trigger real, uncharged EVM computation on every Universal Validator/full node, without ever paying the `upc` gas fee that `DeductGasFeesFromReceipt` is meant to collect. This can be used to burn node CPU/resources for free, repeatedly, which is the same "DoS via gas-free EVM calls" impact as the source H-07 finding.

### Likelihood Explanation
Likelihood depends on whether the underlying `github.com/pushchain/evm` fork still exhibits the same `gasRemaining==0`/non-`ErrOutOfGas` behavior that motivated the original minievm fix. That engine's source is external to this repository and could not be directly inspected here, so I cannot confirm the exact trigger condition inside the fork. However, the accounting-side bug in `fees.go` — treating `GasUsed == 0` as always meaning "nothing happened" — is present and verifiable in this repo, and is the same brittle assumption that caused the original vulnerability's impact (no gas charged) to matter at all.

### Recommendation
- Do not use `receipt.GasUsed == 0` alone as the signal to skip fee collection in `DeductGasFeesFromReceipt` (`x/uexecutor/keeper/fees.go`); distinguish "receipt is nil / call never entered the EVM" from "receipt exists but reports zero gas used after real execution."
- Confirm with the `pushchain/evm` fork maintainers whether `DerivedEVMCall`/`ApplyMessage`-equivalent code paths can produce a non-nil receipt with `GasUsed == 0` on stack-overflow/invalid-jump/invalid-opcode errors (mirroring the pre-fix minievm behavior), and if so, ensure gas is always charged/reflected in the receipt regardless of the specific EVM error.
- Add a minimum/floor gas charge (e.g., charge the tx's declared `gasLimit` or a sane floor) whenever `execErr != nil` but the call demonstrably entered EVM execution, rather than relying purely on `receipt.GasUsed`.

### Proof of Concept
A concrete PoC requires reproducing the same stack-overflow trigger against `github.com/pushchain/evm`'s tracer/execution path (unavailable in this repository's index) to confirm it yields `GasUsed == 0` on a non-nil receipt, analogous to the original minievm PoC contract with `triggerStackOverflow()`. The exploitable path in this repo is: deploy a UEA-callable contract containing unbounded self-recursion, submit `MsgExecutePayload` targeting it via `CallUEAExecutePayload` → `ExecutePayloadV2` → `DeductGasFeesFromReceipt`, and observe whether `receipt.GasUsed == 0` while `execErr != nil`, in which case no `upc` is deducted despite real EVM execution having occurred [6](#0-5) [5](#0-4) .

// CallUEAExecutePayload executes a universal payload through UEA
func (k Keeper) CallUEAExecutePayload(
	ctx sdk.Context,
	from, ueaAddr common.Address,
	universal_payload *types.UniversalPayload,
	verificationData []byte,
) (*evmtypes.MsgEthereumTxResponse, error) {
	abi, err := types.ParseUeaABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UEA ABI")
	}

	abiUniversalPayload, err := types.NewAbiUniversalPayload(universal_payload)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal payload")
	}

	gasLimit := new(big.Int)
	gasLimit, ok := gasLimit.SetString(universal_payload.GasLimit, 10)
	if !ok {
		return nil, fmt.Errorf("invalid gas limit: %s", universal_payload.GasLimit)
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,
		ueaAddr,
		big.NewInt(0),
		gasLimit,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"executeUniversalTx",
		abiUniversalPayload,
		verificationData,
	)
}
