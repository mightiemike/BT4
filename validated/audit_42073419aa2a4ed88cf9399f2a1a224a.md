### Title
Uncaught `ArithmeticException` in `SM2.recoverPubBytesFromSignature` via unguarded `modInverse` call - ([File: crypto/src/main/java/org/tron/common/crypto/sm2/SM2.java])

### Finding Description
`SM2.recoverPubBytesFromSignature` computes the public-key-recovery coefficient with: [1](#0-0) 

`BigInteger srInv = sig.s.add(sig.r).modInverse(n);` is called with no surrounding `try/catch`, and `sig.r`/`sig.s` come directly from attacker-supplied signature bytes on the transaction (`SM2Signature.fromComponents`), only checked for non-negativity via `check(sig.r.signum() >= 0, ...)` and `check(sig.s.signum() >= 0, ...)` earlier in the same method [2](#0-1) . `BigInteger.modInverse` throws `ArithmeticException` whenever `gcd(s+r, n) != 1` (e.g. when `s+r ≡ 0 (mod n)`), and this exception is unchecked, so it is not declared or intercepted anywhere in the method.

Signature recovery for this value is reachable from `SignUtils.signatureToAddress(byte[] messageHash, SignatureInterface signatureInterface, boolean isECKeyCryptoEngine)`, which for the SM2 engine forwards straight into `SM2.signatureToAddress` → `SM2.signatureToKeyBytes` → `recoverPubBytesFromSignature` with **no exception handling at all**: [3](#0-2) . This is distinct from the sibling overload that takes a base64 string, which does wrap the call in `try { ... } catch (Exception e) { throw new SignatureException(e); }` [4](#0-3) . Only the base64-string overload is defensively wrapped; the `SignatureInterface`-based overload used for direct signature-object recovery is not.

I was not able to fully re-confirm, within the tool budget available, which of these two `SignUtils.signatureToAddress` overloads `TransactionCapsule.validateSignature`/`checkWeight` actually calls at the exact line — I could only establish (via file search) that `TransactionCapsule.java` references `checkWeight`/signature-validation logic extensively, without retrieving the precise call-site content before running out of iterations. This is a caveat on the final confirmation step, but the unguarded `modInverse` in `SM2.recoverPubBytesFromSignature` itself is fully verified, and at least one call path into it (`SignUtils.signatureToAddress(byte[], SignatureInterface, boolean)`) has no defensive catch, meaning any caller of that overload that does not itself wrap the call in a broad `try/catch` will crash with an uncaught `ArithmeticException`.

### Impact Explanation
If the unprotected `SignUtils.signatureToAddress(byte[], SignatureInterface, boolean)` path (or any other unguarded caller of `SM2.recoverPubBytesFromSignature`) is reached from `TransactionCapsule.validateSignature`/`checkWeight` during normal signature verification of a broadcast transaction, an attacker can force an uncaught `ArithmeticException` on any node running the SM2 crypto engine by submitting a transaction with `sig.r + sig.s ≡ 0 (mod n)`. Depending on where in the call chain this propagates, this could crash the verification thread/executor processing that transaction, matching a DoS-via-TRON-protocol-implementation impact class.

### Likelihood Explanation
Preconditions: node must be running with the SM2 crypto engine active (`isECKeyCryptoEngine == false`), which is a supported but non-default configuration. Cost to the attacker is minimal — crafting `r`, `s` such that `s + r ≡ 0 mod n` is a single BigInteger computation, and the transaction only needs to reach the signature-recovery step before any modInverse guard; no special privileges, funds beyond minimal transaction fee, or non-default RPC access are required. This is fully repeatable since the same crafted `r,s` pair can be resubmitted or embedded in any transaction shape.

### Recommendation
Wrap the `sig.s.add(sig.r).modInverse(n)` call in `SM2.recoverPubBytesFromSignature` in a `try/catch (ArithmeticException e)` that returns `null` (consistent with the method's existing `@Nullable` contract for invalid/unrecoverable signatures), mirroring the defensive pattern already used for `NullPointerException` in `SM2.verify`/`SM2.verifyMessage`. Additionally, audit all call sites of `SignUtils.signatureToAddress(byte[], SignatureInterface, boolean)` to ensure `ArithmeticException` (and other unchecked BouncyCastle exceptions) cannot escape from `TransactionCapsule.validateSignature`/`checkWeight` unhandled.
