### Title
Hardcoded fixed-Tgas callback budgets in the NEAR Wallet Contract don't scale with attacker-controlled list sizes, risking permanent `has_in_flight_tx` deadlock - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract` (the eth-implicit account emulation contract that turns RLP-encoded Ethereum transactions into NEAR cross-contract promise chains, functionally analogous to the reported LayerZero cross-chain relay) hardcodes fixed gas budgets for its own callback continuations instead of estimating them from the size of the action being relayed.

### Finding Description
`inner_rlp_execute` and its callbacks compute the gas to attach to callback continuations using fixed constants defined at the top of the file: [1](#0-0) 

These constants (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, each derived from `Gas::from_tgas(5)`) are combined with `action.gas()` to set the gas budget for a callback function (e.g. `address_check_callback`, `nep_141_storage_balance_callback`): [2](#0-1) [3](#0-2) 

Critically, `Action::gas()` (used as the size-scaling component) is a *fixed* 2 Tgas for every non-`FunctionCall` action, regardless of the actual size of the action's data: [4](#0-3) 

However, the `AddKey` action can carry an attacker/relayer-controlled `FunctionCallPermission.method_names: Vec<String>` of unbounded length (parsed from the RLP-encoded Ethereum transaction): [5](#0-4) 

That list is serialized/joined and used to build the outgoing `add_access_key_allowance_with_nonce` promise **inside** the callback itself, from the callback's own fixed prepaid-gas budget: [6](#0-5) 

Because the "size-scaling" term (`action.gas()`) is hardcoded to 2 Tgas irrespective of `method_names.len()`, and the WASM execution cost of joining/serializing that list inside the callback grows with its length, a sufficiently large `method_names` list can exhaust the callback's fixed gas budget (`ADDRESS_CHECK_CALLBACK_GAS` = 10 Tgas + 2 Tgas fixed = 12 Tgas total) before the callback finishes, causing the callback's own execution to abort with `GasExceeded`.

### Impact Explanation
`self.has_in_flight_tx` is set to `false` at the *start* of `address_check_callback`/`nep_141_storage_balance_callback`, but state mutations from a function call that aborts (panics/out-of-gas) are rolled back entirely: [7](#0-6) 

If the callback aborts due to insufficient hardcoded gas, `has_in_flight_tx` remains permanently `true` (it was set `true` when the original promise was dispatched in `rlp_execute`), and no other logic ever resets it. Every subsequent call to `rlp_execute` short-circuits with the "transaction already in progress" error: [8](#0-7) 

This permanently and irrecoverably locks the eth-implicit account out of processing any future relayed Ethereum-emulated transactions, which is the wallet-contract's sole mechanism for that account to act — effectively freezing that account's usable balance/functionality on-chain, mirroring the "loss of cross-chain deployment" impact in the source report.

### Likelihood Explanation
Likelihood is Medium: it requires a relayer/attacker to submit (or an honest relayer to be tricked into forwarding) an RLP-encoded Ethereum transaction whose decoded action is an `AddKey` with `address_check: Some(_)` (i.e. targeting an eth-implicit account not yet confirmed via the registrar) and an unusually large `method_names` list, sized so total callback WASM work (string join, serde, promise construction) exceeds the fixed budget. This is a bounded, deterministic input a submitter fully controls, requiring no validator collusion — only a single crafted transaction/RLP payload.

### Recommendation
Do not hardcode `Action::gas()` to a flat 2 Tgas for `AddKey` (or any action carrying variable-length, attacker-supplied data such as `method_names`). Scale the gas estimate with the size of the data being processed (e.g., proportional to `method_names` byte length, mirroring how protocol-level actions charge `*_byte` fees per length). Additionally, make `has_in_flight_tx` recoverable: e.g., only set it to `false` at the very end of successful callback execution, or add a way to detect/clear a stuck in-flight flag (such as a time-based or nonce-based unlock) rather than relying entirely on best-effort callback completion.

### Proof of Concept
1. Deploy the `WalletContract` for an eth-implicit account `A`, associate it with an Ethereum private key.
2. Craft an RLP-encoded Ethereum transaction whose decoded NEAR action is `AddKey` with `access_key.permission = FunctionCall { method_names: <very large Vec<String>>, .. }`, with `target` set so `address_check: Some(address)` is triggered (target is another eth-implicit account not yet in the registrar).
3. Submit via `rlp_execute(target, tx_bytes_b64)`. This sets `has_in_flight_tx = true` and dispatches the registrar lookup promise with `.then(address_check_callback(...))`, where `address_check_callback` is funded with `ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas())` = 10 Tgas + 2 Tgas (fixed, independent of list size).
4. When the registrar lookup resolves (`maybe_account_id.is_none()`), `address_check_callback` attempts to build `action_to_promise(target, action)`, which serializes/joins the large `method_names` list — this WASM computation, funded only from the fixed 12 Tgas budget, exceeds the budget and the callback aborts with `HostError::GasExceeded`.
5. Because the abort rolls back all of `address_check_callback`'s state changes (including the `has_in_flight_tx = false` reset at its start), `has_in_flight_tx` remains `true` forever.
6. Any subsequent call to `rlp_execute` for account `A` now permanently returns `"Error: transaction already in progress, please try again later."`, freezing the account's ability to relay any further Ethereum-emulated transactions.

Note: I was not able to fully trace every downstream constraint (e.g., protocol-level `max_gas_burnt`/`max_total_prepaid_gas` limits or NEAR SDK-imposed method_names length caps) that might further bound or prevent this exact PoC from near-primitives level; a background Devin session with full repository/test access would be needed to confirm the exact `method_names` list size required to trigger `GasExceeded` and to validate the deadlock end-to-end via test-loop integration tests.

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
    }
