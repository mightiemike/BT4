### Title
`ValidateMultiSign`/`BatchValidateSign` TVM precompiles omit chain ID from the signed digest, enabling cross-chain signature replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `validatemultisign(address,uint256,bytes32,bytes[])` and `batchvalidatesign` TVM precompiled contracts let any Solidity contract on TRON verify off-chain ECDSA signatures against an account's on-chain `Permission` weights. The digest that signers must sign is built purely from `address || permissionId || data`, with no chain-specific value mixed in, so a valid signature produced for one TRON network can be replayed verbatim on any other TRON-compatible network that hosts the same account/permission configuration.

### Finding Description
`ValidateMultiSign.execute` recovers the digest to be checked as: [1](#0-0) 

`combine = address || permissionId || data`, then `hash = Sha256Hash.hash(combine)`. This hash is what off-chain signers actually sign, and it is later used with `recoverAddrBySign` to check weighted signatures against the account's `Permission`: [2](#0-1) 

The same pattern (no chain-binding value in the signed message) is used by the sibling precompile `BatchValidateSign`: [3](#0-2) 

The unit test confirms exactly what gets signed off-chain — `sha256(address || permissionId || data)` — with no chain ID or other domain-separating value included: [4](#0-3) 

TRON account addresses are deterministically derived from the signer's private key independent of network, and identical `Permission` configurations (and identical contract deployments) frequently exist across TRON mainnet, testnets (Shasta/Nile), and forked/private TRON-based chains that share the same genesis tooling. Because the precompile's digest has no domain separator (no chain ID, no consuming-contract address, no nonce baked in by the protocol itself), any consuming dApp that relies on `validatemultisign`/`batchvalidatesign` purely for meta-transaction/authorization purposes — without independently embedding a chain ID and nonce inside the `data` parameter — is exposed to replay of a signature across any other TRON-compatible chain where the same address/permission state exists. This mirrors the reported Forwarder bug class: a signature-verification digest that lacks (or fails to bind/validate) chain-specific context, permitting cross-chain replay of authenticated requests.

### Impact Explanation
Any smart contract built on TRON that uses `validatemultisign`/`batchvalidatesign` as its authorization mechanism (e.g., gasless meta-transactions, multisig wallets, cross-chain bridges, custodial approval flows) inherits this weakness unless the contract author manually folds a chain ID/nonce into `data`. An attacker who captures a signature authorized on one TRON network can replay it on a different TRON network/fork hosting the same account and permission, causing unauthorized execution of privileged actions — a concrete authorization/accounting-bypass impact consistent with "High" severity replay findings.

### Likelihood Explanation
Exploitation requires that the same account address and permission set exist on two TRON-compatible networks (mainnet vs. testnet, or a forked/sidechain deployment) and that the consuming contract does not itself add chain-specific data — a realistic and common situation for dApps that deploy identical contracts/config to mainnet and test/side networks for staging or multi-chain operation. The attack itself needs no privileged role: any observer of a broadcast transaction/signature can attempt replay on the other chain.

### Recommendation
Modify the digest construction in `ValidateMultiSign.execute` and `BatchValidateSign.doExecute` (and document the change for all TVM contracts relying on these precompiles) to mix in a chain-binding value — e.g. `combine = address || permissionId || chainId || data` — so a signature is only valid for the specific chain it was produced for. Alternatively/additionally, update documentation to mandate that all consumers embed `block.chainid` (via the TVM `CHAINID` opcode, already exposed per `AllowTvmCompatibleEvmTest#testChainId`) inside `data` before signing, and provide a reference implementation to reduce misuse. [5](#0-4) 

### Proof of Concept
1. Deploy the same permission-checking contract (using `validatemultisign`) with identical bytecode/address and an identical account `Permission` on TRON mainnet and on a TRON-based testnet/fork.
2. A user signs `sha256(address || permissionId || data)` off-chain to authorize a specific privileged action on mainnet, as shown in the test helper `ValidateMultiSignContractTest#testDifferentCase` (lines 104-125) which builds and signs exactly this digest.
3. An attacker observes/captures the signature (e.g., from a broadcast transaction calling the mainnet contract).
4. The attacker submits the identical `(address, permissionId, data, signatures)` tuple to the equivalent contract on the testnet/fork network. Because the precompile's digest never included a chain-specific value, `ValidateMultiSign.execute` returns success (`DataWord.ONE()`), authorizing the same privileged action on the second chain without the signer's consent for that network.
