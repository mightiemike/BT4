### Title
Inconsistent TRON Power (voting balance) computation across VoteWitness/UnfreezeBalanceV2 actuators and their TVM-native counterparts - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java])

### Summary
Analogous to the reported `balanceOfNFT`/`balanceOfNFTAt`/`_balanceOfNFT` inconsistency in VotingEscrow (where different entry points compute "the same" voting balance differently), java-tron has a directly comparable divergence: the "TRON Power" value that backs an account's votes (`getTronPower()` vs `getAllTronPower()`) is selected using inconsistent gating conditions across the different code paths that read or mutate votes.

### Finding Description
Four/five related locations decide whether to use `AccountCapsule.getTronPower()` (legacy, resource-frozen-balance based) or `AccountCapsule.getAllTronPower()` (post-migration, `oldTronPower` + TRON_POWER-type frozen balances) [1](#0-0) :

- `VoteWitnessActuator.validate()` (regular transaction path) gates the switch on a single flag, `supportAllowNewResourceModel()`: [2](#0-1) 

- `UnfreezeBalanceV2Actuator.updateVote()` (regular transaction path) uses the same single-flag condition: [3](#0-2) 

- `UnfreezeBalanceV2Processor.updateVote()` — the TVM/native-contract equivalent invoked when a smart contract calls `unfreezeBalanceV2`/`unfreeze()` — also uses only the single flag `supportAllowNewResourceModel()`: [4](#0-3) 

- But `VoteWitnessProcessor.execute()` — the TVM native-contract path invoked when a smart contract calls `vote()` — requires **both** flags (`supportUnfreezeDelay() && supportAllowNewResourceModel()`) before using `getAllTronPower()`: [5](#0-4) 

- And the `TotalVoteCount` precompiled contract (`totalVoteCount(address)`, callable by any smart contract to query an account's voting capacity) also requires **both** flags: [6](#0-5) 

`supportUnfreezeDelay()` and `supportAllowNewResourceModel()` are independent, separately-activated proposal switches persisted in `DynamicPropertiesStore` (each referenced independently across `FreezeBalanceActuator`, `FreezeBalanceV2Actuator`, `DelegateResourceActuator`, `UnDelegateResourceActuator`, `WithdrawExpireUnfreezeActuator`, etc.), meaning there is a real, reachable network state where `supportAllowNewResourceModel()==true` while `supportUnfreezeDelay()==false` (this is the normal sequential order in which these hard-fork proposals get activated on-chain).

In that window, for the exact same account and exact same on-chain state:
- `UnfreezeBalanceV2Processor.updateVote()` (TVM `unfreezeBalanceV2`) computes `ownedTronPower` via `getAllTronPower()`.
- `VoteWitnessProcessor.execute()` (TVM `vote()`) and the `TotalVoteCount` precompile compute the comparable quantity via `getTronPower()` (a different, generally smaller/differently-composed value, since it sums bandwidth/energy frozen balances rather than the TRON_POWER-type frozen balance + historical `oldTronPower`).

This is the same bug class as the reported VotingEscrow issue: multiple entry points that are supposed to report/enforce the same underlying "voting balance"/"voting power" invariant diverge because the flash-loan-style/anti-inconsistency guard (here, the flag-gating condition selecting the power-accounting formula) is applied inconsistently.

### Impact Explanation
The divergence directly affects vote-scaling correctness after an unfreeze and the on-chain vote tally used for Super Representative (witness) election, which is a core state/accounting/settlement path (`Wallet.countVote()` sums whatever `VotesCapsule` new/old vote records exist) [7](#0-6) . Because `UnfreezeBalanceV2Processor.updateVote()` may decide "tron power still enough, no need to scale down votes" using a different formula (`getAllTronPower()`) than what `VoteWitnessProcessor`/`TotalVoteCount` would compute for the same state, votes recorded for an account can remain inconsistent with the account's actually-enforced voting capacity as evaluated by the vote-casting path. This is an accounting/state divergence in the consensus-relevant vote-count data, not merely a read-only query mismatch, since the affected function (`updateVote`) mutates `VotesCapsule`/`AccountCapsule` state that feeds directly into SR election results.

### Likelihood Explanation
The divergence is deterministic and requires no privileged access — any unprivileged account that freezes/unfreezes TRON_POWER-type balance and votes via a smart contract (through the TVM freeze/vote/unfreeze precompiles) can trigger the code paths that use the two different formulas. The only precondition is that the chain currently has `AllowNewResourceModel` enabled but `UnfreezeDelay` not yet enabled (or another combination producing divergent flag states), which is a standard and expected intermediate state during proposal rollouts rather than a contrived edge case.

### Recommendation
Standardize the gating condition for choosing between `getTronPower()` and `getAllTronPower()` across all vote-power-related code paths — `VoteWitnessActuator`, `UnfreezeBalanceV2Actuator`, `VoteWitnessProcessor`, `UnfreezeBalanceV2Processor`, and the `TotalVoteCount` precompile — so they all use the identical condition (either both flags, matching `VoteWitnessProcessor`/`TotalVoteCount`, or a single flag, matching `VoteWitnessActuator`/`UnfreezeBalanceV2Actuator`), and add regression tests asserting equal outputs across the TVM and non-TVM code paths for the same account state.

### Proof of Concept
1. Activate proposal `AllowNewResourceModel` on-chain while leaving `UnfreezeDelay` inactive (an intermediate, achievable state on the migration path, per `DynamicPropertiesStore` flags referenced in `FreezeBalanceV2Actuator`/`UnfreezeBalanceV2Actuator`/`DelegateResourceActuator`).
2. Have an account freeze TRON_POWER-type balance (contributing to `getTronPowerFrozenV2Balance()`), and separately have a historical `oldTronPower` recorded, then vote for a witness up to the `getAllTronPower()` threshold via a normal `VoteWitnessContract` (which in this flag state uses `getAllTronPower()` per `VoteWitnessActuator.validate()` line 131).
3. From a smart contract, call `unfreezeBalanceV2` (triggers `UnfreezeBalanceV2Processor.updateVote()`, line ~250, using `getAllTronPower()` under the same flag condition) to partially unfreeze TRON_POWER; the check `ownedTronPower >= totalVote * TRX_PRECISION` uses `getAllTronPower()`, potentially concluding votes need not be scaled down.
4. From a smart contract, call `totalVoteCount(owner)` (the `TotalVoteCount` precompile, gated on both flags) or attempt to `vote()` via `VoteWitnessProcessor` (also gated on both flags): both return/enforce `getTronPower()` instead, a differently-composed and generally smaller value — demonstrating the account's recorded votes (unchanged by step 3) are inconsistent with the tron power reported/enforced by the TVM vote path, evidencing the accounting divergence.

  public long getTronPower() {
    long tp = 0;
    for (int i = 0; i < account.getFrozenCount(); ++i) {

    }

    tp += account.getDelegatedFrozenV2BalanceForBandwidth();
    tp += account.getAccountResource().getDelegatedFrozenV2BalanceForEnergy();
    return tp;
  }

  public long getAllTronPower() {
    if (account.getOldTronPower() == -1) {
      return getTronPowerFrozenBalance() + getTronPowerFrozenV2Balance();
    } else if (account.getOldTronPower() == 0) {
      return getTronPower() + getTronPowerFrozenBalance() + getTronPowerFrozenV2Balance();
    } else {
      return account.getOldTronPower() + getTronPowerFrozenBalance()
          + getTronPowerFrozenV2Balance();
    }
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
