I now have enough evidence to provide a definitive analog analysis.

The strongest and clearest analog to the Notional "debt cap bypass via independent target formula" bug is the documented `try_forward` size-clamp workaround in `runtime/runtime/src/congestion_control.rs`, combined with the receipt-size-limit validation gap described in `test-loop-tests/src/tests/max_receipt_size.rs`. This is a known, self-documented issue (near/nearcore#12606) where a hard cap (`max_receipt_size`) is validated at receipt-creation time, but a *separate* downstream mutation path (`output_data_receivers` / large returned values appended after validation) lets the actual receipt size exceed that same cap — exactly mirroring the Notional pattern where cap enforcement happens at one computation point but a different code path pushes the real value past it without re-checking.

### Title
Receipt size can exceed `max_receipt_size` after post-validation mutation, bypassing the size cap used for congestion/bandwidth admission - (File: runtime/runtime/src/congestion_control.rs)

### Summary
`max_receipt_size` is enforced by `validate_receipt` when a receipt is first created, but `output_data_receivers` (added when a promise result is returned to a waiting callback) and large returned values are appended to the receipt *after* that validation point, so the final, on-the-wire receipt can be larger than `max_receipt_size` [1](#0-0) . Downstream, congestion control's forwarding logic silently "pretends" any oversized receipt is exactly `max_receipt_size` for admission accounting rather than rejecting or re-validating it [2](#0-1) .

### Finding Description
This is directly analogous to the Notional `PrimeSupplyCap`/`ExternalLending` bug: a hard cap (`max_receipt_size`, this repo's equivalent of `maxUnderlyingDebt`) is computed/checked at one point, but a separate, later code path (appending `output_data_receivers` or large return values, this repo's equivalent of the `targetExternalUnderlyingLend` formula) produces a final value that is not re-checked against that same cap. The receipt validation in `validate_receipt` runs only at creation/receipt-admission time and does not run again after `output_data_receivers`/large-value mutations are applied, so the invariant "no receipt exceeds `max_receipt_size`" is not actually enforced end-to-end [1](#0-0) .

The bandwidth/congestion admission code in `try_forward` explicitly documents this as a known bug and works around it by clamping the *believed* size to `max_receipt_size` for the purpose of gas/size accounting, rather than actually preventing propagation of the oversized receipt [2](#0-1) . Because `outgoing_receipts_usual_size_limit`/`outgoing_receipts_big_size_limit` and the bandwidth-request generation logic are all built on the assumption that no receipt exceeds `max_receipt_size` (the same invariant used to size-bound `ChunkStateWitness`), an oversized receipt slipping through the cap silently inflates the real payload beyond what the size-based admission math accounts for [3](#0-2) .

### Impact Explanation
`max_receipt_size` is one of the load-bearing invariants behind the entire `ChunkStateWitness` size budget (~21 MiB total), which chunk validators rely on to bound proof/receipt data they must download and verify [4](#0-3) . If a receipt can grow past `max_receipt_size` after passing validation, and the forwarding/admission layer only "pretends" it's within bounds instead of rejecting it, the actual bytes moved through `outgoing_receipts`/`source_receipt_proofs` and ultimately embedded in `ChunkStateWitness` can exceed the sizes the protocol was designed to bound. This directly threatens witness-size guarantees that stateless validation depends on, and — since it is a deterministic, protocol-level bug reachable by any account calling a contract that returns large values or does a promise-return with populated `output_data_receivers` — it is reachable purely via a transaction/contract call, not any privileged or network-level actor [5](#0-4) .

### Likelihood Explanation
This is not a hypothetical: it is an already-known, tracked bug (issue #12606) reproduced by dedicated regression tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`) showing that a normal user transaction — deploying a standard contract and calling a method that returns a large value or performs a promise-return DAG — produces a receipt whose final size exceeds `max_receipt_size`, and that the runtime does not reject it, instead silently clamping it for admission-accounting purposes [6](#0-5) . No special privileges, validator collusion, or network-level manipulation are required — a single signed transaction from any account is sufficient to trigger it.

### Recommendation
Re-validate the final constructed receipt (including any `output_data_receivers` and returned-value mutations applied after the initial `validate_receipt` call) against `max_receipt_size` before it is queued for forwarding/buffering, and reject/fail the receipt if it exceeds the limit rather than clamping the perceived size in `try_forward`. This closes the gap between the size cap that is checked and the actual size that is later propagated, mirroring the fix recommended for the Notional debt-cap bug: enforce the same cap consistently across every code path that can influence the underlying value, not just the primary validation entry point.

### Proof of Concept
The existing regression tests in-repo already demonstrate the bug end-to-end: `test_max_receipt_size_promise_return` constructs a promise DAG where a receipt is exactly `max_receipt_size` at creation, and a later `output_data_receivers` mutation pushes it over the limit; `test_max_receipt_size_value_return` has a contract return a value equal to `max_receipt_size`, which is then wrapped in a data receipt exceeding the limit. Both tests assert (`assert_oversized_receipt_occurred`) that an oversized receipt does show up on-chain rather than being rejected, confirming the cap is bypassed [7](#0-6) .

```markdown
## State witness size limits

Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 21MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.
```

```markdown
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
```
