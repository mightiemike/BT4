### Title
Front-Runnable Human-Readable AccountId Claim in `SetAccountIdActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java`)

### Summary
The `SetAccountIdContract` transaction lets any account claim an arbitrary, attacker-chosen byte-string `accountId` (a human-readable alias resolvable via `GetAccountById`), and the check that the id is still free is performed only at validation time against a first-come-first-served index. This mirrors the `enrollCourier()` bug class: a unique identifier that a permissionless caller can select is protected only by an "if unused" check, so it can be claimed by an observer who front-runs the pending transaction, permanently denying the original claimant that id.

### Finding Description
`SetAccountIdActuator.validate()` requires that the target account has not yet set an id and that the chosen `accountId` is not already present in `AccountIdIndexStore`: [1](#0-0) 

`execute()` then unconditionally binds the caller-supplied `accountId` to the sender's address and writes it into both `AccountStore` (`account.setAccountId(...)`) and the permanent `AccountIdIndexStore` index: [2](#0-1) 

Once set, the binding is immutable: the actuator explicitly rejects any later attempt to change an already-set id ("This account id already set"), and rejects re-use of an already-claimed id ("This id has existed") — proven by the actuator test asserting these exact failure paths: [3](#0-2) [4](#0-3) 

`AccountIdIndexStore` performs case-insensitive lowercasing of the id but otherwise stores it as a simple first-write-wins key→address mapping with no allocation/ordering mechanism and no fee scaling with contention: [5](#0-4) 

Because pending transactions are visible in the mempool before inclusion in a block, an attacker monitoring the network for a `SetAccountIdContract` with a desirable `accountId` can submit a competing transaction with the same `accountId` (case-insensitively) and a higher fee/priority. The attacker's transaction gets mined first, `couriers`-equivalent state (`AccountIdIndexStore`) is populated for that id, and the original user's transaction subsequently fails validation with `ContractValidateException("This id has existed")`, exactly analogous to the `require(couriers[id].cut == 0)` front-running described in the report.

### Impact Explanation
This is a concrete, reachable state/accounting integrity issue for an unprivileged, permissionless actuator (`SetAccountIdContract` is executable by any account via `SetAccountIdServlet`/gRPC with no privilege check beyond the account existing): [6](#0-5) 
- Denial of service against the legitimate claimant for a specific desired accountId.
- Since binding is permanent and irreversible once set on either side (account cannot re-set, id cannot be reused), the attacker can grief-squat any observed `accountId` cheaply (fee is 0, per `calcFee()` returning 0), and the id is resolvable on-chain via `GetAccountById` for exchanges/tools that rely on the human-readable id → address mapping. [7](#0-6) 

### Likelihood Explanation
Likelihood is high in practice: any node/attacker observing the P2P transaction pool for `SetAccountIdContract` transactions can trivially construct and broadcast a competing transaction with the same `accountId` payload and no meaningful cost (fee is zero), analogous to the low-cost front-running described for `Berachain`.

### Recommendation
Do not allow the caller to freely pick an externally visible, permanently-bound identifier without mitigating front-running: e.g., require a commit-reveal scheme (commit hash of id, reveal later), charge a nontrivial fee for `SetAccountIdContract` proportional to abuse risk, or allow reclaiming/expiring unclaimed ids reserved by an address rather than a race-to-claim on a public string.

### Proof of Concept
1. User A builds and signs a `SetAccountIdContract` with `accountId = "alice"` and broadcasts it to the network (visible in mempool before inclusion, per standard java-tron transaction broadcast flow).
2. Attacker observes the pending transaction, extracts `accountId = "alice"`, and immediately broadcasts their own `SetAccountIdContract` with the same `accountId` from their own address, paying equal/higher priority.
3. If attacker's transaction is included first, `AccountIdIndexStore.put()` binds `"alice"` (lowercased) to the attacker's address [8](#0-7) .
4. User A's original transaction is then processed and fails validation with `ContractValidateException("This id has existed")` as demonstrated in `nameAlreadyUsed()` [9](#0-8) , permanently denying User A the `"alice"` id since ids cannot be changed once set and cannot be reused once claimed.

  private static byte[] getLowerCaseAccountId(byte[] bsAccountId) {
    return ByteString
        .copyFromUtf8(ByteString.copyFrom(bsAccountId).toStringUtf8().toLowerCase(Locale.ROOT))
        .toByteArray();
  }

  public void put(AccountCapsule accountCapsule) {
    byte[] lowerCaseAccountId = getLowerCaseAccountId(accountCapsule.getAccountId().toByteArray());
    super.put(lowerCaseAccountId, new BytesCapsule(accountCapsule.getAddress().toByteArray()));
  }

  public byte[] get(ByteString name) {
    BytesCapsule bytesCapsule = get(name.toByteArray());
    if (Objects.nonNull(bytesCapsule)) {
      return bytesCapsule.getData();
    }
    return null;
  }

  @Override
  public BytesCapsule get(byte[] key) {
    byte[] lowerCaseKey = getLowerCaseAccountId(key);
    byte[] value = revokingDB.getUnchecked(lowerCaseKey);
    if (ArrayUtils.isEmpty(value)) {
      return null;
    }
    return new BytesCapsule(value);
  }

  @Override
  public boolean has(byte[] key) {
    byte[] lowerCaseKey = getLowerCaseAccountId(key);
    byte[] value = revokingDB.getUnchecked(lowerCaseKey);
    return !ArrayUtils.isEmpty(value);
  }
