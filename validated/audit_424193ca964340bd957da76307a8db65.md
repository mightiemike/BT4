## Title
`ExecutorViewWithChangeSet::get_resource_state_value_metadata` discards in-session metadata for `InPlaceDelayedFieldChange`, reading stale base-view metadata - ([File: aptos-move/aptos-vm/src/move_vm_ext/session/view_with_change_set.rs])

### Summary
`AbstractResourceWriteOp::InPlaceDelayedFieldChange` carries its own `metadata: StateValueMetadata` field [1](#0-0)  and this field is mutable via `metadata_mut()`, used generically across all write-op variants precisely because deposit/metadata updates can be applied after write-op creation [2](#0-1) . Despite this, `get_resource_state_value_metadata` in `ExecutorViewWithChangeSet` ignores the in-session metadata for `InPlaceDelayedFieldChange`/`ResourceGroupInPlaceDelayedFieldChange` and always forwards to `base_executor_view`: [3](#0-2) 

The comment at line 280 ("We could either return from the read, or do the base read again") shows this was a conscious but unenforced design choice, not a proven invariant.

### Finding Description
`metadata_mut()` is the generic accessor used by execution code to update the `StateValueMetadata` on any `AbstractResourceWriteOp` variant after creation (e.g., to set/refresh a deposit/slot-fee metadata during gas or storage-fee processing). For `Write`/`WriteWithDelayedFields`/`WriteResourceGroup`, that mutated metadata is embedded in the `write_op`/`metadata_op` and is correctly returned by `get_resource_state_value_metadata` because those branches read `write_op.as_state_value_metadata()`. But for `InPlaceDelayedFieldChange` and `ResourceGroupInPlaceDelayedFieldChange`, the mutated `metadata` field on the op itself is never consulted by `get_resource_state_value_metadata` — the function instead unconditionally forwards to `self.base_executor_view.get_resource_state_value_metadata(state_key)`, which reads metadata from before the current session's changes were applied.

This means: if code elsewhere in the same session/session-squash path calls `metadata_mut()` on an `InPlaceDelayedFieldChange` op to update its `StateValueMetadata` (e.g., during resource-write-set finalization when applying storage-fee deposits or eviction/creation bookkeeping), any subsequent read of that key's metadata through `ExecutorViewWithChangeSet` (this same resolver instance, which is reused across the epilogue/fee-charging session per the file's own test-only constructor comment about "cross-session squash" and "respawned epilogue session") returns the stale `base_executor_view` value instead of the just-updated in-session value.

### Impact Explanation
`StateValueMetadata` carries fields such as `deposit`/creation/eviction-relevant slot-rent bookkeping that feed into storage-fee refunds and eventually the committed `StateValue`'s metadata written to the JMT. If a later step in the same session (e.g., epilogue gas/storage-fee logic, or a subsequent read used to compute a write) reads metadata through this resolver and gets the stale base value rather than the in-session update, the final committed `StateValueMetadata` bound to that `StateKey` can diverge from what the correct VM semantics would produce — i.e., wrong metadata is committed to state for a key with an in-place delayed field change. This is a state-corruption-class defect scoped to the metadata field of affected keys.

### Likelihood Explanation
Triggering requires only an ordinary transaction that produces an `InPlaceDelayedFieldChange` op (e.g., an unmaterialized aggregator/delayed-field update where only the field value changes, not the surrounding resource bytes) and a subsequent same-session `metadata_mut()` update plus a same-session metadata read via this resolver, e.g., in the epilogue/fee-charging flow. No privileged operator action is needed — an unprivileged Move transaction using aggregators/delayed fields can produce this write shape. However, whether the current call sequence in production actually calls `metadata_mut()` on `InPlaceDelayedFieldChange` before a same-session read through this exact resolver method needs confirmation — I did not find, within the index, an explicit call site that mutates an `InPlaceDelayedFieldChange`'s metadata and then re-reads it via `ExecutorViewWithChangeSet::get_resource_state_value_metadata` in the same session. This ordering dependency is a real uncertainty that limits confidence to "codebase inconsistency confirmed, concrete exploit call chain not fully traced within available index coverage."

### Recommendation
Change the `InPlaceDelayedFieldChange`/`ResourceGroupInPlaceDelayedFieldChange` branches in `get_resource_state_value_metadata` to return `Some(op.metadata.clone())` (the in-session metadata) rather than forwarding to `base_executor_view`, consistent with how `metadata_mut()` treats these variants as holding authoritative, generically-updatable metadata alongside the other write-op kinds. At minimum, add an invariant check/assertion that the in-session metadata for these ops always matches the base view's value if the fallback path is intentionally kept, to catch any future divergence.
