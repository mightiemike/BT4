### Title
`ensure_match_transaction_info` omits checkpoint-hash validation, letting replay/archive verification accept a diverging final state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated check used by replay/verification tooling to confirm that a freshly executed `TransactionOutput` matches a previously committed `TransactionInfo`. It validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but it never validates `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. Because these checkpoint hashes are the actual Sparse-Merkle/Jellyfish-Merkle roots representing the durable world state (not merely the diff), a re-executed transaction whose write-set diff hashes identically but whose *application onto the base state* diverges (e.g., due to a base-state read from a different/incorrect prior version, non-determinism, or a storage/execution bug upstream) will silently pass this check.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) 
It checks `status`, `gas_used`, `write_set_hash == txn_info.state_change_hash()`, and `event_root_hash == txn_info.event_root_hash()`, but explicitly documents (and skips) the state/hot-state/position checkpoint-hash comparison: [2](#0-1) 

This function is called directly by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which is the authenticated-integrity tool operators use to confirm an archive/backup replays to the same ledger state as originally committed: [3](#0-2) 

`state_change_hash` only commits to the *write-set diff* produced by the transaction (`CryptoHash::hash(self.write_set())`), not to the resulting Sparse Merkle Tree root after that diff is applied to the (possibly different) base state. `state_checkpoint_hash` is the only field that binds the actual resulting durable state root. Because the tool never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, replay-verify can report success even though the locally-computed final state root diverges from the authenticated on-chain root.

### Impact Explanation
This breaks the state-commitment guarantee that `replay_on_archive` is meant to provide: it authenticates transaction-level effects (events/gas/status/diff hash) but not the derived global state root that clients and light-client proofs ultimately rely on. If the pre-existing (base) state used during replay is subtly wrong — for example due to a prior undetected bug, DB corruption, or divergence introduced by a upstream execution engine change (a class of bug this same code area already tracks — see the analogous `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature-gating machinery) — the tool used to catch exactly this kind of hard-fork/replay divergence will not flag it. This directly matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong ... state proof accepted as valid" impact categories, since it is the state proof/commitment validation layer itself that fails to check the correct invariant.

### Likelihood Explanation
The gap is only exercised through the intentional un-gated combination of feature flags/backup data (i.e., it requires an actual state divergence to exist for the missing check to matter), and the code comment itself flags this as a known, not-yet-fixed gap ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), which the team explicitly ties to future risk once the newer trading-native checkpoint fields are enabled. It is not exploitable by an unprivileged network attacker to corrupt consensus state directly (consensus-path checkpoint hashes are separately validated during normal block commit via `do_state_checkpoint.rs`'s `get_state_checkpoint_hashes` ensure), so this is best characterized as a detection/verification gap in the archive-replay tool and CLI debugger paths (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) rather than a way to corrupt mainnet consensus state itself.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash` (and, when present, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) computed from the locally re-executed state against the corresponding fields in the provided `txn_info`, as the existing TODO comment already recommends, before any current or future callers rely on it to gate acceptance of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or other checkpoint-bearing verification flows.

### Proof of Concept
Not applicable as an externally-triggerable exploit; the issue is demonstrated by direct code inspection: `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) never reads `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`, while its sole meaningful consumer for archive verification, `storage/db-tool/src/replay_on_archive.rs:392-397`, relies on it as the pass/fail criterion for replay correctness.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
