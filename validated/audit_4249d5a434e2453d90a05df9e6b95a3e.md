### Title
Permissionless `TransferToGasKey` Action Allows Any Caller to Inflate a Victim's Gas Key Balance Above `MAX_BALANCE_TO_BURN`, Permanently Blocking `DeleteKey` and `DeleteAccount` - (File: `runtime/runtime/src/access_keys.rs`)

---

### Summary

`action_transfer_to_gas_key` executes on the **receipt receiver's** account with no authorization check on the caller. Any unprivileged account can therefore send a `TransferToGasKey` receipt to a victim's account and push the victim's gas key balance above `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR). Both `delete_gas_key` and `action_delete_account` hard-reject deletion when the balance exceeds that threshold, so the attacker can persistently front-run every `DeleteKey` or `DeleteAccount` attempt the victim makes, preventing them from ever reclaiming their storage-staking deposit.

---

### Finding Description

**Permissionless write path.**
`action_transfer_to_gas_key` takes `account_id` from the receipt receiver field and unconditionally adds `action.deposit` to the named gas key's balance:

```rust
// runtime/runtime/src/access_keys.rs:257-288
pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,          // ← receipt receiver, not the caller
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    ...
    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit)...;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
```

There is no check that `predecessor_id == account_id`. Any account can craft a transaction whose receiver is the victim and whose action list contains `TransferToGasKey { public_key: victim_gas_key, deposit: 2_NEAR }`.

**Hard guard on deletion.**
`delete_gas_key` rejects deletion whenever the balance exceeds the constant:

```rust
// runtime/runtime/src/access_keys.rs:103-110
if gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN {
    result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh { ... }.into());
    return Ok(());
}
```

`action_delete_account` applies the same guard over the aggregate of all gas key balances:

```rust
// runtime/runtime/src/actions.rs:339-347
let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
    result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh { ... }.into());
    return Ok(());
}
```

The threshold is exactly 1 NEAR:

```rust
// core/primitives-core/src/account.rs:554
pub const MAX_BALANCE_TO_BURN: Balance = Balance::from_near(1);
```

**Why the victim cannot atomically escape.**
The victim's only recourse is `WithdrawFromGasKey`, which requires specifying an exact withdrawal amount. Because the attacker can observe the victim's pending `DeleteKey` transaction in the mempool and submit a `TransferToGasKey` in the same block, the victim's withdrawal amount is stale by the time it executes. After the attacker's receipt runs first, the remaining balance is `attacker_deposit`, which may still exceed 1 NEAR. The `DeleteKey` action in the same batch then fails. The attacker repeats this for every retry.

---

### Impact Explanation

The victim is unable to delete a gas key or their own account for as long as the attacker is willing to spend NEAR. Because `DeleteAccount` is the only way to reclaim the storage-staking deposit locked in the account, the victim's locked NEAR is effectively frozen. The victim's gas key balance does increase (the attacker's NEAR flows into it), but the victim cannot convert that into a deleted account and a freed storage deposit without the attacker's cooperation. This matches the "contract execution flow breakage" and "denial of service not at the network level, fixable without a hardfork" impact categories.

---

### Likelihood Explanation

The attack requires the attacker to spend slightly more than 1 NEAR per front-run attempt, so it is economically bounded. However, a motivated attacker (e.g., one who wants to prevent a competitor from reclaiming stake, or a griefing bot) can sustain it indefinitely. The `TransferToGasKey` host function is also callable from contracts (`promise_batch_action_transfer_to_gas_key`), so the attack can be automated cheaply on-chain. The victim has no atomic escape because `WithdrawFromGasKey` requires a known exact amount.

---

### Recommendation

1. **Remove the deletion guard entirely.** The `MAX_BALANCE_TO_BURN` check was designed to prevent accidental burning of large balances, but it creates a griefing surface. Instead, require the owner to explicitly call `WithdrawFromGasKey` before `DeleteKey` if they want to recover the balance, and allow deletion to burn whatever remains (up to any reasonable cap enforced at deposit time, not at deletion time).

2. **Alternatively, add a `force_delete_gas_key` path** that withdraws the full balance to the account atomically before removing the key, so the owner can always delete in one step regardless of the current balance.

3. **Restrict `TransferToGasKey` to `predecessor_id == account_id`** (i.e., only the account owner may fund their own gas key). This closes the permissionless write path entirely and is the minimal fix.

---

### Proof of Concept

```
// Setup: victim "bob.near" has a gas key with public key GK_PK, balance = 0.

// Step 1 – Attacker inflates the gas key balance above MAX_BALANCE_TO_BURN.
// Attacker signs a V0 transaction:
//   signer_id:   "attacker.near"
//   receiver_id: "bob.near"
//   actions:     [TransferToGasKey { public_key: GK_PK, deposit: 2_000_000_000_000_000_000_000_000 }]
//                                                        ^^^ 2 NEAR > MAX_BALANCE_TO_BURN (1 NEAR)

// Step 2 – Bob tries to delete the gas key.
// Bob signs:
//   signer_id:   "bob.near"
//   receiver_id: "bob.near"
//   actions:     [DeleteKey { public_key: GK_PK }]
//
// Runtime executes delete_gas_key:
//   gas_key_info.balance = 2 NEAR > MAX_BALANCE_TO_BURN (1 NEAR)
//   → ActionErrorKind::GasKeyBalanceTooHigh { balance: 2 NEAR }
//   → DeleteKey fails, key survives.

// Step 3 – Bob tries to delete his account.
// Bob signs:
//   signer_id:   "bob.near"
//   receiver_id: "bob.near"
//   actions:     [DeleteAccount { beneficiary_id: "bob.near" }]
//
// Runtime executes action_delete_account:
//   gas_key_balance_to_burn = 2 NEAR > MAX_BALANCE_TO_BURN (1 NEAR)
//   → ActionErrorKind::GasKeyBalanceTooHigh { balance: 2 NEAR }
//   → DeleteAccount fails, account survives, storage deposit remains locked.

// Step 4 – Bob tries to escape: WithdrawFromGasKey(1.5 NEAR) + DeleteKey in one tx.
// Attacker front-runs with another TransferToGasKey(2 NEAR) in the same block.
// After attacker's receipt: balance = 2.5 NEAR.
// Bob's WithdrawFromGasKey(1.5 NEAR) succeeds → balance = 1 NEAR.
// Bob's DeleteKey: 1 NEAR == MAX_BALANCE_TO_BURN → succeeds (boundary case).
// BUT if attacker deposits 2 NEAR + 1 yoctoNEAR, balance after withdrawal = 1 NEAR + 1 yocto > threshold → fails again.
// Attacker repeats indefinitely.
```

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
