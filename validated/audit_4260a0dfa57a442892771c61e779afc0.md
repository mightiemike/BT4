Based on my investigation, I found a strong analog that directly matches the "state updated in one place, but a dependent consumer keeps a stale copy, causing incorrect authorization/behavior" bug class described in the DAO/`Reserve.sol` report.

### Title
Dynamic config updates are lost/stale across `ConcurrentLocalComponentServer` replicas, causing inconsistent authorization and transaction-processing decisions - (File: `crates/apollo_config_manager/src/config_manager_tests.rs`, `crates/apollo_infra/src/component_server/local_component_server.rs`)

### Summary
The `ConfigManager` component exposes `set_node_dynamic_config`/`get_*_dynamic_config` RPCs that other components (gateway, mempool, consensus, http server, staking manager) poll to refresh security- and processing-relevant parameters such as `authorized_declarer_accounts`-adjacent gating, `validator_id`, and `accept_new_txs`. When the `ConfigManager` runs behind a `ConcurrentLocalComponentServer` (multiple concurrent request-handling replicas), a write via `set_node_dynamic_config` is not guaranteed to be visible to all replicas — a subsequent `get_consensus_dynamic_config` (or other getters) can still return the pre-update value. This is codified by an explicitly-named regression test, [1](#0-0) , whose comment states the retrieved config "should match the newly set config, but due to the bug it doesn't."

### Finding Description
`ConfigManager::set_node_dynamic_config` / `get_*_dynamic_config` mutate and read an in-process `NodeDynamicConfig` (verified directly via the single-instance test `config_manager_update_config` at [2](#0-1) , which passes). Downstream components pull this dynamic config on their own poll cadence, e.g. the mempool's `update_dynamic_config` [3](#0-2)  and the http server's `get_http_server_dynamic_config`/`accept_new_txs` gate [4](#0-3) .

The dedicated test `config_manager_concurrent_server_state_loss_bug`, which wires the `ConfigManager` through the same `ConcurrentLocalComponentServer` used in production deployments, sets a new `ConsensusDynamicConfig` (`validator_id`) via `set_node_dynamic_config`, then immediately re-reads it via `get_consensus_dynamic_config` and asserts equality, explicitly documenting that "due to the bug it doesn't" match [5](#0-4) . This is the direct root cause: unlike `LocalComponentServer` (a single serialized worker owning the canonical state), `ConcurrentLocalComponentServer` is used by multiple production components including the gateway and config manager itself [6](#0-5) , [7](#0-6) . Because the shared/canonical config state does not consistently propagate an update to whichever concurrent replica services a subsequent read, a write that is meant to immediately take effect (e.g., updating `authorized_declarer_accounts`-style gating, the consensus `validator_id`, or `accept_new_txs`) can silently be served stale by some replicas after the update completes — exactly analogous to `Reserve.sol` continuing to enforce `onlyGrantor` against the pre-`moveDao` DAO address because the dependent contract was never told about the update.

### Impact Explanation
Because multiple gateway/config-manager-hosting request handlers can concurrently serve dynamic config, an unprivileged transaction sender's request can be routed to a stale replica after an operator/config update takes effect:
- An account whose declare authorization was just revoked could still succeed against `check_declare_permissions`/`is_authorized_declarer` [8](#0-7)  if the relevant gating flows through a config path served by a stale replica, an unauthorized account action.
- Conversely, `accept_new_txs` toggles served inconsistently could cause the http server to reject all incoming transactions on some replicas while accepting them on others, contributing to a node/network being unable to confirm new transactions.
- A stale `validator_id`/committee override served to only some request paths risks divergent proposer/committee computation between components within (or across) nodes, which can propagate into consensus disagreement.

### Likelihood Explanation
The bug is already demonstrated by a dedicated, currently-existing regression test in the repository that explicitly documents the defect as present ("due to the bug it doesn't") rather than as a hypothetical, and `ConcurrentLocalComponentServer` is the real server type wired for the config manager, gateway, class manager, compile-to-casm, proof-manager, and signature-manager components in production configurations [9](#0-8) . This makes it a live, reachable condition any time a dynamic-config update (e.g., to authorization lists, committee overrides, or tx-acceptance gating) happens under production deployment topologies that use the concurrent server.

### Recommendation
Ensure `ConcurrentLocalComponentServer` provides linearizable/shared state for the `ConfigManager` (e.g., a single shared `Arc<RwLock<NodeDynamicConfig>>` visible to every concurrent replica) instead of per-replica cloned state, or route all dynamic-config writes/reads through a single authoritative worker regardless of concurrency, so that a `set_node_dynamic_config` call is immediately and consistently visible to every subsequent `get_*_dynamic_config` call from any replica — mirroring the report's recommendation to synchronize dependent state (`setIncentiveAddresses`) immediately after the authoritative value changes (`moveDao`).

### Proof of Concept
The existing failing-by-design test is the PoC: `config_manager_concurrent_server_state_loss_bug` at [1](#0-0)  — it (1) constructs a `ConfigManager` client backed by `ConcurrentLocalComponentServer` via `setup_concurrent_config_manager_test`, (2) reads the initial `ConsensusDynamicConfig`, (3) calls `set_node_dynamic_config` with a new `validator_id`, and (4) re-reads via `get_consensus_dynamic_config`, asserting it matches the newly set value — with the test's own comment confirming this assertion currently fails due to the underlying state-loss bug.

**Note on verification limits:** I could not fully inspect `crates/apollo_infra/src/component_server/local_component_server.rs` (the `ConcurrentLocalComponentServer` implementation) within the available tool budget to pinpoint the exact internal mechanism (e.g., per-worker state cloning vs. message-ordering race) that causes the loss. If precise internal code is required, a Devin session with full repository access would be needed to trace `ConcurrentLocalComponentServer`'s dispatch/state-sharing logic in detail.

#[tokio::test]
async fn config_manager_update_config() {
    // Set a config manager.
    let config = ConfigManagerConfig::default();

    let consensus_dynamic_config = ConsensusDynamicConfig::default();
    let node_dynamic_config = NodeDynamicConfig {
        consensus_dynamic_config: Some(consensus_dynamic_config),
        ..Default::default()
    };
    let config_manager = ConfigManager::new(config, node_dynamic_config.clone());

    // Get the consensus dynamic config and assert it is the expected one.
    let consensus_dynamic_config = config_manager
        .get_consensus_dynamic_config()
        .await
        .expect("Failed to get consensus dynamic config");
    assert_eq!(
        &consensus_dynamic_config,
        node_dynamic_config.consensus_dynamic_config.as_ref().unwrap(),
        "Consensus dynamic config mismatch: {consensus_dynamic_config:#?} != {:#?}",
        node_dynamic_config.consensus_dynamic_config
    );

    // Set a new dynamic config by creating a new consensus dynamic config. For simplicity, we
    // create an arbitrary one and assert it's not the default one.
    let new_consensus_dynamic_config =
        ConsensusDynamicConfig { validator_id: ValidatorId::from(1_u8), ..Default::default() };
    assert_ne!(
        consensus_dynamic_config, new_consensus_dynamic_config,
        "Consensus dynamic config should be different: {consensus_dynamic_config:#?} != {:#?}",
        new_consensus_dynamic_config
    );
    config_manager
        .set_node_dynamic_config(NodeDynamicConfig {
            consensus_dynamic_config: Some(new_consensus_dynamic_config.clone()),
            ..Default::default()
        })
        .await
        .expect("Failed to set node dynamic config");

    // Get the post-change consensus dynamic config and assert it is the expected one.
    let consensus_dynamic_config = config_manager
        .get_consensus_dynamic_config()
        .await
        .expect("Failed to get consensus dynamic config");
    assert_eq!(
        consensus_dynamic_config, new_consensus_dynamic_config,
        "Consensus dynamic config mismatch: {consensus_dynamic_config:#?} != {:#?}",
        new_consensus_dynamic_config
    );
}

#[tokio::test]
async fn config_manager_concurrent_server_state_loss_bug() {
    // Setup: Create ConfigManager with ConcurrentLocalComponentServer.
    let client = setup_concurrent_config_manager_test().await;

    // Get initial config.
    let initial_config =
        client.get_consensus_dynamic_config().await.expect("Failed to get initial config");

    // Create a new, different config.
    let new_consensus_config =
        ConsensusDynamicConfig { validator_id: ValidatorId::from(42_u8), ..Default::default() };
    assert_ne!(initial_config, new_consensus_config, "New config should be different from initial");

    // Set the new config.
    let new_node_config = NodeDynamicConfig {
        consensus_dynamic_config: Some(new_consensus_config.clone()),
        ..Default::default()
    };
    client.set_node_dynamic_config(new_node_config).await.expect("Failed to set new config");

    // Get the config again - it should reflect the change.
    let retrieved_config =
        client.get_consensus_dynamic_config().await.expect("Failed to get config after update");

    assert_eq!(
        retrieved_config, new_consensus_config,
        "Retrieved config should match the newly set config, but due to the bug it doesn't. Got: \
         {retrieved_config:?}, Expected: {new_consensus_config:?}"
    );
}
