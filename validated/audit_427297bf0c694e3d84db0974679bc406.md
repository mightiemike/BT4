## Analog Found: Dead `LiquidityCap` Invariant in `x/uregistry`/`x/uexecutor` PRC20 Minting Path

The external report's bug class — a value that is *declared* as an enforcement mechanism (allowance limiting withdrawals) but is never actually consulted/enforced at the point where funds move — has a direct analog in Push Chain's token-registry and PRC20 minting path.

### Title
Unenforced `TokenConfig.liquidity_cap` allows unbounded PRC20 minting past the declared max-supply cap - (File: `x/uexecutor/keeper/handler.go`)

### Summary
`TokenConfig.LiquidityCap` is documented as the "max supply cap for this token" [1](#0-0)  and is required to be a non-empty value at registration time via `ValidateBasic` [2](#0-1) . However, exactly like the report's `allowance()`, which was checked as a `view`-only value that could never be updated or actually enforced against consumption, `LiquidityCap` is stored purely as metadata and is never read anywhere in the PRC20 minting path.

### Finding Description
The inbound-deposit flow that mints PRC20 tokens on Push Chain is:
1. `x/uexecutor` keeper's `depositPRC20` fetches `TokenConfig` from `x/uregistry` and forwards to `CallPRC20Deposit`, with no cap check performed on the fetched config: [3](#0-2) 
2. `CallPRC20Deposit` issues a `DerivedEVMCall("depositPRC20Token", ...)` as the module sender, minting the requested `amount` unconditionally: [4](#0-3) 

Nowhere in `x/uexecutor/keeper/*` — the package responsible for turning a validated cross-chain inbound event into an actual PRC20 mint — is `LiquidityCap` ever read back from `TokenConfig` and compared against a running total or against the incoming `amount`. A repo-wide search confirms `LiquidityCap` only appears in: the proto/generated types, `ValidateBasic` (presence-only check), test fixtures, and config JSON seed files — never in any mint/deposit/inbound-execution code path.

This mirrors the report's root cause precisely: a field intended to gate/limit value transfer exists in the data model and is validated for well-formedness, but the code path that actually performs the value-increasing action (`withdraw()` in the report; `depositPRC20`/mint here) never consults it, rendering the cap purely cosmetic.

### Impact Explanation
This falls under the allowed impact category "corruption of PRC20 or native asset accounting... token mapping" and "unauthorized mint... of user or protocol-controlled funds." Because inbound minting is triggered by ordinary, unprivileged user action (a real deposit event on the source-chain gateway observed and voted on by honest Universal Validators — no malicious validator assumption required), an attacker (or simply organic volume) can cause PRC20 supply for a given token to exceed the registry's own declared `liquidity_cap` with no on-chain guardrail stopping it. Any downstream logic, monitoring, or risk assumption built on `liquidity_cap` as a real supply ceiling (e.g., auto-swap slippage/pricing assumptions in `CallPRC20DepositAutoSwap`, or operational risk limits per token) is silently bypassed.

### Likelihood Explanation
High — this requires no privileged actor, no malicious validator, and no crafted edge-case input. Ordinary honest-validator finalization of a legitimate (or attacker-funded) inbound deposit that merely exceeds the configured cap is sufficient; the check simply does not exist in the reachable code path.

### Recommendation
Enforce `TokenConfig.LiquidityCap` in `x/uexecutor/keeper/handler.go`'s `depositPRC20` (and the auto-swap variant) by tracking cumulative minted supply per PRC20 (e.g., via `balanceOf`/`totalSupply` on the PRC20 contract, or a dedicated per-token minted-supply counter in `x/uregistry`/`x/uexecutor` state) and rejecting or capping the mint when `currentSupply + amount > liquidityCap`, mirroring the report's recommendation to make the limiting mechanism state-mutating and actually consulted, and to add an authoritative callback that keeps supply state consistent when partial/full mints occur.

### Proof of Concept
1. Register a `TokenConfig` with `liquidity_cap = "1000000"` (per `token_config.go` `ValidateBasic`, any non-empty string passes — there is no check that mints stay under it later).
2. Have (honest) Universal Validators observe and vote a real/attacker-funded source-chain deposit event for `amount = 10000000` (10x the cap) via `MsgVoteInbound`.
3. Once the vote threshold passes, `depositPRC20` → `CallPRC20Deposit` → `DerivedEVMCall("depositPRC20Token", ...)` mints the full `10000000` with no reference to `LiquidityCap` anywhere in the call chain [5](#0-4) [6](#0-5) .
4. PRC20 total supply now exceeds the registry-declared `liquidity_cap` by 10x, with zero errors or reverts anywhere in the pipeline.

```go
func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
```

```go
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
```
