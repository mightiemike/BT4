Confirmed: `TransferAssetActuator` has no restriction preventing the asset issuer from freely transferring away their TRC10 token balance at any time, regardless of any active `AssetIssueContract` sale window.

### Title
Asset issuer can DoS an active TRC10 token sale by transferring away the sale token balance mid-sale - (File: `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
An analog of the OpenEdition "cancel-by-revoking-permission" bug exists in java-tron's TRC10 sale mechanism. `AssetIssueContract` defines a sale with `startTime`/`endTime` during which any account can call `ParticipateAssetIssueContract` ("buy") to exchange TRX for the issuer's token. Nothing locks or escrows the issuer's token balance for the sale duration, so the issuer can broadcast an ordinary `TransferAssetContract` at any point during the active window and move the entire remaining token balance to another address they control, deterministically breaking `participate` for every subsequent buyer while the sale nominally remains "open" per its timestamps.

### Finding Description
`ParticipateAssetIssueActuator.validate()` only checks the sale's time window and that the issuer (`toAddress`) currently holds enough of the asset: [1](#0-0) 
There is no reservation, freeze, or escrow of the issuer's token supply tied to the sale's `startTime`/`endTime`. The issuer's token balance is an ordinary asset balance that can be moved freely at any time via `TransferAssetActuator`, which performs no check against any in-progress sale: [2](#0-1) 
Because `validate()` and `execute()` in `ParticipateAssetIssueActuator` run atomically per transaction, a buyer's TRX is never actually deducted when validation fails — but the buyer's transaction is deterministically rejected with `"Asset balance is not enough !"` once the issuer has moved the tokens away: [3](#0-2) 
This mirrors the OpenEdition report exactly: the seller/creator retains unilateral, unrestricted control over the resource backing an already-started, time-boxed sale (there, minter role; here, token balance), and can exercise that control mid-sale to silently and permanently kill the sale for every remaining buyer, without the sale's own state (its time window) reflecting the cancellation.

### Impact Explanation
Any account that issued a TRC10 token and started a public sale window can unilaterally and irreversibly stop that sale after buyers have already begun participating, by simply transferring the token elsewhere — an ordinary, otherwise-legitimate transaction. Buyers relying on the advertised `startTime`/`endTime` window have no way to detect in advance that the sale is dead; every subsequent `ParticipateAssetIssueContract` broadcast will fail with `"Asset balance is not enough !"`, producing a denial-of-service against the sale's remaining buyers/participants and an inconsistent on-chain state (sale reports itself "active" via timestamps while functionally closed).

### Likelihood Explanation
Trivial to trigger: any account with the ability to issue a TRC10 asset (any anonymous account able to broadcast `AssetIssueContract`) can, after other users start participating, broadcast a normal `TransferAssetContract` moving the balance away. No special/privileged system role (SR/committee) is required — only ownership of the asset being sold, which any user gains simply by issuing it.

### Recommendation
Either (a) escrow/lock the asset amount backing an active sale in the `AssetIssueStore`/`AccountCapsule` such that `TransferAssetActuator` cannot reduce the issuer's balance below the amount still reserved for the sale while `now < endTime`, or (b) make `ParticipateAssetIssueActuator.validate()`/documentation explicitly acknowledge that sale availability is not guaranteed by the time window and that the issuer can withdraw tokens at will, so wallets/dApps do not treat the time window as a binding commitment.

### Proof of Concept
1. Account `A` issues asset `X` with `startTime = now`, `endTime = now + 1h`, and `totalSupply = 1000`.
2. Account `B` broadcasts `ParticipateAssetIssueContract` and successfully buys some of `X` (sale works as expected).
3. Mid-window, account `A` broadcasts `TransferAssetContract` moving its entire remaining balance of `X` to a second address `A2` that it controls (see [4](#0-3) ) — this succeeds unconditionally regardless of the still-open sale window.
4. Account `C` broadcasts `ParticipateAssetIssueContract` for the same asset within `[startTime, endTime)`; `validate()` reaches `toAccount.assetBalanceEnoughV2(...)` (see lines 195-198 cited above), finds the balance now 0, and throws `"Asset balance is not enough !"`, permanently denying `C` (and all further buyers) participation even though the sale's advertised time window has not expired.

  public boolean execute(Object result) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) result;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    long fee = calcFee();
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    AssetIssueStore assetIssueStore = chainBaseManager.getAssetIssueStore();
    try {
      TransferAssetContract transferAssetContract = this.any.unpack(TransferAssetContract.class);
      byte[] ownerAddress = transferAssetContract.getOwnerAddress().toByteArray();
      byte[] toAddress = transferAssetContract.getToAddress().toByteArray();
      AccountCapsule toAccountCapsule = accountStore.get(toAddress);
      if (toAccountCapsule == null) {
        boolean withDefaultPermission =
            dynamicStore.getAllowMultiSign() == 1;
        toAccountCapsule = new AccountCapsule(ByteString.copyFrom(toAddress), AccountType.Normal,
            dynamicStore.getLatestBlockHeaderTimestamp(), withDefaultPermission, dynamicStore);
        accountStore.put(toAddress, toAccountCapsule);

        fee = fee + dynamicStore.getCreateNewAccountFeeInSystemContract();
      }
      ByteString assetName = transferAssetContract.getAssetName();
      long amount = transferAssetContract.getAmount();

      AccountCapsule ownerAccountCapsule = accountStore.get(ownerAddress);
      if (!ownerAccountCapsule
          .reduceAssetAmountV2(assetName.toByteArray(), amount, dynamicStore, assetIssueStore)) {
        throw new ContractExeException("reduceAssetAmount failed !");
      }
      accountStore.put(ownerAddress, ownerAccountCapsule);

      toAccountCapsule
          .addAssetAmountV2(assetName.toByteArray(), amount, dynamicStore, assetIssueStore);
      accountStore.put(toAddress, toAccountCapsule);

      adjustBalance(accountStore, ownerAccountCapsule, -fee);
      if (dynamicStore.supportBlackHoleOptimization()) {
        dynamicStore.burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }
      ret.setStatus(fee, code.SUCESS);
    } catch (BalanceInsufficientException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    } catch (InvalidProtocolBufferException | ArithmeticException e) {
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    return true;
  }
