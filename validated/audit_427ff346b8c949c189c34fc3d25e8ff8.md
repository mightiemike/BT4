Based on my investigation, I found a concrete integrity gap that is explicitly acknowledged as a TODO in the code itself, in the transaction-output-to-authenticated-`TransactionInfo` verification path used by replay/verify tooling.

### Title
Replay-verify's `ensure_match_transaction_info` skips checkpoint-hash validation, allowing a state-root divergence to pass verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to confirm that a locally re-executed transaction's output matches the authenticated `TransactionInfo` stored in the accumulator (and ultimately signed via `LedgerInfo`). It checks status, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash — but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, per its own inline TODO.

### Finding Description [1](#0-0) 

The function performs `ensure!` checks for status, gas used, write-set hash vs `state_change_hash`, and event root hash vs `event_root_hash`, but the final block is only a comment:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
```
This is the exact same shape of the external bug class (H-02): a construction/verification path takes an authenticated value (there, `slashStore`; here, `state_checkpoint_hash`/`position_state_checkpoint_hash`) and the surrounding check silently omits the field that would catch a mismatch, so the "vault"/replay path never fails even though the underlying data (slashing correctness / state-root correctness) is wrong.

`ensure_match_transaction_info` is called from several replay/verification entry points: [2](#0-1) , `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs`. These are the tools whose entire purpose is to independently re-execute historical transactions and confirm the recomputed result matches the authenticated on-chain `TransactionInfo` fetched via a `TransactionInfoWithProof`/accumulator proof — i.e., they are the last line of defense for detecting a state-root divergence (bug in the VM, executor, or write-set conversion) between the archive and honest execution.

Because the state-checkpoint-hash fields (which are the accumulator-committed Sparse-Merkle-Tree/JMT root summarizing world state at that transaction, and, per the new `position_state_checkpoint_hash` field, native-position/trading state) are excluded from the comparison, a scenario where the write set matches (`state_change_hash` correct) but the resulting Merkle root diverges — e.g., due to a bug in accumulating/committing "position" (native order-book / trading) state, or a stale/incorrect state view being used to build the checkpoint — would not be flagged by replay-verify. The check would report success (`Ok(())`) despite `state_checkpoint_hash` / `position_state_checkpoint_hash` values in `txn_info` not corresponding to what local execution actually produces.

### Impact Explanation
This falls in the "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong accumulator root ... accepted as valid" categories from the required impact list. Replay-verify (`replay_on_archive`, chunk executor catch-up verification, and the debugger/CLI tools) is the mechanism operators and auditors rely on to catch state-root divergence bugs on mainnet archives before they become consensus-breaking or before bad data is trusted for restore/fast-sync. If the position/state checkpoint hash is wrong in the archived `TransactionInfo` (whether from a prior VM/executor bug or corruption), this comparator will not detect it — masking a real ledger-state integrity defect and letting bootstrapping/restore/audits proceed on an unverified (and possibly wrong) root.

### Likelihood Explanation
The gap is unconditional and unprivileged — it applies to every call of `ensure_match_transaction_info` regardless of caller, and is explicitly documented as a known omission ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), i.e., the code path is on a track to be enabled for production trading-native state without being fixed first. It requires only that some upstream divergence in checkpoint/position-state-root computation exists (a plausible outcome given `position_state_checkpoint_hash` is newly repurposed on `TransactionInfoV1`, per `types/src/transaction/mod.rs:2452`) for this comparator to silently pass over it.

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the values carried in the authenticated `txn_info`, failing loudly on mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any feature relying on `position_state_checkpoint_hash`) is enabled in production.

### Proof of Concept
Not directly runnable as a PoC because the exercise of this gap requires an actual state-root-divergence bug elsewhere (e.g., in position/state checkpoint computation) to be present; the code snippet itself is sufficient proof that such a divergence would go undetected:
- `types/src/transaction/mod.rs:2139-2204` — `ensure_match_transaction_info` checks `status`, `gas_used`, `write_set_hash` (vs `state_change_hash`), `event_root_hash`, then returns `Ok(())` without checking `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`.
- Callers (`storage/db-tool/src/replay_on_archive.rs`, `execution/executor/src/chunk_executor/mod.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`) treat a returned `Ok(())` as "replay verified", so any checkpoint-hash-only divergence is reported as a clean replay.

Note: I was unable to fully inspect `storage/db-tool/src/replay_on_archive.rs` and `execution/executor/src/chunk_executor/mod.rs` in full detail (tool errors on the final iteration prevented reading their full bodies), so I cannot confirm whether any additional/redundant checkpoint-hash validation exists outside of `ensure_match_transaction_info` at those call sites. The core comparator function and its documented gap, however, are confirmed directly from the code and its own TODO comment.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
