No vulnerability found for this question.

**Reasoning:**

The premise misunderstands what `TrustedStateChange` and `latest_epoch_change_li` are used for. `TrustedState::verify_and_ratchet_inner` is a **pure verification** function used by light clients / callers holding a `TrustedState` to authenticate a `StateProof` — it does not write to the Aptos DB, JMT, or accumulator, and it is not part of the executor→storage commit path at all.

Key points that invalidate the exploit theory:

1. **Staleness is self-contained per call, not dependent on caller bookkeeping.** Every call to `verify_and_ratchet_inner` re-checks staleness against the version and validator set embedded in `self` (the `TrustedState` passed in), via the version check [1](#0-0)  and via `is_ledger_info_stale`/`epoch_change_verification_required`, both of which dispatch on the current `EpochState`/`Waypoint` contained in `self` [2](#0-1) . A stale `epoch_change_li` replay would be verified against the caller's *current* `TrustedState` (whatever it ratcheted to, `Version` or `Epoch`), not against a separately cached `latest_epoch_change_li`. There is no code path where dropping the `latest_epoch_change_li` reference causes the next call's staleness check to be skipped or weakened.

2. **`latest_epoch_change_li` is a convenience output, not a security invariant.** It's returned only so a caller can persist a waypoint/epoch-change checkpoint if it wants to; the ratchet safety itself derives entirely from the `TrustedState` enum (`EpochWaypoint`/`EpochState`) returned as `new_state`, which is fully captured in `TrustedStateChange::new_state()` regardless of variant [3](#0-2) . Losing the `&'a LedgerInfoWithSignatures` reference on a `Version`-only ratchet does not weaken any subsequent verification because subsequent verification never consults that reference — it consults `self`.

3. **No committed-state or storage-sync production usage found.** Searching the codebase, `TrustedStateChange`/`verify_and_ratchet` usages are confined to unit tests (`types/src/unit_tests/trusted_state_test.rs`) and executor test helpers (`execution/executor-test-helpers/src/integration_test_impl.rs`, `execution/executor/tests/db_bootstrapper_test.rs`) — there is no evidence this is wired into mainnet storage-sync/state-sync-driver code that persists `latest_epoch_change_li` as claimed. This fails the scope requirement that the finding "corrupt committed state, corrupt proof material, misbind an authenticated response, or create hard-fork-only divergence."

Given the staleness/epoch checks are self-verifying per call based on the caller's actual current `TrustedState` and this code path does not touch committed storage, the described replay scenario does not corrupt any authenticated or committed state.
