### Title
`ensure_match_transaction_info` and `TransactionOutputListWithProofV2::verify` never check `state_checkpoint_hash` — a corrupted/wrong state root passes replay-verify and authenticated output-proof verification - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` (used by replay-verify tooling and the debugger to prove that re-executed output matches the authenticated `TransactionInfo`) and the sibling `TransactionOutputListWithProofV2::verify` (used to authenticate a `TransactionOutputListWithProof` against a `LedgerInfo`) both check status, gas, write-set hash and event-root hash, but **never check `state_checkpoint_hash`** (nor `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` on `TransactionInfoV1`). The code even contains a self-acknowledging TODO admitting the gap for the V1-only fields, but the omission also silently applies to the pre-existing, already-live `state_checkpoint_hash` field.

### Finding Description
`TransactionInfo` carries `state_checkpoint_hash`, an authenticated field asserting the root hash of the Sparse-Merkle state tree at that transaction (`types/src/transaction/mod.rs:2409-2412`). This hash is folded into `TransactionInfo::hash()`, which is what gets placed as a leaf in the transaction accumulator and thus tied to a signed `LedgerInfo` root (`execution/executor/src/workflow/do_ledger_update.rs:95-123`).

Two verification entry points are supposed to prove "the transaction output I computed locally is exactly what the authenticated ledger says happened":

1. `TransactionOutput::ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) — checks `status`, `gas_used`, `write_set_hash` vs `state_change_hash`, and `event_root_hash`, but does **not** compare any locally-derived state root against `txn_info.state_checkpoint_hash()` (or the V1 hot/position hashes). This is used by:
   - `storage/db-tool/src/replay_on_archive.rs:392` — the primary tool operators use to verify historical replay integrity against an archive.
   - `aptos-move/aptos-debugger/src/aptos_debugger.rs:243` and `aptos-move/cli/src/commands.rs:2653` — debugging/replay tools.

2. `TransactionOutputListWithProofV2::verify` (types/src/transaction/mod.rs:2941-3022) — the authenticated verification path for `TransactionOutputListWithProof`, used by light clients/full nodes to accept a batch of `(txn, output)` pairs as proven against a `LedgerInfo`. It verifies event root, write-set hash, gas, status and transaction hash, but likewise never checks `state_checkpoint_hash`, so an output whose write-set replays correctly but whose downstream *checkpointed* state root differs is accepted as fully verified.

Because a state root and a write-set hash are computed independently (write-set hash is over the txn's own deltas; the checkpoint hash is over the *entire accumulated Sparse Merkle Tree* at a checkpoint boundary, built from many prior write sets plus base state), a consistent write-set hash does **not** imply a consistent state-checkpoint root. Any code path that mutates state incorrectly upstream (bad JMT update, bad restore, a divergent hot-state/position-state materialization) but happens to still produce a matching per-transaction write-set/event/gas/status will pass both of these "verification" functions even though the actual state-commitment (the thing consensus and light clients ultimately trust) is wrong.

The developers' own comment (lines 2197-2202) explicitly documents that this is a real, currently-existing gap for the checkpoint hashes, warning that "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution," but frames it only as future work gated on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. The gap for the base `state_checkpoint_hash` (which is a mainnet-live field on every `TransactionInfo`, V0 and V1 alike, not something behind an unlaunched feature flag) is not called out at all and is exercised today.

### Impact Explanation
This breaks the "committed state that differs from correct VM result... accepted as valid" and "authenticated proof accepted as valid" integrity gates:
- `replay_on_archive` (the tool operators/auditors run to detect historical state divergence, e.g. after a bug fix or hard fork audit) can silently report success even though the locally recomputed state-checkpoint root does not match what is recorded/signed in the ledger, masking a real divergence.
- `TransactionOutputListWithProofV2::verify` is a state-proof-bearing API surface; a full node/light client consuming this API accepts a `(txn, output)` list as fully authenticated against a signed `LedgerInfo` without validating that the state root committed in `TransactionInfo` matches anything about the actual resulting state — the check that exists only proves the individual transaction's write-set/events/status, not that the cumulative state tree is correct.

This does not itself corrupt storage (nothing recomputes a wrong root and commits it), but it removes a critical safety net: a bug elsewhere (JMT corruption, wrong hot/position state materialization, an incorrect restore) that produces the right write-set/events/gas/status per-transaction but the wrong cumulative state root would not be caught by these specific verification routines, undermining confidence in the "if replay-verify passes, storage is correct" invariant that operators and auditors rely on.

### Likelihood Explanation
No attacker action is required — this is a pure verification-completeness gap present in unprivileged, always-reachable code (`ensure_match_transaction_info` and `TransactionOutputListWithProofV2::verify` run on any invocation of `replay_on_archive`, the debugger, or full-node processing of a `TransactionOutputListWithProof`). The bug is latent/passive: it doesn't cause a divergence by itself, but it will fail to detect one whenever some other bug produces a state-root divergence while keeping write-set/event/gas/status identical (a realistic scenario for state-only corruption such as JMT/restore bugs). The likelihood of the *masking* effect firing is tied to the likelihood of an underlying state-corruption bug, which cannot be bounded here, but the missing check itself is deterministic and always present.

### Recommendation
- In `TransactionOutput::ensure_match_transaction_info`, thread through the locally computed state-checkpoint hash (and hot/position checkpoint hashes when applicable) and assert equality against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, mirroring the existing `write_set_hash`/`event_root_hash` checks.
- In `TransactionOutputListWithProofV2::verify`, add the same checkpoint-hash comparison wherever a `state_checkpoint_hash` is present on the corresponding `TransactionInfo`, instead of only checking events/write-set/gas/status/txn-hash.
- Do not gate the base `state_checkpoint_hash` check behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS`; that flag should only gate the additional position-state hash, not the pre-existing state-checkpoint field.

### Proof of Concept
This is a verification-completeness defect, not a state-mutating exploit, so no on-chain PoC transaction is applicable. The gap can be demonstrated by unit test:
1. Construct a `TransactionOutput` with a write set, events, gas, and status matching some `TransactionInfoV0`/`V1`.
2. Construct the `TransactionInfo` with the correct `write_set_hash`/`event_root_hash`/`gas_used`/`status` but a deliberately wrong `state_checkpoint_hash` (e.g. `HashValue::random()`).
3. Call `txn_output.ensure_match_transaction_info(version, &txn_info, None, None)` — it returns `Ok(())` despite the mismatched state-checkpoint hash, i.e. it passes verification even though the committed state root is provably wrong.
4. Similarly, build a `TransactionOutputListWithProofV2` with a mismatched `state_checkpoint_hash` in one `TransactionInfo` entry and call `.verify(...)` — it returns `Ok(())`.

Note: I could not fully trace every consumer of `TransactionOutputListWithProofV2` (e.g., whether any caller performs an out-of-band checkpoint-hash check before trusting the result), so the concrete blast radius of the second entry point should be validated against all callers before treating it as independently exploitable in a live full-node/light-client context.
