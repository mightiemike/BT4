### Title
Unbounded native-stack recursion in `bytecode_hash_node` during declare-transaction CASM hash validation - ([File: crates/starknet_api/src/contract_class/compiled_class_hash.rs])

### Summary
`DeclareTransaction::check_compile_class_hash_v2_declaration` calls `casm.hash(&HashVersion::V2)` [1](#0-0) , which recurses through `bytecode_hash_node` over the `NestedIntList` segment tree describing the compiled bytecode's structure, with recursion depth equal to the tree's nesting depth and no depth limit [2](#0-1) . This runs directly in the gateway/sequencer process — unlike Sierra→CASM compilation itself, which is delegated to a sandboxed subprocess bound by CPU-time/memory `rlimit`s but not a stack-size limit [3](#0-2) .

### Finding Description
`bytecode_hash_node` is defined as:
```rust
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where H: StarkHash, NL: HashableNestedIntList {
    if node.is_leaf() { ... }
    else {
        let inner_nodes = node.iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        ...
    }
}
``` [2](#0-1) 

This is called from `hash_inner`/`HashableCompiledClass::hash`, invoked from two attacker-reachable, unsandboxed sites:
1. `SierraCompiler::compile` in the sequencer's Sierra-compilation component computes `executable_class.hash(&HashVersion::V2)` right after deserializing the compiler subprocess's stdout, in the *parent* process [4](#0-3) .
2. `DeclareTransaction::check_compile_class_hash_v2_declaration` recomputes `casm.hash(&HashVersion::V2)` while validating a declare transaction's `compiled_class_hash` field, again in the main sequencer process [5](#0-4) .

`bytecode_segment_lengths` is a `NestedIntList` produced by the Sierra→CASM compiler based on the contract's control-flow/function structure [6](#0-5) ; its nesting depth follows the nesting of branches/function calls in the declared Sierra program, which an attacker fully controls when submitting a `DECLARE` transaction. Only the total bytecode size (`max_bytecode_size`, default 80×1024 felts) and compiler CPU/memory limits are enforced on the compilation subprocess [7](#0-6) ; nothing bounds the *depth* of the resulting segment tree, and the recursive hash computation over that tree happens back in the unsandboxed sequencer process, exactly mirroring the CVE's pattern of an unbounded stack-recursive function operating on attacker-controlled nested/untrusted data with no depth guard, unlike the counterpart Cairo0/VM recursion tests where recursion is explicitly noted to not consume native stack ("the stack in the heap as a memory segment") [8](#0-7) , and unlike Sierra-gas/Cairo-steps-tracked recursion which is bounded by metered resources before overflow [9](#0-8) .

### Impact Explanation
A sufficiently deep `NestedIntList` (achievable by crafting a Sierra program with deeply nested branch/function structure within the bytecode-size limit) can drive `bytecode_hash_node` recursion deep enough to exhaust the native call stack of the sequencer/gateway/class-compilation process handling the `DECLARE` transaction, crashing that process. Since this hash computation is deterministic and identical for every honest node that must validate the same declare transaction (gateway ingestion and, again, CASM-hash validation), all nodes processing this transaction would independently crash in the same code path — a network-wide denial-of-service preventing new transaction confirmation, matching the "network unable to confirm new transactions" impact criterion.

### Likelihood Explanation
Reachable via a single unprivileged `DECLARE` transaction (V2/V3) with an attacker-authored Sierra class; no special privileges, staking, or p2p position needed — only the ability to submit a declare transaction that passes basic size limits. Exploitability depends on how deep a segment tree the actual `cairo-lang-sierra-to-casm` compiler can be induced to emit within `max_bytecode_size`; this was not directly verified against the compiler's segment-generation logic (external `cairo-lang-*` crates), so the achievable depth versus default thread stack size is a residual uncertainty.

### Recommendation
Impose an explicit maximum nesting-depth check on `bytecode_segment_lengths`/`NestedIntList` before/while calling `bytecode_hash_node` (reject or fee-charge classes exceeding a safe depth bound), or convert `bytecode_hash_node` to an iterative, explicit-stack-based traversal so recursion depth is decoupled from the native call stack, in `crates/starknet_api/src/contract_class/compiled_class_hash.rs`. Apply the analogous fix to the mirrored recursive traversal in `crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs` (`create_bytecode_segment_structure_inner` / `BytecodeSegmentNode::hash`), used during OS re-execution.

### Proof of Concept
Not independently executed; a concrete PoC would require crafting a Cairo1 contract whose compiled Sierra program forces the Sierra→CASM compiler to emit a `NestedIntList` with recursion depth in the tens of thousands (e.g., via deeply chained/nested function calls or match arms) while staying within `DEFAULT_MAX_BYTECODE_SIZE` (80×1024 felts), then submitting it as a `DECLARE` transaction and observing a stack-overflow crash in the gateway/compiler process when `casm.hash(&HashVersion::V2)` is invoked. This step (verifying achievable segment-tree depth from the external Cairo compiler) was not completed and is flagged as an open verification item.

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}
