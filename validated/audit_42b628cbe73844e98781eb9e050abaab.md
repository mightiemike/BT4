Based on my research, I found a concrete analog to the OFTCore unbounded-`_toAddress` bug class in Push Chain's outbound execution path.

### Title
Unbounded user-controlled outbound `payload` size can permanently block EVM outbound nonce sequencing on destination chain - (File: `x/uexecutor/keeper/create_outbound.go`, `universalClient/chains/evm/tx_builder.go`)

### Summary
`OutboundTx.Payload` is copied verbatim, with no length bound, from the `UniversalTxOutboundEvent` log emitted by `UniversalGatewayPC` — a value fully controlled by whatever contract call the user routed through `MsgExecutePayload`/`ExecutePayloadV2`. This payload is later ABI-encoded as the `data` argument of `Vault.finalizeUniversalTx` and signed/broadcast on the destination EVM chain using a strictly sequential per-signer nonce (`GetNextNonce`/`GetPendingNonce`). If the resulting destination-chain transaction cannot fit within that chain's block gas limit, it can never be mined, and because EVM nonces are sequential, every subsequent outbound queued behind it for the same TSS signer address on that chain is permanently blocked — mirroring the LayerZero `_toAddress` bug where a single unexecutable message wedges the nonce and blocks the whole channel.

### Finding Description
`BuildOutboundsFromReceipt` (`x/uexecutor/keeper/create_outbound.go:69-91`) takes `event.Payload` directly from an EVM log with no size validation: [1](#0-0) 

`OutboundTx.ValidateBasic()` (`x/uexecutor/types/outbound_tx.go:65-70`) only checks that `Payload` is non-empty for `PAYLOAD`/`FUNDS_AND_PAYLOAD` types — it never bounds its length: [2](#0-1) 

The `evm.TxBuilder.encodeFunctionCall` (`universalClient/chains/evm/tx_builder.go:320-349`) packs this unbounded `payloadBytes` as the `bytes data` argument of `Vault.finalizeUniversalTx`, and `GetOutboundSigningRequest` builds a transaction with an explicit `gasLimit` taken from the event (`universalClient/chains/evm/tx_builder.go:108-153`). Nothing constrains this gas limit or the payload size against the destination chain's actual block gas limit.

Contrast with the Solana path, which explicitly polices oversized payloads via `maxRefRouteIxData` (hard reject with `BuildRefRouteTransactions`) and a warning for the direct route (`universalClient/chains/svm/tx_builder.go:980-990`) — no equivalent guard exists on the EVM side.

Because EVM nonces (`GetNextNonce`/`GetPendingNonce`, `universalClient/chains/evm/tx_builder.go:156-166`) are strictly sequential per TSS signer per destination chain, a transaction that is signed and broadcast but can never be included (because it exceeds the destination chain's block gas limit, similar to the Arbitrum→Optimism scenario in the original report) permanently occupies that nonce slot. All subsequent `PendingOutbounds` entries destined for the same chain queue behind the stuck nonce indefinitely — this is the direct Push Chain analog of the OFTCore/LayerZero nonce-blocking DoS.

### Impact Explanation
This falls squarely within "denial of service...not network-level and...reachable without privileged control" and can also indirectly cause "permanent freezing" of user funds: any outbound behind the stuck nonce (funds releases, gas refunds, `INBOUND_REVERT` refunds) cannot execute, and PRC20/native asset held for the outbound remains locked pending manual/administrative TSS/nonce intervention, since the codebase provides no automatic detection or skip-forward mechanism for a wedged EVM nonce (unlike the ballot-recompute/`RevertStuckInbound` admin tooling that exists for stuck *inbound* ballots).

### Likelihood Explanation
An unprivileged user can trigger this purely through the standard `MsgExecutePayload` → UEA execution flow: any contract call the user routes through their UEA that emits a `UniversalGatewayPC` outbound event with a large `payload` (e.g., a large `bytes` argument to a destination-chain call) and a correspondingly large declared `gasLimit` will produce an oversized/unexecutable outbound. No validator, relayer, or admin collusion is required — only that the destination chain's per-block gas limit is smaller than what the crafted payload/gas limit would need, which is a normal cross-chain condition (analogous to differing L1/L2 gas limits in the original report).

### Recommendation
1. Enforce a maximum size on `OutboundTx.Payload` in `OutboundTx.ValidateBasic()` (`x/uexecutor/types/outbound_tx.go`), calibrated to a safe fraction of the lowest-gas-limit chain Push Chain supports outbound to.
2. Cap the outbound `GasLimit` accepted from `UniversalTxOutboundEvent` against the destination chain's registered/configured max block gas limit (from `uregistry` chain config) before creating the `OutboundTx`, rejecting or reverting oversized requests instead of queuing them.
3. Mirror the Solana `maxRefRouteIxData` hard-reject pattern in the EVM `TxBuilder`/`create_outbound.go` path rather than only warning.
4. Add operational tooling (analogous to `RevertStuckInbound`) to detect and skip/replace a wedged EVM nonce for a destination chain so a single unexecutable outbound cannot indefinitely block the queue.

### Proof of Concept
1. Attacker deploys a UEA-controlled contract call via `MsgExecutePayload` whose execution triggers `UniversalGatewayPC.withdrawAndCall` (or equivalent) with an outbound `payload` sized to require, say, 40M gas of destination-chain execution and a matching `gasLimit` field, targeting an EVM chain whose block gas limit is 30M.
2. `BuildOutboundsFromReceipt` creates the `OutboundTx` with this oversized payload/gas_limit without validation (`create_outbound.go:69-91`), and `attachOutboundsToUtx` queues it in `PendingOutbounds` with the next sequential nonce for the destination chain's TSS signer.
3. TSS coordinator signs and the relayer broadcasts the transaction (`evm/tx_builder.go:169-247`); the transaction is rejected/never mined by the destination chain because it exceeds the block gas limit.
4. Every subsequent outbound destined for that chain from the same TSS signer address remains queued behind the unusable nonce, since `GetNextNonce`/`GetPendingNonce` are strictly sequential, reproducing the LayerZero-style permanent channel block — until manual operator intervention.

Note: I was unable to fully trace whether `assignSignNonce` in `universalClient/tss/coordinator/coordinator.go` contains any nonce-skip/retry logic that might partially mitigate this (the function body wasn't fully read due to iteration limits), so the exact persistence/recoverability of the stuck-nonce condition should be verified directly in that file before treating this as fully confirmed.
