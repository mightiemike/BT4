### Title
HTTP Trigger JWT authorization binds only to method/params digest, not to DON/Gateway identity, enabling cross-DON replay of workflow-execution requests - (File: `core/utils/jwt.go`)

### Summary
`WorkflowMetadataHandler.Authorize` in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go` verifies HTTP-trigger requests using a JWT whose only content-binding is a digest over the JSON-RPC `method`+`params` (`core/utils/jwt.go`, `CreateRequestJWT`/`VerifyRequestJWT`). Nothing in the signed claims binds the token to a specific Gateway/DON instance, and replay protection (`jti` cache) is local to a single handler/DON. This mirrors the Futureswap `instantWithdraw` bug class: the signed payload is "generic enough" that a signature produced for one target can be replayed against a different, independently-authorized target that happens to accept the same signer/content.

### Finding Description
`CreateRequestJWT` computes claims as: [1](#0-0) 
The `digest` claim is `req.Digest()` (a hash of the JSON-RPC method/params only); `Audience`/`Issuer` are optional and, in the observed call sites (tests and the production request-signing helpers), are left empty: [2](#0-1) [3](#0-2) 

`VerifyRequestJWT` only checks the ECDSA signature, expiry/issuedAt bounds, `jti` presence, and that `verifiedClaims.Digest` matches the recomputed request digest — it does not check `Audience`/`Issuer` against any DON/Gateway-specific value: [4](#0-3) 

The consumer, `WorkflowMetadataHandler.Authorize`, verifies the JWT, then checks a per-handler replay cache (`h.jwtCache.isReplay(claims.ID)`) and looks up the signer against workflow-scoped authorized keys held by *that* handler instance: [5](#0-4) 

Because (1) the signed digest covers only method+params (i.e., the JSON body of the trigger request, including the workflow selector) and not any DON/Gateway identifier, and (2) the `jti` replay cache is local to a single gateway/DON handler instance, a JWT that authorizes execution on one DON is not inherently tied to that DON. If the same workflow (same owner/name/tag, hence identical `WorkflowSelector` and therefore identical request digest) with the same authorized signer key is also deployed/registered on a different DON/Gateway (e.g., a staging vs. production environment, or a second DON operated by the same organization), the identical signed JWT — captured off the wire, from logs, or from a legitimately-observed request — can be replayed verbatim against that other Gateway/DON. The second gateway's `Authorize` call will pass (signature valid, digest matches, signer is authorized for that workflow ID there, and its own local `jti` cache has never seen this token), triggering an unauthorized/duplicate workflow execution there.

This is directly analogous to the Futureswap issue: the user's signed message (`Message` struct in Futureswap; here, the JWT `digest`) contains no data that scopes it to the specific verifying contract/DON, so it can be replayed to any other verifier accepting the same signer and message shape.

### Impact Explanation
Impact is limited to griefing/DoS-style unauthorized re-triggering of a workflow execution on a different DON/Gateway than intended — not fund theft or node compromise, matching the same "no theft, but griefing vector" classification the external report gives. If the replayed workflow execution has side effects (e.g., re-sends an HTTP action, re-mints/burns based on external state, or re-triggers downstream on-chain writes), this could cause unintended duplicate business-logic execution or resource exhaustion (workflow re-execution, downstream rate limits, cache pollution) on the second DON, which is an "unsafe workflow execution" per the target impact categories.

### Likelihood Explanation
Likelihood is low-to-moderate and conditional: it requires (a) the same private key to be an "authorized key" for the same workflow ID/selector on two independently-operated DONs/Gateways, and (b) the attacker to capture the JWT in transit (it is not treated as a long-term secret and is sent as plaintext `Auth` in the JSON-RPC request). This is plausible in real CRE deployments that mirror the same workflow across multiple environments (e.g., staging/production or multi-region DONs) using the same signer, but it is not automatically exploitable against arbitrary users the way the original Futureswap bug was (where cross-dapp key reuse is common). No test or code path was found that binds the JWT to a DON/Gateway ID (e.g., via `aud`), which was not fully verifiable to the end due to index truncation of some call sites — it's possible some production callers do set `WithAudience`, which would mitigate this.

### Recommendation
Bind the JWT to the specific Gateway/DON (and ideally the specific workflow ID) by requiring and verifying a non-empty `aud` (or a dedicated claim) equal to the DON ID/Gateway identifier in `VerifyRequestJWT`, rejecting tokens whose audience does not match the serving DON. Additionally, consider including the DON ID as part of the signed digest computation itself (similar to how the Futureswap fix added the `Registry` contract address into the signed struct) rather than relying solely on optional, unenforced `aud`/`iss` claims.

### Proof of Concept
1. Deploy the same workflow (same owner, name, tag → same `WorkflowSelector`) with the same authorized signer key on two DONs/Gateways, DON-A and DON-B, both using `WorkflowMetadataHandler.Authorize`.
2. Client signs one JWT via `CreateRequestJWT(req)` (no audience) and submits it to DON-A's HTTP trigger endpoint; DON-A accepts it (`Authorize` succeeds), workflow executes, and DON-A's local `jti` cache marks the token used.
3. Attacker (or the client itself) resubmits the identical, unmodified JSON-RPC request + JWT to DON-B.
4. `VerifyRequestJWT` recomputes the same digest (same method/params), signature checks out, `claims.ID` is not present in DON-B's separate `jwtCache`, and the signer is found in DON-B's `authorizedKeys[workflowID]` — `Authorize` succeeds and the workflow executes a second, unintended time on DON-B, as demonstrated by the structure of `Authorize`: [5](#0-4)

func CreateRequestJWT[T any](req jsonrpc.Request[T], opts ...Option) (*jwt.Token, error) {
	// Apply options
	options := &jwtOptions{}
	for _, opt := range opts {
		opt(options)
	}

	expiryDuration := maxJWTExpiryDuration
	if options.expiryDuration != nil {
		expiryDuration = *options.expiryDuration
	}

	digest, err := req.Digest()
	if err != nil {
		return nil, err
	}

	var issuer string
	if options.issuer != nil {
		issuer = *options.issuer
	}

	var subject string
	if options.subject != nil {
		subject = *options.subject
	}

	var audience []string
	if options.audience != nil {
		audience = options.audience
	}

	now := time.Now()
	jti := uuid.New().String()

	claims := JWTClaims{
		Digest: "0x" + digest,
		RegisteredClaims: jwt.RegisteredClaims{
			ID:        jti,
			Issuer:    issuer,
			Subject:   subject,
			Audience:  jwt.ClaimStrings(audience),
			ExpiresAt: jwt.NewNumericDate(now.Add(expiryDuration)),
			IssuedAt:  jwt.NewNumericDate(now),
		},
	}

	return jwt.NewWithClaims(&SigningMethodEth{}, claims), nil
}

// VerifyRequestJWT verifies a signed JWT for a JSON-RPC request
// It recovers and returns the public key used to sign the JWT, checks the issuer, validates the digest,
// and performs all validations done by jwt.ParseWithClaims() including expiration checks.
func VerifyRequestJWT[T any](tokenString string, req jsonrpc.Request[T], opts ...VerifyOption) (*JWTClaims, gethcommon.Address, error) {
	options := &verifyOptions{}
	for _, opt := range opts {
		opt(options)
	}

	maxExpiryDuration := maxJWTExpiryDuration
	if options.maxExpiryDuration != nil {
		maxExpiryDuration = *options.maxExpiryDuration
	}

	issuedAtTolerance := defaultIssuedAtTolerance
	if options.issuedAtTolerance != nil {
		issuedAtTolerance = *options.issuedAtTolerance
	}
	signedString, signature, err := splitToken(tokenString)
	if err != nil {
		return nil, gethcommon.Address{}, err
	}
	decodedSignature, err := base64.RawURLEncoding.DecodeString(signature)
	if err != nil {
		return nil, gethcommon.Address{}, fmt.Errorf("signature segment is not valid base64url: %w", err)
	}
	pubKey, err := GetSignersEthAddress([]byte(signedString), decodedSignature)
	if err != nil {
		return nil, gethcommon.Address{}, err
	}
	verifiedToken, err := jwt.ParseWithClaims(tokenString, &JWTClaims{}, func(token *jwt.Token) (any, error) {
		if token.Method.Alg() != EthereumSigningMethod.Alg() {
			return nil, fmt.Errorf("unsupported JWT 'alg': '%s'. Expected '%s'", token.Method.Alg(), EthereumSigningMethod.Alg())
		}
		if _, ok := token.Method.(*SigningMethodEth); !ok {
			return nil, jwt.ErrSignatureInvalid
		}
		return pubKey, nil
	})
	if err != nil {
		return nil, gethcommon.Address{}, err
	}
	verifiedClaims, ok := verifiedToken.Claims.(*JWTClaims)
	if !ok {
		return nil, gethcommon.Address{}, errors.New("claims payload is not in the expected format")
	}
	if !verifiedToken.Valid {
		return nil, gethcommon.Address{}, errors.New("signature or claims validation failed")
	}
	reqDigest, err := req.Digest()
	if err != nil {
		return nil, gethcommon.Address{}, err
	}
	if verifiedClaims.ID == "" {
		return nil, gethcommon.Address{}, errors.New("JWT ID (jti) is required but missing")
	}
	if verifiedClaims.ExpiresAt == nil {
		return nil, gethcommon.Address{}, errors.New("expiredAt (exp) is required but missing")
	}
	if verifiedClaims.IssuedAt == nil {
		return nil, gethcommon.Address{}, errors.New("issuedAt (iat) is required but missing")
	}
	now := time.Now()
	issuedAt := verifiedClaims.IssuedAt
	if issuedAt.After(now.Add(issuedAtTolerance)) {
		return nil, gethcommon.Address{}, fmt.Errorf("issuedAt (iat) is too far in the future (beyond tolerance of %.0f seconds)", issuedAtTolerance.Seconds())
	}
	duration := verifiedClaims.ExpiresAt.Sub(verifiedClaims.IssuedAt.Time)
	if duration > maxExpiryDuration {
		return nil, gethcommon.Address{}, fmt.Errorf("token lifetime %.0f sec exceeds the maximum allowed %.0f sec. Reduce the gap between 'iat' and 'exp'", duration.Seconds(), maxExpiryDuration.Seconds())
	}
	if verifiedClaims.Digest != "0x"+reqDigest {
		return nil, gethcommon.Address{}, fmt.Errorf("claim digest '%s' does not match calculated request digest '0x%s'", verifiedClaims.Digest, reqDigest)
	}

	return verifiedClaims, pubKey, nil
}

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
