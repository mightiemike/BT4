### Title
`replay_on_archive`'s `ensure_match_transaction_info` skips checkpoint/state-root fields, so a corrupted state root can be reported as a verified replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the function `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` uses to authenticate re-executed transaction outputs against the archived, authenticated `TransactionInfo` — only checks status, gas, write-set hash (`state_change_hash`) and event root hash. It explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, which are the fields that actually bind a checkpoint version to its Merkle/JMT state root.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  checks four things: status equality, gas used, write-set hash vs `state_change_hash`, and event root hash vs `event_root_hash`. The function's own comment acknowledges the gap: [2](#0-1) 

This comment states explicitly that the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution," and flags this as something that must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`."

This is not hypothetical dead code — `storage/db-tool/src/replay_on_archive.rs` is the concrete consumer: it re-executes a chunk of historical transactions with `AptosVMBlockExecutor`, then calls `ensure_match_transaction_info` per transaction against the archived (trusted, backup-derived) `TransactionInfo` to decide pass/fail: [3](#0-2) . Because the state checkpoint hash (the value that commits to the JMT/state-tree root produced by re-execution) is never compared, `replay_on_archive` will consider a chunk "verified" even if the locally-recomputed state tree root at a checkpoint transaction diverges from the state root that is actually anchored on-chain via the transaction accumulator/`TransactionInfo`.

### Impact Explanation
`replay_on_archive` (and `aptos-debugger`, the other caller of `ensure_match_transaction_info`) is the tool operators and the Aptos team use to detect state divergence between execution and the historical, authenticated ledger — i.e., to catch exactly the class of bug that would indicate a consensus/state-computation bug or an undetected fork. Because checkpoint/state root hashes are excluded from the match check, a real state-root divergence (e.g., from a subtle VM nondeterminism, a storage bug, or a malicious archive/backup source feeding a doctored state) would silently pass replay verification. This directly undermines a proof/commitment-integrity guarantee: "authenticated state-commitment output bound to the wrong version/root is accepted as valid" by the one tool designed to catch it. This is a genuine gap in a state-integrity verification path, though its blast radius is limited to the correctness of the replay-verify tool itself (not client-facing consensus), which caps it below "critical" — I assess it as **high**.

### Likelihood Explanation
This is not a theoretical trigger — every invocation of `replay_on_archive` exercises this code path on every transaction in every chunk, and the missing checks are unconditional (not gated behind the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature; the feature only determines whether the extra hash fields are *populated*, but the comparator already omits them regardless of the flag). Any scenario that produces a state-checkpoint-hash divergence while leaving write-set/event/gas/status identical (e.g., a bug isolated to hot-state pruning, position-state committer, or JMT layer that doesn't touch the write set representation) reproduces silently.

### Recommendation
- **Short term:** In `ensure_match_transaction_info` (`types/src/transaction/mod.rs`), when the caller supplies (or the executor produces) `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, compare them against the corresponding fields on `txn_info` and fail loudly on mismatch, matching the pattern already used for `state_change_hash`/`event_root_hash`.
- **Long term:** Add regression tests in `storage/db-tool` that inject a deliberately wrong state checkpoint hash and assert that `replay_on_archive`/`aptos-debugger` fail the check, closing the gap before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled.

### Proof of Concept
Not independently reproducible from static analysis alone — the underlying bug is an intentional/acknowledged omission documented in-code (`types/src/transaction/mod.rs:2197-2202`) rather than a crash or exploit I could execute. The concrete PoC path: run `replay_on_archive` over a chunk where the VM/executor produces a `TransactionOutput` whose write set, events, gas, and status match the archived `TransactionInfo` but whose corresponding state Merkle root (checkpoint hash) differs; `ensure_match_transaction_info` returns `Ok(())` and the chunk is reported verified despite the state-root divergence.

**Note on confidence:** I verified the comparator code, its single production caller, and the explicit developer TODO comment confirming the gap, but I was not able to trace how/whether `state_checkpoint_output`'s hashes are otherwise cross-checked elsewhere in the `replay_on_archive`/`aptos-debugger` pipeline (e.g., via a separate root-hash check outside `ensure_match_transaction_info`) due to remaining tool-call budget; if such an out-of-band check exists it would mitigate this finding's likelihood.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
