## Finding

### Title
Self-trading via `MarketSellAssetActuator` causes the maker-side settlement to be silently overwritten and lost - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator` (TRC10 order-book "market sell" instruction) settles a taker/maker match by mutating an in-memory `AccountCapsule` for the taker but re-fetching a **fresh, stale copy** of the account from the `AccountStore` for the maker and immediately persisting it. When the taker and the maker are the *same account* (a self-trade, which is trivially reachable by any user broadcasting a `MarketSellAssetContract` that matches their own resting order), the final `accountStore.put()` in `execute()` — which writes back the taker's in-memory capsule — overwrites the maker-side credit that was just written to the store, permanently discarding the proceeds of the maker fill.

### Finding Description
`MarketSellAssetActuator.execute()` loads the taker's `AccountCapsule` once at the top of the method and passes that same in-memory object through order creation and matching, only persisting it once, at the very end: `accountStore.put(accountCapsule.createDbKey(), accountCapsule);` [1](#0-0) 

Inside `matchSingleOrder`, the taker's credit is applied directly to that same in-memory object (no store write yet): [2](#0-1) 

```java
addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule);
addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive);
```

The taker-side overload just mutates the passed-in capsule: [3](#0-2) 

But the maker-side overload independently re-reads the account **from the store** (a stale copy that has not seen any of the current transaction's mutations), applies the credit, and writes it straight back to the store: [4](#0-3) 

When the taker's order self-matches against the taker's own earlier resting order (maker == taker, same owner address), both code paths operate on the *same account key* but on two divergent in-memory objects:
1. The maker-path fetch/put persists `stale_state + makerBuyTokenQuantityReceive` to the store immediately.
2. The final `accountStore.put()` in `execute()` then overwrites that with `taker_in_memory_state + takerBuyTokenQuantityReceive` — a version that never saw the maker credit — discarding it entirely.

This is the exact bug class described in the external report: special/asymmetric handling of maker vs. taker settlement when they are actually the same identity leads to loss of one side's expected balance credit, because the code was written assuming maker and taker are always distinct accounts.

### Impact Explanation
Any user can lose their own maker-side settlement proceeds (TRX or TRC10 tokens) whenever their own new sell order matches against their own previously-resting order on the same market pair. This is a direct asset-accounting corruption bug reachable purely through a normal, unprivileged `MarketSellAssetContract` broadcast transaction — no special permissions, validator role, or malicious peer needed. It results in silent, permanent loss of value credited to the user's account, exactly mirroring the "loss of funds" impact called out in the source report (although here it manifests as full loss of the maker credit rather than merely a missing free-balance increment).

### Likelihood Explanation
Triggering the bug requires only that a single account first place a limit sell order and later place another sell order on the opposite side (buy) of the pair that price-matches the same account's own resting order — a trivial, deterministic sequence any user (accidentally or intentionally) can construct with two ordinary transactions. `MarketSellAssetActuatorTest` contains no test exercising this same-owner match scenario, indicating it is unhandled/untested in the actuator logic.

### Recommendation
`matchSingleOrder`/`addTrxOrToken` should not fetch-and-persist the maker's account independently of the taker's in-memory object. Instead:
- Detect when `makerOrderCapsule`'s owner equals the taker's owner and apply both the taker and maker credits/debits to the *same* in-memory `AccountCapsule` object before a single, final `accountStore.put()`, or
- Always load the maker account once per match into a cache keyed by address (reusing the taker's own in-memory object when addresses match) rather than doing independent read-modify-write cycles for the maker inside `addTrxOrToken(MarketOrderCapsule, long)`.

### Proof of Concept
1. Account A creates a sell order: sell 100 TOKEN_B for 100 TOKEN_A (maker order), which rests in the order book.
2. Account A creates a second order: sell 100 TOKEN_A for 100 TOKEN_B (taker), which price-matches and fully fills against A's own resting maker order from step 1.
3. During `matchSingleOrder`, `addTrxOrToken(takerOrderCapsule, ..., takerAccountCapsule)` credits TOKEN_B to A's in-memory taker capsule; `addTrxOrToken(makerOrderCapsule, ...)` separately fetches A's account from the store, credits TOKEN_A, and writes it back.
4. `execute()` finishes by calling `accountStore.put()` with the taker's in-memory capsule (which lacks the TOKEN_A maker credit), overwriting the store and erasing the TOKEN_A credit that was written in step 3.
5. Result: account A ends up missing the TOKEN_A proceeds from the maker fill of its own order — a silent loss of funds analogous to the reported DEX self-trade bug.
