### Title
Unbounded per-cycle reward-recomputation loop in `MortgageService.computeReward`/`getOldReward` allows DoS via broadcast vote/freeze/withdraw transactions - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.withdrawReward()` / `queryReward()` — invoked from ordinary, unprivileged broadcast transactions (`VoteWitnessContract`, `UnfreezeBalanceContract`, `UnfreezeBalanceV2Contract`, `WithdrawBalanceContract`) — call `computeReward(beginCycle, endCycle, accountCapsule)`, which for any cycle range prior to `newRewardAlgorithmEffectiveCycle` falls back to `getOldReward()`. That fallback runs a raw `for (long cycle = begin; cycle < end; cycle++) computeReward(cycle, votes)` loop whose length is proportional to the number of maintenance cycles elapsed since the account last interacted with voting/freezing (`beginCycle`), each iteration itself iterating over every one of the account's votes. This is directly analogous to the Sherlock/Carapace H-9 pattern: a critical, unbounded loop over accumulated on-chain state, reachable from a single ordinary transaction, with no cap on iteration count.

If `dynamicPropertiesStore.allowOldRewardOpt()` is not enabled, this executes a plain sequential loop from `begin` to `end` (both proportional to elapsed maintenance cycles, which accrue automatically over time via `MaintenanceManager.doMaintenance()`), and for every cycle it calls `computeReward(cycle, votes)`, which itself loops over every vote entry the account holds (up to `MAX_VOTE_NUMBER`): [6](#0-5) 

Each inner iteration performs two store reads (`delegationStore.getReward`, `delegationStore.getWitnessVote`). The total cost of a single `withdrawReward()` call is therefore `O(cycles_elapsed × votes)` DB reads, executed synchronously and unmetered (no TVM energy accounting) inside normal actuator `execute()`/`validate()` processing during block generation — unlike the `VoteRewardUtil` TVM-path variant which is gated behind `VMConfig.allowTvmVote()`, this non-VM path has no energy limit to bound the work.

Because `beginCycle`/`endCycle` bookkeeping is only advanced when `withdrawReward()` successfully runs, an account that stays dormant (never votes/unfreezes/withdraws) accumulates an ever-growing cycle gap. When it finally submits any of the affected transaction types, the actuator must walk through the entire accumulated cycle range synchronously as part of ordinary block/transaction processing — this is functionally identical to the Sherlock report's pattern of looping over an unbounded, attacker/time-growable collection inside a "critical" state-transition function.

### Impact Explanation
A sufficiently dormant account (one whose `beginCycle` predates `newRewardAlgorithmEffectiveCycle` by many maintenance cycles, and/or that holds up to `MAX_VOTE_NUMBER` votes) can, via a single ordinary broadcast transaction (vote, unfreeze, or withdraw), force the processing node to execute a large number of sequential loop iterations and store reads with no energy/gas accounting to cap the cost. This can:
- Slow down or stall transaction processing for that transaction, potentially causing the node to exceed block production timing budgets (`Manager.generateBlock` timeout checks), effectively acting as a denial-of-service against block production.
- Make the affected account practically unable to withdraw/vote if the computation becomes prohibitively expensive, mirroring the Carapace report's outcome ("protection buyers won't be covered ... contract useless").

Because this executes outside TVM energy metering (unlike the `VoteRewardUtil`/TVM equivalent, which is bounded by `maxEnergyLimit`), there is no built-in throttle on the amount of work a single transaction can trigger through this code path.

### Likelihood Explanation
Reachability requires no privileged role — any account holder can trigger the vulnerable path by simply not calling any vote/freeze/withdraw actuator for a long time and then submitting one. This is a normal usage pattern (long-term "set and forget" freezers/voters are common on TRON), so the precondition (large cycle gap) can arise organically, and an attacker can also deliberately create and let dormant such accounts age before triggering the transaction to maximize node cost. The severity is mitigated somewhat by `allowOldRewardOpt()`/`RewardViCalService`, which — when enabled — replaces the raw per-cycle loop with an O(1) delta-lookup via precomputed `Vi` accumulators; however, the raw loop remains present as the un-gated fallback and is unconditionally reachable whenever that optimization flag is off or for state predating its historical window boundaries. I could not fully verify from the indexed code whether `allowOldRewardOpt` is enabled by default on all currently deployed networks; this determination would require checking the deployed dynamic parameter value/committee proposal history, which is outside what the indexed code confirms.

### Recommendation
Ensure the O(1)/precomputed reward path (`RewardViCalService`/`allowOldRewardOpt`) is unconditionally used for the entire historical cycle range, removing the raw sequential fallback loop in `MortgageService.getOldReward()`, or otherwise bound the number of cycles a single transaction may traverse (e.g., cap processed cycles per call and require multiple calls to fully catch up, similar to the batched mitigation adopted for `_accruePremiumAndExpireProtections` in the referenced report). Additionally, consider metering this synchronous work against a resource/time budget so that a pathological dormant account cannot stall block production.

2. 3. Have `A` vote for `MAX_VOTE_NUMBER` witnesses to maximize the inner-loop multiplier.
4. Submit any transaction from `A` that triggers `MortgageService.withdrawReward(A)` (e.g., `WithdrawBalanceContract`).
5. Observe that `computeReward(beginCycle, endCycle, accountCapsule)` invokes `getOldReward()`'s `for (long cycle = begin; cycle < end; cycle++)` loop `N` times, each doing `MAX_VOTE_NUMBER` store reads — i.e. `N × MAX_VOTE_NUMBER` synchronous store lookups performed inside normal transaction processing, unbounded by any energy/gas metering.

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
