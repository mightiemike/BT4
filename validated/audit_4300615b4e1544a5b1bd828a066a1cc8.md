### Title
`last-update` clock is only advanced when the index changes, letting `next-index`/`next-liquidity-index` use a stale timestamp to compute interest for an incorrect elapsed period - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The vault `accrue` function only writes `last-update` to `stacks-block-time` when the computed `index`/`lindex` actually differ from their previous values. When the interest calculation yields no change to the index for a block (e.g., zero utilization, zero rate, or a very short elapsed time that rounds down to no change), `last-update` is left untouched even though block time has advanced. The next call to `accrue` then computes `time-delta` against this stale `last-update`, using a larger-than-actual elapsed duration for the interest multiplier calculation.

### Finding Description
In `v0-vault-stx.clar` (and the equivalent `vault-sbtc`, `vault-ststx`, `vault-usdc`, `vault-usdh`, `vault-ststxbtc` files), `accrue` computes the next index values and only conditionally persists the new clock: [1](#0-0) 

```clarity
(define-public (accrue)
  ...
  (if (not (is-eq idx next))
      (var-set index next)
      false)
  (if (not (is-eq lidx nliq))
      (var-set lindex nliq)
      false)
  ...
  (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
      (var-set last-update stacks-block-time)
      false)
  (ok { index: next, lindex: nliq })))))
```

`time-delta` used inside `calc-multiplier-delta` (called from `next-index`/`next-liquidity-index`, driven by `last-update`) is the elapsed time since the last stored `last-update`, not since the last block. Because the write to `last-update` is gated on the index actually changing, any accrue call where the computed multiplier rounds `index` back to the same value (routine for near-zero utilization/rate, or for very small time deltas due to integer division truncation in `mul-div-down`/`mul-div-up`) leaves the old `last-update` in place. Subsequent calls to `borrow`, `repay`, `redeem`, `deposit`, or `liquidate` (all of which call `accrue`/`accrue-and-cache` before mutating state) will then compute interest as if the elapsed time spans from that old, stale timestamp all the way to the current block — i.e., the accrued interest window silently accumulates extra unaccounted seconds/blocks that were never applied because the intermediate accrue's index recomputation happened to round to no change.

This matches the "clock advanced only on change" bug class: the timestamp used to gate a calculation is only invalidated/refreshed conditionally, not unconditionally on every block/observation, allowing state elsewhere (utilization, rate curve, borrowed principal) to shift in between while the clock silently lags. [2](#0-1) 

The interest multiplier calculation (`calc-multiplier-delta`, shared math in every vault contract) is directly driven by this `last-update`-derived `time-delta`: [3](#0-2) 

### Impact Explanation
Because `time-delta` grows unbounded across any accrue calls that don't trigger an index change, once the rate/utilization does become non-zero, the next `accrue` will apply the borrow/liquidity rate over an inflated multi-block time window instead of the correct single-block window. This causes debt (`total-debt`) and liquidity index (`lindex`) to be miscalculated — either understating interest owed by borrowers for a period (temporary freezing/loss of yield to lenders) or, once accrued, overstating interest in a lump sum that is charged against `total-borrowed`/`assets` incorrectly relative to actual elapsed exposure. This falls into the High-severity "temporary freezing of unclaimed yield" impact bucket, since lenders' accrued liquidity-index gains are delayed/miscalculated relative to actual time elapsed, and reserve/treasury minting (`treasury-lp`) tied to `reserve-inc` is similarly skewed.

### Likelihood Explanation
This requires no attacker action beyond normal usage: any period of zero/near-zero utilization or rate (common for a freshly deployed or lightly used vault, or briefly after a `system-repay` that fully repays debt) is sufficient to trigger the stale-clock condition, since `next-index`/`next-liquidity-index` will legitimately compute `next == idx` in that state. It is a routine single-transaction/per-block-observation issue rather than requiring adversarial interleaving, making it moderately likely to occur in normal vault operation over time.

### Recommendation
Persist `last-update` unconditionally on every successful `accrue` call (when not paused), regardless of whether `index`/`lindex` changed, so that `time-delta` for the next accrue is always measured from the true previous observation time rather than from the last time the index happened to move.

### Proof of Concept
1. Vault is deployed with `index = INDEX-PRECISION`, `lindex = INDEX-PRECISION`, `last-update = T0`, and zero outstanding debt (rate/utilization = 0).
2. At block time `T1` (say 100 blocks later), a user calls `deposit`, which triggers `accrue`. `next-index`/`next-liquidity-index` compute `next == idx` and `nliq == lidx` (since rate/utilization is 0 or multiplier rounds to the same integer value), so per the code in [4](#0-3)  neither `index`/`lindex` nor `last-update` are updated — `last-update` remains `T0`.
3. Between `T1` and `T2` (further 1000 blocks later), a large borrow raises utilization/rate above zero.
4. At `T2`, any state-mutating call triggers `accrue` again. `calc-multiplier-delta` computes `time-delta = T2 - T0` (1100 blocks) instead of the correct `T2 - T1` (1000 blocks) window during which the rate was actually non-zero, applying the non-zero rate over an inflated window that includes the earlier zero-rate period, mis-crediting/mis-charging interest relative to real elapsed exposure.
