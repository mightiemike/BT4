### Title
Precision loss in legacy per-cycle vote reward calculation causes permanent loss of witness reward funds - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` splits a fixed witness reward pool among voters using floating-point percentage math (`voteRate = userVote/totalVote`, `reward += voteRate * totalReward`). Because each voter's share is independently computed and truncated to a `long`, the sum of all individually-rounded shares can be strictly less than `totalReward`, and there is no mechanism to reclaim or redistribute the shortfall. This mirrors the Debita `claimIncentives()` root cause: percentage-based distribution of a fixed pool with per-claimant rounding and no sweep/withdraw path for the residual.

### Finding Description
When a voter withdraws their vote reward for a cycle prior to the new VI-based algorithm's effective cycle, `withdrawReward()`/`queryReward()` call `computeReward(long beginCycle, long endCycle, AccountCapsule)`, which for old cycles delegates to `getOldReward()` → `computeReward(cycle, votes)`: [1](#0-0) 

Here, `totalReward` is a fixed value recorded once per cycle via `delegationStore.addReward(cycle, witnessAddress, value)` in `payReward()`: [2](#0-1) 

Each voter's share is computed as `(double) userVote / totalVote * totalReward`, then narrowed to `long` on assignment to `reward` (a `long` accumulator). Because this division/multiplication is performed independently for each voter and each result is truncated, the sum of all voters' claimed rewards for a witness in a cycle is generically `totalReward - ε`, where `ε` grows with the number of distinct voters — exactly the same rounding pattern described in the Debita report (`porcentageLent = (lentAmount * 10000) / totalLentAmount` truncated per claimant). `delegationStore.getReward(cycle, srAddress)` is never decremented as voters withdraw and there is no function anywhere in `MortgageService`, `DelegationStore`, or the actuators to reclaim the residual `ε` after all voters have withdrawn for that cycle.

This TRX was already deducted from real accounts (via `Commons.adjustBalance` when block rewards/tx fees are produced) and is only ever re-credited to accounts through `adjustAllowance()`. Any amount lost to this rounding is TRX that is deducted from the funding source but never credited to any account — it disappears from active circulation permanently, unlike the fully-precise BigInteger-based `computeReward(long beginCycle, long endCycle, AccountCapsule)` path used after `newAlgorithmCycle`, which multiplies by `DelegationStore.DECIMAL_OF_VI_REWARD` before dividing to avoid this exact class of loss: [3](#0-2) 

The presence of the hardened, BigInteger-based VI algorithm alongside the un-hardened legacy double-based `computeReward(cycle, votes)` confirms that the double-based path is recognized internally as an imprecise legacy computation, but it is still reachable by any address holding votes cast before `newAlgorithmCycle` whenever they call `withdrawReward`/`queryReward`.

### Impact Explanation
For every witness/cycle pair with multiple voters, a small but nonzero amount of TRX reward is permanently unclaimable by any account — analogous to the Debita incentivizer/user loss. Unlike an isolated rounding of a single value, this loss compounds across every witness and every legacy cycle with more than a couple of voters, and there is no code path to reclaim or sweep it, so it is a systemic (if small per-instance) drain of TRX from the reward accounting with no corresponding beneficiary — an unrecoverable accounting divergence.

### Likelihood Explanation
This is triggered automatically by ordinary voters calling the standard `withdrawReward` flow (unprivileged, always reachable) for any cycle prior to `newRewardAlgorithmEffectiveCycle`; no special preconditions beyond having voted for a witness alongside other voters in the same cycle are required. It occurs on essentially every multi-voter cycle rather than being a rare edge case.

### Recommendation
Replace the double-based percentage computation in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` with an integer/BigInteger-based proportional formula consistent with the VI-reward path (e.g., scale by a fixed precision constant before dividing, as already done via `DelegationStore.DECIMAL_OF_VI_REWARD`), or add an explicit sweep mechanism that tracks and reclaims/redistributes any residual `totalReward` left unclaimed after all voters for a cycle have withdrawn.

### Proof of Concept
Given a witness with `totalReward = 1000` for a cycle and 3 voters each with `userVote = 1` out of `totalVote = 3`:
- `voteRate = 1/3 = 0.3333...`
- Each voter's `reward += voteRate * totalReward` = `333.33...` → truncated to `333`
- Sum claimed by all 3 voters = `333 * 3 = 999`
- `1` unit of TRX is permanently unclaimable — `delegationStore.getReward(cycle, srAddress)` still logically "owed" `1000`, but no code path exists to credit or reclaim the missing `1`. [1](#0-0)

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
