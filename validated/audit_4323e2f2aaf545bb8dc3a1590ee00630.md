### Title
Unbounded per-account TRC10 asset map causes O(n) iteration in `BandwidthProcessor.updateUsage`, enabling a griefing/DoS vector via bandwidth (net) metering - ([File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java])

### Summary
`BandwidthProcessor.updateUsage(AccountCapsule)` iterates over an account's entire TRC10 `assetMap`/`assetMapV2` on every bandwidth-usage recalculation. [1](#0-0)  This mirrors the reported bug class ("iterate over user's positions ... hitting gas/processing limits") but instead of a user's own staking positions, the unbounded collection is the account's asset map, which can be inflated by *any third party* sending the victim account many distinct TRC10 tokens.

### Finding Description
`updateUsage` loops over `accountCapsule.getAssetMap()` (when `allowSameTokenName == 0`) and always loops over a merged `assetMapV2`/`getAllFreeAssetNetUsageV2()` map (regardless of the same-token-name flag), calling `increase(...)` per entry: [1](#0-0) 

There is no bound on the number of distinct assets an account can accumulate: `addAssetAmountV2`/`addAssetV2` simply insert new map entries for each newly-seen token without any cap: [2](#0-1) [3](#0-2) 

Since TRC10 tokens are transferred to a victim's account by `TransferAssetContract` initiated by *any* account (the attacker), an attacker can issue many token IDs and send trace amounts of each to a target address, inflating the target's `assetV2` map arbitrarily. Every subsequent `getAccountResource` RPC call and every future transaction from (or touching) that account invokes `BandwidthProcessor.updateUsage`, which is now O(n) in the poisoned map size: [4](#0-3) 

This is directly analogous to the reported issue class: an unbounded, attacker/user-influenced collection is iterated in full inside a function invoked as part of normal transaction/account-state processing, with no batching or pagination mechanism, risking degraded per-block processing time as the collection grows.

### Impact Explanation
Impact is a resource-exhaustion / griefing vector rather than fund loss: transactions/RPC calls touching a victim account with a bloated asset map become slower to process (CPU cost proportional to map size), and because `updateUsage` runs during block/transaction processing (via bandwidth consumption paths and `getAccountResource`), a sufficiently large map could measurably increase per-transaction and per-block processing time on all full nodes validating blocks involving that account, which is a DoS/availability concern rather than a direct fund-safety break. Severity is bounded by the cost of issuing many TRC10 tokens (each requires a chain fee/deposit), which raises the bar for an attacker but does not eliminate the vector.

### Likelihood Explanation
Medium-low: exploitation requires the attacker to pay TRC10 issuance costs for many distinct tokens and to send them to the victim, and TRON's TRC10 issuance fee (`AssetIssueFee`) makes large-scale abuse costly but not infeasible for a well-funded attacker targeting a specific high-value account (e.g., an exchange hot wallet or DApp treasury) to degrade its subsequent transaction/RPC performance.

### Recommendation
Impose a maximum number of distinct TRC10 asset entries an account may hold (reject/cap further `TransferAssetContract` transfers of new asset IDs beyond the cap in `TransferAssetActuator`), and/or refactor `BandwidthProcessor.updateUsage` to lazily recompute per-asset free-bandwidth usage only for the specific asset involved in the current transaction rather than iterating the full map unconditionally.

### Proof of Concept
Conceptual (not executed): (1) Attacker issues N TRC10 tokens (paying issuance fee each time). (2) Attacker calls `TransferAssetContract` to send 1 unit of each of the N tokens to victim address V, causing `AccountCapsule.addAssetAmountV2` to add N entries to V's `assetV2` map with no upper bound. (3) Any subsequent transaction touching V, or an RPC call to `getAccountResource`, invokes `BandwidthProcessor.updateUsage`, which iterates all N entries via the `map.forEach` at [5](#0-4) , incurring processing cost linear in N with no cap enforced anywhere in the codebase reviewed.

  public boolean addAssetAmountV2(byte[] key, long amount,
      DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    //key is token name
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAsset(nameKey, addExact(currentAmount, amount, disableJavaLangMath))
          .putAssetV2(tokenID, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenIDStr = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenIDStr);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAssetV2(tokenIDStr, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    return true;
  }
