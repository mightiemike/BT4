### Title
Pause of interest accrual silently freezes yield instead of reverting - (File: `mainnet/contracts/vault/v0-vault-stx.clar`, and identically in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`)

### Summary
Each vault's `accrue` function checks the `accrue` flag in `pause-states`. When set, it returns the *last cached* `index`/`lindex` pair and exits early, without updating any state, rather than reverting the calling operation. This matches the allowed analog class "a pause that passes through instead of reverting."

### Finding Description
`accrue` reads current state and, if paused, short-circuits to `(ok { index: idx, lindex: lindex })` — the values already in `var-get index` / `var-get lindex` — without touching `last-update`, `principal-scaled`, or minting the treasury share of the newly-accrued (in this case zero) interest: [1](#0-0) 

Every state-mutating vault entrypoint (`deposit`, `redeem`, `system-borrow`, `system-repay`) unconditionally calls `(try! (accrue))` at the top of its `let` binding and proceeds to use the (possibly stale) `index`/`lindex` values to price shares, mint/burn `zft`, and move `assets`, regardless of whether accrual actually happened: [2](#0-1) [3](#0-2) 

Because accrual "succeeds" (returns `ok`) instead of reverting when paused, all downstream logic that depends on `accrue` having brought the index current — deposit/redeem share pricing (`convert-to-assets-preview`/`convert-to-shares-preview`), debt-cap checks in `system-borrow`, and reserve-factor treasury minting — silently operates on stale indexes for the entire duration the accrue-pause flag is set. No caller (including `market.clar`, which calls these vaults transitively via `vault-accrue`/`accrue-and-cache`) is informed that accrual did not occur; from their perspective the call returned `ok` normally.

### Impact Explanation
While `deposit`/`redeem` at a frozen (stale) share price is arguably neutral if the price simply doesn't move, the real consequence is on protocol reserves: the reserve-factor/treasury-share minting logic (`reserve-inc`, `treasury-lp`, `(try! (ft-mint? zft treasury-lp .dao-treasury))`) only executes inside the "not paused" branch of `accrue`. Debt continues to accrue implicitly to borrowers via `total-debt`/other reads that use `next-index`-independent computations is not the case here — because `index`/`lindex` are frozen, *no* interest is computed or attributed to suppliers or to the treasury for the whole pause window, even though vault operations (deposits/redeems/borrows) keep happening using the stale index. This results in a permanent freezing (loss) of the yield/reserve amount that should have accrued to LPs and the DAO treasury during the pause window — it is never retroactively recovered once unpaused, since `next-index`/`next-liquidity-index` are computed from `last-update`, and if `last-update` itself was never advanced during the paused window, the subsequent unpause recomputes interest from the last real update, but any deposits/redeems executed mid-pause were settled at the wrong (frozen) price, permanently misallocating value between users who transacted during the pause and the pool. This lands on the in-scope "temporary/permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
This does not require any privileged/DAO compromise beyond the intended ability to flip `pause-states` (an admin lever, likely intended for emergency response) — the bug is that pausing accrual doesn't pause dependent operations, it just silently disables interest math while dependent operations continue. Any deposit/redeem/borrow/repay executed while `accrue` is paused, in a single transaction, will use the stale index and never true-up.

### Recommendation
When `(get accrue states)` is true, either (a) make `accrue` return an error so all dependent operations (`deposit`, `redeem`, `system-borrow`, `system-repay`) revert instead of silently proceeding with stale indexes, or (b) if pass-through is intentional, also pause `deposit`/`redeem`/`system-borrow`/`system-repay` whenever `accrue` is paused so no value-changing operation can execute against a frozen index.

### Proof of Concept
1. DAO/admin sets `pause-states` with `accrue: true` on `v0-vault-usdc` (or any vault) via `set-pause-states`.
2. Time passes; real interest would have accrued (`next-index`/`next-liquidity-index` would be higher than stored `index`/`lindex`).
3. A user calls `redeem`, which calls `(try! (accrue))` — this returns `ok` with the stale `idx`/`lindex` instead of reverting.
4. `redeem` proceeds to compute `inkind` via `convert-to-assets-preview` using the stale liquidity index, and completes the redemption normally — no revert, no error signaling that accrual was skipped.
5. Because the "not paused" branch (which computes `reserve-inc`/`treasury-lp` and mints to `.dao-treasury`) never ran, the interest/yield that should have been attributed to the pool/treasury for this period is never minted or accounted for — it is permanently lost for that window, since `last-update` is unchanged and the elapsed time is not retroactively re-applied once the vault is unpaused (the next `accrue` call computes interest only from `last-update` to `stacks-block-time` under the *current*, not historical, state). [4](#0-3)
