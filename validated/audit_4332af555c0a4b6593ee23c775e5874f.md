### Title
Reward dilution via vote-count inflation at DPoS maintenance cycle boundary - (`consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`, `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The Ethereum Credit Guild `SurplusGuildMinter` bug lets an attacker inflate `_gaugeWeight` right before `notifyPnL()` and immediately unstake afterward, diluting every other guild holder's reward while claiming a disproportionate share for a momentary stake. java-tron's DPoS witness-vote reward system exhibits the same structural pattern: the total-vote denominator used to compute every voter's reward share for a whole cycle is fixed once, at the maintenance boundary, from whatever votes exist at that instant, while the voter's own eligibility snapshot for that same cycle is captured lazily on the *next* action — creating a window where a large, momentary vote can both dilute long-term voters and be paid out to the transient voter.

### Finding Description
Reward accrual for TRON witnesses/voters is computed with a per-cycle "Vi" (vote index) delta model:

- `MaintenanceManager.doMaintenance()` applies all pending vote deltas from `VotesStore` (accumulated during the whole current epoch via `countVote`) onto `witnessCapsule.setVoteCount(...)`, then immediately snapshots this *just-updated* total vote count as the fixed denominator for the **next** cycle: `delegationStore.setWitnessVote(nextCycle, witness.createDbKey(), witness.getVoteCount())`. [1](#0-0) [2](#0-1) 

- Block/transaction-fee rewards accumulated during a cycle are recorded per witness via `delegationStore.addReward(cycle, witnessAddress, value)`. [3](#0-2) 

- An individual voter's reward for a cycle is `userVote / totalVote(cycle) * totalReward(cycle)` (old algorithm) or a Vi-delta multiplication (new algorithm), computed lazily by `MortgageService.withdrawReward` / `computeReward`, which relies on a **per-account, per-cycle vote snapshot** (`delegationStore.getAccountVote`/`setAccountVote`) that is only refreshed the next time the account calls `VoteWitnessActuator`, `UnfreezeBalanceV2Actuator`, or `WithdrawBalanceActuator` (all of which call `mortgageService.withdrawReward()` first, using the account's *pre-action* vote list, before the new/cleared votes are applied). [4](#0-3) [5](#0-4) [6](#0-5) 

Because the total-vote denominator for cycle *N+1* is locked in at the maintenance instant from whatever votes exist right then, and because unfreezing frozen TRX (`UnfreezeBalanceV2Contract`) only defers the return of principal (14-day withdrawal delay) but does **not** require waiting to remove the resulting vote/tron-power, an account can:
1. Freeze a large amount of TRX and cast a large vote for a target witness right before a maintenance boundary.
2. At maintenance, this inflates `witnessCapsule.getVoteCount()` and thus the fixed `totalVote(cycle N+1)` denominator used to divide up cycle N+1's rewards among *all* voters of that witness, diluting every genuine long-term voter's share for the entire cycle.
3. Immediately after maintenance, call `UnfreezeBalanceV2` (or vote with an empty list) to clear the vote going forward — this action's `mortgageService.withdrawReward()` call snapshots the account's vote list for the just-started cycle N+1 (`delegationStore.setAccountVote(N+1, address, accountCapsule)`) using the still-large vote list that existed at the top of that call, *before* `updateVote`/`clearVotes` runs.
4. On any subsequent action, `computeReward` uses this persisted cycle-N+1 snapshot with the full inflated vote count to pay the attacker a share of cycle N+1's reward pool proportional to a vote that was, in practice, only held for an instant around the maintenance boundary.

This mirrors the reported bug class: transient influence over a reward-accounting checkpoint (`_gaugeWeight`/`notifyPnL` in the ECG report vs. `witness.voteCount` snapshot/`doMaintenance` in java-tron) both dilutes genuine long-term participants and lets the manipulator collect disproportionate rewards.

### Impact Explanation
Real, long-term GUILD-analogue voters (TRX holders who vote for a witness and keep their vote for the full cycle) receive a diluted share of that cycle's block/transaction-fee rewards, while the transient voter captures a reward slice proportional to a vote they held only momentarily. This is an unprivileged resource/reward-accounting corruption affecting the consensus incentive layer (`MortgageService`, `DelegationStore`, `MaintenanceManager`), reachable by any account submitting ordinary `FreezeBalanceV2`, `VoteWitness`, and `UnfreezeBalanceV2` contracts through normal broadcast transactions — no special privilege required.

### Likelihood Explanation
Likelihood is limited by several practical factors: the attacker must actually freeze real TRX (locking capital, though not for the reward-cycle's full duration since unfreezing tron power itself is not delayed, only principal withdrawal is), must time the vote transaction to land in the last block(s) before a maintenance boundary, and the payoff scales with the fraction of total reward pool captured relative to capital committed and the target witness's total existing vote base — for cycles/witnesses with large existing vote totals, the dilution/gain is proportionally small, similar to the low severity assessed in the original report ("GUILD holders' interest split is small"). This makes it a real but likely low-to-medium severity griefing/self-dealing vector rather than a critical one.

### Recommendation
Decouple the per-cycle vote-count denominator used for reward division from votes cast in the final moments before a maintenance boundary — e.g., require votes to be "active" for at least one full completed cycle before counting toward the reward-share denominator, or snapshot each voter's per-cycle vote record atomically with the same total-vote-count snapshot taken during `doMaintenance` rather than lazily on the next unrelated action. Alternatively, disallow unvoting/unfreezing that would remove tron power within the same cycle a vote was cast, or apply a minimum holding period for votes before they are eligible to be counted for `withdrawReward` reward computation.

### Proof of Concept
Conceptual sequence (would need to be validated against a running java-tron testnet):
1. Freeze `X` TRX via `FreezeBalanceV2Contract` and cast `VoteWitnessContract` votes for target witness `W` in the last block(s) of cycle `N`.
2. Let `MaintenanceManager.doMaintenance()` run: `W.voteCount` increases by the attacker's vote, and `delegationStore.setWitnessVote(N+1, W, W.getVoteCount())` snapshots the inflated total as the fixed denominator for cycle `N+1`.
3. Immediately submit `UnfreezeBalanceV2Contract` (or vote with an empty list) — this calls `mortgageService.withdrawReward(owner)` first, which persists `delegationStore.setAccountVote(N+1, owner, accountCapsuleWithLargeVote)` before `updateVote` clears the vote.
4. During cycle `N+1`, real long-term voters of `W` accrue reward at a rate diluted by the attacker's inflated denominator.
5. After cycle `N+1` completes, the attacker triggers any action calling `withdrawReward` again; `computeReward(N+1, N+2, accountCapsuleWithLargeVote)` pays out a reward share proportional to the vote recorded in step 3, despite the vote having been cleared immediately after maintenance.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
