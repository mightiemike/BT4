### Title
Missing deadline/expiration binding to price-slippage protection in `ExchangeTransactionActuator` (Bancor-style exchange) - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
The `ExchangeTransactionContract` used by `ExchangeTransactionActuator` provides only a static minimum-output check (`expected`), analogous to `minOutputAmount` in `sellAllAmount()`/`buyAllAmount()`, but carries no user-specified deadline tying that slippage guarantee to a time window. [1](#0-0)  A signed exchange transaction can sit unconfirmed and later be broadcast/included when pool reserves have shifted; only the coarse `expected` bound protects the user, exactly the bug class in the external report.

### Finding Description
`ExchangeTransactionContract` only carries `owner_address`, `exchange_id`, `token_id`, `quant`, and `expected` (minimum output) — no expiration/deadline field scoping how long that `expected` value remains valid. [2](#0-1)  In `ExchangeTransactionActuator.execute`, the actual output is computed at execution time via `exchangeCapsule.transaction(...)` against the pool's *current* `firstTokenBalance`/`secondTokenBalance`, and is only checked against the caller-supplied `expected` inside `doValidate()` (the "token required must greater than expected" check confirmed by tests). [3](#0-2) [4](#0-3)  The bonding-curve math itself lives in `ExchangeCapsule.transaction`, which is purely a function of the pool's live balances at the moment of execution, with no timestamp/expiry input at all. [5](#0-4) 

This differs from Ethereum mempools in that Tron transactions do carry a generic `raw_data.expiration` field enforced by the node/consensus layer, which bounds how long *any* transaction can remain unconfirmed before the network rejects it outright. However, that generic expiration is a network-level anti-replay/anti-staleness control, not a user-tunable, exchange-specific deadline coupled to `expected`; it does not close the underlying price-staleness gap described in the external report, since the default/allowed expiration window (extendable by chain parameters, historically up to hours) is large relative to expected on-chain pool price movement, and the `expected` value is fixed at signing time regardless of how close to expiration the transaction is executed. I was not able to fully verify the exact configured default/maximum expiration window and whether it has been tightened in this codebase (`common/src/main/java/org/tron/core/config/args/MiscConfig.java`, `framework/src/main/java/org/tron/core/db/Manager.java` reference `expiration` logic but I did not get to inspect their content before running out of iterations), so the precision of the exploitable time window is uncertain.

### Impact Explanation
If a user signs an `ExchangeTransactionContract` with a conservative `expected` (minimum-output) to allow for normal slippage, and the transaction remains unconfirmed (e.g., due to low fee/congestion, or deliberately delayed rebroadcast by a party controlling the signed transaction) up until close to the network's expiration boundary, the trade can execute against a pool state that has moved substantially from what the signer anticipated — while still nominally satisfying the fixed `expected` floor. This can cause economic loss to the trader (worse execution price than intended) without any error being raised, since `ExchangeTransactionActuator` has no way to reject the transaction for being "stale" relative to the trader's intent, only for violating the static `expected` floor.

### Likelihood Explanation
Likelihood is *lower* than the pure-Ethereum analog because java-tron transactions already have a protocol-level `expiration` field that bounds staleness for all transactions (which the external report's judge also noted reduces MEV/pending-tx concerns on networks with baseline expiration semantics). Exploitation requires the attacker/holder of the signed transaction to strategically time (re)broadcast within the existing expiration window while the exchange pool price has drifted favorably for them and unfavorably for the signer — feasible but bounded by however tight the configured expiration window is, which I could not confirm precisely in this pass.

### Recommendation
Add an explicit, user-specified deadline/expiration field to `ExchangeTransactionContract` (and equivalently to `MarketSellAssetContract`/market order contracts) that is validated in `ExchangeTransactionActuator.doValidate()`/`execute()` against the block timestamp, in addition to the existing `expected` minimum-output check, so that a stale but not-yet-network-expired signed transaction cannot be executed once its issuer-intended validity window has passed.

### Proof of Concept
Not independently reproduced; based on static analysis of `ExchangeTransactionContract`'s fields [2](#0-1) , `ExchangeTransactionActuator.execute`/`doValidate` logic [6](#0-5) , and `ExchangeCapsule.transaction`'s pool-state-dependent pricing [5](#0-4) , none of which reference or check any deadline/expiration value tied to the trade intent.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
