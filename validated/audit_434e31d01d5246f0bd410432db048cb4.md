### Title
Shared `last-update` timestamp resets on debt-index tick even when liquidity-index is unchanged, permanently discarding rounded-down supplier interest - ([File: mainnet/contracts/vault/v0-vault-stx.clar], and identical logic in v0-vault-sbtc.clar, v0-vault-ststx.clar, v0-vault-ststxbtc.clar, v0-vault-usdc.clar, v0-vault-usdh.clar)

### Summary
Each vault tracks two indices off a single shared clock, `last-update`: `index` (debt index, rounded **up** via `mul-div-up`) and `lindex` (liquidity/supplier index, rounded **down** via `mul-div-down`). In `accrue`, the clock is only rewritten to `stacks-block-time` if *either* index changed, and both `next-index`/`next-liquidity-index` recompute the elapsed interest strictly from `(- stacks-block-time (var-get last-update))`. Because debt index rounds up and liquidity index rounds down, at short time deltas the debt index frequently ticks (by the rounding-up minimum unit) while the liquidity index's true fractional accrual is truncated to zero. Since the shared clock advances whenever *any* index changed, the liquidity index's un-materialized fractional interest for that window is discarded rather than carried forward, because the next call starts `time-delta` from zero again.

### Finding Description
The relevant logic: [1](#0-0) 
computes `next-index` using `calc-multiplier-delta rate time-delta true` (round-up) and `next-liquidity-index` using `calc-multiplier-delta liquidity-rate time-delta false` (round-down): [2](#0-1) 

`accrue` then does: [3](#0-2) 

The clock update is gated on `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))` — i.e. it fires whenever *either* index moved. Since `next-index` rounds `mul-div-up`, even a tiny `time-delta` with nonzero `rate` produces a nonzero remainder that rounds the multiplier up by 1 unit of `INDEX-PRECISION`, causing `idx` to tick almost every call. `next-liquidity-index` rounds `mul-div-down`, so the same tiny `time-delta` frequently yields multiplier == `INDEX-PRECISION` unchanged (fraction truncated to zero), so `lindex` stays put. Because `idx` ticked, the `or` condition is true, and `last-update` is reset to the current block time — even though `lindex`'s fractional progress toward its own rounding threshold was never captured. The next call restarts `time-delta` for the liquidity index from zero, so the truncated remainder from the prior window is never retried and is permanently lost. Given `accrue` is invoked on essentially every state-changing entry point (`system-borrow`, `system-repay`, deposits/withdrawals via the tokenized-vault trait), high call frequency causes this clock-reset-on-any-change condition to fire continuously, systematically starving the liquidity/supplier index of the sub-unit interest it should have accumulated, while the debt/borrower side keeps accruing correctly (rounded up in the protocol's favor).

This matches the "clock advanced only on change" analog class: a single shared clock variable is advanced based on the state of one tracked quantity (debt index) while being relied upon by a second, independently-rounded quantity (liquidity index) whose own invalidation condition is different. The interleaving requires no adversarial input — it happens naturally from normal usage frequency and is fully reachable under Clarity's single-transaction, single-block evaluation (each `accrue` call is one atomic execution reading `stacks-block-time` and `var-get last-update` once).

### Impact Explanation
This results in permanent freezing/loss of unclaimed yield owed to liquidity suppliers (depositors) of the vault: the accrued-but-rounded-down fractional liquidity interest for each short window is discarded rather than retained for a future window, so suppliers systematically under-accrue relative to the true economic yield generated by borrowers' interest payments. This falls under the in-scope High impact category: "theft of unclaimed yield or royalties, permanent freezing of unclaimed yield or royalties."

### Likelihood Explanation
High. `accrue()` is called on nearly every borrowing, repayment, deposit, and redemption operation in all six vaults (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-ststxbtc`, `v0-vault-usdc`, `v0-vault-usdh`), which occur frequently and at irregular, often short, intervals under normal protocol usage — no attacker action is required, just ordinary transaction cadence, making the rounding-truncation-then-clock-reset pattern occur continuously.

### Recommendation
Decouple the invalidation of `last-update` from a single shared "any index changed" condition, or track per-index last-update timestamps (`last-update-debt`, `last-update-liquidity`) so that when only the debt index changes, the liquidity index's `time-delta` continues to accumulate from its own true last-materialized point rather than being reset. Alternatively, always round the liquidity index computation up (or track a running remainder) so fractional interest is never silently discarded across accrue calls.

### Proof of Concept
1. Vault has nonzero utilization/rate such that a short `time-delta` (a few seconds, from normal transaction spacing) yields: `mul-div-up(rate * time-delta * INDEX-PRECISION, SECONDS-PER-YEAR-BPS)` → nonzero (rounds up any remainder), while `mul-div-down` of the liquidity-rate variant for the same window → zero (remainder truncated).
2. A user calls any state-changing vault entry point (e.g. `system-borrow`), which internally calls `accrue`, per [4](#0-3) .
3. Inside `accrue`: `next` (debt index) ≠ `idx` (ticks up by 1 unit), but `nliq` (liquidity index) == `lidx` (unchanged, remainder truncated to 0).
4. The condition `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))` evaluates true because of the debt index change alone, so `last-update` is reset to `stacks-block-time` — [5](#0-4) .
5. Repeat step 2-4 on the next short-interval transaction: `time-delta` for the liquidity index restarts from zero rather than continuing to accumulate the previously-truncated remainder, so the fractional interest owed to suppliers for that elapsed window never gets captured — it is permanently lost, while the debt index (and thus borrower obligations, and protocol reserve share via `debt-delta`) continues to accrue correctly every call.
6. Over many high-frequency calls, the liquidity index (and thus the yield paid to zft/vault-share holders) permanently lags behind the true economic interest generated by borrowers, without the reserve/treasury mechanism capturing the difference either (since treasury share minting is also computed strictly from the same fresh `next`/`idx` debt-delta each call).
