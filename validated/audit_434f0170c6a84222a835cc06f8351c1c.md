### Title
Divide-before-multiply page/cell alignment math in `BucketStorage::allocate_to_fill_page` can violate its own invariant and trip an `assert!`, panicking the node - (File: bucket_map/src/bucket_storage.rs)

### Summary
`BucketStorage::allocate_to_fill_page` (used when creating and growing the on-disk accounts-index bucket-map files) computes an aligned byte allocation size by chaining `div` then `mul` operations twice in a row, mirroring the exact bug-class from the Sherlock report (divide-before-multiply causing truncation). Unlike the FluidLocker case, the truncation here is not silently accepted — it is checked by an `assert!`, so instead of silent fund loss the analogous failure mode is a validator panic.

### Finding Description
`allocate_to_fill_page` is used whenever a new `BucketStorage` (index or data bucket for the disk-backed `AccountsIndex`/`bucket_map`) needs to be sized to fill a full OS page: [1](#0-0) 

```rust
fn allocate_to_fill_page(capacity: &mut Capacity, cell_size: u64) -> u64 {
    let mut bytes = capacity.capacity() * cell_size;
    if let Capacity::Actual(_) = capacity {
        const PAGE_SIZE: u64 = 4 * 1024;
        let full_page_bytes = bytes / PAGE_SIZE * PAGE_SIZE / cell_size * cell_size;
        if full_page_bytes < bytes {
            let bytes_new = ((bytes / PAGE_SIZE) + 1) * PAGE_SIZE / cell_size * cell_size;
            assert!(bytes_new >= bytes, ...);
            assert_eq!(bytes_new % cell_size, 0);
            bytes = bytes_new;
            *capacity = Capacity::Actual(bytes / cell_size);
        }
    }
    bytes
}
```

The exact same anti-pattern flagged in the FluidLocker report is present here: the expression divides by `PAGE_SIZE`, multiplies back by `PAGE_SIZE`, then divides by `cell_size`, then multiplies back by `cell_size` — two consecutive floor-divisions compounding truncation error rather than computing the aligned quantity with a single, order-safe operation (e.g., `ceil_div` performed once). The intent is to round `bytes` up to the next page boundary and then floor to a multiple of `cell_size` so the allocation is `cell_size`-aligned, but the chained div/mul sequence means the final `bytes_new` can, for certain `cell_size`/`PAGE_SIZE` combinations, floor-round *below* `bytes`, which is caught only defensively by `assert!(bytes_new >= bytes, ...)`.

This function is called from `new_with_capacity`, which is the constructor path used for both index and data buckets in the on-disk `bucket_map` backing the `AccountsIndex`: [2](#0-1) 
and is invoked repeatedly during index growth (`grow_index`) and data-bucket growth in `bucket.rs`, which is exercised continuously by the accounts-index background flush/threshold logic in `bucket_map_holder.rs`.

### Impact Explanation
If the `assert!(bytes_new >= bytes, ...)` is ever violated for some combination of `cell_size` and requested `capacity` (e.g., non-power-of-two `Capacity::Actual` sizes derived from `threshold_entries_per_bin` / restart-time reload paths), the validator process panics inside accounts-index bucket allocation — this is a node-panic outcome, which is one of the accepted impact categories for this scan (concrete node panic). Because this code runs on the disk-index growth/restart path used whenever `IndexLimit::Threshold`/`Minimal` disk index is enabled, a panic here would take down validator startup or background index-flush threads.

### Likelihood Explanation
The `assert` currently guards against the mis-derived math and no failing case has been demonstrated to trigger in the samples checked (small/common `cell_size` values like `IndexEntry`/`DataBucket` header sizes divide `PAGE_SIZE` cleanly in the examples worked through). However, the search coverage was incomplete: I was not able to fully confirm the range of `cell_size` values `data` buckets can take when scaled for large slot-list `MultipleSlots` growth (`data_bucket_from_num_slots`, `bucket.rs`), nor verify all `Capacity::Actual` call sites (e.g., threshold-derived `entries_per_bin` computed in `bucket_map_holder.rs`) are always constructed such that `bytes_new >= bytes` holds for every possible `cell_size`. This is a real but not fully proven reachable panic — it depends on finding a concrete `(cell_size, capacity)` pair where the chained floor-divisions round down past `bytes`.

### Recommendation
Replace the chained divide-then-multiply rounding with a single ceiling-division performed in the correct order, e.g.:
```rust
let full_page_bytes = bytes.div_ceil(PAGE_SIZE) * PAGE_SIZE; // round up to full pages first
let bytes_new = full_page_bytes.div_ceil(cell_size) * cell_size; // then round up (not down) to a whole number of cells
```
using `div_ceil` (ceiling division) instead of floor division followed by re-multiplication, so the two roundings compose correctly and the `bytes_new >= bytes` invariant is guaranteed by construction rather than merely checked defensively.

### Proof of Concept
Not exercised against a live build (index-only, static-analysis of `bucket_map/src/bucket_storage.rs:165-185`); a concrete failing `(cell_size, capacity)` input satisfying `full_page_bytes < bytes` yet also making the corrective `bytes_new` computation land below `bytes` was not constructed within the available search budget. The worked examples (`cell_size=24`, `cell_size=200` against `PAGE_SIZE=4096`) did not trigger the assertion, so this should be treated as a code-quality/robustness finding matching the reported bug class rather than a confirmed exploitable panic.
