Confirmed: `ExchangeInjectContract` and `ExchangeWithdrawContract` lack the `expected`/minimum-amount field that `ExchangeTransactionContract` has for slippage protection. [1](#0-0) 

### Title
Unbounded slippage in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` allows sandwich extraction of LP value - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's on-chain bancor-style `Exchange`/`ExchangeV2` AMM pools support injecting (`ExchangeInjectContract`) and withdrawing (`ExchangeWithdrawContract`) proportional liquidity. Unlike `ExchangeTransactionContract`, which carries an `expected` field used to bound slippage for swaps, neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` carry any user-specified minimum/maximum bound on the paired token amount computed from the current pool ratio. This is the direct analog of the reported `VaderPoolV2.mintFungible` issue: liquidity providers cannot protect themselves against pool-ratio manipulation that happens between transaction broadcast and inclusion.

### Finding Description
`ExchangeInjectActuator.execute`/`doValidate` computes the paired token amount purely from the current on-chain `firstTokenBalance`/`secondTokenBalance` ratio at execution time: [2](#0-1) 
The `ExchangeInjectContract` protobuf message only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no field allowing the sender to bound the resulting `anotherTokenQuant` (unlike swaps, which have `expected`): [3](#0-2) 
The same absence of a bound applies to `ExchangeWithdrawActuator`, whose paired amount is likewise derived from the live ratio with no floor set by the withdrawer: [4](#0-3) 
By contrast, `ExchangeTransactionActuator` (swap) explicitly validates a caller-supplied minimum via `tokenExpected`: [5](#0-4) 
Because any account can broadcast `ExchangeTransactionContract` swaps against the same exchange, an attacker who observes a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` (via the p2p mempool broadcast, which is visible to any node) can order two large swaps around the victim's transaction — one to skew the `firstTokenBalance`/`secondTokenBalance` ratio before the victim's inject/withdraw executes, and a reverse swap afterward to restore it — capturing the difference between the fair-value paired amount and the manipulated one.

### Impact Explanation
This enables value extraction from any unprivileged user who injects or withdraws liquidity on a `Exchange`/`ExchangeV2` pool, analogous to the "up to 100% of LP value" impact described in the original report, constituting asset/accounting corruption for the victim account reachable purely through normal broadcast transactions (`ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) with no privileged access required.

### Likelihood Explanation
Likelihood is bounded by TRON's block-production model: transaction ordering within a block is controlled by the witness producing that block, not by arbitrary mempool reordering by any peer, so a fully generic "frontrunner observes mempool and reorders" attack is harder here than on an Ethereum-style public mempool with MEV searchers. However, a witness itself (or an attacker colluding with block production, or simply issuing same-block sandwich transactions accepted in submission order within a block) can still exploit this deterministically, and even without perfect ordering control, statistical/opportunistic sandwiching across adjacent blocks remains possible since anyone can submit `ExchangeTransactionContract` swaps against the same `exchange_id` before and after a known pending inject/withdraw.

### Recommendation
Add an explicit user-specified bound to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., a `min_another_token_quant` field, mirroring the `expected` field already used in `ExchangeTransactionContract`), and enforce it in `ExchangeInjectActuator.doValidate`/`execute` and `ExchangeWithdrawActuator.doValidate`/`execute` so the actuator fails validation if the pool-ratio-derived `anotherTokenQuant` falls outside the caller's tolerance at execution time.

### Proof of Concept
1. Victim broadcasts `ExchangeInjectContract` injecting `tokenQuant` of `firstTokenID`, expecting `anotherTokenQuant` of `secondTokenID` computed from the current ratio (as in `ExchangeInjectActuator.execute`, lines 71-83).
2. Before the victim's transaction is packed into a block, an attacker submits an `ExchangeTransactionContract` swap that heavily skews `firstTokenBalance`/`secondTokenBalance` for the same `exchange_id`.
3. The victim's `ExchangeInjectContract` executes against the skewed reserves, receiving fewer LP-equivalent value (the exchange's proportional balances) than intended, since `exchangeCapsule.setBalance(...)` is set using the manipulated ratio.
4. The attacker submits a second `ExchangeTransactionContract` swap to restore the original ratio, pocketing the difference, all using only unprivileged broadcast transactions against the public `ExchangeInjectActuator`/`ExchangeTransactionActuator` contract types.
