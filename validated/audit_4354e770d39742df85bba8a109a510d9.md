Based on my research, this is a legitimate and serious finding.

### Title
Speculative `SyncScriptCache` never re-validates a verified script's linked module dependencies after a same-block module republish, letting BlockSTM commit output derived from stale module bytecode - (File: `third_party/move/move-vm/types/src/code/cache/script_cache.rs`)

### Summary
`SyncScriptCache` is a single, block-scoped cache shared by every transaction incarnation in `MVHashMap` [1](#0-0) . Once a script hash is inserted as `Code::Verified`, all later lookups for that hash short-circuit and return the cached `Arc<Script>` without ever re-resolving or re-validating its linked module dependencies [2](#0-1) . The eager loader's verification path confirms this: on a cache hit it returns immediately (`Some(Verified(script)) => return Ok(script)`) and skips the code path that would call `unmetered_get_existing_eagerly_verified_module` for each immediate dependency [3](#0-2) .

### Finding Description
Module reads are versioned and validated via `SyncModuleCache`/`captured_reads` so that a stale module read normally triggers re-execution [4](#0-3) . But that protection only applies when the loader actually queries `get_module_or_build_with` for a dependency. On a script-cache hit (`Some(Verified(script))`), the loader never touches module storage at all for that script's dependencies, so no module read is captured and no invalidation can occur for that dependency chain going forward [5](#0-4) .

Concretely:
1. Under speculative (out-of-order) BlockSTM execution, a later-indexed script transaction B can execute before an earlier-indexed module-publish transaction A. B builds and verifies its script against the pre-upgrade module (v1), and `insert_verified_script` permanently caches it as `Code::Verified` for the block [2](#0-1) .
2. A commits its module republish (v2).
3. B is invalidated/re-run due to whatever *other* read caused revalidation (or is re-run speculatively again). On re-verification, `get_script` finds the entry already `Code::Verified` and returns it directly - the immediate dependency handles baked into the `Arc<Script>` still point to the stale v1 `Module`, and this path records no module read to ever be invalidated by B's validation logic.
4. B's execution therefore runs against the old module logic even though the committed ledger state (after A) reflects v2, producing outputs (write set, events) that diverge from what strict sequential re-execution (A then B, with B correctly seeing v2) would produce.

### Impact Explanation
This breaks the core BlockSTM correctness invariant that parallel execution must always be equivalent to some sequential execution of the same block. A validator's committed write set for the script transaction can silently reflect obsolete module logic, causing state divergence between implementations or configurations of BlockSTM (e.g., differing degrees of speculation/incarnation ordering), which is a hard-fork/consensus-safety-class defect: the same block could be validated differently depending on scheduling nondeterminism.

### Likelihood Explanation
Exploitation requires only unprivileged inputs: any account can publish a module upgrade and any account can submit a script transaction whose script bytes hash to a hash already resolved earlier in block execution. Triggering the specific interleaving (speculative early execution of the script transaction before the module publish, followed by a re-execution that hits the cache) depends on BlockSTM's internal scheduling, which is influenced by transaction ordering within the block and is not fully attacker-controlled, but is realistic to construct (e.g., by placing the script transaction shortly after the publish, or replaying with dependency-only reads on module functions rather than resources, which minimizes captured module reads elsewhere).

### Recommendation
The verified-script cache-hit path must still traverse and validate (i.e., record as captured reads and re-check) all immediate module dependencies of a cached verified script on every use, rather than returning the cached `Arc<Script>` unconditionally, or the script cache entry should be keyed/invalidated with the same per-block module version tracking used by `SyncModuleCache` so a same-block module republish forces script re-verification.

### Proof of Concept
Not independently confirmed by running the actual BlockSTM scheduler in this review; based on static code trace only. A concrete proof would build an integration test using `SyncScriptCache`/`SyncModuleCache` in a simulated multi-incarnation run (similar to `aptos-move/block-executor/src/combinatorial_tests`) where:
1. Transaction B (higher index, calls a function in module M via a script) is scheduled to execute speculatively before Transaction A (lower index, republishes M).
2. B's script gets cached as `Code::Verified` referencing the pre-upgrade `Module` for M.
3. A commits, republishing M.
4. B is invalidated on some other read and re-executed; assert its `get_script` call returns the pre-upgrade-linked `Arc<Script>` and that no new module read for M is captured, so B's write set differs from what sequential (A-then-B) execution would produce.

I was not able to find, within the reviewed files, any global invalidation of `script_cache` triggered by module publishes in the block executor; this should be verified further in `aptos-move/block-executor/src/executor.rs` and `captured_reads.rs` (not fully reviewed) before treating this as fully confirmed, since it is possible an out-of-band invalidation exists elsewhere that was not surfaced in this review's search results.

    fn insert_verified_script(
        &self,
        key: Self::Key,
        verified_script: Self::Verified,
    ) -> Arc<Self::Verified> {
        use dashmap::mapref::entry::Entry::*;

        match self.script_cache.entry(key) {
            Occupied(mut entry) => {
                if !entry.get().is_verified() {
                    let new_script = Code::from_verified(verified_script);
                    let verified_script = new_script.verified().clone();
                    entry.insert(CachePadded::new(new_script));
                    verified_script
                } else {
                    entry.get().verified().clone()
                }
            },
            Vacant(entry) => entry
                .insert(CachePadded::new(Code::from_verified(verified_script)))
                .verified()
                .clone(),
        }
    }

    fn unmetered_verify_and_cache_script(&self, serialized_script: &[u8]) -> VMResult<Arc<Script>> {
        use Code::*;

        let hash = sha3_256(serialized_script);
        let deserialized_script = match self.module_storage.get_script(&hash) {
            Some(Verified(script)) => return Ok(script),
            Some(Deserialized(deserialized_script)) => deserialized_script,
            None => self
                .runtime_environment()
                .deserialize_into_script(serialized_script)
                .map(Arc::new)?,
        };

        let locally_verified_script = self
            .runtime_environment()
            .build_locally_verified_script(deserialized_script)?;

        let immediate_dependencies = locally_verified_script
            .immediate_dependencies_iter()
            .map(|(addr, name)| {
                self.module_storage
                    .unmetered_get_existing_eagerly_verified_module(addr, name)
            })
            .collect::<VMResult<Vec<_>>>()?;

        let verified_script = self
            .runtime_environment()
            .build_verified_script(locally_verified_script, &immediate_dependencies)?;

        Ok(self
            .module_storage
            .insert_verified_script(hash, verified_script))
    }
