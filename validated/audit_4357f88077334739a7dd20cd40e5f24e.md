### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, allowing replay-verify to accept a corrupted state/hot-state/position-state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity gate used by replay/debug tooling to confirm that a locally-recomputed `TransactionOutput` matches the on-chain-committed `TransactionInfo` for a given version. It checks status, gas, write-set hash and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that authenticate the Merkle root of the world state / hot-state / native-position state at checkpoint boundaries. [1](#0-0) 

### Finding Description
The comparator explicitly documents the gap in its own source:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
``` [2](#0-1) 

This mirrors the structural pattern in the seed report: a validation function is supposed to compare a locally computed value against an authenticated/expected value, but a coding gap means the comparison never actually happens for a subset of the checked fields — so any divergence in those fields is silently accepted rather than rejected. In the Stakehouse case the comparison compared a value to itself (`x != x`), always failing; here the comparison is simply omitted for the checkpoint-hash fields, always "passing" regardless of the actual values.

The state/hot-state/position-state checkpoint hashes are computed independently in `DoStateCheckpoint::run` / `get_state_checkpoint_hashes` / `compute_position_checkpoint`, and are baked into `TransactionInfo` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash` on `TransactionInfoV1`). [3](#0-2) [4](#0-3) 

`ensure_match_transaction_info` is invoked by replay/debug consumers (`aptos-move/aptos-debugger`, `aptos-move/cli`, and `execution/executor/src/chunk_executor/mod.rs`) as the sole cross-check that a locally re-executed transaction's output reproduces the committed ledger state. [5](#0-4) 

Because the function returns `Ok(())` without comparing these three hash fields, any of the following would go undetected by this check:
- The locally executed state root (regular Sparse Merkle Tree checkpoint) differs from the committed `state_checkpoint_hash`.
- The hot-state root differs from the committed `hot_state_checkpoint_hash` (gated by feature `HOT_STATE_ROOT_IN_TXN_INFO`).
- The native-position state root differs from the committed `position_state_checkpoint_hash` (gated by feature `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `types/src/on_chain_config/aptos_features.rs:203-209`).

### Impact Explanation
This breaks the "committed state must match the correct VM/executor result" and "authenticated proof/root context must stay bound to the right ledger state" invariants required by the State-Integrity Gate. `ensure_match_transaction_info` is the mechanism replay/debug/verification tooling (`replay_on_archive`, chunk executor replay path, `aptos-debugger`) relies on to detect a divergence between locally recomputed state and the authenticated on-chain root. With checkpoint-hash comparison silently skipped, a state-root divergence (e.g., due to a storage/restore bug, a non-deterministic execution bug, or corrupted persisted state) in the regular state root, hot-state root, or position-state root would not be flagged as a mismatch by this gate — tooling could report a "successful" replay/verification while the underlying committed state root is actually wrong. This directly matches the in-scope impact "Committed state that differs from the correct VM result or corrupts durable ledger data" and "wrong ... state proof accepted as valid," since checkpoint hashes are the values bound into the transaction-accumulator-committed `TransactionInfo`.

### Likelihood Explanation
The code path is exercised on every call to `ensure_match_transaction_info`, which is used unconditionally by chunk-executor replay and CLI/debugger replay-verify flows — no attacker action or privilege is needed to trigger the omission; it's a standing gap in the validation logic. The severity is currently bounded by the fact that `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` may not yet be enabled on mainnet, and the comment states the gap should be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`." However, the regular `state_checkpoint_hash` field is unconditionally present and used, so the omission already weakens the classic state-checkpoint verification for archive replay in the general case, independent of the new trading-native feature.

### Recommendation
In `ensure_match_transaction_info`, add explicit `ensure!` checks comparing the locally computed checkpoint hash(es) (state, hot-state when enabled, position-state when enabled) against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()` (if such an accessor exists on `TransactionInfoV1`), and `txn_info.position_state_checkpoint_hash()`, mirroring the pattern already used for `write_set_hash` and `event_root_hash`, before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or `HOT_STATE_ROOT_IN_TXN_INFO` in production.

### Proof of Concept
Not independently exploitable as a runtime state-corruption bug by itself — it is a missing-assertion gap. The concrete demonstration is the source comment co-located with the function itself, acknowledging that `replay_on_archive`-style tooling can report success even when the "authenticated position state root diverges from local execution": [1](#0-0) 
A full PoC would require constructing a `TransactionOutput`/`TransactionInfo` pair with mismatched `state_checkpoint_hash` and running it through `ensure_match_transaction_info`, showing `Ok(())` is returned despite the hash mismatch — this exercise was not run in this read-only analysis but is directly supported by the code shown.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
