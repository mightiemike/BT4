### Title
Sequencer crash via `Bouncer::try_update` non-`BlockFull` error path panicking in concurrent commit - ([File: crates/blockifier/src/concurrency/worker_logic.rs])

### Summary
In concurrent (multi-worker) block execution, `WorkerExecutor::commit_tx` calls `Bouncer::try_update` to check whether a just-executed transaction's resource weights fit in the remaining block capacity. The result is only explicitly handled for the `TransactionExecutorError::BlockFull` variant; any other error variant returned from `try_update` (e.g. `TransactionExecutorError::StateError`, propagated via the `?` inside `get_tx_weights`/`try_update`) causes the worker thread to `panic!`, rather than gracefully rejecting or reverting the offending transaction.

### Finding Description
`Bouncer::try_update` computes marginal resource weights for a transaction via `get_tx_weights(...)?` and returns `TransactionExecutorResult<()>`, which can surface `TransactionExecutorError::StateError` (or other propagated errors) in addition to the expected `BlockFull` condition. [1](#0-0) 

In the concurrent execution path, `commit_tx` matches on the error from `try_update` and only special-cases `BlockFull`; every other variant falls into a `panic!("Bouncer update failed. {error:?}: {error}")`, which is explicitly marked with a `TODO` acknowledging that the error should probably be propagated instead of panicking: [2](#0-1) 

This is structurally analogous to the reported SafEth bug class: a downstream operation invoked as part of normal per-transaction processing (here, a state read performed while accounting for bouncer weights) is expected to almost always succeed, but any non-`BlockFull` failure is not handled gracefully — instead of skipping/rejecting only the offending transaction, the entire worker thread (and by extension, block-building/validation for the whole block) is torn down via `panic!`. Because `commit_tx` is invoked from `commit_while_possible`, which unwraps `commit_tx`'s outer `Result` with `unwrap_or_else(|_| panic!(...))` already, a state error at this layer is not distinguished from unrecoverable committer/API misuse - both terminate execution abruptly: [3](#0-2) 

### Impact Explanation
A panic inside a worker thread used for concurrent transaction execution aborts the in-progress block-building or block-validation task for the entire block, not just the offending transaction. If reachable by an unprivileged transaction (e.g., one whose state footprint or execution artifacts induce a `StateError` when the bouncer computes `get_tx_weights` for it, rather than a benign `BlockFull`), a single malicious/crafted transaction submitted to the sequencer could repeatedly disrupt block production, an impact category explicitly in scope ("a network unable to confirm new transactions"). This differs from the ordinary, well-handled failure modes (transaction revert, `BlockFull`) that the bouncer/executor otherwise handle without aborting the whole block.

### Likelihood Explanation
I was not able to conclusively identify, within the available tool budget, a concrete state-reader condition reachable purely from an untrusted transaction's calldata/class declaration that would deterministically cause `get_tx_weights` to return a `StateError` (as opposed to `BlockFull`) during normal committer execution. The panic path exists and is explicitly flagged by the developers as needing better error propagation (`// TODO(Avi, 01/07/2024): Consider propagating the error.`), which indicates the authors are aware this is not a fully "impossible" path, but I could not fully trace `get_tx_weights`'s internal state accesses (e.g., compiled-class-hash/class-info lookups) to confirm a concrete unprivileged trigger before running out of investigation budget.

### Recommendation
Propagate non-`BlockFull` errors from `Bouncer::try_update` in `commit_tx` as a proper `Result` (e.g., treat as `CommitResult::ValidationFailed`/tx-rejection or surface as a recoverable block-builder error) instead of `panic!`, consistent with how `BlockFull` is already handled without crashing the worker.

### Proof of Concept
Not established with certainty — a concrete unprivileged-transaction trigger for the `StateError` (or other non-`BlockFull`) branch of `try_update` inside `get_tx_weights` was not confirmed within the investigation scope; further tracing of `get_tx_weights`'s internal state-reader calls (class hash / compiled-class-hash lookups, Patricia update resource computation) would be required to build a full end-to-end PoC.

    fn commit_while_possible(&self) {
        if let Some(mut tx_committer) = self.scheduler.try_enter_commit_phase() {
            while let Some(tx_index) = tx_committer.try_commit() {
                let commit_result = self.commit_tx(tx_index).unwrap_or_else(|_| {
                    panic!("Commit transaction should not be called after clearing the state.");
                });
                match commit_result {
                    CommitResult::Success => {}
                    CommitResult::NoRoomInBlock => {
                        tx_committer.uncommit();
                        self.scheduler.halt();
                    }
                    CommitResult::ValidationFailed => {
                        tx_committer.uncommit();
                        return;
                    }
                }
            }
        }
