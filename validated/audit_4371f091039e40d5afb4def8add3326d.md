### Title
Unbounded per-vote scan of `ActiveBallotIDs` in `CreateBallot`/`ExpireBallotsBeforeHeight` enables gas-exhaustion DoS of the ballot voting pipeline - (File: `x/uvalidator/keeper/ballot.go`)

### Summary
Every time a Universal Validator casts the first vote on a new, distinct crosschain observation (inbound, outbound, chain-meta, TSS event, or fund migration), `CreateBallot` unconditionally calls `ExpireBallotsBeforeHeight`, which iterates **the entire `ActiveBallotIDs` set** and performs a `Ballots.Get` for every entry. [1](#0-0) [2](#0-1)  Because `ActiveBallotIDs` size is driven by the volume of distinct, honestly-observed crosschain events (each hashed to a unique ballot ID), an unprivileged attacker can inflate this collection simply by generating many genuine but distinct external-chain interactions (e.g., many small deposits with unique tx hashes/log indices) faster than the 2/3-quorum voting can finalize/retire them. [3](#0-2)  This is the same bug class as the reported `clearLoop()`/`PointsMap.clear()` issue: an unbounded loop over an attacker-influenced, ever-growing collection executed inside normal transaction processing.

### Finding Description
`GetOrCreateBallot` is the entry point every voting flow in `x/uexecutor` and `x/utss` funnels through via `VoteOnBallot`. [4](#0-3) [3](#0-2)  When a ballot does not yet exist (i.e., the first vote on a new observation), it calls `CreateBallot`, which — before storing the new ballot — always calls `ExpireBallotsBeforeHeight(ctx, blockHeight)`: [5](#0-4) 

`ExpireBallotsBeforeHeight` iterates every key in `ActiveBallotIDs` and does a full `Ballots.Get` lookup for each to check its expiry height: [6](#0-5) 

This means the cost of creating *any* new ballot is `O(N)` where `N` is the number of currently active (unresolved) ballots across **all** four voting subsystems (`INBOUND_TX`, `OUTBOUND_TX`, `CHAIN_META`, `TSS_EVENT`, `FUND_MIGRATION`). Since ballot IDs are derived from a hash of the observation itself, an attacker who triggers many distinct genuine crosschain events (unique source-chain tx hashes, log indices, amounts, etc.) causes honest Universal Validators to create a correspondingly large number of distinct new ballots. As long as event-creation throughput outpaces quorum-finalization throughput (which requires waiting for 2/3+ of UVs to independently observe and vote across multiple blocks), `ActiveBallotIDs` grows. Every subsequent new-ballot creation must pay the full `O(N)` expiry-scan cost, so the aggregate cost across `N` ballot creations is `O(N^2)`.

Once `N` grows large enough that a single `ExpireBallotsBeforeHeight` scan approaches the block gas limit, any transaction attempting to vote on a brand-new observation (`MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, `MsgVoteTssKeyProcess`, `MsgVoteFundMigration`) will run out of gas and fail. Because this check is unconditional and sits on the critical path for creating *any* new ballot, this can escalate from "slow" to "impossible" — permanently blocking new observations (including outbound signing, TSS key events, and fund migrations) from ever reaching consensus, since they can never even be created once the active set is large enough.

### Impact Explanation
This breaks the "Honest-validator finalization path" invariant: ordinary, honestly-observed user-created source events must not prevent honest UVs from converging (finalizing) new ballots. A sufficiently large `ActiveBallotIDs` backlog — inflatable by an unprivileged attacker generating many cheap, distinct crosschain events — makes the ballot-creation step itself unbounded in gas cost, eventually causing OOG failures for legitimate votes across inbound, outbound, chain-meta, and TSS/fund-migration flows. This is a protocol-wide liveness/DoS impact on the universal execution and TSS coordination pipeline, not merely a single-message failure, since ballot creation is the single choke point shared by every crosschain observation type.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires sustained attacker effort to generate a large volume of distinct crosschain events faster than the network can finalize them, and the exact threshold depends on chain gas limits and how quickly 2/3-quorum voting resolves ballots in practice. However, no privileged access, validator collusion, or protocol bug beyond this unbounded-loop pattern is required — an attacker only needs ordinary access to source chains to submit many distinct low-value transactions.

### Recommendation
Avoid the unconditional full-collection scan on every new-ballot creation. Options:
- Only run `ExpireBallotsBeforeHeight` periodically (e.g., once per `BeginBlocker`/`EndBlocker`) rather than on every `CreateBallot` call.
- Maintain expiry-ordered secondary indexing (e.g., a height-bucketed index) so expired ballots can be found and removed in `O(1)`/`O(log N)` instead of scanning the full active set.
- Cap the number of concurrently active ballots per observation type, or rate-limit new-ballot creation, to bound worst-case gas cost.

### Proof of Concept
1. An attacker repeatedly performs small, cheap deposits (or other observable actions) on a connected external chain, each with a unique tx hash/log index, faster than the 2/3 UV quorum can finalize prior ballots.
2. Honest UVs observe each event and submit `MsgVoteInbound` for each distinct observation; each first vote invokes `GetOrCreateBallot` → `CreateBallot` → `ExpireBallotsBeforeHeight`, which scans the full `ActiveBallotIDs` set. [1](#0-0) 
3. As `ActiveBallotIDs` grows (backlog builds because finalization requires multiple blocks/votes while new distinct events keep arriving), each subsequent `CreateBallot` call becomes progressively more expensive.
4. Once the scan cost for the current active-set size approaches the block gas limit, any `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta`/`MsgVoteTssKeyProcess`/`MsgVoteFundMigration` that would create a *new* ballot fails with out-of-gas, halting further consensus progress on crosschain observations network-wide until the backlog is somehow cleared.

// GetOrCreateBallot returns the ballot if it exists, otherwise creates it.
func (k Keeper) GetOrCreateBallot(
	ctx context.Context,
	id string,
	ballotType types.BallotObservationType,
	voters []string,
	votesNeeded int64,
	expiryAfterBlocks int64,
) (types.Ballot, bool, error) {

	if ballot, err := k.Ballots.Get(ctx, id); err == nil {
		k.Logger().Debug("ballot found (existing)", "ballot_id", id)
		return ballot, false, nil
	}

	k.Logger().Debug("ballot not found, creating new", "ballot_id", id, "ballot_type", ballotType.String())
	newBallot, err := k.CreateBallot(ctx, id, ballotType, voters, votesNeeded, expiryAfterBlocks)

	return newBallot, true, err
}

// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
