### Title
Unbounded growth of per-shop session-ID list in `KVSessionStorage` causes DoS of session lookup/deletion on the app-uninstall webhook path - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
`KVSessionStorage.addShopIds` appends session IDs to a per-shop list on every `storeSession` call without checking for duplicates or bounding the list size, mirroring the `TwapOracle.registerPair`/`update` bug class where an ever-growing, never-pruned collection is iterated in full by a critical code path (`findSessionsByShop`/`deleteSessions`), eventually causing that code path to fail or become prohibitively slow.

### Finding Description
`KVSessionStorage.storeSession` calls `addShopIds(session.shop, [session.id])` on every session write: [1](#0-0) 

`addShopIds` simply concatenates the new id(s) onto the existing array stored under the `shop:<shop>` key, with no deduplication and no upper bound: [2](#0-1) 

Because Shopify online-session IDs are deterministic per shop+user (e.g. re-derived on every login/token exchange), routine, unprivileged re-authentication by ordinary shop staff/customers can repeatedly call `storeSession` with the same `session.id`. Each call still appends a duplicate entry into the `shop:<shop>` array (there is no `includes` check before pushing), so the array grows without bound purely from normal, low-privilege usage over time — no compromised owner/admin action is required, unlike the original `TwapOracle` report where an owner had to add too many pairs.

This unbounded array is then fully iterated by `findSessionsByShop`, which loads *every* id in the array via `Promise.all`: [3](#0-2) 

`findSessionsByShop` and `deleteSessions` (which loops one id at a time, awaiting each delete sequentially) are the exact functions used by `AppInstallations.includes`/`AppInstallations.delete` in `shopify-app-express`, which are invoked from the `APP_UNINSTALLED` webhook handler (`deleteAppInstallationHandler`) and from OAuth-completion flows: [4](#0-3) [5](#0-4) 

As the shop-keyed id array grows (bounded only by how many times sessions are stored for that shop, which is attacker/user reachable without special privilege), `deleteSessions`'s sequential per-id loop and `findSessionsByShop`'s full-array load both grow linearly, degrading and eventually starving the webhook-authenticated uninstall-cleanup handler and OAuth session bookkeeping — directly analogous to `TwapOracle.update`'s unbounded loop that could lock the oracle.

### Impact Explanation
This is a DoS of a request-authentication/session-storage code path (`findSessionsByShop`/`deleteSessions`, reached from the `APP_UNINSTALLED` webhook handler and OAuth completion helpers). As the per-shop id list grows, KV reads/writes and the sequential delete loop become slower and can exceed request/webhook timeout budgets, causing session cleanup on uninstall to fail or apps to be unable to reliably determine/clear install state for a shop — potentially leaving stale or inconsistent session data. Unlike the original report (which required a compromised/careless owner), here the growth is driven by ordinary, unprivileged session creation (repeated logins/token exchanges), making it reachable without any privileged action.

### Likelihood Explanation
Likelihood is moderate: the growth requires many `storeSession` calls for the same shop over time (e.g., frequent online-token issuance/re-auth, which is normal in embedded/session-token apps), and the failure mode manifests as a gradual performance degradation rather than an instant crash. No attacker privilege or secret compromise is needed — just accumulation from routine unprivileged sessions — but exploiting it as a fast, deliberate DoS would require sustained high-frequency legitimate-looking session churn, which is plausible but not immediate.

### Recommendation
- In `addShopIds`, deduplicate before storing: `[...new Set([...shopIds, ...ids])]`.
- Cap or periodically prune the per-shop id list (e.g., remove ids whose underlying session no longer exists) instead of relying solely on `removeShopIds` at delete time.
- Consider paginating/batching `findSessionsByShop` and `deleteSessions` operations, or parallelizing `deleteSessions` deletes (`Promise.all`) instead of sequential awaiting, to bound worst-case latency.

### Proof of Concept
1. Repeatedly complete OAuth/token-exchange for the same shop+user in an app using `@shopify/shopify-app-session-storage-kv`, so `storeSession` is called many times with the same (or many distinct) session IDs for that shop.
2. Each call triggers `addShopIds`, which appends without checking for existing entries, growing the `shop:<shop>` KV value unboundedly.
3. Trigger the `APP_UNINSTALLED` webhook (or any code calling `AppInstallations.delete`/`includes`), which calls `findSessionsByShop` then `deleteSessions`.
4. Observe that `findSessionsByShop`'s `Promise.all` over the bloated id list and `deleteSessions`'s sequential per-id loop scale linearly with the accumulated (duplicate-laden) array, degrading/DoS-ing the uninstall cleanup and session-lookup path.

    const sessionIds = await this.namespace.get<string[]>(
      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );
  }

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  async includes(shopDomain: string): Promise<boolean> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      for (const session of shopSessions) {
        if (session.accessToken) return true;
      }
    }
    return false;
  }

  async delete(shopDomain: string): Promise<void> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      await this.sessionStorage.deleteSessions!(
        shopSessions.map((session: Session) => session.id),
      );
    }
  }
