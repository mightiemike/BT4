## Finding: Epoch-history verification silently skips validator-signature checks for out-of-range epochs during backup restore [1](#0-0) 

### Title
Restore-time `EpochHistory::verify_ledger_info` unconditionally accepts a `LedgerInfoWithSignatures` whose epoch exceeds the locally-known epoch history, bypassing validator-signature verification - (File: `storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs`)

### Summary
`EpochHistory::verify_ledger_info` is the function that is supposed to cryptographically bind an untrusted `LedgerInfoWithSignatures` (loaded from backup storage) to the validator set trusted by the restoring node. When the `epoch` field of the supplied ledger info is greater than the number of epoch-ending ledger infos already restored into `EpochHistory`, the function does not attempt any signature check — it just logs a warning and returns `Ok(())`: [2](#0-1) 

This function is called from both the state-snapshot restore path and the transaction restore path to authenticate `LedgerInfoWithSignatures` objects that are read directly from backup-storage-provided files, e.g. in `StateSnapshotRestoreController::run_impl`: [3](#0-2) 

### Finding Description
Backup restore establishes trust in three layers:
1. `EpochHistoryRestoreController` bootstraps a chain of validator-verified `LedgerInfo`s from epoch-ending backups, forming `EpochHistory.epoch_endings` (a `Vec<LedgerInfo>` indexed by epoch number) [4](#0-3) .
2. Later restore steps (state-snapshot restore, transaction restore) load a fresh `LedgerInfoWithSignatures` straight out of an untrusted backup file, and call `EpochHistory::verify_ledger_info` to check it is properly signed by the correct epoch's validator set before trusting it as the root of a state/transaction proof.
3. `verify_ledger_info` normally verifies the signature via `self.epoch_endings[epoch - 1].next_epoch_state().verify(li_with_sigs)` [5](#0-4) .

The bug is the special-case at the top of the function: if the untrusted `li_with_sigs.ledger_info().epoch()` is **larger** than `self.epoch_endings.len()` (i.e., ahead of what has actually been chained/verified so far), the function skips verification entirely and returns `Ok(())`, only emitting a `warn!` log. The developers' own `TODO(aldenhu): fix this from upper level` comment confirms this is a known, unresolved gap.

Because the `epoch` field itself comes from the same untrusted `LedgerInfo` object being verified, an attacker who can supply/tamper with the backup content (e.g. a compromised or MITM'd backup storage/bucket, or a malicious snapshot manifest handed to `db-tool restore`) can set `epoch` to an arbitrarily large, never-seen value. This deterministically routes execution into the "skip verification" branch, so **no validator signature check ever happens** for that `LedgerInfoWithSignatures` regardless of its actual (possibly empty or garbage) `AggregateSignature`.

Once the `li` passes this fake "verification," the only remaining checks are purely *self-consistency* checks that a benign consistent forgery can trivially satisfy:
- `txn_info_with_proof.verify(li.ledger_info(), manifest.version)` only checks that the supplied `TransactionInfo` hashes correctly under the accumulator root *claimed inside the same forged `li`* [6](#0-5) .
- `state_root_hash == manifest.root_hash` only checks internal consistency between the forged proof and the (also attacker-supplied) manifest.

None of these checks require any relationship to the real, validator-signed chain state.

### Impact Explanation
This breaks the core proof-integrity invariant that "authenticated proof-bearing responses must stay bound to the right ledger version, root, and object." A restoring/bootstrapping node (validator or fullnode being rebuilt from backup) can be made to commit a completely fabricated state snapshot and/or transaction history as if it were the legitimately signed chain state, because the one check meant to bind that data to the real validator set is bypassed. This is a direct analog of the referenced Olympus finding: an operation that is supposed to require a freshness/authenticity guarantee ("beat" / signature verification) instead proceeds unconditionally when that guarantee cannot be established, because the "can't verify" case is treated as "assume valid" rather than "reject."

### Likelihood Explanation
Exploitation requires control over, or the ability to tamper with, the backup artifacts consumed by the restore tool (`storage/backup/backup-cli`) — e.g., a compromised backup bucket, a MITM on the backup transport, or a malicious file handed to `aptos-db-tool restore`. This is exactly the threat model that the epoch-history/waypoint verification exists to defend against, so it is a realistic attacker who is expected to be defeated by this code path but is not.

### Recommendation
Change the `epoch > self.epoch_endings.len()` branch in `EpochHistory::verify_ledger_info` from returning `Ok(())` to returning an `Err`, so out-of-range epochs are always rejected rather than treated as trusted. If out-of-order verification is genuinely needed (e.g., concurrent/streamed epoch history restore), the caller must be restructured so verification is deferred until the necessary epoch-ending ledger info is actually available, rather than skipped.

### Proof of Concept
1. Attacker controls (or MITMs) the backup storage location used by `aptos-db-tool restore` / `RestoreCoordinator`.
2. Attacker crafts a `StateSnapshotBackup` manifest plus its `(TransactionInfoWithProof, LedgerInfoWithSignatures)` proof file such that:
   - The embedded `LedgerInfo.epoch` is set to a very large value (larger than any epoch actually covered by `EpochHistory.epoch_endings`, e.g. `u64::MAX / 2`).
   - `AggregateSignature` is empty or arbitrary (never checked).
   - `TransactionInfo`/state-checkpoint hash/root hash and accumulator proof are all internally self-consistent (attacker fully controls both sides), and the state chunks contain attacker-chosen key/value pairs with proofs against the attacker's own fabricated tree.
3. Node operator runs restore; `StateSnapshotRestoreController::run_impl` calls `txn_info_with_proof.verify(...)` (passes, self-consistent) then `epoch_history.verify_ledger_info(&li)`.
4. Inside `verify_ledger_info`, `epoch > self.epoch_endings.len()` is true, so the function logs a warning and returns `Ok(())` without ever calling `ValidatorVerifier::verify`.
5. The attacker-controlled state snapshot is accepted and written into the node's durable storage as legitimate chain state.

    pub fn verify_ledger_info(&self, li_with_sigs: &LedgerInfoWithSignatures) -> Result<()> {
        let epoch = li_with_sigs.ledger_info().epoch();
        ensure!(!self.epoch_endings.is_empty(), "Empty epoch history.",);
        if epoch > self.epoch_endings.len() as u64 {
            // TODO(aldenhu): fix this from upper level
            warn!(
                epoch = epoch,
                epoch_history_until = self.epoch_endings.len(),
                "Epoch is too new and can't be verified. Previous chunks are verified and node \
                won't be able to start if this data is malicious."
            );
            return Ok(());
        }
        if epoch == 0 {
            ensure!(
                li_with_sigs.ledger_info() == &self.epoch_endings[0],
                "Genesis epoch LedgerInfo info doesn't match.",
            );
        } else if let Some(wp_trusted) = self
            .trusted_waypoints
            .get(&li_with_sigs.ledger_info().version())
        {
            let wp_li = Waypoint::new_any(li_with_sigs.ledger_info());
            ensure!(
                *wp_trusted == wp_li,
                "Waypoints don't match. In backup: {}, trusted: {}",
                wp_li,
                wp_trusted,
            );
        } else {
            self.epoch_endings[epoch as usize - 1]
                .next_epoch_state()
                .ok_or_else(|| anyhow!("Shouldn't contain non- epoch bumping LIs."))?
                .verify(li_with_sigs)?;
        };
        Ok(())
    }

/// Verifies that a given `transaction_info` exists in the ledger using provided proof.
fn verify_transaction_info(
    ledger_info: &LedgerInfo,
    transaction_version: Version,
    transaction_info: &TransactionInfo,
    ledger_info_to_transaction_info_proof: &TransactionAccumulatorProof,
) -> Result<()> {
    ensure!(
        transaction_version <= ledger_info.version(),
        "Transaction version {} is newer than LedgerInfo version {}.",
        transaction_version,
        ledger_info.version(),
    );

    let transaction_info_hash = transaction_info.hash();
    ledger_info_to_transaction_info_proof.verify(
        ledger_info.transaction_accumulator_hash(),
        transaction_info_hash,
        transaction_version,
    )?;

    Ok(())
}
