### Title
Feeless `estimateEnergy` RPC call can consume full block-production CPU budget per internal VM execution, repeated across the binary-search loop, enabling single-request DoS - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
When `vm.constantCallTimeoutMs` is left at its default value of `0`, `VMActuator.calculateCpuLimitInUs` falls back to granting constant (read-only) calls the *same* CPU budget as a real block-producing transaction (`maxCpuTimeOfOneTx * cpuLimitInUsRatio`), and `getCpuLimitInUsRatio()` forces `cpuLimitInUsRatio = 1.0` for constant calls because their `executorType` is `ET_PRE_TYPE`. Since `Wallet.estimateEnergy` (invoked by the unauthenticated `EstimateEnergyServlet`) performs multiple internal VM executions per HTTP request, each of those executions is separately entitled to the full block CPU budget, letting a single feeless request consume CPU time equivalent to many full block-production slots.

`calculateCpuLimitInUs` only shortens the deadline for constant calls when `constantCallTimeoutMs > 0`; with the default `0` (per `reference.conf`), it falls through to `maxCpuTimeOfOneTxMs * cpuLimitInUsRatio` — the same formula used for real transactions. In addition, `getCpuLimitInUsRatio()` returns `1.0` whenever `executorType != ET_NORMAL_TYPE`, and constant calls are always forced into `ET_PRE_TYPE`: [3](#0-2) [4](#0-3) 

Consequently, each constant-call VM execution is entitled to the **full** `dps.getMaxCpuTimeOfOneTx()` — the same ceiling a real block-producing transaction is allowed. `EstimateEnergyServlet.doPost` is unauthenticated, requires no fee/signature, and calls `wallet.estimateEnergy(...)`, which is documented (and architecturally implied by its name and by the class `EstimateEnergyMessage`) to internally run a dichotomy/binary-search loop of many separate constant-call VM executions to converge on an energy estimate: [5](#0-4) 

If an attacker deploys/uses a contract engineered to run its execution time right up to `maxCpuTimeOfOneTx` on every internal call (e.g., a tight loop that consumes exactly the energy limit given at each binary-search energy guess), each of the internal executions inside a single `estimateEnergy` request can independently run for up to the full block CPU budget before being cut off by `OutOfTimeException`. None of the standard protections apply here: there's no fee (constant calls don't broadcast/pay), no energy/bandwidth accounting (constant calls bypass consumption), and `RateLimiterServlet` (which `EstimateEnergyServlet` extends) only limits request *rate*, not the CPU cost of a single request.

I was not able to directly inspect the loop/iteration count inside `Wallet.estimateEnergy` in this session (the search for `estimateEnergy`/`binarySearch` inside `Wallet.java` did not return matches, possibly due to indexing limits), so the exact "30-40 iterations" figure in the question could not be independently confirmed from the available index. The core CPU-budget-sharing bug in `VMActuator`/`calculateCpuLimitInUs`, however, is directly confirmed by the code above.

### Impact Explanation
This is a **DoS via RPC-API**: a single unauthenticated, feeless HTTP POST to `/wallet/estimateenergy` can cause the node to spend CPU time on the calling thread proportional to `(number of internal VM executions) × maxCpuTimeOfOneTx`, which — if the internal loop count is large (tens of iterations, as `estimateEnergy` binary search implementations typically are) — could be many multiples of the CPU time a real block is allotted to spend on a single transaction. Repeated concurrent requests from one attacker could stall RPC-handling threads and degrade node availability.

### Likelihood Explanation
- Precondition: `vm.constantCallTimeoutMs` unset or `0`, which is the documented default in `reference.conf`.
- Attacker needs no privileges: anonymous HTTP client, no signed transaction, no fee.
- Attacker must craft/deploy a contract whose execution time is tunable to approach `maxCpuTimeOfOneTx` at each binary-search energy guess — feasible with an unbounded loop gated by a computed iteration count, well within the reach of any contract deployer.
- Repeatable indefinitely and cheaply (deployment itself costs a normal transaction fee once; subsequent read-only `estimateEnergy` calls are free).

### Recommendation
Apply a real bound to constant-call CPU time regardless of `constantCallTimeoutMs` configuration — e.g., always cap constant-call CPU time to a small fraction of `maxCpuTimeOfOneTx` (not `1.0×`) by changing `getCpuLimitInUsRatio()`/`calculateCpuLimitInUs` to use a strictly-smaller ratio for `ET_PRE_TYPE`/`isConstantCall` executions, and/or enforce a safe non-zero default for `vm.constantCallTimeoutMs` rather than allowing `0` to mean "unbounded/full block budget." Additionally, cap or account for the total number of internal VM executions and their aggregate CPU cost within a single `estimateEnergy` request.

  private double getCpuLimitInUsRatio() {

    double cpuLimitRatio;

    if (ExecutorType.ET_NORMAL_TYPE == executorType) {
      // self witness generates block
      if (blockCap != null && blockCap.generatedByMyself
          && !blockCap.hasWitnessSignature()) {
        cpuLimitRatio = 1.0;
      } else {
        // self witness or other witness or fullnode verifies block
        if (trx.getRet(0).getContractRet() == contractResult.OUT_OF_TIME) {
          cpuLimitRatio = CommonParameter.getInstance().getMinTimeRatio();
        } else {
          cpuLimitRatio = CommonParameter.getInstance().getMaxTimeRatio();
        }
      }
    } else {
      // self witness or other witness or fullnode receives tx
      cpuLimitRatio = 1.0;
    }

    return cpuLimitRatio;
  }

  static long calculateCpuLimitInUs(boolean isConstantCall, long maxCpuTimeOfOneTxMs,
      double cpuLimitInUsRatio, long constantCallTimeoutMs) {
    if (isConstantCall && constantCallTimeoutMs > 0L) {
      return constantCallTimeoutMs * VMConstant.ONE_THOUSAND;
    }
    return (long) (maxCpuTimeOfOneTxMs * VMConstant.ONE_THOUSAND * cpuLimitInUsRatio);
  }
