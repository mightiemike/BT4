## Title
Admin `MsgUpdateTokenConfig` can change `NativeRepresentation.ContractAddress` (PRC20) for a token with no re-index/backward-compat check, permanently orphaning outbound lookups for already-minted PRC20 balances - (File: `x/uregistry/keeper/msg_update_token_config.go`, `x/uregistry/keeper/keeper.go`)

### Summary
This is the direct Push Chain analog of the Karak `slashingHandler` mismatch (M-01): a registry mapping that downstream code treats as immutable per deployed asset can be silently changed after users already hold balances minted against the old mapping, causing the module to permanently fail to resolve those balances — the same "unsynchronized state after config change breaks a check that used to pass" root cause.

### Finding Description
`x/uregistry`'s `TokenConfig.NativeRepresentation.ContractAddress` records which PRC20 contract is the canonical native representation for an external `(chain, token_address)` pair [1](#0-0) . `UpdateTokenConfig` lets the admin overwrite this field on an existing token config with no validation that the new PRC20 differs meaningfully, no migration path for balances already minted against the old PRC20, and no protection for in-flight cross-chain state: [2](#0-1) 

The reverse index `GetTokenConfigByPRC20` is keyed by the *current* `NativeRepresentation.ContractAddress` via the `PRC20Index` — once the admin updates the token config to point at a new PRC20, the index no longer resolves the old PRC20 address for that `(chain, ...)`: [3](#0-2) 

`x/uexecutor`'s outbound-creation path depends on this reverse lookup being stable for every PRC20 a user could legitimately hold and try to withdraw. When a user calls the gateway's `withdraw`/burn flow on their existing (old) PRC20 balance, the resulting on-chain event carries the *old* PRC20 address (`event.Token`), and `BuildOutboundsFromReceipt` looks it up via `GetTokenConfigByPRC20(ctx, event.ChainId, event.Token)`: [4](#0-3) 

If the admin has since repointed the token config to a different PRC20 contract, this lookup returns `collections.ErrNotFound` and the function returns an error instead of an `OutboundTx`, even though the user's EVM-side burn of the old PRC20 already occurred inside the very same EVM receipt that `BuildOutboundsFromReceipt` is processing. The same reverse-lookup dependency also exists in the rescue-funds path: [5](#0-4) 

This mirrors the Karak finding precisely: `NativeVault.slashAssets` captured `slashStore` as a fixed reference and reverted permanently once `Core`'s `assetSlashingHandlers` was updated to a new handler; here, `BuildOutboundsFromReceipt`/`AttachRescueOutboundFromReceipt` implicitly assume the PRC20⇄token mapping used at mint time remains resolvable via the *current* registry state, and a legitimate registry update (`MsgUpdateTokenConfig`) breaks that assumption for every balance minted before the update.

### Impact Explanation
Any ordinary, unprivileged holder of a PRC20 token whose native representation gets repointed by the admin loses the ability to withdraw/bridge-out that balance: their on-chain burn succeeds (value is destroyed on the EVM side within the executed receipt) but the Cosmos-module-level accounting that is supposed to create the corresponding `OutboundTx` errors out, so no outbound is ever recorded. Depending on how the caller of `BuildOutboundsFromReceipt` handles this error (not fully verifiable from the indexed source alone), this results in either: (a) the entire `executeUniversalTx`/withdraw-triggering transaction being treated as failed with the burn already committed (permanent loss of user funds), or (b) a persistently un-resolvable `UniversalTx`/log with no path to recovery, i.e., DoS of the withdraw functionality for every balance minted against the old PRC20. Both outcomes fall squarely under the allowed impact gate ("permanent loss ... of user ... controlled funds" and "denial of service ... reachable without privileged control" — the *trigger* here is the victim's own ordinary withdraw transaction, not an admin action).

### Likelihood Explanation
Token-config updates via `MsgUpdateTokenConfig` are a documented, expected admin operation (`x/uregistry/README.md` lists it as a normal message, not an edge case) [6](#0-5) , and nothing in `UpdateTokenConfig` or `ValidateBasic` prevents changing `NativeRepresentation.ContractAddress` on a token that already has outstanding minted supply. Any chain with an active token whose native representation is later corrected/rotated (e.g., swapping to a new PRC20 implementation, fixing a misconfigured address) will trigger this for all pre-existing holders. This is a realistic operational scenario rather than a contrived one, matching the "confirmed, non-hypothetical" bar the original Karak report was judged against.

### Recommendation
- Before allowing `UpdateTokenConfig` to change `NativeRepresentation.ContractAddress`, require either (a) that the old PRC20 has zero outstanding supply, or (b) retain the old PRC20 address in a historical/alias index so `GetTokenConfigByPRC20` continues to resolve it (similar to `TssKeyHistory` never being deleted in `x/utss`, which was designed precisely to keep old keys valid during a transition).
- Alternatively, add a keeper-level migration routine that atomically swaps user balances from the old PRC20 to the new one when the native representation changes, so no burn against a stale PRC20 address can ever occur.
- At minimum, make `BuildOutboundsFromReceipt`/`AttachRescueOutboundFromReceipt` fail safe (abort/refund via a retryable pending state) instead of returning a hard error when the PRC20 reverse-lookup misses, so funds are never silently stranded.

### Proof of Concept
1. Admin adds `TokenConfig{Chain: eip155:1, Address: extToken, NativeRepresentation.ContractAddress: PRC20-A}`; inbound deposits mint PRC20-A to users over time.
2. Admin calls `MsgUpdateTokenConfig` to change `NativeRepresentation.ContractAddress` to `PRC20-B` for the same `(chain, extToken)` key — this succeeds unconditionally per `UpdateTokenConfig` [2](#0-1) .
3. A user holding pre-existing PRC20-A balance calls the gateway's withdraw path, burning PRC20-A inside an `executeUniversalTx` receipt.
4. `BuildOutboundsFromReceipt` decodes the event with `event.Token = PRC20-A` and calls `GetTokenConfigByPRC20(ctx, "eip155:1", PRC20-A)` [4](#0-3) ; the `PRC20Index` now only resolves `PRC20-B`, so the call returns `collections.ErrNotFound` [7](#0-6) , and no `OutboundTx` is created for the user's already-burned funds.

**Uncertainty:** I was not able to trace the exact caller that invokes `BuildOutboundsFromReceipt` (referenced in `create_outbound.go` and `app/upgrades/chain-meta/upgrade.go`) far enough in the index to confirm definitively whether the enclosing transaction/state change is rolled back or partially committed on this error path (i.e., whether the burn is truly unrecoverable or only "stuck pending"). This should be verified directly in the repository (e.g., a Devin session with full file access) before finalizing severity, since it determines whether the impact is "permanent loss" or "temporary DoS pending admin remediation."

// UpdateTokenConfig updates an existing token configuration in the uregistry.
func (k Keeper) UpdateTokenConfig(ctx context.Context, tokenConfig *types.TokenConfig) error {
	storageKey := types.GetTokenConfigsStorageKey(tokenConfig.Chain, tokenConfig.Address)

	// Check if the token config exists
	if has, err := k.TokenConfigs.Has(ctx, storageKey); err != nil {
		return err
	} else if !has {
		return fmt.Errorf("token config for %s on chain %s does not exist", tokenConfig.Address, tokenConfig.Chain)
	}

	if err := k.TokenConfigs.Set(ctx, storageKey, *tokenConfig); err != nil {
		return err
	}
	k.Logger().Info("token config updated",
		"chain", tokenConfig.Chain,
		"token_address", tokenConfig.Address,
	)
	return nil
```

// GetTokenConfigByPRC20 looks up a token config by PRC20 address via the
// PRC20Index (O(1)). Returns ErrNotFound if the registered chain doesn't match.
func (k Keeper) GetTokenConfigByPRC20(
	ctx context.Context,
	chain string,
	prc20Addr string,
) (types.TokenConfig, error) {

	if strings.TrimSpace(prc20Addr) == "" {
		return types.TokenConfig{}, fmt.Errorf("prc20 address is empty")
	}
	// Same canonical form as the index function, so any case variant hits the row.
	prc20Addr = canonicalPRC20(prc20Addr)

	// PRC20 addresses are globally unique by construction; MatchExact returns at most one.
	iter, err := k.TokenConfigs.Indexes.PRC20Index.MatchExact(ctx, prc20Addr)
	if err != nil {
		return types.TokenConfig{}, err
	}
	defer iter.Close()

	for ; iter.Valid(); iter.Next() {
		pk, err := iter.PrimaryKey()
		if err != nil {
			return types.TokenConfig{}, err
		}
		cfg, err := k.TokenConfigs.Get(ctx, pk)
		if err != nil {
			return types.TokenConfig{}, err
		}
		if cfg.Chain == chain {
			return cfg, nil
		}
	}

	return types.TokenConfig{}, collections.ErrNotFound
}
```
