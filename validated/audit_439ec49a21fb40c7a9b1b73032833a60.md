### Title
Unbounded recursive post-order traversal in `MemTrieUpdate` allows a single wide/deep write set to stack-overflow every validator during chunk apply - (File: `core/store/src/trie/mem/memtrie_update.rs`)

### Summary
`MemTrieUpdate::post_order_traverse_updated_nodes`, invoked from `to_memtrie_changes_internal` on every trie commit, walks the tree of *updated* trie nodes using plain (non-tail) Rust recursion with no depth bound. `max_length_storage_key` is `4_194_304` bytes (≈8.4M nibbles), so a contract that performs many `storage_write` calls whose keys form a long chain of one-nibble-diverging prefixes can force the updated-node subtree to be a deep, linear chain of `Branch`/`Extension` nodes. Since the function recurses once per node along that chain with no iterative fallback, this is directly analogous to the reported `getHatLevel()` bug: an attacker-controlled linked structure drives recursion depth on a code path that ordinary, unprivileged execution (a `FunctionCall` receipt) must traverse.

### Finding Description
- `post_order_traverse_updated_nodes` recurses into every `Branch`/`Extension` child that is `Updated`, with no maximum-depth guard: [1](#0-0) 
- It is called unconditionally at the end of every trie update to build the ordered list of nodes for hashing/serialization, on the path used to produce the new state root for a chunk: [2](#0-1) 
- This is reachable purely through unprivileged transaction execution: any `FunctionCall` action that issues enough `storage_write` host calls (`wasm_storage_write_*` gas costs) mutates the trie, and the mutated subtree is exactly what gets tracked as "updated nodes" and post-order traversed at commit time.
- `max_length_storage_key` is `4_194_304` (≈4MB / 4,194,304 nibbles worth of key material), and there is no limit tying trie *branch depth* to a smaller bound; depth is governed by how many divergence points (branch nodes) exist along a chain of similar keys, not by total key length alone, but a contract can trivially create thousands of divergence points cheaply (e.g., writing keys `"k", "k0", "k00", "k000", ...`, each sharing an ever-longer prefix with the last, forcing one new `Branch` per key).
- Note that the codebase is otherwise aware of this exact class of risk and has explicitly converted equivalent traversals to iterative, stack-based algorithms elsewhere (e.g. `flatten_nodes` in `trie_storage_update.rs`, `generic_delete`/squash logic in `insert_delete.rs`/`squash.rs`, and `get_subtree_size` in `trie_recording.rs`, whose comment states "Non recursive approach to avoid any potential stack overflows"): [3](#0-2) [4](#0-3) 
`post_order_traverse_updated_nodes` was apparently missed during that hardening effort and remains genuinely recursive.

### Impact Explanation
Because `to_memtrie_changes_internal` runs deterministically on every node applying the chunk (all validators and full nodes tracking the shard), a sufficiently deep updated-node chain can exhaust the call stack during ordinary block/chunk processing. Depending on stack frame size and available stack, this can crash (`abort`/`SIGSEGV`) the node process applying the chunk — a transaction-triggered halt affecting all nodes that must apply that chunk, which is one of the explicitly accepted "concrete" impacts (state-transition halt / invalid-state-transition-adjacent DoS). Even short of an outright crash, because this is a deterministic function on the block-application critical path, differing stack limits or build configurations between node implementations/versions could cause divergent success/failure of the apply, undermining consensus safety guarantees.

### Likelihood Explanation
Reachability requires only a normal `FunctionCall` action from any unprivileged account — no special privileges, validator status, or network position are needed. The cost is bounded by gas (`wasm_storage_write_base` + per-byte costs), but crafting a chain of a few thousand keys with incrementally longer shared prefixes is well within a single `max_gas_burnt` budget (300 Tgas), and can also be amplified across a small number of chained receipts if a single receipt's gas isn't sufficient. This makes the likelihood Medium: it is straightforward to construct but requires deliberate, moderately sized crafted input (unlike a trivial one-line call), and the actual crash depends on host stack size/build (release vs. debug, thread stack size), which is uncertain without empirical testing in this environment.

### Recommendation
Convert `post_order_traverse_updated_nodes` to an explicit-stack, iterative post-order traversal, following the same pattern already used in `flatten_nodes` (`trie_storage_update.rs`) and `traverse_all_nodes` (`state_parts.rs`), which use a `Vec`-based crumb/state machine instead of Rust call-stack recursion. This removes any dependency between attacker-controlled trie shape and native stack depth, eliminating the DoS/halt vector while preserving identical output ordering semantics.

### Proof of Concept
Conceptual outline (cannot be executed in this read-only environment):
1. Deploy a test contract exposing a method that loops calling `storage_write` with keys `b"k"`, `b"k0"`, `b"k00"`, `b"k000"`, ... each one byte longer than the last and sharing the previous key as a strict prefix, for N ≈ several thousand iterations (bounded by `max_gas_burnt` / `wasm_storage_write_base` and `max_length_storage_key`).
2. Submit this as a single `FunctionCall` transaction (optionally split across a chain of self-recursive receipts, as already demonstrated feasible by the existing `max_self_recursion_delay` test pattern) so that all writes land in the same chunk's trie update.
3. Observe that at commit time, `to_memtrie_changes_internal` → `post_order_traverse_updated_nodes` recurses once per created `Branch` node along the incremental-prefix chain (≈N stack frames), and measure/monitor for stack exhaustion (crash) or note that the depth scales unbounded with N, unlike other traversal functions in the same crate that were rewritten iteratively for this exact reason.
