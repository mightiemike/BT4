## Analysis Summary

I traced the external "price rounds to zero" bug class to its structural analog in Aptos: **a proof/commitment comparator that silently skips checking a subset of the committed root fields it claims to validate**, so a divergent authenticated state is accepted as matching.

### Title
Replay-verification comparator omits state/hot-state/position checkpoint hashes, allowing a diverged committed root to be accepted as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by replay/verification tooling to assert that a locally re-executed `TransactionOutput` matches an already-committed, authenticated `TransactionInfo` (status, gas, write-set hash, event root hash). It is explicitly documented, in its own body, to **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [1](#0-0) , even though those are the exact fields that carry the state-Merkle root and the new native-position tree root into the consensus-authenticated `TransactionInfo`/`TransactionInfoV1` [2](#0-1) .

### Finding Description
`ensure_match_transaction_info` checks four things — status, gas used, write-set hash, event root hash — and then returns `Ok(())` unconditionally, deliberately skipping any comparison of the checkpoint-hash fields on `TransactionInfo` [3](#0-2) . This function is the sole correctness gate used by `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info(version, &expected_txn_infos[idx], Some(&expected_writesets[idx]), Some(&expected_events[idx]))` to decide whether replay matches the authenticated ledger [4](#0-3) . It is also used from `aptos-debugger` and `aptos-move/cli/src/commands.rs` for the same replay-verify purpose.

With the newly introduced `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature (feature id 122) [5](#0-4) , execution now commits a `position_state_checkpoint_hash` into `TransactionInfoV1`, built from a separate native-position Jellyfish Merkle tree that is chained across blocks/chunks via `ProvablePositionStateSummary` [6](#0-5) , and this root is what consensus/state-sync trust as authenticating the position ledger state (analogous to `state_checkpoint_hash` for account state). Because `ensure_match_transaction_info` never compares this field (nor `state_checkpoint_hash`/`hot_state_checkpoint_hash`) against the freshly recomputed value, any divergence between the locally recomputed position/state Merkle root and the archived, already-signed `TransactionInfo` goes completely undetected by replay-verify tooling.

This is precisely the "rounds to zero / silently passes" bug class from the source report: a validation function that is supposed to gate acceptance of a computed value against an authenticated on-chain commitment has an unchecked path (in the oracle's case, `price == 0`; here, three checkpoint-hash fields) that lets a wrong value slip through as "verified."

### Impact Explanation
`replay_on_archive` and the debugger's replay-verify path are the primary tools operators and auditors use to confirm that historical execution/storage handling reproduces the authenticated ledger, including for hard-fork or storage-schema migration validation. If the state Merkle root, hot-state root, or the new native-position root diverges from the archived, signed value — due to an execution bug, storage bug, or a bug in the trading-native subsystem itself — this tool will report the chunk as successfully verified. This directly violates the "Wrong ... state proof accepted as valid" / "Authenticated API or state-view output bound to the wrong version, object, or proof context" gate criteria: the comparator is the authoritative bound between recomputed state and the consensus-committed root, and it is missing entirely for these fields. The comment even names the exact operational consequence: "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

### Likelihood Explanation
The gap is unconditional and always present in current code (the comparator never checks these fields for any TransactionInfoV1-enabled chunk), so it triggers as soon as `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or hot-state root in txn info) is enabled and any divergence exists between local replay and the archived commitment — no adversarial input crafting is required, only a bug or discrepancy in the trading-native/hot-state computation path elsewhere in the stack. The code comment itself flags this as a known, un-fixed gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), indicating it is not yet resolved.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s freshly computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against the values recomputed during replay/state-checkpoint construction, returning an error on mismatch, mirroring the existing `write_set_hash`/`event_root_hash` checks. This must be wired in (and gated appropriately by `transaction_info_v1`/feature flags) before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on any network where replay-verify is relied on for integrity assurance.

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on a test network so `TransactionInfoV1.position_state_checkpoint_hash` is populated and consensus-signed.
2. Introduce (or naturally hit, via a real bug) a divergence between the locally recomputed native-position JMT root and the archived committed root — e.g., replay against a database with a corrupted/incorrectly-migrated native-position tree, or a version of the executor with a bug in `ProvablePositionStateSummary`.
3. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`) over the affected version range.
4. Observe that `execute_and_verify` reports no error because `ensure_match_transaction_info` only checks status/gas/write-set hash/event root hash — the position (or state/hot-state) checkpoint hash mismatch is never inspected — confirming replay-verify falsely reports success despite a corrupted/divergent authenticated root [1](#0-0) [7](#0-6) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
