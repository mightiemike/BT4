## Title
Attached deposit permanently lost in `WalletContract::address_check_callback` when target address resolves to an already-registered account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (used to give ETH-implicit accounts a NEAR-native execution path, NEP-518) tracks a caller's attached deposit via `CallerDeposit` so it can be refunded if the requested cross-contract action ultimately fails [1](#0-0) . However, one specific rejection branch inside `address_check_callback` returns an error response and drops `caller_deposit` on the floor instead of refunding it, so the deposit is permanently retained by the wallet contract with no recovery path — the same root cause shape as the referenced report (funds move into the contract, the operation is rejected, and the accounting/consumption of the request leaves the depositor with no way to reclaim their assets).

### Finding Description
`rlp_execute` is `#[payable]`, so any unprivileged caller can attach a NEAR deposit when invoking it [2](#0-1) . `CallerDeposit::new` records the deposit for any external (non-self) caller [3](#0-2) , with the explicit comment that this tracking exists "to refund the caller's deposit if the cross-contract call fails" [4](#0-3) .

For an EOA base-token transfer whose target is another eth-implicit address, `inner_rlp_execute` schedules a call to the address registrar and forwards `caller_deposit` into `address_check_callback` [5](#0-4) . In that callback, if the registrar reports that the target address is already claimed by a *named* account (`maybe_account_id.is_some()`), and the caller is **not** using a wallet-owned access key (`env::signer_account_id() != current_account_id`), the function returns an error response directly:

```rust
return PromiseOrValue::Value(ExecuteResponse {
    success: false,
    success_value: None,
    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
});
``` [6](#0-5) 

Note that `caller_deposit` is a parameter of this function but is never referenced in this branch — unlike the properly-handled failure path in `rlp_execute_callback`, which explicitly refunds `caller_deposit` when the underlying promise fails [7](#0-6) . Because this callback function returns a `Value` (a normal successful return, not a panic/failed receipt), the NEAR runtime's automatic deposit-refund-on-failure mechanism does not trigger — that mechanism only fires when an action *receipt* fails, not when a contract method completes successfully but chooses to reject the logical operation [8](#0-7) . The attached deposit is thus absorbed into the Wallet Contract account's own balance with no method exposed to reclaim it — the contract has no owner/admin withdrawal function.

### Impact Explanation
An external caller who attaches NEAR to `rlp_execute` and hits this specific rejection path (target address collides with an already-registered named account) permanently loses their attached deposit. This is a direct analog of the report's core defect: assets are moved into the contract as part of a request, the request is rejected by contract logic, and there is no compensating transfer or recovery mechanism, so funds become permanently stuck. This is reachable by any single unprivileged transaction from an ordinary caller (no validator/relayer/operator privilege required, no malicious peer/network assumption).

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (1) a caller to attach a non-zero deposit to `rlp_execute` for an emulated EOA base-token transfer with `address_check: Some(_)`, and (2) the address-registrar lookup to resolve to an already-registered named account. This can occur incidentally (e.g., relayers/users experimenting or mis-targeting an address that has since been claimed by a named account) rather than requiring an adversarial setup.

### Recommendation
In the `maybe_account_id.is_some()` branch of `address_check_callback`, refund `caller_deposit` (mirroring the logic already present in `rlp_execute_callback`'s `PromiseResult::Failed` arm) before returning the error `ExecuteResponse`, for both the relayer-ban sub-branch and the direct-error sub-branch.

### Proof of Concept
1. Deploy/attach the wallet contract to an eth-implicit account `E`.
2. An external account `A` (not holding an access key on `E`) calls `E.rlp_execute(target, tx_bytes_b64)` attaching `N` yoctoNEAR, where the encoded Ethereum transaction is an `EOABaseTokenTransfer` whose destination address hashes to an eth-implicit address that has meanwhile been registered to a named account via the address registrar.
3. `inner_rlp_execute` builds `caller_deposit = Some(CallerDeposit { account_id: A, yocto_near: N })` and schedules `address_registrar.lookup(...).then(address_check_callback(target, action, caller_deposit))` [9](#0-8) .
4. The registrar lookup returns `Some(account_id)`, and since `env::signer_account_id() != current_account_id` (a plain external caller, not a wallet-owned relayer key), `address_check_callback` returns the "Invalid target" error `Value` without ever using `caller_deposit` [6](#0-5) .
5. `A`'s `N` yoctoNEAR remains in `E`'s account balance permanently; no subsequent call can retrieve it since the contract exposes no such recovery method.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
