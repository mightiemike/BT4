### Title
Negative/negative-overflow exchange pool balances via unbounded Bancor-curve output when `allowHardenExchangeCalculation()` is disabled - (File: `ExchangeTransactionActuator.java`, `ExchangeCapsule.java`, `ExchangeProcessor.java`)

### Summary
When the hardened-exchange-calculation proposal is inactive, `ExchangeCapsule.transaction()` uses the legacy `ExchangeProcessor` (Bancor-relay double-math) and only guards against negative resulting balances when `hardenedCalc == true` (`ExchangeCapsule.java:160`). An attacker who repeatedly sells a large quantity of one side of the pool relative to the current balance can make `exchangeFromSupply` return an output larger than the pool's actual counter-token balance, driving `firstTokenBalance`/`secondTokenBalance` negative, since `ExchangeTransactionActuator.doValidate()` (lines 194-197) only rejects balances that are exactly `0`, never negative or about-to-go-negative values.

### Finding Description
`ExchangeTransactionActuator.execute()` computes the counter-asset amount via `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` [1](#0-0) . Inside `ExchangeCapsule.transaction()`, the resulting balance is only checked for negativity when `hardenedCalc` is true: `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) { throw ... }` [2](#0-1) . When `hardenedCalc` is `false` (legacy path, selected before `allowHardenExchangeCalculation()` is activated on-chain), the new balances are stored unconditionally via `this.exchange = this.exchange.toBuilder().setFirstTokenBalance(...).setSecondTokenBalance(...)` regardless of sign [3](#0-2) .

The legacy `ExchangeProcessor.exchange()` computes the swap via a Bancor-relay double-precision formula (`exchangeToSupply`/`exchangeFromSupply`) that is not algebraically bounded by the actual pool reserve [4](#0-3) . For sufficiently large `sellTokenQuant` relative to the current `sellTokenBalance`, the relay amount approaches `supply * (1 - 2^0.0005)`, and feeding that relay into `exchangeFromSupply` for a comparatively small `buyTokenBalance` can yield an `exchangeBalance` output that exceeds `buyTokenBalance` itself — i.e., the trade can return more counter-tokens than the pool actually holds.

`doValidate()` only performs these checks relevant to balance sufficiency:
- `firstTokenBalance == 0 || secondTokenBalance == 0` (rejects only exact-zero, not negative or soon-to-be-negative) [5](#0-4) .
- `tokenBalance > balanceLimit` on the *sell* side balance after adding `tokenQuant` (an upper bound check, irrelevant to depletion of the buy side) [6](#0-5) .
- `anotherTokenQuant < tokenExpected` (only a minimum-received guard for the trader, not a pool-solvency guard) [7](#0-6) .

None of these checks verify `anotherTokenQuant <= currentBuyTokenBalance`. Once the buy-side balance is pushed negative by one large trade, subsequent trades on the opposite direction (selling the now-scarce token back) continue to be computed off increasingly distorted (negative) reserve values, since the only zero check trips on exact `0`, which a negative balance will never equal.

### Impact Explanation
This allows an unprivileged, funded account to extract more of the counter-asset (TRX or TRC10) from an `Exchange` pool than was ever deposited into it, corrupting `ExchangeCapsule`'s `firstTokenBalance`/`secondTokenBalance` invariants and creating value out of thin air for the attacker while destroying value for other exchange participants/the protocol's TRC10/TRX accounting. This falls under the "asset/accounting corruption" and "unauthorized creation/destruction of value" bounty class.

### Likelihood Explanation
Exploitability strictly requires the network to not have activated the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal (i.e., `allowHarden()` returns `false`), which is the legacy/default state on chains where that proposal has not been passed by the committee. Given that state, any account with sufficient TRX/TRC10 balance can submit `ExchangeTransactionContract` transactions with `calcFee() == 0` (no fee cost) repeatedly, self-funding large sell quantities to trigger the described numerical excess. No special privileges, signatures beyond normal transaction signing, or non-default node configuration are needed — the attack is fully repeatable and cost is limited to bandwidth/energy for ordinary transactions.

### Recommendation
Remove the `hardenedCalc &&` conditional guard in `ExchangeCapsule.transaction()` so that the negative-balance check applies unconditionally regardless of legacy or hardened math path, and/or add an explicit `doValidate()` check ensuring `anotherTokenQuant` does not exceed the current opposite-side balance before allowing execution, independent of the harden-proposal activation state.

### Proof of Concept
```java
// Conceptual JUnit outline (framework/src/test/java/org/tron/core/actuator/ExchangeTransactionActuatorTest.java)
// Preconditions: allowHardenExchangeCalculation() == false (hardenedCalc=false), allowStrictMath()=true/false either way.
ExchangeCapsule exchangeCapsule = new ExchangeCapsule(...);
exchangeCapsule.setBalance(firstTokenBalanceSmall, secondTokenBalanceSmall); // e.g. small pool

// Attacker sells a very large quant of firstToken relative to firstTokenBalance
long anotherTokenQuant = exchangeCapsule.transaction(
    firstTokenID, hugeSellQuant, /*useStrictMath*/ true, /*hardenedCalc*/ false);

// Expected (buggy) result: anotherTokenQuant > secondTokenBalanceSmall
assertTrue(anotherTokenQuant > secondTokenBalanceSmall);
// Resulting pool state:
assertTrue(exchangeCapsule.getSecondTokenBalance() < 0); // invariant violated, no exception thrown
```
Because `doValidate()`'s zero-balance check (`ExchangeTransactionActuator.java:194-197`) never fires on negative values, subsequent calls to `ExchangeTransactionActuator.execute()` against the same `exchangeId` will keep succeeding, letting the attacker drain further balances derived from the corrupted (negative) reserve state.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
