### Title
Toggling `enable_casm_hash_migration` mid-chain causes a deterministic panic in `finalize_block`, halting block production - (File: `crates/blockifier/src/blockifier/transaction_executor.rs`)

### Summary
The Karak finding shows that a security-relevant, admin-mutable mapping (`slashingHandler`) being changed after related state was created leads to a hard-coded equality check reverting forever. The analogous root cause here is the `enable_casm_hash_migration` versioned-constant flag combined with the bouncer-tracked `class_hashes_to_migrate` set: `finalize_block` unconditionally asserts that this set is empty whenever the flag is off, but the set is populated purely from execution-time behavior of `should_migrate`, not from the flag itself.

### Finding Description
`finalize_block` reads the current block's `enable_casm_hash_migration` versioned constant and asserts an invariant against data computed independently during transaction execution: [1](#0-0) 

The `class_hashes_to_migrate` map is populated whenever `should_migrate` (in `crates/blockifier/src/utils.rs`) determines that a class hash's compiled-class-hash v1 in the current state differs from its v2 hash — which is a property of individually declared/executed classes (per-class state), not of the current block's versioned constant: [2](#0-1) 

`enable_casm_hash_migration` is a versioned constant that changes automatically as the network activates new Starknet protocol versions (part of the `VersionedConstants` table keyed by `StarknetVersion`), i.e., it is *not* a value fixed at declare time for any given class — it is a chain-wide setting that can differ from block to block as the protocol version advances: [3](#0-2) [4](#0-3) 

This mirrors the Karak pattern precisely: a per-object piece of state (here, a class's v1/v2 compiled-class-hash mismatch, populated by any unprivileged user's `invoke`/`declare` transaction that touches an old-format class) is checked against a global config value (`enable_casm_hash_migration`) that can be toggled independently by protocol/version changes, with a hard assertion instead of graceful handling when the two go out of sync.

### Impact Explanation
If a block executes any transaction that legitimately triggers migration (an unprivileged user invoking or declaring against a Cairo1 class stored with a v1 compiled-class-hash) while the currently active `enable_casm_hash_migration` versioned constant for that block is `false` (e.g., due to a version rollback, a bug in version selection, or misaligned deployment of nodes running different binary versions with different default assumptions), the sequencer panics via `assert!` inside `finalize_block`. Because this runs on the hot path of every block's finalization (`TransactionExecutor::finalize` → `finalize_block`), a panic here crashes block-building/execution for that block, and — since any unprivileged transaction touching an affected class can trigger the migration entry — this is trivially reachable from a single submitted transaction. This constitutes a "network unable to confirm new transactions" condition (High) if such a mismatch occurs consistently across the fleet, since it repeats every time the same class is executed under the same versioned constants configuration.

### Likelihood Explanation
The likelihood is moderate to high in any deployment where node operators can end up on a version whose `enable_casm_hash_migration` constant is `false` (e.g. a stale/rolled-back binary, or an intentional per-chain override) while previously-migrated or migration-eligible classes exist in state — a state fully reachable by ordinary user declare/invoke transactions with no special privilege required. Unlike a purely operator-triggered issue, the *trigger* (a transaction referencing a class whose stored compiled-class-hash is v1) is fully attacker/user-controlled; the only external dependency is which versioned-constants set is active for the block, which is a property of the node/protocol-version configuration rather than of a malicious actor, matching the "unsynchronized state" root cause pattern from the source report.

### Recommendation
- Replace the `assert!` in `finalize_block` (crates/blockifier/src/blockifier/transaction_executor.rs, lines 265-270) with a recoverable error path (e.g., return `TransactionExecutorError`) instead of panicking, so the sequencer can reject/skip the specific transaction or block rather than crashing.
- Consider gating `should_migrate` from being invoked/populating `class_hashes_to_migrate` at all when `enable_casm_hash_migration` is `false` for the given block context, so the invariant can never be violated by construction rather than being asserted after the fact.
- Ensure `enable_casm_hash_migration` transitions (true→false in particular) are treated as a protocol upgrade concern with explicit migration/compatibility handling, not a silent versioned-constants diff.

### Proof of Concept
1. Assume a Starknet version/build where `VersionedConstants.enable_casm_hash_migration == true` is active, and some class `C` (Cairo1) is declared/stored with only the v1 compiled-class-hash in state (a state reachable via ordinary `declare` transaction flows shown in `crates/blockifier/src/blockifier/transaction_executor_test.rs` lines 404-536, which explicitly test the "declared with old hash version" scenario).
2. An unprivileged user submits an `invoke` transaction that calls into class `C`. During execution, `should_migrate` (crates/blockifier/src/utils.rs:122-143) detects that the state's compiled-class-hash for `C` differs from the freshly computed v2 hash, and the bouncer records `C` in `class_hashes_to_migrate`.
3. Before/at finalization of this block, the effective `enable_casm_hash_migration` versioned constant for the block context is `false` (e.g., a sequencer node running against an older/rolled-back `StarknetVersion`, or a version where this flag transitions back to false in a later versioned-constants file — note `crates/blockifier/src/blockifier_versioned_constants.rs` lists monotonically increasing versions V0_13_0 through V0_14_3, but nothing in the reviewed code technically prevents a future/rolled-back diff introducing `enable_casm_hash_migration = false` while migration-eligible classes already exist in state).
4. `finalize_block` (crates/blockifier/src/blockifier/transaction_executor.rs:265-270) evaluates `!block_context.versioned_constants.enable_casm_hash_migration` as `true` and asserts `class_hashes_to_migrate.is_empty()`, which is `false` because step 2 populated it — the process panics, aborting block finalization for every block containing such a transaction under that versioned-constants configuration.

*Note: I could not fully verify within the available index whether any protocol version transition realistically ships `enable_casm_hash_migration = false` after having shipped `true` (this depends on the specific versioned-constants JSON diffs across releases, which are large data files not fully retrievable through the index). This is the key remaining uncertainty for confirming real-world reachability of the mismatch, though the code path and assertion itself are confirmed to exist exactly as described.*

```rust
// Class should migrate if his compiled class hash v2 is different from the one in the state.
/// Returns a map of class hashes to their compiled class hashes for migration if the class should
/// migrate, otherwise returns None.
pub fn should_migrate(
    state_reader: &impl StateReader,
    class_hash: ClassHash,
) -> StateResult<Option<(ClassHash, CompiledClassHashV2ToV1)>> {
    let state_compiled_class_hash = state_reader.get_compiled_class_hash(class_hash)?;
    match state_compiled_class_hash {
        // Class hash does not exist in the state, or is a Cairo 0 class.
        CompiledClassHash(hash) if hash == StarkHash::ZERO => Ok(None),
        state_compiled_class_hash => {
            let compiled_class_hash_v2 = state_reader.get_compiled_class_hash_v2(
                class_hash,
                &state_reader.get_compiled_class(class_hash)?,
            )?;
            // If the state compiled class hash is compiled class hash v2, the class should not
            // migrate.
            if state_compiled_class_hash == compiled_class_hash_v2 {
                return Ok(None);
            }
            Ok(Some((class_hash, (compiled_class_hash_v2, state_compiled_class_hash))))
        }
    }
}
```
