### Title
`ExchangeInjectActuator.execute` uses overflow-prone primitive arithmetic while `doValidate` uses overflow-free `BigInteger` math, causing valid transactions to fail unexpectedly - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` computes the counter-asset amount (`anotherTokenQuant = balance * quant / otherBalance`) two different ways: `doValidate()` uses `BigInteger` (which cannot overflow), while `execute()` uses primitive `long` arithmetic via `multiplyExact`/`floorDiv` [1](#0-0) . This is the same bug class as the reported `BigDiv.vy` issue: an intermediate multiplication (`balance * quant`) can overflow even though the final divided result is well within `long` range, causing the calculation to fail (throw) in cases where it should succeed.

### Finding Description
`doValidate()` computes `anotherTokenQuant` with `BigInteger` multiplication/division, which never overflows and correctly determines whether the resulting balances stay under `getExchangeBalanceLimit()`: [2](#0-1) 

`execute()`, however, recomputes the *same* value using raw `long` multiplication guarded by `multiplyExact`, which throws `ArithmeticException` as soon as the **intermediate product** `secondTokenBalance * tokenQuant` (or `firstTokenBalance * tokenQuant`) exceeds `Long.MAX_VALUE` — regardless of whether the final quotient `anotherTokenQuant` is small and perfectly safe: [1](#0-0) 

Since exchange pool balances are only bounded by the dynamic, admin-configurable `getExchangeBalanceLimit()` [3](#0-2) , it is entirely possible for `balance` and `quant` to each be large (e.g. on the order of 1e9–1e18, consistent with the `1_000_000_000_000_000_000L` supply constant used elsewhere in the exchange code, e.g. `ExchangeProcessor`/`SafeExchangeProcessor`) such that their product exceeds `Long.MAX_VALUE` (~9.2e18) while the quotient `anotherTokenQuant` remains small and entirely valid. In that case:
- `doValidate()` succeeds (BigInteger math, no overflow, all balance-limit checks pass).
- `execute()` then throws `ArithmeticException` from `multiplyExact`, which is caught and converted into `ContractExeException`, marking the transaction `FAILED`.

This exactly mirrors the audited `BigDiv` flaw: "calculations such as `(a*b)/d` can fail if the numerators are large... even though the end result is well below the maximum," and the described exploit path — an attacker can front-run/adjust pool balances (via their own `ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction` transactions, all unprivileged, permissionless calls) to push `firstTokenBalance`/`secondTokenBalance` into the range that causes a victim's pending `ExchangeInjectContract` transaction to pass validation but fail at execution.

Other exchange actuators (`ExchangeWithdrawActuator`) consistently use `BigInteger`/`BigDecimal` in both `doValidate` and `execute`, so they don't exhibit this specific validate/execute arithmetic mismatch [4](#0-3) . `ExchangeInjectActuator` is the outlier.

### Impact Explanation
This is a functional-correctness / availability bug reachable by any account authorized to call `ExchangeInjectContract` (the exchange creator) via a normal broadcast transaction. A transaction that legitimately passes all consensus validation checks can subsequently throw an unexpected `ArithmeticException` during `execute()`, causing the transaction to fail on-chain (fee consumed, action not applied) even though the true numeric result would have been valid. Because pool balances can be pushed towards the overflow threshold by other permissionless exchange transactions, this can be weaponized to reliably cause a specific pending `ExchangeInject` transaction to fail (a targeted execution-time DoS), consistent with the "front run to force targeted transactions to fail" impact described in the source report.

### Likelihood Explanation
Requires the exchange's `firstTokenBalance`/`secondTokenBalance` and the injected `tokenQuant` to be large enough that their product exceeds `Long.MAX_VALUE`; this can occur with sufficiently large exchange pools (limited only by the tunable `getExchangeBalanceLimit()` dynamic parameter) or by an attacker inflating a pool via legitimate exchange injections before submitting/front-running a targeted transaction. This makes the bug moderately likely to trigger only for exchanges with very large balances, but it is realistically reachable without any privileged access — just ordinary `ExchangeInjectContract` transactions.

### Recommendation
Make `execute()` compute `anotherTokenQuant` the same way `doValidate()` does — using `BigInteger` multiply/divide (or a proper "multiply-then-divide without overflow" helper as used in `MarketUtils.multiplyAndDivide`, which itself falls back to `BigInteger` on overflow) — instead of primitive `multiplyExact`/`floorDiv`. This keeps validate/execute semantics consistent and avoids spurious `ArithmeticException`s when the true result is well within range.

### Proof of Concept
1. Create an exchange pool where `firstTokenBalance` and `secondTokenBalance` are large (approaching `getExchangeBalanceLimit()`), and construct/allow a `tokenQuant` such that `secondTokenBalance * tokenQuant` (raw product) exceeds `Long.MAX_VALUE` while `secondTokenBalance * tokenQuant / firstTokenBalance` (the true `anotherTokenQuant`) is small and valid — analogous to the reported example `a=340282366920938463463374607431768211456`, `bigDiv2x1(a,a,a,false)` overflowing despite the result being small.
2. Submit this `ExchangeInjectContract` transaction; `doValidate()` (BigInteger path) accepts it as all balance-limit and balance-sufficiency checks pass.
3. During block application, `execute()` recomputes the value with `multiplyExact(secondTokenBalance, tokenQuant)`, which throws `ArithmeticException`, is caught, and the transaction is marked `FAILED` via `ContractExeException` — despite having passed validation.
