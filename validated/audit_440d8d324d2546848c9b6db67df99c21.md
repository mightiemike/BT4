### Title
Shrink-candidate selection undercounts tombstone bytes, causing wasted shrink CPU/IO and understated storage reclamation - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb`'s shrink-eligibility checks (`is_shrinking_productive`, `alive_bytes_after_shrink`, `select_candidates_by_total_usage`) estimate the post-shrink size of a storage using only "alive" account bytes, while the actual rewrite performed by `shrink_storage()` also carries forward "tombstone" accounts (zero-lamport single-ref accounts that cannot yet be purged). The tombstone bytes are a real, unavoidable cost of the shrink operation but are invisible to the cost/benefit estimates that decide whether and how much to shrink — an accounting gap directly analogous to the reported bug class where a real, mandatory cost (L1 data fee) is excluded from a fee/cost estimate, causing the estimate to diverge from the true resource cost and degrading the system for legitimate operations.

### Finding Description
When a storage is shrunk, `shrink_collect()` separates its stored accounts into three buckets: obsolete (dropped), alive (rewritten), and "tombstones to carry forward" — zero-lamport single-ref accounts that must be preserved until the next full snapshot (`can_purge_zero_lamport_single_ref_after_shrink`): [1](#0-0) 

The actual bytes written back to the new storage are `alive_total_bytes + tombstones_total_bytes`: [2](#0-1) [3](#0-2) 

However, the *pre-shrink decision logic* that determines whether a store is worth shrinking, and how many bytes will be saved, only looks at `alive_bytes_after_shrink()`, which excludes tombstones entirely: [4](#0-3) 

The same undercounted metric feeds the batch-level candidate selection used by `shrink_candidate_slots`, where `bytes_saved` and the running `alive_ratio`/`total_bytes` accumulator are computed purely from `alive_bytes_after_shrink`: [5](#0-4) 

Because tombstone bytes are omitted from these estimates:
1. `is_shrinking_productive()` can return `true` (i.e., "there is enough garbage to justify a shrink") for a store whose true post-shrink size (alive + tombstones) is actually close to, or not meaningfully smaller than, its current size — the real "should_not_shrink" gate applied later inside `shrink_storage()` uses `total_rewrite_bytes` (which *does* include tombstones) and can then abort the shrink after the expensive index scan and unique-account collection have already run.
2. `select_candidates_by_total_usage()` overestimates the bytes that will actually be reclaimed across a batch of candidates, so it can stop selecting additional candidates believing the target alive-ratio goal has been met, while the true post-shrink storage footprint remains larger than assumed because tombstone bytes were never subtracted from the running `total_bytes` estimate.

An unprivileged user can trivially create this pattern: closing many accounts to zero lamports (creating zero-lamport single-ref "tombstones") before the next full snapshot is taken forces those bytes to be carried forward on every subsequent shrink pass of the affected slot, systematically at odds with the shrink cost model.

### Impact Explanation
This falls under the accepted "disproportionate storage and CPU cost" impact category. The effect is twofold:
- **Wasted CPU/IO**: `shrink_storage()` performs a full index read, unique-account collection, and (in the pathological case) storage allocation, only to discover — after nontrivial work — that the shrink was not worth it once tombstone bytes are properly counted via `should_not_shrink(total_rewrite_bytes, written_bytes)`.
- **Understated reclamation / storage bloat**: `select_candidates_by_total_usage()`'s batch-selection loop can terminate early (believing the shrink-ratio goal is satisfied) while real on-disk usage remains higher than modeled, since tombstone bytes are excluded from the alive_ratio accounting used to decide when to stop, allowing storage to grow disproportionately relative to the accounting used to control it.

This does not require any validator/peer/operator role — it is triggerable purely through standard account-closing transactions by any user, and the root cause is a genuine cost/accounting mismatch in the shrink subsystem rather than a mocked or theoretical scenario.

### Likelihood Explanation
Any workload that creates zero-lamport single-ref accounts between full snapshots (a routine and common on-chain pattern, e.g., closing token/program accounts) will populate `tombstone_offsets` for the corresponding storages. Since full snapshots are taken periodically rather than continuously, there is a persistent window in which many slots can accumulate carried-forward tombstones, making the divergence between estimated and actual shrink cost/benefit a regular occurrence rather than an edge case.

### Recommendation
Include `tombstones_total_bytes` (or an equivalent tombstone-byte estimate obtained from `store.tombstone_offsets_read_lock()`) in:
- `AccountsDb::alive_bytes_after_shrink()` (or a new "bytes after shrink" helper used specifically for candidate scoring) so that `is_shrinking_productive()` and the batch selection loop in `select_candidates_by_total_usage()` both reflect the true post-shrink storage size.
- The `bytes_saved` computation in `select_candidates_by_total_usage()`, so the cumulative `total_bytes`/`alive_ratio` used to decide when to stop batching accurately represents what will remain on disk after tombstones are carried forward.

### Proof of Concept
Conceptual repro (matches the existing test harness style in `accounts-db/src/accounts_db/tests/impl.rs`):
1. Store N accounts with substantial data size in slot S; root and flush.
2. Zero out a large fraction of those accounts (creating zero-lamport single-ref entries) in a later slot before a full snapshot is taken, so `can_purge_zero_lamport_single_ref_after_shrink(S)` is `false` and the zeroed accounts become tombstones for slot S.
3. Call `shrink_candidate_slots()`/`shrink_slot_forced()` on slot S and observe that `is_shrinking_productive` and `select_candidates_by_total_usage` treat the store as highly reclaimable (since `alive_bytes_after_shrink` ignores tombstone bytes), while the actual rewritten storage size returned from `shrink_storage()` (`shrink_collect.written_bytes` vs `alive_total_bytes + tombstones_total_bytes`) shows a much smaller real reduction, or the store is skipped altogether via `should_not_shrink(total_rewrite_bytes, written_bytes)` after having already performed the full index scan/collection.     /// Given the input `ShrinkCandidates`, this function sorts the stores by their alive ratio
    /// in increasing order with the most sparse entries in the front. It will then simulate the
    /// shrinking by working on the most sparse entries first and if the overall alive ratio is
    /// achieved, it will stop and return:
    /// first tuple element: the filtered-down candidates and
    /// second duple element: the candidates which
    /// are skipped in this round and might be eligible for the future shrink.
    fn select_candidates_by_total_usage(
        &self,
        shrink_slots: &ShrinkCandidates,
        shrink_ratio: f64,
    ) -> (IntMap<Slot, Arc<AccountStorageEntry>>, ShrinkCandidates) {
        struct StoreUsageInfo {
            slot: Slot,
            alive_ratio: f64,
            alive_bytes_after_shrink: u64,
            store: Arc<AccountStorageEntry>,
        }
        let mut store_usages = Vec::with_capacity(shrink_slots.len());
        let mut total_alive_bytes: u64 = 0;
        let mut total_bytes: u64 = 0;
        for slot in shrink_slots {
            let Some(store) = self.storage.get_slot_storage_entry(*slot) else {
                continue;
            };
            let alive_bytes_after_shrink = self.alive_bytes_after_shrink(&store) as u64;
            total_alive_bytes += alive_bytes_after_shrink;
            let written_bytes = store.written_bytes();
            total_bytes += written_bytes;
            debug_assert!(
                written_bytes > 0,
                "shrink candidate has zero written bytes! slot: {slot} id: {}",
                store.id(),
            );
            let alive_ratio = alive_bytes_after_shrink as f64 / written_bytes as f64;
            store_usages.push(StoreUsageInfo {
                slot: *slot,
                alive_ratio,
                alive_bytes_after_shrink,
                store: store.clone(),
            });
        }
        store_usages.sort_by(|a, b| {
            a.alive_ratio
                .partial_cmp(&b.alive_ratio)
                .unwrap_or(std::cmp::Ordering::Equal)
        });

        // Working from the beginning of store_usage which are the most sparse and see when we can stop
        // shrinking while still achieving the overall goals.
        let mut shrink_slots = IntMap::default();
        let mut shrink_slots_next_batch = ShrinkCandidates::default();
        for store_usage in &store_usages {
            let store = &store_usage.store;
            let alive_ratio = (total_alive_bytes as f64) / (total_bytes as f64);
            debug!(
                "alive_ratio: {:?} store_id: {:?}, store_ratio: {:?} requirement: {:?}, \
                 total_bytes: {:?} total_alive_bytes: {:?}",
                alive_ratio,
                store_usage.store.id(),
                store_usage.alive_ratio,
                shrink_ratio,
                total_bytes,
                total_alive_bytes
            );
            if alive_ratio > shrink_ratio {
                // we have reached our goal, stop
                debug!(
                    "Shrinking goal can be achieved at slot {:?}, total_alive_bytes: {:?} \
                     total_bytes: {:?}, alive_ratio: {:}, shrink_ratio: {:?}",
                    store_usage.slot, total_alive_bytes, total_bytes, alive_ratio, shrink_ratio
                );
                if store_usage.alive_ratio < shrink_ratio {
                    shrink_slots_next_batch.insert(store_usage.slot);
                } else {
                    break;
                }
            } else {
                let current_store_size = store.written_bytes();
                let after_shrink_size = store_usage.alive_bytes_after_shrink;
                let bytes_saved = current_store_size.saturating_sub(after_shrink_size);
                total_bytes -= bytes_saved;
                shrink_slots.insert(store_usage.slot, Arc::clone(store));
            }
        }
        (shrink_slots, shrink_slots_next_batch)
    }

    /// Returns the expected alive bytes after shrinking `store`.
    pub(crate) fn alive_bytes_after_shrink(&self, store: &AccountStorageEntry) -> usize {
        // Obsolete accounts are already excluded from `store.alive_bytes()`.
        // Zero-lamport single-ref accounts are counted as alive until shrink can purge them,
        // which is gated by the latest full snapshot slot.
        if self.can_purge_zero_lamport_single_ref_after_shrink(store.slot()) {
            store.alive_bytes_exclude_zero_lamport_single_ref_accounts()
        } else {
            store.alive_bytes()
        }
    }

    fn is_shrinking_productive(&self, store: &AccountStorageEntry) -> bool {
        let alive_count = store.count();
        let total_bytes = store.written_bytes();
        let alive_bytes = self.alive_bytes_after_shrink(store) as u64;
        if Self::should_not_shrink(alive_bytes, total_bytes) {
            trace!(
                "shrink_slot_forced ({}): not able to shrink at all: num alive: {}, bytes alive: \
                 {}, bytes total: {}, bytes saved: {}",
                store.slot(),
                alive_count,
                alive_bytes,
                total_bytes,
                total_bytes.saturating_sub(alive_bytes),
            );
            return false;
        }

        true
    }

#[test]
fn test_shrink_candidate_slots() {
    let mut accounts =
        AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);

    let pubkey_count = 30000;
    let pubkeys: Vec<_> = (0..pubkey_count)
        .map(|_| solana_pubkey::new_rand())
        .collect();

    let some_lamport = 223;
    let no_data = 0;
    let owner = *AccountSharedData::default().owner();

    let account = AccountSharedData::new(some_lamport, no_data, &owner);

    let mut current_slot = 0;

    current_slot += 1;
    for pubkey in &pubkeys {
        accounts.store_for_tests((current_slot, [(pubkey, &account)].as_slice()));
    }
    let shrink_slot = current_slot;
    accounts.add_root_and_flush_write_cache(current_slot);

    current_slot += 1;
    let pubkey_count_after_shrink = 25000;
    let updated_pubkeys = &pubkeys[0..pubkey_count - pubkey_count_after_shrink];

    for pubkey in updated_pubkeys {
        accounts.store_for_tests((current_slot, [(pubkey, &account)].as_slice()));
    }
    accounts.add_root_and_flush_write_cache(current_slot);
    accounts.clean_accounts_for_tests();

    assert_eq!(
        pubkey_count,
        accounts.all_account_count_in_accounts_file(shrink_slot)
    );

    // Only, try to shrink stale slots, nothing happens because shrink ratio
    // is not small enough to do a shrink
    // Note this shrink ratio had to change because we are WAY over-allocating append vecs when we flush the write cache at the moment.
    accounts.shrink_ratio = AccountShrinkThreshold::TotalSpace { shrink_ratio: 0.4 };
    accounts.shrink_candidate_slots(&EpochSchedule::default());
    assert_eq!(
        pubkey_count,
        accounts.all_account_count_in_accounts_file(shrink_slot)
    );

    // Now, do full-shrink.
    accounts.shrink_all_slots(false, None);
    assert_eq!(
        pubkey_count_after_shrink,
        accounts.all_account_count_in_accounts_file(shrink_slot)
    );
}
