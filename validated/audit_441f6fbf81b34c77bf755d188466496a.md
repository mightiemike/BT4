## Analysis

The reported Radiant/MultiFeeDistribution issue is a classic "attacker inflates a storage array across many cheap transactions, then a later single operation iterates the whole array and runs out of gas" bug. I found a structurally identical pattern in Push Chain's inbound voting/finalization path.

### Title
Unbounded full-collection `PendingInbounds.Walk` on every inbound ballot finalization enables dust-inbound gas-griefing DoS - ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
`afterInboundBallotTerminal` (invoked as the `BallotHooks.AfterBallotTerminal` callback every time *any* inbound ballot reaches a terminal state) performs an **unbounded `Walk` over the entire `PendingInbounds` collection** to locate the entry owning the just-finalized ballot ID, instead of doing a keyed lookup. An unprivileged external-chain user can cheaply create many small/garbage cross-chain deposit events that Universal Validators must faithfully observe and vote on, inflating `PendingInbounds` without bound. Because `PendingInbounds` entries persist until *all* their variant ballots reach a terminal state (pass/reject/expire), and expiry only occurs after `DefaultExpiryAfterBlocks`, an attacker can keep the collection large for an extended window. Each subsequent inbound-ballot finalization (a normal, honest-validator action) then pays an ever-growing linear-scan cost.

### Finding Description
`x/uexecutor/keeper/ballot_hooks.go` locates the `PendingInboundEntry` for a terminal ballot by scanning every entry in the collection: [1](#0-0) 

This is documented as intentional because "Ballot IDs are one-way canonical digests... and this hook only fires on terminal transitions," with the comment assuming "the pending set is small and transient" — the same false assumption the audited MultiFeeDistribution contract made about `userLocks`/`userEarnings`.

`PendingInbounds` entries are created on the *first* validator vote for any logical inbound event and are variant-aware — every unique `Inbound` payload byte-sequence becomes a separate `InboundVariant`: [2](#0-1) 

An inbound event is derived directly from a real deposit the attacker makes on any connected external chain (no minimum-amount enforcement is visible in the inbound flow), so the attacker fully controls how many distinct `PendingInboundEntry` keys exist at once — this is the direct analog of a user "creating a significant amount of locks." Entries are removed only once **all** variants of that entry reach a terminal ballot status: [3](#0-2) 

Every terminal transition anywhere in the system (this attacker's own dust deposits, or any other honest user's unrelated inbound finalizing) now re-scans the whole, attacker-inflated `PendingInbounds` set inside `VoteInbound`'s call chain (`VoteInbound` → `VoteOnInboundBallot` → `uvalidatorKeeper.VoteOnBallot` → `CheckIfFinalizingVote` → `MarkBallotFinalized` → `fireBallotTerminalHook` → `AfterBallotTerminal`): [4](#0-3) [5](#0-4) 

### Impact Explanation
Every `MsgVoteInbound` transaction that happens to finalize a ballot (from any honest Universal Validator, for any user's legitimate inbound) now incurs gas cost proportional to the total number of concurrently pending inbound entries across the whole chain, not just the attacker's own. As the attacker keeps submitting cheap dust deposits on any connected external chain faster than the `DefaultExpiryAfterBlocks` window clears them, this scan cost grows without bound. This can:
- push individual finalizing `MsgVoteInbound` transactions toward/over the block gas limit, causing them to fail or be unable to be included, which **stalls finalization of legitimate users' inbound bridging transactions** (their `UniversalTx` is never created and their deposited funds effectively can't progress) — a form of permanent-freezing/DoS reachable by an ordinary unprivileged external actor with no reliance on malicious validators.
- degrade consensus-critical vote processing chain-wide (this hook fires inside `VoteInbound`, a gasless, validator-submitted message), amplifying the effect across all Universal Validators simultaneously.

This matches the "denial of service... not network-level and reachable without privileged control" and "permanent freezing of user or protocol-controlled funds" allowed-impact categories.

### Likelihood Explanation
Medium. It requires an attacker to be willing to pay for many small deposit transactions on an external chain (cheap on most L2s/testnets) and does not require any privileged access, validator compromise, or malicious node behavior — only honest validators faithfully observing and voting on real (if trivial-value) deposits, exactly as intended by protocol design. The main constraint is the natural expiry of stale ballots, which bounds — but does not eliminate — the size the attacker can force the collection to reach, and it can be continuously refreshed by ongoing dust submissions.

### Recommendation
Replace the full-collection `Walk` in `afterInboundBallotTerminal` with a direct/keyed lookup. Since `RecordInboundVote` already knows the `utx_key` for a given `ballotID` at vote time, thread that key through the `AfterBallotTerminal` hook (or maintain a `ballotID -> utxKey` secondary index) instead of scanning the entire `PendingInbounds` collection on every terminal transition. Additionally, consider bounding `PendingInbounds` size (e.g., a minimum bridgeable amount per inbound, or a cap on concurrently tracked pending entries) to prevent dust-based inflation, mirroring the "restrict max array elements" / "minimum lockable amount" remediation applied to the original MultiFeeDistribution report.

### Proof of Concept
1. Attacker repeatedly sends minimal-value deposits to the gateway contract on any enabled external chain (e.g., 1 wei of a supported asset), each producing a distinct `tx_hash`/`log_index` pair.
2. Universal Validators observe and call `MsgVoteInbound` for each event; `RecordInboundVote` creates a new `PendingInboundEntry` per unique event, growing `PendingInbounds` linearly with the number of dust deposits.
3. Attacker sustains submission faster than `DefaultExpiryAfterBlocks` clears stale entries, keeping `PendingInbounds` large.
4. Any subsequent `MsgVoteInbound` that finalizes a ballot (attacker's own or another legitimate user's) triggers `afterInboundBallotTerminal`'s unfiltered `Walk` over the full, inflated `PendingInbounds` collection, consuming gas proportional to its size — observable as increasing gas usage/latency in vote-finalizing transactions as the collection grows, eventually risking transaction failure at the block gas limit.

func (k Keeper) MarkBallotFinalized(ctx context.Context, id string, status types.BallotStatus) error {
	if status != types.BallotStatus_BALLOT_STATUS_PASSED && status != types.BallotStatus_BALLOT_STATUS_REJECTED {
		return fmt.Errorf("invalid finalization status: %v", status)
	}

	ballot, err := k.Ballots.Get(ctx, id)
	if err != nil {
		return err
	}

	k.Logger().Debug("marking ballot as finalized",
		"ballot_id", id,
		"final_status", status.String(),
	)

	if err := k.ActiveBallotIDs.Remove(ctx, id); err != nil {
		return err
	}
	if err := k.FinalizedBallotIDs.Set(ctx, id); err != nil {
		return err
	}

	ballot.Status = status
	if err := k.Ballots.Set(ctx, id, ballot); err != nil {
		return err
	}

	k.fireBallotTerminalHook(ctx, ballot.Id, ballot.BallotType, status)
	return nil
}
