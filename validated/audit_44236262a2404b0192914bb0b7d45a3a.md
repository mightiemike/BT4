## Title
Precision loss from `double`-based fractional power (bancor formula) in `ExchangeProcessor` causes incorrect TRC10 exchange settlement - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The Numa `setMaxSpotOffsetBps` bug stems from computing a fractional operation (`Math.sqrt`) in a way that gets truncated to an integer, systematically skewing a price-scaling factor away from its intended value. Java-tron's legacy TRC10 bancor-relay `ExchangeProcessor` has the same root-cause pattern: it computes a fractional exponentiation (`Math.pow(x, 0.0005)` / `Math.pow(x, 2000.0)`) in IEEE-754 `double` and truncates the result to a `long` via `(long) issuedSupply` / `(long) exchangeBalance`, causing settlement amounts computed and accepted at rates that diverge from the exact bancor-curve result. This code path is directly reachable by any unprivileged user through `ExchangeTransactionActuator` / `ExchangeWithdrawActuator`, and is still the default path unless the chain-parameter-gated hardened path is enabled.

### Finding Description
`ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` implement the TRC10 relay-token bancor formula using `double` arithmetic and a fractional exponent, then truncate to `long`: [1](#0-0) [2](#0-1) 

This is functionally analogous to the Numa bug: instead of `Math.sqrt(x)` truncated to `uint160`, java-tron truncates a `Math.pow(x, fractionalExponent)` result to a `long`, and instead of `uint160` casting, it is `(long)` casting a `double`. Both patterns compute a mathematically fractional quantity that legitimately requires fixed/arbitrary precision, but instead rely on floating-point/integer truncation, causing systematic divergence between the intended exact exchange rate and the actual on-chain result.

The team has already acknowledged this precision-loss class internally: a `SafeExchangeProcessor` was added that recomputes the same formula using `BigDecimal` with 18-digit scale and `RoundingMode.HALF_UP`, explicitly to avoid the double-based precision loss: [3](#0-2) 

However, this safe path is only used when the `allowHardenExchangeCalculation` chain parameter is enabled, and dispatch between the two implementations happens in `ExchangeCapsule.transaction`: [4](#0-3) 

A dedicated regression test (`testStrictMath`) confirms that for real-world balance/quantity triples, the legacy `ExchangeProcessor` (double-based) and `SafeExchangeProcessor` (BigDecimal-based) produce **different** results: [5](#0-4) 

### Impact Explanation
This is reachable by any unprivileged user who trades against a TRC10 exchange pair via `ExchangeTransactionActuator.execute` (and `ExchangeWithdrawActuator` for the withdrawal-side computation), both of which call `exchangeCapsule.transaction(...)`, which internally invokes `ExchangeProcessor.exchange`: [6](#0-5) 

Because the settlement quantity (`anotherTokenQuant`) is computed via the imprecise double-power formula and directly credited/debited to account balances, unprivileged users receive/pay amounts that deviate from the exact bancor-curve value — this is a direct on-chain accounting/settlement divergence (funds are moved incorrectly), the same impact class described in the Numa report ("conversions... occur at inaccurate rates").

### Likelihood Explanation
`ExchangeTransactionActuator`/`ExchangeWithdrawActuator` are ordinary, permissionless, frequently-used TRC10 transaction types requiring no special privilege — any account with sufficient balance can trigger the mispriced calculation on every trade against a bancor-relay exchange pair. The precision-loss path (`ExchangeProcessor`, not `SafeExchangeProcessor`) is the default/legacy path unless the `allowHardenExchangeCalculation` chain parameter has been switched on via committee proposal; I was unable to fully confirm the current default value of that parameter (its exact getter/config are in `DynamicPropertiesStore.java` and `ProposalUtil.java`, which I did not have iterations left to inspect fully), so it is possible the parameter is already enabled on the live network — this should be verified before treating this as an actively unmitigated issue in production.

### Recommendation
Ensure the `SafeExchangeProcessor` (BigDecimal-based, higher-precision) path is the sole/default execution path for TRC10 bancor exchange calculations (i.e., confirm `allowHardenExchangeCalculation` is enabled network-wide, or remove the legacy double-based `ExchangeProcessor` entirely), consistent with how the Numa fix recommendation was to "increase the precision of the affected variables to avoid precision loss."

### Proof of Concept
The existing test `ExchangeProcessorTest.testStrictMath` in java-tron's own test suite is a working PoC demonstrating the divergence: for the same `(balance, balance, quant)` triples, the legacy double-based `ExchangeProcessor` and the BigDecimal-based `SafeExchangeProcessor` produce different settlement quantities: [5](#0-4) 

This is directly analogous to the Numa PoC, where the sqrt-truncated `maxSpotOffsetPlus1SqrtBps`/`maxSpotOffsetMinus1SqrtBps` produced different effective percentage changes than the intended ones.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
