### Title
Relayer fee transfer is dispatched unconditionally before the user's action is validated, letting a relayer collect payment for transactions that never execute - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In `inner_rlp_execute`, the Wallet Contract schedules the relayer's fee-refund transfer via `env::promise_batch_create` / `env::promise_batch_action_transfer` immediately upon successfully parsing an eth-emulated base-token or ERC-20 transfer, before the underlying action promise (`action_to_promise`) is even constructed and before its execution result is known.

### Finding Description
`inner_rlp_execute` parses the incoming RLP transaction and, for `EOABaseTokenTransfer` / `ERC20Transfer` kinds with a non-zero `fee`, immediately fires a transfer promise to the relayer (`predecessor_account_id`) at [1](#0-0) . This happens before the function proceeds to build the promise for the user's actual requested action via `action_to_promise` later in the same function [2](#0-1) .

`env::promise_batch_create`/`promise_batch_action_transfer` are host calls that queue an outgoing receipt unconditionally as soon as they are invoked — the resulting action is committed regardless of what the enclosing function later returns, as long as the function does not panic. If the subsequent `match transaction_kind { ... }` block or `action_to_promise` returns an `Err` (e.g. `Error::User(UserError::UnsupportedAction(...))` for an `AddKey` full-access-key action, or other user/parse errors surfaced later in the flow), `inner_rlp_execute` returns `Err(e)`, and `rlp_execute` converts that into a normal (non-panicking) `PromiseOrValue::Value(e.into())` [3](#0-2) . Because the function returns normally rather than panicking, the previously-scheduled fee-refund receipt to the relayer is **not rolled back** — it is confirmed and executed even though the user's intended action was never performed.

This is the structural analog of the `MerkleVesting.withdraw()` bug: a value-transferring operation (the relayer fee payment) is dispatched without any dependency on / validation of the success of the operation it is meant to compensate for, so a failure downstream does not undo or gate the transfer.

### Impact Explanation
A relayer (or a user acting as their own relayer for a self-submitted eth-emulated transaction) can craft an RLP-encoded transaction whose `TransactionKind` matches `EOABaseTokenTransfer`/`ERC20Transfer` with a non-zero `fee`, but whose actual action later fails to convert into a promise (e.g. an unsupported action variant reached through this code path, or any future error branch added between the fee dispatch and the final promise construction). The relayer immediately receives the fee, funded from the wallet-contract account's own balance, while the user's transaction is never executed. This is unauthorized value movement out of the wallet-contract account: NEAR tokens are transferred to the relayer without the corresponding service being rendered, and the wallet owner has no way to prevent or reverse it since the transfer receipt is already committed by the time the error is returned.

### Likelihood Explanation
The likelihood depends on whether a reachable `Err` path exists strictly after the fee-dispatch code and the nonce increment but is returned without a panic. In the reviewed code, the fee dispatch happens after nonce increment and inside the `Ok` parse branch, and the immediately-following code (the `match transaction_kind` building the final promise) can still return `Err` via `action_to_promise`'s `?` for `AddKey` with `FullAccessKey` permission, or via any new/unhandled variant added to `action_to_promise` in the future for these transaction kinds. Today the specific `EOABaseTokenTransfer`/`ERC20Transfer` kinds mostly map to `Transfer`/`FunctionCall` actions which do not themselves error in `action_to_promise`, so an attacker's practical trigger surface may currently be narrow; however, the ordering itself is fragile — any future error branch (parsing edge case, gas/format validation, or added action kind) reintroduces an exploitable free-fee condition without needing an audit of the transfer logic again, because the underlying host-call ordering makes the payment unconditional by construction, not by explicit success/failure gating.

### Recommendation
Do not dispatch the relayer fee transfer via an independent `promise_batch_create` call ahead of constructing the main action promise. Instead, chain the fee-refund transfer as part of the same promise (e.g., via `.then()`/batch actions on the already-successfully-constructed action promise, or move the fee dispatch to occur only after `action_to_promise` has returned `Ok`), so that any error which aborts building the user's action also prevents the fee transfer from being scheduled. Alternatively, only build and queue the fee-refund promise once the full promise chain (including the `action_to_promise(...)?` call) has been assembled without error, mirroring the pattern already used for the "call the registrar contract" flow, which correctly defers the nonce increment/fee decision to `address_check_callback` after the async result is known.

2. Ensure the parsed `action`/`transaction_kind` combination causes the subsequent `match transaction_kind { ... }` block (lines 412-472) or `action_to_promise` (lines 475-501) to return `Err(...)` on this call — e.g., by using an `AddKey` action requesting a full-access key, which triggers `Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))` at [5](#0-4) , assuming it can be reached through one of the fee-eligible transaction kinds (this requires confirming which `TransactionKind`s can carry an `AddKey`-mapped `near_action::Action`; this part of the parsing (`internal::parse_rlp_tx_to_action`) was not fully inspected and would need to be verified in a live session).
3. Submit the transaction via `rlp_execute` as the relayer. Observe that the relayer's account balance increases by `fee` (the transfer receipt created at line 382-383 is confirmed on-chain), while the `ExecuteResponse` returned to the caller reports `success: false` and the user's requested action never took effect.
4. Compare wallet-contract account balance before/after: it decreases by `fee` with no corresponding effect performed, demonstrating unauthorized value movement.
