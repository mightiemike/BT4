### Title
Unbounded, unpaginated `ExchangeStore.getAllExchanges()` causes O(n log n) CPU cost per `ListExchanges` RPC/HTTP call, scaling with attacker-created state - ([File: chainbase/src/main/java/org/tron/core/store/ExchangeStore.java])

### Finding Description
`ExchangeStore.getAllExchanges()` streams the entire `Exchange` column family, maps every entry, and sorts the whole collection with a `Comparator` on every single invocation, with no page size, cursor, or upper bound: [1](#0-0) 

This is reachable from unauthenticated clients via `ListExchangesServlet.doPost/doGet` → `wallet.getExchangeList()` → `ExchangeStore.getAllExchanges()`, and similarly via the gRPC `listExchanges` RPC and the Solidity/PBFT node mirrors: [2](#0-1) 

The only gate on this endpoint is `RateLimiterServlet`, which throttles request *rate*, not per-request *cost* — it does not account for the size of the dataset being scanned/sorted, so it cannot mitigate a large `n`. There is no bandwidth/energy metering on query endpoints (by design, queries are free reads), and there is no cap on the number of `Exchange` records that can exist.

New `Exchange` records are created via `ExchangeCreateActuator.execute`, one record per `ExchangeCreateContract` transaction, each gated only by `calcFee()` = `dynamicStore.getExchangeCreateFee()` (a chain-configurable, proposal-settable fee) plus the requirement that the account holds enough of both tokens being exchanged: [3](#0-2) [4](#0-3) 

No actuator-level cap exists on the total number of exchanges (`getLatestExchangeNum()` only increments a counter used as an ID), so an attacker who is willing to pay `N × exchangeCreateFee` can inflate the `Exchange`/`ExchangeV2` stores to arbitrary size, permanently degrading every full node's `ListExchanges` response time and CPU usage, since the created records are never pruned.

### Impact Explanation
This is a "DoS via RPC-API" class issue: an attacker-controlled amount of on-chain state (`Exchange` records) directly drives unbounded CPU work (stream + O(n log n) sort) on every call to a public, unauthenticated read endpoint (`ListExchanges` HTTP/gRPC/Solidity/PBFT variants). Because the created records persist forever in the store, this is not a transient load but a **permanent** degradation of the endpoint for all nodes that replicate the chain state, and repeated concurrent calls can be used to amplify CPU/latency impact well beyond what `RateLimiterServlet`'s per-IP rate limiting is designed to bound (it limits request frequency, not per-request computational cost).

### Likelihood Explanation
The precondition is non-trivial: creating N exchange records costs `N × exchangeCreateFee` in TRX (a chain-configurable, non-negligible fee burned/sent to the blackhole per `ExchangeCreateActuator.execute`), plus the attacker must hold matching balances of the two tokens for each exchange (satisfiable using TRX on both sides via `TRX_SYMBOL_BYTES` handling). This makes populating tens of thousands of records economically costly but not infeasible for a well-funded attacker, and it is a **one-time** cost that yields a **permanent** amplification factor for subsequent free reads via `ListExchanges`. No signature/permission bypass is needed — this is achievable by any ordinary funded account. I could not fully verify the exact numeric default of `getExchangeCreateFee()` from the available index (only its usage sites were found), so the precise attacker cost-per-record is uncertain; this affects the practicality (cheap vs. expensive) but not the existence of the underlying unbounded-scan/sort design flaw.

### Recommendation
- Add pagination/limit parameters to `ExchangeStore.getAllExchanges()` (and the `ListExchanges*` servlets/RPCs) similar to other list endpoints that already support offset/limit.
- Avoid sorting the full dataset on every request; either maintain a sorted index incrementally or sort only the requested page.
- Consider capping the maximum number of live `Exchange` records or charging a fee that scales with total exchange count to prevent unbounded state growth.

  }
