### Title
Non-deterministic OsRng-based state-diff encryption keys break Starknet OS output determinism — ([File: crates/starknet_os/src/hints/hint_implementation/output.rs])

### Summary
`calculate_keys_using_sha256_hash` (invoked via the `GenerateKeysUsingSha256Hash` hint in `encrypt.cairo`) seeds the committee `symmetric_key` and `sn_private_keys` using `rand::rngs::OsRng`, a true non-deterministic entropy source, rather than a value derivable deterministically from block/state data alone. [2](#0-1) 

### Finding Description
When `use_kzg_da` DA compression with a committee (`n_keys != 0`) is active, `process_data_availability` calls `encrypt_state_diff`, which triggers the `GenerateKeysUsingSha256Hash` hint. [3](#0-2) 
That hint fills 32 random bytes from `OsRng` and hashes them together with the compressed state diff to derive `symmetric_key` and `sn_private_keys`. [4](#0-3) 
Because `OsRng` output is not reproducible, two independent, honest executions of the Starknet OS over the identical block (e.g., a sequencer producing the block versus a validator/prover re-executing the OS for verification, or two provers computing the same block for redundancy) will derive different `symmetric_key`/`sn_private_keys`, hence different `sn_public_keys`, different `encrypted_symmetric_key`, and a different `ciphertext` for the DA segment. This entire encrypted segment is copied verbatim into the OS output via `serialize_data_availability`, which is the program output that feeds the block's data-availability commitment. [5](#0-4) 
This directly contradicts the codebase's own stated invariant that OS/consensus-relevant randomness must be deterministic — as seen in the parallel `RandomEcPoint` hint, which is explicitly overridden to use a *seeded* RNG "to make the output deterministic," with an explicit TODO noting "the aggregator should not use randomness." [6](#0-5) 
Unlike that hint, `calculate_keys_using_sha256_hash` was not given a deterministic/seeded source.

### Impact Explanation
Any block that is settled with `use_kzg_da=true` and a non-empty committee (public keys configured) is affected — this path is reached for every ordinary user transaction included in such a block, without any attacker action being required beyond having a transaction land in an affected block. Non-deterministic OS output for this DA segment means:
- Two honest re-executions/proofs of the same block (e.g., by different provers, or a validator replaying the OS to check the sequencer's claimed output) will not agree on the encrypted DA bytes, producing different program outputs/commitments for what should be the same block.
- This can manifest as honest-node divergence on the committed KZG/DA blob content and can prevent independent verification or proof aggregation of the block from succeeding, i.e., a network unable to confirm/finalize the affected blocks.

### Likelihood Explanation
This triggers deterministically whenever the feature is enabled (`use_kzg_da` + non-empty committee), which is a normal, non-adversarial configuration exercised in this codebase's own test matrix (`test_encrypted_state_diff_use_kzg_da_true_full_output_*_private_keys_*` hint-coverage fixtures), meaning it is not a rare edge case but a standing property of every block produced under this configuration.

### Recommendation
Replace the `OsRng`-derived randomness in `calculate_keys_using_sha256_hash` with a value deterministically derivable by all executors from data already committed to/verifiable within the block (e.g., derive the seed purely from the compressed state diff, the block hash/number, and other in-block/state values), removing the `OsRng.fill_bytes` call entirely, mirroring the deterministic approach already used for `RandomEcPoint`.

### Proof of Concept
1. Configure a chain to run with `use_kzg_da = true` and a non-empty committee `public_keys` list (the standard privacy/committee DA flow).
2. Run the Starknet OS over a given block state diff twice, independently, in two separate processes/provers (or once as "sequencer" and once as "validator re-execution").
3. Observe: `symmetric_key`, `sn_private_keys`, `sn_public_keys`, `encrypted_symmetric_key`, and the final ciphertext (`encrypted_start..encrypted_end`) segment differ between the two runs, because each invocation of `calculate_keys_using_sha256_hash` draws fresh bytes from `OsRng`. [2](#0-1) 
4. Since this segment is serialized verbatim into the OS's committed output, the two runs produce different program outputs for the identical logical block, demonstrating the divergence.

```rust
pub(crate) fn calculate_keys_using_sha256_hash(mut ctx: HintContext<'_>) -> OsHintResult {
    // Generate a cryptographically secure random seed.
    let mut random_bytes = [0u8; 32];
    OsRng.fill_bytes(&mut random_bytes);

    let mut hasher = Sha256::new();
    hasher.update(random_bytes);

    // In addition, hash the compressed state diff for extra defense against potential attacks on
    // randomness source.
    let compressed_start = ctx.get_ptr(Ids::CompressedStart)?;
    let compressed_end = ctx.get_ptr(Ids::CompressedEnd)?;
    let array_size = (compressed_end - compressed_start)?;
    for i in 0..array_size {
        let felt = ctx.vm.get_integer((compressed_start + i)?)?;
        hasher.update(felt.to_bytes_be());
    }
    let random_key_seed = hasher.finalize().to_vec();

    const SYM_LABEL: &[u8] = b"SYM"; // domain separation: symmetric key
    const PRIV_LABEL: &[u8] = b"PRIV"; // domain separation: private keys

    // Derive the symmetric key (full 32 bytes):
    let symmetric_key = {
        let hash = Sha256::new().chain_update(&random_key_seed).chain_update(SYM_LABEL).finalize();
        Felt::from_bytes_be(&hash.into())
    };
```
