Based on my investigation, I did not find a component in java-tron that structurally mirrors Morpho's `wExp(x)` (a fixed-point exponential with an explicit upper-bound `require()` check whose bound is too loose). However, I did find a closely related bug class — **silent numeric overflow/precision corruption in an exponential pricing function used for on-chain asset accounting**, in the legacy `ExchangeProcessor` bonding-curve math, which is the closest reachable analog.

### Title
Unchecked exponential (`Math.pow`) computation in legacy `ExchangeProcessor` can silently corrupt exchange/account balances via double-precision overflow - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute a bancor-style bonding-curve formula using `Math.pow` (via `Maths.pow`) on `double` values with no bound/overflow checks, then narrow the result to a `long` with a raw `(long)` cast [1](#0-0) . This is the same bug class as the reported `wExp` issue: an exponential-like computation whose input/output range is not properly bounded, so instead of reverting on out-of-range input it silently returns an incorrect (wrapped/saturated/garbage) value that then gets committed to state.

### Finding Description
`ExchangeProcessor.exchange()` is the default/legacy code path for TRX↔TRC10 token exchange math, computing token quantities using `1.0 + quant/newBalance` raised to a fractional power via `StrictMath.pow`/`Math.pow` [2](#0-1) . There is no validation that intermediate `double` results stay within representable `long` range before the `(long) issuedSupply` / `(long) exchangeBalance` cast is performed [3](#0-2) . When a `double` value exceeds `Long.MAX_VALUE`/`Long.MIN_VALUE`, or becomes `NaN`/`Infinity`, casting to `long` in Java does not throw — it silently saturates or truncates, exactly analogous to `wExp` overflowing without reverting.

The project itself acknowledges this exact issue class: a hardened replacement, `SafeExchangeProcessor`, was introduced that uses `BigDecimal` and `StrictMathWrapper.addExact`/`subtractExact` specifically to detect overflow and throw `ArithmeticException` instead of silently continuing [4](#0-3) . Tests directly demonstrate the divergence: `ExchangeProcessorTest.testStrictMath` shows the strict (`useStrictMath=true`) and hardened processors can even disagree, and there is a test explicitly named `hardenedExecuteOverflowThrowsArithmeticException` confirming the corrupted-pool/overflow scenario is a known, reproducible condition when the legacy path is used [5](#0-4) .

Which processor is used is controlled by `allowHarden()`/`dynamicStore.allowHardenExchangeCalculation()`, selected per-call in `ExchangeCapsule.transaction` [6](#0-5) , and invoked from `ExchangeTransactionActuator.execute`/`doValidate` on every user-submitted `ExchangeTransactionContract` [7](#0-6) .

### Impact Explanation
If the hardening flag is not enabled (e.g., pre-upgrade chains, or chains where this maintenance-hard-fork flag has not been activated by super representatives), any account can submit an `ExchangeTransactionContract` (or `ExchangeInject`/`ExchangeCreate`) that drives the legacy `double`-based bonding curve into an overflow region, producing a silently wrong (potentially negative, zero, or wildly inflated) `anotherTokenQuant`. That value is then used directly to credit/debit account balances and exchange pool balances [8](#0-7) , which can corrupt TRX/TRC10 accounting (asset creation from nothing, or draining an exchange pool) — a direct asset/accounting corruption impact.

### Likelihood Explanation
Reachability is confirmed: it is triggered by an ordinary, unprivileged broadcast transaction (`ExchangeTransactionContract`) with attacker-chosen `quant`/pool balances near boundary conditions, no special permissions required. Likelihood is gated entirely on whether `allowHardenExchangeCalculation` is active on the target network; I could not confirm the current default/activation state of that flag from available context, so this should be validated against the live chain parameters before treating it as currently exploitable.

### Recommendation
Make `SafeExchangeProcessor` (or an equivalent overflow-checked implementation) the unconditional path for exchange math rather than a flag-gated hardening option, or add explicit pre-condition bound checks (mirroring the `wExp` fix approach: derive and enforce the maximum safe input from the known `Long`/`double` representable range before calling `Math.pow`) in `ExchangeProcessor` itself so out-of-range inputs revert with `ContractValidateException`/`ArithmeticException` instead of silently producing a wrapped value.

### Proof of Concept
Conceptually mirrors the report's `testWExpSpecial`: using `ExchangeProcessorTest`-style setup, seed an `ExchangeCapsule` pool with balances/`sellTokenQuant` chosen so that `1.0 + quant/newBalance` raised to `2000.0` (in `exchangeFromSupply`) or a similarly large exponent drives the double result beyond `Long.MAX_VALUE`; observe that `ExchangeProcessor.exchange()` returns a truncated/negative value while `SafeExchangeProcessor.exchange()` throws `ArithmeticException` for the same inputs, as already demonstrated by `testHardenedOverflowDetection`/`testSafeProcessorAddExactOverflowThrows` [9](#0-8) .

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Test
  public void testHardenedLargeQuant() {
    long sellBalance = 1_000_000_000_000L;
    long buyBalance = 1_000_000_000_000L;
    long sellQuant = 1_000_000_000_000L; // 100% of sell balance

    long result = SafeExchangeProcessor.INSTANCE.exchange(sellBalance, buyBalance, sellQuant);
    Assert.assertTrue("Result must be positive for large quant", result > 0);
