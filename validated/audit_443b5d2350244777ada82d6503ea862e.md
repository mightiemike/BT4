### Title
Unauthenticated `batchProver_setCommitments` RPC allows forged sequencer commitments to be injected into a batch prover's pending-proof pipeline - (File: crates/batch-prover/src/rpc.rs)

### Summary
`BatchProverRpcServerImpl::set_commitments` in `crates/batch-prover/src/rpc.rs` writes an attacker-supplied `SequencerCommitment` (merkle_root, index, l2_end_block_number) directly into `ledger_db` with no signature or DA-inclusion check. The RPC authentication middleware `Auth` in `crates/common/src/rpc/auth.rs` only gates `backup_create`, `backup_validate`, `backup_info` via `PROTECTED_METHODS`, so `batchProver_setCommitments` passes through unauthenticated even when no API key is configured.

### Finding Description
The binding that should hold is: `ledger_db.get_commitment_by_index(i).merkle_root == SequencerCommitment::serialize_and_calculate_sha_256(inscription)` for an inscription with `blob.sender() == sequencer_da_public_key`, i.e. every commitment record used by the prover must have been produced by observing an actual sequencer-signed `DataOnDa::SequencerCommitment` on Bitcoin.

`set_commitments` breaks this binding directly: it takes attacker-controlled `Vec<SequencerCommitmentRpcParam>`, constructs a `SequencerCommitment` from raw fields with zero validation against any DA inscription, and unconditionally calls: [1](#0-0) 

The docstring itself warns "It overrides the commitment already if exists, so use with caution" — confirming it is meant as a privileged/manual operator tool, not a public endpoint: [2](#0-1) 

The only gate for RPC methods is the `Auth` middleware, whose `PROTECTED_METHODS` list does not include `setCommitments` (namespaced as `batchProver_setCommitments`): [3](#0-2) 

Since the method name isn't in `PROTECTED_METHODS`, the middleware immediately forwards the call to the underlying service without ever checking `api_key`, regardless of whether one is configured. This means an unprivileged network attacker who can reach the batch prover's RPC bind address can call `batchProver_setCommitments` and have their forged commitment stored via `put_commitment_by_index`, `put_commitment_index_by_l1`, and `put_prover_pending_commitment`. This poisoned commitment is later fed as ground truth into `create_circuit_input` (line 549-559, reads via `get_commitment_by_range`) and ultimately `submit_fake_proof`/proving pipeline, which build a `BatchProofCircuitOutput` embedding `sequencer_commitment_hashes` derived from the forged record.

### Impact Explanation
This corrupts only the local, node-specific `ledger_db` of the batch prover that is exposed with a reachable RPC and no API key — it does not by itself change consensus-verified state. A real proof built over the forged commitment would still need to pass STF execution against actual L2 blocks (`create_circuit_input`/`prove` execute real state transitions keyed by `l2_end_block_number`), and any submitted batch proof is ultimately checked against DA-observed sequencer commitments elsewhere in the pipeline (e.g., `sov-modules-stf-blueprint`/light-client-prover code referencing `sequencer_commitment_hashes`), which is the layer that would need to accept a mismatched commitment for actual chain-level impact (minted funds, false state root, or fork split). I could not fully trace that downstream verification path (`verify_batch_proof_seq_comm_relation` in `crates/sovereign-sdk/module-system/sov-modules-stf-blueprint/src/lib.rs` and `crates/light-client-prover/src/circuit/mod.rs`) within the available iterations to confirm whether a forged commitment surviving `create_circuit_input`/`prove` could produce a proof that would actually be accepted by light-client provers or other honest nodes. Absent that confirmation, the demonstrated impact is limited to: an unauthenticated attacker mutating a batch prover node's local ledger state and disrupting/misdirecting its own proving pipeline (denial-of-service / operational corruption of that single node), which falls under "unauthenticated JSON-RPC call that mutates node state" — a High-severity class per the rules, not the Critical "accepted forged commitment" class, since there is no demonstrated path to that forged commitment being accepted as valid by the wider protocol (light client prover, other batch provers, or the DA-verification logic that binds commitments to `sequencer_da_public_key`).

### Likelihood Explanation
Preconditions match the documented default: `rpc_config.api_key = None` and the batch prover's RPC bind host reachable by the attacker. No BTC cost, DA key, or special privilege is required — a single unauthenticated JSON-RPC POST suffices, and it is fully repeatable per commitment index/block.

### Recommendation
Add `setCommitments` (and other state-mutating/manual-override RPC methods) to `Auth::PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs` so they require an API key, and/or have `set_commitments` validate the supplied commitment against an actual DA inscription (verify `merkle_root` against `serialize_and_calculate_sha_256` of a real `DataOnDa::SequencerCommitment` blob whose `sender() == sequencer_da_public_key`) before persisting it, rather than trusting caller-supplied fields unconditionally.

    async fn set_commitments(
        &self,
        commitments: Vec<SequencerCommitmentRpcParam>,
    ) -> RpcResult<()> {
        for commitment in commitments {
            let l1_height = commitment.l1_height.to::<u64>();
            let commitment = SequencerCommitment {
                merkle_root: commitment.merkle_root,
                index: commitment.index.to::<u32>(),
                l2_end_block_number: commitment.l2_end_block_number.to::<u64>(),
            };

            info!(
                "Overriding sequencer commitment, index={} merkle_root={} l2_end_height={} l1_height={}",
                commitment.index,
                hex::encode(commitment.merkle_root),
                commitment.l2_end_block_number,
                l1_height,
            );

            self.context
                .ledger_db
                .put_commitment_by_index(&commitment)
                .map_err(internal_rpc_error)?;
            // This might cause some duplicate commitment indices appear in l1 -> index table which is ok
            self.context
                .ledger_db
                .put_commitment_index_by_l1(SlotNumber(l1_height), commitment.index)
                .map_err(internal_rpc_error)?;
            self.context
                .ledger_db
                .put_prover_pending_commitment(commitment.index)
                .map_err(internal_rpc_error)?;
        }

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }
