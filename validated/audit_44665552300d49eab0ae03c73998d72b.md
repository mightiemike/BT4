### Title
CANCELALLUNFREEZEV2 TVM opcode bypasses the committee-controlled `ALLOW_CANCEL_ALL_UNFREEZE_V2` gate enforced by the transaction-type Actuator - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/CancelAllUnfreezeV2Processor.java])

### Summary
`CancelAllUnfreezeV2Actuator.validate()` (used for direct `CancelAllUnfreezeV2Contract` broadcast transactions) explicitly refuses to run unless the committee has approved `ALLOW_CANCEL_ALL_UNFREEZE_V2` via `dynamicStore.supportAllowCancelAllUnfreezeV2()`. The TVM-opcode path that performs the identical state mutation (`CANCELALLUNFREEZEV2` / `cancelAllUnfreezeV2()` in a smart contract) is gated in `OperationRegistry` only by `VMConfig.allowTvmFreezeV2`, which is populated from `ds.supportUnfreezeDelay()` — a different, weaker flag — and `CancelAllUnfreezeV2Processor.validate()` performs no feature-flag check at all.

### Finding Description
- `CancelAllUnfreezeV2Actuator.validate()` requires `dynamicStore.supportAllowCancelAllUnfreezeV2()` to be true, throwing `"Not support CancelAllUnfreezeV2 transaction, need to be opened by the committee"` otherwise. [1](#0-0) 
- The opcode `Op.CANCELALLUNFREEZEV2` is registered in `OperationRegistry.appendFreezeV2Operations`, guarded by the `BooleanSupplier proposal = VMConfig::allowTvmFreezeV2` — the same proposal flag used to gate `FREEZEBALANCEV2`, `UNFREEZEBALANCEV2`, and `WITHDRAWEXPIREUNFREEZE`, not a flag specific to cancel-all-unfreeze. [2](#0-1) 
- `ConfigLoader.load()` sets `snapshot.allowTvmFreezeV2 = ds.supportUnfreezeDelay();` — i.e. the opcode gate tracks the `UNFREEZE_DELAY_DAYS` proposal, not `ALLOW_CANCEL_ALL_UNFREEZE_V2`. [3](#0-2) 
- `ProposalUtil.validator` confirms these are two distinct, independently-approvable committee proposals: `ALLOW_CANCEL_ALL_UNFREEZE_V2` merely requires `UNFREEZE_DELAY_DAYS` to already be non-zero as a *precondition*, it is not the same flag and is not implied by it. [4](#0-3) 
- `CancelAllUnfreezeV2Processor.validate()` (the native-contract logic actually executed by the opcode via `Program.cancelAllUnfreezeV2Action()`) only checks that the repo/store exists, the address is valid, and the account exists — it never checks `supportAllowCancelAllUnfreezeV2()` or any equivalent flag. [5](#0-4) 

Exploit flow: if a chain has approved `UNFREEZE_DELAY_DAYS` (which is required to unlock ordinary Freeze V2 opcodes: freeze/unfreeze/withdraw-expire-unfreeze) but has **not yet** separately approved `ALLOW_CANCEL_ALL_UNFREEZE_V2`, any unprivileged account can deploy or call a smart contract that invokes the `cancelAllUnfreezeV2()` TVM builtin. `OperationRegistry` will permit dispatch because `allowTvmFreezeV2` (== `supportUnfreezeDelay()`) is true, and `CancelAllUnfreezeV2Processor` performs the state mutation (clears the account's `unfrozenV2` list, re-freezes non-expired entries, credits expired balances back) unconditionally, with no committee-gate check. The same action attempted via a direct `CancelAllUnfreezeV2Contract` transaction through `CancelAllUnfreezeV2Actuator` would be correctly rejected in this exact state.

### Impact Explanation
This lets any unprivileged account or contract caller execute a resource/asset-affecting operation (`cancelAllUnfreezeV2`, which mutates frozen/unfrozen balances, total resource weights, and account balance) before the committee has authorized that specific feature, bypassing an intended governance control. This maps to an "unauthorized state change" impact class rather than a strict consensus/fork-split (all synchronized nodes evaluate the same `DynamicPropertiesStore` flags deterministically for a given block, so this does not by itself cause chain divergence between up-to-date and stale nodes — the mismatch is between two different in-protocol entry points, not between differing node software versions).

### Likelihood Explanation
Exploitability depends entirely on the chain's proposal history: it requires a state where `UNFREEZE_DELAY_DAYS > 0` but `ALLOW_CANCEL_ALL_UNFREEZE_V2` has not yet been separately approved by the committee. Whether such a window currently exists on TRON mainnet cannot be confirmed from the code alone (governance proposal history is off-repo, out of scope for this index), but the code path itself is a latent, reproducible bug on any chain configuration (testnet, private chain, or a future/past window on mainnet) where the two proposals are approved out of the assumed lock-step order. No special privileges, keys, or non-default node config are needed — only a normal funded account able to deploy/call a contract using the `CANCELALLUNFREEZEV2` opcode.

### Recommendation
Add an explicit `dynamicStore.supportAllowCancelAllUnfreezeV2()` (or equivalent) check inside `CancelAllUnfreezeV2Processor.validate()`, and/or change the `OperationRegistry.appendFreezeV2Operations` proposal supplier for `Op.CANCELALLUNFREEZEV2` from `VMConfig::allowTvmFreezeV2` to a dedicated supplier backed by `ALLOW_CANCEL_ALL_UNFREEZE_V2`, so both entry points (direct transaction and TVM opcode) enforce identical governance gating.

### Proof of Concept
```java
// JUnit-style PoC targeting CancelAllUnfreezeV2Processor directly (native path),
// demonstrating it executes with NO feature-flag check, unlike the Actuator.

@Test
public void testProcessorBypassesCommitteeGate() throws Exception {
  // Simulate a chain state where UNFREEZE_DELAY_DAYS is approved
  // but ALLOW_CANCEL_ALL_UNFREEZE_V2 is NOT approved.
  dbManager.getDynamicPropertiesStore().saveUnfreezeDelayDays(1L);      // supportUnfreezeDelay() == true
  dbManager.getDynamicPropertiesStore().saveAllowCancelAllUnfreezeV2(0); // NOT approved

  // 1) Direct transaction path correctly rejects:
  CancelAllUnfreezeV2Actuator actuator = new CancelAllUnfreezeV2Actuator();
  actuator.setChainBaseManager(dbManager.getChainBaseManager())
      .setAny(getCancelAllUnfreezeV2Contract());
  assertThrows(
      "Not support CancelAllUnfreezeV2 transaction, need to be opened by the committee",
      ContractValidateException.class, actuator::validate);

  // 2) Native/TVM opcode path (as invoked by Op.CANCELALLUNFREEZEV2 via
  //    OperationRegistry, gated only by VMConfig.allowTvmFreezeV2 == supportUnfreezeDelay()):
  CancelAllUnfreezeV2Param param = new CancelAllUnfreezeV2Param();
  param.setOwnerAddress(ownerAddress);
  CancelAllUnfreezeV2Processor processor = new CancelAllUnfreezeV2Processor();
  processor.validate(param, repository);       // does NOT throw - no committee-gate check
  processor.execute(param, repository);        // mutates account state despite gate being closed
}
```
Expected: step (1) throws `ContractValidateException`, while step (2) completes successfully and mutates state — proving the TVM native-contract path can execute the operation while the same operation via the direct contract-type transaction is blocked by the committee gate.

    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);

    byte[] ownerAddress = param.getOwnerAddress();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);

          ACCOUNT_EXCEPTION_STR + readableOwnerAddress + NOT_EXIST_STR);
