### Title
Division-before-multiplication precision loss in `MortgageService.payReward()` brokerage calculation - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payReward()` computes a witness's brokerage cut by first dividing the integer `brokerage` percentage by `100` (producing a `double`), then multiplying that ratio by `value`. This is the same division-before-multiplication ordering flagged in the D3Vault report, and it introduces avoidable floating-point truncation error into every block reward and transaction-fee reward payout, which then feeds `delegationStore.addReward()` and `adjustAllowance()`.

### Finding Description
The vulnerable code:
```java
private void payReward(byte[] witnessAddress, long value) {
  long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
  int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
  double brokerageRate = (double) brokerage / 100;
  long brokerageAmount = (long) (brokerageRate * value);
  value -= brokerageAmount;
  delegationStore.addReward(cycle, witnessAddress, value);
  adjustAllowance(witnessAddress, brokerageAmount);
}
``` [1](#0-0) 

`brokerage / 100` is performed first as a `double` division (introducing binary floating-point rounding for non-power-of-two percentages), and only then multiplied by `value` and truncated to `long` via `(long)` cast (which always truncates toward zero rather than rounding). This is precisely the "divide before multiply" anti-pattern from the external report: doing `a/b*c` instead of `a*c/b` compounds rounding error and loses precision that would otherwise be preserved by multiplying first.

This function is the sole payout path used for both block rewards and transaction-fee rewards: [2](#0-1) 
and it directly determines `brokerageAmount` (credited to the SR's `allowance` via `adjustAllowance`) versus `value` (credited to the voter-reward pool via `delegationStore.addReward`) — a state-splitting operation identical in nature to the `realDebt`/`totalBorrows` split in the reported bug.

Notably, elsewhere in this same codebase, analogous reward/limit computations (`RewardViCalService`, `DelegationStore.accumulateWitnessVi`, `VoteRewardUtil`, `ResourceProcessor`, `RepositoryImpl`) have all been hardened to use `BigInteger` multiply-then-divide to avoid exactly this class of precision loss: [3](#0-2) [4](#0-3) 
`MortgageService.payReward()` was not updated to this pattern and still uses the legacy double-based divide-then-multiply approach.

### Impact Explanation
Every block reward and transaction-fee reward payment to every Super Representative goes through `payReward()`. Because the brokerage split is computed by dividing first, the resulting `brokerageAmount` and the remaining voter-reward `value` are both systematically imprecise (truncated toward zero rather than accurately rounded), and small integer amounts multiplied by `double` ratios can silently drop fractional SUN. Over the lifetime of the chain, across every block (approximately every 3 seconds) and every SR, these small individual errors accumulate into a measurable and persistent misallocation between what is paid to the witness's own allowance versus what is distributed to voters via the reward pool — a real, ongoing state/accounting divergence rather than a one-off rounding artifact. This is core protocol state accounting, not privileged or mocked code — it executes automatically on every block for every account earning rewards.

### Likelihood Explanation
This is triggered unconditionally on every block production and every transaction-fee distribution cycle for all witnesses/SRs — no attacker action or privileged access is required. The precision loss is deterministic given any `brokerage` value that isn't a "clean" fraction of the reward amount (which is the common case), so it occurs continuously rather than being an edge case.

### Recommendation
Replace the double-based divide-then-multiply computation with an exact integer multiply-then-divide (using `Math.multiplyExact`/`BigInteger` to guard overflow), consistent with the hardened pattern already used elsewhere in the codebase (e.g., `ResourceProcessor.calculateGlobalLimitV2`, `RewardViCalService.getNewRewardAlgorithmReward`):
```java
long brokerageAmount = Math.multiplyExact(value, (long) brokerage) / 100;
```
or the `BigInteger` equivalent when overflow safety must be guaranteed for large `value`.

### Proof of Concept
Given `brokerage = 33` (33%) and `value = 7` (SUN):
- Current code: `brokerageRate = 33.0/100 = 0.33`; `brokerageAmount = (long)(0.33 * 7) = (long)2.31 = 2`.
- Correct multiply-first approach: `(7 * 33) / 100 = 231 / 100 = 2` — same result here, but for values where the double representation of `brokerage/100` is not exact (e.g., `brokerage = 1`, repeated over billions of blocks with varying `value`), the double rounding and truncation diverge from the precise integer computation, causing a persistent, non-recoverable drift between the SR's brokerage `allowance` and the voter `reward` pool recorded in `delegationStore`.
