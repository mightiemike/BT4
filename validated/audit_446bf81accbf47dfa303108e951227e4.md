### Title
Receipt Size Limit Bypass via Post-Validation `output_data_receivers` Mutation and `value_return` DataReceipt Overflow — (`runtime/runtime/src/lib.rs`)

### Summary

An unprivileged user can deploy a contract that causes the runtime to produce action receipts or data receipts whose serialized Borsh size exceeds `max_receipt_size` (4 MiB). The size check in `validate_receipt` runs in `NewReceipt` mode during per-action execution, but two post-validation code paths mutate the receipt or construct a new receipt without re-checking the total size. The resulting oversized receipts are forwarded across shards, violating the `ChunkStateWitness` size invariant and breaking the receipt size enforcement that the protocol depends on. The bug is acknowledged in the codebase as issue #12606 and has a live workaround in congestion control, confirming it is a real, reachable, unfixed invariant break.

### Finding Description

**Root cause path 1 — `promise_return` + `output_data_receivers` mutation:**

During `apply_action_receipt`, each action is executed and newly created receipts are validated with `validate_receipt(..., ValidateReceiptMode::NewReceipt)` at line ~871 of `runtime/runtime/src/lib.rs`. This check enforces `max_receipt_size`.

After the per-action loop completes, the runtime handles `output_data_receivers` at lines 1031–1049:

```rust
if !action_receipt.output_data_receivers().is_empty() {
    if let Ok(ReturnData::ReceiptIndex(receipt_index)) = result.result {
        // Modifying a new receipt instead of sending data
        match result.new_receipts.get_mut(receipt_index as usize)...receipt_mut() {
            ReceiptEnum::ActionV2(new_action_receipt) | ... => new_action_receipt
                .output_data_receivers
                .extend_from_slice(&action_receipt.output_data_receivers()),
        }
    }
}
```

A contract that calls `promise_return(C)` where receipt C was sized to exactly `max_receipt_size` will pass the `NewReceipt` size check. The runtime then appends `output_data_receivers` from the parent receipt to C, growing C beyond `max_receipt_size`. No re-validation occurs. The oversized receipt is forwarded directly via `receipt_sink.forward_or_buffer_receipt`.

**Root cause path 2 — `value_return` producing an oversized DataReceipt:**

`value_return` in `runtime/near-vm-runner/src/logic/logic.rs` checks only `max_length_returned_data` (also 4 MiB):

```rust
if num_bytes > self.config.limit_config.max_length_returned_data {
    return Err(HostError::ReturnedValueLengthExceeded { ... });
}
```

When the return value is exactly `max_length_returned_data` bytes and the parent receipt has `output_data_receivers`, the runtime wraps the value in a `DataReceipt` struct (adding `data_id: CryptoHash` = 32 bytes plus Borsh framing). The resulting `DataReceipt` exceeds `max_receipt_size`. `validate_data_receipt` only checks `max_length_returned_data`, not the total receipt wire size.

**Downstream handling confirms the bug is live:**

`ValidateReceiptMode::ExistingReceipt` explicitly skips the size check to tolerate these receipts:

```rust
/// 2) There is a bug which allows to create receipts that are above the size limit. Runtime has
///    to handle them gracefully until the receipt size limit bug is fixed.
///    See https://github.com/near/nearcore/issues/12606 for details.
ExistingReceipt,
```

The congestion control layer in `runtime/runtime/src/congestion_control.rs` has a live workaround that clamps oversized receipt sizes to avoid them getting stuck:

```rust
// There is a bug which allows to create receipts that are above the size limit.
// See https://github.com/near/nearcore/issues/12606
if size > max_receipt_size {
    size = max_receipt_size;
}
```

### Impact Explanation

The `max_receipt_size` limit exists to keep `ChunkStateWitness` under 17 MiB. Oversized receipts violate this invariant. Concretely:

- A receipt exceeding 4 MiB can be forwarded cross-shard, inflating `source_receipt_proofs` beyond `outgoing_receipts_big_size_limit` (4.5 MiB).
- The `ChunkStateWitness` size budget is broken, which can cause chunk validators to diverge from the chunk producer's result (execution flow breakage).
- The congestion control clamping workaround means the oversized receipt's true size is not counted against the outgoing size budget, allowing a single receipt to consume more bandwidth than the protocol intends.
- This is a non-network-level DoS: it is triggered by ordinary user-submitted transactions and contract calls, and could be fixed without a hardfork by re-validating receipt size after the `output_data_receivers` mutation.

### Likelihood Explanation

Any unprivileged user can deploy a contract (e.g., using the `generate_large_receipt` or `max_receipt_size_promise_return_method2` patterns already present in the test suite) and trigger this path. The test `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs` demonstrate the exact attack scenario and confirm that oversized receipts are produced and propagated on mainnet-equivalent configurations. No privileged access, validator control, or external system dependency is required.

### Recommendation

Re-validate the total Borsh-serialized receipt size **after** appending `output_data_receivers` at `runtime/runtime/src/lib.rs:1031–1049`, before forwarding the receipt. Similarly, when constructing a `DataReceipt` from a `value_return` result, check that `sizeof(DataReceipt envelope) + data.len()` does not exceed `max_receipt_size`. Both checks should return an `ActionError::NewReceiptValidationError(ReceiptSizeExceeded)` to the caller rather than silently producing an oversized receipt.
