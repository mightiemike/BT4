### Title
Unbounded, non-deduplicated session-ID array growth in `KVSessionStorage` causes DoS of shop session lookups used by the auth flow - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage` tracks all session IDs belonging to a shop in a single JSON array stored under the key `shop:<shop>`. Every call to `storeSession` unconditionally appends the session's id to that array with no duplicate check, and nothing ever prunes stale/duplicate entries except an explicit `deleteSession`/`deleteSessions` call. This mirrors the reported Curves.sol bug class: a per-tenant array that is grown by a routine, reachable, legitimate flow (token exchange / re-authentication) but never bounded or deduplicated, which is then iterated in full by a security-relevant lookup (`findSessionsByShop`).

### Finding Description
`storeSession` calls `addShopIds`, which reads the current array and blindly concatenates the new id(s), regardless of whether the id is already present: [1](#0-0) [2](#0-1) 

Compare this to the Redis adapter, which explicitly checks `if (!idKeysArray.includes(idKey))` before pushing [3](#0-2) . The KV adapter has no such guard, so the same session id can be appended repeatedly.

`storeSession` for the same (deterministic) session id is re-invoked by normal, unprivileged app usage: in the token-exchange flow, whenever a shop's stored offline (or per-user online) session is missing or close to expiry, `performTokenExchange` re-derives the *same* session id (`api.session.getOfflineId(shop)` / `api.session.getJwtSessionId(shop, sub)`) and calls `config.sessionStorage.storeSession(...)` again: [4](#0-3) 

Because `addShopIds` never checks for an existing entry, each such re-exchange (which happens repeatedly over the lifetime of an install — token expiry, App Bridge reloads, staff members generating distinct online sessions, or an attacker/merchant deliberately forcing re-exchanges by invalidating the token, e.g. via repeated 401 responses that trigger `invalidateAccessToken`) appends another copy of the id to the shop's tracking array in KV. The array is never garbage collected outside of explicit `deleteSession` calls, so it grows monotonically and without bound purely from reachable, unprivileged protocol usage — exactly the "array only grows" root cause described in the analog report.

The array is later fully materialized and iterated by `findSessionsByShop`: [5](#0-4) 

which is used by `AppInstallations.includes`/`delete` — functions invoked on installation checks and uninstall/GDPR flows: [6](#0-5) 

### Impact Explanation
As the tracked id array grows without bound: (1) `findSessionsByShop` performs a `Promise.all` KV `get` for every (duplicated) id in the array, which in a Cloudflare Workers KV environment is bounded by subrequest limits — once the array is large enough this call will throw or time out, breaking `AppInstallations.includes`/`delete`, i.e. a functional DoS of the install-check/auth path for that shop; (2) the `shop:<shop>` value itself keeps growing and can eventually approach Workers KV per-value size limits, at which point `storeSession`'s `addShopIds`/`removeShopIds` writes begin failing, breaking session persistence entirely for the shop. This denies service to a legitimate shop's authentication flow, matching the accepted "DoS of an auth handler" class.

### Likelihood Explanation
No privileged access is required — the growth is driven purely by the normal, unprivileged token-exchange re-authentication path that every embedded app using `KVSessionStorage` + token exchange goes through repeatedly over time, and can be accelerated by a single merchant/customer forcing repeated re-exchanges (e.g., triggering 401s to invalidate the stored access token, or having many staff members generate distinct online sessions). The bug is deterministic and always present in `KVSessionStorage`; the only variable is how long/how many cycles are needed to reach an impactful array size, which depends on KV/runtime limits.

### Recommendation
In `addShopIds`, deduplicate before writing (e.g., `[...new Set([...shopIds, ...ids])]`) as the Redis adapter already does. Additionally, consider pruning ids from the shop-tracking array whenever the corresponding session is found to be expired/inactive during `findSessionsByShop`, and/or capping array size, to prevent unbounded growth even under repeated legitimate re-exchange traffic.

### Proof of Concept
1. Configure an embedded app with `@shopify/shopify-app-session-storage-kv` and `future.tokenExchange` enabled.
2. As a normal merchant, let the offline/online session token repeatedly near/hit expiry (or force it by triggering a 401 so `invalidateAccessToken` clears the stored token) and reload the embedded app each time; each reload runs `performTokenExchange` → `config.sessionStorage.storeSession(offlineSession)` (and `onlineSession` if online tokens are used) with the same deterministic session id.
3. Observe that `KVSessionStorage.addShopIds` appends the id again on every cycle (`packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts:75-79`), so the `shop:<shop>` KV array grows by one entry per cycle indefinitely.
4. After enough cycles, call `findSessionsByShop(shop)` (e.g., via `AppInstallations.includes`) and observe degraded latency, subrequest-limit failures, or write failures once the KV value size limit is approached.

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    const sessionIds = await this.namespace.get<string[]>(
      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );
  }

    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));

  async includes(shopDomain: string): Promise<boolean> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      for (const session of shopSessions) {
        if (session.accessToken) return true;
      }
    }
    return false;
  }

  async delete(shopDomain: string): Promise<void> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      await this.sessionStorage.deleteSessions!(
        shopSessions.map((session: Session) => session.id),
      );
    }
  }
