### Title
Unbounded request body buffering in webhook/flow/fulfillment-service authentication handlers enables memory-exhaustion DoS - (`packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/flow/authenticate.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts`, and their `shopify-app-react-router` equivalents)

### Summary
In `shopify-app-remix` and `shopify-app-react-router`, the request-authentication handlers for webhooks, Flow extensions, and fulfillment-service callbacks all read the entire incoming HTTP request body into memory via `await request.text()` before performing any size check or HMAC validation. No maximum body-size limit is imposed anywhere in this code path, so an attacker can send an arbitrarily large POST body to these public endpoints and force the app server to buffer it fully in memory, exhausting available memory — the same bug class described in the external report (unbounded gRPC message-length limit leading to memory exhaustion), applied here to unbounded HTTP body buffering in a request-authentication handler.

### Finding Description
Each of the following authenticate factories accepts any POST request and immediately calls `request.text()` to materialize the full body as a string, prior to validating the Shopify HMAC signature or checking body size:

- `authenticateWebhookFactory` in `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts` (and the identical `shopify-app-react-router` version): `const rawBody = await request.text();` then passed to `api.webhooks.validate(...)`. [1](#0-0) 
- `authenticateFlowFactory` in `packages/apps/shopify-app-remix/src/server/authenticate/flow/authenticate.ts`: same unbounded `request.text()` call before `api.flow.validate(...)`. [2](#0-1) 
- `authenticateFulfillmentServiceFactory` in `packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts`: same pattern before `api.fulfillmentService.validate(...)`. [3](#0-2) 

Downstream, the core validation in `@shopify/shopify-api` (`validateHmacFromRequestFactory` / `validateFactory`) only rejects a request based on missing/invalid HMAC — it does not enforce any length limit on `rawBody` before hashing it. [4](#0-3) [5](#0-4) 

By contrast, `shopify-app-express` explicitly mitigates this by capping the body size before processing: `express.text({type: '*/*', limit: '500kb'})`. [6](#0-5) 

The `remix`/`react-router` handlers have no analogous limit — they rely entirely on the underlying HTTP server/runtime's default (which for many Node/edge runtimes is unbounded or very large), meaning the library itself does not enforce a safe default the way the report recommends ("a maximum ... message-length limit of a few megabytes").

### Impact Explanation
An anonymous, unauthenticated actor can send a POST request with an oversized body (e.g., hundreds of megabytes or larger, limited only by the runtime) to any of these public authentication endpoints (`/webhooks`, `/flow`, `/fulfillment_order_notification`, or the app-registered path). Because the body is read into memory in full before HMAC verification even starts, this constitutes a denial-of-service vector: repeated large requests can exhaust server memory, degrading or crashing the application for all merchants using the app — directly matching the "DoS of an auth handler" acceptance criterion.

### Likelihood Explanation
The webhook/flow/fulfillment-service authentication endpoints are, by design, publicly reachable POST endpoints (Shopify calls them without prior session establishment), so no privileged access or secret knowledge is required to trigger this. The only gating check before the unbounded read is `request.method !== 'POST'`, which any anonymous requester trivially satisfies. This makes exploitation straightforward for any external attacker who can reach the app's public URL.

### Recommendation
- Short term: Enforce a maximum request body size (e.g., a few hundred KB to a few MB, consistent with `shopify-app-express`'s `500kb` limit) in the `remix`/`react-router` webhook, flow, and fulfillment-service authenticate handlers before calling `request.text()`, rejecting oversized requests (e.g., HTTP 413) without buffering the full body.
- Longer term: Add a shared, configurable body-size limit inside `@shopify/shopify-api`'s `validateHmacFromRequestFactory`/`validate` code paths so all adapters (Express, Remix, React Router, Cloudflare Workers, etc.) get consistent protection by default, rather than depending on each adapter package to opt in individually.

### Proof of Concept
1. Deploy a `shopify-app-remix` (or `shopify-app-react-router`) app with a webhook route wired to `authenticate.webhook`.
2. Send `POST /webhooks` with a body of several hundred MB (or GB, depending on available runtime limits) and arbitrary/missing HMAC headers.
3. Observe that `authenticateWebhookFactory` calls `await request.text()` and buffers the entire payload into memory before the HMAC check in `api.webhooks.validate` rejects it — repeating this with concurrent large requests exhausts server memory, causing degraded performance or a crash, before any authentication/signature check has had a chance to reject the request cheaply.
