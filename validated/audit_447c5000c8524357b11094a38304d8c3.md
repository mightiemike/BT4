### Title
Deposit removed from `DepositDataMempool` even when its system transaction reverts and is excluded from the produced block - ([File: crates/sequencer/src/runner.rs])

### Summary
`CitreaSequencer::produce_l2_block_inner` fetches a snapshot of deposits with `fetch_deposits` and later calls `remove_deposits(&deposit_data)` on that same unfiltered snapshot after the block is saved. However, `process_sys_txs` explicitly reverts and *skips* (does not include in the produced block) any deposit whose system transaction fails with `EvmSystemTransactionNotSuccessful` - a case the code comments acknowledge happens ("deposits to non-EOA addresses can revert"). Because `remove_deposits` is not restricted to the deposits that were actually included, a skipped/reverted deposit is purged from the mempool exactly as if it had succeeded.

### Finding Description
The binding claimed is: `deposit present in accepted_deposit_txs cleared` == `deposit's system tx confirmed successful and included in the produced L2 block`.

Trace:
- `send_raw_deposit_transaction` (`crates/sequencer/src/rpc.rs:329-388`) simulates the deposit with `evm.get_call` against `BlockId::pending()` and, if it succeeds, calls `add_deposit_tx`, storing the raw deposit bytes in `accepted_deposit_txs` and marking its `calc_tx_id` in `pending_deposits` <cite repo="Thankgoddavid56/citrea--004" path="crates/sequencer/src/rpc.rs" start="339-353" end="366" />.
- On block production, `produce_l2_block_inner` fetches a *snapshot* of pending deposits via `fetch_deposits` (non-destructive) into the local `deposit_data` variable [1](#0-0) .
- This same `deposit_data` is passed to `dry_run_transactions` → `produce_and_run_system_transactions` → `process_sys_txs`, which builds a `BridgeDeposit` system event per deposit and applies each one individually with its own `checkpoint()`/`revert()` [2](#0-1) .
- Inside `process_sys_txs`, if `apply_l2_block_txs` fails with `L2BlockModuleCallError::EvmSystemTransactionNotSuccessful` **and** the event is a deposit, the working set is reverted, the nonce is rolled back, and the loop `continue`s **without** pushing the transaction into `all_txs` [3](#0-2) . That deposit is therefore silently excluded from the produced block - no cBTC is credited, no receipt exists for it.
- Yet at the end of `produce_l2_block_inner`, after the block is saved, the code unconditionally calls `self.deposit_mempool.lock().remove_deposits(&deposit_data)` using the **original, unfiltered** `deposit_data` snapshot fetched at the top of the function, not the subset that actually succeeded and was included in `all_txs`/`txs_to_run` [4](#0-3) .
- `DepositDataMempool::remove_deposits` matches by `calc_tx_id` and removes both from `accepted_deposit_txs` and `pending_deposits` for every deposit passed to it, with no knowledge of whether it was actually applied successfully [5](#0-4) .

Because `add_deposit_tx`'s only accept-time guard is a one-shot `eth_call` simulation against `BlockId::pending()` at submission time (`make_deposit_tx_from_data`, `crates/sequencer/src/deposit_data_mempool.rs:40-48`; `crates/sequencer/src/rpc.rs:339-366`), and the actual on-chain application happens later, in a batch context with other `SYSTEM_SIGNER` transactions (light-client `setBlockInfo`, other deposits) that may mutate bridge/light-client state between simulation and inclusion, a deposit that passed simulation can legitimately revert (`EvmSystemTransactionNotSuccessful`) when actually applied. The sequencer code anticipates and handles this ("as deposits to non-EOA addresses can revert") but fails to propagate that outcome to the mempool cleanup step.

Note on the specific "gas exhaustion" mechanism in the question: tracing `dry_run_transactions`'s handling of `EvmGasUsedExceedsBlockGasLimit` shows that variant is only reachable for the user-EVM-transaction loop (`crates/sequencer/src/runner.rs:317-338`), not for system transactions inside `process_sys_txs`, whose only handled failure/skip case is `EvmSystemTransactionNotSuccessful`. Any other error from `apply_l2_block_txs` for a system tx (including a hypothetical gas-limit failure) hits the `return Err(...)` branch at `crates/sequencer/src/runner.rs:1698`, which aborts the *entire* block production (`produce_l2_block_inner` returns `Err`, caught only by a log line in `produce_l2_block`, `crates/sequencer/src/runner.rs:473-475`) — in that case `remove_deposits` is never reached, so the exact gas-exhaustion-then-silently-removed chain described in the question does not occur as stated. The actually-demonstrable and exploitable variant of the broken binding is the `EvmSystemTransactionNotSuccessful` revert-and-skip path, not gas exhaustion.

### Impact Explanation
A deposit whose underlying Bitcoin move-to-vault transaction is real (funds already spent to the bridge/vault on L1) can have its corresponding `citrea_sendRawDepositTransaction` request accepted, silently dropped from the produced block due to a revert during actual application, and then permanently purged from the sequencer's deposit mempool as if successfully processed. No cBTC is minted for that deposit, and if the revert condition is not transient (e.g., a hard mismatch that persists across resubmission attempts because `eth_call` at a later pending block still reverts for the same underlying reason), the depositor has no way to get their deposit recognized again — the mempool state no longer tracks it. This matches "funds permanently frozen," a Critical-severity outcome per the given taxonomy. The blast radius is limited to the specific reverted deposit (not chain-wide state divergence, since the reverted system tx is excluded from the actual on-chain block, so all nodes/provers observe the same correct chain state) — the damage is local to the sequencer's off-chain bookkeeping, not the L2 state root itself.

### Likelihood Explanation
This requires the sequencer, during ordinary batching (not a special attacker capability), to include a `BridgeDeposit` system event that reverts at apply time after passing `eth_call` simulation at submission time. The attacker's only capability is submitting `citrea_sendRawDepositTransaction` with a deposit blob and inscribing/mining the underlying Bitcoin transaction — both within the stated unprivileged capabilities. However, reliably engineering the specific state-drift condition (so the deposit passes standalone simulation but reverts once actually batched with other `SYSTEM_SIGNER` txs) depends on internal `BridgeWrapper`/light-client Solidity validation logic, which is out of scope for this repository per the rules ("Solidity system-contract... defects with no path through this repository"). The Rust-side bug (unfiltered `remove_deposits` call) is real and demonstrable purely at the `crates/sequencer` level without needing the Solidity trigger, by directly forcing `apply_l2_block_txs` to return `EvmSystemTransactionNotSuccessful` for a deposit in a unit/integration test.

### Recommendation
Track which deposits from the fetched `deposit_data` snapshot were actually included/successful in `process_sys_txs` (e.g., have `process_sys_txs`/`produce_and_run_system_transactions` return the list of deposit blobs that succeeded, alongside `all_txs`), and pass only that successfully-applied subset to `remove_deposits` at the end of `produce_l2_block_inner`, instead of the original unfiltered `deposit_data`. Deposits skipped due to `EvmSystemTransactionNotSuccessful` should remain in `accepted_deposit_txs`/`pending_deposits` (or be explicitly re-queued) so they can be retried in a later block.

### Proof of Concept
```rust
// crates/sequencer/src/deposit_data_mempool.rs (added test)
// Binding under test:
//   LHS: deposit removed from mempool (remove_deposits called with this deposit)
//   RHS: deposit's BridgeDeposit system tx receipt shows success (included in produced block)
//
// This test operates purely at the DepositDataMempool level to demonstrate that
// remove_deposits has no concept of "success" - it removes whatever list it is given,
// which is exactly what runner.rs::produce_l2_block_inner does with the *unfiltered*
// `deposit_data` snapshot regardless of whether process_sys_txs actually included
// each deposit in `all_txs`.

#[test]
fn test_remove_deposits_purges_reverted_deposit_not_just_successful_ones() {
    let mut mempool = DepositDataMempool::new();
    let deposit1 = hex::decode(DEPOSIT1).unwrap(); // simulates a deposit whose
                                                    // system tx reverts on-chain
                                                    // (EvmSystemTransactionNotSuccessful)
    let deposit2 = hex::decode(DEPOSIT2).unwrap(); // simulates a deposit that succeeds

    assert!(mempool.add_deposit_tx(deposit1.clone()).unwrap());
    assert!(mempool.add_deposit_tx(deposit2.clone()).unwrap());

    // fetch_deposits mirrors runner.rs's unfiltered `deposit_data` snapshot
    let deposit_data = mempool.fetch_deposits(2);
    assert_eq!(deposit_data.len(), 2);

    // Simulate process_sys_txs outcome: deposit1's system tx reverts with
    // EvmSystemTransactionNotSuccessful and is skipped (NOT pushed into all_txs),
    // deposit2 succeeds and is pushed into all_txs.
    let successfully_included = vec![deposit2.clone()]; // what SHOULD be removed

    // BUG: runner.rs calls remove_deposits(&deposit_data) unconditionally,
    // not remove_deposits(&successfully_included)
    let removed_count = mempool.remove_deposits(&deposit_data);

    // Demonstrates the broken binding: deposit1 (reverted, never credited, never
    // included in the block) is removed exactly like deposit2 (successful).
    assert_eq!(removed_count, 2); // BUG: should be 1 (only deposit2)
    assert_eq!(mempool.accepted_deposit_txs.len(), 0); // deposit1 permanently lost

    // Correct behavior would be:
    // let removed_count = mempool.remove_deposits(&successfully_included);
    // assert_eq!(removed_count, 1);
    // assert!(mempool.accepted_deposit_txs.contains(&deposit1)); // retained for retry
}
```
To fully validate end-to-end against `runner.rs`, an integration test in `bin/citrea/tests` would need to force a `BridgeDeposit` system event to return `L2BlockModuleCallError::EvmSystemTransactionNotSuccessful` from `apply_l2_block_txs` (e.g., a deposit to a contract address that reverts) and assert that after `produce_l2_block`, (a) the produced block's transaction list does not contain that deposit's system tx, and (b) the deposit mempool no longer contains it — proving the mempool-removal and actual-inclusion outcomes diverge.

```rust
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
```
