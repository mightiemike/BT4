### Title
Wall-clock resource budgets in block-proposal validation can cause signers to diverge on block validity - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
The external report's bug class is: a message that passes validation on one side (with an attacker-controllable, effectively unbounded resource cost) but is evaluated against a hard, fixed resource ceiling on the other side, and the two sides can reach different verdicts on the same input, with no way to reconcile them deterministically. In LayerZero this was gas on the source chain (unbounded) vs. gas on the destination chain (capped at `2_000_000`). In `stacks-core`, the analogous asymmetry exists in the `NakamotoBlockProposal` validation path, which bounds transaction-by-transaction execution/analysis using **wall-clock timeouts and memory budgets** (`block_deadline`, `per_tx_max_execution_time`, `per_tx_max_analysis_time`, `resource_budgets`) rather than the deterministic Clarity cost-model that governs actual block acceptance in `append_block`.

### Finding Description
`BlockProposal::validate()` in [1](#0-0)  replays a miner-proposed block's transactions using a `block_deadline = Instant::now() + Duration::from_secs(timeout_secs)` and per-transaction `ResourceBudget`s built from `max_tx_execution_time_secs`, `max_tx_analysis_time_secs`, and `max_tx_mem_bytes` [2](#0-1) . If the wall-clock deadline is exceeded, the block is rejected with `ValidateRejectCode::InvalidBlock` and the reason "Block validation timed out before tx {i} could be processed" [3](#0-2) .

This wall-clock/memory ceiling is inherently non-deterministic across signer nodes: it depends on each signer's CPU speed, current load, and available memory, none of which are consensus-visible inputs. By contrast, the actual on-chain block acceptance path (`NakamotoChainState::append_block` → `StacksChainState::process_block_transactions`, see [4](#0-3) ) enforces the deterministic Clarity `ExecutionCost` model (`CostOverflowError`, `BlockCostLimitError`, etc., as seen in the cost-limit test fixtures), not wall-clock time.

A miner can therefore craft a block whose transactions sit just below the Clarity cost limit (so it is fully valid and will be accepted once actually appended to the chain) but whose wall-clock execution time is close to the configured `timeout_secs`/`max_tx_execution_time_secs`. On slower, more loaded, or resource-constrained signer nodes, `postblock_proposal.rs` will time out and reject the proposal (`InvalidBlock`); on faster/idle signer nodes it will finish in time and accept it. This breaks the equality that every signer should reach the same accept/reject verdict for a given block — the verdict instead depends on local hardware/load, which is exactly the "validation verdict two nodes disagree on" class called out in scope.

### Impact Explanation
This is a minority-triggerable (any miner can propose such a block; no privileged role or majority collusion required), unprivileged divergence in signer validation verdicts. Some signers will sign the block (because it validated within their wall-clock budget) while others will reject it (because it timed out on their hardware), producing a bounded, temporary tip/signature disagreement among signers — matching the "High" impact tier ("a minority-triggerable ... static-validation divergence ... temporary tip disagreement"). It does not by itself cause a permanent chain split, since the deterministic Clarity cost check in `append_block` is still the ultimate arbiter of what gets written to the chain; but it can stall block confirmation, cause miners to have block proposals inconsistently signed/rejected, and create signer set disagreement/timeouts that degrade liveness, directly mirroring the "channel gets blocked" liveness impact of the LayerZero finding.

### Likelihood Explanation
Likelihood is medium: an adversarial miner does not need special privileges — they only need to construct a block whose transactions are complex enough to sit near common `max_tx_execution_time_secs`/`timeout_secs` configuration values (these are operator-configurable, so the exact margin needed varies, but crafting Clarity contracts with expensive-but-cost-limit-compliant operations, e.g., heavy string/list manipulation, is straightforward). Because the trigger depends on relative machine performance rather than a fixed on-chain quantity, it will not affect every signer identically, which is what creates the disagreement rather than a uniform accept or uniform reject.

### Recommendation
Do not use wall-clock time or machine-dependent resource ceilings as a signer-facing validity criterion for block proposals. Either (a) rely exclusively on the deterministic Clarity `ExecutionCost` model (the same one enforced in `append_block`) as the sole gating criterion for proposal validation, treating timeouts purely as a local performance safeguard that never produces a consensus-relevant "invalid" verdict distinguishable from a "retry"/"no answer" response, or (b) make the timeout-based rejection reason clearly non-authoritative (e.g., "unable to validate in time" rather than "invalid"), and require signers to keep the block open for future validation/retry (as apparently already anticipated for "node unreachable" cases per `docs/signer-flows.md`, where an unreachable node's proposal endpoint response is treated as "assume higher" rather than a hard reject [5](#0-4) ). Apply the same non-authoritative treatment to timeout-based rejections in `postblock_proposal.rs` so that hardware/load variance cannot manifest as an actual accept/reject disagreement among signers.

### Proof of Concept
1. An adversarial miner builds a Nakamoto block containing one or more Clarity transactions engineered to consume near-maximal but still cost-limit-compliant execution resources (i.e., they will pass `process_block_transactions`'s deterministic `ExecutionCost` checks and would be accepted by `append_block`).
2. The transactions are additionally engineered (e.g., via expensive-but-not-cost-heavy operations, or many transactions each individually cheap but numerous) so that their real wall-clock execution time is close to the configured `timeout_secs` / `max_tx_execution_time_secs` used in `BlockProposal::validate()` [6](#0-5) .
3. The miner submits the block proposal to the signer set.
4. Signers running on slower/loaded hardware hit `Instant::now() >= block_deadline` and reject the block with `ValidateRejectCode::InvalidBlock` / "Block validation timed out before tx {i} could be processed" [3](#0-2) .
5. Signers on faster/idle hardware finish validation before the deadline and sign the block as valid.
6. The signer set now disagrees on the validity of an otherwise chain-acceptable block, causing signature-weight fragmentation and delayed/failed block confirmation until the miner or a subsequent tenure resolves it — a liveness/consensus-verdict disagreement directly analogous to the source/destination-chain asymmetry in the reported LayerZero bug.

**Uncertainty note:** I was unable to fully confirm within the available context whether the timeout/memory-budget path in `postblock_proposal.rs` is used only as an additional safety net alongside a primary deterministic cost check that would independently reject the same transactions, or whether it can be the sole rejection reason for an otherwise cost-compliant block. Confirming the exact interplay between `resource_budgets` (wall-clock/memory) and the deterministic `ExecutionCost` enforcement inside `try_mine_tx_with_len` would require deeper tracing of `stackslib/src/chainstate/stacks/miner.rs`'s `try_mine_tx_with_len`, which was only partially inspected.
