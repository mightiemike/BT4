### Title
`DelegateAction` Signature Lacks Chain-ID Binding, Enabling Cross-Network Replay of Meta-Transactions — (File: `core/primitives/src/action/delegate.rs`)

### Summary

The `DelegateAction` (NEP-366 meta-transaction) signed payload does not include any chain identifier. A `SignedDelegateAction` produced on one NEAR network (e.g., testnet) can be replayed verbatim on another NEAR network (e.g., mainnet) by any party who observed the original submission, provided the victim holds the same account and access key on both networks with a compatible nonce. Regular `SignedTransaction` avoids this by including a `block_hash` that is chain-specific; `DelegateAction` has no equivalent binding.

### Finding Description

`DelegateAction` is the inner payload of a meta-transaction. Its signed fields are: [1](#0-0) 

```
sender_id, receiver_id, actions, nonce, max_block_height, public_key
```

None of these fields identify the network. The hash that is actually signed is produced by: [2](#0-1) 

`SignableMessage::new(&self, SignableMessageType::DelegateAction)` prepends only a NEP-366 discriminant integer (`1 << 30 + 366`): [3](#0-2) [4](#0-3) 

The discriminant distinguishes message types (e.g., `DelegateAction` vs `DelegateActionV2`) but carries no chain identity. Compare this with `SignedTransaction`, which includes a `block_hash` field that is chain-specific: [5](#0-4) 

The `block_hash` in a regular transaction is validated against the chain's recent block history, making cross-chain replay impossible. `DelegateAction` has no such field.

The same structural omission applies to `DelegateActionV2`: [6](#0-5) 

At execution time, `apply_delegate_action` checks signature validity, nonce, `max_block_height`, and sender existence — but none of these checks are chain-specific: [7](#0-6) 

The only replay protection within a single network is the nonce: [8](#0-7) 

### Impact Explanation

An attacker who observes a `SignedDelegateAction` submitted on network A can wrap it in a new outer `SignedTransaction` (paying the outer gas themselves) and submit it on network B. If the victim's account exists on both networks with the same access key and a nonce on network B that is lower than the delegate action's nonce, the inner actions execute on network B without the victim's consent. Inner actions can include `Transfer`, `FunctionCall`, `AddKey`, `DeleteKey`, and `DeleteAccount` — enabling unauthorized fund transfers, key manipulation, or account deletion on the replayed network.

### Likelihood Explanation

The conditions required are:
1. The victim holds the same named account on both networks (common — NEAR account names are human-readable and many users maintain accounts on both mainnet and testnet).
2. The same access key is registered on both networks (less common but realistic for users who reuse key material across environments).
3. The nonce in the delegate action exceeds the current access-key nonce on the target network.
4. `max_block_height` has not expired on the target network (block heights on mainnet and testnet diverge, so this is a constraint but not a reliable barrier).

A malicious relayer is the natural attacker: they receive the `SignedDelegateAction` from the user on one network and replay it on another. The outer transaction is public once submitted, so any observer can also attempt the replay.

### Recommendation

Include the chain ID (from `GenesisConfig::chain_id`, e.g., `"mainnet"` or `"testnet"`) in the `DelegateAction` signed payload, analogous to how `block_hash` binds a regular transaction to a specific chain. The `SignableMessage` scheme in `core/primitives/src/signable_message.rs` is the correct place to extend the signed bytes with a chain-ID field, or alternatively add a `chain_id: String` field directly to `DelegateAction` and `DelegateActionV2` and include it in the borsh-serialized hash. Verification in `apply_delegate_action` must then assert that the chain ID in the payload matches the executing network's chain ID. [9](#0-8) 

### Proof of Concept

1. User `alice.near` exists on both mainnet and testnet with the same ED25519 access key (nonce 5 on mainnet, nonce 3 on testnet).
2. Alice signs a `DelegateAction` on testnet: `sender_id="alice.near"`, `receiver_id="bob.near"`, `actions=[Transfer{deposit: 10 NEAR}]`, `nonce=4`, `max_block_height=<testnet future height>`.
3. The relayer (or any observer) extracts the `SignedDelegateAction` bytes from the submitted testnet transaction.
4. The attacker constructs a new `SignedTransaction` on mainnet with `receiver_id="alice.near"` and `actions=[Action::Delegate(signed_delegate_action)]`, signs the outer transaction with their own mainnet key, and submits it.
5. Mainnet runtime executes `apply_delegate_action`: signature verifies (same key, same payload bytes), nonce 4 > current mainnet nonce 3, `max_block_height` check passes if the mainnet block height is below the value Alice set. Result: 10 NEAR transferred from `alice.near` to `bob.near` on mainnet without Alice's intent. [7](#0-6) [10](#0-9)

#[derive(BorshSerialize)]
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
#[non_exhaustive]
pub enum SignableMessageType {
    /// A delegate action, intended for a relayer to included it in an action list of a transaction.
    DelegateAction,
    /// A delegate action with gas key support, intended for a relayer to include it in an action
    /// list of a transaction.
    DelegateActionV2,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum ReadDiscriminantError {
    #[error("does not fit any known categories")]
    UnknownMessageType,
    #[error("NEP {0} does not have a known on-chain use")]
    UnknownOnChainNep(u32),
    #[error("NEP {0} does not have a known off-chain use")]
    UnknownOffChainNep(u32),
    #[error("discriminant is in the range for transactions")]
    TransactionFound,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum CreateDiscriminantError {
    #[error("nep number {0} is too big")]
    NepTooLarge(u32),
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
