### Title
`LogBlockQuery.getPossibleBlock` performs full bloom-section scan and bit-set iteration before enforcing `MAX_RESULT`, enabling low-cost repeatable RPC-API DoS - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java])

### Summary
`LogBlockQuery.getPossibleBlock()` builds and `AND`s a `BitSet` across every bloom section in the requested block range, then iterates every set bit to populate `blockNumList`, and only after all of that work checks `blockNumList.size() >= MAX_RESULT` before throwing `JsonRpcTooManyResultException`. Because the size gate is applied post-hoc rather than bounding the amount of work performed, an anonymous `eth_getLogs` caller can force full-range bloom computation on every call and still get rejected at the end, burning CPU/DB-read/thread-pool resources repeatably.

### Finding Description
In `getPossibleBlock()` [1](#0-0) , the method:
1. Computes `allConditionsIndex` from the filter (`getConditions()`).
2. Allocates a `blockNumBitSet` sized to the full section range (`maxSection - minSection + 1`) and, for every condition, calls `subMatch()` which iterates every section in the range, submits concurrent futures to `sectionExecutor` for each unique bloom bit index via `sectionBloomStore.get(section, bitIndex)`, and merges bits — this cost scales with the block-range width (`maxSection - minSection`), not with the number of matches.
3. `blockNumBitSet.and(bitSet)` is executed for each condition, then every set bit is walked via `nextSetBit` to build `blockNumList`.
4. Only at line 93 is `blockNumList.size() >= MAX_RESULT` checked, after which `JsonRpcTooManyResultException` is thrown.

There is no early-exit/size-bound check performed before or during the section scan and bit iteration — the "reject" only happens after the "expensive work" (DB reads across sections through `sectionBloomStore`, thread-pool submissions, and full `BitSet` iteration) is already complete. Since the filter accepts wildcard address/topics and a wide `fromBlock`/`toBlock` range (bounded only by chain height `currentMaxBlockNum`), an unprivileged JSON-RPC caller controls how many sections get scanned per call, independent of whether the query is destined to fail the `MAX_RESULT` check.

I was not able to fully verify, within available tool calls, whether `TronJsonRpcImpl`/`LogFilterWrapper` impose an independent cap on the raw block-range width (`toBlock - fromBlock`) before constructing `LogBlockQuery`; grep results show these classes reference `LogBlockQuery`/`getFromBlock`/`getToBlock` but I did not confirm the presence or absence of a pre-flight range-size rejection. If such a cap exists and is small, the practical severity of this finding is reduced; if it doesn't exist (as appeared to be the case from what was inspected), the full chain height range is scannable per call.

### Impact Explanation
This is an RPC-API DoS: an anonymous JSON-RPC client can repeatedly send `eth_getLogs` requests with a full/near-full block range and permissive filters, each of which forces the node to scan bloom sections proportional to chain height, spawn per-section/per-bit concurrent tasks on `sectionExecutor`, and iterate the resulting `BitSet`, before ultimately being rejected via `JsonRpcTooManyResultException`. Repeated in a tight loop this wastes CPU, I/O (via `sectionBloomStore.get`), and thread-pool capacity, potentially degrading RPC responsiveness for legitimate users — matching the "DoS via RPC-API" bounty class. It does not affect consensus or funds.

### Likelihood Explanation
Preconditions are default config and a live node with substantial chain history (more sections to scan increases cost). No privileged role, signed transaction, or fee is required — this is a pure read-only JSON-RPC call, so the attacker cost is close to zero and the request is trivially repeatable in a loop. Feasibility depends on how large a block range/section count is reachable per call, which in turn depends on whether an upstream range cap exists (unconfirmed here).

### Recommendation
Enforce the `MAX_RESULT` (or a distinct, smaller result-count/section-count bound) incrementally during the scan rather than only at the end — e.g., check size after each section's contribution to `blockNumBitSet`/`blockNumList` and abort early with `JsonRpcTooManyResultException` as soon as the bound is exceeded, instead of computing the full `AND` across all sections and walking every set bit first. Additionally, consider capping the allowed `toBlock - fromBlock` width (i.e., `maxSection - minSection`) independently of match count, so the amount of scanning work per RPC call is bounded regardless of the filter's selectivity.

  public List<Long> getPossibleBlock() throws ExecutionException, InterruptedException,
      JsonRpcTooManyResultException {
    List<Long> blockNumList = new ArrayList<>();
    if (minBlock > currentMaxBlockNum) {
      return blockNumList;
    }

    int[][][] allConditionsIndex = getConditions();

    int capacity = (maxSection - minSection + 1) * SectionBloomStore.BLOCK_PER_SECTION;
    BitSet blockNumBitSet = new BitSet(capacity);
    blockNumBitSet.set(0, capacity);

    // works serial
    for (int[][] conditionsIndex : allConditionsIndex) {
      BitSet bitSet = subMatch(conditionsIndex);
      blockNumBitSet.and(bitSet);
    }

    for (int i = blockNumBitSet.nextSetBit(0); i >= 0; i = blockNumBitSet.nextSetBit(i + 1)) {
      // operate on index i here
      if (i == Integer.MAX_VALUE) {
        break; // or (i+1) would overflow
      }
      long blockNum = (long) minSection * SectionBloomStore.BLOCK_PER_SECTION + i;
      if (minBlock <= blockNum && blockNum <= maxBlock) {
        blockNumList.add(blockNum);
      }
    }

    if (blockNumList.size() >= MAX_RESULT) {
      throw new JsonRpcTooManyResultException(
          "query returned more than " + MAX_RESULT + " results");
    }

    return blockNumList;
  }

  private BitSet subMatch(int[][] bitIndexes) throws ExecutionException, InterruptedException {

    int capacity = (maxSection - minSection + 1) * SectionBloomStore.BLOCK_PER_SECTION;
    BitSet subBitSet = new BitSet(capacity);

    for (int section = minSection; section <= maxSection; section++) {
      BitSet partialBitSet = partialMatch(bitIndexes, section);

      for (int i = partialBitSet.nextSetBit(0); i >= 0; i = partialBitSet.nextSetBit(i + 1)) {
        // operate on index i here
        if (i == Integer.MAX_VALUE) {
          break; // or (i+1) would overflow
        }
        int offset = (section - minSection) * SectionBloomStore.BLOCK_PER_SECTION + i;
        subBitSet.set(offset);
      }
    }

    return subBitSet;
  }
