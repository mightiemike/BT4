### Title
Time-of-check/time-of-use race in token-exchange session invalidation allows a stale-session write to clobber a concurrently refreshed valid session (approve()-style lost-update) - (File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts)

### Summary
`storeSession` across all session storage backends is an unconditional, non-versioned upsert keyed only by `session.id` (confirmed in `MemorySessionStorage.storeSession`) [1](#0-0) . `performTokenExchange` reads the current session once at the start of the request, holds that stale reference (`sessionToInvalidate`) across an `await` boundary that performs a network call to Shopify, and later — on a 401 error — blindly writes that stale, now-invalidated copy back to storage. This is the same class of bug as the ERC20 `approve()` race: a write decision is made based on a value read before an asynchronous external operation, and the storage layer applies the write unconditionally ("last write wins") instead of checking that the value hasn't changed since the read.

### Finding Description
In `performTokenExchange`, the flow is:
1. Load the current session and capture it as `sessionToInvalidate` [2](#0-1) .
2. If the session is not active, call `api.auth.tokenExchange` and `storeSession(offlineSession)` to persist a **new, valid** access token [3](#0-2) .
3. On the other hand, if the exchange or a subsequent Admin API call for the *same session id* throws an `HttpResponseError` with code 401, the middleware calls `invalidateAccessToken(sessionToInvalidate, config)`, which sets `session.accessToken = undefined` on the **stale in-memory `sessionToInvalidate` object** and calls `storeSession(session)` again [4](#0-3) [5](#0-4) .

Because `sessionToInvalidate` was captured before the `await api.auth.tokenExchange(...)` call, and `storeSession` performs no compare-and-swap or version check, two requests racing on the same session id can interleave such that:
- Request A reads the old/expired session, then awaits token exchange.
- Request B (racing) also reads the same old session, but completes its exchange first and calls `storeSession(offlineSession)` with a fresh, valid `accessToken`.
- Request A's original call later fails (e.g., transient 5xx→401 mapping from Shopify, or an already-consumed/rotated token) and its catch handler runs `invalidateAccessToken(sessionToInvalidate, config)`, overwriting storage with `accessToken: undefined` — wiping out the token Request B had just legitimately stored.

The exact same read‑then‑stale‑write pattern is duplicated in the Remix and React Router token-exchange strategies (`token-exchange.ts` + `invalidate-access-token.ts` in both packages) [6](#0-5) [7](#0-6) .

### Impact Explanation
A successful race destroys the shop's valid offline (or online) access token in the app's session store, even though a legitimate, freshly-exchanged token exists. Because `respondToInvalidSessionToken` is called without the retry header on the 401 path [8](#0-7) , App Bridge does not automatically retry — the app must go through re-authentication, effectively a denial-of-service against that shop's authenticated session/auth handler until the merchant reloads and completes a fresh exchange. This is triggerable without a leaked secret, MITM, or privileged access — ordinary concurrent requests carrying the same (still technically valid, short-lived) session token, combined with any transient 401 from Shopify's token endpoint, are sufficient.

### Likelihood Explanation
Likelihood is moderate-to-low: it requires two roughly concurrent requests for the same session id, plus one of them independently hitting a 401 from Shopify (e.g. revoked/rotated grant, or a transient error the library maps to 401) while the other is completing a legitimate re-exchange. Multi-tab/embedded-app usage and App Bridge's own retry-on-stale-token behavior increase the chance of overlapping requests for the same shop during token refresh windows, but this is not remotely triggerable by an unauthenticated third party against an arbitrary shop.

### Recommendation
- Never write back a session object captured before an `await`ed external call; reload the session immediately before any invalidating write, or use a compare-and-swap based on a version/timestamp/access-token-value check.
- Update `SessionStorage.storeSession` (or add a new method) to support conditional/optimistic writes so an invalidation write can no-op if the stored `accessToken` has already changed since it was read (i.e., don't overwrite a valid token with `undefined` unless the persisted value still matches the value being invalidated).
- Apply the same fix uniformly to `packages/apps/shopify-app-express/src/helpers/invalidate-access-token.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/helpers/invalidate-access-token.ts`, and `packages/apps/shopify-app-react-router/src/server/authenticate/helpers/invalidate-access-token.ts`.

### Proof of Concept
1. Client holds a session token valid for a shop with an expired stored offline session.
2. Fire two concurrent requests to an endpoint protected by `validateAuthenticatedSession`/token-exchange:
   - Request B completes the exchange first and calls `storeSession(offlineSession)` with a valid `accessToken`.
   - Request A's own call to `api.auth.tokenExchange` (or a subsequent Admin call using the just-exchanged token, depending on integration) throws an `HttpResponseError` with `code === 401` (can be simulated in tests by mocking `shopify.api.auth.tokenExchange` to reject with `HttpResponseError({code: 401, ...})` after Request B has already resolved and stored, as demonstrated by the existing test `invalidates the stored token and responds 401 without the retry header when the exchange returns 401` [9](#0-8) ).
3. Verify that after both requests settle, `sessionStorage.loadSession(offlineId)` shows `accessToken: undefined`, even though Request B's exchange succeeded and should have left a valid token in place — confirming the lost-update race.
