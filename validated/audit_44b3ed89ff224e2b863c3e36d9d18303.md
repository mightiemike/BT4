### Title
Deposit into vault contracts allows minting zero shares for a non-zero, value-losing deposit — ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The vault `deposit` entry points (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) validate that the deposited underlying `amount` is non-zero, but never validate that the resulting minted shares (`inkind`, computed via `convert-to-shares-preview`) are non-zero. This is the mint-side mirror of the reported "burn zero shares" rounding bug: the `redeem` path in the very same contracts was hardened with an explicit `ERR-OUTPUT-ZERO` check, but the analogous `deposit` path was not.

### Finding Description
`convert-to-shares-preview` rounds down: [1](#0-0) 

`deposit` computes `inkind` from this preview and only guards `amount > u0`, `inkind >= min-out` (slippage), and the supply cap — it never asserts `inkind > u0`: [2](#0-1) 

By contrast, the `redeem` function in the same file was patched to explicitly forbid the zero-output case that the external report describes (burning shares for zero underlying out): [3](#0-2) 

Because `min-out` is caller-supplied and commonly passed as `0` (as seen throughout the test suite), a caller depositing a small `amount` relative to the vault's `total-assets-preview()/total-supply-preview()` ratio can have `mul-div-down amount ts ta` round down to `0`. The deposit then proceeds: the underlying is pulled from the account via `receive-underlying`, `assets` is incremented by the full `amount`, but `ft-mint?` mints `0` shares to `recipient`, permanently stranding the depositor's contributed value inside the vault's `assets` accounting with no shares to redeem it back.

### Impact Explanation
This is a single-transaction rounding defect: the deposited underlying is irrevocably absorbed into vault assets while the depositor receives no claim (0 shares) on it. This is a permanent freezing/loss of the depositor's funds — the same class of impact ("permanent freezing of funds") flagged as Critical in the impact taxonomy. It requires no privileged access, no DAO compromise, and no interference from a second user; the rounding can occur naturally as the vault's asset/share ratio grows (via interest accrual or many deposits), causing the threshold "amount too small to mint 1 share" to be reachable by any depositor, especially in higher-decimal/high-liquidity vaults.

### Likelihood Explanation
Likelihood grows over time as the vault's `total-assets-preview()/total-supply-preview()` ratio increases (via accrual of interest, `treasury-lp` mint dilution described in `accrue`, etc.), widening the range of `amount` values that round to zero shares. A user (or a front-end bug/integrator sending a dust deposit, or a user depositing after significant interest has accrued) with default `min-out = 0` can trigger this without any adversarial second party.

### Recommendation
Add an explicit zero-shares guard to every `deposit` function, mirroring the existing `ERR-OUTPUT-ZERO` check already present in `redeem`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the other `asserts!` in `deposit`, in all vault contracts (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` equivalents).

### Proof of Concept
1. Vault has been running long enough (or has accrued enough interest via `accrue`/`treasury-lp` mint) that `total-assets-preview() / total-supply-preview() > 1`, i.e., each share is worth more than 1 unit of underlying.
2. Attacker or unaware user calls `deposit(amount, 0, recipient)` with `amount` small enough that `mul-div-down(amount, ts, ta) == 0` (e.g., `amount = 1` when `ta/ts` ratio ≥ 2).
3. `asserts! (> amount u0)` passes (amount is 1, not 0). `asserts! (>= inkind min-out)` passes since `min-out = 0` and `inkind = 0`. [4](#0-3) 
4. `receive-underlying` pulls `amount` from the depositor into the vault; `assets` is incremented by `amount`; `ft-mint? zft 0 recipient` mints zero shares.
5. The depositor's `amount` is now permanently part of vault `assets` backing all other shareholders, but the depositor holds no shares and cannot redeem any value back — a permanent loss of their deposited funds.
