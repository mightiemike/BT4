### Title
L1-handler cancellation-timelock validation uses local wall-clock time, causing honest-node divergence on block validation - (File: `crates/apollo_l1_events/src/transaction_record.rs`)

### Summary
`TransactionRecord::update_time_based_state` (invoked from `TransactionManager::validate_tx`) decides whether an L1-to-L2 message that has an outstanding cancellation request is now `CancelledOnL2` by comparing each validator's own local `unix_now()` against `cancellation_requested_at + cancellation_timelock`. Because this comparison is not pinned to a deterministic, consensus-agreed timestamp (e.g., the proposed block's timestamp), different honest validating nodes evaluating the exact same proposal at almost the same wall-clock instant can reach different `ValidationStatus` results for the same transaction hash.

### Finding Description
`L1EventsProvider::validate` passes `self.clock.unix_now()` — sourced from each node's own OS clock via `DefaultClock` — into `TransactionManager::validate_tx`, which forwards it into `TransactionRecord::update_time_based_state`. [4](#0-3) [5](#0-4) 

Inside `update_time_based_state`, the timelock-expiry check is a strict inequality against the local clock:
```
let is_cancellation_timelock_passed =
    unix_now >= *requested_at.saturating_add(cancellation_timelock);
if is_cancellation_timelock_passed {
    self.state = TransactionState::CancelledOnL2;
}
``` [3](#0-2) 

`validate_tx` then branches directly on this mutated state to return either `ValidationStatus::Validated` or `InvalidValidationStatus::CancelledOnL2`: [2](#0-1) 

Per the project's own flow documentation, an `Invalid` validation result (including `CancelledOnL2`) is treated by the validating node as a reason to **fail block validation** for the entire proposal: [6](#0-5) 

Because the proposer computes `get_txs`/inclusion decisions and each validator independently re-derives validity using its own clock (rather than a value bound to the proposal, e.g. the block's L2 timestamp), a message whose cancellation-request timelock is right at the boundary can be judged `Validated` by some validators and `CancelledOnL2`/invalid by others for the identical proposed block. This is a classic non-determinism-based honest-node divergence bug class, directly analogous to the reachability structure of the referenced Ethereum Alarm Clock incident: an L1 message sender (unprivileged, reachable actor per the scope rules) can trigger a cancellation request close to the timelock boundary and thereby control which side of a race different nodes land on when independently evaluating "now" against the timelock.

### Impact Explanation
If a sufficient fraction of validators evaluate the boundary transaction differently, the network can split on whether to accept the block, potentially stalling block finalization/consensus for that height (network unable to confirm new transactions) or causing repeated proposal rejections until the disputed L1 handler ages out of the boundary window. This matches the "honest-node divergence" / "network unable to confirm new transactions" impact categories explicitly in scope. The trigger is reachable by any L1 message sender who requests a cancellation timed to land near validators' expected propose/validate windows — no privileged role is required.

### Likelihood Explanation
Medium: triggering the exact race requires a cancellation request whose expiry timestamp is close to the moment different validators call `validate()`, which depends on network propagation timing across nodes' local clocks (subject to normal NTP-scale clock skew, typically well under a second, but validation calls across a distributed validator set are not synchronized to sub-second precision, and validator processing/latency jitter can span the timelock boundary window on its own). An attacker fully controls the L1 message and cancellation-request timing, and can retry across many blocks/messages to increase the chance of hitting the divergence window, without needing to control block/network timing precisely. This is a probabilistic but externally-triggerable condition, not a guaranteed single-shot exploit, hence Medium rather than High.

### Recommendation
Replace `self.clock.unix_now()` in the `validate` code path (and analogously in `get_txs`/proposal path, though propose already isn't distributed the same way validators are) with a deterministic, consensus-derived timestamp — e.g., the block's `block_timestamp`/L2 header timestamp passed in from the batcher — so all validators computing `update_time_based_state` for a given block height converge on the same result. If wall-clock time must be used for auxiliary purposes (metrics, cooldowns not part of consensus outcome), it should be clearly separated from any state transition (`CancelledOnL2`) that feeds into `ValidationStatus` and thus into whether a block is accepted.

### Proof of Concept
1. Node A and Node B are both honest validators for block height `H`.
2. An L1 message sender sends `LogMessageToL2` for tx `T`, then shortly after calls `startL1ToL2MessageCancellation`, timed so that `cancellation_requested_at + cancellation_timelock` falls at wall-clock time `t0`.
3. The proposer includes `T` in the proposal for height `H` and broadcasts it near `t0`.
4. Node A calls `validate(T, H)` at local time `t0 - ε` (its clock reads just before expiry) → `update_time_based_state` computes `is_cancellation_timelock_passed = false` → returns `ValidationStatus::Validated`. [3](#0-2) 
5. Node B, due to network/processing latency or clock skew, calls `validate(T, H)` at local time `t0 + ε` → `is_cancellation_timelock_passed = true` → state becomes `CancelledOnL2` → returns `Invalid(CancelledOnL2)`. [2](#0-1) 
6. Per the documented validation flow, Node A accepts the block while Node B fails validation for the same block/proposal, producing honest-node divergence on the identical L2 state transition input. [6](#0-5) 

Note: I was not able to fully verify from the available index whether `commit_block`/downstream consensus logic has an additional safeguard (e.g., re-validation against a canonical timestamp before finalizing) that might mask this divergence at the consensus layer; a full audit of the consensus integration (outside `apollo_l1_events`) would be needed to confirm whether this divergence actually propagates to a chain-halting or block-rejection outcome versus being absorbed/retried transparently.

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }
