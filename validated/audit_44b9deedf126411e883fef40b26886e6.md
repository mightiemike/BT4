### Title
Grandparent outgoing receipt buffer silently abandoned after second dynamic resharding, permanently stranding deposits — (`runtime/runtime/src/congestion_control.rs`)

---

### Summary

Under dynamic resharding (V3, active at protocol version 85+), `ReceiptSinkV2Info::new` populates `parent_shard_ids` by calling `ShardLayout::get_split_parent_shard_ids`, which for `ShardLayoutV3` returns **only** the single most-recently-split parent (`v3.last_split`). After a second resharding, a stable shard's outgoing receipt buffer keyed by the **grandparent** shard ID is excluded from both the forwarding loop and the bandwidth-request generation. Any receipts with attached deposits that remain in that buffer are permanently stranded: the sender's account has already been debited, but the receiver never receives the deposit.

---

### Finding Description

**Root cause — `get_split_parent_shard_ids` returns only one generation:** [1](#0-0) 

For `ShardLayoutV3` the function short-circuits at line 407 and returns `BTreeSet::from([v3.last_split])` — exactly one shard ID, the parent of the **most recent** split. For `V0/V1/V2` it iterates all shards and collects every parent, but V3 never does that.

**`ReceiptSinkV2Info::new` consumes this one-element set:** [2](#0-1) 

`parent_shard_ids` therefore contains only the immediate parent of the latest split.

**`forward_from_buffer` drains only `parent_shard_ids` and current-layout shards:** [3](#0-2) 

The two loops cover `parent_shard_ids` (one entry for V3) and `shard_layout.shard_ids()` (current shards). A grandparent shard ID appears in neither set and is never processed.

**`generate_bandwidth_requests` also looks only one level up:** [4](#0-3) 

`shard_layout.get_parent_shard_id(to_shard)` for V3 returns the immediate parent only (`last_split` children → `last_split`; all others → self). Grandparent buffers are not included in bandwidth requests, so no bandwidth grant is ever issued for them.

**The TODO in the same file acknowledges the incomplete cleanup:** [5](#0-4) 

And the dynamic-resharding architecture doc lists it as an open item:

> `runtime/runtime/src/congestion_control.rs:336` — Parent shard's outgoing buffer cleanup after resharding.

**Concrete scenario (two splits, one stable shard):**

| Epoch | Shard layout | `parent_shard_ids` on stable shard S | S's A-buffer |
|-------|-------------|--------------------------------------|--------------|
| N | {A, S} | ∅ | S buffers large receipts → A |
| N+1 | {B, C, S} (A→B,C) | {A} | S drains A-buffer; if B/C congested, some remain |
| N+2 | {D, E, C, S} (B→D,E) | {B} | **A-buffer never touched again** |

In epoch N+2 and beyond, `parent_shard_ids = {B}`. The A-buffer in S is not iterated by `forward_from_buffer`, not included in `generate_bandwidth_requests`, and has no path to delivery. The receipts' `deposit` fields represent NEAR tokens already deducted from senders.

**Secondary effect — assertion panic:** [6](#0-5) 

`all_buffers_empty` is computed only over the iterated buffers (B + current shards). If those are all empty but the A-buffer is not, `all_buffers_empty = true` while `own_congestion_info.buffered_receipts_gas() != 0`, triggering a panic in every honest node processing that shard's chunk — a non-network-level denial of service.

---

### Impact Explanation

**Balance loss.** Receipts in the abandoned grandparent buffer carry `deposit` amounts that were atomically deducted from the originating account at transaction-processing time (`runtime/runtime/src/lib.rs`, `update_validator_accounts` / action-receipt charging). Because the buffer is never drained, the receiver account never receives the deposit. The total supply is conserved on-chain (the tokens remain locked in the buffer's trie state), but the receiver's balance is permanently short by the sum of all stranded deposits. This matches the "stealing or loss of funds" impact category.

**Contract execution flow breakage.** Any contract logic that depends on receiving a cross-shard callback or deposit from the stranded receipts will never execute, breaking application invariants.

---

### Likelihood Explanation

**Low.** Three conditions must coincide:

1. **Dynamic resharding active** — requires protocol version ≥ 85 (`DynamicResharding` feature) and a `ShardLayoutConfig::Dynamic` epoch config. Active on mainnet from v85 onward.
2. **Two reshardings separated by at least `min_epochs_between_resharding` epochs** — the cooldown prevents back-to-back splits, but two splits in consecutive allowed windows is a normal operational expectation as the network grows.
3. **Grandparent buffer non-empty at the second resharding boundary** — requires that congestion on the intermediate child shards (B, C) prevented full draining of the A-buffer during the entire intermediate epoch (~12 hours on mainnet). An adversary can deliberately congest B and C by flooding them with large receipts, making this condition reachable.

An unprivileged user can trigger conditions 1 and 3 without any special role: send large cross-shard transactions to fill the grandparent buffer, then congest the child shards. Condition 2 depends on the network's organic growth or a second forced split.

---

### Recommendation

1. **Fix `get_split_parent_shard_ids` for V3** to return all ancestor shard IDs, not just `last_split`. The `ShardsAncestorMapV3` already stores the full ancestor chain; iterate it.

2. **Fix `generate_bandwidth_request`** to walk the full ancestor chain (not just one level) when computing buffer sizes for a child shard, mirroring the fix above.

3. **Address the existing TODO** at `runtime/runtime/src/congestion_control.rs:337`: once a grandparent buffer is confirmed empty, remove its entry from `BufferedReceiptIndices` to prevent the `all_buffers_empty` assertion from diverging from `buffered_receipts_gas`.

4. **Add an invariant check** that `ShardsOutgoingReceiptBuffer::shards()` contains no shard IDs that are absent from both `parent_shard_ids` and `shard_layout.shard_ids()` at the start of `forward_from_buffer`, to catch this class of regression in tests.

### Proof of Concept

```
Epoch N   (layout V3, shards {A=1, S=2}):
  - User sends 100 large cross-shard txs from S to accounts in A, each with 1 NEAR deposit.
  - Congestion on A causes all receipts to be buffered: S.outgoing_buffer[A] = 100 receipts.

Epoch N+1 (layout V3, shards {B=3, C=4, S=2}; A split into B, C):
  - ReceiptSinkV2Info::new → parent_shard_ids = {A=1}  (get_split_parent_shard_ids returns {last_split=A})
  - forward_from_buffer drains A-buffer each chunk.
  - Adversary floods B and C with compute-heavy txs → B, C fully congested.
  - Bandwidth grants for B, C are 0 (size_limit=0 in outgoing_limit).
  - After the entire epoch, S.outgoing_buffer[A] still has 80 receipts (20 forwarded before congestion).

Epoch N+2 (layout V3, shards {D=5, E=6, C=4, S=2}; B split into D, E):
  - ReceiptSinkV2Info::new → parent_shard_ids = {B=3}  (last_split=B)
  - forward_from_buffer iterates: B-buffer, D-buffer, E-buffer, C-buffer, S-buffer.
  - S.outgoing_buffer[A=1] is NOT iterated. 80 receipts × 1 NEAR deposit = 80 NEAR permanently stranded.
  - generate_bandwidth_requests: for D, includes B-buffer (get_parent_shard_id(D)=B). A-buffer excluded.
  - No bandwidth ever requested or granted for A-buffer receipts.

Epoch N+3, N+4, …:
  - parent_shard_ids = ∅ (no new resharding) or {next_split} — never {A}.
  - S.outgoing_buffer[A] is never drained. 80 NEAR lost to receivers.
  - If all other buffers drain to zero: assert_eq!(buffered_receipts_gas(), 0) panics → node crash.
```

    pub fn get_split_parent_shard_ids(&self) -> BTreeSet<ShardId> {
        // V3 doesn't store shards which weren't split in the map, so we can return early.
        // Using explicit match to force handling a new shard layout version when it's added.
        match self {
            ShardLayout::V0(_) | ShardLayout::V1(_) | ShardLayout::V2(_) => {}
            ShardLayout::V3(v3) => return BTreeSet::from([v3.last_split]),
        }

        let mut parent_shard_ids = BTreeSet::new();
        for shard_id in self.shard_ids() {
            let parent_shard_id = self
                .try_get_parent_shard_id(shard_id)
                .expect("shard_id belongs to the shard layout");
            let Some(parent_shard_id) = parent_shard_id else {
                continue;
            };
            if parent_shard_id == shard_id {
                continue;
            }
            parent_shard_ids.insert(parent_shard_id);
        }
        parent_shard_ids
    }
