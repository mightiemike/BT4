### Title
Unbounded full-store scan and sort in `AssetIssueStore.getAssetIssuesPaginated` allows attacker-controlled O(n log n) work regardless of requested `limit` - (File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java)

### Summary
`getAssetIssuesPaginated(offset, limit)` always calls `getAllAssetIssues()` first, which iterates and materializes **every** `AssetIssueCapsule` in the entire underlying LevelDB/RocksDB store, then sorts the full list, before applying the requested `offset`/`limit` window. The `limit` cap (`ASSET_ISSUE_COUNT_LIMIT_MAX`) is only applied after the full O(n) iteration and O(n log n) sort have already been paid, so the cost of a single paginated query is proportional to the total number of asset issues ever created on chain, not to the page size requested by the caller.

### Finding Description
The relevant code is: [1](#0-0) 

`getAllAssetIssues()` streams the entire store via `iterator()` with no bound, and `getAssetIssuesPaginated` immediately sorts that full unbounded list with a `Comparator` before slicing to `[offset, offset+limit)`. The only guard, `limit > ASSET_ISSUE_COUNT_LIMIT_MAX`, clamps the *returned* window size but does nothing to bound the amount of work performed to produce that window — the full iteration and full sort happen unconditionally on every call.

This method is exposed to unprivileged callers via `Wallet.java` (referenced from `getAssetIssuesPaginated`/`getAllAssetIssues` call sites in `framework/src/main/java/org/tron/core/Wallet.java`), which backs the public `GetPaginatedAssetIssueList` gRPC/HTTP query API. Because this is a pure read/query endpoint (not a transaction), it is not covered by TRON's per-transaction bandwidth/energy fee metering — there is no fee or resource charge tied to the amount of store data scanned to answer a query. An attacker can therefore repeatedly call this endpoint with any `offset`/`limit` (e.g., `offset=0, limit=1`) and force the node to perform a full-table scan and sort on every single call, at zero incremental cost to the attacker, while the node incurs cost proportional to the total number of asset issues in the store.

### Impact Explanation
This is a public-cost/query-DoS issue: unprivileged, unauthenticated callers can force disproportionate CPU/memory work (full store iteration + full sort) per request instead of work bounded by the requested page size. Repeated calls can be used to degrade node responsiveness for legitimate API consumers (a resource-exhaustion vector), though it does not directly cause theft, minting, or accounting corruption of TRX/TRC10/TRC20/shielded value — it is a query-endpoint cost-underpricing/availability issue rather than a value-theft issue.

### Likelihood Explanation
High feasibility: the endpoint is public, requires no authentication, no special preconditions, and can be invoked repeatedly and cheaply (it's a read-only RPC call, not a fee-metered transaction). The magnitude of impact scales with the total number of `AssetIssueCapsule` entries in the store, which grows over time as more TRC10 assets are issued, making the attack more effective as the chain ages.

### Recommendation
Avoid materializing and sorting the entire asset list on every paginated call. Maintain a persistently sorted index (e.g., a secondary key ordered by name) so pagination can seek directly to `offset` without a full scan/sort, or cap/rate-limit the total number of entries scanned per query independent of `limit`, and/or apply request-level rate limiting to this RPC/HTTP endpoint at the API gateway layer.

### Proof of Concept
Java integration test plan (JUnit) against `AssetIssueStore`:
1. Populate `AssetIssueStore` with a large number (e.g., 200,000) of synthetic `AssetIssueCapsule` entries with random names.
2. Instrument/measure wall-clock time and allocations for `getAssetIssuesPaginated(0, 1)` (smallest possible page) vs. `getAssetIssuesPaginated(0, 200000)`.
3. Assert expectation under a fix: time/memory for `limit=1` should be near-constant regardless of total store size (e.g., O(log n) or O(page size)), and independent measurements should not show linear scaling with total asset count.
4. Current behavior (bug): both calls take substantially similar, store-size-proportional time because `getAllAssetIssues()` + full sort dominates cost regardless of `limit`, demonstrating the underpriced/unbounded work per query.

  public List<AssetIssueCapsule> getAllAssetIssues() {
    return Streams.stream(iterator())
        .map(Entry::getValue)
        .collect(Collectors.toList());
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
