### Title
Local Metering Balance Can Be Overestimated When Capability Spend Exceeds Earmarked Deduction - (File: core/services/workflows/metering/metering.go)

### Summary
`Report.Settle` in the workflow metering package attempts to "refund" the difference between the credit amount earmarked for a capability step (`step.Deduction`) and the actual amount reported as spent (`spentCredits`). When the actual spend exceeds the earmarked deduction, the refund calculation becomes negative, `balanceStore.Add` rejects negative values, and the local in-memory balance is silently left un-adjusted instead of being reduced by the overspend. This mirrors the reported `GaugeExtraRewarder.setDistributionRate` bug class: the accounting step that should cover the "extra" amount owed is skipped/short-circuited, letting the tracked available balance overstate what is actually left.

### Finding Description
In `Report.Settle`, after aggregating node-reported spend into `spentCredits`, the code performs: [1](#0-0) 

`step.Deduction` is the credit amount that was already subtracted from the local balance at `Deduct` time (via `balanceStore.Minus`), and the intent of `balance.Add(step.Deduction.Sub(spentCredits))` is to return any unused earmarked credit back to the pool. If `spentCredits > step.Deduction` (actual capability spend exceeds what was reserved for that step), the argument to `Add` becomes negative: [2](#0-1) 

`Add` explicitly rejects any negative amount with `ErrInvalidAmount`, so the call fails, and `Settle` only logs `"invariant: spend exceeded reserve"` without ever reducing the balance by the overspent amount: [3](#0-2) 

Regardless of this failure, `AddSpent(spentCredits)` still runs, correctly tracking total spend for billing purposes, but the working `balance` field—used to authorize future steps—never reflects the true remaining credit: [4](#0-3) 

This `balance` is later used to compute how much can still be spent in subsequent steps of the same workflow execution: [5](#0-4) 

Because the overspend was never subtracted, this available-balance computation is based on an inflated (overestimated) balance, exactly analogous to the referenced bug where a reserve/balance check omits an amount that should have already been accounted for before the check.

### Impact Explanation
The local balance tracker is the in-execution enforcement mechanism that caps how many "universal credits" a workflow execution can spend on capability invocations after it was granted a limited reservation via `ReserveCredits`. When a step's real spend legitimately or intentionally exceeds its earmarked deduction (e.g., variable gas costs, compute time, or a capability/adapter reporting a higher spend than initially estimated), the failure to decrement the balance means later steps in the same execution can be authorized (`ByDerivedAvailability`/`ByResource`) against credit that no longer actually exists, allowing the workflow execution to consume more capability resources than its billing reservation intended to permit. This decouples the enforcement guardrail from actual spend and can let a workflow execution exceed its intended/reserved credit ceiling for the remainder of its run.

### Likelihood Explanation
This does not require a malicious node, peer, or operator; it can be triggered by any workflow that uses a capability whose real-world resource consumption naturally or occasionally exceeds the pre-computed deduction earmark (e.g., gas price volatility for `GAS.*` spend types, or compute time variance) — an ordinary condition reachable by any workflow owner (unprivileged user) submitting/executing a workflow, i.e., within the job/workflow ingestion and execution path.

### Recommendation
In `Report.Settle`, when `spentCredits` exceeds `step.Deduction`, explicitly subtract the overage from the balance (e.g., via `balanceStore.Minus`, clamped at zero) instead of relying on `Add` with a value that can be negative and silently failing. Ensure the local balance is always adjusted to reflect true remaining credit regardless of whether the step under- or over-spent its earmark.

### Proof of Concept
1. Workflow reserves credits and calls `Deduct` for a step with `ByResource`/`ByDerivedAvailability`, earmarking `step.Deduction` credits (subtracted from `balance` via `Minus`).
2. The capability response returns `ResponseMetadata.Metering` values whose aggregated `spentCredits` (computed in `Settle`, lines 476-497) exceeds `step.Deduction` (e.g., real gas usage is higher than the pre-estimated limit).
3. `Settle` computes `step.Deduction.Sub(spentCredits)` → negative value; `balance.Add(negative)` returns `ErrInvalidAmount`; `Settle` only logs the invariant warning and proceeds.
4. `balance` is left unchanged from its post-`Minus` state (i.e., it is not further reduced by the extra overspend amount), overstating credits actually available.
5. A subsequent `Deduct` call (`getMaxSpendForInvocation`, `core/services/workflows/metering/metering.go:796`) computes spend limits from this overstated `balance`, permitting further capability spend beyond what the workflow's billing reservation should allow.

// Add increases the current credit balance.
func (bs *balanceStore) Add(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	bs.balance = bs.balance.Add(amount)

	return nil
}
