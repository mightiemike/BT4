### Title
`DeleteAccount`'s balance refund to a nonexistent beneficiary is permanently burnt instead of returned - ([File: runtime/runtime/src/actions.rs])

### Summary
This is a valid analog. `DeleteAccountAction` pays out the deleted account's entire remaining balance to `beneficiary_id` via a system-generated refund receipt [1](#0-0) . Per NEAR's refund semantics, if that refund receipt fails to execute (e.g. because `beneficiary_id` does not exist at execution time), the transferred value is not returned to anyone — it is permanently burnt [2](#0-1) . This mirrors the reported bug class: a value transfer to a specific recipient failing causes irrecoverable loss of funds that were rightfully owed to a party, rather than being reachable through a fallback claim path.

### Finding Description
When `action_delete_account` runs, it computes the account's current balance and, if positive, pushes a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` — a "refund" receipt with `predecessor_id == "system"` — and immediately deletes the account (`*account = None`) [3](#0-2) . The account being deleted is not reversible once this executes.

Refund receipts are governed by special rules documented in `docs/RuntimeSpec/Refunds.md`:
> "If the execution of a refund fails, the refund amount is burnt." [2](#0-1) 

The test suite confirms this is enforced: a refund receipt targeting a beneficiary account that does not exist (and is not implicit-creatable by a refund) fails with `AccountDoesNotExist`, and the destination account is never brought into existence — the funds are simply gone [4](#0-3) . This is consistent with `check_account_existence`/`implicit_creation_allowed`, which explicitly forbid any account kind (named, NEAR-implicit, ETH-implicit, deterministic, universal) from being created by a refund receipt [5](#0-4) , and the accompanying unit test that documents "Refunds are free, and account deletion with a beneficiary makes one, so no kind may be created by one however lonely the transfer is" [6](#0-5) .

The direct consequence: any account owner who calls `DeleteAccount` with a `beneficiary_id` that turns out to be non-existent at the moment the receipt executes (a named account that was never created, mistyped, or — more importantly — an account that gets deleted by an unrelated transaction/receipt in the time between the `DeleteAccount` transaction being signed/submitted and the refund receipt being processed, since receipts execute asynchronously and possibly cross-shard) will have their entire account balance permanently destroyed rather than refunded back to the depositor/owner, exactly analogous to the reported issue where a rightful recipient can never receive value because the transfer to them unconditionally fails.

### Impact Explanation
This causes concrete, permanent loss of funds for the deleting account's owner: the entire NEAR balance held by the account at deletion time is burnt from total supply with no way to recover it, triggered by a single ordinary `DeleteAccount` action from an unprivileged signer. Unlike an ordinary failed transfer (which generates a deposit refund back to the predecessor), a refund-of-a-refund is explicitly disallowed by design, so there is no fallback path — the money is gone. This matches "permanently frozen funds" in the validation criteria.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) user/wallet error specifying a beneficiary that doesn't exist, or (b) a race where the beneficiary account is deleted (self-deletion, or deleted by its own owner) between when the `DeleteAccount` action is submitted/queued and when the resulting refund receipt is actually applied (which can span multiple blocks/shards due to NEAR's asynchronous, cross-shard receipt model). Given wallets and users routinely reuse or recycle account names, and given that receipt execution is asynchronous, this is a realistic occurrence rather than a purely theoretical one, though it is not attacker-forced against a third party (the loss lands on the deleting account's own balance/owner).

### Recommendation
Consider disallowing `DeleteAccount` actions whose `beneficiary_id` cannot be verified to exist at action-application time, or — since existence at execution time can't be perfectly guaranteed for cross-shard receipts — fall back to burning-avoidance by crediting the protocol treasury or re-queuing/retrying instead of unconditionally burning the deposit refund when a `DeleteAccount` beneficiary refund fails. At minimum, document this sharply as a "gotcha" for wallets/tooling and require them to verify beneficiary existence immediately before submitting the `DeleteAccount` transaction.

### Proof of Concept
1. Alice's account holds a balance and she submits `DeleteAccountAction { beneficiary_id: "bob.near" }`, where `bob.near` currently exists.
2. In the same/adjacent block, `bob.near` submits its own `DeleteAccount` action (self-deletion) that gets applied first, or is otherwise removed before Alice's beneficiary refund receipt is processed on `bob.near`'s shard.
3. Alice's `DeleteAccount` action executes: her account is removed and a `Receipt::new_balance_refund(bob.near, alice_balance)` is emitted [3](#0-2) .
4. That refund receipt arrives at `bob.near`'s shard; `bob.near` no longer exists, so `check_account_existence` rejects the `Transfer` action with `AccountDoesNotExist`, exactly as demonstrated for the analogous `refund_may_not_create_universal_account` test [7](#0-6) .
5. Per refund semantics, this failed refund's deposit is burnt rather than returned to Alice [2](#0-1) . Alice's entire balance is now permanently destroyed with no recovery path.

    /// free, so they must not create an account, a `0u` one included.
    #[test]
    fn refund_may_not_create_universal_account() {
        init_test_logger();
        let key = SecretKey::from_seed(KeyType::ED25519, "refund-target").public_key();
        let account_id = derive_universal_account_id(&state_init_for(&[key]).to_raw());
        let (runtime, tries, root, apply_state, _signers, epoch) = setup_runtime(
            vec![alice_account()],
            Balance::from_near(100),
            Balance::ZERO,
            Gas::from_teragas(1000),
        );

        let result = runtime
            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,
                from_ref(&Receipt::new_balance_refund(&account_id, funding())),
                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);
        store_update.commit();

        // Assert on the reason, not just the absence: without this the test would
        // also pass if the refund receipt were dropped instead of refused.
        let [outcome] = &result.outcomes[..] else {
            panic!("the refund receipt must produce exactly one outcome, got {:?}", result.outcomes)
        };
        assert_matches!(
            &outcome.outcome.status,
            ExecutionStatus::Failure(TxExecutionError::ActionError(err))
                if matches!(err.kind, ActionErrorKind::AccountDoesNotExist { .. }),
            "a refund to a missing `0u` id must fail with AccountDoesNotExist",
        );
        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
        assert!(
            get_account(&state, &account_id).unwrap().is_none(),
            "a refund must not bring a `0u` account into existence",
        );
    }
