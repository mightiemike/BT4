### Title
Transaction-triggered chunk-apply panic via unresolvable `receiver_shard_id().unwrap()` on stale delayed receipts across resharding - (File: runtime/runtime/src/congestion_control.rs)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs:874-878` calls `.unwrap()` on the `Result<ShardId, EpochError>` returned by `Receipt::receiver_shard_id`. For `GlobalContractDistribution` receipts, `receiver_shard_id` (`core/primitives/src/receipt.rs:437-466`) returns `Err(EpochError::ShardingError(...))` whenever `shard_layout.resolve_to_current_shard(target_shard)` cannot map the receipt's stale `target_shard` to any shard in the current layout. This is directly analogous to the Envoy bug class: code assumes a value (here, a successfully remapped shard id) still exists after a "reset"-like event (a resharding/shard-layout change) has invalidated it, and unconditionally unwraps, crashing the process instead of handling the now-invalid state gracefully. [1](#0-0) [2](#0-1) 

### Finding Description
`receipt_filter_fn` is invoked from `DelayedReceiptQueueWrapper::pop` (`congestion_control.rs:880-909`) every time the runtime drains the persistent delayed-receipt queue during normal chunk application (`process_delayed_receipts`, `runtime/runtime/src/lib.rs:2570-2663`), which runs unconditionally for every new chunk. [3](#0-2) [4](#0-3) 

A `GlobalContractDistribution` receipt is created whenever any unprivileged account submits a `DeployGlobalContract` transaction; its `target_shard` is fixed to the sender's shard at creation time. If that receipt is delayed (e.g., due to compute/gas saturation on the target shard, which an attacker can trigger with cheap `burn_gas_raw`-style calls) across a resharding event, its `target_shard` becomes stale relative to the shard layout at the time it is finally popped. `receiver_shard_id` attempts to recover via `shard_layout.resolve_to_current_shard(target_shard)`, but this recovery only works when the current layout's split history still traces back to `target_shard`. The nearcore test-suite itself documents that this exact scenario is exploitable after two sequential resharding events (`test_stale_global_contract_distribution_after_double_resharding`), explicitly stating that "processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard." [5](#0-4) 

While `receiver_shard_id` itself was hardened to return a typed `Err` instead of panicking directly, the call site in `receipt_filter_fn` still unconditionally `.unwrap()`s that `Result`, converting any case where `resolve_to_current_shard` cannot find a mapping (e.g., split-history that is only tracked for "V3"/dynamic shard layouts per the test's own caveat, deeper/older resharding chains, or shard-layout histories not fully retained) back into an unrecoverable panic on the hot path used by every honest validator applying the same chunk. [6](#0-5) 

### Impact Explanation
Because `process_delayed_receipts`/`receipt_filter_fn` runs deterministically on every validator applying the same chunk, a triggered panic here is not an isolated node crash but a chain-wide halt: every honest node processing the chunk containing (or draining past) the stale receipt panics identically, since block/chunk application is consensus-critical and deterministic. This matches the "transaction-triggered halt" acceptance criterion — an unprivileged account only needs to (1) deploy a global contract to create a `GlobalContractDistribution` receipt, and (2) keep its shard congested/gas-saturated with ordinary `FunctionCall` transactions long enough for the receipt to be delayed across resharding boundaries. [4](#0-3) 

### Likelihood Explanation
Exploitability is gated by two conditions that are not fully attacker-controlled: (1) dynamic resharding must actually occur while the receipt is delayed (this is normally an epoch/protocol-governed event, not something a single transaction can force on demand), and (2) the shard split-history must fail to resolve the stale `target_shard` — the repository's own regression test demonstrates this occurring after **two** resharding generations under `DynamicResharding`/V3 shard layouts, and explicitly notes "the fix only works with V3 shard layouts (dynamic resharding)... [with] static resharding, the shard layout doesn't maintain a full split history," implying other resharding paths may not be covered by the current `resolve_to_current_shard` recovery. Because triggering resharding itself is outside a single transaction's control, likelihood is **Medium**: an attacker cannot unilaterally cause the halt in one submission, but can reliably set up the precondition (a saturated shard holding a stale distribution receipt) and simply wait for/exploit resharding events, or exploit any future/edge shard-layout transition not covered by `resolve_to_current_shard`.

### Recommendation
- Replace the `.unwrap()` in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:876`) with graceful handling of the `Err(EpochError::ShardingError(..))` case — e.g., treat an unresolvable stale `GlobalContractDistribution` receipt as belonging to no shard / drop it with a logged warning and burn its bookkeeping, or propagate a `RuntimeError`/`StorageError::StorageInconsistentState` through `pop`'s `Result` return type instead of panicking inline.
- Audit all other call sites of `receiver_shard_id(...).unwrap()` (also present in `chain/chain/src/chain.rs`, `chain/chain/src/spice/chunk_validation.rs`, `chain/chain/src/store/mod.rs`, `core/primitives/src/state_record.rs`) for the same "assume Ok after a resharding reset" pattern.
- Extend `resolve_to_current_shard` (or the split-history retention) to guarantee resolution for every historically valid `target_shard`, regardless of shard-layout config type (static vs. dynamic/V3), so the `Err` path becomes truly unreachable rather than merely "unlikely."

### Proof of Concept
The repository already contains a working proof of concept demonstrating this exact panic path end-to-end: `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs:32-186`. It:
1. Deploys a test contract and then a global contract from `user0`, creating a `GlobalContractDistribution` receipt with `target_shard = S_A` (user0's shard).
2. Saturates `S_A`'s compute budget every block via cheap `burn_gas_raw` calls so the distribution receipt is pushed into, and stays in, the delayed-receipt queue.
3. Forces two sequential dynamic-resharding splits (via `DynamicReshardingConfig::force_split_shards`) while the receipt remains delayed, making its `target_shard` stale by two generations.
4. Stops saturating and lets the delayed queue drain, asserting the chain height keeps advancing (`head_height >= drain_end`) — the test comment states failure of this assertion indicates the chain "stalled ... likely panicked processing stale receipt." [7](#0-6) 

Note: because this specific double-resharding scenario is covered by an existing regression test, it appears to already be mitigated for the V3/dynamic-resharding path via `resolve_to_current_shard`; however the unconditional `.unwrap()` at `congestion_control.rs:876` remains a latent single point of failure for any resharding path or split-history edge case (e.g., static resharding, as the test comment itself flags) that `resolve_to_current_shard` does not cover, and it does not defensively convert failures into a recoverable error.
