## Analysis

The Sherlock report describes a fee/value-accounting bypass: one code path (`fundPool`/`_fundPool`) properly deducts a `percentFee` before moving funds into a strategy, but a parallel path (`allocate`/`_allocate`) moves value into the same destination without applying that deduction — letting a caller obtain value transfer without paying the fee the protocol expects to collect.

The closest reachable analog in this nearcore build is the `one_yocto_on_promise` "skip balance deduction" path used when a WASM contract attaches exactly 1 yoctoNEAR to a promise/yield function call while its own account balance is zero.

### Root cause

`ExecutionResultState` tracks a contract's own balance in `current_account_balance`, and every attached deposit on an outgoing promise action is normally subtracted from it via `deduct_balance`: [1](#0-0) 

In `promise_batch_action_function_call_weight`, when the attached amount is exactly 1 yoctoNEAR, `one_yocto_on_promise` is enabled, and the contract's `current_account_balance` is zero, the balance deduction is skipped entirely and instead only an internal accounting counter (`subsidized_amount`) is incremented — but the outgoing action receipt is still appended with the full 1 yoctoNEAR deposit that will be paid out to the receiver when the receipt executes: [2](#0-1) 

The identical pattern is duplicated in the yield/resume promise-creation path: [3](#0-2) 

The dedicated test explicitly documents that the "skipped deduction" is only tracked for bookkeeping (`subsidized_amount`), not actually charged to any account or the sender's balance: [4](#0-3) 

`subsidized_amount` is later surfaced through chunk apply stats (`core/primitives/src/chunk_apply_stats.rs`) and runtime (`runtime/runtime/src/lib.rs`, `chain/chain/src/runtime/mod.rs`), which appear to be for metrics/observability rather than reconciling the created value against a burn or an actual debit elsewhere — I was not able to fully trace those 10 call sites in `runtime/runtime/src/lib.rs` within the remaining budget, so whether the protocol nets this out (e.g., via a corresponding burn or treasury charge) is **not fully confirmed** and should be verified directly in that file.

### Why this matches the report's bug class

Just like `Allo.allocate()` moving value to a strategy while skipping the `percentFee` deduction that the parallel `fundPool()` path enforces, this code creates an outgoing receipt carrying real value (1 yoctoNEAR) to a receiver account while explicitly skipping the balance debit that the normal code path (`deduct_balance`) would otherwise apply on the sender. If `subsidized_amount` is not actually settled against total supply anywhere in the apply loop, each qualifying promise/yield call mints 1 yoctoNEAR that is credited to the receiver but never debited from the sender — a supply-inflation analog to the fee bypass in the original report, reachable by any contract call (transaction-triggered).

### Title
Value created without balance deduction in `one_yocto_on_promise` promise/yield paths - (File: `runtime/near-vm-runner/src/wasmtime_runner/logic.rs`)

### Summary
When `one_yocto_on_promise` is active and a contract's balance is zero, `promise_batch_action_function_call_weight` and `promise_yield_create`'s resume/create paths append an outgoing action with a 1 yoctoNEAR deposit to a receipt but skip the `deduct_balance` call that would normally charge the sender for that deposit, instead only incrementing a bookkeeping counter `subsidized_amount`.

### Finding Description
`ExecutionResultState::deduct_balance` is the sole mechanism that keeps a contract's `current_account_balance` consistent with the deposits attached to outgoing action receipts [5](#0-4) . The `skip_deduct` branch in `promise_batch_action_function_call_weight` bypasses this invariant specifically for the 1-yoctoNEAR case with a zero-balance account, while still calling `ctx.ext.append_action_function_call_weight(... amount ...)` with the full deposit [2](#0-1) . The same pattern recurs in the yield-create path [3](#0-2) . The receiver of that receipt will still receive 1 yoctoNEAR of real transferable value when the receipt executes, even though the sender's balance was never reduced.

### Impact Explanation
If the `subsidized_amount` counter is purely informational (used for stats/metrics) and is not reconciled against total supply (e.g., burned or charged to a protocol treasury) at chunk-apply or block-production time, this constitutes token supply inflation reachable from an ordinary contract call: any deterministic/zero-balance account can repeatedly invoke `ft_transfer_call`-style patterns (or any promise function call requiring the standard "assert one yocto" convention) to mint 1 yoctoNEAR per call without ever holding that balance. Over many transactions and many calls per transaction (bounded only by `max_promises_per_function_call_action` and gas), this creates unbacked value transfers to arbitrary receivers.

### Likelihood Explanation
The trigger condition — `amount == 1 yoctoNEAR`, `config.one_yocto_on_promise` enabled, and the calling account's balance being zero — is intentionally designed to be reachable (the comment states it exists so "deterministic accounts" can call functions like `ft_transfer_call` without being pre-funded), meaning this path is expected to be exercised in normal operation, not merely an edge case. This makes it a straightforward, repeatable action-level trigger, not a hard-to-reach exploit condition.

### Recommendation
Confirm whether `subsidized_amount` is charged against total supply, a treasury account, or a shard-level burn anywhere in `runtime/runtime/src/lib.rs`'s ~10 usages. If it is not reconciled, either (a) require the deposit to be actually paid via the standard `deduct_balance` path (removing the skip), or (b) explicitly debit the equivalent amount from a bounded protocol-level pool/burn so that no net new value is created, and ensure `subsidized_amount` is capped or rate-limited per account so it cannot be used as a per-call minting primitive.

### Proof of Concept
1. Deploy/initialize a deterministic or otherwise zero-balance contract account with `one_yocto_on_promise` enabled.
2. From that contract, call a method that internally issues `promise_batch_action_function_call_weight` (or `promise_batch_action_function_call`) targeting another account with `amount = 1 yoctoNEAR`.
3. Because `current_account_balance` is zero, `skip_deduct` is true: `deduct_balance` is never invoked [6](#0-5) , yet the outgoing receipt still carries the 1 yoctoNEAR deposit.
4. When the resulting receipt executes on the receiver's shard, the receiver's balance increases by 1 yoctoNEAR that was never debited from the sender.
5. Repeat across multiple promises/transactions to accumulate unbacked yoctoNEAR, verifiable by comparing total on-chain balances before/after against the chunk's `subsidized_amount` stat exposed in `core/primitives/src/chunk_apply_stats.rs` to see if it is ever offset.

impl ExecutionResultState {
    /// Create a new state.
    ///
    /// # Panics
    ///
    /// Note that `context.account_balance + context.attached_deposit` must not overflow `u128`,
    /// otherwise this function will panic.
    pub fn new(context: &VMContext, gas_counter: GasCounter, config: Arc<Config>) -> Self {
        let current_account_balance = context
            .account_balance
            .checked_add(context.attached_deposit)
            .expect("current_account_balance overflowed");
        let current_storage_usage = context.storage_usage;
        Self {
            config,
            gas_counter,
            logs: vec![],
            total_log_length: 0,
            return_data: ReturnData::None,
            current_account_balance,
            subsidized_amount: Balance::ZERO,
            current_storage_usage,
        }
    }

    ///
    /// ### Args
    ///
    /// * `amount`: the amount to deduct from the current account balance.
    pub(crate) fn deduct_balance(&mut self, amount: Balance) -> Result<()> {
        self.current_account_balance =
            self.current_account_balance.checked_sub(amount).ok_or(HostError::BalanceExceeded)?;
        Ok(())
    }

#[test]
fn test_one_yocto_on_promise_enabled() {
    let mut logic_builder = VMLogicBuilder::default();
    logic_builder.config.one_yocto_on_promise = true;
    logic_builder.context.account_balance = Balance::ZERO;
    logic_builder.context.attached_deposit = Balance::ZERO;
    let mut logic = logic_builder.build();

    let index = promise_create(&mut logic, b"rick.test", 0, 0).expect("should create a promise");

    // 1 yoctoNEAR should succeed even with zero balance
    promise_batch_action_function_call_weight(&mut logic, index, 1, Gas::ZERO, 0)
        .expect("1 yoctoNEAR should succeed with feature enabled");

    // 2 yoctoNEAR should still fail
    promise_batch_action_function_call_weight(&mut logic, index, 2, Gas::ZERO, 0)
        .expect_err("2 yoctoNEAR should fail with zero balance");

    // Transfer with 1 yoctoNEAR should still fail (feature only applies to function calls)
    let num_1u128 = logic.internal_mem_write(&1u128.to_le_bytes());
    logic
        .promise_batch_action_transfer(index, num_1u128.ptr)
        .expect_err("transfer should still fail with zero balance");

    assert_eq!(
        logic.result_state().subsidized_amount,
        Balance::from_yoctonear(1),
        "subsidized_amount should track the skipped deduction"
    );
}
