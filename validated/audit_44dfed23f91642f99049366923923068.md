## Title
VOTEWITNESS opcode energy metering uses unchecked 256-bit modular multiplication (`DataWord.mul`), allowing energy-cost underpricing/bypass via array-length overflow - (File: `actuator/src/main/java/org/tron/core/vm/EnergyCost.java`)

### Summary
The reported bug class ("arithmetic overflow because a safe-math library isn't used") maps to `EnergyCost.getVoteWitnessCost` / `getVoteWitnessCost2`, which compute TVM memory-expansion cost for the `VOTEWITNESS` opcode using `DataWord.mul()` — a 256-bit modular multiplication that silently wraps around instead of throwing on overflow, unlike the newer `getVoteWitnessCost3` path.

### Finding Description
`getVoteWitnessCost` (the default/legacy path) and `getVoteWitnessCost2` (used when `VMConfig.allowEnergyAdjustment()` is enabled but `allowTvmOsaka()` is not) take attacker-controlled stack values (`amountArrayLength`, `witnessArrayLength`) directly from TVM bytecode operands and multiply them by the word size using `DataWord.mul(wordSize)`: [1](#0-0) 

Because `DataWord` represents a 256-bit value and `mul()` performs modular arithmetic (mod 2^256) rather than a checked multiply, an attacker can supply a `DataWord` array-length value engineered so that `length * WORD_SIZE (32)` wraps around to a small number. This wrapped, incorrect value is then fed into `memNeeded(...)` and `calcMemEnergy(...)`, producing a drastically under-priced energy cost for what should be an enormous (and normally rejected) memory expansion.

The project's own regression test explicitly documents this exact overflow behavior and the fix: [2](#0-1) [3](#0-2) 

The corrected implementation, `getVoteWitnessCost3`, replaces `DataWord.mul()` with `BigInteger` arithmetic that cannot silently overflow, and correctly throws `Program.OutOfMemoryException` for the same crafted input: [4](#0-3) 

However, `getVoteWitnessCost3` is only reached when `VMConfig.allowTvmOsaka()` is enabled; otherwise it explicitly falls back to the vulnerable `getVoteWitnessCost2`/`getVoteWitnessCost` path: [5](#0-4) 

This is directly analogous to the external report's root cause: arithmetic performed without overflow protection ("safe math") on values that ultimately govern accounting/metering (there, token balances; here, TVM energy cost), where the fix (BigInteger-checked math) already exists in the codebase but is gated behind a not-yet-default-active flag, exactly mirroring the original report's remediation ("this library is already in the contracts... but not consistently used").

### Impact Explanation
If reached by a contract with the vulnerable feature flag configuration (`allowTvmOsaka` disabled, which is the default/legacy state before the corresponding TIP activates on-chain), a crafted smart contract calling `VOTEWITNESS` with an overflow-inducing array length would have its true (astronomically large) requested memory size wrapped to a small value. This bypasses the intended `checkMemorySize` rejection and drastically underprices the energy charged for the operation. Underpriced VM operations are a known DoS vector on account-based blockchains: they let an attacker consume disproportionate node CPU/memory resources for a fraction of the intended energy fee, and can also open the door to resource-exhaustion attacks against block-producing/validating nodes (an accounting/energy-metering corruption class the review rules explicitly call in-scope).

### Likelihood Explanation
The `VOTEWITNESS` opcode is invoked by ordinary smart-contract execution reachable from any broadcast transaction (a `TriggerSmartContract`), requiring no privileged role. The overflow condition is deterministic and fully attacker-controlled (crafting the stack operand for `amountArrayLength`/`witnessArrayLength` bytecode push values), as demonstrated by the project's own test using `0xff...ff` (2^256-1). The only precondition is that `allowTvmOsaka` is not yet activated on the running network, which is the default/legacy configuration.

### Recommendation
Use `BigInteger`-based (or otherwise overflow-checked) arithmetic unconditionally for `getVoteWitnessCost`/`getVoteWitnessCost2`, i.e., backport the `getVoteWitnessCost3` logic to the default code path instead of gating the fix behind `allowTvmOsaka`, since the underlying `DataWord.mul()` overflow risk exists regardless of that feature's activation state.

### Proof of Concept
The existing test `testLargeArrayLengthOverflow` in `VoteWitnessCost3Test.java` demonstrates the underlying overflow: pushing `DataWord largeLength = new DataWord("ffff...ff")` (2^256-1) as the VOTEWITNESS array-length operand causes `DataWord.mul()`-based cost calculation (`cost1`/`cost2`) to silently wrap and compute a tiny/incorrect memory-energy cost, while the BigInteger-based `cost3` path correctly throws `Program.OutOfMemoryException`. Running the same crafted bytecode/operand against a node with `allowTvmOsaka` disabled (default) would result in the underpriced/wrapped calculation being used to actually charge and execute the opcode.   public static long getVoteWitnessCost(Program program) {
    Stack stack = program.getStack();
    long oldMemSize = program.getMemSize();
    DataWord amountArrayLength = stack.get(stack.size() - 1).clone();
    DataWord amountArrayOffset = stack.get(stack.size() - 2);
    DataWord witnessArrayLength = stack.get(stack.size() - 3).clone();
    DataWord witnessArrayOffset = stack.get(stack.size() - 4);

    DataWord wordSize = new DataWord(DataWord.WORD_SIZE);

    amountArrayLength.mul(wordSize);
    BigInteger amountArrayMemoryNeeded = memNeeded(amountArrayOffset, amountArrayLength);

    witnessArrayLength.mul(wordSize);
    BigInteger witnessArrayMemoryNeeded = memNeeded(witnessArrayOffset, witnessArrayLength);

    return VOTE_WITNESS + calcMemEnergy(oldMemSize,
        (amountArrayMemoryNeeded.compareTo(witnessArrayMemoryNeeded) > 0
            ? amountArrayMemoryNeeded : witnessArrayMemoryNeeded), 0, Op.VOTEWITNESS);
  }

  public static long getVoteWitnessCost3(Program program) {
    if (!VMConfig.allowTvmOsaka()) {
      return getVoteWitnessCost2(program);
    }

    Stack stack = program.getStack();
    long oldMemSize = program.getMemSize();
    BigInteger amountArrayLength = stack.get(stack.size() - 1).value();
    BigInteger amountArrayOffset = stack.get(stack.size() - 2).value();
    BigInteger witnessArrayLength = stack.get(stack.size() - 3).value();
    BigInteger witnessArrayOffset = stack.get(stack.size() - 4).value();

    BigInteger wordSize = BigInteger.valueOf(DataWord.WORD_SIZE);

    BigInteger amountArraySize = amountArrayLength.multiply(wordSize).add(wordSize);
    BigInteger amountArrayMemoryNeeded = memNeeded(amountArrayOffset, amountArraySize);

    BigInteger witnessArraySize = witnessArrayLength.multiply(wordSize).add(wordSize);
    BigInteger witnessArrayMemoryNeeded = memNeeded(witnessArrayOffset, witnessArraySize);

    return VOTE_WITNESS + calcMemEnergy(oldMemSize,
        (amountArrayMemoryNeeded.compareTo(witnessArrayMemoryNeeded) > 0
            ? amountArrayMemoryNeeded : witnessArrayMemoryNeeded), 0, Op.VOTEWITNESS);
  }

  public void testLargeArrayLengthOverflow() {
    // Use a very large value that would overflow in DataWord.mul() in cost2
    // DataWord max is 2^256-1, multiplying by 32 would overflow
    // In cost3, BigInteger handles this correctly and should trigger memoryOverflow
    String maxHex = "ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff";
    DataWord largeLength = new DataWord(maxHex);
    DataWord zeroOffset = new DataWord(0);

    Program program = mockProgram(zeroOffset, new DataWord(1),
        zeroOffset, largeLength, 0);

    boolean overflowCaught = false;
    VMConfig.initAllowTvmOsaka(1);    // cost3 self-dispatches; exercise the v3 (BigInteger) path
    try {
      EnergyCost.getVoteWitnessCost3(program);
    } catch (Program.OutOfMemoryException e) {
      // cost3 should detect memory overflow via checkMemorySize
      overflowCaught = true;
    } finally {
      VMConfig.initAllowTvmOsaka(0);
    }
    assertTrue("cost3 should throw memoryOverflow for huge array length", overflowCaught);
  }

    // cost3 self-dispatches: with osaka off it delegates to cost2, so a cost3 left in the shared
    // jump table (e.g. read by a constant call whose view has osaka off) still charges v2 energy.
    String maxHex = "ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff";
    DataWord huge = new DataWord(maxHex);
    DataWord zero = new DataWord(0);

    VMConfig.initAllowTvmOsaka(0);
    long viaCost3 =
        EnergyCost.getVoteWitnessCost3(mockProgram(zero, new DataWord(1), zero, huge, 0));
    long viaCost2 =
        EnergyCost.getVoteWitnessCost2(mockProgram(zero, new DataWord(1), zero, huge, 0));
    assertEquals("cost3 must equal cost2 when osaka is off", viaCost2, viaCost3);

    // sanity: with osaka on, cost3 instead runs v3 and detects the overflow that cost2 wraps away.

      // expected
    } finally {
      VMConfig.initAllowTvmOsaka(0);
