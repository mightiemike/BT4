## Title
`liquidate-multi` batch liquidation can be fully aborted by a single Clarity runtime panic in one position, stranding unrelated healthy liquidations - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`liquidate-multi` is documented and designed to isolate per-position liquidation failures so that one bad position cannot block the others: "Failed liquidations return error codes but don't revert entire batch" [1](#0-0) . It implements this by mapping `call-liquidate` over the position list and collecting each result as an `(response ...)` entry [2](#0-1) . However, `liquidate` (invoked per-position through `call-liquidate`) relies on several `unwrap-panic` calls whose safety depends on state that is influenced by attacker-controlled per-position parameters (asset id chosen via arbitrary `<ft-trait>` reference, index cache population order, etc.) [3](#0-2) . A Clarity runtime panic (unwrap of `none`, division by zero, etc.) triggered inside any single element processed by `map` aborts the entire transaction, exactly like the referenced precompile-panic bug where a single malformed sub-call propagates a Go panic up through the whole Cosmos SDK message and fails the entire outer operation. The mechanism is the same "fold/map that is supposed to absorb per-item failure, but a runtime panic inside one item escapes the isolation boundary and kills the whole batch."

### Finding Description
`liquidate-multi` takes up to 64 positions and processes them via `(map call-liquidate positions)` [4](#0-3) . `call-liquidate` simply calls the public `liquidate` function with `price-feeds` fixed to `none` [5](#0-4) , and the design intent — stated explicitly in the code comments — is that each element's `(response ...)` result is independently `ok`/`err` so that one failing liquidation does not prevent the rest from succeeding [6](#0-5) .

This isolation only holds for *graceful* Clarity errors returned via `(err ...)`. It does **not** hold for Clarity runtime panics, which Clarity's `map` cannot catch — a panic anywhere inside one iteration aborts the entire enclosing transaction (the whole `liquidate-multi` call, not just that one element), the direct Clarity analog of the "precompile panics on malformed input, and the panic propagates all the way up through the Cosmos SDK baseapp, aborting the whole message" root cause in the referenced report.

`liquidate` contains multiple `unwrap-panic` calls on `get-cached-indexes`, e.g. for the debt asset's index and for the "other collateral" repay computation: [7](#0-6) [8](#0-7) 

These `unwrap-panic` calls are only safe as long as `accrue-and-cache`/`accrue-user-debts`/`accrue-user-collateral` has actually populated the `index-cache` map entry for the exact `(timestamp, aid)` key being read for every asset id that participates in the liquidation math, including the derived "other collateral" asset ids computed from `pos-full` [9](#0-8) . Because a caller of `liquidate-multi` supplies an arbitrary `<ft-trait>` per position (any asset the market recognizes, potentially different assets/positions across the 64 entries) and because `price-feeds` is fixed to `none` for the whole batch (so no in-band price refresh occurs), any position whose asset accrual/cache path does not populate an index for an asset id reached later in the same call (e.g., through `scale-debt-for-liquidation`'s `unwrap-panic (get-cached-indexes asset-id)` at line 864 or the "other collateral" branch above) turns a per-item business error into a raw runtime panic. That panic is not representable as `(err u...)`, so it cannot be isolated by `map`; it terminates the whole `liquidate-multi` invocation, discarding every other position's otherwise-successful liquidation in the same batch.

### Impact Explanation
This breaks the explicit design guarantee of `liquidate-multi` — its whole purpose (per the code comment) is to "prevent front-running attacks that prevent bad debt socialization" by allowing many liquidations to be submitted together and having failures of individual positions be non-fatal to the batch [10](#0-9) . If a single crafted or edge-case position can panic instead of returning an `err`, an attacker (or even an unrelated user's edge-case position, e.g. one whose collateral asset was never accrued/cached that block) can repeatedly cause well-formed batch liquidations targeting genuinely unhealthy/insolvent positions to fail entirely. During market stress this stalls timely liquidation of unhealthy positions across the whole batch, which is the same class of impact as the CCTX report (temporary freezing / denial of timely settlement of otherwise-valid operations), and in Zest's context risks temporary freezing of funds and increased bad-debt exposure for the protocol because legitimate liquidations that would have succeeded standalone are blocked when bundled.

### Likelihood Explanation
Likelihood depends on whether an attacker (or ordinary usage pattern) can construct a batch element whose accrual/cache path does not cover every asset id later read via `unwrap-panic` in `liquidate`. This is plausible given: (1) `price-feeds` is unconditionally `none` for `liquidate-multi`, removing the in-band price/cache-priming path available to single `liquidate` calls, and (2) the "other collateral" repayable computation reads `get-cached-indexes debt-aid` a second time after other state mutations, relying on cache freshness assumptions that are harder to guarantee across 64 heterogeneous positions in one transaction. I was not able to fully trace every accrual code path (`accrue-user-debts`, `accrue-user-collateral`, `accrue-and-cache`) end-to-end within this pass to conclusively prove a concrete panic-triggering input exists for all supported assets; this is the part of the analysis I could not fully verify given tool/iteration limits.

### Recommendation
Replace the `unwrap-panic (get-cached-indexes ...)` calls inside `liquidate`/`scale-debt-for-liquidation`/the "other collateral" branch with `unwrap!`/`try!` that return a structured `(err ...)` instead of panicking, and ensure `call-liquidate` wraps `liquidate` in a way that any residual panic source is eliminated before merging into `liquidate-multi`'s per-element response list. More generally, audit every `unwrap-panic` reachable from `liquidate-multi`'s per-position execution path and convert them to recoverable errors, since `map`/`fold` in Clarity cannot isolate a raw runtime panic the way the batch API's documentation implies.

### Proof of Concept
Conceptual PoC (not executed, due to tool limitations in this pass):
1. Construct a `liquidate-multi` call with two positions: Position A is a genuinely unhealthy, liquidatable position on a common asset (e.g. STX/USDC) that would succeed if liquidated alone. Position B specifies an asset combination/borrower state such that, when reached inside `liquidate`, `get-cached-indexes` for some asset id has no entry in `index-cache` for the current `stacks-block-time` (e.g., an asset whose accrual path is skipped because the position has zero balance for that asset, or because `price-feeds` being `none` means the market's cache is stale/never primed for that particular aid in that transaction).
2. Submit `liquidate-multi` with `[A, B]`.
3. Because `map` evaluates each element within the same Clarity transaction, `unwrap-panic` firing while processing position B causes a full contract-call abort, and per Clarity semantics that aborts the entire `liquidate-multi` transaction — position A's liquidation, which would otherwise have succeeded and returned `(ok {...})` in the result list, is also rolled back.
4. Repeating this pattern lets an attacker reliably suppress batch liquidations that include any position sharing the vulnerable pattern, mirroring the CCTX report's repeated-panic denial-of-finalization technique.
