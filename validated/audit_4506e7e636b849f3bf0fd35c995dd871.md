### Title
Unbounded full-table iteration in `listExchanges`/`listProposals` (and `getExchangeList`/`getProposalList`) allows anonymous-RPC DoS as the `ExchangeStore` grows via unprivileged transactions - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`ProposalStore.getAllProposals()` and `ExchangeStore.getAllExchanges()` iterate over the *entire* underlying LevelDB/RocksDB column without any bound, and these are exposed as unauthenticated, un-paginated RPC/HTTP endpoints (`ListExchanges`, `ListProposals`) that any anonymous client can call. `ExchangeCreateContract` (`ExchangeCreateActuator`) is an unprivileged actuator reachable by any funded account, which lets the entry count grow unboundedly over time. This mirrors the reported bug class (unbounded iteration over an approved/accumulated set inside a single execution, whose cost scales with the number of entries), except here the analog surface is a store scan triggered by an RPC call rather than an on-chain payout loop.

### Finding Description
`ExchangeStore.getAllExchanges()` and `ProposalStore.getAllProposals()` both stream the *entire* store with no limit: [1](#0-0) [2](#0-1) 

These are called directly, with no cap, from `Wallet.getExchangeList()` / `Wallet.getProposalList()`: [3](#0-2) [4](#0-3) 

...and are wired to unauthenticated gRPC methods and an unauthenticated HTTP servlet, all reachable by any anonymous client with no argument validation or size limit: [5](#0-4) [6](#0-5) [7](#0-6) 

By contrast, the project already recognizes this exact risk and mitigated it for the *paginated* variants by capping the requested range with `EXCHANGE_COUNT_LIMIT_MAX`: [8](#0-7) 

However, the un-paginated `ListExchanges`/`ListProposals` (and gRPC/HTTP equivalents) bypass this protection entirely and always materialize every record in the store.

Critically, the `ExchangeStore` backing this scan can be grown by any account, not just privileged actors: `ExchangeCreateActuator.execute()`/`doValidate()` only requires that the caller's account exists and holds enough balance to cover `calcFee()` (`getExchangeCreateFee()`) plus the two token amounts — there is no committee/witness restriction, and no on-chain cap on the total number of exchanges that can be created: [9](#0-8) [10](#0-9) 

An attacker able to repeatedly broadcast `ExchangeCreateContract` transactions (paying the configured fee each time) can grow `ExchangeStore`/`ExchangeV2Store` to an arbitrarily large size. Once large, any anonymous caller invoking `ListExchanges` (gRPC) or `/wallet/listexchanges` (HTTP) forces the node to iterate, deserialize, sort, and serialize the full data set on every single call — an operation whose cost scales linearly (or worse, due to the `sorted()` comparator) with store size, with no limit, unlike the paginated APIs that already enforce `EXCHANGE_COUNT_LIMIT_MAX`.

### Impact Explanation
This is a node-level denial-of-service vector reachable from an anonymous RPC/HTTP client, analogous to the unbounded-loop gas-exhaustion class in the report but manifesting as unbounded CPU/memory/response-size consumption per RPC call. As the store grows (via cheap, repeated, unprivileged transactions), each subsequent `ListExchanges`/`ListProposals` call becomes progressively more expensive, degrading or potentially crashing (OOM) full/witness nodes serving public API traffic, and increasing response payload size without bound. Because the paginated equivalents already demonstrate the maintainers recognize the need for a cap, the un-paginated endpoints represent an inconsistent/incomplete mitigation of the same underlying resource-exhaustion class.

### Likelihood Explanation
Likelihood is moderate: exploitation requires an attacker to first pay the `ExchangeCreateFee` (and token balances) many times to grow the store to a size large enough to matter, which has a monetary cost, but is otherwise completely unprivileged and requires no special permissions, keys, or trusted role — any account can do it. Once the store is large (whether through attacker action or organic growth over the chain's lifetime), the read-side amplification (`ListExchanges`/`ListProposals`) is free to trigger repeatedly from any anonymous client, making repeated DoS trivial and cheap after the one-time setup cost.

### Recommendation
- Enforce a hard cap on the response size / iteration count in `ExchangeStore.getAllExchanges()` and `ProposalStore.getAllProposals()`, or remove/deprecate the un-paginated `ListExchanges`/`ListProposals` (and their HTTP servlets) in favor of the already-capped paginated versions.
- If backward compatibility is required, apply the same `EXCHANGE_COUNT_LIMIT_MAX`-style limit to `getExchangeList()`/`getProposalList()` internally.
- Consider adding a maximum total count / rate limit on `ExchangeCreateContract` execution (e.g., per-account or global cap) in `ExchangeCreateActuator.doValidate()`, similar to `MAX_VOTE_NUMBER` or `UNFREEZE_MAX_TIMES` caps used elsewhere in the codebase for other unbounded-growth vectors.

### Proof of Concept
1. From any funded account, repeatedly broadcast `ExchangeCreateContract` transactions (paying `getExchangeCreateFee()` each time) to grow `ExchangeStore`/`ExchangeV2Store` to a large number of entries — no special permission is required, per `ExchangeCreateActuator.doValidate()`.
2. As an anonymous client, repeatedly call the gRPC `ListExchanges` method or HTTP `POST /wallet/listexchanges` (`ListExchangesServlet`), which invokes `Wallet.getExchangeList()` → `ExchangeStore.getAllExchanges()`, forcing a full, unbounded, sorted scan and serialization of every stored exchange on each call.
3. Observe that CPU time and response payload size grow linearly with the number of exchanges created in step 1, with no server-side limit, unlike the paginated `GetPaginatedExchangeList` API which is capped by `EXCHANGE_COUNT_LIMIT_MAX`.

  private boolean doValidate() throws ContractValidateException {
    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }
    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (!this.any.is(ExchangeCreateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [ExchangeCreateContract],real type[" + any
              .getClass() + "]");
    }
    final ExchangeCreateContract contract;
    try {
      contract = this.any.unpack(ExchangeCreateContract.class);
    } catch (InvalidProtocolBufferException e) {
      throw new ContractValidateException(e.getMessage());
    }

    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);

    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }

    if (!accountStore.has(ownerAddress)) {
      throw new ContractValidateException("account[" + readableOwnerAddress + NOT_EXIST_STR);
    }

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    if (accountCapsule.getBalance() < calcFee()) {
      throw new ContractValidateException("No enough balance for exchange create fee!");
    }

    byte[] firstTokenID = contract.getFirstTokenId().toByteArray();
    byte[] secondTokenID = contract.getSecondTokenId().toByteArray();
    long firstTokenBalance = contract.getFirstTokenBalance();
    long secondTokenBalance = contract.getSecondTokenBalance();

    if (dynamicStore.getAllowSameTokenName() == 1) {
      if (!Arrays.equals(firstTokenID, TRX_SYMBOL_BYTES) && !isNumber(firstTokenID)) {
        throw new ContractValidateException("first token id is not a valid number");
      }
      if (!Arrays.equals(secondTokenID, TRX_SYMBOL_BYTES) && !isNumber(secondTokenID)) {
        throw new ContractValidateException("second token id is not a valid number");
      }
    }

    if (Arrays.equals(firstTokenID, secondTokenID)) {
      throw new ContractValidateException("cannot exchange same tokens");
    }

    if (firstTokenBalance <= 0 || secondTokenBalance <= 0) {
      throw new ContractValidateException("token balance must greater than zero");
    }

    long balanceLimit = dynamicStore.getExchangeBalanceLimit();
    if (firstTokenBalance > balanceLimit || secondTokenBalance > balanceLimit) {
      throw new ContractValidateException("token balance must less than " + balanceLimit);
    }

    if (Arrays.equals(firstTokenID, TRX_SYMBOL_BYTES)) {
      if (accountCapsule.getBalance() < addExact(firstTokenBalance, calcFee())) {
        throw new ContractValidateException("balance is not enough");
      }
    } else {
      if (!accountCapsule.assetBalanceEnoughV2(firstTokenID, firstTokenBalance, dynamicStore)) {
        throw new ContractValidateException("first token balance is not enough");
      }
    }

    if (Arrays.equals(secondTokenID, TRX_SYMBOL_BYTES)) {
      if (accountCapsule.getBalance() < addExact(secondTokenBalance, calcFee())) {
        throw new ContractValidateException("balance is not enough");
      }
    } else {
      if (!accountCapsule.assetBalanceEnoughV2(secondTokenID, secondTokenBalance, dynamicStore)) {
        throw new ContractValidateException("second token balance is not enough");
      }
    }

    return true;
