## Analog Found

### Title
Unbounded allocation from unchecked contract-controlled length felt in deprecated syscall array reads - (File: `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`)

### Summary
The EVerest CVE is a classic "attacker supplies a length field that is used to size/allocate a buffer without validating it against the actual amount of available data," causing a heap overflow/OOM condition. The sequencer contains the same bug-class pattern in `read_felt_array` in the deprecated (Cairo 0) syscall handling path: a length felt taken directly from contract-controlled VM memory is converted to a `usize` and passed straight into a memory-range read that will attempt to size a `Vec` accordingly, with no sanity check against the amount of data actually available in the segment.

### Finding Description
`read_felt_array` in the deprecated syscalls hint processor reads an `array_size` felt directly out of VM memory (fully controlled by the executing Cairo 0 contract, since it is the contract's own code that writes the memory cells used as syscall request arguments such as `calldata_size` for `library_call`/`call_contract`), converts it to a `usize`, and passes it straight to `felt_range_from_ptr` with no upper bound or plausibility check: [1](#0-0) 

`felt_range_from_ptr` then calls into `vm.get_integer_range(ptr, size)` using that unchecked size: [2](#0-1) 

Compare this to the fix that already exists elsewhere in the same codebase for the identical bug class, in `apollo_cairo_utils`, which explicitly validates a contract-controlled length felt against the number of remaining elements *before* allocating, specifically to prevent "a contract-controlled length felt from triggering an unbounded `Vec::with_capacity`": [3](#0-2) 

The `read_felt_array` path used by the deprecated (Cairo 0) syscall executor lacks this same guard: `array_size` is not checked against any bound (e.g., remaining segment size, `max_calldata_length`, or a hard cap) before it is used to size a read/allocation.

### Impact Explanation
Any transaction sender can deploy and invoke a Cairo 0 contract that calls `library_call_syscall` or `call_contract_syscall` with an attacker-chosen `calldata_size` value up to `usize::MAX` on a 64-bit host. This value flows unchecked into a range read that will attempt to reserve capacity proportional to that size. Depending on the underlying VM memory-range implementation's allocation strategy, this can trigger an oversized allocation attempt, which in Rust either aborts the process (allocation failure via `handle_alloc_error`) or consumes excessive memory — a process crash/DoS of the executing sequencer node during ordinary transaction execution. Because this is reachable from ordinary transaction execution (not p2p, not privileged-operator-only), it falls in the reachable-attack-surface categories requested (blockifier execution / syscalls).

### Likelihood Explanation
Deploying and calling Cairo 0 contracts remains supported, and `library_call`/`call_contract` syscall handling is exercised by any invoke transaction targeting such a contract, so the reachable path requires only a single crafted transaction with no special privileges — high likelihood, low complexity to trigger.

### Recommendation
Add an explicit bound check on the `array_size` felt in `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`) before it is used to size any read — e.g., cap it at a reasonable maximum, or validate it does not exceed the current segment's available cell count — mirroring the guard already implemented in `crates/apollo_cairo_utils/src/lib.rs`.

### Proof of Concept
Deploy a Cairo 0 contract whose entry point invokes `library_call_syscall` (or `call_contract_syscall`) while writing a very large value (e.g., `2**63`) into the `calldata_size` memory cell of the syscall request, paired with a `calldata` pointer to a small or otherwise plausible-looking data pointer. Invoking this entry point via a normal `INVOKE` transaction routes execution through `read_felt_array` at `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:931-949`, which passes the unchecked size to `felt_range_from_ptr`/`vm.get_integer_range`.

### Caveat / Uncertainty
I could not directly inspect the internal implementation of `cairo-vm`'s `get_integer_range`/`get_continuous_range` (external dependency, not part of this repository), so I cannot fully confirm whether that specific function pre-allocates a `Vec` of the requested size before validating memory bounds, or whether it fails fast on missing memory cells first. The root-cause gap I can confirm from this repository's own code is the missing bound/plausibility check on the attacker-controlled `array_size` in `read_felt_array` before it is handed to a memory-range read — which is the same class of missing validation that was explicitly fixed elsewhere in this codebase (`apollo_cairo_utils`). If `cairo-vm`'s internals already bound-check before allocating, this would reduce to a dependency-mitigated issue rather than an exploitable one; I was not able to verify this either way given tool/dependency-visibility limits.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}
