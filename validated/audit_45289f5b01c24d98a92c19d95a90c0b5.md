The analog here is not about DAI/USSD but the equivalent bug class — "funds deposited into a contract can become permanently unretrievable because the code path that should refund them silently drops the refund logic" — appears in the NEAR Wallet Contract implementation.

### Title
Attached NEAR deposit from an external `rlp_execute` caller is permanently lost (no refund path) when the address-check callback exits via the registrar-failure or "invalid target" branches - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
When an unprivileged external caller (a relayer without an access key) invokes `rlp_execute` on an ETH-implicit account's Wallet Contract with an attached NEAR deposit, the contract tracks that deposit via `CallerDeposit` so it can be refunded if the downstream cross-contract call fails [1](#0-0) . That refund is only ever issued from `rlp_execute_callback` on `PromiseResult::Failed` [2](#0-1) . However, when a base-token transfer targets another eth-implicit account, execution instead first routes through `address_check_callback` [3](#0-2) , and several of its early-return branches (registrar call failed, unexpected registrar response, and the "Invalid target" case where the address turns out to belong to an existing named account) return `ExecuteResponse { success: false, .. }` directly, discarding `caller_deposit` without ever creating a refund promise [4](#0-3) .

### Finding Description
The attached deposit is real NEAR that was already transferred into the Wallet Contract's own account balance as part of the `rlp_execute` function call (it is the `attached_deposit` captured in `ExecutionContext` and wrapped into `CallerDeposit::new` at [5](#0-4) ). The Wallet Contract's owner-controlled spending is gated entirely through `rlp_execute`, whose actions are limited to `Transfer`, `FunctionCall`, `AddKey`, `DeleteKey` (see `action_to_promise` at [6](#0-5) ) and can only be authorized by the ETH private key owner via a signed RLP transaction, or by an authorized relayer key. There is no method that lets an arbitrary external caller reclaim a deposit that the contract itself failed to refund. Once `address_check_callback` takes the "registrar call failed", "unexpected response", or "Invalid target" branch, the deposit that was moved into the contract's balance is stranded there permanently — the contract has no code path that ever moves it back out again.

### Impact Explanation
This is a permanent loss of funds for any relayer/external caller that attaches a NEAR deposit to `rlp_execute` and happens to hit one of these branches (e.g., the target’s address is discovered by the registrar lookup to correspond to an existing named account, or the registrar call itself fails/returns unparseable data — both of which are plausible without any malicious behavior by the caller, e.g. registrar downtime or address collision with a legitimately registered account). Because the deposit is silently absorbed into the Wallet Contract's balance with no redemption mechanism, this matches the reported bug class of "missing redeem/withdraw functionality causing permanently locked funds," but manifests here as concrete unauthorized retention of a transacting caller's NEAR tokens by the protocol's own Wallet Contract.

### Likelihood Explanation
Any relayer without a dedicated access key that submits `rlp_execute` with an attached fee/deposit for a base-token transfer to another ETH-implicit account can trigger this, since the address-check path is taken whenever `target_kind` is `EthImplicit` with a non-empty address to verify [7](#0-6) . This does not require any validator or node compromise — a single external transaction reaching this code path is sufficient, and the failure modes (registrar call failure/bad response, or address turning out to be registered) are realistic operational conditions rather than contrived edge cases.

### Recommendation
Add a refund promise for `caller_deposit` in every early-return branch of `address_check_callback` that currently returns `PromiseOrValue::Value(ExecuteResponse { success: false, .. })` without spawning a refund transfer — mirroring the refund logic already present in `rlp_execute_callback`'s `PromiseResult::Failed` arm.

### Proof of Concept
1. An external relayer account (not the wallet contract's key holder) calls `rlp_execute` on an ETH-implicit account with a non-zero attached deposit, targeting another ETH-implicit account, triggering the `EOABaseTokenTransfer { address_check: Some(address), .. }` path [7](#0-6) .
2. The cross-contract lookup to the address registrar either fails, returns malformed data, or returns `Some(account_id)` while the caller is not the signer of the wallet itself.
3. `address_check_callback` returns `ExecuteResponse { success: false, .. }` directly without constructing any `promise_batch_create`/`promise_batch_action_transfer` refund for the `caller_deposit` [8](#0-7) .
4. The deposit remains in the Wallet Contract's account balance; since only owner-authorized `rlp_execute` actions can move funds out, the external caller has no mechanism to recover the deposit — it is permanently frozen.

fn action_to_promise(target: AccountId, action: near_action::Action) -> Result<Promise, Error> {
    match action {
        near_action::Action::FunctionCall(action) => Ok(Promise::new(target).function_call(
            action.method_name,
            action.args,
            action.deposit,
            action.gas,
        )),
        near_action::Action::Transfer(action) => Ok(Promise::new(target).transfer(action.deposit)),
        near_action::Action::AddKey(action) => match action.access_key.permission {
            near_action::AccessKeyPermission::FullAccess => {
                Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))
            }
            near_action::AccessKeyPermission::FunctionCall(access) => Ok(Promise::new(target)
                .add_access_key_allowance_with_nonce(
                    action.public_key,
                    access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited),
                    access.receiver_id,
                    access.method_names.join(","),
                    action.access_key.nonce,
                )),
        },
        near_action::Action::DeleteKey(action) => {
            Ok(Promise::new(target).delete_key(action.public_key))
        }
    }
