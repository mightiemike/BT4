### Title
Deploy syscall ignores constructor failure return value, causing OS/blockifier execution divergence - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/deploy_contract.cairo`)

### Summary
The Starknet OS's `deploy_contract` function invokes the deployed contract's constructor via `select_execute_entry_point_func`, which returns an `is_reverted` status flag indicating whether the constructor execution succeeded or failed — analogous to `ICohort(_cohort).requestClaim(...)`'s ignored success/failure return value in the external report. Instead of propagating this status to the caller (as is correctly done for regular `call_contract`/`library_call` syscalls), `deploy_contract` hard-asserts the value must be `0` (non-reverted), discarding any legitimate failure signal.

### Finding Description
In `deploy_contract`, the constructor is executed and its revert status captured: [1](#0-0) 

Rather than checking `is_reverted` and constructing a proper (possibly-failed) syscall response — the pattern used elsewhere for entry-point calls, see `contract_call_helper`, which correctly branches on `is_reverted` and sets `failure_flag=is_reverted` in the response header: [2](#0-1) 

`deploy_contract` simply asserts `is_reverted = 0`, and its caller `execute_deploy` unconditionally writes `failure_flag=0` into the syscall response header regardless of what actually happened during constructor execution: [3](#0-2) 

Both functions carry explicit TODO markers acknowledging this gap: [4](#0-3) [5](#0-4) 

Meanwhile, in `blockifier` (the sequencer's native execution engine that actually builds blocks), the deploy syscall's constructor execution error is propagated through normal error channels via `execute_deployment(...)?`: [6](#0-5) 

Constructor execution failures in blockifier are represented as `ConstructorEntryPointExecutionError` / entry-point execution errors that, in the general call flow, are converted into a catchable failed `CallInfo` (the same mechanism used for ordinary reverted inner calls reachable via `Result::Err` in Cairo1, matching the pattern demonstrated in feature contracts that `match` on `call_contract_syscall`'s result and continue after a caught revert). The OS, however, does not mirror this behavior for deploy: it treats any constructor failure as an unconditional hard assertion failure instead of a representable/catchable syscall failure.

### Impact Explanation
Any unprivileged account contract can invoke the `deploy` syscall to deploy a new contract whose constructor is designed to fail (e.g., always panics, or panics under attacker-chosen calldata/salt). If blockifier accepts and completes such a transaction (treating the constructor failure as a normal reverted inner call, consistent with how other entry-point failures are handled and potentially caught by the calling contract), the transaction is included in a block by the sequencer. When the Starknet OS later re-executes that same block (for state-root computation and/or SNOS proving), it reaches `assert is_reverted = 0` in `deploy_contract` and fails outright, since the constructor genuinely reverted. This produces an execution divergence between the sequencer's blockifier-based execution and OS re-execution for the very same transaction/block — resulting either in the OS failing to reproduce the state commitment (proving/verification failure) or in a wrong/unrepresentable outcome for that block. This can lead to the network being unable to confirm/finalize blocks containing such a transaction, a liveness-breaking condition reachable from a single ordinary transaction.

### Likelihood Explanation
High likelihood: deploying a contract with a constructor that reverts is a completely ordinary, permissionless operation requiring no special privileges — any account can submit an invoke transaction that calls `deploy_syscall` with calldata that causes the constructor to fail (e.g., a deliberately failing assert in the constructor). No special preconditions, race conditions, or privileged roles are needed.

### Recommendation
Update `deploy_contract`/`execute_deploy` (and `execute_deploy_syscall` in the deprecated syscall path, which has the same `TODO(Yoni, 1/1/2027): handle failures` note) to check the `is_reverted` value returned from `select_execute_entry_point_func` and construct a proper syscall response (`failure_flag=is_reverted`, appending `ERROR_ENTRY_POINT_FAILED` to retdata on failure), mirroring the handling already implemented in `contract_call_helper`. This ensures OS re-execution stays consistent with blockifier's deploy-failure handling and cannot hard-fail on a legitimately reverted constructor.

### Proof of Concept
1. Deploy an account/contract, then submit an invoke transaction whose `__execute__` calls `deploy_syscall` targeting a class whose constructor unconditionally panics (e.g. `assert(0 == 1, 'fail')`).
2. In blockifier, this constructor failure surfaces as a normal reverted inner call (consistent with the general entry-point-error-to-catchable-result conversion used elsewhere in the codebase, e.g. `syscalls::call_contract_syscall(...)` `Result::Err` patterns in `crates/blockifier_test_utils/resources/feature_contracts/cairo1/cende_test_contract.cairo` lines 107-124), allowing the transaction to be accepted into a block.
3. When the Starknet OS re-executes the block to compute the state commitment/proof, `deploy_contract`'s `assert is_reverted = 0` at `crates/apollo_starknet_os_program/.../deploy_contract.cairo:91` fails because the constructor actually reverted, causing OS execution/proving for that block to fail — a divergence from blockifier's accepted execution.
