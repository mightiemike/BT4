### Title
L1 handler transactions can consume block resources at fixed, negligible cost, letting an L1 message sender DoS other transactions - (File: crates/blockifier/src/transaction/l1_handler_transaction.rs)

### Summary
The Kairos report describes a borrower looping cheap/free actions against a shared, capped resource (a lender's approval) to deny service, because the protocol failed to tie the cost of the action to the resource consumed. The sequencer has a structurally identical gap for L1→L2 messages: the on-chain fee check for `L1HandlerTransaction` only requires `paid_fee_on_l1 != 0`, completely decoupled from the actual L2 resources (`sierra_gas`, `l1_gas`, `message_segment_length`) the transaction is allowed to consume, up to `l1_handler_max_amount_bounds`. This lets any L1 message sender repeatedly submit L1 handler transactions that each pay a fixed, negligible fee while consuming near-maximum per-tx resource bounds, exhausting shared block capacity (bouncer weights) and denying inclusion of other transactions in the same block.

### Finding Description
`L1HandlerTransaction::execute_raw` only checks that the L1-paid fee is non-zero, not that it is proportional to consumed resources: [1](#0-0) 

The per-transaction resource ceiling for L1 handlers is `l1_handler_max_amount_bounds`, and `remaining_gas` for the execution is seeded from that bound, so each L1 handler transaction is permitted to consume up to that fixed maximum of L2 gas/resources regardless of the fee actually paid on L1: [2](#0-1) 

The `paid_fee_on_l1` value is attacker-controlled from L1: it is read directly off the `LogMessageToL2` event's `msg.value`, with no minimum tied to gas price or resource consumption: [3](#0-2) 
Test/tooling code even hard-codes a fixed, arbitrary non-zero value (e.g. `Fee(1)`) as "paid", underscoring that the check accepts trivial amounts: [4](#0-3) [5](#0-4) 

Each accepted L1 handler transaction's resource footprint (message segment length, sierra/proving gas, l1_gas) is added to the block's shared `Bouncer` capacity accounting, which is a hard cap shared by all transactions in the block: [6](#0-5) 
Once accumulated weights exceed `block_max_capacity`, subsequent transactions are rejected with `BlockFull`/`TransactionTooLarge`, i.e., legitimate transactions can no longer be included in that block: [7](#0-6) 

The batcher does cap the number of L1 handler transactions proposed per block (`max_l1_handler_txs_per_block_proposal`), but within that cap each transaction can still individually consume up to `l1_handler_max_amount_bounds` of shared resources while paying only a fixed, negligible fee, so the cap does not eliminate the cost/consumption mismatch — it only bounds the blast radius per block, not per-transaction economic accountability.

### Impact Explanation
This is analogous to the Kairos DoS: a resource with a hard cap (lender approval → block bouncer capacity) can be exhausted by an unprivileged actor (borrower → L1 message sender) at near-zero marginal cost because the fee/cost check is not proportional to the resource actually consumed (min-interest missing → fee only checked for non-zero, not proportional to gas). The result is denial of service: legitimate transactions (and other L1 handler transactions) in the affected block get excluded due to `BlockFull`, degrading network throughput/availability without the attacker bearing commensurate cost. This matches the "network unable to confirm new transactions" / DoS impact class.

### Likelihood Explanation
Reachable by any L1 account controlling `msg.value` when calling `sendMessageToL2` on the Starknet core contract — no privileged role required. The attacker only needs to design an L2 entry point/contract that is cheap to call from L1 but whose resource accounting (calldata size, sierra gas) approaches `l1_handler_max_amount_bounds`, while paying the minimal accepted L1 fee. The `TODO`/comment in the code ("For now, assert only that any amount of fee was paid... Consider removing this check. It is covered by the starknet core contract") indicates the sequencer team is already aware fee enforcement for L1 handlers is weak and relies on an assumption about L1-side enforcement that is not verified in this codebase.

### Recommendation
Tie the accepted `paid_fee_on_l1` to the actual/maximum resources the L1 handler transaction is permitted to consume (e.g., require `paid_fee_on_l1 >= receipt.fee` or a fee proportional to `l1_handler_max_amount_bounds`) instead of merely checking for non-zero. Consider also weighting `max_l1_handler_txs_per_block_proposal`/bouncer admission by paid fee so underpaying L1 handler transactions cannot claim a disproportionate share of block capacity.

### Proof of Concept
1. Attacker calls `sendMessageToL2` on L1 with `value = 1` wei (minimal non-zero fee) and calldata/selector targeting an L2 entry point engineered to consume gas close to `l1_handler_max_amount_bounds` (e.g., heavy storage writes/large calldata within the payload size limit). [8](#0-7) 
2. The scraper picks up the `LogMessageToL2` event and constructs an `L1HandlerTransaction` with `paid_fee_on_l1 = Fee(1)`. [3](#0-2) 
3. During execution, `check_all_gas_amounts_within_bounds` passes because the resource usage is within `l1_handler_max_amount_bounds`, and the only fee check `paid_fee != Fee(0)` trivially passes. [1](#0-0) 
4. Repeating this up to `max_l1_handler_txs_per_block_proposal` times per block accumulates near-maximal bouncer weight per transaction while the attacker pays only `n * 1 wei` total, eventually triggering `BlockFull`/`TransactionTooLarge` for other transactions competing for the same block's capacity. [9](#0-8)

pub async fn send_message_to_l2(
    starknet_core_contract: &StarknetL1Contract,
    l1_handler: &L1HandlerTransaction,
) -> TransactionReceipt {
    const PAID_FEE_ON_L1: U256 = U256::from_be_slice(b"paid"); // Arbitrary value.

    let l2_contract_address = l1_handler.contract_address.0.key().to_hex_string().parse().unwrap();
    let l2_entry_point = l1_handler.entry_point_selector.0.to_hex_string().parse().unwrap();

    // The calldata of an L1 handler transaction consists of the L1 sender address followed by
    // the transaction payload. We remove the sender address to extract the message
    // payload.
    let payload =
        l1_handler.calldata.0[1..].iter().map(|x| x.to_hex_string().parse().unwrap()).collect();
    let msg = starknet_core_contract.sendMessageToL2(l2_contract_address, l2_entry_point, payload);

    msg
        // Sets a non-zero fee to be paid on L1.
        .value(PAID_FEE_ON_L1)
        // Sends the transaction to the Starknet L1 contract. For debugging purposes, replace
        // `.send()` with `.call_raw()` to retrieve detailed error messages from L1.
        .send().await.expect("Transaction submission to Starknet L1 contract failed.")
        // Waits until the transaction is received on L1 and then fetches its receipt.
        .get_receipt().await.expect("Transaction was not received on L1 or receipt retrieval failed.")
}
