### Title
Permanent, irreversible lock of a NEAR Wallet Contract account when an async callback receipt fails after clearing the in-flight guard - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the NEAR "eth-wallet"/relayer-facing contract mentioned as in-scope) uses a single boolean flag, `has_in_flight_tx`, to serialize Ethereum-emulated transactions submitted via `rlp_execute`. The flag is only ever cleared to `false` inside cross-contract callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`), each of which performs further external, attacker/relayer-influenced promise chaining (calls to an `AddressRegistrar` contract and to arbitrary NEP-141 token / target contracts) after the flag is reset. Because NEAR rolls back **all** state changes of a receipt on failure (including any changes made earlier in the same function body), if the callback receipt itself fails for any reason after it sets `has_in_flight_tx = false`, that reset is rolled back and the flag reverts to `true`. Since `rlp_execute` unconditionally rejects any further calls while `has_in_flight_tx == true`, and no other method can clear it, the wallet contract becomes permanently unable to process any future transaction for that account.

### Finding Description
`rlp_execute` (`runtime/runtime/../wallet-contract/src/lib.rs:88-128`) checks `self.has_in_flight_tx` and rejects all calls while it is `true` [1](#0-0) . It is set to `true` right before returning a chained `Promise` in `rlp_execute`, `address_check_callback`, and `nep_141_storage_balance_callback` [2](#0-1) [3](#0-2) [4](#0-3) .

The *only* places that ever set it back to `false` are the first line of each of the four `#[private]` callback methods: `address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, and `ban_relayer` [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) .

This mirrors the QuickSwap `activeIncentive` bug class: a piece of core, per-account state (`activeIncentive` in Algebra / `has_in_flight_tx` here) is only reset by a downstream external-call-dependent code path, and if that external interaction fails in a way that reverts the whole call, the reset never lands, permanently disabling the core operation (swaps in Algebra, `rlp_execute` here).

Per the runtime-execution semantics documented for this codebase, a receipt whose result is `Err` triggers `state_update.rollback()`, discarding *all* state changes from that receipt, not just the failing action [9](#0-8) . `AGENTS.md` for the runtime states the same invariant generally: "If any action fails, the whole receipt fails, its execution outcome is Err" and its state changes are rolled back [10](#0-9) [11](#0-10) .

Consequently, even though `self.has_in_flight_tx = false;` is textually the first statement of `address_check_callback` / `nep_141_storage_balance_callback` / `rlp_execute_callback`, that mutation is only durable if the *entire remaining execution of that receipt* (including whatever `.then()`-chained sub-promise it schedules, gas accounting, and receipt validation) succeeds. Each of these callbacks does non-trivial, partially attacker-influenced follow-up work after the reset:
- `address_check_callback` deserializes an external `AddressRegistrar` response, then (on the "not found" path) builds and forwards another cross-contract action from user/relayer-supplied `Action`/`target` data [12](#0-11) .
- `nep_141_storage_balance_callback` similarly branches on an external NEP-141 token response and, in the "not registered" branch, chains two more function calls (`storage_deposit` + the user's transfer) with sizes/gas coming from attacker/relayer-controlled `FunctionCallAction` fields (`args`, `gas`) [13](#0-12) .

The gas budget passed to these callbacks is a small fixed constant plus the user-requested `action.gas()` (e.g. `RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) [14](#0-13) , and `Action::gas()` for non-FunctionCall actions is hard-coded to `2 Tgas` regardless of actual payload size [15](#0-14) . Any receipt-level failure in this second half of a callback's execution (e.g. the callback running out of the gas budget while constructing/sending a large or otherwise costly follow-up receipt, or the second `.then()` receipt failing pre-validation) causes `Runtime::apply_action_receipt` to roll back the whole receipt, including the `has_in_flight_tx = false` write made moments earlier in the same execution. The result: `has_in_flight_tx` is permanently stuck at `true`.

I was not able to fully verify (within the available tool budget) whether NEAR's gas/size limits make it computationally infeasible for an attacker/relayer to size a follow-up promise such that it exceeds the fixed callback gas budget while the deposit/attached-gas accounting still allows the outer `rlp_execute` transaction to be admitted; this would need to be confirmed with a live test against `runtime/near-wallet-contract` gas costing and NEAR's promise/action-size limits, which is the concrete next step for a background agent to validate.

### Impact Explanation
If `has_in_flight_tx` gets stuck at `true`, the affected account's `WalletContract` becomes permanently unable to execute `rlp_execute` (its only mutating entry point) because of the unconditional early-return guard [16](#0-15) . This is a transaction-triggered, permanent denial of service / freeze of that wallet-contract account: any funds or access-key permissions gated behind that contract's Ethereum-transaction-emulation flow become permanently unusable via `rlp_execute`, matching the "permanently frozen funds" / "transaction-triggered halt" acceptance criteria. Unlike the original Algebra bug (temporary swap DoS reversible by unsetting `activeIncentive`), here there is no unprivileged recovery path once the flag is stuck, since only the contract's own callback flow (which is what got broken) can clear it.

### Likelihood Explanation
The vulnerable code path is directly reachable by any unprivileged transaction signer or relayer calling `rlp_execute` with an Ethereum-emulated transaction that routes through `address_check_callback` (base-token transfer with `address_check`) or `nep_141_storage_balance_callback` (ERC-20 emulation), both of which chain further attacker-influenced cross-contract calls after resetting the guard flag. No validator, node-operator, or network-layer privilege is required — a single crafted transaction from the account owner or a relayer is sufficient to attempt to trigger the failure mode. Likelihood is Medium: it requires crafting a specific gas/size profile that causes the callback's second-stage promise construction/dispatch to exceed its fixed gas allocation or otherwise fail, which needs further gas-accounting verification, but the structural flaw (all-or-nothing rollback erasing an early guard-flag reset) is definite and confirmed by the runtime's rollback semantics.

### Recommendation
- Short term: Persist the `has_in_flight_tx = false` reset independently of the follow-up promise's success by committing it as an unconditional, isolated state update (e.g., emit it as part of a `Data`/refund receipt that always executes regardless of downstream failures) or defensively resize the callback gas budgets to strictly bound the worst-case follow-up promise cost so the callback body cannot itself fail after the reset.
- Long term: Redesign the guard so it does not rely on "reset happens first in the function body" as a durability guarantee under NEAR's per-receipt atomic rollback model; e.g., use a separate always-succeeding finalizer receipt (analogous to a "pull" pattern) whose sole job is clearing `has_in_flight_tx`, decoupled from the variable-cost external-call chaining logic.

### Proof of Concept
1. Attacker (as their own relayer, `signer_account_id == current_account_id`) submits `rlp_execute` with an RLP-encoded Ethereum transaction that decodes to `EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), .. }` or `EthEmulationKind::ERC20Transfer { .. }`, entering the `address_check_callback` / `nep_141_storage_balance_callback` path [17](#0-16) .
2. Craft the inner action's `FunctionCallAction.args`/`gas` (or `AddKeyAction`/`method_names`) so that, once the registrar/NEP-141 lookup resolves and the callback proceeds past `self.has_in_flight_tx = false;`, constructing/dispatching the second-stage chained promise (`action_to_promise(...).then(ext.rlp_execute_callback(...))`) exceeds the callback's fixed attached gas budget (`ADDRESS_CHECK_CALLBACK_GAS` / `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, both dominated by small fixed constants plus a coarse `Action::gas()` estimate) [18](#0-17) [19](#0-18) .
3. The callback receipt fails (e.g., `FunctionCallError`/out-of-gas) after already having executed `self.has_in_flight_tx = false;` in-memory; per `apply_action_receipt`'s rollback semantics, the entire receipt's state changes — including that reset — are discarded, and the trie retains the pre-callback value `has_in_flight_tx = true` [9](#0-8) .
4. Any subsequent call to `rlp_execute` for this account now immediately returns `"Error: transaction already in progress, please try again later."` forever, since nothing else in the contract can clear `has_in_flight_tx` [20](#0-19) .
