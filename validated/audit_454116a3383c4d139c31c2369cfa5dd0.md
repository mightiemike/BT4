## Title
Wallet Contract permanently locks the external caller's attached deposit when an intermediate cross-contract call fails - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Sherlock report flags that `FootiumEscrow`/`FootiumPrizeDistributor` use `IERC20.transfer` without checking/handling the return value, which lets a non-standard token's failed transfer leave funds permanently stuck in the contract instead of triggering a proper failure/refund path. The reachable analog in `nearcore` is the NEAR **Wallet Contract**, which similarly forwards an external caller's attached NEAR deposit through multi-step cross-contract calls, but only refunds that deposit for *one* of the possible failure points, silently swallowing the deposit on the others.

### Finding Description
`WalletContract::rlp_execute` computes a `CallerDeposit` for any external (non-self) caller who attaches NEAR to the call: [1](#0-0) 

This `caller_deposit` is threaded through every promise chain so that, if the final Near action fails, the caller gets their yoctoNEAR back. That refund logic is correctly implemented in the terminal callback: [2](#0-1) 

However, for two intermediate multi-step flows the same `caller_deposit` is passed along but is **not** refunded if the *intermediate* promise itself fails or returns unparsable data:

- `address_check_callback` (invoked after calling the address registrar for `EOABaseTokenTransfer` with `address_check`): on `PromiseResult::Failed` or a deserialization error it returns a failure `ExecuteResponse` directly, never touching `caller_deposit`: [3](#0-2) 

- `nep_141_storage_balance_callback` (invoked after calling `storage_balance_of` on the NEP-141 token for an emulated ERC20 transfer): the same pattern — `PromiseResult::Failed` or deserialization failure returns without any refund of `caller_deposit`: [4](#0-3) 

In both cases, the function signature explicitly receives `caller_deposit: Option<CallerDeposit>` (showing the developers intended it to be used for refunds), but the failure branches drop it on the floor: [5](#0-4) [6](#0-5) 

Because the wallet contract account received the attached NEAR when the outer call to `rlp_execute` was made, and no promise is created to send it back in these two failure branches, the yoctoNEAR permanently remains in the wallet contract's balance with no code path that will ever return it to the original external caller.

### Impact Explanation
Any external, unprivileged relayer/caller who attaches NEAR while invoking `rlp_execute` for (a) a base-token transfer to an unregistered eth-implicit address (which triggers the address-registrar lookup) or (b) an emulated ERC-20 transfer to an unregistered NEP-141 account (which triggers `storage_balance_of`) will have their attached deposit permanently frozen inside the Wallet Contract if the registrar call or `storage_balance_of` call fails or returns something the wallet contract can't parse (e.g., registrar/token temporarily unavailable, out of gas, malformed/unexpected response, or a malicious/non-standard token contract). This is a direct "permanently frozen funds" outcome, matching the report's core bug class (a value-transfer path whose failure isn't correctly detected/handled, leaving assets stuck), reachable purely through submitting a transaction/RPC call to a deployed Wallet Contract.

### Likelihood Explanation
The test suite itself demonstrates that a refund is expected on the terminal callback failure path (`test_caller_refunds`), confirming the intended invariant "external caller gets its deposit back if the cross-contract call fails": [7](#0-6) 
But no analogous test exists (or passes) for the address-registrar or `storage_balance_of` intermediate failure paths, and the source code shows those specific branches omit the refund. Triggering the `Failed` branch requires only a benign real-world condition (registrar/token contract unavailable, insufficient gas forwarded, or a bad/unexpected JSON response) — not any privileged or adversarial network behavior — so likelihood is realistic for normal relayer traffic.

### Recommendation
In `address_check_callback` and `nep_141_storage_balance_callback`, mirror the refund logic used in `rlp_execute_callback`: when `env::promise_result(0)` is `PromiseResult::Failed` (or fails to deserialize), issue a `promise_batch_create` + `promise_batch_action_transfer` back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the failure `ExecuteResponse`, exactly as done at lines 296-311 of `lib.rs`.

### Proof of Concept
1. An external relayer calls `rlp_execute` on a deployed Wallet Contract with an RLP-encoded Ethereum tx representing an `EOABaseTokenTransfer` to an eth-implicit `target` requiring `address_check`, attaching N yoctoNEAR as `attached_deposit` (predecessor ≠ current account, so `CallerDeposit::new` returns `Some`).
2. `inner_rlp_execute` schedules a call to the address registrar and chains `address_check_callback` with `caller_deposit = Some(...)`.
3. If the address-registrar cross-contract call fails (e.g., registrar contract paused, insufficient gas, or any transient failure) `env::promise_result(0)` is `PromiseResult::Failed`; `address_check_callback` returns a failure response at lines 142-148 without creating any refund promise.
4. The N yoctoNEAR attached by the relayer, originally received by the wallet contract, remains part of the wallet contract's balance permanently — the relayer has no way to reclaim it, unlike the documented/tested behavior for `rlp_execute_callback` failures.
5. The identical pattern applies to `nep_141_storage_balance_callback` when the `storage_balance_of` call to the NEP-141 `token_id` fails or returns unexpected data during an emulated ERC-20 transfer.
