### Title
Unchecked subtraction in stateless-decompression header parsing causes a panic (DoS) on a maliciously crafted OS output/state diff - ([File: crates/starknet_os/src/hints/hint_implementation/stateless_compression/utils.rs])

### Summary
The Rust re-implementation of the Starknet OS state-diff decompression routine (`unpack_felts`, `unpack_felts_to`, and `decompress`) computes `n_elms - result.len()` and indexes fixed-length bit buffers using values derived directly from attacker-influenced header fields, without validating that the header-declared bucket lengths are consistent with the actual number of elements to unpack. This mirrors the `aac_sync` bug class in CVE-2016-7393: a parser trusts length/marker fields from untrusted input and uses them directly to slice/index a buffer, leading to an out-of-bounds read (in Rust, manifesting as an integer-underflow panic or slice-index panic).

### Finding Description
`decompress()` reconstructs a state diff from a `Felt` iterator that is fed from a Starknet OS execution output/proof (i.e., data that is ultimately produced by parsing a compressed state diff blob). Internally it calls `unpack_chunk`/`unpack_chunk_to_usize`, which call: [1](#0-0) 

and [2](#0-1) 

Both functions compute `n_elms - result.len()` (lines 504 and 528) where `n_elms` comes from header fields parsed earlier in `decompress` (`unique_value_bucket_lengths`, `n_repeating_values`, `data_len` — see lines 571-600). These header values are extracted with `unpack_chunk_to_usize` from felts that are themselves untrusted (part of the "compressed" input/output stream being parsed). There is no check anywhere that `n_elms >= result.len()` at each iteration, nor that the header-declared bucket lengths are internally consistent (e.g., that a bucket's declared length doesn't exceed the number of felts actually available, or that indices in `repeating_value_pointers`/`bucket_index_per_elm` fit within `all_values`/`bucket_offset_trackers`, see lines 587-615). A crafted header can therefore cause:
- `n_elms - result.len()` to underflow (panics in debug builds; wraps to a huge `usize` in release builds), which is then used at line 505 as `n_packed_elms * LENGTH` to slice `felt.to_bits_le()` (`[0..n_packed_elms * LENGTH]`), causing a slice-index-out-of-bounds panic (`felt.to_bits_le()` only ever returns 251/252 bits).
- `all_values[*offset]` (line 612) or `bucket_offset_trackers[bucket_index]` (line 611) to be indexed out of bounds if `bucket_index_per_elm`/`repeating_value_pointers` contain out-of-range values, again causing a panic.

This is analogous to the AAC parser stack-based buffer overflow: a length/marker read from the untrusted stream is used to index/slice a fixed buffer without a bounds check, and a crafted stream turns that into an out-of-bounds access.

### Impact Explanation
`decompress`/`PartialOsStateDiff::try_from_output_iter` runs as part of Starknet OS re-execution / OS-output parsing, which is on the path used to validate committed state diffs. A malformed or maliciously constructed state-diff/PIE output that reaches this parser (e.g., during OS re-execution, proof verification, or output ingestion) can trigger a Rust panic, crashing the process performing the decompression. If this path is reachable by an honest node processing a state diff produced or replayed from an untrusted/attacker-influenced source (rather than only a fully-trusted local prover run), this results in denial of service of that component and could cause honest-node divergence if some nodes panic while others do not (e.g., due to differing build settings — debug vs. release — for the underflow check), or contribute to a node being unable to progress block processing.

### Likelihood Explanation
The likelihood depends on how directly attacker/proposer-controlled data reaches `PartialOsStateDiff::try_from_output_iter`/`decompress`. In this repository, decompression is applied to the output stream of the Starknet OS itself, which is normally produced by a trusted proving pipeline; however if this parsing is applied to state diff data before/without full validation of internal consistency (bucket lengths, pointers) — as the code currently does — any component that decompresses a state diff without first proving/validating that header lengths are internally consistent is exposed. I could not fully trace every caller of `PartialOsStateDiff` (e.g., feeder-gateway ingestion, proof verifier, aggregator) within the available context, so the exact reachability from a single unprivileged transaction/L1 message is not fully confirmed from the code alone.

### Recommendation
Add explicit bounds checks before every subtraction and indexing operation in `unpack_felts`, `unpack_felts_to`, and `decompress`:
- Use `checked_sub` (or `saturating_sub` with an explicit error) instead of `n_elms - result.len()`.
- Validate that `bucket_index_per_elm` entries are `< all_bucket_lengths.len()` and that `repeating_value_pointers` entries are `< unique_values.len()` before indexing.
- Propagate a proper `OsHintError`/`OsOutputError` instead of panicking, so malformed input results in a graceful error rather than a process crash.

### Proof of Concept
Construct a compressed felt stream whose header (`unpack_chunk_to_usize(compressed, HEADER_LEN, HEADER_ELM_BOUND)` at `decompress` line 571) declares `unique_value_bucket_lengths` or `data_len` values that don't match the number of felts actually following in the stream (e.g., declare a large `n_125_bit_elms` bucket length while supplying only 1 felt for it). Feeding this into `decompress()` (or `PartialOsStateDiff::try_from_output_iter`) causes `n_elms - result.len()` in `unpack_felts` (line 504) to underflow once the supplied felts are exhausted before `n_elms` unique elements have been produced, panicking the process (or, in release mode, producing a huge `n_packed_elms * LENGTH` value that panics on the subsequent slice operation at line 505). pub fn unpack_felts<const LENGTH: usize>(
    compressed: &[Felt],
    n_elms: usize,
) -> Vec<BitsArray<LENGTH>> {
    let n_elms_per_felt = BitLength::min_bit_length(LENGTH).unwrap().n_elems_in_felt();
    let mut result = Vec::with_capacity(n_elms);

    for felt in compressed {
        let n_packed_elms = min(n_elms_per_felt, n_elms - result.len());
        for chunk in felt.to_bits_le()[0..n_packed_elms * LENGTH].chunks_exact(LENGTH) {
            result.push(BitsArray(chunk.try_into().unwrap()));
        }
    }

    result
}

pub fn unpack_felts_to<U>(compressed: &[Felt], n_elms: usize, elm_bound: ElmBoundType) -> Vec<U>
where
    U: TryFrom<BigUint>,
    U: for<'a> TryFrom<&'a BigUint>,
    <U as TryFrom<BigUint>>::Error: std::fmt::Debug,
{
    let n_elms_per_felt = get_n_elms_per_felt(elm_bound);
    let elm_bound_as_big = BigUint::from(elm_bound);
    U::try_from(&elm_bound_as_big).unwrap_or_else(|_| {
        panic!("Elm bound {elm_bound} is too large for type {}", type_name::<U>())
    });
    let mut result = Vec::with_capacity(n_elms);

    for felt in compressed {
        let mut remaining_value = felt.to_biguint();
        let n_packed_elms = min(n_elms_per_felt, n_elms - result.len());
        for _ in 0..n_packed_elms {
            let (new_remaining_value, value) = remaining_value.div_rem(&elm_bound_as_big);
            result.push(
                value.try_into().expect(
                    "Value is the remainder modulo elm_bound, so it should fit in the type",
                ),
            );
            remaining_value = new_remaining_value;
        }
    }

    result
}
