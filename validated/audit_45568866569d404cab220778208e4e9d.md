### Title
JSON injection via incomplete quote escaping in `escapeBytesSelfType` for attacker-controlled name/description/url fields - (File: framework/src/main/java/org/tron/core/services/http/JsonFormat.java)

### Summary
`JsonFormat.escapeBytesSelfType` builds "self-type" (human-readable) JSON output for BYTES protobuf fields (e.g. asset `name`, `abbr`, `description`, `url`, `account_name`, `asset_name`, witness `url`) by only escaping the literal `"` character and never escaping pre-existing `\` bytes in the raw on-chain data before wrapping the value in JSON quotes. Because attackers fully control these byte fields when broadcasting ordinary transactions (`AssetIssueContract`, `AccountUpdateContract`, `TransferAssetContract`, `WitnessCreateContract`), they can choose byte sequences whose escaped form manipulates the resulting quote/backslash parity and corrupts the JSON structure returned by public, unauthenticated HTTP read APIs (`visible=true`), mirroring the `Bio.tokenURI` JSON-injection bug class.

### Finding Description
`printFieldValue` wraps the return value of `escapeBytes`/`escapeBytesSelfType` in a fixed pair of quotes added by the caller: [3](#0-2) 

`escapeBytesSelfType` only escapes `"` characters (via `replaceAll("\"", "\\\\\"")`) and does not first escape backslashes present in the raw bytes: [4](#0-3) 

The fields covered by this "self-type" formatting path are populated straight from attacker-supplied bytes in ordinary, unprivileged transactions/contracts, e.g. `AssetIssueContract.name/abbr/description/url` and `AccountUpdateContract.account_name`, `TransferAssetContract.asset_name`, `WitnessCreateContract.url`: [5](#0-4) 

These bytes are stored verbatim on-chain (e.g. `AssetIssueCapsule` constructs the `name` field directly from the caller-supplied string without sanitization: [6](#0-5) ) and are later re-serialized to JSON by public read-only HTTP endpoints that call `JsonFormat.printToString(reply, visible)` with `visible=true`, e.g. `GetAssetIssueByNameServlet`/`GetAssetIssueByIdServlet`: [7](#0-6) 

Because the escaping only inserts a backslash immediately before each literal `"`, a raw `\` byte already present in the field (fully attacker-chosen, since these are opaque byte fields, not validated as UTF-8 or ASCII) changes the resulting backslash/quote parity when the string is embedded between the fixed surrounding quotes emitted by `printFieldValue`, which can cause the JSON string literal to terminate earlier or later than intended by the server, corrupting the structure of the emitted JSON document (extra/altered keys, or a broken string boundary that lets subsequently-emitted sibling-field content be re-interpreted as new JSON structure). This is the exact bug class described in the Bio Protocol report: naive string concatenation into a JSON document without properly escaping the escape character itself, allowing an unprivileged, self-controlled data field to break out of its JSON string context.

The function does contain a self-check (`JSON.parseObject("{\"key\":\"" + result + "\"}")`, falling back to hex on failure), which mitigates many single-field trivial cases, but the check only validates the escaped value against an isolated single-key wrapper rather than the real multi-field JSON document actually produced by `printSingleField`/`JsonGenerator`, so it does not guarantee that a crafted byte sequence which passes the isolated check cannot still corrupt the surrounding real JSON output that has different trailing content (commas, subsequent field names) after the field's closing quote.

### Impact Explanation
Any client or third-party service that consumes these "self-type" (`visible=true`) HTTP JSON responses (`/wallet/getassetissuebyname`, `/wallet/getassetissuebyid`, `/wallet/getaccount`, etc.) can receive a malformed or attacker-influenced JSON document for data that is nominally read-only and informational. Depending on how downstream consumers (explorers, wallets, exchanges) parse or display these fields, this can lead to spoofed/altered field values, broken parsing, or (if further reflected into HTML/JS contexts by a frontend) downstream XSS, exactly as flagged in the original report as Medium severity because the payload always originates from the same account applying it to their own asset/account metadata.

### Likelihood Explanation
Reachable by any unprivileged account: creating an `AssetIssueContract` or issuing `AccountUpdateContract`/`WitnessCreateContract`/`TransferAssetContract` with crafted byte content is a normal, permissionless transaction, and the vulnerable rendering path is triggered by any anonymous caller of the corresponding read-only HTTP API with `visible=true`. No special privileges or leaked keys are required.

### Recommendation
In `escapeBytesSelfType` (and generally wherever raw bytes are rendered as "self-type" JSON strings), escape backslash characters first, then quotes (and ideally other JSON control characters), mirroring the complete `escapeText` routine already used for proper STRING fields at [8](#0-7) , instead of the partial `replaceAll("\"", "\\\\\"")` escaping, and validate the escaped value against the actual surrounding JSON template used by `printSingleField` rather than an isolated single-field wrapper.

### Proof of Concept
1. Broadcast an `AssetIssueContract` (or `AccountUpdateContract`) transaction where the `name`/`description`/`url` (or `account_name`) byte field is set to a byte sequence containing a trailing/leading `\` immediately adjacent to a `"` byte, e.g. bytes `... 5C 22 2C 22 78 22 3A 22 ...` (`\",\"x\":\"...`), chosen so that after `escapeBytesSelfType`'s single quote-escaping pass the backslash/quote parity flips.
2. Call the corresponding public read HTTP API with `visible=true` (e.g. `GET /wallet/getassetissuebyname?value=<hex>&visible=true`).
3. Compare the raw HTTP response bytes against strict JSON parsing/expected schema: observe that the string boundary for the injected field is not where the server intended, and that content following in the JSON document can be corrupted/misattributed to an unintended key, analogous to the `Bio.tokenURI` PoC in the original report.

  static String escapeText(String input) {
    StringBuilder builder = new StringBuilder(input.length());
    CharacterIterator iter = new StringCharacterIterator(input);
    for (char c = iter.first(); c != CharacterIterator.DONE; c = iter.next()) {
      switch (c) {
        case '\b':
          builder.append("\\b");
          break;
        case '\f':
          builder.append("\\f");
          break;
        case '\n':
          builder.append("\\n");
          break;
        case '\r':
          builder.append("\\r");
          break;
        case '\t':
          builder.append("\\t");
          break;
        case '\\':
          builder.append("\\\\");
          break;
        case '"':
          builder.append("\\\"");
          break;
        default:
          // Check for other control characters
          if (c >= 0x0000 && c <= 0x001F) {
            appendEscapedUnicode(builder, c);
          } else if (Character.isHighSurrogate(c)) {
            // Encode the surrogate pair using 2 six-character sequence (\\uXXXX\\uXXXX)
            appendEscapedUnicode(builder, c);
            c = iter.next();
            if (c == CharacterIterator.DONE) {
              throw new IllegalArgumentException(
                  "invalid unicode string: unexpected high surrogate pair value "
                      + "without corresponding low value.");
            }
            appendEscapedUnicode(builder, c);
          } else {
            // Anything else can be printed as-is
            builder.append(c);
          }
          break;
      }
    }
    return builder.toString();
