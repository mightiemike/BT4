## Title
Truncated `pox_treatment` bitvec is silently padded with `1` (reward), letting a miner punish a stacker while claiming reward for it - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoChainState::check_pox_bitvector` cross-checks the block header's `pox_treatment` `BitVec<4000>` against the burn-chain block-commit's actual PoX outputs (`tenure_block_commit.treatment`). For every PoX address the block-commit paid or burned, it looks up that address's index/indices in the active reward set's `rewarded_addresses` list and reads the corresponding bit(s) out of the header's bitvec. There is no check anywhere that the bitvec's length equals `rewarded_addresses.len()` (the length that `RewardSet::pox_treatment_bitvec_len` — [1](#0-0)  — defines as the canonical length). When an index falls outside the actual bitvec, the code does not reject the block; it silently substitutes `true`: [2](#0-1) 

This mirrors the reported bug class: two arrays (`pox_treatment` bits and `rewarded_addresses` indices) that are supposed to be equal-length/aligned, but the equality is never enforced — instead of failing closed, the code fails open with a default value.

### Finding Description
`check_pox_bitvector` builds `address_to_indeces`, a map from each rewarded PoX address to its index positions in `active_reward_set.rewarded_addresses()`: [3](#0-2) 

Then, for each address the block-commit actually treated (rewarded or punished), it reads the bit at each corresponding index from the miner-supplied `block_bitvec`: [4](#0-3) 

If `block_bitvec.get(ix)` returns `None` (i.e., the bitvec is shorter than the reward set, which is legal because `BitVec<4000>` lengths are only bounded from above, not fixed), the missing bit is treated as `true` ("rewarded"), with only a warning logged. The subsequent decision logic is:
- `all_1` (every checked bit is 1) and `treated_addr.is_punish()` → reject.
- `all_0` (every checked bit is 0) and `treated_addr.is_reward()` → reject.
- Any mixed combination of 1s and 0s across the checked indices → accepted unconditionally (this is the documented "either is acceptable" case for addresses spanning multiple reward slots).

Because a short bitvec pads missing high-index bits with `1`, an address that maps to multiple indices (which happens whenever a stacker locks more than one reward slot's worth of STX, a very common case — the existing test `pox_treatment` in `stackslib/src/chainstate/nakamoto/coordinator/tests.rs` uses exactly this 3-slots-per-stacker scenario) can have some of its real bits explicitly set to `0` (punish) while the remaining, higher indices are omitted from the bitvec and therefore default to `1`. The resulting `bitvec_values` mix real 0s with synthetic 1s, so neither `all_1` nor `all_0` holds, and the check is bypassed regardless of what the block-commit's on-chain payout actually did for that address.

This lets a miner construct a `pox_treatment` bitvec that is shorter than the number of reward-set entries, deliberately covering only the low indices with `0` while relying on the out-of-range default of `1` for the rest, causing the consistency check between the header and the burnchain transaction to pass even when it does not truly reflect the block-commit's UTXO outputs for that stacker's remaining slots.

### Impact Explanation
This breaks the equality the network is supposed to enforce: "the header's `pox_treatment` bits for a stacker must match whether that stacker was actually rewarded or burned in the corresponding block-commit." A validator using a truncated bitvec that doesn't match the true reward-set length will silently and permissively fill in missing high-index bits as `1`, defeating the very sanity check whose purpose (per the function's own doc comment) is to prevent a miner from claiming inconsistent PoX treatment. This is a minority-triggerable (single malicious miner) validation-logic bypass on a block-acceptance/rejection rule, which is a High-severity, static-validation-divergence class of finding per the described impact taxonomy (a case where a block that other honest miners/signers would treat as invalid could instead be accepted, or vice versa, depending on how signer-side validation independently reconstructs the bitvec).

### Likelihood Explanation
Any reward cycle where at least one stacker controls more than one reward slot (extremely common, and demonstrated by the existing `pox_treatment` regression test using 3 slots per stacker) creates the multi-index condition needed to exploit the default-fill behavior. No node operator or admin cooperation is required — a single miner constructing its own header/bitvec at block-production time can trigger this on every prepare/reward cycle.

### Recommendation
`check_pox_bitvector` should validate the invariant explicitly and fail closed rather than defaulting missing bits to `true`:
- Reject the block outright if `block_bitvec.len() != rewarded_addresses.len()` (i.e., enforce equality of `pox_treatment.len()` and `RewardSet::pox_treatment_bitvec_len()`), instead of only relying on `BitVec` deserialization to bound the maximum size.
- Remove the `unwrap_or_else(|| { warn!(...); true })` fallback in the `bitvec_value` lookup and instead propagate a hard `ChainstateError::InvalidStacksBlock` when an index is missing from the bitvec.

### Proof of Concept
1. Boot a Nakamoto reward cycle where a stacker's `amount_stacked` spans 3 reward slots (as in the existing `pox_treatment` test), so `rewarded_addresses` contains that address at 3 distinct indices, e.g. `[2, 5, 8]`.
2. As the block-producing miner, construct a `LeaderBlockCommitOp` whose `treatment` marks this stacker as `is_punish()` in reality (e.g., its payout actually went to the burn address for part of the commit outputs).
3. Craft the block header's `pox_treatment` bitvec so it is only 6 bits long (covering indices 0-5, i.e., missing index 8), and set bit 2 = `0` (punish) and bit 5 = `1` (reward) — a legally short but internally inconsistent bitvec relative to the 9+ entry `rewarded_addresses`.
4. Submit the block. `check_pox_bitvector` computes `bitvec_values = [false, true, true]` (bit 8 defaulted to `true` via `unwrap_or_else`), so neither `all_1` nor `all_0` holds, and the punish/reward mismatch check for this stacker is skipped, allowing the block to pass PoX-consistency validation despite representing an inconsistent state versus the true block-commit outputs.
