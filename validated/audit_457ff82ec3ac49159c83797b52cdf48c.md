### Title
Unvalidated sBTC aggregate pubkey in PoX-5 signer-set computation can produce a non-reproducible / crash-diverging sBTC waterfall address - (File: stackslib/src/chainstate/nakamoto/signer_set.rs)

### Summary
`pox_5_compute_and_update_signers` reads the aggregate public key from the configured sBTC registry contract's `get-current-aggregate-pubkey` read-only call and only validates that the returned buffer is exactly 33 bytes long, mirroring the reported bug class of "missing validation on a parameter that is then used to derive consensus state without checking its semantic validity" (analogous to the `USDKG` constructor accepting a zero address without checking it is a meaningful, non-degenerate value).

### Finding Description
In `pox_5_compute_and_update_signers`: [1](#0-0) 
the code fetches `pubkey_buff` and checks only `pubkey_buff.len() != 33`, then converts it into `pubkey_array: [u8; 33]` and passes it straight to `sbtc_pox5_deposit_taproot_output_key`: [2](#0-1) 
That helper strips the compression-prefix byte and treats the remaining 32 bytes as an x-only pubkey without verifying that: (a) the prefix byte is a valid compressed-point marker (`0x02`/`0x03`), or (b) the 32-byte value is actually a valid x-coordinate on the secp256k1 curve. This x-only value is fed into `build_deposit_script`/taproot output-key derivation to compute `sbtc_address`, which becomes part of the consensus-critical `RewardSet::Waterfall` data written into every node's chainstate for that reward cycle: [3](#0-2) 

Because `get-current-aggregate-pubkey` is exposed by an arbitrary/configurable sBTC registry contract (non-mainnet nodes can point at different registry contracts, and the value itself is written by contract logic reachable by any principal that can drive that contract's public functions, e.g. `signers-voting.clar`'s `vote-for-aggregate-public-key`, which validates length (`u33`) but not curve validity): [4](#0-3) 
an attacker who can get a bogus-but-33-byte "pubkey" recorded (e.g. via signer voting reaching threshold, or via a differently-configured registry stub on non-mainnet) can cause the taproot key-derivation step to run on cryptographically invalid input. Depending on the underlying elliptic-curve library used for `sbtc_deposit_taproot_output_key` (not shown in the excerpts inspected), an invalid x-coordinate can either (1) panic/abort node processing — since this runs inside block processing via `check_and_handle_prepare_phase_start`, a panic here would halt/crash any node that reaches this code path deterministically, or worse (2) if different secp256k1 library versions/build configurations across node implementations handle "point not on curve" differently (error vs. silently mapping to a fallback value), nodes could compute different `sbtc_address` values for the same reward cycle, producing a state root divergence for the `RewardSet::Waterfall` structure that is part of chainstate.

### Impact Explanation
This falls in the "High" band: a minority-triggerable divergence in a consensus-relevant static computation (the sBTC waterfall PoX address derivation), bounded to the given reward cycle's signer/reward-set data. If it manifests as a panic, it is a targeted DoS against block processing for the prepare-phase transition; if it manifests as differing derived output keys across node builds/library versions, it produces a non-reproducible piece of consensus state (`sbtc_address` in `RewardSet::Waterfall`), which downstream code relies on for reward-set validation.

### Likelihood Explanation
Reaching this path requires only that the sBTC registry's `get-current-aggregate-pubkey` return a 33-byte buffer that does not decode to a valid curve point at the moment `pox_5_compute_and_update_signers` runs (once per prepare phase after PoX-5 activation). On networks where the registry state is set via `signers-voting.clar`'s length-only check, a minority of signers reaching the vote threshold with a malformed key (or a bug/misconfiguration in the registry contract) is sufficient — no majority or admin/privileged party outside the existing PoX-5 signer-voting mechanism is needed. This is currently unexercised code in this snapshot (PoX-5/Epoch-4.0 scaffolding, per the surrounding comments), so likelihood of it being production-exposed today is unclear, but the missing on-curve validation is a real gap in the code as written.

### Recommendation
Validate the aggregate pubkey immediately after retrieval in `pox_5_compute_and_update_signers`: parse it with a proper secp256k1 public-key type (e.g. `Secp256k1PublicKey::from_slice`/equivalent) and reject the reward-cycle computation (returning a `ChainstateError`) if it is not a valid compressed point, rather than only checking the byte length. Also add the same on-curve validation inside `sbtc_deposit_taproot_output_key`/`sbtc_pox5_deposit_taproot_output_key` in `stackslib/src/chainstate/stacks/sbtc.rs` as defense in depth, and add the equivalent full point-validity check to `signers-voting.clar`'s `vote-for-aggregate-public-key` (currently only length-checked) so invalid keys can never be recorded in the first place.

### Proof of Concept
1. Deploy/point `pox_5_sbtc_registry_contract` (or drive `signers-voting.clar` votes) so that `get-current-aggregate-pubkey` returns a 33-byte buffer whose last 32 bytes are not a valid secp256k1 x-coordinate (e.g., all `0xFF`s), while keeping the leading byte as `0x02`/`0x03` so it looks well-formed.
2. Let the chain reach the start of the next prepare phase after PoX-5 activation, triggering `check_and_handle_prepare_phase_start` → `pox_5_compute_and_update_signers`. [5](#0-4) 
3. Observe that only the length check at line 792 gates the value before it flows into taproot key derivation; verify whether the underlying elliptic-curve call panics or produces divergent output across builds, causing either a block-processing crash or a mismatched `sbtc_address` in the persisted `RewardSet::Waterfall`.

*Note: I could not directly inspect `sbtc_deposit_taproot_output_key`'s internal curve-validation behavior (the file read for `stackslib/src/chainstate/stacks/sbtc.rs` lines 1–88 could not be completed before the tool budget ran out), so whether it panics, errors gracefully, or silently produces a non-deterministic result is unconfirmed and would need to be verified in a live session before treating this as fully proven.*

        coinbase_height: u64,
    ) -> Result<Option<SignerCalculation>, ChainstateError> {
        let current_epoch = clarity_tx.get_epoch();
        if current_epoch < StacksEpochId::Epoch25 {
            // before Epoch-2.5, no need for special handling
            return Ok(None);
        }

        // now, determine if we are in a prepare phase, and we are the first
        //  block in this prepare phase in our fork
        if !pox_constants.is_in_prepare_phase(first_block_height, burn_tip_height.into()) {
            // if we're not in a prepare phase, don't need to do anything
            return Ok(None);
        }

        let Some(cycle_of_prepare_phase) =
            pox_constants.reward_cycle_of_prepare_phase(first_block_height, burn_tip_height.into())
        else {
            // if we're not in a prepare phase, don't need to do anything
            return Ok(None);
        };

        // Dispatch must be cycle-stable: every block of this prepare phase
        // must agree on which pox contract supplies cycle_of_prepare_phase's
        // signer set, regardless of which block first triggers the update.
        // Tip-keyed `active_pox_contract` is wrong here -- it can flip

            pox_constants.active_pox_contract_for_cycle(first_block_height, cycle_of_prepare_phase);

            return Ok(None);
