### Title
Integer-division rounding loses PoX-5 STX-staker rewards permanently when `stx-staker-rewards * PRECISION < cycle-staked-ustx` - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
The `calculate-rewards` flow in `pox-5.clar` computes the per-uSTX reward accumulator with a single fixed-point integer division, `(/ (* stx-staker-rewards PRECISION) cycle-staked-ustx)`, and then immediately treats the *entire* `stx-staker-rewards` amount as accounted-for (folded into `last-accounted-rewards-only`) regardless of whether the division rounded down to zero or lost a remainder. [1](#0-0) 

### Finding Description
`calculate-rewards` is a `define-public` function, callable by any principal, that computes and permanently records the newly accrued rewards for a distribution half-cycle: [2](#0-1) 

After bond distributions consume their share, the remainder is split between the reserve and STX stakers:
```
(reserve-cut (/ (* remaining-rewards RESERVE_RATIO) u10000))
(stx-staker-rewards (- remaining-rewards reserve-cut))
...
(accrued-rewards-per-ustx (if no-stx-stakers
    u0
    (/ (* stx-staker-rewards PRECISION) cycle-staked-ustx)
))
``` [3](#0-2) 

This mirrors exactly the pattern in the external report: a numerator (`stx-staker-rewards`) scaled by a fixed `PRECISION` constant and divided by a large denominator (`cycle-staked-ustx`, the total uSTX staked, which can be enormous — STX total supply is on the order of 1.6e9 STX = 1.6e15 microSTX, and can be much larger when aggregated over many stackers). If `stx-staker-rewards * PRECISION` rounds down to `0` in this integer division (i.e. `stx-staker-rewards < cycle-staked-ustx / PRECISION`), `accrued-rewards-per-ustx` becomes `0`, so no staker ever accrues a claim to that reward increment.

Critically, the code does not compensate for this rounding loss: it still marks the *entire* `gross-accrued-rewards` (minus `reserve-deposit`) as accounted:
```
(var-set last-accounted-rewards-only
    (+ prev-accounted-rewards
        (- gross-accrued-rewards reserve-deposit)))
``` [4](#0-3) 

Because `calculate-rewards` is unprivileged and can be invoked by anyone as soon as a new half-cycle boundary is crossed (gated only by `calculation-height > last-calc`), an attacker can force many small, frequent `calculate-rewards` calls — each carrying a small `gross-accrued-rewards`/`stx-staker-rewards` slice — instead of allowing rewards to accumulate into one large batch. Each small slice is far more likely to round `accrued-rewards-per-ustx` down to zero when `cycle-staked-ustx` is large, permanently and silently destroying that reward increment: it is neither credited to stakers (because `accrued-rewards-per-ustx` is 0) nor left available for a future, larger calculation (because `last-accounted-rewards-only` already advanced past it and `reserve-balance` didn't absorb it either).

This is the direct analog of the `FarmKeeper._collectFees` bug: a `SCALE_FACTOR`/`PRECISION` too small relative to plausible amount/liquidity ratios, exploitable by any unprivileged caller repeatedly triggering the accrual function with small increments to force rounding to zero and permanently lose funds that should have gone to reward recipients.

### Impact Explanation
This falls under the "poison or reward mis-payment bounded to fees" High-impact category: an unprivileged, minority-triggerable caller can force permanent loss of STX-staker rewards through repeated small-increment calls to `calculate-rewards`, with no way to recover the lost fraction. The loss is bounded (per call, at most `cycle-staked-ustx/PRECISION - 1` microSTX of `stx-staker-rewards`) but is a real, silent chain-state reward misallocation reproducible by any node applying the same deterministic (but flawed) arithmetic — it does not cause consensus disagreement (all nodes compute the same wrong result), but it does cause STX stakers to permanently lose rewards they are entitled to.

### Likelihood Explanation
Likelihood is Medium: it requires `cycle-staked-ustx` to be large relative to `PRECISION`, and requires an attacker (or even an accidental frequent caller, since the function is public/permissionless) to trigger `calculate-rewards` at every eligible half-cycle boundary with correspondingly small `stx-staker-rewards` amounts rather than allowing reward accumulation to batch into larger, safer slices. As total value staked in PoX-5 grows, the probability of hitting the rounding-to-zero condition increases.

### Recommendation
Track a fractional remainder (e.g., store the truncated remainder of `(* stx-staker-rewards PRECISION)` modulo `cycle-staked-ustx` and carry it forward into the next `calculate-rewards` call) so that rounding loss is deferred and eventually distributed rather than permanently destroyed, or increase `PRECISION` to a magnitude sufficiently larger than the realistic range of `cycle-staked-ustx` to make rounding-to-zero events negligible, analogous to increasing `SCALE_FACTOR` from `1e12` to `1e18` in the original report.

### Proof of Concept
1. Let `cycle-staked-ustx = 10_000_000_000_000` (10 trillion uSTX, a plausible aggregate stacked amount) and `PRECISION = 1_000_000` (illustrative; exact value should be confirmed against the constant definition in `pox-5.clar`, which was not directly inspected before this analysis had to conclude).
2. An attacker calls `calculate-rewards` immediately at every eligible half-cycle boundary rather than letting rewards batch, so that each call's `stx-staker-rewards` slice is small, e.g. `stx-staker-rewards = 5_000_000` (5 STX-equivalent in microSTX).
3. `accrued-rewards-per-ustx = (5_000_000 * 1_000_000) / 10_000_000_000_000 = 5_000_000_000_000 / 10_000_000_000_000 = 0` (integer division truncates to 0).
4. Despite `accrued-rewards-per-ustx` being `0`, the contract still executes `(var-set last-accounted-rewards-only (+ prev-accounted-rewards (- gross-accrued-rewards reserve-deposit)))`, marking the entire `stx-staker-rewards` slice as accounted for.
5. Repeating step 2–4 across many half-cycles permanently drains reward value that stakers were entitled to, with no compensating credit ever issued, since each slice independently underflows to zero in the fixed-point division.
