### Title
Governance activation of ALLOW_TVM_PRAGUE can silently overwrite pre-existing account/delegated-resource state at a hardcoded system address - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
The `ALLOW_TVM_PRAGUE` committee proposal triggers a one-time deployment of the TIP‑2935 `BlockHashHistory` contract at a fixed, publicly known address (`HISTORY_STORAGE_ADDRESS`). If any unprivileged account already exists at that exact address before the proposal is approved, `HistoryBlockHashUtil.deploy()` converts it in place into a contract account and wipes its delegated-resource accounting fields, rather than refusing to deploy or preserving/settling that state. This mirrors the Mochi bug class: a governance-controlled action reassigns/repurposes an identifier (there, an NFT id-space; here, an account address) and in doing so silently overwrites pre-existing unprivileged state tied to that identifier.

### Finding Description
`ProposalService.process()` handles the `ALLOW_TVM_PRAGUE` proposal type by saving the flag and unconditionally invoking `HistoryBlockHashUtil.deploy(manager)`: [1](#0-0) 

`deploy()` only guards against re-deployment when code/contract already exist at the address, but explicitly treats a pre-existing **account** (an EOA that anyone can create simply by sending TRX to this well-known constant address) as the common case, mutating it in place instead of refusing the operation: [2](#0-1) 

The address is a hardcoded, publicly known constant computed independent of any private key: [3](#0-2) 

Because this address is public and derivable ahead of time, any unprivileged user can, before a `ALLOW_TVM_PRAGUE` proposal passes, activate that address as a normal account (e.g., a simple transfer) and have other unrelated users delegate/freeze resources to it via `FreezeBalanceV2Contract`/`DelegateResourceContract`. The comment block acknowledges the collision is expected and "matches" the CREATE2-collision handling pattern used elsewhere in the VM: [4](#0-3) 

That CREATE2 precedent is `Program.createContractImpl()`, which likewise force-converts an existing account to `Contract` type and unconditionally clears delegated-resource accounting on collision: [5](#0-4) 

The difference is that CREATE2 collisions require the attacker/deployer to control both the salt and the deploying factory contract, so the "victim" state at that specific address is attacker-created and only reachable at low probability by chance for a third party. Here, by contrast, `HISTORY_STORAGE_ADDRESS` is a **single global, deterministic constant** known to everyone in advance of `ALLOW_TVM_PRAGUE` activation, so *any* honest user or delegator could unknowingly interact with (freeze/delegate to) that exact address before the governance-triggered deploy fires, and have their delegated-resource bookkeeping wiped without any settlement when the SRs approve the proposal — analogous to the Mochi report's core issue where a governance-changeable identifier is reused/overwritten and clobbers third-party state that was valid under the old configuration.

### Impact Explanation
When `deploy()` hits the pre-existing-account branch, it calls `updateAccountType(Contract)` and `clearDelegatedResource()` on the account, zeroing its aggregate delegated-resource-in fields while leaving any `DelegatedResourceStore`/`DelegatedResourceAccountIndexStore` entries created by other delegators untouched. This produces a state desync between the (now-zeroed) aggregate counters on the target account and the individual delegation records held by delegators, which can corrupt resource/reward accounting: legitimate `UnDelegateResourceContract` operations by delegators, or bandwidth/energy calculations that rely on the target's aggregate counters, may become inconsistent with the actual outstanding delegation records. Balance/asset state is explicitly preserved by the code (mirroring "preserving balance/asset state" per the comments), but resource-delegation accounting is not settled, which is the specific corruption class flagged by the analog report (overwriting state tied to an identifier when governance repurposes it).

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (1) an attacker or unaware user to activate the exact `HISTORY_STORAGE_ADDRESS` account before the SR committee approves `ALLOW_TVM_PRAGUE` (trivial — a single TRX transfer to a known address, fully unprivileged and RPC-reachable), and (2) some other user delegating/freezing resources to that address in the interim (also unprivileged and plausible since the address looks like an ordinary account to observers who don't know its future special purpose), and (3) the SR committee actually approving `ALLOW_TVM_PRAGUE` (a privileged but expected one-time mainnet event, not attacker-controlled, but deterministic and public in advance). The deploy is designed to run "at most once per chain history," so the exposure window is bounded but real, tied to activation timing that is publicly anticipated.

### Recommendation
In `HistoryBlockHashUtil.deploy()`, before converting a pre-existing account at `HISTORY_STORAGE_ADDRESS`, check whether it has any outstanding delegated-resource state (`getDelegatedFrozenV2BalanceForBandwidth()`/`getDelegatedFrozenV2BalanceForEnergy()`, non-empty `UnfrozenV2List`) or existing delegation index entries, and either refuse to deploy (log and skip, same as the code/contract-collision branch) or properly settle/refund the delegated resources before clearing them, mirroring the safer pattern already partially followed in `Program.createContractImpl()`.

### Proof of Concept
1. Prior to any SR proposal for `ALLOW_TVM_PRAGUE`, an attacker computes/knows `HISTORY_STORAGE_ADDRESS` (`410000f90827f1c53a10cb7a02335b175320002935`) from the public source code.
2. Attacker sends a small TRX transfer to that address, creating a normal `AccountType.Normal` account there.
3. A third-party user calls `DelegateResourceContract`/`FreezeBalanceV2Contract` targeting that address, incrementing its `delegatedFrozenV2BalanceForBandwidth`/`Energy` fields (unprivileged, broadcast transaction).
4. SRs approve the `ALLOW_TVM_PRAGUE` proposal; `ProposalService.process()` calls `HistoryBlockHashUtil.deploy(manager)`.
5. `deploy()` takes the `accountExisting` branch, calling `updateAccountType(Contract)` and `clearDelegatedResource()`, zeroing the aggregated delegation counters on the account while the delegator's own records remain, producing accounting inconsistency reachable purely through normal RPC/broadcast-transaction flows plus a public, deterministic governance event.

  public static void deploy(Manager manager) {
    if (manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS)
        || manager.getContractStore().has(HISTORY_STORAGE_ADDRESS)) {
      logger.warn("TIP-2935: foreign state at {}, skipping deploy",
          Hex.toHexString(HISTORY_STORAGE_ADDRESS));
      return;
    }

    manager.getCodeStore().put(HISTORY_STORAGE_ADDRESS,
        new CodeCapsule(HISTORY_STORAGE_CODE));
    manager.getContractStore().put(HISTORY_STORAGE_ADDRESS,
        new ContractCapsule(HISTORY_STORAGE_CONTRACT));

    AccountCapsule account = manager.getAccountStore().get(HISTORY_STORAGE_ADDRESS);
    boolean accountExisting = account != null;
    if (!accountExisting) {
      account = new AccountCapsule(HISTORY_STORAGE_ACCOUNT);
    } else {
      account.updateAccountType(Protocol.AccountType.Contract);
      account.clearDelegatedResource();
    }
    manager.getAccountStore().put(HISTORY_STORAGE_ADDRESS, account);
