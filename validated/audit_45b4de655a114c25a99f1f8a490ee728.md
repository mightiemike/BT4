Confirmed: any unprivileged account can call `ExchangeCreateContract` to create a bancor-style AMM exchange and become its "creator" [1](#0-0) , and that creator is the only one authorized to later call `ExchangeWithdrawContract` [2](#0-1) . This confirms the withdraw path is reachable by any regular user, not a privileged/trusted role.

### Title
`ExchangeWithdrawContract` provides no slippage/minimum-output protection for the paired token, unlike `ExchangeTransactionContract` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeTransactionContract` (a bancor-style TRC10 AMM swap) lets the caller specify an `expected` minimum-received amount, which is checked in `ExchangeTransactionActuator.doValidate()` before execution [3](#0-2) . In contrast, `ExchangeWithdrawContract`, used by the AMM pool's creator to withdraw liquidity, only specifies `token_id` and `quant` — there is no corresponding "minimum expected" field for `anotherTokenQuant`, the paired token amount the withdrawer will receive [4](#0-3) . That amount is computed purely from the exchange's live balances at execution time via a bonding-curve ratio, with zero bound the caller can enforce [5](#0-4) .

### Finding Description
`ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` as a simple ratio of the exchange's current `firstTokenBalance`/`secondTokenBalance` against the requested `tokenQuant`: [6](#0-5) 
This ratio depends entirely on the pool's state at the moment the transaction executes. Because the exchange balances can be moved by any other account's `ExchangeTransactionContract` trades that are ordered before this withdrawal within the same block (e.g., a sandwiching swap), the withdrawer has no way to guarantee the `anotherTokenQuant` they will actually receive matches what they observed when constructing/signing the transaction.

This directly parallels the reported bug class: the withdrawal function does not let the caller express (and have enforced) their slippage tolerance for the amount received. It is actually a stronger version of the reported issue — `ERC5095` at least specifies a slippage buffer (even if wrong/hardcoded), whereas `ExchangeWithdrawActuator`/`ExchangeWithdrawContract` provides no `expected`/minimum-output field at all, so `doValidate()` cannot reject an execution that would give the withdrawer far less of the paired token than anticipated [7](#0-6) . The only checks present are that the exchange balance is non-zero and sufficient, and a fixed-point precision-loss tolerance ("Not precise enough" 0.0001) — neither protects against adverse price movement [8](#0-7) .

By comparison, `ExchangeTransactionActuator` for trades enforces the exact analog of ERC4626/ERC5095's caller-side slippage check via the `expected` field [3](#0-2) , showing the protocol authors recognized the need for this protection in one exchange-interaction path but omitted it from another.

### Impact Explanation
Any account that creates an AMM pair via `ExchangeCreateContract` (unprivileged, open to all users) and later withdraws liquidity via `ExchangeWithdrawContract` can receive materially less of the paired token than the pool state showed when they built the transaction, if the pool is traded against beforehand in the same block (front-running/sandwiching). Since the contract has no field to specify or enforce a minimum acceptable output, the loss cannot be bounded by the caller — this is a real accounting/settlement issue affecting fund-recovery correctness for a market/exchange primitive, not merely theoretical.

### Likelihood Explanation
Reaching this path requires no privileged role — creating an exchange and withdrawing from it are both open, unprivileged operations [1](#0-0) . An attacker (or MEV-style block producer/witness, who in java-tron's PoS model controls transaction ordering within a block) can trivially observe a pending `ExchangeWithdrawContract` and insert a swap ahead of it to shift the pool ratio, since no on-chain check prevents this. This mirrors the original report's note that the cost to trigger this class of issue is low and the vulnerability is exercised on every use of the affected function.

### Recommendation
Add an `expected`/minimum-output field to `ExchangeWithdrawContract` (paralleling `ExchangeTransactionContract.expected`), and have `ExchangeWithdrawActuator.doValidate()`/`execute()` reject the withdrawal if the computed `anotherTokenQuant` (and/or `tokenQuant` itself, if partial withdrawal amounts can also be affected) is below that caller-specified minimum, exactly as `ExchangeTransactionActuator` already does for trades.

### Proof of Concept
1. Account A calls `ExchangeCreateContract` to create pool P(TokenX, TRX) with balances `X0, Y0`.
2. Account A (or another liquidity party) submits `ExchangeWithdrawContract` for a `tokenQuant` of `TokenX`, expecting to receive `anotherTokenQuant ≈ Y0 * tokenQuant / X0` TRX based on the pool state they observed.
3. Before this transaction is packed, a witness/attacker inserts an `ExchangeTransactionContract` trade against pool P that shifts the ratio unfavorably for TRX (e.g., sells a large amount of TokenX into the pool, depressing TRX reserve relative to TokenX).
4. `ExchangeWithdrawActuator.execute()` (lines 77-89) then computes `anotherTokenQuant` from the now-shifted balances, giving Account A significantly less TRX than expected in step 2, with no field to have prevented or capped this loss.
