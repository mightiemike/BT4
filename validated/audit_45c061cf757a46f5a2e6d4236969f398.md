I'll investigate the codebase areas mentioned (write-set conversion, transaction info construction, storage commit, accumulators, Merkle proofs, restore flows, authenticated API responses) to check for a genuine, locally-provable integrity issue analogous to the reported bug class.## Finding: Backup restore commits unauthenticated write sets to durable storage without binding them to the accumulator-proven `TransactionInfo.state_change_hash`

### Title
Transaction-backup restore persists write sets without verifying `state_change_hash`, allowing state-corrupting restores - (File: `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`)

### Summary
When restoring the "transaction" backup type (as opposed to "transaction_output"), `LoadedChunk::load` deserializes `write_set` bytes directly from the backup archive and stores them in `write_sets`, but only verifies the accompanying `txns`, `events`, and `persisted_aux_info` against the accumulator-proven `TransactionInfo` list — never the write set itself.

### Finding Description
In `LoadedChunk::load`, each record read from the backup file is split into `(txn, aux_info, txn_info, events, write_set)` [1](#0-0) . Verification is then performed by wrapping only `txns`, `events`, and `persisted_aux_info` (not `write_sets`) into a `TransactionListWithProofV2`/`TransactionListWithProof` and calling `.verify()` against the trusted `ledger_info`: [2](#0-1) .

`TransactionListWithProof` (used for transactions, not outputs) has no `write_set` field at all, so its `verify` path can only check transaction hashes, event roots, and the accumulator proof of `TransactionInfo` — it structurally cannot check write sets. By contrast, `TransactionOutputListWithProof::verify` (used for the "transaction_output" backup type) explicitly binds the write set to the ledger by hashing it and comparing to `txn_info.state_change_hash()`: [3](#0-2) .

After loading, `write_sets` is carried through unchanged and eventually persisted directly to the ledger DB via `save_transactions_impl` → `WriteSetDb::put_write_set` [4](#0-3) , and, when the "save before replay" phase is used (`save_before_replay_version` → `restore_handler.save_transactions`), it is used with `kv_replay=true` to recompute committed state directly via `calculate_state_and_put_updates` [5](#0-4) , and separately consumed for the "save, don't replay" flow in `save_before_replay_version` [6](#0-5) .

In both cases, the write set the restoring node trusts is never checked against `txn_info.state_change_hash()`, even though `txn_info` itself was authenticated by `TransactionAccumulatorRangeProof` against a signed `LedgerInfoWithSignatures`. The proof only certifies the hash of `TransactionInfo`, and the invariant that `state_change_hash == hash(write_set)` is supposed to be what ties the write set to that authenticated info — but nothing enforces it in this restore path.

### Impact Explanation
A corrupted, buggy, or maliciously tampered transaction backup archive (the write-set portion of a record) can cause a restoring node to persist an incorrect write set for a given version into `WriteSetSchema`, and — in the KV-replay path — to derive and commit incorrect state values/state tree updates from that write set, all while passing every check the restore code performs. This directly corrupts durable ledger data (the persisted write set and/or derived state) at a version that is otherwise "verified" via range proof, without any error being raised. This falls squarely under committed state/durable ledger data diverging from the correct result during restore.

### Likelihood Explanation
This does not require breaking cryptography — it only requires a backup source (file storage, GCS/S3 bucket, custom `BackupStorage` implementation, or a corrupted/incompletely-validated manifest) to supply a `write_set` value inconsistent with the trusted `txn_info.state_change_hash` for the same record. Because backups are typically fetched from external/replicated storage rather than a fully trust-anchored channel, and because the analogous "transaction_output" restore path already demonstrates this exact hash check is considered a required invariant, the missing check in the "transaction" restore path is a straightforward, reachable gap in normal restore operation.

### Recommendation
In `LoadedChunk::load`, after obtaining `txn_infos`, verify `CryptoHash::hash(&write_set) == txn_info.state_change_hash()` for every `(write_set, txn_info)` pair before accepting the chunk, mirroring the check already performed in `TransactionOutputListWithProof::verify` [3](#0-2) . Ideally, this check should be pushed into a shared verification helper so both the transaction and transaction-output restore/verify paths cannot diverge again.

### Proof of Concept
1. Produce (or tamper with) a "transaction" backup chunk file so that one record's serialized `write_set` differs from the write set that was originally used to compute `txn_info.state_change_hash` (the rest of the record — `txn`, `txn_info`, `events`, `aux_info` — is left untouched and still matches the accumulator proof).
2. Run backup restore (`TransactionRestoreController`) against this manifest with a valid `range_proof`/`ledger_info` for the unmodified fields.
3. `LoadedChunk::load`'s call to `txn_list_with_proof.verify(...)` succeeds because it never inspects `write_sets`.
4. The tampered `write_sets` are passed to `restore_handler.save_transactions` (or `save_transactions_and_replay_kv`), which writes them straight to `WriteSetSchema` (and, in the KV-replay path, folds them into `calculate_state_and_put_updates` to update committed state) — producing a restored database whose durable write-set/state at that version differs from the one actually validated by the ledger's accumulator proof.
