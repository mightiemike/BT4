## Analysis: Imprecise floating-point unit conversion in witness reward/brokerage accounting

The bug report's core concern is that unit conversions implemented with mixed arithmetic (percentage scaling, rate multiplication, division ordering) are error-prone and can silently corrupt accounting. Java-tron has an almost identical pattern in its witness reward-splitting logic, and unlike several sibling calculations in the same codebase, it was never migrated to an exact-arithmetic path.

### Title
Floating-point brokerage-rate conversion in witness reward accounting can produce non-deterministic/imprecise SR reward splits - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payReward` converts the witness's integer brokerage percentage (0–100) into a `double` rate and multiplies it by the reward `value` (denominated in SUN) to compute the operator/voter split of block rewards, transaction-fee rewards, and standby-witness pay. This mirrors exactly the reported anti-pattern of doing financial unit conversion via `double` instead of exact integer/BigInteger math.

### Finding Description
`payReward` is: [1](#0-0) 

```java
private void payReward(byte[] witnessAddress, long value) {
  long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
  int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
  double brokerageRate = (double) brokerage / 100;
  long brokerageAmount = (long) (brokerageRate * value);
  value -= brokerageAmount;
  delegationStore.addReward(cycle, witnessAddress, value);
  adjustAllowance(witnessAddress, brokerageAmount);
}
```

This function is invoked from three reward-distribution entry points reached every block/cycle during normal protocol operation: [2](#0-1) , including the standby-witness payout loop that additionally computes `(double) totalPay / voteSum` and casts `w.getVoteCount() * eachVotePay` back to `long` per witness — the same "confusing chained unit conversion" shape flagged in the report (rate derivation, then multiply, then truncate) at [3](#0-2) .

The rest of the reward-accounting subsystem, by contrast, deliberately uses exact `BigInteger` arithmetic for the "new algorithm" VI-based reward delta to avoid exactly this class of precision loss: [4](#0-3) . The codebase has also gone through explicit "hardening" passes replacing `double`/naive integer math with `BigInteger`/`BigDecimal` in analogous places — e.g. `RepositoryImpl.calculateGlobalEnergyLimit` gated by `hardenResourceCalculation()` [5](#0-4) , `EnergyProcessor.scaleByRate` gated by `hardenCalculation()` [6](#0-5) , and the `ExchangeProcessor` → `SafeExchangeProcessor` migration to `BigDecimal` [7](#0-6) . `MortgageService.payReward`, however, has no such hardened counterpart or feature flag — it unconditionally performs the floating-point conversion in production, confirmed by the absence of any `allowHarden*`/`disableJavaLangMath` guard in the file.

### Impact Explanation
Because `double` cannot exactly represent most `brokerage/100` fractions, and IEEE-754 multiply-then-truncate-to-`long` rounds non-deterministically with respect to the mathematically exact integer computation, the SR-operator vs. voter-pool split of every block reward, transaction-fee reward, and standby-witness payment can differ by 1+ SUN from the exact `brokerage * value / 100` result. This is a real, protocol-level accounting computation that runs on every full node for every reward cycle — a persistent bias here (rounding always toward the operator or always toward the pool depending on IEEE-754 truncation direction) causes drift of value between the reward pool (`delegationStore.addReward`) and the witness's own allowance (`adjustAllowance`) over the life of the chain, i.e., a slow, cumulative asset/accounting-corruption effect on witness/voter reward totals.

### Likelihood Explanation
This is not attacker-triggered but is executed unconditionally as part of consensus-driven reward accounting on every full node in the network, so any precision mismatch is realized on every applicable payment, not just under adversarial input. The likelihood of the underlying arithmetic imprecision manifesting is effectively 100% for brokerage values that don't divide evenly (e.g. any brokerage not a multiple that yields an exact binary fraction), though the per-payment magnitude is small (sub-SUN to low-SUN rounding error).

### Recommendation
Replace the `double`-based brokerage rate conversion with exact integer/`BigInteger` math consistent with the rest of the reward pipeline, e.g.:
```java
long brokerageAmount = BigInteger.valueOf(value)
    .multiply(BigInteger.valueOf(brokerage))
    .divide(BigInteger.valueOf(100))
    .longValueExact();
```
and apply the same fix to `payStandbyWitness`'s `eachVotePay`/`pay` computation. This should be done consistently with the "hardened calculation" pattern already used elsewhere in the codebase (`hardenCalculation()`/`allowHarden*` flags plus `BigInteger`/`BigDecimal`), ideally gated behind a chain-parameter activation to preserve historical determinism, mirroring how `SafeExchangeProcessor` and `RepositoryImpl`'s hardened paths were introduced.

### Proof of Concept
For `brokerage = 33`, `value = 100`: exact split is `33 * 100 / 100 = 33` to the operator, `67` to the pool. With the current code: `brokerageRate = 33.0/100 = 0.33` (not exactly representable in binary), `brokerageAmount = (long)(0.33 * 100)`. Depending on binary representation error, `0.33 * 100` can evaluate to `32.999999999999996`, truncating to `32` instead of the exact `33`, silently shifting 1 SUN from the operator's allowance into the delegation reward pool for that cycle — repeated over every reward payment across the chain's lifetime.

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
