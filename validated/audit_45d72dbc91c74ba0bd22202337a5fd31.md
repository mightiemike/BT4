## Title
Sandwichable liquidity `Inject`/`Withdraw` operations in the on-chain Bancor-style Exchange (no slippage/minOut protection) - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Java-tron implements an on-chain Bancor-formula AMM ("Exchange") where any account can swap tokens via `ExchangeTransactionContract`, while only the pool creator can add/remove liquidity via `ExchangeInjectContract`/`ExchangeWithdrawContract`. Unlike the swap contract, which carries a caller-supplied `expected` (minOut) field, the inject/withdraw contracts have no slippage-bound field at all, and their proportional-amount computation is derived purely from the exchange pool's current spot balances. Any unprivileged account can front-run a pending inject/withdraw transaction with an `ExchangeTransactionContract` swap to skew the pool ratio, forcing the pending operation to execute at an unfavorable ratio, then back-run to reverse the swap and capture the extracted value — the same sandwich pattern described in the reference report for rETH `stake`/`unstake`/`rebalanceToWeight`.

### Finding Description
`ExchangeTransactionContract` includes an `expected` field that the actuator enforces (`anotherTokenQuant < tokenExpected` reverts), giving swap callers slippage protection: [1](#0-0) 

However, `ExchangeInjectContract`/`ExchangeWithdrawContract` carry only `owner_address`, `exchange_id`, `token_id`, `quant` — no minimum/expected counterpart amount: [2](#0-1) 

`ExchangeInjectActuator.execute` computes the counterpart amount strictly from the *current* pool ratio at execution time, with no bound supplied by the caller: [3](#0-2) 

`ExchangeWithdrawActuator.execute` does the same for withdrawals: [4](#0-3) 

The only access restriction on Inject/Withdraw is that the caller must be the exchange creator: [5](#0-4) [6](#0-5) 

But the swap (`ExchangeTransactionActuator`) that can be used to manipulate the pool ratio is open to any account with no creator restriction, so any unprivileged attacker can broadcast the front-run/back-run swaps: [7](#0-6) 

The bonding-curve pricing used for these swaps (`ExchangeCapsule.transaction`, backed by `ExchangeProcessor`/`SafeExchangeProcessor`) is a pure function of current pool balances — i.e., a manipulable spot price with no TWAP or oracle protection: [8](#0-7) 

This is structurally identical to the referenced rETH bug class: an operation (`stake`/`unstake`/`rebalanceToWeight` there, `Inject`/`Withdraw` here) that derives amounts from the AMM's instantaneous spot balances without a caller-provided minOut, while the sibling swap operation does have that protection. An attacker can:
1. Observe a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction from the creator in the mempool.
2. Front-run with an `ExchangeTransactionContract` swap that shifts `firstTokenBalance`/`secondTokenBalance` ratio.
3. Let the creator's inject/withdraw execute at the skewed ratio, causing them to deposit disproportionately more value (or withdraw disproportionately less) than the true fair-value.
4. Back-run with the reverse swap to restore the ratio and capture the extracted value, paying only the AMM's ~0.05%-equivalent curve fee, similar to the rETH PoC math in the report.

### Impact Explanation
The exchange creator (an account holder, not a privileged system role) suffers direct, deterministic value extraction on every `Inject`/`Withdraw` they broadcast, mirroring the "asset or accounting corruption" impact class. Any TRC10-token/TRX Bancor pool created via `ExchangeCreateContract` is exposed; the attack is purely economic and requires no bug in signature/permission handling, only unprotected proportional math combined with attacker-controlled spot-price manipulation.

### Likelihood Explanation
The attack requires only mempool visibility of a pending inject/withdraw transaction and the ability to broadcast ordinary `ExchangeTransactionContract` swaps — both are unprivileged, anonymous-reachable actions. No special permission, leaked key, or malicious peer/node role is needed; the attacker is a normal network participant exploiting the missing slippage bound, exactly as in the analog report.

### Recommendation
Add an `expected`/`min_another_token_quant` field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring the field already present on `ExchangeTransactionContract`), and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` before mutating balances, so callers can bound the counterpart amount and revert on unfavorable pool-ratio manipulation.

### Proof of Concept
1. Creator broadcasts `ExchangeInjectContract{exchangeId, tokenId=firstToken, quant=Q}` intending to inject `Q` of firstToken at the current pool ratio.
2. Attacker sees this in the mempool and front-runs with `ExchangeTransactionContract` selling firstToken into the pool, shifting `firstTokenBalance`/`secondTokenBalance` (per `ExchangeCapsule.transaction`, `chainbase/.../ExchangeCapsule.java:124-158`).
3. Creator's inject executes: `anotherTokenQuant = floorDiv(secondTokenBalance * Q, firstTokenBalance)` at the now-skewed ratio (`ExchangeInjectActuator.java:71-83`), forcing the creator to contribute an unfavorable amount of secondToken with no minOut check possible (no such field exists in `ExchangeInjectContract`).
4. Attacker back-runs with the reverse swap, restoring the ratio and pocketing the difference minus the bonding-curve fee — analogous to the ETH/rETH sandwich profit computed in the reference report.
