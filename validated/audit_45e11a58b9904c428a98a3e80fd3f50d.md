### Title
Post-execution re-fetch of `ContractCapsule` in `pay()` diverges from the pre-execution snapshot used to compute the caller/creator energy split - ([File: chainbase/src/main/java/org/tron/core/db/TransactionTrace.java])

### Finding Description
`TransactionTrace.pay()` reads `contractCapsule.getConsumeUserResourcePercent(...)` and `contractCapsule.getOriginEnergyLimit()` from `contractStore.get(callContract.getContractAddress())` **after** `exec()` has already run to completion: [1](#0-0) 

`exec()` invokes `runtime.execute(transactionContext)`, which drives `VMActuator`, whose `Repository` (`rootRepository`) is created once at the start of the call and is only committed back to the persistent `ContractStore`/`AccountStore` at the end of VM execution. Crucially, the caller/creator energy-limit split that gates how much energy a non-owner caller vs. the contract's origin account may spend is computed **before** any opcode executes, from the *same* store but at the *pre-execution* snapshot: [2](#0-1) 

Because Tron supports `SELFDESTRUCT`/`SUICIDE2` and `CREATE2` re-deployment to the same address within a single transaction (demonstrated by `testCreate2SuicideToAccount`/`testCreate2SuicideToBlackHole` in `FreezeTest.java` and by `Create2Test.java`), a contract can destroy itself and redeploy new code (with a new, internally-defaulted `consumeUserResourcePercent`/`originEnergyLimit`, since those fields are only explicitly supplied on the top-level `CreateSmartContract` transaction, not on an internal `CREATE2` opcode) at the same address in the middle of the same call: [3](#0-2) [4](#0-3) 

The result is that `getTotalEnergyLimitWithFixRatio` sizes the transaction's caller/creator energy budget using the *old* `ContractCapsule` fields, while `TransactionTrace.pay()` later applies the *new*, post-redeploy `ContractCapsule` fields to actually split the metered `energyUsageTotal` between `origin` and `caller` via `ReceiptCapsule.payEnergyBill`: [5](#0-4) 

No code path re-validates or pins the percent/limit values between the pre-execution sizing step and the post-execution billing step; they are two independent reads of the same mutable on-disk record separated by attacker-controlled state mutation.

### Impact Explanation
An attacker who controls (or deploys) a contract can arrange for its own code to be destroyed and redeployed at the same address mid-transaction, changing `consumeUserResourcePercent`/`originEnergyLimit`. Because the energy *ceiling* granted to the transaction (which determines how much of the contract origin's frozen energy could be tapped, and thus how much VM work could run "for free" from the origin account's perspective) is computed from the pre-redeploy percent, while the actual fee/energy split charged in `pay()` uses the post-redeploy percent, the amount actually billed to `origin` vs `caller` can diverge from the ratio that was used to authorize how much energy the call was allowed to consume. This can result in the contract's origin account being charged an unintended share of energy fees (or, conversely, the caller being under-charged relative to the budget it was granted), a scoped billing/fee-split correctness defect.

### Likelihood Explanation
Requires only an unprivileged deployer to write a contract whose triggerable function makes a nested self-destructing/`CREATE2`-redeploy sub-call to its own address — no special privilege, admin action, or off-chain access is needed. The redeploy-at-same-address mechanic is already exercised by the codebase's own test suite (`FreezeTest`, `Create2Test`), confirming the mechanism is reachable through normal `TriggerSmartContract` transactions.

### Recommendation
Capture the `ContractCapsule` (or the specific `consumeUserResourcePercent`/`originEnergyLimit` values) used by `VMActuator.getTotalEnergyLimitWithFixRatio`/`getTotalEnergyLimitWithFloatRatio` into the `TransactionContext`/`ReceiptCapsule` at the time the energy limit is computed, and have `TransactionTrace.pay()` consume that captured snapshot instead of re-reading `contractStore.get(...)` after execution. This guarantees the percent/limit used to size the transaction and the percent/limit used to bill it are always the same value.

### Proof of Concept
Java integration test plan (extends existing `TransactionTraceTest`/`Create2Test` infrastructure):
1. Deploy contract `A` at address `X` with `consumeUserResourcePercent = 30`, `originEnergyLimit = 1_000_000`, funded origin account with frozen energy.
2. `A`'s fallback/trigger function performs: `SUICIDE`-style self-destruct is not directly re-enterable in the same call frame for `A` itself, so instead have `A` be created via a `Factory` using `CREATE2`; `A`'s triggered method calls `SUICIDE2` on itself and, later in the same top-level transaction (via a second internal call orchestrated by the `Factory`), the `Factory` `CREATE2`-redeploys new code `A'` to the same address `X` with default `consumeUserResourcePercent = 0`.
3. Instrument/log (or use a test-only hook) the `consumeUserResourcePercent`/`originEnergyLimit` values read inside `VMActuator.getTotalEnergyLimitWithFixRatio` at line 727-730, and separately capture the values read inside `TransactionTrace.pay()` at line 248-252.
4. Assert that the two captured percent values differ (`percentAtLimitComputation != percentAtBilling`).
5. Assert that `ReceiptCapsule.payEnergyBill`'s resulting `originEnergyUsage`/`callerEnergyUsage` split does not correspond to the ratio that `getTotalEnergyLimitWithFixRatio` used when authorizing `creatorEnergyLimit`/`callerEnergyLimit`, demonstrating the billing/authorization mismatch.
