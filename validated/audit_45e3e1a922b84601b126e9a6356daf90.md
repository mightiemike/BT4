### Title
Missing verification that `shop` parameter matches session-token `dest` in `tokenExchange` allows cross-tenant token exchange - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Summary
This is the same bug class as the reported issue: two independently-derived values that should be reconciled before being used together are instead consumed without a consistency check. In the `Multicall` report, `msg.value` (fixed at request time) and `price` (recomputed from mutable `entryFee` at execution time) are never compared, so funds are misallocated. In `shopify-app-js`, `tokenExchange()` accepts a caller-supplied `shop` string and a `sessionToken` (JWT) as two independent inputs, decodes/validates the JWT's signature/expiry/audience, but never checks that the JWT's `dest` claim matches the supplied `shop` before using `shop` to build the outbound OAuth URL.

### Finding Description
`tokenExchange` in `packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts` does: [1](#0-0) 

It calls `decodeSessionToken(config)(sessionToken)` purely to validate the JWT (signature, `exp`/`nbf`, `aud`), but discards the returned payload — it never reads `payload.dest` and never compares it to the `shop` argument. The `shop` value used to build the request URL (`https://${cleanShop}/admin/oauth/access_token`) comes entirely from the caller-supplied `shop`, only checked for domain-format validity via `sanitizeShop`, not for correspondence to the token's actual `dest`.

The `shop` value that reaches `tokenExchange` in `shopify-app-remix`/`shopify-app-express` is taken from an untrusted request query parameter, not derived from the JWT: [2](#0-1) 

and is passed straight through the `TokenExchangeStrategy.exchangeToken` → `api.auth.tokenExchange` call chain: [3](#0-2) 

Contrast this with the equivalent code path in `admin/authenticate.ts`, where session-token authentication (a different strategy) *does* derive `shop` from the validated JWT `dest` rather than from the query string: [4](#0-3) 

This shows the library is aware that `shop` must be derived from the verified token in security-sensitive contexts — but the `tokenExchange` code path does not enforce that invariant itself; it relies entirely on the caller to have already reconciled `shop` with the token, and on Shopify's server-side OAuth endpoint to reject a mismatched `subject_token`/domain combination.

### Impact Explanation
If a consumer of `shopify-app-js` (or a future internal caller) ever derives `shop` from a source other than the token's `dest` (e.g., a URL parameter, as the remix/express integrations already do for the `id_token` flow), a client can present a validly-signed session token for shop A together with an arbitrary `shop=B` value. `tokenExchange` will happily build and send a token-exchange request to `https://B/admin/oauth/access_token` using subject_token bound to A. Locally, the library performs no defense-in-depth check that would catch this before making the outbound request. The severity is bounded by Shopify's own OAuth server presumably rejecting a `dest` mismatch, but the client-side library provides no verification of its own — matching the reported bug's core flaw of "one value used without validating its relationship to another value that was supposed to constrain it."

### Likelihood Explanation
Reachable by any authenticated app user session (a normal, unprivileged merchant/customer browser session) that can supply an arbitrary `shop` query parameter alongside a session token — this is exactly the `token-exchange` authentication strategy used for embedded-app / non-`ShopifyAdmin`-distribution flows, invoked on every unauthenticated admin request. No privileged actor or leaked secret is required; only a normal session token (obtainable by any installed merchant) and control of the `shop` query parameter.

### Recommendation
In `tokenExchange` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), capture the payload returned by `decodeSessionToken` and assert that `new URL(payload.dest).hostname` equals the sanitized `shop` argument before constructing the outbound request; throw an `InvalidJwtError`/`InvalidOAuthError` on mismatch. This mirrors the recommended fix pattern in the report: validate the relationship between the two independently-supplied values before using them together, rather than trusting the caller to have already reconciled them.

### Proof of Concept
1. An attacker who has a valid embedded-app session (session token signed for `shopA.myshopify.com`, i.e. `dest=https://shopA.myshopify.com`) intercepts/controls a request to the app's token-exchange endpoint.
2. The attacker sets the `shop` query parameter to `shopB.myshopify.com` while keeping the legitimately-obtained `sessionToken` for shop A.
3. `getShopFromRequest`/`getSessionTokenContext` pass `shop = "shopB.myshopify.com"` and the shop-A session token into `TokenExchangeStrategy.exchangeToken` → `api.auth.tokenExchange`.
4. `tokenExchange` validates the JWT signature/expiry only, ignoring `dest`, and sends a token-exchange POST to `https://shopB.myshopify.com/admin/oauth/access_token` with `subject_token` bound to shop A.
5. Whether this succeeds in obtaining a token for shop B depends entirely on Shopify's server-side validation of `dest` vs. domain — the `shopify-app-js` library itself performs no such check, so the library's client-side security posture doesn't defend the app against this scenario independently of the Shopify backend's behavior.
