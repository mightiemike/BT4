### Title
`AccountsDb::construct_candidate_clean_keys` consumes the full-snapshot-advance flag even when the corresponding cleanup is only partially applied, permanently deferring zero-lamport purge/sweep for the missed range - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb` uses a dirty flag, `latest_full_snapshot_slot_advanced_since_clean`, to decide when `clean_accounts()` should drain `zero_lamport_accounts_to_purge_after_full_snapshot` and run `sweep_slots_after_snapshot()` (which purges fully-tombstoned storages and detects newly-shrinkable storages up to the latest full snapshot slot). The flag is unconditionally cleared (`swap(false, ...)`) as soon as the block is entered, but the actual work inside that block is gated by `max_clean_root_inclusive`, which can be capped below the latest full snapshot slot by an in-flight accounts scan. When that happens, entries/slots beyond the capped root are left unprocessed, yet the flag that would have re-triggered this work on a later `clean_accounts()` call has already been consumed and won't be set again until the next call to `set_latest_full_snapshot_slot()` (i.e., the next full snapshot).

### Finding Description
`AccountsDb::set_latest_full_snapshot_slot` updates `latest_full_snapshot_slot` and then unconditionally sets `latest_full_snapshot_slot_advanced_since_clean = true`: [1](#0-0) 

The comment on the field states the intended contract explicitly: "Set by `set_latest_full_snapshot_slot` when the snapshot advances. Read and cleared by clean": [2](#0-1) 

Inside `construct_candidate_clean_keys`, the flag is read-and-cleared via `swap(false, Ordering::Acquire)` as the left-hand side of an `&&` expression, so the swap executes unconditionally the moment `clean_accounts()` reaches this point: [3](#0-2) 

The body of that block does two things gated differently:
1. It drains `zero_lamport_accounts_to_purge_after_full_snapshot` via `retain`, but an entry is only actually processed (purged) when `max_clean_root_inclusive >= slot && latest_full_snapshot_slot >= slot`. Entries whose `slot` exceeds `max_clean_root_inclusive` are simply kept in the set for "later."
2. It calls `sweep_slots_after_snapshot(last_swept_full_snapshot_slot, latest_full_snapshot_slot)`, defined here: [4](#0-3) 

`max_clean_root_inclusive` is computed in `clean_accounts()` via `self.max_clean_root(...)`, which folds in `scan_tracker.min_ongoing_scan_root()` — the minimum root pinned by any currently in-flight `scan_accounts` call: [5](#0-4) 

`scan_accounts` (the backing implementation for account scans such as `getProgramAccounts`) registers a `ScanGuard` that pins the scan's root in `ongoing_scan_roots` for the scan's duration, explicitly to prevent clean from advancing past it: [6](#0-5) [7](#0-6) 

So: if an ordinary, unprivileged scan is in flight when `clean_accounts()` runs, `max_clean_root_inclusive` can be pinned well below `latest_full_snapshot_slot()`. In that single `clean_accounts()` call, the flag is consumed (cleared) exactly once, but the drain/sweep work it was supposed to gate only completes for the capped range. The remaining zero-lamport entries and un-swept slot range are left pending, and — unlike a `retry`/`catch`-based repair — nothing will re-enter this code block on the next `clean_accounts()` call (even once the scan finishes and `max_clean_root_inclusive` grows) because the boolean has already been reset to `false`. The block is only re-armed by the next call to `set_latest_full_snapshot_slot()`, i.e., the next full-snapshot cycle.

This mirrors the reported Solidity pattern precisely: a setter (`set_latest_full_snapshot_slot`) unconditionally flips a completion-tracking flag, a dependent state-catch-up routine (`construct_candidate_clean_keys`'s drain/sweep, analogous to `melt`) can be only partially executed due to an orthogonal guard (`max_clean_root_inclusive`/`min_ongoing_scan_root`, analogous to `notFrozen`), and the flag consumption is not conditioned on that routine's actual completion (no re-arming on partial failure), so the tracking state (`last_swept_full_snapshot_slot`, `zero_lamport_accounts_to_purge_after_full_snapshot`) is left stale relative to what the flag implied.

### Impact Explanation
The consequence is not incorrect account data (the zero-lamport purge/sweep gating exists precisely to preserve incremental-snapshot correctness), but rather that the recovery/catch-up mechanism is silently disabled until the next full snapshot slot advances. This means:
- Fully-tombstoned storages that could otherwise be purged immediately (via `sweep_slots_after_snapshot`'s tombstone-purge path) are instead retained until the next full snapshot occurs.
- Storages that became newly shrinkable due to zero-lamport reclaim are not added to `shrink_candidate_slots` until the next full snapshot occurs.
- `zero_lamport_accounts_to_purge_after_full_snapshot` retains stale entries for an extended, unbounded-by-clean-cadence period.

This results in disproportionate accumulation of otherwise-reclaimable storage/index entries on an honest validator, i.e., a "disproportionate storage cost" outcome, for a duration that can span a full snapshot interval instead of the next `clean_accounts()` pass.

### Likelihood Explanation
Triggering the race requires only that any in-flight account scan (via `scan_accounts`, which backs common read paths, not solely large unfiltered `getProgramAccounts` calls) hold a pinned `min_ongoing_scan_root` lower than `latest_full_snapshot_slot()` at the moment `clean_accounts()` executes — a condition that is a normal, expected part of production operation (clean and scans are documented to race against each other; see the `ScanGuard` comment about clean happening concurrently with scans). No malicious or privileged behavior is required.

### Recommendation
Do not clear `latest_full_snapshot_slot_advanced_since_clean` unconditionally on entry. Only clear it once the drain/sweep has fully covered up to `latest_full_snapshot_slot` (e.g., re-set it to `true` if `max_clean_root_inclusive < latest_full_snapshot_slot` after the retain/sweep step, or track completion per-slot rather than via a single boolean), so a capped `max_clean_root_inclusive` cannot cause the catch-up logic to be skipped indefinitely until the next full snapshot.

### Proof of Concept
1. Start a long-lived `scan_accounts` (e.g., via an RPC read at an older commitment) that pins `min_ongoing_scan_root` to slot `S1`.
2. While the scan is active, trigger a full snapshot so `set_latest_full_snapshot_slot(S2)` is called with `S2 > S1`, setting `latest_full_snapshot_slot_advanced_since_clean = true`.
3. Let `clean_accounts()` run: `max_clean_root_inclusive` resolves to `min(S1, proposed_root)` (`accounts_db.rs:1453-1465`), so it is capped at `S1`. The flag is swapped to `false` at `accounts_db.rs:1688-1690`, but only entries/slots `<= S1` are drained/swept; entries/slots in `(S1, S2]` remain pending in `zero_lamport_accounts_to_purge_after_full_snapshot`/unswept.
4. End the scan (now `min_ongoing_scan_root` no longer limits the root) and call `clean_accounts()` again with a root `>= S2`. Because the flag is already `false`, the entire block at `accounts_db.rs:1688-1712` is skipped, so the pending slots in `(S1, S2]` are still not purged/swept — despite the constraint that made them ineligible having been removed.
5. Observe that `last_swept_full_snapshot_slot` stays at its pre-`S1` value and `zero_lamport_accounts_to_purge_after_full_snapshot` keeps the deferred entries until the next `set_latest_full_snapshot_slot()` call, confirming the missed catch-up.

    /// Loop through slots in `[last_swept_full_snapshot_slot + 1, latest_full_snapshot_slot]` and
    /// re-examine each storage now that a full snapshot has advanced past its slot:
    /// 1) if it holds only tombstones, purge it directly; or
    /// 2) if its dead zero-lamport accounts made it shrinkable, add it to the shrink candidates.
    ///
    /// Advances `last_swept_full_snapshot_slot` to `latest_full_snapshot_slot` on completion.
    ///
    /// Returns the count of storages that were added to the shrink candidates set.
    fn sweep_slots_after_snapshot(
        &self,
        last_swept_full_snapshot_slot: Slot,
        latest_full_snapshot_slot: Slot,
    ) -> u64 {
        let start = last_swept_full_snapshot_slot.saturating_add(1);

        let mut added_to_shrink_count = 0;
        {
            // Held for the scan. Safe because the only paths that take this lock in production
            // validator code run in earlier/later phases of the same AccountsBackgroundService
            // iteration, never concurrently with clean_accounts.
            let mut shrink_candidates = self.shrink_candidate_slots.lock().unwrap();
            for slot in start..=latest_full_snapshot_slot {
                if let Some(store) = self.storage.get_slot_storage_entry(slot) {
                    if store.has_only_tombstones() {
                        // Now just contains tombstones and no live index entries: purge
                        self.purge_dead_slots_from_storage(
                            iter::once(&slot),
                            &self.clean_accounts_stats.purge_stats,
                        );
                    } else if self.is_shrinking_productive(&store)
                        && self.is_candidate_for_shrink(&store)
                        && shrink_candidates.insert(slot)
                    {
                        added_to_shrink_count += 1;
                    }
                }
            }
        }

        self.last_swept_full_snapshot_slot
            .store(latest_full_snapshot_slot, Ordering::Relaxed);
        added_to_shrink_count
    }

impl<'a> ScanGuard<'a> {
    /// Begin a scan: checks the bank hasn't been removed and pins `max_root` in
    /// `ongoing_scan_roots`.
    ///
    /// Returns `None` if the bank has already been removed.
    ///
    /// `max_root_inclusive_fn` is called while holding the `ongoing_scan_roots` write lock.
    pub(crate) fn try_new(
        scan_tracker: &'a ScanTracker,
        scan_bank_id: BankId,
        max_root_inclusive_fn: impl FnOnce() -> Slot,
    ) -> Option<Self> {
        {
            let locked_removed_bank_ids = scan_tracker.removed_bank_ids.lock().unwrap();
            if locked_removed_bank_ids.contains(&scan_bank_id) {
                return None;
            }
        }

        let max_root_inclusive = {
            let mut w_ongoing_scan_roots = scan_tracker
                // This lock is also grabbed by clean_accounts(), so clean
                // has at most cleaned up to the current `max_root` (since
                // clean only happens *after* BankForks::set_root() which sets
                // the `max_root`)
                .ongoing_scan_roots
                .write()
                .unwrap();
            // `max_root()` grabs a lock while
            // the `ongoing_scan_roots` lock is held,
            // make sure inverse doesn't happen to avoid
            // deadlock
            let max_root_inclusive = max_root_inclusive_fn();
            if let Some(min_ongoing_scan_root) =
                ScanTracker::min_ongoing_scan_root_from_btree(&w_ongoing_scan_roots)
                && min_ongoing_scan_root < max_root_inclusive
            {
                let current = max_root_inclusive - min_ongoing_scan_root;
                scan_tracker
                    .max_distance_to_min_scan_slot
                    .fetch_max(current, Ordering::Relaxed);
            }
            *w_ongoing_scan_roots.entry(max_root_inclusive).or_default() += 1;
            max_root_inclusive
        };
