### Title
Gateway/mempool admit transactions whose L2 gas amount can exceed the batcher's block `sierra_gas`/`proving_gas`/`receipt_l2_gas` capacity, permanently freezing the sender's nonce - (File: crates/apollo_gateway/src/stateless_transaction_validator.rs)

### Summary
The Notional finding is a class of bug where a protocol enforces a threshold ("reduce debt below `minBorrowSize`, or wipe it entirely") that is checked at one stage (`getLiquidationFactors`) but not reconcilable with a hard, unavoidable revert enforced at another stage (`deleverageAccount`'s `checkMinBorrow`), producing states that can never be resolved. I looked for an analogous "threshold checked in one place, enforced irreconcilably in another place" pattern reachable by an ordinary transaction sender in the sequencer, focused on gateway admission vs. block-building/bouncer capacity enforcement.

### Finding Description
Transaction admission happens in two independent places with two independent, non-reconciled limits:

1. `StatelessTransactionValidator::validate_resource_bounds` in the gateway checks only that `l2_gas.max_price_per_unit >= min_gas_price` and that `l2_gas.max_amount <= config.max_l2_gas_amount` (and skips this amount check entirely for `Declare` transactions) [1](#0-0) .
2. The mempool's admission path performs nonce/fee/capacity-in-bytes checks but never checks a transaction's resource bounds against the batcher's `BouncerConfig.block_max_capacity` (the actual per-block ceiling for `sierra_gas`, `proving_gas`, `receipt_l2_gas`, `n_events`, `state_diff_size`, etc., configured independently at [crates/apollo_node/resources/config_schema.json:91-150]) [2](#0-1) .
3. The only place that ever compares a transaction's actual/declared resource weights against `block_max_capacity` is deep inside block building, via `Bouncer::try_update` / `verify_tx_weights_within_max_capacity`, which returns `TransactionExecutionError::TransactionTooLarge` if the transaction's weights exceed `block_max_capacity` [3](#0-2) [4](#0-3) .

Because `max_l2_gas_amount` (gateway config) and `block_max_capacity` (batcher/bouncer config) are separate, independently configurable values with no cross-validation between them, and because `Declare` transactions skip the `max_l2_gas_amount` check altogether [5](#0-4) , it is possible for a transaction (or a chain of resource-heavy state writes/events/builtins accounted for in `BouncerWeights`, which is not fully reducible to a single "max_l2_gas_amount" figure — e.g. `n_events`, `message_segment_length`, `state_diff_size`) to pass all gateway and mempool checks yet be individually larger than `block_max_capacity`, i.e., exceed what any single block can ever hold — exactly the `TransactionTooLarge` case shown in the tests [6](#0-5) [7](#0-6) .

Because Starknet requires strict, in-order nonce execution per account (the gateway itself enforces `account_nonce <= incoming_tx_nonce <= max_allowed_nonce`, and the batcher/OS execute nonces sequentially) [8](#0-7) , once such an oversized transaction occupies the lowest pending nonce for an account, it can never be executed by any batcher/block builder (it will always raise `BlockFull`/`TransactionTooLarge` and be skipped or rejected — see `TransactionExecutorError::BlockFull`/`TransactionTooLarge` and the halt-on-no-room behavior in `try_update`/`execute_txs`) [9](#0-8) [10](#0-9) . All subsequent transactions from that account, no matter how small, are blocked behind that nonce forever, because gap/ordering logic in the mempool treats a lower stuck transaction as "not yet executable" indefinitely [11](#0-10) .

### Impact Explanation
This is analogous to the Notional bug's "account is always ineligible for liquidation" deadlock: a legitimate, unprivileged, single-transaction-reachable action creates a state (an over-capacity transaction occupying the account's lowest pending nonce) that can never be resolved by the normal transaction-processing pipeline. The affected account becomes permanently unable to get any transaction included — a partial/no-progress "deadlock" analogous to "partial liquidations are not possible." Depending on deployment (a single such transaction could also degrade block packing efficiency, but the account-freezing effect is the more direct, permanent-impact analog), this matches the "network unable to confirm new transactions" criterion for the affected account.

### Likelihood Explanation
Reachable directly by any unprivileged transaction sender: an attacker (or even an honest user with a misconfigured client) simply submits a transaction whose resource-bound-derived weights are individually smaller than the gateway's `max_l2_gas_amount`/other stateless checks but larger than the batcher's `block_max_capacity` along some other bouncer dimension (`n_events`, `message_segment_length`, `state_diff_size`, or, for `Declare` transactions, `l2_gas.max_amount` itself since that check is skipped entirely). No special privileges, mempool cooperation, or malicious operator behavior are required — only that the deployment's gateway/mempool config and bouncer config are not manually kept consistent (which the codebase does not enforce programmatically).

### Recommendation
- Add an explicit cross-check either in `StatelessTransactionValidator::validate_resource_bounds` or in mempool admission (`add_tx`) that rejects any transaction whose maximum possible resource consumption (as derivable from `resource_bounds`) cannot fit within `BouncerConfig.block_max_capacity`, mirroring `Bouncer::within_max_capacity_or_err` at admission time rather than only at block-building time.
- Remove the special-case exemption that skips the `max_l2_gas_amount` check for `Declare` transactions, or add an equivalent bound specific to declare-transaction resource usage.
- Ensure this same admission-time check also accounts for the non-gas bouncer dimensions (`n_events`, `message_segment_length`, `state_diff_size`), not just `l2_gas`/`sierra_gas`.

### Proof of Concept
1. Configure (or use default) gateway `max_l2_gas_amount` and batcher `bouncer_config.block_max_capacity` values that are not mutually consistent for some dimension other than raw `l2_gas` (e.g., submit a `Declare` transaction, for which the `max_l2_gas_amount` check is skipped per `crates/apollo_gateway/src/stateless_transaction_validator.rs:78-85`).
2. Submit a transaction whose actual execution would produce `BouncerWeights` (e.g., `n_events`, `state_diff_size`, or `sierra_gas`) exceeding `block_max_capacity` as validated only in `Bouncer::within_max_capacity_or_err`/`verify_tx_weights_within_max_capacity` (see the test at `crates/blockifier/src/bouncer_test.rs:485-526` demonstrating `TransactionTooLarge` is only raised at block-building time).
3. This transaction passes `StatelessTransactionValidator::validate` and mempool admission (no equivalent check exists there) and is accepted with the account's current (lowest) nonce.
4. At block-building time, every batcher/block-builder invocation for this transaction returns `TransactionExecutionError::TransactionTooLarge`, so it is never included in any block.
5. Because the mempool/gateway enforce strict nonce ordering per account, this account's nonce can never advance, and all subsequent queued or future transactions from the same account are permanently unable to be confirmed.

        &self,
        tx: &RpcTransaction,
    ) -> StatelessTransactionValidatorResult<()> {
        if !self.config.validate_resource_bounds {
            return Ok(());
        }

        let resource_bounds = *tx.resource_bounds();
        // The resource bounds should be positive even without the tip.
        if ValidResourceBounds::AllResources(resource_bounds).max_possible_fee(Tip::ZERO) == Fee(0)
        {
            return Err(StatelessTransactionValidatorError::ZeroResourceBounds { resource_bounds });
        }

        if resource_bounds.l2_gas.max_price_per_unit.0 < self.config.min_gas_price {
            return Err(StatelessTransactionValidatorError::MaxGasPriceTooLow {
                gas_price: resource_bounds.l2_gas.max_price_per_unit,
                min_gas_price: self.config.min_gas_price,
            });
        }

        // TODO(Arni): Consider adding a validation for max_l2_gas_amount for declare.
        if let RpcTransaction::Declare(_) = tx {
        } else if resource_bounds.l2_gas.max_amount.0 > self.config.max_l2_gas_amount {
            return Err(StatelessTransactionValidatorError::MaxGasAmountTooHigh {
                gas_amount: resource_bounds.l2_gas.max_amount,
                max_gas_amount: self.config.max_l2_gas_amount,
            });
        }

        Ok(())
    }

    fn update_accounts_with_gap(&mut self, address_to_nonce: AddressToNonce) {
        for (address, account_nonce) in address_to_nonce {
            // If a delayed declare transaction exists at the account nonce, it is next to execute,
            // so no gap exists.
            if self.delayed_declares.contains(address, account_nonce) {
                self.remove_from_accounts_with_gap(address);
                continue;
            }

            // Gap exists when lowest transaction nonce is higher than account nonce.
            let gap_exists = match self.tx_pool.get_lowest_nonce(address) {
                Some(lowest_nonce) => account_nonce < lowest_nonce,
                None => false, // No transactions for the account, so no gap.
            };

            // Update the eviction tracking set accordingly.
            if gap_exists {
                if self.accounts_with_gap.insert(address) {
                    // Newly entered gap: all current pool txs for this account are now stuck.
                    let n_stuck = self.tx_pool.n_txs_for_address(address);
                    self.n_stuck_txs += n_stuck;
                    warn!(
                        "Account {address} has a nonce gap; {n_stuck} transaction(s) are now \
                         stuck."
                    );
                }
                // Stayed in gap: per-tx deltas were already applied at add/remove sites.
            } else {
                // Left gap: remaining pool txs for this account are no longer stuck.
                self.remove_from_accounts_with_gap(address);
            }
        }
