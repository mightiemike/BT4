### Title
Unbounded allocation from attacker-controlled length felt in deprecated (Cairo0) syscall array parsing before any size validation - ([File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs])

### Summary
Apache Thrift's Rust binary protocol read a length-prefixed string field and allocated a buffer of that size before validating it against the actual remaining input, allowing a small malicious message to trigger huge memory allocation (resource exhaustion). The Starknet sequencer's deprecated (Cairo0) syscall array reader has the same shape of bug: it reads an untrusted length felt supplied directly by contract calldata and immediately uses it to size a memory read/allocation, with no check against the size of any backing data, before any downstream size-limit validation runs.

### Finding Description
`read_felt_array` for the deprecated (Cairo0) syscall ABI reads `array_size` directly as a `Felt` value taken from the syscall request memory (which for Cairo0 contracts is populated straight from user-supplied calldata, e.g. `keys_len`/`data_len`/`payload_size`), then converts it to a `usize` and passes it straight into `felt_range_from_ptr`: [1](#0-0) 

`felt_range_from_ptr` forwards this attacker-chosen `size` straight into `vm.get_integer_range(ptr, size)`, which builds a `Vec<Felt>` of that size: [2](#0-1) 

Unlike the Cairo1 (non-deprecated) path, where the array size is derived from `array_data_end_ptr - array_data_start_ptr`, i.e. the difference between two real VM `Relocatable` pointers that must both resolve to valid memory (bounding the size by segment reality), the deprecated path's `array_size` is an arbitrary attacker-supplied felt with no relationship to real memory layout: [3](#0-2) 

This means a Cairo0 contract function that forwards a caller-supplied `keys_len`/`data_len`/`payload_size` argument straight into `emit_event`, `send_message_to_l1`, or `deploy`'s constructor calldata (as the `test_emit_events`/`emit_event_recurse` pattern shows is a normal, unremarkable code shape for Cairo0 contracts) can set that length to an arbitrarily large value: [4](#0-3) 

Any size validation that exists downstream (e.g. `exceeds_event_size_limit`, which enforces `max_data_length`/`max_keys_length`) is only applied *after* `EmitEventRequest::read` has already invoked `read_felt_array` and attempted the oversized allocation/read: [5](#0-4) [6](#0-5) 

This is directly analogous to the Thrift CVE: a length prefix taken from untrusted input is used to size a memory allocation/read before it is validated against any real bound.

### Impact Explanation
A single `invoke` transaction that calls a legacy/previously-declared Cairo0 contract entry point which forwards an attacker-chosen length felt into a deprecated syscall (`emit_event`, `send_message_to_l1`, `deploy`) causes the sequencer's execution engine to attempt allocating/reading a `Vec<Felt>` sized by that felt before any protocol size limit is enforced. A large but `usize`-representable value (e.g. billions) causes a multi-gigabyte allocation attempt in the node process executing that single transaction, which can exhaust memory / crash the executing process (gateway validation, mempool re-execution, or block-building execution). This can degrade or halt the sequencer's ability to process further transactions, which is the "network unable to confirm new transactions" impact class called out in the validation rules.

### Likelihood Explanation
Reachability is high: Cairo0 (deprecated) contract classes remain invocable on Starknet for backward compatibility, and any unprivileged account can send an `invoke` transaction calling such a contract with attacker-chosen calldata. No special privileges (operator/prover/staker) are required — only that a Cairo0 contract exists (already deployed, or deployable by any account) whose entry point relays a length argument into one of the deprecated syscalls, which is an unremarkable and common contract-authoring pattern illustrated in the codebase's own test fixtures.

### Recommendation
Validate the declared `array_size` against the actual available/backing data (or against the same protocol-level bounds enforced elsewhere, e.g. `max_data_length`/`max_keys_length`/`max_calldata_length`) *before* calling `felt_range_from_ptr`/`vm.get_integer_range` in `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs::read_felt_array`, mirroring the fix already applied to `CairoArray::try_from` in `crates/apollo_cairo_utils/src/lib.rs` (validate length against remaining/available data before allocating). Alternatively, derive the size from actual VM pointer arithmetic as done in the non-deprecated syscall path, rather than trusting a raw felt.

### Proof of Concept
1. Deploy (or reuse an already-deployed) Cairo0 contract whose external function accepts `(events_count, keys_len, keys, data_len, data)` and forwards them into `emit_event`, similar to `test_emit_events`/`emit_event_recurse` in `crates/blockifier_test_utils/resources/feature_contracts/cairo0/test_contract.cairo:849-864`.
2. Submit a single `invoke` transaction calling this function with `keys_len` (or `data_len`) set to a very large value (e.g. `10_000_000_000`), while providing a valid `keys` pointer to a small real memory segment.
3. During gateway/mempool re-execution or block building, `EmitEventRequest::read` → `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:931-949`) converts the felt to `usize` and calls `felt_range_from_ptr(vm, ptr, size)`, which calls `vm.get_integer_range(ptr, size)` (`crates/blockifier/src/execution/execution_utils.rs:228-237`), attempting to allocate/read a vector sized by the attacker-chosen value before `exceeds_event_size_limit` (`crates/blockifier/src/execution/syscalls/vm_syscall_utils.rs:260-283`) ever runs, causing excessive memory allocation from a single transaction.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
