Based on the code I traced, this finding is valid. The described mismatch between `process_sys_txs`'s per-event failure handling and the caller's unconditional `remove_deposits` call is exactly as claimed.

### Title
Deposits that revert inside `process_sys_txs` are silently dropped from `DepositDataMempool` without minting cBTC or emitting a Deposit event - (File: `crates/sequencer/src/runner.rs`)

### Summary
`citrea_sendRawDepositTransaction`'s `eth_call` simulation only validates a deposit blob against `BlockId::pending()` at submission time [1](#0-0) . When the deposit is actually replayed later inside `process_sys_txs`, a failure (e.g. Bridge.sol's `require(!processedTxIds[txId])` reverting because a colliding deposit committed first) is caught, the transaction is reverted, and it is silently `continue`d without being added to `all_txs` [2](#0-1) . However, the caller unconditionally removes the entire originally-fetched `deposit_data` set from the mempool regardless of which entries actually succeeded [3](#0-2) .

### Finding Description
Binding: cBTC credited by a `SYSTEM_SIGNER` Bridge deposit == exactly one Bitcoin move-to-vault output actually presigned by Clementine, counted once. After the flow described below, the left side becomes `0` (no `Deposit` event, no cBTC minted) while the right side of the binding (the depositor's legitimate entitlement) is unchanged, and the mempool nonetheless treats the deposit as handled.

Trace:
1. A deposit blob is submitted via `send_raw_deposit_transaction`, simulated with `evm.get_call(dep_tx, Some(BlockId::pending()), ...)` against the state at submission time, and if it succeeds it is added to `DepositDataMempool` [4](#0-3) .
2. Later, at block production, the sequencer fetches a batch of pending deposits (`deposit_data`) and turns them into `SystemEvent::BridgeDeposit` events via `populate_deposit_system_events(deposit_data)` [5](#0-4) , which are executed sequentially in `process_sys_txs` against a fresh `ProverStorage` snapshot for that L2 height.
3. Inside the loop, each deposit is applied via a revertable checkpoint. If it fails with `EvmSystemTransactionNotSuccessful` (which is what Bridge.sol's `require(!processedTxIds[txId], ...)` produces), the working set is reverted and the loop does `continue`, meaning that deposit is never pushed into `all_txs` and no `Deposit`-equivalent side effect survives [6](#0-5) .
4. Back in the caller, after the block is produced and saved, `self.deposit_mempool.lock().remove_deposits(&deposit_data)` is called on the full, originally-fetched `deposit_data` set — not filtered by which entries were actually included in `all_txs`/succeeded in `process_sys_txs` [3](#0-2) .

Root cause: there is no correlation kept between which deposits succeeded inside `process_sys_txs` and which are removed from the mempool at the call site; `deposit_data` used for removal is the pre-execution input set, not the post-execution success set. This means any deposit that reverts on-chain during replay (for any reason not visible to the earlier `eth_call` simulation at a different block/state) is permanently evicted from the mempool with no retry, no event, and no credited cBTC, while Bridge.sol's `processedTxIds` is not rolled back for the deposit that "won" the race.

### Impact Explanation
If two deposits' underlying `calc_tx_id` collide (whether via legitimate duplicate resubmission, a race between concurrently-pending mempool entries evaluated independently against `pending` state, or a maliciously crafted competing blob), the losing deposit is dropped from `DepositDataMempool` forever with no cBTC minted and no `Deposit` event, and any resubmission attempt will fail identically since `processedTxIds[txId]` is already set on the Bridge.sol side. This matches "funds permanently frozen" under the Critical severity bucket. The defect is generic to any on-chain deposit failure discovered only at replay time (not just the txId-collision case), so it is repeatable across blocks and deposits whenever such divergence between simulation-time and replay-time state occurs.

### Likelihood Explanation
The `eth_call` simulation in `send_raw_deposit_transaction` is evaluated against `BlockId::pending()` at submission time, while actual execution happens later against a different `ProverStorage` snapshot in `process_sys_txs`, so state can diverge (e.g., another pending deposit with a colliding `txId` commits first). No privileged role is required to submit a deposit blob or to observe/replay data for a colliding transaction; the mismatch is purely a bookkeeping bug in the sequencer's own removal logic once such a revert occurs, at negligible cost to trigger repeatedly. The main external uncertainty is whether such a `calc_tx_id` collision between two distinct blobs can be practically engineered without cooperation from Clementine's presigning process (which is out of scope), but the mempool-removal defect itself is exploitable by benign or accidental duplicate submissions with no such cooperation needed.

### Recommendation
`process_sys_txs` should return which deposits actually succeeded, and the caller should only call `remove_deposits` on that successful subset. Deposits that failed on replay should either remain in the mempool for retry or be explicitly removed with a corresponding failure notification/event, but never silently dropped from the mempool while credit-side effects were reverted.

### Proof of Concept
`cargo test` plan (sequencer harness, regtest/mock-DA):
1. Submit deposit A via `citrea_sendRawDepositTransaction`; assert it is accepted into `DepositDataMempool`.
2. Before A is fetched for block production, submit/force inclusion of a competing deposit B whose ABI blob decodes to the same `calc_tx_id` fields as A (e.g. by resubmitting A's raw bytes through a path that bypasses `DepositDataMempool`'s own duplicate check, or by directly invoking `process_sys_txs` with two colliding `SystemEvent::BridgeDeposit` entries) so that B commits first and sets `processedTxIds[txId] = true` in Bridge.sol.
3. Trigger block production including A; assert that `process_sys_txs` hits the `continue` branch at [7](#0-6)  for A, and that A is absent from `all_txs`.
4. Assert `remove_deposits(&deposit_data)` at [8](#0-7)  nonetheless removes A from `DepositDataMempool`.
5. Assert no `Deposit` event was ever emitted for A and no cBTC balance change occurred for A's recipient, while A cannot be resubmitted successfully (fails identically due to `processedTxIds[txId]` already being `true`).
