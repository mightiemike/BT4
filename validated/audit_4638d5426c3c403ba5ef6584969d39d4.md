### Title
FeatureVerifier::verify_field_definition performs only a shallow top-level check and fails to recurse into generic type arguments, allowing `SignatureToken::Function` to be smuggled into struct field types via `StructInstantiation` when the function-values feature is disabled - (File: `third_party/move/move-bytecode-verifier/src/features.rs`)

### Summary
`verify_field_definition` calls `verify_signature_token` directly on the field's top-level `SignatureToken` without ever invoking `preorder_traversal`, unlike `verify_signatures`, which does traverse every nested token in the module's signature table. This creates an asymmetric coverage gap: signature-table entries are deeply checked for illegal `SignatureToken::Function` occurrences, but struct field types declared inline (via `StructFieldInformation::Declared`/`DeclaredVariants`) are only checked at their outermost variant.

### Finding Description
`verify_struct_defs` iterates struct fields and calls `verify_field_definition` for each: [1](#0-0) 

This function checks only `&field.signature.0` itself against `SignatureToken::Function`: [2](#0-1) 

If a field's declared type is `SignatureToken::StructInstantiation(SomeStruct, [SignatureToken::Function(...)])`, the top-level token is `StructInstantiation`, not `Function`, so `verify_signature_token` returns `Ok(())` and the nested `Function` argument is never inspected. By contrast, `verify_signatures` explicitly walks every nested token via `tok.preorder_traversal()` before applying the same check: [3](#0-2) 

This confirms the asymmetry described in the question: `preorder_traversal` is invoked only from `verify_signatures`, never from `verify_struct_defs`/`verify_field_definition`, so struct field declarations bypass the deep function-value feature gate that signature-table entries are subject to.

### Impact Explanation
This is a confirmed logic bug in `FeatureVerifier`, meaning a module can declare a struct field whose type nests `SignatureToken::Function` inside a generic instantiation and pass this specific verifier pass even when `enable_function_values` is disabled. However, I was not able to confirm — within the scope of this review — that this alone results in an illegal function value actually being constructed, serialized, and committed to state storage. Constructing and storing such a value would still require passing independent, unaudited-in-this-review layers: kind/ability checking of generic instantiations (whether `Function` types satisfy the constraints of the struct's type parameter), and the value serialization/ability rules governing whether such a struct can ever obtain the `store`/`key` abilities needed to be written into global storage as a resource. Without tracing those layers (e.g. `signature_v2.rs` kind checking, ability propagation for struct instantiations, and the runtime's storage-serialization path), I cannot confirm the described end state — "the field's resource type layout committed into a struct-tag write-set entry contains a function value type illegal for storage, corrupting BCS layout on state-view read" — is actually reachable on mainnet. The verifier gap itself is real; the full chain to committed-state corruption is unverified.

### Likelihood Explanation
Reaching this code path only requires publishing an unprivileged Move module, so if the full chain to storage did materialize, likelihood would be high. But because the additional gating layers (ability/kind checks) were not verified in this review, the realistic likelihood of full state corruption is uncertain.

### Recommendation
Regardless of whether the full storage-corruption chain is reachable, `verify_field_definition` should be hardened to match `verify_signatures`'s coverage by using `field.signature.0.preorder_traversal()` (or equivalent) rather than checking only the outer token, closing the asymmetry described.

### Proof of Concept
Not fully constructed — a proof-of-concept module would need to declare a struct field of type `StructInstantiation(SomeStruct, [SignatureToken::Function(...)])` and run `FeatureVerifier::verify_module` with `enable_function_values = false`, expecting a `FEATURE_NOT_ENABLED` error that will not occur. This confirms the verifier gap, but does not by itself demonstrate write-set/BCS corruption without further tracing of ability checking and storage serialization, which I could not complete in this review.     fn verify_signatures(&self) -> PartialVMResult<()> {
        if !self.config.enable_function_values {
            for (idx, sig) in self.code.signatures().iter().enumerate() {
                for tok in &sig.0 {
                    for t in tok.preorder_traversal() {
                        self.verify_signature_token(t)
                            .map_err(|e| e.at_index(IndexKind::Signature, idx as u16))?
                    }
                }
            }
        }
        Ok(())
    }

    fn verify_signature_token(&self, tok: &SignatureToken) -> PartialVMResult<()> {

            Err(PartialVMError::new(StatusCode::FEATURE_NOT_ENABLED)
                .with_message("function value feature not enabled".to_string()))
        } else {
            Ok(())
        }
