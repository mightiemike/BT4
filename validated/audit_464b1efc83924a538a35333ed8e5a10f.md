## Title
ExchangeInjectActuator and ExchangeWithdrawActuator lack slippage/deadline protection, enabling sandwich attacks on liquidity operations — (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Unlike `ExchangeTransactionContract` (token swap), which carries a caller-supplied `expected` field enforced via `"token required must greater than expected"` [1](#0-0) , the liquidity-management operations `ExchangeInjectContract` and `ExchangeWithdrawContract` compute the counter-token amount purely from the exchange's on-chain reserves at execution time, with no caller-specified minimum/maximum bound and no deadline. This is structurally identical to the reported `formPOL`/`withdrawPOL` bug class: a liquidity deposit/withdrawal executed against the live pool ratio without slippage protection is vulnerable to a sandwich attack.

### Finding Description
In `ExchangeInjectActuator.execute`, `anotherTokenQuant` is derived directly from the current `firstTokenBalance`/`secondTokenBalance` ratio of the `ExchangeCapsule`: [2](#0-1) 

The corresponding validation in `doValidate` recomputes the same ratio-based amount and only checks it against balance limits and `> 0`, never against a value supplied by the transaction owner: [3](#0-2) 

Similarly, `ExchangeWithdrawActuator.execute` derives `anotherTokenQuant` from the live pool ratio: [4](#0-3) 

Its validator's only sanity check is an internal "Not precise enough" comparison between two different rounding methods of the *same* live ratio — it is not a caller-supplied slippage bound and does not detect that the ratio itself was manipulated relative to what the transaction sender expected when they signed the transaction: [5](#0-4) 

Both actuators restrict the caller to the exchange's creator address [6](#0-5) [7](#0-6) , but the attacker in the sandwich scenario is not the creator — it is any anonymous account able to broadcast an unprivileged `ExchangeTransactionContract` swap, which any address can submit against `ExchangeTransactionActuator` with no restriction. Because TRON has a public mempool/pending-transaction window before block packing, an attacker can:
1. Observe a pending `ExchangeInject`/`ExchangeWithdraw` transaction from the exchange creator.
2. Broadcast a swap (`ExchangeTransactionContract`) that shifts `firstTokenBalance`/`secondTokenBalance` to a favorable ratio, ensuring it gets ordered before the creator's transaction (e.g. via higher-fee/priority ordering by the block-producing SR).
3. Let the creator's inject/withdraw execute at the skewed ratio, causing the creator to receive/contribute an off-ratio amount of the counter token.
4. Reverse the swap afterward to extract the imbalance as profit, at the exchange creator's expense.

### Impact Explanation
This causes direct value extraction from TRON's native on-chain AMM-style `Exchange`/`ExchangeV2` pools during liquidity injection or withdrawal — a real accounting/asset-corruption impact analogous to the original `formPOL` finding, where the protocol's own liquidity actions are sandwiched by unprivileged MEV actors for profit. Because both TRX and TRC10 asset balances are moved through `AccountCapsule.addAssetAmountV2`/`reduceAssetAmountV2` based on the manipulated ratio, losses are realized on-chain and are irreversible once the block is confirmed.

### Likelihood Explanation
Exploitability requires only the ability to broadcast an ordinary, unprivileged `ExchangeTransactionContract` transaction (available to any account) timed around a pending inject/withdraw transaction from an exchange creator — no elevated privileges, leaked keys, or malicious SR/P2P behavior are needed. The likelihood is bounded by transaction-ordering control (visible pending transactions, fee-based prioritization), which is a well-established assumption in this bug class (matching the original report's threat model).

### Recommendation
Add caller-specified slippage bounds to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `expected`/`minAnotherTokenQuant` fields similar to `ExchangeTransactionContract.getExpected()`), validated in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` doValidate/execute before mutating balances, and consider adding an expiration/deadline check to reject stale transactions whose intended ratio has since materially diverged.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeInjectContract` intending to inject `tokenQuant` of `firstTokenID` at the currently observed ratio.
2. Attacker observes the pending transaction and broadcasts an `ExchangeTransactionContract` swap (processed by `ExchangeTransactionActuator`) that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably for the injector, and ensures it lands in an earlier position in the same or an earlier block.
3. The creator's inject executes via `ExchangeInjectActuator.execute` using the now-skewed ratio at lines 71-83, causing the creator to over-contribute the counter token relative to fair value.
4. Attacker submits a reverse swap to restore the ratio and pocket the difference, all executed via ordinary, unprivileged `ExchangeTransactionContract` broadcasts.
