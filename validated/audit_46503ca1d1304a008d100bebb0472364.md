The reported Gearbox bug is about a contract assuming a called external contract's return value always conforms to a strict interface (ERC-20 `bool`), and reverting/misbehaving when a non-conforming token doesn't provide it. The closest reachable analog in this codebase is in the NEAR **Wallet Contract**, which similarly assumes that cross-contract calls it makes to an *arbitrary, attacker/relayer-chosen* NEP-141 token or the address registrar will return a strictly-conforming JSON response, and mishandles the case where they don't — but unlike Gearbox's revert (safe), here the mishandling causes attached user funds to be silently lost.

### Title
Wallet Contract loses attached `caller_deposit` refund when a non-conforming cross-contract response fails to deserialize - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` lets a relayer submit an RLP-encoded Ethereum transaction that is translated into a NEAR action and, for emulated base-token/ERC-20 transfers, chains cross-contract calls to an address registrar or an arbitrary NEP-141 token before finally routing through `rlp_execute_callback`, which is the only place that refunds `caller_deposit` back to the caller on failure.

### Finding Description
`inner_rlp_execute` unconditionally constructs a `CallerDeposit` from the attached deposit [1](#0-0) , and this value is threaded through the promise chain to be refunded specifically inside `rlp_execute_callback` when the cross-contract execution ends in `PromiseResult::Failed` [2](#0-1) .

However, two intermediate callbacks — `address_check_callback` (for base-token transfers to another eth-implicit account, checked against the address registrar) and `nep_141_storage_balance_callback` (for emulated ERC-20 transfers, checking `storage_balance_of` on the token contract) — deserialize the `PromiseResult::Successful` payload with `serde_json::from_slice` and, on deserialization failure, return early with a failed `ExecuteResponse` **without ever forwarding to `rlp_execute_callback`, and without refunding `caller_deposit`**: [3](#0-2) [4](#0-3) 

Both of these promise chains are attached to a target account chosen by the relayer/user themselves (the address registrar lookup target and the NEP-141 `token_id` = `target`) [5](#0-4) . Any contract deployed at that target that returns a technically-successful execution outcome whose return value is not the exact expected JSON shape (`Option<AccountId>` or `Option<StorageBalance>`) — e.g., a non-standard/legacy NEP-141-like token, a stub/registrar-mimicking contract, or simply a contract with a bug — causes the deserialization branch to be taken. This is directly analogous to the ERC-20 "missing/non-conforming return value" bug class from the report: the wallet contract assumes cross-contract responses always conform to the expected schema, and its error-handling path for the non-conforming case is incomplete (it drops the refund that exists on every other failure path).

### Impact Explanation
Whenever this path is hit, the deposit attached to the `rlp_execute` call (tracked as `caller_deposit`, meant to reimburse the relayer/predecessor on failure) is neither transferred to the intended token/registrar operation nor refunded — it is retained by the wallet contract with no code path to reclaim it, since `has_in_flight_tx` is reset to `false` and (for the ERC20Transfer case) the nonce has already been incremented in `inner_rlp_execute` before the callback runs [6](#0-5) , so the transaction cannot be replayed to try again. This constitutes permanently frozen/lost funds for the caller of an unprivileged, transaction-signer-reachable entry point (`rlp_execute`).

### Likelihood Explanation
This is triggerable by any relayer or the account owner themselves simply by directing an ERC-20-emulated transfer or a base-token transfer (with address check) at a NEAR account whose `storage_balance_of` / registrar `lookup` method returns a value that doesn't deserialize into the expected `Option<StorageBalance>` / `Option<AccountId>` shape — no special privileges or validator/network position needed, only a single `rlp_execute` transaction and a target contract that doesn't perfectly conform to the assumed NEP-141/registrar schema.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, the deserialization-failure branches should refund `caller_deposit` the same way `rlp_execute_callback`'s `PromiseResult::Failed` branch does, before returning the failed `ExecuteResponse`, ensuring attached funds are never left permanently stuck due to a non-conforming (but technically successful) cross-contract response.

### Proof of Concept
1. Deploy a NEP-141-like token contract at some `token_id` whose `storage_balance_of` method returns success but with a payload that is not valid `Option<StorageBalance>` JSON (e.g., returns a bare string or a differently-shaped object — analogous to a "non-standard token").
2. As a relayer, submit an RLP-encoded Ethereum transaction to the user's eth-implicit `WalletContract` representing an ERC-20 transfer with `target = token_id`, attaching some deposit, via `rlp_execute`.
3. `inner_rlp_execute` classifies this as `EthEmulationKind::ERC20Transfer`, increments the nonce, and calls `storage_balance_of` on `token_id`, chaining to `nep_141_storage_balance_callback` with `caller_deposit` set from the attached deposit [7](#0-6) .
4. Because the token's response fails to deserialize into `Option<StorageBalance>`, `nep_141_storage_balance_callback` returns `ExecuteResponse { success: false, ... }` directly, without refunding `caller_deposit` [4](#0-3) .
5. The attached deposit remains in the wallet contract's balance permanently; the nonce has already advanced so the same logical transaction cannot be resubmitted to recover it.
