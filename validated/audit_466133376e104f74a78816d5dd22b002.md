## Root Cause Confirmation

I've confirmed the analog exploit path. The `X-Shopify-Hmac-Sha256` header is validated only against the raw request **body**, computed with `createSHA256HMAC(config.apiSecretKey, rawBody, HashFormat.Base64)` [1](#0-0) . The `X-Shopify-Shop-Domain` header used to decide *which shop's offline session/access token to load* is never included in that HMAC computation [2](#0-1) .

### Title
Fulfillment Service webhook authentication trusts an unsigned `X-Shopify-Shop-Domain` header to select the merchant session, decoupling the HMAC-verified data from the security decision - (File: `packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts`)

### Summary
The fix for the GuardianProver bug was to include all data that drives a critical decision (`_proof.data`, which determines whether a liveness bond is returned) inside the hash that guardians actually sign. The equivalent pattern exists in `authenticateFulfillmentServiceFactory`: the HMAC only covers `rawBody`, but the value that determines *whose* stored access token gets used (`shop`) is pulled from an unsigned header and never covered by the HMAC.

### Finding Description
`authenticateFulfillmentServiceFactory` validates the request via `api.fulfillmentService.validate({rawBody, rawRequest: request})` [3](#0-2) . That validator only checks the HMAC against `rawBody` [2](#0-1) [4](#0-3) .

After validation succeeds, the code reads `shop` directly from the `X-Shopify-Shop-Domain` header — which is **not part of the HMAC input** — and uses it to look up and inject the merchant's offline access token into the returned `admin` client: [5](#0-4) 

This mirrors the GuardianProver flaw exactly: the "signed"/verified quantity (body HMAC) and the quantity that drives the sensitive outcome (which shop's credentials load) are disjoint. Whoever can produce *any* body whose HMAC is valid for that body (e.g. replaying/observing one legitimate fulfillment-service callback for Shop A, since the same `apiSecretKey` is shared across all shops using this app) can pair that valid `(body, hmac)` pair with an arbitrary `X-Shopify-Shop-Domain` header value, because the domain header is completely unauthenticated.

### Impact Explanation
If an attacker (or a malicious/compromised fulfillment integration on one shop) obtains a single valid `(rawBody, X-Shopify-Hmac-Sha256)` pair for their own shop, they can replay it with the `X-Shopify-Shop-Domain` header changed to a different installed shop's domain. Because the shop domain is never covered by the signature, the request passes `validate()` and the handler loads the **victim shop's** offline session/access token via `ensureValidOfflineSession(params, shop)` and hands back an authenticated `admin` GraphQL client scoped to that other tenant [6](#0-5) . This is a cross-tenant access primitive: the attacker's forged/replayed payload gets processed as if it were a genuine fulfillment order notification for the victim, and any webhook-handler business logic (order updates, metafield writes, etc.) executes with that victim's access token.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid `(body, hmac)` pair — realistically obtainable by an app developer/integration that itself controls a fulfillment service registered against the app (a normal, low-privilege participant, not someone who has leaked the app's `apiSecretKey`). Since `apiSecretKey` is shared by the app across **all** installed shops, a body/HMAC pair valid for one shop is cryptographically valid data regardless of which `X-Shopify-Shop-Domain` header accompanies it — the library performs no binding between the two. This does not require MITM or dependency compromise; it exploits the verification-vs-decision mismatch directly.

### Recommendation
Bind the shop domain into the signed material, mirroring the GuardianProver remediation. Concretely: rather than trusting `request.headers.get(ShopifyHeader.Domain)` as an independent input to `ensureValidOfflineSession`, either
1. Include the domain header value in the HMAC-covered plaintext (analogous to signing `_meta`, `_tran`, and `_proof.data` together), or
2. Cross-check the header-derived shop against an authenticated identifier (e.g. verify the shop is expected/known via a prior authenticated channel) before using it to select session storage.

### Proof of Concept
1. App developer registers a fulfillment service for Shop A and receives a legitimate callback: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Attacker resends the exact same `(B, HMAC(secret,B))` pair but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (any other shop that installed the same app).
3. `api.fulfillmentService.validate` succeeds because it only checks `HMAC(secret,B)` against `B` [2](#0-1) .
4. `shop` is read from the forged header and `ensureValidOfflineSession(params, shop)` loads Shop B's session/access token, returning an `admin` client authenticated as Shop B to the attacker-controlled caller [7](#0-6) .

**Note on verification confidence:** I traced this through the `shopify-app-remix` handler and the underlying `shopify-api` HMAC validator, but could not execute the code to empirically confirm runtime behavior beyond what the test suite in `authenticate.test.ts` demonstrates (which shows the `X-Shopify-Shop-Domain` header is indeed read post-HMAC-check and used directly for session lookup, consistent with this analysis).

  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
