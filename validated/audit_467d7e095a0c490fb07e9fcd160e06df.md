### Title
`DelegateAction` (NEP-366/NEP-611) Signature Omits Chain-ID Binding, Enabling Cross-Network Meta-Transaction Replay — (File: `core/primitives/src/action/delegate.rs`)

---

### Summary

The `DelegateAction` and `DelegateActionV2` signature hashes (`get_nep461_hash`) do not include any chain-specific identifier (chain ID or genesis hash). A `SignedDelegateAction` created for one NEAR network (e.g., testnet) is cryptographically valid on any other NEAR network (e.g., mainnet) that shares the same account ID and public key. A malicious relayer can replay a testnet-signed meta-transaction on mainnet, executing unauthorized actions — including token transfers — against the victim's mainnet account.

---

### Finding Description

`DelegateAction.get_nep461_hash()` computes the signed payload as:

```
hash( borsh(MessageDiscriminant(NEP_366)) ‖ borsh(DelegateAction) )
``` [1](#0-0) 

`SignableMessage` wraps only a constant NEP discriminant and the action body: [2](#0-1) 

The discriminant is a fixed integer derived from the NEP number (366 or 611), not from any chain-specific value: [3](#0-2) 

`DelegateAction` itself contains only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` — none of which are chain-specific: [4](#0-3) 

`apply_delegate_action` in the runtime verifies the signature, checks block height, checks that `sender_id` matches the receipt's `receiver_id`, and validates the access key nonce — but performs **no chain-origin check**: [5](#0-4) 

The signature verification step: [6](#0-5) 

The nonce validation step: [7](#0-6) 

Neither step nor any other step in `apply_delegate_action` checks which network the `DelegateAction` was intended for. The same is true for `DelegateActionV2` / `VersionedSignedDelegateAction`: [8](#0-7) 

The outer `SignedTransaction` wrapping the `DelegateAction` does include a `block_hash` that ties it to a specific chain. However, the attacker does **not** reuse the outer transaction — they create a **new** outer `SignedTransaction` with a valid mainnet `block_hash` while reusing the inner `SignedDelegateAction` verbatim. The outer transaction's chain binding therefore provides no protection against this attack.

---

### Impact Explanation

A malicious relayer who receives a `SignedDelegateAction` intended for testnet can:

1. Wrap it in a **new** mainnet `SignedTransaction` (signed by the attacker as relayer, with a valid mainnet `block_hash`).
2. Submit it to mainnet.
3. If the victim's account exists on mainnet with the same public key and a nonce lower than the `DelegateAction.nonce`, `apply_delegate_action` accepts the signature as valid and executes the inner actions on mainnet.

The inner actions execute with `predecessor_id = sender_id` (the victim), so any contract that checks `predecessor_id` (e.g., a fungible-token contract checking `ft_transfer` caller) treats the call as legitimately from the victim. Concrete impacts:

- **Loss of funds**: inner `Transfer` actions drain the victim's mainnet balance.
- **Unauthorized transaction**: inner `FunctionCall` actions execute on mainnet contracts as the victim.
- **Key manipulation**: inner `AddKey`/`DeleteKey` actions modify the victim's mainnet access keys.

The exact corrupted value is the victim's mainnet account balance (decremented by the transferred amount) and/or account state (modified by the inner actions), without the victim's consent on mainnet.

---

### Likelihood Explanation

The attack requires:

1. **Same account/key on both networks** — extremely common for NEAR developers and power users who create accounts on testnet and mainnet with the same name and key pair.
2. **Valid nonce on mainnet** — if the victim's mainnet access key nonce is lower than the `DelegateAction.nonce`, the replay succeeds. A freshly created mainnet account (nonce = 0) is trivially vulnerable to a testnet action with nonce = 1.
3. **Valid `max_block_height` on mainnet** — if the victim sets a large `max_block_height` (e.g., `current_testnet_height + 1_000_000`), mainnet block heights are independent and the action remains valid on mainnet for an extended window.

The attacker only needs to act as a testnet relayer — an entirely unprivileged role open to anyone. The victim shares the `SignedDelegateAction` with the relayer expecting it to be submitted on testnet; the relayer instead (or additionally) submits it on mainnet.

---

### Recommendation

Bind the `DelegateAction` signature to the chain by including the genesis hash or chain ID in the signed payload. The most backward-compatible approach is to add a `chain_id: String` field to `DelegateAction` (and `DelegateActionV2`) so that the borsh-serialized body — and therefore the NEP-461 hash — differs across networks. Alternatively, extend `SignableMessage` to carry a chain-specific tag alongside the NEP discriminant, analogous to how `SignedTransaction` is implicitly chain-bound via `block_hash`.

---

### Proof of Concept

```
Setup:
  alice.near exists on both testnet (nonce=5) and mainnet (nonce=0).
  alice.near uses the same ed25519 key pair on both networks.

Step 1 (testnet):
  Alice creates DelegateAction {
      sender_id:       "alice.near",
      receiver_id:     "bob.near",
      actions:         [Transfer { deposit: 100 NEAR }],
      nonce:           1,          // valid on mainnet (mainnet nonce=0)
      max_block_height: 200_000_000, // valid on mainnet
      public_key:      <alice's key>,
  }
  Alice signs it → SignedDelegateAction (signature covers no chain ID).
  Alice hands it to the testnet relayer (the attacker).

Step 2 (mainnet, attacker):
  Attacker constructs a mainnet SignedTransaction:
      signer_id:   "attacker.near"
      receiver_id: "alice.near"       // receipt lands on alice's shard
      block_hash:  <valid mainnet block hash>
      actions:     [Delegate(SignedDelegateAction from Step 1)]

Step 3 (mainnet runtime, apply_delegate_action):
  signed_delegate_action.verify()
    → hash = NEP_366_discriminant ‖ borsh(DelegateAction)
    → signature valid (same key, same payload, no chain binding)  ✓
  block_height (1_000_000) < max_block_height (200_000_000)       ✓
  delegate_action.sender_id ("alice.near") == receipt.receiver_id ✓
  access_key nonce (0) < delegate_action.nonce (1)                ✓

Result:
  A new receipt is emitted: predecessor="alice.near", receiver="bob.near",
  actions=[Transfer(100 NEAR)].
  100 NEAR is transferred from alice.near to bob.near on mainnet
  without Alice's knowledge or consent.
```

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

    // Generate a new receipt from DelegateAction.
    let new_receipt = Receipt::V0(ReceiptV0 {
        predecessor_id: sender_id.clone(),
        receiver_id: delegate_action.receiver_id().clone(),
        receipt_id: CryptoHash::default(),

        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: action_receipt.signer_id().clone(),
            signer_public_key: action_receipt.signer_public_key().clone(),
            gas_price: action_receipt.gas_price(),
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: delegate_action.get_actions(),
        }),
    });

    // Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas.
    // If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction.
    // Gas is refunded to the signer, this is Relayer.
    // Some contracts refund the deposit. Usually they refund the deposit to the predecessor and this is sender_id/Sender from DelegateAction.
    // Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit.

    let prepaid_send_fees = total_prepaid_send_fees(&apply_state.config, action_receipt.actions())?;
    let required_cost = receipt_required_cost(apply_state, &new_receipt)?;
    // This gas will be burnt by the receiver of the created receipt.
    // Compute costs of that are not relevant at this point, the "used" gas is
    // only reserved for execution later, potentially on a different shard.
    result.gas_used = result.gas_used.checked_add_result(required_cost.gas)?;
    // This gas was prepaid on Relayer shard. Need to burn it because the receipt is going to be sent.
    // gas_used is incremented because otherwise the gas will be refunded. Refund function checks only gas_used.
    result.gas_used = result.gas_used.checked_add_result(prepaid_send_fees.gas)?;
    result.gas_burnt = result.gas_burnt.checked_add_result(prepaid_send_fees.gas)?;
    result.compute_usage = safe_add_compute(result.compute_usage, prepaid_send_fees.compute)?;
    result.new_receipts.push(new_receipt);

    Ok(())
}
