## Title
Unbounded recursion in `bytecode_hash_node` over compiler-supplied `NestedIntList` segment structure can cause a stack-overflow DoS during compiled class hash computation - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
`compiled_class_hash.rs::bytecode_hash_node` recursively walks the `bytecode_segment_lengths` field (`NestedIntList`) of a `CasmContractClass` with no depth bound, similar in shape to the Netty HAProxy TLV recursion bug (unbounded recursive descent over an attacker-influenced nested structure). This function is invoked on every declare transaction (compiled-class-hash verification) and whenever the compiled class hash is (re)computed (e.g. `SierraCompiler::compile` in `apollo_compile_to_casm/src/lib.rs:69`, and the casm-hash migration path via `get_compiled_class_hash_v2`).

### Finding Description
`bytecode_hash_node` recurses once per nesting level of the segment tree: [1](#0-0) 

It has no depth check, unlike the analogous helper in the blockifier, `NestedFeltCounts::new_inner`, which explicitly asserts `segmentation_depth <= 1`: [2](#0-1) 

The `NestedIntList` value being walked (`bytecode_segment_lengths`) is not produced or bounded by sequencer code — it is deserialized straight from the Sierra→CASM compiler's JSON output: [3](#0-2) 

and then hashed in the same (non-sandboxed) process immediately after compilation: [4](#0-3) 

The segment tree reflects the nested control-flow (function/branch) structure of the submitted Cairo/Sierra program, as documented in the corresponding Starknet OS Cairo hashing code, which walks the exact same shape recursively (`bytecode_hash_internal_node`): [5](#0-4) 

While the CASM compilation subprocess itself is resource-limited (`ResourceLimits::new` with CPU-time/memory bounds), that isolation only protects the compiler binary invocation. The subsequent `hash()` call that walks the returned `NestedIntList` recursively executes directly inside the `SierraCompiler` component process (used by class-manager/gateway class compilation), with no equivalent stack-depth guard.

### Impact Explanation
A crafted Sierra program compiled to CASM with a sufficiently deep segment nesting can drive `bytecode_hash_node` (and its Starknet-OS Cairo counterpart) into unbounded recursion, causing a process-level `StackOverflowError`/abort that is not a catchable Rust panic — crashing the compiling component (or the batcher/blockifier process that recomputes hashes during casm-hash migration or re-execution). This is reachable from a single contract declarer submitting a class through the normal declare-transaction flow, matching the CWE-674 stack-exhaustion class in the reported advisory. A crash of the sequencer's compilation/execution component constitutes a denial of service against block production/confirmation.

### Likelihood Explanation
Medium. The attacker needs the Sierra→CASM compiler to actually emit a segment tree deep enough to exhaust the stack; this requires a program with a correspondingly deep nested control-flow structure and is bounded in practice by `max_bytecode_size` limits enforced on the compiled CASM. It is not a trivial one-line exploit like the Netty TLV case, but no explicit depth cap exists in the hashing path, unlike the sibling `NestedFeltCounts::new_inner` function which the developers already recognized needed (and added) a depth assertion for a similar structure — indicating the team is aware this shape of recursion is a risk area but did not apply the same guard to `bytecode_hash_node`.

### Recommendation
Add an explicit maximum recursion/segmentation-depth check (mirroring the `assert!(segmentation_depth <= 1, ...)` guard already used in `NestedFeltCounts::new_inner`) to `bytecode_hash_node` in `crates/starknet_api/src/contract_class/compiled_class_hash.rs`, returning a proper error instead of recursing, and apply the equivalent bound to the corresponding Cairo `bytecode_hash_internal_node` implementations used by the Starknet OS. Alternatively, convert `bytecode_hash_node` to an explicit iterative/stack-based traversal with a hard depth limit validated at CASM-deserialization time.

### Proof of Concept
Conceptual (cannot be executed without a live compiler toolchain/repo checkout):
1. Author a Cairo1 contract whose Sierra output compiles to CASM with an artificially deep, nested branch/function structure (e.g., thousands of nested `if`/`match` arms), such that `cairo-lang-starknet-classes`' segment computation emits a `NestedIntList::Node` chain nested to a depth on the order of the Rust thread stack limit (default ~8MB main thread / configurable smaller for worker threads) divided by the per-frame cost of `bytecode_hash_node`.
2. Submit this class via a DECLARE transaction (or invoke `SierraCompiler::compile` directly through the class-manager/gateway compilation path).
3. Observe that `CasmContractClass::hash(&HashVersion::V2)` → `bytecode_hash` → `bytecode_hash_node` recurses to the segment-tree depth and aborts the process with a stack overflow instead of returning a `Result` error, crashing the compiling/hashing component and any thread that later recomputes the hash (e.g. during casm-hash migration in `get_compiled_class_hash_v2`).

fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

        match bytecode_segment_lengths {

                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);

            }
            NestedIntList::Node(segments_vec) => {

                let mut segments = Vec::with_capacity(segments_vec.len());

                        segment,

                }

// Returns the hash of the contract class bytecode according to its segments.
//
// The hash is computed according to a segment tree. Each segment may be either a leaf or divided
// into smaller segments (internal node).
// For example, the bytecode may be divided into functions and each function can be divided
// according to its branches.
//
// The hash of a leaf is the Poseidon hash the data.
// The hash of an internal node is `1 + poseidon(len0, hash0, len1, hash1, ...)` where
// len0 is the total length of the first segment, hash0 is the hash of the first segment, and so on.
//
// For each segment, the *prover* can choose whether to load or skip the segment.
// When full_contract is TRUE, all segments are loaded regardless of their usage.
//
// * Loaded segment:
//   For leaves, the data will be fully loaded into memory.
//   For internal nodes, the prover can choose to load/skip each of the children separately.
//
// * Skipped segment:
//   The inner structure of that segment is ignored.
//   The only guarantee is that the first field element is enforced to be -1.
//   The rest of the field elements are unconstrained.
//   The fact that a skipped segment is guaranteed to begin with -1 implies that the execution of
//   the program cannot visit the start of the segment, as -1 is not a valid Cairo opcode.
//
// In the example above of division according to functions and branches, a function may be skipped
// entirely or partially.
// As long as one function does not jump into the middle of another function and as long as there
// are no jumps into the middle of a branch segment, the loading process described above will be
// sound.
