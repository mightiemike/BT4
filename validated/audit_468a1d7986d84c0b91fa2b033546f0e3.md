Confirmed: unlike `ExchangeTransactionContract`, both `ExchangeInjectContract` and `ExchangeWithdrawContract` in the proto lack an `expected`/slippage field, confirming the vulnerability is real and specific to the inject/withdraw paths. [1](#0-0) [2](#0-1) 

### Title
Missing slippage protection in `ExchangeInjectActuator` (`ExchangeInjectContract`) enables sandwich attacks against native TRX/TRC10 AMM pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
java-tron includes a native constant-product AMM ("bancor-style" `Exchange`/`ExchangeV2` pools) implemented via `ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, and `ExchangeTransactionContract`. [3](#0-2)  The swap path (`ExchangeTransactionContract`) already includes an `expected` field enforced during validation to protect against price manipulation. [4](#0-3) [5](#0-4)  However, `ExchangeInjectContract` (add-liquidity) has no equivalent slippage/expected parameter, exactly mirroring the `VectorBonding.sol` `addLiquidity()` bug described in the report.

### Finding Description
`ExchangeInjectActuator.execute()` computes `anotherTokenQuant` purely from the pool's live ratio at execution time (`secondTokenBalance * tokenQuant / firstTokenBalance` or the inverse), with no user-supplied bound on the resulting exchange rate or the amount of the counter-token to be pulled from the account. [2](#0-1)  `doValidate()` similarly recomputes `anotherTokenQuant` from the pool ratio without any user-specified minimum/maximum acceptable amount. [6](#0-5)  Because the pool ratio (`firstTokenBalance`/`secondTokenBalance`) can be freely and atomically changed by any unprivileged account via `ExchangeTransactionActuator` (a public, permissionless swap), an attacker can:
1. Front-run a pending `ExchangeInjectContract` transaction with an `ExchangeTransactionContract` swap that skews the pool ratio.
2. Let the victim's inject execute at the manipulated ratio, forcing them to deposit a much larger (or effectively worthless) amount of the counter-token than the fair-value ratio would require.
3. Back-run with a reverse swap to restore the ratio and extract the excess value deposited by the victim.

This is the exact bug class in the report: an AMM operation lacking slippage bounds is executed atomically against a manipulable on-chain price, letting an attacker sandwich it for profit. The `ExchangeWithdrawContract` path exhibits the identical missing-slippage pattern for liquidity removal. [7](#0-6) 

The primary limiting factor is that `ExchangeInjectActuator.doValidate()` requires the caller to be the exchange's creator (`!accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` throws `"account[...] is not creator"`). [8](#0-7)  So the victim must specifically be the pool creator (an ordinary, unprivileged user who created the trading pair — not a system-trusted role like a witness/SR), while the attacker performing the sandwich (via `ExchangeTransactionContract`) is fully unprivileged and requires no special role.

### Impact Explanation
A successful sandwich against `ExchangeInjectContract` forces the pool creator to overpay the counter-token relative to fair value, transferring value to the attacker — an underpriced/overpaid public-work-style accounting loss executed entirely through permissionless, in-scope actuators (`ExchangeTransactionActuator`, `ExchangeInjectActuator`). Funds are directly moved out of the victim account via `accountCapsule.reduceAssetAmountV2`/`setBalance` calls driven by the manipulated ratio. [9](#0-8) 

### Likelihood Explanation
Any account can submit `ExchangeTransactionContract` swaps against a given `exchange_id` with no permission restriction, and can observe/front-run a pending `ExchangeInjectContract` transaction in the mempool since transaction ordering within a block/broadcast window is attacker-influenceable. No special role, timing race beyond ordinary front-running, or trusted access is required for the attacker side of the sandwich.

### Recommendation
Add a slippage-protection parameter to `ExchangeInjectContract` (and `ExchangeWithdrawContract`), analogous to the `expected` field already present in `ExchangeTransactionContract`, allowing the caller to bound the acceptable `anotherTokenQuant` (min/max), and enforce it in `ExchangeInjectActuator.execute()`/`doValidate()` before mutating balances.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from the pool creator for exchange `id=N`, injecting `tokenQuant` of `firstTokenID`.
2. Attacker submits an `ExchangeTransactionContract` swap on exchange `N` that sells a large amount of `secondTokenID`, spiking `secondTokenBalance` relative to `firstTokenBalance`. [10](#0-9) 
3. The victim's `ExchangeInjectContract` executes; `anotherTokenQuant` is now computed from the skewed ratio, requiring the creator to deposit far more `secondTokenID` than at the pre-attack price. [11](#0-10) 
4. Attacker submits a reverse `ExchangeTransactionContract` swap to restore the ratio, extracting the excess value the victim was forced to deposit.
