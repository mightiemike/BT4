### Title
Panic-inducing stale shard mapping for delayed receipts after resharding causes a transaction-triggered chain halt - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
The external report describes a stale-reference bug class: after a "migration" event (OriginToken redeploy), code elsewhere continued to hold references that were valid pre-migration but became invalid/unusable post-migration, permanently freezing user funds. The reachable nearcore analog is in the delayed-receipt queue's post-resharding shard-filtering logic, `DelayedReceiptQueueWrapper::receipt_filter_fn`, which recomputes a receipt's target shard via `Receipt::receiver_shard_id(&shard_layout)` and unconditionally `.unwrap()`s the result. When a shard undergoes resharding more than once while a receipt is still sitting in the (duplicated) delayed queue, the receiver-account-to-shard mapping recorded against an older shard layout can fail to resolve against the current layout, causing the `unwrap()` to panic during normal chunk application — an ordinary, user-triggered halt rather than a value-preserving migration path.

### Finding Description
`DelayedReceiptQueueWrapper::pop` drains the trie-backed delayed receipt queue and, for each dequeued item, calls `self.receipt_filter_fn(&receipt)` to decide whether the receipt belongs to the current shard: [1](#0-0) 

```
    // With ReshardingV3, it's possible for a chunk to have delayed receipts that technically
    // belong to the sibling shard before a resharding event.
    // Here, we filter all the receipts that don't belong to the current shard_id.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
        let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }
```

This mirrors the report's root cause pattern exactly: on resharding, the delayed-receipt queue is *duplicated* into both child shards rather than partitioned (per `docs/architecture/how/resharding_v2.md`), and each child later re-derives "does this receipt belong to me" by recomputing `receiver_shard_id` against the *current* epoch's shard layout — i.e., by re-resolving a reference (receiver account → shard) using post-migration state, exactly as the Marketplace contract kept resolving OriginToken by its old address after the token was migrated. The `test_stale_global_contract_distribution_after_double_resharding` regression test in `test-loop-tests/src/tests/global_contracts_distribution.rs` documents the exact failure mode this code guards against: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations," and the test explicitly forces two sequential shard splits (the shard containing the receipt's original account, then a second split) to try to reproduce it: [2](#0-1) 

The underlying issue is that `receiver_shard_id` is computed lazily/on read using the shard layout *at the time it is popped*, not a value that was fixed and consistently propagated at receipt-creation/enqueue time. Any additional resharding generations, out-of-order draining, or edge cases in account-to-shard remapping that the current guard doesn't anticipate can produce a receiver id that `receiver_shard_id` cannot resolve for the current layout, at which point the `.unwrap()` calls in `receipt_filter_fn` (both in `pop` and in `peek_iter`) turn a data/layout inconsistency into an unconditional panic rather than a recoverable error.

### Impact Explanation
A panic inside `receipt_filter_fn`, which runs during ordinary chunk application while draining the delayed receipt queue, aborts the validator/node process applying that chunk. Because this runs on every honest node applying the same chunk, it manifests as a network-wide, transaction/receipt-triggered chain halt (all nodes crash identically rather than diverging), which matches the accepted impact category "a transaction-triggered halt." Because the trigger is simply having a receipt sit in the delayed queue across resharding boundaries, it is reachable purely from previously-submitted transactions/receipts and shard-layout changes that the protocol performs autonomously — no special validator/operator privileges are required to have created the underlying receipt.

### Likelihood Explanation
This is a narrow, resharding-specific edge case (ReshardingV3, and specifically receipts spanning *multiple* resharding generations while still delayed) that the codebase's own regression test targets and appears designed to prevent under the currently exercised scenario. It is not an every-block occurrence — it requires congestion sufficient to leave receipts in the delayed queue across at least two consecutive shard splits. Whether the existing test currently passes (i.e., whether the guard fully closes the gap for all account-remapping edge cases) could not be confirmed by static inspection alone; the `.unwrap()` calls remain present in the reachable code path, so any account-to-shard remap case not covered by the current fix still causes a hard panic instead of a graceful degrade/skip.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` (and in `peek_iter`) with fallible handling: if `receiver_shard_id` cannot resolve a receiver against the current shard layout, the receipt should be handled deterministically (e.g., re-derive by walking the resharding ancestry from the epoch the receipt was enqueued in, or fail the operation with a well-defined, recoverable error instead of panicking) so that no single receipt can halt chunk application. Long term, delayed receipts should carry an explicit, versioned shard/account binding established at enqueue time and validated/migrated as part of resharding, rather than being recomputed against the shard layout current at dequeue time — the same fix direction as the report's recommendation of validating references after a migration/config update rather than trusting stale addresses.

### Proof of Concept
A concrete, minimal reproduction is already encoded in-repo as `test_stale_global_contract_distribution_after_double_resharding` (`test-loop-tests/src/tests/global_contracts_distribution.rs:32-186`): it forces `DynamicResharding` to sequentially split first the shard containing the account that issued a `GlobalContractDistribution`/delayed receipt, then split a second shard, saturates the chain to keep the receipt in the delayed queue across both splits, then drains the queue and asserts the chain does not stall/panic. This test's own comments state the panic path directly: `receipt_filter_fn()` calling `receiver_shard_id()` which fails to remap the stale target shard after two resharding generations, i.e., the exact "stale post-migration reference" bug class from the external report, reachable by an ordinary user whose transaction produced the delayed receipt before resharding began.
