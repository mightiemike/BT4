The block execution path (`process_transaction_payload` in `transactions.rs`) and `handle_poison_microblock` never re-check `sequence`/`prev_block`/`version` equality — those are only checked in the advisory mempool-relay path (`can_include_tx` in `blocks.rs`), which is not part of consensus/block validation (`validate_transactions_static` doesn't check it either). ### Title
PoisonMicroblock block-execution path omits sequence/prev_block/version equality check, enabling reward theft from non-equivocating miners - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`handle_poison_microblock` (invoked from `process_transaction_payload` via `ClarityTransactionConnection::run_poison_microblock`) only verifies that two microblock headers share the same signer (`check_microblock_header_signer`: `pkh1 == pkh2`), but never re-verifies `sequence`, `prev_block`, or `version` equality that the mempool-only gate (`can_include_tx`, `blocks.rs:6844-6868`) enforces to ensure the headers actually represent a genuine equivocation. Because a single microblock private key signs an entire tenure's stream, any two legitimately sequential (non-conflicting) microblocks from an honest miner trivially satisfy `pkh1==pkh2`, so a crafted `PoisonMicroblock` tx referencing two real, non-conflicting headers is accepted by block execution and slashes the honest miner's coinbase, paying a 5% commission to the attacker.

### Finding Description
The claimed equality is: *is-genuine-double-sign == (`pkh1==pkh2` AND `sequence1==sequence2` AND `prev_block1==prev_block2`)*.

- The mempool-only static gate in `can_include_tx` (`stackslib/src/chainstate/stacks/db/blocks.rs:6844-6868`) enforces all three conditions (`sequence`, `prev_block`, `version` equality) plus pubkey-hash equality before rejecting non-conflicting poison txs with `MemPoolRejection::PoisonMicroblocksDoNotConflict`. [1](#0-0) 
- However, the actual state-transition function that all nodes must execute to validate/replay a block, `process_transaction_payload`'s `TransactionPayload::PoisonMicroblock` arm, calls `clarity_tx.run_poison_microblock` directly with no equivalent check, only rejecting txs with non-empty post-conditions. [2](#0-1) 
- `handle_poison_microblock` itself only calls `check_microblock_header_signer`, which solely compares `pkh1 != pkh2` — no `sequence`, `prev_block`, or `version` comparison exists at execution time. [3](#0-2) [4](#0-3) 
- Block-level static validation (`validate_transactions_static` in both epoch2 `block.rs` and Nakamoto `nakamoto/mod.rs`) checks tx uniqueness, network, chain-id, anchor-mode/coinbase well-formedness, and epoch-permitted tx types — it never inspects `PoisonMicroblock` payload semantics. [5](#0-4) [6](#0-5) 
- Root cause: because one microblock private key signs an entire honest tenure's microblock stream, `pkh1==pkh2` is trivially true for *any* two microblocks a given miner ever produced (forking or not). The `sequence`/`prev_block` equality is what actually distinguishes "two headers claiming the same slot" (genuine equivocation) from "two different, legitimate points in a normal, non-forking stream." Without re-checking it at execution time, the guard collapses to "same signer," which is not sufficient proof of double-signing.
- Attacker's exact input: take any two distinct, honestly-produced, non-conflicting `StacksMicroblockHeader`s (different `sequence`/`prev_block`) from a target miner's own broadcast (non-forked) microblock stream, and submit `TransactionPayload::PoisonMicroblock(header_A, header_B)` directly in a self-authored block (bypassing `will_admit_mempool_tx`/`can_include_tx`, which are mempool-relay-only and not invoked by `process_block`/`process_transaction`).
- Exploit flow: block containing this tx is processed by `process_transaction` → `process_transaction_payload` → `run_poison_microblock` → `handle_poison_microblock`, which succeeds because `pkh1==pkh2`, inserts a poison report via `insert_microblock_poison`, and later `find_mature_miner_rewards`/`calculate_miner_reward` (`stackslib/src/chainstate/stacks/db/accounts.rs:1027-1052`, `794-905`) redirects `POISON_MICROBLOCK_COMMISSION_FRACTION` (5%) of the target miner's matured coinbase to the attacker's address, destroying the remainder. [7](#0-6) [8](#0-7) 
- This check is deterministic and identical on every conforming node — every honest node running this code accepts the same malicious tx as "valid poison," so this is not a fork/divergence bug but a universally-accepted invalid slashing, i.e., every node in the network wrongly punishes the honest miner and mis-pays the attacker.

### Impact Explanation
This causes reward theft/mis-payment: an honest miner's future coinbase is docked and 5% is paid to an attacker who never observed any actual equivocation, merely two legitimate, sequential, non-conflicting microblocks. This matches "reward mis-payment bounded to fees"-style High impact (the loss is capped at `POISON_MICROBLOCK_COMMISSION_FRACTION` of one coinbase per report, not a full block-reward double-payment or chain split), since all nodes converge on the same wrong outcome deterministically rather than disagreeing with each other. It is repeatable for any miner whose microblock stream is publicly observable (which is required by protocol) and whose reward has not yet matured (within `MINER_REWARD_MATURITY` blocks).

### Likelihood Explanation
Preconditions: attacker needs no special stake — they only need the ability to get their own crafted `PoisonMicroblock` transaction into a mined block, e.g., by mining a block themselves during a single leader slot (a single miner-slot is explicitly permitted for the assumed attacker), and any target miner's normal (non-conflicting) two-or-more-microblock stream, which is broadcast in the clear by protocol design. No majority stake, no compromised keys, no signer collusion required. This is easily repeatable against every miner in every tenure with more than one microblock, within the maturity window, at minimal BTC/stake cost (just enough to win a single sortition).

### Recommendation
Re-enforce genuine-equivocation semantics inside `handle_poison_microblock` (or immediately before it is invoked in `process_transaction_payload`), mirroring the mempool's `can_include_tx` logic: require `mblock_header_1.sequence == mblock_header_2.sequence`, `mblock_header_1.prev_block == mblock_header_2.prev_block`, `mblock_header_1.version == mblock_header_2.version`, and the two headers to be non-identical, in addition to the existing `pkh1==pkh2` check, before accepting the tx as valid poison at execution time.

### Proof of Concept
Rust integration test in `stackslib/src/chainstate/stacks/db/transactions.rs` test module, modeled on `process_poison_microblock_same_block` (`transactions.rs:5478-5597`):
1. Build a chainstate, insert a microblock pubkey hash via `StacksChainState::insert_microblock_pubkey_hash`.
2. Construct two *legitimate, non-conflicting* `StacksMicroblockHeader`s signed by the same `block_privk`, e.g. `mblock_1` with `sequence=1, prev_block=X` and `mblock_2` with `sequence=2, prev_block=X'` (`X' == mblock_1.block_hash()`), i.e., a normal, non-forking two-microblock stream (assert via `StacksChainState::validate_parent_microblock_stream` that this stream is NOT flagged as forked/poisoned).
3. Assert (equality check before the fix): `mblock_1.header.sequence != mblock_2.header.sequence` and `mblock_1.header.prev_block != mblock_2.header.prev_block` — i.e., these do NOT satisfy the genuine-equivocation equality.
4. Build `TransactionPayload::PoisonMicroblock(mblock_1.header, mblock_2.header)`, sign it, and call `StacksChainState::process_transaction` directly (bypassing `will_admit_mempool_tx`).
5. Assert it currently succeeds (`Ok`) and `StacksChainState::get_poison_microblock_report` returns a report — demonstrating that a non-conflicting header pair is accepted as valid poison, confirming the missing re-check.
6. After the fix, assert the same call returns `Err(Error::InvalidStacksTransaction(_, false))` and no poison report is inserted, matching the mempool's `PoisonMicroblocksDoNotConflict` rejection semantics.
