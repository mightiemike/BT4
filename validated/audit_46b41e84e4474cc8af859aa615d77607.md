### Title
Wallet Contract `AddKey` method-name comma-injection lets a signed single method name expand into additional allowed methods - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract (used to let ETH-implicit accounts issue NEAR actions from an Ethereum-style signed transaction) reconstructs a `FunctionCallPermission.method_names: Vec<String>` into a single comma-joined string before handing it to the low-level `Promise::add_access_key_allowance_with_nonce` API, which the NEAR runtime re-splits on `,` into a list of allowed method names. Because the ABI decoder that produces `method_names` from the signed Ethereum transaction does not forbid `,` inside an individual method-name element, a single element containing a comma is silently expanded into multiple allowed methods at execution time — a scope-expanding string round-trip mismatch analogous to the Heimdall path/query re-encoding bug.

### Finding Description
The owner of an ETH-implicit account authorizes actions by signing an RLP Ethereum transaction; the wallet contract ABI-decodes it into `near_action::Action::AddKey` with `FunctionCallPermission.method_names: Vec<String>` [1](#0-0) . Nothing in the ABI decode path or in `try_into_near_action` validates that an individual method name does not contain a `,` character [2](#0-1) .

When the contract turns this `near_action::Action::AddKey` into an actual NEAR promise, it collapses the `Vec<String>` of method names into one comma-joined string: [3](#0-2) 

That joined string is passed to the host function underlying `promise_batch_action_add_key_with_function_call`, whose documented behavior is to split the string on `,` to recover the list of method names: [4](#0-3) [5](#0-4) 

Consequently, if the RLP-signed data specifies exactly one intended method name that happens to contain an embedded comma (e.g. `"withdraw,transfer"`), the value the owner cryptographically authorized is a single opaque string `"withdraw,transfer"` — which, compared byte-for-byte against real contract method identifiers in `verify_function_call_permission`/`validate_access_key_permission`, would never match any real callable method and thus would functionally behave as "deny all" [6](#0-5) . But because the wallet contract's join/host-split round-trip does not preserve that string as one token, the on-chain access key ends up permitting two independent methods, `"withdraw"` and `"transfer"`, neither of which the signer's intended (single, ostensibly non-matching) restriction implies.

This is the same bug class as the Heimdall advisory: a value is reconstructed from a structured representation into an encoded string form, then independently re-parsed by a downstream component using a different (looser) interpretation of the encoding, silently broadening the scope of a security-relevant restriction (an access-key method allowlist) beyond what was validated/signed.

### Impact Explanation
A malicious relayer/dApp that constructs the RLP transaction data shown to (and blindly signed by) the eth-implicit account owner can embed a comma inside what looks like an innocuous/impossible method name to make the wallet UI/owner believe they are creating a heavily restricted (or effectively unusable) `FunctionCallPermission` access key for a delegate/relayer public key. In reality, due to the join-then-split round trip, the resulting on-chain access key grants that delegate key the ability to call multiple real methods (e.g., a token `transfer`/`ft_transfer` method), which can be used to move funds or otherwise act beyond the explicitly signed/reviewed authorization — i.e., an access-control bypass that leads to unauthorized value movement from the ETH-implicit account. This satisfies "invalid state transition acceptance" / "unauthorized value movement" per the validation criteria, reached purely through a signed Wallet Contract `rlp_execute` call (an ordinary contract-call code path, no privileged/validator access required).

### Likelihood Explanation
Exploitation requires a scenario where a third party (relayer, dApp, malicious front end) constructs and requests the signature for the AddKey Ethereum transaction while the actual account owner does not carefully decode/verify the raw ABI-encoded method-name bytes before signing (a realistic blind-signing UX assumption, similar to typical wallet phishing setups). No network-level or validator-level privilege is needed — only submission of a normal `rlp_execute` NEAR function call built from a signed Ethereum transaction, reachable by any unprivileged account. The likelihood is moderate: it depends on social/UX conditions (crafted method name at signing time) rather than a pure on-chain invariant violation, but the reachability itself is trivial for anyone who can get such a transaction signed.

### Recommendation
- Reject (or escape) any method name containing a `,` character when decoding `FunctionCallPermission.method_names` from the ABI-encoded Ethereum transaction in `near_action`/`types.rs`, or
- Avoid the string-join round trip entirely in `action_to_promise` by using an API/host-function surface that accepts the method names as a true list (e.g., pre-validate that no element embeds the separator before calling `add_access_key_allowance_with_nonce`), and
- Add an explicit check/test asserting that the number of method names decoded from the ABI equals the number of method names ultimately stored in the resulting on-chain `AccessKey` for the Wallet Contract's `rlp_execute` path.

### Proof of Concept
1. Owner of an ETH-implicit account is asked to sign (via `rlp_execute`) an `AddKey` action whose ABI-encoded `method_names` array is `["withdraw,transfer"]` (single element containing an embedded comma) restricting a relayer's new key to that one nominal name, targeting the wallet's own account: see `abi_encode`'s `AddKey` encoding path used in tests [7](#0-6) .
2. The wallet contract decodes this into `near_action::Action::AddKey { access_key.permission = FunctionCall(FunctionCallPermission { method_names: vec!["withdraw,transfer".to_string()], .. }) }` [2](#0-1) .
3. `action_to_promise` joins this single-element vector with `,` — producing the identical string `"withdraw,transfer"` — and calls `Promise::add_access_key_allowance_with_nonce(..., "withdraw,transfer", ...)` [8](#0-7) .
4. The runtime host function `promise_batch_action_add_key_with_function_call` splits this string on `,` via `split_method_names`, producing `["withdraw", "transfer"]` as the stored `FunctionCallPermission.method_names` on-chain [4](#0-3) .
5. The relayer's key — nominally restricted to the (never-matchable) single method `"withdraw,transfer"` — can now successfully call `"transfer"` (or `"withdraw"`) on the eth-implicit account's designated receiver, moving funds/authorizing calls that were never actually reviewed/signed for by the account owner in that granular form.

Note: full confirmation that the ABI decoder (`ethabi`) and `types.rs::Action::try_into_near_action` place no restriction on comma characters inside a `String` array element was verified by inspection of `types.rs` and `near_action.rs`; I did not find any character-validation logic on `method_names` elements in the wallet-contract crate. If such validation exists elsewhere and was not surfaced by search, that would mitigate this finding — this should be double-checked in a live session.

/// Uses `,` separator to split `method_names` into a vector of method names.
/// Returns an empty vec if the empty slice is given.
/// Throws `HostError::EmptyMethodName` in case there is an empty method name inside.
pub(crate) fn split_method_names(method_names: &[u8]) -> Result<Vec<Vec<u8>>, HostError> {
    if method_names.is_empty() {
        Ok(vec![])
    } else {
        method_names
            .split(|c| *c == b',')
            .map(|v| if v.is_empty() { Err(HostError::EmptyMethodName) } else { Ok(v.to_vec()) })
            .collect()
    }
}

fn abi_encode(target: String, action: Action) -> Vec<u8> {
    const ADD_KEY_SELECTOR: &[u8] = &[0x75, 0x3c, 0xe5, 0xab];
    const TRANSFER_SELECTOR: &[u8] = &[0x3e, 0xd6, 0x41, 0x24];

    let mut buf = Vec::new();
    match action {
        Action::AddKey(add_key) => {
            buf.extend_from_slice(ADD_KEY_SELECTOR);
            let (public_key_kind, public_key) = match add_key.public_key {
                PublicKey::ED25519(key) => (0, key.as_ref().to_vec()),
                PublicKey::SECP256K1(key) => (1, key.as_ref().to_vec()),
                // ETH-style wallet contracts cover ed25519/secp256k1 only;
                // ML-DSA-65 access keys do not flow through this path.
                PublicKey::MLDSA65(_) => {
                    panic!("test fed an ML-DSA-65 pubkey into the ETH wallet contract ABI path")
                }
            };
            let nonce = add_key.access_key.nonce;
            let (is_full_access, is_limited_allowance, allowance, receiver_id, method_names) =
                match add_key.access_key.permission {
                    AccessKeyPermission::FullAccess => {
                        (true, false, Balance::ZERO, String::new(), Vec::new())
                    }
                    AccessKeyPermission::FunctionCall(permission) => (
                        false,
                        permission.allowance.is_some(),
                        permission.allowance.unwrap_or_default(),
                        permission.receiver_id,
                        permission.method_names,
                    ),
                    // TODO(gas-keys): do we need to support GasKey permissions here?
                    AccessKeyPermission::GasKeyFullAccess(_) => unimplemented!(),
                    AccessKeyPermission::GasKeyFunctionCall(_, _) => unimplemented!(),

            let tokens = &[
                ethabi::Token::Uint(public_key_kind.into()),
                ethabi::Token::Bytes(public_key),
                ethabi::Token::Uint(nonce.into()),

                ethabi::Token::Bool(is_limited_allowance),
                ethabi::Token::Uint(allowance.as_yoctonear().into()),
                ethabi::Token::String(receiver_id),
                ethabi::Token::Array(method_names.into_iter().map(ethabi::Token::String).collect()),
            ];
            buf.extend_from_slice(&ethabi::encode(tokens));
