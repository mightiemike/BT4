### Title
Reachable panic on `RuntimeError::ReceiptValidationError`/`UnexpectedIntegerOverflow` in the apply loop causes a transaction-triggered chunk-application halt - ([File: chain/chain/src/runtime/mod.rs])

### Summary
`chain/chain/src/runtime/mod.rs` maps `RuntimeError` variants returned from `Runtime::apply` into either graceful `Error` values or a hard `panic!`. Two variants, `RuntimeError::UnexpectedIntegerOverflow` and `RuntimeError::ReceiptValidationError`, are explicitly converted into `panic!(...)` calls with a `TODO(#2152): process gracefully` comment marking them as known-unhandled paths. [1](#0-0) 

### Finding Description
This mirrors the CVE-2024-24432 bug class exactly: a reachable assertion/panic inside core message/transaction processing that can be triggered by attacker-controlled input to crash the process (DoS), rather than being confined to a debug-only or truly-unreachable invariant check.

In nearcore, `Runtime::apply` (`runtime/runtime/src/lib.rs:1860`) is the state-transition function invoked once per chunk for every submitted transaction and cross-shard receipt. Its `Result<ApplyResult, RuntimeError>` is unwrapped by the caller in `chain/chain/src/runtime/mod.rs` via a `match` that turns `RuntimeError::UnexpectedIntegerOverflow` and `RuntimeError::ReceiptValidationError` into hard Rust panics rather than propagating them as an `Error` the chain layer can handle (e.g., `Error::InvalidTransactions` or `Error::StorageError`, as the other two variants do).

`ReceiptValidationError` is the type returned by `validate_receipt`, which is invoked from within the action-execution loop against *newly created receipts* (i.e., receipts materialized from a contract call's promises/actions during `apply_action`), at `runtime/runtime/src/lib.rs:969-979`. If a validation check that is supposed to catch a malformed/oversized new receipt before it is committed is bypassed or has a gap (for example a new action kind, encoding edge case, or limit-check ordering bug not caught by `validate_actions_with_mode`/`validate_receipt`), the error surfaces up through `Runtime::apply` as `RuntimeError::ReceiptValidationError`, and the calling glue in `chain/chain/src/runtime/mod.rs:372` immediately `panic!`s the node process for the entire chunk — not just failing the one action/receipt.

Similarly, `UnexpectedIntegerOverflow` originates from checked-arithmetic paths inside the runtime (e.g., `update_validator_accounts`, `runtime/runtime/src/lib.rs:1751-1793`) that are meant to be defense-in-depth "should never happen" invariants, but if the invariant is ever wrong (protocol upgrade edge case, rounding bug in stake/reward accounting, or an integer overflow triggered by carefully sized stake/reward amounts across epoch boundaries), the resulting error is turned into a hard panic instead of a recoverable `Error`.

The key parallel to the Open5GS CVE is structural: both are "reachable assertion" bugs where a validation gap deep in message/state processing surfaces as a language-level abort (Rust `panic!` / C `assert`) instead of a typed, recoverable error, turning an input-validation gap into an availability failure for the whole node/process rather than a rejected single message.

### Impact Explanation
A panic thrown from within chunk application in `chain/chain/src/runtime/mod.rs` aborts processing of the entire chunk on every validator/node applying it — this is a transaction-triggered halt, one of the explicitly accepted high-severity outcomes (denial of service against block/chunk production, potentially affecting all honest nodes simultaneously since `apply` is deterministic and every node processes the same chunk). This is categorically worse than a single failed transaction/receipt, because the surrounding code has multiple other `RuntimeError` variants (`InvalidTxError`, `StorageError`, `ValidatorError`) that are handled gracefully — only these two are explicitly panic-only, and the accompanying `TODO(#2152)` comments confirm this is a recognized, still-open gap rather than an intentional invariant crash.

### Likelihood Explanation
Likelihood is Medium: reaching either panic requires actually hitting a validation/arithmetic gap the developers believe should not occur ("should never happen" invariants), so it is not trivially triggerable with an arbitrary transaction today. However, `ReceiptValidationError` is reachable through any code path that creates a *new* receipt via contract-execution promises (FunctionCall-driven `promise_batch_action_*` host calls), which is fully attacker-influenced input (method args, action composition) processed by `validate_receipt` before commit; a bypassable limit or an unhandled new action encoding here reaches the panic directly from a contract call made by any unprivileged caller. The extensive test suite guarding action validation (`validate_actions_with_mode`, universal/deterministic state-init limits, delegate-action nesting, etc., seen throughout `runtime/runtime/src/action_validation.rs`) indicates the nearcore team is actively hardening exactly this surface, meaning any regression or missed edge case in a newly added action type converts directly into this panic path.

### Recommendation
- Replace the `panic!` arms for `RuntimeError::ReceiptValidationError` and `RuntimeError::UnexpectedIntegerOverflow` in `chain/chain/src/runtime/mod.rs:366-372` with a graceful `Error` variant (e.g., treat as a chunk-application/consensus-halting error that is surfaced and handled the same way `Error::StorageError` is, or, if genuinely unrecoverable, ensure it is at minimum logged with full context and triggers a controlled shutdown rather than an uncontrolled panic mid-apply).
- Audit every code path that can produce a `ReceiptValidationError` for a *new* receipt to guarantee `validate_receipt`/`validate_actions_with_mode` is exhaustive over all `Action` variants (particularly newly-added ones like `UniversalStateInit`, `DeterministicStateInit`, `TransferToGasKey`, `WithdrawFromGasKey`, `DelegateV2`) so that no attacker-composable action sequence from a `FunctionCall`'s promise batch can produce an invalid receipt that slips past validation.
- Add fuzz/property tests that specifically attempt to drive `Runtime::apply` into returning `ReceiptValidationError`/`UnexpectedIntegerOverflow` from a single transaction, to close TODO(#2152) rather than leaving it open.

### Proof of Concept
A concrete PoC transaction sequence could not be constructed without further investigation into which exact validation gap (if any) currently exists in `validate_receipt`/`validate_actions_with_mode` for the newest action variants, since the provided context did not reveal an unguarded case reaching the panic today — the codebase shows heavy, apparently effective validation coverage (see `runtime/runtime/src/action_validation.rs` and the associated test suite) for existing action types.
