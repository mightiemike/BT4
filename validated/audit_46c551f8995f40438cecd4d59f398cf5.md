### Title
Cross-shard receipt failing `validate_receipt` triggers unconditional `panic!` on `RuntimeError::ReceiptValidationError`, halting the validator (analog of CVE-2015-2929) - ([File: chain/chain/src/runtime/mod.rs])

### Summary
CVE-2015-2929 is a Tor bug where a remote, unprivileged peer sends a malformed Hidden-Service descriptor that fails an internal sanity check, hitting an `assert()` and crashing the client. The nearcore analog is a receipt that is malformed/invalid relative to the current validation rules arriving as an *incoming* cross-shard receipt: `process_incoming_receipts` calls `validate_receipt(..., ValidateReceiptMode::ExistingReceipt)` and converts any validation failure directly into `RuntimeError::ReceiptValidationError` [1](#0-0) . That error is then turned into an unconditional `panic!("{}", e)` in the chain runtime adapter that wraps `Runtime::apply` [2](#0-1) , which aborts the node process instead of returning a recoverable `Error`.

### Finding Description
`Runtime::apply` is the top-level chunk state-transition entry point that every validator/RPC node executes when applying a chunk, including receipts routed to it from other shards. Incoming (cross-shard) receipts are only validated in the lenient `ExistingReceipt` mode, which was intentionally weakened because "there is a bug which allows to create receipts that are above the size limit," per the doc comment on `ValidateReceiptMode::ExistingReceipt` [3](#0-2) . Any receipt that still fails this lenient validation (e.g. an oversized/malformed receipt admitted under a known historical bug, or a receipt whose fields fail id/limit checks in `validate_receipt`/`validate_action_receipt`) is converted straight into `RuntimeError::ReceiptValidationError` inside `process_incoming_receipts` [1](#0-0) .

Unlike `RuntimeError::InvalidTxError`, which is handled gracefully (`Error::InvalidTransactions`), the call site in `chain/chain/src/runtime/mod.rs` maps `RuntimeError::ReceiptValidationError(e)` to `panic!("{}", e)` [4](#0-3) . Because the receipt is produced by a different shard as an ordinary consequence of executing some earlier transaction/receipt (i.e., it is fully attacker/transaction-controlled content flowing between shards, not a network-layer or validator-only artifact), a single malformed cross-shard receipt is sufficient to crash every honest node that applies the receiving shard's chunk — mirroring the Tor CVE's "malformed descriptor → assertion failure → application exit" pattern.

### Impact Explanation
This is a transaction-triggered halt: any node (validator or RPC/tracking node) that applies the chunk containing the malformed incoming receipt calls `panic!`, terminating the process. Because all honest nodes tracking that shard receive and must apply the same receipt, this is a deterministic, network-wide denial of service rather than a single-node crash, directly matching the "transaction-triggered halt" category called out in the validation rules.

### Likelihood Explanation
The `ExistingReceipt` validation mode is explicitly documented as weaker than `NewReceipt` validation specifically because of a known bug (referenced as nearcore issue #12606 in the code comments) that lets over-limit receipts be created and slip past the strict checks applied at creation time [5](#0-4) . The codebase's own regression tests (`test_max_receipt_size_promise_return`) exist precisely to demonstrate that such oversized receipts can be generated by an ordinary contract call and must not crash the runtime [6](#0-5) ; but that test only covers the path where the oversized receipt is generated locally as an *outgoing* receipt, not the case where it arrives as an *incoming* receipt on the receiving shard and fails `validate_receipt` there, which still results in the `panic!` at `chain/chain/src/runtime/mod.rs:372`. The reachability from an unprivileged, ordinary `FunctionCall`/promise chain (deployable by any signer) makes this plausible without special validator or network privileges.

### Recommendation
Change the `RuntimeError::ReceiptValidationError` arm in `chain/chain/src/runtime/mod.rs` (and any similar callers, e.g. `integration-tests/src/user/runtime_user.rs`) from `panic!` to a recoverable `Error` (as is already done for `RuntimeError::InvalidTxError`), or fix the root-cause bug (#12606) so that oversized/invalid receipts can never be produced or admitted as incoming receipts, ensuring `process_incoming_receipts` cannot observe a validation failure in production. At minimum, treat `ReceiptValidationError` the same way `StorageInconsistentState` is treated for delayed receipts — as a non-fatal `Error::StorageError`/chunk-processing error — rather than aborting the process.

### Proof of Concept
1. A contract deployed by any account uses the promise API to build a receipt (e.g. via `output_data_receivers`/`promise_return`, as used in `test_max_receipt_size_promise_return`) whose serialized size exceeds `max_receipt_size` due to the known creation-time gap (#12606) [6](#0-5) .
2. That oversized receipt is routed as an **incoming** receipt to the target shard in the next chunk.
3. On the receiving shard, `Runtime::apply` → `process_incoming_receipts` calls `validate_receipt(..., ExistingReceipt)`, which fails on `ReceiptSizeExceeded` (or another `ReceiptValidationError` variant), producing `RuntimeError::ReceiptValidationError` [7](#0-6) .
4. `chain/chain/src/runtime/mod.rs` maps this to `panic!("{}", e)`, crashing every honest node that applies that shard's chunk [4](#0-3) .
