### Title
Missing deep-copy of child `Storage` object before the ENERGY_LIMIT hard fork lets reverted/rejected internal calls corrupt parent contract storage - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.getStorage()` is supposed to give each nested `Repository` (created for every internal `CALL`/`CREATE`) its own independent `Storage` object, so that writes made by a child execution frame can be safely discarded if that frame reverts or throws, and only get applied to the parent when `commit()` is explicitly invoked. When `StorageUtils.getEnergyLimitHardFork()` is false, the code instead does `storage = parentStorage;`, i.e. the child reuses the exact same `Storage` instance (and its internal `rowCache` map) as the parent, rather than making an independent copy. This is analogous to the `ZeroLocker` `initialLastPoint = lastPoint` aliasing bug: a variable that is meant to represent an isolated snapshot is actually a shared reference, so mutations meant to be scoped to the child leak straight into the parent regardless of whether `commit()`/rollback logic ever runs.

### Finding Description
`getStorage()`:
```java
@Override
public Storage getStorage(byte[] address) {
  Key key = Key.create(address);
  if (storageCache.containsKey(key)) {
    return storageCache.get(key);
  }
  Storage storage;
  if (this.parent != null) {
    Storage parentStorage = parent.getStorage(address);
    if (StorageUtils.getEnergyLimitHardFork()) {
      // deep copy
      storage = new Storage(parentStorage);
    } else {
      storage = parentStorage;
    }
  } else {
    storage = new Storage(address, getStorageRowStore());
  }
  ...
``` [1](#0-0) 

The `Storage` class itself has a proper deep-copy constructor that clones `addrHash`, `address`, and every `StorageRowCapsule` in `rowCache`: [2](#0-1) 

But that path is only taken when `StorageUtils.getEnergyLimitHardFork()` is true. When it is false, `storage = parentStorage` makes the child's `Storage` variable an alias to the parent's, exactly like the Solidity `Point memory initialLastPoint = lastPoint;` bug that failed to create an independent copy.

Because `putStorageValue`/`getStorageValue` mutate the shared `rowCache` `HashMap` directly (`storage.put(key, value)` in `Storage.put`), any write performed through the child `Repository` (e.g. inside an internal `CALL`/`CREATE` created in `Program.createContractImpl`/`Program.callToAddress` via `getContractState().newRepositoryChild()`) is immediately visible in the parent's storage object — independent of whether the child ever calls `commit()`. The `commitStorageCache` logic that is supposed to gate propagation from child to parent becomes meaningless for storage, because the "child" and "parent" objects are the same object: [3](#0-2) 

Critically, on exception or `REVERT` inside an internal call, `Program.callToAddress`/`createContractImpl` deliberately skip `deposit.commit()` and instead reject the internal transaction, expecting the child's cached mutations to simply be discarded because they were never merged into the parent: [4](#0-3) 

With the aliasing bug, storage writes already happened in-place on the (shared) `rowCache`, so they are **not** discarded on revert/exception — the parent repository (and ultimately the persisted `StorageRowStore` on `commit()` of the root) ends up with contract storage state from a call that was supposed to be rolled back.

The project's own regression test explicitly documents and exercises this "old version" (pre-hard-fork) sharing behavior, confirming that writes to the child are immediately observable in the root/parent before any `commit()` is called: [5](#0-4) 

### Impact Explanation
This breaks the fundamental TVM invariant that state changes made in a nested call frame are only committed if that frame succeeds. When the hard fork flag is off (fresh/private chains bootstrapping the node, or forks that have not yet reached the activation block height for `ENERGY_LIMIT_HARD_FORK`), any user-submitted transaction that triggers an internal `CALL`/`CREATE` that later reverts or throws (`OutOfEnergyException`, `REVERT` opcode, `TransferException`, stack overflow, etc.) can still leave storage-slot writes performed during that failed internal call permanently applied to the target contract's storage. This is a consensus-relevant state-corruption bug reachable by anyone broadcasting a normal smart-contract transaction (no privileged actor needed), and it can be used to desynchronize storage state from what should have resulted from correct EVM/TVM semantics, or by an attacker to force storage writes to persist despite reverting the surrounding call (e.g. to leave behind approvals/balances/flags in a victim contract that a revert should have undone).

### Likelihood Explanation
The vulnerable path is guarded by a single boolean feature flag (`StorageUtils.getEnergyLimitHardFork()`), which is derived from on-chain fork-activation state (`statsByVersion(ForkBlockVersionConsts.ENERGY_LIMIT, ...)`). Any deployment that has not yet activated this specific hard fork (new private chains, sidechains, or a node bootstrapping from genesis before this particular fork height is reached) runs with the vulnerable code path active by default, and the bug is triggered by ordinary internal contract calls that revert — a very common and easily attacker-controlled condition, requiring no special permissions.

### Recommendation
Remove the conditional branch entirely and always perform the deep copy (`storage = new Storage(parentStorage);`) regardless of the hard-fork flag, so a child `Repository`'s `Storage` object is always independent from its parent's until explicitly merged via `commit()`. If backward-compatibility with historical chain data processed under the old flag is required, ensure any legacy branch is only used for replaying/verifying old blocks and never for live transaction execution going forward.

### Proof of Concept
1. Deploy/observe a node where `StorageUtils.getEnergyLimitHardFork()` returns `false` (e.g. fresh chain before fork activation, as reproduced by `StorageTest.testParentChildOldVersion` which explicitly sets up this scenario).
2. Contract A has a `CALL` to contract B that writes to storage slot `X` and then reverts (or an internal transfer fails, throwing `TransferException`/`OutOfEnergyException` before `deposit.commit()` is reached in `Program.callToAddress`).
3. Because `RepositoryImpl.getStorage()` returned the parent's exact `Storage` object for B's child repository, `storage.put(X, value)` already mutated the shared `rowCache` at write time.
4. Even though `callResult.getException() != null` causes `internalTx.reject()` and `callResult.rejectInternalTransactions()` (no `deposit.commit()`), when the root transaction eventually commits, the storage row for `X` in contract B is still updated with the value written by the reverted internal call, as directly demonstrated by `StorageTest.testParentChildOldVersion` asserting `rootRepository.getStorageValue(...)` reflects the child's writes without any explicit `childRepository.commit()` call: [6](#0-5)
