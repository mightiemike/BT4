### Title
Unrecovered `panic` in lazy field-index construction on malformed-but-accepted wire bytes causes process crash - ([File: internal/protolazy/lazy.go])

### Summary
`proto.Unmarshal` on a message with lazily-decoded submessage fields defers full validation of the containing buffer. When that buffer is later indexed on-demand (triggered by ordinary access to any lazy field), `protolazy.buildIndex` re-parses the same bytes with a *stricter, buggier* tag-varint parser than the one used during the original `Unmarshal`. If `buildIndex` fails, the caller does not return an error — it calls `panic(...)`, unconditionally crashing the process. This mirrors the Vapor bug pattern: bytes accepted as parseable at one stage trigger a hard, unrecoverable failure (assertion/panic) at a later stage on the same unprivileged data path.

### Finding Description
`proto.Unmarshal` for a message with message/group-typed fields eligible for lazy decoding routes through `MessageInfo.unmarshalPointerLazy` (`internal/impl/lazy.go:175`). Its top-level tag-parsing loop decodes multi-byte tags via a fast 2-byte check, falling back to `protowire.ConsumeVarint(b)` for anything longer: [1](#0-0) 

`protowire.ConsumeVarint` accepts the full standard varint range (up to 10 bytes / 64 bits), including redundant/"denormalized" over-long encodings of small values — this is a recognized, intentionally-supported wire-format edge case (see `Denormalized` handling in `testing/protopack/pack.go:338`). So a message whose tag bytes are encoded with extra continuation bytes (still resolving to a valid field number) is accepted by `unmarshalPointerLazy` with no top-level error, and `proto.Unmarshal` returns success. The raw buffer is stored unmodified for later lazy access: [2](#0-1) 

Later, when *any* lazily-deferred field of that same message is accessed (a completely ordinary operation — e.g. a generated getter or reflection `Get` on a message-typed field), `MessageInfo.lazyUnmarshal` is invoked: [3](#0-2) 

This calls `XXX_lazyUnmarshalInfo.FindFieldInProto`, which lazily builds a field index over the *entire* stored buffer via `buildIndex`: [4](#0-3) 

Critically, if `buildIndex` returns an error, the code does not propagate it as an error — it panics: [5](#0-4) 

`buildIndex`'s own tag-varint decoder, however, is inconsistent with the one used in `unmarshalPointerLazy`/`protowire.ConsumeVarint`. It only unrolls a fixed 5-byte fast path when 5+ bytes remain in the buffer, and returns `errOutOfBounds` if the tag's continuation bit is still set after the 5th byte — even though more bytes remain and a full 64-bit `ConsumeVarint`-style parse would successfully terminate the varint: [6](#0-5) 

The `Remaining() < 5` slow-path fallback is only taken when *fewer* than 5 bytes remain — precisely the case where an over-long-but-valid tag (6–10 bytes) with sufficient trailing bytes will *not* hit the slow path, and will instead be rejected by the 5-byte-only fast path.

This means: a message can be unmarshaled successfully by `proto.Unmarshal` (top-level tag parsing succeeds via `protowire.ConsumeVarint`), yet subsequently panic the process the first time any lazy field on that message is accessed, because `buildIndex` re-parses the exact same bytes with a parser that cannot handle the same over-long tag encoding.

### Impact Explanation
A panic that is not recovered by the caller terminates the goroutine and, in a typical Go server (gRPC handler, HTTP handler, RPC dispatcher) that does not wrap every request in a `recover()`, brings down the whole process — a remote, unauthenticated denial-of-service triggered purely by parsing an untrusted, schema-conforming message. This matches the CWE-231 / "improper handling of parsing errors leading to crash" class described in the Vapor advisory: an input that should have produced a graceful decode error instead reaches an unconditional panic deep in the runtime.

### Likelihood Explanation
Lazy decoding is enabled by default (`LazyEnabled()` returns true unless the `GOPROTODEBUG=nolazy` env var is explicitly set): [7](#0-6) 

Any service that unmarshals attacker-supplied protobuf bytes into a message containing message/group-typed fields, and later accesses those fields (essentially any normal usage pattern), is on this path. The trigger is a single denormalized/over-long tag varint (6+ bytes encoding a valid small field number) placed anywhere in the top-level bytes of such a message.

### Recommendation
- Make `buildIndex`'s tag-varint parser consistent with `protowire.ConsumeVarint` (i.e., always support the full 10-byte / 64-bit varint range, not just a 5-byte fast path gated on `Remaining() >= 5`), or fall back to the slow path whenever the fast path's fixed-width unrolling fails rather than immediately erroring.
- Change `FindFieldInProto` to propagate the `buildIndex` error to the caller (returning `found=false` or bubbling up an error) instead of calling `panic`, so malformed/edge-case wire data degrades to a decode error rather than crashing the process.

### Proof of Concept
Conceptual (not fully verified end-to-end due to inability to run code in this environment — see caveat below):
1. Construct a message type with at least one message-typed field (lazy-eligible by default).
2. Craft wire bytes for that message where one field's tag is encoded as a redundant/over-long varint (6+ bytes, all but the last with the continuation bit set, resolving to a small valid field number), analogous to the `Denormalized` tag construct already exercised in `testing/protopack`.
3. Call `proto.Unmarshal(buf, m)` — this succeeds without error via the `unmarshalPointerLazy` → `protowire.ConsumeVarint` fallback path.
4. Access any lazily-decoded field of `m` (e.g. `m.GetSomeMessageField()`), triggering `lazyUnmarshal` → `FindFieldInProto` → `buildIndex(lazy.Protobuf)`.
5. `buildIndex`'s 5-byte-only fast path rejects the over-long tag with `errOutOfBounds`, and `FindFieldInProto` panics with `"findFieldInfo: error building index when looking for field %d: %v"`, crashing the process if unrecovered.

**Caveat / unverified aspects:** I was unable to fully re-verify, within the available tool budget, the exact maximum-length/overflow semantics of `protowire.ConsumeVarint` (`encoding/protowire/wire.go`) and the exact byte-length threshold at which `coderFieldInfo.isLazy` is set for a given field, to construct a concrete byte-for-byte proof-of-concept guaranteed to compile/run. The control-flow inconsistency between `unmarshalPointerLazy`'s tag parsing and `buildIndex`'s fixed 5-byte fast path, and the unconditional `panic` in `FindFieldInProto` on any `buildIndex` error, are directly confirmed by reading the cited source. A background engineering session with code-execution access would be needed to produce and run a byte-exact proof-of-concept and confirm the discrepancy is actually reachable given all bounds checks (e.g., `Remaining()` semantics in `internal/protolazy/bufferreader.go`, which I could not fully inspect).

// FindFieldInProto looks for field fieldNum in lazyUnmarshalInfo information
// (including protobuf), returns startOffset/endOffset/found.
func (lazy *XXX_lazyUnmarshalInfo) FindFieldInProto(fieldNum uint32) (start, end uint32, found, multipleContiguous bool, multipleEntries []IndexEntry) {
	if lazy.Protobuf == nil {
		// There is no backing protobuf for this message -- it was made from a builder
		return 0, 0, false, false, nil
	}
	index := atomicLoadIndex(&lazy.index)
	if index == nil {
		r, err := buildIndex(lazy.Protobuf)
		if err != nil {
			panic(fmt.Sprintf("findFieldInfo: error building index when looking for field %d: %v", fieldNum, err))
		}
		// lazy.index is a pointer to the slice returned by BuildIndex
		index = &r
		atomicStoreIndex(&lazy.index, index)
	}
	return lookupField(index, fieldNum)
}
