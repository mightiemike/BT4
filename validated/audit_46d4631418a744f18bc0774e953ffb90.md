The reported bug class is an *unbounded* recursion/traversal depth (OctoRPKI never limited certificate chain depth). protobuf-go's analogous code paths — binary unmarshal, protowire group/field consumption, prototext/protojson unmarshal, validation, and map/message decoding — all enforce an explicit recursion depth limit and return `errRecursionDepth` / `ValidationInvalid` once exceeded, so there is no equivalent "runs forever" condition on any decode path with a trusted schema and default parser.

Specifically:
- `protowire.DefaultRecursionLimit = 10000` bounds nested groups in `consumeFieldValueD` (`encoding/protowire/wire.go`) [1](#0-0) [2](#0-1) .
- `proto.Unmarshal`/`UnmarshalOptions.Unmarshal` seed `RecursionLimit` with that default and decrement it on every nested message/map, erroring with `errRecursionDepth` when exhausted [3](#0-2) [4](#0-3) .
- The generated-message fast path in `internal/impl` tracks `depth` the same way in `unmarshalPointer`, `consumeMap`, and `consumeMapOfMessage` [5](#0-4) [6](#0-5) .
- The internal validator (`internal/impl/validate.go`) enforces the same depth bound before recursing into nested/grouped/map states [7](#0-6) .
- `prototext` and `protojson` decoders enforce equivalent `RecursionLimit` checks, confirmed by tests covering exactly-at-limit and exceed-limit cases [8](#0-7) .

Since every relevant decode/validate entry point already caps traversal depth deterministically, there is no reachable unprivileged request path in protobuf-go analogous to OctoRPKI's missing depth check.
