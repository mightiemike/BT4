### Title
Unauthenticated `eth_getLogs`/`eth_newFilter` queries can be crafted to force massive per-request `ByteUtil.decompress` fan-out, and the rate limiter only counts requests/QPS, not query cost, enabling asymmetric RPC-API DoS - ([File: chainbase/src/main/java/org/tron/core/store/SectionBloomStore.java])

### Summary
`SectionBloomStore.get(section, bitIndex)` calls `ByteUtil.decompress` on every unique Bloom bit index for every block-section touched by a log query, and `LogBlockQuery.partialMatch` only memoizes results within a single query invocation (`resultCache`), never across requests. Because `maxAddressSize`, `maxSubTopics`, and `maxBlockRange` bound a single request's cost but not the aggregate cost across many concurrent/parallel requests, and the JSON-RPC servlet's rate limiter (`GlobalRateLimiter`/`RateLimiterServlet`) throttles by request count or QPS rather than by decompression fan-out, an attacker can amplify server CPU work by issuing many maximally-sized queries concurrently.

### Finding Description
The vulnerable path is: `TronJsonRpcImpl.getLogs`/`newFilter`/`getFilterLogs` → `getLogsByLogFilterWrapper` → `LogBlockQuery.getPossibleBlock` → `subMatch`/`partialMatch` → `SectionBloomStore.get(section, bitIndex)` → `ByteUtil.decompress`. [1](#0-0) 

Per query, `LogBlockQuery.partialMatch` collects the *unique* bit indexes from the address/topic conditions and, for each section in `[minSection, maxSection]`, submits a decompress call per unique bit index: [2](#0-1) 

`SectionBloomStore.get` unconditionally runs `Inflater`-based decompression on the stored bytes, with no cross-request cache: [3](#0-2) 

The per-request bounding configs (`maxBlockRange=5000` → ~3 sections of `BLOCK_PER_SECTION=2048`, `maxAddressSize=1000`, `maxSubTopics=1000` per up to 4 topic slots) still permit thousands of OR-conditions per request, each hashed to up to 3 bit indexes within the 2048-bit Bloom space: [4](#0-3) [5](#0-4) [6](#0-5) 

The JSON-RPC servlet's rate limiting only gates request admission (per-IP/global QPS or concurrency permits), not query cost: [7](#0-6) [8](#0-7) 

Since `uniqueBitIndexes` is recomputed and re-decompressed independently for every request (no shared/global cache across `LogBlockQuery` instances), N concurrent maximal-range/maximal-condition requests multiply CPU work roughly linearly with N and with query complexity, while the admission-control layer treats each request as equally "cheap" from a QPS-budget perspective.

### Impact Explanation
This maps to the "DoS via RPC-API" bounty class: sustained CPU exhaustion on the JSON-RPC-enabled node (FullNode/SolidityNode) from a modest number of unauthenticated concurrent `eth_getLogs`/`eth_newFilter`+`eth_getFilterLogs` requests, each within documented per-request limits (`maxBlockRange`, `maxAddressSize`, `maxSubTopics`) but collectively causing disproportionate decompression cost. This can degrade or stall JSON-RPC service availability for legitimate users, without requiring any privileged role, signed transaction, or fee payment.

### Likelihood Explanation
Preconditions are minimal: JSON-RPC HTTP API enabled (`httpFullNodeEnable`/`httpSolidityEnable`), no authentication required, and the ability to open multiple concurrent connections/source IPs (to spread load under `IPQPSRateLimiterAdapter`/`GlobalRateLimiter`'s per-IP QPS caps, or simply operate within the default global QPS budget of 1000/50000). The attacker needs no funded account, no special permissions, and pays no on-chain fee — HTTP requests only. Repeatability is high since it uses only public, documented API parameters, and the cost amplification is structural (no caching across requests) rather than a corner-case bug. That said, the actual severity depends on tuning of `rate.limiter` (default QPS caps, `global.qps`) and hardware capacity, and operators can mitigate by configuring stricter `IPQPSRateLimiterAdapter`/`GlobalPreemptibleAdapter` limits on the JSON-RPC servlet or lowering `maxBlockRange`/`maxAddressSize`/`maxSubTopics`.

### Recommendation
- Introduce a lightweight cross-request cache (e.g., time/size-bounded LRU keyed by `(section, bitIndex)`) for decompressed `BitSet`s in `SectionBloomStore`, since section bitmaps are append-only/immutable once a section is sealed.
- Add a cost-aware admission control for JSON-RPC log queries (e.g., weight permits by estimated section-count × unique-bitIndex count, or a dedicated `GlobalPreemptibleAdapter`/concurrency cap specifically for `eth_getLogs`/`eth_getFilterLogs`).
- Consider tightening default `maxAddressSize`/`maxSubTopics`/`maxBlockRange` and/or adding a combined "query complexity budget" check in `LogFilter`/`LogFilterWrapper` construction that rejects filters whose address×topic combinatorics exceed a safe threshold.

Fire this request from N concurrent connections/source IPs (e.g., N=50-100 via a simple load-testing script such as `wrk`/`hey` with distinct `X-Forwarded-For`/source sockets to spread across `IPQPSRateLimiterAdapter` buckets). Expected observation: CPU time inside `Inflater.inflate` (via `ByteUtil.decompress`, called from `SectionBloomStore.get`) scales roughly linearly with N and with (sections × unique bit indexes), confirmed via JFR/async-profiler sampling on the node process, while `GlobalRateLimiter`/`RateLimiterServlet` continue to admit requests based on QPS/IP quotas rather than rejecting based on the underlying decompression fan-out — i.e., the configured "cheap" request-based rate limit does not prevent the aggregate CPU amplification.

  private BitSet partialMatch(final int[][] bitIndexes, int section)
      throws ExecutionException, InterruptedException {
    // 1. Collect all unique bitIndexes
    Set<Integer> uniqueBitIndexes = new HashSet<>();
    for (int[] index : bitIndexes) {
      for (int bitIndex : index) { //normally 3, but could be less due to hash collisions
        uniqueBitIndexes.add(bitIndex);
      }
    }

    // 2. Submit concurrent requests for all unique bitIndexes
    Map<Integer, Future<BitSet>> bitIndexResults = new HashMap<>();
    for (int bitIndex : uniqueBitIndexes) {
      Future<BitSet> future
          = sectionExecutor.submit(() -> sectionBloomStore.get(section, bitIndex));
      bitIndexResults.put(bitIndex, future);
    }

    // 3. Wait for all results and cache them
    Map<Integer, BitSet> resultCache = new HashMap<>();
    for (Map.Entry<Integer, Future<BitSet>> entry : bitIndexResults.entrySet()) {
      BitSet result = entry.getValue().get();
      if (result != null) {
        resultCache.put(entry.getKey(), result);
      }
    }

  public BitSet get(int section, int bitIndex) throws EventBloomException {
    long keyLong = combineKey(section, bitIndex);
    byte[] key = Long.toHexString(keyLong).getBytes();
    BytesCapsule bytesCapsule = get(key);
    if (bytesCapsule == null) {
      return null;
    }
    byte[] data;
    try {
      data = ByteUtil.decompress(bytesCapsule.getData());
    } catch (Exception e) {
      throw new EventBloomException("decompress byte failed");
    }
    return BitSet.valueOf(data);
  }
