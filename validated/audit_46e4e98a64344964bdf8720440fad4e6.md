This confirms the analog. The Stacks codebase itself explicitly documents that the `ResourceBudget`/`ResourceLimiter` wall-clock timers used during miner block-assembly and signer block-proposal validation are deliberately **non-deterministic** and must never gate consensus-critical state transitions — only the deterministic `ExecutionCost` tracker (used with `ResourceBudget::unlimited()`) is consensus-critical [1](#0-0) . This is the same "expensive computation must be reproduced under an independent, overhead-bearing budget" bug class as the OP report, applied to the Stacks signer's block-validation flow.

### Title
Wall-clock-based per-tx/per-block validation timeouts in `/v3/block_proposal` cause non-reproducible, machine-speed-dependent signer verdicts on the same block - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
A miner can craft a transaction (or set of transactions) whose real Clarity execution/analysis time sits close to the configured `block_proposal_max_tx_execution_time_secs` / `block_proposal_max_tx_analysis_time_secs` / `block_proposal_validation_timeout_secs` budgets. Because these budgets are enforced via wall-clock `Instant`-based timers rather than the deterministic, consensus-critical `ExecutionCost` model, different signer nodes — with different CPU speed, load, or concurrent validation work — can independently arrive at different verdicts (`Success` vs. `ProblematicTransaction`/`InvalidBlock`) for the *exact same block*, even though the block is fully valid and was successfully produced by the miner.

### Finding Description
Stacks' consensus-critical state transition uses the deterministic cost tracker (`ExecutionCost`), and `StacksChainState::process_transaction` is always invoked with `ResourceBudget::unlimited()`/`TransactionResourceBudgets::unlimited()` on the replay/commit path so the actual chain state is fully deterministic across nodes [2](#0-1) .

However, the signer-invoked `/v3/block_proposal` validation path (`NakamotoBlockProposal::validate`) additionally enforces wall-clock deadlines that are *not* part of that deterministic model: an overall `block_deadline` computed from `timeout_secs` and a per-transaction `per_tx_max_execution_time` / `per_tx_max_analysis_time`, both measured with `Instant::now()` [3](#0-2) . If a per-tx timer or the block-level deadline elapses, the transaction is classified `Problematic`/the block is rejected as `InvalidBlock`, purely due to local timing [4](#0-3) .

These timers are implemented with `TimeTracker::MaxTime`, whose `check_not_expired` compares `Instant::elapsed()` against a fixed `Duration` [5](#0-4) . `ResourceLimiter`/`ResourceBudget` are explicitly documented as "NOT related to cost tracking," used only for "defense-in-depth" on "non-consensus voting paths (mining/block-proposal validation)" [6](#0-5) , and `TransactionResourceBudgets` documentation states these budgets "MUST be `ResourceBudget::unlimited()` during consensus-critical processing, because that must remain deterministic" [7](#0-6) .

This is precisely the OP fault-proof bug class transplanted onto Stacks' signer verification layer: a computation ("the transaction actually executes fine and was included by the miner") must be reproduced by a second party (the signer node validating the proposal) under an artificial resource envelope (wall-clock time) whose availability is *not* guaranteed to match across machines — unlike the OP case where the overhead was a fixed extra-gas cost, here the "overhead" is simply CPU-speed/load variance, but the effect is the same: the same input can pass on the original executor and fail reproduction on a different, honest verifier.

### Impact Explanation
Because block approval in Nakamoto requires a supermajority (70%) of signer weight, a single miner cannot force acceptance of an invalid block this way. But a minority of signers on slower/busier hardware will independently and non-maliciously produce `ProblematicTransaction`/`InvalidBlock` rejections for a block that other signers accept, purely as an artifact of wall-clock speed rather than of the block's actual validity. This yields "a validation verdict two nodes disagree on" for identical input — matching the allowed High-severity impact class of "static-validation divergence ... temporary tip disagreement." It can also cause a miner's otherwise-valid block to be rejected by more signers than expected near the timeout thresholds, delaying tenure or triggering unnecessary tenure-extend logic, without requiring any signer/majority collusion, private key access, or Bitcoin-consensus assumptions.

### Likelihood Explanation
Triggering this only requires a minority actor (the block-proposing miner) to include a transaction whose Clarity execution or contract-analysis time is engineered to sit near the default budgets (`DEFAULT_BLOCK_PROPOSAL_MAX_TX_EXECUTION_TIME_SECS` = 30s, `DEFAULT_BLOCK_PROPOSAL_MAX_TX_ANALYSIS_TIME_SECS` = 30s, `DEFAULT_BLOCK_PROPOSAL_VALIDATION_TIMEOUT_SECS` = 60s) [8](#0-7) . This is entirely feasible with expensive-but-legal Clarity contracts (e.g., large read-count loops, as already exercised by the existing `replay_validation_test_budget_exhausted`/analysis-timeout tests) [9](#0-8) , without needing any operator, admin, or another party's key. It does not require majority control — only that different signer nodes' hardware/load naturally straddle the timing threshold on the same input.

### Recommendation
Do not gate signer approve/reject decisions on wall-clock measurements taken independently per node. Either (a) derive the per-tx/per-block "problematic" classification purely from the deterministic `ExecutionCost` budget already used for consensus, or (b) if wall-clock protection must remain for defense-in-depth against runaway VM bugs, ensure its thresholds are set with enough margin (and/or normalized against a reference benchmark) that no legitimately-costed transaction (within the deterministic cost budget) can plausibly straddle the timeout on reasonably provisioned hardware, and treat any wall-clock-triggered rejection as informational/soft rather than a hard `ProblematicTransaction`/`InvalidBlock` verdict that feeds into the signer's vote.

### Proof of Concept
1. Deploy/submit a smart contract whose read/compute pattern is legal under the deterministic `ExecutionCost` budget but takes real wall-clock time close to `block_proposal_max_tx_execution_time_secs` (e.g., a large-`read_count` loop, as constructed by `make_big_read_count_contract` in the existing replay tests) [10](#0-9) .
2. The miner successfully mines and proposes a block containing this transaction (its own `max_execution_time_secs` may be looser, as shown in `signer_rejects_contract_publish_on_analysis_time_expired`, where miner and validator configs intentionally diverge) [11](#0-10) .
3. Signers on faster/idle hardware validate the transaction within budget and vote to accept; signers on slower/busier hardware hit `check_not_expired` first and reject it as `ProblematicTransaction`/`InvalidBlock` [4](#0-3) , producing a temporary split in signer verdicts for an identical, otherwise-valid block.
