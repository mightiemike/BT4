### Title
Precision loss in witness brokerage/reward split due to premature division before multiplication - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payReward` (invoked by `payBlockReward` and `payTransactionFeeReward`, both called for every block reward and every transaction-fee reward payout to Super Representatives) computes the witness's brokerage cut by first dividing the integer `brokerage` percentage by `100` as a `double`, and only then multiplying by `value`. This mirrors exactly the reported bug class: doing division in the middle of a fee calculation instead of last, causing systematic underpayment (leaked value) that accumulates every cycle.

### Finding Description [1](#0-0) 

```java
private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
}
```

The correct order for accuracy would be `brokerageAmount = brokerage * value / 100` (multiply first, then divide, ideally using integer/`BigInteger` math to avoid double rounding). Instead, `brokerage / 100` is computed first as a `double`, which:
1. Loses precision because `brokerage/100` is frequently not exactly representable in binary floating point (e.g. `20/100 = 0.2`, which is not exact in IEEE-754 double).
2. Truncates the final product `(long) (brokerageRate * value)` to a long, discarding fractional remainder — this is exactly the "division in the midst of calculation" pattern called out in the referenced report, causing systematic leakage rather than just rounding noise.

This function is on the reward-distribution hot path called for both `payBlockReward` and `payTransactionFeeReward` [2](#0-1) , which are invoked by the block-producing/consensus reward logic in `Manager.java` on every produced block, for every witness, every cycle.

By contrast, other reward-related computations in the same codebase (e.g. `computeReward` for the Vi-based new algorithm, `RewardViCalService.accumulateWitnessVi`, `DelegationStore.accumulateWitnessVi`) correctly use `BigInteger` and perform multiplication before division: `reward.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)` [3](#0-2) . `payReward`'s brokerage split was not similarly hardened.

### Impact Explanation
Every block reward and transaction fee reward paid to every Super Representative on the network is split between witness self-take (brokerage) and voter rewards via this exact code path. Precision loss here causes small but continuous misallocation between the `brokerageAmount` credited to the witness's allowance and the `value` credited to the voter reward pool for that cycle, on essentially every block. Over the life of the chain across all 27+ active witnesses, this compounds into a nontrivial, protocol-wide value leakage/misaccounting between witnesses and their voters — a resource/reward accounting corruption analogous to the referenced medium-severity finding, though the amount lost per call is a fraction of a SUN.

### Likelihood Explanation
This is not a privileged or adversarial path — it executes automatically and deterministically on every block for every witness as part of core consensus reward accounting, so the likelihood of it firing is effectively 100% under normal operation. It is not currently gated behind any `hardenCalculation`/`allowHarden...` feature flag the way other resource/energy calculations in the codebase have been, so no opt-in fix is currently possible.

### Recommendation
Replace the double-based percentage calculation with integer/`BigInteger` arithmetic that multiplies before dividing, consistent with the pattern already used elsewhere in the codebase (e.g. `DelegationStore.accumulateWitnessVi`, `ResourceProcessor.calculateGlobalLimitV1`):

```java
long brokerageAmount = BigInteger.valueOf(value)
    .multiply(BigInteger.valueOf(brokerage))
    .divide(BigInteger.valueOf(100))
    .longValueExact();
```

This eliminates floating point rounding error entirely and matches the mitigation recommended in the referenced report (do all multiplication first, then divide once at the end).

### Proof of Concept
With `brokerage = 33` and `value = 100` (a single reward payout):
- Buggy path: `brokerageRate = (double) 33 / 100 = 0.33` (exact in this case, but generally not exact for arbitrary integers), `brokerageAmount = (long)(0.33 * 100) = 33` — appears fine for round numbers, but for values like `brokerage = 7`, `value = 999_999_999_999L`:
  - Buggy: `brokerageRate = 0.07` (not exactly representable), `brokerageAmount = (long)(0.07 * 999999999999) = 69999999999` (potential off-by-one vs exact due to floating point representation error, and definitely diverges once `value` grows into ranges where double mantissa (53 bits) can't exactly represent the product).
  - Correct: `BigInteger.valueOf(999999999999L).multiply(BigInteger.valueOf(7)).divide(BigInteger.valueOf(100)) = 69999999999` exactly, guaranteed no rounding drift regardless of magnitude.
- As `value` approaches or exceeds 2^53 (~9×10^15 SUN, i.e. ~9 million TRX in SUN units, plausible for large aggregate block/fee reward pools), double-precision multiplication in `brokerageRate * value` can no longer represent the exact integer product, guaranteeing measurable, reproducible truncation/rounding divergence from the mathematically correct integer result on every affected payout.
