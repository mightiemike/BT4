### Title
Unvalidated `beneficiary_id` in `DeleteAccountAction` Permanently Burns Funds When Beneficiary Account Does Not Exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction::beneficiary_id` is only checked for *syntactic* account-id validity before the delete is executed. Nothing verifies that the beneficiary account actually exists. Because the balance payout is issued as a separate, already-committed system refund receipt after the source account has been irreversibly deleted, a `beneficiary_id` that does not resolve to a live (or creatable) account causes the entire remaining balance to be permanently burned instead of delivered or returned to the signer.

### Finding Description
`validate_delete_action` only runs `validate_action_account_id`, a pure syntax check, on `beneficiary_id`: [1](#0-0) 

`action_delete_account` then unconditionally queues a `Transfer` refund receipt to that (unverified) `beneficiary_id`, deletes the account, and the deletion commits as its own state transition: [2](#0-1) 

The payout is emitted via `Receipt::new_balance_refund`, which is a system-predecessor ("refund") receipt: [3](#0-2) 

When this refund receipt is later processed against a `beneficiary_id` that doesn't exist, `check_account_existence` rejects the `Transfer` action with `AccountDoesNotExist` — and refund receipts are explicitly *not* allowed to implicitly create the destination account, even for accounts whose id format would otherwise support implicit creation: [4](#0-3) 

This is confirmed by the test `refund_may_not_create_universal_account`, which asserts that a balance-refund receipt to a nonexistent id fails with `AccountDoesNotExist` and never creates the account: [5](#0-4) 

Crucially, unlike an ordinary user-initiated `Transfer` to a nonexistent account — which is not committed and effectively costs the sender only fees, since the deposit never left their balance — a *refund* receipt that fails has its deposit **burned**, not returned to anyone: [6](#0-5) 

Because the `DeleteAccount` action and its beneficiary payout are two separate receipts (the delete commits first, the transfer is a follow-up receipt), there is no atomic rollback: once the account is deleted, the funds are already gone from any recoverable account, and if the beneficiary lookup fails, they are destroyed rather than returned to the (now-deleted) source account or the original owner.

### Impact Explanation
Any signer or contract that submits a `DeleteAccount` action with a `beneficiary_id` that is syntactically valid but does not exist (a typo, a since-deleted account, or an account that was never created) will have the account's *entire remaining NEAR balance* irrecoverably burned. This is a direct, transaction-triggered, permanent loss of user funds — exactly the "invalid receiver address" failure mode described in the reference report, but here it results in outright token destruction (reducing total supply) rather than merely stuck funds in a contract.

### Likelihood Explanation
Reachable by any single unprivileged transaction signer (or a contract issuing `promise_batch_action_delete_account`) with no special privileges — a user only needs to mistype or otherwise supply a nonexistent `beneficiary_id` when deleting their own account. No malicious peer, validator, or network-level behavior is required.

### Recommendation
Before executing the account deletion (or before committing it irreversibly), validate that `beneficiary_id` corresponds to an existing account (or is an implicit-account format that can always be created), or execute the deletion and the beneficiary transfer atomically so a beneficiary lookup failure rolls back the deletion instead of burning the funds. At minimum, refund the balance to `predecessor_id`/signer instead of burning it when the beneficiary-lookup refund fails.

### Proof of Concept
1. Account `alice.near` holds balance `B`.
2. `alice.near` submits `DeleteAccount { beneficiary_id: "no-such-account.near" }` (syntactically valid, unused account id).
3. `validate_delete_action` passes (format only) — [1](#0-0) .
4. `action_delete_account` deletes `alice.near` and queues `Receipt::new_balance_refund("no-such-account.near", B)` — [2](#0-1) ; the delete-account receipt commits.
5. The refund receipt is later processed; `check_account_existence` rejects the `Transfer` with `AccountDoesNotExist` since the id neither exists nor is creatable by a refund — [4](#0-3) .
6. Because the receipt's predecessor is `system`, the failed transfer's deposit `B` is added to `other_burnt_amount` and permanently destroyed — [6](#0-5) .
7. `alice.near` no longer exists and `B` NEAR has been removed from total supply with no recipient.

    fn refund_may_not_create_universal_account() {
        init_test_logger();
        let key = SecretKey::from_seed(KeyType::ED25519, "refund-target").public_key();
        let account_id = derive_universal_account_id(&state_init_for(&[key]).to_raw());
        let (runtime, tries, root, apply_state, _signers, epoch) = setup_runtime(
            vec![alice_account()],
            Balance::from_near(100),
            Balance::ZERO,
            Gas::from_teragas(1000),
        );

        let result = runtime
            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,
                from_ref(&Receipt::new_balance_refund(&account_id, funding())),
                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);
        store_update.commit();

        // Assert on the reason, not just the absence: without this the test would
        // also pass if the refund receipt were dropped instead of refused.
        let [outcome] = &result.outcomes[..] else {
            panic!("the refund receipt must produce exactly one outcome, got {:?}", result.outcomes)

            ExecutionStatus::Failure(TxExecutionError::ActionError(err))

        );
        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
        assert!(
            get_account(&state, &account_id).unwrap().is_none(),
            "a refund must not bring a `0u` account into existence",
        );
    }
