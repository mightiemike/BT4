## Analysis Result

The strongest reachable analog to the ERC-20 "no revert on failure" bug class is in the **NEAR Wallet Contract** (`near-wallet-contract`), which lets an unprivileged caller (any relayer/RPC submitter) invoke `rlp_execute` with an attached NEAR deposit that represents an external caller's funds, tracked via `CallerDeposit` and intended to be refunded if a downstream cross-contract call fails. This mirrors the reported pattern: a value-moving path checks the *happy-path* success but omits proper failure handling on some branches, allowing loss of funds.

### Title
Caller deposit is permanently lost when `address_check_callback` or `nep_141_storage_balance_callback` fail - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` accepts a `#[payable]` deposit from an external caller (any unprivileged relayer) and tracks it as `CallerDeposit` so it can be refunded if the eth-emulated transaction ultimately fails. This refund logic is implemented only in `rlp_execute_callback`, but two other callbacks in the same execution chain — `address_check_callback` and `nep_141_storage_balance_callback` — can short-circuit and return a failure `ExecuteResponse` without ever scheduling the caller-deposit refund.

### Finding Description
`CallerDeposit::new` captures the `attached_deposit` of an external (non-self) caller when `rlp_execute` is invoked [1](#0-0) . This deposit is threaded through the promise chain and is expected to be refunded whenever the eventual action promise fails, as implemented in `rlp_execute_callback`: [2](#0-1) 

However, for two `EthEmulationKind` variants, the flow first issues an intermediate query promise (`address_registrar.lookup` for `EOABaseTokenTransfer`, or `storage_balance_of` for `ERC20Transfer`) before ever reaching `rlp_execute_callback`: [3](#0-2) 

The callbacks for these intermediate queries, `address_check_callback` and `nep_141_storage_balance_callback`, both handle `PromiseResult::Failed` by directly returning an error `ExecuteResponse` — with **no** call to `env::promise_batch_create` / `promise_batch_action_transfer` to refund `caller_deposit`, unlike the equivalent failure branch in `rlp_execute_callback`: [4](#0-3) [5](#0-4) 

Because the `#[payable]` deposit attached to the original `rlp_execute` call is already credited to the wallet contract's account balance the moment the `FunctionCall` action executes (deposits are added to the receiver's balance before the method body runs), any path that fails to schedule a refund leaves that NEAR permanently in the wallet contract account with no code path to return it to the caller.

### Impact Explanation
Any unprivileged relayer/caller who submits an `rlp_execute` transaction for an `EOABaseTokenTransfer` with `address_check` set, or an `ERC20Transfer` to an unregistered receiver, and attaches a deposit, will have that deposit silently and permanently trapped in the wallet contract if:
- the address registrar's `lookup` call fails (e.g., registrar contract paused, deleted, out of gas, or panics), or
- the token's `storage_balance_of` call fails (e.g., malformed/malicious/paused token contract, transient cross-shard congestion causing the call to run out of gas).

This is a concrete "permanently frozen funds" outcome triggered purely by a single external caller's transaction plus a failure of a called contract — no validator, node, or privileged actor is required.

### Likelihood Explanation
Reachable by any unprivileged caller of `rlp_execute` who attaches a NEAR deposit while relaying an `EOABaseTokenTransfer` with `address_check` or an `ERC20Transfer`. Triggering the failure only requires the downstream registrar/token contract call to fail, which is plausible (bad/incompatible token contracts, gas exhaustion under congestion, or a malicious/failing registrar), making this a Medium-to-High likelihood, high-impact fund-loss bug for real relayer deposits.

### Recommendation
Add the same caller-deposit refund logic used in `rlp_execute_callback`'s `PromiseResult::Failed` branch to both `address_check_callback` and `nep_141_storage_balance_callback` before returning the failure `ExecuteResponse`, ensuring `caller_deposit` is refunded on every failure branch in the promise chain, not just the final one.

### Proof of Concept
1. Deploy `WalletContract` for an eth-implicit account and fund it as usual.
2. As an external (non-self) relayer, call `rlp_execute` with a `tx_bytes_b64` encoding an `EOABaseTokenTransfer` where `address_check` targets an eth-implicit receiver, attaching a deposit `> 0` (see `test_caller_refunds` for the harness pattern) [6](#0-5) .
3. Cause the `address_registrar.lookup` cross-contract call to fail (e.g., point `ADDRESS_REGISTRAR_ACCOUNT_ID` at a deleted/panicking contract, or exhaust its gas).
4. Observe: `address_check_callback` returns `ExecuteResponse { success: false, ... }` at [7](#0-6)  without emitting any refund receipt to the caller — compare against the refund emitted in the `rlp_execute_callback` failure path [8](#0-7) .
5. The caller's attached deposit remains in the wallet contract's balance permanently, with no execution path to reclaim it.

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
