This confirms the mechanism. `verify_transactions` iterates `inclusion_proof.wtxids` (the full ordered list of wtxids from the actual mined Bitcoin block, checked against `block_header.tx_count` and the block's merkle root) and filters to those matching `reveal_tx_prefix`, then zips against `completeness_proof` in that exact order, rejecting with `ValidationError::RelevantTxNotInProof` if the completeness proof's transaction doesn't match the wtxid at that position [1](#0-0) . This means `da_txs`' order in `run_l1_block` is not an arbitrary, node-local, or attacker-influenced "mempool ordering" choice — it is exactly the transaction order baked into the mined Bitcoin block itself, the same block whose header hash and PoW every node already verifies via `verify_header_chain` before calling `verify_transactions` [2](#0-1) .
