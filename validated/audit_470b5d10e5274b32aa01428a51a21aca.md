### Title
Reward amounts irrecoverably accumulate due to floating-point precision loss in legacy vote-reward distribution - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)`, used for cycles prior to the new-reward-algorithm effective cycle, computes each voter's share of a Standard Representative (SR)'s per-cycle reward using double-precision floating-point math and truncates the result to a `long`. [2](#0-1)  Because `(double) userVote / totalVote` almost never divides evenly, and the truncated `long` result is strictly ≤ the exact mathematical share, the sum of what is actually credited to all voters of an SR for a given cycle is generally less than the `totalReward` recorded via `delegationStore.addReward(cycle, witnessAddress, value)` for that SR/cycle. [3](#0-2)  The undistributed remainder is never tracked, refunded, or redistributed anywhere — it is simply lost, exactly analogous to the `MultiRewards._notifyRewardAmount()` bug where `reward % rewardsDuration` is stuck in the contract with no recovery mechanism.

### Finding Description
`withdrawReward`/`queryReward` in `MortgageService` route reward computation for cycles before `getNewRewardAlgorithmEffectiveCycle()` through the legacy `computeReward(long cycle, List<Pair<byte[], Long>> votes)` helper: [4](#0-3) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;
    reward += voteRate * totalReward;
  }
  return reward;
}
``` [2](#0-1) 

Every voter who withdraws (via `WithdrawBalanceActuator` → `mortgageService.withdrawReward(address)`) has their share independently floor-truncated from a double multiplication. Unlike the "new" VI-based algorithm (`computeReward(long beginCycle, long endCycle, AccountCapsule)`), which uses `BigInteger` arithmetic scaled by `DECIMAL_OF_VI_REWARD = 10^18` specifically to minimize rounding error, [5](#0-4) [6](#0-5)  the legacy path has no such mitigation and no mechanism to carry forward or reconcile the residual dust once all voters for a given SR/cycle have withdrawn. The `totalReward` value recorded by `delegationStore.addReward` (funded ultimately from block rewards via `Manager.payReward` → `MortgageService.payReward`) is thus never fully paid out; the difference is permanently unaccounted for. [7](#0-6) 

### Impact Explanation
Each individual truncation is small (sub-unit of SUN per voter per cycle), matching the reported "Low" severity — no single loss is significant. However this occurs for every voter, every SR, every legacy cycle, and is unrecoverable: the shortfall is neither refunded to voters nor reclaimable by the SR or protocol, representing a systemic, permanent leakage of otherwise-owed voter rewards.

### Likelihood Explanation
Likelihood is high: `computeReward(long cycle, ...)` executes on the hot path of every `WithdrawBalanceContract` transaction (a standard, frequently broadcast, unprivileged transaction type) for any account with votes in a cycle prior to the new-algorithm cutover, and fires for every SR the voter voted for. [8](#0-7) 

### Recommendation
Replace the double-based proportional computation with integer/`BigInteger` arithmetic (e.g., `userVote * totalReward / totalVote` using `BigInteger` to avoid overflow), and track/carry forward the truncation remainder per SR/cycle so it can be included in a subsequent distribution, mirroring the approach already used by the new VI-based (`DECIMAL_OF_VI_REWARD`-scaled) reward algorithm.

### Proof of Concept
Given an SR with `totalVote = 3`, `totalReward = 10`, and three voters each with `userVote = 1`:
- Each voter's `voteRate = 1.0/3.0 = 0.333...`, so `reward = (long)(0.333... * 10) = 3` per voter.
- Sum distributed to all three voters = `9`, while `totalReward = 10`.
- `1` unit is permanently lost with no mechanism to recover it, repeating on every cycle this pattern occurs for any SR with votes not evenly dividing the reward.

Note: it was not possible within available search results to fully trace whether `getNewRewardAlgorithmEffectiveCycle()` has already passed on mainnet (making the legacy path effectively dormant) or whether the code path is still actively reachable for new/old chains; this should be verified in a full codebase review before treating this as currently exploitable in production.
