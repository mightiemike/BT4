### Title
Unbounded Linear-Scan Growth in Secondary Index Reverse Map Enables CPU/Storage DoS - (File: accounts-db/src/accounts_index/secondary.rs)

### Summary
When a validator is run with a secondary account index enabled (`--account-index program-id`, `spl-token-mint`, or `spl-token-owner`), every account write is fed through `AccountsIndex::update_secondary_indexes` [1](#0-0) , which calls `SecondaryIndex::insert()` for the relevant index. That function maintains a `reverse_index: DashMap<Pubkey, RwLock<Vec<Pubkey>>>` mapping an account (inner_key) to the set of outer index keys (e.g. distinct owning-program IDs, or distinct SPL-token owner/mint values) it has ever been associated with, and checks membership with a linear `outer_keys.contains(key)` scan before pushing [2](#0-1) . This is architecturally the same anti-pattern flagged in the external report's `SimpleMap::find` (O(n) linear search growing with the number of historical entries), just relocated from a Move `SimpleMap` to a Rust `Vec` guarded by a comment asserting the list "should" stay small.

### Finding Description
The comment on `SecondaryReverseIndexEntry` explicitly states the assumption behind using a `Vec` instead of a `HashSet`: "The only cases where an inner key should map to a different outer key is if the key had different account data for the indexed key across different slots. As this is rare..." [3](#0-2) .

This assumption is not enforced. The unit test `run_test_secondary_indexes_same_slot_and_forks` demonstrates that when the same account pubkey is repeatedly written with different indexed field values (owner for `program-id`/`spl-token-owner`, mint for `spl-token-mint`) across different slots, all historical values accumulate in the reverse-index `Vec` rather than being replaced — "Both pubkeys will now be present in the index" [4](#0-3) . The entries are only ever purged from the reverse index when the account is fully removed from the primary index (`handle_dead_keys` + `purge_secondary_indexes_by_inner_key_if`) [5](#0-4)  — not simply when the indexed value changes while the account remains alive.

For the `program-id` index specifically, the outer key is the account's `owner` field [6](#0-5) . Any account currently owned by the System Program can have its owner reassigned to an arbitrary pubkey via `SystemInstruction::Assign` — an ordinary, unprivileged, single-signer instruction. An attacker can repeatedly `Assign` the same account to a fresh distinct pubkey each transaction/slot. Each such write calls `program_id_index.insert(new_owner, pubkey)`, which does `outer_keys.contains(key)` over the ever-growing `Vec<Pubkey>` for that account before pushing the new owner [7](#0-6) . Because old owner values are never evicted while the account stays alive, this Vec grows unbounded with the number of `Assign` calls the attacker issues, making each subsequent `insert()` for that account progressively more expensive (classic unbounded linear-scan growth, the exact bug class described in the report).

### Impact Explanation
This only manifests on validators that opt in to a secondary account index (`--account-index program-id|spl-token-mint|spl-token-owner`), which is common on RPC nodes serving `getProgramAccounts`/`getTokenAccountsByOwner` efficiently. On such nodes, an attacker can drive per-account CPU cost of every subsequent account write up over time by cheaply and repeatedly toggling the account's indexed field (owner/mint) across many transactions, without any node-side bound on the reverse-index Vec size. This inflates CPU cost of `update_secondary_indexes` (called on the account-write hot path during flush, `update_index_for_flush` / `update_secondary_index_cached_accounts`) [8](#0-7)  disproportionately to the resources the attacker spends (ordinary transaction fees), degrading the affected RPC/validator node's account-processing throughput.

### Likelihood Explanation
Moderate. Exploitation requires the target node to have opted into a secondary index (not default), and the attacker must issue many transactions (e.g., `Assign` to new owners) targeting the same account(s) across many slots to grow the affected Vec. This is achievable by any unprivileged user with no special access, over a sustained period, satisfying the "disproportionate storage and CPU cost" acceptance criterion via ordinary user actions rather than validator/operator-privileged paths.

### Recommendation
Replace `SecondaryReverseIndexEntry`'s `Vec<Pubkey>` with a `HashSet<Pubkey>` (or a small-size-optimized set) so that membership checks and insert/removal are O(1) amortized instead of O(n), removing the unbounded linear-scan cost as the number of historical outer keys for an account grows. Alternatively, actively evict/replace the previous outer-key mapping for an inner_key when the indexed field changes to a new value (rather than accumulating all historical values), bounding the reverse-index entry size to the number of concurrently valid slots/forks rather than all-time history.

### Proof of Concept
1. Start a validator/RPC node with `--account-index program-id`.
2. From an unprivileged wallet, create an account owned by the System Program.
3. Repeatedly submit `SystemInstruction::Assign` transactions from that wallet, each assigning the account to a new, distinct arbitrary pubkey, across many slots (e.g., thousands of iterations).
4. Each `Assign` triggers `update_secondary_indexes` → `program_id_index.insert(new_owner, pubkey)` → `SecondaryIndex::insert` [9](#0-8) , appending to the reverse-index `Vec<Pubkey>` for that account (confirmed accumulation behavior per the existing unit test at [4](#0-3) ).
5. Measure the per-call cost of `insert()`/`outer_keys.contains(key)` as the Vec length grows — it will scale linearly with the number of prior `Assign` calls for that account, since no eviction occurs while the account remains alive.

    /// Inserts `inner_key` into `key`'s map.
    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }
