### Title
Stale cached signer-weight total in `signers-voting.clar` lets a signer vote reach the approval threshold against an outdated total-weight — ([File: stackslib/src/chainstate/stacks/boot/signers-voting.clar])

### Summary
`get-and-cache-total-weight` in `signers-voting.clar` permanently memoizes the total signer weight for a reward cycle the first time it is read, keyed only by `reward-cycle`. `get-threshold-weight` then derives the 70% approval threshold from that cached number. Under PoX-5, the signer set for a cycle (`.signers` `cycle-signer-set`, populated via `set-signers`) is not a one-time, immutable snapshot the way it was under PoX-4 — `pox_5_compute_and_update_signers` derives weights from live delegated-stacking state and calls `set-signers` for the cycle (guarded only by `last-set-cycle == reward-cycle`, which does not prevent the *same* cycle's entry being (re-)written with a different weight distribution before votes are cast). Once any vote for that cycle has occurred, `cycle-total-weight` is frozen to whatever total existed at that first vote, even if `.signers`' `cycle-signer-set` is later updated with a materially different total weight.

### Finding Description
`get-and-cache-total-weight` (signers-voting.clar:103-109):
```

            (ok total))))

Under PoX-5, `.signers`' `cycle-signer-set` entry for a reward-cycle is written by `set-signers`, which is only guarded by `(is-eq (var-get last-set-cycle) reward-cycle)` — it does not forbid overwriting an already-set cycle's entry with different weights, and the node-side `pox_5_compute_and_update_signers` computes weights from the live, continuously-changing delegated-stacking maps (`signer-delegated-per-cycle`, `signer-shares-staked-for-cycle`) rather than a frozen PoX-4-style snapshot:

Because `cycle-total-weight` is memoized on first vote and never invalidated when `.signers`' underlying set for that same `reward-cycle` is later rewritten, the threshold used by `vote-for-aggregate-public-key` can diverge from the weight distribution that is actually authoritative at approval time — this exactly mirrors the reported bug class: a value cached from a mutable upstream source (here, PoX-5's dynamically-recomputed signer weight total) is treated as immutable by a downstream consumer (the voting threshold), producing an equality (`new-total >= threshold-weight`) that no longer reflects the live signer-weight state.

### Impact Explanation
If the cached total-weight is stale relative to the true, later-written total (e.g., stale-low because it was cached against an earlier, smaller signer set before more signers reached the delegation minimum, or the total shrank after that point due to undelegation), the 70% bar computed from it is wrong for the actual signer population, letting a minority-weighted subset of signers (relative to the true, current total) push `new-total >= threshold-weight` and get `aggregate-public-keys` set for the cycle via `map-insert`. This is a minority-triggerable divergence in a validation verdict (aggregate-key approval) that other nodes computing against the live `.signers` total would not necessarily reach the same way, i.e., a signer-set/threshold divergence bounded to the DKG/aggregate-key approval process for the cycle — classified as High under the given impact bands (minority-triggerable divergence in signer/threshold-of-consensus logic).

### Likelihood Explanation
This requires: (1) at least one vote is cast for a reward-cycle before `.signers`' `cycle-signer-set` for that cycle reaches its final/authoritative weight distribution, and (2) `set-signers` is invoked again for the same `reward-cycle` with different weights afterward (plausible under PoX-5's continuous delegation model, where `pox_5_compute_and_update_signers` is exercised at reward-set-calculation points that could, depending on epoch/anchor-block timing rules, run more than once for the same cycle, or where weights simply differ from what was true at the first vote). Whether the current coordinator/epoch machinery ever actually calls `set-signers` twice for the same `reward-cycle` in production, or only ever computes it once and the true bug is instead in whether `set-signers` can be called with different weights at all, could not be fully confirmed from what is indexed here — the coordinator call sites that invoke `pox_5_compute_and_update_signers` were not fully traceable within this pass.

### Recommendation
Invalidate `cycle-total-weight` whenever `.signers` is updated for that cycle (e.g., have `set-signers` clear/refresh the corresponding `cycle-total-weight` entry in `signers-voting.clar`, or have `get-and-cache-total-weight` re-derive from `.signers` rather than trusting a memoized value once it exists), and/or make `set-signers` reject overwriting an already-set cycle rather than only checking `last-set-cycle`.

### Proof of Concept
Not independently reproduced in this pass; the analysis is based on static reading of `signers-voting.clar`'s caching logic and `signer_set.rs`'s PoX-5 weight computation, without confirming from the coordinator whether `set-signers` is actually re-invoked for an already-voted-on cycle in the current build. This should be validated with a Devin session that traces every call site of `update_signers`/`set-signers` across epoch/coordinator code and writes a Clarity-level unit test that (a) calls `set-signers` for cycle N with weights W1, (b) casts a vote (caching total-weight), (c) calls `set-signers` again for cycle N with different weights W2, and (d) casts enough further votes to hit `>= threshold-weight` computed from W1 while being under 70% of W2, confirming approval against a stale threshold.

    fn pox_5_compute_and_update_signers(
        clarity: &mut ClarityTransactionConnection,
        pox_constants: &PoxConstants,
        reward_cycle: u64,
        pox_contract: &str,
        coinbase_height: u64,
        _current_calculation_btc_height: u32,
        _current_epoch: &StacksEpochId,
    ) -> Result<SignerCalculation, ChainstateError> {
        let is_mainnet = clarity.is_mainnet();
        let signers_contract = &boot_code_id(SIGNERS_NAME, is_mainnet);

        // Build the `(signer_key, amount_ustx)` pair stream
        let mut entries = Self::pox_5_stake_entries(clarity, reward_cycle, pox_contract)?;
        let Pox5SignerSetOutput {
            signer_set,
            pox_ustx_threshold,
        } = Self::pox_5_make_signer_set(&mut entries, pox_constants)?;

        if signer_set.is_empty() {
            error!("Fatal network condition: reward set computed with an empty signer set. Cannot continue producing blocks");
            return Err(ChainstateError::PoxNoRewardCycle);
        }

        let events = Self::update_signers(
            clarity,
            reward_cycle,
            &signer_set,
            signers_contract,
            signer_set.len() > 0,
            coinbase_height,
            is_mainnet,
        )?;
