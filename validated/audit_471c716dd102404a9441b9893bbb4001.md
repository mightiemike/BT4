### Title
Unchecked floating-point Bancor curve overflow in TRC10 Exchange trades allows pool-draining/miscalculated trade amounts - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
java-tron's TRC10 "Exchange" (bancor-style) market implements the same class of bug as the external report: a market-pricing function that can return an erroneous, unchecked boundary value (here, `Infinity`/overflow silently truncated by a `(long)` cast) which is then used verbatim to update pool reserves and credit an attacker's account, without any sanity/overflow check unless an optional, disabled-by-default "hardened" arithmetic mode is enabled.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations depending on the `hardenedCalc` flag: [1](#0-0) 

By default, `hardenedCalc` is `false` because it is derived from `AbstractExchangeActuator.allowHarden()`, which reads the on-chain dynamic property `allowHardenExchangeCalculation()`: [2](#0-1) 

This property is a governance-gated dynamic parameter (toggled only via committee proposal), so by default every `ExchangeTransactionContract`, `ExchangeCreateContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` uses the *unhardened* path.

In the unhardened path, `ExchangeProcessor` computes the bancor curve purely in `double` arithmetic with no bounds/NaN/Infinity checking: [3](#0-2) 

`exchangeFromSupply` raises `(1 + supplyQuant/supply)` to the power `2000.0`. If a caller sells a `sellTokenQuant` that is very large relative to the pool's `sellTokenBalance`, the intermediate `relay` (supplyQuant) computed in `exchangeToSupply` grows large enough that `(1+relay/supply)^2000` overflows to `Double.POSITIVE_INFINITY`. The result is then multiplied by `balance` and cast directly to `long`:
```
long out = (long) issuedSupply;   // NaN -> 0, Infinity -> Long.MAX_VALUE
...
return (long) exchangeBalance;    // same silent truncation
```
There is no check for `NaN`/`Infinity`/negative results before this value is used. This is the direct analog of the report's root cause: an internal pricing function silently returning a degenerate boundary value on an unhandled error/overflow condition, and that value flowing unchecked into the trade settlement.

That erroneous `buyTokenQuant` is returned to `ExchangeCapsule.transaction()`, which (only in hardened mode) validates that resulting balances are non-negative: [4](#0-3) 

In the default (unhardened) path this check is skipped entirely, so `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` (plain `long` subtraction, no `subtractExact`) can silently underflow/wrap to a corrupted value while `buyTokenQuant` (potentially `Long.MAX_VALUE`) is credited to the caller's account via `addAssetAmountV2` in `ExchangeTransactionActuator.execute()`: [5](#0-4) 

The only pre-execution guard is `doValidate()`, which merely checks that `tokenQuant > 0`, that `tokenBalance + tokenQuant` stays under `getExchangeBalanceLimit()`, and that the caller holds enough of the *sold* asset — none of which bound the ratio `sellTokenQuant / sellTokenBalance` that drives the curve into overflow: [6](#0-5) 

### Impact Explanation
An attacker who controls an asset with a sufficiently large total supply (trivial to arrange by issuing their own TRC10 token with `totalSupply` near `Long.MAX_VALUE` and creating/injecting it into an Exchange pool paired against TRX or another valuable token) can broadcast a single `ExchangeTransactionContract` selling a huge quantity of their own token relative to the pool's reserve of that token. This drives the bancor curve's `pow(x, 2000)` computation into `Infinity`, which truncates to a huge (or `Long.MAX_VALUE`) `buyTokenQuant`. The attacker is credited that amount of the counter-asset while the pool's real reserve is only decremented via unchecked `long` subtraction (silent overflow/underflow), corrupting the pool's on-chain accounting and/or effectively draining far more of the counter-asset than the pool holds — a direct asset/accounting corruption analogous to the reported "receive far more future/collateral than a fair rate would allow."

### Likelihood Explanation
High. The vulnerable path is the *default* behavior of the exchange (hardening is opt-in via a rarely-flipped governance dynamic property), reachable by any account via an ordinary broadcast transaction (`ExchangeCreateContract`/`ExchangeInjectContract` to set up a pool, then `ExchangeTransactionContract` to trigger the overflow). No privileged role, leaked key, or malicious peer is required — only issuing one's own TRC10 asset, which is a standard unprivileged operation.

### Recommendation
- Make the "hardened" exchange arithmetic (`SafeExchangeProcessor` and the negative-balance check in `ExchangeCapsule.transaction`) the mandatory, always-on behavior rather than gating it behind the `allowHardenExchangeCalculation` dynamic property.
- In `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, explicitly detect `NaN`/`Infinity`/negative intermediate results and reject the transaction (throw `ContractValidateException`/`ArithmeticException`) instead of silently truncating via `(long)` cast.
- Add an explicit bound on `sellTokenQuant` relative to `sellTokenBalance` (e.g., reject trades where the bancor exponent input would exceed a safe threshold) before invoking the curve math, mirroring the "fail early" recommendation from the original report.
- Use `Math.subtractExact`/`Math.addExact` unconditionally (not only in hardened mode) when updating pool balances and account balances after a trade.

### Proof of Concept
1. Attacker issues a custom TRC10 asset `ATK` with `totalSupply` close to `Long.MAX_VALUE` (e.g., `9_000_000_000_000_000_000L`), a normal unprivileged `AssetIssueContract` operation.
2. Attacker calls `ExchangeCreateActuator`/`ExchangeInjectActuator` to create a small pool pairing `ATK` (reserve = `1`) against TRX (reserve = e.g. `100_000_000_000L`, 100k TRX) — `ExchangeCreateActuator.execute()` at [7](#0-6)  performs no check on the ratio between the two reserves.
3. Attacker broadcasts an `ExchangeTransactionContract` selling almost all of their `ATK` supply (`sellTokenQuant ≈ 9e18`) against the tiny `ATK` reserve (`1`). Inside `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [3](#0-2) , the ratio `sellTokenQuant / newBalance` is astronomically large, driving `pow(1+x, 0.0005)` and subsequently `pow(1+relay/supply, 2000.0)` toward `Infinity`, so `buyTokenQuant` truncates to a value far exceeding the pool's real `100_000_000_000L` TRX reserve.
4. `ExchangeTransactionActuator.execute()` [8](#0-7)  credits the attacker's account with this inflated TRX amount via `addAssetAmountV2`/`addExact` while the pool's `secondTokenBalance` is decremented with plain, unchecked `long` subtraction (since `hardenedCalc` is `false` by default), corrupting the pool state and allowing withdrawal of far more TRX than the pool actually holds.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
