### Title
Webhook HMAC validation does not bind the request to the claimed shop domain, topic, or webhook ID — allowing a malicious app‑installer to forge cross‑tenant webhook events - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
The Balancer report describes a check that is supposed to bind burned-BPT to actual withdrawal amount but instead accepts any amount (`BPT_IN_FOR_EXACT_TOKENS_OUT`), letting an attacker manipulate state that is shared across all depositors. The structurally identical pattern exists in the shopify-app-js webhook pipeline: the HMAC signature that is supposed to authenticate an inbound webhook only covers the **raw request body**. It never binds the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers into what is verified. Those headers are read out and trusted afterward to decide which shop's session/access token to use. A holder of any valid (body, HMAC) pair — obtainable by installing the app on their own shop and triggering a real webhook — can replay that exact body/HMAC pair while substituting the `domain` header of a different (victim) shop that also has the app installed, and the signature will still validate.

### Finding Description
`validateFactory` in [1](#0-0)  performs HMAC validation strictly against `rawBody` via `validateHmacFromRequestFactory`, then *separately* extracts the shop-identifying headers (`domain`, `topic`, `webhookId`, etc.) without ever incorporating them into the signed material: [2](#0-1) 

The HMAC digest is computed only from `rawBody`: [3](#0-2) 

(Actual path: `packages/apps/shopify-api/lib/utils/hmac-validator.ts` lines 153-162, `validateHmacString`.)

After the HMAC check succeeds, `checkWebhooksHeaders`/`checkEventsHeaders` pull `domain`, `topic`, and `webhookId` directly off the (unauthenticated w.r.t. these fields) headers and return them as trusted fields: [4](#0-3) 

Downstream, the `domain` value returned by this "valid" check is used directly to look up and attach the **offline session/access token** for that shop, and the (attacker-controlled) body is parsed and handed to the app's webhook handler as if it legitimately originated from that shop: [5](#0-4) 

Because the API secret key (used to compute the HMAC) is the **same for every shop that has the app installed** (it's the app's client secret, not a per-shop secret), any merchant who installs the app can:
1. Trigger any real webhook event on their own store (getting a genuinely Shopify-signed `(rawBody, hmac)` pair), or directly compute their own valid HMAC over an arbitrary JSON body since they only need the app's secret key exposed via legitimate webhook deliveries to correlate body/HMAC pairs.
2. POST that same `rawBody`/`hmac` pair directly to the app's public webhook endpoint, substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a **different shop** that also has the app installed.
3. The HMAC check still passes (it only validates `rawBody`), `checkWebhooksHeaders` accepts the forged `domain`, and the app's webhook handler executes using the victim shop's session/access token with attacker-chosen topic/body content.

This is the same root-cause shape as the reported Balancer bug: a security check that is supposed to bind the "amount you get" (there: BPT burned) to a specific, protected value, but instead is scoped too loosely, letting one actor's legitimately-signed artifact be reinterpreted against another actor's state.

### Impact Explanation
An attacker who has installed the app on any shop can forge webhook deliveries that the app will treat as authentic events from an arbitrary other shop that has the app installed (cross-tenant confusion). Depending on the app's webhook handlers, this can lead to:
- Triggering privileged handler logic (data writes, order/customer mutations, uninstall/GDPR flows, billing changes, etc.) against a victim shop's data using the victim's stored offline access token.
- Denial of service or data corruption for victim shops by supplying malicious/garbage payloads for topics the victim never actually triggered.
- Because `webhookId`/`topic`/`eventId` aren't authenticated either, replay/idempotency logic relying on these values can also be subverted.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app (a single unprivileged merchant/customer of the app), which is normally trivial for any public Shopify app, and that the target victim shop also has the app installed with a webhook endpoint reachable over the public internet (standard deployment). No secrets need to be leaked — the attacker only needs one legitimately signed webhook delivery to their own shop (or the ability to compute an HMAC using their own valid delivery as an oracle) and can then swap the header claiming shop identity.

### Recommendation
Bind the shop domain (and ideally topic/webhook ID) into the authenticated material, or otherwise cryptographically tie the header claims to the verified payload, e.g.:
- Compute/verify the HMAC over `rawBody + domain + topic + webhookId` (or use a per-shop signing context) rather than `rawBody` alone, matching Shopify's actual verification contract more strictly at the framework level, and/or
- Cross-check that the `domain` header actually corresponds to a shop with an active session created via that app's OAuth/install flow *and* additionally verify that the specific webhook subscription (webhookId) is one the app itself registered for that shop before trusting the payload, and/or
- Reject/flag webhook deliveries where the domain header doesn't match an expected allow-list validated out-of-band (e.g., via the Admin API) before dispatching to handlers with the shop's access token.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers (or has Shopify trigger) any webhook, e.g. `PRODUCTS_CREATE`, capturing the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header sent by Shopify (`H = HMAC-SHA256(apiSecretKey, B)`).
3. Attacker crafts a new POST to the same public webhook endpoint (`/webhooks`) with:
   - Body: `B` (unchanged, so the HMAC still matches)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (victim shop that also has the app installed)
   - Header `X-Shopify-Topic`, `X-Shopify-Webhook-Id` optionally altered.
4. `validateFactory` validates `H` against `B` successfully (per [6](#0-5) ), then reads `domain = victim-shop.myshopify.com` from the header and returns `valid: true`.
5. `authenticateWebhookFactory` loads `victim-shop.myshopify.com`'s offline session and executes the app's webhook handler as though the event genuinely originated from the victim shop ( [7](#0-6) ).

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
}
