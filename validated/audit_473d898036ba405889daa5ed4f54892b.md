### Title
Legitimate `ExchangeInject` transactions revert when the proportional counterpart token amount rounds down to zero for skewed-ratio/low-value pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
Java-tron's built-in Bancor-style TRC10 exchange (`Exchange`/`ExchangeV2`) computes the counterpart token amount to inject proportionally to the existing pool ratio. If that computed amount rounds down to zero (which happens whenever the pool ratio is skewed enough relative to the injected quantity — the direct analog of "low decimal token" input amounts in the reported AMM swap-fee bug), `ExchangeInjectActuator` explicitly reverts the whole transaction instead of proceeding without the zero-valued leg.

### Finding Description
`ExchangeInjectActuator.doValidate()` computes the counterpart quantity using integer/BigInteger division based on the current pool balances: [1](#0-0) 

If `tokenQuant` is small relative to the balance ratio (`bigFirstTokenBalance`/`bigSecondTokenBalance`), `anotherTokenQuant` rounds down to `0`, and the actuator unconditionally throws `ContractValidateException("the calculated token quant must be greater than 0")`, aborting the whole inject operation. This mirrors the reported bug class: a downstream computed value that is "rounded down to zero" causes a hard revert of an otherwise valid user operation, rather than gracefully handling/skipping the zero leg.

The same rounding computation is performed again in `execute()` using plain `long` division: [2](#0-1) 

Because `ExchangeCreateActuator` allows any user to create a pool with an arbitrarily skewed `firstTokenBalance`/`secondTokenBalance` ratio (e.g., a pool with a token that mimics a "low decimal" asset, similar to GUSD in the report), any subsequent legitimate injector whose input amount is "not large enough" relative to that ratio will have their transaction revert — even though the amount they supplied is fully valid and non-zero. This is confirmed directly by the existing regression test: [3](#0-2) 

### Impact Explanation
This is a state/accounting-availability issue in an unprivileged, in-scope feature (the TRC10 Bancor exchange, reachable by any account via `ExchangeInjectContract`). Pool creators (or third parties who inject first) can inadvertently or intentionally skew a pool's balance ratio such that small, legitimate injections consistently and deterministically revert, denying normal use of the exchange for that token pair. Users still pay the transaction bandwidth/energy cost for a failed transaction, and the pool becomes practically un-injectable for smaller counterparties, degrading availability of the on-chain exchange functionality — directly analogous to the "swap reverted for input amount not large enough" impact in the original report.

### Likelihood Explanation
Likelihood is moderate to high: any user can create an `Exchange` pair with arbitrary initial balances (no restriction preventing highly skewed ratios), and any other unprivileged user attempting a proportionally small injection into that pool will trigger the revert deterministically — no special privileges or edge-case timing required, just a sufficiently skewed pool ratio, which is common for pools involving tokens with very different unit values/precisions.

### Recommendation
When the computed `anotherTokenQuant` rounds down to zero, do not unconditionally reject the transaction. Options: (1) round up the minimum-required `tokenQuant` and reject with clear guidance ("increase injected amount to at least X"), or (2) allow the injection while treating the zero-quantity leg as a no-op (analogous to the report's recommendation to simply skip sending the zero fee rather than reverting), provided this does not open manipulation vectors on pool ratios. At minimum, surface a deterministic minimum viable injection amount to callers/frontends so genuine users aren't blocked without actionable information.

### Proof of Concept
Using the existing test harness pattern in `ExchangeInjectActuatorTest`:
1. Create/inject an `Exchange` pool where `firstTokenBalance` (TRX) is small (e.g. 100) and `secondTokenBalance` (token `456`) is large (e.g. 400000000).
2. As a user, call `ExchangeInject` with `tokenId = firstTokenId ("_")`, `quant = 100` (a fully valid, positive TRX amount).
3. `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` computes to a value that, depending on exact ratios, rounds to `0`.
4. `doValidate()` throws `ContractValidateException("the calculated token quant must be greater than 0")`, reverting the transaction — reproduced exactly by the existing test `SameTokenNameOpenCalculatedTokenQuantLessThanZero`. [4](#0-3)

    accountCapsule.setBalance(firstTokenQuant);

    ExchangeInjectActuator actuator = new ExchangeInjectActuator();

    TransactionResultCapsule ret = new TransactionResultCapsule();

    try {
      actuator.validate();
      actuator.execute(ret);
      fail();

    } catch (ContractExeException e) {
      Assert.assertFalse(e instanceof ContractExeException);
    } finally {
      ;
      dbManager.getExchangeV2Store().delete(ByteArray.fromLong(1L));
