Investigation summary: the kernel CVE stems from unchecked pointer arithmetic (`next := p.ErrorContextData + len`) where a huge/negative-appearing length value can wrap the pointer around memory (32-bit overflow), producing an infinite loop or an out-of-bounds read entirely within unsafe C pointer semantics. Protobuf-go's wire-format parsers do not use raw pointer arithmetic for buffer traversal; they operate on Go slices with explicit length checks before every advance/slice operation, e.g. `protowire.ConsumeVarint` bounds-checks `len(b)` at every byte before returning a length [1](#0-0) , `protowire.ConsumeBytes` explicitly rejects a length exceeding the remaining slice before ever slicing `b[n:][:m]` [2](#0-1) , and the lazy/unmarshal loops in `internal/impl/decode.go` and `internal/impl/lazy.go` advance `b = b[n:]` only after `n` has been validated non-negative [3](#0-2) [4](#0-3) . The `protolazy.BufferReader` skip/decode helpers likewise bound-check `len(b.Buf)-i` before any fast-path advance and fall back to a slow, bounds-checked varint decoder otherwise [5](#0-4) . Because Go slice indexing panics rather than silently wrapping on out-of-range access, there is no reachable code path in the scoped production parsers (binary unmarshal, lazy unmarshal, prototext unknown-field marshaling) that reproduces the kernel's pointer-wraparound infinite-loop/OOB-read pattern under a trusted schema with default binary/JSON parsing.

func ConsumeBytes(b []byte) (v []byte, n int) {
	m, n := ConsumeVarint(b)
	if n < 0 {
		return nil, n // forward error code
	}

		return nil, errCodeTruncated
	}
	return b[n:][:m], n + int(m)
}
