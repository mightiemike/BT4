### Title
Unchecked `SessionStorage.storeSession()` boolean return value in token-exchange authentication flow allows requests to proceed as authenticated after silent session-persistence failure - ([File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts])

### Summary
The `SessionStorage` interface documents `storeSession()` as returning `Promise<boolean>` to signal whether the write succeeded or silently failed, but the token-exchange authentication code paths in `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router` never check this return value before treating the freshly exchanged session as valid and calling `next()` / returning the session to the caller.

### Finding Description
`SessionStorage.storeSession(session: Session): Promise<boolean>` is explicitly specified to return `true` if successfully stored and `false` otherwise, allowing conforming implementations to fail without throwing. [1](#0-0) [2](#0-1) 

In `performTokenExchange`, after exchanging the session token for an offline (and optionally online) access token, the code calls `storeSession` but discards the boolean result and unconditionally proceeds to set `res.locals.shopify.session` and call `next()`, treating the request as authenticated regardless of whether persistence actually succeeded: [3](#0-2) 

The identical unchecked pattern exists in the Remix `TokenExchangeStrategy.authenticate()`: [4](#0-3) 

This mirrors the reported ERC20/`approve()` bug class: an operation whose success/failure is communicated purely through a return value (rather than a thrown exception) is invoked without inspecting that value, so the caller's subsequent logic ("the session is now durably stored, so trust it") is decoupled from what actually happened in the underlying operation. Just as `IERC20Metadata.approve()` can return `false` (or nothing, per non-compliant tokens) without reverting, a `SessionStorage` implementation (e.g., a custom or third-party adapter, or one hitting a transient DB/network failure that it maps to `false` rather than throwing) can fail to persist the session while the token-exchange flow proceeds as if authentication succeeded and the session is durable.

### Impact Explanation
If `storeSession` returns `false` (write failure reported without throwing), the current request is still allowed through as authenticated (`next()` is called, `session` is attached to the response locals/returned to the route handler), but the offline/online access token obtained from Shopify is never persisted. On the very next request, `loadSession` will find no session, forcing the app back into the OAuth/token-exchange path — repeating a fresh call to Shopify's token-exchange endpoint on every request from that shop, effectively defeating session caching and putting sustained, unnecessary load on both the app's auth handler and Shopify's OAuth backend for that tenant (impact scoped to a single shop that experiences persistent storage-write failures, degrading its own auth handler rather than enabling cross-tenant compromise).

### Likelihood Explanation
Likelihood depends on the underlying `SessionStorage` implementation returning `false` instead of throwing on failure — a valid state per the documented interface contract but one the calling code never accounts for. This is realistic with community/custom storage adapters (the interface explicitly instructs implementers to return `false` rather than throw), transient database errors mapped to `false`, or storage back-pressure/rate-limiting scenarios, making it a Medium-likelihood latent defect in the auth handler rather than a directly attacker-triggerable exploit.

### Recommendation
Check the boolean result of every `storeSession` call in the token-exchange (and equivalent OAuth callback) paths across `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router`. On `false`, do not proceed to `next()`/return the session as authenticated — instead treat it as a persistence failure (log it, return a 500, or retry) so that authentication state and durable storage state cannot diverge, analogous to replacing an unchecked `approve()` with a checked call (e.g., `forceApprove` or an explicit success assertion) in the reported analog.

### Proof of Concept
1. Configure a custom `SessionStorage` (or a built-in one under transient failure conditions) whose `storeSession()` implementation returns `false` on write failure instead of throwing (this is the documented, spec-compliant behavior per `implementing-session-storage.md`).
2. Send a request bearing a valid Shopify session token to an embedded app route protected by `performTokenExchange` (Express) or the Remix `TokenExchangeStrategy`.
3. Force the underlying storage write to fail (e.g., simulate a DB outage) so `storeSession` resolves to `false`.
4. Observe that the middleware/strategy still calls `next()` / returns the `newSession` as valid (lines 101–132 in `perform-token-exchange.ts`, lines 67–108 in `token-exchange.ts`), granting the current request authenticated access, while no session was actually persisted — the next request for the same shop will re-trigger a full token exchange with Shopify, repeating indefinitely under sustained storage failure.
