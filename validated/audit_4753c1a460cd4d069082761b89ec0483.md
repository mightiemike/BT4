### Title
Wrong `receiver_id` used in `validate_delegate_action` when checking inner `DeterministicStateInit` actions — (`runtime/runtime/src/action_validation.rs`)

---

### Summary

`validate_delegate_action` passes the **outer transaction's `receiver`** (the relayer's target account, i.e., the `DelegateAction` sender's account) instead of `delegate_action.receiver_id()` (the actual inner-action target) to `validate_actions_with_mode`. This is the exact nearcore analog of the Teller Finance bug: a wrong identifier is used at a dispatch/validation boundary, causing the feature to be permanently broken for legitimate callers and creating a bypass path for crafted inputs.

---

### Finding Description

In `runtime/runtime/src/action_validation.rs`, `validate_delegate_action` selects the `inner_receiver` to pass to `validate_actions_with_mode`:

```rust
fn validate_delegate_action(
    limit_config: &LimitConfig,
    delegate_action: VersionedDelegateActionRef<'_>,
    receiver: &AccountId,          // ← outer tx receiver (sender's account)
    ...
) -> Result<(), ActionsValidationError> {
    let actions = delegate_action.get_actions();
    let inner_receiver =
        if ProtocolFeature::FixDelegatedDeterministicStateInit.enabled(...) {
            delegate_action.receiver_id()   // correct
        } else {
            receiver                        // BUG: outer tx receiver, not delegate target
        };
    validate_actions_with_mode(limit_config, &actions, inner_receiver, ...)?;
``` [1](#0-0) 

`validate_actions_with_mode` calls `validate_action_with_mode` for each inner action, which for `Action::DeterministicStateInit` calls `validate_deterministic_state_init(limit_config, a, receiver)`:

```rust
fn validate_deterministic_state_init(
    limit_config: &LimitConfig,
    action: &DeterministicStateInitAction,
    receiver_id: &AccountId,
) -> Result<(), ActionsValidationError> {
    let derived_id = derive_near_deterministic_account_id(&action.state_init);
    if derived_id != *receiver_id {
        return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver { ... });
    }
``` [2](#0-1) 

The `receiver_id` passed here is the **outer transaction's receiver** (the `DelegateAction` sender's account, e.g., `alice.near`), not `delegate_action.receiver_id()` (the actual deterministic account target, e.g., `0s69284a5453e7be5632b28b6a01baecf6c12c156d`). The derived ID of the `DeterministicStateInit` action will virtually never match the outer tx receiver, so the check always fails.

**Two concrete broken invariants result:**

**1. Permanent DoS for legitimate use.** Any user who submits a meta transaction (`DelegateAction`) containing a `DeterministicStateInit` inner action targeting the correct deterministic account will have their transaction rejected at tx validation with `InvalidDeterministicStateInitReceiver`. The feature is completely unusable via meta transactions. The code comment confirms: *"This makes it impossible to initialize deterministic accounts from meta transactions."* [3](#0-2) 

**2. Validation bypass for crafted inputs.** An attacker who controls a deterministic account `det_account_b` (whose derived ID equals the outer tx receiver) can craft a `DelegateAction` with `receiver_id = det_account_a` (a different account) but inner action `state_init_b` (which derives to `det_account_b`). Pre-fix, the wrong-receiver check compares `derive(state_init_b) == outer_tx.receiver == det_account_b` → passes. The receipt is then created targeting `det_account_a`, but `state_init_b` is for `det_account_b`. The receipt validation catches this and fails with `NewReceiptValidationError::ActionsValidation(InvalidDeterministicStateInitReceiver)`, burning the relayer's gas without any legitimate execution.

The integration test `test_deterministic_state_init_meta_tx_receiver_check_pre_fix` confirms both effects:

```rust
// Pre-fix: exploit tx passes initial tx validation
let outcome = try_meta_tx_deterministic_receiver_exploit(fix_version - 1)
    .expect("without the fix, exploit tx passes initial tx validation");
// ...but fails at receipt execution
assert_matches!(outcome.status,
    FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
        kind: ActionErrorKind::NewReceiptValidationError(
            ReceiptValidationError::ActionsValidation(
                ActionsValidationError::InvalidDeterministicStateInitReceiver { .. }
            )
        ), ..
    }))
);
``` [4](#0-3) 

The exploit construction is:

```rust
let delegate_action = DelegateAction {
    sender_id: det_account_b.clone(),
    receiver_id: det_account_a,          // wrong target
    actions: vec![NonDelegateAction::try_from(inner_action).unwrap()],
    // state_init_b derives to det_account_b, not det_account_a
    ...
};
// outer tx receiver = det_account_b → old check: derive(state_init_b)==det_account_b ✓ passes
``` [5](#0-4) 

---

### Impact Explanation

- **Contract execution flow breakage**: `DeterministicStateInit` actions are permanently broken inside meta transactions (NEP-366 `DelegateAction`). Any relayer or user attempting to initialize a deterministic account via a meta transaction will have their transaction rejected at admission, with no workaround short of a direct (non-meta) transaction.
- **Relayer gas drain**: An attacker who controls a deterministic account can craft meta transactions that pass initial validation but fail at receipt execution, causing the relayer to burn gas with no useful outcome. This is a financial loss for the relayer.

Both impacts are reachable by an unprivileged user submitting ordinary transactions to the network.

---

### Likelihood Explanation

Any user who:
1. Holds a deterministic account with an access key (achievable by anyone who deploys a global contract and calls `DeterministicStateInit`), and
2. Submits a meta transaction containing a `DeterministicStateInit` inner action

will trigger the DoS. The bypass path requires additionally that the outer tx receiver matches the derived ID of the inner `state_init`, which is structurally guaranteed when the sender of the `DelegateAction` is itself a deterministic account.

---

### Recommendation

Use `delegate_action.receiver_id()` instead of the outer `receiver` when selecting `inner_receiver` in `validate_delegate_action`. This is exactly what the `FixDelegatedDeterministicStateInit` protocol feature does:

```rust
let inner_receiver = delegate_action.receiver_id(); // always use the delegate's own target
``` [6](#0-5) 

The fix is already present in the codebase, gated behind `ProtocolFeature::FixDelegatedDeterministicStateInit`. It must be activated via a protocol upgrade to take effect on-chain.

---

### Proof of Concept

**DoS path** (legitimate use broken):
1. Deploy a global contract and derive a deterministic account ID `det_account`.
2. Submit a meta transaction: outer tx receiver = `alice.near` (the sender), `DelegateAction.receiver_id = det_account`, inner action = `DeterministicStateInit { state_init: ... }` where `derive(state_init) == det_account`.
3. Pre-fix: `validate_delegate_action` checks `derive(state_init) == alice.near` → fails → `InvalidDeterministicStateInitReceiver` at tx admission. The feature is unusable.

**Bypass path** (crafted input passes tx validation, fails at receipt):
1. Attacker controls `det_account_b` (a deterministic account with an access key).
2. Attacker crafts: outer tx receiver = `det_account_b`, `DelegateAction.receiver_id = det_account_a` (different account), inner action = `state_init_b` (derives to `det_account_b`).
3. Pre-fix: check is `derive(state_init_b) == det_account_b` → passes tx validation.
4. Receipt is created targeting `det_account_a`; receipt validation checks `derive(state_init_b) == det_account_a` → fails → `NewReceiptValidationError`. Relayer's gas is burnt. [7](#0-6) [1](#0-0)

fn validate_delegate_action(
    limit_config: &LimitConfig,
    delegate_action: VersionedDelegateActionRef<'_>,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ActionsValidationError> {
    let actions = delegate_action.get_actions();
    let inner_receiver =
        if ProtocolFeature::FixDelegatedDeterministicStateInit.enabled(current_protocol_version) {
            // This is the correct receiver id to use for the check.
            delegate_action.receiver_id()
        } else {
            // This is a bug fixed with `FixDelegatedDeterministicStateInit` that
            // validated against the wrong id. This makes it impossible to
            // initialize deterministic accounts from meta transactions.
            // The bug cannot be abused, if someone crafts a state init that passes
            // validation here, it will fail when it is checked as incoming receipt.
            receiver
        };
    validate_actions_with_mode(
        limit_config,
        &actions,
        inner_receiver,
        current_protocol_version,
        mode,
    )?;
    Ok(())
}
