## Title
Incomplete self-format JSON string escaping in `escapeBytesSelfType` allows JSON-structure corruption in public HTTP API responses - ([File: framework/src/main/java/org/tron/core/services/http/JsonFormat.java])

### Summary
The reported bug class is "an escaping function that filters some but not all special characters, allowing context-escape injection because backslash/quote ordering is not handled correctly." The closest reachable analog in java-tron is `escapeBytesSelfType()` in `JsonFormat.java`, used to render "human readable" (`visible=true` / self-type) string fields (asset names, memos, URLs, account names, token IDs) in HTTP API JSON responses.

### Finding Description
`escapeBytesSelfType` only escapes double quotes and never escapes backslashes: [1](#0-0) 

Because backslashes in the raw field value are passed through unescaped while quotes are turned into `\"`, attacker-controlled bytes containing a backslash immediately preceding a quote (or other backslash sequences) change the meaning of the escape sequence when the result is concatenated into the response JSON, the classic "escape order" bug named in the external report (quotes must not be escaped before backslashes, or vice versa must be done consistently). The fields subject to this self-format branch are largely attacker-controlled state written by ordinary, unprivileged users: `AssetIssueContract.name/abbr/description/url`, `AccountUpdateContract.account_name`, `WitnessCreateContract.url`, `Note.memo`, `TransferAssetContract.asset_name`, `ExchangeCreateContract.*_token_id`, `MarketSellAssetContract.*_token_id`, etc., all registered in `NameFieldNameMap`: [2](#0-1) 

The code attempts a partial mitigation by validating the single-field escape via `JSON.parseObject("{\"key\":\"" + result + "\"}")` and falling back to hex on failure: [3](#0-2) 

This self-check only verifies that the escaped value is valid *in isolation* as a single key/value pair; it does not guarantee correctness once the same escaped string is spliced into the surrounding full response JSON document (which may contain sibling keys, arrays, or nested objects), so escape sequences that happen to parse validly in the narrow test harness can still alter the structure of the final document produced by the servlet layer.

### Impact Explanation
Any unprivileged user who controls one of the `NameFieldNameMap` fields (e.g., by issuing a token with a crafted `name`/`abbr`/`url`, updating an account name, creating a witness with a crafted URL, or sending a shielded `memo`) can inject data into the JSON representation returned by public read-only HTTP endpoints (`GetAssetIssueByName`, `GetAccountServlet`, `GetPaginatedAssetIssueList`, etc., all of which use the self-type/visible formatting path in `JsonFormat`). This is a JSON response-integrity/injection issue affecting any third-party client parsing these public API responses — not privilege escalation of the node itself, but it can corrupt or manipulate the structure of data returned to other unprivileged API consumers (analogous to "malicious inputs escaping the intended context" in the original report).

### Likelihood Explanation
Moderate-to-low. Exploitation requires crafting a string containing specific backslash/quote sequences that (a) survive protobuf/UTF-8 validation for the given field, and (b) produce a still-parseable-but-different JSON structure once embedded into the larger response, which is a non-trivial but not implausible bar given the existing `JSON.parseObject` fallback only validates a minimal single-key template rather than the full response context. I could not fully verify a complete, alternate valid-JSON payload that survives both the isolated pre-check and injects into the outer document within the tool time available, so the specific weaponized payload remains unproven; the missing-backslash-escaping root cause itself is confirmed in code.

### Recommendation
In `escapeBytesSelfType` (and `escapeText`/`unicodeEscaped` companions used for self-type formatting), escape backslashes *before* escaping quotes (mirroring `escapeText`'s ordering, which already handles `\\` and `"` together), and validate the escaped value against the full response document structure rather than a synthetic single-field wrapper, or simply reuse the properly ordered `escapeText` routine for all self-type string fields instead of the ad hoc `result.replaceAll("\"", "\\\\\"")` call.

### Proof of Concept
1. Issue an asset (`AssetIssueContract`) or update an account (`AccountUpdateContract.account_name`) with a `name`/`account_name` value containing a raw backslash followed by a double quote, e.g. bytes: `\` + `"` + `,"injected":"x`.
2. Query the asset/account via a public read endpoint that renders the field with `escapeBytesSelfType` (self-type/visible JSON output).
3. Because backslashes are left unescaped while quotes are converted to `\"`, the resulting substring's escape semantics diverge from what `JSON.parseObject`'s single-key sanity check validated, potentially corrupting/altering the outer JSON structure returned to the API caller.   static String escapeBytesSelfType(ByteString input, final String fliedName) {
    //Address
    if (HttpSelfFormatFieldName.isAddressFormat(fliedName)) {
      return StringUtil.encode58Check(input.toByteArray());
    }
    //Normal String
    if (HttpSelfFormatFieldName.isNameStringFormat(fliedName)) {
      String result = new String(input.toByteArray());
      result = result.replaceAll("\"", "\\\\\"");
      try {
        JSON.parseObject("{\"key\":\"" + result + "\"}");
        return result;
      } catch (Exception e) {
        return ByteArray.toHexString(input.toByteArray());
      }
    }
    //HEX
    return ByteArray.toHexString(input.toByteArray());
  }
