### Title
DKG vault export endpoint permits EditRole users to exfiltrate DKG secret material via insufficient role check - (File: core/web/router.go)

### Summary
The `/v2/vault/dkg_results/export` route is protected by `auth.RequiresEditRole` instead of `auth.RequiresAdminRole`, unlike every comparable secret-export route in the same router (`/keys/eth/export/:address`, `/keys/csa/export/:ID`, `/keys/ocr/export/:ID`, `/keys/ocr2/export/:ID`, `/keys/p2p/export/:ID`, `/keys/vrf/export/:keyID`, etc., which all use `RequiresAdminRole`). This allows any user account holding only the EditRole to call `ExportDKGResult` and retrieve the raw hex-encoded `ReportWithResultPackage` DKG secret share/result material.

### Finding Description
`VaultController.ExportDKGResult` reads a stored DKG result package from the vault ORM and returns its full hex-encoded bytes plus a SHA-256 checksum to any caller that passes the route's auth check. [2](#0-1) 

The route registration wires this handler with `auth.RequiresEditRole` rather than `auth.RequiresAdminRole`: [1](#0-0) 

Compare this to the surrounding route table, where every analogous secret/key export operation (ETH, CSA, OCR, OCR2, P2P, VRF, Solana/Cosmos/StarkNet/Aptos/Stellar/Tron/Sui/TON key export) is consistently gated behind `RequiresAdminRole`, while only the lower-sensitivity "create" actions use `RequiresEditRole`: [3](#0-2) 

This is an inconsistent authorization level: exporting DKG result packages is a secret-disclosure operation equivalent in sensitivity to exporting an ETH/OCR/CSA private key, yet it is reachable by any authenticated EditRole account, without needing AdminRole. No additional authorization check exists inside `ExportDKGResult` itself to compensate for the router-level gap. The `RequiresEditRole`/`RequiresAdminRole` middleware performs only role membership checks based on the authenticated session/token's role and does not add secret-specific access control.

### Impact Explanation
An EditRole-only account (a legitimate but lower-privileged authenticated user, e.g., one that can create jobs/keys but is not intended to extract raw secret key material) can call `POST /v2/vault/dkg_results/export` and receive the plaintext-hex DKG result package for any known `instanceId`. This is unauthorized disclosure of DKG vault secret material — matching the impact category of "secret disclosure" under the target's threat model, since DKG result packages are treated with the same sensitivity as exportable keys elsewhere in this exact router (which is why all other export endpoints require AdminRole).

### Likelihood Explanation
Feasibility is high once the precondition (an EditRole account) is satisfied: the request is a single unauthenticated-role-check-bypassing (relative to intended design) API call, `POST /v2/vault/dkg_results/export` with a valid `instanceId`, and is fully repeatable for any stored result. The precondition of obtaining an EditRole account is explicitly permitted by the audit's threat model as an attacker capability (obtainable via lower-privilege admin action or self-registration path).

### Recommendation
Change the role requirement for both vault DKG routes to `auth.RequiresAdminRole`, matching the pattern used by all other export endpoints in `core/web/router.go`:
```go
authv2.POST("/vault/dkg_results/verify", auth.RequiresAdminRole(vault.VerifyDKGResult))
authv2.POST("/vault/dkg_results/export", auth.RequiresAdminRole(vault.ExportDKGResult))
```
(At minimum, `ExportDKGResult`, which discloses the raw secret package, must require `RequiresAdminRole`.)

### Proof of Concept
Add an RBAC route test (following the existing pattern used for `/v2/keys/eth/export/:address`) in `core/web/router_test.go` or the vault controller test suite:
1. Seed an authenticated test client whose session/token role is `EditRole` only (not Admin).
2. Insert a DKG result package into the vault ORM (`vault.NewVaultORM`) for a known `instanceId`.
3. Call `POST /v2/vault/dkg_results/export` with `{"instanceId": "<seeded>"}` using the EditRole client.
4. Assert the response status is `403 Forbidden` (matching the assertion used for the EditRole client against `/v2/keys/eth/export/:address`).
5. Currently, per `core/web/router.go` lines 441-443, this request succeeds with `200 OK` and returns the hex-encoded DKG secret package, demonstrating the bypass. After applying the fix (`RequiresAdminRole`), the same test should return `403`.

func (vc *VaultController) ExportDKGResult(c *gin.Context) {
	var req ExportDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId is required"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	hexPackage := hex.EncodeToString(v.ReportWithResultPackage)
	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewExportDKGResultResource(hexPackage, shaStr), "exportDKGResult")
