### Title
Unauthenticated APP_UNINSTALLED webhook replay causes persistent session deletion / recovery DoS due to missing freshness binding in webhook HMAC validation - (File: `packages/apps/shopify-api/lib/webhooks/validate.ts`, `packages/apps/shopify-app-express/src/app-installations.ts`)

### Summary
`validateHmacFromRequestFactory` / `validateFactory` verify Shopify webhook authenticity purely by checking the HMAC of the raw request body against a value derived from `config.apiSecretKey` [1](#0-0) . No timestamp, nonce, or delivery/session identifier is included in the signed material, and `webhookId`/`eventId` headers are extracted but never checked for uniqueness or freshness anywhere in `validate.ts` [2](#0-1) . This means any previously legitimate webhook payload (body + `X-Shopify-Hmac-Sha256` header) remains valid forever and can be replayed at any later time by anyone who obtained a copy of it (e.g., recorded from logs, a proxy, or a compromised delivery relay), even though it was only ever generated for one specific past installation "session."

### Finding Description
This is the same root-cause pattern as the referenced Swafe finding: a piece of state that is cryptographically valid only in the context of one temporal "session" (an OAuth installation, in this case) is accepted by the endpoint without binding to that session, so a stale-but-validly-signed artifact from an earlier session can be replayed to corrupt/overwrite state relevant to the *current* session.

In `shopify-app-express`, the `APP_UNINSTALLED` webhook handler is auto-registered and, on any successfully-validated delivery, unconditionally deletes **all** current sessions for the shop: [3](#0-2) [4](#0-3) 

The validation path that gates this deletion is `api.webhooks.validate()` → `validateFactory` → `validateHmacFromRequestFactory`, which only checks that `HMAC-SHA256(apiSecretKey, rawBody) == header`. There is no timestamp window check (unlike the OAuth/app-proxy HMAC path, which enforces a 90-second window via `validateHmacTimestamp`) and no dedup/idempotency check keyed on `webhookId`/`eventId` [5](#0-4) .

Attack flow:
1. Shop installs the app; Shopify delivers a legitimate `APP_UNINSTALLED` webhook at some point (e.g., during a test uninstall, or by an attacker briefly installing/uninstalling the app themselves since the webhook body for `APP_UNINSTALLED` is typically an empty/static JSON body and the HMAC only depends on that body + the app's fixed secret, not on the timestamp header, which is not part of the signed payload nor checked for freshness).
2. Attacker records this valid `(body, X-Shopify-Hmac-Sha256, X-Shopify-Topic, X-Shopify-Shop-Domain, X-Shopify-Webhook-Id, X-Shopify-Api-Version)` header/body set for the target shop.
3. Shop reinstalls the app, creating a fresh offline (and possibly online) `Session` via OAuth/token-exchange, stored via `sessionStorage.storeSession()`.
4. Attacker replays the recorded request to the app's webhook endpoint at any later time. `validateFactory` accepts it because the HMAC still matches the (unchanged) body and secret — no session/installation binding exists to reject it as stale.
5. `deleteAppInstallationHandler` fires and calls `AppInstallations.delete(shop)`, which loads all sessions for the shop via `findSessionsByShop` and deletes them via `deleteSessions` [4](#0-3) .
6. The shop's freshly-installed, currently valid offline/online access tokens are wiped from storage even though the app is still installed, forcing the merchant back through OAuth/re-authentication and breaking any in-flight or scheduled background jobs that depend on the stored session — a persistent, repeatable DoS against the "installed" state, analogous to how stale guardian shares blocked recovery in the Swafe report.

### Impact Explanation
An unauthenticated third party who has obtained one historical, legitimately-signed `APP_UNINSTALLED` webhook delivery for a shop (no secret leak required — HMACs are not bound to time or install session) can repeatedly and indefinitely delete that shop's stored sessions/access tokens by replaying the same request. This denies the merchant continued use of the app without noticing an obvious compromise, and can be repeated after every re-authentication, mirroring the "persistent recovery DoS" impact class in the reference report (blocking a critical function — continued authenticated access — despite the legitimate installation succeeding).

### Likelihood Explanation
Moderate. It requires the attacker to have captured one valid webhook delivery for the target shop (e.g., via shared logs, a debugging proxy, a previously-installed and then removed attacker's own copy of the app if `APP_UNINSTALLED` payload/headers are shop-specific but otherwise static, or network capture). Because the HMAC validation has no timestamp/freshness component and no `webhookId` replay protection, once captured the artifact is valid forever, materially increasing exploitability compared to the OAuth flow which enforces a nonce/cookie-bound `state` and a timestamp window for HMAC-signed requests.

### Recommendation
- Add anti-replay protection to `validateHmacFromRequestFactory`/`validateFactory` for webhooks: track processed `webhookId` (or `eventId` for Events-type webhooks) values within a bounded time window and reject duplicates, similar to Shopify's own recommended idempotency handling.
- Enforce a maximum age on webhook deliveries using the `X-Shopify-Triggered-At` (or equivalent) header, analogous to `validateHmacTimestamp` already used for the admin/app-proxy signator in `hmac-validator.ts`.
- In `AppInstallations.delete` / `deleteAppInstallationHandler`, avoid destructive session-wide deletion based solely on a bare `APP_UNINSTALLED` webhook; cross-check against actual installation state (e.g., verify with the Admin API, or track delivery IDs already processed) before wiping stored sessions.

### Proof of Concept
1. Install the app on a test shop; capture the `APP_UNINSTALLED` webhook request Shopify sends (body + `X-Shopify-Hmac-Sha256`, `X-Shopify-Topic`, `X-Shopify-Shop-Domain`, `X-Shopify-Webhook-Id`, `X-Shopify-Api-Version` headers), e.g., via the existing test harness pattern in `packages/apps/shopify-app-express/src/__tests__/integration/oauth.test.ts` (`appUninstalledWebhookRequest`) [6](#0-5) .
2. Reinstall the app (OAuth completes, a fresh session is stored).
3. Replay the exact same captured POST to `/webhooks` at any later time.
4. Observe: `validateFactory` returns `valid: true` (HMAC still matches), and `AppInstallations.delete(shop)` removes the newly created session(s), even though the app remains installed — confirming the replay causes unauthorized, repeatable session invalidation.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
    webhookId: webhookId!,
  };

  const name = getHeader(headers, headerNames.name);
  if (name) fields.name = name;

  const triggeredAt = getHeader(headers, headerNames.triggeredAt);
  if (triggeredAt) fields.triggeredAt = triggeredAt;

  const eventId = getHeader(headers, headerNames.eventId);
  if (eventId) fields.eventId = eventId;

  return {valid: true, ...fields};
}
