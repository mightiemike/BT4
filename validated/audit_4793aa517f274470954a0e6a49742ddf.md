### Title
Unauthenticated Request-ID Collision Allows Cross-Workflow Griefing of Gateway HTTP Trigger Requests - (File: `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`)

### Summary
The Gateway's HTTP trigger handler tracks in-flight workflow-execution requests in a single map keyed only by the caller-supplied JSON-RPC `id` field, with no namespacing by authenticated caller/workflow owner. Any unprivileged client of the public HTTP trigger endpoint can pick the same `id` as another workflow's in-flight request, causing the second (or first, depending on race outcome) request to be rejected with a "requestID already used" conflict error — the same "TOCTOU on a caller-supplied ID with no namespacing" bug class described in the front-running `createAccount` report.

### Finding Description
`HandleUserTriggerRequest` processes each JSON-RPC request in this order: parse/validate → resolve workflow → `authorizeRequest` (per-workflow auth) → `checkRateLimit` → `setupCallback`, where the actual "claim" of the request identity happens: [1](#0-0) 

`setupCallback` performs a classic check-then-act: it checks `h.callbacks[requestID]` for existence and, if absent, inserts an entry — all keyed purely by `req.ID`, the raw, attacker-controlled JSON-RPC id string supplied in the original request: [2](#0-1) 

Unlike the vault gateway path, which explicitly guards against this by re-writing the request ID with an authorized-owner prefix before using it as a lookup key (`prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID`): [3](#0-2) 

the HTTP trigger handler never namespaces `req.ID` by the authorized workflow/owner before using it as the sole key into the shared `h.callbacks` map: [4](#0-3) 

Because `authorizeRequest` only validates that the caller may invoke a specific `workflowID` — it does not bind or reserve `req.ID` to that workflow/owner — any other unrelated caller (targeting a different workflow entirely) can supply an identical `id` value. Whichever request reaches `setupCallback` first "wins" the map slot; the other is rejected via `jsonrpc.ErrConflict`: [5](#0-4) 

This is directly analogous to the reported `createAccount` front-running bug: a resource identifier chosen by the requester is checked for prior existence and then claimed, with no mechanism (seed + sender-address hashing, or here, owner/workflow-scoped namespacing) to prevent an unrelated party from colliding with someone else's pending identifier and causing their legitimate request to fail.

### Impact Explanation
An unauthenticated or low-privileged external caller of the Gateway's public HTTP trigger capability (any party permitted to submit `workflows.execute` JSON-RPC calls, which is the intended entry point for triggering workflows over HTTP) can grief unrelated users/workflows by continuously guessing or observing request IDs and re-submitting requests with the same `id` before the legitimate request completes. This causes legitimate workflow-execution requests to fail with a conflict error rather than executing, denying service to victims. This matches the report's "Griefing" impact category and the required "unsafe transaction/workflow execution" / denial class of impact for this analog.

### Likelihood Explanation
Exploitability depends on the attacker being able to guess or observe another party's `id` value and race their own request into the shared map before/at the same time as the victim's. If request IDs are high-entropy random strings chosen client-side and never disclosed, blind guessing is impractical, lowering likelihood to a race/observation scenario (e.g., a client publishing predictable IDs, monitoring logs/telemetry, or intentionally target testing with a colliding ID they simply chose in advance, e.g. "1", "test", or IDs disclosed via error messages/logs that echo back the ID). Given the check-then-insert has no atomicity issue itself (protected by `callbacksMu`), the actual risk is entirely about ID predictability/observability, not concurrency — same root cause as the original report where `accountId` collision, not gas price alone, is the crux.

### Recommendation
Namespace the callback map key by the authorized caller/workflow identity rather than the raw client-supplied `id`, mirroring the pattern already used in `core/capabilities/vault/gateway_vault_request_processor.go` (owner-prefixed request ID). For example, after `authorizeRequest` succeeds, derive the callback key as `workflowID + separator + req.ID` (or `authorizedOwner + separator + req.ID`) before calling `setupCallback`, so that identical client-chosen `id` values from different workflows/owners can never collide with each other.

### Proof of Concept
Conceptual PoC (not run against live code, based on static analysis of the call flow):
1. Attacker sends a valid `workflows.execute` JSON-RPC request to the gateway HTTP trigger endpoint for `workflowA` with `id: "X"`.
2. Victim independently sends a valid `workflows.execute` request for an unrelated `workflowB` with the same `id: "X"` at roughly the same time (or the attacker observes/guesses the victim's chosen ID beforehand and races it).
3. Both pass `validatedTriggerRequest`, `resolveWorkflowID`, and `authorizeRequest` independently (each is authorized only for their own workflow — no cross-check on `id`).
4. In `setupCallback`, whichever request acquires `callbacksMu` first inserts `h.callbacks["X"]`; the second lookup finds `found == true` and is rejected via:
```go
if _, found := h.callbacks[requestID]; found {
    h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used...", requestID), callback)
    return nil, fmt.Errorf("in-flight request ID: %s", requestID)
}
``` [5](#0-4)

The victim's legitimate workflow-execution request fails with a conflict error even though the attacker had no authorization over the victim's workflow — a denial-of-service/griefing outcome caused purely by unnamespaced ID collision, analogous to the `createAccount` `accountId` front-running scenario.

Note: I was unable to trace the full public network exposure/authentication model of the HTTP trigger endpoint (e.g., whether upstream layers enforce per-caller authentication before reaching `HandleUserTriggerRequest`, or how request IDs might be observed by third parties) due to index size limits on this large codebase. If more certainty on the transport-level auth model is needed, a full Devin session with complete repository access should be used to trace `http_handler.go`'s caller and any upstream authentication middleware.

func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, doneCh)
```

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
