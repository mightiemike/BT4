### Title
Cross-Chain Replay of `SignedDelegateAction` Due to Missing Chain Binding in Signed Payload — (`core/primitives/src/action/delegate.rs`)

### Summary

`DelegateAction` (meta-transaction) signatures do not include a chain identifier (`chain_id` or genesis hash) in the signed payload. A malicious relayer who receives a `SignedDelegateAction` intended for testnet can replay it verbatim on mainnet — or any other NEAR network — if the sender's account and public key exist on both networks and the nonce/height conditions are satisfied. This executes the inner actions (e.g., token transfers, key additions) on the victim's mainnet account without their authorization.

### Finding Description

`DelegateAction` is the struct that a user signs to create a meta-transaction (NEP-366). Its signed payload is:

```rust
// core/primitives/src/action/delegate.rs:46-64
pub struct DelegateAction {
    pub sender_id: AccountId,
    pub receiver_id: AccountId,
    pub actions: Vec<NonDelegateAction>,
    pub nonce: Nonce,
    pub max_block_height: BlockHeight,
    pub public_key: PublicKey,
}
```

The hash that Alice signs is computed in `get_nep461_hash()`:

```rust
// core/primitives/src/action/delegate.rs:353-357
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}
```

`SignableMessage` prepends only a NEP discriminant (a fixed `u32` constant `MIN_ON_CHAIN_DISCRIMINANT + 366`):

```rust
// core/primitives/src/signable_message.rs:61-65
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}
```

**No `chain_id`, genesis hash, or any network-specific value is included in the signed bytes.** The `max_block_height` field is a bare block height integer, not a block hash, so it provides no chain binding.

By contrast, a regular `SignedTransaction` includes `block_hash` in its body, which is chain-specific and prevents cross-chain replay. `DelegateAction` has no equivalent.

`apply_delegate_action` performs these checks:

```rust
// runtime/runtime/src/actions.rs:430-448
if !signed_delegate_action.verify() { ... }          // signature check (no chain binding)
if apply_state.block_height > delegate_action.max_block_height() { ... }  // height check
if delegate_action.sender_id() != sender_id { ... }  // sender check
validate_delegate_action_key(...);                    // nonce check
```

None of these checks bind the signature to a specific NEAR network. The same `SignedDelegateAction` passes all checks on any network where the account, key, nonce, and height conditions are met.

`DelegateActionV2` (NEP-611) has the identical structural problem — its `get_nep461_hash()` also uses only a fixed discriminant with no chain binding:

```rust
// core/primitives/src/action/delegate.rs:180-184
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateActionV2);
    let bytes = borsh::to_vec(&signable).expect("failed to serialize");
    hash(&bytes)
}
```

### Impact Explanation

A malicious relayer who receives Alice's `SignedDelegateAction` for testnet can wrap it in a new outer `SignedTransaction` (which the relayer signs) targeting mainnet. The outer transaction's `block_hash` is mainnet-specific, but Alice's inner `SignedDelegateAction` is chain-agnostic. The runtime on mainnet will accept it if:

1. Alice's `sender_id` exists on mainnet (common — account names are shared across networks).
2. Alice's `public_key` is registered on mainnet (common for developers using the same key pair).
3. The `nonce` in the `DelegateAction` is greater than Alice's current access-key nonce on mainnet.
4. The `max_block_height` is in the future on mainnet (mainnet and testnet have similar block heights, both in the ~100M range).

The inner actions execute with `sender_id` as `predecessor_id`, so any action Alice authorized — `Transfer`, `FunctionCall`, `AddKey`, `DeleteKey` — executes on mainnet against Alice's mainnet account and balances. This constitutes an **unauthorized transaction** and potential **loss of funds**.

### Likelihood Explanation

- Many NEAR users and developers maintain accounts with the same name and key pair on both mainnet and testnet.
- The relayer is the natural adversary: they receive the raw `SignedDelegateAction` off-chain before submission.
- Nonce conditions are easily satisfiable: a testnet `DelegateAction` with nonce `N` replays on mainnet whenever Alice's mainnet access-key nonce is below `N`.
- Block height overlap is near-certain: both networks advance at ~1 block/second and have similar heights, so a `max_block_height` set for testnet is almost always valid on mainnet.

### Recommendation

Include a chain-specific value in the `DelegateAction` signed payload. The standard approach is to add a `chain_id` field (the genesis hash or the string identifier such as `"mainnet"` / `"testnet"`) to `DelegateAction` and `DelegateActionV2`, and incorporate it into `get_nep461_hash()`. This mirrors how regular `SignedTransaction` uses `block_hash` to bind to a specific chain. A protocol version gate would be required to activate the new field.

### Proof of Concept

1. Alice holds account `alice.near` on both testnet and mainnet with the same ed25519 key pair. Her mainnet access-key nonce is 5.
2. Alice signs a `DelegateAction` for testnet: `sender_id="alice.near"`, `receiver_id="token.testnet"`, `actions=[Transfer{deposit: 10 NEAR}]`, `nonce=6`, `max_block_height=120_000_000`, `public_key=<Alice's key>`.
3. Alice sends the `SignedDelegateAction` to a relayer off-chain.
4. The malicious relayer, instead of submitting to testnet, wraps the identical `SignedDelegateAction` in a mainnet transaction: `SignedTransaction { signer_id: relayer, receiver_id: "alice.near", actions: [Delegate(signed_delegate_action)], block_hash: <mainnet block hash> }`.
5. `apply_delegate_action` on mainnet: signature verifies (hash is chain-agnostic), `block_height < 120_000_000` passes, `sender_id` matches, nonce `6 > 5` passes.
6. A new receipt is created with `predecessor_id="alice.near"`, `receiver_id="token.mainnet"` (or whatever mainnet contract matches), executing the transfer from Alice's mainnet account — an action Alice never authorized for mainnet.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }
