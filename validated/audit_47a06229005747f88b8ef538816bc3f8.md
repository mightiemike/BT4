### Title
Excess-gas refund is permanently and irrecoverably denied when `refundUnusedGas` fails, with no partial-refund fallback - (File: x/uexecutor/keeper/outbound.go)

### Summary
`applyGasRefund` computes the full excess gas amount (`gasFee - gasFeeUsed`) owed back to a user after an outbound executes, and attempts to return it via `CallUniversalCoreRefundUnusedGas` (first with a swap back to PC, then falling back to a no-swap PRC20 deposit). If both attempts fail — e.g., because the `UniversalCore` contract's underlying token/liquidity balance cannot cover the refund amount — the function simply records `PcRefundExecution.Status = "FAILED"` and returns. There is no mechanism anywhere in the codebase (no retry job, no partial-amount fallback) that later recovers or re-attempts this refund, so the user's legitimately-owed excess gas is permanently lost. This mirrors the reported bug class: an all-or-nothing balance check that denies the entire benefit instead of returning `min(desired, available)`.

### Finding Description
`applyGasRefund` is invoked from both `handleFailedOutbound` and `handleSuccessfulOutbound` in `x/uexecutor/keeper/outbound.go` during outbound finalization [1](#0-0) . It computes `refundAmount := gasFee - gasFeeUsed` and tries two on-chain paths to return it to the user, in order: a swap-based refund and a no-swap direct PRC20 deposit [2](#0-1) .

Both paths ultimately call `CallUniversalCoreRefundUnusedGas`, which is a `DerivedEVMCall` into the `UniversalCore` system contract's `refundUnusedGas` function [3](#0-2) . Neither the Go keeper code nor (as far as is verifiable from this index) the `refundUnusedGas` contract logic checks the available balance/liquidity up front and clamps the requested amount to `min(refundAmount, available)`. Instead, when the call fails for any reason (including insufficient balance in the contract to cover the refund), the outcome is:

```go
resp, err := k.CallUniversalCoreRefundUnusedGas(ctx, gasToken, refundAmount, recipientAddr, false, big.NewInt(0), big.NewInt(0))
if err != nil {
    refundPcTx.Status = "FAILED"
    refundPcTx.ErrorMsg = err.Error()
} else {
    ...
}
outbound.PcRefundExecution = refundPcTx
outbound.RefundSwapError = swapFallbackReason
``` [4](#0-3) 

This `FAILED` status is terminal: the outbound has already transitioned to `Status_REVERTED` (failed case) or completed successfully (successful case) before `applyGasRefund` runs, and `UpdateOutbound` simply persists the `FAILED` refund record [5](#0-4) . No retry mechanism, cron job, or later reconciliation logic that scans for `PcRefundExecution.Status == "FAILED"` and reattempts (even partially) was found anywhere in the codebase.

This is structurally the same defect pattern as the ZeroLend `stakeTo4Year` bug: rather than checking available balance and refunding `min(calculated, available)` so the user gets at least a partial, correct amount, the code performs an all-or-nothing attempt and silently (from the user's perspective) forfeits the entire owed amount on failure.

### Impact Explanation
Under the "unprivileged attacker" framing, any external-chain event that triggers an outbound with `gasFee > gasFeeUsed` (routine — happens whenever an outbound consumes less gas than estimated) creates an entitlement to a refund. If the `UniversalCore` contract's gas-token/PC liquidity is temporarily insufficient (which does not require any privileged action — it can occur under normal operational conditions such as a spike in refund volume, thin liquidity pools, or a token whose fee-tier/quote path is unconfigured), the user's rightful refund is permanently and silently lost with no recovery path. This is a permanent loss of protocol/user-owed funds, matching the in-scope impact category "permanent loss ... of user or protocol-controlled funds," and it is reachable via ordinary, unprivileged user transaction/outbound flows.

### Likelihood Explanation
The triggering condition — refund path (swap or no-swap) failing due to insufficient contract-held liquidity or a transient EVM call failure — does not require any privileged actor; it can arise from normal usage patterns (e.g., many simultaneous refunds, temporarily depleted swap liquidity, or a misconfigured/unsupported gas token fee tier causing `GetDefaultFeeTierForToken` to fail and pushing straight to the no-swap path, which can likewise fail if PRC20 deposit balance is insufficient) [6](#0-5) . Because there is no partial-refund or retry logic, any single such failure event results in permanent loss for that user, making the likelihood of occurrence moderate to high over the system's operational lifetime, especially at scale.

### Recommendation
1. Before attempting `CallUniversalCoreRefundUnusedGas`, query the available balance/liquidity backing the refund (analogous to `underlying.balanceOf(address(bonusPool))` in the reported bug) and compute `amountToRefund = min(refundAmount, available)`.
2. If `available < refundAmount`, refund the partial amount immediately and persist the shortfall (e.g., a `RemainingRefund` field on the outbound) so it can be retried later once liquidity is replenished, rather than marking the entire refund as unrecoverably `FAILED`.
3. Add a retry/reconciliation job (or an explicit user-triggerable claim path) that re-attempts `PcRefundExecution.Status == "FAILED"` entries, so transient liquidity shortages do not translate into permanent fund loss.

### Proof of Concept
Conceptual reproduction (cannot be fully executed without contract-level control over `UniversalCore`'s liquidity, but the code path is directly traceable):
1. Submit an inbound that results in an outbound with a large `GasFee` estimate relative to actual `GasFeeUsed`, so `applyGasRefund` computes a large positive `refundAmount`.
2. Drain or avoid pre-funding the `UniversalCore` contract's gas-token/PC balance so that neither the swap-based nor the no-swap `depositPRC20`/`refundUnusedGas` call can complete successfully.
3. Observe (as in the existing test `TestGasFeeRefund` scaffolding [7](#0-6) ) that `outbound.PcRefundExecution.Status` becomes `"FAILED"` and remains so permanently — no subsequent block processing, job, or user action changes this state, and the refund amount is never delivered to the user.

**Note on verification limits:** the `UniversalCore.sol` contract's `refundUnusedGas` implementation was not found in this repository's indexed contents (likely lives in a separate contracts repo or was excluded due to index size limits), so the exact on-chain balance-check/revert behavior of `refundUnusedGas` itself could not be directly confirmed here — the analysis is based on the Go-side keeper logic, which unconditionally attempts the full `refundAmount` and has no fallback/partial-amount/retry logic on failure. If a full audit of the contract logic is needed, a Devin session with repository/browser access to the contracts source would be required to confirm whether `refundUnusedGas` itself contains any partial-amount handling.

// CallUniversalCoreRefundUnusedGas calls refundUnusedGas on UniversalCore to return excess gas fee
// to the recipient. withSwap=true swaps the gas token back to PC; withSwap=false deposits PRC20 directly.
func (k Keeper) CallUniversalCoreRefundUnusedGas(
	ctx sdk.Context,
	gasToken common.Address,
	amount *big.Int,
	recipient common.Address,
	withSwap bool,
	fee *big.Int,
	minPCOut *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UniversalCore ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	// fee is uint24 in Solidity — pass as *big.Int (go-ethereum ABI packs non-standard widths as *big.Int)
	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress,
		handlerAddr,
		big.NewInt(0),
		nil,
		true,
		false,
		true,
		&nonce,
		"refundUnusedGas",
		gasToken,
		amount,
		recipient,
		withSwap,
		fee,
		minPCOut,
	)
}
