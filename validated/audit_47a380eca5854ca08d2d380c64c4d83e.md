### Title
L1Handler `paid_fee` check runs after message-consumption state is committed, but a rejection still marks the L1→L2 message as consumed — ([File: crates/blockifier/src/transaction/l1_handler_transaction.rs], [File: crates/apollo_batcher/src/block_builder.rs])

### Summary
This is a direct structural analog of the reported bug: a mandatory "fee settlement" step is executed atomically with (and gates the success of) a critical bookkeeping action, so that a downstream failure in the fee step forces the important action to be reverted/rejected, while the "consumed" bookkeeping performed independently of that revert can diverge from the actual on-chain state.

### Finding Description
In `L1HandlerTransaction::execute_raw` [1](#0-0) , the flow is:
1. `execution_state` (nested transactional state) executes the L1 handler entry point, including `consume_l1_to_l2_message`, which is called *before* the fee check, on the outer `tx_execution_context` [2](#0-1) .
2. If the gas-bound check passes, `execution_state.commit()` is called, folding the message-consumption state change into the outer `state` [3](#0-2) .
3. Immediately after that commit, the code checks `if paid_fee == Fee(0)` and, if true, returns `Err(TransactionFeeError::InsufficientFee)` from `execute_raw` — even though the message-consumption changes were just committed into the (still-transactional) outer state.

Because `execute_raw` returns `Err`, the top-level caller (`TransactionExecutor::execute` in `crates/blockifier/src/blockifier/transaction_executor.rs`) discards *all* of `transactional_state`'s changes via `transactional_state.abort()` [4](#0-3) . This means the "commit" performed inside `execute_raw` is illusory — the message consumption is fully rolled back at the true state level.

However, at the batcher layer, `collect_execution_results_and_stream_txs` unconditionally inserts the L1Handler's `tx_hash` into `execution_data.consumed_l1_handler_tx_hashes` *before* it inspects whether `result` is `Ok` or `Err` [5](#0-4) . Only after this unconditional insertion does the code branch on `result`, and on `Err` the tx is simply added to `rejected_tx_hashes` [6](#0-5) .

This is structurally identical to the reported class of bug: a fee-accounting step (here, the `paid_fee` check) that is bundled atomically with — and can force reversion of — an important, otherwise-successful operation (message consumption), while a separate bookkeeping ledger (`consumed_l1_handler_tx_hashes`) records the operation as done regardless of the failure.

### Impact Explanation
If this divergence is exploited or triggered (e.g., an L1 message deliberately or accidentally sent with `paid_fee_on_l1 == 0`, or any other `Err` returned from `execute_raw` for an L1Handler transaction — including any state error, gas overdraft returning fee-check errors that are propagated as errors rather than "reverted" transactions), the batcher's local bookkeeping treats the message as consumed while the actual Starknet state (and thus the OS/committed state) never marked the message nonce as consumed. Depending on how `consumed_l1_handler_tx_hashes` is later used (e.g., dedup against the L1 provider / mempool to prevent re-fetching the same L1→L2 message), this could permanently prevent the L1 message from ever being retried and successfully executed, effectively freezing whatever L1→L2 action (e.g., a bridge deposit) the message was meant to trigger — a permanent freezing-of-funds scenario, matching the report's "accrual of bad debt due to forced revert."

### Likelihood Explanation
Reachability requires only that an L1 message sender (an unprivileged actor who can call `sendMessageToL2` on the L1 core contract) submit a message, and that the corresponding `L1HandlerTransaction::execute_raw` return an `Err` variant (e.g. `paid_fee_on_l1 == 0`, or any other execution error surfaced as `Err` rather than being converted into "reverted"). This is plausible: a user only weakly controls `paid_fee_on_l1` (it's set on L1 at message-send time) and other error paths (state errors, malformed calldata causing `StateError`) can also surface as `Err`. The exact operational consequence of `consumed_l1_handler_tx_hashes` diverging from true consumption could not be fully traced to its consumer in the L1 provider / mempool component within the available search budget, so the ultimate severity of the divergence (silent permanent loss vs. benign re-queue) remains **unverified** and should be confirmed by tracing `consumed_l1_handler_tx_hashes` usage in the L1 provider/mempool crates.

### Recommendation
- Move the `if paid_fee == Fee(0)` check (and any other post-execution fee-related check for L1Handler transactions) to occur *before* `execution_state.commit()`, so that a failing fee check reverts the execution state consistently, matching the pattern already used for account transactions' `PostExecutionReport`.
- In `collect_execution_results_and_stream_txs`, only insert into `consumed_l1_handler_tx_hashes` inside the `Ok(...)` branch (or otherwise make the insertion conditional on whether the transaction's message-consumption state was actually committed), so the bookkeeping cannot diverge from the real state when `execute_raw` returns `Err`.

### Proof of Concept
Not independently reproduced within this investigation (no execution environment access). The trace supporting the claim is:
1. `crates/blockifier/src/transaction/l1_handler_transaction.rs:98-113` — commits execution state (including message consumption) then can still return `Err` on `paid_fee == Fee(0)`.
2. `crates/blockifier/src/blockifier/transaction_executor.rs:177-181` — any `Err` from `execute_raw` triggers a full `transactional_state.abort()`, discarding the "commit" from step 1.
3. `crates/apollo_batcher/src/block_builder.rs:641-649` and `708-716` — `tx_hash` is unconditionally inserted into `consumed_l1_handler_tx_hashes` prior to branching on `Ok`/`Err`, so the bookkeeping records "consumed" even when the underlying state changes were aborted.

I was unable to trace, within the tool budget, exactly how `consumed_l1_handler_tx_hashes` is consumed downstream (e.g., by the L1 provider to decide whether to re-offer the message), which is necessary to fully confirm the "permanent freeze" impact versus a merely cosmetic/logging divergence. This should be verified with a live Devin session that can grep across the `apollo_l1_provider` / mempool crates and, ideally, run an integration test that forces an `Err` from an L1Handler transaction (e.g. `paid_fee_on_l1 = Fee(0)`) inside `BlockBuilder::build_block` and inspects whether the message is ever retried.
