### Title
Historical write-set resource decoding in the REST API uses the current (post-upgrade) Move type layout instead of the layout at the transaction's own version - (File: `api/types/src/convert.rs`)

### Summary
`MoveConverter::into_transaction_info` and `MoveConverter::try_into_write_set_payload` decode a transaction's `WriteSet` into JSON `WriteSetChange`s by resolving each resource's Move struct layout through `self.inner` (an `AptosValueAnnotator` built from a single `StateView`). The API layer constructs exactly one `StateView`/`MoveConverter` at the **latest** ledger version and reuses it to render an entire batch of historical transactions spanning many different versions, per `api/src/context.rs` `render_transactions_sequential`/`render_transactions_non_sequential`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`into_transaction_info` builds `changes` by calling `try_into_write_set_changes` for every state key/write-op in the transaction's committed `WriteSet`, which internally resolves struct layouts via `self.inner.view_resource`/`view_module` (backed by the single, latest-version `StateView`). The code itself flags this exact defect with an explicit `TODO` comment:

```
// TODO: the resource value is interpreted by the type definition at the version of the converter, not the version of the tx: must be fixed before we allow module updates
``` [4](#0-3) 

The same defect and comment is duplicated for `try_into_write_set_payload` (used for `GenesisTransaction`/`WriteSetPayload::Direct`). [5](#0-4) 

The `MoveConverter` is constructed once per API call from `self.context.latest_state_view_poem(ledger_info)` and then applied to a whole list of `TransactionOnChainData` items that may span many different, older versions (e.g. `/transactions?start=...&limit=...` returns a range of historical transactions). [2](#0-1) [3](#0-2) 

Because the struct's Move type layout (field names, field types, field count/order, or presence of nested generics) is fetched from module bytecode as it exists at the single fixed (latest) version rather than the version at which each individual transaction's write-set was actually produced, any account/module upgrade that changes a resource's on-chain layout will cause historical write-set values (raw BCS bytes committed at an older version) to be decoded/annotated using the wrong (newer) layout. This can silently produce corrupted or type-confused JSON in the authenticated `/transactions` (and related) API responses: wrong field values, misinterpreted byte offsets, dropped/garbled fields, or (in more severe cases) a decode `Err` silently dropped via `.ok()`+`.flatten()`, causing whole `WriteSetChange` entries for that historical transaction to disappear from the API response without any error being surfaced to the client. [6](#0-5) 

This is an authenticated API/state-view output bound to the wrong version and object context: the JSON-rendered write-set for a transaction at version V no longer corresponds to the actual committed state at version V, even though the response is presented (and typically consumed by indexers/wallets/explorers) as an authoritative representation of that committed transaction.

### Impact Explanation
The BCS-encoded (`Bcs` accept-type) transaction API responses are unaffected, since they return the raw `TransactionOnChainData`/`WriteSet` bytes untouched (`BasicResponse::try_from_bcs` in `get_transaction_inner`). The vulnerability is scoped to the JSON-rendering path (`AcceptType::Json`), which is nonetheless the default and most widely consumed interface by indexers, wallets, and block explorers. A silent misinterpretation of historical resource data means downstream consumers relying on the JSON API (rather than replaying BCS/write-set data themselves) can be given incorrect committed-state information for older transactions after any module upgrade changes a resource layout — this is exactly the "Authenticated API...output bound to the wrong version, object, or proof context" impact category. No ledger data is corrupted on disk and no consensus/commit invariant is broken (durable storage, accumulators, and proofs remain correct); the damage is confined to the read-serving/JSON-conversion layer.

### Likelihood Explanation
This requires no attacker action — it is triggered automatically any time a module's resource struct layout changes across versions covered by the queried transaction range (a normal, permitted on-chain event for upgradeable Aptos Framework/user modules), combined with any client requesting historical transactions/write-set payloads via the JSON REST API. Given how routine module upgrades are, and that `render_transactions_sequential`/`render_transactions_non_sequential` process arbitrary version ranges through a single latest-version converter, likelihood of hitting the bug in the wild is moderate-to-high, though its user-visible severity is bounded (decode failure being silently swallowed is more likely to produce missing data than an unnoticed factually-wrong value, per the `.ok()`+`.flatten()` handling).

### Recommendation
- Construct (or select) a `MoveConverter`/`StateView` bound to each transaction's own version when rendering ranges of historical transactions, instead of reusing a single latest-version view for the whole batch, in `render_transactions_sequential`/`render_transactions_non_sequential` (`api/src/context.rs`).
- Propagate decode errors from `try_into_write_set_changes` instead of silently discarding them via `.ok()`+`.flatten()` in `into_transaction_info`, so that a version/layout mismatch surfaces as an explicit API error rather than a silently incomplete response.
- Apply the same fix to `try_into_write_set_payload`'s `Direct` write-set case.

### Proof of Concept
1. Deploy a module with resource `struct R has key { a: u64 }` and execute a transaction at version V that writes `R { a: 1 }`.
2. Upgrade the module so that `struct R` now has `{ a: u64, b: bool }` (a compatible upgrade at the VM level, since layout compatibility rules govern execution but not the API's historical rendering).
3. Query `GET /v1/transactions?start=V&limit=1` (or `GET /v1/transactions/by_version/V`) with `Accept: application/json`.
4. Observe that the JSON `changes[].data` for the `WriteResource` at version V is decoded using the **new** two-field layout against the **old** one-field BCS bytes, either producing a decode error (silently dropped, causing the change to vanish from the response) or, depending on the specific layout change, misinterpreted field values — while the equivalent `Accept: application/x-bcs` request continues to return the correct raw bytes for version V.

    pub fn render_transactions_sequential<E: InternalError>(
        &self,
        ledger_info: &LedgerInfo,
        data: Vec<TransactionOnChainData>,
        mut timestamp: u64,
    ) -> Result<Vec<aptos_api_types::Transaction>, E> {
        if data.is_empty() {
            return Ok(vec![]);
        }

        let state_view = self.latest_state_view_poem(ledger_info)?;
        let converter = state_view.as_converter(self.db.clone(), self.indexer_reader.clone());
        let txns: Vec<aptos_api_types::Transaction> = data
            .into_iter()
            .map(|t| {
                // Update the timestamp if the next block occurs
                if let Some(txn) = t.transaction.try_as_block_metadata_ext() {
                    timestamp = txn.timestamp_usecs();
                } else if let Some(txn) = t.transaction.try_as_block_metadata() {
                    timestamp = txn.timestamp_usecs();
                }
                let txn = converter.try_into_onchain_transaction(timestamp, t)?;
                Ok(txn)
            })
            .collect::<Result<_, anyhow::Error>>()
            .context("Failed to convert transaction data from storage")
            .map_err(|err| {
                E::internal_with_code(err, AptosErrorCode::InternalError, ledger_info)
            })?;

        Ok(txns)
    }
