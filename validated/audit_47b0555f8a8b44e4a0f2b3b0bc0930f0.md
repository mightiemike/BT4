Based on my investigation, I found a genuine, code-proven integrity gap analogous to the reported PDA-validation bug: a validation function that is supposed to bind execution output to committed metadata but silently skips fields that are part of the authenticated commitment.

### Title
`TransactionOutput::ensure_match_transaction_info` omits state-checkpoint / hot-state / position-state root validation, allowing `replay-verify` to certify a divergent state root as matching - ([File: types/src/transaction/mod.rs])

### Summary
`ensure_match_transaction_info` is the function used by replay-verification tooling (chunk-executor's `verify_execution`, the `aptos-move/cli` replay command, `aptos-debugger`, and `storage/db-tool`'s `replay_on_archive`) to assert that a locally re-executed `TransactionOutput` matches the `TransactionInfo` that was actually committed on-chain. The function checks status, gas, write-set hash, and event-root hash, but its own comment admits it "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)" [1](#0-0) . This means a local execution that reproduces a different `state_checkpoint_hash` (state root), `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` than what is on-chain will still be reported as a successful, matching replay.

### Finding Description
`ensure_match_transaction_info` performs targeted equality checks: [2](#0-1) 

Only `status`, `gas_used`, `write_set_hash` (`state_change_hash`), and `event_root_hash` are compared against `txn_info`. The state-checkpoint-related roots carried by `TransactionInfo` — `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — are never read or compared here, despite being part of the same `TransactionInfo` type [3](#0-2) .

This function is the sole correctness gate in the replay path:
- `execution/executor/src/chunk_executor/mod.rs`'s `verify_execution` calls it per-transaction to decide whether a locally-executed transaction output matches the transaction info recorded on the archive/ledger during a verified chunk replay [4](#0-3) .
- `aptos-move/cli/src/commands.rs`'s replay path calls it the same way to decide pass/fail for a single-transaction replay [5](#0-4) .

Because the state-checkpoint hash is exactly the Sparse-Merkle-Tree / state root produced by `DoStateCheckpoint`, and this is what the chunk-executor's `known_state_checkpoints` mechanism cross-checks during live enqueueing (`known[idx] == Some(computed_last_checkpoint_hash)` in `execution/executor/src/workflow/do_state_checkpoint.rs`) [6](#0-5) , the omission in `ensure_match_transaction_info` is a real, distinct gap in the offline/tooling verification path, not merely a duplicate of protections elsewhere.

### Impact Explanation
If VM execution logic diverges from mainnet's actual committed execution result in a way that produces the correct write set and events but a different post-execution state root (e.g., a bug specific to how the state merkle tree is assembled from the write set, or divergent handling of hot/position state), replay-verification tooling (`db-tool replay_on_archive`, `aptos-debugger`, CLI's `replay` command, and the `ChunkExecutor`'s `verify_execution_mode.should_verify()` path used during backup restore/replay) would all falsely report a passing, matching replay. This directly undermines the "committed state that differs from the correct VM result... accepted as valid" and "authenticated API or state-view output bound to the wrong version, object, or proof context" integrity gates: replay-verify is explicitly a tool relied upon to detect exactly this class of divergence before/after hard forks, and its correctness gate silently excludes the state root fields.

### Likelihood Explanation
The gap is deterministic and always present — it does not require attacker action, only that a real execution divergence (e.g., an on-chain bug, storage schema change, or replay engine defect) manifest in the state/hot-state/position-state checkpoint hash while leaving write-set/event hashes matching. Given `TransactionInfo`'s `state_change_hash` is the hash of the write set itself, and `state_checkpoint_hash` is a separately-computed periodic SMT root, these are not fully coupled — a bug that corrupts SMT insertion/root computation (but not the write set content itself) would be invisible to this check.

### Recommendation
Extend `ensure_match_transaction_info` in `types/src/transaction/mod.rs` to compare the locally computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when available/applicable) against the corresponding fields on `txn_info`, consistent with how `do_state_checkpoint.rs`'s `known_state_checkpoints` validation already treats these fields as commit-critical. At minimum, replay-verify tooling should fail loudly instead of silently ignoring these root fields, per the existing TODO in the code.

### Proof of Concept
Not independently reproducible without a concrete VM/state-computation divergence bug to trigger it (this finding documents a verification-gap in the tooling itself, confirmed by the code's own comment and the omitted field comparisons) [1](#0-0) . A conceptual PoC: construct a `TransactionOutput` whose write set and events exactly match a given `TransactionInfo` but whose actual resulting state-tree root (via a modified/buggy `DoStateCheckpoint` implementation) differs from `txn_info.state_checkpoint_hash()`; `ensure_match_transaction_info` returns `Ok(())`, while the true ledger state has silently diverged.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
