### Title
`DeleteAccount` action permanently burns funds when `beneficiary_id` is a syntactically valid but non-existent account - (File: `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/actions.rs`)

### Summary
The `DeleteAccount` action lets any account owner move their entire remaining balance to an arbitrary `beneficiary_id` when deleting their own account. Action validation only checks that `beneficiary_id` is a *syntactically* valid `AccountId` — it never checks that the account actually exists. If the beneficiary account does not exist, the balance-refund receipt this action generates fails (refunds are never allowed to implicitly create an account) and, because it is a system/refund receipt, the failure causes the entire balance to be **burned outright** rather than returned to anyone. This mirrors the reported `transferPosition` bug class: a public, unprivileged, value-moving function with no validity check on the destination, leading to permanent loss of value.

### Finding Description
`validate_delete_action` only validates the format of `beneficiary_id`: [1](#0-0) 

There is no check that `beneficiary_id` corresponds to an existing account. When the action executes, `action_delete_account` takes the account's remaining balance and issues a `Receipt::new_balance_refund` addressed to that unchecked `beneficiary_id`, then unconditionally removes the account: [2](#0-1) 

That refund receipt is a system-predecessor ("refund") receipt. Refund receipts are explicitly forbidden from implicitly creating the destination account, for *any* account type, including named accounts: [3](#0-2) 

So if `beneficiary_id` does not already exist, the transfer inside the refund receipt fails with `AccountDoesNotExist` (confirmed by the test `refund_may_not_create_universal_account`): [4](#0-3) 

Finally, when a refund receipt (system-predecessor) fails, the runtime does not return the funds to anyone — it burns them into `other_burnt_amount`: [5](#0-4) 

By this point the source account has already been deleted (`*account = None;` in `action_delete_account`, executed before the refund receipt is even processed), so there is no way to recover the balance — it is gone permanently.

### Impact Explanation
Any single unprivileged transaction signer who submits a `DeleteAccount` action with a `beneficiary_id` that is well-formed but does not exist (e.g., a typo'd named account, or an account that was never created) permanently and irrecoverably burns their entire account balance. This is a direct, transaction-triggered, unauthorized-value-destruction path reachable from a single submitted transaction — no privileged role, validator, or network condition is required. It matches the "permanently frozen/lost funds" impact category.

### Likelihood Explanation
This requires no adversary and no special conditions — it happens on ordinary use whenever a user (or a wallet/tooling bug) supplies an incorrect but syntactically valid `beneficiary_id` while deleting an account with a positive balance. Given `DeleteAccount` is a commonly available action and `beneficiary_id` is fully attacker/user-controlled input with only format-level validation, the likelihood of triggering this by mistake (or via a malicious dApp/relayer crafting the delete-account transaction on a user's behalf) is high.

### Recommendation
Before allowing execution (or at minimum before removing the source account), require that `beneficiary_id` resolve to an existing account, or change the refund mechanics so that a failed beneficiary transfer returns the balance to the deleted account's own residual state/predecessor instead of being burned. At minimum, `action_delete_account` should verify the beneficiary account exists (a state read is already available in this context) and reject the action with an explicit error (e.g., a new `BeneficiaryAccountDoesNotExist` `ActionErrorKind`) rather than silently deleting the account and later burning the funds via a failed refund.

### Proof of Concept
1. Account `alice.near` holds a balance and has never created `nonexistent.near`.
2. `alice.near` submits a transaction to `alice.near` containing `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent.near" })`.
3. `validate_delete_action` accepts the action because `"nonexistent.near"` is a syntactically valid `AccountId`.
4. `action_delete_account` computes `account_balance`, enqueues `Receipt::new_balance_refund("nonexistent.near", account_balance)`, and deletes `alice.near`'s account state.
5. The refund receipt executes: `check_account_existence`/`implicit_creation_allowed` reject implicit creation of `nonexistent.near` because the receipt `is_refund == true`, causing the transfer to fail with `ActionErrorKind::AccountDoesNotExist`.
6. Because the failed receipt's predecessor is `system` (a refund), the runtime burns `account_balance` into `stats.balance.other_burnt_amount` instead of returning it anywhere.
7. `alice.near`'s balance is permanently lost with no recovery path, reproducing the same "position permanently lost due to unchecked recipient" bug class as the referenced report.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
