Confirmed finding: the `accept_new_txs` pause gate exists only in `apollo_http_server`'s `add_rpc_tx`/`add_tx` handlers via `check_new_transactions_are_allowed`, not inside the `Gateway` component itself.### Title
Operator-paused `accept_new_txs` gate lives only in `apollo_http_server`, silently bypassed by transactions arriving via P2P — (File: `crates/apollo_mempool_p2p/src/runner/mod.rs`)

### Summary
Analogous to the Illuminate `Redeemer.sol` bug (an admin-controlled "pause" flag protecting only one entry point while other entry points into the same downstream state-changing function remain unprotected), the sequencer's only mechanism to stop transaction admission — `HttpServerDynamicConfig.accept_new_txs` — is enforced exclusively inside the `apollo_http_server` route handlers, not inside `Gateway::add_tx`/`add_tx_inner` itself. Any transaction that reaches `Gateway::add_tx` through a path other than the local HTTP server (specifically, transactions relayed peer-to-peer via `MempoolP2pRunner`) skip this check entirely and are admitted to the mempool even while the operator has paused ingestion.

### Finding Description
The pause flag is checked with `check_new_transactions_are_allowed(accept_new_txs)` only inside the two HTTP handler functions `add_rpc_tx` and `add_tx` in `crates/apollo_http_server/src/http_server.rs:167-217`, before they call `add_tx_inner` → `app_state.gateway_client.add_tx(...)`. [1](#0-0) [2](#0-1) 

The `Gateway` component itself — reached through `apollo_gateway_types::communication::GatewayClient::add_tx` — has no notion of this pause flag at all. Its top-level `add_tx`/`add_tx_inner` only checks `check_declare_permissions` (an unrelated per-tx-type `block_declare`/`authorized_declarer_accounts` gate) and stateless/stateful validators; there is no `accept_new_txs`/pause check anywhere in `crates/apollo_gateway/src/gateway.rs`. [3](#0-2) 

Crucially, `MempoolP2pRunner`, which forwards transactions received from other peers over gossip directly into the same `gateway_client.add_tx(GatewayInput { rpc_tx, message_metadata })` call, does not go through the HTTP server route handlers and therefore never sees the `accept_new_txs` check: [4](#0-3) 

This is architecturally identical to the reported bug class: a pause switch is implemented as a guard clause bolted onto one specific ingress function (`add_rpc_tx`/`add_tx` in the HTTP layer, analogous to `redeem()`), while a second, equally-authorized ingress function into the same protected state-mutating logic (the P2P `add_tx` path via `MempoolP2pRunner`, analogous to `autoRedeem()`/`authRedeem()`) has no equivalent guard.

### Impact Explanation
If an operator sets `accept_new_txs=false` (e.g. during an incident, exploit, or unprofitable-market pause) intending to stop the sequencer's `Gateway`/`Mempool` from admitting further transactions, an attacker (or any honest peer relaying gossip) can still get transactions accepted into that same node's mempool by having them arrive over the mempool P2P gossip topic instead of the local HTTP endpoint. Because `MempoolP2pRunner` calls the identical `gateway_client.add_tx` used by the HTTP server, and the pause check never executes on that path, the paused node keeps validating, admitting, and later proposing/executing transactions that the operator explicitly intended to block. This can result in exactly the transaction processing the pause was meant to prevent (e.g. continuing to admit transactions from blocked/malicious senders, dangerous contract interactions, or transactions during an emergency freeze), causing unauthorized account action / continued state mutation contrary to operator intent, satisfying the "unauthorized account action" / "network unable to confirm new transactions [as intended]" impact bar.

### Likelihood Explanation
Likelihood is high given normal, expected p2p operation: any node running `mempool_p2p` with `execution_mode` enabled continuously receives and relays transactions from peers via `MempoolP2pRunner::start` (`crates/apollo_mempool_p2p/src/runner/mod.rs:104-128`), which unconditionally forwards them to the Gateway regardless of the HTTP-server-level pause. No privileged or malicious actor action is required beyond a single unprivileged transaction being broadcast on the mempool gossip topic (which any network participant, or the transaction's own submitter to a different node, can trigger) — it will propagate to the paused node's Gateway and bypass the intended pause.

### Recommendation
Move the `accept_new_txs` (pause) check out of the HTTP-server-only route handlers and into the shared `Gateway`/`GenericGateway::add_tx_inner` entry point (or equivalently into `MempoolCommunicationWrapper::add_tx`), so that every path that ultimately calls `Gateway::add_tx` — whether from the local HTTP server or from `MempoolP2pRunner`'s P2P forwarding — is subject to the same operator pause decision. Alternatively, propagate the dynamic config into the `Gateway` component and have `MempoolP2pRunner` (or `Gateway::add_tx_inner`) consult it before admitting transactions received over gossip.

### Proof of Concept
1. Operator sets `http_server_config.dynamic_config.accept_new_txs = false` on Node A to pause new-transaction ingestion (confirmed by `is_ready` returning `SERVICE_UNAVAILABLE` and `POST /gateway/add_transaction` returning `HttpServerError::DisabledError` — see `crates/apollo_http_server/src/http_server_test.rs:100-115`).
2. An unprivileged user submits the same (or any) transaction to Node B (an un-paused peer) via its HTTP server; Node B's `Gateway` validates it and its `MempoolP2pPropagator` broadcasts it over the `apollo_mempool_transaction_propagation` gossip topic.
3. Node A's `MempoolP2pRunner::start` receives the gossip batch and calls `self.gateway_client.add_tx(GatewayInput { rpc_tx, message_metadata })` directly (`crates/apollo_mempool_p2p/src/runner/mod.rs:104-128`), with no `accept_new_txs` check anywhere on this path.
4. Node A's `Gateway::add_tx_inner` runs full stateless/stateful validation and, on success, forwards the transaction to Node A's `Mempool` via `mempool_client.add_tx` — i.e., the transaction is admitted on Node A despite the operator having paused new-transaction acceptance on that very node.
