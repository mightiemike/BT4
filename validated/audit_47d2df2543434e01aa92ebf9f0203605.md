### Title
L1Handler transactions have no user-configurable fee/gas bound, so a fixed protocol-wide `l1_handler_max_amount_bounds` combined with L1-message consumption on revert causes permanent loss of the L1 sender's bridged message and fee - ([File: crates/blockifier/src/transaction/l1_handler_transaction.rs])

### Summary
The Notional report flags `depositUnderlyingExternal()` for lacking slippage control: the depositor cannot bound the deposit outcome against changes (from other transactions) between submission and execution, so intervening state changes can silently degrade the result. The sequencer has a structurally analogous gap for `L1HandlerTransaction`s (transactions triggered by an unprivileged L1 message sender): unlike V3 account transactions, which let the sender specify `resource_bounds`/`max_fee` matching *their own* risk tolerance, an L1Handler transaction's gas ceiling is a single, fixed, network-wide constant (`l1_handler_max_amount_bounds`) that the L1 message sender has no ability to configure per message. If L2 gas usage/price context shifts between when the L1 message is sent and when it is executed on L2 (e.g., due to intervening transactions/congestion raising costs — the direct analog of "other prime-rate-changing transactions" front-running the deposit), the transaction can blow the fixed bound, revert, and yet still be treated as consumed, permanently losing the user's bridged message/fee.

### Impact Explanation
An L1 message sender bridging funds to L2 via an `l1_handler` entry point has no way to specify their own acceptable gas/fee ceiling — unlike V3 transactions, which allow `resource_bounds` tuned to the sender's own risk appetite. The bound applied is a fixed constant (`l1_handler_max_amount_bounds`) set at the protocol/versioned-constants level. If, between L1 message submission and L2 inclusion, other transactions or contract-state changes cause the L1Handler's execution cost to exceed this fixed bound (analogous to another actor's transaction changing the "rate" the depositor relied on), the transaction reverts via `FeeCheckReport::check_all_gas_amounts_within_bounds` returning an error, and the state changes (e.g., minting tokens/crediting a deposit on L2) are rolled back. Yet the transaction is still recorded as executed and its hash is placed in `consumed_l1_handler_tx_hashes`, which is fed back to the L1 events provider as "consumed." This is a permanent loss of the L1 sender's bridged asset/fee: the deposit's L2-side effect never happens, but the L1-side message that represented it is retired and cannot be resent.

### Likelihood Explanation
This is reachable purely by an unprivileged L1 message sender invoking any `l1_handler` entry point (e.g., a bridge deposit) whose gas cost is close to the fixed `l1_handler_max_amount_bounds`. No privileged operator/proposer action is required — ordinary variance in contract state (storage growth, other legitimate transactions altering state prior to the L1Handler's execution) can push actual gas usage over the fixed ceiling. Because the sender cannot specify a bound of their own, they cannot protect themselves the way an account-transaction sender can with `resource_bounds`.

### Recommendation
Give L1Handler transactions a sender-specified (or L1-message-embedded) upper bound on gas/fee analogous to V3 `resource_bounds`, and reconcile `paid_fee_on_l1` against the *actual* fee required (not just non-zero), rejecting/holding the message rather than marking it consumed when the required fee/gas exceeds what was paid. Alternatively, avoid marking an L1Handler transaction as "consumed" toward the L1 provider when it reverted due to exceeding `l1_handler_max_amount_bounds`, so the message remains retryable instead of being permanently lost.

### Proof of Concept
1. An L1 depositor calls the Starknet core contract to send an L1→L2 message invoking a contract's `l1_handler` (e.g., a bridge `deposit` handler), paying a small non-zero `paid_fee_on_l1`.
2. Before this L1Handler transaction is included on L2, other legitimate transactions increase the state/gas cost of executing that handler (e.g., growing a dictionary/storage the handler must read/write), pushing the L1Handler's actual gas usage above `l1_handler_max_amount_bounds`.
3. When the L1Handler transaction executes in `L1HandlerTransaction::execute_raw`, `FeeCheckReport::check_all_gas_amounts_within_bounds` fails; `execution_state.abort()` rolls back all deposit-crediting state changes, and the transaction is recorded with a `revert_error` [1](#0-0) .
4. The batcher nonetheless inserts the transaction's hash into `consumed_l1_handler_tx_hashes` unconditionally [2](#0-1) , and on block commit reports it to the L1 events provider as consumed [3](#0-2) .
5. The depositor's L1 message is now permanently retired with no L2-side effect and no possibility of resubmission, despite having paid a fee on L1 — a direct funds-loss analog to the missing slippage protection in the original report.
