### Title
`DeleteAccountAction` permanently burns account balance if the immutable `beneficiary_id` does not exist - ([File: runtime/runtime/src/actions.rs])

### Summary
`DeleteAccountAction::beneficiary_id` is chosen by the account owner at the moment of self-deletion and is never validated to reference an existing account. The remaining balance is dispatched as a *system refund receipt*, and refund receipts are structurally forbidden from creating any account. If `beneficiary_id` does not exist (typo, not-yet-created account, or an account deleted between transaction construction and execution), the transfer fails and — because it originates from `"system"` — the entire balance is unconditionally burned rather than returned to the (now nonexistent) source account or the signer.

### Finding Description
`action_delete_account` unconditionally builds `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` without any check that `beneficiary_id` exists, then deletes the source account: [1](#0-0) 

`Receipt::new_balance_refund` sets `predecessor_id: "system"`, marking the resulting receipt as a refund: [2](#0-1) 

When this refund receipt is later applied, `is_refund` is derived from `predecessor_id().is_system()`, and `check_account_existence` is invoked for the `Transfer` action against `implicit_creation_allowed`, which unconditionally returns `false` whenever `is_refund` is true — for every account type, including named accounts: [3](#0-2) [4](#0-3) 

So if `beneficiary_id` does not exist, the action fails with `AccountDoesNotExist`. Because the enclosing receipt's predecessor is `"system"`, the runtime treats this as a failed refund and **burns** the deposit instead of returning it anywhere: [5](#0-4) 

This is also explicitly documented as intended refund semantics ("If the execution of a refund fails, the refund amount is burnt"): [6](#0-5) 

Unlike a normal `Transfer` action (which the signer/predecessor can retry, correct, or which fails atomically before any state change), `DeleteAccountAction` is irreversible: the source account is removed from state in the very same action (`*account = None;`) regardless of whether the beneficiary transfer receipt later succeeds, since the deletion and refund-receipt creation happen synchronously while the refund receipt itself executes asynchronously in the outbox and can fail with no way to recover. This mirrors the reported bug class exactly: the "recipient address" (`beneficiary_id`) is fixed at the time of the privileged action and cannot be changed afterward; if that address turns out to be unable to receive (nonexistent, analogous to a token-level block), the funds are not merely stuck — they are destroyed outright.

### Impact Explanation
Any account owner (or an access key holder with full access) who submits a `DeleteAccount` action with a `beneficiary_id` that does not exist at execution time — whether due to typo, race (beneficiary deleted between signing and execution), or misunderstanding that beneficiary accounts must pre-exist — permanently and unrecoverably loses their entire remaining account balance, since it is burned rather than refunded to any party. This is a direct, protocol-level, unauthorized/irrecoverable loss of user funds triggered by a single ordinary transaction, with no compensating control, matching the "permanently frozen funds" (here, destroyed funds) acceptance criterion.

### Likelihood Explanation
Reachable by any unprivileged transaction signer via a single `DeleteAccount` action; no special protocol feature gate or validator collusion is required, and no pre-execution check enforces that `beneficiary_id` exists. Typos in account IDs and races against concurrent account deletions are realistic, non-adversarial occurrences, making accidental triggering plausible; a user misled by third-party tooling could also be induced to target a nonexistent beneficiary.

### Recommendation
Validate that `beneficiary_id` refers to an existing (and initialized) account before allowing `DeleteAccountAction` to execute, returning an `ActionError` (e.g., a new `BeneficiaryAccountDoesNotExist` kind) if it does not — mirroring the existing `AccountDoesNotExist` check pattern in `check_account_existence`. Alternatively, if the beneficiary transfer receipt fails, route the balance to a recoverable destination (e.g., burn only after routing through a normal, creatable-account-eligible transfer, or retain it in a system-recoverable pool) instead of unconditionally burning it.

### Proof of Concept
1. Create account `alice.near` with balance `B`.
2. From `alice.near`, submit `DeleteAccountAction { beneficiary_id: "nonexistent.near" }` where `nonexistent.near` has never been created.
3. `action_delete_account` (`runtime/runtime/src/actions.rs:380-386`) removes `alice.near` from state and enqueues `Receipt::new_balance_refund("nonexistent.near", B)`.
4. That refund receipt is later applied; `check_account_existence` rejects the `Transfer` action with `AccountDoesNotExist` because `implicit_creation_allowed` returns `false` for `is_refund == true` (`runtime/runtime/src/actions.rs:928-947`).
5. `runtime/runtime/src/lib.rs:1047-1054` detects `receipt.predecessor_id().is_system()` and `result.result.is_err()`, and adds `B` to `stats.balance.other_burnt_amount` — the funds are permanently destroyed; neither `alice.near` (deleted) nor `nonexistent.near` (never created) nor any validator/treasury account receives them.

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.
