### Title
Unrevocable, dynamically-mutable delegation of code execution via `GlobalContractDeployMode::AccountId` lets a global-contract publisher rug every account that opts in ("proxy admin" rug vector) - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
`DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` lets any account publish shared WASM code addressable by that account's `AccountId`, explicitly documented as allowing "the owner to update the contract for all its users" [3](#0-2) . Any unprivileged account can then attach itself to that shared code with `UseGlobalContractAction` [4](#0-3) . Because code resolution is fully dynamic — every call re-reads whichever code currently sits at the `GlobalContractCode { AccountId(id) }` trie slot, not a hash pinned at the time of "use" — the publisher can redeploy new, malicious code to that same `AccountId` slot at any later moment (`action_deploy_global_contract` → `apply_distribution_current_shard`, which simply `state_update.set`s the trie key each time) [5](#0-4) , and it will immediately become the executable code for every account that adopted it, with no consent, delay, versioning pin, or opt-out mechanism.

### Finding Description
This mirrors the external report's "Rug pull by proxy Admin" vector (4a): a party who does not control an account's balance can nevertheless take over that account's executable logic at any later time and steal its funds, because the "implementation" backing the account is mutable and controlled unilaterally by a third party.

Mechanics in nearcore:
1. Account `Owner` deploys arbitrary WASM code as a global contract using `GlobalContractDeployMode::AccountId` [6](#0-5) . The code is written under trie key `GlobalContractCode { identifier: AccountId(Owner) }`.
2. Any unprivileged account `Victim` calls `UseGlobalContractAction` referencing `GlobalContractIdentifier::AccountId(Owner)`. This sets `Victim`'s `AccountContract` to `GlobalByAccount(Owner)`, with no restriction and no user-visible “pin” of the current code hash [7](#0-6) .
3. On every subsequent `FunctionCall` receipt into `Victim`, the runtime resolves the contract to execute by re-looking up whatever code is *currently* stored at `AccountId(Owner)`'s slot — `RuntimeContractIdentifier::resolve` follows the `GlobalContractIdentifier` and fetches the live hash, it does not remember the hash observed at "use" time [1](#0-0) .
4. `Owner` can call `DeployGlobalContractAction` again with the same `AccountId` mode at any time. `apply_distribution_current_shard` simply overwrites the trie value at the same `GlobalContractCode` key with the new code and bumps an internal freshness nonce — there is no owner-consent check from `Victim`, no time-lock, no governance, and no way for `Victim` to detect or block the swap before it lands on their shard [8](#0-7) .
5. The new code executes in `Victim`'s own account context on the next call. Contract logic executing as `Victim` has full authority to issue `Promise::new(...).transfer(...)` and other actions using `Victim`'s own NEAR balance and access keys (this is standard contract-authored promise behavior, not a special privilege) — so `Owner` can plant a backdoor that drains `Victim`'s balance to an attacker-controlled account on the next invocation, entirely from a normal, unprivileged transaction flow.

This is confirmed working end-to-end in existing tests that exercise cross-shard update propagation of `AccountId`-mode global contracts and show that a later deploy under the same identifier supersedes the earlier one for every account that already "uses" it [9](#0-8) [10](#0-9) .

### Impact Explanation
Any account that adopts an `AccountId`-mode global contract has effectively handed permanent, revocation-free control of its own contract logic — and therefore its balance and access-key management surface — to whoever controls the publishing `AccountId`. There is no cryptographic commitment to the code the victim inspected at adoption time; the publisher can swap in logic that transfers away the victim's NEAR balance, deletes/adds access keys, or otherwise acts adversarially, at the publisher's sole discretion. This is a concrete unauthorized-value-movement vector reachable purely from ordinary account-level transactions (`DeployGlobalContractAction` + `UseGlobalContractAction` + a later `FunctionCall`), matching the "Rug pull by proxy Admin" class in the referenced report (issue 4a). Because uptake of shared/global contracts is an advertised, intended usage pattern (to save per-account storage costs), this is a realistic trust trap for any project or wallet that recommends users "use" a shared `AccountId`-mode contract.

### Likelihood Explanation
Likelihood depends entirely on user/dApp behavior: a victim must voluntarily call `UseGlobalContractAction` pointing at an `AccountId`-mode contract published by a party they trust. This is analogous to trusting an upgradeable proxy's admin key — the protocol offers no safeguard (no timelock, no hash-pinning at use time, no way to freeze/immutabilize adoption) against the publisher becoming malicious or being compromised later, so once adoption happens the attack is a single subsequent transaction (`DeployGlobalContractAction`) away, with certain success and no ability for the victim to preempt it.

### Recommendation
- Document prominently (and enforce, if desired) that `UseGlobalContractAction` referencing `AccountId` mode grants the publisher indefinite mutable control over the code executed on behalf of the adopting account; provide a way for adopters to "pin" a specific code hash (i.e., effectively convert their reference to `CodeHash` mode) once they are satisfied with the code, so future `Owner` deploys under the same `AccountId` do not silently propagate to already-attached accounts.
- Consider adding a `DetachGlobalContract`/`FreezeGlobalContractVersion` action so adopting accounts can lock in the currently-referenced code hash without needing to redeploy their own copy.
- At minimum, surface an explicit warning/acknowledgement requirement (analogous to a signed consent) when an account uses `AccountId`-mode identifiers, distinguishing this from the immutable `CodeHash` mode.

### Proof of Concept
1. `Owner` submits `DeployGlobalContractAction { code: benign_code, deploy_mode: AccountId }` (signed, ordinary transaction).
2. `Victim` submits `UseGlobalContractAction { contract_identifier: AccountId(Owner) }`, setting `Victim.contract = GlobalByAccount(Owner)` [11](#0-10) .
3. `Victim` funds their account normally and interacts with the (currently benign) shared contract, believing its logic is fixed.
4. `Owner` submits a second `DeployGlobalContractAction { code: malicious_code, deploy_mode: AccountId }` targeting the same `Owner` `AccountId`. This overwrites the `GlobalContractCode{AccountId(Owner)}` trie value [5](#0-4) , distributed to all shards via the standard `GlobalContractDistributionReceipt` forwarding mechanism [12](#0-11) .
5. Any subsequent `FunctionCall` receipt to `Victim` resolves to the new malicious code (`RuntimeContractIdentifier::resolve` re-fetches the live hash every time, per step above), which issues a `Transfer` promise moving `Victim`'s NEAR balance to `Owner`/an attacker account — funds are stolen from an account that never authorized or was informed of the code swap.

    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {

            account_id: account_id.clone(),

        }
        .into());
        return Ok(());

    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}

fn forward_distribution_next_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    epoch_info_provider: &dyn EpochInfoProvider,
    state_update: &mut TrieUpdate,
    receipt_sink: &mut ReceiptSink,
    receipt_to_tx: &mut Vec<(CryptoHash, ReceiptToTxInfo)>,
) -> Result<(), RuntimeError> {
    let shard_layout = epoch_info_provider.shard_layout(&apply_state.epoch_id)?;
    let already_delivered_shards = BTreeSet::from_iter(
        global_contract_data
            .already_delivered_shards()
            .iter()
            .cloned()
            .chain(std::iter::once(apply_state.shard_id)),
    );
    let Some(next_shard) = shard_layout
        .shard_ids()
        .filter(|shard_id| !already_delivered_shards.contains(&shard_id))
        .next()
    else {
        return Ok(());
    };
    let already_delivered_shards = Vec::from_iter(already_delivered_shards);
    let predecessor_id = receipt.predecessor_id().clone();
    let next_receipt = global_contract_data.forward(next_shard, already_delivered_shards);
    let mut next_receipt = Receipt::new_global_contract_distribution(predecessor_id, next_receipt);
    let receipt_id = apply_state.create_receipt_id(receipt.receipt_id(), 0);
    next_receipt.set_receipt_id(receipt_id);
    if apply_state.save_receipt_to_tx {
        receipt_to_tx.push((
            receipt_id,
            ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: *receipt.receipt_id(),
                    parent_predecessor_id: receipt.predecessor_id().clone(),

                receiver_account_id: next_receipt.receiver_id().clone(),
                shard_id: apply_state.shard_id,
            }),

/// Test that nonce-based idempotency prevents stale overwrites during global contract updates.
///
/// Deploys a trivial contract first (AccountId mode), waits for distribution,
/// then deploys rs_contract (AccountId mode) with a higher auto-incremented nonce.

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_global_contract_nonce_prevents_stale_overwrite() {
    init_test_logger();
    let mut env = GlobalContractsReshardingTestEnv::setup();

    let deploy_user = env.users[0].clone();

    // Step 1: Deploy trivial contract as first version (AccountId mode).
    tracing::info!(target: "test", "Deploying first version of global contract (trivial contract)...");
