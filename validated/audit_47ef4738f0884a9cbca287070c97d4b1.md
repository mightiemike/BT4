## Finding

### Title
`DbStateView` silently returns an **unverified** state value as verified when the Merkle-proof fetch errors - ([File: storage/storage-interface/src/state_store/state_view/db_state_view.rs])

### Summary
`DbStateView::get` is the read path used by `verified_state_view_at_version`, whose entire purpose is to hand out state reads that are checked against a specific, ledger-bound state root hash. When the proof-fetch call fails, the verification is silently skipped via `if let Ok(...)`, and the function still returns the value obtained from a *separate*, unauthenticated read path as if it had been verified.

### Finding Description
`DbStateView::get` (constructed only via `VerifiedStateViewAtVersion::verified_state_view_at_version`) is supposed to guarantee that every value it returns for `version` is checked against `maybe_verify_against_state_root_hash`, which is the `state_checkpoint_hash` taken from an authenticated `TransactionInfo` proof: [1](#0-0) 

The verification step is:
```rust
if let Ok((value, proof)) =
    self.db.get_state_value_with_proof_by_version(key, version)
{
    proof.verify(root_hash, *key.crypto_hash_ref(), value.as_ref())?;
}
Ok(self.db.get_state_value_with_version_by_version(key, version)?)
``` [2](#0-1) 

Two independent DB reads are used:
1. `get_state_value_with_proof_by_version` — fetches a value **and** a `SparseMerkleProof`, and is used only to run `proof.verify(...)`.
2. `get_state_value_with_version_by_version` — an unauthenticated read from the raw state-KV store, whose result is what's actually returned to the caller.

If call (1) returns `Err` (e.g. the Jellyfish Merkle node for that path/version is momentarily unavailable — a real possibility since the state-KV DB and the state-Merkle DB are pruned/updated on independent code paths, per the comment "DB doesn't support returning proofs for buffered state" already on this struct), the `if let Ok(...)` branch is simply skipped — the function does **not** propagate the error and does **not** abort. It falls through to call (2) and returns whatever raw value is present, without ever having checked it against `root_hash`. The function's contract ("only optionally verify proof" per doc comment) already acknowledges that verification may be skipped, but the surrounding callers (`api/src/context.rs`, `vm-validator/src/vm_validator.rs`, `storage/db-tool/src/replay_on_archive.rs`) treat `verified_state_view_at_version` as an authenticated view bound to `ledger_info`'s state root, not as best-effort.

### Impact Explanation
This breaks the "Authenticated API or state-view output bound to the wrong version, object, or proof context" invariant: a value returned from a nominally proof-checked state view can, on a transient/racy proof-read failure, be an unverified (and in a corrupted or actively-forking storage scenario, a *wrong*) value silently accepted as if it had passed Merkle-proof verification. Consumers include VM validation (`vm-validator/src/vm_validator.rs`) and the REST API context (`api/src/context.rs`), both of which rely on this view's contract for correctness of account/resource state used to validate transactions and serve authenticated reads.

### Likelihood Explanation
The bug is a defensive-fallback / error-swallowing defect rather than something directly triggerable by attacker-supplied transaction input. It manifests only when the proof-side read errors while the raw KV read succeeds for the same key/version — plausible during pruning races or transient storage errors, but I was not able to fully verify (within the tool budget available) whether the two underlying stores can diverge in a way that is reliably reachable by an external, unprivileged actor on a mainnet node, versus only being a rare local storage race. This uncertainty should be resolved with further tracing of `state_kv_db` vs `state_merkle_db` pruning ordering before treating this as confirmed high/critical severity.

### Recommendation
Do not use `if let Ok(...)` to swallow errors from the proof-fetch call. Propagate the error (`?`) so any failure to authenticate the returned value causes `get` to fail loudly, rather than silently returning an unverified value under the "verified" state-view contract.

### Proof of Concept
Not independently reproduced — would require constructing a state store where `get_state_value_with_proof_by_version` errors (e.g., missing/pruned Merkle node) while `get_state_value_with_version_by_version` still succeeds for the same key/version, then observing that `DbStateView::get` returns the raw value without verification error.

Given the residual uncertainty on exact reachability noted above, I present this as the strongest local analog found, but recommend further investigation into pruner interleaving between `state_kv_db` and `state_merkle_db` before treating it as confirmed.
