### Title
Case-insensitive owner-binding checks vs. case-sensitive KVStore key partitioning allow duplicate/orphaned secret rows for the same JWT-derived owner - ([File: core/capabilities/vault/workflow_owner_derivation.go])

### Summary
`DeriveJWTAuthorizedVaultWorkflowOwner` derives a canonical checksummed hex owner via `common.BytesToAddress(addr).Hex()` and only checks the JWT's `workflow_owner` claim against it with `strings.EqualFold` [4](#0-3) . Downstream, all owner-binding validations in `authorizer.go` and `capability.go` use `vaultutils.NormalizeOwner` (case-insensitive) to compare a request's `SecretIdentifier.Owner` against the authorized owner, and `vaultutils.WorkflowOwnerToLabel` parses the owner through `common.HexToAddress`, which is also case-insensitive [5](#0-4) . However, the OCR plugin's `KVStore` partitions rows using `vaulttypes.KeyFor(id)`, which does raw, case-sensitive string concatenation of `id.Owner` [1](#0-0)  and `WriteMetadata`/`GetMetadata` key on `metadataPrefix+owner` verbatim [6](#0-5) .

### Finding Description
An attacker who legitimately holds a JWT authorizing owner `0xAb5801...` (checksummed) can submit a `SecretsCreate`/`Update`/`Delete` request where `SecretIdentifier.Owner` is instead lowercase (`0xab5801...`) or uppercase. The owner-binding check (`validateEncryptedSecretOwnerMismatch` / `validateSecretIdentifierOwnerMismatch`) passes because it uses `NormalizeOwner`, which lowercases both sides before comparing [7](#0-6) . The TDH2 ciphertext label check (`EnsureRightLabelOnSecret` → `WorkflowOwnerToLabel`) also passes because `common.HexToAddress` normalizes case when producing the 20-byte address for the label [8](#0-7) . The request then reaches the OCR plugin's `stateTransitionCreateSecretsRequest`/`KVStore.WriteSecret`, which stores the row under `keyPrefix + vaulttypes.KeyFor(id)` using the exact (differently-cased) `id.Owner` string byte-for-byte, and separately stores per-owner metadata under `metadataPrefix+owner` verbatim [9](#0-8) . Because all case comparisons upstream treat `0xAb58...` and `0xab58...` as the same identity, but the KVStore uses them as distinct map keys, a single JWT-authorized owner can create secrets under multiple differently-cased raw-key partitions that never collide in `GetSecret`/`DeleteSecret`/metadata tracking (each cased variant gets its own independent metadata list and secret keys) — enabling: (1) an attacker creating a secret at a given `(key,namespace)` under one case-variant, then updating/deleting the "same" logical secret under a different case-variant, silently creating an orphaned/duplicate row instead of overwriting or deleting the original (since `store.GetSecret`/`removeIDFromMetadata` look up metadata keyed by that same raw-case owner string, and a lowercase request never sees the uppercase-partition's metadata); and (2) subtly, a `ListSecretIdentifiers` request for one case variant will not surface secrets created under a different case variant, silently disclosing incomplete lists that could mislead deletion/cleanup logic and leave a duplicate secret persisting under the node's committed KV state after a workflow believes it deleted all copies.

### Impact Explanation
This matches the "secret disclosure or secret overwrite due to owner-identity confusion" impact class: an attacker fully authorized for owner X can create multiple silently-diverging storage partitions for what should be a single logical owner identity, causing (a) delete/update operations that appear successful but leave stale duplicate ciphertext rows persisting in committed OCR state (a form of data integrity/tampering and unintended data retention), and (b) `ListSecretIdentifiers` inconsistency where secrets exist but are not enumerable under the case variant used for listing, which could be leveraged to hide/orphan secrets from cleanup or auditing tooling that relies on List to drive Delete.

### Likelihood Explanation
The precondition is simply that an attacker already possesses a valid JWT (or allow-listed identity) for their own owner — no privilege escalation against another tenant's owner boundary is required, since `NormalizeOwner` correctly stops access to a *different* owner. The bug is a self-inflicted-but-attacker-controlled partitioning inconsistency: the attacker only needs to vary the case of the `Owner` field they submit in `SecretIdentifier`/`ListSecretIdentifiersRequest`, which is entirely under their control in every gateway-routed request. This is trivially reproducible without any race condition or timing dependency.

### Recommendation
Canonicalize `SecretIdentifier.Owner` (and any owner field used for KVStore keys / metadata keys) to a single canonical form (e.g., lowercase, no `0x` prefix, matching `vaultutils.NormalizeOwner`) at the earliest ingress point — ideally in `GatewayVaultRequestProcessor` param stamping before it reaches the OCR plugin/KVStore — so that `vaulttypes.KeyFor` and `metadataPrefix+owner` always operate on a normalized string identical to what `NormalizeOwner`-based authorization checks use. The comment in `vaultutils/owner.go` — referencing a planned "VaultOwnerAddressCanonicalizationEnabled" ingress-level fix — indicates the maintainers are aware this is needed but not yet done.

### Proof of Concept
Integration test in `core/services/ocr2/plugins/vault`:
1. Build a `ReportingPlugin` with a `WriteKVStore` backed by an in-memory `kv`.
2. Issue `CreateSecrets` for `SecretIdentifier{Owner: "0xAb5801a7D398351b8bE11C439e05C5B3259aeC9B", Namespace:"main", Key:"k"}` with a ciphertext correctly labeled for that address (`EncryptSecretWithWorkflowOwner`), running it through `Observation`+`StateTransition` to commit via `WriteSecret`.
3. Issue a second `CreateSecrets` for the same logical owner but `Owner: "0xab5801a7d398351b8be11c439e05c5b3259aec9b"` (lowercase) and the same `Namespace`/`Key`, with ciphertext re-encrypted for the lowercase-parsed address (still passes `EnsureRightLabelOnSecret` since `HexToAddress` is case-insensitive).
4. Assert: (a) the second create succeeds without a "key already exists" error (violating uniqueness for what should be identical secret), and (b) `store.GetMetadata(ctx, checksumOwner)` and `store.GetMetadata(ctx, lowercaseOwner)` return two disjoint `StoredMetadata` lists, proving the same authorized identity now has two independent, non-overlapping partitions rather than one canonical row — matching the invariant violation described (no single canonical row; duplicate/orphaned rows exist).

func validateEncryptedSecretOwnerMismatch(encryptedSecrets []*vaultcommon.EncryptedSecret, workflowOwner string) error {
	if len(encryptedSecrets) == 0 {
		return errors.New("request batch must contain at least 1 item")
	}
	for idx, encryptedSecret := range encryptedSecrets {
		if encryptedSecret == nil {
			return fmt.Errorf("encrypted secret must not be nil at index %d", idx)
		}
		if encryptedSecret.Id == nil {
			return fmt.Errorf("secret ID must not be nil at index %d", idx)
		}
		if vaultutils.NormalizeOwner(encryptedSecret.Id.Owner) != vaultutils.NormalizeOwner(workflowOwner) {
			return fmt.Errorf("encrypted secret owner at index %d %q does not match authorized workflow owner %q", idx, encryptedSecret.Id.Owner, workflowOwner)
		}
	}
	return nil
}

func DeriveJWTAuthorizedVaultWorkflowOwner(orgID string, tenantID uint64, claimedWorkflowOwnerFromJWT string) (string, error) {
	if orgID == "" {
		return "", errors.New("org_id is required for JWT-derived vault workflow owner")
	}
	if tenantID == 0 {
		return "", ErrMissingTenantID
	}
	prefix := strconv.FormatUint(tenantID, 10)
	addr, err := workflows.GenerateWorkflowOwnerAddress(prefix, orgID)
	if err != nil {
		return "", fmt.Errorf("could not derive vault workflow owner address: %w", err)
	}
	derived := common.BytesToAddress(addr).Hex()
	if claimedWorkflowOwnerFromJWT != "" && !strings.EqualFold(strings.TrimSpace(claimedWorkflowOwnerFromJWT), derived) {
		return "", fmt.Errorf("JWT workflow_owner claim %q does not match derived workflow owner %q", claimedWorkflowOwnerFromJWT, derived)
	}
	return derived, nil
}

// EnsureRightLabelOnSecret verifies that the TDH2 ciphertext label matches the workflow
// owner label (Ethereum address, left-padded to 32 bytes). owner must be non-empty;
// when the public key is nil, verification is skipped for the same reasons as
// verifyEncryptedSecret.
func EnsureRightLabelOnSecret(publicKey *tdh2easy.PublicKey, secret string, owner string) error {
	cipherText, err := verifyEncryptedSecret(publicKey, secret)
	if err != nil {
		return err
	}
	if cipherText == nil {
		return nil
	}
	if owner == "" {
		return errors.New("owner must not be empty for secret label verification")
	}

	expected := vaultutils.WorkflowOwnerToLabel(owner)
	secretLabel := cipherText.Label()
	if secretLabel == expected {
		return nil
	}

	return fmt.Errorf("secret label [%s] does not match workflow owner label [%s]",
		hex.EncodeToString(secretLabel[:]), hex.EncodeToString(expected[:]))
}
