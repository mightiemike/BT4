No `.sol` source is present in this repo (the `UniversalCore`/PRC20 Solidity contracts are likely external or bytecode-only), so I cannot confirm cap enforcement lives there. Based on everything reachable in the Go keeper code, here is the analog finding.

### Title
`TokenConfig.LiquidityCap` is stored and validated but never enforced when minting PRC20 on inbound deposits - (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/evm.go`)

### Summary
This is the direct analog of the `investFIAT`/`maxRaiseWei` bug: a configured cap (`LiquidityCap`) exists on the `TokenConfig` record, is required to be non-empty at registration time, but is never read or compared against cumulative/attempted mint amounts anywhere in the Go-side deposit path before PRC20 tokens are minted to a user's UEA.

### Finding Description
`TokenConfig.LiquidityCap` is documented as "max supply cap for this token" [1](#0-0) , and `ValidateBasic` requires it to be non-empty when a token is registered [2](#0-1) . However, the deposit path that actually mints PRC20 tokens into a recipient's UEA — `depositPRC20` — only fetches the token config to resolve the native PRC20 contract address, converts the string amount, and calls `CallPRC20Deposit`; it never calls `GetLiquidityCap()` or compares the deposit amount (or any running total) against it [3](#0-2) . `CallPRC20Deposit` and `CallPRC20DepositAutoSwap` likewise just forward `amount` straight into the `DerivedEVMCall` to the handler contract with no cap check [4](#0-3) [5](#0-4) . This flow is reachable by any unprivileged user: `ExecuteInboundFunds` invokes `depositPRC20` for every finalized inbound (`FUNDS`, `FUNDS_AND_PAYLOAD`, `GAS_AND_PAYLOAD`, CEA) after honest-validator ballot consensus, with the `Amount` field taken directly from the attacker-observed/attacker-controlled source-chain deposit [6](#0-5) . No repo-visible code path (Go keeper, ante handler, or precompile) reads `LiquidityCap` to gate minting; the only other consumers of the field are protobuf marshal/unmarshal code and unit tests of `ValidateBasic` [7](#0-6) .

I could not locate any Solidity source for the `UniversalCore`/handler contract (`depositPRC20Token`, `depositPRC20WithAutoSwap`) in this repository — those call targets appear to be deployed bytecode outside the indexed source tree, so I cannot rule out that the cap is enforced inside the EVM contract itself. This is a real gap in my verification, not a confirmed vulnerability.

### Impact Explanation
If the on-chain handler contract does not itself enforce `LiquidityCap` (unverifiable from this repo), an unprivileged user can repeatedly submit real (honestly-observed) inbound deposits from an external chain and have the Go-side keeper mint unlimited PRC20 into their UEA with no supply ceiling, corrupting the PRC20/native asset accounting invariant the `LiquidityCap` field is meant to protect (unauthorized mint beyond the registered cap). If the contract does enforce it internally, the Go-side gap is only a defense-in-depth/observability issue, not an exploitable one.

### Likelihood Explanation
Medium-to-unknown: the trigger requires no privileged role — any user depositing on a supported source chain drives this path once validators reach honest consensus on the inbound. Likelihood of actual exploitability is uncertain because the enforcement point in the target contract could not be verified from this repository's source (no `.sol` files were indexed).

### Recommendation
Add an explicit `LiquidityCap` check in `depositPRC20` (or before calling `CallPRC20Deposit`/`CallPRC20DepositAutoSwap`), comparing the token's current on-chain total supply (or a tracked running total) plus the incoming `amount` against `tokenConfig.GetLiquidityCap()`, rejecting/reverting the deposit (and routing to the existing revert/refund flow) if the cap would be exceeded — mirroring the suggested `require(raisedWei <= maxRaiseWei)` fix from the original report. Confirm independently whether the deployed `UniversalCore`/PRC20 handler contract already performs this check on-chain; if so, this Go-side gap is lower priority but should still be closed for defense-in-depth and consistent failure handling.

### Proof of Concept
Not verifiable end-to-end from this repository alone: a full PoC would require the deployed handler/PRC20 contract bytecode or source (not present in the indexed repo) to confirm whether `depositPRC20Token`/`depositPRC20WithAutoSwap` enforce a supply cap internally. On the Go side, the PoC steps are: (1) register a `TokenConfig` with a small `LiquidityCap`; (2) submit multiple honestly-voted `Inbound` (`FUNDS`/`FUNDS_AND_PAYLOAD`) events whose cumulative `Amount` exceeds that cap; (3) observe that `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` succeeds unconditionally with `PcTx.Status == "SUCCESS"` regardless of the configured cap, as seen in the existing integration test pattern [8](#0-7) .

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
