## Finding

### Title
Batch-proof method-id upgrade signatures never expire and are not bound to the state they were authorised against, allowing a stale, superseded security-council authorisation to be activated later than intended - (File: `crates/light-client-prover/src/circuit/mod.rs`)

### Summary
A `BatchProofMethodId` DA transaction is accepted by the light-client circuit purely if (a) its `activation_l2_height` is strictly greater than whatever the *currently stored* last activation height happens to be at processing time, (b) the `chain_id` matches, and (c) 3-of-5 security-council signatures over the serialized body verify. The signed body carries no timestamp, deadline, nonce, or reference to the `last_activation_height`/chain state that existed when it was signed. Consequently, a validly-signed method-id upgrade message never expires: it stays perpetually replayable on Bitcoin DA and will be accepted by every honest light-client prover as long as its `activation_l2_height` is numerically above whatever the current tip is when it is finally inscribed - even if the council later issued a superseding, higher-`activation_l2_height` upgrade that was meant to supersede/invalidate it.

### Finding Description
The light-client circuit's method-id handling is: [1](#0-0) 

and the signed payload structure is: [2](#0-1) 

The only freshness/ordering check is `batch_proof_method_id.body.activation_l2_height <= last_activation_height` against the *current* on-chain last activation height, not against the height that existed when the security council actually produced the signature. Signature verification itself checks only that indices are ascending/in-bounds and that the ECDSA signatures are valid over the fixed body bytes — there is no expiry field, no binding nonce, and no reference to a "previous activation height at signing time": [3](#0-2) 

This is the same bug class as the referenced report: an authorization ("proposal") produced by a privileged party has no expiration and can therefore be executed/activated far later than intended, once circumstances (i.e., what the "current" chain state actually is) have changed. Anyone who has ever seen a validly-signed `BatchProofMethodIdBody` (e.g., leaked, cached, or an earlier draft the council decided to supersede with a newer, higher-height fix) can inscribe it onto Bitcoin DA at any later point — inscribing a DA transaction requires no special role or key, only that the *embedded* signatures verify, which they always will since ECDSA signatures don't expire. The comment in the code even acknowledges signatures are only meant to defend against *replay of already-applied* IDs ("This prevents replay attacks of old method IDs"), but this only blocks replay of activation heights that have already been superseded — it does nothing to stop a stale-but-not-yet-superseded signed body (with a still-higher activation height than whatever is currently applied) from being surfaced and activated long after the council intended it to be dropped.

### Impact Explanation
If the security council ever signs a method-id body and does not use it (e.g., a fix is found before publication, or the message was drafted with a generous future `activation_l2_height` and superseded by a different, still-higher-height upgrade), that old signed body remains forever valid to insert as long as its `activation_l2_height` exceeds the applied height at the moment of inscription. This breaks the binding "accepted method-id upgrade == what the key holders currently authorise" — the light client will apply a `method_id` the council no longer intends to use. Because `BatchProofMethodIdAccessor` entries are looked up per L2 height range via `binary_search_by_key` to select which `method_id` verifies a given batch proof, a stale/superseded method id becoming active changes which RISC0 circuit governs proof verification for that range: `crates/light-client-prover/src/circuit/mod.rs:288-312`. If the resurfaced method id corresponds to a circuit later found to be flawed (which is plausibly *why* it was superseded), this permits a false state transition to be proved and accepted, i.e., a Critical-class impact (false state transition proved).

### Likelihood Explanation
No key compromise is needed to exploit this — only possession of a previously validly-signed `BatchProofMethodId` message (which is inherently semi-public: it's meant to be broadcast to Bitcoin, so intermediate signed-but-unpublished versions are exposed to anyone with access to the coordination channel used by the council, or even simply not yet inscribed but already shared for review). The attack surface is "resubmit old but still-technically-valid data," which is a very low bar once such a message exists, and the security council process (signing multiple candidate upgrades over time, superseding earlier ones) makes creation of such stale-but-valid messages a normal operational occurrence rather than a rare edge case.

### Recommendation
Bind the signed `BatchProofMethodIdBody` to the exact state it was authorised against and/or add an expiry: include the `last_activation_height` (or previous method id) the signers observed at signing time as part of the signed message, and reject the upgrade unless it matches the currently stored last activation height exactly (rather than merely being numerically greater). Alternatively/additionally, add a signing timestamp or L1/L2 height deadline field to `BatchProofMethodIdBody` and reject method-id upgrades whose deadline has passed.

### Proof of Concept
1. Security council signs `BatchProofMethodIdBody { method_id: X, activation_l2_height: 500, chain_id }` (call it A) intending to deploy it soon after the current tip (say last activation height is 100).
2. Before A is inscribed, the council finds an issue and instead signs and inscribes `BatchProofMethodIdBody { method_id: Y, activation_l2_height: 300, chain_id }` (call it B), which is accepted since `300 > 100` — new last activation height is 300.
3. A is never revoked on-chain (no revocation mechanism exists) and remains a validly-signed message with `activation_l2_height: 500 > 300`.
4. Anyone in possession of A (e.g., obtained from the council's internal coordination before it was scrapped) inscribes it on Bitcoin DA at an arbitrary later time. The circuit check `crates/light-client-prover/src/circuit/mod.rs:539` only compares `500 <= 300` → false, so A is accepted, silently reverting/overriding the intended method id Y with the stale X for all future L2 heights ≥ 500, exactly as the council did not want.
