### Title
Global TotalNetWeight/TotalEnergyWeight desynchronization via TVM `freezeBalance` precompile allows resource-limit manipulation - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java])

### Summary
The Big Bang bug class (a secondary code path fails to trigger the reconciliation step that keeps a globally-shared accounting variable in sync with per-user state, letting an attacker manipulate a system-wide rate) has a structural analog in java-tron's TVM native `freezeBalance` precompile. `FreezeBalanceProcessor.execute()` (the TVM/smart-contract entry point for the legacy freeze model) updates the global `TotalNetWeight`/`TotalEnergyWeight` counters using the raw per-call `frozenBalance / TRX_PRECISION`, instead of the incremental delta computed from the account's *accumulated* frozen balance the way the non-TVM `FreezeBalanceActuator.execute()` does.

### Finding Description
`FreezeBalanceActuator.execute()` (the standard, non-TVM transaction path) computes weight increments correctly by taking the floor-divided *before* and *after* total frozen balance and adding only the delta: [1](#0-0) [2](#0-1) 

This ensures that `floor(total/TRX_PRECISION)` is computed once against the cumulative balance, so repeated small freezes (each below the 1 TRX rounding boundary) still sum correctly to the true floor of the total.

By contrast, `FreezeBalanceProcessor.execute()` — reached only via the TVM `freezeBalance` native/precompiled call from a smart contract — unconditionally adds `frozenBalance / TRX_PRECISION` for *each individual call*, without ever comparing to the account's previous accumulated frozen balance: [3](#0-2) 

Meanwhile, the account's own recorded frozen balance is accumulated correctly and in full (`frozenBalance + accountCapsule.getFrozenBalance()`): [4](#0-3) 

Because a user's personal weight used at consumption time is derived from `floor(fullAccumulatedFrozenBalance / TRX_PRECISION)`: [5](#0-4) 

An attacker who freezes via a smart contract in a sequence of small sub-precision-rounding increments (e.g., 1.5 TRX at a time) can end up with a personal weight (`floor(total/precision)`) that is strictly larger than the sum of weights it actually contributed to the shared `TotalEnergyWeight`/`TotalNetWeight` denominators, because each call's own floor-division loses fractional remainder independently instead of against the cumulative running total. This is directly analogous to the Tapioca root cause: a secondary/alternate transaction path (leverage executor / TVM precompile) does not correctly reconcile with the shared accounting state (`reAccrueBigBangMarkets` / `TotalEnergyWeight`) that a global rate/limit formula (`interest rate` / `calculateGlobalEnergyLimit`) depends on.

### Impact Explanation
`calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` divide each account's own weight by the network-wide `TotalEnergyWeight`/`TotalNetWeight` to derive the account's share of the fixed `TotalEnergyCurrentLimit`/`TotalNetLimit`: [5](#0-4) 
If the attacker's own weight (computed from the fully accumulated frozen balance) systematically exceeds what it contributed to the global denominator, the attacker obtains a disproportionately larger personal energy/bandwidth limit relative to their real stake, while every other frozen account on the network receives a smaller effective share of the fixed global limit than they should, since the total limit is shared across an under-counted denominator relative to real aggregate weight. This is a resource-accounting/economic-fairness corruption reachable by any account through a broadcast smart-contract transaction invoking the freeze precompile, with no privileged role required.

### Likelihood Explanation
The bug requires only deploying/using a smart contract that repeatedly calls the `freezeBalance` TVM precompile with small amounts (each ≥ 1 TRX minimum per `validate()`, but chosen so cumulative totals cross rounding boundaries differently than a single freeze would). This is fully reachable by any unprivileged account issuing ordinary contract-call transactions; no special permissions or race conditions are needed, only patience in issuing multiple sequential freeze calls.

### Recommendation
Modify `FreezeBalanceProcessor.execute()` to compute the total-weight delta the same way `FreezeBalanceActuator` and `FreezeBalanceV2Processor` do: capture `oldWeight = floor(accountCapsule.getFrozenBalance()/TRX_PRECISION)` (or the energy-frozen equivalent) before mutating the account, apply the mutation, then compute `newWeight = floor(newTotal/TRX_PRECISION)` and add only `newWeight - oldWeight` to `repo.addTotalNetWeight`/`repo.addTotalEnergyWeight`, instead of blindly adding `frozenBalance / TRX_PRECISION` per call.

### Proof of Concept
Conceptual sequence (exact reachability of the legacy `freezeBalance` TVM opcode/precompile in the currently active hard-fork configuration was not independently verified from the index; this assumes the path in `FreezeBalanceProcessor` remains live for contracts under the applicable resource-model flags):
1. Deploy a contract, call the `freezeBalance` TVM entry point with `frozenBalance = 1_500_000` sun (1.5 TRX) for ENERGY. `FreezeBalanceProcessor.execute()` sets the account's frozen-for-energy balance to `1_500_000`, and adds `1_500_000 / 1_000_000 = 1` to `TotalEnergyWeight`.
2. Call `freezeBalance` again with another `1_500_000` sun. The account's frozen-for-energy balance becomes `3_000_000` (accumulated correctly), but `TotalEnergyWeight` only receives another `+1` (total `+2`), whereas `floor(3_000_000/1_000_000) = 3` is the "correct" delta that the non-TVM `FreezeBalanceActuator` would have added.
3. At resource-consumption time, `calculateGlobalEnergyLimitV2`/`calculateGlobalEnergyLimit` computes the attacker's own weight as `floor(3_000_000/1_000_000) = 3`, using this larger numerator against the smaller, under-incremented global `TotalEnergyWeight` denominator — granting the attacker a larger proportional share of `TotalEnergyCurrentLimit` than the amount it contributed to the shared total, at the expense of the rest of the network's fair share.

  private void addTotalWeight(ResourceCode resourceCode, DynamicPropertiesStore dynamicStore,
                              long frozenBalance, long increment) {
    long weight = dynamicStore.allowNewReward() ? increment : frozenBalance / TRX_PRECISION;
    switch (resourceCode) {
      case BANDWIDTH:
        dynamicStore.addTotalNetWeight(weight);
        break;
      case ENERGY:
        dynamicStore.addTotalEnergyWeight(weight);
        break;
      case TRON_POWER:
        dynamicStore.addTotalTronPowerWeight(weight);
        break;
      default:
        logger.debug("Resource Code Error.");
    }
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
