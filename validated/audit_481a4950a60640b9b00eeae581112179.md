### Title
Missing zero-result validation in maker/taker exact-match branch of order matching leads to asset loss - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder()` computes cross-multiplied quantities via `MarketUtils.multiplyAndDivide()`, which — like the reported Adrastia Oracle `aggregateUnderlying()` division — can floor-divide to `0` when the numerator is much smaller than the denominator. Two of the three branches in `matchSingleOrder` explicitly check for and handle a `0` result, but the "taker == maker" (exact match) branch does not, letting a maker order be fully closed out (`sellTokenQuantityRemain = 0`, state `INACTIVE`) while receiving `0` tokens in return.

### Finding Description
`matchSingleOrder` first computes: [1](#0-0) 
which is checked for `== 0` and safely handled by returning the sell token to the taker.

In the "taker > maker" branch, the analogous quantity `makerBuyTokenQuantityReceive` is also explicitly checked against `0`, and if so, the sell-token remainder is returned to the maker instead of silently closing the order: [2](#0-1) 

However, in the "taker == maker" branch, the same computation `makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)` has no such check: [3](#0-2) 

`multiplyAndDivide` performs an integer floor division that truncates to `0` whenever `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`: [4](#0-3) 

`validate()` only bounds each side's absolute quantity via `getMarketQuantityLimit()`; it never enforces a minimum price ratio between maker and taker orders, so a taker can construct a sell/buy quantity pair whose price ratio against a resting maker order drives this specific term to zero: [5](#0-4) 

When this happens, `makerOrderCapsule.setSellTokenQuantityRemain(0)` and the order is marked `INACTIVE` (fully filled), but `addTrxOrToken(makerOrderCapsule, 0)` credits the maker with nothing — the maker's remaining sell-side balance is effectively destroyed with no compensation, since it was already deducted from their account at order-creation time via `transferBalanceOrToken`.

### Impact Explanation
This is reachable by any account broadcasting a `MarketSellAssetContract` transaction (TRON's on-chain decentralized exchange), requiring no special privileges. It results in silent asset/accounting corruption: a maker's escrowed tokens are consumed by the DEX matching engine without any corresponding payout, and the resulting order-book state (`INACTIVE`, remain = 0) hides the loss instead of surfacing an error, mirroring the "invalid data passes validation but corrupts the resulting balance" risk described in the source report.

### Likelihood Explanation
An attacker controls both the taker order parameters (`sellTokenQuantity`/`buyTokenQuantity`) and can time it against small, low-priced resting maker orders in the book, or can even place both the maker and taker orders (across two of their own accounts, or targeting a legitimate small maker order) to trigger the exact-match branch with a degenerate ratio. No node-privilege or key compromise is needed — only crafting quantities that satisfy the exact-match condition (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`) with a ratio small enough that `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity` floors to zero.

### Recommendation
Add the same `makerBuyTokenQuantityReceive == 0` guard used in the "taker > maker" branch to the "taker == maker" branch, returning the maker's remaining sell tokens instead of closing the order with zero compensation. Additionally, consider enforcing a minimum price/quantity ratio at `validate()` time to prevent degenerate divisions across all matching branches, consistent with the general principle (from the source report) that all consumers of a division result must independently validate it can't silently truncate to zero.

### Proof of Concept
1. Place a maker sell order: sell `100` of token A for `1` of token B (`makerSellQuantity=100`, `makerBuyQuantity=1`), leaving `makerSellRemainQuantity=100`.
2. As taker, submit a `MarketSellAssetContract` selling token B for token A such that `takerBuyTokenQuantityRemain` (computed from taker's own sell/buy quantities against the maker price) equals exactly `100` (the maker's remaining sell quantity), landing in the "taker == maker" branch.
3. Inside that branch, `makerBuyTokenQuantityReceive = multiplyAndDivide(100, 1, 100) = 1` in this simple example — but by choosing a smaller `makerBuyQuantity` relative to `makerSellQuantity` at a scale where `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity` (e.g. `makerSellQuantity` much larger than `makerBuyQuantity` and a small remaining quantity), the division floors to `0`.
4. The maker order is marked `INACTIVE`/fully consumed and `addTrxOrToken(makerOrderCapsule, 0)` is called, permanently losing the maker's escrowed token A with zero token B received in return.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
