### Title
Receipt-size limit is enforced before mutation, allowing receipts to exceed `max_receipt_size` after validation - ([File: runtime/runtime/src/verifier.rs])

### Summary
`validate_receipt` in `ValidateReceiptMode::NewReceipt` checks a receipt's serialized size against `limit_config.max_receipt_size` at creation time [1](#0-0) . However, fields such as `output_data_receivers` can be appended to an already-validated receipt afterward (e.g. via `promise_return` in a promise DAG), pushing its serialized size above `max_receipt_size` post-validation, while the runtime continues to process and persist the oversized receipt into state/witness data. This is the same bug class as the reported Ethereum CL issue "Previous epoch attestation list limit overflow": a size/count bound is checked at one point in the pipeline but the underlying list/collection is mutated afterward, so the actual persisted object silently exceeds the protocol-mandated limit.

### Finding Description
`validate_receipt`/`validate_action_receipt` bound the size of a *newly created* receipt using `ValidateReceiptMode::NewReceipt` [2](#0-1) . The codebase itself documents that this check can be bypassed: `ValidateReceiptMode::ExistingReceipt` exists specifically "because... there is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed" (referencing near/nearcore#12606) [3](#0-2) .

The concrete mechanism is exercised by tests: a function call creates a receipt whose size is validated against `max_receipt_size` (4 MiB) at creation, but the receipt is later mutated — `output_data_receivers` is appended when a subsequent promise resolves — growing the receipt beyond `max_receipt_size` after the validation checkpoint has already passed [4](#0-3) . A second variant shows the same overflow via a returned value being wrapped into a data receipt that also exceeds the limit [5](#0-4) . Both tests are explicit that "the receipt should be rejected, but currently isn't because of a bug".

Because `max_receipt_size` is one of the load-bearing invariants used to bound `ChunkStateWitness` size (target ≤ 21 MiB uncompressed) [6](#0-5) , and because the receipt-size field feeds directly into congestion accounting (`compute_receipt_size`/`receipt_size`, which is part of the protocol and used for buffer/queue byte accounting) [7](#0-6) , an oversized receipt slipping past the "hard limit" undermines both the witness-size budget and the congestion/bandwidth accounting that assumes `max_receipt_size` is actually enforced.

### Impact Explanation
An unprivileged account can trigger this purely through a deployed contract call by chaining promises so that a callback appends `output_data_receivers`, or by returning an oversized value that gets wrapped into a data receipt after the size check. The result is a receipt exceeding `max_receipt_size` being propagated through the delayed/incoming receipt queues, counted in state witnesses, and byte-accounted for congestion control — feeding a value into system components that assume the invariant `size ≤ max_receipt_size` holds. This can inflate `ChunkStateWitness` beyond its intended budget, and since congestion/bandwidth accounting uses `receipt_size` for bytes-tracking limits (`removed_delayed_bytes`, buffered-receipt byte limits), an unenforced oversized receipt undermines the correctness of those size-based limits used to bound cross-shard state.

### Likelihood Explanation
The bug is already known and reproduced by first-party regression tests in this repo (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`), demonstrating it is reliably triggerable by a normal RPC caller deploying and invoking an ordinary contract — no privileged access, validator role, or network-level manipulation is required [8](#0-7) .

### Recommendation
Re-validate receipt size (in `NewReceipt` mode, or an equivalent "final" mode) after all mutations to `output_data_receivers`/returned-data wrapping are complete, immediately before the receipt is persisted/queued, rather than only at the initial creation point in `action_function_call`/`receipt_manager.rs`. Alternatively, cap the growth from `promise_return`/data-receipt wrapping so the post-mutation size provably cannot exceed `max_receipt_size`, closing the gap that currently requires `ValidateReceiptMode::ExistingReceipt` to "tolerate" oversized receipts.

### Proof of Concept
Use the existing regression tests as the PoC outline:
1. Deploy `near_test_contracts::rs_contract()`.
2. Call `max_receipt_size_promise_return_method1` with `args_size` computed so that the intermediate promise-C receipt is exactly at `max_receipt_size`, then let its `output_data_receivers` be populated by the chained promise — see `test_max_receipt_size_promise_return` [9](#0-8) .
3. Observe via `assert_oversized_receipt_occurred` that a receipt above `max_receipt_size` is present in incoming-receipt proofs on chain, confirming the size limit was not enforced post-mutation [10](#0-9) .

```rust
                size: receipt_size,
                limit: limit_config.max_receipt_size,
```

```rust
/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
```

```markdown
Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 21MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.

The limits are:

* `max_transaction_size = 1.5 MiB`
  * All transactions must be below 1.5 MiB, otherwise they'll be considered invalid and rejected.
  * Previously was 4MiB, now reduced to 1.5MiB
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
```
