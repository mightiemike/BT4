### Title
Zero-Cost Liquidity Manipulation of TRON's On-Chain Bancor-Style Exchange Distorts Trade Pricing - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The Aloe bug is about an attacker instantly injecting and withdrawing pool liquidity at zero cost to distort a price/volatility metric that other logic (LTV) depends on. `java-tron` has an analogous on-chain AMM primitive — the native `Exchange` (Bancor-style relay token market) — whose reserve balances directly set the trade rate computed in `ExchangeCapsule.transaction()`/`ExchangeProcessor.exchange()`. `ExchangeInjectActuator` and `ExchangeWithdrawActuator` both charge `calcFee() == 0` [1](#0-0)  and impose no minimum holding time or time-weighting between inject/withdraw, letting the exchange creator instantaneously distort reserves for free around a victim's trade.

### Finding Description
`ExchangeInjectActuator.execute` lets a caller add tokens to an exchange's reserves, recomputing `firstTokenBalance`/`secondTokenBalance` immediately with no fee (`calcFee()` returns 0 in the sibling actuator and no fee-based cost gates the reserve mutation) [2](#0-1) . These reserves are the exact inputs to the constant-relay/Bancor pricing formula used for every trade: `ExchangeCapsule.transaction()` reads `firstTokenBalance`/`secondTokenBalance` and calls `ExchangeProcessor.exchange()` (or `SafeExchangeProcessor`) to compute the swap output [3](#0-2) [4](#0-3) .

`ExchangeWithdrawActuator` symmetrically removes reserves, restricted only to the exchange's original creator (`account[...] is not creator`), but again with `calcFee() == 0` [5](#0-4) [1](#0-0) . Since exchange creation itself is permissionless (any normal, unprivileged account can call `ExchangeCreateActuator`), the "creator-only" restriction on withdraw does not make this a privileged-role scenario — it simply means an attacker plays both the role of pool creator and manipulator of their own market, which any user can trade against via `ExchangeTransactionActuator`.

There is no time-weighted reserve tracking, no minimum liquidity duration, and no block-delay requirement between `Inject` and `Withdraw`. This mirrors the root cause in the Aloe report: a party can add large one-block liquidity, cause pricing based on that liquidity to be computed, then withdraw it — all at negligible cost (bandwidth/energy only, since `calcFee()` is 0) — and the same imbalance directly drives the price a counterparty receives from `ExchangeTransactionActuator`.

### Impact Explanation
An attacker who creates (or already controls) an `Exchange` pair can:
1. `ExchangeInject` a large, disproportionate amount into one side of the reserve to shift the Bancor-style rate in their favor.
2. Induce or wait for a victim's `ExchangeTransactionActuator` trade to execute against the manipulated reserve, extracting value at a distorted rate.
3. `ExchangeWithdraw` the injected liquidity back out, restoring the pool, at zero protocol fee (`calcFee()==0` for both operations).

This constitutes a free (aside from bandwidth/energy) sandwich/rate-manipulation attack against any counterparty trading through the exchange, directly affecting settlement/accounting correctness of trades executed via the on-chain market feature — a concrete underpriced/mispriced-settlement impact, not merely a UX or best-practice issue.

### Likelihood Explanation
The attack requires only standard, unprivileged account actions available to any TRON user (`ExchangeCreate`, `ExchangeInject`, `ExchangeWithdraw`, `ExchangeTransaction`) and costs nothing but ordinary transaction fees, so it is fully reachable by any external, non-privileged actor. Its likelihood is tempered by two factors I could not fully verify in this pass: (1) whether TRON's block-production/mempool model gives an attacker reliable transaction-ordering control analogous to Ethereum MEV/sandwiching (needed to guarantee the victim trade lands between inject and withdraw), and (2) current real-world usage/liquidity of the legacy TRX `Exchange` feature, which affects how attractive this is versus third-party DEXes. These require further investigation before assigning a precise severity.

### Recommendation
- Introduce a non-zero fee and/or a minimum holding period (analogous to a cooldown) between `ExchangeInject`/`ExchangeWithdraw` operations on the same exchange to prevent same-block or near-instant reserve manipulation.
- Consider time-weighting reserve balances used in `ExchangeCapsule.transaction()` pricing rather than using the instantaneous post-inject/withdraw balances.
- Audit whether `ExchangeTransactionActuator`'s `expected` slippage parameter provides sufficient protection against this class of manipulation, and if not, add explicit protections (e.g., disallow inject/withdraw and transaction from being included in the same block, or apply a decay-based reserve snapshot).

### Proof of Concept
Conceptual sequence (requires further live-network/mempool-ordering confirmation):
1. Attacker calls `ExchangeCreateActuator` to create `Exchange(TRX, TOKEN)` with modest initial reserves.
2. Attacker calls `ExchangeInjectActuator` with a large TRX amount to skew `firstTokenBalance`/`secondTokenBalance` [6](#0-5) , paying no fee since `calcFee()` returns `0`.
3. A victim calls `ExchangeTransactionActuator`, whose payout is computed directly from the current, attacker-skewed reserves via `ExchangeCapsule.transaction()` [7](#0-6) .
4. Attacker calls `ExchangeWithdrawActuator` (permitted because attacker is the creator) to pull the injected liquidity back out at zero fee [8](#0-7) , restoring the original reserve ratio while having profited from the victim's mispriced trade.

**Caveat**: I could not confirm in this pass whether transaction ordering within a single block/producer window can be reliably controlled by an attacker on `java-tron`, which is necessary to fully weaponize step 3 against an arbitrary victim rather than against the attacker's own follow-up trade. This should be validated (e.g., by examining block-production/mempool ordering code) before treating this as a fully proven, high-severity finding.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
