### Title
`liquidate-multi` batch DoS: an `unwrap-panic` inside a single position's `liquidate` call aborts the entire batch, defeating the documented "isolated failure" guarantee - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` is explicitly documented as processing each position independently, returning ok/err per entry without reverting the rest of the batch: `;; Failed liquidations return error codes but don't revert entire batch` [1](#0-0) . It implements this via `(ok (map call-liquidate positions))`, where `call-liquidate` invokes the public `liquidate` function directly (not via `contract-call?`) for each position [2](#0-1) . This pattern only holds if every failure path inside `liquidate` resolves to a controlled `(err ...)` response. However, `liquidate` contains `unwrap-panic` calls on `get-cached-indexes`, e.g. at the "remaining debt" and "other debt repayable" calculations [3](#0-2)  and [4](#0-3) , and on the bad-debt list append at line 1540 [5](#0-4) . A Clarity `unwrap-panic` on `none` triggers a runtime abort of the whole transaction, not a graceful error returned up the call stack like `asserts!`/`try!` do. Since all positions in `liquidate-multi` execute within one transaction, any single position that reaches an `unwrap-panic` path with a `none` value silently reverts every other (otherwise successful) liquidation in the same call - exactly analogous to the EigenLayer report where one bad strategy inside a multi-strategy withdrawal DoSes the whole withdrawal.

### Finding Description
The batch entry point `liquidate-multi` is designed so that a bad/malicious position cannot block the liquidation of other, unrelated positions in the same call — this is stated directly in the code comment and is the documented security property of the function [6](#0-5) .

The mechanism relies on each call to `liquidate` returning a `(response {...} uint)` value that `map` simply collects, so an individual `err` doesn't propagate a revert to the enclosing `map`/`ok`. This holds for every `asserts!`/`try!` failure inside `liquidate`, because those short-circuit only the *current* function's execution and produce a typed `err`, which `map` happily aggregates.

It does **not** hold for `unwrap-panic`. Multiple points inside `liquidate` use `unwrap-panic (get-cached-indexes debt-aid)` to fetch the just-cached borrow index for the debt asset being processed [3](#0-2) , [4](#0-3) . `get-cached-indexes` reads `index-cache` keyed by `{ timestamp: stacks-block-time, aid }` [7](#0-6) . This value is populated earlier in `liquidate` via `accrue-user-debts`/`accrue-user-collateral` over the borrower's own debt/collateral list [8](#0-7) . If, for a particular position in the batch, the cache for that specific `debt-aid`/timestamp combination is not populated at the moment the `unwrap-panic` branch is reached — for example because the "no collateral left" / "other-debt-repayable" branch is reached for a debt asset whose cache entry was evicted, mismatched, or simply not written for that exact `aid` under some edge-case ordering of collateral/debt lists — the call panics instead of returning `ERR-*`. Similarly, the bad-debt append at line 1540 uses `unwrap-panic (as-max-len? ... u64)`, which panics rather than erroring if the max-length invariant is violated by list composition for that borrower.

Because `liquidate-multi` batches up to 64 arbitrary borrower/asset combinations supplied by the caller (or, in a griefing scenario, chosen adversarially by anyone who front-runs a liquidator's batch by structuring their own unhealthy position to hit one of these panic paths), a single crafted or edge-case position anywhere in the list is enough to unwind the entire transaction — including all the legitimately profitable, otherwise-successful liquidations that were bundled with it. This is the same class of bug as the referenced report: a multi-item entry point (`queueWithdrawal`/`completeQueuedWithdrawal` there, `liquidate-multi` here) that folds/maps over several independent sub-operations, one of which can hard-fail in a way the code did not anticipate, wiping out the state changes for all the others in the same atomic call.

### Impact Explanation
This lands on **temporary freezing of funds**: while the panic is live for a given borrower/asset combination, liquidators cannot batch that position with any other position without risking the whole batch reverting, delaying liquidation of genuinely unhealthy positions (protocol insolvency risk grows the longer liquidation is delayed) and wasting liquidator gas repeatedly. It does not directly steal funds, but it denies the liquidation functionality "even if temporarily," which the original report's judge treated as Medium severity for the identical mechanism (multi-item batch, one bad item blocks all).

### Likelihood Explanation
Likelihood depends on how reachable the `unwrap-panic` branches are under normal liquidation conditions (this is not fully verifiable from static review alone — the exact conditions under which `get-cached-indexes` would return `none` for a debt asset already accrued in the same call are not confirmed with certainty from the code read so far). At minimum, the design pattern itself (documented "isolated batch" guarantee implemented via `unwrap-panic` on a cache lookup and on `as-max-len?`) is a structural risk: any future edge case, config change, or unexpected combination of collateral/debt lists that causes cache-miss or length-overflow on one position turns an intended "isolated failure" into a "whole batch reverts" DoS, silently violating the documented invariant.

### Recommendation
- Replace `unwrap-panic` in `liquidate` with `match`/`unwrap!` patterns that return a typed `err` (e.g., `ERR-INDEX-CACHE-MISS`) instead of panicking, so that `call-liquidate`/`map` in `liquidate-multi` can honor the documented "err doesn't revert the batch" contract for every failure path, not just `asserts!`/`try!` ones.
- Add an explicit unit/property test for `liquidate-multi` that forces one position to hit each `unwrap-panic` site and asserts the remaining positions still succeed.

### Proof of Concept
1. Liquidator submits `liquidate-multi` with N unhealthy borrower positions, each individually liquidatable and profitable [9](#0-8) .
2. `map call-liquidate positions` invokes `liquidate` for each position sequentially in the same transaction [2](#0-1) .
3. For one crafted/edge-case position, execution reaches the `unwrap-panic (get-cached-indexes debt-aid)` branch (either the "remaining-debt-to-repay" or "other-debt-repayable" calculation) with a `none` cache result, or reaches the `unwrap-panic (as-max-len? ...)` bad-debt list append with an overflow condition [3](#0-2) , [4](#0-3) , [5](#0-4) .
4. Clarity's runtime aborts the entire top-level transaction on `unwrap-panic (none)`, rolling back all state changes made by the previously-processed, otherwise-successful liquidations in the same `liquidate-multi` call, even though `call-liquidate`/`map` never itself propagates an `err` for those other positions.
5. The liquidator's whole batch fails with no on-chain effect, and the documented "failed liquidations don't revert the entire batch" property [1](#0-0)  is violated for this class of failure.
