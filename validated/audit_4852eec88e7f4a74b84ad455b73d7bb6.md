### Title
Relayer fee is paid unconditionally before the emulated transfer/ft_transfer action is confirmed to succeed - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Across report's bug class is: a bridging path calls the wrong/unsupported function on the destination system, so the "main" operation reverts, yet the surrounding logic proceeds as if things were fine. The closest reachable analog in nearcore is in the NEAR Wallet Contract's `inner_rlp_execute`, which unconditionally sends the relayer's fee **before** it knows whether the actual user-intended action (a base-token `Transfer` or an emulated ERC-20 `ft_transfer`) will succeed.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-410`) parses an RLP-encoded Ethereum transaction into a Near `Action` plus a `TransactionKind`. For `EOABaseTokenTransfer` and `ERC20Transfer` kinds carrying a non-zero `fee`, the code immediately fires a transfer promise to pay the relayer: [1](#0-0) 

This fee-payment promise (`env::promise_batch_create` + `env::promise_batch_action_transfer` to `context.predecessor_account_id`, i.e. the relayer) is created eagerly and is **not** chained after, or conditioned on, the success of the actual action promise (the `Transfer` or the `ft_transfer` cross-contract call created later in the same function, e.g. via `action_to_promise` or the NEP-141 `storage_balance_of`/`storage_deposit`/`ft_transfer` chain at lines 433-458). The fee-payment receipt and the "real" action receipt are dispatched as independent, unlinked receipts from the same function-call execution.

Because Near receipts execute independently and asynchronously, if the emulated action later fails on-chain — for example because the ERC-20 emulation calls `ft_transfer` on a target contract that reverts, does not implement NEP-141 correctly, or fails the `storage_deposit` step, or because the plain `Transfer` action targets an account that no longer exists — the relayer fee transfer has **already been irrevocably sent** in a separate receipt. There is no rollback or reconciliation between the two receipts.

This mirrors the Across bug precisely at the conceptual level: a value-transfer or fee-related side effect is triggered based on an *assumption* that a subsequent operation (calling a specific method on a possibly-incompatible target) will succeed, without actually gating on its outcome.

### Impact Explanation
This allows unauthorized/unconditional value movement out of the user's wallet contract: the relayer collects a paid fee even when the user's intended transfer never executes. A malicious or careless relayer can systematically submit transactions whose underlying action is designed to fail (e.g., targeting a token contract lacking `ft_transfer`/`storage_deposit` support, or an account that will fail `Transfer`), while still collecting the fee every time, since the fee-paying receipt has no data dependency on the outcome of the action receipt. This is a "fee bypass"/"unauthorized value movement" class of impact: the wallet owner is repeatedly charged for services that never take effect.

### Likelihood Explanation
Reachable by any relayer or the wallet's own signer submitting a `rlp_execute` transaction (an ordinary transaction/RPC call, no privileged access needed). The relayer only needs to choose a `target`/token contract that will make the second, real action promise fail (which is trivial and fully within an unprivileged party's control) while the emulated transfer/transfer-fee logic still computes a non-zero fee. The existing test suite (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/emulation.rs`) only validates the "happy path" (successful ERC-20/base-token transfers with correct relayer refunds); there is no test asserting the fee is withheld or refunded when the corresponding action fails, which is consistent with this not being handled.

### Recommendation
Chain the relayer-fee payment so that it only executes after (and conditionally upon) confirmation that the user's underlying action succeeded — e.g., attach the fee-transfer as a `.then()` continuation of the main action promise (similar to how `rlp_execute_callback` already inspects `env::promise_result(0)`), or perform the fee transfer inside the callback only when the action's `PromiseResult::Successful` branch is taken, refunding/skipping it entirely on `PromiseResult::Failed`.

### Proof of Concept
1. A relayer submits an RLP transaction to the Wallet Contract's `rlp_execute` with `target` set to a NEP-141-like contract but with a payload/receiver combination guaranteed to fail (e.g., a receiver_id/token contract combination such that `ft_transfer` or the earlier `storage_deposit`/`storage_balance_of` chain fails), while `gas_price`/`gas_limit` are set so that `tx_fee` (computed at `internal.rs:59-64`) is non-zero.
2. `inner_rlp_execute` parses this to `TransactionKind::EthEmulation(ERC20Transfer { fee, .. })` (or `EOABaseTokenTransfer`) with non-zero `fee`.
3. Per `lib.rs:374-385`, before any confirmation of the transfer's success, a `promise_batch_create`/`promise_batch_action_transfer` sends `fee` yoctoNEAR from the wallet contract to `context.predecessor_account_id` (the relayer) as an unconditional, separate receipt.
4. The main action promise chain (`nep_141_storage_balance_callback` → `ft_transfer`/`storage_deposit`, or `action_to_promise` for `Transfer`) subsequently fails, as reported in `rlp_execute_callback`'s `PromiseResult::Failed` branch (`lib.rs:296-312`), yet the fee sent in step 3 is not reverted or reclaimed.
5. Net effect: relayer is paid `fee` yoctoNEAR from the wallet even though the user's intended action never completed — repeatable indefinitely by any relayer that controls the transaction contents.
