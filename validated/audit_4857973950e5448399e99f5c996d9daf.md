### Title
Rounding in `ExchangeInjectActuator`'s liquidity-provisioning math truncates in the depositor's favor, letting a user under-fund the counter-side of an Exchange pool while the legacy (default) math path remains live - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes the "matching" amount of the other token a liquidity-injecting user must pay using integer truncation (`BigInteger.divide()` / `LongMath.floorDiv`), which always rounds toward zero. This means the amount deducted from the depositor's balance for the paired token is always `≤` the exact proportional amount, so the depositor consistently pays fractionally less than a mathematically-fair injection would require, while the pool's recorded balances (and thus its internal price ratio) still get updated using that same rounded-down value. This is the same bug class described in the Trail of Bits Umee report: a fixed-precision computation that is truncated to an integer, with the rounding direction chosen so it benefits the user rather than the protocol/pool.

### Finding Description
In `doValidate()` and `execute()` of `ExchangeInjectActuator`, the paired ("another") token amount is derived from the pool ratio: [1](#0-0) 

and the same truncating math is used in `execute()`: [2](#0-1) 

Both `BigInteger.divide()` (used in validation) and `LongMath.floorDiv`-driven arithmetic used in execution truncate toward zero for positive operands — i.e., they always round down. Because the depositor's `anotherTokenQuant` is exactly what gets subtracted from their own asset balance via `reduceAssetAmountV2`, a systematically-downward-rounded value directly reduces what the user must pay to inject liquidity, while the pool's balances (`exchangeCapsule.setBalance(...)`) are updated with that same reduced value — meaning the pool's recorded price ratio is nudged away from the "fair" ratio in the depositor's favor.

This directly mirrors the root cause in the ToB report: "the amount ... is calculated using ... fixed-precision decimal numbers that are truncated to integer values... If an error occurs, it will benefit the user." Crucially, whether this rounding-favoring-the-user path is even reachable depends on the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter, which defaults to `0` (disabled): [3](#0-2) [4](#0-3) 

The codebase does contain a comprehensive later hardening effort (`SafeExchangeProcessor`, `BigDecimal`/`BigInteger` exact-overflow checks, "Not precise enough" tolerance checks) gated behind `ALLOW_HARDEN_EXCHANGE_CALCULATION`/`ALLOW_HARDEN_RESOURCE_CALCULATION`, which is clearly designed to remediate exactly this class of bug. However, since these proposals default to off and must be separately voted in by the committee, the legacy truncating arithmetic in `ExchangeInjectActuator` remains the live, reachable behavior unless/until that governance proposal passes.

### Impact Explanation
Every `ExchangeInjectContract` executed under the default (non-hardened) configuration lets the depositor pay a rounded-down amount of the paired token relative to the mathematically exact pool ratio. Repeated over many small injections (analogous to the Umee "repeat the process again and again" exploit scenario), this systematically siphons value out of the exchange pool's internal accounting relative to fair pricing, degrading the integrity of the AMM-style `Exchange`/`ExchangeV2` balances that other traders rely on for `ExchangeTransactionActuator` pricing. This falls under the accepted "accounting"/"underpriced-public-work" impact category since it lets an unprivileged user extract more value (or contribute less collateral) than the exchange's own bonding-curve math intends.

### Likelihood Explanation
Any unprivileged account that created (or has creator rights on) an `Exchange` pool can call `ExchangeInjectContract` repeatedly with attacker-chosen `quant` values to maximize the truncated remainder each time, with no special privileges required and no protection unless the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal has been activated by the witness committee. Because the hardened path is opt-in and not the default, the likelihood of this remaining exploitable on any deployment that hasn't explicitly enacted the proposal is high.

### Recommendation
- Short term: Make `ALLOW_HARDEN_EXCHANGE_CALCULATION` (and `ALLOW_HARDEN_RESOURCE_CALCULATION`) default to `1`/enabled at genesis for new networks, or schedule automatic activation, rather than leaving truncation-favoring-the-user math as the permanent default fallback.
- Long term: For any injection/withdrawal math that must round, always round in the direction that benefits the pool/module (e.g., ceiling the amount the user must pay in, floor the amount the pool pays out), consistent with the `RepositoryImpl.divideCeil`/`divideCeilExact` pattern already used elsewhere in the codebase for resource math.
- Add fuzz/property tests asserting that no sequence of `ExchangeInjectContract`/`ExchangeWithdrawContract` calls can leave a user with more combined value than they contributed, under the default (non-hardened) configuration.

### Proof of Concept
Conceptual PoC (concrete numeric proof requires simulation against `ExchangeInjectActuatorTest`'s harness):
1. Attacker creates (or uses an existing) `Exchange` pool with `firstTokenBalance`/`secondTokenBalance` chosen so that `secondTokenBalance * tokenQuant` is not evenly divisible by `firstTokenBalance` for a range of small `tokenQuant` values.
2. Attacker repeatedly submits `ExchangeInjectContract` with `tokenQuant` values engineered to maximize the truncated remainder of `anotherTokenQuant = floor(secondTokenBalance * tokenQuant / firstTokenBalance)` (see `ExchangeInjectActuator.java` lines 215-227), with `ALLOW_HARDEN_EXCHANGE_CALCULATION` left at its default value of `0`.
3. Each injection lets the attacker add liquidity while paying less of the paired token than the pool's true ratio requires, incrementally skewing the pool's recorded ratio in the attacker's favor at the expense of the pool's/other users' fair pricing — mirroring the Umee "repeat the process again and again" loop that drains value via accumulated rounding.
