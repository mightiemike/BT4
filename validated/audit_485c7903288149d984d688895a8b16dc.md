**Analysis:** `TokenCancelOfferEvent` is a plain historical event payload — it stores `to_address`, `token_id`, and `amount` as immutable data serialized at the time the event was emitted, with no live reference to current storage state, and no accessor or storage-schema logic that dereferences the `token_id` against a resource that must still exist. [1](#0-0) 

The API layer never "joins" this event with a resource lookup to build a proof-bearing response. Event queries (`api/src/events.rs`) resolve strictly against the requested `ledger_version` via `context.get_events(...)` and independently convert the raw event bytes using the state view *at that same version*, without dereferencing `token_id` into a live resource. [2](#0-1) 

Resource lookups are a completely separate API path (`api/src/state.rs::resource`) that is version-bound on its own via `self.context.state_view(ledger_version)`, and returns a 404/`resource_not_found` if the resource is absent at that version — it does not embed or validate against any previously emitted event's `token_id`. [3](#0-2) 

The premise assumes the API produces a single "event/resource pairing" response object bound to one proof/root that could become inconsistent if the token is deleted in the same block. In reality, events and resources are independently versioned artifacts: an event is a durable historical record of what happened at its transaction version (it correctly reflects that a cancel-offer occurred, referencing a `TokenId` that existed prior to or at that point), and a resource query is a separate, independently authenticated lookup bound to whatever version the caller requests. Aptos never fabricates a joint "event+current-resource" authenticated object, so there is no proof/version misbinding here — a deleted token_data resource simply yields "not found" for later resource queries while the event correctly remains as a historical, version-bound record. This falls under the excluded "event-only mismatches" category and does not correspond to any wrong write set, proof node, root, or version binding.
