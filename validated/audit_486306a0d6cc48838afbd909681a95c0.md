### Title
Missing parameter-range validation in `ProposalUtil.validator()` for governance parameters that are validated only at config-load time - (File: `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`)

### Summary
The reported pattern (constructor/initializer skips a validation check that the corresponding runtime "setter" enforces, or vice versa) has a direct analog in java-tron's on-chain governance-parameter mechanism. `CommitteeConfig.postProcess()` clamps `unfreezeDelayDays` to `[0, 365]` when the node loads its config file (the "constructor" path), but `ProposalUtil.validator()` — the actual runtime gate that validates every committee proposal before its value is written into `DynamicPropertiesStore` (the real "setter" path used in production) — contains no `case` for `UNFREEZE_DELAY_DAYS` at all, so it silently falls through to the `default: break;` branch with zero validation.

### Finding Description
`ProposalUtil.validator()` is a large `switch` over `ProposalType` that enforces explicit bounds for most governance parameters, e.g. `MAX_CPU_TIME_OF_ONE_TX`, `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO [1,1000]`, `ADAPTIVE_RESOURCE_LIMIT_MULTIPLIER [1,10000]`, `ALLOW_HARDEN_EXCHANGE_CALCULATION {0,1}`, etc. [1](#0-0)  Any `ProposalType` not explicitly handled falls through to a no-op `default` branch. [2](#0-1) 

`UNFREEZE_DELAY_DAYS` is a defined `ProposalType` (code 70) documented in its own enum comment as `// 0, [1, 365]`, i.e. it should only accept values in `[1,365]`. [3](#0-2)  A `grep` over `ProposalUtil.java` for `UNFREEZE_DELAY_DAYS` found no matching `case` in the validator switch — the value is never range-checked when set via a committee proposal.

By contrast, the equivalent "constructor" path — `CommitteeConfig.postProcess()`, invoked once at node startup when binding `committee.unfreezeDelayDays` from `reference.conf`/`config.conf` — does clamp the value to `[0, 365]`. [4](#0-3)  The two paths do not even agree on the same bound (`[0,365]` at config load vs. documented `[1,365]` for the runtime setter), and the runtime setter path enforces nothing at all.

The actual value change is applied unconditionally by `ProposalService.process()`, which writes whatever numeric value passed `ProposalUtil.validator()` straight into `DynamicPropertiesStore` via the corresponding `save*` method (the same dispatch pattern used for all other validated parameters such as `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO`, `TOTAL_ENERGY_LIMIT`, etc.). [5](#0-4)  Since `UNFREEZE_DELAY_DAYS` has no `case` in `validator()`, a proposal carrying an arbitrary value (negative, zero, or far beyond 365) for that parameter passes validation unimpeded and is committed to consensus state.

### Impact Explanation
`getUnfreezeDelayDays()` feeds directly into unfreeze/resource-lock actuators that gate how long a user's frozen TRX/resources must remain locked before they can be unfrozen. An out-of-range value (e.g. 0, negative, or an unbounded large number) accepted through committee proposal without the intended `[1,365]` bound can corrupt resource-accounting invariants network-wide (locking funds indefinitely, or allowing immediate unfreeze contrary to protocol intent), since every full node applies the same unvalidated value deterministically from the proposal. This is a consensus-state parameter, so the effect is systemic rather than confined to a single account.

### Likelihood Explanation
Reaching this path requires a committee proposal to be created and approved — the same privilege level required by the original report's `setCushionFactor`/`setSpreads`-style admin setters, which the original finding still rated Medium severity purely because of the missing validation, independent of caller privilege. The bug is a straightforward oversight (a missing `case` in an otherwise-exhaustive switch), not requiring any unusual conditions to trigger once a proposal for `UNFREEZE_DELAY_DAYS` (code 70) is submitted and approved through the normal governance flow.

### Recommendation
Add an explicit `case UNFREEZE_DELAY_DAYS:` to `ProposalUtil.validator()` enforcing the same range documented in the enum comment (`[1, 365]`), and audit other `ProposalType` values that likewise lack a validator branch (e.g. confirm coverage for `ALLOW_MULTI_SIGN`, `ALLOW_ADAPTIVE_ENERGY`, `MAX_DELEGATE_LOCK_PERIOD`) to ensure every parameter reachable through the governance-proposal "setter" path is validated with bounds consistent with its config-time "constructor" validation in `CommitteeConfig.postProcess()`.

### Proof of Concept
1. A witness/committee member submits a `ProposalCreateContract` setting parameter code `70` (`UNFREEZE_DELAY_DAYS`) to an out-of-range value, e.g. `0` or `100000`.
2. During proposal approval, `ProposalUtil.validator(dynamicPropertiesStore, forkController, 70, value)` is invoked; because there is no `case UNFREEZE_DELAY_DAYS` in the switch, execution falls to `default: break;` and no `ContractValidateException` is thrown. [2](#0-1) 
3. Once approved, `ProposalService.process()` dispatches the same value into `DynamicPropertiesStore` unchecked, and it becomes active network-wide, unlike the config-time path which would have clamped it to `[0,365]` had it been supplied via `config.conf`. [4](#0-3)
