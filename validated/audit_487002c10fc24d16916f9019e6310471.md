### Title
Unannounced, Immediate-Effect Resource-Sharing Parameter Changes Enable Front-Running of Unsuspecting Contract Callers - ([File: actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java])

### Summary
`UpdateSettingContractActuator` and `UpdateEnergyLimitContractActuator` let a smart contract's `originAddress` (deployer/owner) change `ConsumeUserResourcePercent` and `OriginEnergyLimit` respectively at any time, with the new value taking effect on the very next block/transaction that touches the contract. There is no time lock, no notice period, and no validation that the new value differs meaningfully from the current one. This mirrors the zAuctionAccountant bug class: a privileged party can alter behavior that unprivileged users (any account calling the contract) rely on, with the change landing immediately and unpredictably, including in a front-running window against pending user transactions.

### Finding Description
`UpdateSettingContractActuator.execute()` unpacks the new `consume_user_resource_percent` and writes it straight into the `ContractCapsule`, clearing the LRU cache so it is active for the very next transaction: [1](#0-0) 

The only guard in `validate()` is a static range check (`[0, 100]`) and an owner check — there is no comparison against the previous value, no cooldown, and no delayed activation: [2](#0-1) 

The same pattern exists for `UpdateEnergyLimitContractActuator`, which changes `OriginEnergyLimit` (how much energy the contract owner subsidizes per call) immediately and without a delay: [3](#0-2) 

Both parameters directly determine how transaction fees for calling the contract are split between the caller (an unprivileged, unrelated user) and the contract's origin address. Because the change is committed to chain state as soon as the block including the `UpdateSettingContract`/`UpdateEnergyLimitContract` transaction is processed, an owner can:
- Observe a pending high-value call to their contract in the mempool.
- Submit (and get included ahead of, or in the same maintenance/packing window as) the victim's transaction an `UpdateSettingContract` changing `consume_user_resource_percent` from a caller-friendly value (e.g. 0, meaning the owner pays) to 100 (caller pays all), or drastically lower `origin_energy_limit`.
- The victim's transaction, already signed and broadcast with a `fee_limit` calculated under the old cost-sharing assumption, now executes under the new split and either burns unexpectedly more of the caller's own resources/TRX, or runs out of energy/fee mid-execution.

This is exactly the underlying issue described in the report: users cannot be sure what the behavior of a call will be, because that behavior can be altered arbitrarily and immediately by a privileged actor, with no advance warning mechanism (time lock) and no argument sanity check (e.g., rejecting a no-op or requiring a minimum change window).

### Impact Explanation
The impacted party is not the privileged contract owner but any unprivileged account that calls the affected smart contract. A front-run or badly timed `UpdateSettingContract`/`UpdateEnergyLimitContract` transaction causes:
- Unexpected accounting outcome: the caller pays energy/bandwidth fees they did not budget for based on the state of the contract when they signed their transaction.
- Possible transaction failure (out-of-energy) after resources have already been partially consumed and charged, since TVM execution fees are charged for work performed even on failure.

This fits the "accounting" impact category — unprivileged users suffer unannounced, unpredictable fee/resource-accounting changes triggered unilaterally by a privileged party, with no protocol-level safeguard (timelock, delayed activation, or no-op check).

### Likelihood Explanation
Any contract owner can trigger this at will, at zero cost beyond a normal transaction fee (`calcFee()` returns 0 for both actuators): [4](#0-3) 
Because Tron's mempool/pending transactions are publicly observable, an owner (or anyone colluding with a block-producing witness) can time such a change to land just before a high-value call to maximize the fee shifted onto the caller. No special conditions or governance approval are required, unlike the committee-controlled `ProposalService` parameters which already benefit from supermajority witness approval plus mandatory activation at the next maintenance cycle.

### Recommendation
- Require a minimum delay (e.g., activate at the next maintenance cycle, similar to `ProposalService`) before `ConsumeUserResourcePercent`/`OriginEnergyLimit` changes take effect, so pending transactions are unaffected.
- Reject no-op updates (new value == current value) and emit an event/log sufficiently in advance of activation so wallets/dApps can warn users.
- Consider bounding the magnitude of a single change (e.g., percent change per epoch) to reduce the blast radius of a single front-run.

### Proof of Concept
1. Contract `C` is deployed by owner `O` with `consume_user_resource_percent = 0` (owner subsidizes all energy).
2. User `U` builds and signs a transaction `T` calling `C`, computing `fee_limit` assuming `O` pays for energy.
3. `U` broadcasts `T`; it sits in the mempool.
4. `O` observes `T` and immediately submits `UpdateSettingContract{contract_address=C, consume_user_resource_percent=100}` (validated only by the `[0,100]` range check in `UpdateSettingContractActuator.validate()`), getting it processed in the same or an earlier block than `T`.
5. When `T` executes, the actuator/VM now charges 100% of energy to `U` instead of `O`, per the mutated `ContractCapsule` written in `UpdateSettingContractActuator.execute()`; `U`'s `fee_limit` — sized for 0% — may be exceeded, causing `OUT_OF_ENERGY` failure while `U`'s TRX for consumed resources is still burned.
