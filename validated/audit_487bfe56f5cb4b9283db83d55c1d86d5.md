This confirms the direct analog. The `ExchangeTransactionContract` (a swap/trade against the pool) explicitly includes an `expected` field checked at line 219 of `ExchangeTransactionActuator.java` (`if (anotherTokenQuant < tokenExpected) throw ...`), giving traders slippage protection. In contrast, `ExchangeInjectContract` — the liquidity-provision equivalent of `mintFungible` — has no such field, so an LP injecting liquidity has no way to bound the ratio/amount they are forced to contribute based on live pool reserves.

### Title
Unbounded slippage in `ExchangeInjectActuator` liquidity provisioning enables front-run value extraction from LPs - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`java-tron`'s bancor-style `Exchange`/`ExchangeV2` AMM lets a creator "inject" (add) liquidity to a token pair via `ExchangeInjectContract`. The amount of the paired token the LP must contribute (and, implicitly, the value they receive credit for) is computed strictly from the exchange's *current* on-chain reserves at execution time, with no user-supplied bound on acceptable ratio/amount — mirroring the `VaderPoolV2.mintFungible` unlimited-slippage bug from the external report.

### Finding Description
`ExchangeInjectActuator.execute()` computes `anotherTokenQuant` purely from the live `firstTokenBalance`/`secondTokenBalance` of the `ExchangeCapsule` at the moment the transaction is processed: [1](#0-0) . The same unconstrained calculation is repeated in `doValidate()` [2](#0-1) . The `ExchangeInjectContract` protobuf message carries only `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum-output field, unlike `ExchangeTransactionContract`, which does carry an `expected` field. By contrast, `ExchangeTransactionActuator` (the trade/swap actuator) explicitly validates the trader's minimum acceptable output: [3](#0-2) . Because transactions within a block are processed sequentially (`validate()` then `execute()` per transaction, in ordering determined by the block producer/mempool), an attacker can submit `ExchangeTransactionContract` swaps that shift `firstTokenBalance`/`secondTokenBalance` immediately before the victim's `ExchangeInjectContract` is processed, altering the ratio used to compute `anotherTokenQuant`, and then submit a reversing trade afterward to restore the pool state — pocketing the difference at the victim LP's expense, exactly as described for `VaderPoolV2.mintFungible`.

### Impact Explanation
An LP calling `ExchangeInject` to add liquidity has no on-chain mechanism to cap the amount of the second token they will be forced to contribute, nor any floor on the effective value credited to them relative to reserves at submission time. A block producer or any actor able to order transactions within a block (which in TRON is the witness producing the block) can sandwich an injection to extract value from the LP, up to the full economic loss illustrated in the referenced report. This is a genuine accounting/settlement manipulation affecting unprivileged users interacting with the built-in `Exchange`/`ExchangeV2` market feature.

### Likelihood Explanation
Exploitation requires the ability to order or front-run transactions within the same block relative to the victim's inject transaction — achievable by a witness (block producer) trivially, or by any user racing transactions via fee/ordering games during network congestion. The `Exchange` feature is a native, actively reachable protocol feature (not privileged or internal-only), and the missing-bound code path is on every `ExchangeInjectContract` execution, so likelihood is non-trivial though it depends on active market manipulation rather than a passive bug.

### Recommendation
Add a user-specified minimum/maximum bound (analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeInjectContract`, e.g. a `min_another_token_quant` field, and enforce `anotherTokenQuant >= min_another_token_quant` in `ExchangeInjectActuator.doValidate()`/`execute()`, mirroring the existing slippage check pattern already used in `ExchangeTransactionActuator.java` lines 217-221.

### Proof of Concept
1. Exchange pool holds `firstTokenBalance = A`, `secondTokenBalance = B`.
2. Victim submits `ExchangeInjectContract` intending to inject `tokenQuant` of the first token, expecting to pay/receive proportional to `A:B`.
3. Attacker (or the block-producing witness) inserts an `ExchangeTransactionContract` swap immediately before the victim's transaction in the same block, shifting the ratio to `A':B'` via `exchangeCapsule.transaction(...)`.
4. Victim's `ExchangeInjectActuator.execute()` computes `anotherTokenQuant` from the manipulated `A':B'` ratio [1](#0-0) , causing the victim to contribute more of the second token than fair value, or receive less credited pool share, than intended.
5. Attacker submits a reversing swap after the victim's injection is processed, restoring `A:B` and capturing the difference.
