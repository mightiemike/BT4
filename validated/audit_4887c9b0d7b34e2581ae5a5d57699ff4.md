## Title
`unwrap()` on assumed-present account data during startup lt-hash/capitalization calculation can panic AccountsDb - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb::calculate_accounts_lt_hash_at_startup_from_index` and `AccountsDb::calculate_capitalization_at_startup_from_index` both walk the accounts index bin-by-bin, and for every pubkey they find in the index they call `.get_loaded_account(...)` followed by an unconditional `.unwrap()`, justified only by a comment asserting the load must succeed. This mirrors exactly the reported nord bug class: an option is assumed non-empty based on an invariant comment, and `unwrap()` is used instead of handling the `None` case defensively.

### Finding Description
In `calculate_accounts_lt_hash_at_startup_from_index`:
```
self.accounts_index
    .get_with_and_then(&pubkey, ancestors, false, |(slot, account_info)| {
        (!account_info.is_zero_lamport()).then(|| {
            self.get_account_accessor(slot, &account_info.storage_location())
                .get_loaded_account(|loaded_account| {
                    Self::lt_hash_account(&loaded_account, &pubkey)
                })
                // SAFETY: The index said this pubkey exists, so
                // there must be an account to load.
                .unwrap()
        })
    })
``` [1](#0-0) 

and identically in `calculate_capitalization_at_startup_from_index`:
```
self.get_account_accessor(slot, &account_info.storage_location())
    .get_loaded_account(|loaded_account| loaded_account.lamports())
    // SAFETY: The index said this pubkey exists, so
    // there must be an account to load.
    .unwrap()
``` [2](#0-1) 

`get_loaded_account` itself documents that the underlying storage entry "may not be present if slot was cleaned up in between reading the accounts index and calling this function to get account meta from the storage entry", returning `None` in that race:
```
fn get_loaded_account<T>(
    &mut self,
    mut callback: impl for<'local> FnMut(LoadedAccount<'local>) -> T,
) -> Option<T> {
    match self {
        LoadedAccountAccessor::Stored(maybe_storage_entry) => {
            // storage entry may not be present if slot was cleaned up in
            // between reading the accounts index and calling this function to
            // get account meta from the storage entry here
            maybe_storage_entry
                .as_ref()
                .and_then(|(storage_entry, offset)| { ... })
        }
    }
}
``` [3](#0-2) 

The comment in the caller ("SAFETY: The index said this pubkey exists, so there must be an account to load") is the same style of unverified assumption seen in the nord `Receipt::Trade` bug — a comment stating an invariant that is not actually enforced against concurrent mutation, followed by `unwrap()`. The general reader path (`retry_to_get_account_accessor`) is explicitly hardened against this exact race (storage entry removed between index read and storage lookup due to shrink/clean/purge) via a documented retry loop with a bounded number of acceptable failed iterations and an explicit panic message when the race is *not* resolvable within bounds. [4](#0-3)  No equivalent retry/guard exists in the two startup calculation functions above — they take a single snapshot read from the index bin and immediately dereference storage once, unwrapping on failure with no retry.

### Impact Explanation
If storage for a pubkey is reclaimed (via clean/shrink/purge) between the index bin snapshot and the subsequent per-pubkey storage lookup inside these functions, `get_loaded_account` returns `None` and the `unwrap()` panics, crashing the node process — the same "node panic" class documented in the external report. Both functions are explicitly documented as "NOT safe to call concurrently with flush operations," but they say nothing about concurrency with clean/shrink/purge, and the accounts index bins are locked/read independently per bin while storage removal (clean_accounts, shrink, purge_slots) can run in the background per the race diagram in `retry_to_get_account_accessor`. [5](#0-4) 

### Likelihood Explanation
These two functions are documented as "Only intended to be called at startup by ledger-tool or tests" [6](#0-5)  and "Only intended to be called at startup (or by tests)... NOT safe to call concurrently with flush operations" [7](#0-6) . I was not able to fully confirm from the available index whether a live validator can invoke `calculate_accounts_lt_hash_at_startup_from_index` (via `Bank::verify_accounts` / `run_final_hash_calc`, called by `ledger-tool`) at a point where background clean/shrink/purge threads are concurrently active outside of the documented startup window — this determines whether the finding is genuinely reachable by an unprivileged/background process race or is confined to a single-threaded startup context where clean/shrink have not yet started. Given this uncertainty and that the callers are explicitly scoped to startup/ledger-tool/tests (arguably a "bootstrap-phase-only" context), I cannot assert this is definitively reachable as a live, attacker-triggerable panic without further investigation of the exact call sites and their concurrency guarantees.

### Recommendation
Replace the `.unwrap()` calls with explicit handling that either (a) retries the index lookup similar to `retry_to_get_account_accessor`'s bounded retry loop, or (b) treats an unexpectedly missing account as a hard, clearly-labeled internal-consistency error while ensuring the invariant is actually enforced (e.g., by holding the necessary locks/guards across both the index and storage reads, as scans do), rather than only documented in a comment.

### Proof of Concept
Not independently reproducible from the available static analysis; the analog requires concurrently running `clean_accounts`/`shrink`/`purge_slots` against `calculate_accounts_lt_hash_at_startup_from_index` or `calculate_capitalization_at_startup_from_index` while iterating accounts_index bins, analogous to the existing regression tests `test_load_account_and_shrink_race_with_retry` / `test_load_after_remove_unrooted_and_restore_to_same_slot` [8](#0-7) [9](#0-8) , which demonstrate the same race exists for the general read path and was fixed there but not in the two startup-calculation functions identified above.

    let epoch_schedule = EpochSchedule::default();
    db.load_delay = RACY_SLEEP_MS;
    let db = Arc::new(db);
    let pubkey = Arc::new(Pubkey::new_unique());
    let exit = Arc::new(AtomicBool::new(false));
    let slot = 1;

    // Store an account
    let lamports = 42;
    let mut account = AccountSharedData::new(1, 0, AccountSharedData::default().owner());
    account.set_lamports(lamports);
    db.store_for_tests((slot, [(pubkey.as_ref(), &account)].as_slice()));

    // Set the slot as a root so account loads will see the contents of this slot
    db.add_root(slot);

    let t_shrink_accounts = {
        let db = db.clone();
        let exit = exit.clone();

        std::thread::Builder::new()
            .name("account-shrink".to_string())
            .spawn(move || {
                loop {
                    if exit.load(Ordering::Relaxed) {
                        return;
                    }
                    // Simulate adding shrink candidates from clean_accounts()
                    db.shrink_candidate_slots.lock().unwrap().insert(slot);
                    db.shrink_candidate_slots(&epoch_schedule);
                }
            })
            .unwrap()

    let t_do_load = start_load_thread(
        with_retry,
        Ancestors::default(),
        db,
        exit.clone(),
        pubkey,
        move |_| lamports,
    );

    sleep(Duration::from_secs(RACE_TIME));
    exit.store(true, Ordering::Relaxed);
    t_shrink_accounts.join().unwrap();
    t_do_load.join().map_err(std::panic::resume_unwind).unwrap()
}

#[test]
fn test_load_after_remove_unrooted_and_restore_to_same_slot() {
    let slot = 402240429;
    let bank_id = 1;
    let pubkey = Pubkey::new_unique();
    let account = AccountSharedData::new(42, 0, AccountSharedData::default().owner());

    let db = Arc::new(AccountsDb::default_for_tests());
    let ancestors = Ancestors::from(vec![slot]);

    let exit = Arc::new(AtomicBool::new(false));

    // Control thread – performs the sequential remove-then-store cycle that mirrors
    // what happens in production when a duplicate bank is purged and the slot is
    // subsequently re-processed by the banking stage.
    let t_store = {
        let db = db.clone();
        let account = account.clone();
        let exit = exit.clone();
        std::thread::Builder::new()
            .name("control".to_string())
            .spawn(move || {
                loop {
                    if exit.load(Ordering::Relaxed) {
                        return;
                    }
                    // Step A: purge the slot (simulate remove_unrooted_slots).
                    if db.accounts_cache.slot_cache(slot).is_some() {
                        db.remove_unrooted_slots(&[(slot, bank_id)]);
                    }
                    // Step B: re-store the account (simulate store_accounts_unfrozen).
                    db.store_for_tests((slot, &[(&pubkey, &account)][..]));
                }
            })
            .unwrap()
    };

    // Load thread – continuously attempts to load the account.
    let t_do_load = {
        let db = db.clone();
        let exit = exit.clone();
        std::thread::Builder::new()
            .name("load".to_string())
            .spawn(move || {
                loop {
                    if exit.load(Ordering::Relaxed) {
                        return;
                    }
                    let _ = db.load(
                        &ancestors,
                        &pubkey,
                        LoadHint::FixedMaxRoot,
                        PopulateReadCache::False,
                    );
                }
            })
            .unwrap()
    };

    // Prior to the fix, it failed with a panic in 'retry_to_get_account_accessor' after ~1 second,
    // run long enough to catch the failure reliably.
    sleep(Duration::from_secs(5));
    exit.store(true, Ordering::Relaxed);
    t_store.join().unwrap();
    // Propagate any panic from the load thread in retry_to_get_account_accessor).
    t_do_load.join().map_err(std::panic::resume_unwind).unwrap();
}
