### Title
Missing Early Return in `validate_delegate_action_key` Advances Nonce on Rejected `DelegateAction` — (`File: runtime/runtime/src/actions.rs`)

### Summary

In `validate_delegate_action_key`, when a `DelegateAction` signed with a `FunctionCallPermission` key carries `deposit > 0`, the code sets `result.result = Err(DepositWithFunctionCall)` but — before protocol version 85 — does **not** return early. Execution falls through to the `receiver_id` and `method_name` checks. If those checks pass, the function reaches the unconditional nonce-advance block and writes the new nonce to state. Control then returns to `apply_delegate_action`, which sees `result.result.is_err()` and exits without spawning a receipt. The net effect: the sender's access-key (or gas-key) nonce is permanently incremented in the trie even though the action was rejected and no receipt was created.

### Finding Description

`validate_delegate_action_key` (`runtime/runtime/src/actions.rs:535`) validates the access key used to sign a `DelegateAction`. The permission-check block at line 636 handles `FunctionCallPermission` keys:

```
if function_call.deposit > Balance::ZERO {
    result.result = Err(DepositWithFunctionCall);
    // PRE-v85: no return here — falls through
}
if delegate_action.receiver_id() != &function_call_permission.receiver_id {
    result.result = Err(ReceiverMismatch { … });
    return Ok(());
}
// method-name check …
```

After all permission checks, the nonce-advance block runs unconditionally:

```rust
match nonce_update {
    DelegateNonceUpdate::AccessKey => {
        access_key.nonce = delegate_nonce.nonce();
        set_access_key(state_update, …);   // writes to trie
    }
    DelegateNonceUpdate::GasKey { nonce_index } => {
        set_gas_key_nonce(state_update, …); // writes to trie
    }
}
```

There is no guard on `result.result.is_ok()` before this block. If the `receiver_id` and method-name checks both pass (or method_names is empty), the nonce is written to the trie with `result.result` already set to `Err`. The caller `apply_delegate_action` (line 448) then checks `result.result.is_err()` and returns without spawning a receipt — but the trie write has already been committed to `state_update`.

The fix — `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError` (activated at protocol version 85) — adds the missing `return Ok(())` immediately after setting the `DepositWithFunctionCall` error. The buggy code path is preserved in the binary for protocol versions 83–84 (the range covered by `MIN_SUPPORTED_PROTOCOL_VERSION = 83`).

A secondary consequence: when both `deposit > 0` **and** `receiver_id` mismatches, the `DepositWithFunctionCall` error is silently overwritten by `ReceiverMismatch`, returning the wrong error to the user. The unit test `test_delegate_deposit_with_function_call_reports_receiver_mismatch_before_fix` explicitly documents this pre-fix behavior.

### Impact Explanation

**Contract execution flow breakage / nonce manipulation.** The invariant "a rejected action must not mutate state" is violated: the sender's access-key nonce (or gas-key nonce at a specific `nonce_index`) is permanently incremented in the trie even though no receipt was spawned and no value was transferred. An attacker (or a malicious relayer) who knows the sender's key permissions can craft a `DelegateAction` with `deposit = 1 yoctoNEAR`, a matching `receiver_id`, and an allowed method name, causing the sender's nonce to be consumed without any action executing. Repeated submissions burn successive nonces. For gas keys with a finite `num_nonces`, all nonce slots can be exhausted, permanently disabling the key without the key owner's consent.

### Likelihood Explanation

Low-to-medium. The bug is active only on nodes running protocol version 83 or 84 (between `MIN_SUPPORTED_PROTOCOL_VERSION = 83` and the fix at v85). The mainnet network has been at v86 since the scheduled upgrade, so the fix is live on mainnet. However, the buggy code path remains in the binary and is exercised for any chunk whose `current_protocol_version` is 83 or 84 (e.g., during a protocol upgrade transition window or on a network that has not yet upgraded past v84). The trigger requires only a valid signed `DelegateAction` submitted through any relayer — no privileged access is needed.

### Recommendation

The fix is already present and gated by `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError` at protocol version 85. No additional code change is needed for networks running v85+. For completeness, the legacy fallthrough path (lines 642–649) could be removed once `MIN_SUPPORTED_PROTOCOL_VERSION` is raised above 85, eliminating the dead code and the risk of future regressions.

### Proof of Concept

**Setup (protocol version 84, pre-fix):**

1. Alice holds account `alice.near` with a `FunctionCallPermission` access key:
   - `receiver_id = "token.near"`, `method_names = []` (any method allowed), `allowance = None`.
   - Current nonce = N.

2. Alice signs a `DelegateAction`:
   - `sender_id = "alice.near"`, `receiver_id = "token.near"`, `nonce = N+1`
   - Inner action: `FunctionCall { method_name: "ft_transfer", deposit: 1 yoctoNEAR, gas: 5 Tgas }`

3. Relayer submits the outer `SignedTransaction` wrapping this `DelegateAction`.

**Execution trace (pre-v85):**

- `validate_delegate_action_key` is called.
- `deposit = 1 > 0` → `result.result = Err(DepositWithFunctionCall)`. No early return.
- `receiver_id "token.near" == permission.receiver_id "token.near"` → no `ReceiverMismatch`, no early return.
- `method_names` is empty → no `MethodNameMismatch`, no early return.
- Nonce update block: `access_key.nonce = N+1`; `set_access_key(state_update, "alice.near", pk, &access_key)` — **trie write committed**.
- Returns `Ok(())`.
- `apply_delegate_action` sees `result.result.is_err()` → returns without spawning a receipt.

**Outcome:** Alice's nonce is now N+1 in the trie. No receipt was created. No value was transferred. Alice's nonce slot N+1 is permanently consumed. Repeating with nonces N+2, N+3, … exhausts Alice's usable nonce range without her consent. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
