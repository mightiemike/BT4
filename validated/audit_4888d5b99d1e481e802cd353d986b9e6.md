Based on my investigation, I found a directly analogous bug-class pattern in the near-wallet-contract's `inner_rlp_execute` function.

### Title
Wallet Contract pays relayer fee unconditionally before the user's underlying action executes, allowing a malicious relayer to collect payment for actions that never succeed - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs)

### Summary
The `near-wallet-contract` (the reference contract deployed to ETH-implicit / global-contract accounts so that Ethereum-signed transactions can be relayed onto NEAR, see `runtime/near-wallet-contract/src/lib.rs`) computes a relayer `tx_fee` from the signed Ethereum transaction and, for base-token and emulated ERC-20 transfers, unconditionally schedules a transfer of that fee to the relayer (`predecessor_account_id`) *before* the wallet's own action (the transfer/ERC-20 call the user actually signed) has been attempted or confirmed to succeed.

### Finding Description
In `parse_rlp_tx_to_action` (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:83-166`), once the fee is computed and the transaction is classified as `EOABaseTokenTransfer` or `ERC20Transfer`, `inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-411`) immediately creates a refund promise: [1](#0-0) 
This `env::promise_batch_action_transfer(refund_promise, *fee)` call is fired synchronously in the same function invocation that later, separately, schedules the actual user action (a native Transfer, or a `storage_balance_of`→callback→`ft_transfer` chain for ERC-20) via `action_to_promise` / the ERC-20 storage-check-and-transfer promise chain (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:412-471`). The refund promise and the main-action promise are two **independent, unlinked promises** batched from the same receipt — NEAR provides no atomicity between sibling promises spawned in one function call. If the main action later fails (e.g., the ERC-20 `ft_transfer` reverts because the receiver is unregistered and `storage_deposit` handling in the callback chain fails, gas runs out in the callback, or the target contract behaves unexpectedly for a specific fee/amount combination), the relayer refund promise created earlier is unaffected and still executes to completion, crediting the relayer's account.

This mirrors the Putty root cause precisely: an unconditional "premium" payment (the relayer fee, paid up front and un-gated on success) is decoupled from the "exercise" step (the user's real transfer/ERC-20 action) whose success is not guaranteed, giving the party who receives the premium (the relayer) no incentive to ensure completion, and — because promises are independent siblings rather than causally dependent — there is no rollback that claws back the fee if the main action fails.

### Impact Explanation
A malicious or careless relayer can be paid the fee, extracted directly from the user's ETH-implicit wallet balance, for an Ethereum-emulated transfer that never actually delivers funds to the intended recipient (because the paired promise fails independently). This is unauthorized value movement out of the user's account with no compensating benefit, directly matching "concrete unauthorized value movement" in the rules. Because the wallet contract is the reference implementation used for all ETH-implicit accounts on NEAR (deployed as a global contract per `runtime/near-wallet-contract/src/lib.rs:69-105`), this affects any unprivileged relayer-submitted transaction against any ETH-implicit account.

### Likelihood Explanation
The `nonce`-increment logic explicitly acknowledges only replay risk, not fee/settlement atomicity: comments at lines 350-365 and 389-408 reason about "faulty relayer" bans and nonce handling but never address the case where the paired action fails independently of the refund. The ERC-20 path in particular routes through an extra `storage_balance_of` cross-contract call and callback (`lib.rs:433-458`) before the transfer is attempted, widening the window in which the transfer can fail for reasons unrelated to the fee promise (e.g., insufficient gas in the callback, target FT contract quirks, `storage_deposit` requirements not met) while the fee has already been irrevocably promised to the relayer in the same top-level call.

### Recommendation
Chain the relayer-fee transfer as a `.then()` continuation of the main action's promise (or execute it from within `rlp_execute_callback` after inspecting the `PromiseResult` of the main action), so the fee is only paid out if the main action succeeds. Alternatively, retain the fee in escrow and refund it to the relayer only from the existing `rlp_execute_callback`, conditioned on `ExecuteResponse.success`.

### Proof of Concept
Conceptual sequence (cannot be executed without full protocol/test harness access, but derivable from the code):
1. Relayer submits an RLP-encoded Ethereum ERC-20 `transfer(receiver, amount)` transaction, targeting an unregistered NEP-141 receiver, with a legitimate `max_fee_per_gas * gas_limit` fee.
2. `inner_rlp_execute` → `parse_rlp_tx_to_action` classifies it as `ERC20Transfer { fee, .. }`, and immediately issues `promise_batch_action_transfer(refund_promise, fee)` to the relayer [2](#0-1) .
3. Separately, the code schedules `storage_balance_of` → callback → (attempted) `ft_transfer` [3](#0-2) ; if this chain fails (e.g., callback runs out of gas, or `storage_deposit` isn't funded so the eventual `ft_transfer` panics on an unregistered account), the ERC-20 transfer never completes.
4. The relayer's fee transfer from step 2 already succeeded independently and is not rolled back — the relayer is paid for a transfer that did not happen.

I could not find any code that links these two promises causally or reverts the fee promise on failure of the main action; this is a plausible, though not runtime-verified (no test harness execution performed), instance of the same "unconditional payment decoupled from unguaranteed settlement" bug class described in the Putty report.
