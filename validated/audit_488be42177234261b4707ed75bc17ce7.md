Found a valid analog. `TransactionRecord::is_validatable` explicitly documents that a "rejected transaction" *is* validatable, meaning a `Rejected` L1Handler transaction can be re-validated and re-included in a later block — the exact same class of bug as the `RFPSimpleStrategy::_distribute` issue, where a status change to a terminal/negative state (`Rejected`) is not checked before the item is allowed to proceed again.

### Title
Rejected L1Handler transactions remain validatable/proposable and can be re-executed after a prior block rejected them - (File: `crates/apollo_l1_events/src/transaction_record.rs`)

### Summary
`TransactionRecord::is_validatable` (and correspondingly `is_proposable`) does not exclude the `Rejected` state, so an L1Handler transaction that was rejected during execution of one proposal (`mark_rejected`, called from `TransactionManager::commit_txs`) can still be validated and re-included in a subsequent proposal, and its `Pending`-only check in `get_txs`/`maintain_indices` does not prevent it from being fed to the batcher again via `validate_tx`.

### Finding Description
The `RFPSimpleStrategy` bug pattern is: a payload transitions to a rejected/blocked status, but a downstream "distribute/execute" path doesn't check for that status and processes the item anyway.

The same pattern exists in the L1 events provider's transaction lifecycle:
- When a block containing an L1Handler transaction is committed but the transaction itself is rejected during execution (e.g. reverted/excluded by the bouncer), `TransactionManager::commit_txs` calls `record.mark_rejected()`, setting `state = TransactionState::Rejected`. [1](#0-0) 
- `TransactionRecord::mark_rejected` sets the state to `Rejected` and a `rejected` flag, with an explicit comment that "double reject not currently checked." [2](#0-1) 
- However, `is_validatable()` — the gate used by `TransactionManager::validate_tx` to decide whether a validator should accept an L1Handler transaction proposed by the block builder — only excludes `Committed`, `Cancelled`, and `Consumed` states. It explicitly documents (in its own doc comment) that a rejected transaction is validatable: [3](#0-2) 
- `TransactionManager::validate_tx` then only special-cases `Committed`, `CancelledOnL2`, and `Consumed` in its `match record.state` when `is_validatable()` is false — it has no arm for `Rejected` (that branch is unreachable given `is_validatable` allows `Rejected` through), meaning a `Rejected` record simply falls into the "validated" branch as if it were a fresh `Pending` transaction. [4](#0-3) 

### Impact Explanation
Because a proposer can still include an already-rejected L1Handler message in a new proposal, and a validating node will accept it (since `is_validatable` returns `true` for `Rejected`), a previously-rejected L1-to-L2 message can be executed and committed to L2 in a later block. This causes the same L1 message to be processed even though its earlier processing attempt was explicitly rejected/discarded by the sequencer, an unauthorized re-execution of a message from L1 the network already determined should not be applied in that form — directly analogous to the "rejected milestone can be executed" issue, and reachable purely from the normal L1-message → L1Handler-transaction → block-inclusion path (no privileged actor needed, since a Rejected state is entered as a normal consequence of ordinary execution/bouncer behavior on an ordinary L1 message).

### Likelihood Explanation
Likelihood depends on the reachability of `mark_rejected` for L1Handler transactions in the first place (e.g. via bouncer exclusion of the tx during block-closing), which is a normal, expected code path (`commit_txs` accepts a `rejected_txs` list precisely to record this). Once a transaction enters `Rejected`, every subsequent `validate_tx`/`get_txs` cycle treats it identically to `Pending`, so re-proposal is deterministic, not a race condition.

### Recommendation
Update `TransactionRecord::is_validatable` (and `is_proposable`, used by `maintain_indices`/`get_txs`) to explicitly exclude `TransactionState::Rejected`, matching the doc comment's stated intent versus its actual implementation. Add the missing `Rejected` arm to `TransactionManager::validate_tx`'s match statement (returning an appropriate `InvalidValidationStatus`, e.g. `AlreadyRejected`), and decide/implement an explicit mechanism (if desired) for how/when a `Rejected` L1Handler transaction can become proposable again (e.g. only after being re-scraped as a fresh event), rather than allowing it silently by omission.

### Proof of Concept
1. An L1Handler transaction `tx1` is added via `add_tx` and becomes `Pending`, entering the proposable index. [5](#0-4) 
2. `tx1` is proposed in block N via `get_txs`, executed by the blockifier, but rejected (e.g., reverted/excluded from bouncer), so at block N's commit, `commit_block` classifies it into `rejected_txs`, and `TransactionManager::commit_txs` calls `mark_rejected()`, setting `state = Rejected`. [6](#0-5) 
3. In block N+1, a (possibly malicious or simply unpruned) proposer includes `tx1` again in its proposal (nothing in `get_txs`'s `Pending`-only assertion prevents constructing/forwarding it manually via the consensus `ValidateTransactionProvider` path since validation, not proposal-side filtering, is the actual gate for validators).
4. The validating node calls `L1EventsProvider::validate(tx1_hash, N+1)` → `TransactionManager::validate_tx` → `record.is_validatable()` returns `true` (since state is `Rejected`, none of `is_committed`/`is_cancelled`/`is_consumed` apply) → `ValidationStatus::Validated` is returned. [7](#0-6) 
5. The block builder adds `tx1` to the block via `add_txs_to_block`, and it is re-executed and potentially committed to L2, despite having been explicitly rejected in block N.

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

    pub fn commit_txs(
        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],
    ) {
        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);
            self.with_record(tx_hash, |r| r.mark_committed()).unwrap();

                 sync commits with empty rejected_txs, and records are only removed via L1 \
                 cancellation/consumption, which can't race a block.",

        }

    pub fn add_tx(
        &mut self,
        tx: L1HandlerTransaction,
        block_timestamp: BlockTimestamp,
        scrape_timestamp: UnixTimestamp,
    ) {
        let tx_hash = tx.tx_hash;
        // If exists, return false and do nothing. If not, create the record as a HashOnly payload.
        let is_new_record = self.create_record_if_not_exist(tx_hash);
        // Replace a HashOnly payload with a Full payload. Do not update a Full payload.
        // A hash only payload can come from catching up from state sync, and then updated by
        // add_events from the scraper. However, if we get the same full tx twice (from the scraper)
        // it could indicate a double-scrape, and may cause the tx to be re-added to the proposable
        // index.
        self.with_record(tx_hash, move |record| match &record.tx {
            TransactionPayload::HashOnly(_) => {
                if !is_new_record {
                    info!(
                        "Transaction {tx_hash} already exists as a HashOnly payload. It was \
                         probably gotten via state sync component, and is now updated with a Full \
                         payload."
                    );
                }
                record.tx.set(tx, block_timestamp, scrape_timestamp);
                // Counts the HashOnly -> Full transition, regardless of whether the HashOnly
                // was just created here or pre-existed from state sync.
                L1_MESSAGE_SCRAPER_L1_HANDLER_TX_COUNT.increment(1);
            }
            TransactionPayload::Full { tx: _, created_at_block_timestamp: _, scrape_timestamp } => {
                warn!(
                    "Transaction {tx_hash} already exists as a Full payload, scraped at \
                     {scrape_timestamp}. This could indicate a double scrape. Ignoring the new \
                     transaction."
                );
            }
        });
    }
