### Title
Rescue-funds path lets caller bind an arbitrary PRC20/asset to a stuck UTX, causing outbound to instruct release of the wrong token - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
`AttachRescueOutboundFromReceipt` builds a `RESCUE_FUNDS` outbound from a `RescueFundsOnSourceChain` event that is emitted by `UniversalGatewayPC` "when a user initiates a rescue" [1](#0-0) . The `prc20` field inside that event is fully attacker-controlled (it is just an address topic supplied by whoever calls the gateway's rescue entrypoint), yet the keeper uses it, unchecked against the asset that was actually part of the original stuck `UniversalTx`, to resolve the external asset that TSS/validators will be told to release.

### Finding Description
`AttachRescueOutboundFromReceipt` looks up the original UTX purely by `universalTxId` from the event, verifies eligibility (deposit failed / auto-revert reverted), and then resolves the asset to hand back to the recipient solely from `event.PRC20`: [2](#0-1) 

Nowhere is `event.PRC20` cross-checked against `originalUtx.InboundTx.AssetAddr` (the token that was actually deposited/locked for that specific UTX). The resulting outbound is built as: [3](#0-2) 

Here `Amount` is copied verbatim from `originalUtx.InboundTx.Amount` (denominated in the *original* token's unit), while `ExternalAssetAddr`/`Prc20AssetAddr` are derived from whatever `event.PRC20` the caller chose to pass. This outbound is queued in `PendingOutbounds` and later signed/broadcast by TSS/UVs exactly like any other outbound — the finalization path (`FinalizeOutbound` / `handleFailedOutbound` / `handleSuccessfulOutbound` in `x/uexecutor/keeper/outbound.go`) trusts the `ExternalAssetAddr`/`Amount` fields that were attached here; it performs no independent re-derivation from the original inbound. Honest validators observing/signing the rescue outbound have no way to detect that the token field does not match the token that was actually locked for that UTX, because the on-chain `OutboundTx` record itself already carries the mismatched mapping.

This is a direct structural analog of the reported [H01] bug class: a "rescue" code path that is supposed to be scoped/bound to a specific asset instead performs an unconstrained cross-asset operation because a required binding check (here: PRC20 == the UTX's original locked asset) is missing, rather than the reported case of an unrelated defensive balance check reverting things it shouldn't.

### Impact Explanation
An unprivileged attacker who owns any of their own stuck UTXs (a deposit that legitimately failed, or a non-CEA inbound whose auto-revert reverted) can call the gateway's rescue function specifying an arbitrary `prc20` address instead of the token that was actually associated with that UTX. This produces an `OutboundTx` that instructs the source-chain gateway/TSS to release `originalUtx.InboundTx.Amount` units of a completely different token to the recipient bound to that UTX. Depending on decimal/value differences between the real locked token and the attacker-chosen token, this can result in unauthorized release of protocol/escrow-held funds of an unrelated PRC20/token pair — i.e., corruption of token mapping and unauthorized release of funds, both explicitly in scope under the Registry/Accounting and Universal Execution impact categories.

### Likelihood Explanation
The rescue path is reachable by any ordinary user through the normal `rescueFunds`-style call on `UniversalGatewayPC`; the only preconditions are that the caller has a UTX eligible for rescue (failed CEA deposit, or reverted non-CEA auto-revert) and knows/controls the `universalTxId`. Both are achievable through normal, unprivileged interaction with the bridge (e.g., deliberately causing a deposit to fail with a low-value token, then invoking rescue with a high-value `prc20`). No validator, relayer, or admin compromise is required — honest UVs and TSS members simply process the `OutboundTx` fields as attached.

### Recommendation
In `AttachRescueOutboundFromReceipt`, validate that `event.PRC20` matches the PRC20 token config actually associated with `originalUtx.InboundTx.SourceChain` + `originalUtx.InboundTx.AssetAddr` before building the rescue outbound (i.e., derive `ExternalAssetAddr`/`Prc20AssetAddr` strictly from the original inbound's stored asset instead of from attacker-supplied event data), rejecting the rescue if the caller-provided `prc20` does not match.

### Proof of Concept
1. Attacker submits a CEA inbound depositing token A (e.g., a low-value token) with amount `N`, engineered/observed to fail on deposit (`PcTx[0].Status == "FAILED"`), producing a stuck UTX `U` whose `InboundTx.AssetAddr = TokenA`.
2. Attacker calls the gateway's rescue entrypoint for UTX `U`, but passes `prc20 = PRC20_B` (the PRC20 representation of a high-value token B) instead of PRC20_A.
3. `AttachRescueOutboundFromReceipt` decodes the event, confirms `U` is eligible (deposit failed), and — without checking that `PRC20_B` corresponds to `TokenA` — resolves `tokenCfg` for `PRC20_B` and builds an outbound with `Amount = N` (originally denominated for Token A) and `ExternalAssetAddr = TokenB` [4](#0-3) .
4. This outbound enters `PendingOutbounds`; once honest UVs reach quorum on it, TSS releases `N` units of Token B from the source-chain escrow to the attacker-controlled recipient — a token the attacker never actually deposited.

Note: I could not locate the Solidity source of `UniversalGatewayPC`'s rescue entrypoint in the indexed content (only the Go-side ABI/event decoders and the keeper consumer were available), so I cannot fully confirm from source whether the contract itself imposes any additional access control or on-chain PRC20 binding before emitting `RescueFundsOnSourceChain`. If such a binding exists there, it would need to be verified to fully confirm exploitability; a full audit of that contract via a Devin session with repository access is recommended to close this gap.

// event emitted by UniversalGatewayPC when a user initiates a rescue on the source chain.
type RescueFundsOnSourceChainEvent struct {
	UniversalTxId  string   // 0x-prefixed bytes32 — the original UTX whose funds are stuck
	PRC20          string   // 0x-prefixed address — PRC20 token whose counterpart is locked
	ChainNamespace string   // source chain namespace (e.g. "eip155")
	Sender         string   // 0x-prefixed address — user who initiated the rescue
	TxType         TxType   // always TxType_RESCUE_FUNDS
	GasFee         *big.Int // gas fee charged (in gas-token units)
	GasPrice       *big.Int // gas price on the source chain
	GasLimit       *big.Int // gas limit used for the rescue execution
}
