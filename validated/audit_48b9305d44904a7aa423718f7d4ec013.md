### Title
Signature-stripped transaction re-broadcast can poison the txID dedup cache and permanently block the legitimately-signed original from being processed - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.broadcastTransaction` inserts the transaction's `txID` (computed only from `raw_data` via `Sha256Hash.hash`, never covering the `signature` field) into `dbManager.getTransactionIdCache()` **before** the signature is actually validated in `Manager.pushTransaction`. An attacker who observes a victim's pending transaction (e.g. via the anonymous `getTransactionListFromPending` HTTP/gRPC API) can rebroadcast a signature-stripped/corrupted clone with the identical `txID` first; the cache entry is created and never removed even though the clone subsequently fails signature validation, causing the later legitimately-signed original to be rejected as `DUP_TRANSACTION_ERROR` without ever being validated or executed.

### Finding Description
`TransactionUtil.getTransactionId` / `TransactionCapsule.getTransactionId` derive the transaction ID purely from `raw_data`, independent of the `signature` list, as documented in the question's premise. In `Wallet.broadcastTransaction`: [1](#0-0) 

the code checks and **populates** `dbManager.getTransactionIdCache()` keyed solely on this `txID`, before `dbManager.pushTransaction(trx)` is invoked at line 575, which is where the actual signature check (`trx.validateSignature`) occurs: [2](#0-1) 

If signature validation fails (e.g., because the attacker stripped or corrupted the signature list), `pushTransaction` throws `ValidateSignatureException`, which is caught in `broadcastTransaction`'s catch block and converted to a `SIGERROR` response: [3](#0-2) 

Critically, none of the exception handlers remove the just-inserted `txID` entry from `transactionIdCache`. The entry persists until the cache's own expiry policy evicts it (an hour-scale TTL in the test setup). Consequently, when the victim's properly-signed original transaction (same `raw_data`, hence the same `txID`) is later submitted through `broadcastTransaction`, the cache check at line 559 finds the `txID` already present and immediately returns `DUP_TRANSACTION_ERROR` — the legitimate transaction never reaches `pushTransaction`, `validateSignature`, or any actuator logic, regardless of how well-formed and properly signed it is.

The attacker needs the victim's `raw_data` before the original propagates/confirms. This is obtainable without any peer/witness/node-operator privilege via the publicly exposed pending-transaction query API (`getTransactionListFromPending`, exposed over both HTTP and gRPC per `FullNodeHttpApiService`/`RpcApiService`), satisfying the "unprivileged attacker" constraint without requiring P2P peer access or MITM.

None of the standard defenses stop this: `TransactionCapsule.validateSignature` and permission/weight checks only run *after* the cache is poisoned, `ForkController` gates and energy/bandwidth accounting are irrelevant to a rejected-before-execution request, and there is no `txID + signature` composite key or any cache-removal-on-failure logic.

### Impact Explanation
This is a targeted, repeatable Denial-of-Service against a specific victim's operation (e.g. `AccountPermissionUpdateContract`, vote, or delegate transaction): the attacker can prevent the victim's legitimately signed transaction from ever being accepted for as long as the poisoned cache entry survives, by pre-emptively occupying the `txID` slot with an unsigned/invalid clone. This matches TRON bounty's "DoS via the TRON protocol implementation" / RPC-API impact class — it is a state-independent, low-cost griefing vector that blocks a specific owner-controlled operation without requiring any compromise of keys or consensus.

### Likelihood Explanation
- Cost to attacker: essentially free — a single anonymous `broadcastTransaction` gRPC/HTTP call with a corrupted signature list, no need to pay signature verification cost, no bandwidth/energy is consumed since the transaction fails before execution.
- Precondition: attacker must learn the victim's pending `raw_data` and race to submit the corrupted clone before the original is processed. This is achievable via the public `getTransactionListFromPending` endpoint (no special role required) combined with timing (the attacker must submit before the legit one arrives at the queried node, or at each node it wants to block).
- Repeatable per targeted transaction; the effect is local to whichever node(s) received the poisoned entry first (in a distributed network the attacker would need to race broadcast propagation across many nodes to fully block acceptance network-wide, which lowers reliability but does not eliminate the local-node DoS effect).

### Recommendation
Do not insert `txID` into `transactionIdCache` until after `pushTransaction` (specifically signature validation) succeeds, or explicitly remove/invalidate the cache entry in every catch branch of `broadcastTransaction` (especially `ValidateSignatureException`, `ContractValidateException`, etc.) so that failed submissions cannot occupy the txID slot. Alternatively, key the dedup cache on `txID` plus a fingerprint of the actual verified signature/owner set rather than `raw_data` hash alone.

### Proof of Concept
```java
// JUnit-style integration test sketch (framework/src/test/java/org/tron/core/WalletMockTest.java style)

@Test
public void testTxIdCachePoisoningBlocksLegitTx() throws Exception {
  Wallet wallet = new Wallet();
  // victim's real transaction, with valid raw_data for AccountPermissionUpdateContract
  Transaction rawVictimTx = buildAccountPermissionUpdateTx(victimOwnerAddress);

  // Attacker clones raw_data but clears/corrupts signatures
  Transaction attackerClone = rawVictimTx.toBuilder().clearSignature().build();

  // Setup real (non-mocked) dbManager/tronNetDelegate with trxCacheEnable=true
  // 1. Attacker broadcasts corrupted clone first
  GrpcAPI.Return attackerResult = wallet.broadcastTransaction(attackerClone);
  assertEquals(GrpcAPI.Return.response_code.SIGERROR, attackerResult.getCode());

  // 2. Victim signs and broadcasts the legitimate tx with identical raw_data (same txID)
  Transaction signedVictimTx = signWithVictimKey(rawVictimTx, victimPrivateKey);
  GrpcAPI.Return victimResult = wallet.broadcastTransaction(signedVictimTx);

  // BUG: victim's properly signed tx is rejected as duplicate instead of being processed
  assertEquals(GrpcAPI.Return.response_code.DUP_TRANSACTION_ERROR, victimResult.getCode());
}
```
Expected (buggy) result: `victimResult` returns `DUP_TRANSACTION_ERROR` even though the victim's transaction was never actually processed or persisted, demonstrating the owner-op DoS via txID cache poisoning independent of signature validity.
