### Title
Unbounded request body buffering before HMAC/signature validation causes memory-exhaustion DoS in webhook/flow/fulfillment-service authentication handlers - (File: packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts)

### Summary
The CryptoNote report describes a remote DoS where a peer could send an unbounded amount of data that the node would fully buffer/process *before* any validation, exhausting memory. The `shopify-app-remix`/`shopify-app-react-router` webhook (and flow/fulfillment-service) authentication handlers exhibit the same root-cause pattern: they call `await request.text()` to read the entire raw HTTP body into memory unconditionally, before any HMAC/signature check is performed, and with no size limit enforced by the library.

### Finding Description
`authenticateWebhookFactory` reads the full request body as a string as the very first data-processing step, prior to calling `api.webhooks.validate`: [1](#0-0) 

The same unauthenticated-buffer-then-validate pattern exists in the `flow` and `fulfillment-service` handlers (`request.text()` called before signature/HMAC checks), and is duplicated verbatim in the `shopify-app-react-router` package.

Downstream, `webhooks.process`/`webhooks.validate` in `@shopify/shopify-api` only checks `rawBody.length` for emptiness and then computes an HMAC over the already-fully-buffered string: [2](#0-1) 

Nowhere in this call path — from the public HTTP entry point (`request.text()`) through `validateHmacFromRequestFactory` — is a maximum body size enforced. The library's own webhook docs explicitly delegate body-size handling to the app developer's choice of body parser, but the `shopify-app-remix`/`shopify-app-react-router` fetch-based handlers bypass any such parser and call `request.text()` directly: [3](#0-2) 

Webhook (and flow / fulfillment-service) endpoints are, by design, public unauthenticated HTTP endpoints reachable by anyone who knows or guesses the route (they must be reachable by Shopify without a prior session). An anonymous attacker can therefore POST an arbitrarily large body to these routes; the full body is buffered into memory (`request.text()`) before the HMAC comparison ever runs, so the "authentication" step provides no protection against the resource-exhaustion cost of ingesting the payload — mirroring the CryptoNote flaw where unbounded attacker-supplied data was processed/allocated before being validated.

### Impact Explanation
A remote, completely unauthenticated attacker can repeatedly send very large HTTP bodies to any app's `/webhooks` (or flow/fulfillment-service) route. Each request forces the Node/edge runtime to allocate memory proportional to the attacker-chosen body size before the HMAC check rejects it. With concurrent or repeated large requests, this can exhaust process memory or cause excessive GC pressure, resulting in denial of service for the merchant app — impacting all shops served by that app instance. This matches the class of "Uncontrolled Resource Consumption" in the reference report.

### Likelihood Explanation
High likelihood: the vulnerable route is public by construction (webhook/flow/fulfillment-service endpoints must be reachable without a session), requires no credentials, no valid HMAC, and no prior interaction — a single anonymous POST with a large payload is sufficient to trigger the resource cost. The only mitigating factor is any body-size limit imposed by the surrounding hosting infrastructure (e.g., a reverse proxy or serverless platform), which is outside the library's control and not guaranteed in self-hosted Node deployments.

### Recommendation
Enforce a maximum allowed request body size before calling `request.text()` (or stream-read with an early abort once a size threshold is exceeded) in `authenticateWebhookFactory`, `authenticate` (flow), and `authenticate` (fulfillment-service) in both `shopify-app-remix` and `shopify-app-react-router`. Reject oversized requests with an early `413 Payload Too Large` response prior to buffering the full body. Consider adding this same safeguard inside `@shopify/shopify-api`'s `webhooks.process`/`webhooks.validate` so all adapters (Express, Cloudflare Workers, etc.) benefit consistently, rather than relying solely on app-provided body parsers.

### Proof of Concept
1. Deploy an app using `shopify-app-remix` (or `shopify-app-react-router`) with a webhook route wired to `authenticate.webhooks`.
2. As an anonymous client (no Shopify HMAC secret, no session), send: `POST /webhooks HTTP/1.1` with a body of several hundred MB to several GB (chunked transfer or `Content-Length`).
3. Observe that `await request.text()` in `authenticate.ts` fully buffers the payload into memory before `api.webhooks.validate` runs and rejects it for an invalid HMAC — by which point the memory has already been consumed.
4. Repeat concurrently to exhaust the process's available memory, causing the app server to slow down, OOM-crash, or become unresponsive for all tenants.
