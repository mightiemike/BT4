### Title
Unbounded `UniversalPayload.GasLimit` accepted from attacker-controlled inbound payloads bypasses block/consensus gas invariants - ([File: x/uexecutor/keeper/evm.go])

### Summary
The zkSync report concerns `_getOverheadForTransaction` allowing computed overhead values (encoding length, pubdata size, computation gas) to exceed protocol-defined maximums (`BOOTLOADER_TX_ENCODING_SPACE`, `MAX_PUBDATA_PER_BLOCK`, `L2_TX_MAX_GAS_LIMIT`) because the transaction's user-supplied size/gas fields are never bound-checked before being used in metering math. The same *class* of bug — accepting an attacker-controlled numeric field into gas-accounting logic without an explicit upper-bound check — exists in how `UniversalPayload.GasLimit` flows from an inbound/CEA payload through `UniversalPayload.ValidateBasic()` [1](#0-0)  into `CallUEAExecutePayload`, which parses it and passes it directly as the EVM call's gas limit with no maximum-value check [2](#0-1) .

### Finding Description
`UniversalPayload.ValidateBasic()` only checks that `gas_limit`, `max_fee_per_gas`, `max_priority_fee_per_gas`, `value`, `nonce`, and `deadline` are valid non-negative integers — it does not enforce any upper bound (e.g., against a chain-wide max execution gas limit, block gas limit, or `math.MaxInt64`) [1](#0-0) .

This same unbounded value is later parsed directly from the string field via `SetString` and passed as the `*big.Int` gas limit argument to `k.evmKeeper.DerivedEVMCall` in `CallUEAExecutePayload` [2](#0-1) . There is no check that this value fits within `int64`/`uint64` (Go's `big.Int.Int64()`/similar conversions can silently truncate or the value can be arbitrarily large), nor any check against the node's/EVM module's configured maximum execution gas, analogous to zkSync's `L2_TX_MAX_GAS_LIMIT` check that was flagged as missing.

Separately, `CalculateGasCost` in `x/uexecutor/keeper/fees.go` computes `gasCost = effectiveGasPrice * gasUsed` using `receipt.GasUsed` (bounded by the actual EVM execution, so this particular multiplication is not directly attacker-inflatable) [3](#0-2) , and `DeductGasFeesFromReceipt` does check `gasUsedBig.Cmp(abiPayload.GasLimit) > 0` [4](#0-3) , but this check happens only *after* the EVM call has already been dispatched with the attacker-supplied gas limit — it does not prevent the initial call from being fed a gas limit that violates protocol invariants.

### Impact Explanation
Whether this is materially exploitable for fund loss, DoS, or consensus divergence is uncertain from the code reviewed:
- The actual EVM execution (`DerivedEVMCall`/Cosmos EVM module) almost certainly enforces its own block gas limit and would reject or cap a call whose gas limit exceeds the block's gas limit — this would make the missing upper-bound check in `ValidateBasic()` a defense-in-depth gap rather than a directly exploitable invariant violation, similar to how the zkSync issue itself was "partially resolved" by removing overhead entirely pending a proper fix.
- I was not able to verify, within the available index, whether `DerivedEVMCall`/`CallEVM` in the `cosmos/evm` dependency enforces a hard ceiling on the gas limit consistently across all honest-validator executions (i.e., whether an oversized `GasLimit` could cause different nodes to compute different results, get rejected inconsistently, or consume excessive resources before failing). This is a boundary of the current investigation and would need direct code-level verification of the `evmKeeper.DerivedEVMCall` implementation (likely vendored, not fully indexed here).

### Likelihood Explanation
Any unprivileged attacker can submit an inbound/CEA payload (via source-chain deposit + relayed inbound vote, or a `MsgExecutePayload`) with an arbitrarily large `gas_limit` string, since `ValidateBasic()` accepts any non-negative integer string for that field. Reaching this code path requires no privileged access — it is on the default inbound/payload-execution path exercised by `ExecuteInboundGas`, `ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`, and `ExecutePayloadV2`/`msg_execute_payload.go`, all of which call `CallUEAExecutePayload` with the user-supplied `GasLimit`.

### Recommendation
Add an explicit upper-bound check on `UniversalPayload.GasLimit` (and ideally `MaxFeePerGas`/`MaxPriorityFeePerGas`) in `UniversalPayload.ValidateBasic()` and/or `ValidateForExecution()`, capping it to a well-defined maximum consistent with the chain's configured max execution/block gas limit, mirroring the zkSync recommendation to check computed/declared values against protocol maximums before use. Additionally, verify at the `CallUEAExecutePayload` call site that the parsed `gasLimit` fits safely into the type expected by `DerivedEVMCall` and does not exceed the node's configured gas ceiling, rather than relying solely on downstream EVM module enforcement.

### Proof of Concept
Not independently verified end-to-end due to inability to inspect the vendored `evmKeeper.DerivedEVMCall`/Cosmos EVM gas-limit enforcement in this pass. Conceptually: submit an inbound (`FUNDS_AND_PAYLOAD` or `GAS_AND_PAYLOAD`) whose `UniversalPayload.GasLimit` is set to a very large numeric string (e.g., `"115792089237316195423570985008687907853269984665640564039457584007913129639935"`, i.e., `2^256-1`). `ValidateBasic()` accepts it since it is a valid non-negative uint256 string [1](#0-0) ; `CallUEAExecutePayload` parses it with `big.Int.SetString` and forwards it unchecked to `DerivedEVMCall` [2](#0-1) . Whether this causes inconsistent honest-validator behavior, a panic/DoS during EVM gas metering, or is safely rejected by the downstream EVM keeper requires further investigation of that dependency, which is out of reach with the current index.
