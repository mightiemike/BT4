## Analysis

I found a concrete native analog to the "batch purchase failure due to one bad item" bug class in `BuildOutboundsFromReceipt`. This function iterates over EVM logs in a payload's execution receipt to extract multiple `UniversalTxWithdraw` outbound events, and its callers (`AttachOutboundsToExistingUniversalTx`, `CreateUniversalTxFromReceiptIfOutbound`) use its all-or-nothing result.

### Title
Single Malformed/Disabled Outbound Log Aborts Attachment of All Sibling Outbounds From the Same Payload Execution - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
A UEA/CEA payload can emit multiple `UniversalTxWithdraw` events in one EVM receipt (e.g., a payload that fans out to several destination chains in one call). `BuildOutboundsFromReceipt` decodes each log and, on the first one that fails (`IsChainOutboundEnabled` error, an outbound-disabled destination chain, or a `GetTokenConfigByPRC20` lookup miss), immediately `return nil, err`, discarding every outbound already parsed in earlier iterations of the loop. [1](#0-0) 

### Finding Description
The loop body decodes each log and returns early on error instead of skipping the bad entry and continuing: [2](#0-1) 

Both call sites propagate this error verbatim and never attach any of the outbounds that were already successfully decoded from earlier logs in the same receipt: [3](#0-2) 

This is invoked from the inbound execution flow right after a payload runs successfully — a payload that legitimately withdraws to several chains at once: [4](#0-3) 
and the equivalent gas+payload path: [5](#0-4) 

The bug-class parallel to the external report is direct: the BuyerAgent bug fails an entire batch purchase because one asset's external state (ownership/approval) is invalid; here, the entire batch of outbound events from one receipt fails to attach because one event's destination-chain/token config is invalid or disabled, even though the other outbounds in the same receipt are perfectly valid and independently attachable.

The trigger is unprivileged and user-reachable: any UEA/CEA payload deliverer (via `MsgExecutePayload`, gasless, "any user" authority) or any inbound whose payload calls a contract emitting multiple `UniversalTxWithdraw` events can construct a payload where one destination CAIP-2 chain is currently outbound-disabled, or one PRC20/token pairing has no registered `TokenConfig`. The attacker does not need to be a validator, TSS participant, or admin — they only need to control the payload/contract logic that emits the gateway events, which any external account can do by submitting a normal payload/transaction. [6](#0-5) 

### Impact Explanation
When this happens, `AttachOutboundsToExistingUniversalTx` returns an error which is captured only as `utx.RevertError` (a diagnostic string), and none of the outbounds — including fully valid ones destined for correctly configured chains — get attached to the UTX or written to `PendingOutbounds`: [7](#0-6) 

The PC-side effects (deposit, payload execution, EVM state changes, gas fee deduction) have already committed at this point — the payload really did run and really did emit the withdraw events on-chain — but the protocol-side bookkeeping that would let Universal Validators broadcast those withdrawals is silently dropped for the entire batch. This is a **permanent freezing of funds**: the legitimate outbound(s) in the batch are never indexed into `PendingOutbounds`, so UVs never sign/broadcast them via TSS, and the value that was supposed to leave via those outbounds is stuck with no recorded pending outbound and no automatic revert (this failure path only sets `RevertError`, it does not build a compensating revert outbound). This matches the "permanent freezing of user or protocol-controlled funds" and "unauthorized state transitions in universal execution flows" impact categories in scope.

### Likelihood Explanation
Reaching an outbound-disabled chain or missing token-config entry does not require any privileged access — an ordinary user constructs a payload/contract that emits a `UniversalTxWithdraw` event for a chain/token combination that the registry currently doesn't support (which can legitimately occur any time `uregistry` disables a chain or a token isn't yet configured, or when a payload targets a chain not yet whitelisted). Since `x/uregistry`'s configs are admin-curated and can change over time (chains get disabled, tokens get added/removed), any payload racing a config change, or any payload deliberately crafted to include one bad withdraw target alongside valid ones, reliably triggers the all-or-nothing failure. This requires no validator collusion, no dishonest node, and no external chain compromise — it is reachable purely from ordinary payload submission.

### Recommendation
Change `BuildOutboundsFromReceipt` to process each log independently: on a per-log decode/config error, log the failure, optionally attach a partial/failed marker or skip that specific event, and continue building the remaining valid outbounds instead of returning `nil, err` for the whole receipt. The valid, well-configured outbounds should still be attached to the UTX and indexed in `PendingOutbounds` so honest UVs can process them, while the invalid entry is surfaced via `RevertError`/logging for operator review, consistent with how other single-item failures elsewhere in this module already are recorded without discarding sibling work (e.g., the individual `execErr`/`payloadErr` handling in the same file).

### Proof of Concept
1. Deploy a UEA/CEA payload target contract whose single call emits two `UniversalTxWithdraw` events on `UniversalGatewayPC`: event A targeting a chain/token pair that is registered and outbound-enabled, and event B targeting a chain that has `IsOutboundEnabled = false` (or a PRC20 address with no matching `TokenConfig`).
2. Submit an inbound (`FUNDS_AND_PAYLOAD` or `GAS_AND_PAYLOAD`) whose payload calls this contract; get it to quorum via `MsgVoteInbound` from honest UVs.
3. Observe that `ExecutePayloadV2` succeeds and produces a receipt containing both logs, `AttachOutboundsToExistingUniversalTx` is then called.
4. In `BuildOutboundsFromReceipt`, the loop processes event A successfully (append to `outbounds`), then hits event B and returns `nil, err` immediately at line 56 of `create_outbound.go`.
5. Assert: `utx.OutboundTx` is empty (event A's valid outbound was never attached), `utx.RevertError` is set to the "outbound is disabled for chain ..." message, and no entry exists in `PendingOutbounds` for event A's outbound id — despite event A being fully valid and independently attachable. This demonstrates that a single malformed/disabled outbound in a batch of otherwise-valid outbounds permanently blocks all outbounds derived from that receipt.

func (k Keeper) AttachOutboundsToExistingUniversalTx(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	utx types.UniversalTx,
) error {
	outbounds, err := k.BuildOutboundsFromReceipt(ctx, utx.Id, receipt)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}

// CreateUniversalTxFromReceiptIfOutbound
// Creates a UniversalTx ONLY if outbound events exist in the receipt.
// Safe to call from ExecutePayload, EVM hooks
func (k Keeper) CreateUniversalTxFromReceiptIfOutbound(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalTxKey, err := k.BuildPcUniversalTxKey(ctx, pcTx)
	if err != nil {
		return errors.Wrap(err, "failed to create UniversalTx key")
	}

	outbounds, err := k.BuildOutboundsFromReceipt(ctx, universalTxKey, receipt)
	if err != nil {
		return err
	}

	if len(outbounds) == 0 {
		return nil
	}

	utx, err := k.CreateUniversalTxFromPCTx(ctx, pcTx)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}
