### Title
Missing reserved-address check in blockifier's contract-deployment path (unlike the Starknet OS) - (File: `crates/blockifier/src/execution/execution_utils.rs`)

### Summary
The Starknet OS explicitly forbids deploying a contract to any of the protocol's reserved system addresses (`ORIGIN_ADDRESS`, `BLOCK_HASH_CONTRACT_ADDRESS = 0x1`, `ALIAS_CONTRACT_ADDRESS = 0x2`, `RESERVED_CONTRACT_ADDRESS = 0x3`) via an explicit `assert_not_zero` check in `deploy_contract.cairo`. The Rust blockifier, which the sequencer uses to actually execute and admit transactions into blocks, performs no equivalent check anywhere in its deployment path (`execute_deployment`, `SyscallHintProcessor::deploy`, `DeployAccountTransaction::run_execute`). This mirrors the reported bug class of "missing validation of a critical address parameter" from the meebits report — except here the un-validated address is a protocol-reserved system address rather than a beneficiary, and the consequence is state-corruption/proving divergence rather than lost NFT proceeds.

using the reserved constants: [2](#0-1) 

This check is invoked from both the deprecated deploy syscall and the current deploy syscall in the OS program: [3](#0-2) [4](#0-3) 

In contrast, the Rust blockifier's deployment routine only checks that the destination address currently has no class deployed (`current_class_hash != ClassHash::default()`), and never compares the address against the reserved values: [5](#0-4) 

The `deploy` syscall implementation that feeds `execute_deployment` similarly performs no reserved-address check before computing/using the deployed address: [6](#0-5) 

And `DeployAccountTransaction::run_execute`, the entry point used for `DeployAccount` transactions submitted directly by any unprivileged user, likewise builds a `ConstructorContext` and calls `execute_deployment` with no address validation: [7](#0-6) 

`ContractAddress::validate()`, which is the only address-range check present in the API layer, only rejects the value `0x1` (`BLOCK_HASH_TABLE_ADDRESS`) and out-of-range values above the upper bound — it does **not** exclude `0x2` (`ALIAS_CONTRACT_ADDRESS`) or `0x3` (`RESERVED_CONTRACT_ADDRESS`), and in any case it is only invoked in the gateway's stateless validation for `sender_address` of Declare/Invoke transactions, not for computed deployment addresses: [8](#0-7) [9](#0-8) 

`ALIAS_CONTRACT_ADDRESS` (0x2) and `BLOCK_HASH_CONTRACT_ADDRESS` (0x1) are not cosmetic reservations — they back the stateful-compression alias mapping and the block-hash lookup table that the OS itself reads/writes during block building and state commitment (see `crates/apollo_starknet_os_program/.../state/aliases.cairo` and `state.cairo`, which reference these constants).

### Impact Explanation
If a transaction sender manages to have a `deploy` syscall or `DeployAccount` transaction resolve to one of these reserved addresses, the sequencer's blockifier (used for gateway validation, mempool admission, and block building) would happily execute the constructor and write class-hash/storage entries at that address — silently corrupting the storage backing the OS's block-hash table or alias mapping. When that same block is later re-executed by the Starknet OS (for STARK proving), the OS's `assert_not_zero` in `deploy_contract.cairo` would fail on the very same deployment, causing OS re-execution to diverge from/reject a block that the sequencer already built and propagated. This is exactly the "honest-node divergence" / "network unable to confirm new transactions" class of impact: a block accepted by the blockifier-driven sequencer can be un-provable by the OS, halting block finalization until manual intervention, and any writes made through the corrupted reserved-address storage would produce a wrong committed root/block hash relative to what the OS/State-commitment layer expects.

### Likelihood Explanation
Reaching this state requires the attacker to control the constructor-address computation (`salt`, `class_hash`, `constructor_calldata`, and possibly `deployer_address=0` via `deploy_from_zero`/`DeployAccount`) such that the Pedersen-hash-derived `contract_address` (see `calculate_contract_address` in `crates/starknet_api/src/core.rs:326-346`) lands exactly on `0x1`, `0x2`, or `0x3` out of a ~2^251 address space. This is computationally equivalent to a hash-preimage search and is not achievable by brute force with realistic resources today. This significantly limits the practical likelihood of an attacker triggering the divergence directly through hash grinding. The finding is nonetheless a genuine code-level omission: the Rust execution engine that the sequencer actually uses for admission/execution lacks a safety check that the Cairo re-execution/proving engine enforces, and the asymmetry could become directly exploitable if any other code path (e.g. future changes, special-cased addresses, or non-hash-based address assignment) allows attacker-influenced deployment addresses to coincide with these reserved slots.

### Recommendation
Add the same reserved-address check present in `deploy_contract.cairo` to the blockifier's Rust deployment path so both execution engines enforce identical constraints:
- In `crates/blockifier/src/execution/execution_utils.rs::execute_deployment`, reject `deployed_contract_address` if it equals `ContractAddress::default()` (origin), `BLOCK_HASH_TABLE_ADDRESS` (0x1), or the `ALIAS_CONTRACT_ADDRESS`/`RESERVED_CONTRACT_ADDRESS` values exposed via `OsContractAddresses` (`crates/blockifier/src/blockifier_versioned_constants.rs:1346-1365`).
- Apply the same check in `DeployAccountTransaction::run_execute` (`crates/blockifier/src/transaction/transactions.rs`) before invoking `execute_deployment`, since `contract_address()` there is also attacker-influenced.
- Ensure the check happens before any state is written, mirroring the OS's placement of the assertion prior to `dict_update`.

### Proof of Concept
Not concretely demonstrable here because triggering the divergence requires inverting the Pedersen-based `calculate_contract_address` function to land on one of `0x1`/`0x2`/`0x3` — a hash-preimage search infeasible to brute force. The finding is a static-analysis-level asymmetry: compare the assertion in [10](#0-9) 
against the complete absence of an equivalent check in [5](#0-4) 
and [7](#0-6) 
to confirm the omission.

/// Instantiates the given class and assigns it an address.
/// Returns the call info of the deployed class' constructor execution.
pub fn execute_deployment(
    state: &mut dyn State,
    context: &mut EntryPointExecutionContext,
    ctor_context: ConstructorContext,
    constructor_calldata: Calldata,
    remaining_gas: &mut u64,
) -> ConstructorEntryPointExecutionResult<CallInfo> {
    let strip_vm_frames = context.versioned_constants().strip_vm_frames_in_sierra_gas;
    // Address allocation in the state is done before calling the constructor, so that it is
    // visible from it.
    let deployed_contract_address = ctor_context.storage_address;
    let current_class_hash =
        state.get_class_hash_at(deployed_contract_address).map_err(|error| {
            ConstructorEntryPointExecutionError::new(
                EntryPointExecutionError::from(error)
                    .annotated(TrackedResource::CairoSteps, strip_vm_frames),
                &ctor_context,
                None,
            )
        })?;
    if current_class_hash != ClassHash::default() {
        return Err(ConstructorEntryPointExecutionError::new(
            EntryPointExecutionError::from(StateError::UnavailableContractAddress(
                deployed_contract_address,
            ))
            .annotated(TrackedResource::CairoSteps, strip_vm_frames),
            &ctor_context,
            None,
        ));
    }

impl ContractAddress {
    /// Validates the contract address is in the valid range for external access.
    /// The lower bound is above the special saved addresses and the upper bound is congruent with
    /// the storage var address upper bound.
    pub fn validate(&self) -> Result<(), StarknetApiError> {
        let value = self.0.0;
        let l2_address_upper_bound = Felt::from(*L2_ADDRESS_UPPER_BOUND);
