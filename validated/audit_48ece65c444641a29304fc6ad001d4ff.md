### Title
Missing tenant-isolation check in `tokenExchange()` — attacker-controlled `shop` is never cross-validated against session token's `dest` claim - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Summary
`tokenExchange()` decodes `sessionToken` only to validate its signature/`aud`/`exp`/`nbf`, but never checks that the token's `dest` claim matches the `shop` parameter used to build the `/admin/oauth/access_token` POST URL and the resulting `Session.shop`. In `shopify-app-remix`, the `shop` value fed into `tokenExchange` comes from `getShopFromRequest(request)`, which reads the `shop` query-string parameter directly off the incoming request — a value fully controlled by the client, independent of the signed `sessionToken`.

### Finding Description
`tokenExchange()` calls `decodeSessionToken(config)(sessionToken)` only for its side effect of verifying the JWT signature and `aud`, discarding the returned payload entirely: [1](#0-0) . The `shop` value used to build the request URL and later stored on the created `Session` (`cleanShop`) comes solely from the function's own `shop` parameter, sanitized with `sanitizeShop()` for format validity only — not cross-checked against the token's `dest` claim: [2](#0-1) .

`decodeSessionToken()` itself only validates signature, `aud`, `exp`, and `nbf` — it never enforces any relationship between `dest` and a caller-supplied shop: [3](#0-2) .

Critically, in `shopify-app-remix`, the `shop` passed into `tokenExchange` via `TokenExchangeStrategy.exchangeToken` originates from `sessionContext.shop`, and `getShopFromRequest()` simply reads the `shop` query parameter off the raw request URL with no cross-validation against the JWT: [4](#0-3) , and this flows straight into `api.auth.tokenExchange({sessionToken, shop, ...})`: [5](#0-4) .

By contrast, `shopify-app-express`'s `performTokenExchange` middleware derives `shop` directly from `payload.dest` rather than from any request parameter: [6](#0-5) , which happens to avoid the mismatch in that integration but demonstrates the core library function `tokenExchange()` provides no such guarantee itself — it is entirely dependent on the caller passing a consistent shop.

### Impact Explanation
Within the library, `createSession()` stores `shop: cleanShop` — the caller-supplied (potentially attacker-controlled) value, not the value derived from the verified JWT: [7](#0-6) . If Shopify's `/admin/oauth/access_token` endpoint at the attacker-specified shop's domain does not itself reject a `subject_token` minted for a different shop (this enforcement point is outside this codebase and cannot be verified here), the resulting session would be persisted under a shop the attacker does not administer, using an access token improperly correlated to the wrong tenant — a tenant-isolation violation. At minimum, this allows an attacker to force the library to issue OAuth token-exchange POST requests against arbitrary shop domains under their control input, independent of the shop the presented session token was actually issued for.

### Likelihood Explanation
Exploitability requires only that an attacker hold a valid session token for their own shop (trivial for any embedded-app end user) and be able to control the `shop` query parameter on a request to an app built on `shopify-app-remix`'s token-exchange strategy, which reads `shop` straight from the URL without cross-checking the JWT `dest`. The severity of the actual compromise depends on whether Shopify's backend OAuth endpoint independently enforces that the `subject_token`'s `dest` matches the shop being exchanged against — a check that occurs outside of this repository and could not be confirmed from the code alone, so the finding here is primarily a defense-in-depth gap in the library itself rather than an unconditionally exploitable takeover.

### Recommendation
In `tokenExchange()` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), capture the decoded payload and assert that `new URL(payload.dest).hostname` equals the sanitized `shop` before constructing the request or session, throwing an `InvalidJwtError`/`InvalidSession` error on mismatch — mirroring the safe pattern already used in `shopify-app-express`'s `performTokenExchange`, which derives shop solely from `payload.dest`. Apply the same fix (or always derive `shop` from `payload.dest` rather than request query parameters) in `shopify-app-remix`'s and `shopify-app-react-router`'s `TokenExchangeStrategy`.

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
