### Title
Unbounded per-request memory duplication in `ServletOutputStreamCopy.write(int)` lacks a size cap present in `BufferedResponseWrapper` - ([File: framework/src/main/java/org/tron/core/services/filter/ServletOutputStreamCopy.java])

### Summary
`CharResponseWrapper`, used by `HttpApiAccessFilter.doFilter` and `HttpInterceptor.doFilter`, wraps every HTTP API response in a `ServletOutputStreamCopy` that duplicates each byte into an in-memory `ByteArrayOutputStream copy` purely for byte-size metering, with no upper bound. This differs from the newer `BufferedResponseWrapper`, which explicitly enforces a `maxBytes` cap and sets an `overflow` flag. An attacker who can trigger a large HTTP API response (e.g. wide-range `GetBlockByLimitNext`, large `TriggerConstantContract` return data) causes the filter to hold a full duplicate copy of that response in memory for the request's duration, in addition to whatever buffering the underlying handler already performs.

### Finding Description
`HttpApiAccessFilter.doFilter` wraps the real `HttpServletResponse` in a `CharResponseWrapper` for every non-disabled endpoint: [1](#0-0) . `CharResponseWrapper.getOutputStream()`/`getWriter()` create a `ServletOutputStreamCopy` around the real stream: [2](#0-1) . `ServletOutputStreamCopy.write(int b)` writes the byte to both the real `outputStream` and an internal `copy` `ByteArrayOutputStream` initialized at 4096 bytes with no `MAX_RESPONSE_SIZE` enforcement (the field exists but is never checked): [3](#0-2) . `HttpInterceptor.doFilter` also wraps responses with the same `CharResponseWrapper` purely to read `getByteSize()` for metrics: [4](#0-3) . By contrast, `BufferedResponseWrapper` explicitly bounds buffered bytes via `maxBytes` and marks `overflow` instead of growing without bound: [5](#0-4) .

However, this does not amount to an unbounded-allocation DoS beyond what already exists: the bytes are still streamed through to the real `outputStream` as they're generated (not buffered-then-sent), so the extra memory cost is one extra copy of the response body concurrently alive during the request, roughly doubling peak memory for that single request/response — not an unbounded multiplier and not a leak beyond the request lifecycle (the `copy` buffer is garbage after the request completes). This is bounded by whatever caps already exist on response size from the underlying handler (e.g., block-range limits, energy/return-data limits for contract calls), any container-level response size limits, and the number of concurrent connections the server allows. I was not able to confirm within the available context whether `GetBlockByLimitNextServlet` and related handlers enforce a maximum block-range/response-size limit — grep results show block-limit-related constants (`BLOCK_LIMIT_NUM`) exist in `RpcApiService`/`NodeConfig`/`GetBlockByLimitNextServlet`, suggesting some bound is already applied at the handler layer, but I could not verify the exact numeric cap or confirm it fully bounds worst-case payload size.

### Impact Explanation
At most this causes each large response to consume roughly 2x memory (once in the servlet's normal write path, once in the extra `copy` buffer) for the duration of that single request. This is a magnitude/efficiency concern, not an unbounded-growth vulnerability, since the buffer size is capped by the size of a single response (which is itself bounded by other application-level query/response limits, container limits, and connection concurrency), and the buffer is released once the request completes. Sustained DoS would require the attacker to already be able to generate a large response and to do so at scale — a capability limited more by pre-existing endpoint-level range/size constraints and connection limits than by this specific code path.

### Likelihood Explanation
Exploitability strictly depends on unbounded (or excessively large) response sizes being reachable from an unprivileged client for real endpoints such as `GetBlockByLimitNextServlet`, `GetBlockByLimitNextOnSolidityServlet`/`OnPBFTServlet`, or `TriggerConstantContract`. Given the presence of `BLOCK_LIMIT_NUM`-style constants referenced in `RpcApiService`, `NodeConfig`, and `GetBlockByLimitNextServlet`, it appears the block-range endpoints already enforce a cap on the number of blocks returned per request, which would bound response size and thus bound the extra memory this bug introduces. Without being able to confirm the exact cap value and confirm there is no bypass, I cannot conclusively establish that an attacker can force truly excessive ("unbounded") response sizes through this path.

### Recommendation
Regardless of severity, align `ServletOutputStreamCopy`/`CharResponseWrapper` with the `BufferedResponseWrapper` pattern: enforce the already-declared `MAX_RESPONSE_SIZE` (or a configurable cap) in `write(int b)`/`write(byte[], int, int)`, and once exceeded, stop growing `copy` (e.g., record an overflow flag and report a saturated size to `getByteSize()`) rather than allowing indefinite growth tied to response size.

### Proof of Concept
Not applicable as a standalone high-severity finding: no JUnit/request-level PoC demonstrates genuinely unbounded growth — growth is bounded by the size of a single HTTP response body, which existing block-range/query limits appear to constrain. A PoC would need to first show a concrete, unbounded-response-size endpoint exists (e.g., a block-range endpoint that does not enforce `BLOCK_LIMIT_NUM`), which I could not confirm from available context; without that, this reduces to a code-quality/hardening observation rather than a demonstrable, scoped DoS.

class ServletOutputStreamCopy extends ServletOutputStream {

  private OutputStream outputStream;
  private ByteArrayOutputStream copy;
  private int MAX_RESPONSE_SIZE = 4096;

  public ServletOutputStreamCopy(OutputStream outputStream) {
    this.outputStream = outputStream;
    this.copy = new ByteArrayOutputStream(MAX_RESPONSE_SIZE);
  }

  @Override
  public void write(int b) throws IOException {
    outputStream.write(b);
    copy.write(b);
  }
