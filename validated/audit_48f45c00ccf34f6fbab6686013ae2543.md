### Title
Exchange creator can drain pool reserves via `ExchangeWithdrawActuator` down to near-zero, letting the Bancor-relay pricing formula be manipulated to freeze/exploit `ExchangeTransactionActuator` trading — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
The TRON `Exchange` (Bancor-style AMM) module has the same root-cause pattern as the Sandclock `forceUnsponsor()` bug: a privileged-but-still-user-level action (`ExchangeWithdrawActuator`, callable by whoever created the exchange, which any unprivileged account can do via `ExchangeCreateActuator`) can drive one side of the pool's reserve balance down to an arbitrarily small positive value with no minimum-reserve floor. This creates the same "near-zero denominator" condition that lets the AMM's pricing math (`ExchangeCapsule.transaction()`, backed by `ExchangeProcessor`/`SafeExchangeProcessor`) be manipulated with tiny inputs, producing extreme, attacker-controllable swings in output amounts and enabling a denial-of-service ("Not precise enough"/zero-quant reverts) against other unprivileged traders using `ExchangeTransactionActuator`.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` only rejects a withdrawal when the resulting balance would be exactly zero: [1](#0-0) 

and otherwise only checks that quantities are `> 0` and that the price-precision tolerance (`0.0001`) is satisfied: [2](#0-1) 

There is no minimum reserve/floor enforced anywhere in `ExchangeWithdrawActuator`, `ExchangeCapsule`, or `DynamicPropertiesStore` (only an upper bound, `getExchangeBalanceLimit`, exists, e.g. as used in `ExchangeTransactionActuator`): [3](#0-2) 

This mirrors exactly the reported Sandclock issue: `forceUnsponsor()` allowed draining `totalUnderlying()` down to a value disproportionate to `totalShares`, after which a tiny deposit could produce an extremely large/attacker-controlled share count. Here, an exchange creator can withdraw one token's balance down to `1` (or any tiny value) while `firstTokenBalance`/`secondTokenBalance` stay nonzero, satisfying all validation checks.

Once one reserve is reduced to a tiny value, every subsequent trade via `ExchangeTransactionActuator` calls `ExchangeCapsule.transaction()`: [4](#0-3) 

which is implemented with a Bancor-relay double/BigDecimal `pow()` formula that is highly sensitive to the ratio between `quant` and `balance`: [5](#0-4) [6](#0-5) 

With a near-zero reserve on one side, tiny `tokenQuant` inputs from unprivileged users produce wildly disproportionate `anotherTokenQuant` outputs (or `0`, or `ArithmeticException`/overflow that gets converted to a validate/execute failure): [7](#0-6) 

### Impact Explanation
This produces two concrete impacts on unprivileged users interacting through `ExchangeTransactionActuator`:
1. **Invalid-state / halt (DoS):** After the reserve skew, legitimate trades from other users can be systematically rejected (`anotherTokenQuant < tokenExpected` failing, or `anotherTokenQuant` rounding to `0`/`<=0`), effectively freezing the exchange pool for anyone but the manipulator, who can time trades around the skewed ratio.
2. **Settlement/price manipulation:** Because the relay formula is acutely sensitive near a near-zero balance, the creator (or a colluding actor observing the skewed pool) can execute trades at an economically unfair rate immediately after the withdrawal, extracting value from any counterparties who trade against the skewed pool before it re-equilibrates — the same "plant a bomb" dynamic called out in the original report.

This is a concrete accounting/pricing manipulation and availability issue on a market-style component reachable by any account, not a purely theoretical or trusted-role-only issue, since exchange creation itself is unprivileged (`ExchangeCreateActuator` is open to any account).

### Likelihood Explanation
Likelihood is moderate-to-high: creating an exchange and withdrawing nearly all of one side's balance requires only being the exchange's creator (trivial, since anyone can create one), and no protocol-level minimum-reserve check prevents it. The only friction is the `0.0001` precision-tolerance check in withdraw, which an attacker can trivially satisfy by choosing exact integer ratios.

### Recommendation
Enforce a protocol-level minimum reserve (analogous to the Sandclock fix) in `ExchangeWithdrawActuator.doValidate()`/`execute()`, e.g. require `firstTokenBalance - tokenQuant >= MIN_RESERVE` and `secondTokenBalance - anotherTokenQuant >= MIN_RESERVE` (in addition to the existing `== 0` check), where `MIN_RESERVE` is a chain-configurable dynamic property similar to `getExchangeBalanceLimit`. Additionally, consider bounding the maximum single-withdrawal percentage of a pool's reserve to prevent large, one-shot ratio distortions.

### Proof of Concept
1. Attacker account creates an exchange via `ExchangeCreateActuator` with `firstTokenBalance = 100_000_000`, `secondTokenBalance = 100_000_000`.
2. Attacker (creator) calls `ExchangeWithdrawActuator` withdrawing `firstTokenQuant = 99_999_999` of the first token; this passes all checks in `ExchangeWithdrawActuator.doValidate()`/`execute()` because `firstTokenBalance` after withdrawal is `1`, which is `!= 0`. [8](#0-7) 
3. Pool state is now `firstTokenBalance = 1`, `secondTokenBalance ≈ 1` (proportionally reduced).
4. Any subsequent unprivileged user calling `ExchangeTransactionActuator` against this pool now interacts with `ExchangeCapsule.transaction()` at an extreme balance ratio; even a `tokenQuant = 1` trade produces disproportionate or zero output via the Bancor relay formula, and further trades are rejected by `anotherTokenQuant < tokenExpected` or throw `ArithmeticException`, effectively freezing the exchange for other participants while the attacker can trade opportunistically around the skew. [9](#0-8)
