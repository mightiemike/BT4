### Title
Accruing every asset in a user's full position causes borrow/repay/collateral operations to revert when any single linked vault has `accrue` paused - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`borrow`, `collateral-add`, and `collateral-remove` in the market contract call `accrue-user-debts`/`accrue-user-collateral` over the **entire** set of a user's existing collateral and debt assets before acting on the single asset the user actually intends to touch. Each entry is accrued via `unwrap-panic` on `accrue-and-cache`, which in turn calls the target vault's `accrue`. If any one of those linked vaults has its `accrue` pause flag set (a state analogous to a "blocked"/"destroying" pool in the Kintsu report), the `unwrap-panic` fails and the entire transaction reverts - even though the paused asset is unrelated to the action the user is trying to perform.

### Finding Description
`borrow` fetches the caller's position and unconditionally accrues every asset in it before resolving prices: [1](#0-0) 

`collateral-remove` (when the user has debt) does the same over the full position: [2](#0-1) 

Both rely on `accrue-user-debts`/`accrue-user-collateral`, which `fold` over every list entry and `unwrap-panic` the result of `accrue-and-cache` for each asset: [3](#0-2) 

`accrue-and-cache` propagates any failure from `vault-accrue` via `try!`, so a failing vault call bubbles up and is then hit by the caller's `unwrap-panic`: [4](#0-3) 

Vault pause state includes an `accrue` flag, and the DAO's `set-pause-states` explicitly forces one final accrual before pausing accrue - confirming that once `accrue` is paused, subsequent calls to the vault's `accrue` are expected to be blocked going forward: [5](#0-4) 

Because `accrue-user-debts`/`accrue-user-collateral` iterate unconditionally over *all* of a user's linked assets rather than skipping ones whose vault is paused, a single paused vault (analogous to a "destroying"/"blocked" pool in the external report) poisons every other operation the user tries to perform, even on completely unrelated assets.

### Impact Explanation
Any user who holds even a small collateral or debt position in an asset whose vault has `accrue` paused by the DAO becomes unable to `borrow`, `collateral-add`, or `collateral-remove` on any other asset in their position, because the fold-based accrual step reverts via `unwrap-panic` before the actual intended operation is reached. This is a temporary denial of service that freezes the user's ability to manage unaffected collateral/debt positions for as long as the unrelated vault remains paused - a temporary freezing of funds/functionality.

### Likelihood Explanation
This requires the DAO to pause `accrue` on a vault (an intended, foreseeable operational action, e.g., during a migration or vault deprecation) while any user simultaneously holds a position that also touches another, unrelated asset. Given the multi-collateral/multi-debt design of the market, cross-asset positions are common, making this reachable under normal operational pausing, not requiring any privileged compromise beyond ordinary DAO pause administration.

### Recommendation
In `accrue-debt-asset` and `accrue-collateral-asset` (and their callers), check each linked vault's pause state before attempting to accrue it. If a vault's `accrue` is paused, skip accruing that specific asset (using its last cached/stored index) instead of propagating failure via `unwrap-panic`, so operations on unaffected assets in the same position can still proceed.

### Proof of Concept
1. User deposits collateral in Vault A and borrows against it, then also opens a small debt/collateral position in Vault B.
2. DAO calls `set-pause-states` on Vault B with `accrue: true` (a normal, sanctioned pause action) - [5](#0-4) .
3. User calls `borrow` on Vault A's asset. `borrow` fetches the full position (`get-position`) and calls `accrue-user-debts`/`accrue-user-collateral` over both Vault A and Vault B entries - [1](#0-0) .
4. The fold reaches Vault B's entry, calls `accrue-and-cache` → `vault-accrue`, which fails because `accrue` is paused; the `try!` failure is then hit by `unwrap-panic` in `accrue-debt-asset`/`accrue-collateral-asset` - [6](#0-5) .
5. The entire `borrow` transaction reverts, even though the user only intended to interact with Vault A, denying the user access to an otherwise healthy, unaffected position.
