### Title
Any unprivileged account can submit fee-free `MsgExecutePayload` transactions, bypassing gasless-tx admission controls meant only for bonded Universal Validators - (File: app/txpolicy/gasless.go)

### Summary
Push Chain's gasless-tx machinery (`app/txpolicy/gasless.go`, `app/ante/fee.go`, `app/cosmos/min_gas_price.go`, `app/ante/account_init_decorator.go`) was designed so that Universal Validators — a small, permissioned, bonded set — don't need to hold gas tokens just to vote on inbounds/outbounds/chain-meta/TSS events. However, `MsgExecutePayload`, whose authority is documented as "any" (i.e. any external account, not a bonded UV), is also placed on the same gasless allowlist. Because gasless-ness is determined purely by message type and not by the caller's privileged status, any unprivileged attacker can submit unlimited `MsgExecutePayload` transactions that skip both the minimum-gas-price check and fee deduction, and — for brand-new addresses — trigger free on-chain account creation via `AccountInitDecorator`.

### Finding Description
`IsGaslessTx` in [1](#0-0)  whitelists `MsgExecutePayload` together with the UV-only vote messages (`MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, `MsgVoteTssKeyProcess`, `MsgVoteFundMigration`) and `MsgMigrateUEA`. This whitelist is consumed identically by every gasless-aware ante decorator:

- `MinGasPriceDecorator` skips the FeeMarket minimum-fee check entirely for any gasless tx: [2](#0-1) 
- `DeductFeeDecorator` skips fee deduction (no balance required) for any gasless tx: [3](#0-2) 
- `AccountInitDecorator` creates a brand-new on-chain account for a gasless tx's signer, verifying only a lightweight signature over `account_number=0, sequence=0` before short-circuiting the remaining sig/fee decorators: [4](#0-3) 

Unlike `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta`/`MsgVoteTssKeyProcess`/`MsgVoteFundMigration`, which can only be usefully submitted by a bonded, tombstone-checked Universal Validator (enforced deep in the corresponding keeper logic, e.g. `IsChainInboundEnabled`/bonded-UV checks referenced in `x/uexecutor/README.md`), `MsgExecutePayload` is explicitly callable by "any" signer per the module's own documentation: [5](#0-4) . None of the gasless ante decorators distinguish "gasless because you're a permissioned UV doing protocol bookkeping" from "gasless because your message type happens to be on the same whitelist" — the check is purely `sdk.MsgTypeURL(msg)` membership, with no caller-identity gate at the ante layer.

This is the same class of bug as the reference report: a privileged bypass (`gasless == true`, analogous to the pre-`start` privileged window) was added to unblock a legitimate, narrow use case, but the corresponding code path failed to also verify that the caller actually belongs to the class the bypass was designed for.

### Impact Explanation
Because `MinGasPriceDecorator` and `DeductFeeDecorator` both defer wholesale to `IsGaslessTx`, an unprivileged external attacker can construct arbitrary `MsgExecutePayload` transactions — using freshly generated keypairs each time — and get them admitted into the mempool/block without paying any fee and without meeting the FeeMarket's minimum gas price. Each such transaction from a not-yet-existing address also causes `AccountInitDecorator` to persist a brand-new base account on-chain (state growth) at zero cost, since fee assessment is skipped entirely for the whole tx. This is a denial-of-service / resource-exhaustion vector reachable by any unprivileged party without relying on malicious validators, malicious peers, or any privileged control — it undermines the chain's built-in spam-resistance economics (min-gas-price + fee deduction) specifically for a message type that, by design, is open to arbitrary callers.

### Likelihood Explanation
High. No special access, stake, or validator status is required — an attacker only needs to generate keypairs and submit transactions with a syntactically valid `MsgExecutePayload` (it does not need to succeed at the application layer; `AccountInitDecorator`'s account creation and the fee-skip both occur in the ante pipeline, before/independent of whether `Keeper.ExecutePayload` itself ultimately errors out, e.g. on `"UEA is not deployed"`).

### Recommendation
Do not gate fee/min-gas-price/account-init bypass purely on message type. For message types like `MsgExecutePayload` that are callable by arbitrary unprivileged users, either:
- Remove them from the gasless allowlist and require normal fee payment, or
- Add an explicit caller-privilege check (e.g., restrict the free-tx bypass to signers who are bonded, non-tombstoned Universal Validators, similar to the checks already performed deep in the UV-vote keeper logic) before treating the transaction as gasless in the ante handler.

### Proof of Concept
1. Generate a new keypair `K` with no on-chain account and no funds.
2. Construct a `MsgExecutePayload` (any `UniversalAccountId`/`UniversalPayload`/`verification_data` — even a payload guaranteed to fail deep validation) signed by `K` with `account_number=0, sequence=0`, and `fee=0`.
3. Submit the tx. `MinGasPriceDecorator` and `DeductFeeDecorator` short-circuit via `IsGaslessTx` (`app/txpolicy/gasless.go`), so no minimum fee or balance is required. `AccountInitDecorator` creates the account for `K` on-chain for free.
4. Repeat with a fresh keypair per transaction, at no cost, to flood the mempool/state with free transactions and accounts — something that is only supposed to be economically possible for the small set of bonded Universal Validators.
