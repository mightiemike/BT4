### Title
Liquidation bad-debt socialization fold silently absorbs per-asset failures without reverting already-applied write-offs - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`socialize-debt-asset`, the `fold` helper used by `liquidate` to write off a borrower's remaining debt once their collateral is exhausted, stops processing further debt entries as soon as one entry fails, but it does not communicate that failure back up in a way that forces the enclosing `liquidate` transaction to revert. Debt entries processed *before* the failing one have already had `vault-socialize-debt`, the `index-cache` update, and `.v0-market-vault debt-remove-scaled` applied. Because Clarity only reverts a transaction when the outer public function ultimately returns an `(err ...)`, if `liquidate` does not propagate the fold's terminal `success: false` into an assertion, the transaction commits with some of the borrower's debt written off as bad debt and other debt entries left completely untouched — a silent, partial insolvency write-off.

### Finding Description
`socialize-debt-asset` is defined as: [1](#0-0) 

The accumulator starts as `{ borrower: ..., success: true }`. On the first failing entry, the function returns `failed-status` (`success: false`) via `unwrap!`, which is a local early-return, not a transaction abort. Every following iteration hits the `(if (not (get success acc)) acc ...)` short-circuit and does nothing — it never retries or signals the caller to unwind. Inside the branch that *did* succeed, three side-effecting operations already ran: `vault-socialize-debt` (writes off debt in the vault), a `map-set` on `index-cache` for that asset, and a cross-contract `debt-remove-scaled` call clearing the position's scaled debt for that asset in `market-vault`. None of these are conditioned on the eventual outcome of the whole fold.

This exactly matches the requested "fold that absorbs failure" mechanism: the value bound is the per-asset socialization outcome (`success` flag); the invalidating event is a failure partway through the debt list (e.g. `vault-socialize-debt` or `debt-remove-scaled` returning an error for one asset, such as a vault being paused mid-liquidation or an unknown-vault routing miss for a newly-added asset id); the later use is the enclosing `liquidate` transaction finishing and committing `(ok ...)` for the borrower's liquidation while the fold's own failure marker is discarded, unless the call site explicitly asserts on `success` (which the code available does not show being checked/asserted after the fold call).

### Impact Explanation
If the enclosing `liquidate` flow does not gate its final `(ok ...)` on the fold's `success` field, a borrower whose collateral is fully exhausted can end up with only a subset of their remaining debt assets socialized (marked as bad debt / cleared) while other debt-asset entries are left dangling in `market-vault` with no matching collateral to ever repay them, since collateral was already zeroed out by the liquidation. This creates unrecoverable bad debt that is inconsistently accounted for across vaults — some vaults absorb the loss (correct write-off), others do not get notified at all despite the position having no collateral left to satisfy them — a direct path to protocol insolvency for the affected vaults, which is a Critical-impact outcome (protocol insolvency), since the debt can never be legitimately repaid or liquidated again from a position with zero collateral.

### Likelihood Explanation
The likelihood depends on whether `vault-socialize-debt` or `debt-remove-scaled` can plausibly fail for one debt asset but not another within the same `liquidate` call on a no-collateral-left borrower with multiple debt assets (e.g., one vault paused for `repay`/write-down operations while another is not, or a temporary cross-contract call error). This is a realistic operational scenario (per-vault pause states exist, as seen in `vault-*.clar` `pause-states`), making the failure condition reachable without any privileged action. I was not able to retrieve the exact call site inside `liquidate` that consumes this fold's `success` field before the tool budget ran out, so it is not fully confirmed whether the outer function checks and asserts on it; this is the main open verification gap.

### Recommendation
After the `fold socialize-debt-asset` call completes, explicitly check the accumulator's `success` field and `asserts!`/`try!` on it so that any partial failure aborts the entire `liquidate` transaction (reverting the already-applied `vault-socialize-debt`/`debt-remove-scaled` calls atomically), rather than allowing `liquidate` to return `(ok ...)` when only some debt assets were successfully written off.

### Proof of Concept
1. Borrower has two debt assets, e.g. STX and USDC, and collateral that a liquidator seizes down to zero (`no-collateral-left` becomes true) via `liquidate`.
2. The socialization path folds over the borrower's remaining debt list with `socialize-debt-asset`, first processing STX: `vault-socialize-debt`, `index-cache` update, and `debt-remove-scaled` for STX succeed and commit their mutations.
3. The USDC vault is paused for the relevant operation (or otherwise returns an error) at the moment `vault-socialize-debt` is invoked for the USDC entry; `unwrap!` returns `failed-status` for that iteration without reverting anything already applied.
4. Because subsequent iterations see `success: false` and no-op, the fold terminates with `success: false`, but if `liquidate`'s final response is not conditioned on this flag, the outer public function still returns `(ok {...})`.
5. Result: STX debt for the borrower is erased/socialized as bad debt while the borrower's USDC debt entry remains recorded in `market-vault` with no collateral backing it, and the transaction shows success — a state depended on by lenders that under-collateralized/unrecoverable debt now silently exists in the USDC vault's books. (define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
