**Analysis:**

The premise mischaracterizes normal saturating-subtraction logic as a bug. `FeePerByte` is just a unit-typed alias defined in `aptos-move/aptos-gas-algebra/src/algebra.rs:43` and has no involvement in the subtraction itself — it is only used afterward as a multiplier on the already-computed `NumBytes` excess. [1](#0-0) 

The actual boundary logic lives in `discounted_write_op_size_for_v1` (and its `IoPricingV2`/`IoPricingV3` counterparts, `write_op_size`), which computes `size.checked_sub(quota).unwrap_or(NumBytes::zero())`: [2](#0-1) [3](#0-2) 

`checked_sub` is Rust's standard overflow-safe subtraction — it deliberately returns `None` when `size < quota` rather than wrapping/underflowing, and `unwrap_or(NumBytes::zero())` is the intended fallback that implements the "free write-bytes quota" discount (i.e., no bytes are charged when the write is within the free quota). This is not "protected only by" an incidental guard — it is the designed saturating-subtraction semantics with no underflow path at all, since the checked variant by construction cannot underflow.

Walking through the three boundary cases the question asks for:
- `size = quota - 1`: `checked_sub` → `None` → `0` excess bytes (correct, within quota).
- `size = quota`: `checked_sub` → `Some(0)` → `0` excess bytes (correct, exactly at quota).
- `size = quota + 1`: `checked_sub` → `Some(1)` → `1` excess byte (correct).

This exactly matches the intended formula `excess = max(0, size - quota)`. There is no off-by-one, no underflow, and no arithmetic corruption of `bytes_fee`.

Regarding `StateValueMetadata`/`bytes_deposit`: in the V1 creation path, only `slot_deposit` is written into `StateValueMetadata` via `op.metadata_mut.set_slot_deposit(slot_fee.into())`; `bytes_fee` from `discounted_write_op_size_for_v1` only feeds into the `charge` returned to the gas meter, not into any persisted `StateValueMetadata` field for V1. [4](#0-3) 

Since the value is attacker-influenced only through `write_len`, and the subtraction is fully saturating with no unwrap panics or wraparound possible, there is no path by which unprivileged transaction input can corrupt committed state, proof material, or produce a hard-fork divergence via this code.

    fn write_op_size(&self, key: &StateKey, value_size: u64) -> NumBytes {
        let value_size = NumBytes::new(value_size);

        if self.feature_version >= 3 {
            let key_size = NumBytes::new(key.size() as u64);
            (key_size + value_size)
