Confirmed: `DecodeUtil.addressValid()` only checks that the address is non-empty, exactly 21 bytes, and starts with the correct network prefix byte — it never rejects the all-zero address body (i.e., `0x41` followed by 20 zero bytes) [1](#0-0) . `AccountPermissionUpdateActuator.checkPermission()` relies solely on this check for every key address in a permission, with no additional "is this a known/spendable address" or "is this not the burn/zero address" check [2](#0-1) .

### Title
Unvalidated zero-value address accepted as Owner-permission key in `AccountPermissionUpdateActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
This is a genuine analog of the Lido bug class ("address parameter accepted without a zero-value check, no way to recover afterward"), but it manifests as an **irreversible account state**, not a redeploy requirement, since java-tron actuators aren't upgradable contracts.

### Finding Description
`AccountPermissionUpdateContract` lets any account owner (an unprivileged, self-service transaction) replace its Owner/Witness/Active permissions with a new set of `Key` addresses and weights [3](#0-2) . During `validate()`, each key address is checked only via `checkPermission()`, which in turn calls `DecodeUtil.addressValid()` [4](#0-3) . That helper validates length/prefix but performs no check that the address body is non-zero [1](#0-0) . Consequently, a transaction that sets the Owner permission's sole key to the "zero address" (prefix byte + 20 zero bytes) passes validation and is committed via `account.updatePermissions(...)` [5](#0-4) .

Because the private key corresponding to the all-zero address is unknown/unobtainable (same rationale as Ethereum's canonical "burn address" being address(0)), once an account's Owner permission is set to only such a key, no future `AccountPermissionUpdateContract` (which itself requires a valid Owner-permission signature) can ever be submitted to restore access — this exactly mirrors the reported bug class: a critical address field accepted without a "not-zero" check, with no compensating setter/recovery path afterward.

### Impact Explanation
If exploited (accidentally via wallet/UI bug, or maliciously if an attacker can get a victim to sign such an update), the account's TRX balance, delegated resources, voting power, and any assets tied to that address become permanently unmanageable — the account cannot transfer, vote, unfreeze, or reconfigure permissions again, since all of these require a valid Owner or Active permission signature. This is a genuine, irreversible loss-of-control (invalid/permanent state) impact, analogous to the "must redeploy" outcome in the Lido report.

### Likelihood Explanation
This requires the account owner to submit an `AccountPermissionUpdateContract` transaction with an all-zero address as a permission key — most likely to occur due to a client-side bug (e.g., an empty/uninitialized address field defaulting to zero-fill) rather than a knowledgeable user intentionally bricking their own account. The transaction is unprivileged (any account can call it on itself) and requires no special network conditions, so likelihood is driven entirely by client tooling correctness rather than any protocol-level access control.

### Recommendation
Add an explicit check in `AccountPermissionUpdateActuator.checkPermission()` (and ideally centrally in `DecodeUtil.addressValid()` or a dedicated helper used at this call site) rejecting any `Key.getAddress()` whose 20-byte body is all zero, in addition to the existing length/prefix validation.

### Proof of Concept
1. Build an `AccountPermissionUpdateContract` for account `A` where the `owner` `Permission` contains a single `Key` with `address = 0x41 || 00*20` (passes `DecodeUtil.addressValid` since length is 21 and prefix matches) and `weight = 1`, `threshold = 1`.
2. Submit and sign the transaction with `A`'s current valid Owner permission key.
3. `AccountPermissionUpdateActuator.validate()` succeeds (all `checkPermission` checks pass since the zero-body address is length/prefix valid) and `execute()` commits `account.updatePermissions(...)`, overwriting the Owner permission.
4. Any subsequent transaction from `A` requiring Owner-permission signature (including another `AccountPermissionUpdateContract` to fix the mistake) can never be validly signed, permanently locking the account.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
