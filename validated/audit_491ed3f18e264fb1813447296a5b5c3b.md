### Title
Exchange (bonding-curve) trading can be permanently blocked by driving a token's pool balance to zero - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
Java-tron's on-chain token exchange feature (`ExchangeCreateContract` / `ExchangeTransactionContract` / `ExchangeInjectContract` / `ExchangeWithdrawContract`) implements a Bancor-like bonding-curve swap between two tokens held in an `ExchangeCapsule`. Both the transaction actuator and the inject actuator hard-fail once either side of the pool balance reaches exactly zero, closing the exchange permanently for everyone, analogous to the reported 1inch `FixedRateSwap` issue where a small/zero balance of one token blocks all further exchanges.

### Finding Description
`ExchangeTransactionActuator.doValidate()` rejects any trade once either pool balance is 0: [1](#0-0) 

The same check exists in `ExchangeInjectActuator.doValidate()`, meaning even the exchange creator cannot top up (inject) more liquidity once a balance is zero: [2](#0-1) 

The actual swap math is computed by `ExchangeCapsule.transaction()`, which calls the Bancor-style `ExchangeProcessor.exchange()` (or `SafeExchangeProcessor` when "hardened" mode is enabled) and updates `firstTokenBalance`/`secondTokenBalance` directly based on the formula's output: [3](#0-2) [4](#0-3) 

Because the "buy" amount is a floating point / long-truncated computation, and the hardened-calc branch only rejects results that go **negative** (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`), it does not prevent a balance from landing exactly at 0: [5](#0-4) 

Once a balance hits 0, both `ExchangeTransactionActuator` and `ExchangeInjectActuator` permanently refuse any further operation on that exchange with "the exchange has been closed" — this is reachable by any unprivileged account broadcasting an `ExchangeTransactionContract` with a `tokenQuant` sized to drain the counter-token to exactly zero (or arbitrarily close, given the bonding curve's shape as the pool balance shrinks toward 0, trades become effectively impossible far earlier than exact zero, per the report's premise of "small balance blocking the exchange"). Only `ExchangeWithdrawActuator`, restricted to the exchange creator, can remove liquidity — there is no unprivileged mechanism to force liquidity back in once trading is blocked, and even the creator's own `ExchangeInjectActuator` is blocked by the same zero-balance check.

### Impact Explanation
This is a denial-of-service against a core, unprivileged, broadcast-reachable market feature: any account can permanently disable a specific on-chain Exchange pair by draining one side to (or effectively near) zero, since even the pool creator's remediation path (`ExchangeInject`) is blocked by the identical `firstTokenBalance == 0 || secondTokenBalance == 0` guard. This matches the 1inch report's root cause (a hard balance-zero/insufficiency check blocking all further exchange operations with no recovery path) and its class of impact (market/liquidity DoS via unprivileged calls), though java-tron's `Exchange` feature is a legacy/soon-deprecated on-chain market rather than a smart contract, and TRX/TRC10 asset loss is not caused — only availability of that specific exchange instance is affected.

### Likelihood Explanation
High: any account holding either token in the pool can call `ExchangeTransactionContract` (only fee balance and asset balance for `tokenQuant` are required — see `doValidate()`'s balance checks) to push the counter-token balance toward zero as the bonding curve narrows; no special permission or state is required, and the built-in `ExchangeBalanceLimit` check only caps upper bounds, not lower bounds: [6](#0-5) 

### Recommendation
- Emit an event/log when an exchange's balances approach a critically low threshold (not only at exact 0), so it can be monitored and remediated externally, mirroring the reporter's recommendation.
- Add a minimum-balance floor (not just a `>0` check) in `ExchangeCapsule.transaction()` to reject trades that would drive a balance below a safe minimum, rather than only rejecting negative results.
- Allow the exchange creator's `ExchangeInjectActuator` to top up liquidity even when a balance is at/near zero, so a legitimate recovery path exists instead of a hard, permanent "exchange has been closed" state.

### Proof of Concept
1. Exchange creator calls `ExchangeCreateContract` to create a pool with small `firstTokenBalance`/`secondTokenBalance` for tokens A/B.
2. Any account with enough token A repeatedly (or in one large trade sized via the bonding-curve formula) submits `ExchangeTransactionContract` selling token A for token B, driving `secondTokenBalance` toward/to 0 as computed in `ExchangeCapsule.transaction()`.
3. Once `secondTokenBalance == 0`, all subsequent `ExchangeTransactionContract` calls fail validation at `ExchangeTransactionActuator.doValidate()` line 194 with "the exchange has been closed".
4. The creator's attempt to remediate via `ExchangeInjectContract` also fails at the identical check in `ExchangeInjectActuator.doValidate()` line 200, leaving the exchange permanently unusable.

```java
  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
```
