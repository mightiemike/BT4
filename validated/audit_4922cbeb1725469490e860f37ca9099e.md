### Title
Cross-Endpoint HMAC Signature Reuse Due to Missing Domain/Purpose Binding in `validateHmacFromRequestFactory` - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
`validateHmacFromRequestFactory` computes the same `HMAC-SHA256(apiSecretKey, rawBody)` regardless of which Shopify feature (Flow action, Fulfillment Service callback, or generic Webhook) is being validated, and compares it to the identical `X-Shopify-Hmac-Sha256` header value in all three cases. The signed material (the raw HTTP body only) contains no tag identifying the intended recipient/purpose of the signature, mirroring the reported class of bug where a message hash omits binding to the "processing contract" (here, the specific validation endpoint/type).

### Finding Description
`validateHmacFromRequestFactory` in [1](#0-0)  is shared across three distinct `HmacValidationType`s: `Flow`, `Webhook`, and `FulfillmentService`, as defined in [2](#0-1) . The `flow/validate.ts` and `fulfillment-service/validate.ts` modules both call this same factory with only the `type` discriminator changed: [3](#0-2)  and [4](#0-3) .

Crucially, the `type` value is used only to select an error message on failure (in `handleInvalidWebhook`-style branching), never as part of the signed data. The actual HMAC comparison is `validateHmacString(config, rawBody, hmac, HashFormat.Base64)` — i.e., `HMAC-SHA256(apiSecretKey, rawBody)` — identical for Flow, Webhook, and Fulfillment Service requests, all keyed off the same `ShopifyHeader.Hmac` (`X-Shopify-Hmac-Sha256`) header unless a `webhookType`-specific header is supplied. This is structurally the same defect pattern as the Opera-Bridge report: the signed payload lacks a domain-separation value (equivalent to `chain.id`/`address(this)`) identifying which contract/endpoint/purpose the signature is valid for, so a signature computed over a given `rawBody` is not bound to the specific validation context it is meant for.

### Impact Explanation
If Shopify (or a party who can obtain a validly-signed body, e.g. through legitimate webhook delivery) ever produces the same raw body bytes for two different callback purposes (or if an app registers overlapping routes for Flow, Fulfillment Service, and Webhook handling using the same underlying `validate()` call), a signature captured from one channel could be replayed against a different validation call and be accepted, since verification does not incorporate the endpoint type into the hashed material. This could let an attacker who intercepts or replays a legitimately-signed body cause it to be accepted by a different, unintended handler (e.g., a Fulfillment Service body accepted as a Flow trigger), potentially triggering unintended business logic in the app depending on how each handler processes payloads.

### Likelihood Explanation
Likelihood is low/speculative: exploitation requires an attacker to obtain a validly HMAC-signed raw body from Shopify and find that Shopify (or the app) has multiple distinct validation contexts sharing an identical body shape, or requires the app itself to route the same body to more than one of Flow/Webhook/Fulfillment-Service validators. Under normal usage each callback type has a distinct payload/route, limiting the practical replay surface. This is a design weakness (missing domain separation in the signed data, analogous to the missing chain ID/contract address) rather than a demonstrated end-to-end forgeable request.

### Recommendation
Bind the `HmacValidationType` (and ideally the target route) into the signed/verified material — e.g., verify the `type` (and any distinguishing header, such as the specific webhook topic or resource) as part of, or alongside, the HMAC check, rather than relying solely on `HMAC(secret, rawBody)` with the type only affecting error messaging. This ensures a signature computed for one endpoint/purpose cannot be replayed against another endpoint that shares the same secret and body shape.

### Proof of Concept
Not independently reproduced end-to-end; this is based on static analysis showing `validateHmacFromRequestFactory` at [1](#0-0)  uses `type` only for error branching, not as verified input, and that `flow/validate.ts` and `fulfillment-service/validate.ts` both delegate to this same function with an identical `HMAC(secret, rawBody)` check [3](#0-2) [4](#0-3) . A concrete exploit chain would require identifying a real-world case where Shopify or the integrating app produces identical raw bodies across two of these validation contexts, which was not verified in this investigation due to index/context limitations.

```typescript
export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
```
