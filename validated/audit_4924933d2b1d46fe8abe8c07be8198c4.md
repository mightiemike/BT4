### Title
`ensure_match_transaction_info` never validates `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, letting replay-verify tooling accept a corrupted state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by Aptos's own state-integrity auditing tools (`replay-verify`, `db-tool replay-on-archive`, and the CLI transaction replayer) to confirm that locally re-executed VM output matches the transaction info that was actually committed and accumulator-proven on chain. It checks `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event-root hash, but it never compares the recomputed state/hot-state/position **checkpoint** hashes against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. Since these checkpoint hashes are the authenticated Jellyfish-Merkle/global-state roots committed into the ledger accumulator, a divergence there is exactly the class of bug replay-verify exists to catch, and it is silently missed.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  performs four `ensure!` checks (status, gas, write-set hash, event root hash) and then returns `Ok(())`, with an explicit acknowledging comment: [2](#0-1) 
stating the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)", so replay-verify tooling "can report a successful replay even when the authenticated position state root diverges from local execution."

This function is invoked directly on live, unprivileged, mainnet-relevant integrity-verification paths:
- `storage/db-tool/src/replay_on_archive.rs`, the dedicated replay-verify tool that re-executes archived transactions and diffs them against the historically committed `TransactionInfo` proofs: [3](#0-2) 
- `execution/executor/src/chunk_executor/mod.rs`'s `verify_execution`, used by the `TransactionReplayer`/backup-restore verify flow: [4](#0-3) 
- `aptos-move/cli/src/commands.rs`'s single-transaction replay command: [5](#0-4) 

None of these call sites independently re-derive and compare the state checkpoint root; they rely entirely on `ensure_match_transaction_info` for output validation. Because `state_checkpoint_hash` is the root of the entire versioned key-value state (and, when the new `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` feature flags are enabled, also folds in the hot-state root and the native "position" JMT root — see the feature/flag wiring in [6](#0-5)  and [7](#0-6) ), any bug in `DoStateCheckpoint`/`DoLedgerUpdate` or in the new native-position commit path (e.g. `storage/aptosdb/src/db/aptosdb_writer.rs::position_summary_at_commit`, which is explicitly documented as computing a root that is "not consensus-committed" in the flag-off fallback path — [8](#0-7) ) would not be flagged by any of these tools even though the write-set/event/gas/status fields all still match.

### Impact Explanation
Replay-verify and archive-replay tools exist specifically to detect state-commitment divergence between the VM's correct recomputation and what was actually committed to the ledger — this is the last line of defense against a consensus-vs-storage state-root bug going undetected across the historical chain. Because the state/hot-state/position checkpoint hashes are excluded from the comparison, a real state-root corruption (e.g., in state checkpoint/JMT construction, or in the new native-position summary computation) would pass `replay_on_archive` and `db-tool replay-verify` as "succeeded", giving false assurance that the chain's committed state root is correct. This falls squarely within the "authenticated ... proof-bearing responses must stay bound to the right ledger version, root, and object" and "hard-fork-only divergence during commit, replay, restore ... verification" impact categories, since it defeats detection of a wrong accumulator/state root being accepted as valid.

### Likelihood Explanation
This is not an attacker-triggered exploit but a guaranteed gap in existing, always-run verification logic — any state-root corruption bug (whether introduced by a future refactor of `DoStateCheckpoint`, the new native-position/trading-native subsystem, or a JMT batching bug) will deterministically bypass detection by these tools. The comment in the code confirms the authors are aware this must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`", indicating the gap is real and currently live in the comparator used by both existing (state_checkpoint_hash) and new (position_state_checkpoint_hash) proof fields.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when applicable per active feature flags) against the values in `txn_info`, or otherwise fail loudly if these cannot be verified when a checkpoint is present. At minimum, gate the enablement of `COMPUTE_TRADING_NATIVE_STATE_ROOTS` on this check being implemented, as the existing comment recommends, and audit all three call sites (`replay_on_archive.rs`, `chunk_executor::verify_execution`, and the CLI replayer) to ensure they cannot report success while checkpoint hashes are unchecked.

### Proof of Concept
1. In `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, re-execute an archived transaction whose write-set/events/gas/status match the historical `TransactionInfo` but whose true committed `state_checkpoint_hash` (or `position_state_checkpoint_hash`, once native-position writes are active) differs from what local execution would compute (e.g. simulate by feeding a `TransactionInfo` with all fields matching except `state_checkpoint_hash`/`position_state_checkpoint_hash`).
2. Observe that `ensure_match_transaction_info` ( [1](#0-0) ) returns `Ok(())` because it never inspects these fields.
3. `replay_on_archive`/`replay-verify` reports the chunk as successfully verified despite the state root mismatch, confirming the detection gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
