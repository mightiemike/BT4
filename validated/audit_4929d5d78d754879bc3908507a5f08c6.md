### Title
Denial of Service via Unchecked Arithmetic Overflow Panic in `GasVector::cost` When Computing Fee From Attacker-Controlled Resource Bounds/Tip - (File: crates/starknet_api/src/execution_resources.rs)

### Summary
`GasVector::cost`, used by the blockifier fee module to compute the actual fee charged for a transaction, performs `checked_mul`/`checked_add` arithmetic on gas amounts, gas prices, and the transaction's `tip` field, and calls `panic!()` on any overflow instead of returning a `Result` or saturating. Because `tip`, `max_amount`, and `max_price_per_unit` in `ResourceBounds` are values a transaction sender fully controls (subject only to a *minimum* price check, not a maximum bound), a single crafted V3 transaction can drive this computation into overflow and crash the sequencer node processing the transaction — the same bug class as the referenced SurrealDB `rand::time()` advisory (CWE-248, uncaught panic reachable by an untrusted caller).

### Finding Description
`GasVector::cost` explicitly documents that it "panics on overflow": [1](#0-0) 

It computes `tipped_l2_gas_price = gas_prices.l2_gas_price.checked_add(tip.into())`, then for each resource multiplies gas amount by price with `checked_mul`, and sums with `checked_add`, calling `panic!` via `unwrap_or_else` on any `None` result.

Contrast this with the sibling method `ValidResourceBounds::max_possible_fee`, which performs the *same style* of computation but deliberately uses `saturating_mul`/`saturating_add` to avoid any panic on attacker-controlled resource bounds: [2](#0-1) 

This shows the codebase is aware that `tip`, `max_amount`, and `max_price_per_unit` are adversarial inputs that must be handled with saturating arithmetic for the pre-execution balance/fee-bound check — but the *actual* fee computation performed after execution (`GasVector::cost`, invoked from `crates/blockifier/src/fee/fee_utils.rs`) still uses panicking `checked_*` arithmetic.

`tip`, and the `max_amount`/`max_price_per_unit` fields of `ResourceBounds` (per-resource: L1 gas, L2 gas, L1 data gas), are set directly by the transaction sender in a V3 `InvokeTransaction`/`DeclareTransaction`/`DeployAccountTransaction`. The gateway's stateless validator only checks a lower bound on L2 gas price relative to the block's base price (`validate_resource_bounds` — "ensures the max L2 gas price exceeds a configurable percentage of the base gas price"), and caps `max_l2_gas_amount`, but does not appear to enforce an upper limit on `max_price_per_unit` for L1/L1-data gas or on `tip` sufficient to prevent `u128`/`Fee` overflow in downstream fee arithmetic.

### Impact Explanation
A panic inside the fee-accounting path invoked during transaction execution (blockifier) crashes the sequencer process handling that transaction/block, causing denial of service — the sequencer becomes unable to confirm new transactions until restarted, and any batcher/executor threads sharing state may be left in an inconsistent state. This matches the "network unable to confirm new transactions" acceptance criterion.

### Likelihood Explanation
Reaching this code only requires submitting one otherwise well-formed V3 transaction (invoke, declare, or deploy-account) with extreme `tip` and/or extreme `max_price_per_unit`/`max_amount` resource-bound values that pass the gateway's existing (minimum-bound-only) stateless checks, then letting it reach the fee-charging path in the blockifier during block building/execution. No special privileges, staking, or operator/peer compromise are required — any unprivileged transaction sender can attempt this.

### Recommendation
Change `GasVector::cost` to use saturating (or checked-with-error-propagation) arithmetic consistent with `ValidResourceBounds::max_possible_fee`, returning a bounded/saturated `Fee` (or a proper `TransactionFeeError`) instead of panicking. Additionally, consider adding upper-bound validation on `tip` and `max_price_per_unit` in the gateway's stateless transaction validator to reject transactions whose resource-bound combination could overflow fee arithmetic, defense-in-depth alongside the arithmetic fix.

### Proof of Concept
1. Submit a V3 invoke transaction with resource bounds set so that `l2_gas.max_price_per_unit + tip` (as `u128`) is very close to `u128::MAX`, or such that `gas_amount * price` for any resource overflows `u128`/`Fee`'s internal type when the transaction executes and consumes gas up to (or reported as) its bound.
2. Ensure the values pass the gateway's stateless minimum-price check (only a lower bound relative to the base gas price is enforced), so the transaction is admitted to the mempool and later picked up for execution.
3. During block building, the blockifier computes the actual fee via `GasVector::cost` (`crates/starknet_api/src/execution_resources.rs:156-186`), triggering `checked_mul`/`checked_add` overflow and the corresponding `panic!`, crashing the sequencer process handling that block.

    /// Computes the cost (in fee token units) of the gas vector (panicking on overflow).
    pub fn cost(&self, gas_prices: &GasPriceVector, tip: Tip) -> Fee {
        let tipped_l2_gas_price =
            gas_prices.l2_gas_price.checked_add(tip.into()).unwrap_or_else(|| {
                panic!(
                    "Tip overflowed: addition of L2 gas price ({}) and tip ({}) resulted in \
                     overflow.",
                    gas_prices.l2_gas_price, tip
                )
            });

        let mut sum = Fee(0);
        for (gas, price, resource) in [
            (self.l1_gas, gas_prices.l1_gas_price, Resource::L1Gas),
            (self.l1_data_gas, gas_prices.l1_data_gas_price, Resource::L1DataGas),
            (self.l2_gas, tipped_l2_gas_price, Resource::L2Gas),
        ] {
            let cost = gas.checked_mul(price.get()).unwrap_or_else(|| {
                panic!(
                    "{resource} cost overflowed: multiplication of gas amount ({gas}) by price \
                     per unit ({price}) resulted in overflow."
                )
            });
            sum = sum.checked_add(cost).unwrap_or_else(|| {
                panic!(
                    "Total cost overflowed: addition of current sum ({sum}) and cost of \
                     {resource} ({cost}) resulted in overflow."
                )
            });
        }
        sum
    }

    /// Returns the maximum possible fee that can be charged for the transaction.
    /// The computation is saturating, meaning that if the result is larger than the maximum
    /// possible fee, the maximum possible fee is returned.
    pub fn max_possible_fee(&self, tip: Tip) -> Fee {
        match self {
            ValidResourceBounds::L1Gas(l1_bounds) => {
                l1_bounds.max_amount.saturating_mul(l1_bounds.max_price_per_unit)
            }
            ValidResourceBounds::AllResources(AllResourceBounds {
                l1_gas,
                l2_gas,
                l1_data_gas,
            }) => l1_gas
                .max_amount
                .saturating_mul(l1_gas.max_price_per_unit)
                .saturating_add(

                )
                .saturating_add(
                    l1_data_gas.max_amount.saturating_mul(l1_data_gas.max_price_per_unit),
