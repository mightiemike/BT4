### Title
Integer-division truncation drift in `totalNetWeight`/`totalEnergyWeight` from batched multi-entry unfreeze in `UnfreezeBalanceProcessor.execute` - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java])

### Summary
`FreezeBalanceProcessor.execute` credits `totalNetWeight`/`totalEnergyWeight` by `floor(frozenBalance / TRX_PRECISION)` **per individual freeze call**, while `UnfreezeBalanceProcessor.execute` sums the raw (un-truncated) `frozenBalance` of **all matured `Frozen` entries together** and only then applies a single `floor(sum / TRX_PRECISION)` when debiting the same global counters. Because `FreezeBalanceProcessor.validate`/`FreezeBalanceV2*` only enforce `frozenBalance >= TRX_PRECISION` (not that it be an exact multiple of `TRX_PRECISION`), and an account may hold up to two concurrent `Frozen` entries (`frozenCount` must be `0` or `1` at the time of a new freeze), an attacker can perform two separate freezes with fractional (non-multiple-of-`TRX_PRECISION`) sun amounts and let both mature before unfreezing, causing the batched floor-sum at unfreeze time to differ from the sum of the per-call floors credited at freeze time.

### Finding Description
- Entry point: TVM `FREEZE`/`UNFREEZE` opcodes call `Program.freeze` / `Program.unfreeze`, which build a `FreezeBalanceParam`/`UnfreezeBalanceParam` from attacker-controlled `DataWord` inputs and invoke `FreezeBalanceProcessor`/`UnfreezeBalanceProcessor` directly — fully reachable by any unprivileged contract caller. [1](#0-0) 
- On freeze, validation only requires `frozenBalance >= TRX_PRECISION`; there is no requirement that `frozenBalance % TRX_PRECISION == 0`. [2](#0-1) 
- Each freeze call independently credits the global weight with its own truncated value: `repo.addTotalNetWeight(frozenBalance / TRX_PRECISION)` (same pattern for energy). [3](#0-2) 
- `validate` allows a new freeze whenever the current `frozenCount` is `0` or `1`, so an account can accumulate up to two live `Frozen` entries with independently chosen sub-precision remainders (e.g. two freezes of `1,500,000` sun = 1.5 TRX each). [4](#0-3) 
- On unfreeze, `UnfreezeBalanceProcessor.execute` iterates the `Frozen` list and **sums the raw balances of every matured entry** into a single `unfreezeBalance` before dividing once by `TRX_PRECISION`: `repo.addTotalNetWeight(-unfreezeBalance / TRX_PRECISION)`. [5](#0-4) [6](#0-5) 
- Example: freeze 1.5 TRX twice (two separate calls) → credited weight = `floor(1.5)+floor(1.5) = 1+1 = 2`. When both entries mature and are unfrozen together, debited weight = `floor(3.0) = 3`. Net drift on `totalNetWeight` = `+2 − 3 = −1`, even though the account's true aggregate frozen stake at all times matches the correctly-computed floor of its actual balance. This under/over-counts relative to a freshly-computed invariant of "global weight == floor(total live frozen stake / TRX_PRECISION)," and the sign/magnitude of the drift depends on the fractional remainders chosen by the attacker, who fully controls both freeze amounts.
- Note: a single freeze immediately followed by unfreezing that exact same single entry cancels exactly (`floor(A/P)` added then subtracted), so the drift specifically requires batching ≥2 concurrently-live entries with independently truncated fractional remainders into one unfreeze call — a condition trivially reachable by any account performing two freezes before either matures.

### Impact Explanation
`totalNetWeight`/`totalEnergyWeight` are the network-wide denominators used to compute the global bandwidth/energy unit price (`totalNetWeight`/`totalEnergyWeight` divide the total issuance to derive per-unit price). A persistent, attacker-inducible drift between the tracked global weight and the true aggregate frozen stake causes systemic underpricing or overpricing of bandwidth/energy for the entire network, repeatable indefinitely by any account performing overlapping freeze/unfreeze cycles with fractional sun amounts, at negligible cost (only TRX freeze/unfreeze, no fees consumed for freezing itself).

### Likelihood Explanation
Fully feasible with an unprivileged contract: no special permissions are needed, only two ordinary `FREEZE` opcode calls with amounts not divisible by `TRX_PRECISION` (e.g., `1,000,001` sun) followed by an `UNFREEZE` call after both entries mature. The `frozenCount <= 1` gate in `validate` explicitly permits exactly the two-entry-overlap precondition required. This can be repeated indefinitely by any account to accumulate compounding drift, and can be done by many attacker-controlled accounts in parallel for greater network-wide effect.

### Recommendation
Make the truncation symmetric and entry-scoped instead of batch-scoped:
- Track and persist the per-entry (or per-account) contribution to `totalNetWeight`/`totalEnergyWeight` credited at freeze time (i.e., store the already-truncated weight, or store frozen balances only in units of `TRX_PRECISION`), and subtract exactly that stored/credited value at unfreeze time rather than recomputing `floor(sum_of_raw_balances / TRX_PRECISION)` over a batch.
- Alternatively, enforce `frozenBalance % TRX_PRECISION == 0` in `FreezeBalanceProcessor.validate` / `FreezeBalanceV2Processor.validate` (and their actuator counterparts) so no sub-`TRX_PRECISION` remainder can ever exist, eliminating the possibility of divergent truncation between freeze-time and unfreeze-time weight adjustments.

### Proof of Concept
```java
// Illustrative integration test targeting UnfreezeBalanceProcessor / FreezeBalanceProcessor
@Test
public void testTotalNetWeightDriftFromBatchedUnfreeze() {
  // Setup: fresh account with sufficient balance, dynamicStore.totalNetWeight = baseline
  long baseline = dynamicStore.getTotalNetWeight();

  FreezeBalanceParam f1 = new FreezeBalanceParam();
  f1.setOwnerAddress(owner); f1.setReceiverAddress(owner);
  f1.setFrozenBalance(1_500_000L); // 1.5 TRX
  f1.setFrozenDuration(3); f1.setResourceType(BANDWIDTH);
  freezeProcessor.validate(f1, repo);
  freezeProcessor.execute(f1, repo); // credits +1 (floor(1.5))

  FreezeBalanceParam f2 = new FreezeBalanceParam();
  f2.setOwnerAddress(owner); f2.setReceiverAddress(owner);
  f2.setFrozenBalance(1_500_000L); // 1.5 TRX, second overlapping entry (frozenCount was 1, still allowed)
  f2.setFrozenDuration(3); f2.setResourceType(BANDWIDTH);
  freezeProcessor.validate(f2, repo);
  freezeProcessor.execute(f2, repo); // credits +1 (floor(1.5)) -> total credited so far = baseline + 2

  long afterFreezeWeight = dynamicStore.getTotalNetWeight();
  Assert.assertEquals(baseline + 2, afterFreezeWeight);

  // advance block time past both expireTimes so both entries are matured
  advanceBlockTimestampPastExpiry();

  UnfreezeBalanceParam u = new UnfreezeBalanceParam();
  u.setOwnerAddress(owner); u.setReceiverAddress(owner);
  u.setResourceType(BANDWIDTH);
  unfreezeProcessor.validate(u, repo);
  unfreezeProcessor.execute(u, repo); // sums both entries (3.0 TRX) then subtracts floor(3.0) = 3

  long afterUnfreezeWeight = dynamicStore.getTotalNetWeight();
  // Expected (no drift) would be baseline (net zero), but actual result is baseline - 1
  Assert.assertEquals(baseline - 1, afterUnfreezeWeight); // demonstrates drift, invariant violated
}
```
Expected result: `afterUnfreezeWeight` deviates from `baseline` by `-1` even though the account has fully unfrozen all its stake (true aggregate frozen stake is `0`), demonstrating the accounting invariant `totalNetWeight == floor(aggregate_frozen_stake / TRX_PRECISION)` is violated and can be repeated/amplified across many accounts and cycles.
