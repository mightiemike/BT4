## Title
Zero-weight reward set collapses Nakamoto signer approval threshold to zero, letting a block be accepted network-wide without any real signer support - (File: `stackslib/src/chainstate/nakamoto/mod.rs`)

### Summary
`NakamotoBlockHeader::compute_voting_weight_threshold` computes the minimum signer weight needed to approve a block as `ceil(total_weight * 7 / 10)` with no floor check on `total_weight`. [1](#0-0)  If `total_weight` is `0`, the computed `threshold` is `0`. This value is then used directly in `verify_signer_signatures`, where `total_weight_signed` starts at `0` and the block is accepted if `total_weight_signed >= threshold`. [2](#0-1)  With `threshold == 0`, `0 >= 0` is trivially true, so a block with **zero valid signer signatures** passes verification.

### Finding Description
`total_weight` is taken from `reward_set.total_signing_weight()` [3](#0-2) , i.e. the sum of the `weight` field over all signers in the reward set for the cycle. The intended invariant is: *a block is only valid if signers holding at least 70% of the total signing weight signed it*. This is exactly analogous to the Convergence bug, where `totalWeightLocked == 0` silently turned the "must reach quorum" check into a no-op (division producing a degenerate zero threshold instead of reverting), because the code assumes the denominator/threshold-defining quantity can never be zero in practice.

Here the same class of bug appears as an *arithmetic degenerate case* rather than a literal division by zero: `(0 * 7) % 10 == 0` so `ceil = 0`, and `(0 * 7) / 10 + 0 = 0`, giving `threshold = 0`. There is no explicit guard rejecting `total_weight == 0` before or after this computation in `compute_voting_weight_threshold`, and the caller `verify_signer_signatures` never separately validates that the reward set actually contains a nonzero total weight before comparing against the (possibly zero) threshold — it only checks `total_weight_signed < threshold` [4](#0-3) .

### Impact Explanation
If a reward set with `total_weight == 0` is ever committed (e.g., a reward-cycle boundary/edge case where the computed reward set ends up with no signer weight, or a corrupted/degenerate reward-set entry makes it through this path), any Nakamoto block—regardless of how many or how few valid signer signatures it carries—would pass `verify_signer_signatures` with a "supermajority reached" verdict of `0 >= 0`. This breaks the equality that block acceptance requires signer-weight consensus, i.e. a validation verdict that other, correctly-computed nodes (which would legitimately reject a `total_weight == 0` reward set as un-attestable) would disagree with. This matches the "Critical: an invalid block accepted... network-wide" / "High: a minority-triggerable ... static-validation divergence" impact classes.

### Likelihood Explanation
This requires the reward-set weight computation to yield `total_weight == 0` for some cycle — an edge condition, similar in spirit to the acknowledged-but-considered-unlikely `totalWeightLocked == 0` case in the original report ("no gauge has received any vote"). The report itself was accepted as valid Medium/High severity despite being characterized as unlikely in practice, on the principle that: "causes a loss of funds/consensus divergence but requires certain external conditions or specific states." I was not able to fully trace, within the remaining investigation budget, every code path that constructs the `RewardSet` passed into `verify_signer_signatures` to determine whether `total_signing_weight() == 0` is provably unreachable (e.g., via a hard invariant enforced elsewhere in reward-set construction) or merely believed to be unreachable, mirroring the sponsor's own initial assessment in the source report ("this scenario is unlikely to occur in reality... nevertheless your point is valid").

### Recommendation
Explicitly guard against `total_weight == 0` in `compute_voting_weight_threshold` (or in `verify_signer_signatures` before calling it), returning an error such as `ChainstateError::NoRegisteredSigners` instead of silently producing a threshold of `0` that any signature set — including an empty one — trivially satisfies:
```rust
pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
    if total_weight == 0 {
        return Err(ChainstateError::NoRegisteredSigners(0));
    }
    ...
}
```

### Proof of Concept
1. Construct (or find a path that produces) a `RewardSet` whose `total_signing_weight()` returns `0` (e.g., a reward cycle with signers all of `weight == 0`, or an empty signer list slipping past the earlier `reward_set.signers()` check).
2. Call `NakamotoBlockHeader::verify_signer_signatures` on any `NakamotoBlock` header for that reward set with an **empty** `signer_signature` vector.
3. `total_weight_signed` remains `0`; `compute_voting_weight_threshold(0)` returns `0`; the check `total_weight_signed < threshold` (`0 < 0`) is `false`, so the function returns `Ok(0)` — the block is treated as validly signed with zero real signer weight, despite carrying no signatures at all.

Note: I could not, within the remaining tool budget, definitively confirm whether any upstream code path can actually construct a `RewardSet` with `total_signing_weight() == 0` that reaches `verify_signer_signatures` (this would need tracing `RewardSet` construction across reward-cycle/PoX boundary code, which I did not have iterations left to complete). This is flagged as an analog worth flagging based on the arithmetic pattern matching the reported bug class, but the reachability of `total_weight == 0` for this code path is unverified.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
