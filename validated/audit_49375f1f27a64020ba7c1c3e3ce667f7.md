### Title
Unchecked `--accounts-db-ancient-ideal-storage-size` allows setting the ancient-storage ideal size to zero, causing a validator panic in `collect_sort_filter_ancient_slots` - (File: accounts-db/src/ancient_append_vecs.rs)

### Summary
The ancient-append-vec packing algorithm derives its per-pass "ideal storage size" tuning parameter from an admin-configurable value, `ancient_storage_ideal_size` (exposed via the `--accounts-db-ancient-ideal-storage-size` CLI flag), with no minimum-value validation. This value is combined with a computed quantity and then force-unwrapped into a `NonZeroU64`. If the operator sets the option to `0` (or a value that ends up as the maximum term evaluating to `0`), the `NonZeroU64::new(0).unwrap()` call panics, crashing the validator. This mirrors the reported bug class: an unchecked, operator-settable numeric parameter feeding directly into arithmetic (here, a `NonZeroU64` construction that is later used as a divisor) that the downstream logic assumes is always valid.

### Finding Description
`AccountsDb` stores an ancient-storage sizing default, `DEFAULT_ANCIENT_STORAGE_IDEAL_SIZE`, which is documented as overridable via `--accounts-db-ancient-ideal-storage-size`: [1](#0-0) 

This is threaded through `AccountsDbConfig::ancient_storage_ideal_size: Option<u64>` (a plain `u64`, not `NonZeroU64`, so `0` is a representable/valid value at the config layer): [2](#0-1) 

At runtime, `collect_sort_filter_ancient_slots` recomputes the `PackedAncientStorageTuning::ideal_storage_size` field for every ancient-shrink pass by taking the max of a computed value and the (potentially operator-set) `self.ancient_storage_ideal_size`, then unwraps it into a `NonZeroU64`: [3](#0-2) 

If the operator sets `ancient_storage_ideal_size` to `0`, and in the same pass the computed term `total_alive_bytes * 2 / max_ancient_slots.max(1)` also evaluates to `0` (e.g., when there are no ancient slots with alive bytes yet, or `max_ancient_slots` is large relative to alive bytes), the `.max(0)` no longer protects against zero, and `NonZeroU64::new(0)` returns `None`, so `.unwrap()` panics.

This `ideal_storage_size` value is subsequently used as a divisor in multiple places in the same shrink/ancient-packing pipeline, e.g. `div_ceil` in `truncate_to_max_storages`: [4](#0-3) 

and as a plain divisor in `many_ref_accounts_can_be_moved`: [5](#0-4) 

Even setting aside the immediate panic path, because `ideal_storage_size` is only guaranteed non-zero by the `NonZeroU64` wrapper (rather than being range-validated at the CLI/config layer), an operator-supplied value of `0` (or a pathologically tiny value) defeats the packing algorithm's assumptions the same way `rewardsDuration = 0` breaks `notifyRewardAmount`'s reward-rate division in the referenced report — the setter accepts the value unconditionally and the consuming arithmetic assumes it is sane.

### Impact Explanation
A panic inside `combine_ancient_slots_packed` / `shrink_ancient_slots` — which runs as part of routine background account shrinking — crashes the validator process (node panic due to a misconfigured but operator-controlled parameter). This is a concrete, non-theoretical impact (validator crash), matching the "node panic" acceptance criterion. Because ancient-slot combining runs periodically in the background on every validator, once triggered it can repeatedly panic on restart until the flag is removed/corrected, effectively taking the node offline.

### Likelihood Explanation
This requires an operator to explicitly pass `--accounts-db-ancient-ideal-storage-size 0` (or an unusually small value combined with a state where `total_alive_bytes` computes to zero in a pass). This is a privileged/admin misconfiguration rather than something an unprivileged network participant can trigger remotely, so likelihood is Low, but it is a real, straightforward-to-hit operator error (analogous to the "admin privilege"-contingent Medium severity in the source report) rather than a purely theoretical condition — the code path is reachable through a documented, supported CLI flag with no bounds validation.

### Recommendation
Validate `ancient_storage_ideal_size` (and any other admin-supplied divisor/tuning parameters that feed ancient-append-vec or shrink logic) against a sane minimum (e.g., reject/clamp values below some reasonable floor, similar to how `accounts_shrink_ratio` is range-checked against `0.0..=1.0` in `validator/src/commands/run/execute.rs`) at CLI parsing time, and replace the `.unwrap()` on `NonZeroU64::new(...)` in `collect_sort_filter_ancient_slots` with a saturating fallback to a safe default rather than panicking.

### Proof of Concept
1. Start the validator with `--accounts-db-ancient-ideal-storage-size 0`.
2. Allow the node to run until `shrink_ancient_slots`/`combine_ancient_slots_packed` is invoked with a set of ancient slots whose combined `total_alive_bytes` is `0` for the pass (e.g., all candidate ancient storages have zero alive bytes at that moment).
3. In `collect_sort_filter_ancient_slots`, `(0 * 2 / max_ancient_slots.max(1)).max(0)` evaluates to `0`, and `NonZeroU64::new(0).unwrap()` panics, crashing the validator process.

Note: I was unable to fully confirm, within the available tool budget, whether `validator/src/commands/run/args.rs`/`execute.rs` apply any additional CLI-level bounds validation specifically to `accounts_db_ancient_ideal_storage_size` (I confirmed the flag exists and is wired into `AccountsDbConfig`, but did not get to read the exact parsing/validation lines before running out of iterations). If such validation exists and rejects `0`, this specific zero-value panic path would be mitigated at the CLI layer, though the underlying `.unwrap()` in `ancient_append_vecs.rs` would remain a latent risk for any future caller of `AccountsDbConfig` that does not go through the CLI (e.g., programmatic construction, tests, or other tools).

    fn collect_sort_filter_ancient_slots(
        &self,
        slots: Vec<Slot>,
        tuning: &mut PackedAncientStorageTuning,
    ) -> AncientSlotInfos {
        let mut ancient_slot_infos = self.calc_ancient_slot_info(slots, tuning);
        // ideal storage size is total alive bytes of ancient storages
        // divided by half of max ancient slots
        tuning.ideal_storage_size = NonZeroU64::new(
            (ancient_slot_infos.total_alive_bytes.0 * 2 / tuning.max_ancient_slots.max(1) as u64)
                .max(self.ancient_storage_ideal_size),
        )
        .unwrap();

        ancient_slot_infos.filter_ancient_slots(tuning, &self.shrink_ancient_stats);
        ancient_slot_infos
    }
