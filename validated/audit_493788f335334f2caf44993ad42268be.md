### Title
Double-counting of dead bytes/accounts in `AccountStorageEntry::remove_accounts` can panic the validator via `usize` subtraction underflow - (File: `accounts-db/src/account_storage_entry.rs`)

### Summary
`AccountStorageEntry::remove_accounts` decrements `num_alive_bytes` and `num_alive_accounts` via `fetch_sub` and only *afterwards* asserts that the amount removed did not exceed the value that existed before the subtraction. Because the counters are unsigned (`AtomicUsize`), any underflow wraps before the `assert!` fires, and the caller reaching this state panics the validator process. The code base itself documents a scenario where the same account can be counted as "dead" by two independent paths (zero-lamport single-ref accounting and normal clean/shrink accounting), which is structurally identical to the yVaultLPFarming bug class: an implicit assumption that a monotonically-tracked quantity can only move in one direction, which is not actually guaranteed to hold, and once violated turns a normal accounting update into an underflow.

### Finding Description
`AccountStorageEntry::remove_accounts` computes: [1](#0-0) 

The subtraction happens via `fetch_sub` *before* validation, and the `assert!` is only a post-hoc invariant check, not a guard. If any caller ever passes `num_bytes`/`num_accounts` larger than what is currently tracked as alive (`prev_num_alive_bytes`/`prev_num_alive_accounts`), the atomics wrap around (since they are `usize`), and the subsequent `assert!` panics the process.

The codebase explicitly acknowledges a scenario that can produce exactly this double-decrement: zero-lamport single-ref (ZLSR) accounts are tracked as alive in `num_alive_bytes`, but can independently be marked dead by both the shrink path and a normal `clean` pass: [2](#0-1) 

`remove_dead_accounts` (called from `clean`/`handle_reclaims` and other reclaim paths) is the primary caller of `remove_accounts`, computing `dead_bytes` from account data lengths and invoking `store.remove_accounts(dead_bytes, offsets.len())`: [3](#0-2) 

This is architecturally analogous to the `yVaultLPFarming` finding: the caller assumes `currentBalance` (here, the amount being removed) can never exceed `previousBalance` (the tracked alive total), but that assumption is only "usually" true and is violated whenever an account's aliveness bookkeeping is touched by two different reclaim/dead-accounting code paths (shrink vs. clean vs. obsolete-marking) for the same bytes, exactly as flagged in the storage entry's own doc comment.

### Impact Explanation
An underflow here does not merely fail silently: it causes an `assert!` panic in `AccountStorageEntry::remove_accounts`, which is on the hot path of `clean_accounts`, `handle_reclaims`, and slot removal used continuously by every validator. A panic in this code halts/crashes the validator process (node panic), directly impacting liveness — worse than the original finding's transaction-level DoS, since it affects the whole node rather than a single vault operation.

### Likelihood Explanation
The doc comment in `account_storage_entry.rs` (lines 39–45) is written by the Agave maintainers themselves acknowledging that ZLSR accounts "could be counted as dead twice" between the shrink path and cleanup, and states "this should be fine" — implying the current code relies on the double-count never actually reaching `remove_accounts` with more bytes than are tracked. This is an unenforced invariant spanning multiple independent subsystems (shrink, clean, obsolete-account marking), which is exactly the kind of cross-module assumption that historically breaks under migration/refactor changes (as it did for yVaultLPFarming's farm/strategy migration). No test in the visible code base directly stresses concurrent double-counting between shrink and clean paths to disprove the underflow is unreachable.

### Recommendation
Change `remove_accounts` to validate the subtraction is safe using `checked_sub`/`fetch_update` (compare-and-swap semantics) *before* mutating the atomics, returning an error or clamping to zero instead of allowing a wrapped intermediate value to occur even momentarily. Additionally, audit all callers (clean/shrink/obsolete-marking) to ensure no code path can attempt to remove the same account's bytes from `num_alive_bytes`/`num_alive_accounts` more than once, closing the gap acknowledged in the existing doc comment.

### Proof of Concept
Not independently reproduced against a running validator in this review; the finding is based on direct code inspection of `AccountStorageEntry::remove_accounts` (`accounts-db/src/account_storage_entry.rs:268-289`) combined with the maintainers' own acknowledgment of double-dead-counting for ZLSR accounts (`accounts-db/src/account_storage_entry.rs:36-45`) and the fact that `remove_dead_accounts` in `accounts-db/src/accounts_db.rs:5096-5111` feeds externally-computed byte/account counts directly into this unguarded subtraction.

    /// Removes `num_bytes` and `num_accounts` from the storage,
    /// and returns the remaining number of accounts.
    pub(crate) fn remove_accounts(&self, num_bytes: usize, num_accounts: usize) -> usize {
        let prev_num_alive_bytes = self.num_alive_bytes.fetch_sub(num_bytes, Ordering::Release);
        let prev_num_alive_accounts = self
            .num_alive_accounts
            .fetch_sub(num_accounts, Ordering::Release);

        // enforce invariant that we're not removing too many bytes or accounts
        assert!(
            num_bytes <= prev_num_alive_bytes && num_accounts <= prev_num_alive_accounts,
            "Too many bytes or accounts removed from storage! slot: {}, id: {}, initial num alive \
             bytes: {prev_num_alive_bytes}, initial num alive accounts: \
             {prev_num_alive_accounts}, num bytes removed: {num_bytes}, num accounts removed: \
             {num_accounts}",
            self.slot,
            self.id,
        );

        // SAFETY: subtraction is safe since we just asserted num_accounts <= prev_num_accounts
        prev_num_alive_accounts - num_accounts
    }
