## Analog Found

### Title
Uncaught panic in gateway state reader on declared-class/class-manager inconsistency causes persistent transaction-validation denial of service - (File: `crates/apollo_gateway/src/sync_state_reader.rs`)

### Summary
The Part-DB bug is a class of vulnerability where a piece of user-influenced state passes an initial superficial check but later access of that same state triggers an *uncaught exception*, permanently breaking every subsequent attempt to access it. The sequencer analog is in `SyncStateReader::get_contract_class_from_client`, which first asks state-sync storage "is this class declared?" and, if so, unconditionally assumes the class manager must have the executable — and calls `panic!()` if it doesn't.

### Finding Description
`SyncStateReader::get_contract_class_from_client` in `crates/apollo_gateway/src/sync_state_reader.rs` implements the following logic: [1](#0-0) 

It queries `state_sync_client.is_class_declared_at(...)` (backed by the local storage's `declared_classes` table) and, if that returns `true`, queries the class manager for the executable class via `class_manager_client.get_executable(class_hash)`. If the class manager doesn't have it — `.unwrap_or_else(|| panic!(...))` — the thread panics instead of returning a `StateResult` error.

This function backs `get_compiled_class` and `get_compiled_classes`, which are invoked by the blockifier during **stateful validation of every transaction** that touches a contract of that class hash (e.g., an `Invoke` calling the contract, or an `Account`/constructor deployed with that class hash) — see the call sites at: [2](#0-1) [3](#0-2) 

The state-sync storage (`declared_classes` table) and the class manager's file-backed class storage (`FsClassStorage`) are two independently-persisted subsystems. Their invariant — "declared implies executable class present in class manager" — is enforced only by best-effort ordering/retry logic in the sync pipelines (`crates/apollo_central_sync/src/lib.rs`, `crates/apollo_p2p_sync/src/client/class.rs`), not by any atomic transaction across the two stores. This exact scenario is even codified in a test expecting the panic as "correct" behavior: [4](#0-3) 

Once the invariant is violated for a given `class_hash` (e.g., through a crash/restart window, a partial write recovered incorrectly, or any transient class-manager storage gap), **every future transaction referencing that class hash permanently panics during gateway stateful validation** — there is no path to clear the bad state without manual operator intervention, mirroring Part-DB's "permanently inaccessible via the UI" failure mode.

### Impact Explanation
A panic inside the gateway's synchronous validation path (invoked via `tokio::runtime::Handle::block_on` from the transaction-processing thread) either:
- kills the request-handling task for that transaction (denial of service for anyone submitting a transaction that touches the affected class), or
- if triggered on a shared blocking-pool thread that isn't unwind-safe/caught, can bring down the gateway component's request-processing capacity entirely for the process.

Because the corrupted state is keyed by `class_hash` and persists indefinitely in storage, **every account/contract deployed with that class hash becomes permanently unable to have any of its transactions validated**, and the network is unable to confirm new transactions for those accounts until an operator manually repairs storage — a persistent denial of service matching the "network unable to confirm new transactions" acceptance criterion.

### Likelihood Explanation
The trigger condition (declared-but-missing-executable) is not attacker-arbitrary but is a real, reachable inconsistency window inherent to the split-storage design (state-sync DB vs. class-manager `FsClassStorage`) that the codebase's own recovery code and tests (`crates/apollo_class_manager/src/class_storage.rs` orphaned-directory recovery, `crates/apollo_gateway/src/sync_state_reader_test.rs`) acknowledge can occur, e.g. via crash/restart timing, replay of the compiled-classes stream, or a class-manager write failure that isn't perfectly mirrored by storage rollback. Any subsequent, entirely ordinary transaction (Invoke/Declare/DeployAccount) that references the affected class hash deterministically re-triggers the panic — no special privileges are required to submit it.

### Recommendation
Replace the `panic!()` in `get_contract_class_from_client` with a typed `StateError` (e.g., `StateError::StateReadError` or a dedicated inconsistency variant) so the gateway can gracefully reject the specific transaction (or retry/backoff) instead of crashing the validation path. Additionally, add reconciliation/self-healing logic (or alerting) so that a declared-but-unexecutable class is detected and repaired rather than causing a permanent, unrecoverable per-class outage.

### Proof of Concept
1. Induce (or simulate in a test, as `sync_state_reader_test.rs` already does) a state where `state_sync_client.is_class_declared_at(block, class_hash)` returns `true` for some `class_hash`, but `class_manager_client.get_executable(class_hash)` returns `None` (e.g., via crash-recovery timing between the state-diff commit and the class-manager write, or a corrupted/incompletely-synced class-manager store).
2. Submit any ordinary `Invoke` transaction whose sender or called contract is deployed with `class_hash`, or a `DeployAccount`/`Declare` referencing it.
3. Gateway stateful validation calls `SyncStateReader::get_compiled_class` → `get_contract_class_from_client`, hits the `unwrap_or_else(|| panic!(...))` branch, and the thread panics.
4. Repeat step 2 with any other transaction touching the same class hash — the panic recurs indefinitely, permanently denying validation for that class. [1](#0-0)

    fn get_contract_class_from_client(&self, class_hash: ClassHash) -> StateResult<ContractClass> {
        let is_class_declared = self
            .runtime
            .block_on(self.state_sync_client.is_class_declared_at(self.block_number, class_hash))
            .map_err(|e| StateError::StateReadError(e.to_string()))?;

        if !is_class_declared {
            return Err(StateError::UndeclaredClassHash(class_hash));
        }

        let contract_class = self
            .runtime
            .block_on(self.class_manager_client.get_executable(class_hash))
            .map_err(|e| StateError::StateReadError(e.to_string()))?
            .unwrap_or_else(|| {
                panic!(
                    "Class with hash {class_hash:?} doesn't appear in class manager even though \
                     it was declared"
                )
            });

        Ok(contract_class)
    }
