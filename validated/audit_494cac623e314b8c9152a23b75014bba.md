## Title
Receipt size-limit bypass via post-validation `output_data_receivers` mutation causes real byte size to diverge from the size accounted against outgoing/congestion byte budgets — (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
NEAR enforces a hard `max_receipt_size` on newly created receipts and a family of hard/soft byte budgets (`outgoing_receipts_usual_size_limit`, `outgoing_receipts_big_size_limit`, witness size caps) that are all designed to bound `ChunkStateWitness` to a documented ~21 MiB total. A single unprivileged contract call can create a receipt whose *validated* size is at the limit, then have its `output_data_receivers` extended **after** that validation, and later have its outgoing-forwarding accounting *clamp the counted size back down to `max_receipt_size`* even though the real serialized receipt is larger. The result is the same class of bug as the reported GitLab CVE: a value used for a size/quota check is decoupled from the true payload size, letting a low-privileged caller push more real bytes through the system than the accounting believes it consumed.

### Finding Description
1. Receipt size is only validated once, at creation time, in `validate_receipt` (`runtime/runtime/src/verifier.rs:680-696`) via `ValidateReceiptMode::NewReceipt`. The doc comment on `ValidateReceiptMode::ExistingReceipt` explicitly acknowledges: *"There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed. See https://github.com/near/nearcore/issues/12606"* (`runtime/runtime/src/verifier.rs:727-739`).
2. The concrete mutation-after-validation path is in `runtime/runtime/src/lib.rs:1152-1170`: when a `FunctionCall` result is a `ReturnData::ReceiptIndex`, the runtime `extend_from_slice`s the *caller's* `output_data_receivers` onto an already newly-created (and already size-validated) receipt, growing it past `max_receipt_size` without re-running `validate_receipt`. `test-loop-tests/src/tests/max_receipt_size.rs:124-208` (`test_max_receipt_size_promise_return`) and `:210-267` (`test_max_receipt_size_value_return`) both demonstrate this concretely: a receipt validated at exactly `max_receipt_size` is later inflated above the limit and is *not* rejected.
3. The oversized receipt does not just sit inertly — it is fed into the cross-shard forwarding path. `try_forward` in `runtime/runtime/src/congestion_control.rs:403-463` explicitly clamps the counted `size` down to `max_receipt_size` *only for comparison and bookkeeping purposes* ("Let's pretend that all receipts are at most `max_receipt_size` to avoid receipts getting stuck", `:413-427`), then pushes the real (larger) `receipt` while decrementing `forward_limit.size -= size` using the artificially small clamped value (`:451-458`). `buffer_receipt` (`:465-500`) similarly records `own_congestion_info.add_receipt_bytes(size)` and the outgoing metadata using the same clamped `size`, not the true wire size.
4. This is a direct analog of the reported bug class: a value (receipt byte size) that gates a resource/size limit is decoupled from reality after the check has already passed, so the accounted "repository size"/"receipt size" understates the real payload that ultimately gets included and transmitted.

### Impact Explanation
The per-shard outgoing byte budgets (`outgoing_receipts_usual_size_limit` = 100 KiB, `outgoing_receipts_big_size_limit` = 4.5 MiB) and the overall witness size caps (`MAX_UNCOMPRESSED_STATE_WITNESS_SIZE` = 64 MiB, `MAX_COMPRESSED_STATE_WITNESS_SIZE` = 48 MiB, documented total ≈21 MiB budget in `docs/misc/state_witness_size_limits.md`) exist specifically to keep `ChunkStateWitness` distributable. Because the true byte size of a forwarded receipt can exceed what is charged against these budgets, a malicious low-privileged account can cause the actual outgoing/witness payload to grow beyond the sizes the protocol believes it is enforcing, degrading the guarantee the whole size-limit system is built on. Because forwarding, buffering and witness assembly are otherwise deterministic across all validators, this does not directly cause state-root divergence, but repeated abuse can push witnesses past hard size caps that are enforced elsewhere (`validate_partial_encoded_state_witness`, `chain/client/src/stateless_validation/validate.rs:83-109`), causing chunk validators to reject/drop the witness and chunk producers to repeatedly fail to get a shard's chunk endorsed — a transaction-triggered degradation/halt of chunk production for the affected shard.

### Likelihood Explanation
Reachable purely with a standard `FunctionCall` transaction from any funded account: deploy an ordinary contract, create a promise chain, and use `promise_return`/large `value_return` to build a receipt at exactly `max_receipt_size`, then let the runtime append `output_data_receivers` afterward (exactly what the existing regression tests already reproduce). No validator, network, or operator privilege is required — only a signed transaction and enough attached gas.

### Recommendation
Re-validate the final receipt size (via `validate_receipt` with `NewReceipt` semantics) after `output_data_receivers` are appended in `runtime/runtime/src/lib.rs:1152-1170`, rejecting/erroring the action if the post-mutation size exceeds `max_receipt_size`. Separately, `try_forward`/`buffer_receipt` in `runtime/runtime/src/congestion_control.rs` should account outgoing/congestion byte budgets using the receipt's true serialized size rather than a size clamped down to `max_receipt_size`, so that the "avoid receipts getting stuck" workaround for issue #12606 does not simultaneously let the real payload evade the byte-budget accounting it is supposed to be measured against.

pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,

    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");

            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    fn try_forward(
        receipt: Receipt,
        gas: Gas,
        mut size: u64,
        shard: ShardId,
        outgoing_limit: &mut HashMap<ShardId, OutgoingLimit>,
        outgoing_receipts: &mut Vec<Receipt>,
        apply_state: &ApplyState,
        stats: &mut ReceiptSinkStats,
    ) -> Result<ReceiptForwarding, RuntimeError> {
        // There is a bug which allows to create receipts that are above the size limit. Receipts
        // above the size limit might not fit under the maximum outgoing size limit. Let's pretend
        // that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
        // See https://github.com/near/nearcore/issues/12606
        let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
        if size > max_receipt_size {
            tracing::debug!(
                target: "runtime",
                receipt_id=?receipt.receipt_id(),
                size,
                max_receipt_size,
                "try_forward observed a receipt with size exceeding the size limit",
            );
            size = max_receipt_size;
        }

        // Default case set to `Gas::MAX`: If no outgoing limit was defined for the receiving
        // shard, this usually just means the feature is not enabled. Or, it
        // could be a special case during resharding events. Or even a bug. In
        // any case, if we cannot know a limit, treating it as literally "no
        // limit" is the safest approach to ensure availability.
        let default_gas_limit = Gas::MAX;

        // Since bandwidth scheduler, a shard is not allowed to send any receipts if it doesn't have a grant.
        let default_size_limit = 0;

        let default_outgoing_limit =
            OutgoingLimit { gas: default_gas_limit, size: default_size_limit };
        let forward_limit = outgoing_limit.entry(shard).or_insert(default_outgoing_limit);

        let admission_gas = if ProtocolFeature::ClampOutgoingGasAdmission
            .enabled(apply_state.current_protocol_version)
        {
            gas.min(apply_state.config.congestion_control_config.allowed_shard_outgoing_gas)
        } else {
            gas
        };

        if forward_limit.gas >= admission_gas && forward_limit.size >= size {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "forwarding buffered receipt");
            outgoing_receipts.push(receipt);
            forward_limit.gas = forward_limit.gas.saturating_sub(gas);
            forward_limit.size -= size;
            stats.forwarded_receipts.entry(shard).or_default().add_receipt(size, gas);

            Ok(ReceiptForwarding::Forwarded)
        } else {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "not forwarding buffered receipt");
            Ok(ReceiptForwarding::NotForwarded(receipt))
        }
    }
