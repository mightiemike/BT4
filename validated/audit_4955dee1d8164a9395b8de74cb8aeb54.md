### Title
`ensure_match_transaction_info` omits state/hot-state/position checkpoint-hash verification, allowing replay-verify tooling to silently accept a corrupted or forked state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single-transaction integrity check used by replay/backup-verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a locally re-executed `TransactionOutput` matches the authenticated, on-chain `TransactionInfo` for a given version. The function checks transaction status, gas used, write-set hash (`state_change_hash`), and event-root hash, but it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that authenticate the Sparse-Merkle/JMT state root, hot-state root, and native-trading position-state root that are committed into `TransactionInfoV1` and folded into the transaction accumulator.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  performs four checks (status, gas, write-set hash, event-root hash) and then returns `Ok(())`. The trailing comment in the code itself documents the gap: [2](#0-1) 

This function is the sole correctness oracle used by the archive replay-verifier's `execute_and_verify` loop: [3](#0-2) 

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as separate, independently-committed fields (assembled in `DoLedgerUpdate::assemble_transaction_infos`): [4](#0-3) 

These checkpoint hashes are exactly the roots that `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` are designed to make "consensus-verified" per the feature-flag documentation: [5](#0-4) 

Because `ensure_match_transaction_info` never compares these fields against the locally recomputed values, any divergence between the archived/committed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` and what local re-execution would produce is invisible to `replay_on_archive` (and to the CLI/debugger callers that reuse this same function). A wrong state root, a corrupted JMT/position-tree write, or a hard-fork-only divergence in the position/hot-state subsystem would not surface as a replay failure — the exact "committed state differs from correct VM result" and "wrong ... state proof accepted as valid" conditions covered by the state-integrity gate.

### Impact Explanation
Replay-verification and archive-verification tooling exists specifically to catch mismatches between on-chain committed state and locally re-executed state (used, e.g., after chain upgrades, in backup verification pipelines, and by node operators auditing archives). With `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `HOT_STATE_ROOT_IN_TXN_INFO` enabled, this verifier will report a transaction as "matching" even when its authenticated position-state root or hot-state root is wrong, masking:
- A corrupted/incorrect native-position or hot-state Jellyfish Merkle root committed to the ledger accumulator.
- A silent hard-fork-only divergence in the trading-native or hot-state subsystems that would otherwise be the primary detection mechanism for replay-verify.

This is a proof/verification-integrity gap rather than a consensus-safety bypass by itself (the accumulator/ledger-info signature checks elsewhere still bind the committed `TransactionInfo` to its accumulator leaf), but it defeats the intended safety net that is supposed to catch exactly this class of corruption before it reaches production tooling and operators. Given the explicit TODO acknowledging this is a known gap tied to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, the risk is concrete and immediate once that feature is turned on.

### Likelihood Explanation
The gap is unconditional in the current code — `ensure_match_transaction_info` always skips these three fields regardless of feature-flag state, though it only becomes practically exploitable/relevant once `TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, and/or `COMPUTE_TRADING_NATIVE_STATE_ROOTS` are enabled on-chain (these flags exist in the codebase, are used by `BlockExecutorConfigFromOnchain::with_features`, and are exercised by smoke tests). No malicious actor input is required to trigger the missed check — it is a latent gap in the verifier itself, matching the "unprivileged root cause" requirement.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (where present in `txn_info`) against the expected values, mirroring the existing `write_set_hash`/`event_root_hash` pattern, and fail loudly (as the other checks do) on mismatch. This should be done before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet, as the code comment itself recommends.

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1`, `HOT_STATE_ROOT_IN_TXN_INFO`, and `COMPUTE_TRADING_NATIVE_STATE_ROOTS`.
2. Suppose a bug (in the native-position tree merklization, hot-state root computation, or storage commit path) causes the locally-recomputed `hot_state_checkpoint_hash` or `position_state_checkpoint_hash` to diverge from the value committed in the archived `TransactionInfoV1` for some version (write-set hash, events, gas, and status all still match, since those subsystems don't necessarily affect the checked fields).
3. Run `storage/db-tool/src/replay_on_archive.rs` (`Verifier::verify` → `execute_and_verify` → `TransactionOutput::ensure_match_transaction_info`) against the archive.
4. Because `ensure_match_transaction_info` only checks status/gas/write_set hash/event-root hash [6](#0-5) , the verifier reports success for this transaction, even though its authenticated state/hot-state/position root is wrong — confirming the gap documented in the adjacent TODO [2](#0-1) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
