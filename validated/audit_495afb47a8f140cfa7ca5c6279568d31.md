### Title
Uncaught DOMException in `sanitizeHost` due to invalid-length base64 `host` param crashing auth handler - (File: packages/apps/shopify-api/lib/utils/shop-validator.ts)

### Summary
`sanitizeHost` validates the `host` query parameter with a permissive regex `^[0-9a-zA-Z+/]+={0,2}$` that does not enforce base64 length/padding correctness, then unconditionally calls `decodeHost(sanitizedHost)` (which calls `atob`) and `new URL()` without a try/catch. An attacker-controlled `host` string like `"A"` (length ≡ 1 mod 4) passes the regex but is invalid base64, causing `atob` to throw a `DOMException`/`SyntaxError` that propagates uncaught through `sanitizeHost` and into callers such as `validateShopAndHostParams`.

### Finding Description
`sanitizeHost` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` uses `base64regex = /^[0-9a-zA-Z+/]+={0,2}$/` [2](#0-1)  to test the raw `host` string. This regex only checks the character set and optional trailing padding (0–2 `=`), but never validates that the string length is a multiple of 4 (a requirement for valid base64/`atob`). Strings such as `"A"`, `"AB"`, or any base64-alphabet string whose length is ≡ 1 mod 4 pass the regex but are invalid base64.

When `sanitizedHost` is truthy, the code immediately calls `decodeHost(sanitizedHost)` [3](#0-2) , which wraps the global `atob`. Node's `atob` implements the WHATWG forgiving-base64 decode algorithm, which throws a `DOMException`/`InvalidCharacterError` when the input length modulo 4 equals 1 (and in other malformed cases). This call, along with the subsequent `new URL(https://${...})`, is not wrapped in try/catch inside `sanitizeHost`.

This function is called directly from `validateShopAndHostParams` in shopify-app-remix and shopify-app-react-router: `const host = api.utils.sanitizeHost(url.searchParams.get('host')!);` [4](#0-3)  with no surrounding try/catch there either. The caller `authenticateAdmin` wraps this call in try/catch [1](#0-0) , but that catch only special-cases `Response` instances for CORS headers and always re-throws the error — it does not convert this DOMException into a graceful `InvalidHostError`/login redirect. So the exception ultimately escapes `authenticateAdmin` as an unhandled exception, rather than failing closed with the intended `InvalidHostError`.

Existing test coverage (`shop-validator.test.ts`) only exercises well-formed base64-alphabet strings without correct padding awareness for the "invalid" test cases (e.g., `'plain-string-is-not-base64'` — length not congruent to malformed edge case that reliably reproduces the crash) [5](#0-4) , so this specific malformed-length edge case is not covered or guarded against.

### Impact Explanation
This is a Denial-of-Service in an authentication-handling code path: any unauthenticated client can trigger an unhandled exception in `sanitizeHost`, which propagates through `validateShopAndHostParams` and `authenticateAdmin`, causing the request to fail with an uncaught error/500 instead of the intended fail-closed `InvalidHostError` → redirect-to-login behavior. This matches Shopify's "DoS in an authentication handler" impact class. It does not, on its own, allow session/token forgery, cross-tenant access, or secret disclosure — the impact is limited to request-level failure/crash on the `host` validation path.

### Likelihood Explanation
No privileges are required: an anonymous attacker only needs to send a GET request with a `shop` value that passes `sanitizeShop` and a crafted `host` value (e.g., `"A"`) that passes `base64regex` but is invalid base64 length. This works against the default configuration, requires no secrets, and is trivially repeatable per-request.

### Recommendation
In `sanitizeHost` (`packages/apps/shopify-api/lib/utils/shop-validator.ts`), either:
1. Strengthen `base64regex` to enforce proper base64 length (e.g., `/^(?:[A-Za-z0-9+/]{4})*(?:[A-Za-z0-9+/]{2}==|[A-Za-z0-9+/]{3}=)?$/` or equivalent length%4 check), or
2. Wrap the `decodeHost(sanitizedHost)` and `new URL(...)` calls in a try/catch that sets `sanitizedHost = null` on any thrown error (mirroring the existing fail-closed behavior for regex mismatches), before optionally throwing `InvalidHostError` when `throwOnInvalid` is set.
