### Title
Incorrect JSON-RPC transaction status reporting for failed non-EVM transactions - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/types/TransactionReceipt.java])

### Summary
The `TransactionReceipt` constructor derives the Ethereum-style `status` field solely from `txInfo.getReceipt().getResultValue()` (the TVM-specific `contractResult` enum), treating both `DEFAULT` (0) and `SUCCESS` (1) as success. This ignores the transaction-level `TransactionInfo.result` (`code.SUCESS`/`code.FAILED`), which is the actual indicator of whether the transaction succeeded on-chain.

### Finding Description
The status assignment is: [1](#0-0) 

The `contractResult` enum is defined as: [2](#0-1) 

`DEFAULT = 0` is the protobuf default/unset value for `contractRet`. It is only meaningfully populated by the TVM execution path in `RuntimeImpl.setResultCode`, which always assigns one of `SUCCESS`, `REVERT`, or an error code once a smart-contract-related runtime executes: [3](#0-2) 

For transaction types that do not go through the TVM runtime (e.g., TRC10 asset transfers, exchange operations, proposal contracts, etc.), the `ResourceReceipt.result` field is never explicitly set and remains at its protobuf default of `0` (`DEFAULT`) — regardless of whether the actuator actually threw a `ContractExeException`/`ContractValidateException` and the transaction was marked `FAILED` at the transaction-info level (`TransactionInfo.result` = `code.FAILED`, fee still deducted). Because the code only checks `getResultValue() <= 1`, any such failed non-EVM transaction is reported as `status = "0x1"` (success) via JSON-RPC `eth_getTransactionReceipt`, when the on-chain outcome was actually a failure.

### Impact Explanation
Any unprivileged party can submit a transaction (e.g., a TRC10-related or other non-smart-contract contract type) that gets included in a block but fails execution at the actuator level. Third-party systems that integrate with TRON via the Ethereum-compatible JSON-RPC interface (bridges, exchanges, payment processors) commonly rely on `status == "0x1"` to confirm a transaction succeeded before crediting funds or triggering downstream actions. A misreported success status for an actually-failed transaction can cause automated systems to treat a failed operation as successful, leading to state divergence between the reported receipt and the real on-chain outcome and potential value-crediting errors in relying systems.

### Likelihood Explanation
This requires no privileged access — any user can submit a transaction of a type whose actuator can fail post-inclusion (fee charged, action not applied) without going through TVM's `setResultCode`. The condition is deterministic and repeatable: any transaction whose `ResourceReceipt.contractRet` remains `DEFAULT(0)` while `TransactionInfo.result == FAILED` triggers the mis-reporting every time it is queried via JSON-RPC.

### Recommendation
Compute `status` from the authoritative transaction-level result (`txInfo.getResult()`, i.e., `TransactionInfo.code`), falling back to `contractResult` only to distinguish `REVERT` vs. other EVM-specific failure states for smart-contract calls. E.g.:
```java
this.status = txInfo.getResult() == TransactionInfo.code.SUCESS ? "0x1" : "0x0";
```
or explicitly special-case `DEFAULT` to defer to `txInfo.getResult()` rather than assuming success.

### Proof of Concept
Java unit test plan (in `framework/src/test/java/org/tron/core/services/jsonrpc/types/`):
1. Build a `TransactionInfo` where `receipt.contractResult` is left unset (defaults to `DEFAULT`/0) and `result` is set to `TransactionInfo.code.FAILED` (simulating a non-EVM actuator failure, e.g., `resMessage` populated with an error, fee > 0).
2. Construct a `BlockCapsule` containing a corresponding non-`TriggerSmartContract`/non-`CreateSmartContract` transaction (e.g., a `TransferAssetContract`).
3. Instantiate `new TransactionReceipt(blockCapsule, txInfo, context, energyFee)`.
4. Assert that `receipt.getStatus()` equals `"0x0"` (expected, correct behavior) — the test will fail against current code because it returns `"0x1"`, demonstrating the divergence between the actual failed execution and the reported JSON-RPC status.
