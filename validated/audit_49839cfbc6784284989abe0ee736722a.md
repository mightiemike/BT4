### Title
Attacker-Controlled Unbounded Growth of `DelegatedResourceAccountIndexCapsule` Causes O(n) List-Rebuild Cost on Victim's Unfreeze — Analog of Attacker-Grown Iterated Array DoS - ([File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java])

### Summary
The external report describes a denial-of-service pattern where an attacker can freely grow an array that belongs to (or is associated with) a victim, and that array is later iterated/rebuilt during a normal victim operation, causing gas/CPU cost proportional to the attacker-inflated array size. In java-tron's legacy (pre-`AllowDelegateOptimization`) resource-delegation model, the same structural weakness exists: any funded account can unilaterally append entries to an arbitrary victim address's `DelegatedResourceAccountIndexCapsule.fromAccountsList` by calling `FreezeBalanceContract` with that victim as `receiverAddress` — no consent or signature from the victim is required. Later, when the victim (receiver) is party to *any* unfreeze operation that clears a delegation relationship, `UnfreezeBalanceActuator.execute` rebuilds the victim's entire `fromAccountsList` by copying it into an `ArrayList`, calling `.remove()`, and writing it back with `setAllFromAccounts` — an O(n) operation whose cost is fully controlled by the attacker's prior actions, executed inside consensus-critical actuator logic that is priced at a fixed fee of 0.

### Finding Description
`FreezeBalanceActuator.delegateResource` (lines 289–370) is invoked whenever a `FreezeBalanceContract` specifies a `receiverAddress` for BANDWIDTH/ENERGY delegation: [1](#0-0) 

The receiver's index capsule is fetched or created and a new entry is unconditionally appended to its `fromAccountsList` if not already present — the receiver never signs or otherwise consents to this: [1](#0-0) 

`validate()` only requires that the receiver account exists and is not a contract when `AllowTvmConstantinople` is enabled — it does not require any relationship or consent from the receiver, and the minimum freeze is only 1 TRX: [2](#0-1) [3](#0-2) 

An attacker who controls (or cheaply creates) many distinct owner accounts, each freezing the minimum 1 TRX and delegating to the same victim `receiverAddress`, can grow the victim's `fromAccountsList` without bound, entry by entry, since each distinct owner→victim pair is a unique element (uniqueness is checked per-owner side only, not capped).

Later, when the victim account is involved as the `receiverAddress` side of *any* single unfreeze operation that fully clears one delegated-resource relationship (frozen balance reaches zero for both bandwidth and energy for that pair), the non-optimized path fully materializes, copies, mutates and rewrites the entire `fromAccountsList`: [4](#0-3) 

The cost of this rebuild (`ArrayList` copy, linear `.remove()`, `setAllFromAccounts` which clears and re-adds every element to the protobuf builder) scales linearly with the number of entries in `fromAccountsList` — a quantity entirely controlled by the attacker, not by the victim. `calcFee()` for both `FreezeBalanceActuator` and `UnfreezeBalanceActuator` returns 0, so this asymmetric CPU cost imposed on block-producing nodes is not compensated by any dynamic fee: [5](#0-4) 

Additionally, the same unbounded list is exposed via read-only RPC/HTTP endpoints (`GetDelegatedResourceAccountIndex`, `/wallet/getdelegatedresourceaccountindex`), which will return an ever-growing response for the affected address: [6](#0-5) [7](#0-6) 

This class of behavior was demonstrated to be problematic in the reported test `testMultiFreezeDelegatedBalanceForBandwidth`, which builds a `DelegatedResourceAccountIndexCapsule` with 100 pre-populated `toAccount` entries to exercise this exact list-mutation path: [8](#0-7) 

### Impact Explanation
Because `calcFee()` is 0 for both `FreezeBalanceActuator` and `UnfreezeBalanceActuator`, and delegation to a receiver requires only a minimal 1 TRX freeze with no consent from the receiver, an attacker can cheaply and unilaterally inflate the size of a specific victim account's `DelegatedResourceAccountIndexCapsule.fromAccountsList` to an arbitrarily large N (bounded only by how many distinct sender accounts/relations the attacker is willing to fund). Any subsequent unfreeze transaction touching that account as receiver — potentially triggered by the victim themselves, or even by the same attacker unwinding their own delegations — forces the node executing that transaction (during block validation/execution) to perform O(N) work rebuilding the protobuf-backed list, with no fee compensation. This is a computational resource-exhaustion / node-performance DoS vector directly analogous to the reported `getBadgeMultiplier`/`delegatesOf` bug, though bounded in severity by the requirement to fund at least 1 TRX per delegation relation (unlike the ERC1155-report's essentially free `delegateBadgeTo` calls). It also produces unbounded RPC response sizes for `GetDelegatedResourceAccountIndex`.

### Likelihood Explanation
Medium. The attack is reachable purely through normal, unprivileged, publicly broadcastable `FreezeBalanceContract` transactions (no special permission, no P2P/node compromise, no leaked keys) and requires only that the legacy (non-`AllowDelegateOptimization`) delegation path still be reachable. However, exploitation cost scales with the number of distinct funded accounts the attacker needs (1 TRX + fees per relation), and modern mainnet TRON networks have largely migrated to `AllowDelegateOptimization`/`delegateV2` flows, which store one DB key per relation (`convert`/`delegate` in `DelegatedResourceAccountIndexStore`) rather than a single-growing-list capsule, mitigating this specific issue for chains where that feature has been activated. The severity is therefore highest on networks/forks where the legacy path (`supportAllowDelegateOptimization() == false`) is still active.

### Recommendation
- Cap the number of entries permitted in `DelegatedResourceAccountIndexCapsule.toAccountsList` / `fromAccountsList` (e.g., enforce a maximum count in `FreezeBalanceActuator.validate()`/`delegateResource`), independent of `AllowDelegateOptimization`.
- Ensure all networks migrate to and permanently enable the per-relation key-based `DelegatedResourceAccountIndexStore.delegate/unDelegate` model (already used when `supportAllowDelegateOptimization()` is true), and consider removing/hard-disabling the legacy single-list code path in `FreezeBalanceActuator`/`UnfreezeBalanceActuator` to eliminate the unbounded-list rebuild cost entirely.
- Introduce fee/energy accounting proportional to the size of `fromAccountsList`/`toAccountsList` mutated during freeze/unfreeze so unbounded growth is economically disincentivized rather than free.

### Proof of Concept
1. Ensure the target java-tron network has `AllowDelegateOptimization` disabled (legacy path), i.e. `dynamicPropertiesStore.supportAllowDelegateOptimization() == false`.
2. Choose victim address `V`.
3. For `i = 1..N`: create/fund a fresh account `A_i` with ≥1 TRX, broadcast `FreezeBalanceContract{ownerAddress=A_i, receiverAddress=V, frozenBalance=1_000_000 (1 TRX), resource=BANDWIDTH}`. Each transaction appends one entry to `V`'s `DelegatedResourceAccountIndexCapsule.fromAccountsList` per `FreezeBalanceActuator.delegateResource` (lines 334–345 of `FreezeBalanceActuator.java`).
4. Repeat for large N (e.g., tens of thousands), each transaction being independently cheap and valid.
5. Trigger any `UnfreezeBalanceContract` that fully clears one owner→`V` delegated relationship (e.g., unfreeze `A_1`'s delegation to `V` after the freeze duration elapses). This causes `UnfreezeBalanceActuator.execute` to fetch, copy, mutate, and rewrite `V`'s entire `fromAccountsList` of size N (lines 174–182 of `UnfreezeBalanceActuator.java`), imposing O(N) CPU cost on the executing node for a transaction priced at fee 0.
6. Observe CPU/latency cost of block processing scaling with attacker-chosen N, and unbounded response size from `GetDelegatedResourceAccountIndex`/`/wallet/getdelegatedresourceaccountindex` for address `V`.
