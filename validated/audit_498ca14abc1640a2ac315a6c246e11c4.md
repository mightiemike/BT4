## Title
Unvalidated `RevertInstructions.FundRecipient` format lets attacker's own inbound corrupt the on-chain revert recipient, permanently misdirecting refunds to a garbage/zero address - ([File: x/uexecutor/keeper/build_revert_outbound.go])

### Summary
`buildRevertOutbound` copies `inbound.RevertInstructions.FundRecipient` verbatim into the queued `INBOUND_REVERT` outbound's `Recipient` field with no format validation against the destination (source) chain's namespace. `LenientCanonicalizeAddress` (called from `Inbound.Canonicalize`) never rejects malformed input — on parse failure it silently falls back to the trimmed raw string — and `Inbound.ValidateForExecution` never checks `RevertInstructions.FundRecipient` at all. The unvalidated value is later fed into the EVM outbound tx builder's `ethcommon.HexToAddress(data.Recipient)`, which itself never errors on malformed hex, silently producing an unintended (frequently zero) address that gets ABI-encoded and TSS-signed for broadcast to the Vault contract.

### Finding Description
The revert-recipient handling has three successive gaps that together let a caller-supplied, wrong-namespace address string flow untouched all the way into a signed on-chain transaction:

1. **Canonicalization is lenient by design and doesn't reject cross-namespace formats.** `Inbound.Canonicalize()` calls `utils.LenientCanonicalizeAddress(p.SourceChain, p.RevertInstructions.FundRecipient)`: [1](#0-0) 
`LenientCanonicalizeAddress` explicitly returns the trimmed raw string, unchanged, whenever the value doesn't parse for the given chain namespace: [2](#0-1) 
So a Solana base58 pubkey submitted as `FundRecipient` on an `eip155:...`-sourced inbound fails `CanonicalizeEVMAddress` and is stored as-is.

2. **`ValidateForExecution` never checks `RevertInstructions.FundRecipient` format at all.** It validates `Amount`, `AssetAddr`, and (conditionally) `Recipient`, but has no branch touching `RevertInstructions`: [3](#0-2) 

3. **`buildRevertOutbound` uses the raw, unvalidated value directly as the outbound `Recipient`.** [4](#0-3) 
This outbound is then attached to `PendingOutbounds` for TSS signing with no further recipient validation: [5](#0-4) 

4. **The universalClient EVM tx builder also doesn't validate the recipient before encoding it into the signed calldata.** `target := ethcommon.HexToAddress(data.Recipient)` is used directly with no error check: [6](#0-5) 
go-ethereum's `HexToAddress`/`FromHex` never returns an error for malformed hex — it silently decodes whatever valid hex prefix exists (often nothing, for a base58 string) and left/right-pads to 20 bytes, typically yielding the zero address for non-hex input. The signing request built in `GetOutboundSigningRequest` (lines 83-154 of the same file) validates `TxID`, `DestinationChain`, `GasPrice`, `GasLimit`, and `Amount`, but never `Recipient`.

The attacker fully controls this path through an ordinary deposit: they submit a source-chain gateway call (e.g. `addFunds`) with `revertInstructions.fundRecipient` set to a foreign-namespace string, and then cause their own inbound to require a revert (e.g. a `FUNDS_AND_PAYLOAD` inbound whose attacker-supplied payload reverts, or a `FUNDS` deposit that fails at `depositPRC20`). Honest Universal Validators faithfully observe and vote on the real on-chain event data — no malicious UV/TSS/relayer is required — and the malformed `FundRecipient` flows through consensus into a `PENDING` outbound that honest TSS signers will sign and broadcast as-is.

### Impact Explanation
The resulting on-chain `revertUniversalTx`/`finalizeUniversalTx`-style Vault call is signed with a `revertRecipient` address that does not correspond to any address the depositor controls (commonly the EVM zero address). Once broadcast and confirmed, the refund is unrecoverable through the normal protocol flow — this is a permanent loss/freeze of the refunded principal, matching the "Required Impacts" criterion for permanent freezing/loss of user funds via the revert/refund accounting path.

### Likelihood Explanation
High for the attacker's own funds: the attacker fully controls `FundRecipient` content and can reliably trigger a revert path (e.g., by crafting a payload guaranteed to fail), so the corrupted recipient reaches the signed outbound deterministically, without needing any privileged party's cooperation.

### Recommendation
- In `Inbound.ValidateForExecution` (or a new revert-specific validation step run before `buildRevertOutbound`), strictly validate `RevertInstructions.FundRecipient` against `SourceChain`'s namespace format (reusing the strict, error-returning `CanonicalizeAddressByNamespace`), and fall back to `Sender` (which is itself namespace-validated at execution time) when it fails, instead of silently accepting an unparseable string.
- In `universalClient/chains/evm/tx_builder.go`, validate `data.Recipient` with `ethcommon.IsHexAddress` before calling `HexToAddress`, and reject/abort signing requests with an invalid recipient rather than silently encoding a zero/garbage address.

### Proof of Concept
1. Attacker calls the source chain (`eip155:11155111`) Gateway with a `FUNDS_AND_PAYLOAD` deposit whose `universal_payload` is crafted to revert on Push Chain, and sets `revert_instructions.fund_recipient = "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v"` (a Solana base58 pubkey, invalid for the `eip155` namespace).
2. Honest UVs observe and vote the inbound as submitted; `Inbound.Canonicalize()` runs `LenientCanonicalizeAddress("eip155:11155111", "EPjFWdd5...")`, which fails to parse as an EVM address and returns the trimmed base58 string unchanged (`utils/canonical.go:175-181`).
3. `ValidateForExecution` passes (it never inspects `RevertInstructions`), the payload execution fails as designed, and `handleFailedInboundValidation`/`ExecuteInboundFundsAndPayload` call `buildRevertOutbound`, which sets `outbound.Recipient = "EPjFWdd5..."` unchanged (`x/uexecutor/keeper/build_revert_outbound.go:10-14`).
4. The outbound is attached to `PendingOutbounds` with `Status_PENDING` for TSS signing (`x/uexecutor/keeper/create_outbound.go:349-371`), with no recipient re-validation.
5. When the universalClient EVM tx builder processes this outbound, `target := ethcommon.HexToAddress("EPjFWdd5...")` silently decodes to the zero address (invalid hex), which is packed into the `revertUniversalTx` calldata and signed by honest TSS participants (`universalClient/chains/evm/tx_builder.go:317-372`), permanently misdirecting the refund.

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

	return nil
}

// LenientCanonicalizeAddress canonicalizes addr for chain, falling back to
// the trimmed input when it does not parse.
func LenientCanonicalizeAddress(chain, addr string) string {
	canon, err := CanonicalizeAddressByNamespace(chain, addr)
	if err != nil {
		return strings.TrimSpace(addr)
	}
	return canon
}
