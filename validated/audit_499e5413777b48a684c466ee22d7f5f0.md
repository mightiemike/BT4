### Title
Integer underflow in confirmation-depth calculation causes premature CONFIRMED status for pending events - (File: `universalClient/chains/evm/event_confirmer.go`)

### Summary
`EventConfirmer.processPendingEvents` computes confirmation depth using unsigned 64-bit arithmetic without checking that `receipt.BlockNumber` is not greater than the previously-fetched `latestBlock`. Because `latestBlock` is fetched once at the top of the function and then reused while iterating over up to 1000 pending events (each requiring its own `GetTransactionReceipt` RPC round-trip), the chain can progress by two or more blocks before a given event is checked. When that happens, `receipt.BlockNumber` exceeds the cached `latestBlock` by 2+, and the unsigned subtraction wraps to a value close to `2^64-1`, instantly satisfying `confirmations >= requiredConfirmations` regardless of the transaction's real confirmation depth.

### Finding Description [1](#0-0) 
`latestBlock` is fetched exactly once per invocation, before the loop begins, and is then reused for every pending event processed in that pass: [2](#0-1) 
The confirmation depth is computed as:
```go
confirmations := latestBlock - receipt.BlockNumber.Uint64() + 1
```
This is plain `uint64` arithmetic with no bounds check on `receipt.BlockNumber <= latestBlock`. If the receipt's block number is at least 2 higher than the cached `latestBlock` (e.g., the source chain produced new blocks while the loop was busy calling `GetTransactionReceipt` for up to 1000 events, or a very recent transaction was picked up whose block was mined after `latestBlock` was captured), the subtraction underflows and wraps around to a value near `2^64-1`. This trivially satisfies `confirmations >= requiredConfirmations` for any realistic threshold (`fastConfirmations`/`standardConfirmations`), causing the event to be promoted straight to `store.StatusConfirmed` with effectively zero real confirmations.

Downstream, confirmed inbound events are picked up by `EventProcessor.processConfirmedEvents` and immediately turned into a `VoteInbound` call: [3](#0-2) . This means the confirmation-depth guarantee — the mechanism intended to protect cross-chain deposit/outbound processing from being finalized before enough blocks have passed to reduce reorg risk — can be silently bypassed.

Note: this defect does not require an adversarial reorg or a malicious relayer; it is a plain logic bug in the honest client's own code. Since every Universal Validator runs the identical `event_confirmer.go` implementation and observes the same source-chain block production, the race condition is systemic rather than node-specific, so multiple honest UVs are likely to hit it under comparable timing conditions for the same event.

### Impact Explanation
Premature confirmation of inbound/outbound events undermines the confirmation-depth safety margin designed to guard against reorgs on the source chain. An inbound event confirmed with far fewer than the required confirmations is fed into `VoteInbound`, i.e., into the on-chain finalization/ballot flow, before its source-chain transaction can be considered safely settled. However, protocol-level finalization of an inbound `UniversalTx` still requires a ballot/majority of UV votes on-chain (outside this file's scope), so this bug alone is a weakening of a defense-in-depth safety check within the client rather than a complete, single-actor bypass of consensus-level protections.

### Likelihood Explanation
The underflow is triggered purely by normal chain progression during the processing loop (batch of up to 1000 events, each requiring a separate RPC round trip) — no adversarial input or reorg is strictly necessary, only enough elapsed wall-clock time for 2+ new blocks to be produced on the watched chain relative to the cached `latestBlock`. This is realistic on any chain with block times shorter than the time it takes to process a full batch of pending events (RPC latency × up to 1000 events).

### Recommendation
Guard against `receipt.BlockNumber.Uint64() > latestBlock` before performing the subtraction (skip/treat as zero confirmations in that case), and prefer fetching the latest block height per-event or refreshing it periodically inside the loop rather than caching a single stale value for the entire batch, e.g.:
```go
receiptBlock := receipt.BlockNumber.Uint64()
if receiptBlock > latestBlock {
    continue // not enough information yet; treat as unconfirmed
}
confirmations := latestBlock - receiptBlock + 1
```

### Proof of Concept
1. Mock `rpcClient.GetLatestBlock` to return `L`.
2. Have `GetTransactionReceipt` return a receipt with `BlockNumber = L + 2` (simulating the chain advancing during the loop, or a very recent tx picked up after `latestBlock` was cached) for a pending event with `event.BlockHeight != 0`.
3. Call `processPendingEvents`.
4. Observe `confirmations := latestBlock - receipt.BlockNumber.Uint64() + 1` underflow to `2^64 - 1`, satisfying `confirmations >= requiredConfirmations` and the event immediately transitioning from `StatusPending` to `store.StatusConfirmed` on the very first tick, despite having effectively zero real confirmations.
