### Title
Precision loss in legacy vote-reward calculation causes users to lose dust FLUX-equivalent TRX rewards - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
The legacy (pre-new-reward-algorithm) per-cycle reward computation in `MortgageService#computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a super representative's cycle reward by first dividing `userVote` by `totalVote` into a `double` ratio, and then multiplying that ratio by `totalReward`. This is the same anti-pattern as the reported `FluxToken#getClaimableFlux()` bug: an avoidable division-before-multiplication step that introduces floating-point/integer-truncation precision loss, causing voters to receive a systematically smaller reward than the mathematically exact `userVote * totalReward / totalVote`.

### Finding Description
`computeReward(long cycle, List<Pair<byte[], Long>> votes)` is used for every cycle prior to `newRewardAlgorithmEffectiveCycle` (the "old reward" path): [1](#0-0) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;
    reward += voteRate * totalReward;
  }
  return reward;
}
```

Instead of computing the exact integer ratio `userVote * totalReward / totalVote` (which is what the *new* reward algorithm does, using `BigInteger` multiply-then-divide, see `computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)` at lines 224-226 and `RewardViCalService#getNewRewardAlgorithmReward`), this legacy path performs the division first (`userVote / totalVote`) and only then multiplies by `totalReward`. Because `double` has only 52 bits of mantissa and the division is truncated/rounded before the multiplication, the final `long` cast of `voteRate * totalReward` is systematically ≤ the exact value `userVote * totalReward / totalVote`, exactly analogous to the `FluxToken` bug where `((bpt * veMul) / veMax) * veMax` loses precision relative to `bpt * veMul * veMax / veMax`.

For comparison, the codebase's own "new algorithm" reward path avoids this exact mistake by doing multiply-then-divide in exact integer arithmetic: [2](#0-1) 

This confirms the team is aware multiply-before-divide is the precision-preserving order, yet the legacy `computeReward(cycle, votes)` overload still uses the lossy divide-before-multiply order in `double`.

This function is reachable by any unprivileged account that has voted for a super representative and calls `withdrawReward`/`queryReward` (invoked via the public `WithdrawBalanceContract` processed by `WithdrawRewardProcessor`/`VoteRewardUtil`, and via `MortgageService#withdrawReward` in the wallet API), for any cycle number below `newRewardAlgorithmEffectiveCycle`: [3](#0-2) [4](#0-3) 

### Impact Explanation
Every unprivileged voter who withdraws or queries rewards accrued during "old algorithm" cycles receives a slightly smaller TRX reward than they are actually entitled to, due to the `double`-based divide-then-multiply computation. While each individual loss is a "dust" amount (sub-unit rounding), it is a systemic under-delivery of promised rewards across the entire network for every voter and every legacy cycle, matching the impact category "Contract fails to deliver promised returns, but doesn't lose value" from the referenced report (the lost dust effectively remains unspent/unaccounted, not stolen).

### Likelihood Explanation
This code path executes on every call to `withdrawReward`/`queryReward` for any account with votes whose reward cycle predates `newRewardAlgorithmEffectiveCycle`, which is the default/legacy path for reward computation. It requires no special privilege — any voter triggers it simply by withdrawing standby witness voting rewards. It is a deterministic arithmetic issue, not a race condition, so likelihood of occurrence is high whenever such legacy-cycle rewards are computed.

### Recommendation
Replace the divide-then-multiply `double` computation with an integer multiply-then-divide (or `BigInteger`) computation, consistent with the "new algorithm" path already in the same file:

```java
long userVote = vote.getValue();
reward += Math.multiplyHigh/BigInteger... // multiply first, then divide
reward += BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward))
             .divide(BigInteger.valueOf(totalVote)).longValue();
```

This mirrors the exact-arithmetic pattern already used at [2](#0-1)  and eliminates the redundant floating-point division-before-multiplication that causes dust loss.

### Proof of Concept
Given `userVote = 3`, `totalVote = 7`, `totalReward = 10_000_000` (i.e. 10 TRX):

- Exact value: `userVote * totalReward / totalVote = 30_000_000 / 7 = 4_285_714` (integer division, floor).
- Legacy path: `voteRate = (double) 3 / 7 = 0.42857142857142855`; `reward = (long)(0.42857142857142855 * 10_000_000) = 4_285_714` in this case coincides, but for larger `totalReward`/`totalVote` values (e.g. `totalVote` in the hundreds of millions range typical for SR votes, and `totalReward` in the TRX-precision range), the double's 52-bit mantissa cannot represent the exact rational `userVote/totalVote`, so `(long)(voteRate * totalReward)` diverges from the exact integer result by 1 or more sun per cycle per voter — reproducible the same way the original PoC demonstrates a `~7.9 sun` (in FLUX terms `299999999999992086000` vs `300000000000000000000`) shortfall, but here recurring every reward cycle for every voter using the legacy algorithm.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
