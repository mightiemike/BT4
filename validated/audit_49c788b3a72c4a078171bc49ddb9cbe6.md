The reported libssh2 bug relies on C's `realloc` semantics, where growing a heap array does not zero-initialize the newly added memory, leaving a dangling/garbage pointer that gets freed on a later error path. In protobuf-go, the analogous "grow the backing array on a repeated field during parsing" operations all funnel through Go's `make()`, which always zero-initializes the returned memory as guaranteed by the Go runtime. This applies to every `grow*Slice` helper used by the wire decoders (e.g. `growBoolSlice`, `growInt32Slice`, `growInt64Slice`, `growUint32Slice`, `growUint64Slice`, `growFloat32Slice`, `growFloat64Slice`), which all follow the pattern `s := make([]T, 0, addCap+len(*sp)); s = s[:len(*sp)]; copy(s, *sp); *sp = s` [1](#0-0) , and is used from the generated wire-format decoders such as `consumeBoolSlice`, `consumeUint32Slice`, `consumeSint64Slice`, `consumeUint64Slice`, `consumeFixed32Slice`, `consumeFixed64Slice`, and `consumeDoubleSlice` [2](#0-1) [3](#0-2) .

Because any newly grown capacity is always zero-valued (never attacker-influenceable garbage), a parse failure that triggers a cleanup path over a partially-populated slice can only encounter zero/nil entries in the unfilled region, not stale or attacker-controlled pointers as in the libssh2 case. I also checked the descriptor pre-allocation logic in `initDecls`/`allocEnums`/`allocMessages`/`allocExtensions` (`internal/filedesc/desc_init.go`) and the `sync.Pool`-based scratch buffers in `internal/order/range.go`, and none of these exhibit reuse of uninitialized or stale memory across an error/cleanup boundary — pooled slices are always re-sliced to `[:0]` before use [4](#0-3) .

Since Go's memory model eliminates the specific "uninitialized-then-freed" precondition that makes the libssh2 bug exploitable, there is no equivalent unsafe-memory or use-of-uninitialized-pointer analog reachable via a trusted-schema, default binary/JSON parsing path in protobuf-go.
