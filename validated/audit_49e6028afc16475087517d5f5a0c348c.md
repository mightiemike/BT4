### Title
Unconditional overwrite of `DelegatedResourceCapsule` expire time (instead of taking the maximum) can shorten the effective resource lock for previously delegated balance - (File: `chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceCapsule.java`)

### Summary
`DelegatedResourceCapsule.addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy` accumulate the delegated balance for an `(owner, receiver)` pair but unconditionally overwrite the stored `expireTimeForBandwidth`/`expireTimeForEnergy` with whatever value is passed in the latest call, instead of taking `Maths.max(oldExpireTime, newExpireTime)` as is done for the equivalent "positions" merge in the Ajna report. This is the same root-cause pattern as the Ajna finding: a single on-chain record aggregates state produced by multiple independent calls, and a later call can silently reduce a time-based guarantee (deposit/expire time) that was previously established for balance already merged into that record.

### Finding Description
The V1 freeze/delegate path (`FreezeBalanceActuator`) and the native-contract freeze path (`FreezeBalanceProcessor`) both key delegated resources by `(from, to)` via `DelegatedResourceCapsule.createDbKey` [1](#0-0) . When a record already exists for that pair, the actuator calls `addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy`, which does:

```
public void addFrozenBalanceForBandwidth(long bandwidth, long expireTime) {
    this.delegatedResource = this.delegatedResource.toBuilder()
        .setFrozenBalanceForBandwidth(this.delegatedResource.getFrozenBalanceForBandwidth() + bandwidth)
        .setExpireTimeForBandwidth(expireTime)
        .build();
}
``` [2](#0-1) 

The balance field is additive (`+=`), but the expire-time field is simply replaced by the new call's `expireTime`, with no comparison to the previous value. The same unconditional-replace pattern exists for energy [3](#0-2) .

This capsule is written from two call sites without any check that the new `expireTime` is not earlier than the existing one:
- `FreezeBalanceActuator.delegateResource(...)`, invoked from `execute()` for the `FreezeBalanceContract` (legacy freeze) path [4](#0-3) 
- `FreezeBalanceProcessor.delegateResource(...)`, the equivalent native-contract (TVM) implementation [5](#0-4) 

Crucially, `FreezeBalanceActuator.validate()` only checks that `frozenDuration` lies within `[minFrozenTime, maxFrozenTime]` — a range configured by the committee via `DynamicPropertiesStore` — but performs **no check whatsoever** relative to any pre-existing `DelegatedResourceCapsule` for the `(owner, receiver)` pair [6](#0-5) .

This is in stark contrast to the newer, lock-based `DelegateResourceActuator` (Freeze V2), whose `validate()` explicitly guards against this exact hazard via `validRemainTime`, which rejects a new delegation whose lock period would produce an expire time earlier than the remaining time of the existing lock:

```
private void validRemainTime(ResourceCode resourceCode, long lockPeriod, long expireTime, long now)
    throws ContractValidateException {
  long remainTime = expireTime - now;
  if (lockPeriod * BLOCK_PRODUCED_INTERVAL < remainTime) {
    throw new ContractValidateException(...);
  }
}
``` [7](#0-6) 

The existence of this exact defensive check in the V2/lock code path — and its complete absence in the legacy `FreezeBalanceActuator`/`FreezeBalanceProcessor` merge point that writes into the very same `DelegatedResourceCapsule.expireTimeForBandwidth/Energy` fields — demonstrates that the developers recognized the "expire time can be shrunk by a later merge" hazard for one code path but did not apply an equivalent `Maths.max`/remaining-time safeguard to the other, mirroring the Ajna report's core observation that a shared/merged state record can have its time field silently regressed by a later, unrelated write.

### Impact Explanation
If the committee-configured `minFrozenTime`/`maxFrozenTime` range allows differing `frozenDuration` values (i.e., is not pinned to a single fixed value), an account can:
1. Freeze and delegate balance `B1` to `receiver` with the maximum allowed `frozenDuration`, producing `expireTime = now1 + maxFrozenTime`.
2. Later (before that expiry), freeze and delegate additional balance `B2` to the same `receiver` with the minimum allowed `frozenDuration`, producing `expireTime2 = now2 + minFrozenTime`, where `expireTime2 < expireTime` (i.e., `now2 + minFrozenTime < now1 + maxFrozenTime`).
3. Because `addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy` unconditionally overwrite the expire time, the single `DelegatedResourceCapsule` record now holds `B1 + B2` at the earlier `expireTime2`.
4. This lets the owner unfreeze the entire merged balance (including `B1`, originally meant to remain locked until `expireTime`) once `expireTime2` passes — an early, unintended release of frozen/delegated TRX-power, corrupting the resource/bandwidth-energy accounting and the total network/energy weight bookkeeping tied to frozen duration guarantees.

This is analogous to the Ajna finding's impact category (accounting-time corruption affecting withdrawal timing), applied here to on-chain resource freeze/delegation accounting rather than LP deposit time.

### Likelihood Explanation
Reachability is high in principle: both `FreezeBalanceActuator` (broadcast `FreezeBalanceContract` transaction) and `FreezeBalanceProcessor` (invoked via TVM `freezeBalanceV1`-style native opcode from a smart contract) are reachable directly from an ordinary account/anonymous broadcast transaction with no privileged role required. However, I was **not able to verify from the indexed code** whether `minFrozenTime` and `maxFrozenTime` are currently configured to the same fixed value on mainnet (historically TRON pinned freeze duration to a fixed 3-day period), which is the precondition for an attacker to produce two different `expireTime` values for the same `(owner, receiver)` pair. If `minFrozenTime == maxFrozenTime` is enforced as a de-facto constant in the live network configuration, the two consecutive freeze calls will always take place at increasing wall-clock time with the same duration, so the later `expireTime` will always be ≥ the earlier one, and the missing check becomes latent/non-exploitable in practice. I could not locate the default value assignment for `minFrozenTime`/`maxFrozenTime` in `DynamicPropertiesStore` within the indexed content to confirm this either way.

### Recommendation
Mirror the safeguard already implemented in `DelegateResourceActuator`/`validRemainTime` for the legacy freeze/delegate path: either (a) reject a new `FreezeBalanceContract`/native freeze call to an existing `(owner, receiver)` `DelegatedResourceCapsule` whose resulting `expireTime` would be earlier than the currently stored one, or (b) change `DelegatedResourceCapsule.addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy` to store `Math.max(existingExpireTime, newExpireTime)` instead of unconditionally overwriting it, consistent with how LP deposit-time merges should be handled per the referenced Ajna finding.

### Proof of Concept
Conceptual PoC (contingent on the unverified precondition that `minFrozenTime < maxFrozenTime` is actually configurable/active):
1. Account `A` broadcasts `FreezeBalanceContract` with `resource=BANDWIDTH`, `receiverAddress=R`, `frozenDuration=maxFrozenTime`, `frozenBalance=B1` → `DelegatedResourceStore` entry `(A,R)` created with `expireTimeForBandwidth = now1 + maxFrozenTime*FROZEN_PERIOD` via `FreezeBalanceActuator.delegateResource` [8](#0-7) .
2. Before that expiry, `A` broadcasts a second `FreezeBalanceContract` to the same `R` with `frozenDuration=minFrozenTime`, `frozenBalance=B2`. `validate()` performs no check against the existing record's `expireTimeForBandwidth` [9](#0-8) , so `execute()` calls `delegateResource`, which calls `addFrozenBalanceForBandwidth(B2, now2 + minFrozenTime*FROZEN_PERIOD)`, overwriting `expireTimeForBandwidth` to the earlier value while balance becomes `B1+B2` [2](#0-1) .
3. At `now2 + minFrozenTime*FROZEN_PERIOD` (earlier than the original `B1` lock would have expired), `A` can successfully call `UnfreezeBalanceContract` for the full merged `B1+B2`, releasing `B1` earlier than its original lock guarantee.
