**Analysis:**

The premise assumes `structure_from_ty_arg!` and `abort_unless_arithmetics_enabled_for_structure!` can disagree on which `Structure` variant is in play, letting a type tag "pass" the feature check for one structure while falling through to the `_` arm meant for another. Tracing the actual code shows this can't happen:

- `structure_from_ty_arg!` resolves `ty_args[0]` to a single `Option<Structure>` via `Structure::try_from(TypeTag)`, which only matches exact canonical type-tag strings (e.g. `0x1::bls12381_algebra::Fr`) [1](#0-0) .
- `abort_unless_arithmetics_enabled_for_structure!` derives the feature flag to check directly from that *same* `structure_opt` value via `feature_flag_from_structure`, which maps every BLS12-381 variant to `FeatureFlag::BLS12_381_STRUCTURES` and every BN254 variant to `FeatureFlag::BN254_STRUCTURES` [2](#0-1) .

Because both the feature-flag gate and the `match` dispatch in `inv_internal` consume the identical `structure_opt` produced once at the top of the function [3](#0-2) , there is no way for the gate to "pass for a different structure" than the one being matched — they are the same value, not independently re-derived from potentially stale state.

The only real reason `inv_internal`'s `_` fallback arm fires is that `inv()` is only implemented for field types (`Fr`, `Fq12`, `Fq`), so a caller supplying a group structure like `Structure::BLS12381G1`/`G2`/`Gt` (which does pass the `BLS12_381_STRUCTURES` feature check) will still deterministically hit `MOVE_ABORT_CODE_NOT_IMPLEMENTED` at line 65 [4](#0-3) . That is intended, consistent behavior for every validator running the same binary against the same on-chain `FeatureFlag` config — it is not caller-controlled non-determinism.

`FeatureFlag` values are committed on-chain configuration, read identically by every validator executing the same block; an unprivileged transaction sender cannot mutate feature flags mid-transaction or cause two validators evaluating the *same* on-chain config to see different flag values. A scenario where "upgraded vs non-upgraded validators" produce different abort codes for the same transaction is the expected, governance-gated behavior of introducing new `Structure` variants behind a `FeatureFlag` — this is precisely why the flag-gating mechanism exists, and it requires a trusted governance/validator upgrade decision, which is out of scope per the review's "trusted operator mistakes" exclusion.

No unprivileged-input path exists here that corrupts a write set, proof, root, or `TransactionInfo` binding independent of a legitimate protocol upgrade decision.
