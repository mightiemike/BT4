## Analog Found

### Title
Attached deposit from an external caller is permanently lost when the registrar or NEP-141 storage check cross-contract call fails or returns malformed data - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` tracks an external caller's attached deposit in `CallerDeposit` so it can be refunded if the eventual action fails [1](#0-0) . This refund is correctly performed in `rlp_execute_callback` when the final action promise fails [2](#0-1) . However, several earlier error branches in `address_check_callback` and `nep_141_storage_balance_callback` return an error `ExecuteResponse` directly without ever issuing that refund, silently dropping the tracked `caller_deposit` — the exact "empty `receive()`/no-fallback-refund" pattern described in the external report.

### Finding Description
`inner_rlp_execute` computes `caller_deposit = CallerDeposit::new(&context)`, which is `Some` whenever `predecessor_account_id != current_account_id`, i.e. whenever an external, unprivileged account calls `rlp_execute` with an attached deposit [3](#0-2) . For two transaction kinds the wallet must perform an intermediate cross-contract call before dispatching the user's real action, and `caller_deposit` is threaded through as an argument to the follow-up callback:

- `EOABaseTokenTransfer { address_check: Some(_), .. }` calls the address registrar and continues into `address_check_callback` [4](#0-3) .
- `ERC20Transfer { .. }` calls `storage_balance_of` on the token contract and continues into `nep_141_storage_balance_callback` [5](#0-4) .

In `address_check_callback`, if the registrar call fails, or its response cannot be deserialized, or the target turns out to be an existing named account with a non-owner signer, the function returns `PromiseOrValue::Value(ExecuteResponse{ success: false, ... })` immediately — `caller_deposit` is simply dropped and never refunded: [6](#0-5) 

Likewise, in `nep_141_storage_balance_callback`, if the `storage_balance_of` call fails, its response is malformed, or the wrapped action is unexpectedly not a `FunctionCall`, the function returns an error `Value` without refunding `caller_deposit`: [7](#0-6) 

In every one of these branches, only `rlp_execute_callback` (reached later, on the final action's own failure) contains the refund logic [8](#0-7) ; the earlier failure paths bypass it entirely, so the attached NEAR deposit, which is already credited to the wallet contract's account balance the moment `rlp_execute` (marked `#[payable]`) is called [9](#0-8) , simply remains stuck on the wallet contract with no code path left to return it to the caller.

### Impact Explanation
Any unprivileged account that calls `rlp_execute` on someone else's wallet contract (a normal, permissionless relayer-style call) with a non-zero attached deposit, targeting either (a) an eth-implicit address requiring an address-registrar lookup, or (b) an ERC-20 emulated transfer requiring a NEP-141 storage-balance check, can have that deposit permanently frozen if the intermediate cross-contract call fails or returns unexpected data. This is a concrete "permanently frozen funds" outcome: the depositor's NEAR is retained by the wallet contract with no reachable method to recover it, and no compensating action was performed either.

### Likelihood Explanation
Triggering the registrar/storage-balance failure is straightforward and requires no privileged access: an attacker or even an honest but misconfigured relayer can call `rlp_execute` targeting an account without a deployed/available registrar or against a token contract that returns malformed JSON, is paused, or runs out of gas on `storage_balance_of`. Because `CallerDeposit::new` only activates for external (non-self) callers with a positive attached deposit, this is directly reachable by any transaction signer interacting with the wallet contract, matching the "unprivileged transaction signer" reachability requirement.

### Recommendation
In every early-return error branch of `address_check_callback` and `nep_141_storage_balance_callback` (registrar call failure, malformed registrar response, "target is existing named account" case, `storage_balance_of` failure, malformed storage-balance response, and unexpected non-`FunctionCall` action), issue the same refund-to-`caller_deposit.account_id` transfer performed in `rlp_execute_callback` before returning the error `ExecuteResponse`, so attached deposits from external callers are never silently retained by the wallet contract.

### Proof of Concept
1. Deploy a `WalletContract` and have an external account `alice.near` (`predecessor_account_id != current_account_id`) call `rlp_execute` with a nonzero attached deposit for an RLP-encoded Ethereum transaction whose `to` address requires the address-registrar check (`EOABaseTokenTransfer { address_check: Some(_), .. }`).
2. Ensure the address registrar cross-contract call fails (e.g., point `ADDRESS_REGISTRAR_ACCOUNT_ID` at a nonexistent or non-responsive account, or exhaust gas on the lookup).
3. `address_check_callback` observes `PromiseResult::Failed` and returns `ExecuteResponse{ success: false, ... }` at [10](#0-9)  without ever spending or refunding `caller_deposit`.
4. Query `alice.near`'s account balance: the originally attached deposit has been debited from her account and credited to the wallet contract, but no refund receipt was ever generated — contrast with `test_caller_refunds` in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs` (lines 170-229), which only exercises the refund path reachable through `rlp_execute_callback`'s `PromiseResult::Failed` branch, not these earlier callback failure branches.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
