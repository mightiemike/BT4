Based on my investigation, I found a strong analog to the Entropy.sol collusion issue in java-tron's DPoS block-production scheduling, which is the standard root cause enabling producer-biased "randomness" for TVM contracts using `BLOCKHASH`.

### Title
Deterministic, publicly-predictable DPoS witness scheduling lets a colluding block producer bias `BLOCKHASH`-derived randomness in TVM contracts - ([File: consensus/src/main/java/org/tron/consensus/dpos/DposSlot.java])

### Summary
`DposSlot.getScheduledWitness(long slot)` deterministically computes the next block producer purely from public on-chain state (`getActiveWitnesses()`, `getLatestBlockHeaderTimestamp()`), with no unpredictable component. [1](#0-0)  This mirrors the Entropy report's root cause: when there is no additional entropy source, a party who knows they will control block production (the "provider"/proposer analog) can pre-compute several candidate outcomes and choose the one most favorable to them before committing.

### Finding Description
Any Super Representative (SR) can compute in advance, from purely public state, exactly which slot(s) it will be scheduled to produce [2](#0-1)  and `DposService.validBlock` only checks that the block's declared witness matches this deterministic schedule and satisfies the time slot invariant — it does not add any unpredictability to the process. [3](#0-2)  Meanwhile, the TVM exposes `BLOCKHASH` as an opcode that many higher-level gambling/lottery/NFT-mint contracts use as a source of "randomness" (`OperationActions.blockHashAction` → `program.getBlockHash(blockIndex)`, wired into the opcode table with `Op.BLOCKHASH`). [4](#0-3) [5](#0-4) 

This is directly analogous to the Entropy.sol report's core issue: value derived from a party that has advance, provable knowledge of (and control over) the "random" seed (here, the produced block and its hash/contents) can bias outcomes against uninformed counterparties. In the Entropy report, the `blockhash` option was supposed to add unpredictability, but the report notes this only raises the bar to require collusion with "a block proposer" — in java-tron's DPoS model, the scheduled block proposer for any future slot is *always* known in advance and is not a rare/incidental participant, but a deterministic, guaranteed-turn validator. An SR that also participates as a "provider" or player in a smart contract lottery/gambling/NFT-mint dApp built on TVM can:
1. Know exactly which future slot(s) they will produce.
2. Construct multiple candidate blocks/transaction orderings for that slot (choosing which pending user transactions to include/exclude, and the resulting block hash), and select the block whose resulting `BLOCKHASH`-derived value maximizes their payout — exactly as in the report's exploit scenario with Alice.

### Impact Explanation
This allows a validator (SR) with dApp involvement to deterministically bias outcomes of any TVM contract that uses `BLOCKHASH` (or values derived from the block it produces) as a randomness source, extracting value from other participants in gambling, lottery, or NFT-mint dApps deployed on java-tron. This is an accounting/value-extraction corruption of the affected dApp's economics; it does not compromise node security or consensus safety directly, but it undermines the fairness guarantee smart contract authors rely on when using `BLOCKHASH`.

### Likelihood Explanation
Likelihood is Low-Medium: it requires the attacker to be an active SR (a class of privileged-but-not-node-compromising actor who is already permitted to produce blocks under normal DPoS rules) and to also be a participant/provider in the target dApp. This is analogous to the original report's own difficulty rating of "Low" — the attack is stealthy (looks like random chance) and requires no special exploit of node internals, only foreknowledge of one's own scheduled slot, which `DposSlot.getScheduledWitness` inherently provides to every SR for every future slot. [1](#0-0) 

### Recommendation
- Short term: Document explicitly, in TVM/Solidity developer guidance, that `BLOCKHASH` (and any value derived from the current or recent producer's block) is producer-biasable and must not be used as a sole randomness source for value-bearing outcomes; provide secure integration examples (e.g., commit-reveal across multiple blocks/parties, or external VRF).
- Long term: Consider providing a native, less producer-influenced randomness precompile/opcode (e.g., threshold VRF among multiple SRs, or verified external oracle randomness) so dApp authors are not pushed toward insecure `BLOCKHASH`-based designs.

### Proof of Concept
1. Attacker registers/operates as an SR and deploys (or participates in) a TVM gambling contract that computes winners using `blockhash(block.number-1)` (via the `BLOCKHASH` opcode, `OperationActions.blockHashAction`). [4](#0-3) 
2. Using `DposSlot.getScheduledWitness`, the attacker (or any observer) can compute in advance which future slot(s) the attacker-SR will produce. [1](#0-0) 
3. When that slot arrives, the attacker-SR (via `DposTask.produceBlock`) constructs the block, having full control over transaction inclusion/ordering and thus the resulting block hash used by the gambling contract's `BLOCKHASH`-based RNG. [6](#0-5) 
4. The attacker selects/produces the block variant that yields a winning `BLOCKHASH` for their own wager, submits it, and it passes `validBlock`'s checks (which only validate slot/witness/time, not randomness fairness). [3](#0-2) 

**Note on completeness:** I was unable to fully trace `Program.getBlockHash`'s exact implementation (e.g., how many past blocks it allows querying, whether it restricts to very recent blocks) within the available tool iterations, since the file content for that specific method was not returned before the search budget was exhausted. This detail would refine exactly how far back an attacker's manipulation window extends, but does not change the core finding that `BLOCKHASH`-based randomness is producer-biasable given java-tron's fully deterministic and publicly predictable DPoS scheduling.

  public ByteString getScheduledWitness(long slot) {
    final long currentSlot = getAbSlot(consensusDelegate.getLatestBlockHeaderTimestamp()) + slot;
    if (currentSlot < 0) {
      throw new RuntimeException("current slot should be positive.");
    }
    int size = consensusDelegate.getActiveWitnesses().size();
    if (size <= 0) {
      throw new RuntimeException("active witnesses is null.");
    }
    int witnessIndex = (int) currentSlot % (size * SINGLE_REPEAT);
    witnessIndex /= SINGLE_REPEAT;
    return consensusDelegate.getActiveWitnesses().get(witnessIndex);
  }

  public boolean validBlock(BlockCapsule blockCapsule) {
    if (consensusDelegate.getLatestBlockHeaderNumber() == 0) {
      return true;
    }
    ByteString witnessAddress = blockCapsule.getWitnessAddress();
    long timeStamp = blockCapsule.getTimeStamp();
    if (timeStamp % BLOCK_PRODUCED_INTERVAL != 0
      && consensusDelegate.getDynamicPropertiesStore().allowConsensusLogicOptimization()) {
      logger.warn("ValidBlock failed: witness: {}, timeStamp: {}",
        ByteArray.toHexString(witnessAddress.toByteArray()), timeStamp);
      return false;
    }
    long bSlot = dposSlot.getAbSlot(timeStamp);
    long hSlot = dposSlot.getAbSlot(consensusDelegate.getLatestBlockHeaderTimestamp());
    if (bSlot <= hSlot) {
      logger.warn("ValidBlock failed: bSlot: {} <= hSlot: {}", bSlot, hSlot);
      return false;
    }

    long slot = dposSlot.getSlot(timeStamp);
    if (slot == 0
      && consensusDelegate.getDynamicPropertiesStore().allowConsensusLogicOptimization()) {
      logger.warn("ValidBlock failed: slot error, witness: {}, timeStamp: {}",
        ByteArray.toHexString(witnessAddress.toByteArray()), new DateTime(timeStamp));
      return false;
    }
    final ByteString scheduledWitness = dposSlot.getScheduledWitness(slot);
    if (!scheduledWitness.equals(witnessAddress)) {
      logger.warn("ValidBlock failed: sWitness: {}, bWitness: {}, bTimeStamp: {}, slot: {}",
          ByteArray.toHexString(scheduledWitness.toByteArray()),
          ByteArray.toHexString(witnessAddress.toByteArray()), new DateTime(timeStamp), slot);
      return false;
    }

    return true;
  }
