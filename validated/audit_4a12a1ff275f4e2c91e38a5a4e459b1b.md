### Title
Stale parent header from a PoX-orphaned fork remains attachable in `find_next_staging_block::can_attach`, letting an epoch2.x block be accepted on top of a non-canonical parent - ([File: stackslib/src/chainstate/stacks/db/blocks.rs])

### Summary
`StacksChainState::find_next_staging_block`'s `can_attach` check verifies the **candidate's own** sortition's `pox_valid` flag but validates the **parent** link solely by looking up `(parent_anchored_block_hash, parent_consensus_hash)` in the `block_headers` table via `hdr_sql`, without checking whether the parent's sortition (`parent_consensus_hash`) still has `pox_valid = 1`. Because PoX invalidation (`SortitionDB::invalidate_descendants_of` / `invalidate_descendants_with_closures`) only flips `pox_valid = 0` on rows in the `snapshots` table and never deletes rows from `block_headers`, a header row for a block whose tenure was later orphaned by a PoX reorg remains permanently query-able and "attachable" as a parent.

### Finding Description
The claimed equality is: *parent tenure's authorising sortition == the sortition on the canonical PoX fork*. This is broken as follows.

In `find_next_staging_block` (stackslib/src/chainstate/stacks/db/blocks.rs:3759-3868):
- The candidate's own consensus hash is checked for `pox_valid` via `SortitionDB::get_block_snapshot_consensus` [1](#0-0) .
- But the parent linkage check (`can_attach`) only executes `SELECT * FROM block_headers WHERE block_hash = ?1 AND consensus_hash = ?2` and treats any `Some(_)` row as sufficient proof that "we have the parent, will process" [2](#0-1) . It performs no lookup of the parent's own sortition snapshot or its `pox_valid` status.

When a PoX reorg happens, `invalidate_descendants_with_closures` sets `pox_valid = 0` on descendant rows in the `snapshots` table but explicitly only touches `snapshots` — it never deletes or updates `block_headers` [3](#0-2) . The coordinator's `forget_orphan_stacks_blocks` helper, used to *restore* previously-orphaned blocks if a PoX fork later becomes canonical again, confirms that block/staging data (and by extension `block_headers` rows already inserted via `advance_tip`) is intentionally retained rather than purged on PoX invalidation [4](#0-3) .

Exploit flow: an attacker who wins a single sortition slot on the new/canonical PoX fork constructs an epoch2.x `StacksBlock` whose header's `parent_block` / declared `parent_consensus_hash` point to a stale, already-processed block hash from a fork that has since been PoX-invalidated (its `block_headers` row was written before the reorg and is never removed). The attacker sets `total_work.work` to `parent.total_work.work + 1` (values are fully known/public from the stale header) so that `check_block_attachment` (stackslib/src/chainstate/stacks/db/blocks.rs:5879-5900), which only checks hash-linkage and work-counter continuity, also passes. `get_parent_header_info` (stackslib/src/chainstate/stacks/db/blocks.rs:5906-5945) likewise just re-reads the same stale `block_headers` row with no `pox_valid` check. As a result the staging block is accepted, processed, and appended even though its parent's authorizing sortition is not on the canonical PoX fork.

### Impact Explanation
Every honest node running this exact code path would deterministically accept the same invalid block on top of a parent whose original authorizing sortition is not canonical — this is "an invalid block accepted ... network-wide," matching the Critical category defined in the rules. Depending on the specific stale parent chosen, this can produce a block whose ancestry/state root does not correspond to any node's actual canonical chainstate/MARF lineage, effectively rewriting fork continuity rules and enabling chain-history/state confusion without requiring majority stake — an unprivileged single-slot miner or block-relayer can trigger it.

### Likelihood Explanation
Preconditions: (1) a PoX reorg/anchor-block invalidation must have previously occurred, orphaning a tenure whose block was already processed and thus has a `block_headers` row; (2) the attacker needs any legitimate, currently-valid sortition (a single miner slot is sufficient, satisfying the "minority stake, single miner slot" constraint) to produce a candidate `StagingBlock` with a valid own-consensus-hash; (3) the attacker crafts the header's `parent_block`/`total_work` fields to match the retained stale header. This is entirely within reach of a minority/unprivileged participant and requires only ordinary BTC spend to win one sortition; no signer collusion or majority stake is needed. It is repeatable on every PoX reorg that leaves stale `block_headers` rows behind.

### Recommendation
In `find_next_staging_block`'s `can_attach` branch, after finding the `hdr_row` for the parent, additionally look up `SortitionDB::get_block_snapshot_consensus` for `candidate.parent_consensus_hash` and reject (mark not attachable / delete/orphan) if the snapshot is missing or `pox_valid == false`, mirroring the check already done for the candidate's own consensus hash. Equivalently, join against a canonical-fork-scoped view of `block_headers` rather than treating table membership alone as proof of a valid parent.

### Proof of Concept
Rust integration test plan (extends existing `blocks.rs` test harness, e.g. near `test_process_next_staging_block`/`test_orphan_*` tests):
1. Build a two-tenure epoch2.x chain: process block `B0` (genesis) then block `B1` under consensus hash `CH1`, so `B1`'s row lands in `block_headers` and its snapshot has `pox_valid = 1`.
2. Trigger a PoX reorg that invalidates `CH1`'s sortition: call `SortitionDB::invalidate_descendants_of` (or drive it through `process_new_pox_anchor`) targeting the burn block containing `CH1`, and assert `SortitionDB::get_block_snapshot_consensus(..., &CH1).unwrap().pox_valid == false`.
3. Assert (equality LHS): `block_headers` still contains a row for `(CH1, B1.block_hash())` (i.e., `StacksChainState::get_anchored_block_header_info` returns `Some(_)`).
4. Mine a new, legitimately-won block `B2` on the new canonical fork with consensus hash `CH2` (`pox_valid == true`), but set `B2.header.parent_block = B1.block_hash()`, `parent_consensus_hash = CH1`, and `total_work.work = B1.total_work.work + 1` to satisfy `check_block_attachment`.
5. Store `B2` via `store_staging_block` and call `process_next_staging_block` / `process_blocks_at_tip`.
6. Assert (equality RHS, expected to fail pre-fix): `find_next_staging_block` returns `Some((_, B2_staging))` and `B2` is fully processed/appended (`StacksChainState::get_anchored_block_header_info(..., &CH2, &B2.block_hash())` returns `Some`), despite `CH1`'s snapshot having `pox_valid == false` — demonstrating the broken equality "parent tenure's authorising sortition == the sortition on the canonical PoX fork."
7. After applying the recommended fix (checking `pox_valid` of `parent_consensus_hash` in `can_attach`), re-run and assert `B2` is instead left `attachable = 0`/orphaned and never processed.

Note: this analysis targets legacy epoch2.x block processing in `stackslib/src/chainstate/stacks/db/blocks.rs`, not `auth.rs` as labeled in the question header — the file citation in the prompt appears mismatched with the actual `find_next_staging_block`/`can_attach` code location, which I've cited directly above. I was not able to fully verify whether any additional Nakamoto-era (`stackslib/src/chainstate/nakamoto/mod.rs`) safeguard retroactively blocks this for post-Nakamoto chains, since epoch2.x processing paths may still be reachable during bootstrapping/replay; further review of `stacks-inspect`'s `replay_block` and any epoch-gating around `process_next_staging_block` is recommended to confirm the current exposure window.

/// Forget that all Stacks blocks that were mined on descendants of `burn_header` are orphaned.
/// They may be valid again, after a PoX reorg.
fn forget_orphan_stacks_blocks(
    sort_conn: &DBConn,
    chainstate_db_tx: &mut DBTx,
    burn_header: &BurnchainHeaderHash,
    invalidation_height: u64,
) -> Result<(), Error> {
    if let Ok(sns) = SortitionDB::get_all_snapshots_for_burn_block(sort_conn, burn_header) {
        for sn in sns.into_iter() {
            // only retry blocks that are truly in descendant
            // sortitions.
            if sn.sortition && sn.block_height > invalidation_height {
                StacksChainState::forget_orphaned_epoch_data(
                    chainstate_db_tx,
                    &sn.consensus_hash,
                    &sn.winning_stacks_block_hash,
                )?;
            }
        }
    }
    Ok(())
}
