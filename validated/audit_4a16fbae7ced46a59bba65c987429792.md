### Title
On-chain Bancor-formula Exchange pool spot price is manipulable within a single transaction and used unprotected for swap/inject/withdraw accounting - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
The external report describes a vault that values its assets using the manipulable spot price of an AMM pool, with no `_minLockPeriod`/time-lock protection, letting an attacker skew the pool price, get over-credited shares, then reverse the skew — all within a flash-loan-atomic sequence. java-tron ships a comparable on-chain AMM: the TRC10 `Exchange` object (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract`), whose price is derived purely from the current `firstTokenBalance`/`secondTokenBalance` ratio stored in `ExchangeCapsule`, with no oracle, TWAP, or minimum holding period.

### Finding Description
`ExchangeCapsule.transaction()` computes the swap output using a Bancor-style relay-token formula (`ExchangeProcessor.exchange` / `SafeExchangeProcessor.exchange`) driven solely by the pool's current `firstTokenBalance`/`secondTokenBalance`, i.e. the instantaneous spot price with no external oracle or time-weighting. [1](#0-0) 

`ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the "another token" amount proportionally to the *current* pool ratio at execution time (`anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance`), reading the same mutable, unlagged balances: [2](#0-1) [3](#0-2) 

Because TRON transactions execute atomically and multiple transactions can be packed by the same block producer / broadcast in sequence within one block, any account can:
1. Call `ExchangeTransactionContract` with a large `tokenQuant` to swap and skew `firstTokenBalance`/`secondTokenBalance` toward a favorable ratio.
2. In the same block, call `ExchangeInjectContract` (open to any account, not just the pool creator — see validation, which checks only token/balance sufficiency, not creator identity) to add liquidity at the now-skewed ratio, or otherwise act on `ExchangeTransactionContract` again to extract value.
3. Reverse the initial swap to restore the ratio, walking away with the mispriced difference net of the Bancor curve's own slippage/fee.

This is structurally the same "atomic spot-price manipulation with no time lock" bug class as the report: no `minLockPeriod`-style delay exists between when the pool ratio is set and when it is consumed for accounting, and there is no alternative price feed — the pool balances themselves are the sole price source. [4](#0-3) 

### Impact Explanation
Exploitation lets an attacker execute intra-block/atomic price manipulation against any TRC10 `Exchange` pool. Because pools also hold TRX and TRC10 balances directly under the `Exchange` capsule (asset accounting is state, not merely notional), a successful sandwich-like sequence can result in unauthorized extraction of pooled TRX/TRC10 value from the exchange, i.e. asset/accounting corruption directly affecting on-chain balances. `ExchangeInject` in particular is open to arbitrary accounts (not privileged), so it is a directly reachable unprivileged surface.

### Likelihood Explanation
Medium: the `Exchange` contracts are legacy TRC10 features that see limited usage today, and the Bancor curve's own slippage (`ExchangeProcessor`/`SafeExchangeProcessor` exponential relay formula) imposes real cost on large skewing trades, which reduces (but does not eliminate) attacker profitability compared to a naive constant-product pool with zero fees. Balance limits (`getExchangeBalanceLimit`) also cap absolute pool sizes, bounding maximum exploitable value.

### Recommendation
- Do not use the raw, instantaneous `firstTokenBalance`/`secondTokenBalance` ratio as the sole basis for `ExchangeInject`/`ExchangeWithdraw` proportional accounting within the same block as a large `ExchangeTransaction` swap; consider a time-weighted or previous-block-checkpointed ratio for inject/withdraw pricing.
- Consider restricting `ExchangeInjectContract` usage or adding a cooldown between a swap and a subsequent inject/withdraw on the same exchange pool, analogous to enforcing a non-zero `_minLockPeriod` in the referenced report.
- Evaluate whether large single-transaction swaps should be rate-limited or slippage-capped relative to pool depth (`getExchangeBalanceLimit`) to reduce the profitability of intra-block price skewing.

### Proof of Concept
1. Attacker holds TRX and TRC10 token `B` and identifies an `Exchange` pool `(TRX, B)` with balances `firstTokenBalance`, `secondTokenBalance`.
2. Attacker broadcasts `ExchangeTransactionContract` selling a large `tokenQuant` of TRX into the pool, shifting `firstTokenBalance`/`secondTokenBalance` sharply (per `ExchangeCapsule.transaction`, `chainbase/.../ExchangeCapsule.java:124-169`).
3. In the same or immediately following block, attacker (or colluding account) calls `ExchangeInjectContract` with token `B`, where `anotherTokenQuant` (the TRX credited proportionally) is computed off the now-skewed ratio (`actuator/.../ExchangeInjectActuator.java:60-83`), extracting more TRX-equivalent value than a fair-price injection would allow.
4. Attacker reverses the initial swap via a second `ExchangeTransactionContract` call to restore the ratio, then withdraws liquidity, net profiting from the temporary mispricing versus the true underlying TRX/B value, at the expense of other liquidity/token holders in the pool.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
