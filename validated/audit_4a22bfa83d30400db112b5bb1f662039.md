### Title
Unchecked `storeSession()` boolean return value in OAuth callback allows request to proceed as authenticated after a failed session persist - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/auth-code-flow.ts`)

### Summary
The `SessionStorage.storeSession()` contract explicitly returns a `Promise<boolean>` to signal whether the session was actually persisted [1](#0-0) . Multiple unprivileged, anonymous-request-reachable OAuth callback handlers call `storeSession()` after Shopify returns an access token, but discard the boolean result and unconditionally continue the authenticated flow (issuing the app-installed redirect, triggering `afterAuth` hooks, and beginning a second OAuth leg for online tokens) as if the session had been durably saved.

### Finding Description
`storeSession()` is defined to return `false` on failure without throwing, e.g. the reference file-based implementation explicitly catches write errors and returns `false` instead of raising [2](#0-1) , and the official migration guide instructs implementers to check this return value and log a failure if it is `false` [3](#0-2) .

Despite this documented contract, the OAuth callback path in `shopify-app-remix`'s `AuthCodeFlowStrategy.handleAuthCallbackRequest` calls `storeSession()` and ignores the result: [4](#0-3) 

The identical unchecked pattern also exists in `shopify-app-express`'s `authCallback` handler (`await config.sessionStorage.storeSession(callbackResponse.session);`) [5](#0-4) , and in the offline-token refresh path used to keep sessions alive across requests [6](#0-5) .

Because none of these call sites check the return value, a storage-layer failure (e.g. a transient DB write error, unique-constraint conflict, or a custom `SessionStorage` implementation returning `false`) is silently swallowed. The code proceeds to: (1) trigger `afterAuth` hooks with a session object that is not actually retrievable from storage, (2) redirect the merchant into the embedded app as if installation succeeded, and (3) in the offline-token-refresh path, return the *newly refreshed* in-memory session to the caller even though the persisted store may still contain the old/expired or no token at all. This is directly analogous to ignoring a `transferFrom` boolean return value in the original report: the code assumes a state-mutating operation succeeded and continues with privileged follow-on actions without confirming that the underlying state change actually took effect.

### Impact Explanation
This is a data-integrity/availability issue in the authentication pipeline rather than a straightforward auth bypass: a failed `storeSession()` call is not surfaced to the merchant or app operator, so:
- The app can consider a shop "installed" and complete the OAuth redirect/afterAuth webhook registration flow even though no session was durably saved, causing the next request from that shop to fail to find a session and force a repeat/loop of OAuth, or in the worst case operate with stale/incorrect session data if a custom storage partially wrote state.
- In `ensureOfflineTokenIsNotExpired`, if the refreshed token fails to persist, the in-memory `offlineSession` (with a new access token) is still returned and used for the current request, while the persisted store retains the old token — subsequent requests using the stored (unrefreshed) session may then fail with 401s, indirectly causing session desync/DoS-like behavior for that shop.
This does not, on its own, grant a cross-tenant/forged-session bypass, since no other tenant's data is exposed; the impact is confined to reliability/consistency of the current shop's own session state after a storage failure.

### Likelihood Explanation
Requires a genuine session-storage write failure (transient DB error, connection blip, custom `SessionStorage` implementation that legitimately returns `false`) at the exact moment of an OAuth callback or offline-token refresh — an anonymous merchant hitting the OAuth callback endpoint is enough to reach this code path, but the failure condition itself (storage returning `false`) is opportunistic, not attacker-controlled.

### Recommendation
Check the boolean returned by `storeSession()` at every call site (`shopify-app-remix`'s `auth-code-flow.ts`, `shopify-app-express`'s `auth-callback.ts`, and `ensure-offline-token-is-not-expired.ts`), and on `false`: log/alert the failure, avoid proceeding to `afterAuth`/redirect logic that assumes durable persistence, and return an error response (e.g. 500) instead of treating the OAuth exchange as successful — mirroring the pattern already documented in the project's own v5→v6 migration guide.

### Proof of Concept
Not applicable as a standalone exploit script — the issue is a missing-check defect reachable by any anonymous shop completing OAuth install/reinstall (`GET {config.auth.callbackPath}?...`) or by any request that triggers `ensureOfflineTokenIsNotExpired` while the configured `SessionStorage.storeSession()` implementation returns `false` (e.g., simulate by injecting a custom `SessionStorage` whose `storeSession` returns `false` and observing that `handleAuthCallbackRequest`/`ensureOfflineTokenIsNotExpired` still proceed with `afterAuth`/redirect/token-use logic without any error surfaced).
