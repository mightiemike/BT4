## Analysis

The reported bug class—mismatched checked/unchecked arithmetic on two logically-coupled running totals within the same code path, where one uses safe arithmetic and the other does not—has a direct analog in Agave's snapshot/index-rebuild path.

### Title
Unchecked subtraction on `accounts_data_len` during index generation can silently underflow/wrap, unlike the adjacent checked `capitalization` subtraction - (File: `accounts-db/src/accounts_db.rs`)

### Summary
In `AccountsDb::generate_index` (startup index generation from snapshot storages), two coupled totals — `capitalization` and `accounts_data_len` — are both decremented by "duplicate account" contributions found during the duplicate-pubkey visit pass. The capitalization subtraction is guarded with `checked_sub().expect(...)`, but the immediately adjacent `accounts_data_len` subtraction uses a bare `-=` operator.

### Finding Description
During `generate_index`, `total_accum.accounts_data_len` is first accumulated as the sum of `data_len` for every non-zero-lamport account across all storages/slots (including duplicate/older versions of the same pubkey), via `IndexGenerationAccumulator::accumulate` and the per-slot scan in the storage-scanning helper: [1](#0-0) 

The duplicate-pubkey pass then computes `accounts_data_len_from_duplicates` — the data length of all *older* (non-max-slot) duplicate versions of each pubkey — via `visit_duplicate_pubkeys_during_startup`: [2](#0-1) 

That value is then subtracted from the running total right next to the capitalization subtraction: [3](#0-2) 

Note the asymmetry: `capitalization` uses `checked_sub(...).expect("capitalization cannot underflow")`, while `accounts_data_len -= accounts_data_len_from_duplicates` is a plain, unchecked subtraction — exactly the "unmatching logic" pattern described in the external report (one operand checked, the paired operand not). In Rust release builds, integer arithmetic does not panic on overflow/underflow by default (`overflow-checks` is typically off in release profiles), so if `accounts_data_len_from_duplicates` ever exceeds `total_accum.accounts_data_len` (e.g., due to a bug in accounting for zero-lamport accounts, obsolete-account skipping, or any accounting drift between the per-slot scan and the duplicate-visit pass), the subtraction wraps to a huge `u64` value instead of panicking, unlike the capitalization path which would loudly `expect`-panic.

### Impact Explanation
`accounts_data_len` computed here becomes `IndexGenerationInfo::accounts_data_len`, which seeds the bank's `accounts_data_size_initial` used for the accounts-data-size budget/limit enforced during transaction processing. A silent wraparound would produce an incorrect (potentially astronomically large or, after further deltas, incorrect) accounts-data-size baseline on the affected node, diverging from other honest nodes that computed the value correctly (or that took a different, non-buggy startup path). This is a snapshot-generation/rebuild correctness bug: an honest node rebuilding its index from a snapshot could silently compute a different `accounts_data_len` than the value it would get by replaying, or than other validators loading the same snapshot get if the code path only mis-triggers under specific duplicate/zero-lamport-account arrangements.

### Likelihood Explanation
This is a debug/no-debug asymmetry: in debug builds the panic behavior of `capitalization` is safety-mirrored, giving false confidence that `accounts_data_len` is equally protected. It is not — `-=` silently wraps in release mode. Because this path only runs at startup while rebuilding the index from an on-disk snapshot (a security-relevant, unprivileged-triggerable code path since it runs on every restart/snapshot load), any latent accounting mismatch between the per-slot data-length sum and the duplicate-visit data-length sum turns into a silent wraparound rather than a hard, diagnosable panic, making the underlying bug harder to detect and fix, and letting corrupted state propagate.

### Recommendation
Match the capitalization pattern: replace the bare subtraction with checked arithmetic and an explicit panic/expect on underflow, e.g.
```rust
total_accum.accounts_data_len = total_accum
    .accounts_data_len
    .checked_sub(accounts_data_len_from_duplicates)
    .expect("accounts_data_len cannot underflow");
```
This makes the invariant explicit and ensures any accounting drift is caught immediately (as a panic during startup) rather than silently corrupting the accounts-data-size baseline.

### Proof of Concept [3](#0-2) 
Compare the checked pattern used one line above for `capitalization` versus the unchecked `accounts_data_len -= accounts_data_len_from_duplicates`. There is no test analogous to `test_calculate_capitalization_overflow_intra_slot`/`test_calculate_capitalization_overflow_inter_slot` that exercises an `accounts_data_len` underflow-detection panic, confirming the guard is genuinely absent rather than covered elsewhere: [4](#0-3)
