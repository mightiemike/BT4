## Title
`ensure_match_transaction_info` never checks `position_state_checkpoint_hash` / hot-state checkpoint hash, so replay-verify can accept a corrupted Trading-Native state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the invariant that binds an executed `TransactionOutput` to the authenticated `TransactionInfo` carried by the accumulator/proof (status, gas, write-set hash, event root hash). It is explicitly documented in-code to skip validating the state/hot-state and `position_state_checkpoint_hash` fields, meaning a state root for the "trading-native" Position subsystem can diverge from what was actually computed without this function detecting it. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` checks four invariants between a produced `TransactionOutput` and the `TransactionInfo` it is supposed to match: execution status, gas used, write-set hash (`state_change_hash`), and event root hash. [2](#0-1) 

It explicitly does **not** check the checkpoint hashes for state/hot-state and the position (`position_state_checkpoint_hash`), as stated directly in the code comment:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

This is corroborated by the `TradingNative`/`Position` native-state machinery added elsewhere in the codebase (e.g. `storage/aptosdb/src/native_state_committer.rs`, `storage/aptosdb/src/db/aptosdb_native_position.rs`), which maintains a separate Merkle tree and checkpoint hash for Position state distinct from the main state tree, and `position_state_checkpoint_hash` is threaded through `execution/executor-types/src/execution_output.rs` and `execution/executor-types/src/state_checkpoint_output.rs`, and consumed at bootstrap in `state-sync/state-sync-driver/src/bootstrapper.rs`.

Because `ensure_match_transaction_info` is the generic function used by replay/verification tooling (its own doc calls out `db-tool`'s `replay_on_archive`) to assert that a re-executed `TransactionOutput` matches the committed `TransactionInfo`, any bug in local Position-state computation, storage commit, or hot-state application that corrupts the `position_state_checkpoint_hash` (or the hot-state checkpoint hash) would go completely undetected by this check. Replay would report success even though the authenticated Position state root (and consequently proofs served against it) is wrong.

### Impact Explanation
This falls squarely within the "Proof And Storage Pivots" scope: authenticated state-view output (the Position/trading-native state root) is not bound to a verified/matching commitment during replay-verify, which is the exact tool operators and auditors use to catch state divergence. If any other bug (execution nondeterminism, a native-committer accounting error, a Merkle-leaf update bug, etc.) corrupts the Position state root, replay-verify — the safety net meant to catch precisely such divergence — will not flag it, because this comparator omits the check. That allows a wrong ledger/state commitment to be silently accepted as correct, undermining the state-commitment integrity guarantee that replay tooling exists to enforce.

The impact is currently bounded by the fact that `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is a feature flag not yet enabled (per the comment "Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), so as long as that flag stays off in production, the missing check may be inert. However, the code path (`ensure_match_transaction_info`) is unconditionally missing the check regardless of the flag's state, and I could not verify from the index whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is already enabled on any live network or whether other call sites rely on this function being complete before that flag flips.

### Likelihood Explanation
Low-to-moderate today given the explicit TODO and presumed flag-gating, but the root cause is a genuine, code-confirmed gap (not speculative) in a verification-critical function, and the risk becomes concrete as soon as `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on, at which point any independent bug in Position-state computation would be masked from replay-verify.

### Recommendation
Add validation of the state checkpoint hash(es) — including `position_state_checkpoint_hash` and hot-state checkpoint hash — inside `ensure_match_transaction_info`, gated appropriately (e.g. only when the relevant feature/roots are enabled and known), before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on for any network. Until this is done, `replay_on_archive` and similar replay-verify tooling should not be relied upon to catch Position/hot-state root divergence.

### Proof of Concept
Not applicable as a runtime exploit — this is a code-audit finding of a missing invariant check, not an incorrectly-computed value. It is demonstrated directly by the source at `types/src/transaction/mod.rs:2139-2204`: the function performs `ensure!` checks for status, gas, write-set hash, and event root hash, but returns `Ok(())` without any check against `position_state_checkpoint_hash` or the state/hot-state checkpoint hash, as acknowledged by the adjacent comment.

**Note on confidence**: I was not able to fully trace whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently active on any deployed network, nor find all downstream consumers that assume `ensure_match_transaction_info` is a complete state-binding check — this would require further investigation with direct repository access (e.g. a Devin session) beyond what the current search index could confirm.

```rust
    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
