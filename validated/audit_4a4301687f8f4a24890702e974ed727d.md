### Title
Starknet OS `charge_fee` accepts the fee-token `transfer` return value without validating `success`, allowing free-of-charge transaction inclusion analogous to Cooler's unchecked-transfer rollover bug - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo])

### Summary
The reported Cooler bug is caused by `roll()`/`clear()` treating a non-reverting `transferFrom` call as proof of payment without checking the ERC20 `success` return value, letting the borrower "pay" nothing while still progressing state. The Starknet OS `charge_fee` function has the same root-cause pattern: it invokes the fee token's `transfer` entry point through `non_reverting_select_execute_entry_point_func`, and only asserts that the call did not *revert* (`is_reverted = 0`). It never inspects the felt `retdata` returned by `transfer` (the ERC20 `success` boolean), so a fee token whose `transfer` implementation can return `success = 0` (Cairo boolean false) without triggering a revert is treated by the OS exactly like a successful payment.

### Finding Description
`charge_fee` builds calldata for `TRANSFER_ENTRY_POINT_SELECTOR` on the fee token contract and executes it via `non_reverting_select_execute_entry_point_func`: [1](#0-0) 

`non_reverting_select_execute_entry_point_func` only asserts `is_reverted = 0` and returns `retdata_size`/`retdata` to the caller, but `charge_fee` discards these return values entirely (it does not bind or check them): [2](#0-1) 

Compare this with `run_validate`, which explicitly checks the retdata contents for `VALIDATED` after calling the same helper: [3](#0-2) 

No equivalent check exists for the fee-transfer retdata in `charge_fee`. As in the Cooler `roll()` case, the transfer's actual balance effect is governed by the fee token contract's storage writes (which the OS does separately account for via `contract_state_changes`), but the *logical acceptance* of the transfer as "payment complete" is gated only on it not reverting — not on the boolean success value the ERC20 standard defines as the actual signal of transfer success. If the deployed fee token's `transfer` function can return `0` (failure) instead of asserting/reverting on insufficient balance (i.e., a non-reverting ERC20 implementation, as explicitly assumed in the Cooler report's threat model), `charge_fee` would treat the transaction as fee-paid.

### Impact Explanation
This is scoped to the specific, protocol-controlled STRK/ETH fee-token classes used on Starknet, whose `transfer` implementation is expected to always revert on insufficient balance (unlike an arbitrary attacker-supplied token in Cooler). Given the fee token is "well known to the sequencer" (per the blockifier's own comment) and its Cairo implementation reverts on failure, the practical exploitability of this specific analog depends entirely on whether a class-hash-replaceable/implementation change to the canonical fee token could ever return `0` instead of reverting. Under the current known ERC20 implementations bundled in this repo (`ERC20.cairo`), `ERC20_transfer` uses `assert`-based checks that abort execution (which propagates as `is_reverted`), so under the current fee-token class this specific path does not appear currently reachable by an unprivileged transaction sender in production. I was not able to fully verify whether any governance/upgrade path could change the fee token class hash to one with non-reverting failure semantics, which is required to make this concretely exploitable today.

### Likelihood Explanation
Low under the current known fee-token contract behavior (which reverts on failure), but the code pattern itself — trusting call success solely on the absence of a revert rather than checking the entry point's own success/return semantics — is the same class of bug as the Cooler report and would immediately become exploitable if the fee-token's `transfer` implementation ever changes to return a non-reverting failure indicator.

### Recommendation
In `charge_fee`, capture the `retdata_size`/`retdata` from `non_reverting_select_execute_entry_point_func` and assert that they encode `success = 1` (analogous to the check already performed in `run_validate` for `VALIDATED`), rather than relying solely on the absence of a Cairo revert to conclude that the fee transfer succeeded.

### Proof of Concept
Not applicable as a runnable PoC against the current in-repo fee-token contract, since its `transfer` implementation reverts (rather than returning `false`) on insufficient balance, per [4](#0-3)  (unrelated helper) and the ERC20 template's `assert`-based transfer logic. The structural gap is demonstrated purely by code inspection: `charge_fee` never consumes the `retdata` returned by the transfer call [1](#0-0) , unlike `run_validate`'s explicit retdata check [5](#0-4) .

// Same as `select_execute_entry_point_func`, but does not support reverts and does
// not have an implicit 'revert_log' argument.
func non_reverting_select_execute_entry_point_func{
    range_check_ptr,
    remaining_gas: felt,
    builtin_ptrs: BuiltinPointers*,
    contract_state_changes: DictAccess*,
    contract_class_changes: DictAccess*,
    outputs: OsCarriedOutputs*,
}(block_context: BlockContext*, execution_context: ExecutionContext*) -> (
    retdata_size: felt, retdata: felt*, is_deprecated: felt
) {
    let revert_log = init_revert_log();
    let (is_reverted, retdata_size, retdata, is_deprecated) = select_execute_entry_point_func{
        revert_log=revert_log
    }(block_context=block_context, execution_context=execution_context);
    assert is_reverted = 0;
    return (retdata_size, retdata, is_deprecated);
}
