Based on my investigation, the key finding is the `afterInboundBallotTerminal` hook in `x/uexecutor/keeper/ballot_hooks.go`, which performs an unbounded, non-paginated `Walk` over the entire `PendingInbounds` collection on every terminal ballot transition, explicitly justified by a comment assuming "the pending set is small and transient" — an assumption an attacker can invalidate.

### Title
Unbounded `PendingInbounds.Walk` in ballot-termination hook enables state-processing DoS via cheap spam inbounds - (File: x/uexecutor/keeper/ballot_hooks.go)

### Summary
`afterInboundBallotTerminal` scans the entire `PendingInbounds` collection with an unpaginated `Walk` to find the ballot being finalized, every single time any inbound ballot reaches a terminal state. [1](#0-0) 

### Finding Description
The comment explicitly states the design assumption: "the pending set is small and transient" [2](#0-1) . However, `PendingInbounds` entries are populated by `RecordInboundVote`, called whenever any validator votes on an observed inbound event — which is driven by ordinary user deposit/inbound transactions on external chains that Push Chain's universal validators observe and vote on. [3](#0-2) 

Unlike `VTVLVesting.vestingRecipients` (which only ever grows because there's no removal), `PendingInbounds` entries *are* removed once all ballot variants reach terminal state [4](#0-3) . But removal only happens *after* the `Walk` runs, and it happens on the honest-validator finalization path itself. This means:
1. An unprivileged user can generate many distinct cheap/low-value cross-chain inbound events (e.g., dust deposits/messages from an external chain) that validators will observe and vote on, each creating a new `PendingInbounds` entry.
2. Every terminal ballot transition (pass/expire/reject) — including for entries the attacker created — triggers a full linear `Walk` over the current `PendingInbounds` set to locate the matching ballot ID by scanning every entry's `Variants` list.
3. If many such entries are outstanding simultaneously (e.g., due to ballot-voting-window delays, slow-to-converge chains, or a burst of concurrent inbounds), each terminal-transition hook call becomes O(N) over the full pending set, and this cost is paid inside block processing (an `AfterBallotTerminal` hook invoked from the state machine, not a read-only query).

This differs qualitatively from the analogous read-only `AllPendingOutbounds`/`AllExpiredInbounds` query endpoints, which use bounded pagination via `query.CollectionPaginate` [5](#0-4) . The `ballot_hooks.go` walk, by contrast, runs unconditionally and unbounded inside consensus-critical state transition logic on every ballot finalization.

### Impact Explanation
This is a state-machine/consensus-path cost blow-up, not merely an off-chain query DoS. As the number of concurrently outstanding (not-yet-fully-terminal) inbound ballots grows, each individual ballot's terminal-transition processing degrades linearly, and since this triggers on every ballot for every inbound (not just attacker-created ones), an attacker flooding the mempool/inbound-observation pipeline with many low-value inbound events can inflate the average and worst-case per-block processing cost for finalizing ballots, potentially degrading block production or making some blocks fail to include all terminal transitions in a timely manner. Because `PendingInbounds` cardinality is driven purely by "how many distinct inbound events are simultaneously mid-ballot" (a function of vote timing and network conditions, which an attacker can amplify by generating bursts of cheap/dust inbound events across supported source chains), this is reachable without any privileged role.

### Likelihood Explanation
Likely low-to-medium in practice because: (a) ballot voting windows are typically short so the pending set doesn't grow unboundedly in steady state; (b) an attacker would need to sustain many concurrent low-value inbound events across external chains to keep `PendingInbounds` large, which costs gas/fees on the source chains; (c) the underlying design intentionally trades this Walk cost against not storing an index from ballotID → utxKey. Still, the assumption "pending set is small" is not enforced by any code-level bound, and Push Chain is a system explicitly designed for cheap/gasless multi-chain interactions, lowering the cost of generating many concurrent inbound events compared to a typical L1.

### Recommendation
Maintain a direct index from `ballotID → utxKey` (set alongside `RecordInboundVote`, removed alongside the corresponding `PendingInbounds` removal) so `afterInboundBallotTerminal` can do an O(1) lookup instead of an O(N) `Walk` over the full pending set. Alternatively, bound the maximum size of `PendingInbounds`/enforce faster ballot expiry so N stays provably small.

### Proof of Concept
1. Attacker issues a burst of many distinct low-value/dust inbound transactions on a supported external chain, each observed and voted on by universal validators, each creating a new `PendingInbounds` entry via `RecordInboundVote`.
2. While these entries remain pending (bounded only by the ballot voting window, not by any explicit cap), each individual ballot's terminal transition (`AfterBallotTerminal` → `afterInboundBallotTerminal`) performs a full `Walk` over the current `PendingInbounds` set size N.
3. As N increases with sustained inbound spam, per-ballot finalization cost scales linearly, inflating aggregate block-processing cost proportional to N × (number of ballots finalized in that window), which is attacker-influenced through inbound volume alone.

<br>

Note: I was unable to fully verify concrete bounds on ballot-voting-window duration or exact gas/cost economics of generating inbound events in this codebase within the available exploration; a full assessment of practical severity would benefit from reviewing `x/uvalidator` ballot expiry parameters and the `universalClient` inbound-observation cost model, which I did not have iterations remaining to inspect in depth.
