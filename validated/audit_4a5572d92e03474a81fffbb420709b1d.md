## Analysis

The question's specific mechanism — that `base58ToHex` itself causes "address confusion" — does not hold up. Tracing the code path: [1](#0-0) 

`base58ToHex` is a pure, lossless round-trip: it base58-decodes a string back into the exact same raw bytes that were originally encoded via `solana.PublicKey(...).String()`, then hex-encodes them. Since the sender bytes are read directly from a fixed 32-byte slice at `decoded[offset:offset+32]`, converted to a `solana.PublicKey`, stringified to base58, and then decoded straight back to hex, the two conversions cancel out exactly — there is no length ambiguity, no truncation, and no way for "trailing fields" or "discriminators" appearing elsewhere in the payload to bleed into this specific 32-byte window. This part of the exploit theory is not supported by the code. [2](#0-1) 

However, tracing further up the call chain surfaces a related but distinct real issue in the same subsystem: **the SVM event listener never verifies which program actually emitted a given "Program data:" log line before parsing it as a gateway event.** [3](#0-2) 

`processSignatureBatch` fetches transactions returned by `GetSignaturesForAddress(gatewayAddr, ...)` — an RPC call that returns any transaction where the gateway's pubkey merely appears among the transaction's account keys (not necessarily as the invoked program) — and then flatly iterates `tx.Meta.LogMessages`, running `determineEventType`/`ParseEvent` on every single log line: [4](#0-3) 

`determineEventType` and `parseSendFundsEvent` only check the `"Program data: "` string prefix and the first 8 bytes (discriminator) of the base64 payload; there is no correlation to the surrounding `"Program <id> invoke [n]"` / `"Program <id> success"` log-frame that Solana runtimes emit to indicate which program produced a given log line. An unprivileged attacker can therefore:

1. Submit a transaction that references the gateway program's pubkey as an arbitrary (even read-only, non-executed) account key — satisfying `GetSignaturesForAddress` inclusion.
2. In the same transaction, invoke their own attacker-deployed program that emits a `sol_log_data`/"Program data:" log whose first 8 bytes exactly match the known `send_funds` discriminator and whose remaining bytes are a well-formed `sender/recipient/bridge_token/bridge_amount/data/revert_recipient/tx_type` Borsh layout — all attacker-chosen.
3. No real funds are ever locked/transferred through the actual gateway program.

Because every honest node runs the identical listener logic against the identical public transaction, this is not a "malicious validator" scenario — it is an unprivileged attacker fooling the honest client-side parser into treating an unrelated program's log as a genuine gateway `send_funds` inbound event, which then flows into `parseUniversalTxEvent` → `store.Event` → `VoteInbound`, causing all honest UVs to converge on a forged event and vote it through.

I could not verify within the available context whether `x/uexecutor`'s `VoteInbound`/finalization path performs any independent on-chain corroboration (e.g., checking an actual balance/lock movement on the source chain, or a Merkle/receipt proof tied to the gateway program ID) that would catch this before minting/crediting the recipient — that check exists (if at all) outside `universalClient/chains/svm/` and I was unable to trace it further in this session. If no such independent verification exists, this converts directly into unauthorized minting/crediting on Push Chain for zero real inbound value, matching the "unauthorized mint" impact class in scope.

### Title
Gateway event listener trusts log content over invocation context, allowing forged `send_funds`/outbound events - (File: `universalClient/chains/svm/event_listener.go`)

### Summary
`processSignatureBatch` classifies and parses every log line in a transaction referencing the gateway address purely by string prefix and an 8-byte discriminator match, without binding the log to the program that actually emitted it.

### Finding Description
`GetSignaturesForAddress` returns any transaction where the gateway pubkey appears in the account list, not only transactions that invoke the gateway program. `determineEventType` (event_listener.go:398-422) and `parseSendFundsEvent`/`parseOutboundObservationEvent` (event_parser.go:63-134) accept any `"Program data: "`-prefixed log whose first 8 bytes match a known discriminator, with no check against the surrounding `Program <id> invoke/success` log frame that would tie the data to the real gateway program.

### Impact Explanation
An attacker-controlled program can emit a log that satisfies the discriminator and byte-length checks for `send_funds` (or the outbound-observation events), with fully attacker-chosen sender, recipient, token, amount, payload, and revert recipient, while never calling the real gateway and without moving any real funds. If not independently re-validated downstream in `x/uexecutor`, this results in forged inbound/outbound observations reaching honest-validator consensus, and unauthorized mint/release/refund of funds — the impact class the question is aiming at, though not the specific `base58ToHex` mechanism it names.

### Likelihood Explanation
Requires only submitting an ordinary Solana transaction (including a self-deployed program) that references the gateway pubkey as an account key — no privileged access, no validator/relayer compromise. Moderate-to-high likelihood, gated on whether a downstream check exists that I could not confirm.

### Recommendation
Parse `tx.Meta.LogMessages` with awareness of the `Program <id> invoke [n]` / `Program <id> success` frames (or use structured `innerInstructions`/CPI program-id metadata) so that a `"Program data:"` line is only accepted when it falls within a frame whose program ID equals the configured gateway address, not merely when the gateway address appears anywhere in the transaction's account keys.

### Proof of Concept
1. Deploy an arbitrary Solana program `P` (attacker-controlled).
2. Build a transaction with two instructions: (a) any no-op instruction that lists the real gateway program's pubkey as a read-only account, (b) a call to `P` that emits `sol_log_data` with bytes = `send_funds` discriminator || fabricated sender/recipient/token/amount/payload/revert_recipient/tx_type per the Borsh layout in `decodeUniversalTxEvent`.
3. Submit the transaction to Solana as an ordinary user.
4. The universalClient's SVM listener picks it up via `GetSignaturesForAddress(gatewayAddr,...)`, matches the discriminator in `P`'s log, and stores/votes a forged inbound `send_funds` event despite no interaction with the real gateway program.

**Note:** the question's premise that `base58ToHex` itself normalizes addresses incorrectly is not supported by the code — that conversion is bijective and correct. The above is the closest real gap found in the same file/subsystem matching the stated invariant ("only well-formed SVM gateway bytes can become an inbound or outbound observation"), but confirming exploitability to actual fund loss requires checking whether `x/uexecutor` independently validates inbound observations against real on-chain state, which is outside what I could verify in this pass.

// base58ToHex converts a base58 encoded string to hex format (0x...)
func base58ToHex(base58Str string) (string, error) {
	if base58Str == "" {
		return "0x", nil
	}

	// Decode base58 to bytes
	decoded, err := base58.Decode(base58Str)
	if err != nil {
		return "", fmt.Errorf("failed to decode base58: %w", err)
	}

	// Convert to hex with 0x prefix
	return "0x" + hex.EncodeToString(decoded), nil
}

// determineEventType determines the event type based on the log discriminator
func (el *EventListener) determineEventType(log string) string {
	if !strings.HasPrefix(log, "Program data: ") {
		return ""
	}

	eventData := strings.TrimPrefix(log, "Program data: ")
	decoded, err := base64.StdEncoding.DecodeString(eventData)
	if err != nil {
		return ""
	}

	if len(decoded) < 8 {
		return ""
	}

	discriminator := strings.ToLower(hex.EncodeToString(decoded[:8]))

	// Look up event type from discriminator map
	eventType, ok := el.discriminatorToEventType[discriminator]
	if !ok {
		return ""
	}

	return eventType
