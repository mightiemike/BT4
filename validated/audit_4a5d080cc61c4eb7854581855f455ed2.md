### Title
Attacker-triggered node panic (DoS) via `.unwrap()` on `AotContractExecutor::from_path` in Sierra-to-Native compilation - (File: crates/apollo_compile_to_native/src/compiler.rs)

### Summary
The reported CVE (CVE-2017-14975) is a NULL-pointer dereference in Poppler caused by an uninitialized/unchecked data structure being dereferenced after a parsing step, allowing an attacker-supplied input to crash the process. The closest reachable analog in this sequencer codebase is in the Sierra-to-Cairo-Native compilation pipeline, where the result of loading a compiled artifact from disk is force-unwrapped without validating that the expected data is actually present, in a step that is directly triggered by an attacker-submitted `declare` transaction.

### Finding Description
`SierraToNativeCompiler::compile` in `apollo_compile_to_native/src/compiler.rs` invokes the external native-compiler binary via `compile_with_args`, then loads the resulting object/library file from disk: [1](#0-0) 

The critical line is:
```
Ok(AotContractExecutor::from_path(output_file.path())
    .map_err(|e| CompilationUtilError::CompilationError(e.to_string()))?
    .unwrap())
```
`.map_err(...)?` only converts and propagates the outer `Result`'s `Err` variant; the inner value produced by `from_path` is then force-unwrapped with `.unwrap()`. If `from_path` can legitimately return `Ok(None)` (e.g., because the compiled output file exists but does not contain the expected/parseable executor data — analogous to Poppler's uninitialized-structure/NULL-dereference condition), this `.unwrap()` will panic the calling thread rather than returning a typed error.

This call is reached from a user-controlled declare transaction:
- `NativeClassManager::set_and_compile` calls `compiler.compile(...)` synchronously when `CairoNativeMode::WaitOnCompilation` is configured, directly on the thread handling the incoming declare transaction/class caching path: [2](#0-1) 
- It's also invoked from the async compilation worker (`process_compilation_request` / `run_compilation_worker`) for `LazyCompilation` mode: [3](#0-2) 

Unlike the Sierra→CASM compiler (`apollo_compile_to_casm`), which explicitly documents and enforces process isolation and resource limits so that compiler crashes/DoS cannot affect the sequencer process: [4](#0-3) 
the native compiler path re-loads and interprets the produced artifact *in-process* after the subprocess exits, and a malformed or unexpected input that causes `from_path` to yield `None` will panic the parent (gateway/batcher) process directly, not merely the isolated subprocess.

### Impact Explanation
A panic in `SierraToNativeCompiler::compile` propagates up through `process_compilation_request`, which is only guarded by `.unwrap_or(())` for the outer `Result` — it does not protect against a raw `panic!` unwind from an inner `.unwrap()`. In `WaitOnCompilation` mode this executes synchronously on the request-handling thread of the gateway or batcher, so a panic there can crash/abort the handling thread or process (depending on panic strategy), constituting a denial-of-service reachable from any account able to submit a `declare` transaction with a Sierra program that triggers this edge case in the native compiler's output. This matches the report's "network unable to confirm new transactions" outcome category when native compilation is enabled (`cairo_native_mode` not `Off`).

### Likelihood Explanation
Likelihood depends on operational configuration: `cairo_native_mode` defaults to `Off` in the shipped config schema, meaning native compilation (and this code path) is disabled by default: [5](#0-4) 
When native execution is enabled (`wait_on_compilation` or `lazy_compilation`), this path is directly reachable by any unprivileged declarer submitting a Sierra class. I was unable to fully verify, from the code visible in this index, the exact conditions under which `cairo_native::executor::AotContractExecutor::from_path` returns `Ok(None)` versus `Err`, since that type is defined in the external `cairo_native` crate and was not present in the indexed codebase. This is a limitation of the analysis — confirming the exploitability requires inspecting the `cairo_native` crate's `AotContractExecutor::from_path` implementation, which a Devin session with full repository/dependency access could verify.

### Recommendation
Replace the `.unwrap()` in `crates/apollo_compile_to_native/src/compiler.rs` with proper error propagation (e.g., `.ok_or_else(|| CompilationUtilError::CompilationError("Compiled executor missing expected data".into()))?`), and audit `process_compilation_request`/`run_compilation_worker` to ensure panics from the compiler invocation are caught (e.g., via `std::panic::catch_unwind`) rather than allowed to propagate to the request-handling thread, consistent with the isolation guarantees already documented and implemented for the Sierra→CASM path.

### Proof of Concept
Conceptual PoC (requires a node configured with `cairo_native_mode = wait_on_compilation` or `lazy_compilation`):
1. Submit a `declare` transaction with a syntactically valid Sierra program (passing gateway's `validate_sierra_version`/size/entry-point checks) that is nonetheless crafted so the native compiler binary produces an output file lacking the data `AotContractExecutor::from_path` expects (e.g., empty/truncated shared object due to an edge case in native codegen).
2. The gateway/batcher thread calls `NativeClassManager::set_and_compile` → `SierraToNativeCompiler::compile` → `AotContractExecutor::from_path(...).unwrap()`.
3. If `from_path` returns `Ok(None)` for this malformed artifact, the `.unwrap()` panics, crashing the handling thread/process — denial of service from a single unprivileged transaction.

I could not construct or verify a concrete Sierra program that reliably drives `AotContractExecutor::from_path` to `Ok(None)` using only the indexed code, since the internals of the `cairo_native` dependency are outside this repository's index.

fn process_compilation_request(
    class_cache: RawClassCache,
    compiler: Arc<SierraToNativeCompiler>,
    compilation_request: CompilationRequest,
    panic_on_compilation_failure: bool,
) -> Result<(), CompilationUtilError> {
    let (class_hash, sierra, casm) = compilation_request;
    if let Some(CompiledClasses::V1Native(_)) = class_cache.get(&class_hash) {
        // The contract class is already compiled to native - skip the compilation.
        return Ok(());
    }
    let sierra_for_compilation = into_contract_class_for_compilation(sierra.as_ref());
    let start = Instant::now();
    let compilation_result = compiler.compile(sierra_for_compilation);
    let duration = start.elapsed();
    log::info!(
        "Compiling to native contract with class hash: {:#066x}. Duration: {:.3} seconds",
        class_hash.0,
        duration.as_secs_f32()
    );
    match compilation_result {
        Ok(executor) => {
            let native_compiled_class = NativeCompiledClassV1::new(executor, casm);
            class_cache.set(
                class_hash,
                CompiledClasses::V1Native(CachedCairoNative::Compiled(native_compiled_class)),
            );
            log::info!("Compilation succeeded");
            Ok(())
        }
