### Title
Missing `supportUnfreezeDelay()` Feature-Gate Check in TVM Native `WithdrawExpireUnfreezeProcessor` - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawExpireUnfreezeProcessor.java`)

### Summary
The transaction-level `WithdrawExpireUnfreezeActuator` gates the withdrawal of expired unfrozen (Stake V2) balances behind a committee-controlled feature switch, `dynamicStore.supportUnfreezeDelay()`. The TVM native-contract counterpart that performs the identical state transition, `WithdrawExpireUnfreezeProcessor` (invoked from smart contract execution), omits this same gating check in its `validate()` method.

### Finding Description
`WithdrawExpireUnfreezeActuator.validate()` explicitly refuses to execute the withdraw operation unless the network-wide feature has been enabled by the committee: [1](#0-0) 

This mirrors a pause/gate check that must precede a claim-like state transition — exactly the bug class described in the report, where a claim/withdraw function must verify a paused/disabled state before mutating balances.

However, the parallel execution path reachable from TVM smart contract calls, `WithdrawExpireUnfreezeProcessor.validate()`, performs the same balance/account lookups and arithmetic checks but never calls `supportUnfreezeDelay()`: [2](#0-1) 

Its `execute()` method then performs the balance mutation (crediting `totalWithdrawUnfreeze` back to the account balance and clearing/rewriting the `UnfrozenV2` list) without re-checking the feature flag: [3](#0-2) 

This is structurally identical to the reported bug class: two functionally equivalent code paths implement the same state-mutating operation, but only one of them enforces the governance/pause-style precondition (`whenNotPausedToken` in the original report vs. `supportUnfreezeDelay()` here). An attacker/user reaching the withdraw logic via the TVM native-contract path bypasses the intended feature gate that the actuator path enforces.

### Impact Explanation
If the committee has not (or no longer) enabled the `UNFREEZE_DELAY_DAYS` feature via `ProposalService` (which flips `supportUnfreezeDelay()`), directly broadcasting a `WithdrawExpireUnfreezeContract` transaction is correctly rejected. But the same withdrawal effect can be produced through the TVM native-contract call path (`WithdrawExpireUnfreezeProcessor`), which does not perform this check, allowing balance state changes that the actuator layer was designed to prevent while the feature is disabled. This creates inconsistent, ungoverned execution of a balance-affecting operation and undermines the committee's ability to gate/disable this functionality network-wide, which is an accounting/consensus-consistency concern between the two enforcement paths.

### Likelihood Explanation
Reachability depends on how/where `WithdrawExpireUnfreezeProcessor` is wired into TVM opcode/native-contract dispatch; if any deployed smart contract can invoke this native contract call, any account with unfrozen V2 balances can trigger it. Practical exploitability also depends on whether `UnfrozenV2` list entries can exist while `supportUnfreezeDelay()` is false (e.g., if the committee toggles the flag off after entries were created while it was on), a scenario plausible given committee proposals can change `UNFREEZE_DELAY_DAYS` over time as seen in `ProposalService.process()`.

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check to `WithdrawExpireUnfreezeProcessor.validate()` that is enforced in `WithdrawExpireUnfreezeActuator.validate()`, throwing `ContractValidateException` when the feature is not enabled, to keep both execution paths consistent.

### Proof of Concept
Not independently executable from static analysis alone — full confirmation requires tracing the TVM opcode/native-contract dispatch table to confirm `WithdrawExpireUnfreezeProcessor` is reachable via a smart-contract call (its wiring point in `Program.java` could not be fully confirmed with the tools available). Conceptually: (1) commit UnfreezeBalanceV2 transactions while `supportUnfreezeDelay()` is true, populating `UnfrozenV2` entries; (2) have committee disable the feature (`UNFREEZE_DELAY_DAYS` proposal set back to a disabling value); (3) attempt `WithdrawExpireUnfreezeContract` via a normal transaction — rejected by `WithdrawExpireUnfreezeActuator.validate()`; (4) invoke the equivalent operation via the TVM native-contract call path — not blocked by `WithdrawExpireUnfreezeProcessor.validate()`, allowing the withdrawal to succeed despite the feature being disabled.

  public void validate(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("Invalid address");
    }
    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    if (Objects.isNull(accountCapsule)) {
      String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);
      throw new ContractValidateException(ACCOUNT_EXCEPTION_STR
          + readableOwnerAddress + NOT_EXIST_STR);
    }

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = accountCapsule.getInstance()
        .getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze < 0) {
      throw new ContractValidateException("no unFreeze balance to withdraw ");
    }
    try {
      LongMath.checkedAdd(accountCapsule.getBalance(), totalWithdrawUnfreeze);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
  }

  public long execute(WithdrawExpireUnfreezeParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();
    DynamicPropertiesStore dynamicStore = repo.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    List<Protocol.Account.UnFreezeV2> unfrozenV2List = ownerCapsule.getInstance().getUnfrozenV2List();
    long totalWithdrawUnfreeze = getTotalWithdrawUnfreeze(unfrozenV2List, now);
    if (totalWithdrawUnfreeze <= 0) {
      return 0;
    }
    ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
        .setBalance(ownerCapsule.getBalance() + totalWithdrawUnfreeze)
        .build());
    List<Protocol.Account.UnFreezeV2> newUnFreezeList = getRemainWithdrawList(unfrozenV2List, now);
    ownerCapsule.clearUnfrozenV2();
    ownerCapsule.addAllUnfrozenV2(newUnFreezeList);
    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    return totalWithdrawUnfreeze;
  }
