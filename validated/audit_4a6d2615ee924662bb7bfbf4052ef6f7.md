**Analysis:**

`tower_epoch_credits_iter` deliberately iterates over the vote account's *entire* `epoch_credits_iter` (all epochs since the stake's `credits_observed` was last updated), not just a single "reward epoch." This multi-epoch accumulation is intentional legacy tower-rewards behavior: a stake account can go unredeemed across several epochs, and this loop sums `stake_amount * earned_credits` for each epoch in that unredeemed range, advancing `new_credits_observed` monotonically via `calc_earned_credits`. [1](#0-0) 

The "only count credits earned in the reward epoch" invariant referenced in the question applies specifically to the **Alpenglow** path (`calculate_alpenglow_points`), which explicitly checks `epoch != reward_epoch_delegated_stakes.epoch` and returns zero points for stale/mismatched epochs — this guard does not exist (and is not needed) in the tower path because tower rewards are, by design, cumulative across skipped epochs. [2](#0-1) 

Double-counting is prevented because `new_credits_observed` is advanced to `max(new_credits_observed, final_epoch_credits)` on every iteration, and the stake's persisted `credits_observed` field ensures subsequent reward calculations only start from the last point where credits were paid.
