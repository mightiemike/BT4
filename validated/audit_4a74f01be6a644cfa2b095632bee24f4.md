### Title
`handle_poison_microblock` fails to validate that both headers share the same `prev_block`/tenure context, enabling reward-slashing based on two genuinely-signed but non-forking microblocks from different tenures - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`StacksChainState::handle_poison_microblock` (stackslib/src/chainstate/stacks/db/transactions.rs:722-857) only checks that `mblock_header_1` and `mblock_header_2` were signed by the same key (`check_microblock_header_signer`) and that the recovered `pubkh` was recorded somewhere within the miner-reward maturity window. It never checks `mblock_header_1.prev_block == mblock_header_2.prev_block`, never checks `mblock_header_1.sequence == mblock_header_2.sequence`, and never checks that the two headers actually differ. That equality/cross-check exists only in the mempool admission path (`will_admit_mempool_tx`, stackslib/src/chainstate/stacks/db/blocks.rs:6844-6850), which is not re-enforced during transaction/block processing.

### Finding Description
The claimed-invariant is: `poison_reward_paid == genuine_previously_broadcast_double_sign` (i.e. slashing should only occur when the SAME miner key signed two DIFFERENT, conflicting microblocks descending from the SAME parent at the SAME sequence — a real equivocation/fork within one tenure's stream).

The on-chain enforcement path is: [1](#0-0) 
which only recovers and compares the ECDSA-recoverable public key hash of the two headers via `check_microblock_header_signer`: [2](#0-1) 
and then checks that hash was recorded for some prior block height and is within `MINER_REWARD_MATURITY`: [3](#0-2) 
followed directly by recording a poison report keyed only by `mblock_pubk_height` and `mblock_header_1.sequence`: [4](#0-3) 

At no point is `mblock_header_1.prev_block` compared to `mblock_header_2.prev_block`, nor is `mblock_header_1.sequence` compared to `mblock_header_2.sequence`, nor is header-distinctness enforced. The only place these checks exist is in the mempool's static rejection logic used by `will_admit_mempool_tx`: [5](#0-4) 
This is a mempool admission gate, not a consensus-level validity rule re-checked when a block containing the transaction is processed via `process_transaction` → `handle_poison_microblock`.

Because microblock sequence numbers are scoped per-tenure (they restart at 0 for each anchored block's microblock stream — see the "first microblock header sequence" check in `validate_parent_microblock_stream`), and because the microblock signing key (`microblock_pubkey_hash`) can be reused by the same miner across separate, non-forking tenures, two entirely genuine, honestly-broadcast microblock headers from two DIFFERENT tenures can coincidentally carry the same `sequence` value while being signed by the same key. An unprivileged observer (anyone who received both broadcast microblocks over the network — no forgery required, no private key needed) can package these two genuine headers into a single `PoisonMicroblock` transaction. `handle_poison_microblock` will accept it as valid because it only checks "same signer key" + "maturity window", never checking that the headers came from the same parent/tenure/fork.

### Impact Explanation
This breaks the equality `poison_reward_paid == genuine_previously_broadcast_double_sign`: an honest miner who never equivocated within a single microblock stream is slashed, and the reporting party is awarded a commission of that miner's coinbase (per the reward record inserted at lines 828-855). This is a reward mis-payment/theft against a specific miner, triggerable by any unprivileged, minority participant merely relaying two already-public, honestly-signed headers — matching the "poison or reward mis-payment" High-severity bucket. All correctly-running nodes will agree the transaction is valid (since the check that's missing is missing everywhere in the consensus path), so it is not a network split, but it is an incorrect/wrongful slash and reward reassignment.

### Likelihood Explanation
Preconditions: (1) the target miner must reuse the same `microblock_pubkey_hash` across two distinct, non-forking tenures — this depends on the actual production key-derivation scheme in the miner's keychain, which I could not fully confirm within the available context (only a small-range test usage of `keychain.get_microblock_key(1+i)` was found in stacks-node/src/tests/mempool.rs); (2) the sequence numbers of the two genuine streams must collide, which is likely since sequences restart at 0 each tenure and streams are typically short. No BTC spend or stake is required by the attacker beyond broadcasting a standard Stacks transaction; they only need to have observed two already-public microblocks. This is repeatable for every miner that reuses a microblock key and produces short streams.

### Recommendation
In `handle_poison_microblock` (stackslib/src/chainstate/stacks/db/transactions.rs), before proceeding to record a poison report, enforce the same cross-checks that `will_admit_mempool_tx` performs at the consensus level: require `mblock_header_1.sequence == mblock_header_2.sequence`, `mblock_header_1.prev_block == mblock_header_2.prev_block`, `mblock_header_1.version == mblock_header_2.version`, and `mblock_header_1 != mblock_header_2` (distinct signatures/content), in addition to the existing same-signer check. This ties the poison proof to an actual fork at a specific point in a specific stream rather than merely "same key, any two headers."

### Proof of Concept
Rust integration test plan (stackslib/src/chainstate/stacks/db/transactions.rs test module):
1. Set up chainstate with a miner key `block_privk`/`microblock_privk`, and insert `microblock_pubkey_hash` at height 1 for tenure A via `insert_microblock_pubkey_hash`.
2. Build a genuine microblock stream for tenure A (`prev_block = tenure_A_anchor_hash`, `sequence = 3`), signed with `microblock_privk`. This is `mblock_header_1`.
3. Insert the SAME `microblock_pubkey_hash` again at a later height (simulating reuse in tenure B), and build a genuine, non-conflicting microblock stream for tenure B (`prev_block = tenure_B_anchor_hash`, `sequence = 3`), signed with the SAME `microblock_privk`. This is `mblock_header_2` (fabricated as "poison" only in the sense of being repurposed, but it is a real, honestly-produced header from tenure B).
4. Construct `TransactionPayload::PoisonMicroblock(mblock_header_1, mblock_header_2)` from a third-party reporter and call `StacksChainState::process_transaction`.
5. Assert (equality check): `mblock_header_1.prev_block != mblock_header_2.prev_block` (they are genuinely from different tenures, i.e. no real fork occurred) AND the current code returns `Ok(..)` with a poison report inserted — demonstrating `poison_reward_paid` is wrongly asserted even though `genuine_previously_broadcast_double_sign` is `false`. After applying the recommended fix (comparing `prev_block`/`sequence`/header distinctness), the same call must return `Err(Error::InvalidStacksTransaction(..))`.
