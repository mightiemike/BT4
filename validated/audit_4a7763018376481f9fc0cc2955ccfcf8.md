### Title
Wallet Contract pays the relayer fee refund before the async registrar target-address check resolves, allowing a replayed RLP transaction to double-collect the fee - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (`near-wallet-contract`), which is deployed as a global contract backing ETH-implicit accounts and executed via `rlp_execute` from any relayer/RPC caller, fires the relayer's fee-refund `Promise` unconditionally at RLP-parse time, while deliberately deferring the nonce bump for the one transaction kind that requires an async registrar lookup. This mirrors the Sushi finding's root cause: a value payout is triggered from a computation that is not gated on (or synchronized with) the state update (the nonce/"checkpoint") that is supposed to prevent the same value from being claimed again.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-411`) processes an incoming RLP-encoded Ethereum transaction that a relayer submits on behalf of a user's ETH-implicit account:

1. It parses the RLP tx into a Near `action` and a `transaction_kind` via `internal::parse_rlp_tx_to_action` (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:43-77`), which also computes a `tx_fee` meant as a "refund" payment to the relayer.
2. Nonce handling (`lib.rs:349-365`): for every transaction kind **except** `EthEmulation(EOABaseTokenTransfer { address_check: Some(_), .. })`, the nonce is bumped immediately. For that one case, the nonce bump is explicitly deferred, per the code comment, "because we still do not know if the transaction has a relayer error or not" — i.e. the target address still needs to be resolved asynchronously through the address registrar contract.
3. Immediately after that nonce-handling branch, and independent of whether the nonce was bumped or deferred, the code checks the transaction kind again (`lib.rs:367-385`) and — for `EOABaseTokenTransfer{fee,..}` / `ERC20Transfer{fee,..}` with non-zero `fee` — creates a `Promise` that transfers `fee` from the wallet account to `predecessor_account_id` (the relayer), **before** the inner action/registrar resolution promise has even been dispatched or resolved.

This means for the `address_check: Some(_)` case, the relayer fee-refund promise executes even though: (a) the nonce is not yet consumed, and (b) it is not yet known whether the target-address resolution (registrar lookup) will validate the transaction. The code's own inline comment acknowledges the risk is bounded only by the assumption that "only one transaction is allowed to be in-flight at a time" (`self.has_in_flight_tx`, see `lib.rs:319-327`, `ban_relayer`), which guards concurrent execution within a single call, not sequential re-submission of the same identically-signed, non-nonce-consumed RLP transaction across separate `rlp_execute` calls.

This is directly analogous to the Sushi Trident bug: `collect()` pays out yield computed from `rangeFeeGrowth()` without updating the checkpoint that `burn()` also reads, so calling `collect()` before `burn()` double-pays. Here, the wallet contract pays the relayer's fee from a value computed at parse time without gating it on (or synchronizing it with) the nonce checkpoint that is supposed to make the transaction single-use, for exactly the one code path where the nonce bump is intentionally deferred.

### Impact Explanation
If the same signed RLP transaction (whose target requires registrar resolution, i.e. `address_check: Some(_)`) can be resubmitted to `rlp_execute` more than once before the nonce is eventually consumed, each resubmission fires a new `fee` transfer promise to whichever account is the caller/relayer of that specific call. This drains the ETH-implicit wallet account's NEAR balance by `fee` per replay — unauthorized value movement out of the user's account to a party (or colluding parties acting as "relayer") that did not do proportionally more work, and can be repeated as long as the nonce remains unconsumed.

### Likelihood Explanation
Reachability is straightforward: any account can call `rlp_execute` on an ETH-implicit account with an RLP-encoded transaction (no privileged role required), since the wallet contract is invoked as ordinary contract code by a `FunctionCall` action from any predecessor. The likelihood that this is actually exploitable end-to-end depends on:
- Whether the registrar-callback path (not visible in the excerpts I was able to inspect) increments the nonce or otherwise invalidates the parsed transaction before a second identical `rlp_execute` call can be admitted while `has_in_flight_tx` is false again.
- Exact semantics of `has_in_flight_tx`/`ban_relayer` reset between separate top-level calls.

I was not able to fully trace the registrar-callback resolution code or confirm whether a second submission of the exact same un-consumed-nonce transaction is actually accepted by `validate_tx_relayer_data` (`internal.rs:318-368`, which re-checks `nonce != expected_nonce`) after the first attempt's fee has already been paid. This uncertainty means the finding should be treated as a **plausible but not fully confirmed** double-payment path; a full audit of the registrar-resolution promise callback and of `has_in_flight_tx` reset timing (both outside what I could inspect from the indexed excerpts) is required to confirm exploitability.

### Recommendation
Do not dispatch the relayer fee-refund `Promise` until after the underlying action (including any async registrar-based target resolution) has been confirmed to succeed and the nonce has been durably consumed. If the nonce bump must be deferred for the `address_check: Some(_)` case, defer the fee-refund promise identically, and pay it only from the callback that finalizes the nonce, so the same signed transaction cannot yield the fee more than once regardless of how many times it is resubmitted.

### Proof of Concept
Cannot provide a concrete, runnable PoC from static analysis alone: exercising this path requires driving `inner_rlp_execute` through the `EOABaseTokenTransfer{ address_check: Some(_) }` branch and the address-registrar callback in a live/sandbox NEAR environment, and confirming whether a second `rlp_execute` call with the same nonce is admitted before the callback resolves. This would need to be validated with an actual Devin/test-loop session against `runtime/near-wallet-contract/implementation/wallet-contract` (e.g. extending the existing `test_caller_refunds` / `test_base_token_transfer_with_relayer_refund` tests in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/`) rather than asserted here as proven. fn inner_rlp_execute(
    current_account_id: AccountId,
    predecessor_account_id: AccountId,
    target: AccountId,
    tx_bytes_b64: String,
    nonce: &mut u64,
) -> Result<Promise, Error> {
    if *nonce == u64::MAX {
        return Err(Error::AccountNonceExhausted);
    }
    let context = ExecutionContext::new(
        current_account_id.clone(),
        predecessor_account_id,
        env::attached_deposit(),
    )?;
    let caller_deposit = CallerDeposit::new(&context);

    let parsing_result = internal::parse_rlp_tx_to_action(&tx_bytes_b64, &target, &context, *nonce);
    let (action, transaction_kind) = match parsing_result {
        Ok((action, transaction_kind)) => {
            // Increment nonce for all cases where the registrar contract is not needed
            // to prevent replay of those transactions. For transactions that go through
            // the registrar we still do not know if the transaction has a relayer error
            // or not, therefore we must delay incrementing the nonce.
            //
            // Note: relayers with access keys cannot use this delay to needlessly spend
            // the users tokens because only one transaction is allowed to be in-flight
            // at a time.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                address_check: Some(_),
                ..
            }) = &transaction_kind
            {
            } else {
                *nonce = nonce.saturating_add(1);
            }

            // If the action is an emulated base token or ERC-20 transfer with a non-zero fee then
            // create a promise to send the refund to the relayer. This allows any relayer
            // to safely serve base token transfers from any wallet without additional
            // on-boarding because the relayer will receive some compensation for sending
            // the transaction. Users should always verify the fee before signing a base token
            // transfer. Relayers should also verify the fee before sending to make sure the
            // user's signed transaction will refund enough to cover the relayer's gas costs.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                fee,
                ..
            })
            | TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) =
                &transaction_kind
            {
                if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
                    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
                    env::promise_batch_action_transfer(refund_promise, *fee);
                }
            }

            (action, transaction_kind)
        }
        Err(err @ Error::User(_)) => {
            // Increment nonce on all user errors to prevent replay.
            *nonce = nonce.saturating_add(1);
            return Err(err);
        }
        Err(err) => {
            // Do not increment nonce on Relayer or AccountId errors.
            // The latter error is an issue in the deployment (so the nonce is meaningless).
            // The former arises from the relayer itself doing something wrong and thus the
            // user's transaction could still be valid and potentially submitted properly by
            // another relayer. To allow this we do not increment the nonce.
            //
            // Note: if a relayer is using an access key for this wallet then that key will
            // still be revoked (in the main logic of `rlp_execute`). This fact together with
            // the condition that there only be one in-flight transaction at a time implies
            // that a relayer cannot maliciously burn a large portion of the user's tokens.
            // If the relayer is not using an access key then they are spending their own
            // resources on the gas and therefore we do not care if the relayer submits
            // the same faulty transaction multiple times.
            return Err(err);
        }
    };

pub fn parse_rlp_tx_to_action(
    tx_bytes_b64: &str,
    target: &AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<(near_action::Action, TransactionKind), Error> {
    let tx_bytes = decode_b64(tx_bytes_b64)?;
    let tx_kind: EthTransactionKind = tx_bytes.as_slice().try_into()?;
    let tx: NormalizedEthTransaction = tx_kind.try_into()?;
    let target_kind = validate_tx_relayer_data(&tx, target, context, expected_nonce)?;

    // Compute the fee based on the user's Ethereum transaction.
    // This is sent as a refund to the relayer in the case of an emulated base token
    // transfer or ERC-20 transfer. The reason for this refund is that it allows a
    // user with $NEAR to use a relayer service from their wallet immediately without
    // additional on-boarding.
    let tx_fee = {
        // Limit the cost by `VALUE_MAX` since we will convert this to a $NEAR amount.
        // The call to `low_u128` is safe because `VALUE_MAX` is the largest accepted value.
        let wei_amount = tx.max_fee_per_gas.saturating_mul(tx.gas_limit).min(VALUE_MAX).low_u128();
        NearToken::from_yoctonear(wei_amount.saturating_mul(MAX_YOCTO_NEAR as u128))
    };

    // The way an honest relayer assigns `target` is as follows:
    // 1. If the Ethereum transaction payload represents a Near action then use the receiver_id,
    // 2. If the payload looks like a supported Ethereum emulation then use the address registrar:
    // 2.a. if the tx.to address is registered then use the associated account id,
    // 2.b. otherwise, tx.to == target
    // 3. Otherwise, tx.to == target
    // Given this algorithm, the only way to have `TargetKind::EthImplicit` is in the
    // following cases:
    // I)   The Ethereum transaction payload is not parseable as a known action,
    // II)  The payload is parsable as a Near action and the receiver_id is an eth-implicit account
    // III) The payload is parsable as a supported Ethereum emulation but the to address is
    //      not registered in the address registrar.

/// Validates the transaction is following the Wallet Contract protocol.
/// This includes checks for:
/// - from address matches current account address
/// - to address is present and matches the target address (or hash of target account ID)
/// - nonce matches expected nonce
/// If this validation fails then the relayer that sent it is faulty and should be banned.
fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
        return Err(Error::Relayer(RelayerError::InvalidChainId));
    }

    let to = tx.to.ok_or(Error::User(UserError::EvmDeployDisallowed))?.raw();

    let target_kind = parse_target(target, context.current_address);

    // valid targets satisfy `to == target` or `to == hash(target)`
    let is_valid_target = match target_kind {
        TargetKind::CurrentAccount if to == context.current_address => {
            target == &context.current_account_id
        }
        TargetKind::EthImplicit(address) if to == address => {
            target.as_str()
                == format!("0x{}{}", hex::encode(address), context.current_account_suffix())
        }
        _ => to == account_id_to_address(target),
    };

    if !is_valid_target {
        return Err(Error::Relayer(RelayerError::InvalidTarget));
    }

    let nonce = if tx.nonce <= U64_MAX {
        tx.nonce.low_u64()
    } else {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    };
    if nonce != expected_nonce {
        return Err(Error::Relayer(RelayerError::InvalidNonce));
    }

    // Relayers must attach at least as much gas as the user requested.
    let gas_limit = if tx.gas_limit < U64_MAX { tx.gas_limit.as_u64() } else { u64::MAX };
    if env::prepaid_gas().as_gas() < gas_limit.saturating_mul(GAS_MULTIPLIER) {
        return Err(Error::Relayer(RelayerError::InsufficientGas));
    }

    Ok(target_kind)
}
