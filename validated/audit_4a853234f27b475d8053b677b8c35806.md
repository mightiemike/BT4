### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting replay/restore accept a divergent state root as valid - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by chunk-executor/replay-verify tooling to check that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` that came with a proof (from an archive node or backup). It verifies `status`, `gas_used`, the write-set hash (`state_change_hash`), and the event root hash, but it explicitly does **not** verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that commit the JMT/state-checkpoint root to the transaction-accumulator leaf. This gap is called out by the code itself in a `TODO(trading-native)` comment. [1](#0-0) 

### Finding Description
`TransactionInfo` commits to two independent things: the write-set/event content (via `state_change_hash` / `event_root_hash`) and the resulting global state root (via `state_checkpoint_hash`, and on TransactionInfoV1, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`). [2](#0-1) [3](#0-2) 

`ensure_match_transaction_info` is the local-vs-authenticated equality check used after re-executing a transaction while replaying against an authenticated `TransactionInfo` (obtained together with an accumulator proof, e.g. from an archive/backup). It asserts equality of status, gas, write-set hash and event root hash, but the state-checkpoint-related hashes are never compared — the function returns `Ok(())` even when those fields mismatch: [4](#0-3) 

This function is invoked by the replay-verify utilities (`storage/db-tool/src/replay_on_archive.rs`), the debugger (`aptos-move/aptos-debugger/src/aptos_debugger.rs`) and the CLI (`aptos-move/cli/src/commands.rs`) as the pass/fail gate for whether a locally computed transaction output "matches" an authenticated on-chain `TransactionInfo`. Because it omits the checkpoint-hash comparison, any of these tools can report a **successful** replay/verify for a transaction whose actual committed state root (Sparse-Merkle/JMT root, or under `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, the hot-state/position-state roots) diverges from the locally executed result, as long as the write-set bytes and events happen to hash the same. Since the comment ties this specifically to `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (a feature referenced in `storage/aptosdb/src/db/aptosdb_writer.rs` / `aptosdb_reader.rs` and `types/src/on_chain_config/aptos_features.rs`), enabling that feature adds new checkpoint-root fields whose correctness this verification path silently ignores.

### Impact Explanation
This breaks the state-commitment/proof-integrity invariant that "committed state that differs from the correct VM result" must be detectable. A node (or auditor) using replay-verify tooling to confirm that an archived/backed-up ledger segment is authentic and correctly executed can be given a false "match" even though the state-checkpoint root diverges from what local execution actually produced — i.e., a wrong state root can be accepted as valid by the tooling that is supposed to catch exactly this class of divergence. This directly matches the required "hard-fork-only divergence during commit, replay, restore, or proof verification" and "wrong ... state proof accepted as valid" impact classes, since state-checkpoint hashes are part of what is chained into the transaction accumulator and ultimately the `LedgerInfo` that validators sign.

### Likelihood Explanation
The gap is unconditional in the code path (no feature-flag guard exists in `ensure_match_transaction_info` itself) and is reachable any time replay-verify/debugger/CLI tooling is used to validate historical transactions against an archive, which is a routine operational and security-auditing workflow (e.g., verifying backups or detecting divergence after a state-root related bug). The author's own TODO comment confirms the omission is known but not yet remediated, indicating this is a live, unresolved gap rather than a theoretical one.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash` (and, when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) between the locally computed output and the authenticated `TransactionInfo`, mirroring how `state_change_hash`/`event_root_hash` are already checked, before enabling reliance on this tooling for the trading-native state-root feature.

### Proof of Concept
Conceptual PoC (tooling-level, not consensus-level):
1. Run replay-verify (`storage/db-tool/src/replay_on_archive.rs`) or the debugger against an archive segment where the write-set bytes/events are byte-identical to what local re-execution produces (so `state_change_hash`/`event_root_hash` match), but the state-checkpoint root embedded in the authenticated `TransactionInfo` differs from what local execution's Sparse-Merkle/JMT computation would produce (e.g., because of a state-checkpoint construction bug, downstream of the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` path).
2. `ensure_match_transaction_info` returns `Ok(())` because it never compares `state_checkpoint_hash` fields.
3. The tool reports a successful/matching replay even though the actual committed state root diverged from the correct VM result.

**Caveat / uncertainty:** I was not able to fully trace, within the available search budget, whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently enabled on mainnet or is still gated behind a disabled feature flag, nor whether other independent checks elsewhere in the replay pipeline (outside `ensure_match_transaction_info`) might separately validate these checkpoint hashes and thus mitigate the practical exploitability of this specific gap. This should be confirmed with a full-repository session before treating the impact as unconditionally exploitable on mainnet.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
