### Title
Unbounded delegation-index growth enables RPC/HTTP query DoS via `DelegatedResourceAccountIndexStore` - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
The reported bug class is a static, unenforced-at-scale cap (`MAX_DELEGATES`) that lets an attacker cheaply saturate a per-address delegation list, causing later legitimate delegation/transfer/lock operations to revert (DoS via unbounded per-account list growth). The closest reachable analog in java-tron is the **unbounded, attacker-growable `from`/`to` delegation index lists maintained per address in `DelegatedResourceAccountIndexStore`**, which are read in full (with a RocksDB prefix scan + in-memory sort) on every call to the anonymous, RPC/HTTP-exposed `getDelegatedResourceAccountIndex` / `getDelegatedResourceAccountIndexV2` APIs.

### Finding Description
`DelegateResourceActuator`/`DelegateResourceProcessor` allow any account to delegate BANDWIDTH/ENERGY resources to any other account with a minimum stake of only `1 TRX`: [1](#0-0) 

Each delegation writes two new keyed entries into `DelegatedResourceAccountIndexStore` — one under `V2_FROM_PREFIX+owner+receiver` and one under `V2_TO_PREFIX+receiver+owner` — with no limit on how many distinct `owner` addresses can point at the same `receiver`: [2](#0-1) [3](#0-2) 

There is no analog to `MAX_DELEGATES`: nothing bounds the number of `from`/`to` entries an address can accumulate. When the index for an address is later queried, `getWithPrefix` performs an unbounded `prefixQuery` over all entries under that address's prefix, materializes them into a list, and sorts the entire list by timestamp: [4](#0-3) 

This lookup is reachable anonymously through both gRPC and HTTP without any privileged access: [5](#0-4) [6](#0-5) 

An older test already demonstrates the store accumulating on the order of 100 entries for a single address without any actuator-level limit check: [7](#0-6) 

The core issue mirrors the `VotingEscrow` report's root cause: a broadcastable, low-cost operation (`DelegateResourceContract`, minimum 1 TRX, refundable via lock-period unfreeze/undelegate) repeatedly targeting one victim/receiver address can grow that address's index list without bound, because neither `DelegateResourceActuator.validate()` nor `DelegateResourceProcessor.validate()` impose any cap analogous to `MAX_DELEGATES`.

### Impact Explanation
Unlike the Alchemix bug, this does not block the *write* path (delegation itself never reverts due to list size), so it does not freeze the victim's own tokens/resources. The concrete, reachable impact is a **read-path denial of service**: any anonymous client can call `getDelegatedResourceAccountIndex`/`V2` (gRPC `RpcApiService`, or HTTP `GetDelegatedResourceAccountIndexServlet`/`V2Servlet`) against a Sybil-saturated address, forcing the node to execute an unbounded RocksDB prefix scan and full in-memory sort on every such query. Repeated queries against several saturated addresses can degrade FullNode/SolidityNode/PBFT-node API responsiveness (CPU/memory amplification per request), which is a legitimate DoS-via-RPC-API concern.

### Likelihood Explanation
Medium-low. The attack is Sybil-cost-bound: creating N index entries against a victim requires N distinct funded accounts each staking ≥1 TRX (recoverable later via undelegate/unfreeze, but requiring bandwidth/energy and account creation fees for each Sybil address), unlike the Solidity PoC's 1-Wei-per-delegate cost. This raises the bar compared to the original report, but the absence of any per-address cap (there is no committee-gated "MAX index size" parameter anywhere in `DelegatedResourceAccountIndexStore` or the delegate actuators/processors) means the growth is theoretically unbounded and cumulative across blocks, so a patient/well-funded attacker can still build up a large list over time.

### Recommendation
- Add a maximum number of tracked `from`/`to` delegation-index entries per address (analogous to `MAX_VOTE_NUMBER`), enforced in `DelegateResourceActuator.validate()` / `DelegateResourceProcessor.validate()`, rejecting further `DelegateResourceContract`s once a receiver's index list exceeds the cap.
- Alternatively/additionally, paginate `getWithPrefix` in `DelegatedResourceAccountIndexStore` (limit + offset) instead of returning the entire prefix-scanned, sorted list in one RPC/HTTP response, and enforce a hard iteration/time budget in `prefixQuery` usage for this store.
- Consider decoupling "index enumeration for display" from consensus-critical state so that index growth cannot be weaponized against public query endpoints.

### Proof of Concept
Not independently reproduced against java-tron in this analysis (no execution environment available). The construction path is: (1) fund M distinct new accounts with ≥1 TRX each and freeze balance via `freezeBalanceV2`; (2) from each account, broadcast a `DelegateResourceContract` (via `DelegateResourceActuator`) delegating the minimal allowed 1 TRX of BANDWIDTH/ENERGY to a single victim `receiverAddress`, each call adding a `V2_TO_PREFIX+receiver+owner` entry per `delegateResource()` in `DelegateResourceActuator.java` lines 282-316; (3) call `getDelegatedResourceAccountIndexV2` (gRPC or `GetDelegatedResourceAccountIndexV2Servlet`) against the victim address repeatedly and measure response latency growth as M increases, confirming the unbounded `prefixQuery`+sort cost in `DelegatedResourceAccountIndexStore.getWithPrefix()`.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

package org.tron.core.services.http;

import com.google.protobuf.ByteString;
import java.io.IOException;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;
import org.tron.api.GrpcAPI.BytesMessage;
import org.tron.common.utils.ByteArray;
import org.tron.core.Wallet;
import org.tron.json.JSONObject;
import org.tron.protos.Protocol.DelegatedResourceAccountIndex;


@Component
@Slf4j(topic = "API")
public class GetDelegatedResourceAccountIndexV2Servlet extends RateLimiterServlet {

  private static final  String VALUE_FIELD_NAME = "value";

  @Autowired
  private Wallet wallet;

  protected void doGet(HttpServletRequest request, HttpServletResponse response) {
    try {
      boolean visible = Util.getVisible(request);
      String address = request.getParameter(VALUE_FIELD_NAME);
      if (visible) {
        address = Util.getHexAddress(address);
      }
      fillResponse(ByteString.copyFrom(ByteArray.fromHexString(address)), visible, response);
    } catch (Exception e) {
      Util.processError(e, response);
    }
  }

  protected void doPost(HttpServletRequest request, HttpServletResponse response) {
    try {
      PostParams params = PostParams.getPostParams(request);
      boolean visible = params.isVisible();
      String input = params.getParams();
      if (visible) {
        JSONObject jsonObject = JSONObject.parseObject(input);
        String value = jsonObject.getString(VALUE_FIELD_NAME);
        jsonObject.put(VALUE_FIELD_NAME, Util.getHexAddress(value));
        input = jsonObject.toJSONString();
      }

      BytesMessage.Builder build = BytesMessage.newBuilder();
      JsonFormat.merge(input, build, visible);

      fillResponse(build.getValue(), visible, response);
    } catch (Exception e) {
      Util.processError(e, response);
    }
  }

  private void fillResponse(ByteString address, boolean visible, HttpServletResponse response)
      throws IOException {
    DelegatedResourceAccountIndex reply =
        wallet.getDelegatedResourceAccountIndexV2(address);
    if (reply != null) {
      response.getWriter().println(JsonFormat.printToString(reply, visible));
    } else {
      response.getWriter().println("{}");
    }
  }
}
