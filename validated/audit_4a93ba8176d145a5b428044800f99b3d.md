### Title
Stale per-timestamp index cache is not invalidated by intra-transaction debt socialization, causing mispriced zToken collateral during batched liquidations - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` caches vault liquidity/borrow indexes in the `index-cache` map keyed only by `{ timestamp: stacks-block-time, aid: aid }` [1](#0-0)  so that repeated operations on the same asset within one block reuse a single cached index instead of re-querying the vault. This is the same class of bug as the Hybra Finance `_checkpoint` finding: a value computed once and reused for the rest of the transaction is not re-validated when its underlying source is mutated later in that same transaction by a different code path.

### Finding Description
`accrue-and-cache` populates `index-cache` on first use and returns the cached `{index, lindex}` for every subsequent call with the same `(timestamp, aid)` key in the transaction [1](#0-0) . This cache is meant to reflect the vault's true `index`/`lindex` state as produced by the vault's own `accrue()` function.

However, `liquidate()` in the market contract can trigger bad-debt socialization on a vault directly through a fold over `socialize-debt-asset`, which calls the vault's `socialize-debt` entry point when a liquidation leaves the borrower with unrecoverable debt [2](#0-1) . On the vault side, `socialize-debt` directly overwrites `lindex` (`var-set lindex new-lindex`) and reduces `principal-scaled`/`assets`, i.e. it mutates the vault's liquidity index outside of the normal `accrue()`/`next-liquidity-index` timestamp-delta path [3](#0-2) . Crucially, this mutation happens on the vault contract and is never written back into the market's `index-cache` map — the cache entry for that `(timestamp, aid)` pair, if already populated earlier in the same transaction, is left holding the pre-socialization `lindex`.

`liquidate-multi` executes several liquidations atomically in a single transaction via `(map call-liquidate positions)` [4](#0-3) . If an earlier position in the batch shares a collateral zToken whose underlying vault gets its `lindex` cached (e.g., through `accrue-and-cache`/`accrue-user-collateral` while evaluating that position's health) and that same liquidation also triggers `socialize-debt` on that vault (haircutting `lindex`), then a later position in the same batch that holds zTokens backed by the same vault will have its collateral value evaluated using the market's stale cached `lindex` instead of the freshly-haircut one, because `get-cached-indexes`/`accrue-and-cache` returns the cache hit rather than re-querying the vault [1](#0-0) .

### Impact Explanation
Because zToken collateral value scales with the vault's liquidity index (documented in `docs/vaults.md` as "Redemption value = shares × lindex"), using the stale, pre-haircut index overstates the USD value of zToken collateral for later positions processed in the same `liquidate-multi` transaction. This causes the liquidator to seize more collateral than the actual (post-haircut) value warrants, or lets an unhealthy position appear healthy and skip liquidation — either outcome is a direct mispricing of collateral during an active liquidation event, i.e., theft of, or improper freezing/loss of, borrower/lender funds tied to that vault.

### Likelihood Explanation
This requires: (1) a `liquidate-multi` call containing at least two positions, (2) the first liquidated position causing bad-debt socialization on a vault (an event that already occurs in production during undercollateralized liquidations), and (3) a later position in the same batch holding zToken collateral backed by that same vault. All three conditions are reachable by any liquidator constructing the batch themselves, so no privileged access or DAO compromise is needed — only the natural sequencing of a `liquidate-multi` call and the (attacker-controllable) order of positions within it.

### Recommendation
Invalidate or refresh the market's `index-cache` entry for an asset whenever `socialize-debt` is invoked on the corresponding vault within the same transaction — e.g., have `socialize-debt-asset`/the liquidation fold explicitly `map-set` (or `map-delete`) the `index-cache` entry for the affected `aid` with the vault's post-socialization `lindex`, or have subsequent `accrue-and-cache` calls always re-query the vault after any socialization event rather than trusting the per-timestamp cache.

### Proof of Concept
Not independently verified end-to-end in this review — I was unable to inspect `socialize-debt-asset`'s exact call path and the price-resolution routine for zTokens deeply enough to confirm every step (in particular the precise place where `lindex` from `index-cache` is consumed for zToken USD valuation). This should be validated with a Clarinet/Clarigen test that: (1) sets up two borrowers with zToken collateral backed by the same vault, (2) liquidates the first borrower via `liquidate-multi` in a way that forces `socialize-debt` (bad debt), and (3) liquidates the second borrower in the same batch call, then asserts whether the second liquidation's collateral valuation used the pre- or post-haircut `lindex`.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
