### Title
Market taker orders can be forced to revert after fee/balance mutation via attacker-controlled `MAX_MATCH_NUM` order-book flooding - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.execute()` deducts the market-sell fee and the sell-token amount from the taker's account, persists the new order to `marketAccountStore`/`orderStore`, and only afterwards calls `matchOrder()`, which can throw a `ContractValidateException` if more than `MAX_MATCH_NUM` (20) maker orders are consumed at the best price. This exception is caught and re-thrown as `ContractExeException`, which causes the whole transaction (including the already-mutated fee/balance/order state) to be rolled back at the block-processing level, exactly mirroring the reported bug class: a legitimate operation that already paid/deducted a fee is reverted because of an unrelated global-state condition (here, the number of resting maker orders at the best price, which is influenced by other market participants, not the taker).

### Finding Description
In `execute()`, the fee is subtracted and burned/transferred, the sell-side balance/asset is moved, and the taker order plus `MarketAccountOrderCapsule` bookkeeping are written to the store before matching begins: [1](#0-0) 

`createAndSaveOrder()` immediately persists the new order and account-order bookkeeping via `marketAccountStore.put(...)` / `orderStore.put(...)`, independent of whether the subsequent match step succeeds: [2](#0-1) 

`matchOrder()` then walks the maker order book at the best price and throws once more than `MAX_MATCH_NUM` maker orders are consumed in a single taker transaction: [3](#0-2) 

This `ContractValidateException` is caught by the outer `execute()` handler, which marks the result `FAILED` and re-throws `ContractExeException`: [4](#0-3) 

At the block/transaction-processing layer, `Manager.pushTransaction()` wraps `processTransaction()` in a revoking-store session that is only merged (persisted) if no exception propagates out; any thrown `ContractExeException`/`ContractValidateException` means `tmpSession.merge()` never runs and all state changes made during `execute()` — including the fee deduction, balance/asset transfer, and order/`MarketAccountOrderCapsule` writes — are discarded: [5](#0-4) 

The existing unit test `exceedMaxMatchNumLimit` demonstrates this exact scenario: a taker order that would need to match more than `MAX_MATCH_NUM` maker orders causes `execute()` to throw `ContractExeException`, confirming the revert path is reachable through ordinary usage of the actuator, not just theoretically: [6](#0-5) 

Because `MAX_MATCH_NUM` is a fixed constant (20) unrelated to the taker's own balance, quantity, or fee correctness, and the number of maker orders resting at the best price is controlled by other, unprivileged market participants, an attacker can deliberately populate the order book with many small maker orders at the current best price so that any subsequent legitimate taker sell order that would need to sweep across those makers is forced to revert — mirroring the report's core issue of a valid fee-deducting operation being reverted due to unrelated global state.

### Impact Explanation
This allows an unprivileged attacker to grief legitimate market participants: by seeding `MAX_MATCH_NUM + 1` (21+) small maker orders at the best price for a given pair, any taker attempting a sell that would sweep through that liquidity is guaranteed to hit the `ContractValidateException`/`ContractExeException` path and have their transaction (fee deduction, order placement, and any partial matches already computed in memory) discarded. This is a denial-of-service against the market/exchange functionality — a specific, valid market order execution path can be reliably blocked by a third party manipulating shared (global-to-the-pair) order-book state, which is the same root cause class as the report (a check on unrelated aggregate/global state causing revert of an otherwise valid fee-bearing operation).

### Likelihood Explanation
Likelihood is Low-to-Medium: placing 21 small maker orders on a token pair to poison a specific price level requires minimal capital (`MAX_ACTIVE_ORDER_NUM` per account is 100, so even a single attacker account suffices) and no privileged role, and `supportAllowMarketTransaction()` must be enabled by the committee for the market feature to be active at all. The existing test suite already shows this is an easily triggerable condition once the market feature is on.

### Recommendation
Avoid letting a match-count/global limit check that is unrelated to the taker's own validated inputs cause a full transaction revert after fee and balance state has already been mutated. Options: perform the `MAX_MATCH_NUM` check (or an equivalent liquidity-sweep cap) during `validate()` using a read-only simulation before any state mutation in `execute()`, or restructure `matchOrder()` so that exceeding `MAX_MATCH_NUM` results in a partial fill (stopping the match loop and saving the remainder as a resting order) instead of throwing and rolling back the entire transaction.

### Proof of Concept
Reference the existing `exceedMaxMatchNumLimit` test, which already reproduces the exact revert: [6](#0-5) 
1. Attacker creates `MAX_MATCH_NUM + 1` maker sell orders for pair (A, B) at the best available price using `MarketSellAssetActuator`.
2. A legitimate user submits a `MarketSellAssetContract` (taker) sized to sweep across all of these maker orders.
3. `execute()` deducts the taker's fee and sell-token balance, persists the taker order, then `matchOrder()` throws `ContractValidateException("Too many matches...")` once `matchOrderCount > MAX_MATCH_NUM`.
4. `ContractExeException` propagates to `Manager.pushTransaction`, the revoking-store session is never merged, and the taker's entire transaction (fee, balance, order) is rolled back — denying the legitimate user's market order despite it being fully valid and funded.

  private MarketOrderCapsule createAndSaveOrder(AccountCapsule accountCapsule,
      MarketSellAssetContract contract) {
    MarketAccountOrderCapsule marketAccountOrderCapsule = marketAccountStore
        .getUnchecked(contract.getOwnerAddress().toByteArray());
    if (marketAccountOrderCapsule == null) {
      marketAccountOrderCapsule = new MarketAccountOrderCapsule(contract.getOwnerAddress());
    }

    // note: here use total_count
    byte[] orderId = MarketUtils
        .calculateOrderId(contract.getOwnerAddress(), sellTokenID, buyTokenID,
            marketAccountOrderCapsule.getTotalCount());
    MarketOrderCapsule orderCapsule = new MarketOrderCapsule(orderId, contract);

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    orderCapsule.setCreateTime(now);

    marketAccountOrderCapsule.addOrders(orderCapsule.getID());
    marketAccountOrderCapsule.setCount(marketAccountOrderCapsule.getCount() + 1);
    marketAccountOrderCapsule.setTotalCount(marketAccountOrderCapsule.getTotalCount() + 1);
    marketAccountStore.put(accountCapsule.createDbKey(), marketAccountOrderCapsule);
    orderStore.put(orderId, orderCapsule);

    return orderCapsule;

  @Test
  public void exceedMaxMatchNumLimit() throws Exception {

    InitAsset();

    int start = 10;
    int limit = MarketSellAssetActuator.getMAX_MATCH_NUM();
    int step = 1;
    int end = start + step * limit;

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 400L;
    long sellTokenQuant = buyTokenQuant * (end / start + 1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant,
            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    // at least limit+1 times
    for (int i = start; i <= end; i += step) {
      addOrder(buyTokenId, (long) start, sellTokenId, i, OWNER_ADDRESS_SECOND);
    }

    // this order(taker) need to match 21 times
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage =
        "Too many matches. MAX_MATCH_NUM = " + MarketSellAssetActuator.getMAX_MATCH_NUM();
    try {
      TransactionResultCapsule ret = new TransactionResultCapsule();
      actuator.validate();
      actuator.execute(ret);
      fail(errorMessage);
    } catch (ContractExeException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    } catch (Exception e) {
      Assert.assertTrue(false);
    }
  }
