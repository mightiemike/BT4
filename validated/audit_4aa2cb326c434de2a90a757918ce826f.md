### Title
Unchecked subtraction on `accounts_data_len` during index generation can panic or silently corrupt accounts-data-len accounting - ([File: accounts-db/src/accounts_db.rs])

### Summary
During `generate_index()` at startup (from snapshot load / ledger rebuild), `AccountsDb` computes `accounts_data_len` by summing the data length of every non-zero-lamport account across all storages, then subtracts the amount attributable to duplicate pubkey versions (`accounts_data_len_from_duplicates`) to get the correct total. This subtraction is done with a plain `-=` operator instead of `checked_sub`, unlike the parallel `capitalization` computation in the same block, which explicitly uses `checked_sub().expect("capitalization cannot underflow")`.

### Finding Description
In `generate_index()`, the running total `total_accum.accounts_data_len` (accumulated per-slot in `generate_index_for_slot`, [1](#0-0) , incremented at [2](#0-1) ) is reduced by `accounts_data_len_from_duplicates`, which is computed separately by `visit_duplicate_pubkeys_during_startup` for all pubkeys that appear in more than one slot.

The two related quantities are combined asymmetrically: [3](#0-2) 

`capitalization` is subtracted with `checked_sub(...).expect("capitalization cannot underflow")`, guarding against underflow with a controlled panic and a clear message. `accounts_data_len`, however, is decremented with a bare `-=`, which:
- In a debug build, panics with a generic "attempt to subtract with overflow" message (no context, harder to diagnose than the capitalization case).
- In a release build (the build validators actually run, since `overflow-checks` is off by default for release profiles), the subtraction **silently wraps** to a huge `u64` value instead of panicking.

If `accounts_data_len_from_duplicates` were ever computed to be larger than the accumulated `total_accum.accounts_data_len` (e.g., due to any accounting mismatch in how duplicate/zero-lamport accounts are tallied across slots, or a discrepancy between "non-zero-lamport data length included in the running total" vs. what `visit_duplicate_pubkeys_during_startup` treats as "duplicate data length"), the result is either an uncontrolled panic (denial of service at startup — the node cannot come up) or, in release builds, a silently corrupted `accounts_data_len` value that is later used to derive the bank's `accounts_data_len` for `AccountsDataSizeLimit` enforcement, wire-format serialization, and other downstream accounting.

This is directly analogous to the external report's root cause: a quantity used later without checking whether an unchecked upstream modification/derivation could make a subtraction go negative, while a sibling computation right next to it (`performanceFee` bound check that was supposed to exist elsewhere / `capitalization`'s checked_sub here) does perform the safety check.

### Impact Explanation
- If triggered, on a validator/RPC node this happens during `generate_index()`, which is unconditionally run when loading from a snapshot or rebuilding the accounts index at startup. A panic here means the node cannot start until manually recovering (denial of service against the specific node).
- Worse, in release builds the silent wraparound means `accounts_data_len` becomes a bogus, extremely large `u64` without any panic or log signal beyond the printed value, corrupting an accounting invariant that is normally protected everywhere else with `checked_add`/`checked_sub` (as seen for `capitalization` right next to it). This falls into the "silent balance/accounting change" and "node panic" categories called out as in-scope impact classes.

### Likelihood Explanation
This code path executes on every node startup that loads/rebuilds from a snapshot (all validators, RPC nodes), making the surrounding code reachable unconditionally. Whether `accounts_data_len_from_duplicates` can actually exceed the running total in practice depends on invariants maintained elsewhere in duplicate-pubkey bookkeeping that I was not able to fully trace within the available tool budget (specifically the internals of `visit_duplicate_pubkeys_during_startup` and how it reconciles zero-lamport vs. non-zero-lamport duplicate handling across all slots). I could not find a corresponding `checked_sub` guard for this specific field anywhere in `accounts_db.rs`, whereas the analogous `capitalization` computation is explicitly guarded, which is the concrete, verifiable asymmetry that maps to the reported bug class. Because I could not fully verify a concrete transaction sequence that forces `accounts_data_len_from_duplicates > total_accum.accounts_data_len`, likelihood should be treated as uncertain/lower-confidence — the report is best framed as a code-hardening/defensive-check gap rather than a confirmed exploitable path.

### Recommendation
Change:
```rust
total_accum.accounts_data_len -= accounts_data_len_from_duplicates;
```
to:
```rust
total_accum.accounts_data_len = total_accum
    .accounts_data_len
    .checked_sub(accounts_data_len_from_duplicates)
    .expect("accounts_data_len cannot underflow");
```
so that any accounting inconsistency produces the same clear, immediate, controlled panic that the neighboring `capitalization` subtraction already has, rather than silently wrapping in release builds — matching the report's recommendation to add the missing bound/underflow check consistently everywhere the value is used, not just in some call sites.

### Proof of Concept
I was unable to construct a concrete end-to-end account/transaction sequence (using only unprivileged operations) that forces `accounts_data_len_from_duplicates` to exceed `total_accum.accounts_data_len` within the tool budget available, since that would require tracing the full logic of `visit_duplicate_pubkeys_during_startup` and how zero-lamport/duplicate accounts are excluded from the running total across all slots — code I did not have the chance to fully inspect. The finding is therefore reported as a verified code-level asymmetry (unchecked `-=` vs. the neighboring `checked_sub().expect(...)` for `capitalization`) at [4](#0-3) , presented as the closest concrete analog to the reported bug class; further investigation of `visit_duplicate_pubkeys_during_startup` and its interaction with zero-lamport account handling during index generation would be required to confirm a triggering sequence.
