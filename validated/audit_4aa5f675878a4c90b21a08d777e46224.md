### Title
Unbounded linear-scan DoS via `getAssetIssueListByName`/`getAssetIssueByName` over the ever-growing `AssetIssueV2Store` - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getAssetIssueListByName` and the `AllowSameTokenName==1` branch of `Wallet.getAssetIssueByName` call `getAllAssetIssues()` and perform a full linear `stream().filter()` scan over every asset ever issued to answer a single by-name query, with no index by name. Because there is no cap on the total number of assets that can ever be created (the `ASSET_ISSUE_COUNT_LIMIT_MAX=1000` constant only clamps the `limit` parameter of the pagination helper, not the store size), an attacker who repeatedly pays the asset-issuance fee from distinct funded accounts can grow this store indefinitely, making every subsequent name-based RPC query proportionally more expensive.

### Finding Description
`Commons.getAssetIssueStoreFinal` picks `AssetIssueV2Store` when `AllowSameTokenName != 0` [1](#0-0) . `Wallet.getAssetIssueListByName` uses this selector to fetch `getAllAssetIssues()` and then does an unindexed `filter(assetIssueCapsule -> assetIssueCapsule.getName().equals(assetName))` scan over the entire list on every call [2](#0-1) . The `AllowSameTokenName==1` path of `getAssetIssueByName` does the same full-list filter [3](#0-2) . `AssetIssueStore.getAllAssetIssues()` iterates the whole underlying DB (`Streams.stream(iterator())`) [4](#0-3) .

Contrary to the question's premise, `ASSET_ISSUE_COUNT_LIMIT_MAX` does **not** cap the total number of assets that can exist; it is only used inside `getAssetIssuesPaginated` to clamp a caller-supplied `limit` to at most 1000 entries per page [5](#0-4) . There is no enforced ceiling on how many `AssetIssueContract` transactions can be committed over the lifetime of the chain, so store growth (and therefore per-query scan cost) is unbounded over time, not capped at 1000 as the question assumes.

The issuance path (`AssetIssueActuator.execute`) does enforce `accountCapsule.getAssetIssuedName().isEmpty()` in `validate()`, meaning **each account may issue only one asset ever** [6](#0-5) , and each issuance costs `dynamicStore.getAssetIssueFee()` charged as `calcFee()` [7](#0-6) . This means the attacker must fund and issue-once-per a large number of distinct accounts to inflate the store — a real but non-trivial economic cost per entry, not a free spam vector.

### Impact Explanation
This is a valid, if lower-severity, "DoS via RPC-API" issue: unauthenticated `getAssetIssueListByName`/`getAssetIssueByName` RPC/HTTP calls trigger an O(N) full-store scan where N is the total historical asset count, with no index, no cache, and no upper bound on N. As N grows over the life of the chain (attacker- or organically-driven), every query's CPU cost grows linearly, and combined with `BandwidthProcessor.updateUsage` calls per matched capsule inside the filter loop, repeated public queries degrade RPC-API responsiveness for all clients. The impact is scoped to elevated CPU / response latency on public query endpoints, not to consensus, funds, or key material.

### Likelihood Explanation
Preconditions: `AllowSameTokenName` must be `1` (attacker cannot set this themselves; it must already be enabled network-wide, as stated to be default on current mainnet). Given that, the attack is feasible for any unprivileged party, but each additional inflating entry costs one funded account plus the full `AssetIssueFee` (issuance is limited to once per account by the `"An account can only issue one asset"` check), making mass inflation to very large N economically nontrivial rather than free. This differs materially from the question's premise of a 1000-entry ceiling reached via "duplicate-name assets" cheaply — there is no ceiling, but there's also no free/duplicate-name shortcut to bypass the per-account fee. Repeated read-side flooding (`getAssetIssueListByName`) itself is free/cheap for the attacker once the store has been inflated by anyone.

### Recommendation
- Maintain a secondary index (e.g., a name→id map or store) for `AssetIssueV2Store` lookups by name instead of scanning `getAllAssetIssues()` on every query.
- Alternatively/additionally, cap or paginate `getAssetIssueListByName` results and enforce a maximum scan length, and consider rate-limiting name-based query RPCs.
- Clarify/enforce that `ASSET_ISSUE_COUNT_LIMIT_MAX` (or a similar bound) actually limits total store growth if that was the original intent, since currently it only clamps pagination `limit`.

  public AssetIssueList getAssetIssueListByName(ByteString assetName) {
    if (assetName == null || assetName.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),
            chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues();

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getName().equals(assetName))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }
