### Title
Unbounded recursion depth in CASM bytecode segment processing (class hashing, OS bytecode segmentation, and felt-size estimation) triggered by a maliciously structured declared Sierra program - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
The Sierra-to-CASM compilation pipeline runs the actual compiler binary under CPU/memory/time resource limits, but the CASM class-hash computation and later bytecode-segment processing that operate on the compiler's output (`bytecode_segment_lengths`, a `NestedIntList`) are unbounded, unguarded recursive functions with no depth limit, mirroring the PDFBox page-tree class of bug where a "carefully crafted" nested structure drives an extremely long/expensive recursive traversal.

### Finding Description
When a class is declared, `SierraCompiler::compile` first compiles Sierra to CASM inside a resource-limited subprocess, then immediately computes the compiled-class hash in the *unrestricted* calling process: [1](#0-0) . The subprocess compilation step is wrapped with CPU time/memory `ResourceLimits`, [2](#0-1) , but the subsequent hash computation on the returned `CasmContractClass` has no such protection.

That hash computation walks the `bytecode_segment_lengths: NestedIntList` tree recursively with no depth bound: `bytecode_hash_node` recurses once per nesting level of the segment structure, allocating a new stack frame and a `Vec` per call [3](#0-2) . `NestedIntList` is a simple recursive enum (`Leaf(usize)` / `Node(Vec<NestedIntList>)`) with no depth cap enforced anywhere it is constructed or consumed [4](#0-3) .

The same unguarded recursive pattern over `bytecode_segment_lengths` is repeated in code paths that every executing/re-executing node runs:
- Blockifier's felt-size accounting recurses the same structure with only an assertion on depth-vs-1 for the *outer* call sites but general recursion for arbitrary segmentation depth: [5](#0-4) .
- The Starknet OS hint implementation builds a `BytecodeSegmentNode` tree by recursing over the same untrusted structure with no depth limit before generating hints for the prover/re-execution: [6](#0-5) .

`bytecode_segment_lengths` is derived from the compiler's own segmentation of the *attacker-supplied* Sierra program's control-flow (functions/branches). The only limits enforced at declaration time are on flat sizes — `max_bytecode_size` and `max_contract_class_object_size` — not on segmentation nesting depth: [7](#0-6)  and [8](#0-7) . A contract crafted with many nested small functions/branches close to the bytecode size ceiling (~80K felts) can therefore drive the compiler to emit a `NestedIntList` whose nesting depth is on the order of the number of code segments, with none of the recursive consumers above bounding that depth.

This is structurally analogous to the PDFBox CVE: an attacker-controlled, "tree-shaped" artifact (there: PDF page tree; here: `NestedIntList` bytecode-segment tree) is walked by naive unbounded recursion, and the attacker fully controls the shape/depth of that tree within otherwise-accepted size limits.

### Impact Explanation
A single `DECLARE` transaction can force every sequencer/full node that (a) compiles+hashes the class in the gateway/class-manager, (b) executes the class (blockifier felt-size accounting), or (c) re-executes/proves the block (Starknet OS hints) to perform deep unbounded recursion. Depending on stack frame size and platform stack limits, this can manifest as a process-level stack overflow (process crash/abort) or a substantial, unmetered increase in class-hashing/hinting latency outside the metered VM step budget. Because the resource limits (`ResourceLimits`/CPU time) only wrap the external compiler subprocess and not this in-process recursive post-processing, this computation escapes the sequencer's existing DoS mitigations for declare transactions. A crash or stall in this shared code path (used identically by class-hash computation, execution, and OS re-execution) can halt block building/re-execution across nodes, i.e. a network unable to confirm new transactions.

### Likelihood Explanation
Reachable from a single, unprivileged `DECLARE` transaction — no special privileges, operator/proposer/prover role, or network conditions are required. The attacker only needs to craft a Sierra program (many small functions/deeply nested branches) that passes existing libfunc/version/size validation while maximizing segmentation nesting depth, which is a data-shaping exercise well within reach of any contract declarer.

### Recommendation
- Impose an explicit maximum nesting depth (or convert the recursive walk to an iterative, explicit-stack algorithm) for `NestedIntList`/`BytecodeSegmentNode` processing in `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs`), `NestedFeltCounts::new_inner` (`crates/blockifier/src/execution/contract_class.rs`), and `create_bytecode_segment_structure_inner` (`crates/starknet_os/src/hints/hint_implementation/compiled_class/utils.rs`).
- Reject/limit segmentation depth as part of class validation before it's used in hashing/execution paths, similar to how `max_bytecode_size` and `max_contract_class_object_size` are enforced today.
- Ensure the class-hash computation step in `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs`) is also covered by resource limiting (or bounded iteratively), not just the compiler subprocess invocation.

### Proof of Concept
1. Author a Cairo1 contract with a large number of small, deeply/sequentially nested functions/branches such that the Sierra→CASM compiler emits a maximally nested `bytecode_segment_lengths` (`NestedIntList::Node(vec![NestedIntList::Node(vec![...])])`) while staying under `max_bytecode_size`/`max_contract_class_object_size`.
2. Submit this class via a `DECLARE` transaction to the gateway.
3. Observe `SierraCompiler::compile` (`crates/apollo_compile_to_casm/src/lib.rs:60-74`) invoking `executable_class.hash(&HashVersion::V2)`, which recurses through `bytecode_hash_node` (`crates/starknet_api/src/contract_class/compiled_class_hash.rs:111-132`) to a depth proportional to the crafted segmentation, outside of any subprocess resource limit — measure abnormal CPU time/stack growth compared to a flat/shallow-segmented contract of the same bytecode size.

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
}
