### Title
Missing declared-class validation in Starknet OS `execute_replace_class` causes divergence from Blockifier execution - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The Starknet OS's Cairo implementation of the `replace_class` syscall (both the Cairo0 path in `deprecated_execute_syscalls.cairo` and the Cairo1 path in `syscall_impls.cairo`) unconditionally writes the caller-supplied `class_hash` into the contract's state entry, with no check that the class hash corresponds to a declared class. The Rust `blockifier` execution layer, which actually decides the canonical state during block building, does perform this check and rejects the call when the class is undeclared. This mirrors the `removeWrapping` bug class: a state-mutating operation is permitted in one code path without validating an invariant (that the referenced entity — wrapped token / declared class — actually exists/is still valid), while a parallel path enforces the invariant, producing divergent, unusable, or unrecoverable state.

### Finding Description
Any account contract can invoke the `replace_class` syscall with an arbitrary felt as `class_hash`. In the Rust execution path used by the sequencer to build blocks, `syscall_base.rs`'s `replace_class` explicitly calls `self.state.get_compiled_class(class_hash)?` before updating the contract's class hash, and the test suite documents that using an undeclared class hash produces an `"is not declared"` error and the transaction reverts: [1](#0-0) [2](#0-1) [3](#0-2) 

In contrast, the Starknet OS Cairo implementation of the same syscall performs the state update unconditionally, with an explicit TODO acknowledging the missing check: [4](#0-3) 

The equivalent deprecated (Cairo0) syscall path in the OS has the same unconditioned behavior: [5](#0-4) 

A grep across all `.cairo` files in the repository confirms there is no `"is not declared"` / undeclared-class check anywhere in the OS execution code, so no other layer of the OS compensates for this gap.

### Impact Explanation
The Starknet OS re-executes each block's transactions to independently reconstruct the state diff/root that the sequencer's blockifier computed, and this reconstruction must match exactly for the block to be provable and for honest nodes to agree on state. Because the OS does not validate that `class_hash` in `replace_class` is declared, while the blockifier does:
- A transaction that reverts under blockifier (because the class is undeclared) would instead succeed under the OS's re-execution, applying an invalid class hash to the contract's state entry.
- This produces a state root/computed state diff mismatch between the sequencer's committed block and the OS's re-execution, i.e., honest-node divergence and inability to produce a valid proof for the block — a form of the network being unable to confirm new transactions/blocks.
- Additionally, even if this specific case isn't hit within the same transaction, a contract whose class hash is permanently set to an undeclared value becomes stuck: any future call into it requires the OS to load the corresponding compiled class facts, which do not exist for an undeclared hash, permanently bricking that contract within the OS's ability to reprocess it (analogous to the original bug's "unwrapping permanently failing").

### Likelihood Explanation
Reaching this path requires only a single unprivileged transaction from any account contract invoking the `replace_class` syscall with an arbitrary (undeclared) class hash — no special privileges, timing, or node compromise needed. This is a directly reachable Cairo0/Cairo1 contract syscall available to any deployed contract.

### Recommendation
Add the same "declared class" validation to the OS's `execute_replace_class` (both `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo`) that exists in the blockifier: verify that a compiled-class fact exists for `class_hash` (mirroring `get_compiled_class`/`is_declared` checks) before writing the new `StateEntry`, and fail/abort the syscall execution (consistent with blockifier's revert-with-error behavior) if it is not declared. This resolves the outstanding `TODO(Yoni, 1/1/2026)` and removes the divergence between blockifier and OS execution.

### Proof of Concept
1. Deploy any Cairo1 (or Cairo0) contract exposing a function that calls the `replace_class` syscall with a user-supplied class hash (e.g., the existing `test_replace_class` test entry point used in `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs`).
2. Submit an invoke transaction calling this entry point with an undeclared class hash (e.g., `felt!(1234_u16)`), as done in the `undeclared_class_hash` test: [6](#0-5) 
3. Observe that the blockifier-based sequencer execution reverts this transaction with `"is not declared"`.
4. Feed the same transaction/block into the Starknet OS re-execution path (`execute_replace_class` in `syscall_impls.cairo` / `deprecated_execute_syscalls.cairo`); because no declared-class check exists there, the OS applies the state update and computes a state diff/root that differs from the blockifier's (reverted) result, producing a state commitment mismatch.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())

        // Not enough gas to execute the syscall.
        return ();
