### Title
Unmetered native-crypto CPU exhaustion via reusable Sapling proofs in `ShieldedTransferActuator.validate()` cheap-check-first / expensive-checkProof-last ordering - (File: `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
`ShieldedTransferActuator.validate()` runs all cheap structural/arithmetic checks (`checkSender`, `checkReceiver`, `validateTransparent`, duplicate-nullifier check, `merkleRootExist(anchor)`) before invoking `checkProof()`, which performs full native Groth16 verification (`librustzcashSaplingCheckSpend`/`CheckOutput`) and only then the RedJubjub `librustzcashSaplingFinalCheck`. Because the Sapling zk-proof and output proof are independent of the per-transaction sighash, an attacker who owns one legitimately-included shielded note can reuse the exact same `SpendDescription`/`ReceiveDescription` proof bytes across unlimited distinct transactions, cheaply recomputing only the spend-authority signature per transaction, and deliberately supply a bad `bindingSignature` to fail only at the very last, most expensive step — forcing the node to redo the full pairing-based verification for every broadcast while the sender pays no committed fee (validation failures are rolled back before any bandwidth/fee is merged).

### Finding Description
`validate()` order is:
1. `checkSender` / `checkReceiver` / `validateTransparent` — cheap field/length/balance checks [1](#0-0) 
2. duplicate nullifier + `merkleRootExist(anchor)` + spent-nullifier lookup, scoped to nullifiers *within this transaction only* (a fresh `HashSet` per call) [2](#0-1) 
3. Only after all of the above pass, `checkProof()` runs the expensive native SNARK/pairing checks in order `CheckSpend` → `CheckOutput` → arithmetic balance → `FinalCheck` (binding signature) [3](#0-2) 

Critically:
- `CheckSpendParams` includes the transaction `signHash`, so the RedJubjub `spendAuthoritySignature` is tx-specific, but this is a cheap EC signature that the attacker can recompute for free using their own self-generated spending key (no third-party spend authority needed) [4](#0-3) .
- `CheckOutputParams` does **not** depend on `signHash` at all (`ctx`, `cv`, `cm`, `epk`, `zkproof` only), so a single generated output proof can be replayed verbatim, unmodified, across an unlimited number of different transactions [5](#0-4) .
- The duplicate-nullifier check only guards against duplicates *inside the same transaction*; the global anti-double-spend guard (`nullifierStore.has(...)`) is only populated on committed/executed spends, so a nullifier belonging to a transaction that is always crafted to fail at `FinalCheck` is never marked spent and can be resubmitted indefinitely with a fresh anchor/nullifier reuse [2](#0-1) .
- Because the whole `processTransaction` runs inside a revoking `ISession` that is only merged on success, any bandwidth/fee side effects of a validation-failing transaction are rolled back, and pending-shielded-tx counters are only incremented on success — so nothing meters or throttles these deliberately-failing transactions on a per-broadcast basis [6](#0-5) .
- A fully shielded-from-shielded-note transaction requires zero conventional ECDSA signatures (`validateSignature` short-circuits for shielded senders), so the normal signature-verification-based spam cost that gates most other TRON transaction types does not apply here [7](#0-6) .

Exploit flow: the attacker performs one legitimate public-to-shielded deposit (paying a real, one-time fee) to obtain a note actually included in the Sapling commitment tree, and obtains one valid `SpendDescription` zk-proof and one valid `ReceiveDescription` zk-proof for that note. They then broadcast many `ShieldedTransferContract` transactions, keeping the `SpendDescription`/`ReceiveDescription` proof bytes fixed, varying only cheap fields (e.g., `expiration`, `ref_block`) to get a fresh `signHash`/txid, recomputing the trivial `spendAuthoritySignature`, and always supplying an intentionally-wrong `bindingSignature`. Each such transaction sails through all cheap checks, forces the node through full `CheckSpend`+`CheckOutput` Groth16 pairing verification, and only then fails at `librustzcashSaplingFinalCheck` — exactly the scenario in the question, confirmed by existing tests exercising this exact failure mode (`"librustzcashSaplingFinalCheck error"`) [8](#0-7) .

### Impact Explanation
This is a mempool-wide validation-time CPU exhaustion DoS (DoS via the TRON protocol implementation): each rejected transaction costs the attacker only a cheap EC signature and negligible bandwidth, while the victim node must perform full native elliptic-curve pairing verification (`CheckSpend` + `CheckOutput`) before rejection, and no fee is ever collected because the failure occurs during `validate()` prior to `execute()`/fee commitment, and the enclosing revoking session discards any partial bandwidth charge on failure. At scale (mass broadcast of such "almost valid" transactions, replaying the same reusable proof material), this can materially degrade or stall transaction processing throughput on full nodes/witnesses that must validate every broadcast transaction.

### Likelihood Explanation
Preconditions are modest and attacker-controlled: shielded transactions must be enabled on the chain (a standard, long-enabled protocol feature, not a privileged/non-default configuration), and the attacker needs one initial legitimate shielded deposit to obtain a real, tree-included note (a normal funded-account action). After that one-time setup, the attack is trivially repeatable and cheap per iteration (reuse of proof bytes + recompute of a lightweight signature + broadcast), and there is no code path found that specifically throttles repeated, always-failing shielded transactions from the same reused nullifier/anchor before they reach the expensive `checkProof` stage.

### Recommendation
Reorder/harden `checkProof()`/`validate()` so the cheapest-to-verify, most attack-relevant component of the proof set is checked first, or add per-signHash/per-anchor rate limiting for shielded transactions that reuse the same nullifier or proof material across distinct, rapidly-broadcast transactions. Concretely: (1) verify `librustzcashSaplingFinalCheck` (binding signature) before running `CheckSpend`/`CheckOutput` where the protocol allows reordering, since binding-signature verification is comparatively cheap and would reject a large class of "almost valid" spam earlier; (2) track/limit the rate of distinct transactions referencing the same nullifier or note per time window regardless of ultimate success/failure, independent of the `shieldedTransInPendingCounts` success-only counter; (3) require a minimal bandwidth/energy charge to be committed (not fully rolled back) for transactions that reach the actuator's expensive validation stage, so repeated cheap-fail-late submissions are metered.
