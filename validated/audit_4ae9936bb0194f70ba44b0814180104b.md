### Title
Unchecked `reduceAssetAmountV2` return value in `MarketSellAssetActuator.transferBalanceOrToken()` can allow order creation without actual token deduction - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
The external report describes a compound-protocol `redeem` function that fails to verify the caller actually holds enough tokens before debiting them, recommending an explicit `require(amount <= balance)` guard. The java-tron analog is `MarketSellAssetActuator.transferBalanceOrToken()`, which reduces a seller's TRC10 asset balance by calling `AccountCapsule.reduceAssetAmountV2(...)` but never checks the boolean it returns, unlike the sibling actuators that perform the exact same operation.

### Finding Description
`MarketSellAssetActuator.execute()` calls `transferBalanceOrToken(accountCapsule)` to debit the seller's token before creating and matching the market order: [1](#0-0) 

`reduceAssetAmountV2` returns `false` (without throwing) whenever the requested amount is not `<= currentAmount` or the asset entry is absent: [2](#0-1) 

`MarketSellAssetActuator` ignores this return value entirely, so if the deduction silently fails, the actuator proceeds anyway: it creates and persists the order (`createAndSaveOrder`), potentially matches it against existing maker orders and credits the counter-party/buy-side token via `addTrxOrToken`, all without the seller ever having paid the `sellTokenQuantity`.

This is inconsistent with how the codebase normally treats this exact primitive. Both `TransferAssetActuator` and the shared helper `Commons.adjustAssetBalanceV2` explicitly check the return value and abort the transaction (`ContractExeException` / `BalanceInsufficientException`) when the reduction fails: [3](#0-2) [4](#0-3) 

`MarketSellAssetActuator` breaks this pattern, mirroring the reported bug class: a value-transferring "redeem"/"sell" path that does not enforce (at the point of state mutation) that the amount removed is actually available/removed.

### Impact Explanation
If `reduceAssetAmountV2` ever returns `false` at execute() time (e.g., because state diverged from the `validate()`-time snapshot, because of future refactors that remove/alter the pre-check, or because of edge cases in `assetBalanceEnoughV2`/`reduceAssetAmountV2` handling of the `AllowSameTokenName` V1/V2 asset-map dual bookkeeping), the actuator will still create a live sell order and, on matching, transfer the *buy*-side asset to the counter-party and to the taker — crediting value without the corresponding debit having occurred. That is an accounting/asset-integrity bug: value can be created out of thin air in the TRC10 market subsystem, which is a form of asset corruption reachable directly by any account broadcasting a `MarketSellAssetContract` transaction.

### Likelihood Explanation
Under the current code, `validate()` calls `ownerAccount.assetBalanceEnoughV2(sellTokenID, sellTokenQuantity, dynamicStore)` immediately before `execute()` runs for the same transaction, so in the ordinary single-transaction pipeline this specific defect is largely masked: [5](#0-4) 

However, this makes correctness depend entirely on `validate()` staying perfectly in sync with `reduceAssetAmountV2`'s internal logic (including its `AllowSameTokenName` branching and the `importAsset` migration step), with no defense-in-depth at the point of mutation — exactly the anti-pattern the external report flags. Any future change to either function (or any state mutation between validate and execute within the same actuator lifecycle) would silently reintroduce a real exploitable asset-creation bug, and there is currently no test in `MarketSellAssetActuatorTest`-style coverage that exercises a *failing* `reduceAssetAmountV2` at execute time to catch this regression.

### Recommendation
Mirror the pattern used by `TransferAssetActuator` and `Commons.adjustAssetBalanceV2`: check the boolean returned by `reduceAssetAmountV2` in `MarketSellAssetActuator.transferBalanceOrToken()` and abort the transaction (throw `ContractExeException`) if it returns `false`, e.g.:
```java
if (!accountCapsule.reduceAssetAmountV2(sellTokenID, sellTokenQuantity, dynamicStore, assetIssueStore)) {
  throw new ContractExeException("reduceAssetAmount failed !");
}
```
This ensures the sell-side deduction is enforced at the point of mutation rather than relying solely on the earlier `validate()` check, closing the same class of gap described in the external report (enforce `amount <= balance` at redemption/execution time, not just at a separate validation step).

### Proof of Concept
Not independently reproducible from static analysis alone: exploitation requires constructing a state where `assetBalanceEnoughV2` (used in `validate()`) and `reduceAssetAmountV2` (used in `execute()`) disagree — e.g., a divergence introduced by a future code change, a mid-flight `AllowSameTokenName` transition, or an asset-map inconsistency reached via `importAsset`. I was not able to fully verify a concrete transaction sequence that triggers `reduceAssetAmountV2` to return `false` while `assetBalanceEnoughV2` returned `true` in the current codebase; this would require dynamic testing (e.g., a Devin session with build/test tooling) to confirm reachability and to check whether any other actuator or block-processing path can run between `validate()` and `execute()` for the same transaction.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
