### Title
Unchecked `BigInteger`→`long` truncation in witness-vote-reward (Vi) accounting can corrupt user reward balances - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
java-tron's post-"new reward algorithm" vote-reward accounting mirrors the Sushi-Masterchef "accumulated reward per share" pattern described in the external report: a scaled accumulator (`Vi`, scaled by `DECIMAL_OF_VI_REWARD = 1e18`) is incremented each cycle by `reward * 1e18 / voteCount`, and later multiplied by a user's own vote weight to compute their share of rewards. Just like `cumulatedReward` in the report, `Vi` can be inflated arbitrarily when the divisor (`voteCount`, analogous to `lockedSupplyWithMultiplier`) is small, and the final reward is produced by an unchecked narrowing conversion (`BigInteger.longValue()`) instead of the `LongMath.checkedAdd/checkedMultiply` guards used elsewhere in the same codebase for identical arithmetic.

### Finding Description
The Vi accumulation logic lives in `DelegationStore.accumulateWitnessVi`: [1](#0-0) 

`reward` is the total sun paid to a witness in the cycle (via `payReward`), and `voteCount` is the witness's total vote count for that cycle. `deltaVi = reward * 1e18 / voteCount` is stored as an **unbounded `BigInteger`** (`setWitnessVi`), so no overflow occurs at this step — but nothing constrains how large `Vi` can grow.

The consumer of `Vi`, `MortgageService.computeReward`, multiplies this potentially huge `BigInteger` back against an individual voter's `userVote` count and then narrows the result to a primitive `long` via `.longValue()`: [2](#0-1) 

`BigInteger.longValue()` performs a **silent narrowing conversion** — it does not throw on overflow, it simply returns the low-order 64 bits of the result, which can be an arbitrarily wrong (including negative) `long`. This is the same TVM-reachable computation path used by `VoteRewardUtil.computeReward` for TVM-native voting/withdrawal: [3](#0-2) 

The corrupted `reward` value is then added, unchecked, to the account's `allowance` via `adjustAllowance`, and is eventually converted into real TRX balance by `WithdrawBalanceActuator`/`WithdrawRewardProcessor`: [4](#0-3) [5](#0-4) 

Notably, this codebase already treats similar reward/vote arithmetic as overflow-sensitive elsewhere — `VoteWitnessProcessor` uses `LongMath.checkedAdd`/`checkedMultiply` to guard vote-sum overflow, and `WithdrawBalanceActuator.validate()` uses `LongMath.checkedAdd` before allowing a withdrawal: [6](#0-5) [7](#0-6) 

...but this same discipline is absent from `MortgageService.computeReward` and `VoteRewardUtil.computeReward`, where the multiplication/division on `Vi` deltas is unguarded.

The trigger condition — a witness receiving a disproportionately large reward relative to its total vote count — is directly analogous to the Sherlock report's "small stake, large reward" scenario. `WitnessStore.getWitnessStandby` only filters out witnesses with `voteCount < 1`, so a witness with as little as `voteCount = 1` can still be included in the standby-pay set (e.g., on chains/networks with fewer registered witnesses than `WITNESS_STANDBY_LENGTH`, such as private/consortium deployments or early-stage networks): [8](#0-7) 

and `MortgageService.payStandbyWitness`/`payReward` will still credit that witness's cycle `reward` proportional to `voteCount`: [9](#0-8) 

### Impact Explanation
If `Vi` for a witness grows large enough (due to a tiny `voteCount` denominator relative to accrued `reward`), any voter for that witness — not just an attacker — who later triggers `computeReward` (via `VoteWitnessContract`, `WithdrawBalanceContract`, or the TVM-native `withdrawreward`/`vote` opcodes) will have their reward computed through an unchecked `BigInteger.longValue()` truncation. This can silently produce an arbitrarily wrong (including negative) `long` reward, which is added to the account's `allowance` and eventually becomes real spendable TRX balance. This is an unprivileged accounting-corruption / potential-DoS vector reachable purely through ordinary vote/reward-withdrawal transactions, matching the report's "resource and reward accounting" bug class.

### Likelihood Explanation
Low likelihood on Tron mainnet under normal conditions (many actively-voted SRs make `voteCount` large), matching the external report's own "Medium, low likelihood" conclusion. It becomes materially more likely on smaller/private java-tron deployments, or transiently if most votes are withdrawn from a witness in a cycle where it still receives standby/block pay, driving `voteCount` down while `reward` remains nontrivial.

### Recommendation
- Use `Math.multiplyExact`/`LongMath.checkedMultiply` semantics or perform the final range check before calling `BigInteger.longValue()` in `MortgageService.computeReward` and `VoteRewardUtil.computeReward` (e.g., use `bitLength() <= 63` check or `longValueExact()` and catch `ArithmeticException`).
- Enforce a minimum `voteCount` threshold before a witness is eligible to accrue `Vi`/rewards (mirroring the report's "minimum deposit" mitigation), rather than only filtering `voteCount < 1` in `WitnessStore.getWitnessStandby`.
- Apply the same `LongMath.checkedAdd` discipline already used in `VoteWitnessProcessor` and `WithdrawBalanceActuator.validate()` to the reward-accumulation loops in `MortgageService`/`VoteRewardUtil`.

### Proof of Concept
Not independently executable from the index alone (requires a running java-tron network/testbed with controllable witness registration and reward parameters). Conceptual reproduction:
1. On a network with fewer registered witnesses than `WITNESS_STANDBY_LENGTH` (or after mass unvoting of a witness), have Witness `W` end a cycle with `voteCount = 1` while still receiving a `payReward`/`payStandbyWitness` credit of `X` sun for that cycle.
2. `accumulateWitnessVi` computes `deltaVi = X * 1e18 / 1 = X * 1e18`, stored as `Vi` for `W`.
3. A normal voter `V` with `userVote = N` (large, e.g. millions) who voted for `W` calls `withdrawReward`/`vote` triggering `computeReward`: `deltaVi.multiply(N).divide(1e18).longValue()`. Since `deltaVi.multiply(N)` can exceed `Long.MAX_VALUE`, `.longValue()` silently truncates, yielding an incorrect (possibly negative or huge) reward credited to `V`'s allowance and eventually withdrawable as TRX balance.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  public List<WitnessCapsule> getWitnessStandby(boolean isSortOpt) {
    List<WitnessCapsule> ret;

    sortWitnesses(all, isSortOpt);
    if (all.size() > Parameter.ChainConstant.WITNESS_STANDBY_LENGTH) {
      ret = new ArrayList<>(all.subList(0, Parameter.ChainConstant.WITNESS_STANDBY_LENGTH));
    } else {
      ret = new ArrayList<>(all);
