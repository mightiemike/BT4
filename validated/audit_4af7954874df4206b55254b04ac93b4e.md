### Title
Panic (HashMap index out-of-bounds) in `resolve_entry_point_pc` when a Cairo0 class omits an `entry_points_by_type` variant - ([File: crates/blockifier/src/execution/deprecated_entry_point_execution.rs])

### Summary
`resolve_entry_point_pc` indexes `compiled_class.entry_points_by_type` with the direct `[]` operator instead of a fallible lookup. If a declared/loaded deprecated (Cairo0) class's `entry_points_by_type` map is missing the key for the entry-point type being invoked (e.g. no `Constructor` entry at all), the indexing operation panics rather than returning a `PreExecutionError`. This is analogous to the reported yasm NULL-pointer-dereference class of bug: a malformed/edge-case input structure that the code assumes is always populated is dereferenced/accessed without a presence check, crashing the process.

### Finding Description
`resolve_entry_point_pc` in `crates/blockifier/src/execution/deprecated_entry_point_execution.rs` does: [1](#0-0) 

```rust
let entry_points_of_same_type = &compiled_class.entry_points_by_type[&call.entry_point_type];
```

`entry_points_by_type` is a `HashMap<EntryPointType, Vec<EntryPointV0>>` [2](#0-1) . Rust's `Index` implementation for `HashMap` panics if the key is absent — it does not return `None`/an error. The subsequent code (checking `filtered_entry_points.is_empty()`) only handles the case where the key exists but its `Vec` is empty; it never handles the case where the key is entirely missing from the map.

Elsewhere in the codebase, deprecated-class conversions build this map by conditionally inserting keys only when the corresponding entry-point vector is non-empty: [3](#0-2) 

This shows the map is not guaranteed to contain all three `EntryPointType` variants (`Constructor`, `External`, `L1Handler`) — a class can legitimately have zero constructors, zero L1 handlers, etc., in which case the key is simply absent rather than mapped to an empty `Vec`.

`resolve_entry_point_pc` is invoked from `initialize_execution_context`, which is called from `execute_entry_point_call` for every Cairo0 (`CompiledClassV0`) entry-point execution — including constructor calls triggered by `DeployAccount`/`deploy` and L1 handler invocations triggered by L1 messages: [4](#0-3) 

I was not able to fully confirm, within the available search budget, whether the gateway's stateless/class validation for user-submitted Declare V0/V1/V2 (Cairo0) transactions enforces that `entry_points_by_type` contains all three keys (even as empty vectors) before a class is accepted and stored. The grep for validation logic (`crates/apollo_gateway/src/stateless_transaction_validator.rs`) returned hits referencing `entry_points_by_type`, but I did not have an iteration left to read that code and verify whether it normalizes/validates key presence. This is the key open question that determines whether this is reachable from a plain user-submitted Declare transaction (in-scope, single-tx reachable) versus only from p2p class sync of already-committed classes (which would be out of scope per the "network-DoS/p2p" exclusion).

### Impact Explanation
If reachable from a single Declare + Deploy(Account) sequence (or a class replacement + L1 handler invocation) submitted by an ordinary user, an attacker-crafted Cairo0 class with a deliberately absent `Constructor` (or `L1Handler`) key in `entry_points_by_type` would cause every sequencer node that attempts to execute that entry point to panic. Since blockifier execution is invoked directly in the sequencer's transaction-execution path (not in a subprocess with resource limits, unlike Sierra→CASM compilation), this panic would propagate up and crash the executing thread/process for any full node/sequencer attempting to build or re-execute the block containing this transaction — a chain-halting, "network unable to confirm new transactions" condition, and it would also cause honest-node divergence between nodes that already know how to special-case it and paths where it panics.

### Likelihood Explanation
Likelihood is uncertain and hinges entirely on whether upstream validation (stateless transaction validator / class conversion pipeline for Declare txs) guarantees a full 3-key `entry_points_by_type` map for every accepted class. If such normalization exists (e.g., always inserting empty `Vec`s for missing types before storing the class), this bug is unreachable from user transactions and only a defensive-code-quality issue. If no such normalization exists, a single Declare transaction with a crafted Cairo0 class, followed by a triggering call (deploy/L1 handler), is sufficient — making it trivially reachable by any unprivileged actor.

### Recommendation
Replace the direct `HashMap` indexing in `resolve_entry_point_pc` with `compiled_class.entry_points_by_type.get(&call.entry_point_type).map(Vec::as_slice).unwrap_or(&[])` (or equivalent), so a missing key is treated identically to an empty `Vec` and produces `PreExecutionError::EntryPointNotFound`/`NoEntryPointOfTypeFound` instead of panicking. Additionally, verify/enforce during class validation (Declare stateless validation and any class-conversion code such as `apollo_protobuf/src/converters/class.rs`) that `entry_points_by_type` always contains all three `EntryPointType` keys (with empty vectors where applicable), closing off this and any similar indexing assumptions elsewhere in the codebase (e.g. `crates/blockifier/src/execution/contract_class.rs` line referencing `entry_points_by_type[&...]`).

### Proof of Concept
Conceptual PoC (not fully verified against gateway validation, see caveat above):
1. Craft a Cairo0 (deprecated) contract class JSON whose `entry_points_by_type` object omits the `CONSTRUCTOR` key entirely (rather than providing an empty array), while `EXTERNAL`/`L1_HANDLER` are populated normally.
2. Submit this class via a `DECLARE` transaction (V0/V1/V2) from an ordinary account.
3. Submit a `DEPLOY_ACCOUNT` (or invoke a `deploy` syscall) referencing this class hash, triggering a constructor call.
4. During execution, `execute_entry_point_call` → `initialize_execution_context` → `resolve_entry_point_pc` is called with `call.entry_point_type == EntryPointType::Constructor`; since the map lacks that key, `compiled_class.entry_points_by_type[&EntryPointType::Constructor]` panics, crashing the executing node process instead of returning a graceful `PreExecutionError`.

/// Executes a specific call to a contract entry point and returns its output.
pub fn execute_entry_point_call(
    call: ExecutableCallEntryPoint,
    compiled_class: CompiledClassV0,
    state: &mut dyn State,
    context: &mut EntryPointExecutionContext,
) -> Result<CallInfo, EntryPointExecutionError> {
    let VmExecutionContext { mut runner, mut syscall_handler, initial_syscall_ptr, entry_point_pc } =
        initialize_execution_context(&call, compiled_class, state, context)
            .map_err(EntryPointExecutionError::from)?;

    let (implicit_args, args) = prepare_call_arguments(
        &call,
        &mut runner,
        initial_syscall_ptr,
        &mut syscall_handler.read_only_segments,
    )
    .map_err(EntryPointExecutionError::from)?;
    let n_total_args = args.len();

    // Execute.
    run_entry_point(&mut runner, &mut syscall_handler, entry_point_pc, args)?;

    finalize_execution(runner, syscall_handler, call, implicit_args, n_total_args)
        .map_err(EntryPointExecutionError::from)
}

pub fn initialize_execution_context<'a>(
    call: &ExecutableCallEntryPoint,
    compiled_class: CompiledClassV0,
    state: &'a mut dyn State,
    context: &'a mut EntryPointExecutionContext,
) -> Result<VmExecutionContext<'a>, PreExecutionError> {
    // Verify use of cairo0 builtins only.
    let program_builtins: HashSet<&BuiltinName> =
        HashSet::from_iter(compiled_class.program.iter_builtins());
    let unsupported_builtins =
        &program_builtins - &HashSet::from_iter(CAIRO0_BUILTINS_NAMES.iter());
    if !unsupported_builtins.is_empty() {
        return Err(PreExecutionError::UnsupportedCairo0Builtin(
            unsupported_builtins.iter().map(|&item| *item).collect(),
        ));
    }

    // Resolve initial PC from EP indicator.
    let entry_point_pc = resolve_entry_point_pc(call, &compiled_class)?;
