### Title
GraphQL `MaxDepth(10)` limit does not bound the number of aliased root-level queries, allowing DB-load amplification DoS via `POST /query` - ([File: core/web/router.go])

### Finding Description
`graphqlHandler` in `core/web/router.go` only registers `graphql.MaxDepth(10)` as a schema option when `!app.GetConfig().Insecure().InfiniteDepthQueries()`, and this is the sole cost/complexity control applied to the schema before parsing and executing incoming queries: [1](#0-0) 

`graphql.MaxDepth` in the `graph-gophers/graphql-go` library only restricts the nesting depth of a query's selection sets; it does not cap the number of sibling fields, the number of aliases applied to the same field, or an overall query "cost"/complexity budget. This means an attacker can send a single POST to `/query` containing hundreds or thousands of aliased invocations of the same shallow (depth ≤ 10) root field, e.g. `b0: bridges(limit: 50){...} b1: bridges(limit: 50){...} ... bN: bridges(limit: 50){...}`, and each alias is executed as an independent resolver invocation.

Every root query resolver (e.g. `Bridges`, `Bridge`, `Chain`, etc. in `core/web/resolver/query.go`) performs its own authorization check via `authenticateUser(ctx)` and then issues its own store/ORM call, e.g.: [2](#0-1) 

Because `authenticateUser` only requires *any* valid authenticated session (no role/complexity gating is enforced beyond that), a low-privileged, non-admin session (or even the anonymous state that reaches the resolver, since `AuthenticateGQL` does not abort the request when no session cookie is present, it simply skips attaching a session to the context) is sufficient to reach these resolvers: [3](#0-2) 

Since none of the middlewares in the `/query` chain — `AuthenticateGQL`, `loader.Middleware`, or `graphqlHandler`'s schema options — implement a query-cost/complexity analyzer or an alias-count cap, the number of independent DB-hitting resolver calls per HTTP request is unbounded aside from `MaxDepth`, which alias fan-out does not trigger (depth remains constant regardless of alias count). The `loader.Middleware` dataloader batching only mitigates N+1 patterns for *nested* child-field lookups keyed by ID; it does not reduce the amplification from repeated root-level aliases, each of which independently invokes its own resolver and DB query/pagination logic.

### Impact Explanation
A single authenticated (even non-admin/view-only) request can force the node to execute a large multiple of DB queries/ORM calls in one HTTP round trip, consuming CPU, DB connections, and memory disproportionately to the request size and depth limit intended to bound cost. This matches a resource-exhaustion / denial-of-service impact against the node's web API and backing datastore, degrading availability for legitimate operators and other node functions sharing the same DB connection pool.

### Likelihood Explanation
The precondition (an authenticated session with any role reaching the resolver layer) is trivially satisfiable by any user who can log in via the standard session flow; no special privilege or key leakage is required. Crafting an aliased query is straightforward and repeatable — the attacker fully controls the GraphQL document body sent to `POST /query`, and the resolver code enforces no per-request field/alias budget, only `authenticateUser` and, separately, `MaxDepth(10)` on nesting. Exploitation is deterministic and repeatable on every request.

### Recommendation
Add a query complexity/cost-limiting mechanism in addition to `graphql.MaxDepth`, such as `graphql-go`'s alias/field-count limiting middleware or a custom pre-execution cost estimator (counting total fields/aliases weighted by resolver cost) with a hard cap, rejecting queries above threshold before execution in `graphqlHandler` (`core/web/router.go`). Additionally, consider applying per-request/per-session rate limiting on `/query` proportional to computed query cost, not just raw request count.

### Proof of Concept
Integration test plan:
1. Stand up the router via `NewRouter` with a valid authenticated session (any non-admin role).
2. Send a `POST /query` request whose GraphQL document contains a shallow (depth 1-2) query with an increasing number of aliases of `bridges(limit: 50){ id name }`, e.g. 10, 100, 1000 aliases.
3. Instrument/mock `BridgeORM().BridgeTypes` (or use a counting wrapper/store) to count invocations per request.
4. Assert that invocation count scales linearly with alias count and that no error/rejection occurs even at high alias counts (demonstrating the missing cap), while confirming `MaxDepth(10)` alone does not reject these queries.
5. Optionally measure wall-clock/DB-call latency growth to confirm resource exhaustion trend, and assert that a fix introducing a complexity/alias cap causes such requests to be rejected with a bounded error instead of executing.

func graphqlHandler(app chainlink.Application) gin.HandlerFunc {
	rootSchema := schema.MustGetRootSchema()

	// Disable introspection and set a max query depth in production.
	var schemaOpts []graphql.SchemaOpt

	if !app.GetConfig().Insecure().InfiniteDepthQueries() {
		schemaOpts = append(schemaOpts,
			graphql.MaxDepth(10),
		)
	}

	schema := graphql.MustParseSchema(rootSchema,
		&resolver.Resolver{
			App: app,
		},
		schemaOpts...,
	)

func (r *Resolver) Bridges(ctx context.Context, args struct {
	Offset *int32
	Limit  *int32
}) (*BridgesPayloadResolver, error) {

		return nil, err
	}

	offset := pageOffset(args.Offset)
	limit := pageLimit(args.Limit)

	brdgs, count, err := r.App.BridgeORM().BridgeTypes(ctx, offset, limit)
	if err != nil {
		return nil, err
	}

	return NewBridgesPayload(brdgs, safeInt32(count)), nil
}

			return
		}
