This is a valid analog: an unprivileged meta-transaction sender (the delegate-action `sender_id`) can unilaterally choose an expensive signature scheme (ML-DSA-65) for their inner signing key, and that extra cost is charged as burnt gas against the **relayer** (the outer transaction's signer), who never agreed to pay for that specific key type per-call and has no way to cap or reject it at the protocol level.

### Title
Malicious meta-transaction sender can inflate relayer's gas burn via ML-DSA-65 inner signature verification cost - (File: `runtime/runtime/src/config.rs`)

### Summary
NEP-366 meta transactions let a `sender_id` sign a `DelegateAction` off-chain and have a `relayer` submit and pay for it. NEP-483 post-quantum support adds a `signature_verification_costs` surcharge (`ml_dsa_65_verification_cost`, 100 Ggas) that is charged as *burnt* gas whenever a signature uses `KeyType::MLDSA65` — including "each `Delegate` action's inner signer" [1](#0-0)  — and this charge is computed and burnt against the outer transaction's signer (the relayer), not the sender who chose the key [2](#0-1) .

### Finding Description
`signature_verification_cost` sums the outer signer's cost plus, for every `Delegate`/`DelegateV2` action present, the inner delegate's signature-kind cost, and adds it into the transaction's burnt amount at conversion time via `calculate_tx_cost`/`tx_cost` [3](#0-2) . The `sender_id` of the `DelegateAction` fully controls which `public_key`/key type it signs with (`DelegateAction.public_key`) [4](#0-3) , and the relayer is the one who ends up paying: "All gas and balance costs for submitting `delegate_action.actions` are subtracted from the relayer" [5](#0-4) . Tests confirm the mechanism directly: switching only the *inner* delegate signer from ed25519 to ML-DSA-65 adds exactly `ml_dsa_65_verification_cost` extra burnt gas to the relayer's outer transaction [6](#0-5) , and that this is billed to the relayer as burnt tokens is explicit in the unit test `ml_dsa_65_delegate_inner_verify_charged_as_burnt_gas` [7](#0-6) . Nothing in `apply_delegate_action` or the relayer-facing API lets the relayer see or bound this surcharge before committing to sponsor the meta-transaction; the relayer can only discover the extra cost after having accepted/signed the wrapping transaction, and per NEP-366's design the relayer already commits to paying "all gas and balance costs" once it wraps the `SignedDelegateAction` [8](#0-7) .

### Impact Explanation
This is directly analogous to the reported bug class: an unprivileged party who does not pay the fee (the delegate-action sender) controls an input (signature scheme) that inflates the fee charged to a third party who does pay (the relayer), with no oracle/cap protecting the payer. A malicious or careless `sender_id` can repeatedly submit `DelegateAction`s signed with ML-DSA-65 keys to a relayer that accepts arbitrary users' meta-transactions, forcing the relayer to burn 100 Ggas extra per meta-transaction beyond what it priced its service around, draining relayer-held NEAR balance faster than expected. Because the relayer commits to paying before it can inspect/reject the inner signature scheme's cost implications at scale, this is an economically exploitable fee-inflation vector reachable purely through submitted meta-transactions, matching the "fee bypass / unauthorized value movement via attacker-controlled input to a fee calculation charged to another party" pattern in the source report.

### Likelihood Explanation
Requires only submitting a `DelegateAction` signed with an ML-DSA-65 access key to a relayer service — no special privilege, validator role, or network position needed; any account holder can add such a key and no protocol code prevents the delegate action from choosing it. General-purpose or naively-implemented relayers (which the docs already flag as risky/trust-dependent [9](#0-8) ) are the most exposed, but any relayer accepting meta-transactions from untrusted senders is affected.

### Recommendation
Relayers should validate/whitelist the delegate action's inner signature scheme (and other cost-affecting fields) before agreeing to sponsor a meta-transaction, and the protocol/tooling could expose an explicit, relayer-visible cost estimate (including `signature_verification_costs`) for a given `SignedDelegateAction` prior to submission so relayers can reject unexpectedly expensive inner signatures.

### Proof of Concept
1. Sender creates an access key of `KeyType::MLDSA65` on their own account and signs a `DelegateAction` with it (any receiver/action).
2. Relayer, unaware of the extra cost, wraps this in a `SignedTransaction` and submits it (as in `test_ml_dsa_inner_delegate_verify_charged_as_gas`) [6](#0-5) .
3. On conversion, `signature_verification_cost` adds `ml_dsa_65_verification_cost` (100 Ggas) to the burnt gas charged to the relayer's account, confirmed by the assertion `tx_gas_burnt(pq) == tx_gas_burnt(ed) + verify_gas` [10](#0-9) .
4. Repeating this at scale against a relayer accepting many senders' meta-transactions drains the relayer's NEAR balance beyond what it can recoup, with no protocol-level cap or oracle protecting it.

```rust
/// Extra cost burnt at conversion for the signature verifications this
/// transaction triggers: the signer's own signature plus each `Delegate`
/// action's inner signer, each looked up by scheme in
/// `signature_verification_costs`. The charge is the extra verification cost
/// relative to the classical schemes; only ML-DSA-65 is non-zero, while
/// ed25519/secp256k1 stay 0 for backwards compatibility. The compute cost
/// debits the chunk's wall-clock budget and may be set independently of the
/// gas cost.
fn signature_verification_cost(
    fees: &RuntimeFeesConfig,
    signer_public_key: &PublicKey,
    actions: &[Action],
) -> Result<ParameterCost, IntegerOverflowError> {
    let costs = &fees.signature_verification_costs;
    let mut total = costs[signature_kind(signer_public_key.key_type())];
    for action in actions {
        if let Some(delegate_action) = delegate_inner_action(action) {
            let kind = signature_kind(delegate_action.public_key().key_type());
            total = total.checked_add_result(costs[kind])?;
        }
    }
    Ok(total)
}
```

```markdown
With meta transactions, Alice can create a `DelegateAction`, which is very
similar to a transaction. It also contains a list of actions to execute and a
single receiver for those actions. She signs the `DelegateAction` and forwards
it (off-chain) to a relayer. The relayer wraps it in a transaction, of which the
relayer is the signer and therefore pays the gas costs. If the inner actions
have an attached token balance, this is also paid for by the relayer.
```
