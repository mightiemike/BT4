Based on my research, I found a strong analog in nearcore's gas-key / meta-transaction (delegate action) handling, matching the "safety check that should block an action doesn't" bug-class from the report.

### Title
Delegated (meta-transaction) `WithdrawFromGasKey` bypasses the gas-key withdrawal safeguard - ([File: runtime/runtime/src/action_validation.rs])

### Summary
`WithdrawFromGasKeyAction` is meant to move balance out of a gas key only through a properly-authorized, ephemeral gas-key-nonce transaction path. When the same action is nested inside a `Delegate`/`DelegateV2` action (a meta-transaction relayed by a third party), the dedicated safeguard rejecting it is gated behind the not-yet-fully-active `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate`, so on protocol versions preceding that gate the withdrawal executes and drains the gas key balance exactly the way the report describes liquidation continuing to run while the vault is "paused" — a safety check exists in the code, but the execution path that should be blocked isn't actually blocked for all callers.

### Finding Description
`validate_delegate_action` in `runtime/runtime/src/action_validation.rs` only rejects a nested `WithdrawFromGasKey` action when `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` is enabled for the current protocol version: [1](#0-0) 

Without that feature enabled, the nested `WithdrawFromGasKey` action passes validation and is executed downstream by `action_withdraw_from_gas_key`, which withdraws directly from the gas key's balance and credits the account: [2](#0-1) 

The dedicated regression test for this exact issue confirms the pre-fix behavior explicitly: a delegated (relayer-submitted) withdrawal is admitted and "moves balance out of the gas key, which is the hole this rule closes": [3](#0-2) 

This mirrors the reported bug class precisely: a value-affecting operation (`liquidatePosition`/`WithdrawFromGasKey`) has an intended guard (`paused`/`RejectWithdrawFromGasKeyInDelegate`), but the guard is not applied on the path that is actually reachable in practice (meta-transactions relayed on behalf of a sender), so the protected operation still executes and moves value.

### Impact Explanation
On any protocol version where `RejectWithdrawFromGasKeyInDelegate` is not yet enabled, a sender (or anyone able to construct a signed `DelegateAction`/`DelegateV2` on the sender's behalf via a relayer) can drain a gas key's balance through the meta-transaction path even though the direct, non-delegated gas-key withdrawal flow enforces its own nonce/authorization semantics (`verify_and_charge_gas_key_tx_ephemeral`) that the delegated path does not replicate. This is a concrete unauthorized-value-movement path consistent with the "Validate" criteria (unauthorized value movement via a submitted transaction), matching the severity class of the reported liquidation-while-paused issue.

### Likelihood Explanation
The path is reachable by an ordinary relayer/meta-transaction sender submitting a single transaction containing a `Delegate`/`DelegateV2` action with a nested `WithdrawFromGasKey` action — no privileged role or validator/network position is required. Likelihood is high on any deployment running a protocol version prior to the activation of `RejectWithdrawFromGasKeyInDelegate`, since no other check in the runtime blocks this nested action.

### Recommendation
Confirm the current/target protocol version's activation status of `RejectWithdrawFromGasKeyInDelegate`. If it is not yet active on the deployed/target network, treat this as a live authorization gap: either backport the guard as an unconditional check (independent of protocol-version gating) in `validate_delegate_action`, or ensure the feature activates before any network exposes gas keys with nonzero balances to meta-transaction relaying.

### Proof of Concept
1. Create an account with a full-access key and a gas key funded via `TransferToGasKeyAction` (see setup in `test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs:72-110`).
2. On a protocol version prior to `RejectWithdrawFromGasKeyInDelegate` activation, have a relayer submit a `Delegate`/`DelegateV2` action (signed by the sender's own regular key, not the gas key) containing a nested `WithdrawFromGasKeyAction` targeting the gas key.
3. Observe the transaction succeeds and the gas key balance decreases by the withdrawn amount, as asserted in the test at lines 112–137, confirming the bypass. [4](#0-3) 

**Uncertainty note:** I could not directly confirm within the available context whether `RejectWithdrawFromGasKeyInDelegate` is currently active on this repo's `STABLE_PROTOCOL_VERSION` (the `version.rs` activation-version match arm was not retrieved before tool access ended). If this feature is already active at the network's current/target protocol version, this finding would be already mitigated in production and only relevant to older/rolling-upgrade windows (still a valid "transaction-triggered" state-divergence/authorization risk during the upgrade transition, as the test itself exercises).

pub(crate) fn action_withdraw_from_gas_key(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &WithdrawFromGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    let Some(updated_balance) = gas_key_info.balance.checked_sub(action.amount) else {
        result.result = Err(ActionErrorKind::InsufficientGasKeyBalance {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
            balance: gas_key_info.balance,
            required: action.amount,
        }
        .into());
        return Ok(());
    };
    gas_key_info.balance = updated_balance;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);

    let new_account_balance = account.amount().checked_add(action.amount).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "Account balance integer overflow".to_string(),
        ))
    })?;
    account.set_amount(new_account_balance);
    Ok(())
}

#[test]
fn test_reject_delegated_gas_key_withdraw_protocol_upgrade() {
    init_test_logger();

    if !ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(PROTOCOL_VERSION) {
        return;
    }

    let new_protocol = ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.protocol_version();
    let old_protocol = new_protocol - 1;
    assert!(
        old_protocol >= MIN_SUPPORTED_PROTOCOL_VERSION,
        "no supported protocol version still admits a delegated WithdrawFromGasKey, so there is \
         nothing left to test here - remove this test"
    );

    let sender = create_account_id("alice");
    let relayer = create_account_id("relayer");
    let epoch_length = 10;

    // Boundary "mm": "alice" lands on the first shard, "relayer" on the second,
    // so the delegate receipt crosses a shard on its way to the sender.
    let shard_layout = ShardLayout::multi_shard_custom(vec![create_account_id("mm")], 1);

    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .protocol_version(old_protocol)
        .protocol_upgrade_schedule(ProtocolUpgradeVotingSchedule::new_immediate(new_protocol))
        .epoch_length(epoch_length)
        .shard_layout(shard_layout)
        .add_user_account(&sender, Balance::from_near(1_000))
        .add_user_account(&relayer, Balance::from_near(1_000))
        .build();

    let gas_key: Signer =
        InMemorySigner::from_seed(sender.clone(), KeyType::ED25519, "gas_key").into();
    let add_key_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::AddKey(Box::new(AddKeyAction {
            public_key: gas_key.public_key(),
            access_key: AccessKey::gas_key_full_access(1),
        }))],
    );
    env.rpc_runner().run_tx(add_key_tx, Duration::seconds(10));

    let fund_tx = env.rpc_node().tx_from_actions(
        &sender,
        &sender,
        vec![Action::TransferToGasKey(Box::new(TransferToGasKeyAction {
            public_key: gas_key.public_key(),
            deposit: Balance::from_near(10),
        }))],
    );
    env.rpc_runner().run_tx(fund_tx, Duration::seconds(10));

    // Before the upgrade the nested withdrawal is admitted and moves balance out
    // of the gas key, which is the hole this rule closes.
    assert_eq!(
        env.rpc_node().protocol_version_at_head(),
        old_protocol,
        "expected to start pre-upgrade"
    );
    let (_, balance_before) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    let tx = delegated_withdraw_tx(&env, &sender, &relayer, &gas_key);
    let outcome = env
        .rpc_runner()
        .execute_tx(tx, Duration::seconds(10))
        .expect("delegated withdrawal admitted pre-upgrade");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::SuccessValue(_),
        "pre-upgrade delegated withdrawal should execute",
    );
    let (_, balance_after) =
        query_gas_key_and_balance(&env.rpc_node(), &sender, &gas_key.public_key());
    assert_eq!(
        balance_after,
        balance_before.checked_sub(WITHDRAW_AMOUNT).unwrap(),
        "the nested withdrawal should have drained the gas key",
    );
