## Title
Floor-division precision loss in `DelegateResourceActuator`/`DelegateResourceProcessor` allows delegation of frozen balance beyond truly-available (un-consumed) collateral - (File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java)

### Summary
The Paladin `_pledge` finding is a case where a pre-transfer eligibility check is computed from an *unrounded* input value (`amount`), while the value that is actually credited/consumed (`bias`) is a floored/truncated derivative of that input. Because the check uses the un-truncated value instead of the truncated one, the check can pass while the real, truncated outcome diverges from what the check assumed. The same pattern exists in java-tron's `DelegateResourceActuator.validate()` (and its TVM twin `DelegateResourceProcessor.validate()`): the "already consumed bandwidth/energy" amount used to gate how much frozen balance an account may delegate is computed via a `double`-based formula and then floor-truncated with a `(long)` cast, before being compared against `delegateBalance`.

### Finding Description
In `DelegateResourceActuator.validate()`, the amount of bandwidth already consumed by the owner is estimated as:
```java
long netUsage = (long) (accountNetUsage * TRX_PRECISION * ((double)
    (dynamicStore.getTotalNetWeight()) / dynamicStore.getTotalNetLimit()));
long v2NetUsage = getV2NetUsage(ownerCapsule, netUsage, this.disableJavaLangMath());
if (ownerCapsule.getFrozenV2BalanceForBandwidth() - v2NetUsage < delegateBalance) {
  throw new ContractValidateException(
      "delegateBalance must be less than or equal to available FreezeBandwidthV2 balance");
}
``` [1](#0-0) 

The identical pattern exists for `ENERGY`: [2](#0-1) 

and is duplicated verbatim in the TVM-native path: [3](#0-2) 

`(long) (x * (double) a / b)` truncates toward zero, i.e. floors the true (rational) consumed-usage value. `getV2NetUsage`/`getV2EnergyUsage` then subtract fixed frozen-balance offsets and clamp at zero: [4](#0-3) 

Because the floor always makes `netUsage`/`energyUsage` (and therefore `v2NetUsage`/`v2EnergyUsage`) less than or equal to the mathematically exact value, the "available FreezeV2 balance" computed as `frozenV2Balance - v2NetUsage` is always greater than or equal to the true available (un-consumed) collateral. The validate check therefore accepts `delegateBalance` values that are, in exact arithmetic, larger than the owner's genuinely free (unused) FreezeV2 balance — the mirror image of the Paladin bug, where a check performed against the pre-truncation `amount` let a caller pass a gate that the truncated `bias` would not actually satisfy.

### Impact Explanation
When the check passes on an inflated "available" figure, `execute()`/`DelegateResourceProcessor.execute()` moves `delegateBalance` out of the owner's `FrozenV2` balance into the `DelegatedResource`/receiver's `AcquiredDelegatedFrozenV2Balance`, crediting the receiver with bandwidth/energy resource entitlement: [5](#0-4) 
This can let an owner delegate collateral that is, in reality, still backing their own consumed bandwidth/energy, resulting in resource-accounting divergence: both the owner (via ongoing usage decay) and the receiver (via delegated balance) can end up drawing resource entitlement from the same frozen TRX, effectively creating "phantom" bandwidth/energy not fully backed by frozen collateral. This is an underpriced-resource/accounting-divergence impact class similar in nature (though smaller in magnitude, since usage numbers are bandwidth/energy points, not TRX) to the acknowledged Paladin issue.

### Likelihood Explanation
This path is reachable by any unprivileged account holding FreezeV2 balance for bandwidth or energy that has also actively consumed bandwidth/energy in the current window, via a standard `DelegateResourceContract` transaction or the corresponding TVM native contract call — no privileged role required. The magnitude of the discrepancy per call is small (bounded by rounding error of `usage * TRX_PRECISION * weight/limit`), so exploiting it meaningfully would require many repeated delegate operations or specific ratio values that maximize the truncation error, similar to how Paladin's issue was assessed as low-severity/acknowledged rather than critical.

### Recommendation
Compute the consumed-usage-in-TRX conversion using integer/`BigInteger` arithmetic with ceiling rounding (consistent with the hardened `divideCeilExact`/`BigInteger` patterns already used elsewhere in this codebase, e.g. `ResourceProcessor.divideCeil`/`divideCeilExact` and `RepositoryImpl.usageToBalance`) instead of a floor-truncating `double`/`(long)` cast, so that the eligibility check is evaluated against a usage estimate that is never smaller than the true value. This mirrors the recommended fix pattern for Paladin: base the gating check on the truncated/rounded value that will actually be applied, not on a pre-truncation estimate. [6](#0-5) 

### Proof of Concept
1. Freeze balance for BANDWIDTH via `FreezeBalanceV2Contract`.
2. Consume bandwidth close to, but not exactly at, a value whose `netUsage = accountNetUsage * TRX_PRECISION * (totalNetWeight/totalNetLimit)` produces a fractional true value (e.g. pick `totalNetWeight`/`totalNetLimit` such that the ratio is non-terminating, as already exercised in the repo's own precision tests, e.g. `CalculateGlobalLimitHardenTest.testGlobalNetLimitV2ExactPrecision`).
3. Call `DelegateResourceContract` with `delegateBalance` set exactly to `frozenV2BalanceForBandwidth - floor(netUsage)`, i.e. one unit above the true `frozenV2BalanceForBandwidth - exactNetUsage`.
4. `validate()` at [1](#0-0)  passes because the floored `v2NetUsage` understates true usage, even though `delegateBalance` exceeds the mathematically exact available collateral.
5. `execute()` transfers the balance to the receiver's `AcquiredDelegatedFrozenV2BalanceForBandwidth`, while the owner's account still reflects the (higher, real) bandwidth usage against the now-reduced `FrozenV2BalanceForBandwidth`, demonstrating the accounting divergence.

  public static long getV2NetUsage(AccountCapsule ownerCapsule, long netUsage, boolean
      disableJavaLangMath) {
    long v2NetUsage= netUsage
        - ownerCapsule.getFrozenBalance()
        - ownerCapsule.getAcquiredDelegatedFrozenBalanceForBandwidth()
        - ownerCapsule.getAcquiredDelegatedFrozenV2BalanceForBandwidth();
    return max(0, v2NetUsage, disableJavaLangMath);
  }

  public static long getV2EnergyUsage(AccountCapsule ownerCapsule, long energyUsage, boolean
      disableJavaLangMath) {
    long v2EnergyUsage= energyUsage
          - ownerCapsule.getEnergyFrozenBalance()
          - ownerCapsule.getAcquiredDelegatedFrozenBalanceForEnergy()
          - ownerCapsule.getAcquiredDelegatedFrozenV2BalanceForEnergy();
    return max(0, v2EnergyUsage, disableJavaLangMath);
  }
