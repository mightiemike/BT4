**Reasoning:**

`BurnToken::try_from_bytes` simply delegates to `bcs::from_bytes(bytes)` [1](#0-0) . BCS (Binary Canonical Serialization) is specifically designed to be a canonical, deterministic format, and its deserializer enforces that the entire input buffer must be consumed — any trailing bytes after a fully-deserialized value cause `bcs::from_bytes` to return an `Err` (e.g. `Error::RemainingInput`), rather than silently succeeding. This is a core invariant of the BCS spec (not something this call site opts into or out of), so appending garbage/padding after a valid `BurnToken` payload will deterministically fail deserialization.

Additionally, the premise of "one node's bcs deserializer version accepting it, another rejecting it" is not a realistic divergence vector in this codebase: all validators build from the same workspace-pinned `bcs` dependency (locked via `Cargo.lock`), and BCS's trailing-byte rejection has been a stable, foundational behavior of the format since its introduction — it is not version-dependent behavior that has changed across releases. There is no code in `burn_token.rs` that reinterprets, truncates, or partially consumes the byte buffer in a way that could introduce divergence; the function is a thin, single-call wrapper around the canonical deserializer.

Since this does not represent unprivileged-input-driven corruption of committed state, proof material, or authenticated responses — and the byte-for-byte replay determinism the question worries about is actually guaranteed by BCS's canonical-format design, not violated by it — this does not meet the state-integrity gate for acceptance.
