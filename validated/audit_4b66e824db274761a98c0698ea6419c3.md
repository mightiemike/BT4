### Title
Native `long` multiply-then-divide overflow in `ExchangeInjectActuator.execute()` diverges from BigInteger-safe validation, causing validated exchange transactions to revert - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator` computes the paired token amount (`anotherTokenQuant`) for a TRON bancor-style `Exchange` pool twice: once safely with `BigInteger` in `doValidate()`, and again in `execute()` using primitive-`long` arithmetic (`multiplyExact` then `floorDiv`). Because the multiplication is performed on raw `long` operands *before* the division that would bring the value back into range, the intermediate product `secondTokenBalance * tokenQuant` (or `firstTokenBalance * tokenQuant`) can exceed `Long.MAX_VALUE` and throw `ArithmeticException` in `execute()` even though the equivalent `BigInteger` computation in `doValidate()` succeeded. This is the same overflow class as the reported Tapioca `Market._isSolvent`/`_computeMaxBorrowableAmount` bug: `share * totalAmount` overflowing before the division reduces the value back to a representable range.

### Finding Description
`doValidate()` computes the pool-implied paired amount safely: [1](#0-0) 

But `execute()` re-derives the same value using native `long` operations instead of reusing the already-validated result: [2](#0-1) 

`multiplyExact(secondTokenBalance, tokenQuant)` computes the full product as a `long` before any division occurs. If `secondTokenBalance * tokenQuant > Long.MAX_VALUE (9,223,372,036,854,775,807)`, `multiplyExact` throws `ArithmeticException`, even though the *final* `anotherTokenQuant` (after division by `firstTokenBalance`) is well within the pool's `getExchangeBalanceLimit()` bound and was already computed successfully in `doValidate()` via `BigInteger.multiply().divide()`, which never has this intermediate-overflow limitation.

The `ArithmeticException` is caught in `execute()`: [3](#0-2) 

and converted into a `ContractExeException`, marking the transaction `FAILED` — i.e., a transaction that passed all validation checks reverts purely due to an avoidable overflow in the execution-time recomputation.

This mirrors the external report's root cause precisely: the multiply-before-divide pattern on fixed-width integers overflows even though the mathematically correct (post-division) result would fit, and the codebase already demonstrates awareness of this exact issue by using `BigInteger` in `doValidate()` but failing to apply the same safety in `execute()`.

### Impact Explanation
Any unprivileged account (any account owning the `Exchange` pool via `ExchangeCreateActuator`, calling `ExchangeInjectContract`) can trigger a validated-but-reverting transaction whenever pool balances and inject quantity are large enough that `secondTokenBalance * tokenQuant` (or the mirrored `firstTokenBalance * tokenQuant`) exceeds `Long.MAX_VALUE`. Because `doValidate()` uses `BigInteger` and does not reject such inputs (the final ratio is within `getExchangeBalanceLimit()`), the transaction is broadcast and accepted into a block as valid, then fails deterministically at `execute()`. This:
- Wastes the submitter's bandwidth/fee for a transaction that should have succeeded.
- Leaves the pool's legitimate inject operation permanently unusable at that balance/quant combination (a state-divergence/DoS on market functionality), matching the "actions might revert due to overflow" impact class in the original report.
- Represents an inconsistency between the actuator's validate and execute phases — a correctness bug that undermines the guarantee that a validated transaction can be executed.

### Likelihood Explanation
The overflow requires a specific magnitude relationship between the two pool token balances and the injected quantity (as with the original report, this occurs naturally when the two tokens have very different value scales, e.g., a TRC10 asset with a large integer supply paired against TRX or another token with different decimal conventions). Exchange pool balances and inject quantities are both attacker-controlled up to `getExchangeBalanceLimit()`, and the pool creator (who calls `ExchangeInjectContract`) is an ordinary, unprivileged account. No special privilege is required to construct pools/balances that trigger this divergence.

### Recommendation
In `ExchangeInjectActuator.execute()`, reuse `BigInteger` arithmetic (as already done in `doValidate()`) to compute `anotherTokenQuant`, or refactor so `execute()` reuses the value computed during validation, instead of recomputing it with primitive `multiplyExact`/`floorDiv`. This avoids the intermediate-overflow divergence between validation and execution and ensures a transaction that passes `validate()` cannot fail during `execute()` due to arithmetic overflow.

### Proof of Concept
1. Create an `Exchange` pool (`ExchangeCreateActuator`) with `firstTokenBalance` and `secondTokenBalance` chosen from tokens of very different decimal/scale (e.g., a high-supply TRC10 token vs. TRX), within `getExchangeBalanceLimit()`.
2. Call `ExchangeInjectContract` with a `tokenQuant` such that `secondTokenBalance * tokenQuant` (the raw product before division by `firstTokenBalance`) exceeds `Long.MAX_VALUE`, while the resulting `anotherTokenQuant` (product ÷ `firstTokenBalance`) still satisfies `newTokenBalance/newAnotherTokenBalance <= balanceLimit` in `doValidate()`.
3. Observe that `doValidate()` (lines 209-227) passes because it uses `BigInteger`.
4. Observe that `execute()` (lines 71-83) throws `ArithmeticException` from `multiplyExact`, is caught, and the actuator throws `ContractExeException`, resulting in transaction status `FAILED` despite having passed validation — reproducing the exact multiply-before-divide overflow class described in the external report.
