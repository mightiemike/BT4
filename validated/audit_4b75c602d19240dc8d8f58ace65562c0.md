`TransactionOutput::ensure_match_transaction_info` skips verifying `position_state_checkpoint_hash`, allowing replay/verification tooling to accept a corrupted native-position state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check that authenticates a locally-computed `TransactionOutput` against the on-chain-committed `TransactionInfo` (status, gas, write-set hash, event root). The `TransactionInfoV1` variant added for the native-position ("trading-native") subsystem carries an additional authenticated field, `position_state_checkpoint_hash`, but the comment in the code explicitly documents that this field is **not** checked by `ensure_match_transaction_info`.

### Finding Description
`TransactionInfoV1` includes `position_state_checkpoint_hash` as an authenticated commitment to the native-position Merkle state root, alongside `state_checkpoint_hash` and `hot_state_checkpoint_hash`. [1](#0-0) 

However, the verification routine that compares a re-executed `TransactionOutput` against the authenticated `TransactionInfo` — used by replay/verification tooling such as `replay_on_archive` and the Aptos debugger — checks status, gas used, write-set hash, and event root hash, but explicitly does **not** validate `position_state_checkpoint_hash`. The code contains a direct acknowledgment of this gap: [2](#0-1) 

The comment states verbatim: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." This is called from `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` (confirmed via `grep_search` for `ensure_match_transaction_info`), which are the tools operators use to detect state divergence during replay/verification.

### Impact Explanation
If the native-position (perpetuals/trading) subsystem's committed Merkle root diverges from what a node locally computes (e.g., due to a bug in `commit_native_position`/`NativeStateCommitter::apply` in `storage/aptosdb/src/db/aptosdb_writer.rs` and `storage/aptosdb/src/native_state_committer.rs`, or corruption during restore/replay), the standard replay-verification path used to catch exactly this kind of corruption will not detect it, because `position_state_checkpoint_hash` is silently skipped. This is a genuine authenticated-commitment integrity gap: the position state root is part of the on-chain `TransactionInfo` (thus part of what validators sign and the accumulator commits to), but the tooling meant to verify local computation matches the authenticated value does not check it. Silent divergence of durable position/perpetuals ledger state could persist undetected, which is a state-commitment integrity concern for a subsystem holding real trading positions.

### Likelihood Explanation
This is not an attacker-triggerable exploit per se (there's no unprivileged actor analogous to "any user calling revokeLender"); rather it is a code-proven gap: the verification function's own documentation confirms the check is missing, and the position-checkpoint hash is deliberately excluded pending enabling of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. The likelihood of the underlying divergence actually occurring depends on bugs elsewhere in the native-position commit/restore path, which I could not fully trace before running out of iterations (in particular, I was unable to confirm whether `do_ledger_update.rs` independently validates `position_state_checkpoint_hash` during normal block-execution/consensus commit, separate from the replay-tool path — my last tool calls to inspect that file did not complete due to the iteration limit). It is therefore uncertain whether this gap is confined to auxiliary debugging/replay tools (lower severity) or also affects the primary consensus commit path (higher severity).

### Recommendation
Extend `ensure_match_transaction_info` to compute and compare `position_state_checkpoint_hash` (and the other currently-skipped `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields) whenever `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, so replay-verification tooling can actually detect position-state divergence, and confirm independently that the primary block-commit path in `execution/executor/src/workflow/do_ledger_update.rs` performs this validation before treating a block as committed.

### Proof of Concept
Not applicable / not independently constructible from available tool access — this finding is based on the explicit TODO/comment in the verification function's own source rather than a demonstrated exploit, and I was unable to complete verification of the consensus commit path (`do_ledger_update.rs`) before the iteration limit was reached. This should be treated as a documented, code-proven verification gap rather than a fully proven end-to-end exploit; further investigation of `do_ledger_update.rs` and `execution/executor-types/src/state_checkpoint_output.rs` is recommended to determine whether the primary commit path independently closes this gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
