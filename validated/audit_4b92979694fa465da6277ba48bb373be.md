## Title
Unverified state-value chunks accepted during `KvOnly` backup restore can leave durable KV storage permanently inconsistent with the authenticated Merkle root - (File: `storage/aptosdb/src/state_restore/mod.rs`)

### Summary
`StateSnapshotRestore::add_chunk` accepts a `SparseMerkleRangeProof` for every state-value chunk, but when `restore_mode == StateSnapshotRestoreMode::KvOnly` it discards that proof entirely and writes the chunk straight to the state-KV database with no cryptographic check that the values are the ones committed on-chain. The multi-phase backup/restore coordinator (`storage/backup/backup-cli/src/coordinators/restore.rs`) relies on this unverified path to seed the KV store from a backup snapshot, and later verifies only the *tree structure* (not the KV bytes) of a later snapshot via `TreeOnly` mode. Keys that are not subsequently touched by verified transaction replay never get their values checked against any accumulator/Merkle root, so a compromised or corrupted backup source can plant wrong values permanently into the restored `AptosDB`.

### Finding Description
`StateSnapshotRestore::add_chunk` in [1](#0-0)  takes both `chunk: Vec<(K, V)>` and `proof: SparseMerkleRangeProof`, but its `KvOnly` arm calls only `self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;` — the `proof` argument is never passed to any verification routine. Contrast this with the `Default` arm just below it (lines 227-249), which explicitly documents and performs "verify proof -> write state_kv_db -> write state_merkle_db," and the `TreeOnly` arm (lines 219-226), which calls `tree_restore....add_chunk_impl(...)` that internally calls `verify_chunk`/`verify` against the `expected_root_hash` established when the receiver was constructed (see `StateSnapshotRestore::new`, [2](#0-1) ).

The `StateSnapshotRestoreController` still downloads and deserializes the `proof` for each chunk in `KvOnly` mode ( [3](#0-2) ), giving the appearance that data is authenticated, but that proof is silently dropped once it reaches `add_chunk`.

This unverified path is actually exercised in production restore logic. `RestoreCoordinator::run_impl` restores a KV-only snapshot at `kv_snapshot.version` using `StateSnapshotRestoreMode::KvOnly` (phase 1.a), and separately restores the Merkle tree structure of a *later* snapshot at `tree_snapshot.version` using `StateSnapshotRestoreMode::TreeOnly` (phase 2.a) — see [4](#0-3)  and [5](#0-4) . Between the two versions, only transactions are replayed with verified write sets (`TransactionRestoreBatchController` / `replay_kv`, [6](#0-5) ). Transaction-output verification checks each txn's write set hash against `state_change_hash` in its accumulator-proven `TransactionInfo` ( [7](#0-6) ), but it only re-verifies keys that are actually written by a replayed transaction. Any key present in the initial (unverified) `KvOnly` snapshot but never touched again by a subsequent transaction keeps whatever value the backup source supplied — a value that was never checked against any `SparseMerkleRangeProof` or accumulator root.

The `TreeOnly` restore at `tree_snapshot.version` only reconstructs Merkle tree node hashes/positions; it does not re-derive or re-check the KV byte content behind those hashes (`StateValueRestore` isn't invoked for `TreeOnly`). So the eventual `state_kv_db` can end up holding values for untouched keys that are simply whatever the KvOnly restore wrote, with no guarantee they hash to the leaf value recorded in the (separately, structurally verified) Jellyfish Merkle tree.

### Impact Explanation
This breaks the state-storage/proof invariant that the codebase otherwise enforces everywhere else in the restore and proof-verification code (`verify_chunk` in `JellyfishMerkleRestore`, `TransactionInfoWithProof::verify`, `TransactionOutputListWithProofV2::verify`, etc.): durable KV content must be provably bound to a proof/root before being written. A node restored this way is left with a `state_kv_db` that may silently diverge from the correct on-chain state for any key untouched by post-snapshot transaction replay — i.e., "committed state that differs from the correct VM result / corrupts durable ledger data" that is served afterward through this node's authenticated state APIs (`get_state_value_with_proof`, etc.), which combine the (possibly wrong) stored value with a Merkle proof computed from the tree. Depending on how the leaf hash used for later proof responses is derived, this can produce internally-inconsistent proof responses or, if the node also seeds gossip/serving from this data, propagate incorrect data to state-sync peers.

### Likelihood Explanation
This requires an untrusted or compromised backup storage backend (the explicit "restore flows" attack surface called out in the task) supplying a `KvOnly` state snapshot, or a `KvOnly` chunk stream corrupted in transit/at rest with an out-of-date/incorrect proof file that is never checked. Given `BackupStorage` implementations commonly point at externally-hosted or shared cloud storage, and the restore coordinator invokes this exact code path (`RestoreCoordinator::run_impl`, phase 1.a) by default whenever a KV snapshot precedes the tree snapshot, this is a realistic operational path rather than a purely theoretical one.

### Recommendation
In the `KvOnly` branch of `StateSnapshotRestore::add_chunk`, verify the incoming chunk against the tree's `expected_root_hash` using the supplied `SparseMerkleRangeProof` (the same way `TreeOnly`/`Default` do) before writing to `state_kv_db`, even though the tree itself is not being persisted in this mode. Alternatively, require that `KvOnly` restores always be immediately followed, for the *same* version, by a verified `TreeOnly` pass over the *entire* key range before any transaction replay is permitted to build on top of it, and reject partial/skipped verification silently succeeding as it does today.

### Proof of Concept
1. Configure a `RestoreCoordinator` with a KV snapshot manifest at version `V1` and a tree snapshot manifest at version `V2 > V1`, mirroring the real coordinator flow in `storage/backup/backup-cli/src/coordinators/restore.rs` lines 236-303.
2. Serve a `StateSnapshotBackup` for `V1` whose declared `root_hash` matches the ledger-info-authenticated `TransactionInfoWithProof` (so the top-level `run_impl` check at `storage/backup/backup-cli/src/backup_types/state_snapshot/restore.rs` lines 123-136 passes), but whose per-chunk blob content for one or more keys does not actually hash into that Merkle root (i.e., forge the `SparseMerkleRangeProof` files, or simply swap blob values while keeping stale/mismatched proof files, since they are never validated in `KvOnly` mode).
3. Run `StateSnapshotRestoreController::run_impl` with `restore_mode: StateSnapshotRestoreMode::KvOnly` — observe that `add_chunk` writes the tampered KV data with no error, since `storage/aptosdb/src/state_restore/mod.rs` lines 213-217 never calls into `verify_chunk`.
4. Complete phase 2 with a legitimate `TreeOnly` restore of `V2` and legitimate transaction replay between `V1+1` and `V2` that does not touch the tampered key(s).
5. Query the restored node for the tampered key's value — the value returned no longer matches genuine on-chain history, despite the node reporting itself fully synced/restored.
