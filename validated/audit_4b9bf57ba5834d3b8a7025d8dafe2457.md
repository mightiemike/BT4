### Title
Unauthenticated Open Redirect via `exitIframe` Query Parameter Bypassing Origin Validation - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts`)

### Summary
`sanitizeRedirectUrl` (and its `react-router` twin) is meant to vet a redirect destination before it is embedded into an auto-executing `<script>window.open(...)</script>` served by `renderAppBridge`. It rejects `file://` URIs, whitespace, disallowed protocols, and doubled-slash relative paths, but it never checks that the resolved URL's origin matches the `domain` argument it receives. Any absolute `http(s)://attacker.example` URL passes validation unchanged.

### Finding Description
The exit-iframe responder reads the `exitIframe` query parameter directly from the unauthenticated request and forwards it, unmodified, into `renderAppBridge`: [1](#0-0) 

This check runs at the very top of `authenticateAdmin`, before HMAC/session-token/session validation, and before `strategy.respondToOAuthRequests`: [2](#0-1) 

`renderAppBridge` passes the raw `destination` into `sanitizeRedirectUrl`: [3](#0-2) 

`sanitizeRedirectUrl`/`isSafe` only rejects `file://` URIs (3+ slashes), whitespace, non-`http(s)` protocols, and pathnames with doubled slashes — it never compares `url.origin`/`url.hostname` to the `domain` parameter that was supplied: [4](#0-3) 

Consequently `sanitizeRedirectUrl(config.appUrl, 'https://attacker.example')` returns `https://attacker.example` unmodified, since `new URL('https://attacker.example', config.appUrl)` is a fully valid, absolute `https:` URL with no doubled-slash pathname. The value is then reflected verbatim into an auto-executing script tag returned with a `200 OK`:
```
<script>window.open("https://attacker.example", "_top")</script>
```
Because the redirect target is `_top` and the endpoint is designed to "exit" the Shopify admin iframe, the browser's top-level context is navigated away from the merchant's Shopify admin session to the attacker-controlled page — while it is served from, and appears to originate at, the legitimate app's own domain. This is the same class of bug as the reported issue: a data structure/parameter (`exitIframe` URL) that is consumed without full validation of a critical field (destination origin), even though a validation routine (`validator.go` there / `sanitizeRedirectUrl` here) exists and is partially applied.

Note that the documented, intentional use of `redirect(...)` (via `authenticate.admin(request).redirect(...)`) explicitly warns callers that the helper "does not validate the destination URL" and to avoid passing raw user input — but the exit-iframe endpoint itself does exactly that, with no opt-in by app developers and no authentication gate, making this a framework-level gap rather than a caller misuse issue.

### Impact Explanation
An attacker can send an anonymous GET request such as:
```
GET /auth/exit-iframe?exitIframe=https://attacker.example&shop=victim-shop.myshopify.com
```
to any Shopify Remix/React Router app using the default `exitIframePath`, and receive a `200 OK` HTML page hosted on the legitimate app's own domain that immediately opens/navigates the top-level frame to the attacker's site. This enables convincing phishing (e.g., a fake Shopify/App re-authorization page) launched from a trusted app domain, and can be chained with the embedded-iframe flow that legitimately triggers this same endpoint during re-auth, making the attack URL look like a normal part of the app's auth flow.

### Likelihood Explanation
High. No authentication, session token, or shop installation is required — a single crafted URL sent to an anonymous victim is sufficient. The endpoint and query parameter name are fixed/predictable (`config.auth.exitIframePath`, default well-known), and the vulnerable code path is reached unconditionally for any request to that path before any session or HMAC checks occur.

### Recommendation
In `sanitizeRedirectUrl`/`isSafe`, after resolving the URL, verify that `url.origin` matches the `domain` origin unless the caller explicitly opts into cross-origin redirects (e.g., via a separate, clearly-named parameter/allow-list). At minimum, `respondToExitIframeRequest` should validate that the `exitIframe` destination stays within `config.appUrl`'s origin (or a small, explicit allow-list of same-app relative paths) before calling `renderAppBridge`, since this destination is always attacker-reachable pre-authentication.

### Proof of Concept
1. Identify a Shopify app built with `@shopify/shopify-app-remix` (or `shopify-app-react-router`) using default configuration (`exitIframePath` defaults to `/auth/exit-iframe`).
2. Craft the URL: `https://<app-domain>/auth/exit-iframe?exitIframe=https%3A%2F%2Fattacker.example%2Fphish&shop=any-shop.myshopify.com`
3. Send to a victim, or embed as an iframe redirect target from a Shopify admin context.
4. The app responds `200 OK` with:
   ```html
   <script data-api-key="..." src="https://cdn.shopify.com/shopifycloud/app-bridge.js"></script>
   <script>window.open("https://attacker.example/phish", "_top")</script>
   ```
   which navigates the top-level browser window to the attacker's page. [5](#0-4)

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}
