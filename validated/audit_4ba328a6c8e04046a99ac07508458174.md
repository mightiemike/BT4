### Title
Divide-before-multiply precision loss in energy/bandwidth resource-limit calculation - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
The Sherlock report flags `claim_batch()` for computing `amount_per_claim = batch.amount * release_amount / 1e18` first and then multiplying by `number_of_claims`, causing integer-division truncation that under-delivers (or zeroes out) the amount a user is entitled to. java-tron contains the same bug class in its legacy (non-hardened) resource-limit formulas, where an intermediate integer division truncates a fractional "weight" before it is multiplied by a ratio, which understates the energy/bandwidth a user is entitled to for the TRX they have frozen.

### Finding Description
In the legacy code path of `EnergyProcessor.calculateGlobalEnergyLimit()`, the energy weight is computed by dividing first and multiplying second: [1](#0-0) 
```
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
```
`frozeBalance / TRX_PRECISION` is an **integer** division that truncates any frozen balance that is not an exact multiple of `TRX_PRECISION` (1 TRX = 1,000,000 sun) — exactly the "divide then multiply" pattern described in the report (`amount_per_claim = batch.amount * release_amount / 1e18` computed before multiplying by `number_of_claims`). The identical pattern also appears in `RepositoryImpl.calculateGlobalEnergyLimit()`'s legacy branch: [2](#0-1) 
and in the analogous `scaleByRate`/`calculateGlobalLimitV2` bandwidth code in `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java` / `ResourceProcessor.java`.

The java-tron team itself has already recognized this exact bug class and written a "hardened" replacement that multiplies before dividing using `BigInteger` (`calculateGlobalLimitV2` in `ResourceProcessor.java`, guarded by `hardenResourceCalculation()`): [3](#0-2) 
and a dedicated regression test explicitly demonstrating that the legacy divide-then-multiply formula produces a different (wrong) result than the multiply-then-divide (`BigInteger`) formula: [4](#0-3) 
```
long expected = BigInteger.valueOf(10000L).multiply(...).divide(...).longValueExact();
...
long buggy = 10000L * (totalEnergyLimit / totalEnergyWeight);
Assert.assertNotEquals(buggy, resultNew);
```
This test directly proves the root cause: dividing `totalEnergyLimit / totalEnergyWeight` (or `frozeBalance / TRX_PRECISION`) before multiplying loses precision compared to multiplying first and dividing once at the end.

The corrected, multiply-first behavior is gated behind the `allowHardenResourceCalculation` flag, checked via `hardenResourceCalculation()` / `hardenCalculation()`: [5](#0-4) 
This is one of the chain-parameter flags activated only through an on-chain committee proposal (`ProposalUtil`/`ProposalService`), meaning the legacy divide-then-multiply code remains the live/default computation until/unless that proposal is passed and activated network-wide.

### Impact Explanation
This affects `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`, which determine how much energy/bandwidth an account is entitled to based on TRX they have frozen (via `FreezeBalanceV2`/staking). Truncating the fractional weight before multiplying systematically understates a legitimate user's resource entitlement whenever their frozen balance is not an exact multiple of `TRX_PRECISION` or when `totalEnergyLimit`/`totalEnergyWeight` don't divide evenly — this is an accounting/entitlement-loss issue analogous to the reported vesting bug (funds/resources users are entitled to are silently reduced due to integer truncation ordering). It does not on its own allow theft of others' funds, but represents a consistent under-delivery of value owed to unprivileged users, invoked on every transaction that consumes energy (`EnergyProcessor.useEnergy`) and in bandwidth consumption paths.

### Likelihood Explanation
The buggy path is the default/legacy computation used unless `allowHardenResourceCalculation` has been activated via governance proposal; based on the available code, no evidence in the index shows this proposal has been activated by default, so the affected formula is reachable via ordinary resource consumption by any unprivileged user with a frozen TRX balance that doesn't align cleanly with `TRX_PRECISION`/`totalEnergyWeight`, making the likelihood high whenever hardening is not yet enabled on a given network.

### Recommendation
Activate/backport the already-implemented hardened formula (`calculateGlobalLimitV1`/`calculateGlobalLimitV2` in `ResourceProcessor.java`, which multiply via `BigInteger` before dividing) as the default computation rather than leaving it opt-in behind a proposal, or expedite the governance proposal to enable `allowHardenResourceCalculation` on all networks, eliminating the legacy divide-then-multiply arithmetic in `EnergyProcessor.calculateGlobalEnergyLimit`, `EnergyProcessor.calculateGlobalEnergyLimitV2`, and the equivalent code in `RepositoryImpl.java`/`BandwidthProcessor.java`.

### Proof of Concept
Using the values from the existing repo test `RepositoryImplHardenTest.testCalculateGlobalEnergyLimitHardenedParityWithNonIntegerRatio`: [6](#0-5) 
- `totalEnergyLimit = 50_000_000_000`, `totalEnergyWeight = 1_234_567`, `frozeBalance = 10_000_000_000` (energyWeight = 10000).
- Correct (multiply-then-divide) result: `BigInteger(10000).multiply(50_000_000_000).divide(1_234_567)` = `405000004...` (exact value per test, `expected`).
- Legacy divide-then-multiply result: `10000L * (50_000_000_000L / 1_234_567L)` = `10000 * 40500` = `405000000`, which the test explicitly asserts `assertNotEquals` against the correct value — confirming the precision loss is real and reproducible with the legacy (non-hardened, currently-default) formula in `EnergyProcessor`/`RepositoryImpl`.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
```

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
```

  public void testCalculateGlobalEnergyLimitHardenedParityWithNonIntegerRatio() {

    long totalEnergyWeight = 1_234_567L;
    long frozeBalance = 10_000_000_000L;

    dbManager.getDynamicPropertiesStore().saveTotalEnergyCurrentLimit(totalEnergyLimit);
    dbManager.getDynamicPropertiesStore().saveTotalEnergyWeight(totalEnergyWeight);

    AccountCapsule account = new AccountCapsule(
        ByteString.copyFromUtf8("owner"),
        ByteString.copyFrom(ByteArray.fromHexString(
            Wallet.getAddressPreFixString() + "548794500882809695a8a687866e76d4271a1abc")),
        AccountType.Normal, 0L);
    account.setFrozenForEnergy(frozeBalance, 0L);

    VMConfig.initAllowHardenResourceCalculation(0);
    long resultOld = repository.calculateGlobalEnergyLimit(account);

    VMConfig.initAllowHardenResourceCalculation(1);
    long resultNew = repository.calculateGlobalEnergyLimit(account);

    long expected = java.math.BigInteger.valueOf(10000L)
        .multiply(java.math.BigInteger.valueOf(totalEnergyLimit))
        .divide(java.math.BigInteger.valueOf(totalEnergyWeight))

    Assert.assertEquals(expected, resultNew);
