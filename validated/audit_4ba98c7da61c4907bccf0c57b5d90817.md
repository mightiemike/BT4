### Title
DoS of OAuth callback handler via unhandled webhook-registration exceptions - (File: `packages/apps/shopify-api/lib/webhooks/register.ts`)

### Summary
The webhook registration logic used during the offline OAuth callback iterates over every registered webhook handler and issues a GraphQL mutation for each one. Any exception other than `InvalidDeliveryMethodError` is re-thrown instead of being isolated to that single handler, which bubbles all the way up through `registerWebhooks` into `authCallback`'s single try/catch, causing the whole OAuth callback to fail with a 500 response — even though the session itself was already successfully created and stored.

### Finding Description
`runMutation` in `register.ts` only tolerates one specific failure mode: [1](#0-0) 

Any other error thrown by `client.request(query)` (rate limiting/throttling, transient GraphQL/API errors, deprecated or invalid topic responses, network failures, etc.) is not caught here — it propagates out of `runMutation`, through the per-topic loop in `runMutations`, through `registerTopic`, and out of the top-level `register()` function: [2](#0-1) 

`registerWebhooks` (the `shopify-app-express` helper) does not wrap the call to `api.webhooks.register` in its own try/catch either: [3](#0-2) 

The caller, `authCallback`, invokes `registerWebhooks` for every offline OAuth completion and wraps the *entire* callback flow (session storage, webhook registration, `afterAuth` hook) in a single try/catch: [4](#0-3) 

Because the webhook handler registry (`webhookRegistry`) is a single, app-wide configuration shared by every merchant installing the app (not per-shop), a single malfunctioning/malicious webhook handler definition (e.g., an invalid callback URL that Shopify's API rejects with an unexpected error shape, a deprecated/removed topic, or persistent throttling on the webhook mutation) causes the exception to be thrown for **every shop** that goes through the offline OAuth callback, not just one merchant. This mirrors the reported bug class: one bad "adapter" (here, one bad webhook handler/topic in the shared registry) permanently breaks a shared control-flow loop (`register()`) that is invoked on every relevant transaction (here, every OAuth callback), producing a DoS of the authentication handler for the whole app rather than just the offending resource.

### Impact Explanation
If any topic in the shared webhook registry consistently triggers a non-`InvalidDeliveryMethodError` exception (e.g., due to an API-side rejection, deprecated topic, or persistent throttling), `authCallback` returns a 500 error for **every** new or re-authenticating shop, even though `callbackResponse.session` was already valid and stored. This effectively denies service to the app's install/auth flow for all merchants until the underlying issue with the single handler is resolved or the registry is changed, since the same registry and same failing mutation are executed on every offline OAuth callback.

### Likelihood Explanation
This does not require a privileged actor: any transient Shopify API behavior (rate limiting, deprecated topic response format changes, or an errant webhook config shipped by the developer) is enough to trigger the unhandled throw path, since `runMutation` only special-cases one error type. Given that `register()` runs unconditionally as part of every offline OAuth callback, the failure surface is exercised on the hot path of authentication for all shops.

### Recommendation
Isolate failures per-handler/per-topic in `runMutation`/`runMutations` (similar to how `InvalidDeliveryMethodError` is already handled) so that a single failing webhook registration is recorded as a failed `RegisterResult` rather than throwing and aborting the whole registration and OAuth callback. Additionally, `authCallback`/`registerWebhooks` should not allow a webhook-registration failure to abort session persistence and the `afterAuth` hook entirely — at minimum it should be caught and logged without failing the whole callback, since the OAuth session itself is already valid at that point.

### Proof of Concept
1. Configure the app with a webhook handler registry containing one handler whose topic/config makes Shopify's Admin GraphQL API return a non-userError failure (e.g., a throttled/5xx response, or a topic no longer supported causing `client.request` to throw).
2. Trigger the offline OAuth flow for any shop (`/auth` → Shopify consent → `/auth/callback`).
3. Observe that `api.auth.callback` succeeds and the session is stored, but `registerWebhooks` → `register()` → `runMutation` throws when processing the bad handler.
4. `authCallback`'s catch block (`packages/apps/shopify-app-express/src/auth/auth-callback.ts` lines 64-68) sends a 500 response and skips `afterAuth`, for **every** shop hitting this code path, as long as the offending handler remains in the shared registry.

async function runMutations({
  config,
  client,
  topic,
  handlers,
  operation,
}: RunMutationsParams): Promise<RegisterResult[]> {
  const registerResults: RegisterResult[] = [];

  for (const handler of handlers) {
    registerResults.push(
      await runMutation({config, client, topic, handler, operation}),
    );
  }

  return registerResults;
}
