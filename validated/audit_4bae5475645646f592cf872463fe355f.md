### Title
BitcoinLightClient.verifyInclusion falsely reports inclusion for an all-zero witness transaction ID in an unset/non-existent block - (File: `crates/evm/src/evm/system_contracts/src/BitcoinLightClient.sol`)

### Summary
`BitcoinLightClient.verifyInclusion(uint256 _blockNumber, ...)` is an unguarded, permissionless `external view` function [1](#0-0) . For a `_blockNumber` that has never been set by the system caller via `setBlockInfo` (e.g. a future height), `blockHashes[_blockNumber]` defaults to `bytes32(0)` [2](#0-1) . `_verifyInclusion` then reads `coinbaseDepths[0x0]` and `witnessRoots[0x0]`, both of which default to zero for a hash that was never recorded [3](#0-2) . With `_wtxId = bytes32(0)`, an empty `_proof`, and `_index = 0`, the call collapses into bitcoin-spv's single-transaction shortcut (`txid == merkleRoot && index==0 && proof.length==0 → true`), so `verifyInclusion` returns `true` for a block that was never observed by the light client — exactly the "zero value bypasses a downstream validity check" bug class from the referenced report, where a computed/default zero (`targetedRate`) slips past a check that assumed a meaningful non-zero value.

### Finding Description
The contract's own top-of-file warning states: *"Block hash getters returning 0 value means no such block is recorded"* [4](#0-3) . Despite this documented invariant, `verifyInclusion(uint256, bytes32, bytes, uint256)` does not check that `_blockHash != bytes32(0)` before proceeding [1](#0-0) . It forwards straight to `_verifyInclusion`, which:
1. Requires `_proof.length == coinbaseDepths[_blockHash] * HASH_LENGTH`. For an unset hash, `coinbaseDepths[_blockHash] == 0`, so this trivially passes with an empty proof.
2. Reads `witnessRoots[_blockHash]`, which is also `0` for an unset hash.
3. Calls `ValidateSPV.prove(_wtxId, _witnessRoot, _proof, _index)` [3](#0-2) .

If the caller supplies `_wtxId = bytes32(0)`, `_proof = ""`, `_index = 0`, then `_wtxId == witnessRoot (0) && _index == 0 && proof.length == 0`, which is bitcoin-spv's well-known "single coinbase-only-block" shortcut that returns `true` unconditionally. The result: the light client asserts that the zero wtxId is included in a Bitcoin block/height that the system has never even processed — i.e., a forged inclusion result for a block that does not exist in Citrea's view of Bitcoin.

This is the direct analog of the report's bug class: a value that legitimately defaults to zero in one context (unset storage) is treated by a downstream boolean check the same way a genuine, validated zero value would be (a real coinbase-only witness root), and the check does not distinguish "not yet observed" from "legitimately zero."

### Impact Explanation
This breaks the DA-integrity binding the light client is meant to enforce: *"proof of inclusion returned == transaction actually happened in a recorded Bitcoin block."* Here `verifyInclusion` returns `true` for a height Citrea has not recorded, which is a forged DA inclusion result — one of the explicitly listed Critical-impact categories. Any application or integrator on Citrea (the docs explicitly note "there are cross-chain applications that live on Citrea that may need that information" [5](#0-4) ) that trusts `LIGHT_CLIENT.verifyInclusion` as a source of truth for "this exact wtxId happened on Bitcoin at this height" can be fed a false positive using only the all-zero wtxId and an unset future block number.

Note: exploitation against the canonical `Bridge.deposit`/`replaceDeposit` paths is not practical, since those require finding a real transaction whose computed wtxId hashes to exactly zero (computationally infeasible) and are additionally gated by `onlySystemOrOperator` and a full Schnorr signature check after inclusion is checked [6](#0-5) . The exposure is specific to direct, permissionless calls to `BitcoinLightClient.verifyInclusion` itself.

### Likelihood Explanation
High for direct exploitation of the getter itself: the function is `external`, has no access modifier, and the only requirement is supplying constants (`_wtxId = 0`, `_proof = ""`, `_index = 0`) and any block number Citrea has not yet processed (trivially known, since `blockNumber` is public) [7](#0-6) . No signature, no privileged role, and no economic cost is required.

### Recommendation
In `_verifyInclusion` (and the `verifyInclusion` overloads), explicitly reject the case where `_blockHash == bytes32(0)` or where `_blockNumber >= blockNumber` before consulting `witnessRoots`/`coinbaseDepths`, so that "not yet recorded" can never be conflated with "recorded and legitimately zero."

### Proof of Concept
1. Read the current tracked height via `BitcoinLightClient.blockNumber()`; pick any `futureBlockNumber >= blockNumber` (never set by `setBlockInfo`).
2. Call `verifyInclusion(futureBlockNumber, bytes32(0), "" /* empty proof */, 0)`.
3. Observe the call returns `true`, even though no block has ever been recorded at `futureBlockNumber` and `coinbaseDepths`/`witnessRoots` for that (zero) block hash were never set by the system caller — a forged inclusion proof for a non-existent block. [8](#0-7)

```text
    /// @notice Verifies the inclusion of a transaction ID in the merkle root hash of a block
    /// @dev Transaction ID and proof elements must be in little endian
    /// @param _blockNumber Block number of the block
    /// @param _txId Transaction ID
    /// @param _blockHeader Block header of the associated Bitcoin block
    /// @param _proof Merkle proof
    /// @param _index Index of the transaction
    /// @return If the transaction ID is included in the merkle root hash of the block
    function verifyInclusionByTxId(uint256 _blockNumber, bytes32 _txId, bytes calldata _blockHeader, bytes calldata _proof, uint256 _index) external view returns (bool) {
        bytes32 _blockHash = _blockHeader.hash256View();
        require(blockHashes[_blockNumber] == _blockHash, "Invalid block header");
        require(_proof.length == coinbaseDepths[_blockHash] * HASH_LENGTH, "Invalid proof length");
        bytes32 _txRoot = _blockHeader.extractMerkleRootLE();
        return ValidateSPV.prove(_txId, _txRoot, _proof, _index);
    }

    function _verifyInclusion(bytes32 _blockHash, bytes32 _wtxId, bytes calldata _proof, uint256 _index) internal view returns (bool) {
        require(_proof.length == coinbaseDepths[_blockHash] * HASH_LENGTH, "Invalid proof length");
        bytes32 _witnessRoot = witnessRoots[_blockHash];
        return ValidateSPV.prove(_wtxId, _witnessRoot, _proof, _index);
    }
```

```markdown
Bitcoin's SegWit upgrade moved some of the data that would regularly be in input data to another field called witness, and this resulted in another type of transaction ID called the witness transaction ID. As you may expect, this is the hash of the full transaction hex including both the witness field and the legacy fields, and `_witnessRoot` is the root of the Merkle tree constructed from the witness transaction IDs of transactions. 

Transaction IDs are unique, so why did we choose the witness root instead of the regular root? Firstly, anyone who wishes to prove the inclusion of a transaction through its regular ID can do so by proving the full header, as the block hash is also written; this can be verified since the block hash is the hash of the header. But more importantly, the regular root gives us less information as we cannot know about the witness fields of the transactions. The Bridge needs to know about the witness field of the transactions it verifies, and there are cross-chain applications that live on Citrea that may need that information.
```
