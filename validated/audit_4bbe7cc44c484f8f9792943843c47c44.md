This is an analog to the Rocketpool "unsanitized data inserted into a template string, allowing delimiter escape" bug class, found in `MsgExecutePayload`'s `UniversalAccountId.GetCAIP2()`.

### Title
Unvalidated `:` delimiter in `UniversalAccountId.ChainNamespace`/`ChainId` allows CAIP-2 identity/chain-config collision in `MsgExecutePayload` - (File: `x/uexecutor/types/universal_account_id.go`)

### Summary
`UniversalAccountId.GetCAIP2()` builds the CAIP-2 chain identifier with `fmt.Sprintf("%s:%s", p.ChainNamespace, p.ChainId)` [1](#0-0)  and `ValidateBasic()` only trims whitespace and checks non-emptiness — it never rejects `:` (or other delimiter characters) inside `ChainNamespace`/`ChainId` [2](#0-1) . This is the same bug class as the Rocketpool report: attacker-controlled fields are concatenated into a delimiter-separated template string used downstream for routing/lookup, without stripping or rejecting the delimiter itself.

### Finding Description
`MsgExecutePayload` is a fully gasless, unprivileged, user-submittable message — any account may submit it [3](#0-2) . Its `UniversalAccountId` field (`ChainNamespace`, `ChainId`, `Owner`) is taken directly from the message body [4](#0-3)  and passes only `ValidateBasic()` before being used [5](#0-4) .

In `ExecutePayload`, the derived CAIP-2 string is used as the direct lookup key into the chain registry (`uregistryKeeper.GetChainConfig`) that decides whether the chain is enabled, its gas token, and other chain-specific semantics [6](#0-5) . Because `GetCAIP2()` does no delimiter-safe encoding (unlike the deliberately delimiter-safe `hashFields` helper elsewhere in the codebase, which per-field-hashes precisely "so a sub-hash can't contain ':' … no field value can shift a boundary and collide with a different tuple" [7](#0-6) ), an attacker can submit `ChainNamespace = "eip155:1"`, `ChainId = "extra"`, producing `"eip155:1:extra"`, or conversely craft namespace/id pairs whose concatenation collides with a different legitimate (namespace, id) tuple's CAIP-2 string.

### Impact Explanation
A collision in the CAIP-2 identifier changes which `ChainConfig`/`TokenConfig` row is used to gate and account for the payload execution (enabled/disabled inbound flag, gas token, chain-specific behavior) — this falls under the "Registry and accounting path" invariant: chain config, token config, and gas-token selection "must not misroute value or attach the wrong asset semantics." At minimum this can let an attacker force `ExecutePayload` to be evaluated against an unintended chain's config (e.g., bypassing a disabled-chain gate, or acquiring a different gas-token/PRC20 mapping than the one that should apply to the attacker's actual claimed origin chain). The `UniversalAccountId` also feeds the UEA-address derivation via `CallFactoryToGetUEAAddressForOrigin`/`DeployUEAV2` [8](#0-7) , so a crafted namespace/id pair could in principle steer UEA/account derivation toward an unintended identity space, though final authorization is still gated by the UEA contract's stored owner-key signature check documented in the README [9](#0-8) , which limits the worst-case fund-theft impact.

### Likelihood Explanation
High reachability: the message is public, gasless, and requires no special role — a bare `MsgExecutePayload` with a crafted `UniversalAccountId` triggers the vulnerable code path directly. However, exploitation requires that a registry entry actually exists whose CAIP-2 key can be produced through a colliding namespace/id split, and the practical value of the collision is currently limited by the downstream contract-level signature check, so real material impact depends on registry contents and further code paths (e.g., DeployUEAV2/factory address derivation) that were not fully traced in this session.

### Recommendation
Reject `:` (and other CAIP-2 reserved characters) in `ChainNamespace` and `ChainId` inside `UniversalAccountId.ValidateBasic()`, or construct `GetCAIP2()` using a collision-resistant encoding (length-prefixed or per-field-hashed, mirroring `hashFields` in `x/uexecutor/types/keys.go`) instead of naive `fmt.Sprintf("%s:%s", …)` concatenation.

### Proof of Concept
1. Submit `MsgExecutePayload` with `UniversalAccountId{ChainNamespace: "eip155:1", ChainId: "extra", Owner: <valid hex>}`.
2. `ValidateBasic()` passes (both fields non-empty, owner is valid hex).
3. `GetCAIP2()` returns `"eip155:1:extra"`, identical to what a legitimate `UniversalAccountId{ChainNamespace: "eip155", ChainId: "1:extra"}` (or other splits) would produce.
4. `k.uregistryKeeper.GetChainConfig(sdkCtx, "eip155:1:extra")` is looked up using the attacker-chosen split rather than a canonical, unambiguous chain identity, demonstrating the registry key is not injective over attacker input.

**Note:** I was unable to fully confirm whether any currently-configured registry entries make this collision produce a materially different (enabled vs. disabled, or different gas-token) outcome, since `uregistry` config contents are chain-deployment-specific data not fully covered by the indexed code. A Devin session with full repo/config access would be needed to enumerate real `ChainConfig`/`TokenConfig` entries and confirm an end-to-end misrouting proof.

```markdown
### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
```

```markdown
#### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**

#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
```

```go
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	// Get Caip2Identifier for the universal account
	caip2Identifier := universalAccountId.GetCAIP2()

		"from", evmFrom.Hex(),
		"chain", caip2Identifier,
		"owner", universalAccountId.Owner,
	)

	if _, err := types.NewAbiUniversalPayload(universalPayload); err != nil {

		return errors.Wrapf(err, "invalid verificationData format")

	if err != nil {
		return errors.Wrapf(err, "failed to get chain config for chain %s", caip2Identifier)
	}

	if !chainConfig.Enabled.IsInboundEnabled {
		k.Logger().Warn("execute payload rejected: chain inbound disabled", "chain", caip2Identifier)
		return fmt.Errorf("inbound is disabled for chain %s", caip2Identifier)
	}
```

```go
// hashFields = sha256( hex(sha256(domain)) : hex(sha256(f0)) : ... ). Per-field
// hashing makes it injective — a sub-hash can't contain ':', so no field value
// can shift a boundary and collide with a different tuple.
func hashFields(domain collections.Prefix, parts ...string) string {
	hashed := make([]string, 0, len(parts)+1)
	d := sha256.Sum256(domain.Bytes())
	hashed = append(hashed, hex.EncodeToString(d[:]))
	for _, p := range parts {
		sum := sha256.Sum256([]byte(p))
		hashed = append(hashed, hex.EncodeToString(sum[:]))
	}
	final := sha256.Sum256([]byte(strings.Join(hashed, ":")))
	return hex.EncodeToString(final[:])
}
```
