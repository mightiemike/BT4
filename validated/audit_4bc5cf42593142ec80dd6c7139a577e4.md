## Analog Found

### Title
Attacker-chosen `TxType` selects a shallow FAST confirmation depth for fund-carrying inbound deposits, enabling reorg-driven unauthorized PRC20/native mint - (File: universalClient/chains/evm/event_parser.go)

### Summary
The external report is about `MysteryBox.sol` using too few VRF block confirmations (`REQUEST_CONFIRMATIONS = 3`), letting a chain reorg change the randomness outcome after the request was already considered final. The Push Chain analog is the inbound event confirmation-depth selection in the Universal Client: the confirmation tier (`FAST` vs `STANDARD`) used before a deposit event is voted into finality is chosen from a field (`TxType`) that is fully controlled by the caller of the source-chain gateway contract, not derived from anything security-relevant like deposit amount. This lets an unprivileged depositor deliberately pick the shallow, 5-block `FAST` tier for a transaction that still carries a real `token`/`amount` payload, instead of the deeper 12-block `STANDARD` tier, reducing the reorg-resistance margin before Push Chain treats the deposit as final and mints corresponding value.

### Finding Description
`finalizeEvent` in `universalClient/chains/evm/event_parser.go` sets the event's `ConfirmationType` purely from the attacker-supplied `TxType` word emitted in the gateway event data: [1](#0-0) 

The same amount/token parsing happens unconditionally before this branch, regardless of `TxType`: [2](#0-1) 

`TxType` values 0 (`GAS`) and 1 (`GAS_AND_PAYLOAD`) map to `FAST`; everything else maps to `STANDARD`: [3](#0-2) 

The SVM parser has the identical attacker-selectable split: [4](#0-3) 

`FAST` requires only 5 confirmations by default versus `STANDARD`'s 12 (both defined in registry config and defaulted in code): [5](#0-4) [6](#0-5) 

The `EventConfirmer` promotes an event straight to `CONFIRMED` — the state that triggers `VoteInbound` — as soon as `confirmations >= requiredConfirmations`: [7](#0-6) 

Once 2/3+ honest Universal Validators vote the same (already-shallow-confirmed) observation, `VoteInbound` finalizes the ballot and creates the `UniversalTx`, which drives the mint/payload execution on Push Chain: [8](#0-7) 

Because `TxType` is a parameter the depositor supplies directly when calling the source-chain gateway (it is not inferred from deposit size or any risk classification), an ordinary user — without any validator or node compromise — can deliberately pick `GAS`/`GAS_AND_PAYLOAD` for a transaction that still moves real funds, forcing the Universal Client to apply the 5-block tier instead of the 12-block tier that would otherwise apply to a `FUNDS`/`FUNDS_AND_PAYLOAD` deposit of the same value.

### Impact Explanation
If the source chain later reorgs deeper than the FAST threshold (5 blocks) but shallower than the STANDARD threshold (12 blocks) — a materially more probable depth on most EVM/SVM chains than a 12+ block reorg — the deposit transaction that funded the mint disappears from the source chain's canonical history after Push Chain has already minted the corresponding PRC20/native representation and possibly executed the user's payload. This is an unauthorized/unbacked mint of protocol-controlled value: Push Chain's accounting now reflects tokens that were never actually locked/transferred on the source chain, corrupting PRC20 accounting and the vault-backing invariant. This falls squarely under "unauthorized mint... of user or protocol-controlled funds" and "corruption of PRC20 or native asset accounting" in the allowed impact gate, triggered purely by an unprivileged user's transaction shape and ordinary chain instability — no malicious validator or node assumption is required.

### Likelihood Explanation
The trigger is entirely within an unprivileged user's control (they choose `TxType` in their own gateway call) and requires no cooperation from validators, relayers, or admins — only a naturally occurring reorg between 5 and 12 blocks deep on the source chain, which is a realistic (if not frequent) event on many EVM L2s/sidechains and even mainnets during network stress, exactly the scenario the original report highlights for Polygon. Likelihood is moderate: it depends on reorg depth and timing, but the attacker fully controls the "which tier applies" decision, which is the crux of the analog.

### Recommendation
Do not let the caller-supplied `TxType` alone determine confirmation depth when the event still carries a non-zero `token`/`amount`. Either (a) force `STANDARD` confirmations whenever `amount > 0` regardless of `TxType`, reserving `FAST` strictly for zero-value/gas-only observations, or (b) tie the confirmation tier to a value threshold configured in `uregistry` rather than to an attacker-controlled enum, mirroring the recommended fix of raising `REQUEST_CONFIRMATIONS` to a safe, non-attacker-selectable depth in the original report.

### Proof of Concept
1. Attacker calls the source-chain gateway's `sendFunds`/equivalent method with `TxType = 0` (`GAS`) or `1` (`GAS_AND_PAYLOAD`), but still populates `token`/`amount` with a real deposit value (nothing in the ABI/event layout prevents this — the parser reads `token`/`amount` unconditionally before branching on `TxType`, per `universalClient/chains/evm/event_parser.go:169-174` and `227-240`).
2. The Universal Client tags the resulting `store.Event` with `ConfirmationType = FAST`, requiring only 5 confirmations (`universalClient/chains/evm/event_confirmer.go:248-267`).
3. After 5 blocks, honest Universal Validators observe the event as `CONFIRMED` and vote it via `MsgVoteInbound`; once 2/3+ agree, `VoteInbound` finalizes the ballot and Push Chain mints the corresponding PRC20/native asset (`x/uexecutor/keeper/msg_vote_inbound.go:75-87`).
4. A reorg of depth 6-11 blocks on the source chain (below `STANDARD`'s 12-block threshold, which would have prevented finalization at this point) removes the original deposit transaction from the canonical chain.
5. Push Chain's mint is now unbacked by any real source-chain funds — an unauthorized/unbacked mint that persists as canonical state.

Note: I could not fully verify from the indexed code whether any additional amount cap or value-based routing exists specifically for `TxType_GAS`/`GAS_AND_PAYLOAD` at the contract level (outside this repo's scope) that might independently bound the exploitable amount; this would need to be checked in the gateway/vault Solidity contracts, which are not part of this repository.

```go
// finalizeEvent marshals the payload and sets confirmation type on the event.
func finalizeEvent(event *store.Event, payload *common.UniversalTx, logger zerolog.Logger) {
	if b, err := json.Marshal(payload); err == nil {
		event.EventData = b
	} else {
		logger.Warn().Err(err).Msg("failed to marshal universal tx payload")
	}

	if payload.TxType == 0 || payload.TxType == 1 {
		event.ConfirmationType = store.ConfirmationFast
	} else {
		event.ConfirmationType = store.ConfirmationStandard
	}
}
```

```go
// getRequiredConfirmations returns the required number of confirmations based on confirmation type
func (ec *EventConfirmer) getRequiredConfirmations(confirmationType string) uint64 {
	switch confirmationType {
	case store.ConfirmationFast:
		if ec.fastConfirmations >= 0 {
			return ec.fastConfirmations
		}
		return 5
	case store.ConfirmationStandard:
		if ec.standardConfirmations >= 0 {
			return ec.standardConfirmations
		}
		return 12
	default:
		// Default to standard if unknown
		if ec.standardConfirmations >= 0 {
			return ec.standardConfirmations
		}
		return 12
	}
```

```go
// GetStandardConfirmations returns the chain's standard block confirmations from registry config (BlockConfirmation.StandardInbound). Used for outbound tx completion. Returns 12 if not set.
func (c *Chains) GetStandardConfirmations(chainID string) uint64 {
	c.chainsMu.RLock()
	cfg := c.chainConfigs[chainID]
	c.chainsMu.RUnlock()
	if cfg != nil && cfg.BlockConfirmation != nil && cfg.BlockConfirmation.StandardInbound > 0 {
		return uint64(cfg.BlockConfirmation.StandardInbound)
	}
	return 12
}
```
