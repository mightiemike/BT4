### Title
Unbounded `ExchangeStore.getAllExchanges()` sort in `ListExchanges` RPC/HTTP endpoint enables state-scaling CPU DoS - ([File: chainbase/src/main/java/org/tron/core/store/ExchangeStore.java])

### Summary
`ExchangeStore.getAllExchanges()` streams and sorts every stored `Exchange` record with no size limit, and this method is reached directly by the unauthenticated `ListExchanges` gRPC RPC (`RpcApiService.listExchanges`) and the `/wallet/listexchanges` HTTP endpoint (`ListExchangesServlet`) via `Wallet.getExchangeList()`. Because exchange records are attacker-creatable (`ExchangeCreateActuator`), an attacker can grow `n` and force every future `ListExchanges` call — by anyone — to pay O(n log n) CPU cost that is not covered by bandwidth/energy metering on the read path.

A paginated alternative (`GetPaginatedExchangeList` / `Wallet.getPaginatedExchangeList`) exists and is capped by `EXCHANGE_COUNT_LIMIT_MAX`, but the unpaginated `ListExchanges` API remains reachable and unbounded: [7](#0-6) 

The request-level defense (`RateLimiterServlet` / `GlobalRateLimiter`) only throttles the *rate* of admitted requests (QPS-based, per-IP and global); it performs no per-request cost accounting and does not scale limits with attacker-controlled state size: [8](#0-7) [9](#0-8) 
Each admitted call still pays full O(n log n) iteration+sort cost, so as `n` (attacker-created exchanges) grows, every legitimately rate-limited call becomes proportionally more expensive, unlike normal transaction execution which is metered by bandwidth/energy.

### Impact Explanation
This falls under "DoS via RPC-API": a single unprivileged actor can permanently inflate the cost of a public read API for all clients (including other full nodes' HTTP/gRPC front ends and any process consuming `/wallet/listexchanges` or `ListExchanges`), causing elevated latency/CPU load on full nodes each time the endpoint is called, in proportion to attacker-created exchange records. The impact is a resource-exhaustion/availability issue on the query path, not a consensus-state or fund-safety issue — the created `Exchange` records themselves are legitimate chain state, not corrupted data.

### Likelihood Explanation
- Preconditions: attacker needs a funded account and must broadcast N `ExchangeCreateContract` transactions, each burning `EXCHANGE_CREATE_FEE` (default 1024 TRX) plus depositing >0 balance of two distinct tokens. This is a real, non-trivial, and non-recoverable economic cost (e.g., 50k exchanges ≈ 51.2M TRX burned), which strongly limits practical feasibility at large N; a determined/well-funded attacker could still create a moderate N (e.g., thousands) at lower but still real cost.
- The query itself requires no authentication and is protected only by QPS-style rate limiting, not by query-size/cost limiting, so once state is inflated the amplification (repeated O(n log n) work per call, by anyone) is real and repeatable indefinitely without further cost to the attacker (or any other caller).
- The same unbounded-list pattern is not unique to Exchange in this codebase (e.g., `getAssetIssueList`), suggesting this is a broader, known design tradeoff rather than an isolated defect, which somewhat reduces novelty/severity but does not eliminate the DoS potential of the specific `ListExchanges` path highlighted here.

### Recommendation
- Deprecate/cap the unpaginated `ListExchanges` (`Wallet.getExchangeList`) RPC/HTTP path: enforce a maximum returned/scanned record count (mirroring `EXCHANGE_COUNT_LIMIT_MAX` used by `getPaginatedExchangeList`), or make it internally delegate to a bounded/paginated implementation.
- Avoid full-collection sort in `ExchangeStore.getAllExchanges()`; maintain exchanges pre-sorted by creation order (e.g., using an incrementing exchange ID as the natural DB key ordering, since `createDbKey()` is already derived from `id`), removing the need for an O(n log n) sort at query time.
- Consider a per-endpoint cost-aware rate limiter (already partially supported via `RateLimiterContainer`/`IRateLimiter` adapters) that scales allowed QPS down as the underlying store size grows, or add a hard maximum record count constant enforced in `ExchangeCreateActuator.validate()` for total live exchanges.

  int n = 50_000;

  }

  long start = System.nanoTime();
  List<ExchangeCapsule> all = chainBaseManager.getExchangeStore().getAllExchanges();
  long elapsed = System.nanoTime() - start;

  // Repeat with n/10 records and assert elapsed time for n does not scale ~linearly

  public ExchangeList getPaginatedExchangeList(long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestExchangeNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestExchangeNum();
    if (latestExchangeNum <= offset) {
      return null;
    }
    limit =
        limit > EXCHANGE_COUNT_LIMIT_MAX ? EXCHANGE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestExchangeNum ? latestExchangeNum : end;

    ExchangeList.Builder builder = ExchangeList.newBuilder();
    ImmutableList<Long> rangeList = ContiguousSet
        .create(Range.openClosed(offset, end), DiscreteDomain.longs())
        .asList();
    rangeList.stream().map(ExchangeCapsule::calculateDbKey).map(key -> {
      try {
        return getExchangeStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getExchangeStore(),
            chainBaseManager.getExchangeV2Store()).get(key);
      } catch (Exception ex) {
        return null;
      }
    }).filter(Objects::nonNull)
        .forEach(exchangeCapsule -> builder
            .addExchanges(exchangeCapsule.getInstance()));
    return builder.build();

  }
