### Title
First Nakamoto `TenureChangePayload.previous_tenure_end` accepted without verifying the referenced epoch2 block is on the canonical burnchain fork - (File: stackslib/src/chainstate/nakamoto/tenure.rs)

### Summary
`check_first_nakamoto_tenure_change` resolves `previous_tenure_end` purely via a raw local header lookup (`Self::get_block_header`) and never calls the canonical-fork check (`check_valid_consensus_hash` / `SortitionDB::get_block_snapshot_for_winning_stacks_block`) that is used elsewhere in this same file for consensus-hash validation. This lets the function accept an epoch2 header that is locally known but resides on a stale/orphaned epoch2 fork, rather than requiring it to be the canonical epoch2 tip that every node must agree on.

### Finding Description
The equality that must hold is: `previous_tenure_end` (and thus `prev_tenure_consensus_hash`) must resolve to the globally-canonical epoch2 chain tip — the same epoch2 block every honest node identifies as the terminal epoch2 block via the canonical burnchain/sortition fork. Instead, the code only guarantees: `previous_tenure_end` resolves to *some* header that exists in this node's local `nakamoto_block_headers`/`block_headers` table.

Concretely, in `check_first_nakamoto_tenure_change` (stackslib/src/chainstate/nakamoto/tenure.rs:553-611): [1](#0-0) 
`Self::get_block_header` is a pure keyed lookup by `StacksBlockId` against the local headers table — it does not consult the `SortitionDB` at all, and in particular does not call `check_valid_consensus_hash` (defined immediately afterward in the same file, stackslib/src/chainstate/nakamoto/tenure.rs:617-637) which is the function this codebase uses elsewhere to confirm a consensus hash sits on the canonical sortition fork via `SortitionDB::get_block_snapshot_consensus` + `sort_handle.get_block_snapshot_by_height`.

The subsequent checks (`previous_tenure_blocks == 1`, `prev_tenure_consensus_hash == parent_header.consensus_hash`, and `parent_header.anchored_header.as_stacks_epoch2()`) all operate on whatever header `get_block_header` returned — none of them re-derive or check canonicality against the sortition history. If a node has ever locally stored an epoch2 header belonging to a fork that was subsequently orphaned by a burnchain reorg (headers are not deleted from the chainstate DB when a burnchain fork is abandoned), `get_block_header` will still return it, and `check_first_nakamoto_tenure_change` will happily synthesize a `last_epoch2_tenure` from it and return `Ok(Some(...))`, treating it as valid.

### Impact Explanation
If the first-ever Nakamoto tenure-change is accepted with `previous_tenure_end` pointing at a non-canonical epoch2 tip, different honest nodes that stored different epoch2 forks locally would bootstrap Nakamoto genesis state from different parent state roots. This is a Critical-class issue matching "a non-reproducible state root" / "chain split": nodes would diverge on the very first Nakamoto block's parent linkage and MARF root, producing an unrecoverable chain split at the epoch2→epoch3 boundary.

### Likelihood Explanation
Exploitability is bounded by whether a node can actually have a locally-stored, non-canonical epoch2 header reachable at the exact `StacksBlockId` an attacker would need to reference, and whether the caller of `check_first_nakamoto_tenure_change` (a function not fully inspected due to iteration limits) performs an equivalent canonical check before or after invoking it. I was not able to fully trace the calling function (`check_tenure_tx` / the code beginning at stackslib/src/chainstate/nakamoto/tenure.rs:639 was cut off) to confirm or rule out a redundant canonical check performed on `tenure_payload.previous_tenure_end`'s underlying consensus hash elsewhere in the validation pipeline. This is a material gap in my verification.

### Recommendation
Inside `check_first_nakamoto_tenure_change`, after resolving `parent_header`, explicitly verify that `parent_header.consensus_hash` is on the canonical sortition fork by calling `Self::check_valid_consensus_hash` (or `SortitionDB::get_block_snapshot_for_winning_stacks_block`) against the `SortitionHandle`, and reject the tenure-change if the snapshot is missing or non-canonical — mirroring the guard already implemented for the non-first-tenure case.

### Proof of Concept
Integration test plan:
1. Build a two-fork epoch2 burnchain harness where fork A produces epoch2 block `H_A` (canonical) and fork B produces epoch2 block `H_B` (processed by the node at some point, then orphaned when fork A becomes canonical via a deeper burnchain reorg). Both headers remain in `StacksChainState`'s local headers table.
2. Craft a first Nakamoto `TenureChangePayload` with `previous_tenure_end = StacksBlockId(H_B)` and `prev_tenure_consensus_hash = H_B.consensus_hash`.
3. Call `NakamotoChainState::check_first_nakamoto_tenure_change` directly (or via full block validation) and assert it currently returns `Ok(Some(_))` (bug) instead of `Ok(None)`.
4. Assert, on the fix, that after adding the canonical check, the same payload is rejected with `Ok(None)`, while a payload referencing `H_A` (canonical) is accepted.
5. Extend to a two-node network test where node 1 only ever saw fork A and node 2 saw both forks; confirm both must reject anything but the canonical tip, preventing divergent Nakamoto genesis roots.
