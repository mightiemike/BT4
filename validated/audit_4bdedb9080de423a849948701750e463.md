### Title
Reflected XSS via unsanitized session token echoed in `InvalidJwtError` message sent through `res.send(error.message)` - ([File: packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts])

### Summary
`decodeSessionToken` embeds the raw, attacker-controlled Bearer token directly into the `InvalidJwtError` message without sanitization. When that error propagates up through `getCurrentSessionId` in `validateWithAuthCodeFlow`, it is caught and passed unmodified to `res.send(error.message)`, which Express serves as `text/html` by default, allowing an attacker-controlled token value containing HTML/script to be reflected into the HTTP response.

### Finding Description
`decodeSessionToken` catches any JWT verification failure and re-throws with the raw token spliced into the message string: `Failed to parse session token '${token}': ${error.message}` [1](#0-0) . This function is invoked from `getCurrentSessionId` with the Bearer token taken directly from the `Authorization` header [2](#0-1) , with no sanitization of the token contents. Any malformed JWT (e.g., wrong signature, garbage payload) causes `jose.jwtVerify` to fail, which triggers the catch block and embeds the full raw token into the thrown `InvalidJwtError`.

In the Express middleware, `validateWithAuthCodeFlow` calls `api.session.getCurrentId(...)`, and any thrown error (including `InvalidJwtError` from `decodeSessionToken`) is caught and forwarded to `handleSessionError` [3](#0-2) . `handleSessionError` then calls `res.status(401); res.send(error.message);` for `InvalidJwtError` instances [4](#0-3) .

Express's `res.send(string)` sets `Content-Type: text/html` by default if no content type has been explicitly set beforehand, which is the case here (no `res.type()`/`res.set('Content-Type', ...)` call precedes it). This means a crafted Bearer token, such as `<script>alert(document.domain)</script>`, sent as an `Authorization: Bearer <script>...</script>` header on any request that reaches `validateAuthenticatedSession` in the non-token-exchange path, results in that raw string being reflected verbatim into the HTML response body — a classic reflected XSS pattern, since the attacker fully controls the injected content and no encoding/escaping occurs anywhere along the path.

### Impact Explanation
This is a reflected XSS in an authentication-checking middleware endpoint of apps built with `@shopify/shopify-app-express`. Since the payload is attacker-supplied and reflected without escaping into an HTML response, an attacker could craft a link/request (e.g., via a merchant's browser making a request with a malicious `Authorization` header set by attacker-controlled JS or a crafted fetch call from a compromised context) causing script execution in the context of the merchant's session against the app's origin. This corresponds to a reflected XSS / content-injection weakness in the authentication handler, falling into an information-disclosure / injection impact class rather than a full session-forgery bypass.

### Likelihood Explanation
The `Authorization: Bearer` header is fully attacker-controlled on any unauthenticated request to an endpoint protected only by `validateAuthenticatedSession` with the legacy Auth Code flow (`useTokenExchange` disabled/not applicable). No secrets or privileged access are required — any anonymous HTTP client can set this header and trigger `InvalidJwtError`. The main precondition is that the app does not use `future.tokenExchange`, which is the non-default legacy path but is still commonly deployed. Because browsers/JS clients typically don't allow attacker-injected raw HTML into request headers to be reflected via typical browser XSS delivery (this generally requires the "attacker" to control a request performed on the victim's behalf, e.g., via CSRF-like flows or a malicious script running same-origin), practical browser-based exploitation is limited, but the reflected, unsanitized echo of attacker input into an HTML response is a genuine and reproducible bug in this code path.

### Recommendation
- Do not include the raw token value in error messages that can be surfaced to HTTP responses; log the raw token server-side only (with redaction) and use a generic error message such as `'Failed to parse session token: invalid signature'` for the thrown `InvalidJwtError`.
- In `handleSessionError` (and any other caller sending `error.message` to clients), explicitly set `Content-Type: application/json` (or `text/plain`) and encode the message, rather than relying on Express's default `text/html` content type for `res.send(string)`.

### Proof of Concept
```ts
// packages/apps/shopify-app-express/src/middlewares/__tests__/validate-authenticated-session.xss.test.ts
import request from 'supertest';
import express from 'express';
import {validateAuthenticatedSession} from '../validate-authenticated-session';
// ... construct app/api/config per existing test setup in validate-authenticated-session.test.ts

it('reflects raw bearer token content unsanitized on invalid JWT', async () => {
  const maliciousToken = '<script>alert(document.domain)</script>';

  const res = await request(app)
    .get('/protected')
    .set('Authorization', `Bearer ${maliciousToken}`);

  expect(res.status).toBe(401);
  // Content-Type defaults to text/html because res.send(error.message) is used
  expect(res.headers['content-type']).toMatch(/text\/html/);
  // The raw script tag is reflected unescaped into the body
  expect(res.text).toContain('<script>alert(document.domain)</script>');
});
```
Expected (vulnerable) result: the response body contains the literal `<script>` payload with `Content-Type: text/html`, confirming the token content is echoed unsanitized through `decodeSessionToken`'s `InvalidJwtError` message and `handleSessionError`'s `res.send(error.message)`.

function handleSessionError(_req: Request, res: Response, error: Error) {
  switch (true) {
    case error instanceof InvalidJwtError:
      res.status(401);
      res.send(error.message);
      break;
    default:
      res.status(500);
      res.send(error.message);
      break;
  }
}
