### Title
Denial of `SystemInstruction::CreateAccount` via lamport pre-funding front-run - (File: `programs/system/src/system_processor.rs`)

### Summary
The system program's `create_account` helper rejects account creation whenever the destination account already holds a positive lamport balance, regardless of who put the lamports there. Since an ordinary, unprivileged transaction can transfer lamports to *any* pubkey without needing that pubkey's signature, an attacker can front-run a legitimate `CreateAccount` instruction by sending a trivial amount of lamports (even 1 lamport) to the target address, causing the victim's account-creation transaction to fail with `AccountAlreadyInUse`. This mirrors the Vader "Vests can be denied" bug class: a state-guard (`amount == 0` / `lamports == 0`) that gates a one-time initialization can be pre-empted by a griefer to deny the legitimate first-write.

### Finding Description
`create_account` in the System program bails out solely on the destination account's lamport balance: [1](#0-0) 

Because `SystemInstruction::Transfer` lets anyone credit lamports to an arbitrary pubkey without that pubkey signing, an attacker who observes (or predicts) the address that will be used in an upcoming `CreateAccount` instruction (e.g., a freshly generated nonce/stake/escrow keypair address referenced in an unconfirmed or not-yet-broadcast transaction, or a deterministically-derived `create_with_seed`/PDA-style address) can submit a cheap transfer of 1 lamport to that address first. When the victim's `CreateAccount` instruction is later processed, `to.get_lamports() > 0` is true, and the instruction returns `SystemError::AccountAlreadyInUse`, reverting the victim's transaction. Unit tests confirm this exact behavior is by design for the classic `CreateAccount` path — an account with any lamports and no data still fails: [2](#0-1) 

Notably, the codebase already has a purpose-built mitigation instruction, `SystemInstruction::CreateAccountAllowPrefund`, whose tests explicitly distinguish "account already has data" or "already owned by another program" (still rejected) from a merely pre-funded, empty, system-owned account (which this variant is designed to tolerate): [3](#0-2) 

The existence of `CreateAccountAllowPrefund` as a separate, newer instruction confirms that plain `CreateAccount` remains susceptible to lamport-prefund griefing, and that callers must opt in to the safer variant to avoid it.

### Impact Explanation
Any unprivileged actor observing a target address destined for `CreateAccount` (durable nonce accounts, stake accounts, or any program's CPI-driven account initialization that still uses the plain `CreateAccount` instruction rather than `CreateAccountAllowPrefund`) can grief that specific creation deterministically and cheaply, causing the victim's transaction to fail (and its transaction fee to still be charged, since fees are deducted on signature verification regardless of execution outcome). This is a reliable, repeatable denial-of-service against a specific unprivileged flow, but it does not cause fund theft, lamport inflation, double-spend, CPI privilege escalation, or consensus divergence — it is bounded to griefing/DoS of account initialization for callers who haven't migrated to `CreateAccountAllowPrefund`.

### Likelihood Explanation
High for any caller/program still relying on plain `CreateAccount` for addresses whose pubkeys are known or predictable ahead of confirmation (e.g., addresses embedded in an offline-signed or nonce transaction, or seed-derived addresses). The attack requires only a single, cheap `Transfer` instruction and no special privileges, matching the "unprivileged-sender" scope. Programs/callers that have already switched to `CreateAccountAllowPrefund` are unaffected.

### Recommendation
Ensure all first-party flows requiring account creation prefer `SystemInstruction::CreateAccountAllowPrefund` over plain `CreateAccount` when the destination address may be publicly derivable/predictable before confirmation, since that variant already treats a merely lamport-funded, empty, system-owned account as an acceptable base for initialization rather than rejecting it outright.

### Proof of Concept
1. Victim intends to submit `CreateAccount(from=payer, to=new_account, lamports, space, owner)` where `new_account` is a freshly generated keypair or seed-derived address whose pubkey is visible before the transaction lands (e.g., broadcast but unconfirmed, or a durable-nonce transaction signed offline and held).
2. Attacker submits `SystemInstruction::Transfer { lamports: 1 }` to `new_account` — no signature from `new_account` is required, only from the sender of the 1 lamport.
3. Once the attacker's transfer lands first, `new_account.lamports() > 0`.
4. The victim's `CreateAccount` instruction executes `create_account` at [4](#0-3)  which now returns `SystemError::AccountAlreadyInUse`, failing the victim's entire transaction (fee still charged) and denying the intended account initialization.
