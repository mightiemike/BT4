### Title
Missing Early Return in `validate_delegate_action_key` Causes Nonce Consumption on Failed Delegate Actions and Wrong Error Reporting - (`File: runtime/runtime/src/actions.rs`)

### Summary

In `validate_delegate_action_key`, when a `DelegateAction` using a `FunctionCall`-restricted access key carries a non-zero deposit, the function correctly sets `result.result = Err(DepositWithFunctionCall)` but — before `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError` is enabled — **does not return early**. Execution falls through to the `receiver_id` and `method_name` checks. If those checks pass, the function reaches the unconditional nonce-update block and **commits the incremented nonce to the trie** before returning. The caller (`apply_delegate_action`) then sees `result.result.is_err()` and skips receipt creation. The net result is: the sender's access-key nonce is permanently consumed, no action executes, and the error surfaced to the user may be wrong.

### Finding Description

`validate_delegate_action_key` (`runtime/runtime/src/actions.rs:535`) validates the access key used to sign a `DelegateAction`. For a `FunctionCall`-restricted key the function checks, in order:

1. `deposit > 0` → sets `Err(DepositWithFunctionCall)` — **no early return** (pre-fix)
2. `receiver_id` mismatch → sets `Err(ReceiverMismatch)` + `return Ok(())`
3. `method_name` mismatch → sets `Err(MethodNameMismatch)` + `return Ok(())`

If check 1 fires but checks 2 and 3 do not (receiver and method both match), execution falls through to the unconditional nonce-update block at lines 685–699:

```rust
match nonce_update {
    DelegateNonceUpdate::AccessKey => {
        access_key.nonce = delegate_nonce.nonce();
        set_access_key(state_update, sender_id.clone(), public_key.clone(), &access_key);
    }
    DelegateNonceUpdate::GasKey { nonce_index } => {
        set_gas_key_nonce(state_update, sender_id.clone(), public_key.clone(),
                          nonce_index, delegate_nonce.nonce());
    }
}
```

The nonce write is committed to `state_update` (the trie). The function then returns `Ok(())`. Back in `apply_delegate_action` (line 449), the caller checks `result.result.is_err()` and returns without creating a receipt. The deposit is never transferred, but the nonce slot is permanently spent.

The codebase itself documents this as a bug and gates the fix behind `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError`:

```rust
// Before this fix, the missing early return allowed execution
// to fall through to the receiver_id and method_name checks,
// which could overwrite this error with a different one.
if ProtocolFeature::FixDelegateActionDepositWithFunctionCallError
    .enabled(apply_state.current_protocol_version)
{
    return Ok(());
}
```

The test `test_delegate_deposit_with_function_call_reports_receiver_mismatch_before_fix` (line 1764) confirms the pre-fix behavior: when both `deposit > 0` and `receiver_id` mismatches, the reported error is `ReceiverMismatch` instead of `DepositWithFunctionCall`, proving the overwrite path is reachable.

### Impact Explanation

Two concrete broken invariants:

1. **Nonce consumed without action execution.** The sender's access-key nonce (or gas-key nonce-index slot) is incremented in the trie even though the delegate action fails and no receipt is created. The invariant "nonce advances ↔ action receipt is emitted" is violated. For gas keys with a bounded `num_nonces` (max 1024), repeated triggering exhausts nonce slots without any corresponding execution.

2. **Wrong error code returned.** When `deposit > 0` and `receiver_id` mismatches, the user receives `ReceiverMismatch` instead of `DepositWithFunctionCall`, breaking the authorization-failure signal and making correct client-side error handling impossible.

### Likelihood Explanation

The trigger requires a sender to sign a `DelegateAction` with `deposit > 0` using a `FunctionCall`-restricted access key whose `receiver_id` and `method_names` match the action. This is a user-error scenario (the sender signed an action that violates their own key's permission), but it is reachable by any unprivileged user without any privileged assumption. The relayer submits the outer transaction but does not control the signed delegate action content. The bug is present on all protocol versions before `FixDelegateActionDepositWithFunctionCallError`.

### Recommendation

The fix is already present in the codebase behind the protocol feature gate. The unconditional early return after setting `Err(DepositWithFunctionCall)` must be applied regardless of protocol version, or the nonce-update block must be conditioned on `result.result.is_ok()`. The correct post-fix behavior (no nonce consumption on failed permission checks) should be enforced from the earliest supported protocol version.

### Proof of Concept

The existing unit test `deposit_with_function_call_and_receiver_mismatch` (line 1717) and `test_delegate_deposit_with_function_call_reports_receiver_mismatch_before_fix` (line 1764) demonstrate the wrong-error path. To demonstrate nonce consumption, extend the test to inspect `state_update` after `validate_delegate_action_key` returns with `result.result.is_err()`:

```rust
// Pre-fix protocol version
let version = ProtocolFeature::FixDelegateActionDepositWithFunctionCallError.protocol_version() - 1;

// FunctionCall key: receiver = "token.test.near", method_names = []
// DelegateAction: receiver = "token.test.near", deposit = 1 yoctoNEAR, method = "any"
// → deposit > 0 fires, receiver matches, method matches → falls through to nonce update

let result = deposit_with_function_call_and_receiver_mismatch_same_receiver(version);
// result.result is Err(DepositWithFunctionCall) — but nonce was already written to state_update
// Verify: get_access_key from state_update shows nonce = initial_nonce + 1
// Verify: apply_delegate_action creates no receipt
```
