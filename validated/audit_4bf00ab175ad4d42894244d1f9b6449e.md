### Title
Unhandled `TypeError: Invalid URL` in `sanitizeHost` crashes auth flow instead of throwing `InvalidHostError` - (File: packages/apps/shopify-api/lib/utils/shop-validator.ts)

### Summary
`sanitizeHost` constructs `new URL('https://' + decodeHost(sanitizedHost))` unconditionally as soon as the input passes the loose base64 character-set regex, with no try/catch around the `URL` constructor call. An attacker can supply a base64 string that decodes to a value containing forbidden host code points (e.g. a space), causing the WHATWG `URL` parser to throw a raw `TypeError`, which propagates out of `sanitizeHost` uncaught in place of the expected `InvalidHostError`.

### Finding Description
`sanitizeHost` first checks the raw `host` value against a loose base64 regex (`/^[0-9a-zA-Z+/]+={0,2}$/`) [1](#0-0) . If that matches, it immediately calls `new URL(\`https://${decodeHost(sanitizedHost)}\`)` with no try/catch [2](#0-1) , and only afterwards checks `throwOnInvalid` to decide whether to raise `InvalidHostError` [3](#0-2) . `decodeHost` is a thin wrapper over `atob`, which happily decodes arbitrary bytes without validating that the result is host-safe [4](#0-3) .

Any base64 payload whose decoded bytes contain a forbidden host code point (e.g. a space, `<`, `>`, backslash, control character, etc.) will pass the regex but make the WHATWG URL parser throw `TypeError: Invalid URL` when constructing the `https://` URL, rather than failing the `hostRegex` check.

This is directly reachable by an anonymous client: `sanitizeHost` is invoked with the raw `host` query parameter in `clientSideRedirect` inside `packages/apps/shopify-app-express/src/redirect-to-auth.ts`, triggered from the app's own `redirectToAuth` handler whenever `req.query.embedded === '1'` [5](#0-4) . Note the crash occurs inside the `if (sanitizedHost) {...}` block, unconditionally, before the `throwOnInvalid` check — so it happens regardless of whether the caller opted into throwing on invalid input. There is no surrounding try/catch in `redirect-to-auth.ts`, nor in `sanitizeHost` itself, so a plain `TypeError` bubbles out of an auth-adjacent request handler instead of a typed `InvalidHostError` that downstream code is designed to handle.

The remix/react-router `validateShopAndHostParams` helper calls `sanitizeHost` similarly, without a try/catch [6](#0-5) , and `buildEmbeddedAppUrl` calls `sanitizeHost(config)(host, true)` also with no surrounding try/catch [7](#0-6) .

### Impact Explanation
This is a denial-of-service against an authentication-adjacent code path: a single crafted request to a route that resolves `host` (e.g. the Express `auth` begin route with `embedded=1`, or an embedded-app-url resolution route) throws an uncaught `TypeError` instead of the intended `InvalidHostError`. Depending on the runtime/framework wiring around the handler, this can surface as an unhandled promise rejection/500, and breaks the "fail closed with a typed error" invariant that other code relies on to distinguish invalid-input from a crash. This matches Shopify's DoS-in-authentication-handler impact class, though the severity is limited (no memory exhaustion, no data leak — a single malformed request per crash, and Express's default handler generally converts sync throws to a 500 response rather than crashing the process).

### Likelihood Explanation
Fully reachable by an unauthenticated attacker: `host` is a client-supplied query parameter on public app routes and requires no secret, cookie, or elevated privilege — only default library configuration. Constructing the payload is trivial (`Buffer.from('a b').toString('base64')` → `YSBi`, which passes the base64 regex and decodes to a string containing a space, a forbidden host code point).

### Recommendation
Wrap the `new URL(...)` construction in `sanitizeHost` in a try/catch, treating any thrown error as an invalid host (set `sanitizedHost = null`) before the existing `throwOnInvalid` branch runs, so the function always fails closed with `InvalidHostError` (or `null`) instead of leaking a raw `TypeError`.

```ts
// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';
import {InvalidHostError} from '../../error';

test('sanitizeHost fails closed on malformed decoded host instead of throwing raw TypeError', () => {
  const shopify = shopifyApi(testConfig());
  const malformedHost = Buffer.from('a b').toString('base64'); // 'YSBi'

  // Currently throws TypeError: Invalid URL instead of InvalidHostError
  expect(() => shopify.utils.sanitizeHost(malformedHost, true)).toThrow(
    InvalidHostError,
  );
});
```
Expected (desired) behavior: throws `InvalidHostError`. Actual current behavior: throws an unhandled `TypeError: Invalid URL` from the native `URL` constructor.
