### Title
Missing minimum-output (slippage) protection in `ExchangeWithdrawContract` allows withdrawer to receive fewer tokens than expected - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract`, unlike `ExchangeTransactionContract`, has no `expected` (minimum-output) field. The amount of the "other" token a withdrawer receives is computed from the exchange pool's live `firstTokenBalance`/`secondTokenBalance` ratio at execution time, not at the time the user signs and broadcasts the transaction. If the pool ratio shifts between broadcast and block inclusion (e.g., because another account's `ExchangeTransactionContract` or `ExchangeInjectContract` executes first, or is deliberately front-run), the withdrawer can receive materially less of the paired token than they expected when they signed the transaction, with no on-chain mechanism to abort the withdrawal.

### Finding Description
`ExchangeWithdrawActuator.execute()` computes the paired-token payout purely from the exchange's current balances at execution time: [1](#0-0) 

There is no user-supplied lower bound checked against `anotherTokenQuant` anywhere in `validate()` or `execute()`. Compare this to `ExchangeTransactionContract`/`ExchangeTransactionActuator`, which explicitly carries an `expected` field and enforces it: [2](#0-1) 

The protobuf definitions confirm the asymmetry: `ExchangeTransactionContract` has `expected`, `ExchangeWithdrawContract` does not: [3](#0-2) 

Because the exchange pool balances are mutable shared state (any account can call `ExchangeInjectContract`/`ExchangeTransactionContract`/another `ExchangeWithdrawContract` against the same `exchange_id`), the ratio used to compute `anotherTokenQuant` for a pending, already-signed `ExchangeWithdrawContract` can change before it is packed into a block. This is directly analogous to the reported AaveStrategy issue: a redeem-like operation (`ExchangeWithdraw`) lacks a minimum-expected-output guard, so a parameter/state change that occurs concurrently with the pending transaction can cause the caller to receive less than they intended, with no revert path.

### Impact Explanation
The exchange creator (the only account allowed to call `ExchangeWithdraw`, per the `is not creator` check) can be economically harmed by receiving fewer paired tokens than anticipated when withdrawing liquidity, if pool-affecting transactions (trades, injects, or partial withdraws) land in the same or an earlier block. This is an accounting/economic-loss issue reachable purely via broadcast transactions against the public `Exchange`/`ExchangeV2` market feature — no privileged actor is required. It does not cause consensus divergence or node compromise; it is analogous in class/severity to the referenced low-difficulty finding.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires either (a) natural concurrent trading activity on the same exchange pool between the time the withdraw transaction is signed and when it is included in a block, or (b) deliberate front-running by another account submitting a competing `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` against the same `exchange_id` to shift the ratio before the victim's withdrawal executes. Both are unprivileged, achievable by any account, and require no special network position.

### Recommendation
Add an optional minimum-expected-output field (analogous to `expected` on `ExchangeTransactionContract`) to `ExchangeWithdrawContract`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by reverting if the computed `anotherTokenQuant` falls below the caller-specified minimum. More broadly, audit other exchange/market and resource-accounting actuators for similar missing slippage/minimum-output protections whenever the payout is computed from mutable shared state at execution time rather than at signing time.

### Proof of Concept
1. Exchange `E` holds tokens A/B with balances such that withdrawing `q` of A currently returns `r` of B.
2. Alice (the exchange creator) signs and broadcasts `ExchangeWithdrawContract{exchange_id=E, token_id=A, quant=q}` expecting to receive `r` of B.
3. Before Alice's transaction is packed, Bob broadcasts an `ExchangeTransactionContract` (or another account submits `ExchangeInjectContract`) against exchange `E` that shifts the A/B ratio.
4. Alice's withdrawal executes with the new ratio in `ExchangeWithdrawActuator.execute()` (lines 74-89 as cited), yielding `r' < r` of B, with no validation rejecting the reduced payout, since no `expected` field exists on `ExchangeWithdrawContract` to check against.
