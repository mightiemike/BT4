Based on my investigation, the codebase explicitly addresses this exact scenario by design, contradicting the premise of the question.

The comment and implementation of `load_nakamoto_reward_set_for_tenure` in `stackslib/src/chainstate/nakamoto/coordinator/mod.rs` (lines 359-412) makes clear that the reward set used to validate a tenure's blocks is keyed to the **tenure's election sortition** (`tenure_snapshot`), not the burnchain tip at the moment of validation:

> "`tenure_snapshot` must be the snapshot of the sortition that elected the tenure (the sortition whose consensus hash the tenure's blocks carry), not the burnchain tip: a tenure extended across a reward-cycle boundary is still signed by the reward set that was active at its election." [1](#0-0) 

The reward cycle used for lookup is computed directly from `tenure_snapshot.block_height` via `burnchain.block_height_to_reward_cycle`, and `append_block` receives the correct `active_reward_set` parameter that is resolved against the block's actual tenure/consensus hash, not against a cached tip-relative value. [2](#0-1)  The block's `consensus_hash` is validated against the sortition snapshot (`check_sortition_exists`) that determines its reward cycle in `append_block`. [3](#0-2) 

Additionally, the relay-path (`net/relay.rs`) and unsolicited-message path (`net/unsolicited.rs`) both derive the reward cycle for signature verification from the block's sortition snapshot's `consensus_hash`/`block_height` — not from a stale cached tip — before calling `verify_signer_signatures`. [4](#0-3) [5](#0-4)  The `check_reload_cached_reward_set` logic in `net/p2p.rs` also explicitly invalidates cached reward sets on any Nakamoto reorg to prevent staleness. [6](#0-5) 

The premised equality — "reward_set used by `verify_signer_signatures` for block B == the reward set of block B's actual tenure's reward cycle" — is enforced by construction: every code path that calls `verify_signer_signatures` first resolves the reward cycle from the block's own consensus hash / tenure election snapshot, computed via `block_height_to_reward_cycle`, rather than reusing a cycle-(N-1) cached value across the boundary. I found no code path where a stale reward set (e.g., a cached `active_reward_set` from cycle N-1) is passed into `verify_signer_signatures` for a block whose tenure's sortition places it in cycle N. The `get_nakamoto_next_recipients` and `get_nakamoto_reward_cycle_info` functions both explicitly gate reward-set loading on `is_naka_reward_cycle_start_for_epoch`/`block_height_to_reward_cycle` at the block's own height, and the coordinator refuses to advance past a reward-cycle boundary until the correct anchor block/reward set for the new cycle is known.
