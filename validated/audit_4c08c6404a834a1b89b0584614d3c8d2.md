### Title
Blocking `GlobalRateLimiter.acquire()` under default configuration allows unprivileged flooding to exhaust Jetty/gRPC worker threads (DoS) - ([File: framework/src/main/java/org/tron/core/services/ratelimiter/GlobalRateLimiter.java])

### Summary
`GlobalRateLimiter.acquire(RuntimeData)` calls the blocking `com.google.common.util.concurrent.RateLimiter.acquire()` on both the per-IP limiter and the shared static global limiter. Since `rate.limiter.apiNonBlocking` defaults to `false`, this blocking path is the out-of-the-box behavior for both `RateLimiterServlet` (HTTP) and `RateLimiterInterceptor` (gRPC), so any client sending concurrent requests exceeding the configured QPS causes the handling thread to sleep inside `acquire()` until a token becomes available, tying up the finite Jetty/gRPC worker pool.

### Finding Description
`GlobalRateLimiter.acquirePermit()` dispatches to `acquire()` (blocking) when `Args.getInstance().isRateLimiterApiNonBlocking()` is false: [1](#0-0) 

Both `RateLimiterServlet.service()` (HTTP path, reachable from e.g. `/wallet/broadcasttransaction`) and `RateLimiterInterceptor.interceptCall()` (gRPC path) call `GlobalRateLimiter.acquirePermit(runtimeData)` synchronously on the request-handling thread before dispatching to the actual servlet/handler: [2](#0-1) [3](#0-2) 

`isRateLimiterApiNonBlocking()` defaults to `false` both in `reference.conf` and `config.conf` (i.e. blocking mode is the shipped default, not a special/non-default configuration an operator must opt into): [4](#0-3) [5](#0-4) [6](#0-5) 

Jetty's HTTP server (`new Server(this.port)`) uses Jetty's default `QueuedThreadPool`, a bounded thread pool, and the servlet layer has no async/timeout dispatch around `GlobalRateLimiter.acquire()`: [7](#0-6) 

On the gRPC side, when `node.rpc.thread` is set (>0) a bounded fixed thread pool is created as the gRPC executor: [8](#0-7) 

Because `RateLimiter.acquire()` from Guava is a blocking call that sleeps the calling thread until a token is available (with no timeout, no queue-length cap, and no separation between the rate-limiting check and the worker-thread pool that serves it), a burst of concurrent requests exceeding `global.qps`/per-IP `qps` will pile up worker threads all sleeping inside `acquire()`. Because the thread pool is finite, once all worker threads are blocked, no further requests of any kind (including unrelated GET/JSON-RPC endpoints funneled through the same Jetty connector) can be dispatched, producing a full HTTP/gRPC service stall.

None of the existing checks mitigate this: `perEndpointAcquired` short-circuits per-endpoint QPS but the global blocking `acquire()` is unconditionally reached once the per-endpoint check passes, and there is no thread-pool isolation, request queue limit, or timeout wrapping the call.

### Impact Explanation
This maps to "DoS via RPC-API": an unprivileged remote client can stall the node's entire HTTP and/or gRPC front end by saturating the bounded worker thread pool with threads parked in `RateLimiter.acquire()`, denying service to all other legitimate clients (including read-only/GET and JSON-RPC clients sharing the same Jetty connector/thread pool). No funds or consensus state are affected — the impact is availability/DoS at the API layer.

### Likelihood Explanation
- Preconditions: default configuration (`apiNonBlocking=false` is the shipped default) plus any global/IP QPS ceiling that a burst of concurrent connections can exceed (default `global.qps=50000`, `global.ip.qps=10000`, but any node operator using a stricter, still-default-style config, or simply enough concurrent connections from many source IPs, reaches this).
- Cost to attacker: none — this requires no signed transaction, no fee, no funded account; a flood of concurrent anonymous HTTP/gRPC connections is sufficient.
- Feasibility: trivially repeatable with common load-testing tools (e.g., multiple concurrent `curl`/`ab`/custom clients hitting `/wallet/broadcasttransaction` or any rate-limited HTTP/gRPC endpoint), and each additional wave of connections consumes additional bounded worker threads.
- Note: for genuinely high default QPS values (50000 global) a single attacker may need substantial concurrency/bandwidth to exceed it, but per-IP QPS (`global.ip.qps=10000` default, and smaller in any tightened config) combined with connection-limited environments lowers the bar considerably, and any operator-tuned lower QPS (a common, documented, still-default-style tuning knob in this same file) makes this trivial.

### Recommendation
Avoid blocking the request-handling thread on the shared `RateLimiter`. Options:
1. Force non-blocking (`tryAcquire`) semantics for the global limiter regardless of `apiNonBlocking`, since blocking a finite worker thread pool on a shared limiter is unsafe by construction.
2. If blocking semantics must be preserved, bound the wait with `RateLimiter.tryAcquire(timeout, unit)` and reject with a fast error (mirroring the non-blocking rejection path) instead of `acquire()`'s unbounded block.
3. Dispatch the wait onto a dedicated bounded executor/async servlet (Jetty `AsyncContext`) so that blocked permits do not consume threads from the main servlet/gRPC worker pool that serves unrelated requests.

### Proof of Concept
```java
// JUnit/integration sketch, extending RateLimiterServletTest infra
@Test
public void testBlockingGlobalLimiterStallsThreadPool() throws Exception {
  Args.getInstance().setRateLimiterApiNonBlocking(false); // default
  Args.getInstance().setRateLimiterGlobalQps(1); // small QPS to simulate saturation quickly

  // Start RateLimiterServlet-backed HttpService with Jetty's default bounded QueuedThreadPool
  // Fire N concurrent HTTP POSTs (N > pool size) to an endpoint served by RateLimiterServlet
  ExecutorService clients = Executors.newFixedThreadPool(THREADS);
  List<Future<Long>> futures = new ArrayList<>();
  for (int i = 0; i < THREADS; i++) {
    futures.add(clients.submit(() -> {
      long start = System.nanoTime();
      httpClient.execute(new HttpPost(serverUri)); // any rate-limited endpoint
      return System.nanoTime() - start;
    }));
  }

  // Meanwhile issue a control request to an unrelated endpoint on the same Jetty connector
  long controlLatencyNanos = timeControlRequest();

  // Assert: control request latency spikes / times out because all worker
  // threads are parked inside GlobalRateLimiter.acquire() -> RateLimiter.acquire()
  Assert.assertTrue("control request should be stalled by thread-pool exhaustion",
      controlLatencyNanos > TimeUnit.SECONDS.toNanos(5));
}
```
Expected result: with `apiNonBlocking=false` (default) and a small `global.qps`, concurrent flooding causes worker threads to park in `GlobalRateLimiter.acquire()` long enough that an unrelated control request on the same connector experiences multi-second+ latency or outright failure, demonstrating thread-pool exhaustion / node-wide stall.
