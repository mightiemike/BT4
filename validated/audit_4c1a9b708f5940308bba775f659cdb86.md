Cross-tenant fulfillment-service action via shop-domain/HMAC decoupling - (File: packages/apps/shopify-app-remix/src/server/authenticate/fulfillment-service/authenticate.ts)

### Summary
`authenticate` in the fulfillment-service handler verifies only that the raw request body was HMAC-signed with the app's shared `apiSecretKey`, then uses the unauthenticated `X-Shopify-Shop-Domain` header to look up which shop's offline session/admin client to attach to the request. Because the HMAC never covers the shop domain, a merchant who legitimately installs the app and receives one genuine fulfillment-service callback can replay that exact (body, HMAC) pair against the same public endpoint with the domain header swapped to a different (victim) shop that also uses the app.

### Finding Description
The handler reads the raw body, calls `api.fulfillmentService.validate({rawBody, rawRequest: request})`, and only after HMAC succeeds does it read the shop from headers: [1](#0-0) 

That validation ultimately calls `validateHmacFromRequestFactory`, which computes the HMAC over `rawBody` alone, using the single app-wide `config.apiSecretKey`, and never incorporates the `Shop-Domain`/topic headers into the signed material: [2](#0-1) 

The resulting `shop` value — taken straight from `request.headers.get(ShopifyHeader.Domain)` with no cross-check against the signed payload — is then used to fetch the offline session and build the admin client: [3](#0-2) 

`ensureValidOfflineSession` / `createOrLoadOfflineSession` load whatever session exists for that attacker-supplied shop string, with no attempt to verify it corresponds to the shop that actually produced the signed body: [4](#0-3) [5](#0-4) 

Because `apiSecretKey` is one shared secret for the entire app (not per-shop), any (rawBody, HMAC) pair that is valid for one shop is also a cryptographically valid HMAC for any other shop under the same app. The same header-derived, HMAC-unbound "shop" pattern also exists in the general webhook authenticator (`check.domain` comes straight from headers, not from the signed body) and in the React Router equivalent: [6](#0-5) 

### Impact Explanation
An attacker who is a legitimate, unprivileged merchant of the target app can capture a genuine fulfillment-service callback delivered to their own shop (valid body + valid `X-Shopify-Hmac-Sha256`), then POST that exact body/HMAC pair directly to the app's public fulfillment-service endpoint with the `X-Shopify-Shop-Domain` header changed to a different, victim shop that also has the app installed. Since the endpoint accepts this as valid (HMAC checks out) and resolves the offline session purely from the spoofed header, the attacker's replayed/crafted payload is processed under the victim shop's offline session and `admin` GraphQL/REST client — i.e., attacker-controlled fulfillment data is treated as an authenticated action against a different tenant. This matches "cross-tenant webhook/fulfillment action" (forged authenticated request causing state change/data access under another shop's identity).

### Likelihood Explanation
Preconditions: attacker must (a) install the app themselves (normal, unprivileged merchant action) to obtain at least one genuine (body, HMAC) pair from a real fulfillment-service/webhook delivery, and (b) know or guess the victim shop's `myshopify.com` domain (shop domains are not secret and are enumerable/guessable). No leaked secrets, no privileged role, and no MITM are required — the endpoint is a public HTTP handler and the attacker fully controls headers and can replay a body they legitimately received. This is deterministically reproducible with a unit test that computes a valid HMAC for a body and then sets an arbitrary `X-Shopify-Shop-Domain` header for a different (existing) session in storage.

### Recommendation
Do not treat the `X-Shopify-Shop-Domain` (or `Topic`) header as trusted merely because the overall request HMAC is valid. Bind shop identity to the verified content, e.g.: (1) include the shop domain in the HMAC-signed material where the delivery mechanism allows, or (2) cross-validate the header-derived shop/topic against fields embedded in the verified `rawBody` payload (most Shopify fulfillment-service/webhook payloads include shop/store identifiers), rejecting mismatches, and/or (3) rate-limit/replay-protect using webhook/event IDs so a captured payload cannot be relayed to a different domain.

import {AppDistribution, BasicParams} from '../types';

export async function createOrLoadOfflineSession(
  {api, config, logger}: BasicParams,
  shop: string,
) {
  if (config.distribution === AppDistribution.ShopifyAdmin) {
    logger.debug('Creating custom app session from configured access token', {
      shop,
    });
    return api.session.customAppSession(shop);
  } else {
    logger.debug('Loading offline session from session storage', {shop});
    const offlineSessionId = api.session.getOfflineId(shop);
    const session = await config.sessionStorage!.loadSession(offlineSessionId);

    return session;
  }
}
