## Finding Confirmed [1](#0-0) 

### Title
Module-lock reentrancy bypass for same-module closure dispatch - (File: third_party/move/move-vm/runtime/src/reentrancy_checker.rs)

### Summary
`ReentrancyChecker::enter_function` enforces the AIP-73 module-lock guarantee ("all calls reentering any module will lead to an abort") only on the *cross-module* branch, which checks `module_lock_count` before erroring on reentry. The *intra-module* branch — taken when a closure is dispatched (`CallType::ClosureDynamicDispatch`) into a function of the module that is already executing — never checks `module_lock_count` at all, and unconditionally allows the call while merely bumping the reentrancy multiset counter.

### Finding Description
`enter_function` has two branches that decide what happens on a call: [2](#0-1) 

- Cross-module branch (`callee_module != caller_module`, line 78): if the module was already entered (`Entry::Occupied`) **and** `self.module_lock_count > 0`, the call is rejected with `RUNTIME_DISPATCH_ERROR` ("module lock is active").
- Intra-module branch (`callee_module == caller_module`, `call_type == ClosureDynamicDispatch`, line 102): the counter for the module is simply incremented via `.or_default() += 1` — there is **no check of `module_lock_count`** here, so the call is always allowed to proceed regardless of whether a module lock is active.

This asymmetry means that once module-lock mode is active — either because the outer call was `CallType::NativeDynamicDispatch` (`is_locking` always returns `true` for that call type, line 58) or because the currently-executing function carries `#[module_lock]` (as used in production for `dispatch_withdraw_hook`/`dispatch_deposit_hook` in `dispatchable_fungible_asset.move` to "preserve AIP-73 reentrancy semantics" [3](#0-2)  — a closure captured/invoked from *within that same module* that resolves back into a function of the same module is never blocked by the module-lock check. It only trips the separate, weaker mode-1 resource lock (`check_resource_access`, line 169) if the reentrant code directly touches a `borrow_global`/`move_from` on a resource of that module; any other state-mutating side effect (calling further natives, dispatching to other dispatchable assets, emitting events, mutating non-resource global state through additional dispatch, etc.) sails through untouched.

This directly contradicts the documented invariant: "While a function with this attribute [`#[module_lock]`] is running, all calls reentering any module will lead to an abort" (functions.md) and the worked example there where a callback attempting to "re-enter `transfer`" (the *same* module as the locked function) is supposed to be blocked. The existing transactional test `reentrancy_module_lock.move` only exercises the *cross-module* path (the closure is invoked from inside `callee::call_me`, i.e. `caller_module == callee` when the closure fires, so `callee_module(caller) != caller_module(callee)`), which is why the module-lock error fires there. There is no corresponding test where the closure is invoked directly from within the locked module itself (same-module dispatch), which is exactly the gap the intra-module branch leaves open.

### Impact Explanation
An attacker-authored package can define a `#[module_lock]`-tagged (or otherwise natively-dispatched) function that, from within its own module, invokes a captured closure pointing to another function of the *same* module performing state-mutating side effects that avoid direct resource borrows of that module (e.g., re-invoking further dispatchable hooks, mutating derived/side-table state, or driving a second leg of a balance-affecting operation before the first leg completes). Because the module-lock check is skipped on this path, the reentrant call is permitted, letting the attacker construct a same-module reentrant sequence the module-lock feature was specifically built to forbid, corrupting the resulting write set relative to correct AIP-73 semantics. This affects committed state (the transaction's write set/resource values), which is in scope per the state-integrity gate.

### Likelihood Explanation
The trigger requires only unprivileged actions: publishing/using a Move package that builds and invokes a closure bound to a sibling function of the same module while under module-lock, and does not directly `borrow_global`/`move_from` the module's own resources in the reentrant leg (so the unrelated mode-1 `check_resource_access` guard doesn't happen to catch it). This is straightforward to construct from ordinary bytecode/closures and doesn't rely on any trusted-operator error.

### Recommendation
In the intra-module branch of `enter_function` (reentrancy_checker.rs:102-113), add the same `module_lock_count > 0` rejection used in the cross-module branch before incrementing the counter, so that same-module closure/native reentry is uniformly blocked whenever module-lock mode is active, matching the documented "all calls reentering any module abort" guarantee.

### Proof of Concept
Extend `reentrancy_module_lock.move` so the closure is invoked *directly inside* the locked module (making `caller_module == callee_module`) instead of via an external `callee::call_me`, and have the reentrant target avoid a direct `R[@addr]` access:

```move
module 0x42::caller {
    struct R has key, copy, drop { count: u64 }

    fun init(s: &signer) { move_to(s, R{count: 0}); }

    #[module_lock]
    fun callback_not_ok(): bool {
        let notify: |u64| has copy + drop = |amt| reentrant(amt);
        notify(1);          // intra-module ClosureDynamicDispatch while module_lock_count > 0
        true
    }

    // Deliberately does not touch R directly, so mode-1 resource-lock
    // (check_resource_access) does not trigger; only module-lock (mode-2)
    // is supposed to block this call, but the intra-module branch never
    // checks module_lock_count.
    fun reentrant(amt: u64) {
        // side-effecting reentrant logic here
    }
}
```

Under correct AIP-73 semantics this `notify(1)` call should abort with `RUNTIME_DISPATCH_ERROR` ("module lock is active"), consistent with `reentrancy_module_lock.move`'s cross-module case. Tracing the code shows it instead proceeds through the intra-module branch of `enter_function` without any `module_lock_count` check, so `callback_not_ok` completes without an abort — the assertion the transactional test should make ("call must be rejected") fails, confirming the bypass.

impl ReentrancyChecker {
    // note(inline): as `call_type` is sometimes a fixed value, this inline is very valuable
    #[inline(always)]
    pub fn enter_function(
        &mut self,
        caller_module: Option<&ModuleId>,
        callee: &LoadedFunction,
        call_type: CallType,
    ) -> PartialVMResult<()> {
        if call_type.is_locking(callee) {
            self.enter_module_lock();
        }

        let callee_module = callee.module_or_script_id();
        if Some(callee_module) != caller_module {
            // Cross module call.
            // When module lock is active, and we have already called into this module, this
            // reentry is disallowed
            match self
                .active_modules
                .entry(callee.owner.interned_module_or_script_id())
            {
                Entry::Occupied(mut e) => {
                    if self.module_lock_count > 0 {
                        return Err(PartialVMError::new(StatusCode::RUNTIME_DISPATCH_ERROR)
                            .with_message(format!(
                                "Reentrancy disallowed: reentering `{}` via function `{}` \
                     (module lock is active)",
                                callee_module,
                                callee.name()
                            )));
                    }
                    *e.get_mut() += 1
                },
                Entry::Vacant(e) => {
                    e.insert(1);
                },
            }
        } else if call_type == CallType::ClosureDynamicDispatch || caller_module.is_none() {
            // If this is closure dispatch, or we have no caller module (i.e. top-level entry).
            // Count the intra-module call like an inter-module call, as reentrance.
            // A static local call is governed by Move's `acquire` static semantics; however,
            // a dynamic dispatched local call has accesses not known at the caller side, so needs
            // the runtime reentrancy check. Note that this doesn't apply to NativeDynamicDispatch
            // which already has a check in place preventing a dispatch into the same module.
            *self
                .active_modules
                .entry(callee.owner.interned_module_or_script_id())
                .or_default() += 1;
        }
        Ok(())
    }
