### Title
Stale ztoken liquidity-index cache not invalidated by debt socialization within the same block - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`accrue-and-cache` in `v0-4-market.clar` caches a vault's liquidity index (`lindex`) keyed only by `{timestamp: stacks-block-time, aid}`, explicitly to avoid repeated cross-contract calls to a vault within the same block. However, this cache is never invalidated by other in-block/in-transaction operations that change the vault's actual backing ratio, most notably `vault-socialize-debt`. If a socialize-debt (bad-debt write-off) mutation runs after the index for that vault has already been cached in the current block, subsequent ztoken price resolutions in the same or a following call within that block via `resolve-ztoken` will keep returning the pre-socialization `lindex`, mispricing the ztoken collateral/debt.

### Finding Description
`accrue-and-cache` reads/writes `index-cache` keyed by the current block timestamp and asset id: [1](#0-0) 

This cached `lindex` is the sole input to `resolve-ztoken`, which is the mechanism used to price all `z*` collateral (zSTX, zsBTC, zstSTX, zUSDC, zUSDH, zstSTXbtc) throughout borrow/withdraw/liquidation health checks: [2](#0-1) 

Separately, the market exposes `vault-socialize-debt`, which calls into the underlying vault to write off bad debt — an operation that changes the vault's assets-to-shares ratio (i.e., the liquidity index) without going through `vault-accrue`/`accrue-and-cache`: [3](#0-2) 

The project's own documentation confirms the cache is intentionally *not* invalidated intra-block — only a new block clears it: "Cache Invalidation: Cache is timestamp-based using `stacks-block-time`, automatically invalidating when a new block is processed." [4](#0-3) 

Because the cache key is `{timestamp, aid}` and not tied to any version/nonce of the vault's actual index, any code path that first triggers `accrue-and-cache(aid)` (e.g. via `accrue-user-collateral`/`accrue-user-debts` at the start of a market entry point) and later, in the same transaction, calls `vault-socialize-debt` for that same `aid` before a subsequent price resolution of the associated ztoken, will have the second resolution read the stale, pre-write-off `lindex` instead of the updated one.

### Impact Explanation
A stale liquidity index for a ztoken means the market either overvalues or undervalues that collateral/debt relative to its true post-write-off backing for the remainder of the block. This can let a position that should be flagged unhealthy (undercollateralized after a bad-debt socialization event lowered the real backing) pass a health check using the old, higher cached index, or vice versa cause legitimate positions to be wrongly liquidated. Exploited around a socialize-debt event, this can permit borrowing/withdrawing against collateral that is not actually sufficiently backed, i.e., temporary freezing/mispricing of funds and improper draw-down of the vault's real assets — falling under the "temporary freezing of funds" / mispricing-driven fund-extraction impact class.

### Likelihood Explanation
This requires a specific sequence — a transaction (or a set of calls within the same block) that first populates the ztoken's index cache and then executes `vault-socialize-debt` on the same underlying vault before further pricing of that ztoken occurs — so it is not trivially triggerable by an arbitrary user in isolation. It depends on the exact call ordering inside the market's public entry points (e.g., a combined liquidation/socialize flow) which I could not fully trace within available tool iterations; likelihood is therefore rated Medium, contingent on confirming the exact top-level function ordering that pairs `accrue-and-cache` with `vault-socialize-debt` for the same `aid` in one call.

### Recommendation
Invalidate (or bypass) the `index-cache` entry for an asset whenever `vault-socialize-debt` (or any other operation that mutates the vault's backing ratio) is executed for that asset within the same block, e.g., by removing the cache entry for that `aid` immediately after `vault-socialize-debt` succeeds, or by re-deriving `lindex` freshly (bypassing the cache) for any ztoken price resolution that occurs after a socialize-debt call in the same transaction.

### Proof of Concept
1. Within block N, a market entry point calls `accrue-user-collateral`, which calls `accrue-and-cache(vault-id)` for asset X, caching `lindex = L0` in `index-cache` under key `{timestamp: T, aid: X}` [1](#0-0) .
2. Later in the same block/transaction, `vault-socialize-debt(X, amount)` is invoked, writing off bad debt on vault X and changing its real assets/shares ratio to `lindex = L1 != L0` [3](#0-2) .
3. A subsequent call in the same block that prices ztoken zX (e.g. another user's borrow/withdraw/health check) invokes `resolve-ztoken`, which calls `get-cached-indexes`/`accrue-and-cache(X)` again with the same key `{timestamp: T, aid: X}` — this hits the cache and returns the stale `L0` instead of `L1` [5](#0-4) .
4. The health/valuation computed for zX collateral/debt in step 3 is therefore based on outdated backing, diverging from the true post-write-off value for the remainder of block N.

## Index Caching

The market maintains a timestamp-based cache for vault liquidity indexes to optimize ztoken price resolution:

```clarity
;; In market.clar
(define-map index-cache- 
  { timestamp: uint, aid: uint }
  { index: uint, lindex: uint })

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache- cache-key)))
    (match cached?
      existing existing
      (let ((fresh (vault-accrue aid)))
        (map-set index-cache- cache-key fresh)
        fresh))))
```

**Purpose:** 
- Multiple price resolutions for the same vault within a single block use cached indexes
- Avoids redundant cross-contract calls to vaults
- Significantly reduces gas costs for transactions involving multiple ztoken prices

**Cache Invalidation:** Cache is timestamp-based using `stacks-block-time`, automatically invalidating when a new block is processed.
