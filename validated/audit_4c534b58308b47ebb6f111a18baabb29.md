### Title
Public gateway HTTP ingress lacks per-connection header/body/request timeouts, enabling HTTP slow-request Denial of Service - ([File: crates/apollo_http_server/src/http_server.rs])

### Summary
The sequencer's externally-reachable transaction ingress (`apollo_http_server`, serving `/gateway/add_transaction` and `/gateway/add_rpc_transaction`) is started with bare `axum::serve(listener, app)` and no header-read timeout, no request timeout, and no connection-count limit. Any unprivileged sender who can reach this port can open many TCP connections and trickle headers/body at a rate below TCP idle-timeout detection (there is none configured at all here), tying up the connection indefinitely and exhausting the node's ability to accept new legitimate transaction submissions — the same class of bug as CVE-2020-8251.

### Finding Description
`HttpServer::run` binds a `TcpListener` and calls `serve(listener, app).await` directly: [1](#0-0) 

This is bare `axum::serve`, which uses hyper's default HTTP/1.1 connection handling with **no** `http1_header_read_timeout`, no idle/keepalive timeout, and no cap on the number of concurrently accepted TCP connections. The only protections configured are body-size limits: [2](#0-1) 

Contrast this with the sequencer's *internal* inter-component RPC server (`RemoteComponentServer`), which is deliberately hardened against exactly this class of attack: it uses a hyper-util `ServerBuilder` with `keep_alive_interval`/`keep_alive_timeout`, TCP-level keepalive probes, and — critically — a `Semaphore`-bound `max_concurrency` that rejects excess connections with `503`: [3](#0-2) [4](#0-3) 

None of these mitigations (connection semaphore, keepalive detection, header/body timeout) exist on the public-facing `apollo_http_server`. Its configuration (`HttpServerStaticConfig`) only exposes `max_request_body_size` and `dynamic_config_poll_interval` — there is no `request_timeout`, `header_timeout`, or `max_concurrency` field at all: [5](#0-4) 

Because the OS-level TCP connection accept loop in `axum::serve` has no cap and hyper's HTTP/1.1 server does not time out a connection that is slowly trickling headers or body bytes (as long as *some* bytes eventually arrive, or even if none arrive since there's no idle timeout either), an attacker can hold open an effectively unlimited number of connections against `add_transaction`/`add_rpc_transaction`, exhausting file descriptors / ephemeral ports / worker resources on the node, exactly mirroring the Node.js `unfinished HTTP/1.1 request` DoS described in the report.

### Impact Explanation
Any unprivileged network client that can reach the sequencer's HTTP gateway port can exhaust its connection-handling resources by opening many connections and sending headers/body extremely slowly (or not completing them). Once resources (file descriptors, ephemeral ports, or per-connection task memory) are exhausted, the node becomes unable to accept new transaction submissions from legitimate senders, effectively halting new transaction ingestion on that node — a network-availability impact ("a network unable to confirm new transactions") satisfying the required impact bar for a Medium/High finding. It does not corrupt state or funds, but it directly matches the CWE-400 resource-exhaustion class of the reference report, scoped to the transaction-ingress endpoint reachable by an ordinary sender.

### Likelihood Explanation
The endpoint is designed to be internet-facing (it is the primary transaction submission API for the network). The attack requires no authentication, no valid transaction content, and no special privileges — only the ability to open TCP connections to the gateway's port and trickle bytes, exactly as demonstrated in the report's reproduction script. Given the complete absence of any timeout or connection-limiting configuration on this specific server (unlike the internal component servers which are properly hardened), likelihood is high whenever the HTTP gateway component is deployed with a publicly reachable port (the standard "http_server" deployment configurations in `crates/apollo_deployments/resources/services/**` show `components.http_server.execution_mode: "Enabled"` in exactly this configuration).

### Recommendation
Harden `HttpServer::run` in `crates/apollo_http_server/src/http_server.rs` the same way `RemoteComponentServer` is hardened:
- Replace the bare `axum::serve(listener, app)` with a hyper-util `ServerBuilder`/`serve_connection` loop (or configure `axum::serve` via `Builder::http1().header_read_timeout(...)`) that enforces a header-read timeout and an overall request timeout.
- Add a connection-count cap (e.g., a `Semaphore`-guarded accept loop like `RemoteComponentServer`) so excess connections are rejected with `503` rather than accepted indefinitely.
- Add explicit configuration fields (`header_timeout_ms`, `request_timeout_ms`, `max_concurrency`) to `HttpServerStaticConfig`, mirroring `RemoteServerConfig`'s `keepalive_interval_ms`/`keepalive_timeout_ms`/`max_concurrency`.
- Set TCP keepalive on accepted sockets as already done for `RemoteComponentServer`.

### Proof of Concept
Using the same technique as the referenced report's PoC (adapted to the sequencer's gateway):
1. Open N TCP connections to the `apollo_http_server` port (default 8080) which serves `/gateway/add_transaction`.
2. For each connection, send `POST /gateway/add_transaction HTTP/1.1` headers plus a `Content-Length` header quickly, then send the body one byte at a time with long delays (e.g., every 60s), similar to the report's `client.write(body[i])` loop.
3. Because `axum::serve` in `crates/apollo_http_server/src/http_server.rs` (lines 120-123) is not configured with any header/body/request timeout, none of these connections are ever closed by the server.
4. Repeating this with enough parallel connections exhausts the node's socket/file-descriptor/worker capacity, preventing legitimate senders' `add_transaction`/`add_rpc_transaction` requests from being accepted — denial of service on transaction ingestion.
