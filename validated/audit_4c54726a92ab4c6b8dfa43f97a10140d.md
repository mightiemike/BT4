### Title
External caller's excess attached NEAR deposit to the Wallet Contract's `rlp_execute` is not refunded on success, only on failure - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point is `#[payable]` and accepts an arbitrary `attached_deposit` from any external (non-owner) caller/relayer that submits a signed Ethereum-style transaction on behalf of the eth-implicit account owner [1](#0-0) . The amount actually required to execute the decoded action is determined independently from the RLP-encoded Ethereum transaction's `value`/`yocto_near` fields, not from `attached_deposit` itself. The contract only refunds the external caller's `CallerDeposit` when the resulting cross-contract promise **fails**; when it **succeeds**, no comparison is made between what was attached and what the action actually needed, so any surplus is silently retained by the wallet's own account balance with no path back to the caller.

### Finding Description
`inner_rlp_execute` builds an `ExecutionContext` directly from `env::attached_deposit()` [2](#0-1)  and separately constructs a `CallerDeposit` to track that value only for later refund purposes [3](#0-2) . The actual action to be executed (its NEAR "value"/deposit) is derived from the ABI/RLP-decoded Ethereum transaction fields (`yocto_near`, `Wei` value) via `parse_rlp_tx_to_action`, which is entirely independent of how much the external caller attached to the `rlp_execute` call itself.

In `rlp_execute_callback`, the refund logic is asymmetric:
- On `PromiseResult::Failed`, the full `CallerDeposit` is refunded to the caller [4](#0-3) .
- On `PromiseResult::Successful`, there is **no** check that `attached_deposit` matches the amount actually consumed by the action; the function simply returns success with no comparison or partial refund [5](#0-4) .

This is confirmed by `test_caller_refunds`: an external `caller` attaches 3 NEAR to fund a `register` call that only strictly needs a small registration deposit. On the failing path, the caller's balance decrease is `< deposit_amount` (refunded) [6](#0-5) . On the succeeding path, the assertion only checks the decrease is `>= deposit_amount`, i.e. the entire attached deposit is consumed/absorbed regardless of what the action itself required, with no logic anywhere that would return any unused portion to the external caller [7](#0-6) .

This mirrors the reported Solidity bug class: an "amount" is specified independently of the caller-supplied value (`msg.value` analog = `attached_deposit`), the code path only "checks/refunds" one side of the inequality (failure case), and any surplus over what was actually needed is not returned to the sender — it is absorbed permanently by the receiving contract/account (the wallet), which the depositing party (an external relayer, not the wallet owner) does not control.

### Impact Explanation
Any external, unprivileged relayer account that calls `rlp_execute` with `attached_deposit` (via `#[payable]`) greater than what the decoded action actually requires permanently loses the difference into the eth-implicit wallet's account balance if the resulting promise happens to succeed. There is no mechanism to reclaim this excess: `CallerDeposit`-based refunds are wired only to the `Failed` branch of `rlp_execute_callback`. This is a genuine unauthorized value transfer/loss of funds for the relayer (the depositor), moving NEAR tokens they did not intend to give away into an account they do not own or control, triggerable by a single transaction/RPC call from any account. It fits the "unauthorized value movement" / "permanently frozen (from the depositor's perspective) funds" category.

### Likelihood Explanation
Reachable trivially by any account acting as relayer for a Wallet Contract instance: attach any deposit to `rlp_execute` larger than the action's specified value and have the inner promise succeed. No special privileges, validator status, or malicious peer/node behavior needed — only a signer submitting a normal transaction/RPC call, matching the required exploitability bar (unprivileged transaction signer / RPC caller).

### Recommendation
In `rlp_execute_callback` (and generally whenever `CallerDeposit` is tracked), compare the tracked `attached_deposit` against the amount actually consumed by the executed action on the success path as well, and refund any positive difference to `caller_deposit.account_id`, symmetric to the existing failure-path refund logic at `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:296-312`.

### Proof of Concept
1. Deploy the Wallet Contract to an eth-implicit account (as in `TestContext::new`).
2. As an external, non-owner account (`worker.root_account()`), sign and submit an Ethereum-style tx via `rlp_execute_from` whose decoded action requires only a small NEAR amount (e.g., a `register` call needing ~0.32 NEAR, as in `test_caller_refunds`), but attach a much larger `attached_deposit` (e.g., 3 NEAR) to the outer `rlp_execute` call.
3. Ensure the inner cross-contract call succeeds (target `address_registrar.id()` instead of a fake account, per the second half of `test_caller_refunds`).
4. Observe the caller's balance decreases by the *entire* attached deposit (≥ 3 NEAR), not just the amount the action required, and that the excess remains in the wallet contract's account balance with no code path returning it to the caller [7](#0-6) .

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
