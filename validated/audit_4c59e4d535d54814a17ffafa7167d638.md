## Finding: `ensure_match_transaction_info` Never Validates the State-Checkpoint Root, Making Replay/Backup Verification Blind to State-Root Divergence

This is a genuine local analog of the reported bug class (a verification routine that silently omits fields that are actually part of the authenticated commitment), independently confirmed in the codebase.

### Title
Replay/backup verification (`ensure_match_transaction_info`) never checks `state_checkpoint_hash`, so state-root divergence bugs pass verification undetected - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionInfo` commits to a transaction's `state_checkpoint_hash` (and, for V1, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`), and these fields are part of the accumulator-proven `TransactionInfo` hash [1](#0-0) . However, `TransactionOutput::ensure_match_transaction_info` — the routine used to confirm that a freshly re-executed transaction output matches a trusted `TransactionInfo` — checks status, gas, write-set hash, and event root hash, but never checks the checkpoint hash(es) at all, a gap the code itself documents [2](#0-1) .

### Finding Description
`ensure_match_transaction_info` is the sole cross-check used by:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, the routine backing `VerifyExecutionMode`, which re-executes a chunk of transactions and diffs the result against a trusted (accumulator-proven) `TransactionInfo` list [3](#0-2) .
- `storage/db-tool/src/replay_on_archive.rs`, the `replay-verify`-style tool that re-executes historical transactions from backup and validates them against expected `TransactionInfo`s [4](#0-3) .
- `aptos-move/aptos-debugger` and `aptos-move/cli/src/commands.rs` (debugger/simulation replay tooling).

In all of these, the only fields actually compared to the trusted `TransactionInfo` are `status`, `gas_used`, `state_change_hash` (write-set hash), and `event_root_hash` [5](#0-4) . The `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields — which are the state-tree root commitments and are hashed into the same `TransactionInfo` that is authenticated by the transaction accumulator — are never compared. This is explicitly acknowledged in a TODO left in the code:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [6](#0-5) 

Critically, this gap is not limited to the not-yet-enabled `position_state_checkpoint_hash`/hot-state fields gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS` [7](#0-6) . The base `state_checkpoint_hash` field — used by every ordinary block/state checkpoint on mainnet today — is likewise never validated in this comparator, since the same function body applies to all cases.

By contrast, the actual commit path (`DoLedgerUpdate::assemble_transaction_infos`) correctly derives `state_checkpoint_hash` and folds it into the `TransactionInfo` whose hash becomes an accumulator leaf [8](#0-7) , so the state root is properly bound for normal consensus commit. The blind spot is specifically in the independent re-verification path (`verify_execution`/replay-verify/db-tool), whose entire purpose is to catch determinism or state-computation bugs by comparing a locally re-derived result against the trusted, accumulator-proven `TransactionInfo`.

### Impact Explanation
If a bug in state-tree computation (e.g., JMT merge, sharding, or a future protocol change) produces a state root that diverges from the correct/expected value while write set contents, events, gas, and status remain identical, `ensure_match_transaction_info` will report a match. Consequently:
- `chunk_executor::verify_execution` (used to validate replayed backups/archives before considering them trustworthy) will falsely report success.
- `db-tool replay_on_archive`, the tool operators/auditors run specifically to detect state-root divergence across software versions (e.g., before enabling a new on-chain feature or during a hard-fork readiness check), will falsely report success.

This directly undermines a proof/verification invariant explicitly in scope ("Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state"): a corrupted or non-deterministic state root can pass the exact mechanism designed to catch it.

### Likelihood Explanation
The gap is unconditional (not behind a feature flag) for the base `state_checkpoint_hash` field, and is directly reachable by anyone running the shipped `db-tool replay-verify`/`aptos-debugger` tooling, or by the chunk executor's `VerifyExecutionMode` path during backup/replay validation. It requires an underlying state-computation divergence to be masked (this is not itself a way to corrupt live committed mainnet state, since the primary commit path still correctly binds `state_checkpoint_hash` into the accumulator-proven `TransactionInfo`), but the impact is real: it silently disables the safety net meant to detect exactly this kind of divergence.

### Recommendation
Extend `ensure_match_transaction_info` to recompute the state checkpoint root from post-execution state (when available/applicable) and compare it against `txn_info.state_checkpoint_hash()` (and, once enabled, `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()`), removing the TODO gap before any code path relies on this function as a correctness guarantee.

### Proof of Concept
Not applicable as a live-exploit PoC (this is a detection/verification-tooling gap, not a way to corrupt committed state); the root cause is demonstrated directly by the code at [2](#0-1)  and its callers at [3](#0-2)  and [4](#0-3) : constructing a `TransactionOutput` whose write set/events/gas/status match a given `TransactionInfo` but whose corresponding state tree root differs will pass `ensure_match_transaction_info` without error, regardless of the state divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
