### Title
Stale `storageRowStore` entries persist after `SELFDESTRUCT`, enabling storage collision on CREATE2 address reuse - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
`RepositoryImpl.deleteContract(byte[])` removes an address's entries from `getCodeStore()`, `getAccountStore()`, and `getContractStore()` when a contract self-destructs, but never clears the corresponding rows in `StorageRowStore`. Because CREATE2 addresses are fully attacker-controlled and deterministic (`WalletUtil.generateContractAddress2`), an attacker can destroy a contract and redeploy new code to the identical address, inheriting the old contract's leftover storage values.

### Finding Description
`SELFDESTRUCT` (`SUICIDE`/`SUICIDE2`) is handled in `Program.suicide`/`suicide2` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:451-582`), which transfers balance/resources and calls `getResult().addDeleteAccount(...)`. This is ultimately committed via `ContractState.deleteContract` → `RepositoryImpl.deleteContract`: [1](#0-0) 

only three stores are cleaned - `getCodeStore()`, `getAccountStore()`, `getContractStore()`. The `StorageRowStore` (which persists each contract's key/value storage slots, keyed by `addrHash = sha3(address)` plus the slot key, see `actuator/src/main/java/org/tron/core/vm/program/Storage.java:29-59`) is never touched by `deleteContract`.

When a contract is later deployed to the *same* address via `CREATE2`, address computation is fully deterministic and attacker-controlled: [2](#0-1) 

In `Program.createContractImpl` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:812-873`), the reuse path is:
- `existingAccount = getContractState().getAccount(newAddress)` returns `null` because `deleteContract` already removed the account entry.
- `contractAlreadyExists` becomes `false`, so a brand-new account/contract entry is created at the same address and the constructor of the new contract runs.

However, the `Storage` object for that address (`Storage(byte[] address, StorageRowStore store)`) derives row keys purely from `addrHash(address)` and the storage slot key - independent of contract code/version identity. Because the old contract's rows were never deleted from `StorageRowStore`, the redeployed contract's `SLOAD`s on the same slot indices will return the previous contract's stale values instead of the EVM/TVM-expected zero-initialized storage.

Existing checks do not prevent this: `canSuicide`/`canSuicide2` only gate freeze-related conditions, not storage cleanup; `isContractExist` in the Constantinople path only decides whether account metadata is treated as "already existing" (it is not, since the account row was deleted) - it does not perform any storage wipe either.

### Impact Explanation
This is a genuine state/accounting-corruption bug (TRON bounty class: asset/accounting corruption / unauthorized state change). A redeployed contract at a reused CREATE2 address can silently inherit non-zero storage slots from a self-destructed predecessor. If the new contract's logic relies on default-zero storage for security-relevant state (e.g., an "initialized"/"owner" flag, an allowance/balance mapping, a reentrancy guard), this stale data can let the deployer bypass initialization logic or grant itself privileges/state that should not exist for a freshly deployed contract, corrupting the contract's internal accounting. The impact is scoped to state stored under the reused address in `storageRowStore`; it does not by itself corrupt account balances in `AccountStore` (those are correctly wiped), and it does not affect other addresses' storage.

### Likelihood Explanation
- Precondition: an ordinary funded account able to broadcast `CreateSmartContract`/`TriggerSmartContract` transactions - no privileged role needed.
- Attack requires TVM Constantinople-era CREATE2 support (`allowTvmConstantinople`), which is standard/default-enabled on current java-tron networks.
- The attacker fully controls the CREATE2 `salt` and initcode, so address collision is deterministic (not a hash-collision attack) and 100% repeatable at will, at the cost of ordinary deployment/energy fees for two contract creations plus one `SELFDESTRUCT` call.
- The only extra requirement is that the attacker's own second contract deliberately (or via bugged reliance on "storage always starts zero") reads those pre-existing slots — this is exactly the scenario the question's PoC targets.

### Recommendation
Extend `RepositoryImpl.deleteContract` (and/or the `SUICIDE`/`SUICIDE2` commit path) to also purge all `StorageRowStore` rows belonging to the destroyed address's `addrHash` prefix before the address can be reused, or block address reuse for storage purposes by keying storage row hashing on a component that changes across the contract's lifetime (e.g., contract creation nonce/hash) rather than solely on the static account address.

### Proof of Concept
```java
// Pseudocode JUnit outline based on existing test infra (ProgramResultTest / FreezeV2Test style)
@Test
public void selfdestructRedeployStorageCollisionTest() throws Exception {
  // 1. Deploy contract A via CREATE2 with salt S using TvmTestUtils, e.g. factory.deploy(S, codeA)
  byte[] addrA = WalletUtil.generateContractAddress2(factoryAddr, salt, codeA);
  // A's constructor sets storage slot 0 = 0x1 (e.g., "initialized" flag)

  // 2. Call A.destroy() -> triggers SELFDESTRUCT -> RepositoryImpl.deleteContract(addrA)
  triggerSuicide(ownerAddr, addrA, ownerAddr);
  Assert.assertNull(dbManager.getAccountStore().get(addrA));
  Assert.assertNull(dbManager.getContractStore().get(addrA));

  // 3. Directly inspect storageRowStore for addrA's addrHash-derived key - it is NOT cleared
  byte[] rowKey = Storage.compose(slot0Key, Hash.sha3(addrA)); // conceptually
  Assert.assertNotNull(dbManager.getStorageRowStore().get(rowKey)); // BUG: stale row survives

  // 4. Redeploy contract B (different code, no explicit initializer) to the SAME address
  //    via CREATE2 with identical salt S -> newAddress == addrA (deterministic)
  factory.deploy(salt, codeB); // succeeds because account/contract entries were wiped

  // 5. B reads slot 0 expecting default zero (uninitialized) but observes leftover 0x1
  DataWord leftover = repository.getStorageValue(addrA, DataWord.ZERO());
  Assert.assertNotEquals(DataWord.ZERO(), leftover); // demonstrates storage collision / stale state
}
```
Expected (buggy) result: step 5 shows the freshly-deployed contract B inherits the "initialized" flag (or any other slot value) left behind by the destroyed contract A, confirming `deleteContract` fails to purge `storageRowStore`, allowing state corruption on address reuse.
