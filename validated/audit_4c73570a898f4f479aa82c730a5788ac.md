## Title
Panic-based DoS via unvalidated empty-calldata L1 handler message hashing - (File: `crates/starknet_api/src/hash.rs`)

### Summary
`l1_handler_message_hash` (invoked via `L1HandlerTransaction::calc_msg_hash`) unconditionally calls `calldata.0.split_first().expect("Invalid calldata, expected at least from_address")` to peel off the "from address" element before hashing the L1→L2 message payload. `Calldata` has no non-empty invariant and `starknet_api::transaction::L1HandlerTransaction` derives `Deserialize`, so a transaction with zero-length calldata is a constructible value at the type level, as explicitly documented in the codebase's own regression test for the sibling function `payload_size` [1](#0-0) .

### Finding Description
`l1_handler_message_hash` reads the first calldata element via `.expect(...)`, which panics if `calldata.0` is empty [2](#0-1) . This mirrors the CVE-2015-8744 bug class: a fixed "header" field (here, the mandatory `from_address` prefix of L1 handler calldata) is read without first checking that the input is large enough to contain it, causing an unhandled panic/crash instead of a clean rejection. In contrast, the sibling accessor `payload_size` on `executable_transaction::L1HandlerTransaction` was hardened against exactly this case using `saturating_sub`, with an explicit comment and regression test noting that `Calldata` has no non-empty invariant and empty calldata is constructible via `Deserialize` [3](#0-2) . `calc_msg_hash` was not given the same treatment.

### Impact Explanation
A panic in a shared library function used inside sequencer processes (gateway/RPC/OS re-execution paths that compute or verify L1↔L2 message hashes) can crash the calling service, denying availability to that component (DoS), and in a synchronous/inline `expect()` panic context inside a `tokio` task without `catch_unwind`, could crash the owning process/thread. This matches the CVE analog's "small/malformed input crashes the message-processing component" DoS class.

### Likelihood Explanation
I could not fully confirm, within the available tool budget, a concrete unauthenticated end-to-end call path that reaches `calc_msg_hash`/`l1_handler_message_hash` with an *empty* calldata `L1HandlerTransaction` that has not already passed through calldata-non-empty validation. All L1-message-derived transaction constructors I found (`send_message_to_l2`, `From<MessageFromL1> for L1HandlerTransaction`, `From<L1HandlerTransaction> for L1ToL2Message`) always prepend a `from_address` element, so calldata length ≥ 1 in the "happy path" from a real L1 contract event [4](#0-3) . The residual risk is any RPC/API code path (e.g. `apollo_rpc/src/v0_8/api/api_impl.rs`, which calls `calc_msg_hash` per `grep_search`) that accepts a raw/attacker-supplied `L1HandlerTransaction` JSON body (rather than routing through the `MessageFromL1` wrapper) — I was not able to inspect that call site's exact input validation before running out of iterations.

### Recommendation
Harden `l1_handler_message_hash` (and `calc_msg_hash`) to return a `Result`/error instead of panicking on empty calldata, matching the pattern already used for `payload_size`, and add an explicit stateless validation rule (in `apollo_gateway`'s stateless transaction validator) rejecting L1 handler transactions with empty calldata before they reach any hash computation.

### Proof of Concept
Not independently verified end-to-end due to inability to trace the exact untrusted-input call path into `calc_msg_hash` within the tool budget; the panic itself is trivially reproducible in isolation:
```rust
let tx = starknet_api::executable_transaction::L1HandlerTransaction {
    tx: starknet_api::transaction::L1HandlerTransaction {
        calldata: Calldata(Arc::new(vec![])), // empty
        ..Default::default()
    },
    ..Default::default()
};
tx.tx.calc_msg_hash(); // panics: "Invalid calldata, expected at least from_address"
``` [5](#0-4) 

**Caveat:** Given the ambiguity in confirming a fully unauthenticated reachable path (as opposed to internally-constructed transactions that are already guaranteed non-empty by their producers), this finding should be treated as **medium-confidence** rather than a fully proven exploit chain — further investigation of `apollo_rpc/src/v0_8/api/api_impl.rs`'s two `calc_msg_hash` call sites is needed to confirm whether attacker-controlled empty calldata can reach this function without prior validation.
