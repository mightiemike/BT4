### Title
`liquidate-multi` strands a liquidator's repaid debt tokens when a later step of `liquidate` fails, because failures are absorbed instead of propagated - (File: `local-testing/contracts/market/market.clar`)

### Summary
`liquidate-multi` calls `call-liquidate` via `map`, which invokes the public `liquidate` function directly (not via `contract-call?`). `liquidate` first pulls debt tokens from the liquidator through a genuine `contract-call?` (`vault-system-repay` → vault's `system-repay` → `receive-underlying`), and only afterward performs the market-vault bookkeeping steps (`debt-remove-scaled`, `collateral-remove`) using their own separate `contract-call?`s.

### Finding Description
In Clarity, automatic state rollback on error only occurs at the boundary of the specific `contract-call?` that returned the error — it does not retroactively undo the effects of earlier, already-succeeded `contract-call?`s made by the same enclosing (directly-called) function. `local-testing/contracts/market/market.clar:1519-1530` executes, in order:
1. `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))` — a `contract-call?` that pulls `debt-to-repay` tokens from the liquidator (`tx-sender`) into the vault and commits immediately on success.
2. `(try! (contract-call? .market-vault debt-remove-scaled borrower scaled-to-remove debt-aid))`
3. `(try! (contract-call? .market-vault collateral-remove account amount ft asset-id collateral-receiver))` (this is the collateral payout step).

If step 2 or 3 fails for any reason (e.g., a stale/edge-case bookkeeping mismatch, rounding boundary, or a disabled/misconfigured collateral asset for that specific borrower at that specific moment), `liquidate` returns `(err ...)`. Because `liquidate-multi` invokes `liquidate` only through the plain function call chain `map → call-liquidate → liquidate` (`local-testing/contracts/market/market.clar:1616-1622`, `local-testing/contracts/market/market.clar:929-940`) and never wraps that inner call with `try!`, the resulting `err` is simply captured as one element of the response list — it does **not** abort or roll back `liquidate-multi`'s overall transaction, and it does **not** retroactively undo step 1's already-committed `contract-call?` effects.

### Impact Explanation
The liquidator's debt-token payment made in step 1 (`vault-system-repay`) is permanently consumed by the vault (debt reduced / interest booked) while the liquidator receives no collateral in return for that specific position, because the failure happened downstream of the token pull. This is a temporary/permanent freezing (effectively loss) of the liquidator's funds for that position within `liquidate-multi`, landing on the in-scope "temporary freezing of funds" (or theft-adjacent loss for the liquidator) impact class — the funds are not stranded in a recoverable pending state, they are consumed by the vault's own accounting with no compensating collateral transfer, and no revert occurs to return them.

### Likelihood Explanation
This requires one of the batched liquidation legs in `liquidate-multi` to reach the `debt-remove-scaled` or `collateral-remove` step and fail there specifically (after the repay step already succeeded) — e.g. via a race between two legs of the same batch touching overlapping state, a borrower's position changing mid-batch (partial liquidation by a leg earlier in the same `positions` list altering `pos-full`/collateral available for a later leg on the same borrower), or an edge-case in `scale-debt-for-liquidation`/`collateral-remove` bounds checks. This is plausible specifically because `liquidate-multi` is documented as processing multiple positions "atomically" per call but deliberately not reverting on a per-leg failure, and batches can reference the *same* borrower/asset combination across multiple entries in the `positions` list, allowing an earlier leg's mutation to affect a later leg's evaluation without a fresh top-level abort boundary protecting the whole batch.

### Recommendation
Ensure that any state-changing steps of `liquidate` that occur before a possible failure point are not committed independently of the overall outcome for that leg. Concretely: reorder `liquidate` so that the collateral/debt bookkeeping calls (`debt-remove-scaled`, `collateral-remove`) that can fail are evaluated and validated (or at least attempted) before the token-pulling `vault-system-repay` step executes, or otherwise ensure the entire per-position leg is wrapped so that a failure in a later step causes the earlier `contract-call?` effects to be reverted (e.g., by having `call-liquidate` explicitly refund/undo any partial repay before returning the error, or restructure `liquidate` so token movement is the last, not an early, side-effecting call).

### Proof of Concept
1. Borrower B has a liquidatable position with debt asset USDC and collateral asset X.
2. `liquidate-multi` is called with two entries for the same borrower B: leg 1 liquidates part of B's USDC debt against collateral X; leg 2 (same borrower, same collateral) is crafted (or occurs due to natural position shifts from leg 1) such that by the time leg 2 executes, `find-collateral-amount`/`scale-debt-for-liquidation` bounds computed from data read at the start of leg 2 no longer match the just-mutated position from leg 1, causing the `collateral-remove` (or `debt-remove-scaled`) `contract-call?` in leg 2 to fail its own internal invariant and return `err`.
3. By this point in leg 2's execution of `liquidate`, `vault-system-repay` has already executed successfully in `local-testing/contracts/market/market.clar:1519`, pulling the liquidator's USDC into the vault via `receive-underlying` (`local-testing/contracts/vault/vault-usdc.clar:924`).
4. `liquidate` returns `(err ...)` for leg 2; `call-liquidate` returns that same `(err ...)`; `map` in `liquidate-multi` (`local-testing/contracts/market/market.clar:1622`) simply stores it in the output list; the overall `liquidate-multi` call still returns `(ok (list ... (err ...)))`.

(define-public (system-repay (amount uint))
  (let (
        (states (var-get pause-states))
        (u (try! (accrue)))
        (scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (debt (total-debt))
        (total-borrowed-amount (var-get total-borrowed))
        (capped-amount (if (> amount debt) debt amount))
        (principal-reduction (calc-principal-ratio-reduction capped-amount scaled-principal debt))
        (capped-reduction (if (> principal-reduction scaled-principal) scaled-principal principal-reduction))
        (updated-scaled-principal (- scaled-principal capped-reduction))
        (principal-repaid (mul-div-down capped-amount total-borrowed-amount debt))
        (interest-paid (- capped-amount principal-repaid))
        (total-borrowed-new (if (> total-borrowed-amount principal-repaid) (- total-borrowed-amount principal-repaid) u0)))

    (try! (check-caller-auth))
    (asserts! (not (get repay states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-underlying capped-amount tx-sender))
    (var-set principal-scaled updated-scaled-principal)
    (var-set total-borrowed total-borrowed-new)
    (var-set assets (+ (var-get assets) interest-paid))

    (print {
      action: "system-repay",
      caller: contract-caller,
      data: {
        amount-requested: amount,
        amount-repaid: capped-amount,
        principal-repaid: principal-repaid,
        interest-paid: interest-paid,
        principal-scaled: updated-scaled-principal,
        total-borrowed: total-borrowed-new,
        assets: (var-get assets),
        index: idx
      }
    })

    (ok true)))
