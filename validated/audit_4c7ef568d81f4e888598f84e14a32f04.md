### Title
Rounding-Direction Ambiguity in Workflow Metering Credit Conversion Allows Systematic Credit Underbilling - (File: `core/services/workflows/metering/balance_store.go`)

### Summary
The workflow-metering `balanceStore` converts between resource-usage units (gas, compute, etc.) and universal "credits" using standard (nearest-value) decimal rounding instead of rounding consistently against the caller. Because this conversion is invoked on every `Deduct`/`Settle` cycle for every capability step of every workflow execution, an unprivileged workflow author can repeatedly trigger conversions that round in their favor, systematically under-deducting credits relative to actual resource consumption — the same rounding-direction bug class described in the report, applied to Chainlink's CRE/workflow billing path instead of a Solana staking pool.

### Finding Description
`convertToBalance` and `convertFromBalance` perform the tokens/credits-equivalent conversion with no caller-supplied rounding direction: [1](#0-0) 

For gas-type resources it calls `amount.Div(rate).Round(defaultDecimalPrecision)` [2](#0-1)  — `decimal.Round` rounds to the nearest value (round-half-away-from-zero), which can round the resulting credit amount *down* relative to the true resource cost about as often as it rounds up. There is no `RoundDirection`/ceiling option to guarantee the deduction never underestimates true cost, unlike the SPL `pool_tokens_to_trading_tokens` reference remediation in the report.

This conversion is the authoritative basis for local balance debits during workflow execution:
- `MinusAs` deducts `balToMinus := bs.convertToBalance(resourceType, amount)` from the reserved balance [3](#0-2) .
- `Report.Settle` converts each capability's actual spend value to credits via `r.balance.ConvertToBalance(unit, value)` and refunds `step.Deduction.Sub(spentCredits)` back to the pool after each capability step of a workflow execution [4](#0-3) .

Because `Settle` is called once per capability step and workflows can chain an attacker-controlled number of capability invocations (each with attacker-influenced parameters/loop counts that shape the reported `SpendValue`), a workflow author who is fully unprivileged with respect to the billing service can select spend values that land just below rounding boundaries. Each such step causes `spentCredits` to be computed slightly lower than the true resource cost, so more of the earmarked `step.Deduction` is refunded to the local balance than should be. Repeating this over many steps/executions (the same "napkin math + PoC script" pattern used in the report to show repeated exploitability) drains real resource usage from the node/billing service while consuming fewer credits than intended — a direct financial/accounting-tampering impact on the billing invariant documented in `doc.go`: "Metering ... value ... converted to a balance value to be deducted" [5](#0-4) .

### Impact Explanation
This is a misreporting/data-tampering class issue against the billing invariant: an unprivileged workflow author (no special node/operator privilege required) can cause the local credit ledger to systematically under-charge for actual compute/gas resource consumption, and because `AddSpent`/`Settle` results feed into `SubmitWorkflowReceipt` to the billing service [6](#0-5) , this translates into real-world under-billing that can be repeated across many capability steps and many workflow executions, similar to how the original report showed repeatable extraction from a staking pool.

### Likelihood Explanation
Reachability requires only the ability to author/execute a workflow with multiple capability calls with attacker-influenced parameters (a standard, unprivileged CRE user capability), and the rounding boundary is a pure arithmetic property of `decimal.Round`/`Div` with no direction control — no privileged access, malicious peer, or cryptographic break is needed, making the precondition realistic and the exploit path directly reachable in production.

### Recommendation
Adopt the same fix pattern the report recommends: pass an explicit rounding direction (e.g., always round in favor of the billing service/node — ceiling when computing credits owed, floor when computing resource entitlements granted for a given credit balance) into `convertToBalance`/`convertFromBalance`, and audit all callers (`MinusAs`, `AddAs`, `Settle`, `creditToSpendingLimits`) to ensure debits always round up and credits/refunds always round down.

### Proof of Concept
1. Configure a resource conversion rate (e.g., gas rate) such that a chosen `SpendValue` reported by a capability produces a non-terminating decimal quotient in `convertToBalance` (`amount.Div(rate)`), landing just below the `.Round(defaultDecimalPrecision)` rounding boundary.
2. Author a workflow invoking that capability with parameters (loop count, batch size, etc.) chosen so the reported `SpendValue` repeatedly hits this rounding-down boundary — this is workflow-author controlled input, not privileged.
3. Each `Settle` call computes `bal` slightly less than the true resource cost [7](#0-6) , so `step.Deduction.Sub(spentCredits)` refunds more credit back to the balance than the resources actually consumed warrant [8](#0-7) .
4. Repeat across many steps/executions to accumulate a measurable gap between credits charged and actual resource consumption, mirroring the report's "profit/cost" repeated-exploit methodology.

```go
// convertToBalance converts a resource dimension amount to a credit amount.
// This method should only be used under a read lock.
func (bs *balanceStore) convertToBalance(fromResourceType string, amount decimal.Decimal) (decimal.Decimal, error) {
	rate, ok := bs.conversions[fromResourceType]
	if !ok {
		return amount, ErrResourceTypeNotFound
	}

	// Special case for gas as gas token conversions are provided in amount per credit.
	// Other rates are provided as the inverse.
	if isGasSpendType(fromResourceType) {
		if rate.IsZero() {
			return decimal.Zero, nil
		}

		return amount.Div(rate).Round(defaultDecimalPrecision), nil
	}

	return amount.Mul(rate), nil
}
```

```go
// MinusAs lowers the current credit balance based on an amount of resource dimensions.
func (bs *balanceStore) MinusAs(resourceType string, amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	balToMinus, err := bs.convertToBalance(resourceType, amount)
	if err != nil {
		return err
	}

	if balToMinus.GreaterThan(bs.balance) {
		return ErrInsufficientBalance
	}

	bs.balance = bs.balance.Sub(balToMinus)

	return nil
}
```
