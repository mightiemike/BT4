### Title
Gas fee bypass via integer truncation of `baseFee` in `CalculateGasCost` — free EVM execution funded by module burn allowance - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`Keeper.CalculateGasCost` truncates the network `baseFee` (an 18-decimal `sdkmath.LegacyDec`) down to whole `upc` units via integer division (`baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))`). If the actual base fee is a fractional amount of `upc` per gas unit (i.e., less than `1e18` in the internal `LegacyDec` representation, meaning "less than 1 upc"), this division truncates `baseFeeBig` to `0`. `effectiveGasPrice` is then `0`, so `gasCost = effectiveGasPrice * gasUsed = 0` regardless of how much gas was actually consumed. `Keeper.DeductGasFeesFromReceipt` explicitly special-cases this: `if gasCost.Sign() <= 0 { return nil }`, silently skipping `DeductAndBurnFees` entirely. ### Finding Description
`DeductGasFeesFromReceipt` is the sole gate that charges a UEA/CEA recipient for the module-originated EVM call it just performed via `DerivedEVMCall`. It computes cost from `CalculateGasCost(baseFee, maxFeePerGas, maxPriorityFeePerGas, receipt.GasUsed)` and only calls `DeductAndBurnFees` when `gasCost.Sign() > 0`.

The bug is in how `baseFee` is unwrapped: the code assumes `baseFee` (fetched from `feemarketKeeper.GetBaseFee`) always represents a whole number of `upc` per gas unit, and recovers that whole number by doing `baseFeeBig.Div(baseFeeBig, 1e18)` on the `LegacyDec`'s internal representation. This is an integer/floor division — any base fee whose real magnitude is below `1` `upc`/gas (i.e., the internal `LegacyDec` value is below `1e18`) is floored to exactly `0`. The step-1 validation (`maxFeePerGas.Cmp(baseFeeBig) < 0`) then trivially passes for any non-negative `maxFeePerGas`, and the final gas cost multiplication collapses to `0 * gasUsed = 0`, no matter how large `receipt.GasUsed` is.

Because the base fee is dynamically adjusted by the EIP-1559-style fee market based on network congestion, it can and will fall to values below `1 upc`/gas during periods of low chain usage — this is normal, honest-validator, honest-node behavior, not an attack requiring privileged actors. Any ordinary unprivileged user submitting a `UniversalPayload` for execution during such a period gets their EVM call executed by the module (funded through `DerivedEVMCall`/module gas advance) with zero fee deducted and zero coins burned, bypassing the fee-accounting invariant entirely.

### Impact Explanation
This corrupts gas fee accounting: EVM execution paid for by the module (or the network gas budget) is not reimbursed by the recipient at all when the truncation condition is hit, regardless of `receipt.GasUsed`. This falls under the in-scope impact "corruption of ... gas fee accounting ... reachable from ordinary user ... payloads" since it requires no malicious validator, relayer, or admin — only a naturally occurring low base-fee condition combined with an ordinary payload submission.

### Likelihood Explanation
Likelihood depends on the feemarket's base-fee dynamics and the actual decimal scale relationship between `upc` and the EVM's smallest denomination unit as used by the feemarket module. If the feemarket ever produces a base fee smaller than 1 whole `upc` per gas (which is plausible under low congestion or immediately post-genesis when the base fee is initialized low), every subsequent payload execution during that window is fee-free until the base fee rises back above 1 `upc`.

### Recommendation
Do not floor-truncate the base fee to whole `upc` units. Perform the entire cost calculation in the `LegacyDec` (or full-precision) domain and only convert to the final integer `upc` amount at the very end (rounding up, not down), e.g. `gasCost = ceil(baseFee_asDec * gasUsed)`, so fractional base fees still produce a non-zero, correctly rounded charge. Additionally, consider treating `gasCost.Sign() <= 0` as an error condition (or logging/alerting) rather than silently skipping fee deduction, since a legitimate zero-cost outcome should be extremely rare and worth flagging.

### Proof of Concept
1. Assume network state where `feemarketKeeper.GetBaseFee(ctx)` returns a `LegacyDec` whose value is, e.g., `0.5` `upc` (internal representation `5*10^17`) — a realistic outcome of the fee market under low block utilization.
2. Submit an ordinary `UniversalPayload` with `MaxFeePerGas = 1` (or any value ≥ 0) and any `GasLimit`; execute it through the normal inbound/payload execution path so that `receipt.GasUsed = 100000` (nonzero).
3. In `CalculateGasCost`: `baseFeeBig := 5*10^17; baseFeeBig.Div(baseFeeBig, 1e18) == 0`. `maxFeePerGas (1) >= 0` passes. `effectiveGasPrice = 0`. `gasCost = 0 * 100000 = 0`.
4. In `DeductGasFeesFromReceipt`: `gasCost.Sign() <= 0` is true → function returns `nil` without calling `DeductAndBurnFees`.
5. Assert: the recipient's balance is unchanged (no fee burned) despite `receipt.GasUsed = 100000` — confirming the fee-bypass, in violation of the expected invariant that any nonzero `GasUsed` must produce a nonzero, correctly rounded fee charge.
