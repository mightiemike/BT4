### Title
Stale-class-cache use bypasses declaration validity for Cairo 0 classes - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` serves compiled classes from a process-global, long-lived `ContractClassManager` cache (`GlobalContractCache`). For Cairo 1 (V1/V1Native) classes it re-validates a cache hit against the current committed state via `is_declared`, explicitly because "existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)". For Cairo 0 (V0) classes this re-validation is skipped entirely (`RunnableCompiledClass::V0(_) => {}`), and it cannot be added trivially because `FetchCompiledClasses::is_declared` is documented and implemented (`crates/apollo_state_reader/src/apollo_state.rs`) to "always return `false`" for Cairo 0 classes. [1](#0-0) [2](#0-1) 

### Finding Description
The `ContractClassManager` (`GlobalContractCache`, backed by `Arc<Mutex<SizedCache>>`) is populated any time `get_compiled_classes` succeeds against the underlying committed-state reader, and it is never invalidated per class hash — only wholesale via `clear()`. [3](#0-2) [4](#0-3) 

The code comment at line 76-78 acknowledges that a cached class can outlive the block that declared it, e.g. after a reverted block, and for that reason a Cairo 1 hit is re-checked against `state_reader.is_declared`. However, the same hazard applies equally to Cairo 0 classes, and for those the mitigating check is structurally impossible: `FetchCompiledClasses::is_declared` is defined to only ever report on Cairo 1 declarations ("Cairo 0 classes always return `false`"), and `ApolloReader::is_declared` implements this by checking `get_class_definition_block_number`, which is populated only for Sierra (Cairo 1) declarations. So a V0 cache hit is returned unconditionally with no cross-check against the authoritative committed declaration state at all. [5](#0-4) 

The compiled-class cache is looked up via `StateReader::get_compiled_class`, which is the exact call made from execution paths reachable by any transaction sender or L1 message: e.g., `execute_replace_class` reads the class to verify declaration before switching a contract's class, and `Deploy`/constructor execution resolves the compiled class of the deployed class hash. [6](#0-5) 

Because the state view fed into `StateReaderAndContractManager` reflects a specific block's committed state, and Starknet nodes/sequencers can observe state that is later invalidated (block reversions/reorgs at the L2 sequencer level, discarded speculative/candidate blocks, or a preconfirmed/optimistic view being rolled back before final commitment), a Cairo 0 class hash that was declared only in such a since-discarded view can remain permanently servable from the cache with no re-validation, unlike its Cairo 1 counterpart.

### Impact Explanation
If a Cairo 0 class becomes cached from a state view that is later invalidated, any subsequent transaction (from any unprivileged sender) referencing that class hash — via `deploy`, constructor `class_hash`, or `replace_class` — can have it silently served from the stale global cache as if it were validly declared in the current canonical state, bypassing the "must be declared" invariant that is otherwise enforced identically for Cairo 1 classes at this exact call site. Consequences include:
- Execution of code the current committed state does not recognize as declared (an unauthorized/never-validated code path being run against real accounts/contracts).
- Divergent execution results between an "honest" node whose class cache never observed the reverted/discarded view (correctly rejects the class as `UndeclaredClassHash`) and a node whose cache still holds the stale V0 entry (executes it) — a state/consensus divergence risk (wrong committed root / honest-node divergence), which is the closest sequencer analog of the underlying "use of a freed/invalidated object" bug class in the CVE.
- Because this affects the trusted server-side execution cache rather than user-supplied data, the asymmetry between V0 and V1 handling here is best classified as a logic/consistency defect in a security-relevant invariant (declaration validity), even though full exploitation requires a state view invalidation event (e.g., an L2 reorg or discarded candidate block) to first populate the stale entry.

### Likelihood Explanation
The asymmetric handling is unconditional and code-level (no config flag), and every reachable path (`deploy`, `replace_class`, `library_call`, etc. for Cairo 0 classes) funnels through `get_compiled_class` → `get_compiled_from_class_manager`. The most difficult precondition is producing the "stale/invalidated declaration" state in the first place (a reverted block, discarded speculative block, or pre-final view later replaced) since Starknet declarations are normally permanent; the actual triggering of the bypass, once such a state exists, requires nothing more than an ordinary transaction referencing the class hash. I could not fully verify from the available context every mechanism inside the batcher/consensus layer by which a previously-read, uncommitted, or later-reverted state view could populate this specific global cache (e.g., whether candidate/optimistic block building shares the same `ContractClassManager` instance as finalized execution) — this would require deeper tracing through `apollo_batcher`'s block-candidate lifecycle and reorg handling, which was not fully available in the indexed context.

### Recommendation
Apply the same anti-staleness check used for Cairo 1 classes to Cairo 0 classes: extend `FetchCompiledClasses::is_declared` (or add a parallel check) to also validate Cairo 0 declaration block numbers against the current `StateNumber`, and call it unconditionally in `get_compiled_from_class_manager` regardless of `RunnableCompiledClass` variant, rather than special-casing `V0(_) => {}`. Alternatively, ensure the `ContractClassManager` cache is authoritatively invalidated (per-class or wholesale) whenever the underlying committed state view it was populated from is discarded/reverted, for both Cairo 0 and Cairo 1 classes.

### Proof of Concept
Conceptual reproduction (exact trigger depends on batcher/reorg internals not fully traceable in this pass):
1. A sequencer node observes (via a candidate/speculative or soon-to-be-reverted state view) a `Declare` of a Cairo 0 class `C` at hash `H`.
2. During execution of that view, `StateReaderAndContractManager::get_compiled_from_class_manager(H)` is invoked (e.g., via a `deploy` or `replace_class` referencing `H`), causing `contract_class_manager.set_and_compile(H, ...)` to populate the global `GlobalContractCache` with `RunnableCompiledClass::V0`.
3. The view containing the declaration of `H` is discarded/reverted (block reorg or discarded candidate), so `H` is no longer declared according to canonical committed state.
4. A new transaction from any user calls `replace_class(H)` or deploys with `class_hash = H`. `get_compiled_from_class_manager` hits the cache, matches `RunnableCompiledClass::V0(_) => {}`, skips any declaration re-check (since `is_declared` cannot report true/false meaningfully for V0), and returns the stale compiled class — executing code for a class hash that current canonical state does not recognize as declared, in contrast to what would happen for an equivalent Cairo 1 class (which would correctly fail with `StateError::UndeclaredClassHash`). use std::sync::{Arc, Mutex, MutexGuard};

use cached::{Cached, SizedCache};

use crate::core::ClassHash;

type ContractLRUCache<T> = SizedCache<ClassHash, T>;
type LockedClassCache<'a, T> = MutexGuard<'a, ContractLRUCache<T>>;

// TODO(Yoni, 1/2/2025): consider defining CachedStateReader.
/// Thread-safe LRU cache for contract classes (Sierra or compiled Casm/Native), optimized for
/// inter-language sharing when `blockifier` compiles as a shared library.
#[derive(Clone, Debug)]
pub struct GlobalContractCache<T: Clone>(pub Arc<Mutex<ContractLRUCache<T>>>);

impl<T: Clone> GlobalContractCache<T> {
    /// Locks the cache for atomic access. Although conceptually shared, writing to this cache is
    /// only possible for one writer at a time.
    pub fn lock(&self) -> LockedClassCache<'_, T> {
        self.0.lock().expect("Global contract cache is poisoned.")
    }

    pub fn get(&self, class_hash: &ClassHash) -> Option<T> {
        self.lock().cache_get(class_hash).cloned()
    }

    pub fn set(&self, class_hash: ClassHash, contract_class: T) {
        self.lock().cache_set(class_hash, contract_class);
    }

    pub fn clear(&mut self) {
        self.lock().cache_clear();
    }

    pub fn new(cache_size: usize) -> Self {
        Self(Arc::new(Mutex::new(ContractLRUCache::<T>::with_size(cache_size))))
    }
}
