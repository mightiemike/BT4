### Title
Unvalidated `ovk` length allows expensive `librustzcashSaplingOutputProof` to be computed before rejection - ([File: framework/src/main/java/org/tron/core/zen/ShieldedTRC20ParametersBuilder.java])

### Summary
`generateOutputProof` calls the native, computationally expensive `JLibrustzcash.librustzcashSaplingOutputProof` before validating that `output.ovk` is exactly 32 bytes. An attacker who submits a shielded TRC-20 mint/transfer/burn request with a malformed `ovk` therefore forces the node to perform the full zk-SNARK output proof generation, which is then discarded when the subsequent length check throws.

### Finding Description
In `generateOutputProof(ReceiveDescriptionInfo output, long ctx)`, the sequence is:
1. `cm`/`pkD` emptiness checks [1](#0-0) 
2. Note encryption via `output.getNote().encrypt(pkD)` [2](#0-1) 
3. The expensive native call `JLibrustzcash.librustzcashSaplingOutputProof(...)` [3](#0-2) 
4. Only **after** the proof is generated does the code check `ArrayUtils.isEmpty(output.ovk) || output.ovk.length != 32` and throw `"ovk is null or invalid and ovk should be 32 bytes (256 bit)"` [4](#0-3) 

This is reachable from `build(boolean withAsk)`, the public entrypoint for constructing mint/transfer/burn shielded TRC-20 parameters, for every path (`MINT`, `TRANSFER`, `BURN`) that calls `generateOutputProof` [5](#0-4) [6](#0-5) [7](#0-6) . The `receives` list (containing `ReceiveDescriptionInfo` with attacker-supplied `ovk`) is populated by `addOutput`, which is exposed to callers constructing shielded contract parameters via `Wallet` (grpc/http API for building `ShieldedTRC20Parameters`). Since the entire `build()` body is wrapped in a `try/catch(Exception e)` that re-wraps everything as `ZksnarkException`, the malformed-`ovk` exception is caught and surfaces as a normal "build error" response to the caller — but only after the native proof computation has already run and consumed CPU cycles. The identical ordering bug (proof-then-validate) also exists in the equivalent `ZenTransactionBuilder.generateOutputProof` [8](#0-7) .

This confirms the described flaw: deterministic/expensive cryptographic proving work is performed on input that is trivially and cheaply invalidatable (a length check on `ovk`), before that cheap check is applied.

### Impact Explanation
Each malformed-`ovk` request forces at least one call to `librustzcashSaplingOutputProof` (a Groth16 zk-SNARK proof generation over BLS12-381, a relatively CPU-heavy operation) that is fully wasted, since the result is discarded when the subsequent length check throws. An attacker who can invoke the public API for building `ShieldedTRC20Parameters` (mint/transfer/burn) can repeatedly submit requests with a 1-byte (or any non-32-byte) `ovk` and force the node to burn CPU resources on proof generation for every call, without needing any valid transaction to be broadcast or accepted on-chain. This is a public-cost (resource-exhaustion) issue rather than a fund-theft or consensus-safety issue: no value is moved, no invariant of shielded pool accounting is violated, and no state divergence occurs — the impact is scoped to CPU/proving-context resource waste on the node processing the API call.

### Likelihood Explanation
The precondition is simply that a caller invoke the shielded-parameter-building API (mint/transfer/burn) with an `ovk` argument whose length isn't 32 bytes. This is a low-privilege, straightforward, repeatable action requiring no special node privileges, no valid keys, and no prior state — the bug is purely in validation ordering within `generateOutputProof`. Because the check is a cheap length/emptiness check that could be performed before calling the native proof routine, the current ordering is unnecessary and easily triggered by any client sending malformed input to the shielded parameter construction endpoint.

### Recommendation
Move the `ovk` validation (`ArrayUtils.isEmpty(output.ovk) || output.ovk.length != 32`) to the top of `generateOutputProof`, before calling `output.getNote().encrypt(pkD)` and before `JLibrustzcash.librustzcashSaplingOutputProof(...)`, in both `ShieldedTRC20ParametersBuilder.generateOutputProof` and `ZenTransactionBuilder.generateOutputProof`. This ensures cheap validation always precedes expensive/deterministic cryptographic work.

### Proof of Concept
```java
// Java test sketch (JUnit) - place in a test class with access to ShieldedTRC20ParametersBuilder
@Test
public void ovkValidatedAfterExpensiveProof() throws Exception {
  ShieldedTRC20ParametersBuilder builder = new ShieldedTRC20ParametersBuilder();
  builder.setShieldedTRC20ParametersType(ShieldedTRC20ParametersType.MINT);
  builder.setShieldedTRC20Address(SOME_CONTRACT_ADDRESS);
  builder.setTransparentFromAmount(BigInteger.valueOf(100));

  // Build a valid note/PaymentAddress but attach a malformed ovk (e.g. length 1)
  ReceiveDescriptionInfo badOutputInfo = buildValidReceiveInfoWithOvk(new byte[]{0x01});
  builder.setReceives(Collections.singletonList(badOutputInfo));

  int proofCallsBefore = JLibrustzcashProofCallCounter.get(); // instrument/mocks around librustzcashSaplingOutputProof
  try {
    builder.build(false);
    Assert.fail("expected ZksnarkException for invalid ovk");
  } catch (ZksnarkException e) {
    Assert.assertTrue(e.getMessage().contains("ovk is null or invalid"));
  }
  int proofCallsAfter = JLibrustzcashProofCallCounter.get();

  // Assert that the expensive native proof call was still executed despite invalid ovk
  Assert.assertEquals(1, proofCallsAfter - proofCallsBefore);
}
```
Expected result with the current code: the native proof call counter increments by 1 even though the request is ultimately rejected, demonstrating wasted proving work. After moving the `ovk` check to the top of `generateOutputProof`, the counter should remain unchanged (0 proof calls) when the `ovk` is malformed.
