### Title
Insufficient JSON escaping in `escapeBytesSelfType` "Normal String" branch allows malformed/broken JSON in HTTP API responses - (File: framework/src/main/java/org/tron/core/services/http/JsonFormat.java)

### Summary
`escapeBytesSelfType` handles bytes fields tagged as "name string" (e.g. `Account.account_name`, `WitnessCreateContract.url`, `AssetIssueContract.name/abbr/description/url`, `Note.memo`) by converting the raw bytes to a `String` and escaping only double quotes, then validating the result with `JSON.parseObject` before embedding it, unescaped, directly into the outer JSON response. [1](#0-0)  These fields are attacker-controlled via ordinary transactions (`AccountUpdateContract`, `WitnessCreateContract`, `AssetIssueContract`, etc.), and the validation only guards against the wrapper test string failing to parse — it does not guarantee the same string is safe when spliced into the real response's JSON string context.

### Finding Description
`printFieldValue` for `BYTES` fields calls `escapeBytes(value, field.getFullName(), selfType)` and writes the result directly between quotes with no further escaping: `generator.print("\""); generator.print(escapeBytes(...)); generator.print("\"");`. [2](#0-1)  For fields registered in `HttpSelfFormatFieldName.NameFieldNameMap` (e.g. `protocol.Account.account_name`, `protocol.WitnessCreateContract.url`, `protocol.AssetIssueContract.name/description/url`, `protocol.Note.memo`), `escapeBytesSelfType` converts the raw bytes to a Java `String` using the JVM's platform default charset (not explicit UTF-8), escapes only literal `"` characters via `replaceAll("\"", "\\\\\"")`, and then validates by wrapping the (partially-escaped) string in a throwaway JSON object and calling `JSON.parseObject`. [3](#0-2) 

Unlike `escapeText` (used for normal `STRING` fields), which fully escapes backslashes, control characters (`\n`, `\r`, `\t`, `\b`, `\f`), other 0x00–0x1F control bytes, and surrogate pairs, [4](#0-3)  the "Normal String" bytes branch does none of this. It relies entirely on `JSON.parseObject` succeeding as a proxy for "safe to embed." This is a validate-then-use-different-value pattern: the check is performed on a differently constructed wrapper string, but the *decision* only determines whether raw hex fallback is used — if the lenient `JSON.parseObject` (fastjson-based, per `org.tron.json.JSON`) accepts raw control characters or other constructs that a strict JSON consumer (JavaScript `JSON.parse`, RFC 8259-compliant parsers) would reject, the un-escaped `result` string is emitted verbatim into the final HTTP response. Any unescaped control character (e.g. a literal `\n` byte, or other 0x00–0x1F bytes) embedded inside a bytes field like `account_name` or `url` can pass a lenient parse yet produce a JSON document that is not strictly valid per RFC 8259, because raw control characters inside a JSON string are illegal per spec even though many lenient JSON libraries (including fastjson in typical configurations) will accept them.

This is reachable by an unprivileged attacker: setting `account_name` via `AccountUpdateContract`, `url`/`description` via `AssetIssueContract`/`WitnessCreateContract`/`UpdateAssetContract`, or `memo` via shielded `Note`, all broadcastable through the public wallet API without special privileges.

### Impact Explanation
The impact is limited to output-format integrity, not consensus, funds, or auth: it can produce HTTP JSON responses (via `wallet/getaccount`, `wallet/listwitnesses`, `wallet/getassetissuebyname`, etc.) that are not strictly RFC 8259-compliant, potentially breaking or confusing strict downstream JSON consumers (block explorers, SDKs, monitoring tooling) that parse these responses. It does not by itself grant unauthorized execution, fund theft, replay, or double-settlement, and does not affect on-chain state or consensus — the malformed data only affects the read-side JSON formatting layer. This should be classified as a data-integrity/robustness defect in a public read API rather than a critical security vulnerability with direct value/authorization impact.

### Likelihood Explanation
Trivially reproducible: any account holder can submit `AccountUpdateContract`, `WitnessCreateContract`, or `AssetIssueContract` with a `name`/`url`/`description` byte sequence containing a raw control character (e.g. `0x0A`) and no unescaped quote, then query the corresponding read API to observe the resulting JSON. No special permissions, fees beyond normal transaction fees, or race conditions are required — it is deterministic and repeatable.

### Recommendation
Replace the ad-hoc "escape quotes then probe with `JSON.parseObject`" logic in `escapeBytesSelfType`'s "Normal String" branch with the same rigorous, spec-compliant escaping used by `escapeText` (escape `\`, `"`, and all control characters 0x00–0x1F, handle surrogate pairs), and decode bytes using an explicit charset (e.g. UTF-8) rather than the platform default. Drop the `JSON.parseObject` round-trip validation entirely in favor of deterministic escaping, falling back to hex only when the byte sequence cannot be decoded as valid text (e.g. invalid UTF-8), not based on a lenient parser's tolerance.

### Proof of Concept
```java
// JsonFormatEscapeBytesSelfTypeTest.java
import com.google.protobuf.ByteString;
import org.junit.Test;
import org.tron.core.services.http.JsonFormat;
import static org.junit.Assert.*;

public class JsonFormatEscapeBytesSelfTypeTest {

  @Test
  public void controlCharBypassesEscaping() throws Exception {
    // Simulates account_name / url bytes containing a raw newline (0x0A),
    // as would be set via AccountUpdateContract.setAccountName(ByteString)
    // or AssetIssueContract.setUrl(ByteString) by any unprivileged sender.
    byte[] raw = "evil\nname".getBytes("UTF-8");
    ByteString bs = ByteString.copyFrom(raw);

    // Directly exercise the package-private method (or via reflection if needed)
    String escaped = JsonFormat.escapeBytesSelfType(bs, "protocol.Account.account_name");

    // Expectation: output should be strictly RFC 8259 compliant, i.e. the raw
    // control character must be escaped (e.g. to \n), NOT left as a literal
    // 0x0A byte, since it will be embedded verbatim between quotes in the
    // final HTTP JSON response by printFieldValue().
    assertFalse("Raw control character leaked into JSON string value",
        escaped.contains("\n"));

    // Build the full field output the way printFieldValue does, and verify
    // it round-trips through a STRICT JSON parser (e.g. javax.json or
    // org.json with JSONTokener in strict mode), not just fastjson's
    // lenient JSON.parseObject.
    String fullJson = "{\"account_name\": \"" + escaped + "\"}";
    // A strict parser (e.g. Jackson with STRICT_DUPLICATE_DETECTION / default
    // control-char rejection, or org.json.JSONTokener) should successfully
    // parse this; currently it will contain a literal newline and fail
    // strict RFC 8259 validation while still passing fastjson's lenient
    // JSON.parseObject used internally for the check.
    new org.json.JSONObject(fullJson); // expected to throw JSONException today
  }
}
```
Expected result today: the raw newline is preserved in `escaped` (test assertion fails), and constructing a strict `org.json.JSONObject` from the resulting full response fragment throws `JSONException` due to the unescaped control character — demonstrating that `JSON.parseObject`'s lenient validation is not an adequate proxy for "safe to embed in a strict-JSON response."

  static String escapeBytesSelfType(ByteString input, final String fliedName) {
    //Address
    if (HttpSelfFormatFieldName.isAddressFormat(fliedName)) {
      return StringUtil.encode58Check(input.toByteArray());
    }
    //Normal String
    if (HttpSelfFormatFieldName.isNameStringFormat(fliedName)) {
      String result = new String(input.toByteArray());
      result = result.replaceAll("\"", "\\\\\"");
      try {
        JSON.parseObject("{\"key\":\"" + result + "\"}");
        return result;
      } catch (Exception e) {
        return ByteArray.toHexString(input.toByteArray());
      }
    }
    //HEX
    return ByteArray.toHexString(input.toByteArray());
  }

  static String escapeText(String input) {
    StringBuilder builder = new StringBuilder(input.length());
    CharacterIterator iter = new StringCharacterIterator(input);
    for (char c = iter.first(); c != CharacterIterator.DONE; c = iter.next()) {
      switch (c) {
        case '\b':
          builder.append("\\b");
          break;
        case '\f':
          builder.append("\\f");
          break;
        case '\n':
          builder.append("\\n");
          break;
        case '\r':
          builder.append("\\r");
          break;
        case '\t':
          builder.append("\\t");
          break;
        case '\\':
          builder.append("\\\\");
          break;
        case '"':
          builder.append("\\\"");
          break;
        default:
          // Check for other control characters
          if (c >= 0x0000 && c <= 0x001F) {
            appendEscapedUnicode(builder, c);
          } else if (Character.isHighSurrogate(c)) {
            // Encode the surrogate pair using 2 six-character sequence (\\uXXXX\\uXXXX)
            appendEscapedUnicode(builder, c);
            c = iter.next();
            if (c == CharacterIterator.DONE) {
              throw new IllegalArgumentException(
                  "invalid unicode string: unexpected high surrogate pair value "
                      + "without corresponding low value.");
            }
            appendEscapedUnicode(builder, c);
          } else {
            // Anything else can be printed as-is
            builder.append(c);
          }
          break;
      }
    }
    return builder.toString();
  }
