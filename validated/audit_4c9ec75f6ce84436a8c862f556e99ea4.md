### Title
`cost_model::calculate_cost` undercounts CPI-driven account-data allocations, allowing bypass of the per-block accounts-data-growth budget - (File: `cost-model/src/cost_model.rs`)

### Summary
`CostModel::calculate_allocated_accounts_data_size` only inspects the transaction's top-level (statically compiled) `SystemInstruction`s to estimate how much account data a transaction will allocate. An attacker can deploy an ordinary BPF program whose single top-level instruction performs no allocation itself, but which internally issues a CPI to the System Program's `CreateAccount`/`Allocate`, causing real account-data growth that is invisible to the estimator and therefore never counted against `CostTracker`'s block-level `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (`cost-model/src/block_cost_limits.rs:37`) budget.

### Finding Description
`CostModel::calculate_cost` calls `calculate_transaction_cost`, which computes `allocated_accounts_data_size` via `Self::calculate_allocated_accounts_data_size(instructions, feature_set)` [1](#0-0) . That helper iterates only `transaction.program_instructions_iter()` — the instructions compiled directly into the transaction message — and for each one checks `calculate_account_data_size_on_instruction`, which returns `SystemProgramAccountAllocation::None` for any `program_id` that is not the System Program [2](#0-1) . The function's own doc comment acknowledges the limitation: "eventually, potentially determine account data size of all writable accounts / at the moment, calculate account data size of account creation" [3](#0-2) .

This same top-level-only calculation is used both for the pre-execution admission estimate (`calculate_cost`, used by `QosService`/banking stage to gate block inclusion via `CostTracker::try_add`) and for the post-execution accounting (`calculate_cost_for_executed_transaction`) — neither path re-derives `allocated_accounts_data_size` from what actually happened during execution (including CPI) [4](#0-3) .

`CostTracker::try_add` uses this value to enforce the block-wide `allocated_data_size` limit, comparing the running total against `limits.allocated_data_size` before admitting a transaction [5](#0-4) , which is derived from `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA = 100_000_000` bytes per block [6](#0-5) .

An attacker deploys a program `P` whose entrypoint (invoked as the sole top-level instruction, with a compute-budget instruction requesting the max CU limit) issues `invoke(&system_instruction::create_account(...))` or `invoke(&system_instruction::allocate(...))` against an account it controls. Because the top-level instruction's `program_id` is `P`, not `system_program::id()`, `calculate_account_data_size_on_instruction` returns `None` and the transaction's `allocated_accounts_data_size` is computed as `0`, regardless of how much data the CPI actually allocates (bounded at runtime only by the per-transaction cap `MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION`/`MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` enforced in `transaction_accounts.rs::can_data_be_resized` [7](#0-6) , which is per-transaction and CPI-depth-agnostic, not per-block).

Because the *per-transaction* runtime resize cap is enforced independent of the *cost model's* per-block estimate, the two are decoupled: the cost model can admit many such transactions into a block (each contributing `0` to `allocated_accounts_data_size`) while each transaction actually grows account data by up to the per-transaction maximum during execution. This lets an attacker pack a block with far more real account-data growth than the `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` budget was designed to permit, without ever tripping `CostTrackerError::WouldExceedAccountDataBlockLimit`.

### Impact Explanation
This breaks the invariant that "all account data allocation in a transaction is charged, including allocations made through CPI." The direct consequence is that the leader's block-level accounts-data-growth budget (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`) — which exists specifically to bound AccountsDb growth/IO per slot — can be silently exceeded. Repeated abuse across many blocks can drive excessive AccountsDb growth and IO pressure beyond what validators are provisioned for, which can degrade block-production throughput/latency cluster-wide, consistent with a Liveness/Loss-of-Availability class finding.

### Likelihood Explanation
The attack requires only: (1) deploying an ordinary BPF/SBF program (permitted to any unprivileged account with funds), (2) having that program CPI into `system_instruction::create_account`/`allocate`/`allocate_with_seed` on an account it can sign for, and (3) submitting normal transactions with the max compute-unit limit and a single top-level instruction. No special privileges, feature-gate bypass, or race condition is needed, and the exploit is fully repeatable/scriptable across many transactions and blocks at ordinary fee cost. The main uncertainty is the magnitude of real-world impact: each individual transaction is still capped by the per-transaction resize limit, so the "loss" is a systemic under-budgeting of block-level accounts-data growth rather than an unbounded single-transaction blowup, and whether this alone is sufficient to reach "block production degraded below usable capacity" would need empirical confirmation via cluster-scale testing.

### Recommendation
Extend `calculate_allocated_accounts_data_size` (or add a companion mechanism) to account for allocation potential introduced by non-system-program top-level instructions that can perform CPI — e.g., conservatively charge every writable account touched by a non-system top-level instruction as a potential full allocation up to `MAX_PERMITTED_DATA_LENGTH`/the resize cap, or track actual `resize_delta` from execution (already computed in `transaction_accounts.rs`) and feed it back into `calculate_cost_for_executed_transaction`'s `allocated_accounts_data_size` instead of recomputing it from static top-level instructions only.

### Proof of Concept
1. Unit test in `cost-model/src/cost_model.rs`: construct a `RuntimeTransaction` whose sole instruction targets a non-system `program_id` (simulating an attacker's deployed program), and assert `CostModel::calculate_allocated_accounts_data_size` returns `0` even though the instruction is documented/intended to CPI-allocate account data.
2. Bank/SVM integration test: deploy a minimal SBF program that CPIs `system_instruction::create_account` with `space = MAX_PERMITTED_DATA_LENGTH` (or `allocate`) on a fresh account; submit the transaction with `ComputeBudgetInstruction::set_compute_unit_limit` at max; execute via `BankClient`; confirm the account's data length grew via CPI while `CostModel::calculate_cost(&tx, ...).allocated_accounts_data_size()` (computed pre-execution) is `0`.
3. Assert violation: compare the pre-execution estimate (`0`) against the actual post-execution accounts-data delta (`MAX_PERMITTED_DATA_LENGTH` bytes) to demonstrate the estimate is not an upper bound, contradicting the required invariant.

    /// eventually, potentially determine account data size of all writable accounts
    /// at the moment, calculate account data size of account creation
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }
