### Title
Forged shadow-parent commit fields let any miner falsely trigger PoX-punishment treatment on a non-descendant block-commit - ([File: stackslib/src/chainstate/burn/operations/leader_block_commit.rs])

### Summary
`check_pox_pre_waterfall` decides, per block-commit, whether that commit is a "descendant" of the PoX reward-cycle's anchor block, which in turn decides whether its outputs must be treated as `Reward` (legitimate PoX payout) or `Punish` (forfeited payout) against the reward-cycle's Stackers. One of the three ways `descended_from_anchor` can become `true` is a cheap syntactic heuristic on the commit's own `parent_block_ptr`/`parent_vtxindex` fields, rather than an actual chain-ancestry check, and this heuristic is fully attacker-controlled.

### Finding Description
In `check_pox_pre_waterfall`, `descended_from_anchor` is computed as: [1](#0-0) 

```
let directly_descended_from_anchor = epoch_id.block_commits_to_parent() && self.block_header_hash == v0.anchor_block;
let maybe_shadow_parent = epoch_id.supports_shadow_blocks()
    && self.parent_block_ptr != 0
    && self.parent_vtxindex == 0;
let descended_from_anchor = directly_descended_from_anchor
    || maybe_shadow_parent
    || tx.descended_from(parent_block_height, &v0.anchor_block)?;
```

`maybe_shadow_parent` is set purely from `self.parent_block_ptr` and `self.parent_vtxindex` — both fields the miner freely chooses when constructing their own `LeaderBlockCommit` burnchain transaction. The comment at line 932-936 explicitly states this is an *assumption*, deferred for verification to Stacks-block-processing time via `validate_shadow_parent_burnchain`. That deferred check, however, only fires "if the parent [Nakamoto block header] is a shadow block"; otherwise it is a no-op that returns `Ok(())` unconditionally: [2](#0-1) 

Crucially, the burn-op-level `descended_from_anchor` decision is made and consumed at *sortition/burn-op processing time*, which happens as soon as the block-commit is mined into a Bitcoin block — well before, and independently of, whether any Stacks block referencing that commit as a tenure-start is ever produced or validated. Nothing forces a miner who sets `parent_vtxindex = 0` and an arbitrary nonzero `parent_block_ptr` to ever produce (or have produced) a genuine shadow-block tenure at that height; `validate_shadow_parent_burnchain` only constrains things *if and when* a corresponding Stacks block with a shadow parent is later staged, which is not required for the burn-op's `Treatment` computation to already have taken effect.

Consequence for a normal, non-participating burn commit: without the heuristic, a commit that isn't genuinely descended from the anchor and whose outputs are all burn addresses is treated as an ordinary out-of-cycle burn — `Ok(vec![])`, no effect on Stackers' payouts: [3](#0-2) 

But if the miner sets `parent_vtxindex = 0` and any nonzero `parent_block_ptr` (regardless of whether a real shadow tenure exists there), `maybe_shadow_parent` forces `descended_from_anchor = true`. Combined with `self.all_outputs_burn() == true` and `v0.allow_nakamoto_punishment == true` (true for Nakamoto epochs, per `epoch_id.allows_pox_punishment()`), the code instead returns: [4](#0-3) 

i.e., every one of the current reward-cycle's legitimate PoX recipients is marked `Treatment::Punish` for that sortition slot — forfeiting their expected payout for a slot in which the miner never actually mined off the true PoX anchor lineage.

This breaks the intended equality: *"treat as Reward/Punish only for commits that are provably descended from the PoX anchor block."* Any single, unprivileged miner submitting one burnchain transaction can force the `Punish` branch onto honest Stackers without ever running a real competing/shadow tenure, purely by choosing two integer fields in their own commit.

### Impact Explanation
This is a minority-triggerable (single miner, no cooperation needed), unprivileged divergence in a validation verdict that determines whether real PoX/BTC reward payouts to Stackers are honored or forfeited for a given sortition. It falls under "reward mis-payment... temporary tip disagreement" / High severity in the requested taxonomy, since Stackers can lose an expected reward-cycle payout because of a burn-commit that was never a legitimate descendant of the PoX anchor.

### Likelihood Explanation
Likelihood requires only that a miner (1) knows the current PoX anchor's reward-cycle context (public), (2) submits a plain burn-output `LeaderBlockCommit` (which any miner can already legitimately do when they don't want to pay PoX), and (3) sets `parent_vtxindex = 0` with a nonzero `parent_block_ptr`. No majority, no elevated privilege, no Bitcoin-consensus assumptions beyond normal commit submission are needed. The gating conditions (`epoch_id.supports_shadow_blocks()`, `allow_nakamoto_punishment`) are properties of the current epoch, not of the attacker, and are true in Nakamoto epochs.

### Recommendation
Do not treat `parent_vtxindex == 0 && parent_block_ptr != 0` alone as proof of shadow-block descent at burn-op processing time. Either (a) defer the `Punish` determination until the actual referenced parent block/tenure has been verified to be a genuine shadow block descending correctly from the anchor (mirroring the checks in `validate_shadow_parent_burnchain`), or (b) require the burn-op processing code itself to query sortition/staging state for a real shadow tenure at `parent_block_ptr` before honoring `maybe_shadow_parent`, falling back to `tx.descended_from(...)` otherwise.

### Proof of Concept
1. During a Nakamoto-epoch reward cycle with an active PoX anchor block and non-empty reward set, have a miner (any single miner, no majority) build a `LeaderBlockCommitOp` whose `block_header_hash` does **not** match the anchor and which is **not** actually chain-descended from the anchor (`tx.descended_from` would return `false`).
2. Set `commit_outs` to all burn addresses (`all_outputs_burn() == true`).
3. Set `parent_vtxindex = 0` and `parent_block_ptr` to any nonzero burn height (need not correspond to a real shadow tenure the miner produced).
4. Submit the commit to the Bitcoin chain as usual.
5. On processing, `check_pox_pre_waterfall` computes `maybe_shadow_parent = true`, forcing `descended_from_anchor = true`; since outputs are all-burn and `allow_nakamoto_punishment` is true, the function returns `Treatment::Punish` for every recipient in the current reward set — even though no genuine shadow-descendant relationship was ever established or later validated for this burn transaction.         // points to the shadow block's tenure's burnchain block.

            && self.parent_vtxindex == 0;

            || maybe_shadow_parent
            || tx.descended_from(parent_block_height, &v0.anchor_block)
            .map_err(|e| {

                       parent_block_height, &v0.anchor_block, e);
                op_error::BlockCommitAnchorCheck
