### Title
Stale per-block index cache lets `liquidate`/`repay` compute debt with an out-of-date vault index after a same-transaction vault mutation - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The `RaffleMintV1.withdrawNonRaffleProceeds()` report is a classic "clear-state-after-external-call" reentrancy: an external call is made and the balance/authorization that gated it is only invalidated afterward, so a re-entrant call sees the stale, not-yet-cleared value. Clarity has no fallback-triggered reentrancy on `stx-transfer?`/`ft-transfer?`, so the direct analog is out of scope. However, `mainnet/contracts/market/v0-4-market.clar` contains the same underlying bug class in single-transaction form: a **cached value that is read after its underlying source has already moved**, without the cache being invalidated. The `index-cache-` map is used to avoid repeated vault `accrue` calls within one block/tx, but multiple code paths (`liquidate`, `repay`, `borrow`) mix reads from this cache with direct vault mutations that change the real vault index, so a stale cached index can be used for debt-owed calculations after the true value has already changed earlier in the same call graph.

### Finding Description
`market.clar`/`v0-4-market.clar` maintains `index-cache-` keyed by `{ timestamp: stacks-block-time, aid }` to avoid calling vault `accrue` multiple times in a block: [1](#0-0) 

`accrue-and-cache` populates this cache once per `(aid, timestamp)` and every subsequent lookup for that timestamp reuses the cached `{index, lindex}` tuple instead of re-querying the vault: [2](#0-1) 

In `liquidate`, the flow explicitly separates "accrue first to populate cache" from "resolve prices/debt using the cache", and then performs `vault-system-repay` (which calls the vault's own `accrue`, mutating the vault's real `index`/`lindex` state var) followed by reads of `get-cached-indexes` for the *remaining* debt-repayable computation: [3](#0-2) [4](#0-3) 

The vault's `accrue` function is the actual state-mutating source of truth for `index`/`lindex`: [5](#0-4) 

Because `vault-system-repay` is called mid-function (line 1496 area) and re-triggers vault `accrue`, but the market's own `index-cache-` entry for that `(aid, timestamp)` was already written earlier in the same call and is never refreshed, the later `remaining-debt-to-repay` calculation at lines 1500-1507, which calls `get-cached-indexes` again, uses the value captured before the mutation rather than the post-mutation vault state. This is the same defect shape as the report: "a value is bound, its source is invalidated/moved by an intervening action, and a later step consumes the stale binding" — except here the interleaving is guaranteed by ordinary sequential evaluation within one Clarity transaction rather than by reentrancy.

### Impact Explanation
If the cached index diverges from the vault's freshly-accrued index during a single `liquidate` call, `remaining-debt-to-repay` and the final collateral/debt apportionment (`coll-final`, `scaled-to-remove`, bad-debt socialization) are computed against a stale debt/interest snapshot. This can under- or over-value the amount of debt considered "remaining," causing collateral to be released to the liquidator disproportionately to actual outstanding debt, or bad-debt socialization to be skipped/triggered incorrectly. This lands in the "temporary freezing of funds" / protocol-insolvency-adjacent impact band, since it can cause the market to under-collect debt relative to collateral released within a single liquidation call.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires interest to have actually accrued a non-zero delta between the two reads within the same transaction (i.e., the vault's index genuinely changes as a result of `vault-system-repay`'s internal `accrue` call), and it depends on exact call ordering in `liquidate`/`liquidate-redeem`. I was not able to fully trace every `accrue-and-cache` call site and confirm the exact set of intervening mutations across `market.clar` due to tool/iteration limits, so the precision of "index actually changes mid-function" is not fully verified against the complete control flow.

### Recommendation
Ensure the market's `index-cache-` entry for `(aid, timestamp)` is invalidated or refreshed immediately after any call that triggers the underlying vault's `accrue` (e.g., `vault-system-repay`, `vault-system-borrow`), before any subsequent read via `get-cached-indexes`/`accrue-and-cache` in the same transaction. Alternatively, restructure `liquidate` so that all debt/collateral math that depends on the borrow index is computed from a single, consistently-refreshed index value rather than mixing an early cached snapshot with later cache reads after a vault-mutating call.

### Proof of Concept
Conceptual sequence within one `liquidate` call:
1. `accrue-user-debts`/`get-cached-indexes` populate `index-cache-` for `(debt-aid, stacks-block-time)` — this is the value used for `borrow-index`, `debt-info`, etc.
2. `vault-system-repay debt-aid debt-to-repay debt-ft debt-address` is invoked, which internally calls the vault's `accrue`, updating the vault's live `index`/`lindex` `data-var`s.
3. Later in the same `liquidate` body, `remaining-debt-to-repay` computation calls `get-cached-indexes` again for `debt-aid` at the same `stacks-block-time` key — this returns the value cached in step 1, not the value mutated in step 2.
4. The final apportionment of `coll-final`/bad-debt socialization is computed from this now-stale index, producing an inconsistency between the vault's true debt state and the market's liquidation accounting for that single call.

I was unable to fully confirm within the tool budget whether `vault-system-repay`'s internal `accrue` call actually produces a *material* index delta before `get-cached-indexes` is read again in the same execution (this depends on exact time deltas and whether `index-cache-` is written/read multiple times per call), so this should be validated against the full `market.clar`/`v0-4-market.clar` control flow before treating it as confirmed exploitable.

(define-map index-cache- 
  { timestamp: uint, aid: uint }
  { index: uint, lindex: uint })

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid }))
    ;; Check cache first, accrue vault if needed
    (match (map-get? index-cache- cache-key)
      existing existing
      (let ((fresh (vault-accrue aid)))
        (map-set index-cache- cache-key fresh)
        fresh))))
