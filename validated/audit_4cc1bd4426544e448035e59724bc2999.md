### Title
`accrue` pause pass-through leaves `index`/`lindex` stale while borrowing, repaying, depositing and redeeming continue - (File: mainnet/contracts/vault/v0-vault-stx.clar)

### Summary
The `accrue` pause flag is meant to gate the interest-accrual mechanism, but instead of reverting the caller's transaction when `accrue` is paused, `accrue` silently returns the *old* `index`/`lindex` values as if they were current, while every other lending entrypoint (`deposit`, `redeem`, `system-borrow`, `system-repay`) keeps operating normally because they are gated by their own, independent pause flags. This lets debt/interest-sensitive operations proceed against a frozen index while `last-update` is never advanced, so once `accrue` is unpaused the entire elapsed period's interest is compressed into a single jump that is applied against balances/positions that were mutated in the interim on stale numbers.

### Finding Description
`accrue` reads the shared `pause-states` var and, when `accrue` is `true`, returns `(ok { index: idx, lindex: lidx })` unconditionally without recomputing or updating storage: [1](#0-0) 

When not paused, `accrue` recomputes `next-index`/`next-liquidity-index`, mints reserve share to the treasury for the delta, and stores `last-update`: [2](#0-1) 

`deposit`, `redeem`, `system-borrow`, and `system-repay` each unconditionally call `(try! (accrue))` first and are gated by their *own* pause flag (`deposit`, `redeem`, `borrow`, `repay`), not by the `accrue` flag: [3](#0-2) [4](#0-3) 

Because `pause-states` is a single tuple with six independent boolean fields, an admin can pause `accrue` alone while leaving `borrow`/`repay`/`deposit`/`redeem` active: [5](#0-4) 

This is the same bug class as the external report: an update path that is supposed to keep a piece of shared state (there: the factory's stored code cells; here: `index`/`lindex`/`last-update`) internally consistent instead takes a shortcut ("pass-through") that leaves the state stale/inconsistent, and every subsequent consumer of that state (there: `load_data`/`recv_internal`; here: `system-borrow`/`system-repay`/`redeem`) keeps operating on it as if it were valid.

Sequence:
1. Admin pauses only `accrue` in `pause-states` (leaves `borrow`, `repay`, `deposit`, `redeem` active) — an ordinary operational pause, not a compromise.
2. Time passes (blocks accumulate); `last-update` is never advanced because `accrue`'s paused branch never calls `var-set last-update`.
3. During the pause window, users call `system-borrow`/`system-repay` (or `deposit`/`redeem`); each internally calls `accrue`, which returns the frozen `idx`/`lidx` from before the pause began. `system-borrow` computes `scaled-amount` and `debt` off this frozen index while `total-borrowed` and `principal-scaled` are still mutated for real, permanently baking positions at the stale rate.
4. Admin unpauses `accrue`. The next call to `accrue` computes `next-index` based on the entire elapsed time span since the old `last-update` (which never moved during the pause) and applies the whole multi-period jump in one shot, retroactively repricing all debt/supply that was created or changed during the pause window against a jump that did not apply to them at creation time.
5. Reserve fee minting (`treasury-lp`) computed from the jump also fires only at the unpause moment, based on `scaled-principal` as it stands then — not reflecting the actual sequence of borrows/repays that happened while paused — permanently misallocating/losing part of the reserve fee income for that window.

### Impact Explanation
This mishandles interest-accrual bookkeeping, causing the reserve fee (protocol/treasury yield) for the paused window to be computed incorrectly and, depending on the direction of debt changes during the pause, either forgone entirely or double-counted against unrelated positions. This is a temporary/permanent freezing or misallocation of unclaimed yield (reserve fee minted to `.dao-treasury`), matching the High-severity class ("theft of unclaimed yield or royalties, permanent freezing of unclaimed yield or royalties, or temporary freezing of funds").

### Likelihood Explanation
Likelihood is moderate: it requires an admin operational action (pausing only `accrue` while other flags stay open) which is a legitimate, foreseeable partial-pause combination given the pause flags are independent booleans in the same struct, plus ordinary user activity (borrow/repay/deposit/redeem) during that window — no privileged compromise or DAO takeover is needed to trigger the inconsistency, only normal use of the exposed admin pause granularity.

### Recommendation
- Short term: when `accrue` is paused, either (a) revert all state-mutating lending calls (`deposit`, `redeem`, `system-borrow`, `system-repay`) instead of allowing them to proceed on a stale index, or (b) make `accrue`'s paused branch still be a no-op for `index`/`lindex` *but* also block the callers that depend on interest-sensitive amounts from mutating `total-borrowed`/`principal-scaled` while paused.
- Long term: collapse the six independent pause flags into an explicit dependency model (e.g., pausing `accrue` should imply pausing `borrow`/`repay`/`deposit`/`redeem`), and add invariant tests asserting that `last-update`, `index`, and `lindex` cannot diverge from the operations that are still permitted while any related flag is paused.

### Proof of Concept
1. Admin calls whatever admin function sets `pause-states` with `accrue: true` and all other flags `false`.
2. Wait N blocks/time.
3. User A calls `system-borrow`; `accrue` returns stale `idx`; `system-borrow` computes `scaled-amount` from that stale `idx`, updates `principal-scaled`/`total-borrowed`, sends underlying — succeeds despite the frozen accrual state.
4. Admin sets `pause-states` with `accrue: false`.
5. Any subsequent call to `accrue` (via `deposit`/`redeem`/`system-borrow`/`system-repay`) now computes `next-index` over the full elapsed period from the old `last-update`, applying the entire multi-block interest jump at once — retroactively repricing User A's position created mid-window and minting/skipping treasury reserve fee inconsistent with the actual timeline of debt changes, at [2](#0-1) .
