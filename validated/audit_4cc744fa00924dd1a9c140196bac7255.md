### Title
Unpausing liquidation via `set-pause-liquidation` never clears the manual pause flag - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`set-pause-liquidation` branches on `(and was-paused (not paused))` to pick between two mutually-exclusive `var-set` operations instead of always writing the caller's intended pause state. When called to *unpause* liquidations (the exact transition the branch condition is designed to detect), the function only writes `liquidation-grace-end` and skips the `var-set pause-liquidation paused` mutation that lives in the untaken branch, so the manual pause flag that was set on a prior pause call is stranded at `true` forever.

### Finding Description
The pause data is held as: [1](#0-0) 

and the setter is: [2](#0-1) 

Trace the two possible DAO calls:
1. Pause: `was-paused = false`, caller passes `paused = true`. Condition `(and false (not true))` = `false` → the `else` branch executes `(var-set pause-liquidation paused)`, correctly setting `pause-liquidation = true`.
2. Unpause: `was-paused = true`, caller passes `paused = false` to resume liquidations. Condition `(and true (not false))` = `true` → the `then` branch executes, which only does `(var-set liquidation-grace-end (+ stacks-block-time grace-period))`. The `else` branch — the only place that writes `pause-liquidation` — is never reached, so `pause-liquidation` keeps its stale value `true`.

The read path confirms the stale flag is load-bearing: [3](#0-2) 

`liquidation-paused` returns `(or manual-pause grace-active)`. Because `manual-pause` (the `pause-liquidation` var) is never reset by the unpause call, `liquidation-paused` returns `true` unconditionally regardless of the grace period elapsing — the DAO's "unpause" transaction silently fails to unpause. Identifiers `pause-liquidation`, `liquidation-grace-end`, and `liquidation-paused` were confirmed to exist in the production contract `mainnet/contracts/market/v0-4-market.clar`, matching this documented logic.

This is a single-transaction guard/mutation mismatch: the branch selected by the "was previously paused, now unpausing" guard omits the mutation required to actually clear the state that the guard itself is testing — analogous to the report's stale-approval-not-reset pattern, just manifesting as a stuck pause flag instead of a stuck approval hash.

### Impact Explanation
Once triggered, liquidations for the entire market are permanently disabled with no on-chain path to re-enable them through the intended `set-pause-liquidation(false, ...)` call, since that call path never clears the flag. Unhealthy borrow positions can never be liquidated, allowing bad debt to accumulate without bound and directly threatening protocol insolvency — lender deposits become backed by under-collateralized debt that can never be seized. This lands on the Critical impact class (protocol insolvency).

### Likelihood Explanation
High. No attacker or adversarial interleaving is required — the bug is deterministic and triggers on the very next legitimate governance action after any pause/unpause cycle. Any DAO-initiated emergency pause followed by an attempted unpause reproduces the stuck state every time.

### Recommendation
Restructure `set-pause-liquidation` so that `pause-liquidation` is always written to the caller-supplied `paused` value on every invocation (e.g., via `begin`), independent of which grace-period branch is taken:
```clarity
(define-public (set-pause-liquidation (paused bool) (grace-period uint))
  (let ((was-paused (var-get pause-liquidation)))
    (if (and was-paused (not paused))
        (var-set liquidation-grace-end (+ stacks-block-time grace-period))
        true)
    (var-set pause-liquidation paused)
    (ok true)))
```
Ensure the flag mirrors the intended state on every call regardless of the grace-period sub-branch.

### Proof of Concept
1. DAO calls `set-pause-liquidation(true, u0)` while `pause-liquidation = false` → `was-paused=false`, condition false → else-branch executes → `pause-liquidation = true`. Liquidations correctly paused.
2. DAO later calls `set-pause-liquidation(false, grace-period)` intending to resume liquidations → `was-paused=true`, condition `(and true (not false))=true` → then-branch executes → only `liquidation-grace-end` is updated; `pause-liquidation` is left at `true`.
3. `liquidation-paused()` computes `manual-pause = (var-get pause-liquidation) = true`, so it returns `true` unconditionally, irrespective of `grace-active` or elapsed time.
4. Any subsequent liquidation attempt gated on `liquidation-paused` remains blocked indefinitely; the DAO has no further call in this function to clear `pause-liquidation`, leaving liquidations permanently disabled.
