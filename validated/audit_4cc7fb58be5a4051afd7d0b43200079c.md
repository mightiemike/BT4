## Analysis

I've confirmed the key mechanism: the `accrue` function (shared across all vaults: `v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`) computes `next-index` and `next-liquidity-index` using a *shared* `last-update` clock, but only advances that clock `(if (or ... changed)) (var-set last-update ...)`. [1](#0-0) 

Both `next-index` and `next-liquidity-index` independently compute `time-delta` from the same `(var-get last-update)`, apply different rates (`interest-rate` vs `calc-liquidity-rate`), and round in different directions (round-up for debt, round-down for liquidity) via `calc-multiplier-delta`. [2](#0-1) [3](#0-2) 

## Title
Shared accrual clock advances on ANY index change, silently discarding rounded-away liquidity-index time for LPs — (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent vaults)

### Summary
`accrue()` uses one `last-update` timestamp to gate both the debt index (`index`) and the liquidity index (`lindex`). It resets `last-update` to `stacks-block-time` whenever *either* index changed, not only when the liquidity index itself changed. Because the liquidity multiplier is computed with `mul-div-down` (rounds toward the old value) and can round to exactly `INDEX-PRECISION` (no-op) for a small time-delta/low liquidity-rate while the debt multiplier (rounded up, different rate) still changes, the elapsed period counted toward LP yield is wiped out and never re-accrued once the shared clock jumps forward.

### Finding Description
In `next-index` / `next-liquidity-index`, the multiplier for each side is `INDEX-PRECISION + round(rate * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS)`. [4](#0-3) 

Because `calc-liquidity-rate` scales down the borrow rate by utilization and the reserve factor, the liquidity rate is strictly smaller than the borrow rate, so it takes a smaller `time-delta` to make the liquidity-side numerator underflow the divisor (`SECONDS-PER-YEAR-BPS`) and round down to zero delta (`calc-index-next lidx multiplier` stays equal to `lidx`), while the borrow-side multiplier (rounded up) already differs from `idx` for the same `time-delta`. In `accrue()`:

```
(if (not (is-eq idx next)) (var-set index next) false)
(if (not (is-eq lidx nliq)) (var-set lindex nliq) false)
...
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
``` [1](#0-0) 

The `last-update` clock is the sole "source" both formulas read `time-delta` from. It moves forward as soon as *either* branch changed — including when only the debt side changed. When that happens, `lindex` is left untouched, but the time window that would eventually have produced a nonzero liquidity-index increment (once `time-delta` grew large enough) is discarded: the next call to `accrue()` restarts `time-delta` from the new (later) `last-update`, so the sub-threshold liquidity interest for the already-elapsed window is never recovered. This mirrors the reported bug class: a bound/clock value invalidated by a change to one quantity silently strands the accrual state of a different quantity that depends on the same clock.

This function is called on every `deposit`, `redeem`, `system-borrow`, `system-repay` and via `liquidate`'s `accrue-and-cache`, so it fires continuously in production with real utilization/rate values — it is not a rare edge case, it is the standard interest path.

### Impact Explanation
This causes a permanent, silent loss of a fraction of unclaimed yield owed to liquidity providers (LP share value grows via `lindex`), each time debt-side accrual "consumes" the shared clock before the liquidity-side delta has crossed its rounding threshold. Over the life of a vault with many small-interval accrual calls (e.g., frequent borrow/repay activity keeping `time-delta` small each call), LPs systematically under-accrue yield versus what the interest-rate model promises, while borrowers are still charged the full (rounded-up) debt interest. This is a "permanent freezing/loss of unclaimed yield" scenario for depositors — High impact per the given classification.

### Likelihood Explanation
High-frequency vaults (e.g., `zSTX`, `zUSDC`) with many transactions per block/short intervals between accruals, combined with low utilization (which lowers the liquidity rate relative to the borrow rate through `calc-liquidity-rate`'s extra utilization/reserve-factor scaling), make the rounding-to-zero condition common on the liquidity side while the debt-side multiplier still moves. No attacker action is required — this occurs from normal protocol usage under realistic rate/utilization values, so it is a systemic, protocol-native issue rather than a crafted attack, but it still requires the specific numeric conditions (small `time-delta`, low liquidity rate) to trigger measurable loss.

### Recommendation
Track two independent `last-update` timestamps — one for the debt index and one for the liquidity index — so each accrual path only advances its own clock when its own index actually changes. Alternatively, always advance `last-update` unconditionally to `stacks-block-time` on every `accrue()` call (removing the `if` guard) so `time-delta` for both computations is symmetric and small residuals are dropped equally, or keep `last-update` fixed until *both* indexes have moved so neither computation is truncated mid-window. Add tests that check LP share value growth (`lindex`) equals the sum of expected per-call increments over many small-interval accrual calls with low utilization, to catch this class of rounding loss.

### Proof of Concept
1. Set up a vault (e.g., `v0-vault-usdc`) with nonzero utilization producing a small nonzero borrow `interest-rate`, and low utilization so `calc-liquidity-rate` (which multiplies by `util-pct` in BPS and `(BPS - reserve-factor)`) yields a rate small enough that for a 1-second `time-delta`, `mul-div-down(liquidity-rate, time-delta*INDEX-PRECISION, SECONDS-PER-YEAR-BPS)` truncates to `0`, while `mul-div-up(rate, time-delta*INDEX-PRECISION, SECONDS-PER-YEAR-BPS)` for the borrow rate is `>= 1` (rounds up, so any nonzero rate*time-delta product yields a nonzero result).
2. Call `system-borrow` (or any function invoking `accrue()`) once per second across several 1-second blocks. Each call: `next` (debt index) increases by 1 unit (due to round-up), `nliq` (liquidity index) stays equal to `lindex` (rounds down to 0 delta) — but `last-update` advances anyway due to the `or` in the guard.
3. Observe: `lindex`/`total-assets-preview` for LPs never increases even though real time has elapsed and `index` (debt) has grown, because each call resets the window before the liquidity side accumulates enough elapsed time to round to a nonzero delta.
4. Compare against expected behavior (an un-truncated/continuous accrual model) where the same total elapsed time should have produced a nonzero liquidity index increase — the difference is the amount of LP yield permanently lost.

Note: I was unable to fully verify the exact numeric utilization/rate curve constants (`points-ir`) configured at deployment, since those interpolation-table values are set via DAO configuration calls not fully visible in the indexed contract text; a live/local-testing run (e.g., in `local-testing/tests/`) would be needed to concretely reproduce specific loss magnitudes.
