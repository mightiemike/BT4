### Title
Unauthorized free contract declaration via the special `'BOOTSTRAP'` sender address is not restricted to genesis - (File: `crates/starknet_api/src/executable_transaction.rs`)

### Summary
The sequencer implements a special "bootstrap declare" transaction flow, intended only for initializing a brand-new Starknet system, that is identified purely by a hardcoded, keyless sender address (`'BOOTSTRAP'`), a nonce of `0`, and zero fee. This flow completely skips `__validate_declare__` execution and fee charging [1](#0-0) , and the blockifier honors it purely on these client-supplied fields with no cryptographic ownership proof [2](#0-1) . Nowhere in the reachable code paths I inspected (gateway declare permission check, blockifier execution, OS re-execution) is this flow gated by block number/genesis state — it is only gated by a static, node-level `is_authorized_declarer` allow-list config [3](#0-2) .

### Finding Description
`DeclareTransaction::bootstrap_address()` returns a fixed felt-encoded constant (`'BOOTSTRAP'`), not a real account with a private key [4](#0-3) . `is_bootstrap_declare` recognizes any V3 declare transaction with `sender_address == bootstrap_address()`, `nonce == 0`, and `charge_fee == false` [5](#0-4) . When this condition holds, `AccountTransaction::execute_raw` in the blockifier skips `perform_pre_validation_stage`, `run_or_revert` (which would invoke `__validate_declare__`), and fee handling entirely, going straight to `run_execute` which only records the class declaration [2](#0-1) . The equivalent Starknet OS Cairo code re-implements the identical bypass with no additional constraints beyond `sender_address == 'BOOTSTRAP' and nonce == 0 and version == 3` and `max_possible_fee == 0` [6](#0-5) .

Critically, the bootstrap transaction's nonce is never incremented, by design, so the same "account" can theoretically resubmit bootstrap declares indefinitely (the code comments explicitly acknowledge that after execution the mempool keeps re-proposing it until it is rejected for double-declaring the same class hash) [7](#0-6) . The gateway state reader also has explicit genesis/empty-state fallbacks (`GenesisStateReader`, `GenesisFixedBlockStateReader`) that exist specifically to let bootstrap transactions validate when "no blocks exist yet" [8](#0-7) [9](#0-8) , but once real blocks exist, `SyncStateReader::from_number` is used instead — there is no evidence in the reachable execution/OS code that the bypass condition itself becomes unreachable once the chain has left genesis. The only gate found is `check_declare_permissions`'s `is_authorized_declarer` allow-list check in the gateway, which is a static per-node configuration value, not a protocol/state-machine invariant tied to block height [3](#0-2) .

This mirrors the DNN advisory pattern: a special "installation"/bootstrap code path meant to run only once during initial setup remains reachable after the system is live, and is gated only by operational configuration rather than a hard protocol invariant — allowing whoever can reach it (in DNN's case, any unauthenticated HTTP client hitting `InstallWizard.aspx`; here, any transaction sender who knows/uses the fixed `'BOOTSTRAP'` address, which requires no private key) to perform a privileged action (declaring classes for free with zero validation, fee, or nonce consumption) outside of the intended one-time initialization window.

### Impact Explanation
If the `is_authorized_declarer` allow-list for a given node/deployment is not tightened immediately after genesis (or if any node config keeps the bootstrap address whitelisted, e.g., by oversight or because it's a shared default config), any party who submits a V3 declare transaction with `sender_address = 'BOOTSTRAP'`, `nonce = 0`, and zero-fee resource bounds can declare arbitrary classes without paying fees, without any signature/validation, and without consuming any real account's nonce — indefinitely, not just at genesis. This is an unauthorized privileged action (fee-free, validation-free declaration) reachable from an ordinary submitted transaction, and could be used to spam free declarations (resource/DoS abuse against declare-fee economics) for as long as the misconfiguration persists.

### Likelihood Explanation
Reaching this path requires only crafting an RPC declare transaction with the known constant sender address, nonce zero, and zero-fee resource bounds — no cryptography, no privileged access, and no dependency on chain state beyond the gateway's static declarer allow-list. Exploitability is entirely contingent on whether operators keep the `'BOOTSTRAP'` address in the `is_authorized_declarer` list after genesis, which I could not verify from the indexed code (the config default/policy in `crates/apollo_gateway_config/src/config.rs` was not fully retrievable). This uncertainty should be resolved before treating this as a confirmed, actively exploitable bug in current deployments.

### Recommendation
Do not rely solely on the operator-controlled `is_authorized_declarer` allow-list to gate the bootstrap-declare bypass. Enforce a protocol-level invariant (checked in both the blockifier execution path and the Starknet OS Cairo re-execution) that bootstrap declare transactions are only valid when the current block number is genesis (e.g., block 0) or before any prior class has been declared by a real account, so the bypass cannot be exploited after the chain has left its initialization phase regardless of gateway configuration.

### Proof of Concept
1. Query/assume the well-known constant `sender_address = 0x424f4f545354524150` ('BOOTSTRAP') used by `DeclareTransaction::bootstrap_address()` [4](#0-3) .
2. Craft an RPC V3 declare transaction with `sender_address = bootstrap_address()`, `nonce = 0`, `signature = []`, and resource bounds producing `max_possible_fee == 0` (e.g., `ValidResourceBounds::create_for_testing_no_fee_enforcement()`), as done in `generate_bootstrap_declare` [10](#0-9) .
3. Submit it to the gateway on a live (post-genesis) chain whose config still authorizes the bootstrap address as a declarer.
4. Observe that `is_bootstrap_declare` evaluates true and the blockifier declares the class while skipping `__validate_declare__` and fee charging [11](#0-10) , confirmed by the existing unit test `test_bootstrap_declare` which asserts the resulting state diff contains only the class declaration with no fee/nonce changes [12](#0-11) .

        // Do not run validate or perform any account-related actions for declare transactions that
        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {

                let mut context = EntryPointExecutionContext::new_invoke(
                    tx_context.clone(),
                    self.execution_flags.charge_fee,
                    SierraGasRevertTracker::new(GasAmount::default()),
                );
                let mut remaining_gas = 0;
                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());
