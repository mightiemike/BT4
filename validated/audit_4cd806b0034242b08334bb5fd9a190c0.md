## Analysis

The reported bug class — a background/delayed operation writing back state using a **stale, previously-loaded copy of an entity instead of its current state**, silently reverting a concurrent update — has a concrete analog in `shopify-app-js` in the token-exchange invalidation path.

### Title
Stale In-Memory Session Snapshot Overwrites Concurrently-Refreshed Access Token on 401 Invalidation - (File: `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`)

### Summary
`performTokenExchange` loads a session from storage at the start of the request and keeps that in-memory object (`sessionToInvalidate`) as the value to "invalidate" if the subsequent token-exchange call fails with `401`. Because `invalidateAccessToken` performs a full `storeSession` write using this stale snapshot, a session refreshed by a concurrent request in the meantime gets clobbered by the older data.

### Finding Description
`sessionToInvalidate` is captured from `config.sessionStorage.loadSession(sessionId)` before any network round-trip to Shopify occurs: [1](#0-0) 

If the subsequent `api.auth.tokenExchange` call returns `401`, the code invokes `invalidateAccessToken(sessionToInvalidate, config)` on that stale snapshot: [2](#0-1) 

`invalidateAccessToken` blindly clears `accessToken` on the passed-in object and persists the *entire* object back to storage: [3](#0-2) 

`storeSession` implementations perform a full upsert/replace of the row (not a partial patch), e.g. MySQL's `REPLACE INTO`: [4](#0-3)  and Postgres's `INSERT ... ON CONFLICT DO UPDATE SET` over all columns: [5](#0-4)  and the in-memory store's plain key overwrite: [6](#0-5) 

Because loading the "old" session and detecting the 401 failure happen at the start and end of an async flow that includes a network call to Shopify's OAuth token endpoint, there is a real window in which another concurrent request for the same shop (e.g., a second browser tab, or a retried App Bridge fetch) can complete a fresh token exchange and store a valid, newer access token/session in the interim. When the first request's later `invalidateAccessToken` call fires, it overwrites the newer, valid stored session with the stale pre-exchange snapshot (now with `accessToken: undefined`), discarding the concurrently-obtained valid token.

The identical pattern (load-old-session → hold as closure/param → later write it back verbatim on error) also exists in the Remix and React Router adapters' `invalidateAccessToken` helpers and `handleClientError` flows: [7](#0-6) [8](#0-7) 

### Impact Explanation
A valid, freshly-obtained access token for a shop's offline (or online) session can be wiped out by a concurrent request that is still processing an earlier, now-outdated snapshot. This forces the app to re-run token exchange / re-authentication for that shop even though a good token had just been stored, causing intermittent denial-of-service style failures for legitimate merchant sessions until the app happens to refresh again. It does not directly expose secrets or allow cross-tenant access, but it is a session-storage integrity bug where a mutation is applied against a stale reference rather than the current record, exactly mirroring the reported bug class (deduction applied against a stale "latest" reference instead of the current one).

### Likelihood Explanation
Requires two concurrent requests bearing session tokens for the same shop/session id where one exchange succeeds and one fails with 401 in an overlapping window — plausible under normal embedded-app usage (multiple tabs, parallel fetches, App Bridge retries) without requiring any privileged access, since it's triggered purely by ordinary session-token traffic from a single merchant's browser.

### Recommendation
Before invalidating, re-load the current session from storage (or compare a version/updated-at marker, or perform an atomic conditional update keyed on the specific access token being invalidated) rather than writing back the pre-exchange in-memory snapshot. Only clear `accessToken` if the currently stored token still matches the one that was actually rejected.

### Proof of Concept
1. Client A sends a session-token request for shop `S`; offline session in storage has token `T0`.
2. `performTokenExchange` loads session (`T0`) into `sessionToInvalidate` and calls `tokenExchange`.
3. Before Client A's exchange call returns, Client B (second tab / retry) completes its own token exchange for the same shop and stores a new valid session with token `T1` via `storeSession`.
4. Client A's exchange fails with `401` (e.g., transient Shopify error), so `invalidateAccessToken(sessionToInvalidate, config)` runs, storing the old session object (`accessToken: undefined`, all other `T0`-era fields) back into storage.
5. Storage now has no usable access token even though `T1` had just been validly obtained, forcing unnecessary re-authentication for the shop. [9](#0-8)

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
}
