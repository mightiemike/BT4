## Title
Unsigned underflow in Bitcoin difficulty-retarget calculation causes the DA header-chain verifier to compute the wrong next-epoch target - (File: `crates/bitcoin-da/src/verifier.rs`)

### Summary
`calculate_new_difficulty` in the Bitcoin DA verifier computes the epoch timespan as an unsigned `u32` subtraction, `last_timestamp - epoch_start_time`, and then clamps it with unsigned comparisons. Bitcoin Core performs this same calculation with **signed** 64-bit arithmetic precisely because `last_timestamp` can be numerically smaller than `epoch_start_time` (a block's timestamp is only constrained to be greater than the median of the previous 11 blocks, not monotonically increasing relative to the start of its own retarget epoch). When that happens here, the `u32` subtraction wraps around to a huge value instead of going negative, and the subsequent clamp logic pushes the timespan to its *maximum* bound instead of the *minimum* bound that the correct signed computation would produce. This is the same bug class as the Nethermind `SMOD` flaw: an unsigned/absolute-value trick that is not analogous to the signed reference semantics at an extreme input, silently producing a materially different (and wrong) numeric result rather than erroring out. [1](#0-0) 

### Finding Description
`calculate_new_difficulty` is:

```rust
fn calculate_new_difficulty(
    epoch_start_time: u32,
    last_timestamp: u32,
    current_target_bits: u32,
    max_target: U256,
    expected_epoch_timespan: u32,
) -> [u8; 32] {
    // Step 1: Calculate the actual timespan of the epoch
    let mut actual_timespan = last_timestamp - epoch_start_time;
    if actual_timespan < expected_epoch_timespan / 4 {
        actual_timespan = expected_epoch_timespan / 4;
    } else if actual_timespan > expected_epoch_timespan * 4 {
        actual_timespan = expected_epoch_timespan * 4;
    }
    ...
``` [2](#0-1) 

`epoch_start_time` is the timestamp of the first block of the current 2016-block epoch, carried forward in `LatestDaState`, and `last_timestamp` is the timestamp of the last block of that epoch, taken directly from the (attacker/miner-controlled) Bitcoin block header being verified: [3](#0-2) 

The only constraint enforced on a block's timestamp anywhere in this verifier is that it exceeds the median of the *previous 11* blocks' timestamps:
```rust
fn verify_timestamp(block_time: u32, mut prev_11_timestamps: [u32; 11]) -> bool {
    prev_11_timestamps.sort_unstable();
    let median_time = prev_11_timestamps[5];
    block_time > median_time
}
``` [4](#0-3) 

This rule (identical to real Bitcoin's median-time-past rule) does **not** guarantee `last_timestamp >= epoch_start_time`: a miner can legally set decreasing timestamps across an epoch as long as each new timestamp exceeds the rolling MTP of the preceding 11 blocks — this is the basis of Bitcoin's known "time-warp" timestamp-manipulation surface, which is why Bitcoin Core deliberately computes `nActualTimespan` with a signed 64-bit type and clamps a *negative* value up to `nPowTargetTimespan/4` (tightening difficulty).

In this implementation, when `last_timestamp < epoch_start_time`, the `u32` subtraction wraps (Rust's default release profile has `overflow-checks = false`, and no override exists in this repo's `Cargo.toml`s, so the wrap is silent rather than a panic — confirmed by the absence of any `overflow-checks` setting in the repo). The wrapped value is close to `u32::MAX`, which is far larger than `expected_epoch_timespan * 4`, so the `else if` branch fires and clamps `actual_timespan` to `expected_epoch_timespan * 4` — the *maximum* allowed timespan (loosest possible adjustment, target increases toward `max_target`, i.e. difficulty decreases). This is the exact opposite of the semantically-correct outcome (clamp to `expected_epoch_timespan / 4`, i.e. difficulty increases), which is what Bitcoin Core's signed computation produces for the same header sequence.

The resulting `current_target_bits` feeds directly into `verify_header_chain_mainnet` / `verify_header_chain_testnet4` / `verify_header_chain_signet`, which use it as the proof-of-work target against which subsequent block hashes are checked via `verify_target_hash`: [5](#0-4) [6](#0-5) 

Because the computed target is wrongly loosened, the DA header-chain verifier — which underlies the light-client proof's acceptance of L1 headers and hence of all DA inclusion/completeness claims built on top of it (`LatestDaState`, `BlockHashAccessor`) — will accept blocks whose actual proof-of-work is weaker than what the real Bitcoin consensus rules would have required for that epoch.

### Impact Explanation
This breaks the DA-integrity binding between "the target the verifier believes is valid for an epoch" and "the target Bitcoin consensus actually enforces for that epoch." A wrongly loosened target lets an attacker who can influence block timestamps (a capability inherent to being a Bitcoin block producer, not a Citrea-privileged role) get a chain of headers accepted by Citrea's `BitcoinVerifier` with less real proof-of-work than genuine Bitcoin consensus would require, which is a forged/weakened DA inclusion result — matching the Critical impact category "a forged DA inclusion or completeness result." It is deterministic and silent (no panic, no explicit error), and it happens purely inside this repository's header-chain verification logic used by the light-client circuit and full-node DA processing.

### Likelihood Explanation
The precondition — a block near the end of a 2016-block epoch having a timestamp lower than the epoch's first block, while still exceeding the median-time-past of the previous 11 blocks — is a known category of Bitcoin timestamp manipulation available to any block producer (no majority hashrate required, just the ability to occasionally find blocks with a favorable timestamp choice over the ~2-week epoch window). This is the same underlying condition Bitcoin Core explicitly guards against with signed arithmetic, confirming the scenario is realistic on the real chain, not merely theoretical for this codebase's logic.

### Recommendation
Compute the timespan with signed/checked arithmetic that mirrors Bitcoin Core's semantics, e.g. cast both timestamps to `i64`, subtract, and clamp using signed comparisons (or use `saturating_sub`/`checked_sub` with an explicit branch for the "before" case) before clamping to `[expected_epoch_timespan/4, expected_epoch_timespan*4]`, ensuring a numerically negative timespan clamps to the *minimum* bound exactly as Bitcoin Core does.

### Proof of Concept
1. Feed `verify_header_chain_mainnet` (or `testnet4`/`signet`) a sequence of 2016 headers where the last header's timestamp is smaller than `epoch_start_time` (the first header's timestamp) while still satisfying `block_time > median(prev_11_timestamps)` at every step (achievable by choosing a slowly-decreasing timestamp sequence, since the median trails behind).
2. Observe that `calculate_new_difficulty` computes `actual_timespan = last_timestamp - epoch_start_time` as a `u32`, which wraps to a value near `u32::MAX`.
3. The `else if actual_timespan > expected_epoch_timespan * 4` branch fires, clamping to the loosest bound instead of the tightest, producing `current_target_bits` that permit weaker-PoW blocks than genuine Bitcoin consensus would allow for that epoch — divergent from the reference (signed) computation.

/// Calculates the new difficulty target for the next epoch.
fn calculate_new_difficulty(
    epoch_start_time: u32,
    last_timestamp: u32,
    current_target_bits: u32,
    max_target: U256,
    expected_epoch_timespan: u32,
) -> [u8; 32] {
    // Step 1: Calculate the actual timespan of the epoch
    let mut actual_timespan = last_timestamp - epoch_start_time;
    if actual_timespan < expected_epoch_timespan / 4 {
        actual_timespan = expected_epoch_timespan / 4;
    } else if actual_timespan > expected_epoch_timespan * 4 {
        actual_timespan = expected_epoch_timespan * 4;
    }
    // Step 2: Calculate the new target
    let new_target_bytes = bits_to_target(current_target_bits);
    let mut new_target = U256::from_be_bytes(new_target_bytes)
        .wrapping_mul(&U256::from(actual_timespan))
        .wrapping_div(&U256::from(expected_epoch_timespan));
    // Step 3: Clamp the new target to the maximum target
    if new_target > max_target {
        new_target = max_target;
    }

    new_target.to_be_bytes()
}
