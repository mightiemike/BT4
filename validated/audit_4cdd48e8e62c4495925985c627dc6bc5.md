### Title
Unbounded per-sender flood of distinct MessageIds can exhaust functionsHandler's shared pendingRequests cache and deny service to other senders - ([File: core/services/gateway/handlers/functions/handler.functions.go])

### Summary
`requestCache.NewRequest` enforces only a single global cap (`len(c.cache) >= int(c.maxCacheSize)`), keyed by `(sender, messageId)`, with no per-sender quota inside the cache itself. If the operator disables `UserRateLimiter` (an explicitly supported "not specifying RateLimiter config disables rate limiting" mode per `FunctionsHandlerConfig`), a single unprivileged sender can submit `MaxPendingRequests` distinct signed requests with unique `MessageId`s to fill the shared cache and cause `NewRequest` to return "request cache is full" for every other sender's legitimate request until entries time out.

### Finding Description
`HandleLegacyUserMessage` in `core/services/gateway/handlers/functions/handler.functions.go` checks `allowlist` and `userRateLimiter` before calling `h.handleRequest`, which calls `h.pendingRequests.NewRequest(...)`. [1](#0-0)  Inside `requestCache.NewRequest`, the only capacity guard is the global check `if len(c.cache) >= int(c.maxCacheSize) { return errors.New("request cache is full") }`, keyed by `globalId{sender, messageId}` — there is no per-sender limit enforced by the cache itself. [2](#0-1) 

The `UserRateLimiter` field is explicitly optional: `FunctionsHandlerConfig` documents "Not specifying RateLimiter config disables rate limiting", and `NewFunctionsHandlerFromConfig` only constructs `userRateLimiter` when `cfg.UserRateLimiter != nil`. [3](#0-2) [4](#0-3)  When `userRateLimiter` is nil, the `if h.userRateLimiter != nil && !h.userRateLimiter.Allow(...)` check is a no-op and every message passes through to `handleRequest`. [5](#0-4) 

The `Sender` and `MessageId` fields inside `api.Message.Body` are attacker-controlled on the legacy path (the sender only needs a valid ECDSA key to sign the message; there's no server-side allocation of sender identity or message ID uniqueness across senders), so an attacker can generate arbitrarily many distinct `(sender-controlled-messageId)` keys without colliding with existing cache entries, simply incrementing a local counter. Each accepted request occupies a slot in the shared `pendingRequests` cache for the full `RequestTimeoutMillis` window (via `time.AfterFunc(c.timeout, ...)`), so submitting `MaxPendingRequests` requests in quick succession fully saturates the shared bounded resource, and `NewRequest` returns `"request cache is full"` for all subsequent callers, including legitimate senders, until earlier entries time out. [6](#0-5) 

The `OnchainAllowlist` check does mitigate this in configurations where an allowlist is configured, but it is likewise optional ("Not specifying OnchainAllowlist config disables allowlist checks"), so in a deployment relying solely on rate-limiting (or with neither allowlist nor rate limiter configured) an unprivileged sender able to reach the gateway HTTP/WS endpoint can execute this flood.

### Impact Explanation
This is a denial-of-service against the gateway's Functions request/response pipeline: while the cache is saturated, every legitimate user's `secrets_set`/`secrets_list`/`heartbeat` request is rejected with "request cache is full" until the attacker's entries expire after `RequestTimeoutMillis`, and the attacker can resubmit continuously to keep the cache full indefinitely. This matches a resource-exhaustion / availability-impact class finding scoped to the gateway service layer (not chain-state or fund-loss), consistent with a "temporary denial of service of a subsystem" bounty tier rather than a critical fund/consensus compromise.

### Likelihood Explanation
Feasibility is high but strictly conditional on operator configuration: it requires `UserRateLimiter` to be nil/disabled (and ideally `OnchainAllowlist` also disabled or the attacker sender being allowlisted) in the deployed `FunctionsHandlerConfig`. Given the config comments explicitly describe both as optional/disable-able, and `MaxPendingRequests` is a finite value, an attacker with network access to the gateway and the ability to produce valid ECDSA-signed legacy messages (no special privilege required) can trivially generate `MaxPendingRequests` distinct signed messages and repeat the flood as entries expire, making this fully repeatable and scriptable.

### Recommendation
Add a per-sender bound inside `requestCache` (e.g., track counts per `sender` and reject/evict when a single sender exceeds a configurable fraction of `maxCacheSize`), or enforce a mandatory minimum rate limit for `functionsHandler` (do not allow `UserRateLimiter` to be fully disabled without an alternative per-sender cap), and reserve capacity fairness across senders (e.g., a max-per-sender-in-flight-requests counter enforced in `NewRequest` regardless of the optional global rate limiter configuration).

### Proof of Concept
Integration test in `core/services/gateway/handlers/functions/handler.functions_test.go`:
1. Build a `functionsHandler` via `newFunctionsHandlerForATestDON`-style helper but pass `userRateLimiter = nil` and a small `MaxPendingRequests = N` (e.g., 5) with a long `RequestTimeoutMillis`.
2. From a single attacker key, generate `N` signed `secrets_set` messages with distinct `MessageId`s (e.g., "1", "2", ..., "N") via `newSignedMessage`, and call `handler.HandleLegacyUserMessage` for each, asserting `require.NoError` each time (all accepted, filling the cache).
3. Generate one more request from a second, legitimate sender with a fresh `MessageId`, call `HandleLegacyUserMessage`, and assert the returned error is `"request cache is full"` (propagated from `handleRequest`/`pendingRequests.NewRequest`), demonstrating denial of service to the legitimate sender while the attacker's N slots remain occupied.

func (h *functionsHandler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	sender := common.HexToAddress(msg.Body.Sender)
	if h.allowlist != nil && !h.allowlist.Allow(sender) {
		h.lggr.Debugw("received a message from a non-allowlisted address", "sender", msg.Body.Sender)
		promHandlerError.WithLabelValues(h.donConfig.DonId, ErrNotAllowlisted.Error()).Inc()
		return ErrNotAllowlisted
	}
	if h.userRateLimiter != nil && !h.userRateLimiter.Allow(msg.Body.Sender) {
		h.lggr.Debugw("rate-limited", "sender", msg.Body.Sender)
		promHandlerError.WithLabelValues(h.donConfig.DonId, ErrRateLimited.Error()).Inc()
		return ErrRateLimited
	}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalId]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalId{request.Body.Sender, request.Body.MessageId}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
	if len(c.cache) >= int(c.maxCacheSize) {
		return errors.New("request cache is full")
	}
	codec := api.JsonRPCCodec{}
	timer := time.AfterFunc(c.timeout, func() {
		err := c.deleteAndSendOnce(key, handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(request), ErrorCode: api.RequestTimeoutError})
		if err != nil {
			lggr.Errorw("failed to send timeout response", "error", err)
		}
	})
	c.cache[key] = &pendingRequest[T]{Callback: callback, responseData: responseData, timeoutTimer: timer}
	return nil
}
