## Finding

### Title
Replay-verification tool `replay_on_archive` accepts corrupted/incorrect position and hot-state checkpoint roots as valid because `ensure_match_transaction_info` never checks them - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole equality check used by the archive replay-verification tool (`storage/db-tool/src/replay_on_archive.rs`) to confirm that locally re-executed transaction outputs match the authenticated `TransactionInfo` pulled from a backup/archive. The function checks status, gas, write-set hash (`state_change_hash`), and event root hash, but explicitly skips `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — fields that anchor the state/hot-state/position Merkle roots into the transaction-accumulator-committed `TransactionInfo`.

### Finding Description [1](#0-0) 

The comparator computes and validates:
- `status` vs expected `TransactionStatus`
- `gas_used`
- `write_set_hash == txn_info.state_change_hash()`
- `event_root_hash == txn_info.event_root_hash()`

But the code contains its own acknowledgment of the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This is directly consumed by `Verifier::execute_and_verify` in the archive-replay tool, which locally re-executes transactions from backup data via `AptosVMBlockExecutor` and calls `ensure_match_transaction_info` as the *only* verification of correctness against the archived, ledger-info-signed `TransactionInfo`: [3](#0-2) 

Because `TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as fields that are themselves accumulated into the transaction-info hash (and hence into the ledger-info-signed accumulator root): [4](#0-3) 

...a divergence between the locally computed Sparse-Merkle/Jellyfish state root, hot-state root, or the newly introduced "trading-native" position-state root (built in `execution/executor/src/workflow/do_state_checkpoint.rs`, e.g. `get_position_checkpoint_hashes`) and what was actually committed on-chain will not be caught by this replay tool, even though the write set and events match.

The related executor code that produces these checkpoint hashes is itself complex and version-range-dependent (`get_position_checkpoint_hashes`), computing SMT-style summaries incrementally from a `parent`/`persisted` base state and combining per-transaction write ops into leaf updates: [5](#0-4) 

If this computation has any bug (index-range errors, wrong `last_checkpoint_index`, incorrect base-summary selection at genesis/first-block boundaries, etc.), the resulting root would silently diverge from the authenticated on-chain root without failing archive replay-verification.

### Impact Explanation
This breaks the "committed state that differs from the correct VM result... must not silently pass proof/replay verification" invariant. `replay_on_archive` is explicitly a security/integrity tool meant to detect state divergence between a purportedly-synced archive node and canonical, locally re-executed results. Its entire purpose is defeated for the state/hot-state/position checkpoint roots: a corrupted or malicious archive (or a node with a subtly buggy trading-native state root computation) can present transaction infos with wrong checkpoint hashes, and this tool will still report "replay successful," masking a genuine ledger-state divergence. Since this is the same class of check used to validate hard-fork/replay correctness of the authenticated ledger state, a bug here directly undermines confidence in "authenticated" proof/replay tooling, matching the report's proof-and-storage-pivot scope (in-scope: "Hard-fork-only divergence during commit, replay, restore, or proof verification").

### Likelihood Explanation
The gap is not theoretical: it is called out by the developers themselves in the code comment as a known, currently-unaddressed limitation gating the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature. The relevant checkpoint-hash computation (`get_position_checkpoint_hashes`) is new, non-trivial logic involving incremental checkpoint/latest summary extension, base-summary selection at genesis, and index-range slicing — exactly the kind of code prone to off-by-one or base-state selection bugs. Because the comparator that would normally catch such bugs during replay-verification deliberately does not check these hashes, any regression in that logic would go undetected by this tool until/unless some other consensus-level check (out of scope here) also fails.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding locally computed roots whenever they are present/expected in `txn_info`, before further enabling or relying on `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-gated features. At minimum, `replay_on_archive` should fail loudly (or emit a distinct warning) rather than silently pass when these fields cannot be checked.

### Proof of Concept
Conceptual repro (cannot be executed without a full node/backup environment):
1. Run `replay_on_archive` against an archive/backup where a transaction's committed `TransactionInfo` (V1) has correct `state_change_hash`/`event_root_hash` but a `position_state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`state_checkpoint_hash`) that does not match what local re-execution via `do_state_checkpoint.rs`'s checkpoint-summary logic would produce (e.g., inject a bug in `get_position_checkpoint_hashes`, such as an off-by-one in `last_checkpoint_index` or wrong base-summary selection at a chunk boundary).
2. Execute `Verifier::verify`/`execute_and_verify`, which calls `ensure_match_transaction_info`.
3. Observe that verification succeeds ("replayed and verified") despite the position/state/hot-state root divergence, because these fields are never compared, per the code path cited above.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
