Based on the code I reviewed, I found a valid analog of the report's bug class ("low-liquidity market manipulation of a stateful pricing/rate mechanism") in java-tron's TRC10 Bancor-relay exchange (the on-chain AMM market, functionally the closest analog to Morpho Blue's stateful IRM/market-math component). The root cause is structurally identical: a market's price/rate is derived purely from the instantaneous token balances held in the pool, and the contract enforces only an upper bound (`getExchangeBalanceLimit`) on those balances, never a lower bound/minimum liquidity floor, at either creation or after a withdrawal.

### Title
Unprivileged creation and manipulation of near-zero-liquidity TRC10 exchange markets allows attackers to control the Bancor-relay exchange rate - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
The TRC10 `Exchange`/`ExchangeV2` feature implements an on-chain Bancor-relay AMM (`ExchangeCapsule.transaction` → `ExchangeProcessor`/`SafeExchangeProcessor`). As with Morpho Blue's stateful IRM, the exchange rate is derived entirely from the current pool balances with no minimum-liquidity safeguard, so any unprivileged account can create or drive a market into a near-zero-liquidity state and dictate the resulting price for anyone who subsequently trades against it.

### Finding Description
`ExchangeCreateActuator.doValidate()` only checks that `firstTokenBalance` and `secondTokenBalance` are `> 0` and below `dynamicStore.getExchangeBalanceLimit()`; there is no minimum liquidity requirement: [1](#0-0) 

This means an attacker can create a market with e.g. `firstTokenBalance = 1`, `secondTokenBalance = 1`. The exchange rate for any subsequent trade is computed purely from these two balances by `ExchangeCapsule.transaction()`, which calls the Bancor-relay formula in `ExchangeProcessor`/`SafeExchangeProcessor`: [2](#0-1) [3](#0-2) 

Because the formula's exponent terms (`quant / newBalance`, `supplyQuant / supply`) are extremely sensitive when the balance is tiny (1 unit), an attacker who is the sole liquidity provider fully controls the resulting price curve for any counterparty who trades against the pool, exactly analogous to how Morpho's `AdaptiveCurveIrm` was manipulated by driving utilization to 100% with 1 wei of supply/borrow. `ExchangeWithdrawActuator.doValidate()` similarly permits the creator to withdraw liquidity down toward this same degenerate near-zero state at any time after the market has already attracted deposits, re-creating the same low-liquidity manipulation window on a previously healthy market: [4](#0-3) 

Unlike `ExchangeTransactionActuator`, which at least enforces a caller-supplied `tokenExpected` slippage floor, `ExchangeCreateActuator` and `ExchangeWithdrawActuator` have no rate/impact-based validation tied to a liquidity floor, so nothing prevents driving a market to (or creating it at) the degenerate 1-unit state.

### Impact Explanation
A victim who queries the pool's implied price and submits an `ExchangeTransactionContract` (setting `tokenExpected` based on a stale or attacker-influenced quote) against a 1-unit-liquidity pool can be forced into an extremely disadvantageous conversion rate, resulting in direct loss of TRX/TRC10 assets, mirroring the report's "loss of funds for small depositors" and "attacker-controlled rate" outcomes. Because balances are also used unmodified as the base for subsequent trades (`ExchangeCapsule.transaction`), an attacker-created degenerate pool can persist indefinitely and be advertised/linked to lure counterparties, and the resulting extreme balance ratios also stress the double-precision `Math.pow` path in the legacy `ExchangeProcessor` (mitigated only when `allowStrictMath`/`allowHarden` proposals are active), increasing the chance of rounding-driven value extraction at the edges.

### Likelihood Explanation
Exploitability requires no privileged role: any account can call `ExchangeCreateActuator` (paying only `getExchangeCreateFee()`) to create a 1-unit pool, or the market creator can call `ExchangeWithdrawActuator` to drain their own market down to near-zero balances at will. Both paths are reachable directly via broadcast transactions from any account, matching the "unprivileged" scope required by this analysis.

### Recommendation
Enforce a minimum liquidity floor (analogous to Morpho's recommended "sufficient assets" check before invoking the rate function) in `ExchangeCreateActuator.doValidate()` and `ExchangeWithdrawActuator.doValidate()`, e.g. require `firstTokenBalance`/`secondTokenBalance` (and the resulting balances after withdrawal) to remain above a configurable minimum before allowing market creation, injection, withdrawal, or transaction execution against the pool.

### Proof of Concept
1. Attacker account A calls `ExchangeCreateActuator` with `firstTokenBalance = 1` (TRX), `secondTokenBalance = 1` (TRC10 token `X`) — passes validation since both are `> 0` and below `getExchangeBalanceLimit()` (`ExchangeCreateActuator.java:201-208`).
2. The resulting `ExchangeCapsule` now has a 1:1 balance ratio with total liquidity of 1 unit each side.
3. Victim B, observing/being directed to this market, submits `ExchangeTransactionContract` to swap a nontrivial amount of TRX for token `X` (or vice versa); `ExchangeCapsule.transaction()` computes the output via the Bancor-relay formula purely from the 1-unit base balances (`ExchangeCapsule.java:124-158`, `ExchangeProcessor.java:17-45`), yielding an exchange rate entirely dictated by the tiny pool state that A alone established.
4. Alternatively, on an existing, previously well-funded market, the creator (A) calls `ExchangeWithdrawActuator` repeatedly, which only checks `firstTokenBalance < tokenQuant` / `secondTokenBalance < anotherTokenQuant` (`ExchangeWithdrawActuator.java:221-227`) with no floor, allowing A to withdraw down to the same degenerate low-liquidity state right before B's transaction is broadcast.   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
