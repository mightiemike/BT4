## Title
Unvalidated DA block height allows a light-client proof to diverge from the real Bitcoin chain state - (File: `crates/bitcoin-da/src/spec/header.rs`, `crates/bitcoin-da/src/verifier.rs`)

### Summary
`HeaderWrapper::height` is a free-standing `u64` field supplied by whoever builds the light-client circuit input. `verify_hash()` only checks that the *precomputed hash* matches the digest of the 80-byte Bitcoin header (`version`, `prev_blockhash`, `merkle_root`, `time`, `bits`, `nonce`); `height` is never part of that preimage and is never cross-checked against the BIP-34 height that Bitcoin actually encodes in the block's coinbase transaction (which is already present in the same proof input as `inclusion_proof.coinbase_tx`). This is exactly the class of bug described in the SP1Blobstream report: a block-height value is accepted as a bare, separately-supplied input instead of being derived/validated from the block data it is supposed to describe.

### Finding Description
`HeaderWrapper` stores `height` as an ordinary struct field: [1](#0-0) 

`verify_hash()` only recomputes the digest of the raw 80-byte header bytes (`self.header`), which does **not** include `height`: [2](#0-1) 

In the light-client circuit's DA path (`BitcoinVerifier::verify_transactions` / `verify_header_chain_common`), `block_header.height()` is used for the consecutive-height check, the epoch/difficulty-retarget index, and the previous-timestamps index, but it is never checked against the BIP-34 height embedded in `inclusion_proof.coinbase_tx.input[0].script_sig`, even though that coinbase transaction is already an input to `verify_transactions`: [3](#0-2) [4](#0-3) 

By contrast, `BitcoinHeaderShortProof::verify()` (used for the EVM light-client system transaction path) deliberately ignores `self.header.height` and instead independently derives the trusted height from the BIP-34 script in the coinbase transaction: [5](#0-4) 

This shows the codebase already recognizes that `HeaderWrapper.height` is untrusted input in one place, but the light-client circuit's own header-chain verification (`verify_header_chain_common`, `verify_header_chain_mainnet/testnet4/signet`) never applies the same BIP-34 derivation/check, and instead trusts the bare `height` field for:
- the "heights are consecutive" check,
- computing `epoch_block = height % BLOCKS_PER_EPOCH` (decides *when* to recompute the difficulty target),
- indexing `prev_11_timestamps[height % 11]`. [6](#0-5) 

Because the target/difficulty recomputation is gated on `height % BLOCKS_PER_EPOCH == 0` rather than on the real epoch boundary from the actual chain, a prover who supplies a `height` value that is internally consistent (each new header height is one greater than the previous output's stored height) but shifted relative to Bitcoin's true height can cause the circuit to compute a target/bits value using the wrong epoch window. `verify_target_hash` then checks the block hash against this attacker-influenced target instead of the value that is actually enforced by Bitcoin consensus at the real height, all while `verify_hash`, `prev_hash` chaining, and the block's own PoW hash still validate. The resulting `LightClientCircuitOutput.latest_da_state.block_height` (and the chain built on it) can diverge from the true DA chain while still producing a proof accepted by verifiers (e.g. Clementine's bridge proof, per `docs/light-client-circuit.md`), which relies on the light-client proof's height/DA-state binding. [7](#0-6) 

### Impact Explanation
This breaks the equality "the DA height and difficulty state committed by the light-client proof == the actual Bitcoin chain's height/difficulty state at that point," which is exactly the class of binding this program calls out as Critical ("a light client proof split across honest provers," "a forged DA inclusion or completeness result," "honest nodes converging on an unproved root"). Since the light-client proof is the artifact consumed by Clementine's Bridge Proof to resolve operator challenges, an inconsistency here can let a dishonest prover produce a proof whose committed DA state (height, resulting difficulty target lineage) does not correspond one-to-one with the real Bitcoin chain, while still passing all of the circuit's internal checks (`verify_hash`, `prev_hash` continuity, and `verify_target_hash` against the miscalculated target).

### Likelihood Explanation
Exploitation requires only control over the circuit input construction for a light-client proof — no privileged role, key, or majority hashrate is needed, since `HeaderWrapper.height` is simply not constrained by the block-hash preimage or by the coinbase BIP-34 data that is already part of the same proof input. Any party able to submit an input to the light-client-prover binary (or run the guest program directly) can supply a shifted-but-self-consistent height sequence.

### Recommendation
Derive `height` inside `verify_transactions` (or `verify_header_chain_common`) from the BIP-34 script in `inclusion_proof.coinbase_tx`, the same way `BitcoinHeaderShortProof::verify()` already does, and assert it equals `block_header.height()` before that value is used for consecutive-height checks, epoch/difficulty computation, or committed into `LatestDaState`. Alternatively, include `height` in the data covered by `verify_hash()`'s preimage so it cannot be supplied independently of the header it purports to describe.

### Proof of Concept
1. Take a genuine Bitcoin header `H` at true height `h` with valid PoW and a valid coinbase transaction encoding BIP-34 height `h`.
2. Build `HeaderWrapper::new(H, tx_count, h', txs_commitment)` with `h' != h` (but internally consistent with the previous light-client proof's stored height, i.e. `h' == prev_output.latest_da_state.block_height + 1`).
3. Feed this into `LightClientCircuitInput.da_block_header` together with the real `inclusion_proof`/`completeness_proof` for block `H`.
4. `run_circuit` → `verify_header_chain_mainnet` (or testnet4/signet) passes: `verify_hash()` succeeds because it only checks the real header bytes; the consecutive-height check succeeds because `h'` is consistent with the previous forged state; `verify_target_hash` is evaluated against a target computed from the *forged* epoch position (`h' % BLOCKS_PER_EPOCH`), not the true one.
5. The resulting `LightClientCircuitOutput.latest_da_state.block_height` is `h'`, permanently decoupled from the real chain height `h`, and this incorrect binding propagates to any downstream consumer (e.g. Clementine bridge proof verification) trusting the light-client proof's DA height.

pub struct HeaderWrapper {
    pub(crate) header: BitcoinHeaderWrapper,
    pub(crate) tx_count: u32,
    pub(crate) height: u64,
    pub(crate) txs_commitment: [u8; 32],
    pub(crate) precomputed_hash: BlockHashWrapper,
}

impl BlockHeaderTrait for HeaderWrapper {
    type Hash = BlockHashWrapper;

    fn prev_hash(&self) -> Self::Hash {
        BlockHashWrapper::from(self.header.prev_blockhash.to_byte_array())
    }

    fn hash(&self) -> Self::Hash {
        self.precomputed_hash.clone()
    }

    fn verify_hash(&self) -> bool {
        self.hash() == BlockHashWrapper(self.block_hash())
    }

    fn txs_commitment(&self) -> Self::Hash {
        BlockHashWrapper::from(self.txs_commitment)
    }

    fn height(&self) -> u64 {
        self.height
    }

    fn time(&self) -> sov_rollup_interface::da::Time {
        sov_rollup_interface::da::Time::from_secs(self.header.time as i64)
    }

    fn bits(&self) -> u32 {
        self.header.bits.to_consensus()
    }

    fn coinbase_txid_merkle_proof_height(&self) -> u64 {
        f64::log2(self.tx_count as f64).ceil() as u64
    }
}
