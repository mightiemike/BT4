### Title
Stale/compromised access token is never cleared from persistent session storage during token invalidation - ([File: packages/apps/shopify-app-express/src/helpers/invalidate-access-token.ts])

### Summary
`invalidateAccessToken()` "revokes" a session's access token by setting `session.accessToken = undefined` and calling `storeSession(session)` [1](#0-0) , but every RDBMS-backed `SessionStorage` implementation serializes the session via `Session.toPropertyArray()`, which explicitly filters out any property whose value is `undefined`/`null` before building the `INSERT ... ON CONFLICT DO UPDATE SET` statement [2](#0-1) . Because `accessToken` is `undefined`, it is dropped from the `entries` array and therefore omitted from both the column list and the `DO UPDATE SET` clause, e.g. in the PostgreSQL adapter [3](#0-2) . This is structurally identical to the reported bug class: a "set to falsy/zero value" update is silently dropped by a guard (`value !== undefined`), so the caller believes the sensitive field (feeIndex/groupIndex in the original report, `accessToken` here) was cleared/updated, when in fact the previous value is left untouched in storage.

### Finding Description
The invalidation helpers in `shopify-app-express` [4](#0-3) , `shopify-app-react-router` [5](#0-4) , and `shopify-app-remix` [6](#0-5)  are all invoked from the 401-handling branch of token-exchange logic, e.g. `performTokenExchange()`, when a downstream Shopify Admin/token-exchange call returns HTTP 401, signaling the stored access token is stale/revoked/compromised [7](#0-6) . The intent is clearly to purge the bad token from persistent storage so it can never be used again and a fresh token-exchange is forced next time.

However, `storeSession()` in database-backed adapters relies on `Session.toPropertyArray()`, whose filter `value !== undefined && value !== null` removes the `accessToken` key entirely once it's set to `undefined` [2](#0-1) . The resulting `entries` array is used to build both the `INSERT` column list and the `ON CONFLICT ... DO UPDATE SET` clause; a key that isn't in `entries` is not part of the `SET` clause and the pre-existing column value in the database row is left completely unmodified. The same dynamic-projection pattern (build query from `toPropertyArray()`) exists across the RDBMS-family adapters (Postgres shown here, and structurally the same approach documented for MySQL/SQLite/Drizzle adapters). This matches the reported bug class exactly: a guard designed to skip "empty" updates instead silently no-ops a security-critical field reset, deceiving the calling code (and the app owner) into believing the sensitive value was cleared.

The `MemorySessionStorage` test double masks this in most unit tests because it stores the same in-memory `Session` object reference, so `accessToken: undefined` is trivially visible on read-back [8](#0-7)  — this explains why the existing test suite (`perform-token-exchange.test.ts`) shows `expect(stored?.accessToken).toBeUndefined()` passing even though the same code path against a real database-backed adapter would not clear the column. This discrepancy between in-memory test coverage and real persistent-storage behavior is exactly what let the original PairInfos.sol issue slip through — the owner (or here, the app) believes the sensitive field was reset when it wasn't.

### Impact Explanation
If a merchant's stored offline/online access token is flagged as invalid/compromised (e.g. Shopify returns 401 during token exchange because the token was revoked by the merchant, by Shopify, or due to a suspected leak), the app's intended remediation — wiping the token from the database — silently fails for any RDBMS-backed session storage. The old (now-untrusted/stale) `accessToken` value remains in the `shopify_sessions` table indefinitely. Any other code path that reads the session directly from storage (bypassing the in-memory reference used immediately after invalidation, e.g. a subsequent process, worker, or webhook handler that calls `loadSession`) will retrieve and could reuse the stale token, defeating the entire purpose of the invalidation and continuing to trust a token Shopify has already rejected/revoked.

### Likelihood Explanation
This triggers automatically and deterministically any time a 401 is returned from `tokenExchange` (a normal, expected occurrence for expired/rotated/revoked tokens) while using any RDBMS/dynamic-projection session storage adapter — no attacker action is required to trigger the no-op; it happens on every legitimate invalidation attempt. It is a systemic app-level and library-level logic defect, always reachable from the standard authenticated-request flow when the merchant's token is stale.

### Recommendation
Do not rely on `toPropertyArray()`'s undefined-filtering semantics for clearing fields. Either:
- Change `invalidateAccessToken()` to explicitly set `accessToken` to an empty string (or another sentinel that survives the `!== undefined && !== null` filter) so it is included in the `SET` clause, or
- Add a dedicated `clearAccessToken`/`invalidateSession` storage method that issues an explicit `UPDATE ... SET "accessToken" = NULL WHERE "id" = $1` for all RDBMS adapters, bypassing the property-array projection entirely, or
- Change the property-array/serialization contract so that explicitly-set `undefined` values are distinguished from "not present" and are still included (as `NULL`) in the generated `SET`/column list.

### Proof of Concept
1. Configure an app with `PostgreSQLSessionStorage` (or MySQL/SQLite) and store an offline session with `accessToken: 'stale-token'`.
2. Trigger a request that goes through `performTokenExchange`, where the mocked `tokenExchange` (or any downstream Admin API call performed with that session) returns an `HttpResponseError` with `code: 401`.
3. Observe `invalidateAccessToken(sessionToInvalidate, config)` is called, setting `sessionToInvalidate.accessToken = undefined` and calling `config.sessionStorage.storeSession(sessionToInvalidate)` [9](#0-8) .
4. Directly query the underlying `shopify_sessions` table (bypassing the app's in-process object) for that session id: the `accessToken` column still contains `'stale-token'`, because the generated `UPDATE ... SET` clause built from `toPropertyArray()` never included the `accessToken` column [10](#0-9) .
5. A subsequent `loadSession(id)` call (e.g., from a different process, retried request, or background job) returns the `Session` object still populated with the stale `accessToken`.

  public async storeSession(session: Session): Promise<boolean> {
    await this.ready;

    // Note milliseconds to seconds conversion for `expires` property
    const entries = session
      .toPropertyArray(true)
      .map(([key, value]) =>
        key === 'expires'
          ? [key, Math.floor((value as number) / 1000)]
          : [key, value],
      );
    const query = `
      INSERT INTO "${this.options.sessionTableName}"
      (${entries.map(([key]) => `"${key}"`).join(', ')})
      VALUES (${entries
        .map((_, i) => `${this.client.getArgumentPlaceholder(i + 1)}`)
        .join(', ')})
      ON CONFLICT ("id") DO UPDATE SET ${entries
        .map(([key]) => `"${key}" = Excluded."${key}"`)
        .join(', ')};
    `;
    await this.client.query(
      query,
      entries.map(([_key, value]) => value),
    );
    return true;
