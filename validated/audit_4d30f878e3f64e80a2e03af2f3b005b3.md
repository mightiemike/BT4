### Title
Address Registrar `register()` permanently retains any excess attached NEAR deposit beyond the required storage cost - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar::register` function is a `#[payable]` method that any unprivileged account can call by attaching NEAR to a `FunctionCall` action. It validates only that `given_deposit >= required_deposit` and, on a successful (non-collision) registration, never refunds the difference between the attached deposit and the actual storage cost, permanently keeping the full amount in the contract.

### Finding Description
`register()` computes `required_deposit` from the exact number of bytes needed to store the address/account mapping, then reads `given_deposit` via `env::attached_deposit()` [1](#0-0) . It panics only if the deposit is insufficient [2](#0-1) . In the success path (`Entry::Vacant`), the entry is inserted and the function returns without ever comparing `given_deposit` to `required_deposit` or refunding the surplus [3](#0-2) . A refund transfer back to the caller is issued only in the `Entry::Occupied` (collision) branch [4](#0-3) , meaning that path explicitly acknowledges the need to return unused deposit but the success path does not implement equivalent logic. This directly mirrors the reported Sense `Periphery.sponsorSeries` bug class: a payable entry point that accepts more value than it needs and only returns it in some code branches, silently keeping any excess in the other branches.

This is confirmed by the project's own integration test, which asserts that an over-deposit is *not* refunded on success: [5](#0-4) 
The deposit passed (`320000000000000000000` yoctoNEAR, far larger than the storage cost of a short `birchmd.near` entry) is retained in full by the contract, as opposed to only the storage-cost portion, per `post_tx_account_balance - pre_tx_account_balance >= deposit_amount`.

### Impact Explanation
`AddressRegistrar` is the fixed, hard-coded account that every deployed Wallet Contract (`near-wallet-contract`, NEAR's ETH-address-emulation account type) consults and calls into for address registration [6](#0-5) . Any unprivileged transaction signer (a user or a relayer forwarding a user's ETH-style transaction) who registers an account name with an over-estimated deposit permanently loses the excess NEAR: it is neither refunded nor recoverable, since the contract has no withdraw/refund path for the surplus. This is a genuine, concrete loss of user funds reachable directly through a single contract call (`register`), matching the required impact bar ("permanently frozen funds").

### Likelihood Explanation
Likelihood is high in practice: `required_deposit` is a dynamically computed, non-round-number quantity (`storage_byte_cost * bytes_to_store`), so any caller who doesn't compute the exact minimal deposit off-chain (e.g., attaching a round number like `1 NEAR` or reusing NEP-141's fixed `NEP_141_STORAGE_DEPOSIT_AMOUNT` constant used elsewhere in the same wallet-contract codebase) will overpay and lose the difference. Since this is the only registrar contract referenced by the Wallet Contract flow, it is likely to be invoked by many distinct end users/relayers.

### Recommendation
In the `Entry::Vacant` success branch of `register()`, compute `given_deposit.saturating_sub(required_deposit)` and, if non-zero, issue a `promise_batch_action_transfer` refund of the surplus back to `env::predecessor_account_id()`, mirroring the refund logic already present in the `Entry::Occupied` branch.

### Proof of Concept
1. Deploy `AddressRegistrar` (as done in `TestContext::new()` used across the wallet-contract test suite).
2. Call `register({"account_id": "shortname.near"})` attaching a deposit far larger than the byte-cost-derived `required_deposit` (e.g., `NearToken::from_yoctonear(320000000000000000000)` as in the existing `test_register_without_deposit` test) [7](#0-6) .
3. Observe that `register()` succeeds (`Entry::Vacant` branch), and the entire attached deposit — not just the storage cost — is retained by the contract; no refund receipt is created, confirmed by the test assertion `post_tx_account_balance - pre_tx_account_balance >= deposit_amount` [8](#0-7) .
4. The caller has permanently lost `given_deposit - required_deposit` yoctoNEAR with no recovery mechanism.
