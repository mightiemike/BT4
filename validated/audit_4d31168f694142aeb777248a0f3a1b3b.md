### Title
`ensure_match_transaction_info` skips checkpoint-root comparison, letting `replay_on_archive` accept a divergent committed state root as valid - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-comparison function used by replay/verification tooling to check a freshly-executed `TransactionOutput` against the archived, ledger-committed `TransactionInfo`. It verifies status, gas used, write-set hash, and event root hash, but explicitly and admittedly does **not** verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that authenticate the committed state (Sparse-Merkle/JMT and native-position) root. This mirrors the bug-class in the external report: a check exists for one dimension (write-set/event hashes ≈ `totalPrice`) while a second, security-relevant dimension (state checkpoint root ≈ `msg.value`/currency consistency) is silently left unchecked, so divergent/incorrect data is accepted where it should be rejected.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  compares a `TransactionOutput` produced by re-execution against an `expected` `TransactionInfo` retrieved from backup/archive storage. It checks:
- `status` vs `txn_info.status()` [2](#0-1) 
- `gas_used` vs `txn_info.gas_used()` [3](#0-2) 
- write-set hash vs `txn_info.state_change_hash()` [4](#0-3) 
- event root hash vs `txn_info.event_root_hash()` [5](#0-4) 

But it never checks `txn_info.state_checkpoint_hash()`, the `hot_state_checkpoint_hash`, or the `position_state_checkpoint_hash` fields carried by `TransactionInfoV1` [6](#0-5) . The code itself documents this gap: [7](#0-6) 

i.e. the comment admits that "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution," and that checkpoint-hash validation must be added "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`."

The concrete consumer of this comparator is the archive-replay verifier used to attest ledger correctness offline: `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` calls `ensure_match_transaction_info(version, &expected_txn_infos[idx], Some(&expected_writesets[idx]), Some(&expected_events[idx]))` on every VM-executed output and only fails the transaction if this function returns an error [8](#0-7) . Because `ensure_match_transaction_info` cannot detect a mismatch confined to the checkpoint/state-root fields, `replay_on_archive` (and the other callers in `aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`) will report these transactions as successfully verified even when the locally-computed state (or hot-state, or native-position) Merkle root differs from the state root that was actually committed and signed into the chain's `TransactionInfo`/accumulator.

### Impact Explanation
This breaks the "proof and storage pivot" invariant that "authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object" and that "replay paths ... must not reinterpret committed data into a different ledger state." Concretely:
- A state root divergence (whether from a storage bug, a non-deterministic VM/native execution path, or a maliciously/accidentally corrupted state-checkpoint field in an archive) will not be flagged by the replay-verify tool, since only write-set/event hashes are checked, not the state checkpoint root that is actually anchored in the signed `LedgerInfo`/accumulator chain.
- Operators and auditors rely on `replay_on_archive` as the ground-truth attestation that a historical/backup dataset is internally consistent and matches the mainnet-committed state. A silent skip of checkpoint-hash comparison means this attestation can pass even though the state root committed on-chain is not reproducible from local execution — a direct proof-integrity gap for a security-critical verification tool.
- Because the affected fields are exactly the ones gating the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature (native "position" state, i.e. Aptos's TradingNative feature), this gap is pre-existing/latent now for `state_checkpoint_hash`/`hot_state_checkpoint_hash` on any transaction, and will become fully exploitable for `position_state_checkpoint_hash` divergence as soon as that feature is turned on, with no accompanying fix to this comparator.

### Likelihood Explanation
The vulnerable code path is unconditionally reached whenever `ensure_match_transaction_info` is used by any of its callers (db-tool replay-verify, aptos-debugger, aptos-move CLI) — there is no feature gate on the comparator itself. Any scenario that produces a correct write set/events but a wrong state checkpoint root (a plausible non-deterministic bug class distinct from write-set/event computation, e.g. issues in Merkle root computation, hot-state root computation, or native-position tree updates) would be silently missed. The severity of triggering it does not require an attacker at all — it is an unprivileged, non-malicious integrity gap in the verification tool's own logic, self-documented by the aptos-core team as a known and currently-unaddressed omission.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash()` (and, when present, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) between the locally-derived checkpoint output and `txn_info`, failing verification on any mismatch, consistent with how `write_set_hash` and `event_root_hash` are already validated. This requires passing the state-checkpoint hashes computed during replay (as already available via `StateCheckpointOutput`/`DoStateCheckpoint`) into this comparator instead of leaving the field entirely unchecked, and doing so before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled as the comment recommends.

### Proof of Concept
1. Take an archived/backup transaction chunk whose associated `TransactionInfo` has correct `transaction_hash`, `state_change_hash` (write-set hash), and `event_root_hash`, but a `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) that does not match the root actually produced by replaying that transaction locally (e.g., due to a bug in state-checkpoint/Merkle root computation, or a corrupted backup manifest field).
2. Run `db-tool replay-on-archive` (`storage/db-tool/src/replay_on_archive.rs`) over this range.
3. `execute_and_verify` calls `TransactionOutput::ensure_match_transaction_info` for each transaction [9](#0-8) ; because that function only checks status/gas/write-set-hash/event-root-hash and never touches `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [10](#0-9) , the call returns `Ok(())` despite the state-root divergence.
4. The tool reports the chunk as fully verified with no failed transactions, even though the actual committed state root cannot be reproduced from local execution — the proof-integrity failure is masked.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
