### Title
Loss of Funds via `DeleteAccount` to a Non-Existent `beneficiary_id` - (File: `runtime/runtime/src/actions.rs`)

### Summary
The external report is about missing zero-address validation on a fee-recipient setter, causing funds to be sent to an unusable address. The reachable analog in nearcore is `action_delete_account`, which unconditionally creates a balance-refund receipt to the caller-supplied `beneficiary_id` without ever validating that this account actually exists. Because refund receipts are terminal (they never spawn a further refund on failure, to avoid infinite refund loops), a `DeleteAccount` action pointed at a non-existent `beneficiary_id` — the NEAR analog of a "zero address" — causes the deleted account's entire balance to be permanently and irrecoverably lost.

### Finding Description
`action_delete_account` computes `account_balance` from the account being deleted and pushes a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` with no check that `beneficiary_id` corresponds to an existing account: [1](#0-0) 

The only validation performed on `beneficiary_id` anywhere in the pipeline is that it is a syntactically valid `AccountId` (`InvalidAccountId`), as documented for `DeleteAccountAction`: [2](#0-1) 

There is no existence check comparable to a "zero address" check. The runtime's own regression test confirms that when a balance-refund receipt targets an account that does not exist, the receipt fails with `AccountDoesNotExist` and the target account is never created — i.e., the transferred value is simply dropped, not returned to any party: [3](#0-2) 

This mirrors the reported Solidity bug class exactly: a value-carrying "recipient" field (there, `feeAddress`; here, `beneficiary_id`) is accepted without any existence/validity guard beyond superficial format checks, and funds routed to that unchecked recipient are permanently lost when the recipient turns out to be unusable.

### Impact Explanation
Any unprivileged transaction signer who submits a `DeleteAccount` action (directly or via a meta-transaction/relayer) with a `beneficiary_id` that does not exist on-chain causes their own account balance to be burned with no recovery path — a permanent, protocol-accepted loss of funds. This can happen accidentally (typo in the beneficiary account name) or be used adversarially against a victim by a relayer/dApp that constructs the delete transaction on the user's behalf with an unregistered `beneficiary_id`, since the signer has no independent confirmation that the beneficiary account exists at execution time (it could be deleted between signing and execution, or never have existed).

### Likelihood Explanation
High reachability: `DeleteAccount` is a standard, unprivileged action available to any account owner or meta-transaction sender, requiring only a signed transaction with no special permission beyond `check_actor_permissions`. No adversarial validator, network, or sync assumptions are required — a single submitted transaction from an ordinary user is sufficient to trigger the loss.

### Recommendation
Before creating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` refers to an existing account (or otherwise reject/short-circuit `DeleteAccount` actions whose `beneficiary_id` cannot receive funds), analogous to adding the missing zero-address check recommended for the Solidity setters. At minimum, surface a clear execution error (e.g., a new `ActionErrorKind` such as `BeneficiaryAccountDoesNotExist`) prior to detaching the balance from the deleted account, so the deletion — and the loss of funds — cannot proceed silently.

### Proof of Concept
1. Create account `victim.near` with a non-zero balance and a full-access key.
2. Sign and submit a `DeleteAccount { beneficiary_id: "doesnotexist.near" }` action from `victim.near` (directly, or via a meta-transaction as shown in `integration-tests/src/tests/features/delegate_action.rs:577-623` using an arbitrary unregistered `beneficiary_id` instead of `relayer`). [4](#0-3) 
3. The account `victim.near` and its data are deleted (`action_delete_account`), and a `Receipt::new_balance_refund` to `doesnotexist.near` is generated and pushed to `new_receipts`.
4. When that refund receipt executes, `AccountDoesNotExist` is returned and the account is not created, exactly as verified by `refund_may_not_create_universal_account` — the funds are gone, credited to no one. [5](#0-4)

        let key = SecretKey::from_seed(KeyType::ED25519, "refund-target").public_key();

        let (runtime, tries, root, apply_state, _signers, epoch) = setup_runtime(

            .apply(

                &None,

                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);
        store_update.commit();

        // Assert on the reason, not just the absence: without this the test would
        // also pass if the refund receipt were dropped instead of refused.
        let [outcome] = &result.outcomes[..] else {

        );
        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
        assert!(
            get_account(&state, &account_id).unwrap().is_none(),
            "a refund must not bring a `0u` account into existence",
        );
    }
