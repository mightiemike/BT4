### Title
Unchecked out-of-bounds mmap access in `BucketStorage` due to bounds checks compiled out in release builds - (File: `bucket_map/src/bucket_storage.rs`)

### Summary
`BucketStorage::get`, `get_mut`, `get_slice`, `get_slice_mut`, `occupy`, and `free` — the low-level accessors used by the disk-backed bucket map that backs the accounts index — validate the `ix` (cell index) argument only with `debug_assert!`, which compiles to a no-op in release builds. In release, these functions compute a byte offset from `ix` and hand out `unsafe`-constructed slices/pointers into the mmap'd file with no runtime bounds check at all, mirroring the `readMem`/`writeMem` pattern in the reported bug: only a partial validity check (alignment there, `debug_assert` here) is performed before raw memory is accessed.

### Finding Description
`get_start_offset_with_header` computes `(self.cell_size * ix) as usize` and is guarded only by `debug_assert!(ix < self.capacity(), "bad index size")`. [1](#0-0) 

That offset then feeds `get_slice`/`get_slice_mut`, which again only `debug_assert!` that the resulting byte slice is large enough before doing an `unsafe` cast to `*const T`/`*mut T` and calling `slice::from_raw_parts`/`from_raw_parts_mut`: [2](#0-1) 

`get`, `get_mut`, `get_header`, `get_header_mut`, `occupy`, and `free` all funnel through this same unchecked path: [3](#0-2) 

In a `--release` validator build (the only build type used in production), `debug_assert!` is a no-op, so there is no runtime check anywhere in this path that `ix` is within `capacity()`. If any caller in `bucket.rs`/`index_entry.rs` ever computes or receives an `ix`/data offset that is out of range — e.g., through an arithmetic error in the packed `storage_offset`/`capacity_when_created_pow2` bit-packed fields (`PackedStorage`, `MultipleSlots::data_loc`) used to recompute a data-bucket location after a resize — the resulting slice construction reads/writes arbitrary bytes past the mmap'd region, i.e., unvalidated memory access analogous to the reported `readMem`/`writeMem` issue. [4](#0-3) 

### Impact Explanation
The accounts index (`BucketMap`) is on the hot path for every account lookup, insert, and update performed by any validator processing any transaction — this is not a validator/peer/operator-privileged-only code path, it is triggered by ordinary account read/write activity from unprivileged users' transactions. An out-of-bounds mmap read returns garbage bytes interpreted as an `IndexEntry`/slot list, which can silently corrupt the `(slot, storage location)` mapping for an account, potentially causing a stale or wrong-version account load on that node; an out-of-bounds write corrupts the mmap file underlying the bucket, which can propagate corruption into the on-disk/restart index and crash the process (SIGSEGV/SIGBUS) if the access lands outside the mapped pages — a node panic in the accounts index, not merely a debug-only lint concern.

### Likelihood Explanation
Because the only check is `debug_assert!`, this is not defense-in-depth in production — it is the sole safety net during development/testing, and it silently disappears in the actual release binaries validators run. Reachability of a bad `ix` requires a latent arithmetic bug in the offset-recomputation logic (`MultipleSlots::data_loc`, `PackedStorage::offset`) that is only ever exercised in release; there is currently no known concrete trigger, consistent with the source report's own "no known way to exploit it currently, but no guarantee it can't be" characterization that the judge accepted as Medium.

### Recommendation
Replace the `debug_assert!` bounds checks in `get_start_offset_with_header`, `get_slice`, `get_slice_mut`, `occupy`, `free`, and `is_free` with real `assert!`/checked-index logic (or return `Result`/`Option`) so out-of-range `ix` values cannot reach the `unsafe` slice construction in release builds. Additionally, add an explicit bounds check on the computed byte range against `self.mmap.len()` before slicing.

### Proof of Concept
Not directly reproducible without first finding a caller bug that produces an out-of-range `ix`/offset (e.g., via `MultipleSlots::data_loc`'s pow2 shift after a data-bucket resize); however, the following demonstrates that the guard is inert in release builds:
```rust
// bucket_map/src/bucket_storage.rs
pub(crate) fn get_slice<T>(&self, ix: u64, len: u64, header: IncludeHeader) -> &[T] {
    let start = self.get_start_offset(ix, header); // debug_assert!(ix < capacity) -> no-op in release
    let slice = {
        let size = std::mem::size_of::<T>() * len as usize;
        let slice = &self.mmap[start..]; // panics via normal slice indexing only if start > mmap.len()
        debug_assert!(slice.len() >= size); // no-op in release
        &slice[..size] // panics if size > slice.len(), but only via a panic, not before unsafe cast below succeeds with garbage data if size fits
    };
    ...
    unsafe { std::slice::from_raw_parts(ptr, len as usize) }
}
```
Compiling with `cargo build --release` and calling `bucket_storage.get::<IndexEntry<T>>(ix)` with an `ix` at or beyond `capacity()` (but still within the mmap'd region, e.g. capacity computed with page-rounding slack) returns a slice over unrelated/uninitialized bytes with zero runtime validation, silently corrupting the interpreted `IndexEntry`/`MultipleSlots` data.

    pub(crate) fn get_slice<T>(&self, ix: u64, len: u64, header: IncludeHeader) -> &[T] {
        // If the caller is including the header, then `len` *must* be 1
        debug_assert!(
            (header == IncludeHeader::NoHeader) || (header == IncludeHeader::Header && len == 1)
        );
        let start = self.get_start_offset(ix, header);
        let slice = {
            let size = std::mem::size_of::<T>() * len as usize;
            let slice = &self.mmap[start..];
            debug_assert!(slice.len() >= size);
            &slice[..size]
        };
        let ptr = {
            let ptr = slice.as_ptr().cast();
            debug_assert!((ptr as usize).is_multiple_of(std::mem::align_of::<T>()));
            ptr
        };
        unsafe { std::slice::from_raw_parts(ptr, len as usize) }
    }
