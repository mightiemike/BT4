## Finding

The analog of the "unchecked decrement causing underflow" bug in `StakingB_1.sol` exists in java-tron's TVM-reachable resource-weight accounting code.

### Root cause

`DynamicPropertiesStore` guards its total resource-weight adders against underflow with an explicit `max(0, ...)` clamp (only applied when `allowNewReward()` is on) and a no-op fast path for zero amounts: [1](#0-0) 

This is the path used by the regular (non-TVM) `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`, and the code even carries a comment noting this was previously buggy: "adjust total resource, used to be a bug here" in `UnfreezeBalanceProcessor` [2](#0-1) .

However, the equivalent methods on `RepositoryImpl` — which back all TVM native-contract processors (`FreezeBalanceProcessor`, `UnfreezeBalanceProcessor`, `FreezeBalanceV2Processor`, `UnfreezeBalanceV2Processor`, `CancelAllUnfreezeV2Processor`) — perform the same add/subtract but **without any clamp or zero-check**: [3](#0-2) 

These `Repository.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight` calls are invoked directly from smart-contract-triggered native TVM operations, e.g. `unfreezeBalanceV2()` and `withdrawExpireUnfreeze()` in `Program.java`: [4](#0-3) 

and via the processors, e.g. `UnfreezeBalanceV2Processor.updateTotalResourceWeight` / `CancelAllUnfreezeV2Processor.updateFrozenInfoAndTotalResourceWeight`: [5](#0-4) [6](#0-5) 

### Why this matters

Both code paths compute the weight delta as `(newBalance/TRX_PRECISION) - (oldBalance/TRX_PRECISION)`, which is subject to integer-division rounding. Because `RepositoryImpl`'s version is missing the `max(0, ...)` floor that its non-TVM sibling in `DynamicPropertiesStore` was given, repeated freeze/unfreeze/delegate/undelegate/cancel operations issued through a smart contract (any unprivileged account can deploy and call a contract that invokes these TVM opcodes) can drive `TOTAL_NET_WEIGHT`, `TOTAL_ENERGY_WEIGHT`, or `TOTAL_TRON_POWER_WEIGHT` negative over time. These globals are consensus-critical: they are the denominator used network-wide to compute per-account bandwidth/energy limits (`getTotalNetLimit()/getTotalNetWeight()`), so corrupting them to a negative or wildly wrong value is a network-wide resource-accounting/DoS issue reachable purely from broadcast transactions invoking a contract, matching the report's "unprivileged actor decrements a global counter without validating state, causing underflow that breaks the system for everyone" pattern.

### Title
Unchecked/unclamped total resource weight decrement in TVM native-contract processors can underflow global net/energy/TronPower weight - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.addTotalNetWeight`, `addTotalEnergyWeight`, and `addTotalTronPowerWeight` (used exclusively by TVM native-contract freeze/unfreeze/delegate processors) lack the `max(0, …)` underflow guard that the equivalent `DynamicPropertiesStore` methods (used by the plain, non-TVM actuators) already have.

### Finding Description
Chain-wide resource weight totals (`TOTAL_NET_WEIGHT`, `TOTAL_ENERGY_WEIGHT`, `TOTAL_TRON_POWER_WEIGHT`) are maintained via two parallel implementations: one on `DynamicPropertiesStore` (guarded, floor at 0) and one on `RepositoryImpl` (unguarded, can go negative). TVM opcodes such as `unfreezeBalanceV2`, `withdrawExpireUnfreeze`, `cancelAllUnfreezeV2`, `freezeBalanceV2` — all invocable from within any deployed smart contract by any unprivileged account — route their weight adjustments exclusively through the unguarded `RepositoryImpl` path. Rounding from `/TRX_PRECISION` division on repeated small freeze/unfreeze cycles can cause cumulative negative drift that is never clamped back to zero in this path, unlike in the normal actuator path.

### Impact Explanation
`TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT` are used as the divisor for computing every account's bandwidth/energy allotment network-wide. A corrupted (negative or erroneously small) global weight value can distort resource pricing/allocation for the entire network, and in specific arithmetic conditions could produce division anomalies or DoS-like resource starvation for other users — analogous to the reported "amountOfUsers underflow blocks other users" pattern, but at the level of chain-wide resource accounting rather than a single contract's user list.

### Likelihood Explanation
Reachable by any account without special privileges: deploy a contract and repeatedly call `freezeBalanceV2`/`unfreezeBalanceV2`/`cancelAllUnfreezeV2` opcodes to accumulate rounding drift over many transactions. No node-operator or validator privilege is required — only gas/fee cost, which is attacker-controllable and cheap.

### Recommendation
Apply the same underflow protection used in `DynamicPropertiesStore.addTotalNetWeight/addTotalEnergyWeight/addTotalTronPowerWeight` (zero-amount short-circuit plus `max(0, total)` clamp) to `RepositoryImpl`'s corresponding methods, ensuring both code paths behave consistently and neither can drive the global weight counters negative.

### Proof of Concept
1. Deploy a contract that calls `freezeBalanceV2` for a small amount, then repeatedly calls `unfreezeBalanceV2` for slightly different amounts across many transactions, exploiting `/TRX_PRECISION` rounding so that `newWeight - oldWeight` is more negative on unfreeze than positive on the paired freeze.
2. Because `RepositoryImpl.addTotalEnergyWeight`/`addTotalNetWeight` (`actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java:1165-1186`) never floors the result at 0 (unlike `DynamicPropertiesStore`'s guarded twin), repeated execution accumulates negative drift in `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT`.
3. Observe that the network-wide resource weight, read by all other users' bandwidth/energy calculations, is corrupted.

  public boolean unfreezeBalanceV2(DataWord unfreezeBalance, DataWord resourceType) {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner,
        unfreezeBalance.longValue(), null,
        "unfreezeBalanceV2For" + convertResourceToString(resourceType), nonce, null);

    try {
      UnfreezeBalanceV2Param param = new UnfreezeBalanceV2Param();
      param.setOwnerAddress(owner);
      param.setUnfreezeBalance(unfreezeBalance.sValue().longValueExact());
      param.setResourceType(parseResourceCodeV2(resourceType));

      UnfreezeBalanceV2Processor processor = new UnfreezeBalanceV2Processor();
      processor.validate(param, repository);
      long unfreezeExpireBalance = processor.execute(param, repository);
      repository.commit();
      if (unfreezeExpireBalance > 0) {
        increaseNonce();
        addInternalTx(null, owner, owner, unfreezeExpireBalance, null,
            "withdrawExpireUnfreezeWhileUnfreezing", nonce, null);
      }
      return true;
    } catch (ContractValidateException e) {
      logger.warn("TVM UnfreezeBalanceV2: validate failure. Reason: {}", e.getMessage());
    } catch (ArithmeticException e) {
      logger.warn("TVM UnfreezeBalanceV2: balance out of long range.");
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return false;
  }

  public void updateTotalResourceWeight(AccountCapsule accountCapsule,
                                        Common.ResourceCode freezeType,
                                        long unfreezeBalance,
                                        Repository repo) {
    switch (freezeType) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(-unfreezeBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        repo.addTotalNetWeight(newNetWeight - oldNetWeight);
        break;
      case ENERGY:
        long oldEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForEnergyV2(-unfreezeBalance);
        long newEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        repo.addTotalEnergyWeight(newEnergyWeight - oldEnergyWeight);
        break;
      case TRON_POWER:
        long oldTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        accountCapsule.addFrozenForTronPowerV2(-unfreezeBalance);
        long newTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        repo.addTotalTronPowerWeight(newTPWeight - oldTPWeight);
        break;
      default:
        //this should never happen
        break;
