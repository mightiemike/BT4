The reported CVE-2026-58060 bug class is a header field (HSS level count) that is read and used to size an allocation independent of the actual data present, allowing a tiny input to trigger a huge allocation. I searched protobuf-go's wire decoding paths for an analogous pattern.

In protobuf-go's generated coder functions (e.g. `consumeInt32Slice`, `consumeFixed32Slice`, `consumeDoubleSlice` in [1](#0-0) , [2](#0-1) ), every `grow*Slice(count)` pre-allocation is derived from `len(b)` — the actual bytes already consumed via `protowire.ConsumeBytes` — not from an independent, attacker-supplied count field decoupled from the payload size. Since `protowire.ConsumeBytes` itself rejects a length prefix exceeding the remaining buffer [3](#0-2) , any pre-sized allocation is bounded by bytes actually present in the input, unlike the HSS level-count field which is read and used to size structures before the corresponding data is available/validated.

Similarly, `protodelim.UnmarshalOptions.UnmarshalFrom` reads a varint size prefix and explicitly enforces a `MaxSize` bound (default 4 MiB) before calling `make([]byte, size)`, rejecting oversized declared sizes with `SizeTooLargeError` [4](#0-3) . This is the opposite of the reported bug — it's an already-guarded analog, not a vulnerable one.

I found no protobuf-go decode path where a count/level field is used to size an allocation independent of, and unbounded relative to, the actual bytes present in the request.
