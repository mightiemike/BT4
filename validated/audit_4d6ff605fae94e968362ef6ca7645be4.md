### Title
`ensure_match_transaction_info` skips checkpoint-hash verification, letting execution replay/verify tooling accept a diverged state root as valid — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the routine used by the executor's chunk-verification path (`execution/executor/src/chunk_executor/mod.rs::verify_execution`) and by replay/debug tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger`, `aptos-move/cli`) to confirm that a locally re-executed `TransactionOutput` matches the `TransactionInfo` that was actually committed to the ledger (and is bound into the transaction accumulator / ledger-info signature). It checks status, gas, write-set hash (`state_change_hash`), and event root hash, but it never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that authenticate the actual Merkle state root produced by applying the write sets to prior state.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates status, gas, the write-set hash, and the event root hash, but the function's own trailing comment documents that it deliberately skips the state/hot-state/position checkpoint hashes: [2](#0-1) .

This comparator is the sole state-equivalence check used by:
- the chunk executor's execution-verification path used during backup/chunk replay, which iterates re-executed outputs against externally supplied `transaction_infos` and calls this function per transaction [3](#0-2) ;
- `db-tool`'s `replay_on_archive`, which re-executes archived transactions and calls the same comparator to decide whether replay succeeded [4](#0-3) ;
- the Aptos debugger and CLI transaction-replay tooling, which use it to confirm a locally computed output matches the recorded, chain-committed `TransactionInfo` [5](#0-4) [6](#0-5) .

Because `state_checkpoint_hash` (the Sparse Merkle Tree root summarizing the entire world state at a checkpoint boundary) is never compared, a replayed/re-executed output whose write set happens to hash identically (same `state_change_hash`) but which is applied on top of already-diverged prior state — or whose downstream checkpoint materialization diverges for any other reason — will still pass `ensure_match_transaction_info`. The write-set hash only proves the delta is byte-identical; it says nothing about whether applying that delta to the actual persisted state tree reproduces the state root that was cryptographically committed to (and signed over, via the ledger info) in the original chain history. This is precisely the invariant the code comment calls out as unvalidated ("replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution").

### Impact Explanation
This breaks the state-commitment/proof-integrity guarantee for the tools whose entire purpose is to detect ledger state divergence:
- `replay_on_archive` and chunk-executor `verify_execution` are used to validate that re-execution against archived history reproduces the authenticated chain state — this is a primary tool for catching non-determinism bugs, state corruption, or malicious data before they propagate. With the checkpoint hash unchecked, a state root divergence (e.g., corrupted persisted state, a non-deterministic VM behavior affecting some derived/native state root such as the position/hot-state root) is silently reported as "matched," giving false assurance that historical execution is byte-for-byte reproducible when the underlying committed state root is not.
- Downstream, operators/auditors relying on `replay_on_archive` or `verify_execution` success to certify chain integrity (e.g., before promoting a node, or as part of incident investigation) would get a false negative on a real divergence in committed ledger state.

This qualifies under the gate's "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Committed state that differs from the correct VM result ... " categories, since it's a proof/replay-verification gap on the exact fields (`state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) that bind to the authenticated ledger state root.

### Likelihood Explanation
The gap is unconditional and structural — it exists on every call to `ensure_match_transaction_info` regardless of feature flags; the associated TODO explicitly says it should be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying the authors are aware the position/hot-state root path is not yet gated by this check. I was not able to fully confirm, within the remaining tool budget, whether some other independent check (outside `ensure_match_transaction_info`) redundantly validates `state_checkpoint_hash` in the `chunk_executor` or `replay_on_archive` flows (e.g., via a separate ledger-info accumulator-root check against locally recomputed `TransactionInfo`s) — I found no such check via search of `execution/executor/src/chunk_executor/**` for `state_checkpoint_hash`, but this is not certain to be an exhaustive check of all call chains, since `db-tool`/backup-cli flow was not fully traced within the iteration limit. If such a redundant check exists elsewhere in the verify_execution/restore pipeline, it would reduce this to a defense-in-depth/tooling-hygiene issue rather than a hard proof-integrity gap; if no such check exists, the impact stands as described.

### Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` against locally recomputed checkpoint hashes (via `DoStateCheckpoint`/state-checkpoint materialization) whenever those fields are present in the given `TransactionInfo`, mirroring the strict equality checks already applied to `state_change_hash` and `event_root_hash`. This should be done before any feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that depends on the position/hot-state root path is enabled, as the code comment itself flags.

### Proof of Concept
Not directly exploitable as a standalone PoC without a concrete state-divergence trigger (e.g., a hot-state or position-state materialization bug); the demonstrable defect is a code-level proof: construct a `TransactionOutput` whose `write_set` hashes identically to `txn_info.state_change_hash()` and whose events hash to `txn_info.event_root_hash()`, but where the corresponding `state_checkpoint_hash` computed via `DoStateCheckpoint` over the actual persisted state diverges from `txn_info.state_checkpoint_hash()`. Calling `ensure_match_transaction_info` on this pair returns `Ok(())` [7](#0-6) , demonstrating that the routine used by `chunk_executor::verify_execution` and `replay_on_archive::execute_and_verify` [4](#0-3)  cannot detect this class of divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
