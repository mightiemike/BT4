### Title
ERC-20 emulated transfer via the Near Wallet Contract silently converts an attached ETH `value` into extra NEP-141 token amount instead of a native transfer, letting a user's attached NEAR deposit be misappropriated to the token-contract path - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The Near Wallet Contract's Ethereum-transaction emulation layer accepts a single RLP transaction that carries both an ERC-20 `transfer(to, value)` call (encoded in `tx.data`) and a native ETH `value` field. When the calldata is recognized as `ERC20_TRANSFER_SELECTOR`, the code classifies the whole transaction as `EthEmulationKind::ERC20Transfer` and builds a `FunctionCall` action to the token contract, but the `tx.value` (the native NEAR-equivalent deposit the user intended to send) is folded into that same `FunctionCall`'s `deposit` field instead of being routed to the token receiver or refused.

### Finding Description
`parse_rlp_tx_to_action` in [1](#0-0)  dispatches on the parsed `ParsableTransactionKind`. When the calldata matches an ERC-20 selector, `parse_tx_data` delegates to `eth_emulation::try_emulation`, which for `ERC20_TRANSFER_SELECTOR` builds a `FunctionCall` action targeting the NEP-141 token contract with `method_name: "ft_transfer"` and a fixed `yocto_near: 1` [2](#0-1) .

After this classification, `parse_rlp_tx_to_action` unconditionally combines the transaction's native `tx.value` (the ETH-equivalent NEAR amount the signer intended to attach) with the action via `try_into_near_action`: [3](#0-2) 

Inside `try_into_near_action`, for the `FunctionCall` variant, this `additional_value` (derived from `tx.value`) is added directly to the fixed `yocto_near` and becomes the `deposit` sent to the **token contract**, not routed as a native transfer to the intended receiver: [4](#0-3) 

So if a relayer/user submits a signed Ethereum transaction with `to = <ERC-20 token address>`, `data = transfer(receiver, amount)`, and a non-zero `value` field, the wallet contract will attach `value` (converted to yoctoNEAR) as the `deposit` of the `ft_transfer` FunctionCall sent to the **token contract account**, not to the intended token receiver, and not as any accounted native transfer. The emitted `Action` only records `ParsableEthEmulationKind::ERC20Transfer { receiver_id, fee }` — there is no code path that splits off the native value into a separate `Transfer` action to `receiver_id`, unlike the base-token-transfer path (`EOABaseTokenTransfer`) which is handled via a dedicated `Action::Transfer`.

This exactly mirrors the reported OpenQ bug class: a function accepting both a "value" (native protocol token) and a token-address/transfer instruction records/moves only the token amount, while the attached native value is deposited to the wrong place (the token contract, as extra deposit for `ft_transfer`) and is not credited to the user's intended recipient.

### Impact Explanation
The attached native NEAR value (`tx.value`) that the signer intended to send is deposited onto the fungible-token contract account as part of the `ft_transfer` call's `deposit`, rather than being transferred to the intended `receiver_id`. This is unauthorized loss/misdirection of value for the wallet owner: NEAR that the user believed was being sent alongside (or instead of) the token transfer ends up stuck in/absorbed by the token contract's balance instead of reaching the recipient, and the wallet contract has no accounting or refund mechanism for this deposit (it is not tracked via `CallerDeposit`, which is only used for the *predecessor's* attached deposit into `rlp_execute`, not for the emulated `tx.value`). This is a concrete unauthorized value movement / permanently misdirected funds bug reachable purely by an unprivileged signer/relayer submitting a single RLP transaction to `rlp_execute`.

### Likelihood Explanation
Likelihood is high given reachability: any holder of an eth-implicit account (Wallet Contract) can construct such a transaction themselves, or any relayer forwarding a user's raw signed transaction can trigger this by simply setting a non-zero `value` alongside ERC-20 `transfer` calldata — no special privilege, validator collusion, or malicious node is required. It only requires a single `rlp_execute` call. The chance of accidental triggering by a legitimate wallet/tooling that naively sets both an ETH `value` and calldata (a common pattern from ordinary Ethereum tooling misuse) is realistic since Ethereum tooling frequently defaults `value` to zero explicitly, but some poorly configured wallets/scripts could set non-zero values by mistake, and a malicious relayer can trivially craft such a transaction to strand user funds without being classified as "faulty" (since the relayer-fault checks in `validate_tx_relayer_data` do not cover this case).

### Recommendation
When the parsed transaction kind is `EthEmulationKind::ERC20Transfer`, reject (or separately account for) a non-zero `tx.value`. Concretely, in `internal.rs::parse_rlp_tx_to_action`, before combining `tx.value` into the action via `try_into_near_action`, check whether `transaction_kind` is `TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { .. })` and if `tx.value` is non-zero, either:
- return `Error::User(UserError::...)` rejecting the transaction (mirroring the strict OpenQ-fix `require(msg.value == 0)`), or
- construct an additional native `Action::Transfer` to `receiver_id` for the `tx.value` portion, executed alongside the `ft_transfer`, so the native and token amounts are both correctly delivered to the intended receiver.

### Proof of Concept
1. Deploy/own an eth-implicit Wallet Contract account and mint some NEP-141 tokens to it (as in `test_erc20_emulation`, [5](#0-4) ).
2. Craft an RLP-encoded Ethereum transaction with `to = <token_contract_address>`, `value = X` (non-zero, e.g. `Wei::new_u128(...)`), and `data = ERC20_TRANSFER_SELECTOR ++ abi.encode(other_address, transfer_amount)` — similar to the existing test transaction but with `value` set to something other than `Wei::zero()` (compare to the always-zero `value: Wei::zero()` used in `test_erc20_emulation`, [6](#0-5) ).
3. Sign and submit via `wallet_contract.rlp_execute(token_contract_id, &signed_transaction)`.
4. Observe that `ft_transfer` succeeds and moves `transfer_amount` tokens, but `X` yoctoNEAR (converted via `MAX_YOCTO_NEAR` in `try_into_near_action`, [4](#0-3) ) is deposited as `deposit` on the `FunctionCall` to the token contract account, never reaching `other_address`/`receiver_id` and not returned to the wallet owner — the native value is misdirected/lost from the user's perspective.
