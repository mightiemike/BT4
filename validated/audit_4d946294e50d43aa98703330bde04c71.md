### Title
Stale per-block index cache in `market.clar` lets liquidation bad-debt socialization desynchronize debt/collateral pricing within the same block - (File: `local-testing/contracts/market/market.clar`)

### Summary
`market.clar` caches each vault's `{index, lindex}` in `index-cache- { timestamp, aid }`, populated once per block via `accrue-and-cache` [1](#0-0) . The cache is intentionally reused for the whole block ("Cache Invalidation... automatically invalidated each block" per `stacks-block-time`) [2](#0-1) . However, `socialize-debt` on the vault mutates `lindex` and `principal-scaled` directly, bypassing `accrue`/`accrue-and-cache` entirely [3](#0-2) . If `socialize-debt` runs in a transaction earlier in a block (e.g., triggered by `liquidate`'s bad-debt path), a *later* transaction in the same block that calls `accrue-and-cache` for that asset will hit the cache and reuse the pre-socialization `lindex`, since the cache key only depends on `{timestamp, aid}` and was already populated earlier in the block.

### Finding Description
1. Value bound: `index-cache- { timestamp: stacks-block-time, aid }` → `{index, lindex}`, populated in tx-1 of a block by `accrue-and-cache` calling the vault's public `accrue` [4](#0-3) [1](#0-0) .
2. Event that invalidates the source: a liquidation triggers `vault-socialize-debt`, which the market calls after `liquidate` detects bad debt, and which writes `lindex`/`principal-scaled` directly on the vault, without calling `accrue` or updating the market's cache [5](#0-4) [6](#0-5) .
3. Later use: a subsequent transaction in the same block (same `stacks-block-time`) calling `borrow`, `repay`, `collateral-remove`, etc. calls `accrue-and-cache asset-id` again; since the map already has an entry for `{timestamp, aid}`, it returns the **cached, now-stale** `lindex` instead of the post-socialization value [7](#0-6) . This stale `lindex` is then used to price ztoken collateral via `resolve-ztoken` [8](#0-7) , and health/notional calculations in `get-notional-evaluation`/`calculate-asset-notional-value` [9](#0-8) .
4. Interleaving under Clarity evaluation order: map state written by `map-set index-cache- ...` in one confirmed transaction persists on-chain and is read by `map-get?` in any later transaction of the same block sharing the identical `stacks-block-time` — this is exactly the intended, documented cross-transaction reuse behavior of the cache, not a hypothetical.

### Impact Explanation
Because `socialize-debt` writes down `lindex` to reflect a shortfall (bad debt write-off) that occurred during liquidation, the stale cached (pre-write-down) `lindex` used by later same-block transactions overstates the ztoken collateral's true value. A user (or the same liquidator/attacker orchestrating both transactions) can exploit this window to borrow against overstated zToken collateral, or to avoid liquidation on a position that should be unhealthy post-write-down, before the block-boundary cache reset occurs. This falls under **temporary freezing of funds / mispriced collateral leading to under-collateralized borrowing**, and since a bad-debt event has already reduced the liquidity index for real depositors, extracting extra borrow capacity against the stale higher value effectively extracts more value than backed by real collateral — a form of protocol insolvency risk for the affected vault.

### Likelihood Explanation
Requires: (a) a liquidation that triggers bad-debt socialization for a ztoken-backed vault, and (b) a follow-up transaction (can be same actor, same block, ordered after) that exercises `borrow`/`collateral-add`/`collateral-remove` for a position holding that ztoken as collateral, before the block ends. This is achievable by an attacker submitting both transactions themselves in the same block (e.g., self-triggering a liquidation of a secondary account, then immediately borrowing against a primary account's zToken collateral in the same block), making it realistically triggerable rather than purely theoretical.

### Recommendation
Invalidate/refresh the market's `index-cache-` entry whenever `socialize-debt` (or any other vault-state mutation outside `accrue`) changes `lindex`/`index`, e.g., by having `market-vault`/`market.clar` explicitly clear or overwrite the cached entry for that `{timestamp, aid}` immediately after calling `vault-socialize-debt`, or by having the cache read live vault state on socialize-debt paths instead of trusting the per-timestamp cache unconditionally.

### Proof of Concept
1. Attacker/user A holds zAsset (e.g., zsBTC) as collateral in Market and borrows near max LTV via `borrow` — no PoC transaction needed yet.
2. In the same block, attacker's account B has an unhealthy debt position that triggers `liquidate` with bad-debt: `liquidate` detects `fresh-debt-list` still non-zero post-seizure and calls the socialization fold, invoking `vault-socialize-debt` on the sBTC vault, which writes down `lindex` [10](#0-9) [11](#0-10) . This transaction lands first in the block and populates/uses `index-cache-` for sBTC before write-down, or does not touch the market's cache at all (since socialize-debt is vault-side only) — the market cache for sBTC's `{timestamp, aid}`, if already populated by an earlier same-block call, still holds the pre-write-down `lindex`.
3. Later in the same block, attacker calls `market.borrow` or `market.collateral-add` using the zsBTC collateral; `accrue-and-cache` for sBTC hits the cache (since the entry for that block's timestamp already exists) and returns the stale, higher `lindex`, causing zsBTC collateral to be overvalued in `resolve-ztoken`/`get-notional-evaluation`, letting the attacker borrow more than the post-write-down collateral value actually supports.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
