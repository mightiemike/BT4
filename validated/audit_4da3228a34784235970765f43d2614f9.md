### Title
Vault-level `repay` pause blocks `liquidate()` because market's `liquidate` routes debt settlement through the same paused vault call - (File: mainnet/contracts/vault/v0-vault-usdc.clar, mainnet/contracts/market/v0-4-market.clar)

### Summary
The vault contracts expose a DAO-controlled `set-pause-states` function that can independently pause `deposit`, `redeem`, `borrow`, `repay`, `accrue`, and `flashloan` operations. The `repay` flag is checked inside the vault's `system-repay` function. Both the market's user-facing `repay()` and its `liquidate()` function funnel debt settlement through this same `vault-system-repay` → vault `system-repay` call path, so pausing vault-level `repay` (e.g., during an incident affecting deposits/borrows for that asset) also disables all liquidations denominated in that debt asset.

### Finding Description
The vault's pause switch is granular per-operation via a single struct: [1](#0-0) 

The `repay` flag guard is enforced unconditionally inside `system-repay`, with no distinction between a plain user repayment and a repayment issued as part of a liquidation: [2](#0-1) 

The market's `repay()` function calls `vault-system-repay`, which resolves to this same vault entrypoint: [3](#0-2) 

Critically, `liquidate()` also calls `vault-system-repay` to settle the borrower's debt as part of the liquidation flow: [4](#0-3) 

The market also implements its own dedicated liquidation pause (`is-liquidation-paused`, driven by `pause-liquidation` and grace periods) which is intentionally separate and scoped only to liquidation: [5](#0-4) [6](#0-5) 

However, this market-level liquidation pause is orthogonal to the vault-level `repay` pause. If the DAO pauses `repay` at the vault layer (for example to stop ordinary users from repaying an asset that is being deprecated, migrated, or is under investigation) while leaving `pause-liquidation` at the market layer `false`, `liquidate()` will still unconditionally attempt `vault-system-repay`, hit the vault's `(asserts! (not (get repay states)) ERR-PAUSED)`, and abort — exactly the bug class described in the external report: a pause intended for normal user operations inadvertently blocks liquidation, which is the one operation that should remain available to reduce risk during a pause/incident.

### Impact Explanation
While the vault `repay` pause is active for a given asset, no borrower whose debt is denominated in that asset can be liquidated, regardless of how unhealthy their position becomes. This is a temporary freezing of the ability to unwind risky positions: undercollateralized debt can accumulate bad debt during the pause window, and if collateral prices continue to fall, the eventual loss (socialized via `socialize-debt`/bad-debt handling) can exceed what timely liquidation would have captured — directly harming lenders' claims on the vault's `assets`. This lands on temporary freezing of funds, with downside risk toward protocol insolvency if the pause persists during a market stress event.

### Likelihood Explanation
Likelihood is Medium. It requires only a single legitimate DAO administrative action — calling `set-pause-states` with `repay: true` on a vault — which is a normal, documented control lever (not a compromise or misconfiguration of the egroup/asset registry) and is plausible during any operational incident involving that asset. There is no attacker required; the interaction is a pure code-path coupling between the market's `liquidate()` and the vault's `repay` pause flag.

### Recommendation
Decouple debt settlement performed during liquidation from the vault's user-facing `repay` pause. Options:
- Add a distinct internal/system repay path (or parameter) in the vault that liquidation calls, which is not gated by the `repay` pause flag, mirroring how `is-liquidation-paused` is already a distinct, intentional gate at the market layer.
- Alternatively, have `vault-system-repay` accept a `is-liquidation` flag and skip the `(get repay states)` check when the call originates from `liquidate()`, while still respecting `is-liquidation-paused` at the market layer as the sole gate for halting liquidations.

### Proof of Concept
1. DAO calls `set-pause-states` on the relevant debt-asset vault (e.g., `v0-vault-usdc.clar`) with `{ ... repay: true ... }`. [1](#0-0) 
2. Market's `pause-liquidation` remains `false` and no grace period is active, so `is-liquidation-paused` returns `false` for that asset. [5](#0-4) 
3. A borrower's position with debt in the paused asset becomes unhealthy (`current-ltv >= ltv-liq-partial`).
4. A liquidator calls `liquidate()`. Execution passes the market-level health/liquidation-pause checks and reaches `(try! (vault-system-repay debt-aid debt-to-repay debt-ft debt-address))`. [4](#0-3) 
5. Inside the vault, `system-repay` hits `(asserts! (not (get repay states)) ERR-PAUSED)` and the entire `liquidate()` transaction reverts with `ERR-PAUSED`, even though the market never intended to block liquidations. [7](#0-6) 
6. The unhealthy position remains open and un-liquidatable for the duration of the vault `repay` pause, regardless of further collateral price deterioration.
