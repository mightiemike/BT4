### Title
Unauthenticated quadratic-time DoS via duplicate query keys in `normalizeQuery` before HMAC verification - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
`normalizeQuery` in `hmac-validator.ts` builds up combined values for repeated `URLSearchParams` keys using naive string concatenation (`normalizedQuery[key] = \`${existingValue},${value}\``) in a loop, executed on every call to `validateHmac` before any HMAC/signature check occurs. An unauthenticated attacker can send thousands of duplicate non-reserved query keys with large values to `/auth/callback` or an app-proxy route to force expensive, superlinear string-building work in a pre-authentication code path.

### Finding Description
`validateHmac` calls `normalizeQuery(query, signator)` as its very first step, prior to checking for `hmac`/`signature` presence, prior to `validateHmacTimestamp`, and prior to any secret-based comparison: [1](#0-0) 

When the input is a `URLSearchParams` instance (which is exactly what both the OAuth callback path and the app-proxy authenticate path pass in), `normalizeQuery` iterates every `[key, value]` entry and, for keys other than the small `APP_PROXY_SINGLE_VALUE_PARAMS` set (`hmac`, `shop`, `signature`, `timestamp`), concatenates repeated values with `,`: [2](#0-1) 

Because JS strings are immutable, `normalizedQuery[key] = \`${existingValue},${value}\`` reallocates and copies the entire accumulated string on every repeated occurrence of the same key. For `k` duplicate entries of a given key each of size `s`, this produces O(k² · s) total work/memory churn, entirely before any signature is verified and with no secret required.

This is reachable unauthenticated:
- OAuth callback: `validQuery` in `oauth.ts` calls `validateHmac(config)(query)` directly on the callback query before the state/nonce comparison happens: [3](#0-2) 
- App Proxy: `validateAppProxyHmac` in the remix/react-router adapters constructs a `URLSearchParams` directly from the incoming request URL and passes it straight to `api.utils.validateHmac`: [4](#0-3) 

No app secret, cookie, or prior authentication is needed to reach this code — an attacker can hit these public endpoints directly with a crafted query string containing many repeated non-reserved keys (e.g. `custom`).

### Impact Explanation
This is a CPU/memory amplification DoS in an authentication-adjacent handler (`validateHmac`), reachable pre-authentication on both the OAuth callback route and the App Proxy route. A single crafted request with tens of thousands of duplicate keys and large values can consume disproportionate CPU/memory on the app server, degrading or blocking legitimate OAuth/app-proxy traffic — matching Shopify's "Denial of Service in an authentication flow" impact class. It does not lead to signature forgery or credential/token compromise; the impact is scoped to availability of the validation path.

### Likelihood Explanation
- No privileges, secrets, or non-default configuration required.
- Both `/auth/callback` and app-proxy endpoints are public by design and pass raw, attacker-controlled `URLSearchParams` into `validateHmac`.
- The attack is trivially repeatable: any anonymous HTTP client can send an arbitrarily large query string (subject only to the HTTP server/framework's own query-string/URL length limits, which are outside this library's control and not guaranteed to be restrictive).
- Feasibility scales with how permissive the surrounding HTTP stack is about URL/query length; where large query strings are accepted, the quadratic cost is directly attacker-controlled.

### Recommendation
- Bound the number of accepted query parameters/entries (and/or total query length) before calling `normalizeQuery`, rejecting requests that exceed a small sane limit (e.g. tens of params) with a 400 rather than processing them.
- Replace the per-key string concatenation with an array-accumulation strategy (push values into an array keyed by parameter name, `join(',')` once at the end) to make the cost linear rather than quadratic in the number of duplicates per key.
- Consider moving the size/param-count guard earlier, ahead of `normalizeQuery`, so pathological inputs are rejected before any processing.

```ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('duplicate-key URLSearchParams cause superlinear normalizeQuery cost', async () => {
  const shopify = shopifyApi(testConfig({apiSecretKey: 'secret'}));

  const bigValue = 'A'.repeat(1024); // 1KB
  const params = new URLSearchParams();
  params.set('shop', 'shop.myshopify.com');
  params.set('timestamp', String(Math.trunc(Date.now() / 1000)));
  params.set('signature', 'unused');

  for (let i = 0; i < 50000; i++) {
    params.append('custom', bigValue); // not in APP_PROXY_SINGLE_VALUE_PARAMS
  }

  const start = Date.now();
  await shopify.utils.validateHmac(params, {signator: 'appProxy'});
  const elapsed = Date.now() - start;

  // Demonstrates disproportionate cost growth relative to input size (~50MB nominal payload)
  console.log(`elapsed: ${elapsed}ms`);
  expect(elapsed).toBeGreaterThan(0); // replace with perf assertion / profiling in practice
});
```
Run this alongside a smaller variant (e.g. 5,000 duplicates) to observe non-linear (roughly quadratic) growth in wall-clock time as the duplicate count increases, confirming the cost is incurred inside `normalizeQuery` prior to any HMAC/signature verification.
