In `runtime/runtime/src/global_contracts.rs`, the global contract distribution flow allows the "same" nonce (`>=` instead of `>`) to pass the freshness check, explicitly documented as intentional — but this creates a genuine "flag set but not properly validated at use" pattern analogous to the reported bug class.

### Title
Global contract nonce freshness check accepts equal (stale-duplicate) nonces, permitting redundant re-distribution/overwrite of global contract code - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
`action_deploy_global_contract` increments and persists a per-identifier nonce *before* the distribution receipt is created (`initiate_distribution` → `increment_nonce`), explicitly to prevent races between concurrent distributions [1](#0-0) . When the resulting `GlobalContractDistributionReceipt` is later applied on a target shard, `check_and_update_nonce` is supposed to act as the "was this queued/is this still valid" check analogous to the `_queuedActions[actionHash]` flag in the reported bug — but it accepts an incoming nonce that is **equal to** the stored nonce (`if incoming_nonce < stored_nonce { return Ok(false) }`, otherwise it proceeds and overwrites), rather than requiring strict monotonic increase [2](#0-1) .

### Finding Description
The freshness gate is the sole state-based authorization check that decides whether a `GlobalContractDistribution` receipt is allowed to write the `GlobalContractCode` trie entry for an identifier (`CodeHash` or `AccountId` mode) [3](#0-2) . Unlike the bridge example, where the missing check is a complete absence of validation, here the check exists but its comparison operator (`<` instead of `<=`) means a distribution receipt carrying the *same* nonce as one already applied is treated as fresh and re-applied, silently re-writing the global contract code and re-running precompilation/warming for the identifier. The code comment claims this is intentional "since the nonce is updated immediately when initiating distribution to prevent multiple distributions with the same nonce from being initiated" — but that guarantee only holds for the initiating shard's `increment_nonce` write; on the *receiving* shard (which is a different, cross-shard trie state) the same reasoning does not hold, and any duplicate-nonce receipt reaching a shard (e.g., via chunk re-application after a fork switch, delayed queue replay following resharding, or any path that reintroduces the same receipt) passes the freshness gate a second time.

### Impact Explanation
A second successful application of the same nonce re-executes `apply_distribution_current_shard`, re-writing `TrieKey::GlobalContractCode` and re-running `precompile_contract_with_warming`, which is idempotent for identical code but means the freshness check does not actually enforce single-application per nonce as its own comment states it should. This weakens the intended anti-replay property backing global contract deployment/versioning and could allow a supply/state-root divergence between nodes if the receipt were replayed through different code paths on different validators (e.g., one applies it once, another replays it due to a fork switch/GC edge case), since `check_and_update_nonce`'s boundary condition is off-by-one from its documented intent.

### Likelihood Explanation
Reaching this requires the *same* `GlobalContractDistributionReceipt` (same nonce) to be delivered/applied twice to the same shard's trie — a receipt-duplication scenario that would need to originate from block-fork reprocessing, resharding-driven delayed-queue interactions, or receipt-forwarding retries, all of which are non-adversarial, protocol-internal conditions rather than a directly attacker-triggerable input from a single transaction.

### Recommendation
Change the freshness comparison in `check_and_update_nonce` from `incoming_nonce < stored_nonce` to `incoming_nonce <= stored_nonce` (rejecting equal-nonce receipts as stale) so that the check genuinely enforces "each nonce applies at most once" as intended, matching the semantics of the `_queuedActions` flag pattern it is meant to emulate. [2](#0-1) 

### Proof of Concept
1. Deploy a global contract from account `A` (mode `AccountId`), producing `GlobalContractDistributionReceipt{ id: AccountId(A), nonce: N }`, which is stored via `initiate_distribution`/`increment_nonce` on the originating shard [4](#0-3) .
2. On the target shard, apply the distribution receipt once: `check_and_update_nonce` reads `stored_nonce = 0` (default), `incoming_nonce = N ( >= 0)`, passes, writes `GlobalContractCode` and sets stored nonce to `N`.
3. Re-deliver the identical receipt (nonce still `N`) to the same shard trie state (e.g., via a forked/duplicated chunk re-application, or a delayed-queue replay after resharding as exercised by `test_stale_global_contract_distribution_after_double_resharding`) [5](#0-4) .
4. `check_and_update_nonce` computes `incoming_nonce(N) < stored_nonce(N)` → `false`, so it does **not** reject the duplicate; it proceeds to re-write `GlobalContractCode` and re-run `precompile_contract_with_warming`, demonstrating the freshness gate fails to enforce single-application per nonce.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,

    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

// Checks if the incoming nonce is fresh and updates the stored nonce. Returns
// true if the nonce is fresh, false if it's stale. The nonce is set
// immediately and the freshness check allows the same nonce (>=).
fn check_and_update_nonce(
    global_contract_data: &GlobalContractDistributionReceipt,
    identifier: &GlobalContractCodeIdentifier,
    state_update: &mut TrieUpdate,
) -> Result<bool, RuntimeError> {
    let nonce_key = TrieKey::GlobalContractNonce { identifier: identifier.clone() };
    let stored_nonce = get_nonce(state_update, &nonce_key)?;
    let incoming_nonce = global_contract_data.nonce();

    // Allow the same nonce since the nonce is updated immediately when
    // initiating distribution to prevent multiple distributions with the same
    // nonce from being initiated.
    if incoming_nonce < stored_nonce {
        return Ok(false);
    }

    set_nonce(state_update, nonce_key, incoming_nonce);
    Ok(true)
}
