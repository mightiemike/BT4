### Title
Silent uint32 overflow in `protolazy.BufferReader.DecodeVarint32` causes lazy-field index desync/misattribution - (File: internal/protolazy/bufferreader.go)

### Summary
`internal/protolazy/bufferreader.go`'s `DecodeVarint32` decodes a 5-byte varint into a `uint32` accumulator, but the final shift (`(v & 127) << 28`) silently wraps modulo 2^32 with no overflow check, unlike the correct 64-bit `ConsumeVarint`/`DecodeVarint` used elsewhere. [1](#0-0)  This function is the length parser used by `buildIndex` when scanning `BytesType` (length-delimited) fields to build the lazy-field offset index. [2](#0-1)  A crafted 5-byte length varint whose true value is a multiple of 2^32 decodes as `0` (or another wrapped value) with no error, causing `buildIndex` to end a field's byte range prematurely and reinterpret the field's genuine payload bytes as the start of a new, unrelated tag/field — a boundary desync in the same class as the Netty chunk-size int-overflow smuggling bug.

### Finding Description
Lazy unmarshaling is enabled by default (`enableLazy` starts at `1` unless `GOPROTODEBUG=nolazy` is set) [3](#0-2) , so eligible message fields are decoded lazily on first access via `MessageInfo.lazyUnmarshal`, which calls `XXX_lazyUnmarshalInfo.FindFieldInProto` to look up a field's byte range from an index built by `buildIndex`. [4](#0-3) [5](#0-4) 

`buildIndex` walks the raw sub-message bytes tag-by-tag, and for `BytesType` fields it computes the field length with `r.DecodeVarint32()` then skips that many bytes: `n, err = r.DecodeVarint32(); if err == nil { err = r.Skip(int(n)) }`. [6](#0-5) 

`DecodeVarint32` accumulates into a 32-bit `x`/`v`; for the 5th input byte it executes `x |= (v & 127) << 28` with no check that the true (unsigned 64-bit) value fits in 32 bits — Go silently truncates the shift result modulo 2^32, and the function returns success (`nil` error) as long as the 5th byte has its continuation bit clear. [7](#0-6)  This is the exact "chunk size silently overflows int" pattern from the Netty report, but applied to protobuf-go's length-delimited field length instead of an HTTP chunk size. Note that the general 64-bit `ConsumeVarint`/`DecodeVarint` paths correctly detect this same class of overflow and return `errOverflow`. [8](#0-7) [9](#0-8) 

Because the outer message boundary that gates entry into `buildIndex` is parsed correctly by the eager 64-bit path (`protowire.ConsumeBytes`), the attacker only needs to embed the crafted 5-byte length varint *inside* a lazily-decoded sub-message's bytes — no 4 GB of actual data need be sent. The wrapped, too-small length value causes `buildIndex` to close the "field" at the wrong offset, so the remaining bytes that are semantically the field's own payload get reinterpreted by the index builder as an independent tag/field entry, corrupting the `Start`/`End` offsets recorded for that and all subsequent fields in the index. `FindFieldInProto`/`lookupField` and `AppendField` then hand out these mis-aligned byte ranges to `mi.unmarshalField`, which unmarshals whatever field number was assigned that byte range. [10](#0-9) [11](#0-10) 

### Impact Explanation
This produces a within-message parser desync: data an attacker intended to be interpreted (or that a correct 64-bit decoder would interpret) as belonging to one field/byte-range gets attributed by the lazy index to a different field number/boundary than intended, and vice versa. Downstream code relying on `lazy.SizeField`/`AppendField`/lazy field access (e.g. selective re-serialization, extension/unknown-field preservation, or per-field access APIs) can therefore read or re-emit bytes under the wrong field identity — an integrity issue on data attribution within a message, analogous to the confidentiality/integrity impact rated in the Netty CVE (I: Low, A: Low). No memory-safety violation was found (bounds are still enforced by `Skip`'s `len(b.Buf) < b.Pos+n` check on 64-bit platforms), so the practical impact is limited to field-boundary/desync corruption rather than out-of-bounds memory access.

### Likelihood Explanation
Lazy unmarshaling is on by default for any process using protobuf-go without explicitly disabling it via `GOPROTODEBUG=nolazy`. [12](#0-11)  The vulnerable code path (`buildIndex` → `DecodeVarint32`) runs automatically whenever an untrusted, attacker-supplied message containing an eligible lazily-decoded field is unmarshaled and any field of that sub-message is subsequently accessed — a normal, unprivileged decode-and-read flow, requiring only a specially crafted 5-byte length varint, not a multi-gigabyte payload.

### Recommendation
Make `DecodeVarint32` reject values that don't fit in 32 bits (mirror the overflow detection already present in `DecodeVarint`/`ConsumeVarint`), e.g. by accumulating in `uint64` and checking `x > math.MaxUint32` before returning, or by explicitly checking the high bits of the 5th byte's contribution before OR-ing them into `x`.

### Proof of Concept
Within the raw bytes of a lazily-decoded sub-message (bytes handed to `buildIndex`), place a length-delimited field whose length varint is the 5-byte sequence:

```
tag_byte              // field N, wire type 2 (BytesType)
0x80 0x80 0x80 0x80 0x10   // varint that == 2^32 in 64-bit decoding, but DecodeVarint32 returns 0
<attacker-controlled bytes B...>  // intended to be a NEW field/tag under correct 64-bit parsing,
                                   // but buildIndex now (incorrectly) closes field N's range
                                   // immediately after the length bytes (End == Start), leaving
                                   // bytes B to be scanned as an unrelated new tag/field entry
```

Trace: `buildIndex`'s `BytesType` case calls `r.DecodeVarint32()` [13](#0-12) , which for input `80 80 80 80 10` computes `x = 0` (each of the first four bytes contributes 0, and `16<<28` wraps to `0` in 32-bit arithmetic) and returns `(0, nil)` — no error — where the true 64-bit value would be `4294967296`. [14](#0-13)  `Skip(0)` then advances `Pos` by zero bytes past the length field, so `buildIndex` records field N's `End` right after the length varint and immediately begins parsing bytes `B...` as the next tag, producing an index entry set that disagrees with what a correct 64-bit-aware parser of the same bytes would produce (which would instead treat `B...` as truncated payload of field N and fail/consume it as part of N, not as new fields).

// decodeVarint32 decodes a varint32 at the current position
func (b *BufferReader) DecodeVarint32() (x uint32, err error) {
	i := b.Pos
	buf := b.Buf

	if i >= len(buf) {
		return 0, io.ErrUnexpectedEOF
	} else if buf[i] < 0x80 {
		b.Pos++
		return uint32(buf[i]), nil
	} else if len(buf)-i < 5 {
		v, err := b.DecodeVarintSlow()
		return uint32(v), err
	}

	var v uint32
	// we already checked the first byte
	x = uint32(buf[i]) & 127
	i++

	v = uint32(buf[i])
	i++
	x |= (v & 127) << 7
	if v < 128 {
		goto done
	}

	v = uint32(buf[i])
	i++
	x |= (v & 127) << 14
	if v < 128 {
		goto done
	}

	v = uint32(buf[i])
	i++
	x |= (v & 127) << 21
	if v < 128 {
		goto done
	}

	v = uint32(buf[i])
	i++
	x |= (v & 127) << 28
	if v < 128 {
		goto done
	}

	return 0, errOverflow

done:
	b.Pos = i
	return
}

// FindFieldInProto looks for field fieldNum in lazyUnmarshalInfo information
// (including protobuf), returns startOffset/endOffset/found.
func (lazy *XXX_lazyUnmarshalInfo) FindFieldInProto(fieldNum uint32) (start, end uint32, found, multipleContiguous bool, multipleEntries []IndexEntry) {
	if lazy.Protobuf == nil {
		// There is no backing protobuf for this message -- it was made from a builder
		return 0, 0, false, false, nil
	}
	index := atomicLoadIndex(&lazy.index)
	if index == nil {
		r, err := buildIndex(lazy.Protobuf)
		if err != nil {
			panic(fmt.Sprintf("findFieldInfo: error building index when looking for field %d: %v", fieldNum, err))
		}
		// lazy.index is a pointer to the slice returned by BuildIndex
		index = &r
		atomicStoreIndex(&lazy.index, index)
	}
	return lookupField(index, fieldNum)
}

// EnableLazyUnmarshal enables lazy unmarshaling.
func EnableLazyUnmarshal(enable bool) {
	if enable {
		atomic.StoreInt32(&enableLazy, 1)
		return
	}
	atomic.StoreInt32(&enableLazy, 0)
}

// LazyEnabled reports whether lazy unmarshalling is currently enabled.
func LazyEnabled() bool {
	return atomic.LoadInt32(&enableLazy) != 0
}

func (mi *MessageInfo) lazyUnmarshal(p pointer, num protoreflect.FieldNumber) {
	var f *coderFieldInfo
	if int(num) < len(mi.denseCoderFields) {
		f = mi.denseCoderFields[num]
	} else {
		f = mi.coderFields[num]
	}
	if f == nil {
		panic(fmt.Sprintf("lazyUnmarshal: field info for %v.%v", mi.Desc.FullName(), num))
	}
	lazy := *p.Apply(mi.lazyOffset).LazyInfoPtr()
	start, end, found, _, multipleEntries := lazy.FindFieldInProto(uint32(num))
	if !found && multipleEntries == nil {
		panic(fmt.Sprintf("lazyUnmarshal: can't find field data for %v.%v", mi.Desc.FullName(), num))
	}
	// The actual pointer in the message can not be set until the whole struct is filled in, otherwise we will have races.
	// Create another pointer and set it atomically, if we won the race and the pointer in the original message is still nil.
	fp := pointerOfValue(reflect.New(f.ft))
	if multipleEntries != nil {
		for _, entry := range multipleEntries {
			mi.unmarshalField(lazy.Buffer()[entry.Start:entry.End], fp, f, lazy, lazy.UnmarshalFlags())
		}
	} else {
		mi.unmarshalField(lazy.Buffer()[start:end], fp, f, lazy, lazy.UnmarshalFlags())
	}
	p.Apply(f.offset).AtomicSetPointerIfNil(fp.Elem())
}
