## Finding

### Title
`DbStateView::get` silently skips state-proof verification when the proof lookup errors, breaking the binding between "verified" state reads and the authenticated state root - ([File: storage/storage-interface/src/state_store/state_view/db_state_view.rs])

### Summary
`VerifiedStateViewAtVersion::verified_state_view_at_version` constructs a `DbStateView` that is supposed to bind every state read at a given version to a Merkle-proof-authenticated `state_root_hash` (obtained after verifying the `TransactionInfoWithProof`/`LedgerInfo` chain). [1](#0-0) 

However, the actual read path, `DbStateView::get`, only performs the proof check inside an `if let Ok(...)` guard, and unconditionally returns the value fetched by a second, independent, unverified DB call regardless of whether the proof check ran or succeeded: [2](#0-1) 

### Finding Description
This is a direct analog of the Chainlink bug class: a data-integrity check exists in the code, but a failure/edge-case path silently bypasses it and the caller still consumes the (unverified) data as if it had been authenticated.

Concretely, in `get()`:
```rust
if let Some(root_hash) = self.maybe_verify_against_state_root_hash {
    if let Ok((value, proof)) =
        self.db.get_state_value_with_proof_by_version(key, version)
    {
        proof.verify(root_hash, *key.crypto_hash_ref(), value.as_ref())?;
    }
}
Ok(self.db.get_state_value_with_version_by_version(key, version)?)
```
Two failure modes break the state-proof binding invariant:
1. **Silent skip on error**: if `get_state_value_with_proof_by_version` returns `Err` (e.g., due to a storage error, missing sharded proof data, race with pruning, or any other transient/DB inconsistency), the `if let Ok(...)` simply does not execute the `proof.verify(...)` call, and no error propagates. Execution falls straight through to the unconditional return, handing back a state value that was never checked against `root_hash` at all.
2. **Verified value ≠ returned value**: even when the `Ok` branch is taken, `proof.verify(...)` is checked against `value` obtained from `get_state_value_with_proof_by_version`, but the value actually handed back to the caller comes from a second, separate query, `get_state_value_with_version_by_version`. There is no assertion that the two reads agree, so the function's implicit contract - "return a value that has been checked against `root_hash`" - is not actually enforced by the code; it only holds if the two independent storage calls happen to be consistent.

`verified_state_view_at_version` is documented/used specifically for `StateViewId::TransactionValidation`, i.e., contexts that are supposed to give VM callers state reads authenticated against a specific `LedgerInfo`-approved root hash, distinguishing this from the unauthenticated `state_view_at_version`/`latest_state_checkpoint_view` paths that explicitly pass `maybe_verify_against_state_root_hash: None`. [3](#0-2) [4](#0-3) 

### Impact Explanation
A consumer of `verified_state_view_at_version` believes every read it performs has been checked against an authenticated `state_checkpoint_hash` rooted in a validator-signed `LedgerInfo`. Because the verification is best-effort (swallowed on `Err`) and decoupled from the value that is actually returned, any storage bug, inconsistency between the KV store and the Jellyfish Merkle tree, or a corrupted/stale on-disk value at that key can be silently accepted as "verified" state. This directly matches the "Committed state that differs from the correct VM result" and "Authenticated API or state-view output bound to the wrong version, object, or proof context" categories in scope, since the entire point of this state view is to guarantee state values are bound to the specific authenticated root.

### Likelihood Explanation
The bug requires the fallible-proof-lookup path to actually error (or the two independent reads to diverge) — this is not a routine event under normal, uncorrupted storage, so this is best characterized as a defense-in-depth failure: the verification mechanism intended to catch storage bugs/corruption is itself silently disabled exactly when it would be needed, rather than a bug that is trivially triggerable by an unprivileged external actor on a healthy node. I was not able to fully confirm, from the available index, every caller of `verified_state_view_at_version` or whether any call site depends on this verification for consensus-relevant decisions versus purely defensive tooling; this would need further tracing in a full checkout.

### Recommendation
- Change `get()` to propagate the error from `get_state_value_with_proof_by_version` instead of silently discarding it via `if let Ok(...)`.
- Use the value obtained from the proof-verified read (not a second independent call) as the value that is returned, or explicitly assert the two reads are identical before returning.

### Proof of Concept
Not exploitable purely from external inputs without inducing a divergent/erroring DB read at the proof-lookup call; the concrete break is demonstrated by code inspection: [2](#0-1)  shows the verification is optional-on-success only and structurally decoupled from the returned value, while [1](#0-0)  shows the caller-facing contract that a "verified" view is supposed to check every read against `state_root_hash`.

impl VerifiedStateViewAtVersion for Arc<dyn DbReader> {
    fn verified_state_view_at_version(
        &self,
        version: Option<Version>,
        ledger_info: &LedgerInfo,
    ) -> StateViewResult<DbStateView> {
        let db = self.clone();

        if let Some(version) = version {
            let txn_with_proof =
                db.get_transaction_by_version(version, ledger_info.version(), false)?;
            txn_with_proof.verify(ledger_info)?;

            let state_root_hash = txn_with_proof
                .proof
                .transaction_info
                .state_checkpoint_hash()
                .ok_or_else(|| StateViewError::NotFound("state_checkpoint_hash".to_string()))?;

            Ok(DbStateView {
                db,
                version: Some(version),
                maybe_verify_against_state_root_hash: Some(state_root_hash),
            })
        } else {
            Ok(DbStateView {
                db,
                version: None,
                maybe_verify_against_state_root_hash: None,
            })
        }
    }
