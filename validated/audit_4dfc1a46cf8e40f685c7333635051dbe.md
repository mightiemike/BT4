Based on my investigation, I found the mechanism analogous to the report's rounding pattern: `next-liquidity-index` in the vault contracts rounds the supplier interest rate **down**, and it is called through the permissionless, public `accrue()` function without any restriction on caller or frequency.

### Title
Frequent permissionless `accrue()` calls can round supplier interest to zero via truncated `mul-div-down` in `next-liquidity-index` - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent vault contracts)

### Summary
`accrue()` is a public, permissionless function that any address can call at any time [1](#0-0) . It calls `next-liquidity-index()`, which computes the new liquidity index by multiplying the current `lindex` by a growth multiplier derived from `(time-delta)` since `last-update`, using `mul-div-down` (round-down) for the interest multiplier [2](#0-1) . `calc-multiplier-delta` with `round-up=false` uses `mul-div-down` for the fractional interest term [3](#0-2) , and `last-update` is only reset when the index actually changes [4](#0-3) .

### Finding Description
This mirrors the report's root cause: interest is computed as `principal * increment / precision²`-style truncating division, and calling the accrual entrypoint at high frequency keeps `time-delta` tiny, driving the rounded-down increment to zero on each call while `last-update` (the "prevIndex" analog) never advances past the current block because the update to `last-update` is itself gated on the index having changed [5](#0-4) . Since `accrue()` has no caller restriction (no `check-caller-auth`, unlike `system-borrow`/`system-repay` [6](#0-5) ), an attacker can call `accrue()` (directly or by triggering `deposit`/`redeem`/`transfer`, which all invoke `accrue()` via `try!` [7](#0-6) ) every block, repeatedly re-evaluating `next-liquidity-index()` with minimal `time-delta`. Because `calc-multiplier-delta` rounds the fractional interest increment down to zero for sufficiently small `rate * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS` terms, the liquidity index growth is truncated away each time, and this happens *before* any real elapsed-time interest can accumulate into a nonzero increment — the classic "mutation evaluated on a value whose growth is truncated by an artificially shrunk time delta" pattern.

Unlike the debt index (`next-index`), which deliberately rounds **up** (`round-up=true`) to protect the protocol from underbilling borrowers [8](#0-7) , the liquidity/supplier index rounds down, meaning the party disadvantaged by the truncation is always the suppliers collectively — every holder of the vault's ztoken, not merely a single targeted victim (this is a difference from the original per-user report, but the mechanism — precision loss from repeated small-time-delta accrual calls — is otherwise directly analogous).

### Impact Explanation
Interest that would otherwise accrue to liquidity-index-based ztoken holders is permanently lost to rounding rather than being distributed later, because each `accrue()` call also advances what is effectively the reference point (via the "no-op" `last-update`-unless-changed and multiplier-reset-to-`INDEX-PRECISION` logic) for the next computation. This is a temporary/permanent freezing of unclaimed supplier yield — dust amounts are truncated away every time the index is prevented from growing meaningfully before the next accrual, degrading effective realized APY for suppliers versus the nominal configured rate.

### Likelihood Explanation
Likelihood is low-to-medium: it requires an attacker to spam transactions calling `accrue()` (or any of `deposit`/`redeem`/`transfer`, which are all unauthenticated and inexpensive) at high frequency relative to block time, similar to the original report's requirement of frequent triggering. On Stacks, transaction cost and block cadence bound how effective this griefing can be, and the loss per call is at most a few index-precision units, so the aggregate economic benefit to an attacker is unclear and the impact is diffuse across all suppliers rather than concentrated on one victim — the impact per unit time is bounded and the attack is not clearly profitable, which is why I rate confidence in real-world impact as low.

### Recommendation
Consider tracking sub-precision remainder/dust across accrual calls (carry-forward accumulator) instead of discarding the truncated fraction on every `next-liquidity-index()` computation, or rate-limit/batch `accrue()` so that the liquidity index is only recomputed after a minimum time delta, preventing an attacker from repeatedly resetting the accrual window before meaningful interest can compound.

### Proof of Concept
1. Attacker observes a vault (e.g. `v0-vault-stx.clar`) with nonzero utilization and thus nonzero `liquidity-rate`.
2. Attacker calls `accrue()` (or any of `deposit`/`redeem`/`transfer` with minimal amounts) in consecutive blocks/transactions.
3. Each call computes `next-liquidity-index()`: `time-delta = stacks-block-time - last-update` is small; `calc-multiplier-delta(liquidity-rate, time-delta, false)` computes `mul-div-down(rate, time-delta * INDEX-PRECISION, SECONDS-PER-YEAR-BPS)`, which truncates to `0` for sufficiently small `time-delta`.
4. Because the multiplier is `INDEX-PRECISION` (no growth), `calc-index-next` returns `lindex` unchanged; the `is-eq lidx nliq` check is true, so `last-update` is *not* advanced this call path only for the lindex branch, but is left dependent on the borrow index changing (see line 860-863) [9](#0-8) .
5. Repeating this at high frequency keeps resetting the effective window before the truncated fractional interest can accumulate into a full unit, causing cumulative dust loss to suppliers relative to the nominal configured liquidity rate.

I could not fully verify the exact economic magnitude of the loss (e.g., precise `INDEX-PRECISION`/`SECONDS-PER-YEAR-BPS` constants) from the indexed snippets alone; a Devin session with full repository access would be needed to compute concrete numeric bounds and confirm whether the accumulated dust is material enough to matter in production given real block times and typical `liquidity-rate` magnitudes.
