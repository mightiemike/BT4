## Analysis Summary

Reducing the external report to its core invariant: **a signed/authenticated commitment must be verified against the exact context it claims to represent before being trusted.** In the join-signature bug, the missing binding (chain/contract/round) let a valid-looking signature be replayed into the wrong context. The Aptos-native analog I traced is a **missing binding-check between recomputed state and its already-authenticated commitment** in the storage catch-up/restore path, not just a coincidental parallel — it's the same "trust a re-derived value without re-checking it against its supposed origin" pattern.

### Title
Missing state-checkpoint-hash verification during State Merkle DB catch-up allows silently corrupted state root to be persisted as authentic - (File: `storage/aptosdb/src/state_store/mod.rs`)

### Summary
`StateStore::replay_write_sets_after_snapshot` (invoked from DB open when the State Merkle DB lags behind the Ledger DB, e.g. after a crash between committing transaction infos/write-sets and committing the merkle snapshot) recomputes state from persisted write sets and directly commits the result as the new persisted state summary/root — without ever comparing the recomputed root(s) against the already-committed, accumulator-authenticated `state_checkpoint_hash` values in the corresponding `TransactionInfo` records.

### Finding Description
On the normal execution/commit path, `DoStateCheckpoint::get_state_checkpoint_hashes` explicitly asserts that a freshly computed checkpoint root matches the `known_state_checkpoints` extracted from `TransactionInfo` before treating it as valid: [1](#0-0) 

However, the catch-up path used when the State Merkle DB needs to be advanced to match the Ledger DB (`replay_write_sets_after_snapshot`) recomputes the ledger state from raw write sets and hands it straight to `buffered_state.update_and_report` — no equivalent `ensure!(recomputed_root == txn_info.state_checkpoint_hash())` exists here: [2](#0-1) 

The checkpoint indices are derived only to *segment* the write-set batch (`all_checkpoint_indices` via `txn_info.has_state_checkpoint_hash()`), not to *validate* the resulting root: [3](#0-2) 

This same unchecked pattern is also present in the backup restore hot-path `save_transactions_impl`, where `kv_replay` recomputes state via `calculate_state_and_put_updates` and immediately calls `set_state_ignoring_summary` without comparing to `txn_info.state_checkpoint_hash()`: [4](#0-3) 

This is consistent with a broader, self-acknowledged gap: `TransactionOutput::ensure_match_transaction_info` — used by chunk-executor's `verify_execution` (state-sync replay-verification) and by `aptos-debugger`'s mismatch printer — also skips comparing `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a limitation the code explicitly documents as allowing "replay-verify tooling... to report a successful replay even when the authenticated position state root diverges from local execution": [5](#0-4) [6](#0-5) 

### Impact Explanation
If the write-set replay/catch-up computation ever diverges from the originally-executed-and-committed state (due to an indexing bug in checkpoint-boundary detection, a bug in `update_with_db_reader`/`StateUpdateRefs::index_write_sets`, partial/corrupted write-set rows, or any other latent defect), the node will silently persist a wrong Jellyfish Merkle root as the "current" state for that version — with no assertion catching the divergence against the ledger's own already-authenticated `state_checkpoint_hash`. Because state-proof-serving APIs (`get_state_value_with_proof_by_version`, etc.) read off this same Merkle DB, the node would then produce state values/proofs for a version whose root no longer matches what the corresponding `TransactionInfo`/accumulator says is correct, while callers have no signal that anything is wrong (no error is raised; the version, root "claim", and object all look consistent from the outside). This directly violates the "authenticated API and state-view output bound to the wrong version/root" and "restore/replay paths must not reinterpret committed data into a different ledger state" invariants.

### Likelihood Explanation
This code path is exercised on every AptosDB restart where the State Merkle DB is behind the Ledger DB — a routine, unprivileged, node-operational scenario (e.g., following any crash/restart during normal commit), not a rare or attacker-controlled trigger. The missing assertion means any future regression in the state-recomputation logic used here (which is separate from, and not covered by, the primary execution-time checkpoint validation) would go completely undetected in production rather than failing loudly, which is the defining difference from the equivalent, protected code path in `DoStateCheckpoint`.

### Recommendation
Add the same defensive check used in `DoStateCheckpoint::get_state_checkpoint_hashes` to `replay_write_sets_after_snapshot` (and to the `kv_replay` branch of `restore_utils::save_transactions_impl`): after recomputing `new_state`/`new_state_summary`, assert that the resulting root(s) at each checkpoint index equal the corresponding `TransactionInfo::state_checkpoint_hash()` (and `hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` where applicable) before committing/persisting, and fail loudly (panic or hard error) on mismatch rather than silently accepting the recomputed state.

### Proof of Concept
Not directly demonstrable without inducing an actual state-recomputation divergence bug (e.g., a defect in `update_with_db_reader` or in `all_checkpoint_indices` derivation), since exploiting this requires a *second*, independent bug to actually corrupt the recomputed root; this finding documents the missing invariant/verification layer that would otherwise have caught such corruption before persistence, per the code paths cited above.

    /// Replays all write sets after the previously committed snapshot until things have caught up.
    fn replay_write_sets_after_snapshot(
        state_db: &Arc<StateDb>,
        snapshot_next_version: Version,
        num_transactions: u64,
        buffered_state: &mut BufferedState,
        out_current_state: &Mutex<LedgerStateWithSummary>,
        persisted_state: &PersistedState,
        delete_hot_state_on_restart: bool,
    ) -> Result<()> {
        info!("Replaying writesets from {snapshot_next_version} to {num_transactions} to let state Merkle DB catch up.");

        let write_sets = state_db
            .ledger_db
            .write_set_db()
            .get_write_sets(snapshot_next_version, num_transactions)?;
        let txn_info_iter = state_db
            .ledger_db
            .transaction_info_db()
            .get_transaction_info_iter(snapshot_next_version, write_sets.len())?;
        let all_checkpoint_indices = txn_info_iter
            .into_iter()
            .collect::<Result<Vec<_>>>()?
            .into_iter()
            .positions(|txn_info| txn_info.has_state_checkpoint_hash())
            .collect();

        let state_update_refs = StateUpdateRefs::index_write_sets(
            snapshot_next_version,
            &write_sets,
            write_sets.len(),
            all_checkpoint_indices,
        );
        let current_state = out_current_state.lock().clone();
        let (hot_state, state) = persisted_state.get_state();
        let (new_state, _state_reads, hot_state_updates) = current_state
            .ledger_state()
            .update_with_db_reader(&state, hot_state, &state_update_refs, state_db.clone())?;
        let state_summary = persisted_state.get_state_summary();
        let new_state_summary = current_state.ledger_state_summary().update(
            &ProvableStateSummary::new(state_summary, state_db.as_ref()),
            &hot_state_updates,
            &state_update_refs,
        )?;
        let updated = LedgerStateWithSummary::from_state_and_summary(new_state, new_state_summary);

        // `delete_on_restart` wiped the hot state KV for this range; re-write it so it
        // matches the JMT we're about to commit.
        if delete_hot_state_on_restart {
            let db = &state_db.hot_state_kv_db;
            let mut sharded_batches = db.new_sharded_native_batches();
            Self::put_hot_state_updates(&hot_state_updates, &mut sharded_batches)?;
            db.commit(num_transactions - 1, None, sharded_batches)?;
        }

        // synchronously commit the snapshot at the last checkpoint here if not committed to disk yet.
        buffered_state.update_and_report(
            updated,
            hot_state_updates,
            0,    /* estimated_items, doesn't matter since we sync-commit */
            true, /* sync_commit */
        )?;
        Ok(())
