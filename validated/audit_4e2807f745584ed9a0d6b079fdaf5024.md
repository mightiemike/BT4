### Title
Starknet OS `send_message_to_l1` syscall accepts out-of-range L1 addresses that Blockifier rejects, causing execution divergence - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The Rust Blockifier and the Cairo Starknet OS implement the `SendMessageToL1` syscall independently, and they must produce identical results for the same transaction so that block execution (Blockifier) and proof generation / re-execution (OS) agree on the resulting state, events, and outputs. Blockifier validates that the `to_address` parameter is a legal 160-bit Ethereum address (when the chain is not L3) and rejects the call otherwise, while the OS's Cairo implementation of the same syscall performs no such validation.

### Finding Description
In Blockifier, `send_message_to_l1` explicitly validates the `to_address` field: [1](#0-0) 
This uses `EthAddress::try_from(message.to_address)`, which fails for any `to_address` that does not fit in 160 bits (unless `chain_info.is_l3` is true), producing an "Out of range" execution error and reverting the calling entry point. This is confirmed by the negative test case: [2](#0-1) 

The deprecated (Cairo0) syscall handler performs the identical check: [3](#0-2) 

However, the Starknet OS's Cairo implementation of the same syscall, `execute_send_message_to_l1` in `syscall_impls.cairo`, writes `request.to_address` directly into the `MessageToL1Header` output with no range or format check whatsoever: [4](#0-3) 

The equivalent deprecated (Cairo0) OS syscall implementation, `execute_deprecated_syscalls`'s `SendMessageToL1` branch, likewise copies the `to_address` and payload straight into the output without any validation: [5](#0-4) 

No `is_l3`, `EthAddress`, or address-bound check exists anywhere in the OS's Cairo sources (`grep` for `is_l3`/`EthAddress`/`160` in `*.cairo` returned no relevant matches in the OS execution code), confirming this validation is entirely absent from the canonical (proof-verified) execution path.

### Impact Explanation
This is analogous to the referenced CVE's root cause class: a message/parameter passed across a trust boundary (contract → syscall handler) is insufficiently vetted by one privileged component (the OS/prover, which is the ultimate authority for the committed state and L1 output) even though a parallel, supposedly equivalent component (Blockifier) does vet it. Since block execution and proof generation must be exactly consistent, this divergence means:
- Blockifier will revert a call that invokes `send_message_to_l1_syscall` with an out-of-range `to_address` (treating it as a failed inner call / possible transaction revert), while
- The OS, when independently re-executing/proving the same Cairo bytecode and calldata, will not detect any error, will treat the call as succeeding, and will emit an oversized/invalid `to_address` into `messages_to_l1` output.

This produces a mismatch between the state/output committed by the sequencer (Blockifier) and the state/output that would be produced/accepted by the OS's independent re-execution, i.e., honest-node divergence and potentially a wrongly computed commitment/output (the L1 messages segment feeding into the block's data-availability / message output, which is part of what gets committed on L1). This falls squarely into the impact categories called out in scope ("wrong committed root or block hash, honest-node divergence").

### Likelihood Explanation
Reachable from a single, unprivileged transaction: any contract can invoke `send_message_to_l1_syscall(to_address, payload)` with an attacker-chosen `to_address` value exceeding 160 bits, exactly as done in the test/feature contracts already present in the repo (e.g. `test_send_message_to_l1`). No special privileges, staking, or malicious-operator behavior are required — a normal deployed contract and an ordinary invoke transaction suffice to trigger the divergent code paths.

### Recommendation
Add the identical Ethereum-address range/validity check to the OS's Cairo `execute_send_message_to_l1` (and the deprecated Cairo0 equivalent) that Blockifier performs in `syscall_base.rs`/`hint_processor.rs`: reject (or fail the syscall / entry point) when `to_address` does not fit within 160 bits, unless the chain is configured as L3 (mirroring the `is_l3` bypass used in Blockifier). This must be done consistently across both the Rust execution layer and the Cairo OS layer to guarantee identical state transitions and outputs between the two systems.

### Proof of Concept
1. Deploy a contract with an external function (as in `test_contract.cairo`'s `test_send_message_to_l1`) that calls `send_message_to_l1_syscall(to_address, payload)` where `to_address` is set to a felt value ≥ 2^160 (e.g., `0x10000000000000000000000000000000000000000`), on a non-L3 chain.
2. Submit an ordinary invoke transaction calling this function.
3. Observe that Blockifier's execution reverts/fails the call with an "Out of range" error (as reproduced in `test_send_message_to_l1_invalid_address`), while the Starknet OS Cairo program, when re-executing the identical trace/bytecode for proving, has no equivalent check in `execute_send_message_to_l1` and would accept the call, emitting the invalid `to_address` into the `messages_to_l1` output — producing a mismatched result between the two execution layers.

Note: I was unable to fully trace how OS execution traces are actually generated (i.e., whether the OS always executes from Blockifier-produced hints such that a Blockifier-reverted call could never reach the OS's `execute_send_message_to_l1` code path in practice, or whether the OS independently re-derives execution from raw Cairo bytecode/calldata without depending on Blockifier's revert decision). This distinction is important to confirm exploitability with certainty and would benefit from further investigation of the hint-generation/OS-input pipeline (e.g., in `starknet_os_flow_tests` or the OS runner code) in a full Devin session with complete repository access.

        if !self.context.tx_context.block_context.chain_info.is_l3 {
            EthAddress::try_from(message.to_address)?;

        let ordered_message_to_l1 =

        self.l2_to_l1_messages.push(ordered_message_to_l1);
        self.context.n_sent_messages_to_l1 += 1;

        Ok(())
    }

// Sends a message to L1.
func execute_send_message_to_l1{range_check_ptr, syscall_ptr: felt*, outputs: OsCarriedOutputs*}(
    contract_address: felt
) {
    alloc_locals;
    let request = cast(syscall_ptr + RequestHeader.SIZE, SendMessageToL1Request*);
    let success = reduce_syscall_gas_and_write_response_header(
        total_gas_cost=SEND_MESSAGE_TO_L1_GAS_COST, request_struct_size=SendMessageToL1Request.SIZE
    );
    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();
    }

    tempvar payload_start = request.payload_start;
    tempvar payload_size = request.payload_end - payload_start;

    assert [outputs.messages_to_l1] = MessageToL1Header(
        from_address=contract_address, to_address=request.to_address, payload_size=payload_size
    );
    memcpy(
        dst=outputs.messages_to_l1 + MessageToL1Header.SIZE, src=payload_start, len=payload_size
    );
    let (outputs) = os_carried_outputs_new(
        messages_to_l1=outputs.messages_to_l1 + MessageToL1Header.SIZE + payload_size,
        messages_to_l2=outputs.messages_to_l2,
    );

    return ();
}
