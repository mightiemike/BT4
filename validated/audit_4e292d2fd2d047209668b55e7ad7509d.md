### Title
Postponed-receipt / received-data state is excluded from both storage-staking accounting and congestion-control memory accounting, enabling unbounded unpaid state growth reachable from ordinary contract calls - (File: `runtime/runtime/src/lib.rs`)

### Summary
The CVE describes a QUIC endpoint allocating a `PATH_RESPONSE` per `PATH_CHALLENGE` that is freed only when the (potentially malicious) remote peer acknowledges it — giving the remote party unilateral control over when memory is released, with no accounting/limit tying allocation to that party's cost. NEAR's runtime has a structurally identical pattern for `PostponedReceipt` / `PostponedReceiptId` / `PendingDataCount` / `ReceivedData` state: entries are written to the receiver account's trie namespace when an `ActionReceipt` has unmet `input_data_ids`, and are only removed when the matching `Data` receipt arrives. Unlike every other form of account state, this bookkeeping is explicitly excluded from account `storage_usage` (so no storage-staking deposit is required to keep it alive) and from the NEP-539 congestion-control "memory" metric (so it never triggers the backpressure red light). A contract-controlled promise chain can therefore keep creating this state faster than it resolves, at essentially zero incremental cost, growing validator state/trie memory without bound.

### Finding Description
When an incoming `ActionReceipt` has unmet `input_data_ids`, `Runtime::process_action_receipt` writes `TrieKey::PostponedReceiptId` links and a `TrieKey::PendingDataCount` counter, then calls `set_postponed_receipt` to persist the whole receipt under `TrieKey::PostponedReceipt` — all keyed by the *receiver* account: [1](#0-0) 

None of these writes touch `account.storage_usage()`. Contrast this with other trie writes on the same code paths (`action_deploy_contract`, `install_universal_account`), which explicitly call `account.set_storage_usage(...)` before persisting data: [2](#0-1) [3](#0-2) 

This omission is intentional and documented: the genesis `StorageComputer` (which mirrors what should be charged) explicitly maps `PostponedReceipt`, `ReceivedData`, and `DelayedReceipt` state records to `None` — "we don't charge storage for receipts": [4](#0-3) 

Because `check_storage_stake` only ever looks at `account.storage_usage()`, this postponed/received-data state is invisible to the storage-staking mechanism that is supposed to make an attacker pay proportionally for every byte of state they keep alive: [5](#0-4) 

The second layer of defense — NEP-539 congestion control's "memory" dimension (`max_congestion_memory_consumption`) — is also explicitly bypassed for this state. `compute_receipt_congestion_gas` assigns `Data`, `PromiseYield`, and `PromiseResume` receipts **zero** congestion cost, with the code comment stating the MVP does not account for data/postponed receipts because it "would require reading the postponed receipt from the trie": [6](#0-5) 

The spec confirms this is a known, accepted gap in the model, not merely an oversight in one function: [7](#0-6) 

So the only two mechanisms nearcore has for bounding unbounded receipt/data state growth — (1) storage staking charged to the account, and (2) congestion-control's memory-based backpressure — both explicitly skip postponed receipts and their bookkeeping records. The only thing that eventually clears this state is the corresponding `Data` receipt for the same `data_id`, delivered by `process_receipt`'s `Data` arm: [8](#0-7) 

An attacker fully controls when that resolving `Data` receipt is produced, because it is only emitted when the *antecedent* receipt (which the attacker also creates, e.g. via `promise_then`/`promise_and` chains in their own deployed contract) is actually executed. Execution of that antecedent is itself subject to the runtime's normal congestion/delayed-queue admission control (`process_incoming_receipts`/`process_delayed_receipts`), which the attacker can keep saturated by continuously submitting more transactions — each of which is cheap (gas-only, no storage deposit) and adds more unaccounted `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` state on top. This is the direct analog of the QUIC bug: the "release" of the allocation is gated on an event (peer ACK / matching `Data` receipt) that the attacker themselves controls and can simply withhold or perpetually postpone, while the local node (QUIC endpoint / NEAR validator) has already committed the resource with no compensating charge or limit.

### Impact Explanation
Every validator/RPC node applying chunks must persist this excluded state in its trie (and typically also in flat storage / in-memory tries used for fast reads and witness generation). Because neither storage staking nor congestion control's memory metric charges or throttles this specific class of state, a single unprivileged account can drive state/memory growth on all validators proportionally to how many postponed-receipt chains it opens and keeps unresolved, at a cost bounded only by ordinary gas fees rather than by the amount of state actually retained. Sustained abuse can grow per-shard state size and node memory usage without the corresponding economic cost that the protocol's storage-staking design assumes exists for every persisted byte, which is the resource-exhaustion analog of the reported CVE (heap growth uncorrelated with attacker cost, releasable only at the attacker's discretion).

### Likelihood Explanation
The `input_data_ids` / postponed-receipt mechanism is standard NEAR cross-contract-call machinery (`promise_then`, `promise_and`) available to any deployed contract; no privileged role, validator collusion, or network-level attack is required — only a signed transaction that deploys a contract exercising ordinary promise combinators in a loop while its own contracts avoid completing the chained callbacks promptly (e.g., by targeting congested shards or by fanning out enough parallel chains that congestion admission control keeps deferring their resolution). The exclusion from storage accounting and congestion-memory accounting is unconditional (not gated behind a rare edge case), which makes the underlying mechanism reliably reachable.

### Recommendation
Charge the receiver account's `storage_usage` for the bytes of `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` entries created in `Runtime::process_action_receipt` (and decrement it when they are cleared in the `Data` arm of `process_receipt`), analogous to how `action_deploy_contract` and `install_universal_account` account for their writes. Separately, include postponed-receipt/received-data byte size in the NEP-539 congestion "memory" metric (`receipt_bytes`) so that this class of state can actually trigger the existing backpressure red light, closing the gap the code comments in `congestion_control.rs` acknowledge.

### Proof of Concept
Conceptual reproduction (would need to be executed against a running/test-loop node to fully confirm state growth over time):
1. Deploy a contract on account `attacker.near` that, on each call, issues a batch of `promise_then` calls each generating a fresh `input_data_id` pointing at a callback receipt on `attacker.near` itself, while its antecedent promise targets a heavily-loaded/deliberately-congested receiver shard so the antecedent's completion (and thus the resolving `Data` receipt) is delayed by the runtime's normal congestion/delayed-queue handling.
2. Repeatedly submit transactions calling this method from many signer accounts (only gas cost, no extra deposit) at a rate exceeding the antecedent resolution rate.
3. Observe (via `state-viewer` state stats or trie iteration over `TrieKey::PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` columns) that these entries accumulate under `attacker.near`'s key range, while `get_account(attacker.near).storage_usage()` and `CongestionInfo::receipt_bytes` for the shard do not reflect this growth, and no `LackBalanceForState`/congestion-rejection is ever triggered by it (`runtime/runtime/src/verifier.rs:48-84`, `runtime/runtime/src/congestion_control.rs:678-713`).

/// Computes the expected storage per account for a given stream of StateRecord(s).
/// For example: the storage for Contract depends on its length, we don't charge storage for receipts
/// and we compute a fixed (config-configured) number of bytes for each account (to store account id).
struct StorageComputer<'a> {
    /// Map from account id to number of storage bytes used.
    result: HashMap<AccountId, u64>,
    /// Configuration that keeps information like 'how many bytes should accountId consume' etc.
    config: &'a StorageUsageConfig,
}

impl<'a> StorageComputer<'a> {
    fn new(config: &'a StorageUsageConfig) -> Self {
        Self { result: HashMap::new(), config: &config }
    }

    /// Updates user's storage info based on the StateRecord.
    fn process_record(&mut self, record: &StateRecord) {
        // Note: It's okay to use unsafe math here, because this method should only be called on the trusted
        // state records (e.g. at launch from genesis)
        let account_and_storage = match record {
            StateRecord::Account { account_id, .. } => {
                Some((account_id.clone(), self.config.num_bytes_account))
            }
            StateRecord::Data { account_id, data_key, value } => {
                let storage_usage =
                    self.config.num_extra_bytes_record + data_key.len() as u64 + value.len() as u64;
                Some((account_id.clone(), storage_usage))
            }
            StateRecord::Contract { account_id, code } => {
                Some((account_id.clone(), code.len() as u64))
            }
            StateRecord::AccessKey { account_id, public_key, access_key } => {
                let access_key: AccessKey = access_key.clone();
                let storage_usage = self.config.num_extra_bytes_record
                    + public_key.trie_id_len() as u64
                    + borsh::object_length(&access_key).unwrap() as u64;
                Some((account_id.clone(), storage_usage))
            }
            StateRecord::GasKeyNonce { account_id, public_key, index: _index, nonce } => {
                let storage_usage = self.config.num_extra_bytes_record
                    + public_key.trie_id_len() as u64
                    + size_of::<NonceIndex>() as u64
                    + borsh::object_length(&nonce).unwrap() as u64;
                Some((account_id.clone(), storage_usage))
            }
            StateRecord::PostponedReceipt(_) => None,
            StateRecord::ReceivedData { .. } => None,
            StateRecord::DelayedReceipt(_) => None,
        };
        if let Some((account_id, storage_usage)) = account_and_storage {
            *self.result.entry(account_id).or_default() += storage_usage;

pub fn check_storage_stake(
    account: &Account,
    account_balance: Balance,
    runtime_config: &RuntimeConfig,
) -> Result<(), StorageStakingError> {
    let billable_storage_bytes = account.storage_usage();
    let required_amount = runtime_config
        .storage_amount_per_byte()
        .checked_mul(u128::from(billable_storage_bytes))
        .ok_or_else(|| {
            format!(
                "Account's billable storage usage {} overflows multiplication",
                billable_storage_bytes
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    let available_amount = account_balance
        .checked_add(account.locked())
        .ok_or_else(|| {
            format!(
                "Account's amount {} and locked {} overflow addition",
                account.amount(),
                account.locked(),
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    if available_amount >= required_amount {
        Ok(())
    } else {
        if is_zero_balance_account(account) {
            return Ok(());
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(
            required_amount.checked_sub(available_amount).unwrap(),
        ))
    }
}

pub(crate) fn compute_receipt_congestion_gas(
    receipt: &Receipt,
    config: &RuntimeConfig,
) -> Result<Gas, IntegerOverflowError> {
    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt) => {
            // account for gas guaranteed to be used for executing the receipts
            action_receipt_congestion_gas(receipt, config, action_receipt.into())
        }
        VersionedReceiptEnum::Data(_data_receipt) => {
            // Data receipts themselves don't cost gas to execute, their cost is
            // burnt at creation. What we should count, is the gas of the
            // postponed action receipt. But looking that up would require
            // reading the postponed receipt from the trie.
            // Thus, the congestion control MVP does not account for data
            // receipts or postponed receipts.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::PromiseYield(_) => {
            // The congestion control MVP does not account for yielding a
            // promise. Yielded promises are confined to a single account, hence
            // they never cross the shard boundaries. This makes it irrelevant
            // for the congestion MVP, which only counts gas in the outgoing
            // buffers and delayed receipts queue.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::PromiseResume(_) => {
            // The congestion control MVP does not account for resuming a promise.
            // Unlike `PromiseYield`, it is possible that a promise-resume ends
            // up in the delayed receipts queue.
            // But similar to a data receipt, it would be difficult to find the cost
            // of it without expensive state lookups.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(Gas::ZERO),
    }
