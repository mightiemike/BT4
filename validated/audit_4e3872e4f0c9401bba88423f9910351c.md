### Title
Unbounded memory allocation from unvalidated array-length felt in `read_felt_array` (EmitEvent / SendMessageToL1 / MetaTxV0 syscalls) - (File: `crates/blockifier/src/execution/execution_utils.rs`, `crates/blockifier/src/execution/syscalls/vm_syscall_utils.rs`)

### Summary
`read_felt_array` converts an attacker-supplied `Felt` (read directly from Cairo VM memory, fully controlled by the executing contract) into a `usize` and immediately uses it as the length to read/allocate a `Vec<Felt>`, with no upper bound check performed before the allocation attempt. This function is reached during the *request-parsing* phase of multiple syscalls (`EmitEvent`, `SendMessageToL1`, `MetaTxV0`), i.e. before any gas-based or size-based validation of the array length occurs.

### Finding Description
`read_felt_array` reads the declared array size as a `Felt`, converts it to `usize`, and passes it straight into `felt_range_from_ptr` to build the array — there is no comparison against a maximum allowed length prior to the allocation attempt: [1](#0-0) 

This is invoked while parsing syscall *requests*, i.e. before the syscall's real resource/gas accounting for the array length is applied:
- `EmitEventRequest::read` calls `read_felt_array` twice (keys and data) and only validates size limits (`exceeds_event_size_limit`) afterward, in the syscall body, not before allocation: [2](#0-1) 
- `SendMessageToL1Request::read` reads the L1 payload via `read_felt_array` with no linear-factor override, so the allocation is not gas-metered by payload length at all: [3](#0-2) 
- `MetaTxV0Request::read` similarly calls `read_felt_array` for the signature before request-level cost accounting: [4](#0-3) 

The generic dispatcher shows that request parsing (`SyscallRequestWrapper::<Request>::read`, which triggers `read_felt_array`) happens before the syscall's linear gas cost is computed and checked against the caller's remaining gas: [5](#0-4) 

`SyscallRequest::get_linear_factor_length` defaults to `0` unless explicitly overridden, and `EmitEventRequest`/`SendMessageToL1Request` do not override it: [6](#0-5) 

Because the declared length felt is attacker-chosen and unbounded (up to `usize::MAX`), the allocation attempted inside `felt_range_from_ptr`/`read_felt_array` can be arbitrarily large, mirroring the ImageMagick SVG bug class (CWE-770/CWE-789: memory allocation without limits based on an untrusted size field), except here the "file" is Cairo VM memory content fully controlled by the calling contract.

### Impact Explanation
A contract invoked by any transaction can place a huge value in the felt slot that `read_felt_array` treats as `keys_len`/`data_len`/`payload_size`/signature length, causing the sequencer process to attempt a massive `Vec` allocation during syscall request parsing — before any per-syscall size limit (`exceeds_event_size_limit`) or gas-based rejection takes effect. A large-enough allocation attempt aborts the process (OOM) or causes severe resource exhaustion on every node executing that transaction, since all validators/full nodes re-execute it identically. This can halt block production / transaction execution network-wide, matching "network unable to confirm new transactions".

### Likelihood Explanation
High. Any account contract can call `emit_event`, `send_message_to_l1`, or the `meta_tx_v0` syscall with a manipulated length felt in the calldata/segment it controls; no privileged role is required — a single crafted transaction is enough to reach the vulnerable path.

### Recommendation
Validate the declared array length against a hard maximum (and against remaining memory-segment bounds) in `read_felt_array`/`felt_range_from_ptr` before allocating, similar to the bounds check already used in `apollo_cairo_utils`'s `CairoArray::try_from` (validate length against remaining data before `Vec::with_capacity`): [7](#0-6) 
Additionally, ensure request parsing that can allocate proportionally to a felt-controlled length always charges/validates against the syscall's linear-factor gas cost (or a fixed cap) *before* allocating, not after, for `EmitEvent` and `SendMessageToL1`.

### Proof of Concept
1. Deploy a contract whose Cairo code invokes `emit_event` (or `send_message_to_l1`, `meta_tx_v0`) via the corresponding syscall.
2. Craft the syscall's memory layout so the felt at the `keys_len`/`data_len`/`payload_size` position is a very large value (e.g., close to `usize::MAX` on the host, which is representable since `Felt` is a ~252-bit field element).
3. Submit a single transaction invoking this contract; during syscall request parsing, `read_felt_array` (`crates/blockifier/src/execution/execution_utils.rs:931-949`) converts this felt to a `usize` and passes it to `felt_range_from_ptr` before any `exceeds_event_size_limit`/gas check runs, triggering an oversized allocation attempt and process abort/resource exhaustion on every executing node.

pub type EmitEventResponse = EmptyResponse;

pub fn exceeds_event_size_limit(
    versioned_constants: &VersionedConstants,
    n_emitted_events: usize,
    event: &EventContent,
) -> Result<(), EmitEventError> {
    let EventLimits { max_data_length, max_keys_length, max_n_emitted_events } =
        versioned_constants.tx_event_limits;
    if n_emitted_events > max_n_emitted_events {
        return Err(EmitEventError::ExceedsMaxNumberOfEmittedEvents {
            n_emitted_events,
            max_n_emitted_events,
        });
    }
    let keys_length = event.keys.len();
    if keys_length > max_keys_length {
        return Err(EmitEventError::ExceedsMaxKeysLength { keys_length, max_keys_length });
    }
    let data_length = event.data.0.len();
    if data_length > max_data_length {
        return Err(EmitEventError::ExceedsMaxDataLength { data_length, max_data_length });
    }

    Ok(())
}
