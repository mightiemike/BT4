### Title
Missing default connection limit in `HttpService.initServer()` allows unauthenticated HTTP connection-exhaustion DoS - (File: `framework/src/main/java/org/tron/common/application/HttpService.java`)

### Summary
`HttpService.initServer()` only attaches Jetty's `ConnectionLimit` bean when `Args.getInstance().getMaxHttpConnectNumber() > 0`, and this setting is not enabled by default. In the shipped default configuration, the FullNode's Jetty `Server` accepts an unbounded number of concurrent TCP connections on the HTTP API port, letting an anonymous attacker open many sockets and starve the server's connectors/thread pool.

### Finding Description
`HttpService.initServer()` builds the Jetty `Server` and conditionally registers a connection cap: [1](#0-0) 

The `ConnectionLimit` bean — the only mechanism in this class that bounds concurrent TCP connections — is added to `this.apiServer` **only if** `maxHttpConnectNumber > 0`. There is no other connection-count guard anywhere in this class: `initContextHandler()` only wires a `SizeLimitHandler` for request body size, not connection count. No `QueuedThreadPool` sizing or acceptor/selector tuning is done in this file either, so the server relies on Jetty's own defaults when this optional limit is not configured.

Because `maxHttpConnectNumber` defaults to a disabled value (`<=0`) unless an operator explicitly sets it in `config.conf`, a freshly-started FullNode with default configuration has no cap on concurrent HTTP client connections. An unprivileged remote attacker can open a large number of raw TCP sockets to the HTTP API port, send partial/no HTTP requests, and hold them open indefinitely. Since Jetty allocates connection/acceptor resources per open socket and eventually threads per active request, this can exhaust the server's connector or thread-pool capacity, causing legitimate HTTP/RPC callers to be delayed or refused — all without the attacker broadcasting any transaction or paying any bandwidth/energy fee, since this is a raw socket-level attack against the HTTP listener itself, not a transaction-validation path.

None of the usual transaction-level protections apply here (`validateSignature`, actuator `validate()`, energy/bandwidth accounting, `ForkController`) because the attack never submits a transaction; it targets the HTTP transport layer before any TRON protocol logic is reached.

### Impact Explanation
Concrete impact: node's HTTP API becomes unresponsive/unavailable to legitimate wallets, exchanges, and dApp backends relying on the FullNode HTTP interface, purely via cheap, unauthenticated socket exhaustion. This matches the "DoS via RPC-API" bounty impact class — full node availability degradation with zero cost to the attacker.

### Likelihood Explanation
- Preconditions: node running with default config, i.e. `maxHttpConnectNumber` unset or `<=0` (the shipped default), which is the out-of-the-box condition for most FullNodes.
- Cost to attacker: negligible — just opening many TCP sockets from one or few hosts (no TRX, no signed transaction, no energy).
- Feasibility: trivial and repeatable with a simple script; the attack requires no privileged role, no MITM, and no protocol-level knowledge.

### Recommendation
Enable a sane, non-zero default for `maxHttpConnectNumber` (rather than leaving it opt-in), or unconditionally register a `ConnectionLimit` in `HttpService.initServer()` using a bounded default value, plus configure explicit acceptor/selector and thread-pool sizing (e.g., a bounded `QueuedThreadPool` with idle-timeout for unauthenticated/slow connections) so that the server degrades gracefully instead of exhausting shared resources.

### Proof of Concept
```java
// JUnit-style PoC (framework/src/test/java/.../HttpServiceConnectionExhaustionTest.java)
@Test
public void testUnboundedConnectionsWithDefaultConfig() throws Exception {
  // Start FullNodeHttpApiService with default Args (maxHttpConnectNumber <= 0)
  FullNodeHttpApiService service = context.getBean(FullNodeHttpApiService.class);
  service.start();

  List<Socket> sockets = new ArrayList<>();
  int N = 5000;
  for (int i = 0; i < N; i++) {
    Socket s = new Socket("127.0.0.1", httpPort);
    s.getOutputStream().write("GET / HTTP/1.1\r\n".getBytes()); // partial request, never completed
    sockets.add(s); // keep open, never close
  }

  // Attempt a legitimate call
  long start = System.currentTimeMillis();
  HttpResponse resp = HttpUtil.getHttpResponse(
      "http://127.0.0.1:" + httpPort + "/wallet/getnowblock", 3000 /*ms timeout*/);
  long elapsed = System.currentTimeMillis() - start;

  // Expected on vulnerable code: request times out / connection refused
  assertTrue("Expected legitimate request to be starved/refused", resp == null || elapsed >= 3000);

  for (Socket s : sockets) { s.close(); }
}
```
Expected result on the vulnerable default configuration: the legitimate `/wallet/getnowblock` call times out or is refused, demonstrating that no `ConnectionLimit` was registered by `HttpService.initServer()`. After setting `maxHttpConnectNumber` to a positive value, `ConnectionLimit` engages and rejects excess connections, protecting legitimate callers.

  protected void initServer() {
    this.apiServer = new Server(this.port);
    int maxHttpConnectNumber = Args.getInstance().getMaxHttpConnectNumber();
    if (maxHttpConnectNumber > 0) {
      this.apiServer.addBean(new ConnectionLimit(maxHttpConnectNumber, this.apiServer));
    }
    this.apiServer.setErrorHandler(new OversizedRequestErrorHandler());
  }
