### Title
OAuth `state` cookie collision across concurrent auth flows causes DoS of the OAuth callback handler - (File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts)

### Summary
`shopify.auth.begin()` writes the OAuth CSRF-protection nonce to a single, shop‑agnostic cookie (`STATE_COOKIE_NAME`, `shopify_app_state`) scoped only by `callbackPath`, never by `shop`. If a second OAuth flow is started in the same browser before an in‑flight flow completes, the second flow's nonce overwrites the first flow's cookie value, and the first flow's `callback()` request will fail nonce validation and throw `InvalidOAuthError`. This mirrors the reported bug class: a shared, non‑discriminated identifier (there: transaction hash without a proposal nonce; here: cookie name/path without a per‑flow/per‑shop discriminator) causes an otherwise-valid second "transaction" (OAuth attempt) to invalidate/collide with the first, producing a revert-equivalent failure (`InvalidOAuthError`) in the auth handler.

### Finding Description
`begin()` generates a per-flow nonce and stores it via a cookie keyed only by the fixed name `STATE_COOKIE_NAME` and `path: callbackPath` — not by shop or any other flow-specific identifier: [1](#0-0) 

`callback()` reads and deletes that same fixed cookie, then compares its value against the `state` query parameter returned by Shopify; if they don't match it throws `InvalidOAuthError`: [2](#0-1) [3](#0-2) 

Because the cookie is not scoped per shop or per flow, any second `begin()` call from the same browser (e.g., another tab, an embedded reload, or an attacker-triggered request such as `<img src="/auth?shop=attacker-shop.myshopify.com">`) silently overwrites the outstanding nonce cookie for *any* other in-progress flow sharing the same `callbackPath`. The library documents an analogous, related sibling collision for the post-auth session cookie (`SESSION_COOKIE_NAME`) explicitly in `cookiePath`'s doc comment, confirming the maintainers are aware that shared, non-scoped cookies collide across concurrent flows for different shops: [4](#0-3) 

This is the direct analog of the GovernorAlpha issue: a shared hash/key (there: `keccak256(target, value, signature, data, eta)`; here: `shopify_app_state` cookie name+path) is reused across two independent "transactions" (proposals / OAuth flows) that can legitimately occur concurrently, causing the earlier one to fail its validation check.

### Impact Explanation
The practical impact is a denial-of-service against the OAuth callback handler for an in-progress, legitimate authorization flow. An attacker who can get a victim's browser to issue a GET to the app's `/auth?shop=...` endpoint (trivial via CSRF, since `begin()` performs no CSRF protection on the request that starts the flow — that's its whole purpose) while the victim has a genuine OAuth flow open in another tab/frame will overwrite the victim's `shopify_app_state` cookie. When the victim's legitimate flow reaches `callback()`, `safeCompare(query.state!, stateFromCookie)` fails and the library throws `ShopifyErrors.InvalidOAuthError`, aborting the victim's installation/login attempt. This does not grant the attacker a forged session or cross-tenant access (the two flows' access tokens are independently minted via `postResponse` to Shopify, keyed by `code`, not by the cookie), so the effect is limited to disrupting a specific auth attempt.

### Likelihood Explanation
Likelihood is limited by the fact that exploitation requires precise timing (attacker request must land between the victim's `begin()` and `callback()`), and the impact is only a failed OAuth attempt (the victim can simply retry) rather than data compromise. This is consistent with the original report's disposition ("won't fix — safe to assume two [flows] will never need to be committed in the same [window]"), and the maintainers' own doc comment for the sibling `SESSION_COOKIE_NAME` collision shows this class of collision is a known, accepted design tradeoff rather than an overlooked defect.

### Recommendation
Scope the OAuth state cookie per flow (e.g., include a per-request nonce suffix in the cookie name, or scope by `shop`/`callbackPath+shop`) similar to the `cookiePath` mitigation already offered for `SESSION_COOKIE_NAME`, so concurrent flows for different shops (or repeated flows for the same shop) do not clobber each other's CSRF state.

### Proof of Concept
1. Victim visits `https://app.example.com/auth?shop=legit-shop.myshopify.com`; `begin()` sets `shopify_app_state=<nonce1>` cookie (path=`callbackPath`).
2. Before the victim completes the redirect back to `callbackPath`, an attacker-controlled page causes the victim's browser to load `https://app.example.com/auth?shop=attacker-shop.myshopify.com` (e.g., via a hidden `<img>`/`<iframe>`), triggering another `begin()` that overwrites `shopify_app_state` with `<nonce2>`.
3. The victim's browser is redirected back from Shopify to `callbackPath?state=<nonce1>&...`; `callback()` reads the cookie (`<nonce2>`) and compares it to `<nonce1>` — mismatch — throws `ShopifyErrors.InvalidOAuthError`, aborting the victim's legitimate authorization.

*Note: I could not fully verify runtime cookie-jar semantics for identically-named/path cookies across different `shop` values in every supported adapter (Express/Remix/Cloudflare) within the available index; behavior may vary slightly by cookie library defaults, but the code shows no shop-specific discriminator is added to the cookie key in `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`.*
