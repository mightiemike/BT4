## Finding confirmed: mint/reward-map desynchronization when a reward epoch has zero reward-eligible validators

### Title
Inflation credited to protocol treasury without a matching increase to `minted_amount` when all validators are excluded from an epoch's reward stats — supply-accounting divergence analogous to "stuck emissions for nullified epochs" - (File: `chain/epoch-manager/src/reward_calculator.rs`)

### Summary
`RewardCalculator::calculate_reward` computes `epoch_protocol_treasury` and inserts it into the returned `rewards_map` *before* checking whether there are any reward-eligible validators. If `validator_block_chunk_stats` (the per-epoch reward-tracking stats, from which validators removed for `NotEnoughBlocks`/`NotEnoughChunks`/`NotEnoughChunkEndorsements` are stripped) is empty, the function returns early with `(res, Balance::ZERO)` — the map still contains the non-zero treasury entry, but the returned `epoch_actual_reward` (which becomes `EpochInfo::minted_amount`) is `Balance::ZERO`. [1](#0-0) 

### Finding Description
`calculate_reward` is invoked once per epoch boundary by `EpochManager::finalize_epoch`, using `total_supply` and `max_inflation_rate` from the epoch's last block. [2](#0-1) 

Before the `num_validators == 0` early return, `epoch_protocol_treasury` is already written into `res`, the same map that becomes `EpochInfo::validator_reward`. The early return only zeroes the aggregate `epoch_actual_reward`, not the per-account map:

```
res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury);
if num_validators == 0 {
    return (res, Balance::ZERO);
}
``` [3](#0-2) 

Two independent values flow from this call downstream:

1. `epoch_actual_reward` (renamed `minted_amount`) is stored on the next `EpochInfo` and later added to `total_supply` at the epoch's first block (`new_total_supply = prev.total_supply + minted_amount - balance_burnt`). [4](#0-3) 

2. The full `res` map (including the treasury entry) is stored as `EpochInfo::validator_reward` and later read by `NightshadeRuntime::process_state_update` via `compute_stake_return_info`, which builds `ValidatorAccountsUpdate.validator_rewards` from that same map, independent of `minted_amount`. [5](#0-4) 

At apply time, `Runtime::update_validator_accounts` credits the protocol-treasury account's actual on-chain `amount` directly from `validator_accounts_update.validator_rewards`, with no reference to `minted_amount` at all: [6](#0-5) 

So in the `num_validators == 0` case: the treasury account is credited `epoch_protocol_treasury` tokens on-chain, while the block's `minted_amount` used for the `total_supply` update is `Balance::ZERO`. This causes the chain's recorded `total_supply` to diverge from the true sum of on-chain balances by exactly `epoch_protocol_treasury` — silent, uncounted inflation, or equivalently a permanent accounting drift between `total_supply` (verified at consensus-finality) and reality.

`validator_block_chunk_stats` becomes empty specifically because `finalize_epoch`/`compute_validators_to_reward_and_kickout` strips validators kicked for `NotEnoughBlocks`/`NotEnoughChunks`/`NotEnoughChunkEndorsements` from the reward stats before calling `calculate_reward`. [7](#0-6) 

The "never kick everyone" safety valve (`all_kicked_out` guard) only prevents the *validator set itself* from being emptied by restoring one validator's kickout removal from `validator_kickout`; it operates on `validator_kickout`, the set used for the *next* validator selection, not on the *already-computed* `validator_block_chunk_stats`/reward-stats map consumed by `calculate_reward` for the *current* reward tally. This is the mechanism by which every validator's chunk/block ratio could fall below its kickout threshold in the same epoch while stake, uptime data, and the guard's effects apply to different downstream artifacts — leaving the reward-stats input to `calculate_reward` legitimately empty even though a validator set continues to exist.

### Impact Explanation
This is a supply-integrity/accounting bug: the protocol treasury account receives real, spendable NEAR tokens that are not reflected in `total_supply`. `total_supply` is a consensus-critical, cross-node-verified quantity (per the economics spec, "consensus-finality verifies total supply"), so any divergence between the credited balance and the tracked supply is a real accounting/inflation-integrity violation — extra value is created and becomes spendable by the treasury account without being accounted for in the chain's canonical total-supply ledger. This satisfies the "supply inflation" / "invalid state transition acceptance" category, since the state transition that is accepted (treasury credited, `total_supply` unchanged) does not conserve the protocol's invariant `new_total_supply = prev.total_supply + minted_amount - balance_burnt` in terms of actual token movement.

### Likelihood Explanation
Reaching `num_validators == 0` requires every account counted in `validator_block_chunk_stats` for the epoch (i.e., every validator that is not already exempted by the kickout stake cap) to be removed from reward stats via `NotEnoughBlocks`/`NotEnoughChunks`/`NotEnoughChunkEndorsements` kickout reasons. This is a rare, validator-availability-dependent condition (widespread outage/downtime across the whole active set) rather than something a single unprivileged transaction can trigger deterministically in one step; it depends on chain-wide liveness conditions over an epoch, not on adversarial code that any RPC caller/contract can invoke directly. Given the difficulty of confirming with certainty (via code alone) that this exact path is reachable purely through validator/staking transactions without additional validator-node cooperation, this should be treated as low-to-moderate likelihood, and I could not fully verify within the available exploration whether the described removal from reward stats happens strictly before or fully independent from the "never kick everyone" stake-cap exemption for every account in the same epoch.

### Recommendation
In `RewardCalculator::calculate_reward`, do not insert `epoch_protocol_treasury` into `res` until after confirming reward-eligible validators exist, or explicitly zero the treasury entry (and any other map entries) when `num_validators == 0`, so that the returned map and the returned `epoch_actual_reward`/`minted_amount` stay consistent. Alternatively, change `update_validator_accounts` / `compute_stake_return_info` to derive the actually-credited treasury reward strictly from `minted_amount`-consistent bookkeeping rather than reading independently from the `validator_reward` map so a mismatch cannot silently inflate a real account balance.

### Proof of Concept
1. Drive an epoch where every validator counted toward the reward stats accumulates `produced/expected` ratios below `block_producer_kickout_threshold`/`chunk_producer_kickout_threshold` (or, for chunk-validator-only accounts, below `chunk_validator_only_kickout_threshold`) simultaneously, causing all such accounts to be kicked from the epoch's reward-stats bookkeeping (`lib.rs:829`-equivalent removal before `calculate_reward` is invoked), matching the scenario exercised (with a single validator) by `RewardCalculator::calculate_reward`'s own unit test showing the early-return behavior. [8](#0-7) 
2. Observe that `calculate_reward` returns `(res, Balance::ZERO)` where `res` still contains `protocol_treasury_account -> epoch_protocol_treasury > 0`.
3. At the epoch's first block, `EpochInfo::minted_amount()` is `Balance::ZERO`, so `new_total_supply = prev_total_supply - balance_burnt` (no inflation added), per the total-supply formula. [4](#0-3) 
4. `NightshadeRuntime::process_state_update` nonetheless builds `ValidatorAccountsUpdate { validator_rewards: {treasury: epoch_protocol_treasury, ...}, ... }` from the stored `EpochInfo::validator_reward` map. [5](#0-4) 
5. `Runtime::update_validator_accounts` credits the treasury account's `amount` by `epoch_protocol_treasury`, unconditionally on `minted_amount`. [6](#0-5) 
6. The treasury account's on-chain balance is now `epoch_protocol_treasury` higher than before, while the chain's tracked `total_supply` did not increase — a permanent divergence between recorded supply and actual token balances.

    pub fn calculate_reward(
        &self,
        validator_block_chunk_stats: HashMap<AccountId, BlockChunkValidatorStats>,
        validator_stake: &HashMap<AccountId, Balance>,
        total_supply: Balance,
        _protocol_version: ProtocolVersion,
        epoch_duration: u64,
        online_thresholds: ValidatorOnlineThresholds,
        max_inflation_rate: Rational32,
    ) -> (HashMap<AccountId, Balance>, Balance) {
        let mut res = HashMap::new();
        let num_validators = validator_block_chunk_stats.len();
        let use_hardcoded_value = self.genesis_protocol_version == PROD_GENESIS_PROTOCOL_VERSION;
        let protocol_reward_rate = if use_hardcoded_value {
            Rational32::new_raw(1, 10)
        } else {
            self.protocol_reward_rate
        };
        let epoch_total_reward = Balance::from_yoctonear(
            (U256::from(*max_inflation_rate.numer() as u64)
                * U256::from(total_supply.as_yoctonear())
                * U256::from(epoch_duration)
                / (U256::from(self.num_seconds_per_year)
                    * U256::from(*max_inflation_rate.denom() as u64)
                    * U256::from(NUM_NS_IN_SECOND)))
            .as_u128(),
        );
        let epoch_protocol_treasury = Balance::from_yoctonear(
            (U256::from(epoch_total_reward.as_yoctonear())
                * U256::from(*protocol_reward_rate.numer() as u64)
                / U256::from(*protocol_reward_rate.denom() as u64))
            .as_u128(),
        );
        res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury);
        if num_validators == 0 {
            return (res, Balance::ZERO);
        }
