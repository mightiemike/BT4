### Title
Unbounded full-table iteration in `/wallet/getassetissuelist` enables asymmetric-cost DoS - ([File: framework/src/main/java/org/tron/core/services/http/GetAssetIssueListServlet.java])

### Finding Description
`GetAssetIssueListServlet.doGet`/`doPost` call `wallet.getAssetIssueList()` with no offset/limit parameters, unlike the sibling `GetPaginatedAssetIssueListServlet` which requires `offset`/`limit` and caps `limit` via `ASSET_ISSUE_COUNT_LIMIT_MAX` in `AssetIssueStore.getAssetIssuesPaginated`. [1](#0-0) 

The unpaginated path ultimately reaches `AssetIssueStore.getAllAssetIssues()`, which streams the *entire* underlying key-value store (`iterator()` over the whole column family) into a `List` on every single call, with no bound on size: [2](#0-1) 

By contrast, the paginated variant sorts and slices, but still first materializes the same full `getAllAssetIssues()` list before slicing — so even the "paginated" endpoint pays the O(n) iteration/sort cost, though this question is scoped to the non-paginated servlet. [3](#0-2) 

`GetAssetIssueListServlet` extends `RateLimiterServlet`, which throttles by request *count/rate*, not by *cost per item* — there is no mechanism to charge more or throttle harder as the number of asset issues in the store (and hence per-request iteration cost) grows.

An unprivileged attacker can grow `n` (the number of `AssetIssueContract` entries) by broadcasting `AssetIssueContract` creation transactions signed with their own funded account — this does not require any privileged role, only paying the standard bandwidth/asset-issue fee, which is a one-time, bounded cost per asset created (no on-chain code path found here charges a *per-query* fee back to the HTTP caller of `getassetissuelist`, since it's a read-only GET/POST API call, not a chain transaction). Once the store is inflated, every subsequent unauthenticated call to `/wallet/getassetissuelist` re-iterates and re-serializes the full growing dataset, creating a repeatable, low-cost-to-attacker, linear (or worse, due to serialization/GC) CPU and I/O cost to the node for each request.

### Impact Explanation
This is a Denial-of-Service via RPC-API: an unbounded, attacker-influenced iteration over a store whose size the attacker directly controls, exposed on a public HTTP endpoint with no pagination and no adaptive per-item throttling. Repeated calls after inflating the asset-issue table can degrade full-node CPU and response latency for all API consumers, and — combined with `RateLimiterServlet`'s coarse rate-only limiting — does not scale its cost accounting to the actual work performed per request.

### Likelihood Explanation
- No privileged role needed: any funded account can submit `AssetIssueContract` transactions to grow `AssetIssueStore`; any anonymous client can call the HTTP endpoint repeatedly.
- The inflate step has real but bounded and one-time cost (issuance fee + bandwidth per asset); the exploit step (repeated GETs) is free/cheap and repeatable indefinitely.
- No fork gate, permission check, or existing rate limiter mitigates the per-item iteration cost — `RateLimiterServlet` only limits calls per time window, not cost-weighted throughput.
- Feasibility is realistic on any full node running default configuration exposing the HTTP API (which is default-enabled per `FullNodeHttpApiService`).

### Recommendation
- Enforce pagination (offset/limit with a hard maximum, as already used in `GetPaginatedAssetIssueListServlet`/`ASSET_ISSUE_COUNT_LIMIT_MAX`) on `GetAssetIssueListServlet`, or deprecate/disable the unpaginated endpoint by default.
- Avoid materializing the full store into memory before slicing in `AssetIssueStore.getAssetIssuesPaginated`; use a bounded iterator/cursor instead of `getAllAssetIssues()` + sort + subList.
- Add a per-request cost-aware limiter (e.g., based on current asset-issue count) to `RateLimiterServlet` or a dedicated guard for known O(n) endpoints.

### Proof of Concept
```java
// JUnit-style PoC against a test DB (chainbase/AssetIssueStore)
@Test
public void testUnboundedAssetIssueListCost() {
  int n = 100_000;
  for (int i = 0; i < n; i++) {
    AssetIssueCapsule capsule = buildDummyAssetIssueCapsule("token" + i);
    assetIssueStore.put(capsule.createDbKey(), capsule);
  }

  long start = System.nanoTime();
  List<AssetIssueCapsule> all = assetIssueStore.getAllAssetIssues(); // == wallet.getAssetIssueList() path
  long elapsed = System.nanoTime() - start;

  assertEquals(n, all.size());
  // Expected: elapsed grows ~linearly with n; repeated HTTP GET /wallet/getassetissuelist
  // calls will incur this same cost every time, with no query fee charged to caller
  // and no adaptive throttling in RateLimiterServlet.
}
```
Request-level reproduction: after issuing N `AssetIssueContract`s via signed transactions from a funded account, repeatedly call `curl http://<node>:8090/wallet/getassetissuelist` and observe response latency/CPU scaling with N, with each call succeeding and no per-item fee or adaptive rejection.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
