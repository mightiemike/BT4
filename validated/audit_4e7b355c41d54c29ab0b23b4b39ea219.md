## Analysis

The reported bug class (assuming an external callback executes successfully, and unconditionally reverting/failing the whole operation if it doesn't) has a concrete, reachable analog in the NEAR Wallet Contract's ERC-20 emulation callback flow.

### Title
Callback Gas Starvation on Untrusted Target Response Permanently Bricks the Wallet Contract's `has_in_flight_tx` Flag - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::nep_141_storage_balance_callback` (and its sibling callbacks) assume that the cross-contract call they depend on will always complete cheaply enough to let the callback finish and reset `has_in_flight_tx`. If the callback receipt itself fails (e.g. runs out of its statically-allocated prepaid gas while parsing an oversized/malformed response from the `target` contract), the whole receipt — including the `self.has_in_flight_tx = false` state write — is rolled back, per the runtime's per-receipt rollback semantics. Because `has_in_flight_tx` is only ever reset inside these callbacks, the wallet becomes permanently unable to process `rlp_execute` again.

### Finding Description
`rlp_execute` guards re-entrancy with `has_in_flight_tx`, which is only cleared inside the promise callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), each of which sets it to `false` as their first statement. [1](#0-0) [2](#0-1) 

For the ERC-20 emulation path, the wallet contract issues a `storage_balance_of` cross-contract call to the token contract identified by the transaction's `target`, and processes the result inside `nep_141_storage_balance_callback`, which is allocated only `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (5 Tgas base + storage-deposit gas + rlp_execute_callback gas): [3](#0-2) [4](#0-3) 

The `target` account (the token contract) is derived from the signed Ethereum transaction's `to` field / address registrar lookup and is not restricted to a fixed, trusted allow-list of tokens — any account can be the ERC-20 `target`: [5](#0-4) 

Per the runtime's execution model, actions within a receipt execute atomically and, on any failure (including running out of prepaid gas), the entire receipt's state changes are rolled back: [6](#0-5) 

Therefore, if the token contract (chosen by the transaction's `target`) returns a `storage_balance_of` payload that is large or malformed enough that deserializing/processing it inside `nep_141_storage_balance_callback` exceeds the small statically-reserved callback gas, the callback receipt fails as a whole. This failure rolls back the `self.has_in_flight_tx = false` write that would have happened at the top of that function, while the earlier `rlp_execute` call already durably committed `has_in_flight_tx = true`. Since no other code path resets the flag, every subsequent call to `rlp_execute` immediately short-circuits with `"transaction already in progress"`: [7](#0-6) 

permanently disabling the wallet contract for that account.

### Impact Explanation
This results in a transaction-triggered, permanent denial of service for the wallet contract account: the account's `has_in_flight_tx` flag becomes stuck `true` forever, and `rlp_execute` (the sole entry point for the eth-implicit account to move funds or perform any action) becomes permanently unusable, effectively freezing all funds/functionality behind that wallet contract instance. This can be triggered by a single submitted transaction where the signer interacts with (or is tricked into interacting with) a token contract whose `storage_balance_of` response is oversized or expensive to deserialize relative to the fixed low gas budget reserved for the callback.

### Likelihood Explanation
Likelihood is realistic: the `target`/token contract is attacker- or third-party-controlled and not vetted by the wallet contract; the callback gas budget is a small, fixed constant (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) independent of the size of data the external contract can choose to return, so any token contract (malicious, buggy, or simply non-conforming to the expected `StorageBalance` schema/size) can trigger the gas-exhaustion/rollback path with a single call.

### Recommendation
Do not rely on a fixed, minimal gas allowance for the callback that must process attacker-influenced external data; either bound/validate the size of `storage_balance_of` responses before they are queued for deserialization, allocate gas margin proportional to potential worst-case response size, or restructure state updates so `has_in_flight_tx` is reset via a mechanism that cannot be rolled back by a downstream callback failure (e.g., reset it eagerly/idempotently, or use a timeout/self-healing recovery path rather than making the "in-flight" flag depend solely on successful completion of a data-dependent, gas-bounded callback.

### Proof of Concept
1. Attacker deploys (or an ordinary buggy) NEP-141 token contract whose `storage_balance_of` view returns a payload that is technically valid to call but expensive/large to pass through `serde_json::from_slice::<Option<StorageBalance>>` within `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`. [8](#0-7) 
2. The wallet contract owner (or a relayer on their behalf) submits an RLP-encoded ERC-20 `transfer` transaction targeting that token via `rlp_execute`, which sets `has_in_flight_tx = true` and schedules `storage_balance_of` → `nep_141_storage_balance_callback`. [9](#0-8) 
3. The callback receipt exceeds its prepaid gas while processing the oversized/malformed response and fails as a whole, rolling back the `has_in_flight_tx = false` write.
4. All future `rlp_execute` calls on that wallet contract now immediately fail with `"Error: transaction already in progress, please try again later."`, permanently. [7](#0-6)

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
