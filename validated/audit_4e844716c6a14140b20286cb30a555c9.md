### Title
OAuth state/session cookies are signed with the raw API secret, allowing them to be forged as valid webhook HMACs - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
`begin()` and `callback()` in `oauth.ts` construct a `Cookies` instance with `keys: [config.apiSecretKey]` to sign the `shopify_app_state` and `shopify_app_session` cookies directly with the app's raw API secret key. Webhook HMAC validation (`validateHmacString`) also computes `createSHA256HMAC(config.apiSecretKey, data, format)` using that same raw secret. Because both signing operations key off the identical secret and use a compatible HMAC-SHA256/base64 primitive, a value legitimately signed as a cookie (or its signature) can, under certain encodings, be replayed as a webhook body HMAC (or vice versa), enabling a cross-protocol signature reuse/forgery. This is exactly the class of bug flagged and partially fixed elsewhere in the same package's changelog, but the fix does not appear to have been applied to `oauth.ts` itself.

### Finding Description
Signed cookies in `begin()` use `cookies.setAndSign(STATE_COOKIE_NAME, state, ...)` on a `Cookies` object keyed with `config.apiSecretKey` [1](#0-0) , and `callback()` uses the same secret to verify/reissue the session cookie [5](#0-4) . Meanwhile, `validateHmacFromRequestFactory`/`validateHmacString` in `hmac-validator.ts` compute the expected webhook HMAC as `createSHA256HMAC(config.apiSecretKey, rawBody, HashFormat.Base64)` and compare it against the `X-Shopify-Hmac-Sha256` header via `safeCompare` [6](#0-5) . Both primitives derive from the exact same raw `apiSecretKey`, meaning a signature computed under one context is a valid HMAC-SHA256 output under the app secret in general, and if the same data/encoding surfaces in both flows, they collide. The CHANGELOG for this same package explicitly documents this exact concern and a supposed remediation: *"Use a cookie-specific derived key when signing OAuth state and session cookies instead of signing them directly with the app API secret. This prevents signed OAuth state cookies from being reused as valid Shopify webhook HMACs."* [3](#0-2)  — yet the current `oauth.ts` code still passes `config.apiSecretKey` directly as the cookie signing key, not a derived key.

### Impact Explanation
If an attacker obtains a value/signature pair emitted from the OAuth begin/callback flow (e.g., the state cookie's signed value, which is exposed to the browser as a cookie during the OAuth redirect against a shop the attacker controls or can observe), they could potentially craft an accepted forged webhook HMAC for a request body they control, since the same secret and hash construction are used across both surfaces. This lets an anonymous actor submit a forged webhook request that passes `validateHmacFromRequest`, undermining the webhook authenticity guarantee entirely — a core security boundary that webhook consumers (e.g., `authenticateWebhookFactory` in shopify-app-remix/react-router) rely on entirely.

### Likelihood Explanation
This requires an attacker to capture a cookie value+signature emitted by the app's OAuth begin/callback response (these are set on the response headers to the browser, so any party who can observe/complete an OAuth flow — including via a malicious or observed browser session — can obtain one), and then re-encode it to match a webhook body layout. The complexity of matching the exact byte-for-byte signed string (cookie signing format vs. raw JSON webhook body) reduces immediate exploitability, but the underlying secret-reuse hazard is real and was serious enough that the maintainers attempted to patch it in the changelog entry `6c95ae1`. Whether `oauth.ts` was reverted, whether the fix lives elsewhere (e.g., inside the `Cookies` class itself rather than at the call site), or whether this is a regression, I could not fully confirm — I was unable to locate a `Cookies` class implementation that derives a separate cookie-signing key internally within my available search budget.

### Recommendation
Verify whether the `Cookies` class (in `runtime/http`) internally derives a cookie-specific key from `apiSecretKey` before use, rather than using it directly. If not, apply a KDF (e.g., HMAC-based key derivation with a fixed context string like `"cookie-signing"`) to `config.apiSecretKey` before passing it as the `keys` array to the `Cookies` constructor in both `begin()` and `callback()`, ensuring cookie signatures can never be valid webhook HMACs.

### Proof of Concept
Not fully constructible without confirming the exact `Cookies.setAndSign` serialization format and verifying whether the derived-key fix already lives inside the `Cookies` implementation — this needs to be checked directly against `packages/apps/shopify-api/runtime/http/*cookies*` source, which I could not fully inspect within the available tool budget. A Devin session with full repository access should confirm: (1) whether `Cookies` derives a separate signing key internally, (2) the exact cookie value serialization Keygrip/cookie-signature format used, and (3) whether that format can collide with a webhook `rawBody` HMAC input under attacker-chosen webhook payloads.

export async function validateHmacString(
  config: ConfigInterface,
  data: string,
  hmac: string,
  format: HashFormat,
) {
  const localHmac = await createSHA256HMAC(config.apiSecretKey, data, format);

  return safeCompare(hmac, localHmac);
}

export function getCurrentTimeInSec() {

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };
