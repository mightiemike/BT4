## Title
Unchecked `u64` subtraction in `update_remaining_gas` can silently underflow/wrap - ([File: crates/blockifier/src/execution/execution_utils.rs])

## Summary
`update_remaining_gas` in the blockifier's execution utilities performs a raw, unchecked `u64` subtraction to deduct a call's consumed gas from the caller's remaining gas budget, rather than using `checked_sub` with an explicit panic/error path as is done everywhere else in the gas-accounting code (`GasCounter::spend`, `GasAmount::checked_sub`, `sierra_gas_to_steps_gas`, etc.). This is directly analogous to the reported firedancer QUIC bug class: an arithmetic subtraction that is not proven safe by construction and relies on invariants holding elsewhere in the code, with no defense-in-depth check at the point of subtraction.

## Finding Description [1](#0-0) 

```rust
pub fn update_remaining_gas(remaining_gas: &mut u64, call_info: &CallInfo) {
    *remaining_gas -= call_info.execution.gas_consumed;
}
```

This contrasts with the rest of the gas-tracking code in the same crate, which consistently guards subtractions against underflow with explicit checks or panics:
- `GasCounter::spend` uses `checked_sub(...).expect("Overuse of gas; should have been caught earlier")` [2](#0-1) 
- `GasAmount::checked_sub` [3](#0-2) 
- `sierra_gas_to_steps_gas` falls back to `GasAmount::ZERO` on underflow with a debug log rather than wrapping [4](#0-3) 
- The syscall dispatcher explicitly asserts against underflow before subtracting: "Sanity check for preventing underflow" [5](#0-4) 

In Rust, `u64` subtraction only panics in debug builds; in a release build (the configuration production sequencers run) `*remaining_gas -= gas_consumed` silently wraps around on underflow instead of panicking, producing a near-`u64::MAX` "remaining gas" value if `gas_consumed` ever exceeds `remaining_gas`. This mirrors the underlying bug class in the QUIC report: an unguarded subtraction whose safety depends entirely on an invariant enforced elsewhere (there, packet-size bounds; here, that a callback never reports consuming more gas than it was given).

## Impact Explanation
If this invariant is ever violated — e.g. due to a future change in gas accounting, a Cairo-native/Cairo-VM discrepancy in `gas_consumed` reporting, or a bug in a nested call's gas bookkeeping — a wraparound would grant an effectively unlimited gas budget to subsequent execution in the same call chain. That could let a transaction execute arbitrarily more computation than its resource bounds allow, breaking the fee/resource-accounting invariants that back bouncer weights and L2 gas billing, and could result in honest-node divergence if different node builds (debug vs. release) diverge in panic-vs-wrap behavior for the same transaction.

## Likelihood Explanation
I could not find a concrete, currently-reachable code path where `gas_consumed` exceeds `remaining_gas` at the call site of `update_remaining_gas` — the gas-limiting logic (`cap_remaining_gas`/`GasCounter::limit_usage`) is designed to prevent this, similar to how the QUIC report describes its bug as "not actually reachable today." I was unable to fully trace every call site invoking `update_remaining_gas` (only 2 references found in the same file) within the available indexing, so I cannot rule out an edge case (e.g., interaction with Cairo-native execution or partial call reverts) with full confidence.

## Recommendation
Replace the unchecked subtraction in `update_remaining_gas` with a checked/saturating operation consistent with the rest of the gas-accounting code, and panic or return an error explicitly (as `GasCounter::spend` does) if the underflow invariant is ever violated, so any regression fails loudly and safely instead of silently wrapping in release builds.

## Proof of Concept
Not established — I could not construct a concrete transaction or call sequence in which `call_info.execution.gas_consumed` exceeds `remaining_gas` at this call site with the tools and indexing available. This finding is reported as a defense-in-depth gap analogous to the reference bug, not as a proven, presently-exploitable underflow.

    sierra_builtin_gas_costs: &BuiltinGasCosts,
