## Analysis

The external advisory concerns `toolshed`'s `CopyCell<T>` having an `unsafe impl<T> Send for CopyCell<T>` with no bounds on `T`, letting non-`Send` data cross threads without synchronization and causing data races. The closest reachable analog in this sequencer codebase is in the storage crate's mmap-file backing store, which is used to append/read transactions, transaction outputs, state diffs, Sierra/CASM contract classes, and deprecated classes — all data written as a direct result of processing submitted transactions and declared classes.

`FileHandler<V, Mode>` wraps a raw pointer into the mmap region and is force-declared `Send`/`Sync` via unbounded unsafe impls, exactly like the toolshed pattern: [1](#0-0) 

The write path takes the `Mutex<MMapFile<V>>` and mutates the shared `mmap` buffer in place: [2](#0-1) 

But the read path (`Reader::get`, used by `RO` handlers) dereferences the **same underlying memory** through the raw `memory_ptr` field entirely outside the mutex, with no synchronization at all: [3](#0-2) 

Both the `RW` and `RO` handlers returned from `open_file` share the identical `mmap_ptr` and the same underlying `Arc<Mutex<MMapFile<V>>>`-backed memory: [4](#0-3) 

These handlers back concrete storage tables driven by transaction execution/block building — e.g. `append_state_diff`/`append_transaction`/`append_casm` from `FileHandlers<RW>` and corresponding `get_*_unchecked` reads: [5](#0-4) [6](#0-5) 

### Title
Unsynchronized raw-pointer reads racing with mutex-protected mmap writes in `FileHandler` (`unsafe impl Send/Sync` without adequate bounds) - (File: crates/apollo_storage/src/mmap_file/mod.rs)

### Summary
`FileHandler<V, Mode>` stores a raw `*const u8` pointer into a memory-mapped file and is manually marked `unsafe impl Send`/`unsafe impl Sync` for all `V`/`Mode`, mirroring the toolshed `CopyCell<T>` unsound-`Send` bug class. The `Writer::append` path mutates the mmap contents under a `Mutex<MMapFile<V>>`, while `Reader::get` dereferences the same memory through the un-guarded `memory_ptr` field with no lock and no atomic/fence synchronization, so writer and reader threads can race on the same backing buffer.

### Finding Description
`open_file` creates one shared `Arc<Mutex<MMapFile<V>>>` and clones the raw `mmap.as_ptr()` into both the `RW` and `RO` `FileHandler`s [7](#0-6) . `Writer::append` locks the mutex, writes serialized bytes directly into the mmap slice, calls `flush_async_range`, then releases the lock [8](#0-7) . `Reader::get`, however, builds a byte slice straight from `self.memory_ptr` and deserializes it — entirely without acquiring `mmap_file`'s mutex or any other synchronization primitive [9](#0-8) . Because the type is forced to be `Send + Sync` via unconditional unsafe impls rather than requiring proper interior synchronization on the pointer field, nothing in the type system (or the runtime) prevents a reader thread from observing a torn/partially-written value while a writer thread is concurrently copying bytes into the same underlying allocation — this is a textbook data race under the Rust/LLVM memory model, identical in class to the reported `CopyCell<T>` issue where `Send` was granted without the bounds needed to make cross-thread sharing sound.

### Impact Explanation
`FileHandler<RO>` backs reads of transactions, transaction outputs, thin state diffs, Sierra/CASM/deprecated contract classes used both by RPC-facing storage reads and by the block-building/execution pipeline (`get_state_diff_from_location`, `get_thin_state_diff_unchecked`, class/CASM loaders) [10](#0-9) [11](#0-10) . If a reader observes a torn write (e.g., during a class or state-diff append triggered by processing a declared class or executed transaction) it can either fail deserialization, or worse, silently deserialize a corrupted-but-well-formed byte sequence into a different `ThinStateDiff`/`CasmContractClass`/`Transaction`. Feeding wrong CASM/class bytes into execution or wrong state-diff bytes into commitment computation can produce a divergent execution result or an incorrect committed state root/block hash on the affected node relative to honest peers that didn't race — a correctness/consensus-safety issue, not just a crash.

### Likelihood Explanation
Triggering requires only ordinary write/append concurrency with a read against a location whose append is still in flight — this occurs naturally any time a node processes new transactions/declared classes while serving reads (e.g., another in-flight RO transaction or a concurrent state read) against the same mmap files, without any attacker-controlled synchronization needed beyond normal transaction submission causing appends. No privileged access is needed; a normal transaction sender or class declarer causes appends to these files as part of ordinary block processing.

### Recommendation
Do not grant blanket `unsafe impl Send`/`Sync` on `FileHandler`. Ensure reads only occur on data ranges guaranteed to have a happens-before relationship with the write that produced them (e.g., by requiring `Reader::get` to also acquire the `mmap_file` mutex, or by using an atomic/fence-based publication protocol so a `LocationInFile` is only handed to a reader after the write is guaranteed visible), and constrain the manual `Send`/`Sync` impls with the bounds actually required for soundness (e.g., `V: Send`/`Sync`, plus explicit reasoning for the raw pointer field), analogous to how `RemoteComponentClient` deliberately avoids ad-hoc unsafe impls in this same codebase [12](#0-11) .

### Proof of Concept
1. Open a storage instance and obtain both `FileHandlers<RW>` and `FileHandlers<RO>` via `open_storage_files`/`open_file` [13](#0-12) .
2. From thread A, repeatedly call `append_state_diff` (or `append_casm`/`append_transaction`) with large payloads that straddle a `growth_step` boundary, causing `grow()`/`flush()`/mutex-protected mmap writes [14](#0-13) .
3. From thread B, concurrently call `Reader::get` on a `LocationInFile` for data whose append on thread A has not yet completed/synchronized (e.g., a location returned to a coordinating structure prior to any fence), reading straight through `memory_ptr` without taking the lock [15](#0-14) .
4. Under ThreadSanitizer/Miri, this reproduces as a reported data race; on relevant hardware/compiler optimization scenarios it can yield deserialization of corrupted bytes into a wrong `ThinStateDiff`/`CasmContractClass`, producing divergent state relative to a node that didn't race.

    fn grow_file_if_needed(&mut self, offset: usize) {
        let mut mmap_file = self.mmap_file.lock().expect("Lock should not be poisoned");
        if mmap_file.size < offset + mmap_file.config.max_object_size {
            debug!(
                "Attempting to grow file. File size: {}, offset: {}, max_object_size: {}",
                mmap_file.size, offset, mmap_file.config.max_object_size
            );
            mmap_file.grow();
        }
    }

impl<V: ValueSerde + Debug> Writer<V> for FileHandler<V, RW> {
    fn append(&mut self, val: &V::Value) -> LocationInFile {
        trace!("Inserting object: {:?}", val);
        let serialized = V::serialize(val).expect("Should be able to serialize");
        let len = serialized.len();
        let offset;
        {
            let mut mmap_file = self.mmap_file.lock().expect("Lock should not be poisoned");
            offset = mmap_file.offset;
            trace!("Inserting object at offset: {}", offset);
            let mmap_slice = &mut mmap_file.mmap[offset..];
            mmap_slice[..len].copy_from_slice(&serialized);
            mmap_file
                .mmap
                .flush_async_range(offset, len)
                .expect("Failed to asynchronously flush the mmap after inserting");
            mmap_file.offset += len;
            mmap_file.should_flush = true;
        }
        let location = LocationInFile { offset, len };
        self.grow_file_if_needed(location.next_offset());
        location
    }
