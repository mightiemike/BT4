## No vulnerability found for this question.

**Reasoning summary:**

The claimed equality — "STX credited to a miner in fork A's chainstate at height H == STX credited to a possibly different miner in fork B's chainstate at height H, persisting after reorg" — does not hold as a real bug, because reward computation and account crediting are inherently fork-scoped by construction:

1. `NakamotoChainState::get_matured_miner_reward_schedules` resolves the matured tenure header via `Self::get_header_by_coinbase_height(chainstate_tx.deref_mut(), tip_index_hash, matured_coinbase_height)`, where `tip_index_hash` is fork-specific (derived from that fork's own consensus hashes/block ids). [1](#0-0) 

2. `StacksChainState::get_scheduled_block_rewards_at_block` looks up the `payments` table keyed by `index_block_hash`, which is `StacksBlockHeader::make_index_block_hash(consensus_hash, block_hash)` — this hash differs between fork A and fork B's tenures at the same coinbase height because the consensus hash (tied to the winning sortition) differs per fork. [2](#0-1) 

3. Crediting of the matured reward to a miner's balance happens inside `process_matured_miner_rewards` / `process_matured_miner_reward`, which is executed against a `ClarityTx` operating on that fork's own MARF trie root. Each fork maintains an independent MARF state keyed by its own chain of `StacksBlockId`s, so a balance credited while processing fork A's blocks exists only in the MARF nodes reachable from fork A's tip. [3](#0-2) 

4. When the node reorgs from fork A to fork B, `stx-get-balance` and all state reads resolve against the canonical tip's MARF root (fork B's), which was built from fork B's tenures and never incorporates fork A's Clarity state mutations. The `payments` table rows for fork A remain in SQLite but are unreachable/unqueried once the canonical tip and its `index_block_hash` lineage point to fork B — `get_scheduled_block_rewards_at_block` for fork B's matured tenure only returns fork B's payment row.

Because both the scheduling lookup key (`index_block_hash`, which encodes fork-specific consensus hash) and the actual balance-mutating MARF trie are strictly partitioned per fork, there is no mechanism by which a matured reward computed/persisted while validating fork A remains spendable or double-counted after the node's canonical tip moves to fork B. The equality holds: each fork's miner balance is independently derived from that fork's own header chain and MARF state, and reorg simply discards the non-canonical fork's trie state entirely, consistent with standard blockchain reorg semantics — this is not a defect introduced by `get_matured_miner_reward_schedules`/`get_scheduled_block_rewards_at_block` and does not require majority-stake or privileged conditions to bypass, meaning no minority-attacker-triggerable divergence exists here.

    /// Process matured miner rewards for this block.
    /// Returns the number of liquid uSTX created -- i.e. the coinbase
    pub fn process_matured_miner_rewards(
        clarity_tx: &mut ClarityTx<'_, '_>,
        miner_share: &MinerReward,
        users_share: &[MinerReward],
        parent_share: &MinerReward,
    ) -> Result<u128, Error> {
        let mut coinbase_reward = miner_share.coinbase;
        StacksChainState::process_matured_miner_reward(clarity_tx, miner_share)?;
        for reward in users_share.iter() {
            coinbase_reward += reward.coinbase;
            StacksChainState::process_matured_miner_reward(clarity_tx, reward)?;
        }

        // give the parent its confirmed share of the streamed microblocks
        assert_eq!(parent_share.total(), parent_share.tx_fees_streamed_produced);
        StacksChainState::process_matured_miner_reward(clarity_tx, parent_share)?;
        Ok(coinbase_reward)
    }
