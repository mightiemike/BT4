### Title
CREATE2 deterministic address collision allows front-running DoS of contract deployment - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
The java-tron TVM implementation of the `CREATE2` opcode computes contract addresses deterministically from `(sender, salt, keccak256(code))`, exactly the pattern flagged in the external report for the Gnosis Safe `createProxyWithNonce` deployment. Any unprivileged account that can predict this triple can pre-deploy a contract (or otherwise cause the target address to already hold contract code) at the target address before the legitimate deployer's transaction lands, causing the legitimate `CREATE2` call to fail and return zero, i.e. the same "front-run and block deployment" bug class described in the report.

### Finding Description
`create2Action` in `OperationActions.java` pops `value`, `inOffset`, `inSize`, and `salt` from the stack and calls `program.createContract2(...)`. [1](#0-0) 

`Program.createContract2` computes the target address deterministically via `WalletUtil.generateContractAddress2(senderAddress, salt.getData(), programCode)` and immediately calls `createContractImpl`. [2](#0-1) 

The address derivation is a straightforward hash of `sender || salt || keccak256(code)`, fully predictable off-chain by anyone who knows the deploying factory address, the salt, and the init code — precisely analogous to the deterministic `create2` scheme used by the Gnosis Safe `GnosisSafeProxyFactory.createProxyWithNonce`. [3](#0-2) 

Inside `createContractImpl`, if an account/contract already exists at the computed address (`contractAlreadyExists`), the code does not silently succeed — instead it sets a `BytecodeExecutionException` ("Trying to create a contract with existing contract address"), which propagates as a revert of the sub-call and results in `stackPushZero()` (CREATE2 returns the zero address, i.e. failure) to the caller. [4](#0-3) [5](#0-4) [6](#0-5) 

Because any TVM contract (deployed by any unprivileged account) is free to choose its own salt and target factory address it wishes to call `CREATE2` against, an attacker can precompute the same `(sender, salt, codehash)` triple used by a victim's pending factory-deployment transaction (observable in the mempool as an ordinary broadcast transaction, exactly as flagged in the original report for Ethereum-style front-running) and race a transaction that deploys arbitrary code to that same address first. When the victim's transaction is subsequently processed, `contractAlreadyExists` is `true` and the CREATE2 call in the victim's contract fails, blocking whatever multisig/committee/governance-style contract the victim was relying on `CREATE2` to set up — the same "block usage of a deterministically-deployed contract" impact described in the report for the Gnosis Safe fast-confirm committee.

This is not a defect in the CREATE2 semantics themselves (matching EVM/geth `create2` collision behavior is expected), but it is the same underlying bug class: any protocol or governance logic on top of java-tron's TVM that relies on `CREATE2` for deterministic, front-runnable deployment of security-critical infrastructure (e.g., a multisig committee, an oracle, or a controller contract) inherits this front-running DoS risk with no mitigation available at the VM layer — there is no built-in salt-uniqueness enforcement, commit-reveal, or private mempool consideration in java-tron's implementation.

### Impact Explanation
Impact is a targeted denial-of-service: an unprivileged attacker who observes a pending transaction that will call `CREATE2` (via mempool sniffing on the P2P/broadcast layer) can front-run it, causing the legitimate deployment to permanently fail at that predicted address (a new salt/nonce must be chosen and re-broadcast, itself again front-runnable). Any smart contract or protocol built on top of java-tron that relies on `CREATE2` for deploying access-control-critical infrastructure (e.g., proxy factories, multisig committee setup, escrow contracts) can have its setup blocked indefinitely by a griefing attacker, without requiring any special privilege — this maps to a DoS class impact via the RPC/broadcast-transaction path.

### Likelihood Explanation
High. Any account can call `CREATE2` from within a contract, and any pending transaction calling `CREATE2` with a fixed, guessable salt is visible in the mempool before confirmation, allowing straightforward front-running (as explicitly acknowledged as a still-open risk even after mitigation in the original report). No privileged role or leaked key is required — only the ability to observe pending transactions and pay for a competing transaction with higher priority/fee.

### Recommendation
- Application-level contracts that use `CREATE2` for deploying access-critical infrastructure (multisig committees, proxies, etc.) on java-tron should include sender-specific or otherwise unguessable salts (e.g., derived from `msg.sender` and a private nonce known only to the deployer) to reduce front-running predictability, and/or use commit-reveal patterns.
- Document, for contract authors targeting the TVM, that `CREATE2` collisions with existing contract code cause the call to fail (return zero) rather than silently overwrite, so DoS via address squatting is a known risk that must be mitigated in application-level salt selection — java-tron itself cannot fix this at the VM level without deviating from EVM-compatible `CREATE2` semantics.
- Consider recommending/providing a standard "safe factory" pattern in TRON tooling that incorporates deployer-address entropy into the salt to raise the cost of front-running (analogous to the mitigation adopted in the referenced Gnosis Safe governance action).

### Proof of Concept
1. Victim broadcasts a transaction that triggers a factory contract's function which internally executes `create2(0, codeOffset, codeSize, salt)` with a fixed, attacker-visible `salt` (e.g., `salt = 0` or a well-known value), targeting deployment of a committee/multisig contract at address `A = generateContractAddress2(factory, salt, initcode)`. [3](#0-2) 
2. Attacker observes the pending transaction in the mempool, computes the same address `A` off-chain using the same formula, and crafts/broadcasts their own `CREATE2` call from the same factory contract address with the same salt and same init-code hash (or otherwise causes contract code to exist at `A`, e.g. by triggering their own deployment through the same factory first) with higher energy/fee to be included first.
3. When the attacker's transaction lands first, `getContractState().getAccount(A)` returns a non-null account with deployed code, so `isContractExist(...)` returns `true` in the victim's subsequent transaction. [4](#0-3) 
4. The victim's `CREATE2` sub-call then hits the `contractAlreadyExists` branch, sets a `BytecodeExecutionException`, rejects internal transactions, and pushes zero onto the stack — the victim's governance/committee setup silently fails. [7](#0-6)

  public void createContract2(DataWord value, DataWord memStart, DataWord memSize, DataWord salt) {
    if (VMConfig.allowTvmOsaka()) {

    }

    byte[] senderAddress;
    if ((VMConfig.allowTvmCompatibleEvm() || VMConfig.allowTvmOsaka())
        && getCallDeep() == MAX_DEPTH) {
      stackPushZero();
      return;
    }
    if (getCallDeep() == MAX_DEPTH) {
      MUtil.checkCPUTimeForCreate2();
    }
    if (VMConfig.allowTvmIstanbul()) {
      senderAddress = getContextAddress();
    } else {
      senderAddress = getCallerAddress().toTronAddress();
    }
    byte[] programCode = memoryChunk(memStart.intValue(), memSize.intValue());

    byte[] contractAddress = WalletUtil
        .generateContractAddress2(senderAddress, salt.getData(), programCode);
    createContractImpl(value, programCode, contractAddress, true);
  }

  public static byte[] generateContractAddress2(byte[] address, byte[] salt, byte[] code) {
    byte[] mergedData = ByteUtil.merge(address, salt, Hash.sha3(code));
    return Hash.sha3omit12(mergedData);
  }
