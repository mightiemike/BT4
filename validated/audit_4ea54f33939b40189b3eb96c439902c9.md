### Title
Ballot early-rejection logic (`ShouldReject`) is dead code, letting split honest votes deadlock inbound/outbound finalization until expiry - (File: `x/uvalidator/types/ballot.go`)

### Summary
`x/uvalidator` implements a generic ballot machine used by every crosschain observation path (inbound, outbound, chain-meta, TSS events, fund migrations). The type defines two independent notions of ballot resolution: `ShouldPass`/`ShouldReject` (which detects the moment a passing outcome becomes mathematically impossible) and `IsFinalizingVote` (the actual production path invoked from `VoteOnBallot`/`CheckIfFinalizingVote`). `IsFinalizingVote` only checks `yesVotes >= threshold` or `noVotes >= threshold` — it never uses the "impossible-to-pass" logic in `ShouldReject`. This mirrors the audited bug class: a safety/finality condition that exists in the codebase and reads as protective, but is never exercised by the real execution path, creating a false sense of correctness.

### Finding Description
`x/uvalidator/types/ballot.go` defines two finalization surfaces: [1](#0-0) 

and the production one: [2](#0-1) 

`ShouldReject` computes `potentialYesVotes = len(EligibleVoters) - noVotes` and returns true the instant a YES outcome becomes impossible, even with votes still outstanding. `IsFinalizingVote`, which is the function actually called from `CheckIfFinalizingVote` in the live voting flow [3](#0-2) , instead requires `noVotes` itself to *reach the same supermajority threshold as YES* (`VotingThreshold`, computed as `2/3+1` per `x/uvalidator/keeper/ballot.go` L283 and the README) before rejecting.

Because both PASS and REJECT require the *same* `2/3+1` count, a ballot with all `EligibleVoters` having cast their vote can land in a state where neither `yesVotes >= threshold` nor `noVotes >= threshold` holds (e.g. 5 eligible voters, threshold 4, split 3 YES / 2 NO). At that point `ShouldReject` would correctly report the ballot as already dead (`potentialYesVotes = 5-2 = 3 < 4`), but that logic is never invoked in `VoteOnBallot`/`CheckIfFinalizingVote`. The ballot remains `BALLOT_STATUS_PENDING` in `ActiveBallotIDs` with no further voters able to change the outcome, until `BlockHeightExpiry` is reached and `MarkBallotExpired` is triggered on the next late vote attempt or pruning pass [4](#0-3) .

### Impact Explanation
This stalls finalization of the underlying crosschain observation (inbound tx, outbound tx, chain-meta update, TSS event, or fund migration — every consumer of the generic ballot machine per `x/uvalidator/README.md`) for the full `expiryAfterBlocks` window even though the vote outcome was already determined the moment the split became irreversible. This is a liveness/DoS defect reachable purely from honest, unprivileged, non-malicious voting behavior (UVs genuinely disagreeing on an observation, e.g. differing views of a source-chain event) — no compromised validator or privileged actor is required, satisfying the "denial of service...reachable without privileged control" allowed-impact category. It delays inbound settlement / outbound release / TSS event processing rather than causing fund loss directly, so severity is bounded by the ballot's `expiryAfterBlocks` window, not permanent.

### Likelihood Explanation
Requires a genuine 3-way-or-more vote split among eligible UVs where results diverge such that neither the YES nor NO count reaches the `2/3+1` threshold while some votes remain uncast or after all are cast. This is plausible whenever UVs momentarily disagree on an observation (e.g., due to source-chain view differences, timing, or reorgs) rather than requiring active malice, making it a realistic — if not everyday — occurrence in a live consensus system with dozens of UVs.

### Recommendation
Wire `ShouldReject` (or equivalent "potential YES votes < threshold" logic) into `IsFinalizingVote`/`CheckIfFinalizingVote` so that a ballot is proactively marked `BALLOT_STATUS_REJECTED` the moment a passing outcome becomes mathematically impossible, rather than only when NO votes themselves independently reach the pass-threshold. Alternatively, remove the unused `ShouldReject`/`ShouldPass` helpers if the team intends `IsFinalizingVote`'s symmetric-threshold behavior, and document explicitly that a full-turnout split ballot is expected to sit PENDING until expiry.

### Proof of Concept
1. Create a ballot with 5 `EligibleVoters` and `VotingThreshold = 4` (via `NewBallot`/`GetOrCreateBallot`, matching the `2/3+1` formula in `x/uvalidator/keeper/ballot.go` L283).
2. Have voters cast: 3 × `VOTE_RESULT_SUCCESS`, 2 × `VOTE_RESULT_FAILURE` (all 5 eligible voters have now voted).
3. Call `VoteOnBallot` for each vote as in `x/uvalidator/keeper/voting.go` L120-197; after the 5th vote, `CheckIfFinalizingVote`/`IsFinalizingVote` returns `isFinalizing = false` because `yesVotes(3) < 4` and `noVotes(2) < 4`.
4. Separately call `ballot.ShouldReject()` on the same state and observe it returns `true` (`potentialYesVotes = 5-2 = 3 < 4`), proving the ballot's outcome was already determined but the production path leaves it `PENDING`.
5. The ballot remains in `ActiveBallotIDs` and blocks re-voting (`already X` on subsequent identical votes) until `BlockHeightExpiry`, at which point it is force-marked `EXPIRED` rather than `REJECTED` per `x/uvalidator/keeper/voting.go` L148-167.

// ShouldPass returns true if the YES votes meet or exceed the stored voting threshold.
func (b Ballot) ShouldPass() bool {
	yesVotes, _ := b.CountVotes()
	return yesVotes >= int(b.VotingThreshold)
}

// ShouldReject returns true if the NO votes make it impossible to reach the threshold.
func (b Ballot) ShouldReject() bool {
	_, noVotes := b.CountVotes()
	potentialYesVotes := len(b.EligibleVoters) - noVotes
	return potentialYesVotes < int(b.VotingThreshold)
}

// IsFinalizingVote checks if the ballot is reaching the finalization in this tx
func (b Ballot) IsFinalizingVote() (Ballot, bool) {
	// Only pending ballots can still be finalized
	if b.Status != BallotStatus_BALLOT_STATUS_PENDING {
		return b, false
	}

	// Count votes
	yesVotes := 0
	noVotes := 0
	for _, v := range b.Votes {
		switch v {
		case VoteResult_VOTE_RESULT_SUCCESS:
			yesVotes++
		case VoteResult_VOTE_RESULT_FAILURE:
			noVotes++
		}
	}

	// If YES or NO has reached/exceeded threshold → finalizing
	if int64(yesVotes) >= b.VotingThreshold {
		b.Status = BallotStatus_BALLOT_STATUS_PASSED
		return b, true
	}
	if int64(noVotes) >= b.VotingThreshold {
		b.Status = BallotStatus_BALLOT_STATUS_REJECTED
		return b, true
	}

	return b, false
}

// CheckIfFinalizingVote inspects whether the just-cast vote pushes the ballot
// over its threshold and, if so, drives the finalization through
// MarkBallotFinalized — the single canonical write path for terminal status
// transitions, which applies CEI-style ordering on the secondary indexes.
func (k Keeper) CheckIfFinalizingVote(ctx context.Context, b types.Ballot) (types.Ballot, bool, error) {
	ballot, isFinalizing := b.IsFinalizingVote()
	if !isFinalizing {
		return b, false, nil
	}

	k.Logger().Debug("ballot reached finalization threshold",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)

	if err := k.MarkBallotFinalized(ctx, ballot.Id, ballot.Status); err != nil {
		return ballot, false, errors.Wrap(err, "failed updating finalized ballot")
	}

	k.Logger().Debug("ballot finalized",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)
	return ballot, true, nil
