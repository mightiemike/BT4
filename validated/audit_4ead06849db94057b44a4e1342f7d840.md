### Title
Mutable `GlobalByAccount` Global Contract Reference Allows Silent Code Substitution After Trust Is Established - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
NEAR's global-contract feature lets any account point its executable code at a contract published by another account via `GlobalContractIdentifier::AccountId`, using `UseGlobalContractAction`. Unlike the `CodeHash` mode (immutable), the `AccountId` mode is explicitly designed so the *publishing* account can redeploy new code under the same identifier at any later time, and every account that previously linked to it (`AccountContract::GlobalByAccount(id)`) will silently start executing the new code with no new transaction, consent, or on-chain verification from the linked account. This mirrors the PoolTogether `VaultFactory` finding: a "trusted-looking" composition primitive (an account using `UseGlobalContractAction`, analogous to deploying via the official `VaultFactory`) gives no protocol-level guarantee that the referenced dependency (`GlobalByAccount` contract, analogous to `TwabController`/`PrizePool`) remains authentic/immutable over time — the authenticity of the referenced code is left entirely to off-chain trust in the publishing account.

### Finding Description
`GlobalContractIdentifier::AccountId(AccountId)` is documented as intentionally mutable: "This allows the owner to update the contract for all its users." [1](#0-0) 

When an account calls `UseGlobalContractAction`, the runtime resolves the identifier and stores only a *reference* (`AccountContract::GlobalByAccount(id)`) — not a hash-pinned snapshot of the code: [2](#0-1) 

Any subsequent `DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` from the same publishing account overwrites the code stored under `TrieKey::GlobalContractCode { identifier: AccountId(...) }`: [3](#0-2) [4](#0-3) 

Every account with `AccountContract::GlobalByAccount(id)` transparently executes whatever code currently lives at that identifier the next time a `FunctionCall` is dispatched to it, with no re-validation, no notice, and no requirement that the linked account sign a new transaction: [5](#0-4) 

This is structurally identical to the reported bug class: a composition mechanism (`UseGlobalContractAction`, like `VaultFactory.deployVault`) lets an unprivileged account link its own execution semantics to an *unverified, third-party-controlled* dependency (the `AccountId`-addressed global contract, like `TwabController`/`PrizePool`), and the protocol provides no factory/registry-style guarantee that the referenced dependency's implementation remains what it originally appeared to be.

### Impact Explanation
Because linking is by mutable account identity rather than by immutable code hash, a malicious (or later-compromised) publisher account can:
- Publish an initially benign global contract, wait for other unprivileged accounts, dApps, wallets, or relayers to link to it (`UseGlobalContractAction`) or grant `FunctionCall` access keys targeting it, and later redeploy malicious code under the exact same `AccountId` identifier.
- Every account still referencing `AccountContract::GlobalByAccount(id)` will immediately begin executing the new, attacker-controlled logic on their next `FunctionCall` receipt — without any further signature or approval from the linked account.
- Depending on what the substituted logic does with attached deposits, cross-contract calls, or state transitions the account was relying on, this can lead to unauthorized value movement (deposits/attached NEAR redirected by the swapped code) or the account's contract logic becoming permanently unreliable/frozen relative to its intended behavior, since the account owner has no on-chain way to detect or prevent the swap besides re-issuing `UseGlobalContractAction` toward a different identifier after the fact.

### Likelihood Explanation
The `AccountId` deploy/use mode is a documented, fully reachable feature usable by any unprivileged account holding a full-access key, requiring no special privilege. The only precondition is that some victim account voluntarily executed `UseGlobalContractAction` referencing the attacker's `AccountId` at some point — a normal, expected usage pattern for the feature (e.g. to receive future logic upgrades from a trusted-looking publisher), making this readily reachable in production usage rather than a theoretical edge case.

### Recommendation
Consider one or more of:
- Encouraging/aiding wallets, indexers, and RPC consumers to surface prominently that `AccountId`-mode global contracts are mutable and to warn when the underlying code hash changes after a user has linked to it.
- Providing an explicit, cheap on-chain mechanism for a linked account to pin/verify the currently-referenced code hash at call time, or to be notified/blocked automatically if the referenced code hash changes unexpectedly.
- For sensitive integrations, recommending exclusive use of the immutable `CodeHash` deploy mode rather than `AccountId` mode, and documenting this trust distinction clearly at the protocol level (mirroring the "curation by front-ends" mitigation PoolTogether ultimately relied on).

### Proof of Concept
1. Account `owner.near` deploys a benign global contract in `AccountId` mode via `DeployGlobalContractAction { deploy_mode: AccountId }` (see `pytest/tests/contracts/deploy_call_global_smart_contract.py` for the reference flow). [6](#0-5) 
2. Victim account `victim.near` links to it: `UseGlobalContractAction { contract_identifier: AccountId(owner.near) }`, setting `AccountContract::GlobalByAccount(owner.near)` on its own account. [7](#0-6) 
3. Later, `owner.near` redeploys different (malicious) WASM code under the same `AccountId` identifier via another `DeployGlobalContractAction { deploy_mode: AccountId }`, overwriting `TrieKey::GlobalContractCode { identifier: AccountId(owner.near) }`. [8](#0-7) 
4. Any subsequent `FunctionCall` receipt sent to `victim.near` executes the newly substituted, attacker-controlled code — with no additional transaction, consent, or verification required from `victim.near`. [9](#0-8)

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}
