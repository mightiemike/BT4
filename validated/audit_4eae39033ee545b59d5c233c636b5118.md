### Title
Exchange pool sandwich attack around `ExchangeInjectContract`/`ExchangeWithdrawContract` price-changing transactions - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
java-tron's built-in Bancor-style TRC10 `Exchange` feature is analogous to the Unitas oracle-swap sandwich bug class: a broadcast transaction that changes the exchange pool's price ratio (`ExchangeInjectContract` / `ExchangeWithdrawContract`, submitted by the exchange creator) is publicly visible in the mempool before it is packed into a block, allowing any unprivileged attacker to sandwich it with two `ExchangeTransactionContract` swaps to extract value from the pool, mirroring the "front-run + back-run a price update" pattern described in the external report.

### Finding Description
The `Exchange` module implements an on-chain constant-supply/Bancor relay market between two TRC10 tokens (or TRX and a TRC10 token). Swaps go through `ExchangeCapsule.transaction()`, which uses `ExchangeProcessor`/`SafeExchangeProcessor` to price a swap purely from the current `firstTokenBalance`/`secondTokenBalance` ratio stored in the `ExchangeCapsule`. [1](#0-0) 

The pool ratio (i.e., the "price") can be shifted at will by the exchange creator via `ExchangeInjectActuator` (adds liquidity, recalculating `anotherTokenQuant` from the current ratio) and `ExchangeWithdrawActuator` (removes liquidity, likewise recalculated from the current ratio): [2](#0-1) [3](#0-2) 

Both actuators only require that the caller is the exchange creator; there is no atomicity guarantee that prevents other transactions from interleaving with the inject/withdraw transaction in the same block or before it is confirmed: [4](#0-3) 

Any account can submit an `ExchangeTransactionContract` swap at any time using `ExchangeTransactionActuator.execute()`, which resolves the trade using whatever pool ratio exists at execution time: [5](#0-4) 

This is structurally identical to the Unitas bug class: a state-changing transaction that moves the price (here, `ExchangeInject`/`ExchangeWithdraw`, analogous to the oracle "Feeder" price update) sits visibly in the mempool before confirmation, and an unprivileged attacker can submit two `ExchangeTransactionContract` swaps — one immediately before, one immediately after — to buy the underpriced/oversupplied token pre-update and sell it back post-update at the new ratio, extracting the imbalance from the pool's assets, which are ultimately backed by the exchange creator's and other participants' deposited tokens/TRX.

### Impact Explanation
An attacker observing a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` in the mempool (or simply timing swaps around routine liquidity operations) can sandwich it with two `ExchangeTransactionContract` swaps to extract value from the pool, at the expense of the pool's liquidity/collateral. This is asset/accounting corruption via the exchange market-math actuators, reachable purely through anonymous, unprivileged broadcast transactions, matching the accepted-as-High classification of the analogous Unitas report (profit extraction + collateral drain via price-update sandwiching).

### Likelihood Explanation
Any account can submit `ExchangeTransactionContract` transactions with no special permission, and block producers (or the attacker itself, if colluding with/being an SR, or simply via standard mempool observation and gas/ordering games akin to typical TRON MEV) can order transactions within a block. Exploitability depends on the size of the inject/withdraw relative to pool depth and the swap fee/slippage built into the Bancor formula, similar to the "usually small % change" mitigating argument raised for the Unitas case — but the underlying mechanism is present and reachable without any privileged role beyond being the pool's own creator triggering routine liquidity management.

### Recommendation
- Consider enforcing that `ExchangeInject`/`ExchangeWithdraw` operations cannot be sandwiched, e.g., by applying inject/withdraw with a TWAP or previous-block price rather than the instantaneous same-block ratio, or by bounding the maximum ratio delta a single inject/withdraw can cause within one block.
- Consider adding a minimum-received/maximum-slippage style protection consistent with `ExchangeTransactionActuator`'s existing `tokenExpected` check so pool-side moves cannot silently worsen swap outcomes beyond a bound the counterparty accepted.
- Evaluate rate-limiting or same-block ordering constraints between `ExchangeInject`/`ExchangeWithdraw` and `ExchangeTransaction` contracts touching the same `exchangeId`.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeWithdrawContract` withdrawing a large share of `firstTokenBalance`, which recomputes `anotherTokenQuant` from the current ratio and shifts the effective exchange rate (see `ExchangeWithdrawActuator.execute()`, lines 77–89).
2. Attacker observes this transaction in the mempool and submits `ExchangeTransactionContract` swapping token A → token B with gas/ordering set to land just before the withdraw is confirmed, buying token B cheaply against the pre-withdraw ratio.
3. The withdraw transaction executes, shifting `firstTokenBalance`/`secondTokenBalance` and thus the effective price via `ExchangeCapsule.transaction()`.
4. Attacker submits a second `ExchangeTransactionContract` swapping token B back to token A immediately after, realizing the price differential as profit extracted from the pool, exactly mirroring the "swap before / update / swap after" pattern in the source report.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
