This confirms the root cause: since `frozenCount` must be `0` or `1` [1](#0-0) , each account holds exactly one merged `Frozen` entry per resource type, and unfreeze eligibility is gated purely on that single entry's `expireTime <= now` [2](#0-1) .

### Title
Freeze-lock duration bypass via expire-time overwrite on repeated FreezeBalanceContract deposits - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java)

### Summary
`FreezeBalanceActuator.execute()` merges a new freeze deposit's TRX amount into the account's existing frozen balance for a resource (BANDWIDTH/ENERGY/TRON_POWER), but unconditionally overwrites the single stored `expireTime` with the new deposit's `now + duration`, instead of taking the maximum of the old and new expire times. This lets any account holder shorten (or lengthen) the effective unlock time of their entire previously-frozen balance by issuing an additional small `FreezeBalanceContract` transaction with a different duration.

### Finding Description
When freezing TRX for BANDWIDTH, the actuator computes `expireTime = now + duration` for the incoming deposit and calls `accountCapsule.setFrozenForBandwidth(newFrozenBalanceForBandwidth, expireTime)`, where `newFrozenBalanceForBandwidth` is the sum of the new and any pre-existing frozen balance, but `expireTime` is derived only from the new deposit's duration [3](#0-2) . The same pattern is repeated for ENERGY [4](#0-3)  and TRON_POWER [5](#0-4) , and is duplicated in the TVM-reachable native-contract path used by the `freeze` opcode [6](#0-5) .

Because the account model only supports a single merged `Frozen{frozenBalance, expireTime}` record per resource (enforced by the `frozenCount must be 0 or 1` check) [1](#0-0) , this is exactly the "share lock extension/overwrite on subsequent deposits" bug class from the report: a per-user (per-resource) lock timestamp is stored rather than per-deposit, and every new deposit overwrites it. In the vault report this manifested as unwanted lock *extension*; here it manifests as an unwanted lock *reduction*: a user who froze a large amount for a long `frozenDuration` (e.g. close to `maxFrozenTime`) can subsequently submit a second `FreezeBalanceContract` for the same resource with the minimum allowed `frozenDuration` (`minFrozenTime`, e.g. 3 days) and 1 TRX. This overwrites the whole accumulated balance's `expireTime` to `now + minFrozenTime`, which is earlier than the original commitment. `UnfreezeBalanceActuator`/`UnfreezeBalanceProcessor` validate unfreeze eligibility solely against this single overwritten `expireTime` [7](#0-6) , so the entire previously-committed balance becomes unfreezable far earlier than intended.

### Impact Explanation
The freeze/unfreeze duration is the mechanism by which TRON enforces a minimum stake-commitment period for BANDWIDTH, ENERGY, and TRON_POWER (voting weight). Bypassing that commitment lets any account artificially shorten the lock on an arbitrarily large frozen balance for the cost of a minimal top-up deposit, undermining assumptions built on frozen-duration commitments (e.g., resource/weight stability used for network accounting, `totalNetWeight`/`totalEnergyWeight`, and voting power stability during governance windows). This is reachable by any unprivileged account via a plain broadcast transaction (`FreezeBalanceContract`) or via a smart contract using the `freeze`/`FREEZE` opcode, requiring no special privileges.

### Likelihood Explanation
High likelihood: the path is trivially reachable by any account with existing frozen balance by simply broadcasting a second `FreezeBalanceContract` transaction (or invoking the `freeze` TVM opcode) with a shorter `frozenDuration`, no elevated permissions or unusual preconditions are needed.

### Recommendation
When merging a new freeze deposit into an existing frozen balance, compute the new `expireTime` as `max(existingExpireTime, now + newDuration)` instead of unconditionally overwriting it, for all three code paths (`FreezeBalanceActuator`, and the equivalent logic in `FreezeBalanceProcessor`). This preserves the intended stake-lock guarantee regardless of the number or size of subsequent top-up freezes.

### Proof of Concept
1. Account A freezes `1000 TRX` for `BANDWIDTH` with `frozenDuration = maxFrozenTime` (e.g., far in the future), setting `Frozen{frozenBalance=1000, expireTime=now+maxFrozenTime}`.
2. Shortly after, Account A submits another `FreezeBalanceContract` for `BANDWIDTH` with `frozenBalance = 1 TRX` (minimum) and `frozenDuration = minFrozenTime`.
3. `FreezeBalanceActuator.execute()` sets `newFrozenBalanceForBandwidth = 1001` and `expireTime = now + minFrozenTime`, overwriting the previous long-duration commitment [3](#0-2) .
4. After `minFrozenTime` elapses, Account A calls `UnfreezeBalanceContract`; `UnfreezeBalanceActuator.validate()` sees `expireTime <= now` on the single merged entry and allows unfreezing the full `1001 TRX` [7](#0-6) , well before the originally committed `maxFrozenTime` lock would have expired.
