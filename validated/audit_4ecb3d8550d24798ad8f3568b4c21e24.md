### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant webhook spoofing that triggers another shop's session/installation removal - (File: packages/apps/shopify-api/lib/webhooks/validate.ts)

### Summary
The Realitycards finding shows that `removeUserFromOrderbook` trusted a caller-supplied identity/target without restricting who may invoke it, letting an attacker trigger removal of a *different* user. The analogous root cause in shopify-app-js is that webhook authenticity is verified solely by hashing the raw request body with the app's shared API secret, while the `shop`/`domain` value used to decide **which tenant's session/installation gets deleted** is read from an HTTP header that is excluded from that HMAC computation. Any party who can obtain one validly-signed webhook body (e.g., their own shop's `APP_UNINSTALLED` webhook, which every merchant legitimately receives once they install/uninstall the app) can replay that same valid body while substituting the shop-domain header to point at a victim shop, and the app will treat it as an authentic webhook for the victim.

### Finding Description
- `validateHmacFromRequestFactory` computes the local HMAC only from `rawBody` and compares it against the `X-Shopify-Hmac-Sha256` (or events-equivalent) header — headers other than the HMAC header are never part of the signed data: [1](#0-0) 
- `checkWebhooksHeaders` (used by `shopify.webhooks.validate`/`process` after the HMAC check passes) reads the `domain` (shop) straight from the `X-Shopify-Shop-Domain` request header, with no cross-check against the signed body: [2](#0-1) 
- `validateFactory` orchestrates this: it runs `detectWebhookType`, then `validateHmacFromRequestFactory` (body-only HMAC check), and only afterward calls `checkWebhookHeaders`, which trusts the header-supplied `domain`: [3](#0-2) 
- The `shop`/`domain` value produced here flows directly into consuming code as the tenant identifier. In `shopify-app-express`, the built-in `APP_UNINSTALLED` handler unconditionally deletes that shop's stored sessions/installation record: [4](#0-3) 
- The `shopify-app-react-router`/`shopify-app-remix` webhook authenticator similarly derives `shop`/`session` for the authenticated context directly from `check.domain` returned by `validate`, without any additional binding between the domain header and the signed payload: [5](#0-4) 

Because the API secret is shared by the app across all installing shops, a merchant (attacker) who has installed the app can legitimately receive a correctly-HMAC-signed webhook body for their own shop (any topic, e.g. `APP_UNINSTALLED`). Since the HMAC only authenticates the body, replaying that exact body to the app's webhook endpoint with a modified `X-Shopify-Shop-Domain` (or `X-Shopify-Event-Domain`) header still yields `valid: true`, but `domain` now points at an arbitrary victim shop of the attacker's choosing. This is directly analogous to the Realitycards bug: the function that performs the sensitive removal (`deleteAppInstallationHandler` / session deletion) is invoked with an attacker-controlled target identity because the access-control check (HMAC) does not bind to that identity.

### Impact Explanation
An attacker can force deletion of another shop's offline session and `AppInstallations` record (equivalent to spoofing that shop's uninstall), disrupting that victim's app for that shop — background jobs, webhook processing gated on session existence, and API calls relying on the offline session will fail until the victim reinstalls. This is a cross-tenant denial-of-service / unauthorized state-mutation impact triggered by an unprivileged actor (any merchant with the app installed) against a completely unrelated shop, without needing to know the API secret or breach TLS. It mirrors the "malicious user can trigger another user's removal" impact from the report: an unrelated third party can force a security-relevant removal action against a victim who did nothing to trigger it.

### Likelihood Explanation
Likelihood is limited by the delivery path: Shopify's own webhook delivery infrastructure typically sets the domain header to match the actual originating shop, so under normal HTTPS delivery from Shopify to the app, header and body are consistent. The attack requires the attacker to intercept/replay the raw POST to the app's public webhook endpoint with a modified header — feasible because it is the attacker's own outbound HTTP call to a public endpoint (no MITM against Shopify needed), using a webhook payload/HMAC that was legitimately delivered to them for their own shop. This is a moderate-likelihood issue: it requires the app to have at least one endpoint reachable from the internet that calls `shopify.webhooks.validate`/`process`, and for the attacker to control the headers of the replayed request (trivial with tools like curl), which is realistic for any self-hosted webhook endpoint.

### Recommendation
Do not trust the `X-Shopify-Shop-Domain` (or equivalent events header) as a bare identity signal for authorization purposes; instead:
1. Include the domain/shop (and other authoritative fields like topic/webhook-id) as part of the data that is HMAC-verified, or independently verify the domain against the shop associated with the session/API credentials being acted upon.
2. Where feasible, cross-validate the shop against an existing session record before performing destructive actions (e.g., only delete sessions for `domain` if a session for that domain was already established via a previously verified OAuth flow, and rate-limit/log mismatches).
3. Consider binding webhook replay protection (e.g., checking `X-Shopify-Webhook-Id`/timestamp uniqueness) to prevent replaying previously legitimate payloads at all, closing this and other replay-based issues.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and lets it complete OAuth normally.
2. Attacker triggers `APP_UNINSTALLED` (or captures any legitimately delivered webhook) and records the raw body `B` and the corresponding valid `X-Shopify-Hmac-Sha256: H` value that Shopify computed for `B` using the app's shared secret.
3. Attacker POSTs to the app's public webhook endpoint (`shopify.webhooks.process`/`validate` route) with:
   - Body: `B` (unchanged — signature must remain valid)
   - Header: `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because only `B` is hashed) — verified logic: [6](#0-5) 
   - Header: `X-Shopify-Shop-Domain: victim.myshopify.com` (replaced)
   - Header: `X-Shopify-Topic: app/uninstalled`
4. `validateHmacFromRequestFactory` returns valid (body hash matches). `checkWebhooksHeaders` returns `domain: 'victim.myshopify.com'` taken from the attacker-controlled header: [7](#0-6) 
5. The registered `APP_UNINSTALLED` callback (`deleteAppInstallationHandler`) is invoked with `shop = 'victim.myshopify.com'`, deleting `victim.myshopify.com`'s stored sessions/installation record: [4](#0-3) 

*Note:* I could not find code in this repository that binds the `domain` header to the signed body (e.g., no signature covering headers, no cross-check against a stored session before acting), so the analysis above is based solely on what is present in the indexed files; if such a cross-check exists elsewhere (e.g., custom app-level guards not present in this package), it would mitigate this finding.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };

function checkWebhooksHeaders(
  headers: Headers,
): WebhookValidationMissingHeaders | WebhookValidationValid {
  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];
  const missingHeaders: string[] = [];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);
  const domain = getRequiredHeader(headers, headerNames.domain, missingHeaders);
  const apiVersion = getRequiredHeader(
    headers,
    headerNames.apiVersion,
    missingHeaders,
  );
  const webhookId = getRequiredHeader(
    headers,
    headerNames.webhookId,
    missingHeaders,
  );

  if (missingHeaders.length) {
    return {
      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
    };
  }

  const fields: WebhooksWebhookFields = {
    webhookType: WebhookType.Webhooks,
    hmac: hmac!,
    topic: topicForStorage(topic!),
    domain: domain!,
    apiVersion: apiVersion!,
