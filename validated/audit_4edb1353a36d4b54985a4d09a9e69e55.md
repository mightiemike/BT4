### Title
RecursionLimit bypass when skipping unknown/extension fields via `protowire.ConsumeFieldValue` - (File: proto/decode.go)

### Summary
`proto.UnmarshalOptions.RecursionLimit` is the mechanism applications use to bound the CPU/stack cost of parsing attacker-controlled, deeply nested protobuf messages. However, when the slow-path unmarshaler encounters a field number that is not part of the trusted schema (an "unknown" field, which any peer can trivially produce just by using an unused field number), it skips that field's bytes with `protowire.ConsumeFieldValue`, which internally enforces its own **fixed** `DefaultRecursionLimit` instead of the caller-configured, and possibly much smaller, `RecursionLimit`. An attacker can therefore nest nested groups inside an unknown field number far beyond the application's configured recursion budget, up to the hardcoded default, defeating the app's intended CPU-limiting control — the same bug class as ALPINE-CVE-2026-40016 (a configured resource/CPU limit silently not applied on a code path an unprivileged sender can reach).

### Finding Description
`proto.Unmarshal`/`UnmarshalOptions.Unmarshal` default `RecursionLimit` to `protowire.DefaultRecursionLimit` if unset, but explicitly allow callers to configure a smaller value to bound decode cost: [1](#0-0) 

The slow-path decoder decrements/checks this configured limit for known fields (messages, lists, maps) via `o.unmarshalMessage`/`o.unmarshalMap`, which invoke `errRecursionDepth` checks tied to `o.RecursionLimit`: [2](#0-1) 

But when a field number is *not* found in the message descriptor (`fd == nil`, i.e. an "unknown" field — trivially reachable by sending any unused field number), the decoder falls back to `protowire.ConsumeFieldValue` to skip the value: [3](#0-2) 

`protowire.ConsumeFieldValue` does not take a caller-supplied depth; it always starts recursion counting at the package-level constant `DefaultRecursionLimit`, completely independent of the caller's `RecursionLimit`: [4](#0-3) 

The same disconnect exists in the map-decoding fast path, where unknown fields inside a map entry are also skipped with the unbounded-relative-to-caller `protowire.ConsumeFieldValue`: [5](#0-4) [6](#0-5) 

The consequence: an application that sets a small `RecursionLimit` (e.g. 5–10) specifically to bound the CPU/stack cost of parsing untrusted nested messages gets that protection enforced only for fields that are *part of the schema*. For any field number outside the schema (or any extension range without a resolvable extension), an attacker can nest length/group-delimited data to `DefaultRecursionLimit` depth regardless of the app's configured, tighter limit — an outcome directly analogous to the Dovecot Sieve report where a configured CPU/resource limit could be bypassed up to ~130x via a code path that didn't honor the same check.

### Impact Explanation
Confidentiality and integrity are not impacted. Availability is affected: a service that deliberately configures a small `RecursionLimit` as a defense-in-depth measure against CPU/stack exhaustion from attacker-supplied nested protobuf payloads can have that specific defense bypassed via unknown fields, allowing recursion up to the much larger hardcoded default. This raises actual CPU/stack cost for those requests beyond what the operator intended to allow, mirroring the "CPU limit bypass" impact class of the reference CVE.

### Likelihood Explanation
Reaching this path requires no special privileges, custom resolver, or malicious peer/node — any unprivileged sender of a protobuf message to a service using `proto.Unmarshal`/`UnmarshalOptions.Unmarshal` with a reduced `RecursionLimit` can trigger it, simply by including a field number that is not present in the target message's schema (or an extension range without a registered extension) encoded with deeply nested groups. This is a normal, expected part of the wire format (unknown fields are legal and commonly forward/backward-compatibility mechanisms), so the path is trivially reachable on any endpoint parsing default binary protobuf with a lowered `RecursionLimit`.

### Recommendation
Thread the caller's configured recursion/depth budget into `protowire.ConsumeFieldValue` (or provide a depth-aware variant) and have all unknown-field/extension skip paths in `proto/decode.go` and `internal/impl/codec_map.go` use the caller's remaining `RecursionLimit`/`opts.depth` instead of the fixed `protowire.DefaultRecursionLimit`, so that the configured limit uniformly bounds cost for both known and unknown fields.

### Proof of Concept
```go
package main

import (
	"fmt"

	"google.golang.org/protobuf/proto"
	"google.golang.org/protobuf/testing/protopack"
)

// Build a value for an *unknown* field number (e.g. 9999, not present in
// the target message's schema) consisting of deeply nested groups.
func nestedUnknownGroup(depth int) []byte {
	// field 9999 encoded as a group, nested `depth` times
	inner := protopack.Message{}
	for i := 0; i < depth; i++ {
		inner = protopack.Message{
			protopack.Tag{9999, protopack.StartGroupType},
			protopack.Raw(inner.Marshal()),
			protopack.Tag{9999, protopack.EndGroupType},
		}
	}
	return inner.Marshal()
}

func main() {
	// Application configures a small RecursionLimit specifically to bound
	// CPU cost of parsing untrusted, deeply nested protobuf payloads.
	opts := proto.UnmarshalOptions{RecursionLimit: 3}

	// Craft a payload whose *known* nesting is within the limit, but whose
	// unknown field (9999) is nested far beyond the configured limit.
	payload := nestedUnknownGroup(2000) // >> RecursionLimit of 3

	m := &SomeAppMessage{} // trusted, generated message type with a small schema
	err := opts.Unmarshal(payload, m)
	// Expected if limit were honored uniformly: "exceeded maximum recursion depth"
	// Actual: succeeds (or fails only near protowire.DefaultRecursionLimit),
	// because protowire.ConsumeFieldValue ignores opts.RecursionLimit entirely.
	fmt.Println("unmarshal err:", err)
}
```
Because `protowire.ConsumeFieldValue` (invoked from `proto/decode.go`'s unknown-field fallback) always uses the fixed `DefaultRecursionLimit` rather than the 3-deep limit the application configured, the crafted payload's unknown field is processed to a depth far exceeding the app's intended CPU-bounding policy, demonstrating the bypass. // ConsumeFieldValue parses a field value and returns its length.
// This assumes that the field [Number] and wire [Type] have already been parsed.
// This returns a negative length upon an error (see [ParseError]).
//
// When parsing a group, the length includes the end group marker and
// the end group is verified to match the starting field number.
func ConsumeFieldValue(num Number, typ Type, b []byte) (n int) {
	return consumeFieldValueD(num, typ, b, DefaultRecursionLimit)
}

func consumeFieldValueD(num Number, typ Type, b []byte, depth int) (n int) {
