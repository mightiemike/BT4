## Title
Unsanitized asset `url`/`description`/`name` fields allow HTML/JS injection into block-explorer front ends via HTTP JSON API - (File: `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`)

### Summary
Any unprivileged account can issue a TRC10 asset (`AssetIssueContract`) with a `name`, `abbr`, `url`, and `description` field. These fields are validated only for length (and, for `name`/`abbr`, for being printable ASCII, which still permits `<`, `>`, `'`, `;`), but never sanitized against HTML/JS metacharacters. The values are later served verbatim through the node's public JSON HTTP API (e.g. `getassetissuebyid`, `getassetissuebyname`, `getassetissuelistbyname`), with only a minimal JSON-quote-escaping step applied. Any front end (block explorer, wallet) that renders these fields as HTML without additional escaping is exposed to stored XSS — the exact bug class described in the Sablier report, where an attacker-controlled token metadata string is propagated unsanitized into rendered output.

### Finding Description
`TransactionUtil` defines the validation rules for asset metadata: [1](#0-0) 

- `validUrl()` calls `validBytes()`, which enforces **only a maximum length (256 bytes)** — no character restriction at all.
- `validAssetDescription()` calls `validBytes()` with max length 200 — again, **no character restriction**.
- `validAssetName()`/`validTokenAbbrName()` call `validReadableBytes()`, which restricts to the printable-ASCII range `0x21`–`0x7E`. This range still includes `<` (0x3C), `>` (0x3E), `/` (0x2F), `'` (0x27), and `;` (0x3B) — the exact characters the Sablier report recommends blocking.

These validators are invoked from `AssetIssueActuator.validate()` when a user issues a new asset: [2](#0-1) 

Once accepted on-chain, these strings are exposed via the node's public HTTP JSON-RPC endpoints, e.g.: [3](#0-2) 

The serialization path (`JsonFormat.printToString` → `escapeBytesSelfType`) only escapes double quotes for JSON well-formedness; it does not perform any HTML/JS sanitization of the underlying content: [4](#0-3) 

Note the `url` and `description` fields are not even in `HttpSelfFormatFieldName`'s name-string map path that would apply quote-escaping — meaning by default they are hex-encoded unless `visible=true` self-type formatting is requested, at which point they receive only the same quote-escaping, not HTML escaping. Any downstream consumer (e.g., a block explorer or wallet UI) that inserts these fields into DOM/HTML without its own escaping is vulnerable to injected `<script>`, `<img onerror=...>`, or similar payloads chosen by the asset issuer.

### Impact Explanation
This is directly analogous to the Sablier finding: attacker-controlled, insufficiently-sanitized on-chain metadata (asset `url`/`description`, and even `name`/`abbr`) is served unmodified by node RPC/HTTP APIs to any front end that queries asset information. A malicious asset issuer can craft `url`/`description` values containing HTML/JS payloads; when displayed by a wallet or explorer that trusts the API response, this enables stored XSS — potentially used to spoof signing prompts, exfiltrate session data, or perform actions on behalf of a victim user, consistent with the "fake wallet popup" scenario in the original report.

### Likelihood Explanation
Issuing a TRC10 asset is available to any account able to pay the required TRX fee and satisfy basic validation; no privileged role is required. `validUrl`/`validAssetDescription` impose no character filtering, so an attacker can trivially embed arbitrary HTML/JS-relevant characters within the length limits (256/200 bytes respectively) — comfortably enough for compact XSS payloads. Any application that queries `getassetissuebyid`/`getassetissuebyname`/`getassetissuelistbyname` and renders these fields is directly affected.

### Recommendation
- Add character-set restrictions (not just length) to `TransactionUtil.validUrl` and `TransactionUtil.validAssetDescription`, at minimum disallowing `<`, `>`, `'`, `"`, `;`, and control characters, or restrict to the same printable/readable filter used for `validAssetName`/`validTokenAbbrName` while additionally excluding those specific characters.
- Consider HTML-escaping (not just JSON-quote-escaping) name/url/description fields in `JsonFormat.escapeBytesSelfType` before they are returned by HTTP/gRPC API endpoints, or clearly document that all asset metadata fields must be treated as untrusted and escaped by any consumer before rendering as HTML.

### Proof of Concept
1. Attacker broadcasts an `AssetIssueContract` transaction with `url` (or `description`) set to a payload such as `"><img src=x onerror=alert(document.cookie)>` — this passes `validUrl`/`validAssetDescription` since only length is checked.
2. Once the asset is confirmed, any client queries the public HTTP API, e.g. `http://<node>:8090/wallet/getassetissuebyid?value=<assetId>`, handled by `GetAssetIssueByIdServlet.doGet`.
3. The response JSON contains the raw, unsanitized `url`/`description` string (only quote characters escaped).
4. A front end (explorer/wallet) that renders this field as HTML executes the injected script in the context of that site. [3](#0-2) [5](#0-4)

  private static boolean validBytes(byte[] bytes, int maxLength, boolean allowEmpty) {
    if (ArrayUtils.isEmpty(bytes)) {
      return allowEmpty;
    }
    return bytes.length <= maxLength;
  }

  private static boolean validReadableBytes(byte[] bytes, int maxLength) {
    if (ArrayUtils.isEmpty(bytes) || bytes.length > maxLength) {
      return false;
    }
    // b must be readable
    for (byte b : bytes) {
      if (b < 0x21) {
        return false; // 0x21 = '!'
      }
      if (b > 0x7E) {
        return false; // 0x7E = '~'
      }
    }
    return true;
  }

  static String escapeBytesSelfType(ByteString input, final String fliedName) {
    //Address
    if (HttpSelfFormatFieldName.isAddressFormat(fliedName)) {
      return StringUtil.encode58Check(input.toByteArray());
    }
    //Normal String
    if (HttpSelfFormatFieldName.isNameStringFormat(fliedName)) {
      String result = new String(input.toByteArray());
      result = result.replaceAll("\"", "\\\\\"");
      try {
        JSON.parseObject("{\"key\":\"" + result + "\"}");
        return result;
      } catch (Exception e) {
        return ByteArray.toHexString(input.toByteArray());
      }
    }
    //HEX
    return ByteArray.toHexString(input.toByteArray());
  }
