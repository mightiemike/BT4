## Finding

### Title
Stale global class cache bypasses `is_declared` re-verification for Cairo 0 classes after a block revert - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` serves compiled classes from the global, long-lived `ContractClassManager` cache (`GlobalContractCache`). For Cairo 1 (`RunnableCompiledClass::V1`/`V1Native`) cache hits, the code explicitly re-checks `state_reader.is_declared(class_hash)` before trusting the cached entry, precisely because "existence in the cache does not guarantee [declaration], since it might contain a declared class from a reverted block." For Cairo 0 (`RunnableCompiledClass::V0`) cache hits, this re-check is skipped entirely: [1](#0-0) 

The `FetchCompiledClasses::is_declared` contract itself documents that Cairo 0 classes "always return `false`", i.e. it is structurally incapable of validating Cairo 0 declaration state: [2](#0-1) 

### Finding Description
The global class cache (`RawClassCache`/`GlobalContractCache`) used by `TrivialClassManager`/`NativeClassManager` is populated by `set_and_compile` whenever a class is fetched during block execution, and it persists across blocks: [3](#0-2) . It is only explicitly cleared in one place in the whole codebase's production path — `PyBlockExecutor::revert_block`, and even there the comment shows it is a deliberate compensating control: "Clear global class cache, to properly revert classes declared in the reverted block": [4](#0-3) .

The batcher's production `ConcurrentTransactionExecutor`/`WorkerExecutor` flow (`crates/apollo_batcher/src/block_builder.rs`, `crates/blockifier/src/blockifier/concurrent_transaction_executor.rs`) shares the same long-lived `contract_class_manager` across blocks and does not call `.clear()` on abort/finalize; only the explicit Python-bound revert path does. This means that if a block that declares a Cairo 0 class is executed (populating the cache), and that block is later reverted (chain reorg, aborted proposal path, or any other revert not going through `PyBlockExecutor::revert_block`), the compiled V0 class remains served straight from cache with **no** verification that the class is still declared in the current committed state — unlike the V1 path, which explicitly guards against this exact scenario.

Because class hashes are content-derived, this is not a "wrong bytecode served" bug; the vulnerability is that an unauthorized state transition (contract deployment/class use without matching, currently-committed declaration) can succeed purely because of cache staleness, when the same transaction executed against the authoritative state reader (cache miss / cold node) would fail with `StateError::UndeclaredClassHash`.

### Impact Explanation
This produces:
- **Honest-node divergence**: A sequencer/validator node that has a warm cache (previously executed the now-reverted block) will accept and execute a `Deploy`/`DeployAccount`/invoke transaction that references the Cairo 0 class hash, while a node without that warm cache (freshly started, joined later, or whose cache entry was evicted) correctly rejects the same transaction with `UndeclaredClassHash`. Different honest nodes reach different verdicts for the identical transaction, which can lead to differing state diffs / committed roots for the same block.
- **Unauthorized account action**: A contract can be deployed and executed at a class hash that is not currently declared in the canonical state (the declare fee/step and the corresponding declared-class commitment were never (re-)applied after the revert), effectively bypassing the declaration requirement enforced everywhere else in the state-reading path.

### Likelihood Explanation
Reachable by any unprivileged party once a revert occurs (block reorg/abort) that leaves a previously-cached Cairo 0 class hash in `ContractClassManager`'s global cache: the attacker (any transaction sender) simply submits a `Deploy`/`DeployAccount` transaction using that class hash. The trigger condition (a revert not going through the one explicit `.clear()` call site) is plausible given the batcher/proposer pipeline can abort/discard in-progress blocks and the class cache is shared/long-lived across the process. I could not fully confirm from the indexed code whether every revert path in the production batcher (as opposed to `native_blockifier`'s Python-bound revert) also clears the cache — this is the main remaining uncertainty and would need to be checked directly in the repository (e.g., via a Devin session) to confirm all revert/abort code paths.

### Recommendation
Apply the same `is_declared` re-validation on cache hits for `RunnableCompiledClass::V0` as is already done for V1/V1Native in `get_compiled_from_class_manager`, or extend `FetchCompiledClasses::is_declared` so it can meaningfully validate Cairo 0 classes instead of being hard-coded to `false`. Alternatively, ensure the global `ContractClassManager` cache is invalidated/cleared on every block-revert/abort code path (batcher abort, reorg handling), not only in `PyBlockExecutor::revert_block`.

### Proof of Concept
1. Node executes block N that declares Cairo 0 class `C` (deprecated contract). `contract_class_manager.set_and_compile(class_hash(C), V0)` caches it.
2. Block N is reverted through a path that does not call `contract_class_manager.clear()` (e.g., batcher-level abort/reorg handling that is not the `PyBlockExecutor::revert_block` path).
3. Storage no longer marks `class_hash(C)` as declared (`is_declared`/`get_deprecated_class_definition_at` returns `None`), matching the storage-layer revert tests in `crates/apollo_storage/src/state/state_test.rs` (`declare_revert_declare_scenario`), which confirm declared-class state is actually rolled back at the storage layer: [5](#0-4) .
4. An unprivileged sender submits a `DeployAccount`/`Deploy` transaction that references `class_hash(C)`.
5. `StateReaderAndContractManager::get_compiled_from_class_manager` finds the cache hit is `RunnableCompiledClass::V0`, takes the `V0(_) => {}` branch (no `is_declared` check), and returns the cached class, letting the transaction execute successfully — whereas a node without the warm cache entry would call `state_reader.get_compiled_classes` and receive `StateError::UndeclaredClassHash`, rejecting the transaction.

    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }
