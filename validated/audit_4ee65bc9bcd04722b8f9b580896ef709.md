## Analog Vulnerability Found

### Title
Unchecked fire-and-forget refund promises in the Wallet Contract cause permanent loss of caller/relayer deposits on failed refund - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The reported bug class is a low-level `.call{value: ...}()` whose boolean success return value is discarded, so a failed value transfer is silently treated as success and the caller loses funds without any error surfacing. The Wallet Contract (`near-wallet-contract`) — a production, publicly deployable contract reachable by any unprivileged transaction signer or relayer calling `rlp_execute` — contains the exact analog: it dispatches NEAR `Transfer` actions as "fire-and-forget" promises to refund an external caller's deposit or a relayer's fee, and never attaches a callback to observe whether that refund promise actually succeeded.

### Finding Description
`rlp_execute` accepts an attached deposit from any caller and tracks it in `CallerDeposit` so it can be refunded if the underlying cross-contract action fails [1](#0-0) .

When the dispatched action promise fails, `rlp_execute_callback` creates a **new, unmonitored** promise batch to send the refund back to the caller and immediately returns `ExecuteResponse` without waiting for or checking the outcome of that refund promise: [2](#0-1) 

The same fire-and-forget pattern is used for paying the relayer's fee in `inner_rlp_execute`: [3](#0-2) 

Because no `.then(...)` callback is attached to either `env::promise_batch_action_transfer` call, the contract state (`has_in_flight_tx = false`, nonce already incremented) is finalized as if the refund/fee payment definitely succeeded, mirroring the audited Solidity bug where `(bool success, ) = recipient.call{...}("")` is issued but `success` is discarded.

At the NEAR protocol level, if this refund receipt fails (e.g., the intended recipient account no longer exists, was deleted, or the transfer otherwise fails at execution), the protocol’s standard deposit-refund mechanism sends the failed deposit back to the **predecessor** of that receipt [4](#0-3)  — which is the Wallet Contract account itself, not the original caller/relayer. Since the Wallet Contract keeps no state or retry logic tracking this in-flight refund, the tokens end up permanently stuck in the Wallet Contract's own balance: the original caller/relayer who was supposed to be made whole never receives their funds, and there is no code path in the contract to detect or recover this.

### Impact Explanation
This is a concrete, unauthorized-outcome-class bug: value that protocol-level accounting shows leaving the Wallet Contract for a refund is not actually confirmed to reach the intended recipient, and on failure it is permanently reabsorbed by the contract with no mechanism to reclaim or resend it. For an external caller (anyone can call `rlp_execute` and attach a deposit, as exercised in `test_caller_refunds` [5](#0-4) ) or a relayer expecting a fee, this results in permanently frozen funds — a Medium-severity impact matching the acceptance criteria.

### Likelihood Explanation
The condition is reachable by any unprivileged party who calls `rlp_execute`/`rlp_execute_from` with a deposit and whose target action fails (e.g., targeting a nonexistent account, as already demonstrated by the existing `test_caller_refunds` test scenario using `"fake.near"`). If the refund's own target account is unavailable at execution time (deleted, insufficient state, etc.) — plausible in a relayer/meta-transaction setting with time between signing and execution — the refund silently fails and is never retried or surfaced, since the code that dispatches it never checks the promise result.

### Recommendation
Attach a `.then(...)` callback to both fire-and-forget transfer promises (the caller-deposit refund in `rlp_execute_callback` and the relayer-fee payment in `inner_rlp_execute`) so the contract can observe `env::promise_result` for these transfers. On failure, persist the pending refund (e.g., in contract state) so it can be retried or claimed later, instead of allowing the funds to be silently reabsorbed with no recovery path — analogous to adding `require(success, ...)`/explicit success handling for the Solidity `.call`.

### Proof of Concept
1. An external caller invokes `rlp_execute_from` with a nonzero attached deposit and an inner action targeting an account/method designed to fail (as in `test_caller_refunds`) [6](#0-5) .
2. The inner action fails, so `rlp_execute_callback`'s `PromiseResult::Failed` branch fires and creates a refund promise via `env::promise_batch_create` / `env::promise_batch_action_transfer` to `caller_deposit.account_id` [7](#0-6) .
3. If that refund receipt itself fails at execution (e.g., the caller's account was deleted in the interim, or any other execution failure), the protocol redirects the failed deposit back to the Wallet Contract account (the predecessor of the refund receipt) per standard deposit-refund rules [4](#0-3) .
4. `rlp_execute_callback` has already returned `ExecuteResponse { success: false, ... }` without checking the refund's outcome, so the contract has no record that the refund failed; the caller's funds remain stranded inside the Wallet Contract balance indefinitely.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );
