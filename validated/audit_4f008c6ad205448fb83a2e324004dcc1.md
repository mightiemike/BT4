### Title
`AccountLocks::try_lock_transaction_batch` grants conflicting write locks within a single batch due to check-then-lock-in-two-passes design - ([File: accounts-db/src/account_locks.rs])

### Summary
`try_lock_transaction_batch` performs the conflict check for *every* transaction in the batch against the pre-batch lock state in one pass, and only applies locks in a second, later pass. Because `lock_write`/`lock_readonly` are not invoked until after all checks in the batch have completed, two transactions in the *same* batch call that both request a write lock on the same account both pass `can_lock_accounts` and are both subsequently granted the write lock via `lock_write`, which simply increments a counter with no re-validation.

### Finding Description
`try_lock_transaction_batch` is implemented as two separate iterations over `validated_batch_keys`: [1](#0-0) 

Pass 1 calls `self.can_lock_accounts(keys.clone())` for every transaction in the batch, but `can_lock_accounts` only reads existing state via `can_write_lock`/`can_read_lock` — it never mutates `write_locks`/`readonly_locks`: [2](#0-1) [3](#0-2) 

Only after *all* transactions in the batch have been checked does pass 2 call `lock_accounts` → `lock_write`, which unconditionally increments the `u64` counter for the key with no conflict re-check: [4](#0-3) [5](#0-4) 

If two transactions in the same call to `try_lock_transaction_batch` both list the same account as writable (e.g., TX1 = `VoteInstruction::Authorize`, TX2 = `VoteInstruction::Withdraw`, both writing the vote account and both signed by the current `authorized_withdrawer`), pass 1 evaluates `can_write_lock(vote_account)` for TX1 against the *original* `self.write_locks` map (no entry yet) → true, and evaluates `can_write_lock(vote_account)` for TX2 against the *same, still-unmodified* map (because pass 1 never calls `lock_write`) → also true. Both entries remain `Ok(())`. Pass 2 then calls `lock_write` for both, incrementing the counter to 2 with no error ever being raised. The intended mutual-exclusion invariant of `AccountLocks` — that only one transaction in a batch may hold a write lock on a given account at a time — is violated purely by the ordering of checks versus locks in this function, independent of any attacker-controlled instruction content.

### Impact Explanation
`AccountLocks` exists specifically so that batches of transactions containing account conflicts are serialized/rejected, preventing concurrent mutation of the same account across parallel execution paths (banking-stage schedulers, unified scheduler, etc., all consume this same accounting structure). If both TX1 and TX2 spuriously receive the write lock on the vote account, downstream code that trusts a successful lock result to permit concurrent/parallel execution of the two transactions may execute or commit them without enforced ordering, letting the two vote-state mutations (`Authorize` then possibly-stale `Withdraw`, or vice versa) interleave non-deterministically. This falls under the consensus/safety-divergence bounty category described in the prompt: identical bank inputs could yield different vote-account bytes/bank hash depending on non-deterministic scheduling/interleaving on different validators, which is a cluster-halting/consensus-divergence class issue.

### Likelihood Explanation
Preconditions are minimal and match the prompt: a funded fee payer and knowledge of an existing vote account's `authorized_withdrawer` keypair (this is the vote account's own authority, so the "attacker" is simply the account's own withdraw authority acting on their own vote account — no privileged access to validator internals is required). The two transactions need only be submitted so that a single call to `try_lock_transaction_batch` receives both of them, which occurs naturally whenever a leader/replay stage batches several sanitized transactions together for a locking pass. This is fully reproducible in a unit test directly against `AccountLocks` without any need for a live cluster.

### Recommendation
Change `try_lock_transaction_batch` to check-and-lock each transaction incrementally within a single pass (i.e., call `can_lock_accounts` and `lock_accounts` together for each transaction before moving to the next), so that a lock granted to an earlier transaction in the batch is visible to the conflict check of a later transaction in the same batch. This restores the invariant that `can_write_lock`/`can_read_lock` are evaluated against the true, up-to-date lock state including all locks already granted earlier in the same batch.

### Proof of Concept
Unit test directly on `AccountLocks` (no bank required, using existing `dev-context-only-utils` qualifiers to expose `is_locked_write`):
```rust
#[test]
fn test_try_lock_transaction_batch_same_batch_write_conflict() {
    let mut locks = AccountLocks::default();
    let vote_account = Pubkey::new_unique();

    let tx1_keys = vec![(&vote_account, true)]; // writable
    let tx2_keys = vec![(&vote_account, true)]; // writable, same batch

    let batch: Vec<TransactionResult<_>> =
        vec![Ok(tx1_keys.into_iter()), Ok(tx2_keys.into_iter())];

    let results = locks.try_lock_transaction_batch(batch);

    // Expected (correct) behavior: only one of the two should succeed.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "both conflicting writable-account transactions in the same batch were granted the write lock"
    );
}
```
Expected current (buggy) result: `ok_count == 2`, demonstrating that `write_locks[vote_account] == 2` after the call, i.e., both TX1 and TX2 hold the write lock simultaneously — violating the mutual-exclusion invariant that the fix should restore (`ok_count == 1`).

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }
