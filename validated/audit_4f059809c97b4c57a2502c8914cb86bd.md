Based on my research, I found a strong analog to the reported bug class in java-tron's `Wallet.getPaginatedNowWitnessList()` API, which is an unprivileged, publicly reachable RPC that performs an unbounded loop over the entire `VotesStore`.

### Title
Unbounded iteration over `VotesStore` in `Wallet.getPaginatedNowWitnessList()` allows resource-exhaustion DoS - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
The reported bug describes `ResetClearLoopSubsystem.clearLoop()` looping over every player of an empire with no bound, risking out-of-gas when the player set grows large. The analogous pattern in java-tron is `Wallet.getPaginatedNowWitnessList()`, a public API callable by any unprivileged client, which internally calls `countVote()` and iterates the *entire* `VotesStore` on every invocation, regardless of the `limit`/`offset` pagination parameters requested.

### Finding Description
`getPaginatedNowWitnessList` accepts `offset` and `limit` and caps `limit` to `WITNESS_COUNT_LIMIT_MAX` [1](#0-0) , but before any pagination is applied it unconditionally calls the private `countVote(votesStore)` helper, which iterates every entry in `VotesStore` — one entry per account that has voted — building an in-memory map for every witness's vote delta [2](#0-1) . The pagination (`skip`/`limit`) is only applied afterward, to the already-fully-materialized witness list [3](#0-2) . The `countVote` implementation itself walks the full `VotesStore` iterator with no size cap and performs nested `forEach` operations over each `VotesCapsule`'s old/new vote lists [4](#0-3) .

`VotesStore` size is directly driven by unprivileged user activity: every account that calls `VoteWitnessContract` gets an entry created via `VoteWitnessActuator.countVoteAccount()` [5](#0-4) , and entries persist until the next maintenance cycle clears them in `MaintenanceManager.countVote()` [6](#0-5) . Since any account can call `VoteWitnessContract` (subject only to owning TRX for TronPower) and there is no cap on the *number of distinct voting accounts*, an attacker can create a very large number of accounts and cast votes from each, inflating `VotesStore` to millions of entries before the next maintenance period. Every call to `getPaginatedNowWitnessList` (even requesting a single witness with `limit=1`) will then force a full linear scan/allocation over the bloated store — mirroring the `PointsMap.clear()` pattern of "loop through all X regardless of what was actually requested."

### Impact Explanation
This is a publicly reachable, unprivileged read API. Because the cost of `countVote()` scales with the total number of unique accounts that voted in the current epoch — a quantity fully controlled by unprivileged users — a full node can be forced to do excessive work (CPU + heap allocation for `HashMap` entries and nested list iterations) on each RPC call, for a value the caller doesn't even need (since results are truncated to `limit` afterward). Repeated/concurrent calls to this endpoint amplify the effect, potentially degrading full-node/API service availability (DoS), analogous to the OOG risk described in the report, but manifesting as a compute/heap exhaustion condition on API-serving nodes rather than a reverted transaction.

### Likelihood Explanation
Likelihood is Low/Medium: an attacker needs to fund and submit `VoteWitnessContract` transactions from many distinct accounts (each transaction costs bandwidth/energy and requires the account to hold frozen TRX for TronPower), so scaling `VotesStore` to a size large enough to matter requires sustained, costly transaction volume. However, unlike a reverting on-chain OOG bug, this doesn't require any single transaction to be enormous — it only requires cumulative growth of `VotesStore`, which is unbounded by protocol design (bounded only per-account by `MAX_VOTE_NUMBER` for votes-per-tx, not by number of distinct voters).

### Recommendation
- Bound the work done by `countVote()`/`getPaginatedNowWitnessList` independent of pagination — e.g., avoid materializing vote deltas for the full witness set before applying `offset`/`limit`, or cache/precompute the vote-delta map once per block rather than recomputing per RPC call.
- Consider capping or rate-limiting the number of distinct voting accounts processed per call, or moving this expensive "real-time" aggregation off the request hot-path (e.g., periodic recomputation, or requiring the maintenance-period cached values only).
- Add metrics/logging on `VotesStore` size growth so operators can detect this precondition being exploited.

### Proof of Concept
1. Create a very large number of TRON accounts (N), each freezing enough TRX for at least 1 TronPower.
2. From each account, submit `VoteWitnessContract` votes for any witness — this creates N entries in `VotesStore` via `VoteWitnessActuator.countVoteAccount()` [7](#0-6) .
3. Before the next maintenance period clears `VotesStore` (which happens only once per maintenance cycle in `MaintenanceManager.doMaintenance()` [8](#0-7) ), repeatedly call the `getPaginatedNowWitnessList` gRPC/HTTP API with `limit=1`.
4. Each call triggers a full O(N) scan/allocation in `countVote()` [4](#0-3)  regardless of the requested `limit`, consuming CPU/memory on the serving node disproportionate to the tiny result requested.

```java
  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
```

```java
  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }
```
