### Title
Rescue outbound accepts attacker-chosen PRC20 without binding it to the original inbound's deposited asset, allowing wrong-token/wrong-amount fund release - (File: x/uexecutor/keeper/create_outbound.go)

### Summary
This is the same bug class as the "missed depositary check" report: a critical fund-moving function trusts an externally supplied identifier (there, `depositary`; here, `PRC20` token address from an EVM log) to select which asset gets moved, without checking it matches the asset actually associated with the underlying record. In `AttachRescueOutboundFromReceipt` [1](#0-0) , the `PRC20` field decoded from the `RescueFundsOnSourceChain` event [2](#0-1)  is used to resolve `tokenCfg` and is written directly into the resulting `RESCUE_FUNDS` outbound as `ExternalAssetAddr`/`Prc20AssetAddr`, with no check that it equals the token originally recorded on `originalUtx.InboundTx.AssetAddr` for that UTX.

### Finding Description
`AttachRescueOutboundFromReceipt` locates the stuck `UniversalTx` from `event.UniversalTxId`, verifies rescue eligibility (CEA-deposit-failed or reverted auto-revert) [3](#0-2) , then resolves the external asset purely from the event-supplied `event.PRC20`: [4](#0-3) 

It never cross-checks that `tokenCfg` (looked up by `event.PRC20`) corresponds to `originalUtx.InboundTx.AssetAddr` — the token that was actually deposited/locked for this specific UTX. The resulting outbound is built with the attacker-influenced token identity but the *original* amount field: [5](#0-4) 

`GetTokenConfigByPRC20` only validates that `(chain, prc20)` is *some* registered pair on the source chain [6](#0-5)  — it does not, and cannot, know which token the specific stuck UTX actually holds. So any PRC20 that is registered for the same source chain (e.g., a higher-value token than the one that was truly deposited) will pass this lookup successfully and populate `ExternalAssetAddr`/`Prc20AssetAddr` on the outbound with a mismatched asset, while `Amount` still comes from the original (different-token) inbound.

This outbound then flows through the normal `attachOutboundsToUtx` → `PendingOutbounds` → UV TSS-signing pipeline [7](#0-6)  exactly like any other outbound, i.e. honest validators will sign and relay whatever `(DestinationChain, ExternalAssetAddr/Prc20AssetAddr, Amount, Recipient)` is stored on the UTX — the module trusts the caller-supplied token binding rather than re-deriving it from the original inbound record.

### Impact Explanation
If the rescue call path is reachable by an ordinary/unprivileged account (the event is emitted by user-initiated `rescueFundsOnSourceChain`-style calls on `UniversalGatewayPC`, as evidenced by the `sender` and `universalTxId` being caller-supplied indexed log fields and by the fact rescue is meant to let a user recover their own stuck funds), an attacker who owns a stuck UTX can supply a PRC20 address for a different, more valuable token registered on the same source chain. This decouples the amount field (denominated for the original asset) from the asset field (now a different token), producing a `RESCUE_FUNDS` outbound instructing release/refund of the wrong asset/amount on the source chain — a form of unauthorized release/misrouted refund and PRC20/native-asset accounting corruption, matching the in-scope "corruption of ... token mapping ... or canonical UniversalTx state" and "unauthorized release/refund" impact categories.

### Likelihood Explanation
Reaching this code only requires: (1) an unprivileged user's own inbound to enter a rescue-eligible state (CEA deposit failed, or non-CEA auto-revert REVERTED — both are ordinary user-triggerable outcomes, e.g. depositing to an unregistered/misconfigured asset as shown in the test setup), and (2) calling the rescue entry point on `UniversalGatewayPC` with an arbitrary registered `PRC20` argument. No privileged role, validator collusion, or admin action is needed on the Push Chain side; the only unverified guard is a missing equality check between `event.PRC20` and the original inbound's asset/PRC20 binding.

### Recommendation
In `AttachRescueOutboundFromReceipt`, do not trust `event.PRC20` in isolation. Re-derive the expected PRC20/token from `originalUtx.InboundTx.SourceChain` + `originalUtx.InboundTx.AssetAddr` (the token config recorded for the original inbound) and require `event.PRC20` to equal that expected PRC20 address before building the outbound; reject the rescue (or ignore the log) if there is a mismatch, analogous to checking the "depositary" is the expected one before allowing the exchange in the original report.

### Proof of Concept
1. User submits an inbound (`SourceChain=eip155:X`, `AssetAddr=TokenA`) that becomes rescue-eligible (e.g., CEA deposit fails, as in `setupRescueFundsTest` [8](#0-7) ).
2. Registry also has `TokenB` (a different, more valuable token) registered on the same `eip155:X` chain with its own PRC20 mapping.
3. Attacker triggers `RescueFundsOnSourceChain(universalTxId=<UTX for TokenA inbound>, prc20=<TokenB's PRC20>, ...)`.
4. `AttachRescueOutboundFromReceipt` calls `GetTokenConfigByPRC20(ctx, sourceChain, TokenB_PRC20)` which succeeds (TokenB is validly registered on that chain) [4](#0-3) , and builds a `RESCUE_FUNDS` outbound with `ExternalAssetAddr = TokenB.Address`, `Prc20AssetAddr = TokenB_PRC20`, but `Amount = originalUtx.InboundTx.Amount` (denominated in TokenA units) — mismatched asset/amount pairing enters the PENDING outbound queue for TSS signing.

Note: I could not locate the Solidity source of `UniversalGatewayPC.rescueFundsOnSourceChain` in this repository (the EVM contract implementation is not indexed here), so the exact on-chain access-control/authorization checks around who may emit this event (e.g., whether it enforces `msg.sender == original inbound sender`) could not be independently verified from this codebase alone. This is a limitation of the index coverage for this repo; confirming the contract-side caller/PRC20 binding requires reviewing the actual contract source (possibly in a separate repo) or starting a full Devin session with access to it.

// RescueFundsOnSourceChainEvent holds decoded data from the RescueFundsOnSourceChain

type RescueFundsOnSourceChainEvent struct {
	UniversalTxId  string   // 0x-prefixed bytes32 — the original UTX whose funds are stuck

	ChainNamespace string   // source chain namespace (e.g. "eip155")

	GasFee         *big.Int // gas fee charged (in gas-token units)
	GasPrice       *big.Int // gas price on the source chain
	GasLimit       *big.Int // gas limit used for the rescue execution

func (k Keeper) GetTokenConfigByPRC20(
	ctx context.Context,
	chain string,
	prc20Addr string,
) (types.TokenConfig, error) {

	if strings.TrimSpace(prc20Addr) == "" {
		return types.TokenConfig{}, fmt.Errorf("prc20 address is empty")
	}
	// Same canonical form as the index function, so any case variant hits the row.
	prc20Addr = canonicalPRC20(prc20Addr)

	// PRC20 addresses are globally unique by construction; MatchExact returns at most one.
	iter, err := k.TokenConfigs.Indexes.PRC20Index.MatchExact(ctx, prc20Addr)
	if err != nil {
		return types.TokenConfig{}, err
	}
	defer iter.Close()

	for ; iter.Valid(); iter.Next() {
		pk, err := iter.PrimaryKey()
		if err != nil {
			return types.TokenConfig{}, err
		}
		cfg, err := k.TokenConfigs.Get(ctx, pk)
		if err != nil {
			return types.TokenConfig{}, err
		}
		if cfg.Chain == chain {
			return cfg, nil
		}
	}

	return types.TokenConfig{}, collections.ErrNotFound
}

func setupRescueFundsTest(
	t *testing.T,
	numVals int,
) (
	*app.ChainApp,
	sdk.Context,
	[]string, // universalVals
	string, // utxId of the failed CEA UTX
	[]stakingtypes.Validator,
) {
	t.Helper()

	// Reuse the CEA environment (validators, chain/token config, authz for inbound voting).
	chainApp, ctx, vals, _, coreVals, _ := setupInboundCEAPayloadTest(t, numVals)

	testAddress := utils.GetDefaultAddresses().DefaultTestAddr
	recipient := utils.GetDefaultAddresses().TargetAddr2
	// Use an asset address that has no registered token config — depositPRC20 will fail.
	unregisteredAsset := common.HexToAddress("0x000000000000000000000000000000000000DEAD")

	inbound := &uexecutortypes.Inbound{
		SourceChain: "eip155:11155111",
		TxHash:      "0xrescue01",
		Sender:      testAddress,
		Recipient:   recipient,
		Amount:      "1000000",
		AssetAddr:   unregisteredAsset.String(),
		LogIndex:    "1",
		TxType:      uexecutortypes.TxType_FUNDS_AND_PAYLOAD,
		UniversalPayload: &uexecutortypes.UniversalPayload{
			To:                   recipient,
			Value:                "1000000",
			Data:                 "0x",
			GasLimit:             "21000000",
			MaxFeePerGas:         "1000000000",
			MaxPriorityFeePerGas: "200000000",
			Nonce:                "1",
			Deadline:             "9999999999",
			VType:                uexecutortypes.VerificationType(1),
