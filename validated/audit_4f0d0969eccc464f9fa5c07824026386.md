## Title
Failed `afterAuth` hook executions are silently treated as completed for up to 60 seconds, causing incomplete authentication setup to be accepted as valid - (File: `packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts`)

### Summary
The `IdempotentPromiseHandler` used by the token-exchange authentication strategies in `shopify-app-remix`, `shopify-app-react-router`, and `shopify-app-express` marks a session-token identifier as "already run" *before* the wrapped `afterAuth` promise has actually completed successfully. If that promise throws (e.g. network failure, webhook registration failure inside the app's `afterAuth` hook), the identifier is not cleared and remains marked as "consumed" until a 60-second TTL expires. Any retry of the authentication flow using the same session token during that window will skip re-running `afterAuth` entirely, silently treating the incomplete/failed setup as done — analogous to the StakeWise pattern of crediting a result before the underlying process (validator activation / hook completion) has actually finished.

### Finding Description
`IdempotentPromiseHandler.handlePromise` decides whether to invoke `promiseFunction` using `isPromiseRunnable`, which immediately inserts the identifier into the map with the current timestamp and returns `true` the first time it's seen: [1](#0-0) 

Note that `isPromiseRunnable` marks the identifier as used *synchronously, before* `promiseFunction()` is awaited. If `promiseFunction()` subsequently throws, the `finally` block only prunes identifiers older than `IDENTIFIER_TTL_MS` (60000 ms) — the just-failed identifier is younger than that, so it stays in the map as "already handled": [2](#0-1) 

This handler is used to gate the `afterAuth` hook call keyed by the raw session token in the token-exchange authentication strategy: [3](#0-2) 

and identically in the React Router and Express packages: [4](#0-3) [5](#0-4) 

Session tokens (JWTs) issued by App Bridge are short-lived (typically ~1 minute), which is the same order of magnitude as `IDENTIFIER_TTL_MS`. A client retrying the same request (same `sessionToken`) after a transient `afterAuth` failure — e.g. due to a `fetch` error while registering webhooks, writing billing state, or any other side effect the app performs in `afterAuth` — will have that hook silently skipped on the retry, since `isPromiseRunnable` already recorded the identifier as run on the first (failed) attempt.

### Impact Explanation
The app's authentication flow returns a valid, usable session to the caller even though a required post-authentication side effect (`afterAuth`) never successfully completed. Because the failure is swallowed for retries within the TTL window, the merchant/session is granted the same access/behavior as a properly completed authentication, without app-specific setup (webhook registration, billing checks, or other state initialization performed in `afterAuth`) actually having succeeded — directly mirroring the "new users gain rewards before the underlying process finishes" bug class: state is treated as finalized before the operation it depends on has actually completed.

### Likelihood Explanation
This requires only a normal, unprivileged request flow: any merchant/app session going through the token-exchange strategy where the `afterAuth` hook transiently fails (e.g., due to a flaky network call, mockable/observable from an attacker's perspective by inducing errors in dependent services) and is retried with the same session token before it expires. No privileged access is required — it is reachable purely through the standard embedded-app authentication path.

### Recommendation
Only mark an identifier as "handled" after `promiseFunction()` resolves successfully; remove the identifier (or never insert it) on failure so that a subsequent retry with the same identifier will re-attempt `afterAuth` rather than silently skip it. For example, move the `this.identifiers.set(identifier, Date.now())` call to run after successful completion of `promiseFunction`, or delete the identifier in a `catch` block before rethrowing.

### Proof of Concept
1. An embedded app authenticates via token exchange; `handleAfterAuthHook` is invoked with the session token as `identifier`.
2. `afterAuth` throws (e.g., simulated failed webhook registration request).
3. `isPromiseRunnable('token')` already set the identifier in the map before the failure, so it isn't cleared (`clearStaleIdentifiers` only removes entries older than 60s).
4. Client retries the exact same request (same `sessionToken`, still valid/un-expired) within 60 seconds.
5. `handlePromise` calls `isPromiseRunnable('token')` → returns `false` → `afterAuth` is *not* re-invoked, no error is thrown, and the caller proceeds treating authentication + setup as fully successful, even though the original `afterAuth` side effect never completed. [6](#0-5)

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }

  private async clearStaleIdentifiers() {
    this.identifiers.forEach((date, identifier, map) => {
      if (Date.now() - date > IDENTIFIER_TTL_MS) {
        map.delete(identifier);
      }
    });
  }
