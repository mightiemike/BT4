### Title
Out-of-bounds read via unchecked `LocationInFile` offset/length in mmap-backed storage `Reader::get()` - (File: crates/apollo_storage/src/mmap_file/mod.rs)

### Summary
`FileHandler::get()` performs a raw, `unsafe` pointer-offset read of `location.len` bytes at `memory_ptr + location.offset` with no validation that this range lies within the region of the mmap file that has actually been grown/backed by the OS. This mirrors the CVE-2026-74567 root cause: a chunk/offset value derived from stored metadata is used to compute a read address and length, but only a partial invariant ("caller must ensure serialized data ≤ max_object_size") is relied upon instead of an explicit bounds check against the real allocation/backing size before dereferencing.

### Finding Description
`FileHandler::get()` is the read path used by every mmap-backed table in `apollo_storage` (transactions, transaction outputs, thin state diffs, Sierra/CASM/deprecated contract classes): [1](#0-0) 

It does:
```rust
let mut bytes = unsafe {
    std::slice::from_raw_parts(
        self.memory_ptr.offset(location.offset.try_into()?),
        location.len,
    )
};
```
with no check that `location.offset + location.len` is within `mmap_file.size` (the portion of the file actually grown via `file.set_len()`) or within `config.max_size` (the length the `MmapMut` was created with).

The write side documents, but does not enforce, the precondition this depends on: [2](#0-1) 
"the caller **must** ensure ... the serialized data is not larger than the maximum object size."

`grow_file_if_needed` only extends the file's backing store lazily, keyed off `max_object_size`, immediately after each `append()`: [3](#0-2) 

If a serialized object (a `Transaction`, `TransactionOutput`, `SierraContractClass`, `CasmContractClass`, `DeprecatedContractClass`, or `ThinStateDiff`) ever exceeds `config.max_object_size` (default 256 MB, see `MmapFileConfig::default` at [4](#0-3) ), the direct write `mmap_slice[..len].copy_from_slice(&serialized)` in `append()` ( [5](#0-4) ) can write past the file region the OS has actually backed, and the resulting `LocationInFile{offset, len}` persisted to the DB tables will describe a range beyond the valid backing store. Any subsequent `get()` on that location then performs the unchecked unsafe read described above, dereferencing memory that is unbacked/uncommitted for the mapping — undefined behavior analogous to the kernel's OOB read past the `kmemdup`-sized allocation in `keyring_get_key_chunk()`.

### Impact Explanation
An out-of-bounds/unbacked-memory read through `mmap`-mapped pages typically triggers `SIGBUS` (Linux, when the mapped byte range is beyond the file's actual extent) or reads adjacent uncontrolled memory, crashing the sequencer/full-node process handling that read. Because this path underlies transaction, transaction-output, state-diff, and contract-class storage — all touched during block building, gateway validation, RPC serving, and OS re-execution — a crash here can halt block production or re-execution on affected nodes, which maps to "a network unable to confirm new transactions" if triggered broadly (e.g., during common re-execution/replication of the same oversized object across validators).

### Likelihood Explanation
Reachability depends entirely on whether an unprivileged actor (contract declarer or high-calldata transaction sender) can get an object serialized into these mmap files whose size exceeds `max_object_size` (256 MB) or otherwise breaks the offset/size invariant that `get()` relies on. I could not confirm within the available index whether the gateway/bouncer enforce a tight enough bound (e.g., `max_contract_bytecode_size`, calldata length limits) on every object type stored via this mechanism (contract classes, CASM, transactions, outputs, state diffs) to make this precondition unreachable in practice. This is the main open uncertainty in this analysis — without confirming an actual size-limit bypass, likelihood cannot be rated with full confidence, and I would recommend a background engineering pass to check bouncer/gateway size caps against `MmapFileConfig::max_object_size` for every stored value type, and to check whether `state_diff` accumulation across many transactions in one block could exceed `max_object_size` when serialized as a single `ThinStateDiff` object.

### Recommendation
- Make `get()` bounds-checked: validate `location.offset + location.len <= mmap_file.size` (and `<= config.max_size`) before constructing the raw slice, returning an error instead of invoking `from_raw_parts` on an unchecked range.
- Make `append()` reject (return an error rather than write) any object whose serialized length exceeds `max_object_size`, instead of relying on an undocumented/unenforced caller invariant.
- Audit all producers of data that ends up serialized into these mmap files (declared contract classes/CASM, transactions, transaction outputs, per-block `ThinStateDiff`) to confirm gateway/bouncer/versioned-constants size limits are strictly below `max_object_size` in every configuration.

### Proof of Concept
Not independently verified end-to-end (would require confirming an actual size-limit bypass at the gateway/bouncer layer for one of the stored object types, which was not confirmed from the available index). Conceptually: craft a declare transaction (or otherwise produce a `SierraContractClass`/`CasmContractClass`/`ThinStateDiff`) whose serialized form exceeds `MmapFileConfig::max_object_size`; if accepted, `Writer::append()` writes past the currently grown file region, and a later `Reader::get()` on the resulting `LocationInFile` dereferences unbacked mapped memory, crashing the process.

impl<V: ValueSerde> FileHandler<V, RW> {
    fn grow_file_if_needed(&mut self, offset: usize) {
        let mut mmap_file = self.mmap_file.lock().expect("Lock should not be poisoned");
        if mmap_file.size < offset + mmap_file.config.max_object_size {
            debug!(
                "Attempting to grow file. File size: {}, offset: {}, max_object_size: {}",
                mmap_file.size, offset, mmap_file.config.max_object_size
            );
            mmap_file.grow();
        }
    }
}

impl<V: ValueSerde + Debug> Writer<V> for FileHandler<V, RW> {
    fn append(&mut self, val: &V::Value) -> LocationInFile {
        trace!("Inserting object: {:?}", val);
        let serialized = V::serialize(val).expect("Should be able to serialize");
        let len = serialized.len();
        let offset;
        {
            let mut mmap_file = self.mmap_file.lock().expect("Lock should not be poisoned");
            offset = mmap_file.offset;
            trace!("Inserting object at offset: {}", offset);
            let mmap_slice = &mut mmap_file.mmap[offset..];
            mmap_slice[..len].copy_from_slice(&serialized);
            mmap_file
                .mmap
                .flush_async_range(offset, len)
                .expect("Failed to asynchronously flush the mmap after inserting");
            mmap_file.offset += len;
            mmap_file.should_flush = true;
        }
        let location = LocationInFile { offset, len };
        self.grow_file_if_needed(location.next_offset());
        location
    }
