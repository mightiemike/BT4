Missing slippage protection in `ExchangeInject`/`ExchangeWithdraw` allows sandwich attacks on exchange creators - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's built-in AMM-style `Exchange` feature has three user-facing operations that mutate the token-pair ratio: `ExchangeInjectContract`, `ExchangeWithdrawContract`, and `ExchangeTransactionContract`. Only `ExchangeTransactionContract` carries an `expected` field used for slippage/minimum-output protection. `ExchangeInjectContract` and `ExchangeWithdrawContract` have no equivalent `minOut`/`maxAnotherTokenQuant` parameter, even though their `anotherTokenQuant` (the counter-asset amount computed from the live pool ratio) is fully attacker-manipulable between submission and execution, exactly matching the bug class described in the external report.

### Finding Description
`ExchangeInjectActuator.execute()` and `ExchangeWithdrawActuator.execute()` compute the required/returned amount of the "other" token purely from the current on-chain pool ratio at execution time: [1](#0-0) [2](#0-1) 

Neither contract exposes a caller-supplied bound on this derived quantity. Comparing the three exchange-related protobuf messages confirms the asymmetry: `ExchangeTransactionContract` explicitly carries an `expected` field that is enforced in validation, but `ExchangeInjectContract`/`ExchangeWithdrawContract` do not: [3](#0-2) 

The enforcement path for `ExchangeTransactionContract` shows what "correct" slippage protection looks like in this codebase — it fails validation if the computed output falls below the caller's `expected`: [4](#0-3) 

`ExchangeInjectActuator.doValidate()` and `ExchangeWithdrawActuator.doValidate()` have no analogous check — they only validate that the pool has enough balance and that a "precision" tolerance (0.01%) is respected, not that the amount matches any user expectation: [5](#0-4) [6](#0-5) 

Note that both `ExchangeInject` and `ExchangeWithdraw` are restricted to the exchange's creator (`accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`), but this creator role is not a privileged system role — any unprivileged account can call `ExchangeCreate` to become the creator of its own pool. The attacker side of the sandwich (submitting `ExchangeTransactionContract` buy/sell transactions before and after the victim's inject/withdraw) requires no special privilege at all — any account holding the relevant tokens can do this via `wallet/exchangetransaction`. [7](#0-6) 

### Impact Explanation
An attacker can observe a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction in the mempool and sandwich it with `ExchangeTransactionContract` buy/sell operations to shift `firstTokenBalance`/`secondTokenBalance` immediately before the victim's transaction executes, then reverse the trade afterward. Because `anotherTokenQuant` is derived purely from the manipulated ratio at execution time and there is no `minOut`/`maxIn` bound, the victim (exchange creator):
- On inject: is forced to contribute more of the paired asset than intended for the same amount of the injected token, or receives a worse effective price than expected.
- On withdraw: receives fewer of the paired asset tokens than expected for the amount they withdraw.

This is a direct value-extraction vector against a normal user's assets via MEV-style manipulation of an on-chain resource shared with other actors, matching "underpriced/mispriced public work" and accounting-manipulation impact categories.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the attacker to hold both tokens of a specific exchange pair, monitor the mempool for a specific creator's inject/withdraw transaction, and act within the same block window (achievable by any block producer/validator or MEV-aware relay in a PoS/DPoS chain like TRON). It does not require any privileged role — it is exploitable by any unprivileged holder of the relevant token pair.

### Recommendation
Add a `min_another_token_quant` (or `max_another_token_quant` for inject) field to `ExchangeInjectContract` and `ExchangeWithdrawContract` protobuf definitions, mirroring the `expected` field already present in `ExchangeTransactionContract`. Enforce it in `ExchangeInjectActuator.doValidate()`/`ExchangeWithdrawActuator.doValidate()` analogously to the check at `ExchangeTransactionActuator` line 219 (`if (anotherTokenQuant < tokenExpected) throw ...`), rejecting the transaction if the computed counter-asset amount falls outside the caller-specified bound.

### Proof of Concept
1. Attacker monitors mempool and sees exchange creator C submit `ExchangeWithdrawContract` for exchange pool P (first=TRX, second=TokenX), withdrawing `tokenQuant` of TRX, expecting `anotherTokenQuant` TokenX based on current ratio (see `ExchangeWithdrawActuator.execute` lines 77-89).
2. Attacker front-runs with `ExchangeTransactionContract` selling a large amount of TokenX into the pool (or buying TRX), shifting `firstTokenBalance`/`secondTokenBalance` unfavorably for C's forthcoming withdraw (using `ExchangeCapsule.transaction`, lines 124-169).
3. C's `ExchangeWithdrawContract` executes against the now-skewed ratio, receiving less TokenX than intended, with `doValidate()`'s only guard being the 0.01% "Not precise enough" rounding check (lines 228-243), which does not protect against ratio manipulation.
4. Attacker back-runs with a reverse `ExchangeTransactionContract` to restore the ratio and lock in profit extracted from C.
Since neither `ExchangeWithdrawContract` nor `ExchangeInjectContract` accepts a `minOut`/`maxIn` bound, C had no way to prevent step 3 from executing at an unfavorable rate.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
