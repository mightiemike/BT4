## Summary

The strongest local integrity analog is not a fund-loss issue like the yaxis report, but the same *root-cause class*: **a component's "authoritative value" is computed/validated inconsistently across two code paths that are supposed to represent the same state**. In yaxis, `Vault.balance()` summed raw token amounts while `Controller.balanceOf()` summed only `strategy.want`, so the two balance sheets silently diverged. The Aptos analog is `TransactionOutput::ensure_match_transaction_info` in [1](#0-0) , which is the authenticity check used to confirm a locally-computed `TransactionOutput` matches the trusted, on-chain-committed `TransactionInfo` during replay/verification. It checks status, gas, write-set hash, and event root hash — but its own inline comment admits it **does not check the state-checkpoint hash, hot-state-checkpoint hash, or `position_state_checkpoint_hash`** fields of `TransactionInfoV1`: [2](#0-1) 

### Title
Replay/verify comparator omits checkpoint-root fields, allowing divergent state/position roots to pass authenticity checks - (File: `types/src/transaction/mod.rs`)

### Finding Description
`ensure_match_transaction_info` is the function that asserts a `TransactionOutput` (whether produced by execution or reconstructed during replay/backup-verify) is consistent with the corresponding, ledger-committed `TransactionInfo`. It validates `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash` [3](#0-2) . However, `TransactionInfoV1` (gated by the `TRANSACTION_INFO_V1` feature) can also carry a `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and, when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, a `position_state_checkpoint_hash` — all of which are computed during execution in `DoStateCheckpoint::run` and folded into the transaction-accumulator-committed `TransactionInfo` [4](#0-3) . These checkpoint hashes are the authenticated commitments to the state Merkle root (and, for the native-position subsystem, the position Merkle root) at that version — exactly the kind of "proof-bearing" field the Gate calls out.

Because `ensure_match_transaction_info` never compares these fields against the locally-computed values, any tool or path that relies on this function as its sole consistency check (e.g., replay-verification against archived history, or comparing a freshly-computed `TransactionOutput` to a trusted `TransactionInfo` obtained from storage/backup) will report success even if the locally recomputed state root, hot-state root, or position-state root differs from the authenticated one committed in the accumulator.

### Impact Explanation
If a local state (main state JMT or the native-position state) diverges from the authoritative on-chain root — due to a bug in `DoStateCheckpoint`'s incremental root computation, a bug in the position-state extension logic (`storage/aptosdb/src/db/aptosdb_writer.rs::position_summary_at_commit`), or a storage/restore bug — this divergence would not be caught by `ensure_match_transaction_info`. Tooling built on top of it (the comment explicitly names `db-tool`'s `replay_on_archive`) would falsely certify a corrupted replay as consistent with the authenticated chain history, defeating one of the primary reasons for the equality check to exist: verifying that state-commitment roots (not just write sets and events) survived the executor→storage/replay handoff unchanged. This is a genuine proof/authenticity-binding gap under the Gate's "Committed state that differs from the correct VM result" and "Wrong ... state proof accepted as valid" categories, since the very field meant to authenticate the state root is excluded from verification.

### Likelihood Explanation
The gap is unconditional and structural — it is not a rare edge case but a guaranteed omission for every invocation of `ensure_match_transaction_info` once `TRANSACTION_INFO_V1` (and further, `HOT_STATE_ROOT_IN_TXN_INFO` / `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled. The feature flags exist and are wired through `BlockExecutorConfigFromOnchain::with_features` [5](#0-4) , and the comment itself flags this as a pre-condition that must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" — i.e., the codebase's own authors have identified this as an outstanding gap prior to relying on that feature in production. Exploitability requires an underlying root-computation bug elsewhere (this function only fails to *detect* such a bug), so likelihood of real-world triggering depends on there being a separate defect in checkpoint-root computation, but the detection/verification layer itself is provably incomplete today.

### Recommendation
Extend `ensure_match_transaction_info` to accept and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `TransactionInfoV1`) against locally recomputed values before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` in any environment where replay-verification is relied upon for state integrity guarantees.

### Proof of Concept
Not independently exploitable without a companion root-computation bug; the local proof is the code's own acknowledged gap: `ensure_match_transaction_info` never reads `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` in its comparison logic [6](#0-5) , while these fields are populated as authenticated state-root commitments during execution [7](#0-6) . I was unable to fully trace every call site under `aptos-move/cli/src/commands.rs` (the file content was not retrievable via the indexed tools in the final iteration), so I cannot confirm every consumer of `ensure_match_transaction_info` in db-tool without a full source checkout — a Devin session with full repository access would be needed to enumerate all call sites and confirm end-to-end reachability from `replay_on_archive`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
