### Title
Truncate-then-multiply gas cost calculation causes gas-fee underpayment / potential zero-fee execution in `CalculateGasCost()` - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`CalculateGasCost()` in `x/uexecutor/keeper/fees.go` converts the EIP-1559 `baseFee` (an `sdkmath.LegacyDec`) into an integer "upc" amount by dividing its raw internal representation by `1e18` (`baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))`), truncating any fractional part, and only afterwards multiplies the truncated result by `gasUsed` to obtain `gasCost`. This is structurally the same divide-then-multiply precision loss pattern flagged in the Andromeda `claim_batch()` report: dividing first destroys precision that a subsequent multiplication by a large factor (`gasUsed`, which can be in the hundreds of thousands or millions) would otherwise have preserved. [1](#0-0) 

### Finding Description
`CalculateGasCost` is called from `DeductGasFeesFromReceipt`, which fetches the live network base fee via `k.feemarketKeeper.GetBaseFee(sdkCtx)` and passes it straight in. [2](#0-1) 

Inside `CalculateGasCost`, the code assumes "the base fee is always a whole number of upc -- no fractional upc exists," and unconditionally truncates the `LegacyDec` to an integer before multiplying by `gasUsed`:
```go
baseFeeBig := baseFee.BigInt()
baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))
...
gasCost := new(big.Int).Mul(effectiveGasPrice, gasUsedBig)
``` [3](#0-2) 

This assumption is not something the scoped code enforces or can verify — `baseFee` is produced by the standard EIP-1559 fee-market algorithm (external `cosmos/evm` x/feemarket dependency), which adjusts the base fee each block by a percentage of the parent base fee based on how full the previous block was. That adjustment is inherently proportional/percentage-based and stored as an `sdk.LegacyDec` with 18 decimal places of *fractional* precision — i.e. `LegacyDec` is designed precisely to represent non-integer values like `999999999.912345678901234567`. Nothing in the scoped code path guarantees the adjusted base fee always lands exactly on a whole-upc boundary; the comment's invariant is an assumption, not an enforced guarantee, and I could not find `CalculateBaseFee`/`ElasticityMultiplier` logic in this repository to confirm otherwise (it lives in the vendored `cosmos/evm` dependency, outside `x/`, `universalClient/`, and `precompiles/usigverifier/`).

If the base fee ever carries a fractional-upc component (e.g. `1000000000.4 upc` after a block-to-block base-fee decrease), `baseFeeBig.Div(...)` truncates it down to `1000000000`, discarding the `0.4`. Because the discarded fraction is applied only once but the truncated integer is then multiplied by potentially large `gasUsed` values, the *aggregate* fee undercharged per transaction can be non-trivial — and in the extreme case where the base fee itself is below `1e18` (i.e., less than 1 whole upc, entirely plausible on a fee-market fresh chain or during periods of very low usage), `baseFeeBig` truncates to `0`, making `effectiveGasPrice = 0` and `gasCost = 0` regardless of `gasUsed`. `DeductGasFeesFromReceipt` explicitly treats `gasCost.Sign() <= 0` as "nothing to deduct" and returns `nil`, silently skipping the burn: [4](#0-3) 

The correct order (matching the report's recommendation of multiply-before-divide) would be to multiply `baseFee` (as `LegacyDec`) by `gasUsed` first, and only truncate/convert to the integer `upc` denomination at the very end.

### Impact Explanation
This affects gas-fee accounting for `DerivedEVMCall`/universal-payload executions charged through `DeductAndBurnFees` — an in-scope invariant ("corruption of ... gas fee accounting ... revert destination"). Any unprivileged user submitting a `UniversalPayload` transaction during a period when the network's EIP-1559 base fee has a non-integer upc component (or is below 1 upc) benefits from systematic fee underpayment, or in the low-base-fee case, pays **zero** gas fee for real EVM gas consumed. This is a protocol-fee-accounting defect that unprivileged users can trigger simply by transacting normally; it does not require any privileged actor.

### Likelihood Explanation
Likelihood depends entirely on whether the live `feemarket` base fee value can carry a fractional-upc component under Push Chain's actual configuration. I was **not able to confirm this from the scoped repository** — `x/uexecutor/keeper/fees.go`'s own comment insists the base fee is always a whole upc, and the base-fee-adjustment algorithm itself lives in the external `cosmos/evm` `x/feemarket` module, not in `x/`, `universalClient/`, or `precompiles/usigverifier/`. Genesis configs observed in this repo set `base_fee` as `"1000000.000000000000000000"` (whole numbers), suggesting operators seed it as an integer, but nothing in the scoped code path prevents the EIP-1559 adjustment formula from producing non-integer intermediate values over time as base fee rises/falls by percentage amounts. Given this uncertainty about a scoped root cause versus a dependency-only behavior, and that the assumption might hold true in practice (external dependency may itself always round to integer upc), I flag this with **medium-low confidence** rather than as a certain, unconditionally-triggerable bug.

### Recommendation
Do not truncate `baseFee` to an integer before multiplying by `gasUsed`. Instead, perform the multiplication in `LegacyDec` (or scaled big.Int) space first, and only truncate/round to the integer `upc` amount as the final step:
```go
gasCostDec := baseFee.MulInt64(int64(gasUsed)) // or MulInt(gasUsedBig)
gasCost := gasCostDec.TruncateInt().BigInt()
```
Additionally, verify (and assert/log) that the `feemarket` base fee is actually guaranteed integer-upc by the deployed `x/feemarket` configuration; if not guaranteed, this fix is required to prevent systematic fee underpayment/zero-fee execution.

### Proof of Concept
Conceptual (cannot be run against this index — would need a live/test harness with `x/feemarket` producing a fractional base fee):
1. Configure/observe `feemarket` base fee to decrease via the EIP-1559 adjustment algorithm to a value with a fractional upc component, e.g. `baseFee = 999999999.9 upc` (LegacyDec), or below `1e18` entirely (e.g. `baseFee = 0.5 upc`) during a low-usage period.
2. Submit a `UniversalPayload` transaction that consumes `gasUsed = 500000`.
3. `CalculateGasCost` computes `baseFeeBig.Div(baseFeeBig, 1e18)`, truncating `0.9` (or all of `0.5`) to `0`.
4. Resulting `gasCost = 0 * 500000 = 0` (or undercharged by `0.9 * 500000` upc versus the mathematically correct multiply-first result).
5. `DeductGasFeesFromReceipt` sees `gasCost.Sign() <= 0` and skips `DeductAndBurnFees` entirely — the user pays no gas fee for real EVM execution that consumed `gasUsed` gas.
