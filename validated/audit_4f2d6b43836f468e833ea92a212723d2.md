## Vulnerability Analysis Result

### Title
Gateway's `add_tx` entry point does not enforce the `accept_new_txs` pause flag, allowing paused nodes to keep admitting transactions via P2P propagation - (File: crates/apollo_gateway/src/gateway.rs)

### Summary
The sequencer exposes an operator-controlled dynamic-config flag, `accept_new_txs`, meant to pause admission of new transactions into a node. This flag is checked only in the HTTP server's request handlers, but the underlying `Gateway`/`GenericGateway::add_tx` function — the single shared entry point that both the HTTP server and the P2P mempool-propagation runner call — never checks it. This mirrors the reported `Redeemer` bug class: one caller path enforces the "paused" guard while other callers reaching the same state-mutating function do not.

### Finding Description
`accept_new_txs` is read from `HttpServerDynamicConfig` and gated exclusively inside the two HTTP handlers `add_rpc_tx` and `add_tx` via `check_new_transactions_are_allowed`: [1](#0-0) [2](#0-1) 

However, the actual transaction-ingestion logic lives in `GenericGateway::add_tx` / `add_tx_inner`, which performs stateless validation, declare-permission checks, stateful validation, and forwards to the mempool — with no reference anywhere to `accept_new_txs` or any equivalent pause guard: [3](#0-2) [4](#0-3) 

A grep across `crates/apollo_gateway/**` confirms `accept_new_txs` is never referenced there. Critically, the Gateway's `add_tx` is also invoked directly by the mempool P2P runner when a peer forwards a transaction it received over gossip — completely bypassing the HTTP server (and therefore the pause check): [5](#0-4) 

The documented transaction-submission flow also shows this dual path: an HTTP submission goes `HTTP -> Gateway -> Mempool`, while gossip-relayed transactions go `Runner -> Gateway (Sequencer B) -> Mempool`, both converging on the same unguarded `Gateway::add_tx`: [6](#0-5) 

Because `Gateway`/`GenericGateway` is also the reusable component behind `apollo_infra`'s remote/local execution modes, any caller of the Gateway component other than the specific HTTP handlers (in particular the P2P propagation path, which is triggered by ordinary transactions submitted by any unprivileged user to any node in the network and then gossiped) inherits this gap.

### Impact Explanation
`accept_new_txs` exists so operators can halt admission of new transactions on a node (e.g., during maintenance, a detected issue, or a coordinated upgrade window). Because the check is enforced only at the HTTP ingress and not inside `Gateway::add_tx` itself, a node that has been configured to reject new transactions (`accept_new_txs=false`, and reported as unready via `is_ready`) will still validate, admit to its mempool, and potentially include in a proposed block any transaction that reaches it through P2P gossip from peers. This defeats the intended admission-control guarantee and creates an honest-node divergence: some nodes in the network believe they have paused ingestion (and report so via readiness), yet continue to process and potentially propose transactions through the unguarded path, which can affect block-building consistency during an operator-declared quiescent window.

### Likelihood Explanation
The P2P path is exercised by normal operation (any account submitting a transaction to any peer node in the network); no malicious peer behavior is required — this is reachable purely from a single, unprivileged, ordinarily-submitted transaction propagating through the network's mempool gossip. Any node operator relying on `accept_new_txs=false` to actually stop transaction admission during an incident will be silently bypassed as soon as any peer gossips a transaction to them.

### Recommendation
Move the `accept_new_txs` (or an equivalent pause) check into `GenericGateway::add_tx`/`add_tx_inner` in `crates/apollo_gateway/src/gateway.rs`, so it is enforced uniformly regardless of whether the caller is the HTTP server or the P2P mempool runner, consistent with how the original report recommends adding the missing guard to every code path that performs the same sensitive action.

### Proof of Concept
1. Operator sets dynamic config `accept_new_txs = false` on Node A (HTTP endpoint now returns `SERVICE_UNAVAILABLE` per `is_ready`, and `add_rpc_tx`/`add_tx` reject with `DisabledError`).
2. A user submits a valid transaction to Node B (`accept_new_txs = true` there).
3. Node B gossips the transaction over the mempool-p2p topic.
4. Node A's `MempoolP2pRunner` receives the broadcast and calls `gateway_client.add_tx(GatewayInput { rpc_tx, message_metadata })` directly [7](#0-6) , which routes into `GenericGateway::add_tx_inner` with no `accept_new_txs` check, and the transaction is validated and forwarded into Node A's mempool despite Node A being configured/reported as not accepting new transactions.

    async fn add_tx_inner(
        &self,
        tx: RpcTransaction,
        p2p_message_metadata: Option<BroadcastedMessageMetadata>,
    ) -> GatewayResult<GatewayOutput> {
        let mut metric_counters = GatewayMetricHandle::new(&tx, &p2p_message_metadata);
        metric_counters.count_transaction_received();
        if let RpcTransaction::Invoke(RpcInvokeTransaction::V3(ref inv)) = tx {
            if !inv.proof_facts.is_empty() {
                metric_counters.count_private_transaction_received();
            }
        }
        let is_p2p = p2p_message_metadata.is_some();

        if let RpcTransaction::Declare(ref declare_tx) = tx {
            if let Err(e) = self.check_declare_permissions(declare_tx) {
                metric_counters.record_add_tx_failure(&e);
                return Err(e);
            }
        }

        // Perform stateless validations.
        self.stateless_tx_validator.validate(&tx)?;
