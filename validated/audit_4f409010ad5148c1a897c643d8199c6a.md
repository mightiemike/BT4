## Analysis

I found a concrete analog: an **HTTP Parameter Pollution (HPP) inconsistency in the OAuth callback handler**, where the `shop` value that is cryptographically validated (via HMAC) differs from the `shop` value that is actually used to complete the OAuth flow and construct the resulting session — mirroring the DeXe root cause of inconsistent extraction of a duplicated key from a list, where different code paths read different entries for the "same" logical value.

### Title
OAuth callback shop-parameter confusion via duplicate query keys allows the HMAC-verified shop to diverge from the shop used for token exchange/session creation - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
`callback()` reads the `shop` query parameter twice using two different extraction methods that resolve duplicate keys differently, so a request with a duplicated `shop` parameter can pass HMAC/state validation for one shop value while the token-exchange request and resulting `Session` are built with a different shop value.

### Finding Description
In `callback()`: [1](#0-0) 
the raw `shop` is read with `query.get('shop')` on the `URLSearchParams`, which returns the **first** occurrence of a duplicated key.

Later, the query used for HMAC/state verification is built with: [2](#0-1) 
`Object.fromEntries(query.entries())`, which resolves duplicate keys to the **last** occurrence (later entries overwrite earlier ones when building the object). This `authQuery` (with the *last* `shop` value) is what actually gets validated by `validateHmac`/`safeCompare` in `validQuery()`: [3](#0-2) 

But the shop value actually used to perform the access-token exchange and build the returned `Session` is taken again via `query.get('shop')` (the *first* occurrence): [4](#0-3) 

This is precisely the same bug class as the DeXe report: two different consumers derive a "single" value from a data source (a list of delegation amounts / a list of duplicate query params) using inconsistent selection logic (sum-of-all vs. last-entry-wins in DeXe; first-vs-last in this case), so the value that was validated is not the value that is ultimately used.

### Impact Explanation
Because `shop` (used for `sanitizeShop`, the `/admin/oauth/access_token` POST target, and `session.shop`) is taken from the *first* duplicate, while HMAC/state verification is performed against the *last* duplicate, a request crafted with two `shop` params (attacker-controlled first value, legitimate/self-signed last value) passes the app's HMAC/state check while directing the OAuth code exchange and the persisted `Session.shop` to a different, attacker-chosen `*.myshopify.com`-shaped domain. This breaks the invariant that "if HMAC+state validate, the shop in the resulting session is the one Shopify actually authenticated," which is the exact trust boundary `validQuery()` is meant to enforce. It falls into the "accepted forged Shopify request" / cross-tenant-shop-confusion category even though Shopify's own authorization-code binding to a specific shop domain would likely cause the downstream `/admin/oauth/access_token` call to fail server-side, limiting the practical blast radius primarily to bypassing the app's own internal consistency guarantee (session created for a shop value never actually verified by HMAC) and unnecessary token-exchange requests being sent to an attacker-chosen Shopify-shaped domain with the app's `client_secret` in the POST body.

### Likelihood Explanation
This is reachable by any single actor who can initiate the app's own OAuth `begin`/`callback` flow for their own store (no elevated privilege needed) and modify the callback URL before it's requested (e.g., before their browser completes the redirect). It requires only crafting one extra duplicated `shop` query parameter, which is trivial to construct.

### Recommendation
Extract `shop` and every other security-relevant parameter exactly once and consistently, from the same normalized/deduplicated query object used for HMAC verification (`authQuery`), rather than mixing `query.get(...)` (first-wins) and `Object.fromEntries(query.entries())` (last-wins). Duplicate occurrences of single-value parameters like `shop`, `hmac`, `state`, `code`, and `timestamp` should be explicitly rejected (as is already done for `appProxy` signator in `normalizeQuery` in `hmac-validator.ts`), rather than silently resolved. [5](#0-4) 

### Proof of Concept
1. Attacker registers/owns a normal store `evil.myshopify.com` and begins installing the target app (`GET /auth/begin?shop=evil.myshopify.com`), receiving a signed `shopify_app_state` cookie and being redirected to Shopify's OAuth authorize screen.
2. Shopify redirects back to the app's callback with a legitimately-signed URL, e.g.
   `https://app.example.com/auth/callback?code=C&hmac=H&shop=evil.myshopify.com&state=S&timestamp=T`
3. Before this request is sent (e.g., by editing the address bar / intercepting the redirect in the attacker's own browser), the attacker inserts a duplicate `shop` parameter *before* the real one:
   `https://app.example.com/auth/callback?shop=spoofed-target.myshopify.com&code=C&hmac=H&shop=evil.myshopify.com&state=S&timestamp=T`
4. In `callback()`:
   - `query.get('shop')` returns `spoofed-target.myshopify.com` (first).
   - `authQuery = Object.fromEntries(query.entries())` collapses to `shop: 'evil.myshopify.com'` (last), which matches what Shopify actually signed, so `validateHmac`/`safeCompare` succeed.
5. `sanitizeShop(query.get('shop')!, true)` computes `cleanShop = 'spoofed-target.myshopify.com'`, and the app POSTs `client_id`, `client_secret`, and `code=C` to `https://spoofed-target.myshopify.com/admin/oauth/access_token`, then creates `Session { shop: 'spoofed-target.myshopify.com', ... }` — despite the HMAC/state validation never having covered that shop value at all.

async function validQuery({
  config,
  query,
  stateFromCookie,
}: {
  config: ConfigInterface;
  query: AuthQuery;
  stateFromCookie: string;
}): Promise<boolean> {
  return (
    (await validateHmac(config)(query)) &&
    safeCompare(query.state!, stateFromCookie)
  );
}

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
