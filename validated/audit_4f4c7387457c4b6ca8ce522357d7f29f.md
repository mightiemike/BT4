### Title
Long-running account scans pin `min_ongoing_scan_root`, letting an unprivileged client force unbounded `AccountsIndex` slot-list growth and disproportionate clean/CPU cost - ([File: accounts-db/src/accounts_scan.rs])

### Summary
The Ditto report's bug class is: an unprivileged actor cheaply inflates a data structure that a shared matching/maintenance routine must iterate over, so that later, unrelated operations either blow past a compute/gas budget or become disproportionately expensive/blocked. The closest reachable analog in this AccountsDB codebase is the interaction between `ScanGuard`/`ongoing_scan_roots` (which pins the maximum root that `clean_accounts` is allowed to purge) and the per-pubkey `slot_list` in the in-memory `AccountsIndex`. While a scan is pinned to an old root, `clean_accounts` cannot reclaim any rooted version of an account newer than that pinned root, so every subsequent write to actively-used accounts keeps appending to their `slot_list` instead of being cleaned. This is directly analogous to the order-book bug: an inexpensive, repeatable, unprivileged action (issuing a scan, e.g. via `getProgramAccounts`) combined with ordinary network write activity causes an internal list (bids ↔ `slot_list`) to grow unbounded, degrading the cost of later index scans (matching ↔ `latest_slot`/`get_account_info_with_and_then`) and of AccountsDB maintenance (`clean_accounts`, `calculate_accounts_lt_hash_at_startup_from_index`, shrink) that must walk these lists.

### Finding Description
`ScanGuard::try_new` pins `max_root_inclusive` into `ongoing_scan_roots` for the lifetime of a scan: [1](#0-0) 

The comment explicitly documents that `clean_accounts()` also takes this same lock and therefore "has at most cleaned up to the current `max_root`" — i.e. clean is not allowed to advance its cleaning root past the oldest pinned scan root: [2](#0-1) 

`clean_accounts` uses `max_clean_root_inclusive` to decide, per pubkey, which rooted `slot_list` entries are reclaimable via `latest_slot`/`purge_older_root_entries`/`collect_reclaims`: [3](#0-2) [4](#0-3) 

Older, non-reclaimed rooted versions accumulate directly in each pubkey's `AccountMapEntry::slot_list`, which every reader must walk to find the "latest" visible version: [5](#0-4) [6](#0-5) [7](#0-6) 

`flush_rooted_accounts_cache_with_clean` explicitly notes: "If there is a long running scan going on, this could prevent any cleaning based on updates from slots > `max_clean_root`", confirming this is a known, load-bearing constraint rather than a hypothetical: [8](#0-7) 

An unprivileged client can start an account scan (any RPC path that performs a bank-wide account scan, e.g. `getProgramAccounts`) and keep it open (e.g., by requesting large/slow result sets, or issuing back-to-back overlapping scans) for an extended period. While that scan's root stays the minimum pinned root, ordinary transaction traffic that repeatedly writes to a set of hot accounts (rent, vote-adjacent accounts, or any frequently-touched program state) causes those accounts' `slot_list` to keep growing rather than being pruned by clean each cycle, since `should_collect_reclaims` only fires for entries below `max_clean_root_inclusive`. This is the same mechanism as the report's "tiny bids": a cheap, repeatable, unprivileged action defeats an assumption ("lists stay small because they get pruned regularly") that other code paths (`latest_slot`, `calculate_accounts_lt_hash_at_startup_from_index`, `load`, `shrink`, snapshot generation's duplicate-pubkey walk) rely on for bounded-cost iteration. [9](#0-8) [10](#0-9) 

### Impact Explanation
- Disproportionate CPU cost: `latest_slot` (called on every account read/scan/hash calculation) is `O(slot_list.len())`; once slot lists for hot accounts have grown large due to a stalled clean, every subsequent `get_with_and_then`/`load`/lt-hash computation for those pubkeys becomes proportionally slower.
- Disproportionate storage cost: unreclaimed rooted versions remain resident in the in-memory/disk `AccountsIndex` bucket maps until clean can advance again, inflating index memory/disk usage without bound for the duration of the pin.
- Delayed clean/shrink and snapshot generation: because `clean_accounts` cannot advance `max_clean_root_inclusive`, `shrink_candidate_slots`/`shrink_ancient_slots`/snapshot duplicate-pubkey accounting (`visit_duplicate_pubkeys_during_startup`) inherit more work per cycle the longer the pin persists.
- This does not cause consensus-breaking behavior or a stale/incorrect balance read (the `latest_slot` logic remains correct), so the impact is confined to the "disproportionate storage and CPU cost" category permitted by the validation rubric, not a hash/capitalization divergence or panic.

### Likelihood Explanation
Likelihood is moderate: triggering it requires only unprivileged capabilities (issuing scans and ordinary transactions), no special privileges or validator role. However, the actual severity is bounded by how long a scan can practically be kept "ongoing" and by how much organic write traffic exists on the pinned hot accounts, and the report's own SECURITY.md exclusions carve out RPC-scan-based DoS requiring multiple calls / unfiltered `getProgramAccounts` as generally out of scope, which weakens confidence that this specific vector was intended to be in-scope versus a known/accepted tradeoff of the scan-pinning design.

### Recommendation
- Bound the maximum duration/age a scan is permitted to pin `ongoing_scan_roots`, after which the scan is aborted/retried against a fresh root rather than indefinitely blocking `clean_accounts`.
- Track and alert on `max_distance_to_min_scan_slot` (already computed in `ScanGuard::try_new`) with a hard ceiling that forces remediation (e.g., cancel the oldest scan) instead of only recording a metric.
- Consider decoupling "reclaim older *rooted* duplicate versions for correctness/space" from "give the scan its consistent view," e.g., by keeping reclaimed-but-still-referenced entries in a side structure rather than leaving them in the live `slot_list` that every hot-path reader must scan.

### Proof of Concept
Deterministic reproduction is not fully available from static analysis alone (it depends on RPC scan-cancellation behavior and real network write throughput on hot accounts), so this is presented as a concrete, code-supported mechanism rather than an executed exploit:
1. Client A issues a scan-based RPC call that internally invokes `ScanGuard::try_new`, pinning the current root as `min_ongoing_scan_root` in `accounts-db/src/accounts_scan.rs` (lines 100-144), and keeps the scan open as long as possible.
2. Meanwhile, normal transaction traffic repeatedly updates a small set of hot accounts across many subsequent slots.
3. Each background pass of `AccountsDb::clean_accounts` (`accounts-db/src/accounts_db.rs` lines 1873-2014) computes `max_clean_root_inclusive` bounded by the pinned scan root (per the comment in `flush_rooted_accounts_cache_with_clean`, lines 4334-4350) and therefore cannot reclaim the newer rooted duplicate entries for the hot accounts touched in step 2.
4. The `slot_list` for those hot pubkeys (`accounts-db/src/accounts_index/account_map_entry.rs` lines 18-31) grows with each write and is not pruned until the scan finishes; every `latest_slot` call (`accounts-db/src/accounts_index.rs` lines 429-465) used by reads, lt-hash calculation, and shrink over those pubkeys becomes proportionally more expensive, and index memory/disk usage for those entries grows correspondingly.

impl<'a> ScanGuard<'a> {
    /// Begin a scan: checks the bank hasn't been removed and pins `max_root` in
    /// `ongoing_scan_roots`.
    ///
    /// Returns `None` if the bank has already been removed.
    ///
    /// `max_root_inclusive_fn` is called while holding the `ongoing_scan_roots` write lock.
    pub(crate) fn try_new(
        scan_tracker: &'a ScanTracker,
        scan_bank_id: BankId,
        max_root_inclusive_fn: impl FnOnce() -> Slot,
    ) -> Option<Self> {
        {
            let locked_removed_bank_ids = scan_tracker.removed_bank_ids.lock().unwrap();
            if locked_removed_bank_ids.contains(&scan_bank_id) {
                return None;
            }
        }

        let max_root_inclusive = {
            let mut w_ongoing_scan_roots = scan_tracker
                // This lock is also grabbed by clean_accounts(), so clean
                // has at most cleaned up to the current `max_root` (since
                // clean only happens *after* BankForks::set_root() which sets
                // the `max_root`)
                .ongoing_scan_roots
                .write()
                .unwrap();
            // `max_root()` grabs a lock while
            // the `ongoing_scan_roots` lock is held,
            // make sure inverse doesn't happen to avoid
            // deadlock
            let max_root_inclusive = max_root_inclusive_fn();
            if let Some(min_ongoing_scan_root) =
                ScanTracker::min_ongoing_scan_root_from_btree(&w_ongoing_scan_roots)
                && min_ongoing_scan_root < max_root_inclusive
            {
                let current = max_root_inclusive - min_ongoing_scan_root;
                scan_tracker
                    .max_distance_to_min_scan_slot
                    .fetch_max(current, Ordering::Relaxed);
            }
            *w_ongoing_scan_roots.entry(max_root_inclusive).or_default() += 1;
            max_root_inclusive
        };

    /// Calculates the accounts lt hash
    ///
    /// Only intended to be called at startup (or by tests).
    /// Only intended to be used while testing the experimental accumulator hash.
    /// NOT safe to call concurrently with flush operations
    pub fn calculate_accounts_lt_hash_at_startup_from_index(
        &self,
        ancestors: &Ancestors,
    ) -> AccountsLtHash {
        // This impl iterates over all the index bins in parallel, and computes the lt hash
        // sequentially per bin.  Then afterwards reduces to a single lt hash.
        // This implementation is quite fast.  Runtime is about 150 seconds on mnb as of 10/2/2024.
        // The sequential implementation took about 6,275 seconds!
        // A different parallel implementation that iterated over the bins *sequentially* and then
        // hashed the accounts *within* a bin in parallel took about 600 seconds.  That impl uses
        // less memory, as only a single index bin is loaded into mem at a time.
        let mut lt_hash = self
            .accounts_index
            .account_maps
            .par_iter()
            .fold(
                LtHash::identity,
                |mut accumulator_lt_hash, accounts_index_bin| {
                    for pubkey in accounts_index_bin.keys() {
                        let account_lt_hash = self
                            .accounts_index
                            .get_with_and_then(&pubkey, ancestors, false, |(slot, account_info)| {
                                (!account_info.is_zero_lamport()).then(|| {
                                    self.get_account_accessor(
                                        slot,
                                        &account_info.storage_location(),
                                    )
                                    .get_loaded_account(|loaded_account| {
                                        Self::lt_hash_account(&loaded_account, &pubkey)
                                    })
                                    // SAFETY: The index said this pubkey exists, so
                                    // there must be an account to load.
                                    .unwrap()
                                })
                            })
                            .flatten();
                        if let Some(account_lt_hash) = account_lt_hash {
                            accumulator_lt_hash.mix_in(&account_lt_hash.0);
                        }
                    }
                    accumulator_lt_hash
                },
            )
            .reduce(LtHash::identity, |mut accum, elem| {
                accum.mix_in(&elem);
                accum
            });

    fn visit_duplicate_pubkeys_during_startup(
        &self,
        pubkeys: &[Pubkey],
    ) -> (u64, u64, Box<DuplicatesLtHash>, u128) {
        let mut accounts_data_len_from_duplicates = 0;
        let mut num_duplicate_accounts = 0_u64;
        let mut duplicates_lt_hash = Box::new(DuplicatesLtHash::default());
        let mut capitalization_from_duplicates = 0_u128;
        self.accounts_index.scan(
            pubkeys.iter(),
            |pubkey, slots_refs| {
                if let Some((slot_list, _ref_count)) = slots_refs
                    && slot_list.len() > 1
                {
                    // Only the account data len in the highest slot should be used, and the rest are
                    // duplicates.  So find the max slot to keep.
                    // Then sum up the remaining data len, which are the duplicates.
                    // All of the slots need to go in the 'uncleaned_slots' list. For clean to work properly,
                    // the slot where duplicate accounts are found in the index need to be in 'uncleaned_slots' list, too.
                    let max = slot_list.iter().map(|(slot, _)| slot).max().unwrap();
                    slot_list.iter().for_each(|(slot, account_info)| {
                        if slot == max {
                            // the info in 'max' is the most recent, current info for this pubkey
                            return;
                        }
                        let maybe_storage_entry = self
                            .storage
                            .get_account_storage_entry(*slot, account_info.store_id());
                        let mut accessor = LoadedAccountAccessor::Stored(
                            maybe_storage_entry.map(|entry| (entry, account_info.offset())),
                        );
                        accessor.check_and_get_loaded_account(|loaded_account| {
                            let data_len = loaded_account.data_len();
                            let lamports = loaded_account.lamports();
                            if lamports > 0 {
                                accounts_data_len_from_duplicates += data_len;
                            }
                            num_duplicate_accounts += 1;
                            let account_lt_hash = Self::lt_hash_account(&loaded_account, pubkey);
                            duplicates_lt_hash.0.mix_in(&account_lt_hash.0);
                            capitalization_from_duplicates = capitalization_from_duplicates
                                .checked_add(u128::from(lamports))
                                .expect("capitalization cannot overflow");
                        });
                    });
                }
            },
            ScanFilter::All,
        );
        (
            accounts_data_len_from_duplicates as u64,
            num_duplicate_accounts,
            duplicates_lt_hash,
            capitalization_from_duplicates,
        )
    }

    // Given a SlotList `L`, a list of ancestors and a maximum slot, find the latest element
    // in `L`, where the slot `S` is an ancestor or root, and if `S` is a root, then `S <= max_root`
    pub(crate) fn latest_slot(
        &self,
        ancestors: Option<&Ancestors>,
        slot_list: &[SlotListItem<T>],
        max_root_inclusive: Option<Slot>,
    ) -> Option<usize> {
        let mut current_max = 0;
        let mut rv = None;
        if let Some(ancestors) = ancestors
            && !ancestors.is_empty()
        {
            for (i, (slot, _t)) in slot_list.iter().rev().enumerate() {
                if (rv.is_none() || *slot > current_max) && ancestors.contains_key(slot) {
                    rv = Some(i);
                    current_max = *slot;
                }
            }
        }

        // If we found an ancestor, then we can return early without checking the roots
        // If there is a root that is newer than the newest ancestor but not an ancestor
        // then the root is from a different fork and should not be returned
        if let Some(rv) = rv {
            return Some(slot_list.len() - 1 - rv);
        }

        let max_root_inclusive = max_root_inclusive.unwrap_or(Slot::MAX);

        slot_list
            .iter()
            .enumerate()
            .filter(|(_, (slot, _t))| *slot <= max_root_inclusive)
            .max_by_key(|(_, (slot, _t))| *slot)
            .map(|(index, _)| index)
    }
