## Analog Vulnerability Found

### Title
Instantaneous-ratio usage-transfer calculation in `UnDelegateResource` allows a delegator to shift bandwidth/energy usage debt away from themselves onto other delegators sharing the same receiver - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
The reported bug is a classic "share computed from instantaneous pool state instead of a value fixed at deposit time" flaw: `unstake()` divides by the *current* `totalTokenBalance`/`totalStaked` rather than the ratio that existed when the staker deposited, letting a later depositor's `unstake()` skim value contributed by earlier depositors. The same structural flaw exists in java-tron's TRON Power resource-delegation accounting: when an owner un-delegates bandwidth/energy from a receiver, the amount of "usage debt" transferred back to the owner is computed as a fraction of the receiver's *current, aggregate* frozen balance (which mixes contributions from the receiver's own stake and from *all* other delegators), instead of being tracked per-delegation.

### Finding Description
`UnDelegateResourceActuator.execute()` and its TVM-native counterpart `UnDelegateResourceProcessor.execute()` compute the usage to claw back from the receiver with:

```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
``` [1](#0-0) 

The identical energy-side computation exists at: [2](#0-1) 

and again in the TVM native path: [3](#0-2) 

The divisor `receiverCapsule.getAllFrozenBalanceForBandwidth()` (analogous to `totalStaked`/`totalTokenBalance` in the report) is defined as the sum of the receiver's own frozen balance *plus all* delegated-in balances from every delegator, V1 and V2 combined: [4](#0-3) 

This mirrors exactly the flawed pattern in the report: `userShare = (userStaked * totalTokenBalance) / info.totalStaked`. Because multiple independent owners can delegate resources to the same receiver (this is an explicitly supported multi-delegator model, see `DelegateResourceProcessor.delegateResource`), the pool composition (`getAllFrozenBalanceForBandwidth()`/`getAllFrozenBalanceForEnergy()`) and the receiver's `netUsage`/`energyUsage` fluctuate due to actions taken by *other* delegators between the time a given owner's resource is delegated and the time they un-delegate it. `transferUsage` is therefore not tied to the usage actually attributable to that specific owner's delegation; it is a snapshot ratio computed at un-delegate time against a pool that other, unrelated actors can freely inflate or shrink by delegating/un-delegating around the same receiver — exactly as Bob inflating the pool right before Alice's `unstake()` skews her `userShare`.

### Impact Explanation
An owner who delegates resources to a shared receiver can time their `UnDelegateResourceContract`/`unDelegateResource` TVM call so that the pool denominator (`getAllFrozenBalanceForBandwidth`/`Energy`) is inflated by other delegators' concurrent activity, understating the `transferUsage` clawed back to them. The residual usage debt is left stranded on the receiver's account without a corresponding backing delegation, and it is other delegators to the same receiver who ultimately absorb the resulting under/over-accounted usage the next time *they* un-delegate (since the pool ratio they see has been distorted). This is an accounting-divergence issue affecting bandwidth/energy resource settlement between delegators, not attacker-vs-protocol theft of TRX, so impact is bounded to unfair resource-fee accounting among co-delegators of a receiver rather than direct fund loss.

### Likelihood Explanation
Reaching this path requires no privileged role — any account can call `DelegateResourceContract`/`UnDelegateResourceContract` (or the TVM-native equivalents) against any receiver, including receivers that already have other delegators. Exploitation requires coordinating delegate/undelegate timing relative to other delegators sharing the same receiver, which is plausible but requires multiple accounts (attacker-controlled or opportunistic) delegating to the same receiver, making likelihood medium rather than trivial.

### Recommendation
Track usage attribution per-delegation (e.g., persist the usage-window state at the moment resources are delegated, similar to how `MortgageService`/`DelegationStore` checkpoint vote weight per-cycle via `getWitnessVi` snapshots) rather than deriving `transferUsage` from the receiver's live aggregate pool ratio at un-delegate time. This avoids letting concurrent delegate/undelegate activity from unrelated parties skew the usage settled back to a specific delegator.

### Proof of Concept
1. Owner A delegates `X` TRX of bandwidth to Receiver R. R consumes bandwidth heavily, growing `netUsage` close to its `netLimit` (computed via `calculateGlobalNetLimit`, itself based on `getAllFrozenBalanceForBandwidth()`) — see [5](#0-4) .
2. Before A un-delegates, Owner B (attacker, possibly colluding with R) delegates additional TRX bandwidth to the same R, inflating `receiverCapsule.getAllFrozenBalanceForBandwidth()`.
3. A calls `UnDelegateResourceContract` for `X`. `transferUsage = receiverCapsule.getNetUsage() * (X / inflatedTotal)` is computed with the enlarged denominator, understating the usage clawed back to A relative to what A's frozen balance actually caused while delegated — the same "later staker dilutes/steals from earlier depositor's share" pattern from the report, applied to bandwidth/energy usage accounting instead of token balances.
4. The residual, unaccounted usage remains attributed to R and is settled unfairly against whichever delegator (e.g., B) later un-delegates and inherits a pool ratio distorted by A's earlier, mis-priced exit.
