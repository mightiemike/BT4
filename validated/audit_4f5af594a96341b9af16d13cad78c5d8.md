### Title
Deposit Refund Misdirected to Delegate Sender Instead of Relayer Who Paid — (`runtime/runtime/src/actions.rs`)

### Summary

In NEAR's meta-transaction (NEP-366) execution path, when a `DelegateAction` inner receipt fails on the receiver's shard, the attached deposit is refunded to the **delegate sender** (Alice) rather than the **relayer** who actually paid for it. An unprivileged user can craft a `DelegateAction` with a large attached deposit that is guaranteed to fail, causing the relayer to lose the deposit while the user receives it.

### Finding Description

`apply_delegate_action` in `runtime/runtime/src/actions.rs` constructs the inner receipt as `Receipt::V0` with a plain `ActionReceipt`:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),          // Alice (delegate sender)
    receiver_id: delegate_action.receiver_id().clone(),
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(), // Relayer
        ...
    }),
});
``` [1](#0-0) 

When this inner receipt fails on the receiver's shard, `refund_unspent_gas_and_deposits` issues the deposit refund:

```rust
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(),
        deposit_refund,
    ));
}
``` [2](#0-1) 

`balance_refund_receiver()` resolves to `predecessor_id` when `refund_to` is `None`:

```rust
pub fn balance_refund_receiver(&self) -> &AccountId {
    self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
}
``` [3](#0-2) 

Because the inner receipt is `Receipt::V0` / `ReceiptEnum::Action` (not `ActionReceiptV2`), `refund_to` is always `None`:

```rust
ReceiptEnum::Action(_) | ... => &None,
ReceiptEnum::ActionV2(action_receipt_v2) => &action_receipt_v2.refund_to,
``` [4](#0-3) 

So the deposit refund always goes to `predecessor_id` = Alice (the delegate sender), not to `signer_id` = the relayer who paid.

The code comment in `apply_delegate_action` explicitly acknowledges this asymmetry:

> "If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction. Gas is refunded to the signer, this is Relayer." [5](#0-4) 

The `total_deposit` function also notes this:

> "Note, here Relayer pays the deposit but if actions fail, the deposit is refunded to Sender of DelegateAction" [6](#0-5) 

The architecture documentation explicitly names the exploit:

> "there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard." [7](#0-6) 

### Impact Explanation

The relayer's NEAR balance is debited for the full deposit amount when the transaction is processed. When the inner action fails, the deposit is refunded to Alice (the delegate sender), not the relayer. The relayer suffers a permanent loss equal to the deposit amount. The `ActionReceiptV2.refund_to` field exists in the protocol as a mechanism to redirect deposit refunds, but `apply_delegate_action` never sets it, leaving the relayer with no protocol-level protection.

**Broken invariant:** The party whose balance was debited for a deposit must receive the refund when the action fails.

**Corrupted value:** `receipt.balance_refund_receiver()` returns Alice's account ID instead of the relayer's account ID. The exact amount lost equals `total_deposit(delegate_action.get_actions())`.

### Likelihood Explanation

Any unprivileged user who can find a relayer willing to submit meta transactions can exploit this. The attack requires:
1. Constructing a `DelegateAction` with a large `Transfer` or `FunctionCall` deposit attached to an inner action that will fail (e.g., calling a non-existent method on any contract).
2. Submitting it to a relayer.

No special permissions, validator access, or key compromise are required. The relayer cannot distinguish a malicious `DelegateAction` from a legitimate one that happens to fail at runtime.

### Recommendation

In `apply_delegate_action`, construct the inner receipt as `Receipt::V0` with `ReceiptEnum::ActionV2(ActionReceiptV2 { refund_to: Some(action_receipt.signer_id().clone()), ... })`. This sets the relayer as the deposit-refund recipient, matching the gas-refund behavior and restoring the invariant that the payer receives the refund.

### Proof of Concept

1. Relayer has 1000 NEAR. Alice has 0 NEAR.
2. Alice creates a `DelegateAction`:
   - `sender_id = alice`
   - `receiver_id = some_contract`
   - `actions = [FunctionCall { method_name: "nonexistent", deposit: 500 NEAR, gas: 10 TGas }]`
3. Alice signs it and sends it to the relayer off-chain.
4. Relayer wraps it in a transaction (relayer is signer, alice is receiver), paying 500 NEAR deposit + gas.
5. On `some_contract`'s shard, the function call fails (`MethodNotFound`).
6. `refund_unspent_gas_and_deposits` fires: `deposit_refund = 500 NEAR`, `receipt.balance_refund_receiver() = alice`.
7. Alice receives 500 NEAR. Relayer's balance is reduced by 500 NEAR + gas costs.

The relayer loses 500 NEAR with no recourse at the protocol level.
