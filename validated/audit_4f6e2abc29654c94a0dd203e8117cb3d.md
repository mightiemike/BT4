### Title
Adversarial account-size fragmentation can make `PackedAncientStorage::pack` exceed `target_slots_sorted`, causing whole-batch ancient-pack bail-out - (File: accounts-db/src/ancient_append_vecs.rs)

### Summary
`PackedAncientStorage::pack` [1](#0-0)  is a sequential, non-splitting bin-packer whose number of output storages is only guaranteed to be "close to" `total_bytes / ideal_size`, not exactly `ceil(total_bytes / ideal_size)`. `calc_accounts_to_combine`, however, decides how many `target_slots_sorted` to make available using the naive theoretical minimum `alive_bytes / ideal_storage_size` (rounded up) [2](#0-1) , and `combine_ancient_slots_packed_internal` unconditionally discards the *entire* batch's work if the real pack output is larger than that slot budget [3](#0-2) . Because account sizes are fully attacker-controlled, an attacker can choose data lengths (e.g., values just over half of the dynamically-computed `ideal_storage_size`) that make the greedy packer produce noticeably more storages than the naive estimate, triggering this bail-out.

### Finding Description
`combine_ancient_slots_packed_internal` computes `ideal_storage_size` dynamically per call as `total_alive_bytes * 2 / max_ancient_slots`, floored at `self.ancient_storage_ideal_size` [4](#0-3) . It then builds `target_slots_sorted` in `calc_accounts_to_combine` by pushing essentially every slot without ref>1 constraints, sized against a theoretical minimum `min_resulting_packed_slots = alive_bytes / ideal_storage_size` (ceiling) [2](#0-1) .

`PackedAncientStorage::pack` then greedily concatenates each slot's `AliveAccounts` list, in slot order, into storages up to `ideal_size`, never splitting an individual account across storages (an account only starts a new storage once the current one would exceed `ideal_size`) [5](#0-4) . This is a "next-fit"-style bin-packer: its known worst-case waste per storage boundary is bounded only by the size of a single item, which for accounts sized around `ideal_size/2` (or larger) can leave close to half of every storage's capacity unused. The existing unit tests only validate this fragmentation is "close to" ideal (`packed.bytes >= ideal_size - largest_account_size`) [6](#0-5) ; they do not assert `pack.len() <= target_slots_sorted.len()`.

If an attacker constructs many old-slot accounts whose sizes are deliberately chosen (e.g., just over `ideal_storage_size/2`, or otherwise chosen so no two of them can share a storage) relative to the dynamically recomputed `ideal_storage_size`, the resulting `pack.len()` from `PackedAncientStorage::pack` can exceed `accounts_to_combine.target_slots_sorted.len()`. When that happens, `combine_ancient_slots_packed_internal` returns early at line 506-509 without writing anything, discarding *all* the work already done in that call — `collect_sort_filter_ancient_slots`, `get_unique_accounts_from_storage_for_combining_ancient_slots`, and `calc_accounts_to_combine` (which invoke `shrink_collect` on every included slot) — for every slot swept into that batch, not just the attacker's own slots.

The only documented mitigation for pack failures in the code comments concerns "accounts with multiple refs" (`many_ref_accounts_can_be_moved`) [7](#0-6) ; there is no explicit guard checking that the bin-packing fragmentation itself will not blow the slot budget for the size-based case described here.

### Impact Explanation
This maps to disproportionate/wasted CPU cost in background cleanup (ancient packing) relative to attacker cost: `shrink_ancient_stats`-tracked work (`collect_sort_filter_ancient_slots`, `shrink_collect` per included slot, sorting, and the `pack()` bin-packing pass) is performed every call to `combine_ancient_slots_packed`, but the result is discarded whenever fragmentation from adversarial sizes pushes `pack.len()` over `target_slots_sorted.len()`. Because `target_slots_sorted` largely tracks the number of slots ingested in the batch (not a corrected, worst-case bin-packing bound), and the recomputed `ideal_storage_size` depends on the same attacker-controlled total bytes each call, the same conditions can recur across many calls, repeatedly wasting the packing pass for the whole batch of ancient slots swept in (not only the attacker's own). This is a denial-of-progress / resource-exhaustion issue in background cleanup, not a consensus, balance, or hash-divergence bug.

### Likelihood Explanation
Feasibility depends entirely on unprivileged, attacker-controlled inputs: an attacker who creates many accounts, chooses their `data_len` (hence `stored_size`), lets them age into ancient slots, and repeats over epochs can influence the size distribution fed to `PackedAncientStorage::pack`. The magnitude of the effect is bounded by the classic "next-fit" bin-packing approximation ratio (roughly up to ~2x extra storages in adversarial cases) and by the recomputed `ideal_storage_size`, which the exact repository code and comments do not further bound against this specific failure mode. Full quantification (e.g., exact `ancient_storage_ideal_size` default and `get_ancient_append_vec_capacity()` constant, and how often the same fragmentation pattern would recur across the `HIGH_SLOT_OFFSET`-driven high-slot rotation meant to guarantee eventual progress) could not be completely confirmed in this review — those definitions were not found within the retrieved code, so the degree of "permanence" versus eventual convergence via the high-slot mechanism remains uncertain.

### Recommendation
Make `target_slots_sorted` sizing (or the check at line 506) robust to the actual worst-case behavior of `PackedAncientStorage::pack` rather than the naive `alive_bytes / ideal_storage_size` estimate — e.g., have `pack()` return whether it could fit within a supplied slot budget and, if not, shrink/redistribute the batch (drop the largest/most-fragmenting slot and retry) instead of discarding the whole batch; alternatively, size storages by a fitting-aware estimate (e.g., first-fit-decreasing by pre-sorting individual accounts, or reserving a safety margin scaled to the largest account size actually observed in the batch) so that `pack.len() <= target_slots_sorted.len()` is guaranteed by construction rather than assumed.

```rust
// accounts-db/src/ancient_append_vecs.rs (adapted from existing test scaffolding,
// e.g. test_pack_ancient_storages_varying / test_combine_ancient_slots_packed_internal)
#[test]
fn poc_adversarial_sizes_exceed_target_slots() {
    // Choose ideal_size and adversarial account sizes such that no two accounts
    // can share one packed storage (each account > ideal_size / 2), forcing
    // pack() to emit ~1 storage per account, while calc_accounts_to_combine's
    // naive `alive_bytes / ideal_size` estimate predicts far fewer required slots.
    let ideal_size: u64 = 1000;
    let adversarial_account_size: usize = 600; // > ideal_size / 2

    // Build N slots each holding 1 adversarial-size account (simulating attacker-controlled data_len).
    let num_slots = 8;
    let (db, storages, slots, _infos) = get_sample_storages(num_slots, Some(adversarial_account_size));

    let original_results = storages
        .iter()
        .map(|store| db.get_unique_accounts_from_storage(store))
        .collect::<Vec<_>>();
    let slots_vec = slots.collect::<Vec<_>>();
    let accounts_to_combine = original_results
        .iter()
        .zip(slots_vec.iter().cloned())
        .map(|(accounts, slot)| AliveAccounts {
            accounts: accounts.stored_accounts.iter().collect::<Vec<_>>(),
            bytes: accounts
                .stored_accounts
                .iter()
                .map(|a| AppendVec::calculate_stored_size(a.data_len()))
                .sum(),
            slot,
        })
        .collect::<Vec<_>>();

    let pack = PackedAncientStorage::pack(
        accounts_to_combine.iter(),
        NonZeroU64::new(ideal_size).unwrap(),
    );

    // naive theoretical minimum used by calc_accounts_to_combine
    let total_bytes: u64 = accounts_to_combine.iter().map(|a| a.bytes as u64).sum();
    let naive_min_slots = total_bytes.saturating_sub(1) / ideal_size + 1;

    // Assert the actual pack output exceeds the naive estimate used to size target_slots_sorted,
    // demonstrating the mismatch that triggers the bail-out at
    // `if pack.len() > accounts_to_combine.target_slots_sorted.len() { return; }`
    assert!(
        pack.len() as u64 > naive_min_slots,
        "expected fragmentation to exceed naive estimate: pack.len()={}, naive_min_slots={}",
        pack.len(),
        naive_min_slots
    );
}
```
Expected result: `pack.len()` exceeds the naive `alive_bytes / ideal_storage_size` estimate that sizes `target_slots_sorted`, reproducing the condition under which `combine_ancient_slots_packed_internal` bails out and discards the batch's cleanup work. A full integration PoC should further wire this through `combine_ancient_slots_packed_internal` across repeated simulated epochs to confirm repeated bail-outs and measure `shrink_ancient_stats` CPU accumulation without resulting storage writes.

```rust
impl<'a> PackedAncientStorage<'a> {
    /// return a minimal set of 'PackedAncientStorage's to contain all 'accounts_to_combine' with
    /// the new storages having a size guided by 'ideal_size'
    fn pack(
        mut accounts_to_combine: impl Iterator<Item = &'a AliveAccounts<'a>>,
        ideal_size: NonZeroU64,
    ) -> Vec<PackedAncientStorage<'a>> {
        let mut result = Vec::default();
        let ideal_size: u64 = ideal_size.into();
        let ideal_size = ideal_size as usize;
        let mut current_alive_accounts = accounts_to_combine.next();
        // starting at first entry in current_alive_accounts
        let mut partial_inner_index = 0;
        // 0 bytes written so far from the current set of accounts
        let mut partial_bytes_written = Saturating(0);
        // pack a new storage each iteration of this outer loop
        loop {
            let mut bytes_total = 0usize;
            let mut accounts_to_write = Vec::default();

            // walk through each set of alive accounts to pack the current new storage up to ideal_size
            let mut full = false;
            while !full && current_alive_accounts.is_some() {
                let alive_accounts = current_alive_accounts.unwrap();
                if partial_inner_index >= alive_accounts.accounts.len() {
                    // current_alive_accounts have all been written, so advance to next set from accounts_to_combine
                    current_alive_accounts = accounts_to_combine.next();
                    // reset partial progress since we're starting over with a new set of alive accounts
                    partial_inner_index = 0;
                    partial_bytes_written = Saturating(0);
                    continue;
                }
                let bytes_remaining_this_slot =
                    alive_accounts.bytes.saturating_sub(partial_bytes_written.0);
                let bytes_total_with_this_slot =
                    bytes_total.saturating_add(bytes_remaining_this_slot);
                let mut partial_inner_index_max_exclusive;
                if bytes_total_with_this_slot <= ideal_size {
                    partial_inner_index_max_exclusive = alive_accounts.accounts.len();
                    bytes_total = bytes_total_with_this_slot;
                } else {
                    partial_inner_index_max_exclusive = partial_inner_index;
                    // adding all the alive accounts in this storage would exceed the ideal size, so we have to break these accounts up
                    // look at each account and stop when we exceed the ideal size
                    while partial_inner_index_max_exclusive < alive_accounts.accounts.len() {
                        let account = alive_accounts.accounts[partial_inner_index_max_exclusive];
                        let account_size = account.stored_size();
                        let new_size = bytes_total.saturating_add(account_size);
                        if new_size > ideal_size && bytes_total > 0 {
                            full = true;
                            // partial_inner_index_max_exclusive is the index of the first account that puts us over the ideal size
                            // so, save it for next time
                            break;
                        }
                        // this account fits
                        partial_bytes_written += account_size;
                        bytes_total = new_size;
                        partial_inner_index_max_exclusive += 1;
                    }
                }

                if partial_inner_index < partial_inner_index_max_exclusive {
                    // these accounts belong in the current packed storage we're working on
                    accounts_to_write.push((
                        alive_accounts.slot,
                        // maybe all alive accounts from the current or could be partial
                        &alive_accounts.accounts
                            [partial_inner_index..partial_inner_index_max_exclusive],
                    ));
                }
                // start next storage with the account we ended with
                // this could be the end of the current alive accounts or could be anywhere within that vec
                partial_inner_index = partial_inner_index_max_exclusive;
            }
            if accounts_to_write.is_empty() {
                // if we returned without any accounts to write, then we have exhausted source data and have packaged all the storages we need
                break;
            }
            // we know the full contents of this packed storage now
            result.push(PackedAncientStorage {
                bytes: bytes_total as u64,
                accounts: accounts_to_write,
            });
        }
        result
    }
```
