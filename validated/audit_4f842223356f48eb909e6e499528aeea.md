### Title
Permanent deposit freeze: failed `BridgeDeposit` system events are never purged from `DepositDataMempool`, permanently blocking a specific `calc_tx_id` from ever minting cBTC - (File: crates/sequencer/src/runner.rs, crates/sequencer/src/deposit_data_mempool.rs)

### Summary
`process_sys_txs` only removes a `BridgeDeposit` from `DepositDataMempool::pending_deposits`/`accepted_deposit_txs` via `remove_deposits`, which is only invoked for successfully-applied deposits (the ones pushed into `all_txs`). When a deposit's `apply_l2_block_txs` returns `EvmSystemTransactionNotSuccessful`, the code reverts the working set, decrements `*nonce`, and `continue`s, leaving the entry's `calc_tx_id` in `pending_deposits` forever. Since `add_deposit_tx` rejects any resubmission whose `calc_tx_id` is already pending, this permanently blocks that deposit's Bitcoin-side funds from ever minting cBTC on L2.

### Finding Description
The binding that should hold is: `pending_deposits.contains(calc_tx_id(deposit)) == true` if and only if that `calc_tx_id` is genuinely awaiting successful on-chain inclusion (i.e., not yet permanently resolved success or failure).

Tracing the code:
- `DepositDataMempool::add_deposit_tx` computes `txid = calc_tx_id(&req)` from only `tx.version`, `tx.vin`, `tx.vout`, `tx.locktime` of the embedded `moveTx` [1](#0-0) , and rejects the insert if that `txid` is already in `pending_deposits` [2](#0-1) .
- `fetch_deposits` reads without removing [3](#0-2) ; removal only happens via `remove_deposits`, which is driven by the caller's list of *successfully included* deposits [4](#0-3) .
- In `process_sys_txs`, a `sys_tx_rlp` is only appended to `all_txs` (the list later used to determine what gets removed from the mempool) after `apply_l2_block_txs` succeeds [5](#0-4) . On `EvmSystemTransactionNotSuccessful` for a deposit event, the code reverts the checkpoint, decrements `*nonce`, and `continue`s to the next event — it never calls anything analogous to `remove_deposits` for this failed entry [6](#0-5) .

Because `calc_tx_id` is derived only from the Bitcoin transaction's `version`/`vin`/`vout`/`locktime`, and not from the full ABI-encoded proof/witness fields used by Bridge.sol for validation, two structurally different `deposit` blobs (different proof/witness content, but same underlying Bitcoin transaction fields) hash to the same `calc_tx_id`. An unprivileged attacker who can observe a target Bitcoin deposit transaction (public on the Bitcoin network, even in mempool) can construct and submit via `citrea_sendRawDepositTransaction` a deposit blob carrying the legitimate transaction's `version`/`vin`/`vout`/`locktime` fields but with a deliberately invalid witness/proof designed to pass initial simulation yet deterministically revert on Bridge.sol execution (`EvmSystemTransactionNotSuccessful`). This entry is accepted into `pending_deposits` first (first inserter wins the txid slot), gets fetched and processed by the sequencer, fails permanently, and — due to the missing removal path — remains in `pending_deposits` forever. The legitimate depositor's later, correct deposit blob with the same `calc_tx_id` is then rejected by `add_deposit_tx`'s duplicate check indefinitely, with no expiry/removal path anywhere in `DepositDataMempool`.

No existing guard (`Auth`, `is_system_caller`, batch-proof/method-id checks, JMT witness checks) prevents this, because the vulnerability is purely in sequencer-local mempool bookkeeping, not in state-transition validity.

### Impact Explanation
This permanently freezes the ability of a specific Bitcoin-side deposit (identified by its `calc_tx_id`) to ever mint cBTC on Citrea L2, matching the "funds permanently frozen" Critical category. The blast radius is per-`calc_tx_id` (i.e., per targeted Bitcoin deposit transaction), but is fully repeatable — an attacker can do this against any deposit they can observe before/concurrently with the legitimate submission, at negligible cost (one crafted RPC call), and the freeze persists across all future L2 blocks/nodes since the sequencer's in-memory `DepositDataMempool` has no expiry mechanism.

### Likelihood Explanation
Preconditions: attacker needs only unprivileged RPC access to call `citrea_sendRawDepositTransaction` with a crafted blob (this is explicitly granted attacker capability), and knowledge of a target Bitcoin deposit transaction's `version`/`vin`/`vout`/`locktime` fields, which are visible on Bitcoin before or as soon as the transaction is broadcast/mined. Cost is a single RPC call plus (if desired) minimal Bitcoin fees to inscribe an equivalent-looking spend; no majority hashrate, no key compromise, no privileged role is needed. The attack is deterministically repeatable against any deposit the attacker can front-run or race, making it a low-cost, high-impact griefing vector.

### Recommendation
In `process_sys_txs` (crates/sequencer/src/runner.rs), on `EvmSystemTransactionNotSuccessful` for a `BridgeDeposit` event, additionally call `DepositDataMempool::remove_deposits` (or an equivalent purge) for that specific failed deposit blob so its `calc_tx_id` is freed from `pending_deposits`/`accepted_deposit_txs`, allowing a corrected/legitimate resubmission. Additionally, consider deriving `calc_tx_id` (or an additional dedup key) from the full deposit proof/witness content — not just `version`/`vin`/`vout`/`locktime` — to prevent a malicious blob with a bogus proof from occupying the same identity slot as the legitimate deposit before it is fetched.

```rust
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
```

```rust
    fn calc_tx_id(req: &Deposit) -> anyhow::Result<[u8; 32]> {
        let call = BridgeContract::depositCall::abi_decode_raw(req, true)
            .map_err(|e| anyhow::anyhow!("Could not decode DepositCall ABI: {e:?}"))?;

        let tx = call.moveTx;

        let mut data = Vec::new();

        data.extend_from_slice(&tx.version.0);
        data.extend_from_slice(&tx.vin.0);
        data.extend_from_slice(&tx.vout.0);
        data.extend_from_slice(&tx.locktime.0);

        let hasher = Sha256::hash(&data);

        let second = Sha256::hash(&hasher);

        Ok(second)
    }
```
