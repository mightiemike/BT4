### Title
Post-validation mutation of `output_data_receivers` lets action receipts exceed `max_receipt_size` after passing size validation - ([File: runtime/runtime/src/lib.rs])

### Summary
`apply_action_receipt` validates every newly created receipt with `validate_receipt(..., NewReceiptMode)` (which enforces `max_receipt_size`) *before* the receipt's `output_data_receivers` are appended [1](#0-0) . Immediately afterward, when the parent receipt has non-empty `output_data_receivers` and the action result is a `ReturnData::ReceiptIndex`, the runtime mutates the *already-validated* new receipt in place by extending its `output_data_receivers` with the parent's list, without re-validating the resulting size [2](#0-1) . This mirrors the jq root cause: a size check passes, then more data is appended afterward to the object that was already accepted as valid, without the invariant ("size <= limit") being re-checked.

### Finding Description
`validate_receipt` computes `borsh::object_length(receipt)` and rejects it if it exceeds `limit_config.max_receipt_size` — but only at the point it's called, right after `apply_action` returns the new receipts and before output-data wiring occurs [3](#0-2) . A `promise_then`/`promise_return`-style DAG can construct a receipt whose size is *exactly* at `max_receipt_size` (so it passes `validate_receipt`), and because the executing receipt itself has `output_data_receivers`, the runtime's post-processing step copies those `output_data_receivers` into the just-validated new receipt via `extend_from_slice`, pushing it over the limit with no subsequent size check [4](#0-3) . The resulting oversized receipt is then serialized, hashed, and forwarded/buffered as a normal receipt. This is exactly the tracked and reproduced bug referenced by `ValidateReceiptMode::ExistingReceipt`'s doc comment ("There is a bug which allows to create receipts that are above the size limit... See https://github.com/near/nearcore/issues/12606") [5](#0-4) , and it is reproduced end-to-end by `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in the test suite [6](#0-5) .

Downstream, `ReceiptSink::forward_or_buffer_receipt`/`try_forward` explicitly clamps the oversized receipt's size to `max_receipt_size` for admission-limit accounting as a documented workaround for issue #12606 [7](#0-6) , meaning the oversized receipt is not rejected but silently let through congestion/bandwidth accounting with an incorrect (clamped) size, which desynchronizes the real byte cost from the accounted cost across the accounting subsystem that is meant to bound `ChunkStateWitness`/congestion size.

### Impact Explanation
This produces a receipt that violates the protocol's `max_receipt_size` invariant (analogous to the jq object entering “invalid state” but being reused as if valid). Because the size-limit is one of the hard limits explicitly designed to bound `ChunkStateWitness` to ~21 MiB (see `max_receipt_size - 4 MiB` in the size-limits doc) [8](#0-7) , oversized receipts undermine the state-witness size guarantees relied on by chunk validators, and the congestion-accounting clamp means the *real* resource cost is undercounted while still being propagated — a path toward state-witness bloat / resource-limit bypass reachable purely from a submitted transaction (no privileged role needed), via ordinary `promise_then`/`promise_return`/`value_return` usage.

### Likelihood Explanation
High feasibility: this is not a hypothetical — it is a confirmed, reproduced, and already tracked bug in this exact codebase (`near/nearcore#12606`), with dedicated regression tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`) demonstrating that an unprivileged contract call can trigger it deterministically by constructing a receipt at exactly `max_receipt_size` and having it be a promise-DAG node with non-empty `output_data_receivers` [9](#0-8) .

### Recommendation
After extending `output_data_receivers` (or any other post-`apply_action` mutation of a new receipt) at `runtime/runtime/src/lib.rs:1161-1169`, re-run `validate_receipt` (or at minimum re-check `borsh::object_length(...) <= max_receipt_size`) on the mutated receipt, and fail the action with `NewReceiptValidationError`/`ReceiptSizeExceeded` if it now exceeds the limit — mirroring the fix pattern of checking size immediately after every mutation, not only once before it, so an “already validated” object is never trusted for size guarantees after further appends (the exact class of defect in the jq CVE).

### Proof of Concept
Reuse the existing repro path already present in the codebase:
1. Deploy `near_test_contracts::rs_contract()`.
2. Call `max_receipt_size_promise_return_method1`, which builds DAG `A -then-> B`; `A` (`max_receipt_size_promise_return_method2`) creates promise `C` with a `FunctionCall` whose args are sized so the resulting receipt for `C` is exactly `max_receipt_size` bytes, then does `promise_return(C)` [10](#0-9) .
3. Because `A`'s own receipt had `output_data_receivers` (its continuation to `B`), the runtime's post-processing copies these into `C`'s already-size-validated receipt, pushing `C` over `max_receipt_size` without re-validation [4](#0-3) .
4. Observe via `assert_oversized_receipt_occurred` that an incoming/outgoing receipt with size `> max_receipt_size` is accepted and propagated by the chain, exactly as asserted by `test_max_receipt_size_promise_return` [11](#0-10) .
