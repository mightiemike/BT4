### Title
Transaction pool computes an incorrect pending base fee at the EIP‑1559 (London) activation block, diverging from consensus-validated block base fee - ([File: crates/chainspec/src/api.rs], [File: crates/consensus/common/src/validation.rs], [File: crates/transaction-pool/src/maintain.rs])

### Summary
The transaction pool's pending-block base-fee estimate is computed via the generic `EthChainSpec::next_block_base_fee` default implementation, which does not special-case the block where the London hardfork activates. Consensus validation, however, explicitly special-cases that exact block and requires `alloy_eips::eip1559::INITIAL_BASE_FEE`. At the London-activation block this produces two different "correct" base fees for the same block: the pool computes `0`/`None`, while consensus validation requires `1_000_000_000` wei. This causes the pool to admit/rank transactions as "pending"/ready that would actually be invalid (fee cap too low) once included in a block that must carry the mandated `INITIAL_BASE_FEE`.

### Finding Description
`EthChainSpec::next_block_base_fee` (the default trait method used by generic pool code) computes the fee purely via `calc_next_block_base_fee` and returns `None` if the parent header has no `base_fee_per_gas` (i.e., the parent is pre-London): [1](#0-0) 

`crates/transaction-pool/src/maintain.rs` calls this same generic method to compute the pool's `pending_block_base_fee`, falling back to `0` when it returns `None`: [2](#0-1) 

That `pending_basefee` is stored in `BlockInfo` and used by the pool to classify transactions into the Pending/BaseFee/Queued subpools (i.e., whether a transaction currently satisfies the dynamic fee-cap requirement): [3](#0-2) [4](#0-3) 

By contrast, consensus header validation explicitly special-cases the exact block at which London "transitions" (activates), using `INITIAL_BASE_FEE` instead of calling the generic `next_block_base_fee` helper for that block: [5](#0-4) 

So at the single block where `is_london_active_at_block` first becomes true (`transitions_at_block == true`), the two code paths diverge:
- Pool (`maintain.rs` → `EthChainSpec::next_block_base_fee`): parent has no `base_fee_per_gas`, so the trait method's `parent.base_fee_per_gas()?` short-circuits to `None`, and `unwrap_or_default()` yields `pending_basefee = 0`.
- Consensus (`validate_against_parent_eip1559_base_fee`): detects the transition and requires `expected_base_fee = INITIAL_BASE_FEE` (1 gwei), independent of the parent's (missing) base fee.

This is exactly the "pool admission diverging from block validity" class: the pool will treat any transaction with `max_fee_per_gas >= 0` as satisfying `ENOUGH_FEE_CAP_BLOCK` and promote it to the Pending subpool for the transition block, while a block actually built for that height must carry `base_fee_per_gas = INITIAL_BASE_FEE`, which will reject/exclude any transaction whose `max_fee_per_gas` is below 1 gwei.

### Impact Explanation
This is a state read (pool's fee threshold) that differs from what the protocol's own header-validation rule computes for the identical block height, i.e., a divergence between transaction-pool admission and block validity/consensus rules — an explicitly in-scope "High" impact category. Concretely:
- Low/zero-fee transactions get promoted into the Pending subpool and can be selected by a builder to construct the London-activation block, producing an invalid/rejected block or transactions that fail validation once actually executed against the mandated `INITIAL_BASE_FEE`.
- Conversely, legitimate fee-cap transactions might be mis-ranked relative to the real, higher required base fee.

### Likelihood Explanation
The divergence is deterministic and reproducible, but its trigger window is narrow: it only manifests at the exact block where the London hardfork activates for a given chain configuration (a one-time, single-block event per chain). This has already occurred historically on Ethereum mainnet (irrelevant now) but remains live for any custom/dev/test chain spec that schedules London activation at a specific block number (which is a supported and exercised configuration path in `reth_chainspec`/`EthereumHardforks`), so the bug is reachable without any privileged actor — it is purely a function of chain configuration and block height.

### Recommendation
Make the pool's fee estimation consistent with consensus validation by reusing the same special-cased expected-base-fee computation (i.e., factor the `transitions_at_block` / `INITIAL_BASE_FEE` logic out of `validate_against_parent_eip1559_base_fee` into `EthChainSpec::next_block_base_fee`, or have the pool call a shared helper) so that both paths compute an identical value at the London activation boundary.

### Proof of Concept
1. Configure a chain spec where `London` activates at a specific future block number `N` (supported by `EthereumHardforks`/`ChainSpec`).
2. Advance the chain to block `N-1` (pre-London, header has no `base_fee_per_gas`).
3. Observe transaction-pool maintenance calling `chain_spec.next_block_base_fee(tip.header(), tip.timestamp())` in `crates/transaction-pool/src/maintain.rs:444-447`, which returns `None` (parent has no base fee) → `pending_block_base_fee = 0` via `unwrap_or_default()`.
4. Submit/keep a low-fee EIP‑1559 transaction with `max_fee_per_gas < 1_000_000_000`; the pool promotes it to the Pending subpool because `0 <= max_fee_per_gas`.
5. Compare against `validate_against_parent_eip1559_base_fee` in `crates/consensus/common/src/validation.rs:319-348`, which for block `N` (the transition block) requires `expected_base_fee = INITIAL_BASE_FEE = 1_000_000_000`.
6. A block built at height `N` including the low-fee transaction, or reflecting the pool's `0` fee expectation, is inconsistent with the consensus-mandated `INITIAL_BASE_FEE`, demonstrating the pool-vs-validation divergence.

/// Validates the base fee against the parent and EIP-1559 rules.
#[inline]
pub fn validate_against_parent_eip1559_base_fee<ChainSpec: EthChainSpec + EthereumHardforks>(
    header: &ChainSpec::Header,
    parent: &ChainSpec::Header,
    chain_spec: &ChainSpec,
) -> Result<(), ConsensusError> {
    if chain_spec.is_london_active_at_block(header.number()) {
        let base_fee = header.base_fee_per_gas().ok_or(ConsensusError::BaseFeeMissing)?;

        let expected_base_fee = if chain_spec
            .ethereum_fork_activation(EthereumHardfork::London)
            .transitions_at_block(header.number())
        {
            alloy_eips::eip1559::INITIAL_BASE_FEE
        } else {
            chain_spec
                .next_block_base_fee(parent, header.timestamp())
                .ok_or(ConsensusError::BaseFeeMissing)?
        };
        if expected_base_fee != base_fee {
            return Err(ConsensusError::BaseFeeDiff(GotExpected {
                expected: expected_base_fee,
                got: base_fee,
            }))
        }
    }

    Ok(())
}
