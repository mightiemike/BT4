I have sufficient evidence to write up the finding now. The key asymmetry is confirmed: `CallUEAExecutePayload` (user-derived path) explicitly parses and enforces `universal_payload.GasLimit` [1](#0-0) , while `CallExecuteUniversalTx` (module-as-sender path used for `isCEA` smart-contract recipients) passes `nil` for `gasLimit`, relying solely on the EVM fork's internal default [2](#0-1) , with the payload's declared `GasLimit` only checked *after* execution, inside `DeductGasFeesFromReceipt`, purely as a fee-accounting sanity check [3](#0-2) .

### Title
Unbounded EVM gas limit for attacker-controlled CEA recipient contracts enables gas-griefing of Universal Validators during inbound voting - (File: x/uexecutor/keeper/evm.go)

### Summary
This is the Push Chain analog of the "malicious module/hook may not be removed" bug class. In the external report, an untrusted callee (module/hook) could consume unbounded gas during a low-level call it controls, griefing the caller. In Push Chain, `CallExecuteUniversalTx` — used to invoke `executeUniversalTx` on an attacker-deployed "CEA" recipient contract for `isCEA` inbounds — calls `DerivedEVMCall` with `gasLimit = nil` instead of enforcing the `UniversalPayload.GasLimit` the way the sibling `CallUEAExecutePayload` path does.

### Finding Description
For `isCEA` inbounds whose recipient is a plain deployed contract (not a UEA), `ExecuteInboundGasAndPayload` / `ExecuteInboundFundsAndPayload` invoke `k.CallExecuteUniversalTx(...)` [4](#0-3) , which builds the derived EVM call like this:

```go
return k.evmKeeper.DerivedEVMCall(
    ctx,
    recipientABI,
    ueModuleAccAddress,
    recipientAddr,
    big.NewInt(0),
    nil,          // gasLimit — no explicit cap
    true,
    false,
    true,
    &nonce,
    "executeUniversalTx",
    ...
)
``` [2](#0-1) 

Compare this to the user-derived UEA path, `CallUEAExecutePayload`, which parses `universal_payload.GasLimit` and passes it explicitly to `DerivedEVMCall` [1](#0-0) . The `GasLimit` field carried in `UniversalPayload` is only consulted *after* the EVM call completes, as an accounting check inside `DeductGasFeesFromReceipt`:

```go
gasUsedBig := new(big.Int).SetUint64(receipt.GasUsed)
if gasUsedBig.Cmp(abiPayload.GasLimit) > 0 {
    return fmt.Errorf("gas used (%d) exceeds gas limit (%s)", receipt.GasUsed, abiPayload.GasLimit.String())
}
``` [3](#0-2) 

Since the recipient's code executes fully before this check runs, a malicious recipient contract can consume gas up to whatever "sensible default" `DerivedEVMCall` falls back to when `gasLimit` is `nil` — a value not bound to the small `GasLimit` an attacker declares in the crafted inbound. The post-hoc check only causes the `CacheContext` to be discarded (`writeCache()` skipped) and the `PCTx` marked `FAILED` with a "gas fee deduction failed" message [5](#0-4)  — it does not undo the computational cost already incurred by the EVM interpreter.

This code path runs inside `MsgVoteInbound`, a gasless message type [6](#0-5) , executed independently by every Universal Validator casting a vote toward quorum. Because the recipient contract's bytecode is entirely attacker-controlled (any user can submit an `Inbound` claiming an arbitrary deployed contract as `Recipient` with `IsCEA: true`, as shown in the CEA test setup that just points `Recipient` at a self-deployed contract) [7](#0-6) , an attacker can deploy a recipient that deliberately burns close to the uncapped default gas budget on every invocation (e.g., a tight loop), and repeat this via new `TxHash`/`LogIndex` inbounds at no cost to itself, since the vote transactions cost the attacker nothing and the gas actually "spent" is real computational load on each honest validator node.

### Impact Explanation
This does not steal or freeze funds — `writeCache()` is correctly skipped, so no state corruption or fund loss occurs, matching the discipline the codebase already applies for the "free execution" gap (see the `F-2026-16738` regression test) [8](#0-7) . The impact is denial-of-service class: repeated, cheap (gasless), unprivileged submissions of inbounds targeting gas-burning CEA recipient contracts force every Universal Validator processing `MsgVoteInbound` for that inbound to redundantly execute uncapped EVM computation, which can degrade UV throughput/liveness for inbound finalization — a reachable, non-network-level DoS vector caused purely by ordinary user-submitted inbound data, without any privileged or malicious-validator assumption.

### Likelihood Explanation
The trigger requires only: (1) deploying an arbitrary contract on a supported source chain that implements `executeUniversalTx` and burns gas, and (2) getting that inbound observed and voted on by honest UVs to quorum — both are ordinary, unprivileged actions available to any user, and `MsgVoteInbound` costs the submitter nothing, so the attack can be repeated at negligible cost.

### Recommendation
Mirror the `CallUEAExecutePayload` pattern: pass the inbound's declared `UniversalPayload.GasLimit` (parsed and bounds-checked) as the explicit `gasLimit` argument to `DerivedEVMCall` inside `CallExecuteUniversalTx`, so the EVM interpreter itself enforces the cap before executing arbitrary recipient bytecode, rather than relying on a post-execution fee-accounting check that only prevents state persistence, not gas/computation griefing.

### Proof of Concept
1. Attacker deploys `MaliciousRecipient` on a supported EVM source chain implementing `executeUniversalTx(...)` with a loop that consumes gas up to whatever `DerivedEVMCall`'s nil-gasLimit default allows.
2. Attacker crafts/submits (via the normal inbound observation path) an `Inbound` with `IsCEA: true`, `Recipient: MaliciousRecipient`, and a `UniversalPayload.GasLimit` set arbitrarily low (e.g. `"21000"`) so the post-hoc fee check in `DeductGasFeesFromReceipt` will fail and roll back state.
3. Three honest UVs each submit `MsgVoteInbound` for this inbound to reach quorum; each execution of `ExecuteInboundGasAndPayload`/`ExecuteInboundFundsAndPayload` calls `CallExecuteUniversalTx` with `gasLimit=nil`, letting `MaliciousRecipient` burn gas up to the uncapped default on every one of the three (or more, if re-voted/retried) validator executions.
4. Each vote transaction succeeds (per existing test behavior) despite the internal `CallExecuteUniversalTx`/fee-deduction failure [9](#0-8) , so the attacker can repeat this with new `TxHash` values indefinitely at zero cost, while each occurrence forces every UV node to burn real computation processing the malicious contract.
