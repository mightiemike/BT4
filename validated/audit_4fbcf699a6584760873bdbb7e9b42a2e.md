### Title
Webhook shop domain is trusted from unsigned `X-Shopify-Shop-Domain` header, allowing cross-tenant shop spoofing when replaying a self-obtained valid HMAC - (File: packages/apps/shopify-api/lib/webhooks/process.ts)

### Summary
The webhook HMAC verification in `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts`) only signs `rawBody` with `config.apiSecretKey`; the `X-Shopify-Shop-Domain` header is never included in the HMAC computation. `webhooks.process` (`packages/apps/shopify-api/lib/webhooks/process.ts`) then passes `webhookCheck.domain` — taken verbatim from that unsigned header — directly to the registered handler `callback` as the `shop` argument. Any party who has legitimately obtained one valid `(rawBody, HMAC)` pair for the app (e.g., by installing the app on their own store) can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value, causing the handler to run with an attacker-chosen `shop`.

### Finding Description
- `validateHmacFromRequestFactory` computes/verifies the HMAC solely over `rawBody` using `config.apiSecretKey` via `validateHmacString` → `createSHA256HMAC(config.apiSecretKey, data, format)` and compares with `safeCompare`: [1](#0-0) 
- `validateFactory` in `validate.ts` runs this HMAC check and, if valid, separately extracts header fields including `domain` from `X-Shopify-Shop-Domain` with no cross-check against the signed body: [2](#0-1) 
- `callWebhookHandlers` in `process.ts` invokes `handler.callback(topic, webhookCheck.domain, rawBody, webhookId, apiVersion, context)`, passing the header-derived, unsigned `domain` straight to the app-registered callback: [3](#0-2) 
- Because `config.apiSecretKey` is the app's single client secret shared across every shop that installs the app (not a per-shop secret), any user who installs the app on their own shop can trigger a real webhook delivery to themselves and thereby possess a valid `(rawBody, HMAC)` pair signed with that shared secret.
- That attacker can then POST directly to the app's webhook endpoint (bypassing Shopify's delivery infrastructure entirely) with the captured body/HMAC unchanged but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`. The HMAC check passes (it never covered the domain), and `webhooks.process` invokes the handler with `shop = 'victim-shop.myshopify.com'`.
- Neither `validate.ts` nor `process.ts` performs any check that the domain header corresponds to a shop actually entitled to send that payload (e.g., cross-referencing an installed session/access token for that shop, or embedding/verifying the shop inside the signed payload).

### Impact Explanation
This is a genuine cross-tenant trust confusion (TENANT_ISOLATION) primitive at the library level: the webhook processing pipeline reports a shop identity to the host application's business logic that is not covered by any cryptographic guarantee. Concrete impact is scoped to how the host callback uses `shop` — for apps that key any state mutation, cache invalidation, uninstall/GDPR handling, or queued jobs off the `shop` parameter passed by `process()`, an attacker can inject attacker-controlled webhook body content attributed to a victim shop, causing cross-tenant data confusion or DoS/log-poisoning of the victim tenant's processing pipeline. It maps to Shopify's "cross-tenant data/state access" bounty impact class, though actual severity is bounded by what a given app's webhook callback does with the (unauthenticated) shop value.

### Likelihood Explanation
Feasibility is moderate-to-high and fully unprivileged: the only precondition is installing the target public app on an attacker-controlled shop (a normal, self-service action requiring no special access) and capturing one legitimately delivered webhook body/HMAC pair, then replaying it directly to the app's HTTP webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No secret is stolen — the attacker uses their own genuinely-issued HMAC, and the header is trivially attacker-controlled since it's not authenticated. This is repeatable for any webhook topic the attacker's shop is subscribed to.

### Recommendation
Do not treat `X-Shopify-Shop-Domain` as authenticated shop identity on its own. At minimum, the library should document this trust boundary clearly and/or provide a helper that requires host apps to verify the domain against a stored, previously-authenticated session/access-token record for that shop before acting on webhook data (i.e., reject webhooks for shops the app doesn't have valid session data for, matching how OAuth session storage already tracks installed shops). Longer-term, consider incorporating the shop domain into the HMAC-covered payload validation path where possible, or explicitly surfacing an "untrusted domain header" warning in `WebhookValidationValid`/docs so host apps know they must re-validate `domain` before using it for tenant-scoped operations.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/webhooks/__tests__/process-domain-spoof.test.ts
import {shopifyApi, LATEST_API_VERSION} from '../../..';
import {testConfig} from '../../../__tests__/test-config';
import {DeliveryMethod} from '../types';

test('attacker-controlled X-Shopify-Shop-Domain header is passed to callback despite unrelated valid HMAC', async () => {
  const shopify = shopifyApi(testConfig());
  const callback = jest.fn();

  shopify.webhooks.addHandlers({
    ORDERS_CREATE: [
      {deliveryMethod: DeliveryMethod.Http, callback},
    ],
  });

  const rawBody = '{"attacker":"payload"}'; // body attacker legitimately received on their own shop
  const hmac = /* HMAC-SHA256(apiSecretKey, rawBody) that attacker obtained from their own real webhook delivery */
    validHmacForRawBodyOnAttackerShop;

  await shopify.webhooks.process({
    rawBody,
    rawRequest: {
      headers: {
        'X-Shopify-Topic': 'orders/create',
        'X-Shopify-Hmac-Sha256': hmac,
        'X-Shopify-Shop-Domain': 'victim-shop.myshopify.com', // spoofed, not part of HMAC
        'X-Shopify-Api-Version': LATEST_API_VERSION,
        'X-Shopify-Webhook-Id': 'attacker-generated-id',
      },
    },
    rawResponse: {} as any,
  });

  // Callback receives spoofed shop despite HMAC only proving body+secret validity
  expect(callback).toHaveBeenCalledWith(
    'ORDERS_CREATE',
    'victim-shop.myshopify.com',
    rawBody,
    'attacker-generated-id',
    LATEST_API_VERSION,
    undefined,
  );
});
```
