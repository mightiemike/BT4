### Title
Off-by-one in `handle_poison_microblock`'s maturity boundary lets a miner/report-orderer make a valid poison report ineffective at the exact maturity block, keeping a slashed coinbase - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`handle_poison_microblock` accepts a poison-microblock report as long as `height + MINER_REWARD_MATURITY >= current_height`, but `find_mature_miner_rewards`/`calculate_matured_miner_rewards` for the block at `current_height == height + MINER_REWARD_MATURITY` is invoked in `setup_block`/`inner_setup_block` *before* that same block's own transactions (including any poison report tx it contains) are processed. This creates a one-block window at the exact boundary in which a report is transaction-valid but functionally too late, letting an unpunished miner keep a coinbase that should have been clawed back while the honest reporter still pays a fee.

### Finding Description
The claimed equality is: "the last block height at which a report is accepted (`height + MINER_REWARD_MATURITY`) must equal the last height *before* `find_mature_miner_rewards` computes `reward_height` and pays out."

- `handle_poison_microblock` rejects only if `height.checked_add(MINER_REWARD_MATURITY) < current_height`, i.e. it **accepts** reports up to and including `current_height == height + MINER_REWARD_MATURITY` [1](#0-0) .
- `find_mature_miner_rewards` is invoked with `tip_stacks_height` equal to the block currently being appended, and computes `reward_height = tip_stacks_height - MINER_REWARD_MATURITY`, then looks up `get_poison_microblock_report(clarity_tx, reward_height)` [2](#0-1) .
- Crucially, this lookup happens inside block *setup* (`inner_setup_block` / `setup_normal_block_processing`), which runs **before** the block's own transactions are processed via `process_block_transactions` [3](#0-2)  and, for epoch-2.x blocks, at [4](#0-3)  followed by transaction processing later at [5](#0-4) .

So, for a poison pubkey-hash inserted at height `H`, the report is only *effective* if it lands in the chain state by the end of block `H + MINER_REWARD_MATURITY - 1`, because `find_mature_miner_rewards` for the block at height `H + MINER_REWARD_MATURITY` reads report state that was frozen before that block's own transactions ran. But `handle_poison_microblock`'s guard (`<` instead of `<=`) still treats a report submitted in block `H + MINER_REWARD_MATURITY` itself as valid. The transaction succeeds, is committed, costs the reporter a fee — yet `find_mature_miner_rewards` for that maturity height already executed using the pre-transaction (report-less) state, so the clawback never applies and the offending miner's coinbase is paid out normally.

None of the existing guards (`check_tenure_tx`, `verify_signer_signatures`, `validate_vrf_seed`, static validators, MARF hashing) touch this ordering; it is purely a Clarity-level height check vs. block-setup ordering mismatch.

### Impact Explanation
This is deterministic across all honest nodes (every node performs `setup_block` before `process_block_transactions` in the same way), so there is **no chain split, no non-reproducible state root, and no invalid-block-accepted-network-wide** condition — every node computes the same (wrong) outcome. The concrete effect is bounded to: (a) the honest reporter's transaction fee is spent for nothing, and (b) the malicious miner who produced the poisoned microblock stream keeps a coinbase that should have been slashed, if they (as the current miner/miner-slot holder) can arrange for the report to land in exactly the boundary block rather than an earlier one. This matches the "poison or reward mis-payment bounded to fees" category (High), not a Critical chain-split/double-payment scenario, since the payout is still internally consistent and identical across all nodes.

### Likelihood Explanation
The attacker needs only their own miner slot (no majority stake) to influence which block a competing/incoming poison report transaction lands in — e.g. by simply not including it earlier and including it (or letting it be included) exactly in the block whose height equals `H + MINER_REWARD_MATURITY`. This is fully within the "single miner slot" unprivileged capability described. It requires precise height accounting (public and computable from the microblock-pubkey-hash-height record) but no unusual resources. It is repeatable per-poisoned-key/miner instance, once per boundary.

### Recommendation
Change the acceptance condition in `handle_poison_microblock` from `height + MINER_REWARD_MATURITY < current_height` (reject) to `height + MINER_REWARD_MATURITY <= current_height` (reject), i.e. require `height.checked_add(MINER_REWARD_MATURITY).expect(...) < current_height` to become `<=`, so that a report is only accepted up to and including block `H + MINER_REWARD_MATURITY - 1`, matching the last block whose `find_mature_miner_rewards` invocation can still observe it before that reward matures.

### Proof of Concept
Rust integration test plan (chainstate test harness):
1. Mine/insert a microblock stream whose public key hash is stored at height `H` (via a poisoned microblock fork setup as in existing poison-microblock tests).
2. Advance the chain to height `H + MINER_REWARD_MATURITY - 1` and submit a poison-microblock report tx there in one fork branch (control case) — assert the reporter is credited with the slashed coinbase once maturity is processed at `H + MINER_REWARD_MATURITY`.
3. In a second fork branch, delay the same report tx until it is included in the block at exactly height `H + MINER_REWARD_MATURITY` — assert the tx is accepted (no `InvalidStacksTransaction`) yet, after `finish_block`/`find_mature_miner_rewards` runs, the coinbase recipient balance shows the *original miner* was paid (not the reporter), i.e. `get_poison_microblock_report(reward_height=H)` returns `None` at the time of reward computation despite the report existing in the block's own transaction set.
4. Assert both sides of the equality explicitly: `height + MINER_REWARD_MATURITY - 1` (last effective report height) vs. `tip_stacks_height - MINER_REWARD_MATURITY` evaluated at the block that actually pays the reward, showing they diverge by exactly one block at the current implementation, and converge after applying the recommended `<=` fix.
