### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify tooling accept a corrupted/wrong state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check that compares a locally re-executed `TransactionOutput` against the authenticated `TransactionInfo` (the leaf committed into the transaction accumulator and covered by validator signatures). It validates status, gas used, write-set hash, and event root hash, but the code contains an explicit acknowledgment that it does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [1](#0-0) .

### Finding Description
The function performs targeted `ensure!` checks for status, gas, write-set hash and event root hash [2](#0-1) , then returns `Ok(())` without ever inspecting `txn_info.state_checkpoint_hash()`, the hot-state checkpoint hash, or the position-state checkpoint hash [1](#0-0) . The comment in the code itself documents the gap: "this comparator ignores the checkpoint hashes... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [1](#0-0) .

This matters because `state_checkpoint_hash` is the field that binds a `TransactionInfo` to a specific Jellyfish Merkle / state-summary root (main state, and — once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled — the hot-state and native-position roots too) [3](#0-2) . This same accessor is used elsewhere in `do_ledger_update.rs` where `TransactionInfo` is assembled from the state-checkpoint output for hashing into the transaction accumulator [4](#0-3) . `ensure_match_transaction_info` is used as the authoritative cross-check between execution output and committed `TransactionInfo` in the debugger/CLI replay tooling (`aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`) and in `execution/executor/src/chunk_executor/mod.rs`.

The consequence: if a bug in `DoStateCheckpoint`/`do_state_checkpoint.rs` (which independently computes `state_checkpoint_hashes`, `hot_state_checkpoint_hashes`, and `position_state_checkpoint_hashes` per-transaction, see the index-based construction at lines 82/101-103/107-109 in `do_ledger_update.rs`) produces a wrong state root for a given transaction — e.g., a mismatched index between the "latest" vs "checkpoint" summaries in the native-position accumulation logic in `do_state_checkpoint.rs` (lines 98-191, which juggles `parent_latest`, `new_ckpt`, and range-based `collect()` calls per checkpoint index) — the replay/verification path that is supposed to catch such state divergence (`ensure_match_transaction_info`) will not detect it, because it never compares the checkpoint hash fields at all.

### Impact Explanation
This breaks the "authenticated committed-state must survive/verify against the correct VM result" invariant required by the task's State-Integrity Gate: a wrong state/hot-state/position-state root that diverges from correctly re-executed output can pass `replay_on_archive`-style verification silently. In a hard-fork/replay/tooling context this is a proof-integrity blind spot — operators and auditors relying on this comparator to validate historical state roots (including the newer native-position feature) would get a false "match" even though the underlying committed root is wrong. This is exactly the kind of "authenticated API or state-view output bound to the wrong version/root" and "replay path... reinterpreting committed data into a different ledger state" scenario in scope.

### Likelihood Explanation
The bug is not by itself an attacker-triggerable state corruption — it's a missing verification step. However, its likelihood of mattering is tied directly to the correctness of `DoStateCheckpoint`'s newly-added native-position/hot-state hash computation, which is complex (index-aligned parallel arrays, checkpoint-vs-latest splitting) and explicitly still gated behind an unreleased feature flag (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`). The code authors themselves flagged this exact risk with a TODO, indicating it is a known, not-yet-fixed gap rather than a theoretical concern. Because the feature is not yet enabled in production, current impact is latent, but the check should be fixed before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` ships, as the TODO itself states.

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality between the locally computed state/hot-state/position-state checkpoint hashes (when present) and `txn_info.state_checkpoint_hash()` / the hot-state and position-state accessors, mirroring the existing `write_set_hash`/`event_root_hash` pattern, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any consumer that depends on this comparator for integrity) is enabled.

### Proof of Concept
No exploit PoC is applicable — this is a missing-assertion/verification-gap finding, not an attacker-triggerable state corruption by itself. The proof is the code itself: `ensure_match_transaction_info` only checks status/gas/write-set-hash/event-root-hash [2](#0-1)  and explicitly documents that checkpoint hashes are skipped [1](#0-0) , meaning any latent bug in the (independently, and newly, computed) `state_checkpoint_hashes` / `hot_state_checkpoint_hashes` / `position_state_checkpoint_hashes` arrays in `do_state_checkpoint.rs` would not be caught by replay verification that relies on this function.
