### Title
Deleting the protocol treasury account permanently halts chunk application at every future epoch boundary - (File: `runtime/runtime/src/lib.rs`)

### Summary
`Runtime::update_validator_accounts` credits the protocol treasury account with its epoch reward by looking it up with `get_account` and treating a missing account as a fatal `StorageInconsistentState` error rather than skipping it. Because `protocol_treasury_account_id` is an ordinary account (not automatically protected from `DeleteAccount`), anyone holding its access key can delete it via a single unprivileged `DeleteAccount` transaction. On the very next epoch boundary, the deterministic reward-crediting code path hits the "account not found" branch and returns a fatal storage error, causing every honest node applying that chunk to fail identically — a protocol-level, transaction-triggered halt, mirroring the "stale reward entry causes revert" pattern from the referenced Maverick report.

### Finding Description
`RewardCalculator::calculate_reward` unconditionally inserts a reward entry for `protocol_treasury_account` into its reward map every epoch, independent of whether that account currently exists: [1](#0-0) 

At the following epoch boundary, `Runtime::update_validator_accounts` attempts to credit this reward to the treasury account. If the treasury account is not also a staking validator, the code does a mandatory `get_account` lookup and converts "account missing" into a fatal, un-recoverable `StorageInconsistentState` error instead of skipping the stale/removed entry: [2](#0-1) 

This is structurally identical to the referenced bug class: an array/map of "reward" entries can contain a stale reference (a reward token that was removed in the audited contract; here, an account that was deleted) whose accumulated value is *not* cleared from the reward-accounting structure, and the claiming/crediting loop does not defensively skip that stale entry — it dereferences/looks it up directly and reverts the whole operation when it is missing.

The treasury account can be deleted by its own key holder through the ordinary, unprivileged `DeleteAccount` action, provided it is not staking, its storage usage is below `MAX_ACCOUNT_DELETION_STORAGE_USAGE`, and any gas-key balances are below the burn threshold — none of these are treasury-specific protections: [3](#0-2) 

Nothing in `action_delete_account` or in the `EpochManager`/`RewardCalculator` code checks or prevents the protocol treasury account from being deleted, and nothing removes/updates `protocol_treasury_account_id` when this happens (it is a fixed value from genesis config, not derived from live account existence): [4](#0-3) 

### Impact Explanation
Once the treasury account is deleted, `finalize_epoch`/`calculate_reward` will keep producing a non-zero (or zero, but still keyed) reward entry for `protocol_treasury_account` every subsequent epoch, and `update_validator_accounts` will keep hitting the `ok_or_else(StorageInconsistentState(...))` branch on every chunk that processes a `ValidatorAccountsUpdate` at an epoch boundary. `StorageInconsistentState` is treated as a fatal storage error in the runtime and is deterministic across all honest nodes (since state, config, and code are identical), so every node independently fails to apply the chunk at that height. This satisfies the "transaction-triggered halt" impact criterion: a single unprivileged transaction (self-`DeleteAccount` on the treasury account) permanently prevents the chain from progressing past the next epoch boundary, freezing all validator rewards and blocking all further transactions network-wide — a Critical/High-severity liveness failure, not merely a "no impact" edge case.

### Likelihood Explanation
The path is directly reachable by one signed transaction from the account that legitimately controls the treasury account's private key. This does not require any special validator, operator, or protocol privilege beyond holding the treasury account's own key (or its access key), which is the same class of actor considered "unprivileged" for the purpose of this analysis (a normal `DeleteAccount` action from an ordinary account, not a malicious validator/operator/node). Because `check_actor_permissions`/`action_delete_account` only checks staking status, storage size, and gas-key balance — never "is this the treasury account" — there is no protocol-level barrier stopping the deletion. Once deleted, the fatal error path is deterministic and will trigger at the very next epoch finalization with certainty, since `calculate_reward` always emits a treasury entry.

### Recommendation
In `Runtime::update_validator_accounts`, treat a missing protocol treasury account the same way `RewardCalculator`/`EpochManager` should treat a removed validator: skip crediting silently (or route the un-creditable reward to burn/ treasury-recreation) instead of returning a fatal `StorageInconsistentState`. Additionally, either (a) prevent deletion of the account configured as `protocol_treasury_account_id` at the action-validation layer, or (b) make `calculate_reward`/`finalize_epoch` tolerant of a non-existent treasury account by checking existence before crediting and adjusting `minted_amount`/supply accounting accordingly, so a self-inflicted or malicious deletion of the treasury account cannot escalate into a network-wide state-transition failure.

### Proof of Concept
1. Note the genesis `protocol_treasury_account` (e.g., `near`), which starts with a normal balance, no locked stake, and small storage usage (no access-key/contract bloat beyond `MAX_ACCOUNT_DELETION_STORAGE_USAGE`).
2. Have the holder of that account's access key submit a single `DeleteAccount` transaction targeting itself (`action_delete_account`, `runtime/runtime/src/actions.rs:330`), which succeeds because the account is not staking and is small enough to delete.
3. Wait for the current epoch to finalize. `EpochManager::finalize_epoch` calls `RewardCalculator::calculate_reward`, which unconditionally inserts `res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury)` (`chain/epoch-manager/src/reward_calculator.rs:84`).
4. On the first block of the new epoch, `Runtime::update_validator_accounts` runs `get_account(state_update, account_id)?.ok_or_else(...)` for the (now-deleted) treasury account (`runtime/runtime/src/lib.rs:1810-1815`) and returns `Err(RuntimeError::StorageError(StorageInconsistentState(...)))`.
5. Every node applying this chunk independently fails identically, since the same account state and reward calculation feed into the same code path — the chain cannot advance past this block, producing a permanent, transaction-triggered halt.

    account: &mut Option<Account>,

    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,

    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
