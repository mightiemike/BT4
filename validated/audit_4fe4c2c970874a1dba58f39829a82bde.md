## Finding

### Title
Wallet Contract's `CHAIN_ID` is a compile-time constant baked into the WASM binary, enabling Ethereum-style signature replay across a NEAR chain fork - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The NEAR Wallet Contract (used to let ETH-implicit accounts sign EIP-155/EIP-2930-style transactions that get relayed into native NEAR actions) validates the `chain_id` field of the user's Ethereum transaction against a hardcoded constant `CHAIN_ID` that is baked into the contract at compile time, rather than derived from the actual live network the contract executes on. This is structurally identical to the reported bug class: a "domain separator" fixed at deployment instead of bound dynamically to the chain the contract is running on, which becomes replayable if the chain forks into two live networks sharing the same account/contract state.

### Finding Description
`CHAIN_ID` is defined as: [1](#0-0) 

The comment explicitly states the value is fixed "to allow this contract to be easily compiled with the appropriate value for the network it will be deployed on" (397 for mainnet, 398 for testnet) — i.e., it is a deployment-time constant embedded in the WASM, analogous to `DOMAIN_SEPARATOR` being computed once in `GSP::init` with a hardcoded `chainId`.

This constant is used as the sole binding between a user's signed Ethereum-style transaction and the specific NEAR network it is authorized for: [2](#0-1) 

The check `tx.chain_id != Some(CHAIN_ID)` is the entire replay-protection mechanism tying a signature to "this network." Because `CHAIN_ID` is compiled into the deployed WASM bytecode and never re-derived from the runtime environment (there is no call to anything like the genesis `chain_id` at execution time), any two live networks that both run the same compiled wallet-contract binary (e.g., the two sides of a contentious hard fork that both retain the deployed contract and account state) will accept exactly the same signed relayer payload.

Users sign transactions via `crypto::sign_transaction` over an `EthTransactionKind`/`Transaction2930` containing this same `chain_id` field, and relayers submit them through `rlp_execute`: [3](#0-2) 

Nonce protection (`self.nonce`) only prevents replay *within* a single contract instance's own state; if the fork duplicates that state (both forks start from the identical pre-fork nonce), the same signed transaction remains valid and unused on both chains simultaneously.

### Impact Explanation
If NEAR undergoes a hard fork producing two persistent chains that both continue to host the same Wallet Contract deployment and the same eth-implicit account state (nonce, keys, balances), any relayer (or the attacker acting as relayer) can replay a previously-submitted, validly-signed RLP transaction on the second fork. Because the wallet-contract executes native NEAR actions (`Transfer`, `FunctionCall`, `AddKey`, `DeleteKey`) on behalf of the ETH-implicit account, this results in unauthorized value movement / unauthorized action execution on the forked chain without the user re-signing anything — the exact "concrete unauthorized value movement" class called out in the validation criteria.

### Likelihood Explanation
This requires a NEAR hard fork event that produces two chains sharing identical pre-fork wallet-contract state — a low-frequency but historically real event class in blockchains (the report's own example, ETH/ETC, is precisely this scenario). Given `CHAIN_ID` is a build-time constant rather than a value re-derived per-execution from the actual running chain, there is no mitigation once such a fork occurs: every ETH-implicit account using the wallet contract is exposed simultaneously.

### Recommendation
Do not bake `CHAIN_ID` into the wallet contract as a compile-time constant tied only to "mainnet vs testnet." Instead, derive/bind the value that gates `tx.chain_id` from a runtime-observable, fork-distinguishing property of the chain itself (e.g., reading it dynamically, or incorporating a per-fork discriminator into the signed payload/validation the same way EIP-2612 remediation recomputes `DOMAIN_SEPARATOR` per-signature instead of caching it at deployment).

### Proof of Concept
1. Deploy the Wallet Contract (as done in `integration-tests/src/tests/features/wallet_contract.rs`) with `CHAIN_ID = 397` compiled in, on Network A.
2. Create an eth-implicit account, fund it, and have the user sign an `Transaction2930` with `chain_id: 397` calling `rlp_execute` to transfer funds to `receiver_id` — see `create_rlp_execute_tx` / `validate_tx_relayer_data`: [4](#0-3) 
3. Suppose Network A hard-forks into Network A and Network A' at the block right after this transaction is submitted but before the relayer submits it on-chain (or the fork happens to re-diverge from a state snapshot that predates consumption of the nonce on one branch). Both forks run byte-identical wallet-contract code with the same `CHAIN_ID = 397` and the same pre-fork nonce.
4. The relayer submits the same signed RLP bytes to both Network A and Network A'. `validate_tx_relayer_data` on each network independently accepts the transaction because `tx.chain_id == Some(397)` on both, and each network's independent nonce state accepts nonce N once. The transfer executes twice — once per fork — using a single user signature, moving value on a chain the user never intended to authorize a duplicate transaction on.

fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
