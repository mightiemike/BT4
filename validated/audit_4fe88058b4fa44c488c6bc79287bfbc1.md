## Finding

### Title
Silent skip of state-value proof verification on proof-fetch error - ([File: storage/storage-interface/src/state_store/state_view/db_state_view.rs])

### Summary
`DbStateView::get` is supposed to cryptographically verify a fetched state value against a trusted state root hash whenever `maybe_verify_against_state_root_hash` is `Some`. The verification is implemented with an `if let Ok((value, proof)) = ...` pattern that silently no-ops when the proof-fetch call errors, yet the function still falls through and returns the value obtained from a *separate*, proof-less lookup, as if verification had occurred.

### Finding Description
`DbStateView::get` is: [1](#0-0) 

```rust
if let Some(root_hash) = self.maybe_verify_against_state_root_hash {
    if let Ok((value, proof)) =
        self.db.get_state_value_with_proof_by_version(key, version)
    {
        proof.verify(root_hash, *key.crypto_hash_ref(), value.as_ref())?;
    }
}
Ok(self
    .db
    .get_state_value_with_version_by_version(key, version)?)
```

The intent of `maybe_verify_against_state_root_hash` is to guarantee proof-checked reads (it is only set when `verified_state_view_at_version` has already verified a `TransactionWithProof` against a `LedgerInfo` and derived a trusted `state_root_hash`, see [2](#0-1) ). However, if `self.db.get_state_value_with_proof_by_version(key, version)` returns `Err(...)` — e.g. because the Jellyfish Merkle proof for that version has already been pruned by the state-merkle pruner while the raw key-value entry is still retained by the (independently-windowed) state-kv pruner — the `if let Ok(...)` block is skipped entirely without propagating the error or recording that verification did not happen. Execution then proceeds unconditionally to `get_state_value_with_version_by_version`, which reads the value directly from the KV store with no proof at all, and returns it as the function's result.

Callers of `DbStateView::get` (through the `TStateView` trait) cannot distinguish "value verified against root_hash" from "value returned because proof-fetch happened to fail," even though the struct's own field name and construction logic (`verified_state_view_at_version`) promise the former.

### Impact Explanation
This breaks the "authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object" invariant: a state view constructed specifically to guarantee proof-verified reads can silently degrade to unverified reads whenever the underlying proof-fetch path errors, without any signal to the caller. Any consumer relying on `DbStateView` with `maybe_verify_against_state_root_hash = Some(...)` for authenticity guarantees would unknowingly accept an unverified value.

### Likelihood Explanation
The two lookups (`get_state_value_with_proof_by_version` vs `get_state_value_with_version_by_version`) go through different storage components with independently configured pruning windows (state-merkle pruner vs. state-kv pruner), so a version/key combination for which the Merkle proof is pruned while the raw KV entry still exists is a realistic, non-malicious scenario, matching exactly the "pruned or not-yet-flushed range" condition described in the exploit question. That said, in this codebase snapshot the only observed caller of `verified_state_view_at_version` (which is the sole constructor that sets `maybe_verify_against_state_root_hash = Some`) is a test helper, `integration_test_impl.rs`; I was not able to confirm, within the available index, a live unprivileged-input-reachable production caller of this verified path (e.g. within the API/view-function serving code) before running out of tool calls. This limits confidence that the bug is currently exploitable end-to-end from an unprivileged request in mainnet production code, as opposed to being a latent correctness bug in a verification helper.

### Recommendation
Change the `if let Ok(...)` to propagate errors from the proof-fetch call when verification is required, e.g.:
```rust
if let Some(root_hash) = self.maybe_verify_against_state_root_hash {
    let (value, proof) = self.db.get_state_value_with_proof_by_version(key, version)?;
    proof.verify(root_hash, *key.crypto_hash_ref(), value.as_ref())?;
}
```
so that any error in fetching the proof surfaces as an error from `DbStateView::get` instead of silently falling back to an unverified read.

### Proof of Concept
Unit test sketch (mock `DbReader`):
1. Implement a mock `DbReader` where `get_state_value_with_proof_by_version` returns `Err(StorageError::NotFound(...))` for a given `(key, version)`.
2. Have the same mock's `get_state_value_with_version_by_version` return `Ok(Some((version, tampered_state_value)))` for the same `(key, version)`.
3. Construct a `DbStateView` with `maybe_verify_against_state_root_hash = Some(trusted_root_hash)` and call `get(key)`.
4. Current behavior: returns `Ok(Some((version, tampered_state_value)))` with no error, despite `trusted_root_hash` never having authenticated the value.
5. Expected/fixed behavior: `get` should return `Err(...)` because verification could not be performed.

impl VerifiedStateViewAtVersion for Arc<dyn DbReader> {
    fn verified_state_view_at_version(
        &self,
        version: Option<Version>,
        ledger_info: &LedgerInfo,
    ) -> StateViewResult<DbStateView> {
        let db = self.clone();

        if let Some(version) = version {
            let txn_with_proof =
                db.get_transaction_by_version(version, ledger_info.version(), false)?;
            txn_with_proof.verify(ledger_info)?;

            let state_root_hash = txn_with_proof
                .proof
                .transaction_info
                .state_checkpoint_hash()
                .ok_or_else(|| StateViewError::NotFound("state_checkpoint_hash".to_string()))?;

            Ok(DbStateView {
                db,
                version: Some(version),
                maybe_verify_against_state_root_hash: Some(state_root_hash),
            })
        } else {
            Ok(DbStateView {
                db,
                version: None,
                maybe_verify_against_state_root_hash: None,
            })
        }
    }
