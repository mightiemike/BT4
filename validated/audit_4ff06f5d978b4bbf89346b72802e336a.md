Found it. The comment in `starknet_api/src/executable_transaction_test.rs` explicitly confirms `L1HandlerTransaction`'s `Calldata` has no non-empty invariant and is constructible with empty calldata via `Deserialize`, yet `l1_handler_message_hash` in `starknet_api/src/hash.rs` unconditionally calls `.expect()` on `split_first()`, which panics on an empty vector.

### Title
Panic-inducing unchecked `split_first().expect()` on attacker-controllable empty L1 handler calldata crashes the node's msg-hash computation - ([File: crates/starknet_api/src/hash.rs])

### Summary
`l1_handler_message_hash` (used by `L1HandlerTransaction::calc_msg_hash`) assumes the transaction's `calldata` always contains at least one element (the L1 `from_address` prepended by the messaging layer) and calls `.expect("Invalid calldata, expected at least from_address")` on `calldata.0.split_first()`. Because `Calldata` carries no non-empty invariant and `L1HandlerTransaction` derives `Deserialize`, an `L1HandlerTransaction` with empty calldata is constructible from external/RPC-supplied JSON, which will panic this function and crash the calling process.

### Finding Description
`starknet_api::hash::l1_handler_message_hash` at [1](#0-0)  does:
```rust
let (from_address, payload) =
    calldata.0.split_first().expect("Invalid calldata, expected at least from_address");
```
This function is reached via `L1HandlerTransaction::calc_msg_hash` [2](#0-1)  which is invoked from RPC handlers such as `estimateMessageFee`/related message-hash lookups in `apollo_rpc/src/v0_8/api/api_impl.rs` and the L1 events pipeline (`apollo_l1_events/src/l1_events_provider.rs`, `apollo_l1_events/src/l1_scraper.rs`).

The sibling function `payload_size()` on the same struct was explicitly hardened against this exact scenario, with a comment directly acknowledging the invariant is not enforced: [3](#0-2)  using `saturating_sub` "to guard the empty-calldata case ... `L1HandlerTransaction` derives `Deserialize` and `Calldata` has no non-empty invariant." A dedicated regression test proves this construction is possible: [4](#0-3) . However, `calc_msg_hash`/`l1_handler_message_hash` was not given equivalent hardening and will panic instead of returning an error whenever `calldata` is empty.

This is directly analogous to the CVE-2025-63679 bug class: a single untrusted, attacker-influenced message field (there, an NGAP field; here, `calldata`) that is not length-validated before being consumed by fixed-shape parsing logic, causing the receiving process to crash.

### Impact Explanation
Any code path that deserializes an `L1HandlerTransaction`/`RpcL1HandlerTransaction` with empty `calldata` (e.g., a malformed/adversarial message record accepted by an RPC endpoint, an L1 event forwarding path, or any JSON-based transaction submission/deserialization boundary that does not enforce a minimum calldata length) and subsequently calls `calc_msg_hash` will panic. In Rust, an uncaught panic in a service task typically aborts that request/task; depending on how the panic propagates in whichever binary calls this (RPC node process, L1 events scraper, etc.), this can crash or repeatedly disrupt the affected process, preventing it from continuing to process transactions/messages — a "network unable to confirm new transactions" class of impact if it hits a sequencer-critical component.

### Likelihood Explanation
Likelihood is moderate: the exact reachability of `calc_msg_hash` from a fully unprivileged, un-authenticated external input (as opposed to only well-formed events already validated by the L1 event pipeline, which always prepends `from_address`) was not fully confirmed within the scope of this investigation. The `From<EventData> for L1HandlerTransaction` and `From<MessageFromL1> for L1HandlerTransaction` conversions both always prepend the L1 sender address, so the genuinely dangerous path requires a boundary that deserializes an `L1HandlerTransaction`/`RpcL1HandlerTransaction` directly from external JSON without going through those constructors and then calls `calc_msg_hash` on it — this is exactly the scenario the `executable_transaction_test.rs` comment warns about for `payload_size()`, but I could not fully trace every caller of `calc_msg_hash` to confirm one accepts raw untrusted JSON before this fix would need to be verified with a running/tested build.

### Recommendation
Change `l1_handler_message_hash` to return a `Result`/`StarknetApiError` instead of panicking on empty calldata (mirroring the `saturating_sub`/graceful-handling fix already applied to `payload_size`), and audit every deserialization boundary that can produce an `L1HandlerTransaction`/`Calldata` from untrusted input to enforce a non-empty invariant before this hash function (or any similar consumer) is invoked.

### Proof of Concept
```rust
use starknet_api::hash::l1_handler_message_hash;
use starknet_api::transaction::fields::Calldata;
use starknet_api::core::{ContractAddress, Nonce, EntryPointSelector};
use std::sync::Arc;

// Empty calldata, as shown constructible in executable_transaction_test.rs.
let calldata = Calldata(Arc::new(vec![]));
let _ = l1_handler_message_hash(
    &ContractAddress::default(),
    Nonce::default(),
    &EntryPointSelector::default(),
    &calldata,
); // panics: "Invalid calldata, expected at least from_address"
```
