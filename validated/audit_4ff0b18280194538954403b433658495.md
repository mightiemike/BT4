### Title
Market order matching rounds the maker's fixed-price fill amount down, letting the taker systematically underpay - ([File: chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java])

### Summary
`MarketUtils.multiplyAndDivide()` computes exchange amounts using `floorDiv` (round-towards-zero/down) division, and this helper is used in `MarketSellAssetActuator.matchSingleOrder()` to compute how much the resting limit order ("maker") receives when its entire remaining inventory is consumed by an incoming market order ("taker"). Rounding this quantity down systematically benefits the taker at the expense of the maker who fixed the price ahead of time, mirroring the UniV3Oracle tick-rounding bug where rounding in the wrong direction let the acting party extract value from the party who committed to a price in advance.

### Finding Description
In `MarketSellAssetActuator.matchSingleOrder()`, when the incoming taker order is larger than the maker's remaining inventory ("taker > maker" branch), the amount of buy-token the maker receives for giving up its entire remaining sell-token balance is computed as: [1](#0-0) 

`makerBuyTokenQuantityReceive` is derived via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, which performs `floorDiv` on the multiplied values: [2](#0-1) 

The maker's order fixes a price ratio (`makerSellQuantity`/`makerBuyQuantity`) in advance — analogous to the Swapper owner's `scaledOfferFactor` in the referenced report. The taker (caller broadcasting `MarketSellAssetContract`) is the acting party consuming that fixed price, analogous to the "bot" performing the swap. Because the computed fill amount `makerBuyTokenQuantityReceive` is rounded DOWN, the maker gives up its full remaining sell-token inventory but receives a rounded-down (i.e., smaller) amount of buy-token in return. The taker's remaining sell-token balance is then reduced only by this floored amount: [3](#0-2) 

meaning the taker keeps more of its own sell-token balance than the maker's committed price should have allowed, effectively paying less than the price the maker fixed. This is the same class of bug as the report: rounding should protect the party whose price is fixed and committed (the maker/order owner), not the party actively executing the trade (the taker), yet here the rounding direction favors the taker.

### Impact Explanation
Every time a taker's market order fully exhausts a maker's remaining inventory (a very common outcome for TRC10/TRX market orders), the maker receives a `floorDiv`-rounded (i.e. undercounted) amount of proceeds while the taker retains excess of its own balance. While a single truncation is bounded by less than 1 unit of the smallest denomination per match, this occurs on every "taker > maker" match across the DEX, systematically transferring value from resting-order owners to aggressive takers over time, and — as in the referenced report — the effect compounds when repeated across many orders/transactions or when quantities/discounts are set with tight margins.

### Likelihood Explanation
This code path is reached by any user broadcasting a `MarketSellAssetContract` transaction (`MarketSellAssetActuator`) that matches against existing resting orders where the taker's remaining sell quantity exceeds a maker order's remaining sell quantity — a routine, permissionless, and extremely common occurrence in the on-chain order book market feature.

### Recommendation
When computing the amount owed to the maker for consuming its entire remaining inventory (`makerBuyTokenQuantityReceive` in the "taker > maker" branch of `MarketSellAssetActuator.matchSingleOrder()`), round the division in `MarketUtils.multiplyAndDivide` (or a dedicated variant used here) UP (ceiling) instead of down, so the maker's fixed price is never underpaid at the taker's benefit. Symmetric care should be taken in the other matching branches (`taker == maker`, `taker < maker`) to ensure rounding is always resolved against the acting/taker side and never against the maker whose price is fixed.

### Proof of Concept
Given a maker order with `makerSellQuantity = 3`, `makerBuyQuantity = 2` (i.e., price is 2/3 buy-token per sell-token) and `makerSellRemainQuantity = 3` fully consumed by a larger taker order:
`makerBuyTokenQuantityReceive = multiplyAndDivide(3, 2, 3) = floorDiv(3*2, 3) = 2` — this is exact here, but for values like `makerSellRemainQuantity = 5`, `makerBuyQuantity = 2`, `makerSellQuantity = 3`: `floorDiv(5*2, 3) = floorDiv(10,3) = 3` (true value 3.33), so the maker receives 3 instead of the fair ~3.33, and the taker's remaining sell-token balance is reduced by only 3 rather than the fair ~3.33, letting the taker retain the fractional difference at the maker's expense.   public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
