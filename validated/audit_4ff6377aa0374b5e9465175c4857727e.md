The strongest analog I found sits in the Starknet OS's Cairo implementation of the `replace_class` syscall, which omits a declared-class check that the Rust `blockifier` (the actual sequencer execution engine) enforces on the very same syscall.

### Title
Starknet OS `replace_class` syscall omits the declared-class (and Cairo version) check that `blockifier` enforces - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
`blockifier`'s Rust implementation of the `replace_class` syscall validates that the target class hash is declared and is a Cairo1 (V1) class before allowing the contract's class pointer to change. The Starknet OS's Cairo re-implementation of the same syscall (used for proof generation / re-execution) performs neither check — the declared-class check is explicitly marked as a `TODO`, and no Cairo-version check exists at all.

### Finding Description
In `blockifier`, `SyscallHandlerBase::replace_class` reads the compiled class (which fails with `UndeclaredClassHash` if it isn't declared) and rejects replacement to a non-Cairo1 class: [1](#0-0) 

The deprecated syscall handler used for Cairo0-invoking contracts enforces the same invariant ("Ensure the class is declared (by reading it)"): [2](#0-1) 

In contrast, the Starknet OS's Cairo `execute_replace_class` (used during Starknet OS re-execution to build the STARK proof of a block) contains an explicit unresolved `TODO` for this exact check and performs the state update unconditionally, sourcing the new `class_hash` straight from syscall input: [3](#0-2) 

The deprecated (Cairo0-context) OS syscall path has the identical gap, with no declared-class check and no code comment even acknowledging it: [4](#0-3) 

This is the same bug class as the reported finding: one code path (`blockifier`, analogous to `updateConfig`) performs the validation, while the parallel code path that is supposed to enforce identical semantics (the Starknet OS, analogous to `initialize`) does not.

### Impact Explanation
The Starknet OS's execution trace is what gets proven and is expected to reproduce exactly the state transition that `blockifier` computed when the block was built. If the OS's `replace_class` is more permissive than `blockifier`'s (e.g., it does not reject replacement to an undeclared class hash or to a Cairo0/V0 class), any divergence between the class-declaration state visible to the prover's hints and what `blockifier` actually enforced could let the OS emit a different final class hash / state root than the one `blockifier` committed to, or mask a class hash that should have caused transaction rejection. This is a state-commitment / honest-node divergence risk: a properly-formed block containing a `replace_class` call that `blockifier` would only allow because it validated declaration, together with a discrepancy in how the OS treats undeclared or V0-class replacement, undermines the guarantee that OS re-execution faithfully re-derives the committed state, which is foundational to proof soundness and the "wrong committed root" / "network unable to confirm new transactions" failure modes called out as in-scope impacts.

### Likelihood Explanation
Reachability is straightforward: any contract can invoke the `replace_class` syscall with an attacker-chosen `class_hash` from ordinary contract execution triggered by a single submitted transaction — no special privileges are required. The missing check is explicitly flagged by the code's own author via the `TODO(Yoni, 1/1/2026)` comment, confirming it is a known, currently-unimplemented gap rather than validation performed elsewhere and simply not visible locally.

### Recommendation
Add the same declared-class lookup (and Cairo-version/V1 check) to the Starknet OS's `execute_replace_class` in both `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo` that `blockifier::execution::syscalls::syscall_base::replace_class` performs, so the OS's re-execution semantics for this syscall are provably identical to the sequencer's execution engine.

### Proof of Concept
1. Deploy a contract whose Cairo code invokes the `replace_class` syscall with a `class_hash` that has never been declared (or that corresponds to a Cairo0/V0 class).
2. Under `blockifier`, `SyscallHandlerBase::replace_class` calls `self.state.get_compiled_class(class_hash)?`, which fails with `StateError::UndeclaredClassHash` (or is rejected via the `is_cairo1` check), so the transaction reverts/fails as designed.
3. During Starknet OS re-execution/proving of a block containing state where this check's absence is exploitable (e.g., via a hint-controlled `GetContractAddressStateEntry`/state view that differs from `blockifier`'s canonical state), `execute_replace_class` in `syscall_impls.cairo`/`deprecated_execute_syscalls.cairo` performs the state-entry class hash update with no declared-class or version verification, per the code shown above — demonstrating the code-level absence of the check that is present in the equivalent `blockifier` path.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }

    );
    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();
    }

    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.

    %{ GetContractAddressStateEntry %}

        key=contract_address,

    );
