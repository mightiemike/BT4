### Title
Legacy Exchange (Bancor-style TRC10 swap) calculation path lacks bounds/negative-balance checks that were added only to the hardened path - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The reported bug describes an unconstrained AMM-style swap (`_maybeExchangeBase` with `revertBuyOnInsufficientFunds=false`) that lets a caller exchange without any limit check, draining the pool's opposite asset. java-tron's TRC10 bancor-relay `Exchange` feature (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`) implements an analogous constant-product/bancor pool where users swap `firstToken`/`secondToken` (including TRX) held by the pool. The same class of "swap output not properly bounded against pool balance" issue exists structurally between the legacy and "hardened" calculation paths.

### Finding Description
`ExchangeCapsule.transaction()` computes the swap output via either the legacy `ExchangeProcessor` (double/BigDecimal-based bancor formula) or, only if the `hardenedCalc` flag is true, `SafeExchangeProcessor`. Critically, the resulting-balance-must-be-non-negative safety check is gated behind that same flag: [1](#0-0) 

Note that `newFirstTokenBalance`/`newSecondTokenBalance` are computed unconditionally, but the guard `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) throw ...` only fires when `hardenedCalc` is `true`. In the default (non-hardened) path — which is what runs unless the `AllowHardenExchangeCalculation` dynamic property/proposal has been activated — a computed `buyTokenQuant` that (due to floating-point/`Math.pow` rounding in the legacy `ExchangeProcessor`, or extreme/edge-case inputs) equals or exceeds the actual pool balance is written back into the store without any rejection, silently producing a negative or corrupted pool balance.

The actuator-level check in `ExchangeTransactionActuator.doValidate()` only caps *growth* of the balance being sold into the pool against `getExchangeBalanceLimit()`, and separately checks the caller has enough of the token being sold — it does **not** independently verify that the computed `anotherTokenQuant` (the amount to be paid out of the pool) is less than the pool's current balance of that token: [2](#0-1) 

This mirrors the root cause of the reported issue: a swap path that is reachable via an ordinary user-broadcast transaction, whose output size is bounded only by the pricing-curve math and not by an explicit "cannot exceed available pool liquidity" check, with the actual protective bound (`SafeExchangeProcessor`'s negative-balance assertion) existing but only conditionally enforced.

### Impact Explanation
If the legacy bancor math ever returns a `buyTokenQuant` at or beyond the counter-asset's pool balance (rounding error accumulation via repeated `Math.pow`/double conversions in `ExchangeProcessor`, or via specially crafted extreme `sellTokenQuant` values), `ExchangeCapsule.transaction()` will commit a negative `firstTokenBalance`/`secondTokenBalance` into the on-chain `Exchange` state via `Commons.putExchangeCapsule` in `ExchangeTransactionActuator.execute()`: [3](#0-2) 

This corrupts the pool's accounting permanently (subsequent legitimate `ExchangeWithdrawContract`/`ExchangeTransactionContract` operations on that exchange would operate against a corrupted/negative balance), analogous to the pool-drain/DoS impact described in the report — this is TRC10 asset accounting corruption reachable via a normal broadcast transaction, not a privileged operation.

### Likelihood Explanation
This requires the exchange to still run through the non-hardened path (default state prior to `AllowHardenExchangeCalculation` activation) and requires an attacker to find/construct sell quantities that push the bancor-curve rounding to output `buyTokenQuant >= buyTokenBalance`. The existence of a dedicated `SafeExchangeProcessor` plus an explicit negative-balance guard, added specifically for the hardened path, indicates the java-tron team identified that the legacy math can produce out-of-bounds results — this fix was only applied conditionally rather than unconditionally to all exchange calculations.

### Recommendation
Apply the same non-negative-balance validation (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) unconditionally in `ExchangeCapsule.transaction()`, regardless of `hardenedCalc`, or migrate all exchange calculations to always route through `SafeExchangeProcessor`. Additionally, `ExchangeTransactionActuator.doValidate()` should explicitly assert `anotherTokenQuant < tokenBalance(anotherTokenID)` before allowing the trade to proceed, independent of the calculation path used.

### Proof of Concept
A concrete numeric proof of concept requires reproducing the exact floating-point rounding behavior of `ExchangeProcessor`'s bancor formula under extreme balances/quantities, which cannot be fully derived from static code review alone; this would need to be validated by running `ExchangeProcessor.exchange()` against boundary values (e.g., very small pool balance vs. very large sell quantity) with `AllowHardenExchangeCalculation` disabled to confirm whether `buyTokenQuant` can reach or exceed `buyTokenBalance`, and confirming the resulting negative balance is persisted via `ExchangeTransactionActuator.execute()`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
