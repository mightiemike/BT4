## Analysis Result

I traced this to a concrete divergence between `ValidateBasic` (CAIP-2 sanity check at vote-ingest time) and `ParseCAIP2` (called deep inside execution, after ballot finalization).

`ValidateBasic` only requires `SourceChain` to contain a `:` character: [1](#0-0) . This is deliberately lenient — the module's design philosophy documented in the same function's comment is that "invalid inbounds still produce an on-chain UTX record (with a failed PCTx / revert) instead of silently dropping the vote" [2](#0-1) .

`ParseCAIP2`, however, additionally rejects an empty namespace or empty reference (e.g. `SourceChain = ":11155111"` or `"eip155:"`), both of which pass `ValidateBasic`'s "contains `:`" check but fail `ParseCAIP2` [3](#0-2) .

Inside `ExecuteInboundFundsAndPayload`, the `ParseCAIP2` error is the **one exception** to the module's otherwise-consistent "capture as FAILED PCTx + revert outbound" pattern — it is returned raw instead of being routed through `handleFailedInboundValidation`/`buildRevertOutbound`: [4](#0-3) . Every other failure in that same function (factory lookup, UEA deploy, PRC20 deposit) is deliberately caught into `execErr`/`shouldRevert` and recorded on the UTX [5](#0-4) .

Because this raw error bubbles up through `ExecuteInbound` → `VoteInbound`'s Step 8 call [6](#0-5) , and `MsgVoteInbound` is a gasless message processed as a normal Cosmos SDK message, an error returned by the handler causes baseapp to discard **all** state writes for that message — including the just-created `UniversalTx` (Step 5) and the `PendingInbounds` removal (Step 6) that happened earlier in the very same message execution [7](#0-6) .

**However**, I could not fully verify one link before running out of iterations: whether the ballot itself (`VoteOnInboundBallot`) also gets rolled back in this scenario, or whether it was already durably committed via the earlier `commit()` call on a separate `CacheContext` before the `ExecuteInbound` step. The comment on that `tmpCtx`/`commit()` pattern explicitly exists "to not commit any ballot state change in case of error" [8](#0-7) , but this commit happens only for the vote itself (Steps 2–3), *before* the later Step 5-8 sequence that is not similarly cache-isolated. I was not able to confirm within this session whether Cosmos SDK's baseapp truly discards writes made to `sdkCtx` (not a further sub-`CacheContext`) when a later step in the same message returns an error, versus whether the earlier `commit()` already persisted the ballot-passed state irreversibly into the block's working multistore regardless of what happens afterward in the same message. This distinction determines whether the bug causes (a) a permanently un-recorded vote requiring UVs to resend `MsgVoteInbound` every time (a repeatable but recoverable retry loop, since `ParseCAIP2` fails deterministically every time and every validator hits the identical error), or (b) a UTX/ballot state that is "half persisted" in some inconsistent form. Either way, the practical effect is that an attacker-crafted `SourceChain` value (e.g. `":11155111"`) that passes `ValidateBasic` but fails `ParseCAIP2` causes every validator's finalizing vote on that specific inbound to error out identically and indefinitely, preventing that inbound from ever reaching an on-chain UTX or revert outbound — exactly mirroring the external report's "unhandled exception in cross-chain message processing blocks that message's finalization."

### Title
Inconsistent `SourceChain` validation lets a malformed CAIP-2 identifier bypass revert handling and permanently strand an inbound - (File: `x/uexecutor/keeper/execute_inbound_funds_and_payload.go`)

### Summary
`ValidateBasic` accepts any `SourceChain` string containing a `:`, but `ParseCAIP2` (invoked only during post-finalization execution) additionally rejects empty namespace/reference segments. Unlike every other execution-time failure in this file, the `ParseCAIP2` error is returned raw instead of being converted into a FAILED `PCTx` + `INBOUND_REVERT` outbound.

### Finding Description
`Inbound.ValidateBasic()` is the only gate applied before a vote is accepted and tallied; it merely checks that `SourceChain` contains a colon [1](#0-0) . `ParseCAIP2` is stricter and is called only after ballot finalization, inside `ExecuteInboundFundsAndPayload` [4](#0-3) . A `SourceChain` like `":123"` or `"eip155:"` satisfies `ValidateBasic` but fails `ParseCAIP2`, and the resulting error is propagated directly rather than routed through the module's own `handleFailedInboundValidation` recovery path (used consistently elsewhere in the same function, see lines 104–158). This propagates through `ExecuteInbound` and `VoteInbound`'s final dispatch [6](#0-5) , causing the whole `MsgVoteInbound` message to fail.

### Impact Explanation
Because the value that trips `ParseCAIP2` is attacker-controlled (a validator relays whatever `SourceChain` the source-chain event/attacker supplies) and the failure is 100% deterministic, every Universal Validator that attempts to cast the finalizing vote on this specific inbound hits the identical unhandled error. The module's own design intent — "the vote path must always record a UTX" — is defeated for this input class, since the UTX-creation and pending-inbound-removal state performed earlier in the same message also fails to persist when the message ultimately errors. This can permanently strand a specific cross-chain deposit: no UTX, no revert outbound, no path for the user to be refunded on the source chain, matching the "permanent freezing of user or protocol-controlled funds" and "denial of service ... reachable without privileged control" impact categories.

### Likelihood Explanation
Likelihood is high for the specific class of malformed `SourceChain` strings (empty namespace or empty reference) since these are trivial to construct and pass `ValidateBasic` unmodified. It requires only that a UV observes/relays such an inbound (or that the value originates from event data that includes a malformed CAIP-2 string), which is within the "ordinary user deposits / payloads" unprivileged-attacker threat model. No malicious validator behavior is required — honest validators voting on the same crafted event all hit the same deterministic bug.

### Recommendation
Move the `ParseCAIP2` check for `SourceChain` into `ValidateBasic` (or perform the equivalent namespace/reference validation there) so malformed CAIP-2 identifiers are rejected at vote-ingest time rather than causing an unhandled error deep in execution. Alternatively, wrap the `ParseCAIP2` failure inside `ExecuteInboundFundsAndPayload` with the same `handleFailedInboundValidation`/revert-outbound pattern used for every other execution failure in that function, so a bad `SourceChain` degrades to a recorded FAILED `PCTx` + `INBOUND_REVERT` instead of aborting the entire message.

### Proof of Concept
1. Submit (or have a validator observe and relay) an `Inbound` with `SourceChain = ":11155111"` (contains `:`, satisfies `ValidateBasic`), `TxType = TxType_FUNDS_AND_PAYLOAD`, and otherwise-valid fields.
2. Have enough validators call `MsgVoteInbound` to reach quorum.
3. On the finalizing vote, `VoteInbound` reaches Step 8 → `ExecuteInbound` → `ExecuteInboundFundsAndPayload`, which calls `types.ParseCAIP2(":11155111")`, which fails.
4. Because this error is returned raw (not routed through `handleFailedInboundValidation`), the entire `MsgVoteInbound` transaction errors, and the UTX creation/pending-inbound removal from the same message are not persisted.
5. Repeat for any subsequent UV attempting to finalize/re-finalize: the identical deterministic error recurs, and the inbound never produces a queryable `UniversalTx` or revert outbound — the deposit is permanently stuck.

func ParseCAIP2(chain string) (namespace string, chainId string, err error) {
	parts := strings.SplitN(chain, ":", 2)
	if len(parts) != 2 {
		return "", "", fmt.Errorf("invalid CAIP-2 identifier %q: missing ':'", chain)
	}
	if parts[0] == "" {
		return "", "", fmt.Errorf("invalid CAIP-2 identifier %q: empty namespace", chain)
	}
	if parts[1] == "" {
		return "", "", fmt.Errorf("invalid CAIP-2 identifier %q: empty chain reference", chain)
	}
	return parts[0], parts[1], nil
