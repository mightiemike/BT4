### Title
Wallet Contract pays the relayer's ETH-emulation fee unconditionally, before knowing whether the underlying action will succeed - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The NEAR Wallet Contract's `inner_rlp_execute` fires a separate, unchained `Transfer` promise to pay the relayer's requested fee for an emulated ETH base-token transfer or ERC-20 transfer *before* the promise for the actual user action (the transfer / `ft_transfer`) is created and *without* making that payment conditional on that action's outcome. This is the same root-cause pattern as the fee-on-transfer report: the contract accounts for value movement based on a caller-declared quantity/intent, instead of verifying the actual, final outcome of the operation it is supposed to be compensating.

### Finding Description
In `inner_rlp_execute`, once the Ethereum transaction is parsed into a `(action, transaction_kind)` pair, the fee refund to the relayer is dispatched immediately and unconditionally: [1](#0-0) 

```rust
if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
    fee, ..
})
| TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) =
    &transaction_kind
{
    if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
        let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
        env::promise_batch_action_transfer(refund_promise, *fee);
    }
}
```

This `refund_promise` is a standalone promise batch, entirely independent of the promise chain that later performs the actual action and eventually resolves in `rlp_execute_callback`, which is the only place that checks whether the action succeeded and refunds the caller's deposit on failure: [2](#0-1) 

For the `EOABaseTokenTransfer { address_check: Some(_), .. }` case in particular, the fee is paid out even though the contract has not yet confirmed the transaction is legitimate: the actual action is only constructed afterward, inside `address_check_callback`, and if the registrar lookup shows the target is already a *named* account (i.e., the relayer supplied the wrong `target`, which the contract itself calls "faulty relayer" behavior), the callback returns a failure `ExecuteResponse` without ever creating/sending the transfer/`ft_transfer` action: [3](#0-2) 

Because the fee-payment promise in `inner_rlp_execute` already executed before this check runs, the wallet's balance is unconditionally decremented by `fee` even though the user's intended action never executes. The same disconnect exists for the `ERC20Transfer` case: the fee is sent regardless of whether the subsequent `storage_balance_of` / `storage_deposit` / `ft_transfer` chain (in `nep_141_storage_balance_callback` / `rlp_execute_callback`) ultimately succeeds or fails.

### Impact Explanation
Any submitter of an RLP-encoded transaction through the Wallet Contract (a relayer, or the user acting as their own relayer) can cause the wallet account to lose the declared `fee` amount of $NEAR to the relayer even when:
- the relayer's `target` is invalid (triggers the "faulty relayer" / address-check failure path), or
- the downstream transfer/`ft_transfer` action itself fails for any reason (e.g., insufficient balance, receiver problems).

This is an unauthorized value movement out of the user's own wallet account: funds are transferred to a third party (the relayer) despite the contract's own logic recognizing the operation as failed/invalid. It directly parallels the reported bug class — the contract trusts a caller-supplied "amount to be paid" as if it corresponds to a successfully completed operation, instead of verifying the actual completion/result before moving value.

### Likelihood Explanation
Reachable by any account calling `rlp_execute` and it takes only a single, trivially constructable Ethereum-style transaction with a non-zero `max_fee_per_gas` * `gas_limit` (which becomes `tx_fee`) and an invalid `target`/eth-emulation payload to trigger the loss deterministically — no privileged role or race condition needed.

### Recommendation
Chain the relayer fee-refund transfer to the same promise result as the main action (e.g., include it as part of the batch/callback logic executed only in `rlp_execute_callback` upon success, or make the fee payment part of the same promise batch as the underlying transfer/`ft_transfer` action) so that the fee is only paid out once the wallet contract has confirmed the user's intended action actually succeeded.

### Proof of Concept
1. Deploy a Wallet Contract instance and fund it.
2. Sign an Ethereum-style transaction with `max_fee_per_gas * gas_limit` set to a non-zero fee, and `to` set to an address that resolves (via the address registrar) to an existing *named* account — i.e., a target that will fail the "faulty relayer" check in `address_check_callback`.
3. Submit it via `rlp_execute` with any relayer/predecessor account.
4. Observe: `inner_rlp_execute` fires the `fee` transfer to the predecessor immediately; `address_check_callback` subsequently returns `success: false` ("Invalid target...") without ever creating the intended transfer action.
5. Compare wallet balance before/after: it is reduced by `fee`, even though `ExecuteResponse.success == false` and no user-intended action was executed.
