### Title
`DelegateAction` (NEP-366 Meta Transaction) Signed Payload Omits `chain_id`, Enabling Cross-Chain Replay — (`File: core/primitives/src/action/delegate.rs`)

---

### Summary

`DelegateAction` and `DelegateActionV2` (NEP-366/NEP-611 meta transactions) sign a payload that contains no `chain_id`. The signed bytes are `hash(borsh(discriminant || DelegateAction))` where the discriminant is a fixed NEP-number prefix. Because block heights (used as the expiry bound via `max_block_height`) are not chain-specific, a `SignedDelegateAction` created for one NEAR network (e.g., testnet) is cryptographically valid on any other NEAR network (e.g., mainnet) where the same account, key, and a valid nonce exist. No runtime check in `apply_delegate_action` rejects a structurally valid signature on the wrong chain.

---

### Finding Description

**`DelegateAction` struct — no `chain_id` field:**

`DelegateAction` contains: `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`. [1](#0-0) 

The signed hash is computed as:

```rust
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}
``` [2](#0-1) 

`SignableMessage` prepends only a fixed 4-byte NEP discriminant (`2^30 + 366`). No `chain_id` is included anywhere in the signed payload. [3](#0-2) 

**Contrast with regular transactions:**

`TransactionV0` and `TransactionV1` include `block_hash` in their signed payload. [4](#0-3)  The transaction hash is `hash(borsh(transaction))`, which covers `block_hash`. [5](#0-4)  Because block hashes are globally unique per chain, a regular transaction signed on mainnet cannot be replayed on testnet — the `block_hash` will not exist within `transaction_validity_period` blocks on the other chain. `DelegateAction` has no equivalent chain-binding field.

**`apply_delegate_action` performs no chain check:**

The full validation sequence is:
1. `signed_delegate_action.verify()` — verifies the signature against `get_nep461_hash()` (no chain_id). [6](#0-5) 
2. `apply_state.block_height > delegate_action.max_block_height()` — block height is not chain-specific. [7](#0-6) 
3. `sender_id` match check. [8](#0-7) 
4. `validate_delegate_action_key()` — nonce and access key check, not chain-specific. [9](#0-8) 

None of these checks bind the action to a specific chain.

**`DelegateActionV2` has the same omission:**

`DelegateActionV2` also lacks `chain_id` and uses the same `SignableMessage` scheme with a different NEP discriminant (`2^30 + 611`). [10](#0-9) [11](#0-10) 

---

### Impact Explanation

An attacker who obtains a `SignedDelegateAction` intended for one NEAR network can submit it on a different NEAR network. If the sender's account exists on both networks with the same key and a valid nonce, the inner actions execute on the target network without the user's authorization for that chain. Inner actions can include `Transfer`, `AddKey`, `DeleteKey`, `FunctionCall`, `DeleteAccount` — all of which directly affect funds and account control. The corrupted value is the sender's balance or key set on the target chain.

---

### Likelihood Explanation

The preconditions are:
1. The same account and key exist on both networks (common for developers and dApp users who create accounts on both mainnet and testnet).
2. The nonce on the target network is lower than the nonce in the `SignedDelegateAction` (likely if the account is less active on the target network).
3. The `max_block_height` has not expired on the target network (block heights on mainnet and testnet are in the same numeric range and grow at similar rates).
4. The attacker obtains the `SignedDelegateAction` — it is transmitted off-chain to a relayer, so a malicious relayer, a public dApp frontend, or any interceptor can replay it.

The NEP-366 design explicitly acknowledges that "some level of trust between the relayer and Alice is required." A malicious relayer is the most direct unprivileged attacker path. [12](#0-11) 

---

### Recommendation

Add a `chain_id: String` field to `DelegateAction` and `DelegateActionV2`. Include it in the Borsh-serialized signed payload so that the signature is bound to a specific chain. During `apply_delegate_action`, verify that `delegate_action.chain_id == apply_state.chain_id` (where `apply_state` already carries the genesis `chain_id`). This mirrors how Ethereum's EIP-155 solved the same problem by including `chain_id` in the signed transaction hash.

Alternatively, include the genesis hash (a chain-unique constant) in the `SignableMessage` discriminant or as a prefix to the signed bytes, analogous to how `block_hash` binds regular transactions to a specific chain.

---

### Proof of Concept

1. Alice has account `alice.near` on both mainnet and testnet, using the same ED25519 key pair. Her mainnet access key nonce is 4; her testnet access key nonce is 10.

2. Alice signs a `DelegateAction` on testnet to transfer 100 NEAR to `bob.near`:
   ```
   DelegateAction {
     sender_id: "alice.near",
     receiver_id: "bob.near",
     actions: [Transfer { deposit: 100 NEAR }],
     nonce: 11,
     max_block_height: 250_000_000,  // far future, valid on both chains
     public_key: alice_ed25519_key,
   }
   ```
   Signed hash = `hash(borsh(0x4000016E || DelegateAction))` — no chain_id.

3. The `SignedDelegateAction` is forwarded to a testnet relayer. The relayer (or any observer) copies it.

4. The attacker wraps the identical `SignedDelegateAction` in a mainnet transaction:
   ```
   SignedTransaction {
     signer_id: attacker.near,
     receiver_id: alice.near,   // must match sender_id
     actions: [Delegate(signed_delegate_action)],
     block_hash: <valid mainnet block hash>,
   }
   ```

5. `apply_delegate_action` on mainnet:
   - `verify()` → **passes** (signature is over the same bytes, no chain_id)
   - `block_height (e.g. 130_000_000) > max_block_height (250_000_000)` → **false, passes**
   - `sender_id == receiver_id of outer tx` → **passes**
   - nonce check: mainnet nonce is 4, delegate nonce is 11 → **passes** (11 > 4)

6. A new receipt is created on mainnet transferring 100 NEAR from `alice.near` to `bob.near`. Alice loses 100 mainnet NEAR she never authorized for mainnet.

The broken invariant: `SignedDelegateAction.verify()` returns `true` on a chain the user never intended to authorize. [13](#0-12)

    pub fn verify(&self) -> bool {

pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
#[non_exhaustive]
pub enum SignableMessageType {
    /// A delegate action, intended for a relayer to included it in an action list of a transaction.
    DelegateAction,
    /// A delegate action with gas key support, intended for a relayer to include it in an action
    /// list of a transaction.
    DelegateActionV2,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum ReadDiscriminantError {
    #[error("does not fit any known categories")]
    UnknownMessageType,
    #[error("NEP {0} does not have a known on-chain use")]
    UnknownOnChainNep(u32),
    #[error("NEP {0} does not have a known off-chain use")]
    UnknownOffChainNep(u32),
    #[error("discriminant is in the range for transactions")]
    TransactionFound,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum CreateDiscriminantError {
    #[error("nep number {0} is too big")]
    NepTooLarge(u32),
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }

## Relayer

Meta transactions only work with a relayer. This is an application layer
concept, implemented off-chain. Think of it as a server that accepts a
`SignedDelegateAction`, does some checks on them and eventually forwards it
inside a transaction to the blockchain network.

A relayer may choose to offer their service for free but that's not going to be
financially viable long-term. But they could easily have the user pay using
other means, outside of Near blockchain. And with some tricks, it can even be
paid using fungible tokens on Near.

In the example visualized above, the payment is done using \$FT. Together with
the transfer to John, Alice also adds an action to pay 0.1 \$FT to the relayer.
The relayer checks the content of the `SignedDelegateAction` and only processes
it if this payment is included as the first action. In this way, the relayer
will be paid in the same transaction as John.

Note that the payment to the relayer is still not guaranteed. It could be that
Alice does not have sufficient $FT and the transfer fails. To mitigate, the
relayer should check the $FT balance of Alice first.

Unfortunately, this still does not guarantee that the balance will be high
enough once the meta transaction executes. The relayer could waste NEAR gas
without compensation if Alice somehow reduces her \$FT balance in just the right
moment. Some level of trust between the relayer and its user is therefore
required.

The vision here is that there will be mostly application-specific relayers. A
general-purpose relayer is difficult to implement with just the MVP. See
limitations below.
