Unauthenticated `GetPaginatedNowWitnessList`/`ListWitnesses` RPC triggers unbounded O(n) `VotesStore` scan controllable by unprivileged accounts - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
`Wallet.getPaginatedNowWitnessList` calls a private `countVote(VotesStore)` helper that does a full iteration over every `VotesCapsule` row in `VotesStore` on every single call, regardless of the requested `offset`/`limit`. Because each unique account that broadcasts a `VoteWitnessContract` creates/updates exactly one row in `VotesStore` keyed by its own address, and that row is only cleared during the next `MaintenanceManager.doMaintenance()` cycle (every 6 hours), an unprivileged attacker with many funded accounts can inflate `VotesStore` size and force every caller of this public read endpoint to pay for an O(n) scan for hours.

### Finding Description
- `Wallet.getPaginatedNowWitnessList(offset, limit)` fetches the full witness list, then unconditionally calls the private `countVote(votesStore)` method, which iterates the *entire* `VotesStore` via `votesStore.iterator()` to compute vote deltas before applying pagination: [1](#0-0) 
- The `countVote` implementation walks every `VotesCapsule` entry and every `Vote` inside its `oldVotes`/`newVotes` lists with no size cap, cursor limit, or early exit: [2](#0-1) 
- `VotesStore` is a plain key-value store keyed by voter address with no bound on the number of rows: [3](#0-2) 
- `VoteWitnessActuator.countVoteAccount` writes one row per unique owner address into `VotesStore`, keyed by `ownerAddress`, on every successful `VoteWitnessContract` execution: [4](#0-3) 
- The only validation gate is that `sum(voteCount) * TRX_PRECISION <= tronPower`, i.e., the attacker just needs a small nonzero frozen balance (TRON power) per account, and up to `MAX_VOTE_NUMBER` (30) distinct witness addresses per vote transaction: [5](#0-4) 
- `calcFee()` for `VoteWitnessContract` returns 0, so the only cost is bandwidth/energy for the transaction itself and freezing a minimal amount of TRX for TRON power: [6](#0-5) 
- The rows persist until `MaintenanceManager.doMaintenance()` runs, which is on a fixed ~6-hour cycle, and which itself performs the equivalent full-store scan/delete via its own `countVote(VotesStore)`: [7](#0-6) 
- The HTTP endpoint `GetPaginatedNowWitnessListServlet` is unauthenticated and only wrapped by a generic `RateLimiterServlet`, which throttles request rate/IP but does nothing to bound the per-request cost once a request is admitted: [8](#0-7) 

None of the standard defenses (signature/permission checks, `DecodeUtil.addressValid`, fork gates, fee accounting) limit the *number of distinct voter rows* that can accumulate in `VotesStore`, nor do they cap the cost of `countVote` per RPC call. The `WITNESS_COUNT_LIMIT_MAX` pagination cap only bounds the *output* size, not the internal scan cost, since `countVote` runs before pagination is applied.

### Impact Explanation
This maps to the "DoS via RPC-API" bounty class: an unauthenticated, unprivileged actor can degrade the responsiveness of a public read-only RPC/HTTP endpoint (`getPaginatedNowWitnessList`, exposed via `GetPaginatedNowWitnessListServlet` and gRPC `ListWitnesses`/`GetPaginatedNowWitnessList`) for all clients, by inflating a chain-state store (`VotesStore`) with cheap writes that persist for up to 6 hours before maintenance clears them. The severity depends on how large `VotesStore` can practically grow (bounded by number of unique accounts willing to vote and their bandwidth costs) and how much CPU each iteration adds, but the scaling is confirmed to be O(n) in store size with no mitigating cap in the read path.

### Likelihood Explanation
- Preconditions are minimal and fully within an unprivileged actor's control: create/fund N accounts, freeze a small amount of TRX each for TRON power, and broadcast a `VoteWitnessContract` from each.
- Cost is bounded by standard TRX creation/freezing/bandwidth costs — no elevated privilege or protocol-level fee beyond ordinary tx costs (`calcFee()` = 0 for the vote itself).
- The attack is trivially repeatable every maintenance cycle (~6 hours) and the affected read endpoint has no authentication.
- The main constraint on real-world severity is the practical cost of funding/maintaining N accounts and observing measurable RPC latency degradation at scale, which would need to be validated experimentally (per the proof idea) to determine actual severity thresholds.

### Recommendation
Avoid a full `VotesStore` scan on every read-path RPC call. Options include: maintaining an incrementally-updated in-memory/aggregate vote-delta cache that is updated on each `VoteWitnessContract` execution (write path) instead of recomputed on each read (read path); capping/pagination-aware iteration in `countVote` so cost is bounded independent of `VotesStore` size; or moving the real-time vote delta computation off the hot RPC path (e.g., precomputed periodically) with appropriate consistency documentation.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }
