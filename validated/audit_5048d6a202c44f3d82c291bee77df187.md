## Analysis

The Gitcoin report describes a bug class: a payable/deposit-accepting function that only checks a lower bound on the value sent (not an exact match), succeeds on the happy path, and provides no mechanism to reclaim the excess. In nearcore, this bug class maps directly to `AddressRegistrar::register` in the wallet-contract's companion contract. [1](#0-0) 

The function is `#[payable]`, reachable by any unprivileged transaction signer or RPC caller submitting a `FunctionCall` action with an attached deposit. It computes `required_deposit` from storage cost and only rejects the call if `given_deposit < required_deposit` — it never checks for equality, and on the success path (`Entry::Vacant`) it stores the entry but never refunds `given_deposit - required_deposit`: [2](#0-1) 

Only the collision path (`Entry::Occupied`) explicitly refunds the caller's whole deposit; the success path keeps the entire attached deposit regardless of how much it exceeds `required_deposit`. There is no owner/admin withdrawal method anywhere in this contract, so any excess is permanently stuck in the contract's account balance.

### Title
Excess attached deposit permanently locked in `AddressRegistrar::register` with no recovery mechanism - (File: runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs)

### Summary
`AddressRegistrar::register` is a `#[payable]` method that validates only a lower bound (`given_deposit >= required_deposit`) on the attached NEAR deposit. On the successful registration path it retains the full attached deposit instead of refunding the difference between what was sent and what was actually required for storage. Unlike the collision path, which explicitly refunds the entire deposit, the success path has no refund logic at all, and the contract exposes no withdrawal/sweep method for the owner or caller to recover the excess.

### Finding Description
Any account (an unprivileged transaction signer or an RPC/meta-transaction caller) can call `register(account_id)` and attach an arbitrary amount of NEAR via the transaction's `FunctionCall` action deposit. The contract computes:
```
required_deposit = storage_byte_cost * bytes_to_store
```
then checks only `given_deposit < required_deposit` to reject underpayment. If the caller overpays (deliberately or by mistake — e.g. by copying a boilerplate deposit value, or by using a client that rounds up), and the target address slot is `Vacant` (i.e. registration succeeds), the whole `given_deposit`, including the excess above `required_deposit`, is absorbed into the contract's account balance permanently. No logic refunds the difference, and no other method in the contract (`lookup`, `get_address`, `new`) provides any way to withdraw or reclaim that balance. This is architecturally different from the protocol-level attached-deposit refund guarantees that apply to failed receipts elsewhere in nearcore (see `docs/RuntimeSpec/Refunds.md` and `refund_unspent_gas_and_deposits` in `runtime/runtime/src/lib.rs`) — those refunds only trigger on receipt *failure*, not on a successful call that simply over-collects.

### Impact Explanation
Overpaid NEAR becomes permanently frozen in the `AddressRegistrar` contract's account with no code path to release it — this fits the "permanently frozen funds" acceptance criterion. Since the contract is part of the wallet-contract ecosystem used by relayers/callers performing ETH-style transactions and address registration (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`), any caller/relayer that attaches more NEAR than strictly required for a first-time registration loses that excess irrecoverably.

### Likelihood Explanation
Likelihood is moderate: it requires a caller to attach more than the exact `required_deposit` on a successful (non-colliding) `register` call. This is plausible in practice since callers/relayers computing an approximate or padded deposit value (a common client-side pattern to avoid underpayment failures) will systematically overpay, and there is no client-facing indication of the exact required amount enforced strictly.

### Recommendation
On the `Entry::Vacant` success path, mirror the `Entry::Occupied` path's refund logic: compute `excess = given_deposit - required_deposit` and, if `excess > 0`, issue a `promise_batch_action_transfer` back to `env::predecessor_account_id()` for the excess amount before/after inserting the entry. Alternatively, require exact-amount validation (reject if `given_deposit != required_deposit`) or provide an owner-controlled sweep method to recover any accumulated dust/excess balance.

### Proof of Concept
1. Deploy `AddressRegistrar` and call `new()`.
2. Compute `required_deposit` for a target `account_id` (e.g., `storage_byte_cost * (20 + account_id.len())`).
3. Call `register(account_id)` attaching `given_deposit = required_deposit + N` yoctoNEAR (any `N > 0`), from an account not yet colliding with an existing address.
4. Observe: `Entry::Vacant` branch executes, `Some(address)` is returned (success), and the contract's account balance permanently increases by the full `given_deposit`, not just `required_deposit`. No transfer/refund is emitted for the `N` excess, and no method exists to later withdraw it. [3](#0-2)

```rust
    #[payable]
    pub fn register(&mut self, account_id: AccountId) -> Option<String> {
        // It is not allowed to register eth-implicit accounts because the purpose
        // of the registry is to allow looking up the named account associated with
        // an address obtained via hashing, but eth-implicit accounts are already
        // parsable as addresses.
        if is_eth_implicit(&account_id) {
            let log_message = format!("Refuse to register eth-implicit account {account_id}");
            env::log_str(&log_message);
            return None;
        }

        // Must store the address and the account id
        let bytes_to_store = 20 + (account_id.len() as u128);
        let required_deposit =
            NearToken::from_yoctonear(env::storage_byte_cost().as_yoctonear() * bytes_to_store);
        let given_deposit = env::attached_deposit();
        // The caller must pay for the storage cost of registering.
        if given_deposit < required_deposit {
            let message = format!(
                "Insufficient deposit to cover storage cost. Given={} Expected={}",
                given_deposit.as_yoctonear(),
                required_deposit.as_yoctonear(),
            );
            env::panic_str(&message);
        }

        let address = account_id_to_address(&account_id);

        match self.addresses.entry(address) {
            Entry::Vacant(entry) => {
                let address = format!("0x{}", hex::encode(address));
                let log_message = format!("Added entry {} -> {}", address, account_id);
                entry.insert(account_id);
                env::log_str(&log_message);
                Some(address)
            }
            Entry::Occupied(entry) => {
                let log_message = format!(
                    "Address collision between {} and {}. Keeping the former.",
                    entry.get(),
                    account_id
                );
                env::log_str(&log_message);
                // Transfer the deposit back to the caller since no storage was updated.
                let refund_promise = env::promise_batch_create(&env::predecessor_account_id());
                env::promise_batch_action_transfer(refund_promise, given_deposit);
                None
            }
        }
    }
```
