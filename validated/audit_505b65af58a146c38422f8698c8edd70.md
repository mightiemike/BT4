## Finding

Based on the available code, this appears to be a genuine logic flaw in the sharded block executor's cross-shard state propagation, not just a hypothetical.

### Title
Aborted transaction's `RemoteTxnWrite(write_op=None)` is indistinguishable from "key deleted", corrupting dependent shard's cross-shard state read - ([File: aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs])

### Summary
The cross-shard commit protocol uses `write_op: Option<WriteOp>` to represent both "the state was unchanged/unavailable" and "the key was written." The comment on `RemoteTxnWrite` explicitly states this dual meaning is used to signal transaction abort: "The write op is None if the transaction is aborted." [1](#0-0)  However, the receiving side collapses this into a plain `Option<StateValue>` without carrying any distinct "unchanged/no-write" vs "deleted" signal.

### Finding Description
`CrossShardCommitReceiver::start` unwraps the incoming `RemoteTxnWrite` and stores the resulting value directly into the cross-shard state view:
```rust
RemoteTxnWriteMsg(txn_commit_msg) => {
    let (state_key, write_op) = txn_commit_msg.take();
    cross_shard_state_view
        .set_value(&state_key, write_op.and_then(|w| w.as_state_value()));
},
``` [2](#0-1) 

`CrossShardStateView::set_value` then marks the corresponding `RemoteStateValue` entry as resolved with that `Option<StateValue>`:
```rust
pub fn set_value(&self, state_key: &StateKey, state_value: Option<StateValue>) {
    self.cross_shard_data
        .get(state_key)
        .unwrap()
        .set_value(state_value);
}
``` [3](#0-2) 

Because `cross_shard_data` is pre-populated with every dependency key via `RemoteStateValue::waiting()` [4](#0-3) , once resolved to `None`, any subsequent read of that key by the dependent shard's `StateView` will treat it as "value does not exist" for the remainder of that dependency's key, rather than falling back to the correct pre-transaction value in `base_view`. The fallback path `self.base_view.get_state_value(...)` is only used when the key is entirely absent from `cross_shard_data` (i.e., not a tracked dependency) — for tracked dependency keys, the resolved `None` is authoritative and final.

The sender side, `CrossShardCommitSender::on_transaction_committed`, is invoked from the block executor's commit hook for every committed transaction that has registered dependents:
```rust
fn on_transaction_committed(&self, txn_idx: TxnIndex, txn_output: &TransactionOutput) {
    let global_txn_idx = txn_idx + self.index_offset;
    if self.dependent_edges.contains_key(&global_txn_idx) {
        self.send_remote_update_for_success(global_txn_idx, txn_output);
    }
}
``` [5](#0-4) 

This hook fires for committed outputs regardless of whether the transaction's VM-level execution status was a `Keep(Success)` or `Keep(MoveAbort/ExecutionFailure)` — an aborted transaction still produces a committed `TransactionOutput` (with an effectively empty write set), and the commit hook does not distinguish this case. When the sender builds `RemoteTxnWrite` for a dependency key that the aborted transaction never wrote (which is the entire write set, since it aborted), it sends `write_op = None`, per the documented abort semantics in `messages.rs`.

The net effect: a dependent shard consuming this cross-shard key resolves it to "no value" — which for a state value means "the account/resource does not exist" — instead of correctly reflecting the true pre-transaction state (which should be served by falling back to `base_view`, since the aborting transaction made no actual change to global state).

### Impact Explanation
Any unprivileged transaction that intentionally aborts (e.g., via a Move `abort` or assertion failure — trivially triggerable by any user) and is identified by the block partitioner as a dependency source for a cross-shard read in another shard will cause the dependent shard to read a false "non-existent" state for that key instead of the correct value from `base_view`. Because block-executor's downstream commit/write-set computation for the dependent transaction is done using this corrupted read, the dependent shard's resulting write set (and hence the transaction output that gets flushed to storage) can diverge from what a non-sharded (canonical) VM execution over the same input would produce. This directly matches the "committed state that differs from the correct VM result" and "hard-fork-only divergence" impact classes for validators/executors that use the sharded block executor code path.

### Likelihood Explanation
Triggering an aborting transaction is available to any unprivileged user. The only additional requirement is that the block partitioner classify this transaction as a dependency edge for a transaction assigned to another shard (an execution-scheduling artifact, not something the attacker needs to control precisely — it can occur naturally whenever two transactions from the same block touch the same resource across shard boundaries and the writer aborts). I was not able to directly inspect the body of `send_remote_update_for_success` or the `TStateView::get_state_value` implementation for `CrossShardStateView` in this pass (tool budget was exhausted before I could pull those exact lines), so the precise fallback logic for `get_state_value` should be independently re-verified before treating this as fully confirmed; the conclusion above is based on the confirmed `set_value`/`RemoteStateValue` resolution pattern and the documented `None`-means-abort semantics in `messages.rs`.

### Recommendation
Change `RemoteTxnWrite`'s payload to distinguish three states instead of two: "written with value," "deleted," and "no write / fall back to base view." For example, wrap the field as `Option<Option<WriteOp>>` or introduce an explicit enum (`Unwritten`, `Deleted`, `Written(WriteOp)`), and have `CrossShardStateView`'s `get_state_value` fall back to `base_view.get_state_value` when the resolved cross-shard entry indicates "unwritten," rather than treating any `None` as a deletion.

### Proof of Concept
Unit test outline for `aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs` / `cross_shard_state_view.rs`:
1. Set up a `CrossShardStateView` with `base_view` containing `state_key -> Some(existing_value)`, and register `state_key` as a cross-shard dependency.
2. Simulate the source shard's committed output for the (aborted) source transaction, whose write set does not contain `state_key`.
3. Call `CrossShardCommitSender::send_remote_update_for_success` (or manually construct `RemoteTxnWrite::new(state_key, None)` per the abort semantics) and feed it through `CrossShardCommitReceiver::start`/`set_value`.

pub struct CrossShardStateView<'a, S> {
    cross_shard_data: HashMap<StateKey, RemoteStateValue>,
    base_view: &'a S,
}

impl<'a, S: StateView + Sync + Send> CrossShardStateView<'a, S> {
    pub fn new(cross_shard_keys: HashSet<StateKey>, base_view: &'a S) -> Self {
        let mut cross_shard_data = HashMap::new();
        trace!(
            "Initializing cross shard state view with {} keys",
            cross_shard_keys.len(),
        );
        for key in cross_shard_keys {
            cross_shard_data.insert(key, RemoteStateValue::waiting());
        }
        Self {
            cross_shard_data,
            base_view,
        }
    }

    #[cfg(test)]
    fn waiting_count(&self) -> usize {
        self.cross_shard_data
            .values()
            .filter(|v| !v.is_ready())
            .count()
    }

    pub fn set_value(&self, state_key: &StateKey, state_value: Option<StateValue>) {
        self.cross_shard_data
            .get(state_key)
            .unwrap()
            .set_value(state_value);
