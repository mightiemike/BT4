## Title
Unconditional relayer fee payout despite failed ERC-20/NEP-141 transfer due to inconsistent handling of non-standard-compliant NEP-141 tokens - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract's ERC-20-to-NEP-141 emulation layer rigidly assumes every target token strictly implements the standard NEP-141/NEP-145 JSON response shapes (`Option<StorageBalance>` for `storage_balance_of`, `U128` for `ft_balance_of`/`ft_total_supply`). When a token deviates even slightly from this exact schema — the direct analog of an ERC-20 that "does not return a bool value" — the emulated transfer always fails at the deserialization step. Because the relayer's fee refund is dispatched as an independent receipt *before* the transfer's actual outcome is known, the relayer is paid regardless of whether the token transfer succeeds, draining the wallet's NEAR balance with no corresponding value delivered to the intended recipient.

### Finding Description
`eth_emulation::try_emulation` maps the ERC-20 `transfer` selector directly onto NEP-141's `ft_transfer`, and the wallet contract must additionally probe `storage_balance_of` to decide whether a `storage_deposit` is required first [1](#0-0) . The probe's response is deserialized with a hard assumption about the exact NEP-141/NEP-145 JSON shape: [2](#0-1) 

If the target contract's response cannot be parsed into `Option<StorageBalance>` (e.g., a token that responds slightly differently than the exact standard, analogous to an ERC-20 that omits the expected `bool` return), the whole operation is unconditionally treated as failed with `"Unexpected response from NEP-141 storage_balance_of"` — no partial fallback or alternate handling exists.

Separately, and critically, the relayer's compensation for performing this action is not gated on the outcome of that action at all. It is dispatched as an independent receipt at parse time, before the `storage_balance_of` → `storage_deposit`/`ft_transfer` promise chain is even created: [3](#0-2) 

Because this refund promise (`env::promise_batch_create(&context.predecessor_account_id)` / `env::promise_batch_action_transfer`) is a separate receipt from the `.then()`-chained transfer promise built later in `inner_rlp_execute` [4](#0-3) , the two outcomes are independent: the fee payment to the relayer succeeds even when the intended NEP-141 transfer fails outright due to the strict/inconsistent handling of the token's response format.

### Impact Explanation
Any relayer submitting an ERC-20 (NEP-141) transfer transaction on behalf of a wallet-contract user is guaranteed to receive the quoted fee out of the user's account balance, even when the underlying transfer is guaranteed to fail because the target token does not conform exactly to the assumed NEP-141/NEP-145 response schema. This is unauthorized value movement out of the user's wallet: NEAR tokens leave the account with no corresponding NEP-141 tokens moving to the intended recipient, and the loss is deterministic/repeatable for any token contract that does not match the hardcoded expected JSON shape.

### Likelihood Explanation
This is triggerable by any relayer (an unprivileged party — this includes the account owner acting through their own relayer, or any third party operating the well-defined `rlp_execute` entry point) simply by submitting an ERC-20 `transfer` calldata targeting a NEP-141 contract that does not exactly implement the standard `storage_balance_of` response shape assumed here. No special privileges, validator collusion, or network-level assumptions are required — it is reachable from a single submitted transaction.

### Recommendation
Do not dispatch the relayer fee refund as an independent, unconditional receipt. Instead, chain the fee payment after the actual transfer promise resolves (e.g., include the fee transfer as part of, or contingent upon, the same `.then()` callback chain that determines `ExecuteResponse.success`), so that a failed/non-standard-token transfer does not still result in the relayer being paid from the user's balance. Additionally, consider gracefully handling non-conforming `storage_balance_of`/`ft_balance_of` responses (e.g., falling back to always issuing `storage_deposit`) instead of unconditionally failing when the exact NEP-141/145 schema is not matched.

### Proof of Concept
1. Deploy a NEP-141-like fungible token contract that implements `ft_transfer`/`ft_balance_of` correctly but whose `storage_balance_of` returns a JSON object that does not deserialize into `near_contract_standards::storage_management::StorageBalance` (e.g., extra/renamed required fields, or a different success/failure encoding) — analogous to a non-standard ERC-20 that omits the expected `bool` return.
2. A user signs an RLP Ethereum transaction with the ERC-20 `transfer` selector against this token, with a non-zero relayer `fee`, and submits it via a relayer to `rlp_execute`.
3. `inner_rlp_execute` immediately schedules the relayer fee refund receipt (lib.rs lines 374-385) independent of the transfer outcome.
4. The `storage_balance_of` cross-contract call returns, and `nep_141_storage_balance_callback` fails to deserialize the response, returning `success: false` with `"Unexpected response from NEP-141 storage_balance_of"` — no tokens are transferred.
5. Observe that the relayer's fee refund receipt still lands successfully, so the wallet's NEAR balance decreases by the fee amount even though the ERC-20/NEP-141 transfer never occurred.
