### Title
Malformed `host` query parameter causes unhandled exception in `decodeHost`/`sanitizeHost`, crashing unauthenticated admin/auth request handlers - ([File: packages/apps/shopify-api/lib/auth/decode-host.ts])

### Summary
`decodeHost` blindly calls the native `atob()` on the `host` query parameter without any error handling, assuming the caller has already ensured the string is valid, well-formed Base64. The pre-check performed by `sanitizeHost` (a regex) does not actually guarantee that the string is decodable by `atob`, so a malformed-but-regex-matching `host` value reaches `atob()` unguarded and throws, propagating out of `sanitizeHost` uncaught by any of its callers.

### Finding Description
`decodeHost` is a one-line wrapper around the native `atob`: [1](#0-0) 

It is invoked from `sanitizeHost`, which first validates the input against a permissive regex that only checks the character set and optional trailing `=` padding, but never validates that the string length is compatible with valid Base64 (i.e., a multiple of 4 once padding is considered): [2](#0-1) 

`atob` throws a `DOMException`/`InvalidCharacterError`-style error whenever the decoded string length is invalid (e.g. a Base64 string whose length modulo 4 equals 1), even though such a string is accepted by the regex `^[0-9a-zA-Z+/]+={0,2}$`. For example, the 5-character string `host=abcde` passes the regex but makes `atob('abcde')` throw.

Because `decodeHost` has no `try/catch`, and `sanitizeHost` also has no `try/catch` around the `decodeHost` call, this exception is not converted into the expected `InvalidHostError` — it propagates as a raw, unhandled JS exception out of `sanitizeHost` to its callers.

`sanitizeHost` (and therefore this unguarded decode path) is reachable from anonymous, unauthenticated HTTP requests through multiple auth entry points, without any surrounding try/catch:
- `getEmbeddedAppUrl` calls `sanitizeHost(...)` then `decodeHost(host)` directly on the raw `host` query param of any request: [3](#0-2) 
- `validateShopAndHostParams` (shopify-app-remix and shopify-app-react-router) calls `api.utils.sanitizeHost(url.searchParams.get('host')!)` directly on every embedded-admin authentication request, with no try/catch: [4](#0-3) [5](#0-4) 

This is directly analogous to the reported `abi.decode` issue: a decode routine assumes its input has already been validated as well-formed, but the actual validation performed upstream (the regex in `sanitizeShop`/`sanitizeHost`, similar to relying on "correctly encoded data" assumptions in `Cell`/`YakSwapCell`) is insufficient to guarantee that the decode call will not throw, and the resulting exception is not defensively handled where it is invoked.

### Impact Explanation
An anonymous attacker can send a single unauthenticated request (e.g. `GET /?shop=<shop>.myshopify.com&host=abcde`) to any embedded app's admin authentication route (`shopify.authenticate.admin` in shopify-app-remix / shopify-app-react-router) or to any code path calling `shopify.auth.getEmbeddedAppUrl`. This triggers an unhandled exception inside the auth-validation logic instead of the intended graceful `InvalidHostError`/redirect-to-login behavior. Depending on the runtime's global error handling, this can manifest as an uncaught exception causing a 500 error (denial of expected behavior for that route) or, in server runtimes without a catch-all error boundary around the request handler, a process-level unhandled exception. This is a denial-of-service class issue on an authentication handler reachable by any anonymous request, not requiring a merchant/session.

### Likelihood Explanation
High — no authentication is required, and the input needed to trigger the crash (`host` values whose length mod 4 equals 1, matching the loose Base64-charset regex) is trivial to construct with a single crafted query string on any embedded app.

### Recommendation
- In `decodeHost`, wrap the `atob` call in a `try/catch` and surface a controlled error (e.g., return `null`/throw the library's own `InvalidHostError`) instead of letting the native decode exception propagate.
- In `sanitizeHost`, strengthen the pre-validation to also check that the Base64 string length is valid (`length % 4 !== 1`, and consistent with the presence/absence of padding) before calling `decodeHost`, or catch the exception thrown by `decodeHost` and convert it into the existing `InvalidHostError` / `null` return path.
- Add regression tests for malformed-but-charset-matching `host` values (e.g., length 1, 5, 9 mod 4 == 1) verifying they produce `InvalidHostError`/`null` rather than an unhandled exception, for `sanitizeHost`, `getEmbeddedAppUrl`, and `validateShopAndHostParams` in both shopify-app-remix and shopify-app-react-router.

### Proof of Concept
1. Deploy an embedded app using `shopify-app-remix` or `shopify-app-react-router` with default configuration.
2. Send an unauthenticated request: `GET /?shop=my-shop.myshopify.com&host=abcde` (any Base64-charset string whose length mod 4 is 1, e.g. 5, 9, 13 characters, also works with longer strings such as `abcdefghi`).
3. Observe that `sanitizeHost('abcde')` passes the `base64regex` check, then `decodeHost('abcde')` calls `atob('abcde')`, which throws due to invalid Base64 length.
4. Because neither `decodeHost` nor `sanitizeHost` nor the calling `validateShopAndHostParams`/`getEmbeddedAppUrl` catch this exception, it propagates as an unhandled error rather than the expected `InvalidHostError`/login-redirect behavior, confirming the DoS-class defect on this unauthenticated auth handler.

      throw new ShopifyErrors.InvalidRequestError(
        'Request does not contain a host query parameter',
      );
    }

  };
