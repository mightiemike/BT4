### Title
Unauthenticated STARK proof verification during gateway `add_tx` enables CPU resource-exhaustion by any transaction sender - (File: crates/apollo_transaction_converter/src/transaction_converter.rs)

### Summary
The gateway performs expensive STARK proof verification (`starknet_proof_verifier::verify_proof`) for any `RpcInvokeTransaction::V3` carrying `proof_facts`/`proof` fields, as part of `convert_rpc_tx_to_internal_rpc_tx` → `run_proof_verification`, *before* any stateful signature/fee/balance validation occurs. Unlike declared classes, whose Sierra→CASM compilation is explicitly bounded by a `declare_compilation_semaphore` to prevent a "declare flood" from exhausting compiler resources, invoke transactions with client-side proofs have no equivalent concurrency limit on proof verification, only a per-transaction size cap. This mirrors the reported bug class: expensive "preflight" work is performed on unauthenticated/unauthorized input before the check that would normally gate it.

### Finding Description
In `add_tx_inner` (`crates/apollo_gateway/src/gateway.rs:214-298`), the flow is: `check_declare_permissions` (declare-only) → `stateless_tx_validator.validate` → (semaphore-gated) `convert_rpc_tx_to_internal_and_executable_txs` → stateful validation (`extract_state_nonce_and_run_validations`, which performs the actual signature/nonce/fee checks) → mempool admission.

For invoke transactions, `convert_rpc_tx_to_internal_and_executable_txs` (`crates/apollo_gateway/src/gateway.rs:435-466`) calls `transaction_converter.convert_rpc_tx_to_internal_rpc_tx`, which in `crates/apollo_transaction_converter/src/transaction_converter.rs:256-265` spawns `spawn_proof_verification` for any non-empty `proof_facts`. That path runs `run_proof_verification` (`crates/apollo_transaction_converter/src/transaction_converter.rs:398-424`), which does a `contains_proof` cache lookup and, on cache miss, executes `starknet_proof_verifier::verify_proof` inside `tokio::task::spawn_blocking` — a CPU-intensive STARK proof verification.

Crucially, `stateless_tx_validator.validate` (`crates/apollo_gateway/src/stateless_transaction_validator.rs:33-54`) only checks structural/size properties of the proof (`validate_proof_size`, `validate_proof_facts_and_proof_consistency`, `validate_client_side_proving_allowed`) — it does not verify the account's ECDSA/account signature, nonce, or ability to pay fees. The real cryptographic/economic authorization only happens later, in the stateful validator (invoked after the proof-verification task has already completed/consumed CPU).

The `declare` path explicitly acknowledges and mitigates this exact bug class: `crates/apollo_gateway_config/src/config.rs:27-38` states "Compiling a declared Sierra class to CASM is CPU- and memory-intensive, and it happens during transaction ingestion before the transaction's signature and balance are verified... Bound the number of compilations running concurrently to protect the node from resource exhaustion," implemented via `declare_compilation_semaphore` in `crates/apollo_gateway/src/gateway.rs:240-251`. No analogous semaphore/rate-limit exists for the proof-verification path taken by invoke transactions with `proof_facts`.

An attacker (any address, unprivileged, no special access) can submit a stream of V3 invoke transactions with distinct valid-looking `proof_facts`/`proof` payloads (up to `max_proof_size` from `StatelessTransactionValidatorConfig`) that pass all stateless structural checks but fail signature/fee validation. Each triggers a full, unbounded-concurrency STARK proof verification on the gateway's CPU pool before the transaction is ever rejected for an invalid signature or insufficient balance.

### Impact Explanation
This causes CPU/thread-pool exhaustion on gateway nodes reachable by any unprivileged sender submitting ordinary RPC transactions (or via P2P propagation of the same gateway `add_tx` path). Sustained proof-verification floods can degrade the gateway's ability to admit legitimate transactions, delaying block production/network liveness — a network-availability impact from a resource-only vector, though it can be sustained per-request without any admission-side concurrency cap (unlike the declare path, which the same codebase treats as worth explicit protection). This is a resource-consumption/availability issue rather than a fund-loss or consensus-divergence bug.

### Likelihood Explanation
High reachability: any account can submit a standard `RpcInvokeTransaction::V3` with `proof_facts`/`proof` through the normal `add_tx` RPC endpoint or via P2P gossip, with no special privileges, staking, or prior on-chain history required. The only per-request friction is the `max_proof_size` byte cap and passing purely structural stateless checks, both trivially satisfiable by a scripted attacker generating garbage-but-well-formed proof payloads.

### Recommendation
Apply the same defense already used for declare-compilation to the proof-verification path: introduce a bounded semaphore/concurrency limiter (analogous to `declare_compilation_semaphore`) around `run_proof_verification`/`spawn_proof_verification` in `crates/apollo_transaction_converter/src/transaction_converter.rs`, and/or move a cheap authenticity check (e.g., a fast structural/replay check against the mempool or a rate limit per sender address) before invoking `verify_proof`, so that unauthenticated proof floods cannot consume unbounded CPU ahead of stateful validation.

### Proof of Concept
1. Craft `N` distinct `RpcTransaction::Invoke(RpcInvokeTransaction::V3)` transactions, each with a unique, well-formed (correct byte-length, internally consistent `proof_facts`/`proof` pair) but ultimately verification-failing (or verification-succeeding-but-otherwise-invalid, e.g. bad signature/insufficient balance) proof payload sized close to `max_proof_size`.
2. Submit all `N` transactions concurrently to the gateway's `add_tx` RPC endpoint from a single or few funded/unfunded accounts (the sender need not be authorized for anything since only structural stateless checks are performed before proof verification).
3. Observe that all `N` requests pass `stateless_tx_validator.validate` and proceed to `convert_rpc_tx_to_internal_rpc_tx`, each spawning a `tokio::task::spawn_blocking` STARK proof verification with no concurrency cap, unlike the declare path's `declare_compilation_semaphore`; measure elevated CPU usage / increased `GATEWAY_ADD_TX_LATENCY` / `PROOF_VERIFICATION_LATENCY` for concurrent legitimate transactions during the flood, confirming resource contention prior to any signature/fee authorization.     async fn add_tx_inner(
        &self,
        tx: RpcTransaction,
        p2p_message_metadata: Option<BroadcastedMessageMetadata>,
    ) -> GatewayResult<GatewayOutput> {
        let mut metric_counters = GatewayMetricHandle::new(&tx, &p2p_message_metadata);
        metric_counters.count_transaction_received();
        if let RpcTransaction::Invoke(RpcInvokeTransaction::V3(ref inv)) = tx {
            if !inv.proof_facts.is_empty() {
                metric_counters.count_private_transaction_received();
            }
        }
        let is_p2p = p2p_message_metadata.is_some();

        if let RpcTransaction::Declare(ref declare_tx) = tx {
            if let Err(e) = self.check_declare_permissions(declare_tx) {
                metric_counters.record_add_tx_failure(&e);
                return Err(e);
            }
        }

        // Perform stateless validations.
        self.stateless_tx_validator.validate(&tx)?;

        let tx_signature = tx.signature().clone();

        // Declare conversions overload the compiler component's CPU and memory. Reject declares if
        // there are too many declares compiling in parallel. The permit is held only across
        // compilation and released before stateful validation.
        let compilation_permit = if matches!(tx, RpcTransaction::Declare(_)) {
            Some(self.declare_compilation_semaphore.try_acquire().map_err(|_| {
                let error = StarknetError::too_many_concurrent_declare_compilations();
                metric_counters.record_add_tx_failure(&error);
                error
            })?)
        } else {
            None
        };

        let (internal_tx, executable_tx, proof_data) =
            self.convert_rpc_tx_to_internal_and_executable_txs(tx, &tx_signature).await?;
        drop(compilation_permit);

    async fn run_proof_verification(
        proof_facts: ProofFacts,
        proof: Proof,
        proof_manager_client: SharedProofManagerClient,
    ) -> Result<bool, TransactionConverterError> {
        let contains_proof = proof_manager_client.contains_proof(proof_facts.clone()).await?;

        if contains_proof {
            return Ok(false);
        }

        let proof_facts_hash = proof_facts.hash();
        let verify_start = Instant::now();
        tokio::task::spawn_blocking(move || {
            starknet_proof_verifier::verify_proof(proof_facts, proof)
        })
        .await
        .expect("proof verification task panicked")?;
        let verify_duration = verify_start.elapsed();
        PROOF_VERIFICATION_LATENCY.record(verify_duration.as_secs_f64());
        info!(
            "Proof verification took: {verify_duration:?} for proof facts hash: \
             {proof_facts_hash:?}"
        );

        Ok(true)
    }

        &self,

                max_proof_size: self.config.max_proof_size,

// Compiling a declared Sierra class to CASM is CPU- and memory-intensive, and it happens during
// transaction ingestion before the transaction's signature and balance are verified. Bound the
// number of compilations running concurrently to protect the node from resource exhaustion.
//
// Derivation: compilations are served by the sierracompiler instances, so the safe per-gateway
// bound is the sierracompiler fleet's headroom divided across the gateway fleet, i.e.
// `per_instance_capacity * num_sierracompiler_instances / num_gateway_instances`. Observed
// sierracompiler usage per compilation is small (memory spike ~0.75% of an instance), so a single
// instance can absorb many concurrent compilations. 40 stays well within that envelope while still
// capping the blast radius of a declare flood; retune via the formula above if the
// sierracompiler/gateway instance ratio or per-instance capacity changes.
const DEFAULT_MAX_CONCURRENT_DECLARE_COMPILATIONS: usize = 40;
