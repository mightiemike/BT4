### Title
Front-runnable canonical address permanently disables TIP-2935 history-storage governance activation - (File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java)

### Summary
The `ALLOW_TVM_PRAGUE` governance proposal permanently activates the TIP-2935 (EIP-2935) history-storage feature by calling `HistoryBlockHashUtil.deploy()` once, at maintenance-time proposal processing. This deploy step checks whether contract/code already exists at the fixed canonical address `HISTORY_STORAGE_ADDRESS`, and if so, silently skips deployment forever. Because any unprivileged user can put a smart contract at that address before governance activates the fork, the mitigation-style "already exists" check makes it possible to permanently block the intended governance action — the same bug class as the Maia `addEcosystemToken()` finding, where a permissionless actor pre-populates a mapping/address the privileged action later checks against, causing the governance-intended state to never be reachable.

### Finding Description
`ProposalService.process()` handles `ALLOW_TVM_PRAGUE` by flipping the dynamic property and invoking `HistoryBlockHashUtil.deploy(manager)`: [1](#0-0) 

`deploy()` is guarded by an existence check against the canonical address, and if code or contract metadata is already present there, it logs a warning and returns without ever writing the TIP-2935 bytecode, without setting the install marker: [2](#0-1) 

The canonical address `HISTORY_STORAGE_ADDRESS` is a fixed, publicly known constant: [3](#0-2) 

Because this is a normal 21-byte TRON address (not a hash-derived CREATE2 address requiring a preimage), any unprivileged account can deploy a smart contract to that exact address before the `ALLOW_TVM_PRAGUE` proposal is approved and processed (e.g., via a `CreateSmartContract` transaction that specifies/derives that address, or — as the code's own comment notes — simply transferring TRX to create an account there and, for the code/contract-store branch specifically, an attacker-controlled contract deployment). Once `manager.getCodeStore().has(...)` or `manager.getContractStore().has(...)` is true for that address, `deploy()` unconditionally returns early on every future invocation of the proposal (and per code comments, "Proposal validation rejects re-activation," so this runs "at most once per chain history"), meaning the governance action can never succeed for the lifetime of the chain.

This mirrors the Maia bug class precisely:
- Privileged/governance action (`addEcosystemToken` / `ALLOW_TVM_PRAGUE` activation) is gated by a check on a global address/key.
- An unprivileged actor can populate that same key ahead of time via ordinary, permissionless functionality (creating a hToken with that underlying / deploying a contract at that address).
- Once populated, the check makes the governance function into a permanent no-op / revert, defeating the intended feature rollout — a classic "redundant/mis-scoped existence check that an attacker can trigger first" DoS.

### Impact Explanation
If an attacker deploys any contract at `HISTORY_STORAGE_ADDRESS` prior to `ALLOW_TVM_PRAGUE` being approved by governance, the TIP-2935 (EIP-2935) history-storage feature can never be installed on that chain — `saveBlockHashHistoryInstalled(1L)` is never reached, so `write()` will also perpetually no-op: [4](#0-3) 
This is a governance/feature-activation DoS: the on-chain committee proposal succeeds (the dynamic property flag flips) but the actual protocol upgrade payload silently and permanently fails to install, causing a persistent divergence between the intended (spec-compliant, EVM/Ethereum-compatible) chain behavior and the actual chain behavior — cross-chain tooling and contracts relying on TIP-2935/BLOCKHASH-history compatibility at the canonical address will silently get wrong/absent data forever, with no retry or recovery path once the flag is set.

### Likelihood Explanation
Likelihood is high for any network preparing to enable `ALLOW_TVM_PRAGUE`: the target address is a known constant published in the client source, requiring no computation (unlike CREATE2 salt search), and deploying a contract to a specific address is a normal, permissionless, unprivileged action available to any account with enough TRX for the deployment fee. The main friction is that the attacker must act before the community-approved proposal is processed (i.e., win the race against governance timing), which is realistic since proposal approval /maintenance-cycle timing is publicly observable in advance.

### Recommendation
Do not treat "foreign state already at the canonical address" as a silent, permanent skip. Instead:
- Detect the collision before/at proposal validation time and reject or delay activation with an explicit, auditable signal (event/log/alert) rather than silently no-op'ing forever.
- Consider forcibly reserving/pre-allocating the canonical address at genesis or at a well-known early block (so it cannot be front-run by user transactions), consistent with how EIP-2935 handles this on Ethereum via a pre-signed deployer transaction.
- If a collision is detected at activation time, provide a governance-controlled remediation path (e.g., a subsequent proposal type that retries deployment with cleanup of the colliding account/contract, or migrates the storage location) instead of permanently disabling the feature with only a log line.

### Proof of Concept
1. Before governance proposes/approves `ALLOW_TVM_PRAGUE`, an attacker submits a `CreateSmartContract` transaction that results in a contract or code being stored at `HISTORY_STORAGE_ADDRESS = 410000f90827f1c53a10cb7a02335b175320002935` (any means that populates `CodeStore` or `ContractStore` at that literal address).
2. Governance later proposes and gets `ALLOW_TVM_PRAGUE` approved; at maintenance time, `ProposalService.process()` hits the `ALLOW_TVM_PRAGUE` case and calls `HistoryBlockHashUtil.deploy(manager)`. [1](#0-0) 
3. Inside `deploy()`, `manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS)` or `getContractStore().has(...)` returns true due to the attacker's pre-existing contract, so the function logs a warning and returns without writing the BlockHashHistory bytecode or setting the install marker. [2](#0-1) 
4. Because "Proposal validation rejects re-activation" per the code's own documentation, this is a one-shot call — the feature is now permanently un-installable, confirmed by `write()` perpetually no-op'ing via the `isBlockHashHistoryInstalled()` gate. [4](#0-3) 

Note: I was not able to trace the exact transaction type/API path that lets an ordinary user deploy a contract to an arbitrary, non-CREATE2-derived address like `HISTORY_STORAGE_ADDRESS` (normal `CreateSmartContract` addresses are derived from sender+nonce, not chosen freely) — full confirmation of the exact attack transaction requires inspecting `WalletUtil.generateContractAddress` and related account-address derivation logic, which I could not fully verify within available context. If regular contract creation cannot target an arbitrary fixed address, the more directly confirmed front-run vector is simply sending TRX to `HISTORY_STORAGE_ADDRESS` to create a plain (non-contract) account there — the code path explicitly discusses and handles this "pre-existing non-contract account" case by mutating it in place, which itself confirms the address is reachable/writable by ordinary user transactions before governance activation.
