## Finding: `CrossShardStateView::get_usage` returns a fixed "untracked" sentinel instead of forwarding to the real usage, causing epoch-boundary `StateStorageUsage` divergence between sharded and non-sharded execution

### Summary
`CrossShardStateView::get_usage` unconditionally returns `StateStorageUsage::new_untracked()`, discarding whatever usage the wrapped `base_view` actually reports: [1](#0-0) 

This is inconsistent with the sibling wrapper `AggregatorOverriddenStateView`, which correctly forwards the call to its `base_view`: [2](#0-1) 

### Finding Description
`get_usage()` is not a purely diagnostic API — it is the sole data source for the Move native `get_state_storage_usage_only_at_epoch_beginning`, whose doc-comment explicitly states the result is deterministic only because "the execution layer guarantees a fresh state view" at the first transaction of the block: [3](#0-2) 

That native is called from `aptos_framework::state_storage::on_new_block`, which is invoked by every validator on every block via the `block` module's friend relationship, and which — precisely at epoch boundaries (`epoch != usage.epoch`) — overwrites the on-chain `StateStorageUsage` resource with whatever `(items, bytes)` the native returns: [4](#0-3) 

This resource is committed global state at `0x1::state_storage::StateStorageUsage`, hashed into the state root like any other resource, and is later consumed by `storage_gas.move` to (re)derive the per-item/per-byte gas-pricing curve for the entire following epoch — meaning a wrong value here doesn't just corrupt one resource but skews gas accounting (and hence balance debits) for every transaction in the epoch.

The bug: because `CrossShardStateView::get_usage()` hardcodes `StateStorageUsage::new_untracked()` rather than delegating to `base_view.get_usage()`, any block executed through the sharded execution path (which composes a `CrossShardStateView` over the shard-local state view) that lands on an epoch boundary will compute `items = 0, bytes = 0` for the epoch-beginning usage snapshot, regardless of the real accumulated item/byte counts in the DB. A non-sharded execution of the identical block, given the identical prior committed state, will call the real `StateView::get_usage()` (or, for the reused code path, `AggregatorOverriddenStateView`, which correctly forwards to `base_view.get_usage()`), producing the true tracked `(items, bytes)`.

This is not attacker-controlled data corruption — it's a deterministic execution-path bug — but the review's "hard-fork-only divergence" criterion is squarely met: two conformant, non-malicious execution strategies (BlockSTM vs. sharded block executor) that are required to be bit-for-bit interchangeable for consensus purposes produce different write sets, and hence different state roots, for the identical epoch-boundary block.

### Impact Explanation
- The `StateStorageUsage` resource, part of committed on-chain state, would contain different `(items, bytes)` values depending solely on which internal execution engine processed the block — not on any input difference.
- This corrupts the state root/proof for that block: any two conformant execution paths that must produce identical results diverge, which is the definition of a hard-fork-inducing bug.
- Downstream, `storage_gas.move`'s gas-curve computation for the whole subsequent epoch is derived from this wrong snapshot, meaning every transaction's storage-fee gas charge (and therefore account balance debits) in that epoch would differ between the two execution strategies as well, compounding the divergence far beyond a single resource.

### Likelihood Explanation
Triggering this requires no malicious input at all — only that a validator (or code path) uses the sharded block executor for a block that happens to be the first block of a new epoch, while another validator/path uses the plain executor for the same block content. This is a deterministic code defect rather than an adversarial exploit, so likelihood depends entirely on whether/when the sharded execution path is actually exercised for epoch-boundary blocks in production; I was unable to fully trace (within the iteration budget) whether `sharded_executor_service.rs` actually instantiates `CrossShardStateView` as the base view for the "first transaction of the block" context used by `on_new_block`. Regardless of current invocation frequency, the code as written is unconditionally wrong whenever that path is taken.

### Recommendation
Change `CrossShardStateView::get_usage` to delegate to `self.base_view.get_usage()`, matching the pattern already used in `AggregatorOverriddenStateView`, so that the sharded and non-sharded paths compute identical `StateStorageUsage` for the same underlying committed state.

### Proof of Concept
1. Prepare identical prior committed state with non-trivial state usage (`items > 0`, `bytes > 0`).
2. Execute a block that triggers an epoch change (so `on_new_block` calls `get_state_storage_usage_only_at_epoch_beginning`) via the plain `BlockExecutor`/`StateView` path — observe `StateStorageUsage.usage = (real_items, real_bytes)`.
3. Execute the identical block via the sharded block executor, where the per-shard resolver is backed by `CrossShardStateView::create_cross_shard_state_view` over the same prior state — observe `StateStorageUsage.usage = (0, 0)` due to `new_untracked()`.
4. Diff the two committed `StateStorageUsage` resources (and resulting state roots) — they differ for identical input, demonstrating the divergence.

```rust
/// Warning: the result returned is based on the base state view held by the
/// VM for the entire block or chunk of transactions, it's only deterministic
/// if called from the first transaction of the block because the execution layer
/// guarantees a fresh state view then.
fn native_get_usage(
    context: &mut SafeNativeContext,
    _ty_args: &[Type],
    _args: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    assert!(_ty_args.is_empty());
    assert!(_args.is_empty());

    context.charge(STATE_STORAGE_GET_USAGE_BASE_COST)?;

    let ctx = context.extensions().get::<NativeStateStorageContext>();
    let usage = ctx.resolver.get_usage().map_err(|err| {
        PartialVMError::new(StatusCode::VM_EXTENSION_ERROR)
            .with_message(format!("Failed to get state storage usage: {}", err))
    })?;

    Ok(smallvec![Value::struct_(Struct::pack(vec![
        Value::u64(usage.items() as u64),
        Value::u64(usage.bytes() as u64),
    ]))])
```

```text
    public(friend) fun on_new_block(epoch: u64) acquires StateStorageUsage {
        assert!(
            exists<StateStorageUsage>(@aptos_framework),
            error::not_found(ESTATE_STORAGE_USAGE)
        );
        let usage = borrow_global_mut<StateStorageUsage>(@aptos_framework);
        if (epoch != usage.epoch) {
            usage.epoch = epoch;
            usage.usage = get_state_storage_usage_only_at_epoch_beginning();
        }
    }
```
