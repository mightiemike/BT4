## Analysis: Wallet Contract deposit leftover not refunded on success [1](#0-0) 

### Title
Wallet Contract Retains Excess Caller Deposit on Successful Cross-Contract Call - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `rlp_execute` flow tracks an external caller's attached deposit (`CallerDeposit`) purely so it can be refunded if the downstream cross-contract call fails. On success, no such refund is ever issued — the code path only refunds on `PromiseResult::Failed`, never checking whether the deposit that was actually forwarded to the target (`action.deposit`, derived independently from the RLP-encoded Ethereum transaction) matches the full amount the caller attached to the `rlp_execute` call.

### Finding Description
`CallerDeposit::new` captures the entire `context.attached_deposit` (the full deposit attached by an external, non-self predecessor to the outer NEAR transaction) as the amount eligible for refund: [2](#0-1) 

This `caller_deposit` is threaded through every callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`), but the only place it is ever used is inside `rlp_execute_callback`, and strictly in the `Failed` branch: [3](#0-2) 

Meanwhile, the actual amount transferred to the target account/contract is `action.deposit`, which is parsed independently from the RLP-encoded Ethereum transaction (via `internal::parse_rlp_tx_to_action`) and passed into the outgoing promise in `action_to_promise`: [4](#0-3) 

There is no assertion anywhere in `inner_rlp_execute` that `action.deposit == context.attached_deposit`. Because attached NEAR deposit is credited to the receiving account's balance the moment the `FunctionCall` action executes (independent of what the contract's own logic subsequently forwards), any portion of the caller's attached deposit that is not equal to `action.deposit` is permanently absorbed into the Wallet Contract's own account balance once the downstream promise succeeds — this is exactly analogous to the reported "unchecked collateral leftovers" pattern: after the "swap"/forwarding step, any leftover asset is not verified or returned to the party who supplied it.

This is corroborated by the contract's own test suite, which documents the asymmetry explicitly: [5](#0-4) 

The comment "External caller does not get a refund when their tokens are spent" at line 215 shows the refund-only-on-failure design is intentional for the "tokens spent" case, but the code does not verify that "spent" actually equals "attached" — it never checks or reconciles `action.deposit` against `context.attached_deposit` before forwarding.

### Impact Explanation
Any unprivileged account acting as a relayer/caller of `rlp_execute` who attaches a NEAR deposit greater than the amount required to satisfy the RLP-encoded Ethereum transaction's `value`/fee fields loses that excess permanently to the Wallet Contract's own balance whenever the downstream call happens to succeed, with no refund path. This is a direct value-loss vector for the calling account (a relayer transaction submitter), reachable purely by supplying transaction data through the public `rlp_execute` entry point — it requires no privileged role.

### Likelihood Explanation
Reachability requires only that some external, non-privileged account calls the public, `#[payable]` `rlp_execute` method with `attached_deposit` exceeding what the parsed action actually forwards, and that the downstream call/promise succeeds. Whether real relayers routinely misjudge the deposit amount (versus computing it exactly from the RLP tx `value` field) could not be fully confirmed — I was unable to inspect `internal::parse_rlp_tx_to_action`'s full logic (in `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`) within the available tool budget to determine whether the SDK/relayer tooling always guarantees `attached_deposit == action.deposit`, or whether mismatches (e.g., due to the 24-vs-18-decimal Wei/yoctoNEAR conversion visible in `create_rlp_execute_tx`) are a normal occurrence in practice.

### Recommendation
Before forwarding `action.deposit` to the target in `action_to_promise`, assert that `context.attached_deposit == action.deposit` (accounting for any legitimate fee carve-out), and reject/refund the transaction outright (or refund the excess in both the success and failure paths of `rlp_execute_callback`) if there is a positive leftover. At minimum, extend the `PromiseResult::Successful` branch of `rlp_execute_callback` to refund any unspent portion of `context.attached_deposit` beyond what was actually forwarded, symmetric to the existing `Failed`-branch refund.

### Proof of Concept
1. Deploy a Wallet Contract instance for an eth-implicit account, as in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs`.
2. As an external caller (e.g. `worker.root_account()`), call `rlp_execute` with a signed RLP transaction whose `value`/`args.deposit` field requests a transfer of `X` yoctoNEAR to a valid, reachable target (so the promise succeeds), but attach `attached_deposit = X + Y` (`Y > 0`) to the outer NEAR transaction, mirroring the setup in `test_caller_refunds`: [6](#0-5) 
3. Observe that the promise succeeds (`result.success == true`) and the caller's balance decreases by the full `X + Y`, while only `X` is credited to the target — the extra `Y` remains stuck in the Wallet Contract's balance with no `CallerDeposit`-based refund, since the refund logic is only triggered on `PromiseResult::Failed`.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
