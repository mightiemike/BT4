## Confirmed root cause

`set_promise_yield_receipt` / `enqueue_promise_yield_timeout` write directly to trie via bare `set()` calls, with no adjustment to `account.storage_usage()` [1](#0-0) . Compare this to normal contract storage writes, which explicitly update `outcome.storage_usage` and get checked by `check_storage_stake` before commit [2](#0-1) [3](#0-2) . Promise-yield state (the receipt itself plus its timeout-queue entry) is never billed against the creating account's storage stake, so it is not covered by NEAR's normal "you must pay for the bytes you store" defense.

The `PromiseYieldTimeout` queue is explicitly documented as **a single, per-shard, non-partitioned FIFO** shared by every account on the shard [4](#0-3) . Any account can append to it cheaply: `wasm_yield_create_base` costs ~0.15 Tgas on current mainnet params [5](#0-4) , versus a 300 Tgas per-function-call budget, and up to `max_promises_per_function_call_action` = 1024 yields can be queued per call [6](#0-5) .

Crucially, congestion control — the mechanism nearcore built precisely to stop "single account floods the shard cheaply" DoS (as shown by all the fairness/PTQ/pool-size protections already present for ordinary receipts) — explicitly **excludes** `PromiseYield`/`PromiseResume` receipts from gas accounting: `compute_receipt_congestion_gas` returns `Gas::ZERO` for both, with the code comment stating this is because yields "are confined to a single account, hence they never cross the shard boundaries" [7](#0-6) . That reasoning is only true for the receipt's cross-shard delivery — it ignores that the *timeout entry* is not confined to the account, it lands in the shared per-shard `PromiseYieldTimeout` queue that competes with every other account's yields for the shard's per-chunk compute budget.

Finally, `resolve_promise_yield_timeouts` runs **last**, after local, delayed, and incoming receipts, and only while `total.compute < compute_limit` [8](#0-7) ; if higher-priority receipt processing (which the same attacker can also cheaply flood via ordinary self-calls) is saturating the chunk's compute budget every block, this phase gets zero budget and the queue is starved indefinitely, since draining is strict FIFO ordered by `expires_at` [9](#0-8) .

### Title
Unmetered, unbounded per-shard `PromiseYieldTimeout` queue lets a single account DoS all yield/resume users on the shard - (File: `runtime/runtime/src/congestion_control.rs`, `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`promise_yield_create` is a cheap host function (a fixed base fee plus per-byte, ~0.15 Tgas on mainnet) that any unprivileged account can call repeatedly from ordinary function-call transactions. Each call pushes an entry into the `PromiseYieldTimeout` queue, which is a **singleton, per-shard** trie-backed FIFO shared by every account on that shard, not a per-account structure. Congestion control — the subsystem specifically engineered to prevent a single cheap sender from monopolizing shared, bounded chunk resources (analogous to what the Sherlock report calls for with a per-call minimum/cap) — deliberately charges `Gas::ZERO` congestion cost to `PromiseYield`/`PromiseResume` receipts. The timeout entries also bypass storage staking (no `storage_usage` update), so the attacker pays only the yield's fixed create fee, not for the state it occupies or the shared processing slot it consumes.

### Finding Description
- The queue is documented as one FIFO per shard, addressed by a global `PromiseYieldIndices` singleton key, holding entries from *all* accounts on the shard [4](#0-3) .
- `enqueue_promise_yield_timeout`/`set_promise_yield_receipt` write raw trie entries with no storage-stake accounting [1](#0-0) .
- `compute_receipt_congestion_gas` assigns zero congestion cost to yield/resume receipts, meaning arbitrarily large queue growth from one account never trips `shard_accepts_transactions`'s rejection threshold that would otherwise throttle a flooding sender [7](#0-6) .
- `resolve_promise_yield_timeouts` is the last processing phase in a chunk and only proceeds while compute budget remains, draining strictly in `expires_at` order [9](#0-8) ; the processing order is local → delayed → incoming → yield timeouts [10](#0-9) .

An attacker on a given shard can (1) submit many cheap self-directed function calls, each creating up to `max_promises_per_function_call_action` yields (paying only the modest `yield_create_base`/`yield_create_byte` fees, no storage stake), continuously enqueuing entries into the shared timeout queue faster than a single chunk's compute budget can ever drain even the attacker's own backlog once expiry hits; and (2) simultaneously (or even independently, since ordinary traffic can already saturate `compute_limit`) ensure local/delayed/incoming receipt processing consumes the full per-chunk compute budget, leaving the yield-timeout phase permanently starved of compute.

### Impact Explanation
Because the queue is a shared per-shard FIFO and its front is strictly ordered by `expires_at`, once the attacker's high-volume, low-`expires_at` entries clog the head of the queue, every other account's promise-yield timeouts on the same shard — used by production patterns like cross-contract oracle callbacks and yield/resume based escrows — cannot resolve, either because the compute budget for the phase is fully consumed processing the flood, or because FIFO ordering forces draining the attacker's entries first. Contracts that rely on a yield timing out to release funds or unblock state (a common failure-safety pattern for `yield_create`/`yield_resume`) can be left permanently stuck as long as the flood is sustained, which is inexpensive to sustain indefinitely. This matches the accepted "permanently frozen funds"/"transaction-triggered halt of user-observable progress" impact class, reached purely through a single account's normal `FunctionCall` transactions.

### Likelihood Explanation
Likelihood is high: `promise_yield_create` is a stable, unprivileged host function reachable via a normal `FunctionCall` action from any funded account; no special permissions, staking, or validator role is required. The attack cost is bounded by gas price times a modest fixed fee per yield, orders of magnitude below the fee an attacker would pay to achieve equivalent disruption through the congestion-controlled `Action` receipt path (which the protocol explicitly throttles per-shard). This is exactly the "single unprivileged tx sender, low-cost, no per-call/per-account limit" bug class described in the source report, mapped onto nearcore's own exempted-from-congestion receipt kind.

### Recommendation
- Charge non-zero congestion cost (gas and/or bytes) for `PromiseYield` creation so that `shard_accepts_transactions`/`process_tx_limit` throttle a flooding sender once the shared timeout queue backs up, instead of hard-coding `Gas::ZERO` in `compute_receipt_congestion_gas`.
- Charge storage stake against the creating/receiving account for `PromiseYieldReceipt` and `PromiseYieldTimeout` entries, mirroring ordinary contract storage accounting, so growth is bounded by the account's own balance rather than being free.
- Reserve a minimum guaranteed compute budget for `resolve_promise_yield_timeouts` each chunk (analogous to the "keep minimum incoming queue length to avoid deadlocks" idea already used for delayed receipts) so the phase can never be starved indefinitely by other receipt classes.
- Consider partitioning/limiting the timeout queue per-account (or per-account rate-limiting yield creation) so a single account cannot dominate a shared, shard-wide resource.

### Proof of Concept
1. Deploy a contract that in a single `FunctionCall` action calls `promise_yield_create` in a loop up to `max_promises_per_function_call_action` (1024) times, each with a short/no-op callback method — cost per call is `base + yield_create_base + yield_create_byte * len` [11](#0-10) .
2. Submit this transaction repeatedly (from one signer, incrementing nonce) every block, well within `max_total_prepaid_gas`/`max_gas_burnt` per receipt.
3. Each yield enqueues into the shared `PromiseYieldTimeout` queue with `expires_at = block_height + yield_timeout_length_in_blocks` (200 blocks by default) [12](#0-11) , at zero congestion-gas cost [13](#0-12) .
4. In parallel, submit ordinary self-call `Action` receipts to saturate `compute_limit` every chunk so `total.compute >= compute_limit` before the runtime reaches the last processing phase [8](#0-7) .
5. After ~200 blocks, other accounts' legitimate yields on the same shard reach `expires_at` but their timeout entries sit behind the attacker's in the strictly ordered FIFO and/or the phase never runs, so their `PromiseResume` timeout receipts are never generated — any contract logic depending on that timeout (e.g., fund release/escrow expiry) is permanently blocked while the flood continues.

pub fn check_storage_stake(
    account: &Account,
    account_balance: Balance,
    runtime_config: &RuntimeConfig,
) -> Result<(), StorageStakingError> {
    let billable_storage_bytes = account.storage_usage();
    let required_amount = runtime_config
        .storage_amount_per_byte()
        .checked_mul(u128::from(billable_storage_bytes))
        .ok_or_else(|| {
            format!(
                "Account's billable storage usage {} overflows multiplication",
                billable_storage_bytes
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    let available_amount = account_balance
        .checked_add(account.locked())
        .ok_or_else(|| {
            format!(
                "Account's amount {} and locked {} overflow addition",
                account.amount(),
                account.locked(),
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    if available_amount >= required_amount {
        Ok(())
    } else {
        if is_zero_balance_account(account) {
            return Ok(());
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(
            required_amount.checked_sub(available_amount).unwrap(),
        ))
    }
}

pub fn promise_yield_create(
    ctx: &mut Ctx,
    memory: &mut [u8],
    method_name_len: u64,
    method_name_ptr: u64,
    arguments_len: u64,
    arguments_ptr: u64,
    gas: u64,
    gas_weight: u64,
    register_id: u64,
) -> Result<u64> {
    ctx.result_state.gas_counter.pay_base(base)?;
    if ctx.context.is_view() {
        return Err(HostError::ProhibitedInView {
            method_name: "promise_yield_create".to_string(),
        }
        .into());
    }
    ctx.result_state.gas_counter.pay_base(yield_create_base)?;

    let method_name = get_memory_or_register(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        method_name_ptr,
        method_name_len,
    )?;
    if method_name.is_empty() {
        return Err(HostError::EmptyMethodName.into());
    }
    let arguments = get_memory_or_register(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        arguments_ptr,
        arguments_len,
    )?;
    let method_name = method_name.to_owned();
    let arguments = arguments.to_owned();

    // Input can't be large enough to overflow, WebAssembly address space is 32-bits.
    let num_bytes = method_name.len() as u64 + arguments.len() as u64;
    ctx.result_state.gas_counter.pay_per(yield_create_byte, num_bytes)?;
    // Prepay gas for the callback so that it cannot be used for this execution any longer.
    ctx.result_state.gas_counter.prepay_gas(Gas::from_gas(gas))?;

    // Here we are creating a receipt with a single data dependency which will then be
    // resolved by the resume call.
    pay_gas_for_new_receipt(&mut ctx.result_state.gas_counter, &ctx.fees_config, true, &[true])?;
    let (new_receipt_idx, data_id) =
        ctx.ext.create_promise_yield_receipt(ctx.context.current_account_id.clone())?;

    let new_promise_idx = checked_push_promise(ctx, Promise::Receipt(new_receipt_idx))?;
    pay_action_base(
        &mut ctx.result_state.gas_counter,
        &ctx.fees_config,
        ActionCosts::function_call_base,
        true,
    )?;
    pay_action_per_byte(
        &mut ctx.result_state.gas_counter,
        &ctx.fees_config,
        ActionCosts::function_call_byte,
        num_bytes,
        true,
    )?;
    ctx.ext.append_action_function_call_weight(
        new_receipt_idx,
        method_name,
        arguments,
        Balance::ZERO,
        Gas::from_gas(gas),
        GasWeight(gas_weight),
    )?;

    ctx.registers.set(
        &mut ctx.result_state.gas_counter,
        &ctx.config.limit_config,
        register_id,
        *data_id.as_bytes(),
    )?;
    Ok(new_promise_idx)
}
