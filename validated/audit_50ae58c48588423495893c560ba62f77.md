### Title
Silent `long` overflow in `MarketUtils.multiplyAndDivide` corrupts DEX order settlement amounts - (File: `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java`)

### Summary
`MarketUtils.multiplyAndDivide(a, b, c, disableMath)` is the core pricing/matching formula used by the on-chain order-book market (`MarketSellAssetActuator`) to compute how much of the buy-token a taker or maker receives during order matching. When the fast-path `a*b` multiplication overflows a `long`, the function falls back to `BigInteger` arithmetic but converts the *final* result back to `long` using the non-checked `.longValue()` instead of `.longValueExact()`. If the final quotient `(a*b)/c` itself still exceeds `Long.MAX_VALUE`, this silently truncates/wraps to an incorrect (potentially negative or arbitrary) `long`, which is then used directly to credit/debit user account balances.

### Finding Description
The vulnerable function: [1](#0-0) 

The fast path uses `multiplyExact`/`floorDiv`, which throw `ArithmeticException` on overflow of the intermediate product `a*b`. The fallback branch (entered only when the fast path's `a*b` overflows) recomputes using `BigInteger`, but returns `aBig.multiply(bBig).divide(cBig).longValue()` — `longValue()` does not check range and silently truncates high-order bits instead of throwing.

This function is called directly in the market matching engine to determine settlement quantities for both taker and maker: [2](#0-1) [3](#0-2) [4](#0-3) 

The only guard on the input quantities is a configurable `quantityLimit`, checked at order creation time — it does not bound the *product* or the ratio between colliding orders' quantities: [5](#0-4) 

Because `a` (`takerSellRemainQuantity`/`makerSellRemainQuantity`) and `b` (`makerSellQuantity`/`makerBuyQuantity`) are independent order-book values each bounded only by `quantityLimit`, and `c` (`makerBuyQuantity`/`makerSellQuantity`) can be set arbitrarily small (as low as 1) by any user creating a maker order, an attacker can construct order pairs where:
1. `a*b` overflows `long` (triggering the `BigInteger` fallback), and
2. the final quotient `(a*b)/c` still exceeds `Long.MAX_VALUE`, causing `.longValue()` to silently wrap to a corrupted value (potentially negative).

That corrupted value then flows into `takerOrderCapsule`/`makerOrderCapsule` quantity fields and ultimately into asset/TRX balance adjustments via `MarketUtils.returnSellTokenRemain` and account balance updates in the actuator, producing an inconsistent or exploitable token settlement.

This differs materially from the original Angle report: there, the overflowing value was cast via `SafeCast.toUint128`, which reverts the transaction — a DoS-only outcome that Angle explicitly declined to fix because "swaps will be reverting." Here, `.longValue()` does **not** revert; it silently produces a wrong number that is committed to state.

### Impact Explanation
This is a settlement/accounting-integrity issue in the decentralized exchange module, reachable by any unprivileged user placing sell/buy orders via `MarketSellAssetContract`. A crafted pair of orders can cause the matching engine to compute and credit/debit a wrapped (potentially negative or drastically wrong) token quantity instead of throwing, corrupting account balances or order-book state rather than safely aborting the transaction.

### Likelihood Explanation
Reachability depends on the committee-configured `getMarketQuantityLimit()` dynamic parameter being large enough (roughly `> ~3.04e9` for the multiplication to overflow `long`, per `sqrt(Long.MAX_VALUE)`) and on the ability to set very small buy/sell ratios in a maker order, both of which are plausible operational configurations. I was unable to verify the current default value of `getMarketQuantityLimit()` in this pass, so confirming exact real-world reachability requires checking the deployed dynamic property value; regardless, the code path itself is unsound irrespective of the specific limit chosen, since no additional check bounds the final `(a*b)/c` result before consuming it as a `long`.

### Recommendation
Change the fallback conversion in `MarketUtils.multiplyAndDivide` from `.longValue()` to `.longValueExact()` so that any residual overflow of the final quotient throws `ArithmeticException` (consistent with the fast path's `multiplyExact`/`floorDiv` semantics), causing the transaction to fail safely instead of silently committing a corrupted settlement amount.

### Proof of Concept
1. User A creates a maker sell order with `sellTokenQuantity = X` (large, near `quantityLimit`) and `buyTokenQuantity = 1` (minimal), placing it in the order book.
2. User B (taker) creates a matching sell order with `sellTokenQuantity`/`buyTokenQuantity` chosen so that, in `matchSingleOrder`, `MarketUtils.multiplyAndDivide(a, b, c, ...)` is invoked with `a`, `b` both large enough that `a*b` overflows `long` (triggering the `BigInteger` fallback) and `c = 1` so the quotient `(a*b)/1` also exceeds `Long.MAX_VALUE`.
3. `.longValue()` truncates the oversized `BigInteger` to an incorrect (possibly negative) `long`, which becomes `takerBuyTokenQuantityReceive`/`makerBuyTokenQuantityReceive` in [6](#0-5)  and is used to update order/account state, instead of the transaction reverting as intended by the exact-arithmetic hardening used elsewhere in this codebase (e.g. `SafeExchangeProcessor`, `ResourceProcessor.divideCeilExact`).

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
