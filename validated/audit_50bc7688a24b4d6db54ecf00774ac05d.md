## Title
`TransactionOutput::ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification, allowing replay-verify to accept a divergent state root — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the local proof-binding check used by debugger/replay tooling (`aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) and by the chunk executor (`execution/executor/src/chunk_executor/mod.rs`) to confirm a locally-computed `TransactionOutput` matches an authenticated `TransactionInfo` pulled from storage/backup/network. It validates status, gas used, `state_change_hash` (write-set hash), and `event_root_hash`, but it deliberately does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, even though these are fields committed into `TransactionInfo` and covered by the transaction accumulator/ledger-info signature. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` compares only a subset of the fields that `TransactionInfoV0`/`V1` commit to: it checks `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event root hash against `event_root_hash`. [2](#0-1) 

The function's own comment acknowledges the gap explicitly:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [3](#0-2) 

`TransactionInfoV1` includes `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as committed, hashed fields of the object stored in the transaction accumulator. [4](#0-3) 

These checkpoint hashes are computed independently during execution in `DoStateCheckpoint::run`/`get_state_checkpoint_hashes`, which derives the state root, hot-state root, and (when `compute_trading_native_state_roots` is enabled) the position-state root from the locally computed state summary. [5](#0-4) 

Because `ensure_match_transaction_info` never cross-checks these checkpoint hashes against the corresponding fields of the authenticated `TransactionInfo`, any code path that relies on this function as its sole "did local execution match the authenticated ledger" check will silently accept a divergence in the state/hot-state/position-state root while still reporting a "successful match". This is a genuine broken invariant: the transaction accumulator leaf (`TransactionInfo`) is supposed to bind the exact post-execution state root, but the verifier used by replay tooling and part of the chunk-executor path does not enforce that binding for these fields.

### Impact Explanation
If local execution genuinely diverges from the authenticated chain (a state-computation bug, non-determinism, or a hard-fork-only divergence in state accumulation logic), tooling relying on `ensure_match_transaction_info` (debugger replay, CLI replay, and the chunk-executor verification path in `execution/executor/src/chunk_executor/mod.rs`) would fail to detect the divergence in the state checkpoint hash. This directly undermines a core proof-integrity guarantee: that a `TransactionInfo` accepted as matching an authenticated chunk correctly commits to the executed state. In the trading-native/position-state feature area this is explicitly called out as capable of masking a divergence in the "authenticated position state root" from local execution. This matches the required scope of "wrong ... state proof accepted as valid" and "hard-fork-only divergence during commit, replay, ... verification."

### Likelihood Explanation
The gap is only exercised when the caller depends on `ensure_match_transaction_info` for checkpoint-hash validation. I was not able to fully confirm, within tool-call limits, whether `execution/executor/src/chunk_executor/mod.rs`'s use of `ensure_match_transaction_info` is the terminal check for state consistency during real state-sync/chunk-apply (as opposed to state checkpoint hashes being separately re-verified via a different path such as `get_state_checkpoint_hashes`'s `known_state_checkpoints` comparison in `do_state_checkpoint.rs`, which does check state/hot-state hashes against `known` values supplied from the `TransactionInfo`). It is plausible that the checkpoint-hash consistency is enforced elsewhere in the mainline chunk-apply path (`DoStateCheckpoint::get_state_checkpoint_hashes` does compare `known[idx] == Some(computed_last_checkpoint_hash)`), which would mean the concrete impact is confined to the debugger/CLI replay tools and the `compute_trading_native_state_roots` position-state feature — exactly as the code's own TODO states. Because I could not fully trace all call sites and confirm the absence of a redundant checkpoint check in every affected path within the available iterations, I cannot assert this rises to a "committed state differs from correct VM result on mainnet" impact; the code's own comment scopes it as a replay-verify tooling blind spot tied to a not-yet-enabled feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`).

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` to compare the locally computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when available) against the corresponding fields on the given `TransactionInfo`, as the existing TODO already specifies, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled on mainnet.

### Proof of Concept
Not applicable as a runnable exploit — this is a code-review-level gap in an internal consistency-checking function, self-documented by the maintainers' own TODO comment. The concrete corrupted-invariant path is:
1. Local execution produces a `TransactionOutput` whose true post-execution state/hot-state/position-state root differs from the authenticated `TransactionInfo` (e.g., due to a hard-fork/non-determinism bug).
2. `ensure_match_transaction_info` is called to validate the output against the authenticated `TransactionInfo`. [6](#0-5) 
3. Because only `status`, `gas_used`, `state_change_hash`, and `event_root_hash` are checked, the function returns `Ok(())` despite the state-root divergence. [7](#0-6) 

Given the residual uncertainty about whether an independent check elsewhere (`do_state_checkpoint.rs`'s `known_state_checkpoints` comparison) already closes this gap for the mainline commit path, this should be treated as a confirmed code-level gap with self-acknowledged but not fully mainnet-proven severity, rather than a fully proven critical/high mainnet exploit.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
