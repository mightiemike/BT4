## Title
Backup restore accepts unverified `LedgerInfoWithSignatures` when the restored epoch history is shorter than the ledger info's epoch, allowing malicious backup data to write arbitrary state/transactions into a node's local ledger - (File: `storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs`)

### Summary
The db-restore tool (`aptos-db-tool` restore / bootstrap flow) treats the backup archive it reads from as an untrusted data source and is supposed to validate every `LedgerInfoWithSignatures` it consumes against a chain of real validator signatures rooted at genesis (`EpochHistory`), analogous to how `BeefyAdapter` is supposed to validate `_beefyBooster` against a permission registry before trusting it with token custody. However, `EpochHistory::verify_ledger_info` silently skips signature verification whenever the ledger info's epoch number exceeds the number of epoch-ending `LedgerInfo`s it has accumulated, and callers in the state-snapshot and transaction restore paths only call this verifier when an `EpochHistory` happens to be present and only trust its `Ok(())` result — including the "skipped" `Ok(())`. A backup source (or metadata provider) that supplies an incomplete/omitted epoch-ending history alongside a forged `(TransactionInfoWithProof, LedgerInfoWithSignatures)` pair can therefore have its self-consistent-but-fabricated root hash accepted, causing the restore process to commit attacker-chosen state values and transactions into the target `AptosDB` as if validator-endorsed.

### Finding Description
`EpochHistory::verify_ledger_info` is the sole gate that binds a `LedgerInfoWithSignatures` coming from backup storage to the real validator set: [1](#0-0) 

Note the early-return branch:
```rust
if epoch > self.epoch_endings.len() as u64 {
    warn!(... "Epoch is too new and can't be verified. Previous chunks are verified and node \
        won't be able to start if this data is malicious.");
    return Ok(());
}
```
This returns `Ok(())` — i.e., "verified" — without ever checking `li_with_sigs.verify_signatures(...)` when the epoch history built from the backup metadata is shorter than the ledger info's claimed epoch.

Both the state-snapshot and transaction restore paths rely on this check as their only defense against forged `LedgerInfoWithSignatures`, and they only invoke it when `epoch_history` was actually supplied: [2](#0-1) [3](#0-2) 

In both cases the code:
1. Loads a `(proof, li)` pair straight from backup storage (untrusted content, chosen by whatever service/bucket answers the restore tool's requests).
2. Verifies internal self-consistency: the accumulator proof matches `li`'s own root hash, and `manifest.root_hash`/write set hashes are consistent with the (attacker-controlled) `li`.
3. Calls `epoch_history.verify_ledger_info(&li)` — but if `epoch_history.epoch_endings` (built earlier from the same untrusted backup's advertised epoch-ending manifests, see `EpochHistoryRestoreController::run_impl`) doesn't yet cover `li`'s epoch, this call is a no-op that returns `Ok(())`.
4. Proceeds to write the (fabricated) state values / transactions into the local `AptosDB` using `manifest.root_hash` as the trusted root for the `JellyfishMerkleTree` restore, or replays the forged transaction list.

Because `epoch_endings` itself is populated purely from whatever epoch-ending manifests the same untrusted storage backend chooses to serve (`RestoreCoordinator::run_impl` builds it via `metadata_view.select_epoch_ending_backups(...)` against `self.storage`), a backup source can simply omit or truncate epoch-ending backups so `epoch_endings.len()` never reaches the epoch used in a forged snapshot/transaction chunk, permanently keeping the "too new" bypass active for that data.

### Impact Explanation
This breaks the fundamental storage-restore invariant that all proof-bearing data ingested into `AptosDB` must be bound to a ledger version/root that is validator-endorsed. A malicious or compromised backup storage endpoint can:
- Cause the restore tool to commit an entirely fabricated state tree (arbitrary account balances, module bytecode, etc.) as the "genesis"/checkpoint state at a chosen version, since `manifest.root_hash` and the state values are attacker-controlled and the signature check is skipped.
- Cause fabricated transactions/outputs/events to be replayed and persisted as canonical history.

Any node bootstrapped or fast-synced from such a backup ends up with ledger data that diverges from the real chain — a direct "committed state differs from the correct VM result / corrupts durable ledger data" impact, and it undermines any later proof verification that trusts this restored data as ground truth.

### Likelihood Explanation
The restore/bootstrap tooling is explicitly designed to work against backup storage that is not the node operator's own trusted infrastructure in many deployments (shared/community S3 buckets, unauthenticated HTTP backup services, etc.), and the code comment itself acknowledges the danger ("won't be able to start if this data is malicious") without actually preventing it. No special privilege is needed beyond controlling the backup storage/manifest content the victim's restore tool is pointed at — an "unprivileged" data-supplier role, directly analogous to the malicious vault owner supplying an unvalidated `_beefyBooster`.

### Recommendation
Remove the silent bypass in `EpochHistory::verify_ledger_info`: if `epoch > self.epoch_endings.len()`, the function should fail closed (return an error) rather than `Ok(())`, unless the caller can independently establish trust (e.g., via a `trusted_waypoints` entry) for that specific ledger info/version. Additionally, `EpochHistoryRestoreController` should refuse to proceed with restore/replay when its constructed `epoch_endings` chain does not extend to the target version's epoch, instead of allowing downstream consumers to silently treat unverifiable ledger infos as verified.

### Proof of Concept
1. Stand up a malicious `BackupStorage` implementation (or compromise an existing one) that:
   - Serves epoch-ending manifests only up through epoch `N`.
   - Serves a state-snapshot manifest whose `proof` file contains a self-consistent but forged `(TransactionInfoWithProof, LedgerInfoWithSignatures)` pair with `epoch = N + 1` and an attacker-chosen `root_hash`, plus attacker-chosen leaf chunks that hash to that root.
2. Run `aptos-db-tool restore` (or the `RestoreCoordinator`) against this storage with `--skip-epoch-endings` unset (default), targeting a version in epoch `N+1`.
3. `EpochHistoryRestoreController` builds `epoch_endings` with length `N` (covering only epochs it was given).
4. `StateSnapshotRestoreController::run_impl` calls `epoch_history.verify_ledger_info(&li)`; since `li.epoch() == N+1 > epoch_endings.len() == N`, verification is skipped and returns `Ok(())`.
5. The tool proceeds to restore the attacker's state values into the target `AptosDB` under `manifest.root_hash`, completing with no error — the node's local ledger now reflects the attacker's fabricated state.

    pub fn verify_ledger_info(&self, li_with_sigs: &LedgerInfoWithSignatures) -> Result<()> {
        let epoch = li_with_sigs.ledger_info().epoch();
        ensure!(!self.epoch_endings.is_empty(), "Empty epoch history.",);
        if epoch > self.epoch_endings.len() as u64 {
            // TODO(aldenhu): fix this from upper level
            warn!(
                epoch = epoch,
                epoch_history_until = self.epoch_endings.len(),
                "Epoch is too new and can't be verified. Previous chunks are verified and node \
                won't be able to start if this data is malicious."
            );
            return Ok(());
        }
        if epoch == 0 {
            ensure!(
                li_with_sigs.ledger_info() == &self.epoch_endings[0],
                "Genesis epoch LedgerInfo info doesn't match.",
            );
        } else if let Some(wp_trusted) = self
            .trusted_waypoints
            .get(&li_with_sigs.ledger_info().version())
        {
            let wp_li = Waypoint::new_any(li_with_sigs.ledger_info());
            ensure!(
                *wp_trusted == wp_li,
                "Waypoints don't match. In backup: {}, trusted: {}",
                wp_li,
                wp_trusted,
            );
        } else {
            self.epoch_endings[epoch as usize - 1]
                .next_epoch_state()
                .ok_or_else(|| anyhow!("Shouldn't contain non- epoch bumping LIs."))?
                .verify(li_with_sigs)?;
        };
        Ok(())
    }
