## Analog Found

### Title
Wallet Contract relayer fee is paid and the Ethereum-style nonce is consumed before the underlying action is known to succeed, causing user fund loss on insufficient/incorrect gas estimation - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The near-wallet-contract's `rlp_execute` entry point (reachable by any unprivileged NEAR transaction signer or RPC caller submitting a `FunctionCall` to an eth-implicit account) pays out a relayer fee and permanently consumes the account's replay-protection nonce *before* the actual requested action (base-token transfer / ERC-20 transfer / arbitrary call) is confirmed to succeed. If the caller mis-estimates the gas required for the multi-hop promise chain that performs the actual action, that action can fail asynchronously while the fee has already been paid and the nonce already burned - an unrecoverable loss of user funds for no delivered service, structurally identical to the reported `RedemptionSender` bug where tokens are burned before the cross-chain message is confirmed deliverable.

### Finding Description
`inner_rlp_execute` increments the wallet's nonce for essentially all transaction kinds immediately after successfully parsing the RLP transaction, *before* the promise that performs the actual action is created: [1](#0-0) 

In the same function, if the parsed transaction specifies a non-zero relayer fee, a **separate, unconditional** `promise_batch_create` + `promise_batch_action_transfer` is dispatched to pay the relayer immediately - independent of, and not chained to, the promise that will actually execute the user's intended action: [2](#0-1) 

The actual action is only executed afterward via `action_to_promise(...).then(rlp_execute_callback)`, and the gas attached to that downstream chain (`callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` or `ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas())`) is derived from user/relayer-controlled values rather than validated against the gas actually attached to the outer `rlp_execute` `FunctionCall`: [3](#0-2) 

If the caller (a relayer, or the account owner calling directly, both unprivileged callers reachable via a signed transaction/RPC) under-provisions gas for the full multi-hop chain (registrar lookup, storage-balance check, storage_deposit, `ft_transfer`, callback), the outer `FunctionCall` can succeed just long enough to (a) commit the nonce increment and (b) dispatch the unconditional fee-refund transfer, while the downstream action promise later fails with `PromiseResult::Failed`. In that failure branch, only the `caller_deposit` (attached NEAR deposit) is refunded - the relayer fee already paid out is not reversed: [4](#0-3) 

Because the nonce was already incremented, the user cannot resubmit the identical logical transaction; it is permanently consumed even though the intended action never executed, and the relayer fee already paid cannot be recovered.

### Impact Explanation
This produces unauthorized/irrecoverable value movement from an unprivileged user's wallet: a fee is paid to a relayer for a service (execution of the user's intended action) that was not delivered, and the user's one-time nonce is burned so the action can never be retried under that nonce. This is directly analogous to the reported Medium-severity finding: value is transferred (burned/paid) based on an unvalidated gas/fee assumption, and the downstream operation that was supposed to justify that payment fails, permanently losing user funds with no automatic recovery path.

### Likelihood Explanation
Any relayer (permissionless, using an access key scoped only to `rlp_execute`) or the account owner acting as their own relayer can trigger this simply by mis-estimating gas for a multi-hop transaction (ERC-20 transfer to an unregistered NEP-141 receiver, or an address-check-gated base-token transfer), which is a very plausible operational mistake since there is no `estimateFees`-equivalent helper exposed by the Wallet Contract to compute the minimum safe attached gas for these branching promise chains.

### Recommendation
- Defer paying the relayer fee until the actual action promise has resolved successfully (chain the fee-refund transfer onto the success path of `rlp_execute_callback` rather than dispatching it eagerly in `inner_rlp_execute`).
- Do not increment the nonce for transaction kinds whose downstream execution can still fail purely due to gas mis-estimation, or validate that sufficient gas is attached for the *entire* worst-case promise chain (registrar/storage lookups + callbacks + final action) before consuming the nonce and paying any fee, analogous to exposing/enforcing an `estimate_fees`-style minimum-gas check prior to committing irreversible state changes.

### Proof of Concept
1. A relayer (or the wallet owner) calls `rlp_execute` for an ERC-20 `Transfer` action where the receiver is not yet registered with the token's NEP-141 contract, and where the signed Ethereum transaction specifies a non-zero relayer fee.
2. The relayer attaches gas to the outer NEAR `FunctionCall` sufficient to pass initial parsing and dispatch `storage_balance_of` + the fee-refund transfer, but insufficient to cover the subsequent `storage_deposit` + `ft_transfer` + `rlp_execute_callback` chain (per `nep_141_storage_balance_callback`, `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:194-273`).
3. `inner_rlp_execute` increments `self.nonce` (line 364) and unconditionally dispatches the relayer's fee transfer (lines 374-385).
4. The downstream promise chain later fails due to insufficient gas; `rlp_execute_callback` refunds only `caller_deposit`, not the relayer fee (lines 296-312).
5. Result: the relayer has been paid, the user's nonce is consumed, and the intended ERC-20 transfer never happened - the user's fee payment is permanently lost with no possibility of resubmitting the same nonce.
