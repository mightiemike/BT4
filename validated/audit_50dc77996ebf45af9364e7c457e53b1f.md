### Title
Unbounded growth of `savedCallbacks` map allows memory-exhaustion DoS via unauthenticated `HandleLegacyUserMessage` flood - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` inserts an entry into `h.savedCallbacks` for every accepted `web_api_trigger` message before any allowlist or rate-limiting is applied, as explicitly flagged by the `// TODO: apply allowlist and rate-limiting here` comment. Because eviction only happens on a periodic ticker (`pruneCallbacks`, run every `CallbackPruneIntervalSec`, default 30s) and not synchronously at insertion time, an attacker who can submit distinct `MessageId`s faster than the prune interval can grow the map far beyond `defaultMaxSavedCallbacks` (20000), consuming unbounded gateway memory.

### Finding Description
`HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) validates payload structure, timestamp freshness, and method name, then calls `common.ValidatedRequestFromMessage(msg)` and unconditionally stores the callback: [1](#0-0) [2](#0-1) 

Unlike the sibling `functionsHandler.HandleLegacyUserMessage`, which enforces an allowlist and a per-sender rate limiter before doing any work (`core/services/gateway/handlers/functions/handler.functions.go:208-219`), this capabilities handler has no such check — the TODO comment at line 384 confirms this gap is acknowledged but unimplemented.

The only bound on map size is enforced in `pruneCallbacks` (`core/services/gateway/handlers/capabilities/handler.go:299-339`), which is invoked solely from a background ticker in `Start()` (`core/services/gateway/handlers/capabilities/handler.go:269-285`) at `CallbackPruneIntervalSec` cadence (default 30s per `defaultCallbackPruneIntervalSec`). There is no synchronous cap check at insertion time in `HandleLegacyUserMessage`. The constant comment itself acknowledges this: `defaultMaxSavedCallbacks = 20000 // could briefly exceed under heavy load` (line 44).

Entry into this code path is via `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`), which routes any legacy request carrying a `DonId` to the relevant handler's `HandleLegacyUserMessage` after only `msg.Validate()` (structural validation) — no authentication of the caller identity is required to reach the handler, since this is a "legacy" user-facing HTTP endpoint intended for arbitrary external users of web API trigger capabilities.

Each request only needs: a unique `MessageId` (attacker controlled, and the only length check is `len(jsonRequest.ID) > 200`), a valid `payload.Timestamp` within `MaxAllowedMessageAgeSec`, method `web_api_trigger`, and a message that passes `common.ValidatedRequestFromMessage` (structural/signature validation of the message envelope, not caller authorization/allowlisting). None of these checks constitute rate limiting or a hard cap on stored callbacks.

### Impact Explanation
An attacker able to reach the gateway's user-facing HTTP endpoint can flood it with valid `HandleLegacyUserMessage` (`web_api_trigger`) requests using unique `MessageId`s. Each accepted request adds an entry to `h.savedCallbacks` holding a `savedCallback` struct (including a live `handlers.Callback`), and the map is only trimmed once per `CallbackPruneIntervalSec` (default 30s). Sustained submission faster than the prune interval causes unbounded (until process OOM) growth of gateway process memory, resulting in denial of service of the gateway service and, if OOM occurs, that host process crashes — impacting all DONs/handlers served by that gateway instance. This matches a memory-exhaustion DoS bounty impact category.

### Likelihood Explanation
Feasibility is high: the endpoint is unauthenticated with respect to caller identity/allowlisting for this handler (no allowlist/rate-limiter, contrary to the sibling `functionsHandler`), and generating unique `MessageId`s and a validly-formed/signed message envelope is cheap and fully attacker-controlled. Preconditions match the stated requirement: attacker just needs to generate unique message IDs and issue requests faster than the 30s prune tick, which is trivial for an unprivileged network client with modest throughput. The vulnerability is explicitly acknowledged in code comments (both the TODO for allowlist/rate-limiting and the "could briefly exceed under heavy load" note), which increases confidence this is a known, unmitigated gap rather than a theoretical race.

### Recommendation
- Enforce a synchronous hard cap on `len(h.savedCallbacks)` inside `HandleLegacyUserMessage` before insertion (reject/backpressure with an error response, e.g. `api.HandlerError`/rate-limit error, when at or above `MaxSavedCallbacks`), rather than relying solely on periodic `pruneCallbacks`.
- Implement the TODO: add an allowlist and a per-sender rate limiter (mirroring `functionsHandler`'s `allowlist`/`userRateLimiter` pattern) to `HandleLegacyUserMessage` before any callback is stored.
- Optionally reduce `CallbackPruneIntervalSec` or trigger eviction opportunistically per-insert (e.g., check-and-prune when size exceeds threshold) to shrink the exposure window.

### Proof of Concept
Unit/integration test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` via `NewHandler` with default config (`MaxSavedCallbacks` default 20000, `CallbackPruneIntervalSec` default 30).
2. In a loop, synchronously call `h.HandleLegacyUserMessage(ctx, msg, callback)` many more times than `MaxSavedCallbacks` (e.g. 50000) within a duration shorter than the configured prune interval, each with a unique `MessageId`, valid `Timestamp`, method `MethodWebAPITrigger`, and a payload/signature that passes `common.ValidatedRequestFromMessage`.
3. After the loop (before the ticker fires `pruneCallbacks`), assert `len(h.savedCallbacks) > h.config.MaxSavedCallbacks`, demonstrating the map size synchronously exceeded the configured cap.
4. Expected (fixed) behavior: insertion should be rejected once `len(h.savedCallbacks) >= MaxSavedCallbacks`, so the assertion `len(h.savedCallbacks) <= h.config.MaxSavedCallbacks` should hold at all times, including mid-burst, not just after the next prune tick.
