### Title
Meta-Transaction Deposit Refund Misdirection Allows Sender to Drain Relayer's Attached Deposit — (`runtime/runtime/src/actions.rs`)

---

### Summary

In NEAR's meta-transaction (NEP-366) flow, `apply_delegate_action` creates the inner action receipt with `predecessor_id = sender_id` (Alice). When that inner receipt fails on the receiver's shard, the runtime sends the full deposit refund to `receipt.balance_refund_receiver()`, which resolves to `receipt.predecessor_id()` — Alice — not the relayer who actually funded the deposit. An unprivileged sender can exploit this by crafting a `DelegateAction` with a large attached deposit that is guaranteed to fail on the receiver's shard, causing the relayer to permanently lose the deposited NEAR tokens while Alice gains them.

---

### Finding Description

**Step 1 — Relayer pays the deposit.**
When the relayer submits the outer transaction, `verify_and_charge_transaction` deducts the full cost — including all attached deposits inside the inner actions — from the relayer's account. The relayer is the `signer_id` of the outer receipt.

**Step 2 — Inner receipt is created with Alice as predecessor.**
`apply_delegate_action` constructs the forwarded receipt:

```rust
// runtime/runtime/src/actions.rs  lines 456-469
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),          // ← Alice, NOT the relayer
    receiver_id: delegate_action.receiver_id().clone(),
    receipt_id: CryptoHash::default(),
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(), // ← relayer
        ...
        actions: delegate_action.get_actions(),
    }),
});
```

`predecessor_id` is set to `sender_id` (Alice). The relayer's identity is only preserved in `signer_id`. [1](#0-0) 

**Step 3 — On failure, deposit refund goes to Alice.**
`refund_unspent_gas_and_deposits` computes the deposit refund and routes it to `receipt.balance_refund_receiver()`:

```rust
// runtime/runtime/src/lib.rs  lines 1269-1273
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(),   // ← resolves to predecessor_id = Alice
        deposit_refund,
    ));
}
``` [2](#0-1) 

`balance_refund_receiver()` returns `refund_to.as_ref().unwrap_or_else(|| self.predecessor_id())`. Because the inner receipt is a `Receipt::V0` with `ReceiptEnum::Action` (not `ActionReceiptV2`), `refund_to` is always `None`, so the refund unconditionally goes to `predecessor_id` = Alice. [3](#0-2) 

**Step 4 — Gas refund correctly goes to the relayer.**
Gas refunds use `action_receipt.signer_id()` (the relayer), so gas is correctly returned. Only the deposit refund is misdirected. [4](#0-3) 

**The broken invariant:** The party that funded the deposit (relayer) does not receive the deposit refund when the inner action fails. The code comment at line 471–475 acknowledges this explicitly but treats it as a relayer responsibility rather than a protocol fix: [5](#0-4) 

The protocol documentation also explicitly acknowledges the financial incentive for Alice to exploit this: [6](#0-5) 

---

### Impact Explanation

The relayer pays for the deposit upfront. If the inner receipt fails, the deposit (which can be any amount up to the relayer's balance, as specified by Alice in the `DelegateAction`) is transferred to Alice's account. The relayer suffers a direct, permanent loss of NEAR tokens equal to the attached deposit. This is a **stealing of funds** impact: Alice gains tokens she did not own, at the relayer's expense.

---

### Likelihood Explanation

Alice can trivially craft a `DelegateAction` that will fail on the receiver's shard:
- Call a non-existent method on any contract.
- Call a method that requires a specific contract state Alice knows will not be satisfied.
- Target a receiver account that has no contract deployed.

The relayer cannot always predict execution failure because contract state can change between the time Alice signs the `DelegateAction` and the time it executes. The attack requires no special privileges — any NEAR account holder can be Alice.

---

### Recommendation

Use `ActionReceiptV2` (which has a `refund_to: Option<AccountId>` field) when constructing the inner receipt inside `apply_delegate_action`, and set `refund_to = Some(action_receipt.signer_id())` (the relayer). This mirrors the existing `promise_refund_to` / `set_refund_to` host function mechanism already present in the runtime.

Alternatively, add a `refund_to` field to `DelegateAction` itself so the relayer can explicitly specify where deposit refunds should go, analogous to the `refundAddr` parameter suggested in the external report's mitigation. [7](#0-6) 

---

### Proof of Concept

1. Alice has zero NEAR. She crafts a `DelegateAction`:
   - `sender_id = alice.near`
   - `receiver_id = some_contract.near`
   - `actions = [FunctionCall { method_name: "nonexistent", deposit: 100_000_000_000_000_000_000_000_000 /* 100 NEAR */ }]`
   - Signs it with her key.

2. Alice sends the signed `DelegateAction` to a relayer off-chain.

3. The relayer wraps it in a transaction (`signer = relayer.near`, `receiver = alice.near`), paying 100 NEAR + gas from its own account.

4. On Alice's shard, `apply_delegate_action` creates the inner receipt with `predecessor_id = alice.near`, `signer_id = relayer.near`.

5. On `some_contract.near`'s shard, the function call fails (`MethodNotFound`).

6. `refund_unspent_gas_and_deposits` issues a deposit refund receipt to `receipt.balance_refund_receiver()` = `alice.near`.

7. Alice's balance increases by 100 NEAR. The relayer's balance is permanently reduced by 100 NEAR (plus gas).

Alice has stolen 100 NEAR from the relayer with a single signed message and no NEAR of her own.

    /// A list of actions to process when all input_data_ids are filled
