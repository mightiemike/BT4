## #Vulnerability Found

### Title
Signer/Node Block-Proposal Timestamp Validation Uses Local Wall-Clock Instead of a Canonical Reference, Causing Divergent Accept/Reject Verdicts - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
The Nakamoto block-proposal validation endpoint rejects a proposed block if its header timestamp is "too far into the future," but the reference point for "future" is each validating node's own local `get_epoch_time_secs()` call rather than any consensus-derived value (such as the burn-chain header timestamp). This is the same bug class as the reported EMA issue: a time-sensitive accept/reject decision is computed against an unsynchronized, locally-observed clock instead of a canonical timestamp, so different validators can reach different verdicts for the identical block.

### Finding Description
`NakamotoBlockHeader::timestamp` is attacker-controlled (set by the tenure's miner) and is documented as needing to be "at most 15 seconds into the future" for signers to consider the block valid [1](#0-0) . The actual check is implemented in `NakamotoBlockProposal::validate`:

```
if self.block.header.timestamp > get_epoch_time_secs() + 15 {
    ...
    return Err(BlockValidateRejectReason { reason_code: ValidateRejectCode::InvalidTimestamp, ... });
}
``` [2](#0-1) 

`get_epoch_time_secs()` reads each node/signer's own local system clock at the moment it happens to process the HTTP `/v3/block_proposal` request — this call is not derived from any burnchain header field or other value that is guaranteed to be identical across nodes (unlike `burn_header_timestamp`, which is read from the Bitcoin block header and is thus canonical, see `BlockSnapshot::burn_header_timestamp` [3](#0-2) ). Because request propagation, network latency, and per-machine clock skew vary between signers, two signers evaluating the exact same block proposal at (nominally) the "same time" can compute different `get_epoch_time_secs()` values and thus reach opposite verdicts on whether the timestamp check passes.

This mirrors the external report's root cause precisely: a consensus-affecting time-window check is evaluated against "whenever/wherever the check happens to run" (`block.timestamp` in the report's EMA case, `get_epoch_time_secs()` here) instead of against a value that is fixed and identical for every validator (the report's suggested `_submitTimestamp`; here, an analog would be the block's tenure burn-view timestamp already available as `tenure_burn_chain_tip.burn_header_timestamp` from `validate_normal_nakamoto_block_burnchain`, which the proposal-validation path already loads via `Self::validate_nakamoto_tenure_snapshot` [4](#0-3) ).

### Impact Explanation
A miner (an unprivileged party requiring no other party's key) can pick a block timestamp deliberately placed at the edge of the "+15 seconds" boundary. Signers whose local clocks are fast, or who process the request slightly later due to network jitter, will reject the block (`InvalidTimestamp`), while signers whose clocks are slow, or process it earlier, will accept it. This produces a temporary split in signer votes for the same block/tenure — some signers sign, others reject — which can delay or prevent the block from reaching the 70%+ signature weight threshold needed for it to become canonical, causing a temporary tip disagreement across signers/nodes. This falls under the allowed "High" impact category: "a minority-triggerable sortition/VRF/static-validation divergence... temporary tip disagreement."

### Likelihood Explanation
Likelihood is significant because:
- Clock skew and processing/network jitter across independently operated signer nodes are common and expected in production deployments; no majority collusion is required.
- The window is only 15 seconds, and there is no tolerance/grace period reconciling the boundary against a shared reference, so even small, ordinary skew (a few seconds) between the miner's clock and a signer's clock, or between two signers' clocks, is sufficient to trigger divergent verdicts.
- The miner already fully controls the timestamp field placed in the header, so triggering the boundary condition requires no privileged access — only normal block production.

### Recommendation
Anchor the "future" bound to a value that is identical for every validator rather than each validator's local wall clock. Options:
- Use the tenure's burn-chain view timestamp (`tenure_burn_chain_tip.burn_header_timestamp`, already fetched in this code path) plus a fixed allowance, instead of `get_epoch_time_secs()`.
- If a local-clock check must remain (e.g., as a DoS guard), widen the tolerance substantially and treat it as a soft/advisory check that does not, by itself, determine final signer consensus, so that ordinary clock skew cannot cause a persistent split in signer verdicts.

### Proof of Concept
1. A miner produces a Nakamoto block with `header.timestamp = T0 + 14` (T0 = the miner's local "now").
2. Signer A's clock reads slightly behind T0 (e.g., -2s) when it processes the proposal: `T0 - 2 + 15 = T0 + 13 < T0 + 14` → **rejected** as `InvalidTimestamp`.
3. Signer B's clock reads slightly ahead of T0 (e.g., +2s), or B processes the request a couple seconds later: `T0 + 2 + 15 = T0 + 17 > T0 + 14` → **accepted**.
4. The same block is thus rejected by A and accepted by B purely due to clock/processing differences, exactly reproducing (in structure) the external report's demonstration that using a non-canonical, locally-observed timestamp instead of an agreed reference produces incorrect/divergent results for identical input — here manifesting as inconsistent signer verdicts on the same block proposal (test harness for the timestamp bounds already exists at [5](#0-4) , demonstrating the sensitivity of this check to timing).
