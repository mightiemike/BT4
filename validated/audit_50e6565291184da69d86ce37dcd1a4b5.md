### Title
Unconditional panic on `AotContractExecutor::from_path` load failure crashes the compilation worker/batcher on any declared class - ([File: crates/apollo_compile_to_native/src/compiler.rs])

### Summary
`SierraToNativeCompiler::compile` in `crates/apollo_compile_to_native/src/compiler.rs` correctly maps *compilation* failures (the subprocess invocation) into a `Result`, but the subsequent step that *loads* the compiled artifact via `AotContractExecutor::from_path` is force-unwrapped, so any load-time failure (as opposed to a compile-time failure) causes an unconditional panic — regardless of the `panic_on_compilation_failure` config flag. This is the same bug class as the NEAR nearcore fix: compilation succeeding while the subsequent load step fails and is mishandled with a panic instead of being treated as a deterministic error.

### Finding Description
In `SierraToNativeCompiler::compile`: [1](#0-0) 

The subprocess-based compilation (`compile_with_args`) is properly guarded with `ResourceLimits` (CPU time, file size, memory) and converted into `CompilationUtilError` on failure. However, once the subprocess produces the output artifact file, the code does:
```
Ok(AotContractExecutor::from_path(output_file.path())
    .map_err(|e| CompilationUtilError::CompilationError(e.to_string()))?
    .unwrap())
```
The `?` only propagates the outer `Result`'s `Err` variant; the `.unwrap()` afterward means that if `AotContractExecutor::from_path` returns `Ok(None)` — e.g., because loading/mmap'ing the compiled shared object fails for reasons distinct from compiler-reported errors (disk I/O errors reading the temp file in the parent process, virtual-memory/mmap resource exhaustion in the parent process which is *not* covered by the `ResourceLimits` applied only to the child compiler subprocess, dynamic-linker/versioning failures, or truncated/corrupted output) — the process panics unconditionally.

This differs fundamentally from the `panic_on_compilation_failure` config path, which is an intentional, opt-in escape hatch guarded in `process_compilation_request` (`crates/blockifier/src/state/native_class_manager.rs:294-318`). The `.unwrap()` in the compiler itself bypasses that guard entirely, firing even when `panic_on_compilation_failure` is `false` (the production default, per `crates/apollo_node/resources/config_schema.json:257-261`).

`compile()` is reached via `process_compilation_request` → `run_compilation_worker` (async `LazyCompilation` mode) or synchronously via `NativeClassManager::set_and_compile` in `WaitOnCompilation` mode: [2](#0-1) 

`set_and_compile` is invoked whenever a class not yet in cache is read during execution, e.g. from `StateReaderAndContractManager::get_compiled_from_class_manager`: [3](#0-2) 

This path is reached deterministically whenever any account submits a `Declare` transaction (or invokes/library-calls a previously declared class not yet cached) for a Cairo1 class, on a node running with Cairo Native enabled.

### Impact Explanation
When triggered in `WaitOnCompilation` mode, the panic occurs synchronously inside the block-building/validation call stack (batcher), crashing that thread mid-execution of a transaction/block. Because compilation-then-load behavior is deterministic given the same Sierra input and environment, every honest validator running Cairo Native with the same triggering class would hit the identical panic when executing/validating the block containing the triggering `Declare` (or first execution) transaction — this can manifest as a network-wide inability to build/validate that block (deterministic execution divergence/halt) rather than an isolated single-node crash, which matches the "network unable to confirm new transactions" impact bar. In `LazyCompilation` mode, the panic occurs in the background worker thread; depending on the thread's panic behavior it may only lose the worker (degrading to CASM fallback) but still represents an unhandled, security-relevant panic surface directly reachable from unprivileged contract declaration.

### Likelihood Explanation
Reaching the panic requires: (1) Cairo Native mode enabled (`cairo_native_mode != Off`), which is an operator/network configuration choice, not attacker-controlled, and (2) an actual load failure of the produced artifact at `AotContractExecutor::from_path`, which is a lower-probability, more environment-dependent condition (parent-process resource exhaustion, disk error, dynamic-loader issue) than a compile-time syntax/semantic error, which is already handled without panicking. This makes the likelihood moderate: it depends on Cairo Native being enabled and on encountering conditions that make the compiled artifact fail to load despite the subprocess having produced output successfully — exactly the scenario the referenced NEAR fix addresses for wasmtime.

### Recommendation
Change `SierraToNativeCompiler::compile` to convert a load failure (`Ok(None)` or any error from `AotContractExecutor::from_path`) into a `CompilationUtilError::CompilationError`/`UnexpectedError` rather than unwrapping, so it flows through the existing `Result`-based error handling (and respects `panic_on_compilation_failure` semantics) instead of causing an unconditional panic:
```rust
AotContractExecutor::from_path(output_file.path())
    .map_err(|e| CompilationUtilError::CompilationError(e.to_string()))?
    .ok_or_else(|| CompilationUtilError::UnexpectedError(
        "Failed to load compiled native executor from path".to_owned(),
    ))
```

### Proof of Concept
1. Enable Cairo Native (`cairo_native_mode = "wait_on_compilation"` or `"lazy_compilation"`) on a sequencer node.
2. Submit a `Declare` transaction (or trigger execution of an already-declared but uncached class) whose Sierra program compiles successfully via the `cairo-native` compiler subprocess but whose resulting artifact fails to load in-process via `AotContractExecutor::from_path` (e.g., by constraining the parent process's available virtual memory/mmap capacity, or via a crafted/edge-case artifact that the loader rejects post-compilation while the compiler itself succeeds).
3. Observe the `.unwrap()` in `crates/apollo_compile_to_native/src/compiler.rs:58-60` panics inside `process_compilation_request`, crashing the compilation worker thread (`LazyCompilation`) or the batcher's synchronous execution path (`WaitOnCompilation`), independent of the `panic_on_compilation_failure` config value.
