Based on my investigation, I found a plausible analog to the CVE's bug class (unhandled panic/exception triggered by attacker-controlled, unvalidated numeric/length data), but I could not fully confirm end-to-end reachability from a single untrusted L1 message due to index truncation on the RPC handler file. I'm presenting what I found with the caveats needed to judge confidence.

### Title
Unchecked `split_first().expect()` on `L1HandlerTransaction` calldata can panic the sequencer on empty payload - (File: `crates/starknet_api/src/hash.rs`)

### Summary
`l1_handler_message_hash`, used to compute the L1↔L2 message hash for L1 handler transactions, calls `calldata.0.split_first().expect("Invalid calldata, expected at least from_address")` [1](#0-0) . This mirrors the CVE's bug class: parsing/consuming untrusted external data (there, an HTTP `Content-Length` header; here, transaction `calldata`) with no validation and no error handling, so malformed input triggers a Rust panic (`std::terminate`-equivalent) instead of a graceful error.

### Finding Description
`Calldata` has no non-empty invariant, and `L1HandlerTransaction` derives `Deserialize`, so it can be constructed with an empty `calldata` vector [2](#0-1) . The codebase already acknowledged and fixed exactly this hazard in the sibling function `payload_size()`, switching to `saturating_sub` specifically because "Calldata has no non-empty invariant and L1HandlerTransaction derives Deserialize" [3](#0-2) . However, `l1_handler_message_hash` (invoked via `L1HandlerTransaction::calc_msg_hash`) still uses `.expect()` on `split_first()` rather than returning a `Result`, so the same class of empty-calldata input that was hardened in one function remains unguarded in the message-hash computation [4](#0-3) .

### Impact Explanation
If this hash computation is reachable on attacker/L1-message-controlled data before any non-empty-calldata validation occurs, it would cause an unrecoverable panic that crashes the node process, matching the CVE's "remote process crash via malformed... input" pattern — a network-availability impact (nodes unable to process further transactions) rather than a state-corruption one.

### Likelihood Explanation
I could not fully confirm this reachability path. `calc_msg_hash`/`l1_handler_message_hash` is referenced from `crates/apollo_rpc/src/v0_8/api/api_impl.rs` (5 occurrences) and `crates/apollo_l1_events/src/l1_events_provider.rs` / `l1_scraper.rs`, but I was unable to retrieve the actual RPC handler code (the file read returned only its `use` statement due to index truncation), so I cannot confirm whether: (a) the RPC path constructs `L1HandlerTransaction` from raw, attacker-suppliable fields that could legitimately produce empty calldata, or (b) calldata is always guaranteed non-empty by the L1 core-contract event encoding (which always prepends `from_address`) before reaching this function, as seen in the L1 event test encoder [5](#0-4) . Given the sequencer normally only manufactures `L1HandlerTransaction`s from L1 scraper events (which structurally always include `from_address`), the more likely reachable path — if any — is through an RPC endpoint that computes a message hash from user-supplied fields directly (e.g., a message-status/fee-estimation style endpoint), which I could not verify due to the missing file content.

### Recommendation
Change `l1_handler_message_hash` to return a `Result` (or otherwise handle the empty-calldata case defensively, consistent with the fix already applied to `payload_size()`) instead of using `.expect()`, and audit all call sites (including the RPC layer in `apollo_rpc/src/v0_8/api/api_impl.rs`) to confirm whether externally/L1-influenced data can reach this function with empty calldata.

### Proof of Concept
Not fully constructible without confirming the RPC call path; the panic itself is trivially reproduced in isolation: constructing an `L1HandlerTransaction` with `calldata: Calldata(Arc::new(vec![]))` and calling `.calc_msg_hash()` panics via the `.expect()` in `l1_handler_message_hash` [6](#0-5) , analogous to the empty-calldata unit test already present for `payload_size()` [7](#0-6) .

**Confidence caveat:** Due to index size limits, I could not retrieve the full contents of `crates/apollo_rpc/src/v0_8/api/api_impl.rs` to confirm the exact untrusted-input reachability required by the validation rules. I recommend starting a full Devin session with repository access to trace the RPC call sites and confirm or refute exploitability before treating this as a confirmed finding.

    nonce: Nonce,
    entry_point_selector: &EntryPointSelector,
    calldata: &Calldata,

    encoded.extend(from_address.to_bytes_be());
