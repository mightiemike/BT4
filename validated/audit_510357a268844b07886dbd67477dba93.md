### Title
PBFT sign quorum verification counts distinct signature bytes instead of distinct signer identities, allowing a single signer to forge quorum - ([File: framework/src/main/java/org/tron/core/net/messagehandler/PbftDataSyncHandler.java])

### Summary
`PbftDataSyncHandler.validPbftSign` is java-tron's structural analog to the reported `PriceUpdates::verify` bug: a committee-of-signers scheme (Wormhole guardians ↔ TRON super representatives/PBFT signers) that is supposed to require a quorum (2/3+1) of *distinct signers* before accepting an update (a price feed ↔ a PBFT-committed block/SR-list). Just like the original bug conflated "number of signatures present" with "number of distinct approving parties," this function's quorum check is performed on a `Set<ByteString>` built from the raw signature byte strings, not from the recovered signer addresses.

### Finding Description
The quorum check: [1](#0-0) 
builds `srSignSet` directly from the list of raw signatures (`srSignSet.addAll(srSignList)`) and compares its size against `Param.getInstance().getAgreeNodeCount()` (the 2/3+1 quorum threshold) *before* any signature is cryptographically validated or its signer identity is checked for uniqueness.

Each signature is later validated asynchronously in `ValidPbftSignTask.call()`: [2](#0-1) 
which recovers the signer address from the signature and checks only that the address belongs to the current SR set (`srSet.contains(...)`) — it does not track how many *distinct addresses* have contributed valid signatures. It simply removes the (now-verified) signature from `srSignSet` and returns `true` if the recovered address is a legitimate SR.

Because ECDSA signing over the same message hash produces a fresh byte-level signature each time unless RFC6979 deterministic nonces are strictly enforced, a single compromised or malicious SR/PBFT signer can trivially generate any number of distinct valid signatures (`(r,s)` pairs) for the same `dataHash` using its one private key. Each such signature is:
- distinct at the byte level, so it counts as a unique entry in `srSignSet`, inflating the count check to reach `agreeNodeCount`.
- valid on `ValidPbftSignTask` because it correctly recovers to that single signer's SR address, which is a legitimate member of `srSet`.

The final check `if (srSignSet.size() != 0) return false;` only confirms all submitted signatures were successfully consumed/validated — it never asserts that the underlying *set of distinct recovered addresses* has size ≥ `agreeNodeCount`. This mirrors the root cause identified in the external report: verifying "each item is individually valid" without verifying "a threshold of *unique* approvers is met."

### Impact Explanation
If exploitable, this allows a single malicious or compromised SR (super representative/PBFT signer) to fabricate a PBFT commit quorum (`DataType.BLOCK` or `DataType.SRL` sign data) that is accepted and persisted via `PbftSignDataStore.putBlockSignData` / `putSrSignData`: [3](#0-2) 
This PBFT-committed data is used by full nodes as external finality proof (via `getBlockPbftCommitData` / `getSRLPbftCommitData` exposed through `TronNetDelegate`), meaning fake "committee consensus" state could be persisted and relied upon by nodes/light clients that trust PBFT commit data as evidence of super-majority agreement — a settlement/finality-integrity impact analogous to accepting an under-signed Wormhole VAA as valid.

### Likelihood Explanation
Exploitation requires only a single valid SR/PBFT private key (which is possible for any elected SR or a compromised signer, not necessarily a privileged/trusted "root" role in the security sense audited here — SR compromise or malicious SR behavior is within the standard adversarial model for consensus-layer bugs) and the ability to generate multiple non-deterministic ECDSA signatures over the same hash, which is straightforward using standard ECDSA (random `k`) unless the signing routine is confirmed to strictly use RFC6979 deterministic k for every call path that produces these signatures. I was unable to fully confirm from the available context whether `ECKey.sign` in `crypto/src/main/java/org/tron/common/crypto/ECKey.java` enforces deterministic signatures on every invocation, which is the key precondition for this exploit; this should be verified before treating this as conclusively exploitable.

### Recommendation
Fix `validPbftSign` to track quorum by recovered **signer address**, not by raw signature bytes:
1. Recover the signer address for every signature first.
2. Deduplicate by address (not by signature bytes) and reject duplicate signers.
3. Only after validating each signature belongs to a legitimate, unique SR, check that the number of *unique valid signer addresses* is ≥ `Param.getInstance().getAgreeNodeCount()`.

### Proof of Concept
Conceptual PoC (not runtime-verified due to tool limitations in this pass):
1. Attacker controls one SR private key `k1` that is a legitimate member of `currentSrList`.
2. Attacker computes `dataHash = Sha256Hash.hash(true, raw.toByteArray())` for a `Raw` PBFT message they want falsely quorum-certified.
3. Attacker repeatedly calls `ECKey.sign(dataHash)` (or equivalent) with `k1`, producing `agreeNodeCount` distinct byte-level ECDSA signatures over the same hash (possible whenever the nonce `k` is not strictly deterministic per call).
4. Attacker submits these signatures as `srSignList` in a `PbftCommitMessage`.
5. In `validPbftSign`: `srSignSet.size()` reaches `agreeNodeCount` (step 1 check passes); each `ValidPbftSignTask` recovers `k1`'s address, finds it in `srSet`, and removes the signature from `srSignSet`, so the loop returns `true` for all; final `srSignSet.size() == 0` check passes.
6. `validPbftSign` returns `true` despite only one real signer (not 2/3+1 of the SR committee) having approved — the fabricated PBFT commit data is persisted as if it had super-majority consensus.
