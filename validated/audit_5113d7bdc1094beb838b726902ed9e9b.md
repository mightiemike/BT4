## Finding: `ensure_match_transaction_info` skips verifying state/hot-state/position checkpoint roots during transaction-output verification

### Title
Chunk-executor and replay-verification code accept transaction outputs without checking the authenticated state-checkpoint root — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used across replay/verification code paths (chunk executor state sync, `db-tool replay_on_archive`, `aptos-debugger`, CLI) to confirm that a locally re-computed `TransactionOutput` matches the authenticated `TransactionInfo` carried in the (validator-signed) transaction accumulator. The function checks status, gas, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that bind a locally-computed state root to the authenticated ledger state root.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates:
- transaction status vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- write-set hash vs. `txn_info.state_change_hash()`
- event root hash vs. `txn_info.event_root_hash()`

but the code contains a self-documented TODO acknowledging the gap: [2](#0-1) 

This comment explicitly states that the comparator ignores `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, and that this allows `db-tool`'s `replay_on_archive` to report a "successful replay" even when the authenticated position/state root diverges from local execution.

`TransactionInfoV0`/`V1` carry these checkpoint hashes as the binding between an executed transaction and the Sparse-Merkle/JMT world-state root at that version [3](#0-2)  and [4](#0-3) . These are produced during commit by `assemble_transaction_infos` in the executor, which does independently compute `state_checkpoint_hash`, `hot_state_checkpoint_hashes`, and `position_state_checkpoint_hashes` and place them into the `TransactionInfo` [5](#0-4) . However, that correctness only holds for a node that independently produces its own `TransactionInfo` from execution; the consumer-side check (`ensure_match_transaction_info`) that is supposed to validate a separately-obtained `TransactionOutput` against an authenticated `TransactionInfo` does not re-derive or compare the checkpoint hash fields.

`ensure_match_transaction_info` is called from `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and `aptos-move/cli/src/commands.rs` — i.e., it is the shared verification primitive for chunk-based state sync application and for replay/verification tooling used to validate historical state.

### Impact Explanation
Because the state/hot-state/position checkpoint hash fields are not compared, any code path that trusts `ensure_match_transaction_info` as its correctness gate can accept a `TransactionOutput` whose resulting state root diverges from the authenticated on-chain state-checkpoint root, while still reporting the transaction as correctly matching. In the chunk executor (`execution/executor/src/chunk_executor/mod.rs`), this is the function used to validate transaction outputs before they are folded into locally maintained state during state-sync chunk application; a state-root divergence introduced by any other subtle bug (e.g., in the state-checkpoint computation, hot-state Merkle snapshot, or the newer "position state" root added for trading-native features) would not be caught here, and could be silently persisted into a node's durable state — exactly the "committed state that differs from the correct VM result" and "hard-fork-only divergence during commit/replay" categories called out in scope. For `db-tool replay_on_archive`, this means replay-verification of archived history can report success despite the position/state checkpoint root diverging, undermining its use as an integrity check for archived ledger data.

The severity depends on whether an actual root-computation bug exists elsewhere to be masked by this gap; the code comment confirms the authors are aware this is a real, currently-unmitigated verification hole, not a hypothetical.

### Likelihood Explanation
Likelihood of exploitation depends on an independent divergence bug in state/hot-state/position-state root computation existing and reaching one of these unprivileged verification call sites without other layered checks (e.g., accumulator-level verification against the signed `LedgerInfo` in a different sync mode). This is a real, currently acknowledged gap in local code (confirmed by the in-repo TODO), but I was not able to fully trace, within the available iterations, whether all callers of `ensure_match_transaction_info` (particularly the state-sync chunk-executor path) have an independent, redundant checkpoint-root check elsewhere in the pipeline that would prevent an actual state-root divergence from being persisted. That verification is necessary to determine whether this gap is currently exploitable end-to-end or merely a latent defense-in-depth weakness pending the "trading-native" state roots feature.

### Recommendation
Extend `ensure_match_transaction_info` to also verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally recomputed values whenever those roots are locally derivable at the call site (as flagged by the existing TODO), and audit all callers (`chunk_executor`, `replay_on_archive`, `aptos-debugger`, CLI) to ensure none of them rely solely on this comparator as their sole correctness gate for state-root integrity.

### Proof of Concept
Not applicable as a runnable PoC — the finding is a static code-review result based on the explicit TODO/comment in `ensure_match_transaction_info` at [2](#0-1) , confirming the checkpoint-hash fields are excluded from the verification logic at lines 2139-2204 of the same file.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
