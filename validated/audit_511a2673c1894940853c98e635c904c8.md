## Title
`replay-verify` accepts a divergent state root because `ensure_match_transaction_info` never compares state/hot-state/position checkpoint hashes - (File: `types/src/transaction/mod.rs`)

### Summary
The `TransactionOutput::ensure_match_transaction_info` comparator, which is the sole correctness gate used by Aptos's replay-verification tooling, only checks transaction status, gas used, the write-set hash (`state_change_hash`), and the event root hash against the persisted, ledger-info-authenticated `TransactionInfo`. It never compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. As a result, a locally re-executed transaction whose resulting Sparse-Merkle / hot-state / native-position root diverges from the authenticated on-chain root is reported as a successful, verified replay.

### Finding Description
`ensure_match_transaction_info` is defined in [1](#0-0)  and explicitly documents the gap in its own body: [2](#0-1) 

It checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (hash of `self.write_set()`) vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

but it never touches `txn_info.state_checkpoint_hash()`, the `hot_state_checkpoint_hash` field carried by `TransactionInfoV1`, or `position_state_checkpoint_hash` — all of which are part of the hashed, accumulator-committed `TransactionInfo` struct (`TransactionInfoV0`/`TransactionInfoV1`, [3](#0-2) ).

This function is the only correctness check performed by `db-tool`'s `replay_on_archive` verifier: for every replayed chunk, `execute_and_verify` re-executes transactions from an archived database and calls `ensure_match_transaction_info` on each output, treating a return of `Ok(())` as proof the replay matches the archived (validator-signed) ledger: [4](#0-3) 

Because the checkpoint hash fields are skipped, if the state-checkpoint root, hot-state root, or the newly introduced native-position root computed during local replay differs from what is stored in the archived `TransactionInfo` (e.g., due to a bug in state-checkpoint/hot-state/position root computation reachable via `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, see feature plumbing in [5](#0-4) , or a corrupted/tampered archive), the tool will still report "replay succeeded."

### Impact Explanation
This breaks the proof-and-storage invariant that "replay paths ... must preserve deterministic proof binding" and that authenticated data must be verified against the correct root. `replay_on_archive`/`replay-verify` is the mechanism operators and Aptos Labs use to confirm that historical execution results (and, going forward, the native trading/position state root) match the authenticated chain state before trusting a snapshot/backup or before rolling out state-root-affecting changes (e.g., trading-native feature). A silent pass on state-root divergence means a corrupted or incorrectly computed durable state (state checkpoint, hot state, or position state) can go undetected by the verification tool meant to catch exactly this class of bug — i.e., a hard-fork-class state divergence during replay/verification is masked rather than caught, directly matching the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category.

### Likelihood Explanation
The gap is deterministic and always present (not input-dependent or requiring an attacker) — the comparator unconditionally skips these fields. It manifests as soon as any bug or inconsistency in state-checkpoint/hot-state/position root computation exists at a checkpoint transaction, or when replaying against a corrupted archive; the developers' own TODO explicitly flags this as a blocking prerequisite ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), confirming the root cause is real and currently unmitigated in code, only guarded by the fact that the associated feature is not yet turned on.

### Recommendation
Extend `ensure_match_transaction_info` to compute and compare `state_checkpoint_hash` (when the txn is a checkpoint), `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields of `txn_info`, failing loudly on any mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or any feature relying on these roots) is enabled and before this comparator is relied upon as a correctness gate for replay/backup verification.

### Proof of Concept
1. Take an archived database (or a locally produced one) where the persisted `TransactionInfo` at a checkpoint version has a `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` that does not match what fresh VM execution against the same inputs would produce (e.g., due to a state-checkpoint computation bug, or by directly mutating the stored `TransactionInfo` checkpoint hash field, which does not affect `write_set`/`events`/`gas_used`/`status`).
2. Run `db-tool replay-on-archive` against this database for the relevant version range, using `execute_and_verify` in [6](#0-5) .
3. Because `ensure_match_transaction_info` never inspects the checkpoint-hash fields, `Ok(())` is returned and the tool reports the chunk as verified/passed, despite the state root being different from what local execution computed — silently confirming a divergent ledger state as valid.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
