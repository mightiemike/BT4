## Analysis Result [1](#0-0) 

### Title
Order-matching loop aborts the entire taker transaction on exceeding MAX_MATCH_NUM, allowing cheap DOS of `MarketSellAssetContract` trades - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.execute()` performs the market-sell "settlement" for a taker order by iterating over multiple maker orders and updating both taker and maker virtual balances in a single all-or-nothing transaction, mirroring the reported Vault design flaw where any one of several inner settlements failing reverts the whole outer transaction.

### Finding Description
`execute()` deducts the fee and sell-token balance from the taker, creates the order, then calls `matchOrder()` which loops through up to `MAX_MATCH_NUM` (20) maker orders, calling `matchSingleOrder()` for each to update both taker's and maker's balances via `addTrxOrToken`/`addAssetAmountV2`/`setBalance`. [2](#0-1) 

Inside the matching loop, if the number of matched maker orders exceeds `MAX_MATCH_NUM`, a `ContractValidateException` is thrown directly from the middle of the loop: [3](#0-2) 

This exception propagates up through `execute()`'s outer catch block, which sets the transaction result to `FAILED` and rethrows as `ContractExeException`: [4](#0-3) 

Because this happens inside the same DB session/transaction as all the other balance mutations already performed for the taker (fee deduction, sell-token deduction, order creation) and for the makers matched so far in the loop, the failure causes the whole transaction to be rejected/rolled back — exactly the pattern described in the report: multiple "settlement" operations bundled into one all-or-nothing transaction, where one failure (here, simply matching too many small orders) reverts everything.

### Impact Explanation
An unprivileged attacker can pre-populate the order book for a given token pair with more than `MAX_MATCH_NUM` (20) small maker sell orders at the best price. Any legitimate taker whose sell order would need to match against more than 20 orders to fill (even partially, since the check fires as soon as `matchOrderCount > MAX_MATCH_NUM` inside the loop, not only when trying to exceed the limit on the last remaining quantity) will have their entire transaction fail with "Too many matches." This denies market participants the ability to execute otherwise valid trades against existing liquidity, and can be triggered cheaply and repeatedly by anyone willing to place small maker orders, since order creation itself has generous limits (`MAX_ACTIVE_ORDER_NUM` = 100 per account) and no cost proportional to griefing potential.

### Likelihood Explanation
The precondition (order book fragmented into >20 small orders at a matching price) is trivially and cheaply achievable by any account, and the resulting exception path is deterministic and always reachable whenever a taker's order would otherwise match with more than 20 counter-orders. No privileged role or special contract state is required.

### Recommendation
Instead of throwing a validation exception that aborts the entire transaction when `MAX_MATCH_NUM` is exceeded, the actuator should stop matching gracefully after `MAX_MATCH_NUM` orders are filled, commit the partial fills already applied, and return the unmatched remainder of the taker's order to the order book (or to the taker), consistent with how the function already handles the "remaining quantity" case via `saveRemainOrder`. More generally, per-counterparty settlement failures should not be allowed to void already-applied, valid partial settlements within the same transaction.

### Proof of Concept
1. Attacker creates 21+ small `MarketSellAssetContract` maker orders selling token A for token B at the best price (well within `MAX_ACTIVE_ORDER_NUM`).
2. Victim submits a `MarketSellAssetContract` selling token B for token A with a quantity that would require matching more than 20 of the attacker's orders to fill.
3. `matchOrder()` iterates the maker orders; once `matchOrderCount` exceeds `MAX_MATCH_NUM = 20`, a `ContractValidateException("Too many matches...")` is thrown from inside the loop. [3](#0-2) 
4. `execute()` catches this, marks the transaction `FAILED`, and throws `ContractExeException`, reverting the victim's entire transaction (fee deduction, order creation, and all balance updates already applied for previously matched makers in the loop). [4](#0-3)

  private void matchOrder(MarketOrderCapsule takerCapsule, MarketPrice takerPrice,
      TransactionResultCapsule ret, AccountCapsule takerAccountCapsule)
      throws ItemNotFoundException, ContractValidateException {

    byte[] makerSellTokenID = buyTokenID;
    byte[] makerBuyTokenID = sellTokenID;
    byte[] makerPair = MarketUtils.createPairKey(makerSellTokenID, makerBuyTokenID);

    // makerPair not exists
    long makerPriceNumber = pairToPriceStore.getPriceNum(makerPair);
    if (makerPriceNumber == 0) {
      return;
    }
    long remainCount = makerPriceNumber;

    // get maker price list
    List<byte[]> priceKeysList = pairPriceToOrderStore
        .getPriceKeysList(MarketUtils.getPairPriceHeadKey(makerSellTokenID, makerBuyTokenID),
            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);
      if (makerPrice == null) {
        return;
      }

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists
      MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);

      // match different orders which have the same price
      while (takerCapsule.getSellTokenQuantityRemain() != 0
          && !orderIdListCapsule.isOrderEmpty()) {
        byte[] orderId = orderIdListCapsule.getHead();
        MarketOrderCapsule makerOrderCapsule = orderStore.get(orderId);

        matchSingleOrder(takerCapsule, makerOrderCapsule, ret, takerAccountCapsule);

        // remove order
        if (makerOrderCapsule.getSellTokenQuantityRemain() == 0) {
          // remove from market order list
          orderIdListCapsule.removeOrder(makerOrderCapsule, orderStore,
              pairPriceKey, pairPriceToOrderStore);
        }

        matchOrderCount++;
        if (matchOrderCount > MAX_MATCH_NUM) {
          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
        }
      }

      // the orders of makerPrice have been all consumed
      if (orderIdListCapsule.isOrderEmpty()) {
        pairPriceToOrderStore.delete(pairPriceKey);

        // need to delete marketPair if no more price(priceKeysList is empty after deleting)
        priceKeysList.remove(0);

        // update priceInfo's count
        remainCount = remainCount - 1;
        // if really empty, need to delete token pair from pairToPriceStore
        if (remainCount == 0) {
          pairToPriceStore.delete(makerPair);
          break;
        } else {
          pairToPriceStore.setPriceNum(makerPair, remainCount);
        }
      }
    } // end while
  }
