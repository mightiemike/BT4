### Title
Attacker-supplied `compiled_class_hash` on a Declare transaction is not validated against the canonical (Blake2/V2) CASM hash for all transaction versions, allowing a class-hash "kind" mismatch to be committed to state - ([File: crates/blockifier/src/transaction/transactions.rs])

### Summary
`DeclareTransaction::run_execute` only recomputes and cross-checks the sender-supplied `compiled_class_hash` against the canonical Blake2 (`HashVersion::V2`) hash of the actual CASM when the transaction version is `>= THREE` **and** the `block_casm_hash_v1_declares` versioned constant is enabled. For `DeclareTransactionV2` (and for V3 when the flag is disabled), the attacker-supplied `compiled_class_hash` is written to state as-is, without verifying it is the canonical hash of the CASM bytecode that is actually declared and later executed.

### Finding Description
`ContractClass::compiled_class_hash()` always defines the canonical/committed hash of a class as the `HashVersion::V2` (Blake2) hash of its CASM: [1](#0-0) . There is also an older `HashVersion::V1` (Poseidon) hash algorithm still supported by `CasmContractClass::hash()`: [2](#0-1) .

The only place that forces a `compiled_class_hash` supplied on a declare transaction to equal the canonical V2 hash is `check_compile_class_hash_v2_declaration`: [3](#0-2) . But this check is invoked from the blockifier only under a conjunction of conditions - transaction version `>= THREE` **and** the `block_casm_hash_v1_declares` versioned constant: [4](#0-3) 

For `DeclareTransactionV2` this guard is never entered, and even for V3 it is skipped whenever `block_casm_hash_v1_declares` is off for the active protocol version. In both bypass cases, `try_declare` is called with the transaction's raw, attacker-controlled `compiled_class_hash` (`Some(*compiled_class_hash)`), which is what gets written into the state's `compiled_class_hashes` map - not a recomputed value: [5](#0-4) .

This is directly analogous to the reported bug class: the Reservoir oracle message committed a price under an `id` (message identifier) that failed to encode which "kind" of price (floor vs. bid-ask-midpoint) it authenticated, letting one kind of signed data be substituted where another was expected. Here, the `compiled_class_hash` field on a declare transaction is supposed to be a single canonical commitment to a specific class's CASM, but the hashing "kind" (V1 Poseidon vs. V2 Blake2) used to produce/verify that commitment is not enforced consistently across all transaction versions/flag states, so a value computed under the "wrong" hash kind can be accepted and permanently committed as the class's `compiled_class_hash` in state.

### Impact Explanation
Because `compiled_class_hash` is supposed to be the sole state-committed link between a `class_hash` and its executable CASM, allowing an unverified/mismatched value to be written to `compiled_class_hashes` breaks that invariant. Since the enforcement depends on a versioned-constants flag (`block_casm_hash_v1_declares`) and on the transaction version, this is also a source of honest-node divergence: two conforming sequencer builds or protocol-version windows that disagree on this flag (or process a V2 vs V3 declare) will compute different state maps / state roots for the same input transaction, which can produce a wrong committed root / block hash and break OS re-execution equivalence - both are explicitly in-scope impact categories.

### Likelihood Explanation
Any unprivileged account can submit a `DeclareTransactionV2` (still a supported transaction type in `starknet_api`/`blockifier`, per `DeclareTransaction::V2` handling throughout `transaction_hash.rs` and `transactions.rs`) with a `compiled_class_hash` value it fully controls, since no CASM-vs-hash consistency re-check gate is applied for that version. Reaching this path requires nothing beyond crafting and signing a normal declare transaction, so it is directly reachable from a single submitted transaction by any account, matching the "single submitted transaction" reachability bar required by the rules.

### Recommendation
Enforce the `compiled_class_hash` == canonical `HashVersion::V2` CASM hash check unconditionally for every declare transaction version that carries a `compiled_class_hash` (V2 and V3), independent of the `block_casm_hash_v1_declares` versioned constant, or explicitly document/version-gate the V1 hash as a first-class, permanently supported commitment scheme rather than a partially-enforced legacy fallback. At minimum, `try_declare` should never persist a transaction-supplied `compiled_class_hash` into state without first validating it against the CASM that is bound to the declared `class_hash`.

### Proof of Concept
Note: I was not able to fully trace every call path into `try_declare`/`run_execute` (e.g., how `apollo_transaction_converter`'s RPC-layer check at `transaction_converter.rs:353` interacts with p2p-propagated or re-executed transactions, and the default/historical value of `block_casm_hash_v1_declares` across protocol versions) within the available tool budget, so I cannot claim this is exploitable end-to-end against a specific already-deployed protocol version without further verification. The concrete code-level gap is nonetheless demonstrated by the existing test matrix, which explicitly exercises both hash kinds and shows the mismatch is only caught for V3 declares: [6](#0-5) 
A minimal PoC would be: submit a `DeclareTransactionV2` (or a V3 declare while `block_casm_hash_v1_declares` is disabled for the active version) whose `compiled_class_hash` is computed with `CasmContractClass::hash(&HashVersion::V1)` instead of `HashVersion::V2`, and confirm via `state.get_compiled_class_hash(class_hash)` that the mismatched (Poseidon) value is committed to state rather than being rejected, as demonstrated for the "wrong" case that *is* caught only in the V3+flag-enabled branch: [7](#0-6)

    /// Verifies that the compiled class hash field in the declare tx,
    /// is compiled_class_hash_v2 of the compiled contract.
    pub fn check_compile_class_hash_v2_declaration(&self) -> Result<(), StarknetApiError> {
        let compiled_class = &self.class_info.contract_class;
        let compiled_class_hash_v2 = match &compiled_class {
            ContractClass::V0(_) => return Ok(()),
            ContractClass::V1((casm, _)) => casm.hash(&HashVersion::V2),
        };
        let compiled_class_hash = self.compiled_class_hash();
        if compiled_class_hash_v2 != compiled_class_hash {
            let err_var = CasmHashMismatch {
                hash: self.class_hash(),
                actual: compiled_class_hash,
                expected: compiled_class_hash_v2,
            };
            return Err(StarknetApiError::DeclareTransactionCasmHashMissMatch(Box::new(err_var)));
        }
        Ok(())
    }
