## Title
Webhook HMAC verification does not bind the `X-Shopify-Shop-Domain` header to the signed payload, enabling cross-tenant webhook replay - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
The library's webhook authentication computes the HMAC solely over the raw request body using the app-level `apiSecretKey`, and never binds the `domain` (shop) header into that signature. An unprivileged merchant who has the app installed on their own store can capture a genuinely Shopify-signed `(rawBody, hmac)` pair delivered to their own webhook endpoint and replay it to the app with the `X-Shopify-Shop-Domain` header changed to any other shop that has the app installed. `webhooks.validate` accepts the request as valid and reports the attacker-chosen domain, which is then used to load that victim shop's offline session/access token and execute the webhook handler logic (including the attacker-controlled payload) with the victim's privileges.

### Finding Description
`validateHmacFromRequestFactory` verifies a webhook exclusively like this: [1](#0-0) 

It reads only the HMAC header and the raw body, and calls `validateHmacString`, which computes `createSHA256HMAC(config.apiSecretKey, rawBody, ...)`: [2](#0-1) 

No header — including `X-Shopify-Shop-Domain` — is ever included in the signed material. `validateFactory` then calls `checkWebhookHeaders`, which pulls the `domain` straight out of the (unauthenticated) header and returns it as trusted data once the (header-independent) HMAC check passes: [3](#0-2) 

Downstream, both the Remix and React Router webhook authenticators take this attacker-influenceable `check.domain` and use it directly to load the shop's offline session (with its real Admin access token) and construct an authenticated `admin` client for it: [4](#0-3) 

The `apiSecretKey` used to compute/verify the HMAC is the single app-level client secret, shared across every shop that has the app installed — it is not shop-specific. Consequently, once a merchant's own store triggers a real webhook (which is authentically signed by Shopify using this same shared secret), that merchant possesses a `(rawBody, hmac)` pair that remains valid regardless of which `X-Shopify-Shop-Domain` header accompanies it, because the header is not part of the signed data.

### Impact Explanation
This is a confused-deputy / cross-tenant access vulnerability: a single unprivileged merchant with the app installed can forge the shop-attribution of a webhook request and cause the app to execute its webhook-handling business logic — with the payload/body they authored — against an arbitrary other shop's Admin API session and access token. Depending on the app's webhook handlers (e.g., updating products, orders, discounts, fulfillments), this can lead to unauthorized modification of another merchant's store data using that merchant's own access token, entirely analogous to the original report where an unauthenticated parameter (`receiver` in `executeFlashloan`) was used to apply a privileged, fee-bearing operation to an arbitrary third party without their authorization.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on one's own store (available to any merchant), (2) triggering any webhook event on that store to obtain a legitimately-signed `(rawBody, hmac)` pair, and (3) POSTing that pair to the app's public webhook endpoint with a modified `X-Shopify-Shop-Domain` header pointing at a target shop known to have the app installed. No secret material needs to be leaked and no MITM is required — the webhook endpoint is a public HTTP endpoint by design.

### Recommendation
Bind the shop domain (and other security-relevant headers such as topic/webhook id) into the HMAC-verified material, or otherwise cryptographically tie the `X-Shopify-Shop-Domain` header to the signed payload before trusting it to select which shop's session/access token to use. At minimum, apps/libraries should not implicitly trust the header-derived `domain` for authorization purposes without an additional binding check.

### Proof of Concept
1. Merchant M installs the app on `m.myshopify.com` and triggers a webhook event (e.g., updates a product), causing Shopify to POST a legitimately HMAC-signed webhook `(rawBody, hmac)` to the app's callback URL.
2. M captures this exact `rawBody` and `X-Shopify-Hmac-Sha256` header value.
3. M sends their own POST request to the same app webhook endpoint, reusing the identical `rawBody` and `hmac` header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a different shop known to have the app installed).
4. `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts`) validates the HMAC successfully because it only checks `rawBody` against the shared `apiSecretKey`, ignoring the domain header.
5. `checkWebhookHeaders` returns `domain: 'victim.myshopify.com'`, and `authenticateWebhookFactory` loads `victim.myshopify.com`'s offline session/access token and hands an authenticated `admin` client plus M's crafted payload to the app's webhook handler, which then executes against the victim shop.
