### Title
Unbounded Memory Allocation via Attacker-Controlled Array Length in Deprecated (Cairo 0) Syscall Argument Parsing - ([File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs])

### Summary
`read_felt_array` in the deprecated (Cairo 0) syscall argument parser reads an array-length felt directly from Cairo VM memory that is fully under the control of the executing contract's own bytecode/hints (e.g., `EmitEvent`, `SendMessageToL1` payloads), converts it to a `usize`, and passes it straight to `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)` without first validating that `size` is bounded by the amount of data actually available. This mirrors the CVE's root cause: a single operation converts a user-controlled length/value into an allocation whose size is disproportionate to any resource accounting performed beforehand.

### Finding Description
`read_felt_array` reads a `Felt` length (`array_size`), converts it with `usize::try_from(array_size.to_biguint())`, and immediately calls `felt_range_from_ptr(vm, array_data_start_ptr, size)`: [1](#0-0) 

`felt_range_from_ptr` forwards that `size` directly into `vm.get_integer_range(ptr, size)`: [2](#0-1) 

This function is used to parse the `EmitEvent` and `SendMessageToL1` request payloads for Cairo 0 (deprecated) contracts, where the `keys_len`/`data_len`/`payload_size` felt is emitted by the executing contract's own code path (fully attacker-controlled, since any contract deployer can write Cairo 0 bytecode that pushes an arbitrary felt there before invoking the syscall): [3](#0-2) [4](#0-3) 

Notably, the codebase already fixed exactly this class of bug in a different location (`apollo_cairo_utils`), where a comment explicitly documents the risk: "a declared count larger than the number of remaining Felts cannot be valid. Validate before allocating to prevent a contract-controlled length felt from triggering an unbounded `Vec::with_capacity`": [5](#0-4) 

`read_felt_array`/`felt_range_from_ptr` in the deprecated syscall path does not have the equivalent guard — it relies solely on `vm.get_integer_range` failing if the memory segment doesn't actually contain that many values, but the size passed to it (and the resulting allocation attempt, e.g., `Vec::with_capacity`/`values.into_iter().map(...).collect()` inside the underlying VM crate) is not bounded up front by remaining program data before the allocation is attempted.

### Impact Explanation
If `get_integer_range` (or its underlying container) allocates proportional to `size` before verifying the requested range actually exists in memory, a malicious Cairo 0 contract can supply an astronomically large `keys_len`/`data_len`/`payload_size` felt (up to `usize::MAX`, since `usize::try_from` only rejects values exceeding `usize::MAX`, not values that are merely large-but-valid `usize`s) to force a multi-gigabyte or larger allocation attempt during `EmitEvent`/`SendMessageToL1` execution. Depending on how the allocation fails (OOM abort vs. graceful error return), this can crash the executing sequencer/validator process (`mongod`-style OOM kill analog), causing an halt in block building or an inability to process further transactions — a network-availability impact consistent with "network unable to confirm new transactions."

### Likelihood Explanation
Reaching this code path requires only deploying and invoking a Cairo 0 (deprecated syscalls are still supported for backward compatibility) contract that calls `emit_event_syscall` or `send_message_to_l1_syscall` with a manipulated length field in its Cairo assembly/hints, then submitting a normal transaction that invokes it — no special privileges beyond ordinary contract deployment and invocation are needed. This makes it directly reachable by any unprivileged transaction sender/contract deployer.

### Recommendation
Add the same defensive check used in `apollo_cairo_utils` (`crates/apollo_cairo_utils/src/lib.rs`) to `read_felt_array` in `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`: before calling `felt_range_from_ptr`, verify that `array_size` does not exceed the remaining size of the memory segment (or a hard protocol-defined maximum, e.g. `SIERRA_ARRAY_LEN_BOUND`), returning an error instead of attempting the allocation/range read. Additionally, audit `felt_range_from_ptr`/`vm.get_integer_range` usages throughout `blockifier` and the `starknet_os` hint processors for the same pattern (any place converting an untrusted felt directly into an allocation size or `Vec` length without a prior bound check).

### Proof of Concept
Not independently executable from static analysis alone; would require constructing a Cairo 0 contract that:
1. Writes a syscall request buffer for `EmitEvent` (or `SendMessageToL1`) with `data_len` (or `payload_size`) set to a very large felt value (e.g., `2^40`, well within `usize` range on 64-bit but far exceeding actually-populated calldata),
2. Invokes the corresponding deprecated syscall,
3. Observes whether `read_felt_array` → `felt_range_from_ptr` → `vm.get_integer_range` attempts to allocate/materialize a vector of that size before validating the segment actually contains that many values, potentially aborting the process via allocation failure.

Verification of the actual allocation behavior of `cairo_vm::VirtualMachine::get_integer_range` (whether it pre-allocates based on `size` or incrementally reads and fails fast) could not be completed because that function is defined in the external `cairo-vm` crate, which is outside the indexed codebase — this is a limitation of the current analysis and would need to be confirmed by inspecting the `cairo-vm` dependency source directly (a Devin session with full filesystem/dependency access could resolve this).

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
}

pub fn felt_range_from_ptr(
    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;
    // Extract values as `Felt`.
    let values = values.into_iter().map(|felt| *felt).collect();
    Ok(values)
}
