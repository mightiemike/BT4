### Title
Per-block granularity of the `MAX_RESULT` check in `matchBlockOneByOne()` allows a single block to materialize far more `LogFilterElement`s than the configured cap before throwing - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogMatch.java])

### Finding Description
`matchBlockOneByOne()` iterates over candidate block numbers and, for each block, calls the static `matchBlock()` which scans every `TransactionInfo`/`Log` in that block and unconditionally appends every match into an in-memory `matchedLog` list with no size bound at all [1](#0-0) . Only after the whole block's `matchedLog` list is fully built does the caller check `logFilterElementList.size() + matchedLog.size() > LogBlockQuery.MAX_RESULT` and throw `JsonRpcTooManyResultException` [2](#0-1) . Consequently, if a single block contains more matching logs than `MAX_RESULT` (10000) [3](#0-2) , the entire over-limit list for that one block is fully constructed in memory before the exception is raised — the check never prevents the single-block materialization, only the accumulation across blocks.

However, the number of logs an attacker can emit within one block is not attacker-controlled without bound: it is capped by the block's total energy budget, since every `LOG0`-`LOG4` opcode consumes energy (base log cost plus per-topic and per-byte-of-data costs) that must be paid for in TRX-backed energy/fee by the attacker's transaction(s) [4](#0-3) . So while the per-block check is architecturally a gap (it should be enforced incrementally, e.g. inside `matchBlock` or per-log), the "unbounded" framing in the question is not accurate — the maximum overshoot in a single block is bounded by (block energy limit ÷ minimum LOG opcode cost), a finite, network-parameterized quantity, and generating it costs the attacker real, non-trivial fees proportional to the burden created.

### Impact Explanation
In the worst case a single block could yield a `matchedLog` list somewhat larger than `MAX_RESULT` (bounded by the chain's per-block energy limit divided by the minimal LOG cost) before the exception fires, causing a memory spike on the JSON-RPC node larger than the documented 10000-result cap. This is a real implementation gap in enforcing the cap at finer granularity, but the overshoot is bounded, not unbounded, and is paid for via ordinary transaction fees rather than being "free" underpriced work.

### Likelihood Explanation
To exploit this, an attacker needs to deploy a contract that emits as many `LOG0`-`LOG4` events as the block energy limit allows and get it included in a block, then query `eth_getLogs` covering that block. This is technically reachable by any unprivileged user with enough TRX for energy/fees, but the cost of producing the overshoot scales with the overshoot itself (attacker pays for every log opcode), which limits the value of the attack as a low-cost DoS vector.

### Recommendation
Move the `MAX_RESULT` size check inside `matchBlock()` (or make it incremental per log) so the exception is thrown as soon as the running total exceeds `MAX_RESULT`, rather than after fully materializing an entire block's matches. This bounds the worst-case per-block memory allocation to `MAX_RESULT` regardless of how many logs a single block actually contains.

### Proof of Concept
Extend `LogMatchOverLimitTest` with a single-block case where one `TransactionInfo` contains `MAX_RESULT * 3` (or a similarly large) log count, and assert that `matchBlockOneByOne()` still throws `JsonRpcTooManyResultException`, then inspect (e.g., via a counting/interceptor variant of `matchBlock`) that the internal list built for that single block does not need to grow past `MAX_RESULT` entries — confirming the current implementation fully constructs the oversized list before checking, versus a fixed implementation that stops early.

  public static List<LogFilterElement> matchBlock(LogFilter logFilter, long blockNum,
      String blockHash, List<TransactionInfo> transactionInfoList, boolean removed) {

    int txCount = transactionInfoList.size();
    List<LogFilterElement> matchedLog = new ArrayList<>();
    int logIndexInBlock = 0;

    for (int i = 0; i < txCount; i++) {
      TransactionInfo transactionInfo = transactionInfoList.get(i);
      int logCount = transactionInfo.getLogCount();

      for (int j = 0; j < logCount; j++) {
        Log log = transactionInfo.getLog(j);

        if (logFilter.matchesExactly(log)) {
          List<DataWord> topicList = new ArrayList<>();
          for (ByteString topic : log.getTopicsList()) {
            topicList.add(new DataWord(topic.toByteArray()));
          }

          LogFilterElement logFilterElement = new LogFilterElement(blockHash,
              blockNum,
              ByteArray.toHexString(transactionInfo.getId().toByteArray()),
              i,
              ByteArray.toHexString(log.getAddress().toByteArray()),
              topicList,
              ByteArray.toHexString(log.getData().toByteArray()),
              logIndexInBlock,
              removed,
              transactionInfo.getBlockTimeStamp()
          );
          matchedLog.add(logFilterElement);
        }

        logIndexInBlock += 1;
      }
    }

    return matchedLog;
  }
