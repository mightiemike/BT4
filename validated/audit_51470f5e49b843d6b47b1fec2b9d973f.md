### Title
Wire-length vs on-trie-length divergence for ML-DSA-65 public keys causes gas fee underpricing for `TransferToGasKey`/`WithdrawFromGasKey` actions - (File: runtime/runtime/src/config.rs)

### Summary
The reported Chainlink issue is a "byte-scale assumption" bug: code that assumes all price feeds share one decimal scale, but the assumption silently breaks for some inputs, producing a wrong calculated value. `nearcore` has a structurally identical assumption for `PublicKey` byte-length pricing: two different accessors, `PublicKey::len()` (wire/borsh length) and `PublicKey::trie_id_len()` (on-trie length), which are equal for `ED25519`/`SECP256K1` but diverge drastically for `MLDSA65` (1953 bytes vs 33 bytes) [1](#0-0) [2](#0-1) .

### Finding Description
`gas_key_send_pk_len` in `runtime/runtime/src/config.rs` selects which length function to use for pricing the *send* fee of a `TransferToGasKey`/`WithdrawFromGasKey` action's embedded `public_key` field (which is transmitted as a full wire-format pubkey, i.e., 1953 bytes for ML-DSA-65):

```rust
fn gas_key_send_pk_len(config: &RuntimeConfig, public_key: &PublicKey) -> usize {
    if config.wasm_config.fix_ml_dsa_cost_charging {
        public_key.len()
    } else {
        public_key.trie_id_len()
    }
}
``` [3](#0-2) 

This value feeds directly into `total_send_fees` for `TransferToGasKey`, via `gas_key_transfer_send_fee(fees, sender_is_receiver, gas_key_send_pk_len(config, &action.public_key))` [4](#0-3) . Before the `fix_ml_dsa_cost_charging` protocol feature is enabled, the send fee for a `TransferToGasKey`/`WithdrawFromGasKey` action carrying an ML-DSA-65 key is billed using `trie_id_len()` (33 bytes) even though the actual bytes placed on the wire/in the receipt are `len()` (1953 bytes) — a ~59x undercharge, exactly analogous to the oracle assuming an 8-decimal scale when the actual feed uses a different one.

### Impact Explanation
If this branch is active (i.e., the runtime config has not yet flipped `fix_ml_dsa_cost_charging`), any transaction signer can submit `TransferToGasKey`/`WithdrawFromGasKey` actions carrying ML-DSA-65 public keys and pay gas fees computed for only 33 bytes of wire data while actually consuming ~1953 bytes of receipt payload. This under-prices real resource consumption (bandwidth/witness size, per-byte send fee) exactly like the Chainlink bug under/over-prices assets — it is a fee/gas metering bypass reachable purely by an unprivileged transaction signer, without any special permissions, and could be used to cheaply inflate the size of outgoing receipts/witnesses relative to the gas paid for them.

### Likelihood Explanation
The vulnerable branch only manifests when `config.wasm_config.fix_ml_dsa_cost_charging` is `false`; the code comments explicitly document this as "preserve the (incorrect) existing behavior if the fix is not enabled" and describe it as an interim/consensus-compatibility path rather than the corrected one [3](#0-2) . Whether this parameter is currently `true` or `false` on the target network at the reviewed protocol version could not be conclusively confirmed within the available tool budget — the `FixMlDsaCostCharging` protocol-feature gate in `core/primitives-core/src/version.rs` and its exact activation protocol version were located but not fully read before the iteration budget ran out. If the feature is not yet active for the deployed protocol version, this underpricing is live and reachable by any signer able to submit an ML-DSA-65-keyed `TransferToGasKey`/`WithdrawFromGasKey` transaction.

### Recommendation
- Confirm the protocol version at which `FixMlDsaCostCharging` activates and verify it is enabled for all currently supported/mainnet protocol versions before ML-DSA-65 keys can be used in `TransferToGasKey`/`WithdrawFromGasKey` actions.
- Alternatively, remove the legacy branch entirely for any protocol version where ML-DSA-65 send actions are permitted, always pricing send fees by the true wire length (`public_key.len()`), eliminating the possibility of a length-assumption mismatch analogous to the oracle-decimals bug.
- Add an explicit invariant/test asserting `gas_key_send_pk_len` never returns a length smaller than the actual serialized bytes placed in the receipt for any enabled protocol version.

### Proof of Concept
1. Deploy/observe a network state where `fix_ml_dsa_cost_charging` is `false` for the active protocol version.
2. As a normal account holder, add an ML-DSA-65 access key and submit a `TransferToGasKey` (or `WithdrawFromGasKey`) action referencing that key's full 1953-byte `PublicKey`.
3. Compute the expected send fee using `gas_key_byte` × wire length (1953 bytes) versus the fee actually charged, which uses `trie_id_len()` (33 bytes) per `gas_key_send_pk_len` [3](#0-2) .
4. Observe the transaction is accepted while paying gas fees for only ~33 bytes of wire data instead of the ~1953 bytes actually transmitted, confirming the underpricing predicted by the code's own comments — mirroring `test_gas_key_transfer_send_fee_uses_wire_length`, which explicitly documents that send fee "must scale with wire length ... not trie_id_len" [5](#0-4) .

/// The gas-key SEND fee prices bytes put on the wire, so it must scale with
/// `public_key.len()` (1953 for ML-DSA-65), not the on-trie `trie_id_len()`
/// (33). A "use `trie_id_len` everywhere" fix would leave this wrong; only the
/// split (send = `len`, exec = `trie_id_len`) is correct, which is what
/// `config.rs` now does.
#[test]
fn test_gas_key_transfer_send_fee_uses_wire_length() {
    let config = RuntimeConfig::test();
    let receiver = alice_account();
    let ed25519_key = SecretKey::from_seed(KeyType::ED25519, "gas-key-seed").public_key();
    let ml_dsa_65_key = SecretKey::from_seed(KeyType::MLDSA65, "gas-key-seed").public_key();

    let send_fee = |public_key: &PublicKey| -> u64 {
        let actions = [Action::TransferToGasKey(Box::new(TransferToGasKeyAction {
            public_key: public_key.clone(),
            deposit: Balance::ZERO,
        }))];
        total_send_fees(&config, false, &actions, &receiver).unwrap().gas.as_gas()
    };
    let wire_len = |public_key: &PublicKey| public_key.len() as u64;

    let gas_key_byte_send = config.fees.fee(ActionCosts::gas_key_byte).send_fee(false).gas.as_gas();
    // Send fee scales with wire length, so the ML-DSA-65 vs ed25519 gap is the
    // difference in their `len()`; the (equal) base fee cancels.
    let expected_delta = gas_key_byte_send * (wire_len(&ml_dsa_65_key) - wire_len(&ed25519_key));
    let measured_delta = send_fee(&ml_dsa_65_key) - send_fee(&ed25519_key);
    assert_eq!(
        measured_delta, expected_delta,
        "gas-key send fee must scale with wire length (len), not trie_id_len",
    );
}
