## Title
Super Representative can arbitrarily change delegation "brokerage" fee for voters/delegators with no event and no advance-notice timelock - (`actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
The `UpdateBrokerageContract` lets a Super Representative (SR/witness) unilaterally set the percentage of block/vote rewards it keeps for itself (the "brokerage" — effectively a fee charged to its voters/delegators) to anywhere from 0% to 100%, with no on-chain event/log and no advance-notice delay before the new rate can be applied to reward computation. This mirrors the Tracer finding: a market/fee-setting party can silently change a fee that immediately affects unprivileged counterparties (voters), who have no reliable off-chain signal to react before rewards are split under the new rate.

### Finding Description
`UpdateBrokerageActuator.execute()` unpacks the caller-supplied `brokerage` value and stores it directly via `delegationStore.setBrokerage(ownerAddress, brokerage)`: [1](#0-0) 

Validation only bounds the value to `[0, 100]` and checks that the address is a registered witness with an existing account — there is no timelock, no minimum notice period, and no cap tied to a previously-announced value: [2](#0-1) 

The stored value directly determines the split of every future reward payment for that SR's voters, via `MortgageService.payReward()`: [3](#0-2) 

The write path (`DelegationStore.setBrokerage`/`getBrokerage`) stores the value under a `cycle = -1` bucket by default: [4](#0-3) 

No `Event`/log construct exists for this contract type — unlike Solidity's `emit`, java-tron actuators do not emit any indexed notification when brokerage changes; the only way to observe the change is to poll `getBrokerage`/query the raw transaction stream (confirmed via `GetBrokerageServlet`), which most delegator wallets/front-ends do not do proactively.

### Impact Explanation
Delegators (unprivileged token holders who vote for an SR) receive a share of block rewards computed as `value - brokerageAmount`, where `brokerageAmount = brokerage% * value`. A witness can raise brokerage from, e.g., 20% to 100% at any time, and this can take effect for reward cycles processed after the update with no advance notice and no event for monitoring tools to detect and alert delegators. Voters who already delegated (vote allocation itself is a slower/social process, not something that reacts within a block) end up with drastically reduced or zero rewards for that cycle, without being able to withdraw their vote in time. This is a direct economic/accounting-fairness impact on unprivileged users analogous to the referenced Tracer fee-griefing finding.

### Likelihood Explanation
Any account that is already a registered witness (achievable permissionlessly by anyone who can win enough votes, i.e. not a protocol-trusted/owner-only role) can call `UpdateBrokerageContract` at will, at zero cost (`calcFee()` returns 0), as often as desired: [5](#0-4) 
Likelihood is moderate: it requires the caller to already be an elected/active SR, but no further permission or timelock is required to abuse it against their own voters.

### Recommendation
- Emit an on-chain event/log (or a dedicated queryable "pending brokerage" record) whenever `UpdateBrokerageContract` is executed, including old and new values.
- Introduce a timelock/effective-cycle delay (e.g., the change only takes effect N cycles/maintenance periods after being submitted) so delegators have time to react (unvote) before the new rate is applied to reward splitting.
- Consider limiting the maximum single-step change (e.g., ±X percentage points per update) rather than allowing an immediate jump from 0% to 100%.

### Proof of Concept
1. Register/operate as an active SR with existing voters (delegators).
2. Submit `UpdateBrokerageContract{owner_address: <SR>, brokerage: 100}` via `UpdateBrokerageServlet`/gRPC (`framework/src/main/java/org/tron/core/services/http/UpdateBrokerageServlet.java`, `RpcApiService.updateBrokerage`).
3. `UpdateBrokerageActuator.validate()` only checks `0 <= brokerage <= 100` and witness/account existence — the transaction succeeds instantly with no on-chain notification event. [6](#0-5) 
4. On the next reward payment, `MortgageService.payReward()` uses the new `brokerage` value to compute `brokerageAmount`, routing up to 100% of the block reward to the SR and leaving 0% to be recorded via `delegationStore.addReward()` for voters: [7](#0-6) 
5. Delegators who have not polled `getBrokerage` off-chain have no way to know their reward share was cut to zero until after rewards for that cycle are already computed.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }

  public void setBrokerage(long cycle, byte[] address, int brokerage) {
    put(buildBrokerageKey(cycle, address), new BytesCapsule(ByteArray.fromInt(brokerage)));
  }

  public int getBrokerage(long cycle, byte[] address) {
    BytesCapsule bytesCapsule = get(buildBrokerageKey(cycle, address));
    if (bytesCapsule == null) {
      return DEFAULT_BROKERAGE;
    } else {
      return ByteArray.toInt(bytesCapsule.getData());
    }
  }

  public void setBrokerage(byte[] address, int brokerage) {
    setBrokerage(-1, address, brokerage);
  }

  public int getBrokerage(byte[] address) {
    return getBrokerage(-1, address);
  }
