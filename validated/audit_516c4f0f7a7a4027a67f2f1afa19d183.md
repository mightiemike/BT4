No vulnerability found for this question.

**Analysis:** The exploit hypothesis requires that a rogue BLS public key reach `ValidatorVerifier` aggregation without a PoP check ever being enforced. That is not the case in this codebase.

`bls12381::PublicKey::try_from` in [1](#0-0)  is documented as **not** subgroup-checking or PoP-checking the key on its own — but it is never used in isolation on the validator-registration path. Both entry points that write a consensus public key into on-chain validator state — `stake::initialize_validator` and `stake::rotate_consensus_key` — unconditionally gate the write behind `bls12381::public_key_from_bytes_with_pop`, aborting with `EINVALID_PUBLIC_KEY` if it returns `None`: [2](#0-1) [3](#0-2) 

`public_key_from_bytes_with_pop` calls the native `verify_proof_of_possession_internal`, which deserializes the raw bytes via `bls12381_deserialize_pk` (which internally calls `PublicKey::try_from`) and then explicitly calls `pop.verify(&pk)` before returning `true`/`Some`: [4](#0-3) [5](#0-4) 

`ProofOfPossession::verify` explicitly subgroup-checks both the PoP and the public key (`pk_validate = true`), which is exactly the mechanism that prevents both small-subgroup and rogue-key attacks, as documented in the module comments in `bls12381_keys.rs` (lines 8–21) and in the Move-layer native warnings (`bls12381.rs` lines 419–420, 453–454).

There is no code path where a validator's consensus key stored in `ValidatorConfig`/`ValidatorSet` — the data `ValidatorVerifier` is built from — bypasses this PoP gate. Genesis also routes through `stake::rotate_consensus_key` with the same check [6](#0-5) . Since an unprivileged actor cannot get a rogue key past the PoP-gated entry functions into the on-chain validator set, the rogue-key aggregation scenario described in the question cannot be reached — the invariant "only PoP-verified keys are aggregated" holds end-to-end in this codebase, so there is no state-integrity impact to report.

fn native_bls12381_verify_proof_of_possession(
    context: &mut SafeNativeContext,
    ty_args: &[Type],
    mut arguments: VecDeque<Value>,
) -> SafeNativeResult<SmallVec<[Value; 1]>> {
    debug_assert!(ty_args.is_empty());
    debug_assert!(arguments.len() == 2);

    context.charge(BLS12381_BASE)?;

    let pop_bytes = safely_pop_arg!(arguments, Vec<u8>);
    let key_bytes = safely_pop_arg!(arguments, Vec<u8>);

    let pk = match bls12381_deserialize_pk(key_bytes, context)? {
        Some(pk) => pk,
        None => return Ok(smallvec![Value::bool(false)]),
    };

    let pop = match bls12381_deserialize_pop(pop_bytes, context)? {
        Some(pop) => pop,
        None => return Ok(smallvec![Value::bool(false)]),
    };

    // NOTE(Gas): 2 bilinear pairings and a hash-to-curve
    context.charge(BLS12381_PER_POP_VERIFY * NumArgs::one())?;
    let valid = pop.verify(&pk).is_ok();

    Ok(smallvec![Value::bool(valid)])
}

    /// Verifies the proof-of-possesion (PoP) of the private key corresponding to the specified
    /// BLS public key. Implicitly, subgroup checks the PoP and the specified public key, so
    /// the caller is not responsible for doing it manually.
    pub fn verify(&self, pk: &PublicKey) -> Result<()> {
        // CRYPTONOTE(Alin): We call the signature verification function with pk_validate set to true
        // since we do not necessarily trust the PK we deserialized over the network whose PoP we are
        // verifying here.
        let result = self.pop.verify(
            true,
            &pk.to_bytes(),
            DST_BLS_POP_IN_G2,
            &[],
            &pk.pubkey,
            true,
        );
        if result == BLST_ERROR::BLST_SUCCESS {
            Ok(())
        } else {
            Err(anyhow!(
                "Proof-of-possession (PoP) did NOT verify: {:?}",
                result
            ))
        }
    }
