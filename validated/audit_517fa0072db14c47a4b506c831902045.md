## Analysis

I examined `apollo_l1_events` — the crate governing the lifecycle of L1→L2 (`L1HandlerTransaction`) messages inside the sequencer, since it is the closest analog to `RFPSimpleStrategy`'s milestone status state-machine: both maintain a single "status" enum for an entity, with independent boolean bookkeeping fields that are supposed to gate transitions but are not consistently checked before overwriting the primary status.

### Title
Rejected L1 handler transaction can never re-enter the proposable state, permanently stranding its bridged L1→L2 message - (File: `crates/apollo_l1_events/src/transaction_record.rs`)

### Summary
`TransactionRecord` tracks the lifecycle of an L1 handler transaction with a `state: TransactionState` field and separate metadata booleans (`committed`, `rejected`) meant to validate transitions [1](#0-0) . `mark_rejected` sets `state = Rejected` and `rejected = true`, but the `rejected` flag is only ever written, never read back anywhere in the crate to gate subsequent transitions [2](#0-1) . Meanwhile, the only transition that returns a record to `Pending` (the proposable state) does not exist at all — `is_proposable()` strictly requires `state == Pending` [3](#0-2) , and `maintain_indices` removes any non-proposable transaction from the `proposable_index` used to select L1 handler transactions for future blocks [4](#0-3) .

### Finding Description
When a proposal round completes, `TransactionManager::commit_txs` calls `mark_rejected` on every transaction hash in `rejected_txs` that was included in a proposed block but not part of the finally committed block [5](#0-4) . This unconditionally flips `state` to `Rejected` with no check of whether the prior state was legitimately still `Pending`/proposable, mirroring the original bug class where a status enum is force-set without validating the pre-transition state.

Crucially, there is no reciprocal path: no method in `transaction_record.rs` or `transaction_manager.rs` ever sets `state` back to `Pending` after it becomes `Rejected`. `mark_consumed` and `mark_cancellation_request` can still mutate `state` away from `Rejected` (to `Consumed` or `CancellationStartedOnL2`) since they check only `committed`/`consumed_at`, not `rejected` [6](#0-5) , but absent an L1 cancellation or consumption event, a `Rejected` L1 handler transaction is stuck forever: it is excluded from `proposable_index` and can never be re-proposed, since `get_txs` and `maintain_indices` only operate on `Pending` records [7](#0-6) .

This is directly analogous to the RFP report's root cause: a status field is transitioned without validating/consulting the entity's true prior/terminal status, leading to an incorrect permanent state that drives further (mis)handling — here, permanent exclusion from block proposal instead of wrongful resubmission.

### Impact Explanation
If this "rejected" classification can occur for a transaction that is still a legitimate, not-yet-processed L1→L2 message (e.g., a proposal round failed for reasons unrelated to the L1 handler transaction's own validity — such as a consensus round timing out or being abandoned for other transactions in the same block), the corresponding L1 message (which could represent a bridged deposit or other user-initiated cross-layer action) would never be executed on L2. Since the transaction record is also never removed automatically in the `Rejected` state (only `CancellationFinalizedOnL1` and consumption timelock expiry trigger removal from `records`), the underlying funds/message tied to that L1 handler transaction would be **permanently frozen** — the user cannot get it executed on L2, and (depending on the L1 bridge contract's design) may have no path to reclaim/cancel it if their L1 contract logic assumes eventual L2 processing.

### Likelihood Explanation
Reachability requires only that an L1 handler transaction gets included in a proposed block that is subsequently not the one committed (`rejected_txs` in `commit_txs`), which can occur through ordinary block-building/consensus churn — this is a single L1 message combined with normal sequencer proposal activity, not a privileged or adversarial action, matching the allowed "L1 message" attack surface. However, I could not fully verify (given tool budget) the exact semantics `apollo_batcher`/consensus attaches to the `rejected_txs` argument — whether it is only populated for transactions proven invalid at execution (in which case permanent rejection is by design) or also for transactions simply not selected in a losing proposal (in which case this is a genuine freezing bug). This distinction materially affects severity and should be confirmed against the caller of `TransactionManager::commit_txs`.

### Recommendation
1. Read the `rejected` (and `committed`) flags before performing state transitions in `mark_consumed` and `mark_cancellation_request`, consistent with the assertions already present in `mark_committed`/`mark_rejected`.
2. Clarify and enforce, at the call site in the batcher/consensus code, whether "rejected" is meant to be a terminal, un-recoverable status (permanently invalid transaction) or a "not included this round" status. If the latter, implement an explicit transition back to `Pending` so the transaction re-enters `proposable_index`, instead of allowing `Rejected` to be a silent dead end.
3. Add a state-machine invariant test (mirroring `Scheduler`'s exhaustive `should_panic` transition tests in `crates/blockifier/src/concurrency/scheduler_test.rs`) enumerating all `(current_state, event)` pairs for `TransactionRecord`, asserting that invalid transitions panic/error rather than silently succeeding.

### Proof of Concept
1. L1 handler transaction `T` is scraped and recorded (`state = Pending`).
2. `T` is selected via `get_txs` into a proposal, which is broadcast but the underlying block is not the one finally committed for that round.
3. Consensus/batcher informs `TransactionManager::commit_txs` that `T`'s hash is in `rejected_txs` (regardless of whether `T` was individually invalid or just part of a losing proposal) [8](#0-7) .
4. `mark_rejected` sets `state = Rejected` [9](#0-8) .
5. `maintain_indices` removes `T` from `proposable_index` since `is_proposable()` is now `false` [10](#0-9) .
6. No subsequent call in the crate ever restores `T.state` to `Pending`; `T` will never be offered again via `get_txs`, permanently excluding its L1 message from L2 execution unless/until an L1 cancellation event is scraped for it.

    /// The timestamp is the L1 block timestamp where this tx was marked consumed.

    pub fn mark_consumed(&mut self, timestamp: BlockTimestamp) -> Option<BlockTimestamp> {
        if self.is_committed() {
            debug!("Marking a committed transaction {} as consumed.", self.tx.tx_hash());
        } else {
            // TODO(guyn): check if this situation should be an error.
            // TODO(guyn): check other state combinations that may be worth an error/warning/debug
            // log.
            debug!(
                "Marking a non-committed transaction {} as consumed. Previous state: {:?}",
                self.tx.tx_hash(),
                self.state
            );
        }
        self.state = TransactionState::Consumed;
        // First check if the tx was already consumed. Double consumption is a bug!
        // If None, it wasn't previously consumed: mark the time and return None to signal
        // everything is ok. If Some, it was already consumed: report the time when it was
        // previously consumed, the caller decides what to do.
        match self.consumed_at {
            Some(existing) => Some(existing),
            None => {
                self.consumed_at = Some(timestamp);
                None
            }
        }
    }

    pub fn commit_txs(
        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],
    ) {
        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);
            self.with_record(tx_hash, |r| r.mark_committed()).unwrap();
        }
        for &tx_hash in rejected_txs {
            self.with_record(tx_hash, |r| r.mark_rejected()).expect(
                "Rejected L1 handler tx has no record. Unreachable: all L1 handler txs in a \
                 committed block were validated as known (validation rejects unknown hashes), \
                 sync commits with empty rejected_txs, and records are only removed via L1 \
                 cancellation/consumption, which can't race a block.",
            );
        }
    }

    // Update `proposable_index` and `consumed_queue` indices with this transaction.
    fn maintain_indices(&mut self, hash: TransactionHash) {
        if let Some(record) = self.records.get(&hash) {
            let TransactionPayload::Full { scrape_timestamp, .. } = record.tx else {
                // We haven't scraped this tx yet, so it isn't indexed.
                return;
            };

            let tx_hash = hash;
            // Check if we need to add this tx to the proposable index.
            if record.is_proposable() {
                // Assumption: txs will only be added to the index once, on arrival, so this
                // preserves arrival order.
                let tx_hashes = self.proposable_index.entry(scrape_timestamp).or_default();
                if !tx_hashes.contains(&tx_hash) {
                    tx_hashes.push(tx_hash);
                }
            } else {
                // This tx needs to be removed from the proposable index if it was on it.
                // Remove from the vec for this timestamp, and drop the entry if it becomes empty.
                match self.proposable_index.entry(scrape_timestamp) {
                    Entry::Occupied(mut entry) => {
                        let tx_hashes = entry.get_mut();
                        if let Some(index_in_vec) = tx_hashes.iter().position(|&h| h == tx_hash) {
                            tx_hashes.remove(index_in_vec);
                            if tx_hashes.is_empty() {
                                entry.remove();
                            }
                        }
                    }
                    Entry::Vacant(_) => {}
                }
            }
