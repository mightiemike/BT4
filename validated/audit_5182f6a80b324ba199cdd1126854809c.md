### Title
Duplicate delegation index entries cause phantom "ghost" delegation to survive full repayment due to single-match `List.remove()` in `DelegatedResourceAccountIndexCapsule` - ([File: chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java])

### Summary
`DelegatedResourceAccountIndexCapsule.addFromAccount`/`addToAccount` append `ByteString` entries unconditionally with no de-duplication check, while `removeFromAccount`/`removeToAccount` rely on `List.remove(Object)`, which deletes only the first `equals()`-matching element. [1](#0-0)  If a receiver/owner pair ever appears twice in the same list (e.g., via repeated legacy freeze-delegation calls that reuse these list-based add methods), a single subsequent `remove*Account` call — issued once the underlying `DelegatedResourceCapsule` balance is fully repaid to zero — deletes only one occurrence, leaving a stale "ghost" entry permanently in the public index.

### Finding Description
`addFromAccount`/`addToAccount` build a new protobuf list by simply calling `.addFromAccounts(...)`/`.addToAccounts(...)` without first checking `contains()`, so the same `ByteString` address can be inserted multiple times. [2](#0-1)  Conversely, `removeFromAccount`/`removeToAccount` copy the list into an `ArrayList` and call `fromList.remove(fromAccount)` / `toList.remove(toAccount)`, which is `List.remove(Object)` — this deletes only the first element for which `.equals()` returns true, then stops. [3](#0-2)  These list-based add/remove methods belong to the legacy (V1) delegation-index bookkeeping used by `FreezeBalanceActuator`/`UnfreezeBalanceActuator`, which is distinct from the newer V2 per-relationship keyed storage (`delegateV2`/`unDelegateV2`, `V2_FROM_PREFIX`/`V2_TO_PREFIX`) used by `DelegateResourceProcessor`/`UnDelegateResourceProcessor`, where each relationship is stored under its own unique DB key (`prefix+owner+receiver`) rather than in an appended list, so the V2 path is not affected by this defect. [4](#0-3)  For the V1 path, if an owner performs the legacy freeze-with-receiver delegation to the same receiver more than once, the receiver's address can be appended into `toAccounts`/`fromAccounts` twice; a single fully-repaying unfreeze afterward removes only one of the two duplicate entries, leaving one stale entry in the index even though the real `DelegatedResourceCapsule` balance backing the delegation has been reduced to zero.

### Impact Explanation
Because `Wallet`'s `getDelegatedResourceAccountIndex` gRPC/HTTP endpoint (and its PBFT/Solidity variants) reads directly from this index structure, a stale duplicate entry would be reported to any caller as an active delegation relationship between owner and receiver, even though no real, currently-backing frozen balance exists. [5](#0-4)  This creates a divergence between the authoritative balance state (`DelegatedResourceCapsule` = 0) and the publicly queryable index, which can mislead downstream automated systems (liquidity/resource dashboards, delegation trackers) that rely on this index as a source of truth, without allowing any theft or double-spend of TRX/resources themselves — the impact is limited to state/reporting divergence, not fund loss.

### Likelihood Explanation
Exploitability strictly depends on whether the legacy V1 freeze-delegation flow (`FreezeBalanceActuator`) can actually add the same receiver address twice to the same list without deduplication in real-world repeated-freeze scenarios — I confirmed the underlying capsule's unconditional-append / first-match-only-remove behavior directly in code, but did not fully trace every call site inside `FreezeBalanceActuator`/`UnfreezeBalanceActuator` to conclusively prove duplicate insertion is reachable purely from repeated ordinary `FreezeBalanceContract` transactions (this legacy freeze/delegate mechanism may also be gated or partially superseded by the newer resource-model flags such as `supportDR()`/`ALLOW_NEW_RESOURCE_MODEL` in current network configurations). This uncertainty should be resolved with an integration test before treating this as fully confirmed against a live, exploitable path.

### Recommendation
Change `removeFromAccount`/`removeToAccount` to remove **all** matching occurrences (e.g., `list.removeIf(entry -> entry.equals(target))` in a loop, or use `Collections.frequency` to remove all copies), and/or change `addFromAccount`/`addToAccount` to check `contains()` before appending to prevent duplicates from being created in the first place.

### Proof of Concept
```java
// Unit test in DelegatedResourceAccountIndexCapsuleTest (or similar)
@Test
public void testGhostEntryAfterDuplicateAddThenSingleRemove() {
  ByteString receiver = ByteString.copyFrom(new byte[]{1,2,3});
  DelegatedResourceAccountIndexCapsule capsule =
      new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(new byte[]{9,9,9}));

  // Simulate two legitimate delegation events to the same receiver
  capsule.addToAccount(receiver);
  capsule.addToAccount(receiver);
  assertEquals(2, capsule.getToAccountsList().size());

  // Simulate a single full-repayment unfreeze/undelegate event
  capsule.removeToAccount(receiver);

  // BUG: one stale/ghost entry remains even though balance is fully repaid
  assertEquals(1, capsule.getToAccountsList().size());
  assertTrue(capsule.getToAccountsList().contains(receiver));
}
```
Expected assertion (demonstrating the bug): after one `addToAccount` call matching one `removeToAccount` call, the list should be empty, but because of the prior duplicate insertion the list still contains 1 stale entry, confirming the ghost-entry condition described.

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
  }
