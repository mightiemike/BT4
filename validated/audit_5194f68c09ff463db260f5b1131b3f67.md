## Title
Post-auth hook silently skipped after a transient failure due to premature idempotency-key consumption in `IdempotentPromiseHandler` - (File: `packages/apps/shopify-app-express/src/helpers/idempotent-promise-handler.ts`)

### Summary
The token-exchange authentication handlers (`shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`) use `IdempotentPromiseHandler.handlePromise()` to make sure the `afterAuth` hook only runs once per session token. The handler marks an identifier as "consumed" *before* the wrapped promise resolves, not after it succeeds. If the wrapped `afterAuth` call fails, the identifier stays marked as used for up to 60 seconds, so any subsequent request that reaches the handler with the same session token silently no-ops instead of retrying, and the caller is told the operation succeeded. This mirrors the reported bug class: an irreversible bookkeeping action ("burn"/mark-as-done) is committed regardless of whether the guarded operation actually completed, and there is no compensating mechanism to redo or signal the failure on retry.

### Finding Description
`isPromiseRunnable()` inserts the identifier into the `identifiers` map the moment it is first seen, before `promiseFunction()` is awaited: [1](#0-0) 

If `promiseFunction()` throws, the exception propagates out of `handlePromise` to the first caller, but the identifier remains in the map (only pruned once it exceeds `IDENTIFIER_TTL_MS` = 60000ms, in `clearStaleIdentifiers`). Any subsequent call with the same identifier within that window takes the `isPromiseRunnable(identifier) === false` branch, skips `promiseFunction()` entirely, and still resolves successfully via `return Promise.resolve();`.

This handler is used to gate the `afterAuth` hook in the token-exchange authentication path, keyed by the raw session token: [2](#0-1) 

In `performTokenExchange`, the offline (and optionally online) access token is fetched and persisted to session storage *before* `callAfterAuthHook` is invoked: [3](#0-2) 

If `afterAuth` throws (e.g., a transient failure while registering mandatory webhooks), the request gets a 500, but the exchanged session was already stored as active. A retry using the same still-valid session token will either:
- hit the "session is active" fast path and skip the exchange/hook entirely, or
- re-enter `callAfterAuthHook` with the same `sessionToken` identifier, which `IdempotentPromiseHandler` now treats as already-run and silently skips — returning success to `performTokenExchange`, which then calls `next()` as if setup completed.

The identical pattern exists in the Remix and React Router equivalents: [4](#0-3) [5](#0-4) [6](#0-5) 

The unit tests confirm the "mark before success" behavior is by design and even demonstrate the identifier surviving a rejected promise: [7](#0-6) 

### Impact Explanation
This is analogous to the Axelar finding: a state-changing, effectively irreversible action (marking the auth completion as "done" for a given session token) is committed independently of whether the guarded critical operation (`afterAuth`, which apps commonly use to register mandatory webhooks or provision per-shop resources) actually succeeded, and there is no refund/retry/alerting mechanism. A single merchant hitting a transient failure during the first token-exchange authenticated request will have all functionally-identical retries within the 60-second TTL window silently succeed without the required setup work ever running — effectively denying the post-auth setup logic in the authentication handler for that window, with the app and merchant left in an inconsistent, unrecoverable-until-timeout state and no error surfaced to indicate the hook didn't execute.

### Likelihood Explanation
Reachable by any single embedded app installer/merchant via a normal HTTP round trip (no privileged access required): the client-side App Bridge/browser retry, a proxy retry, or simply the merchant reloading the page while the `afterAuth` hook is transiently failing (e.g., due to a downstream API hiccup) is enough to trigger the silent skip, since it merely requires reusing the same still-valid session token within 60 seconds of the first failure.

### Recommendation
Only mark an identifier as consumed after `promiseFunction()` resolves successfully (or cache the settled promise itself, including rejections, and re-throw on subsequent look-ups rather than silently resolving). E.g.:
```ts
async handlePromise({promiseFunction, identifier}) {
  if (!this.identifiers.has(identifier)) {
    const promise = promiseFunction();
    this.identifiers.set(identifier, {promise, timestamp: Date.now()});
  }
  const entry = this.identifiers.get(identifier)!;
  try {
    return await entry.promise;
  } finally {
    this.clearStaleIdentifiers();
  }
}
```
This way a failed `afterAuth` invocation does not block legitimate retries from actually re-running the hook, and the caller is not told an unfinished/failed operation succeeded.

### Proof of Concept
1. Configure token exchange with an `afterAuth` hook that throws on its first invocation for shop `test-shop`.
2. Send an authenticated request with a fresh session token for `test-shop`; `performTokenExchange` stores the offline session then calls `callAfterAuthHook`, which throws, and the request receives `500`. The identifier (`sessionToken`) is now marked used in `IdempotentPromiseHandler`.
3. Within 60 seconds, resend a request using the same session token (or one that produces the same session id / hits the active-session fast path). `handlePromise` now returns `Promise.resolve()` without invoking `afterAuth` again, and `performTokenExchange` proceeds to `next()`, returning `200` as if the post-auth setup (e.g., mandatory webhook registration) had succeeded, even though it never ran.

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }
