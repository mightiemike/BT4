### Title
Replay-guard digest is recorded before owner-binding validation, allowing an unprivileged attacker to pre-emptively squat a predictable victim digest and cause denial-of-service - ([File: core/capabilities/vault/authorizer.go])

### Summary
`RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go` binds solely on the digest string (method+params+id), with no caller/owner binding. In `core/capabilities/vault/authorizer.go`, `AuthorizeRequest` calls `a.replayGuard.CheckAndRecord(authResult.Digest(), ...)` *before* `validateSecretOwnersMatchAuthorized` is invoked, so any caller who can obtain a valid JWT for their own account can burn a digest for arbitrary attacker-chosen `params` (including a target owner's address) even though that request is subsequently rejected for owner mismatch.

### Finding Description
The pipeline in `authorizer.go` is:
```go
if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil { ... }
if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil { ... }
``` [1](#0-0) 

`JWTBasedAuth.AuthorizeRequest` only validates the token signature, tenant, scope, and that `requestDigest == claims.RequestDigest`; it derives `workflowOwner` purely from the attacker's own JWT claims (`OrgID`/`TenantID`/`WorkflowOwner`), independent of the `Owner` field embedded in `req.Params`: [2](#0-1) 

Because `req.Digest()` is computed purely from the request's `Method`, `Params`, and `ID` — with no binding to the authenticated caller — an attacker who can predict/observe a victim's future `request_id` + `method` + `params` combination (e.g. deterministic IDs, or a fixed `vault.secrets.list` call with a known/observable owner and namespace) can craft an identical raw request, obtain a legitimately-issued JWT for their own (unrelated) account whose `request_digest` claim matches that crafted request's digest, and submit it. `AuthorizeRequest` succeeds through digest/scope/tenant checks and calls `CheckAndRecord`, which records the digest as seen — this happens *before* `validateSecretOwnersMatchAuthorized` runs and rejects the attacker's own request for owner mismatch. The rejection of the attacker's request does not undo the `seen` map insertion. `RequestReplayGuard.CheckAndRecord` itself has no notion of owner/caller identity: [3](#0-2) 

When the real victim later submits their genuine request with identical `Method`/`Params`/`ID`, `req.Digest()` yields the same digest, and `CheckAndRecord` returns `ErrRequestAlreadySeen`, so the victim's legitimate request is denied until the entry expires.

### Impact Explanation
This is a targeted denial-of-service against a specific victim's Vault operation (e.g. `vault.secrets.list`, `vault.secrets.create/update/delete`) without requiring the attacker to control or spoof the victim's owner identity — the attacker's malicious request is itself rejected, but the side effect of poisoning the shared `seen` map persists for the entry's expiry window. This matches a Chainlink bounty "denial of service against a specific node/operation" style impact scoped to the Vault capability.

### Likelihood Explanation
Exploitability requires the attacker to (a) hold a valid JWT for their own account/org that can be minted with an attacker-controlled `request_digest` claim (or a valid allowlist authorization for their own workflow), and (b) predict or observe the exact `request_id`/`method`/`params` a victim will use for a future request. This is realistic for low-entropy or deterministic request IDs, or for well-known/fixed calls like listing secrets for a publicly-derivable owner address (owner derivation from `OrgID`/`TenantID` is deterministic per `DeriveJWTAuthorizedVaultWorkflowOwner`). No special privilege beyond a normal authenticated Vault client account is required, and the attack is repeatable against future request windows.

### Recommendation
Reorder the checks in `authorizer.go` so `validateSecretOwnersMatchAuthorized` runs *before* `CheckAndRecord`, ensuring only requests that pass owner-binding validation can occupy a replay-guard slot. Additionally, consider binding the replay-guard key to the authorized caller/owner (e.g. `hash(digest, authResult.AuthorizedOwner())`) rather than the raw content digest alone, so an unrelated caller cannot pre-record a slot for another owner's request.

### Proof of Concept
Unit test plan for `authorizer_test.go`:
1. Construct `reqVictim` with `Method = vault.secrets.list`, `Params = {request_id: "req-1", owner: victimOwner, namespace: "main"}`; compute `digest := reqVictim.Digest()`.
2. Construct `reqAttacker` with identical `Method`/`Params`/`ID` content (attacker knows/predicts `victimOwner`, `"req-1"`, `"main"`).
3. Mock `jwtBasedAuth.AuthorizeRequest` to return `AuthResult{workflowOwner: attackerOwner, digest: digest, expiresAt: future}` for `reqAttacker` (simulating attacker's own valid JWT bound to that digest).
4. Call `authorizer.AuthorizeRequest(ctx, reqAttacker)` — assert it returns an owner-mismatch error (attacker's own request correctly rejected).
5. Mock `jwtBasedAuth.AuthorizeRequest` to return `AuthResult{workflowOwner: victimOwner, digest: digest, expiresAt: future}` for `reqVictim` (victim's genuine, valid authorization).
6. Call `authorizer.AuthorizeRequest(ctx, reqVictim)` — assert it now returns `ErrRequestAlreadySeen`, proving the victim's legitimate request is denied solely because of the earlier rejected attacker request.

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
