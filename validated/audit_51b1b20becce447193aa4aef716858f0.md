### Title
Incomplete State Reversion in `CancelAllUnfreezeV2Actuator` — Vote Accounting Not Restored When Frozen Balance Is Restored - (File: `actuator/src/main/java/org/tron/core/actuator/CancelAllUnfreezeV2Actuator.java`)

### Summary
`CancelAllUnfreezeV2Actuator` is the java-tron analog of `cancelWithdrawal`: it reverses a pending `UnfreezeBalanceV2` operation by moving unexpired entries from `unfrozenV2List` back into frozen resource balances. Like the reported bug, it restores some — but not all — of the state that the original operation mutated: it restores `FrozenV2` balances and the global `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight`, but it never calls the vote-adjustment logic (`updateVote`) that `UnfreezeBalanceV2Actuator` invokes when the original unfreeze happens. This produces the same class of bug: an asymmetric revert that leaves the account's vote-related accounting permanently degraded relative to its restored resource balance.

### Finding Description
When a user unfreezes TRON_POWER (or bandwidth/energy) via `UnfreezeBalanceV2Actuator.execute`, the actuator calls `this.updateVote(accountCapsule, unfreezeBalanceV2Contract, ownerAddress)` in addition to updating total resource weight [1](#0-0) . This call trims/reduces the user's outstanding `Votes` when the newly-unfrozen TRON_POWER can no longer back the votes previously cast (i.e., it mutates vote-related state as a side effect of the unfreeze).

When the manager-equivalent operation `CancelAllUnfreezeV2Actuator` reverses this unfreeze before it expires, it re-adds the amount back into `FrozenV2` and re-adds the corresponding weight to the global totals via `updateFrozenInfoAndTotalResourceWeight` / `addTotalResourceWeight` [2](#0-1) . However, nowhere in `CancelAllUnfreezeV2Actuator.execute` (or in the corresponding TVM-facing `CancelAllUnfreezeV2Processor.execute`) is any vote-related state restored or recalculated [3](#0-2) [4](#0-3) .

This mirrors the root cause pattern in the external report exactly: the original action (`queueWithdrawal` / `unfreezeBalanceV2`) mutates two pieces of state (`hypeBuffer` + `_pendingWithdrawals` / `FrozenV2`&weight + `Votes`), but the cancellation path (`cancelWithdrawal` / `cancelAllUnfreezeV2`) only reverts one of them (frozen balance/weight), leaving the other (votes) permanently inconsistent with the restored balance.

### Impact Explanation
After a `CancelAllUnfreezeV2` call, an account's `FrozenV2`/TRON_POWER balance is fully restored to its pre-unfreeze value, but any votes that were trimmed by the preceding `UnfreezeBalanceV2` call are not restored. This causes:
- A durable divergence between an account's actual voting power (backed by frozen TRON_POWER) and its recorded `Votes`, understating the account's cast votes relative to its now-restored stake.
- Aggregate witness vote totals computed from `VotesStore`/`Votes` entries becoming inconsistent with the real total frozen TRON_POWER supply, a state/accounting divergence that affects SR ranking computations network-wide, not just the single user.
- No direct asset loss, but it is an unprivileged-user-reachable (any account can freeze → unfreeze → cancel) accounting-inconsistency bug consistent with the "invalid-state/divergence" impact category, matching the external report's acknowledged (non-critical, accounting integrity) severity class.

### Likelihood Explanation
This is trivially reachable by any account holder using standard freeze/unfreeze/cancel flows or TVM natives — no privileged role is required. The sequence `freezeBalanceV2` → `voteWitness` (consuming TRON_POWER) → `unfreezeBalanceV2` (trims votes) → `cancelAllUnfreezeV2` (restores balance, not votes) is a realistic and easily-triggerable path, as exercised (without vote-state assertions) in `FreezeV2Test.testFreezeV2Operations` [5](#0-4)  and `CancelAllUnfreezeV2ActuatorTest.testCancelAllUnfreezeV2` [6](#0-5) , neither of which validates vote-state consistency after cancellation, suggesting this asymmetry is untested.

### Recommendation
Modify `CancelAllUnfreezeV2Actuator.execute` (and `CancelAllUnfreezeV2Processor.execute` for the TVM path) to invoke the same vote-restoration/recalculation logic used in `UnfreezeBalanceV2Actuator.updateVote`, proportionally restoring or recalculating votes for the TRON_POWER amount being re-frozen, mirroring the mitigation pattern from the source report (fully reverting all state mutated by the original action, not just the primary balance/weight fields).

### Proof of Concept
1. Account freezes TRX for `TRON_POWER` via `freezeBalanceV2`.
2. Account casts votes for a witness using `voteWitness`, consuming the full TRON_POWER.
3. Account calls `unfreezeBalanceV2` for `TRON_POWER` — `UnfreezeBalanceV2Actuator.updateVote` trims the account's `Votes` because available TRON_POWER backing the vote has decreased [7](#0-6) .
4. Before the unfreeze expires, account calls `cancelAllUnfreezeV2` — `FrozenV2` balance and `TotalTronPowerWeight` are restored to pre-unfreeze values [2](#0-1) , but the previously trimmed `Votes` entry is never restored.
5. Result: the account now has its full original TRON_POWER frozen balance back, but a permanently reduced `Votes` record — an accounting divergence between stake and recorded votes that persists until the account manually re-votes.

    TransactionResultCapsule ret = (TransactionResultCapsule) result;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }
    long fee = calcFee();
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    byte[] ownerAddress;
    try {
      ownerAddress = getOwnerAddress().toByteArray();
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    AccountCapsule ownerCapsule = accountStore.get(ownerAddress);
    List<UnFreezeV2> unfrozenV2List = ownerCapsule.getUnfrozenV2List();
    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    AtomicLong atomicWithdrawExpireBalance = new AtomicLong(0L);
    /* The triple object is defined by resource type, with left representing the pair object
    corresponding to bandwidth, middle representing the pair object corresponding to energy, and
    right representing the pair object corresponding to tron power. The pair object for each
    resource type, left represents resource weight, and right represents the number of unfreeze
    resources for that resource type. */
    Triple<Pair<AtomicLong, AtomicLong>, Pair<AtomicLong, AtomicLong>, Pair<AtomicLong, AtomicLong>>
        triple = Triple.of(
        Pair.of(new AtomicLong(0L), new AtomicLong(0L)),
        Pair.of(new AtomicLong(0L), new AtomicLong(0L)),
        Pair.of(new AtomicLong(0L), new AtomicLong(0L)));
    for (UnFreezeV2 unFreezeV2 : unfrozenV2List) {
      updateAndCalculate(triple, ownerCapsule, now, atomicWithdrawExpireBalance, unFreezeV2);
    }
    ownerCapsule.clearUnfrozenV2();
    addTotalResourceWeight(dynamicStore, triple);

    long withdrawExpireBalance = atomicWithdrawExpireBalance.get();
    if (withdrawExpireBalance > 0) {
      ownerCapsule.setBalance(ownerCapsule.getBalance() + withdrawExpireBalance);
    }

    accountStore.put(ownerCapsule.createDbKey(), ownerCapsule);
    ret.setWithdrawExpireAmount(withdrawExpireBalance);
    Map<String, Long> cancelUnfreezeV2AmountMap = new HashMap<>();
    cancelUnfreezeV2AmountMap.put(BANDWIDTH.name(), triple.getLeft().getRight().get());
    cancelUnfreezeV2AmountMap.put(ENERGY.name(), triple.getMiddle().getRight().get());
    cancelUnfreezeV2AmountMap.put(TRON_POWER.name(), triple.getRight().getRight().get());
    ret.putAllCancelUnfreezeV2AmountMap(cancelUnfreezeV2AmountMap);
    ret.setStatus(fee, code.SUCESS);
    return true;

  public Map<String, Long> execute(CancelAllUnfreezeV2Param param, Repository repo) throws ContractExeException {
    Map<String, Long> result = new HashMap<>();
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    long withdrawExpireBalance = 0L;
    for (Protocol.Account.UnFreezeV2 unFreezeV2: ownerCapsule.getUnfrozenV2List()) {
      if (unFreezeV2.getUnfreezeExpireTime() > now) {
        String resourceName = unFreezeV2.getType().name();
        result.put(resourceName, result.getOrDefault(resourceName, 0L) + unFreezeV2.getUnfreezeAmount());

        updateFrozenInfoAndTotalResourceWeight(ownerCapsule, unFreezeV2, repo);
      } else {
        // withdraw
        withdrawExpireBalance += unFreezeV2.getUnfreezeAmount();
      }
    }
    if (withdrawExpireBalance > 0) {
      ownerCapsule.setBalance(ownerCapsule.getBalance() + withdrawExpireBalance);
    }
    ownerCapsule.clearUnfrozenV2();

    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);

    result.put(VMConstant.WITHDRAW_EXPIRE_BALANCE, withdrawExpireBalance);
    return result;
  }
