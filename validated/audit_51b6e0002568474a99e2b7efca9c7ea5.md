### Title
Fee Paid Unconditionally on Action Failure Drains Contract's Own Balance — (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In `inner_rlp_execute`, the relayer fee is dispatched as an independent promise batch before the action promise is created. When the action promise subsequently fails, `rlp_execute_callback` refunds the **full** attached deposit to the caller rather than `deposit − fee`. The net effect is that the contract's pre-existing balance decreases by the fee amount on every failed action.

### Finding Description
`inner_rlp_execute` unconditionally creates a fee-transfer promise for `EOABaseTokenTransfer` and `ERC20Transfer` transactions when `predecessor != current_account_id` and `fee > 0`: [1](#0-0) 

This promise is **not** chained to the action promise; it executes regardless of whether the action succeeds or fails.

`CallerDeposit::new` captures the full attached deposit `D`: [2](#0-1) 

On action failure, `rlp_execute_callback` refunds the full `D` to the caller: [3](#0-2) 

Because the fee `F` was already sent out and the full `D` is refunded, the contract's own balance decreases by `F` per failed action. There is no validation that `D ≥ F` and no adjustment of the refund amount.

### Impact Explanation
The wallet contract's balance is the user's NEAR balance. A malicious relayer (any unprivileged `predecessor != current_account_id`) can:
1. Obtain a user-signed Ethereum transaction with a nonzero fee (e.g., high `max_fee_per_gas * gas_limit`).
2. Submit it via `rlp_execute` when they know the action will fail (e.g., calling a method on a contract that will reject it, or a transfer that will be rejected).
3. Collect fee `F` from the contract's pre-existing balance while also receiving the full deposit refund `D`.

Repeated over many transactions (the `has_in_flight_tx` flag only prevents concurrency, not sequential submissions), this drains the user's NEAR balance by `F` per round.

### Likelihood Explanation
Any relayer can act as the attacker. The relayer controls submission timing and can choose to submit a signed transaction at a moment when the action is known to fail. The user cannot revoke a signed transaction once the relayer holds it. The fee `F` is bounded only by `VALUE_MAX ≈ 2^128 − 1` yoctonear, so a single transaction with a large fee can cause significant loss.

### Recommendation
The fee should only be paid when the action succeeds, **or** the refund on failure should be reduced by the fee already paid. Two concrete fixes:

1. **Chain the fee promise to the action promise** so it only executes on success (use `.then` instead of an independent batch).
2. **Adjust `CallerDeposit`** to store `D − F` instead of `D`, so the refund on failure does not include the already-paid fee.

### Proof of Concept
```rust
// Pseudocode for a Rust unit test
let fee = NearToken::from_near(1); // large fee embedded in signed tx
let deposit = NearToken::from_near(1); // relayer attaches D = fee

// Simulate action promise failure in rlp_execute_callback
```
