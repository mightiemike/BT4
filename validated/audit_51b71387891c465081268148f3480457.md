### Title
Wallet Contract pays relayer's fee before the underlying transaction is known to succeed, causing fund loss when the action is rejected as a "faulty relayer" error - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The NEAR Wallet Contract's `inner_rlp_execute` unconditionally dispatches the relayer's fee-refund transfer *before* the emulated Ethereum transaction (the "real" action) is actually attempted, and before it is known whether that action will succeed. In one specific path — `EOABaseTokenTransfer` with `address_check: Some(_)` — the fee can be paid to the relayer even though the subsequent `address_check_callback` may determine that the relayer submitted a bad/faulty target and abort the real transfer entirely (banning the relayer). This mirrors the reported ERC20 issue: an irreversible value-moving step (fee transfer) executes ahead of, and independent of, the fallible operation (the actual transfer/action) whose failure is not used to prevent or reverse the earlier payment.

### Finding Description
`inner_rlp_execute` parses the RLP transaction and, for any `EOABaseTokenTransfer`/`ERC20Transfer` kind with a non-zero `fee`, immediately creates and dispatches a `Transfer` receipt paying the relayer (`predecessor_account_id`) that `fee`: [1](#0-0) 

This fee-payment promise is scheduled unconditionally, regardless of `address_check`. Immediately afterward, the *actual* action promise is constructed based on `transaction_kind`. For the `EOABaseTokenTransfer { address_check: Some(address), .. }` branch, execution first calls out to the address registrar and only decides whether to actually perform the transfer (or instead ban the relayer) in a later callback: [2](#0-1) 

The callback, `address_check_callback`, can determine that the relayer supplied a bad target (i.e. an address that actually corresponds to an existing named account) and, in that case, does not perform the intended transfer at all — instead it schedules `create_ban_relayer_promise`, which simply returns a "faulty relayer" error and revokes the relayer's access key: [3](#0-2) [4](#0-3) 

Critically, the relayer fee was already sent to the relayer in `inner_rlp_execute` *before* this outcome was known, and there is no code path that refunds or claws back that fee when `ban_relayer`/`address_check_callback` determines the transaction is rejected. The only refund logic that exists is for `caller_deposit` (the deposit attached by an external caller), handled in `rlp_execute_callback` on `PromiseResult::Failed`: [5](#0-4) 

That refund mechanism only covers `caller_deposit`, not the fee already paid out to the relayer via `promise_batch_action_transfer` in `inner_rlp_execute`. Because `promise_batch_action_transfer` is a fire-and-forget action (it has no boolean return value to check, unlike `ERC20::transfer`), and the code does not gate this transfer on the eventual success of the real action, the fee payment is effectively an "unsafe/unchecked transfer" analog: value moves out of the user's wallet unconditionally, ahead of and independent from the actual operation's success/failure determination.

### Impact Explanation
The user's signed transaction pays a fee intended to compensate the relayer for correctly executing a base-token transfer. If a relayer (which need not be malicious — it could also deliberately exploit this) submits a `target` account that the address registrar recognizes as an existing named account for the destination address, the whole flow is redirected to `address_check_callback`, which detects the "faulty relayer" condition and never performs the user's intended transfer. Despite this, the fee that was sent to the relayer at the top of `inner_rlp_execute` is not reversed. The user thus loses the fee (a real value transfer already dispatched and executed) while receiving neither the intended transfer nor a refund, and the wallet's own access-key ban does nothing to recover the already-spent fee. This is a concrete unauthorized/irrecoverable value movement (fee) tied to a transaction that is ultimately rejected — directly analogous to the reported bug pattern of an unchecked/irrecoverable transfer causing user fund loss.

### Likelihood Explanation
This is reachable by any relayer using the Wallet Contract for base-token transfers with a non-zero fee and an `address_check` target — a normal, expected usage pattern for the contract (relayers are explicitly compensated with fees for gas costs per the code comments). A relayer only needs to submit (intentionally or by mistake) a `target` that resolves via the address registrar to an existing named account for the recipient address to trigger the "faulty relayer" ban path after the fee has already been paid. No privileged access is required; this is triggerable purely from a submitted RLP transaction plus the relayer's choice of `target` when calling `rlp_execute`.

### Recommendation
Defer the relayer fee-refund transfer until after the real action's outcome is known (e.g., dispatch it only from within `rlp_execute_callback`/`address_check_callback` conditioned on success), or make the fee payment itself refundable/reversible when the callback determines a faulty-relayer / failed condition, similar to how `caller_deposit` is already refunded on `PromiseResult::Failed`. Alternatively, gate the initial fee-dispatch on whether `address_check` will actually be attempted so the fee is not committed before the validity of the target has been confirmed.

### Proof of Concept
1. A relayer submits `rlp_execute(target, tx_bytes_b64)` where `tx_bytes_b64` encodes an `EOABaseTokenTransfer` with a non-zero `fee` and an address that requires `address_check` (i.e., the `to` address is another eth-implicit account).
2. `inner_rlp_execute` immediately schedules and sends the `fee` to the relayer via `env::promise_batch_create`/`env::promise_batch_action_transfer` (lines 382-383).
3. The relayer supplies (mistakenly or intentionally) a `target` account ID that the `ADDRESS_REGISTRAR_ACCOUNT_ID` contract resolves to an existing named `account_id` for that address.
4. `address_check_callback` receives `maybe_account_id = Some(...)`, detects a faulty relayer, and calls `create_ban_relayer_promise`, which resolves to `ExecuteResponse { success: false, error: Some("Error: faulty relayer") }` without ever performing the user's intended transfer.
5. The user's fee, already transferred in step 2, is not refunded anywhere in this flow — the user has lost the fee value with no corresponding service performed.
