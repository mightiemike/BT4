### Title
Storage-key aliasing collapses distinct contracts' keys into a shared alias namespace, causing state-diff corruption on compression - (File: crates/blockifier/src/state/stateful_compression.rs)

### Summary
`allocate_aliases_in_storage` and `compress`/`decompress` in `crates/blockifier/src/state/stateful_compression.rs` allocate and look up aliases for storage keys using only the raw `StorageKey` value (`AliasKey = StorageKey`), without incorporating the owning `ContractAddress`. As a result, identical storage-key values belonging to *different* contracts are aliased through the *same* slot in the shared alias contract, analogous to the reported bug where a value legitimately belonging to one domain (chain B collateral) is used to update accounting in a different domain (chain A treasury).

### Finding Description
`allocate_aliases_in_storage` iterates per contract address and, for storage keys above `MAX_NON_COMPRESSED_CONTRACT_ADDRESS`, inserts an alias keyed only by `StorageKey` via `alias_updater.insert_alias(key)`: [3](#0-2) 

`compress_storage_key` similarly calls `self.get_alias(*storage_key)` (ignoring `contract_address` for lookup purposes beyond the `should_compress_storage_key` gate), and `get_alias` reads/writes the alias contract's storage keyed solely by that `StorageKey`: [4](#0-3) 

If two distinct contracts in the same state diff happen to write to storage keys with the same numeric value (a very plausible event — e.g. both contracts use `storage_key!(1993)` or any equal large key), the alias contract's single storage cell for that raw key is shared: the second contract's key allocation reads/overwrites the alias entry belonging to the first contract's key. This means the compressed representation (used for the on-chain published state diff / DA) may replace one contract's key with an alias that, when decompressed, resolves to the wrong key — effectively causing the state-diff to misattribute a storage write to the wrong slot, structurally identical to the reported bug where a value computed in one context (chain/contract) is applied to a different context.

### Impact Explanation
If this collision causes the compressed/decompressed state diff to not round-trip correctly, the published state diff (and any consumer decompressing it, including nodes independently building state from DA, or the Starknet OS re-execution/commitment path) could commit an incorrect storage value to the wrong contract's slot. This can lead to: honest-node state divergence, wrong committed root, or effectively lost/frozen funds if the misattributed slot is a balance or allowance cell (e.g., an ERC-20 storage key colliding with another contract's key of identical numeric value), mirroring the original report's "yields from one domain incorrectly available/consumed in another domain, causing fund unavailability."

### Likelihood Explanation
Storage keys for common patterns (e.g., low-index mapping slots, small deterministic keys) frequently repeat across different contracts (many ERC-20-like contracts use very similar/simple storage layouts), so key collisions across distinct `ContractAddress`es are not rare, especially for `MIN_VALUE_FOR_ALIAS_ALLOC`-and-above keys in different Cairo 1 contracts that both write to a numerically identical slot within the same block's state diff. Any block containing two contracts whose state diffs use identical raw storage-key values would trigger the shared-alias code path, requiring only ordinary transactions from unprivileged senders touching two different contracts in one block.

### Recommendation
Scope the alias key by both `ContractAddress` and `StorageKey` (e.g., hash or concatenate them into the `AliasKey`/alias-contract storage key) instead of using the bare `StorageKey`, so that aliases allocated for one contract's storage keys can never collide with, or be read/written by, another contract's storage keys.

### Proof of Concept
Not executed; concept: construct a block with two distinct contracts (`contract_address!(1)` and `contract_address!(2)`) both writing to the same raw `StorageKey` value ≥ `MIN_VALUE_FOR_ALIAS_ALLOC` in the same block's state diff. Run `allocate_aliases_in_storage` followed by `compress`; observe that the alias contract storage slot keyed by that raw `StorageKey` is populated once and used by `compress_storage_key` for both contracts' entries, producing an alias-to-(contract,key) mapping that is ambiguous — decompression cannot distinguish which contract the aliased key belongs to, since `AliasDecompressorUtil::restore_alias_key` only maps `Alias -> AliasKey (bare StorageKey)`, discarding the contract-address dimension entirely, as seen in `crates/blockifier/src/state/stateful_compression_test_utils.rs:81-97`.
