## Analysis

The external report's bug class is: **an unprivileged attacker can cheaply create an unbounded number of entries in a queue that is later iterated in full**, causing denial of service to the processing/finalization of that queue.

Push Chain's analog is the `PendingOutbounds` collection in `x/uexecutor`, combined with the `AllPendingOutbounds` query that Universal Validators (`puniversald`) poll to discover outbounds that need TSS signing and broadcast.

- Every outbound creation is driven by a user-controlled `MsgExecutePayload` whose payload calls the `UniversalGatewayPC` withdraw function; the amount only needs to satisfy `amount > 0` [1](#0-0)  — i.e., a 1-wei withdrawal is valid, exactly like the original report's "1 wei" grief primitive.
- `MsgExecutePayload` is in the gasless whitelist, so the attacker pays **no Cosmos transaction fee** — only minimal EVM gas deducted from their own UEA balance [2](#0-1) , making mass submission cheap.
- Each successful call creates a new `OutboundTx` entry (keyed by a fresh deterministic `outbound_id`) which is indexed into the `PendingOutbounds` collection at creation time, **before** any validator vote [3](#0-2) .
- `PendingOutbounds` entries are removed **only** when validator consensus is reached on the observation, and are explicitly **not** cleaned up on ballot expiry [4](#0-3) .
- The `AllPendingOutbounds` query — used by `puniversald` (`GetAllPendingOutbounds`) to fetch outbounds that need TSS signing — unconditionally `Walk`s the **entire** `PendingOutbounds` collection before applying pagination, under the assumption (stated in a comment) that "pending set is small" [5](#0-4) , and additionally does a per-entry `UniversalTx.Get` lookup [6](#0-5) .
- `puniversald` calls this exact endpoint every polling cycle with `Limit: 1000` [7](#0-6)  — but since the underlying `Walk` scans the whole collection regardless of the requested limit, query cost scales with the *total* number of pending outbounds ever created and not yet finalized, not with the page size.

Because an attacker can create outbounds significantly faster (many per block, no Cosmos fee) than Universal Validators can broadcast+observe+vote them on external chains (bounded by external chain confirmation latency), the attacker can grow `PendingOutbounds` unboundedly, degrading (or effectively DoSing) the query all UVs rely on to discover legitimate outbounds — delaying withdrawal processing for all users, not just the attacker's own funds.

### Title
Unbounded growth of `PendingOutbounds` via cheap self-triggered dust withdrawals enables DoS of outbound processing - (File: x/uexecutor/keeper/create_outbound.go, x/uexecutor/keeper/query_server.go)

### Summary
Any user can cheaply and repeatedly trigger gateway withdrawals of dust amounts (as low as 1 unit) through their own UEA via the gasless `MsgExecutePayload` message. Each call creates a new, indefinitely-persisting `PendingOutbounds` entry. The `AllPendingOutbounds` query that Universal Validators poll to discover outbounds to sign performs a full, unbounded `Walk` over this collection regardless of the caller-requested pagination limit, so an attacker can inflate the collection to a size that materially degrades (or exhausts resources of) the query path all validators depend on to process legitimate outbounds.

### Finding Description
`BuildOutboundsFromReceipt` / `attachOutboundsToUtx` create an `OutboundTx` for any decoded `UniversalTxOutbound` event with a positive amount and add it to `PendingOutbounds` before any validator vote occurs [8](#0-7) . `OutboundTx.ValidateBasic` only requires `amount > 0` [1](#0-0) , so there is no minimum-withdrawal-amount guard. Submission is via `MsgExecutePayload`, which is gasless at the Cosmos fee layer [2](#0-1) , and any account may submit it as long as the payload is validly signed by the UEA owner (an attacker only needs to be the owner of their own UEA to spam their own withdrawals) [9](#0-8) .

`PendingOutbounds` entries survive ballot expiry by design and are removed only on consensus [10](#0-9) . The querier used by validators, `AllPendingOutbounds`, walks the *entire* collection into memory, sorts it, and only then slices by the requested pagination window [11](#0-10) , meaning the cost of a call from `puniversald.GetAllPendingOutbounds` (used every polling cycle by all UVs) grows linearly with total unresolved pending-outbound count, not with the 1000-item page size requested [7](#0-6) .

### Impact Explanation
If an attacker sustains dust-withdrawal creation faster than UVs can externally broadcast/confirm/vote the corresponding outbounds (a realistic asymmetry, since outbound finalization requires external-chain confirmation latency + TSS signing while creation is a single cheap EVM call), `PendingOutbounds` grows without bound. This degrades or denies the `AllPendingOutbounds` query path that every Universal Validator depends on to discover legitimate outbounds needing signature/broadcast, delaying settlement of all users' pending withdrawals chain-wide — a non-network-level DoS reachable by an ordinary unprivileged user, matching the in-scope "denial of service ... reachable without privileged control" criterion.

### Likelihood Explanation
High. No minimum withdrawal amount is enforced, the message is gasless, and only the attacker's own UEA balance (dust amount + minimal EVM gas) is required. No special privileges, validator collusion, or external chain compromise are needed.

### Recommendation
- Enforce a minimum outbound amount (denominated appropriately per token/chain) in `OutboundTx.ValidateBasic` or at outbound-creation time in `create_outbound.go`.
- Cap the number of outstanding `PendingOutbounds` entries per sender/UEA, or add per-account/per-block rate limiting on outbound-creating payload execution.
- Change `AllPendingOutbounds` to walk with a bounded prefix/limit consistent with the requested pagination instead of loading and sorting the full collection on every call, and consider adding a paginated iterator keyed by `CreatedAt` to avoid full-collection scans.

### Proof of Concept
1. Deploy/own a UEA on Push Chain with a small native balance sufficient to cover EVM gas for many calls.
2. Repeatedly submit `MsgExecutePayload` (gasless, no Cosmos fee) whose payload calls the `UniversalGatewayPC` withdraw method for `amount = 1` to an enabled destination chain, incrementing the UEA-tracked payload nonce each time.
3. Each call passes `OutboundTx.ValidateBasic` (amount > 0) and gets appended to `UniversalTx.OutboundTx` and indexed in `PendingOutbounds` [3](#0-2) .
4. Repeat thousands of times across blocks; observe `PendingOutbounds` collection size growing unboundedly (never cleaned up until UV consensus finalizes each one) [10](#0-9) .
5. Observe `AllPendingOutbounds` (called by `puniversald.GetAllPendingOutbounds`) latency/resource cost grow proportionally to total pending count, degrading discovery of legitimate pending outbounds for all users' withdrawals [11](#0-10) .

```markdown
### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
```

```markdown
### `PendingOutbounds`

- **Created** by chain code at outbound creation in `create_outbound.go` —
  BEFORE any validator vote. The chain knows the outbound exists because it
  generated the destination-chain transaction itself; validators are tasked
  with observing whether/how it landed.
- **Keyed** by deterministic chain-derived `outbound_id`.
- **Variant-aware:** validator votes append `OutboundObservationVariant`s as
  they arrive (`RecordOutboundVote` inside `VoteOutbound`). Multiple variants
  per outbound indicate validator divergence on the destination-chain
  observation (different `success`/`tx_hash`/`error_msg`/`gas_fee_used`).
- **Removed ONLY when validators reach consensus** (existing inline
  `PendingOutbounds.Remove` in `msg_vote_outbound.go` on `PASSED`).
- **Ballot expiry does NOT remove the entry** — this is intentional. The
  destination chain already received (or did not receive) the outbound; the
  user's funds are already in flight. Auto-refund risks double-pay (if the
  outbound actually landed), auto-retry risks double-delivery, and there is
  no safe automatic resolution. Operators investigate stuck outbounds via
  the per-variant audit trail (which validators voted what observation) plus
  separate `x/uvalidator` ballot status queries; resolution is governance-
  driven, not chain-driven.
```

```go
// AllPendingOutbounds implements types.QueryServer.
// Returns all pending outbound entries with full outbound data, sorted by block height.
// Uses pagination.reverse for descending order (default: ascending by created_at).
func (k Querier) AllPendingOutbounds(goCtx context.Context, req *types.QueryAllPendingOutboundsRequest) (*types.QueryAllPendingOutboundsResponse, error) {
	if req == nil {
		return nil, status.Error(codes.InvalidArgument, "invalid request")
	}

	ctx := sdk.UnwrapSDKContext(goCtx)

	// Collect all entries (pending set is small)
	var allEntries []types.PendingOutboundEntry
	err := k.PendingOutbounds.Walk(ctx, nil, func(_ string, value types.PendingOutboundEntry) (bool, error) {
		allEntries = append(allEntries, value)
		return false, nil
	})
	if err != nil {
		return nil, status.Error(codes.Internal, err.Error())
	}

	// Sort by CreatedAt (block height)
	reverse := req.Pagination.GetReverse()
	sort.Slice(allEntries, func(i, j int) bool {
		if reverse {
			return allEntries[i].CreatedAt > allEntries[j].CreatedAt
		}
		return allEntries[i].CreatedAt < allEntries[j].CreatedAt
	})

	// Apply pagination
	total := uint64(len(allEntries))
	limit := req.Pagination.GetLimit()
	if limit == 0 {
		limit = query.DefaultLimit
	}
	offset := req.Pagination.GetOffset()

	start := offset
	if start > total {
		start = total
	}
	end := start + limit
	if end > total {
		end = total
	}
	pageEntries := allEntries[start:end]
```

```go
// GetAllPendingOutbounds retrieves up to the first 1000 pending outbound transactions from Push Chain.
// Sorted by created_at (block height) ascending — oldest first.
func (c *Client) GetAllPendingOutbounds(ctx context.Context) ([]*uexecutortypes.PendingOutboundEntry, []*uexecutortypes.OutboundTx, error) {
	resp, err := retryWithRoundRobin(
		len(c.uexecutorClients),
		&c.rr,
		func(idx int) (*uexecutortypes.QueryAllPendingOutboundsResponse, error) {
			return c.uexecutorClients[idx].AllPendingOutbounds(ctx, &uexecutortypes.QueryAllPendingOutboundsRequest{
				Pagination: &query.PageRequest{Limit: 1000},
			})
		},
		"GetAllPendingOutbounds",
		c.logger,
	)
	if err != nil {
		return nil, nil, err
	}
	return resp.Entries, resp.Outbounds, nil
}
```
