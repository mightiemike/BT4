### Title
Unauthenticated JSON-RPC methods on the batch-prover mutate proving/commitment state and can inject a fabricated proof toward DA - (File: crates/batch-prover/src/rpc.rs, crates/common/src/rpc/auth.rs)

### Summary
The batch-prover RPC server ships an `Auth` middleware intended to gate sensitive JSON-RPC methods behind an API key, but the allow-list of protected methods only covers backup-related calls. Highly sensitive `batchProver_*` methods — `setCommitments`, `submitFakeProof`, `pauseProving`, `retryProvingJob`, `prove`, `createCircuitInput` — are left completely unauthenticated, so any network client that can reach the batch-prover's RPC port can mutate the node's commitment/proving state or make it emit a fabricated proof, without any credential.

### Finding Description
The RPC auth middleware is defined as: [1](#0-0) 

`PROTECTED_METHODS` only lists `"backup_create", "backup_validate", "backup_info"`. Every other method, including all `batchProver_*` methods, bypasses the API-key check entirely: [2](#0-1) 

The batch-prover RPC trait exposes state-mutating methods with no additional per-method authorization check in their handlers: [3](#0-2) [4](#0-3) 

`setCommitments` directly overwrites the ledger DB's commitment-by-index, commitment-by-L1 and pending-commitment records with attacker-supplied `merkle_root`/`l2_end_block_number`/`index` values: [5](#0-4) 

`submitFakeProof` builds a `FakeReceipt`/`InnerReceipt::Fake` claim and submits it to the DA service as a `DaTxRequest::ZKProof`, i.e. it can push a proof transaction out of the node without operator involvement: [6](#0-5) 

`retryProvingJob` and `pauseProving` let an unauthenticated caller re-queue commitments or halt proving entirely: [7](#0-6) [8](#0-7) 

This mirrors the reported bug class (an internal, supposedly trusted-only interface reachable and mutable without authentication/authorization due to an incomplete allow-list — analogous to the webhook path reaching Redis/Sidekiq without the intended access boundary). Here the equivalent binding broken is: **the set of proving/commitment RPC mutations should require `api_key` == the operator's configured secret, but the middleware's allow-list omits them, so `attacker-supplied request == authenticated operator request`.**

### Impact Explanation
This matches the "High - an unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`" impact bucket directly: any unauthenticated caller reaching the batch-prover's RPC port can overwrite locally tracked sequencer commitments (`setCommitments`), pause the proving pipeline (`pauseProving`), or force proof resubmission/regeneration (`retryProvingJob`, `prove`). `submitFakeProof` additionally causes the node to emit a fake-receipt "proof" transaction to the DA layer via `da_service.send_transaction`; whether this constitutes a Critical false-state-transition-proved event depends on whether the network's proof verifier (light client / L1 contract / other zkvm backend) would ever accept a `FakeReceipt`-based proof — that verification logic lives outside this file and was not fully confirmed in this pass, so it is reported at the confirmed High severity (unauthenticated state mutation / Auth bypass) rather than asserted as Critical.

### Likelihood Explanation
Likelihood is high wherever the batch-prover RPC port is reachable by anyone other than the operator (default binding is a config choice, but the vulnerability is that the `Auth` layer's allow-list, which exists specifically to protect sensitive endpoints, fails to include these methods even when `api_key` is configured) — the API key protects only `backup_*` calls, so configuring an API key does not protect these commitment/proving-mutation methods at all.

### Recommendation
Expand `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs` to include all state-mutating `batchProver_*` methods (`setCommitments`, `prove`, `submitFakeProof`, `pauseProving`, `retryProvingJob`, `createCircuitInput`), or switch to a deny-by-default model where only explicitly whitelisted read-only methods bypass the API-key check.

### Proof of Concept
1. Start a batch-prover node with `rpc_config.api_key` set (or unset — it makes no difference for these methods).
2. Send an unauthenticated JSON-RPC request `batchProver_setCommitments` with an attacker-chosen `merkle_root`/`index`/`l2_end_block_number` — the handler at `crates/batch-prover/src/rpc.rs:345-381` writes it straight into the ledger DB with no auth check.
3. Alternatively call `batchProver_submitFakeProof` with an `index_start`/`index_end` range to force the node to build a `FakeReceipt` and submit it as a DA `ZKProof` transaction (`crates/batch-prover/src/rpc.rs:514-533`), all without any credential, because `Auth::call` in `crates/common/src/rpc/auth.rs:36` only intercepts `backup_*` method names.

    async fn set_commitments(
        &self,
        commitments: Vec<SequencerCommitmentRpcParam>,
    ) -> RpcResult<()> {
        for commitment in commitments {
            let l1_height = commitment.l1_height.to::<u64>();
            let commitment = SequencerCommitment {
                merkle_root: commitment.merkle_root,
                index: commitment.index.to::<u32>(),
                l2_end_block_number: commitment.l2_end_block_number.to::<u64>(),
            };

            info!(
                "Overriding sequencer commitment, index={} merkle_root={} l2_end_height={} l1_height={}",
                commitment.index,
                hex::encode(commitment.merkle_root),
                commitment.l2_end_block_number,
                l1_height,
            );

            self.context
                .ledger_db
                .put_commitment_by_index(&commitment)
                .map_err(internal_rpc_error)?;
            // This might cause some duplicate commitment indices appear in l1 -> index table which is ok
            self.context
                .ledger_db
                .put_commitment_index_by_l1(SlotNumber(l1_height), commitment.index)
                .map_err(internal_rpc_error)?;
            self.context
                .ledger_db
                .put_prover_pending_commitment(commitment.index)
                .map_err(internal_rpc_error)?;
        }

        Ok(())
    }

    async fn retry_proving_job(&self, job_id: Uuid) -> RpcResult<Uuid> {
        let ledger_db = &self.context.ledger_db;

        let mut commitment_indices = ledger_db
            .get_commitment_indices_by_job_id(job_id)
            .map_err(internal_rpc_error)?
            .ok_or_else(|| internal_rpc_error("Job ID not found"))?;
        commitment_indices.sort_unstable();

        ledger_db
            .remove_proving_job_by_id(job_id)
            .map_err(internal_rpc_error)?;

        for index in &commitment_indices {
            ledger_db
                .put_prover_pending_commitment(*index)
                .map_err(internal_rpc_error)?;
        }
        let _ = self.prove(PartitionMode::Normal).await?;

        let new_id = ledger_db
            .get_job_id_by_commitment_index(commitment_indices[0])
            .map_err(internal_rpc_error)?
            .ok_or_else(|| internal_rpc_error("New job ID not found"))?;

        info!("Retried proving job {}, new job id: {}", job_id, new_id);
        Ok(new_id)
    }
