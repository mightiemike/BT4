The nanopb advisory describes a memory-safety bug specific to C: a `oneof` implemented as a C `union` where decoding a non-pointer field first and then a pointer field causes the non-pointer bytes to be reinterpreted as a pointer, leading to an invalid `free()`/`realloc()`. This class of bug requires manual memory management and untyped union reinterpretation, both of which are absent in protobuf-go.

In protobuf-go, oneofs are implemented using Go interface values, not C unions. The oneof unmarshal code explicitly checks the interface's type descriptor (itab) before reusing the underlying data pointer, and only reuses it when `hdr.Type == itab`, i.e., the concrete Go type already matches the field being decoded [1](#0-0) . Because Go's type system enforces that `hdr.Data` can only be reinterpreted through the type recorded in `hdr.Type`, there is no way for one field's decoded bytes to be misinterpreted as a pointer belonging to a different field variant — Go's runtime and garbage collector, not manual `free()`/`realloc()`, own all memory, so the "invalid free" sink from the advisory does not exist in this codebase. The higher-level reflection-based oneof accessor (`fieldInfoForOneof`) similarly always allocates a fresh wrapper struct via `reflect.New(ot)` when the existing value's concrete type doesn't match, rather than reinterpreting raw memory [2](#0-1) .

Since the vulnerability class (type confusion between union members leading to an invalid free/realloc call) has no structural analog in a memory-safe, GC-managed, interface-based oneof implementation, there is no equivalent reachable bug to report.
