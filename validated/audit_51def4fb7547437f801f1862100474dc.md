### Title
Fixed 5% slippage tolerance on gas-abstraction auto-swap allows sandwich extraction from inbound gas deposits - (File: `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`)

### Summary
The reported bug class is a zero/attacker-controlled slippage tolerance on an AMM swap that lets an unprivileged party sandwich the swap and extract value. Push Chain's analog is `ExecuteInboundGas` / `gasAndPayloadDepositAutoSwap`, which fetch a Uniswap-style quote and then execute `CallPRC20DepositAutoSwap` with `minPCOut` pinned at a fixed 95% of the just-fetched quote [1](#0-0) . Unlike the audited contract, the tolerance here is not user-controlled (good), but the fetched quote itself reflects the *current* AMM pool state, which any unprivileged actor can move beforehand.

### Finding Description
`ExecuteInboundGas` is invoked synchronously as part of finalizing an inbound ballot inside `VoteInbound`/`ExecuteInbound` — i.e., inline in whichever `MsgVoteInbound` transaction pushes the ballot over threshold [2](#0-1) . The execution point (and thus which quote is read) is therefore visible/predictable to on-chain observers, and its exact block position depends on validator/mempool ordering, not on a protocol-controlled internal step isolated from user transactions.

Inside `ExecuteInboundGas`, the quote is fetched from the AMM (`GetSwapQuote`) and `minPCOut` is derived purely as `quote * 95 / 100` — a fixed 5% band around whatever price the pool shows at that moment [1](#0-0) . The identical pattern is duplicated in `gasAndPayloadDepositAutoSwap` for `GAS_AND_PAYLOAD` inbounds [3](#0-2) . There is no check that the pool price is close to a longer-term TWAP/oracle price, and no cap on the swapped amount visible in this code path (unlike the external report's `swapCap`), so the absolute value at risk scales with the size of the bridged inbound.

An unprivileged attacker who can predict (from already-recorded votes in `PendingInbounds`) that an inbound is about to finalize can submit an ordinary AMM swap transaction ahead of the finalizing `MsgVoteInbound` to skew the WPC/PRC20 pool price, then reverse the swap after the module's auto-swap executes at the manipulated price (bounded only by the 5% tolerance). This is the same sandwich mechanic as the `VoltBurn.buyNSendToVoltTreasury()` report, just bounded to a 5% band instead of unbounded 0% slippage.

### Impact Explanation
This falls under "corruption of ... gas fee accounting / refund accounting ... reachable through user-reachable flows with honest validators and honest nodes," since the attack requires no privileged role — only an ordinary AMM swap transaction from any address, timed against publicly visible/predictable inbound-finalization events. Each occurrence can extract up to ~5% of the swapped PRC20 amount from the gas-abstraction/refund flow, funded ultimately from protocol-controlled or user-bridged funds, with no per-call cap visible in this code path.

### Likelihood Explanation
Likelihood is moderate rather than high specifically because the 5% band already substantially limits the attack (unlike the reported 0%-slippage case), and because timing execution to land immediately around a specific `MsgVoteInbound` requires either controlling the finalizing UV's vote broadcast timing or racing the mempool — the same kind of MEV/sandwich conditions common to any AMM. It's a real, reachable, unprivileged trigger, but the existing 5% guard reduces (without eliminating) the exploitable value versus the referenced report.

### Recommendation
- Bound the deviation between the AMM's current spot quote and a manipulation-resistant reference (e.g., a TWAP, or the chain-meta gas price oracle already maintained in `ChainMetas`), rejecting or clamping swaps when the spot price diverges materially from that reference.
- Consider capping the absolute PRC20/PC value processed per auto-swap call (mirroring the `swapCap` pattern from the external report) so a single sandwich cannot extract more than a bounded, small absolute amount.
- Ensure `GetSwapQuote` and the subsequent `CallPRC20DepositAutoSwap` are as close to atomic as possible relative to attacker-controllable transaction ordering (e.g., quote fetched and consumed without an interveningattacker-influenceable block boundary), reducing the window in which pool state can be pre-skewed.

### Proof of Concept
Conceptual (no local devnet/AMM state available in this review to execute end-to-end):
1. Attacker monitors `PendingInbounds`/`Ballots` state via the chain's query endpoints and identifies an inbound close to reaching the 2/3 UV vote threshold for `TxType_GAS` or `TxType_GAS_AND_PAYLOAD`.
2. Attacker swaps a large amount into the PRC20/WPC pool used by `GetUniversalCoreQuoterAddress`/`GetSwapQuote`, skewing the spot price.
3. When the deciding `MsgVoteInbound` lands and finalizes the ballot, `ExecuteInboundGas` (or `gasAndPayloadDepositAutoSwap`) fetches the now-skewed quote and calls `CallPRC20DepositAutoSwap` with `minPCOut = quote*95/100` [4](#0-3) , executing at the manipulated price within the 5% tolerance.
4. Attacker reverses the initial swap, netting up to ~5% of the bridged amount's value, funded by the protocol/user side of the auto-swap.
