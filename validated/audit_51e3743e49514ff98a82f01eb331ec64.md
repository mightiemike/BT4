### Title
Starknet OS `replace_class` syscall omits declared-class validation present in Blockifier - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The Rancher CVE stems from a privileged mutation (ClusterRole overwrite) being driven by an attacker-controlled identifier (`cr-name`) with no verification that the caller is authorized to target that identifier. The analogous pattern in this sequencer is the `replace_class` syscall: the contract's `class_hash` state entry is overwritten using an attacker-supplied `class_hash` value taken directly from transaction calldata, but the two execution engines that must agree on the resulting state diverge on whether that value is validated before the overwrite is committed.

### Finding Description
In `crates/blockifier/src/execution/syscalls/hint_processor.rs` and `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`, `replace_class` explicitly verifies the target class is declared before allowing the state write: [1](#0-0) 

In contrast, the Cairo implementation of the same syscall inside the Starknet OS program — which is used for OS re-execution / proving the block — carries an explicit TODO stating the equivalent check is missing, and proceeds to unconditionally overwrite the contract's `class_hash` state entry with the caller-supplied value: [2](#0-1) 

The deprecated syscalls path has the identical gap: [3](#0-2) 

The `class_hash` value driving this overwrite is fully attacker-controlled calldata to a syscall reachable from any contract invoked by a submitted transaction — structurally identical to the Rancher bug's use of an unverified, attacker-set identifier (`cr-name`) to select the object that gets overwritten, without checking that the identifier corresponds to something the caller is entitled to target (in Blockifier's case: a declared, compatible-version class).

### Impact Explanation
Since Starknet OS re-execution is the authoritative path used to generate the STARK proof and validate/commit the state transition, a state entry produced with an unvalidated (e.g., undeclared, or Cairo0-when-Cairo1-expected) class hash could be accepted by the OS pipeline where Blockifier would have rejected the transaction outright (`StateError::UndeclaredClassHash` / `ForbiddenClassReplacement`, see `crates/blockifier/src/execution/syscalls/hint_processor.rs:96-97`). This creates a root-cause divergence between the two engines that are supposed to compute identical state diffs: Blockifier (consensus execution) enforces class-declaration integrity, while the OS (proof generation / re-execution) does not independently verify it and instead trusts hint-provided state entries. This can manifest as wrong committed state roots or honest-node divergence between the execution and proving layers, matching the required impact bar (wrong committed root / honest-node divergence).

### Likelihood Explanation
`replace_class` is reachable from any Cairo contract via a single invoke transaction — no special privileges are required, matching the "single submitted transaction" reachability bar. The divergence is deterministic (not a race condition) and is directly evidenced by the TODO comment acknowledging the missing check.

### Recommendation
Add the same declared-class check in the OS `execute_replace_class` (and the deprecated equivalent) as exists in Blockifier's `replace_class` hint processor: before committing the new `StateEntry`, verify via the class dictionary/hint that `class_hash` corresponds to an actually declared class (and enforce the same V0/V1 compatibility rule Blockifier applies) so both engines reject/accept the same set of transactions and always compute identical state diffs.

### Proof of Concept
Not independently executed in this ask-only investigation (no runtime/tooling access). Based on static analysis: a contract calling the `replace_class` syscall with a `class_hash` value for a class that was never declared (or a Cairo0 class hash where Blockifier disallows the replacement) would be rejected during Blockifier execution but is not independently rejected in the OS `execute_replace_class` implementation shown above, since that function performs no declared-class lookup before writing the new `StateEntry`.

**Note on completeness:** I could not fully trace how/whether the missing OS-side check is compensated for elsewhere (e.g., a separate global consistency check between all committed `contract_class_changes` and `contract_state_changes` at the end of OS execution) due to the tool-call limit reached before verifying this. If such a global check exists, it could partially or fully mitigate this divergence — this should be confirmed with a full-repo review (e.g., a Devin session) before treating this as fully exploitable.

// Replaces the class.
func execute_replace_class{
    range_check_ptr,
    syscall_ptr: felt*,
    contract_state_changes: DictAccess*,
    revert_log: RevertLogEntry*,
}(contract_address: felt) {
    alloc_locals;
    let request = cast(syscall_ptr + RequestHeader.SIZE, ReplaceClassRequest*);

    // Reduce gas.
    let success = reduce_syscall_gas_and_write_response_header(
        total_gas_cost=REPLACE_CLASS_GAS_COST, request_struct_size=ReplaceClassRequest.SIZE
    );
    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();
    }

    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address,
        prev_value=cast(state_entry, felt),
        new_value=cast(new_state_entry, felt),
    );

    assert [revert_log] = RevertLogEntry(selector=CHANGE_CLASS_ENTRY, value=state_entry.class_hash);
    let revert_log = &revert_log[1];

    return ();
}
