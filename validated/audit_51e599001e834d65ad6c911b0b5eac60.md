### Title
Missing duplicate-address check in `VoteWitnessActuator.validate()` allows duplicate witness votes in a single `VoteWitnessContract` - (File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java)

### Summary
`VoteWitnessActuator.validate()` iterates the `VoteWitnessContract`'s `votes` list and checks each entry's address validity, vote count positivity, account/witness existence, and that the aggregate vote sum does not exceed the voter's TRON power — but it never checks whether the same witness address appears more than once in the list. This mirrors the reported SSV bug class: an ordered/counted list is validated for per-item correctness and aggregate bounds but not for uniqueness of the referenced entity IDs.

### Finding Description
In `validate()`: [1](#0-0) 
the loop checks `DecodeUtil.addressValid`, `voteCount <= 0`, account/witness existence, and accumulates `sum` — but no `Set`/`distinct()` check is performed on `vote.getVoteAddress()` across the list, unlike the equivalent distinctness checks that java-tron does apply elsewhere (e.g. `AccountPermissionUpdateActuator.checkPermission()` explicitly rejects non-distinct addresses via `.distinct()` comparison at [2](#0-1) ).

In `execute()`, `countVoteAccount()` then applies every vote entry directly, one at a time, without merging duplicates: [3](#0-2) 
`AccountCapsule.addVotes()` simply appends a new `Vote` proto entry to the account's votes list without deduplicating by address: [4](#0-3) 

This is notably inconsistent with the newer TVM-based voting path, `VoteWitnessProcessor.execute()`, which explicitly merges votes for the same witness address into a `Map<ByteString, Long>` before applying them — with an inline comment "merge vote for same witness": [5](#0-4) 

The presence of explicit dedup logic in the TVM path, and its absence in the classic `VoteWitnessActuator` path, indicates the java-tron team is aware that duplicate witness addresses in a single vote submission are a real hazard that needs to be normalized before being persisted — yet the older/still-active contract-based actuator does not perform this normalization.

### Impact Explanation
Allowing duplicate vote-address entries in a single `VoteWitnessContract` means an account's persisted `votes` list (`AccountCapsule.getVotesList()`) can contain multiple separate `Vote` entries for the same witness address instead of one canonical entry. This creates divergent/duplicated state representation for what should be a single vote-per-witness relationship, which:
- Produces state that diverges from the invariant assumed elsewhere in the codebase (one `Vote` entry per witness per voter), which downstream consumers of `getVotesList()` (reward computation via `MortgageService`, unfreeze vote proportional reallocation in `UnfreezeBalanceV2Actuator.updateVote()`, TVM's `VoteWitnessProcessor`) may not expect. For example, `UnfreezeBalanceV2Actuator.updateVote()` iterates `accountCapsule.getVotesList()` and recomputes proportional new votes per entry [6](#0-5) , which would produce multiple separate re-scaled `Vote` records for the same witness rather than one, further compounding state divergence over time.
- Represents an accounting/invalid-state class issue: the same conceptual entity (a single voter→witness relationship) is represented redundantly, which is the same root-cause pattern flagged in the external report (duplicate registered operator entries breaking the assumption of one-entry-per-participant).

I was not able to fully trace, within the available tool budget, the exact downstream maintenance/tally code path (`MaintenanceManager` / `DelegationStore.countVote`) that aggregates per-witness vote totals from `VotesCapsule.getNewVotes()`/`getOldVotes()` to confirm whether a witness's total credited vote count would be double-counted, under-counted, or unaffected in aggregate (the `sum` bound check in `validate()` does bound the total votes regardless of duplication, since it sums over every list entry including duplicates). This aggregate-sum check likely prevents a pure "vote count inflation" outcome, but it does not prevent persisted-state duplication of `Vote` records for the same witness, which is itself an invalid/inconsistent state relative to the implicit one-entry-per-witness invariant enforced elsewhere in the codebase.

### Likelihood Explanation
Reaching this path only requires an unprivileged account to submit a `VoteWitnessContract` (via `VoteWitnessActuator`, exposed through the standard transaction/wallet API) containing two or more `Vote` entries with the same `voteAddress` but different (or same) `voteCount` values, as long as the per-entry checks pass and the total sum stays within the account's TRON power. No privileged role is required.

### Recommendation
In `VoteWitnessActuator.validate()`, add a duplicate-address check on `contract.getVotesList()` (e.g., collect `vote.getVoteAddress()` into a `Set`/`.distinct()` list and compare its size to `contract.getVotesCount()`, following the same pattern already used in `AccountPermissionUpdateActuator.checkPermission()`), rejecting the transaction if duplicates are found. Alternatively/additionally, mirror the `VoteWitnessProcessor` approach in `countVoteAccount()` by merging vote entries per witness address into a map before calling `accountCapsule.addVotes(...)` / `votesCapsule.addNewVotes(...)`, so the persisted votes list always contains at most one `Vote` entry per witness address.

### Proof of Concept
Not independently executed; reasoning is based on static code review of `VoteWitnessActuator.validate()`/`countVoteAccount()` versus `AccountPermissionUpdateActuator.checkPermission()` and `VoteWitnessProcessor.execute()`. A concrete PoC would submit a `VoteWitnessContract` with two `Vote` entries for the same witness address (e.g., `voteAddress=W`, `voteCount=1` twice) from an account whose TRON power is ≥ 2 TRX, then inspect `AccountCapsule.getVotesList()` after execution to confirm it contains two separate `Vote` entries for `W` instead of one merged entry — this was not run due to lack of execution tooling in this session.
