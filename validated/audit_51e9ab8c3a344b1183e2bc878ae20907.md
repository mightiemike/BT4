### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash validation, letting replay/verification tooling accept a divergent authenticated state root - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the single authenticity check used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a locally re-executed `TransactionOutput` matches the trusted, on-chain-committed `TransactionInfo`. The function validates status, gas, write-set hash, and event root hash, but explicitly does **not** validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code comment itself documents.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  checks four fields (execution status, gas used, write-set hash, event root hash) against the authenticated `TransactionInfo`, but the trailing comment makes explicit that the state-checkpoint family of hashes is intentionally skipped: [2](#0-1) 

This differs from the block/chunk-execution commit path, where `DoStateCheckpoint` *does* cross-check computed checkpoint roots (main state, hot state, and native-position state) against the `known_state_checkpoints`/`known_position_state_checkpoints` derived from the committed `TransactionInfo`s, e.g. in `execution/executor/src/workflow/do_state_checkpoint.rs` (`get_state_checkpoint_hashes`) and the chunk-executor call site in `execution/executor/src/chunk_executor/mod.rs`: [3](#0-2) [4](#0-3) 

But `ensure_match_transaction_info` is used by out-of-band, unprivileged verification/debugging paths (`db-tool replay_on_archive`, `aptos-debugger`, and the Move CLI) that re-execute historical transactions and compare their locally produced `TransactionOutput`s directly against the `TransactionInfo`s pulled from an (untrusted) archive/full-node, without going through the full `DoStateCheckpoint`/`DoLedgerUpdate` pipeline that performs the checkpoint-hash comparison. Because these paths skip the checkpoint-hash comparison, a `TransactionOutput` whose write set is individually correct (matching hash and events) but whose *aggregate effect on the state tree* (state root, hot-state root, or native-position/"trading-native" state root) diverges from the authenticated ledger state will still pass `ensure_match_transaction_info` successfully.

This is a genuine break of the "committed state must not silently diverge from the authenticated result" invariant specifically for the `position_state_checkpoint_hash` / native-position state root introduced for the trading-native feature (guarded by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), and, more generally, for `state_checkpoint_hash`/`hot_state_checkpoint_hash` whenever replay tooling relies solely on `ensure_match_transaction_info` rather than full state-tree reconstruction.

### Impact Explanation
Replay-verification tooling (`db-tool replay-on-archive`, used in CI/ops to detect consensus/state divergence across historical replay, and `aptos-debugger`) is a primary safety net for catching non-determinism or state-computation bugs across node versions/hard forks. If this check silently ignores checkpoint-hash divergence, a bug that corrupts the aggregate state root (but not individual write-set/event hashes) — e.g., a state-tree update bug, an ordering bug in checkpoint construction, or the native-position ("trading-native") state root diverging from local execution as the code comment explicitly warns — would go undetected by this verification path even though it is exactly the class of bug this tool exists to catch. This matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category: an authenticated state root can diverge from correct execution without being flagged, undermining confidence in the replay-verify safety net that guards mainnet upgrades and the new trading-native feature rollout.

### Likelihood Explanation
The gap is deterministic and always present (not a race condition): any caller of `ensure_match_transaction_info` will not catch checkpoint-hash mismatches, full stop. The comment in the source explicitly flags this as an unresolved TODO ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), indicating the aptos-core team is aware the gap exists but has not yet closed it before the feature flag (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled. Because this is a self-acknowledged, already-diagnosed gap rather than a subtle exploit requiring novel discovery, and because it only affects a diagnostic/verification tool rather than the actual consensus-critical commit path (`DoStateCheckpoint` in block/chunk execution still validates checkpoint hashes correctly), the exploitability is bounded to weakening detection of state divergence rather than allowing an attacker to directly corrupt consensus state.

### Recommendation
Extend `ensure_match_transaction_info` to also validate `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on the `TransactionInfo` variant) against locally recomputed roots before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, or otherwise ensure that all call sites of `ensure_match_transaction_info` (`replay_on_archive.rs`, `aptos_debugger.rs`, Move CLI) additionally perform full state-tree reconstruction and checkpoint-hash comparison equivalent to `DoStateCheckpoint::get_state_checkpoint_hashes`, so that replay verification cannot report success while the authenticated state root diverges from local execution.

### Proof of Concept
No exploit harness is required beyond the self-documented gap in the source: any test that (1) constructs a `TransactionOutput` whose `write_set`/`events` hash correctly matches a given `TransactionInfo`, but (2) is fed through a modified/corrupted state-tree update routine (e.g., a hypothetical position-state root bug), will show that `ensure_match_transaction_info` returns `Ok(())` even though `state_checkpoint_hash`/`position_state_checkpoint_hash` recomputed from the actual resulting state tree do not match the `TransactionInfo`'s committed values — because the function never reads or compares those fields at [5](#0-4) .

**Note on confidence:** I was not able to fully trace the exact call sites in `storage/db-tool/src/replay_on_archive.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` (the index does not surface their full bodies), so I cannot confirm with certainty whether those specific tools additionally perform independent state-root reconstruction elsewhere in their pipeline that might mitigate this gap for the `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields. The gap for `position_state_checkpoint_hash` is explicitly confirmed by the in-source TODO comment. If deeper confirmation of the exploit chain in the replay tooling is needed, a Devin session with full repository/tool access would be needed to inspect those files in full.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
    }
