## Analysis

The External Report's core class is: **when a vault-like accounting function must convert between two units, EIP-4626 requires it to round in the *protocol's* favor; rounding the other way (favoring the user) is a valid vulnerability class even without direct fund theft.**

The direct analog in this codebase is `CalculateGasCost` in `x/uexecutor/keeper/fees.go`, which computes the gas fee a UEA owes the protocol for `ExecutePayloadV2` (`x/uexecutor/keeper/execute_payload.go`), fee that is then burned via `DeductAndBurnFees`. [1](#0-0) 

`baseFee` is an `sdkmath.LegacyDec` sourced from `k.feemarketKeeper.GetBaseFee(sdkCtx)`, which is dynamically recalculated by the `feemarket` module's EIP-1559 base-fee adjustment (multiplication/division of Dec values based on gas-used delta vs. gas target). The code comment asserts base fee "is always a whole number of upc," and unconditionally does `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))` (floor division) to strip the Dec's 18-decimal internal scaling before treating it as the effective per-gas-unit price. [2](#0-1) 

Critically, this floor-division happens on the **per-gas-unit price**, before it is multiplied by `gasUsed`:
```
effectiveGasPrice := new(big.Int).Set(baseFeeBig)   // already floored
gasCost := new(big.Int).Mul(effectiveGasPrice, gasUsedBig)
```
Any sub-upc fractional component of the true base fee is discarded first, then the (already-shrunk) price is multiplied by `gasUsed`. This means the systemic undercharge is proportional to `gasUsed`, not bounded to a single-unit rounding error as it would be if the truncation happened after the multiplication.

### Title
Gas fee for `ExecutePayloadV2` is computed by truncating the fractional base-fee component before multiplying by gasUsed, systematically undercharging users - (File: x/uexecutor/keeper/fees.go)

### Summary
`CalculateGasCost` assumes the feemarket's `LegacyDec` base fee is always an exact integer number of `upc`, and floors it to a `*big.Int` before use as the effective per-gas-unit price. This assumption does not hold in general: the feemarket module's dynamic EIP-1559 base-fee recalculation performs `Dec` multiplication/division that can produce fractional (non-whole-`upc`) results. Flooring the price before multiplying by `gasUsed` (rather than flooring the final total cost) amplifies the rounding loss by `gasUsed`, causing the protocol to collect and burn less than the economically correct fee for every `MsgExecutePayload` gas deduction.

### Finding Description
`DeductGasFeesFromReceipt` reads `baseFee := k.feemarketKeeper.GetBaseFee(sdkCtx)` and passes it into `CalculateGasCost`, which does:
```go
baseFeeBig := baseFee.BigInt()
baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))   // truncates fractional upc
...
effectiveGasPrice := new(big.Int).Set(baseFeeBig)
gasCost := new(big.Int).Mul(effectiveGasPrice, gasUsedBig)
``` [3](#0-2) 

Per EIP-4626-style vault favoring, when computing "the amount a user must supply/pay to receive a given effect" the calculation should round up (ceiling) in favor of the protocol/vault. Here the opposite happens: the per-unit price is floored, and the flooring occurs *before* multiplication by `gasUsed`, so the shortfall compounds with gas usage instead of being capped at a single `upc`.

This deduction is invoked on every `MsgExecutePayload` → `ExecutePayloadV2` call, which is directly reachable by an unprivileged external user (any UEA holder), and the collected `gasCost` is subsequently burned via `DeductAndBurnFees`, so any undercharge is a direct, permanent reduction in the fee revenue the protocol actually collects relative to what the EIP-1559 base-fee schedule dictates. [4](#0-3) 

### Impact Explanation
The undercharge per transaction is bounded by `(fractional_upc_component_of_baseFee) * gasUsed`, which can approach just under `1 * gasUsed` `upc` in the worst case. Since `upc` is the smallest denomination (18-decimal-equivalent to `wei`), this is an accounting/economic-correctness bug — a systemic drift between the fee the network's dynamic gas-price mechanism intends to charge and what is actually collected/burned — rather than a way to steal already-escrowed user or protocol funds. It falls under the explicitly in-scope category of "corruption of ... gas fee accounting," but the realistic magnitude per transaction is small relative to typical `upc` fee totals (base fee values observed in genesis/test configs are on the order of `10^9`+ `upc`), so the drift is a rounding/precision defect rather than a directly drainable, high-value exploit.

### Likelihood Explanation
The path is triggered on the default `MsgExecutePayload` flow used by every ordinary UEA transaction, with no privileged actor required — every gas-fee deduction on Push Chain goes through this exact code. Whether the truncation ever matters in practice depends on whether `feemarketKeeper.GetBaseFee` ever returns a value with a non-zero sub-`upc` fractional component, which depends on the feemarket module's (external, `cosmos/evm`-derived) base-fee adjustment formula — this repository does not implement that formula itself, so I cannot fully confirm from this repo alone how often (if ever) a fractional result is produced in practice; the in-repo comment claims it never happens, but does not demonstrate why the dynamic adjustment formula guarantees an integer result.

### Recommendation
Round the final `gasCost` up (ceiling) after multiplying the un-truncated Dec base fee by `gasUsed`, rather than truncating the per-unit price before multiplication — e.g. compute `gasCost` using `LegacyDec` arithmetic (`baseFeeDec.MulInt64(gasUsed).Ceil().TruncateInt()`) so any rounding favors the protocol, consistent with EIP-4626-style vault-favoring semantics. At minimum, remove or verify the "always a whole number of upc" comment/assumption, since it is not proven within this module's code, and add an explicit invariant check (or ceiling) so any future feemarket change that introduces fractional `upc` base fees does not silently under-collect protocol fees.

### Proof of Concept
Not directly demonstrable purely from this repository, since it depends on `feemarketKeeper.GetBaseFee` (from the imported `cosmos/evm` `feemarket` module) actually returning a value with a non-zero fractional-`upc` component after its dynamic EIP-1559 adjustment; a full PoC would require exercising the base-fee adjustment across blocks (varying `gasUsed` vs `gasTarget`) in an integration test to confirm `GetBaseFee` returns e.g. `1000000000.500000000000000000`, then calling `ExecutePayloadV2` and observing `DeductAndBurnFees` collects `1000000000 * gasUsed` `upc` instead of the mathematically correct (rounded-up) `1000000001 * gasUsed` `upc`.

	baseFee sdkmath.LegacyDec,
	maxFeePerGas *big.Int,
	maxPriorityFeePerGas *big.Int,
	gasUsed uint64,
) (*big.Int, error) {
	baseFeeBig := baseFee.BigInt()
	// @dev: LegacyDec stores values with 18-decimal precision internally, so 1 upc = 1e18
	// in the LegacyDec representation. Since 1 upc is the smallest denomination (like wei
	// in Ethereum), the base fee is always a whole number of upc -- no fractional upc exists.
	// This division unwraps the LegacyDec encoding back to the actual upc amount.
	// Note: baseFee.BigInt() returns a reference to the internal big.Int; the in-place Div
	// mutates it, which is safe here since baseFee is a local value-type copy.
	baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))

	// Step 1: Validate maxFeePerGas >= baseFee
	if maxFeePerGas.Cmp(baseFeeBig) < 0 {
		return nil, fmt.Errorf("maxFeePerGas (%s) cannot be less than baseFee (%s)", maxFeePerGas, baseFeeBig)
	}

	// tipPlusBase := maxFeePerGas

	// @dev: Currently, since we are not using maxPriorityFeePerGas, effectiveGasPrice is just baseFee
