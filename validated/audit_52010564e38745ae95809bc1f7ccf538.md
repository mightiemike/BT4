### Title
Unprotected Factory Implementation/Proxy `initialize()` Allows Attacker to Claim Factory Ownership and Hijack UEA Deployment - (`x/uexecutor/keeper/genesis.go`)

### Summary
The `FactoryV1` proxy and its implementation contract that mints every `UEA` (Universal Executor Account) on Push Chain are deployed at genesis by directly injecting runtime bytecode and manually writing EIP-1967 storage slots, never by an actual constructor/deployment transaction and never followed by a call to `initialize(initialOwner)`. This is the exact "uninitialized implementation" bug class from the report: nothing petrifies the implementation, and nothing claims ownership on behalf of the protocol, so the first unprivileged caller to invoke `initialize` — on either the proxy or the raw implementation address — becomes the `Factory` owner.

### Finding Description
`deployFactoryEA` in [1](#0-0)  deploys three pieces at genesis:
- `deployFactoryImplContract` writes `FactoryImplRuntimeBytecode` directly to `FACTORY_IMPL_ADDRESS_HEX` via `evmKeeper.SetAccount`/`SetCode` [2](#0-1) .
- `deployProxyAdminContract` similarly injects the `ProxyAdmin` bytecode and directly sets its owner storage slot [3](#0-2) .
- `deployFactoryProxy` injects the transparent-proxy bytecode and writes the EIP-1967 admin/implementation slots directly, without ever delegatecalling into `initialize` [4](#0-3) .

Because the implementation and proxy accounts are created by directly setting `CodeHash`/state via `SetAccount`/`SetCode` rather than through a real `CREATE`/constructor execution, any Solidity constructor logic in `FactoryV1` (e.g., OpenZeppelin's `_disableInitializers()` used to "petrify" implementation contracts) never runs. The `initialize(address initialOwner)` selector (`c4d66de8`, visible inside the embedded `FactoryImplRuntimeBytecode` dispatch table) remains callable by anyone, and the `FactoryV1ABI` used elsewhere in the codebase explicitly exposes it as a plain external function with no access control described: [5](#0-4) .

Confirming there is no protected production call to `initialize`: a full repository search shows `initialize`/`setUEAProxyImplementation` are only invoked from `test/utils/contracts_setup.go`, which is test-only setup code [6](#0-5) . `InitGenesis` in the real keeper never calls `initialize` after `deployFactoryEA` [7](#0-6) .

`FactoryV1` (deployed behind this proxy) is the contract that computes and deploys every `UEA` for the whole chain, gated by `setUEAProxyImplementation` — the address the factory delegatecalls into to create new smart accounts, per `x/uexecutor/keeper/evm.go` and the deploy path used throughout inbound execution (`k.DeployUEAV2` / `k.CallFactoryToDeployUEA`) [8](#0-7) [9](#0-8) .

### Impact Explanation
Any unprivileged attacker who submits an EVM transaction calling `initialize(attackerAddress)` on the `FactoryV1` proxy (`FACTORY_PROXY_ADDRESS_HEX`) — or directly on the raw implementation address `FACTORY_IMPL_ADDRESS_HEX` — before any legitimate initialization occurs becomes the recorded `owner()` of the factory. As owner, the attacker can then call `setUEAProxyImplementation(maliciousImpl)`, redirecting every subsequently deployed `UEA` (for every user's cross-chain deposit / `ExecutePayload` / auto-deploy flow) to attacker-controlled bytecode. Since `x/uexecutor` auto-deploys UEAs for arbitrary inbound users via `DeployUEAV2` whenever funds arrive or `ExecutePayload` is called [10](#0-9) , this gives the attacker the ability to intercept, redirect, or drain funds and execute arbitrary logic under the identity of every future UEA created on the chain — a systemic, unauthorized-UEA-execution and fund-draining impact squarely within the "universal execution path" and "unauthorized UEA execution" scope.

### Likelihood Explanation
This is a race-to-claim issue exploitable by any unprivileged party the moment the chain (or a fresh deployment/upgrade re-running this genesis code path) starts, requiring only a single ordinary EVM transaction — no validator, node, or key compromise needed. The window is closed only if some out-of-repo, off-chain/manual initialization transaction happens to land first, which is not enforced or guaranteed anywhere in the scoped Go code; the initialization call is absent from `InitGenesis` entirely.

### Recommendation
Petrify `FactoryV1`'s implementation so it cannot be independently initialized (e.g., have the constructor call `_disableInitializers()` — but since bytecode is injected directly via `SetCode`, this must instead be enforced by writing the "initialized" flag storage slot directly in `deployFactoryImplContract`, exactly mirroring how `deployProxyAdminContract` already directly seeds the owner slot). Additionally, `deployFactoryProxy` should have `InitGenesis` immediately perform a `DerivedEVMCall` invoking `initialize(<protocol-controlled owner, e.g. the uexecutor module account or governance address>)` atomically within the same genesis flow, before any other transaction can be included in a block, so no external caller can front-run it.

### Proof of Concept
1. Deploy/start a node from genesis; `InitGenesis` runs `deployFactoryEA`, writing bytecode and EIP-1967 slots for `FactoryV1` at `FACTORY_PROXY_ADDRESS_HEX` and `FACTORY_IMPL_ADDRESS_HEX`, but issues no `initialize` call (see `x/uexecutor/keeper/genesis.go` and `keeper.go` `InitGenesis`).
2. Before any legitimate/administrative initialization transaction is broadcast, an attacker submits an EVM transaction: `FactoryV1(FACTORY_PROXY_ADDRESS_HEX).initialize(attackerAddr)` (selector `c4d66de8`), using the `FactoryV1ABI` `initialize` entry [5](#0-4) .
3. `owner()` on the proxy now returns `attackerAddr`.
4. Attacker calls `setUEAProxyImplementation(maliciousUEAImpl)` [11](#0-10) , making every subsequent `deployUEA` call (triggered by ordinary user deposits/payload execution through `k.DeployUEAV2`) instantiate a UEA proxy pointing at attacker-controlled logic.
5. Any user whose UEA is deployed from that point on has their smart account controlled by attacker logic, enabling fund theft on deposit/execution.

func deployFactoryProxy(ctx context.Context, evmKeeper types.EVMKeeper) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	proxyAddress := common.HexToAddress(types.FACTORY_PROXY_ADDRESS_HEX)
	proxyAdminOwner := common.HexToAddress(types.PROXY_ADMIN_ADDRESS_HEX)
	factoryImplAddress := common.HexToAddress(types.FACTORY_IMPL_ADDRESS_HEX)

	// Compute the code hash from the runtime bytecode
	codeHash := crypto.Keccak256(types.ProxyRuntimeBytecode)

	// Create the EVM account object
	evmAccount := statedb.Account{
		Nonce:    1,             // to prevent tx nonce=0 conflicts
		Balance:  new(uint256.Int), // zero balance by default
		CodeHash: codeHash,      // link to deployed code
	}

	// Set the EVM account with the factory proxy contract
	err := evmKeeper.SetAccount(sdkCtx, proxyAddress, evmAccount)
	if err != nil {
		panic("failed to set factory proxy contract account: " + err.Error())
	}

	// Store the runtime bytecode linked to the code hash
	evmKeeper.SetCode(sdkCtx, codeHash, types.ProxyRuntimeBytecode)

	// Update proxyAdmin Slot with the proxyAdmin owner address (left padded to 32 bytes)
	evmKeeper.SetState(sdkCtx, proxyAddress, types.PROXY_ADMIN_SLOT, common.LeftPadBytes(proxyAdminOwner.Bytes(), 32))

	// Update proxyImplementation Slot with the factory implementation address (left padded to 32 bytes)
	evmKeeper.SetState(sdkCtx, proxyAddress, types.PROXY_IMPLEMENTATION_SLOT, common.LeftPadBytes(factoryImplAddress.Bytes(), 32))
}

func setupFactoryContract(

		app,

func (k *Keeper) InitGenesis(ctx context.Context, data *types.GenesisState) error {

	if err := data.Params.ValidateBasic(); err != nil {
		return err
	}

	// Only deploy factory contracts on fresh genesis, not on import from export.
	// Re-deploying on import would overwrite existing EVM state or cause nonce collisions.
	if !data.Exported {
		deployFactoryEA(ctx, k.evmKeeper)
	}

	if err := k.Params.Set(ctx, data.Params); err != nil {
		return err
	}

// CallFactoryToDeployUEA deploys a new UEA using factory contract
// Returns deployment response or error if deployment fails
func (k Keeper) CallFactoryToDeployUEA(
	ctx sdk.Context,
	from, factoryAddr common.Address,
	universalAccount *types.UniversalAccountId,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: deployUEA",
		"factory", factoryAddr.Hex(),
		"chain_namespace", universalAccount.ChainNamespace,
		"chain_id", universalAccount.ChainId,
		"owner", universalAccount.Owner,
	)

	abi, err := types.ParseFactoryABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse factory ABI")
	}

	abiUniversalAccount, err := types.NewAbiUniversalAccountId(universalAccount)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal account")
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,        // who is sending the transaction
		factoryAddr, // destination: FactoryV1 contract
		big.NewInt(0),
		nil,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"deployUEA",
		abiUniversalAccount,
	)
}
