## Analysis

I reviewed `RentReclaimer.isOldEnough` at [1](#0-0)  and the calling sweep logic at [2](#0-1) .

The vulnerability is real and reachable by an unprivileged attacker.

### Title
Unprivileged attacker can permanently block rent reclamation via `isOldEnough`'s reliance on unauthenticated "most recent signature touching address" - (File: `universalClient/chains/svm/rent_reclaimer.go`)

### Summary
`isOldEnough` determines whether an orphaned `StoredIxData` PDA is safe to close by querying `GetSignaturesForAddressWithOpts` for the PDA and checking the block time of the single most recent signature that references it: [3](#0-2) . Solana's `getSignaturesForAddress` RPC indexes *any* transaction that lists the address among its account keys — success or failure, and regardless of whether the account is writable or even used meaningfully by the invoked instruction. This means the "age" check is not actually gated on the PDA's creation event; it is gated on the timestamp of the last transaction that happens to *reference* the address at all.

### Finding Description
The orphan PDA address is discoverable by anyone via the same `getProgramAccounts` mechanism the reclaimer itself uses (`discoverOrphans`, [4](#0-3) ), since it is simply a `Memcmp` filter over the gateway program's public account state — no privileged access is required.

Once an attacker knows the PDA address, they can submit cheap, ordinary Solana transactions (e.g., a `SystemProgram` transfer with the PDA appended as an extra non-signer/non-writable `AccountMeta`) that merely reference the PDA in the transaction's account-keys list. This transaction does not need to succeed, does not need to write to the PDA, and does not require any privileged relayer/gateway authority — it is a standard, low-cost, user-submitted transaction. Each such transaction refreshes the "most recent signature" timestamp for that address as seen by `GetSignaturesForAddressWithOpts`.

Because `isOldEnough` unconditionally trusts `sigs[0].BlockTime` as a proxy for "PDA age" (comment: "For StoredIxData PDAs, that's effectively the PDA's age (they only ever see one tx...)"), this assumption is falsifiable by any external party. An attacker repeating such a transaction at an interval shorter than `minAge` (10 minutes default, floor of 1 minute per `rentReclaimMinPDAAgeFloor`) keeps `age >= r.minAge` perpetually false, so `runOnce` perpetually treats the account as "skipped_young" and never invokes `closeOrphan`.

### Impact Explanation
This indefinitely blocks reclamation of rent (protocol/relayer-controlled funds, ~0.002 SOL per orphaned PDA per the file's own comment) from any orphaned `StoredIxData` accounts the attacker targets. Since the attack requires only periodic low-fee transactions (well below any network-flooding threshold — roughly one transaction every <10 minutes per targeted PDA) and no privileged role, it satisfies the in-scope impact category of "permanent freezing... of protocol-controlled funds" and "denial of service... not network-level... reachable without privileged control."

### Likelihood Explanation
High. The PDA address is public, the technique (appending an unrelated account to a cheap instruction) is a standard Solana pattern, and no authentication or ownership check gates who can cause a transaction to reference an arbitrary account. The attacker does not need to interact with the gateway program at all.

### Recommendation
Do not rely on `getSignaturesForAddress`'s "any transaction referencing this address" semantics as a proxy for PDA creation time. Instead, derive age from the actual account creation, e.g., by tracking the slot/blocktime at which `discoverOrphans` (or the underlying `store_execute_ix_data` instruction) first observed the account, using `getSignaturesForAddress` with `until`/pagination to find the *earliest* (creation) signature rather than trusting the most recent one, or by recording creation time in local state the first time an orphan is discovered, and gating `closeOrphan` on that locally tracked timestamp instead of a spoofable on-chain signal.

### Proof of Concept
1. Attacker calls `getProgramAccounts` on the gateway program with the same discriminator/refund-recipient filters used in `discoverOrphans` to learn the orphan PDA's address.
2. Attacker submits a `SystemProgram.Transfer` transaction between two attacker-controlled accounts, with the orphan PDA pubkey appended as an extra read-only `AccountMeta` to the instruction (or any instruction that tolerates/ignores extra accounts).
3. Repeat step 2 every < `minAge` (e.g., every 8 minutes).
4. Observe that `RentReclaimer.runOnce`'s call to `isOldEnough` for that PDA always returns `age < minAge`, so `closeOrphan` is never invoked and the sweep never transitions the account to closed. [1](#0-0)

		opts := &rpc.GetProgramAccountsOpts{
			Commitment: rpc.CommitmentFinalized,
			Filters: []rpc.RPCFilter{
				// match account type
				{Memcmp: &rpc.RPCFilterMemcmp{Offset: 0, Bytes: solana.Base58(storedIxDataAccountDiscriminator)}},

// isOldEnough reports whether the most recent tx touching addr is at least
// minAge old. For StoredIxData PDAs, that's effectively the PDA's age (they
// only ever see one tx — their creating store_execute_ix_data).
func (r *RentReclaimer) isOldEnough(ctx context.Context, addr solana.PublicKey) (bool, error) {
	limit := signatureAgeProbeLimit
	var sigs []*rpc.TransactionSignature
	err := r.builder.rpcClient.executeWithFailover(ctx, "get_signatures_for_address", func(client *rpc.Client) error {
		resp, innerErr := client.GetSignaturesForAddressWithOpts(ctx, addr, &rpc.GetSignaturesForAddressOpts{
			Limit: &limit,
		})
		if innerErr != nil {
			return innerErr
		}
		sigs = resp
		return nil
	})
	if err != nil || len(sigs) == 0 {
		return false, err
	}
	if sigs[0].BlockTime == nil {
		return false, nil
	}
	age := time.Since(time.Unix(int64(*sigs[0].BlockTime), 0))
	return age >= r.minAge, nil
}
