### Title
`accept_new_txs` pause flag is only enforced on the HTTP transaction-submission path, not on the P2P mempool-propagation path - (File: `crates/apollo_mempool_p2p/src/runner/mod.rs`)

### Summary
The reported bug class is: a "pause" check that gates one entry point to a state-changing operation but is skipped on an alternate/retry entry point that reaches the same operation, letting the guarded action occur while the system is supposed to be paused. In this sequencer codebase, the `HttpServerDynamicConfig::accept_new_txs` flag is the mechanism operators use to stop a node from accepting new transactions [1](#0-0) . It is explicitly checked in the two HTTP handlers before a transaction is forwarded to the gateway.

### Finding Description
`add_rpc_tx` and `add_tx` both call `check_new_transactions_are_allowed(accept_new_txs)` before invoking `add_tx_inner`, which forwards the transaction to `app_state.gateway_client.add_tx(...)`: [2](#0-1) 

However, the gateway is also reachable through an entirely separate ingestion path: the mempool P2P runner. When another peer broadcasts a transaction batch over the network, `MempoolP2pRunner` decodes it and calls `gateway_client.add_tx(GatewayInput { rpc_tx, message_metadata })` directly, with no reference to `accept_new_txs` or any equivalent "paused" check: [3](#0-2) 

The only gate on this path is a semaphore-based backpressure limit (`max_concurrent_gateway_requests`), which has nothing to do with the operator's intent to stop accepting transactions: [4](#0-3) 

The gateway's own `add_tx_inner` performs stateless/stateful validation and permission checks, but likewise contains no `accept_new_txs`/pause check: [5](#0-4) 

This mirrors the `OmnichainGovernanceExecutor` pattern exactly: the guard (`whenNotPaused` / `check_new_transactions_are_allowed`) is attached to one caller of the sensitive operation (`_blockingLzReceive` / the HTTP handlers) but not to another caller that reaches the same operation (`retryMessage`→`_nonblockingLzReceive` / the P2P runner→`gateway_client.add_tx`).

### Impact Explanation
When an operator sets `accept_new_txs = false` (e.g., during an incident, a planned pause, or to drain the node before maintenance/upgrade), the operator's expectation is that the node stops admitting new transactions into its mempool. Because the P2P ingestion path bypasses this check entirely, an unprivileged network peer can still get transactions admitted into the "paused" node's mempool simply by broadcasting them over the mempool-p2p topic — the transaction still reaches `gateway_client.add_tx` → mempool `add_tx`, is validated and queued, and can be proposed/included in a block by that node. This defeats the purpose of the pause control and could interfere with maintenance, incident response, or coordinated network procedures that rely on nodes actually halting admission of new transactions, potentially resulting in a node continuing to build/propose blocks with transactions it should have refused, i.e., unauthorized state-changing action occurring despite the node being paused.

### Likelihood Explanation
High reachability: any peer connected via the mempool-p2p network topic can trigger this path by simply broadcasting a transaction batch; no special privileges are required. The condition (operator having set `accept_new_txs=false` while the P2P listener is still running) is the normal operating mode for this flag, since nothing in the runner shuts down or gates on it.

### Recommendation
Enforce the `accept_new_txs` dynamic-config check (or an equivalent pause gate) inside `MempoolP2pRunner`'s message-handling loop before dispatching `gateway_client.add_tx` for peer-broadcast transactions — analogous to fixing the LayerZero contract by moving the `whenNotPaused` guard onto the shared `_nonblockingLzReceive` function rather than only the entry point (`_blockingLzReceive`). The check should live in the single code path reachable by both callers (e.g., inside `gateway_client.add_tx` / `add_tx_inner` itself, or the shared `AppState`), so the P2P route cannot silently bypass it.

### Proof of Concept
1. Operator sets `http_server_config.dynamic_config.accept_new_txs = false` on Sequencer A, expecting it to stop admitting new transactions (verified via `is_ready`, which correctly returns `SERVICE_UNAVAILABLE`) [6](#0-5) .
2. An attacker/peer submits a transaction to Sequencer B's HTTP endpoint (or is itself a network peer), and Sequencer B's mempool-p2p propagator broadcasts it over the p2p transaction-batch topic [7](#0-6) .
3. Sequencer A's `MempoolP2pRunner` receives the broadcast batch and, for each transaction, calls `gateway_client.add_tx(GatewayInput { rpc_tx, message_metadata })` directly — with no `accept_new_txs` check anywhere in this code path [3](#0-2) .
4. The transaction passes gateway validation and is added to Sequencer A's mempool despite `accept_new_txs = false`, proving the pause is bypassable via the P2P path exactly as `retryMessage` bypassed `OmnichainGovernanceExecutor`'s pause via `_nonblockingLzReceive`.
