### Title
Hardcoded `CLEAN_INTERVAL`/`SHRINK_INTERVAL` assume default snapshot cadence, starving `clean_accounts`/`shrink_candidate_slots` when snapshot intervals are configured differently - ([File: runtime/src/accounts_background_service.rs])

### Summary
`AccountsBackgroundService`'s main loop uses two hardcoded timing constants, `CLEAN_INTERVAL` (50s) and `SHRINK_INTERVAL` (1s), to decide when to run `clean_accounts()` and `shrink_candidate_slots()`. The comment explicitly states these values were chosen assuming the *default* incremental snapshot interval of 100 slots (~40s) [1](#0-0) . This is the same bug class as the Chainlink report: a single hardcoded timing constant is applied uniformly, but the actual cadence it is compared against (here, the configurable incremental-snapshot/accounts-hash interval) can differ per deployment, causing the constant to silently stop doing its job.

### Finding Description
Every iteration of the ABS loop, whenever a snapshot request was handled, `previous_clean_time` and `previous_shrink_time` are unconditionally reset to `Instant::now()`, regardless of whether an actual explicit `clean_accounts()`/`shrink_candidate_slots()` call happened on that path: [2](#0-1) 

Only when *no* snapshot request was handled in that iteration does the loop check `duration_since_previous_clean > CLEAN_INTERVAL` / `duration_since_previous_shrink > SHRINK_INTERVAL` and explicitly invoke `clean_accounts()`, `shrink_ancient_slots()`, and `shrink_candidate_slots()`: [3](#0-2) 

`CLEAN_INTERVAL`/`SHRINK_INTERVAL` are fixed constants baked in assuming the incremental snapshot request cadence is ~40s by default [1](#0-0) . The incremental snapshot interval (`accounts_hash_interval_slots` / `incremental_snapshot_archive_interval_slots`), however, is a configurable validator CLI option [4](#0-3) , not tied at all to this hardcoded constant. If an operator configures a shorter incremental snapshot interval than `SHRINK_INTERVAL` (1s) — or even close to `CLEAN_INTERVAL` (50s) — the `if let Some(snapshot_handle_result)` branch will be taken on nearly every loop iteration, continuously resetting `previous_shrink_time`/`previous_clean_time` before the `else` branch (which performs the actual explicit `clean_accounts`/`shrink_candidate_slots` calls) ever gets a chance to run. This is directly analogous to the Chainlink report: the same fixed "heartbeat" (interval constant) is compared against a cadence that varies by deployment configuration, and when that cadence diverges from the assumed default, the protection logic silently stops functioning instead of erroring out.

### Impact Explanation
Starving `shrink_candidate_slots()` and the explicit `clean_accounts()` call leaves storage entries with dead/superseded account versions unshrunk and unswept indefinitely. Over time this produces unbounded growth of AccountsDB storage (append vecs retaining garbage instead of being compacted), disproportionate disk usage, and increased CPU/I/O cost for later operations (scans, index rebuilds, snapshot generation) that must traverse the bloated storage — matching the accepted "disproportionate storage and CPU cost" impact class. Note that periodic cleaning inside the snapshot-generation path itself does still bound `last_cleaned_slot` (per the proof comment) [5](#0-4) , so this is a compaction/shrink-starvation and storage-bloat issue rather than a hard correctness violation.

### Likelihood Explanation
Likelihood depends on operator configuration: default deployments (100-slot incremental snapshot interval, ~40s) are safe since `SHRINK_INTERVAL` (1s) is far shorter, giving many non-snapshot iterations to shrink. However, any validator/cluster configuration that reduces the incremental snapshot cadence (a supported, documented CLI knob) below or near `SHRINK_INTERVAL`/`CLEAN_INTERVAL` would trigger sustained starvation without any explicit error or warning, making this a config-triggerable, silent degradation rather than a purely theoretical concern.

### Recommendation
Do not unconditionally reset `previous_clean_time`/`previous_shrink_time` merely because a snapshot request was handled; only reset them when the corresponding compaction work (clean/shrink) actually ran. Alternatively, derive `CLEAN_INTERVAL`/`SHRINK_INTERVAL` dynamically from the configured incremental snapshot interval rather than hardcoding an assumption about the default, mirroring the Chainlink mitigation of parameterizing the heartbeat per configuration instead of using one constant for all deployments.

### Proof of Concept
1. Start a validator with `--incremental-snapshot-archive-interval-slots` set well below the default (e.g., a few slots), so snapshot requests are handled on nearly every ABS loop iteration.
2. In `AccountsBackgroundService::new`'s loop, the `if let Some(snapshot_handle_result) = snapshot_handle_result` branch is taken almost every iteration, resetting `previous_clean_time`/`previous_shrink_time` each time [6](#0-5) .
3. `duration_since_previous_shrink` and `duration_since_previous_clean` never exceed `SHRINK_INTERVAL`/`CLEAN_INTERVAL`, so the `else` branch containing `bank.rc.accounts.accounts_db.clean_accounts(...)`, `bank.shrink_ancient_slots()`, and `bank.shrink_candidate_slots()` is never reached [7](#0-6) .
4. Dead/shrinkable storage accumulates without bound as the validator continues to run, growing AccountsDB storage disproportionately relative to live account data.
