Confirmed: `MerchantCustomAuth` (ShopifyAdmin distribution) is documented/tested with `isEmbeddedApp: false` [1](#0-0) . With `isEmbeddedApp: false`, `validateShopAndHostParams` is a no-op (`if (config.isEmbeddedApp) {...}` guards the entire body) [2](#0-1) , and `getSessionTokenContext` falls straight to `const shop = url.searchParams.get('shop')!;` with no null/empty check and no sanitization [3](#0-2) . That raw (possibly `null`) `shop` is passed into `strategy.authenticate(request, {..., shop})`, which for `MerchantCustomAuth` calls `this.api.session.customAppSession(shop)` with no validation [4](#0-3) , and `customAppSession` calls `sanitizeShop(config)(shop, true)`, which throws `InvalidShopError` for empty/invalid shop [5](#0-4) .

The top-level `authenticateAdmin` wrapper only special-cases `Response` instances in its catch block; any other thrown error (including `InvalidShopError`, which is not a `Response`) is simply rethrown as-is [6](#0-5) . So in a non-embedded merchant-custom-app configuration, a request to the app with no `shop` query parameter results in an uncaught `InvalidShopError` propagating out of `authenticate.admin()`, rather than a handled HTTP `Response`.

### Title
Uncaught `InvalidShopError` crash in `MerchantCustomAuth.authenticate` for non-embedded custom apps missing `shop` param - (File: packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/merchant-custom-app.ts)

### Summary
For custom apps (`AppDistribution.ShopifyAdmin`) configured as non-embedded (`isEmbeddedApp: false`, the officially documented/tested configuration for this strategy), an unauthenticated request omitting the `shop` query parameter bypasses all shop validation and causes `customAppSession` to throw an uncaught `InvalidShopError`, crashing the `authenticate.admin()` call instead of returning a handled `Response`.

### Finding Description
`validateShopAndHostParams` only validates `shop`/`host` when `config.isEmbeddedApp` is true [7](#0-6) . For non-embedded custom apps this check is skipped entirely. `getSessionTokenContext` also branches on `config.isEmbeddedApp` (not on distribution), so a non-embedded custom app falls through to `const shop = url.searchParams.get('shop')!;` with no null check and no sanitization [8](#0-7) . This unvalidated `shop` (potentially `null`) is handed to `MerchantCustomAuth.authenticate`, which passes it directly to `this.api.session.customAppSession(shop)` without any check [9](#0-8) . `customAppSession` internally calls `sanitizeShop(config)(shop, true)`, and passing `true` as the second argument makes `sanitizeShop` throw `InvalidShopError` rather than silently returning `undefined` for an invalid/missing shop [5](#0-4) . The outer `authenticateAdmin` try/catch only converts `Response` instances into CORS-headered responses; all other errors (including `InvalidShopError`) are rethrown unmodified [6](#0-5) , so the exception propagates as a raw, unhandled library error out of `authenticate.admin()` into the host app's route handler.

### Impact Explanation
This is a low-severity denial-of-service / robustness bug: an anonymous request to any route protected by `authenticate.admin()` in a non-embedded merchant-custom-app configuration, with the `shop` query parameter omitted, causes an unhandled exception instead of a clean 4xx `Response`. Depending on the host framework's error boundary handling, this could surface as an unstyled 500 error or crash the request; it does not lead to cross-tenant access, forged sessions, or secret disclosure since `customAppSession` never returns a valid/usable session in this path — it throws before that. This maps to Shopify's "Denial of Service" bounty class at most, scoped to the authenticate() request path.

### Likelihood Explanation
Easy to trigger: the attacker only needs to send an unauthenticated GET request without the `shop` query parameter to any admin route of a merchant-custom-app deployed with `isEmbeddedApp: false` (the config documented/tested for this exact strategy) [1](#0-0) . No secrets, tokens, or privileged access are required — repeatable on every request.

### Recommendation
In `MerchantCustomAuth.authenticate`, validate `sessionContext.shop` before calling `this.api.session.customAppSession(shop)` and throw/return a proper `Response` (e.g. 400) when the shop is missing or invalid, rather than letting `InvalidShopError` propagate. Alternatively, wrap the `customAppSession` call in a try/catch that converts `InvalidShopError` into a `Response`, and/or add an explicit shop presence/sanitization check in `getSessionTokenContext`'s non-embedded/custom-app branch regardless of the `isEmbeddedApp` flag.
