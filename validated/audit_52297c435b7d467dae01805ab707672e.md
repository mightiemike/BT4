## Title
`ensure_match_transaction_info` never validates the state-checkpoint (JMT) root hash, so `replay-verify` accepts divergent state as correct — ([File: types/src/transaction/mod.rs])

### Summary
The report's core lesson is that a function whose entire purpose is to assert "the committed value equals the correctly-computed value" can silently skip the one invariant that actually matters (PoolTogether's `_currentExchangeRate` accepted an under-collateralized value as the new baseline). The Aptos-native analog is `TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs`, which is the sole correctness check used by the `replay_on_archive` / debugger tooling to confirm that locally re-executed transactions match the authenticated, on-chain `TransactionInfo`. It checks status, gas, write-set hash, and event root — but never checks `state_checkpoint_hash` (the state/Jellyfish-Merkle root that is actually part of the consensus-authenticated `TransactionInfo` and covered by the transaction accumulator proof).

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  and only compares status, gas, write-set hash (`state_change_hash`) and event root hash. It never reads or compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. The function's own comment documents this gap explicitly: [2](#0-1) .

This function is the only verification performed by the archive replay-verification tool, `storage/db-tool/src/replay_on_archive.rs`. In `execute_and_verify`, the executed outputs from a freshly re-executed block are compared to the backup's expected `TransactionInfo`/write-set/events using only `ensure_match_transaction_info`; no separate check of the resulting state root (JMT root) is performed: [3](#0-2) . This code path re-executes directly through `AptosVMBlockExecutor::execute_block` (not through the normal executor pipeline's `DoStateCheckpoint`, which is where `state_checkpoint_hash` normally gets validated during live chunk-executor/state-sync flows, e.g. [4](#0-3) ). Because `replay_on_archive` bypasses that pipeline and relies exclusively on `ensure_match_transaction_info`, the state root is never independently recomputed and compared against the authenticated `state_checkpoint_hash` carried by the backup's `TransactionInfo`.

The same gap affects the CLI/debugger transaction-replay path, which calls the identical function: [5](#0-4) .

### Impact Explanation
`replay-verify` (via `storage/db-tool/src/replay_on_archive.rs`) is the tool operators and auditors use to confirm that a historical/archived ledger segment — retrieved from backups or an archive node — is internally consistent with independent local re-execution, i.e., to detect state divergence, backup corruption, or execution non-determinism that produced a different ledger state than what was authenticated by consensus. Because the state root is never actually checked, a state root divergence (whatever its root cause — non-determinism, storage corruption, an execution bug reintroducing a different state at the same version) will be reported as "replay succeeded" even though the durable state data diverges from the VM's/consensus's correct result. This directly matches the required impact class: committed/replayed state that differs from the correct VM result is accepted as valid, and a state-commitment invariant (the state-checkpoint hash bound into the accumulator-authenticated `TransactionInfo`) is never verified by the tool built for that purpose.

### Likelihood Explanation
This isn't a probabilistic race — it's a deterministic, always-present gap in the verification logic: every call to `ensure_match_transaction_info` (including every replay-verify run over backups) skips the state root check unconditionally. Any latent state-divergence bug elsewhere in the codebase (execution, storage, or backup pipeline) would go undetected by this tool 100% of the time, and the tool's operators have no signal that this check is missing since `ensure_match_transaction_info` returns `Ok(())`.

### Recommendation
In `ensure_match_transaction_info`, after computing the write set and events, recompute the state-checkpoint hash from `self.write_set()` applied on top of the parent state (or otherwise obtain the resulting JMT root for versions where a checkpoint exists) and assert it equals `txn_info.state_checkpoint_hash()`. Do the same for `hot_state_checkpoint_hash()` and `position_state_checkpoint_hash()` before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is turned on, exactly as the existing TODO comment states. At minimum, `replay_on_archive.rs` should perform its own state-root comparison against the backup-provided `TransactionInfo` if the JMT root is available in the replay context.

### Proof of Concept
1. Run `db-tool replay-on-archive` (or `replay-verify`) against a backup segment whose write-set/events/gas/status are legitimate for their `TransactionInfo`, but whose `state_checkpoint_hash` in the backup's `TransactionInfo` does not correspond to the true root that results from applying that write set to the correct parent state (e.g., simulate a corrupted/mismatched backup snapshot, or a hypothetical non-deterministic execution bug that only affects the resulting persisted state slice, not the write set itself).
2. `execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` calls `ensure_match_transaction_info`, which passes because status/gas/write-set-hash/event-root all match.
3. The tool reports "ReplayVerify coordinator succeeded" (`storage/db-tool/src/replay_verify.rs` lines 88-102) even though the actual committed/persisted state root diverges from what local re-execution would produce — the exact "committed value looks fine even though the invariant securing it was never checked" pattern from the external report.
