## Finding

### Title
Wallet Contract pays the relayer fee via an unconditional promise before the underlying transfer/call is confirmed to succeed - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The reported Vault.vy bug is a class of "pay-out before verifying the paired operation succeeded" flaw: `_reduce_position` reduces accounting state by `_reduce_by_amount` without checking that the swap actually delivered that amount. The analogous pattern exists in nearcore's NEAR Wallet Contract (`runtime/near-wallet-contract`), reachable by any unprivileged relayer/transaction sender calling `rlp_execute`.

### Finding Description
In `inner_rlp_execute` [1](#0-0) , once an RLP-encoded Ethereum transaction is parsed into a `TransactionKind`, the code checks whether it is an emulated `EOABaseTokenTransfer` or `ERC20Transfer` carrying a non-zero relayer `fee`: [2](#0-1) 

If so, it immediately fires an **independent** `promise_batch_create` / `promise_batch_action_transfer` that pays the `fee` to the relayer (`context.predecessor_account_id`). This fee-payment receipt is *not* chained (`.then(...)`) to the promise that actually performs the requested transfer/call — that promise is built and returned separately at the bottom of the function, dispatched to either the address-registrar lookup, the NEP-141 storage-balance check, or directly to `action_to_promise` [3](#0-2) .

Because the fee-transfer receipt is a sibling receipt rather than a callback continuation, it is dispatched and will execute regardless of whether:
- the underlying NEAR/ERC-20 transfer to the intended recipient later fails (e.g., token contract call reverts, `rlp_execute_callback` observes `PromiseResult::Failed` and only refunds the *caller's attached deposit*, not the fee that was already paid out, per [4](#0-3) ), or
- for the `EOABaseTokenTransfer` with `address_check: Some(_)` path, the address-registrar callback later determines the target is actually a named account and rejects the whole action / bans the relayer (`address_check_callback`, [5](#0-4) ) — the fee promise was already dispatched before this check runs.

This mirrors the audit report's root cause exactly: state/value is committed based on an assumed successful downstream operation, without verifying (or making the payout contingent on) that operation's actual outcome.

### Impact Explanation
Any relayer submitting a base-token or ERC-20 transfer with a non-zero fee via the Wallet Contract's `rlp_execute` is guaranteed to receive the fee from the wallet's balance even in scenarios where the user's intended transfer does not complete. This is an unauthorized value movement out of the wallet account: the account owner pays a fee for a service (relayed transfer) that was not delivered, and a malicious or careless relayer can repeatedly cause failing/rejected transfers (e.g. targeting a named account via the `address_check` path, or an ERC-20 transfer to a contract designed to fail) purely to collect the unconditional fee.

### Likelihood Explanation
This requires no privileged access — any relayer (or the wallet owner acting as their own relayer) who can submit an `rlp_execute` transaction can trigger this path by including a non-zero `fee` on an `EOABaseTokenTransfer` (with or without `address_check`) or `ERC20Transfer`. The "only one tx in flight" invariant limits abuse to serial rather than parallel repetition, but does not prevent it.

### Recommendation
Chain the relayer-fee transfer into the same promise as the underlying action (or as a `.then()` step gated on `rlp_execute_callback` observing `PromiseResult::Successful`) so the fee is only paid when the wallet's requested action actually succeeds, mirroring how `caller_deposit` refunds are already conditioned on the callback's promise result.

### Proof of Concept
1. Attacker/relayer signs and submits (as `predecessor_account_id`) an RLP transaction via `rlp_execute` representing an `EOABaseTokenTransfer` with `address_check: Some(addr)` and a non-zero `fee`, where `addr` is known to correspond to an existing named account in the registrar.
2. `inner_rlp_execute` immediately creates and dispatches the fee-transfer promise to the relayer [6](#0-5) .
3. The registrar lookup subsequently resolves `maybe_account_id.is_some()`, causing `address_check_callback` to reject the transaction (return `ExecuteResponse{success:false,...}` or ban the relayer) [7](#0-6) .
4. Net effect: the wallet's balance is debited by `fee` even though the transfer never took place and the transaction is reported as failed.

**Uncertainty**: I was not able to fully trace whether `nonce` increments interact with repeatability limits in a way that fully bounds the number of times this can be exploited per relayer key, nor confirm end-to-end behavior via a live test run (only static code inspection was performed). A Devin session with the full test suite (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/`) would be needed to empirically confirm the fee is retained on a failed/rejected transfer.
