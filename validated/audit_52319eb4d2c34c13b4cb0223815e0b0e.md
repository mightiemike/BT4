### Title
Attacker-controlled `ExtraArgs` decode failure escalates to unrecoverable node panic in Solana gas estimation - ([File: core/capabilities/ccip/ccipsolana/gas_helpers.go])

### Summary
`ExtraDataDecoder.DecodeExtraArgsToMap` correctly guards the `agbinary.Uint128` type assertion for the `GasLimit` field with an `ok` check and returns a clean `error` rather than panicking. However, that clean error is unconditionally converted into a `panic(err)` by `EstimateProvider.CalculateMessageMaxGas`, which calls `CalculateMessageMaxGasWithError` and panics on *any* non-nil error, including ones caused entirely by attacker-supplied `msg.ExtraArgs` bytes. This turns a fully anticipated, handled decode failure into a node-crashing panic reachable from message content on a monitored CCIP lane.

### Finding Description
`DecodeExtraArgsToMap` in `core/capabilities/ccip/ccipsolana/extradatacodec.go` decodes the Borsh-encoded `GenericExtraArgsV2`/`SVMExtraArgsV1` payload from `extraArgs` (attacker/message-sender controlled bytes carried in a CCIP message) and, for the `GasLimit` field, performs: [1](#0-0) 
This is already safe: if the underlying gobinding type for the `GasLimit`-tagged field ever differs from `agbinary.Uint128` (e.g. a forked/updated `fee_quoter` binding, or a crafted byte layout that still parses into a wrong reflected type via `reflect.ValueOf(args)`), the function returns a formatted `error` instead of panicking.

That error propagates cleanly up through `EstimateProvider.CalculateMessageMaxGasWithError` in `core/capabilities/ccip/ccipsolana/gas_helpers.go`: [2](#0-1) 
but the sibling wrapper `CalculateMessageMaxGas`, which is the method actually registered as `GasEstimateProvider` in `PluginConfig` and wired into `execocr3.NewExecutePluginFactory` (`core/capabilities/ccip/oraclecreator/plugin.go`), converts *any* returned error into a hard panic: [3](#0-2) 

Because `msg.ExtraArgs` originates from the CCIP message itself (attacker/message-sender-controlled content on the source chain), any condition that makes `DecodeExtraArgsToMap`/`CalculateMessageMaxGasWithError` return an error—whether it's an unknown tag, a malformed Borsh stream, or the guarded `Uint128` mismatch—results in `CalculateMessageMaxGas` panicking. There is no upstream sanitation, replay/signature check, or rate limit that filters `ExtraArgs` content before it reaches gas estimation used in exec plugin OCR report construction. The identical pattern also exists in `core/capabilities/ccip/ccipevm/gas_helpers.go`.

### Impact Explanation
This is a Denial-of-Service vector: any node running the CCIP exec plugin for a Solana-family lane will panic (and, absent goroutine-level recover, crash or destabilize the OCR reporting job) when it processes a message whose `ExtraArgs` fails to decode as expected. Since gas estimation runs as part of building/validating exec reports over messages sourced from chain, an attacker who can get a message with malformed `ExtraArgs` accepted onto the source chain (a normal, unprivileged sender action, not requiring operator/admin access) can trigger this on every node servicing that lane simultaneously.

### Likelihood Explanation
Feasibility is high and requires no privileged access: the attacker only needs to submit a CCIP message with a `GenericExtraArgsV2`/`SVMExtraArgsV1`-tagged `ExtraArgs` blob that fails Borsh decoding or fails the `Uint128` assertion (e.g., due to a future gobinding drift, but even simpler, a payload that decodes structurally but where the field ends up wrapped differently under `reflect.ValueOf`). It is deterministically repeatable and affects all DON members processing that message.

### Recommendation
Change `EstimateProvider.CalculateMessageMaxGas` in both `ccipsolana/gas_helpers.go` and `ccipevm/gas_helpers.go` to not panic on decode/parsing errors that originate from untrusted `ExtraArgs`/`DestExecData` content. Either: (a) change the `EstimateProvider` interface to return `(uint64, error)` so callers can handle decode failures gracefully (e.g., skip the message, log, or fall back to a conservative default gas amount), or (b) recover from the panic at the call site and treat it as a handled error path. At minimum, distinguish "attacker-controlled decode error" from true programming invariant violations, and never let the former propagate as an unrecovered panic in the OCR report-building path.

### Proof of Concept
Unit test in `core/capabilities/ccip/ccipsolana/gas_helpers_test.go`:
1. Construct a `cciptypes.Message` with `Header.SourceChainSelector` set to a Solana chain selector and `ExtraArgs` set to `evmExtraArgsV2Tag` (or `svmExtraArgsV1Tag`) followed by a Borsh payload deliberately truncated/malformed so that `fee_quoter.GenericExtraArgsV2.UnmarshalWithDecoder` succeeds structurally but the resulting `GasLimit`-tagged field is not `agbinary.Uint128` (or simply force an unmarshal error).
2. Call `ExtraDataDecoder{}.DecodeExtraArgsToMap(msg.ExtraArgs)` directly and assert it returns a clean, non-nil `error` (proves the guarded assertion works as intended).
3. Call `EstimateProvider{extraDataCodec: edc}.CalculateMessageMaxGasWithError(msg)` and assert it returns `(0, err)` with no panic.
4. Call `EstimateProvider{extraDataCodec: edc}.CalculateMessageMaxGas(msg)` wrapped in `assert.Panics(t, func() { ... })`/`require.Panics` and confirm it panics with the same underlying error — documenting that a purely attacker-influenced decode failure crashes the calling goroutine instead of being handled.
