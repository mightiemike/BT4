Investigation is constrained by the remaining budget, but the trail found is strong: the repo already contains an explicit, documented fix for exactly this bug class (a boundary-ambiguous timestamp/height check, analogous to the `_getNextFriday` off-by-window bug), and the fix's own guard has a gap.

### Title
PoX-5 waterfall boundary-ambiguity guard is skipped whenever `pox_5_activation_height` is configured independently of `epoch_4_0.start_height`, allowing the known `active_pox_contract` vs `active_pox_contract_for_cycle` divergence to reach consensus code - (File: stackslib/src/core/mod.rs)

### Summary
`PoxConstants::active_pox_contract` (tip-keyed, strict `>` comparison on burn height) and `PoxConstants::active_pox_contract_for_cycle` / `first_pox_waterfall_block` (cycle-keyed, floor-division based) can disagree about which PoX contract (`pox-4` vs `pox-5`) governs a given block when `pox_5_activation_height` falls on or near a reward-cycle boundary [1](#0-0) , exactly the "boundary-adjacent time-window" bug class described in the external report (a check whose validity range is off relative to the other side's window). The codebase itself documents this divergence and mitigates it by (1) providing a cycle-keyed predicate `active_pox_contract_for_cycle` for all cycle-scoped consensus code [2](#0-1) , and (2) a startup assertion in `validate_nakamoto_transition_schedule` that forbids configuring `pox_5_activation_height` at reward-cycle offsets 0 or 1, where the two predicates are known to disagree [3](#0-2) . However, that assertion is gated behind an early return that only fires when `pox_5_activation_height` exactly equals `epoch_4_0.start_height` [4](#0-3) .

### Finding Description
`static_active_pox_contract` picks the active contract using a tip burn height compared with strict `>` against each activation height [5](#0-4) . `active_pox_contract_for_cycle` instead determines the contract from `first_pox_waterfall_block`, which floor-divides the activation height into a reward cycle via `block_height_to_reward_cycle` and then adds 1 [6](#0-5) . These two boundary semantics are asymmetric, and the repo's own tests document that a `pox_5_activation_height` placed at reward-cycle offset 0 or 1 makes the two predicates return different answers for blocks in the ambiguous window [7](#0-6) , and that mid-prepare-phase activation makes tip-keyed `active_pox_contract` itself return different answers within the same prepare phase (`POX_4` then `POX_5`) even though the cycle-keyed predicate must remain stable [8](#0-7) .

The mitigating assertion in `validate_nakamoto_transition_schedule` is supposed to forbid exactly the configurations that trigger this ambiguity, but it is wrapped in a guard that skips the check entirely unless `pox_5_activation_height == epoch_4_0_start`:
```
let epoch_4_0_start = epoch_4_0.start_height;
let pox_5_activation = u64::from(burnchain.pox_constants.pox_5_activation_height);
if pox_5_activation != epoch_4_0_start {
    return;
}
``` [4](#0-3) 

Nothing else in the repo re-checks the offset-0/1 boundary condition for `pox_5_activation_height` when it is *not* pinned to the Epoch 4.0 start height. Consumers of the cycle-keyed predicate still rely on it being unambiguous: `NakamotoSigners::check_and_handle_prepare_phase_start` explicitly notes that tip-keyed dispatch "can flip mid-prepare-phase" and relies on the cycle-keyed predicate for cycle-stable behavior [9](#0-8) , and `PoxDB::get_reward_addresses_in_cycle` similarly switched to the cycle-keyed predicate specifically to match `first_pox_waterfall_block`'s boundary semantics [10](#0-9) . If the un-guarded activation-height/offset combination is used, the ambiguity these two call sites were fixed against is reintroduced silently, without any startup assertion catching it.

### Impact Explanation
If a chain is configured (test network, or any deployment where `pox_5_activation_height` is not forced equal to the Epoch 4.0 start height) with `pox_5_activation_height` at reward-cycle offset 0 or 1, or inside the prepare phase that computes the first PoX-5 signer set, two conforming nodes/forks that observe the boundary from different sides can derive a different cycle-to-contract mapping for the *same* reward cycle. That changes which reward-set computation path (`get_reward_addresses_pox_4` vs the not-yet-existing PoX-5 branch — note `get_reward_addresses_in_cycle`'s match has no PoX-5 arm and panics with "Chainstate is corrupted" on that input) or which signer set (`pox_4_compute_and_update_signers` vs `pox_5_compute_and_update_signers`) is used for a given cycle. This is a minority-triggerable, unprivileged divergence bounded to the specific activation-height configuration: it produces either a signer-set / reward-set computation that some nodes disagree on (temporary tip disagreement / signer set divergence) or a chainstate-corruption panic in `get_reward_addresses_in_cycle`, both of which are consensus-relevant and match the "High" bar (minority-triggerable static-validation divergence / temporary tip disagreement).

### Likelihood Explanation
This requires a specific network/testnet configuration (an operator picking a `pox_5_activation_height` not pinned to `epoch_4_0.start_height` and landing on the ambiguous offsets), so it is not remotely triggerable by an ordinary user transaction; it is a configuration/validation gap rather than something any unprivileged party can flip on mainnet with existing config. Given the maintainers' explicit awareness of and fix for the boundary problem in the equal-height case, and the pattern of the guard only covering that one case, this is very plausible to be reachable in any deployment (e.g., a testnet or fork) that legitimately sets `pox_5_activation_height` to a value other than `epoch_4_0.start_height`.

### Recommendation
Remove the `if pox_5_activation != epoch_4_0_start { return; }` early-return, or otherwise ensure `validate_nakamoto_transition_schedule` (or an equivalent startup check run unconditionally on `pox_5_activation_height`) always evaluates the "must not fall in prepare phase" and "must not be at reward-cycle offset 0 or 1" assertions regardless of whether `pox_5_activation_height` matches `epoch_4_0.start_height`. Additionally, add an explicit `POX_5_NAME` match arm (or an explicit, documented panic message) in `get_reward_addresses_in_cycle` so a misconfiguration fails loudly and specifically rather than through the generic "unknown contract" corruption panic.

### Proof of Concept
1. Configure a burnchain/testnet with `PoxConstants` such that `epoch_4_0.start_height` is some height `H`, but set `pox_5_activation_height = H + k*reward_cycle_length + 1` (offset 1) or `+0` (offset 0), i.e., not equal to `H` [4](#0-3) .
2. `validate_nakamoto_transition_schedule` returns early and never runs the offset/prepare-phase assertions that would otherwise reject this configuration [11](#0-10) .
3. Boot the node into the reward cycle straddling `pox_5_activation_height`. Per the documented test cases, `active_pox_contract` (tip-keyed) and `active_pox_contract_for_cycle` (cycle-keyed) diverge for blocks in that cycle's prepare phase / boundary offsets [8](#0-7) .
4. `PoxDB::get_reward_addresses_in_cycle`, which now uses `active_pox_contract_for_cycle`, either selects a different contract than what `get_pox-info`/tip-keyed RPC reports, or (if the cycle-keyed predicate resolves to `POX_5_NAME`) hits the `unknown_contract => panic!(...)` branch since no PoX-5 arm exists [12](#0-11) , causing chainstate-processing failure/divergence exactly at the misconfigured boundary — the same class of bug as `_getNextFriday`'s wrong-window check, just manifesting as a PoX-contract-dispatch boundary error instead of a Friday-timestamp error.

    /// Returns the PoX contract controlling the signer set and reward set
    /// for `reward_cycle`.
    ///
    /// Cycle-keyed counterpart to `active_pox_contract`.
    ///
    /// All cycle-scoped callers (signer-set computation, reward-address
    /// resolution) must use this; only tip-scoped callers (RPC, "what's
    /// live now") use the burn-height variant.
    ///
    /// The PoX-5 branch is derived from `first_pox_waterfall_block` so that
    /// `active_pox_contract_for_cycle` and the waterfall block-commit /
    /// nakamoto-cycle-start predicates agree on a single boundary.
    ///
    /// For pre-PoX-5 transitions the existing tip-keyed answer is preserved by
    /// evaluating at the cycle's mod-1 (classic reward-phase start) block.
    pub fn active_pox_contract_for_cycle(
        &self,
        first_block_height: u64,
        reward_cycle: u64,
    ) -> &'static str {
        if let Some(wf) = self.first_pox_waterfall_block(first_block_height) {
            if self.nakamoto_first_block_of_cycle(first_block_height, reward_cycle) >= wf {
                return POX_5_NAME;
            }
        }
        // PoX-5 already ruled out, now cascade through earlier
        // activations using a tip-height inside the cycle.
        let h = self.reward_cycle_to_block_height(first_block_height, reward_cycle);
        if h > u64::from(self.pox_4_activation_height) {
            POX_4_NAME
        } else if h > u64::from(self.pox_3_activation_height) {
            POX_3_NAME
        } else if h > u64::from(self.v1_unlock_height) {
            POX_2_NAME
        } else {
            POX_1_NAME
        }
    }

#[test]
fn cycle_predicate_is_stable_across_prepare_phase_for_first_pox5_cycle() {
    // Place activation deep inside the prepare phase that sets up the
    // first PoX-5 cycle. Tip-keyed `active_pox_contract` would return
    // POX_4 for some blocks and POX_5 for others; the cycle-keyed
    // predicate must answer consistently for the cycle as a whole.
    let first = 100u64;
    // offset 9 of cycle 3 = a prepare-phase block of cycle 3 (mod-9).
    let activation = first + 3 * 10 + 9;
    let c = pox_constants_with_pox_5_at(activation as u32);

    // Tip-keyed dispatch genuinely disagrees across the prepare phase:
    // mod-8 of cycle 3 returns POX_4 (burn_height < activation), but
    // mod-0 of cycle 4 returns POX_5 (burn_height > activation).
    let prepare_start = first + 3 * 10 + 8;
    let prepare_end = first + 4 * 10; // mod-0 of cycle 4
    assert_eq!(c.active_pox_contract(prepare_start), POX_4_NAME);
    assert_eq!(c.active_pox_contract(prepare_end), POX_5_NAME);

    // The cycle-keyed predicate is the single source of truth.
    // first_pox_waterfall_block puts cycle 3 as the last classic cycle
    // (it contains the activation height), so cycle 4 is first PoX-5.
    assert_eq!(c.active_pox_contract_for_cycle(first, 3), POX_4_NAME);
    assert_eq!(c.active_pox_contract_for_cycle(first, 4), POX_5_NAME);
}
