### Title
Wallet Contract EIP-155 chain ID is a build-time constant baked into WASM, causing signature replay across any forked NEAR chain that reuses the same wallet-contract WASM - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The NEAR Wallet Contract (the ETH-implicit account emulation contract) validates relayed Ethereum-style transactions by checking `tx.chain_id != Some(CHAIN_ID)` where `CHAIN_ID` is a compile-time constant baked into the WASM binary via `include!("CHAIN_ID")` at build time. This is directly analogous to Beanstalk's `LibTokenPermit::_buildDomainSeparator` using a static `C.getChainId()` constant instead of reading the live `block.chainid`.

### Finding Description
`pub const CHAIN_ID: u64 = std::include!("CHAIN_ID");` [1](#0-0)  hardcodes the chain identifier used to validate the Ethereum-style transactions that users sign to authorize NEAR actions. The value is set once at contract build time per network, per `build.rs`: 397 for mainnet, 398 for testnet, 399 for localnet [2](#0-1) , and this WASM is compiled once and distributed as a static, pre-built binary that is embedded into `nearcore` itself, one variant per network selected purely by matching a `chain_id: &str` string passed at runtime [3](#0-2) [4](#0-3) .

The validation logic that consumes this constant is `validate_tx_relayer_data`, which rejects a transaction if `tx.chain_id != Some(CHAIN_ID)` [5](#0-4) . This mirrors EIP-155's replay protection scheme, whose entire purpose is to bind a signed message to one specific chain so it cannot be replayed on another. Just like the Beanstalk `C.sol` constant, this value is not derived from any live, chain-specific runtime state (there is no `block.chainid`-equivalent check against the actual NEAR network genesis/chain ID at runtime) — it is a value frozen into the WASM bytecode at compile/build time and then matched against a `chain_id: &str` string that is selected in the embedding `nearcore` binary based on a static list (`chains::MAINNET`, `chains::TESTNET`, fallback `LOCALNET`) [3](#0-2) .

If NEAR mainnet (or testnet) is hard-forked — i.e., a new chain is created that inherits the same genesis/state (including all deployed wallet-contract code and all ETH-implicit accounts with their EVM-style public keys) — the forked chain would, by default, run the exact same wallet-contract WASM with `CHAIN_ID = 397` (mainnet) baked in, because chain selection is done by matching the network's string identifier (which the fork operator could keep, e.g., `"mainnet"`, or which could unintentionally coincide) rather than any protocol-level chain-fingerprint that changes across genesis events. Any EIP-155-signed Ethereum-style transaction previously authorized by a user for one chain would validate successfully on the other, since `tx.chain_id` is checked only against this static constant, not against any value unique to the forked chain's own genesis.

### Impact Explanation
A replayed transaction lets an attacker (or the original relayer) resubmit any previously signed wallet-contract meta-transaction (transfers, function calls, add/delete key actions) on the forked chain exactly as it executed on the original chain, since the wallet contract's nonce-check (`nonce != expected_nonce`) is scoped to per-account state on that specific chain and does not itself prevent cross-chain replay [6](#0-5) . This constitutes unauthorized value movement/actions on a forked network using signatures the user only intended to authorize once, on one chain — analogous to the Beanstalk/ETHPoW scenario cited in the report.

### Likelihood Explanation
This requires a hard fork of the NEAR chain — a real historical class of event (as referenced by the ETHPoW precedent in the source report) — combined with the forked chain reusing the same wallet-contract binary/chain-id selection logic without operators explicitly re-provisioning a distinct `CHAIN_ID` constant for the fork. Since chain-id selection here is driven by a hardcoded, compiled-in constant per network rather than any runtime, protocol-derived, unique-per-genesis value, this is a structural design gap rather than requiring any additional privileged capability.

### Recommendation
Do not bake the EIP-155 `CHAIN_ID` into the wallet-contract WASM at build time as a static constant selected only by a coarse network-name string. Instead, derive or bind it to a value that is guaranteed to change on a genesis/hard-fork event (e.g., a hash derived from the genesis config or `protocol_version`/`chain_id` value read at runtime from `env`), so that a forked chain cannot silently inherit the wallet contract's replay-protection value from its parent chain.

### Proof of Concept
1. NEAR mainnet is hard-forked at some block height, producing a new independent chain that copies genesis state, including all deployed wallet-contract WASM code (`CHAIN_ID = 397`) and existing ETH-implicit accounts [1](#0-0) .
2. A user previously signed an EIP-155 Ethereum-style transaction (e.g., a `transfer` or `functionCall` selector) with `chain_id = 397`, intended for use on original mainnet, and submitted it via a relayer to the wallet contract [7](#0-6) .
3. Because the forked chain runs the identical wallet-contract WASM and matches `tx.chain_id != Some(CHAIN_ID)` against the same constant 397 [8](#0-7) , an attacker who observed the signed transaction (or the relayer itself, malicious or not) can resubmit it to the forked chain if the account's nonce state on the fork still matches `expected_nonce`, executing the same action (fund transfer, key addition, etc.) on the forked chain without the user's renewed consent.
