## Finding

### Title
Method-id upgrade domain separator (`chain_id`) collides between Nightly and TestNetworkWithForks, enabling cross-network signature replay - (File: crates/light-client-prover/src/circuit/initial_values.rs, crates/sovereign-sdk/rollup-interface/src/state_machine/da.rs)

### Summary
The `BatchProofMethodIdBody.chain_id` field is documented as the domain-separator that "prevent[s] cross network replay attacks" for security-council-signed batch-proof method-id upgrades. However `citrea_network_to_chain_id` assigns the **same** chain id (`5665`) to both `Network::Nightly` and `Network::TestNetworkWithForks`, and the default (unconfigured) security-council public keys for both networks are also identical. This mirrors the reported class of bug: a domain-separator field intended to bind a signed message to one specific context is stale/wrong and collides with another context, allowing a validly signed message to be replayed where it was not authorized.

### Finding Description
`BatchProofMethodIdBody` carries a `chain_id` field whose sole purpose is domain separation across Citrea networks: [1](#0-0) 

`citrea_network_to_chain_id` maps this field, but assigns identical values to `Nightly` and `TestNetworkWithForks`: [2](#0-1) 

The light-client circuit's method-id-upgrade handler checks only that `circuit_chain_id == batch_proof_method_id.body.chain_id` before verifying the security-council signatures over that same body — it never checks a value unique to the specific network deployment beyond this constant: [3](#0-2) 

Compounding this, the default (env-var-less) security council public keys baked in for `TestNetworkWithForks` are byte-for-byte identical to the ones for `Nightly` (same env-var names, same fallback hex keys / private keys noted in comments): [4](#0-3) [5](#0-4) 

Because both the `chain_id` domain separator and the verifying public keys can be identical across the two networks, a `BatchProofMethodId` DA transaction that is validly signed and broadcast for one network's light-client circuit will also pass the `chain_id` check and signature verification of the other network's circuit — i.e., the equality `verify(network=Nightly, msg) == verify(network=TestNetworkWithForks, msg)` holds when it should not.

### Impact Explanation
If both networks' provers observe the same DA transaction (or an attacker/observer resubmits an already-published, validly-signed method-id-upgrade inscription onto the DA feed consumed by the other network's light-client prover), the second network's `BatchProofMethodIdAccessor` will accept and install a method id that the security council never authorized for that specific network. This is exactly the "unauthorised sequencer commitment or method-id upgrade" Critical-impact scenario: the on-chain guarantee "a method-id upgrade is authorised only for the network it was signed for" is broken purely because the domain-separator field is not actually unique per network in the default configuration.

### Likelihood Explanation
Exploitation requires no privileged key or role — it only requires observing/replaying an already-published, publicly visible DA transaction (inscriptions on Bitcoin DA are public) toward the light-client prover instance of the other network sharing the same `chain_id`/keys. Likelihood is reduced by the fact that production Mainnet/Testnet/Devnet networks use distinct hardcoded keys and chain ids, so the collision is confined to `Nightly` vs `TestNetworkWithForks` (test/staging environments), and the default keys can be overridden via env vars at build time.

### Recommendation
Assign a unique `chain_id` to every `Network` variant (do not reuse `5665` for both `Nightly` and `TestNetworkWithForks`), and ensure the default `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` differ between environments that are meant to be isolated, so the domain separator is never ambiguous between two live circuits.

### Proof of Concept
1. Security council signs a `BatchProofMethodIdBody { method_id, activation_l2_height, chain_id: 5665 }` for the Nightly network per `create_new_method_id_tx`. [6](#0-5) 
2. This DA transaction is broadcast and observed by a `TestNetworkWithForks` light-client prover instance running with default (unset env var) authority keys.
3. In `run_l1_block`, `citrea_network_to_chain_id(Network::TestNetworkWithForks)` returns `5665`, matching `batch_proof_method_id.body.chain_id`, so the chain-id check passes; `verify_method_id_security_council` then succeeds because the default `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` equal `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS`.
4. The method id is inserted into `TestNetworkWithForks`'s `BatchProofMethodIdAccessor` even though it was authorized only for `Nightly`. [7](#0-6)

/// These are chain ids for the citrea networks
/// This function is mainly used to check the chain id of the
/// method id upgrade transactions and to prevent cross network replay attacks
/// The method id upgrade identifiers are not strictly tied to chain ids
/// but for simplicity we use the same values
pub fn citrea_network_to_chain_id(network: sov_rollup_interface::Network) -> u64 {
    match network {
        sov_rollup_interface::Network::Mainnet => 4114,
        sov_rollup_interface::Network::Testnet => 5115,
        sov_rollup_interface::Network::Devnet => 62298,
        sov_rollup_interface::Network::Nightly => 5665,
        sov_rollup_interface::Network::TestNetworkWithForks => 5665,
    }
}

pub(crate) fn create_new_method_id_tx(
    activation_height: u64,
    new_method_id: [u32; 8],
    pub_key: [u8; 32],
    network: Network,
) -> MockBlob {
    let pk_bytes_arr: [[u8; 32]; 5] =
        TEST_PRIVATE_KEYS.map(|s| hex::decode(s).unwrap().try_into().unwrap());

    let msg = borsh::to_vec(&BatchProofMethodIdBody {
        activation_l2_height: activation_height,
        method_id: new_method_id,
        chain_id: citrea_network_to_chain_id(network),
    })
    .unwrap();

    let (_initial_pubkeys, signers) = generate_initial_pub_keys_with_signers_from_pks(pk_bytes_arr);
    let prehash = eip191_hash_message(&msg);
    let signatures_with_index = create_valid_signatures(&signers, &prehash);

    let da_data = DataOnDa::BatchProofMethodId(BatchProofMethodId {
        body: BatchProofMethodIdBody {
            method_id: new_method_id,
            activation_l2_height: activation_height,
            chain_id: citrea_network_to_chain_id(network),
        },
        signatures_with_index,
    });
