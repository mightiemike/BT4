## Title
Missing slippage protection in `ExchangeInjectActuator` allows front-running to force an unfavorable liquidity ratio - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

## Summary
Java-tron's TRC10 "Exchange" (a Bancor-style AMM pool) lets the pool creator add liquidity via `ExchangeInjectContract`. Unlike a real swap (`ExchangeTransactionContract`, which carries an `expected` field for slippage protection), the inject contract only carries `token_id` and `quant` — the amount of the *other* token required is computed on-chain from the *current* pool ratio at execution time, with no maximum/expected bound supplied by the caller. This mirrors the reported `mint()` issue in AlgebraPool: a liquidity-adding operation with no `amountMax` check, executed against a price that can be moved right before it lands.

## Finding Description
`ExchangeInjectActuator.doValidate()` computes `anotherTokenQuant` purely from the exchange's on-chain `firstTokenBalance`/`secondTokenBalance` at validation time: [1](#0-0) 

There is no field in the contract for the caller to bound how much of the "another token" they are willing to contribute, and `execute()` recomputes the same ratio-based amount again (independently, but from the same store state) before debiting the account: [2](#0-1) 

Any anonymous account can submit an `ExchangeTransactionContract` swap against the same `exchangeId` immediately before the injector's transaction is included in a block. `ExchangeTransactionActuator.execute()` mutates `firstTokenBalance`/`secondTokenBalance` via the Bancor-style `exchangeCapsule.transaction(...)` call: [3](#0-2) 

Because block producers order transactions and an attacker can control relative placement (front-running via fee/ordering or simply racing broadcast), the pool ratio seen by `ExchangeInjectActuator` at execution time can differ from the ratio the injector observed when constructing/signing their transaction — exactly analogous to the reported "price moved between intent and mint" scenario. The injector has no way to cap `anotherTokenQuant`, so they can be forced to contribute far more of the second token than intended, or receive far less value than planned once the attacker reverses their swap afterward (extracting the arbitrage).

This differs from `ExchangeTransactionActuator`, which already has the `token_expected` slippage guard validated as "token required must greater than expected": [4](#0-3) 
and `ExchangeWithdrawActuator`, whose ratio-derived `anotherTokenQuant` is at least bounded by the pool's existing balances and a precision check — but still lacks a caller-supplied min/max.

## Impact Explanation
An attacker (any unprivileged, anonymous broadcaster) can sandwich a pending `ExchangeInjectContract` transaction: swap to skew the pool ratio, let the injection execute at the skewed ratio (paying/receiving an unintended amount of the second asset), then swap back to capture the arbitrage. This causes direct, deterministic value loss/asset-accounting corruption for the injecting account — the pool's declared reserves end up reflecting a manipulated ratio rather than the one the liquidity provider intended, with no on-chain guard to prevent it.

## Likelihood Explanation
Exploitation only requires broadcasting an `ExchangeTransactionContract` and observing/predicting the target's pending `ExchangeInjectContract` (visible in the mempool or via block-producer transaction ordering), both of which are ordinary permissionless RPC/broadcast operations. No privileged role, leaked key, or malicious peer is required — this is reachable from any account holding sufficient token balance for the swap leg.

## Recommendation
Add an explicit slippage bound to `ExchangeInjectContract` (e.g., `expected`/`max_another_token_quant`), and have `ExchangeInjectActuator.doValidate()`/`execute()` reject the transaction if the computed `anotherTokenQuant` exceeds (or falls below) the caller-specified bound, mirroring the existing `token_expected` check already implemented in `ExchangeTransactionActuator`.

## Proof of Concept
1. Exchange pool has `firstTokenBalance = A`, `secondTokenBalance = B`.
2. Victim broadcasts `ExchangeInjectContract` injecting `q` of `firstToken`, expecting `anotherTokenQuant ≈ B*q/A`.
3. Attacker broadcasts an `ExchangeTransactionContract` swap that shifts the ratio to `A'`, `B'` before the victim's transaction is packed into the same or an earlier block (e.g., by offering a higher energy/bandwidth priority or exploiting producer ordering).
4. Victim's `ExchangeInjectActuator.execute()` now computes `anotherTokenQuant' = B'*q/A'`, deducting a different, attacker-influenced amount from the victim's account with no validation rejecting the discrepancy (no `expected`/max field exists in the contract to compare against).
5. Attacker swaps back, restoring the pool ratio and pocketing the difference extracted from the victim's injection.
