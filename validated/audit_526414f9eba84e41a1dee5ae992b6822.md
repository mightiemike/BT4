### Title
`ensure_match_transaction_info` never validates `state_checkpoint_hash`, letting replay-verify silently accept a wrong state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by the archive-replay verification tool (`storage/db-tool/src/replay_on_archive.rs`) to confirm that re-executing historical transactions locally produces the same result as the trusted, previously-committed `TransactionInfo`. The function checks status, gas used, write-set hash, and event root hash, but it never compares the recomputed state root (`state_checkpoint_hash`) against the expected one, and this gap is not limited to the yet-unreleased trading-native fields — the baseline state root is skipped too.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates four properties between a locally computed `TransactionOutput` and the canonical `TransactionInfo` read from an archive/backup: execution status, gas used, write-set hash (`state_change_hash`), and event root hash. It ends with: [2](#0-1) 

explicitly acknowledging that checkpoint hashes are skipped, but the comment frames the gap only around the not-yet-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature (hot-state and `position_state_checkpoint_hash`). In fact, `state_checkpoint_hash` — the field that commits to the JMT state root at checkpoint boundaries for every transaction, independent of the trading-native feature — is also absent from the comparison and always has been in this code path.

This function is the sole verification step used by `execute_and_verify` in the replay tool: [3](#0-2) 

The tool re-executes archived transactions with the VM (`executor.execute_block`) and calls `ensure_match_transaction_info` per transaction to decide pass/fail. Because state-checkpoint hash comparison is missing, a divergence in the recomputed state root at a checkpoint transaction (state-checkpoint / block-epilogue) — caused by, e.g., non-determinism in execution, a storage schema bug, or a JMT/state-merkleization defect — would not be flagged as a failure by this tool, even though write-set hash, gas, status and events all matched.

### Impact Explanation
Replay-verify against archived history is one of the primary mechanisms for catching state-commitment divergence (the exact "hard-fork-only divergence during commit/replay" class called out as in-scope). If the state root check is silently absent, a genuine consensus-breaking bug (VM producing a correct write set/events but the state Merkle root or JMT summarization ends up wrong) can pass replay verification undetected. This weakens the guarantee that "committed state differs from the correct VM result" issues get caught before they propagate — i.e., it removes a proof-integrity safety net specifically for the state-root-in-`TransactionInfo` binding, which is exactly the checkpoint field that downstream state proofs and light-client verification (`TransactionInfo` accumulator leaves, `AccumulatorProof::verify`) rely on.

### Likelihood Explanation
The gap is unconditional (present regardless of feature flags) in the code as read; only the doc comment ties it to the not-yet-active `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/position-state feature, but the actual `state_checkpoint_hash` comparison for the baseline (non-trading) checkpoint hash is not present at all in this function. Because `replay_on_archive` is the operational tool relied on to independently confirm ledger-state correctness (used ahead of upgrades/hard-fork checks), a real state-divergence bug elsewhere in execution or storage would go unnoticed by this specific verification path even though it is precisely the kind of tool meant to catch it.

I was not able to fully confirm within the available tool budget whether:
- an earlier version of this function (via git history/blame) did check `state_checkpoint_hash` and it was dropped when the trading-native fields were added (the blame tool call failed due to a missing `ref` parameter and could not be retried), or
- some other layer of `replay_on_archive`/`AptosVMBlockExecutor` independently re-derives and compares the state root elsewhere in the pipeline (I did not find such a check in the code paths examined, but did not exhaustively trace every call site of `execute_block`/`BlockOutput`).

Given this uncertainty about whether an independent state-root check exists elsewhere in the replay pipeline, I present this as the strongest local candidate but flag that its full impact should be confirmed by checking whether `state_checkpoint_hash` is verified anywhere else along the `replay_on_archive` path before treating it as a fully proven, standalone finding.

### Recommendation
In `ensure_match_transaction_info`, compute the local state-checkpoint hash for checkpoint transactions and assert it equals `txn_info.state_checkpoint_hash()` (and, when the trading-native feature is enabled, also validate `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) before returning `Ok(())`, removing the TODO gap for both current and future checkpoint fields.

### Proof of Concept
Not independently exploitable by an unprivileged party against mainnet consensus (no state is actually corrupted by this code); the issue is a missing detection capability. To demonstrate: run `replay_on_archive` against a chunk containing a state-checkpoint transaction, and construct a `TransactionOutput` whose write set/events/gas/status match the archived `TransactionInfo` but whose actual re-derived state root (as would be computed by the executor's Merkle summarization) differs — `ensure_match_transaction_info` returns `Ok(())` because `state_checkpoint_hash` is never compared, i.e. the tool reports the replay as verified despite the state-root mismatch. Full confirmation requires exercising the real executor pipeline (`aptos-move/cli/src/commands.rs` callers and `do_state_checkpoint.rs`) to construct such a controlled mismatch, which was not runnable in this read-only review.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
