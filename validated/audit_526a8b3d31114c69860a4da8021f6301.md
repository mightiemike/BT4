### Title
`liquidate-multi` strands liquidator funds when a per-position failure occurs after `vault-system-repay` but before `collateral-remove` completes - ([File: local-testing/contracts/market/market.clar])

### Summary
`liquidate-multi` executes each batch entry via `(map call-liquidate positions)`, where `call-liquidate` invokes the public `liquidate` function directly (not via `contract-call?`), and the whole batch wrapper always returns `(ok ...)` regardless of individual outcomes. [1](#0-0)  Inside `liquidate`, real value transfer (`vault-system-repay`, which pulls tokens from the liquidator to repay the vault) happens *before* the bookkeeping calls `debt-remove-scaled` and `collateral-remove` that credit the liquidator with seized collateral. [2](#0-1)  If `collateral-remove` (or `debt-remove-scaled`) fails for a given batch entry, `try!` makes `liquidate` return `(err ...)` for *that entry only* — the error is absorbed as a plain list element by `map`, and `liquidate-multi` still returns `(ok (list ...))` for the whole transaction, so the earlier, already-successful `vault-system-repay` transfer persists.

### Finding Description
`liquidate` is a multi-step entry point:
1. `vault-system-repay` pulls the debt-repay amount in underlying tokens from `contract-caller` (the liquidator) and reduces the vault's aggregate `total-borrowed`. This is a successful, self-contained `contract-call?` whose effects commit as soon as it returns `ok`. [3](#0-2) 
2. `debt-remove-scaled` reduces the borrower's individual scaled-debt ledger in `market-vault`. [4](#0-3) 
3. `collateral-remove` seizes the borrower's collateral and sends it to the liquidator/receiver, guarded by `remove-user-collateral`'s `(asserts! (<= amount collateral-amount) ERR-INSUFFICIENT-COLLATERAL)`. [5](#0-4) [6](#0-5) 

Each of these is chained with `try!` inside the *single* `liquidate` function body. [7](#0-6)  If step 3 (or step 2) fails, `try!` makes `liquidate` itself return `(err ...)` — but step 1 already executed as its own successful `contract-call?` and its effects are not undone by a later failure in a *sibling* function invocation that is not itself wrapped in `try!`/`unwrap!` by the outer caller.

The critical amplifier is `liquidate-multi`: it invokes `liquidate` through `call-liquidate` as a **direct intra-contract function call** (not `contract-call?`), and collects results with `map`, explicitly documented as "Failed liquidations return error codes but don't revert entire batch." [8](#0-7)  Because `liquidate-multi` always wraps the map result in `(ok ...)`, the *outermost* public function invoked by the transaction returns `ok`, so Clarity's atomicity — which is scoped to the outermost transaction result, not to intermediate function calls — commits every state change made along the way, including the `vault-system-repay` funds transfer for an entry that ultimately "failed."

### Impact Explanation
If any single position in a `liquidate-multi` batch fails at `debt-remove-scaled` or `collateral-remove` (e.g., because a duplicate/overlapping entry in the same batch has already reduced that borrower's collateral to less than the amount computed for a later entry, or `curr-scaled` debt is fully consumed by a prior entry), the liquidator's underlying tokens paid via `vault-system-repay` for that entry are consumed by the vault (reducing aggregate `total-borrowed`) while the liquidator receives no offsetting collateral for that entry, and the failure is silently absorbed into the results list rather than reverting the sub-operation. This is a direct loss of the liquidator's transferred funds with no corresponding compensation — a fund-stranding/loss scenario matching the "Critical: direct theft of user funds at rest or in motion" bucket, since real underlying tokens leave the liquidator's control with no matching credit.

### Likelihood Explanation
This requires a single caller submitting one `liquidate-multi` transaction whose `positions` list contains entries that interact with each other's collateral/debt state within the batch (e.g., two entries referencing the same `borrower`/`asset-id`, or entries whose combined seizure exceeds the actual balance visible when the first entry executed). Because `map` processes entries sequentially and mutates real state between iterations, engineering such an overlapping batch is fully within a single caller's control and does not require any other party's cooperation or a race across blocks — it is a single-transaction, deterministic sequencing issue, not two users interfering with each other.

### Recommendation
Make `liquidate` atomic per-position within the batch: either wrap each `call-liquidate` outcome so that on error, the sub-operation's `vault-system-repay` effect is unwound (not currently possible without a proper nested-transaction abstraction in Clarity), or reorder `liquidate`'s operations so that `debt-remove-scaled`/`collateral-remove` are validated/executed **before** `vault-system-repay` pulls funds from the liquidator, ensuring the funds-pulling step is the last operation in the sequence and only runs once all bookkeeping has already succeeded.

### Proof of Concept
1. Liquidator submits `liquidate-multi` with two entries targeting the same `borrower` and same `coll-aid`/`debt-aid`, with `debt-amount`/`min-collateral-expected` computed off the pre-batch collateral balance for both entries (both entries computed independently, unaware the first entry will consume the collateral).
2. `map call-liquidate` processes entry 1: `liquidate` executes `vault-system-repay` (pulls tokens from liquidator, reduces vault `total-borrowed`), then `debt-remove-scaled` and `collateral-remove` succeed, draining the borrower's remaining collateral for that asset to zero or near-zero.
3. `map call-liquidate` processes entry 2 for the same borrower/asset: `liquidate` again executes `vault-system-repay` (pulls more tokens from the liquidator, again reduces vault `total-borrowed`), succeeds through `debt-remove-scaled` (if any debt remains), but then `collateral-remove` fails at `remove-user-collateral`'s `ERR-INSUFFICIENT-COLLATERAL` assertion (step in `local-testing/contracts/market/market-vault.clar:205-214`) because the collateral was already removed in step 2.
4. `liquidate` for entry 2 returns `(err ERR-INSUFFICIENT-COLLATERAL)` — but the `vault-system-repay` transfer of entry 2's tokens has already been committed as a successful, independent `contract-call?`.
5. `map` records `(err ...)` for entry 2 in the results list; `liquidate-multi` still returns `(ok (list (ok ...) (err ...)))`. The transaction succeeds overall, and the liquidator's second repayment is permanently lost with no collateral received in return.

```text
(define-private (remove-user-collateral (user-id uint) (asset-id uint) (amount uint))
  (let ((key { id: user-id, asset: asset-id })
        (collateral-amount (default-to u0 (map-get? collateral key))) ;; graceful default
        (legal? (asserts! (<= amount collateral-amount) ERR-INSUFFICIENT-COLLATERAL))
        (updated-collateral-amount (- collateral-amount amount)))

      (if (is-eq updated-collateral-amount u0)
          (map-delete collateral key)
          (map-set collateral key updated-collateral-amount))
      (ok updated-collateral-amount)))
```

```text
(define-public (collateral-remove (account principal) (amount uint) (ft <ft-trait>) (asset-id uint) (recipient principal))
  (let ((states (var-get pause-states))
        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
        (remaining (try! (remove-user-collateral user-id asset-id amount)))
        (updated-mask (if (is-eq remaining u0)
                        (mask-update mask asset-id true false) ;; collateral, remove
                        mask))

    (asserts! (not (get collateral-remove states)) ERR-PAUSED)
```
