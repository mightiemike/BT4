Based on my analysis, I found the strongest analog in java-tron's Dynamic Energy Fee mechanism, which mirrors the reported bug class: a rate/factor value that is intentionally computed only once per accounting period (here, a DPoS maintenance "cycle" instead of a block), allowing all in-cycle activity to escape the throttling meant to price out spam/DoS.

### Title
Dynamic Energy penalty factor updates only once per maintenance cycle, letting attackers spam contracts at the pre-penalty energy price for an entire cycle - (File: chainbase/src/main/java/org/tron/core/capsule/ContractStateCapsule.java)

### Summary
TVM's "dynamic energy" congestion-control feature is designed to raise the energy cost (`energyFactor`) of calling a specific contract once its per-cycle usage exceeds `dynamicEnergyThreshold`, similar in spirit to the reported lending protocol's interest-rate mechanism that updates only once per block. In java-tron the update granularity is a full DPoS maintenance cycle (about every 6 hours) rather than a block, but the same root cause applies: `ContractStateCapsule.catchUpToCycle()` explicitly short-circuits with `if (lastCycle == newCycle) return false;` [1](#0-0) , meaning the increased penalty is only applied starting the cycle *after* usage crossed the threshold.

### Finding Description
`Program.updateContextContractFactor()` fetches (or lazily creates) the `ContractStateCapsule` for the called contract and invokes `catchUpToCycle()` with the current cycle number and the governance-configured `dynamicEnergyThreshold` / `dynamicEnergyIncreaseFactor` / `dynamicEnergyMaxFactor` values [2](#0-1) . `catchUpToCycle()` only recalculates `energyFactor` when `newCycle` differs from the previously stored `updateCycle`; while both remain equal, it returns `false` immediately without inspecting `getEnergyUsage()` against the threshold at all [3](#0-2) . Usage accumulated during the current cycle is only compared to the threshold and converted into an increased `energyFactor` when the cycle boundary is finally crossed, at which point the factor is raised by `increaseFactor` and applied going forward [4](#0-3) .

The computed `contextContractFactor` is what determines the energy penalty applied to every opcode and CALL executed against that contract for the duration of the VM run: `VM.play()` calls `updateContextContractFactor()` once per execution and then multiplies opcode energy costs by `factor / DYNAMIC_ENERGY_FACTOR_DECIMAL` whenever `factor > DYNAMIC_ENERGY_FACTOR_DECIMAL` [5](#0-4) , and `EnergyCost.getCalculateCallCost()` applies the same penalty to CALL-family opcodes [6](#0-5) .

Because the factor snapshot is taken from the state as of the start of the *current* cycle (or is `false`/unchanged mid-cycle), any calls made within a cycle that has not yet "caught up" are always charged the pre-penalty (or stale, lower) factor, no matter how much usage has already been recorded in that same cycle via `addContextContractUsage()` [7](#0-6) .

### Impact Explanation
This is the direct java-tron analog of the reported "interest updated once per block" flaw: the throttling mechanism intended to make sustained congestion/spam against a hot contract progressively more expensive is bypassed for the entirety of every cycle before the penalty catches up. An attacker who repeatedly triggers a targeted contract can drive `energyUsage` far past `dynamicEnergyThreshold` throughout the whole current cycle while still paying the base (unpenalized) energy price, since `energyFactor` is not recalculated until the *next* cycle transition. This lets an attacker sustain a much cheaper DoS/congestion campaign against a specific contract (analogous to the report's "reduced cost of DoS") than the dynamic-energy-fee governance parameters intend, undermining the mechanism's purpose of pricing out abusive high-frequency callers within the same accounting window.

### Likelihood Explanation
`allowDynamicEnergy` must be enabled via committee proposal for this path to matter [8](#0-7) , but once enabled, the reachable path is a routine, unprivileged TVM contract call (`TriggerSmartContract`) — no special permissions or malicious node behavior are needed, only enough resources to send transactions targeting the contract throughout the cycle.

### Recommendation
Recompute (or incrementally apply) the penalty within the same cycle once accumulated `energyUsage` crosses `dynamicEnergyThreshold`, rather than deferring the factor update entirely to the next cycle boundary, so that abusive usage is throttled within the window it occurs in rather than only in the following cycle.

### Proof of Concept
1. Enable `allowDynamicEnergy` (already assumed enabled on target chain) with a low `dynamicEnergyThreshold`.
2. At the start of a new maintenance cycle, repeatedly call the target contract with many transactions, driving `energyUsage` (tracked via `addContextContractUsage`) well past `dynamicEnergyThreshold` within that cycle.
3. Observe that each call in this cycle is charged using the `energyFactor` computed as of the previous cycle transition (`catchUpToCycle` short-circuits at line 96-98 of `ContractStateCapsule.java` since `lastCycle == newCycle`), i.e., the base/unpenalized rate, even though usage has already exceeded the threshold.
4. Only at the next cycle transition does `catchUpToCycle()` observe `getEnergyUsage() > threshold` and raise `energyFactor`, confirming the penalty was deferred for the entire prior cycle of abuse — mirroring the reported "no fees are paid" same-window exploit, here manifesting as "no penalty applied" for a full cycle of sustained congestion.

  public long updateContextContractFactor() {
    ContractStateCapsule contractStateCapsule =
        contractState.getContractState(getContextAddress());

    if (contractStateCapsule == null) {
      contractStateCapsule = new ContractStateCapsule(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber());
      contractState.updateContractState(getContextAddress(), contractStateCapsule);
    } else {
      if (contractStateCapsule.catchUpToCycle(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber(),
          VMConfig.getDynamicEnergyThreshold(),
          VMConfig.getDynamicEnergyIncreaseFactor(),
          VMConfig.getDynamicEnergyMaxFactor(),
          VMConfig.allowStrictMath(),
          VMConfig.disableJavaLangMath())) {
        contractState.updateContractState(getContextAddress(), contractStateCapsule
        );
      }
    }
    contextContractFactor = contractStateCapsule.getEnergyFactor()
        + Constant.DYNAMIC_ENERGY_FACTOR_DECIMAL;
    return contextContractFactor;
