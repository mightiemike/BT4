### Title
L1Handler transactions execute with a hardcoded `paid_fee_on_l1 = Fee(1)` in the consensus/batcher path, bypassing the real L1-paid-fee check - (File: crates/apollo_transaction_converter/src/transaction_converter.rs)

### Summary
The reported bug is about a cross-chain contract (`CrosschainDistributor`) invoking `connext.xcall()` without paying any relayer fee, so the message can never be executed on the destination chain and funds are permanently stranded because the "fee actually required to relay/execute the message" is never verified against what the sender is willing/required to pay. The analogous mechanism in this Starknet sequencer is the `paid_fee_on_l1` field on `L1HandlerTransaction`, which is supposed to represent the fee the L1 sender actually paid to the Starknet core contract to have their L1→L2 message executed, and which the blockifier is meant to check against the actual computed execution fee before allowing the L1 handler to run.

### Finding Description
In `crates/blockifier/src/transaction/l1_handler_transaction.rs` (`execute_raw`), the sequencer enforces a fee check on L1 handler transactions: [1](#0-0) 
This check only asserts `paid_fee != Fee(0)`, and it explicitly relies on `self.paid_fee_on_l1`, which is supposed to be the amount actually paid on L1 (via the `LogMessageToL2` event, see `crates/papyrus_base_layer/src/eth_events.rs`).

However, in the consensus/batcher path that reconstructs an executable `L1HandlerTransaction` from a `ConsensusTransaction` received from other validators, the real L1-paid fee is discarded and replaced with a hardcoded stub value: [2](#0-1) 

This is the exact code path used by `convert_consensus_tx_to_internal_consensus_tx`, which is invoked by validators reconstructing/validating a proposed block's transactions (via `convert_internal_consensus_tx_to_executable_tx` / `block_builder.rs`). Because `Fee(1)` is always non-zero, the `if paid_fee == Fee(0)` check in `l1_handler_transaction.rs` line 106 will always pass, regardless of whatever fee was truly paid (or not paid) on L1 for that message. The TODO comment `// TODO(Gilad): Change this once we put real value in paid_fee_on_l1.` confirms this is a known-incomplete stub rather than intentional design.

### Impact Explanation
If this stubbed value is exercised on the honest validation/re-execution path (as opposed to the proposer's own path where the real `paid_fee_on_l1` from the L1 event scraper is presumably used), a validating node would accept and re-execute an L1 handler transaction as fee-valid even if the true L1-paid fee was `0` or otherwise insufficient. This breaks the invariant that `paid_fee_on_l1` reflects the real amount paid, which is the sequencer's protocol analog of the "relayer fee" in the reported bug. In the worst case this allows a class of transactions (L1→L2 messages) to be included in a locally-validated block that should have been rejected on fee-insufficiency grounds, potentially causing block-validation divergence between the proposer and validators (fee check outcome differs depending on which code path computed `paid_fee_on_l1`), i.e. honest-node divergence over whether an L1 handler transaction is fee-valid.

### Likelihood Explanation
This is reachable by any process that goes through the consensus transaction conversion path for `L1_HANDLER` transactions — i.e., a normal, expected code path for every proposed block containing an L1 handler transaction, not a privileged or malicious-actor-only path. The likelihood of the divergence actually manifesting depends on whether another component upstream (e.g., `apollo_batcher`'s `ValidateTransactionProvider`, seen validating L1 events with the L1 provider) independently re-derives/enforces the correct fee elsewhere before this stub is applied; based on the code inspected, the L1-provider validation step (`crates/apollo_batcher/src/transaction_provider.rs`) checks hash/consumption/cancellation status but was not observed enforcing the paid fee amount itself, leaving the hardcoded `Fee(1)` as the value that flows into blockifier's fee check.

### Recommendation
Thread the real `paid_fee_on_l1` value (as scraped from the L1 `LogMessageToL2` event, already available via `crates/papyrus_base_layer/src/eth_events.rs`) through the consensus transaction conversion path instead of hardcoding `Fee(1)` in `convert_consensus_l1_handler_to_internal_l1_handler`. Ensure the value used during validator re-execution is sourced from the same authoritative record as the value used by the proposer, so that the fee-sufficiency check in `l1_handler_transaction.rs` is meaningful on every node.

### Proof of Concept
Not applicable in the traditional sense (no exploit script), because this was identified via static code review of the fee-plumbing path rather than a runtime exploit. The concrete evidence is:
1. `l1_handler_transaction.rs::execute_raw` treats any non-zero `paid_fee_on_l1` as sufficient: [3](#0-2) 
2. `transaction_converter.rs::convert_consensus_l1_handler_to_internal_l1_handler` hardcodes `Fee(1)` for every consensus-received L1 handler transaction regardless of its real L1-paid fee: [4](#0-3) 

Note: due to index size limits, the full call chain from `block_builder.rs`/`convert_internal_consensus_tx_to_executable_tx` into this function, and whether the batcher's `ValidateTransactionProvider` independently re-validates the true fee before or instead of this stub, could not be fully traced with the tools available. A Devin session with full repository access should confirm whether the proposer path uses the same stub or a different, correct value, to determine whether this causes genuine honest-node divergence or is fully mitigated elsewhere.
