## Title
Global resource-weight (`totalNetWeight`/`totalEnergyWeight`) spot-ratio manipulation via single-transaction freeze can instantly dilute other accounts' bandwidth/energy allowance, forcing unexpected fee payment or transaction failure - (File: `chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java`, `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

## Summary
The DYAD report describes a spot-price value (`kerosenePrice = (TVL - dyadSupply) / keroseneSupply`) that any user can instantaneously move by depositing/withdrawing collateral in a single transaction, which is then used to compute another user's collateralization ratio and can force that user into liquidation. The structurally analogous mechanism in java-tron is the bandwidth/energy allowance formula, which divides an individual account's frozen stake by a chain-wide pool value (`totalNetWeight` / `totalEnergyWeight`) that any account can move instantly by freezing TRX in a single transaction, diluting every other staker's derived resource limit in the same block.

## Finding Description
`BandwidthProcessor.calculateGlobalNetLimit` computes an account's bandwidth allowance as a *spot ratio* of its own frozen balance over the total network-wide frozen weight: [1](#0-0) 

The equivalent energy calculation follows the same pattern: [2](#0-1) 

`totalNetWeight` and `totalEnergyWeight` are simple counters mutated atomically, in the same transaction, by any account's `FreezeBalanceV2Actuator`/`FreezeBalanceActuator`: [3](#0-2) 

and decremented instantly by `UnfreezeBalanceV2Actuator`/native unfreeze processors — note the weight update happens immediately when unfreezing is called, decoupled from the actual return of TRX which may be subject to a withdrawal delay: [4](#0-3) 

Because `totalNetWeight`/`totalEnergyWeight` is a *global spot value* with no time-weighting or averaging (no TWAP-equivalent), any single account can instantly push a large amount of TRX into freeze (increasing the pool denominator) within the same block as a victim's transaction. This immediately reduces every other staked account's `netLimit`/`energyLimit` computed via the ratio `frozeBalance/TRX_PRECISION * totalLimit/totalWeight`, exactly mirroring how kerosene's spot price is diluted by instantaneous TVL changes in the DYAD report.

## Impact Explanation
A victim account whose free-bandwidth/energy allowance is computed from this diluted ratio can suddenly have insufficient bandwidth/energy for a transaction that would have succeeded moments earlier, as enforced in `useAccountNet`: [5](#0-4) 

This forces the victim's transaction to either fail resource validation (`ContractValidateException`/`AccountResourceInsufficientException`) or fall back to burning TRX for fees instead of using their staked free allowance — an unintended state/accounting divergence directly caused by another unprivileged user's single-transaction action, analogous to the report's "force liquidation" impact (unexpected, attacker-triggered degradation of another user's economic position based on a manipulable spot ratio).

## Likelihood Explanation
Freezing TRX to increase `totalNetWeight`/`totalEnergyWeight` requires no special privilege — any account holding sufficient TRX can call `FreezeBalanceV2Contract`. The dilution effect is proportional to the size of the freeze relative to existing total weight, so it is most impactful against a chain with moderate total weight, similar to how the kerosene report scenario requires a "whale" with a large deposit. As in the original report, TRON's docs already frame resource limits as dynamically shared and spot-based, so like the C4 judge's downgrade, this would likely be assessed as medium rather than high, since it's an acknowledged consequence of the shared-pool resource model rather than a broken invariant.

## Recommendation
Consider smoothing `totalNetWeight`/`totalEnergyWeight` changes (e.g., applying weight changes only at epoch/maintenance boundaries, or using a time-weighted average of the total weight) rather than allowing an in-block freeze/unfreeze to instantaneously change every other account's derived resource limit.

## Proof of Concept
1. Attacker observes a victim about to submit a transaction that relies on free/staked bandwidth (`useAccountNet` in `BandwidthProcessor.java`).
2. In the same or an earlier block, attacker calls `FreezeBalanceV2Contract` with a large TRX amount, which calls `dynamicStore.addTotalNetWeight(...)` inside `FreezeBalanceV2Actuator.execute` [6](#0-5) , instantly inflating `totalNetWeight`.
3. Victim's subsequent transaction computes a reduced `netLimit` via `calculateGlobalNetLimit`, causing `bytes > (netLimit - newNetUsage)` to trip in `useAccountNet`, so the transaction either fails resource pre-check or the victim is charged TRX fees instead of using free bandwidth.
4. Attacker can later call `UnfreezeBalanceV2Contract`, which decrements `totalNetWeight` back down immediately via `updateTotalResourceWeight` [7](#0-6) , restoring the ratio for everyone else — demonstrating the pool value was moved purely as a spot manipulation, at the cost of only a temporary stake lock rather than a permanent loss.

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForBandwidth();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalNetLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }

  protected long calculateGlobalLimitV1(long frozeBalance,
      long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
  }

  public void updateTotalResourceWeight(AccountCapsule accountCapsule,
                                        Common.ResourceCode freezeType,
                                        long unfreezeBalance,
                                        Repository repo) {
    switch (freezeType) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(-unfreezeBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        repo.addTotalNetWeight(newNetWeight - oldNetWeight);
        break;
      case ENERGY:
        long oldEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForEnergyV2(-unfreezeBalance);
        long newEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        repo.addTotalEnergyWeight(newEnergyWeight - oldEnergyWeight);
        break;
      case TRON_POWER:
        long oldTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        accountCapsule.addFrozenForTronPowerV2(-unfreezeBalance);
        long newTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        repo.addTotalTronPowerWeight(newTPWeight - oldTPWeight);
        break;
      default:
        //this should never happen
        break;
    }
