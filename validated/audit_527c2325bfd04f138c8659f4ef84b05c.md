## Analysis

The external report's bug class is: a payment/transfer step is assumed to always succeed based on the target implementing a standard interface correctly, but a non-compliant or failing target can revert/fail, and the code around it does not correctly reconcile the associated value movement. The nearcore analog reachable by an unprivileged meta-transaction sender (relayer) is in the NEAR Wallet Contract's Ethereum-transaction emulation flow, which maps ERC-20 semantics onto NEP-141 (`ft_transfer`).

### Title
Relayer fee for emulated ERC-20/base-token transfers is paid unconditionally, even when the underlying action fails - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`inner_rlp_execute` computes a relayer fee (`tx_fee`) from the user's signed Ethereum-style transaction and, for `EOABaseTokenTransfer` and `ERC20Transfer` kinds, immediately creates and dispatches a *separate* promise batch that transfers this fee to the relayer (`predecessor_account_id`), independent of and prior to the promise chain that performs the actual requested action. [1](#0-0) 

### Finding Description
The fee-refund promise is created via `env::promise_batch_create` / `env::promise_batch_action_transfer` targeting the relayer, unconditionally, before the action-execution promise (`action_to_promise`, or the ERC-20 `storage_balance_of` → `storage_deposit` → `ft_transfer` chain) is even attempted: [2](#0-1) 

The actual action for an `ERC20Transfer` is executed through a multi-step cross-contract call to the target NEP-141 (the ERC-20 analog) contract: `storage_balance_of`, optionally `storage_deposit`, and `ft_transfer`: [3](#0-2) 

If that target token contract is non-compliant, paused, blacklists the wallet, or otherwise fails/reverts (the precise analog of the USDT/non-standard ERC-20 in the original report), the callback only distinguishes success/failure of that single promise and — on failure — refunds only the caller's *attached deposit* (`caller_deposit`), never the already-dispatched fee: [4](#0-3) 

Because the fee transfer is a fire-and-forget promise batch with no callback tying it to the outcome of the main action, and because there is no atomic linkage (e.g. via `.then()`/batching) between "action succeeded" and "fee paid," the relayer is compensated even when the user's transfer never completes.

### Impact Explanation
A user signs an Ethereum-style transaction (e.g. an ERC-20/NEP-141 transfer) specifying a gas fee for the relayer. If the target token is non-compliant or the transfer otherwise fails on-chain, the relayer still unconditionally receives the fee out of the user's/current account's balance, while the user's requested transfer does not occur. This is a fee/value-movement bypass: NEAR value leaves the wallet contract's account without the corresponding service (the intended action) being rendered, and there is no mechanism to reclaim or withhold the fee tied to action success.

### Likelihood Explanation
This is triggerable by any relayer submitting a validly signed user transaction (a normal meta-transaction sender, not requiring malicious node/validator/network capabilities) whenever the target contract of an ERC20Transfer or EOABaseTokenTransfer legitimately fails (e.g., non-compliant/paused/blacklisting token, insufficient token balance discovered at execution, or any other on-chain revert) — a realistic and reachable condition given today's diversity of non-standard fungible-token contracts.

### Recommendation
Make the fee payment contingent on the success of the underlying action: only send the relayer fee from within (or chained after, and conditioned on) the `PromiseResult::Successful` branch of `rlp_execute_callback`, instead of dispatching it eagerly and unconditionally in `inner_rlp_execute`. Alternatively, batch the fee-transfer action together with the main action in a single promise so both succeed or fail atomically, and refund the fee to the user (or leave the fee amount) whenever `PromiseResult::Failed` is observed, symmetric to how `caller_deposit` is already refunded.

### Proof of Concept
1. A user signs an Ethereum-style ERC-20 `transfer` transaction targeting a NEP-141 token account, specifying `max_fee_per_gas`/`gas_limit` that translate into a non-zero `tx_fee`.
2. A relayer submits this via `rlp_execute`. `inner_rlp_execute` detects `TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. })`, and since `fee` is non-zero and predecessor != current account, immediately fires a transfer promise batch paying `fee` to the relayer (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:374-385`).
3. Separately, the multi-step promise chain (`storage_balance_of` → optional `storage_deposit` → `ft_transfer`) is created against the target token contract (`lib.rs:433-458`).
4. The target NEP-141 contract fails the `ft_transfer` call (e.g., it is paused, blacklists the account, or is otherwise non-compliant/reverting).
5. `rlp_execute_callback` observes `PromiseResult::Failed`, refunds only `caller_deposit` if present, and reports failure (`lib.rs:296-312`) — but the fee sent in step 2 is not reclaimed; the relayer keeps it despite the transfer never happening.
