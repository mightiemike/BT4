### Title
Workflow registration events are silently dropped and never retried when handling fails in `SyncStrategyEvent` mode - ([File: core/services/workflows/syncer/workflow_registry.go])

### Summary
The `readRegistryEventsLoop` in `core/services/workflows/syncer/workflow_registry.go` advances its read cursor for every on-chain event it observes *before* confirming that the event was successfully processed by the handler. If `handleWithMetrics`/`Handle` fails for a given event (e.g. `WorkflowRegisteredEvent`), the error is only logged — the cursor has already moved past that event, so it is never re-fetched or retried. This reproduces the CIP-001 root cause: an action that succeeds on the "application layer" (the on-chain `WorkflowRegistry` contract, which emits the registration event) is not reliably reflected on the internal "consensus/execution layer" (the node's workflow engine/database), and there is no mechanism to detect the discrepancy or recover from it.

### Finding Description
`readRegistryEventsLoop` queries the `WorkflowRegistry` contract for new finalized log events using a `cursor` that tracks the last processed position [1](#0-0) . For every fetched log, the cursor is unconditionally updated to `log.Sequence.Cursor` inside the same loop that builds the `events` slice, i.e. before any of those events are actually handed to the handler [2](#0-1) .

Only after the cursor has been advanced does the code iterate over `events` and call `w.handleWithMetrics(ctx, event.Event)`; if that call returns an error, it is simply logged with `Errorw` and the loop moves on — the event is not requeued and the cursor is not rolled back [3](#0-2) .

`workflowRegisteredEvent` in the shared handler (`core/services/workflows/syncer/handler.go`) is documented as needing to be idempotent and "must not error if retried multiple times" precisely because retries are expected to happen — but in `SyncStrategyEvent` mode, the cursor-advance-before-handle ordering removes that safety net for any event whose processing legitimately fails (for example, an engine creation/validation failure) [4](#0-3) .

This is structurally identical to the Turnstile bug: the "application layer" (the on-chain registration transaction / event emission) succeeds and is irreversibly recorded, while the "consensus layer" (the node's internal processing of that event, i.e. workflow engine registration into `EngineRegistry`) can silently fail with no revert and no retry path, leaving the workflow owner believing their workflow is registered/active when the node never actually created a running engine for it.

### Impact Explanation
A workflow owner who successfully registers/activates a workflow on-chain may end up with a workflow that never actually runs, with no automatic recovery. Because the on-chain state (the source of truth users observe) shows the workflow as registered/active, but the node's internal engine state silently diverges, this can cause missed executions, inconsistent behavior across nodes in a DON (some may have processed the event successfully, others not, depending on transient handler errors), and loss of trust that "registered = running." This falls under "misreporting/data tampering" and "unsafe workflow execution" impact categories, since core node behavior state diverges from the authoritative on-chain event stream without any error surfaced to the affected party.

### Likelihood Explanation
The `SyncStrategyEvent` code path is one of two supported sync strategies (`SyncStrategyEvent` / `SyncStrategyReconciliation`), selected via config [5](#0-4) [6](#0-5) . Any transient failure while handling an event (DB error, temporary engine-creation failure, resource contention) is sufficient to trigger permanent skipping of that specific event under this strategy, since the cursor has already advanced by the time the handler runs. This does not require malicious behavior by any external party — it's a straightforward operational fault triggerable by ordinary transient errors, making likelihood moderate-to-high in any deployment using the event strategy.

### Recommendation
Only advance/persist the cursor after the corresponding event has been successfully handled (or after exhausting a bounded retry policy with explicit error surfacing), mirroring the `SyncStrategyReconciliation` path's retry semantics (which does retry pending events, as shown by `generateReconciliationEvents` and its `retryCount`/`nextRetryAt` fields [7](#0-6) ). Alternatively, persist failed events into a durable retry queue akin to the reconciliation strategy instead of advancing past them in the event-driven loop.

### Proof of Concept
1. Configure a node with `SyncStrategy: SyncStrategyEvent` for the `WorkflowRegistry` syncer.
2. Owner registers/activates a workflow on-chain, emitting a `WorkflowRegisteredEvent`.
3. `readRegistryEventsLoop` fetches the log, immediately sets `cursor = log.Sequence.Cursor` [8](#0-7) .
4. `w.handleWithMetrics` is invoked and `workflowRegisteredEvent`'s `tryEngineCreate` step transiently fails (e.g., temporary error), returning an error that is only logged [9](#0-8) .
5. On the next tick, the loop queries only for logs after the already-advanced cursor, so the failed event is never re-fetched or retried, and the workflow is permanently left unregistered in the node's `EngineRegistry` despite being active on-chain.

Note: I was unable to fully inspect `handleWithMetrics`'s exact implementation and the complete `v2/handler.go`/`handler.go` bodies within the remaining tool budget, so the exact nature of transient handler failures (and whether any out-of-band reconciliation safety net exists for `SyncStrategyEvent` specifically) could not be fully confirmed; a Devin session with full file access would be needed to verify there is no compensating retry mechanism elsewhere in the event-strategy path.
