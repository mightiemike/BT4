### Title
Wallet Contract loses external caller's attached deposit when `address_check_callback` rejects a stale relayer target instead of refunding it - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`WalletContract::rlp_execute` is `#[payable]` and can be called by any external, unprivileged NEAR account (not just an access key controlled by the wallet owner) — this is exactly the scenario exercised by the existing `test_caller_refunds` test, where an external `caller` attaches a deposit and expects it back if the requested cross-contract call does not go through. When the target is an eth-implicit account and the transaction requires an address-registrar lookup, execution continues into `address_check_callback`. In one of its result branches the deposit tracked in `CallerDeposit` is silently dropped instead of refunded, permanently freezing the caller's attached NEAR.

### Finding Description
`inner_rlp_execute` builds a `CallerDeposit` from the attached deposit whenever the predecessor is not the wallet's own account: [1](#0-0) 

For `EOABaseTokenTransfer` targets that require an address-registrar lookup, the flow schedules `address_registrar.lookup(...).then(address_check_callback(target, action, caller_deposit))`: [2](#0-1) 

Inside `address_check_callback`, when the registrar lookup succeeds and returns `Some(account_id)` (meaning the address the relayer targeted is actually a registered named account, i.e. a faulty/stale relayer target), the code branches on whether the *signer* is the wallet itself: [3](#0-2) 

- If `signer_account_id == current_account_id` (i.e. the wallet owner used an access key and a relayer submitted the tx), a "ban relayer" promise is spawned, which eventually routes through `rlp_execute_callback`.
- If `signer_account_id != current_account_id` — i.e. the caller is an external, unprivileged account paying with its own transaction (exactly the pattern proven possible and expected by `test_caller_refunds`) — the function `return`s a `PromiseOrValue::Value(ExecuteResponse { success: false, ... })` **directly**, without ever creating a promise back to `rlp_execute_callback`.

The only place that refunds `CallerDeposit` is the `Failed` arm of `rlp_execute_callback`: [4](#0-3) 

Because the early `return` in `address_check_callback` bypasses `rlp_execute_callback` entirely, `caller_deposit` (which was already attached to the transaction and thus already credited to the wallet contract's account balance by the runtime) is never transferred back to the external caller. The deposit is permanently stuck in the wallet contract, with no code path left to reclaim it, since the whole request has already terminated with an `ExecuteResponse::success = false` value and `has_in_flight_tx` was reset to `false` at function entry.

This mirrors the reported bug class: a value-carrying call whose intended action does not execute because of an authorization/consistency check failing, but whose attached funds are nonetheless consumed and not returned to the sender, due to an early-exit branch that omits the refund logic present in the "normal" failure path.

### Impact Explanation
Any unprivileged external account can call `rlp_execute` on someone else's deployed Wallet Contract (an eth-implicit account contract that is part of nearcore's `near-wallet-contract` production code) with an attached NEAR deposit, targeting an eth-implicit address that requires an address-registrar check. If between transaction construction and execution the target address becomes a registered named account (a realistic race for any third-party or "faulty relayer" submitting stale/attacker-crafted calldata), the caller's attached deposit is irrecoverably lost inside the wallet contract — a concrete case of permanently frozen/lost funds triggered by a single ordinary transaction, not requiring any privileged, validator, or network-level capability.

### Likelihood Explanation
The `rlp_execute` entrypoint is explicitly designed to be callable by external, non-owner accounts that attach a deposit for relayer compensation or base-token/ERC-20 transfer flows (as demonstrated by the existing `test_caller_refunds` test). Triggering the vulnerable branch only requires that the registrar lookup returns `Some` for the given address while the caller is not the wallet's own signer — a condition that is reachable by any external caller/relayer submitting a transaction targeting an address that is (or becomes) registered, making this readily reproducible without any special privileges.

### Recommendation
In the `maybe_account_id.is_some()` branch of `address_check_callback` where `signer_account_id != current_account_id`, refund the `caller_deposit` (the same way `rlp_execute_callback`'s `Failed` arm does) before returning the `ExecuteResponse`, e.g. by spawning a `promise_batch_action_transfer` back to `caller_deposit.account_id` for `caller_deposit.yocto_near`, or by routing this branch through `rlp_execute_callback` so the existing refund logic is reused uniformly for all failure branches.

### Proof of Concept
1. Deploy a `WalletContract` for eth-implicit account `0xabc...` and an `AddressRegistrar` contract as in the existing test harness (`TestContext::new`).
2. As an external account `caller` (not the wallet owner, no access key on the wallet), craft an RLP transaction whose `to` field is an unregistered address `0xdead...` different from `0xabc...`'s own address, forming an `EOABaseTokenTransfer` with `address_check: Some(0xdead...)`.
3. Before submitting, register `0xdead...`'s corresponding account id in the `AddressRegistrar` (simulating the registrar state changing, or an attacker deliberately registering it first).
4. Call `wallet_contract.rlp_execute(target, tx_bytes_b64)` from `caller` with a non-zero attached deposit (mirroring `test_caller_refunds`'s pattern using `rlp_execute_from`).
5. The registrar lookup returns `Some(account_id)`; since `env::signer_account_id() != current_account_id`, `address_check_callback` returns `ExecuteResponse{success:false, ...}` directly.
6. Observe that `caller`'s balance never regains the attached deposit (unlike in `test_caller_refunds`, where balance is restored on failure) — the deposit remains permanently held by the wallet contract account.
