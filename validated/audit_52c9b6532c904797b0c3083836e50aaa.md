### Title
Missing minimum lock-period enforcement in `DelegateResourceActuator` allows near-zero-duration "locks" - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
`DelegateResourceContract` supports locking delegated bandwidth/energy for a caller-specified `lockPeriod`. The validation logic only bounds the lock period from above (against `maxDelegateLockPeriod`) but never enforces a minimum, unlike the legacy `FreezeBalanceActuator` which explicitly enforces both a `minFrozenTime` and `maxFrozenTime`. This mirrors the reported bug class: a duration-check that verifies an upper/expiry bound but omits the required minimum-duration bound, letting users "lock" funds for far less time than the system's staking/locking model intends.

### Finding Description
In `DelegateResourceActuator.validate()`, when `lock` is true and `dynamicStore.supportMaxDelegateLockPeriod()` is enabled, the only bound check performed is: [1](#0-0) 

```java
if (lock && dynamicStore.supportMaxDelegateLockPeriod()) {
  long lockPeriod = getLockPeriod(true, delegateResourceContract);
  long maxDelegateLockPeriod = dynamicStore.getMaxDelegateLockPeriod();
  if (lockPeriod < 0 || lockPeriod > maxDelegateLockPeriod) {
    throw new ContractValidateException(...);
  }
```

This only rejects negative or overly-large lock periods; any positive value up to `maxDelegateLockPeriod` (including `1`, i.e. a single block interval, ~3 seconds via `BLOCK_PRODUCED_INTERVAL`) is accepted [2](#0-1) . There is no analog to `minFrozenTime`/`getMinFrozenTime()`, which the plain freeze path enforces explicitly: [3](#0-2) 

```java
long frozenDuration = freezeBalanceContract.getFrozenDuration();
long minFrozenTime = dynamicStore.getMinFrozenTime();
long maxFrozenTime = dynamicStore.getMaxFrozenTime();
...
if (needCheckFrozeTime && !(frozenDuration >= minFrozenTime
    && frozenDuration <= maxFrozenTime)) {
  throw new ContractValidateException(...);
}
```

A grep across the repo confirms there is no `minDelegateLockPeriod`/minimum-duration property defined anywhere for delegate locking — only `getMaxDelegateLockPeriod()` exists [4](#0-3) .

When the transaction executes, `expireTime` is computed directly from the attacker-controlled `lockPeriod`: [5](#0-4) 

```java
long expireTime = 0;
if (lock) {
  expireTime = now + lockPeriod * BLOCK_PRODUCED_INTERVAL;
}
```

So a user can create a "locked" delegation (`lock = true`) with `lockPeriod = 1`, producing an `expireTime` only one block interval away, effectively bypassing the intended lock semantics.

Additionally, when re-delegating onto an existing locked position, `validRemainTime` only prevents the *new* lock period from being **shorter than the remaining time of the previous lock** — it does not enforce any absolute minimum lock duration for the position as a whole: [6](#0-5) 

### Impact Explanation
The `lock` flag on `DelegateResourceContract` is intended to guarantee that delegated resources remain committed (non-reclaimable, and per `TransferUsage`/vote-weight related invariants elsewhere in the codebase treat locked resources as a stronger guarantee than unlocked ones) for a meaningful period. Because no minimum lock duration is enforced, this guarantee can be trivially defeated: a caller can mark a delegation as "locked" while effectively expiring it after a single block, undermining any downstream logic, contracts, or off-chain integrations that rely on the "locked" flag/expire time to represent a committed minimum staking duration. This is an accounting/invariant-violation issue rather than a direct fund-theft bug, but it breaks the intended lock guarantee analogous to the original report.

### Likelihood Explanation
This is directly and trivially reachable by any unprivileged account via a normal `DelegateResourceContract` transaction with `lock=true` and a small explicit `lockPeriod`; no privileged role or special state is required. The only precondition is that `supportMaxDelegateLockPeriod` is enabled on the network (a chain parameter, not a per-user gate).

### Recommendation
Introduce and enforce a `minDelegateLockPeriod` dynamic property, analogous to `minFrozenTime`, and validate it symmetrically to the max-bound check:
```java
long minDelegateLockPeriod = dynamicStore.getMinDelegateLockPeriod();
if (lockPeriod < minDelegateLockPeriod || lockPeriod > maxDelegateLockPeriod) {
  throw new ContractValidateException(...);
}
```

### Proof of Concept
1. Ensure `supportMaxDelegateLockPeriod()` is enabled and `maxDelegateLockPeriod` set to its normal chain value.
2. Submit a `DelegateResourceContract` with `lock=true`, `lockPeriod=1` (i.e., one `BLOCK_PRODUCED_INTERVAL`, ~3 seconds).
3. `DelegateResourceActuator.validate()` passes because `1 >= 0 && 1 <= maxDelegateLockPeriod`.
4. `execute()` sets `expireTime = now + 1 * BLOCK_PRODUCED_INTERVAL`, so the resource unlocks after essentially one block, despite being flagged as `lock = true`.
