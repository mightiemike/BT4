I have enough evidence to establish the analog vulnerability in java-tron's DPoS voter reward system, which mirrors the Syndicate's "rewards lost when no registered participants" bug class.

### Title
Voter rewards accrued while a witness has zero effective votes are permanently lost from the Vi (value-per-share) accounting - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
Java-tron's new reward algorithm distributes SR (witness) rewards to voters via a cumulative "value per share" (`Vi`) mechanism, analogous to the Syndicate's `accumulatedETHPerFreeFloatingShare`. When a witness earns block/transaction-fee rewards during a cycle in which its recorded vote count is `0`, the `Vi` delta for that cycle is never computed — the reward is silently dropped from the distribution ledger, exactly like EIP1559 rewards received by the Syndicate while `numberOfRegisteredKnots == 0`.

### Finding Description
Witness rewards are accrued per-cycle into `DelegationStore` via `addReward` (called from `MortgageService.payReward`), after the brokerage cut is paid directly to the witness itself through `adjustAllowance`. The remainder — meant to be distributed to voters — is expected to be captured into the per-cycle `Vi` accumulator by `accumulateWitnessVi`: [1](#0-0) 

If `voteCount == 0` for that cycle (the same condition used to detect the analog of "no registered knots"), the function takes the `if` branch and merely re-writes the previous `Vi` unchanged — it does **not** fold the accrued `reward` into the cumulative Vi at all: [2](#0-1) 

This call is driven every maintenance cycle for **every** witness using the witness's current in-memory vote count, prior to that cycle's vote-count updates being applied: [3](#0-2) 

Because `voteCount` here reflects the vote count that was in effect for the witness during the just-ended cycle, any witness that is elected/active with `0` recorded votes for a cycle (e.g. genesis witnesses, private/low-participation networks, or timing windows where votes were withdrawn between maintenance runs) will still accrue block and transaction-fee rewards via `payBlockReward`/`payTransactionFeeReward`, but that non-brokerage portion of the reward is never attached to any `Vi` delta, and therefore can never be claimed by any voter through `computeReward`/`VoteRewardUtil.computeReward`, which drives voter withdrawals off `deltaVi`: [4](#0-3) 

There is no code path anywhere in `MortgageService`, `DelegationStore`, or `MaintenanceManager` that reclaims this "orphaned" reward back to the witness, a treasury, or reallocates it to a later cycle's Vi once the witness regains votes. This is structurally identical to the reported bug: EIP1559 rewards received while `numberOfRegisteredKnots == 0` are dropped because `updateAccruedETHPerShares`'s `else` branch has no handling logic, and later distribution keys off a share/vote denominator that was zero at accrual time.

### Impact Explanation
The voter-attributable share of a witness's block/tx-fee rewards accrued in a zero-vote cycle becomes permanently unaccounted and unclaimable — a real, non-recoverable loss of TRX rewards from the reward pool's perspective, since the value is retained in `AccountStore` balances at the protocol level (paid via the block reward funding mechanism) but never surfaced to any withdrawable balance. This is an accounting/settlement defect: reward "shares" and actual paid-out reward diverge silently, with no revert, alert, or recovery mechanism.

### Likelihood Explanation
This requires a witness to be actively producing blocks (and thus earning rewards) while having a recorded vote count of `0` for that specific cycle in `DelegationStore`. This is realistically reachable on chain-genesis or low-participation (private/test) networks where witnesses can be active despite having no votes, and it is at least conceivable on mainnet during transient windows where a witness's votes drop to zero right at a maintenance-cycle boundary while it remains in the (stale) active/standby witness set for that cycle. It does not require any privileged action — it is a passive consequence of normal DPoS vote fluctuation and witness activity, matching the "unprivileged-user analog" requirement.

### Recommendation
In `DelegationStore.accumulateWitnessVi`, when `voteCount == 0` but `reward != 0`, do not silently drop the reward. Either (a) carry the un-attributable reward forward to be folded into the Vi delta of the next cycle in which the witness has a non-zero vote count, or (b) return the reward to the witness's own allowance (since there are no voters to whom it can be fairly attributed), rather than leaving it stranded in the per-cycle reward ledger with no corresponding Vi update.

### Proof of Concept
1. Configure a witness `W` to be active (top-27 or standby) while its recorded `WitnessCapsule.voteCount` is `0` (e.g. fresh genesis network before any votes are cast, or unvote all TRX from `W` right before a maintenance cycle where `W` is still counted active from the prior cycle's snapshot).
2. Let `W` produce a block in this cycle; `MortgageService.payBlockReward`/`payTransactionFeeReward` → `payReward` computes `brokerageAmount` (paid instantly to `W` via `adjustAllowance`) and calls `delegationStore.addReward(cycle, W, remainder)`.
3. At the next `MaintenanceManager.doMaintenance()`, `delegationStore.accumulateWitnessVi(curCycle, W, 0)` is invoked (vote count still `0` for the ended cycle) — the `reward == 0 || voteCount == 0` branch fires, and `Vi` for `W` at `curCycle` is left equal to `Vi` at `curCycle - 1`.
4. Even after `W` later receives votes and voters try to claim rewards via `MortgageService.withdrawReward`/`queryReward` (or `VoteRewardUtil` from TVM), `computeReward` only ever sees `deltaVi` from cycles after votes existed — the reward recorded in step 2 is never reflected in any `Vi`, so it is unclaimable by anyone, permanently lost from the distributable reward pool.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
