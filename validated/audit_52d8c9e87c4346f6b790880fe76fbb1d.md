### Title
Divide-before-multiply truncation in legacy `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` formulas can zero out or under-allocate a user's frozen-TRX energy/bandwidth limit - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
The Sherlock report describes `claim_batch()` computing `amount_per_claim = batch.amount * release_amount / 1e18` and then multiplying by `number_of_claims`, i.e. dividing before multiplying, which truncates the intermediate result and can yield zero even though a nonzero amount is legitimately owed. The same divide-then-multiply pattern exists in java-tron's legacy (non-hardened) resource-limit formulas used to translate a user's frozen TRX balance into an energy/bandwidth limit.

### Finding Description
In `EnergyProcessor.calculateGlobalEnergyLimit`, when the chain has not enabled the `allowHardenResourceCalculation` fork, the limit is computed as:
```java
long energyWeight = frozeBalance / TRX_PRECISION;              // divide first (integer truncation)
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));  // then multiply
``` [1](#0-0) 

This divides `frozeBalance` by `TRX_PRECISION` (1,000,000) first, discarding any remainder, before multiplying by the `totalEnergyLimit/totalEnergyWeight` ratio. Exactly like the reported Andromeda bug, dividing before multiplying discards precision that a "multiply first" ordering would have preserved. The same pattern appears in `RepositoryImpl.calculateGlobalEnergyLimit` used by the TVM: [2](#0-1) , and in `ResourceProcessor.calculateGlobalLimitV1` which still truncates `frozeBalance / TRX_PRECISION` before the (now BigInteger-safe) multiplication: [3](#0-2) .

Notably, the java-tron team has already partially remediated this exact bug class for the V2 formula (`calculateGlobalLimitV2`), explicitly noting in a code comment that the fix "preserves fractional weight ... through the multiplication and only truncates at the final divide" specifically to avoid this precision-loss class: [4](#0-3) . Their own regression test directly demonstrates the "buggy" truncate-then-multiply result differing from the corrected multiply-then-divide result: [5](#0-4) 

However, this hardening is opt-in via the `allowHardenResourceCalculation` dynamic property/fork flag [6](#0-5) , and `EnergyProcessor.calculateGlobalEnergyLimit`'s legacy branch (`frozeBalance / TRX_PRECISION` then multiply) is still present in the codebase and executed whenever the hardening flag is not active for a given chain/fork state [7](#0-6) .

### Impact Explanation
`calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` determine how much energy/bandwidth an account is entitled to from its frozen TRX, which is used by `getAccountLeftEnergyFromFreeze` and ultimately by `VMActuator` to size a caller's/origin's free energy for TVM execution: [8](#0-7) . Truncating `frozeBalance / TRX_PRECISION` before multiplying by the limit/weight ratio systematically under-computes (in the worst case, zeroes out) the free energy/bandwidth an unprivileged user is entitled to when `frozeBalance` is not an exact multiple of `TRX_PRECISION`, or when the fractional weight matters at scale (as demonstrated by java-tron's own test comparing "buggy" vs correct results). This is a resource-accounting/underpriced-work class bug: users can be forced to pay TRX fees for energy/bandwidth they should have gotten for free from their frozen stake, or their computed limit can diverge from the economically correct value.

### Likelihood Explanation
Likelihood is moderate: the buggy legacy branch is only exercised while `allowHardenResourceCalculation` is disabled for a given deployment/fork state, and networks that have already activated the hardening proposal are not affected. However, the vulnerable legacy code paths remain live in the codebase (not removed), are reachable via completely permissionless flows (freezing TRX for energy/bandwidth and executing/triggering a smart contract), and the discrepancy is deterministic and reproducible for any account whose frozen balance is not a clean multiple of `TRX_PRECISION` relative to the network's weight/limit ratio.

### Recommendation
Ensure the multiply-before-divide fix (as already implemented for `calculateGlobalLimitV2`/hardened path) is made the default and unconditional behavior rather than opt-in, i.e. remove or deprecate the legacy `frozeBalance / TRX_PRECISION` truncate-then-multiply branches in `EnergyProcessor.calculateGlobalEnergyLimit`, `RepositoryImpl.calculateGlobalEnergyLimit`, and `BandwidthProcessor.calculateGlobalNetLimit`, always computing via `BigInteger.valueOf(frozeBalance).multiply(totalLimit).divide(TRX_PRECISION.multiply(totalWeight))` semantics.

### Proof of Concept
Using `EnergyProcessor.calculateGlobalEnergyLimit`'s legacy formula with `TRX_PRECISION = 1_000_000`:
- Let `frozeBalance = 1_999_999` (just under 2 TRX in SUN), `totalEnergyLimit = 100`, `totalEnergyWeight = 3`.
- Legacy: `energyWeight = 1_999_999 / 1_000_000 = 1` (truncated), then `1 * (100/3) = 33`.
- Correct (multiply-first): `(1_999_999 * 100) / (1_000_000 * 3) = 199_999_900 / 3_000_000 = 66` (approximately double the truncated result).

This mirrors java-tron's own regression assertion contrasting the "buggy" value with the corrected value: [9](#0-8) , confirming the divide-before-multiply precision loss is real and quantifiable in this codebase whenever the hardening flag is not active.

          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }

  }

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
```
