### Title
Stale voting-power snapshot used for reward computation when TVM native contract vote/freeze/unfreeze operations are combined in a single transaction - (File: `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
`VoteRewardUtil.withdrawReward` (invoked from `VoteWitnessProcessor.execute` and `UnfreezeBalanceV2Processor.execute`, both reachable from TVM opcodes `voteWitness`/`unfreezeBalanceV2` in `actuator/src/main/java/org/tron/core/vm/program/Program.java`) snapshots an account's vote allocation once per cycle via `repository.updateAccountVote(address, endCycle, accountCapsule)`. If the same account's vote/unfreeze operation is invoked a second time within the same cycle (which, unlike the Solidity `_checkpoint` case tied to `block.timestamp`, spans an entire voting cycle and is therefore trivially reachable within one transaction that chains multiple native-contract calls through a smart contract), the second call's `withdrawReward` short-circuits without refreshing the snapshot, leaving the reward accounting keyed to the stale, intermediate vote allocation instead of the final one.

### Finding Description
`VoteRewardUtil.withdrawReward` at [1](#0-0)  implements per-cycle checkpointing analogous to `_checkpoint` in the reported VotingEscrow bug:

```
if (beginCycle == currentCycle) {
  AccountCapsule account = repository.getAccountVote(beginCycle, address);
  if (account != null) {
    return;
  }
}
...
repository.updateBeginCycle(address, endCycle);
repository.updateEndCycle(address, endCycle + 1);
repository.updateAccountVote(address, endCycle, accountCapsule);
```

On the first call within a cycle `C`, the current vote list is snapshotted via `updateAccountVote(address, C, accountCapsule)`. If a *second* native-contract vote/unfreeze operation for the same address executes later in the same block/cycle (e.g. a contract that calls the TVM `voteWitness` opcode twice, or `voteWitness` followed by `unfreezeBalanceV2`, both of which call `VoteRewardUtil.withdrawReward`), the guard `beginCycle == currentCycle` is now true and `getAccountVote(beginCycle, address)` returns the already-stored (non-null) snapshot, so the method returns immediately — it never re-snapshots the account's updated vote list.

Because `VoteWitnessProcessor.execute` ( [2](#0-1) ) mutates and persists the live `AccountCapsule` votes regardless of whether `withdrawReward` updated the snapshot, the persisted "current" account state diverges from the cycle-`C` snapshot used later for reward computation. When cycle `C` closes and `withdrawReward` is eventually called again (in a future cycle), `computeReward` uses the stale snapshot stored under key `(C, address)` — reflecting the account's votes as of the *first* call in cycle `C` — not the final vote distribution after the second call in the same transaction. This is the direct analog of the reported bug: a per-period checkpoint is written once and silently skipped on subsequent same-period calls, so voting power used for downstream reward accounting does not reflect the final state established within the same transaction.

`UnfreezeBalanceV2Processor.execute` calls the same `VoteRewardUtil.withdrawReward` before mutating votes ( [3](#0-2) ), so mixing `voteWitness` and `unfreezeBalanceV2` calls for the same account within one transaction reaches the identical stale-snapshot condition.

### Impact Explanation
This causes incorrect SR (super representative) voting reward accounting: an account's reward for a cycle is computed off a vote allocation that does not match its actual, final on-chain vote weight for that cycle, and/or a witness's aggregate vote-based `Vi` reward accrual is computed against a distribution that never actually represents the voter's true holdings for that period. This results in improperly increased or decreased TRX reward payouts (via `adjustAllowance`), i.e. asset/accounting corruption, reachable purely from a broadcast smart-contract transaction with no privileged access required.

### Likelihood Explanation
Reachability requires only deploying a contract that issues two TVM vote/freeze-related opcodes (`voteWitness`, `unfreezeBalanceV2`) affecting the same owner address within a single transaction — a straightforward, unprivileged operation available to any user, and directly analogous to the `create_lock` + `increase_amount` same-tx pattern in the referenced report. The condition is gated behind `beginCycle == currentCycle`, which is the common case for any account that already voted earlier in the ongoing cycle, making it easy to trigger deliberately or unintentionally.

### Recommendation
Do not gate the snapshot write solely on presence of an existing per-cycle `AccountVote` record. Instead, when a same-cycle re-invocation occurs, overwrite the stored `endCycle` snapshot with the current, most up-to-date `AccountCapsule` vote list (mirroring the recommended VotingEscrow fix of overwriting rather than skipping when the checkpoint key is unchanged), ensuring the reward computation always reflects the final vote state at the end of the transaction sequence, not just the first mutation within the cycle.

### Proof of Concept
Not executed against a live node; reasoning based on static code trace:
1. Deploy a contract, or send sequential transactions within the atomic scope enabled by internal calls, that invoke TVM `voteWitness(w1, 100)` then, within the same transaction/cycle, `voteWitness(w2, 100)` for the same owner (both routed through `VoteWitnessProcessor.execute` → `VoteRewardUtil.withdrawReward`).
2. First call: `beginCycle < currentCycle` path executes, ultimately calling `repository.updateAccountVote(address, currentCycle, accountCapsuleWithW1Vote)`.
3. Second call: `beginCycle == currentCycle` now true; `getAccountVote(currentCycle, address)` returns non-null (the W1 snapshot) → method returns without updating the snapshot, even though `VoteWitnessProcessor.execute` proceeds to persist the account's votes as W2.
4. On cycle rollover, the next `withdrawReward` call computes the cycle's reward using the stale W1-vote snapshot instead of the actual final W2 vote allocation, producing an incorrect reward.

  public static void withdrawReward(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmVote()) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long beginCycle = repository.getBeginCycle(address);
    long endCycle = repository.getEndCycle(address);
    long currentCycle = repository.getDynamicPropertiesStore().getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;
      }
      beginCycle += 1;
    }
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      repository.updateBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);
  }

  public void execute(VoteWitnessParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getVoterAddress();
    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);

    VotesCapsule votesCapsule = repo.getVotes(ownerAddress);
    if (votesCapsule == null) {
      votesCapsule = new VotesCapsule(ByteString.copyFrom(ownerAddress),
          accountCapsule.getVotesList());
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    Map<ByteString, Long> voteMap = new HashMap<>();
    Iterator<Protocol.Vote> iterator = param.getVotes().iterator();
    try {
      long sum = 0;
      while (iterator.hasNext()) {
        Protocol.Vote vote = iterator.next();

        byte[] witnessAddress = vote.getVoteAddress().toByteArray();
        /*
          Already covered while doing maintenance in MaintenanceManager.java, for tvm performance,
          we remove the account check
         */
//        if (repo.getAccount(witnessAddress) == null) {
//          throw new ContractValidateException(
//              ACCOUNT_EXCEPTION_STR + StringUtil.encode58Check(witnessAddress) + NOT_EXIST_STR);
//        }
        if (repo.getWitness(witnessAddress) == null) {
          throw new ContractExeException(
              WITNESS_EXCEPTION_STR + StringUtil.encode58Check(witnessAddress) + NOT_EXIST_STR);
        }

        long voteCount = vote.getVoteCount();
        if (voteCount < 0) {
          throw new ContractExeException("Vote count must not be less than 0");
        } else if (voteCount == 0) {
          iterator.remove();
        } else {
          sum = LongMath.checkedAdd(sum, voteCount);
          // merge vote for same witness
          voteMap.put(vote.getVoteAddress(),
              LongMath.checkedAdd(voteMap.getOrDefault(vote.getVoteAddress(), 0L), voteCount));
        }
      }

      long tronPower;
      if (repo.getDynamicPropertiesStore().supportUnfreezeDelay()
          && repo.getDynamicPropertiesStore().supportAllowNewResourceModel()) {
        tronPower = accountCapsule.getAllTronPower();
      } else {
        tronPower = accountCapsule.getTronPower();
      }
      sum =  LongMath.checkedMultiply(sum, TRX_PRECISION);
      if (sum > tronPower) {
        throw new ContractExeException(
            "The total number of votes[" + sum + "] is greater than the tronPower[" + tronPower
                + "]");
      }
    } catch (ArithmeticException e) {
      throw new ContractExeException(e.getMessage());
    }

    for (Map.Entry<ByteString, Long> entry : voteMap.entrySet()) {
      accountCapsule.addVotes(entry.getKey(), entry.getValue());
      votesCapsule.addNewVotes(entry.getKey(), entry.getValue());
    }
    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    repo.updateVotes(ownerAddress, votesCapsule);
  }
