### Title
`liquidate-multi` silently commits partial liquidation state when bad-debt socialization fails mid-position - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate-multi` iterates over a batch of liquidation requests with `(ok (map call-liquidate positions))`. Because the batch wrapper itself always returns `ok`, an internal failure inside one position's `liquidate` call does not roll back that call's already-committed cross-contract effects (debt reduction, collateral transfer) if the failure happens *after* those effects executed. This can leave a borrower with debt that is fully uncollateralized but never socialized, because the bad-debt write-down step is the last operation in the call and its failure is absorbed as a mere "err" list entry rather than a transaction abort. [1](#0-0) 

### Finding Description
`liquidate` executes, in order, within a single call:
1. `vault-system-repay` — liquidator's debt tokens are pulled and applied to the vault (`try!`).
2. `debt-remove-scaled` on `.v0-market-vault` — borrower's scaled debt is reduced (`try!`).
3. `collateral-remove` on `.v0-market-vault` — collateral is transferred to the liquidator (`try!`).
4. If `no-collateral-left` is true, a `fold` over `socialize-debt-asset` attempts to write down any remaining unbacked debt, gated by `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)`. [2](#0-1) 

Steps 1–3 are cross-contract calls that commit their state changes as soon as they succeed — a later failure inside the *same* `liquidate` invocation does not retroactively undo them unless the failure propagates all the way to the top-level transaction response and that top-level response is `err`.

In `liquidate-multi`, the top-level function is:

```
(define-public (liquidate-multi (positions ...))
  (ok (map call-liquidate positions)))
``` [1](#0-0) 

`call-liquidate` invokes `liquidate` as a same-contract function call (not `contract-call?`), and its response is simply collected into a list by `map`: [3](#0-2) 

Because `liquidate-multi` always returns `(ok ...)`, the Stacks VM commits the *entire* transaction, including every state mutation performed inside every `call-liquidate` invocation — regardless of whether that particular invocation's own return value was `ok` or `err`. If, for a given position, steps 1–3 (repay, debt-remove-scaled, collateral-remove) succeed but step 4 (bad-debt socialization) then fails and returns `ERR-BAD-DEBT-SOCIALIZATION-FAILED` via `asserts!`, that `err` is merely recorded as one element of the output list — the debt reduction and full collateral transfer from steps 1–3 remain permanently committed on-chain.

This produces a borrower position with debt still recorded (only partially reduced/undsocialized) but zero remaining collateral (since `collateral-remove` already sent it all out, which is exactly the condition that set `no-collateral-left` to true and triggered the bad-debt path). The remaining debt is never written down against the vault's liquidity index, unlike the intended socialization flow.

### Impact Explanation
This lands on **protocol insolvency**: the vault's aggregate liquidity index/accounting assumes an unresolved debt balance is still economically backed, but the corresponding collateral has already been fully paid out to the liquidator in the same (seemingly "failed") call. The debt becomes permanently unbacked ("bad debt") that the intended write-down mechanism never applies, corrupting future interest-index accrual for all lenders in that asset's vault (silent value leakage / insolvency), since `liquidate-multi` is the only externally documented path that can hit this partial-failure absorption while still committing prior steps.

### Likelihood Explanation
Reachable via a single call to the public `liquidate-multi` entry point with a batch that includes a position whose collateral list becomes fully exhausted by `collateral-remove` while the subsequent `socialize-debt-asset` fold fails (e.g., a nested `vault-socialize-debt` or `debt-remove-scaled` call failing for any of the borrower's other still-tracked debt entries). No cross-user interference or DAO action is required — it is a single-transaction, single-caller sequence purely dependent on the state of one borrower's position and the batch liquidator's chosen parameters.

### Recommendation
Do not wrap `liquidate-multi`'s output unconditionally in `ok`. Either (a) require the bad-debt socialization step to run and succeed as an atomic prerequisite before committing `debt-remove-scaled`/`collateral-remove` for that position, or (b) explicitly detect an `err` result from `call-liquidate` for a position and revert (or skip performing) that position's earlier mutating calls entirely (e.g., by having `liquidate` internally guarantee all-or-nothing execution per position rather than relying on the outer batch wrapper's return value for atomicity).

### Proof of Concept
1. Borrower has a position with two debt assets (A and B) and collateral fully consumed by liquidating asset A's debt.
2. Liquidator calls `liquidate-multi` with a single position targeting debt asset A, providing `debt-amount` sufficient to remove all of A's debt and all remaining collateral.
3. Inside `liquidate`: `vault-system-repay` succeeds (liquidator's tokens pulled), `debt-remove-scaled` succeeds (A's scaled debt zeroed on `.v0-market-vault`), `collateral-remove` succeeds and transfers all remaining collateral to the liquidator, causing `no-collateral-left` to evaluate `true`. [4](#0-3) 
4. The `socialize-debt-asset` fold attempts to socialize borrower's remaining debt-B entry via `vault-socialize-debt`; if that call fails for any reason (e.g., vault-level constraint), `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` triggers, and `liquidate` returns `err`. [5](#0-4) 
5. `call-liquidate` returns this `err` response as a list element; `liquidate-multi` still returns `(ok (list (err u...)))`, so the whole transaction commits.
6. Net effect on-chain: borrower's debt-A is zeroed and all collateral transferred out, but debt-B remains fully recorded with zero backing collateral and was never socialized — an unbacked debt entry now permanently distorts the debt-B vault's liquidity index for all depositors.
