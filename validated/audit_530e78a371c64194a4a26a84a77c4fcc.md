### Title
Sandwichable on-chain swap quote in gas auto-swap and refund paths enables MEV extraction from user deposits and protocol refunds - (File: x/uexecutor/keeper/execute_inbound_gas.go, x/uexecutor/keeper/execute_inbound_gas_and_payload.go, x/uexecutor/keeper/outbound.go, x/uexecutor/keeper/evm.go)

### Summary
The Flayer report's root cause is that a protocol-driven value transfer (fee donation) is priced/executed atomically inside the same transaction using on-chain state that MEV searchers can manipulate around it (JIT liquidity + sandwich), extracting value that should have gone to honest participants. Push Chain has a structurally identical pattern in its gas-token auto-swap logic: `GetSwapQuote` reads the current Uniswap V3 `QuoterV2` price and computes `minPCOut` with a fixed 5% slippage tolerance in the very same call stack that immediately executes the swap via `CallPRC20DepositAutoSwap` / `CallUniversalCoreRefundUnusedGas`. Because the quote and the execution are not separated by any TWAP, commit-reveal, or per-block cap, and because the surrounding EVM transactions in the same block are attacker-controlled, this swap is sandwichable exactly like the Flayer donation.

### Finding Description
Three call sites fetch a live AMM quote and immediately spend it as the swap floor within the same logical operation:

- `ExecuteInboundGas` (GAS inbound path): fetches `quote` via `GetSwapQuote`, computes `minPCOut = quote * 95 / 100`, then calls `CallPRC20DepositAutoSwap` with that floor. [1](#0-0) 

- `gasAndPayloadDepositAutoSwap` (GAS_AND_PAYLOAD inbound path): identical quote → 5%-slippage → swap pattern. [2](#0-1) 

- `applyGasRefund` → `getSwapQuoteForRefund` (outbound excess-gas refund path): same pattern, this time swapping the relayer's leftover gas token back to native PC on behalf of the depositor/sender. [3](#0-2) [4](#0-3) 

Both the quote fetch and the swap execution ultimately go through: [5](#0-4) [6](#0-5) 

The upgrade note confirms this is an intentional (but insufficient) mitigation replacing a previous zero-slippage call: "GAS and GAS_AND_PAYLOAD inbound routes now call the Uniswap V3 QuoterV2 contract to obtain an on-chain swap quote and pass minPCOut (quote × 95%) ... replacing the previous 0-slippage call." [7](#0-6) 

Because Push Chain's `x/uexecutor` module executes this swap as a `DerivedEVMCall`/`CallEVM` triggered by ordinary user activity (an inbound deposit reaching quorum, or an outbound observation reaching quorum), and because the exact block in which the swap fires is knowable in advance (an attacker watching `MsgVoteInbound`/`MsgVoteOutbound` votes accumulate toward threshold can predict the finalizing transaction), an attacker with access to the same block's EVM transaction ordering can:
1. Front-run: swap a large amount of the PRC20 gas token into the WPC/PC pool (or add lopsided liquidity) to depress the quoted output price just before the module's `GetSwapQuote` call executes.
2. Let the module's `depositPRC20WithAutoSwap` / `refundUnusedGas(withSwap=true)` execute against the manipulated price — the 5% band is easily exceeded by an attacker with enough capital for one block, and even when it isn't exceeded, the manipulated price is still worse than fair value by up to that full 5%.
3. Back-run: reverse the initial swap, capturing the value the depositor/relayer refund lost, minus pool fees.

This is the same "no protection against just-in-time price manipulation around an atomic protocol-triggered swap" root cause as the Flayer donation sandwich, just applied to Push Chain's native gas-token auto-swap and refund-swap instead of a Uniswap V4 `donate()` call.

### Impact Explanation
Every GAS / GAS_AND_PAYLOAD inbound deposit, and every outbound excess-gas refund that takes the swap branch, converts user- or protocol-custodied PRC20 into native PC at a price that can be pushed down by up to the full 5% slippage tolerance by an unprivileged attacker within the same block, with the attacker capturing the difference via a sandwich trade. This directly corrupts native/PRC20 asset accounting and refund accounting for ordinary users (`CorePRC20/native asset accounting`, `refund accounting` in the allowed-impact list), and the value is extracted from users/protocol every time an inbound or refund swap fires — not a rare edge case, but potentially every large deposit or refund.

### Likelihood Explanation
No malicious validator, admin, or relayer is required — only an ordinary EVM user with capital and mempool visibility for the target block, which matches the "unprivileged external attacker" and "reachable from ordinary user deposits" gate. The trigger condition (predictable finalization block from public vote accumulation, or simply monitoring pending `MsgVoteInbound`/`MsgVoteOutbound` transactions) is realistic on any chain with a visible mempool, exactly as flagged in the original Uniswap `donate()` documentation cited by the H-20 report. Likelihood is higher for larger deposits/refunds where the 5% band represents meaningful absolute value.

### Recommendation
- Do not derive `minPCOut` from a spot quote fetched in the same transaction that executes the swap; use a time-weighted average price (TWAP) oracle over multiple blocks, or a governance/oracle-set reference price, to bound acceptable slippage.
- Alternatively, cap the maximum swap size per block/per pool that the module will execute atomically, or split large auto-swaps across blocks to reduce the capital efficiency of a sandwich.
- Consider routing gas-token auto-swaps and refund-swaps through a private/protected execution path (e.g., a dedicated pool with restricted LP composition, or an off-chain relayer-committed price) rather than a fully public AMM pool subject to same-block manipulation.

### Proof of Concept
1. Monitor pending `MsgVoteInbound` transactions for a `TxType_GAS` or `TxType_GAS_AND_PAYLOAD` inbound approaching the 2/3 vote threshold, or `MsgVoteOutbound` transactions approaching threshold with `GasFeeUsed < GasFee` (refund path).
2. In the block where the final vote is expected to land, submit a front-running EVM transaction that swaps a large amount of the target PRC20 gas token into the WPC pool (or manipulates the pool's active-liquidity price) to depress `quoteExactInputSingle`'s expected output.
3. Allow the validator's finalizing vote transaction to execute, triggering `ExecuteInboundGas`/`gasAndPayloadDepositAutoSwap`/`applyGasRefund`, which reads the manipulated quote via `GetSwapQuote` and executes `depositPRC20WithAutoSwap`/`refundUnusedGas` at up to 5% worse than fair value. [8](#0-7) 
4. Submit a back-running EVM transaction reversing step 2's swap, capturing the spread extracted from the user's deposit or the protocol's refund.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
}

func (k Keeper) CallPRC20DepositAutoSwap(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount, fee, minPCOut *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: depositPRC20WithAutoSwap",
		"prc20", prc20Address.Hex(),
		"recipient", to.Hex(),
		"amount", amount.String(),
		"fee", fee.String(),
		"min_pc_out", minPCOut.String(),
	)
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // who is sending the transaction
		handlerAddr,        // destination: Handler contract
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20WithAutoSwap",
		prc20Address,
		amount,
		to,
		fee,
		minPCOut,
		big.NewInt(0), // deadline = 0 → contract uses its default
	)
}
