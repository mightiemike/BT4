### Title
`accrue()` pause silently passes through stale indexes instead of reverting - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The vault's `accrue` pause flag does not gate the operations that depend on the accrual index. Instead of causing dependent operations to revert while accrual is paused, `accrue()` silently returns the stale `index`/`lindex` values and `ok`s the call, letting `deposit`, `redeem`, `system-borrow`, and `system-repay` continue to execute against economically stale interest-rate state. This mirrors the reported SAR bug pattern: an edge-case branch (the "paused" case) is "corrected" by returning a plausible-looking but wrong value instead of properly failing/erroring.

### Finding Description
Every vault's `accrue` function checks the `accrue` bit of `pause-states` and, if set, short-circuits with the currently stored `index`/`lindex` rather than computing (or refusing to compute) the up-to-date values: [1](#0-0) 

```
(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          ...)))
```

All lending entry points (`system-borrow`, `system-repay`, `deposit`, `redeem`) call `(try! (accrue))` first and then immediately re-read `(var-get index)`/`(var-get lindex)` to size scaled debt/shares: [2](#0-1) 

Because `accrue` never reverts when paused, none of these dependent calls are blocked either — they simply proceed using the frozen `index`/`lindex` as if they were current. Time (and thus interest that should be reflected in `index`/`lindex`) continues to elapse while the pause is active, but the debt/liquidity indexes are never updated to reflect it. This is the same class of bug as the SAR report: the "special case" (paused) branch is handled by silently substituting an incorrect-but-plausible value (the stale index) instead of properly rejecting the operation, so downstream arithmetic (debt scaling, share conversion) is computed against a value that no longer represents reality.

This pattern is identical across all six vaults (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`), each independently pausable via `set-pause-states`: [3](#0-2) 

### Impact Explanation
While `accrue` is paused for a vault, `system-borrow`/`system-repay`/`deposit`/`redeem` keep operating using the frozen `index`/`lindex`. Interest that should accrue to suppliers during the pause window is never captured into the index — it is not merely delayed, it is permanently skipped, because once accrual resumes, `next-index`/`next-liquidity-index` are computed from the current time delta against the *pre-pause* `last-update`, not reconstructed to account for the gap during which debt/deposit activity happened at the stale rate. Borrowers who take on or repay debt during the pause window lock in debt sized at the stale (lower) index, and depositors minting/redeeming shares do so at a stale (lower) liquidity index — permanently misallocating yield between the treasury/suppliers and the users interacting during the paused window. This is a permanent freezing/misallocation of unclaimed yield for suppliers, since the pass-through prevents the correct index from ever being reconstructed for that period.

### Likelihood Explanation
The pause flags are DAO-controlled (`set-pause-states`, gated by `check-dao-auth`), so triggering this requires the `accrue` bit to be set — typically during incident response or maintenance — while other operation flags (`deposit`, `borrow`, `redeem`, `repay`) remain false. Since each of the six flags is independently settable in the same struct, any legitimate partial pause of "just accrual" while leaving lending operations active reproduces this bug immediately for every affected user transaction in that window, with no attacker collusion needed.

### Recommendation
`accrue()` should not silently substitute stale values when paused. Either:
1. Have `accrue` return an error when the `accrue` flag is set, and have every dependent public function (`deposit`, `redeem`, `system-borrow`, `system-repay`) propagate that error (i.e., also revert) instead of calling `try!` on a value that is `ok` by construction; or
2. Gate `deposit`/`redeem`/`system-borrow`/`system-repay` directly on the `accrue` pause flag so they cannot proceed while accrual is frozen, ensuring index/lindex staleness never silently propagates into scaled-debt/share math.

### Proof of Concept
1. DAO calls `set-pause-states` on `v0-vault-stx` with `{accrue: true, deposit: false, borrow: false, redeem: false, repay: false, flashloan: false}`.
2. Time passes (block timestamps advance), during which the true economic `next-index`/`next-liquidity-index` would be higher than the stored `index`/`lindex`.
3. A user calls `system-borrow`; `accrue()` is invoked, sees `accrue: true`, and returns `(ok {index: idx, lindex: lidx})` — the stale values — without reverting.
4. `system-borrow` proceeds to scale the new debt using the stale `idx` (`mul-div-up amount INDEX-PRECISION idx`), understating the true scaled-debt-to-principal relationship that should apply once real interest is accounted for.
5. When the DAO later unpauses `accrue`, `next-index` is computed from `last-update` (unchanged during the pause) to `stacks-block-time` (now), but all borrow/repay activity that happened during the pause was already settled at the frozen index — that yield is never recovered for suppliers.
