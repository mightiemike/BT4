### Title
Unchecked u64 subtraction in startup index generation can underflow `accounts_data_len` - (File: accounts-db/src/accounts_db.rs)

### Summary
During `generate_index()` (called when a validator/ledger-tool restores AccountsDb state at startup), the code accumulates `accounts_data_len` across all storages and then subtracts the `accounts_data_len_from_duplicates` computed by `visit_duplicate_pubkeys_during_startup` using a plain, non-checked subtraction, unlike the adjacent capitalization computation which uses `checked_sub` with an explicit underflow panic guard.

### Finding Description
`generate_index_for_slot` accumulates non-zero-lamport account data lengths per slot into `accum.accounts_data_len` [1](#0-0) , and adds this into the total accumulator [2](#0-1) .

Later, after computing duplicate-pubkey contributions across bins (`accounts_data_len_from_duplicates`), the code performs:
```rust
total_accum.capitalization = total_accum
    .capitalization
    .checked_sub(capitalization_from_duplicates)
    .expect("capitalization cannot underflow");
total_accum.accounts_data_len -= accounts_data_len_from_duplicates;
``` [3](#0-2) 

Note the deliberate contrast: `capitalization` uses `checked_sub(...).expect(...)` to guarantee a panic on underflow, but the very next line performs a raw `-=` on `accounts_data_len` (a `u64` per the struct field definition seen at `accounts_data_len_from_duplicates: u64` in `DuplicatePubkeysVisitedInfo` [4](#0-3) ). If, due to any inconsistency between the per-slot summation of `accounts_data_len` and the duplicate-contribution computation in `visit_duplicate_pubkeys_during_startup` (e.g., a duplicate pubkey whose "kept"/newest version's data length differs from what was summed into `total_accum.accounts_data_len`, or an edge case where more data length is attributed to duplicates than was actually counted), `accounts_data_len_from_duplicates` exceeds `total_accum.accounts_data_len`, the subtraction wraps around to a value close to `u64::MAX` instead of panicking. This is the exact bug class described in the external report: an unchecked subtraction between two unsigned values that can silently produce a huge positive number instead of failing loudly.

### Impact Explanation
`accounts_data_len` is a capitalization-adjacent, cluster-consensus-relevant quantity tracked by `AccountsDb`/`Bank` used for enforcing the accounts-data-size budget and is persisted/reported across snapshot load and restart [5](#0-4) . If it silently wraps to a near-`u64::MAX` value on a debug-build-agnostic release build (release builds do not panic on integer overflow/underflow by default in Rust), the resulting bogus `accounts_data_len` would diverge between a freshly-generated index (via `generate_index`) at startup and the value recorded elsewhere (e.g. bank/snapshot-persisted value), potentially causing snapshot-vs-replay divergence or spurious data-length-limit enforcement failures for an honest node restoring from a legitimate but edge-case snapshot with duplicate accounts across slots.

### Likelihood Explanation
This code path only runs in the debug/no-overflow-checks assumption of release builds; in debug builds an underflow here would panic (`attempt to subtract with overflow`), same as the reference report's Solidity pre-0.8 bug requiring specific inputs. Triggering it requires a scenario where `visit_duplicate_pubkeys_during_startup`'s duplicate-length accounting and the earlier per-slot summation disagree — this is a narrow internal-accounting inconsistency, not attacker-controlled input in the classic sense, so likelihood is lower than a directly attacker-triggerable path, but the missing `checked_sub`/`expect` guard (present one line above for capitalization) is a clear code-quality/defense-in-depth gap that the analog highlights.

### Recommendation
Mirror the pattern already used for `capitalization` immediately above: replace `total_accum.accounts_data_len -= accounts_data_len_from_duplicates;` with a checked subtraction that panics loudly on underflow, e.g.:
```rust
total_accum.accounts_data_len = total_accum
    .accounts_data_len
    .checked_sub(accounts_data_len_from_duplicates)
    .expect("accounts_data_len cannot underflow");
```
This ensures any accounting bug in duplicate-length computation surfaces as an immediate, loud failure at startup rather than silently corrupting `accounts_data_len` with a wrapped near-`u64::MAX` value.

### Proof of Concept
Not independently reproduced with a concrete failing snapshot — the underflow could not be triggered through available tooling; the finding is based on static code review contrasting the unchecked subtraction at [6](#0-5)  with the checked-and-guarded sibling operation on `capitalization` immediately preceding it at [7](#0-6) , and the definition of the u64-typed `accounts_data_len_from_duplicates` field at [8](#0-7) .
