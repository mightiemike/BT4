This confirms the mechanism: `verifyFundMigrationSigningRequest` independently re-queries the old-TSS-address balance via `builder.GetFundMigrationSigningRequest` (which calls `tb.rpcClient.GetBalance(ctx, fromAddr)` in `universalClient/chains/evm/tx_builder.go`) and rejects the signing round outright if its recomputed hash/amount doesn't match the coordinator's, with no tolerance for balance drift between independent RPC queries.

### Title
Fund-migration signing quorum can be griefed by dust transfers to the old TSS address, causing balance-drift hash mismatches and DoS of TSS re-key fund sweeps - (File: universalClient/tss/sessionmanager/sessionmanager.go, universalClient/chains/evm/tx_builder.go)

### Summary
The Push Chain TSS fund-migration flow computes the amount to sweep from the old TSS address as `balance - gasCost - l1GasFee`, where `balance` is fetched live via RPC (`GetBalance`) independently by the coordinator and by every Universal Validator's session manager during verification. Because each participant queries the external chain's balance at a different point in time, and the flow provides no block-height pinning or tolerance window, any unprivileged actor who sends a trivial native-token transfer to the (publicly derivable) old TSS address between these independent queries can cause the computed sweep amount — and therefore the signing hash — to diverge across participants, causing the signature verification to fail and the TSS quorum to reject the round.

### Finding Description
`computeFundMigrationTransfer` in [1](#0-0)  computes `maxTransfer = balance - gasCost - l1GasFee` from a `balance` argument. When `data.Balance` is not explicitly supplied, `GetFundMigrationSigningRequest` queries this balance live via RPC: [2](#0-1) .

The TSS coordinator initiates the migration by calling `buildFundMigrationTransaction` with `claimedAmount == nil`, which forces a fresh RPC balance query at signing-setup time: [3](#0-2)  and [4](#0-3) .

Each Universal Validator's `SessionManager.verifyFundMigrationSigningRequest` independently re-derives the signing request — again without supplying `Balance`, so it performs its own live RPC query at a possibly different moment — and then strictly compares the resulting hash and `TSSFundMigrationAmount` against the coordinator's values: [5](#0-4) . Any mismatch causes an outright rejection with no retry/tolerance logic: `"fund migration signing hash mismatch: our computed hash does not match coordinator's hash"`.

The code's own comments acknowledge the fund-migration balance is assumed static ("Fund migration only triggers when outbound is disabled and no pending outbounds remain, so the balance at signing time will equal the balance at broadcast time" — [6](#0-5) ) and a partial mitigation exists for the *ACK verify* path (`claimedAmount` reconstructs balance from the already-agreed amount instead of re-querying — see the comment at [7](#0-6) ), but this mitigation is not used for the initial coordinator-to-participant signing-setup handshake, nor for `verifyFundMigrationSigningRequest`'s independent recomputation, both of which still perform live, unsynchronized balance queries.

This is directly analogous to the reported LeXscrow issue: a balance-based invariant check (`totalWithFee` satisfied by contract balance) can be corrupted by an unprivileged party sending a small, unrelated transfer to the address being measured, causing an otherwise-valid flow to fail/revert.

### Impact Explanation
The old TSS address is a value publicly observable on-chain (it is embedded in `FundMigrationInitiatedEventData` gossiped among participants and derivable from historical TSS public keys). Any external, unprivileged actor on the connected external chain (e.g. Ethereum, BSC, etc.) can send a dust-value native-token transfer to this address at any time. If this transfer lands between the coordinator's balance query and any quorum-required participant's independent verification query, that participant's locally recomputed signing hash and `TSSFundMigrationAmount` will diverge from the coordinator's, causing that participant to reject the round. If enough participants are affected simultaneously (attacker can repeat the dust-send at will, cheaply, across multiple attempted retries), the TSS quorum required to complete the fund-migration signing round can be persistently denied, stalling migration of TSS-held funds off the old key. This is a protocol-level, unprivileged, non-network DoS reachable purely by an external chain transaction — matching the "TSS coordination" impact category (denial-of-service of TSS fund migration, not requiring any privileged/malicious validator/relayer assumption).

### Likelihood Explanation
Likelihood is moderate: the attacker needs to time a cheap external-chain dust transaction against a live fund-migration signing round (which only occurs during KEYGEN/REFRESH/QUORUM_CHANGE TSS processes), but this event and the associated old-TSS address are observable via on-chain events, and the attack can be retried cheaply on every migration attempt until it succeeds against at least one quorum-relevant validator, especially since RPC latency differences between independently-operated Universal Validator nodes are common.

### Recommendation
Do not have each participant independently re-query live balance for the fund-migration signing hash. Instead, pin the balance used for the computation to an explicit value/block height chosen once by the coordinator (or another well-defined checkpoint) and propagate it as part of the signed setup message, so every participant recomputes the identical hash from the same agreed-upon balance rather than from independent live RPC snapshots — mirroring the `claimedAmount` reconstruction approach already used in the ACK-verify path, but applied to the initial signing-setup verification as well.

### Proof of Concept
1. Trigger (or wait for) a TSS `KEYGEN`/`REFRESH` process, which produces a `FundMigrationInitiatedEventData` naming the old TSS EVM address (`oldTSSAddr`).
2. As an unprivileged external actor, monitor for the coordinator's signing-setup broadcast (or simply race repeatedly) and send a minimal native-token transfer (e.g., 1 wei) directly to `oldTSSAddr` on the source chain.
3. Some Universal Validator's `verifyFundMigrationSigningRequest` call to `builder.GetFundMigrationSigningRequest` (in `universalClient/chains/evm/tx_builder.go`) queries `GetBalance(oldTSSAddr)` after the dust lands, producing a `maxTransfer` different from the coordinator's originally signed value.
4. `bytes.Equal(signingReq.SigningHash, req.SigningHash)` fails at [8](#0-7) , causing that validator to reject the round; repeating against enough validators denies quorum for the migration.

func computeFundMigrationTransfer(balance, gasPrice *big.Int, gasLimit uint64, l1GasFee *big.Int) (*big.Int, error) {
	gasCost := new(big.Int).Mul(gasPrice, new(big.Int).SetUint64(gasLimit))
	totalFee := new(big.Int).Set(gasCost)
	if l1GasFee != nil && l1GasFee.Sign() > 0 {
		totalFee.Add(totalFee, l1GasFee)
	}
	maxTransfer := new(big.Int).Sub(balance, totalFee)
	if maxTransfer.Sign() <= 0 {
		return nil, fmt.Errorf("insufficient balance for gas: balance=%s gasCost=%s l1GasFee=%s",
			balance.String(), gasCost.String(), l1GasFeeString(l1GasFee))
	}
	return maxTransfer, nil
}
