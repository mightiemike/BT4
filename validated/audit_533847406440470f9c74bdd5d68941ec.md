### Title
Missing declared-class check for Cairo0 (V0) classes in `GlobalContractCache` allows stale/reverted class data to be served, causing honest-node divergence - (File: `crates/blockifier/src/state/state_reader_and_contract_manager.rs`)

### Summary
This is an analog of the "cached value diverges from the authoritative source" bug class described in the external report (`vcon` cached in `CoreRef` but not kept in sync with `Core`). In the sequencer, `StateReaderAndContractManager::get_compiled_from_class_manager` serves compiled classes from a node-local, cross-block `GlobalContractCache` (`ContractClassManager`). The code explicitly re-validates `is_declared` against authoritative state before trusting a cache hit — but only for non-`V0` (Cairo1) classes, leaving Cairo0 (`V0`) classes unvalidated.

### Finding Description
`get_compiled_from_class_manager` looks up a class by `class_hash` in the shared `contract_class_manager` cache first: [1](#0-0) 

The comment explains why the check is needed: cache existence "does not guarantee [declared status], since it might contain a declared class from a reverted block", i.e. the cache is populated during speculative/aborted executions (mempool validation, simulation, rejected proposals) that never actually commit to canonical state, and it is never invalidated on revert. To guard against this, the code calls `self.state_reader.is_declared(class_hash)` — but this call is gated inside the `match` arm that explicitly excludes `RunnableCompiledClass::V0(_)`:

```rust
match &runnable_class {
    RunnableCompiledClass::V0(_) => {}
    _ => {
        if !self.state_reader.is_declared(class_hash)? {
            return Err(StateError::UndeclaredClassHash(class_hash));
        }
    }
}
```

For Cairo0 classes, a cache hit is trusted unconditionally, with no re-check that the class is actually declared in the current (canonical) state.

### Impact Explanation
The `ContractClassManager`/`GlobalContractCache` is a long-lived, per-process cache shared across many block executions (production, re-validation, simulation, mempool pre-checks). Because it is populated as a side effect of `get_compiled_classes` during *any* execution path — including ones that are later discarded (reverted blocks, rejected proposals, speculative validation) — a Cairo0 class hash can become cached on one node without ever being canonically declared. A subsequent transaction referencing that same (uncommitted) class hash will succeed on that node (served from cache) while an honest node that never cached it will correctly reject it with `UndeclaredClassHash`. This produces node-to-node execution divergence for the identical block/transaction, undermining consensus on execution results — the same class of "component desync from an unsynced cache" that the original report flagged, but here manifesting as cross-node non-determinism instead of a within-contract state mismatch.

### Likelihood Explanation
Any unprivileged sender can trigger the divergence path by attempting to execute/simulate against a Cairo0 class hash that some (but not all) sequencer nodes have already warmed via a prior discarded execution (e.g., a transaction included in a locally-executed-but-later-reverted/rejected block, or a validated-but-not-included proposal, or a simulate/estimate-fee RPC call). No governance or special privilege is required — only knowledge of a not-yet-canonically-declared Cairo0 class hash and a transaction that calls into it.

### Recommendation
Apply the same `is_declared` re-validation to `V0` classes as is already done for non-`V0` classes in `get_compiled_from_class_manager`, so cache hits for Cairo0 classes are also verified against canonical state before being trusted: [2](#0-1) 

### Proof of Concept
1. Node A executes/simulates (e.g., via RPC `estimate_fee`/`call`, or speculative batcher execution of a proposal) a transaction that declares and calls a Cairo0 class `C`, populating `ContractClassManager`'s `GlobalContractCache` with `C`, but the containing block/proposal is later discarded (reverted, rejected in consensus, or the RPC call was just a simulation and never became canonical).
2. Node B (or Node A itself afterward, in the canonical chain) never sees class `C` declared in state.
3. A user submits a transaction invoking class `C`'s entry point.
   - On Node A: `get_compiled_from_class_manager` hits the `GlobalContractCache`, matches `RunnableCompiledClass::V0(_) => {}`, skips the `is_declared` check, and executes the call successfully.
   - On Node B: no cache entry exists, `state_reader.get_compiled_classes` fails to find the class in canonical state, and the call is rejected with an undeclared-class error.
4. Nodes A and B produce different execution results for the same transaction/block, an honest-node divergence.

impl<S: FetchCompiledClasses> StateReaderAndContractManager<S> {
    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }
