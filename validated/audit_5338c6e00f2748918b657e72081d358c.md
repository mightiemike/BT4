### Title
Unbounded `PendingInbounds.Walk` in `AfterBallotTerminal` allows attacker-inflated gas cost on every inbound vote — ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
`afterInboundBallotTerminal` (invoked synchronously by `x/uvalidator`'s ballot machine whenever an inbound ballot reaches a terminal state) performs a **full table scan** of the `PendingInbounds` collection to locate the entry owning the finalized `ballotID`, instead of an O(1) lookup by key. Because `MsgVoteInbound` is a gasless message (`app/txpolicy/gasless.go`) and every honest UV's vote transaction triggers this hook on finalization, the per-vote cost of this scan scales linearly with the total number of concurrently pending inbound entries — a number an unprivileged attacker can inflate by generating many low-cost/low-value gateway events on cheap external chains.

### Finding Description
`afterInboundBallotTerminal` walks the entire `PendingInbounds` map on every terminal ballot transition to find the matching variant, because ballot IDs are one-way digests and not directly reversible to their owning `utx_key`: [1](#0-0) 

This is analogous to the reported `chef_set_payouts` / `admin_process_payouts` pattern: an unbounded loop over an attacker-influenceable set, executed inside a hot, consensus-critical code path (here, every single `MsgVoteInbound` that finalizes a ballot), rather than a bounded/paginated operation.

`PendingInbounds` entries are created on the *first* vote for any inbound observation (`RecordInboundVote` inside `VoteInbound`) and are only removed once *all* ballot variants for that entry reach a terminal state: [2](#0-1) 

`MsgVoteInbound` is registered as a gasless message type, meaning the transaction bypasses normal Cosmos SDK gas metering: [3](#0-2) 

Since inbound observations are keyed by `sha256(source_chain:tx_hash:log_index)` (real, attacker-triggerable external-chain events, not admin-controlled), an attacker can drive up the number of concurrently-outstanding `PendingInbounds` entries simply by submitting many distinct low-value gateway transactions on a cheap external chain (e.g. Solana) faster than validators can finalize votes. Each additional outstanding entry adds work to *every subsequent* `AfterBallotTerminal` call, because the walk must scan the full collection (worst case) to find the matching `ballotID`.

### Impact Explanation
Because `MsgVoteInbound` is exempt from ordinary Cosmos gas metering (gasless), this isn't a classic "the tx reverts with out-of-gas" issue as in the original CosmWasm report — instead the risk manifests as a state-machine-level performance/DoS issue: as `PendingInbounds` grows, the per-finalization cost of `afterInboundBallotTerminal` grows linearly, slowing down (and in the extreme, materially degrading) block processing for every UV vote that finalizes a ballot. This is a denial-of-service condition reachable purely through ordinary, unprivileged use of the bridge (submitting many inbound events) with no privileged actor or malicious validator required, fitting the "denial of service ... reachable without privileged control" allowed-impact category. It does not directly cause loss/misdirection of funds by itself, so its severity is bounded to availability/performance degradation rather than fund safety.

### Likelihood Explanation
Exploitability is moderate-to-low in practice: it requires the attacker to sustain a volume of pending, not-yet-finalized inbound events. Since validators generally finalize votes quickly once 2/3 quorum is reached, the number of concurrently outstanding entries in `PendingInbounds` is typically bounded by processing latency rather than growing unbounded. The comment in the code itself states the assumption explicitly ("the pending set is small and transient"), acknowledging the design relies on this being small — an assumption that is not enforced by any hard cap and could be violated under sustained spam across many cheap-fee source chains.

### Recommendation
Replace the linear `Walk` with a direct index: maintain a secondary index/map from `ballotID -> utx_key` (populated when the variant/ballot is created in `RecordInboundVote`) so `afterInboundBallotTerminal` can do an O(1) lookup instead of scanning all of `PendingInbounds`. Alternatively, enforce a hard cap on the number of concurrently outstanding `PendingInbounds` entries (mirroring the report's suggested remediation of "introduce a hard limit"), rejecting or rate-limiting new inbound votes once the cap is reached.

### Proof of Concept
1. An attacker submits many distinct, real (but low-value) gateway transactions on a low-fee external chain (each with a unique `tx_hash`/`log_index`), faster than UVs can reach 2/3 quorum on each.
2. Each event causes a new entry to be created in `PendingInbounds` via `RecordInboundVote` (see `x/uexecutor/keeper/msg_vote_inbound.go` lines 57-66).
3. As UVs continue to submit `MsgVoteInbound` for various inbounds, each ballot finalization triggers `afterInboundBallotTerminal`, which performs a full `PendingInbounds.Walk` (`x/uexecutor/keeper/ballot_hooks.go` lines 86-94) whose cost is proportional to the current size of `PendingInbounds`.
4. As the attacker keeps the pending set inflated, every vote transaction (which is gasless and thus not gas-limited per the SDK's normal fee-based throttling) incurs increasing computational cost, degrading block-processing throughput for the entire crosschain voting pipeline.

Note: I was unable to fully confirm the growth bound of `PendingInbounds` in a live cluster (e.g., actual finalization latency under load, or whether any other guard elsewhere caps concurrent pending inbounds) from static code alone — a Devin session with a running testnet/integration environment would be needed to empirically measure the walk cost under sustained inbound-event spam and confirm real-world severity.

	// the owning audit-trail entry by scanning PendingInbounds for the

	// transient, and this hook only fires on terminal transitions.

		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
