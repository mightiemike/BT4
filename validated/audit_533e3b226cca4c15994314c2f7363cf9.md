### Title
Unbounded state growth in the on-chain order book (`MarketOrderStore`) enables a low-cost storage-exhaustion DoS - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`, `actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java`)

### Summary
The reported Solana bug is a class of "allocate space per order, never deallocate" DoS: temporary IDs consume fixed account space and are only freed by specific cleanup paths, so an attacker who avoids those paths can exhaust the account. In java-tron's on-chain exchange (`MarketSellAssetActuator` / `MarketCancelOrderActuator`), every order — including fully filled and cancelled orders — is written to `MarketOrderStore` and is **never removed**, even by the actuator that is supposed to be the "cleanup" path (`MarketCancelOrderActuator`). Only the transient index structures (`MarketAccountStore`'s active-order list and `MarketPairPriceToOrderStore`) are cleaned up; the order record itself persists in every full node's state database forever. An attacker can cheaply and repeatedly create+cancel/fill minimal orders to grow this store without bound, at a cost limited only to the small, fixed `MarketSellFee`/`MarketCancelFee`.

### Finding Description
`MarketSellAssetActuator.createAndSaveOrder()` writes a new `MarketOrderCapsule` into `orderStore` (`MarketOrderStore`) for every sell order: [1](#0-0) 

When an order is matched or cancelled, `MarketUtils.updateOrderState()` only removes the order id from the per-account active list in `MarketAccountStore`; it does not touch `MarketOrderStore`: [2](#0-1) 

Even the dedicated cleanup actuator, `MarketCancelOrderActuator.execute()`, removes the order only from `pairPriceToOrderStore` (the order book) and, if empty, from `pairToPriceStore`, then re-`put`s the (now `CANCELED`) `MarketOrderCapsule` back into `orderStore` — it never calls `orderStore.delete(...)`: [3](#0-2) 

A grep across the production actuator code confirms `orderStore.delete(...)` is never invoked anywhere outside of unit tests — every order that has ever been created (`MarketSellAssetContract`) remains permanently stored in `MarketOrderStore`, regardless of whether it was fully matched or explicitly cancelled.

This exactly mirrors the reported bug class: a per-action allocation (`client_infos_acc`/`client_infos2_acc` entries ≈ `MarketOrderStore` entries) that is supposed to be reclaimed by a designated deallocation path (`finalize_spot`/`move_spot_avail_funds` ≈ `MarketCancelOrderActuator`) but in practice is never freed, so state monotonically grows with every order regardless of the caller's later behavior.

The only bound on simultaneous "open" orders is `MAX_ACTIVE_ORDER_NUM = 100` per account, enforced in `validate()`: [4](#0-3) 
This bound only caps *active* orders per single address; it does nothing to prevent unlimited cumulative growth of `orderStore`, since (a) orders that are fully filled or cancelled free up the "active" slot but leave a permanent record, and (b) an attacker can use unlimited distinct addresses.

### Impact Explanation
Unlike the Solana report where the account is a fixed 10MB allocation with a hard, predictable exhaustion point that halts trading outright, java-tron's `MarketOrderStore` is backed by RocksDB/LevelDB, so there is no immediate hard cap — but this means the growth is unbounded rather than merely large. Every full node that syncs the chain must permanently store every order record ever created via `MarketSellAssetContract`, forever, with no pruning path in the protocol. This is a state-bloat DoS: sustained cheap transactions can grow disk usage, snapshot size, and sync time for every current and future full node without limit, degrading the network's operability over time (analogous DoS impact via protocol implementation/state accounting, not an RPC-only issue).

### Likelihood Explanation
Reachable directly by any account via a normal broadcast transaction (`MarketSellAssetContract`, optionally followed by `MarketCancelOrderContract`) once market transactions are enabled (`dynamicStore.supportAllowMarketTransaction()`). The attacker only pays the fixed `MarketSellFee`/`MarketCancelFee` and a minimal quantity per order (bounded below by `getMarketQuantityLimit`, not by any meaningfully large minimum), making the attack inexpensive per unit of state growth and requiring no privileged role, no key compromise, and no malicious peer/node behavior — consistent with the report's own caveat that funds are the limiting factor, not permissions.

### Recommendation
Add an explicit deletion of the underlying `MarketOrderCapsule` from `MarketOrderStore` once an order reaches a terminal state (`INACTIVE`/`CANCELED`) and is no longer referenced by any linked-list structure (or after a bounded retention/archival window), instead of persisting it indefinitely. If historical order data must be retained for auditing, move it out of the live chain state (e.g., into node-local/off-chain indexing) rather than into a store that every consensus-participating node must retain forever.

### Proof of Concept
1. Enable market transactions (`supportAllowMarketTransaction`).
2. From account `A`, repeatedly broadcast minimal `MarketSellAssetContract` transactions (e.g., quantity at the protocol minimum, paying `MarketSellFee` each time) that do not match any existing counter-order, causing `saveRemainOrder` to store the order in the book.
3. Immediately cancel each order with `MarketCancelOrderContract` (paying `MarketCancelFee`), which frees the "active order" slot in `MarketAccountStore` (allowing the 100-order-per-account cap to be bypassed) and removes the order from `pairPriceToOrderStore`, but leaves the `MarketOrderCapsule` permanently in `MarketOrderStore`.
4. Repeat steps 2–3 indefinitely (optionally rotating across many funded addresses to also bypass the 100-active-order cap trivially, though that cap is irrelevant to store growth since cancelled/filled orders already free it).
5. Observe that `MarketOrderStore`'s size grows monotonically with each iteration and is never reduced, regardless of how many orders are cancelled or filled — confirmed by the absence of any `orderStore.delete()` call in `MarketSellAssetActuator` or `MarketCancelOrderActuator`.

  private MarketOrderCapsule createAndSaveOrder(AccountCapsule accountCapsule,
      MarketSellAssetContract contract) {
    MarketAccountOrderCapsule marketAccountOrderCapsule = marketAccountStore
        .getUnchecked(contract.getOwnerAddress().toByteArray());
    if (marketAccountOrderCapsule == null) {
      marketAccountOrderCapsule = new MarketAccountOrderCapsule(contract.getOwnerAddress());
    }

    // note: here use total_count
    byte[] orderId = MarketUtils
        .calculateOrderId(contract.getOwnerAddress(), sellTokenID, buyTokenID,
            marketAccountOrderCapsule.getTotalCount());
    MarketOrderCapsule orderCapsule = new MarketOrderCapsule(orderId, contract);

    long now = dynamicStore.getLatestBlockHeaderTimestamp();
    orderCapsule.setCreateTime(now);

    marketAccountOrderCapsule.addOrders(orderCapsule.getID());
    marketAccountOrderCapsule.setCount(marketAccountOrderCapsule.getCount() + 1);
    marketAccountOrderCapsule.setTotalCount(marketAccountOrderCapsule.getTotalCount() + 1);
    marketAccountStore.put(accountCapsule.createDbKey(), marketAccountOrderCapsule);
    orderStore.put(orderId, orderCapsule);

    return orderCapsule;
  }

  public static void updateOrderState(MarketOrderCapsule orderCapsule,
      State state, MarketAccountStore marketAccountStore) throws ItemNotFoundException {
    orderCapsule.setState(state);

    // remove from account order list
    if (state == State.INACTIVE || state == State.CANCELED) {
      MarketAccountOrderCapsule accountOrderCapsule = marketAccountStore
          .get(orderCapsule.getOwnerAddress().toByteArray());
      accountOrderCapsule.removeOrder(orderCapsule.getID());
      marketAccountStore.put(accountOrderCapsule.createDbKey(), accountOrderCapsule);
    }
  }
