### Title
Webhook `X-Shopify-Shop-Domain` header is not covered by the HMAC signature, allowing cross-tenant session/admin-client binding - ([File: packages/apps/shopify-api/lib/utils/hmac-validator.ts])

### Summary
Shopify webhook authenticity is verified with `validateHmacFromRequestFactory`, which computes the HMAC over `rawBody` only. [1](#0-0)  The shop identity (`X-Shopify-Shop-Domain` / events equivalent) is read straight from request headers and is never included in the signed data, yet that value (`webhookCheck.domain`) is later used as the trust anchor to select which shop's offline session/access token to hand to the handler.

### Finding Description
`validateFactory` first validates the HMAC over `rawBody` and, only if that succeeds, extracts the `domain` header via `checkWebhookHeaders`/`checkWebhooksHeaders` without any cryptographic binding between that header and the signed body. [2](#0-1) [3](#0-2) 

Downstream, in the framework adapters (Remix/React Router), the "authenticated" webhook flow uses that unauthenticated `check.domain` value directly to look up and refresh the offline session for that shop, then attaches the corresponding `admin` API client (with that shop's real access token) to the webhook context that is handed to the app's handler code: [4](#0-3) 

This is structurally the same root cause as the reported H-04 bug: an identity value (`id` in the smart-contract case, `domain`/shop in this case) that is *not* covered by the signature is nonetheless used later as the basis for a privilege/authorization decision (which tenant's session and API credentials to use).

### Impact Explanation
Any entity capable of triggering (or replaying) a genuinely HMAC-valid webhook body — e.g., a merchant who has installed the app on their own store and can capture the webhooks Shopify sends them, since HMAC is computed with the app's single shared secret across all shops — can resend that exact `rawBody`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a victim shop. Because the header is not part of the signed data, the HMAC check still passes. The webhook context then reports `shop: <victim-domain>` and provides an `admin` client authenticated with the victim's real offline access token, while `payload`/`rawBody` (attacker-controlled/observed data) is treated as this victim's event. [5](#0-4)  If the app's webhook handler acts on payload data (ids, amounts) using the provided `admin` client (e.g. issuing a refund, creating a discount, modifying an order/customer) without separately re-validating that the payload's own shop-scoped identifiers belong to the shop in `webhookCheck.domain`, an attacker can cause actions to be executed against a different, uninvolved tenant's store using that tenant's access token — a cross-tenant authorization bypass.

### Likelihood Explanation
Exploitability depends entirely on how a specific app's webhook handler uses the `shop`/`payload` combination; the shopify-app-js framework itself does not perform any additional binding between the unauthenticated `domain` header and the signed body. This is a design gap in the SDK/framework rather than a fully self-contained exploit, since the attacker needs a genuine HMAC-valid body/signature pair (obtainable by installing the app on their own store) and a downstream handler that trusts `shop` without cross-checking payload-embedded identifiers. Given many webhook handler implementations index directly by the reported `shop`/`domain` (as the framework itself demonstrates by doing so for session lookup), likelihood of impactful misuse in typical integrations is meaningful, but is not directly weaponizable against the framework in isolation without an app-specific handler that trusts `shop` blindly.

### Recommendation
Bind the shop identity to the HMAC computation (e.g., include the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, or derive/verify the shop from the payload itself) so that spoofing the domain header alone cannot produce a still-valid signature. At minimum, document/require that webhook handlers must not trust the reported `domain`/`shop` for authorization purposes unless it is independently corroborated against shop-scoped identifiers inside the verified payload, mirroring the recommended fix for the smart-contract case of removing trust in an externally supplied, unsigned identity value.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store (`attacker.myshopify.com`) and receives a legitimate webhook, e.g. `orders/create`, with a real `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the shared `apiSecretKey`.
2. Attacker resends the exact same `rawBody` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `validateHmacFromRequestFactory` recomputes the HMAC solely over `rawBody`, which still matches, so `webhookCheck.valid === true` and `webhookCheck.domain === 'victim.myshopify.com'`. [6](#0-5) 
4. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` for `victim.myshopify.com`, obtaining the victim's real offline access token, and constructs an `admin` client scoped to the victim, then invokes the app's handler with `shop: 'victim.myshopify.com'` and the attacker-controlled `payload`. [5](#0-4) 
5. If the handler performs any write/side-effecting action against the Admin API using `admin` based on data in `payload` (e.g., referencing attacker-controlled order/customer identifiers under the mistaken belief they belong to `victim`), the attacker has achieved cross-tenant execution using the victim's credentials.

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}

  const headerNames = WEBHOOK_HEADER_NAMES[WebhookType.Webhooks];

  const hmac = getRequiredHeader(headers, headerNames.hmac, missingHeaders);
  const topic = getRequiredHeader(headers, headerNames.topic, missingHeaders);

    headerNames.webhookId,
    missingHeaders,
  );

      valid: false,
      reason: WebhookValidationErrorReason.MissingHeaders,
      missingHeaders,
