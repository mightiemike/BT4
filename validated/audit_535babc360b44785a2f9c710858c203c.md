### Title
Stale liquidity/borrow index served from `index-cache` after `vault-socialize-debt` mutates vault state in the same block - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` caches vault interest-accrual indexes per `(stacks-block-time, aid)` pair to save cross-contract calls within a block, but the cache is populated exclusively through `accrue-and-cache`/`vault-accrue`. Debt write-off via `vault-socialize-debt` mutates the same vault's true index/lindex directly on the vault contract without touching or invalidating `index-cache`, so any later call in the same block reads the pre-write-off (stale, inflated) index instead of the corrected one.

### Finding Description
`accrue-and-cache` is a memoized read of vault indexes keyed by the current block timestamp: [1](#0-0) 

The cache is populated only via `vault-accrue`: [2](#0-1) 

Bad-debt write-off, however, is routed through a separate private wrapper, `vault-socialize-debt`, which calls the vault's `socialize-debt` entry point directly and never touches the `index-cache` map: [3](#0-2) 

The presence of `ERR-BAD-DEBT-SOCIALIZATION-FAILED` confirms socialize-debt is a real, reachable liquidation-path operation that adjusts the vault's index state (per the protocol's own documentation, the vault model follows the AAVE reserve/index pattern where bad-debt socialization reduces the liquidity index to spread the loss across suppliers): [4](#0-3) [5](#0-4) 

Sequence:
1. Transaction A, within block at timestamp `T`, calls a market entry point that invokes `accrue-and-cache(aid)` for a vault, caching `{index, lindex}` under key `{timestamp: T, aid: aid}` (cache MISS branch, line 254-256).
2. Later in transaction A (e.g. as part of a liquidation that leaves uncovered bad debt), the market calls `vault-socialize-debt(aid, amount)` (line 216-223), which mutates the vault's true `lindex` downward but does not write to `index-cache`.
3. Transaction B, submitted later in the *same block* (same `stacks-block-time` `T`), calls any market function that invokes `accrue-and-cache(aid)` for the same `aid` — e.g. a deposit, borrow, redeem, or price resolution that needs this vault's index.
4. `accrue-and-cache` finds the existing entry for `{T, aid}` and returns it directly via the cache-HIT branch (line 251) — the stale, pre-write-off index/lindex — instead of calling `vault-accrue` again to fetch the vault's now-corrected state.
5. Any pricing, borrowing-power, or redemption-value computation performed in transaction B for that `aid` (including zToken price resolution, which the oracle/market docs state relies on this exact cache) uses an inflated index that no longer reflects the just-socialized loss.

### Impact Explanation
Because the cache silently outlives the very state-mutating call (`socialize-debt`) that should invalidate it, users interacting with the same vault later in the same block can borrow against, or redeem, ztoken collateral priced using a liquidity index that has already been proven wrong (too high) by the socialization event. This causes an inaccurate valuation to be used for borrowing-power/health checks and redemption accounting for the remainder of the block, which can result in over-borrowing against overvalued collateral or over-redemption relative to the vault's actual post-write-off backing — a temporary freezing/misallocation of funds relative to the corrected vault state. This lands in the in-scope "temporary freezing of funds" impact category.

### Likelihood Explanation
Likelihood is constrained to windows where a socialization event and a subsequent user-triggered accrual for the same asset occur in the same block; Stacks blocks can contain multiple transactions sharing one `stacks-block-time`, and liquidations leading to bad-debt socialization are a normal, expected part of protocol operation, so the precondition is realistically reachable without any privileged action, oracle manipulation, or multi-user collusion — it can happen from ordinary sequential usage of the market within one block.

### Recommendation
Invalidate or refresh the `index-cache` entry for the affected `aid` whenever `vault-socialize-debt` (or any other state-mutating vault call besides `vault-accrue`) is executed — e.g., by calling `accrue-and-cache`/re-fetching and overwriting the cache entry immediately after `socialize-debt` succeeds, or by removing the stale entry from `index-cache` so the next read forces a fresh `vault-accrue` call.

### Proof of Concept
Conceptual PoC (Clarity, illustrative — exact vault/market entry points for triggering socialize-debt within a liquidation would need to be confirmed against the vault contracts, which were not fully available in this scan):
```
;; Block T:
;; Tx A (any user/liquidator):
;;   1. calls market function X that internally calls (accrue-and-cache aid)
;;      -> cache MISS, stores {index: I0, lindex: L0} at {timestamp: T, aid: aid}
;;   2. same tx later calls (vault-socialize-debt aid bad-debt-amount)
;;      -> vault's true lindex becomes L1 < L0 (loss socialized to suppliers)
;;   index-cache still holds {index: I0, lindex: L0} for {T, aid}

;; Tx B (any other later tx in same block T):
;;   calls market function Y that calls (accrue-and-cache aid)
;;   -> cache HIT: returns stale {index: I0, lindex: L0}
;;   -> Tx B's price/health/borrow-power computations for that vault's ztoken
;;      use L0 instead of the corrected L1, understating the loss.
```
Confirming the exact magnitude of `lindex` change on `socialize-debt` requires the vault contract source (e.g. `v0-vault-stx.clar`), which was not retrievable in this scan; the market-side caching flaw (no invalidation path from `vault-socialize-debt` back into `index-cache`) is directly verifiable from `v0-4-market.clar` as cited above.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
