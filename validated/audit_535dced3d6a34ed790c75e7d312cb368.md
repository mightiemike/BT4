### Title
Missing zero-address check on ETH transfer destination allows irreversible loss of funds when combined with the `force` (`AllowHigherAmounts`) flag - (File: `core/web/evm_transfer_controller.go`)

### Summary
The Chainlink node exposes an ETH withdrawal endpoint (`POST /v2/transfers/evm`, backed by the `chainlink evm create` CLI command) that transfers funds from a node-controlled address to any `DestinationAddress` supplied by the caller. Just like the Gearbox `CreditManager` bug, the destination address is never validated to be non-zero, and there is an explicit `force`/`AllowHigherAmounts` flag that bypasses the only safety check (balance validation) present in the code path.

### Finding Description
`EVMTransfersController.Create` binds the request body to `models.SendEtherRequest` and dispatches to either `CreateEVMLegacy` or `CreateWithRelayer` [1](#0-0) .

In `CreateEVMLegacy`, only `tr.FromAddress` is checked against the zero address; `tr.DestinationAddress` is never validated: [2](#0-1) 

The `AllowHigherAmounts` flag (exposed to CLI users as `--force`) explicitly skips the only guard rail present, `ValidateEthBalanceForTransfer`: [3](#0-2) 

`CreateWithRelayer` passes `tr.DestinationAddress.String()` straight into `relayer.Transact` with the same lack of a zero-address check, and also honors `!tr.AllowHigherAmounts` to gate balance checks: [4](#0-3) .

The `SendEtherRequest` model itself has no validation preventing `DestinationAddress` from being the zero address: [5](#0-4) .

On the CLI side, `chainlink evm create <amount> <fromAddress> <toAddress> --force` builds exactly this request, setting `AllowHigherAmounts: c.IsSet("force")` with no destination-address sanity check: [6](#0-5) .

This mirrors the Gearbox pattern precisely: a fund-moving function takes a `to` address plus a `force`-style flag that disables the safety check, and neither code path rejects `to == address(0)`.

### Impact Explanation
If a node operator (or an automation script/API caller with access to the node's admin API) mistakenly supplies a zero address as `DestinationAddress` — e.g., due to a scripting bug, unset environment variable defaulting to the zero value, or copy-paste error — combined with `--force`/`allowHigherAmounts: true` to skip the balance sanity check, the node will irreversibly send ETH/native tokens to `address(0)`, permanently burning the funds with no recovery path. This directly causes loss of node operator assets, analogous to the Gearbox liquidator loss-of-funds report.

### Likelihood Explanation
This requires access to the node's authenticated admin API/CLI (which is a real precondition), but there is no additional gate: the endpoint fully trusts caller-supplied `DestinationAddress` and `force` without any zero-address validation. Given this is an administrative fund-transfer endpoint intended for routine, sometimes automated/scripted, operational use, a single scripting or input mistake is sufficient to trigger total loss of the transferred amount — matching the "loss of assets by mistake" bug class from the report exactly.

### Recommendation
Add an explicit check that `tr.DestinationAddress != (common.Address{})` (zero address) in `EVMTransfersController.Create`/`CreateEVMLegacy`/`CreateWithRelayer` before any transfer is executed, returning an HTTP 422/400 error if violated, regardless of the `AllowHigherAmounts`/`force` flag. Consider making the zero-address check unconditional and independent of `force`, mirroring the Gearbox recommendation of "adding a check that `to != address(0)`."

### Proof of Concept
1. Authenticate to the node's admin API (or use the CLI: `chainlink evm create <amount> <fromAddress> 0x0000000000000000000000000000000000000000 --force`).
2. This constructs a `models.SendEtherRequest{DestinationAddress: 0x0, AllowHigherAmounts: true, ...}` and POSTs to `/v2/transfers/evm`.
3. `EVMTransfersController.Create` routes to `CreateEVMLegacy`, which only checks `tr.FromAddress == utils.ZeroAddress` (line 97) — the destination is never checked.
4. Because `AllowHigherAmounts` is `true`, `ValidateEthBalanceForTransfer` is skipped entirely (lines 102-108).
5. `chain.TxManager().SendNativeToken` executes the transfer to `address(0)`, permanently destroying the transferred funds.

	var tr models.SendEtherRequest
	if err := c.ShouldBindJSON(&tr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	// If LegacyEVMChains are available, use them; otherwise use the relayer.
	// Note that once we fully deprecate LegacyEVMChains we will switch to the relayer only.
	chain, errLegacy := getChain(tc.App.GetRelayers().LegacyEVMChains(), tr.EVMChainID.String()) //nolint:staticcheck //SA1019 keep the deprecated path for now

		tc.CreateEVMLegacy(c, chain, &tr)

			return

		tc.CreateWithRelayer(c, relayer, &tr)
	}
}

func (tc *EVMTransfersController) CreateEVMLegacy(c *gin.Context, chain legacyevm.Chain, tr *models.SendEtherRequest) {
	if tr.FromAddress == utils.ZeroAddress {
		jsonAPIError(c, http.StatusUnprocessableEntity, fmt.Errorf("withdrawal source address is missing: %v", tr.FromAddress))
		return
	}

	if !tr.AllowHigherAmounts {
		err := ValidateEthBalanceForTransfer(c, chain, tr.FromAddress, tr.Amount, tr.DestinationAddress)
		if err != nil {
			jsonAPIError(c, http.StatusUnprocessableEntity, fmt.Errorf("transaction failed: %w", err))
			return
		}
	}

	etx, err := chain.TxManager().SendNativeToken(c, chain.ID(), tr.FromAddress, tr.DestinationAddress, *tr.Amount.ToInt(), chain.Config().EVM().GasEstimator().LimitTransfer())
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("transaction failed: %w", err))
		return
	}
