### Title
Verbose Internal Exception Disclosure on Public HTTP/JSON-RPC Wallet APIs - (File: framework/src/main/java/org/tron/core/services/http/Util.java)

### Summary
Multiple public, unauthenticated `full node` HTTP API servlets and the JSON-RPC layer in java-tron catch generic `Exception`/`Throwable` and echo the raw `e.getMessage()` (and in some cases `e.getClass()`) directly back to the client in the JSON response, mirroring the reported MongoDB verbose-error disclosure pattern (internal error text, field names, and processing details returned unauthenticated to callers).

### Finding Description
Several HTTP servlets funnel unexpected exceptions into `Util.printErrorMsg(e)` / `Util.processError(e, response)`, which write the exception's raw message into the client-visible JSON payload: [1](#0-0) 

This helper is invoked from many unauthenticated GET/POST endpoints, e.g. `GetNodeInfoServlet`, `GetPendingSizeServlet`, `GetBurnTrxServlet`, `GetRewardServlet`, and `GetTransactionInfoByBlockNumServlet`: [2](#0-1) [3](#0-2) 

Other servlets (`GetBlockServlet`, `GetTransactionByIdSolidityServlet`, `GetTransactionInfoByIdSolidityServlet`, `ValidateAddressServlet`) directly place `e.getMessage()` into the JSON `"Error"` field or print it raw: [4](#0-3) [5](#0-4) 

Transaction-execution servlets like `EstimateEnergyServlet` and `TriggerSmartContractServlet` go further and echo `e.getClass() + " : " + errString` — leaking the concrete internal Java exception class name in addition to the message: [6](#0-5) [7](#0-6) 

`Wallet.getTransactionApprovedList` follows the same anti-pattern for the generic catch branch: [8](#0-7) 

`Wallet.broadcastTransaction`'s catch-all also forwards `"Error: " + e.getMessage()` verbatim to the caller: [9](#0-8) 

Comparably, `TronJsonRpcImpl.call` propagates raw exception messages into `JsonRpcInternalException`/`JsonRpcInvalidRequestException`, which the JSON-RPC error resolver serializes to clients unmodified: [10](#0-9) [11](#0-10) 

By contrast, the newer `JsonRpcServlet` (top-level RPC dispatch) has already been hardened to return generic `"Internal error"` messages instead of exception details: [12](#0-11) 
showing that the codebase is aware of this class of issue in some places but has not applied it consistently across the HTTP API and the per-method JSON-RPC error paths.

### Impact Explanation
Exposed messages can reveal internal implementation details (Java exception class names, internal validation logic, LevelDB/RocksDB or storage-layer error text propagated through `Exception.getMessage()`, malformed-input parsing internals) to any unauthenticated caller of the full-node HTTP/JSON-RPC API. This is directly analogous to the reported issue: it discloses backend technology/internal architecture and gives attackers precise feedback for crafting further targeted requests (e.g., probing address decoding, RLP/ABI parsing, or TVM execution internals) — an information-disclosure/attack-surface-expansion issue rather than a fund-loss or consensus issue.

### Likelihood Explanation
High reachability: all affected servlets are default, unauthenticated, publicly exposed full-node HTTP endpoints reachable by anyone who can send a GET/POST request (no privileged role required), and malformed/edge-case input (as in the original report) is trivial to construct (e.g., invalid addresses, malformed hex, out-of-range parameters).

### Recommendation
- Standardize all HTTP servlets and JSON-RPC error paths to use a single sanitized error-handling utility (extend `Util.processError`) that returns a generic client-facing message and an internal correlation/trace id, logging full exception details server-side only.
- Remove `e.getClass()` and raw `e.getMessage()` concatenation from `EstimateEnergyServlet`, `TriggerSmartContractServlet`, `Wallet.getTransactionApprovedList`, and `Wallet.broadcastTransaction`.
- Apply the same generic-error pattern already used in `JsonRpcServlet.handleSingle`/`handleBatch` to the per-method JSON-RPC exception handling in `TronJsonRpcImpl`.

### Proof of Concept
1. Send a GET request to any endpoint using `Util.getAddress`/`decodeFromBase58Check` with a malformed address, e.g. `GET /wallet/getreward?address=INVALIDBASE58`.
2. `GetRewardServlet.doGet` catches `DecoderException | IllegalArgumentException` and returns `{"Error": "INVALID address, " + e.getMessage()}`, exposing the raw decoder exception text: [13](#0-12) 
3. Send a malformed contract JSON body to `POST /wallet/triggersmartcontract` (e.g., invalid hex in `function_parameter`); the catch-all block returns `e.getClass() + " : " + errString`, disclosing the concrete Java exception class name (e.g., `java.lang.NumberFormatException` or an internal parser exception) to the unauthenticated caller: [7](#0-6)

  @Override
  public JsonError resolveError(
      Throwable thrownException, Method method, List<JsonNode> arguments) {
    JsonRpcError resolver = getResolverForException(thrownException, method);
    if (notFoundResolver(resolver)) {
      return null;
    }

    String message = hasErrorMessage(resolver) ? resolver.message() : thrownException.getMessage();

    // data priority: exception > annotation > default ErrorData
    Object data = null;
    if (thrownException instanceof JsonRpcException) {
      JsonRpcException jsonRpcException = (JsonRpcException) thrownException;
      data = jsonRpcException.getData();
    }

    if (data == null) {
      data = hasErrorData(resolver)
          ? resolver.data()
          : new ErrorData(resolver.exception().getName(), message);
    }
    
    return new JsonError(resolver.code(), message, data);
  }
