## Analog Found

### Title
Wallet Contract `has_in_flight_tx` Lock Permanently Stuck on Callback Panic, Causing Denial of Service - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The external report describes how non-standard ERC20 tokens (returning unexpected data instead of a `bool`) cause a Solidity contract's `safeTransfer`/`safeTransferFrom` to unexpectedly revert, permanently DoS-ing the calling contract's core flow. The nearcore analog is the NEAR Wallet Contract's `rlp_execute` mutex-style lock (`has_in_flight_tx`), which is reset to `false` only inside `#[private]` callback methods that process the result of a cross-contract call (potentially to an arbitrary, non-standard NEP-141 "ERC-20-emulated" token contract). If that callback function panics for any reason before completing, the entire receipt's state changes — including the `has_in_flight_tx = false` write — are rolled back by the NEAR runtime, permanently locking the wallet contract.

### Finding Description
`WalletContract::rlp_execute` guards against concurrent transactions with an in-flight flag: [1](#0-0) 

It sets the flag `true` before dispatching a promise and requires it to be reset in the corresponding callback: [2](#0-1) 

For emulated ERC-20 transfers, the contract calls `storage_balance_of` on an externally-controlled token/receiver account and processes the (attacker-influenced) response inside `nep_141_storage_balance_callback`, which resets the flag as its first statement before parsing/using that response: [3](#0-2) 

and the follow-up `rlp_execute_callback`, which similarly resets the flag first, then unwinds the cross-contract call result: [4](#0-3) 

The same pattern of "reset flag first, then process result" is repeated in `address_check_callback`: [5](#0-4) 

Under NEAR's execution model, all state mutations made during a `FunctionCall` — including the earlier `self.has_in_flight_tx = false;` write — are committed only if the function returns without panicking; a panic anywhere later in the same function call (deserialization failure of an oversized/malformed cross-contract response, an unhandled `unwrap`/arithmetic overflow, or gas exhaustion while processing an unexpectedly large/malformed response from a non-compliant NEP-141 contract) reverts the *entire* receipt, including the flag reset. This is directly analogous to the reported issue: an external call to a non-standard token can behave unexpectedly and revert transaction logic that assumed a well-formed response, and here that unexpected behavior/panic causes a critical bookkeeping flag never to be cleared.

Once `has_in_flight_tx` remains stuck at `true`, every future call to `rlp_execute` is unconditionally rejected: [6](#0-5) 

There is no unlock/recovery mechanism in the contract for this state; the wallet contract has no method that can clear `has_in_flight_tx` other than these callbacks succeeding.

### Impact Explanation
If a malicious or non-standard NEP-141 token/contract is used as the `target`/`token_id` in an emulated ERC-20 transfer (or any action requiring a callback), and its response causes a panic inside `nep_141_storage_balance_callback`, `address_check_callback`, or `rlp_execute_callback` (e.g., via an oversized/malformed JSON payload that exceeds the callback's fixed gas budget — `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`RLP_EXECUTE_CALLBACK_GAS` — during `serde_json::from_slice` deserialization), the wallet contract's `has_in_flight_tx` flag is permanently stuck `true`. This freezes the user's wallet contract entirely: no further Ethereum-emulated transactions can ever be executed through `rlp_execute`, effectively permanently locking the account's funds and access from this entry point, a transaction-triggered halt of that account's core functionality.

### Likelihood Explanation
The `target`/token account for `EthEmulationKind::ERC20Transfer` is resolved dynamically (via the address registrar or hash-derived mapping) and is not restricted to trusted, standards-compliant contracts; any account can be interacted with this way. A single relayer-submitted, otherwise validly-signed transaction pointing to a token contract that returns a malformed/oversized `storage_balance_of` response (or a legitimate token later upgraded to a non-standard response format) is sufficient to trigger the panic path, making this reachable from a single external transaction with modest crafting effort.

### Recommendation
- Bound and validate the size/shape of any cross-contract response before deserializing it inside `#[private]` callbacks, and treat unexpected/oversized payloads as a graceful `Failed`-equivalent branch rather than allowing an uncontrolled panic.
- Provide an explicit, privileged or time-boxed recovery path to reset `has_in_flight_tx` (e.g., a timeout-based self-heal, or verifying invariants via `promise_result` shape checks with strict size caps before any parsing) so a single malformed external response cannot permanently brick the wallet contract.
- Increase callback gas budgets defensively or reject calls whose predecessor's returned blob exceeds a safe size before attempting `serde_json::from_slice`.

### Proof of Concept
1. Deploy (or select) an account acting as the `token_id`/`receiver_id` target of an `EthEmulationKind::ERC20Transfer` whose `storage_balance_of` method returns a very large or malformed JSON blob (non-compliant with NEP-141/NEP-145 `StorageBalance`).
2. Have the wallet owner (or a relayer with a validly signed transaction) call `rlp_execute` targeting this token for an ERC-20 emulated transfer, per `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:433-458`.
3. The scheduled `nep_141_storage_balance_callback` is invoked with `has_in_flight_tx` already set `true`; it sets `has_in_flight_tx = false` first, then attempts `serde_json::from_slice::<Option<StorageBalance>>(&value)` on the oversized/malformed blob within the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget, causing gas exhaustion (a panic) mid-function.
4. Because the callback panics, the receipt's state changes — including the `has_in_flight_tx = false` write — are discarded by the runtime; the flag remains `true` in the committed state.
5. Any subsequent `rlp_execute` call from the legitimate owner is now rejected with `"Error: transaction already in progress, please try again later."` indefinitely, since no other code path clears the flag.

    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,

                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
