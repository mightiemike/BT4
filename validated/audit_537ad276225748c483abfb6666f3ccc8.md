### Title
Relayer's `CallerDeposit` fee is permanently lost when an external contract (NEP-141 token or address registrar) returns a non-conforming response - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's meta-transaction relayer flow tracks a `CallerDeposit` so that a relayer's attached deposit can be refunded if a cross-contract call it triggers fails. However, refund logic only exists for the `PromiseResult::Failed` case. When an external contract call *succeeds* but returns data that cannot be deserialized into the expected type, the callback returns an error response without ever consulting `caller_deposit`, permanently stranding the relayer's funds in the contract with no recovery path — directly analogous to the reported bug class of "unexpected/non-conforming return values from external token/contract calls causing failure without proper fallback handling."

### Finding Description
`rlp_execute` accepts an RLP-encoded Ethereum transaction from any relayer/caller and constructs a `CallerDeposit` from the attached deposit whenever the predecessor is not the wallet itself: [1](#0-0) . The comment on `CallerDeposit` explicitly states its purpose is "to refund the caller's deposit if the cross-contract call fails": [2](#0-1) .

For ERC20-emulated transfers, `inner_rlp_execute` first calls `storage_balance_of` on the target NEP-141 token and chains to `nep_141_storage_balance_callback`, passing along `caller_deposit`: [3](#0-2) .

In that callback, when the promise result is `Successful` but the returned bytes fail to deserialize into `Option<StorageBalance>` (e.g. the token contract returns a value in an unexpected shape/format — the same class of non-standard-token-interface issue as the ERC20 `approve()` bug in the report), the function returns immediately with a failure `ExecuteResponse` and **never uses `caller_deposit`**: [4](#0-3) .

The same pattern exists in `address_check_callback`, used for EOA base-token transfers with an address check against the registrar contract: an unexpected/non-conforming response from `address_registrar.lookup()` is handled by returning an error without refunding `caller_deposit`: [5](#0-4) .

By contrast, `rlp_execute_callback` — the terminal callback for the "normal" path — *does* correctly refund `caller_deposit` whenever the promise result is `Failed`: [6](#0-5) . This asymmetry shows the refund logic was intended to cover all failure paths but was only implemented for one of them.

Since `has_in_flight_tx` is reset to `false` in the intermediate callbacks before returning the error response, the wallet contract accepts a new transaction afterward, but the yoctoNEAR value attached by the relayer for this failed transaction is never returned and there is no other function in the contract (no owner/admin rescue method) that can recover it: [7](#0-6) .

### Impact Explanation
This causes permanently frozen funds: a relayer's attached deposit (used to compensate the relayer or cover fees for the emulated Ethereum transaction) is locked forever in the wallet contract if the NEP-141 token or the address registrar contract responds with data in an unexpected format on the happy path. Since the wallet contract is meant to work generically with arbitrary NEP-141 tokens (ERC20 emulation) and any contract set as the address registrar, any token/registrar with a nonstandard response encoding (or a future breaking change in the expected schemas) triggers unrecoverable loss for relayers — meeting the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
This is reachable by any relayer submitting a normal `rlp_execute` meta-transaction with a non-zero attached deposit against an ERC20-emulated NEP-141 token (or an EOA transfer requiring the address-check flow) whose `storage_balance_of` / registrar `lookup` response cannot be parsed into the expected `Option<StorageBalance>` / `Option<AccountId>` shape. No malicious validator or privileged role is required — an ordinary transaction sender/relayer interacting with a token that returns a slightly different (but still successful) response format is sufficient to trigger the bug.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, apply the same refund logic used in `rlp_execute_callback` whenever the function is about to return an early failure `ExecuteResponse` (both on `PromiseResult::Failed` and on deserialization failure of a `Successful` result), refunding `caller_deposit` before returning the error.

### Proof of Concept
1. Deploy a NEP-141-labeled token contract whose `storage_balance_of` view method returns a JSON value not matching `Option<StorageBalance>` (e.g., a bare number or a differently-named struct) while still returning `PromiseResult::Successful`.
2. As a relayer, call `rlp_execute` on a Wallet Contract, submitting an RLP transaction that emulates an ERC20 transfer targeting that token, with a nonzero attached NEAR deposit (fee) and `predecessor_account_id != current_account_id`.
3. Observe: `nep_141_storage_balance_callback` runs, `serde_json::from_slice` fails, and the function returns `ExecuteResponse { success: false, ... }` at [4](#0-3)  without issuing any refund transfer to `caller_deposit.account_id`.
4. Confirm the relayer's attached deposit remains in the wallet contract's balance permanently, with no contract method available to reclaim it.

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
