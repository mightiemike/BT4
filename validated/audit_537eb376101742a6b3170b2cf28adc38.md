### Title
Stale index-cache reused after `vault-system-repay` mutates vault state inside `liquidate()` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` maintains a per-block index cache (`index-cache`, keyed by `{ timestamp: stacks-block-time, aid }`) that is meant to avoid repeated cross-contract calls to the vaults for the borrow index (`index`) and liquidity index (`lindex`) of an asset within the same transaction/block [1](#0-0) . The cache is populated once via `accrue-and-cache`, and afterwards every read goes through `get-cached-indexes`, which is a pure `map-get?` with no re-accrual [2](#0-1) .

### Finding Description
The contract itself acknowledges that some vault-mutating calls change the cached indexes mid-transaction: `socialize-debt-asset` explicitly calls `vault-socialize-debt` and then immediately re-primes `index-cache` by calling `vault-accrue` again and overwriting the map entry, with the comment "Refresh cache with new indexes post-write-down (lindex decreased)" [3](#0-2) . This proves the codebase's own model is that a vault-state-changing call (repay/write-down) can move the `index`/`lindex` values that were already cached earlier in the same transaction.

However, in `liquidate()`, the debt index is read from the cache at the start (during `accrue-user-debts` at line 1406, and again for `scale-debt-for-liquidation`) [4](#0-3) [5](#0-4) . Later in the same call, `vault-system-repay` is invoked to actually settle debt in the vault [6](#0-5) . Immediately after that state-changing call — without any re-priming of `index-cache` — the function computes `other-debt-repayable` by calling `get-cached-indexes debt-aid` again to fetch `other-borrow-idx` [7](#0-6) . This is the exact same cache entry (same `{timestamp, aid}` key) that was set before `vault-system-repay` ran, and unlike `socialize-debt-asset`, `liquidate()` never re-invokes `vault-accrue`/`accrue-and-cache` after the repay to refresh it.

### Impact Explanation
If `vault-system-repay` moves the borrow index the way `vault-socialize-debt` is documented to move `lindex` (both are vault-mutating calls that reduce outstanding debt/exchange-rate state), then `other-debt-repayable` — used to decide whether the borrower has "no collateral left" and therefore whether remaining bad debt must be socialized (lines 1526-1560) — is computed from a stale index. This value gates the `no-collateral-left` branch which controls bad-debt socialization for the whole remaining debt list. Miscomputing it as non-zero when it should be zero (or vice versa) can cause bad debt to escape socialization, permanently leaving unbacked debt in the protocol, or can incorrectly skip repayable remaining debt — a temporary/permanent freezing or insolvency-adjacent effect on protocol/lender funds, i.e., the "permanent freezing of funds" / "protocol insolvency" impact class.

### Likelihood Explanation
I could not fully confirm within available tool calls whether `vault-system-repay` mutates `index`/`lindex` immediately (the vault contract implementations `v0-vault-stx.clar` etc. were not read in full before the iteration budget ran out). The strength of the analog rests entirely on the fact that the market contract's own author treated an equivalent operation (`vault-socialize-debt`) as index-mutating and added an explicit cache refresh for it, but did not apply the same treatment to `vault-system-repay` inside `liquidate()`. This is the same bug class as `BoundedQueue.clear()`: a cached value is trusted after the underlying source has been mutated by an intervening operation, within a single transaction's evaluation order (Clarity evaluates `let` bindings and calls sequentially and deterministically, so this interleaving is guaranteed to occur exactly as written, not merely possible).

### Recommendation
After `vault-system-repay` (and any other vault call in `liquidate()` that can move the borrow index or liquidity index), re-invoke `vault-accrue`/`accrue-and-cache` and overwrite `index-cache` for the affected `aid` before it is read again for `other-debt-repayable`, mirroring the pattern already used in `socialize-debt-asset`. Alternatively, compute all cache-dependent liquidation math before any vault-mutating call runs, so no stale read can occur after mutation.

### Proof of Concept
1. `liquidate()` starts: `accrue-user-debts`/`accrue-user-collateral` populate `index-cache` at `{timestamp: stacks-block-time, aid: debt-aid}` with the pre-repay index [4](#0-3) .
2. `scale-debt-for-liquidation` reads that cached index to compute `debt-to-repay`/`scaled-to-remove` [8](#0-7) .
3. `vault-system-repay debt-aid debt-to-repay …` executes, mutating vault state for `debt-aid` [6](#0-5) .
4. `debt-remove-scaled` and `collateral-remove` run against `market-vault` [9](#0-8) .
5. `other-debt-repayable` is computed re-reading `get-cached-indexes debt-aid` — the same, un-refreshed cache entry from step 1 — to derive `other-borrow-idx` used in scaling `other-tokens` into `other-scaled`/`other-debt-repayable` [7](#0-6) .
6. `other-debt-repayable` feeds directly into `no-collateral-left`, which gates whether the remaining debt is force-socialized as bad debt [10](#0-9) .
7. Contrast with `socialize-debt-asset`, which the developers explicitly re-primed the cache for after an equivalent vault mutation, confirming the intended invariant that is violated here [3](#0-2) .

Note: full confirmation that `vault-system-repay` actually changes the cached `index` value (as opposed to being a pure balance transfer with no index effect) requires reading the vault contract implementations (e.g., `mainnet/contracts/vault/v0-vault-stx.clar`), which I was not able to complete before this session's tool budget was exhausted. If `vault-system-repay` does not touch `index`/`lindex`, this finding reduces to a defense-in-depth/no-impact observation rather than a live vulnerability — I recommend a Devin session with full repository access to verify the vault contracts' `system-repay` and `accrue` implementations before treating this as confirmed.

(define-private (scale-debt-for-liquidation
  (debt-final uint)
  (coll-actual uint)
  (curr-scaled uint)
  (asset-id uint))
  (let (;; convert debt amount to scaled units for storage
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        (scaled-debt (mul-div-down debt-final INDEX-PRECISION borrow-index))
        ;; cap at current debt (prevent over-repayment)
        (scaled-to-remove (if (> scaled-debt curr-scaled) curr-scaled scaled-debt))
        (debt-to-repay (mul-div-up scaled-to-remove borrow-index INDEX-PRECISION))
        ;; If debt was capped, scale collateral proportionally
        (coll-final (if (< scaled-to-remove scaled-debt)
                        (mul-div-down coll-actual scaled-to-remove scaled-debt)
                        coll-actual)))
    {
      scaled-to-remove: scaled-to-remove,
      debt-to-repay: debt-to-repay,
      coll-final: coll-final
    }))
