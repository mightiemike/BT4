### Title
Unbounded `PendingInbounds.Walk()` in `afterInboundBallotTerminal` causes O(n²) gas blow-up reachable by ordinary cross-chain deposit spam - (File: `x/uexecutor/keeper/ballot_hooks.go`)

### Summary
The external report describes `massUpdatePools()` looping over an unbounded `poolInfo` array, risking a block-gas-limit DoS. The Push Chain analog is `BallotHooks.afterInboundBallotTerminal`, which performs a full linear `Walk()` over the entire `PendingInbounds` collection every single time any inbound ballot reaches a terminal state, in order to find which entry owns the terminating `ballotID`.

### Finding Description
`PendingInbounds` is a `collections.Map[string, types.PendingInboundEntry]` populated by `RecordInboundVote` [1](#0-0) , which is called on the **first validator vote** for any observed inbound event [2](#0-1) . Every distinct source-chain deposit (attacker-controlled: any unprivileged user can trigger arbitrary numbers of these by sending deposits/transfers on any supported external chain) creates or extends an entry here, and the entry is only removed once **all** of its ballot variants reach a terminal state (PASSED/REJECTED/EXPIRED) via the `BallotHooks` callback wired into `x/uvalidator`'s generic ballot machine [3](#0-2) .

The lookup that locates the owning entry for a terminating ballot is an unindexed, full-collection scan: [4](#0-3) 

The code comment explicitly assumes "the pending set is small and transient" [5](#0-4) , but nothing in the scoped code enforces that assumption — there is no cap on `PendingInbounds` size and no index from `ballotID` to `utxKey`. Because this hook fires synchronously inside `VoteInbound`/`VoteOnBallot` execution (i.e., during a validator's `MsgVoteInbound` transaction), the gas cost of *every* ballot finalization becomes proportional to the total number of concurrently in-flight inbounds across the whole chain, not just to the terminating ballot's own data.

An unprivileged attacker can drive `len(PendingInbounds)` arbitrarily high simply by depositing many small/cheap cross-chain transactions on any supported source chain faster than validators can drive them all to quorum/expiry in the same block window. Since each new terminal event re-scans the full, growing map, the aggregate cost of finalizing N concurrent inbounds is O(N²) rather than O(N), independent of any malicious validator or admin action — purely a function of ordinary deposit volume.

### Impact Explanation
As `PendingInbounds` grows, each subsequent `MsgVoteInbound` transaction that triggers a ballot termination pays an increasing, attacker-inflated gas cost for the `Walk()`. This can push individual validator vote transactions toward (or over) the block gas limit, stalling inbound finalization for the whole chain (a liveness/DoS condition on the universal-execution inbound path), consistent with the "denial of service...reachable without privileged control" allowed impact. This does not require any malicious validator, admin, or peer — only volume of ordinary user deposits.

### Likelihood Explanation
Likelihood is Medium: it requires sustained, high-volume deposit spam across possibly multiple source chains to grow `PendingInbounds` large enough to matter within a narrow window before ballots reach quorum/expiry, and per-entry costs are cheap key-value reads. But no permission, stake, or validator collusion is needed — any address that can transact on a supported source chain can attempt this, making the trigger fully unprivileged.

### Recommendation
Add a secondary index from `ballotID -> utxKey` (mirroring the pattern already used for `PendingOutbounds`) so `afterInboundBallotTerminal` can do an O(1) lookup instead of a full `Walk()`, and/or bound the number of concurrently trackable `PendingInbounds` entries (e.g., per-source-chain rate limiting or a max-pending cap) to eliminate the O(N²) aggregate cost.

### Proof of Concept
1. An attacker submits a large number of distinct, low-value deposit transactions on a supported external chain in a short window.
2. Validators observe each as a separate `Inbound` and call `RecordInboundVote`, each creating a new `PendingInboundEntry` in `PendingInbounds` [6](#0-5) .
3. As ballots begin finalizing (pass/reject/expire), each termination invokes `afterInboundBallotTerminal`, which performs a full `Walk()` over the now-large `PendingInbounds` map [4](#0-3) .
4. As more deposits keep arriving faster than the pending set drains, the per-transaction cost of every validator's `MsgVoteInbound` grows, eventually threatening block-gas-limit exhaustion for inbound-processing transactions network-wide.

func (k Keeper) RecordInboundVote(
	ctx context.Context,
	inbound types.Inbound,
	voter string,
	ballotID string,
) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	height := uint64(sdkCtx.BlockHeight())
	utxKey := types.GetInboundUniversalTxKey(inbound)

	entry, err := k.PendingInbounds.Get(ctx, utxKey)
	if err != nil && !errors.Is(err, collections.ErrNotFound) {
		return err
	}
	if errors.Is(err, collections.ErrNotFound) {
		entry = types.PendingInboundEntry{
			UtxKey:          utxKey,
			CreatedAtHeight: height,
		}
	}

// AfterBallotTerminal is invoked by x/uvalidator when a ballot reaches a
// terminal state. For INBOUND_TX ballots this:
//
//  1. Marks the matching variant in the PendingInbounds entry with the
//     terminal status that was reached.
//  2. If ANY variant is still PENDING, persists the updated entry and
//     returns — the entry continues to wait on the remaining ballot(s).
//  3. If ALL variants are now terminal:
//     a. Removes the entry from PendingInbounds.
//     b. If any variant ended PASSED, the existing post-finalization path
//        in VoteInbound has already produced a UniversalTx — nothing more
//        to do.
//     c. If ALL variants ended EXPIRED/REJECTED (no UTX was ever created),
//        copies the entry into ExpiredInbounds preserving the full
//        per-variant audit trail for the future escape-hatch refund flow.
//
// Hook implementations are required to be idempotent and must not block
// the terminal transition by returning errors for non-fatal conditions.
// Decode failures and "entry already cleared" cases are warning-logged
// and swallowed.
func (h BallotHooks) AfterBallotTerminal(
	ctx sdk.Context,
	ballotID string,
	ballotType uvalidatortypes.BallotObservationType,
	status uvalidatortypes.BallotStatus,
) error {
	switch ballotType {
	case uvalidatortypes.BallotObservationType_BALLOT_OBSERVATION_TYPE_INBOUND_TX:
		return h.afterInboundBallotTerminal(ctx, ballotID, status)
	default:
		// OUTBOUND_TX, TSS_KEY, FUND_MIGRATION — not handled here.
		// See doc comment on BallotHooks for rationale on outbound.
		return nil
	}
}
