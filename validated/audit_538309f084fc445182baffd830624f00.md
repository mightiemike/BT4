### Title
Unverified `write_set` binding to `TransactionInfo.state_change_hash` during transaction backup restore - (File: storage/aptosdb/src/backup/restore_utils.rs)

### Summary
When restoring transactions from a backup (non-replay restore path, i.e. `kv_replay=false`, the default/fast-restore mode), `save_transactions_impl` persists the `write_set` for each transaction directly into `WriteSetDb` without ever checking that the write set's cryptographic hash matches the `state_change_hash` field carried inside the corresponding accumulator-proof-verified `TransactionInfo`.

### Finding Description
`TransactionRestoreController`/`LoadedChunk::load` reads `(txn, aux_info, txn_info, events, write_set)` records from a backup file and verifies only `txn_list_with_proof.verify(ledger_info.ledger_info(), ...)`, which authenticates `txns`, `events`, and `txn_infos` against the transaction accumulator via `TransactionInfoListWithProof::verify` (hashing `transaction_infos` and checking against the accumulator root in the signed ledger info). [3](#0-2)  `write_sets` is decoded from the same record but stored in a separate field of `LoadedChunk` and is not part of the `TransactionListWithProofV2`/`TransactionListWithProof` structure being verified. [4](#0-3) 

Downstream, `save_transactions` → `save_transactions_impl` commits `write_sets[idx]` to `WriteSetDb::put_write_set` purely by positional index, with no assertion that `CryptoHash::hash(write_sets[idx])` equals `txn_infos[idx].state_change_hash()` (the field `TransactionInfo` exposes precisely for this purpose, as seen used elsewhere, e.g. `write_set_hash = CryptoHash::hash(txn_output.write_set())` feeding `state_change_hash` at execution time in `execution/executor/src/workflow/do_ledger_update.rs`). [5](#0-4) [6](#0-5) 

This is only bypassed correctly when `kv_replay` is true and `first_version > 0`, because then `state_store.calculate_state_and_put_updates` re-derives state from the write set directly rather than trusting a pre-existing checkpoint (though even then the raw `write_set` bytes stored in `WriteSetDb` are the same unverified value). [7](#0-6) 

### Impact Explanation
A backup file that is corrupted or supplied by a compromised/misbehaving backup storage backend (`BackupStorage` implementations are pluggable and often point to external, non-consensus-verified storage such as S3/GCS) could substitute a different `write_set` for a given `(txn, txn_info)` pair while keeping `txn`, `events`, and `txn_info` intact and passing accumulator verification. The restoring node would durably persist the wrong `WriteSet` under `WriteSetDb` at that version, i.e. **committed state/write-set data that differs from the correct VM result**, while the accumulator-proof-verified `TransactionInfo.state_change_hash` (exposed via the transactions API and used by light clients/provers) still reflects the *original, correct* hash. This creates a durable mismatch between the authenticated `state_change_hash` and the actual on-disk `write_set` content served by node APIs that expose write sets (e.g. `GET /transactions/by_version` change sets), which is exactly the "authenticated API output bound to the wrong... object" and "corrupts durable ledger data" impact category.

### Likelihood Explanation
This requires control over, or corruption of, backup archive content that is fed into `TransactionRestoreController` — this is a real operational path used for state-sync bootstrapping and disaster recovery, not privileged governance/consensus code, so a malicious or compromised backup source is a plausible "unprivileged" input vector relative to the restoring node's own state-commitment logic. However, exploitation requires the attacker to control or corrupt the specific backup storage location, which somewhat limits practical likelihood — I could not fully verify whether backups are additionally protected by transport/storage-level authentication in production deployment configs, which would reduce likelihood further.

### Recommendation
In `LoadedChunk::load` (or `save_transactions_impl`), assert `CryptoHash::hash(&write_sets[idx]) == txn_infos[idx].state_change_hash()` for every transaction before accepting/persisting the chunk, matching the same check performed by normal VM execution when constructing `TransactionInfo`.

### Proof of Concept
1. Take a valid transaction backup manifest/chunk file.
2. Keep `txn`, `events`, and `txn_info` records unchanged (so `txn_list_with_proof.verify()` in `LoadedChunk::load` still succeeds against the signed `LedgerInfo`).
3. Replace the `write_set` bytes for one record with an alternative `WriteSet` (different key/value writes) — its hash will differ from that transaction's `state_change_hash`, but this is never checked.
4. Run `TransactionRestoreController` against this modified backup; `save_transactions_impl` will persist the substituted `write_set` into `WriteSetDb` at that version with no error, producing a node whose stored write set at that version diverges from the one committed on-chain/authenticated by the ledger info.

Note: I was not able to fully trace whether any later consistency check (e.g., during subsequent JMT/state rebuild from these write sets, `kv_replay=true` path, or verify-mode restore) would eventually catch this discrepancy in all restore configurations — this should be checked with a Devin session that can run the restore test suite (`storage/aptosdb/src/backup/`, `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`) to confirm exploitability end-to-end.

struct LoadedChunk {
    pub manifest: TransactionChunk,
    pub txns: Vec<Transaction>,
    pub persisted_aux_info: Vec<PersistedAuxiliaryInfo>,
    pub txn_infos: Vec<TransactionInfo>,
    pub event_vecs: Vec<Vec<ContractEvent>>,
    pub write_sets: Vec<WriteSet>,
    pub range_proof: TransactionAccumulatorRangeProof,
}

impl LoadedChunk {
    async fn load(
        manifest: TransactionChunk,
        storage: &Arc<dyn BackupStorage>,
        epoch_history: Option<&Arc<EpochHistory>>,
    ) -> Result<Self> {
        let mut file = BufReader::new(storage.open_for_read(&manifest.transactions).await?);
        let mut txns = Vec::new();
        let mut persisted_aux_info = Vec::new();
        let mut txn_infos = Vec::new();
        let mut event_vecs = Vec::new();
        let mut write_sets = Vec::new();

        while let Some(record_bytes) = file.read_record_bytes().await? {
            let (txn, aux_info, txn_info, events, write_set): (
                _,
                PersistedAuxiliaryInfo,
                _,
                _,
                WriteSet,
            ) = match manifest.format {
                TransactionChunkFormat::V0 => {
                    let (txn, txn_info, events, write_set) = bcs::from_bytes(&record_bytes)?;
                    (
                        txn,
                        PersistedAuxiliaryInfo::None,
                        txn_info,
                        events,
                        write_set,
                    )
                },
                TransactionChunkFormat::V1 => bcs::from_bytes(&record_bytes)?,
            };
            txns.push(txn);
            persisted_aux_info.push(aux_info);
            txn_infos.push(txn_info);
            event_vecs.push(events);
            write_sets.push(write_set);
        }

        ensure!(
            manifest.first_version + (txns.len() as Version) == manifest.last_version + 1,
            "Number of items in chunks doesn't match that in manifest. first_version: {}, last_version: {}, items in chunk: {}",
            manifest.first_version,
            manifest.last_version,
            txns.len(),
        );

        let (range_proof, ledger_info) = storage
            .load_bcs_file::<(TransactionAccumulatorRangeProof, LedgerInfoWithSignatures)>(
                &manifest.proof,
            )
            .await?;
        if let Some(epoch_history) = epoch_history {
            epoch_history.verify_ledger_info(&ledger_info)?;
        }

        // make a `TransactionListWithProof` to reuse its verification code.
        let txn_list_with_proof =
            TransactionListWithProofV2::new(TransactionListWithAuxiliaryInfos::new(
                TransactionListWithProof::new(
                    txns,
                    Some(event_vecs),
                    Some(manifest.first_version),
                    TransactionInfoListWithProof::new(range_proof, txn_infos),
                ),
                persisted_aux_info,
            ));
        txn_list_with_proof.verify(ledger_info.ledger_info(), Some(manifest.first_version))?;
