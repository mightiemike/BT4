### Title
Wallet Contract Pays Relayer Fee via Unchained Promise Independent of Main Action Success - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`inner_rlp_execute` creates the relayer-fee transfer as a standalone `Promise` batch (not chained via `.then()`) that is dispatched in parallel with — and independently of — the promise executing the user's actual intended action (base-token `Transfer` or ERC-20 `ft_transfer`). Because NEAR does not roll back sibling receipts spawned from the same function call when one of them fails, the fee payment to the relayer is never conditioned on, nor rolled back if, the paired action fails.

### Finding Description
In `inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:374-385`), for `EOABaseTokenTransfer`/`ERC20Transfer` transaction kinds with a non-zero `fee`, the code does:
```rust
let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
env::promise_batch_action_transfer(refund_promise, *fee);
``` [3](#0-2) 

This creates a brand-new, sibling promise/receipt to the relayer, entirely disconnected from the `promise` variable built later in the same function (`action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))`, line 469), which carries out the actual transfer and eventually reports success/failure via `rlp_execute_callback`. [4](#0-3) 

Since each `promise_batch_create` call spawns an independent action receipt, and NEAR provides no atomicity across sibling receipts from the same function call (each receipt commits or rolls back on its own), the fee-transfer receipt executes and commits independently of whether the main action receipt succeeds. If the wallet account's balance is only just sufficient to cover the fee but insufficient (after the fee is deducted) to also cover the deposit/transfer amount of the main action, or if the main action fails for any other reason (bad receiver, contract call revert, insufficient gas, etc.), the fee is still paid out to the relayer while the user's intended transfer/action fails — exactly mirroring the "fee transfer that is not verified against the success of the underlying operation" pattern in the source report's `_updatePosition`/`_transfer` issue.

### Impact Explanation
This allows a relayer (an unprivileged caller who merely needs a validly signed Ethereum-style transaction from the wallet owner) to be paid the specified fee even when the wallet's actual intended action fails, directly transferring value out of the ETH-implicit wallet account without delivering the corresponding service. The wallet owner suffers an unauthorized/unearned value transfer with no way to recover the fee even though the underlying operation never went through. Because a malicious or careless relayer can specifically craft `target`/gas parameters to intentionally cause the main action to fail (e.g., pointing `target` at a contract that will reject the call, or by relying on limited wallet balance) while collecting the fee, this is a concrete mechanism for unauthorized value movement from a normal user's wallet.

### Likelihood Explanation
Reachable purely by an unprivileged relayer submitting a single, otherwise well-formed `rlp_execute` transaction on behalf of a user (who signed intending to pay a fee for a successful relay). No validator or node compromise is required, and the relayer only needs a validly signed underlying Ethereum-style transaction from the wallet's owner (which the owner would sign expecting the paired action to succeed). The code comments even acknowledge the fee is unconditionally sent ("Users should always verify the fee before signing... Relayers should also verify the fee before sending"), which shows the developers were aware money moves independently of success, but the mitigation relies entirely on off-chain trust/vigilance rather than any on-chain verification — a known-and-accepted risk that nonetheless permits deterministic loss of funds under adversarial or simply degraded conditions.

### Recommendation
Chain the fee-payment promise so that it only executes (or is only retained) contingent on the success of the main action's promise, e.g. by moving the `promise_batch_action_transfer` for the fee into a `.then()` continuation off of the main action's promise (only paying if `PromiseResult::Successful`), or by making the fee payment part of the same combined `Promise` batch chain that also performs the transfer/ft_transfer, so a single receipt failure prevents the fee from being paid. Alternatively, add a callback that inspects the main action's `PromiseResult` and issues the fee transfer only when successful.

### Proof of Concept
1. A relayer holds a wallet owner's signed Ethereum-style transaction with `to` = some receiver, `value` = an amount close to the wallet's full balance, and `gas_price`/`gas_limit` set so that `tx_fee` (computed in `parse_rlp_tx_to_action`, `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:59-64`) is non-zero.
2. Relayer calls `rlp_execute(target, tx_bytes_b64)` on the wallet contract.
3. `inner_rlp_execute` immediately spawns and commits the fee-transfer receipt to the relayer (lines 381-384) — independent of the main transfer.
4. The main action's `Transfer` promise (lines 466-470) subsequently fails because the wallet's balance, after the fee was already deducted, is insufficient to cover the intended `value` transfer (or the receiver rejects the call for any other reason).
5. Result: the relayer has been paid `fee`, while the user's intended transfer never took effect — an unconditional value transfer decoupled from the success of the operation it was meant to compensate.
