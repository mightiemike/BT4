### Title
`DelegateAction` Signed Payload Contains No Chain Binding, Enabling Cross-Fork Signature Replay - (File: `core/primitives/src/action/delegate.rs`)

### Summary
`DelegateAction` (NEP-366 meta-transactions) signs a payload that contains no chain identifier or block hash. Unlike a regular `SignedTransaction`, which includes a `block_hash` that is validated as an ancestor of the current canonical chain, a `SignedDelegateAction` is bound only by a `nonce` and a `max_block_height`. If NEAR mainnet were to undergo a contentious hard fork producing two live chains sharing the same genesis, any `DelegateAction` signed after the fork point for one chain is cryptographically valid on the other chain, because the signed bytes are identical on both. A relayer can replay the user's signed authorization on the sibling chain without the user's knowledge, executing arbitrary inner actions (transfers, function calls, key additions) against the user's account on that chain.

### Finding Description

A regular NEAR `SignedTransaction` includes a `block_hash` field:

```
Transaction { signer_id, public_key, nonce, receiver_id, block_hash, actions }
```

`check_transaction_validity_period` walks the canonical chain to confirm `block_hash` is an ancestor of the current head and within `transaction_validity_period` blocks. A block hash that exists only on chain A cannot satisfy the ancestor check on chain B after a fork, so regular transactions are chain-bound by construction.

`DelegateAction` has no such field:

```rust
pub struct DelegateAction {
    pub sender_id: AccountId,
    pub receiver_id: AccountId,
    pub actions: Vec<NonDelegateAction>,
    pub nonce: Nonce,
    pub max_block_height: BlockHeight,
    pub public_key: PublicKey,
}
```

The signing hash is computed as:

```rust
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}
```

`SignableMessage` prepends only a fixed NEP-366 discriminant (`MIN_ON_CHAIN_DISCRIMINANT + 366`). Neither the genesis hash, the NEAR `chain_id` string, nor any block hash is mixed into the signed bytes. The same Borsh-serialized bytes, and therefore the same signature, are valid on every chain that shares the same genesis state up to the fork point. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

By contrast, a regular transaction's `block_hash` is validated against the canonical chain: [5](#0-4) 

No equivalent chain-binding check exists for `DelegateAction`.

### Impact Explanation

After a fork, both chains share identical account state (balances, nonces, access keys) up to the fork block. A user who signs a `DelegateAction` with nonce `N` for chain A after the fork has their nonce at `N` on chain B as well (because the fork-point state is identical). A relayer holding the signed bytes can submit the same `SignedDelegateAction` to chain B. The runtime's `apply_delegate_action` will:

1. Verify the signature — passes, because the signed bytes are identical.
2. Check `nonce > access_key.nonce` — passes, because the nonce state on chain B is the same as on chain A at the fork point.
3. Execute the inner actions (e.g., `Transfer`, `FunctionCall`, `AddKey`) against the user's account on chain B.

The user loses funds or has unauthorized key additions applied on the chain they did not intend to interact with. [6](#0-5) 

### Likelihood Explanation

A contentious hard fork producing two live NEAR chains is a low-probability event. However, the structural absence of chain binding is a code-level invariant violation that requires no attacker capability beyond holding a legitimately obtained `SignedDelegateAction`. The relayer role is explicitly untrusted in the meta-transaction model (the relayer pays gas but must not be able to alter the user's intent). Cross-fork replay violates this trust boundary without any privileged access.

### Recommendation

**Short term:** Include the genesis block hash (available as `GenesisId.hash`) or the NEAR `chain_id` string in the `DelegateAction` signed payload, analogously to how EIP-712 domain separators bind signatures to a specific chain. The `SignableMessage` wrapper is the correct place to add this binding.

**Long term:** Align the NEP-461 standard with an explicit chain-binding field so that all future signable message types are chain-scoped by default.

### Proof of Concept

1. User Alice signs a `DelegateAction` (nonce=5, max_block_height=10000) authorizing relayer Bob to transfer 100 NEAR to Carol on mainnet.
2. A contentious hard fork occurs at block 9000, producing chain A (mainnet) and chain B (fork).
3. Bob submits the `SignedDelegateAction` on chain A — Alice's nonce advances to 6 on chain A.
4. Bob submits the identical `SignedDelegateAction` bytes on chain B — the runtime calls `signed_delegate_action.verify()`, which recomputes `get_nep461_hash()` over the same bytes and verifies the same signature. Alice's nonce on chain B is still 5 (fork-point state), so the nonce check passes. 100 NEAR is transferred from Alice's account on chain B without her authorization. [7](#0-6) [8](#0-7)

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

pub fn check_transaction_validity_period(
    chain_store: &ChainStoreAdapter,
    prev_block_header: &BlockHeader,
    base_block_hash: &CryptoHash,
    transaction_validity_period: BlockHeightDelta,
) -> Result<(), InvalidTxError> {
    let base_header =
        chain_store.get_block_header(base_block_hash).map_err(|_| InvalidTxError::Expired)?;

    metrics::CHAIN_VALIDITY_PERIOD_CHECK_DELAY
        .observe(prev_block_header.height().saturating_sub(base_header.height()) as f64);

    // First check the distance between blocks
    if prev_block_header.height() > base_header.height() + transaction_validity_period {
        return Err(InvalidTxError::Expired);
    }

    // Then check if there is a path between the blocks (`base` is an ancestor of `prev`)
    validity_period_validate_is_ancestor(&base_header, prev_block_header, chain_store)
}
