### Title
Origin's TRX-fee liability is computed using the caller's frozen-energy balance instead of the origin's own, causing incorrect fee attribution between contract creator and caller - (File: `chainbase/src/main/java/org/tron/core/capsule/ReceiptCapsule.java`)

### Summary
Like the Cosmos-SDK `FeeGranter`/`FeePayer` bug, java-tron has a two-party fee-sponsorship model for contract execution: a contract's creator (`origin`) can subsidize a percentage of the energy consumed by a `caller` (via `consumeUserResourcePercent` / `origin_energy_limit`, configured through `UpdateEnergyLimitContractActuator`) [1](#0-0) . When settling the bill, `TransactionTrace.pay()` splits total energy usage between `origin` and `caller` and calls `ReceiptCapsule.payEnergyBill()` for each party separately [2](#0-1) .

### Finding Description
`ReceiptCapsule` keeps two distinct fields for tracking pre-execution available frozen energy: `originEnergyLeft` (the creator's available energy) and `callerEnergyLeft` (the caller's available energy) [3](#0-2) . `callerEnergyLeft` is populated exclusively for the caller account by `VMActuator.getAccountEnergyLimitWithFixRatio()` [4](#0-3) , while `originEnergyLeft` is populated separately for the creator account in `getTotalEnergyLimitWithFixRatio()` [5](#0-4) .

`payEnergyBill()`'s public entry point correctly caps `originUsage` by the origin's real leftover frozen energy via `getOriginUsage()`, which reads `originEnergyLeft` [6](#0-5) . However, the private helper that actually performs the TRX-fee deduction, also named `payEnergyBill(account, usage, ...)`, is invoked for **both** the origin and the caller, and unconditionally reads the `callerEnergyLeft` field — never `originEnergyLeft` — when the freeze/unfreeze-delay feature is active:

```java
long accountEnergyLeft;
if (dynamicPropertiesStore.getAllowTvmFreeze() == 1
    || dynamicPropertiesStore.supportUnfreezeDelay()) {
  accountEnergyLeft = callerEnergyLeft;
} else {
  accountEnergyLeft = energyProcessor.getAccountLeftEnergyFromFreeze(account);
}
``` [7](#0-6) 

When this helper is called for the **origin** account, `accountEnergyLeft` is set to the *caller's* frozen-energy balance rather than the origin's own. If `usage` (the origin's already-capped energy share) exceeds this mismatched `callerEnergyLeft` value — which can easily happen if the caller has little or no frozen energy while the origin (a dApp/creator subsidizing users) has ample frozen energy — the code incorrectly falls into the "insufficient energy" branch and deducts a TRX `energyFee` from the **origin's** TRX balance for energy the origin actually had available for free:

```java
} else {
  energyProcessor.useEnergy(account, accountEnergyLeft, now);
  ...
  long energyFee = (usage - accountEnergyLeft) * sunPerEnergy;
  account.setBalance(balance - energyFee);
  ...
}
``` [8](#0-7) 

### Impact Explanation
This is a concrete accounting-divergence bug in a reachable, unprivileged code path: any user can trigger a smart contract whose creator has configured `consumeUserResourcePercent < 100` (via `UpdateEnergyLimitContractActuator`, a normal owner action) and has frozen TRX for energy, while the calling account's own frozen-energy balance happens to be smaller than the origin's per-call energy share. In that scenario the origin (fee-sponsoring party, analogous to the `FeeGranter`) is erroneously charged real TRX fees it should not owe, because the fee-liability check uses the wrong account's leftover-energy figure. This mirrors the root cause of the referenced report — mixing up the roles of the two parties in a fee-sponsorship relationship — and results in unintended balance drain from the sponsoring account, i.e., incorrect on-chain accounting/settlement.

### Likelihood Explanation
The conditions are not exotic: `allowTvmFreeze`/`supportUnfreezeDelay` are chain-parameter flags already referenced throughout the codebase as active features (Stake 1.0/2.0 energy freeze mechanisms), and any contract owner can set `consumeUserResourcePercent` below 100 to subsidize callers, which is a standard/common developer practice to sponsor user gas. Any caller with low frozen energy interacting with such a contract will trigger the mis-attributed charge, making this readily reachable without special privileges.

### Recommendation
In the private `payEnergyBill(account, usage, ...)` helper, select the leftover-energy figure based on which account is being billed (use `originEnergyLeft` when `account` is `origin`, and `callerEnergyLeft` when `account` is `caller`) instead of unconditionally reading `callerEnergyLeft`.

### Proof of Concept
1. Contract creator (`origin`) deploys a contract and calls `UpdateSettingContract`/`UpdateEnergyLimitContract` to set `consumeUserResourcePercent < 100` with a large `origin_energy_limit`, and freezes TRX for energy so `originEnergyLeft` is large.
2. A caller with little or no frozen energy (`callerEnergyLeft` small) triggers the contract, consuming energy that is well within the origin's own frozen allowance.
3. During `TransactionTrace.pay()` → `ReceiptCapsule.payEnergyBill()`, `originUsage` is correctly capped below the origin's real `originEnergyLeft`, but the private `payEnergyBill(origin, originUsage, ...)` compares `originUsage` against `callerEnergyLeft` (the caller's small value) instead [7](#0-6) .
4. Since `originUsage > callerEnergyLeft`, the origin is charged an unwarranted TRX `energyFee` for energy it actually had available for free, draining its balance instead of the intended cost-free consumption.
