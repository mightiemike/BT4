**Analysis:**

`maybe_start_cleaner`'s `regular_target_version` is not an independently computed "current version" snapshot — it is read from (or initialized from) `DbMetadataKey::StateMerklePrunerProgress`, i.e., the *actual* regular state-merkle pruner's own persisted `min_readable_version` progress marker. [1](#0-0) 

That progress value is only ever advanced by the real pruner via `set_pruner_target_db_version`, which computes `min_readable_version = latest_version.saturating_sub(self.prune_window)` — always trailing the live commit frontier by at least the configured `prune_window` (100,000–1,000,000 versions by default) — and is only persisted (`save_min_readable_version`) after the corresponding shard pruning batches actually complete. [2](#0-1) [3](#0-2) 

The `prune_window` is explicitly documented to be sized larger than the number of versions the state-committing thread can produce during in-flight execution, precisely to guarantee this margin against concurrent commits. [4](#0-3) 

Consequently, `run_cleanup` only deletes `JellyfishMerkleNodeSchema` entries referenced by `StaleNodeIndexSchema`/`StaleNodeIndexCrossEpochSchema` records whose `stale_since_version <= regular_target_version` — i.e., nodes that the real pruner's own invariants have already sanctioned as safe to delete, using the exact same boundary the live pruner already established with its safety margin. [5](#0-4) 

Because `regular_target_version` is derived from (and never exceeds) the already-persisted, margin-protected pruner progress rather than the live write frontier, enabling the cleaner (`batch_size>0`) cannot cause it to race ahead of concurrently-committing versions. The `batch_size=0` disablement path is simply an operator no-op that skips the cleanup thread entirely and has no effect on the boundary computation when re-enabled — the target is always bound to the previously-validated safe pruning cursor, not to unbounded attacker-driven churn. There is no path by which unprivileged transaction/state churn can push this snapshot ahead of in-flight commits or corrupt proofs for versions being concurrently finalized by the executor-to-storage commit path.
