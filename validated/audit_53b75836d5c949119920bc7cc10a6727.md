### Title
Partial market-order state mutation persists when `MarketSellAssetActuator` aborts mid-match due to `MAX_MATCH_NUM` overflow - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.matchOrder()` mutates and persists maker-order state (`MarketUtils.updateOrderState`, which writes directly to `MarketAccountStore`) *inside* the matching loop, before the taker-side commit (`orderStore.put`/`accountStore.put`) at the end of `execute()`. If the loop throws `ContractValidateException("Too many matches...")` after `MAX_MATCH_NUM` is exceeded, the already-applied maker-side store writes are not explicitly reverted by the actuator itself — mirroring the reported bug class of "state transitioned before all pre-checks/limits are enforced, with no explicit revert path on the failure branch."

### Finding Description
`matchOrder()` iterates over maker orders and, for each match, calls `matchSingleOrder()`, which calls `MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore)` [1](#0-0) . `updateOrderState` immediately persists a store write, removing the order from the maker account's active-order list via `marketAccountStore.put(...)` [2](#0-1) . This happens unconditionally for each maker order matched, on every iteration of the `while` loop in `matchOrder()` [3](#0-2) .

The `MAX_MATCH_NUM` cap check happens only *after* the match/state-mutation for that iteration has already been applied:
```
matchOrderCount++;
if (matchOrderCount > MAX_MATCH_NUM) {
  throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
}
``` [4](#0-3) 

When this exception propagates, `execute()`'s catch block only marks the transaction result as `FAILED` and rethrows `ContractExeException` — it performs no compensating rollback of the maker-side store mutations already applied in the loop:
```
} catch (ItemNotFoundException | InvalidProtocolBufferException
    | BalanceInsufficientException | ContractValidateException e) {
  logger.debug(e.getMessage(), e);
  ret.setStatus(fee, code.FAILED);
  throw new ContractExeException(e.getMessage());
}
``` [5](#0-4) 

This is the same bug class as the report: a resource is transitioned to a new "in-progress/consumed" state via a direct, eagerly-applied write, but the code path that enforces limits/pre-checks (`MAX_MATCH_NUM`) runs only after some of those transitions have already occurred, and the failure path has no explicit "revert to previous state" call analogous to `revertPromoToPending()`.

I was not able to fully confirm from the retrieved code whether the enclosing per-transaction `ISession` (seen in `Manager` block-generation code, e.g. `try (ISession tmpSession = revokingStore.buildSession()) { ...; tmpSession.merge(); } catch (Exception e) { ... }`) discards these writes when `ContractExeException` is thrown, or whether the transaction is still recorded as valid-but-`FAILED` with the session merged regardless (which is the normal java-tron behavior for `FAILED` transactions, since fees are still charged for failed contract calls). This distinction is the crux of whether the maker-order mutations become permanently persisted or are cleanly rolled back, and I could not verify it with certainty from the available index. If the session is merged (as is typical for `FAILED`-status transactions that still pay fees), the maker orders removed from `MarketAccountStore` during the aborted match would remain removed/`INACTIVE` in chain state despite the overall transaction failing, while the corresponding taker-side commit (and any final balance settlement not shown in the retrieved excerpt) never executes.

### Impact Explanation
If the maker-side store mutations are not rolled back, a taker submitting a `MarketSellAssetContract` that matches more than `MAX_MATCH_NUM` (20) resting orders can cause up to 20 maker orders to be evicted from their owners' active order list and marked `INACTIVE` in that iteration, while the transaction as a whole fails. Affected maker orders would no longer be cancellable via `MarketCancelOrderActuator` (which requires `isActive()`) [6](#0-5) , and would be permanently locked out of the tradable order book without any of their remaining assets being credited back — a fund-lock/denial-of-service on affected market participants' orders, reachable purely through broadcasting a crafted `MarketSellAssetContract` transaction.

### Likelihood Explanation
Likelihood is low: it requires an attacker (or unlucky ordinary trader) to submit a sell order whose price matches more than 20 resting maker orders simultaneously, which requires either a thin/fragmented order book being deliberately seeded with many small maker orders at a matching price, or organic congestion. This is feasible for an attacker to engineer by first placing >20 small maker orders at the same price and then triggering a matching taker order.

### Recommendation
- Move the `matchOrderCount > MAX_MATCH_NUM` check before applying any state mutation for that iteration (i.e., check-then-act, not act-then-check), consistent with the report's recommendation to "move all pre-checks before the state transition."
- Alternatively, explicitly and atomically stage all maker-order state changes and only commit them once the entire match loop completes successfully, calling an explicit compensating "revert-to-previous-state" routine for any already-mutated maker orders if `ContractValidateException` is thrown mid-loop.
- Verify and, if necessary, fix the transaction-processing session lifecycle so that any `ContractExeException` thrown from `execute()` guarantees full rollback of all store writes performed during that `execute()` call, not just the writes that happen to be the actuator's final steps.

### Proof of Concept
1. Attacker (or colluding accounts) place 21 small maker `MarketSellAssetContract` orders selling token A for token B, all at the same matching price, so they land in the same `MarketOrderIdListCapsule` bucket returned by `pairPriceToOrderStore.getPriceKeysList(...)`.
2. A taker broadcasts a `MarketSellAssetContract` selling token B for token A with a quantity large enough to match all 21 maker orders in one call.
3. In `matchOrder()`, the loop calls `matchSingleOrder()` for makers 1–21; on the 21st match, `MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore)` has already been applied (removing the order from the maker's active list) for makers 1–21 before the `matchOrderCount > MAX_MATCH_NUM` check throws `ContractValidateException`.
4. `execute()` catches the exception, sets the transaction result to `FAILED`, and rethrows `ContractExeException`, skipping the final `orderStore.put(orderCapsule...)`/`accountStore.put(accountCapsule...)` calls for the taker.
5. Depending on the outer transaction session semantics (unverified in this analysis), the 21 maker orders may remain permanently removed from their owners' active order lists / marked `INACTIVE`, while the transaction itself is recorded as failed and no proceeds are settled — leaving maker orders stuck and unrecoverable.

  public static void updateOrderState(MarketOrderCapsule orderCapsule,
      State state, MarketAccountStore marketAccountStore) throws ItemNotFoundException {
    orderCapsule.setState(state);

    // remove from account order list
    if (state == State.INACTIVE || state == State.CANCELED) {
      MarketAccountOrderCapsule accountOrderCapsule = marketAccountStore
          .get(orderCapsule.getOwnerAddress().toByteArray());
      accountOrderCapsule.removeOrder(orderCapsule.getID());
      marketAccountStore.put(accountOrderCapsule.createDbKey(), accountOrderCapsule);
    }
  }
