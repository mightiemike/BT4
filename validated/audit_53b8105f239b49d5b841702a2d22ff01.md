## Analysis

The reported bug class is a **hardcoded/non-adjustable gas budget for an asynchronous callback**, where insufficient gas causes the callback to fail, and because the callback (VRF's `fulfillRandomWords`) is never retried, the failure becomes permanent and unrecoverable without an admin-controlled parameter.

The closest reachable analog in nearcore is the **NEAR Wallet Contract** (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`), which is the system contract deployed on eth-implicit accounts and driven by any unprivileged caller submitting an RLP-encoded Ethereum-style transaction via `rlp_execute`.

### Root cause

The contract hardcodes a fixed baseline gas budget for its own internal callbacks: [1](#0-0) 

`rlp_execute` sets `has_in_flight_tx = true` *before* returning the promise chain, and only the callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) reset it back to `false`, each running under the fixed `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) budget: [2](#0-1) [3](#0-2) 

Because NEAR discards all state mutations of a function call that fails (including out-of-gas failures), if the fixed 5 Tgas budget for any of these callbacks is ever insufficient for the code paths inside it (e.g., due to a future protocol change to base/action gas costs, as described in `docs/architecture/how/gas.md`), the callback receipt fails and `has_in_flight_tx` is never reset to `false`. There is no admin, owner, or any other method in the contract capable of resetting `has_in_flight_tx`; it is only ever set by `rlp_execute` and cleared inside the very callbacks whose failure is what needs to be recovered from. This is confirmed by the fact that `has_in_flight_tx` only appears in this one file with no external reset path.

This is a direct structural analog to the reported issue: a hardcoded gas amount for a callback that is not admin-adjustable, whose insufficiency (driven by external/protocol-level cost changes, exactly as the VRF report worries about EVM gas-price/opcode changes) permanently and irrecoverably halts the flow, since `rlp_execute` immediately rejects all future transactions while `has_in_flight_tx == true`.

### Title
Hardcoded, non-adjustable callback gas budgets in the Wallet Contract can permanently brick an eth-implicit account - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Wallet Contract deployed on every eth-implicit account uses hardcoded constants (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) as the gas budget for its own internal callback functions that are responsible for clearing the `has_in_flight_tx` guard flag. There is no way to change these constants without a full contract redeploy, and no method exists to reset `has_in_flight_tx` other than a successful callback execution.

### Finding Description
`rlp_execute` sets `has_in_flight_tx = true` and schedules a promise chain ending in one of the `*_callback` methods, each scheduled with a fixed, hardcoded static gas amount [4](#0-3) . If the callback's actual execution cost ever exceeds this hardcoded budget (for any reason — increased base action costs from a future protocol upgrade, larger-than-expected registrar/token responses, etc.), the callback receipt fails with an out-of-gas error. Per NEAR's execution model, state changes from a failed function call execution are never committed, so the `has_in_flight_tx = false` reset never takes effect, while the earlier `has_in_flight_tx = true` write (committed when the parent call returned successfully with a promise) remains persisted. All subsequent calls to `rlp_execute` on that account immediately short-circuit with the "transaction already in progress" error [5](#0-4) , and no other method in the contract can reset the flag.

### Impact Explanation
This produces a permanent, transaction-triggered halt of the wallet contract for the affected eth-implicit account: no further Ethereum-style transactions (transfers, function calls, key management) can ever be executed through it again, effectively freezing any funds/access controlled exclusively through that account's wallet-contract interface. This matches the "permanently frozen funds"/"transaction-triggered halt" acceptance criteria.

### Likelihood Explanation
Likelihood is low-to-medium: under current gas cost constants the 5 Tgas budget appears to have headroom, but it is a static, protocol-independent value not tied to (and not automatically adjusted by) the underlying `RuntimeConfig`/`ExtCostsConfig` gas cost parameters that nearcore itself allows to change across protocol versions (see `core/parameters/res/runtime_configs/*.yaml`). Any future increase in base/action gas costs, or an unexpectedly large registrar/token response, can push a callback over budget without requiring any special conditions.

### Recommendation
Do not hardcode a fixed absolute gas amount for the "return to safe state" callbacks. Instead, either (a) size the callback gas as a generous, config-driven multiple of the current base costs so it can be adjusted alongside `RuntimeConfig` changes without a full contract redeploy, or (b) add a permissionless recovery path that allows `has_in_flight_tx` to be cleared/unstuck if the expected callback receipt is provably no longer pending (e.g., via a timeout mechanism analogous to yield/resume timeouts), so a single stuck callback cannot permanently disable the account.

### Proof of Concept
1. An eth-implicit account owner submits a valid Ethereum-style transaction via `rlp_execute`, which passes validation and returns a promise chain ending in, e.g., `nep_141_storage_balance_callback` scheduled with `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` static gas; `has_in_flight_tx` is set to `true` and committed.
2. The scheduled callback's actual execution (deserializing the storage-balance response, building/chaining the follow-up promise) exceeds the hardcoded gas budget — this can be forced by a large or adversarial response, or naturally occurs after a protocol-level fee increase.
3. The callback receipt fails with an out-of-gas error; per NEAR's execution semantics, its state changes (including `self.has_in_flight_tx = false`) are discarded.
4. The account is left with `has_in_flight_tx == true` permanently in storage.
5. Any subsequent call to `rlp_execute` immediately returns `ExecuteResponse { success: false, error: Some("Error: transaction already in progress...") }`, and no method exists to clear the flag — the wallet contract for this account is permanently unusable.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
