### Title
Unhandled exception in `sanitizeHost` (via `atob`) crashes `redirectWithExitIframe` on attacker-supplied malformed-base64 `host` param - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` validates the `host` query parameter with a regex that only checks the base64 character set, not that the string length is a multiple of 4. A string whose length mod 4 equals 1 (e.g. `"a"`) passes the regex but causes `atob` (called inside `decodeHost`) to throw a `DOMException`/`TypeError` instead of gracefully returning `null`. Because `redirectWithExitIframe` (and `validateShopAndHostParams`, which runs earlier in the same request pipeline) calls `api.utils.sanitizeHost(host)` unguarded, this exception propagates out of the authentication path instead of the intended "return null / redirect" behavior.

### Finding Description
`sanitizeHost` in [1](#0-0)  tests the `host` value with `base64regex = /^[0-9a-zA-Z+/]+={0,2}$/`, which accepts any length string as long as characters are valid base64 characters (padding is optional in this regex). It then calls `decodeHost(sanitizedHost)`, which is a direct wrapper around `atob`: [2](#0-1) 

Per the WHATWG forgiving-base64 decode algorithm implemented by `atob`, if the (padding-stripped) input length modulo 4 equals 1, the call throws an `InvalidCharacterError`/`DOMException` rather than returning a value. A one-character string like `"a"` (or five characters like `"aaaaa"`) satisfies `base64regex` but has length mod 4 == 1, so `atob` throws. This throw happens *before* the `throwOnInvalid` check at line 85 is reached, so it is unconditional regardless of the `throwOnInvalid` argument — even calls that pass `false` (the default, used by `redirectWithExitIframe`) will still throw.

`redirectWithExitIframe` calls `api.utils.sanitizeHost(queryParams.get('host')!)` directly with no try/catch: [3](#0-2) 

The same unguarded call also exists earlier in the authentication pipeline in `validateShopAndHostParams`: [4](#0-3) 

In `authStrategyFactory`'s `authenticateAdmin`, all logic is wrapped in a try/catch, but it only special-cases `Response` instances — any other thrown error (such as this `DOMException`) is simply rethrown: [5](#0-4) 

So instead of the expected graceful redirect/`null`-host handling, the request handler throws an unhandled, non-`Response` exception, which surfaces as an unstyled 500 error / crash of the loader instead of the intended exit-iframe redirect.

### Impact Explanation
This is a Denial-of-Service against the authentication/exit-iframe handling path: any anonymous request carrying a `host` value that is valid base64 characters but has an invalid (mod-4 == 1) length will crash the handler instead of producing the intended redirect response. This matches Shopify's "DoS in an authentication handler" impact class. It does not by itself leak secrets or forge sessions; the impact is scoped to breaking the request/response flow for the targeted route.

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: the attacker only needs to send an unauthenticated GET request to any embedded-admin-protected route with `host=a` (or any base64-charset string whose length mod 4 is 1) and a syntactically valid `shop` param. No secrets, privileged access, or non-default configuration are required — `config.isEmbeddedApp` being true (the normal/default configuration for embedded apps) and lack of a session are enough to route through `validateShopAndHostParams`/`redirectWithExitIframe`.

### Recommendation
Wrap the `atob`/`decodeHost` call inside `sanitizeHost` in a try/catch and treat any decoding failure as an invalid host (return `null`, or throw `InvalidHostError` only if `throwOnInvalid` is true), consistent with the function's existing invalid-host handling. Additionally/optionally, tighten `base64regex` to require a length that is a proper multiple of 4 after padding.
