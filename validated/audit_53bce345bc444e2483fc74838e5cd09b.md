## Title
Receipts can bypass `max_receipt_size` validation and are silently size-clamped by congestion/bandwidth accounting, allowing outgoing-receipt buffers and state witnesses to exceed their designed byte budget - (`runtime/runtime/src/congestion_control.rs`)

### Summary
An unprivileged contract call can produce a `Receipt` whose serialized size exceeds the protocol's `max_receipt_size` hard limit, because the size check happens *before* the receipt is finalized (e.g. before `output_data_receivers` is appended, or for `value_return`-derived `Data` receipts whose size is checked only against `max_length_returned_data`, not `max_receipt_size`). Rather than rejecting such oversized receipts, the runtime's congestion/bandwidth accounting path (`ReceiptSinkV2::try_forward`) "pretends" the receipt is only `max_receipt_size` bytes for admission/bookkeeping purposes, while still forwarding/buffering the full oversized payload. This mirrors the curl CVE's root cause pattern: a size assumption baked into a fixed-capacity accounting/buffer structure is violated by attacker-supplied data, and the code works around the violation with a truncating "pretend" fix rather than actually enforcing the invariant.

### Finding Description
`validate_receipt` enforces `ReceiptSizeExceeded` only when `mode == ValidateReceiptMode::NewReceipt`, checking `borsh::object_length(receipt)` against `limit_config.max_receipt_size`: [1](#0-0) 

However, `ValidateReceiptMode::ExistingReceipt` explicitly tolerates receipts above the size limit "because there is a bug which allows to create receipts that are above the size limit" (tracked as near/nearcore#12606): [2](#0-1) 

The test suite documents two concrete unprivileged paths that create such oversized receipts: (1) a receipt validated at exactly `max_receipt_size`, but which subsequently has `output_data_receivers` appended by promise chaining, pushing it past the limit after validation already passed; and (2) `value_return` wrapping a large value into a `Data` receipt that is checked only against `max_length_returned_data`, not `max_receipt_size`: [3](#0-2) [4](#0-3) 

Instead of rejecting these oversized receipts downstream, `ReceiptSinkV2::try_forward` silently clamps the *accounted* size to `max_receipt_size` while still forwarding the full, larger receipt: [5](#0-4) 

The same clamp-instead-of-reject pattern is repeated in bandwidth request generation: [6](#0-5) 

This means every size-budgeted structure downstream — `own_congestion_info` byte accounting, `outgoing_receipts_usual_size_limit`/`outgoing_receipts_big_size_limit`, and ultimately the `ChunkStateWitness` size budget that is explicitly designed around `max_receipt_size` as a hard per-receipt cap — under-counts the true bytes it is carrying: [7](#0-6) [8](#0-7) 

### Impact Explanation
The entire state-witness size budget (~21 MiB, built from `max_receipt_size`, `outgoing_receipts_usual_size_limit`, `outgoing_receipts_big_size_limit`, etc.) assumes no single receipt exceeds `max_receipt_size`. Because a single unprivileged contract call can produce a receipt exceeding this cap while the runtime's own accounting believes it is within budget (clamped), a chunk producer can be induced to build chunks/witnesses whose *true* serialized size silently exceeds the limits the protocol relies on to bound `ChunkStateWitness` size, `outgoing_receipts` size, and cross-shard buffer/bandwidth accounting. This is a resource-accounting integrity break directly reachable from a single submitted transaction (deploy + call a contract that chains promises or calls `value_return` with a large value), not requiring any validator/peer/network privilege. Depending on how much cumulative oversize accrues, this can push real byte counts past `MAX_UNCOMPRESSED_STATE_WITNESS_SIZE`/`MAX_COMPRESSED_STATE_WITNESS_SIZE`, which are unconditional compile-time caps enforced elsewhere, creating a mismatch between what the producer's accounting "thinks" it produced and what honest validators actually receive/must process.

### Likelihood Explanation
This is not a hypothetical: the bug is already known, tracked upstream as near/nearcore#12606, and reproduced by existing tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`) which explicitly state the receipt "should be rejected, but currently isn't." Triggering it requires only deploying a standard test-style contract and calling it with attacker-chosen `args_size`/`value_size` parameters — fully within reach of any unprivileged transaction signer / contract caller.

### Recommendation
Enforce `max_receipt_size` validation on the fully-finalized receipt (after `output_data_receivers`/promise-chaining mutations, and for `value_return`-derived `Data` receipts) rather than only at an earlier construction stage, so that no receipt can ever leave `NewReceipt` validation above the limit. Once true enforcement is restored, remove the compensating "pretend it's `max_receipt_size`" clamps in `try_forward` and `generate_bandwidth_request` (or keep them only as defense-in-depth, not as the sole safeguard), and add regression tests asserting the true receipt size, not just the clamped accounting size, never exceeds `max_receipt_size` in any code path (promise return, value return, yield/resume).

### Proof of Concept
Already present in-repo as `test-loop-tests/src/tests/max_receipt_size.rs::test_max_receipt_size_promise_return` and `::test_max_receipt_size_value_return`, both of which deploy `near_test_contracts::rs_contract()` and drive it with attacker-controlled `args_size`/`value_size` to produce a receipt above `max_receipt_size` (4,194,304 bytes), confirming the receipt is accepted/forwarded instead of rejected with `ReceiptSizeExceeded`. **File:** docs/misc/state_witness_size_limits.md (L16-22)
```markdown
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
* `max_receipt_total_input_size - 4 MiB + 640 B`
  * Hard limit on the combined size of a receipt's resolved promise inputs (the `ReceivedData` referenced by its `input_data_ids`). Receipts which exceed it fail with `TotalPromiseInputSizeExceeded` without executing their actions.
  * These inputs are read before `per_receipt_storage_proof_size_limit` starts counting, so without this limit a single receipt could pull `max_number_input_data_dependencies * max_receipt_size` (128 * 4 MiB) into the witness.
  * The limit is `max_length_returned_data` (4 MiB) plus the worst-case per-input framing overhead (128 * 5 bytes), so 4 MiB of input data always fits no matter how it's split across data receipts.
```

```markdown
* `outgoing_receipts_usual_size_limit - 100 KiB`
  * Limit on the size of outgoing receipts to another shard. Needed to keep the size of `source_receipt_proofs` small.
  * On most block heights a shard isn't allowed to send receipts larger than 100 KiB to another shard.
* `outgoing_receipts_big_size_limit - 4.5 MiB`
  * On every block height there's one special "allowed shard" which is allowed to send larger receipts, up to 4.5 MiB in total.
  * A receiving shard will receive receipts from `num_shards - 1` shards using the usual limit and one shard using the big limit.

In total that gives 4 MiB + 500 KiB + 8MB + 4 MiB + 5*100 KiB + 4.5 MiB ~= 21 MiB of maximum witness size. Possibly a little more on missing chunks.
```
