### Title
RPC-API DoS via unbounded per-price-key linked-list traversal in `Wallet.getMarketOrderListByPair` - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getMarketOrderListByPair` walks maker order linked lists per price bucket via `MarketOrderIdListCapsule.getAllOrder`, issuing one sequential RocksDB `getUnchecked` per order node up to `MARKET_COUNT_LIMIT_MAX`. An attacker can create many self-funded maker orders at an identical price (same `market_pair_price_to_order` key) via `MarketSellAssetContract`, then repeatedly call the free, unauthenticated `GetMarketOrderListByPair` RPC/HTTP endpoint to force `MARKET_COUNT_LIMIT_MAX` sequential single-key gets per call.

### Finding Description
`getAllOrder` traverses the linked list one node at a time using `orderStore.getUnchecked(orderId)` then `makerOrderCapsule.getNextCapsule(orderStore)`, capped at `limit` (`MARKET_COUNT_LIMIT_MAX`): [1](#0-0) . `Wallet.getMarketOrderListByPair` calls this per price key up to `MARKET_COUNT_LIMIT_MAX` total orders, with no distinction between "hot" (many orders in one bucket) vs "cold" (few orders across many buckets) state: [2](#0-1) . Both the HTTP servlet (`GetMarketOrderListByPairServlet`) and the gRPC `getMarketOrderListByPair` entry points invoke this directly with no additional cost accounting — only a generic `RateLimiterServlet` rate limit and a `checkBodySize` guard, not a state-size-aware cost model: [3](#0-2) .

To build a large bucket, an attacker broadcasts many `MarketSellAssetContract` transactions with identical `sellTokenQuantity`/`buyTokenQuantity` ratios (same normalized price key), each accepted as long as `MAX_ACTIVE_ORDER_NUM` (100) per account isn't exceeded and the account has sufficient asset/TRX balance and pays `MarketSellFee` per order: [4](#0-3) . This per-account cap of 100 is not a global cap — the attacker can use multiple funded accounts (Sybil-style, still requiring real TRX/asset balance and fees per account) to accumulate many more orders into the same price-key bucket, since the linked list is keyed by `(sellTokenId, buyTokenId, price)`, not by account. This is a real cost-bounded but non-trivial precondition: it requires funding N accounts and paying N maker-order fees, whereas the read-side query is comparatively "free" (a servlet/RPC read, no fee or resource cost as it's a query, not a transaction) and can be repeated indefinitely, unbounded by economic cost.

### Impact Explanation
This matches the "DoS via RPC-API" bounty class: sustained I/O amplification against a full/solidity/PBFT node's RocksDB backing store, where a single cheap unauthenticated query forces up to `MARKET_COUNT_LIMIT_MAX` sequential single-key reads instead of a small number, scaling with attacker-created state rather than with query cost. It affects the read-path only (no state corruption, no consensus divergence, no asset loss), so impact is bounded to degraded node responsiveness/availability for this specific endpoint (and the http/grpc/solidity/PBFT wrappers around it), not chain-wide consensus failure.

### Likelihood Explanation
Feasibility requires: (1) paying `MarketSellFee` and providing real sell-token balance for each maker order created (bounded per account at 100 via `MAX_ACTIVE_ORDER_NUM`, but not capped chain-wide across accounts), and (2) the query endpoints being reachable, which they are by default for full/solidity/PBFT nodes without special auth. The attack is repeatable indefinitely on the read side once the bucket is built, since queries are free. The economic cost to build a large single-price bucket (potentially many accounts × maker fee) is the main limiting factor and is not analyzed here in exact TRX terms since `getMarketSellFee`/fee-calculation code paths were not directly retrieved in this session — this is a gap in verification.

### Recommendation
Bound per-query cost independent of attacker-controlled bucket size, e.g.: cap `getAllOrder` traversal cost by iterating with a strict wall-clock/IO budget, add pagination (return a cursor instead of materializing up to `MARKET_COUNT_LIMIT_MAX` per call), or maintain a maximum orders-per-price-key limit enforced in `MarketSellAssetActuator.validate()` (global, not just per-account) to prevent one price bucket from growing unbounded regardless of number of distinct funding accounts.

### Proof of Concept
Not fully reproducible from indexed context alone — exact fee values (`getMarketSellFee`) and `MARKET_COUNT_LIMIT_MAX`'s numeric value were not retrievable via available search tools in this session, so a precise cost/latency benchmark cannot be constructed here. A JUnit-style benchmark would follow the pattern already present in `MarketSellAssetActuatorTest.addOrder` (used to add many orders at the same price, as seen in `exceedMakerBuyOrderNumLimit`) combined with a timed call to `Wallet.getMarketOrderListByPair`, comparing latency for an empty pair vs. a pair with `MARKET_COUNT_LIMIT_MAX` orders at one price key: [5](#0-4) . Due to indexing limits, the full fee/config constants file (`common/src/main/java/org/tron/core/config/Parameter.java`) could not be retrieved in this session; starting a full Devin session with filesystem access would allow confirming exact `MARKET_COUNT_LIMIT_MAX` and fee constants and running the actual benchmark.

  public List<MarketOrderCapsule> getAllOrder(MarketOrderStore orderStore, long limit)
      throws ItemNotFoundException {

    List<MarketOrderCapsule> result = new ArrayList<>();

    long count = 0;
    byte[] orderId = this.getHead();
    if (!ByteArray.isEmpty(orderId)) {
      MarketOrderCapsule makerOrderCapsule = orderStore.getUnchecked(orderId);
      while (makerOrderCapsule != null) {
        result.add(makerOrderCapsule);
        makerOrderCapsule = makerOrderCapsule.getNextCapsule(orderStore);
        count++;
        if (count > limit) {
          break;
        }
      }
    }
    return result;
  }
