## Analysis Summary

The report's bug class — a party resetting a "last-update" timestamp via a normal, permitted action to indefinitely dodge a timeout-gated safety check — maps to a concrete analog in the Stacks signer chainstate logic that gates when a tenure is considered "timed out."

### Title
Sortition winner can indefinitely reset its own inactivity timer via rejected reorg proposals, permanently blocking the tenure fallback gate - (File: `stacks-signer/src/chainstate/mod.rs`, `stacks-signer/src/chainstate/v1.rs`, `stacks-signer/src/chainstate/v2.rs`)

### Summary
`SortitionState::is_timed_out` decides whether the currently-winning miner is "inactive," which is one of the two gates that must be satisfied before signers will accept a `TenureChange::Extended` from the *previous* miner [1](#0-0) . The elapsed-time comparison depends on `get_last_activity_time`, which is bumped every time the *same* winning miner submits a block proposal that conflicts with an already-accepted/pre-committed block in its own tenure [2](#0-1) . Because this activity bump happens even when the conflicting proposal is rejected, a stalling sortition winner can repeatedly submit throwaway, losing block proposals to keep resetting its own "last activity" clock and never actually let `elapsed > timeout` become true.

### Finding Description
`is_timed_out` (both the v1 and v2 chainstate implementations) treats `last_activity_time` (or, absent that, the burn-block-received time) as the anchor for the inactivity timeout: [3](#0-2) 

`last_activity_time` is written by `update_last_activity_time`, which `check_tenure_change_confirms_parent`/`check_latest_block_in_tenure` (in `chainstate/mod.rs`) calls whenever the *current tenure's own miner* submits a proposal that conflicts with a block the signer has already accepted or pre-committed, explicitly to give "the miner some extra buffer time" and because "the miner may just be slow": [4](#0-3) 

Crucially, only the actual sortition winner can trigger this: `check_proposal` in `chainstate/v2.rs` recovers the miner's public key from the block header and rejects any proposal whose signer does not match `current_miner_pkh` for that tenure_id [5](#0-4) . So this is not a spoofable, majority, or third-party attack — it is a single, unprivileged winning miner exploiting its own legitimate signing key.

By continuously sending self-conflicting/reorg block proposals (which are individually rejected, exactly as intended, but still count as "activity"), the winning miner can keep `last_activity_time` from ever going stale. This breaks the equality the report's bug class targets: "if inactive too long ⇒ timed out" never becomes true, no matter how long the miner has actually failed to produce a valid block, mirroring how `updateTPAndSL` resets `lastUpdateTime` to defeat `minAcceptanceDelay` in the reported contract.

The downstream consequence is documented directly in the operator docs: `block_proposal_timeout_ms` gates whether signers will invalidate the new winner (`InvalidatedBeforeFirstBlock`) and only after that invalidation will signers accept a tenure-extend from the *previous* miner: [6](#0-5) 

If `is_timed_out` never returns `true`, the previous miner's `TenureChange::Extended` is permanently rejected by signers, and the network cannot fall back away from a stalling winner.

### Impact Explanation
This is a minority-triggerable (single sortition winner, no collusion required) liveness/validation-divergence bug: it defeats a consensus-adjacent timeout check that signers rely on to agree on which miner is authorized to keep building, causing the network to stall behind an unproductive miner until the next sortition, i.e. a temporary tip/liveness disagreement bounded to that burn window. It does not directly cause a chain split, double payment, or an irreversible reorg, so it falls into the "High" bucket (minority-triggerable validation divergence / temporary tip disagreement) rather than "Critical."

### Likelihood Explanation
Any sortition winner can trigger this at will using only their own already-authorized signing key — no special privilege, no majority collusion, and no reliance on other nodes' misbehavior. The behavior is a straightforward consequence of the documented "extra buffer time" activity-counting logic in `check_tenure_change_confirms_parent`, making it easily and repeatably reachable.

### Recommendation
Separate "did the miner attempt *any* activity" from "did the miner make *forward progress*." Only bump `last_activity_time` for actions that increase confirmed chain height in the tenure (e.g., a newly globally-accepted block), not for proposals that conflict with or fail to exceed the already-accepted/pre-committed tip. Alternatively, cap the number of times a single miner's rejected/conflicting proposals can refresh `last_activity_time` within a tenure, so the inactivity clock cannot be reset indefinitely by an unproductive winner.

### Proof of Concept
1. Miner `M` wins the sortition for tenure `T` and never produces (or refuses to have signed) a real accepted block.
2. Signers receive an initial block/tenure-change and locally/pre-commit-accept some block `B0` in `T`.
3. `M` repeatedly submits new block proposals in `T` whose `chain_length` is `<=` `B0`'s chain length (i.e., proposals that conflict with `B0`).
4. Each such proposal is correctly rejected by `check_tenure_change_confirms_parent`/`check_latest_block_in_tenure`, but each call also invokes `update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())` [7](#0-6) .
5. As long as `M` submits such a proposal more often than `block_proposal_timeout` (default 120s per `mainnet-signer-conf.toml`), `is_timed_out` never returns `true` for tenure `T`.
6. Because the miner is never marked timed out, the previous miner's `TenureChange::Extended` continues to be rejected by signers, per the two-gate rule documented in `mainnet-signer-conf.toml` [6](#0-5) , stalling block production for the tenure indefinitely.

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)

# How long to wait for the current sortition winner to propose a block
# before the signer marks that miner as inactive.
#
# When a new sortition happens, the signer gives the winning miner this
# much time to propose a block. If no proposal arrives, the signer marks
# the winner as InvalidatedBeforeFirstBlock. This is one of two gates
# that must be satisfied before the signer will accept a tenure extend
# from the PREVIOUS miner (the other gate is `tenure_idle_timeout_secs`).
#
# WARNING: Interacts with miner's `tenure_extend_wait_timeout_ms` (default 120_000ms).
# The miner waits `tenure_extend_wait_timeout_ms` before attempting to extend.
#
# If miner's value < this value:
#   Miner extends BEFORE signer invalidates the new winner -> REJECTED
# If miner's value >= this value:
#   Signer invalidates new winner first, then accepts extend -> OK
#
