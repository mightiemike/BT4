## Title
`replay_on_archive` verification (`ensure_match_transaction_info`) omits state-checkpoint hash comparison, allowing an authenticated-history replay-verify to pass despite a divergent computed ledger state - (`File: types/src/transaction/mod.rs`)

### Summary
`db-tool`'s `replay_on_archive` verifier re-executes archived transactions locally and calls `TransactionOutput::ensure_match_transaction_info` to check the freshly-computed output against the `TransactionInfo`/write-set/events recorded in the authenticated backup/archive. That function checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** compare `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` — the fields that summarize the resulting Merkle state root at checkpoints.

### Finding Description
`TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  validates:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `CryptoHash::hash(self.write_set())` vs `txn_info.state_change_hash()`
- computed event root vs `txn_info.event_root_hash()`

It never reads or compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`. The code itself flags this with an explicit TODO comment: [2](#0-1) 

This function is the sole correctness oracle used by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions with `AptosVMBlockExecutor` and calls `executed_outputs[idx].ensure_match_transaction_info(...)` against the `expected_txn_info` pulled from the backup/archive: [3](#0-2) .

Because the write-set hash and event root are checked but the state-checkpoint hash is not, a replay whose write set and events happen to match byte-for-byte but whose resulting Merkle state (state root / hot-state root / position-state root) diverges from the archived value — e.g. due to a State Merkle Tree computation bug, hot-state or "trading native" root computation bug, or any divergence introduced only at the checkpoint-hash-aggregation step rather than in individual write-set contents — would be reported by `replay_on_archive` as a **successful, verified replay**, even though the authenticated state root at that version is wrong.

### Impact Explanation
`replay_on_archive` is one of the primary tools node operators/auditors use to confirm that a locally re-executed history matches the authenticated on-chain ledger (an integrity check against consensus/committed state). If the state-checkpoint-hash divergence is exactly the class of bug this tool is meant to catch (e.g., a state-root computation regression introduced by a change to checkpoint/hot-state root logic, or `position_state_checkpoint_hash` for the newer "trading native" state roots), this verifier would silently pass, giving false assurance that state matches when it does not. This directly weakens the proof/commit-integrity guarantee this tool exists to provide, matching the "authenticated API or state-view output bound to the wrong version/root" and "hard-fork-only divergence during commit, replay ... verification" impact categories. It does not itself corrupt live consensus state, but it is a genuine gap in the state-proof/replay verification invariant: a wrong root is silently accepted as "matching" during replay-verify.

### Likelihood Explanation
Likelihood of the underlying state-checkpoint-hash divergence (from a real state-root computation bug elsewhere) is not something this local code proves; only the incompleteness of the check itself is proven directly by reading the function body and its explicit TODO comment. The gap is “live” today: `replay_on_archive.rs` calls exactly this function with no supplementary checkpoint-hash comparison, so any future/latent divergence in state-root computation (hot-state, position-state, or plain state-checkpoint root) would go undetected by this specific tool right now, not merely once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash()`, and (when populated) `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, against the actual computed checkpoint roots for checkpoint transactions, and have `replay_on_archive`/`execute_and_verify` supply or compute the corresponding actual roots so mismatches are surfaced as replay failures rather than silently accepted.

### Proof of Concept
Not independently reproducible as a live-mainnet fund-loss/consensus-fork PoC from local code alone; the proof here is structural/code-level: the diff between the fields validated in `ensure_match_transaction_info` (status, gas, write-set hash, event root) versus the fields present on `TransactionInfo` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`, seen at [4](#0-3) ) and the fact that `replay_on_archive.rs` relies exclusively on this comparator to declare replay success/failure [5](#0-4) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
