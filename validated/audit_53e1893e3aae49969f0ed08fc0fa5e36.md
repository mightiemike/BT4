### Title
Silent `long` overflow (truncation) in market order matching quantity calculation via `BigInteger.longValue()` - ([File: chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java])

### Summary
`MarketUtils.multiplyAndDivide` is the core price/quantity calculation used by the on-chain order matching engine (`MarketSellAssetActuator`) to compute how many tokens a taker/maker receives when two orders match. Analogous to the Phoenix `adjusted_quote_lot_budget` bug — where a multiplication of quote lots by additional factors can exceed the representable range and abort — this java-tron function's overflow fallback path does not "abort" safely; it silently truncates the result via `BigInteger.longValue()` instead of `longValueExact()`, which is used everywhere else in the exchange code for the same kind of computation.

### Finding Description
`multiplyAndDivide` first tries the fast-path `multiplyExact`/`floorDiv` and, if that throws `ArithmeticException`, falls back to `BigInteger` arithmetic: [1](#0-0) 

The fallback computes `aBig.multiply(bBig).divide(cBig)` and then calls `.longValue()`. Unlike `ExchangeInjectActuator.doValidate()` and `ExchangeWithdrawActuator.doValidate()`, which use `.longValueExact()` (throwing `ArithmeticException` if the `BigInteger` result cannot fit in a `long`) [2](#0-1) 
, `MarketUtils.multiplyAndDivide` silently wraps/truncates when the mathematically correct quotient exceeds `Long.MAX_VALUE`/`Long.MIN_VALUE`, instead of raising an exception.

This function is called directly in the order-matching hot path, `MarketSellAssetActuator.matchSingleOrder`, to compute both `takerBuyTokenQuantityRemain` and `makerBuyTokenQuantityReceive`, i.e., the exact amounts of tokens/TRX that get credited to accounts on a successful match: [3](#0-2) [4](#0-3) [5](#0-4) 

These results directly drive account crediting via `addTrxOrToken`/`addAssetAmountV2` and balance decrements via `subtractExact`: [6](#0-5) 

Token/asset amounts and price-quantity fields (`sellTokenQuantity`, `buyTokenQuantity`) in the market contract are bounded only by `long` (up to `Long.MAX_VALUE`, i.e. ~9.2×10^18), and multiple orders can be chained/matched, so `a * b` computed as `BigInteger` can realistically exceed `Long.MAX_VALUE` even after dividing by `c`, when very large quantities/asset amounts (assets can have up to 10^18-scale precision, similar to the Phoenix `10^b` decimal factor in the report) are used in the order. In that scenario, `.longValue()` returns a truncated/wrapped (potentially negative) `long`, which becomes the settlement amount credited/debited in this transaction.

### Impact Explanation
If the true mathematical result of `multiplyAndDivide` exceeds `Long.MAX_VALUE`, the returned value silently wraps to an incorrect (potentially negative or arbitrarily different) `long`. Since this value feeds directly into on-chain account balance/asset accounting (`addExact`/`subtractExact` on both taker and maker accounts) inside a consensus-critical actuator, a wrapped value could cause: incorrect token amounts credited to one side of the trade (asset/TRX creation/destruction inconsistent with the actual matched order), or a negative credited amount, producing state inconsistent with correct accounting invariants and potentially divergence between nodes if not deterministically hit by all validators the same way (it is deterministic given identical inputs, so it would manifest as a consensus-consistent but economically incorrect settlement — effectively money created or destroyed from thin air in the trade). This matches the report's core concern: quote-lot-style multiplication overflow in a matching engine that must never silently produce wrong settlement values.

### Likelihood Explanation
Reaching the overflow requires large `sellTokenQuantity`/`buyTokenQuantity`/order-quantity values, which are permitted by the market/order contracts since they are plain `long` fields without any documented, code-enforced upper bound preventing this exact overflow path (unlike `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, which use `longValueExact()` and thus fail closed). I could not fully verify from index-available code whether `MarketSellAssetActuator.validate()` enforces additional quantity ceilings (e.g., an asset-amount cap) that would make this unreachable in practice — this needs confirmation by reading the full validate() method and related constants, which were not fully retrievable within the available search iterations.

### Recommendation
Change `MarketUtils.multiplyAndDivide`'s `BigInteger` fallback to use `longValueExact()` (consistent with `ExchangeInjectActuator`/`ExchangeWithdrawActuator`) so that an unrepresentable result throws `ArithmeticException` and is handled explicitly by the caller (rejecting/failing the match) rather than silently truncating. Additionally, review `MarketSellAssetActuator.validate()`/order-creation validation to ensure quantity bounds make the overflow condition unreachable in practice, and add explicit tests asserting that overflow-triggering quantities cause a rejected transaction rather than a wrapped result.

### Proof of Concept
Conceptual PoC (needs confirmation with live values from `validate()` bounds, not fully retrievable in this session):

Create a sell order with `sellTokenQuantity`/`buyTokenQuantity` chosen such that in `matchSingleOrder`, `a = takerSellRemainQuantity`, `b = makerSellQuantity`, `c = makerBuyQuantity` are large enough that `a*b` (computed via `BigInteger`) divided by `c` still exceeds `Long.MAX_VALUE`, while `a*b` alone also exceeds `Long.MAX_VALUE` (forcing the `multiplyExact` fast path to throw and fall into the `BigInteger` fallback).

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
