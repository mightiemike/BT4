### Title
Integer underflow in staleness check allows negative/out-of-range `payload.Timestamp` to bypass freshness validation - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` computes the staleness check using unsigned arithmetic: `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)`. Because `payload.Timestamp` is an attacker-suppliable `int64` field that is cast directly to `uint` without a sign/range check, a negative value wraps around to a huge unsigned number, which defeats the comparison and causes the "stale message" branch to be skipped regardless of the real freshness of the request.

### Finding Description
In [1](#0-0)  the handler unmarshals the attacker-controlled `webapicap.TriggerRequestPayload` from `body.Payload`, which contains the `Timestamp` field used later in freshness validation.

The only pre-check performed on `Timestamp` is a zero check at [2](#0-1) , which does not reject negative or otherwise invalid values.

The staleness comparison itself is: [3](#0-2) 

`uint(payload.Timestamp)` on a negative `int64` (e.g. `-1`) wraps via two's-complement conversion to a value near `math.MaxUint64` (or `math.MaxUint32` on 32-bit builds). Since the left-hand side (`uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`) is bounded by the current epoch time (a small value relative to the wrapped `uint(payload.Timestamp)`), the `>` comparison always evaluates to `false` for any negative timestamp. As a result the "stale message" rejection branch is never taken, and the request is unconditionally forwarded past the freshness gate to `common.ValidatedRequestFromMessage` and then to the DON members at [4](#0-3) .

No other check in this function (or, from what is indexed, upstream of it) validates that `payload.Timestamp` is a plausible non-negative, bounded Unix timestamp before it is used in this unsigned comparison. The freshness/anti-staleness invariant is therefore not actually enforced for any negative `Timestamp` value.

### Impact Explanation
The staleness gate is intended to bound the validity window of a gateway trigger message. By supplying a negative `Timestamp` in an otherwise validly-formed and validly-signed `TriggerRequestPayload`, the sender of the message can cause the gateway to treat the message as always "fresh," fully bypassing the intended freshness/replay-window invariant. This weakens the binding-freshness guarantee relied on to reject stale or delayed workflow trigger requests, and any downstream logic (e.g., workflow engines, telemetry, or rate/ordering assumptions) that relies on `Timestamp` being validated non-negative and within a bounded age window can be fed an inconsistent or bogus timestamp value that was never actually checked.

### Likelihood Explanation
The flaw is trivially reachable: any party able to construct and sign a `TriggerRequestPayload` (the normal path for calling `HandleLegacyUserMessage`) can simply set `Timestamp` to `-1` or any negative `int64`. No special privilege beyond normal ability to submit a gateway web API trigger message is required, and the bypass is 100% deterministic (not probabilistic), making it fully repeatable.

### Recommendation
Validate `payload.Timestamp` is non-negative (and within a sane upper bound) immediately after unmarshalling, rejecting it with `UserMessageParseError` alongside the existing `== 0` check. Additionally, rewrite the staleness comparison using signed arithmetic (or `time.Unix(payload.Timestamp, 0)` compared via `time.Time` subtraction) instead of mixing `uint` subtraction with a cast from a signed field, e.g.:
```go
now := time.Now().Unix()
if payload.Timestamp <= 0 || now-int64(h.config.MaxAllowedMessageAgeSec) > payload.Timestamp {
    // stale/invalid message
}
```
This removes both the negative-timestamp wraparound and any theoretical underflow when `MaxAllowedMessageAgeSec` exceeds `now`.

### Proof of Concept
Add a unit test to `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `TriggerRequestPayload` with `Timestamp = -1` (or `math.MinInt64`), correctly signed/formatted so it passes `common.ValidatedRequestFromMessage`.
2. Configure `h.config.MaxAllowedMessageAgeSec` to a typical small value (e.g., 300).
3. Call `HandleLegacyUserMessage` and assert that the callback receives a `"stale message"`/`HandlerError` response — the test should demonstrate that, with the current code, no such rejection occurs and the request is instead forwarded to `don.SendToNode`.
4. As a differential oracle, compute expected staleness using `big.Int` (or signed 128-bit) arithmetic: `expectedStale := now - int64(MaxAllowedMessageAgeSec) > payload.Timestamp`, and fuzz `payload.Timestamp` across `{0, -1, math.MinInt64, math.MaxInt64}` combined with several `MaxAllowedMessageAgeSec` values, asserting the handler's actual accept/reject decision matches `expectedStale` in every case.

			),

	}
