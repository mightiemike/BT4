## Finding

### Title
Exchange Inject/Withdraw actuators allow zero‑fee, atomic value extraction via proportional‑ratio rounding - (`File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The yAxis report describes a vault that treats all deposited assets as interchangeable at 1:1 value, letting a user deposit one asset and withdraw a different one in the same transaction, paying only the (near-zero) withdrawal fee as a "swap fee." The `Exchange*` actuators in java-tron implement a similar two‑asset pool (TRX/TRC10 "Bancor" exchange) where `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counterpart token amount purely from the current pool ratio, charge `calcFee() == 0`, and impose no restriction preventing inject+withdraw (or withdraw+inject) from being combined in one transaction/block. This creates the same class of "swap at parity, at essentially zero fee" primitive, and the integer rounding direction is asymmetric between the two operations, allowing repeated cycles to skew the pool balance in the attacker's favor at no cost.

### Finding Description
`ExchangeInjectActuator.execute()` computes the amount of the paired token required using floor-rounded integer division of the current pool ratio: [1](#0-0) 

`ExchangeWithdrawActuator.execute()` performs the symmetric operation (also floor-rounded via `BigInteger.divide`) to pay out the counterpart token on withdrawal: [2](#0-1) 

Both actuators charge no protocol fee: [3](#0-2) 

Because `calcFee()` returns `0` for both `ExchangeInjectContract` and `ExchangeWithdrawContract`, and because there is no restriction preventing an account from issuing an inject followed by a withdraw (or vice versa) in the same transaction/block against the same `ExchangeCapsule`, an attacker who is the pool creator (both actuators require `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`, see `ExchangeWithdrawActuator.java:181-183`) can repeatedly inject then withdraw at the current ratio. Because the injected "another token" amount is rounded down (`floorDiv`) while the pool balances are mutated using the exact same ratio calculation on both legs, and because the true Bancor curve is never invoked for inject/withdraw (only `ExchangeTransactionActuator` uses the bonding-curve `ExchangeProcessor`/`SafeExchangeProcessor`), the linear ratio math treats the pool as if both tokens have identical marginal value with no slippage or fee — mirroring the "assets treated at parity, fee ≈ 0" condition described in the report. Repeated inject/withdraw cycles let the pool creator extract residual value from rounding without paying any fee, and since there's no oracle or fee floor, this can be repeated atomically to drain value, especially if attacker also participates as a counterparty via `ExchangeTransactionActuator` in the same block to arbitrage the skewed ratio at no cost.

### Impact Explanation
This impacts token accounting inside `ExchangeCapsule`-backed pools (TRX/TRC10 pairs). Because `calcFee()==0` for inject/withdraw, and the ratio-based (parity-like) computation is reused for both operations without any anti-manipulation delay or minimum fee, a malicious pool creator can repeatedly cycle inject/withdraw to accumulate rounding-favorable outcomes, or combine inject/withdraw with `ExchangeTransactionActuator` swaps in the same block to extract value from other traders interacting with the pool at a skewed rate. This is an accounting/economic exploit rather than node RCE, but it directly corrupts the intended value invariant of the on-chain exchange feature.

### Likelihood Explanation
Likelihood is moderate: the attacker must be the exchange's creator address to call inject/withdraw (`ExchangeInjectActuator.java:175-177`, `ExchangeWithdrawActuator.java:181-183`), so this is limited to self-owned pools, but pool creators routinely interact with their own exchanges, and nothing prevents them from bundling inject/withdraw/transaction calls within one transaction group or block for zero cost, repeatedly, to bias the ratio prior to third-party swaps via `ExchangeTransactionActuator`.

### Recommendation
- Apply a non-zero fee (or a cooldown) to `ExchangeInjectContract`/`ExchangeWithdrawContract` similar to the report's suggestion of a mandatory non-zero withdrawal fee.
- Prevent inject and withdraw (and swap) operations by the same account against the same exchange within the same block/transaction group.
- Ensure inject/withdraw rounding is symmetric and doesn't allow value leakage across repeated cycles (e.g., round in the protocol's favor consistently, or require exact divisibility as already partially enforced in `ExchangeWithdrawActuator`'s "Not precise enough" check, and add the same precision check to `ExchangeInjectActuator`).

### Proof of Concept
1. Attacker creates an `Exchange` pool (TRX/TRC10) as its `creatorAddress`.
2. In the same block/transaction batch, attacker calls `ExchangeInjectActuator` with a `tokenQuant` chosen so the floor-rounded `anotherTokenQuant` favors the attacker (see `ExchangeInjectActuator.java:71-83`), paying `calcFee()==0`.
3. Attacker immediately calls `ExchangeWithdrawActuator` to reverse the position at the now-updated ratio (`ExchangeWithdrawActuator.java:74-89`), again paying `calcFee()==0`.
4. Repeating this cycle nets the attacker a rounding-favorable balance shift in the pool with no fee paid, degrading the pool's token backing ratio available to genuine `ExchangeTransactionActuator` counterparties.
