### Title
Unrecoverable Go error inside `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` can be triggered by attacker-controlled inbound data to atomically roll back a finalized ballot, permanently blocking finalization of a specific cross-chain deposit — ([File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go])

### Summary
The external ERC777 report describes a pattern where an attacker-controlled callback causes a state-changing operation to revert deterministically, permanently blocking a downstream protocol action (liquidation) that depends on that operation succeeding. The Push Chain analog is in the inbound-execution path: `VoteInbound` records a validator's finalizing vote in a nested `CacheContext` and explicitly `commit()`s it [1](#0-0) , intending that the vote survive even if later execution steps fail. However, `ExecuteInbound` and its sub-handlers can still return a raw, unrecovered Go `error` (e.g. from `types.ParseCAIP2`) which bubbles all the way back to `VoteInbound`'s final `return err` [2](#0-1) . Because Cosmos SDK routes and commits each `Msg` inside its own per-message `CacheMultiStore`, a non-nil error returned from the whole `MsgVoteInbound` handler discards **all** state writes made during that message — including the already-`commit()`-ed vote and the newly created `UniversalTx` — not just the failing execution step.

### Finding Description
`VoteInbound` deliberately isolates the ballot-vote write from later execution failures via a nested cache context that is committed *before* execution begins [3](#0-2) . The design intent (per the file's own comments) is that "a `UniversalTx` is always created on-chain regardless of whether the inbound passes execution validation" [4](#0-3) , and most failure paths are indeed captured into a `FAILED` `PCTx` instead of being propagated as Go errors — see `depositPRC20`/`CallPRC20Deposit` failures in `ExecuteInboundFunds` [5](#0-4)  and in `ExecuteInboundFundsAndPayload` [6](#0-5) .

However, `ExecuteInboundFundsAndPayload` contains at least one code path that does **not** follow this containment pattern: parsing the inbound's `SourceChain` via `types.ParseCAIP2` returns directly out of the function on error, without being captured into a `PCTx`:
```go
chainNamespace, chainId, err := types.ParseCAIP2(utx.InboundTx.SourceChain)
if err != nil {
    return fmt.Errorf("invalid SourceChain: %w", err)
}
``` [7](#0-6) 

`ValidateForExecution`, which runs immediately before `ExecuteInbound` is dispatched, only checks amount, asset address, payload shape, and recipient — it never re-validates that `SourceChain` is a `ParseCAIP2`-parseable CAIP-2 string [8](#0-7) . The earlier `ValidateBasic()` gate used to accept the vote only requires the string to contain a `":"` [9](#0-8) . This leaves a gap: a `SourceChain` value that satisfies "contains a colon" but is not a well-formed CAIP-2 reference that `ParseCAIP2` can decode (e.g. malformed/oversized numeric reference, unsupported namespace formatting) will pass `ValidateBasic` and `ValidateForExecution`, reach `ExecuteInboundFundsAndPayload`, and trigger the raw, unwrapped error return shown above.

Because this error is not swallowed into a `PCTx`, it propagates through `ExecuteInbound` → `VoteInbound`'s final `if err := k.ExecuteInbound(ctx, utx); err != nil { return err }` [10](#0-9) , causing the entire `MsgVoteInbound` message handler to return an error. Under standard Cosmos SDK message dispatch, each `Msg` executes against its own `CacheMultiStore`; a returned error causes the SDK to discard **that message's entire write-set** rather than persisting the parts already written. This means the earlier `commit()` of the finalizing vote (intended to be resilient to downstream failures) is itself inside that same discarded write-set, along with the `CreateUniversalTx` call that had already run [11](#0-10) .

### Impact Explanation
For any `Inbound` whose `SourceChain` is crafted to pass the loose `ValidateBasic` check but fail `ParseCAIP2`, the finalizing validator's vote transaction always errors out and none of its state changes — including the vote itself — are persisted. Because the ballot's vote count never actually advances on-chain (the write is rolled back every time), and the same malformed `SourceChain` will fail identically on every retry, the ballot for that specific source-chain event can never reach a persisted `PASSED`/finalized state, and no `UniversalTx` (success, failure-with-revert, or otherwise) is ever durably recorded for it. This is the direct analog of "blocking liquidation": the user's real deposit on the source-chain gateway is never processed to completion on Push Chain — no PRC20 mint, no revert-outbound is ever created — leaving the bridged funds permanently unresolvable through the on-chain flow. This falls under "permanent freezing of user funds" and "denial of service ... reachable without privileged control," since an ordinary external actor fully controls the `SourceChain` string embedded in a real cross-chain event that honest Universal Validators will faithfully observe and vote on.

### Likelihood Explanation
The trigger only requires an attacker to originate (or otherwise get honest UVs to observe) a gateway event whose chain identifier is malformed in a way that is CAIP-2-shaped enough to pass the minimal `ValidateBasic` gate but not `ParseCAIP2`-parseable. Whether this is trivially reachable depends on exactly how permissive `ParseCAIP2` vs. `ValidateBasic` are — I was not able to fully inspect `x/uexecutor/types/caip2.go`'s `ParseCAIP2` implementation within the available context to confirm the precise malformed-string conditions that trigger a parse failure while still satisfying `ValidateBasic`. This is a meaningful open question that should be resolved by reading `x/uexecutor/types/caip2.go` directly. Likewise, I could not verify from the indexed context whether this specific Cosmos SDK / cosmos-evm fork branches `CacheMultiStore` strictly per-message (standard behavior) or per-transaction in this codebase's `runTx`/`msgServiceRouter` wiring — this assumption underlies the "vote gets rolled back" mechanism and should be confirmed against the app's baseapp configuration before treating this as fully proven.

### Recommendation
- Wrap the `ParseCAIP2` failure (and any other raw `return err`/`return fmt.Errorf` inside `ExecuteInboundFundsAndPayload`, `ExecuteInboundGasAndPayload`, and sibling execution functions) into the existing `FAILED`-`PCTx` + revert-outbound containment pattern instead of propagating a bare Go error out of `ExecuteInbound`.
- Alternatively/additionally, validate that `SourceChain` is fully `ParseCAIP2`-parseable inside `ValidateForExecution` (not just `ValidateBasic`), so malformed-but-colon-containing chain identifiers are caught and routed to `handleFailedInboundValidation` before `ExecuteInbound` is ever dispatched.
- Audit all call sites in the inbound-execution family (`execute_inbound_funds.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`) for any other `return err` that isn't first captured into a `PCTx`, since each such site has the same rollback-the-vote failure mode.
- Confirm the per-message vs. per-transaction `CacheMultiStore` semantics in this fork's `runMsgs`/`msgServiceRouter`, and if per-message write discard-on-error is indeed happening, consider persisting the ballot vote via a fully independent store commit (not nested inside the same message's cache) so a downstream execution bug can never un-vote a validator.

### Proof of Concept
1. An attacker triggers (or an honest source-chain event naturally contains) a gateway deposit whose chain reference, when relayed by Universal Validators into `Inbound.SourceChain`, is CAIP-2-shaped (contains `:`) but fails `ParseCAIP2` (exact malformed-string requirements need confirmation from `x/uexecutor/types/caip2.go`).
2. Honest UVs observe the real deposit and submit `MsgVoteInbound` with this `Inbound`, e.g. `TxType_FUNDS_AND_PAYLOAD`.
3. `ValidateBasic()` accepts it (colon present); the first two UV votes are recorded normally (ballot not yet finalized, so `ExecuteInbound` is never reached and nothing errors).
4. The third (quorum-reaching) UV's `MsgVoteInbound` call proceeds through `VoteOnInboundBallot` → `isFinalized = true`, `commit()`s the vote into the message's cache store, creates the `UniversalTx`, passes `ValidateForExecution` (which doesn't check `ParseCAIP2`), and dispatches to `ExecuteInboundFundsAndPayload`, which immediately fails at `types.ParseCAIP2(utx.InboundTx.SourceChain)` and returns a raw error.
5. `ExecuteInbound` and `VoteInbound` propagate this error out of the `MsgVoteInbound` handler, causing the SDK to discard the entire message's write-set — including the finalizing vote and the `UniversalTx` record.
6. The third UV's vote never lands on-chain; the ballot remains one vote short of quorum forever (any resubmission fails identically), and the underlying source-chain deposit is never reflected on Push Chain in any resolvable state (no mint, no revert). This step requires validating the actual SDK per-message caching behavior in this repo's `app.go`/baseapp configuration to fully confirm the rollback semantics described.

// ValidateForExecution checks fields that are required for actual execution of the inbound.
// Called after ballot finalization, before ExecuteInbound. Failures here produce a failed
// PCTx and (for non-isCEA) a revert outbound, rather than dropping the vote.
func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}
