### Title
DoS amplification via free, unauthenticated `EstimateEnergy` RPC triggering repeated full VM re-executions per request - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
The external report's bug class is: an unprivileged, cheap (or in this case, essentially free) client request causes the node/backend service to perform disproportionately expensive work, repeatable at will with no cap, enabling low-cost DoS. In java-tron, `Wallet.estimateEnergy` exposed via the `EstimateEnergy` gRPC/HTTP endpoint exhibits the same amplification pattern: a single incoming request triggers a whole binary-search loop of full `triggerConstantContract`/VM executions, and this endpoint carries no TRX fee and no dedicated per-endpoint rate limit by default.

### Finding Description
`Wallet.estimateEnergy` performs a binary search over the fee-limit space to determine the energy required by a contract call. Each iteration of the search calls `cleanContextAndTriggerConstantContract`, which re-runs the entire smart contract execution through `VMActuator`/`callConstantContract`: [1](#0-0) 

Before the binary search even begins, the code runs a first full execution and a "two-times" probing execution, each individually wrapped in a `while(true)` retry loop that re-executes the contract every time an `OutOfTimeException` is thrown, up to `estimateEnergyMaxRetry` retries per step: [2](#0-1) 

Each of these re-executions calls `callConstantContract`, which constructs a fresh `TransactionContext`, instantiates a new `VMActuator`, and fully executes the contract bytecode against chain state: [3](#0-2) 

This endpoint is reachable anonymously over gRPC (`EstimateEnergy` RPC) and HTTP (`/wallet/estimateenergy` via `EstimateEnergyServlet`), and unlike a broadcast transaction it consumes **no TRX fee at all** — the "trade" (contract execution) is never committed on-chain, so there is zero cost to the caller, unlike the $0.045 govFee in the original report: [4](#0-3) [5](#0-4) 

The node-level rate limiting configuration ships with all per-method limits commented out by default; only the generic global QPS ceilings apply (`global.qps = 50000`, `global.ip.qps = 10000`, `global.api.qps = 1000` fallback), meaning `EstimateEnergy` has no bespoke throttle tuned to its actual per-call cost: [6](#0-5) 

Because a single client request can be crafted (via `TriggerSmartContract.data`) to call a contract function with an expensive loop that runs close to the block energy/time limit, each of the O(log₂(maxFeeLimit)) binary-search steps — plus retries — becomes a maximal-cost VM execution. This produces a large per-request amplification factor of real CPU work for a single, free, generic-rate-limited API call.

### Impact Explanation
Repeatedly invoking `EstimateEnergy` (or the JSON-RPC `eth_estimateGas`, which routes to the same code path) with a heavy contract call can consume disproportionate CPU/VM execution time on the queried node relative to the single request sent, at zero on-chain cost to the attacker. Under the default `global.api.qps = 1000` ceiling (with no per-method throttle), this can be scaled by hitting the endpoint concurrently, degrading responsiveness for legitimate `TriggerConstantContract`/`EstimateEnergy`/JSON-RPC consumers on that node — mirroring the "bog down backend service via cheap repeated requests" DoS class from the report, but reachable without spending anything.

### Likelihood Explanation
High for any node that exposes the HTTP/gRPC/JSON-RPC surfaces with `estimateEnergy`/`supportConstant` enabled (a common node configuration for wallets/dApp backends), since no per-method rate limiter is enabled by default and the endpoint is fully anonymous — no signature, no account balance, and no fee are required to invoke it.

### Recommendation
- Add a dedicated, conservative per-method/per-IP rate limit for `EstimateEnergy`/`TriggerConstantContract`/`eth_estimateGas` in `reference.conf` rather than relying on the generic global fallback.
- Cap total VM execution work per request explicitly (bound total binary-search iterations × execution time, not just per-call `OutOfTimeException` timeouts).
- Consider requiring a minimal computational/PoW-like cost or session-based quota for constant-call estimation on public-facing nodes.

### Proof of Concept
1. Deploy (or find) a contract with a function that executes a loop consuming close to the max single-execution energy/time budget.
2. Send repeated `EstimateEnergy` requests (gRPC `Wallet/EstimateEnergy` or HTTP `/wallet/estimateenergy`) targeting that function, from many source IPs (to stay under `global.ip.qps`) up to the `global.qps`/`global.api.qps` ceiling.
3. Each request triggers the full binary-search sequence in `Wallet.estimateEnergy` (initial run + probe + up to `log2(maxFeeLimit/lowEstimate)` refinement runs, each potentially retried `estimateEnergyMaxRetry` times on timeout), multiplying a single free request into dozens of full VM executions, degrading node performance for other API consumers with no TRX ever spent by the attacker.

  public Transaction callConstantContract(TransactionCapsule trxCap,
      Builder builder, Return.Builder retBuilder, boolean isEstimating)
      throws ContractValidateException, ContractExeException, HeaderNotFound, VMIllegalException {

    if (!Args.getInstance().isSupportConstant()) {
      throw new ContractValidateException("this node does not support constant");
    }

    Block headBlock;
    List<BlockCapsule> blockCapsuleList = chainBaseManager.getBlockStore()
        .getBlockByLatestNum(1);
    if (CollectionUtils.isEmpty(blockCapsuleList)) {
      throw new HeaderNotFound("latest block not found");
    } else {
      headBlock = blockCapsuleList.get(0).getInstance();
    }

    BlockCapsule headBlockCapsule = new BlockCapsule(headBlock);
    TransactionContext context = new TransactionContext(headBlockCapsule, trxCap,
        StoreFactory.getInstance(), true, false);
    VMActuator vmActuator = new VMActuator(true);

    try {
      vmActuator.validate(context);
      vmActuator.execute(context);
    } finally {
      // constant call runs on a pooled RPC worker; drop its thread-local VM config view so it
      // can never leak into a later (block/broadcast) execution on the same thread.
      VMConfig.clearLocalSnapshot();
    }

        logger.warn(CONTRACT_VALIDATE_EXCEPTION, e.getMessage());
      } catch (RuntimeException e) {
        retBuilder.setResult(false).setCode(response_code.CONTRACT_EXE_ERROR)
            .setMessage(ByteString.copyFromUtf8(e.getClass() + " : " + e.getMessage()));

      } catch (Exception e) {
        retBuilder.setResult(false).setCode(response_code.OTHER_ERROR)

        estimateBuilder.setResult(retBuilder);
        responseObserver.onNext(estimateBuilder.build());
