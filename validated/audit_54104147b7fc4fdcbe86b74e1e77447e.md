## Analysis

I found a mechanism structurally analogous to the Elfi bug: a user pre-pays a fee for an action (an L1→L2 message / stop order), and the sequencer can permanently mark that action as "consumed"/finalized — outside of the user-controlled cancel/refund path — even when the corresponding on-chain effect never actually took place, causing irrecoverable loss of the pre-paid fee.

In `crates/apollo_batcher/src/block_builder.rs`, `collect_execution_results_and_stream_txs` unconditionally inserts **every** L1-handler transaction hash into `execution_data.consumed_l1_handler_tx_hashes` *before* looking at whether execution succeeded, reverted, or hard-failed: [1](#0-0) 

That set is only excluded from being treated as "consumed" if the tx hash later also lands in `rejected_tx_hashes` (i.e., a full `Err` from the executor, filtered out in `commit_proposal_and_block` via `rejected_l1_handler_tx_hashes`): [2](#0-1) 

But a **Cairo-level revert** of an `L1Handler` transaction (as opposed to a low-level executor `Err`) is *not* rejected — it returns `Ok(...)` with `revert_error: Some(...)` from `execute_raw`, per `crates/blockifier/src/transaction/l1_handler_transaction.rs`: [3](#0-2) 

A reverted L1Handler tx therefore still ends up in the `Ok(...)` branch of `collect_execution_results_and_stream_txs`, is still inserted into `consumed_l1_handler_tx_hashes`, and is committed to the L1 events provider as "consumed" (`TxMgr`: Pending → Committed) via `commit_block`: [4](#0-3) 

This mirrors the Elfi pattern exactly: the *primary* action (block building / L1-message inclusion) triggers, as a side effect, the removal of the pending item from the state that would otherwise let the affected party recover their prepaid value — here, the L1 sender's `paid_fee_on_l1` (the ETH value attached to `sendMessageToL2` on L1). Once the sequencer reports the message hash as "consumed" to the L1 events provider/L1 core contract bookkeeping, the sender can no longer use the L1-side `startL1ToL2MessageCancellation` / `cancelL1ToL2Message` flow to reclaim the fee they paid on L1, because that flow is only available while the message is *not yet consumed*. Yet the L2 receipt for a reverted L1Handler always carries `fee: Fee(0)` and no state changes are actually committed (`execution_state.abort()`): [5](#0-4) 

So the intended action never happened, no L2-side value was produced, but the message is nonetheless marked "consumed" — permanently and irrecoverably burning the fee the sender paid on L1, exactly as the Elfi order's execution fee was burned by an implicit, non-refunding cancellation.

Note on confidence: I could not fully trace the exact semantics of the L1 provider's `ConsumedOnL1`/`CancelledOnL2` states in `apollo_l1_events` (e.g., whether a later on-L1 cancellation is still technically possible after a reverted-but-"consumed" L2 tx, or whether the core contract's own consumption check is independent of this batcher-side bookkeeping). This ambiguity in the L1↔L2 message lifecycle interaction is the main residual uncertainty in this analog.

### Title
Reverted L1-Handler transactions are marked "consumed" alongside successful ones, permanently forfeiting the sender's `paid_fee_on_l1` — ([File: crates/apollo_batcher/src/block_builder.rs])

### Summary
`collect_execution_results_and_stream_txs` inserts an L1Handler transaction's hash into `consumed_l1_handler_tx_hashes` for every `Ok(...)` execution result, regardless of whether the transaction actually reverted. Because a Cairo-level revert of an `L1Handler` transaction returns `Ok(TransactionExecutionInfo{revert_error: Some(_), receipt.fee: Fee(0), ...})` rather than an `Err`, reverted L1-to-L2 messages are treated identically to successfully-executed ones for consumption-tracking purposes.

### Finding Description
In `crates/blockifier/src/transaction/l1_handler_transaction.rs::execute_raw`, both the success path and every failure path (execution error, post-execution resource-bound violation) return `Ok(TransactionExecutionInfo)`; the only structural difference is whether `revert_error` is `Some`. In `crates/apollo_batcher/src/block_builder.rs::collect_execution_results_and_stream_txs`, the tx hash is added to `execution_data.consumed_l1_handler_tx_hashes` unconditionally for any `InternalConsensusTransaction::L1Handler`, *before* the `match result` that distinguishes success from `Err`. A revert (`Ok` with `revert_error: Some`) only logs a warning and otherwise proceeds through the same "accepted" path as a successful transaction. Consequently, the transaction hash is reported to the L1 events provider as consumed in `commit_proposal_and_block` (`self.l1_events_provider_client.commit_block(consumed_l1_handler_tx_hashes, ...)`), transitioning the message from Pending to Committed in the transaction manager. The user's L1-side value (`paid_fee_on_l1`), which is analogous to the "execution fee" escrowed for the stop order in the Elfi report, is never refunded — the L2 receipt explicitly zeroes the fee for reverted/aborted L1Handler executions, and no compensating mechanism credits the sender.

### Impact Explanation
Any L1 sender whose `L1Handler` message reverts on L2 (due to a bug in the target contract's `@l1_handler`, an out-of-resource condition, or a state mismatch) permanently loses the fee they attached on L1 when calling `sendMessageToL2`, with no way to cancel/reclaim it once the message is reported "consumed" to L1-facing bookkeeping. This is a direct, unauthorized-loss-of-funds scenario reachable by any L1 contract/user sending a message that a target L2 contract might revert on — an outcome outside the sender's control once the L2 execution logic causes a revert.

### Likelihood Explanation
High: any contract author can cause their own `@l1_handler` entrypoint to revert under adversarial or edge-case inputs (reentrancy guards, insufficient balance checks, assertion failures), and any L1 sender relying on that entrypoint is exposed. No special privilege is required — a single L1→L2 message submission, followed by a triggerable revert condition in the target contract, is sufficient.

### Recommendation
Distinguish reverted L1Handler transactions from successfully executed ones when populating `consumed_l1_handler_tx_hashes` (or in the downstream `commit_block` call to the L1 events provider), so reverted messages are treated the same as rejected ones — i.e., excluded from consumption, allowing the sender to still cancel the message and reclaim their L1 fee via the core contract's cancellation flow — unless the protocol explicitly intends reverted L1Handler executions to permanently consume the L1 fee (in which case this should be a documented, audited design decision, not an implicit side effect of shared code paths between success/revert).

### Proof of Concept
1. An L1 contract calls the Starknet core contract's `sendMessageToL2`, attaching a fee (`paid_fee_on_l1`) and targeting an L2 contract's `@l1_handler` entrypoint.
2. The sequencer picks up the message and builds an `L1HandlerTransaction`; execution reaches a `panic`/`assert` inside the target entrypoint (or the receipt's gas exceeds `l1_handler_max_amount_bounds`), causing `execute_raw` in `crates/blockifier/src/transaction/l1_handler_transaction.rs` to return `Ok(TransactionExecutionInfo{revert_error: Some(_), receipt.fee: Fee(0), ..})`.
3. In `crates/apollo_batcher/src/block_builder.rs::collect_execution_results_and_stream_txs`, the tx hash is unconditionally added to `consumed_l1_handler_tx_hashes` before the `match result` branch is evaluated; the `Ok(...)` branch is taken (only a warning is logged) and the tx hash never enters `rejected_tx_hashes`.
4. On block commit, `crates/apollo_batcher/src/batcher.rs::commit_proposal_and_block` reports this hash via `l1_events_provider_client.commit_block(consumed_l1_handler_tx_hashes, rejected_l1_handler_tx_hashes, height)` with the reverted tx included in `consumed_l1_handler_tx_hashes` and absent from `rejected_l1_handler_tx_hashes`, transitioning it to `Committed` state in the L1 events provider's transaction manager.
5. The sender's L1 fee, already reflected as `Fee(0)` on the L2 receipt, is never transferred anywhere and can no longer be reclaimed through the L1 cancellation path once the message is reported consumed — resulting in a permanent, unrecoverable loss of the L1-side fee for an action that never took effect on L2.

    async fn commit_proposal_and_block(
        &mut self,
        height: BlockNumber,
        state_diff: ThinStateDiff,
        address_to_nonce: HashMap<ContractAddress, Nonce>,
        consumed_l1_handler_tx_hashes: IndexSet<TransactionHash>,
        rejected_tx_hashes: IndexSet<TransactionHash>,
        storage_commitment_block_hash: StorageCommitmentBlockHash,
    ) -> BatcherResult<()> {
        info!(
            "Committing block at height {} and notifying mempool & L1 event provider of the block.",
            height
        );
        trace!("Rejected transactions: {:#?}, State diff: {:#?}.", rejected_tx_hashes, state_diff);

        // Proposal commitment is the the partial block hash when it's available, and None
        // otherwise. The commitment is computed here to set the prev_proposal_commitment cache. As
        // this cache is only used for blocks obtained through the decision_reached flow, it can
        // be None for old (pre 0.13.2) blocks.
        let proposal_commitment = match &storage_commitment_block_hash {
            StorageCommitmentBlockHash::Partial(components) => Some((
                height,
                ProposalCommitment {
                    partial_block_hash: PartialBlockHash::from_partial_block_hash_components(
                        components,
                    )
                    .map_err(|e| {
                        error!("Failed to compute partial block hash: {}", e);
                        BatcherError::InternalError
                    })?,
                },
            )),
            StorageCommitmentBlockHash::ParentHash(_) => None,
        };

        // Commit the proposal to the storage.
        self.storage_writer
            .commit_proposal(height, state_diff, storage_commitment_block_hash)
            .map_err(|err| {
                error!("Failed to commit proposal to storage: {}", err);
                BatcherError::InternalError
            })?;
        info!("Successfully committed proposal for block {} to storage.", height);

        self.prev_proposal_commitment = proposal_commitment;

        // Notify the L1 provider of the new block.
        let rejected_l1_handler_tx_hashes = rejected_tx_hashes
            .iter()
            .copied()
            .filter(|tx_hash| consumed_l1_handler_tx_hashes.contains(tx_hash))
            .collect();

        let l1_events_provider_result = self
            .l1_events_provider_client
            .commit_block(consumed_l1_handler_tx_hashes, rejected_l1_handler_tx_hashes, height)
            .await;
