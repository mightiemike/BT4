### Title
Front-runnable user-chosen `yield_id` in `promise_yield_create_with_id` allows griefing/DoS of contract promise creation - (File: `runtime/runtime/src/ext.rs`)

### Summary
The `promise_yield_create_with_id` host function lets a contract create a yielded promise under a caller-supplied 32-byte `user_yield_id` instead of a runtime-generated `data_id`. Uniqueness is enforced only by a duplicate check against a value that is fully attacker-controlled and visible/predictable ahead of inclusion, so any account that can invoke the same contract method can race to "claim" a given `yield_id` before the legitimate caller's transaction executes, causing the legitimate call to silently receive a sentinel/no-op instead of creating its promise - the same class of bug as the reported `loanId` front-running griefing.

### Finding Description
`create_promise_yield_receipt_with_id` in `runtime/runtime/src/ext.rs` performs the duplicate check purely on the attacker-influenceable `user_yield_id`, scoped only by `receiver_id` (the contract account), not by caller/predecessor: [1](#0-0) 

The uniqueness constraint is implemented via a trie mapping (`TrieKey::YieldIdToDataId`) keyed by `(receiver_id, yield_id)` only: [2](#0-1) [3](#0-2) 

The host-function contract documents the exact "loanId-style" race explicitly: two calls with the same `yield_id` for the same account race, and the loser gets a `None`/sentinel result rather than an error that could be reliably detected and retried with a different id chosen after the fact: [4](#0-3) 

At the WASM ABI boundary, `promise_yield_create_with_id` in the runners returns `u64::MAX` as a silent sentinel on collision instead of aborting the call, which is confirmed by the shipped test: [5](#0-4) [6](#0-5) 

This mirrors the reported bug precisely: a user-selected identifier (`loanId` there, `yield_id` here) determines whether an operation succeeds, the collision check is keyed only by the identifier value and a shared namespace (per-loan-manager there, per-contract-account here), and any account able to submit a transaction/contract call ahead of the victim's transaction (via normal mempool ordering, since NEAR chunk producers select and order transactions from the pool) can pre-claim the identifier, causing the victim's otherwise-valid call to lose its intended receipt creation.

### Impact Explanation
Any dApp built on `promise_yield_create_with_id` where the `yield_id` is derived from user input (e.g., an order id, request id, or any value that must be predictable/reproducible by the caller for later resumption via `promise_yield_resume_with_id`) is exposed to griefing: an attacker who can call the same contract with the colliding `yield_id` first causes the victim's call to silently fail to create the yielded promise. Because the failure is a sentinel (`u64::MAX`) rather than a trap, a contract that does not explicitly check for it will continue execution believing the promise/callback was scheduled, when it was not - this can lead to funds already accepted/deposited by the contract call never being followed by the expected callback logic (e.g., no resolution, no refund path triggered), i.e., funds effectively stuck pending manual/administrative intervention. This is a protocol-level (runtime host function) DoS/griefing primitive, not a bug of any single dApp's business logic, since the collision defense mechanism itself is what is being exploited.

### Likelihood Explanation
Exploitation only requires the ability to submit an ordinary transaction/contract call - no elevated privileges, no validator or network-level position, and no reliance on any sync, sandbox, or leaked-key condition. Any account can observe another account's pending transaction (chunk-producer transaction pool visibility works the same way as public mempools referenced in the original report) and submit a competing call with the same `yield_id` value to the same contract account before the victim's transaction is applied. Because the vulnerable API is a general-purpose runtime host function (available since the introduction of `YieldWithId` per `ProtocolFeature::YieldWithId`), likelihood scales with adoption of this specific new host call by contracts that let callers pick or predict `yield_id`.

### Recommendation
Do not rely solely on a caller-supplied value as the sole collision key. Either:
- Scope the uniqueness check by `(predecessor_id, receiver_id, user_yield_id)` so that only the account that "owns" a given call path can collide with itself, closing the cross-account front-running vector; or
- Return a distinguishable, actionable error (rather than a bare sentinel indistinguishable from a valid but negative-looking value) so that calling contracts are forced to explicitly branch on failure instead of silently continuing as if the promise was created; and
- Document (and, where feasible, enforce) that `yield_id` values used across untrusted multi-tenant callers into the same contract must incorporate the caller's account id or another attacker-unpredictable/caller-bound component to avoid exactly this collision-squatting class of griefing.

### Proof of Concept
1. Contract `C` exposes a method `start_flow(id: [u8;32])` that internally calls `promise_yield_create_with_id` with the caller-provided `id`, expecting to later resume the flow via `promise_yield_resume_with_id(id, ...)`.
2. Victim Alice submits a transaction calling `C.start_flow(id=X)` where `X` is meaningful/predictable in her application context (e.g., an order id agreed upon out of band).
3. Attacker observes Alice's pending transaction (or independently predicts `X`) and submits `C.start_flow(id=X)` first, or in the same chunk with favorable ordering.
4. Per `create_promise_yield_receipt_with_id`'s duplicate check (`runtime/runtime/src/ext.rs:378-385`), the attacker's call (if applied first) writes the `YieldIdToDataId` mapping for `X`; Alice's subsequent call with the same `X` finds `has_yield_id_mapping(...) == true` and returns `Ok(None)`, which at the ABI layer surfaces as the `u64::MAX` sentinel (as demonstrated by the existing test `create_with_id_duplicate_in_same_call_returns_sentinel` in `integration-tests/src/tests/runtime/test_yield_resume.rs:360-386`, generalized here to two separate transactions/callers instead of two calls in one transaction).
5. If `C`'s contract logic does not explicitly check for the sentinel, Alice's transaction proceeds as if the yield/promise was successfully created, while no corresponding receipt actually exists - any deposit or state change already committed in `start_flow` before the yield-create call is now orphaned from its intended completion path.

    fn create_promise_yield_receipt_with_id(
        &mut self,
        receiver_id: AccountId,
        user_yield_id: YieldId,
    ) -> Result<Option<(ReceiptIndex, CryptoHash)>, VMLogicError> {
        // Check for duplicate yield_id in trie. TrieUpdate also reflects writes from earlier
        // calls within the same function call, so this also catches in-transaction duplicates.
        if has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)
            .map_err(wrap_storage_error)?
        {
            return Ok(None);
        }

        let input_data_id = self.generate_data_id();

        // Store bidirectional yield_id <-> data_id mappings
        set_yield_id_mapping(&mut self.trie_update, &receiver_id, user_yield_id, input_data_id);

        let receipt_index =
            self.receipt_manager.create_promise_yield_receipt(input_data_id, receiver_id.clone());

        set_promise_yield_status(
            &mut self.trie_update,
            &receiver_id,
            input_data_id,
            PromiseYieldStatus::Yielded,
        );

        Ok(Some((receipt_index, input_data_id)))
    }
