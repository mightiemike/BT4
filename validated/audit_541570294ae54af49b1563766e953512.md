Unconditional Persistent Class Storage in `TransactionConverter::convert_rpc_tx_to_internal` Enables Uncontrolled Disk Growth via Rejected Declare Transactions - (File: crates/apollo_transaction_converter/src/transaction_converter.rs)

### Summary
Every `Declare` transaction submitted to the gateway causes its Sierra class to be compiled and **persistently written** to the class manager's on-disk/cache storage during RPC-to-internal conversion — a step that happens *before* any stateful validation (nonce, fee/balance, resource bounds, `__validate__`) is performed. An attacker can submit a stream of syntactically-valid but ultimately-rejected declare transactions (e.g., with insufficient balance, bad nonce, or invalid signature) each declaring a unique never-before-seen class, causing unbounded growth of the class manager's persistent storage and cache, without ever getting a transaction accepted into the mempool.

### Finding Description
In `add_tx_inner`, the gateway performs only cheap stateless checks (`stateless_tx_validator.validate`) and permission checks before calling `convert_rpc_tx_to_internal_and_executable_txs`: [1](#0-0) 

That function calls `TransactionConverter::convert_rpc_tx_to_internal`, which for `Declare` transactions unconditionally calls `self.class_manager_client.add_class(tx.contract_class)` **before** any stateful validation is run: [2](#0-1) 

On the class-manager side, `ClassManager::add_class` compiles the Sierra class (CPU cost) and then persists it via `CachedClassStorage::set_class`, which writes to durable/`Fs` storage as well as the in-memory cache — this occurs unconditionally as long as the class hash is not already cached: [3](#0-2) [4](#0-3) 

Only *after* this compile-and-persist step does the gateway run `extract_state_nonce_and_run_validations`, i.e., the actual stateful checks (nonce, fee bounds, resource bounds, `__validate__` entry point) that ultimately determine whether the transaction is accepted: [5](#0-4) [6](#0-5) 

If stateful validation fails (bad nonce, insufficient balance, too-high resource bounds, `__validate__` reverts, etc.), the transaction is rejected and never reaches the mempool — but the class it declared has already been compiled and permanently stored in the class manager. There is no rollback of `add_class` on downstream validation failure. This is structurally identical to the TSPortal bug: a validation-adjacent step (`convert_rpc_tx_to_internal`, called prior to real validation) performs an irreversible state-changing operation (`add_class`/`set_class`) that persists regardless of whether the overall transaction is ultimately accepted.

The only mitigating control is `declare_compilation_semaphore`, which merely rate-limits *concurrent* compilations to bound CPU/memory pressure at any instant — it does nothing to prevent an attacker from sequentially declaring an unbounded number of unique classes over time, each of which is durably persisted.

### Impact Explanation
An unprivileged transaction sender can, without ever funding an account correctly or supplying valid nonces/signatures for the final `__validate__` step, cause the class manager to permanently store an arbitrary number of unique compiled classes. This leads to:
- Unbounded growth of class-manager persistent storage (disk exhaustion) and the in-memory `GlobalContractCache` (memory pressure), matching the CWE-400/CWE-770 pattern in the reference report.
- Sustained CPU cost from repeated Sierra→CASM compilation for classes that are never actually declared successfully.
- Potential node-level denial of service (storage exhaustion, degraded compilation throughput, degraded gateway latency for legitimate declares), satisfying the "network unable to confirm new transactions" bar under sustained abuse, since gateway/class-manager resource exhaustion degrades processing of legitimate transactions across the sequencer.

### Likelihood Explanation
High reachability: any external user can submit an RPC `Declare` transaction directly to the gateway's `add_tx` entrypoint. Crafting a unique Sierra class per submission with an invalid nonce/signature/fee is trivial and inexpensive relative to the CPU/storage cost imposed on the sequencer. The `declare_compilation_semaphore` only throttles concurrency, not the sustained rate of unique persisted classes, so a slow-and-steady attacker easily bypasses it.

### Recommendation
Defer the persistent `add_class`/`set_class` write until after stateful validation succeeds (mirroring the TSPortal fix of separating read-only lookups from mutating writes in validation-adjacent code). Concretely:
- Split class conversion into a non-persisting compile/hash step used for validation purposes, and only call the persisting `class_manager_client.add_class` once `extract_state_nonce_and_run_validations` has succeeded (or gate persistence behind mempool acceptance).
- Alternatively, add a per-sender/global rate limit or fee/stake requirement on the number of "trial" declares that can trigger compilation-and-storage within a time window, independent of the compilation concurrency semaphore.
- Add storage growth/size accounting metrics and caps for classes not backed by an accepted transaction, with a garbage-collection/expiry mechanism for orphaned classes.

### Proof of Concept
1. Submit an RPC `Declare` V3 transaction with a unique, valid Sierra `contract_class` (so it passes stateless validation and class-hash computation) but with sender/nonce/resource-bounds crafted to fail stateful validation (e.g., resource bounds below the required threshold, or nonce mismatched with account state) — see `test_run_pre_validation_checks`/`test_deploy_account_nonce_validation`-style rejection paths for the exact conditions that fail after class persistence: [7](#0-6) 
2. Observe that `convert_rpc_tx_to_internal` invokes `class_manager_client.add_class(tx.contract_class)` and the class is compiled and persisted via `CachedClassStorage::set_class` before the request reaches `extract_state_nonce_and_run_validations`.
3. Observe the request ultimately fails with a stateful-validation error (e.g., `InvalidTransactionNonce` or gas-price-too-low), yet the previously-declared class remains stored in the class manager's storage/cache with no rollback.
4. Repeat with a new unique class per request to grow class-manager storage without bound.

**Caveat:** I was not able to fully inspect the underlying `FsClassStorage`/on-disk write path and its size limits/config (only `CachedClassStorage`'s wrapper logic was available), so the exact persistence durability characteristics (e.g., whether there's any existing expiry or size cap in `FsClassStorage`) are not fully confirmed. If deeper verification of `FsClassStorage` internals is needed, a Devin session with full repo access would be required.

    pub async fn add_class(&mut self, class: RawClass) -> ClassManagerResult<ClassHashes> {
        let sierra_class = SierraContractClass::try_from(&class)?;
        let class_hash = sierra_class.calculate_class_hash();
        if let Ok(Some(executable_class_hash_v2)) =
            self.classes.get_executable_class_hash_v2(class_hash)
        {
            // Class already exists.
            return Ok(ClassHashes { class_hash, executable_class_hash_v2 });
        }

        let compilation_start_time = Instant::now();
        let (raw_executable_class, executable_class_hash_v2) =
            self.compiler.compile(class.clone()).await.map_err(|err| match err {
                SierraCompilerClientError::SierraCompilerError(error) => {
                    ClassManagerError::SierraCompiler { class_hash, error }
                }
                SierraCompilerClientError::ClientError(error) => {
                    ClassManagerError::Client(error.to_string())
                }
            })?;
        debug!(
            %class_hash,
            compiled_class_hash = %executable_class_hash_v2,
            compilation_elapsed_ms = compilation_start_time.elapsed().as_millis(),
            class_size_bytes =
                class.size().map_or("Failed to get class size".to_owned(), |size| size.to_string()),
            casm_size_bytes =
                raw_executable_class.size().map_or("Failed to get casm size".to_owned(), |size| size.to_string()),
            "Finished compiling class."
        );

        self.validate_class_length(&raw_executable_class)?;
        Self::validate_class_version(&sierra_class)?;
        self.classes.set_class(
            class_hash,
            class,
            executable_class_hash_v2,
            raw_executable_class,
        )?;

        let class_hashes = ClassHashes { class_hash, executable_class_hash_v2 };
        Ok(class_hashes)
    }
