### Title
Missing bounds validation on `ENERGY_FEE` / `EXCHANGE_CREATE_FEE` governance parameters allows setting sun-per-energy price to zero (or unrestricted values) - ([File: actuator/src/main/java/org/tron/core/utils/ProposalUtil.java])

### Summary
`ProposalUtil.validator` is the central place where every committee-governance parameter change is checked before being applied by `ProposalService.process`. Almost all numeric parameters in this switch statement are range-checked (e.g. `value < 0 || value > LONG_VALUE`), but the `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` cases fall through with no check at all, mirroring exactly the "insufficient timing/parameter validation" bug class from the external report: a governance-controlled economic parameter can be set to 0 (or a negative/overflow-prone value), breaking an implicit invariant the rest of the system depends on.

### Finding Description
In `ProposalUtil.validator`, most fee-like parameters enforce `value < 0 || value > LONG_VALUE` before allowing the proposal, e.g. `ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, `TRANSACTION_FEE`, `ASSET_ISSUE_FEE`, etc. [1](#0-0) 

However, `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` have no validation branch at all — they simply `break`: [2](#0-1) 

Once a proposal carrying these parameters passes (with no bound check performed at creation time either, since `ProposalCreateActuator.validateValue` also delegates to this same `validator`), `ProposalService.process` unconditionally persists the raw value: `saveEnergyFee` / `saveExchangeCreateFee`. [3](#0-2) 

`getEnergyFee()` is the sun-per-energy-unit price used throughout the TVM billing path (`VMActuator`, `ReceiptCapsule`, `TransactionTrace`, etc.) to charge accounts for smart-contract execution resources. If governance sets `ENERGY_FEE` to `0`, or to a negative number (there is no lower-bound `< 0` check), the resulting fee computation can become free-of-charge or produce invalid/underflowed charges, since no other layer re-validates this value before use.

This is a direct structural analog to the reported issue: unbounded/unchecked governance-settable economic parameters that other code implicitly assumes are positive and bounded, with no explicit relationship/bound enforced at the point of change.

### Impact Explanation
If `ENERGY_FEE` is voted to `0` (which requires only a passing committee vote, i.e., no special "trusted" bypass beyond the normal governance process, and is not blocked by any code path), TVM contract execution/energy consumption becomes effectively free chain-wide, breaking the anti-spam/anti-DoS economic model of the network (an underpriced-public-work condition). A negative value could also propagate into fee/receipt arithmetic that assumes non-negative fees, risking inconsistent accounting or exceptions during block processing across nodes.

### Likelihood Explanation
Reaching this code path requires only the standard, unprivileged committee governance flow (any witness can create a proposal, and SRs vote per existing rules) — there is no special/trusted actor requirement beyond what governance already permits for every other successfully-bounded parameter. Because the validation gap is a simple missing `if` branch (unlike the 30+ neighboring cases that do check), it is easy to trigger unintentionally or intentionally by any proposal creator supplying `ENERGY_FEE=0`.

### Recommendation
Add explicit bounds checking to the `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` cases in `ProposalUtil.validator`, consistent with the pattern used for other fee parameters (e.g. `value < SOME_MIN || value > LONG_VALUE`), ensuring `ENERGY_FEE` cannot be reduced to 0 or a negative number. More broadly, review the validator for all parameters that "fall through" with only `break` and no explicit range validation to make sure they carry the same defensive invariant enforcement as the majority of cases.

### Proof of Concept
1. Submit a `ProposalCreateContract` (as any witness) with parameter id `ENERGY_FEE` (11) and value `0`.
2. `ProposalCreateActuator.validate()` calls `ProposalUtil.validateValue` → `validator`, which hits the `case ENERGY_FEE: case EXCHANGE_CREATE_FEE: break;` branch and returns without error. [2](#0-1) 
3. Once the proposal is approved by SRs, `ProposalService.process` persists `saveEnergyFee(0)`. [4](#0-3) 
4. Subsequent smart-contract execution billing via `VMActuator`/`ReceiptCapsule` uses `getEnergyFee() == 0`, resulting in free energy consumption for all contract calls network-wide.
