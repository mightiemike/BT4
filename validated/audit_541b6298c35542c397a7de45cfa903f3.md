### Title
Hard-Revert-on-Insufficient-Supply in `ParticipateAssetIssueActuator` Enables Front-Running Griefing That Wastes Victim Bandwidth/Fees - ([File: actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java])

### Summary
`ParticipateAssetIssueActuator` implements the ICO-style "participate in asset issue" flow: buyers send TRX to `owner_address`/`to_address` and receive a proportional share of a **fixed-supply** token pool held in the issuer's account. Just like `LPDA.buy()`'s `require(newId <= temp.finalId, "TOO MANY")`, this actuator performs an all-or-nothing supply check (`assetBalanceEnoughV2`) with no partial-fill fallback, and — critically — the resource fee (bandwidth/energy) is deducted from the buyer *before* this check is executed. This lets an attacker monitor pending `ParticipateAssetIssueContract` transactions and race ahead of other buyers near supply exhaustion, causing legitimate buyers to pay fees for a transaction that reverts and yields zero tokens.

### Finding Description
`ParticipateAssetIssueActuator.validate()` computes the requested `exchangeAmount` and hard-fails if the issuer's remaining asset balance is insufficient: [1](#0-0) 

This mirrors the LPDA bug's `require(newId <= temp.finalId, "TOO MANY")` — there is no code path that clips the purchase to the remaining supply (i.e. no equivalent of the report's suggested `diff`/partial-fill fix); the whole transaction is rejected via `ContractValidateException`. The same all-or-nothing pattern exists in `execute()`, which throws `ContractExeException` if `reduceAssetAmountV2` fails: [2](#0-1) 

The critical amplifier is *when* fees are charged relative to `validate()`/`execute()`. In `Manager.processTransaction`, `consumeBandwidth(trxCap, trace)` (which deducts bandwidth/energy fees or TRX) runs **before** `trace.exec()` (which invokes the actuator's `validate()`/`execute()`): [3](#0-2) 

So a victim's transaction pays its bandwidth/fee cost regardless of whether the participate call ultimately reverts due to insufficient remaining supply.

### Impact Explanation
An attacker observing the mempool for a popular, supply-limited asset issuance can submit their own smaller `ParticipateAssetIssueContract` transactions with higher priority/fee to drain the issuer's remaining asset balance just before a victim's larger buy is processed. The victim's transaction:
- Still consumes/pays bandwidth or TRX fee (per `BandwidthProcessor.consume`), and
- Reverts with "Asset balance is not enough !", yielding **zero tokens**.

This is a direct DoS/griefing vector against unprivileged users participating in a public token sale, with concrete accounting impact (fee paid, no consideration received) — the same class of harm described in the LPDA report (front-run buyers "minting nothing" after paying gas), adapted to java-tron's fixed-price ICO mechanism instead of a decaying-price Dutch auction.

### Likelihood Explanation
`ParticipateAssetIssueContract` is a standard, unprivileged, publicly reachable transaction type (`ParticipateAssetIssueServlet` / gRPC `ParticipateAssetIssue`). Any account can issue a supply-limited asset via `AssetIssueActuator`, and any account can call participate. Popular/limited-supply issuances create natural contention where this griefing is straightforward to execute by simply submitting small competing participate transactions with higher fees near depletion.

### Recommendation
Modify `ParticipateAssetIssueActuator.execute()`/`validate()` to clip the exchange amount to the actual remaining asset balance instead of hard-failing, analogous to the suggested LPDA fix:
```java
long available = toAccount.getAssetBalanceV2(key); // remaining supply
if (exchangeAmount > available) {
    exchangeAmount = available;
    // recompute refunded 'cost' proportionally and return excess TRX to buyer
}
```
Alternatively (or additionally), defer bandwidth/fee consumption until after contract-level supply validation succeeds, so buyers whose purchase cannot be filled are not charged.

### Proof of Concept
1. Issuer creates an `AssetIssueContract` with a small `total_supply` (e.g. 100 units) via `AssetIssueActuator`.
2. Near supply exhaustion (issuer's remaining `AssetV2` balance = 10 units), Victim broadcasts `ParticipateAssetIssueContract` requesting 10 units' worth of TRX.
3. Attacker sees Victim's pending tx in the mempool and broadcasts their own `ParticipateAssetIssueContract` for 10 units with a higher-priority fee, which is processed first — `toAccount.reduceAssetAmountV2` succeeds, remaining supply becomes 0.
4. Victim's transaction is processed: `consumeBandwidth` already deducted Victim's bandwidth/fee (per `Manager.processTransaction` at [3](#0-2) ), then `validate()` throws `"Asset balance is not enough !"` (per [4](#0-3) ), so Victim pays for a transaction that yields zero tokens.
5. Attacker repeats this pattern for every subsequent Victim, monopolizing the fixed supply while forcing all competitors to pay fees for failed transactions.
