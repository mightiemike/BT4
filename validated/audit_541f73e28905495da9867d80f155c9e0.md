## Title
Delegated `WithdrawFromGasKey` drains gas-key balance without updating the Pending Transaction Queue's accounting, permitting gas-key over-withdrawal / value loss - (File: `runtime/runtime/src/action_validation.rs`, `chain/client/src/pending_transaction_queue.rs`)

### Summary
The stable protocol (v86, `STABLE_PROTOCOL_VERSION = 86`) accepts `WithdrawFromGasKey` actions nested inside a `Delegate`/`DelegateV2` meta-transaction. The fix that rejects this pattern, `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate`, is only scheduled to activate at protocol version 87 [1](#0-0) , one version above the current stable release. Meanwhile the Pending Transaction Queue (PTQ), which is the accounting mechanism that prevents a gas key from being spent below zero across concurrently-pooled transactions, only scans *top-level* actions of a transaction for `WithdrawFromGasKey` [2](#0-1) . This mirrors the reported bug class exactly: a wrapper accounting function (`claimRewards`/here the PTQ's `check_pending` gas-key balance tracker) can be bypassed by reaching the same underlying value-moving primitive (`WithdrawFromGasKey`) through an alternate path (nesting it inside a `Delegate` action) that the accounting does not observe.

### Finding Description
`action_validation.rs::validate_delegate_action` gates the rejection of a nested `WithdrawFromGasKey` strictly behind `RejectWithdrawFromGasKeyInDelegate`:
```
if mode == ValidateReceiptMode::NewReceipt
    && ProtocolFeature::RejectWithdrawFromGasKeyInDelegate.enabled(current_protocol_version)
    && actions.iter().any(|action| matches!(action, Action::WithdrawFromGasKey(_)))
{
    return Err(ActionsValidationError::WithdrawFromGasKeyNotAllowedInDelegate);
}
``` [3](#0-2) 

Because this feature activates at PV 87 and the tree's stable version is 86, on the currently shipped stable protocol a `Delegate`/`DelegateV2` action carrying an inner `WithdrawFromGasKey` action is admitted. The `pending_transaction_queue.rs::check_pending` function, which is the module responsible for computing `PendingConstraints::paid_from_gas_key` (used by `verify_and_charge_gas_key_tx_ephemeral` to ensure a gas key's balance covers pending, not-yet-applied withdrawals), only inspects `tx.transaction.actions()` at the top level:
```
for action in tx.transaction.actions() {
    if let Action::WithdrawFromGasKey(withdraw) = action {
        ...
        *entry = entry.saturating_add(withdraw.amount);
    }
}
``` [4](#0-3) 

A `WithdrawFromGasKey` wrapped inside a `Delegate` action's inner-action list is not a top-level `Action::WithdrawFromGasKey` on the outer transaction — it is nested inside `Action::Delegate(SignedDelegateAction)`. The scan therefore never counts it, so `session_gas_key_withdrawals`/`paid_from_gas_key` under-reports outstanding withdrawals for that gas key while pending transactions are still in flight in the same chunk-production session, exactly analogous to `delayedRewards`/`reservedFeeBalance` under-reporting in the report because the claim path bypassed the wrapper that maintains them.

The regression test in this same tree explicitly documents the exploitable window: pre-upgrade, a relayer-submitted `Delegate` action containing an inner `WithdrawFromGasKey` executes successfully and drains the gas key [5](#0-4) , and the code comment for the fix states the root cause directly: "the SPICE pending transaction queue scans only the top level actions of a transaction for `WithdrawFromGasKey`, so a nested one drains a gas key that the queue still counts as funded" [2](#0-1) .

### Impact Explanation
Any relayer or the gas-key owner (or a colluding attacker who obtains a signed delegate action) can, by wrapping `WithdrawFromGasKey` inside a `Delegate`/`DelegateV2` action, drain a gas key's balance while the PTQ's accounting (`paid_from_gas_key`) still reports the balance as available for other pending gas-key transactions queued in the same session. This is an accounting/state-divergence bug of the exact shape described in the report: value is moved through a path the tracking mechanism does not observe, so a later gas-key transaction can be admitted against a balance that has already been (or will be) withdrawn, i.e., inconsistent/incorrect accounting of a real balance leading to acceptance of transactions that should have been rejected for insufficient gas-key balance (or rejection of transactions that should have succeeded), and can be leveraged toward the runtime detecting `NotEnoughGasKeyBalance` inconsistencies or, in the worst case, admission-control decisions diverging from the runtime's actual charge outcome. This is reachable purely by an unprivileged meta-transaction sender/relayer submitting a normal `Delegate` action through RPC — no validator or node compromise required.

### Likelihood Explanation
High under stable protocol version 86: the guard exists in code but is inert until PV 87 is activated (`RejectWithdrawFromGasKeyInDelegate` maps to version 87 in `version.rs:622`, one above `STABLE_PROTOCOL_VERSION = 86`). Any account holding a gas key, or any relayer relaying a signed delegate action on its behalf, can trivially construct such a transaction — this is demonstrated as a first-class, reproducible scenario by the existing test `test_reject_delegated_gas_key_withdraw_protocol_upgrade`, which asserts the pre-upgrade withdrawal succeeds.

### Recommendation
Activate `RejectWithdrawFromGasKeyInDelegate` at (or before) the currently deployed stable protocol version, or independently teach `pending_transaction_queue.rs::check_pending` to recursively scan inner `Delegate`/`DelegateV2` action lists for `WithdrawFromGasKey` (mirroring how `validate_delegate_action` recurses for other checks), so that gas-key withdrawal accounting cannot be bypassed by nesting the action inside a meta-transaction while the protocol-level action-validation rejection is not yet active.

### Proof of Concept
The existing regression test constructs the exact PoC: fund a gas key, then submit (from a relayer) a `Delegate` action whose sole inner action is `WithdrawFromGasKey` targeting the sender's own gas key:
```rust
let delegate_action = DelegateAction {
    sender_id: sender.clone(),
    receiver_id: sender.clone(),
    actions: vec![
        Action::WithdrawFromGasKey(Box::new(WithdrawFromGasKeyAction {
            public_key: gas_key.public_key(),
            amount: WITHDRAW_AMOUNT,
        })).try_into().unwrap(),
    ],
    ...
};
``` [6](#0-5) 
At the pre-upgrade (i.e., currently stable) protocol version, this transaction is admitted and successfully drains the gas key balance [5](#0-4) , while `pending_transaction_queue.rs::check_pending`'s top-level-only scan never registers this withdrawal against the gas key's pending accounting [4](#0-3) , so concurrently pooled gas-key transactions relying on that balance can be admitted against stale/incorrect accounting.
