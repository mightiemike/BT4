## Finding: Missing prune-boundary check in `get_persisted_auxiliary_info_iterator` causes silent fabrication of `PersistedAuxiliaryInfo::None` for pruned versions

### Title
Authenticated `list_auxiliary_infos` API silently returns fabricated `PersistedAuxiliaryInfo::None` for pruned versions instead of an error, because `AptosDB::get_persisted_auxiliary_info_iterator` skips the prune-boundary check that all sibling iterators perform — (File: `storage/aptosdb/src/db/aptosdb_reader.rs`)

### Summary
Every other version-ranged iterator exposed by `AptosDB` (`get_transaction_iterator`, `get_transaction_info_iterator`, `get_events_iterator`) explicitly calls `self.error_if_ledger_pruned(..., start_version)?` before constructing the iterator, so a caller requesting data at or below the pruner's progress gets a deterministic error. `get_persisted_auxiliary_info_iterator` does not do this [1](#0-0) , while its siblings do [2](#0-1) .

### Finding Description
`PersistedAuxiliaryInfoDb::get_persisted_auxiliary_info_iter_with_opts` cannot distinguish "version never written" from "version pruned/deleted" — both cases manifest as an absent RocksDB key. When the seeked key at `start_version` is missing, the code assumes it's simply pre-genesis/never-populated data and manufactures `PersistedAuxiliaryInfo::None` entries to fill the gap up to the next existing key: [3](#0-2) .

The actual on-disk deletion performed by the pruner is a plain range delete with no distinguishing tombstone semantics: [4](#0-3) , driven by `PersistedAuxiliaryInfoPruner::prune` [5](#0-4) .

Because `get_persisted_auxiliary_info_iterator` omits the `error_if_ledger_pruned` guard that its siblings use, an unprivileged API caller can request a `start_version` that has already been pruned. Instead of receiving the expected pruned-range error (as they would for transactions/events at the same version), the reader silently receives `PersistedAuxiliaryInfo::None` values for versions that in reality carried real (e.g. `V1 { transaction_index }`) data before pruning occurred — the true historical value is now indistinguishable from "not recorded."

This is reachable directly from the unprivileged REST API `list_auxiliary_infos`, which computes `start_version` purely from client-supplied paging parameters and the current ledger version, with no pruning check of its own: [6](#0-5) . The result is serialized and returned as an authenticated JSON/BCS response body: [7](#0-6) .

### Impact Explanation
The authenticated API response is bound to the wrong data for the requested version: it returns a fabricated `PersistedAuxiliaryInfo::None` instead of either (a) the real historical auxiliary info, or (b) a proper "version pruned" error. This differs from the correct semantics enforced everywhere else in the same reader (transactions, transaction infos, events all correctly error on pruned ranges). A consumer relying on `list_auxiliary_infos` (e.g., an indexer or downstream verifier reconstructing transaction execution metadata) would silently ingest incorrect state for pruned history, rather than being told the data is unavailable.

Note: I was not able to fully confirm within this review whether `PersistedAuxiliaryInfo` values feed into any proof/root construction that would make this a proof-verification issue (they don't appear to have a dedicated Merkle/accumulator binding based on what was inspected), so I'm not asserting proof-corruption — only that the authenticated API output layer silently diverges from the correct historical ledger content, which the review's "Authenticated API ... output bound to the wrong version" criterion covers.

### Likelihood Explanation
Any unprivileged caller of the `list_auxiliary_infos` REST endpoint who supplies a `start` page parameter targeting a version older than the node's configured pruning window can trigger this deterministically — no race or attacker-controlled internal state is required, only a normal pruning-enabled node with default ledger pruning and a query for old versions. This is high likelihood on any production fullnode running with ledger pruning enabled (the default configuration).

I was unable to fully verify, given tool/iteration limits, whether the RocksDB `SchemaIterator` used here takes a point-in-time snapshot (which would rule out the specific mid-iteration concurrent-splice scenario described in the exploit question). Regardless of that snapshot behavior, the confirmed, code-level discrepancy — the missing `error_if_ledger_pruned` call compared to sibling iterators — independently causes pruned data to be silently reinterpreted as "no data," which is the core corruption concern.

### Recommendation
Add the same `self.error_if_ledger_pruned("PersistedAuxiliaryInfo", start_version)?` (or equivalent) guard to `get_persisted_auxiliary_info_iterator` in `storage/aptosdb/src/db/aptosdb_reader.rs` before constructing the iterator, mirroring `get_transaction_iterator`/`get_transaction_info_iterator`/`get_events_iterator`. Additionally, consider making `PersistedAuxiliaryInfoDb::get_persisted_auxiliary_info_iter_with_opts` reject (rather than silently pad) when the gap between `start_version` and the first found key falls within the already-pruned range, so "never written" and "pruned" are not conflated even when called from other internal code paths.

### Proof of Concept
1. Start an `AptosDB`/fullnode with ledger pruning enabled and a short pruning window.
2. Commit versions `0..N` including some with real `PersistedAuxiliaryInfo::V1 { .. }` entries.
3. Advance the ledger until the pruner has pruned past those versions (confirm via `PersistedAuxiliaryInfoPrunerProgress` metadata).
4. Call `GET /v1/transactions/auxiliary-info?start=<pruned_version>&limit=N` (or invoke `list_auxiliary_infos` directly).
5. Observe the API returns HTTP 200 with `PersistedAuxiliaryInfo::None` entries for the pruned versions instead of an error — contrast with calling the equivalent transaction/event endpoints at the same version, which correctly return a "version has been pruned" error.
