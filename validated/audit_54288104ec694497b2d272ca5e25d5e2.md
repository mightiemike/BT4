## Title
Unescaped exception message in `Util.processError`/`JsonFormat.printErrorMsg` allows JSON structure injection in HTTP API error responses - (File: `framework/src/main/java/org/tron/core/services/http/JsonFormat.java`)

### Summary
The reported Bio Protocol issue is a JSON-injection bug: user-controlled string data is concatenated directly into a hand-built JSON literal without escaping the `"` character, letting an attacker break out of a string value and inject arbitrary keys into the returned JSON. In java-tron, the field-level serializer (`JsonFormat.printFieldValue` / `escapeText` / `escapeBytesSelfType`) does perform escaping and even a parse-validate-fallback step for the "self type" (human readable) bytes fields such as `AssetIssueContract.description`, `url`, `name` etc. [1](#0-0) [2](#0-1) 

However, `JsonFormat.printErrorMsg` builds a JSON object by raw string concatenation of an exception's message with **no escaping at all**: [3](#0-2) 

### Finding Description
`printErrorMsg` is:
```java
public static String printErrorMsg(Exception ex) {
  StringBuilder text = new StringBuilder();
  text.append("{");
  text.append("\"Error\":");
  text.append("\"");
  text.append(ex.getMessage());
  text.append("\"");
  text.append("}");
  return text.toString();
}
```
`ex.getMessage()` is inserted verbatim between quotes with no call to `escapeText`/`escapeBytes` or any JSON-safe encoder. This is exactly the bug class from the external report: any `"` character (or `\`, newline, control character) inside the exception message will break the JSON string boundary and can inject additional keys/values into the object returned to the HTTP client.

The remaining risk is whether an attacker-controlled string can end up unescaped inside `ex.getMessage()` and reach this code path. This method is used from generic HTTP servlet error handling paths (`Util.processError`/`ScanShieldedTRC20NotesBy*Servlet`, and all the `Get*Servlet` classes that funnel exceptions through the same error-formatting utility). Many of these servlets throw exceptions (e.g. `InvalidProtocolBufferException`, custom validation exceptions) whose messages are built by concatenating raw request parameters (addresses, asset names, etc.) supplied by an unprivileged HTTP caller — this is standard practice throughout java-tron's actuators/validators, which frequently produce messages like `"Invalid param, " + name + " not exists"`. If any such message containing user-controlled text with a `"` character reaches `printErrorMsg`, the resulting HTTP JSON response body is structurally corrupted/injectable.

I was not able to fully trace every one of the ~49 call sites that reference `printErrorMsg`/`processError` down to a specific exception whose message directly embeds unsanitized user text without any prior sanitization, within the scope of this analysis. This is a real gap: confirming a concrete reachable exception message that carries raw special characters (as opposed to safely formatted numeric/hash values) would require deeper tracing of `Util.processError` and the various actuator/servlet validation exception constructors.

### Impact Explanation
If exploitable, this breaks the integrity of the JSON returned by java-tron's public HTTP API on error paths — an unprivileged caller could craft a request whose validation-failure message includes a `"` character, causing the wallet HTTP/JSON-RPC API response to contain attacker-controlled injected keys. Any client/exchange/wallet integration that parses this response and trusts additional injected fields (or that is confused into misparsing the response) could be misled. Because this is limited to unprivileged/public read/query endpoints and only affects response body formatting (not on-chain state, accounting, or settlement), the impact is analogous to the C4 finding's Medium severity — a data-integrity/response-format defect on public API output, not a chain-consensus or funds-safety issue.

### Likelihood Explanation
Likelihood is uncertain without confirming a concrete reachable exception message containing raw special characters from unprivileged user input. `printErrorMsg`'s lack of escaping is a definite, provable root-cause defect independent of any specific caller, since it directly contradicts the escaping discipline used elsewhere in the same file (`escapeText`, `escapeBytesSelfType`). The likelihood of practical exploitation depends on finding at least one exception message-building code path that echoes raw, attacker-supplied text (including a `"`character) back through `processError`, which I could not fully confirm within available tool calls.

### Recommendation
Apply the same JSON-string escaping used elsewhere in `JsonFormat` (`escapeText`) to `ex.getMessage()` before embedding it in `printErrorMsg`, e.g.:
```java
text.append(escapeText(ex.getMessage() == null ? "" : ex.getMessage()));
```
This ensures error responses remain structurally valid JSON regardless of exception message content, closing off the injection vector regardless of which caller populates the message with user-controlled data.

### Proof of Concept
Any code path that surfaces an exception whose `getMessage()` contains a `"` to `Util.processError` → `JsonFormat.printErrorMsg` will produce structurally invalid/injectable JSON, e.g. if a validation exception is thrown with message:
```
Invalid value, "extra_field": "injected
```
the resulting HTTP response body becomes:
```json
{"Error":"Invalid value, "extra_field": "injected"}
```
which is either invalid JSON or, depending on how a downstream lenient parser recovers, yields an object with an unexpectedly injected `extra_field` key — mirroring the Bio Protocol's `tokenURI` JSON injection.

  static String escapeText(String input) {
    StringBuilder builder = new StringBuilder(input.length());
    CharacterIterator iter = new StringCharacterIterator(input);
    for (char c = iter.first(); c != CharacterIterator.DONE; c = iter.next()) {
      switch (c) {
        case '\b':
          builder.append("\\b");
          break;
        case '\f':
          builder.append("\\f");
          break;
        case '\n':
          builder.append("\\n");
          break;
        case '\r':
          builder.append("\\r");
          break;
        case '\t':
          builder.append("\\t");
          break;
        case '\\':
          builder.append("\\\\");
          break;
        case '"':
          builder.append("\\\"");
          break;
        default:
          // Check for other control characters
          if (c >= 0x0000 && c <= 0x001F) {
            appendEscapedUnicode(builder, c);
          } else if (Character.isHighSurrogate(c)) {
            // Encode the surrogate pair using 2 six-character sequence (\\uXXXX\\uXXXX)
            appendEscapedUnicode(builder, c);
            c = iter.next();
            if (c == CharacterIterator.DONE) {
              throw new IllegalArgumentException(
                  "invalid unicode string: unexpected high surrogate pair value "
                      + "without corresponding low value.");
            }
            appendEscapedUnicode(builder, c);
          } else {
            // Anything else can be printed as-is
            builder.append(c);
          }
          break;
      }
    }
    return builder.toString();
  }
