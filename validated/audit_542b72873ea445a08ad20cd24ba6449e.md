## Finding

### Title
Unbounded `ActiveBallotIDs` scan in `ExpireBallotsBeforeHeight` allows attacker-triggered ballot-creation storm to DoS inbound/outbound finalization - (File: `x/uvalidator/keeper/ballot.go`)

### Summary
`CreateBallot` unconditionally calls `ExpireBallotsBeforeHeight`, which iterates **every** entry in the `ActiveBallotIDs` collection and performs a `Ballots.Get` for each one, with no cap on the number of items scanned. A new ballot is created on the first vote for any new observation key (`utx_key = sha256(source_chain:tx_hash:log_index)` for inbounds, or a deterministic outbound id for outbounds). An unprivileged attacker can cheaply generate an unbounded number of distinct, real gateway events on any supported external chain (tiny-value deposits), each of which becomes a brand-new ballot once honest Universal Validators observe and vote it via the gasless `MsgVoteInbound`. As `ActiveBallotIDs` grows, every subsequent first-vote transaction re-walks the entire (unbounded) active set, turning normal chain operation into O(n²) work and threatening to exceed block gas limits — the same unbounded-loop-over-attacker-growable-queue pattern as the UFarmPool `quexCallback` bug.

### Finding Description
`CreateBallot` is the single entry point for creating any of the four ballot types (`INBOUND_TX`, `OUTBOUND_TX`, `CHAIN_META`, `TSS_EVENT`, `FUND_MIGRATION`), and it always calls `ExpireBallotsBeforeHeight` first: [1](#0-0) 

`ExpireBallotsBeforeHeight` iterates the entire `ActiveBallotIDs` collection with no limit, doing a `Ballots.Get` per key to check expiry: [2](#0-1) 

`CreateBallot` is reached via `GetOrCreateBallot` → `VoteOnBallot`, called on every first-vote from `VoteOnInboundBallot`: [3](#0-2) 

The ballot key for inbounds is derived from the raw observation, so any new, distinct source-chain event produces a new ballot: [4](#0-3) 

`MsgVoteInbound` (and `MsgVoteOutbound`/`MsgVoteChainMeta`) is a gasless message type, executed automatically by honest Universal Validators whenever they observe a confirmed source-chain event — no manual/privileged action required on the validator side: [5](#0-4) [6](#0-5) 

An unprivileged attacker fully controls the trigger: they only need to emit many distinct, low-value gateway deposit events on a supported external chain (each is a legitimate, attacker-authored transaction paid for in the *external* chain's gas, not Push Chain's). Honest validators' off-chain client watches the gateway and automatically votes each event in via the confirmed-event pipeline: [7](#0-6) 

Each such vote is a *new* observation → a *new* ballot → a full scan of `ActiveBallotIDs` in `ExpireBallotsBeforeHeight`. Unlike other collection walks in the codebase that are explicitly capped (e.g. `GetConfirmedEvents(1000)`, `GetPendingOutbounds` query pagination), this walk has no bound, so as the active ballot set grows the per-vote cost grows linearly and the cumulative cost of processing an attacker-driven backlog of ballots grows quadratically — the identical bug class as `quexCallback`'s unbounded `depositQueue`/`withdrawQueue` loops, except here the "queue" is `ActiveBallotIDs` and the "attacker deposit" is a cheap external-chain gateway event.

### Impact Explanation
If the attacker sustains a high enough rate of distinct external-chain gateway events (which do not need to carry real value — dust amounts suffice, since the gateway event itself is what creates the ballot, not the deposit's economic value), `ActiveBallotIDs` can grow large enough that `ExpireBallotsBeforeHeight`'s per-vote scan starts consuming a large fraction of, or exceeds, the per-tx/per-block gas budget. Because every `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta` first-vote pays this cost, this can stall or block the honest-validator voting pipeline network-wide, preventing new inbound/outbound/chain-meta ballots from finalizing — a state-machine-level, not merely network-level, denial of service, reachable by an ordinary unprivileged external user without any validator or admin cooperation.

### Likelihood Explanation
Likelihood is significant: the attacker needs no elevated privileges, no cooperation from any Push Chain validator, and only needs to pay gas on an external chain to emit a large number of distinct gateway events (or use multiple attacker-controlled source addresses/log indices to guarantee distinct `utx_key`s). Since `MsgVoteInbound` etc. are gasless and validators vote observed events automatically and unconditionally (subject only to bonded/tombstoned checks), the ballot-creation rate is directly attacker-controlled.

### Recommendation
Bound the cost of `ExpireBallotsBeforeHeight`: either (a) cap the number of `ActiveBallotIDs` entries scanned per invocation (analogous to the 1000-item caps used elsewhere in the codebase) and process the remainder over subsequent calls/blocks, (b) move ballot-expiry sweeping to the `BeginBlocker`/`EndBlocker` with an explicit per-block processing cap instead of running it synchronously and unbounded inside every `CreateBallot` call, or (c) index active ballots by expiry height so that expired-ballot lookups are O(expired count) rather than O(all active ballots).

### Proof of Concept
1. Attacker identifies a supported external chain with cheap gas (e.g. an L2) and the configured gateway contract.
2. Attacker submits a large number (N) of distinct, minimal-value deposit transactions to the gateway, each producing a unique `(source_chain, tx_hash, log_index)` triple.
3. Honest Universal Validators' `EventProcessor` detects, confirms, and votes each event in via gasless `MsgVoteInbound` as designed.
4. Each vote is the first vote for a new `utx_key` → `CreateBallot` → `ExpireBallotsBeforeHeight` walks all of `ActiveBallotIDs` (now containing up to N unresolved ballots, since not all can finalize before more accumulate).
5. As N grows, per-vote processing cost grows linearly; total cost to drain the attacker-created backlog grows quadratically, exhausting gas/CPU budget for legitimate `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta` transactions and stalling ballot finalization chain-wide.

// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
