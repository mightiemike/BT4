### Title
Anyone can force unbounded growth of a victim's `DelegatedResourceAccountIndex` via unsolicited `DelegateResourceContract` transactions - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
`DelegateResourceActuator` lets any account "push" a resource delegation onto an arbitrary `receiverAddress` for as little as 1 TRX, with no consent or minimum-relationship check from the receiver. Each such call permanently inserts a new indexed entry keyed by `(delegator, receiver)` into `DelegatedResourceAccountIndexStore`. A malicious actor can Sybil many low-cost delegator accounts and repeatedly delegate the minimum 1 TRX to a single victim address, forcing that victim's index (`fromAccountsList`) to grow without bound. This mirrors the class of bug in the Paladin `hPAL` report: an attacker with a cheap resource (a large `cooldown` there, minimal frozen TRX here) can unilaterally mutate another user's on-chain accounting state through an unrequested transfer/interaction, imposing cost or degraded service on the victim.

### Finding Description
`DelegateResourceActuator.validate()` only requires `delegateBalance >= TRX_PRECISION` (1 TRX) and rejects delegation only if the receiver is a `Contract` account type — it does not require the receiver to have opted in or have any prior relationship with the sender: [1](#0-0) [2](#0-1) 

`execute()` then calls the private `delegateResource()` helper, which unconditionally records a new index entry for the `(ownerAddress, receiverAddress)` pair and updates the receiver's account state without any receiver-side check or cap: [3](#0-2) 

The underlying `DelegatedResourceAccountIndexStore.delegateV2` simply writes new keys `V2_FROM_PREFIX|from|to` and `V2_TO_PREFIX|to|from` for every distinct sender that delegates to the victim — there is no de-duplication limit or maximum degree per address: [4](#0-3) 

Reading back a victim's full delegation index (`getV2Index`/`getWithPrefix`, used by wallet/API queries and other internal flows) performs a full `prefixQuery` scan over all keys prefixed with the victim's address, i.e., its cost is linear in the number of distinct delegators an attacker has forced onto that account: [5](#0-4) 

Because the minimum delegation amount is trivially small (1 TRX) and the TRX is not burned (it can later be reclaimed by the attacker via `UnDelegateResourceActuator` once the lock/expire condition is satisfied), an attacker can cheaply generate a very large number of distinct sender addresses, each freezing and delegating 1 TRX to the same victim, to bloat the victim's index entry set indefinitely.

### Impact Explanation
This is analogous to the referenced Paladin finding: an inexpensive, attacker-controlled action forcibly mutates another (unconsenting) account's persistent state. Here, the effect is state/store bloat rather than a cooldown extension: every unsolicited delegation permanently adds a `DelegatedResourceAccountIndexCapsule` entry tied to the victim, degrading the performance of any code path that enumerates the victim's delegation index (`getV2Index`, wallet/gRPC queries exposing delegated-resource indices, and internal store iteration during `convert()`/`unDelegateExpire`-style flows). This is a resource-accounting/store-iteration griefing vector reachable from any anonymous account via a normal broadcast transaction, not from a privileged actor.

### Likelihood Explanation
Feasible but not free: each entry requires the attacker to control a distinct source address holding at least 1 TRX to freeze and delegate. This is the same "expensive but feasible, requires malice" profile the original report's judge accepted as valid despite external cost requirements — the per-entry cost here (1 TRX plus minor freeze/lock friction) is very low relative to the persistent, cumulative degradation imposed on the victim, making a sustained Sybil-based campaign practical for a moderately resourced attacker.

### Recommendation
Consider requiring receiver opt-in/allow-listing for unsolicited delegation, or bounding/pagination-limiting the number of distinct delegator entries tracked per receiver, and ensuring `getV2Index`/`getWithPrefix` queries are paginated rather than performing unbounded full-prefix scans, so that a large number of forced entries cannot degrade query cost for a targeted victim.

### Proof of Concept
1. Attacker creates N distinct funded addresses, each holding slightly more than 1 TRX.
2. From each address, submit `FreezeBalanceV2Contract` for 1 TRX, then `DelegateResourceContract` (`balance = 1_000_000` sun, `lock=false`, `receiver_address = victim`) — validated only by `delegateBalance >= TRX_PRECISION` and receiver-not-a-contract checks per `DelegateResourceActuator.validate()`.
3. Each transaction adds a unique `(senderX, victim)` entry via `DelegatedResourceAccountIndexStore.delegateV2`.
4. Repeating this with a large N causes `victim`'s `V2_TO_PREFIX|victim|*` key range to grow unboundedly; any subsequent `getV2Index(victim)` call (exposed through wallet/API "get delegated resource account index" queries) must scan and sort the full, attacker-inflated key range, degrading service for/about the victim.

Note: I was not able to trace the exact gRPC/HTTP API handler(s) that expose `getV2Index` to external callers within the indexed portion of the codebase; a Devin session with full repository access would be needed to confirm the exact externally-reachable RPC method names and any existing pagination/limits on that path.

  private void delegateResource(byte[] ownerAddress, byte[] receiverAddress, boolean isBandwidth,
                                long balance, boolean lock, long lockPeriod) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicPropertiesStore = chainBaseManager.getDynamicPropertiesStore();
    DelegatedResourceStore delegatedResourceStore = chainBaseManager.getDelegatedResourceStore();
    DelegatedResourceAccountIndexStore delegatedResourceAccountIndexStore = chainBaseManager
        .getDelegatedResourceAccountIndexStore();

    // 1. unlock the expired delegate resource
    long now = chainBaseManager.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    delegatedResourceStore.unLockExpireResource(ownerAddress, receiverAddress, now);

    //modify DelegatedResourceStore
    long expireTime = 0;
    if (lock) {
      expireTime = now + lockPeriod * BLOCK_PRODUCED_INTERVAL;
    }
    byte[] key = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, lock);
    DelegatedResourceCapsule delegatedResourceCapsule = delegatedResourceStore.get(key);
    if (delegatedResourceCapsule == null) {
      delegatedResourceCapsule = new DelegatedResourceCapsule(ByteString.copyFrom(ownerAddress),
          ByteString.copyFrom(receiverAddress));
    }

    if (isBandwidth) {
      delegatedResourceCapsule.addFrozenBalanceForBandwidth(balance, expireTime);
    } else {
      delegatedResourceCapsule.addFrozenBalanceForEnergy(balance, expireTime);
    }
    delegatedResourceStore.put(key, delegatedResourceCapsule);

    //modify DelegatedResourceAccountIndexStore
    delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress,
        dynamicPropertiesStore.getLatestBlockHeaderTimestamp());

    //modify AccountStore for receiver
    AccountCapsule receiverCapsule = accountStore.get(receiverAddress);
    if (isBandwidth) {
      receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForBandwidth(balance);
    } else {
      receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForEnergy(balance);
    }
    accountStore.put(receiverCapsule.createDbKey(), receiverCapsule);
  }

  public void delegateV2(byte[] from, byte[] to, long time) {
    byte[] fromKey = Bytes.concat(V2_FROM_PREFIX, from, to);
    DelegatedResourceAccountIndexCapsule toIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(to));
    toIndexCapsule.setTimestamp(time);
    this.put(fromKey, toIndexCapsule);

    byte[] toKey = Bytes.concat(V2_TO_PREFIX, to, from);
    DelegatedResourceAccountIndexCapsule fromIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(from));
    fromIndexCapsule.setTimestamp(time);
    this.put(toKey, fromIndexCapsule);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
