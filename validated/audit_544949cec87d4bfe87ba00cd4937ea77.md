### Title
DoS via unbounded, non-deduplicated shop→session-id index growth in `KVSessionStorage` - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
The Cloudflare KV session storage adapter maintains a per-shop index of session ids (`shop:${shop}` → `string[]`) that is appended to on every `storeSession` call and later fully loaded (via `Promise.all`) whenever `findSessionsByShop` is invoked. Unlike the Redis adapter, the KV adapter does not deduplicate entries before pushing, so repeated `storeSession` calls for the *same* session id (which happens routinely during normal, unprivileged, session-token-driven token exchange) cause the array to grow without bound. This mirrors the Biconomy `LiquidityFarming` pattern: an unbounded list is grown by an ordinary/unprivileged actor and later iterated in full by a legitimate operation, leading to a gas/resource-limit DoS.

### Finding Description
`KVSessionStorage.storeSession` always calls `addShopIds`, which reads the existing id array and concatenates the new id(s) without checking for duplicates: [1](#0-0) 

Compare this to the Redis adapter's `addKeyToShopList`, which explicitly checks `if (!idKeysArray.includes(idKey))` before pushing: [2](#0-1) 

Session ids used by this library are deterministic and stable per (shop, user) pair:
- Offline session id: `offline_${shop}` [3](#0-2) 
- Online (embedded) session id: `${shop}_${userId}` [4](#0-3) 

`storeSession` is called every time an app's session-token/token-exchange flow determines the stored session is missing or no longer active. For example, `performTokenExchange` re-stores the offline (and optionally online) session whenever the existing one isn't active, using the same deterministic id each time: [5](#0-4) 

Because this whole path is driven by a session token supplied on ordinary (unprivileged, merchant/customer-originated) authenticated app requests, an actor can repeatedly force this code path (e.g., by sending a session token that leads to a not-yet-active/soon-expiring session on each request, or simply by causing many storage misses/latency races) to trigger repeated `storeSession` → `addShopIds` calls. Each call appends the same deterministic id again with no dedup check, so the `shop:${shop}` KV array grows unbounded over time, purely from legitimate-looking, unprivileged authentication traffic.

### Impact Explanation
The bloated array is fully materialized and iterated whenever `findSessionsByShop` is called: [6](#0-5) 

`findSessionsByShop` is a documented, expected extension point used by app-installation/uninstall bookkeeping (e.g. `AppInstallations.includes`/`delete`, which is invoked from OAuth/installation-check middleware and app-uninstalled webhook processing): [7](#0-6) 

If the per-shop id array grows to tens/hundreds of thousands of entries, `findSessionsByShop` triggers that many parallel `namespace.get` KV reads via `Promise.all`, which can exhaust request time/CPU/memory limits of the KV runtime (e.g., Cloudflare Workers CPU-time or subrequest limits), causing that handler to fail or time out. Since this handler underlies installation-status checks and uninstall-webhook cleanup, this is a denial of service against authentication/installation-related processing for the affected shop — directly analogous to the referenced report's DoS-by-iteration-limit pattern.

### Likelihood Explanation
This does not require any privileged action or secret compromise — it can be triggered by an ordinary merchant/customer request flow that exercises the standard session-token → token-exchange path repeatedly (a routine, unprivileged, externally reachable operation). The bug is a straightforward missing-deduplication defect that is trivially reachable by normal app traffic patterns, and worsens over time even without active abuse, making accidental as well as intentional triggering plausible.

### Recommendation
In `KVSessionStorage.addShopIds` (and any other adapter lacking this check), deduplicate before storing, matching the Redis adapter's pattern:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```
Additionally, consider bounding/paginating `findSessionsByShop` reads and adding periodic pruning of stale ids, so a large shop-id index cannot cause unbounded parallel reads in a single call.

### Proof of Concept
1. Configure an embedded app using `KVSessionStorage` for session storage.
2. As a normal merchant/customer, repeatedly hit an authenticated endpoint using session-token/token-exchange in a way that keeps `session.isActive(...)` false at request time (e.g., because the offline session naturally has no `expires` set for permanent tokens but a race/latency condition or forced re-auth on each request causes `loadSession` to momentarily miss/expire it), causing `performTokenExchange` to call `sessionStorage.storeSession(offlineSession)` on every request: [8](#0-7) 
3. Each call appends the same deterministic `offline_${shop}` id to the `shop:${shop}` KV array without dedup: [1](#0-0) 
4. After N repeated calls, `shop:${shop}` contains N duplicate ids.
5. Any subsequent call to `findSessionsByShop(shop)` (e.g., from `AppInstallations.includes`/`delete` during install-check or uninstall webhook handling) issues N parallel KV `get` calls via `Promise.all`, which for large N will exceed practical KV/runtime limits and fail or stall — denying legitimate installation/uninstall processing for that shop.

    );

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }

  async includes(shopDomain: string): Promise<boolean> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      for (const session of shopSessions) {
        if (session.accessToken) return true;
      }
    }
    return false;
  }

  async delete(shopDomain: string): Promise<void> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      await this.sessionStorage.deleteSessions!(
        shopSessions.map((session: Session) => session.id),
      );
    }
  }
