### Title
Instant, unrestricted global contract code rewrite under `AccountId` mode allows a deployer to silently change behavior for all dependent accounts with no delay - (File: `runtime/runtime/src/global_contracts.rs`)

### Summary
`GlobalContractDeployMode::AccountId` lets an account owner deploy code that is referenced by their `AccountId` rather than by an immutable code hash. Any account can point at this code via `Action::UseGlobalContract`, and the owner can redeploy new code under the same `AccountId` identifier at any time, instantly and retroactively changing the executable logic used by every account that references it. This mirrors the `updateSolution` finding: a privileged actor can unilaterally swap in arbitrary new code affecting other parties' funds/logic, with no timelock, no opt-out window, and no on-chain warning before the change takes effect.

### Finding Description
`action_deploy_global_contract` in [1](#0-0)  allows any account to deploy code as a global contract. When `deploy_mode` is `AccountId`, `initiate_distribution` derives the global contract's on-chain identifier purely from the deployer's `account_id` rather than the code hash: [2](#0-1) . This means the same identifier (`GlobalContractIdentifier::AccountId(deployer)`) can be redeployed with entirely different code at any later time — confirmed by `test_global_contract_update`, where the deployer redeploys and all accounts using `GlobalContractIdentifier::AccountId(...)` immediately pick up the new code without any additional action from them: [3](#0-2) .

Any other account opts in via `Action::UseGlobalContract`, handled by `action_use_global_contract`/`use_global_contract`, which simply checks that the identifier currently exists in state and then sets the account's contract pointer to `AccountContract::GlobalByAccount(id)` — no reference to *which* version of the code was agreed to, no hash pinning, and no re-approval requirement: [4](#0-3) . The documentation for `GlobalContractDeployMode::AccountId` explicitly states this design intent: "This allows the owner to update the contract for all its users" [5](#0-4) .

This is directly analogous to the `updateSolution` bug class: an entity holding a single key (the global-contract-deploying account) can unilaterally rewrite the logic that other, unrelated accounts (who only submitted a `UseGlobalContract` transaction referencing the `AccountId`) rely on, at any time, with no waiting period for dependents to detect the change and disengage.

### Impact Explanation
Any account (or any contract, since global contracts are commonly used to implement shared/shardable logic such as owner-check libraries per NEP-616, see `test_sharded_contract_owner_check` [6](#0-5) ) that references an `AccountId`-mode global contract is trusting logic that can change underneath it without warning. Because the referencing account's code identity (and therefore its authorization/spending logic) is swapped instantly and network-wide once distribution completes, a malicious or compromised deploying account could push new code that behaves differently for calls it services (e.g. altering "owner-only" checks or fund-transfer logic) for every dependent account, with no on-chain notice period letting dependents unlink first. This is a protocol-level reachable path (regular `DeployGlobalContractAction` and `UseGlobalContractAction` transactions) rather than a validator/operator-only mechanism.

### Likelihood Explanation
Likelihood is moderate: it requires that some account(s) actually reference an `AccountId`-mode global contract belonging to an account not fully trusted (or later compromised/malicious), which is an expected usage pattern per the documented design (shared libraries, NEP-616 sharded-account pattern). Given documented intent ("this allows the owner to update the contract for all its users"), the capability is inherent, not accidental, making exploitation feasible whenever a dependent's trust assumptions in the deployer are violated.

### Recommendation
Apply the same style of mitigation suggested in the original report: introduce a delay between a new `DeployGlobalContractAction` under `AccountId` mode being submitted/distributed and it taking effect for existing `UseGlobalContract` dependents (e.g., a bake-in period during which the old code remains active and dependents can observe the pending change and choose to detach), or allow dependents to pin to a specific code hash/nonce of the `AccountId`-referenced contract rather than always tracking the latest version implicitly.

### Proof of Concept
1. Account `A` deploys a trivial global contract in `AccountId` mode (`tx_deploy_global_contract` with `GlobalContractDeployMode::AccountId`).
2. Account `B` submits `UseGlobalContractAction` referencing `GlobalContractIdentifier::AccountId(A)`.
3. Account `A` redeploys entirely different code under the same `AccountId` identifier (`test_global_contract_update` reproduces exactly this flow) [7](#0-6) .
4. `B`'s subsequent function calls now execute `A`'s new code immediately, with no notice, delay, or re-consent from `B`.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}
