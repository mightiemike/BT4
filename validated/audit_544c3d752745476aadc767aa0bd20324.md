### Title
Silent lt-hash/capitalization corruption from duplicate off-chain account updates in release builds - ([File: runtime/src/bank/accounts_lt_hash.rs])

### Summary
`Bank::enqueue_off_chain_accounts_lt_hash_updates()` only detects and panics on duplicate pubkeys within a single `StorableAccounts` batch when `cfg!(debug_assertions)` is true. In release (production validator) builds, this duplicate check compiles away entirely, so if a caller ever passes a batch containing the same pubkey twice, both versions get enqueued and mixed into the async accounts lt-hash accumulator without deduplication, silently corrupting the bank's calculated accounts lt hash / capitalization instead of panicking as intended.

### Finding Description
`enqueue_off_chain_accounts_lt_hash_updates` explicitly documents that it "does not deduplicate accounts, requiring the caller to ensure there are no duplicates," and guards this invariant with a debug-only check: [1](#0-0) 

The safety net (`panic!("duplicate accounts were enqueued for hashing…")`) is wrapped in `if cfg!(debug_assertions) { ... }`, so it is compiled out in release builds: [2](#0-1) 

When no dedup/panic occurs, every entry in `accounts` (including duplicates) is processed by `load_then_enqueue`, which loads the account's previous version and enqueues an `AccountsLtHashUpdate` that gets asynchronously mixed into `accounts_lt_hash_async_progress`: [3](#0-2) 

This is called by `Bank::store_accounts_without_stakes_cache`, whose own contract states "Callers must ensure there are no duplicates in `accounts`" — i.e., the invariant is enforced purely by caller discipline, not by any release-mode runtime check: [4](#0-3) 

This is analogous to the reported bug class ("duplicate assets" silently causing wrong calculated totals due to missing uniqueness validation): here, a duplicate pubkey slipping into an off-chain store batch (e.g., a future code change to reward/rent/sysvar update paths that accidentally includes the same pubkey twice) would cause the account's lt-hash contribution to be mixed in twice (once per duplicate entry) with `prev_account` loaded from the same stale on-disk/cache state for both entries, producing an incorrect final `AccountsLtHash`/capitalization that only a debug build would have caught via panic. Note that today's known call sites (e.g., `store_stake_accounts_in_partition`, `create_epoch_rewards_sysvar`) appear to construct pubkey-unique batches, so no active bug is being claimed — the vulnerability is the missing release-mode safety net for an invariant multiple call sites rely on, following the same "trust the caller to dedupe, no unique-check enforced in production" pattern as the reported LTV bug.

### Impact Explanation
If a duplicate pubkey ever reaches this off-chain path in a production (release) build, the resulting `AccountsLtHash` used for bank hash/capitalization verification (`bank.capitalization()` vs `calculated_capitalization`, and lt-hash checksum used to build the `SnapshotHash`) would be silently wrong — mixing in a duplicate account's contribution instead of only its final version. This can cause capitalization mismatches or lt-hash divergence at snapshot verification (`verify_snapshot_bank`) or between honest replaying nodes, i.e. a hash/capitalization divergence class of impact. In debug builds, the same scenario is caught immediately via `panic!`, meaning a real occurrence in production goes undetected instead of halting the node — worse than the debug behavior, since a crash-safe fast failure becomes a silent corruption in the exact builds validators actually run.

### Likelihood Explanation
Low-to-moderate. All currently traceable call sites into `enqueue_off_chain_accounts_lt_hash_updates`/`store_accounts_without_stakes_cache` (stake reward distribution, sysvar updates) appear to build pubkey-unique batches under current logic. The risk is latent: any future off-chain caller (or a subtle bug in partition/index construction feeding duplicate pubkeys into a single `StorableAccounts` batch) would go completely undetected in release builds, since the only enforcement mechanism (the debug-only panic) never runs in production. This mirrors exactly the "no uniqueness check in production path" root cause pattern from the reported analog, but the exploitability here depends on an as-yet-unidentified caller regression rather than direct external control, so likelihood is assessed as low without a demonstrated concrete duplicate-producing call path.

### Recommendation
Make the duplicate-pubkey check unconditional (not gated by `cfg!(debug_assertions)`), or perform deduplication defensively (keeping only the last occurrence per pubkey, matching `enqueue_on_chain_accounts_lt_hash_updates`'s existing dedup behavior) inside `enqueue_off_chain_accounts_lt_hash_updates` regardless of build profile, so a caller regression is caught (or safely handled) in production the same way it is in debug builds.

### Proof of Concept
Not independently reproduced against a live validator; based on static code analysis of `runtime/src/bank/accounts_lt_hash.rs` lines 85-170 and its caller `store_accounts_without_stakes_cache` in `runtime/src/bank.rs` lines 4791-4810. A concrete PoC would require constructing a `StorableAccounts` implementation with a duplicated pubkey and invoking `enqueue_off_chain_accounts_lt_hash_updates` (or a caller) compiled with `debug_assertions` disabled, then observing that `calculated_accounts_lt_hash`/capitalization differs from the correct value with no panic — this was not executed as part of this analysis.

    /// Enqueues the accounts lt hash updates for `accounts` to the accounts hasher thread pool.
    ///
    /// This fn is meant to be called by off-chain events, meaning we know/control `accounts`.
    /// Contrasting with `enqueue_on_chain_accounts_lt_hash_updates()`, this fn:
    /// - Does not deduplicate accounts, requiring the caller to ensure there are no duplicates.
    /// - Does not assume loading the previous version of accounts is fast,
    ///   e.g. when storing stake accounts as part of partitioned epoch rewards.
    ///
    /// If Some, `thread_pool_for_hashing_accounts` will be used
    /// to load the previous version of accounts in parallel.
    pub fn enqueue_off_chain_accounts_lt_hash_updates<'a>(
        &self,
        accounts: &impl StorableAccounts<'a>,
        thread_pool_for_loading_accounts: Option<&ThreadPool>,
    ) {
        if cfg!(debug_assertions) {
            // if debug assertions are on, we will check for duplicates
            use ahash::HashSetExt as _;
            let mut seen_accounts = ahash::HashSet::with_capacity(accounts.len());
            let mut duplicate_pubkeys = ahash::HashSet::with_capacity(0); // assume no duplicates
            for index in 0..accounts.len() {
                let pubkey = accounts.pubkey(index);
                if !seen_accounts.insert(pubkey) {
                    // we've already seen this account, so add it to the duplicates list
                    duplicate_pubkeys.insert(pubkey);
                }
            }
            if !duplicate_pubkeys.is_empty() {
                let mut duplicate_accounts = ahash::HashMap::<_, Vec<_>>::default();
                for duplicate_pubkey in duplicate_pubkeys {
                    for index in 0..accounts.len() {
                        let pubkey = accounts.pubkey(index);
                        if pubkey == duplicate_pubkey {
                            duplicate_accounts
                                .entry(pubkey)
                                .or_default()
                                .push(accounts.account(index, |account| account.take_account()));
                        }
                    }
                }
                panic!("duplicate accounts were enqueued for hashing: {duplicate_accounts:?}");
            }
        }

        let thread_pool_for_hashing_accounts = accounts_hasher_thread_pool();

        // A closure that does the loading and enqueueing, so code is shared
        // whether using the thread_pool_for_loading_accounts or not.
        let load_then_enqueue = |index| {
            let address = accounts.pubkey(index);
            let prev_account = self
                .rc
                .accounts
                .load_with_fixed_root_do_not_populate_read_cache(&self.ancestors, address)
                .map(|(account, _slot)| account);
            let curr_account = accounts.account(index, |account| {
                (account.lamports() != 0).then(|| account.take_account())
            });
            if prev_account.is_none() && curr_account.is_none() {
                // the account was ephemeral; skip it
            } else {
                // the account was modified; enqueue this update
                async_progress.spawn(
                    thread_pool_for_hashing_accounts,
                    AccountsLtHashUpdate {
                        address: *address,
                        prev_account,
                        curr_account,
                    },
                );
            }
        };

        if let Some(thread_pool_for_loading_accounts) = thread_pool_for_loading_accounts {
            // The previous version of accounts must be loaded before subsequent account
            // modifications occur, so ThreadPool::spawn() canot be used here.
            thread_pool_for_loading_accounts.install(|| {
                (0..accounts.len())
                    .into_par_iter()
                    .for_each(load_then_enqueue);
            });
        } else {
            (0..accounts.len()).for_each(load_then_enqueue);
        }
    }

        &self,

            .accounts
            .store_accounts_par(accounts, self.bank_id(), None, &self.ancestors);
