### Title
Rounding/truncation drift between `Deduct` and `Settle` in workflow metering can desynchronize tracked credit balance from actual spend, permitting under-billed resource consumption - ([File: core/services/workflows/metering/metering.go])

### Summary
The Allora bug is a class of "asymmetric rounding" issue: one side of an accounting equation is computed with full precision while the other side is truncated, so the two sides drift apart over repeated operations, eventually leaving the paying account short of funds it is obligated to disburse. The Chainlink CRE workflow metering package (`core/services/workflows/metering`) contains a directly analogous pattern in its `Deduct`/`Settle` credit-accounting flow, where an earmarked (deducted) amount and the later-settled actual spend amount can be rounded independently and reconciled with an error path that is silently swallowed rather than enforced.

### Finding Description
`Report.Deduct` earmarks credits from the local `balanceStore` via `ByResource`/`ByDerivedAvailability`, which convert a native-unit amount to credits using `balanceStore.convertToBalance`, rounding gas-denominated conversions to `defaultDecimalPrecision` [1](#0-0) .

Later, `Report.Settle` aggregates each node's reported spend per resource dimension, converts it back to credits via `ConvertToBalance` (again independently rounded/shifted, e.g. gas values are `Shift(18)` before conversion), and accumulates `spentCredits` [2](#0-1) .

The refund/reconciliation step then computes `step.Deduction.Sub(spentCredits)` and calls `r.balance.Add(...)`: [3](#0-2) 

`balanceStore.Add` explicitly rejects negative amounts and returns `ErrInvalidAmount` without mutating `bs.balance` [4](#0-3) . In `Settle`, that error is only logged as an "invariant" warning and is not propagated or otherwise handled [5](#0-4) .

Because the earmark (`Deduction`) and the true spend (`spentCredits`) are computed via separate, independently-rounded conversions (`convertToBalance` at deduct time vs. per-resource aggregation/shift/rounding at settle time), it is possible for `spentCredits` to exceed `step.Deduction` even though the actual on-node work was within the originally reserved amount, purely from rounding drift accumulated across resource dimensions and steps — the same "one side full precision / other side truncated" pattern as the Allora `addShare` vs `delegatorReward.SdkIntTrim()` mismatch. When that happens, `r.balance` is *not* decremented for the shortfall (since `Add` no-ops on negative input), while `r.balance.AddSpent(spentCredits)` unconditionally records the full spent figure in a separate spent-total field [6](#0-5) . The result is that `r.balance` (the value consulted by every subsequent `Deduct` call to determine remaining available credits) can end up higher than it should be relative to the credits actually reserved from the billing service, letting later steps in the same workflow execution draw down more resource usage than the workflow's reserved credit balance actually covers.

### Impact Explanation
This does not directly steal funds on-chain, but it is a data-integrity/misreporting issue in the node's own billing/metering subsystem: the local ledger used to gate further capability invocations during a workflow run can silently diverge from the amount the workflow owner actually reserved and paid for. In sustained or high-throughput workflows with many steps, the repeated per-step rounding drift (mirroring the "repeated increase … over multiple blocks" dynamic in the original report) can allow measurably more compute/resource consumption than was billed, at the expense of the node operator/billing service. The failure mode is intentionally fail-open (by design, so as not to block execution), but the reconciliation error being merely logged rather than acted upon means the accounting invariant ("spend must not exceed reserve") has no actual enforcement.

### Likelihood Explanation
Triggering this requires no privileged access — any workflow owner/user driving a normal workflow execution with several `Deduct`/`Settle` cycles across multiple resource/spend types (compute + gas, multiple nodes) can produce the rounding conditions, since the divergence stems purely from the independent rounding paths in `convertToBalance`/`ConvertToBalance` and the per-unit aggregation/rounding in `Settle`. The magnitude per step is small, but the pattern accumulates, and the comment in the code itself acknowledges this scenario as an "invariant" that can be violated ("invariant: spend exceeded reserve") [7](#0-6) .

### Recommendation
- Reconcile `Deduct` and `Settle` conversions using a single, consistent rounding policy (e.g., always round down/truncate on the side that determines what leaves the payer's balance, matching the direction used in the original Allora fix of truncating `addShare` before use).
- When `step.Deduction.Sub(spentCredits)` is negative, do not silently swallow the `Add` error: either clamp `r.balance` to zero, propagate an error that switches the report into a stricter accounting mode, or record the shortfall separately so it can be reconciled against the billing service instead of being dropped.
- Add invariant tests asserting that cumulative `spentCredits` across all steps of an execution can never exceed the credits actually reserved via `Reserve`.

### Proof of Concept
1. Configure a workflow with a resource/spend type whose conversion rate does not evenly divide reported spend values (e.g., gas rate requiring rounding), across multiple nodes contributing `capabilities.MeteringNodeDetail` entries.
2. Call `Deduct` (earmarking based on `convertToBalance`'s rounded output).
3. Call `Settle` with node metering values whose aggregated, independently-rounded `spentCredits` exceeds `step.Deduction` by a small remainder.
4. Observe: `r.balance.Add(step.Deduction.Sub(spentCredits))` returns `ErrInvalidAmount` (logged only) [8](#0-7) , `r.balance` is left unchanged instead of being reduced for the overage, while `AddSpent` still records the higher true spend — repeating this over multiple steps increases the divergence between `r.balance` (available-for-further-deduction) and the credits truly reserved from billing.

func (bs *balanceStore) convertToBalance(fromResourceType string, amount decimal.Decimal) (decimal.Decimal, error) {
	rate, ok := bs.conversions[fromResourceType]
	if !ok {
		return amount, ErrResourceTypeNotFound
	}

	// Special case for gas as gas token conversions are provided in amount per credit.
	// Other rates are provided as the inverse.
	if isGasSpendType(fromResourceType) {
		if rate.IsZero() {
			return decimal.Zero, nil
		}

		return amount.Div(rate).Round(defaultDecimalPrecision), nil
	}

	return amount.Mul(rate), nil
}

// Add increases the current credit balance.
func (bs *balanceStore) Add(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	bs.balance = bs.balance.Add(amount)

	return nil
}
