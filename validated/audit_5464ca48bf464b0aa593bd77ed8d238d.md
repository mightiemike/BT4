### Title
Arbitrary, unverified `new_seed` in a winning `LeaderBlockCommitOp` lets the round-N winner grind the round-(N+1) sortition outcome - (File: `stackslib/src/chainstate/burn/sortition.rs`)

### Summary
`BlockSnapshot::sample_burn_distribution` (sortition.rs:122-149) and `select_winning_block` (sortition.rs:192-220) select the next tenure's winner using `sortition_hash.mix_VRF_seed(VRF_seed)`, where `VRF_seed` is the raw `new_seed` field taken verbatim from the *current* round's winning `LeaderBlockCommitOp`. Neither the burn-op-level checks in `leader_block_commit.rs` nor the sortition-processing code in `sortition.rs` verify at this stage that `new_seed` is the hash of a real VRF proof; that check (`NakamotoChainState::validate_vrf_seed`, nakamoto/mod.rs:1680-1712) only runs later, when a child Stacks block is validated. This lets the operator who wins round N pick an arbitrary 32-byte `new_seed`, biasing which candidate wins round N+1, at the cost of orphaning their own round-N tenure.

### Finding Description
The claimed equality is: `P(miner M wins sortition round N+1) == burn_fee(M) / total_burns(round N+1)`, independent of any other participant's behavior in round N.

Trace:
- `sortition.rs:189-191` explicitly documents: *"the VRF seed is not guaranteed to be the hash of a valid VRF proof. Miners would only build off of leader block commits for which they (1) have the associated block data and (2) the proof in that block is valid."*
- `select_winning_block` (sortition.rs:192-220) fetches `vrf_seed` via `get_last_vrf_seed` (sortition.rs:155-179), which simply reads `winning_block.new_seed` from the DB — the field the round-N winner supplied in their commit, with no cryptographic tie enforced yet.
- `sample_burn_distribution` (sortition.rs:122-149) computes `index = sortition_hash.mix_VRF_seed(VRF_seed).to_uint256()` and walks the burn-weighted ranges to find the winner — this happens purely as a function of burnchain data at burn-block-processing time, independent of any Stacks-block download or validation.
- After the winner for round N is picked, `sortition.rs:713-715` mixes `winning_block.new_seed` into `next_sortition_hash`, which becomes the seed input for round N+1. This happens unconditionally, before anyone confirms the round-N winner will ever produce a valid Nakamoto block.
- The only place `new_seed` is checked against a real VRF proof is `NakamotoChainState::validate_vrf_seed` (nakamoto/mod.rs:1680-1712) and `check_normal_coinbase_tx` (nakamoto/mod.rs:1808-1856), both of which run during *Stacks block* acceptance, on the round-N miner's own subsequently-produced block — not during burnchain-level sortition processing.
- `leader_block_commit.rs`'s op-level `check_intended`/related validators (confirmed via search) do not reference `new_seed` at all; nothing at commit-acceptance time constrains its bits.

Root cause: sortition winner selection for round N+1 is finalized on the burnchain independent of and prior to any check that round N's declared seed corresponds to a real VRF proof. The guard that exists (`validate_vrf_seed`) only protects the *Stacks* fork-choice (no one will build a valid child block on a tenure whose seed was faked), but it does not roll back or invalidate the *sortition* selection already recorded for round N+1. The burnchain-level VRF-seed chaining and the Stacks-block VRF-proof chaining are decoupled, so the equality above is broken: an attacker who wins round N (at their fair burn-weighted probability) can subsequently pick `new_seed` freely (full 256-bit choice) to bias which point in the round-N+1 burn distribution gets selected, at the cost of sacrificing their own round-N tenure (since their own tenure will become an unbuildable orphan once the mismatch is discovered by other nodes validating children).

### Impact Explanation
This is a minority-triggerable sortition divergence (matches the "High" bucket): a single winning miner in round N can shift the probability of who wins round N+1 away from pure burn-weighted proportionality, without needing majority stake or any privileged role. It does not itself cause a chain split (all honest nodes compute the same burnchain-derived sortition winner for round N+1 deterministically from the same `new_seed`), but it breaks the fairness guarantee of the sortition algorithm and can be used to favor a colluding participant (or a resubmitted commit by the attacker) in the very next round. The attacker forfeits their own round-N tenure/reward as the cost of the attack (since the tenure they win becomes an unbuildable orphan under the arbitrary seed), bounding — but not eliminating — the incentive to do this.

### Likelihood Explanation
Preconditions: attacker must win the round-N sortition, which occurs at their normal fair, burn-proportional probability (no majority stake needed — even a minority miner occasionally wins a round). No leader-key proof validity is required at commit-broadcast time. The attacker can freely choose all 256 bits of `new_seed` in their `LeaderBlockCommitOp`, since neither `leader_block_commit.rs` op checks nor `sortition.rs`'s winner-selection logic constrain it. The only cost is that the attacker's own round-N tenure will be unbuildable once nodes attempt to validate any child block against it (`validate_vrf_seed` will fail), so this is a self-sacrificing, one-shot-per-round bias attempt, repeatable every time the attacker (or a colluder) wins a round.

### Recommendation
Do not use an unverified `new_seed` for burnchain-level sortition-hash chaining. Options: (a) require the block-commit operation to include/verify a valid VRF proof against the announced leader key at burn-op-acceptance time (moving proof verification earlier, before the seed is used to compute the next round's sortition), or (b) decouple sortition winner-selection determinism from the free-form `new_seed` bits, e.g. by deriving the next round's mixing input from a value that cannot be chosen without a proof (such as requiring `new_seed` to be verifiable directly during `check_block_commit_vrf_seed`/burn-op processing rather than deferring to Stacks-block validation).

### Proof of Concept
Rust integration test plan (extending `stackslib/src/chainstate/coordinator/tests.rs` or `stackslib/src/burnchains/tests/burnchain.rs` harness):
1. Set up a burnchain/sortition-db test harness with N miners, assign fixed burn amounts so each miner's fair win probability is known (`burn_fee(M)/total_burns`).
2. For one miner (attacker), have their `LeaderBlockCommitOp::new_seed` always be a fixed/adversarial value (not derived from a real VRF proof) whenever they win a round; never submit the corresponding Nakamoto block (or submit an invalid one) so their tenure is orphaned.
3. Run many simulated rounds (e.g., 10,000) and record, for rounds immediately following an attacker win, the empirical win distribution of round N+1 vs. each candidate's `burn_fee/total_burns` share.
4. Assert `abs(empirical_win_rate(candidate) - fair_share(candidate)) < epsilon` for a control run (no adversarial seed) and show it fails to hold (deviation exceeds statistical noise bound) for the adversarial-seed run, thereby demonstrating the equality `P(win round N+1) == burn_fee_share` is violated only in the adversarial case, and that this bias exists independent of the attacker's own tenure ever being accepted (confirm via `validate_vrf_seed` returning `Err` for the attacker's orphaned tenure while `sample_burn_distribution` for round N+1 still used the adversarial seed).
