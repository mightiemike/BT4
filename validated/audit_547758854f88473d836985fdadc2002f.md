### Title
Front-runnable, sender-unchecked `BatchProofMethodId` processing lets an attacker permanently drop an authorised intermediate method-id upgrade - ([File: crates/light-client-prover/src/circuit/mod.rs])

### Summary
`LightClientProofCircuit::run_l1_block` accepts any `DataOnDa::BatchProofMethodId` blob as long as the council's 3-of-5 signature over the body verifies — it never checks `blob.sender()`, unlike the `Complete`/`Aggregate`/`SequencerCommitment` branches. Because the signed body has no ordering nonce beyond `activation_l2_height`, an attacker who observes a council-signed higher-height update (e.g. B, height 200) in the public mempool can copy it verbatim into their own inscription and get it mined before the council's lower-height update (A, height 100) is confirmed, causing A to be silently and permanently dropped.

### Finding Description
Binding claimed: for every accepted entry, `(activation_l2_height, method_id) ∈ BatchProofMethodIdAccessor == sequence intended by security council`. This is broken by DA-transaction-order manipulation.

Code path in `crates/light-client-prover/src/circuit/mod.rs`:
- The `BatchProofMethodId` branch has **no `blob.sender()` check**, unlike the other three variants: [1](#0-0) 
- Acceptance only requires `activation_l2_height > last_activation_height` (taken from `batch_proof_method_ids.last()`, i.e. append-order, not intended semantic order) and a valid council signature over `body.serialize()`: [2](#0-1) 
- `BatchProofMethodIdAccessor::insert` merely `push`es onto the vector with no reordering or backfill logic: [3](#0-2) 
- `verify_method_id_security_council` validates only the signatures/pubkey-index structure of the body — it is fully independent of which DA transaction, sender, or block carries it: [4](#0-3) 

Exploit flow:
1. Security council prepares two genuine updates: A `{activation_l2_height:100, method_id_A}` and B `{activation_l2_height:200, method_id_B}`, each with valid 3-of-5 signatures over the borsh-serialized body.
2. Council broadcasts B's reveal transaction (or it otherwise becomes visible pre-confirmation, e.g. in mempool).
3. Attacker (no privileged key required — the body+signatures are public data, not tied to any specific UTXO/txid) copies B's exact `body` + `signatures_with_index` bytes into their **own** reveal transaction and pays higher fees to get it mined in an earlier block than A's genuine transaction.
4. `run_l1_block` processes B before A (across sequential L1 blocks, or within one block if ordering allows). It inserts `(200, method_id_B)`.
5. When A's genuine transaction later confirms, `100 <= last_activation_height (200)` is true, so A is skipped via `continue` and is **never** inserted.
6. Consequence: for `process_complete_proof`, `BatchProofMethodIdAccessor` now holds `[(0, old), (200, method_id_B)]`. Any batch proof whose `last_l2_height` falls in `[100,199]` resolves via `binary_search_by_key` to the **old** method id, not `method_id_A`, per: [5](#0-4) 
This causes genuine proofs generated with `method_id_A` semantics to fail ZK verification (an authorised, true state transition becomes unprovable) for the entire L2 height window the council intended A to cover.

No existing guard catches this: there is no sender restriction, no monotonic/queue enforcement tied to council intent, and no re-check/backfill of skipped lower-height updates once a higher one lands.

### Impact Explanation
The council's intermediate method-id upgrade A never activates — it is permanently and silently dropped from `BatchProofMethodIdAccessor`. Any batch proof relying on `method_id_A` for L2 heights [100,199) becomes unverifiable by all full nodes and light client provers (a true state transition made unprovable), or, if the old method id circuit accepts different validity constraints than A's, could open a divergent verification path. This is a Critical-class impact ("a batch or light client proof accepted for a state transition that did not happen or a true one made unprovable"), affecting every full node and prover following the chain, and it is a one-shot but permanent corruption of protocol state (repeatable for any subsequent multi-update council rollout under the same conditions).

### Likelihood Explanation
Preconditions: two genuine council-signed updates queued with different activation heights; the higher one becomes observable (mempool/broadcast) before the lower one confirms. The attacker only needs read access to the public Bitcoin mempool and the ability to pay fees to inscribe/mine their own reveal transaction — both are explicitly in-scope unprivileged capabilities. No key compromise or majority hashrate is needed since the signed body is copied verbatim and the branch performs no sender check. Feasibility is high in any period where the council issues more than one queued upgrade close together in time; cost is limited to standard Bitcoin transaction fees to front-run by one confirmation.

### Recommendation
Enforce that `BatchProofMethodId` updates are applied in the exact order intended by the council rather than DA-arrival order — e.g., require monotonic activation heights AND either (a) reject/queue out-of-order updates until all lower pending activation heights have been consumed, or (b) have the council commit to an ordered, position-bound sequence (e.g., include a strictly incrementing sequence number in the signed body, separate from `activation_l2_height`, that must be consumed in order) so a later-height update cannot be inserted before an earlier one it depends on.

pub fn verify_method_id_security_council(
    initial_da_pubkeys: [[u8; SECURITY_COUNCIL_COMPRESSED_PUBKEY_SIZE];
        SECURITY_COUNCIL_MEMBER_COUNT],
    msg: &[u8],
    signatures_with_idx: &[([u8; SECURITY_COUNCIL_SIGNATURE_SIZE], u8);
         SECURITY_COUNCIL_SIGNATURE_THRESHOLD],
) -> bool {
    // EIP-191 prefix + keccak256 → 32-byte prehash
    let prehash = eip191_hash_message(msg);

    // Check that signature indices are within bounds
    for &(_, index) in signatures_with_idx {
        if index >= 5 {
            log!("Invalid signature index: {}", index);
            return false;
        }
    }

    // Make sure the indexes are in ascending order to prevent duplicates
    for i in 0..signatures_with_idx.len() - 1 {
        if signatures_with_idx[i].1 >= signatures_with_idx[i + 1].1 {
            log!(
                "Signature indices are not in ascending order, failing indices: {}, {}",
                signatures_with_idx[i].1,
                signatures_with_idx[i + 1].1
            );
            return false;
        }
    }

    for signature_with_idx in signatures_with_idx.iter() {
        let signature = signature_with_idx.0;
        let pubkey_idx = signature_with_idx.1;
        let const_pubkey = initial_da_pubkeys[pubkey_idx as usize];

        // ensure the inscription pubkey matches the expected constant (compressed 33B)
        let verifying_key = VerifyingKey::from_sec1_bytes(const_pubkey.as_slice())
            .expect("Initial DA pubkeys must be parsable to k256 VerifyingKey form sec1 bytes");

        let Ok(parsed_sig) = Signature::from_bytes(&signature.into()) else {
            log!("Invalid signature format");
            return false; // invalid signature format, fail
        };

        // verify prehash with the matching verifying key
        if verifying_key
            .verify_prehash(prehash.as_slice(), &parsed_sig)
            .is_err()
        {
            log!("Signature verification failed for index: {}", pubkey_idx);
            return false;
        }
    }

    true
