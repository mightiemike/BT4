### Title
Duplicate witness votes are not merged in `VoteWitnessActuator`, causing unbounded duplicate `Vote` entries in `AccountCapsule` - ([File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java])

### Summary
`VoteWitnessActuator.validate()` only checks that `contract.getVotesCount() <= MAX_VOTE_NUMBER` and that the total voting power sum does not exceed `tronPower`, but it never deduplicates votes by witness address. `countVoteAccount()` (called from `execute()`) then blindly iterates the raw `Votes` list and calls `accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount())` for every entry, unlike the TVM native contract path `VoteWitnessProcessor.execute()`, which explicitly merges votes per witness address into a `HashMap` before writing them to the account.

### Finding Description
In `VoteWitnessActuator.validate()` (actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java:98-121), the loop over `contract.getVotesList()` only validates each vote's address/count and accumulates a `sum` via `LongMath.checkedAdd` for the total tronPower check — it does not deduplicate by `witnessCandidate`. An attacker can submit a single `VoteWitnessContract` with up to `MAX_VOTE_NUMBER` `Vote` entries all pointing at the same witness address, each with a small `voteCount`, so the aggregate `sum` stays within their `tronPower`.

In `countVoteAccount()` (lines 152-191), `voteContract.getVotesList().forEach(...)` calls `accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount())` once per raw entry with no merge-by-address step, so the resulting `AccountCapsule` can end up with `MAX_VOTE_NUMBER` separate `Vote` protobuf entries for the same witness, rather than a single merged entry.

By contrast, `VoteWitnessProcessor.execute()` (actuator/src/main/java/org/tron/core/vm/nativecontract/VoteWitnessProcessor.java:54-108) builds a `Map<ByteString, Long> voteMap` and merges vote counts per witness address before calling `accountCapsule.addVotes` once per unique witness — demonstrably the "correct" invariant-preserving behavior that the actuator path fails to replicate. ### Impact Explanation
This causes on-chain state bloat: an unprivileged account can produce an `AccountCapsule` with up to `MAX_VOTE_NUMBER` redundant `Vote` entries pointing to the same witness, instead of a single merged entry, inflating the serialized size of that account's protobuf state stored via `accountStore.put(...)`. This is a state growth / accounting-invariant violation (one logical vote per witness should not require multiple entries) and produces behavioral divergence between the normal transaction actuator path and the TVM native-contract vote path for functionally identical inputs — a consensus/data-model inconsistency risk, since two logically identical vote intents produce different serialized account states depending on which entry path was used. It does not, however, allow inflating actual voting power beyond `tronPower` (the sum check still holds), so it is not a fund-theft or double-vote-power bug — the impact is limited to state size/duplication and cross-path inconsistency.

### Likelihood Explanation
Trivially reachable by any account holder: it only requires submitting a normal `VoteWitnessContract` transaction (a public, unprivileged API) with a `Votes` list containing repeated entries for the same witness address, each with `voteCount > 0`, sized up to `MAX_VOTE_NUMBER` and within one's `tronPower`. No special permissions, existing bugs, or race conditions are needed — deterministic and repeatable on every call.

### Recommendation
In `VoteWitnessActuator`, merge votes by witness address before validating and writing them — mirroring `VoteWitnessProcessor.execute()`'s use of a `Map<ByteString, Long>` to sum `voteCount` per unique witness address, both during the `sum`/tronPower check in `validate()` and when calling `accountCapsule.addVotes` / `votesCapsule.addNewVotes` in `countVoteAccount()`.

### Proof of Concept
```java
// In VoteWitnessActuatorTest.java (framework/src/test/java/org/tron/core/actuator/)
@Test
public void voteWitnessActuatorDuplicateWitnessNotMerged() throws Exception {
  // Build a VoteWitnessContract with MAX_VOTE_NUMBER Vote entries,
  // all pointing to the SAME witness address, each with voteCount = 1,
  // such that sum * TRX_PRECISION <= account tronPower.
  VoteWitnessContract.Builder builder = VoteWitnessContract.newBuilder()
      .setOwnerAddress(ByteString.copyFrom(ownerAddress));
  for (int i = 0; i < ChainConstant.MAX_VOTE_NUMBER; i++) {
    builder.addVotes(Vote.newBuilder()
        .setVoteAddress(ByteString.copyFrom(witnessAddress))
        .setVoteCount(1)
        .build());
  }
  VoteWitnessActuator actuator = new VoteWitnessActuator();
  actuator.setChainBaseManager(chainBaseManager);
  actuator.setAny(any.pack(builder.build()));

  actuator.validate();
  TransactionResultCapsule ret = new TransactionResultCapsule();
  actuator.execute(ret);

  AccountCapsule accountCapsule = accountStore.get(ownerAddress);
  // BUG: expect a single merged Vote entry for the witness with voteCount = MAX_VOTE_NUMBER,
  // but actuator produces MAX_VOTE_NUMBER separate entries.
  assertEquals(1, accountCapsule.getVotesList().size()); // FAILS: actual size == MAX_VOTE_NUMBER
}
```
Differential comparison: run the equivalent scenario through `VoteWitnessProcessor.execute()` with a `VoteWitnessParam` containing the same duplicated votes, and assert `accountCapsule.getVotesList().size() == 1` there (passes), confirming the actuator path diverges from the TVM native contract path.
