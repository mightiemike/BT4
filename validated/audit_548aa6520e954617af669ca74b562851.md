Confirmed vulnerability: `mark_cancellation_request` in `TransactionRecord` (`crates/apollo_l1_events/src/transaction_record.rs`) only guards against a **committed** transaction, not a **consumed** one, so a stale `CancellationStartedOnL2` state can overwrite `Consumed`, mirroring the Dutch-auction bug's core flaw of not clearing/checking a "final" state before allowing a stale mutation.

### Title
Late `TransactionCancellationStarted` L1 event can overwrite a `Consumed` L1-handler tx state, reviving a spent transaction as cancellable/proposable - (File: crates/apollo_l1_events/src/transaction_record.rs)

### Summary
`TransactionRecord::mark_cancellation_request` only checks `is_committed()` before transitioning state to `CancellationStartedOnL2`, but does not check `is_consumed()`. If the `TransactionConsumed` L1 event for a hash is scraped/applied before (or its committed-flag path bypassed relative to) a late-arriving `TransactionCancellationStarted` event for the same `tx_hash`, the record's `state` (which was `Consumed`) gets unconditionally overwritten to `CancellationStartedOnL2`, silently discarding the `Consumed` marker from the state machine's authoritative field (`consumed_at` remains set, but `state` no longer reflects it).

### Finding Description
`TransactionRecord::mark_cancellation_request` (`crates/apollo_l1_events/src/transaction_record.rs:77-101`):
```rust
pub fn mark_cancellation_request(&mut self, timestamp: BlockTimestamp) -> Option<BlockTimestamp> {
    ...
    if self.is_committed() {
        warn!(...); // no-op, state preserved
    } else {
        info!(...);
        self.state = TransactionState::CancellationStartedOnL2;
    }
    ...
}
```
`is_committed()` (line 159-161) only returns true when `state == Committed`. It does **not** consider `state == Consumed`. `is_consumed()` (line 169-171) exists as a distinct predicate but is never consulted here.

This is directly analogous to the Dutch-auction bug: the auction-settlement path is the *one* flow that fails to invalidate/clear residual bid state before it can be reused, letting a subsequent, logically-stale operation (`cancelBidForNFT`) act on data that should have been purged. Here, `Consumed` is the "terminal, already-settled" state for an L1 handler transaction (`is_validatable` at line 179-181 excludes `is_consumed()` transactions from validation), but `mark_cancellation_request` doesn't defend that terminal state, letting a later `TransactionCancellationStarted` event silently flip `state` back to `CancellationStartedOnL2`, and — after the L2 cancellation timelock elapses via `update_time_based_state` (lines 191-208, which only checks `cancellation_requested_at`/`committed`, not `consumed_at`) — onward to `CancelledOnL2`.

Downstream effects in `TransactionManager` (`crates/apollo_l1_events/src/transaction_manager.rs`):
- `validate_tx` (lines 116-145) determines rejection reason strictly from `record.state`: a tx now sitting in `CancelledOnL2` (having actually been `Consumed`/executed) reports `InvalidValidationStatus::CancelledOnL2` instead of `ConsumedOnL1`, corrupting the provider's reported reason and potentially the state semantics relied on by consensus validation flows (`docs/diagrams/06-l1-handler-flow.md` validation flow, lines 112-160), since the two invalid reasons are treated identically by callers but the underlying accounting (`consumed_at`) vs. `state` are now inconsistent.
- `maintain_indices` (lines 377-429) re-derives `proposable_index` and `consumed_queue` membership from `record.get_consumed_at_timestamp()`/`record.is_proposable()`; since `consumed_at` is untouched, the tx remains in `consumed_queue`, but its `state` no longer says `Consumed`, so any logic keyed off `state` (e.g., the panic/log paths in `add_events` at `l1_events_provider.rs:177-186`, or a repeated `TransactionConsumed` event for the same hash) will misbehave: `consume_tx` in `transaction_manager.rs:247-272` only guards double-consumption via `get_consumed_at_timestamp()`, which is unaffected, so a second `TransactionConsumed` event for the same (now `CancelledOnL2`) tx_hash would still correctly be rejected as double consumption — but any component trusting `record.state` alone for "has this L1 message already been executed" (e.g. snapshot/monitoring code at `transaction_manager.rs:298-339`) will misclassify an executed tx as `cancelled_on_l2`, an invariant violation the code's own comments (e.g. line 231-234 in `finalize_cancellation`) treat as "not supposed to happen."

### Impact Explanation
This breaks the state machine's invariant that a `Consumed` (executed) L1 handler transaction can never transition again. While `get_txs`/staging logic (gated by `is_proposable()` == `Pending`) prevents outright double-execution of the L1Handler tx in a new block, the corrupted `state` field causes incorrect validation-failure reasons and an inconsistent snapshot (`consumed` vs `cancelled_on_l2` buckets), which can propagate into observability/monitoring and any logic that branches on `TransactionState` rather than `consumed_at`. This falls short of a directly provable "loss of funds" or block-hash divergence purely from the code paths visible here; the confirmed, concrete defect is a state-machine consistency violation (mislabeling an executed transaction as cancelled) reachable purely via ordering of two L1-originated events for the same `tx_hash`, which is not attacker-controlled from a single L2 transaction, contract call, declared class, or L1 message in the way required by the validation rules (it depends on the *order* the L1 scraper delivers events, not on state directly triggerable by a malicious L2 sender). It does not, on the evidence found, unambiguously satisfy "concrete loss or permanent freezing of funds, unauthorized account action, wrong committed root/block hash, or honest-node divergence" because both nodes process the same ordered event stream deterministically (no honest-node divergence), and the "committed" guard already blocks the analogous risk once a tx enters the truly authoritative `Committed`/mempool inclusion path.

### Likelihood Explanation
Low-to-moderate: requires a `TransactionConsumed` event to be scraped/applied for a tx_hash, followed later by a `TransactionCancellationStarted` event for the *same* hash — an ordering that is unusual (cancellation on L1 for a message already consumed on L1 should not normally occur from the L1 core contract's own semantics), but the code contains no explicit reachability check preventing it, and the guard that exists (`is_committed()`) does not cover this case.

### Recommendation
In `TransactionRecord::mark_cancellation_request` (and in `update_time_based_state`), also check `self.is_consumed()` (or a broader "is terminal" helper covering both `Committed` and `Consumed`) before allowing the transition to `CancellationStartedOnL2`, so a `Consumed` transaction's `state` is never overwritten, mirroring the recommendation to never let a "settled" state be mutated by a stale/no-longer-relevant follow-up action.

### Proof of Concept
1. L1 scraper emits `Event::L1HandlerTransaction` for `tx_hash = H`; provider calls `tx_manager.add_tx` → record `H` created, `state = Pending`.
2. L1 scraper emits `Event::TransactionConsumed { tx_hash: H, timestamp }`; provider calls `tx_manager.consume_tx(H, ...)` → `record.mark_consumed` sets `state = Consumed`, `consumed_at = Some(t)`.
3. L1 scraper later emits `Event::TransactionCancellationStarted { tx_hash: H, cancellation_request_timestamp }` (e.g., a delayed/out-of-order log from an L1 reorg or scraper batching); `add_events` (`l1_events_provider.rs:144-168`) checks only `tx_manager.exists(H)` (true) and calls `request_cancellation` → `mark_cancellation_request` sees `is_committed() == false` (since state is `Consumed`, not `Committed`) and unconditionally sets `state = CancellationStartedOnL2`.
4. After `l1_handler_cancellation_timelock_seconds` elapses, any call touching this record via `update_time_based_state` (invoked from `validate_tx`) transitions `state` to `CancelledOnL2`.
5. Snapshot (`transaction_manager.rs:298-339`) now buckets `H` under `cancelled_on_l2` even though it was actually consumed/executed, and `validate_tx` reports `InvalidValidationStatus::CancelledOnL2` instead of `ConsumedOnL1` for any node re-validating `H`.     /// Mark a cancellation request for this transaction.
    /// Returns the existing cancellation timestamp if one exists, `None` if this is the first
    /// request.
    pub fn mark_cancellation_request(
        &mut self,
        timestamp: BlockTimestamp,
    ) -> Option<BlockTimestamp> {
        let tx_hash = self.tx.tx_hash();
        // Once committed on L2, cancellation requests are only recorded for debugging purposes, but
        // not processed.
        if self.is_committed() {
            warn!(
                "L1 handler transaction {tx_hash} was not marked for cancellation started on L2 \
                 as it is already committed."
            )
        } else {
            info!("Marking L1 handler transaction {tx_hash} as cancellation started on L2.");
            self.state = TransactionState::CancellationStartedOnL2;
        }

        match self.cancellation_requested_at {
            Some(existing) => Some(existing),
            None => {
                self.cancellation_requested_at = Some(timestamp);
                None
            }
        }
    }

    /// The timestamp is the L1 block timestamp where this tx was marked consumed.
    /// If tx was not already consumed (expected result), return None.
    /// If tx was already consumed (double consumption), return the time when it was previously
    /// consumed. Note that double consumption is a bug.
    pub fn mark_consumed(&mut self, timestamp: BlockTimestamp) -> Option<BlockTimestamp> {
        if self.is_committed() {
            debug!("Marking a committed transaction {} as consumed.", self.tx.tx_hash());
        } else {
            // TODO(guyn): check if this situation should be an error.
            // TODO(guyn): check other state combinations that may be worth an error/warning/debug
            // log.
            debug!(
                "Marking a non-committed transaction {} as consumed. Previous state: {:?}",
                self.tx.tx_hash(),
                self.state
            );
        }
        self.state = TransactionState::Consumed;
        // First check if the tx was already consumed. Double consumption is a bug!
        // If None, it wasn't previously consumed: mark the time and return None to signal
        // everything is ok. If Some, it was already consumed: report the time when it was
        // previously consumed, the caller decides what to do.
        match self.consumed_at {
            Some(existing) => Some(existing),
            None => {
                self.consumed_at = Some(timestamp);
                None
            }
        }

    /// Answers whether any node can include this transaction in a block. This is generally possible
    /// in all states in its lifecycle, except after it had already been added to block, or a short
    /// time after it's cancellation was requested on L1. In particular, this includes states
    /// like: a rejected transaction, a new timelocked transaction, a
    /// transaction whose cancellation was requested on L1 too recently (there will be a
    /// timelock for this).
    pub fn is_validatable(&self) -> bool {
        !self.is_committed() && !self.is_cancelled() && !self.is_consumed()
    }

    pub fn is_staged(&self, epoch: StagingEpoch) -> bool {
        self.staged_epoch == epoch
    }

    pub fn get_consumed_at_timestamp(&self) -> Option<BlockTimestamp> {
        self.consumed_at
    }

    /// Update the state of the record based on the current time and policy.
    /// This updates the state based on time-based state transitions, such as moving from
    /// CancellationStartedOnL2 to CancelledOnL2 after the timelock expires.
    pub fn update_time_based_state(&mut self, unix_now: u64, policy: TransactionRecordPolicy) {
        if let Some(requested_at) = self.cancellation_requested_at {
            if self.committed {
                return; // Committing overrides cancellations.
            }

            let cancellation_timelock = &policy.cancellation_timelock.as_secs();
            let is_cancellation_timelock_passed =
                unix_now >= *requested_at.saturating_add(cancellation_timelock);

            if is_cancellation_timelock_passed {
                self.state = TransactionState::CancelledOnL2;
            }
        }
    }
}

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),

            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())

    pub fn consume_tx(
        &mut self,
        tx_hash: TransactionHash,
        consumed_at: BlockTimestamp,
        unix_now: u64,
    ) -> Result<(), BlockTimestamp> {
        self.clear_old_tx_from_consumed_queue(unix_now);

        let Some(record) = self.records.get(&tx_hash) else {
            debug!(
                "Attempted to consume an unknown transaction: {tx_hash}. This can happen if the \
                 transaction was too old to be scraped (e.g. it was created before we started \
                 scraping)."
            );
            return Ok(());
        };

        // Double consumption is a bug.
        if let Some(previously_consumed_at) = record.get_consumed_at_timestamp() {
            return Err(previously_consumed_at);
        }

        // Mark the transaction as consumed.
        self.with_record(tx_hash, |record| record.mark_consumed(consumed_at));
        Ok(())
    }
