## Finding: `ensure_match_transaction_info` never validates the state-checkpoint root, silently blinding the primary mainnet replay-verification tool

### Title
Replay verification accepts a diverging state root as valid because `TransactionOutput::ensure_match_transaction_info` skips `state_checkpoint_hash` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to check that a freshly re-executed transaction matches the authenticated `TransactionInfo` committed on-chain. It checks status, gas used, write-set hash, and event root hash, but it never checks `state_checkpoint_hash` (the JMT/state root), `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. `storage/db-tool/src/replay_on_archive.rs` — the tool driven in CI by `testsuite/replay-verify/main.py` against testnet/mainnet archives — relies exclusively on this function to decide whether a replay of historical mainnet transactions is correct, and never independently recomputes or compares any state-root value. As a result, a bug that corrupts the JMT/state-checkpoint computation while leaving the write set and events untouched would be reported as a passing replay.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  validates transaction status, gas used, the write-set hash (`state_change_hash`), and the event root hash against the committed `TransactionInfo`. The trailing comment in the same function explicitly documents the gap: [2](#0-1) 

This function is consumed in two places:
1. `execution/executor/src/chunk_executor/mod.rs::verify_execution`, at [3](#0-2) . In this path the gap is largely mitigated because the caller later runs the full commit pipeline (`update_ledger` → `DoStateCheckpoint::run()`), which does independently validate the checkpoint hash against `known_state_checkpoints` from the trusted `TransactionInfo`s, as seen in [4](#0-3) .
2. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, at [5](#0-4) . This tool executes blocks directly via `AptosVMBlockExecutor` and compares outputs *solely* through `ensure_match_transaction_info` — it never invokes `DoStateCheckpoint` or otherwise computes/compares a JMT root; a repo-wide search confirms `state_checkpoint_hash` is never referenced anywhere under `storage/db-tool/`. This tool is exactly the one invoked by the production replay-verify pipeline: `testsuite/replay-verify/main.py`'s `WorkerPod.start()` launches `aptos-debugger aptos-db replay-on-archive` against real network archive data, as seen in [6](#0-5) .

So in the `replay-on-archive` path, there is no second layer of protection: a bug anywhere in JMT construction, state-checkpoint materialization, hot-state root computation, or position-state root computation that leaves the write set (`state_change_hash`) intact but produces a wrong `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` will not be detected by this tool, even though the on-chain `TransactionInfo` (and hence the transaction accumulator/ledger info that light clients and API responses are proven against) carries the authenticated correct root.

### Impact Explanation
`replay_on_archive` is the canonical mainnet/testnet replay-verification job run in CI to catch state-commitment divergence bugs before/after protocol changes. Because it structurally never compares the state-checkpoint root, a state-root computation bug (e.g., in the JMT update logic, buffered-state/hot-state root computation, or the newer position/trading-native root path referenced by the TODO) could pass full replay-verify green while silently producing a wrong state root relative to the authenticated ledger. Such a bug is exactly the class of "Committed state that differs from correct VM result" / "wrong accumulator/Merkle proof accepted as valid" hard-fork-class divergence this scan targets, and this tool's blind spot means the safety net designed to catch it would not.

### Likelihood Explanation
This requires no external attacker — it is a latent gap in the verification tool's own comparator. Any future change (already flagged in-code via the `TODO(trading-native)` note tied to `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that introduces a state/hot-state/position root computation bug will not be caught by `replay-on-archive`, regardless of how carefully the write-set/event logic is reviewed. The likelihood of the underlying root-computation bug is independent of this report, but the detection gap itself is proven directly by the code (the TODO comment plus the absence of any `state_checkpoint_hash` reference in `storage/db-tool`).

### Recommendation
Extend `ensure_match_transaction_info` (or add a parallel check invoked specifically by `replay_on_archive.rs`) to compare the computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields of the expected `TransactionInfo`, mirroring the check already performed by `DoStateCheckpoint::get_state_checkpoint_hashes`. This should be done before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled, as the existing TODO comment recommends, and `replay_on_archive.rs` should be updated to actually compute/track state-checkpoint roots per chunk rather than relying only on `ensure_match_transaction_info`.

### Proof of Concept
1. `ensure_match_transaction_info` at [7](#0-6)  only asserts on `write_set_hash` and `event_root_hash`; it returns `Ok(())` without inspecting `state_checkpoint_hash`.
2. `Verifier::execute_and_verify` in `replay_on_archive.rs` executes a block and calls `ensure_match_transaction_info` per transaction with no other output validation: [8](#0-7) .
3. A search for `state_checkpoint_hash` across `storage/db-tool/**` returns no matches, confirming no independent root check exists in this tool.
4. `testsuite/replay-verify/main.py` invokes exactly this binary/subcommand against real network archives in CI: [6](#0-5) .
5. Therefore, any transaction whose write set and events are correctly reproduced, but whose resulting state-checkpoint/hot-state/position root diverges from the authenticated on-chain value, would cause `replay_on_archive` to report success.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
