### Title
Wallet Contract permanently locks excess `attached_deposit` from external callers on successful `rlp_execute` calls - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `rlp_execute` method is `#[payable]` and accepts an arbitrary `attached_deposit` from any external caller (e.g., a relayer). This deposit amount is never checked against, or reconciled with, the actual payment amount required by the wallet's underlying action (which is entirely determined by the Ethereum transaction's `value`/`yocto_near` fields, decoded independently in `internal.rs`). If the call succeeds, the wallet contract has no logic to refund any unused/excess portion of the attached deposit back to the caller — the excess funds are simply absorbed into the wallet contract's balance with no redemption path for the caller, directly analogous to the reported `buyNFT`/`buyMultipleNFT` bug where excess `msg.value` is locked forever when `paymentToken == WETH`.

### Finding Description
`rlp_execute` is marked `#[payable]` [1](#0-0) , so it accepts any `attached_deposit` from the caller. This deposit is captured into `ExecutionContext::attached_deposit` [2](#0-1) , and wrapped into a `CallerDeposit` struct that records the full amount to be refunded **only if the resulting cross-contract call fails** [3](#0-2) .

Critically, the actual NEAR value transferred by the emulated Ethereum transaction (the analog of `payedAmount` in the report) is computed completely independently, from `tx.value` and the ABI-decoded `yocto_near` field of the transaction data — not from `attached_deposit` at all: [4](#0-3) 

In `rlp_execute_callback`, the refund logic only fires on `PromiseResult::Failed`, refunding the caller's tracked deposit; there is no `Successful` branch that reconciles or refunds any unused portion of the attached deposit: [5](#0-4) 

This is confirmed by the test `test_caller_refunds`: on success, "External caller does not get a refund when their tokens are spent" — the caller's balance drop is `>= deposit_amount`, i.e., the entire attached deposit is consumed by the wallet contract regardless of whether the wallet action required that much: [6](#0-5) 

There is no on-chain mechanism (comparable to `require(msg.value == payedAmount)` in the reported bug) to check that `attached_deposit == 0` (in the common case where no deposit is actually needed by the action) or that it exactly equals whatever balance the action requires. Any relayer/caller who mistakenly (or a griefer targeting itself) attaches excess NEAR to a successful `rlp_execute` call permanently loses that excess to the wallet contract's balance, with no `redeem`/`withdraw` path exposed to that specific caller.

### Impact Explanation
Funds attached in excess of what is strictly required by the relayed action become permanently and irrecoverably absorbed into the target wallet contract's account balance whenever the call succeeds. This is a direct "permanently frozen/locked funds" impact for the caller who over-attached — funds move from the caller to the wallet contract without an equivalent explicit consent to donate that exact excess, and there is no redemption path akin to the deposit refund used on the failure path. Any external relayer service integrating with this contract who miscalculates or is tricked into over-attaching NEAR when submitting a transaction on a user's behalf loses those funds unrecoverably.

### Likelihood Explanation
Likelihood is moderate: this requires an external caller (relayer) to call `rlp_execute` with `attached_deposit` set to something other than exactly what's required and have the underlying action succeed. Since the wallet is specifically designed to support third-party relayers acting on the user's behalf (as shown by `rlp_execute_from` and relayer-refund tests), and the contract API explicitly makes `rlp_execute` payable without documenting the exact amount the caller should attach for the general (non-fee) case, a relayer with an implementation bug (or attaching a "safety margin" deposit) can trigger this at any time via a single transaction call — no privileged access or malicious validator/peer behavior required.

### Recommendation
Add explicit accounting/refund logic in `rlp_execute_callback` for the success path: track how much of the attached deposit was actually required by the resulting action(s) (analogous to `payedAmount`), and refund any leftover back to the original caller (`CallerDeposit.account_id`) in the `PromiseResult::Successful` branch, mirroring the `require(msg.value == payedAmount)` check pattern from the reported analog. Alternatively, document and enforce that `attached_deposit` must be exactly `0` unless it corresponds to a defined fee-payment path, rejecting the call otherwise.

### Proof of Concept
1. Deploy the Wallet Contract for account `alice.near` (eth-implicit) as in `TestContext::new()`.
2. As an external relayer account, call `rlp_execute_from(relayer, target, signed_tx, deposit_amount)` with `deposit_amount` set higher than zero for a signed Ethereum transaction representing e.g. a `FunctionCall`/`Transfer` action that does not itself require any additional NEAR value beyond what's encoded in the RLP tx (`yocto_near`/`tx.value` = 0), following the pattern in `test_caller_refunds` [7](#0-6) .
3. Observe that the relayer's action succeeds (`Successful` branch), and the relayer's account balance decreases by the full `deposit_amount`, none of which is refunded, and the wallet's account balance increases by that unused excess with no way for the relayer to redeem it.

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
