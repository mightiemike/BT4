### Title
Value loss on Exchange/Market liquidity withdrawal and order matching due to floor-division truncation - ([File: chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java])

### Summary
java-tron's built-in Bancor-style `Exchange` (accessed via `ExchangeWithdrawContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`) and the order-book `Market` module both compute counter-token amounts using integer floor division. Any fractional remainder produced by this division is silently discarded rather than credited to the user, exactly analogous to the AMM `lotSize` modulo-truncation issue in the reference report, where a liquidity provider loses value because the leftover from a division/modulo operation is dropped instead of accounted for.

### Finding Description
In `ExchangeWithdrawActuator.execute`/`doValidate`, when a user withdraws liquidity from an `Exchange` pool, the counter-token amount owed is computed as: [1](#0-0) 

using `BigInteger`/`BigDecimal` integer division (`divide`/`divideToIntegralValue`), which floors the result and discards the fractional remainder of the exact ratio `secondTokenBalance * tokenQuant / firstTokenBalance`. That discarded fraction is never returned to the withdrawing user nor tracked anywhere — it simply stays "stuck" as an implicit gain for the remaining pool, the same value-loss pattern described in the report where `amount.sub(amount.mod(lotSize))` discards up to `lotSize - 1`.

The same floor-division pattern appears in `ExchangeInjectActuator.execute`, using `Maths.floorDiv`: [2](#0-1) 

And in the order-book `Market` module, `MarketUtils.multiplyAndDivide` explicitly uses `floorDiv`/`BigInteger.divide` (both truncate toward zero) to compute the exact quantity a taker/maker receives during order matching: [3](#0-2) 

This helper is invoked repeatedly in `MarketSellAssetActuator.matchSingleOrder` to compute `takerBuyTokenQuantityRemain` and `makerBuyTokenQuantityReceive`: [4](#0-3) 

Each match/withdraw/inject truncates the true ratio and discards the fractional remainder, which is never credited to either counterparty; it is effectively absorbed by the pool/order book state.

### Impact Explanation
Each affected transaction (`ExchangeWithdrawContract`, `ExchangeInjectContract`, `MarketSellAssetContract` matching) is broadcastable by any anonymous account. While the amount lost per individual truncation is bounded (at most 1 unit of the smallest token denomination per operation, since these are integer divisions rather than an admin-tunable `lotSize`), it is a systemic, unrecoverable loss of value on every Exchange withdrawal/injection and every Market order match. Over the lifetime of the chain and across many transactions this causes measurable, permanent value leakage from user balances into the AMM/order-book state, with no mechanism to reclaim or account for it. This is an accounting-corruption class issue (funds silently vanish from the economic accounting of the pool) though the magnitude per transaction is small and bounded by integer unit, not attacker-controlled the way `lotSize` is in the referenced report.

### Likelihood Explanation
This occurs on essentially every non-exact-ratio withdrawal, injection, or partial order match — i.e., very frequently in normal usage, since exact-ratio divisions are the exception rather than the rule when floating-point-like ratios are involved. No privileged role or special conditions are required; it is triggered by ordinary user transactions.

### Recommendation
- Document clearly (in user-facing docs and API descriptions for `ExchangeWithdrawContract`, `ExchangeInjectContract`, and `MarketSellAssetContract`) that up to 1 unit of value may be lost per operation due to integer truncation in the ratio calculations in `ExchangeWithdrawActuator`, `ExchangeInjectActuator`, and `MarketUtils.multiplyAndDivide`.
- Consider whether remainder tracking/accrual (e.g., carrying forward the discarded fractional remainder to the next operation on the same pool/order) is feasible without adding excessive complexity, similar to the alternative recommendation in the referenced report.

### Proof of Concept
Not applicable as a single exploitable transaction — the issue is a systemic floor-division truncation in `ExchangeWithdrawActuator.execute` (lines 79-88), `ExchangeInjectActuator.execute` (lines 73-82), and `MarketUtils.multiplyAndDivide` (lines 264-277) as cited above; any withdrawal/injection/match with a token ratio that does not divide evenly demonstrates the discarded remainder.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
