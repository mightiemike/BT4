No vulnerability found for this question.

**Reasoning:** `get_sequencer_commitment_by_index` in `crates/sovereign-sdk/full-node/sov-ledger-rpc/src/server.rs` is a pure, read-only passthrough: it converts the `U32` index and forwards to `self.ledger.get_sequencer_commitment_by_index(index.to())`, mapping errors via `to_ledger_rpc_error` [1](#0-0) . The underlying `LedgerDB` implementation does a direct keyed lookup on the `SequencerCommitmentByIndex` table and returns `None` for any index that isn't present — there is no arithmetic on the index (unlike `get_l2_block_range`, which does subtract `end - start` and could theoretically overflow/underflow, but even there it's guarded by `uint_try_to()` and a max-range check) [2](#0-1) .

This function does not read or compute any state root, does not perform proof verification, and does not produce or compare an equality between "the root RPC reports as final" and "the root a verified proof commits". It simply serves whatever `SequencerCommitment` was previously written via `put_commitment_by_index` [3](#0-2) , which happens elsewhere in the commitment-processing pipeline (outside this file, and outside the scope of this question). An out-of-range or reversed index simply yields `Ok(None)` — there is no code path here that could cause an honest node to report or persist a state root diverging from a proved chain.

Since the target function performs no state-root computation, no proof verification, and no write, the claimed equality ("state root RPC reports as final" vs. "root a verified proof commits") is never evaluated by this code at all, so it cannot be broken by attacker-controlled index/height parameters.
