### Title
Unbounded linear scan over governance-appended `ENERGY_PRICE_HISTORY` string causes growing per-request CPU cost, reachable from anonymous JSON-RPC calls - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcApiUtil.java])

### Summary
The reported pSTAKE issue is a class of "unbounded loop over an append-only history of a mutable rate/parameter" bug: every time the rate changes, an entry is appended to an array, and every later reward computation walks the *entire* history since last update, so gas cost grows without bound as more changes accumulate. The closest analog in java-tron is `ENERGY_PRICE_HISTORY` (and the sibling `BANDWIDTH_PRICE_HISTORY`), a comma-separated string that is appended to every time an `ENERGY_FEE` proposal is approved, and which is scanned linearly, from the end, on every JSON-RPC price lookup.

### Finding Description
`DynamicPropertiesStore.saveEnergyPriceHistory` appends a new `"expirationTime:price"` entry to the stored history string every time the `ENERGY_FEE` proposal type is approved by governance: [1](#0-0) 

The history is retrieved and parsed in `JsonRpcApiUtil.parseEnergyFee`, which splits the whole string on `,` and then linearly scans from the most recent entry backward until a match is found: [2](#0-1) 

This function is invoked from `Wallet.getEnergyFee(long timestamp)`, documented as being used "after `EnergyPriceHistoryLoader` done", and from `BlockEventGet.getEnergyPrice`: [3](#0-2) [4](#0-3) 

Just like `STokensV2._rewardRate` (an ever-growing array whose full history is walked for every user's pending-reward computation), `ENERGY_PRICE_HISTORY` is an ever-growing, never-truncated string whose entire contents are re-parsed and linearly scanned on every lookup call. The number of loop iterations is proportional to the total number of historical `ENERGY_FEE` proposals ever approved on the network, which only grows over the lifetime of the chain and is never pruned or indexed (no binary search, no checkpointing).

### Impact Explanation
Each call to `parseEnergyFee`/`getEnergyFee(timestamp)` does `String.split(",")` on the entire history plus a full linear scan — an O(n) cost with an additional string-splitting allocation overhead that itself is worse than O(n) in practice. Because this is invoked from JSON-RPC/HTTP request handling paths (via `Wallet.getEnergyFee` and `BlockEventGet.getEnergyPrice`) rather than from TVM-metered execution, there is no energy/gas metering to cap the cost — an attacker cannot be charged extra for expensive calls, and the cost is borne entirely by the node servicing anonymous requests. As the chain's `ENERGY_FEE` proposal history grows over years, every such RPC call becomes proportionally more expensive, which is a form of unbounded resource-accounting growth causing performance degradation / potential DoS on public RPC nodes servicing many requests, especially if callers can force parsing repeatedly (e.g., repeated `eth_gasPrice`-style or receipt/log queries that internally call `getEnergyPrice`).

### Likelihood Explanation
The growth of `ENERGY_PRICE_HISTORY` requires network governance action (an approved `ENERGY_FEE` proposal), so it is not attacker-controlled in the short term, similar to how `setRewardRate` in the reported bug required `DEFAULT_ADMIN_ROLE`. However, unlike the STokens case, this array is never bounded in size and there is no plan (as far as visible in the codebase) analogous to pSTAKE's proposed "binary search + monthly rate cap" fix. Over the multi-year lifetime of a production chain with many historical fee proposals, the linear cost accumulates and is triggered by every unprivileged/anonymous read call, making the likelihood of eventual performance impact high, though the severity at any single point in time is currently modest given the number of historical `ENERGY_FEE` proposals is likely still small.

### Recommendation
- Replace the linear string-split-and-scan history format with an indexed/sorted structure (e.g., a `TreeMap<Long timestamp, Long price>` persisted separately, or binary search over a strictly time-sorted array) so lookups are O(log n) instead of O(n).
- Cap or checkpoint the history (e.g., periodically snapshot/prune entries older than a retention window) to keep the per-call cost bounded, mirroring the pSTAKE Finance team's mitigation of capping historical iteration and using cumulative/indexed lookups instead of walking the full change log.

### Proof of Concept
Not applicable as a live exploit — reproducing the worst case requires simulating many years of `ENERGY_FEE` governance proposals in a testnet to grow `ENERGY_PRICE_HISTORY` to a large size, then repeatedly invoking JSON-RPC calls that route through `Wallet.getEnergyFee(timestamp)` / `BlockEventGet.getEnergyPrice` to observe growing CPU time per call, analogous to the `testRewardAlgorithmBenchmark` test used to benchmark reward computation costs: [5](#0-4) 

I was not able to fully trace every JSON-RPC/HTTP endpoint that calls `getEnergyPrice`/`getEnergyFee(timestamp)` (e.g. exact `TronJsonRpcImpl` method names) within the available tool budget, so the precise list of externally reachable RPC methods triggering this path is not fully confirmed and would need further verification.

```java
  public static long parseEnergyFee(long timestamp, String energyPriceHistory) {
    String[] priceList = energyPriceHistory.split(",");

    for (int i = priceList.length - 1; i >= 0; i--) {
      String[] priceArray = priceList[i].split(":");
      long time = Long.parseLong(priceArray[0]);
      long price = Long.parseLong(priceArray[1]);
      if (timestamp > time) {
        return price;
      }
    }

    return -1;
  }
```

```java
      String energyPriceHistory =
          chainBaseManager.getDynamicPropertiesStore().getEnergyPriceHistory();
      long energyFee = parseEnergyFee(timestamp, energyPriceHistory);

      if (energyFee == -1) {
        energyFee = getEnergyFee();
      }

      return energyFee;
    } catch (Exception e) {
      logger.error("GetEnergyFee timestamp={} failed", timestamp, e);
      return getEnergyFee();
    }
  }
```
