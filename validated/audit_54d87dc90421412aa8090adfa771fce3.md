### Title
`TransactionOutput::ensure_match_transaction_info()` skips checkpoint-hash validation, allowing replay verification to accept a state root that diverges from local execution - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the single-transaction integrity check used by `ChunkExecutorInner::verify_execution()` during replay/restore verification to confirm that locally re-executed VM output matches an already-authenticated `TransactionInfo` (obtained from a backup or from the ledger via a signed proof). The function checks status, gas, write-set hash, event root hash, and transaction hash — but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This mirrors the report's bug class: a settlement/accounting code path that transfers value/records committed data but skips the call that reconciles it against the authoritative accounting (there, `LoanManager.loanLiquidation()`; here, the checkpoint-hash comparison against the recomputed state root).

### Finding Description
`TransactionOutput::ensure_match_transaction_info` at [1](#0-0)  validates status, gas, the write-set hash (`state_change_hash`), and the event root hash against `txn_info`, but the function's own comment admits the gap: [2](#0-1) 

```

// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

This comparator is invoked by `ChunkExecutorInner::verify_execution()` in the backup/replay path: [3](#0-2) 

Here, `execution_output.to_commit.transaction_outputs` (freshly recomputed by re-running the VM over historical transactions) is compared against `transaction_infos`/`write_sets`/`event_vecs` supplied from the backup, purely to detect divergence between local execution and the backup's claimed results — this is the mechanism `db-tool replay-verify` and `TransactionRestoreBatchController` (with `VerifyExecutionMode::Verify`) rely on to catch a corrupted or maliciously-doctored backup/transaction stream before restoring it into a node's ledger. Because the state, hot-state, and position-state checkpoint hashes are never diffed against the recomputed `state_checkpoint_output` hashes (produced in `DoStateCheckpoint`, see `execution/executor/src/workflow/do_state_checkpoint.rs`), a transaction whose committed `TransactionInfo.state_checkpoint_hash` (or `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) does not match what local execution actually produces will still pass `verify_execution` as long as write-set/event/gas/status bytes match. Write-set bytes matching does not guarantee the derived Sparse-Merkle-Tree/JMT root matches, since the checkpoint hash is a function of the *entire accumulated state tree* at that version, not just the individual transaction's write set — divergence could arise from prior-version state corruption, sharded/hot-state computation bugs, or (per the TODO) newly-introduced "trading-native"/position-state computation paths.

### Impact Explanation
Replay-verify is the primary safeguard operators use (`storage/backup/backup-cli` verify command, `db-tool replay-on-archive`) to confirm that a downloaded backup or an alternate execution path reproduces the exact same ledger state before it is trusted/restored. Because checkpoint hashes are excluded from the comparison, this verification can give a false "success" signal even when the actual state root (main state, hot state, or the newer position/native-trading state) diverges from correct VM execution. This directly matches the "Proof and Storage Pivots" invariant that "Accumulators, Jellyfish Merkle structures, versioned state views, and restore paths must preserve deterministic proof binding" — the verification tool that is supposed to catch exactly this kind of divergence is blind to it for the checkpoint-hash fields. A wrong/corrupted state root could therefore be silently accepted as verified and later used as a trust anchor for a restore, producing durable ledger data that differs from the correct VM result without any tooling alarm.

### Likelihood Explanation
The bug is not exploitable by an anonymous network attacker to directly corrupt live consensus state (consensus-path commit still computes and persists its own checkpoint hashes independently), which keeps the severity below a full hard-fork/consensus-safety break. The exposure is specifically in the **verification tooling** used around backup/restore and replay auditing, where the code's own TODO acknowledges the gap is a known, currently-open, unpatched limitation gating the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature. Because it is a documented TODO rather than a silently-introduced defect, likelihood of it being unnoticed forever is lower, but it remains a real, currently present integrity gap in the state-verification code path with no unprivileged trigger requirement other than supplying/verifying a backup whose checkpoint hash doesn't match reality.

### Recommendation
Extend `ensure_match_transaction_info` (or add a parallel check invoked from `verify_execution`) to compare the recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` from `execution_output`/`state_checkpoint_output` against the corresponding fields in the supplied `TransactionInfo`, returning an error on mismatch, before any code path that could rely on "verified" replay results (including gating `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled.

### Proof of Concept
1. Construct (or obtain) a transaction backup/output list whose write set, events, gas, and status match the true VM execution for a given version, but whose `TransactionInfo.state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) has been altered/corrupted so it no longer matches the actual resulting state tree root.
2. Run `db-tool`/`TransactionRestoreBatchController` replay-verify (`VerifyExecutionMode::Verify`) over this data; `ChunkExecutorInner::verify_execution` re-executes the VM and calls `ensure_match_transaction_info` per transaction (`execution/executor/src/chunk_executor/mod.rs:692-705`).
3. Observe that verification reports success (no `Err` raised) because `ensure_match_transaction_info` only checks status/gas/write-set-hash/event-root-hash (`types/src/transaction/mod.rs:2139-2204`) and never diffs the checkpoint hash fields against the freshly computed `state_checkpoint_output` hashes, despite the state root actually diverging — exactly as the in-code TODO states.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
