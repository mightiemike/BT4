### Title
Webhook HMAC only signs the raw body, not the shop/topic headers, allowing cross-tenant forged webhook requests - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
Shopify's webhook HMAC (`X-Shopify-Hmac-Sha256`) is computed and verified only over the raw request body. The `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers are checked only for *presence*, never included in the signed payload. All downstream consumers (`shopify.webhooks.process`, `shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`) trust these unsigned headers to decide which shop's offline session/access token to use and which handler to invoke. An attacker who can obtain one valid `(rawBody, hmac)` pair (e.g. by installing the app on their own store and triggering a real webhook) can replay that exact body/HMAC directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) headers to target a different, victim shop.

### Finding Description
`validateHmacFromRequestFactory` in [1](#0-0)  only validates the HMAC against `rawBody`:
```
const validHmac = await validateHmacString(config, rawBody, hmac, HashFormat.Base64);
```
It never binds the HMAC to `ShopifyHeader.Domain`, `ShopifyHeader.Topic`, or `ShopifyHeader.WebhookId`. The subsequent `checkWebhookHeaders` step (invoked from [2](#0-1) ) only verifies these headers are *present*, not that they were signed.

The resulting `check.domain` (attacker-controlled, unsigned) is then trusted as the shop identity everywhere downstream:
- In `authenticateWebhookFactory` (react-router and remix), `ensureValidOfflineSession(params, check.domain)` is called directly with the unsigned domain, loading and exposing a real `session`/`admin` client for whatever shop the attacker names: [3](#0-2) 
- In the core library's `process()` used by `shopify-app-express`, `webhookCheck.domain` is passed straight into the registered handler callback as the `shop` parameter: [4](#0-3) 
- `webhookCheck.topic` (also unsigned) selects which handler runs: [5](#0-4) 

Because the API secret key (`apiSecretKey`) used to compute the HMAC is the app's single client secret, shared across *all* shops that install the app (not a per-shop secret), any merchant who installs the app can generate a body/HMAC pair that is cryptographically valid for the app regardless of which shop's data it is later claimed to represent. The existing test suite even documents that a cookie-signature/HMAC value can be reused across different `X-Shopify-Shop-Domain` values (see `returns false when a cookie signature is replayed as the webhook HMAC` in [6](#0-5) ), confirming the header/body decoupling is a live design property, not merely theoretical.

This exactly mirrors the report's bug class: one value is what's cryptographically authenticated (the body via HMAC), and a *different*, independently-controlled value (the domain/topic headers) is what actually gets used/trusted for the sensitive downstream action (selecting which tenant's session and access token are used), and the two are never checked for consistency.

### Impact Explanation
An attacker who installs the app on their own (or any) store can:
1. Trigger a real webhook delivery to capture a `(rawBody, hmac)` pair that is valid under the shared app secret.
2. POST that exact body+HMAC directly to the app's public webhook endpoint, overriding `X-Shopify-Shop-Domain` to a victim shop that also has the app installed, and optionally overriding `X-Shopify-Topic` to any topic the app handles (e.g. `APP_UNINSTALLED`, `CUSTOMERS_DATA_REQUEST`, order/billing topics).
3. The library reports `valid: true` and hands the attacker-chosen `domain`/`topic`/attacker-crafted body to the app's handler, which loads the **victim's** real offline session/admin client and executes shop-scoped business logic (data mutation, GDPR data handling, uninstall side effects, etc.) as if it legitimately came from Shopify for the victim shop.

This is a cross-tenant forged-request vulnerability enabling data corruption, unauthorized use of a victim's Admin API access token via webhook-triggered logic, and potential denial of service (e.g. forged `APP_UNINSTALLED` webhooks tearing down victim shop state) — all without ever compromising Shopify's own infrastructure or leaking the API secret.

### Likelihood Explanation
Reachable by any single unprivileged merchant who can install the target app on a store they control — no special access or leaked secrets are required, only a normal app install and a direct HTTP POST to the app's public webhook route. The only friction is guessing/knowing the victim's shop domain and topic pairs the app processes, both of which are commonly discoverable or brute-forceable (`*.myshopify.com` shop names).

### Recommendation
Bind the shop domain, topic, and webhook ID into the signed payload verification (or otherwise cryptographically tie them to the HMAC/body), e.g. by validating that Shopify's HMAC was computed with these header values included, or by independently confirming — via an authenticated Admin API call using the resolved session — that the request truly originates from the claimed shop before trusting `check.domain`/`check.topic` for any privileged action. At minimum, document and warn integrators that `domain`/`topic`/`webhookId` are unsigned and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
```
# 1. Attacker installs the app on their own store "attacker.myshopify.com"
#    and captures a legitimate webhook delivery, e.g. PRODUCTS_UPDATE:
POST /webhooks HTTP/1.1
X-Shopify-Topic: PRODUCTS_UPDATE
X-Shopify-Shop-Domain: attacker.myshopify.com
X-Shopify-Hmac-Sha256: <valid-hmac-for-body>
X-Shopify-Webhook-Id: 123
X-Shopify-Api-Version: 2025-01

{"id": 1, "title": "..."}

# 2. Attacker replays the exact body + HMAC, but swaps the domain/topic headers
#    to target victim-shop.myshopify.com and, e.g., APP_UNINSTALLED:
POST /webhooks HTTP/1.1
X-Shopify-Topic: APP_UNINSTALLED
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-Hmac-Sha256: <same-valid-hmac-for-same-body>
X-Shopify-Webhook-Id: 123
X-Shopify-Api-Version: 2025-01

{"id": 1, "title": "..."}
```
Because `validateHmacFromRequestFactory` only checks the HMAC against the (unchanged) body, `check.valid === true` and `check.domain === 'victim-shop.myshopify.com'`; the library/host framework then loads and acts on the victim's real offline session (see `ensureValidOfflineSession(params, check.domain)` in [7](#0-6)  and `handler.callback(webhookCheck.topic, webhookCheck.domain, ...)` in [8](#0-7) ) as though Shopify itself sent this webhook for that shop/topic.

export function validateHmacFromRequestFactory(config: ConfigInterface) {
  return async function validateHmacFromRequest({
    type,
    rawBody,
    webhookType,
    ...adapterArgs
  }: ValidateParams): Promise<ValidationInvalid | ValidationValid> {
    const request = await abstractConvertRequest(adapterArgs);
    if (!rawBody.length) {
      return fail(ValidationErrorReason.MissingBody, type, config);
    }

    // Use appropriate header based on webhook type
    const hmacHeaderName = webhookType
      ? WEBHOOK_HEADER_NAMES[webhookType].hmac
      : ShopifyHeader.Hmac;

    const hmac = getHeader(request.headers, hmacHeaderName);
    if (!hmac) {
      return fail(ValidationErrorReason.MissingHmac, type, config);
    }
    const validHmac = await validateHmacString(
      config,
      rawBody,
      hmac,
      HashFormat.Base64,
    );
    if (!validHmac) {
      return fail(ValidationErrorReason.InvalidHmac, type, config);
    }

    return succeed(type, config);
  };

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);
        await log.debug(
          "Webhook HMAC validation failed. Please note that events manually triggered from a store's Notifications settings will fail this validation. To test this, please use the CLI or trigger the actual event in a development store.",
        );
      }
      return validHmacResult;
    }

    return checkWebhookHeaders(request.headers, webhookType);
  };
}
