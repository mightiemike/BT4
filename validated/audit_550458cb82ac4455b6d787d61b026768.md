### Title
Hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` in the Wallet Contract causes unconditionally-lost user deposits when the registrar lookup fails - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The eth-implicit Wallet Contract deployed by the protocol embeds a compile-time-hardcoded target account, `address-map.near`, used to resolve whether an Ethereum-style target address corresponds to an existing named Near account. This mirrors the AJNA bug class: a single hardcoded external contract address is baked into contract logic that is shared across network deployments (mainnet/testnet/localnet are built from the same source with only `CHAIN_ID` varied, not the registrar id). When the cross-contract call to this hardcoded registrar account fails — whether because the account does not exist on that deployment, is paused, or panics for any reason — the callback that handles the failure (`address_check_callback`) drops the user's attached deposit instead of refunding it, unlike the sibling callback `rlp_execute_callback` which does perform the refund in the equivalent failure branch.

### Finding Description
`ADDRESS_REGISTRAR_ACCOUNT_ID` is compiled into the Wallet Contract WASM from a static file: [1](#0-0) [2](#0-1) 

The contract build pipeline (`build.rs`) produces three separate WASM artifacts (mainnet, testnet, localnet) by only mutating the `CHAIN_ID` file before each Docker build; it never varies `ADDRESS_REGISTRAR_ACCOUNT_ID`: [3](#0-2) [4](#0-3) 

This registrar account is used in `inner_rlp_execute` to perform a cross-contract lookup whenever an emulated base-token transfer targets another eth-implicit account (a scenario that a normal, unprivileged transaction/relayer submission reaches directly): [5](#0-4) 

The `caller_deposit` (the attached deposit of the external caller, tracked precisely so it can be refunded on failure) is passed into the resulting callback: [6](#0-5) 

However, in `address_check_callback`, the `PromiseResult::Failed` branch simply returns an error response and never issues the refund transfer for `caller_deposit`: [7](#0-6) 

Compare this to the otherwise-symmetric `rlp_execute_callback`, whose `PromiseResult::Failed` branch does refund `caller_deposit` to the predecessor account: [8](#0-7) 

Because the registrar account id is a single hardcoded value shared across all deployments/environments and is invoked with a fixed small static gas (`REGISTRAR_LOOKUP_GAS = 5 Tgas`), any condition that causes that specific external call to fail — the account not existing on a given network, the account being migrated/redeployed differently, or simply running out of the fixed gas budget for the lookup — makes the failure path in `address_check_callback` execute, which permanently burns the caller's attached deposit that was supposed to be refundable.

### Impact Explanation
Any unprivileged caller (a relayer or a user calling their own wallet contract directly) who submits an RLP-encoded transaction that is classified as `EOABaseTokenTransfer` with `address_check: Some(_)` (i.e., targeting another eth-implicit account) attaches a deposit that is tracked in `CallerDeposit` for refund purposes. If the fixed cross-contract call to the hardcoded `address-map.near` registrar fails for any reason, the deposit is neither forwarded to the intended action nor refunded to the caller — it is silently retained by the wallet contract with no code path to recover it. This is a concrete "permanently frozen/lost funds" condition reachable by an ordinary transaction submitter, without any privileged, network-layer, or validator-controlled precondition.

### Likelihood Explanation
This is reachable by any account holder using the Wallet Contract to send an emulated base-token transfer to another eth-implicit account — a normal, sanctioned usage path of the Wallet Contract, not an edge case requiring an attacker-controlled configuration. The failure trigger (registrar call failing) can occur from ordinary operational conditions (fixed 5 Tgas budget being insufficient under network congestion, the registrar contract being unavailable/paused, or the hardcoded account not yet existing on a given deployment) — any of which is entirely plausible given that the exact same hardcoded account id is shipped in every build variant.

### Recommendation
In `address_check_callback`, mirror the refund logic already present in `rlp_execute_callback`: when `PromiseResult::Failed` is observed for the registrar lookup, issue a `promise_batch_action_transfer` to refund `caller_deposit` before returning the failure `ExecuteResponse`. Additionally, avoid hardcoding a single hard-wired registrar account id shared verbatim across all network builds; make it a build/deploy-time configurable parameter validated per network, analogous to making the token/registrar address a constructor parameter rather than a hardcoded constant.

### Proof of Concept
1. Deploy (or reuse) a Wallet Contract on an eth-implicit account `A` where the hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` (`address-map.near`) either does not exist on that network or is made to fail the call (e.g., insufficient `REGISTRAR_LOOKUP_GAS` under load, or the registrar contract panics).
2. As the account owner (or a relayer), submit an RLP transaction to `A.rlp_execute(target, tx_bytes_b64)` with attached deposit `D`, where `target` is another eth-implicit account and the parsed transaction kind resolves to `EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), .. }` (see `inner_rlp_execute`, lines 412-432).
3. `CallerDeposit::new` captures `D` tied to the predecessor account since predecessor != current account (`types.rs` lines 180-191).
4. The cross-contract call to the registrar (`address_registrar.lookup(address)`) fails (`PromiseResult::Failed`).
5. `address_check_callback` executes its `Failed` branch (`lib.rs` lines 141-148), which returns an error response but never calls `env::promise_batch_create`/`promise_batch_action_transfer` to refund `caller_deposit`.
6. Result: deposit `D` is retained by the Wallet Contract account permanently with no code path anywhere in the contract to recover it for the caller — contrasted directly with the identical scenario in `rlp_execute_callback`, which does refund on failure.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
