This confirms the analog. The relayer fee payout in `inner_rlp_execute` is fired unconditionally as soon as the transaction is parsed successfully, on a separate, unchained promise batch, before the actual user action (the base-token/ERC-20 transfer) is known to succeed. If that action later fails, `rlp_execute_callback` only refunds `caller_deposit` (the attached deposit minus consumed value) — it never claws back the relayer fee that was already paid out on the disjoint promise. This is the same bug class as the Aave report: a fallible operation's failure path doesn't reverse an already-performed side-effect, so value is paid out to a third party even though the underlying action failed.

### Title
Relayer Fee Paid to Relayer Even When the Underlying Wallet-Contract Action Fails - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The NEAR Wallet Contract (used by eth-implicit accounts to emulate Ethereum transactions) pays the relayer a compensation "fee" via an unconditional, disjoint `Promise::new(predecessor).transfer(fee)` immediately after successfully parsing an RLP transaction, before it is known whether the actual requested action (base-token transfer or ERC-20 `ft_transfer`) will succeed. If that action later fails, only the `caller_deposit` (the leftover attached deposit) is refunded in `rlp_execute_callback` — the already-paid relayer fee is never reclaimed, so the user account is left having paid a relayer for a transaction whose net effect never happened.

### Finding Description
In `inner_rlp_execute` [1](#0-0) , once an `EOABaseTokenTransfer` or `ERC20Transfer` is parsed with a non-zero `fee`, the code immediately creates a **separate** promise batch (`env::promise_batch_create(&context.predecessor_account_id)`) that transfers `fee` to the relayer:
```
if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
    env::promise_batch_action_transfer(refund_promise, *fee);
}
```
This promise is **not** chained (`.then()`) to the main action's promise — it is fired unconditionally and executes independently of whatever happens to the actual user action afterward.

The actual action is dispatched separately (e.g., for `ERC20Transfer` via `nep_141_storage_balance_callback` → `ft_transfer` → `rlp_execute_callback`, or directly via `action_to_promise(target, action)?.then(ext.rlp_execute_callback(...))`) [2](#0-1) .

When that action later fails, `rlp_execute_callback` handles `PromiseResult::Failed` by refunding only the `caller_deposit` (attached deposit minus consumed value), which has nothing to do with the relayer fee:
```
PromiseResult::Failed => {
    // The cross-contract call failed, refund the caller if needed
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(refund_promise, NearToken::from_yoctonear(yocto_near.into()));
    }
    ...
}
``` [3](#0-2) 

There is no mechanism anywhere in the contract that reverses/claws back the relayer fee already sent out when the requested action subsequently fails. The nonce is also already incremented before this point for these transaction kinds (line 364), so the transaction cannot be resubmitted to try again — the value paid to the relayer for the failed attempt is simply gone.

This mirrors the reported bug class exactly: the code assumes a downstream operation ("repay debt" in the original report, "perform action" here) will succeed and unconditionally distributes value up-front / doesn't roll back a completed side-effect when the downstream operation fails, ultimately leaving one party (the router / here, the user's wallet) worse off than the contract's accounting model intends.

### Impact Explanation
Any relayer submitting an RLP-encoded Ethereum-emulation transaction (base-token or ERC-20 transfer) with a non-zero `fee` is guaranteed to receive that fee regardless of whether the underlying action succeeds. A malicious or careless relayer, or a receiver contract engineered to reject the transfer (e.g., NEP-141 token with `ft_transfer` failing due to insufficient balance or a receiver panicking on `ft_on_transfer`), can cause the action to fail while the relayer still collects the fee — a real, concrete, unauthorized value transfer out of the user's eth-implicit wallet account for a transaction that produced no useful effect. This is a single-transaction-reachable value-extraction bug (any account can act as the relayer/predecessor calling `rlp_execute`), reachable by any signer/relayer without special privilege.

### Likelihood Explanation
High likelihood: this triggers on any ordinary failure of the underlying action (e.g., insufficient token balance on `ft_transfer`, receiver-side rejection, gas exhaustion in the target contract), not on network/consensus faults. A relayer only needs to submit a transaction whose target action they know or suspect will fail (or race the target account's state) while still collecting the pre-paid fee.

### Recommendation
Chain the relayer-fee transfer to the same promise DAG as the main action (e.g., using `.and()`/making it part of a single batch, or moving it into `rlp_execute_callback`'s success branch) so it is only paid out if the underlying action succeeds, mirroring how `caller_deposit` is refunded conditionally on `PromiseResult::Failed`.

### Proof of Concept
1. A relayer calls `rlp_execute` with a valid RLP-encoded ERC-20 `transfer` transaction from the user's eth-implicit wallet, specifying a non-zero `max_fee_per_gas`/`gas_limit` (i.e., non-zero `tx_fee`), targeting a NEP-141 token where the wallet's balance is insufficient to cover the transfer amount (or the token's `ft_transfer` will otherwise revert).
2. `inner_rlp_execute` parses successfully, increments the nonce, and immediately fires the disjoint `refund_promise` transferring `fee` to `context.predecessor_account_id` (the relayer) [4](#0-3) .
3. The chained `ft_transfer` promise subsequently fails (insufficient balance).
4. `rlp_execute_callback` observes `PromiseResult::Failed`, refunds only the `caller_deposit` (unrelated to `fee`), and returns `success: false` [3](#0-2) .
5. Net result: the relayer received `fee` yoctoNEAR from the wallet account even though the requested transfer never took effect, and the nonce was already consumed so the user cannot cleanly retry the same intended transaction.
