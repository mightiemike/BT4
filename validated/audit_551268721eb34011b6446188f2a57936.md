### Title
Unrestricted-libfunc Sierra→Native (AOT) compilation of user-declared classes executes attacker-influenced native machine code in-process, unlike the memory-safe CASM interpreter - ([File: crates/apollo_compile_to_native_types/src/lib.rs])

### Summary
Standard Sierra→CASM compilation (`apollo_compile_to_casm`) restricts declared classes to an audited libfunc allowlist by default, and CASM execution runs inside the memory-safe Rust `cairo-vm` interpreter. The Cairo-Native path compiles the same Sierra program with `cairo-native` to an AOT-compiled native object that is then loaded and directly executed as machine code inside the sequencer process — but `apollo_compile_to_native_types::SierraCompilationConfig` has no `audited_libfuncs_only` field/restriction at all, so any libfunc a declarer includes in their Sierra program can be lowered to native code.

### Finding Description
For CASM, the compiler config explicitly gates libfunc usage: [1](#0-0) 
and the compiled class is executed only inside `cairo-vm`'s Rust interpreter (`CairoRunner::run_from_entrypoint`), which is memory-safe regardless of the libfuncs used: [2](#0-1) 

The native compilation config, however, carries no equivalent allowlist: [3](#0-2) 
and the compiler (`SierraToNativeCompiler::compile`) only enforces CPU/memory/file-size resource limits on the subprocess, not a libfunc allowlist, before producing an `AotContractExecutor`: [4](#0-3) 

That executor is then invoked directly as native code in-process during transaction execution: [5](#0-4) 

This mirrors the class of bug in the Redis CVE: an unprivileged, authenticated actor supplies code (a Lua script / here, a Sierra program) that is compiled/interpreted by a component with weaker memory-safety guarantees, and any bug in that lower-level compiler/codegen (LLVM/MLIR-based `cairo-native` lowering of unaudited libfuncs) can directly corrupt process memory since the output runs as native machine code rather than through a safe interpreter loop.

### Impact Explanation
If a bug exists in `cairo-native`'s lowering of any given libfunc (more likely for the non-audited, less-hardened corners of the libfunc set) it can produce a native object whose execution corrupts the sequencer process's memory. Because the code executes as native machine code in the same address space as the sequencer, this could lead to node crash, execution divergence versus CASM/OS re-execution, or worse, undefined behavior/RCE inside the sequencer process — a critical availability/consensus-safety issue for any node running Cairo Native.

### Likelihood Explanation
This is gated by significant uncertainty I could not fully resolve:
- Native compilation and execution are only reachable when `cairo_native` mode is enabled (`CairoNativeMode` other than `Off`), which is a node-operator configuration choice, not something guaranteed to be enabled in production.
- I found references to `NativeClassesWhitelist` (used in `NativeClassManager::get_runnable`) gating which class hashes are actually *executed* as native rather than falling back to CASM, but I was not able to fully inspect its definition/population logic (`crates/blockifier/src/blockifier/config.rs`) within the available budget. If this whitelist is populated only with operator-vetted class hashes (not attacker-controlled), then arbitrary user-declared classes may never reach native *execution*, even if they are compiled to native in the background — which would significantly reduce or eliminate the "single declared class" reachability required by the validation rules.
- Because of this unresolved gating, I cannot confirm this rises to the "concrete, network-reachable-by-any-declarer" bar without further investigation of `NativeClassesWhitelist` and `CairoNativeRunConfig` population.

### Recommendation
- Investigate whether `NativeClassesWhitelist` is attacker-influenceable (e.g., automatically populated from any declared/whitelisted class) or strictly operator-curated; if the former, this is a critical, directly reachable analog.
- Regardless, add an audited-libfuncs restriction (mirroring `SierraCompilationConfig::audited_libfuncs_only` in the CASM pipeline) to `apollo_compile_to_native_types::SierraCompilationConfig`, so that only libfuncs vetted for `cairo-native` codegen safety can be compiled to native machine code for classes that could ever be executed.
- Consider stronger process isolation for AOT-executed native code (e.g., running native execution in a separate sandboxed process/seccomp-restricted context) rather than loading/executing it in the same address space as the sequencer.

### Proof of Concept
Not constructed — this finding is exploratory pending confirmation of (a) whether `cairo_native` is enabled/whitelist-open in a target deployment, and (b) an actual codegen bug in `cairo-native` for a specific libfunc. I could not access `cairo-native`'s internal source (external dependency) to identify a concrete memory-corruption bug, so no working exploit is provided. Given the significant unresolved reachability questions (native mode enablement and whitelist gating) and the lack of a demonstrated concrete codegen bug, I recommend treating this as a leads-for-further-investigation item rather than a confirmed critical vulnerability with proof of exploitability.

    pub fn compile(
        &self,
        contract_class: ContractClass,
    ) -> Result<AotContractExecutor, CompilationUtilError> {
        let compiler_binary_path = &self.path_to_binary;

        let output_file = NamedTempFile::new()?;
        let output_file_path = output_file.path().to_str().ok_or(
            CompilationUtilError::UnexpectedError("Failed to get output file path".to_owned()),
        )?;
        let optimization_level = self.config.optimization_level.to_string();
        let additional_args = [output_file_path, "--opt-level", &optimization_level];
        let resource_limits = ResourceLimits::new(
            Some(self.config.max_cpu_time),
            self.config.max_file_size,
            Some(self.config.max_memory_usage),
        );
        let _stdout = compile_with_args(
            compiler_binary_path,
            contract_class,
            &additional_args,
            resource_limits,
        )?;

        Ok(AotContractExecutor::from_path(output_file.path())
            .map_err(|e| CompilationUtilError::CompilationError(e.to_string()))?
            .unwrap())
    }
