### Title
Frozen asset supply misrouted to the wrong token when an account issues multiple TRC10 assets - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
`AssetIssueActuator` stores a single, overwritable "last issued asset" reference (`AssetIssuedName`/`AssetIssuedID`) on the owner `AccountCapsule` instead of tracking it per-asset. When the same account issues a second TRC10 asset (allowed once `AllowSameTokenName` is enabled, which is the long-standing mainnet configuration), this reference is overwritten. `UnfreezeAssetActuator` later relies exclusively on that single field to decide which asset's balance should receive the unfrozen supply, causing supply to be credited to the wrong token — an accounting corruption directly analogous to the "collection referrer overwritten" bug pattern (a single mutable field standing in for what should be a per-entity mapping).

### Finding Description
`AssetIssueActuator.execute()` unconditionally overwrites the owner account's asset-issuance pointer every time a new asset is issued: [1](#0-0) 

There is no check preventing the same account from issuing a second asset. The "Token exists" duplicate check only applies when `AllowSameTokenName == 0`: [2](#0-1) 

Once `AllowSameTokenName` is enabled (the normal, long-since-activated network state), an account can issue arbitrarily many distinct assets (each gets its own unique auto-incremented ID), yet `AssetIssuedName`/`AssetIssuedID` on the `AccountCapsule` is a single scalar field, not a per-asset map: [3](#0-2) 

Compounding this, `FrozenSupply` entries created at issuance time (`Frozen{FrozenBalance, ExpireTime}`) carry **no asset identifier** and are simply appended to the account's shared `frozenSupply` list without clearing/tagging by asset: [4](#0-3) 

When frozen supply later expires, `UnfreezeAssetActuator.execute()` credits the unfrozen amount back using whatever the account's *current* `AssetIssuedName`/`AssetIssuedID` happens to be — not the asset that was actually frozen: [5](#0-4) 

The validation logic in `UnfreezeAssetActuator` similarly only checks that *some* `AssetIssuedName`/`AssetIssuedID` is set, not that it corresponds to the asset whose frozen supply is being released: [6](#0-5) 

Sequence:
1. Account A issues Asset₁ with `FrozenSupply` (e.g., frozen for the minimum freeze period). `AssetIssuedID = Asset₁`.
2. Account A issues Asset₂ (allowed, no restriction). `AssetIssuedID` is overwritten to `Asset₂`. Asset₂'s own frozen supply (if any) is appended to the *same* shared `frozenSupply` list.
3. Once Asset₁'s frozen entry expires, Account A calls `UnfreezeAsset`. The actuator reads the current `AssetIssuedID` (= `Asset₂`) and credits the unfrozen balance to **Asset₂**, not Asset₁.

### Impact Explanation
This causes token accounting corruption: Asset₁'s previously "frozen" (and eventually meant to circulate) supply is permanently lost from Asset₁'s effective circulating balance (the owner's balance line for Asset₁ never increases), while Asset₂ receives an unbacked credit not derived from anything actually frozen under Asset₂'s terms. This inflates the recipient asset's holder balance beyond its declared/tracked supply accounting and permanently strands the original asset's frozen tokens, corrupting on-chain token supply/balance invariants for two independent, unrelated TRC10 tokens — reachable purely through ordinary broadcast transactions from an unprivileged account.

### Likelihood Explanation
High reachability: any account can trigger this by issuing two assets with frozen supply and then calling `UnfreezeAsset` — all via standard, permissionless `AssetIssueContract`/`UnfreezeAssetContract` broadcast transactions. No privileged role, contract call, or malicious peer/node behavior is required. `AllowSameTokenName` (v2 token model) has been the network's long-standing operating mode, so multi-asset issuance by the same account is a normal user action, not an edge configuration.

### Recommendation
Track frozen supply and the "last issued asset" per-asset rather than as a single account-scalar field:
- Add an asset identifier to each `Frozen` entry (or maintain a separate `Map<assetId, List<Frozen>>`) so `UnfreezeAsset` credits the correct asset.
- Remove/rework the account-level `AssetIssuedName`/`AssetIssuedID` singleton semantics for actuators (`UnfreezeAssetActuator`, `UpdateAssetActuator`) that currently assume an account issues at most one asset; either restrict issuance to one asset per account, or make all downstream logic asset-scoped.

### Proof of Concept
1. Enable `AllowSameTokenName=1` (already the case on current chains).
2. Account A broadcasts `AssetIssueContract` for Asset₁ with a `FrozenSupply` entry (minimum freeze duration). `AccountCapsule.assetIssuedID` becomes Asset₁'s ID; Asset₁'s frozen entry is appended to A's `frozenSupply` list (`AssetIssueActuator.java:96-120`).
3. Account A broadcasts a second `AssetIssueContract` for Asset₂ (no `AllowSameTokenName` restriction blocks this — `AssetIssueActuator.java:210-214`). `AccountCapsule.assetIssuedID` is overwritten to Asset₂'s ID (`AssetIssueActuator.java:116-118`).
4. Wait until Asset₁'s frozen entry expires; Account A broadcasts `UnfreezeAssetContract`.
5. `UnfreezeAssetActuator.execute()` reads `accountCapsule.getAssetIssuedID()` (= Asset₂) and calls `addAssetAmountV2(Asset₂_id, unfreezeAsset, ...)` (`UnfreezeAssetActuator.java:66-69`), crediting Asset₂'s balance with tokens that were frozen under Asset₁ — corrupting both assets' supply accounting.
