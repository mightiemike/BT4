### Title
Unrestricted attacker-controlled initial reserve ratio in `ExchangeCreateContract` allows creation of mispriced duplicate markets - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
`ExchangeCreateActuator` lets any account create a new Bancor-style TRX/TRC10 "Exchange" pool by broadcasting an `ExchangeCreateContract` with arbitrary `first_token_balance`/`second_token_balance` values, which become the pool's initial reserves and therefore its starting exchange rate. The resulting `exchange_id` is just `dynamicStore.getLatestExchangeNum() + 1` [1](#0-0)  — it does not encode the token pair or the chosen price, and the same token pair can have unlimited independent pools created by different (or the same) users at wildly different price ratios. This mirrors the Divergence Protocol bug where `startSqrtPriceX96` is an arbitrary, attacker-supplied value not bound into the battle key, letting anyone spin up a pool/battle with an unfair price.

### Finding Description
In `doValidate()`/`execute()` of `ExchangeCreateActuator`, the only checks on `firstTokenBalance`/`secondTokenBalance` are that they are positive and below `dynamicStore.getExchangeBalanceLimit()`, and that the creator has sufficient balance/asset to fund them [2](#0-1) . There is no check preventing an attacker from:
- Creating a pool for `TRX`/`TOKEN_X` with an extreme reserve ratio (e.g. 1 TRX : 1,000,000,000 TOKEN_X), setting an absurd starting price, or
- Creating any number of duplicate pools for the same token pair, each with a different starting price, since `exchange_id` is a pure incrementing counter unrelated to the pair or price [3](#0-2) .

Once created, `ExchangeTransactionActuator` and `ExchangeWithdrawActuator` compute trade/withdrawal outputs purely from the pool's current `firstTokenBalance`/`secondTokenBalance` via the Bancor `ExchangeProcessor`/`SafeExchangeProcessor` math [4](#0-3)  — i.e., the attacker-chosen starting reserves directly and permanently determine the exchange rate every subsequent trader receives, exactly as `startSqrtPriceX96` fixes the AMM's starting price in the original report.

### Impact Explanation
A user who is told/expects to trade against "the" TRX/TOKEN_X exchange, or who queries pools without carefully validating reserves, can be lured into trading against an attacker-created pool whose price is skewed far from fair market value. Because trades are executed purely against the specified `exchange_id`'s current balances (`Commons.getExchangeStoreFinal(...).get(ByteArray.fromLong(exchangeTransactionContract.getExchangeId()))` [5](#0-4) ), a victim can receive far less (or the attacker can extract far more) than fair value, resulting in accounting/asset loss for the victim — a genuine unfair trade condition, not merely a griefing nuisance.

### Likelihood Explanation
Any funded account can call `ExchangeCreateContract` at any time via a normal broadcast transaction; no privileged role or governance approval is required, and the contract validation logic imposes no floor/ceiling on the reserve ratio beyond the global `ExchangeBalanceLimit` [6](#0-5) . This makes the attack trivially and repeatedly reachable from an anonymous broadcast transaction.

### Recommendation
Bind the initial/implied price (or at minimum a sanity-checked reserve ratio) into how pools are keyed/discovered, or require that a canonical pool per token pair be reused/updated rather than allowing unlimited duplicate pools with independently attacker-chosen starting ratios — analogous to the report's recommendation to fold `startSqrtPriceX96` into the battle key. At minimum, surface existing-pool price checks to callers/wallets before trading, and consider disallowing new pool creation for a pair that already has an active pool.

### Proof of Concept
1. Attacker broadcasts `ExchangeCreateContract{owner=attacker, first_token_id="_", first_token_balance=1, second_token_id="TOKEN_X", second_token_balance=1_000_000_000}` — `ExchangeCreateActuator.execute` accepts it as long as balances are positive and under the balance limit, creating `exchange_id=N` with this skewed ratio [7](#0-6) .
2. A victim, believing exchange `N` reflects fair TRX/TOKEN_X pricing, sends `ExchangeTransactionContract{exchange_id=N, token_id="_", quant=1_000_000}` expecting a fair-market amount of TOKEN_X.
3. `exchangeCapsule.transaction(...)` computes the payout using the attacker-set skewed reserves via the Bancor formula [8](#0-7) , yielding a payout far below fair value — the attacker profits at the victim's expense purely because they controlled the pool's starting reserves at creation time, with no on-chain identifier tying that price to anything verifiable.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
