### Title
Panic on stale `GlobalContractDistribution` receipt during `DelayedReceiptQueueWrapper::pop` after resharding - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally `.unwrap()`s the result of `Receipt::receiver_shard_id`, which can return `Err` for a `GlobalContractDistribution` receipt whose `target_shard` predates the split history the runtime can resolve. This is the same bug class as the reported kernel CVE: a value that is normally assumed to be resolvable/present (backing store / current-shard mapping) is dereferenced without a None/Err check, and an attacker-influenced object (a PRT BO / a stale cross-shard receipt) can legitimately be in the unchecked state.

### Finding Description
`receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs` (~lines 874-877) is:
```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
``` [1](#0-0) 

This is called from `DelayedReceiptQueueWrapper::pop`, on the hot path that drains the delayed-receipt queue every chunk, for **every** receipt as it comes out of the FIFO, regardless of type: [2](#0-1) 

`Receipt::receiver_shard_id` explicitly documents that a `GlobalContractDistribution` receipt's `target_shard` "may be from an arbitrarily old layout (the receipt could have been delayed across multiple resharding events)", and calls `shard_layout.resolve_to_current_shard(target_shard)`, returning an `Err(EpochError::ShardingError(..))` if that historical shard id cannot be resolved: [3](#0-2) 

`ShardLayoutV3::resolve_to_current_shard` recurses through `shards_split_map` and returns `None` only if the shard id is absent from both the current layout and the entire split history: [4](#0-3) 

The repository's own regression test explicitly documents and reproduces this exact panic scenario: a `GlobalContractDistribution` receipt with `target_shard` pointing at a shard from before *two* resharding generations, delayed in the queue through both splits, causing `receiver_shard_id()` to fail and the `.unwrap()` in `receipt_filter_fn` to panic when the delayed queue is finally drained: [5](#0-4) 

The test title itself — `test_stale_global_contract_distribution_after_double_resharding` — and its comment "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn()" confirms this is a known, named bug class that the code has a test guarding against, analogous to the GPU driver's missing NULL check for a BO that legitimately has no backing store (PRT BOs). The reachable trigger is entirely protocol-level: an unprivileged account deploying a global contract (`DeployGlobalContract`/`UseGlobalContract` flow), combined with the network reaching congestion so the resulting `GlobalContractDistribution` receipt sits in the delayed queue across two dynamic-resharding events on its origin shard.

### Impact Explanation
If `resolve_to_current_shard` fails to remap the stale `target_shard` (e.g., due to garbage collection of intermediate split-history layouts, an edge case in `shards_split_map` construction, or resharding generations exceeding what is retained/reconstructable), the `.unwrap()` panics inside chunk application. A panic during `apply_transactions`/receipt processing halts the node process for every validator applying that shard — this is a chain-wide, transaction/receipt-triggered halt (denial of service) rather than a localized error, matching the "transaction-triggered halt" acceptance criterion. Because global contract deployment is available to any account (no special privilege), and delayed queue backlog + repeated resharding are both externally influenceable/observable conditions, this is reachable by ordinary network activity without validator or node compromise.

### Likelihood Explanation
The repository authors evidently identified this as a real risk serious enough to write a dedicated regression test (`test_stale_global_contract_distribution_after_double_resharding`) that manufactures the exact conditions (force-split two shards sequentially, saturate compute to keep the distribution receipt in the delayed queue across both splits, then drain). The test comment states the code "the fix only works with V3 shard layouts (dynamic resharding)" and gates on `ProtocolFeature::DynamicResharding`, implying this is a recently-hardened/edge case still worth monitoring, and that older static-resharding chains ("the shard layout doesn't maintain a full split history") remain more exposed to a shard-history-exhaustion scenario feeding the same `.unwrap()`. I could not fully verify from static analysis alone whether the currently-checked-in `resolve_to_current_shard`/`shards_split_map` construction is airtight for arbitrarily many resharding generations or garbage-collected split history, so the precise conditions under which `Err` is still reachable in the present code are not fully confirmed — this uncertainty is intrinsic to the available index and would benefit from running the existing regression test and auditing GC of old `ShardLayoutV3` split-history entries.

### Recommendation
- Replace the `.unwrap()` calls in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs`) with proper error propagation (`Result`) so a resolution failure surfaces as a handled `RuntimeError`/`StorageError` rather than a hard panic, consistent with how the rest of the congestion-control code (`try_forward`, `forward_or_buffer_receipt`) already propagates `receiver_shard_id()` errors via `?`.
- Ensure `shards_split_map`/split history retention guarantees that any `target_shard` embedded in a still-live (non-GC'd) delayed/buffered receipt can always be resolved, or add an explicit remediation path (e.g., re-route to a deterministic "orphaned" fallback shard) instead of failing.
- Extend `test_stale_global_contract_distribution_after_double_resharding`-style coverage to more resharding generations and to static (V2) shard layouts, and add fuzzing around GC + long delayed-queue residency of `GlobalContractDistribution` receipts.

### Proof of Concept
The existing test `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs` (lines 30-186) is itself a working reproduction outline:
1. Set up dynamic resharding configured to force-split two shards sequentially, the first split targeting the shard of `deploy_user`.
2. `deploy_user` submits a `DeployGlobalContract` action, producing an incoming `GlobalContractDistribution` receipt with `target_shard = S_A` (deploy_user's shard).
3. Continuously saturate that shard's compute budget (via `burn_gas_raw` calls) so the distribution receipt is pushed into, and stays in, the delayed-receipt queue across both resharding events (`initial_num_shards + 2` shards reached).
4. Stop saturating and let the delayed queue drain; on unfixed code, popping the stale receipt via `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn` panics because `receiver_shard_id()` cannot remap `S_A` through two resharding generations, halting chunk production (`head_height < drain_end`).     pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }

fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
