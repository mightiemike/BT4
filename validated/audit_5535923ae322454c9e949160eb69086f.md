### Title
Missing Slippage Protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` Allows Value Loss for AMM Liquidity Providers - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
java-tron's built-in Bancor-style AMM (the `Exchange` module) allows a pool's creator to inject or withdraw liquidity via `ExchangeInjectContract`/`ExchangeWithdrawContract`. Unlike `ExchangeTransactionContract`, which carries an `expected` field used to bound slippage on trades, the inject/withdraw contracts have no equivalent min/max bound on the counterpart token amount, exposing the caller to the exact "missing slippage protection" bug class described in the external report.

### Finding Description
`ExchangeTransactionContract` includes an `expected` field [1](#0-0)  and its actuator enforces it, reverting with `"token required must greater than expected"` if the computed output falls below the caller-specified threshold [2](#0-1) .

By contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no field to bound the paired ("another") token amount [3](#0-2) .

In `ExchangeInjectActuator`, the caller specifies `tokenQuant` for one side of the pool, and `anotherTokenQuant` (the required amount of the paired token) is derived purely from the pool's *current* ratio at both validation and execution time, with no way for the caller to cap it: [4](#0-3) 

Likewise, `ExchangeWithdrawActuator` computes `anotherTokenQuant` (the amount of paired token the LP receives back) from the live pool ratio with no caller-specified minimum: [5](#0-4) 

Both operations are restricted to the exchange's `creatorAddress` [6](#0-5) , [7](#0-6) , but "creator" is not a privileged/trusted chain role — any unprivileged account can become a pool creator simply by broadcasting `ExchangeCreateContract` and paying the associated fee. Once created, that same self-service account is the only one who can inject/withdraw liquidity on their own pool, making this a normal unprivileged-user code path, structurally identical to a Uniswap-v1-style `addLiquidity`/`removeLiquidity` call with no slippage bound.

The exchange pool ratio can move between the time a user signs/broadcasts an `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction and the time it is actually executed, because other pending `ExchangeTransactionContract` trades against the same pool can be included first and shift `firstTokenBalance`/`secondTokenBalance`. Since inject/withdraw amounts are recomputed against the ratio at execution time with no bound, the LP has no way to protect themselves from an adverse ratio shift — this is precisely the missing-slippage-protection root cause identified in the ERC-4626 report, transplanted onto java-tron's native AMM primitive.

### Impact Explanation
- On `ExchangeInject`: if the pool ratio moves unfavorably before execution, the LP is forced to lock up a larger amount of the paired token than they intended for the same `tokenQuant`, effectively depositing at a worse-than-expected rate with no way to cap or reject the trade.
- On `ExchangeWithdraw`: if the ratio moves unfavorably before execution, the LP receives less of the paired token back than expected for the same `tokenQuant` withdrawn, resulting in a silent value loss with no recourse — the transaction still succeeds since there is no `expected`/minimum check.
- This is an accounting/settlement-fairness issue on real on-chain value (TRX and TRC10 tokens held in the `ExchangeCapsule` pool balances), reachable by any account that self-creates an exchange pool — a permissionless, unprivileged action.

### Likelihood Explanation
Likelihood is moderate: it requires the pool ratio to move meaningfully between signing and inclusion of the inject/withdraw transaction, which is realistic on any moderately active pool (e.g., another user's `ExchangeTransactionContract` trade landing first in the same or an earlier block), or simply due to network propagation delay / mempool ordering. No special privilege or contract interaction is needed — a normal TRX/TRC10 holder who creates an exchange and later injects/withdraws liquidity is exposed.

### Recommendation
Add an `expected` (or `min_expected`/`max_expected`, depending on direction) field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, analogous to the existing field in `ExchangeTransactionContract`:
- For `ExchangeInjectContract`: allow the caller to specify a maximum acceptable `anotherTokenQuant`, and revert in `ExchangeInjectActuator.doValidate()`/`execute()` if the computed amount exceeds it.
- For `ExchangeWithdrawContract`: allow the caller to specify a minimum acceptable `anotherTokenQuant`, and revert if the computed amount is below it.

This mirrors the fix pattern already implemented for `ExchangeTransactionContract` (`tokenExpected` check) [2](#0-1) .

### Proof of Concept
1. User A creates an exchange pool for TRX/TokenX via `ExchangeCreateContract` (becoming the pool `creatorAddress`).
2. User A signs and broadcasts an `ExchangeInjectContract` specifying `tokenQuant` of TRX, expecting to also lock roughly `X` TokenX based on the pool ratio observed at signing time.
3. Before this transaction is confirmed, another account executes a large `ExchangeTransactionContract` trade against the same pool (`quant`, `expected` fields set appropriately for that trade), shifting `firstTokenBalance`/`secondTokenBalance` significantly.
4. User A's inject transaction then executes: `ExchangeInjectActuator.execute()` recomputes `anotherTokenQuant` from the now-shifted ratio [8](#0-7) , forcing User A to deposit a materially different (larger) amount of TokenX than intended, with the transaction still succeeding because there is no `expected`/bound field to reject it.
5. Symmetrically, a withdrawal via `ExchangeWithdrawContract` executed after an adverse ratio shift returns less of the paired token than the user anticipated, with no minimum-amount check to abort the withdrawal [9](#0-8) .
