## Finding confirmed via local code

### Title
`TransactionOutput::ensure_match_transaction_info` never validates `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`, allowing replay-verify/debugger tooling to accept a divergent state root as correct - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the authenticated-integrity check used by both the `db-tool replay-on-archive` verifier and the `aptos-debugger` to confirm that locally re-executed transaction outputs match the trusted, previously-committed `TransactionInfo` for a version. It checks `status`, `gas_used`, `state_change_hash` (write set), and `event_root_hash`, but it deliberately skips comparing any of the state-checkpoint-related root hashes carried in `TransactionInfoV1`/`V0`.

### Finding Description
`TransactionInfo` (both V0 and V1 encodings) carries `state_checkpoint_hash`, and V1 additionally carries `hot_state_checkpoint_hash` and `position_state_checkpoint_hash` — these are the Sparse-Merkle/Jellyfish-Merkle state roots that authenticate the entire world state at a checkpoint version [1](#0-0) [2](#0-1) .

`ensure_match_transaction_info` is the single function responsible for confirming that a freshly computed `TransactionOutput` (from re-executing history) matches an already-persisted, presumably-trusted `TransactionInfo`. It verifies status, gas, the write-set hash (`state_change_hash`), and the event root hash, but explicitly does **not** compare `state_checkpoint_hash` and leaves a code comment acknowledging the gap and stating that enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS` requires fixing this first: [3](#0-2) .

This function is the actual verification oracle used by:
- `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes historical transactions from backup and calls `ensure_match_transaction_info` to decide pass/fail for each transaction [4](#0-3) .
- The `aptos-debugger` crate imports `TransactionInfo`/`TransactionOutput` for the same style of replay/verification workflow [5](#0-4) .

Because the state-checkpoint hash (the Merkle root of the entire state tree at a checkpoint) is never checked, a re-executed chunk of transactions whose write sets and events hash identically but whose *cumulative state* diverges (e.g., due to a state-merklization bug, a divergent JMT/hot-state root computation, or a bug in `commit_transaction_accumulator`/`state_checkpoint` logic that doesn't affect individual per-txn write sets) will be reported as a **successful, verified replay** even though the authenticated state root is wrong.

### Impact Explanation
This breaks the "authenticated API and proof-bearing responses must stay bound to the right ledger version, root, and object" invariant for the replay-verify tooling: `replay_on_archive` is the primary tool relied on (per its own file naming and the `testsuite/replay-verify` harness) to certify that binaries executing against real historical/mainnet data reproduce the exact same ledger state, including the state Merkle root. A hard-fork-only or storage-only divergence in state-checkpoint hash computation (state root corruption) would go completely undetected by this tool, since it only validates the write set and event root per transaction — not the accumulated/checkpointed state root that downstream proofs (`get_state_value_with_proof_by_version`, `TransactionInfoWithProof`, backup snapshot verification) ultimately depend on. This directly matches the "Wrong ... state proof accepted as valid" and "Hard-fork-only divergence during ... replay ... verification" impact categories, since replay-verify's entire purpose is to catch exactly this class of regression before it reaches production/mainnet.

### Likelihood Explanation
The code's own comment (lines 2197–2202) confirms this is a known, currently-live gap rather than a purely defensive statement — the comparator "ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." Since `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `hot_state_root_in_txn_info` are configurable on-chain-config-gated features actively under development (per `execution_output.rs`/`aptosdb_writer.rs` references), a future or already-shipped divergence bug in state-root computation for these new checkpoint hash types (position/hot-state) would silently pass replay-verify today, with no code change required to trigger it — it's a standing gap in the verification tool itself.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s locally computed state-checkpoint-related hashes (state checkpoint hash, hot-state checkpoint hash, and position-state checkpoint hash, when present in the transaction info) against `txn_info`'s corresponding fields, returning an error on mismatch just as is done for `state_change_hash` and `event_root_hash`. This requires `TransactionOutput` (or its caller) to have access to the locally computed checkpoint hash(es) at that version, since the write set alone does not include them — the checkpoint-computation pipeline (`DoStateCheckpoint`, `PartialStateComputeResult`) would need to feed the computed hash into this comparison for checkpoint versions.

### Proof of Concept
Not exploitable as a live PoC without a concrete state-root divergence bug elsewhere; the vulnerability is a documented verification gap. Local proof: `types/src/transaction/mod.rs:2139-2204` shows the comparison function omits `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields present on `TransactionInfo`, and `storage/db-tool/src/replay_on_archive.rs:392-397` shows this is the sole correctness check used by the production replay-verify tool for each replayed transaction, meaning any future state-root computation bug (in JMT commit, hot-state, or native-position state summary logic) would pass replay-verify undetected.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
