### Title
Unbounded gzip decompression of legacy declare-transaction program in RPC gateway allows memory-exhaustion zip bomb - (File: crates/apollo_rpc/src/v0_8/api/mod.rs)

### Summary
The `decompress_program` function used to decode the `compressed_program` field of a Cairo-0 (`DEPRECATED_CONTRACT_CLASS`) declare transaction submitted via the RPC gateway performs base64 decoding followed by gzip decompression **with no size limit**, unlike the sibling function `decode_and_decompress_with_size_limit` used elsewhere in the codebase for the same purpose.

### Finding Description
`decompress_program` reads the entire gzip stream into an unbounded `Vec<u8>` via `decoder.read_to_end(&mut decompressed, ...)`, explicitly marked with a `// TODO(dan): add time and size limits.` comment: [1](#0-0) 

This function is invoked directly from `user_deprecated_contract_class_to_sn_api`, which is reached when a client submits a `BroadcastedDeclareV1Transaction` (legacy Cairo-0 declare) to the RPC `add_declare_transaction` write endpoint or to simulation/estimate-fee endpoints, converting the user-supplied `compressed_program` string: [2](#0-1) [3](#0-2) 

This is directly analogous to the chall-manager zip-bomb bug: an attacker crafts a small gzip payload that decompresses to a huge amount of data, and the decoder happily allocates and expands it without limit, unlike the codebase's own `decompress_with_size_limit` pattern that caps output size using `.take(max_size + 1)`: [4](#0-3) 

Other places that decompress user/network-supplied compressed classes correctly cap size (e.g. the p2p class converter uses a 4MB cap, and the deprecated-gateway HTTP path uses `decode_and_decompress_with_size_limit` with a `max_size` from config): [5](#0-4) [6](#0-5) 

`decompress_program` is the outlier without any such bound.

### Impact Explanation
An unauthenticated/unprivileged RPC client can send a small, highly-compressed gzip payload as the `compressed_program` field of a legacy declare transaction (or as part of `simulate_transactions`/`estimate_fee` broadcasted-declare-v1 requests) to the JSON-RPC gateway. The `GzDecoder::read_to_end` call will decompress it into memory without bound, potentially expanding a few KB of compressed input into gigabytes, causing large memory allocation and CPU consumption on the RPC node process. This can exhaust node memory/CPU resources, causing denial of service to that RPC node, degrading availability without requiring authorization — matching the pattern (and CVSS "Availability: High" impact) of the referenced CVE-2025-53633.

### Likelihood Explanation
High likelihood of exploitability: this is reachable via a single unauthenticated RPC call (`starknet_addDeclareTransaction` with a V1 legacy contract class, or trace/estimate simulation endpoints accepting `BroadcastedDeclareV1Transaction`). No special privileges, staking, or node compromise required — only a crafted transaction JSON body. The vulnerable code path even carries an explicit developer TODO acknowledging the missing limit, confirming the gap is unintentional and unaddressed.

### Recommendation
Replace the unbounded `GzDecoder::read_to_end` call in `decompress_program` with a bounded decompression using the same pattern already established elsewhere in the codebase (`decompress_with_size_limit` / `decode_and_decompress_with_size_limit`), e.g. wrap the decoder with `.take(max_size + 1)` and reject the class if the decompressed size exceeds a configured maximum (mirroring `MAX_CAIRO0_PROGRAM_SIZE` used in the p2p class converter). Apply the same bound consistently to all Cairo-0 program decompression call sites, including RPC-submitted declare transactions.

### Proof of Concept
1. Craft a gzip-compressed payload that expands from a few kilobytes to several hundred MB/GB (a classic zip bomb, e.g. repeated zero bytes compressed with maximum ratio).
2. Base64-encode it and place it as `contract_class.program` in a `BROADCASTED_DECLARE_TXN_V1` request body.
3. Submit it to the RPC gateway's `starknet_addDeclareTransaction` (or an estimate/simulate endpoint accepting `BroadcastedDeclareV1Transaction`).
4. `user_deprecated_contract_class_to_sn_api` → `decompress_program` decompresses the payload fully into memory with no limit check, before any subsequent validation, causing large memory consumption / potential OOM on the node handling the request.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
