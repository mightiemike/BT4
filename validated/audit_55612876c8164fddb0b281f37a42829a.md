**Rationale:**

`BlockInfo::match_ordered_only` deliberately excludes `executed_state_id`/`version` because these are exactly the fields the function is designed to allow to differ between an *ordered* (pre-execution, often placeholder) `BlockInfo` and an *executed* (post-execution) `BlockInfo` of the same block — the doc comment states it checks "fields that will not change after execution" [1](#0-0) . The ordered variant uses `ACCUMULATOR_PLACEHOLDER_HASH`/`version == 0` as sentinel values per `is_ordered_only()` [2](#0-1) , so a mismatch on those fields between ordered and executed pairs is expected and intentional, not a bug.

Checking the two real call sites confirms `executed_state_id`/`version` are never attacker-controlled inputs that bypass validation via this function:

- In `consensus/src/block_storage/block_store.rs`, `insert_single_quorum_cert` uses `match_ordered_only` only to confirm a QC's certified block refers to the *same block identity* (epoch/round/id) as the locally-executed `PipelinedBlock`; the comment explicitly notes "decoupled execution allows dummy block infos" [3](#0-2) . The QC itself carries validator signatures over the full `LedgerInfo`/`BlockInfo` hash (including `executed_state_id`/`version`), verified separately via `qc.verify()` elsewhere in the pipeline — signatures a single attacker cannot forge.

- In `consensus/safety-rules/src/safety_rules.rs`, `guarded_sign_commit_vote` uses `match_ordered_only` to confirm the old (ordered) and new (locally executed) ledger infos describe the same block before the validator signs the new one [4](#0-3) . The `new_ledger_info`'s `executed_state_id`/`version` are computed locally by this validator's own VM execution of the block, not supplied externally — there's no unprivileged path to inject a divergent value here.

The actual state-root correctness is enforced by independent VM execution by each validator plus the 2f+1 aggregate signature requirement over the complete `LedgerInfo` hash (which does include `executed_state_id`/`version`), not by `match_ordered_only`. A single malicious/unprivileged party supplying a divergent `executed_state_id` cannot get quorum-certified because other honest validators would independently compute the correct value and refuse to sign a mismatching one. There is no downstream commit-path logic that treats `match_ordered_only` as sufficient proof of state-root correctness; it is purely a block-identity sanity check, and correctness of the committed `executed_state_id`/`version` is guaranteed by signature quorum, not by this function.

    /// This function checks if the current BlockInfo has
    /// exactly the same values in those fields that will not change
    /// after execution, compared to a given BlockInfo
    pub fn match_ordered_only(&self, executed_block_info: &BlockInfo) -> bool {
        self.epoch == executed_block_info.epoch
            && self.round == executed_block_info.round
            && self.id == executed_block_info.id
            && (self.timestamp_usecs == executed_block_info.timestamp_usecs
            // executed block info has changed its timestamp because it's a reconfiguration suffix
                || (self.timestamp_usecs > executed_block_info.timestamp_usecs
                    && executed_block_info.has_reconfiguration()))
    }

    fn guarded_sign_commit_vote(
        &mut self,
        ledger_info: LedgerInfoWithSignatures,
        new_ledger_info: LedgerInfo,
    ) -> Result<bls12381::Signature, Error> {
        self.signer()?;

        let old_ledger_info = ledger_info.ledger_info();

        if !old_ledger_info.commit_info().is_ordered_only()
            // When doing fast forward sync, we pull the latest blocks and quorum certs from peers
            // and store them in storage. We then compute the root ordered cert and root commit cert
            // from storage and start the consensus from there. But given that we are not storing the
            // ordered cert obtained from order votes in storage, instead of obtaining the root ordered cert
            // from storage, we set root ordered cert to commit certificate.
            // This means, the root ordered cert will not have a dummy executed_state_id in this case.
            // To handle this, we do not raise error if the old_ledger_info.commit_info() matches with
            // new_ledger_info.commit_info().
            && old_ledger_info.commit_info() != new_ledger_info.commit_info()
        {
            return Err(Error::InvalidOrderedLedgerInfo(old_ledger_info.to_string()));
        }

        if !old_ledger_info
            .commit_info()
            .match_ordered_only(new_ledger_info.commit_info())
        {
            return Err(Error::InconsistentExecutionResult(
                old_ledger_info.commit_info().to_string(),
                new_ledger_info.commit_info().to_string(),
