### Title
Zero-lamport account at the default (all-zero) `Pubkey` is silently confused with unused/padding AppendVec space, causing accounts to be dropped mid-scan - (File: accounts-db/src/append_vec.rs)

### Summary
This is the same bug class as TRST-M-4: a valid, "empty-looking" record is silently reinterpreted as an absent/sentinel value. In `AppendVec`'s account-scanning routines, an account entry with `lamports == 0` and `pubkey == Pubkey::default()` is treated as the terminator that marks "we passed the last useful account," so the scan breaks immediately instead of validating that this is actually the end of file. `Pubkey::default()` (32 zero bytes) is a real, addressable account (it is in fact the System Program's own address), so a legitimately stored zero-lamport account at that pubkey is indistinguishable from the zero-initialized padding bytes that follow the last real account in a freshly allocated `AppendVec`.

### Finding Description
`scan_accounts_stored_meta` and `scan_stored_accounts_no_data` both use the same heuristic to detect the end of valid data in an `AppendVec` file: [1](#0-0) [2](#0-1) 

```rust
if account_meta.lamports == 0 && meta.pubkey == Pubkey::default() {
    // we passed the last useful account
    break;
}
```

This check exists because `AppendVec` backing files are allocated/zero-initialized ahead of time, so any bytes past the last written account read back as an `AccountMeta{lamports:0,...}`/`StoredMeta{pubkey:[0;32],...}` pair. The code uses this all-zero pattern as a sentinel for "no more accounts here."

The problem is that `Pubkey::default()` (`[0u8; 32]`) is not a reserved/unaddressable value — it decodes to the base58 string `11111111111111111111111111111111`, which is the address of the System Program itself, and it is also a syntactically valid destination for any `SystemInstruction::Transfer`. Nothing in the runtime prevents lamports from being sent to, or drained from, this address. If a real, previously non-empty account at pubkey `Pubkey::default()` is later drained to exactly zero lamports and gets flushed into an `AppendVec`, its on-disk record is bit-for-bit identical to the sentinel the scanner is looking for. `scan_accounts_stored_meta`/`scan_stored_accounts_no_data` will treat that legitimate account record as "end of file" and stop scanning, silently discarding every account written after it in that same storage file — with no error, log, or panic.

This mirrors the external report's root cause precisely: a value that is structurally valid ("empty"/zero) is conflated with the sentinel that signals "invalid/no data here," and the caller "confuses the response with a valid... return value and will presumably finish execution" (here: finish the scan early instead of reading to the true end of file).

Both scanning functions are foundational read paths used by `AccountsDb` to reconstruct accounts from storage — for example `scan_accounts` (used by `AccountStorageEntry`/index generation and snapshot writing) is built directly on `scan_accounts_stored_meta`, and `scan_pubkeys` (used for enumerating pubkeys in a storage, including duplicate detection during startup index generation) is built directly on `scan_stored_accounts_no_data`: [3](#0-2) [4](#0-3) 

### Impact Explanation
If a storage's scan stops early because of an incidental zero-lamport account at `Pubkey::default()`, every account physically stored after that offset in the same `AppendVec` becomes invisible to:
- Startup index generation (`generate_index`/`mark_obsolete_accounts_at_startup` style scans that rely on `scan_pubkeys`/`scan_accounts`), silently dropping accounts from the in-memory index.
- Accounts (lattice) hash / capitalization computation during snapshot verification, since these also iterate storages via `scan_accounts`, producing a hash/capitalization divergence between the honest replay result and what should have been computed, or between nodes that happen to load the storage at different times.
- Snapshot generation/rebuild, since incremental/full snapshot writers walk storages with the same scan primitives, potentially omitting accounts from a newly generated snapshot.

The net effect is a stale/incorrect account view purely as a data-layout coincidence — a class of bug this scan explicitly disallows for its own bookkeeping heuristics (the same file even has a dedicated `is_default_account()`/`sanitize_lamports()` helper acknowledging the ambiguity of "is this padding or a real zeroed account" in test-only code, showing the developers are aware of but have not closed this gap in production scan paths): [5](#0-4) 

### Likelihood Explanation
Reaching this state requires (a) an account at address `Pubkey::default()` (the System Program's own address, or any account deliberately created there) that (b) is written with non-zero lamports at some earlier offset in a storage file, and (c) is later reduced to exactly zero lamports and (d) re-stored (flushed) into the same `AppendVec`, with (e) at least one more account appended after it in that file. Sending lamports to and from address `11111111111111111111111111111111` is possible via ordinary `SystemInstruction::Transfer` instructions available to any unprivileged user; a validator/RPC operator role is not required to trigger the write pattern, only ordinary transaction submission plus the normal account flush/consolidation of `AccountsDb` (an unprivileged, no-special-role path). However, whether it is exploitable in practice depends on internal `AccountsDb` invariants (e.g., zero-lamport accounts are generally excluded from the write cache and may not be written to storage as a "real" record at all per `write_accounts_to_cache`) that were only partially verified here: [6](#0-5) 
This uncertainty (whether a zero-lamport account at `Pubkey::default()` can actually reach `AppendVec` as a standalone stored record, as opposed to being filtered before storage) could not be fully resolved with the available read-only search tools, so likelihood should be treated as unconfirmed/lower-probability rather than proven-exploitable.

### Recommendation
Do not rely on `(lamports == 0 && pubkey == Pubkey::default())` as an end-of-data sentinel. Instead, bound the scan strictly by the storage's tracked `len()`/`current_len` (which is already available and used elsewhere in the same functions, e.g. `self_len`), and only stop when the read offset reaches that authoritative length or a genuine EOF/parse failure occurs, rather than pattern-matching on account content that can coincide with a legitimately stored account.

### Proof of Concept
Not independently reproduced (no execution environment available). Conceptually:
1. Fund the address `Pubkey::default()` (`11111111111111111111111111111111`) with lamports via a normal `SystemInstruction::CreateAccount`/`Transfer`, and store at least one other account (`pubkey_after`) after it in the same slot/`AppendVec`.
2. Force a flush of both accounts to the same `AppendVec` storage.
3. Drain `Pubkey::default()` back to zero lamports in a subsequent transaction, then force a flush/rewrite that leaves the zero-lamport `Pubkey::default()` record followed by `pubkey_after`'s record in the same storage file.
4. Trigger a storage scan (e.g. `scan_pubkeys`/`scan_accounts` via startup index generation or snapshot generation) and observe that `pubkey_after` is silently omitted from the index/hash, matching the two scan implementations shown above: [1](#0-0) [2](#0-1)
