### Title
Memo/multi-sign fee charged once per contract in a multi-contract transaction instead of once per transaction - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
The external report describes `msg.value` being re-applied to a fee accumulator on every loop iteration instead of once. The closest reachable analog in java-tron is `Manager.consumeMultiSignFee()` and `Manager.consumeMemoFee()`, which each iterate over `trx.getInstance().getRawData().getContractList()` and, on every iteration, deduct a *transaction-level* fixed fee (`getMultiSignFee()` / `getMemoFee()`) from that contract's owner account and credit it to the black hole — even though the multi-sign condition and the presence of a memo (`data` field) are properties of the whole transaction, not of an individual contract.

### Finding Description
`consumeMultiSignFee` checks `trx.getInstance().getRawData().getSignatureCount() > 1` once, then loops over every `Contract` in the transaction and subtracts `fee` from the owner of *each* contract: [1](#0-0) 

`consumeMemoFee` follows the identical pattern: it checks whether the transaction-level `data` field is non-empty once, but then re-applies `fee` for every contract in `getContractList()`: [2](#0-1) 

Both `fee` values (`getMultiSignFee()`, `getMemoFee()`) are single scalar values fetched once, analogous to `msg.value` being read once but then applied inside a loop body multiple times — the loop should apply the fee once per transaction, not once per contract, because signature count and memo/data are transaction-wide attributes, not per-contract attributes. If a single transaction packs multiple `Contract` entries (java-tron protobuf `Transaction.raw` defines `repeated Contract contract`, historically supporting multiple contracts per transaction), each additional contract in the same transaction causes the same fixed fee to be deducted again from its owner and credited again into the black hole (or burned via `burnTrx`), multiplying the effective fee collected/burned relative to what a single memo/multi-sig transaction should cost.

### Impact Explanation
This causes accounting corruption analogous to the reported bug: the same conceptual "one-time" fee (multi-sign fee, memo fee) is deducted and credited multiple times for a single transaction if it carries multiple contracts, over-charging affected owner accounts and inflating the amount burned/credited to the black hole beyond the intended per-transaction fee. This diverges from the intended fee model and could cause consensus-relevant state divergence between nodes only if this logic differs across versions, but at minimum it is an economic/accounting correctness issue reachable directly from a broadcast transaction.

### Likelihood Explanation
Likelihood depends on whether the network currently permits transactions with more than one `Contract` in `getContractList()`; if multi-contract transactions are still structurally accepted by validation, then any user submitting a transaction with multiple contracts, more than one signature, and non-empty `data` would trigger the duplicated fee deduction on every submission — making this straightforwardly reachable via a normal broadcast transaction. I could not fully confirm within available tool calls whether current validation explicitly restricts transactions to a single contract, so likelihood cannot be certified as high with full confidence.

### Recommendation
Compute and apply the multi-sign fee and memo fee once per transaction (e.g., against the first/primary owner address, or split appropriately across owners with the total fixed at `fee` rather than `fee * contractCount`), rather than inside the `for (Contract contract : contracts)` loop which re-applies the full fee on each iteration.

### Proof of Concept
Not executable from the available context; the reasoning is derived directly from the loop structure in `consumeMultiSignFee` and `consumeMemoFee` in `Manager.java`, where `fee` is a single value fetched before the loop but `adjustBalance(...)`/`burnTrx(fee)` is invoked inside the loop body once per contract entry.

  public void consumeMultiSignFee(TransactionCapsule trx, TransactionTrace trace)
      throws AccountResourceInsufficientException {
    if (trx.getInstance().getSignatureCount() > 1) {
      long fee = getDynamicPropertiesStore().getMultiSignFee();
      boolean disableJavaLangMath = getDynamicPropertiesStore().disableJavaLangMath();
      List<Contract> contracts = trx.getInstance().getRawData().getContractList();
      for (Contract contract : contracts) {
        byte[] address = TransactionCapsule.getOwner(contract);
        AccountCapsule accountCapsule = getAccountStore().get(address);
        try {
          if (accountCapsule != null) {
            adjustBalance(getAccountStore(), accountCapsule, -fee, disableJavaLangMath);

            if (getDynamicPropertiesStore().supportBlackHoleOptimization()) {
              getDynamicPropertiesStore().burnTrx(fee);
            } else {
              adjustBalance(getAccountStore(), this.getAccountStore().getBlackhole(), +fee,
                  disableJavaLangMath);
            }
          }
        } catch (BalanceInsufficientException e) {
          throw new AccountResourceInsufficientException(
              String.format("account %s insufficient balance[%d] to multiSign",
                  StringUtil.encode58Check(address), fee));
        }
      }

      trace.getReceipt().setMultiSignFee(fee);
    }
  }

      throws AccountResourceInsufficientException {
    if (trx.getInstance().getRawData().getData().isEmpty()) {
      // no memo
      return;
    }

    long fee = getDynamicPropertiesStore().getMemoFee();
    if (fee == 0) {
      return;
    }
    boolean disableJavaLangMath = getDynamicPropertiesStore().disableJavaLangMath();
    List<Contract> contracts = trx.getInstance().getRawData().getContractList();
