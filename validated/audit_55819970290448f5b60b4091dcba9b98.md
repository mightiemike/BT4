## Title
Relayer-Prepaid Meta-Transaction Deposits Can Be Permanently Burned Instead of Refunded via Self-Triggered Account Deletion - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
In NEAR meta-transactions (`Delegate`/`DelegateV2`), a relayer prepays the attached deposit for inner actions, but if an inner action fails, the deposit-refund receipt is always addressed to the delegate-action **sender** (`sender_id`), not the relayer, by protocol design. If the sender deletes her own account before that refund receipt is processed, the refund fails with `AccountDoesNotExist` and the runtime unconditionally burns the deposit into `other_burnt_amount` rather than returning it to anyone. A malicious or careless meta-transaction sender can therefore cause a relayer's prepaid funds to be permanently destroyed, with no recovery path — the direct analog of the reported Moloch "creating proposal is not trustless" bug class (a failed-transfer path silently forfeiting third-party value).

### Finding Description
When a relayer submits a `Delegate`/`DelegateV2` action on behalf of a sender (`Alice`), the runtime spawns a new inner receipt whose `predecessor_id` is set to `sender_id`, not the relayer: [1](#0-0) 

The code comment explicitly documents that if the inner action fails, "deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction," even though the relayer is the one who actually prepaid the deposit. This is confirmed and flagged as a financial risk in the architecture docs: [2](#0-1) 

If the sender's account has been deleted by the time the deposit-refund receipt (a `system`-predecessor receipt targeting the sender as `balance_refund_receiver()`) is processed, `check_account_existence` explicitly rejects transfers to non-existent accounts for refund receipts — refunds are never allowed to (re)create an account: [3](#0-2) [4](#0-3) 

When that happens, the runtime does not attempt any fallback recovery — it unconditionally burns the entire deposit into `other_burnt_amount`: [5](#0-4) 

This burn-on-failed-refund behavior is intentional and documented: [6](#0-5) 

and is unit-tested for the "refund to missing account" case: [7](#0-6) 

Critically, deleting one's own account is entirely self-service and requires no special privilege — only the account owner's own full-access key, with the only defensive check being zero locked stake: [8](#0-7) 

Putting these together: `Alice` (the meta-tx sender) fully controls both (a) whether her inner delegated action fails (she can simply target a method/receiver that will fail), and (b) the timing of her own `DeleteAccount` transaction relative to the cross-shard/cross-block arrival of the deposit-refund receipt. Because deposit refunds travel as ordinary receipts (subject to normal cross-shard/delayed-queue latency), Alice has a practical window to submit `DeleteAccount` before the refund lands, causing the relayer's deposit to be burned instead of refunded to either party.

### Impact Explanation
This causes concrete, permanent loss of third-party funds (the relayer's prepaid deposit) with zero economic benefit to anyone — the tokens are destroyed via `other_burnt_amount`, not merely misdirected. Relayer services (a normal, expected use case for NEP-366 meta-transactions) are exposed to griefing by any sender they relay for: a sender can cause arbitrarily large relayer-funded deposits to be irrecoverably burned by combining a guaranteed-to-fail inner action with a self-account-deletion timed to land after the failure but before the resulting refund receipt executes. This matches the "permanently frozen/lost funds" criterion from an unprivileged, single-signer-reachable path (meta-transaction sender), directly analogous to the reported Moloch bug class where a blocked/failed transfer path causes tribute funds to be irrecoverably diverted from the rightful owner.

### Likelihood Explanation
The attack requires only standard, unprivileged capabilities: (1) being a meta-transaction sender who agrees to have a relayer submit a `Delegate`/`DelegateV2` action with an attached deposit on an inner action that the sender can guarantee will fail (e.g., targeting a nonexistent method or account), and (2) owning a full-access key on the same account to submit a self-`DeleteAccount` transaction. Both preconditions are trivially satisfiable by any account holder; no validator collusion, network-layer manipulation, or privileged access is needed. The main variable is timing precision (landing the deletion between the inner-action failure and refund-receipt execution), which is influenced by cross-shard/delayed-queue latency the sender can observe and repeatedly attempt across blocks/epochs if relayers do not defend against it.

### Recommendation
- Consider refunding deposit failures for meta-transaction inner actions to the relayer (the actual payer) rather than always to `sender_id`, or at minimum give relayers a way to specify/verify the refund recipient (similar to `promise_refund_to`/`refund_to` already supported in `ActionReceiptV2`) before agreeing to relay a transaction.
- Alternatively, when a deposit-refund's `balance_refund_receiver()` account does not exist, instead of unconditionally burning to `other_burnt_amount`, consider routing the amount to a recoverable location (e.g., queued for governance-driven recovery) or preventing self-account-deletion while there are refund receipts outstanding that reference the account as a refund target.
- Document this griefing vector clearly for relayer implementers so they can defensively check sender account status/history before agreeing to prepay deposits, and/or require senders to bond/stake against such griefing.

### Proof of Concept
1. Relayer `R` agrees to relay a `SignedDelegateAction` for sender `Alice`, containing one inner action (e.g., a `FunctionCall` with a non-existent `method_name` and an attached `deposit`) that is guaranteed to fail at execution (`ActionErrorKind::FunctionCallError` or similar), per the dispatch in `apply_delegate_action`. [9](#0-8) 
2. `R`'s relayed transaction executes; the inner action fails, and the runtime creates a deposit-refund receipt with `predecessor_id`/refund target = `Alice` (not `R`), per the documented refund semantics. [2](#0-1) 
3. Before that refund receipt is processed on Alice's shard (it may cross shards / sit in a delayed queue for at least one block), Alice submits her own `DeleteAccount` transaction using her full-access key; `check_actor_permissions` allows this unconditionally (locked stake is zero). [8](#0-7) 
4. When the deposit-refund receipt finally executes, `check_account_existence` rejects the transfer because Alice's account no longer exists and refunds are barred from (re)creating accounts. [4](#0-3) 
5. The runtime detects `receipt.predecessor_id().is_system()` and the failed result, and burns the entire deposit into `other_burnt_amount` — the relayer's funds are gone permanently, with no code path to recover or redirect them. [5](#0-4)

        init_test_logger();
        let key = SecretKey::from_seed(KeyType::ED25519, "refund-target").public_key();
        let account_id = derive_universal_account_id(&state_init_for(&[key]).to_raw());
        let (runtime, tries, root, apply_state, _signers, epoch) = setup_runtime(
            vec![alice_account()],
            Balance::from_near(100),
            Balance::ZERO,
            Gas::from_teragas(1000),
        );

        let result = runtime
            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,
                from_ref(&Receipt::new_balance_refund(&account_id, funding())),
                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);

        // Assert on the reason, not just the absence: without this the test would

        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
        assert!(
            get_account(&state, &account_id).unwrap().is_none(),

        );
