## Analysis: Unchecked `Result` dereference in `receipt_filter_fn` causing a transaction-triggered chunk-processing panic

### Title
Unchecked error result from `receiver_shard_id()` causes a deterministic chunk-application panic in `receipt_filter_fn` - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally `.unwrap()`s the `Result` returned by `Receipt::receiver_shard_id`, which can legitimately return `Err(EpochError::ShardingError)` for a `GlobalContractDistribution` receipt whose `target_shard` cannot be resolved to a current shard. This mirrors the CVE-2024-56776 bug class (dereferencing a possibly-erroneous return value without checking it first), except here the "error pointer" is a Rust `Result::Err` and dereferencing it via `.unwrap()` triggers a `panic!` instead of the intended graceful error path.

### Finding Description
`receiver_shard_id` on `Receipt` explicitly documents that a `GlobalContractDistribution` receipt's `target_shard` may originate from an arbitrarily old shard layout, and falls back to `shard_layout.resolve_to_current_shard(target_shard)`, returning `Err(EpochError::ShardingError(...))` when the shard cannot be resolved: [1](#0-0) 

`resolve_to_current_shard` handles multi-generation resharding correctly only for `ShardLayoutV3` (dynamic resharding), which walks the full `shards_split_map`. For `ShardLayout::V0/V1/V2` (static resharding) it falls back to a **single-generation** `get_children_shards_ids` lookup: [2](#0-1) 

versus the full-history walk in V3: [3](#0-2) 

The consumer of this fallible call, however, does not check the `Result` at all: [4](#0-3) 

This `receipt_filter_fn` is invoked from `DelayedReceiptQueueWrapper::pop`, which is called on every delayed receipt drained during `Runtime::process_delayed_receipts` inside `Runtime::apply` — the core state-transition function executed by every validator/node applying a chunk: [5](#0-4) 

A repository test explicitly documents and reproduces this exact failure mode for the dynamic-resharding (V3) case, confirming the underlying hazard and that the class of bug is only mitigated for V3 layouts, not for static (V1/V2) shard layouts: [6](#0-5) [7](#0-6) 

The `GlobalContractDistribution` receipt is created purely from an ordinary, unprivileged transaction: any account can trigger `DeployGlobalContract`, which calls `initiate_distribution`, embedding the current shard as `target_shard` in the resulting receipt: [8](#0-7) 

If that receipt is delayed (e.g. due to compute/proof-size limits) and the network undergoes shard splits across which `resolve_to_current_shard` cannot resolve the historical `target_shard` (guaranteed unresolvable for static/V1/V2 layouts across 2+ resharding generations, and also possible if a shard is otherwise absent from the split history), `receiver_shard_id` returns `Err`, and the unguarded `.unwrap()` in `receipt_filter_fn` panics.

### Impact Explanation
A panic inside `Runtime::apply`/`process_delayed_receipts` occurs deterministically on every node applying the same chunk (since the delayed receipt queue and shard layout are part of consensus state), so this is not a single-node crash but a **network-wide, transaction-triggered halt**: chunk production/application for the affected shard stops on all honest validators simultaneously once the stale receipt is popped from the delayed queue. This matches the "transaction-triggered halt" acceptance criterion — availability impact only, no funds/balance corruption, consistent with the CVSS 3.1 profile of the analog CVE (`C:N/I:N/A:H`).

### Likelihood Explanation
Reaching this path requires only: (1) an ordinary account submitting a `DeployGlobalContract` transaction, and (2) enough chunk congestion or specific timing to keep the resulting `GlobalContractDistribution` receipt in the delayed queue while the network undergoes shard splits that the current shard layout's split history cannot fully resolve for that receipt's `target_shard`. This is fully attacker-influenceable (an attacker can deliberately congest the shard to delay their own distribution receipt) and requires no validator or privileged access — a single unprivileged transaction sender plus normal (or force-triggered, on dynamic-resharding-enabled deployments) resharding activity suffices, and is guaranteed to trigger under static (V1/V2) shard layouts across any two resharding generations touching the receipt's original shard.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` (and the `epoch_info_provider.shard_layout(...).unwrap()` call in the same function) with proper error propagation — return the filter result as `Result<bool, RuntimeError>` (or equivalent) and have `DelayedReceiptQueueWrapper::pop` propagate the error instead of panicking, consistent with how other storage/consistency errors are surfaced (`StorageError::StorageInconsistentState`) elsewhere in `runtime/runtime/src/lib.rs`. Additionally, extend `resolve_to_current_shard`'s multi-generation walk (or an equivalent split-history reconstruction) to static V1/V2 shard layouts so `receiver_shard_id` does not return `Err` for legitimately delayed cross-resharding `GlobalContractDistribution` receipts.

### Proof of Concept
1. Deploy a global contract from any account (`DeployGlobalContract` action), producing a `GlobalContractDistributionReceipt` whose `target_shard` is the signer's current shard (`runtime/runtime/src/global_contracts.rs:143-171`).
2. Saturate compute/proof-size limits on that shard so the distribution receipt is pushed to the delayed-receipt queue rather than processed immediately.
3. Trigger (or wait for) two shard-split resharding events on the network's shard layout such that the receipt's original `target_shard` is no longer directly present in the current layout and cannot be resolved via the (single-generation, for V1/V2) `resolve_to_current_shard` fallback.
4. When the delayed queue is eventually drained and the stale receipt is popped, `DelayedReceiptQueueWrapper::receipt_filter_fn` calls `receiver_shard_id(&shard_layout).unwrap()`, which panics on the `Err(EpochError::ShardingError)`, halting chunk application on every node processing that shard.

This exact scenario (minus the static/V1-V2 restriction) is reproduced by the repository's own regression test: [9](#0-8)

```rust
fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}
```
