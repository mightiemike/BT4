### Title
Global contract class cache skips reorg/revert re-validation for Cairo 0 classes, enabling execution against a stale (non-committed) class declaration - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` re-validates a class-hash's declaration status against the current state (`is_declared`) only for Cairo 1 classes retrieved from the process-global `ContractClassManager` cache. Cairo 0 classes bypass this check entirely, even though the same staleness scenario the code explicitly guards against for Cairo 1 ("it might contain a declared class from a reverted block") applies identically to Cairo 0.

### Finding Description
The global contract-class cache (`RawClassCache` / `GlobalContractCache`, in `crates/blockifier/src/state/global_cache.rs`) is process-lifetime scoped and shared across block executions, independent of any particular block's committed state. [1](#0-0) 

When `StateReaderAndContractManager` resolves a class hash to a runnable compiled class, it first checks this global cache. For every variant except V0 it calls back into the state reader's `is_declared` to confirm the cached class is still declared in the current state; for V0 it skips this check unconditionally: [2](#0-1) 

The comment on the branch makes the threat model explicit: cache existence "does not guarantee" declaration, because the cache "might contain a declared class from a reverted block." This directly parallels the external report's root cause — code proceeding under the unchecked assumption that a cache reflects the current, canonical state. The mitigation (re-validate against state before trusting the cache) was applied only to the Cairo 1 branch; the Cairo 0 branch has no equivalent modifier/guard.

This asymmetry is also encoded in the test suite: the Cairo 1 path has an explicit `cached_but_verification_failed_after_reorg_scenario` test that exercises and expects `UndeclaredClassHash` after a simulated reorg, while `cairo_0_cached_scenario` has no `is_declared` expectation at all and always returns `Ok`, confirming this is not an incidental oversight in these tests but a deliberate omission for the V0 path. [3](#0-2) 

`is_declared` itself is state-number-scoped (checks the class's declaration block number against the reader's `latest_block`), so it correctly reflects reorgs/reverts when it is actually invoked: [4](#0-3) 

Because the global cache is never scoped or invalidated per state number for the V0 path, once a Cairo 0 class hash is populated into `contract_class_manager` (e.g., via declaration in a block that is later reverted/discarded, such as after a reorg or a batcher retry on a different fork), any later `get_compiled_class` call for that class hash on a state reader pointed at the post-revert state will still return the cached V0 class and be treated as declared, with no re-check against the reader's actual state.

### Impact Explanation
If a Cairo 0 class becomes cached under a class hash that is subsequently not declared in the canonical/committed state (post-reorg/revert), a node whose global cache still holds that entry will accept and execute transactions that reference it as if it were legitimately declared, while a node executing from scratch (or with an empty/cleared cache) will correctly reject the same transaction with `UndeclaredClassHash`. This produces execution divergence between otherwise-honest nodes for the same block — different transaction outcomes, different resulting state, and potentially a different committed state root/block hash for the same block content, which is a consensus-breaking condition (honest-node divergence) rather than a mere state-reader inefficiency.

### Likelihood Explanation
This is reachable purely by a sequence of ordinary, permissionless actions: (1) an unprivileged sender submits a `DECLARE`(V0-compiled or legacy) transaction whose block is later reorganized/discarded on that node (a normal occurrence the codebase itself anticipates, as shown by the explicit reorg-handling comment/tests for the V1 path), and (2) any subsequent transaction from any sender referencing that class hash is processed against the now-stale global cache entry. No attacker-controlled timing beyond ordinary chain reorganization/block-discard behavior is required, and the bug is triggered on the "honest" code path, not a malicious-operator or malicious-peer path.

### Recommendation
Apply the same `is_declared` re-validation to the Cairo 0 (`RunnableCompiledClass::V0`) branch in `get_compiled_from_class_manager` that is already applied to non-V0 variants, removing the special-cased `RunnableCompiledClass::V0(_) => {}` no-op arm so that every cache hit — regardless of Cairo version — is confirmed against the current state's declaration status before being trusted and returned.

### Proof of Concept
1. A class `C` (Cairo 0 / deprecated) is declared in block `N` on a sequencer; `get_compiled_class(C)` is invoked during execution of that block, causing `ContractClassManager::set_and_compile` to insert `C` into the process-global `RawClassCache`. [5](#0-4) 
2. Block `N` is reverted/discarded on this node (e.g., due to a fork choice change or batcher rollback) — the storage/state reader (`ApolloReader`, scoped by `latest_block`/`StateNumber`) no longer reflects `C` as declared, but the global cache entry for `C` is untouched.
3. A new transaction invoking a contract with class hash `C` is submitted and executed. `get_compiled_from_class_manager` hits the cache, matches `RunnableCompiledClass::V0(_) => {}`, skips `is_declared`, increments the cache-hit metric, and returns the stale class as valid. [6](#0-5) 
4. A peer node without that stale cache entry (fresh cache, or one that never executed block `N`) correctly returns `StateError::UndeclaredClassHash(C)` for the same transaction, as demonstrated by the analogous, already-tested Cairo 1 reorg scenario. [7](#0-6)

impl<S: FetchCompiledClasses> StateReaderAndContractManager<S> {
    fn get_compiled_from_class_manager(
        &self,
        class_hash: ClassHash,
    ) -> StateResult<RunnableCompiledClass> {
        if let Some(runnable_class) =
            self.contract_class_manager.get_runnable(&class_hash, &self.native_classes_whitelist)
        {
            match &runnable_class {
                RunnableCompiledClass::V0(_) => {}
                _ => {
                    // The Cairo1 class is cached; verify it is declared,
                    // since existence in the cache does not guarantee that
                    // (it might contain a declared class from a reverted block, for example).
                    if !self.state_reader.is_declared(class_hash)? {
                        return Err(StateError::UndeclaredClassHash(class_hash));
                    }
                }
            }
            self.increment_cache_hit_metric();
            self.update_native_metrics(&runnable_class);
            return Ok(runnable_class);
        }

impl FetchCompiledClasses for ApolloReader {
    fn get_compiled_classes(&self, class_hash: ClassHash) -> StateResult<CompiledClasses> {
        self.get_compiled_class_from_db(class_hash)
    }

    fn is_declared(&self, class_hash: ClassHash) -> StateResult<bool> {
        let state_number = StateNumber(self.latest_block);
        let class_declaration_block_number = self
            .reader()?
            .get_state_reader()
            .and_then(|sr| sr.get_class_definition_block_number(&class_hash))
            .map_err(|err| StateError::StateReadError(err.to_string()))?;
        Ok(
            matches!(class_declaration_block_number, Some(block_number) if block_number <= state_number.0),
        )
    }
