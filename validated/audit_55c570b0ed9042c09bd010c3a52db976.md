### Title
Unbounded per-filter log queue growth via public `eth_newFilter` with no capacity/element cap - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogFilterAndResult.java`)

### Summary
`LogFilterAndResult` backs each JSON-RPC log filter with a capacity-unbounded `LinkedBlockingQueue`, and `TronJsonRpcImpl.handleLogsFilter`/`processLogFilterEntry` unconditionally appends every matching `LogFilterElement` to that queue on every block with no per-filter element cap. An unprivileged caller can create a broad (topic/address-less) filter via `eth_newFilter` and simply never call `eth_getFilterChanges`/`eth_getFilterLogs`, causing the queue to accumulate matching log entries for the entire filter lifetime.

### Finding Description
`LogFilterAndResult` constructs `result` as `new LinkedBlockingQueue<>()` with no bound, and its `add()` implementation is a bare `result.add(logFilterElement)` with no size check. [1](#0-0) 

`TronJsonRpcImpl.handleLogsFilter` iterates all registered filters (`eventFilter2ResultFull`/`eventFilter2ResultSolidity`) on every incoming `LogsFilterCapsule` (i.e., per block/tx log-emission event) and, for every filter whose block range and bloom match, calls `logFilterAndResult.getResult().addAll(localResults)` with no cap on queue size. [2](#0-1) 

The only server-side controls present are: (1) `maxLogFilterNum`, which caps the *number of filters* a client can register, not the size of any individual filter's queue, and (2) `EXPIRE_SECONDS` (300s) lazy expiration, checked only opportunistically inside `processLogFilterEntry`/`handleBLockFilter` when a new block/log event arrives — i.e., the filter (and its queue) is only removed on the *next* event after expiry, and only if some later event triggers the iteration. [3](#0-2) [4](#0-3) 

Note the code comment on the shared `logElementCache` explicitly assumes a bounded rate ("300s * tps(1000) * 1 log/tx ≈ 300_000") and caps that shared cache at 300,000 entries — but this bound is applied only to the deduplication cache, not to each filter's own `result` queue, which can independently reference an unbounded number of `LogFilterElement` objects for the full 300-second window per filter. [5](#0-4) 

An unprivileged attacker only needs public JSON-RPC access to call `eth_newFilter` with a broad `LogFilter` (no address/topic constraints) and then simply avoid ever calling `eth_getFilterChanges`/`eth_getFilterLogs` (which would call `popAll()` to drain the queue). Every block containing matching logs on a busy chain adds more `LogFilterElement` references into this filter's queue with no eviction until drained.

### Impact Explanation
On a full node processing meaningful transaction/log volume, each unpolled broad filter accumulates one `LogFilterElement` reference per matching log for up to the 300-second `EXPIRE_SECONDS` window before being lazily reclaimed. Because the number of concurrent filters is bounded by `maxLogFilterNum` (large, e.g. tens of thousands by default per the code's own tuning comment) and no per-filter element cap exists, an attacker can repeatedly create fresh broad filters (churning through the `maxLogFilterNum` budget as old ones expire) to sustain elevated heap pressure over time from unbounded, unpolled queues. This is a real, code-supported memory-growth avenue distinct from the (correctly capped) shared `logElementCache`.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: `eth_newFilter` is an unauthenticated public JSON-RPC call, requires no fee, and broad/empty topic filters are permitted by the API. The attack is fully repeatable and does not require abnormal chain conditions — any ordinary block/log throughput drives queue growth for the duration a filter remains unpolled (up to 300s per filter, replayable by re-registering new filters). The severity is naturally self-limited by `EXPIRE_SECONDS` and `maxLogFilterNum`, so growth, while real and un-priced, is not literally infinite/unbounded per filter — it is bounded by (chain log throughput during 300s) × (number of live filters up to `maxLogFilterNum`), which for a busy chain and large `maxLogFilterNum` could still be materially memory-significant.

### Recommendation
Add a hard capacity bound to each filter's result queue (e.g., use a bounded `LinkedBlockingQueue<>(maxCapacity)` or track/limit `result.size()` in `add()`/`addAll()`), dropping oldest entries or rejecting further inserts (and optionally marking the filter as "overflowed" so clients know results were truncated) once the cap is hit — mirroring the existing bound already applied to `logElementCache`. Additionally, consider proactively expiring/removing filters via a background sweep rather than relying solely on lazy removal during the next matching event.

### Proof of Concept
Java integration test outline (extends existing `HandleLogsFilterTest`/`JsonrpcServiceTest` patterns):
1. Register a broad `LogFilterAndResult` via the same path `eth_newFilter` uses (construct `FilterRequest` with empty `address`/`topics`), inserted into `eventFilter2ResultFull`.
2. Repeatedly invoke `TronJsonRpcImpl.handleLogsFilter(LogsFilterCapsule)` with synthetic `LogsFilterCapsule` instances carrying non-trivial `TransactionInfo`/log lists, simulating N blocks within the 300s expire window, without ever calling `popAll()`.
3. Assert `logFilterAndResult.getResult().size()` grows linearly/unbounded with N and is never capped, while `logElementCache.size()` is separately capped at 300,000 — demonstrating the discrepancy in bounding strategy.
4. Optionally measure heap growth (e.g., via `Runtime.getRuntime().totalMemory()-freeMemory()`) across iterations to show it does not plateau until the test manually calls `popAll()` or the filter is expired/removed.

  private void processLogFilterEntry(
      Map.Entry<String, LogFilterAndResult> entry,
      Map<String, LogFilterAndResult> eventFilterMap,
      LogsFilterCapsule logsFilterCapsule) {
    LogFilterAndResult logFilterAndResult = entry.getValue();
    if (logFilterAndResult.isExpire()) {
      eventFilterMap.remove(entry.getKey());
      return;
    }

    long blockNumber = logsFilterCapsule.getBlockNumber();
    long fromBlock = logFilterAndResult.getLogFilterWrapper().getFromBlock();
    long toBlock = logFilterAndResult.getLogFilterWrapper().getToBlock();
    if (!(fromBlock <= blockNumber && blockNumber <= toBlock)) {
      return;
    }

    if (logsFilterCapsule.getBloom() != null && !logFilterAndResult.getLogFilterWrapper()
        .getLogFilter().matchBloom(logsFilterCapsule.getBloom())) {
      return;
    }

    LogFilter logFilter = logFilterAndResult.getLogFilterWrapper().getLogFilter();
    List<LogFilterElement> elements =
        LogMatch.matchBlock(logFilter, blockNumber, logsFilterCapsule.getBlockHash(),
            logsFilterCapsule.getTxInfoList(), logsFilterCapsule.isRemoved());

    List<LogFilterElement> localResults = new ArrayList<>(elements.size());
    for (LogFilterElement element : elements) {
      LogFilterElement cachedElement;
      try {
        // compare with hashcode() first, then with equals(). If not exist, put it.
        cachedElement = logElementCache.get(element, () -> element);
      } catch (ExecutionException e) {
        logger.error("Getting/loading LogFilterElement from cache fails", e); // never happen
        cachedElement = element;
      }
      localResults.add(cachedElement);
    }
    logFilterAndResult.getResult().addAll(localResults);
