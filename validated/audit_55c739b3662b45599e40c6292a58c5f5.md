### Title
Multi-signature threshold bypass via signature-bytes deduplication (instead of signer-address deduplication) in `ValidateMultiSign` precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompiled contract, which any smart contract (and therefore any anonymous `TriggerSmartContract` caller) can invoke to validate a TRON multi-sig permission threshold, deduplicates counted signatures by comparing the **exact signature bytes**, not solely by the **recovered signer address**. Because ECDSA signatures are malleable/non-deterministic, one key holder can supply two distinct signature byte-strings that both recover to the same address, and the loop will count that single signer's weight twice. This mirrors the reported Shardus Core root cause: "signatures are counted, instead of signers."

### Finding Description
`ValidateMultiSign.execute()` iterates over the caller-supplied signature array and accumulates `totalWeight` toward `permission.getThreshold()`: [1](#0-0) 

The dedup guard only skips a signature when the **merged (address+rawSignatureBytes)** value has been seen before:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
If `recoveredAddr` was already counted but the current `sign` bytes differ from any previously seen exact bytes for that address, the function does **not** skip — it falls through and adds `weight` again for the same signer. ECDSA signature malleability (flipping `s` to `n-s` and the recovery id) trivially produces a second, distinct-byte, still-valid signature that recovers to the identical address, without needing the private key again. This is structurally the same flaw as the Shardus `validateClosestActiveNodeSignatures` bug: the loop treats "one more valid signature" as "one more valid signer," rather than tracking unique signer identities.

By contrast, the analogous on-chain `checkWeight` function used for regular transaction signature verification already deduplicates by recovered address (post `VERSION_4_7_1` hard fork) and rejects with "has signed twice": [2](#0-1) 
That fork is long activated on mainnet (fork value 27, well below the currently listed fork ceiling of 36 in `Parameter.java`), meaning `checkWeight` is safe. The `ValidateMultiSign` precompile, however, was not updated with equivalent address-only dedup logic and remains reachable by any contract call.

### Impact Explanation
`ValidateMultiSign` returns `true`/1 once `totalWeight >= permission.getThreshold()`. If a smart contract (e.g., a custom multisig wallet, exchange, or escrow contract built on TRON) relies on this precompile to enforce an M-of-N threshold, a single colluding/compromised signer whose individual weight is less than the threshold can forge a second malleable signature of the same message and pass the check alone — effectively bypassing the multi-party authorization requirement. This can lead to unauthorized account/asset operations authorized purely by this precompile's result (e.g., releasing funds, executing privileged contract logic gated by `validatemultisign`), i.e. direct loss-of-funds / unauthorized-account-operation impact.

### Likelihood Explanation
Likelihood is high for any dApp/contract that depends on `ValidateMultiSign` for its own multisig gating logic, since:
- The precompile is called via ordinary `TriggerSmartContract`, reachable by any anonymous account.
- ECDSA signature malleability (deriving a second valid signature from one) is a well-known, cheap, offline operation requiring no additional access to the private key.
- No special network position, staking, or privileged role is required — this is purely a caller-supplied-input validation bug in the precompiled contract logic itself.

The severity depends on how many downstream contracts actually rely on `ValidateMultiSign` to enforce distinct-signer thresholds, which cannot be determined from this repository alone.

### Recommendation
Change the dedup check to key strictly on `recoveredAddr`: once an address has contributed weight, skip it for all further entries regardless of the raw signature bytes, e.g. track only `executedAddrs` (a set of addresses) and check `if (executedAddrs.contains(recoveredAddr)) continue;` before adding weight, removing the byte-exact `sign` comparison branch entirely. This aligns the precompile's logic with the corrected `TransactionCapsule.checkWeight` dedup-by-address approach.

### Proof of Concept
1. Compute `hash = sha256(address || permissionId || data)` as done by `ValidateMultiSign.execute()` (lines 1062–1064).
2. Let `keyA` be one signer in the target permission with weight `w < threshold`.
3. Sign `hash` with `keyA` to get `sig1 = (r, s, v)`.
4. Derive the malleable counterpart `sig2 = (r, n-s, 1-v)` (standard secp256k1 malleability transform) — this is a different byte string but recovers to the same address as `sig1`.
5. Call `validatemultisign(address, permissionId, hash, [sig1, sig2])` on the precompile via a `TriggerSmartContract`.
6. In the loop: iteration 1 adds `weight` for `keyA` (`totalWeight = w`); iteration 2 sees `recoveredAddr` already in `executedSignList` but `sign` (merged with `sig2`) is different from the previously stored merged value for `sig1`, so it does **not** `continue`, and `totalWeight` becomes `2w`.
7. If `2w >= permission.getThreshold()` while `w < threshold`, the precompile returns `true`/1 — a single signer bypasses the multi-signer threshold. [3](#0-2)
