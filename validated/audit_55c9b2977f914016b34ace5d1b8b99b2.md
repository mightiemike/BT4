## Analysis Result

### Title
Unbounded Recursive Receipt-Chain Walk in `tx`/`tx_status` RPC Causes Stack-Exhaustion Crash - ([File: chain/chain/src/chain.rs])

### Summary
The CVE describes a heap-buffer overflow in Lua's `luaG_runerror` caused by unbounded recursion during nested/recursive error handling with no depth guard. The analogous bug class in nearcore is an **unbounded, depth-unchecked recursive function** that walks a chain of execution outcomes/receipts, reachable directly from a JSON-RPC caller querying transaction status — in contrast to a sibling feature in the same codebase that explicitly recognizes and guards against exactly this failure mode.

### Finding Description
`get_recursive_transaction_results` in `chain/chain/src/chain.rs` recursively walks the DAG of execution outcomes for a transaction with **no depth limit whatsoever**: [1](#0-0) 

This is called by `get_final_transaction_result` (used by `tx`, `tx_status`, `EXPERIMENTAL_tx_status`) and `get_partial_transaction_result_option`: [2](#0-1) 

These reach the wire through `ViewClientActor::get_tx_status`, invoked for every `tx`/`tx_status` RPC call and for the polling loop that every wallet/client uses after `send_tx`: [3](#0-2) [4](#0-3) 

Critically, the codebase already contains a sibling feature — the `EXPERIMENTAL_receipt_to_tx` RPC — that performs a structurally identical recursive walk over a receipt-parent chain, but that one is explicitly hardened with a `RECEIPT_TO_TX_MAX_DEPTH = 1000` guard and a dedicated `DepthExceeded` error: [5](#0-4) [6](#0-5) 

There is a dedicated regression test proving the team treats chains approaching/exceeding this depth as a real, reachable condition requiring a hard stop rather than unbounded native recursion: [7](#0-6) 

`get_recursive_transaction_results`, which backs the much more heavily used `tx`/`tx_status` endpoints, received no equivalent protection. An attacker-controlled contract can chain many cross-contract self-calls (as demonstrated by the built-in `max_self_recursion_delay`/`recurse` test helpers, which show that hundreds of receipt hops are achievable within a single transaction's gas budget): [8](#0-7) [9](#0-8) 

producing a deep receipt DAG whose walk depth is bounded only by the attacker's willingness to spend gas creating hops (not by any protocol-level cap), unlike the `receipt_to_tx` code path which now hard-caps at 1000.

### Impact Explanation
Native (non-tail-call-optimized) recursion in Rust with no depth bound can exhaust the thread stack, causing an abrupt process abort (`SIGSEGV`/stack overflow guard-page trap) of the RPC-serving process handling the `tx`/`tx_status`/`EXPERIMENTAL_tx_status` request. Because this same query path also backs the standard "wait for transaction to finish" flow used by every RPC client and node operator, a crash here constitutes a transaction/RPC-triggered halt of node availability for view/RPC functionality — matching the accepted "transaction-triggered halt" impact category.

### Likelihood Explanation
An unprivileged transaction sender can, in a single transaction, deploy or invoke a contract that fans out cross-contract calls to grow a linear receipt chain to the maximum depth its attached gas allows, then have any RPC caller query `tx_status`/`tx` for that transaction hash to trigger the unbounded recursive walk on the serving node. No special privileges are required beyond normal transaction submission and an RPC query, both fully in-scope actor capabilities.

### Recommendation
Convert `get_recursive_transaction_results` in `chain/chain/src/chain.rs` from unbounded native recursion to an iterative (worklist/queue-based) traversal, or add an explicit depth counter mirroring the `RECEIPT_TO_TX_MAX_DEPTH` pattern already used by `EXPERIMENTAL_receipt_to_tx`, returning a graceful error (e.g., a new `Error` variant) once the bound is exceeded instead of allowing the native call stack to grow unbounded.

### Proof of Concept
1. Deploy a contract with a `recurse`/self-delaying method similar to `max_self_recursion_delay` in `runtime/near-test-contracts/test-contract-rs/src/lib.rs:894`, that issues a self cross-contract call on each hop until gas is exhausted, maximizing the depth of the resulting receipt chain (demonstrated to reach 56–221+ hops per `integration-tests/src/tests/runtime/test_evil_contracts.rs:94-131`, and unbounded in principle since no protocol-level cap exists on chain length itself).
2. Submit the transaction and, once accepted, call the `tx` or `tx_status` JSON-RPC method (or `EXPERIMENTAL_tx_status`) against the transaction hash on a node tracking the relevant shard.
3. The node invokes `ViewClientActor::get_tx_status` → `Chain::get_partial_transaction_result_option`/`get_final_transaction_result` → `get_recursive_transaction_results`, which recurses once per receipt in the chain with no depth check, unlike the guarded `receipt_to_tx` sibling path.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

    store_update.commit();

    // Query receipt_0 — needs 1001 hops, exceeds MAX_DEPTH=1000.
    let handle = env.node_datas[0].view_client_sender.actor_handle();
    let view_client: &mut near_client::ViewClientActor = env.test_loop.data.get_mut(&handle);

            assert_eq!(receipt_id, receipt_ids[0], "error reports originally queried receipt");
            assert_eq!(limit, 1000, "limit == MAX_DEPTH=1000");
        }
        other => panic!("expected DepthExceeded error, got: {other:?}"),

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);
    let amount = 1u128;
    let gas_fixed = 0;
    let gas_weight = 1;
    let argument_bytes = recursion.saturating_add(1).to_be_bytes();
    promise_batch_action_function_call_weight(
        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );
    promise_return(promise_idx);
}

    // to avoid having separate cases for every possible combination of features.
