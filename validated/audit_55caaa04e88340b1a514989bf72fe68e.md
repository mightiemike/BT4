## Analog Found

### Title
Standby witness reward distribution loses reward dust due to per-witness truncation - (File: `consensus/src/main/java/org/tron/consensus/dpos/IncentiveManager.java`)

### Summary
`IncentiveManager.reward()` splits a fixed reward pool (`totalPay`, the witness standby allowance) among up to 127 standby witnesses proportionally to their vote count. Each witness's share is computed independently with a floating-point ratio and then truncated to a `long`, exactly mirroring the external report's root cause: a total that is supposed to be fully distributed is instead split into several independently rounded-down pieces whose sum is provably less than the original total, leaving part of the intended reward permanently undistributed.

### Finding Description
`reward()` computes, for each standby witness:
```
long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay / voteSum));
``` [1](#0-0) 

This is the same structural flaw as the referenced `transferPlayerRewards()` bug: the total (`totalPay`) is meant to be fully distributed across N recipients, but each recipient's portion is calculated and rounded independently (via `(long)` truncation of a `double`) rather than derived so the pieces sum exactly to the total. Because every truncation can discard up to almost 1 unit, and there are up to 127 recipients (`WITNESS_STANDBY_LENGTH`), the sum of all `pay` values distributed is generally strictly less than `totalPay`. The undistributed remainder is not credited to any account, not carried over to the next cycle, and not burned through any accounted mechanism — it is silently dropped from the reward pool.

This function is invoked from `MaintenanceManager.doMaintenance()` every maintenance cycle for all newly-updated active/standby witnesses: [2](#0-1) 

Unlike `MortgageService.payReward()`, where the brokerage split is computed as `value -= brokerageAmount` (a complementary subtraction that always conserves the original `value`), here each witness's `pay` is computed from scratch via `voteCount * (totalPay/voteSum)`, so there is no complementary subtraction guaranteeing conservation of `totalPay` across all recipients. [3](#0-2) 

### Impact Explanation
The loss is deterministic and identical across all full nodes (same input state produces the same truncated result everywhere), so it does not cause a consensus fork. However, it represents systemic under-distribution of the standby-witness reward pool: on every maintenance cycle a portion of `totalPay` intended for standby witnesses is neither paid to any witness nor otherwise accounted for, resulting in permanent loss of funds from the reward accounting system. Given the reward pool is re-derived every maintenance cycle and applies to up to 127 witnesses, the aggregate leakage accumulates over the life of the chain. This matches the "Low impact" classification of the original finding since per-cycle loss is small (bounded by number of witnesses in truncation error, i.e., sub-unit per witness).

### Likelihood Explanation
`doMaintenance()` runs on a fixed schedule for every maintenance cycle, and `IncentiveManager.reward()` executes unconditionally whenever `voteSum > 0`, which is effectively every cycle with active voting. No adversarial trigger is required — this is a deterministic, guaranteed miscalculation on every maintenance run, giving it high likelihood, consistent with the original report's "High" likelihood rating.

### Recommendation
Change the distribution so the truncation dust is not lost: e.g., accumulate the sum of already-paid `pay` values and pay the last witness (or the remaining pool) the difference `totalPay - sumPaidSoFar`, or use integer-only proportional math (`totalPay * voteCount / voteSum` using integer/BigInteger division consistently) combined with directing the final remainder to a determinate designated recipient (e.g., the last witness in the list or a treasury account), so the sum of distributed rewards always equals `totalPay` exactly.

### Proof of Concept
Example: `totalPay = 100`, 3 standby witnesses with `voteCount` = 33, 33, 34 (`voteSum = 100`).
- Witness1: `pay = (long)(33 * 100/100) = 33`
- Witness2: `pay = (long)(33 * 100/100) = 33`
- Witness3: `pay = (long)(34 * 100/100) = 34`

That example sums correctly, but with fractional ratios (e.g., `voteSum = 3`, `totalPay = 10`, 3 witnesses each with `voteCount = 1`):
- Each witness: `pay = (long)(1 * 10.0/3) = (long)(3.333...) = 3`
- Total distributed = `3 + 3 + 3 = 9`, while `totalPay = 10`.

One unit of the reward pool is never credited to any account, reproducing the same class of "some of the expected rewards are not distributed" bug described in the external report. [1](#0-0)
