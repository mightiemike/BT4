## Finding

### Title
Fund migration TSS signing verification independently re-queries old-TSS balance, letting an unprivileged attacker desync the signed amount and permanently stall/freeze migration funds - (File: universalClient/tss/sessionmanager/sessionmanager.go)

### Summary
The external report describes a case where a staking contract computes a bonding amount from a "free balance" figure that can silently diverge from the balance actually present at the time the action executes, because nothing pins the value used across the two points in time. Push Chain's fund-migration TSS flow has the same structural flaw: the coordinator computes the sweep amount from a *fresh RPC balance query* of the old TSS address, but every other validator independently re-queries the *same* address's balance at a different point in time to reconstruct and verify the signing hash. Because the old TSS address is a plain, publicly known address on the external chain, any unprivileged party can change its balance between these two queries, causing an honest validator's independently recomputed hash to permanently diverge from the coordinator's, blocking TSS quorum and leaving protocol funds stuck under the retired key.

### Finding Description
When a `KEYGEN` event finalizes, `x/utss` opens a `FundMigration` record and Push Chain's `puniversald` binary must sweep the funds sitting at the old TSS-derived address to the new one. The coordinator builds the transaction to be signed via `buildFundMigrationTransaction`, which — when no `claimedAmount` is supplied (the normal initial-setup path) — queries the current on-chain balance of the old TSS address and derives the maximum sweep amount: [1](#0-0) 

That produces `signingReq.SigningHash`, which is the *only* thing broadcast to signing participants in the DKLS setup message: [2](#0-1) 

The transfer amount itself is computed as `balance - gasCost - l1GasFee`: [3](#0-2) 

Each non-coordinator validator does not receive the amount; it must independently rebuild the hash in `verifyFundMigrationSigningRequest`, and it does so by calling `builder.GetFundMigrationSigningRequest(...)` with a `FundMigrationData` struct that leaves `Balance` unset: [4](#0-3) 

An unset `Balance` forces a brand-new RPC balance lookup at verification time, rather than reusing the coordinator's balance snapshot: [5](#0-4) 

The code even documents that a `claimedAmount` parameter exists specifically to reconstruct the hash deterministically "without racing a successful sweep" for the ACK path, but that parameter is never threaded into the pre-signing `verifyFundMigrationSigningRequest` check used by every participating validator before it agrees to sign: [6](#0-5) 

The old TSS address is a plain externally-owned address on the destination chain — it accepts native-token deposits from anyone, with no authentication. Because the coordinator's balance snapshot (setup time) and each validator's balance snapshot (verify time, potentially blocks later, across a multi-round-trip DKLS signing session) are taken independently and are not pinned to a single agreed value, any unprivileged attacker can send a trivial-value transfer to the old TSS address in that window. This changes the queried balance for at least one validator relative to the coordinator, producing a different `maxTransfer`/hash and triggering the hard rejection: [7](#0-6) 

This is precisely the class of bug in the external report: a "free balance" value is used to decide an amount to act on (bond/sweep), but nothing guarantees the same value is used consistently across the steps that must agree on it, so honest, correctly-functioning components can end up computing conflicting results from attacker-influenced state.

### Impact Explanation
Because `MsgVoteFundMigration`/TSS signing requires quorum agreement on the same signing hash, a validator whose independently recomputed hash mismatches the coordinator's will refuse to sign that round entirely (hard error, not a warn-and-continue). If an attacker repeats the trivial deposit on every subsequent migration attempt/retry, the TSS threshold-signing round for that migration record can be perpetually prevented from reaching quorum. This leaves protocol/user funds parked at the old TSS-controlled address indefinitely — a reachable, unprivileged-attacker-triggered permanent freezing of protocol-controlled funds, which falls squarely within the "In scope" impact category (permanent freezing of protocol-controlled funds; mismatched TSS state accepted/rejected through user-reachable flows with honest validators).

### Likelihood Explanation
The old TSS address for an in-flight `FundMigration` is derivable/observable on-chain (it is the previous `TssKey`'s derived EVM address, and `FundMigration` records including `old_tss_pubkey`/chain are stored in `x/utss` state, queryable by anyone). No special role or timing precision is required — a single, arbitrarily small value transfer sent to that address at any point during the (multi-message, network-bound) DKLS signing round is sufficient to desynchronize at least one honest validator's recomputed balance from the coordinator's. Because migrations happen after every `KEYGEN`, an attacker has recurring, low-cost opportunities to repeat this indefinitely, making sustained denial of the migration highly likely for even a modestly motivated attacker.

### Recommendation
Do not let each participant independently re-query the mutable on-chain balance to reconstruct the signing hash. Instead, have the coordinator include the concrete transfer amount (or the source balance it used) as an explicit, signed field of the setup message payload, and have every validator's `verifyFundMigrationSigningRequest` use that pinned value (the same mechanism already implemented for the `claimedAmount`/ACK reconstruction path) to rebuild and compare the hash, only falling back to a fresh RPC query as a sanity bound (e.g., reject if claimed amount exceeds actual current balance) rather than as the primary source of truth for hash equality. This mirrors the external report's own recommendation: introduce an explicit variable that fixes the amount used across all parties instead of re-deriving it from a balance figure that can legitimately move between steps.

### Proof of Concept
1. Wait for (or trigger, if admin cooperation is possible in a testnet) a `KEYGEN` process; `x/utss` opens a `FundMigration` record and exposes `old_tss_pubkey`/chain via query.
2. Derive the old TSS EVM address (`DeriveEVMAddressFromPubkey`, same function used by the coordinator/session manager) from the public `old_tss_pubkey`.
3. As soon as the coordinator's `EventTypeSignFundMigrate` setup round begins, send a minimal-value native-token transfer to the old TSS address on the destination chain from any unprivileged wallet.
4. Depending on transaction landing time relative to each validator's `verifyFundMigrationSigningRequest` RPC balance query (`universalClient/tss/sessionmanager/sessionmanager.go:1048`), at least one honest validator computes a different `maxTransfer`/`SigningHash` than the coordinator's, and its `verifyFundMigrationSigningRequest` returns `"fund migration signing hash mismatch"` (`sessionmanager.go:1054-1061`), causing that validator to abstain from signing.
5. Repeat on each retry attempt; because the attack costs only a minimal transfer and can be repeated indefinitely, the migration event can be kept from reaching TSS quorum, leaving funds stuck under the old TSS key.

// computeFundMigrationTransfer returns the native amount to sweep from the old
// TSS address to the new one: balance - (gasPrice * gasLimit) - l1GasFee.
// The l1GasFee covers OP-stack sequencer data-availability charges (0 for
// non-L2 chains). All validators must compute the same value — any drift
// here breaks the TSS signing hash.
func computeFundMigrationTransfer(balance, gasPrice *big.Int, gasLimit uint64, l1GasFee *big.Int) (*big.Int, error) {
	gasCost := new(big.Int).Mul(gasPrice, new(big.Int).SetUint64(gasLimit))
	totalFee := new(big.Int).Set(gasCost)
	if l1GasFee != nil && l1GasFee.Sign() > 0 {
		totalFee.Add(totalFee, l1GasFee)
	}
	maxTransfer := new(big.Int).Sub(balance, totalFee)
	if maxTransfer.Sign() <= 0 {
		return nil, fmt.Errorf("insufficient balance for gas: balance=%s gasCost=%s l1GasFee=%s",
			balance.String(), gasCost.String(), l1GasFeeString(l1GasFee))
	}
	return maxTransfer, nil
}
