**Rationale:**

`DefaultPropertyMutate` (and its legacy counterpart `DefaultPropertyMutateEvent`) are plain BCS-serialized event payload structs; their fields, including `old_values: Vec<OptionType<PropertyValue>>`, are not attacker-supplied arbitrary bytes decoded from unprivileged input at the point where "prior value" semantics matter. [1](#0-0) 

The `old_values` content is computed deterministically by the trusted Move module `token.move`'s `mutate_tokendata_property` function, which reads the actual on-chain `token_data.default_properties` map to decide whether to push `option::some(*token_data.default_properties.borrow(key))` or `option::none<PropertyValue>()` — an attacker cannot pass arbitrary `old_values` as a transaction argument; this vector is built by VM execution from real state, not from caller-supplied event fields. [2](#0-1) 

There is also no `DefaultPropertyMutateTranslator` in `storage/indexer/src/event_v2_translator.rs` that reinterprets `old_values` against committed state for an authenticated property-history view — no such translator struct exists for this event type in the indexer's event v1/v2 translation module. [3](#0-2) 

Since the event's `old_values` field is only ever generated by the VM from actual current state (not decoded from attacker-controlled bytes at the read/response layer), and no downstream authenticated component reconstructs "prior committed value" from this event field, there is no path by which unprivileged input can force a mismatch between the true prior on-chain `PropertyValue` and what a property-history view reports. The premise that an attacker can "submit" a forged `old_values` entry independent of actual execution-derived state does not hold in this codebase.
