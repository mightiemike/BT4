### Title
Proof-verification bypass via `contains_proof` reuse allows unverified "client-side-proven" Invoke transactions - (File: crates/apollo_transaction_converter/src/transaction_converter.rs)

### Summary
The Buffer Finance report shows how binding a critical value (market direction) to a signature that is *checked but not committed at the time of the original action* lets an attacker later supply an unverified/self-serving value. The sequencer's client-side-proving feature for `RpcInvokeTransactionV3` has an analogous decoupling: transaction hashing commits only to `proof_facts`, while the accompanying `proof` bytes (the actual cryptographic evidence) are neither hashed nor bound per-submission — verification of `proof` is skipped entirely whenever the proof-manager already has *any* entry for the same `proof_facts` hash, regardless of who submitted the original proof or what invoke transaction it belongs to.

### Finding Description
When an `RpcInvokeTransactionV3` carries non-empty `proof_facts`, the gateway spawns `spawn_proof_verification`, which calls `run_proof_verification`: [1](#0-0) 

This function first asks the proof manager `contains_proof(proof_facts)`, and if `true`, **skips cryptographic verification entirely** (`return Ok(false)`), never checking whether the caller-supplied `proof` bytes are actually a valid proof for anything related to *this* transaction. The `proof_facts` used as the dedup key encode only generic facts (proof version, virtual-OS program hash, block hash/number, config hash) — not the sender, calldata, or nonce of the invoke transaction: [2](#0-1) 

Separately, the transaction hash itself only commits to `proof_facts` (conditionally, when non-empty) and explicitly drops the `proof` field when converting `RpcInvokeTransactionV3` to its internal representation: [3](#0-2) [4](#0-3) 

Because `proof_facts` is not bound to sender/calldata, and because a previously-verified `proof_facts` hash causes all *future, unrelated* invoke transactions referencing the same facts to skip verification, an attacker can:
1. Observe any legitimately verified `proof_facts` value (public, since it is part of a broadcast transaction and part of the tx hash).
2. Submit their own `Invoke` transaction (different sender, calldata, nonce) reusing that same `proof_facts` value together with an arbitrary/garbage `proof` field.
3. The gateway's `run_proof_verification` sees `contains_proof == true` and skips verification of the attacker's bogus `proof` outright, storing no new cryptographic guarantee for the attacker's specific transaction.
4. During execution (`validate_proof_facts` in `blockifier`), only structural checks are performed on `proof_facts` (allowed program hash, allowed proof version, block hash/number, config hash) — there is no re-verification of the underlying `proof` bytes at this stage, since the design assumes the gateway/consensus stage already verified it: [5](#0-4) 

This means the security guarantee intended by "client-side proving" (that a submitted Invoke transaction's `proof_facts` claim is backed by a genuine, individually-verified cryptographic proof) is broken for any transaction that piggybacks on a previously seen `proof_facts` value — the check silently degrades to "someone, at some point, submitted a valid proof for this exact facts tuple," not "this transaction's proof is valid."

### Impact Explanation
Because the correctness of `proof_facts`-gated Invoke transactions is normally supposed to be enforced by real cryptographic proof verification, and that verification can be bypassed via the `contains_proof` short-circuit for any subsequent transaction that reuses public `proof_facts` values, this allows unverified transactions to enter the mempool and be treated by the OS/blockifier as validly "client-side proven." Additionally, since the proof-manager cache state (`contains_proof`) is a local, non-consensus piece of node state, different gateway/sequencer nodes can diverge on whether the same submitted `proof` is actually verified or silently skipped, creating a path to honest-node divergence on transaction/tx validity depending on their local proof-manager cache contents, and enabling acceptance of transactions whose proof-based guarantees were never checked for that specific transaction.

### Likelihood Explanation
Reachable directly by any unprivileged transaction sender submitting a standard `Invoke` V3 transaction through the public gateway — no privileged role, operator access, or network-level attack is required. The only prerequisite is knowledge of a previously broadcast `proof_facts` value (which is inherently public, being part of the transaction and its hash).

### Recommendation
Bind proof verification to the specific transaction rather than merely to the `proof_facts` hash: either (a) always cryptographically verify the `proof` supplied with each transaction regardless of whether the same `proof_facts` were seen before, or (b) if caching is required for performance, cache verification results keyed by the hash of `(proof_facts, proof)` together (not `proof_facts` alone), and additionally bind `proof_facts` to transaction-specific data (e.g., sender address/calldata hash) inside the proof itself, so a cached "valid" result cannot be reused by unrelated transactions.

### Proof of Concept
1. Wait for (or induce) a legitimate transaction A with non-empty `proof_facts = F` and valid `proof = P` to be accepted by the gateway; this stores `F` in the proof manager (`contains_proof(F) == true`) via `store_proof_and_spawn_archiving` / `set_proof`. [6](#0-5) 
2. Craft transaction B with a different `sender_address`/`calldata`/`nonce`, but set `proof_facts = F` and `proof = <arbitrary bytes>`.
3. Submit B to the gateway. In `convert_rpc_tx_to_internal_rpc_tx` → `spawn_proof_verification` → `run_proof_verification`, `contains_proof(F)` returns `true`, so `verify_proof` on B's garbage `proof` is never invoked, and `Ok(false)` is returned as if verification "succeeded" (nothing to newly verify). [7](#0-6) 
4. B proceeds through `validate_proof_facts` in `blockifier`, which only checks structural fields of `F` (already known-valid since reused from A), never re-checking B's bogus `proof`. [5](#0-4) 

Note: full confirmation of the exact downstream privilege granted to "client-side-proven" Invoke transactions (e.g., fee/resource exemptions or trusted execution paths) could not be completed within the available exploration; this should be verified further, as it directly determines the severity of the concrete impact (fund loss vs. divergence only).

    /// Runs proof verification: checks if the proof already exists, and if not, verifies it.
    /// Returns `true` if verification was performed, `false` if skipped (proof already stored).
    /// This is the shared verification logic used by both gateway and consensus flows.
    async fn run_proof_verification(
        proof_facts: ProofFacts,
        proof: Proof,
        proof_manager_client: SharedProofManagerClient,
    ) -> Result<bool, TransactionConverterError> {
        let contains_proof = proof_manager_client.contains_proof(proof_facts.clone()).await?;

        if contains_proof {
            return Ok(false);
        }

        let proof_facts_hash = proof_facts.hash();
        let verify_start = Instant::now();
        tokio::task::spawn_blocking(move || {
            starknet_proof_verifier::verify_proof(proof_facts, proof)
        })
        .await
        .expect("proof verification task panicked")?;
        let verify_duration = verify_start.elapsed();
        PROOF_VERIFICATION_LATENCY.record(verify_duration.as_secs_f64());
        info!(
            "Proof verification took: {verify_duration:?} for proof facts hash: \
             {proof_facts_hash:?}"
        );

        Ok(true)
    }

    /// Spawns a verification-only task. Used by the gateway flow, which stores the proof
    /// separately after all validations pass.
    fn spawn_proof_verification(
        &self,
        proof_facts: ProofFacts,
        proof: Proof,
    ) -> TransactionConverterResult<VerificationHandle> {
        let pmc = self.proof_manager_client.clone();
        let task_proof_facts = proof_facts.clone();
        let task_proof = proof.clone();
        let verification_task = tokio::spawn(async move {
            Self::run_proof_verification(task_proof_facts, task_proof, pmc).await?;
            Ok(())
        });
        Ok(VerificationHandle { proof_facts, proof, verification_task })
    }

    fn validate_proof_facts(
        &self,
        block_context: &BlockContext,
        state: &mut dyn State,
    ) -> TransactionPreValidationResult<()> {
        // Only Invoke V3 transactions can carry proof facts.
        let Transaction::Invoke(invoke_tx) = &self.tx else {
            return Ok(());
        };
        if invoke_tx.version() < TransactionVersion::THREE {
            return Ok(());
        }

        // Parse proof facts.
        let proof_facts = invoke_tx.proof_facts();
        let snos_proof_facts = match ProofFactsVariant::try_from(&proof_facts)
            .map_err(|e| TransactionPreValidationError::InvalidProofFacts(e.to_string()))?
        {
            ProofFactsVariant::Empty => return Ok(()),
            ProofFactsVariant::Snos(snos_proof_facts) => snos_proof_facts,
        };
        let os_constants = &block_context.versioned_constants.os_constants;

        if !os_constants.allowed_proof_versions.contains(&snos_proof_facts.proof_version.as_felt())
        {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Proof version {} is not allowed under this protocol version.",
                snos_proof_facts.proof_version
            )));
        }

        // Validate the program hash.
        let allowed = &os_constants.allowed_virtual_os_program_hashes;
        if !allowed.contains(&snos_proof_facts.program_hash) {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Virtual OS program hash {} is not allowed",
                snos_proof_facts.program_hash
            )));
        }

        // Validate the block hash and block number.
        let proof_block_hash = snos_proof_facts.block_hash.0;
        let proof_block_number = snos_proof_facts.block_number.0;
        Self::validate_proof_block_number(
            proof_block_number,
            block_context.block_info.block_number,
        )?;
        Self::validate_proof_block_hash(proof_block_hash, proof_block_number, os_constants, state)?;

        // Validate the config hash.
        let virtual_os_config_hash = block_context.virtual_os_config_hash();
        let proof_config_hash = snos_proof_facts.config_hash;
        if virtual_os_config_hash != proof_config_hash {
            return Err(TransactionPreValidationError::InvalidProofFacts(format!(
                "Virtual OS config hash mismatch. Computed virtual OS config hash: \
                 {virtual_os_config_hash}, expected virtual OS config hash: {proof_config_hash}."
            )));
        }

        Ok(())
