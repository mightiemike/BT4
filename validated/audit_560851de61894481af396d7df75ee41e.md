### Title
Unbounded loop in `DelegatedResourceAccountIndexStore.convert` allows constant-fee DoS during block processing - (`chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`DelegatedResourceAccountIndexStore.convert(address)` iterates over the full legacy `toAccountsList`/`fromAccountsList` of a `DelegatedResourceAccountIndexCapsule` and, for every entry, performs multiple store writes via `delegate()`. This method is invoked synchronously inside `FreezeBalanceActuator.delegateResource` and `UnfreezeBalanceActuator.execute`, both of which are reachable from ordinary broadcast transactions (`FreezeBalanceContract`/`UnfreezeBalanceContract`). Because the legacy index list has no size cap and the actuator's fee is fixed (`calcFee()` returns `0`), an account that accumulated a large number of distinct delegation relationships (which is explicitly supported and tested, e.g. up to 100+ receivers in `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`) can force every full node to perform an unbounded amount of work for a flat fee once `allowDelegateOptimization` is enabled — the same bug class as the "Unbounded Loops in Redeem Function" report.

### Finding Description
`convert()` reads the pre-optimization index and loops over both lists with no size bound: [1](#0-0) 

Prior to the optimization flag being enabled, `FreezeBalanceActuator.delegateResource` grows these lists on every `FreezeBalanceContract` execution with no upper bound on distinct receivers/senders per address: [2](#0-1) 

Once `supportAllowDelegateOptimization()` becomes true, the very next `FreezeBalanceContract`/`UnfreezeBalanceContract` transaction touching that address triggers the conversion path, which loops through the entire accumulated list synchronously as part of actuator execution: [3](#0-2) [4](#0-3) 

The size of this list, and thus the number of loop iterations and store writes performed by every full node during block application, is entirely attacker-controlled and unbounded, while `calcFee()` for both actuators is fixed at `0`: [5](#0-4) 

This mirrors the reported vulnerability class exactly: an unbounded loop over accumulated relationships (delegations/distributors in the Forta report, delegated-resource index entries here), triggered by an ordinary, unprivileged transaction, with no limit on how many entries a single account can accumulate before the loop is executed.

### Impact Explanation
Since `convert()` is executed during transaction execution while a block is being applied, an attacker who has built up a very large `toAccountsList`/`fromAccountsList` (by repeatedly issuing cheap `FreezeBalanceContract` delegate calls to many distinct addresses before the hard fork enabling `allowDelegateOptimization`) can cause a single subsequent transaction to force every node validating that block to execute a large number of loop iterations and key-value store writes. Because this work happens deterministically as part of consensus-critical execution (not metered against TVM energy, since this is a native actuator with `calcFee()==0`), it can slow down block processing across the network, degrading node performance and potentially causing missed block deadlines — a DoS via the protocol implementation, reachable from a broadcast transaction.

### Likelihood Explanation
The precondition (large accumulated legacy index lists) requires the attacker to have issued many cheap delegate-freeze transactions to distinct receiver addresses before `allowDelegateOptimization` was turned on for the network, which is realistic given `FreezeBalanceContract`'s low, non-scaling fee (`calcFee()` returns `0`), as demonstrated by the codebase's own test building 100+ distinct entries. The triggering step (a normal `FreezeBalanceContract`/`UnfreezeBalanceContract` transaction) is a routine, unprivileged, broadcastable transaction, making exploitation straightforward for any account that has (or creates) a large index list.

### Recommendation
Bound the size of `toAccountsList`/`fromAccountsList` that can accumulate for a single address before the optimization migration, or perform the `convert()` migration incrementally/lazily (e.g., in bounded batches across multiple transactions or as an out-of-band chain-wide migration) rather than as a single unbounded loop inside a single transaction's execution. Alternatively, charge fees proportional to the number of entries converted so the cost scales with the work performed.

### Proof of Concept
1. Before `allowDelegateOptimization` is enabled, from a single owner address, repeatedly submit `FreezeBalanceContract` (with `receiverAddress` set) to N distinct freshly generated receiver addresses; each call appends one entry to the owner's `toAccountsList` and to each receiver's `fromAccountsList` with no cap on N (see `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`, which does this for `RECEIVE_COUNT = 100` and can be scaled arbitrarily).
2. Once the network enables `allowDelegateOptimization` (`supportAllowDelegateOptimization()` becomes true), submit any further `FreezeBalanceContract`/`UnfreezeBalanceContract` transaction referencing that owner address.
3. `delegateResource`/`execute` calls `delegatedResourceAccountIndexStore.convert(ownerAddress)`, which loops N times performing `delegate()` (2 store `put`s each) — this work is repeated by every validating node for this one transaction, at a flat, non-scaling fee.

```java
  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
```
