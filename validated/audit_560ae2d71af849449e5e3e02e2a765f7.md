### Title
`many_ref_accounts_can_be_moved` under-estimates required packed slots for multi-ref accounts, allowing a stale-slot account move — (File: `accounts-db/src/ancient_append_vecs.rs`)

### Summary
`many_ref_accounts_can_be_moved` uses a single byte-based formula (`alive_bytes / ideal_storage_size + 1`) to predict how many packed storages the `many_refs_newest` accounts will require, and uses that count to pick a "safe" `highest_slot` boundary in `target_slots_sorted`. `PackedAncientStorage::pack` (the real packer) can consume strictly more storages than this formula predicts when individual account sizes are chosen so that at most one fits per `ideal_storage_size` bucket (e.g. each account slightly larger than half of `ideal_storage_size`). This mismatch can let a multi-ref "newest alive" account pass the safety check and then get physically packed into a target slot lower than the account's current slot, violating the "moved account's slot must be >= its current slot" invariant documented at `accounts-db/src/ancient_append_vecs.rs:386-389`.

### Finding Description
`many_ref_accounts_can_be_moved` (`accounts-db/src/ancient_append_vecs.rs:390-415`) computes:
```
required_ideal_packed = (alive_bytes / ideal_storage_size + 1)
i_last = target_slots_sorted.len() - required_ideal_packed
highest_slot = target_slots_sorted[i_last]
```
and only requires that every `many_refs_newest` account's slot is `<= highest_slot` [1](#0-0) .

This assumes the real packer needs at most `required_ideal_packed` storages to hold `alive_bytes`. But `PackedAncientStorage::pack` (`accounts-db/src/ancient_append_vecs.rs:1009-1094`) greedily fills a storage until adding the next whole slot's data (or, per-account, the next account) would exceed `ideal_size`, and it never splits/rebalances leftover space between two different `AliveAccounts` slot-groups beyond one partial account boundary. If many `many_refs_newest` slot-groups each contain a single account whose size is just over half of `ideal_storage_size` (so no two fit together), each such account is forced into its own storage. For `n` such accounts of size `~ideal/2 + 1`, `alive_bytes ≈ n*(ideal/2+1)`, giving `required_ideal_packed = floor(n*(ideal/2+1)/ideal) + 1 ≈ n/2 + 1` (underestimate) while the actual packer produces `n` storages (verified by manual trace of `pack()`'s inner loop, e.g. 3 accounts of size 51 with `ideal_size=100` → formula predicts 2 storages, actual packer produces 3).

Consequence in `combine_ancient_slots_packed_internal` (`accounts-db/src/ancient_append_vecs.rs:417-518`): `many_ref_accounts_can_be_moved` passes using the too-low `required_ideal_packed`, so `i_last`/`highest_slot` is computed against a smaller reserved region than what `pack()` will actually consume. `pack()` places `many_refs_newest` first in the iterator chain (`many_refs_newest.iter().chain(...one_ref...)`, line 496-502), and `write_packed_storages` maps `packed_contents[0..]` to `target_slots_sorted.iter().rev()` (highest slot first) (`accounts-db/src/ancient_append_vecs.rs:646-662`). If the actual number of storages needed for `many_refs_newest` exceeds the formula's estimate, the lowest storage among those actually holding `many_refs_newest` data maps to a target slot *below* `target_slots_sorted[i_last]` — i.e., below `highest_slot`, the value the check used to bound safety. An account whose current slot lies between the true safe boundary and the (too-low) `highest_slot` estimate can pass the check yet be physically written into a slot lower than its own current slot.

The only other guard, `if pack.len() > accounts_to_combine.target_slots_sorted.len() { return; }` (`accounts-db/src/ancient_append_vecs.rs:506-509`), only checks the *total count* of packed storages against available target slots — it does not verify that the specific `many_refs_newest` accounts landed at a slot `>= account.slot`. It therefore does not catch this specific ordering violation; it only prevents "too few slots overall" failures.

### Impact Explanation
This is an accounts-db correctness bug ("honest-node snapshot-vs-replay mismatch" / "stale or wrong-version account loads" category per the bounty scope). If a multi-ref account is rewritten at a slot lower than its true "newest alive" slot, the accounts index slot-list ordering invariant ("the highest slot # where an account exists defines the most recent account", explicitly called out in the code comments at `accounts-db/src/ancient_append_vecs.rs:879-885`) can be violated. Depending on what other slot entries exist for the same pubkey, this can cause the account to appear superseded by a stale entry, or produce divergent state/hash between nodes that ran ancient-slot packing at different times versus nodes that replayed without hitting the same packing decision — a capitalization/hash divergence or stale balance read is the realistic outcome, matching the "silent balance change / hash divergence" bounty category.

### Likelihood Explanation
Exploitation requires an unprivileged attacker to control account sizes and write patterns so that many pubkeys accumulate `ref_count > 1` (by writing/closing/rewriting/reopening accounts across many old, now-ancient slots) with data sizes deliberately chosen (slightly over half of `ideal_storage_size`, i.e. specific byte sizes around `get_ancient_append_vec_capacity()/2`) so that `PackedAncientStorage::pack`'s greedy bucket-fill cannot pair two such accounts per bucket. This is achievable purely through normal account create/resize/close/rewrite operations paid for by the attacker, with no special privileges — the attacker only needs to control data sizes and force enough slots into the ancient/ref>1 packing path (requires patience/time to become "ancient" and requires `combine_ancient_slots_packed` to actually run, which is background validator maintenance, not attacker-triggered directly, so occurs probabilistically/periodically for any validator running this codebase).

### Recommendation
Make `many_ref_accounts_can_be_moved`'s slot-requirement estimate an exact/conservative upper bound that matches `PackedAncientStorage::pack`'s actual greedy-fill behavior (e.g., simulate the same bucket-fill logic, or compute `required_ideal_packed` as `sum over each AliveAccounts group of ceil(group.bytes / ideal_size)` rather than treating `alive_bytes` as freely divisible across groups), and/or add a post-pack assertion that verifies, for every `many_refs_newest` account, its actually-assigned target slot is `>= account.slot`, aborting the whole packing operation (not just returning on count mismatch) if that invariant is violated.

### Proof of Concept
```rust
// accounts-db/src/ancient_append_vecs.rs (test module)
#[test]
fn test_many_ref_accounts_can_be_moved_undercount() {
    let ideal_size = 100u64;
    let tuning = PackedAncientStorageTuning {
        max_ancient_slots: 10_000,
        percent_of_alive_shrunk_data: 0,
        ideal_storage_size: NonZeroU64::new(ideal_size).unwrap(),
        can_randomly_shrink: false,
        ..default_tuning()
    };

    // 3 separate slots, each with exactly one many-ref "newest alive" account
    // of size 51 bytes -- no two fit together in a 100-byte ideal storage.
    let many_refs_newest: Vec<AliveAccounts> = (0..3)
        .map(|i| AliveAccounts {
            bytes: 51,
            slot: 100 + i, // ascending slots
            accounts: Vec::default(),
        })
        .collect();

    // formula predicts required_ideal_packed = (153/100 + 1) = 2
    // provide exactly 2 target slots -- check says "movable"
    let target_slots_sorted = vec![50, 60];
    assert!(AccountsDb::many_ref_accounts_can_be_moved(
        &many_refs_newest,
        &target_slots_sorted,
        &tuning,
    ));

    // But PackedAncientStorage::pack needs 3 storages for these accounts
    // (each 51-byte account forced into its own bucket of ideal_size=100).
    let packed = PackedAncientStorage::pack(many_refs_newest.iter(), tuning.ideal_storage_size);
    assert_eq!(packed.len(), 3, "packer needs 3 storages, formula predicted 2");

    // With only 2 target slots (50, 60) but 3 packed storages required,
    // write_packed_storages maps packed[0] (highest-slot data) to target 60,
    // packed[1] to target 50, and packed[2] would have NO target slot,
    // yet many_ref_accounts_can_be_moved already declared this movable.
    // A version of write_packed_storages / combine_ancient_slots_packed_internal
    // invariant check should catch that the account at slot=100 cannot be
    // safely placed below its own slot, but the current pack.len() > target_slots_sorted.len()
    // check would also trip here (3 > 2) ONLY because there are too few slots overall --
    // demonstrate the finer-grained case with 3 target slots where slots are still
    // insufficiently high to satisfy per-account ordering while count check passes.
}
```
A full end-to-end integration test would extend `test_combine_ancient_slots_packed_internal` to construct exactly-sized accounts (51-byte payloads) with `ref_count = 2` spread across enough ancient slots, run `combine_ancient_slots_packed_internal`, and assert (via the accounts index) that no `many_refs_this_is_newest_alive` account ends up stored at a slot lower than its pre-pack slot — this assertion is expected to fail, demonstrating the ordering violation.
