### Title
Replay-verify integrity check silently ignores state-checkpoint hash mismatches - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` — the function used by replay/debug tooling to authenticate a locally re-executed `TransactionOutput` against the on-chain, ledger-info-signed `TransactionInfo` — checks status, gas, write-set hash, and event-root hash, but explicitly and admittedly skips the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields. This means a state root divergence between the locally recomputed state and the authenticated, committed state root is not detected by this verification path.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  compares only `status`, `gas_used`, `write_set` hash, and `event_root_hash` against the trusted `TransactionInfo`. The function contains its own acknowledgment of the gap: [2](#0-1) 

This comment states the comparator ignores the checkpoint hashes (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`), and that replay-verify tooling (e.g., `db-tool`'s `replay_on_archive`) can therefore report a successful replay even when the authenticated position/state root diverges from local execution.

This function is the sole per-transaction integrity check used by `storage/db-tool/src/replay_on_archive.rs`, which re-executes historical transactions via `AptosVMBlockExecutor` and calls `executed_outputs[idx].ensure_match_transaction_info(...)` to decide pass/fail: [3](#0-2) . It is also invoked from `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`, i.e., it is the general-purpose replay/verification primitive used across the debugging and replay-verify tooling, not just an isolated test helper.

Because the `state_checkpoint_hash` (root of the Sparse Merkle Tree describing world state, which the `TransactionInfo` carries and which is bound into the transaction accumulator that validators sign in the `LedgerInfo`) is never compared, a scenario where the VM's write set is unchanged/matches but the *derived state root* (state checkpoint hash) is wrong — e.g., due to a state-tree construction bug, an incorrect JMH/position-state layering, or an execution divergence that manifests only in the checkpoint hash and not in the per-transaction write set — will not be flagged by replay-verify. The write-set hash equality check does not imply state-checkpoint-hash equality, since the checkpoint hash is a periodic (per-block, not necessarily per-transaction) SMT root computed by accumulating write sets over potentially many transactions via `update_in_memory_state`, and is not derivable purely from an individual transaction's write set.

### Impact Explanation
`replay_on_archive` and the debugger's replay verification exist specifically to catch state-commitment divergences: places where local re-execution against archived transactions produces committed ledger data (state/hot-state/position-state checkpoint roots) different from what the authenticated chain history recorded. This is exactly the class of hard-fork/divergence detection tooling relied upon during audits, incident response, and node-consistency validation. With this gap, a real divergence in the state checkpoint root (which is bound into the signed `TransactionInfo`/accumulator and thus is part of the authenticated ledger state) would pass replay-verify undetected, giving false assurance that execution/storage integrity holds when it does not. This directly undermines the proof/commit-integrity guarantee the tool is meant to provide.

### Likelihood Explanation
The gap is not a rare edge case — it is a permanent, always-present blind spot in every invocation of `ensure_match_transaction_info`, since the checkpoint-hash fields are unconditionally excluded from comparison (there is no feature flag gating this — the TODO says to "Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying the check is deferred pending unrelated future work). Any bug that corrupts state-checkpoint/state-root construction (in the executor, JMH restore path, or hot-state/position-state layering) while leaving individual write-sets/events unaffected would systematically evade detection by this tool today.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`-derived (or externally supplied) state checkpoint hash, hot-state checkpoint hash, and position-state checkpoint hash against `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, and `txn_info.position_state_checkpoint_hash()` whenever these are present in the `TransactionInfo`/available from the replay context (this requires passing in the SMT root computed after each checkpoint boundary, analogous to how `state_checkpoint_hashes` are assembled in `execution/executor/src/workflow/do_ledger_update.rs`). Until that validation is added, `replay_on_archive` and related tooling should not be treated as verifying state-root/proof integrity, only write-set/event/status integrity.

### Proof of Concept
Conceptual trace (no exploit against consensus itself, but a verification-tooling gap):
1. A block is executed locally by `replay_on_archive`'s `execute_and_verify` via `AptosVMBlockExecutor::execute_block`, producing `executed_outputs` [4](#0-3) .
2. Assume a bug (in the SMT/hot-state/position-state construction logic, independent of write-set correctness) causes the locally recomputed state checkpoint root to differ from the archived, ledger-info-authenticated `TransactionInfo.state_checkpoint_hash`.
3. `ensure_match_transaction_info` is called per transaction [5](#0-4)  and only checks status/gas/write-set-hash/event-root-hash, all of which still match.
4. The function returns `Ok(())` despite the state-checkpoint hash mismatch [6](#0-5) , so `replay_on_archive` reports the transaction as verified/passing when in fact the recomputed ledger state diverges from the authenticated chain state.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
