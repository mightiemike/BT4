### Title
Unpriced blocking wait in `GlobalRateLimiter.acquire()` allows gRPC executor-thread exhaustion under blocking mode - ([File: RateLimiterInterceptor.java])

### Finding Description
`RateLimiterInterceptor.interceptCall` calls `rateLimiter.acquirePermit(runtimeData)` for the per-endpoint limiter, and when `rateLimiter == null` (an unmapped method, or any method that only has the auto-added `DefaultBaseQqsAdapter` but whose adapter's `acquirePermit` returns quickly) it defaults `perEndpointAcquired = true` unconditionally [1](#0-0) . It then calls `GlobalRateLimiter.acquirePermit(runtimeData)`, which — when `rate.limiter.apiNonBlocking=false` — dispatches to `GlobalRateLimiter.acquire()` [2](#0-1) . That method calls `RateLimiter.acquire()` (Guava's blocking variant) on both the per-IP limiter and the global limiter [3](#0-2) . Guava's `RateLimiter.acquire()` blocks the calling thread until a permit becomes available, with no timeout and no bound on how long or how many callers can be queued simultaneously.

Since `interceptCall` runs synchronously on the gRPC server's call-handling thread (before `next.startCall` is even invoked), every concurrent call that arrives faster than the global/IP QPS replenishment rate pins one server thread in `RateLimiter.acquire()` for as long as it takes tokens to become available. An attacker who opens many concurrent connections/calls (even to a completely unmapped method, which trivially satisfies `perEndpointAcquired`) can force enough threads into this blocking wait to exhaust the server's thread pool, starving unrelated RPCs (including internally-used ones) that share the same executor.

This is a real, reachable path for any unauthenticated caller who can open gRPC connections — no privileged path, key, or governance mechanism is required to trigger it; the only precondition is the operator's own choice to run with `apiNonBlocking=false`.

### Impact Explanation
If the gRPC server thread/executor pool is exhausted by attacker-driven blocking waits, all RPC handling — including calls used internally by other node subsystems that share the same gRPC server/executor — is starved, producing a denial-of-service against the node's public API surface and any co-located functionality that depends on the same thread pool.

### Likelihood Explanation
This requires `rate.limiter.apiNonBlocking=false`, which is a valid, non-default-forced configuration exposed in `common/src/main/resources/reference.conf` / `framework/src/main/resources/config.conf` (present as a configurable, documented option). Given that setting, the attack is trivial and repeatable: open N concurrent gRPC connections at a rate exceeding the configured global/IP QPS; no authentication, fees, or special privileges are needed, and it can be sustained indefinitely by any unprivileged network client.

### Recommendation
Avoid unconditional blocking `RateLimiter.acquire()` calls on the request-handling thread. Use `tryAcquire(timeout)` with a bounded wait (and reject with `RESOURCE_EXHAUSTED` on timeout) instead of unbounded `acquire()`, or move the blocking wait off the gRPC handler thread onto a dedicated bounded executor/queue so exhaustion cannot propagate to the shared server thread pool. Additionally, bound the number of concurrently pending "blocking-mode" acquires (e.g., via a semaphore) so a burst of connections cannot pin more than a safe fraction of server threads.
