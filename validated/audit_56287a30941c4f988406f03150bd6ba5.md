Based on my research, I found a legitimate structural analog to the `MAX_DELEGATES` unbounded-list DoS class: an unbounded, never-pruned list of session IDs tracked per shop in several `SessionStorage` adapters, combined with an auth-path handler that must fully load/iterate that list on every request.

### Title
Unbounded per-shop session-ID list growth causes DoS of the `ensureInstalledOnShop` auth handler - (File: `packages/apps/session-storage/shopify-app-session-storage-redis/src/redis.ts`)

### Summary
For non-embedded apps using online access tokens, `createSession` assigns a brand-new `crypto.randomUUID()` as the session ID on every OAuth completion instead of a deterministic ID. [1](#0-0) 
Several session storage adapters (Redis, Cloudflare KV) maintain a *single unbounded list* of these session IDs per shop, appended to indefinitely with no size cap and no automatic pruning of expired/duplicate entries. [2](#0-1) [3](#0-2) 
This list is fully read back and iterated by `findSessionsByShop`, which does one network round-trip per stored ID. [4](#0-3) 
`findSessionsByShop` is invoked by `AppInstallations.includes`/`.delete`, which are called from the `ensureInstalledOnShop` request-handling path (an auth handler reachable on ordinary shop-scoped HTTP requests). [5](#0-4) 

### Finding Description
This is architecturally the same bug class as the `MAX_DELEGATES` report: an attacker-influenceable list keyed by a single entity (there: an NFT owner address; here: a shop domain) grows without bound because entries are never deduplicated or capped, and a core request-path operation (there: token transfer/burn/mint; here: session lookup for install-check) must fully process the entire list every time it runs.

Root cause chain:
1. `createSession` uses `crypto.randomUUID()` for online-session IDs whenever the app is not embedded, so every OAuth completion (e.g., every time a staff member's online access token flow runs) produces a *new, unique* session ID rather than overwriting a session keyed by user. [6](#0-5) 
2. `RedisSessionStorage.addKeyToShopList` (and the analogous KV `addShopIds`) reads the shop's ID list, appends the new ID, and re-serializes the whole thing back into a single string value with no maximum size or eviction policy. [2](#0-1) 
3. `findSessionsByShop` deserializes that entire list and performs a `GET` for every ID sequentially, so cost is linear (and, because each is a separate network round trip, effectively unbounded latency) in the number of historical session IDs ever created for that shop. [4](#0-3) 
4. `AppInstallations.includes`/`.delete`, which are exercised from the app's install-check middleware, call `findSessionsByShop` directly, meaning this cost is paid on the request path used to gate access to the app. [5](#0-4) 

Unlike the offline session (`offline_${shop}`, a single deterministic key that gets overwritten every OAuth run) and JWT-based embedded online sessions (`${shop}_${userId}`, bounded by staff count), the non-embedded online-session path has no natural bound: any actor who can repeatedly complete the OAuth online-token flow for a shop (a legitimate single merchant/staff account is sufficient — no privilege escalation required) causes the per-shop list to grow forever, since old IDs are never expired or removed automatically.

### Impact Explanation
As the per-shop session ID list grows, every subsequent `findSessionsByShop` call for that shop becomes slower (linear round-trips) and the underlying stored JSON blob grows in size. Because this function is invoked from the `ensureInstalledOnShop`/`AppInstallations` code path — logic that guards ordinary requests to determine whether a shop needs to (re)install — a shop that has accumulated a large number of stale online-session entries will degrade or effectively deny service to itself (and to any code path relying on `findSessionsByShop`, including cleanup/uninstall logic in `AppInstallations.delete`). This mirrors the "increased gas/resource costs during a core operation" and "DoS of the affected entity" impact described in the source report, except here the affected resource is CPU/network time and storage size rather than EVM gas.

### Likelihood Explanation
No exploit primitives (forged tokens, secrets, or cross-tenant access) are required — this occurs purely through ordinary, repeated legitimate use of the non-embedded OAuth online-token flow, which is why it is comparable to the original report's "no profit motive, but damage to protocol/user" griefing classification. The main precondition is that the app is configured as non-embedded with online tokens and uses one of the affected storage adapters (Redis or Cloudflare KV); I was not able to verify from the index whether this is a common production configuration, so likelihood in practice depends on deployment choices I could not fully confirm.

### Recommendation
- Avoid generating a fresh random UUID per OAuth completion for non-embedded online sessions; derive a deterministic ID (e.g., keyed by shop + user, as is already done for embedded apps) so repeated logins overwrite the same entry instead of appending a new one.
- Cap and/or prune the per-shop session ID list in `RedisSessionStorage`/`KVSessionStorage` (e.g., remove expired sessions on write, or store sessions with an index structure that doesn't require reading/rewriting one growing blob).
- Consider paginating or bounding `findSessionsByShop`'s iteration to avoid unbounded work per call.

  public async findSessionsByShop(shop: string): Promise<Session[]> {
    await this.ready;

    const idKeysArrayString = await this.client.get(shop);
    if (!idKeysArrayString) return [];

    const idKeysArray = JSON.parse(idKeysArrayString);
    const results: Session[] = [];
    for (const idKey of idKeysArray) {
      const rawResult = await this.client.get(idKey, false);
      if (!rawResult) continue;

      const session = Session.fromPropertyArray(JSON.parse(rawResult), true);
      results.push(session);
    }

    return results;
  }

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }

  async includes(shopDomain: string): Promise<boolean> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      for (const session of shopSessions) {
        if (session.accessToken) return true;
      }
    }
    return false;
  }

  async delete(shopDomain: string): Promise<void> {
    const shopSessions =
      await this.sessionStorage.findSessionsByShop!(shopDomain);
    if (shopSessions.length > 0) {
      await this.sessionStorage.deleteSessions!(
        shopSessions.map((session: Session) => session.id),
      );
    }
  }
