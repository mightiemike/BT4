## Analysis

The reported bug class — a bookkeeping "ledger" value (the whitelist table's total) becoming decoupled from the actual funds it is supposed to represent, with no atomic check tying the two together — has a direct analog in Agave's accounting of `Bank::capitalization`, the in-memory counter that is supposed to always equal the sum of all lamports across every account in `AccountsDb`.

### Title
Non-atomic check-then-act capitalization update in `store_account_and_update_capitalization` can permanently desynchronize `Bank::capitalization` from actual account balances - (File: `runtime/src/bank.rs`)

### Summary
`Bank::store_account_and_update_capitalization` computes a capitalization delta by reading the *old* account balance, then separately storing the *new* account, updating the atomic `capitalization` counter based on the diff between those two reads. This is a classic two-step "read old value, then write new value and adjust an external total" pattern — the same architectural flaw described in the external report (whitelist-table total vs. contract-balance getting out of sync because they're two separate mutations, not one atomic operation).

### Finding Description [1](#0-0) 

The function reads the old account with `get_account_with_fixed_root_no_cache`, computes `diff`, adjusts `self.capitalization` via `fetch_add`/`fetch_sub`, and only afterward calls `self.store_account(pubkey, new_account)`. The comment on the function itself acknowledges the danger: "Technically this issues (or even burns!) new lamports, so be extra careful for its usage." [2](#0-1) 

This helper is called from several bank-mutation paths outside of the normal, single-threaded, per-message transaction-processing pipeline, e.g. `add_precompiled_account_with_owner` and `add_builtin_account`, both of which read the "old" state, then mutate `capitalization`, then store — with no lock held across the whole read-modify-write sequence relative to concurrent stores of the same pubkey. [3](#0-2) [4](#0-3) 

Just like the reported whitelist-table bug — where the "ledger" (whitelist balances) and the actual contract token balance are updated in two disconnected steps — `capitalization` (the ledger of total lamports) and the actual account storage are updated in two disconnected steps here. If any intervening event changes the account's balance between the "read old" and "store new" steps (e.g., another writer path, or a concurrent core-BPF migration path that also calls this same helper on the same pubkey), the capitalization delta computed will be stale, and `Bank::capitalization` will silently diverge from the true sum of lamports in `AccountsDb`.

### Impact Explanation
`Bank::capitalization` is a consensus-relevant value: it's checked against the value calculated from `AccountsDb` at snapshot load time, and mismatches are treated as fatal snapshot-integrity failures rather than being silently tolerated at runtime. [5](#0-4) [6](#0-5)  If `capitalization` silently diverges from the true account-balance total during live bank operation (rather than being caught immediately), this divergence is carried forward through every subsequent bank until a full-index capitalization recalculation is performed — normally only done at startup via ledger-tool, not during normal validator operation. This is a silent-balance-tracking / capitalization-divergence class issue, and depending on where the divergence surfaces (snapshot restore, ledger-tool verify), it results in a hard node panic/startup failure (`MismatchedCapitalization`) rather than a graceful, immediately-detected error.

### Likelihood Explanation
The vulnerable helper is exercised on normal validator code paths (adding builtin/precompiled program accounts, core-BPF migrations), not just test code — every one of those call sites performs the same read-then-write-then-mutate-counter pattern without an atomic guard tying the read and the counter update together. The window is narrow and requires a specific interleaving (e.g., a concurrent account mutation on the exact same pubkey between the "read old balance" and "store new account" steps), so this is a race-timing dependent issue rather than a trivially reproducible one, similar in nature to the original report's admin-error-dependent scenario.

### Recommendation
Make the balance read, capitalization adjustment, and account store atomic with respect to the same pubkey — e.g. compute the diff and store the account while holding whatever lock/guard the accounts-index maintains for the pubkey/slot in question, or better, have `AccountsDb`/`store_account` return the actual previous stored lamports as part of the same write operation (rather than a separate, unlocked prior read), so the capitalization delta is guaranteed to be computed against the value being replaced, not a possibly-stale snapshot of it. This mirrors the original report's recommendation of adding a check that ties the two decoupled bookkeeping mutations into a single atomic operation.

### Proof of Concept
Not applicable in this analysis context (this is a design/race-timing issue rather than a single-transaction reproducible input); a concrete PoC would require constructing a timing-dependent interleaving between `store_account_and_update_capitalization` (e.g. via `add_builtin_account`/`add_precompiled_account`/core-BPF migration paths) and a concurrent write to the same pubkey's account, which the existing capitalization-diff test helpers (`assert_capitalization_diff`, `test_add_builtin_account_squatted_while_not_replacing`) already demonstrate are sensitive to ordering of reads vs. writes. [7](#0-6)

    /// Technically this issues (or even burns!) new lamports,
    /// so be extra careful for its usage
    pub(crate) fn store_account_and_update_capitalization(
        &self,
        pubkey: &Pubkey,
        new_account: &AccountSharedData,
    ) {
        let old_account_data_size = if let Some(old_account) =
            self.get_account_with_fixed_root_no_cache(pubkey)
        {
            match new_account.lamports().cmp(&old_account.lamports()) {
                std::cmp::Ordering::Greater => {
                    let diff = new_account.lamports() - old_account.lamports();
                    trace!("store_account_and_update_capitalization: increased: {pubkey} {diff}");
                    self.capitalization.fetch_add(diff, Relaxed);
                }
                std::cmp::Ordering::Less => {
                    let diff = old_account.lamports() - new_account.lamports();
                    trace!("store_account_and_update_capitalization: decreased: {pubkey} {diff}");
                    self.capitalization.fetch_sub(diff, Relaxed);
                }
                std::cmp::Ordering::Equal => {}
            }
            old_account.data().len()
        } else {
            trace!(
                "store_account_and_update_capitalization: created: {pubkey} {}",
                new_account.lamports()
            );
            self.capitalization
                .fetch_add(new_account.lamports(), Relaxed);
            0
        };

        self.store_account(pubkey, new_account);

        let existing_genuine_program =

                    if native_loader::check_id(account.owner()) {
                        Some(account)

                        // malicious account is pre-occupying at program_id
                        self.burn_and_purge_account(program_id, account);
                        None
                    }
                });

        // introducing builtin program
        if existing_genuine_program.is_some() {
            // The existing account is sufficient
            return;

#[test]
fn test_add_builtin_account_squatted_while_not_replacing() {
    for pass in 0..3 {
        let (genesis_config, mint_keypair) = create_genesis_config(100_000);
        let bank = Bank::new_for_tests(&genesis_config);
        let program_id = solana_pubkey::new_rand();

        // someone managed to squat at program_id!
        bank.withdraw(&mint_keypair.pubkey(), 10).unwrap();
        if pass == 0 {
            add_root_and_flush_write_cache(&bank);
            assert_ne!(
                bank.capitalization(),
                bank.calculate_capitalization_for_tests()
            );
            continue;
        }
        test_utils::deposit(&bank, &program_id, 10).unwrap();
        if pass == 1 {
            add_root_and_flush_write_cache(&bank);
            assert_eq!(
                bank.capitalization(),
                bank.calculate_capitalization_for_tests()
            );
            continue;
        }

        bank.add_builtin_account("mock_program", &program_id);
        add_root_and_flush_write_cache(&bank);
        assert_eq!(
            bank.capitalization(),
            bank.calculate_capitalization_for_tests()
        );
    }
}
