### Title
Single Disk I/O Failure During Bucket-Map Growth Panics the Entire Validator - ([File: bucket_map/src/bucket_storage.rs])

### Summary
The disk-backed `BucketMap` (used as the on-disk backing store for `AccountsIndex` entries) grows its index/data buckets by creating a new memory-mapped file via `BucketStorage::map_open_file`/`new_map`. Any transient failure of the underlying filesystem (disk full, out of inodes, permission/IO error) while creating or resizing this file causes an unconditional `panic!`/`.unwrap()`, aborting the whole validator process. Because every account read/write depends on the same shared bucket map, one failed I/O operation on a single bucket brings down the entire node — the same "single external dependency failure cascades into total service failure" pattern flagged in the SponsorVault report, where one third-party contract's revert broke all cross-chain `execute()` calls.

### Finding Description
`BucketStorage::map_open_file` (`bucket_map/src/bucket_storage.rs:392-444`) opens (and optionally creates) the mmap-backed bucket file: [1](#0-0) 
If `OpenOptions::open` fails while `create=true`, or if `data.set_len(create_bytes)` fails (e.g., `ENOSPC`), the function unconditionally `panic!`s. The subsequent `MmapMut::map_mut(&data)` call also panics via `.unwrap_or_else` on any mmap failure.

`new_map` (`bucket_map/src/bucket_storage.rs:447-456`) unwraps the `Option` returned by `map_open_file`: [2](#0-1) 

This code path is exercised on the hot path of ordinary validator operation whenever a bucket needs to grow — `Bucket::grow_index`/`grow_data` (`bucket_map/src/bucket.rs:685-747`, `802-820`) call `BucketStorage::new_with_capacity`/`new_resized`, which ultimately calls `new_map`. Growth is triggered from `Bucket::insert`/`try_write`/`batch_insert_non_duplicates` any time `BucketMapError::IndexNoSpace`/`DataNoSpace` is returned, i.e. any time the on-disk index needs more room for accounts: [3](#0-2) [4](#0-3) 

This is also invoked from the accounts index disk flush path (`in_mem_accounts_index.rs`), which retries `try_write` and calls `disk.grow(err)` in a loop whenever the disk index needs to grow to accommodate new writes: [5](#0-4) 

There is no fallback, retry-with-backoff, or graceful degradation (e.g., temporarily refusing new inserts, or falling back to in-memory-only operation) — a single transient filesystem condition (which is external to the validator's own logic, analogous to the third-party `SponsorVault` contract) results in an immediate process-wide panic.

### Impact Explanation
Because `BucketMap` backs the disk-based `AccountsIndex`, which is a shared, singleton structure used by every account read/write/scan/clean/shrink operation on the validator, a single I/O failure on one bucket's growth (disk full, quota exceeded, permission change, or any other transient environment condition) is sufficient to crash the entire validator process. This is a "node panic" caused by an external, non-Byzantine-fault-related dependency failure, matching the accepted-impact category. It is not a targeted or maliciously-crafted-input attack; it can occur simply from normal disk usage growth over time (accounts index disk usage naturally grows with the ledger) or any transient storage hiccup, disrupting validator availability and consensus participation.

### Likelihood Explanation
The accounts index disk backing store (`--accounts-index-path` configurations that use disk buckets) continuously grows as more accounts are added; disk space exhaustion or storage I/O errors are realistic operational conditions, not adversary-controlled exploits. Every `grow_index`/`grow_data` call goes through this exact panic-prone code path with no retry or containment, so the likelihood of hitting this under sustained disk pressure is non-trivial for long-running validators with disk-backed indexes.

### Recommendation
Propagate I/O errors from `map_open_file`/`new_map` as `Result` instead of panicking, and handle bucket-growth failures gracefully in `Bucket::grow`/`grow_index`/`grow_data` and their callers (`insert`, `try_write`, `update`, `batch_insert_non_duplicates`, and the accounts-index disk flush path). On failure, the operation should back off/retry, surface a recoverable error to the caller (so a single write can fail without crashing the whole process), and emit metrics/alerts, rather than immediately terminating the validator.

### Proof of Concept
1. Configure a validator to use a disk-backed accounts index (`--accounts-index-path` pointing at a small/constrained filesystem or a filesystem where the quota can be hit).
2. Let ledger replay/account writes continue until the accounts index bucket map needs to grow (`Bucket::grow_index`/`grow_data`), while the target drive is at or near capacity (or made read-only/quota-limited to simulate a transient I/O failure).
3. Observe that `BucketStorage::map_open_file` hits the `data.set_len(create_bytes).unwrap()` or `panic!` branch inside `map_open_file` (`bucket_map/src/bucket_storage.rs:404-431`), aborting the entire validator process rather than failing just the single insert/grow operation.

    pub(crate) fn grow(&self, err: BucketMapError) {
        match err {
            BucketMapError::DataNoSpace((data_index, current_capacity_pow2)) => {
                //debug!("GROWING SPACE {:?}", (data_index, current_capacity_pow2));
                self.grow_data(data_index, current_capacity_pow2);
            }
            BucketMapError::IndexNoSpace(current_capacity) => {
                //debug!("GROWING INDEX {}", sz);
                self.grow_index(current_capacity);
            }
        }
    }
