### Title
Unguarded `long` overflow in bandwidth/energy resource-usage accounting when `ALLOW_HARDEN_RESOURCE_CALCULATION` is not enacted - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
The external report flags yield-source contracts that skip `SafeMath` on a subset of arithmetic operations, allowing silent overflow/underflow. The same bug class exists in java-tron's on-chain resource accounting: `ResourceProcessor.increase()`/`increaseV2()` (and the mirrored logic in `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`) perform raw `long` multiplications such as `lastUsage * precision` and `usage * precision` instead of overflow-checked arithmetic, unless the `ALLOW_HARDEN_RESOURCE_CALCULATION` chain parameter has been activated by a super-representative proposal. That parameter defaults to `0` (unhardened) as defined in `DynamicPropertiesStore.getAllowHardenResourceCalculation()` and gated in `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`.

### Finding Description
`ResourceProcessor.increase()` computes: [1](#0-0) 
When `hardenCalculation()` is false (the default, since `ALLOW_HARDEN_RESOURCE_CALCULATION` starts at `0`), the code falls back to plain `long` multiplication `lastUsage * precision` and `usage * precision` with no overflow check, unlike the `BigInteger`-based path used when hardening is enabled.

This method is invoked on every bandwidth/energy consumption update for accounts, reachable from ordinary broadcast transactions via `BandwidthProcessor`/`EnergyProcessor` (subclasses of `ResourceProcessor`), and from the TVM native-contract path in `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`'s equivalent `increase()`/`getUsage()`/`calculateGlobalEnergyLimit()` methods, which contain identical unguarded raw-`long` fallbacks: [2](#0-1) [3](#0-2) 

The repository's own test suite explicitly documents that overflow is silent when hardening is disabled: [4](#0-3) 
and that the hardened path throws `ArithmeticException` for the same inputs that silently wrap in the default path: [5](#0-4) 

Because `precision` (`ChainConstant.PRECISION`, 1_000_000) is multiplied against user/account-influenced `usage`/`lastUsage` values that accumulate over the life of an account (via freeze/unfreeze/delegate/undelegate resource actuators, and per-transaction bandwidth/energy consumption), an account whose accumulated usage approaches `Long.MAX_VALUE / precision` (~9.2×10^12) causes the multiplication to wrap around into a negative or otherwise incorrect value. This corrupts the account's tracked resource usage/remaining window, directly affecting resource-limit enforcement (a core piece of the anti-spam/fee model) and can also propagate into global limit computations (`calculateGlobalEnergyLimit`) that scale network-wide energy allocation.

### Impact Explanation
This is a resource/reward accounting corruption bug reachable purely through normal, permissionless transaction broadcast (freeze/unfreeze/delegate resource actuators and everyday bandwidth/energy consumption during transaction execution). A corrupted (e.g., wrapped-negative) usage value could let an account bypass its bandwidth/energy consumption limits (free extra throughput/computation) or could distort the network-wide adaptive energy limit calculation, degrading fairness/availability of the resource model network-wide. This matches the medium-risk classification the original report received (confirmed and escalated by the sponsor and judge), since exploiting it requires driving accumulated counters to an extreme but bounded (long-lived, high-value account) magnitude rather than being trivially triggerable in one transaction.

### Likelihood Explanation
Exploitability requires an account/global counter to reach values on the order of 9.2×10^12 in `lastUsage`/`usage` (window-scaled bandwidth/energy points) before the multiplication by `precision` overflows a signed 64-bit long. This is a large but not impossible magnitude for long-lived, heavily used or intentionally manipulated accounts (e.g., via extreme freeze/delegate amounts, given `calculateGlobalEnergyLimit`'s frozen-balance-based weight computation also lacks overflow protection on the unhardened path). The fact that the codebase already ships a fully-tested hardened alternative behind a not-yet-activated proposal (`ALLOW_HARDEN_RESOURCE_CALCULATION` defaults to `0`) confirms the maintainers recognize this as a real overflow risk that is currently unmitigated on any network that hasn't passed the corresponding proposal.

### Recommendation
Activate (or default-enable) the `ALLOW_HARDEN_RESOURCE_CALCULATION` hardening path network-wide, or unconditionally replace the raw `long` arithmetic fallbacks in `ResourceProcessor.increase()`/`increaseV2()`/`getUsage()` and the parallel methods in `RepositoryImpl` (`calculateGlobalEnergyLimit`, `increase`, `getUsage`) with overflow-checked arithmetic (e.g., `Math.multiplyExact`/`LongMath.checkedMultiply`, or the existing `BigInteger` path unconditionally) rather than gating correctness behind an opt-in governance proposal.

### Proof of Concept [4](#0-3) 
This existing unit test demonstrates that calling `processor.increase(lastUsage, usage, lastTime, now, windowSize)` with `lastUsage = Long.MAX_VALUE / 10` and `ALLOW_HARDEN_RESOURCE_CALCULATION` disabled (the default) completes without any exception—i.e., the `lastUsage * precision` multiplication silently overflows instead of failing, corrupting the resulting usage value that is subsequently stored on the account and used to gate future resource consumption.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
