### Title
Integer-division truncation in `ExchangeWithdrawActuator.validate()` can permanently revert legitimate token withdrawals - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawActuator.validate()` computes the counter-token amount (`anotherTokenQuant`) for an AMM-style TRC10 exchange withdraw using integer division (`divideToIntegralValue`), and then rejects the transaction with `ContractValidateException` if that computed amount is `<= 0`. When the exchange's token balance ratio (analogous to token decimals) is skewed or the withdrawn quantity is small relative to the pool ratio, the division truncates to zero and the withdraw is unconditionally reverted — mirroring the `streamAmt == 0` revert pattern in the reported Locke.sol bug.

### Finding Description
The exchange creator withdraws liquidity from a TRC10 exchange pool via `ExchangeWithdrawContract`. In `validate()`, the counter-token amount is derived by integer division of the pool ratio: [1](#0-0) 

If `bigSecondTokenBalance.multiply(bigTokenQuant)` is smaller than `bigFirstTokenBalance`, `anotherTokenQuant` truncates to `0`, and the actuator throws: [2](#0-1) 

The symmetric branch has the same issue: [3](#0-2) 

This is directly analogous to the Locke.sol issue: `streamAmt = acctTimeDelta * ts.tokens / (endStream - ts.lastUpdate)` truncating to `0` and reverting via `if (streamAmt == 0) revert ZeroAmount();`. In both cases, an integer-division result that legitimately rounds to zero (because of a disproportionate ratio between two quantities — token decimals/stream duration in Locke.sol, pool token balances/quant in java-tron) causes the contract/actuator to unconditionally reject the operation rather than handling the zero case gracefully (e.g., returning zero counter-token, or scaling with higher internal precision before truncating).

### Impact Explanation
A pool creator holding an exchange with a heavily skewed balance ratio (e.g., `firstTokenBalance` much larger than `secondTokenBalance`, which is a state reachable via normal `ExchangeInjectContract`/`ExchangeTransactionContract` usage) can become unable to withdraw any amount of the larger-balance token below a certain threshold quant, because every attempt computes `anotherTokenQuant == 0` and reverts with "withdraw another token quant must greater than zero." This blocks the creator from managing/withdrawing their own liquidity through this actuator until the pool ratio changes (e.g., via further trades) — a temporary denial-of-service on a legitimate state transition, matching the "Medium" severity fund-lock class described in the report. It does not cause direct fund theft, consensus divergence, or key disclosure.

### Likelihood Explanation
Reachable by any account that created an exchange and calls `ExchangeWithdrawContract` (broadcast transaction from an unprivileged actor) — no special privilege is required. It requires the exchange's balance ratio to be skewed enough (analogous to the "low token decimal or long stream duration" precondition in the original report) relative to the requested `tokenQuant`, which is a plausible, externally-triggerable pool state, not solely creator-controlled (the ratio drifts due to other users' trades via `ExchangeTransactionContract`).

### Recommendation
Avoid unconditionally reverting when the computed counter-token quantity truncates to zero due to integer-division precision loss. Options include: performing the ratio calculation with higher internal precision (e.g., scale numerators before dividing, similar to the report's "scale to 18 decimals" suggestion) so genuine non-zero withdrawals aren't blocked, or explicitly documenting/handling the zero case (e.g., requiring a minimum `tokenQuant` proportional to the pool ratio) rather than failing the whole transaction with no recovery path other than waiting for pool ratio changes.

### Proof of Concept
1. Create an exchange with `firstTokenBalance = 10_000_000_000` (first token) and `secondTokenBalance = 1` (second token), e.g., via `ExchangeCreateContract` then large `ExchangeTransactionContract` trades skewing the ratio.
2. Call `ExchangeWithdrawContract` withdrawing `tokenQuant = 1` of the first token.
3. In `validate()`, `anotherTokenQuant = bigSecondTokenBalance(1) * bigTokenQuant(1) / bigFirstTokenBalance(10_000_000_000)` truncates to `0`.
4. The check at [2](#0-1)  throws `ContractValidateException("withdraw another token quant must greater than zero")`, reverting the withdrawal even though the creator legitimately owns liquidity in the pool.
