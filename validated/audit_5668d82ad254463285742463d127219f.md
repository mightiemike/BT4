Based on the analysis, this is the key finding: the `beneficiary_id` in `DeleteAccountAction` is only validated for syntactic correctness (`validate_action_account_id`, which calls `AccountId::validate`) at `runtime/runtime/src/action_validation.rs:447-451`. This is precisely analogous to the Gearbox report, since `AccountId::validate` accepts `"system"` as a syntactically valid account id (2-64 chars, lowercase alphanumeric) even though the docs explicitly state `system` "cannot be used" and "does not exist as part of the state" [1](#0-0) . Critically, `Receipt::new_balance_refund` hardcodes `predecessor_id: "system"` for the beneficiary payout receipt [2](#0-1) , and `action_delete_account` never checks whether `beneficiary_id` itself is `"system"` before emitting that payout receipt [3](#0-2) .

However, tracing this further: `implicit_creation_allowed` explicitly returns `false` when `is_refund` is `true`, regardless of account type [4](#0-3) , and `check_account_existence` for a `Transfer` action targeting a non-existent account returns `ActionErrorKind::AccountDoesNotExist` [5](#0-4) . Since the "system" account is never present in state, a refund receipt to `beneficiary_id = "system"` would hit this exact path, fail with `AccountDoesNotExist`, and per `test_refund_on_send_money_to_non_existent_account` this failure itself does not silently disappear — it produces a `FunctionCallError`/failure outcome, and per protocol rules, a failed refund/transfer just burns/drops the deposit rather than returning it anywhere (there is no secondary refund-of-a-refund mechanism, since `is_refund` refunds cannot recurse). This means an account owner who deletes their own account with `beneficiary_id: "system".parse().unwrap()` (a validly-parsing `AccountId`) would have their entire remaining balance permanently lost — it goes into a receipt that fails execution against a black-hole account with no automatic path to reclaim the funds.

### Title
Self-inflicted fund loss via `DeleteAccountAction.beneficiary_id` set to the reserved `system` account - (File: runtime/runtime/src/action_validation.rs)

### Summary
`validate_delete_action` in `runtime/runtime/src/action_validation.rs` only checks that `beneficiary_id` is a syntactically valid `AccountId` via `validate_action_account_id`, without excluding the reserved `"system"` account id. `"system"` passes standard account-id syntax validation (2–64 lowercase alphanumeric characters) but is explicitly documented as unusable/non-existent in state.

### Finding Description
`validate_delete_action` calls `validate_action_account_id(&action.beneficiary_id)`, which only runs `AccountId::validate` — pure syntax checking [6](#0-5) , [7](#0-6) . `"system"` is a syntactically valid `AccountId` yet is treated as a permanently non-existent, reserved account per the protocol's own documentation and code comments (`Receipt::new_balance_refund` and `new_gas_refund` hardcode `predecessor_id: "system"` to mark refund receipts) [2](#0-1) [8](#0-7) .

When `action_delete_account` executes, it unconditionally emits `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` for any non-zero remaining balance, with no check that `beneficiary_id != "system"` [3](#0-2) . If `beneficiary_id` is `"system"`, the resulting `Transfer` action targets a receiver account that will never exist. `check_account_existence`'s `Transfer` arm only allows implicit creation for non-refund receipts, and this generated receipt is itself a refund (`is_refund=true`), so `implicit_creation_allowed` returns `false` unconditionally [4](#0-3) , and the transfer fails with `ActionErrorKind::AccountDoesNotExist` [5](#0-4) .

### Impact Explanation
The deleting account's entire remaining native-token balance is routed into a receipt destined for an account that can never exist, and the transfer action fails. Because this is a refund receipt, there is no cascading refund-of-a-refund mechanism to return the tokens to anyone; the funds are effectively permanently lost/frozen, matching the "permanently frozen funds" impact criterion.

### Likelihood Explanation
Likelihood requires a user or a delegate/relayer to submit a `DeleteAccount` action with `beneficiary_id: "system"`. This is reachable directly from a single signed transaction (or via a `Delegate`/meta-transaction) authored by the account owner or an actor with `DeleteAccount` permission on the account, with no special privileges needed — the action is unprivileged and available to any account holder deleting their own account.

### Recommendation
Add an explicit check in `validate_delete_action` (or in `action_delete_account`) rejecting `beneficiary_id == "system"` (and any other reserved/non-existent identifiers), returning an `ActionsValidationError`/`ActionErrorKind` (e.g., analogous to `InvalidAccountId` or a new `BeneficiaryIsSystemAccount` variant) before the delete is admitted or executed, so users cannot inadvertently (or as a footgun) burn their remaining balance by targeting the reserved account.

### Proof of Concept
1. Create/fund account `alice.near` with a non-zero balance.
2. Submit a transaction from `alice.near` to itself containing a single `DeleteAccountAction { beneficiary_id: "system".parse().unwrap() }`.
3. Observe that `validate_delete_action` accepts it (since `"system"` is a syntactically valid `AccountId`), the account is deleted via `action_delete_account`, and `Receipt::new_balance_refund(&"system", account_balance)` is emitted.
4. Observe the resulting refund receipt's `Transfer` action fails with `ActionErrorKind::AccountDoesNotExist` because `implicit_creation_allowed` forbids account creation for refund receipts — the account's balance is unrecoverable.
