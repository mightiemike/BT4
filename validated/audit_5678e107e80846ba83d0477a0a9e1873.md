### Title
PromiseYield Timeout Queue Ordering Invariant Broken When `yield_timeout_length_in_blocks` Is Reduced via Protocol Upgrade — (`runtime/runtime/src/lib.rs`, `runtime/runtime/src/function_call.rs`)

---

### Summary

`resolve_promise_yield_timeouts` relies on the `PromiseYieldTimeout` queue being sorted in ascending `expires_at` order and uses a single early-exit `break` to stop processing. The ordering invariant holds only while `yield_timeout_length_in_blocks` is constant or increasing. If a protocol upgrade reduces this parameter, a newly enqueued yield can have an `expires_at` smaller than an already-queued entry, breaking the sort order. The `break` then fires on the older, larger-`expires_at` entry at the front of the queue, permanently blocking the newer entry from being processed until the older entry's timeout eventually fires. The yield callback is invoked late — or not at all within the expected window — constituting a contract execution flow breakage reachable by any ordinary user who calls `yield_create` after the upgrade.

---

### Finding Description

**Invariant relied upon:**

In `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs`):

```rust
// Queue entries are ordered by expires_at
if queue_entry.expires_at > apply_state.block_height {
    break;
}
```

The comment and the `break` together assert that once the front entry has not yet expired, no later entry can have expired either. The entire queue scan stops. [1](#0-0) 

**How `expires_at` is computed:**

Each new `PromiseYield` receipt enqueues a timeout in `function_call.rs`:

```rust
enqueue_promise_yield_timeout(
    state_update,
    &mut promise_yield_indices,
    account_id.clone(),
    receipt.input_data_ids[0],
    apply_state.block_height
        + config.wasm_config.limit_config.yield_timeout_length_in_blocks,
);
``` [2](#0-1) 

`enqueue_promise_yield_timeout` appends unconditionally to the tail of the FIFO queue without any ordering check: [3](#0-2) 

**Why the invariant breaks:**

The ordering invariant holds iff `expires_at` values are non-decreasing as entries are appended. This is true when `yield_timeout_length_in_blocks` is constant, because block heights are strictly increasing. However, `yield_timeout_length_in_blocks` is a versioned runtime config parameter: [4](#0-3) 

It is loaded per-protocol-version from the `RuntimeConfigStore`: [5](#0-4) 

If a protocol upgrade sets `yield_timeout_length_in_blocks` to a smaller value `T_new < T_old`, then for an existing queue entry created at height `H_old` with `expires_at_old = H_old + T_old`, and a new entry created at height `H_new > H_old` with `expires_at_new = H_new + T_new`, it is possible that:

```
expires_at_new = H_new + T_new  <  H_old + T_old = expires_at_old
```

whenever `T_old - T_new > H_new - H_old`. The new entry is appended after the old entry in the queue, but has a smaller `expires_at`. The queue is no longer sorted.

**Consequence:**

At block height `B` where `expires_at_new ≤ B < expires_at_old`:

- `resolve_promise_yield_timeouts` reads the front entry (the old one, `expires_at_old > B`) and immediately `break`s.
- The new entry (index = old_index + 1, `expires_at_new ≤ B`) is never reached.
- The `PromiseResume` receipt that should invoke the yield callback is never emitted.
- The yield receipt remains in the trie; the contract's timeout branch is not executed.

The new yield's callback is delayed until block `expires_at_old`, not `expires_at_new`. The delay is `expires_at_old − expires_at_new` blocks. [6](#0-5) 

---

### Impact Explanation

**Contract execution flow breakage.** Any contract that calls `yield_create` after the protocol upgrade and while old yields remain in the queue will have its timeout callback invoked late. The contract is stuck in the `Started` state for `expires_at_old − expires_at_new` extra blocks. If the contract uses the timeout to release funds, trigger downstream receipts, or enforce a deadline, those actions are delayed or produce incorrect outcomes. The `PromiseYieldTimeout` struct stores `expires_at` as a `BlockHeight` in the trie: [7](#0-6) 

The corrupted value is the effective firing time of the new yield's timeout: it is `expires_at_old` instead of the correct `expires_at_new`.

---

### Likelihood Explanation

- `yield_timeout_length_in_blocks` has been 200 since introduction and has not been changed in any protocol version diff in `CONFIG_DIFFS`.
- No guard in the codebase prevents a future protocol upgrade from reducing it.
- After such an upgrade, the vulnerability is triggered by any ordinary user calling `yield_create` while at least one older yield with a larger `expires_at` is still in the queue — a normal operational condition.
- The trigger requires no special permissions: `yield_create` is a standard WASM host function callable from any deployed contract.

---

### Recommendation

Replace the unconditional `break` in `resolve_promise_yield_timeouts` with a full linear scan (or sort the queue on insertion). The minimal fix mirrors the Astaria recommendation: do not assume ordering; instead scan all entries and process any whose `expires_at ≤ block_height`. Alternatively, enforce the ordering invariant at insertion time in `enqueue_promise_yield_timeout` by asserting that the new `expires_at` is ≥ the tail entry's `expires_at`, and document that `yield_timeout_length_in_blocks` must never be decreased in a protocol upgrade. A protocol-level constraint (e.g., a validation check in the config store diff application) should reject any diff that reduces `yield_timeout_length_in_blocks`.

---

### Proof of Concept

1. Deploy a contract that calls `yield_create` (WASM host function). Call it at block height `H_old = 100` with `yield_timeout_length_in_blocks = 200`. Queue now contains entry A: `expires_at = 300`.

2. A protocol upgrade at block height 150 reduces `yield_timeout_length_in_blocks` to 10.

3. Call `yield_create` again at block height `H_new = 160`. Queue now contains:
   - Entry A (index 0): `expires_at = 300`
   - Entry B (index 1): `expires_at = 170`

4. At block height 170, `resolve_promise_yield_timeouts` reads entry A: `300 > 170` → `break`. Entry B is never processed. The callback for the second yield is not invoked.

5. At block height 300, entry A is processed (its callback fires), then entry B is processed (its callback fires 130 blocks late). Any contract logic that expected the callback at block 170 has been broken. [8](#0-7) [9](#0-8) [3](#0-2)

// Enqueues given timeout to the PromiseYield timeout queue
pub fn enqueue_promise_yield_timeout(
    state_update: &mut TrieUpdate,
    promise_yield_indices: &mut PromiseYieldIndices,
    account_id: AccountId,
    data_id: CryptoHash,
    expires_at: BlockHeight,
) {
    set(
        state_update,
        TrieKey::PromiseYieldTimeout { index: promise_yield_indices.next_available_index },
        &PromiseYieldTimeout { account_id, data_id, expires_at },
    );
    promise_yield_indices.next_available_index = promise_yield_indices
        .next_available_index
        .checked_add(1)
        .expect("Next available index for PromiseYield timeout queue exceeded the integer limit");
}
