## Finding

Push Chain has a structurally identical bug to the reported Wormhole/Securitize issue: the Push Chain → Solana outbound path allows a full `uint256` amount to be irreversibly committed on Push Chain (PRC20 burn/lock inside the `UniversalTxOutbound` EVM event, captured by `BuildOutboundsFromReceipt`) before the destination-chain (Solana) width constraint (`u64`) is ever checked. The `u64` check only happens later, off-chain, in the Universal Client's Solana transaction builder — and if it fails, the outbound is permanently stuck with no automatic refund path.

### Title
Outbound amounts exceeding `u64::MAX` permanently strand user funds on the Push Chain → Solana path due to a uint256/u64 width mismatch discovered only after commit - (File: `universalClient/chains/svm/tx_builder.go`)

### Summary
`OutboundTx.Amount` is populated from a Solidity `uint256` emitted by the `UniversalTxOutbound` event on Push Chain's EVM layer [1](#0-0) , and is stored/committed as part of finalizing the EVM receipt into `OutboundTx{... Amount: event.Amount.String() ...}` with `Status_PENDING` [2](#0-1) . No bound check against `u64` (or any destination-specific numeric width) is performed at this stage. The `u64` fitness of the amount is validated only later, off-chain, by the Universal Client's Solana transaction builder when it tries to build the signing request or transaction: [3](#0-2) .

### Finding Description
When a user (or a module-driven flow) triggers a Push Chain → Solana outbound whose token amount exceeds `u64::MAX` (~1.8×10^19), the sequence is:

1. The EVM gateway contract (`UNIVERSAL_GATEWAY_PC`) emits `UniversalTxOutbound` with `amount` as `uint256` — no upper bound is enforced at the Solidity/event level, matching the pattern in the original report where the source chain accepts a wider type than the destination can decode.
2. `Keeper.BuildOutboundsFromReceipt` decodes this event and creates an `OutboundTx` record with `Status_PENDING`, storing the full-width decimal string in `Amount` [2](#0-1) . This commit happens as part of the same Push Chain EVM transaction that already moved/burned/locked the PRC20 balance — the value transfer on Push Chain's side is already final.
3. The `puniversald` Universal Client later picks up this `OutboundTx` and attempts to build the Solana-side transaction. Both `GetOutboundSigningRequest` and `BuildOutboundTransaction` explicitly check `amount.IsUint64()` and return an error when it doesn't fit [4](#0-3) .
4. If the check fails, no TSS signing session is ever created and no Solana transaction is ever built or broadcast for this outbound. There is no mechanism that automatically reverts, refunds, or otherwise resolves the `OutboundTx`.
5. Per the module's own documented invariant, the `PendingOutbounds` entry is only removed on validator consensus over a destination-chain observation (`PASSED`) [5](#0-4) . Since no destination-chain transaction is ever produced, no observation can ever be voted, and "ballot expiry does NOT remove the entry... there is no safe automatic resolution... resolution is governance-driven, not chain-driven" [6](#0-5) .

This is the same root cause pattern as the external report: the source chain's numeric width (`uint256`) is wider than what the destination chain program can structurally represent (`u64` in the Solana/Anchor gateway, seen throughout `tx_builder.go`'s Borsh encoding of `amount` as 8-byte little-endian [7](#0-6) ), and the funds move (burn/lock) on the source side before the destination's decode/processing capability is verified.

### Impact Explanation
Funds attached to an outbound whose amount exceeds `u64::MAX` become permanently frozen: they have already left Push Chain's live balance/PRC20 accounting via the outbound-triggering EVM call, but they can never be delivered to Solana (structurally impossible to encode `amount` in the Borsh `u64` field), and there is no automatic on-chain remediation — only manual, governance-driven intervention is documented. This matches the "permanent freezing of user or protocol-controlled funds" impact category.

### Likelihood Explanation
Reachable by an ordinary user without any privileged role: a user (or dApp) with a PRC20 balance large enough to exceed `2^64-1` raw units simply initiates a Push Chain → Solana withdrawal/outbound for that amount. For PRC20 tokens with 18 decimals this threshold corresponds to roughly 18.4 tokens — well within reach for tokens with meaningful total supply, and there is no PC-side gate preventing the outbound from being created in the first place. The finding is corroborated by the Universal Client's own test coverage explicitly exercising "amount overflows u64" as an error path rather than a proactively prevented state [8](#0-7) .

### Recommendation
Enforce the destination chain's numeric width (and any other chain-specific structural limits, e.g., Solana's transaction size cap already only warned about post-hoc at [9](#0-8) ) on Push Chain itself, before the outbound-triggering EVM call is allowed to commit/burn/lock funds. Concretely: when `uregistryKeeper`/chain config indicates the destination chain's VM type is SVM (or any non-EVM chain with narrower numeric types), reject the outbound-creating EVM call/transaction if `amount > math.MaxUint64` prior to any state mutation, instead of only discovering this later in the off-chain Universal Client after the value has already moved.

### Proof of Concept
1. Register/enable a Solana destination chain and a PRC20 token config as in existing integration tests (e.g., `test/integration/uexecutor/evm_hooks_and_outbound_test.go`).
2. Trigger (or simulate) a `UniversalTxOutbound` event with `amount` set to `2^64` (18446744073709551616), destined for the Solana chain, via the normal EVM outbound path.
3. Observe `BuildOutboundsFromReceipt` create an `OutboundTx` with `Status_PENDING` and `Amount = "18446744073709551616"` — no error at this stage [2](#0-1) .
4. Feed the resulting `OutboundCreatedEvent` into `TxBuilder.GetOutboundSigningRequest` (or `BuildOutboundTransaction`) in `universalClient/chains/svm/tx_builder.go`; observe the `"amount exceeds u64 max"` error, confirming no TSS signing session or Solana transaction can ever be produced for this outbound [3](#0-2) .
5. Confirm via `x/uexecutor/README.md`'s documented lifecycle that this `PendingOutbounds` entry is never automatically removed or refunded absent a destination-chain observation vote.
