### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash verification, allowing replay-verify to accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to authenticate that a locally re-executed `TransactionOutput` matches the trusted, ledger-info-signed `TransactionInfo` for a version. It checks status, gas used, write-set hash, and event root hash, but a code comment admits it deliberately skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that authenticate the actual state (Merkle) root produced by a transaction. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` validates execution status, gas, write-set hash (`state_change_hash`), and event root hash against the authenticated `TransactionInfo`: [2](#0-1) 

But it explicitly does not check the state-checkpoint-related hashes, with the code comment stating:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
Ok(())
``` [3](#0-2) 

This function is the sole state-matching check used by the chunk executor's `verify_execution` path (used for replay-verify / state-sync-by-execution verification), and by `aptos-debugger` / CLI replay tooling: [4](#0-3) 

Unlike the `TransactionInfo`/write-set/event checks, no equivalent for state-checkpoint hashes is invoked in this call path — the `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields carried in the authenticated `TransactionInfo` (which are themselves covered by the ledger info signature and accumulator proof, per `TransactionInfoWithProof::verify` and `TransactionInfoV1::new`) are never compared against the locally computed state root in this verification routine: [5](#0-4) 

Note: This is distinct from the *live* chunk-execution ledger-update path (`ChunkExecutor::update_ledger`), which does separately pass `known_state_checkpoints`/`known_hot_state_checkpoints`/`known_position_state_checkpoints` into `DoStateCheckpoint::run()` for cross-checking during state sync: [6](#0-5) 
The gap is specifically in the `verify_execution`/replay-verify code path that relies on `ensure_match_transaction_info` alone (db-tool `replay_on_archive`, `aptos-debugger`), which is the exact analog of the external report's pattern: a check that exists and looks like it enforces an invariant, but the underlying comparison is incomplete/incorrect for a subset of cases (here, when `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/trading-native or hot-state features are active), silently permitting acceptance of state that doesn't match the correct result.

### Impact Explanation
Replay-verify tooling exists specifically to catch state divergence between historical execution and the authenticated chain state (a critical detection mechanism for state-integrity bugs, consensus bugs, or storage corruption). Because `ensure_match_transaction_info` does not compare `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, a divergence in the actual Merkle/state root produced by local re-execution vs. the authenticated on-chain `TransactionInfo` will not be flagged by this check. This can mask genuine state corruption or a hard-fork-causing divergence during replay/verification, undermining a proof-integrity safety net that operators and auditors depend on to detect wrong committed state.

### Likelihood Explanation
The gap is unconditionally present in `ensure_match_transaction_info` — it is not gated by a flag; only the fields it fails to check are gated by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state feature. As those features are rolled out, the exposure of this blind spot in replay-verify grows. The code comment itself confirms the developers are aware but have not yet implemented the fix ("Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), indicating this is a known-but-unresolved gap rather than a hypothetical one.

### Recommendation
Add explicit comparisons in `ensure_match_transaction_info` for `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the locally computed state/hot-state/position roots (mirroring the pattern already used for `write_set_hash` and `event_root_hash`), and ensure this check is enforced before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled in production, consistent with the existing code comment's own guidance.

### Proof of Concept
Not applicable as an active exploit against a live consensus path — this is a verification-tooling gap. Conceptually: replay a transaction whose locally recomputed hot/position state root differs from the authenticated `TransactionInfo.state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` (with `COMPUTE_TRADING_NATIVE_STATE_ROOTS` enabled) via `aptos-debugger` or `aptos-move/cli` replay/verify commands that call `ensure_match_transaction_info`; the call will still return `Ok(())` because those hash fields are never compared, per the code path traced at: [1](#0-0) [7](#0-6)

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
