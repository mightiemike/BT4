### Title
Unvalidated `beneficiary_id` in `DeleteAccountAction` can cause permanent loss of an account's funds - (File: runtime/runtime/src/actions.rs)

### Summary
`DeleteAccountAction` lets a signer (or a contract acting on its own account via `promise_batch_action_delete_account`) delete an account and redirect its entire balance to an arbitrary `beneficiary_id` supplied in the action. The protocol only validates that `beneficiary_id` is a syntactically valid `AccountId`; it never checks that the account actually exists before the delete is executed and the refund receipt is generated.

### Finding Description
`action_delete_account` computes the account's remaining balance and unconditionally queues a refund receipt to `beneficiary_id`, then removes the account and returns: [1](#0-0) 

The only check performed on `beneficiary_id` anywhere in the pipeline is a format/charset validation (`InvalidAccountId`), documented here: [2](#0-1) 

There is no check that `beneficiary_id` corresponds to an account that exists on-chain. This is confirmed by an internal test comment that explicitly documents the failure mode: [3](#0-2) 

The same unvalidated `beneficiary_id` is reachable both from a signed transaction (`Action::DeleteAccount`) and from a contract's own account via the Promise API host function `promise_batch_action_delete_account`, which likewise only validates that the bytes form a valid account id, not that the account exists: [4](#0-3) 

This mirrors the reported Solidity bug class exactly: a user-supplied "receiver" (here, `beneficiary_id`) is trusted without existence validation, and a single mistake (typo, unregistered account, or an account that has never been created) causes the transferred value to be routed to a target that cannot receive/claim it as intended.

### Impact Explanation
Because `beneficiary_id` is never checked for existence, a single transaction signer deleting their own account with a mistyped or non-existent (but syntactically valid) `beneficiary_id` results in the account's entire remaining NEAR balance being irrecoverably misdirected — the account that was supposed to receive the funds does not exist, and the account that owned the funds has just been deleted and no longer has any access keys to recover control. This is a direct, unprivileged-triggerable, permanent loss of user funds (aligns with the "permanently frozen funds" / "unauthorized value movement" acceptance criteria), and the action is irreversible since `DeleteAccountAction` is final and immediately removes the account from state in the same apply step.

### Likelihood Explanation
Likelihood is realistic: the action is reachable directly by any account holder submitting a normal transaction, or by any deployed contract calling the Promise API on its own account, with no special privilege required. Since NEAR account names are free-form strings, `beneficiary_id` typos (e.g. `alise.near` instead of `alice.near`) or otherwise-valid-but-never-registered account ids will pass the only check that exists (format validation), making this an easy user error with no on-chain safeguard, exactly the class of issue the original report flags for `deposit`/`withdraw` receivers in the Solidity contract.

### Recommendation
Before committing to delete the account, verify that `beneficiary_id` exists (or restrict deletion to require `beneficiary_id != account_id` and an existing account, similar to how the wallet contract validates targets). Alternatively, disallow leaving `beneficiary_id` unspecified/unverified and default to a documented, safe fallback (e.g., require the beneficiary to be pre-verified via a view call before submission, or reject the delete if the account cannot be shown to exist at apply time), and clearly surface an execution error rather than silently completing the transfer to a non-existent target.

### Proof of Concept
1. Create account `victim.near` with balance `B`.
2. `victim.near` signs a transaction with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "typo-nonexistent.near".parse().unwrap() })` (test helper pattern shown in `runtime/runtime/src/tests/apply.rs:3294-3298` and `chain/chain/src/runtime/tests.rs:1383-1393`).
3. `action_delete_account` removes `victim.near` and queues a `Receipt::new_balance_refund(&"typo-nonexistent.near", B)` (`runtime/runtime/src/actions.rs:380-387`) without ever checking that `typo-nonexistent.near` exists.
4. `victim.near` no longer exists (deleted, no access keys), and the balance `B` is routed to an account that was never registered by anyone, permanently divorcing the funds from any recoverable owner.

Note: I was not able to fully trace, within the available tool budget, the exact terminal behavior of the generated balance-refund receipt when its target account does not exist (e.g., whether NEAR implicitly creates the target account with the balance, or whether the tokens are ultimately burned/orphaned). The root-cause code path (missing existence validation on `beneficiary_id`) and the explicit developer acknowledgment of the risk are confirmed by the cited code and test comment; if precise on-chain fund disposition needs to be confirmed further, a Devin session with full repo/test execution access would be needed to trace `apply_action_receipt` handling of a `Transfer`/balance-refund receipt to a nonexistent named account.

pub fn promise_batch_action_delete_account(
    ctx: &mut Ctx,
    memory: &mut [u8],
    promise_idx: u64,
    beneficiary_id_len: u64,
    beneficiary_id_ptr: u64,
) -> Result<()> {
    ctx.result_state.gas_counter.pay_base(base)?;
    if ctx.context.is_view() {
        return Err(HostError::ProhibitedInView {
            method_name: "promise_batch_action_delete_account".to_string(),
        }
        .into());
    }
    let beneficiary_id = read_and_parse_account_id(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        &ctx.config,
        beneficiary_id_ptr,
        beneficiary_id_len,
    )?;

    let (receipt_idx, sir) = promise_idx_to_receipt_idx_with_sir(ctx, promise_idx)?;

    pay_action_base(
        &mut ctx.result_state.gas_counter,
        &ctx.fees_config,
        ActionCosts::delete_account,
        sir,
    )?;

    ctx.ext.append_action_delete_account(receipt_idx, beneficiary_id);
    Ok(())
