## Title
Accrual pause freezes `last-update` without freezing time-based interest, causing retroactive interest re-application on unpause that mispribes shares mid-block for depositors/redeemers - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) implements `accrue` with an explicit "pause" pass-through: when `pause-states.accrue` is true, `accrue` returns the currently stored `{index, lindex}` as `(ok ...)` instead of reverting or otherwise blocking dependent operations [1](#0-0) . Because the pass-through branch skips `(var-set last-update stacks-block-time)`, the `last-update` timestamp is not advanced while paused, but `deposit`/`redeem`/`system-borrow` continue to execute normally using whatever `index`/`lindex` are currently stored [2](#0-1) .

### Finding Description
`accrue` computes `next-index`/`next-liquidity-index` as a function of elapsed time since `last-update` (`stacks-block-time - last-update`). The non-paused branch updates `index`, `lindex`, mints treasury shares for the reserve cut, and only then advances `last-update` to `stacks-block-time`: [3](#0-2) 

The paused branch simply returns the stale values with no state mutation at all:
```
(if (get accrue states)
    ;; PAUSED: Pass-through without reverting
    (ok { index: idx, lindex: lidx })
``` [4](#0-3) 

Meanwhile `deposit`/`redeem`/`system-borrow` still call `(try! (accrue))` and, on the pass-through `ok`, proceed with the rest of their logic (transferring funds, minting/burning shares, updating debt) using the presently-stored, un-accrued `index`/`lindex` — i.e., the pause never actually blocks these operations, it only blocks the *bookkeeping* of `last-update`/`index`/`lindex`: [5](#0-4) 

Because `last-update` is frozen, the *next* time accrual is unpaused and any transaction calls `accrue`, `next-index`/`next-liquidity-index` compute interest for the entire elapsed wall-clock time since the last real update — including the whole paused interval — and apply it as one lump jump to `index`/`lindex`. This means:
- Any depositor or redeemer whose transaction is included during the pause interacts with the vault using stale, frozen conversion rates (`convert-to-shares-preview`/`convert-to-assets-preview`, both driven by `lindex`) that do not reflect the interest that is retroactively about to be applied.
- The very first transaction that triggers un-paused `accrue` after resuming applies the entire deferred interest atomically to whoever holds shares (and to the debt of whoever borrowed) at that moment — this necessarily favors whoever's shares are outstanding at the instant of the catch-up versus those who transacted (deposited/redeemed) during the pause window.

This is the direct analog of the “pause that passes through instead of reverting” bug class: instead of guarding the state that time-based math depends on (`last-update`), the pause silently allows dependent value-moving operations (`deposit`/`redeem`/`borrow`) to proceed against a frozen source-of-truth, and the frozen value's staleness is only reconciled later via a lump catch-up rather than being prevented at the boundary.

### Impact Explanation
This falls under temporary freezing/mispricing of unclaimed yield: value that should accrue continuously to existing suppliers/debt instead gets deferred and dumped in one lump sum at an unpredictable point after unpause, meaning users who deposit or redeem during the pause window transact at an incorrect (stale) exchange rate relative to the true, deferred interest that will be applied on resumption. Depending on pause duration and rate, this can transfer meaningful unclaimed-yield value between suppliers who happen to be in vs. out of the pool at the moment accrual resumes.

### Likelihood Explanation
Triggering requires only that the DAO/admin toggles `pause-states.accrue` (a legitimate, intended operational control) for a nontrivial duration and that ordinary users continue to call `deposit`/`redeem`/`borrow` during that window — no privileged access or DAO compromise is needed by the attacker to *exploit* the mispricing, only awareness of the pause state (which is public on-chain). This makes the likelihood moderate: it depends on an operational pause happening, but once it does, the mispricing window is deterministic and observable.

### Recommendation
When `accrue` is paused, either (a) also pause `deposit`/`redeem`/`borrow`/`repay` so no value-moving action occurs against the frozen index, or (b) still advance `last-update` (and optionally freeze the rate contribution to zero, but on a per-second basis) while paused so that no retroactive interest is realized once resumed, avoiding the lump-sum catch-up entirely.

### Proof of Concept
1. Vault has `index = lindex = 1e12` (base), `last-update = T0`.
2. DAO calls `set-pause-states` (or equivalent) to set `accrue: true` on `v0-vault-usdh.clar`. `last-update` remains `T0`.
3. Time passes to `T1` (e.g., several days), during which real utilization/interest would have grown `index`/`lindex` substantially.
4. During `[T0, T1]`, User A calls `redeem` — `accrue()` pass-through returns `{index, lindex}` unchanged; `convert-to-assets-preview` uses the stale `lindex`, so A receives assets priced as if no interest had accrued [6](#0-5) .
5. DAO unpauses accrual (`accrue: false`) at time `T1`.
6. User B (any caller) triggers `accrue` (e.g., via `deposit`) — `next-index`/`next-liquidity-index` now compute the full interest for `T1 - T0` in one step and mint the corresponding treasury shares, and `lindex`/`index` jump discontinuously [7](#0-6) .
7. Result: User A, who redeemed during the pause, was priced at the pre-pause rate and missed the deferred interest that got applied entirely to shares outstanding at step 6 — a mispricing that would not occur if either deposits/redeems were also paused, or `last-update` correctly reflected elapsed time.

Note: I could not find a `set-pause-states`/pause-setter function body in the excerpts reviewed to confirm the exact authorization mechanism (likely DAO-only), so the precise privilege gating for toggling `pause-states.accrue` should be verified directly in the vault contract's setter functions before treating this as fully confirmed.
