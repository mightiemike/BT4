### Title
Unhandled `.unwrap()` on `receiver_shard_id()` in delayed-receipt filtering panics the node on a stale cross-shard receipt after resharding - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` unconditionally `.unwrap()`s the `Result` returned by `Receipt::receiver_shard_id()` while popping receipts from the delayed-receipt queue during chunk apply. This mirrors the CVE-2023-42754 bug class: code assumes an object (here, a receipt's target shard) is always resolvable in the current context, but that assumption breaks once the object has been "re-routed" through an intervening subsystem event (resharding), turning a normally infallible path into one that can return `Err` and panic instead of being handled gracefully.

### Finding Description
`receipt_filter_fn` is used by `DelayedReceiptQueueWrapper::pop` while draining the delayed receipt queue during `Runtime::apply`: [1](#0-0) 

It calls `receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap()`. `receiver_shard_id` returns `Result<ShardId, EpochError>`, and for `ReceiptEnum::GlobalContractDistribution` it can return `Err` when the receipt's `target_shard` cannot be resolved to a shard in the current layout: [2](#0-1) 

Resolution depends on `ShardLayoutV3::resolve_to_current_shard`, which recursively walks the `shards_split_map` history: [3](#0-2) 

If a `GlobalContractDistribution` receipt sits in the delayed-receipt queue across two (or more) resharding events, or if the split-history bookkeeping does not retain the mapping far back enough, `resolve_to_current_shard` returns `None`, `receiver_shard_id` returns `Err`, and the `.unwrap()` in `receipt_filter_fn` panics — crashing chunk application on every honest node processing that chunk.

A test explicitly documents this exact scenario and its consequence: [4](#0-3) [5](#0-4) 

The test comment states verbatim: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations."*

### Impact Explanation
This is a transaction-triggered halt: an unprivileged account can deploy a global contract (a normal, permissionless action), causing a `GlobalContractDistribution` receipt to be created and delayed (e.g. by saturating chunk gas so the receipt sits in the delayed queue), and if two resharding events occur while it is delayed, every validator applying that chunk panics in `receipt_filter_fn`. This matches the "transaction-triggered halt" acceptance criterion — a node crash caused entirely by a single submitted transaction combined with protocol-level resharding, not by malicious peers/validators.

### Likelihood Explanation
Reaching this bug requires: (1) an unprivileged `DeployGlobalContract` action, (2) delaying its distribution receipt (achievable by gas-saturating the target shard), and (3) two dynamic-resharding events occurring while the receipt is delayed. This is a narrow but protocol-native combination — dynamic resharding is a normal operational event, not attacker-controlled, so likelihood depends on resharding cadence coinciding with a delayed distribution receipt. The presence of a dedicated regression test in the codebase (`test_stale_global_contract_distribution_after_double_resharding`) indicates this was identified and is being actively guarded against, suggesting it is a recognized, reachable failure mode rather than a purely theoretical one.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` with proper error propagation (return `Result` from the function and handle it in `pop`), and treat an unresolvable `receiver_shard_id` for a stale `GlobalContractDistribution` receipt as a case to route to a fallback/current shard (or drop with a warning) rather than panicking, consistent with how the codebase already tolerates other unusual resharding transients elsewhere in `congestion_control.rs`.

### Proof of Concept
1. Deploy a global contract from an account whose shard will be the target of a resharding split (`DeployGlobalContract` action), producing a `GlobalContractDistribution` receipt with `target_shard = S_A`.
2. Saturate compute on `S_A` every block (e.g., via `burn_gas_raw` calls) so the distribution receipt is pushed into, and remains in, the delayed-receipt queue.
3. Trigger two sequential dynamic-resharding events (via `DynamicReshardingConfig.force_split_shards`) while the receipt remains delayed, so its `target_shard` becomes two generations stale relative to the current shard layout.
4. Stop saturating and let the delayed queue drain; if `resolve_to_current_shard` cannot map the stale `target_shard` forward, `receipt_filter_fn`'s `.unwrap()` panics, halting the chunk application for every node — reproduced by the test scenario in `test-loop-tests/src/tests/global_contracts_distribution.rs:32-186`.

Note: I could not fully verify within the available context whether `shards_split_map` construction (`build_shard_split_map`, `derive_with_layout_history`) guarantees retention of the full split history indefinitely across arbitrarily many resharding generations, or whether some bound/GC on historical layouts could cause `resolve_to_current_shard` to fail even without a bug in `receiver_shard_id` itself. This would need further investigation in `chain/epoch-manager/src/lib.rs` and `chain/epoch-manager/src/adapter.rs` (where `get_shard_layout_history`/`derive_with_layout_history` are used) to determine the exact conditions under which the `.unwrap()` panic is triggerable, and whether it has already been mitigated elsewhere in the current codebase.

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }
