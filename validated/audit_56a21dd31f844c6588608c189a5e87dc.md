### Title
NullPointerException DoS in `BlockChainMetricManager.getDupWitness()` via TOCTOU race between counter increment and map update in `applyBlock()` - (File: framework/src/main/java/org/tron/core/metrics/blockchain/BlockChainMetricManager.java)

### Summary
`BlockChainMetricManager.applyBlock()` increments the `BLOCKCHAIN_DUP_WITNESS` counter via `MetricsUtil.counterInc(...)` (line 141) before it puts the corresponding entry into `dupWitnessBlockNum` (line 144), creating a window in which the counter exists but the map entry does not. If `getDupWitness()` (called from `getBlockChainInfo()` → `getMetricsInfo()` → the `/metrics` HTTP endpoint) executes during this window, `dupWitnessBlockNum.get(witness)` returns `null`, which is auto-unboxed to `long` at line 207 and throws a `NullPointerException`.

### Finding Description
In `BlockChainMetricManager.applyBlock()`:
```

...
dupWitnessBlockNum.put(witnessAddress, block.getNum());                       // line 144

``` [2](#0-1) 

`getDupWitness()` is invoked from `setBlockChainInfo()`, which is reachable via `getBlockChainInfo()` → `MetricsApiService.getMetricsInfo()` → the HTTP `/metrics` servlet, exposed to any HTTP client that can reach the metrics port. [3](#0-2) 

The block-import thread calls `applyBlock()` on every new block. Because `MetricsUtil.getCounters` (the metrics registry) and `dupWitnessBlockNum` (`ConcurrentHashMap`) are two independently-updated data structures with no shared lock, the two writes in `applyBlock()` are not atomic relative to reads in `getDupWitness()`. A reader thread executing between line 141 and line 144 sees a counter entry with no corresponding map entry, causing `dupWitnessBlockNum.get(witness)` to return `null` and the auto-unboxing at `long blockNum = ...get(witness)` to throw an NPE.

### Impact Explanation
This is confined to the metrics HTTP servlet thread pool: an uncaught NPE in `MetricsApiService.getMetricsInfo()` propagates out of the servlet's `doGet`, producing a 500 error for that request (and potentially an unhandled exception in the calling thread, depending on servlet-container exception handling). It does not affect block validation, consensus, or any state that is part of the canonical chain — `witnessInfo`/`dupWitnessBlockNum` are metrics-only, in-memory, and never consulted by block processing, transaction execution, or fork-choice logic. The claimed "state divergence"/"consensus" framing in the question is not substantiated: this bug can at most cause repeated request failures on the `/metrics` endpoint, not corruption of blockchain state or node crash (JVM-level crash requires an uncaught exception escaping all threads, and HTTP servlet exceptions are caught by the servlet container per-request).

### Likelihood Explanation
Preconditions: the node must expose the HTTP metrics endpoint (`fullnode.http.metricsPort`), which is a non-default, operator-opt-in configuration (not found enabled in the default `config.conf`, and no evidence in the codebase that it is on by default). The race window between lines 141 and 144 is extremely small (a few CPU instructions), so triggering the NPE requires very tight timing alignment between block-apply and a concurrent GET during that specific micro-window, and only fires the very first time a given witness address produces a duplicate block (subsequent reads would see the entry already present, since maps aren't cleared). This makes exploitation low-probability per attempt and not reliably repeatable, and does not scale to a meaningful denial of the whole node (only the metrics endpoint, and only intermittently).

### Recommendation
In `applyBlock()`, update `dupWitnessBlockNum` before or atomically with the counter increment (or use a single `ConcurrentHashMap.compute`/synchronized block covering both operations). In `getDupWitness()`, use `dupWitnessBlockNum.getOrDefault(witness, 0L)` instead of `.get(witness)` to avoid the NPE regardless of ordering, and treat the metrics servlet's data as best-effort/eventually-consistent since it does not participate in consensus.

### Proof of Concept
```java
@Test
public void testConcurrentApplyBlockAndGetDupWitness() throws InterruptedException {
  BlockChainMetricManager manager = new BlockChainMetricManager();
  // wire mocked dbManager/chainBaseManager as needed

  ExecutorService pool = Executors.newFixedThreadPool(4);
  AtomicBoolean failed = new AtomicBoolean(false);

  Runnable applier = () -> {
    for (int i = 0; i < 100000; i++) {
      try {
        manager.applyBlock(sameWitnessDuplicateBlockCapsule());
      } catch (Exception e) {
        failed.set(true);
      }
    }
  };
  Runnable reader = () -> {
    for (int i = 0; i < 100000; i++) {
      try {
        manager.getBlockChainInfo();
      } catch (NullPointerException e) {
        failed.set(true);
      }
    }
  };

  pool.submit(applier);
  pool.submit(reader);
  pool.shutdown();
  pool.awaitTermination(30, TimeUnit.SECONDS);

  assertFalse("NPE observed in getDupWitness() due to counter/map race", failed.get());
}
```
Expected result on the current code: the test fails intermittently with `NullPointerException` at `BlockChainMetricManager.getDupWitness()` line 207, confirming the race exists — but this is limited to the opt-in metrics HTTP endpoint and does not affect consensus or core chain state.
