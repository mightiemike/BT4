## Title
Replay-verify's `TransactionOutput::ensure_match_transaction_info` omits checkpoint-hash validation, allowing corrupted/wrong state-checkpoint, hot-state, and position-state roots to pass as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-response/replay comparator that is supposed to prove a locally-computed `TransactionOutput` matches the `TransactionInfo` that is bound (via the transaction accumulator) to a signed `LedgerInfo`. It explicitly checks status, gas, write-set hash, and event root hash, but a code comment inside the function itself admits it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` fields of `TransactionInfoV1`. [1](#0-0) 

### Finding Description
`TransactionInfoV1` carries multiple state roots beyond the write-set/event hash: `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, each derived from a different Sparse-Merkle/JMT summary computed by `DoStateCheckpoint::run` during execution. [2](#0-1) [3](#0-2) 

These per-transaction checkpoint hashes are only cross-checked against externally-provided "known" hashes inside `DoStateCheckpoint::get_state_checkpoint_hashes`, and that check is guarded by `if let Some(known) = known_state_checkpoints` — i.e. it only fires when the caller (e.g. chunk executor, replaying from a downloaded chunk with `TransactionInfo`s already attached) supplies the known hashes. [4](#0-3) 

Separately, `ensure_match_transaction_info` is the generic "does this locally-produced `TransactionOutput` match this authenticated `TransactionInfo`" check used by tooling such as `replay_on_archive` and the Aptos debugger to validate replayed execution against archived, ledger-info-signed data. It verifies `status`, `gas_used`, `write_set_hash` (`state_change_hash`), and `event_root_hash`, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the code comment states this outright: *"this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."* [5](#0-4) 

This is structurally the same integrity gap as the external H-07 report: a value that is supposed to gate acceptance/correctness of committed state ends up not actually being checked (there, `customPrecisionMultipliers` silently collapsed to zero because arithmetic wasn't bounded; here, the checkpoint-hash equality that should gate "replay is correct" is simply omitted from the comparator, effectively "rounding" the divergence check to a no-op / always-pass for these fields).

### Impact Explanation
`replay_on_archive` and the Aptos debugger's replay path use `ensure_match_transaction_info` as the authoritative gate that a re-executed transaction output is faithful to the historical, ledger-info-authenticated record. Because the comparator does not check `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, any divergence in state-checkpoint construction (JMT summary bugs, hot-state root bugs, native-position root bugs, or a maliciously/erroneously altered archive `TransactionInfo` for these specific fields) will not be detected by this check. Given the storage/executor code explicitly calls out `COMPUTE_TRADING_NATIVE_STATE_ROOTS` as the feature this gap blocks from being safely enabled, turning on this feature while replay-verify tooling relies on this comparator would let a wrong position-state (or hot-state) root be accepted as "verified" even though it is not the correct VM/state result. This is a state-commitment / proof-integrity impact: an authenticated response (the replay-verified `TransactionInfo`) is bound to a version but not actually checked against one of its constituent authenticated roots.

### Likelihood Explanation
The gap is currently latent because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and `hot_state_root_in_txn_info` are not yet enabled in the code path exercised by `ensure_match_transaction_info`'s callers (per the TODO comment and the "not yet run in consensus/state-sync" comments in `state_checkpoint_output.rs`). It is not exploitable against mainnet as configured today, but it is a real correctness/verification gap in the invariant that must hold before that feature is turned on, and the code explicitly documents this as an open bug that needs to be fixed before enabling the feature. [6](#0-5) 

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when the caller can supply the corresponding locally-computed values), and make it a hard error before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO` are enabled on any network. Callers of this function (`replay_on_archive.rs`, `aptos_debugger.rs`, `chunk_executor/mod.rs`) will need to be updated to pass through the locally-recomputed checkpoint hashes for this to be effective.

### Proof of Concept
Conceptual PoC (feature-gated, not exploitable with current mainnet config):
1. Enable `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or `hot_state_root_in_txn_info`) so `TransactionInfoV1.position_state_checkpoint_hash` (or `hot_state_checkpoint_hash`) is populated and authenticated via the transaction accumulator/ledger info.
2. Run `replay_on_archive` (or the debugger's replay path) against an archive where the `position_state_checkpoint_hash` in a `TransactionInfo` does not match what local re-execution of the native-position JMT would produce (e.g. due to a bug in `DoStateCheckpoint::compute_position_checkpoint`, or a corrupted archive entry).
3. `ensure_match_transaction_info` will still return `Ok(())` because it never compares `txn_info.position_state_checkpoint_hash()` (or `hot_state_checkpoint_hash()`) against the locally recomputed value — the divergence goes undetected, and replay-verify falsely reports success.

*Note: I could not fully trace the exact call sites in `replay_on_archive.rs` and `aptos_debugger.rs` (grep found matches but I was unable to read their full bodies before the tool budget ran out), so I cannot state with certainty whether those call sites already pass/compare checkpoint hashes through some other path. The core finding — that `ensure_match_transaction_info` itself omits this check, as confirmed by the in-code TODO — is verified directly from `types/src/transaction/mod.rs`.*

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn get_state_checkpoint_hashes(
        execution_output: &ExecutionOutput,
        known_state_checkpoints: Option<Vec<Option<HashValue>>>,
        computed_last_checkpoint_hash: HashValue,
        label: &str,
    ) -> Result<Vec<Option<HashValue>>> {
        let _timer = OTHER_TIMERS.timer_with(&[&format!("get_{label}_checkpoint_hashes")]);

        let num_txns = execution_output.to_commit.len();
        let last_checkpoint_index = execution_output
            .to_commit
            .state_update_refs()
            .last_inner_checkpoint_index();

        if let Some(known) = known_state_checkpoints {
            ensure!(
                known.len() == num_txns,
                "Bad number of known {label} hashes. {} vs {}",
                known.len(),
                num_txns,
            );
            if let Some(idx) = last_checkpoint_index {
                ensure!(
                    known[idx] == Some(computed_last_checkpoint_hash),
                    "{label} root hash mismatch with known hashes passed in. {:?} vs {:?}",
                    known[idx],
                    Some(computed_last_checkpoint_hash),
                );
            }
            Ok(known)
        } else {
            if !execution_output.is_block {
                // We should enter this branch only in test.
                execution_output.to_commit.ensure_at_most_one_checkpoint()?;
            }

            let mut out = vec![None; num_txns];
            if let Some(index) = last_checkpoint_index {
                out[index] = Some(computed_last_checkpoint_hash);
            }
            Ok(out)
        }
