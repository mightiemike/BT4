## Title
Vote account inflation-rewards commission collector can be swapped just before epoch-boundary settlement, redirecting the entire previous epoch's accrued commission away from the collector who actually earned it - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The vote program lets the authorized withdrawer redirect where inflation-reward and block-revenue commission is paid via `update_commission_collector` (`CommissionKind::InflationRewards` / `CommissionKind::BlockRevenue`, SIMD-0232). Unlike the commission *rate*, which is deliberately delayed by a full epoch to prevent "last minute commission rugs," the commission *collector* for inflation rewards is not delayed at all. This lets the withdrawer redirect an entire epoch's worth of already-accrued (but not yet settled) commission to a brand-new collector right before the reward-settlement code runs, instead of paying it to whichever collector was designated during that epoch.

### Finding Description
`update_commission_collector` simply overwrites `inflation_rewards_collector`/`block_revenue_collector` in the live vote state, with no timing restriction: [1](#0-0) 

Compare this to the commission *rate* update path, which the codebase explicitly protects against "last minute commission rugs" by using a snapshot of vote-account state from up to two epochs earlier: [2](#0-1) 

and by looking up `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` before falling back to the live state: [3](#0-2) 

However, the *collector pubkey* used to pay out that same commission is read directly from the current/live vote state (`vote_state`, sourced from `distribution_epoch_vote_accounts`, i.e., the state right before distribution) with no equivalent delay: [4](#0-3) 

For block-revenue commission there is an explicit, deliberate mitigation: the collector id is intentionally read from the epoch-stakes snapshot from the *beginning of the previous epoch*, precisely to avoid this kind of front-running: [5](#0-4) 

No such protection exists for the inflation-rewards collector path in `redeem_delegation_rewards`/`calculate_stake_rewards_and_commissions`, meaning the withdrawer can call `UpdateCommissionCollector` for `CommissionKind::InflationRewards` at any point up until the epoch-boundary reward calculation executes, and the newly designated collector — not the one active throughout the just-completed epoch — receives the full commission computed for that epoch's stake rewards.

### Impact Explanation
This allows the vote account's withdrawer authority to divert an entire epoch's already-earned inflation-reward commission away from a previously designated collector (e.g., a delegation-service operator or third party who was owed that commission for the epoch that already elapsed) to a new address, at the very last moment before settlement. This is a fund-misallocation issue impacting whichever party was relying on the vote account's collector configuration to receive commission it had already earned.

### Likelihood Explanation
Likelihood is Medium: it requires control of the vote account's authorized withdrawer key (a privileged but legitimate participant in the vote-account/collector relationship), and precise timing relative to the epoch boundary, but no other special conditions — any withdrawer can trigger this deterministically every epoch.

### Recommendation
Apply the same delay/snapshot protection used for `block_revenue_collector` and for the commission rate to the `inflation_rewards_collector` (and consistently to `block_revenue_collector` in the inflation-rewards path as well): resolve the commission collector to use from a snapshot taken before the start of the rewarded epoch, or otherwise ensure any pending/accrued commission is settled using the collector that was active while that commission was earned, before allowing `update_commission_collector` to take effect for future settlements.

### Proof of Concept
1. Vote account's `inflation_rewards_collector` is set to Address A for the duration of epoch N.
2. Near the very end of epoch N (last block before the epoch boundary), the authorized withdrawer submits `UpdateCommissionCollector` changing the collector to Address B via `update_commission_collector` (`programs/vote/src/vote_state/mod.rs:908-933`).
3. At the epoch boundary, `redeem_delegation_rewards` computes commission for the entirety of epoch N's stake activity but reads the collector pubkey from the current (post-update) vote state (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:750-757`), sending the full commission to Address B instead of Address A, even though Address A was the designated collector for essentially all of epoch N.

/// Update the vote account's commission collector (SIMD-0232).
pub fn update_commission_collector<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    new_collector: NewCommissionCollector,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    rent: &Rent,
) -> Result<(), InstructionError> {
    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let new_collector_key = new_collector.validate_and_resolve_key(vote_account, rent)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_collector(new_collector_key);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_collector(new_collector_key);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
