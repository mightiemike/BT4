### Title
Coarse-grained "Active" permission scoping lets any permitted key drain an account via arbitrary target/asset/amount contracts - (File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java)

### Summary
The Vault.sol finding is a data-validation gap: an approval granted to a specific spender is not scoped to any particular counterparty, asset, or amount, so that spender (or anything it interacts with) can move *any* of the user's deposited funds. Java-tron's account "Active" permission / multi-signature model has the same structural weakness: an owner delegates signing authority to a key by granting it bits in a 256-bit `operations` bitmask that is keyed **only by `ContractType`** — not by counterparty address, token/asset ID, contract address, or amount. Once a key is authorized for a given `ContractType` (e.g. `TransferContract`, `TransferAssetContract`, `TriggerSmartContract`), it can execute that operation against **any** receiver/asset/contract and for **any** amount using the owner's account and funds, exactly like a broadly-approved "spender" in the Vault report can transfer any of the depositor's balance.

### Finding Description
The `Permission.operations` field is documented as "1 bit 1 contract" [1](#0-0) . When an owner sets up an "Active" permission for a delegate key (or a multisig participant), validation only checks that the requested bit corresponds to an existing/allowed `ContractType`; it never restricts the operation to a specific receiver address, asset id, target smart-contract address, or value/amount [2](#0-1) .

At signature-verification time, `TransactionCapsule.checkPermission` / `TransactionUtil.checkPermissionOperations` / `WalletUtil.checkPermissionOperations` enforce authorization purely by testing the single bit for `contract.getTypeValue()`: [3](#0-2) [4](#0-3) 

No part of this check consults the contract's own fields (`to_address`, `asset_name`, `amount`, `contract_address`, `call_value`, `token_id`, etc.). This mirrors the Vault.sol bug: `allowed(_from)` only checks `msg.sender == _from || userApprovedContracts[_from][msg.sender]`, i.e. an all-or-nothing grant per spender, with no scoping to the specific asset/pair the depositor intended to interact with.

### Impact Explanation
Any account owner who grants an "Active" permission to a third-party key/service (a common pattern for exchange hot-wallet co-signers, automation bots, or dApp session keys) for a given `ContractType` bit (e.g. `TriggerSmartContractContract` or `TransferAssetContract`) is implicitly trusting that key with **unrestricted** use of that capability across the entire account — any receiver, any TRC10 asset, any TRX amount, any smart contract address. If the delegate key is compromised, or the delegate itself is malicious (the "Eve's pool" analog), it can transfer the owner's entire balance of any asset to an attacker-controlled address, or trigger an attacker-controlled smart contract with the owner's TRX/TRC10 endowment, without further owner authorization. This is a broad standing authorization risk resulting in unauthorized asset movement, directly analogous to "malicious pairs can steal approved or deposited tokens."

### Likelihood Explanation
This is reachable via ordinary account/permission setup on-chain (`AccountPermissionUpdateContract`) and normal transaction broadcast with `permission_id` set — no privileged/administrative access is required beyond the account owner's own choice to delegate. Any dApp, exchange, or service instructing users to grant "Active" permissions scoped only by contract type (the officially supported multisig mechanism) exposes users to this risk if the delegate key is later compromised or acts maliciously, matching the report's "malicious LendingPair pool" scenario where broad approval is abused by an unrelated party.

### Recommendation
- Short term: Document clearly (in wallet/dApp integration guidance) that `Permission.operations` bits only scope by `ContractType`, not by counterparty, asset, or amount, and warn integrators/users against granting Active permissions to third-party keys for high-impact contract types (`TransferContract`, `TransferAssetContract`, `TriggerSmartContract`) without additional off-chain controls.
- Long term: Consider extending the permission model (or providing an additional, opt-in restriction layer) to allow scoping delegated authority by counterparty address, asset id, or spending limits, closing the gap between "operation type" authorization and the fine-grained intent users typically have when delegating signing power.

### Proof of Concept
1. Alice (owner) issues `AccountPermissionUpdateContract` adding Bob's key to her "Active" permission with `operations` bit set only for `TransferAssetContract` (she intends Bob's automation bot to only send her a specific TRC10 token to a specific partner) — validated by `AccountPermissionUpdateActuator.checkPermission` [5](#0-4) .
2. Bob's key is compromised (or Bob is malicious). Bob crafts a `TransferAssetContract` transaction with `permission_id` set to Alice's active-permission id, `owner_address = Alice`, `to_address = attacker`, `asset_name = <any TRC10 Alice holds>`, `amount = <Alice's full balance>`.
3. During signature validation, only `checkPermissionOperations` is evaluated — it checks solely that bit `TransferAssetContract.getTypeValue()` is set in Alice's permission `operations`; it never checks `to_address` or `amount` [4](#0-3) .
4. Signature threshold met with Bob's key weight, transaction broadcasts and executes via `TransferAssetActuator`, draining Alice's entire asset balance to the attacker's address [6](#0-5) .

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
