### Title
Stale per-block index cache in `market.clar` can be read after a vault's real index has already advanced within the same transaction - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`market.clar` caches each vault's borrow/liquidity index in `index-cache`, keyed by `{ timestamp: stacks-block-time, aid }`, so that repeated reads within the same block reuse one accrual result instead of re-calling the vault [1](#0-0) . The cache is populated only on the first miss for a given `(timestamp, aid)` pair and returned verbatim on every subsequent lookup in the same block, with no mechanism to detect that the vault's actual `index`/`lindex` moved after the cache entry was written.

### Finding Description
`accrue-and-cache` returns the cached `{index, lindex}` on a hit without re-checking the vault's current state [1](#0-0) . Multi-step market entry points call this helper indirectly through `accrue-user-debts` / `accrue-user-collateral` (for health checks and ztoken price resolution) and separately route directly to a vault's own public functions such as `deposit`, `redeem`, `system-borrow`, and `system-repay` via `vault-deposit`, `vault-redeem`, `vault-system-borrow`, `vault-system-repay` [2](#0-1) . Those vault-side functions internally call `accrue()` and mutate the vault's own `index`/`lindex`/`principal-scaled`/`total-borrowed` state directly (as seen in the vault contracts, e.g. the `system-borrow`/`system-repay` update pattern) without going through `market.clar`'s `index-cache` at all.

Consequently, if within a single transaction the market first resolves and caches an asset's index for `stacks-block-time = T` (e.g., during a pre-operation health check or price resolution step), and then later in the same transaction performs an operation that calls the vault directly and advances its real index (e.g., a `system-borrow`/`system-repay`/`deposit`/`redeem` step for that same asset), any further call to `accrue-and-cache` for that `(T, aid)` key still returns the now-stale cached value instead of the vault's updated index. This is a cached-value-not-invalidated-when-its-source-moves pattern entirely internal to a single transaction/block, matching the documented but incompletely enforced invariant that "Cache is automatically invalidated each block" — the invalidation is per-block only, not per-mutation, so intra-block staleness after a direct vault mutation is not addressed by the design as described.

### Impact Explanation
If a multi-step market operation (e.g., a composite deposit/borrow, or a borrow that touches multiple collateral/debt legs including a ztoken whose underlying vault is also being borrowed/repaid against in the same call) reads a stale liquidity/borrow index for a later health check, the collateral value or debt value used in that check can diverge from the vault's true state. Because the health check is what gates borrowing amounts and liquidation eligibility, a favorable stale value could let a position pass a health check it should not have passed, enabling excess borrowing against overstated collateral or evasion of a liquidation. This directly threatens protocol solvency, which is a Critical-impact class in scope.

### Likelihood Explanation
Exploitability depends on whether any real market entry point actually sequences "cache index for asset A" → "directly mutate vault A's index via a vault call" → "reuse cached index for asset A" within one call, which I was not able to fully confirm before running out of tool iterations — I could not inspect the full bodies of `borrow`, `repay`, or any combined deposit-and-borrow function in `v0-4-market.clar` to verify this exact ordering occurs in a single public entry point. The documentation states interest accrual always happens "before" operations and that this "prevents stale data exploits," which suggests the protocol intends single-fetch-per-block safety, but the cache design as shown only invalidates by block timestamp, not by state mutation, so the underlying mechanism for staleness exists at the code level even if I could not conclusively trace a full public function that triggers it.

### Recommendation
- Short term: Invalidate (or overwrite) the specific `index-cache` entry for an asset immediately after any direct vault call that can change that vault's index (`deposit`, `redeem`, `system-borrow`, `system-repay`, `socialize-debt`), rather than relying solely on the per-block timestamp key.
- Long term: Route all vault state-mutating calls through `accrue-and-cache` (or an equivalent single accrual path) so there is exactly one source of truth for a vault's index per block, eliminating the possibility of a direct vault mutation being invisible to cached readers within the same transaction.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
