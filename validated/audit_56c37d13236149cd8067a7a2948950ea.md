### Title
Leader key reuse across multiple block-commits due to missing consumption check in `check_common` - (File: `stackslib/src/chainstate/burn/operations/leader_block_commit.rs`)

### Summary
`LeaderBlockCommitOp::check_common` only verifies that a leader key *exists* at the referenced `(key_block_ptr, key_vtxindex)` location via `get_leader_key_at`, but never calls `SortitionHandleTx::is_leader_key_consumed` to verify the key has not already backed a prior winning commit. The `LeaderKeyRegisterOp::check` in `leader_key_register.rs` only rejects duplicate *registration* of the same public key, not duplicate *consumption*. This allows one VRF leader key to be referenced and consumed by two distinct block-commits, breaking the "one key -> one commit" invariant.

### Finding Description
The invariant under test: `leader_key.consumed_by == {single LeaderBlockCommitOp}`. In practice this is expected to be enforced either at commit-validation time or at winner-bookkeeping time.

Tracing the code:
- `LeaderKeyRegisterOp::check` (`stackslib/src/chainstate/burn/operations/leader_key_register.rs:213-234`) only calls `tx.has_VRF_public_key(&self.public_key)` to reject re-registration of the same public key. It does nothing about consumption. [1](#0-0) 
- `LeaderBlockCommitOp::check_common` (`stackslib/src/chainstate/burn/operations/leader_block_commit.rs:1210-1233`) requires that a leader key exist at `(leader_key_block_height, self.key_vtxindex)` via `tx.get_leader_key_at(...)`, but it never checks whether that key is already consumed. [2](#0-1) 
- `SortitionDB`/`SortitionHandleTx::is_leader_key_consumed` (`stackslib/src/chainstate/burn/db/sortdb.rs:1434-1467`) exists specifically to check the `"vrf_key_status"` MARF key for whether a key was already spent — but grepping the whole repo shows this function is only referenced inside `sortdb.rs` itself (its definition and its own unit tests); it has no caller from `leader_block_commit.rs` or `burnchain.rs` sortition-processing code. [3](#0-2) 
- `get_consumed_leader_keys` (`stackslib/src/chainstate/burn/db/sortdb.rs:1321-1348`), which is used post-hoc to compute which keys were consumed by the accepted winning commits of a sortition, simply does a positional lookup (`get_leader_key_at`) for every accepted candidate and panics if missing — it does not detect or reject the case where the same key location is referenced by two different winning commits at two different burn-block heights across the commitment window. [4](#0-3) 

Exploit flow: an attacker registers a single leader key `K` at height `H`. In a later burn block `H1` they submit `commit_1` with `key_block_ptr=H, key_vtxindex=V`; if `commit_1` wins that sortition (e.g. no competing commit that round — feasible for a lone miner slot during any period with sparse commit activity, not requiring majority stake), the key is recorded as consumed only via the `vrf_key_status` bookkeeping, which is never actually enforced against future commits (no caller checks it). At burn block `H2 > H1`, the attacker submits `commit_2` again with `key_block_ptr=H, key_vtxindex=V`. `check_common` re-validates only that a key exists at that location — which it still does, since the check is purely a positional existence lookup indexed by height/vtxindex rather than a per-key spent/unspent state check — and accepts `commit_2` if it wins its own sortition. The same VRF key `K` now backs two accepted commits at two different tenures.

### Impact Explanation
Reusing the same VRF leader key across two separately-won sortitions means the VRF seed derivation and leader-key material used to compute sortition winners is not uniquely tied to one commit as consensus assumes. This is a minority-triggerable sortition/VRF divergence: two accepted commits, produced independently and potentially processed differently by two honest nodes evaluating fork-specific state (since `get_leader_key_at`/consumption bookkeeping is fork-relative), can cause disagreement about which commit is the legitimate consumer of key `K`, leading to inconsistent sortition-winner computation between nodes. This matches the "High - minority-triggerable sortition/VRF/static-validation divergence" impact category defined in scope.

### Likelihood Explanation
The attacker needs only: (1) enough BTC to register one leader key and place two block-commits referencing that key at two different heights, and (2) for each of those two commits to individually win its own sortition round (not simultaneously — sequentially, so no majority stake is required, only being the winning commit in each of two separate, possibly low-competition rounds). This is well within a minority/single-miner-slot attacker's capability and is repeatable. No privileged role, no majority signers, no 51% hash power is required — only the ability to broadcast burn-chain operations with the attacker's own BTC, matching the allowed threat model.

### Recommendation
Add an explicit consumption check to `LeaderBlockCommitOp::check_common` (or wherever winner acceptance happens) that calls `SortitionHandleTx::is_leader_key_consumed` (already implemented in `sortdb.rs`) against the resolved `LeaderKeyRegisterOp` before accepting a block-commit, rejecting the commit with a new `op_error::LeaderKeyAlreadyConsumed` if the key was already consumed on that fork. Ensure this check runs against the correct fork-relative chain tip so that reuse across siblings within the same accepted canonical history is caught, and ensure `get_consumed_leader_keys` fails loudly (rather than silently accepting) if two accepted commits in the commitment window resolve to the same leader key.

### Proof of Concept
Rust integration test plan (extending the existing test harness in `leader_block_commit.rs`/`sortdb.rs`):
1. Register `leader_key_K` at height `H`.
2. Advance the sortition DB with `commit_1` at height `H1` referencing `(H, V)`, and make it the sole/winning candidate for that sortition (assert `SortitionDB::is_leader_key_consumed(K) == true` afterward on that fork's tip).
3. Advance to height `H2 > H1`, submit `commit_2` again referencing `(H, V)` as the sole/winning candidate.
4. Call `commit_2.check_common(...)` (or the full `check()` path) and assert it currently returns `Ok(())` — i.e., the equality `leader_key.consumed_by == {commit_1}` is violated because `commit_2` is also accepted, so `leader_key.consumed_by` effectively becomes `{commit_1, commit_2}`.
5. Assert failure of the invariant: query `get_consumed_leader_keys` across the fork's history and show both `commit_1` and `commit_2` resolve to the same `LeaderKeyRegisterOp`, demonstrating the one-key/one-commit invariant is broken pre-fix, and add the recommended `is_leader_key_consumed` check to show `commit_2.check_common(...)` returns `Err(op_error::LeaderKeyAlreadyConsumed)` post-fix.

    pub fn get_consumed_leader_keys(
        &mut self,
        parent_tip: &BlockSnapshot,
        block_candidates: &[LeaderBlockCommitOp],
    ) -> Result<Vec<LeaderKeyRegisterOp>, db_error> {
        // get the set of VRF keys consumed by these commits
        let mut leader_keys = vec![];
        for candidate in block_candidates.iter() {
            let leader_key_block_height = candidate.key_block_ptr as u64;
            let leader_key_vtxindex = candidate.key_vtxindex as u32;
            let leader_key = self
                .get_leader_key_at(
                    leader_key_block_height,
                    leader_key_vtxindex,
                    &parent_tip.sortition_id,
                )?
                .unwrap_or_else(|| {
                    panic!(
                        "FATAL: no leader key for accepted block commit {} (at {},{})",
                        &candidate.txid, leader_key_block_height, leader_key_vtxindex
                    )
                });

            leader_keys.push(leader_key);
        }

        Ok(leader_keys)
    }

    /// Determine whether or not a leader key has been consumed by a subsequent block commitment in
    /// this fork's history.
    /// Will return false if the leader key does not exist.
    pub fn is_leader_key_consumed(
        &mut self,
        leader_key: &LeaderKeyRegisterOp,
    ) -> Result<bool, db_error> {
        if leader_key.block_height >= BLOCK_HEIGHT_MAX {
            return Err(db_error::BlockHeightOutOfRange);
        }
        let chain_tip = self.context.chain_tip.clone();

        let key_status =
            match self.get_indexed(&chain_tip, &db_keys::vrf_key_status(&leader_key.public_key))? {
                Some(status_str) => {
                    if status_str == "1" {
                        // key is still available
                        false
                    } else if status_str == "0" {
                        // key is consumed
                        true
                    } else {
                        panic!("Invalid key status string {}", status_str);
                    }
                }
                None => {
                    // never before seen
                    false
                }
            };

        Ok(key_status)
    }
