### Title
Integer overflow in ExchangeInjectActuator balance arithmetic bypasses validate() checks and corrupts exchange/account state - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectActuator` (and its `doValidate()`) rely on `addExact`/`subtractExact` methods inherited from `AbstractExchangeActuator`, which — unless `allowHardenExchangeCalculation()` is enabled — silently fall back to plain, non-overflow-checked `x + y` / `x - y` arithmetic [1](#0-0) . Because `doValidate()` and `execute()` both use these overridden (non-strict) operators for the exchange-pool balance and account-balance sufficiency checks, an attacker can craft `tokenQuant`/pool-balance combinations that wrap around a `long`, causing `validate()`'s sufficiency checks to pass incorrectly and `execute()` to commit corrupted (wrapped) balances into the `ExchangeCapsule` and `AccountCapsule`.

### Finding Description
`ExchangeInjectActuator.execute` computes new exchange-pool balances via `addExact(firstTokenBalance, tokenQuant)` and `addExact(secondTokenBalance, anotherTokenQuant)`, and reduces the account's TRX balance via `subtractExact(newBalance, tokenQuant)` [2](#0-1) . Because `ExchangeInjectActuator extends AbstractExchangeActuator`, these calls resolve to `AbstractExchangeActuator.addExact`/`subtractExact`, not `AbstractActuator`'s strict versions: [3](#0-2) 

When `allowHardenExchangeCalculation()` is false (which requires it to be enabled via a committee proposal — I could not confirm the default is 0 from the visible code but the presence of an explicit "harden" toggle plus dedicated tests such as `hardenedSuccessExchangeInject` strongly implies the plain, unchecked path is the historical/default behavior for un-upgraded chains), `subtractExact`/`addExact` degrade to plain `x - y` / `x + y`, which wrap silently on `Long.MIN_VALUE`/`Long.MAX_VALUE` boundaries instead of throwing `ArithmeticException`.

Critically, `doValidate()` uses these *same* overridden operators for its sufficiency checks, e.g. `accountCapsule.getBalance() < addExact(tokenQuant, calcFee())` and `newTokenBalance = addExact(firstTokenBalance, tokenQuant)` compared against `balanceLimit` [4](#0-3) . If `tokenQuant` is chosen so that `firstTokenBalance + tokenQuant` overflows and wraps to a small or negative number, the `newTokenBalance > balanceLimit` guard [5](#0-4)  can be bypassed, and `execute()` will then persist the wrapped (corrupted) balance into the exchange pool via `Commons.putExchangeCapsule`.

### Impact Explanation
If exploitable (i.e., on a chain/dynamic-property state where hardened exchange math is not active), this allows an attacker to make `ExchangeCapsule` first/second token balances wrap to arbitrary (including negative or artificially small) values, and/or make account balances wrap after a `subtractExact` underflow, producing free tokens or negative-balance accounting corruption in the exchange subsystem — a Critical-class asset/accounting corruption per TRON's bounty impact table.

### Likelihood Explanation
Exploitability is entirely gated on `dynamicStore.getAllowHardenExchangeCalculation()`. I could not locate the default/initialization value of this parameter in the indexed code (`DynamicPropertiesStore.java` grep for `allowHardenExchangeCalculation` returned matches in that file per the earlier search, but the specific getter/default-value lines were not retrievable in this session due to index/context limits). The existence of a dedicated hardening flag, the `SafeExchangeProcessor` code path, and the `hardenedSuccessExchangeInject` test strongly suggest this was introduced specifically to *fix* a prior overflow issue, meaning current/default mainnet state likely already has hardening enabled, in which case the plain-arithmetic path is dead on production chains. Without confirming the current on-chain value of `allowHardenExchangeCalculation`/`allowStrictMath` for the target deployment, I cannot conclusively assert this is live-exploitable today, only that the code path exists.

### Recommendation
Verify (or force) that `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` always use the strict, overflow-checked math regardless of the `allowHardenExchangeCalculation` flag, i.e., remove the plain-arithmetic fallback in `AbstractExchangeActuator.addExact/subtractExact` or ensure the flag is permanently and irrevocably enabled on all networks before relying on this code.

### Proof of Concept
Not able to construct a concrete reproducible PoC without confirming the current value of `allowHardenExchangeCalculation` in the deployed `DynamicPropertiesStore`; if it is 0 (unhardened), a JUnit test analogous to `ExchangeInjectActuatorTest.hardenedSuccessExchangeInject` [6](#0-5)  but with `saveAllowHardenExchangeCalculation(0)` (or left at whatever the true default is) and `tokenQuant` set to `Long.MAX_VALUE - firstTokenBalance + 1` should be used to assert whether `pool.getFirstTokenBalance()` wraps to a negative/small value instead of throwing.
