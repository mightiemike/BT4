### Title
Unbounded-recursion stack exhaustion in deprecated gateway JSON fallback parsing - (File: `crates/apollo_http_server/src/http_server.rs`)

### Summary
The deprecated `/gateway/add_transaction` HTTP endpoint's error-handling fallback path parses the raw, attacker-controlled request body into an untyped `serde_json::Value` with no depth limiting. `serde_json`'s `Value` deserializer is a classic recursive-descent parser (structurally analogous to the recursive `_yr_re_emit` regex-emission bug in CVE-2017-9304): parsing deeply nested JSON arrays/objects recurses once per nesting level, with no depth cap, and a native stack overflow in Rust aborts the process rather than raising a catchable error.

### Finding Description
`add_tx` in [1](#0-0)  first tries to parse the raw body `tx: String` into the strongly-typed `DeprecatedGatewayTransactionV3` via `serde_json::from_str`. Any input that fails this typed parse (e.g., malformed/garbage JSON, which any unauthenticated caller can trivially produce) falls into the error branch, which calls `check_supported_resource_bounds_and_increment_metrics(&tx)`.

That helper, [2](#0-1) , does:
```rust
if let Ok(tx_json_value) = serde_json::from_str(tx) {
```
Here the target type is inferred as `serde_json::Value` (untyped/generic JSON), which — unlike deserializing into a fixed schema struct — recurses into every nested array/object level of the input text to build the `Value` tree. There is no recursion-depth limit configured (no `serde_stacker`, no custom `Deserializer` depth guard), and Rust panics from genuine stack overflow are not catchable — the OS delivers SIGSEGV and the process/thread aborts.

The only protections in front of this code path are body-size limits (`RequestBodyLimitLayer`, `DefaultBodyLimit`) applied at [3](#0-2) . These bound the *number of bytes*, not the *nesting depth*. A payload consisting almost entirely of nested single-character array delimiters (e.g. `[[[[[...]]]]]`) achieves an extremely deep parse-recursion depth using very little space (2 bytes per nesting level), so even a modest body-size cap (e.g. a few MB) allows nesting depth in the hundreds of thousands to millions — far more than enough to exhaust a typical thread stack (default request-handling stacks are a few MB, well below what's needed to safely process this many recursive frames).

This is directly analogous to CVE-2017-9304: an attacker-supplied, deeply nested/recursive structure drives an unbounded recursive parser/emitter routine to consume the call stack until it overflows, causing the process to crash (denial of service) rather than gracefully erroring.

### Impact Explanation
A stack-overflow abort of the HTTP server process handling `/gateway/add_transaction` crashes the sequencer's transaction-ingestion component. Since this endpoint is reachable by any unauthenticated remote sender submitting a single HTTP request (no valid signature or fee required — the crash triggers before/during transaction validation, in the *error fallback* path used precisely when normal deserialization fails), a single malicious request can repeatedly take down the node's ability to accept new transactions, i.e., "a network unable to confirm new transactions" if this is widely deployed across sequencer nodes reachable at this endpoint.

### Likelihood Explanation
High likelihood of reachability: any external, unprivileged client can POST to `/gateway/add_transaction` with a crafted string body. No authentication, fees, signatures, or prior state is required — the vulnerable code executes specifically on malformed input (the `Err` branch of the initial typed parse), which is trivial to trigger deliberately with a deeply nested bracket payload while staying under the body-size limit.

### Recommendation
- Do not fall back to unbounded, untyped `serde_json::Value` parsing of untrusted request bodies. If a diagnostic/metrics-only parse is needed, cap recursion depth explicitly (e.g., via `serde_stacker::maybe_grow`, or a custom `serde_json::Deserializer` wrapped with a depth-limiting layer, or reject inputs whose bracket/brace nesting exceeds a small fixed bound before invoking `serde_json`).
- Alternatively, remove or gate the `check_supported_resource_bounds_and_increment_metrics` fallback so it never performs a full generic JSON parse of attacker-controlled data outside the already-limited typed schema, or run this fallback parse on a stack-guarded worker (as already done for Cairo Native recursion in `crates/blockifier/src/blockifier/transaction_executor.rs`) so a stack overflow can be safely contained rather than crashing the whole process.
- Add a pre-check that rejects inputs whose JSON nesting depth exceeds a small hard-coded maximum (e.g. 32) before any recursive JSON parsing occurs, mirroring the fix approach taken for CVE-2017-9304 in YARA (bounding recursion depth in `_yr_re_emit`).

### Proof of Concept
1. Send `POST /gateway/add_transaction` with `Content-Type: text/plain` (or as accepted `String` extractor) and a body such as:
```
[[[[[[[[[[[[[[[[[[[[ ... (repeated N times, e.g. N = 2,000,000) ... ]]]]]]]]]]]]]]]]]]]]
```
sized to remain under `max_request_body_size` (bytes = `2*N`).
2. The initial `serde_json::from_str::<DeprecatedGatewayTransactionV3>(&tx)` fails (type mismatch: expects an object, gets a deeply nested array).
3. `validate_supported_tx_version_str` fails to find `"version":"` and returns `Err`, but note the code path continues to call `check_supported_resource_bounds_and_increment_metrics(&tx)` regardless of the version-validation outcome flow order in the source (see lines 201–207): the fallback JSON `Value` parse still executes on the same string.
4. `serde_json::from_str(tx)` in `check_supported_resource_bounds_and_increment_metrics` recursively parses ~N nested array levels, exhausting the request-handling thread's stack and crashing the process.

Note: I could not execute this PoC in a live environment from this analysis; the recursion-depth-vs-stack-size margin (exact default stack size for the axum/tokio task thread, and the exact configured `max_request_body_size` default) should be confirmed by a Devin session with terminal access to validate the precise N needed to trigger the crash in this build.
