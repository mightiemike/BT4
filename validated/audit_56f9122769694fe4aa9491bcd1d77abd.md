### Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay/verify accept a diverged state root - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single integrity gate used by the chunk executor's `verify_execution` (state-sync/chunk-restore path) and by `db-tool`'s `replay_on_archive`/`cli`'s replay commands to confirm that a locally re-executed transaction matches the trusted, already-accumulator-authenticated `TransactionInfo`. It checks status, gas, write-set hash, and event root hash, but explicitly **does not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that authenticate the resulting state-tree root(s). The gap is acknowledged in-code by a `TODO(trading-native)` comment.

### Finding Description
`ensure_match_transaction_info` in `types/src/transaction/mod.rs` compares the freshly produced `TransactionOutput` against the backup/authenticated `TransactionInfo`: [1](#0-0) 

It checks status, gas, write-set hash (`state_change_hash`) and event root hash, but the function returns `Ok(())` immediately afterward with a comment stating the checkpoint hashes are intentionally skipped: [2](#0-1) 

This function is the sole correctness gate in two security-relevant call sites:
1. `execution/executor/src/chunk_executor/mod.rs::verify_execution`, which re-executes a chunk with the real VM against locally reconstructed state and is meant to catch execution/state divergence during restore/replay before the chunk is committed: [3](#0-2) 
2. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, the tool explicitly designed to detect any divergence between mainnet history and re-execution: [4](#0-3) 

Since `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are never compared, any bug that causes the locally rebuilt Sparse/Jellyfish Merkle root (main state, hot state, or the new native-position state introduced for `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) to diverge from the canonical, already-accumulator-proven value will not be flagged as an error by either the chunk-executor's verification path or the dedicated replay-verify tool.

### Impact Explanation
This breaks the "proof and storage pivot" requirement that authenticated state/checkpoint roots be validated on the replay/restore path. Concretely:
- A node performing chunk-restore/state-sync in `VerifyExecutionMode` will accept and commit a chunk whose actually-computed state-checkpoint root differs from the canonical one, because the one comparison that would have caught it is skipped.
- `replay_on_archive`, whose entire purpose is to detect exactly this class of divergence (hard-fork-only nondeterminism, JMT/SMT computation bugs, native-position state root bugs), will silently report success even when the position/state root diverges, per the code's own comment.
- This directly matches the required impact "Wrong accumulator root ... or state proof accepted as valid" / "Hard-fork-only divergence during commit, replay, restore, or proof verification," since the divergence-detection mechanism for state roots is a no-op for these three hash fields.

### Likelihood Explanation
The write-set/event/gas/status fields are still checked, so ordinary execution bugs producing wrong values would still be caught. The residual risk is specifically about the *tree-root computation* layer (state SMT, hot-state SMT, and the newer native-position JMT) diverging from the canonical result while the underlying write set matches — e.g., a bug in incremental Merkle update logic, hot-state promotion/eviction bookkeeping, or the new native-position checkpoint computation. Given this is a newly introduced feature area (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `position_state_checkpoint_hash`) still gated and explicitly called out as unvalidated by the code author, likelihood of an undetected bug reaching this exact comparator is non-trivial but requires a pre-existing root-computation defect to actually manifest — this is a missing safety-net rather than an active corruption itself.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash()`, `hot_state_checkpoint_hash()` (when present), and `position_state_checkpoint_hash()` (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) against the locally computed roots before returning `Ok(())`, and only ship/enable `COMPUTE_TRADING_NATIVE_STATE_ROOTS` after this validation is restored, as the comment itself recommends.

### Proof of Concept
Not applicable as a standalone exploit — this is a missing-check finding. Demonstration path: run `db-tool replay-on-archive` (or chunk-executor restore in `VerifyExecutionMode`) against a chunk where the write set matches the canonical output but the locally recomputed state-checkpoint hash (or, once enabled, `position_state_checkpoint_hash`) differs (e.g., by injecting a bug in the SMT/JMT update code in a test build); `ensure_match_transaction_info` at [5](#0-4)  will return `Ok(())` and the tool/executor will report a clean replay despite the state-root divergence.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
