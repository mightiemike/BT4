Based on my investigation, I found a genuine analog: the sequencer maintains two independently-configured "capacity/threshold" values — `BouncerWeights.receipt_l2_gas` (a per-node static config value enforced during block building) and `VersionedConstants.max_block_size` (the network-wide constant used for EIP-1559 gas-price calculation and, by comment, meant to define the actual block gas ceiling) — that must be kept manually in sync but have no code-level enforcement or propagation mechanism tying them together, mirroring the disclosed `required_validators` desync bug class.

### Title
Divergent, Manually-Synced Block Capacity Constants Between Bouncer and VersionedConstants Can Desync Committed Block Gas Limits - (File: crates/blockifier/src/bouncer.rs)

### Summary
`BouncerWeights.receipt_l2_gas` (enforced per-transaction/per-block by the `Bouncer` during block building) and `VersionedConstants.max_block_size` (used by the fee-market/EIP-1559 logic to determine the gas ceiling for price calculations) represent the same conceptual value — "the maximum L2 gas allowed in a block" — but are two entirely separate configuration fields with no code path that keeps them consistent, exactly like `BaseSettlement.required_validators` and `SettlementSignatureVerifier.required_validators` in the referenced report.

### Finding Description
The `receipt_l2_gas` field on `BouncerWeights` is explicitly documented as needing to match `max_block_size`: [1](#0-0) . The reciprocal comment lives on `VersionedConstants.max_block_size`: [2](#0-1) . These are set independently: `receipt_l2_gas` defaults via `BouncerWeights::default()` [3](#0-2)  or via deployment/config JSON such as `batcher_config.static_config.block_builder_config.bouncer_config.block_max_capacity.receipt_l2_gas` [4](#0-3) , while `max_block_size` is bumped independently through versioned-constants JSON files per Starknet version, e.g. from `5000000000` (0.14.0) to `5800000000` (0.14.1/0.14.2) [5](#0-4) [6](#0-5) . There is no assertion, validation, or automated propagation anywhere in the codebase enforcing `bouncer_config.block_max_capacity.receipt_l2_gas == VersionedConstants::latest_constants().max_block_size` — the linkage exists purely as a code comment, just like the missing `set_required_validators_num` call in the original report.

`receipt_l2_gas` is the value actually enforced per transaction as a hard block-building limit in `Bouncer::try_update` via `bouncer_config.has_room(...)` [7](#0-6) , reachable directly by any submitted transaction consuming gas — each transaction's `bouncer_weights.receipt_l2_gas` (computed in `get_tx_weights`) is checked against this configured capacity [8](#0-7) . Separately, `max_block_size` is used as the ceiling reference for the EIP-1559 gas price clamp computed once per committed block by the consensus orchestrator's fee-market logic [9](#0-8) .

### Impact Explanation
If an operator (or a future release) updates `max_block_size` in the versioned constants without correspondingly updating the batcher's `bouncer_config.block_max_capacity.receipt_l2_gas` (or vice versa), the two subsystems diverge on the “true” block gas ceiling:
- If `receipt_l2_gas` (bouncer capacity) is lower than `max_block_size`, the sequencer will close blocks before the network-intended gas target is reached, systematically under-filling blocks relative to the EIP-1559 fee-market's target assumption, skewing gas price computation away from actual network demand.
- If `receipt_l2_gas` is higher than `max_block_size`, blocks can be built exceeding the gas amount the fee-market model assumes as the ceiling, producing miscalibrated `next_l2_gas_price` values relative to the documented invariant.

Because this constant desync affects every node identically only if all nodes apply the same (correct or incorrect) config; however, if nodes are misconfigured non-uniformly (e.g., a rolling upgrade where only some nodes update `receipt_l2_gas` while `max_block_size` changes network-wide), different nodes accept differently-sized blocks — a path to honest-node divergence on block validity, satisfying the required medium+ impact bar. This mirrors the disputed-but-accepted medium severity of the original finding: a "config not propagated" bug affecting system functionality without a well-defined single-actor exploit.

### Likelihood Explanation
Likelihood is moderate: this is not exploitable by a random attacker transaction directly, but is triggered purely through routine protocol operation — every version upgrade that changes `max_block_size` (which has already happened three times across V0_14_0→V0_14_3 per the diff-regression files) requires a manual, unenforced update to a separate config field in a different crate (`apollo_batcher_config`/deployment JSON) maintained by different teams/processes. The lack of any runtime cross-check means the desync is silent and would only surface as a subtle fee-market miscalibration or block-capacity divergence in production, exactly analogous to how the audited `required_validators` bug went unnoticed because no assertion tied the two duplicate fields together.

### Recommendation
Add a startup/config-validation assertion (e.g., in the batcher or node config validation path) that checks `bouncer_config.block_max_capacity.receipt_l2_gas == VersionedConstants::latest_constants().max_block_size`, or better, derive `receipt_l2_gas` directly from `VersionedConstants::latest_constants().max_block_size` at config-load time instead of maintaining it as an independently configured, manually-synced field.

### Proof of Concept
1. Take the current versioned constants for a given `StarknetVersion` (e.g., V0_14_3), where `max_block_size = 5800000000` [10](#0-9) .
2. Deploy a batcher config with `bouncer_config.block_max_capacity.receipt_l2_gas` left at an older/incorrect value (e.g., `5000000000` from V0_14_0), as would happen if only the versioned-constants file was bumped during a protocol upgrade without touching the deployment config in `crates/apollo_node/resources/config_schema.json:112-116`.
3. Observe that `Bouncer::try_update` enforces the stale `receipt_l2_gas` capacity [11](#0-10) , closing blocks earlier than the network's intended `max_block_size`, while the fee-market clamp logic in `apollo_consensus_orchestrator` continues to reference the new `max_block_size` as the ceiling — producing inconsistent gas-price/block-capacity behavior across the two subsystems, with no code-level check to detect or prevent the mismatch.
