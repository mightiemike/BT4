### Title
Paused `accrue()` silently returns stale index instead of reverting, causing borrowers/depositors to interact using unaccrued interest state - ([File: local-testing/contracts/vault/vault-stx.clar])

### Summary
Every vault contract (`vault-stx.clar`, `vault-sbtc.clar`, `vault-ststx.clar`, `vault-ststxbtc.clar`, `vault-usdc.clar`, `vault-usdh.clar`, and their mainnet `v0-vault-*` counterparts) implements `accrue()` such that when the `accrue` pause flag is set, it silently returns the **old** cached `index`/`lindex` pair — `(ok { index: idx, lindex: lidx })` — instead of reverting, and critically does **not** update `last-update`. [1](#0-0) 

### Finding Description
`accrue()` is called at the top of every state-changing vault entry point (`deposit`, `redeem`, `system-borrow`, `flashloan`, `transfer`, etc.) via `(u (try! (accrue)))`. [2](#0-1) [3](#0-2) 

When the `accrue` bit of `pause-states` is set, the function takes the pass-through branch and returns success with the pre-pause `idx`/`lidx`, skipping the branch that would otherwise compute `next-index`, `next-liquidity-index`, mint treasury reserve shares, and — importantly — update `(var-set last-update stacks-block-time)`: [4](#0-3) 

Because `try!` on this call succeeds (it is `(ok ...)`, not an `(err ...)`), all downstream public functions (`system-borrow`, `deposit`, `redeem`) continue executing normally rather than reverting, using the stale `index`/`lindex` and consuming/updating `total-borrowed`, `principal-scaled`, and `assets` as if the pause did not exist: [5](#0-4) 

This is the "pause that passes through instead of reverting" analog: a health/consistency mechanism (`accrue`, which is supposed to keep `index`/`lindex` synchronized with elapsed `stacks-block-time`) is turned into a no-op that reports success while state (borrow, deposit, redeem) is mutated using data that the pause was meant to freeze. Because `last-update` is never advanced while paused, once unpaused the very next `accrue()` call computes `next-index`/`next-liquidity-index` over the *entire* elapsed real-world time (from the last real update, spanning across the paused window) in a single step, applying the full accrued interest at once. Any deposits, borrows, or redemptions that occurred during the pause window were executed against the frozen `index`, so their scaled-principal/share conversions do not reflect the interest that continues to notionally accrue for the protocol's outstanding debt — meaning depositors who entered/exited or borrowers who borrowed/repaid during the pause window get share/debt conversions computed on stale exchange rates while other users' positions (untouched during the pause) get the correct catch-up rate applied retroactively at the moment of unpause.

### Impact Explanation
Interest/exchange-rate mutations (deposit share minting via `convert-to-shares-preview`, redeem asset conversion via `convert-to-assets-preview`, and debt scaling via `mul-div-up amount INDEX-PRECISION idx`) are all computed off the frozen `idx`/`lidx` while `accrue` is paused. Because operators can pause `accrue` independently of `deposit`/`redeem`/`borrow` (these have separate pause bits in `pause-states`), depositors and borrowers can transact at a stale exchange rate during the pause window, and the interest owed for that window is applied in one lump catch-up the moment `accrue` is unpaused — landing on whichever positions exist at that instant. This misallocates unclaimed yield (interest) between users who transacted during the pause and users who did not, which falls under "theft of unclaimed yield" / "temporary freezing of funds" for users whose expected accrual is diverted.

### Likelihood Explanation
This requires only that the DAO/admin-controlled `accrue` pause bit be set while `deposit`/`borrow`/`redeem` remain unpaused — a state the pause-state bitmap explicitly allows since each operation (`accrue`, `deposit`, `redeem`, `borrow`, `flashloan`) has an independent pause flag rather than `accrue` pause implying pause of all interest-sensitive operations. No malicious collusion or DAO compromise is needed beyond the intended, legitimate use of the existing per-operation pause granularity; a single-transaction interaction with the vault during that window is sufficient to realize the effect.

### Recommendation
Either (a) make `deposit`, `redeem`, and `system-borrow` `asserts!` that `accrue` is not paused before proceeding (so pausing `accrue` blocks all interest-sensitive operations instead of silently allowing them against a stale rate), or (b) remove the pass-through branch and have `accrue()` revert when paused, or (c) ensure `last-update` still advances during the paused period so that no interest is silently deferred/misallocated once unpaused, and reconcile which principals were active during the freeze window.

### Proof of Concept
1. DAO/operator sets the `accrue` pause bit on `vault-stx` (or any vault) while leaving `deposit`/`borrow`/`redeem` unpaused. [1](#0-0) 
2. Time passes (multiple blocks), during which the true `next-index`/`next-liquidity-index` (based on `stacks-block-time`) would have increased.
3. User A calls `deposit`, which internally calls `(try! (accrue))` — this returns `(ok {index: idx, lindex: lidx})` with the **stale** pre-pause values, so `convert-to-shares-preview` mints shares at the old, more-favorable exchange rate rather than the true rate that should apply given elapsed time. [6](#0-5) 
4. Operator unpauses `accrue`. The next call to `accrue()` computes `next-index`/`next-liquidity-index` reflecting the entire elapsed time since `last-update` (which was never advanced during the pause), applying the full catch-up in one step against whichever principal/shares exist at that moment. [7](#0-6) 
5. User A, who deposited during the pause at the stale rate, benefits at the expense of the treasury/other depositors who did not transact during the window, since the lump-sum accrued interest is distributed post-hoc without regard to who held shares during the frozen interval.

Note: I was not able to fully trace `next-index`/`next-liquidity-index`'s exact formula (whether it computes off elapsed time since `last-update` or some other cached state) within the available context — this would benefit from a full read of `vault-stx.clar`'s `next-index` definition to confirm the exact catch-up mechanics, which the current index did not surface completely.

(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next))
                (var-set index next)
                false)
            (if (not (is-eq lidx nliq))
                (var-set lindex nliq)
                false)
            (if (> treasury-lp u0)
                (try! (ft-mint? zft treasury-lp .dao-treasury))
                false)
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
                (var-set last-update stacks-block-time)
                false)
            (ok { index: next, lindex: nliq })))))
