Confirmed: `TrieUpdateWitnessSizeWrapper` at [1](#0-0)  is used directly to enforce the `new_transactions_validation_state_size_soft_limit` in `prepare_transactions_extra`, breaking the tx-inclusion loop once `state_update.recorded_storage_size()` exceeds the limit at [2](#0-1) . This confirms the exact bug-class analog: an unprivileged, single-transaction-reachable accounting variable that gates a protocol size limit, using an arithmetic pattern that (like the Sherlock report's `ohmMinted`/`ohmRemoved` pair) can be driven into an under-reporting state via legitimate updates, letting the "limit" be silently bypassed.

### Title
Storage-witness proof-size accounting in `TrieUpdateWitnessSizeWrapper` can be driven negative and reused to hide unrecorded reads, bypassing the transaction-validation storage-proof soft limit - (File: `chain/chain/src/runtime/trie_update_wrapper.rs`)

### Summary
`prepare_transactions_extra` uses `TrieUpdateWitnessSizeWrapper::recorded_storage_size()` as the sole gate for `new_transactions_validation_state_size_soft_limit`, the soft limit meant to bound the storage proof generated while validating new transactions before they're included in a chunk ( [2](#0-1) ). The wrapper tracks a signed accumulator, `additional_storage_proof_size: i64`, that is adjusted per distinct key on first read only, mixing `saturating_add` and `saturating_sub` operations across unrelated keys and only clamped to zero at the very end, over the sum of the honest trie recorder plus the accumulator ( [3](#0-2) ).

### Finding Description
For a key that exists both in the real trie and in the pending `TrieUpdate` overlay (i.e. an account/state key an attacker previously set to a large value on-chain, then overwrote with a small value in the same block's pending writes), the wrapper does:
```
recorded.additional_storage_proof_size = recorded
    .additional_storage_proof_size
    .saturating_sub(trie_val_len)
    .saturating_add(update_val_len);
``` [4](#0-3) 

This is only charged once per key (gated by `is_first_read`), and there is no floor applied to the accumulator itself — only the final combined `trie_recorded + additional_storage_proof_size` is clamped with `.max(0)` in `recorded_storage_size()` ( [5](#0-4) ). This mirrors the audit report's root cause: a counter meant to only ever grow toward a limit (`ohmMinted` vs `LIMIT`) is silently reduced by an unrelated "credit" computed from a separate, momentarily-zeroed state (`ohmRemoved` inflated because `ohmMinted` was already reset to 0). Here, `additional_storage_proof_size` accrues large negative credit from cheap, large-trie-value/small-update-value keys, and that credit persists globally across all subsequent distinct-key reads in the same `prepare_transactions_extra` pass, masking the cost of the exact attack this wrapper's own test (`test_wrapper_worst_case_scenario`, [6](#0-5) ) says it protects against: a new, TrieUpdate-only entry at the end of a long/expensive trie path that would otherwise generate no real recorder cost, but is supposed to be charged an estimated cost via the `(None, Some(update_val))` branch ( [7](#0-6) ).

Because the negative credit from earlier "shrink" keys and the additive cost of later "insert-only" (attack) keys are summed into one signed accumulator before the single `.max(0)` clamp, an attacker who first forces the pending overlay to contain several keys where `trie_val_len ≫ update_val_len` accrues a large negative accumulator. Subsequent reads of newly inserted (attack) entries — each of which should add `key_len + value_len + TRIE_INSERT_BASE_SIZE_ESTIMATION` — get absorbed by that negative credit instead of raising `recorded_storage_size()`, so the loop in `prepare_transactions_extra` never observes the size limit being crossed ( [8](#0-7) ).

### Impact Explanation
This directly targets one of the protocol's explicit state-witness size limits (`new_transactions_validation_state_size_soft_limit`, 500 KiB, documented in `docs/misc/state_witness_size_limits.md` at [9](#0-8) ), which exists specifically to keep the storage proof recorded for admitting new transactions bounded so the resulting `ChunkStateWitness` stays distributable. If a chunk producer's estimation can be pushed far below the true recorder growth, the producer could include far more attack transactions than the limit intends, inflating the storage proof recorded by chunk validators beyond expectations — this is squarely in the reachable-analog category of "state-witness limits" and "transaction admission and chunk transaction selection."

### Likelihood Explanation
Reaching this path only requires an attacker-controlled account: (1) create a deep/expensive trie region for one of their own keys (e.g. access keys, matching the wrapper's own worst-case test) with a large value, (2) submit transactions in the same or prior chunk that shrink that value via a normal `TrieUpdate`-visible write, and (3) submit further transactions that make `prepare_transactions_extra` read newly-inserted-only keys. All of this is achievable purely through ordinary signed transactions with no special privilege, matching the "single submitted transaction" reachability requirement.

### Recommendation
Do not let negative adjustments from one key subsidize the estimated cost of a different key. Track `additional_storage_proof_size` as unsigned and clamp per-update (e.g. `saturating_sub` immediately floored at 0 for that key's contribution) rather than allowing a global signed accumulator to carry negative "credit" across unrelated keys, or clamp the accumulator to `>= 0` after every single key's adjustment instead of only after summing across the whole pass.

### Proof of Concept
1. Attacker account `A` sets access key `K1` to a very large value (e.g. a full-access key blob padded to be part of a deep trie region containing many other similar keys, as constructed in `test_wrapper_worst_case_scenario`).
2. In the same block, `A` submits a transaction that overwrites `K1` with a very small value (or removes/replaces it), while another attacker-controlled key `K2` is inserted fresh (only in `TrieUpdate`, absent from the real trie) with a large payload.
3. When `prepare_transactions_extra` runs, its first tx-group iteration reads `K1` first (both-exist branch), producing a large negative delta added into `additional_storage_proof_size` ( [4](#0-3) ).
4. A following iteration in the same pass reads `K2` (insert-only branch), which should add its estimated cost, but the net `recorded_storage_size()` remains at/below the limit check at [2](#0-1)  because the negative credit from step 3 offsets it.
5. Repeating steps 1–4 with many such key pairs lets more transactions be admitted per chunk than the 500 KiB soft limit intends, inflating the storage proof chunk validators must later verify.
