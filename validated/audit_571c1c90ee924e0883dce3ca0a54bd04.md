### Title
Stale cached vault index used after same-block debt socialization enables mispriced collateral/debt valuation - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`market.clar`'s `accrue-and-cache` caches each vault's liquidity/debt index keyed only by `{timestamp: stacks-block-time, aid}` [1](#0-0) . Because `stacks-block-time` is identical for every transaction inside the same block, this cache is not merely a single-transaction memo — the `map-set` write persists on-chain and is visible to every subsequent transaction processed in that same block. The cache is invalidated only by the passage of block time, not by any other on-chain event that changes a vault's real index, such as `vault-socialize-debt`, which is dispatched to the underlying vault contract through a separate call path outside of `accrue-and-cache` [2](#0-1) .

### Finding Description
1. In block N (timestamp T), transaction 1 triggers a position operation that calls `accrue-and-cache(aid)` for some vault (e.g. USDC). This is a cache MISS, so the market calls `vault-accrue`, obtains the current `{index, lindex}`, and stores it under key `{timestamp: T, aid}` [1](#0-0) .
2. Still in block N, transaction 2 is a liquidation/bad-debt event that calls the market's `vault-socialize-debt` dispatcher, which forwards directly to the vault's `socialize-debt` entry point [3](#0-2) . This mutates the vault's real internal index/scaled-debt bookkeping to reflect the write-down, independent of elapsed time — it is not routed through `accrue-and-cache`, so the market-side cache entry from step 1 is left untouched.
3. Still in block N, transaction 3 (any other user's supply/borrow/collateral-add/health-check flow) calls `accrue-and-cache(aid)` again. Since the cache key is still `{timestamp: T, aid}`, this is a cache HIT and returns the pre-socialization `{index, lindex}` captured in step 1, even though the vault's true on-chain state has already moved [4](#0-3) .
4. That stale index then feeds directly into notional/collateral-capacity math used to gate new collateral additions and to size zToken-based price/scaled-debt values, e.g. the capacity check in `collateral-add`, which uses `accrue-and-cache` output to compute `current-capacity`/`future-capacity` before allowing new debt exposure [5](#0-4) .

This is the same bug class as the report's cross-transaction ordering hazard (a value bound at one point in time being consumed later without accounting for an intervening state-changing event), narrowed to a single-block, single-cache-key interleaving rather than two users racing each other for benefit — here it is a caching/invalidation gap: the source of truth (vault index) moves via `socialize-debt`, but the consumer (`accrue-and-cache`) has no way to detect that and keeps serving the pre-movement value for the rest of the block.

### Impact Explanation
If a vault's index is written down by `socialize-debt` (representing realized bad debt) but a later transaction in the same block still reads the pre-write-down cached index, collateral/debt valuations computed for that later transaction are based on state that no longer matches the vault's real, lower per-share value. This can let a position pass health/capacity checks (`ERR-UNHEALTHY` gate in `collateral-add`) that should have failed post-write-down, or let stale zToken pricing understate real debt/overstate real collateral — both of which risk under-collateralized debt being created or preserved, contributing to protocol insolvency or temporary freezing of funds tied to that vault's true accounting.

### Likelihood Explanation
Requires a `socialize-debt` (bad-debt/liquidation write-down) event and at least one other unrelated position operation on the same asset to occur in the same block, after that asset's index had already been cached earlier in the block. Both are permissionless-triggerable operations (liquidations occur regularly in a lending protocol, and users routinely submit transactions to any block), so the interleaving is plausible whenever socialization events happen, though it depends on block-level transaction ordering that the affected party does not fully control.

### Recommendation
Invalidate (or bypass) the `index-cache-` entry whenever `vault-socialize-debt` (or any other non-time-based index mutation) executes for that `aid`, e.g. by deleting the cache entry for `{stacks-block-time, aid}` inside the `vault-socialize-debt` dispatcher, or by having `socialize-debt` itself go through `accrue-and-cache`'s write path so the cache is always kept consistent with the vault's latest real index.

### Proof of Concept
1. Block N: Tx A — a user calls a market entrypoint (e.g. `collateral-add`) for asset USDC, which internally calls `accrue-and-cache(USDC)`; cache MISS, vault-accrue returns index=1.00, cached under `{T, USDC}`.
2. Block N: Tx B — a liquidation causes `vault-socialize-debt(USDC, ...)` to run, writing the real USDC vault index down to reflect a loss (e.g. effectively 0.95 in per-share terms), bypassing the market cache.
3. Block N: Tx C — another user calls `collateral-add`/`supply-collateral-add` for USDC; `accrue-and-cache(USDC)` HITs the stale `{T, USDC}` entry (index=1.00) instead of the post-loss value, so `current-capacity`/`future-capacity` and any zToken price resolution for Tx C are computed against value that no longer exists in the vault, potentially allowing Tx C's position to be judged healthy when it should not be.

;; -- Accrual & caching ------------------------------------------------------

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
