### Title
Pausing interest accrual freezes `last-update` and causes a retroactive interest-index burst on unpause - (File: mainnet/contracts/vault/v0-vault-stx.clar and equivalent vault contracts)

### Summary
Each Zest vault (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`) tracks a borrow index and a liquidity index, refreshed lazily against `last-update` (a stacks-block-time timestamp). `last-update` is only advanced when accrual actually mutates the index, and the paused-accrual path deliberately passes through without reverting and without touching `last-update`. This creates a stale clock that, once accrual is unpaused, causes the full elapsed pause duration to be applied as interest in a single call, using whatever rate prevails at that instant.

### Finding Description
`accrue` in the vault contract computes `next-index`/`next-liquidity-index` from `time-delta = stacks-block-time - (var-get last-update)`: [1](#0-0) 

The multiplier is derived from that time-delta and the *current* interest rate: [2](#0-1) 

`last-update` is only rewritten inside `accrue` when the resulting index actually changes, i.e. gated behind an equality check rather than unconditionally: [3](#0-2) 

Critically, when accrual is paused, `accrue` takes the "pass-through" branch that returns the *current* `idx`/`lidx` unchanged and, because nothing changed, never reaches the `var-set last-update stacks-block-time` branch:

```
(if (get accrue states)
    ;; PAUSED: Pass-through without reverting
    (ok { index: idx, lindex: lidx })
    ...)
``` [4](#0-3) 

This is the "clock advanced only on change" + "pause that passes through instead of reverting" pattern: while `pause-states.accrue` is `true`, `last-update` is frozen at its pre-pause value, but wall-clock time (`stacks-block-time`) keeps moving. The moment accrual is un-paused, the very next call to `accrue` (or any function that calls it, e.g. `deposit`, `redeem`, `system-borrow`, `system-repay`) computes `time-delta` spanning the *entire* pause duration plus any time before it, and applies `calc-multiplier-delta` using the *current* interest rate over that whole span in one transaction: [5](#0-4) 

The intent of pausing accrual is presumably to freeze interest growth for maintenance/incident response, but the implementation instead defers it and replays it all atomically on unpause, based on the rate at the unpause moment rather than the (unknown/blended) rates that should have applied during the pause window. Because `calc-multiplier-delta` is a simple linear extrapolation (`rate * time-delta / SECONDS_PER_YEAR`) with no cap on `time-delta`, an arbitrarily long pause produces an arbitrarily large single-block index jump for both `index` (debt) and `lindex` (liquidity/supply value), applied identically to every position that reads the vault next.

### Impact Explanation
This directly manipulates the borrow index and liquidity index for the whole vault in a single transaction, instantly and simultaneously mis-pricing every user's scaled debt and every zToken holder's redeemable value. This is a form of protocol-caused interest/yield miscalculation: depending on which side of the trade a caller can access first after unpause (e.g., redeeming zTokens or repaying debt right before/after the index jump), it can produce theft or freezing of interest owed to suppliers/borrowers. This lands in the "theft of unclaimed yield" / "temporary freezing of funds" High-severity category, since the burst applies retroactively and non-gracefully to legitimate participants who had no way to anticipate the size of the jump.

### Likelihood Explanation
Pause/unpause of accrual is a normal operational lever (used for incident response or maintenance), not an attack requiring privileged-key compromise — any legitimate pause-then-unpause cycle triggers this behavior automatically on the very next accrual call. The longer the pause, the larger and more damaging the single-block jump, making this a systemic design flaw rather than a rare edge case.

### Recommendation
When accrual is paused, `last-update` should still be advanced to `stacks-block-time` on the pass-through path (or captured/reset when the pause is lifted), so that the pause window is excluded from future `time-delta` calculations instead of being silently replayed as one lump-sum interest event at whatever rate happens to be current when accrual resumes.

### Proof of Concept
1. Admin sets `pause-states.accrue = true` on `v0-vault-usdc` at time `T0` (index/`last-update` frozen at `T0`).
2. Time passes — say 30 days — during which no interest is meant to accrue.
3. Admin sets `pause-states.accrue = false` at time `T1 = T0 + 30 days`. Market interest-rate curve/utilization may have shifted meaningfully in that period, or simply the linear extrapolation over 30 days at the *current* rate is not what should have applied throughout.
4. Any user calls `deposit`/`redeem`/`borrow`, which invokes `accrue`:
   - `time-delta = stacks-block-time(T1) - last-update(T0) = 30 days`.
   - `next-index`/`next-liquidity-index` apply `calc-multiplier-delta(current_rate, 30_days)` in one shot, moving `index`/`lindex` by the full 30-day amount instantly.
5. Every outstanding debt and share balance in the vault is repriced atomically based on this single-block jump, rather than having correctly frozen at `T0` and resuming smoothly from `T1`. A user positioned to redeem/borrow immediately after this jump captures/avoids interest they should not have been exposed to, at the expense of other vault participants.
