### Title
Signature malleability allows duplicate-signer weight counting in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract deduplicates multisig signatures by keeping a flat list of `(recoveredAddress, rawSignatureBytes)` pairs and only skips a signature when the *exact byte encoding* of a previously-seen signature repeats. Because the underlying ECDSA signature validation does not enforce canonical (low-s) signatures, an attacker who has one valid signature from a permission key can derive a second, byte-distinct signature over the same hash that recovers to the *same address*, and the precompile will count that address's weight twice instead of rejecting the duplicate.

### Finding Description
`ECKey.ECDSASignature.validateComponents()` only checks that `v ∈ {27,28}` and that `r,s` are within `[1, SECP256K1N)`; it never enforces `s <= HALF_CURVE_ORDER`, so both `s` and `n-s` (with a flipped recovery id) are accepted as valid signatures for the same message and address: [1](#0-0) 

This is used by `recoverAddrBySign`, which is the address-recovery routine called from `ValidateMultiSign`: [2](#0-1) 

The `ValidateMultiSign` precompile then loops over the supplied signature array and tracks already-processed entries in `executedSignList`, which stores both the recovered address and the raw (address‖sig) bytes: [3](#0-2) 

The dedup logic is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;   // exact same bytes already seen -> skip
  }
  MUtil.checkCPUTime();   // NOT a rejection, just a CPU-time accounting call
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
When the same address has already contributed weight but the new signature's *raw bytes* differ (as happens with a malleable/alternate encoding of the same signature), the inner `continue` is skipped and execution falls through to add the address's weight **again**. The only side effect of the "already seen address, different bytes" branch is `MUtil.checkCPUTime()`, which is a CPU-accounting/anti-DoS check, not a signature-uniqueness enforcement — it does not prevent the weight from being added twice.

By contrast, the equivalent consensus-level dedup routine `TransactionCapsule.checkWeight` was hardened against this exact issue post fork `VERSION_4_7_1`, switching the dedup key from the base64-encoded signature to the recovered `encode58Check(address)`: [4](#0-3) 

The `ValidateMultiSign` precompile, however, still primarily keys its "have I seen this signer" logic on raw signature bytes rather than solely the recovered address, leaving the malleability class alive in this specific TVM code path.

### Impact Explanation
`ValidateMultiSign` is exposed to Solidity/TVM contracts as a way to validate that a TRON account's multisig permission threshold has been met (it returns `true`/`1` once `totalWeight >= permission.getThreshold()`). If a single signer's malleable signature pair can be counted twice, a caller controlling fewer than `threshold` distinct signing keys can still satisfy the threshold check by supplying two byte-different signatures from one key (plus possibly fewer real co-signers), causing on-chain contracts that gate privileged actions (e.g., custodial/multisig wallets, bridges, or any contract relying on `ValidateMultiSign` for authorization) to authorize an action that should have required additional independent signers. This is a concrete authorization-bypass / accounting flaw at the TVM precompile level, not merely theoretical, since the precompile is public and directly reachable by any contract or externally-owned account.

### Likelihood Explanation
Deriving a malleable signature for an existing `(r,s,v)` triple is trivial and requires no private key knowledge — flipping `s → n-s` and adjusting `v` produces a second valid signature recoverable to the same address, satisfying `ECDSASignature.validateComponents()`. Any caller of `ValidateMultiSign` who already possesses one signature from an authorized key can immediately exploit this without needing additional access.

### Recommendation
In `ValidateMultiSign.execute()`, deduplicate purely by recovered address (as `TransactionCapsule.checkWeight` was fixed to do for `VERSION_4_7_1`), rejecting/skipping any signature whose recovered address has already contributed weight regardless of the raw signature bytes, instead of falling through to add weight again when only the byte encoding differs. Additionally, consider enforcing canonical low-`s` signatures in `ECDSASignature.validateComponents()` (or in the precompile's use of it) to eliminate the malleability at its source.

### Proof of Concept
1. Attacker/contract has a permission with threshold requiring, say, weight 2, and two keys A (weight 1) and B (weight 1); attacker only controls key A.
2. Attacker obtains one valid signature `sigA` from key A over the ABI-encoded `(address, permissionId, data)` hash used by `ValidateMultiSign` (see hash construction at `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1062-1064`).
3. Attacker derives a second, byte-different but still-valid signature `sigA'` for the same message from `(r, n-s, v')`, which also recovers to address A via `recoverAddrBySign` since `ECDSASignature.validateComponents()` does not reject high-`s` signatures.
4. Attacker calls `ValidateMultiSign(address, permissionId, data, [sigA, sigA'])`.
5. In the execute loop: first iteration adds weight for A (1); second iteration recognizes `recoveredAddr` (A) is already in `executedSignList`, but since `sign` bytes differ, the `continue` is skipped, `MUtil.checkCPUTime()` runs, and weight for A is added again (total weight 2), satisfying the threshold with only one real signer.

**Note:** Full runtime verification of `MUtil.checkCPUTime()`'s exact semantics and `ByteArray.matrixContains()` implementation could not be completed within this session (search for these definitions did not return results, likely due to index/content coverage limits), but the code path in `PrecompiledContracts.java:1080-1120` as read clearly shows the fall-through double-weight-add behavior on the "same address, different signature bytes" branch.   private static byte[] recoverAddrBySign(byte[] sign, byte[] hash) {
    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }

    long currentWeight = 0;

      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());

    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());
      }
      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)

      }
