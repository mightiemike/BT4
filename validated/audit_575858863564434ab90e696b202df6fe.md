### Title
Non-deterministic wall-clock resource budget causes signers to render conflicting validation verdicts on the same block proposal - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
`postblock_proposal.rs` validates a miner's proposed Nakamoto block by re-executing every transaction under a `TransactionResourceBudgets` built from `block_proposal_max_tx_execution_time_secs`/`block_proposal_max_tx_analysis_time_secs`, which are enforced via a wall-clock `TimeTracker` (`clarity/src/vm/resource_limiter.rs`). Because these budgets are timed with `Instant::now()` per-signer-node rather than derived from anything in the block itself, a minority miner can craft a transaction whose true execution time straddles the configured timeout so that signers with slightly different hardware/load reach opposite ACCEPT/REJECT verdicts on the identical block, exactly analogous to the Optimism bug where a gas check based on a live, mutable resource (`gasleft()`) diverges from the outcome the check was meant to guarantee.

### Finding Description
The `ResourceBudget`/`ResourceLimiter`/`TimeTracker` machinery is explicitly documented as non-deterministic and is intentionally kept out of the consensus-critical commit path: [1](#0-0) [2](#0-1) 

During block-proposal validation (the RPC endpoint signers call before they sign/pre-commit a block), this timer is wired in as a real per-transaction cutoff: [3](#0-2) 

If a transaction's Clarity evaluation or analysis takes longer than the configured seconds on that node, the transaction is classified `Problematic`, and the *entire block* is rejected with `ValidateRejectCode::ProblematicTransaction`: [4](#0-3) 

Unlike the deterministic, consensus-critical `LimitedCostTracker` (`clarity/src/vm/costs/mod.rs`, `add_cost`), which enforces the same numeric cost limit on every node regardless of machine speed, this per-tx wall-clock deadline check is fundamentally a physical stopwatch: the elapsed real time for the exact same Clarity execution depends on CPU speed, current system load, garbage/allocator behavior, and other concurrent processes on each signer's node: [5](#0-4) 

This is the same root-cause pattern as the reported Optimism bug: a check is supposed to guarantee a property ("this tx will always execute within budget"/"there is enough gas left for the call"), but the actual quantity checked (wall-clock time / `gasleft()`) is consumed non-uniformly by intervening work, so different observers (different signer nodes / the same contract call at different gas levels) can legitimately reach different Pass/Fail outcomes for what should be one deterministic answer.

### Impact Explanation
A miner (who only needs to win a single, minority-weight sortition) can include a transaction engineered to take, e.g., ~95–105% of the default `block_proposal_max_tx_execution_time_secs`/`block_proposal_max_tx_analysis_time_secs` (a Clarity loop or heavy MARF-touching contract call whose real wall-clock runtime is close to the threshold). Because each signer independently times this on its own hardware, some signers will finish under the deadline and see the block as valid (and proceed to sign/pre-commit), while other signers, running on slower or momentarily loaded machines, will time out, classify the tx as "problematic," and reject the identical block outright. This produces a genuine minority-triggerable static-validation divergence and temporary tip/consensus disagreement among signers on the very same candidate block, which matches the accepted "High" impact class of this scan (validation verdict two nodes disagree on / temporary tip disagreement).

### Likelihood Explanation
Any miner that wins a single sortition can attempt this; no signer collusion or majority stake is required. Hardware and load heterogeneity across a large, permissionless signer set is the normal operating condition of the network, so hitting the "straddle" window is plausible rather than purely theoretical, especially since the miner can iterate/tune the crafted transaction against a machine similar to typical signer hardware before submission.

### Recommendation
Do not let a raw wall-clock deadline gate whether a specific block is accepted or rejected in a way that differs from other signers. Options: (1) treat per-tx execution/analysis timeouts purely as local defense-in-depth that causes the *local* node to skip building/mining with that tx but does not, by itself, justify broadcasting a REJECT vote for a block that a majority of the network otherwise accepts; (2) require a large, generous safety margin (well beyond plausible hardware variance) plus a retry-once-with-higher-budget policy before rejecting; (3) make the per-tx timeout configurable to a value far larger than any legitimate transaction (as already suggested for the miner-side note in `stackslib/src/config/mod.rs`), and monitor/alert instead of auto-rejecting on marginal cases.

### Proof of Concept
1. Deploy/propose a Nakamoto block containing one transaction whose real (wall-clock) evaluation time is engineered to sit close to `block_proposal_max_tx_execution_time_secs` (default value in `stackslib/src/config/mod.rs`), e.g. a contract call doing a fixed, calibrated amount of `var-get`/MARF work.
2. Submit the block proposal to the signer set as in `stackslib/src/net/api/tests/postblock_proposal.rs::test_block_proposal_validation_execution_time_expired_blames_tx`, which demonstrates that setting `block_proposal_max_tx_execution_time_secs` to a boundary value flips the verdict from accept to `ValidateRejectCode::ProblematicTransaction` reject.
3. Because each signer applies its own local `Instant::now()`-based `ResourceLimiter` (`clarity/src/vm/resource_limiter.rs` lines 62-101) independently, signers on marginally slower/busier hardware reject while faster/idle signers accept the same block, producing a split verdict across the signer set for one canonical block proposal.

    /// Returns and error if a deadline is configured and has elapsed. Always
    /// Ok(()) for `NoTracking`.
    pub fn check_not_expired(&self) -> Result<(), String> {
        match self {
            Self::NoTracking => Ok(()),
            Self::MaxTime {
                start_time,
                max_duration,
            } => {
                let elapsed = start_time.elapsed();
                // semantically `>` would be more correct than `>=`, but there
                // are a few tests that assume "zero always expires", and since
                // it makes not practical difference otherwise, we use `>=`.
                if elapsed >= *max_duration {
                    Err(format!(
                        "Elapsed time of {} ms exceeds budget of {} ms.",
                        elapsed.as_millis(),
                        max_duration.as_millis()
                    ))
                } else {
                    Ok(())
                }
            }
        }
    }
