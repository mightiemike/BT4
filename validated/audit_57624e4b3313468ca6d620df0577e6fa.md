### Title
Division-before-multiplication precision loss in witness/voter reward calculation - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService` computes voter and standby-witness rewards by first dividing a ratio (as a `double`) and then multiplying by the reward amount, truncating to `long` afterward. This is the same "divide-before-multiply" anti-pattern flagged in the DODO `finishLiquidation()` report: an intermediate division causes precision loss before the multiplication, and the result is used to update on-chain account/reward balances.

### Finding Description
In `payStandbyWitness()`, the per-vote pay rate is computed by dividing first: [1](#0-0) 
`double eachVotePay = (double) totalPay / voteSum;` followed by `long pay = (long) (w.getVoteCount() * eachVotePay);` — division happens before the multiplication by `voteCount`, and the `double` representation of `eachVotePay` already loses precision before it's scaled up and truncated to `long`.

The same pattern appears in the legacy reward computation used for pre-new-algorithm cycles: [2](#0-1) 
`double voteRate = (double) userVote / totalVote; reward += voteRate * totalReward;` — again, `userVote / totalVote` is computed and rounded via `double` before being multiplied by `totalReward`, rather than multiplying first (`userVote * totalReward`) and dividing once at the end. This is invoked from `computeReward(beginCycle, endCycle, accountCapsule)` used by both `withdrawReward()` and `queryReward()`: [3](#0-2) 

Note that the codebase already demonstrates awareness of this exact bug class elsewhere and has "hardened" fixes using `BigInteger`/exact multiply-then-divide ordering (e.g. `ResourceProcessor.calculateGlobalLimitV1/V2`, `BandwidthProcessor.calculateGlobalNetLimitV2`, and the newer `VoteRewardUtil.computeReward` / `RewardViCalService` which use `BigInteger deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)` — multiply first, divide once): [4](#0-3) [5](#0-4) 
This confirms the project's own remediation pattern for this bug class — but `MortgageService.payStandbyWitness` and the legacy `computeReward(cycle, votes)` path were not updated to the same pattern.

### Impact Explanation
`withdrawReward()` / `queryReward()` are reachable from ordinary, unprivileged transactions — any account can trigger reward withdrawal/accrual (via `WithdrawBalanceActuator`, `VoteWitnessActuator`, `UnfreezeBalanceActuator`, and the TVM native contract `WithdrawRewardProcessor`, all of which call into `mortgageService.withdrawReward(...)`). Because the per-voter/per-witness reward is computed via `double`-division before multiplication, the resulting `long` reward is systematically truncated/rounded incorrectly relative to the correct integer-exact `(userVote * totalReward) / totalVote` computation. Summed across all voters and cycles, this causes:
- accounting drift between the sum of individually paid rewards and the actual `totalReward`/`totalPay` pool (dust leakage or shortfall),
- inconsistent reward amounts depending on `double` rounding behavior for very large `totalReward`/`voteSum`/`totalVote` values (loss of significant bits once values exceed `double`'s 53-bit mantissa, which is plausible given `TRX` values scale to 10^15+ sun).

This affects consensus-level account balance accounting (asset corruption in the sense of incorrect reward distribution), which the validation criteria explicitly accepts.

### Likelihood Explanation
This code path executes on every reward withdrawal and every maintenance-cycle standby-witness payout, triggered by ordinary user transactions and by the periodic `payStandbyWitness()` maintenance call — no privileged access is required to trigger it, only normal chain operation. However, the magnitude of the precision loss is bounded by `double`'s ~15-17 significant decimal digits, so for typical current TRX-scale values the drift per call is small; it accumulates over time and at large vote/reward totals.

### Recommendation
Replace the `double`-based ratio computation with integer/`BigInteger` multiply-then-divide, consistent with the pattern already used in `VoteRewardUtil.computeReward`, `RewardViCalService.accumulateWitnessVi`, and `ResourceProcessor.calculateGlobalLimitV1/V2`:
- In `payStandbyWitness()`: compute `pay = BigInteger.valueOf(w.getVoteCount()).multiply(BigInteger.valueOf(totalPay)).divide(BigInteger.valueOf(voteSum)).longValueExact();` instead of using `double eachVotePay`.
- In the legacy `computeReward(cycle, votes)`: compute `reward += BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward)).divide(BigInteger.valueOf(totalVote)).longValueExact();` instead of `voteRate * totalReward`.

### Proof of Concept
Given `totalPay = 10`, `voteSum = 3`, and three witnesses each with `voteCount = 1`:
- Current code: `eachVotePay = (double)10/3 = 3.3333333333333335`; each `pay = (long)(1 * 3.3333333333333335) = 3`; total paid = 9, leaving 1 unaccounted (dust loss), and the exact rounding behavior differs from the correct `floor(voteCount * totalPay / voteSum)` computation once values grow large enough to exceed `double` precision (e.g. `totalPay` or `voteSum` in the 10^15–10^18 sun range used elsewhere in this codebase for TRX amounts), where `double` division can no longer represent the exact ratio, producing results that diverge from the mathematically correct integer computation — exactly the failure mode the Sherlock report describes for `realDebt`.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
