### Title
Unauthorized eviction of unrelated accounts' transactions survives mempool rejection - ([File: crates/apollo_mempool/src/mempool.rs])

### Summary
An unprivileged transaction sender can submit a single transaction that is ultimately **rejected** by the mempool (`MempoolError::MempoolFull`) while still causing the **irreversible eviction** of unrelated, legitimate transactions belonging to other accounts. This mirrors the NTP crypto-NAK analog: a message that fails its own validation (bad auth data / doomed to be rejected) nonetheless triggers destructive state teardown (association demobilization) as a side effect.

### Finding Description
When an incoming transaction would exceed mempool capacity, `add_tx_validations` calls `handle_capacity_overflow`, which in turn calls `try_make_space` to evict other accounts' transactions to free room: [1](#0-0) [2](#0-1) 

`try_make_space` unconditionally removes victim transactions from `tx_pool` and `tx_queue` while attempting to free `required_space`, and only reports success/failure at the end — it never rolls back the evictions it already performed if the total freed space is still insufficient: [3](#0-2) 

If the freed space is insufficient, `handle_capacity_overflow` returns `Err(MempoolError::MempoolFull)`, and the caller propagates the error, rejecting the incoming (attacker) transaction. However, the already-evicted victim transactions are **not restored** — they remain permanently removed from both the pool and the queue. This is confirmed by an explicit test asserting this exact behavior: [4](#0-3) 

The comment in `add_tx_validations` only guarantees no stranding for the *replaced_tx_reference* (fee-escalation) case ("a rejected incoming transaction never strands the account"), but this guarantee does not extend to third-party accounts evicted via `try_make_space`: [5](#0-4) 

### Impact Explanation
An attacker with no special privileges — any account able to submit one transaction — can craft a transaction sized so that: (1) it forces eviction of other users' legitimate, already-admitted transactions (targeted via `get_evictable_account`, which currently selects from `accounts_with_gap`), and (2) the freed space still isn't enough for the attacker's own oversized transaction, causing it to be rejected. The net effect is that legitimate users' pending transactions disappear from the mempool with no compensating admission, forcing them to resubmit, and in a busy mempool this can be repeated to degrade transaction confirmation for arbitrary accounts — a griefing/DoS vector that causes concrete inconvenience/loss of transaction inclusion for honest senders. This aligns with "a network unable to confirm new transactions" for the affected victim accounts.

### Likelihood Explanation
The path is reachable directly from `add_tx`/`add_tx_validations`, which is invoked for every submitted transaction; no operator, proposer, or peer privileges are required — only that the mempool be near capacity and contain evictable ("gap") accounts, both of which are normal operating conditions. Reproducing this requires only crafting a transaction with an appropriately sized payload (e.g., large signature) relative to current mempool capacity, as directly demonstrated in the existing unit test.

### Recommendation
Make eviction transactional: only commit evictions to `tx_pool`/`tx_queue` once `try_make_space` (and the overall admission) is confirmed to succeed, or stage victim removals and roll them back if `required_space` is not met, restoring evicted transactions before returning `MempoolError::MempoolFull`.

### Proof of Concept
The existing test `rejects_or_accepts_tx_based_on_freed_space` (case `insufficient_eviction_space`) in `crates/apollo_mempool/src/fee_mempool_test.rs` demonstrates the exact scenario: two victim transactions (`tx1`, `tx2`) are added and fill capacity; a third, oversized transaction (`large_tx`) is submitted and rejected with `MempoolError::MempoolFull`, yet the assertion at the end confirms `tx1` and `tx2` are evicted regardless of the outcome: [6](#0-5)

    pub fn try_make_space(&mut self, required_space: u64) -> bool {
        let mut total_space_freed = 0;
        let mut evicted_txs = Vec::new();

        while total_space_freed < required_space {
            let Some(address) = self.get_evictable_account() else {
                break;
            };

            let txs: Vec<_> = self.tx_pool.account_txs_sorted_by_nonce(address).copied().collect();
            for tx_ref in txs.iter().rev() {
                let tx = self
                    .tx_pool
                    .remove(tx_ref.tx_hash)
                    .expect("Transaction must exist in the pool.");
                total_space_freed += tx.total_bytes();
                evicted_txs.push(*tx_ref);
                metric_count_evicted_txs(1);
                self.decrement_stuck_txs_if_gap_account(address, 1);
                if total_space_freed >= required_space {
                    break;
                }
            }

            // Clean up if account is now empty.
            if !self.tx_pool.contains_account(address) {
                self.accounts_with_gap.swap_remove(&address);
            }
        }

        // Keep the queue consistent with the pool: the evicted txs were removed from the pool, so
        // drop their (now-orphaned) queue references too. In fee mode gap accounts are never
        // queued, so this is a no-op there; in Echonet/FIFO mode they are, and skipping this leaves
        // a dangling reference that panics the next `get_txs`.
        self.tx_queue.remove_txs(&evicted_txs);

        total_space_freed >= required_space
    }

    fn handle_capacity_overflow(
        &mut self,
        tx: &InternalRpcTransaction,
        account_nonce: Nonce,
        freed_bytes: u64,
    ) -> Result<(), MempoolError> {
        let address = tx.contract_address();

        let account_has_gap = self.accounts_with_gap.contains(&address);
        let account_has_txs = self.tx_pool.contains_account(address);
        let closing_gap = tx.nonce() == account_nonce;
        let creating_gap = (account_has_gap || !account_has_txs) && !closing_gap;

        // Only the net growth must be evicted: an accompanying replacement removal frees
        // `freed_bytes` (0 when there is no replacement).
        let required_space = tx.total_bytes().saturating_sub(freed_bytes);
        if !creating_gap && self.try_make_space(required_space) {
            return Ok(());
        }

        Err(MempoolError::MempoolFull)
    }

#[rstest]
#[case::insufficient_eviction_space(20, false)]
#[case::sufficient_eviction_space(8, true)]
fn rejects_or_accepts_tx_based_on_freed_space(
    #[case] signature_size: usize,
    #[case] expect_success: bool,
) {
    let tx1 = add_tx_input!(tx_hash: 1, address: "0x1", tx_nonce: 1, account_nonce: 0);
    let tx2 = add_tx_input!(tx_hash: 2, address: "0x1", tx_nonce: 2, account_nonce: 0);

    let large_signature = vec![felt!("0x0"); signature_size];
    let large_tx = AddTransactionArgs {
        tx: internal_invoke_tx(invoke_tx_args!(
            tx_hash: tx_hash!(3),
            signature: TransactionSignature(large_signature.into())
        )),
        account_state: AccountState { address: contract_address!("0x0"), nonce: nonce!(0) },
    };

    let capacity = tx1.tx.total_bytes() + tx2.tx.total_bytes();
    let mut mempool = Mempool::new(
        MempoolConfig {
            static_config: MempoolStaticConfig {
                capacity_in_bytes: capacity,
                ..Default::default()
            },
            ..Default::default()
        },
        Arc::new(FakeClock::default()),
    );

    for tx in [&tx1, &tx2] {
        add_tx(&mut mempool, tx);
    }

    if expect_success {
        add_tx(&mut mempool, &large_tx);
        assert!(mempool.tx_pool.get_by_tx_hash(large_tx.tx.tx_hash()).is_ok());
    } else {
        add_tx_expect_error(&mut mempool, &large_tx, MempoolError::MempoolFull);
    }

    // Transactions tx1 and tx2 are evicted regardless of whether large_tx is accepted or rejected.
    // We do not revert the eviction attempt even if adding large_tx ultimately fails.
    assert!(!mempool.tx_pool.contains_account(contract_address!("0x1")));
}
