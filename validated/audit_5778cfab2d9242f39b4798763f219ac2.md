### Title
Fixed callback gas budget in the NEAR Wallet Contract can be exhausted by an attacker-controlled return value, permanently stuck `has_in_flight_tx` freezing the wallet - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract` (the eth-emulation NEAR Wallet Contract) hard-codes a fixed gas budget, `RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, for the final callback (`rlp_execute_callback`) regardless of the size of the data that callback must process. [1](#0-0)  This is directly analogous to the external report's core bug class: a hard-coded/fixed gas limit chosen without regard for the actual (attacker-influenceable) execution cost, which can be too low for legitimate execution paths and cause failures at exactly the point that matters.

### Finding Description
`inner_rlp_execute` dispatches the user's requested NEAR action (`target`, arbitrary method call chosen via the RLP-encoded Ethereum transaction) and attaches `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) as the static gas for the trailing `rlp_execute_callback`: [2](#0-1) 

`rlp_execute_callback` sets `self.has_in_flight_tx = false` as its first statement, then reads the promise result (`env::promise_result(0)`), and on success wraps the arbitrary-sized returned bytes into an `ExecuteResponse` that is serialized (JSON) and returned; on failure it creates a refund promise: [3](#0-2) 

Because the `target` contract is arbitrary and its returned value size is only bounded by protocol-wide limits (e.g. `max_length_returned_data`), the amount of gas needed to read the register, deserialize/copy the returned bytes, and serialize the `ExecuteResponse` scales with that size. The callback's gas budget is a *flat* 5 Tgas irrespective of how large that value is. If the callback panics with `GasExceeded` (out-of-gas) partway through — a documented, deterministic runtime behavior where "no changes are persisted on chain" for a panicking function call — then all state mutations made inside that call, including `self.has_in_flight_tx = false`, are rolled back: [4](#0-3) 

Since `has_in_flight_tx` was already set to `true` by the *preceding* `rlp_execute` call (which persisted successfully), and the only code path that resets it to `false` is inside this same callback that can panic before persisting, a `GasExceeded` panic in `rlp_execute_callback` leaves `has_in_flight_tx` permanently stuck at `true`. Every subsequent `rlp_execute` call immediately short-circuits with "transaction already in progress" and never dispatches a new action: [5](#0-4) 

This is reachable by any unprivileged caller: the attacker only needs to control (or induce) the `target` contract invoked by the user's signed RLP transaction so that it returns a value near the protocol's maximum returned-data size on success, causing the fixed 5 Tgas callback to run out of gas.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, the wallet contract account becomes permanently unusable — no future `rlp_execute` call can ever succeed again, regardless of gas attached to the outer call, because the check happens before any gas-sensitive logic even executes. This permanently freezes the user's NEAR Wallet Contract account (all associated assets and ability to submit further eth-emulated transactions through it), matching the "permanently frozen funds" acceptance criterion. It mirrors the external report's core issue — a fixed gas allowance that is insufficient for genuine, protocol-permitted inputs — but is more severe here because there is no analogous "cancel" recovery path; the only state that resets the flag is the same code path that can be starved of gas.

### Likelihood Explanation
Reaching this requires only a single ordinary `rlp_execute` transaction targeting a contract whose method returns a large-enough value on success. Nothing privileged is required; the attacker can deploy their own `target` contract to intentionally return a large payload, or an existing contract may organically return values close to the size limit. The fixed nature of `RLP_EXECUTE_CALLBACK_GAS` (independent of any per-call configuration or dynamic sizing) means the vulnerability is deterministic once the returned-value size crosses the gas threshold, making it a Medium-to-High-likelihood issue for any wallet contract instance whose relayer/user routes calls to large-return-value contracts.

### Recommendation
- Size the callback's static gas budget dynamically based on the maximum possible size of data the callback may need to process (e.g., reserve gas proportional to `max_length_returned_data`), or bound/truncate the `success_value` before serializing it in `rlp_execute_callback`.
- Reorder/guard the invariant reset so `has_in_flight_tx` cannot get permanently stuck: e.g., perform the potentially gas-heavy work (reading/serializing the promise result) in a way that cannot cause the whole callback to abort, or provide a separate, minimal-gas recovery path that unconditionally resets `has_in_flight_tx` if the primary callback fails/panics due to gas.
- Add an explicit gas check at the start of the callback (`env::used_gas()`/`prepaid_gas()`) and fail gracefully (still persisting `has_in_flight_tx = false`) rather than allowing an uncontrolled panic mid-function.

### Proof of Concept
1. Deploy a helper contract `evil.near` with a method, e.g. `big_return()`, that returns a byte blob close to the protocol's `max_length_returned_data` limit.
2. Have a user sign an RLP-encoded Ethereum transaction whose `to` targets `evil.near::big_return` (an ordinary `FunctionCall` action, not one of the special-cased `EthEmulationKind` paths so that it goes through the default branch using the flat `RLP_EXECUTE_CALLBACK_GAS`). [2](#0-1) 
3. Submit `rlp_execute(target="evil.near", tx_bytes_b64=...)` with ample total attached gas (e.g. 300 Tgas) so only the fixed 5 Tgas callback allotment is the binding constraint for the callback receipt.
4. The outgoing call to `evil.near::big_return` succeeds and returns the large value; `rlp_execute_callback` is invoked with only `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas), which is consumed reading the register/serializing the large `success_value`, triggering `HostError::GasExceeded` (see existing test pattern) analogous to `test_insufficient_gas` which already demonstrates that under-provisioned gas to `rlp_execute` calls surfaces as "Exceeded the prepaid gas." [6](#0-5) 
5. Because the callback panics, `self.has_in_flight_tx = false` (set at line 280) is never persisted, so `has_in_flight_tx` remains `true` from the prior `rlp_execute` invocation.
6. Any subsequent `rlp_execute` call now immediately returns `"Error: transaction already in progress, please try again later."` forever, since nothing in the contract can reset the flag. [7](#0-6) 

Note: I was not able to execute this scenario in a live environment or precisely quantify the exact byte-size threshold at which 5 Tgas is exhausted (this depends on `ExtCosts` gas-per-byte parameters and `max_length_returned_data`, which I located as referenced constants but did not fully trace to a final numeric threshold). This should be confirmed with an actual test-loop reproduction before treating the exploit as fully validated.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

#[tokio::test]
async fn test_insufficient_gas() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    // If not enough gas is attached to the `rlp_execute` call then the action fails.
    let target = "some.account.near".to_string();
    let action = Action::FunctionCall {
        receiver_id: target.clone(),
        method_name: "greet".into(),
        args: br#"{"name": "Aurora"}"#.to_vec(),
        gas: 5_000_000_000_000,
        yocto_near: 0,
    };
    let signed_transaction = utils::create_signed_transaction(
        0,
        &target.parse().unwrap(),
        Wei::zero(),
        action,
        &wallet_sk,
    );

    let error = wallet_contract
        .inner
        .call(crate::tests::RLP_EXECUTE)
        .args_json(serde_json::json!({
            "target": target,
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_gas::NearGas::from_tgas(7))
        .transact()
        .await
        .unwrap()
        .raw_bytes()
        .unwrap_err();

    assert!(
        error.to_string().contains("Exceeded the prepaid gas."),
        "Error should be that there was not enough gas"
    );
