### Title
Unsafe `BigInteger.longValue()` truncation in vote-reward computation (silent overflow instead of exact-cast failure) - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
The Ajna finding is about `uint256`→`uint128` downcasts that silently truncate instead of reverting, corrupting reward accounting. java-tron's vote-reward subsystem has the equivalent Java analog: reward deltas are accumulated in arbitrary-precision `BigInteger` (the `Vi` "reward-per-vote" index), but the final conversion back to the `long` reward accumulator uses `BigInteger.longValue()`, which silently wraps around (two's-complement truncation) instead of throwing, unlike `longValueExact()`, which the same codebase already uses elsewhere for the exact same class of risk.

### Finding Description
Witness reward-per-vote (`Vi`) is stored as an ever-accumulating `BigInteger`, scaled by `DECIMAL_OF_VI_REWARD = 10^18`: [1](#0-0) 

Each cycle it is monotonically incremented and never decays: [2](#0-1) 

When a user's reward is computed, the delta between two `Vi` snapshots (which can be an arbitrarily large `BigInteger` for a long-held vote position) is multiplied by the user's vote count and divided by `1e18`, then the result is downcast with `.longValue()`: [3](#0-2) 

The same unsafe pattern is duplicated in the TVM-exposed reward path: [4](#0-3) 

and in the historical reward pre-calculation service: [5](#0-4) 

`BigInteger.longValue()` (per JDK spec) does not check whether the value fits in a `long`; if it doesn't, it silently returns the low-order 64 bits reinterpreted as a signed `long`, which can be an arbitrarily different (including negative) value. This is exactly analogous to Solidity's unchecked `uint256(x)` → `uint128` cast that motivated the Ajna finding. Notably, the codebase is aware of this exact class of bug and mitigates it elsewhere using `longValueExact()`: [6](#0-5) [7](#0-6) 

...but the three reward-computation call sites above were left using the unchecked, silently-truncating `.longValue()`.

### Impact Explanation
If `deltaVi * userVote / 1e18` exceeds `Long.MAX_VALUE` (plausible for accounts that keep votes locked across very many maintenance cycles while `Vi` keeps accumulating without bound, combined with a large `userVote`), `.longValue()` silently truncates:
- The truncated value can come out negative, in which case in `MortgageService.computeReward` / `VoteRewardUtil.computeReward` the user's true earned reward is silently discarded (`reward += <corrupted, possibly negative value>`), matching Ajna's "reduced rewards" / "loses the reward" impact — reward accounting divergence with no revert or warning.
- The truncated value could equally emerge as an arbitrary unrelated positive `long`, which is then added to the account's `allowance` in `adjustAllowance` and eventually credited to the account balance via `WithdrawRewardProcessor.execute` (`accountCapsule.setBalance(...)`), i.e., an accounting/settlement divergence where a user's claimable reward no longer reflects real economic entitlement. [8](#0-7) 

This reward path is reachable by any unprivileged voter/staker (both via the DPoS delegation flow and via the TVM `RewardBalance`/withdraw-reward precompiles), so it is not a trusted-role-only or theoretical-only issue — it directly affects unprivileged-user balance/reward accounting.

### Likelihood Explanation
Triggering the overflow requires the accumulated `Vi` delta for a given voter to grow large enough (post multiplication by vote count and division by `1e18`) to exceed `Long.MAX_VALUE` (~9.22e18). Because `Vi` accumulates without bound across the chain's entire cycle history for witnesses with persistently low total vote counts, and vote counts can themselves be large, this is a plausible-over-long-timeframes condition rather than an immediate one — consistent with the original Ajna report's own characterization that the LP-cast case is "highly unlikely" while the exchange/rate-style accumulator case is "more likely." The lack of any bounds check or exact-cast enforcement means the failure mode is silent (wrong number, no revert), which is worse than an outright DoS since it would go undetected and corrupt accounting permanently once it occurs.

### Recommendation
Replace `.longValue()` with `.longValueExact()` (which throws `ArithmeticException` on overflow, consistent with the pattern already used in `PrecompiledContracts.getEnergyTIP7883` and `ResourceProcessor.calculateGlobalLimitV2`) in:
- [9](#0-8) 
- [10](#0-9) 
- [11](#0-10) 

Additionally, consider bounding the growth of `Vi` (e.g., periodic rebasing or capping cycle span used in delta computation) so that legitimate long-held positions cannot approach the overflow threshold, and add regression tests analogous to the existing `RepositoryImplHardenTest`/`CalculateGlobalLimitHardenTest` overflow-detection tests for this reward path.

### Proof of Concept
1. A voter votes for a witness whose total vote weight stays very low relative to the reward paid each cycle over a very large number of cycles (or the witness reward/vote-count ratio is otherwise engineered to maximize `deltaVi` growth), so that `Vi` for that witness (a `BigInteger` per `DelegationStore.accumulateWitnessVi`) grows without bound over time.
2. The voter delays withdrawing rewards for many cycles, so `endVi - beginVi` (computed in `computeReward`) becomes very large.
3. When the voter finally calls withdraw (or the TVM `RewardBalance`/withdraw-reward precompile invokes `VoteRewardUtil.computeReward`), `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)` produces a `BigInteger` exceeding `Long.MAX_VALUE`.
4. `.longValue()` truncates this to an arbitrary 64-bit value (potentially negative or an unrelated large positive number) instead of throwing, silently corrupting the reward the voter receives — either losing earned rewards or receiving an incorrect (possibly inflated) allowance credited to their account balance via `WithdrawRewardProcessor`.

    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }

  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }
