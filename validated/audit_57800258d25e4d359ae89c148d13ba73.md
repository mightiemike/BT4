### Title
Reward accounting divergence between TVM Vote precompile path and system MortgageService path for pre-new-algorithm cycles - (File: `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
Java-tron has two parallel implementations of the "vote reward" accounting logic: `MortgageService` (used by the HTTP `GetRewardServlet` view API and the system-level `withdrawReward`/native reward payout path) and `VoteRewardUtil` (used by the TVM `RewardBalance` precompiled contract for viewing rewards, and by `WithdrawRewardProcessor` for actually paying out rewards to smart-contract-owned accounts). These two implementations compute rewards differently for cycles that occurred before `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`, which can cause the TVM-side view (`RewardBalance` precompile) and the actual TVM withdrawal amount to diverge from what the system-level view/withdrawal would compute for an account with identical vote history — the same inconsistency class flagged in the referenced Backd report, where a "claimable rewards" view diverges from the actual payout because one code path takes into account state/logic that the other omits.

### Finding Description
`MortgageService.computeReward(beginCycle, endCycle, accountCapsule)` explicitly splits the computation at the network's `newAlgorithmCycle` boundary: [1](#0-0) 

For cycles before that boundary it calls `getOldReward()`, which — depending on the `allowOldRewardOpt` dynamic parameter — either delegates to the Vi-based `RewardViCalService.getNewRewardAlgorithmReward()` or falls back to the legacy per-cycle, `double`-based formula (`voteRate * totalReward`) in `computeReward(cycle, votes)`: [2](#0-1) [3](#0-2) 

By contrast, `VoteRewardUtil.computeReward()` — used both by the `RewardBalance` precompile (a TVM view function reachable from any contract call) and by `WithdrawRewardProcessor.execute()` (the actual payout path for TVM-vote-enabled accounts) — has no such split. It unconditionally computes the reward for the *entire* `[beginCycle, endCycle)` range using only the `BigInteger` Vi-delta method, regardless of `newAlgorithmCycle` or `allowOldRewardOpt`: [4](#0-3) 

The precompile and processor that rely on this function: [5](#0-4) [6](#0-5) 

Because the `double`-based old-algorithm formula and the `BigInteger` Vi-delta formula round differently (per-cycle floating point truncation vs. accumulated integer division), an account whose votes span cycles before `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` can get a different total reward depending on whether the query/withdrawal goes through `MortgageService` (when `allowOldRewardOpt` is disabled) or through `VoteRewardUtil` (always Vi-based). This means the `RewardBalance` precompile's view of "claimable reward" for a smart-contract-owned voter is not the value the equivalent EOA/system path would report or actually pay for identical vote history.

### Impact Explanation
This falls into the "resource and reward accounting" category: it is a reachable-from-contract-call view/accounting inconsistency causing accounting corruption between two payout paths. A user or contract relying on `RewardBalance` (queried via a normal contract call, unprivileged) to estimate rewards could see a value that never matches — and worse, `WithdrawRewardProcessor` will actually pay out the Vi-based amount unconditionally, while the "canonical" system computation (`MortgageService`, gated by `allowOldRewardOpt`) may intend a different (legacy) amount for the same historical cycles. This is an accounting-consistency defect rather than a fund-drain bug, matching the Medium-severity characterization of the original finding.

### Likelihood Explanation
Triggering this requires: (1) TVM vote feature enabled (`allowTvmVote`) and `allowChangeDelegation` enabled — both are mainnet-enabled features; (2) an account (particularly a smart contract) whose vote/reward history spans cycles before `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`; and (3) `allowOldRewardOpt` being disabled at the time, or divergence in Vi backfill completeness (`RewardViCalService.isDone()`), such that `MortgageService`'s old-cycle computation differs from the Vi-based one. Because the new-algorithm cutover cycle and `allowOldRewardOpt` are network-wide proposal parameters set long in the past on production chains, whether this divergence is currently exploitable depends on the current configured value of `allowOldRewardOpt` and whether pre-cutover cycles remain relevant to any account's `beginCycle`; I could not verify the current on-chain value of this parameter from the code alone.

### Recommendation
Make `VoteRewardUtil.computeReward()` consistent with `MortgageService.computeReward()` by applying the same `newAlgorithmCycle` / `allowOldRewardOpt` split (i.e., reuse the identical old/new algorithm branching logic, ideally by extracting the shared computation into a single utility used by both `MortgageService` and `VoteRewardUtil`) so that the TVM `RewardBalance` view, the TVM `WithdrawRewardProcessor` payout, and the system `GetRewardServlet`/`withdrawReward` payout all compute identical reward amounts for any given account and cycle range.

### Proof of Concept
1. Deploy a contract and vote for a witness in a cycle prior to `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` (using `allowTvmVote`).
2. Configure `allowOldRewardOpt` to `0` (disabled) via committee proposal, forcing `MortgageService.getOldReward()` to use the legacy `double`-based per-cycle formula for cycles before the cutover.
3. Advance past the cutover cycle so both `beginCycle < newAlgorithmCycle < currentCycle`.
4. Call the `RewardBalance` precompile (via `TransactionTrace.convertToTronAddress`/`VoteRewardUtil.queryReward`) for the contract address, and separately call `GetRewardServlet`/`MortgageService.queryReward()` for an EOA with an identical vote history recreated at the same cycles.
5. Compare results: `VoteRewardUtil.queryReward` (Vi-only, `actuator/.../VoteRewardUtil.java:57-88`) and `MortgageService.queryReward` (old/new split, `chainbase/.../MortgageService.java:136-169`) can diverge in the reward amount reported for the pre-cutover portion of the cycle range, and `WithdrawRewardProcessor.execute` will actually credit the Vi-only amount to the contract's allowance.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }
