### Title
Fail-fast `WorkerPool` design permanently disables the batcher after a single transaction triggers a panic during execution - ([File: crates/blockifier/src/concurrency/worker_pool.rs])

### Summary
The blockifier's `WorkerPool` runs a fixed set of persistent OS threads that execute transactions for every block built by the batcher. If any thread panics while executing a transaction, the pool's design deliberately causes *every other worker thread* to also panic and terminate (via the shared `a_thread_panicked` flag), and the pool never respawns dead threads. Because the same `WorkerPool` instance is reused across all subsequent blocks (created once in `create_batcher`), a single crafted transaction that triggers a Rust-level panic (as opposed to a graceful `Result::Err`) anywhere in the execution path can permanently and irrecoverably disable concurrent block building for the node — closely analogous to the reported CVE where an unhandled exception in a persistent listener thread permanently stops the service from accepting further work.

### Finding Description
`WorkerPool::start` spawns `n_workers` OS threads once, each running `WorkerThread::run_thread` in a loop that pulls `WorkerExecutor`s off an `mpsc::Receiver` for the lifetime of the process: [1](#0-0) 

Each transaction chunk is executed inside `_run_executor`, which wraps `worker_executor.run()` in `panic::catch_unwind`. If a panic occurs, `a_thread_panicked` is set, the scheduler is halted, and the caught panic is explicitly re-raised via `panic::resume_unwind(err)` — this second panic is *not* caught, so the current worker thread terminates for good: [2](#0-1) 

Crucially, at the top of `_run_executor`, before even entering `catch_unwind`, every *other* worker thread checks the shared flag and immediately panics uncaught if it is set: [3](#0-2) 

This means one panicking transaction causes **all** worker threads in the pool to die (fail-fast by design), and `run_thread`'s `while let Some(...)` loop simply exits when a thread dies — there is no thread respawn logic anywhere in `WorkerPool`.

The `WorkerPool` is created exactly once per batcher process and shared across every subsequent block: [4](#0-3) [5](#0-4) 

Once all worker threads are dead, `WorkerPool::run` (`sender.send(...)`) will still succeed (the channel exists), but no thread will ever consume the message, so any subsequent block's `worker_executor.scheduler.wait_for_completion(...)` will block forever, and `check_panic()` will now find `a_thread_panicked == true` and panic in the calling context (`ConcurrentTransactionExecutor::get_new_results` / `run_and_wait`): [6](#0-5) [7](#0-6) 

This propagates up through `block_builder.rs`'s `spawn_blocking(...).await.expect(...)` calls used for `add_txs_to_block`, `is_done`, and `close_block`, which will panic on `Err` from the poisoned pool: [8](#0-7) [9](#0-8) 

The panic-inducing trigger itself would need to be an actual unhandled Rust panic reachable from transaction data rather than a normal `Result::Err` — the codebase contains numerous `panic!`/`unwrap_or_else(|| panic!(...))` guarded overflow checks in fee/gas accounting reachable during transaction execution (e.g. `vm_resource_to_gas_amount`, `GasVector::cost`, `to_discounted_l1_gas`, `Fee::checked_div_ceil`'s internal `.expect(...)`), any of which — if an edge case is missed — would panic inside a worker thread and trigger this fail-fast cascade.

### Impact Explanation
If exploited, a single transaction is sufficient to permanently kill every worker thread in the `WorkerPool`. Because the pool is a batcher-lifetime singleton (not recreated per block), every subsequent block-building attempt (propose or validate) will either hang forever waiting on `wait_for_completion`, or panic when `check_panic()` is invoked, crashing the batcher's block-building task repeatedly. This constitutes a permanent denial-of-service against the sequencer's ability to build or validate new blocks — directly analogous to the reported CVE where a single unhandled exception permanently stops a persistent worker/listener from processing further work, with no recovery short of restarting the batcher process.

### Likelihood Explanation
The likelihood hinges on finding a code path reachable from attacker-controlled transaction/calldata content that hits an *unguarded* Rust panic (as opposed to a `Result::Err`) during concurrent execution inside a worker thread. The codebase shows a defense-in-depth pattern of `checked_*` arithmetic with explicit panics on overflow guarding fee/gas computations, suggesting developers are aware of this risk class and have hardened many of the obvious overflow sites. However, the sheer breadth of the execution path (VM execution, syscalls, gas accounting, Sierra/Cairo native execution) reachable per-transaction means the exhaustiveness of these guards cannot be fully verified from the index alone, and the fail-fast architectural choice (all threads die together, no restart) means even a rare edge case has an outsized, permanent impact.

### Recommendation
- Make `WorkerPool` resilient to individual thread death: respawn a replacement thread when one panics, or automatically create a fresh `WorkerPool` for each new block rather than sharing one pool for the lifetime of the batcher.
- Reconsider the "other threads panic when they observe `a_thread_panicked`" fail-fast design; instead, have the pool cleanly halt the current chunk's scheduler and surface a recoverable error, retaining live worker threads for future blocks.
- Audit and fuzz-test all execution paths reachable from transaction calldata/contract classes for exhaustiveness of `checked_*` arithmetic and other `Result`-based error handling versus raw `panic!`/`.expect()`/`.unwrap()` calls, specifically within `crates/blockifier/src/execution`, `crates/blockifier/src/fee`, and `crates/blockifier/src/bouncer.rs`.

### Proof of Concept
A concrete transaction-triggerable panic path could not be conclusively pinned down within the indexed code (the overflow-guard sites reviewed appear to use `checked_*`/`unwrap_or_else(|| panic!(...))` patterns that are individually well-formed). What is concretely demonstrated is the *architecture-level* vulnerability:
1. Any transaction that causes an uncaught Rust panic inside `WorkerExecutor::run()` on any worker thread will, via the `_run_executor`/`a_thread_panicked` mechanism, cause every other worker thread in the shared `WorkerPool` to panic and terminate as well.
2. Since this `WorkerPool` is created once per batcher (`create_batcher`) and reused for every future block, all subsequent block-building/validation attempts will hang or panic, permanently halting the batcher.
A full working PoC transaction that reaches a specific unguarded panic requires deeper live-testing (e.g. fuzzing blockifier's syscall/VM/native-execution code with adversarial calldata) than is possible from static index review alone — this should be treated as a design-level flag rather than a confirmed exploit primitive, and a Devin session with full repo access and test execution capability would be needed to search for/fuzz a concrete panic-triggering transaction.

impl<S: StateReader + Send + 'static> WorkerPool<S> {
    /// Creates a new WorkerPool with the given stack size and concurrency configuration.
    pub fn start(config: &WorkerPoolConfig) -> Self {
        // Initialize the channels.
        let a_thread_panicked = Arc::new(AtomicBool::new(false));
        let mut senders = Vec::<mpsc::Sender<Option<Arc<WorkerExecutor<S>>>>>::new();
        let mut receivers = Vec::<mpsc::Receiver<Option<Arc<WorkerExecutor<S>>>>>::new();
        for _ in 0..config.n_workers {
            let (sender, receiver) = mpsc::channel();
            senders.push(sender);
            receivers.push(receiver);
        }

        let stack_size = config.stack_size;

        // Run the threads.
        let handlers = receivers
            .into_iter()
            .enumerate()
            .map(|(thread_id, receiver)| {
                let mut thread_builder = std::thread::Builder::new();
                // When running Cairo natively, the real stack is used and could get overflowed
                // (unlike the VM where the stack is simulated in the heap as a memory segment).
                //
                // We pre-allocate the stack here, and not during Native execution (not trivial), so
                // it needs to be big enough ahead.
                // However, making it very big is wasteful (especially with multi-threading).
                // So, the stack size should support calls with a reasonable gas limit, for
                // extremely deep recursions to reach out-of-gas before hitting the
                // bottom of the recursion.
                //
                // The gas upper bound is MAX_POSSIBLE_SIERRA_GAS, and sequencers must not raise it
                // without adjusting the stack size.
                thread_builder = thread_builder.stack_size(stack_size);
                let worker_thread = WorkerThread {
                    a_thread_panicked: a_thread_panicked.clone(),
                    receiver,
                    thread_id,
                };
                thread_builder
                    .spawn(move || worker_thread.run_thread())
                    .expect("Failed to spawn thread.")
            })
            .collect();

        WorkerPool { senders, handlers, a_thread_panicked }
    }

    /// Runs a single worker executor.
    fn _run_executor(&self, worker_executor: &WorkerExecutor<S>) {
        if self.a_thread_panicked.load(Ordering::Acquire) {
            panic!("Another thread panicked. Aborting.");
        }

        // Making sure that the program will abort if a panic occurred while halting
        // the scheduler.
        let abort_guard = AbortIfPanic;
        // If a panic is not handled or the handling logic itself panics, then we
        // abort the program.
        let res = panic::catch_unwind(panic::AssertUnwindSafe(|| {
            worker_executor.run();
        }));
        if let Err(err) = res {
            // First, set the panic flag. This must be done before halting the scheduler.
            self.a_thread_panicked.store(true, Ordering::Release);

            // If the program panics here, the abort guard will exit the program.
            // In this case, no panic message will be logged. Add the cargo flag
            // --nocapture to log the panic message.

            worker_executor.scheduler.halt();
            abort_guard.release();
            panic::resume_unwind(err);
        }

        abort_guard.release();
    }
