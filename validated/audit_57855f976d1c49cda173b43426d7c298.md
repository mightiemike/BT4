### Title
Permanent Burning of Deleted-Account Funds via Unchecked `beneficiary_id` in `DeleteAccountAction` - (File: `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccount` refunds an account's remaining balance to `beneficiary_id` by creating a `Receipt::new_balance_refund`, but validation of that field only checks that it is a *syntactically* valid `AccountId` string — never that the account actually exists. If a signer mistypes (or otherwise sets incorrectly) the `beneficiary_id` to a syntactically valid but non-existent account, the resulting balance-refund receipt fails with `AccountDoesNotExist`, and because refund receipts are "free" (system-predecessor) receipts, the failed refund's deposit is burned rather than returned to the deleting account or anyone else. This mirrors the reported Tokemak bug class: a "send funds to recipient" code path that checks for one narrow bad case (self-transfer / contract address) but omits the broader "recipient doesn't/can't receive" case (zero address), leading to unrecoverable token loss.

### Finding Description
When a `DeleteAccountAction` executes, `action_delete_account` computes the account's balance and, if positive, unconditionally emits a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)`: [1](#0-0) 

The only pre-execution validation of `beneficiary_id` is `validate_delete_action`, which calls `validate_action_account_id`, itself just `AccountId::validate(...)` — a syntax check with no existence check: [2](#0-1) [3](#0-2) 

The runtime execution spec documents that once the receiver account for a refund receipt does not exist, the refund fails, and specifically that a failed refund's deposit is burned instead of refunded because refund/system-predecessor receipts are treated as "free": [4](#0-3) [5](#0-4) 

This is directly demonstrated by the existing unit test `refund_may_not_create_universal_account`, which shows that a `Receipt::new_balance_refund` sent to a non-existent account fails with `ActionErrorKind::AccountDoesNotExist` and the account is never created/credited: [6](#0-5) 

Compare this to `test_delete_account_no_account`, which only tests the case where the *deleted* account itself doesn't exist (an unrelated check), not the case where the `beneficiary_id` doesn't exist: [7](#0-6) 

The parallel to the reported bug is precise: the Tokemak contract checked only `sendTo != address(this)` but not `sendTo != address(0)`, allowing an incorrectly-set recipient to permanently burn rewards. Here, `action_delete_account`/`validate_delete_action` check only that `beneficiary_id` parses as a syntactically valid AccountId, but never that the account exists or is reachable, allowing an incorrectly-set (e.g., mistyped, never-created, or already-deleted) `beneficiary_id` to permanently burn the deleted account's entire remaining NEAR balance. Unlike a standard `Transfer` action to a non-existent named account (which fails the whole receipt/transaction and preserves the sender's balance because the transfer never leaves the origin account), a `DeleteAccount` beneficiary failure is different in kind: the source account has already been irreversibly removed (`*account = None;` at line 404) by the time the refund receipt is dispatched, so there is no longer any account to roll the funds back to — the deletion and the (possibly failing) payout are decoupled across two separate receipts/state transitions.

### Impact Explanation
Any unprivileged account holder can lose their entire remaining NEAR balance by submitting a `DeleteAccount` transaction with an incorrect `beneficiary_id` (e.g., a name that is spelled correctly but was never registered, or an account that gets deleted in the same chunk before the refund lands). The funds are not returned to the sender and not credited to anyone; they are permanently burned out of circulation. This is a supply-reducing, unauthorized-value-loss bug reachable by any single signed transaction from a normal account — matching the "permanently frozen/lost funds" impact class called out in the validation rules.

### Likelihood Explanation
Likelihood is moderate: users must supply an incorrect (but syntax-valid) `beneficiary_id`. This is a realistic operational mistake (typos, referencing an account that was deleted or never created, or programmatically supplying a bad value from client tooling/wallets), and no additional privilege or attacker coordination is needed — a single, ordinary `DeleteAccountAction` from any signer can trigger it deterministically.

### Recommendation
Before creating the balance-refund receipt in `action_delete_account`, verify (or make the resulting refund failure recoverable) that `beneficiary_id` corresponds to an existing account, or alternatively change the failure semantics of `Receipt::new_balance_refund` for `DeleteAccount`-initiated refunds so a failed refund is preserved (e.g., redirected to a well-known treasury/burn-tracked account, or the delete action itself is required to validate beneficiary existence before removing the source account) rather than silently burning the deposit through the generic "refund receipts are free" path.

### Proof of Concept
1. Create account `alice.near` with balance N.
2. Submit `SignedTransaction` from `alice.near` with `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent.near" })` where `nonexistent.near` was never created.
3. `action_delete_account` (`runtime/runtime/src/actions.rs:380-386`) removes `alice.near` (`*account = None`) and emits `Receipt::new_balance_refund(&"nonexistent.near", N)`.
4. When that refund receipt is processed, `nonexistent.near` does not exist, so it fails with `ActionErrorKind::AccountDoesNotExist` (as reproduced by the existing test `refund_may_not_create_universal_account` at `runtime/runtime/src/tests/apply.rs:6880-6926`, which uses the same `Receipt::new_balance_refund` mechanism against a missing account).
5. Because the refund is a system/refund receipt, its failure burns the deposit (per `protocol-model/spec/runtime-execution.md:152`) instead of returning it — `alice.near`'s entire balance N is permanently lost.

        let result = runtime
            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,

                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);

        // Assert on the reason, not just the absence: without this the test would

        );
