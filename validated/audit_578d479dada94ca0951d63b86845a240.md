### Title
Exchange (Bancor-style AMM) liquidity withdrawal lacks minimum-return protection, enabling sandwich attacks - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawActuator`, which processes user-broadcast `ExchangeWithdrawContract` transactions against java-tron's built-in Bancor-formula token exchange, computes the counter-token amount to return purely from the exchange pool's *current* on-chain balances at execution time, with no caller-supplied minimum-return ("expected") parameter to bound slippage. This mirrors exactly the reported bug class: a swap/liquidity operation against an AMM-like market that omits a minimum-return check, allowing a third party to sandwich the operation and extract value.

### Finding Description
The `ExchangeTransactionContract`/`ExchangeTransactionActuator` swap path *does* include slippage protection: the protobuf message carries an `expected` field [1](#0-0) , and `doValidate()` rejects the trade if the computed output is less than the caller-specified minimum: `if (anotherTokenQuant < tokenExpected) { throw new ContractValidateException("token required must greater than expected"); }` [2](#0-1) .

By contrast, `ExchangeWithdrawContract` has no such field — only `owner_address`, `exchange_id`, `token_id`, and `quant` [3](#0-2) . `ExchangeWithdrawActuator.execute()` derives the counter-token amount solely from the pool's live balances at execution time: `anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance).longValueExact();` (or the symmetric branch) [4](#0-3) . The only validation in `doValidate()` re-derives the *same* ratio from the *same* live balances and checks it is "precise enough" against itself (a rounding-consistency check, not an economic slippage bound) [5](#0-4) . There is no way for the withdrawer to specify "I will not accept less than X of the counter token."

Any unprivileged party can submit `ExchangeInjectContract`/`ExchangeTransactionContract` transactions that alter `firstTokenBalance`/`secondTokenBalance` of the target exchange pool immediately around the pending withdraw transaction (front-run then back-run within the same or adjacent blocks), manipulating the pool ratio at the moment the withdrawal is priced, then reversing the trade afterward to capture the value extracted from the withdrawer — a classic sandwich/liquidity-removal attack, analogous to the reported Curve-swap-without-minReturn issue.

### Impact Explanation
This falls squarely within "exchange/market math" — an in-scope actuator state-transition category. An attacker who can observe a pending `ExchangeWithdrawContract` (e.g., in the transaction pool) can manipulate the pool's balance ratio before it executes and reverse the manipulation afterward, extracting value from the exchange creator withdrawing liquidity, with no slippage guard to stop the transaction from executing at a manipulated price. This is a concrete "asset/accounting corruption via leaked value" impact, consistent with the judged severity of the referenced finding (medium — "allows leaking value").

### Likelihood Explanation
Reachable directly from a normal broadcast transaction (`ExchangeWithdrawContract`) with no special privilege required by the attacker (only ordinary `ExchangeTransactionContract`/`ExchangeInjectContract` transactions against the same `exchange_id`); the exchange/withdraw functionality is a long-standing, actively used core feature (`wallet/exchangewithdraw` API), so the attack surface is continuously exposed whenever a creator withdraws.

### Recommendation
Add an `expected`/minimum-return field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` so a withdrawer can bound the acceptable counter-token amount, rejecting the transaction if the pool state at execution yields less than the specified minimum.

### Proof of Concept
1. Exchange pool has balances `firstTokenBalance`, `secondTokenBalance`.
2. Creator broadcasts `ExchangeWithdrawContract` to withdraw `tokenQuant` of `firstTokenID`, expecting a proportional `anotherTokenQuant` of `secondTokenID` based on current ratio.
3. Attacker observes the pending withdraw, submits an `ExchangeTransactionContract` swap that shifts the pool ratio unfavorably for the withdrawer, ordered immediately before the withdraw executes.
4. `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from the now-manipulated balances at lines 74-89, with no `expected` bound to reject the unfavorable outcome — the creator receives a diminished payout.
5. Attacker submits a reversing `ExchangeTransactionContract` afterward to restore the pool ratio and realize profit, completing the sandwich. [6](#0-5) [7](#0-6)
