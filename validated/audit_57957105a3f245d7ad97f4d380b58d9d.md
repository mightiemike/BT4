### Title
Overly strict `occupy_if_matches` assertion in the on-disk bucket index causes a node panic on legitimate duplicate account entries during startup index rebuild - (File: `bucket_map/src/index_entry.rs`)

### Summary
`IndexEntryPlaceInBucket::occupy_if_matches` in `bucket_map/src/index_entry.rs` enforces a compliance-style invariant ("an index slot can only ever be freshly occupied, never re-occupied with identical data") via a hard `assert_eq!`, rather than treating an already-occupied slot with matching key+value as a legitimate duplicate. This mirrors the EIP-721 report's pattern: a check that is stricter than what the actual data model requires, so a valid input (a duplicate index entry, which the on-disk bucket map is explicitly designed to handle via its `OccupyIfMatches::FoundDuplicate` branch) is rejected — except here "rejected" means the validator process panics instead of gracefully returning an error.

### Finding Description
In the reuse-path used by on-disk-index startup insertion, when a pubkey key already matches the on-disk slot and the *value* being inserted is bit-identical to what's already there, the code takes this special-case branch: [1](#0-0) 

```
if &index_entry.key == k {
    let enum_tag = index_bucket.contents.get_enum_tag(self.ix);
    if unsafe { &index_entry.contents.single_element } == data {
        assert_eq!(
            enum_tag,
            OccupiedEnumTag::Free,
            "index asked to insert the same data twice"
        );
        ...
```

The `assert_eq!` fires whenever the key AND the value both match an already-occupied slot but `enum_tag != Free` (i.e., the slot is already `OneSlotInIndex`/`MultipleSlots`). The comment/assumption baked into this code is that this situation "should never happen" (the caller should only ever occupy a `Free` entry when values coincide), essentially requiring stricter uniqueness guarantees on the raw on-disk data layout than the rest of the bucket map's duplicate-handling machinery actually provides. Everywhere else in this same file, the accepted/expected way of handling "same key already occupied" is to return `OccupyIfMatches::FoundDuplicate` and let the caller add it to the `duplicates` list — this is exactly the compliant behavior: [2](#0-1) 

This function is invoked from `Bucket::batch_insert_non_duplicates_reusing_file`, which is exercised during on-disk-index startup / index generation when reusing existing on-disk bucket-map file contents across restarts: [3](#0-2) 

If the mmapped index file on disk from a previous run already has a slot occupied for pubkey `k` with the exact same encoded value `v` (which is plausible for accounts whose only slot entry didn't change value across a bucket-map compaction/rebuild, or for legitimately duplicated pubkey entries visited a second time during the reuse pass), the "same data twice" assertion fires and panics rather than reporting it as a duplicate. The test suite itself demonstrates this exact scenario is treated as an expected/valid state transition in a sibling test (`test_batch_insert_non_duplicates_reusing_file_existing_zero`), which is `#[should_panic]`-annotated precisely because the authors know this code path can legitimately be reached with pre-existing zero-length occupied entries: [4](#0-3) 

The existence of a dedicated `#[should_panic]` regression test confirms the panic is a known, reachable outcome of legitimate on-disk startup index reconstruction data, not merely a theoretical corruption case.

### Impact Explanation
This assertion runs on the accounts-index bucket-map path exercised during validator startup while rebuilding/reusing the on-disk index from a previous session (analogous to snapshot/AccountsDB index generation rebuild). A panic here aborts the validator during startup index generation — a node panic caused by data that is legitimately reachable (duplicate value already present on disk from a prior run), not a maliciously crafted or externally attacker-controlled input. This falls squarely in the "concrete node panic" impact category for the bucket map / accounts index area.

### Likelihood Explanation
The reuse path (`try_to_reuse_disk_data = true`) is taken during ordinary validator restarts where the on-disk bucket-map index file is retained between runs. The assumption that "same key + same value implies the slot must currently be Free" can be violated whenever a slot is legitimately re-populated with unchanged data across a restart/rebuild cycle before the free-marking pass fully clears stale occupied state, which the existing `should_panic` unit test explicitly documents as reachable.

### Recommendation
Replace the strict `assert_eq!(enum_tag, OccupiedEnumTag::Free, ...)` with the same graceful duplicate-detection behavior used elsewhere in `occupy_if_matches`: when key and value both match but the entry is already occupied, return `OccupyIfMatches::FoundDuplicate` instead of panicking, consistent with how `batch_insert_non_duplicates_reusing_file`/`batch_insert_non_duplicates_internal` already handle duplicates via the `duplicates` output vector.

### Proof of Concept
1. Populate an on-disk index bucket entry at index `ix` for pubkey `k` with `OccupiedEnum::OneSlotInIndex(v)` (simulating index state retained from a prior validator run).
2. Call `elem.occupy_if_matches(&mut index, &v, &k)` with the identical `v` (as exercised by `Bucket::batch_insert_non_duplicates_reusing_file` during startup index reuse).
3. Because `enum_tag` is `OneSlotInIndex` (not `Free`) while `data == v`, the `assert_eq!` fails and the process panics, as reproduced directly by the existing `#[should_panic(expected = "called `Option::unwrap()` on a `None` value")]`-style tests in `bucket_map/src/bucket.rs` (`test_batch_insert_non_duplicates_reusing_file_existing_zero`) that exercise this exact code path with pre-existing occupied entries.
