## Analysis

I traced the report's core invariant — "an operation that must be checked/ordered is silently skipped or reordered, breaking a downstream integrity guarantee" — to a concrete analog in the state-checkpoint verification path used by the replay-verify tooling.

### Title
Replay-verify's `ensure_match_transaction_info` silently ignores authenticated checkpoint hashes, letting corrupted/divergent state pass verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function `db-tool`'s `replay_on_archive` verifier uses to decide whether freshly re-executed output matches the consensus-committed, signature-authenticated `TransactionInfo` for a version. It compares status, gas, write-set hash, and event-root hash, but explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — fields that are part of the consensus-signed `TransactionInfoV1` and represent the authenticated state/hot-state/native-position Merkle roots.

### Finding Description [1](#0-0) 

The function builds an `ERR_MSG` comparator that checks `status`, `gas_used`, `write_set_hash` (against `state_change_hash`) and `event_root_hash`, but the code's own comment admits the gap:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This is the sole call site of `ensure_match_transaction_info`: [3](#0-2) 

`execute_and_verify` calls `AptosVMBlockExecutor::execute_block` against archived input transactions, then calls `ensure_match_transaction_info(version, &expected_txn_infos[idx], ...)` — if it returns `Ok(())`, the transaction is treated as verified and dropped from the failure list. Because the comparator omits `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, any divergence in the (authenticated, consensus-signed) checkpoint Merkle roots — the state root, hot-state root, or the new native-position state root introduced by `TRADING_NATIVE`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` features (`aptos-move/framework/move-stdlib/sources/configs/features.move` lines 949-955, `execution/executor-types/src/execution_output.rs` lines 196-202) — is invisible to this check. [4](#0-3) 

### Impact Explanation
The replay-verify tool exists specifically to catch state-commitment divergence (including hard-fork/consensus-bug classes) between archived, consensus-certified `TransactionInfo` and independently re-executed VM output — exactly the "replay/restore/proof-verification divergence" class called out in scope. Because the comparator drops the checkpoint-hash fields, a local execution bug, storage corruption, or non-determinism specifically affecting the state root, hot-state root, or the newly-added native-position state root will be reported as a passing replay even though the actual Merkle root committed by validators has silently diverged from what fresh execution produces. This defeats the primary safety net meant to detect exactly this class of error before it reaches/affects mainnet nodes relying on this tool, and it specifically undermines confidence in the new trading-native state root feature that the comment calls out by name.

### Likelihood Explanation
The gap is unconditional — it fires every time `replay_on_archive` is run, regardless of whether the trading-native features are enabled, since `ensure_match_transaction_info` never inspects those fields at all. No attacker action is required to trigger the missing check; it is a straightforward correctness/verification gap that will mask any real divergence bug in state-checkpoint computation the moment one occurs. The code's own inline TODO acknowledges the bug is real and unaddressed.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `self`'s locally recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in the `TransactionOutput`/execution result) against the corresponding fields on `txn_info`, returning an error on mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` or `TRANSACTION_INFO_V1`-dependent checkpoint hashing is relied upon in production replay-verify workflows.

### Proof of Concept
1. Enable `TRANSACTION_INFO_V1` and `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (or just rely on normal `state_checkpoint_hash`).
2. Introduce (or naturally hit) a bug that makes locally re-executed state, hot-state, or native-position Merkle root diverge from the archived/committed `TransactionInfo`'s checkpoint hash while write-set/events/status/gas remain identical (e.g., a non-deterministic ordering bug only affecting the position tree, or a corrupted archive that preserved write set bytes but not the root).
3. Run `db-tool replay-on-archive` over that version range.
4. `execute_and_verify` calls `ensure_match_transaction_info`, which returns `Ok(())` because it never checks the checkpoint hash fields, so the transaction is silently marked verified and the divergence is never reported despite the ledger's authenticated state root differing from what fresh execution computes.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
