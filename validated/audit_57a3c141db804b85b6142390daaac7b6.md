### Title
Unprivileged CEA inbound with an invalid `Recipient` permanently strands bridged funds with no revert or admin recovery path - (File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go, x/uexecutor/keeper/execute_inbound_gas_and_payload.go)

### Summary
Both `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload` handle "CEA" inbounds (`IsCEA=true`, an explicit `Recipient`) with a documented three-way branch: UEA recipient, deployed-contract recipient, or "neither." When the supplied `Recipient` is not a syntactically valid hex address, the code sets `execErr` *before any PRC20 deposit is attempted*, and the comment explicitly states "isCEA failures never create an INBOUND_REVERT outbound." [1](#0-0) [2](#0-1)  The inbound has already passed validator-ballot consensus and the `UniversalTx` has already been created before this execution path runs, so the funds that were deposited on the source chain (the CAIP-2 gateway/vault) are never minted as PRC20 on Push Chain, and no revert outbound is scheduled to send them back. This mirrors the reported `RestrictedTokenAward` bug class: a "termination" event (validation failure) that occurs before the equivalent of "vesting start" (successful PRC20 deposit) leaves funds permanently unreachable, because the code path that would normally create a refund/revert is skipped for `IsCEA` inbounds.

### Finding Description
The lifecycle for a CEA inbound is: a validator quorum votes `PASSED` on `MsgVoteInbound`, a `UniversalTx` is created, and then `ExecuteInboundFundsAndPayload` / `ExecuteInboundGasAndPayload` run the actual PC-side execution [3](#0-2) . Inside that execution, for `IsCEA=true` inbounds the code performs:

```
if !strings.HasPrefix(strings.ToLower(utx.InboundTx.Recipient), "0x") {
    execErr = fmt.Errorf("recipient must be a valid hex address when isCEA is true")
} else { ... deposit paths ... }
// isCEA failures never create an INBOUND_REVERT outbound.
``` [1](#0-0) 

The identical pattern exists in the gas-and-payload variant, which additionally has an explicit early-return that skips the revert-creation branch for isCEA failures:
```
// --- create revert ONLY for pre-deposit / deposit failures (non-isCEA path)
if execErr != nil && shouldRevert { ... }
// isCEA failures: record FAILED PCTx but no revert
if execErr != nil && utx.InboundTx.IsCEA {
    return nil
}
``` [4](#0-3) 

`Recipient` is a field decoded from the source-chain event supplied by whoever submitted the deposit transaction on the external gateway; it is user-controlled and reaches this code path unmodified by any earlier per-field format check, since `ValidateForExecution`/`ValidateBasic` gate on other fields (source chain, tx hash, amount, etc.) rather than proving `Recipient` is hex-well-formed for the CEA path before consensus. Once the ballot has reached `PASSED` and the UTX exists, the only revert mechanisms in the codebase are:
1. The inline `shouldRevert` path used only for the *non-isCEA* branch, and
2. The admin-only `RevertStuckInbound` escape hatch, which has a **strict precondition that the ballot status is `EXPIRED`**:
```
if ballot.Status != uvalidatortypes.BallotStatus_BALLOT_STATUS_EXPIRED {
    return "", "", errors.Wrap(...)
}
``` [5](#0-4) 

Because the ballot for this inbound already reached `PASSED` (that is how execution got triggered at all), it can never be `EXPIRED`, so the admin escape hatch is structurally inapplicable to this failure mode. The general failed-validation revert helper (`handleFailedInboundValidation`) does create a revert for non-isCEA inbounds but explicitly documents that isCEA failures are excluded: "isCEA failures never create an INBOUND_REVERT outbound (consistent with execute_inbound_funds_and_payload.go)" [6](#0-5) .

### Impact Explanation
An unprivileged user who deposits real assets on a source-chain gateway (e.g. ETH/SOL/PRC20-backing token) can craft the inbound event with `IsCEA=true` and a malformed/non-hex `Recipient` (e.g. empty string, wrong-length string, non-hex characters). Honest universal validators faithfully observe and vote this inbound to `PASSED` — no malicious validator behavior is required. Push Chain then creates the `UniversalTx`, attempts execution, and immediately fails on the `Recipient` hex check with `execErr` set and no deposit performed and no revert outbound scheduled. The source-chain funds remain locked in the external vault/gateway forever: no PRC20 is minted on Push Chain, and no `INBOUND_REVERT` outbound is ever created to send them back, and the sole admin recovery mechanism (`RevertStuckInbound`) categorically cannot apply because it requires an `EXPIRED` ballot, not a `PASSED` one. This is a permanent, protocol-level freezing of user funds triggered purely by unprivileged, ordinary transaction submission — squarely within the "In scope" impact of "permanent freezing ... of user or protocol-controlled funds" reachable via "ordinary user deposits."

### Likelihood Explanation
High. No privileged action, validator collusion, or timing race is required — a single user constructing a slightly malformed `Recipient` string while setting `IsCEA=true` on their inbound deposit is sufficient. The trigger is deterministic and requires only knowledge of the public inbound/UTX schema (documented in `x/uexecutor/README.md`) and control over the payload fields decoded from the gateway event.

### Recommendation
For the "neither" (invalid `Recipient`/no matching UEA or contract) branch of the CEA handling in both `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload`, always attach an `INBOUND_REVERT` outbound (via `buildRevertOutbound`/`attachOutboundsToUtx`, the same helper already used for the non-isCEA failure path) instead of silently returning `nil`. Alternatively, reject inbounds with `IsCEA=true` and a non-hex `Recipient` during ballot voting/`ValidateForExecution`, before consensus finalizes the UTX, so the failure is caught pre-finalization rather than post-consensus with no recovery path. Additionally, consider relaxing `RevertStuckInbound`'s precondition (or adding a parallel admin path) to cover `PASSED`-then-execution-failed CEA inbounds, since currently no recovery mechanism exists for this state at all.

### Proof of Concept
1. On a supported source chain, submit a deposit through the gateway contract that decodes into an `Inbound` with `IsCEA = true` and `Recipient = ""` (or any string not prefixed with `0x`), along with a nonzero `Amount`.
2. Honest universal validators observe the event and submit `MsgVoteInbound` votes; quorum is reached and the ballot transitions to `PASSED`, creating the `UniversalTx` (`InboundTx` populated, no `OutboundTx`/`PcTx` yet).
3. The keeper invokes `ExecuteInboundFundsAndPayload` (or `ExecuteInboundGasAndPayload`), which hits:
   `if !strings.HasPrefix(strings.ToLower(utx.InboundTx.Recipient), "0x") { execErr = ... }` [7](#0-6) 
4. A `FAILED` `PCTx` is recorded on the UTX, but per the code path (and explicit comment "isCEA failures never create an INBOUND_REVERT outbound"), no PRC20 deposit and no revert outbound occur.
5. Attempt `RevertStuckInbound` as admin: it fails immediately because `ballot.Status == BALLOT_STATUS_PASSED`, not `EXPIRED` [5](#0-4) .
6. Result: source-chain funds are irrecoverably stuck — no PRC20 minted, no revert, no admin path.

Note: I was not able to fully verify (within available context) whether `ValidateForExecution`/vote-time validation performs any additional hex-format check on `Recipient` for CEA inbounds prior to ballot finalization — the `x/uexecutor/types/inbound.go` validation logic was only partially inspected. If such a check does exist and rejects malformed `Recipient` values *before* the ballot can reach `PASSED`, this specific trigger would be blocked earlier in the pipeline and the finding would need re-scoping to whatever inputs can still reach the isCEA/"neither" branch post-consensus (e.g., a syntactically valid but non-existent hex address whose UEA-check call errors for other reasons). I'd recommend a Devin session with full repository access to confirm the exact `ValidateForExecution` gating for `Recipient` in the isCEA case before finalizing severity.

### Lifecycle Walkthrough

A typical `FUNDS_AND_PAYLOAD` inbound, end to end:

```
1. UV observes a source-chain gateway event.
2. UV submits MsgVoteInbound. The UTX is created the moment the first vote
   arrives, with id = sha256(sourceChain:txHash:logIndex). Only the
   InboundTx field is populated; PcTx and OutboundTx are empty.
   (UTX id is also added to PendingInbounds.)

3. Threshold of UV votes reached. The keeper executes the inbound:
   a. Mints the PRC20 to the recipient's UEA address.
      A new PCTx (deposit) is appended to UTX.PcTx.
   b. Runs the universal payload through the UEA.
      A second PCTx (executeUniversalTx) is appended.
   (UTX id removed from PendingInbounds.)

4. The payload triggered a destination-chain call (e.g. release funds on
   another chain). An OutboundTx is created with Status_PENDING and
   appended to UTX.OutboundTx. It is also indexed in PendingOutbounds.

5. UVs sign the outbound via TSS, broadcast it, and vote the result back
   via MsgVoteOutbound. The OutboundTx.observed_tx is filled in and
   outbound_status flips to OBSERVED. The PendingOutbounds entry is
   removed.

6. If the destination chain refunds excess gas, a refund PCTx runs on
   Push Chain. PCTx.pc_refund_execution is set on the OutboundTx. The
   refund is just additional evidence attached to the existing OutboundTx.
```
