## Title
`ensure_match_transaction_info` skips checkpoint-hash validation, letting replay-verify accept a divergent state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated invariant-check used by replay/verification tooling (e.g. `storage/db-tool/src/replay_on_archive.rs`) to confirm that a freshly re-executed `TransactionOutput` matches the committed `TransactionInfo` from an authenticated backup/archive. It checks status, `gas_used`, the write-set hash, and the event root hash, but it explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — a gap the code itself documents as a TODO. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` is meant to be the single point that proves a locally computed `TransactionOutput` is consistent with the `TransactionInfo` that was authenticated (via signatures/accumulator proof) from a backup or archive during replay-verify: [2](#0-1) 

It validates:
- execution status vs. `txn_info.status()`
- `gas_used` vs. `txn_info.gas_used()`
- `write_set_hash` vs. `txn_info.state_change_hash()`
- `event_root_hash` vs. `txn_info.event_root_hash()`

It never compares the computed state-checkpoint hash (the Sparse-Merkle/JMT state root after applying the write set) against `txn_info.state_checkpoint_hash()`, nor the hot-state checkpoint hash, nor (with `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) the position-state checkpoint hash. The comment left in the code acknowledges this directly: [3](#0-2) 

Because `TransactionInfo` is what is hashed into the transaction accumulator and ultimately signed by validators in the `LedgerInfo`, `state_checkpoint_hash` is the authenticated commitment to the *entire post-execution ledger state* at that version — not a peripheral field. Skipping it means a `TransactionOutput` whose write set replays to a different state root than what was actually committed (due to a storage bug, a non-deterministic bug in state-checkpoint computation, a JMT/hot-state corruption, or a malicious archive that supplies a tampered `TransactionInfo` with a correct write-set hash but wrong checkpoint hash) is reported as "matching" by this function.

### Impact Explanation
Any caller relying on `ensure_match_transaction_info` to authenticate that replayed execution reproduces the exact committed ledger state (state root) will not detect a divergence limited to the state-checkpoint hash. This is a real state-commitment integrity gap under this task's scope ("Committed state that differs from the correct VM result... Hard-fork-only divergence during... replay"). It is used by `storage/db-tool/src/replay_on_archive.rs` (the mainnet replay-verify tool used to validate archived history against re-execution) and by `aptos-move/aptos-debugger` / `aptos-move/cli`, so a genuine state-root divergence introduced anywhere in the storage/executor stack (e.g., an SMT/hot-state/position-state bug) could pass replay-verify undetected, since only write-set and event hashes are checked, not the resulting root.

I could not fully confirm the exact severity because I was unable to inspect, within the remaining iterations, how `replay_on_archive.rs` uses the return value of `ensure_match_transaction_info` end-to-end (e.g., whether it independently cross-checks state roots elsewhere, or whether this is the sole invariant relied upon). This should be verified before final severity/impact classification.

### Likelihood Explanation
The gap is unconditionally present for all state/hot-state checkpoint hashes today (not gated behind a flag), and is explicitly enabled to remain latent for `position_state_checkpoint_hash` specifically "before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS" per the comment — implying the authors already intend to add this check before that feature ships, but the `state_checkpoint_hash`/`hot_state_checkpoint_hash` omission has no such guard and is live now. Triggering it does not require any privileged access: any bug elsewhere in state-checkpoint computation, or any archive/backup source that is not fully trusted, will silently pass this specific verification path.

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality between the locally computed state-checkpoint hash (and hot-state / position-state checkpoint hash when applicable) and the corresponding fields on `txn_info`, mirroring the pattern already used for `write_set_hash` and `event_root_hash`, before removing or downgrading its reliance in replay/verify tooling.

### Proof of Concept
Not independently reproduced with a runnable exploit in this session (read-only investigation). The structural proof is the source itself:
1. `ensure_match_transaction_info` compares status, gas, write-set hash, and event-root hash only. [2](#0-1) 
2. The trailing comment explicitly documents that checkpoint hashes are ignored and that replay-verify tooling can therefore report success even when the position/state root diverges. [3](#0-2) 
3. This function is invoked from the mainnet replay-verify CLI path (`storage/db-tool/src/replay_on_archive.rs`), `aptos-debugger`, and `cli/commands.rs`, none of which were confirmed (within available time) to perform an independent state-root cross-check that would compensate for this gap. [4](#0-3) 

**Caveat**: Given the self-documenting TODO and the fact I could not trace every downstream consumer's full verification logic in the time available, this should be treated as a confirmed *code-level gap* whose full exploitability (i.e., whether any other check currently compensates) needs a follow-up review before treating it as an unconditionally critical, unmitigated issue.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
