## Analog Found: Receipts can grow past `max_receipt_size` after validation, bypassing the size gate that other code paths rely on to guarantee forward progress

### Title
Post-validation mutation lets a receipt exceed `max_receipt_size`, bypassing the size limit enforced elsewhere in congestion/bandwidth control - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/verifier.rs`)

### Summary
`validate_receipt` enforces `receipt_size <= max_receipt_size` only for `ValidateReceiptMode::NewReceipt`, checked right after a receipt is produced by `apply_action`. [1](#0-0)  But the runtime subsequently *mutates* that already-validated receipt by appending `output_data_receivers` from the calling receipt (the `promise_return`/`value_return` path), which is done **after** the size check has already run, so the final on-chain receipt can be larger than `max_receipt_size` without any further validation. [2](#0-1)  The `ValidateReceiptMode::ExistingReceipt` mode explicitly documents that it must tolerate such oversized receipts because of this bug, referencing issue #12606. [3](#0-2) 

This is structurally the same root cause pattern as the reported Bond `FixedStrikeOptionTeller` bug: a validation check is computed once against an input value, but a later derived/mutated value (the strike price's decimal count there; the receipt's final byte size here) is not re-validated against the same bound, so an operation that should always be constrained by the check can silently produce an out-of-bound artifact that other code then has to special-case forever.

### Finding Description
`validate_receipt(mode=NewReceipt)` is called immediately after `apply_action` produces `new_receipts`, checking `borsh::object_length(receipt) <= max_receipt_size`. [4](#0-3)  `runtime/runtime/src/verifier.rs" start="680" end="696" />

Immediately afterward, in `apply_action_receipt`, if the *current* receipt (the one being executed, i.e., the predecessor of the new receipt) has `output_data_receivers`, and the action's result is `ReturnData::ReceiptIndex`, the runtime extends the **already-validated** new receipt's `output_data_receivers` with the current receipt's own `output_data_receivers` list: [5](#0-4) 

This mutation happens strictly after the size check on that same receipt, so a contract can construct a receipt whose args/actions fill it up to exactly `max_receipt_size`, then use `promise_return`/`promise_then` chaining so that the runtime appends extra `DataReceiver` entries onto it post-validation, pushing the final serialized receipt over the limit — with no subsequent size check. The same class of gap applies to `value_return`, where the returned value is wrapped into a `Data` receipt that is only checked by `validate_data_receipt` for `max_length_returned_data`, not against `max_receipt_size` as a whole receipt. [6](#0-5) 

This is a known, acknowledged issue in the codebase (nearcore#12606), with dedicated regression tests demonstrating it is still reachable via ordinary contract calls: `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` both document "The receipt should be rejected, but currently isn't because of a bug" and assert that an oversized receipt actually occurs. [7](#0-6) [8](#0-7) 

Because oversized receipts must then be persisted and forwarded, the congestion-control and bandwidth-scheduler layers contain explicit workarounds treating any receipt above `max_receipt_size` as if it were exactly `max_receipt_size` for admission/limit purposes, precisely to avoid them getting permanently stuck in the outgoing buffer: [9](#0-8) 

### Impact Explanation
An unprivileged contract caller (any transaction signer with a deployed contract) can, via ordinary `promise_then`/`promise_return` chaining or `value_return`, cause the runtime to construct and commit to state a receipt whose serialized size exceeds the protocol-configured `max_receipt_size` limit — a limit that `validate_receipt`/`ValidateReceiptMode::NewReceipt` is supposed to strictly enforce for every newly created receipt. This is a state-transition-invariant violation: the size bound that other subsystems (congestion control, bandwidth scheduler, storage-proof/witness sizing) implicitly rely on as unconditionally true for "new" receipts is not actually true, forcing those subsystems to carry permanent special-case workarounds (`ValidateReceiptMode::ExistingReceipt`, the `try_forward` clamp) rather than being able to assume the invariant. This is a systemic robustness/invariant-integrity issue reachable by any contract deployer/caller, not a validator- or operator-only condition.

### Likelihood Explanation
High likelihood of triggering: it requires only a standard contract deployment plus a `promise_then`/`promise_return` chain or a large `value_return`, both of which are demonstrated end-to-end by the existing repository test suite (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`) using the standard test contract's helper methods and asserting the oversized-receipt condition actually occurs on the current codebase. [10](#0-9) [11](#0-10)  No special privileges, network position, or validator role are required — it is fully reachable from a normal RPC-submitted transaction.

### Recommendation
Re-run (or move) the `max_receipt_size` check in `validate_receipt`/`ValidateReceiptMode::NewReceipt` to occur *after* the `output_data_receivers` mutation in `apply_action_receipt` (i.e., validate the receipt's final byte size once all post-processing/mutation of `new_receipts` is complete), or reject/truncate the operation that would push an already-size-validated receipt over the limit at the point of mutation (`runtime/runtime/src/lib.rs:1152-1191`), rather than only validating the pre-mutation receipt. Once this is fixed, the `ValidateReceiptMode::ExistingReceipt` workaround and the congestion-control size-clamp for oversized receipts can be scoped strictly to genuinely pre-existing state rather than to receipts producible under the current protocol version.

### Proof of Concept
The repository's own test-loop tests are a working PoC against the current tree:
1. `test_max_receipt_size_promise_return` deploys the standard test contract, then calls `max_receipt_size_promise_return_method1` with `args_size` sized so that promise `C`'s action receipt is exactly `max_receipt_size` bytes; `promise_return` inside the callback causes the runtime to append the caller's `output_data_receivers` to receipt `C` post-validation, pushing it over the limit. `assert_oversized_receipt_occurred` confirms the oversized receipt is produced and persisted rather than rejected. [12](#0-11) 
2. `test_max_receipt_size_value_return` calls `max_receipt_size_value_return_method`, which triggers `return_large_value` to `value_return` a buffer of size `max_receipt_size`; the resulting `Data` receipt (value + wrapping overhead) exceeds `max_receipt_size` and is likewise not rejected. [11](#0-10) [13](#0-12) 

Both tests are explicitly annotated in-source as demonstrating "the bug" (nearcore#12606) rather than a fixed/mitigated condition.

/// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

/// Validates given data receipt. Checks validity of the length of the returned data.
fn validate_data_receipt(
    limit_config: &LimitConfig,
    receipt: &DataReceipt,
) -> Result<(), ReceiptValidationError> {
    let data_len = receipt.data.as_ref().map(|data| data.len()).unwrap_or(0);
    if data_len as u64 > limit_config.max_length_returned_data {
        return Err(ReceiptValidationError::ReturnedValueLengthExceeded {
            length: data_len as u64,
            limit: limit_config.max_length_returned_data,
        });
    }
    Ok(())
}

fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}

pub unsafe fn return_large_value() {
    input(0);
    let mut args = vec![0u8; register_len(0) as usize];
    read_register(0, args.as_mut_ptr());
    let input_args_json: serde_json::Value = serde_json::from_slice(&args).unwrap();
    let args_size = input_args_json["value_size"].as_u64().unwrap();

    let large_value = vec![0u8; args_size as usize];
    value_return(large_value.len() as u64, large_value.as_ptr() as u64);
}
