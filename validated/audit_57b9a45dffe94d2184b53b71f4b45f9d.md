## Analysis Summary

Reducing the external MasterChef bug to its core invariant: *a function whose entire purpose is to certify that accumulated/critical state matches expectations silently skips validating the most important field, letting stale/wrong state pass as "verified."*

Searching Aptos-native code for the same class of gap (a verification routine that omits checking the actual state-root/commitment field while checking everything else) surfaces a genuine, self-documented gap in `TransactionOutput::ensure_match_transaction_info`.

### Title
`TransactionOutput::ensure_match_transaction_info` never validates the state Merkle root (`state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`), letting replay/verify tooling certify a divergent ledger state as matching - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the comparator used to assert that a locally (re-)executed `TransactionOutput` matches a given, trusted `TransactionInfo`. It checks status, gas used, the write-set hash (`state_change_hash`), and the event root hash [1](#0-0) , but it never compares `txn_info.state_checkpoint_hash()` (or the hot-state/position-state checkpoint hashes) against anything computed locally. The gap is explicitly acknowledged in an unresolved TODO right before the function returns `Ok(())`: [2](#0-1) 

### Finding Description
`ensure_match_transaction_info` is invoked from `verify_execution` in the chunk executor's replay path (`VerifyExecutionMode`), which re-executes transactions and checks the result against externally supplied `TransactionInfo` objects: [3](#0-2) . The same comparator is also used by `storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, and the CLI's transaction-replay command (`aptos-move/cli/src/commands.rs`) to confirm that a re-executed transaction reproduces the on-chain-recorded result. In all of these consumers the comparator is treated as the authoritative "does my computed result match the authenticated `TransactionInfo`" check — but it never touches `state_checkpoint_hash`, which is the actual Sparse-Merkle-Tree root binding the transaction to the rest of world state, nor the hot-state or position-state checkpoint roots.

This differs from the normal block-commit path: `ChunkExecutorInner::update_ledger` separately feeds `known_state_checkpoints`/`known_position_state_checkpoints` into `DoStateCheckpoint::run()` [4](#0-3) , which does check the computed checkpoint hash against the known one there. So the primary commit path retains a state-root check outside `ensure_match_transaction_info`. The exposure is specifically in the standalone verify/replay tooling that relies solely on `ensure_match_transaction_info` as its "did replay reproduce authenticated state" oracle.

### Impact Explanation
Any consumer that uses `ensure_match_transaction_info` alone as proof that re-execution reproduces the authenticated ledger state (replay-verify tooling, debugger, CLI replay) will report success even when the recomputed state root diverges from the value bound into the accumulator-proven `TransactionInfo`. This can mask non-deterministic execution bugs, VM upgrades that silently change state layout, or corrupted backup/replay data — exactly the "authenticated API/proof-bearing output bound to the wrong ... proof context" failure mode called out in scope, and a "hard-fork-only divergence during ... replay ... verification" if such tooling is used to gate consensus-relevant validation (e.g., trusted replay verification before promoting a node/backup as authoritative).

### Likelihood Explanation
The gap is not theoretical: it is explicitly flagged by the code's own TODO, which states that `replay_on_archive` (a real db-tool used for replay verification) "can report a successful replay even when the authenticated position state root diverges from local execution." This is a root-cause bug in shared, unprivileged library code (`types/src/transaction/mod.rs`), reachable by any workflow that calls this comparator, no privileged assumptions required.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/enabled) against the locally computed equivalents before returning `Ok(())`, matching the TODO's own guidance, and require that `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and any caller relying on this function) cannot be enabled/relied upon until the checkpoint-hash validation is added.

### Proof of Concept
1. Instrument a debug build so that state computed during chunk replay (`ChunkExecutorInner::enqueue_chunks` / `verify_execution`) differs in its state root from the `state_checkpoint_hash` carried in the supplied (trusted, accumulator-proven) `TransactionInfo`, while status/gas/write-set-hash/event-root remain identical (e.g., simulate a JMT/hot-state computation bug that doesn't affect the write set hash).
2. Run `db-tool replay-on-archive` or the CLI transaction replay path over that range: `verify_execution` calls `ensure_match_transaction_info` at [5](#0-4) .
3. Observe that the call returns `Ok(())` and the tool reports the replay as verified/matching, despite the state Merkle root being wrong — confirmed by the absence of any `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` comparison in `ensure_match_transaction_info`'s body [6](#0-5) .

**Caveat / what I could not fully verify:** I could not fully trace every consumer (e.g., all downstream usages inside `aptos-debugger` and `cli/commands.rs`) to confirm whether any of them perform an independent state-root check elsewhere that would mitigate this gap for their specific workflow (as the main commit path does via `DoStateCheckpoint`). Given index size limits, I recommend a full audit of all five call sites (`aptos-debugger`, `cli/commands.rs`, `chunk_executor/mod.rs`, `replay_on_archive.rs`, and any test-only callers) to determine which ones lack a compensating state-root check.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
