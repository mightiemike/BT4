### Title
Stale cached debt index reused for `other-debt-repayable` calculation after `debt-remove-scaled` mutates position - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
Zest's `liquidate` function binds `borrow-index`/liquidity-index values from the per-block `index-cache` map via `get-cached-indexes` and reuses that same cached value multiple times across a single `liquidate` invocation, including after state-mutating calls (`debt-remove-scaled`, `collateral-remove`, and potentially `socialize-debt-asset`) have already executed within the same `let*`-style sequential binding chain.

### Finding Description
`liquidate` in `mainnet/contracts/market/v0-4-market.clar` performs its computation as one long sequence of `let` bindings evaluated in program order (Clarity evaluates `let` bindings sequentially, top-to-bottom). Early in the function, `accrue-user-debts`/`accrue-user-collateral` populate `index-cache` for the block [1](#0-0) . `scale-debt-for-liquidation` then reads `borrow-index` from that cache via `(unwrap-panic (get-cached-indexes asset-id))` [2](#0-1) .

Later in the same `liquidate` call, after `vault-system-repay` and `debt-remove-scaled`/`collateral-remove` have already mutated the borrower's on-chain debt/collateral state [3](#0-2) , the function computes `other-debt-repayable` for a *different* collateral asset and again calls `(unwrap-panic (get-cached-indexes debt-aid))` to fetch `other-borrow-idx` [4](#0-3) . Because `index-cache` is keyed only by `{ timestamp: stacks-block-time, aid }` and is never invalidated mid-transaction except by the explicit `map-set` inside `socialize-debt-asset` (which refreshes the cache "post-write-down" specifically to account for a decreased `lindex` after bad-debt socialization) [5](#0-4) , any code path that computes `other-debt-repayable`/`other-borrow-idx` in the same `liquidate` call *before* a bad-debt socialization branch executes will use a debt index that does not reflect the write-down that a subsequent socialization (triggered later in the very same call when `no-collateral-left` is true) applies. The comment "Refresh cache with new indexes post-write-down (lindex decreased)" at line 892 is direct evidence the developers recognized this exact cached-value/invalidation hazard for one code path, but the second read of the same cache key for `other-debt-repayable` at line 1522 executes strictly before the `bad-debt-socialized` block that performs the refresh, at lines 1534-1560, meaning that read is not protected by that fix.

### Impact Explanation
The value `other-debt-repayable` scales the amount of debt Zest treats as "repayable" from a borrower's other collateral, which feeds directly into whether remaining debt gets classified as `no-collateral-left`/bad debt and thus whether socialization (loss absorption by all suppliers) triggers. A wrong (stale, block-scoped but pre-mutation) index used here can misclassify a position's remaining-debt-repayable capacity relative to its true post-repay/post-collateral-removal state, leading to either bad debt entering socialization when it should not, or the reverse. Debt socialization spreads losses onto supplier funds protocol-wide, so a miscalculation here can freeze or misallocate unclaimed supplier yield/principal, falling under permanent/temporary freezing of funds impact.

### Likelihood Explanation
This requires only a single `liquidate` transaction against a borrower position with multiple collateral/debt assets where the borrower ends up with `no-collateral-left` = true, which is a normal, frequently-reachable liquidation flow (no multi-block interleaving, no privileged access, no DAO action needed) — it is purely a same-transaction ordering issue inherent to how `index-cache` is read twice around a state mutation.

### Recommendation
Re-derive `other-borrow-idx` from a fresh `accrue-and-cache`/`vault-accrue` call (or explicitly re-read the cache) after any operation that can mutate the debt index for `debt-aid` within the same `liquidate` execution, rather than relying on the value cached before `debt-remove-scaled`/`collateral-remove`/potential socialization. Alternatively, restructure `liquidate` so all reads of a given asset's index happen strictly after all mutations affecting that asset's index within the same call.

### Proof of Concept
1. Borrower has collateral in asset A and asset B, and debt in asset A (`debt-aid`).
2. Liquidator calls `liquidate` targeting collateral A / debt A with `debt-amount` sized so that after repay+collateral-remove, `no-collateral-left` becomes true (position has residual debt but only asset B collateral, itself insufficient/none).
3. Before `no-collateral-left` is evaluated, `other-debt-repayable` is computed for `debt-aid` using `(get-cached-indexes debt-aid)` — the index cached at the *start* of the transaction, before `debt-remove-scaled` for this borrower reduced their scaled debt.
4. If bad-debt socialization subsequently fires in the same call (`socialize-debt-asset` → `vault-socialize-debt` → `map-set index-cache` with a decreased `lindex`), the earlier `other-debt-repayable` figure computed at step 3 used the pre-socialization index, producing an inconsistent accounting of how much "other" debt was actually repayable relative to the post-write-down state, propagating into the borrower's residual/social debt figures reported and stored for that liquidation.
