### Title
Contract-preparation task can leave `PrepareTaskStatus::Working` permanently locked, hanging chunk application on the main thread - ([File: runtime/runtime/src/pipelining.rs])

### Summary
`ReceiptPreparationPipeline::submit` schedules WASM contract preparation for a receipt's `FunctionCall` action on a background thread pool (`contract_compilation_pool()`), setting `PrepareTaskStatus::Working` before calling `prepare_function_call` [2](#0-1) . The main thread later calls `get_contract`, and if the task status is `Working`, it blocks on `task.condvar.wait(&mut status_guard)` until the background job sets `Prepared` and calls `notify_all()` [3](#0-2) . This is functionally identical to the CVE's bug class: a lock/condition (`p2m lock` in Xen; here, `PrepareTaskStatus`/`condvar`) that "remains unavailable indefinitely in certain error conditions."

### Finding Description
The background closure spawned into `contract_compilation_pool()` sets status to `Working`, then calls `prepare_function_call(...)`, and only *after* that call succeeds does it set `Prepared` and `notify_all()` [2](#0-1) . There is no early "on error, still notify" or `catch_unwind` guard around `prepare_function_call`. The `ThreadPool::run_worker` function that executes pool jobs calls `job()` directly with no panic isolation `catch_unwind` [1](#0-0) . If `prepare_function_call` panics for a crafted/adversarial contract or WASM input (attacker-controlled via `Action::FunctionCall` on a contract the attacker deploys and calls), the panic unwinds through the closure before `task.status` is ever moved out of `Working` and before `condvar.notify_all()` is called. The main thread waiting in `get_contract`'s `PrepareTaskStatus::Working` branch [3](#0-2)  then blocks on the condvar forever — this is the direct analog of the Xen p2m lock never being released "in certain error conditions," causing the host (chunk-producing node) to hang.

### Impact Explanation
A hang in `get_contract` occurs on the main runtime-apply thread while it holds `state_update`/`TrieUpdate` and other chunk-apply state, effectively blocking `Runtime::apply` for the shard indefinitely [4](#0-3) . Since `apply` runs on every honest validator/chunk-producer processing that shard's chunk containing the malicious receipt/transaction, this can halt chunk production/block production for that shard across the network — a transaction-triggered halt, which the Validate rules explicitly list as an acceptable impact category.

### Likelihood Explanation
Requires finding or crafting a WASM/contract input that reliably panics inside `prepare_function_call`'s contract preparation/compilation path (rather than returning a `PrepareError`), which the current investigation could not fully confirm — panics inside contract *preparation* (as opposed to execution) are supposed to be converted to `PrepareError`s in normal operation, so this may rely on an existing lower-severity bug (e.g., an `unwrap()`/`expect()`/indexing panic in the preparation/compilation code path) being reachable from attacker-supplied bytecode. This is the main source of uncertainty in this analog: I could not verify a concrete panicking code path inside `prepare_function_call` within the available index.

### Recommendation
Wrap the background preparation closure in `catch_unwind`, and on panic (or on any other early return) unconditionally set `task.status` to a terminal state and call `condvar.notify_all()`, so that a panicking preparation can never leave waiters blocked forever. Additionally, wrap `run_worker`'s `job()` invocation in `catch_unwind` so a single panicking job cannot silently starve other consumers waiting on job-specific synchronization primitives.

### Proof of Concept
Not independently verified against a concrete panicking WASM input; a full PoC would require identifying a specific panic (e.g., `unwrap`/`expect`/OOB index) reachable from adversary-controlled WASM bytes inside `prepare_function_call`'s call graph, submitted via a `FunctionCall` receipt to a deployed contract, then observing that the shard's chunk-apply thread hangs in `get_contract`'s condvar wait rather than progressing or returning an error.
