**Reasoning summary:**

The claimed equality is "leader key used to validate VRF proof == leader key registered by the sortition's actual winning miner." Tracing the code shows this equality is enforced by construction, not by chance:

- `validate_normal_nakamoto_block_burnchain` retrieves the block-commit deterministically via `db_handle.get_block_commit_by_txid(&tenure_burn_chain_tip.sortition_id, &tenure_burn_chain_tip.winning_block_txid)` — i.e., exactly the commit that the burnchain (Bitcoin) sortition already selected as the winner, not anything an attacker supplies at Nakamoto-block-validation time. [1](#0-0) 
- `leader_key` is then fetched via `get_leader_key_at(block_commit.key_block_ptr, block_commit.key_vtxindex)`, using the `key_block_ptr`/`key_vtxindex` fields that are *part of that already-mined winning block-commit* — fields the attacker cannot rewrite after the fact, since the commit itself is immutable Bitcoin-chain data. [2](#0-1) 
- The only place `key_block_ptr`/`key_vtxindex` are chosen is when the miner itself crafts its `LeaderBlockCommitOp`. Burnchain consensus (`check_common`) requires that the referenced leader key actually exists at that height/vtxindex and predates the commit — but there is no separate "ground truth" key for a winning miner other than whatever key_block_ptr they themselves pointed at. [3](#0-2) 
- `common_validate_against_burnchain` and `check_normal_coinbase_tx` then verify the block's consensus hash and the VRF proof against that same deterministically-fetched key. [4](#0-3) [5](#0-4) 

Since "the leader key of the winning miner" is defined as whatever `key_block_ptr`/`key_vtxindex` the winning block-commit references, and that reference is fixed immutably on the burnchain before any Nakamoto block is even proposed, there is no attacker-reachable path to substitute a "different winning block-commit's" key. Any miner who wanted to reference a stale key would still need the corresponding VRF private key to produce a valid proof — at which point it is simply their own key, not a forged mismatch. All honest nodes processing the same burnchain fork derive identical `block_commit`, `key_block_ptr`, `key_vtxindex`, and `leader_key` values, so no fork-choice or validation divergence is possible through this path.

    fn check_normal_coinbase_tx(
        &self,
        leader_vrf_key: &VRFPublicKey,
        sortition_hash: &SortitionHash,
    ) -> Result<(), ChainstateError> {
        assert!(!self.is_shadow_block());

        // If this block has a coinbase, then verify that its VRF proof was generated by this
        // block's miner.  We'll verify that the seed of this block-commit was generated from the
        // parnet tenure's VRF proof via the `validate_vrf_seed()` method, which requires that we
        // already have the parent block.
        if let Some(coinbase_tx) = self.get_coinbase_tx() {
            let (_, _, vrf_proof_opt) = coinbase_tx
                .try_as_coinbase()
                .expect("FATAL: `get_coinbase_tx()` did not return a coinbase");

            let vrf_proof = vrf_proof_opt.ok_or(ChainstateError::InvalidStacksBlock(
                "Nakamoto coinbase must have a VRF proof".into(),
            ))?;

            // this block's VRF proof must have been generated from the last sortition's sortition
            // hash (which includes the last commit's VRF seed)
            let valid = match VRF::verify(leader_vrf_key, vrf_proof, sortition_hash.as_bytes()) {
                Ok(v) => v,
                Err(e) => {
                    warn!(
                        "Invalid Stacks block header {}: failed to verify VRF proof: {}",
                        self.header.block_hash(),
                        e
                    );
                    false
                }
            };

            if !valid {
                warn!("Invalid Nakamoto block: leader VRF key did not produce a valid proof";
                    "consensus_hash" => %self.header.consensus_hash,
                    "stacks_block_hash" => %self.header.block_hash(),
                    "stacks_block_id" => %self.header.block_id(),
                    "leader_public_key" => %leader_vrf_key.to_hex(),
                    "sortition_hash" => %sortition_hash
                );
                return Err(ChainstateError::InvalidStacksBlock(
                    "Invalid Nakamoto block: leader VRF key did not produce a valid proof".into(),
                ));
            }
        }
        Ok(())
    }
