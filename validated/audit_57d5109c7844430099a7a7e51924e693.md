## Title
Restore path silently skips ledger-info signature verification for epoch-history "gaps," letting unverified `LedgerInfoWithSignatures` be treated as trusted during backup restore — (File: `storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs`)

### Summary
`EpochHistory::verify_ledger_info` is the sole gate that authenticates a `LedgerInfoWithSignatures` pulled from backup storage against the validator set / trusted waypoints before it is used to accept a transaction chunk's proof or a state snapshot during restore. When the ledger info's `epoch` is greater than the number of epoch-ending records the restore session has already fetched, the function does not fail closed — it logs a warning and returns `Ok(())`, i.e. treats the ledger info as verified without checking any signature, validator set, or waypoint.

### Finding Description
`EpochHistory::verify_ledger_info` (lines 276-312) checks three cases: genesis (`epoch == 0`), a match against `trusted_waypoints`, or verification via the previous epoch's `next_epoch_state().verify(...)`. Before any of those branches, however: [1](#0-0) 

If `epoch > self.epoch_endings.len()`, the function unconditionally returns `Ok(())` — treating an *unauthenticated* `LedgerInfoWithSignatures` as verified. This value is used by both `state_snapshot/restore.rs` (to authenticate the state-snapshot's `TransactionInfoWithProof`/root hash source) and `transaction/restore.rs`'s `LoadedChunk::load` (to authenticate a transaction chunk's accumulator range proof) as the anchor for proof binding: [2](#0-1) 

The comment at line 280 ("`TODO(aldenhu): fix this from upper level`") together with "Previous chunks are verified and node won't be able to start if this data is malicious" indicates the authors are aware this is a soft spot and are relying on some *upstream* invariant (that epoch history is always fully fetched ahead of the chunks being verified) to make this safe. That invariant is enforced by caller-side sequencing in `coordinators/restore.rs` and `EpochHistoryRestoreController`, not by `verify_ledger_info` itself — so any caller that supplies a partial/incomplete `epoch_endings` list (e.g., `--skip-epoch-endings`, or any code path that instantiates `EpochHistory` with a shorter history) causes ledger infos for genuinely un-verified epochs to pass with zero cryptographic authentication.

### Impact Explanation
If a `LedgerInfoWithSignatures`/`TransactionInfo`/accumulator root supplied by an untrusted or corrupted backup source is accepted without verification, the restore flow can commit transaction infos, write sets, or a state-snapshot root hash that do not correspond to the real, quorum-certified chain state. Since `verify_ledger_info`'s result gates trust for the state-checkpoint hash and the accumulator range proof used later in restore, this is exactly the "authenticated proof bound to wrong version/root" class of bug: a restored node's durable ledger data (state values, transaction infos, accumulator roots) could silently diverge from the correct VM/consensus-produced state while restore reports success.

### Likelihood Explanation
This is gated behind: (1) restoring with `--skip-epoch-endings` (explicitly supported, see `coordinators/verify.rs` line 106) or otherwise supplying an epoch history that doesn't cover the full range being restored, and (2) an adversarial or corrupted backup storage backend supplying a chunk with an epoch beyond that partial history. This is a real, user-reachable configuration (operators commonly skip epoch-ending verification for speed) rather than a purely theoretical parameterization, which is why I flag it — but I could not fully trace, within the remaining budget, every call site to confirm whether `coordinators/restore.rs`'s main (non-`--skip-epoch-endings`) path can also present an epoch history that lags behind the chunks it verifies (e.g., due to `target_version` clipping of `select_epoch_ending_backups`). That caller-side sequencing guarantee is the crux of whether this is exploitable in the *default* restore flow or only in the explicitly-unsafe `--skip-epoch-endings` / verify-only modes.

### Recommendation
`EpochHistory::verify_ledger_info` should fail closed (return an `Err`) rather than `Ok(())` when `epoch > self.epoch_endings.len()`, unless the caller has explicitly opted into an unsafe/partial-verification mode — and in that case, the unsafe mode should be surfaced distinctly (e.g., a separate `verify_ledger_info_allow_gap` used only by `--skip-epoch-endings`) so that normal restore/verify flows can never silently accept an unauthenticated ledger info.

### Proof of Concept
I could not construct or confirm an end-to-end PoC within the remaining tool budget — this requires tracing `EpochHistoryRestoreController`'s output length under `target_version` filtering versus the versions actually consumed by `TransactionRestoreBatchController`/`StateSnapshotRestoreController` to prove the gap is reachable outside `--skip-epoch-endings`. The code-level defect (silent `Ok(())` on out-of-range epoch in `verify_ledger_info`, lines 279-288) is confirmed and cited above, but full exploitability in the default (non-skip) restore path is unverified.
