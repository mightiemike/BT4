### Title
Attacker Can Grief Legitimate `ExchangeInject`/`ExchangeTransaction` Calls by Front-Running The Exchange Balance Limit Then Withdrawing - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` and `ExchangeTransactionActuator` both enforce a global `exchangeBalanceLimit` cap on each token's balance inside a bancor-style `Exchange` pool at validate time, and both have zero-cost fees and no cooldown/lock-up on the corresponding withdraw operation. This reproduces the same "cap + no-cost reversible action" pattern that made the `Leap.depositEth()` griefing attack possible.

### Finding Description
`ExchangeInjectActuator.doValidate()` computes the new pool balances after an injection and reverts if either token balance would exceed `dynamicStore.getExchangeBalanceLimit()`: [1](#0-0) 

The same pattern exists in `ExchangeTransactionActuator.doValidate()`, which reverts a token swap if the resulting token balance in the pool would exceed the limit: [2](#0-1) 

Both actuators declare `calcFee()` returning `0`, meaning there is no protocol-level cost to perform an inject (deposit-like) or withdraw operation beyond bandwidth/energy: [3](#0-2) [4](#0-3) 

Unlike `ExchangeInject`/`ExchangeTransaction`, `ExchangeWithdrawActuator` does not reference `getExchangeBalanceLimit()` at all (confirmed via `grep_search`, which found matches for `getExchangeBalanceLimit` only in `ExchangeCreateActuator`, `ExchangeInjectActuator`, and `ExchangeTransactionActuator`, not in `ExchangeWithdrawActuator`). This means an attacker can always withdraw previously injected tokens without being blocked by the cap, and — as with `PHASE_DEPOSIT` in the Leap contract — there is no lock-up period preventing an inject-then-immediate-withdraw cycle.

This produces the exact bug-class described in the report: an unprivileged user (Bob) can front-run a victim's (Alice's) `ExchangeInjectContract` or `ExchangeTransactionContract` by injecting tokens to push the pool balance right up to `exchangeBalanceLimit`. Alice's transaction then reverts with `"token balance must less than " + balanceLimit"`. Bob then withdraws his injected tokens via `ExchangeWithdrawContract` immediately afterward, at effectively zero net cost (only bandwidth/energy), repeating the block at will.

### Impact Explanation
The impact is a low-cost griefing/denial-of-service vector against the TRX/TRC10 bancor `Exchange` market: an attacker can indefinitely prevent legitimate users from injecting liquidity into or trading against a specific exchange pool once it nears the configured `exchangeBalanceLimit`, without ever locking capital or paying protocol fees. This maps to the "underpriced-public-work / market griefing" impact category — public actuators that should allow fair liquidity provisioning/trading can be selectively blocked by a bundling attacker with no cost trade-off, similar to how Bob blocked Alice's deposit in the original report.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to observe pending `ExchangeInjectContract`/`ExchangeTransactionContract` transactions in the mempool and construct a bundle (inject before, withdraw after) that lands around the victim's transaction within the same or adjacent blocks — feasible for any SR/relayer-adjacent actor or via transaction-ordering manipulation, consistent with the "attacker monitors and bundles" scenario in the original report. It only requires temporary possession of the tokens being injected, not any elevated privilege.

### Recommendation
Add either (a) a minimum holding/cooldown period between an `ExchangeInject` and a subsequent `ExchangeWithdraw` operation on the same exchange by the same account, or (b) a fee/penalty on rapid inject-then-withdraw cycles, so that using the balance cap to grief other users' transactions carries a real capital cost, mirroring the fix the Leap team applied by relaxing/restructuring when caps are enforced.

### Proof of Concept
1. Exchange pool has `firstTokenBalance = X`, `exchangeBalanceLimit = L`, with `L - X = 10`.
2. Alice submits `ExchangeInjectContract` to inject `10` of the first token — this should succeed since `X + 10 == L`.
3. Bob observes Alice's pending transaction and submits a bundle:
   - Bob's `ExchangeInjectContract` injecting `10` (lands first): passes the `newTokenBalance > balanceLimit` check in `ExchangeInjectActuator.doValidate()` ( [1](#0-0) ), succeeds.
   - Alice's `ExchangeInjectContract` (lands second): now `newTokenBalance = X + 10 + 10 > L`, reverts with `"token balance must less than " + balanceLimit"`.
   - Bob's `ExchangeWithdrawContract` (lands third): since `ExchangeWithdrawActuator` does not check `exchangeBalanceLimit`, it succeeds unconditionally, returning Bob's tokens.
4. Net effect: Alice is blocked from injecting/trading against the pool, and Bob pays only bandwidth/energy costs (`calcFee()` is `0` for both `ExchangeInjectActuator` and `ExchangeWithdrawActuator`'s inject/withdraw path), and can repeat this indefinitely.
