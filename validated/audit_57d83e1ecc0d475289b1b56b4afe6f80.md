### Title
Legacy-mode squash of `WriteResourceGroup` with `ResourceGroupInPlaceDelayedFieldChange` leaves stale `inner_ops`, corrupting committed group member bytes - (File: aptos-move/aptos-vm-types/src/change_set.rs)

### Summary
In `VMChangeSet::squash_additional_resource_writes`, when a resource-group write from the main session is squashed with a later `ResourceGroupInPlaceDelayedFieldChange` from the epilogue (e.g. gas-fee aggregator update touching a resource group), the legacy/non-strict path only checks that `maybe_group_op_size` equals the epilogue's `materialized_size`, then keeps `(false, false)` — i.e. it leaves the original `GroupWrite` (including `inner_ops`) completely unchanged.

### Finding Description [1](#0-0) 

The arm matching `(WriteResourceGroup(GroupWrite { maybe_group_op_size, .. }), ResourceGroupInPlaceDelayedFieldChange(ResourceGroupInPlaceDelayedFieldChangeOp { materialized_size, .. }))` only performs a size check:

```rust
if materialized_size.map(|v| v.get()) != Some(*additional_materialized_size) {
    return Err(...); // sizes mismatch -> abort
}
(false, false) // keep entry unchanged
```

There is no mechanism here to fold the delayed-field exchange information from the epilogue's `ResourceGroupInPlaceDelayedFieldChangeOp` back into `group.inner_ops`. The epilogue-side variant carries no per-tag delayed field/value data at all (by design, per the doc comment on `ResourceGroupInPlaceDelayedFieldChangeOp` at lines 280-289: "Actual information of which individual tag has delayed fields ... unnecessary in current implementation, as we need to traverse and materialize all tags anyways"). This design assumption is only safe if the later `into_transaction_output_with_materialized_writes` path re-reads/re-materializes *all* group member tags from the up-to-date view rather than trusting the stale `inner_ops` snapshot captured by the main session before the epilogue's in-place delayed-field exchange happened.

The code's own inline `SAFETY` comment explicitly documents the exact risk: "a matching materialized size does not prove the later session's delayed-field exchange reconciles with the group the earlier session wrote" and states this was fail-closed (hard error) for `gas_feature_version` in `[RELEASE_V1_46, RELEASE_V1_48)`, and reverted to the legacy merge-by-size-only behavior outside that window because "the view-layer fix makes this sound again."

I could not fully verify, within index limits, whether the referenced "view-layer fix" (materializing group writes from `ExecutorView`/`view_with_change_set.rs` rather than trusting the stale `inner_ops`) is actually present and correctly wired for the legacy `gas_feature_version` range outside `[RELEASE_V1_46, RELEASE_V1_48)`, or whether it only covers versions ≥ RELEASE_V1_48. If the "legacy" branch (used for the historical range of `gas_feature_version` values below `RELEASE_V1_46`, i.e. essentially all mainnet feature versions in production before this fix was introduced) relies on `group.inner_ops` as captured before the epilogue instead of a downstream re-materialization step, then a crafted transaction where the epilogue's delayed-field exchange changes an actual resource group member's underlying value (not just size) would result in `GroupWrite.inner_ops` in the final `VMChangeSet` reflecting the pre-epilogue value, while the group's size/metadata_op is accepted as matching. Whether this is exploitable depends entirely on whether `into_transaction_output_with_materialized_writes` (in `aptos-move/aptos-vm/src/block_executor/mod.rs` or `aptos-move/aptos-vm-types/src/storage`) re-derives group member bytes independently of `inner_ops` for the `ResourceGroupInPlaceDelayedFieldChange` case, which I was unable to trace fully with the remaining budget.

### Impact Explanation
If the downstream materialization step does not independently re-derive the affected tag's bytes, this would directly corrupt `GroupWrite.inner_ops` for a resource-group member in the committed write set — potentially misrepresenting a balance or other on-chain state for that tag, which is a committed-state-integrity violation matching the "Committed state differs from correct VM result" impact class.

### Likelihood Explanation
This requires a specific combination: (1) `gas_feature_version` outside `[RELEASE_V1_46, RELEASE_V1_48)`, (2) main-session resource-group write to a group, and (3) an epilogue-triggered in-place delayed-field change to the same group whose `materialized_size` happens to match `maybe_group_op_size`. Given the current codebase state where `RELEASE_V1_48` corresponds to a relatively recent mainnet release, most present-day mainnet feature versions would fall outside the fail-closed window, meaning the legacy path is the one actually in production use today, which would raise likelihood significantly — but this hinges on confirming whether downstream materialization compensates, which is unverified.

### Recommendation
Verify explicitly whether `into_transaction_output_with_materialized_writes` (or equivalent) re-derives resource-group member bytes for the `ResourceGroupInPlaceDelayedFieldChange`-squashed case from a live view rather than trusting `group.inner_ops` captured pre-epilogue. If it does not, extend the legacy arm to re-fetch/re-materialize the affected tags' current values (matching what the strict/fail-closed path avoids by erroring out) instead of silently keeping `(false, false)`, or keep the fail-closed rejection permanently rather than reverting to size-only comparison outside the version window.

### Proof of Concept
Could not be fully constructed without confirming the downstream materialization behavior; the described proof idea (craft a matching-size group write + in-place delayed change with a genuinely different underlying value, assert squash produces correct materialized bytes) is directly actionable against `VMChangeSet::squash_additional_resource_writes` as a unit test in `aptos-move/aptos-vm-types/src/tests/test_change_set.rs`, but confirming end-to-end committed-state corruption requires tracing the executor's materialization path further than was possible within this review's tool budget.
