### Title
Concurrent flush-with-`ReclaimOldSlots` can panic `AccountsIndex::replace` during shrink, crashing the validator - ([File: accounts-db/src/accounts_index/in_mem_accounts_index.rs])

### Finding Description
`AccountsDb::shrink_storage` first decides which accounts are "alive" at slot `S` by inspecting storage-level metadata (`get_unique_accounts_from_storage_for_shrink` / `shrink_collect`), not the accounts index itself [1](#0-0) . It then later calls `store_accounts_for_shrink` → `update_index_for_shrink` → `AccountsIndex::replace(target_slot, old_slot=S, pubkey, info)` [2](#0-1) , which panics if `old_slot` is no longer present in the pubkey's slot list [3](#0-2) .

Separately, when the write-cache flush path writes a newer slot `S+1` for the same pubkey with cleaning enabled, it calls `AccountsIndex::upsert(new_slot=S+1, old_slot=S+1, pubkey, info, reclaims, UpsertReclaim::ReclaimOldSlots)` [4](#0-3) , driven by `reclaim_method = UpsertReclaim::ReclaimOldSlots` whenever cleaning is active [5](#0-4) . Inside `update_slot_list`, the `ReclaimOldSlots` branch removes *every* slot-list entry with `cur_slot < slot` (i.e. any entry older than the new write, including `S`) and pushes it into `reclaims` [6](#0-5) .

Both `replace()` and `upsert()` operate under the same per-pubkey entry write lock, so the two operations are individually atomic but not ordered relative to shrink's two-phase read-then-write flow. Because `shrink_collect`'s "is this account alive" decision is made from storage-level obsolete-account bookkeeping (populated later, in `handle_reclaims`/`mark_accounts_obsolete`, which itself runs *after* `update_index_for_flush` inside `store_accounts_for_flush` [7](#0-6) ) rather than from the index directly, there is a window where:
1. Shrink's `shrink_collect` snapshots slot `S`'s account as alive (obsolete-marking not yet applied).
2. A concurrent flush of the same pubkey at `S+1` acquires the pubkey's slot-list lock first and, via `ReclaimOldSlots`, removes the `S` entry from the index.
3. Shrink later calls `replace(target_slot=S, old_slot=S, pubkey, ...)`, finds no entry at `S`, and hits `assert!(found_slot, "Expected to find a slot to replace in the slot list")`, panicking the validator process.

If the lock race resolves the other way (shrink's `replace()` wins first), no panic occurs, but the rewritten value at `S` is subsequently reclaimed anyway when the flush's `ReclaimOldSlots` runs — in that ordering the newest write (`S+1`) still survives in the slot list and reads via `do_load`/ancestor resolution return the newer value, so no silent stale-read occurs in that branch.

### Impact Explanation
If the panic-triggering ordering occurs, it crashes the validator process via a Rust `assert!` panic inside the accounts index, matching Agave's "node panic" DoS bounty category. The write-cache-vs-shrink guard at the top of `shrink_storage` (`self.accounts_cache.contains(slot)`) only protects against the shrink target slot itself still being cached — it does not protect against a concurrent flush of a *different*, newer slot for the same pubkey racing shrink's index update.

### Likelihood Explanation
Triggering this requires: (1) an account rooted and flushed at slot `S` that becomes shrink-eligible, (2) a fresh write to the same pubkey at a later slot `S+1` that gets flushed with cleaning enabled while shrink is concurrently processing `S`. An unprivileged user controls write timing/frequency for their own accounts and can influence when their account becomes shrink-eligible (large accounts followed by resizes), but they do **not** control validator-internal thread scheduling, the relative ordering of the background flush/clean/shrink services, or exact lock-acquisition timing at instruction granularity. I could not confirm within this investigation whether Agave's `AccountsBackgroundService` already serializes shrink and cache-flush-with-clean sufficiently to make this window unreachable in practice (I found an `assert!(self.storage.no_shrink_in_progress())` in a related reclaim-handling path suggesting some global shrink/reclaim serialization exists, but I did not trace its exact call sites and scope within the tool-call budget available). This uncertainty should be resolved before treating this as a fully proven, reliably-triggerable DoS.

### Recommendation
Make shrink's alive-account determination and its index update atomic with respect to concurrent `ReclaimOldSlots` upserts: either (a) have `update_index_for_shrink`'s `replace()` tolerate a missing `old_slot` by treating it as a no-op (the account was superseded and reclaimed elsewhere, which is the correct outcome) instead of asserting, or (b) hold the per-pubkey index bin/entry lock across both the shrink liveness check and the index replace for that pubkey so the two operations cannot interleave.

### Proof of Concept
Add a concurrency test in `accounts-db/src/accounts_db/tests/impl.rs` modeled on the existing `do_test_load_account_and_shrink_race`, but racing shrink against a *flush of a newer slot* for the same pubkey with `UpsertReclaim::ReclaimOldSlots`:
```rust
// pseudo-outline
// 1. store pubkey at slot S, add_root(S), flush (out of write cache).
// 2. Spawn thread A: repeatedly call shrink_storage-equivalent path (shrink_candidate_slots) for S.
// 3. Spawn thread B: repeatedly store pubkey at S+1, add_root(S+1), and
//    flush_rooted_accounts_cache_with_clean (drives ReclaimOldSlots upsert).
// 4. Run both concurrently under loom/stress iterations; assert no panic occurs,
//    and after settling, do_load returns the account at S+1 (LIFECYCLE_NEUTRALITY:
//    shrink must never change which value a reader observes, and must never crash).
```
Expected assertions: no `assert!(found_slot, ...)` panic ever fires, and post-race `do_load_for_tests` with `Ancestors::default()` returns the value written at `S+1`.
