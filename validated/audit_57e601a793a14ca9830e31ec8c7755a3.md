## Finding: `ensure_match_transaction_info` skips checkpoint-hash verification during replay/restore

### Title
Transaction replay verification omits state/hot-state/position checkpoint hash comparison, allowing corrupted state roots to pass as valid replay - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used to validate that a freshly re-executed transaction matches an on-record `TransactionInfo` during chunk-based replay/verification (backup restore verify, `replay_on_archive`). It checks status, `gas_used`, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually commit to the Sparse-Merkle/JMT state root and the "trading-native" position state root.

### Finding Description [1](#0-0) 

The function computes and asserts equality for `write_set_hash` and `event_root_hash` against the corresponding `TransactionInfo` fields, but the code contains an explicit, self-documenting comment stating the comparator intentionally ignores `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, and that this can let `replay_on_archive`-style tooling report success even when the authenticated state root diverges from local execution.

This function is invoked from `ChunkExecutorInner::verify_execution`, which is the code path used by `TransactionReplayer::enqueue_chunks` (the replay-verify / archive-verification pipeline) to validate that re-executing historical transactions from a backup/archive reproduces the exact committed result: [2](#0-1) 

Because `state_checkpoint_hash` is never compared here, a divergence between the locally-recomputed Jellyfish Merkle Tree root (or hot-state/position state root) and the `TransactionInfo.state_checkpoint_hash` recorded in the backup/archive will not be detected by this verification step, even though `write_set_hash` and `event_root_hash` are checked and pass.

Contrast this with the normal commit path, `ChunkExecutorInner::update_ledger`, which *does* pass `known_state_checkpoints` (derived from the very same, potentially-untrusted `chunk_verifier.transaction_infos()`) into `DoStateCheckpoint::run()` for cross-checking: [3](#0-2) 

That check only verifies internal self-consistency between the recomputed checkpoint tree and the caller-supplied `TransactionInfo`s — it is not a substitute for `ensure_match_transaction_info`'s per-transaction comparison when the latter is used specifically to validate replayed output against externally supplied, pre-verification data (e.g., a backup being restored/verified, as invoked by `verify_execution`).

### Impact Explanation
If the state root committed on-chain (or in a backup archive) is wrong — e.g., due to a storage/JMT bug, a corrupted snapshot restore, or a divergent VM execution on a hard fork — `db-tool`'s replay-verify tooling relying on `ensure_match_transaction_info` (via `ChunkExecutorInner::verify_execution`) can report a clean, successful replay while the authenticated state/position state root silently diverges from what local execution actually produced. This defeats the core purpose of replay-verification: catching state-commitment divergence between archived data and independently re-executed VM output. This falls squarely within the "Wrong accumulator root ... accepted as valid" and "replay ... must preserve deterministic proof binding" impact classes.

### Likelihood Explanation
This is not a hypothetical: the gap is explicitly acknowledged in the code's own comment, indicating it's a real, currently-shipped limitation (guarded only by a note to fix it "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"). It requires no attacker privilege — any latent state-root divergence (bug, corruption, or malicious archive/backup source feeding a replay-verify node) would go undetected by this specific check, though other independent mechanisms (e.g., accumulator proofs over `TransactionInfo` themselves, or full block-level checkpoint validation elsewhere) may mitigate real-world exploitability in some replay contexts. I was not able to fully trace whether `TransactionOutputListWithProofV2`/`TransactionListWithProofV2` verification (accumulator proof over `TransactionInfo` hashes) elsewhere independently guarantees the checkpoint hash is bound correctly for the *replay-verify* archive-restoration use case specifically, since tool access ended before I could inspect `storage/backup/backup-cli/src/backup_types/transaction/restore.rs` in full detail.

### Recommendation
Add comparison of `state_checkpoint_hash` (and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` when applicable) inside `ensure_match_transaction_info`, computing the expected checkpoint hash from the locally re-executed state and asserting equality with `txn_info.state_checkpoint_hash()`, mirroring the existing `write_set_hash`/`event_root_hash` checks, before this code path is relied upon for any authenticated replay/restore verification.

### Proof of Concept
Not independently reproduced with a running node; the finding is derived directly from the code path trace:
1. `ChunkExecutorInner::verify_execution` re-executes transactions via the VM. [4](#0-3) 
2. It calls `txn_out.ensure_match_transaction_info(version, txn_info, Some(write_set), Some(events))`.
3. Inside `ensure_match_transaction_info`, only `status`, `gas_used`, `write_set_hash`, and `event_root_hash` are asserted; `state_checkpoint_hash` is never read or compared, as confirmed by the trailing TODO comment. [5](#0-4) 

Given the honesty of the in-code comment and the confirmed call path from `verify_execution` (part of the replay-verify pipeline), this represents a genuine, currently-present integrity gap in state-checkpoint-hash verification during transaction replay.
