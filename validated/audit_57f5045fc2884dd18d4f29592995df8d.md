### Title
Permissionless `TransferToGasKey` deposits can permanently freeze gas-key deletion and account deletion via griefing - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
`action_transfer_to_gas_key` lets *any* predecessor add a deposit to a target account's gas-key balance with no check that the caller owns or controls that account. `delete_gas_key` and `action_delete_account` both hard-fail once the accumulated gas-key balance exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR), so an attacker can grief a target by pushing that balance over the threshold, permanently blocking the legitimate owner from deleting the gas key or the account — the same "inject value into a balance the target logic gates on" pattern as the Sherlock `removeAsset`/`getTVLForAsset` griefing report.

### Finding Description
`action_transfer_to_gas_key` looks up the access key on `account_id`, confirms it is a gas key, and adds `action.deposit` to `gas_key_info.balance` — with no `actor_id == account_id` / `ActorNoPermission` check inside the function itself: [1](#0-0) 

The deposited balance is tracked purely as an accumulator on the target's `AccessKey`/`GasKeyInfo`, analogous to the Solidity bug's `balanceOf`/`.balance` read that any external actor can inflate.

Two consumers gate on this balance and hard-revert if it is too high:

1. `delete_gas_key` (triggered by `DeleteKeyAction` on a gas key) refuses to delete the key if `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN`: [2](#0-1) 

2. `action_delete_account` sums *all* gas-key balances on the account (`compute_gas_key_balance_sum`) and refuses to delete the account entirely if the sum exceeds the same 1 NEAR threshold: [3](#0-2) 

`GasKeyInfo::MAX_BALANCE_TO_BURN` is a fixed 1 NEAR cap, and once exceeded, the burn path is refused rather than partially executed: [4](#0-3) 

Because `TransferToGasKeyAction` deposits are not restricted to the account owner, an unprivileged transaction sender can repeatedly (or in one shot) fund any observed gas key on a victim account until the cumulative gas-key balance across the account exceeds 1 NEAR. This mirrors the report's core bug class: a permissionless external write into a value that a security-critical removal/cleanup function checks, causing that function to permanently and unconditionally revert.

### Impact Explanation
Once griefed, the victim can no longer:
- Delete the specific gas key via `DeleteKeyAction` (always returns `GasKeyBalanceTooHigh`), and
- Delete their account via `DeleteAccountAction` if the total exceeds the threshold, since `action_delete_account` performs the same check before any state mutation and returns early on failure.

This permanently locks the account's principal balance/state behind an operation that can never succeed, matching the "permanently frozen funds" acceptance criterion — the owner cannot reclaim/withdraw via account deletion, and cannot remove the specific poisoned gas key, regardless of gas spent, because the check is a hard revert, not a partial/best-effort burn.

### Likelihood Explanation
The attack requires only a single transaction (`TransferToGasKeyAction`) sent by any account to a target's gas key with a small deposit (or a few such transactions to accumulate past 1 NEAR); the target must have at least one existing gas key (a NEP-366/NEP-... "GasKeys" feature primitive), which is expected to become common with meta-transaction/relayer usage. No special privileges, races, or validator behavior are required — this is directly reachable by any unprivileged JSON-RPC/transaction submitter.

### Recommendation
Restrict `TransferToGasKeyAction` deposits to be initiated only by the account owner (require `actor_id == account_id`, i.e. signed with a full-access key of the target account), or, if third-party funding is an intended feature (e.g., relayer subsidization), cap per-caller/aggregate deposits so a third party cannot unilaterally push the balance past `MAX_BALANCE_TO_BURN`, or make deletion behavior degrade gracefully (e.g., burn up to the cap and refund/queue the remainder) instead of hard-reverting the entire `DeleteKey`/`DeleteAccount` action.

### Proof of Concept
1. Victim account `victim.near` has a gas key `pk_gas` with `GasKeyInfo.balance = 0`.
2. Attacker (any signer, e.g. `attacker.near`) submits a transaction/receipt with `Action::TransferToGasKey(TransferToGasKeyAction { public_key: pk_gas, deposit: 1_000_000_000_000_000_000_000_000 })` (1 NEAR) targeting `victim.near`. `action_transfer_to_gas_key` executes with no ownership check, setting `gas_key_info.balance = 1 NEAR` (`runtime/runtime/src/access_keys.rs:257-288`).
3. Attacker repeats with a second small deposit (e.g. 1 yoctoNEAR) to push the balance to `> MAX_BALANCE_TO_BURN`.
4. Victim submits `DeleteKeyAction { public_key: pk_gas }` — `delete_gas_key` returns `GasKeyBalanceTooHigh` and the key is never removed (`runtime/runtime/src/access_keys.rs:102-111`).
5. Victim submits `DeleteAccountAction` — `action_delete_account` computes the same sum via `compute_gas_key_balance_sum` and returns `GasKeyBalanceTooHigh` before any state mutation, permanently blocking account deletion and fund recovery via that path (`runtime/runtime/src/actions.rs:370-379`).

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
