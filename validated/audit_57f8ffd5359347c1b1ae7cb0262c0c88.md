### Title
Pre-registering a deterministic future CREATE address as a Witness (SR candidate) leaves stale consensus state after the address becomes a smart contract - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The externally reported Nibiru bug exploits the fact that Cosmos accounts and EVM accounts share the same address space: an attacker preemptively converts a deterministic future contract address into a special account type (`vesting`) whose state-transition path does not fully reconcile with the contract-deployment path, leaving orphaned bytecode. Java-tron shares the analogous architectural pattern — TVM `CREATE` targets deterministic addresses derived from `(rootTransactionId, nonce)`, and the same `AccountStore` keyspace is shared by "special" account roles (e.g. Witness/SR candidates) and contract accounts. Unlike Nibiru, java-tron's internal-`CREATE` collision handler does upgrade a pre-existing account's `type` field to `Contract`, but it does not purge SR-specific state (`isWitness` flag, `WitnessStore` entry, votes, permissions) that was attached to the address before the collision. This leaves a “phantom” witness entry pointing at a live smart-contract address, which is not present in Nibiru's fix path but is a structurally identical “special account state pre-registration blocks/pollutes the contract-address path” bug class.

### Finding Description
`Program.createContractImpl` handles the case where the deterministic `CREATE` target address already has account state (i.e., a “collision”) as follows: [1](#0-0) 

If `existingAccount != null` and it is not already a genuine contract (`!contractAlreadyExists`), the code only performs:
```
existingAccount.updateAccountType(AccountType.Contract);
existingAccount.clearDelegatedResource();
```
`clearDelegatedResource()` only zeroes acquired delegated-frozen-balance fields for bandwidth/energy: [2](#0-1) 

It does **not** clear `isWitness`, votes (`getVotesList`), `ownerPermission`/`witnessPermission`/`activePermission`, or the address's entry in `WitnessStore`.

An attacker can pre-register a deterministic future `CREATE` target address as a Super Representative (witness) candidate before the legitimate deployer's factory contract creates a child there. Registration is permissionless and only requires the target address to already be an existing, funded account (any account can be sent TRX to auto-create it, then upgraded via `WitnessCreateContract`): [3](#0-2) 

`WitnessCreateActuator.validate()` never checks the `AccountType` of the target address (only that it exists and is not already in `WitnessStore`): [4](#0-3) 

Later, when the victim's factory contract calls `CREATE` and lands on that same address (deterministic via `TransactionUtil.generateContractAddress(rootTransactionId, nonce)`): [5](#0-4) 

the collision branch quoted above fires, the account's `type` flips to `Contract`, and deployment proceeds successfully (unlike the Nibiru bug, the contract itself is *not* orphaned here — this specific bug class was clearly hardened for the CREATE2/CREATE collision path, evidenced also by `HistoryBlockHashUtil`'s explicit mirroring of this branch). However, `isWitness=true`, any accumulated votes, and the `WitnessStore` entry for that address are left untouched, because nothing in `createContractImpl` or in `WitnessStore`/vote-counting logic (`VoteWitnessActuator.countVoteAccount`, which also never checks `AccountType`) is aware of, or reconciles with, the CREATE collision: [6](#0-5) 

The net effect: an address that now runs live TVM bytecode as a smart contract simultaneously remains registered as an SR candidate in `WitnessStore`, can still receive votes, and cannot be removed by its "owner" (there is no private key that can withdraw/deregister the witness role, since the address is now controlled purely by contract logic with no ECDSA key).

### Impact Explanation
If such a contract-controlled "phantom witness" accumulates enough votes to enter the active SR set, DPoS block-production scheduling would allocate a production slot to an address that cannot ever produce/sign a block (it has no ECDSA key — the account was never a normal EOA whose key the attacker controls for block signing; the object is a TVM contract). This is a resource/consensus-availability issue: wasted SR slots, degraded block cadence, and permanently "stuck" stale witness state that cannot be cleaned up by any transaction type (no actuator exists to un-witness or purge a contract-typed account from `WitnessStore`). It also constitutes state/storage pollution analogous to Nibiru's "storage waste" impact. I was not able to fully verify, within tool budget, whether the SR-slot scheduler (`DposSlot`/`ConsensusDelegate`) filters out contract-typed addresses before assigning production slots — if it does, actual liveness impact would be limited to accounting/vote-integrity pollution rather than missed blocks. This should be verified directly against `consensus/src/main/java/org/tron/consensus/dpos/DposSlot.java` and `ConsensusDelegate` in a follow-up session.

### Likelihood Explanation
Both preconditions are cheap and fully attacker-controlled: (1) computing the deterministic child address only requires knowing the parent contract's address and the CREATE nonce, both of which are either public (deployed factory address) or guessable/observable pre-deployment; (2) registering a witness only costs `getAccountUpgradeCost()` TRX and requires no special permission. The only constraint is that the target address must already exist in `AccountStore` (an attacker can trivially create it by sending a small TRX transfer). No privileged role, leaked key, or malicious peer is required — this is reachable purely via ordinary, permissionless broadcast transactions (`WitnessCreateContract` + a normal `CREATE`-triggering `TriggerSmartContract`).

### Recommendation
When the `CREATE`/`CREATE2` collision branch in `Program.createContractImpl` (and the analogous top-level `VMActuator.create()` path) upgrades a pre-existing account to `AccountType.Contract`, fully reconcile all "special" account state that is incompatible with being a contract, not just delegated-resource balances:
- Clear `isWitness` and remove the corresponding entry from `WitnessStore` (and any associated `WitnessCapsule`/vote-schedule state) if present.
- Clear `votes`, `ownerPermission`/`witnessPermission`/`activePermission`, and any AssetIssue-name state.
- Alternatively, reject the `CREATE` if the destination account has non-default "special" state (e.g., `isWitness == true` or an active `WitnessStore` entry) rather than silently absorbing it, mirroring the fail-closed approach Nibiru ultimately adopted (disabling the conflicting feature) rather than fail-open state merging.
- Add an explicit account-type check to `WitnessCreateActuator.validate()` and `VoteWitnessActuator` to reject SR registration/voting for addresses whose `AccountType` is `Contract`.

### Proof of Concept
1. Attacker observes/derives the deterministic address of a future TVM `CREATE` target: `addr = sha3omit12(rootTransactionId ++ nonce)` per `TransactionUtil.generateContractAddress(byte[] transactionRootId, long nonce)`.
2. Attacker sends a minimal TRX transfer to `addr` to auto-create the account, then broadcasts a `WitnessCreateContract` transaction with `ownerAddress = addr`, paying `AccountUpgradeCost` — this succeeds per `WitnessCreateActuator.validate()`/`createWitness()`, setting `isWitness=true` and inserting a `WitnessCapsule` into `WitnessStore`.
3. Victim's factory contract executes `CREATE`, landing on `addr` (per `Program.createContract` → `TransactionUtil.generateContractAddress(rootTransactionId, nonce)`).
4. `Program.createContractImpl` finds `existingAccount != null`, `!contractAlreadyExists`, and executes `updateAccountType(AccountType.Contract)` + `clearDelegatedResource()`, then deploys the contract bytecode/SmartContract entry successfully.
5. Inspect state post-deployment: `AccountStore.get(addr).getType() == Contract` and `isWitness() == true` simultaneously; `WitnessStore.has(addr) == true` still holds; `VoteWitnessActuator` will still accept and tally votes for `addr` as a witness candidate. No actuator exists to remove this entry, since `WithdrawBalanceActuator`/witness self-management flows require the caller to control `addr`'s signing key, which no longer applies to a contract account.

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
