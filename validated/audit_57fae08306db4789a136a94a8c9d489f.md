## Finding [1](#0-0) 

### Title
Rejecting one FIFO-mode transaction purges all of the sender's other valid, unrelated queued transactions with no re-insertion path, permanently stranding them in the pool - (File: crates/apollo_mempool/src/mempool.rs, crates/apollo_mempool/src/fifo_transaction_queue.rs)

### Summary
In `Mempool::remove_rejected_txs` (FIFO/Echonet behavior mode), rejecting a single transaction from an account causes `TransactionQueueTrait::remove_by_address` to delete **every** other queued/staged transaction belonging to that same account from the FIFO queue, while only the single rejected transaction is removed from the underlying `tx_pool`. No code path exists to ever re-insert the surviving (valid, non-rejected) transactions back into the FIFO queue, so they remain stuck in the pool, unreachable for sequencing, until they eventually expire via TTL.

### Finding Description
`remove_rejected_txs` iterates rejected transaction hashes and, for each one, removes only that single transaction from `tx_pool`, but then calls `self.tx_queue.remove_by_address(tx.contract_address())`: [2](#0-1) 

`FifoTransactionQueue::remove_by_address` purges **all** queue and staged entries for that address, not just the rejected one: [3](#0-2) 

This is correct semantics for the fee-priority queue (where only one transaction per address can ever be queued at a time), but in FIFO/Echonet mode `add_tx_inner` deliberately places **all** of an account's transactions into the queue regardless of nonce ("Keep all transactions from the same address in the queue"): [4](#0-3) 

The gap-closing logic in `commit_block` that would normally re-insert an account's next pool transaction into the queue is explicitly skipped for FIFO mode: [5](#0-4) 

The maintainers' own test confirms this exact behavior — rejecting `tx_hash: 1` for address `0x1` removes the unrelated, not-yet-executed `future_same_address_tx` (`tx_hash: 2`) from the FIFO queue entirely: [1](#0-0) 

After this removal, `future_same_address_tx` is orphaned: it remains present in `tx_pool` (consuming mempool capacity) but is permanently absent from the FIFO queue, and no subsequent code path re-adds it. It will only ever leave the mempool via TTL expiry (`remove_txs_older_than`), never via inclusion in a block.

### Impact Explanation
Any single transaction from an account that ends up in the sequencer's "rejected" set (e.g., a transaction that reverts on execution or otherwise fails at block-building time — reachable purely through normal transaction submission by an unprivileged sender) silently and permanently removes that account's other already-admitted, valid, unexecuted transactions from consideration for sequencing. This is a logic flaw analogous to the reported Funadmin "one-click deletion" DOS: a single triggering action deletes unrelated valid state, and the deleted transactions are unrecoverable within the mempool's lifetime — the network becomes unable to confirm those specific transactions even though they were legitimately admitted and remain in the pool. Because Echonet/FIFO mode is a supported `BehaviorMode` in this sequencer, an account (or third party crafting a transaction that will be rejected) can weaponize this to strand a victim account's pending transactions indefinitely.

### Likelihood Explanation
The trigger requires only a single submitted transaction whose fate is "rejected" by the sequencer (e.g. due to reverted execution or other rejection criteria surfaced through `CommitBlockArgs::rejected_tx_hashes`), which is directly reachable by any unprivileged transaction sender in normal operation — no special privileges, timing races, or node compromise required. The bug is deterministic per the reproducing test, not probabilistic.

### Recommendation
In `remove_rejected_txs`, do not call the blanket `remove_by_address` in FIFO mode. Instead, `remove_txs` should be used with only the specific rejected transaction reference, mirroring the behavior already provided by `FifoTransactionQueue::remove_txs` (which precisely removes matching tx hashes without disturbing other queued/staged transactions for the same address). Alternatively, add a FIFO-specific re-insertion path that restores an account's remaining pool transactions to the queue after a per-account queue purge.

### Proof of Concept
1. Configure the mempool with `BehaviorMode::Echonet` (FIFO mode).
2. Submit two transactions from the same account: `tx1` (nonce 0) and `tx2` (nonce 1).
3. Stage `tx1` via `get_txs`, then call `commit_block` marking `tx1` as rejected (no committed nonce for the account).
4. Observe (as in `test_rejected_tx_removes_same_address_from_fifo_queue`, [1](#0-0) ) that `tx2`, never rejected and never executed, disappears from all future `get_txs` results even though it still occupies pool capacity — it can never be sequenced.

fn test_rejected_tx_removes_same_address_from_fifo_queue(mut mempool: Mempool) {
    let rejected_tx = add_tx_input!(tx_hash: 1, address: "0x1", tx_nonce: 0, account_nonce: 0);
    let future_same_address_tx =
        add_tx_input!(tx_hash: 2, address: "0x1", tx_nonce: 1, account_nonce: 0);
    let other_address_tx = add_tx_input!(tx_hash: 3, address: "0x2", tx_nonce: 0, account_nonce: 0);

    mempool.update_tx_block_metadata(tx_hash!(1), tx_metadata(1000, 100));
    mempool.update_tx_block_metadata(tx_hash!(2), tx_metadata(1001, 101));
    mempool.update_tx_block_metadata(tx_hash!(3), tx_metadata(1001, 101));

    for input in [&rejected_tx, &future_same_address_tx, &other_address_tx] {
        add_tx(&mut mempool, input);
    }

    // Stage only the first tx (timestamp 1000).
    assert_eq!(mempool.resolve_batch_timestamp(), 1000);
    get_txs_and_assert_expected(&mut mempool, 10, &[rejected_tx.tx]);

    // Reject tx. In FIFO, this removes same-address queued txs.
    commit_block(&mut mempool, [], [tx_hash!(1)]);

    // Next timestamp batch should include only the other address tx.
    assert_eq!(mempool.resolve_batch_timestamp(), 1001);
    get_txs_and_assert_expected(&mut mempool, 10, &[other_address_tx.tx]);
}

    // Returns true if at least one transaction of this address was removed from the queue or from
    // staged transactions.
    fn remove_by_address(&mut self, address: ContractAddress) -> bool {
        let len_before = self.queue.len() + self.staged_txs.len();
        self.queue.retain(|tx| tx.tx_reference.address != address);
        self.staged_txs.retain(|tx| tx.tx_reference.address != address);
        let len_after = self.queue.len() + self.staged_txs.len();
        len_before != len_after
    }
