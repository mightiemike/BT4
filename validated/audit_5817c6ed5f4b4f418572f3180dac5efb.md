### Title
First borrower into an empty vault is charged interest for the entire stale period since the index last changed, because the index/timestamp clock only advances "on change" - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
In every vault contract (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`), the `accrue` function only advances `last-update` when the borrow index (`index`) or liquidity index (`lindex`) actually changes value. When the vault has zero scaled principal (no outstanding debt), the index computation produces no change, so `last-update` is left stuck at an arbitrary, possibly very old timestamp. The first `system-borrow` call after such a dry period will accrue interest as if the debt had existed since that stale timestamp, causing the first borrower to overpay interest — the same root cause described in the referenced Ajna M-4 report, just implemented via an index-based inflator instead of an explicit `t0Debt` check.

### Finding Description
`accrue` in `mainnet/contracts/vault/v0-vault-usdc.clar` (lines 837-865) reads the current `index`/`lindex`, computes `next`/`nliq`, and only commits state changes conditionally: [1](#0-0) 

Critically, the timestamp used to gate future interest calculations, `last-update`, is only bumped when the index actually moved:
```
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
``` [2](#0-1) 

`debt-delta`, `reserve-inc`, and `treasury-lp` are all derived from `scaled-principal`, which is `u0` while the vault carries no debt: [3](#0-2) 

`system-borrow` (called by the `market` contract when a user first borrows from an asset) invokes `accrue` before minting the new scaled debt: [4](#0-3) 

This is the exact "clock advanced only on change" analog: `last-update` is the value bound at the previous accrual; the event that should invalidate it — the passage of time while debt is zero — does not trigger an update because the index computation is gated on `scaled-principal`/utilization being nonzero (a zero-utilization vault produces `next == idx`, so the `is-eq` guard prevents the timestamp bump). The later use is the very next `accrue` call inside the first `system-borrow`, which computes elapsed time as `stacks-block-time - last-update` and applies the full elapsed interest to principal that only just became nonzero, exactly mirroring the Ajna `_accruePoolInterest`/`_updateInterestState` bug where the inflator (functionally the same role as `last-update`) is not reset when debt transitions from zero to nonzero within the same call.

### Impact Explanation
The first borrower on any vault (or any borrower who is first to draw debt again after the vault has been fully repaid to zero debt for a period) is charged interest on their principal for a period during which they held no debt. This is a direct, protocol-enforced transfer of value from the borrower to LP/treasury shares (`treasury-lp` minted on the next `accrue` call once debt exists) that was never legitimately earned — a theft of funds at the point of borrowing. A liquidity provider (or any actor) can also deliberately let a vault sit funded-but-idle for a long time, then wait for a borrower, to maximize the overcharge, similar to the attack vector called out in the referenced report.

### Likelihood Explanation
This triggers on ordinary usage: any vault with zero outstanding debt for even a modest window (deployment period, or a period after all debt is repaid) followed by a normal `borrow` call reproduces the issue without any special permissions, race conditions, or multi-party interference — it is a single-block, deterministic consequence of the call flow `system-borrow -> accrue -> mint debt`.

### Recommendation
`accrue` should record `last-update` unconditionally (or explicitly reset it to `stacks-block-time` whenever `scaled-principal` transitions from zero to a value, or whenever `scaled-principal` was zero at entry), rather than gating the timestamp bump on whether `index`/`lindex` changed. A simple fix is to always `(var-set last-update stacks-block-time)` at the end of `accrue`, independent of whether the indexes moved, so that no matter how long the vault has zero debt, the recorded "clock" always reflects the true elapsed-time baseline for the next interest computation.

### Proof of Concept
1. Vault is funded with liquidity; `scaled-principal` is `u0`. `accrue` is called (e.g., via deposit): `next == idx` and `nliq == lindex` because with zero utilization the index does not move, so the `is-eq` guard is true and `last-update` is left unchanged at time T0. [5](#0-4) 
2. Time passes — e.g., 100 days — with the vault still carrying zero debt; every intervening `accrue` call keeps skipping the `last-update` bump for the same reason.
3. A borrower calls `market.borrow`, which triggers `market-vault`'s call chain into `vault-system-borrow`, which calls `system-borrow` on the underlying vault contract, which calls `accrue` first: [4](#0-3) 
4. Because `scaled-principal` is still `u0` at the moment `accrue` runs (the debt hasn't been added yet), `next` again equals `idx`, so `last-update` still is not bumped to the current time.
5. `system-borrow` then sets `principal-scaled` to a nonzero value, giving the vault debt for the first time — but `last-update` still reflects T0, 100 days earlier.
6. On the very next `accrue` invocation (any subsequent vault interaction), `next-index` computes elapsed time as `stacks-block-time - last-update` (spanning the full 100-day stale window) and applies the corresponding interest to the now-nonzero `scaled-principal`, so the first borrower is charged 100 days of accrued interest despite having held debt for only a fraction of that period.

Note: I was unable to retrieve the body of the private `next-index`/`next-liquidity-index` functions within the available tool budget, so the precise interest-rate curve (in particular, whether the base rate at zero utilization is exactly zero, which is what causes `next == idx` when `scaled-principal` is `u0`) could not be directly confirmed from source in this session. The conditional `last-update` bump logic shown above, however, is confirmed and is structurally identical to the "clock advanced only on change" analog class regardless of the rate curve specifics whenever utilization-driven rate models yield zero rate at zero debt (the standard design for kinked/utilization-based lending curves). A Devin session with full repo access should verify `next-index`/`next-liquidity-index` to confirm the zero-utilization behavior before remediation.
