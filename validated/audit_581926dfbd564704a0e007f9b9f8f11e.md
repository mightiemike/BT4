## Title
Wallet Contract's `has_in_flight_tx` flag can be permanently stuck due to unbounded gas cost of external call callback — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (`WalletContract`) exhibits the same strong-coupling pattern as the OGV `OgvStaking`/`RewardsSource` bug: a core state invariant (`has_in_flight_tx`) is reset only as the *first* statement of a callback that subsequently performs additional gas-metered work depending on data returned by an external, attacker-influenceable contract (a NEP-141 token or the address registrar). If that later work exceeds the callback's fixed attached gas, the whole receipt — including the earlier reset of `has_in_flight_tx` — is rolled back, permanently locking the wallet's only entry point, `rlp_execute`.

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` before returning a promise chain, and the invariant documented at [1](#0-0)  requires it to be reset to `false` whenever the chain finishes. Every callback resets it as its first line, e.g. in `nep_141_storage_balance_callback`: [2](#0-1) 

After that reset, the callback deserializes the external contract's response and, depending on its content, builds further promises (a two-hop `storage_deposit` + token transfer batch) using data whose size/content is controlled by the target NEP-141 token contract: [3](#0-2) 

The gas attached to this callback is a fixed static budget plus the inner action's gas: `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())`, computed once at call time in `inner_rlp_execute`: [4](#0-3) 

Per the runtime's execution model, if any action within a receipt fails (including running out of gas mid-execution), the *entire* receipt's state changes are rolled back via `TrieUpdate`, as documented in the runtime crate: [5](#0-4) [6](#0-5) 

Because `has_in_flight_tx = false` is written at the top of the callback function body but the WASM execution can still exhaust gas later in the *same* function call (deserializing an oversized/malformed response from a malicious or buggy token contract, or building large follow-up promises), an out-of-gas failure late in the callback rolls back the whole action, undoing the `has_in_flight_tx = false` write. The flag is left permanently `true`.

Once `has_in_flight_tx` is stuck at `true`, every subsequent call to `rlp_execute` — the sole entry point for the wallet's owner to submit any Ethereum-style transaction — immediately short-circuits with a failure and can never proceed: [7](#0-6) 

This mirrors the reported bug class exactly: a core function (`rlp_execute`, analogous to `stake`/`unstake`) is strongly coupled to an external call (a NEP-141 token / registrar, analogous to `RewardsSource`) whose behavior (a large or unusual response) can permanently break the core functionality, with no try/catch-style isolation protecting the critical invariant reset from being rolled back together with the triggering failure.

### Impact Explanation
Any account holding a deployed `WalletContract` (the NEAR-side representation of an Ethereum-style EOA) can be permanently denied the ability to submit new transactions through it — a permanent freeze of that account's ability to move its own funds/tokens via this contract, since `rlp_execute` is its only entry point. This is a transaction-triggerable, single-call condition (no privileged actor, validator, or network-layer behavior required), fitting "permanently frozen funds"/halted core functionality.

### Likelihood Explanation
The trigger only requires a `target`/`token_id` chosen by the transaction (an attacker can deploy or control a NEP-141-like contract that returns an oversized `storage_balance_of` payload, or otherwise makes the callback's post-reset logic gas-expensive) and enough gas headroom relative to the fixed callback budget to make the *second half* of the callback (after the reset line) the part that exhausts gas. Because relayers determine what `target`/actions get executed for a given signed Ethereum-style tx and the wallet must accept arbitrary target token contracts for ERC-20 style transfers, a malicious or buggy relayer/token can realistically trigger this without any special privilege.

### Recommendation
Do not rely on ordering-within-a-single-receipt to make `has_in_flight_tx` durable. Split the invariant reset into its own low-gas, first-committed step (e.g., commit the flag reset via a dedicated minimal-gas callback/receipt before any variable-cost, externally-influenced processing begins), or bound/validate the size of external responses before doing further gas-metered work, and attach generous, response-size-independent gas headroom (or reject oversized responses early) so that later failures cannot roll back the already-intended state reset.

### Proof of Concept
1. Deploy an "evil" NEP-141-compatible contract whose `storage_balance_of` view method returns a very large (but well-formed) JSON payload (up to the max return-value size).
2. As a relayer, submit `rlp_execute` on a `WalletContract` account with an RLP-encoded `ERC20Transfer` naming the evil contract as `target`.
3. `inner_rlp_execute` schedules `storage_balance_of` on the evil contract followed by `nep_141_storage_balance_callback`, sized only by `NEP_141_STORAGE_BALANCE_CALLBACK_GAS + action.gas()` [4](#0-3) .
4. The callback runs, sets `has_in_flight_tx = false`, then attempts `serde_json::from_slice` on the oversized payload and/or builds the follow-up multi-action promise; this consumes gas beyond the fixed budget and the receipt fails with an out-of-gas error.
5. Because the receipt failed, all its state writes (including the `has_in_flight_tx = false` write) are rolled back per the runtime's rollback-on-failure semantics.
6. Any further call to `rlp_execute` on this account now immediately returns `"transaction already in progress, please try again later"` forever, permanently locking the wallet contract.

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };

        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;

```markdown
Action receipts contain a list of actions to execute. They arrive on the `receiver_id`'s account and execute actions from the list, one after the other.
If any action fails, the whole receipt fails, its execution outcome is Err.
There are many types of actions. The most interesting one is `FunctionCall` action, which allows to call a method on a smart contract in WASM.
```
