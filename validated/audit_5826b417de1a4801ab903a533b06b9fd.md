### Title
Missing Chain-Binding in `DelegateAction` Signed Payload Enables Cross-Network Replay by Malicious Relayer — (`File: core/primitives/src/action/delegate.rs`)

---

### Summary

`DelegateAction` (NEP-366) and `DelegateActionV2` (NEP-611) signed payloads contain no chain ID, network identifier, or `block_hash`. The `SignableMessage` discriminant is a constant derived solely from the NEP number and is identical on every NEAR network (mainnet, testnet, betanet). A `SignedDelegateAction` that Alice signs for testnet is cryptographically valid on mainnet if the same account, key, and nonce conditions hold. A malicious relayer — an ordinary unprivileged user — who receives Alice's off-chain `SignedDelegateAction` can submit it on a different NEAR network, executing Alice's inner actions (including token transfers) without her authorization on that network.

---

### Finding Description

`DelegateAction` is the signed inner payload of a meta transaction. Alice signs it off-chain and hands it to a relayer, who wraps it in a regular `SignedTransaction` and submits it on-chain. The protocol verifies the signature, nonce, and `max_block_height`, but **never verifies that the action was intended for the current network**.

The signed hash is computed in `DelegateAction::get_nep461_hash`:

```rust
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}
``` [1](#0-0) 

`SignableMessage` prepends a `MessageDiscriminant` whose value is `(1 << 30) + 366` — a compile-time constant identical on every NEAR network:

```rust
const MIN_ON_CHAIN_DISCRIMINANT: u32 = 1 << 30;
const NEP_366_META_TRANSACTIONS: u32 = 366;
// discriminant = 1_073_742_190 — same on mainnet, testnet, betanet
``` [2](#0-1) 

The `DelegateAction` struct itself contains no chain-binding field:

```rust
pub struct DelegateAction {
    pub sender_id: AccountId,
    pub receiver_id: AccountId,
    pub actions: Vec<NonDelegateAction>,
    pub nonce: Nonce,
    pub max_block_height: BlockHeight,
    pub public_key: PublicKey,
    // ← no block_hash, no chain_id, no network identifier
}
``` [3](#0-2) 

Contrast with `TransactionV0`, which includes `block_hash` to bind the transaction to a specific chain: [4](#0-3) 

At execution time, `apply_delegate_action` verifies the signature, `max_block_height`, `sender_id`, nonce, and access-key permissions — but performs no check that the action was signed for the current network:

```rust
pub(crate) fn apply_delegate_action(...) {
    if !signed_delegate_action.verify() { ... }          // sig check — network-agnostic
    if apply_state.block_height > delegate_action.max_block_height() { ... }  // height only
    if delegate_action.sender_id().as_str() != sender_id.as_str() { ... }
    validate_delegate_action_key(...)?;                  // nonce + key permissions
    // ← no network / chain-ID check
``` [5](#0-4) 

The same gap exists in `DelegateActionV2` / `VersionedDelegateActionPayload::get_nep461_hash`, which uses `SignableMessageType::DelegateActionV2` → discriminant `(1 << 30) + 611`, also a network-agnostic constant: [6](#0-5) 

---

### Impact Explanation

**Unauthorized transaction / loss of funds.**

Alice signs a `DelegateAction` on testnet to transfer 100 NEAR to Bob. She sends the `SignedDelegateAction` off-chain to a relayer. A malicious relayer submits it on mainnet instead. If Alice has the same account and key on mainnet and her mainnet nonce for that key is lower than the testnet nonce she used, the runtime accepts the action: Alice's mainnet balance is debited 100 NEAR and Bob's mainnet balance is credited — without Alice ever authorizing a mainnet transfer. The relayer pays only the gas cost (a small fraction of the transferred amount).

The corrupted value is Alice's mainnet `account.amount`, reduced by the transfer deposit without her authorization on that network.

---

### Likelihood Explanation

- Many users share the same account name and key pair across NEAR networks (mainnet / testnet / betanet).
- Testnet accounts are typically more active, so testnet nonces are often higher than mainnet nonces, making the mainnet nonce condition trivially satisfiable.
- `max_block_height` is typically set to a large future value (e.g., `current_height + 100`), which is also valid on mainnet.
- The relayer is an ordinary unprivileged user; no validator or peer access is required.
- The attack requires only that the relayer receive the off-chain `SignedDelegateAction` and submit it to a different network's RPC endpoint — a single JSON-RPC call.

---

### Recommendation

Bind the `DelegateAction` signed payload to a specific network by including a chain-identifying field in the signed data. Two options:

1. **Add a `block_hash` field** to `DelegateAction` (mirroring `TransactionV0`). The runtime would validate it via `check_transaction_validity_period`, which already verifies chain membership.
2. **Add a `chain_id` field** (e.g., the genesis block hash or a genesis-config-derived constant) and validate it in `apply_delegate_action` against `apply_state`'s chain identity.

Either approach ensures that a `SignedDelegateAction` produced for one NEAR network is cryptographically invalid on any other network, closing the cross-network replay vector.

---

### Proof of Concept

1. Alice has account `alice.near` with key `K` and nonce `N=5` on mainnet, and nonce `N=10` on testnet.
2. Alice signs a testnet `DelegateAction`:
   ```
   DelegateAction {
     sender_id: "alice.near",
     receiver_id: "alice.near",
     actions: [Transfer { deposit: 100 NEAR }],
     nonce: 11,          // valid on testnet (> 10), also valid on mainnet (> 5)
     max_block_height: 999_999_999,
     public_key: K,
   }
   ```
   Hash = `sha256( le32(1<<30 + 366) || borsh(DelegateAction) )` — identical on both networks.
3. Alice sends the `SignedDelegateAction` off-chain to a relayer intending testnet submission.
4. The malicious relayer instead submits it on mainnet via `broadcast_tx_commit`:
   ```json
   { "signed_tx": "<relayer_tx wrapping SignedDelegateAction>" }
   ```
5. `apply_delegate_action` on mainnet:
   - `verify()` → **passes** (same key, same hash)
   - `block_height <= max_block_height` → **passes**
   - `sender_id == receipt.receiver_id` → **passes**
   - nonce `11 > 5` → **passes**
6. A new receipt is created routing 100 NEAR from `alice.near` to `alice.near`'s `receiver_id` on mainnet. Alice's mainnet balance is drained without her authorization.

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

    // Generate a new receipt from DelegateAction.
    let new_receipt = Receipt::V0(ReceiptV0 {
        predecessor_id: sender_id.clone(),
        receiver_id: delegate_action.receiver_id().clone(),
        receipt_id: CryptoHash::default(),

        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: action_receipt.signer_id().clone(),
            signer_public_key: action_receipt.signer_public_key().clone(),
            gas_price: action_receipt.gas_price(),
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: delegate_action.get_actions(),
        }),
    });

    // Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas.
    // If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction.
    // Gas is refunded to the signer, this is Relayer.
    // Some contracts refund the deposit. Usually they refund the deposit to the predecessor and this is sender_id/Sender from DelegateAction.
    // Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit.

    let prepaid_send_fees = total_prepaid_send_fees(&apply_state.config, action_receipt.actions())?;
    let required_cost = receipt_required_cost(apply_state, &new_receipt)?;
    // This gas will be burnt by the receiver of the created receipt.
    // Compute costs of that are not relevant at this point, the "used" gas is
    // only reserved for execution later, potentially on a different shard.
    result.gas_used = result.gas_used.checked_add_result(required_cost.gas)?;
    // This gas was prepaid on Relayer shard. Need to burn it because the receipt is going to be sent.
    // gas_used is incremented because otherwise the gas will be refunded. Refund function checks only gas_used.
    result.gas_used = result.gas_used.checked_add_result(prepaid_send_fees.gas)?;
    result.gas_burnt = result.gas_burnt.checked_add_result(prepaid_send_fees.gas)?;
    result.compute_usage = safe_add_compute(result.compute_usage, prepaid_send_fees.compute)?;
    result.new_receipts.push(new_receipt);

    Ok(())
}
