### Title
Unbounded per-slot fanout in `notify_watchers` allows N×M CPU cost disproportionate to fee revenue - (File: rpc/src/rpc_subscriptions.rs)

### Finding Description
`RpcSubscriptions::notify_watchers` (rpc/src/rpc_subscriptions.rs, lines 908-1185) runs once per `NotificationEntry::Bank(CommitmentSlots)` and parallel-iterates over *all* commitment-watching subscriptions via `subscriptions.into_par_iter().for_each(...)` at [1](#0-0) . For `SubscriptionParams::Program(params)`, the per-subscription work calls `bank.get_program_accounts_modified_since_parent(&params.pubkey)` via `check_commitment_and_notify`, which — for that single subscription — scans/collects all accounts owned by the given program that were modified since the parent bank [2](#0-1) . This means each `Bank` notification event does O(subscriptions) parallel work items, and each `Program`-subscription work item itself costs O(accounts-modified-under-that-program-in-the-slot). An attacker who is also a normal RPC client can (a) subscribe to a program they own (paying only for the subscription, not for the notification pipeline), and (b) in the same slot, submit many cheap transactions that each write to a distinct account owned by that program. This directly multiplies the per-notification cost by the number of modified accounts M, while the attacker only pays the base transaction fee for M cheap transactions, not for the O(N subscriptions × M accounts) downstream fan-out cost incurred on the `solRpcNotify` thread pool.

For the `Account` and `Signature` cases the per-subscription cost is O(1) (single `get_account_modified_slot`/`get_signature_status_processed_since_parent` lookup), so those do not exhibit the N×M blow-up claimed generically in the question — only the `Program` subscription path does. There is no cost-accounting or rate-limiting in `notify_watchers` that ties the aggregate CPU work per `Bank` notification to the fees paid for the underlying transactions; the loop simply iterates over every active subscription and, for `Program` subscriptions, over every account touched under the filtered program, with no cap.

### Impact Explanation
This matches the "RPC DoS" / disproportionate CPU cost category, but it is capped by rules in scope: the exploit requires the attacker to (1) hold an active `programSubscribe` subscription (an RPC client action, not a single call within `CLUSTER_SLOT_TIME_TARGET/2`) and (2) generate many transactions touching many program-owned accounts within a slot. The scoped impact is CPU load on the `solRpcNotify` rayon thread pool proportional to (subscriptions × accounts-touched-per-program), which can starve notification delivery for other subscribers on the same node, but it does not affect consensus, AccountsDB correctness, hashing, or snapshot integrity — it is confined to the optional RPC pubsub subsystem and only affects nodes that have `programSubscribe` enabled with committed subscribers.

### Likelihood Explanation
Feasibility requires an actively maintained websocket subscription (attacker-controlled, since attacker is also an RPC client) plus repeated cheap transactions writing to distinct accounts owned by the subscribed program, submitted every slot. This is realistic for a single self-hosted program + self-subscribed client, but the "attack" surface is bounded by the number of transactions the attacker can land in a slot (limited by compute/fee-market and block space), and by the fact that this cost also scales with the attacker's own transaction volume for which they pay a fee. The out-of-scope rule excludes "RPC DoS needing more than one call per CLUSTER_SLOT_TIME_TARGET/2" — the notify_watchers path is not driven by a single external call but by the natural bank-freeze notification cadence (once per slot at most), so the primitive itself doesn't violate that per-call constraint, but the amplification is via subscription persistence + repeated transactions.

### Recommendation
Bound `get_program_accounts_modified_since_parent` result set (or the resulting notification/filter work) per subscription per slot, and/or move to an incremental changed-accounts diff structure so that Program subscription cost scales with actual notified diffs rather than raw modified-account count. Additionally consider per-subscription rate/cost limiting proportional to declared commitment level and enforce a maximum "accounts touched per program per notification" cap with truncation/backpressure, and track aggregate notify_watchers CPU time per subscription in metrics to allow throttling misbehaving subscriptions.

### Proof of Concept
Rust benchmark/integration test plan (using existing test harness `rpc/src/rpc_subscriptions.rs` test utilities, e.g. `RpcSubscriptions::new_for_tests`, and `rpc_pubsub_service::test_connection` as seen in `test_account_commitment`):
1. Create a bank, deploy/own N distinct program-owned accounts (M) under a single program ID.
2. Establish 1 `programSubscribe` subscription with `finalized`/`confirmed` commitment for that program.
3. In a single slot's bank, process M transactions each modifying a distinct account owned by that program, keeping total fees fixed and small (M cheap transfers/allocations).
4. Call `subscriptions.notify_subscribers(commitment_slots)` (which enqueues `NotificationEntry::Bank`) and directly time `RpcSubscriptions::notify_watchers` (or measure end-to-end wall clock via the notification channel) for increasing M (e.g., M = 10, 100, 1000, 10000) while keeping subscription count fixed at 1.
5. Assert/observe that wall-clock time in `notify_watchers` for the Program branch grows with M (i.e., `total_time.as_us()` in the `datapoint_info!("rpc_subscriptions", ...)` block), demonstrating unbounded scaling with attacker-controlled M rather than being bounded by a linear function of total fees paid (fees stay near-constant per cheap tx while cost grows with account count scanned by `get_program_accounts_modified_since_parent`).
6. Repeat with N subscriptions (multiple `programSubscribe` clients) to show the N×M multiplicative growth, confirming the `into_par_iter().for_each` fan-out amplifies cost by subscriber count with no cap tied to fee revenue.
