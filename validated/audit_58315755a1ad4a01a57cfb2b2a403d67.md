### Title
Unprivileged AMM trade can drain an Exchange pool's counter-token balance to near-zero in a single transaction, mirroring the clone-can-zero-limit pattern - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
`ExchangeTransactionActuator` lets any unprivileged account trade against a bancor-style liquidity pool that was created and funded by a different account (the pool creator, who can only reclaim funds via `ExchangeWithdrawActuator`, gated to the creator address). Just like the Frankencoin `reduceLimitForClone()` bug — where an unprivileged clone action can push another user's `limit` to zero in one call because the formula has no floor/reserve for the original owner — the `ExchangeTransactionActuator` formula has no reserve/floor protecting the counter-token balance that ultimately belongs to the pool creator. A single large sell order from any address can drive the other token's balance in the exchange down to a negligible amount, effectively destroying the creator's economic stake with no consent and no fee compensation to the creator.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `ExchangeCapsule.transaction()` [1](#0-0) , which delegates to `ExchangeProcessor.exchange()` using a Bancor-relay formula: [2](#0-1) 

The only validation performed in `doValidate()` bounds the balance of the token being **sold** (must stay below `getExchangeBalanceLimit()`), but places **no floor or reserve check** on the token balance being **bought out of** the pool: [3](#0-2) 

Because the exchange rate is `exchangeBalance = balance * (pow(1 + supplyQuant/supply, 2000) - 1)`, an unprivileged caller who supplies a sufficiently large `sellTokenQuant` can extract nearly the entire counter-token balance in one transaction, leaving the pool (and implicitly the pool creator, who is the only one authorized to `ExchangeWithdrawActuator` the remaining funds) with a balance near zero. Withdrawal by the creator is only blocked by an exact `== 0` check [4](#0-3) , so the creator's claim can be reduced to a negligible remainder without ever formally reaching the "closed" state, and without any compensating fee proportional to the loss inflicted on the creator's stake — exactly the "acknowledged but unmitigated" characteristic of the original Frankencoin finding (no reserved amount for the original stakeholder, no fee charged to the party causing the reduction).

### Impact Explanation
Any anonymous account broadcasting a single `ExchangeTransactionContract` can unilaterally and irreversibly collapse the value of a TRC10/TRX liquidity pool created by another account, without that creator's consent, mirroring "position limit could be fully reduced to zero by clones." This constitutes accounting/asset corruption reachable directly from a broadcast transaction.

### Likelihood Explanation
The path is reachable by any account with a top-level `ExchangeTransactionContract` transaction and requires only enough of the sell token/TRX to cover the trade plus the small `ExchangeTransactionFee`; no special privilege, node compromise, or protocol-level bug is needed — only economically rational trading against an under-protected AMM design, exactly like the "no reserve for original owner" root cause in the referenced report.

### Recommendation
Introduce a reserve/floor mechanism (e.g., cap the fraction of a token's balance that a single trade or a set of unprivileged trades can withdraw from the pool per block, or require a minimum retained balance proportional to the creator's stake), and/or charge trades a fee that scales with pool-balance impact and is credited back to the exchange creator, analogous to the Frankencoin team's own suggested mitigation (fee-to-original-owner plus an untouched reserve).

### Proof of Concept
1. Account A calls `ExchangeCreateActuator` to create an Exchange pool with token X and token Y balances.
2. Account B (unprivileged, unrelated to A) broadcasts a single `ExchangeTransactionContract` selling a very large quantity of token X.
3. `ExchangeCapsule.transaction()` → `ExchangeProcessor.exchange()` computes `buyTokenQuant` approaching the near-entirety of token Y's balance (bounded only by the exponential relay formula, not by any reserve check) [5](#0-4) .
4. `doValidate()` only rejects the trade if `firstTokenBalance == 0 || secondTokenBalance == 0` prior to the trade [4](#0-3) , so the trade executes and the token Y balance is driven to a negligible remainder.
5. Account A, the pool creator, is left holding a nearly worthless pool with no recourse and no compensation, having received no fee from B for the drain.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
