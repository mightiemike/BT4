### Title
`liquidity_cap` on `TokenConfig` is declared but never enforced during inbound PRC20 deposits, allowing unbounded minting past the configured exposure limit - (File: `x/uexecutor/keeper/handler.go`)

### Summary
Aloe's H-4 shows that a risk-limiting metric (`liquidity`) that is supposed to gate a security parameter (IV → LTV) is meaningless if the code never actually measures/enforces it against attacker-influenced state, letting the "cap" be bypassed at negligible cost. Push Chain has a structurally identical pattern: `uregistry.TokenConfig.LiquidityCap` is documented as the "max supply cap for this token" but is never read or compared against any running total anywhere in the deposit/minting path.

### Finding Description
`TokenConfig.LiquidityCap` is defined as the exposure/risk limit for a bridged asset: [1](#0-0) . The only place this field is checked is `ValidateBasic`, and even there it is merely required to be a non-empty string — never parsed as a number or compared to anything: [2](#0-1) .

Tracing the actual inbound-deposit execution path — `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` — the token's `LiquidityCap` is never fetched or checked, only `NativeRepresentation.ContractAddress` and the raw transferred `Amount` are used to mint PRC20 into the recipient: [3](#0-2) [4](#0-3) . The same absence holds in `ExecuteInboundFundsAndPayload` and `ExecuteInboundGasAndPayload`, which call `depositPRC20` directly with the inbound amount and never consult `LiquidityCap` or any tracked cumulative-minted total: [5](#0-4) [6](#0-5) .

A repository-wide search confirms `LiquidityCap` only appears in protobuf plumbing, `ValidateBasic`, and test fixtures — it is never read by any keeper logic that performs minting/deposit accounting.

### Impact Explanation
Because there is no per-token cumulative-minted counter checked against `LiquidityCap`, any number of legitimate, honestly-observed inbound deposits for a given `chain:address` token can push total PRC20 supply for that asset arbitrarily far past the operator-declared cap, with zero additional validation cost beyond the normal inbound-voting flow. This defeats the stated purpose of `LiquidityCap` as a per-asset risk/exposure ceiling (analogous to Aloe's IV-derived LTV ceiling being bypassable for free): the "cap" provides no actual guarantee to protocol accounting, registry consumers, or downstream risk-management tooling that depends on it, even though ordinary users triggering inbound deposits are the only actors involved.

### Likelihood Explanation
High reachability: standard `MsgVoteInbound` traffic for `FUNDS`, `FUNDS_AND_PAYLOAD`, and `GAS_AND_PAYLOAD` inbound types drives every deposit call site, none of which consult `LiquidityCap`. No special privilege or malicious validator/relayer behavior is required — normal, honest inbound observation and voting is sufficient to exceed the cap once cumulative deposits for a token surpass the declared value.

### Recommendation
Track a per-token cumulative-minted (or currently-outstanding) supply value in `x/uregistry` or `x/uexecutor` state, and enforce it at the point of PRC20 deposit (`depositPRC20`/`CallPRC20Deposit`), rejecting or reverting inbound execution when a deposit would push the token's minted total above `LiquidityCap`. Ensure outbound burns/withdrawals decrement the tracked total symmetrically.

### Proof of Concept
1. Register a `TokenConfig` with `LiquidityCap = "1000000"` (small cap) for `chain:address` X, as done in the existing integration test setups, e.g. [7](#0-6) .
2. Submit repeated, independently-valid `Inbound` events (distinct `TxHash`/`LogIndex`) for the same token, each below any single-tx limit, and let honest Universal Validators vote them to quorum via `VoteOnInboundBallot` as in the existing test harness (`ExecVoteInbound`).
3. Each finalized ballot triggers `ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload`, calling `depositPRC20` → `CallPRC20Deposit`, which mints PRC20 with no reference to `LiquidityCap` at all.
4. Observe that cumulative minted PRC20 for the token exceeds `1000000` (the declared cap) with no error, guard, or revert triggered by the registry's own configured limit.

Note: I was unable to verify whether the PRC20 Solidity contract itself (deployed via `UniversalGatewayPC`/`UNIVERSAL_CORE` system contracts) enforces any cap in its `depositPRC20Token`/`mint` implementation, since the compiled contract source was not found in the indexed portion of this repository. If a cap check exists purely in the on-chain Solidity contract logic (outside the indexed `x/` and `precompiles/` Go code), this finding should be validated against that contract's bytecode/ABI before treating it as conclusively unenforced.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
