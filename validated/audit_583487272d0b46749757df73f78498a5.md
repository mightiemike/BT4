### Title
Fund-migration sweep amount computed from a stale balance snapshot — funds arriving at the old TSS address after the snapshot are excluded from the sweep and permanently stranded ([File: universalClient/tss/coordinator/coordinator.go])

### Summary
`solverMetaTryCatch()` in the original report assumes an unprivileged actor cannot alter `address(this).balance` between the moment a value is decided and the moment it is checked/used. The same class of assumption appears in Push Chain's TSS fund-migration flow: the coordinator queries the **live on-chain balance** of the old TSS address once, computes a fixed sweep amount from that single snapshot, and every validator signs a transaction that moves exactly that amount. Any native value that lands at the old TSS address after the snapshot but before/independently of the migration completing is not covered by the signed sweep transaction and has no other path to recovery.

### Finding Description
`InitiateFundMigration` (`x/utss/keeper/msg_initiate_fund_migration.go:13-137`) opens a migration only checking that **outbound** is disabled for the chain — it does **not** require inbound to be disabled: [1](#0-0) 

The coordinator then builds the actual sweep transaction in `buildFundMigrationTransaction` (`universalClient/tss/coordinator/coordinator.go:615-671`), which — when no `claimedAmount` is supplied — queries the *live* balance of the old TSS address from the external chain RPC and derives the transferable amount as `balance − gas − l1GasFee`: [2](#0-1) [3](#0-2) 

This is the exact analog of the audited bug's `startBalance`/`address(this).balance` pattern: a value that is fixed at one point in time (`balance` read via RPC) is trusted to still represent "everything the old key controls" when the transaction is later co-signed by the TSS quorum and eventually broadcast on-chain. Because:
1. Inbound to the chain is not gated off during migration (`InitiateFundMigration` only checks outbound), and
2. There is no mechanism shown in the module to re-snapshot or re-sweep the old address after the fund-migration transaction is signed and broadcast,

any native-asset transfer that reaches the old TSS address after the coordinator's balance query — whether from an ordinary/attacker-triggered deposit to the (now-retiring) address, a delayed relay, or a race with in-flight transactions — is not included in `TSSFundMigrationAmount` and is left behind at an address whose TSS key set is being phased out of active signing duty.

### Impact Explanation
Value left at the old TSS address after the swept amount is fixed cannot be recovered through the normal outbound flow (outbound has been intentionally disabled for that chain as a precondition of migration), and there's no automatic re-sweep in this codebase once a `FundMigration` record is created and voted `PASSED`. This is a **permanent loss/freezing of protocol/user-controlled funds** — the exact impact category called out in scope ("permanent loss, permanent freezing... of user or protocol-controlled funds") — reachable purely by an unprivileged party performing an ordinary deposit/transfer at the wrong moment, with no malicious validator, admin, or TSS-participant assumption required.

### Likelihood Explanation
Likelihood is **moderate**, not certain: it depends on the specific chain's inbound routing (whether ordinary user deposits are sent directly to the TSS-controlled address vs. a separate Gateway contract) and on the timing window between the coordinator's balance query and the transaction settling on the destination chain. I was not able to fully verify from the indexed code whether, for EVM chains, the "old TSS address" is itself the deposit-receiving vault or merely a signer for a separate Gateway contract — this materially affects whether ordinary user deposits can land on it at all. If the TSS EOA is only ever a relayer/signer and never a direct deposit target, the reachable impact would be limited to accidental/attacker-sent stray value rather than legitimate user funds, lowering severity. This distinction could not be confirmed with the available index and would need direct inspection of the Gateway/vault contract wiring and the `universalClient/chains/evm` deposit-detection logic.

### Recommendation
- Disable **inbound** (not just outbound) for a chain before/while a fund migration is pending, so no new value can be routed to the address whose balance was snapshotted.
- After the sweep transaction lands, re-query the old address's balance; if non-zero, either automatically create a follow-up migration/sweep, or explicitly flag the residual balance for an operator-driven recovery flow (mirroring the recommendation in the original report to make the "assumed static value" self-correcting/dynamically re-derived rather than trusted once and reused for a value/authorization decision).
- Consider requiring a balance re-check immediately before or during broadcast (or use a `sweep everything` primitive in the migration transaction itself where the target chain semantics allow it) so the transferred amount is determined atomically with settlement rather than from a stale off-chain read.

### Proof of Concept
Conceptual PoC (I do not have runtime access to construct and execute this against a live/testnet deployment):
1. Admin initiates `MsgInitiateFundMigration` for `chain X`, disabling outbound for `X` per the precondition check.
2. Coordinator queries old TSS address balance = `B`, computes sweep amount `B - gas - l1Fee`, and the TSS quorum signs/broadcasts the sweep tx.
3. Before that sweep tx confirms (or even after, if inbound remains enabled and a user submits a deposit that lands on the old address), a user or attacker sends additional native value `Δ` to the old TSS address on chain `X`.
4. The already-signed sweep transaction moves only `B - gas - l1Fee`; `Δ` remains at the old address.
5. Migration is voted `PASSED`; outbound for `X` stays disabled or moves to the new key exclusively; there is no code path shown that re-sweeps the old address, leaving `Δ` permanently stranded.
