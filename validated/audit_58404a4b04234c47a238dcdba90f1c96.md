### Title
Exchange (constant-product AMM) withdrawal lacks slippage/minimum-output protection - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
java-tron implements an on-chain constant-product AMM via `ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`, processed by `ExchangeInjectActuator`/`ExchangeWithdrawActuator` and the pool math in `ExchangeCapsule.transaction`. The withdraw path, `ExchangeWithdrawActuator.execute`, computes the paired-token refund purely from the exchange's live token balances at execution time and transfers it, without any user-supplied minimum-acceptable-amount parameter, exactly mirroring the `withdraw_liquidity` bug class described in the external report.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `min` / floor field for the paired token the caller is entitled to receive. [1](#0-0) 

In `ExchangeWithdrawActuator.execute`, `anotherTokenQuant` (the amount of the second asset refunded) is derived at execution time strictly from the current on-chain `firstTokenBalance`/`secondTokenBalance` ratio of the pool and the requested `tokenQuant`, then both assets are credited to the caller unconditionally: [2](#0-1) 

The `doValidate` step performs sanity checks (non-zero quant, token belongs to pool, sufficient pool balance, non-zero computed `anotherTokenQuant`, integer-precision check) but never lets the caller bound the *minimum* `anotherTokenQuant` they are willing to accept: [3](#0-2) 

Because the pool ratio can move between when the caller signs/broadcasts the transaction and when it is actually included in a block (via concurrent `ExchangeTransactionContract` swaps or `ExchangeInjectContract`/other `ExchangeWithdrawContract` calls from other participants, or simply block-inclusion delay), the amount of the paired asset ultimately received can be materially less than what the caller expected when constructing the transaction — with no on-chain mechanism to abort the withdrawal if the received amount falls below an acceptable threshold.

### Impact Explanation
Any address that is a pool creator can suffer economic loss on withdrawal because the actuator provides no slippage/minimum-output guard: the refund calculation and transfer happen atomically inside `execute` using whatever pool state exists at that moment, so an adverse pool-ratio shift (e.g., due to a large concurrent swap or another liquidity action being included first in the same block or immediately prior) directly reduces the value of `anotherTokenQuant` the withdrawer receives, with no way to cap this downside on-chain. This is a direct accounting/value-extraction impact on an unprivileged user's funds, matching the underlying bug class (unprotected withdrawal from an AMM-style pool) in the external report.

### Likelihood Explanation
The exchange feature is a long-standing, exposed on-chain contract type (`ExchangeWithdrawContract`) reachable by any account that created a pool via `ExchangeCreateContract`; withdrawal transactions are ordinary user transactions subject to normal mempool/block-ordering, so front-running or unlucky ordering relative to swaps/injects is plausible whenever the pool has meaningful trading activity. However, actual harm requires sufficient concurrent volatility/volume in a given exchange pool, and only the pool's designated creator can invoke the withdraw path (per the creator check in `doValidate`), which somewhat limits who is exposed and how often large pools with independent third-party liquidity churn exist. [4](#0-3) 

### Recommendation
Add an optional minimum-acceptable-amount field (e.g., `expected_another_token_min_amount`) to `ExchangeWithdrawContract`, and enforce it in `ExchangeWithdrawActuator.doValidate`/`execute` by rejecting the transaction (throwing `ContractValidateException`) if the computed `anotherTokenQuant` is below the caller-specified floor, mirroring standard AMM `amountAMin`/`amountBMin` slippage protection. Callers unwilling to bound this can simply set the value to `0` to preserve current behavior.

### Proof of Concept
1. Pool creator submits `ExchangeWithdrawContract{exchange_id, token_id, quant}` expecting a certain `anotherTokenQuant` based on the pool ratio observed off-chain when building the transaction.
2. Before this transaction is included, one or more `ExchangeTransactionContract` (swap), `ExchangeInjectContract`, or other actions shift `firstTokenBalance`/`secondTokenBalance` in `ExchangeCapsule`.
3. When the withdraw transaction executes, `ExchangeWithdrawActuator.execute` recomputes `anotherTokenQuant` from the now-different balances and unconditionally transfers the resulting (potentially much smaller) amount to the owner — there is no field or check in the contract/actuator to reject this outcome. [5](#0-4)
