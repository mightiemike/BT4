### Title
`TransactionOutput::ensure_match_transaction_info` never validates the state/hot-state/position checkpoint roots, letting replay-verify accept a corrupted state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity check used by replay/verification tooling to confirm that a locally re-executed transaction produces the same authenticated result (`TransactionInfo`) as the one stored in archived/synced ledger data. It checks status, gas, write-set hash, and event-root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that actually commit to the post-transaction global (and position/native-trading) state root.

### Finding Description
`ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) validates the four TransactionInfo fields it compares: status, gas_used, write-set hash vs `state_change_hash`, and event root vs `event_root_hash`: [1](#0-0) 

It then falls straight through with an inline acknowledgement that the state-root fields are not validated: [2](#0-1) 

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class committed fields of the object hashed and included in the transaction accumulator: [3](#0-2) 

This comparator is invoked by `storage/db-tool/src/replay_on_archive.rs`, whose entire purpose is to re-execute historical transactions from a backup/archive and confirm the locally computed result matches the authenticated `TransactionInfo` fetched from the archive: [4](#0-3) 

Because the state-root fields are skipped, `replay_on_archive` (and the equivalent call in `aptos-move/aptos-debugger/src/aptos_debugger.rs`) will report success even when the locally re-executed state root (computed by `StateCheckpointOutput`, see `execution/executor-types/src/state_checkpoint_output.rs:78-92`) diverges from the state root that was actually committed/authenticated for that version. The write-set hash check alone does not guarantee the resulting Merkle/JMT state root is correct, since state-root computation involves additional logic (state-summary merging, hot-state, position-state trees) beyond simply hashing the write set.

### Impact Explanation
This breaks the core guarantee that replay-verification tooling is meant to provide: independent, retrospective confirmation that historical state commitments are correct. A bug in state-checkpoint/JMT root computation, hot-state root computation, or the position-state root (native trading) path — whether from a regression, storage bug, or hard-fork-only divergence — would go completely undetected by `replay_on_archive`/`aptos-debugger`, since the tool's own author left the check disabled. This directly matches the in-scope "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "committed state that differs from the correct VM result... corrupts durable ledger data" categories: the authenticated `TransactionInfo.state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` can silently diverge from what is locally recomputed, and no automated safety net exists to catch it.

### Likelihood Explanation
The gap is not hypothetical — it is a self-documented TODO in the code (`TODO(trading-native): ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution`), confirming the maintainers are aware the check is currently absent and gated behind enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. Any state-root computation bug (in JMT construction, hot-state merge, or position-state summary) introduced before that flag is enabled/validated would pass replay-verify undetected today.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash` (when computed), and `position_state_checkpoint_hash` against the values produced by the local `StateCheckpointOutput`/executor pipeline, rather than deferring this until `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled. At minimum, replay/verification tools that consume this function should not report success without checking all state-root-bearing fields, since these are the fields ultimately protecting durable ledger integrity via the accumulator.

### Proof of Concept
Conceptual PoC (no privileged access required):
1. Take any version range where the executor computes a `state_checkpoint_hash` (or `position_state_checkpoint_hash` once the trading-native feature ships) that is wrong due to a bug in state-summary/JMT construction.
2. Run `replay_on_archive` (or `aptos-debugger`'s replay path) over that range against a backup/archive containing the original (correct or also-corrupted) `TransactionInfo`.
3. `ensure_match_transaction_info` only checks status, gas, write-set hash, and event-root hash (`types/src/transaction/mod.rs:2159-2196`); since the state-root fields are never compared (`types/src/transaction/mod.rs:2197-2204`), the tool reports success even though `state_checkpoint_hash`/`position_state_checkpoint_hash` differ from the locally recomputed state root — silently validating a corrupted state commitment.
