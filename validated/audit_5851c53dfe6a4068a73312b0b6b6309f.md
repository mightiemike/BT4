### Title
Contract-controlled `promise_set_refund_to` can permanently burn a caller's attached deposit when the refund target does not exist - (File: `runtime/near-vm-runner/src/wasmtime_runner/logic.rs`, `runtime/runtime/src/lib.rs`)

### Summary
The NEP-536 host function `promise_set_refund_to` lets any contract redirect the deposit refund of an outgoing receipt away from the natural predecessor to an arbitrary `AccountId` chosen by that contract [1](#0-0) . Refunds are always native NEAR "Transfer" receipts, and the protocol has a documented fallback for when a refund receipt itself fails: `"If the execution of a refund fails, the refund amount is burnt."` [2](#0-1)  This mirrors the Connext root cause: a fee/refund payment routed through a channel that can fail (wrong/unavailable target), with no safe fallback to the original depositor — except here the outcome is burning rather than reverting, converting a recoverable failure into a permanent, unrecoverable loss of user funds.

### Finding Description
When a receipt's action fails, the unspent attached deposit is refunded via `Receipt::new_balance_refund` to `receipt.balance_refund_receiver()`, which resolves to the `refund_to` field if set, otherwise the predecessor [3](#0-2) . This is exercised directly in `refund_unspent_gas_and_deposits` [4](#0-3)  and in `settle_state_init_deposit` [5](#0-4) .

The `refund_to` value is set entirely at the calling contract's discretion via `promise_set_refund_to`, with no validation that the target account exists or will continue to exist [6](#0-5) . If the refund receipt is then routed to a nonexistent account, the deposit-refund action receipt itself fails with `AccountDoesNotExist`. Per protocol design, the runtime treats refund receipts specially: rather than re-refunding or otherwise recovering, `apply_action_receipt` burns the deposit into `other_burnt_amount` when a refund fails [7](#0-6) . A dedicated test confirms this exact behavior: a refund to a missing account fails with `AccountDoesNotExist` and the account is never created, with the accompanying comment noting the reason is asserted specifically because "without this the test would also pass if the refund receipt were dropped instead of refused" [8](#0-7) .

The failure mode is entirely reachable by an ordinary, unprivileged contract deployed by any account: the contract creates a cross-contract call promise with an attached deposit from the caller, and calls `promise_set_refund_to` pointing at an account that does not exist (or that gets deleted before the refund executes). If the downstream action fails — which the receiving contract or a malicious/buggy called contract fully controls — the deposit that would normally return to the caller is instead permanently burnt, with no path back to the depositor.

### Impact Explanation
This constitutes permanently frozen/lost funds for the depositing caller: any user attaching a deposit through a contract that uses `promise_set_refund_to` with a bad target loses that deposit irrecoverably on the failure path, which is one of the concretely accepted "permanently frozen funds" outcomes. Unlike a normal failed cross-contract call (where the deposit safely refunds to predecessor), redirection converts what should be a safe rollback into an unrecoverable burn.

### Likelihood Explanation
Reachable via a single `FunctionCall` from any unprivileged account interacting with any contract that uses this host function (intentionally or due to a bug/race — e.g., the target account being deleted between promise creation and refund execution). No special privileges, validator status, or network-level compromise are required — an ordinary deployed contract and an ordinary transaction suffice.

### Recommendation
Validate (or re-validate at refund-execution time) that a `refund_to` target is a legitimate/live account before allowing the refund receipt to be routed there, or fall back to refunding the depositing predecessor instead of burning the deposit when the designated `refund_to` account does not exist. At minimum, ensure the refund-failure path attempts a safe fallback refund rather than unconditionally burning funds, consistent with how the base case (predecessor-refund) is already never allowed to be silently lost.

### Proof of Concept
1. Deploy a contract `A`. In one call, `A` creates a promise to some receiver `B` with `amount = deposit` attached (the caller's funds), and immediately calls `promise_set_refund_to(promise_idx, "does-not-exist.near")` [1](#0-0) .
2. Make the inner action to `B` fail (e.g., call a nonexistent method), analogous to the existing `test_refund_to` integration test structure [9](#0-8) .
3. Because the action fails, the runtime generates `Receipt::new_balance_refund("does-not-exist.near", deposit)` instead of refunding the caller/predecessor.
4. This refund receipt executes against a nonexistent account and fails with `ActionErrorKind::AccountDoesNotExist`, matching the assertion pattern in `refund_may_not_create_universal_account` [10](#0-9) .
5. Per `apply_action_receipt`, this failed refund is added to `other_burnt_amount` rather than returned to any account [7](#0-6)  — the original caller's deposit is permanently and unrecoverably lost.

pub fn promise_set_refund_to(
    ctx: &mut Ctx,
    memory: &mut [u8],
    promise_idx: u64,
    account_id_len: u64,
    account_id_ptr: u64,
) -> Result<()> {
    ctx.result_state.gas_counter.pay_base(base)?;
    if ctx.context.is_view() {
        return Err(HostError::ProhibitedInView {
            method_name: "promise_set_refund_to".to_string(),
        }
        .into());
    }
    let refund_to = read_and_parse_account_id(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        &ctx.config,
        account_id_ptr,
        account_id_len,
    )?;
    let promise = ctx
        .promises
        .get(promise_idx as usize)
        .ok_or(HostError::InvalidPromiseIndex { promise_idx })?;

    let receipt_idx = match &promise {
        Promise::Receipt(receipt_idx) => Ok(*receipt_idx),
        Promise::NotReceipt(_) => Err(HostError::CannotSetRefundToOnJointPromise),
    }?;

    ctx.ext.set_refund_to(receipt_idx, refund_to);
    Ok(())

    }

            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,

                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),

            .unwrap();
        let mut store_update = tries.store_update();

            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);

        // Assert on the reason, not just the absence: without this the test would

        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
