Found a concrete order-of-operations bug analogous to the Flayer issue: in `MaintenanceManager::doMaintenance()`, `witness.getVoteCount()` is used to accumulate the per-witness reward-per-vote value (`accumulateWitnessVi`) for the *current* cycle **before** the new votes for that same maintenance period (`countVote(votesStore)` → `witnessCapsule.setVoteCount(...)`) are applied to `witnessCapsule.getVoteCount()`. The stale (pre-update) vote count is then persisted as `setWitnessVote(nextCycle, ...)` for the *next* cycle, meaning the reward-per-vote denominator used for the next cycle's distribution is calculated from a vote count that doesn't reflect votes cast right before/at maintenance — analogous to Flayer's `quorumVotes` being fixed to a stale (pre-burn) `totalSupply`, permanently skewing the per-unit distribution. ### Title
Reward-per-vote (Vi) accumulation uses stale witness vote count recorded before vote-count updates are applied — (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
`MaintenanceManager::doMaintenance()` calls `delegationStore.accumulateWitnessVi(curCycle, witness.createDbKey(), witness.getVoteCount())` for the current cycle using the witness's `voteCount` field *before* that same method applies the epoch's new votes to the witness objects via `countVote(votesStore)` and `witnessCapsule.setVoteCount(...)`. The (now updated) vote count is only persisted for `nextCycle` via `delegationStore.setWitnessVote(nextCycle, witness.createDbKey(), witness.getVoteCount())` at the very end of the function.

### Finding Description
This mirrors the Flayer bug pattern exactly: a share/vote total is captured and baked into a reward calculation (`quorumVotes` in Flayer / `Vi` accumulation here) at a point in the same function *before* a state-mutating step that changes that total value (`sunsetCollection()` burning tokens in Flayer / `countVote()` updating `witnessCapsule.setVoteCount()` here) is executed. Because `accumulateWitnessVi` runs on line 99 using the pre-update `witness.getVoteCount()`, while the vote-count mutation happens later at lines 111-127, the reward-per-vote value computed for `curCycle` is derived from an out-of-date vote tally relative to the votes that are actually recorded for the witness at that point in the maintenance cycle. This value directly feeds `DelegationStore::accumulateWitnessVi`, which computes `deltaVi = reward * DECIMAL_OF_VI_REWARD / voteCount` and is later used by `VoteRewardUtil.computeReward`/`MortgageService.computeReward` (`deltaVi * userVote / DECIMAL_OF_VI_REWARD`) to determine each voter's claimable reward share. ### Impact Explanation
If the vote-count denominator used to compute `Vi` for a cycle is stale relative to the votes actually attributed to a witness for that cycle, the per-vote reward share (`deltaVi`) is computed against the wrong total. Depending on the direction of vote changes accumulated in `countVote`, this permanently misallocates a witness's reward pool across voters when they later withdraw via `VoteRewardUtil.withdrawReward`/`MortgageService.withdrawReward`, since `Vi` values are stored per cycle and never retroactively corrected. This affects all voters delegating to that witness and cannot be reversed once persisted, consistent with the "permanently locked/misallocated share of distributed value" impact class from the original report.

### Likelihood Explanation
This code path executes on every maintenance cycle (`doMaintenance()`) for every active witness whenever `useNewRewardAlgorithm()` is enabled and `allowChangeDelegation()` is active — i.e., it runs unconditionally as part of normal, unprivileged network operation (any user's votes cast in the prior epoch trigger the vote-count mutation). No special attacker action is required beyond normal voting activity, making it highly likely to manifest under standard operating conditions rather than requiring an adversarial trigger.

### Recommendation
Move `accumulateWitnessVi(curCycle, ...)` to occur after `countVote(votesStore)` has been applied and `witnessCapsule.setVoteCount(...)` persisted, or otherwise ensure the vote-count value used to accumulate `Vi` for `curCycle` is consistent (either both use pre-maintenance totals, or both use post-maintenance totals) with the value later stored via `setWitnessVote(nextCycle, ...)`. This requires careful analysis of the intended semantics of `curCycle` vs `nextCycle` vote counts to avoid off-by-one-cycle mismatches between the `Vi` accumulation and the persisted vote count.

Not independently reproduced (no test harness executed); this is a static code-flow analysis based on `MaintenanceManager.java` lines 96–162 and the downstream reward math in `VoteRewardUtil.java`/`DelegationStore` referenced above.
