### Title
Missing Validate-mode restriction on `replace_class` syscall allows account contracts to mutate their own class during transaction validation - (File: crates/blockifier/src/execution/syscalls/syscall_base.rs)

### Summary
The blockifier enforces a documented sandbox during `ExecutionMode::Validate` (the phase in which an account's `__validate__`/`__validate_declare__`/`__validate_deploy__` entry point runs, before the transaction is admitted to the mempool/block and before fees are charged). Several syscalls are explicitly blocked or restricted in this mode — `deploy`, `meta_tx_v0`, `call_contract` (to any address other than self), and `get_block_hash` (on recent blocks) — via `reject_syscall_in_validate_mode`/`is_validate_mode`/`InvalidSyscallInExecutionMode` checks. `replace_class`, however, has no such check in any of its three implementations (VM Cairo0/Cairo1 hint processor, native syscall handler), so it executes unconditionally regardless of execution mode.

### Finding Description
`SyscallHandlerBase::replace_class` in [1](#0-0)  only validates that the target class is declared and is a Cairo1 class, and then unconditionally calls `self.state.set_class_hash_at(...)`. It never inspects `self.context.execution_mode`, unlike the sibling `deploy` method a few lines below in the same file, which explicitly calls `reject_syscall_in_validate_mode("deploy")` when `should_reject_deploy(...)` returns true ( [2](#0-1) ). The same absence of a mode check exists in the deprecated (Cairo0) executor's `replace_class` ( [3](#0-2) ) and the native executor's `replace_class` ( [4](#0-3) ).

By contrast, `call_contract` is explicitly restricted so it cannot target another contract during Validate ( [5](#0-4) ), `deploy` is gated behind `should_reject_deploy` ( [6](#0-5) ), and `meta_tx_v0`/`get_block_hash` are similarly restricted ( [7](#0-6) , [8](#0-7) ). `replace_class` is the one state-mutating, "privileged" syscall documented elsewhere in the codebase as forbidden in a restricted execution mode (the SNOS "virtual OS" mode explicitly lists `ReplaceClass` as blocked, alongside `Deploy`, `GetBlockHash`, `MetaTxV0` — see [9](#0-8)  and the feature-contract test scenario that groups it with the other three forbidden syscalls [10](#0-9) ) — yet the equivalent restriction is missing in blockifier's actual `ExecutionMode::Validate` enforcement, which is the gate that matters for transaction validation/mempool admission.

This is directly analogous to CVE-2019-14817: Ghostscript's `-dSAFER` sandbox correctly restricted most privileged operations but missed enforcing the restriction for specific procedures (`.pdfexectoken` and others), letting a crafted script perform a state-changing/privileged action that the sandbox was supposed to block. Here, the Validate-mode sandbox correctly restricts `deploy`, `call_contract`, `meta_tx_v0`, and `get_block_hash`, but misses `replace_class`.

### Impact Explanation
An account contract's `__validate__` (or `__validate_deploy__`/`__validate_declare__`) can call `replace_class_syscall` to swap its own class hash mid-validation. Because `execute_validate_transaction`/gateway/mempool logic and fee-estimation code rely on the assumption that account code executed during validation is limited/side-effect-free (per the documented Validate-mode syscall allowlist), an account can:
- Change its bytecode during validation itself (e.g., always validate as "always succeed") and later, in the Execute phase, run a different, malicious class than what any pre-flight checks/simulations assumed, since class replacement mutates committed state directly via `set_class_hash_at`.
- Use this to pass repeated fee-charge/nonce validation cheaply while altering execution behavior for the paid phase within the same transaction, potentially enabling unauthorized account behavior or resource/fee-accounting mismatches between what was validated and what executes, since the class swap happens in the "trusted" validate phase that other components assume is restricted to read-only/self-check semantics.

This is a state-mutation/unauthorized-account-action class of bug reachable by any account contract (any transaction sender) with no operator or protocol privilege required.

### Likelihood Explanation
High likelihood of reachability: any account contract can call `replace_class_syscall` from its own `__validate__` function with a single Invoke/Declare/DeployAccount transaction — no operator or malicious-peer collusion is needed. It requires only deploying/declaring a custom account class, which any unprivileged transaction sender can do.

### Recommendation
Add an `ExecutionMode::Validate` gate to `replace_class` matching the pattern used for `deploy`/`meta_tx_v0`/`call_contract`, e.g. in `SyscallHandlerBase::replace_class` (`crates/blockifier/src/execution/syscalls/syscall_base.rs`) and the deprecated hint processor's `replace_class` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`), returning `InvalidSyscallInExecutionMode`/`reject_syscall_in_validate_mode("replace_class")` when `execution_mode == ExecutionMode::Validate`. Add a regression test (mirroring `disable_deploy_in_validate_mode_flag_behavior` in `crates/blockifier/src/execution/syscalls/syscall_tests/deploy.rs`) that asserts `replace_class` is rejected with "Unauthorized syscall replace_class in execution mode Validate." when invoked from `__validate__`.

### Proof of Concept
1. Deploy an account contract whose `__validate__` entry point calls `replace_class_syscall(new_class_hash)` (as already demonstrated reachable via `test_replace_class`, see `crates/blockifier/src/execution/syscalls/syscall_tests/replace_class.rs` lines 57-92, but invoked from a validate-mode context instead of a plain external call).
2. Submit an Invoke transaction from this account; during the gateway/mempool's `__validate__` execution (`ExecutionMode::Validate`), the `replace_class` syscall succeeds and mutates `state.set_class_hash_at(storage_address, new_class_hash)` with no `InvalidSyscallInExecutionMode` error, unlike an equivalent attempt using `deploy` in the same `__validate__` (`disable_deploy_in_validate_mode_flag_behavior` in `crates/blockifier/src/execution/syscalls/syscall_tests/deploy.rs` lines 323-362), which is correctly rejected.
3. Observe that the account's class hash is changed as a side effect of validation, before the paid Execute phase runs — a state mutation the Validate-mode sandbox is supposed to prevent.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
