### Title
Locked TRX/TRC10 due to non-reversible endowment transfer on failed precompiled contract call - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.callToPrecompiledAddress()` charges the call's endowment (TRX or TRC10) to the target address *before* the precompiled contract logic actually executes, and the code path explicitly comments that this charge "is not reversible by rollback." If the subsequent precompiled-contract execution fails (`out.getLeft() == false`), the method still pushes zero and returns without reversing the value transfer, mirroring the Ajna `StandardFunding.sol` pattern where funds are debited/allocated for an action whose execution can fail, with no code path to restore the funds to their origin.

### Finding Description
In `callToAddress`/`callToPrecompiledAddress`, calls to native/precompiled contracts (e.g. `VoteWitness`, `FreezeBalance`, `WithdrawReward`, proposal precompiles, etc.) are handled by creating a child `Repository deposit = getContractState().newRepositoryChild()` and only committing it back to the parent (`deposit.commit()`) on success: [1](#0-0) 

However, before invoking `contract.execute(data)`, the endowment (msg.value) is unconditionally transferred from `senderAddress` to `contextAddress` on that same `deposit`, and the code explicitly flags this transfer as not being reversible by a rollback: [2](#0-1) 

The execution result is then checked, and on failure the method merely refunds energy and pushes zero onto the stack — it does **not** attempt to reverse or refund the endowment that was already charged: [3](#0-2) 

This is structurally identical to the Ajna bug: value is deducted/allocated for an operation (a proposal execution / a precompiled-contract call) whose completion is not guaranteed, and the deduction is not conditioned on, or reversed by, the failure of that operation — with no accounting path that credits the funds back to the sender.

### Impact Explanation
If a precompiled-contract call (reachable via any TVM contract executing a `CALL`/`CALLCODE`/`DELEGATECALL`/`STATICCALL` to a native precompiled address with a nonzero endowment) fails after the value transfer step but before/while the underlying precompiled logic itself completes, TRX or TRC10 tokens sent as endowment can become effectively locked or misallocated at the target address without the corresponding action (vote, freeze, delegate, withdraw, etc.) taking effect — an asset/accounting corruption reachable from ordinary contract calls, not requiring any privileged actor.

### Likelihood Explanation
Reaching this code path only requires deploying/triggering an ordinary smart contract that performs a `CALL` with value to one of the precompiled contract addresses and constructs input data that fails inside `contract.execute(data)` (e.g., invalid encoded parameters causing the specific precompiled contract's business validation to fail after energy checks pass). This is achievable by any account via a normal `TriggerSmartContract` transaction, so likelihood is non-trivial, though it depends on precisely which precompiled contracts are wired through this path and whether their internal validation happens before or after the endowment transfer — this was not fully confirmed for every precompiled contract in the available time.

### Recommendation
Defer the endowment transfer until after `contract.execute(data)` succeeds, or perform the transfer within the same child repository transaction that is discarded on failure (i.e., make the "Charge for endowment" step actually reversible, contradicting the current comment), so that a failed precompiled contract invocation cannot result in funds being debited without the corresponding effect being applied. Alternatively, on failure, explicitly credit the endowment back to `senderAddress` before returning.

### Proof of Concept
Not independently verified end-to-end (would require constructing a `TriggerSmartContract` transaction whose bytecode issues a `CALL` with nonzero value directly to a precompiled contract address using input data that is malformed enough to make `contract.execute(data)` return `(false, ...)` after the endowment transfer at line 1706/1718, then checking `getAccountStore().get(contextAddress).getBalance()` — analogous to the balance-tracking assertions used in `RuntimeTransferComplexTest`/`EnergyWhenSendAndTransferTest`, e.g.): [4](#0-3) 
This was not run against the codebase; the exact set of precompiled contracts reachable via `callToPrecompiledAddress` and whether any allow endowment plus a failing `execute()` was not exhaustively confirmed.
