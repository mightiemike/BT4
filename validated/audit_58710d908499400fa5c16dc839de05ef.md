## Analysis

The reported bug class — an array/set that grows without bound as users interact with the system, and is later iterated in full inside a hot code path, causing disproportionate/ballooning cost — maps cleanly onto `AccountsDb`'s `zero_lamport_accounts_to_purge_after_full_snapshot` set.

### Title
Unbounded growth of `zero_lamport_accounts_to_purge_after_full_snapshot` causes disproportionate CPU cost in `clean_accounts` - (File: accounts-db/src/accounts_db.rs)

### Summary
`AccountsDb` maintains a `DashSet<(Slot, Pubkey)>` field, `zero_lamport_accounts_to_purge_after_full_snapshot`, that accumulates every zero-lamport account whose purge is deferred because its slot is newer than the latest full snapshot slot [1](#0-0) . Entries are inserted on essentially every `clean_accounts` pass that encounters a zero-lamport account created after the last full snapshot [2](#0-1) , and the set has no size cap. It is only drained (via a full `retain()` scan) once a full snapshot advances [3](#0-2) .

### Finding Description
Ordinary transaction activity (creating and then zeroing/closing accounts, e.g., token accounts) between two full snapshots causes new `(Slot, Pubkey)` entries to be appended to `zero_lamport_accounts_to_purge_after_full_snapshot` on each `clean_accounts` invocation via `filter_zero_lamport_clean_for_incremental_snapshots` [4](#0-3) . `clean_accounts` runs repeatedly on a fixed background cadence (`AccountsBackgroundService`) irrespective of how many zero-lamport accounts have accumulated [5](#0-4) , so the set keeps growing across many clean cycles until the next full snapshot is taken.

When the full snapshot slot finally advances, `construct_candidate_clean_keys` performs a single, synchronous `retain()` pass over the *entire* accumulated set inside the next `clean_accounts` call [6](#0-5) , followed by `sweep_slots_after_snapshot` iterating every slot in the swept range and looking up its storage entry [7](#0-6) . This is directly analogous to the `poolColl.tokens[]` pattern in the referenced report: an array/set with no upper bound that is fully scanned in a function whose cost is proportional to how much unrelated activity accumulated beforehand.

### Impact Explanation
An attacker (or normal heavy account churn) can inflate this set cheaply — creating and zeroing many distinct accounts costs the attacker only the usual transaction fees, while each entry adds a fixed-size `(Slot, Pubkey)` to an unbounded in-memory `DashSet`. The eventual full-snapshot-triggered `retain()` and `sweep_slots_after_snapshot` scan become proportionally more expensive as this backlog grows, causing a CPU/time spike concentrated into a single `clean_accounts` call on the validator's `AccountsBackgroundService` thread. This is a disproportionate-cost issue rather than a correctness bug (no capitalization or hash divergence occurs, since purging is correctly deferred for incremental-snapshot safety).

### Likelihood Explanation
Likelihood is proportional to the interval between full snapshots and the rate of zero-lamport account churn on cluster/validator, both of which unprivileged users can influence (by generating transactions that create and empty many accounts). No special privileges are needed to grow the set; it only requires ordinary transaction activity sustained across the full-snapshot interval.

### Recommendation
Bound or amortize the drain of `zero_lamport_accounts_to_purge_after_full_snapshot`: e.g., cap its size and force earlier partial draining/pressure-based cleaning, or spread the `retain()`/`sweep_slots_after_snapshot` work across multiple clean cycles rather than doing it all in one pass when the full snapshot slot advances.

### Proof of Concept
1. Disable/delay full snapshot generation (or note the normal snapshot interval).
2. Repeatedly submit transactions that create and then zero-out (close) many distinct accounts across many slots, ensuring each such zero-lamport update lands in a rooted slot that is later cleaned via `clean_accounts` while `latest_full_snapshot_slot` is not yet advanced past it.
3. Observe `zero_lamport_accounts_to_purge_after_full_snapshot`'s size grow unbounded across successive `clean_accounts` calls (see `filter_zero_lamport_clean_for_incremental_snapshots` insertion at accounts-db/src/accounts_db.rs:2367-2368).
4. Once the next full snapshot slot is set (`set_latest_full_snapshot_slot`), observe `clean_accounts`'s `construct_candidate_clean_keys` performing a `retain()` over the entire accumulated set plus `sweep_slots_after_snapshot` iterating every slot in range, with cost scaling with the churn volume from step 2.

    fn sweep_slots_after_snapshot(
        &self,
        last_swept_full_snapshot_slot: Slot,
        latest_full_snapshot_slot: Slot,
    ) -> u64 {
        let start = last_swept_full_snapshot_slot.saturating_add(1);

        let mut added_to_shrink_count = 0;
        {
            // Held for the scan. Safe because the only paths that take this lock in production
            // validator code run in earlier/later phases of the same AccountsBackgroundService
            // iteration, never concurrently with clean_accounts.
            let mut shrink_candidates = self.shrink_candidate_slots.lock().unwrap();
            for slot in start..=latest_full_snapshot_slot {
                if let Some(store) = self.storage.get_slot_storage_entry(slot) {
                    if store.has_only_tombstones() {
                        // Now just contains tombstones and no live index entries: purge
                        self.purge_dead_slots_from_storage(
                            iter::once(&slot),
                            &self.clean_accounts_stats.purge_stats,
                        );
                    } else if self.is_shrinking_productive(&store)
                        && self.is_candidate_for_shrink(&store)
                        && shrink_candidates.insert(slot)
                    {
                        added_to_shrink_count += 1;
                    }
                }
            }
        }

        self.last_swept_full_snapshot_slot
            .store(latest_full_snapshot_slot, Ordering::Relaxed);
        added_to_shrink_count
    }
