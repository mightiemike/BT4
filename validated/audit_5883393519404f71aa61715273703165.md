### Title
Time-of-check/time-of-use race in `ReadOnlyAccountsCache::remove_assume_not_present` can leave a stale account cached during ancient-storage squash - (File: accounts-db/src/read_only_accounts_cache.rs)

### Summary
The external report's bug class is "an operation that appears to succeed but silently performs no action because of an unchecked precondition" (a low-level `call()` returning `true` without actually executing anything when the target doesn't exist). The closest reachable analog in Agave's `AccountsDb` is `ReadOnlyAccountsCache::remove_assume_not_present`, which uses a non-atomic check-then-act pattern on a concurrent `DashMap` to decide whether to attempt a cache invalidation at all. If the precondition ("entry not present") is falsely true at the instant of the check, the removal call is skipped entirely and the stale/soon-to-be-stale cache entry survives, even though the caller believed the invalidation "succeeded."

### Finding Description
`remove_assume_not_present` is defined as: [1](#0-0) 

It performs `contains_key(pubkey)` and only calls `self.remove(pubkey)` if that check returns `true`; otherwise it returns `None` and no removal is attempted at all — this is explicitly a performance hint ("Assume the entry does not exist for performance"), not a correctness guarantee. Because `self.cache` is a `DashMap` accessed concurrently from multiple threads (readers doing `do_load` → `PopulateReadCache::True` → `store`, and background squash/shrink threads calling `remove_assume_not_present`), there is a window between the `contains_key` check and the (skipped) `remove` call where another thread can insert a fresh entry for the same pubkey. In that interleaving, the function returns having done nothing, mirroring the report's pattern where a call "succeeds" without performing the expected effect because an existence check was trusted without enforcing atomicity.

This function is invoked from `store_accounts_for_squash`, which is called during ancient-append-vec combining/squashing to flush read-only cache entries for accounts before their storage location changes: [2](#0-1) 

The comment at the call site acknowledges the assumption is probabilistic ("almost always the case that there is no read only cache entry ... give that hint ... for performance"), meaning the code path is designed around an assumption that is not always true, and when it's false, no compensating recheck occurs.

### Impact Explanation
If a race causes an entry to be missed during invalidation around an ancient squash/shrink operation, the read-only cache can continue serving a `(pubkey → old AccountSharedData/slot)` mapping after the account's canonical storage location has moved. Because `AccountsDb::do_load` checks the read-only cache before falling through to `retry_to_get_account_accessor`/storage lookup, this can result in stale account data being returned for reads that hit the read-only cache, which is exactly the "stale/wrong-version account load" impact class relevant to this analog. In the worst case this could manifest as validators returning inconsistent account state for RPC/consensus-adjacent reads if the stale entry outlives further legitimate updates.

### Likelihood Explanation
This requires: (a) ancient squash/shrink to run concurrently with (b) a fresh `store()`/populate-read-cache event for the *same pubkey* landing in the narrow window between `contains_key()` and the (conditionally executed) `remove()`. Both ancient squash and read-population happen on background/replay threads under real validator load, so the race is plausible but requires precise timing; there is no simple single-threaded reproduction, and other invariants elsewhere in `AccountsDb` (e.g., write-cache checks preceding the read-only cache, and store_id/slot equality checks in `retry_to_get_account_accessor`) may reduce the observable blast radius, since the read-only cache is only consulted after the write cache misses. This tempers likelihood to moderate/low without a concrete reproduction.

### Recommendation
Make the invalidation atomic instead of check-then-act: replace `contains_key(...).then(|| remove(...))` with a single atomic `DashMap::remove` (or `remove_if`) call that doesn't rely on a preceding existence check to decide whether removal is attempted. This removes the TOCTOU window and ensures invalidation always occurs unconditionally regardless of whether the entry existed at check time, matching the semantics the "hint" comment assumes.

### Proof of Concept
No standalone PoC is available from static analysis alone; the race requires precise multi-thread interleaving between an ancient-squash thread calling `store_accounts_for_squash`/`remove_assume_not_present` and a concurrent reader thread calling `read_only_accounts_cache.store()` for the same pubkey between the `contains_key` check and the skipped `remove`. A dynamic reproduction (e.g., stress test with concurrent shrink/squash and repeated reads/populates of the same pubkey under a lock-step scheduler or `loom`-style interleaving harness) would be needed to demonstrate the stale entry surviving invalidation; this was not run in this analysis.

    /// remove entry if it exists.
    /// Assume the entry does not exist for performance.
    pub(crate) fn remove_assume_not_present(&self, pubkey: &Pubkey) -> Option<AccountSharedData> {
        // get read lock first to see if the entry exists
        self.cache
            .contains_key(pubkey)
            .then(|| self.remove(pubkey))
            .flatten()
    }

        &self,
        accounts: impl StorableAccounts<'a>,
        storage: &AccountStorageEntry,

        let slot = accounts.target_slot();

        // Flush the read cache if necessary
        let flush_read_cache_us = if self.read_only_accounts_cache.can_slot_be_in_cache(slot) {
            let flush_read_cache_time = Measure::start("flush_read_cache");
            (0..accounts.len()).for_each(|index| {
                // Based on the patterns of how a validator writes accounts, it is almost always
                // the case that there is no read only cache entry for this pubkey and slot.
                // So, we can give that hint to the `remove` for performance.
                self.read_only_accounts_cache
                    .remove_assume_not_present(accounts.pubkey(index));
            });
            flush_read_cache_time.end_as_us()
        } else {
            0
        };
