### Title
Potential chunk-halting panic via `unwrap()` on `receiver_shard_id` for stale delayed receipts after resharding - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` (and its use in `pop`/`peek_iter`) calls `receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap()` while draining the delayed receipt queue. [1](#0-0)  If a receipt in the queue targets a shard id that no longer maps cleanly under the current epoch's `shard_layout` (e.g. a stale `GlobalContractDistribution` receipt surviving across two resharding generations, as noted in a dedicated regression test), `receiver_shard_id` can return an `Err`, and the `.unwrap()` will panic.

### Finding Description
This directly mirrors the CVE-2021-47522 bug class: code assumes a derived value (`report_field` / here, `receiver_shard_id`) is always present/valid for every item reached by the surrounding loop, but a legitimately reachable state (uhid device with no output reports / a receipt surviving two resharding transitions) breaks that assumption, producing a null-deref-equivalent panic. The nearcore team already added a repro test acknowledging this exact scenario: `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs`, whose comment explicitly states: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old `target_shard` after two resharding generations." [2](#0-1)  The delayed receipt queue is drained during ordinary chunk apply (`DelayedReceiptQueueWrapper::pop`), which is invoked from the runtime's `apply` loop that every chunk producer/validator executes when processing any chunk. [3](#0-2) 

The receipt that ends up in this state originates from ordinary transaction/receipt flow (e.g. a global contract deployment transaction from any account, or any receipt whose target shard becomes stale across sequential resharding events), so it is reachable without any special privilege — the state precondition (double resharding while a receipt sits delayed) is triggered by chain configuration/timing rather than by an attacker needing elevated permissions, but the receipt itself can be created by an ordinary unprivileged transaction (e.g., `DeployGlobalContract`).

### Impact Explanation
If `receiver_shard_id` returns an error for a queued receipt (stale target shard across resharding boundaries) and the `.unwrap()` fires, `process_receipts`/`apply` panics inside the runtime. Because this happens deterministically for every node that must apply the same chunk, it would manifest as a synchronized crash/halt across chunk producers and validators processing that shard — a transaction-triggered chain halt, which is a valid, in-scope impact category (permanent liveness loss for the shard until manually patched/restarted).

### Likelihood Explanation
The existing dedicated regression test in the same repo (`test_stale_global_contract_distribution_after_double_resharding`) demonstrates the nearcore team's own belief that this scenario is reachable and was a real concern; the test is designed specifically to prove whether the panic still occurs. [4](#0-3)  Reaching this state requires: (1) an ordinary global-contract deployment transaction, (2) two sequential resharding events splitting the shard that held the deployer's account, and (3) the receipt still sitting in the delayed queue when the second split occurs. This is a non-trivial but achievable sequence of externally-observable/triggerable conditions (dynamic resharding is protocol-governed, but the timing of a delayed receipt surviving two splits can be engineered by an attacker saturating compute on the target shard, as the test itself does). I could not verify from the available code whether `receiver_shard_id` has since been hardened to avoid `Err` in this exact case elsewhere in the codebase — the `.unwrap()` call in `receipt_filter_fn` is unconditional, and I found no protective fallback for a shard-layout mapping miss at that call site specifically.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` (used from `pop` and `peek_iter`) with proper error propagation, or explicitly handle the "receipt's shard is stale/no-longer-mappable" case by treating such receipts as belonging to neither shard temporarily (skip without panicking) until a resharding-aware remap path (as already partially exists for `ShardsOutgoingReceiptBuffer` parent-shard forwarding) is applied to the delayed queue as well.

### Proof of Concept
The nearcore repository's own test demonstrates the trigger sequence: deploy a global contract from an account, force two sequential shard splits (dynamic resharding) of the shard containing that account while saturating chunk compute so the `GlobalContractDistribution` receipt stays in the delayed queue across both splits, then let the queue drain — if `receiver_shard_id` cannot remap the stale `target_shard`, `receipt_filter_fn`'s `.unwrap()` panics and the chain stalls. See `test_stale_global_contract_distribution_after_double_resharding` for the full reproduction steps. [5](#0-4)

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }
