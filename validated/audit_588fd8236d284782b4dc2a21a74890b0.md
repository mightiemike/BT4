### Title
`check_first_nakamoto_tenure_change` accepts any locally-known epoch2x header as the Nakamoto genesis parent instead of requiring it to be the canonical epoch2x tip - (File: `stackslib/src/chainstate/nakamoto/tenure.rs`)

### Summary
`check_first_nakamoto_tenure_change` only verifies that `previous_tenure_end` resolves to *some* stored epoch2x header whose `consensus_hash` matches `prev_tenure_consensus_hash`; it never checks that this header is the canonical/highest epoch2x block for that sortition. The generic block-commit-to-parent-tenure consistency check in `setup_normal_block_processing` is explicitly skipped for this transition because it is gated on `parent_chain_tip.is_nakamoto_block()`, which is false at the epoch2→Nakamoto boundary.

### Finding Description
The equality that should hold is: `tenure_payload.previous_tenure_end == <the canonical epoch2x chain tip as recorded by the node's own fork-choice rules for that sortition>`.

What is actually checked, in `check_first_nakamoto_tenure_change` (`stackslib/src/chainstate/nakamoto/tenure.rs:553-612`):
- `Self::get_block_header(headers_conn, &tenure_payload.previous_tenure_end)` — a raw lookup by `StacksBlockId` (consensus_hash + block_hash) in the local `nakamoto_block_headers`/epoch2 headers table. It returns whatever header exists with that exact ID, without any notion of "is this the tip the node/network settled on."
- `tenure_payload.previous_tenure_blocks != 1` — a shape check.
- `tenure_payload.prev_tenure_consensus_hash != parent_header.consensus_hash` — only checks that the *consensus hash* of whatever header was found matches the claimed one; it does **not** check that `parent_header.block_hash()` is the one and only anchored-block choice the network/node converged on for that sortition.
- `parent_header.anchored_header.as_stacks_epoch2()` — confirms it's an epoch2 header, nothing about canonicity.

Crucially, at the epoch2→epoch3 boundary, a sortition winner's anchored block can have competing valid candidates recorded in local chainstate (e.g. divergent microblock-stream forks producing distinct anchored blocks for the *same* winning sortition/consensus hash, one of which is chosen canonical by epoch2x fork-selection rules and the other of which remains stored as a non-canonical/orphaned block). `check_first_nakamoto_tenure_change`'s `prev_tenure_consensus_hash` match only distinguishes by consensus hash, not the actual block hash chosen as canonical, so a `previous_tenure_end` naming the stale, non-canonical block-hash variant with the correct consensus hash passes all of the function's checks.

The generic safety net that normally ties a Nakamoto tenure-change's declared parent to the sortition's own block-commit pointer (`stackslib/src/chainstate/nakamoto/mod.rs:4462-4497`, in `setup_normal_block_processing`) is explicitly bypassed here:
```
if tenure_cause.is_new_tenure()
    && parent_chain_tip.is_nakamoto_block()
    && !block.is_first_mined()
```
Since `parent_chain_tip` is an epoch2x block for the very first Nakamoto tenure, `parent_chain_tip.is_nakamoto_block()` is `false`, so this block never executes for the genesis transition, and there is no equivalent check that pins `previous_tenure_end` to the actual canonical epoch2x tip.

Attacker input: a miner who wins the first-ever Nakamoto sortition constructs a `TenureChangePayload` whose `previous_tenure_end` names a locally-existing but non-canonical epoch2x block (matching consensus hash, wrong block hash) instead of the network's actual canonical epoch2x tip, and mines/broadcasts the corresponding Nakamoto block.

### Impact Explanation
Nodes that stored the non-canonical epoch2x variant (e.g., because they briefly saw that microblock fork before reorging) will accept the block and permanently build their Nakamoto history from the wrong epoch2x state (wrong parent, hence wrong MARF root and wrong subsequent chain state). Nodes that never stored/kept that specific epoch2x header will reject the block outright (parent header lookup fails). This is a permanent, irreversible fork exactly at the Nakamoto activation boundary — matching the Critical category (chain split / deep fork, non-reproducible state root at the genesis of Nakamoto history).

### Likelihood Explanation
Requires: (1) the attacker to win a single sortition (any miner slot, no majority needed — matches the allowed unprivileged threat model), and (2) at least one honest node in the network to have locally stored a non-canonical epoch2x anchored-block variant sharing the consensus hash of the canonical tenure (a scenario the question's precondition explicitly calls out — late epoch2x microblock/anchor forks at the activation boundary, which do occur historically in Stacks' epoch2x fork-choice history). This is a narrow, boundary-specific condition (occurs exactly once per network, at Nakamoto activation), but if the precondition holds it is fully attacker-triggerable with a single winning block-commit, no signer majority or node compromise required.

### Recommendation
In `check_first_nakamoto_tenure_change`, resolve `previous_tenure_end`/`prev_tenure_consensus_hash` against the node's authoritative canonical epoch2x tip for that sortition (e.g., via `StacksChainState::get_stacks_block_anchored_at`/the sortition DB's recorded winning-stacks-block-hash for that consensus hash, analogous to `SortitionDB::get_block_snapshot_for_winning_stacks_block`) rather than an unscoped header lookup, and reject the tenure-change if `previous_tenure_end`'s block hash does not match that canonical record.

### Proof of Concept
Rust integration test plan (extends existing Nakamoto boundary test harness in `stackslib/src/chainstate/nakamoto/tests/node.rs`):
1. Build an epoch2x chain up to just before Nakamoto activation, and at the final epoch2x sortition, engineer two competing anchored blocks (e.g., two microblock-stream forks) sharing the winning sortition's `consensus_hash` but different `block_hash`, so both end up in local chainstate headers.
2. Have `SortitionDB`/epoch2x fork-choice rules pick block A as canonical; keep block B (non-canonical) also present in `nakamoto_block_headers`/headers table.
3. Construct a first Nakamoto `TenureChangePayload` with `previous_tenure_end = StacksBlockId(consensus_hash, B.block_hash())` and `prev_tenure_consensus_hash = consensus_hash`.
4. Assert `NakamotoChainState::check_first_nakamoto_tenure_change(headers_conn, &payload)` returns `Ok(Some(..))` (i.e., incorrectly accepts B), while asserting the true canonical value is A: `assert_ne!(returned_tenure.block_id, StacksBlockId(consensus_hash, A.block_hash()))`.
5. Show downstream `advance_nakamoto_tenure`/`check_nakamoto_tenure` also accept the block built on B, demonstrating the chain split condition against a second node that only retained A.
