### Title
Ballot `IsFinalizingVote` uses a stricter NO-vote threshold than the documented/`ShouldReject` formula, delaying REJECTED finalization for quorum-style ballots - (File: `x/uvalidator/types/ballot.go`)

### Summary
The generic ballot machine used by `x/uexecutor` (inbound/outbound/chain-meta) and `x/utss` (TSS events/fund migrations) exposes two different, inconsistent formulas for deciding when a ballot should be rejected. The formula actually used on the hot finalization path (`IsFinalizingVote`, invoked from `Keeper.CheckIfFinalizingVote` in `x/uvalidator/keeper/voting.go`) checks `noVotes >= VotingThreshold`, while the semantically-correct "mathematically unreachable" formula (`Ballot.ShouldReject`) checks `len(EligibleVoters) - noVotes < VotingThreshold`. For any ballot whose voting threshold is less than the number of eligible voters — which is the normal case, since the threshold is computed as a `2/3 + 1` supermajority (`votesNeeded := (2*N)/3 + 1` in `x/uexecutor/keeper/voting.go` and `x/uvalidator/keeper/voting.go`) — these two conditions diverge.

### Finding Description
`Ballot.ShouldReject()` ( [1](#0-0) ) implements the intended semantics documented in the module README: "eligibleVoters - noVotes < votingThreshold (the threshold is now mathematically unreachable) -> BALLOT_STATUS_REJECTED" ( [2](#0-1) ).

However, the function that is actually wired into the finalization path, `IsFinalizingVote()`, uses a different and incorrect comparison — it waits for `noVotes >= VotingThreshold` before marking the ballot `REJECTED` [3](#0-2) . `CheckIfFinalizingVote` in the keeper calls `b.IsFinalizingVote()`, not `ShouldReject()`, so this is the code path exercised for every real inbound/outbound/chain-meta/TSS/migration ballot [4](#0-3) .

For a typical 2/3+1 quorum with `N` eligible voters (`votesNeeded := (2*N)/3 + 1`, e.g. `x/uexecutor/keeper/voting.go`) [5](#0-4) , `VotingThreshold < N` whenever `N` is not a multiple of 3. Take `N = 5`, threshold `= (2*5)/3 + 1 = 4`:
- Correct/documented rule (`ShouldReject`): reject once `5 - noVotes < 4`, i.e. `noVotes >= 2` (with 2 NO votes, at most 3 YES votes remain possible, so 4 can never be reached).
- Actual production rule (`IsFinalizingVote`): reject only once `noVotes >= 4`.

So after 2 or 3 honest NO votes are cast (an entirely normal outcome of honest validators independently observing/voting), the ballot remains `PENDING` even though passing is already mathematically impossible. It stays open, consuming an active-ballot slot and blocking a clean "impossible → reject and retry" signal, until it eventually times out via `BlockHeightExpiry` and gets swept to `EXPIRED` instead of `REJECTED` — a different terminal state than the one the design intends for this situation, and one that the rest of the system (indexers, downstream logic keyed off `FinalizedBallotIDs`/`BallotStatus_BALLOT_STATUS_REJECTED`) may not treat identically to `EXPIRED`.

This affects every ballot type routed through the generic machine: inbound votes, outbound votes, chain-meta votes, TSS key-process votes, and fund-migration votes — i.e., the honest-validator finalization path called out in the assignment's "Smart Audit Pivots."

### Impact Explanation
This is a liveness/state-machine-hygiene defect in the honest-validator ballot finalization flow, not a directly exploitable fund-drain or forged-authorization bug (voting itself still requires eligible, authenticated UV signers; an unprivileged external attacker cannot cast votes). The impact is that ballots which are already mathematically decided as failed sit in `PENDING`/`ActiveBallotIDs` far longer than intended, ultimately resolving via expiry (`EXPIRED`) rather than the designed `REJECTED` path, before `RecomputeBallotQuorum`/expiry sweeping intervenes. Depending on how downstream consumers (revert/refund flows, retry logic, monitoring) distinguish `REJECTED` from `EXPIRED`, this can delay revert/refund issuance for a failed inbound/outbound observation and inflate the active-ballot working set. It does not, by itself, corrupt funds, nonces, or authorization, so it does not meet the criteria for the highest-severity fund-loss categories in the Allowed Impact Gate, but it is a genuine, reachable divergence between the documented/intended ballot semantics and the implemented one that affects consensus-adjacent state (`BallotStatus`) under ordinary, honest operation.

### Likelihood Explanation
This triggers deterministically any time the eligible voter count is not a multiple of 3 (the overwhelmingly common case for a real validator set size) and any subset of validators votes NO — no adversarial behavior or privileged access is required, just normal divergent observations among honest Universal Validators. Given `x/uvalidator`'s `README.md` explicitly documents the `ShouldReject`-style formula as intended behavior [2](#0-1) , while the shipped hot path (`IsFinalizingVote`) implements a different, stricter condition, this looks like an unintentional divergence between two code paths rather than deliberate design — directly analogous to the external report's "wrong requirement" pattern (comparing/enforcing against a quantity that doesn't match the semantics of the intended invariant).

### Recommendation
Make `IsFinalizingVote()` use the same mathematically-unreachable-threshold formula as `ShouldReject()` (i.e., `len(b.EligibleVoters) - noVotes < b.VotingThreshold`) instead of `noVotes >= b.VotingThreshold`, so REJECTED is triggered as soon as passing becomes impossible, matching the documented behavior and freeing the ballot slot immediately (or, minimally, unify on one implementation and delete the other to avoid future drift). Add a unit test with `N` not a multiple of 3 (e.g. 5 voters, threshold 4) verifying that 2 NO votes finalize the ballot as REJECTED via `IsFinalizingVote`/`CheckIfFinalizingVote`, not just via `ShouldReject`.

### Proof of Concept
1. Create a ballot with 5 eligible voters and `votingThreshold = 4` (matches `(2*5)/3 + 1` from `x/uexecutor/keeper/voting.go` line 33).
2. Have 2 of the 5 eligible voters cast `VOTE_RESULT_FAILURE` via `VoteOnBallot` → `AddVoteToBallot` → `CheckIfFinalizingVote` → `IsFinalizingVote`.
3. Observe: `noVotes = 2 < VotingThreshold(4)`, so `IsFinalizingVote` returns `isFinalizing = false` and the ballot stays `PENDING`, even though `ShouldReject()` on the same ballot state (`5 - 2 = 3 < 4`) correctly reports the threshold is now unreachable.
4. The ballot remains active, consuming space in `ActiveBallotIDs`, until either 4 total NO votes are cast (unlikely if only 3 voters remain and one has already lost the ability to cause pass, since only 3 YES max remain but no additional NO is required to end the vote logically) or `BlockHeightExpiry` is reached, at which point it is swept to `EXPIRED` — an outcome inconsistent with the intended `REJECTED` result documented in `x/uvalidator/README.md`.

```go
// ShouldReject returns true if the NO votes make it impossible to reach the threshold.
func (b Ballot) ShouldReject() bool {
	_, noVotes := b.CountVotes()
	potentialYesVotes := len(b.EligibleVoters) - noVotes
	return potentialYesVotes < int(b.VotingThreshold)
}
```

```go
// CheckIfFinalizingVote inspects whether the just-cast vote pushes the ballot
// over its threshold and, if so, drives the finalization through
// MarkBallotFinalized — the single canonical write path for terminal status
// transitions, which applies CEI-style ordering on the secondary indexes.
func (k Keeper) CheckIfFinalizingVote(ctx context.Context, b types.Ballot) (types.Ballot, bool, error) {
	ballot, isFinalizing := b.IsFinalizingVote()
	if !isFinalizing {
		return b, false, nil
	}

	k.Logger().Debug("ballot reached finalization threshold",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)

	if err := k.MarkBallotFinalized(ctx, ballot.Id, ballot.Status); err != nil {
		return ballot, false, errors.Wrap(err, "failed updating finalized ballot")
	}

	k.Logger().Debug("ballot finalized",
		"ballot_id", ballot.Id,
		"ballot_status", ballot.Status.String(),
	)
	return ballot, true, nil
}
```
