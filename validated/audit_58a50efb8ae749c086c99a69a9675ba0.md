### Title
Zero-cost CPU exhaustion via repeated ShieldedTransferContract broadcasts forcing native Sapling verification before any bandwidth/fee is charged - ([File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java])

### Summary
An unprivileged attacker can broadcast a syntactically valid `ShieldedTransferContract` carrying a fabricated spend (no transparent sender, hence no signature required) and garbage-but-correctly-sized `SpendDescription`/`ReceiveDescription` fields. Each broadcast forces `ShieldedTransferActuator.validate()` → `checkProof()` to invoke the native `JLibrustzcash` Sapling verification routines, while `BandwidthProcessor.consume()` explicitly skips bandwidth/fee accounting for `ShieldedTransferContract`, so the attacker pays essentially nothing for the CPU burned.

### Finding Description
`ShieldedTransferActuator.validate()` unpacks the contract, checks nullifier/merkle-root/duplicate constraints, and then calls `checkProof()`, which (unless the txid is already cached in `proofStore`) initializes a Sapling verification context and calls `JLibrustzcash.librustzcashSaplingCheckSpend`/`librustzcashSaplingCheckOutput`/`librustzcashSaplingFinalCheck` — all native, CPU-heavy zk-SNARK verification routines: [1](#0-0) 

The internal shielded-pool "fee" bookkeeping (subtracting `fee` from `totalShieldedPoolValue`) happens only after `checkSpend`/`checkOutput` already executed, and is not a real balance debit from the attacker's account — it is a ledger check against the global shielded pool value: [2](#0-1) 

Two facts make this exploitable at effectively zero cost to an unprivileged attacker:

1. **No signature required.** For a shielded-transfer with an empty `transparentFromAddress` (transfer *from* a shielded address), `TransactionCapsule.validateSignature` requires **zero** signatures rather than validating one, so the attacker doesn't even need a valid signing key: [3](#0-2) 

2. **No bandwidth/fee is charged for `ShieldedTransferContract`.** `BandwidthProcessor.consume()`, which is invoked by `Manager.processTransaction()` (`consumeBandwidth(trxCap, trace)`) *before* the actuator's `validate()`/`execute()` run via `trace.exec()`, explicitly `continue`s past all billing logic (`trace.setNetBill`, `useAccountNet`, `useFreeNet`, `useTransactionFee`, and the insufficient-resource exception) whenever `contract.getType() == ShieldedTransferContract`: [4](#0-3) [5](#0-4) 

So the full call chain from an unprivileged RPC client is: `Wallet.broadcastTransaction` → signature-length check (trivially passes) → `dbManager.pushTransaction` → `trx.validateSignature` (passes with 0 signatures) → `processTransaction` → `consumeBandwidth` (no-op for this contract type) → `trace.exec()` → `ShieldedTransferActuator.validate()` → `checkProof()` → native Sapling verification, all before any economic cost is imposed and before the proof is actually valid.

The only "cost" gates are: a valid Merkle anchor (publicly retrievable, not privileged), and a fresh (never-before-used) 32-byte nullifier (trivial to randomize per request), which ensures `proofStore.has(txid)` never hits its cache and the expensive native call runs on every single broadcast.

### Impact Explanation
This is a sustained **RPC-API DoS via CPU exhaustion**: an anonymous/unprivileged client can repeatedly invoke `broadcastTransaction` (HTTP/gRPC) with freshly randomized garbage `SpendDescription`/`ReceiveDescription` payloads, each one causing every receiving/validating node (both the RPC-serving node and any full node that later revalidates the relayed transaction) to run multiple native zk-SNARK pairing/verification operations, without the attacker consuming bandwidth points, energy, or TRX. This matches the TRON bounty "DoS via RPC-API" / "DoS via the TRON protocol implementation" impact class, since node CPU capacity can be exhausted to degrade or stall block processing and RPC responsiveness for legitimate users.

### Likelihood Explanation
Preconditions (`dynamicStore.supportShieldedTransaction()==1` and `getAllowSameTokenName()==1`) are standard mainnet/production settings already enabled on live TRON networks, not privileged or non-default configuration. The attacker requires: no funded account, no signing key, no witness/SR role — only network access to any node's broadcast endpoint. Cost per attempt is bounded by generating one Merkle-anchor lookup (public), one random 32-byte nullifier, and filling fixed-size byte arrays for `zkproof`/`rk`/`spendAuthoritySignature`/valueCommitment — all trivial and free. This is fully repeatable and scriptable, making the attack highly likely to be exploitable in practice.

### Recommendation
- Apply bandwidth/energy or a minimum flat resource charge to `ShieldedTransferContract` transactions in `BandwidthProcessor.consume()` (remove or narrow the unconditional `continue` for `ShieldedTransferContract`) so that broadcasting costs the sender resources regardless of validity.
- Alternatively/additionally, perform cheap structural/sanity checks (e.g., signature scheme point validation, or a lightweight pre-check) prior to invoking the expensive native Sapling verification calls, or apply a per-source-IP/per-account rate limiter specifically for shielded transaction broadcasts.
- Consider requiring the transaction to consume bandwidth/energy proportional to the cost of Sapling verification even when it ultimately fails validation, so failed proofs are not free.

```java
// JUnit-style PoC, mirroring the ShieldedTransferActuatorTest patterns in the repo.
@Test
public void spamShieldedGarbageProofsNoCost() throws Exception {
    dbManager.getDynamicPropertiesStore().saveAllowShieldedTransaction(1);
    dbManager.getDynamicPropertiesStore().saveAllowSameTokenName(1);

    // Obtain a real, currently-valid Merkle anchor (public info, e.g. via wallet API).
    byte[] anchor = dbManager.getMerkleContainer().getCurrentMerkleRoot(); // or equivalent public call

    long totalNs = 0;
    for (int i = 0; i < 1000; i++) {
        byte[] nullifier = randomBytes(32); // fresh every iteration -> proofStore cache never hits

        SpendDescription spend = SpendDescription.newBuilder()
            .setValueCommitment(ByteString.copyFrom(randomBytes(32)))
            .setAnchor(ByteString.copyFrom(anchor))
            .setNullifier(ByteString.copyFrom(nullifier))
            .setRk(ByteString.copyFrom(randomBytes(32)))
            .setZkproof(ByteString.copyFrom(randomBytes(192)))
            .setSpendAuthoritySignature(ByteString.copyFrom(randomBytes(64)))
            .build();

        ReceiveDescription recv1 = randomReceiveDescription();
        ReceiveDescription recv2 = randomReceiveDescription();

        ShieldedTransferContract contract = ShieldedTransferContract.newBuilder()
            .addSpendDescription(spend)
            .addReceiveDescription(recv1)
            .addReceiveDescription(recv2)
            .build(); // no transparentFromAddress -> zero signatures required

        TransactionCapsule tx = buildUnsignedShieldedTx(contract); // no signatures added

        ShieldedTransferActuator actuator = new ShieldedTransferActuator();
        actuator.setChainBaseManager(dbManager.getChainBaseManager())
                .setContract(Any.pack(contract))
                .setTx(tx);

        long start = System.nanoTime();
        try {
            actuator.validate(); // expected to throw due to garbage proof, but only AFTER native calls execute
        } catch (ContractValidateException expected) {
            // expect "librustzcashSaplingCheckSpend error" or similar
        }
        totalNs += System.nanoTime() - start;
    }

    // Assert: no bandwidth/energy/TRX was consumed for these ShieldedTransferContract calls
    // (BandwidthProcessor.consume skips them entirely), yet wall-clock cost is dominated by
    // native Sapling verification calls repeated 1000 times with zero economic cost.
    System.out.println("Total native verification time (ns): " + totalNs);
    Assert.assertTrue("Expected non-trivial CPU cost from repeated native Sapling calls",
        totalNs > TimeUnit.MILLISECONDS.toNanos(50)); // representative of real pairing-check cost
}
```
Expected result: each iteration throws a `ContractValidateException` (e.g. `"librustzcashSaplingCheckSpend error"`), confirming the native verification ran and failed — but only *after* consuming CPU — while `BandwidthProcessor.consume()` (verifiable via code inspection/mocking) never charges bandwidth/energy for these `ShieldedTransferContract` broadcasts, demonstrating unmetered CPU cost per unprivileged RPC call.
