### Title
`L1HandlerTransaction` with empty `calldata` causes an unhandled panic in `l1_handler_message_hash` - (File: `crates/starknet_api/src/hash.rs`)

### Summary
`starknet_api::hash::l1_handler_message_hash` unwraps `calldata.0.split_first()` with `.expect(...)`, assuming the calldata always contains at least the L1 `from_address` element. However, `Calldata` has no non-empty invariant and `L1HandlerTransaction` derives `Deserialize` directly, so an `L1HandlerTransaction` with empty `calldata` is constructible from untrusted/deserialized input. This mirrors the GoBGP MRT bug class (CWE-1284, improper check of input length before consuming fixed structure fields): the code assumes a minimum length without validating it, and panics instead of erroring when the assumption is violated.

### Finding Description
`l1_handler_message_hash` is the function that computes the L1→L2 message hash used to validate that an `L1HandlerTransaction` corresponds to a message actually sent from L1 (fee verification / message hash checks): [1](#0-0) 

Specifically:
```rust
let (from_address, payload) =
    calldata.0.split_first().expect("Invalid calldata, expected at least from_address");
```
This code assumes `calldata.0` is never empty (the L1 sender address is expected to be the first element), but nothing in the type system or deserialization path enforces that invariant. `Calldata` is a plain wrapper around `Vec<Felt>` with no minimum-length check, and the RPC/feeder-gateway `L1HandlerTransaction` struct derives `Deserialize` directly: [2](#0-1) 

Transactions of type `L1_HANDLER` are deserialized generically via `deserialize_transaction_json_to_starknet_api_tx`, which does not perform any minimum-calldata-length validation before constructing the transaction: [3](#0-2) 

The codebase already demonstrates awareness of this exact issue in a sibling function, `L1HandlerTransaction::payload_size()`, which was hardened with `saturating_sub` specifically because "`Calldata` has no non-empty invariant and `L1HandlerTransaction` derives `Deserialize`, so an empty calldata is constructible": [4](#0-3) [5](#0-4) 

However, the same fix was never applied to `calc_msg_hash` / `l1_handler_message_hash`, which is reached through `TryFrom<Transaction> for Transaction (rpc)`, `L1HandlerTransaction::calculate_transaction_hash`/`calc_msg_hash` call sites (`apollo_rpc/src/v0_8/api/api_impl.rs`, `apollo_l1_events/src/l1_events_provider.rs`, `apollo_l1_events/src/l1_scraper.rs`), and any code path (e.g. OS re-execution / consensus deserialization of `transaction::L1HandlerTransaction` via `ConsensusTransaction::L1Handler`) that constructs a raw `L1HandlerTransaction` from deserialized data and then computes its message hash.

### Impact Explanation
If an `L1HandlerTransaction` with empty `calldata` reaches `calc_msg_hash`/`l1_handler_message_hash` (e.g., via RPC message-hash APIs, consensus transaction deserialization of `ConsensusTransaction::L1Handler`, or Starknet OS re-execution consuming block data), the process panics instead of returning a graceful validation error. Depending on where this is invoked (a long-running service such as the RPC node, the l1-events pipeline, or a sequencer/OS re-execution component), this can crash the process, causing denial of service — matching the "network unable to confirm new transactions" / node-crash class of impact accepted by the rules. Because the underlying data type provides no non-empty invariant, this is a genuine input-length-validation gap analogous to the GoBGP MRT parsing bug, not a hypothetical.

### Likelihood Explanation
Likelihood is bounded by uncertainty regarding which reachable entry point can supply an attacker/user-controlled `L1HandlerTransaction` with zero-length calldata before length validation is enforced elsewhere in the stack (e.g., the L1 event scraper always prepends `from_address`, guaranteeing non-emptiness for genuinely-scraped events). The most concrete reachable trigger is a deserialized `transaction::L1HandlerTransaction` (via `serde_json`/bincode deserialization used in consensus/API paths) that never passes through the L1-scraper construction path, since `Deserialize` on `L1HandlerTransaction` performs no length check. This was clearly already recognized as exploitable/reachable by the codebase's own defensive fix in `payload_size()`, but the equivalent hardening was missed in `hash.rs`.

### Recommendation
Change `l1_handler_message_hash` to return a `Result` (or a dedicated error) instead of panicking when `calldata.0` is empty, consistent with the fix already applied to `L1HandlerTransaction::payload_size()`. Propagate the error to callers of `calc_msg_hash`/`calculate_transaction_hash` so malformed/empty-calldata L1Handler transactions are rejected as invalid input rather than causing a runtime panic.

### Proof of Concept
```rust
use starknet_api::core::{ContractAddress, EntryPointSelector, Nonce};
use starknet_api::transaction::fields::Calldata;
use std::sync::Arc;

// Empty calldata is constructible: `Calldata` has no non-empty invariant.
let calldata = Calldata(Arc::new(vec![]));

// This panics with "Invalid calldata, expected at least from_address"
// instead of returning an error.
let _ = starknet_api::hash::l1_handler_message_hash(
    &ContractAddress::default(),
    Nonce::default(),
    &EntryPointSelector::default(),
    &calldata,
);
```
This is directly analogous to the test already present in the codebase confirming empty calldata is constructible for `L1HandlerTransaction`: [6](#0-5) , but unlike `payload_size()`, `l1_handler_message_hash` was not patched to handle this case gracefully.

```rust
/// Calculating the message hash of L1 -> L2 message.
/// For more info: <https://docs.starknet.io/documentation/architecture_and_concepts/Network_Architecture/messaging-mechanism/#structure_and_hashing_l1-l2>
pub fn l1_handler_message_hash(
    contract_address: &ContractAddress,
    nonce: Nonce,
    entry_point_selector: &EntryPointSelector,
    calldata: &Calldata,
) -> L1L2MsgHash {
    let (from_address, payload) =
        calldata.0.split_first().expect("Invalid calldata, expected at least from_address");

    let mut encoded = Vec::new();
    encoded.extend(from_address.to_bytes_be());
    encoded.extend(contract_address.0.key().to_bytes_be());
    encoded.extend(nonce.to_bytes_be());
    encoded.extend(entry_point_selector.0.to_bytes_be());

    let payload_length_as_felt =
        Felt::from(u64::try_from(payload.len()).expect("usize should fit in u64"));
    encoded.extend(payload_length_as_felt.to_bytes_be());

    for felt in payload {
        encoded.extend(felt.to_bytes_be());
    }

    let mut keccak = Keccak256::default();
    keccak.update(&encoded);
    L1L2MsgHash(keccak.finalize().into())
}
```
