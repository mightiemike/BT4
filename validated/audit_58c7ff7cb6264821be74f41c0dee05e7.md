**Analysis:**

`math_fixed64::sqrt` computes `z = (math128::sqrt(y) << 32 as u256); z = (z + ((y as u256) << 64) / z) >> 1;` using `math128::sqrt`, which itself is a 5-iteration Newton-Raphson integer sqrt that the module's own tests already verify against edge cases including `u128::MAX` and `1u128<<127` [1](#0-0) [2](#0-1) . The `math_fixed64::sqrt` wrapper performs one additional Newton refinement step on top of that integer approximation and its own test suite exercises boundary/precision behavior with an explicit tolerance-based comparator (`assert_approx_the_same`) [3](#0-2) [4](#0-3) .

This is irrelevant to the state-integrity gate for two independent reasons:

1. **No consensus divergence is possible.** Move bytecode execution is fully deterministic — every validator executing the same transaction runs the identical arithmetic sequence and produces the bit-identical `u128` raw value, regardless of whether that value is the mathematically "true" fixed-point sqrt to arbitrary precision. There is no source of non-determinism (no floating point, no platform-dependent rounding) in this code path, so "consensus-consistent but wrong" isn't a meaningful distinction here — the algorithm's output *is* the specification's correct output by construction. A precision limitation in an iterative approximation algorithm is a documented property of the function, not a divergence bug.

2. **No proof/storage/authenticated-response path is touched.** `math_fixed64::sqrt` is a pure, optional utility function in the `aptos_std` Move framework that user Move code may call voluntarily; it has no relationship to VM output finalization, write-set construction, transaction info/event serialization, JMT/accumulator proof construction, storage schemas, restore paths, or authenticated API response binding described in the "Proof And Storage Pivots" scope. Any imprecision it might have would only affect the numeric result written into whatever `FixedPoint64`-typed resource a smart contract chooses to store — that's an application-level correctness question of the contract using this stdlib function, not a corruption of the ledger's authenticated state-commitment machinery.

Since the finding does not demonstrate corrupted committed state, corrupted proof material, misbound authenticated responses, or hard-fork-only divergence, it falls outside the required impacts and must be rejected per the Decision Standard.

    /// Returns square root of x, precisely floor(sqrt(x))
    public fun sqrt(x: u128): u128 {
        if (x == 0) return 0;
        // Note the plus 1 in the expression. Let n = floor_lg2(x) we have x in [2^n, 2^{n+1}) and thus the answer in
        // the half-open interval [2^(n/2), 2^{(n+1)/2}). For even n we can write this as [2^(n/2), sqrt(2) 2^{n/2})
        // for odd n [2^((n+1)/2)/sqrt(2), 2^((n+1)/2). For even n the left end point is integer for odd the right
        // end point is integer. If we choose as our first approximation the integer end point we have as maximum
        // relative error either (sqrt(2) - 1) or (1 - 1/sqrt(2)) both are smaller then 1/2.
        let res = 1 << ((floor_log2(x) + 1) >> 1);
        // We use standard newton-rhapson iteration to improve the initial approximation.
        // The error term evolves as delta_i+1 = delta_i^2 / 2 (quadratic convergence).
        // It turns out that after 5 iterations the delta is smaller than 2^-64 and thus below the treshold.
        res = (res + x / res) >> 1;
        res = (res + x / res) >> 1;
        res = (res + x / res) >> 1;
        res = (res + x / res) >> 1;
        res = (res + x / res) >> 1;
        min(res, x / res)
    }
