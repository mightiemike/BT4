### Title
`ensure_match_transaction_info` omits state/hot-state/position checkpoint hashes, letting replay-verify and chunk-execution accept a `TransactionInfo` whose committed state root diverges from actual VM output — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-response/replay invariant check used to assert that a locally re-executed `TransactionOutput` matches a `TransactionInfo` that is itself bound into the transaction accumulator (i.e., proof-bearing, ledger-committed data). The function checks status, gas, write-set hash, and event-root hash, but explicitly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the very fields that represent the committed state root at that version.

### Finding Description [1](#0-0) 

`ensure_match_transaction_info` verifies four properties of the re-executed `TransactionOutput` against the trusted `TransactionInfo` (status, gas, write-set hash via `state_change_hash`, event root hash), but the code contains a self-documented gap:

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
``` [2](#0-1) 

This function is the sole per-transaction correctness gate used by:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, which re-executes transactions during chunk replay/backup-restore and calls `ensure_match_transaction_info` per transaction to decide whether the replay matches the ledger: [3](#0-2) 
- `storage/db-tool/src/replay_on_archive.rs`, the archive-node replay-verification tool used to detect state divergence against historical ledger data.
- `aptos-move/cli/src/commands.rs`.

Because `state_checkpoint_hash` (the SMT/JMT root committed in `TransactionInfo`), `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` are never compared to values independently recomputed from the freshly executed write sets, any of these three roots can be wrong in the persisted/replayed `TransactionInfo` (through a bug elsewhere in `DoStateCheckpoint`/`DoLedgerUpdate`, a storage corruption, or a malicious/compromised historical data source used for replay/backup-restore) and `verify_execution`/`replay_on_archive` will still report success. The state_change_hash (write set) and event_root_hash are checked, but the state root that downstream verified `DbStateView`s and light-client-style proofs rely on (`state_checkpoint_hash()` used directly to bind an authenticated state view, e.g. `storage/storage-interface/src/state_store/state_view/db_state_view.rs::verified_state_view_at_version`) is never independently validated by this comparator. [4](#0-3) 

This is distinct from consensus-time execution, where `DoStateCheckpoint`/`DoLedgerUpdate` do compute the roots from write sets directly and there's a separate check against `known_state_checkpoints` in the normal live-execution path (`chunk_result_verifier.rs`/`DoStateCheckpoint`). The bug is specifically that `ensure_match_transaction_info` — the function reused for offline replay/backup-restore verification and by db-tool for archive auditing — is a weaker, incomplete check that silently drops the state-root fields.

### Impact Explanation
This breaks the "proof and storage pivot" invariant that "VM outputs, transaction infos ... must survive executor-to-storage handoff unchanged" and that "replay paths ... must not reinterpret committed data into a different ledger state." A divergence between the true executed state root and the `state_checkpoint_hash` recorded in a `TransactionInfo` would go undetected by:
1. Chunk-executor replay verification (`verify_execution`) during backup restore, letting corrupted/incorrect state-root metadata be accepted and committed as if verified.
2. `db-tool`'s `replay_on_archive`, the primary tool operators use to detect historical state divergence on archive nodes — it would falsely report a clean replay even though the committed state root is wrong, undermining audits, forks, and postmortems.

Because `state_checkpoint_hash` is directly relied upon to bind an authenticated `DbStateView` (see `verified_state_view_at_version`), a divergence that escapes this check can propagate into authenticated API responses that are asserted-correct but actually anchored to the wrong state root.

### Likelihood Explanation
The gap is intentionally called out in code as pending work ("before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), indicating the position-state-root fields are not yet load-bearing in production, which lowers current real-world likelihood for `position_state_checkpoint_hash`. However, the same comparator function also never validates the pre-existing `state_checkpoint_hash` and `hot_state_checkpoint_hash` fields (this gap is not new/limited to the trading-native feature; those fields have existed and been produced since well before this TODO), so any latent computation bug in `DoStateCheckpoint`/`DoLedgerUpdate`, or corrupted backup manifests fed to `enqueue_chunks`/`verify_execution`, silently passes replay/archive verification today. This is a real, unprivileged gap exploitable simply by an attacker (or bug) producing backup data / archive-node state with a wrong `state_checkpoint_hash` alongside otherwise-correct write sets/events — reachable via the standard restore and replay-verify flows without any special privilege.

### Recommendation
Extend `ensure_match_transaction_info` to independently recompute and compare `state_checkpoint_hash` (and, where applicable, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) against values derived from the freshly executed state, consistent with how `DoStateCheckpoint`/`DoLedgerUpdate` compute these roots in the live-execution path. At minimum, `verify_execution` and `replay_on_archive` should not report a chunk/version as "verified" while these root fields remain unchecked.

### Proof of Concept
1. Take an archived/backed-up chunk of transactions and their `TransactionInfo`s where the write set, events, gas, and status are unmodified but `state_checkpoint_hash` (or `hot_state_checkpoint_hash`) has been tampered with or is stale due to a state-checkpoint computation bug.
2. Feed this chunk through `execution/executor/src/chunk_executor/mod.rs::verify_execution` (used by backup restore, `storage/backup/backup-cli/src/backup_types/transaction/restore.rs`) or through `storage/db-tool/src/replay_on_archive.rs::verify`.
3. Because `ensure_match_transaction_info` [1](#0-0)  only checks status/gas/write-set-hash/event-root-hash, the tampered/incorrect `state_checkpoint_hash` is never compared against a recomputed value, so `verify_execution` returns `Ok(end_version)` and `replay_on_archive::verify` reports no failed transactions, despite the ledger's authenticated state root diverging from the true VM-executed state.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

impl VerifiedStateViewAtVersion for Arc<dyn DbReader> {
    fn verified_state_view_at_version(
        &self,
        version: Option<Version>,
        ledger_info: &LedgerInfo,
    ) -> StateViewResult<DbStateView> {
        let db = self.clone();

        if let Some(version) = version {
            let txn_with_proof =
                db.get_transaction_by_version(version, ledger_info.version(), false)?;
            txn_with_proof.verify(ledger_info)?;

            let state_root_hash = txn_with_proof
                .proof
                .transaction_info
                .state_checkpoint_hash()
                .ok_or_else(|| StateViewError::NotFound("state_checkpoint_hash".to_string()))?;

            Ok(DbStateView {
                db,
                version: Some(version),
                maybe_verify_against_state_root_hash: Some(state_root_hash),
            })
        } else {
            Ok(DbStateView {
                db,
                version: None,
                maybe_verify_against_state_root_hash: None,
            })
        }
    }
