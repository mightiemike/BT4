### Title
Alternate-Path Validation Bypass: v1 Signer Chainstate Duplicate-Tenure-Change Check Misses Locally-Accepted/Pre-Committed Blocks - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The signer's duplicate block-found tenure-change guard exists in two parallel implementations, `v1::SortitionState::validate_tenure_change_payload` and `v2::SortitionState::validate_tenure_change_payload`. The two enforce the same security invariant ("do not sign a second BlockFound tenure-change for a tenure we've already signed a block in") through *different equality checks over different data sets*, exactly the alternate-path pattern in the reported CWE-288 class. v1 only consults globally-accepted blocks, so a tenure-start block that is merely locally-accepted or pre-committed is invisible to it, letting a duplicate tenure-change slip past the check that v2 correctly blocks.

### Finding Description
`v2::SortitionState::validate_tenure_change_payload` looks up the last block in the tenure with `signer_db.get_last_signed_block(&block.header.consensus_hash)`, which — per its own comment — deliberately covers "blocks we have signed (locally or globally accepted)" so that any signed sibling in the tenure vetoes a second `BlockFound` tenure-change: [1](#0-0) 

The v1 implementation of the *same* check instead queries `get_last_globally_accepted_block`: [2](#0-1) 

This is a known-weaker check: a regression test explicitly documents that `get_last_globally_accepted_block` "would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change," and was the reason v2 was written against `get_last_signed_block`: [3](#0-2) 

Signer-side selection of which of these two "channels" is used is driven by the signer's own protocol version, not by anything the node cross-checks between signers: [4](#0-3) 

Because the v1 module is still shipped and reachable for signers below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`, this is a live alternate code path, not dead code — during any rolling network upgrade where signers run mixed protocol versions, some signers evaluate proposals with the strict v2 duplicate check and others with the weaker v1 one.

The equality being broken is: "has this signer already signed a block for this tenure?" v2 answers this correctly using the full signed-state (`LocallyAccepted`/`PreCommitted`/`GloballyAccepted`); v1 answers it using only `GloballyAccepted`, a strict subset. Two signers presented with the identical tenure history can therefore reach different verdicts on the identical `BlockFound` tenure-change block — one rejects it as `DuplicateBlockFound`, the other accepts it — which is precisely the "validation verdict two nodes disagree on" class called out as in-scope.

This directly interacts with the sibling-tenure-start race already acknowledged elsewhere in the codebase (the async-validation timing gap where two sibling tenure-start blocks can both be pre-committed before the node's async validation completes): [5](#0-4) [6](#0-5) 

v1 signers widen that race window: instead of needing the block to be merely un-globally-accepted for a brief async-validation gap, a v1 signer will accept a duplicate `BlockFound` for the tenure at any point before the first sibling reaches *global* acceptance — a much larger, miner-influenced window (global acceptance requires broad signer-set participation and network propagation, whereas local acceptance/pre-commit only requires this signer's own vote).

### Impact Explanation
A miner (unprivileged, no signer/admin key needed) can propose two conflicting `BlockFound` tenure-change blocks for the same tenure. Signers still running on the v1 chainstate path will happily co-sign the second sibling as long as the first has not yet reached global acceptance, while v2 signers reject it. This produces a genuine cross-signer validation-verdict split and can let a subset of pre-commits/signatures accumulate for two different tenure-start blocks at the same height, causing a temporary tip disagreement between nodes that trust different signer subsets — matching the "High: minority-triggerable... static-validation divergence... temporary tip disagreement" bucket in scope. It does not require a majority of signers to misbehave; it only requires that some fraction of the active signer set still runs the weaker v1 path.

### Likelihood Explanation
Triggering requires only that an ordinary miner submit two `BlockFound` tenure-change block proposals for the same tenure before the first is globally accepted — a normal capability of any miner, and something that already happens accidentally in reorg/race scenarios per the existing sibling-validation tests. The only network precondition is that some signers are still operating with `active_signer_protocol_version` below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` (i.e., mid-rollout / mixed-version network), which is a realistic and expected transient state during any signer software upgrade, not an attacker-controlled majority or Sybil condition.

### Recommendation
Backport the `get_last_signed_block` check used in `v2::SortitionState::validate_tenure_change_payload` into `v1::SortitionState::validate_tenure_change_payload`, or otherwise make the duplicate-tenure-change guard consult locally-accepted and pre-committed blocks (not only globally-accepted ones) in both code paths so all signer protocol versions enforce the same equality and cannot be split by version skew.

### Proof of Concept
1. Run a mixed-version signer set where signer A is on `active_signer_protocol_version` ≥ `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` (v2 chainstate path) and signer B is below it (v1 chainstate path).
2. Miner proposes tenure-start block A₁ (`BlockFound`) for tenure T. Both signers pre-commit/locally-accept A₁ but it has not yet reached global acceptance.
3. Miner (or a second competing miner) proposes a conflicting tenure-start block A₂ (`BlockFound`) for the same tenure T before A₁ is globally accepted.
4. Signer A (v2) calls `get_last_signed_block` in `validate_tenure_change_payload`, finds A₁ already signed, and rejects A₂ with `DuplicateBlockFound`: [7](#0-6) 
5. Signer B (v1) calls `get_last_globally_accepted_block`, finds nothing (A₁ is not yet globally accepted), and does not reject A₂: [2](#0-1) 
6. Signer B proceeds to pre-commit/sign A₂ while signer A signs only A₁, producing two competing signed tenure-start blocks for tenure T with disjoint signer support — a verdict divergence and temporary tip disagreement across the network.
