### Title
Miner can self-extend its own tenure inactivity window via rejected reorg-attempt proposals that still reset `last_activity_time` — ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` calls `signer_db.update_last_activity_time(...)` whenever a proposed block conflicts with (fails to exceed) the tenure's last signed/pre-committed block, on the theory that even a failed reorg attempt is still "miner activity." Because this reset happens on *every rejected* proposal, the current tenure's own miner can indefinitely delay being declared "timed out" by `SortitionState::is_timed_out` simply by repeatedly submitting cheap, invalid competing proposals — the same self-triggerable "reset my own clock" pattern described in the external report (attacker uses their own transaction to add extra grace time before an adverse state transition fires).

### Finding Description
`is_timed_out` (both `stacks-signer/src/chainstate/v1.rs:55-94` and `stacks-signer/src/chainstate/v2.rs:46-89`) decides whether a tenure's miner should be treated as inactive by comparing `now` against `last_activity_time` (falling back to burn-block-received time). This flag gates whether a signer will sign a `TenureChange::Extended` from a different miner, i.e., whether the tenure gets handed off.

`last_activity_time` is *not* only updated by legitimate block progress. In `check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:376-448`): [1](#0-0) 

whenever an incoming proposal's `chain_length` does not exceed the tenure's already-signed tip, the code treats this as a "reorg attempt" and, provided the existing signed block is still within `reorg_attempts_activity_timeout`, calls `update_last_activity_time` — even though the proposal is then rejected (`return Ok(false)`). The same pattern repeats for pre-committed-but-not-yet-signed blocks (lines 427-447), again refreshing the timer on a proposal that is not accepted.

This means the tenure's own miner (the only entity whose block headers pass the node's earlier block-validation signature check before this code path is reached) can manufacture an unbounded stream of harmless, self-conflicting proposals (any block at or below the current chain length in its own tenure) purely to keep resetting `last_activity_time`, thereby preventing `is_timed_out` from ever returning true — without producing any block that a signer will actually sign.

### Impact Explanation
This breaks the intended equality "a miner that is not making real progress should eventually be judged inactive by `is_timed_out`, releasing the tenure to a fallback miner." Because `last_activity_time` is stored per-signer in each signer's local `SignerDb` (`get_last_activity_time`/`update_last_activity_time` in `stacks-signer/src/signerdb.rs`), and reception/reset timing of these bogus proposals is not synchronized across the signer set (network delay, selective delivery, or a miner intentionally staggering delivery), different signers can independently reach different verdicts about whether the tenure has timed out at a given moment — one signer may consider the miner inactive and be ready to sign an `Extended` tenure-change from a fallback miner, while another still sees fresh activity and refuses. This is a "validation verdict two nodes disagree on" / temporary tip disagreement, and it also lets a stalling or selfish miner extend its effective tenure hold time beyond what `tenure_last_block_proposal_timeout`/`reorg_attempts_activity_timeout` were designed to bound.

### Likelihood Explanation
No majority collusion is required: the current tenure's miner already holds the only key capable of producing proposals that pass the earlier signature checks and reach this code path, so a single (minority, in the "not needing other parties' keys" sense) actor can trigger this indefinitely by submitting a stream of low-height/self-conflicting proposals. The condition guarding the reset (`signed_time + reorg_attempts_activity_timeout > now`, or `approved_time + tenure_last_block_proposal_timeout > now`) is easily kept true by simply repeating the attempt before each window elapses.

### Recommendation
Do not let a *rejected* reorg-attempt or a non-committing pre-commit conflict reset the same `last_activity_time` clock that governs miner-timeout/hand-off decisions. Consider tracking "activity" only from state transitions that a majority of signers can independently observe and agree on (e.g., actual chain-height progress signed by the required weight threshold), or rate-limit/cap how many times a single tenure's `last_activity_time` can be refreshed by rejected proposals within a timeout window, and require the refresh reason to be visible/auditable across the signer set to avoid divergent per-signer views of tenure liveness.

### Proof of Concept
1. Miner M wins a sortition and produces/gets one block signed (tenure `T` now has a signed tip at height `h`).
2. M realizes it will not be able to keep producing valid blocks (e.g., about to be superseded) and wants to delay hand-off to the fallback/extending miner.
3. Before `tenure_last_block_proposal_timeout`/`reorg_attempts_activity_timeout` elapses, M crafts and submits a new signed proposal for tenure `T` with `chain_length <= h` (a trivially valid, self-signed but non-progressing block).
4. Each signer runs `check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:395-417`), rejects the proposal (`return Ok(false)`), but first calls `update_last_activity_time`, resetting the clock `is_timed_out` reads.
5. M repeats step 3 just before each window would otherwise expire, keeping `is_timed_out` false on some or all signers indefinitely, and staggers delivery so that signers disagree at any given instant about whether tenure `T` has timed out.
