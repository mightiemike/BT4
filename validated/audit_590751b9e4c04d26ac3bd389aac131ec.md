### Title
Unbounded, permanent disk-index bin amplification via deterministic bin targeting and restart-persisted oversized index files - ([File: bucket_map/src/restart.rs], [File: bucket_map/src/bucket.rs])

### Finding Description
`BucketMap::bucket_ix` selects which disk-index bin a pubkey belongs to purely from the raw bytes of the pubkey with no secret/random salt: `read_be_u64(key.as_ref()) >> (64 - max_buckets_pow2)`. [1](#0-0)  Unlike the intra-bucket hash `bucket_index_ix`, which uses a per-bucket `random` value specifically to prevent deterministic pubkey grinding, bin selection has no such protection, so an unprivileged attacker can grind account pubkeys offline to make an arbitrary number of accounts land in a single target bin.

Once many colliding accounts are created (paying only normal account-creation fees), `Bucket::grow_index` is repeatedly invoked and only ever grows the index file relative to `current_capacity` or `anticipated_size`, never shrinks it: `let new_capacity = (current_capacity * 110 / 100).max(anticipated_size);` [2](#0-1)  After growing, `restartable_bucket.set_file(file_name, self.random)` persists the new (larger) `file_name` into the mmapped restart file. [3](#0-2) 

`RestartableBucket::set_file`/`get` read and write this `file_name`/`random` pair directly into the shared restart mmap with no bound or shrink logic. [4](#0-3)  On validator restart, `Restart::get_restart_file` re-opens this file if the header/config matches, and `Restart::get_restartable_buckets` matches each bucket index to its previously recorded `file_name`, reusing the on-disk file (and deleting only files that are *not* referenced by any bucket index) — never resizing referenced files down to fit current live content. [5](#0-4)  `Bucket::new` then reuses this oversized file via `BucketStorage::load_on_restart` whenever a matching path exists. [6](#0-5) 

There is no code path in `bucket.rs`, `bucket_storage.rs`, or `restart.rs` that shrinks an index bucket file after deletions/cleanup — `delete_key` only frees index/data slots in-place without ever triggering a downward resize. [7](#0-6)  Thus after the attacker deletes all their colliding accounts and cleans/purges them, and the validator restarts, the oversized bin file is faithfully reloaded and kept at its historical peak size forever, with no mechanism to reclaim the space.

### Impact Explanation
This is a disproportionate storage/index cost vulnerability: an unprivileged attacker who pays only ordinary transaction fees to create and then close many colliding accounts can permanently inflate one bin's on-disk index file to many multiples of its default size. Because `Restart` persists and reuses this oversized file indefinitely across restarts with no shrink path, disk footprint for that bin stays pinned at the attacker's historical peak, independent of current live-account count — a lasting resource-amplification/DoS-adjacent cost imposed on validator operators disproportionate to fees paid, matching the "unprivileged attacker forces disproportionate storage/index work" bounty category referenced in the audit scope.

### Likelihood Explanation
Feasible and fully attacker-controlled: disk index mode (`IndexLimit::Minimal`/`Threshold`) is a common, non-default-but-supported deployment; `bucket_ix` is a pure deterministic function of the pubkey's leading bits, so grinding pubkeys (e.g., brute-forcing new keypairs and checking `bucket_ix`) to concentrate arbitrarily many accounts into one bin is a normal, unprivileged, offline computation with no cluster interaction required. Repeated account creation/closure at any rate the attacker is willing to pay fees for reliably triggers `grow_index` growth, and the effect persists across any number of subsequent validator restarts since the restart file matching logic never re-evaluates or shrinks the size of a matched bin file.

### Recommendation
Add a shrink/compaction path for disk-index bucket files: after cleanup/purge (or periodically, or specifically at restart when reusing a file via `get_restartable_buckets`), compare a bucket's live entry count against its current capacity and, when significantly over-provisioned (e.g., utilization far below `anticipated_size`/current capacity threshold), reallocate a smaller file, migrate live entries (mirroring the existing grow-and-copy logic in `grow_index`), and update `restartable_bucket.set_file` to point at the smaller file, deleting the old oversized one. At minimum, cap how large `grow_index` is allowed to make a bin (independent of one attacker's transient burst) or track long-term occupancy to detect it should shrink on the next restart rather than blindly reusing the stored `file_name`.

### Proof of Concept
Integration test plan in `bucket_map` crate:
1. Construct a `BucketMapConfig` with a small `max_buckets` (e.g., 1<<2), disk-backed `drives`, and a `restart_config_file`, mirroring the pattern in existing tests (`test_restartable_bucket`, `test_get_restartable_buckets`).
2. Generate N pubkeys (e.g., N=100) that all resolve to `bucket_ix == 0` (grind pubkeys via `BucketMap::bucket_ix`, which is a deterministic pure function taking the top bits of the pubkey — no randomness involved, so this is a plain offline brute-force loop).
3. Insert all N pubkeys into the `BucketMap`, forcing `Bucket::grow_index` to fire multiple times for bin 0; record `stats.index.total_file_size`/`capacity_bytes` for bin 0 via `BucketStats`.
4. Delete all N keys via `BucketMap::delete_key`, drop the `BucketMap` (persisting the restart file with its still-oversized `file_name` for bin 0).
5. Reconstruct a new `BucketMap` with the same config (simulating a validator restart), letting `Restart::get_restart_file` + `Restart::get_restartable_buckets` reuse the existing oversized file for bin 0.
6. Assert that `capacity_bytes`/`total_file_size` for bin 0 after restart equals (or is not meaningfully smaller than) the peak size recorded in step 3, despite bin 0 now containing zero live entries — demonstrating the file size never shrinks toward the live entry count across the delete+restart cycle.

impl RestartableBucket {
    /// this bucket is now using `file_name` and `random`.
    /// This gets written into the restart file so that on restart we can re-open the file and re-hash with the same random.
    pub(crate) fn set_file(&self, file_name: u128, random: u64) {
        if let Some(mut restart) = self.restart.as_ref().map(|restart| restart.lock().unwrap()) {
            let bucket = restart.get_bucket_mut(self.index);
            bucket.file_name = file_name;
            bucket.random = random;
        }
    }
    /// retrieve the file_name and random that were used prior to the current restart.
    /// This was written into the restart file on the prior run by `set_file`.
    pub(crate) fn get(&self) -> Option<(u128, u64)> {
        self.restart.as_ref().map(|restart| {
            let restart = restart.lock().unwrap();
            let bucket = restart.get_bucket(self.index);
            (bucket.file_name, bucket.random)
        })
    }
}

    /// get one `RestartableBucket` for each bucket.
    /// If a potentially reusable file exists, then put that file's path in `RestartableBucket` for that bucket.
    /// Delete all files that cannot possibly be reused.
    pub(crate) fn get_restartable_buckets(
        restart: Option<&Arc<Mutex<Restart>>>,
        drives: &Arc<Vec<PathBuf>>,
        num_buckets: usize,
    ) -> Vec<RestartableBucket> {
        let mut paths = Self::get_all_possible_index_files_in_drives(drives);
        let results = (0..num_buckets)
            .map(|index| {
                let path = restart.and_then(|restart| {
                    let restart = restart.lock().unwrap();
                    let id = restart.get_bucket(index).file_name;
                    paths.remove(&id)
                });
                RestartableBucket {
                    restart: restart.cloned(),
                    index,
                    path,
                }
            })
            .collect();

        paths.into_iter().for_each(|path| {
            // delete any left over files that we won't be using
            _ = fs::remove_file(path.1);
        });

        results
    }
