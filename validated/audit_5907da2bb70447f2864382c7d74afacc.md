### Title
Unchecked plain subtraction on `accounts_data_len` during index generation (asymmetric with the checked capitalization subtraction) - (File: accounts-db/src/accounts_db.rs)

### Summary
Immediately after `generate_index()` deduplicates cross-slot pubkey versions, the code subtracts the duplicates' contribution from two running totals: capitalization and `accounts_data_len`. The capitalization subtraction is protected with `checked_sub().expect(...)`, but the `accounts_data_len` subtraction on the very next line uses a plain `-=` with no overflow/underflow protection.

### Finding Description
In `AccountsDb::generate_index()`: [1](#0-0) 

```
total_accum.lt_hash.mix_out(&duplicates_lt_hash.0);
total_accum.capitalization = total_accum
    .capitalization
    .checked_sub(capitalization_from_duplicates)
    .expect("capitalization cannot underflow");
total_accum.accounts_data_len -= accounts_data_len_from_duplicates;
```

The capitalization computation was clearly hardened against underflow (with an explicit `expect` message documenting the invariant), but `accounts_data_len` — accumulated the same way, from the same per-slot scan (`accounts_data_len += data_len as u64` gated on `!is_account_zero_lamport`, [2](#0-1) ) and reduced against `accounts_data_len_from_duplicates` computed in `visit_duplicate_pubkeys_during_startup` (gated on `lamports > 0`, [3](#0-2) ) — was left as an unchecked `u64 -=`.

This is exactly the bug class described in the external report: complex accounting invariants (here, "duplicates counted can never exceed the total accumulated value") are relied upon implicitly without being enforced by the arithmetic operation itself. If the invariant is ever violated — e.g., through an edge case in how same-slot vs. cross-slot duplicate accounting interacts (the duplicate-visiting pass only considers pubkeys with `slot_list.len() > 1`, i.e., cross-slot duplication as tracked by the accounts index; it does not necessarily reconcile with every path that can inflate/deflate the per-slot `accounts_data_len` counter, such as obsolete-account skipping introduced independently in `generate_index_for_slot`), the result is:
- In a debug build (`overflow-checks` inherited from the dev profile, which is on by default for `debug_assertions`), a panic.
- In a standard release build (no `overflow-checks = true` found anywhere in the workspace via search), silent wraparound to a value near `u64::MAX`.

Unlike the capitalization field — whose correctness is verified end-to-end at snapshot load via `MismatchedCapitalization` ( [4](#0-3) ) — I could not find any equivalent runtime cross-check for `calculated_accounts_data_len`/`IndexGenerationInfo::accounts_data_len` (no `MismatchedAccountsDataLen` or similar verification path exists in the codebase, per search). This means a corrupted `accounts_data_len` value produced here would silently propagate into the bank's accounts-data-size accounting used for the "max accounts data allowed size" runtime limit, with no independent verification to catch the divergence.

### Impact Explanation
`accounts_data_len` computed by `generate_index()` seeds the bank's accounts-data-size tracker at startup (via `IndexGenerationInfo::accounts_data_len`, [5](#0-4) ), which gates transaction execution against `MAX_ACCOUNTS_DATA_ALLOCATION` type limits network-wide. A wraparound here would set this tracker to a huge value, potentially causing an honest node to reject valid transactions it should accept (spurious `MaxAccountsDataAllocationsExceeded`-style rejection) — a state divergence from other honest nodes that computed the value correctly, i.e., a snapshot-vs-replay / node-to-node accounting mismatch. In a debug/test build the `-=` would instead panic the validator (a node panic).

### Likelihood Explanation
Low-to-moderate. This code path only runs once, at startup, during index generation (`generate_index()`), not on every transaction, so it is not attacker-triggerable per-transaction. Triggering it requires a state where `accounts_data_len_from_duplicates` (computed from cross-slot pubkey duplication as seen by the accounts index) exceeds `total_accum.accounts_data_len` (accumulated from raw per-slot storage scans, which also count obsolete/skipped entries differently, see `num_obsolete_accounts_skipped`). I could not conclusively construct or rule out a concrete sequence producing this inequality within the given time; the asymmetry with the adjacent, explicitly-guarded capitalization computation is the strongest evidence that this is an oversight rather than a proven-safe invariant.

### Recommendation
Make the `accounts_data_len` reduction consistent with the capitalization reduction directly above it: use `checked_sub()` with an `.expect("accounts data len cannot underflow")` (or return a hard error / abort index generation) instead of the bare `-=`, so any invariant violation fails loudly and immediately at startup rather than silently corrupting the bank's accounts-data-size accounting or (in release builds) wrapping around.

### Proof of Concept
Not independently reproduced. The proof-of-concept would require constructing a snapshot/ledger startup scenario where the pubkeys reported as cross-slot duplicates by `populate_and_retrieve_duplicate_keys_from_startup` / `visit_duplicate_pubkeys_during_startup` yield a summed `accounts_data_len_from_duplicates` larger than the corresponding `total_accum.accounts_data_len` slice contributed by `generate_index_for_slot`, e.g. via interaction with the obsolete-accounts skip path (`num_obsolete_accounts_skipped`, [6](#0-5) ) which excludes already-obsolete entries from `accounts_data_len` accumulation but is not obviously reconciled with the duplicate-detection accounting in `visit_duplicate_pubkeys_during_startup`. I flag this as the concrete file/line to instrument and fuzz for confirmation, since I could not fully verify feasibility within the available exploration.
