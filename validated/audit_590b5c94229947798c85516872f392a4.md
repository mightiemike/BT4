## Analysis Result

I traced the external Omni "silently-lost-funds-on-unsafe-pause" bug class to its Aptos-native invariant: **an authenticated verification path that silently accepts a mismatched/corrupted state commitment as "verified."** I found a concrete, locally-provable instance of this in the archive replay-verification tooling.

### Title
`db-tool replay-on-archive` reports full replay success while silently skipping state-root (Merkle checkpoint) verification - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info`, the sole correctness check used by the `replay-on-archive` tool, verifies transaction status, gas, write-set hash, and event root — but explicitly does **not** verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The code even documents this gap in a `TODO(trading-native)` comment. Because `replay_on_archive.rs` never independently computes or cross-checks a state Merkle root either, a replayed chunk whose resulting world-state diverges from the authenticated archived ledger can still be reported as a fully verified match.

### Finding Description
`ensure_match_transaction_info` in [1](#0-0)  checks execution status, gas used, the write-set hash (`state_change_hash`) and the event root hash against the archived `TransactionInfo`. It explicitly stops there, with the code comment stating: [2](#0-1) 

This means the function never compares `state_checkpoint_hash` (the Sparse-Merkle/Jellyfish state root), `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` present on `TransactionInfoV0`/`TransactionInfoV1` ( [3](#0-2) , [4](#0-3) ).

This comparator is the *only* verification performed by the `db-tool replay-on-archive` command. Its `execute_and_verify` routine executes each chunk of transactions via `AptosVMBlockExecutor::execute_block` (which, unlike the chunk executor / block executor commit pipeline, does not compute or persist a state Merkle root at all here) and then calls exactly this comparator: [5](#0-4) 

There is no other state-root check anywhere in `replay_on_archive.rs` (confirmed by search — no reference to `state_checkpoint_hash` in that file). Contrast this with the actual commit path (`do_ledger_update.rs`) and normal chunk-executor commit flow, where `state_checkpoint_hash` is computed from the real state tree and baked into the committed `TransactionInfo` before it is accumulated into the transaction accumulator that the network's ledger-info signatures authenticate ( [6](#0-5) ). The archive replay tool bypasses this integrity guarantee entirely.

### Impact Explanation
`replay-on-archive` exists specifically to independently confirm that replaying historical transactions from a backup/archive reproduces the exact ledger state that validators originally committed (write set, events, gas, status, *and* the resulting state root). Because the state-root fields are never compared:
- A VM/execution divergence that changes computed account/resource state (e.g., from a subtle non-determinism bug, a corrupted archive, or a hard-fork-only behavioral change) but coincidentally preserves the write-set hash and status/gas/events would be reported as a clean, fully verified replay.
- More critically, even a **divergent** write-set hash is only caught when explicit `expected_writeset`/`expected_events` are passed and match by luck of construction — but the state root itself (which is the authenticated summary binding the *entire* resulting world state, not merely this transaction's write set) is never independently reconstructed or checked against the archived, ledger-info-signed value. This directly matches the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category: a wrong committed state can pass as correct in the one place designed to catch this class of bug on historical/archival replay.

### Likelihood Explanation
This is not a hypothetical: the code's own `TODO(trading-native)` comment already documents that this exact tool (`db-tool's replay_on_archive`) can "report a successful replay even when the authenticated position state root diverges from local execution." The gap is unconditionally present in the current comparator logic (no feature flag gates the omission) and is exercised on every call the `replay-on-archive` tool makes.

### Recommendation
Extend `ensure_match_transaction_info` (or add a dedicated check invoked from `replay_on_archive.rs`) to independently recompute the resulting state Merkle root for each replayed chunk and assert equality with `txn_info.state_checkpoint_hash()` (and `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` when present), before treating a chunk as verified.

### Proof of Concept
1. Take an archived chunk where the archived `TransactionInfo.state_checkpoint_hash` reflects an on-chain resource value `V`.
2. Run `replay-on-archive` against a target DB (or VM build) whose execution correctly reproduces the write set / event root / gas / status for that transaction (e.g. only a later, unrelated resource diverges due to a non-deterministic bug), but the final state Merkle tree differs from `V`.
3. `execute_and_verify` → `ensure_match_transaction_info` passes because it never inspects `state_checkpoint_hash`, so the tool reports "ReplayVerify coordinator succeeded" for a chunk whose actual committed world-state diverges from the authenticated ledger.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
