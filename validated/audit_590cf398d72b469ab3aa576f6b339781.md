### Title
TOCTOU race between subscription balance check and S4 secret storage write allows secret slot usage without maintaining minimum balance - ([File: core/services/functions/connector_handler.go])

### Summary
`HandleGatewayMessage` checks `h.subscriptions.GetMaxUserBalance(fromAddr)` against `h.minimumBalance` before calling `handleSecretsSet`, but `handleSecretsSet` → `h.storage.Put` performs no independent balance re-validation. The two operations are non-atomic, separated by network/DB latency, so an attacker can submit a `MethodSecretsSet` request while balance is sufficient and then withdraw/drain the on-chain subscription balance before `storage.Put` completes, leaving a stored DON-hosted secret backed by an under-funded (or zero-balance) subscription.

### Finding Description
In `functionsConnectorHandler.HandleGatewayMessage` (core/services/functions/connector_handler.go:146-156), the `MethodSecretsSet` case reads the subscription balance once via `h.subscriptions.GetMaxUserBalance(fromAddr)` and compares it to `h.minimumBalance`. If sufficient, it calls `h.handleSecretsSet`, which unmarshals the payload and calls `h.storage.Put(ctx, &key, &record, request.Signature)` (core/services/functions/connector_handler.go:212-238). `s4.storage.Put` (core/services/s4/storage.go:129-166) validates slot bounds, payload size, expiration window, and the record signature, but performs no call back into `subscriptions.GetMaxUserBalance` or any other funding check. Thus the balance check and the privileged write are two independent, non-atomic operations with a time window between them where the attacker (who controls the timing of their own on-chain subscription's balance, e.g., via `cancelSubscription`/withdrawal transactions they are entitled to submit as subscription owner) can invalidate the funding condition after the check passed but before the write is persisted.

### Impact Explanation
This allows an unprivileged-but-legitimate subscription owner to consume DON-hosted secrets storage capacity (a paid/gated resource, bounded by `MaxSlotsPerUser`/`MaxPayloadSizeBytes`) without maintaining the minimum subscription balance meant to gate that usage. This is a resource-abuse / access-control-bypass issue rather than fund theft, code execution, or transaction forgery — it matches "unauthorized DON-hosted secrets storage usage without maintaining minimum subscription balance."

### Likelihood Explanation
Exploitability requires the attacker to control the timing of on-chain balance mutations relative to gateway message submission — feasible for any account that owns/controls the referenced subscription, since withdrawing/cancelling funds is a permissionless action available to the subscription owner. The race window depends on network/gateway/RPC latency between `GetMaxUserBalance` (an RPC/subgraph read) and `storage.Put` (a DB write), which is realistically several hundred milliseconds to seconds — enough to reliably win the race by broadcasting a withdrawal transaction immediately after or concurrently with sending the `secrets_set` gateway message.

### Recommendation
Make the funding check atomic with the write: re-validate `GetMaxUserBalance` immediately before (or as part of) `storage.Put`, ideally inside the same critical section/transaction as the write, or have `s4.Storage.Put` accept a balance-verification callback/interface it invokes right before committing. Alternatively, perform the balance check using a block-height-pinned/consistent on-chain snapshot and only accept requests referencing recent enough blocks, and/or add a short cool-down/re-check pass over stored secrets to purge/expire slots whose owning subscription balance has since dropped below the minimum.

### Proof of Concept
Integration test plan (extending `core/services/functions/connector_handler_test.go`):
1. Configure `mockSubscriptions.GetMaxUserBalance` to return a value ≥ `minimumBalance` on first call.
2. Configure `mockStorage.Put` to, inside its own execution, trigger a state mutation (e.g., have the mock update an internal flag/counter representing "balance now below minimum" or simply have a second concurrent goroutine call `HandleGatewayMessage` again for the same subscription simulating a withdrawal) before returning success.
3. Call `handler.HandleGatewayMessage(ctx, gatewayID, secretsSetRequest)`.
4. Assert `mockStorage.Put` is invoked and succeeds (`response.Success == true`) even though the "current" balance (as verified by a second independent `GetMaxUserBalance` call made right before/after `Put`) is now below `minimumBalance` — demonstrating `Put` does not re-verify funding and the write silently succeeds despite TOCTOU invalidation of the precondition. func (h *functionsConnectorHandler) handleSecretsSet(ctx context.Context, gatewayId string, body *api.MessageBody, fromAddr ethCommon.Address) {
	var request functions.SecretsSetRequest
	var response functions.SecretsSetResponse
	err := json.Unmarshal(body.Payload, &request)
	if err == nil {
		key := s4.Key{
			Address: fromAddr,
			SlotId:  request.SlotID,
			Version: request.Version,
		}
		record := s4.Record{
			Expiration: request.Expiration,
			Payload:    request.Payload,
		}
		h.lggr.Debugw("handling a secrets_set request", "address", fromAddr, "slotId", request.SlotID, "payloadVersion", request.Version, "expiration", request.Expiration)
		err = h.storage.Put(ctx, &key, &record, request.Signature)
		if err == nil {
			response.Success = true
			promStorageUserUpdatesCount.WithLabelValues().Inc()
		} else {
			response.ErrorMessage = fmt.Sprintf("Failed to set secret: %v", err)
		}
	} else {
		response.ErrorMessage = fmt.Sprintf("Bad request to set secret: %v", err)
	}
	h.sendResponseAndLog(ctx, gatewayId, body, response)
}

func (s *storage) Put(ctx context.Context, key *Key, record *Record, signature []byte) error {
	if key.SlotId >= s.contraints.MaxSlotsPerUser {
		return ErrSlotIdTooBig
	}
	if len(record.Payload) > int(s.contraints.MaxPayloadSizeBytes) {
		return ErrPayloadTooBig
	}
	now := s.clock.Now().UnixMilli()
	if now > record.Expiration {
		return ErrPastExpiration
	}
	expSecs := s.contraints.MaxExpirationLengthSec * 1000
	if expSecs > math.MaxInt64 {
		return fmt.Errorf("expiration seconds overflows int64: %d", expSecs)
	}
	if record.Expiration-now > int64(expSecs) {
		return ErrExpirationTooLong
	}

	envelope := NewEnvelopeFromRecord(key, record)
	signer, err := envelope.GetSignerAddress(signature)
	if err != nil || signer != key.Address {
		return ErrWrongSignature
	}

	row := &Row{
		Address:    sqlutil.New(key.Address.Big()),
		SlotId:     key.SlotId,
		Payload:    make([]byte, len(record.Payload)),
		Version:    key.Version,
		Expiration: record.Expiration,
		Confirmed:  false,
		Signature:  make([]byte, len(signature)),
	}
	copy(row.Payload, record.Payload)
	copy(row.Signature, signature)

	return s.orm.Update(ctx, row)
