### Title
Relayer fee is paid out unconditionally before the ERC-20/base-token transfer outcome is known - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `inner_rlp_execute` schedules an unconditional NEAR transfer (the relayer fee) to the predecessor account as soon as it determines the transaction is a fee-bearing `EOABaseTokenTransfer` or `ERC20Transfer`, *before* the promise that performs the actual value transfer (native NEAR `Transfer` action or NEP-141 `ft_transfer` call) is created and resolved.

### Finding Description
In `inner_rlp_execute` [1](#0-0) , once the transaction kind is determined to be `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, the code immediately does:
```rust
let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
env::promise_batch_action_transfer(refund_promise, *fee);
```
This `refund_promise` is a standalone promise batch — it is **not** chained via `.then()` to the promise that actually performs the underlying transfer, and its execution is not gated on that transfer's success. The real transfer (either a native `Transfer` action, or for `ERC20Transfer`, a cross-contract `ft_transfer`/`storage_deposit`+`ft_transfer` call chained to `rlp_execute_callback`) is constructed afterward at [2](#0-1)  and its success/failure is only checked later in `rlp_execute_callback` [3](#0-2) , which can refund the *fee* on failure only if a `caller_deposit` (the attached NEAR deposit) exists — but the already-created `refund_promise` NEAR fee payment to the relayer is a separate receipt with no such reversal.

Because the NEP-141 `ft_transfer` (or `storage_deposit` + `ft_transfer` batch) can fail for many legitimate reasons controllable by the signing user or reachable through normal operation (insufficient token balance, receiver not registered, target token contract panics, insufficient attached gas relative to the token contract's needs, etc. — see `ERC20Transfer` branch and `nep_141_storage_balance_callback` at [4](#0-3) ), the wallet-contract owner's NEAR balance is unconditionally decreased by the fee amount even when the intended action never executes.

### Impact Explanation
This is unauthorized value movement out of the wallet contract's own NEAR balance: the fee is meant to compensate a relayer for successfully relaying a transfer, but it is paid regardless of whether the transfer (the entire reason for the fee) succeeds. A relayer (an unprivileged party who merely calls `rlp_execute`) can repeatedly submit user-signed transactions that are guaranteed or likely to fail (e.g., transfers exceeding the current token balance, or targeting unregistered/malicious NEP-141 contracts) and still collect the fee every time, draining the wallet owner's NEAR without ever completing the promised action. Nonce incrementing logic at [5](#0-4)  allows the nonce to advance on such attempts (except in the address-check special case), meaning each fee-draining attempt consumes a fresh nonce and cannot be trivially replayed, but a malicious/rational relayer can still choose to always submit failing (fee-only) transactions whenever profitable, i.e., whenever `fee` exceeds attached gas costs, regardless of underlying transfer outcome.

### Likelihood Explanation
This requires only a single relayer-submitted `rlp_execute` transaction; no privileged access, no validator collusion, and no network-level attack is needed. Any relayer that also controls (or colludes with) the target NEP-141 contract, or simply targets a transfer that is known to fail (e.g., due to insufficient balance) can trigger this every time a user signs a fee-bearing base-token or ERC-20 transfer.

### Recommendation
Chain the fee-refund promise so that it is only executed after (and conditioned on) the success of the actual value-transfer promise — e.g., include the fee transfer as part of the same promise, or move its creation into `rlp_execute_callback` (and `nep_141_storage_balance_callback` batch) after checking `PromiseResult::Successful`, rather than creating it unconditionally in `inner_rlp_execute` before the underlying transfer's outcome is known.

### Proof of Concept
1. A wallet-contract owner signs an Ethereum-style `ERC20Transfer` (or base token transfer) transaction with a non-zero `max_fee_per_gas * gas_limit` (computed into `tx_fee` in `parse_rlp_tx_to_action`, see [6](#0-5) ), intending to send tokens they do not actually hold enough of (or targeting a token contract that will panic on `ft_transfer`).
2. A relayer submits this transaction via `rlp_execute`.
3. `inner_rlp_execute` immediately creates and dispatches the fee-refund promise to the relayer's account [7](#0-6) .
4. The subsequent `ft_transfer` cross-contract call fails (`PromiseResult::Failed`), handled in `rlp_execute_callback` [8](#0-7) , which only refunds the attached `caller_deposit` (if any) — not the fee, which was already sent in step 3 and cannot be reclaimed.
5. Net result: the relayer collects the fee even though the ERC-20 transfer never took place, at the expense of the wallet-contract owner's NEAR balance.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
