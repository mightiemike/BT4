### Title
TOCTOU Race in `KVSessionStorage` Shop-Session Index Causes Lost/Corrupted Session Tracking - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage` maintains a per-shop index (`shop:<shop>` key) listing session IDs, used by `findSessionsByShop`. Both `addShopIds` and `removeShopIds` perform a non-atomic read-modify-write on this shared index. Concurrent `storeSession`/`deleteSession` calls for the same shop (e.g. multiple staff members completing online OAuth/token-exchange around the same time, or a webhook-driven uninstall racing a new login) can overwrite each other's update, exactly mirroring the reported `currentWithheldETH` pattern: state is read once, checked/used, and written back later without accounting for concurrent mutators.

### Finding Description
`addShopIds` and `removeShopIds` both do:
```ts
const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
await this.namespace.put(key, JSON.stringify([...shopIds, ...ids])); // or filtered
``` [1](#0-0) 

There is no compare-and-swap, lock, or transaction. If two `storeSession` calls for the same shop (`session.shop`) run concurrently — a realistic scenario since `storeSession` is invoked on every OAuth callback and token-exchange completion, and `useOnlineTokens` apps create a distinct session per staff member — both read the same stale `shopIds` snapshot and each overwrites the index with only its own addition, silently dropping the other's session ID from the shop index: [2](#0-1) 

Symmetrically, a `deleteSession` racing a concurrent `storeSession`/`deleteSession` for the same shop can cause `removeShopIds` to write back a list based on a stale read, either resurrecting a deleted ID or losing a newly added one: [3](#0-2) 

The consequence surfaces in `findSessionsByShop`, which trusts the index and force-unwraps (`!`) the result of `loadSession` for every listed ID without a null check:
```ts
return Promise.all(
  sessionIds.map(async (id) => (await this.loadSession(id))!),
);
``` [4](#0-3) 

If a stale/removed ID lingers in the index (lost update in `removeShopIds`), `loadSession(id)` returns `undefined` at runtime (the `!` is a compile-time-only assertion), and `findSessionsByShop` returns an array containing `undefined`. Any downstream consumer that assumes an array of `Session` objects (e.g. app uninstall/reauth flows in `shopify-app-express`'s `app-installations.ts`, which uses `findSessionsByShop` to look up and clean up sessions) will throw a `TypeError` when accessing `.shop`/`.accessToken`/etc. on the `undefined` entry.

### Impact Explanation
This is the direct analog of the reported bug class: a shared accounting value (`currentWithheldETH` / the shop session index) is read, used to decide an operation, and written back later without synchronization, so concurrent legitimate actors overcommit/undercommit the shared state. Here the result is not a fund lock but corruption of the session index that other request-authentication and shop-cleanup logic (`findSessionsByShop`) relies on — causing unhandled exceptions (denial of service) in session-lookup/cleanup code paths for that shop, and potential loss of tracking for legitimately stored sessions (so a valid session becomes unreachable via `findSessionsByShop` even though `loadSession(id)` for that exact ID would still work). Severity is bounded by the fact that it requires genuine concurrency (multiple simultaneous auth completions for the same shop) and only affects the Cloudflare KV session storage adapter, one of several optional storage backends shipped in this repo.

### Likelihood Explanation
Concurrency for the same shop is realistic and not attacker-privileged: any shop with `useOnlineTokens: true` and multiple staff members, or any shop reinstalling/re-authenticating while a background job or webhook triggers session deletion, can produce overlapping `storeSession`/`deleteSession` calls. No secrets, MITM, or privileged access are required — ordinary concurrent legitimate traffic against the app's OAuth/token-exchange endpoints is sufficient to trigger the race.

### Recommendation
Replace the read-modify-write pattern in `addShopIds`/`removeShopIds` with an atomic primitive (e.g., a KV transaction/compare-and-swap if available, or a retry loop with optimistic concurrency using a version/ETag), or serialize per-shop index updates behind a lock/queue. Additionally, `findSessionsByShop` should filter out `undefined` results from `loadSession` instead of relying on the unsafe non-null assertion, to avoid crashing callers if the index and session store ever diverge.

### Proof of Concept
1. Configure an app with `KVSessionStorage` and `useOnlineTokens: true`.
2. Simulate two staff members of the same shop completing OAuth/token-exchange concurrently, calling `storeSession(sessionA)` and `storeSession(sessionB)` at nearly the same time (e.g., both `await this.namespace.get(key)` before either `put` resolves — trivial to force in a unit test by stubbing `namespace.get`/`namespace.put` with controlled delays).
3. Observe that `shop:<shop>` key in the KV namespace ends up containing only one of `sessionA.id`/`sessionB.id`, not both.
4. Call `findSessionsByShop(shop)` — the result silently omits the untracked session even though `loadSession(untracked.id)` still succeeds.
5. Repeat with a concurrent `deleteSession` racing a `storeSession`; show the deleted ID can remain in the index, causing `findSessionsByShop` to return an array containing `undefined`, which crashes any caller (e.g. uninstall/session-cleanup logic) that assumes `Session` objects.

    );

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  private async removeShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(
      key,
      JSON.stringify(shopIds.filter((id) => !ids.includes(id))),
    );
  }
