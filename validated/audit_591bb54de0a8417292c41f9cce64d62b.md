Based on my investigation, I found where `validate_congestion_info` is called (`chain/chain/src/validate.rs:171`), which delegates to `CongestionInfo::validate_extra_and_header` (`core/primitives/src/congestion_info.rs:204`). This function checks `delayed_receipts_gas`, `buffered_receipts_gas`, and `receipt_bytes` between the locally-computed chunk extra and the header, but explicitly does **not** validate the `allowed_shard` field, per its own `TODO(congestion_control)` comment at line 203.

### Title
Incomplete validation of chunk-header congestion info allows a block/chunk producer to forge `allowed_shard` - (File: core/primitives/src/congestion_info.rs)

### Summary
`CongestionInfo::validate_extra_and_header` is the analog of the Chainlink bug: it validates *some* fields of externally-supplied "returned data" (the chunk header's committed `CongestionInfo`, analogous to `latestRoundData`'s tuple) but omits validation of `allowed_shard`, one of the four fields that make up the committed struct.

### Finding Description
`validate_chunk_with_chunk_extra_and_receipts_root` (`chain/chain/src/validate.rs:171`) calls `validate_congestion_info(prev_chunk_extra.congestion_info(), chunk_header.congestion_info())`, which is `CongestionInfo::validate_extra_and_header` (`core/primitives/src/congestion_info.rs:204-213`). That function compares `delayed_receipts_gas`, `buffered_receipts_gas`, and `receipt_bytes` but leaves `allowed_shard == header.allowed_shard` commented out with `// TODO(congestion_control) validate allowed shard`. The `allowed_shard` value is supposed to be deterministically derived by `finalize_allowed_shard` (`congestion_info.rs:360-368`) from `(own_shard, all_shards, congestion_seed)`, but nothing forces the chunk producer's committed header value to match this derivation.

### Impact Explanation
`allowed_shard` gates cross-shard forwarding under full congestion: `CongestionControl::outgoing_gas_limit` (`congestion_info.rs:80-93`) grants `allowed_shard_outgoing_gas` only to the sender shard matching `allowed_shard`, and zero to everyone else; `outgoing_size_limit` (`:103-111`) similarly grants the large size limit only to the allowed shard. If a chunk producer commits a forged `allowed_shard` in its chunk header and this passes validation (since the field is never checked against the previous chunk extra/deterministic derivation), that producer could designate an unauthorized/attacker-controlled shard as the sole shard allowed to forward receipts during full congestion — bypassing the NEP-539 backpressure guarantee, or conversely blocking the legitimate shard from making progress. This is a state-transition/invalid-block-acceptance class issue: different honest nodes computing the correct `allowed_shard` would reject a chunk with the wrong value if the check were enforced, but currently it is accepted, which can produce inconsistent enforcement of congestion admission rules across the network relative to spec.

### Likelihood Explanation
Exploitability requires a chunk/block producer role (a validator producing chunks for that shard) rather than an arbitrary unprivileged caller — this weakens applicability under the stated scope ("unprivileged transaction signer, contract deployer, ... staker, or RPC caller"), since a staker/validator producing a chunk is a privileged role, not a pure external caller. The spec itself flags this exact gap as an open, undetermined-impact item: "`validate_extra_and_header` explicitly does **not** yet validate the `allowed_shard` field ... whether this is exploitable is not determined from code alone" (`protocol-model/spec/cross-shard-congestion.md:421-423`).

### Recommendation
Extend `CongestionInfo::validate_extra_and_header` to also assert `extra.allowed_shard == header.allowed_shard`, matching the value that would be produced by `finalize_allowed_shard`/`get_new_allowed_shard`, and reject the chunk (return `Err(Error::InvalidCongestionInfo)`/equivalent) if it diverges, consistent with the other checked fields.

### Proof of Concept
Not executable from static analysis alone — this requires acting as a chunk producer for the shard in question and setting `CongestionInfo.allowed_shard` in the committed chunk header to a value different from the one `get_new_allowed_shard` would compute, then observing that `validate_chunk_with_chunk_extra_and_receipts_root` still accepts the chunk despite the mismatch (since `validate_extra_and_header` skips that field).

---
Note on scope: this finding requires a **chunk-producer/validator** role to exploit, not a fully unprivileged caller, and the security-relevant impact of the missing check is explicitly marked as undetermined in the codebase's own documentation. Given the "no validator-only paths" restriction in the rules, this candidate is presented for completeness but is borderline against the stated scope; I could not find any stronger analog reachable purely by an unprivileged transaction/RPC caller for this specific bug class (incomplete validation of a multi-field external data return, e.g. staleness/completeness) in the areas I searched (gas price verification, nonce/access-key verification, congestion control, receipt validation, epoch/header validation) — those all fully validate every field they read.     pub fn finalize_allowed_shard(

        own_shard: ShardId,
        all_shards: &[ShardId],

        let allowed_shard = Self::get_new_allowed_shard(own_shard, all_shards, congestion_seed);

    }

    fn get_new_allowed_shard(
        own_shard: ShardId,
        all_shards: &[ShardId],
        congestion_seed: u64,
    ) -> ShardId {
        if let Some(index) = congestion_seed.checked_rem(all_shards.len() as u64) {
            // round robin for other shards based on the seed
            return *all_shards
                .get(index as usize)
                .expect("`checked_rem` should have ensured array access is in bound");
        }
        // checked_rem failed, hence all_shards.len() is 0
        // own_shard is the only choice.
        return own_shard;
    }
