## Title
Non-deterministic randomness in State-Diff Encryption Hint Causes Honest-Node Divergence in OS Output Commitment — (File: `crates/starknet_os/src/hints/hint_implementation/output.rs`)

## Summary
The KRACK report's root cause is that a communicating party is allowed to non-deterministically reuse/regenerate cryptographic material (nonce/key) at a point where the protocol's security depends on that value being fixed and unique per session, so two computations that should be identical (or non-repeating) silently diverge and can be correlated by an observer. The closest reachable analog in this sequencer is not a wireless nonce, but the analogous invariant that the **Starknet OS program's output must be a deterministic function of the block's transactions** so that independent re-executions (or independent honest provers) of the same block always commit to the same output/root/block hash. The confidential state-diff (DA) encryption hint breaks this invariant by drawing its symmetric/private keys from a true CSPRNG (`OsRng`) rather than deterministically from the block content.

## Finding Description
`encrypt_state_diff` in `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/encrypt.cairo` (lines 45-74) is invoked from `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/output.cairo` (import at line 13) whenever a DA committee is configured (`n_keys > 0`), as part of constructing the OS's committed output (`OsOutput`/`OsOutputHeader`, `output.cairo` lines 26-49).

Inside `encrypt_state_diff`, the hint `%{ GenerateKeysUsingSha256Hash %}` (`encrypt.cairo` line 53) generates `symmetric_key` and `sn_private_keys`, implemented by `calculate_keys_using_sha256_hash` in `crates/starknet_os/src/hints/hint_implementation/output.rs` (lines 149-206): [1](#0-0) 

The seed is derived from `OsRng.fill_bytes(&mut random_bytes)` — a cryptographically secure, **non-deterministic** random source — and only additionally mixed with the (deterministic) compressed state diff "for extra defense", not as the sole entropy source: [2](#0-1) 

Back in Cairo, the only constraints placed on the hint-provided values are range checks (`assert_not_zero`, `assert_le_felt`) on the private keys — there is no constraint tying `symmetric_key`/`sn_private_keys` to any deterministic function of the block: [3](#0-2) 

The resulting `encrypted_symmetric_keys` and ciphertext (`ciphertext[i] = plaintext[i] + BLAKE2s(symmetric_key, i)`, see `encrypt.cairo` lines 33-35 and 199-211) are written into the OS's DA/output segment, which is precisely the data whose hash is used for the KZG/state-diff commitment and ultimately the block hash pipeline (see `output.cairo` header fields and the block hash/commitment flow reflected in `crates/blockifier_reexecution/src/utils.rs` `compare_block_hash`, lines 209-255, and the consensus finalization flow in `docs/diagrams/04-consensus-finalization-flow.md`).

Because `OsRng` supplies fresh entropy on every invocation, **two honest executions of the identical block** (e.g., a validator re-executing/re-proving a proposed block, or the Starknet OS re-execution consistency check that the codebase itself performs — see `crates/blockifier_reexecution/src/rpc_replay.rs` lines 199-241, `compare_state_diffs`/`compare_block_hash`) will derive different `symmetric_key`/`sn_private_keys`, hence different `sn_public_keys`, `encrypted_symmetric_keys`, and ciphertext bytes for the same logical, unencrypted state diff. Any commitment/hash computed over this segment will differ between the two honest computations, even though the underlying transactions and state transition are identical.

## Impact Explanation
This breaks the "Starknet OS re-execution" and "state commitment / block hash" invariants explicitly called out as in-scope: an honest prover/validator independently computing the OS output for a given block (with the DA-committee-encryption feature enabled) will not reproduce the same committed root/block hash as another honest party executing the same block, i.e. **honest-node divergence** and **wrong committed root or block hash**. In a proof-based or multi-prover setting this can prevent the network from reaching agreement on the correct block hash for that height, i.e., a network unable to confirm new blocks when this feature path is active.

## Likelihood Explanation
This is not merely a resource/DoS issue and requires no malicious operator, peer, or prover: it is a deterministic-by-design bug that fires every time the confidential DA-encryption feature is exercised (n_keys > 0), because `calculate_keys_using_sha256_hash` unconditionally draws primary entropy from `OsRng` rather than a value derivable identically by any honest re-executor. Any block whose state diff is destined for encrypted DA output will exhibit this divergence.

## Recommendation
Derive `symmetric_key` and `sn_private_keys` deterministically and solely from data available to every honest re-executor of the block (e.g., hash of the actual compressed state diff, block number, and other committed block context) rather than from `OsRng`, and add explicit Cairo-level constraints (not just range checks) tying the hint output to that deterministic derivation so the prover cannot supply arbitrary values.

## Proof of Concept
1. Configure a chain with DA-committee encryption enabled (non-zero `n_keys`/`public_keys` supplied to `encrypt_state_diff`).
2. Execute the Starknet OS for a given block twice (e.g., once by the original prover, once by an independent re-executor, as already exercised by `crates/blockifier_reexecution` tooling).
3. Observe that `calculate_keys_using_sha256_hash` (`crates/starknet_os/src/hints/hint_implementation/output.rs:149-166`) produces different `random_bytes` each run (from `OsRng`), yielding different `symmetric_key`, `sn_private_keys`, and therefore different `encrypted_symmetric_keys` and ciphertext in the OS output/DA segment.
4. Compute the corresponding commitment/block hash for each run (as done in `compare_block_hash`, `crates/blockifier_reexecution/src/utils.rs:209-255|`) and observe the two hashes differ despite identical underlying transactions and state diff.

pub(crate) fn calculate_keys_using_sha256_hash(mut ctx: HintContext<'_>) -> OsHintResult {
    // Generate a cryptographically secure random seed.
    let mut random_bytes = [0u8; 32];
    OsRng.fill_bytes(&mut random_bytes);

    let mut hasher = Sha256::new();
    hasher.update(random_bytes);

    // In addition, hash the compressed state diff for extra defense against potential attacks on
    // randomness source.
    let compressed_start = ctx.get_ptr(Ids::CompressedStart)?;
    let compressed_end = ctx.get_ptr(Ids::CompressedEnd)?;
    let array_size = (compressed_end - compressed_start)?;
    for i in 0..array_size {
        let felt = ctx.vm.get_integer((compressed_start + i)?)?;
        hasher.update(felt.to_bytes_be());
    }
    let random_key_seed = hasher.finalize().to_vec();
