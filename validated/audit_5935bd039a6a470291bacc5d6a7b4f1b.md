### Title
Relative rounding-error tolerance in `ExchangeWithdrawActuator` can reject valid withdrawals when the computed swap amount is small (analog of divide-by-small-base check flaw) - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
The Smilee report describes `FinanceIGDelta.deltaHedgeAmount` reverting almost always when the reference base value (`sideTokensAmount`) used to compute an absolute rounding-error tolerance is 0 or tiny, because the tolerance (`base/10000`) collapses to 0, making the "is this just rounding dust" check fail for essentially any nonzero rounding error. `java-tron`'s hardened exchange precision check in `ExchangeWithdrawActuator.doValidate()` has the same structural flaw, but with the tolerance base tied to the *computed swap-out amount* (`anotherTokenQuant`) instead of a pool balance: `remainder / anotherTokenQuant > 0.0001` (or the BigDecimal-equivalent comparison against `anotherTokenQuant * 0.0001`).

### Finding Description
When `allowHardenExchangeCalculation()` is enabled, `ExchangeWithdrawActuator.doValidate()` computes the amount of the counter-token to return (`anotherTokenQuant`) via integer/BigDecimal division, then checks whether the true (fractional) ratio deviates from the truncated integer result by more than a relative tolerance of `0.0001` (0.01%) of `anotherTokenQuant`: [1](#0-0) 

and symmetrically for the other branch: [2](#0-1) 

The remainder being checked is essentially the fractional part of the true division result (a value that can range from 0 up to just under 1, since it is `trueValue - floor(trueValue)`), while the tolerance threshold is `anotherTokenQuant * 0.0001`. When `anotherTokenQuant` is small (e.g., 1–100 units, which is common for low-supply/low-decimal TRC10 tokens or dust-sized withdrawals), the threshold shrinks toward 0 (e.g., `1 * 0.0001 = 0.0001`), while the fractional remainder from any non-exact ratio is typically much larger than that. This means nearly any withdrawal that doesn't produce an exact integer ratio will fail with `"Not precise enough"`, exactly mirroring the Smilee bug pattern where an absolute/relative tolerance is derived from a value that is itself small or zero, causing the "is this just a rounding error" check to reject essentially all legitimate transactions instead of only genuinely large-error ones.

This is confirmed by the project's own hardened-mode tests, which show a precise ratio passing and a slightly imprecise one (`quant = 9991`, an off-by-fractional-unit case) immediately failing with `"Not precise enough"`: [3](#0-2) 

The check is only reachable when `AllowHardenExchangeCalculation` is enabled, which is a chain-parameter gated by committee/witness proposal, exposed via `AbstractExchangeActuator.allowHarden()`: [4](#0-3) 

Once that parameter is turned on network-wide, the flawed check applies unconditionally to every unprivileged user's `ExchangeWithdrawContract` transaction.

### Impact Explanation
This causes a denial-of-service of the TRC10 `ExchangeWithdraw` (bancor-style exchange withdrawal) function for any pool/withdrawal amount combination that doesn't produce an exactly-integer counter-token quantity when the resulting `anotherTokenQuant` is small. Legitimate users attempting to withdraw liquidity — especially small positions or tokens with low decimal precision — would have their transactions revert with `ContractValidateException("Not precise enough")` even though the deviation is pure integer-truncation rounding noise, not an actual manipulation or economic loss. This blocks a core protocol function (liquidity withdrawal from the on-chain bancor exchange) for affected users, analogous to the "core protocol function unavailable" impact called out in the source report.

### Likelihood Explanation
The condition triggers deterministically whenever `anotherTokenQuant` is small relative to the pool ratio's fractional remainder — a very common scenario for small withdrawals or low-balance/low-decimal token pools, requiring no adversarial input, only ordinary usage. The only precondition is that `AllowHardenExchangeCalculation` be activated via the standard TRON committee-proposal governance mechanism, after which any unprivileged user's normal `ExchangeWithdraw` calls are affected.

### Recommendation
Do not scale the rounding-error tolerance solely by the (potentially tiny) computed output amount. Use a tolerance based on a fixed minimum absolute unit combined with the relative check (e.g., `max(anotherTokenQuant / 10000, MIN_ABS_TOLERANCE)`), or compare the relative error against the token pool balance (a much larger, stable denominator) rather than against the small computed swap output, consistent with the Sherlock recommendation to check both relative and absolute error bounds.

### Proof of Concept
Using the existing hardened-mode test harness in `ExchangeWithdrawActuatorTest`: [3](#0-2) 
1. Enable `AllowHardenExchangeCalculation` (`saveAllowHardenExchangeCalculation(1)`).
2. Set up an exchange pool (e.g., 100M/200M balances as in `InitExchangeSameTokenNameActive`).
3. Call `ExchangeWithdrawActuator` with a `quant` that yields a non-exact ratio and a small `anotherTokenQuant` (test uses `9991`, producing `"Not precise enough"`).
4. Observe `ContractValidateException("Not precise enough")` is thrown even though the withdrawal request itself is legitimate and only differs from the exact ratio by integer-truncation rounding — demonstrating the check fails almost universally once the computed output value is small.
