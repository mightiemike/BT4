This confirms the analysis. The actual state-changing execution of a deposit system transaction happens via `process_sys_txs`/`apply_l2_block_txs` against the real, current `working_set` at block-production time (not the stale `BlockId::pending()` snapshot used only for the RPC admission `eth_call`), and any deposit whose `txId` has already been nullified fails there with `L2BlockModuleCallError::EvmSystemTransactionNotSuccessful`, causing the working set to be reverted and no balance change to occur, as demonstrated in `crates/evm/src/tests/sys_tx_tests.rs:812-822` and enforced by `require(!processedTxIds[txId], "txId already spent")` in `Bridge.sol:211`. Separately, forging a `moveTx`/`proof`/`shaScriptPubkeys` blob that both passes `validateAndCheckInclusion` (real Merkle inclusion against the light client) and `verifySigInTx`'s Schnorr check requires possessing the actual N-of-N aggregated private key material, which is excluded from the threat model (no key compromise).
