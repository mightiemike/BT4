### Title
Unmetered native zk-SNARK verification cost in `ShieldedTransferActuator.checkProof` combined with bandwidth-fee exemption enables cheap CPU-exhaustion DoS - (File: `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
`ShieldedTransferActuator.validate()`/`checkProof()` unconditionally invokes native `librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck` (Groth16 pairing verifications on BLS12-381) for every submitted `ShieldedTransferContract`, whether the proof is genuine or garbage, yet the transaction is only charged a flat, committee-set `SHIELDED_TRANSACTION_FEE` (default 100,000 sun = 0.1 TRX) that is completely decoupled from this CPU cost. Compounding this, `BandwidthProcessor.consume` explicitly skips bandwidth accounting for `ShieldedTransferContract` (`if (contract.getType() == ShieldedTransferContract) continue;`), so the attacker pays zero bandwidth fee regardless of the transaction's size. Because `Manager.pushTransaction` performs signature check and then `processTransaction` (which triggers `checkProof`) inside a process-wide `synchronized(this)` block, a stream of cheap, invalid shielded transactions serializes and burns CPU on every node that receives/validates them, for a cost far below that of legitimate resource-metered operations like `TransferContract`.

### Finding Description
An unprivileged attacker with a small transparent balance can build a `ShieldedTransferContract` (public → shielded, requiring only a normal ECDSA-signed transparent input, no committee/witness role) containing a `SpendDescription` or `ReceiveDescription` with syntactically well-formed but cryptographically bogus fields:
- correctly-sized `zkproof` (192 bytes), `cv`/`anchor`/`nullifier`/`rk` (32 bytes each), `spendAuthoritySignature`/`bindingSignature` (64 bytes), and `cEnc`/`cOut` at the required `ZC_ENCCIPHERTEXT_SIZE`/`ZC_OUTCIPHERTEXT_SIZE` lengths,
- a valid, already-existing Merkle anchor obtained via `merkleRootExist` (e.g. the well-known empty-tree root or any historical root, trivially fetched via public shielded RPC APIs),
- a fresh 32-byte nullifier (to pass the "not yet spent" / duplicate checks).

Flow: `Wallet.broadcastTransaction` → `Manager.pushTransaction` (chainbase/... `Manager.java:886-953`) → `trx.validateSignature(...)` (cheap ECDSA check, since shielded owner is the transparent-from address) → `processTransaction` → `consumeBandwidth`/actuator `validate()`. Inside `validate()` (`ShieldedTransferActuator.java:196-273`), after cheap checks (nullifier/anchor existence, duplicate cm), `checkProof()` (`ShieldedTransferActuator.java:275-358`) unconditionally initializes a verification context and calls the native `JLibrustzcash.librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck` methods, which perform full elliptic-curve pairing-based zk-SNARK verification — computationally far heavier than the ECDSA signature check that gates a plain `TransferContract`.

Two properties make the fee/cost mismatch exploitable:
1. `calcFee()` (`ShieldedTransferActuator.java:478-489`) returns only the flat `SHIELDED_TRANSACTION_FEE` (or create-account fee), independent of how many spend/receive descriptions are processed or of the intrinsic cost of the crypto verification performed.
2. `BandwidthProcessor.consume` (`chainbase/.../BandwidthProcessor.java:122-125`) explicitly `continue`s (skips) bandwidth billing for `ShieldedTransferContract`, so the attacker is not charged even the standard per-byte network fee that every other contract type must pay.

Because signature validation and the pending-shielded-tx counter check (`shieldedTransInPendingMaxCounts`, `Manager.java:892-943`) both occur cheaply/quickly and the invalid proof causes the transaction to fail fast (freeing the pending slot), an attacker can repeatedly submit such transactions in a loop; each one forces one full native pairing-verification cycle inside the node's `synchronized(this)` transaction-processing critical section (`Manager.java:924`), serializing this against all other transaction/block processing on the node, for a fee that does not reflect that cost.

Existing checks that do NOT stop this:
- `TransactionCapsule.validateSignature` only requires a valid signature from the transparent-from account (an attacker-controlled funded account) — not a barrier.
- `ContractValidateException` from `checkProof` is thrown, but only *after* the expensive native call has already executed.
- The flat `SHIELDED_TRANSACTION_FEE`/`SHIELDED_TRANSACTION_CREATE_ACCOUNT_FEE` bear no relationship to zk-verification CPU cost, and the corresponding governance proposal cases (`SHIELDED_TRANSACTION_FEE`, `ALLOW_SHIELDED_TRANSACTION`) are commented out in `ProposalUtil.java:272-292`, meaning there is no live path in this codebase for the committee to raise the fee if CPU costs prove disproportionate.

### Impact Explanation
This matches the TRON bounty's "DoS via the TRON protocol implementation" class: an unprivileged, ordinarily-funded account can force disproportionately expensive native cryptographic computation on every node's transaction-validation path for far less real fee-value than an equivalent-cost operation would normally require, and this happens inside a global lock that serializes transaction processing, degrading mempool/tx-processing throughput node-wide under sustained submission.

### Likelihood Explanation
- Requires: an ordinary funded account, `ALLOW_SAME_TOKEN_NAME`=1 and shielded-transaction support enabled (both are long-standing, already-activated network parameters on the live TRON chain, not a special/non-default configuration attackers must create).
- Cost per transaction to the attacker: only the flat `SHIELDED_TRANSACTION_FEE` (0.1 TRX default) plus normal transparent-input balance requirement — no bandwidth fee is charged for the shielded contract type.
- Fully repeatable: attacker only needs distinct nullifiers (trivial, random 32 bytes) and a valid, already-known Merkle anchor (trivially obtainable), so the attack can be automated and repeated indefinitely, bounded only by the attacker's available fee balance and the `shieldedTransInPendingMaxCounts` throttle on concurrently pending shielded transactions (which does not bound total throughput over time since invalid transactions fail and free the slot quickly).

### Recommendation
- Charge bandwidth for `ShieldedTransferContract` like any other contract type instead of unconditionally `continue`-ing in `BandwidthProcessor.consume`.
- Scale `SHIELDED_TRANSACTION_FEE`/energy cost with the number of `SpendDescription`/`ReceiveDescription` entries actually verified (each `librustzcashSaplingCheckSpend`/`CheckOutput` call should have an associated energy/fee cost, similar to the `VerifyMintProof`/`VerifyTransferProof`/`VerifyBurnProof` precompiles which do assign `getEnergyForData`).
- Re-enable/restore a governance path (currently commented out in `ProposalUtil.java`) so the committee can adjust `SHIELDED_TRANSACTION_FEE` to reflect real verification cost.
- Consider performing a cheap, cost-bounded pre-check (e.g., curve point validity / structural sanity) before invoking the full pairing-based verification, and/or rate-limit invalid-shielded-tx submissions per source account.

  private void checkProof(List<SpendDescription> spendDescriptions,
      List<ReceiveDescription> receiveDescriptions, long fee) throws ZkProofValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    ZKProofStore proofStore = chainBaseManager.getProofStore();
    if (proofStore.has(tx.getTransactionId().getBytes())) {
      if (proofStore.get(tx.getTransactionId().getBytes())) {
        return;
      } else {
        throw new ZkProofValidateException("record is fail, skip proof", false);
      }
    }

    byte[] signHash = getShieldTransactionHashIgnoreTypeException(tx.getInstance());

    if (CollectionUtils.isNotEmpty(spendDescriptions)
        || CollectionUtils.isNotEmpty(receiveDescriptions)) {
      long ctx = JLibrustzcash.librustzcashSaplingVerificationCtxInit();
      try {
        for (SpendDescription spendDescription : spendDescriptions) {
          if (!JLibrustzcash.librustzcashSaplingCheckSpend(
              new CheckSpendParams(ctx,
                  spendDescription.getValueCommitment().toByteArray(),
                  spendDescription.getAnchor().toByteArray(),
                  spendDescription.getNullifier().toByteArray(),
                  spendDescription.getRk().toByteArray(),
                  spendDescription.getZkproof().toByteArray(),
                  spendDescription.getSpendAuthoritySignature().toByteArray(),
                  signHash)
          )) {
            throw new ZkProofValidateException("librustzcashSaplingCheckSpend error", true);
          }
        }

        for (ReceiveDescription receiveDescription : receiveDescriptions) {
          if (receiveDescription.getCEnc().size() != ZC_ENCCIPHERTEXT_SIZE
              || receiveDescription.getCOut().size() != ZC_OUTCIPHERTEXT_SIZE) {
            throw new ZkProofValidateException("Cout or CEnc size error", true);
          }
          if (!JLibrustzcash.librustzcashSaplingCheckOutput(
              new CheckOutputParams(ctx,
                  receiveDescription.getValueCommitment().toByteArray(),
                  receiveDescription.getNoteCommitment().toByteArray(),
                  receiveDescription.getEpk().toByteArray(),
                  receiveDescription.getZkproof().toByteArray())
          )) {
            throw new ZkProofValidateException("librustzcashSaplingCheckOutput error", true);
          }
        }

        long valueBalance;
        long totalShieldedPoolValue = dynamicStore
            .getTotalShieldedPoolValue();
        try {
          valueBalance = addExact(subtractExact(
              shieldedTransferContract.getToAmount(),
              shieldedTransferContract.getFromAmount()), fee);
          totalShieldedPoolValue = subtractExact(
              totalShieldedPoolValue, valueBalance);
        } catch (ArithmeticException e) {
          logger.debug(e.getMessage(), e);
          throw new ZkProofValidateException(e.getMessage(), true);
        }

        if (totalShieldedPoolValue < 0) {
          throw new ZkProofValidateException("shieldedPoolValue error", true);
        }

        if (!JLibrustzcash.librustzcashSaplingFinalCheck(
            new FinalCheckParams(ctx,
                valueBalance,
                shieldedTransferContract.getBindingSignature().toByteArray(),
                signHash)
        )) {
          throw new ZkProofValidateException("librustzcashSaplingFinalCheck error", true);
        }
      } catch (ZksnarkException e) {
        throw new ZkProofValidateException(e.getMessage(), true);
      } finally {
        JLibrustzcash.librustzcashSaplingVerificationCtxFree(ctx);
      }
    }

    recordProof(tx.getTransactionId(), true);
  }

  public boolean pushTransaction(final TransactionCapsule trx)
      throws ValidateSignatureException, ContractValidateException, ContractExeException,
      AccountResourceInsufficientException, DupTransactionException, TaposException,
      TooBigTransactionException, TransactionExpirationException,
      ReceiptCheckErrException, VMIllegalException, TooBigTransactionResultException {

    if (isShieldedTransaction(trx.getInstance()) && !chainBaseManager.getDynamicPropertiesStore()
        .supportShieldedTransaction()) {
      throw new ContractValidateException("ShieldedTransferContract is not supported.");
    }

    if (isExchangeTransaction(trx.getInstance())) {
      throw new ContractValidateException("ExchangeTransactionContract is rejected");
    }

    pushTransactionQueue.add(trx);
    Metrics.gaugeInc(MetricKeys.Gauge.MANAGER_QUEUE, 1,
        MetricLabels.Gauge.QUEUE_QUEUED);
    try {
      if (!trx.validateSignature(chainBaseManager.getAccountStore(),
          chainBaseManager.getDynamicPropertiesStore())) {
        throw new ValidateSignatureException(String.format("trans sig validate failed, id: %s",
            trx.getTransactionId()));
      }

      synchronized (transactionLock) {
        while (true) {
          try {
            if (isBlockWaitingLock()) {
              TimeUnit.MILLISECONDS.sleep(SLEEP_FOR_WAIT_LOCK);
            } else {
              break;
            }
          } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            logger.debug("The wait has been interrupted.");
          }
        }
        synchronized (this) {
          if (isShieldedTransaction(trx.getInstance())
                  && shieldedTransInPendingCounts.get() >= shieldedTransInPendingMaxCounts) {
            return false;
          }
          if (!session.valid()) {
            session.setValue(revokingStore.buildSession());
          }

          try (ISession tmpSession = revokingStore.buildSession()) {
            processTransaction(trx, null);
            trx.setTrxTrace(null);
            pendingTransactions.add(trx);
            Metrics.gaugeInc(MetricKeys.Gauge.MANAGER_QUEUE, 1,
                    MetricLabels.Gauge.QUEUE_PENDING);
            tmpSession.merge();
          }
          if (isShieldedTransaction(trx.getInstance())) {
            shieldedTransInPendingCounts.incrementAndGet();
          }
        }
      }
    } finally {
      if (pushTransactionQueue.remove(trx)) {
        Metrics.gaugeInc(MetricKeys.Gauge.MANAGER_QUEUE, -1,
            MetricLabels.Gauge.QUEUE_QUEUED);
      }
    }
    return true;
  }
