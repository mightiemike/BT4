### Title
TRX sent via `CALL`/`CALLCODE` to a precompiled contract address gets permanently stuck since no precompile uses or refunds `msg.value` - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
When a TVM contract executes `CALL` or `CALLCODE` with a nonzero value against one of the reserved precompiled-contract addresses (e.g. `ecRecover`, `sha256`, `ripemd160`, `modExp`, `altBN128*`, `batchValidateSign`, `validateMultiSign`, TVM-vote precompiles, `p256Verify`, etc.), `Program.callToPrecompiledAddress` unconditionally transfers the endowment/value to that fixed precompile address before invoking the precompile logic. None of the precompiled contracts consume, forward, or refund this value, so the TRX becomes permanently locked on an address that has no corresponding private key and can never be the source of a signed, protocol-level transfer out. This mirrors the reported bug class where a `payable` function accepts value but never interacts with `msg.value`, permanently stranding funds on the contract.

### Finding Description
In `Program.callToPrecompiledAddress`, the endowment is charged unconditionally whenever the call's value is nonzero, prior to executing the precompiled contract: [1](#0-0) 

This is triggered from any smart contract via a plain `CALL`, `CALLCODE`, or token-transfer opcode targeting a precompile address, dispatched from `OperationActions.exeCall`: [2](#0-1) 

`MUtil.transfer` performs the balance mutation with no restriction on the destination being a "real" contract/account or having any means to move the balance back out: [3](#0-2) 

The set of reserved precompile addresses (fixed constants such as `0x01`..`0x09`, `0x100`, and TVM-vote precompile addresses) is defined in `PrecompiledContracts`: [4](#0-3) 

None of these fixed precompile addresses correspond to a derivable ECDSA keypair, and no actuator (`TransferActuator`, `TransferAssetActuator`, VM code) ever debits balance *from* one of these addresses on behalf of a user — nothing in the codebase treats them as spendable. Once TRX accumulates on such an address via the value-forwarding path above, it is unrecoverable through any normal signed transaction or TVM opcode, since executing code at that address is intercepted by `PrecompiledContracts.getContractForAddress` and routed to the fixed precompile logic instead of arbitrary user bytecode that could implement a withdrawal.

### Impact Explanation
Any contract (and by extension any user interacting with a contract that forwards a `value` parameter to an external call, intentionally or via a bug/exploit) can cause TRX to be sent with `CALL value(x)()` to a precompiled address. This TRX is irrecoverably locked — a permanent, unintentional loss of funds analogous to a burn, but without going through the designated `blackhole`/burn-TRX accounting path (`dynamicStore.burnTrx`), meaning it corrupts on-chain balance accounting relative to protocol expectations (funds simply vanish from circulation outside of the sanctioned burn mechanism, and no proposal/committee action can recover them).

### Likelihood Explanation
Reaching this path only requires a `TriggerSmartContract` transaction from any account whose contract issues a `CALL`/`CALLCODE` with `value > 0` to one of the fixed precompile addresses — no special privileges are needed. This can also happen accidentally in existing/legacy contracts that call an address they believe implements payable logic but which actually resolves to a reserved precompile address, or due to input/address confusion bugs in the calling contract.

### Recommendation
In `Program.callToPrecompiledAddress`, reject (revert/return zero) any call to a precompiled contract address that carries a nonzero `endowment`/value, mirroring how EVM implementations typically disallow sending value to precompiles that don't declare themselves payable, or explicitly route such value through the standard burn/blackhole accounting instead of crediting an unspendable address balance.

### Proof of Concept
1. Deploy a contract with a function that performs `precompileAddr.call.value(V)(data)` where `precompileAddr` is one of the fixed addresses returned by `PrecompiledContracts.getContractForAddress` (e.g., `0x...0002` for `sha256`).
2. Trigger this function via `TriggerSmartContract` with `call_value = V`.
3. Observe that `Program.callToPrecompiledAddress` transfers `V` TRX to the precompile address's account balance and the precompile executes normally (e.g., returns the SHA-256 hash), pushing success onto the stack.
4. Query the account balance at the fixed precompile address afterward — it now holds `V` TRX with no transaction path (no known private key, no actuator logic) able to move it out.

  public static void exeCall(Program program, DataWord adjustedCallEnergy,
      DataWord codeAddress, DataWord value, DataWord tokenId, boolean isTokenTransferMsg) {

    DataWord inDataOffs = program.stackPop();
    DataWord inDataSize = program.stackPop();

    DataWord outDataOffs = program.stackPop();
    DataWord outDataSize = program.stackPop();

    program.memoryExpand(outDataOffs, outDataSize);
    int op = program.getCurrentOpIntValue();
    MessageCall msg = new MessageCall(
        op, adjustedCallEnergy, codeAddress, value, inDataOffs, inDataSize,
        outDataOffs, outDataSize, tokenId, isTokenTransferMsg);

    PrecompiledContracts.PrecompiledContract contract =
        PrecompiledContracts.getContractForAddress(codeAddress);
    if (contract != null) {
      if (program.isConstantCall()) {
        contract =  PrecompiledContracts.getOptimizedContractForConstant(contract);
      }
      program.callToPrecompiledAddress(msg, contract);
    } else {
      program.callToAddress(msg);
    }
    program.step();
  }
