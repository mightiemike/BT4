This confirms the guard: `has_stacks_block`/`has_stored_block` checks in `process_next_staging_block` prevent re-execution of `process_matured_miner_rewards`/MARF writes for an `index_block_hash` that was already processed, and each PoX-fork variant of a block gets a *distinct* `index_block_hash` (`consensus_hash` differs), so no shared MARF root can be double-credited.

### Analysis

**Claimed equality:** reward paid to miner (STX balance in MARF) == coinbase+fees earned under the now-revalidated canonical history.

**Trace:** `try_revalidate_sortition` at [1](#0-0)  only calls `SortitionDB::revalidate_snapshot_with_block`, which is a pure sortition-DB metadata update (`pox_valid`, `canonical_stacks_tip_*`, `stacks_block_accepted` columns in the `snapshots` table) at [2](#0-1) . It never touches the chainstate MARF, never calls `process_matured_miner_reward`, and never calls `account_credit`/`credit` on a `STXBalanceSnapshot`.

Actual STX crediting only happens in `process_matured_miner_reward` / `process_matured_miner_rewards` at [3](#0-2) , invoked from `append_block`/`finish_block` during real Stacks-block processing at [4](#0-3) , which is gated by `process_next_staging_block`'s idempotency check: any block whose `index_block_hash` (derived from `consensus_hash` + `block_hash`) is already stored/processed is skipped entirely rather than reprocessed, per [5](#0-4) .

Critically, when a PoX anchor flips, the *consensus_hash* for a given burn height changes (because it's derived from PoX/ops state), so the same Stacks block re-appearing on a different PoX fork gets a different `index_block_hash` and is treated as an entirely distinct MARF trie/ledger state — this is explicitly documented as intentional in `try_replay_stacks_block`/`replay_stacks_blocks` at [6](#0-5)  and [7](#0-6) . There is no shared/mutable MARF state between fork A and fork B that could be double-credited — orphaned-fork rewards are simply inaccessible from the new canonical tip, not "reversed" into a shared ledger.

Maturity/reward computation itself is a pure function of the canonical ancestor chain walked via `get_header_by_coinbase_height`/`get_matured_miner_reward_schedules` at [8](#0-7) , and `find_mature_miner_rewards` at [9](#0-8) , so it is recomputed fresh and correctly for whichever fork is canonical — including in existing regression tests asserting `stx_balance == expected_coinbase + expected_fees` across PoX-history flips (e.g. [10](#0-9) ).

`revalidate_snapshot_with_block`'s `pox_valid=1` write and `Some(false)`/reaccept logic in `process_new_burn_block`'s loop at [11](#0-10)  only flips DB bookkeeping flags to let the coordinator re-walk and re-accept already-computed, distinct-`index_block_hash` blocks — it does not create, duplicate, or re-issue any reward payment.
