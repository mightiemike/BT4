Based on my investigation, I found a strong analog to the reported bug class in `UnDelegateResourceActuator`.

### Title
Null Dereference of Unlock DelegatedResourceCapsule in `UnDelegateResourceActuator.execute()` Causes Valid UnDelegate Transactions to Revert - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
The reported bug pattern is: a validation step accepts a "no bids yet" / default state as valid (using an OR-style existence check), but the execution step unconditionally dereferences a specific record assumed to exist, causing a revert (NPE-equivalent) for otherwise legitimate operations. The same pattern exists in `UnDelegateResourceActuator`.

### Finding Description
`validate()` accepts a transaction as long as **either** the unlocked or the locked `DelegatedResourceCapsule` exists: [1](#0-0) 

However, `execute()` fetches only the **unlock-keyed** capsule (`lock=false`) and immediately calls mutator methods on it inside the resource-type switch, with no null check: [2](#0-1) 

If a user has only a **locked** delegated resource (i.e., `lockResourceCapsule != null` but `unlockResourceCapsule == null`), `validate()` passes because the OR-condition is satisfied. But in `execute()`, `unlockResource` is `null`, and the call `unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0)` (or the ENERGY equivalent) throws a `NullPointerException`. This directly mirrors the reported bug: a default/non-existent state that validation treats as acceptable is dereferenced downstream without a guard, causing a revert of what should be a valid state transition.

By contrast, the TVM-native equivalent (`UnDelegateResourceProcessor`, used by the `unDelegateResource` precompiled/native contract in the VM path) checks for existence only against the same single key used in both validate and execute: [3](#0-2) [4](#0-3) 
so the TVM path does not have this specific validate/execute key mismatch — this confirms the discrepancy is isolated to the classic `UnDelegateResourceActuator` contract-transaction path.

### Impact Explanation
Any account that has delegated resources exclusively under a **locked** delegation (has never had an unlocked delegation to that receiver, e.g. via `DelegateResourceContract` with `lock=true` only) and attempts to submit an `UnDelegateResourceContract` transaction targeting the expired/locked balance will have their transaction pass `validate()` but throw an unhandled `NullPointerException` in `execute()`. Since `execute()` in actuators is invoked from block-processing/`TransactionTrace`, an uncaught `NullPointerException` here is a broken invariant that can disrupt the actuator's exception-handling contract (actuators are expected to only throw checked `ContractExeException`), and legitimately prevents users from ever un-delegating a purely-locked resource through this path — a functional Denial-of-Service on a specific, valid resource-accounting operation.

### Likelihood Explanation
Reaching the locked-only condition requires that `unLockExpireResource()` (called earlier in `execute()`) has not yet migrated the locked resource into the unlock bucket, i.e., the lock period has not expired at the time of unDelegation. Since `DelegateResourceActuator` allows locking resources with a lock period, and `UnDelegateResourceActuator.validate()` explicitly supports the "only locked resource exists" case as valid input (this is why the code differentiates `unlockResourceCapsule` and `lockResourceCapsule` in validate), this is a directly reachable state via two ordinary user transactions (`DelegateResourceContract` with lock=true, followed by `UnDelegateResourceContract`) from any account — no privileged access required.

### Recommendation
In `execute()`, before dereferencing `unlockResource`, check for null and construct a fresh/zeroed `DelegatedResourceCapsule` (mirroring the pattern used in `DelegateResourceActuator.delegateResource()` which does `if (delegatedResourceCapsule == null) { delegatedResourceCapsule = new DelegatedResourceCapsule(...); }`), or otherwise branch execution based on which of the lock/unlock capsules is non-null, matching the logic already present in `validate()`.

### Proof of Concept
1. Account A delegates BANDWIDTH to account B using `DelegateResourceContract` with `lock=true` and a lock period that has not yet expired (creates only the `lock=true`-keyed `DelegatedResourceCapsule`; no `lock=false` capsule is created).
2. Account A submits `UnDelegateResourceContract` for BANDWIDTH targeting B before the lock period ends.
3. `validate()` finds `lockResourceCapsule != null` (and its expire time check may or may not gate it, but the null unlock-capsule branch of the OR-check alone is sufficient to pass validation when the lock capsule satisfies the balance/expire checks) and returns `true`.
4. `execute()` calls `delegatedResourceStore.get(unlockKey)` which returns `null` since no unlock capsule was ever created, then unconditionally calls `unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0)`, throwing a `NullPointerException`.
