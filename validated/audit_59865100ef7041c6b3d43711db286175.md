## Analysis

I found a directly analogous, already-tracked bug class in the nearcore codebase. The CVE describes a size/quota check performed once whose bypass allows an unbounded-size object into the system. The nearcore analog is the receipt-size validation performed once at receipt-creation time, before further mutation (`output_data_receivers` appended, or the promise return value wrapped into a `DataReceipt`) can push the object above the same limit — and the object is accepted anyway further downstream.

### Title
Receipt size limit (`max_receipt_size`) can be bypassed after validation, admitting oversized receipts into the runtime and cross-shard pipeline - (File: runtime/runtime/src/verifier.rs)

### Summary
`validate_receipt` in `runtime/runtime/src/verifier.rs` enforces `max_receipt_size` only for receipts in `ValidateReceiptMode::NewReceipt` mode, computed via `borsh::object_length(receipt)` at the moment of creation. [1](#0-0) 
Subsequent mutation of an already-validated receipt (e.g. `output_data_receivers` being appended by `create_action_receipt` after the receipt object was built, or the return value being wrapped into a `DataReceipt`) can grow it past `max_receipt_size` without re-validation. [2](#0-1) 
The bug is explicitly acknowledged in-code and tracked as `near/nearcore#12606`, with a dedicated `ValidateReceiptMode::ExistingReceipt` variant added specifically to "tolerate" oversized receipts that slip through: [3](#0-2) 
The congestion-control forwarding path also has an explicit workaround clamping the observed size back down to `max_receipt_size` to avoid receipts becoming permanently stuck, again citing the same tracked bug: [4](#0-3) 
Regression tests reproducing the exact defect exist in `test-loop-tests/src/tests/max_receipt_size.rs` (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`), both explicitly commented as reproducing an unresolved bug. [5](#0-4) [6](#0-5) 

### Finding Description
`max_receipt_size` exists specifically to bound the size of any single receipt included in a `ChunkStateWitness`, because the witness's total size must stay under a fixed budget (documented at ~21 MiB total across all component limits). [7](#0-6) 
The check is a classic "quota gate applied once, before the final size is known" pattern — structurally identical to CVE-2021-40524, where Pure-FTPd checked `max_filesize` against a value that could still change (an initial sentinel) before the real upload size was enforced. In nearcore, `validate_receipt` measures `borsh::object_length(receipt)` at the point a receipt is first produced inside `apply_action`, but a contract call can chain a `promise_return` (adding `output_data_receivers` after the sub-receipt's actions were already fixed) or return a value up to `max_receipt_size` in size that is subsequently wrapped as a `DataReceipt`, in both cases growing the serialized receipt beyond the limit *after* the check ran. The size-checking call site is fixed at receipt creation time: [8](#0-7) 
The developers' own workaround comments make clear this is a known, currently-open defect (not a hardened invariant) that lets receipts above `max_receipt_size` circulate through both the local apply loop and the cross-shard forwarding path.

### Impact Explanation
Because `max_receipt_size` is the load-bearing input to the chunk state witness size budget, receipts that silently exceed it can push `ChunkStateWitness` above the size assumptions chunk validators depend on, or interact unpredictably with the congestion-control forwarding logic which has to special-case (clamp) oversized receipts to avoid them getting permanently stuck between shards. [4](#0-3) 
An unprivileged contract deployer/caller can trigger this purely through ordinary `FunctionCall` actions (promise chaining or large value returns) — no privileged or validator-only access is required — reaching a state-transition-relevant limit meant to bound worst-case per-receipt witness/storage overhead. Because the receipt is still accepted and processed rather than rejected, this can result in receipts being forwarded, delayed, or clamped in ways that differ subtly from the size the sender intended, which is the exact "unbounded resource beyond quota" class the CVE describes, applied to a consensus-relevant size limit rather than a filesystem quota.

### Likelihood Explanation
High likelihood of triggering the defect: it requires only deploying/calling a standard contract (already demonstrated in-repo test helpers `max_receipt_size_promise_return_method1` and `max_receipt_size_value_return_method`) and crafting a call whose promise-return or returned value sits at `max_receipt_size`, both fully reachable from an ordinary signed transaction via RPC. This is already reproduced deterministically by first-party tests, indicating it is not a probabilistic or race-dependent condition.

### Recommendation
Re-validate the final serialized size of a receipt (via `borsh::object_length`) after all post-creation mutations are applied — specifically after `output_data_receivers` are attached in `create_action_receipt`/`ReceiptManager`, and after value-return wrapping into a `DataReceipt` — rather than only at the point the action-execution loop first constructs it. Enforce `ReceiptSizeExceeded` as a hard failure at that final point instead of relying on `ValidateReceiptMode::ExistingReceipt`/clamping to tolerate oversized receipts downstream. Track and resolve the referenced upstream issue (`near/nearcore#12606`) rather than continuing to route around it in `try_forward`.

### Proof of Concept
The existing first-party regression test in this repo already demonstrates the bypass end-to-end: [9](#0-8) 
1. Deploy `near_test_contracts::rs_contract()`.
2. Call `max_receipt_size_value_return_method` with `value_size = max_receipt_size` (4,194,304), which returns a value exactly at the limit that is then wrapped into a `DataReceipt`, pushing the actual serialized receipt above `max_receipt_size`.
3. Call `assert_test_completed` to confirm the downstream promise executed (i.e., the oversized receipt was *not* rejected).
4. `assert_oversized_receipt_occurred` walks the chain and confirms a receipt above `max_receipt_size` was actually accepted into the incoming-receipts/receipt-proofs pipeline. [10](#0-9)

```rust
/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
```

```markdown
## State witness size limits

Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 21MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.

The limits are:

* `max_transaction_size = 1.5 MiB`
  * All transactions must be below 1.5 MiB, otherwise they'll be considered invalid and rejected.
  * Previously was 4MiB, now reduced to 1.5MiB
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
```
