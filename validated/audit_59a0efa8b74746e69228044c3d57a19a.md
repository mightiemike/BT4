### Title
Public transaction-intake HTTP/2 endpoint has no per-connection stream/concurrency limits, enabling stream-flood DoS - ([File: crates/apollo_http_server/src/http_server.rs])

### Summary
The public-facing `apollo_http_server` — the entry point that receives `add_transaction` / `add_rpc_transaction` calls from any unauthenticated client — starts its listener via plain `axum::serve(listener, app)` [1](#0-0)  with no HTTP/2-specific hardening (no `max_concurrent_streams`, no per-connection concurrency semaphore, no keepalive/GOAWAY eviction timers). The router only bounds *decompressed/compressed request body bytes* via `RequestBodyLimitLayer` and `RequestDecompressionLayer` [2](#0-1) , and `HttpServerStaticConfig` exposes only `max_request_body_size`, with no stream-count or connection-concurrency knob at all [3](#0-2) .

This is the exact bug class in CVE-2021-32566 (improper validation/limiting of HTTP/2 stream state in Apache Traffic Server leading to DoS), except here the sequencer's own codebase demonstrates it already knows how to fix it: the internal `remote_component_server.rs` explicitly caps `DEFAULT_MAX_STREAMS_PER_CONNECTION = 8`, wraps every accepted connection in a `connection_semaphore` (`DEFAULT_MAX_CONCURRENCY`), and enforces HTTP/2 keepalive ping/timeout eviction of idle/zombie connections [4](#0-3) [5](#0-4) . Those protections are only applied to the internal component-to-component RPC server, not to the externally reachable gateway HTTP server that any transaction sender can hit directly.

### Finding Description
`HttpServer::run` binds a `TcpListener` and calls `serve(listener, app)` from `axum` directly [6](#0-5) . Axum's `serve` uses `hyper_util`'s auto connection builder with default HTTP/2 settings, which does not cap the number of concurrent streams a single connection may open, nor limit the number of concurrent connections/streams the server will service. Only the size of a *single* request body is bounded (`max_request_body_size`, default 5 MiB) [7](#0-6)  — that limit is per-stream, not per-connection or global, so it does nothing to stop a client from opening thousands of streams (each under the byte limit, or even empty) on one or many connections.

By contrast, the sequencer's internal remote server explicitly recognizes and mitigates this exact risk with `max_streams_per_connection`, a global `max_concurrency` semaphore rejecting excess connections with `503`, and HTTP/2 PING-based keepalive eviction of idle/slow connections [8](#0-7) [9](#0-8) . This confirms the team is aware of the bug class but has not applied the same mitigation to the actually public-facing, unauthenticated ingestion path.

### Impact Explanation
An unprivileged remote client (any transaction sender, no special access needed) can open one or a small number of TCP connections to the gateway and, over HTTP/2, open an unbounded number of concurrent streams (each carrying a cheap/garbage or even truncated request). Because there is no `max_concurrent_streams` setting, no connection-level semaphore, and no idle/slow-stream eviction, the server will attempt to allocate resources (task, buffers, gateway-client dispatch) per stream without bound, exhausting memory/CPU/file descriptors and starving legitimate transaction submissions — a network unable to confirm new transactions, which matches the "network unable to confirm new transactions" impact bar.

### Likelihood Explanation
High: the endpoint is reachable by any external actor without authentication (it is the transaction-submission API), requires no privileged role, and the only existing defenses (body-size caps) do not address stream/connection concurrency at all. The pattern is common HTTP/2 DoS tooling (rapid stream open, or "rapid reset" style floods) and the codebase itself demonstrates the maintainers already had to defend the internal server against the identical primitive, showing the attack surface and mitigation are well understood and simply not carried over to the public entry point.

### Recommendation
Apply the same HTTP/2 hardening used in `remote_component_server.rs` to `apollo_http_server`'s listener: use an explicit `hyper_util`/`hyper` server builder (or an axum/hyper wrapper) that sets a bounded `max_concurrent_streams` per connection, wrap accepted connections in a global concurrency semaphore that rejects excess connections (e.g., with `503`), and configure HTTP/2 keepalive ping interval/timeout to evict idle or unresponsive connections, mirroring `DEFAULT_MAX_STREAMS_PER_CONNECTION`, `DEFAULT_MAX_CONCURRENCY`, `DEFAULT_KEEPALIVE_INTERVAL_MS`, and `DEFAULT_KEEPALIVE_TIMEOUT_MS` already used internally [10](#0-9) . Add corresponding fields to `HttpServerStaticConfig` so these limits are configurable and validated like `max_request_body_size` is today [3](#0-2) .

### Proof of Concept
1. Start `apollo_http_server` with default config (`HttpServerStaticConfig::default()`), which sets no stream/connection concurrency bounds [11](#0-10) .
2. From a single unprivileged client, open an HTTP/2 connection to the gateway `add_transaction`/`add_rpc_transaction` endpoints and issue a very large number of concurrent streams (e.g., thousands), each with minimal/garbage payload under the 5 MiB body cap.
3. Because `serve(listener, app)` [12](#0-11)  applies no `max_concurrent_streams` and no connection-level admission control (unlike `remote_component_server_handler`'s semaphore-guarded design [13](#0-12) ), the server accepts and attempts to process all streams simultaneously, exhausting server resources and degrading/denying service to legitimate transaction submitters.

const DEFAULT_KEEPALIVE_INTERVAL_MS: u64 = 30_000;
const DEFAULT_KEEPALIVE_TIMEOUT_MS: u64 = 10_000;
// Number of unanswered TCP keepalive probes before the OS declares the connection dead.
// 3 probes × keepalive_interval gives a ~90 s probe window at the default interval.
const TCP_KEEPALIVE_RETRIES: u32 = 3;

macro_rules! serve_connection {
    (
        $io:expr,
        $service:expr,
        $max_streams:expr,
        $keepalive_interval:expr,
        $keepalive_timeout:expr
    ) => {
        let result = ServerBuilder::new(TokioExecutor::new())
            .http2()
            .timer(TokioTimer::new())
            .max_concurrent_streams($max_streams)
            .keep_alive_interval($keepalive_interval)
            .keep_alive_timeout($keepalive_timeout)
            .serve_connection($io, $service)
            .await;

        if let Err(e) = result {
            error!("Remote component server start error: {e}");
        }
    };
}
