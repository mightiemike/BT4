### Title
Missing HTTP header/idle-timeout configuration in Jetty-based API servers enables Slowloris-style DoS - (File: framework/src/main/java/org/tron/common/application/HttpService.java)

### Summary
`HttpService.initServer()` constructs the Jetty `Server` with the bare convenience constructor `new Server(this.port)` and never configures an explicit connector timeout (e.g., `ServerConnector#setIdleTimeout`, `HttpConfiguration` header-read limits). The only protective mechanism wired in is `ConnectionLimit`, which is optional and only activated when the operator explicitly sets `node.maxHttpConnectNumber > 0`. This mirrors the reported Slowloris bug class (missing `ReadHeaderTimeout`) in the original report.

### Finding Description
`initServer()` builds the underlying Jetty server for every HTTP-based API service (FullNode HTTP API on 8090, Solidity HTTP API on 8091, PBFT HTTP API on 8092, and the JSON-RPC HTTP services) using: [1](#0-0) 

No `ServerConnector` with an explicit idle timeout is created, and no header-read timeout / `HttpConfiguration` is attached. Jetty's connection idle timeout only resets on *any* I/O activity on the socket — a classic Slowloris client that trickles a byte every few seconds keeps resetting the idle timer indefinitely without ever completing the HTTP request headers, so it is not equivalent to a bounded "time to receive complete headers" guard (which is what `ReadHeaderTimeout` provides in Go's `net/http`). The only bound on concurrent connections is `ConnectionLimit`, added in the same method: [2](#0-1) 
but this is gated behind the `maxHttpConnectNumber` config value, which defaults to being unset/disabled unless the node operator explicitly configures it. The size-limiting handler (`SizeLimitHandler`) added in `initContextHandler()` only bounds the *body size* once a request is dispatched — it does nothing for an attacker who never finishes sending the header block, because Jetty (and the servlet container) won't dispatch the request to any handler until the request line/headers are fully parsed: [3](#0-2) 

This applies to every concrete subclass of `HttpService` (e.g. `FullNodeJsonRpcHttpService`), since none override `initServer()`: [4](#0-3) 

### Impact Explanation
An unauthenticated attacker can open many TCP connections to a FullNode's HTTP/JSON-RPC ports (8090/8091/8092 or the JSON-RPC ports) and send partial HTTP request headers slowly (a few bytes periodically), keeping each connection open and consuming a server-side connection/thread slot without ever completing the header parse. Because there is no header-completion timeout and connection limiting is opt-in/disabled by default, an attacker can exhaust Jetty's connector thread pool / connection resources, denying legitimate API access (public FullNode HTTP/JSON-RPC API, used by wallets, exchanges, and dApps to interact with the chain). This is a resource-exhaustion DoS against a public-facing, unprivileged-reachable service — consistent with the "underpriced-public-work"/availability impact bucket the validation rules call out.

### Likelihood Explanation
The HTTP/JSON-RPC endpoints are commonly exposed publicly by FullNodes (default ports 8090/8091/8092 and JSON-RPC ports), require no authentication, and the missing timeout is unconditional (default configuration) unless an operator manually sets `maxHttpConnectNumber`. Executing a Slowloris attack requires only a handful of long-lived sockets and minimal bandwidth, making this a low-cost, high-likelihood attack against any node that exposes these ports without additional reverse-proxy protection.

### Recommendation
Explicitly configure the Jetty connector with a bounded idle/header timeout instead of relying on `new Server(this.port)` defaults, e.g. build a `ServerConnector` with `HttpConfiguration` and call `setIdleTimeout(...)` on it before adding it to the `Server`, and/or enable `ConnectionLimit` by default with a sane non-zero value rather than leaving it disabled unless manually configured, in `HttpService.initServer()`.

### Proof of Concept
1. Start a FullNode with default config (`maxHttpConnectNumber` unset).
2. From an attacker host, open N TCP connections to the node's HTTP API port (e.g., 8090) and, for each, send an incomplete HTTP request line/header (e.g., `GET / HTTP/1.1\r\nHost: x\r\n`) followed by periodic single-byte writes every ~10–20 seconds, never sending the terminating `\r\n\r\n`.
3. Observe that these connections remain open indefinitely (bounded only by Jetty's default idle timeout reset on each trickle byte), consuming connector resources; with enough concurrent slow connections, legitimate requests to the same API port are refused or delayed, demonstrating denial of service.

*(Note: exact default Jetty idle-timeout value and whether the packaged Jetty version applies any implicit low-level timeout could not be fully confirmed from the indexed source alone — the `build.gradle` only records the dependency reference, not runtime defaults, so this should be verified by a live PoC run against a built node.)*
