## Title
Starknet OS `execute_replace_class` Skips Declaration/Version Validation Present in Blockifier, Causing State-Root Divergence - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
Any unprivileged contract can invoke the `replace_class` syscall with an arbitrary, possibly undeclared or non-Cairo1 class hash. The Rust `blockifier` execution engine validates this input — it rejects the call unless the target class hash is declared and is a Cairo1 class — but the Starknet OS Cairo re-implementation of the same syscall performs none of these checks before unconditionally committing the new class hash into `contract_state_changes`. This mirrors the JumpServer analog: a state-changing "replace/overwrite" operation is executed on a caller-supplied identifier without re-validating it against the constraints enforced elsewhere in the system, letting an invalid overwrite slip through the path that ultimately determines the committed/proven state.

### Finding Description
The blockifier's real syscall implementation enforces two checks before allowing `replace_class`: [1](#0-0) 

```rust
pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
    // Ensure the class is declared (by reading it), and of type V1.
    let compiled_class = self.state.get_compiled_class(class_hash)?;
    if !is_cairo1(&compiled_class) {
        return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
    }
    self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
    Ok(())
}
```

This is confirmed by tests that assert both the "undeclared" and "Cairo0 class hash" cases are rejected: [2](#0-1) 

However, the Starknet OS's own Cairo implementation of the identical syscall — used to independently re-derive/prove the state transition — omits both checks and explicitly flags this as a known TODO: [3](#0-2) 


The same gap exists in the legacy/deprecated OS execution path: [4](#0-3) 

Neither Cairo implementation calls anything equivalent to `get_compiled_class` (to require the class hash be declared) nor `is_cairo1` (to require the target be a Cairo1 class). The OS unconditionally overwrites the contract's `state_entry.class_hash` in `contract_state_changes`, which directly feeds the Patricia-tree state commitment computed by the OS.

### Impact Explanation
Because the OS is the component that independently re-executes every transaction to derive the state diff that gets committed/proven (it cannot simply trust hints for syscall success/failure without breaking soundness), a transaction that calls `replace_class_syscall` with an undeclared or Cairo0 class hash will:
- **Revert** when executed by the real `blockifier` (the engine actually used to build the block and by all full nodes/honest sequencers), producing no class-hash change and a reverted receipt.
- **Succeed** when re-executed by the Starknet OS, because its `execute_replace_class` has no equivalent validation and blindly commits the attacker-chosen (possibly undeclared) class hash.

This is a genuine honest-node divergence for a transaction submitted by an ordinary, unprivileged account — the same transaction produces two different outcomes depending on which correctness-critical component evaluates it. The consequences map directly to accepted impact categories:
- **Wrong committed root**: if the OS's incorrect (successful) outcome is what gets committed/proven, the committed state root will not match the state that full nodes running `blockifier` compute, breaking state-root/state-diff consistency for the network.
- **Permanent freezing of funds**: if the class-hash overwrite is allowed to succeed with an undeclared/incompatible class hash, the target contract's compiled class becomes unresolvable, permanently bricking any subsequent calls to (and funds held by) that contract.
- **Network unable to confirm new transactions**: if the mismatch instead manifests as a proof-generation failure (OS output disagreeing with the block's actual state diff), the affected block cannot be proven, halting L2 finality.

### Likelihood Explanation
The trigger is trivial and requires no special privilege: any account or contract can issue an `INVOKE` transaction that calls `replace_class_syscall(class_hash)` (or the deprecated `replace_class` syscall) with a class hash that is undeclared or is a Cairo0 class. This is a single, ordinary transaction from an unprivileged sender — no coordination with a sequencer/operator is needed to trigger the divergence, since the divergence arises purely from the OS's re-execution logic differing from blockifier's, both of which process the exact same transaction submitted honestly.

### Recommendation
Add the same validation to `execute_replace_class` in both `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo` that exists in `syscall_base.rs::replace_class`:
1. Verify the target `class_hash` corresponds to a declared class (read `contract_class_changes` / class commitment and fail if absent, mirroring `get_compiled_class`).
2. Verify the declared class is a Cairo1 class before allowing the replacement (mirroring `is_cairo1`), rejecting replacement with Cairo0 (V0) class hashes.
Resolve the outstanding `TODO(Yoni, 1/1/2026)` comment as part of this fix so that OS re-execution results match blockifier's revert/accept decisions for every `replace_class` invocation.

### Proof of Concept
1. Deploy an account/contract with a Cairo1 class that exposes `replace_class_syscall`.
2. Submit an `INVOKE` transaction from this contract calling `replace_class_syscall(class_hash=X)` where `X` is a class hash that has never been declared (or is a Cairo0 class hash).
3. Observe that `blockifier` (real block execution) reverts this call per the checks in [1](#0-0) , leaving `address_to_class_hash` unchanged for the contract.
4. Feed the identical transaction/trace to the Starknet OS re-execution (`execute_replace_class` in `syscall_impls.cairo`): because the declared/Cairo1 checks are absent (per the TODO at line 902), the OS commits `class_hash=X` into `contract_state_changes` for the contract, unconditionally succeeding.
5. Compare the two computed state diffs/roots for the same block/transaction: they differ, demonstrating the divergence.

```text
        // Not enough gas to execute the syscall.
        return ();
```
