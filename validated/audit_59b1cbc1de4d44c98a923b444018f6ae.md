### Title
Hardcoded `paid_fee_on_l1` in consensus transaction conversion nullifies L1 handler fee-payment check - ([File: crates/apollo_transaction_converter/src/transaction_converter.rs])

### Summary
The `L1HandlerTransaction`'s `paid_fee_on_l1` field is the one "variable parameter" that Blockifier is supposed to validate before executing an L1-to-L2 message (`if paid_fee == Fee(0) => reject`). However, the wire/consensus representation of an L1 handler transaction (`starknet_api::transaction::L1HandlerTransaction`) does not carry this field at all, and when a node reconstructs an executable transaction from a transaction it received over the consensus/p2p path, it substitutes a hardcoded dummy value (`Fee(1)`) instead of the real fee that was actually paid on L1. This is directly analogous to the reported bug class: a variable, attacker/L1-sender-influenced parameter that flows into the calldata/transaction is not actually verified along one code path, and downstream fee-related logic accepts a placeholder value that trivially satisfies the check, silently bypassing the intended fee-enforcement invariant.

### Finding Description
`blockifier`'s only fee-related gate for L1 handler transactions is: [1](#0-0) 

which only requires `paid_fee_on_l1 != Fee(0)`; the comment there even states "For now, assert only that any amount of fee was paid... covered by the starknet core contract."

The `paid_fee_on_l1` value is set correctly when a node ingests the message directly from L1 events: [2](#0-1) 
and in `papyrus_base_layer::eth_events::parse_event`, which decodes the real `fee` field from the `LogMessageToL2` Ethereum event.

However, `starknet_api::executable_transaction::L1HandlerTransaction` is the only transaction type that carries `paid_fee_on_l1`: [3](#0-2) 
while the plain, network-transmitted `crate::transaction::L1HandlerTransaction` type has no such field. When a node reconstructs an executable L1 handler transaction from a transaction obtained via the consensus/p2p flow (as opposed to directly scraping the L1 event), it cannot recover the real fee and instead hardcodes it: [4](#0-3) 

The `// TODO(Gilad): Change this once we put real value in paid_fee_on_l1.` comment confirms this is an acknowledged placeholder, not an intentional design choice.

The practical effect is that any node validating/re-executing an L1 handler transaction through this consensus conversion path will always see `paid_fee_on_l1 = Fee(1)`, regardless of what the L1 sender actually paid. The only check in the system (`paid_fee == Fee(0)` in `l1_handler_transaction.rs`) can therefore never trigger for that node, making the fee-payment sanity check a permanent no-op along this path.

### Impact Explanation
The `InsufficientFee` check is the only place in the sequencer's execution path that ties an L1-originated transaction's admissibility to the fee the L1 sender actually paid. Silently replacing the real value with a constant that always passes means:
- A transaction that should be rejected (or produce a hard execution error / different receipt) because the L1 sender paid `Fee(0)` will instead be accepted and executed to completion by any node that reconstructs the transaction via the consensus-transmitted representation instead of directly from the L1 event.
- Because the failing branch in `execute_raw` returns a hard `Err(TransactionExecutionError::TransactionFeeError(...))` rather than a normal `revert_error`-bearing `Ok`, a discrepancy between a node that evaluates the real fee (e.g., one that pulled the tx straight from L1 events) and one that evaluates the hardcoded `Fee(1)` (consensus-reconstructed) can produce different execution outcomes/state diffs for the same transaction — a correctness/consistency issue in state computation that is not gated by any privileged actor; it is purely a function of what an ordinary L1 message sender submits on L1 (paying zero or near-zero fee).

### Likelihood Explanation
Any unprivileged L1 message sender can trigger this by calling the Starknet core contract's `sendMessageToL2` with an arbitrarily low (including zero, if the core contract does not itself enforce a minimum) `msg.value`. The only place that would have flagged this transaction is the check in `l1_handler_transaction.rs`, and the hardcoded-substitution bug on the consensus/validator conversion path defeats that check for any code path that goes through `convert_consensus_l1_handler_to_internal_l1_handler`.

### Recommendation
Include `paid_fee_on_l1` as part of the transaction representation that is actually propagated end-to-end (consensus/p2p wire format, or committed alongside the transaction hash), rather than reconstructing it from a hardcoded placeholder. Alternatively, if the fee check is genuinely meant to be enforced only by the L1 core contract and is redundant on L2, remove the dead/misleading `paid_fee_on_l1 == Fee(0)` check and the associated `TransactionFeeError::InsufficientFee` machinery entirely, so there is no illusion of an L2-side fee validation that can silently diverge between code paths.

### Proof of Concept
1. An L1 message sender calls the Starknet core contract's `sendMessageToL2` with `msg.value = 0` (or a value not enforced as non-zero by the core contract), producing a `LogMessageToL2` event with `fee = 0`.
2. A node that ingests this event directly (e.g., via `apollo_l1_events`/`papyrus_base_layer::eth_events::parse_event`) constructs an `executable_transaction::L1HandlerTransaction` with `paid_fee_on_l1 = Fee(0)`, and `execute_raw` in `l1_handler_transaction.rs` returns `Err(TransactionFeeError::InsufficientFee)`.
3. A different node, or the same node validating the transaction via the consensus/p2p flow, calls `TransactionConverter::convert_consensus_l1_handler_to_internal_l1_handler`, which discards the real fee and hardcodes `paid_fee_on_l1 = Fee(1)` (crates/apollo_transaction_converter/src/transaction_converter.rs:473-483). For this node, the `paid_fee == Fee(0)` check in `execute_raw` never triggers, and the transaction executes normally instead of failing.
4. This produces divergent treatment of the identical L1-originated transaction depending solely on which internal code path constructed the executable transaction — a correctness bug directly rooted in an unvalidated/placeholder "variable parameter" (`paid_fee_on_l1`), matching the bug class described in the external report.

**Uncertainty note:** I was not able to fully trace whether the batcher's block-proposal path (as opposed to the consensus-validation path) uses the real fee value or also goes through a hardcoded substitution, nor confirm whether the Starknet L1 core contract enforces any minimum non-zero `msg.value` for `sendMessageToL2`. Both facts affect whether this divergence is actually reachable in a live network versus being latent/dead code guarded by other invariants. Given the index's scope limits, I could not verify these additional call sites with full certainty; a Devin session with full repository access would be needed to confirm the exact proposer-side code path and any L1-contract-level constraints.
