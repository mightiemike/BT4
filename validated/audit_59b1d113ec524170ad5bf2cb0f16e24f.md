## Finding

### Title
`TransactionOutput::ensure_match_transaction_info` never checks `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, silently blinding replay-verify and backup-restore verification to state-root divergence - (File: `types/src/transaction/mod.rs`)

### Summary
The external Zetachain bug boils down to one invariant: *a component that decides "this execution result is authentic" must check every field that participates in the authenticated commitment, not just a subset.* The Solana observer skipped the "did this transaction actually succeed" check. The Aptos analog is `TransactionOutput::ensure_match_transaction_info`, the function used by replay/restore verification tooling to decide whether a locally re-executed transaction matches the authenticated `TransactionInfo` recorded in the accumulator. It checks status, gas, write-set hash, and event-root hash, but explicitly skips the state-checkpoint hash fields, which are exactly the fields that encode the Merkle *state* root committed on-chain.

### Finding Description
`ensure_match_transaction_info` compares a freshly computed `TransactionOutput` against the authenticated `TransactionInfo`: [1](#0-0) 

It verifies `status`, `gas_used`, `write_set` hash (`state_change_hash`) and `event_root_hash`, but the code contains an explicit acknowledgment that it does **not** verify `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`: [2](#0-1) 

These checkpoint hashes are the actual Jellyfish-Merkle **state root** values committed into `TransactionInfo` at checkpoint boundaries, and are produced by `DoStateCheckpoint::run`/`get_state_checkpoint_hashes`, which is the code path that legitimately reconciles a locally computed root against a "known" target root when one is supplied: [3](#0-2) 

That real state-root reconciliation only happens inside the normal (consensus / execute-based state-sync) pipeline, where `known_state_checkpoints` is threaded through from the authenticated `TransactionInfo`. It is a *different* mechanism from `ensure_match_transaction_info`.

`ensure_match_transaction_info` (the comparator missing the state-root check) is the one actually used by:
1. Backup-restore's execution-verification path, `ChunkExecutorInner::verify_execution`, invoked when replaying a backup with `VerifyExecutionMode::should_verify()` (e.g. `--verify-execution` during `db-restore`): [4](#0-3) 
and its caller which drives the skip/verify decision during restore replay: [5](#0-4) 
2. `db-tool`'s `replay_on_archive`, the tool used to continuously replay historical mainnet transactions against an archive and detect non-determinism / hard-fork bugs: [6](#0-5) 
3. The CLI's transaction replay/debug command: [7](#0-6) 

In all three, the actual data committed to the restoring/replaying database still comes from the backup's already proof-verified `write_sets`/`transaction_infos` (verified via `TransactionListWithProofV2::verify`, which is itself correct and does bind hashes to the ledger-info-signed accumulator root). So this gap does not let an attacker force *wrong bytes* into storage through these three paths. What it does break is the safety net whose entire purpose is to catch state-root divergence: `state_checkpoint_hash` is derived from the *cumulative* state tree (all prior writes), not just this transaction's own write set, so a subtle non-determinism/state-tree bug (the classic cause of an accidental hard fork) can leave the write-set/event/gas/status of an individual transaction looking identical while the actual state root diverges — and `ensure_match_transaction_info` will report "match" regardless, because that field is never compared.

### Impact Explanation
This does not let anyone corrupt currently-committed mainnet state in the paths examined, because the checkpoint-hash reconciliation via `known_state_checkpoints` in `do_state_checkpoint.rs` is what protects the actual execution-based chunk-processing/state-sync path, and the raw output-apply path is protected by `TransactionOutputListWithProofV2::verify`'s ledger-info-bound proof. The concrete, provable weakness is narrower: the replay-verify/backup-restore verification tooling — whose specific job is to detect exactly this class of divergence (state-root/hard-fork bugs) during backup restoration (`--verify-execution`) and continuous archive replay auditing — silently ignores the state-root fields of `TransactionInfo`. This degrades the tooling's ability to detect a real state-commitment integrity break (the very "hard-fork-only divergence during commit, replay, restore" class called out as in-scope), rather than causing state divergence itself.

### Likelihood Explanation
The gap is unconditional in the code today (not gated behind an unimplemented feature check at the code level — the `state_checkpoint_hash` field is always populated and always skipped by this comparator; only the trading-native/hot-state fields are additionally noted as feature-gated). It is exercised whenever an operator runs `db-restore --verify-execution` or `db-tool replay-on-archive`, or `aptos move replay` — all normal operational tooling, no privileged access required to trigger the missing check, only to observe its failure to flag an actual divergence should one occur (e.g., during a hard-fork-class bug).

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` (and its call sites in `verify_execution`, `replay_on_archive::execute_and_verify`, and the CLI replay path) to also compare the recomputed state-checkpoint hash(es) against `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` whenever a checkpoint occurs at that version, mirroring the reconciliation already done in `DoStateCheckpoint::get_state_checkpoint_hashes`, before any feature relying on these fields (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled on mainnet.

### Proof of Concept
Not applicable as a runtime exploit against consensus state — the demonstration is code-level: trace `ensure_match_transaction_info`'s field list (status/gas/write-set-hash/event-root-hash only) versus `TransactionInfo`'s full field set (which additionally includes `state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`), and its three call sites in `chunk_executor/mod.rs`, `replay_on_archive.rs`, and `cli/src/commands.rs`, none of which supply or check those additional fields.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
