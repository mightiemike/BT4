### Title
Receipt size hard limit is enforced only at receipt-creation time, letting `output_data_receivers` grow past `max_receipt_size` after validation - (File: `runtime/runtime/src/receipt_manager.rs`)

### Summary
The Discourse advisory describes a message serializer that used an already-expanded list of recipients (`@all`/`@here`) that could grow unboundedly *after* the point the message was considered validated/sized, producing an oversized payload. Nearcore has a structurally analogous defect: an action receipt's `output_data_receivers: Vec<DataReceiver>` list is mutated by later, independent host-function calls (`promise_then`/`promise_batch_then`, implemented via `ReceiptManager::create_action_receipt`) *after* the receipt has already been size-validated and prepared for output, so the hard cap `max_receipt_size` can be silently exceeded. This is a known, still-present defect in this tree (tracked upstream as near/nearcore#12606) with only a symptom-level mitigation (tolerate on the read/apply side) rather than a fix of the root cause (validate-before-mutate ordering).

### Finding Description
`ReceiptManager::create_action_receipt` (`runtime/runtime/src/receipt_manager.rs:112-138`) is called whenever a contract chains a promise (`promise_then`/`promise_batch_then`). For every dependency it declares, it reaches back into an *already created* predecessor receipt and pushes a new `DataReceiver` onto that receipt's `output_data_receivers`: [1](#0-0) 

Because a single receipt can be the dependency of multiple, unrelated later `.then()` calls issued from different receipts/execution contexts, its `output_data_receivers` list keeps growing over the lifetime of the DAG of promises a transaction (or chain of receipts) constructs, well after that receipt's own size was checked at creation.

The size limit itself is enforced by `validate_receipt`, but only in `ValidateReceiptMode::NewReceipt` mode: [2](#0-1) 

The `ExistingReceipt` mode variant explicitly documents that it must tolerate receipts that violate the size limit because of this exact class of bug: [3](#0-2) 

The project's own state-witness size-limit documentation states the limit is supposed to be a hard invariant ("All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected... Previously there was no limit on receipt size."): [4](#0-3) 

And there is an explicit regression test in this tree that reproduces the scenario and documents that it is a known-unfixed bug (linking to `near/nearcore#12606`): a function call receipt is created at exactly `max_receipt_size`, passes validation, and is later mutated by `output_data_receivers` from a downstream `promise_return`, growing it past the hard limit: [5](#0-4) [6](#0-5) 

The mitigation added is purely defensive at the *consumption* side (making `ExistingReceipt` mode tolerant so the runtime doesn't crash / halt) — it does not prevent the receipt from being produced, gossiped, or embedded oversized in `ChunkStateWitness.source_receipt_proofs` / outgoing receipt proofs, both of which this same document says are supposed to be bounded specifically to keep total witness size under ~21 MiB: [7](#0-6) 

### Impact Explanation
An unprivileged contract deployer/caller can, through nothing more than chained cross-contract calls (`promise_then`) targeting one already-created receipt from multiple different call sites (e.g., in a "fan-in" DAG), grow a single outgoing receipt past the protocol's `max_receipt_size` hard cap without triggering the `NewReceipt` validation path that is supposed to reject it. Consequences reachable from this:
- The oversized receipt is not rejected at creation (only `NewReceipt` mode checks size; the mutation happens after that check).
- Because size limits on receipts are the mechanism relied on to bound `ChunkStateWitness` total size (per `docs/misc/state_witness_size_limits.md`) and outgoing/receipt-proof size limits (`outgoing_receipts_usual_size_limit`/`outgoing_receipts_big_size_limit`), an oversized receipt undermines the invariant those limits are built on, risking oversized witnesses, congestion-accounting/compute-cost mis-estimation (since congestion gas and proof-size accounting assume receipts are within the validated bound), or divergent handling between honest nodes if any code path (besides the `ExistingReceipt` tolerance already patched in) still assumes the hard cap holds.
- `ExistingReceipt` mode is explicitly less strict and used for older/already-produced receipts — meaning this is a state-transition-affecting condition (receipts must be handled identically by every node reprocessing them), so any residual code path that still enforces strict size checks on "existing" receipts (e.g., in state-witness assembly/validation, congestion control, or cross-shard receipt-proof serialization) rather than routing through the tolerant `ExistingReceipt` path could reject the chunk on some nodes and accept it on others — a state-root/consensus divergence risk. This is exactly the class of high-severity issue the rules require (state-root divergence / invalid state-transition acceptance), not merely a resource/DoS concern.

### Likelihood Explanation
High, in the sense that the code path is fully triggerable by any account that can deploy and call a WASM contract on any shard, using only the standard `promise_then`/`promise_batch_then` promise APIs — no special privileges, no validator/network position required. The nearcore team itself has already written a regression test that reproduces this exact construction (`test_max_receipt_size_promise_return`) and references it as a currently-open bug (`near/nearcore#12606`), confirming it is both reachable and unresolved at the root-cause level in this tree.

### Recommendation
- Re-validate (or clamp) `max_receipt_size` immediately after any mutation to `output_data_receivers`/other post-creation fields in `ReceiptManager::create_action_receipt`, rather than only checking size once at receipt-conversion time.
- Alternatively, bound the number of times a receipt can be referenced as an `input_data_ids` dependency (i.e., cap growth of `output_data_receivers` per receipt) at creation time so the worst-case receipt size after all possible later mutations is still provably ≤ `max_receipt_size`.
- Audit every downstream consumer of receipts that currently assumes `ReceiptValidationError::ReceiptSizeExceeded` can't happen for "existing" receipts (state-witness assembly, congestion accounting, receipt-proof size accounting) to confirm none of them enforce a hard reject that could diverge between nodes; if any do, migrate them to the same tolerant handling as `ValidateReceiptMode::ExistingReceipt`, or better, eliminate the divergence risk entirely by fixing the root cause above.

### Proof of Concept
The nearcore repository already contains a working, minimal PoC for this exact defect: [8](#0-7) 
It: (1) deploys a contract, (2) has the contract create a promise DAG `A -then-> B`, where executing `A` creates a new promise `C` and calls `promise_return`, changing the DAG to `C -then-> B`; the receipt for `C` is built to be exactly `max_receipt_size` bytes; (3) the later attachment of `output_data_receivers` (routing `C`'s output to `B`) pushes `C`'s serialized size above `max_receipt_size` after the size check has already passed, and (4) `assert_oversized_receipt_occurred` confirms an incoming receipt above `max_receipt_size` is present in the chain, exactly reproducing the analog of the Discourse "unbounded list computed/validated once, then grown past the intended bound" bug class.

```rust
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }
```

```markdown
## State witness size limits

Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 21MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.

The limits are:

* `max_transaction_size = 1.5 MiB`
  * All transactions must be below 1.5 MiB, otherwise they'll be considered invalid and rejected.
  * Previously was 4MiB, now reduced to 1.5MiB
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
```

```rust
/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}
```
