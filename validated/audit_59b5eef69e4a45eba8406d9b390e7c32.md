I found a solid state-integrity analog: the comparator function used by replay-verify tooling to check whether locally-computed execution results match the authenticated on-chain `TransactionInfo` deliberately skips checkpoint-hash comparison, which is the same "single validated input, multiple actually-relevant signals" pattern as the Peggo bug (one authoritative field checked while other trust-critical fields are silently ignored).

### Title
Replay-verify comparator skips state/position checkpoint-hash validation, allowing corrupted state roots to pass verification - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole function used by db-tool's replay-verify (`replay_on_archive.rs`) and `aptos-debugger` to confirm that a node's locally re-executed transaction output matches the ledger's accumulator-authenticated `TransactionInfo`. It validates status, gas used, write-set hash, and event root hash, but explicitly and admittedly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` [1](#0-0) .

### Finding Description
`TransactionInfoV1` (and V0) carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields, which are the authenticated Sparse-Merkle/JMT and position-tree roots committed to the transaction accumulator and thus indirectly signed by validators via the `LedgerInfo` [2](#0-1) . These roots are what state-sync bootstrapping, restore tooling and light-client proof verification treat as ground truth for the state tree at a given version — e.g. `bootstrapper.rs`'s `expected_snapshot_root` reads exactly these fields from the target `TransactionInfo` as the values state-sync must reproduce [3](#0-2) .

However, `ensure_match_transaction_info` — the only function that cross-checks a freshly-computed `TransactionOutput` against a trusted `TransactionInfo` during replay — never compares these checkpoint hashes at all. The code contains its own acknowledgment of the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution.
``` [4](#0-3) 

This function is invoked by `replay_on_archive.rs`'s `execute_and_verify`, which re-executes transactions from archive and calls `ensure_match_transaction_info` per transaction to decide pass/fail for the replay-verify job [5](#0-4) . Because write-set hash equality (`state_change_hash`) is checked but the resulting state-tree root is not, two situations are indistinguishable to this tool: (1) correct execution whose state root matches the ledger, and (2) execution whose write set serializes to the same `state_change_hash` bytes but whose downstream state-tree/Jellyfish-Merkle root computation (or the newer native-position tree, guarded by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature [6](#0-5) ) diverges from what was actually committed/authenticated. Note write_set hash equality does not imply state root equality if storage/executor bugs corrupt how writes are applied into the SMT/JMT or the position tree.

### Impact Explanation
Replay-verify (and `aptos-debugger`, which shares the same comparator) is the primary detection mechanism operators and auditors use to catch state divergence/corruption between archived history and re-execution — effectively an offline integrity check for "did the committed ledger state match correct VM execution." By omitting checkpoint-hash validation, this tool can report a clean pass even though the authenticated state/position root differs from what local execution actually produces, silently masking a state-commitment bug (e.g. in the new native-position/trading state root logic gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO`). This is exactly the "hard-fork-only divergence during commit, replay ... or proof verification" category and an "authenticated API/state-view output bound to the wrong ... proof context," since the verifier accepts a proof context (checkpoint hash) it never actually checks.

### Likelihood Explanation
This isn't a remote/attacker-triggered exploit in the traditional sense — it requires an underlying state-computation divergence to exist (e.g., a bug in the new position/trading-native state root logic, or storage handoff issue) for the gap to matter. But given the code's own comment flags this as a known, real risk tied to the newly introduced `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature (an in-progress feature per the feature flag docs), and that this comparator is the load-bearing safety net specifically meant to catch such divergence, the likelihood of the gap mattering rises directly with the rollout of that feature.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on either side) against values recomputed from local execution/checkpoint output, failing verification on mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled on mainnet.

### Proof of Concept
Not directly exploitable by an external attacker without a pre-existing state-root computation bug; the PoC is the code path itself: run `db-tool replay-on-archive` (or `aptos-debugger`) against a chunk whose `TransactionInfo.state_checkpoint_hash`/`position_state_checkpoint_hash` do not match what local re-execution's `DoStateCheckpoint`/position-tree logic would produce (holding `write_set`/`state_change_hash` and events constant) — `ensure_match_transaction_info` returns `Ok(())` and the replay is reported as verified [7](#0-6) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
