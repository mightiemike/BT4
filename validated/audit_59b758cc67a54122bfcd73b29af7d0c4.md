### Title
Reachable Rust panic (`.expect()` on unset Secp segment) when a contract calls `secp256k1_add`/`secp256k1_mul`/`secp256r1_add`/`secp256r1_mul` syscalls without a prior `secp*_new`/`secp*_get_point_from_x` call - (File: crates/blockifier/src/execution/syscalls/syscall_executor.rs)

### Summary
The default `SyscallExecutor` trait implementations for `secp256k1_add`, `secp256k1_mul`, `secp256r1_add`, and `secp256r1_mul` unconditionally call `.expect("Secp segment must be set.")` on `optional_secp_segment_base` *before* any point validation happens. This field (`secp_points_segment_base`) is only initialized (`Some(...)`) lazily, the first time `allocate_point` runs inside `secp_new` or `secp_get_point_from_x`. If a contract's Cairo code invokes an "add"/"mul" secp syscall as the very first secp-related syscall in its execution (i.e., without ever calling the corresponding "new"/"get_point_from_x" syscall first), the segment base is still `None`, and the `.expect()` unwraps `None`, causing a Rust panic.

### Finding Description
`secp256k1_add`/`secp256k1_mul`/`secp256r1_add`/`secp256r1_mul` are default trait methods in `SyscallExecutor` (crates/blockifier/src/execution/syscalls/syscall_executor.rs): [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

Each of these calls `optional_secp_segment_base.expect("Secp segment must be set.")` *before* delegating to `SecpHintProcessor::secp_add`/`secp_mul`, which is where point-existence validation (`get_point_by_ptr`) actually happens: [5](#0-4) 

The `secp_points_segment_base: Option<Relocatable>` field is only populated inside `allocate_point`, which is reached solely via `secp_new` or `secp_get_point_from_x`: [6](#0-5) 

Because the "add"/"mul" wrappers `.expect()` the segment base *before* the inner function ever checks whether the requested points exist, a contract that invokes `secp256k1_add_syscall`/`secp256k1_mul_syscall`/`secp256r1_add_syscall`/`secp256r1_mul_syscall` as its first secp operation - never having called `secp256k1_new_syscall`, `secp256r1_new_syscall`, or the `get_point_from_x` variants beforehand within the same call - triggers `Option::expect` on `None`, panicking. This directly mirrors CVE-2020-8002: launching a "compute" operation (`add`/`mul`, analogous to launching a grid) that assumes a prior "setup" operation (`new`, analogous to binding a compute shader) was performed, without verifying it actually was.

I was unable to fully verify within the available context whether this panic is caught by a `catch_unwind` boundary somewhere higher in the transaction-execution call stack (only two unrelated `catch_unwind` usages were found in `utils_test.rs` and `concurrency/worker_pool.rs`, neither of which appears to wrap syscall/entry-point execution). If unguarded, this Rust panic during transaction execution would unwind (or abort, depending on panic strategy) the block-production/consensus process for any node executing this transaction — including during Starknet OS re-execution — since all honest sequencer/full nodes would hit the same unrecoverable panic when re-executing the block.

### Impact Explanation
If uncaught, this is a denial-of-service vector: a single malicious contract deployment plus one invoke transaction calling `secp256k1_add_syscall`/`secp256k1_mul_syscall` (or the r1 equivalents) as the first secp operation causes every node executing/re-executing that transaction (batcher, validator, and Starknet OS re-execution) to panic identically. This can halt block production/consensus (an honest network becoming unable to confirm new transactions), which matches the required impact bar. This is a Medium-severity finding, contingent on confirming there is no panic-catching boundary around syscall execution (which I could not fully confirm from the available index).

### Likelihood Explanation
High likelihood of triggering: any account/contract can invoke the vulnerable syscalls directly via ordinary Cairo1 contract code (`starknet::secp256k1::secp256k1_add_syscall(...)` / `secp256k1_mul_syscall(...)` or the r1 equivalents) without ever calling the "new"/"get_point_from_x" syscall in the same execution context. No special privileges are required — only a standard contract deployment and invocation.

### Recommendation
In `secp256k1_add`, `secp256k1_mul`, `secp256r1_add`, and `secp256r1_mul` (crates/blockifier/src/execution/syscalls/syscall_executor.rs), replace the `.expect("Secp segment must be set.")` calls with a graceful error path (e.g., return `SyscallExecutorBaseError::InvalidSyscallInput` or an equivalent recoverable `SyscallExecutionError`/revert) when `optional_secp_segment_base` is `None`, consistent with how `get_point_by_ptr` already returns a recoverable error for invalid point pointers in crates/blockifier/src/execution/syscalls/secp.rs.

### Proof of Concept
1. Deploy a Cairo1 contract whose entry point calls `starknet::secp256k1::secp256k1_add_syscall(p0, p1)` (with arbitrary/dummy `Secp256k1Point` values) as the very first Secp-related syscall invoked during that execution — i.e., do not call `secp256k1_new_syscall` or `secp256k1_get_point_from_x_syscall` beforehand.
2. Submit an ordinary invoke transaction calling that entry point.
3. During execution, `SyscallExecutor::secp256k1_add` runs `optional_secp_segment_base.expect("Secp segment must be set.")` in crates/blockifier/src/execution/syscalls/syscall_executor.rs:326, with `secp_points_segment_base` still `None` (never set by a prior `secp_new`/`secp_get_point_from_x` call), causing a Rust panic in the executing node's process.

```rust
    pub fn secp_add(
        &mut self,
        request: SecpAddRequest,
        vm: &mut VirtualMachine,
        points_segment_base: Relocatable,
        id: usize,
    ) -> SyscallBaseResult<SecpAddResponse> {
        let lhs = self.get_point_by_ptr(request.lhs_ptr)?;
        let rhs = self.get_point_by_ptr(request.rhs_ptr)?;
        let result = *lhs + *rhs;
        let ec_point_ptr =
            self.allocate_point(result.into(), vm, &mut Some(points_segment_base), id)?;
        Ok(SecpOpRespone { ec_point_ptr })
    }

    pub fn secp_mul(
        &mut self,
        request: SecpMulRequest,
        vm: &mut VirtualMachine,
        points_segment_base: Relocatable,
        id: usize,
    ) -> SyscallBaseResult<SecpMulResponse> {
        let ec_point = self.get_point_by_ptr(request.ec_point_ptr)?;
        let result = *ec_point * Curve::ScalarField::from(request.multiplier);
        let ec_point_ptr =
            self.allocate_point(result.into(), vm, &mut Some(points_segment_base), id)?;
        Ok(SecpOpRespone { ec_point_ptr })
    }
```

```rust
    fn allocate_point(
        &mut self,
        ec_point: short_weierstrass::Affine<Curve>,
        vm: &mut VirtualMachine,
        points_segment_base: &mut Option<Relocatable>,
        id: usize,
    ) -> SyscallBaseResult<Relocatable> {
        if points_segment_base.is_none() {
            *points_segment_base = Some(vm.add_memory_segment());
        }
        let point_address = (points_segment_base.expect("Points segment base must be set.")
            + EC_POINT_SEGMENT_SIZE * id)?;
        self.points.insert(point_address, ec_point);
        Ok(point_address)
    }
```
