## Title
State-snapshot restore in `KvOnly` mode commits unverified key-value pairs to durable storage, bypassing Merkle proof authentication - (File: `storage/aptosdb/src/state_restore/mod.rs`)

### Summary
The `StateSnapshotRestore::add_chunk` implementation branches on `StateSnapshotRestoreMode`. In `Default` and `TreeOnly` modes, every chunk of `(key, value)` pairs is checked against the supplied `SparseMerkleRangeProof` and the restore's `expected_root_hash` before (or while) being committed. In `KvOnly` mode, the `proof` argument is accepted but never used — the chunk is written straight to the state-KV store via `StateValueRestore::add_chunk` with no cryptographic verification at all.

### Finding Description
`add_chunk` in [1](#0-0)  matches on `restore_mode`:
- `KvOnly` calls `self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;` — the `proof` parameter is dropped, unused.
- `TreeOnly` calls `tree_restore...add_chunk_impl(..., proof)`, which internally calls `verify_chunk` then `commit_chunk`, cryptographically checking the leaf hashes against `expected_root_hash` per [2](#0-1) .
- `Default` explicitly verifies via `tree_restore.verify_chunk(...)` before writing KV, with a comment justifying the KV-then-tree write order for crash-recovery, but still gated on proof verification.

`KvOnly` is a real, reachable production restore mode: `RestoreCoordinator::run_impl` in [3](#0-2)  invokes `StateSnapshotRestoreController` with `restore_mode: StateSnapshotRestoreMode::KvOnly` to restore the KV snapshot at `kv_snapshot.version` before replaying transactions up to `tree_snapshot.version`. The manifest's `root_hash` is passed down as `expected_root_hash` [4](#0-3) , but because `KvOnly`'s `add_chunk` never consults the accompanying `SparseMerkleRangeProof`, the DB never actually checks that the raw `(key, value)` bytes it commits correspond to that root hash.

Subsequent phase 1.b replays transaction write-sets (whose integrity is protected separately via `TransactionOutputListWithProofV2::verify`, which checks `write_set` hashes against `TransactionInfo.state_change_hash`, itself bound to a validator-signed `LedgerInfo`) on top of this unverified base. Any state key that is *not* touched by a write op between `kv_snapshot.version` and `tree_snapshot.version` keeps whatever value was injected during the unverified `KvOnly` phase. The later `TreeOnly` restore of the tree snapshot (see call sites and `add_chunk_impl`) only reconstructs Jellyfish Merkle tree *nodes* from its own manifest's `(key, value)` chunks — it never cross-checks that the KV store's actual on-disk value for a key matches the hash it just verified into the tree. So the DB's reported Merkle root can match the trusted, validator-signed root while the state-KV table itself holds arbitrary corrupted data for untouched keys.

### Impact Explanation
Any party who controls or can tamper with the backup storage location (e.g., a compromised S3/GCS bucket used for backups, or a MITM against the backup storage API) — without validator collusion or leaked keys — can inject arbitrary state values for any state key not overwritten by transactions replayed after the corrupted snapshot version. This corrupts durable ledger data returned by a restored node to clients (authenticated state reads, indexers, or anything relying on the restored DB), directly matching the "committed state that differs from the correct VM result / corrupts durable ledger data" and "authenticated API ... output bound to the wrong ... proof context" impact categories, since the DB's exposed root hash still matches the genuine chain state while served values do not.

### Likelihood Explanation
Requires an unprivileged attacker with write access to (or ability to tamper with) the backup blob storage, not validator/consensus keys — this is a realistic, lower-trust actor in most production deployments (backups are often stored in third-party or less-hardened infrastructure than validator keys). The `KvOnly` restore path is exercised on every standard `aptos-core` restore/fast-sync-from-backup that uses a separate KV snapshot ahead of a later tree snapshot (`RestoreCoordinator::run_impl` phase 1.a), i.e. it is a normal, not corner-case, code path.

### Recommendation
`StateSnapshotRestoreMode::KvOnly`'s `add_chunk` must verify the supplied `SparseMerkleRangeProof` against `expected_root_hash` (as `Default`/`TreeOnly` already do) before writing to the KV store, even though tree nodes are not persisted in this mode. At minimum, call `JellyfishMerkleRestore::verify_chunk`-equivalent hash-only verification (computing leaf hashes from the KV chunk and checking against the proof/root) prior to `StateValueRestore::add_chunk`, so unverified data is never durably committed.

### Proof of Concept
1. Stand up a `RestoreCoordinator` restore against a backup storage implementation the "attacker" controls (implements `BackupStorage`).
2. Serve a legitimate epoch-ending/transaction-backup chain and a legitimate tree-snapshot manifest at `tree_snapshot.version`, but for the earlier `kv_snapshot` manifest (used with `StateSnapshotRestoreMode::KvOnly`), replace the value bytes for some state key `K` (not touched by any transaction between `kv_snapshot.version` and `tree_snapshot.version`) with attacker-chosen bytes, while leaving `manifest.root_hash` matching the true root (so `txn_info_with_proof.verify` still passes, since that only authenticates `manifest.root_hash` itself, not the per-key data used to reach `restore_mode: KvOnly`).
3. Run the restore to completion; note it succeeds with no error since `KvOnly`'s `add_chunk` never checks the range proof.
4. Query the resulting `AptosDB` for `K` at `tree_snapshot.version` (or later) and observe the served value is the attacker-injected one, while `get_root_hash`/state proofs for other, touched keys still validate against the genuine chain root — demonstrating the DB's authenticated root no longer accurately reflects served data for key `K`.

Note: I was not able to fully trace whether any later full-DB consistency check (e.g., an end-to-end root recomputation over the entire live KV set) exists elsewhere in the restore/fast-sync pipeline outside the files reviewed; if such a check exists it would need to independently re-hash and diff the complete state, which none of the code paths I found perform.

            },

                    .as_mut()
                    .unwrap()
                    .add_chunk_impl(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
            },
            StateSnapshotRestoreMode::Default => {
                // Sequence: verify proof -> write state_kv_db -> write state_merkle_db.
                // This keeps state_kv_db at or ahead of state_merkle_db on disk at every
                // crash point. Were merkle ever ahead, the resume path (which feeds chunks

                // tree_progress] that the tree side skips and therefore does not re-verify.

                    self.tree_restore
                        .lock()
                        .as_mut()
                        .unwrap()
                        .verify_chunk(chunk.iter().map(|(k, v)| (k, v.hash())).collect(), proof)?;
                }
                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["state_value_add_chunk"]);
                    self.kv_restore.lock().as_mut().unwrap().add_chunk(chunk)?;

                {
                    let _timer = OTHER_TIMERS_SECONDS.timer_with(&["jmt_commit_chunk"]);
                    self.tree_restore.lock().as_mut().unwrap().commit_chunk()?;

    /// Restores a chunk of states. This function will verify that the given chunk is correct
    /// using the proof and root hash, then write things to storage. If the chunk is invalid, an
    /// error will be returned and nothing will be written to storage.
    pub fn add_chunk_impl(
        &mut self,
        chunk: Vec<(&K, HashValue)>,
        proof: SparseMerkleRangeProof,
    ) -> Result<()> {
        self.verify_chunk(chunk, proof)?;
        self.commit_chunk()
    }

    /// Verifies a chunk and stages frozen nodes in memory; call [`Self::commit_chunk`] to
    /// flush. On error, in-memory state is partially updated — abort the restore rather
    /// than calling again.
    pub fn verify_chunk(
        &mut self,
        mut chunk: Vec<(&K, HashValue)>,
        proof: SparseMerkleRangeProof,
    ) -> Result<()> {
        if self.finished {
            info!("State snapshot restore already finished, ignoring entire chunk.");
            return Ok(());
        }

        if let Some(prev_leaf) = &self.previous_leaf {
            let skip_until = chunk
                .iter()
                .find_position(|(key, _hash)| key.hash() > *prev_leaf.account_key());
            chunk = match skip_until {
                None => {
                    info!("Skipping entire chunk.");
                    return Ok(());
                },
                Some((0, _)) => chunk,
                Some((num_to_skip, next_leaf)) => {
                    info!(
                        num_to_skip = num_to_skip,
                        next_leaf = next_leaf,
                        "Skipping leaves."
                    );
                    chunk.split_off(num_to_skip)
                },
            }
        };
        if chunk.is_empty() {
            return Ok(());
        }

        for (key, value_hash) in chunk {
            let hashed_key = key.hash();
            if let Some(ref prev_leaf) = self.previous_leaf {
                ensure!(
                    &hashed_key > prev_leaf.account_key(),
                    "State keys must come in increasing order.",
                )
            }
            self.previous_leaf.replace(LeafNode::new(
                hashed_key,
                value_hash,
                (key.clone(), self.version),
            ));
            self.add_one(key, value_hash);
            self.num_keys_received += 1;
        }

        // Verify what we have added so far is all correct.
        self.verify(proof)?;
        Ok(())
