## Analysis

The reported issue is a classic "missing slippage bound at settlement time" bug: a deposit function derives a secondary amount (LP liquidity) from the **current on-chain pool state** at execution time, with no user-supplied bound on that derived amount, so an attacker can shift the on-chain state (price) just before the victim's transaction lands and profit from the mispriced deposit.

java-tron's Bancor-style token Exchange module has the exact same structural flaw in `ExchangeInjectContract`/`ExchangeWithdrawContract`.

### Root cause

`ExchangeInjectActuator.execute()` computes the "other side" amount purely from the **live** `firstTokenBalance`/`secondTokenBalance` of the `ExchangeCapsule` at execution time: [1](#0-0) 

The same live-ratio calculation (with no user-supplied bound) is repeated in validation: [2](#0-1) 

Critically, the protobuf contract for inject/withdraw carries **no** min/max/slippage field, whereas the trade contract (`ExchangeTransactionContract`) explicitly has `expected` for exactly this purpose: [3](#0-2) 

`ExchangeWithdrawActuator` has the identical pattern — computing `anotherTokenQuant` from live balances with no user-chosen bound: [4](#0-3) 

By contrast, `ExchangeTransactionActuator` correctly enforces a slippage bound via `expected`: [5](#0-4) 

### Reachability

Both inject and withdraw are restricted to the exchange's `creator_address`: [6](#0-5) [7](#0-6) 

This is not a privileged/system role — any unprivileged account can call `ExchangeCreateContract` and become the "creator" of its own pool, so this restriction does not disqualify the finding as a trusted-role issue; it only limits who is the *victim* (the creator themselves), while the *attacker* is any unprivileged account trading against that same pool via the unrestricted `ExchangeTransactionContract`.

### Exploit path

1. Attacker observes the creator's pending `ExchangeInjectContract` (broadcast, unconfirmed) intending to inject `tokenQuant` of token A at the pool's current A:B ratio.
2. Attacker front-runs with an `ExchangeTransactionContract` trade that skews `firstTokenBalance`/`secondTokenBalance` (e.g., buying up token A), exploiting that this call has no creator restriction and is available to anyone.
3. The creator's inject transaction executes against the now-skewed balances; `anotherTokenQuant` is computed off the manipulated ratio, forcing the creator to inject a disproportionate amount of token B relative to fair value — effectively donating value into the pool at the skewed price.
4. Attacker back-runs with a reverse trade, extracting the value differential introduced by the mispriced injection, then restoring the ratio.

The same sandwich pattern applies to `ExchangeWithdrawActuator`, where a manipulated ratio at withdrawal time causes the creator to receive less of `anotherTokenID` than fair value, with the difference capturable by the attacker's back-run trade.

### Title
Missing slippage/bound protection in Exchange Inject and Withdraw actuators enables sandwich attacks against pool liquidity operations - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counterpart token amount for a liquidity operation directly from the exchange pool's live on-chain balances at execution time, with no user-specified minimum/maximum bound (unlike `ExchangeTransactionActuator`, which enforces `expected`). This mirrors the Lockbox V2 deposit slippage issue: an attacker can manipulate the pool ratio immediately before the inject/withdraw transaction executes, causing the counterpart amount to be mispriced, and profit by reversing the manipulation afterward (sandwich attack).

### Finding Description
`ExchangeInjectActuator.execute`/`doValidate` and `ExchangeWithdrawActuator.execute`/`doValidate` derive `anotherTokenQuant` solely from `firstTokenBalance`/`secondTokenBalance` read from the `ExchangeCapsule` at execution time — the same pattern as Lockbox V2's `get_liquidity_from_token_a` deriving liquidity from the live `sqrt_price`. Neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` carries a bound field analogous to `expected` in `ExchangeTransactionContract`, so the caller cannot cap their exposure to ratio manipulation between transaction construction/signing and execution.

### Impact Explanation
An attacker with an unprivileged account can use the always-available `ExchangeTransactionContract` to shift a pool's token ratio immediately before a victim's inject/withdraw transaction lands, causing the victim (the pool creator) to deposit or receive a mispriced amount of the counterpart token, and can reverse the trade afterward to extract the resulting value delta. This is a concrete accounting/settlement manipulation impact within the exchange module.

### Likelihood Explanation
Exploitation only requires ordering two `ExchangeTransactionContract`/inject-withdraw transactions around the victim's operation (e.g., via block-producer favor or simply being faster), which is feasible for any user monitoring the mempool for pending inject/withdraw transactions on exchanges they also trade in.

### Recommendation
Add a user-specified bound field (e.g., `expected_another_token_quant` with min/max semantics depending on direction) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validation, mirroring the existing `expected` check in `ExchangeTransactionActuator`.

### Proof of Concept
1. Creator broadcasts `ExchangeInjectContract` to inject `tokenQuant` of token A into exchange `E` at current ratio.
2. Attacker submits `ExchangeTransactionContract` selling token B for token A in `E`, shifting `firstTokenBalance`/`secondTokenBalance` before the creator's tx executes.
3. Creator's inject executes with the skewed ratio; `anotherTokenQuant` (token B deducted from creator) is computed disproportionately high, per [1](#0-0) .
4. Attacker submits a reverse `ExchangeTransactionContract`, extracting the value surplus introduced into the pool, exploiting the lack of a bound check analogous to [5](#0-4)  that exists for trades but not for inject/withdraw.
