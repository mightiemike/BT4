The sequencer contains a direct analog of this exact bug class in its Chainlink oracle integration for L1 gas pricing, and the codebase itself explicitly documents the gap.## Title
L1 gas price Chainlink oracle accepts a feed's clamped `latest_round_data()` answer without checking it against the feed's own `minAnswer`/`maxAnswer`, only against wide static sanity bounds - (File: `crates/apollo_l1_gas_price/src/chainlink_oracle/feed_read.rs`)

### Summary
The sequencer's `L1GasPriceProvider` derives the ETH→STRK conversion rate used to commit `l1_gas_price_fri`/`l1_data_gas_price_fri` into every block's `ConsensusBlockInfo` from Chainlink price feeds read on-chain via `read_feed()`. Like the reported `ChainlinkOracle::getPriceInEth()` bug, the sequencer's reader only fetches `latest_round_data` and `decimals`, and validates the answer solely for zero-ness and staleness/future-dating, then checks it against static, deliberately-wide "sanity" bounds. It never fetches or compares against the feed aggregator's own `minAnswer`/`maxAnswer`. If the underlying feed clamps its reported answer during an extreme price move (the exact scenario the original report describes), the clamped value can still fall inside the wide sanity bounds and be silently accepted as the true market price.

### Finding Description
`read_feed()` in `crates/apollo_l1_gas_price/src/chainlink_oracle/feed_read.rs` decodes the round data and applies only three guards: zero-answer, staleness, and future-timestamp checks, then rescales and calls `check_rate_bounds`: [1](#0-0) 

`check_rate_bounds` in `crates/apollo_l1_gas_price/src/rate_bounds.rs` only rejects a rate that falls outside operator-configured absolute min/max, and the developers explicitly document that these bounds are "wide enough to pass a manipulated but plausible answer": [2](#0-1) 

The default bounds are extremely wide (e.g. ETH/USD accepted from $20 to $50,000, "~10x above the all-time high"; STRK/USD from $0.0001 to $10): [3](#0-2) 

No code path reads the feed's `minAnswer`/`maxAnswer` (or equivalent) from the aggregator contract; only `latest_round_data` and `decimals` are queried: [4](#0-3) [5](#0-4) 

This mirrors the original bug class precisely: if the underlying feed's aggregator hits its internal clamp during a crash or spike, the returned answer is a stale/incorrect but "plausible" value that is well within the sequencer's ±10x sanity range, so it passes every guard and is treated as ground truth.

### Impact Explanation
The accepted rate feeds directly into `derive_eth_to_fri_rate` and then into `L1PricesInFri::convert_from_wei`, which sets `l1_gas_price_fri` and `l1_data_gas_price_fri` committed into `ConsensusBlockInfo` for every proposed block: [6](#0-5) 

A clamped-but-in-range answer causes the sequencer to systematically mis-price L2 gas fees relative to the true L1 cost/market rate for as long as the feed remains clamped. This can cause users to be overcharged in STRK for a given L1 cost, or cause the sequencer to under-recover L1 posting costs, both of which are wrong-committed-value impacts baked into every block header derived from this input.

### Likelihood Explanation
This triggers automatically and passively whenever the Chainlink feed's own aggregator enters a clamped state (e.g. during a severe ETH or STRK market crash/spike) — no attacker action or privileged access is required; it is a standard, foreseeable market condition the same as in the original report. The developers' own TODO comment in `rate_bounds.rs` acknowledges the current absolute bounds are known to be too permissive to catch a "manipulated but plausible" (i.e., clamped) answer, confirming this is a real, currently-unmitigated gap rather than a theoretical one.

### Recommendation
Fetch and check the feed's own `minAnswer`/`maxAnswer` (if the Starknet Chainlink feed contract exposes them) in `read_feed()`, rejecting or flagging answers equal to either bound. Additionally, implement the already-noted TODO of bounding the rate against the previous block's implied rate (a relative/delta check) rather than relying solely on static absolute sanity bounds in `check_rate_bounds`.

### Proof of Concept
1. Assume the Starknet Chainlink ETH/USD feed at `l1_gas_price_provider_config.chainlink_oracle_config.eth_usd_feed_address` is configured, like standard Chainlink aggregators, with internal `minAnswer`/`maxAnswer` clamps (e.g. min $1,500).
2. ETH market price crashes to $500; the aggregator, per Chainlink's documented behavior, continues reporting `minAnswer` ($1,500) via `latest_round_data`.
3. `read_feed()` in `feed_read.rs` reads `answer = 1500 * 10^decimals`, `updated_at` fresh — passes the zero/staleness/future checks.
4. `rescale_to_rate_decimals` and `check_rate_bounds` compare `$1,500` against the configured sanity band `[$20, $50,000]` — well inside bounds, so it is accepted as valid.
5. `derive_eth_to_fri_rate` computes an ETH→STRK rate based on the stale $1,500 ETH price rather than the true $500 price, and this incorrect rate is committed into `l1_gas_price_fri`/`l1_data_gas_price_fri` for every subsequent block until the feed unclamps, overcharging every L2 transaction fee by ~3x relative to true L1 cost.

/// The feed's answer, rescaled to `EXCHANGE_RATE_DECIMALS` and checked against the feed's bounds.
pub(super) async fn read_feed(
    batcher_client: &SharedBatcherClient,
    feed: PairFeed,
    block_timestamp: u64,
) -> RateResult {
    let pair = feed.bounds.pair;
    let pair_name = pair.pair_name();
    let feed_address = feed.feed_address;
    // `decimals` is read with every rate rather than cached: a feed that changes it rescales the
    // answer by a power of ten, which the absolute bounds are too wide to catch.
    let decimals_retdata = call_view(batcher_client, feed_address, DECIMALS_ENTRY_POINT).await?;
    let round_retdata =
        call_view(batcher_client, feed_address, LATEST_ROUND_DATA_ENTRY_POINT).await?;
    let feed_decimals = decode_feed_decimals(decimals_retdata, pair)?;

    let round = decode_feed_round(round_retdata)?;
    if round.answer == 0 {
        return Err(ExchangeRateOracleClientError::InvalidRateError(format!(
            "{pair_name} returned a zero answer"
        )));
    }
    if block_timestamp.saturating_sub(round.updated_at) > feed.freshness.max_staleness_seconds {
        return Err(ExchangeRateOracleClientError::StaleFeedError {
            pair,
            updated_at: round.updated_at,
            block_timestamp,
            max_staleness_seconds: feed.freshness.max_staleness_seconds,
        });
    }
    // Catches a round dated ahead of the block being priced: the staleness check above saturates
    // such a subtraction to zero, which alone treats it as fresh regardless of age.
    if round.updated_at.saturating_sub(block_timestamp)
        > feed.freshness.max_future_updated_at_seconds
    {
        return Err(ExchangeRateOracleClientError::FutureFeedError {
            pair,
            updated_at: round.updated_at,
            block_timestamp,
            max_future_updated_at_seconds: feed.freshness.max_future_updated_at_seconds,
        });
    }

    let rate = rescale_to_rate_decimals(round.answer, feed_decimals)?;
    check_rate_bounds(rate, feed.bounds)?;
    Ok(rate)

// TODO(Asaf): bound the rate's change against the previous block's implied rate. The absolute
// bounds below are wide enough to pass a manipulated but plausible answer, the STRK/USD pair alone
// accepting anything from $0.0001 to $10, which only a bound relative to the last accepted rate
// catches. It must be anchored to the block header rather than to node-local history, so that every
// validator accepts and rejects the same values.
/// Absolute bounds are the only defense against a feed wired to the wrong asset or a
/// plausible-but-poisoned answer: consensus checks that validators agree with each other, never
/// that the agreed value is sane, and every node reads the same chain state.
pub(crate) fn check_rate_bounds(
    rate: ExchangeRate,
    bounds: RateBounds,
) -> Result<(), ExchangeRateOracleClientError> {
    if rate < bounds.minimum_rate || rate > bounds.maximum_rate {
        return Err(ExchangeRateOracleClientError::RateOutOfBoundsError {
            pair: bounds.pair,
            rate,
            min_rate: bounds.minimum_rate,
            max_rate: bounds.maximum_rate,
        });
    }
    Ok(())
