## Title
`liquidate-multi` uses `map` over `call-liquidate`, absorbing individual liquidation failures inside a designed-atomic batch, letting bad-debt socialization for one borrower be silently skipped while the batch as a whole reports success - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` iterates a list of borrower liquidation requests using `(map call-liquidate positions)` and always returns `(ok ...)` regardless of whether individual entries in the resulting list are `err` responses. [1](#0-0) 

### Finding Description
`liquidate-multi`'s doc comment states its purpose explicitly: *"Prevents front-running attacks that prevent bad debt socialization"* and *"Failed liquidations return error codes but don't revert entire batch."* [2](#0-1) 

The single-position `liquidate` function performs the collateral seizure and, if `no-collateral-left` becomes true, runs a `fold socialize-debt-asset` step to socialize any remaining bad debt across the vault, guarded by `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` — if socialization fails, the entire `liquidate` call reverts. [3](#0-2) 

Because `liquidate-multi` simply wraps each `call-liquidate` in `map` and returns `(ok (map call-liquidate positions))`, a per-position failure (e.g. `ERR-BAD-DEBT-SOCIALIZATION-FAILED`, `ERR-SLIPPAGE`, `ERR-LIQUIDATION-PAUSED`, or any other `asserts!`/`try!` failure inside `liquidate`) does not roll back other positions in the batch, and — critically — does not roll back or retry within the batch transaction itself. This is exactly the "fold that absorbs failure" pattern: the outer function's success return masks individual sub-operation failures. A caller (front-end, liquidation bot, or the anti-front-running mechanism the comment describes) that inspects only the outer `(ok ...)` result without unpacking each inner response can believe the whole batch of liquidations/socializations succeeded, when in fact one or more bad-debt-socialization steps silently failed and left that borrower's insolvent position un-socialized in the same block — the specific bad-debt window the function was designed to close.

### Impact Explanation
This lands on **High — temporary freezing of funds / unclaimed yield**: an insolvent borrower position that should have had its bad debt socialized into the vault (spreading the loss across depositors, per `vault-socialize-debt` logic) instead remains in place with stale accounting until a subsequent, separate liquidation transaction is issued. During that window vault depositors' claimable yield/principal accounting understates the true bad debt, and the specific anti-front-running protection `liquidate-multi` was built to provide (atomically clearing bad debt in the same batch, before the position can be manipulated) is defeated for the failed entries, since failures are absorbed rather than causing the batch (or at least visibly flagging) to require re-submission.

### Likelihood Explanation
Likelihood is moderate: it requires one leg of a batch of many independent liquidation calls to hit a legitimate `asserts!`/`try!` failure inside `liquidate` (slippage, pause, zero-amount, bad-debt-socialization failure) while other legs succeed — a very plausible real-world scenario given the number of independent failure paths in `liquidate`, and it requires no attacker action beyond normal batch usage by a keeper/liquidator bot that doesn't decode each list element.

### Recommendation
Either (a) have `liquidate-multi` inspect each `response` produced by `map call-liquidate` and abort the whole transaction if any critical failure (e.g. `ERR-BAD-DEBT-SOCIALIZATION-FAILED`) occurs, or (b) clearly document/enforce at the caller level that every element of the returned list must be checked, and add monitoring/alerting so partial failures in bad-debt socialization are never silently accepted as "batch succeeded."

### Proof of Concept
1. Liquidator submits `liquidate-multi` with two positions: Borrower A (partially collateralized, will fully clear collateral and trigger bad-debt socialization) and Borrower B (healthy liquidation).
2. `map call-liquidate positions` invokes `liquidate` for both; for Borrower A, `no-collateral-left` is `true`, the `fold socialize-debt-asset` sub-step fails for some reason (e.g., one of the vault's `socialize-debt` calls errors), causing `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` to fail and `liquidate` to return `(err u400021)` for Borrower A only.
3. Borrower B's `liquidate` call succeeds and returns `(ok {...})`.
4. `liquidate-multi` returns `(ok (list (err u400021) (ok {...})))` — the outer transaction succeeds.
5. A caller that only checks the outer `ok` (as intended by the function's "don't revert entire batch" design) treats the whole batch as successful; Borrower A's insolvent position is left un-socialized, with collateral already partially seized in the same call before the socialization step failed, and does not get automatically retried.
