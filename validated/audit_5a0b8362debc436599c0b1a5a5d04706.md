### Title
OAuth callback validates HMAC against a different `shop` value than the one used for the token exchange and session creation, enabling shop/parameter-pollution confusion - (File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts)

### Summary
In the OAuth `callback` handler, the `shop` value used to build the access-token exchange request and the created `Session` is taken from `URLSearchParams.get('shop')` (which returns the **first** occurrence of a repeated query parameter), while the value that is actually verified against Shopify's signed `hmac` is taken from `Object.fromEntries(query.entries())` (which collapses repeated keys to the **last** occurrence). A request containing a duplicated `shop` parameter can therefore pass HMAC validation using one shop value while the OAuth flow proceeds using a different, attacker-chosen shop value — the same class of bug as the audited finding, where a security check applied on one code path (`safeTransferFrom`) is not consistently enforced on an equivalent path (`safeBatchTransferFrom`) operating on the same state.

### Finding Description
`callback()` in [1](#0-0)  extracts the raw `URLSearchParams` from the request URL and reads `shop` with `query.get('shop')`, which per the WHATWG URL spec returns only the **first** value when a key is repeated.

Immediately after, it builds `authQuery` via `Object.fromEntries(query.entries())` [2](#0-1) . `Object.fromEntries` iterates entries in order and assigns each key sequentially, so it ends up with the **last** value for a repeated key. This `authQuery` object (a plain object, not a `URLSearchParams` instance) is what gets passed into `validQuery` → `validateHmac(config)(query)` [3](#0-2) .

Inside `validateHmac`, `normalizeQuery` only performs the "must not appear more than once" duplicate-parameter rejection for the `appProxy` signator; for the `admin` signator (used by the OAuth callback) and a non-`URLSearchParams` query, the function returns the object unchanged with no duplicate/array check at all: [4](#0-3) . Because `Object.fromEntries` already silently collapsed the duplicate `shop` key to its last value before this function ever sees it, the HMAC is computed and verified against that "last" value — with no error and no indication that pollution occurred.

Meanwhile, after `validQuery` succeeds, the code re-reads `query.get('shop')` (the **first** value) to compute `cleanShop`, which is used to:
- Send the client_secret/code POST to `https://${cleanShop}/admin/oauth/access_token` [5](#0-4) 
- Create and persist the resulting `Session` with `shop: cleanShop` [6](#0-5) 

This mirrors the audited bug class exactly: a security invariant (parameter must be single-valued / must match what's cryptographically verified) is enforced on one consumption path but silently diverges on another consumption path over the same underlying request data, similar to how `GameItems::safeTransferFrom` enforced transferability while `safeBatchTransferFrom` did not, letting the unguarded path be exploited despite the guarded path appearing safe.

### Impact Explanation
If an attacker can get a legitimately-signed OAuth callback URL (i.e., one issued by Shopify to a merchant during an actual OAuth authorization) delivered to the app with an extra duplicated `shop` query parameter inserted before the genuine one — e.g. `?shop=attacker-controlled.myshopify.com&shop=<victim-shop>.myshopify.com&code=...&state=...&hmac=<hmac signed by Shopify for the single victim shop value>` — then:
- `authQuery.shop` collapses to the last (victim) value, so `validateHmac` succeeds because it matches what Shopify actually signed.
- `query.get('shop')` returns the first (attacker) value, so the app exchanges the authorization `code` against `https://attacker-controlled.myshopify.com/admin/oauth/access_token` and stores the resulting session under the attacker's shop.

Depending on how the `code` behaves against a spoofed shop domain in practice, this can result in cross-tenant session/data confusion, a valid session being persisted for the wrong shop, or a denial-of-service / broken install for the legitimate shop, since the app believes an authenticated OAuth exchange succeeded for the wrong tenant while bypassing the intended integrity guarantee of HMAC validation (the check is supposed to guarantee the request parameters are exactly what Shopify signed, but a discrepancy between what's checked and what's used defeats that guarantee).

### Likelihood Explanation
Exploitation requires an attacker to control or inject the query string used to reach the callback URL while still carrying a valid signature/code/state for a legitimate OAuth attempt — e.g., via an open-redirect, a manipulated link sent to the merchant, or interception/rewriting of the redirect URL before it reaches the app's server. This is a real, unprivileged-attacker-reachable HTTP path (`/auth/callback` handling), and requires no leaked secrets or MITM of the HMAC key itself — only control over the URL delivered to the callback endpoint, which is plausible via phishing/CSRF-style link manipulation in the OAuth redirect chain. The `state`/cookie check does not protect against this because `state` value itself is not duplicated; only `shop` is polluted.

### Recommendation
- Use a single, consistent extraction of `shop` (and all security-relevant parameters) throughout the whole callback flow. Prefer deriving the value once from the normalized query used for HMAC validation, and reuse that exact value for `cleanShop`/session/token-exchange, rather than re-reading `query.get('shop')` from the raw `URLSearchParams`.
- In `normalizeQuery` in `hmac-validator.ts`, apply the same single-value enforcement (`APP_PROXY_SINGLE_VALUE_PARAMS`-style rejection) for the `admin` signator as well, not just `appProxy`, so any duplicate `shop`/`hmac`/`code`/`state` causes the entire query to be rejected outright rather than silently resolved via "last value wins" semantics.
- Ensure `Object.fromEntries(query.entries())` is not used for security-sensitive fields without first checking there are no duplicate keys, since it silently discards data in a direction (last-wins) that is inconsistent with `URLSearchParams.get()` (first-wins) used elsewhere in the same function.

}: {
  config: ConfigInterface;
  query: AuthQuery;

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }
