### Title
Committed L1-Handler Transaction Can Have Its Terminal `Committed` State Overwritten via Later `mark_consumed`/`mark_cancellation_request` Calls, Restoring `is_validatable()` to `true` - (File: `crates/apollo_l1_events/src/transaction_record.rs`)

### Summary
`TransactionRecord::mark_committed` is documented and enforced (via an `assert!`) as a one-way, terminal transition, analogous to the reported `emergencyClose` in the external report — once committed, a transaction is supposed to be permanently ineligible for re-validation/re-inclusion. However, `mark_consumed` and `mark_cancellation_request` mutate `self.state` unconditionally (or based on a stale check), which can overwrite the `Committed` state and ultimately allow `is_validatable()` to evaluate `true` again for a transaction that was already committed to L2, mirroring the "closed vault can be paused then resumed" bug class.

### Finding Description
`TransactionRecord` uses two parallel truth sources: a permanent boolean flag `committed` (set once, guarded by an `assert!(!self.committed, ...)` in `mark_committed`) [1](#0-0) , and a mutable `state: TransactionState` enum that most read-methods (`is_committed`, `is_cancelled`, `is_consumed`, `is_validatable`) actually inspect [2](#0-1) .

`mark_consumed` only uses `is_committed()` for logging, then **unconditionally** overwrites `self.state = TransactionState::Consumed`, even if the prior state was `Committed`: [3](#0-2) 

After this call, `is_committed()` (state-based) returns `false`, even though the record was truly committed — only the internal `committed: bool` still reflects the true history.

`mark_cancellation_request` then decides whether to process a cancellation based on this same state-derived `is_committed()` check: [4](#0-3) 

Because `is_committed()` no longer reflects the true committed history after a `mark_consumed` call, a subsequent cancellation-request event moves `self.state` to `CancellationStartedOnL2`. At that point:
- `is_committed()` → `false` (state is `CancellationStartedOnL2`)
- `is_cancelled()` → `false` (only `true` for `CancelledOnL2`)
- `is_consumed()` → `false` (state moved away from `Consumed`)

Thus `is_validatable()` — defined as `!is_committed() && !is_cancelled() && !is_consumed()` — evaluates `true` again for a transaction that was already permanently committed to L2: [5](#0-4) 

This is the direct analog of the reported bug class: a supposedly irreversible terminal state (`Committed`, guarded by an `assert!`) can be silently unwound by two subsequent, individually-legitimate state-transition calls (`mark_consumed`, `mark_cancellation_request`) that do not check the permanent `committed` boolean, only the transient `state` enum. Only `update_time_based_state` correctly consults the permanent `self.committed` flag [6](#0-5) ; the other mutators do not, creating an inconsistency between the "permanent" and "derived" notions of committed state.

### Impact Explanation
If `is_validatable()` can return `true` for an L1-handler transaction hash that has already been committed to L2, the transaction becomes eligible again for validation/inclusion consideration in the L1 events provider's indices, undermining the invariant that a committed L1→L2 message is consumed exactly once by the sequencer. Depending on downstream consumers of `is_validatable()`/the proposable/validatable indices in `transaction_manager.rs`, this can lead to attempted re-processing of an already-executed L1 handler transaction, causing state/consensus divergence between honest nodes if the race is hit non-deterministically (e.g., depending on the arrival order of L1 "consumed" and "cancellation" events relative to L2 commitment), which the code itself flags as a correctness hazard ("double consumption is a bug", "committed twice... may lead to l2 reorgs").

### Likelihood Explanation
The likelihood depends on event-ordering: `mark_consumed` and `mark_cancellation_request` are driven by L1 events (message consumption and cancellation requests), which are actions independently reachable by the L1 message sender of the L1→L2 message. If the sequencer processes a "consumed" event for an already-committed transaction (plausible if L1 event timestamps/scraping race with L2 commit application) followed by a cancellation-request event for the same hash, the terminal-state guard is bypassed purely through legitimate transaction manager entry points, without any privileged/operator action. I was not able to fully trace `transaction_manager.rs`'s exact call ordering guarantees (e.g., whether it structurally prevents processing a cancellation event after a consumption event for the same hash) within the available exploration budget, so the exact real-world triggerability of the full chain (as opposed to the code-level invariant violation, which is clearly present) is not fully confirmed.

### Recommendation
1. Make `is_committed()`, `is_cancelled()`, and `is_consumed()` consult the permanent `committed` boolean (and similarly a permanent "consumed" flag) rather than solely the transient `state` enum, so that once a transaction is truly committed/consumed, no later mutator can cause these predicates to disagree with history.
2. In `mark_consumed` and `mark_cancellation_request`, guard against overwriting `state` once `self.committed` (or an equivalent permanent "terminal" flag) is `true` — mirroring how `update_time_based_state` already checks `self.committed` before transitioning to `CancelledOnL2`.
3. Add an explicit `is_terminal()`/`is_final()` accessor based purely on the permanent boolean flags, and use it uniformly across all read paths that decide transaction eligibility (`is_validatable`, indices maintenance in `transaction_manager.rs`).

### Proof of Concept
Conceptual sequence exercising the `transaction_record.rs` state machine directly (unit-test style):
```rust
let mut record = TransactionRecord::new(payload);
record.mark_committed();                     // state = Committed, committed = true
assert!(!record.is_validatable());            // correctly not validatable

record.mark_consumed(ts1);                    // state overwritten to Consumed
assert!(!record.is_committed());              // BUG: now false, even though committed == true
assert!(!record.is_validatable());            // still false only because is_consumed() == true

record.mark_cancellation_request(ts2);        // is_committed() (state-based) == false, so branch taken:
                                               // state = CancellationStartedOnL2
assert!(record.is_validatable());             // BUG: now TRUE for an already-committed transaction
```
This reproduces, at the data-structure level, the same "final-state can be undone by subsequent state-mutating calls that don't check the permanent flag" pattern described in the external report's `emergencyClose` → `emergencyPause`/`emergencyResume` PoC.

    pub fn mark_cancellation_request(
        &mut self,
        timestamp: BlockTimestamp,
    ) -> Option<BlockTimestamp> {
        let tx_hash = self.tx.tx_hash();
        // Once committed on L2, cancellation requests are only recorded for debugging purposes, but
        // not processed.
        if self.is_committed() {
            warn!(
                "L1 handler transaction {tx_hash} was not marked for cancellation started on L2 \
                 as it is already committed."
            )
        } else {
            info!("Marking L1 handler transaction {tx_hash} as cancellation started on L2.");
            self.state = TransactionState::CancellationStartedOnL2;
        }

        match self.cancellation_requested_at {
            Some(existing) => Some(existing),
            None => {
                self.cancellation_requested_at = Some(timestamp);
                None
            }
        }
    }
