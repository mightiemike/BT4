### Title
Wallet Contract's hardcoded NEP‑141 storage deposit amount breaks the ERC‑20 emulation for legitimate tokens with higher storage costs - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The immutable NEAR Wallet Contract (the protocol's ETH‑emulation implicit-account contract) hardcodes a fixed NEP‑141 `storage_deposit` amount instead of querying each token's actual `storage_balance_bounds`. This mirrors the reported bug class: a rigid, hardcoded numeric assumption about a token standard parameter (there: 18 decimals; here: a fixed storage deposit) blocks the protocol's own advertised core functionality — supporting ERC‑20/NEP‑141 token transfers for "essentially all tokens" — whenever a legitimate token deviates from the assumed value.

### Finding Description
The Wallet Contract emulates ERC‑20 `transfer` calls by mapping them to NEP‑141 `ft_transfer`, and if the receiver isn't storage-registered it first issues a `storage_deposit` call using a constant amount: [1](#0-0) 

This constant is explicitly justified by an assumption that "essentially all tokens" use the same storage bound, hard-coding it rather than calling `storage_balance_bounds()` on-chain: [2](#0-1) 

When an ERC‑20 transfer is emulated to an unregistered receiver, `nep_141_storage_balance_callback` batches `storage_deposit` (using the hardcoded `NEP_141_STORAGE_DEPOSIT_AMOUNT`) with the `ft_transfer` call in the same promise: [3](#0-2) 

Because these are two `function_call` actions chained on the *same* `Promise`, they execute as dependent actions within the same receipt processing sequence; if `storage_deposit` fails (which the NEP‑141/NEP‑145 standard requires it to do when the attached deposit is below `storage_balance_bounds().min`), the subsequent `ft_transfer` never succeeds and the whole flow is reported as a failed promise in `rlp_execute_callback`: [4](#0-3) 

The Wallet Contract's WASM code is not something a user or relayer can patch — it is a fixed set of bytecode versions resolved from the protocol binary by code hash: [5](#0-4) 

`rlp_execute` is the *only* entry point through which an eth-implicit (Wallet Contract) account can move its NEP‑141 token balances: [6](#0-5) 

Consequently, any NEP‑141 token whose `storage_balance_bounds().min` exceeds the hardcoded `1_250 * 10^18` yoctoNEAR (1.25 milliNEAR) cannot ever be transferred by a Wallet Contract account to a not-yet-registered receiver — the exact same "hardcoded assumption blocks legitimate asset class" bug pattern as the reported Factory 18-decimals issue, just manifesting in the NEAR Wallet Contract's token-transfer emulation instead of a collateral-token decimals check.

### Impact Explanation
This is reachable by any unprivileged actor: a user (or relayer acting on the user's behalf) submitting a single RLP-encoded Ethereum-style transaction via `rlp_execute` that emulates an ERC‑20 `transfer` to a new receiver. For any legitimate NEP‑141 token with storage requirements above the hardcoded constant (which the protocol has no control over once a token is deployed with a different NEP‑145 pricing model), the transfer emulation permanently fails whenever the receiver is unregistered, since the contract code is immutable protocol bytecode that cannot be altered without a network-wide protocol upgrade. This breaks the Wallet Contract's core promised functionality of emulating ERC‑20 transfers for NEP‑141 tokens generally, and can strand a Wallet Contract account's holdings of such a token when it needs to move them to a new/unregistered recipient (e.g., a fresh exchange deposit address), since there's no fallback interface to perform a raw `ft_transfer` from this account type outside of this hardcoded-amount code path.

### Likelihood Explanation
High likelihood of being hit unintentionally: any NEP‑141 token whose storage cost model differs from the "essentially all tokens" assumption (e.g., tokens with richer per-account metadata, or tokens deployed on chains where per-byte storage cost is priced differently at time of the hardcode being fixed) will deterministically trigger this failure the first time a wallet contract account tries to send such a token to a brand-new receiver.

### Recommendation
Replace the hardcoded `NEP_141_STORAGE_DEPOSIT_AMOUNT` with a dynamic on-chain lookup of the token's `storage_balance_bounds()` (or otherwise thread the actual required deposit through the emulation flow) before issuing `storage_deposit`, rather than assuming a fixed constant is valid for every NEP‑141 token the protocol intends to support.

### Proof of Concept
1. Deploy a NEP‑141 token whose `storage_balance_bounds().min` is greater than `1_250 * 10^18` yoctoNEAR (e.g., a token that stores extra per-account metadata).
2. Fund a Wallet Contract (eth-implicit) account with that token.
3. Sign an Ethereum-style `transfer(to, value)` call targeting an address that has never interacted with the token (unregistered), and submit it via `rlp_execute`.
4. Observe `nep_141_storage_balance_callback` batches `storage_deposit` with the hardcoded amount plus `ft_transfer`; `storage_deposit` panics for insufficient deposit per NEP‑145, causing the whole receipt to fail and `rlp_execute_callback` to report `ExecuteResponse{success: false, error: Some("Failed Near promise")}`, as shown at [4](#0-3) . This transfer can never succeed through this contract for this receiver, regardless of retries, since the constant is fixed protocol bytecode.
