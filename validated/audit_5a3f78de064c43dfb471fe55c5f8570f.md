## Analog Found: `TokenConfig.Enabled` flag is never enforced before crediting PRC20 on inbound execution

### Title
Disabled/de-whitelisted tokens can still be minted via PRC20 deposit on inbound execution - (File: `x/uexecutor/keeper/handler.go`)

### Summary
This is a direct structural analog of the reported bug: `uregistry` defines a `TokenConfig.Enabled` flag explicitly documented as "Whether this token is enabled for minting/bridging" [1](#0-0) , mirroring the `Agreement.suspend()` status flag in the original report. Just as `verifyThresholds` validated other agreement fields but never checked `suspend()` state, the inbound execution path fetches `TokenConfig` and uses its `NativeRepresentation.ContractAddress` to mint PRC20 but never reads or enforces the `Enabled` field.

### Finding Description
`depositPRC20` — the function that performs the actual PRC20 mint/credit for every inbound funds path (`FUNDS`, `FUNDS_AND_PAYLOAD`, `GAS_AND_PAYLOAD`) — fetches the `TokenConfig` purely to resolve the PRC20 contract address and never inspects `tokenConfig.Enabled`: [2](#0-1) 

This function is called from every inbound-funds execution path, e.g. `ExecuteInboundFundsAndPayload`: [3](#0-2) 
and the gas-and-payload autoswap deposit path, which similarly resolves `tokenConfig.NativeRepresentation.ContractAddress` without gating on `Enabled`: [4](#0-3) 

By contrast, the codebase does correctly gate other registry flags at the right chokepoints — `ChainConfig.Enabled.IsInboundEnabled`/`IsOutboundEnabled` are checked in `VoteInbound` and `ExecutePayload` before any state changes: [5](#0-4) [6](#0-5) 
This shows the "enabled" check pattern is known and applied to `ChainConfig`, but the analogous `TokenConfig.Enabled` field is defined, stored, and exposed via `GetTokenConfig`/`AddTokenConfig`/`RemoveTokenConfig` [7](#0-6)  yet never actually consulted anywhere in the inbound execution or PRC20-minting code paths — confirmed by an exhaustive repository-wide search that found zero references to `tokenConfig.Enabled` outside of proto/API boilerplate and test fixtures.

### Impact Explanation
An admin can de-whitelist a token (`MsgRemoveTokenConfig`, or by leaving `Enabled=false` on an update) intending to halt minting/bridging of that asset — for example during an incident, a compromised source-chain token contract, or a liquidity-cap breach. Because `depositPRC20` and the autoswap-deposit helpers never check this flag, ordinary users can still submit inbound votes/transactions referencing that (still-registered but disabled) token config and have PRC20 minted to their Universal Executor Account, defeating the intended kill-switch and continuing to mint/accept a token the protocol operator has explicitly tried to suspend. This corrupts PRC20 accounting semantics ("unauthorized mint" class impact) relative to the operator's declared token-enablement state.

### Likelihood Explanation
High reachability: any unprivileged user submitting/observing an inbound (funds, funds+payload, or gas+payload) for a `TokenConfig` entry that still exists in `TokenConfigs` but has `Enabled=false` will trigger this path with no special preconditions — it only requires ordinary validator quorum on an otherwise-valid inbound observation, which the honest-validator ballot flow processes normally since `Enabled` is never part of the ballot's execution guard.

### Recommendation
Add an explicit `tokenConfig.Enabled` check in `depositPRC20` (and any other PRC20-mint/autoswap-deposit helper that resolves a `TokenConfig`) immediately after fetching the config, returning an error (and following the same shouldRevert/PCTx-failure bookkeeping used for other execution errors) when the token is disabled — mirroring the `ChainConfig.Enabled` gate pattern already used in `VoteInbound`/`ExecutePayload`.

### Proof of Concept
1. Admin registers `TokenConfig{Chain: "eip155:X", Address: tokenAddr, Enabled: true, NativeRepresentation: {ContractAddress: prc20Addr}}`.
2. Admin later updates/removes intending to disable it, but since removal is what's exposed (`MsgRemoveTokenConfig`) versus an in-place `Enabled=false` toggle, note: if `MsgUpdateTokenConfig` supports setting `Enabled=false` while keeping the entry, the entry remains in `TokenConfigs` with `Enabled=false`.
3. A user submits a cross-chain deposit referencing that token; validators vote via `VoteInbound`, which only checks `IsChainInboundEnabled`, not token status.
4. On ballot finalization, `ExecuteInboundFundsAndPayload` → `depositPRC20` is invoked, which fetches the `TokenConfig`, ignores `Enabled`, and mints PRC20 to the recipient's UEA — confirming the flag has no enforcement effect.

Note: I was unable to fully inspect `x/uexecutor/types/inbound.go`'s `ValidateForExecution` function contents (only confirmed its existence via grep), so if that function performs additional token-status validation not visible in the reviewed keeper code, it would need to be checked to confirm this is not already mitigated elsewhere. Based on the exhaustive `Enabled`-reference search returning no hits outside proto/test code, I have high confidence the check is genuinely absent, but flagging this uncertainty for completeness.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
