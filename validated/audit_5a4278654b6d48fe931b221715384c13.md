## Title
Asset Issuance Creates Diverging `precision` (Decimals) Metadata Between V1 and V2 Token Records - (File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java)

### Summary
The reported bug describes ZC Tokens being deployed with an incorrect/inconsistent number of decimals depending on token type (perpetual vs. non-perpetual), causing user-facing confusion about withdrawn amounts. `java-tron`'s TRC10 asset-issuance path exhibits the same bug class: for the same logical token, the `precision` (decimals) metadata is silently forced to a different value in one of the two persisted representations of the asset, so different, publicly-reachable read APIs return inconsistent decimals for the identical asset.

### Finding Description
`AssetIssueActuator.execute()` creates two capsules from the same `AssetIssueContract` — one for the legacy V1 store and one for the V2 store. When `AllowSameTokenName` is disabled (the legacy/default mode), the code explicitly zeroes out the precision on the V2 copy while leaving the user-specified precision untouched on the V1 copy: [1](#0-0) 

```
AssetIssueCapsule assetIssueCapsule = new AssetIssueCapsule(assetIssueContract);
AssetIssueCapsule assetIssueCapsuleV2 = new AssetIssueCapsule(assetIssueContract);
...
if (dynamicStore.getAllowSameTokenName() == 0) {
  assetIssueCapsuleV2.setPrecision(0);
  assetIssueStore.put(assetIssueCapsule.createDbKey(), assetIssueCapsule);
  assetIssueV2Store.put(assetIssueCapsuleV2.createDbV2Key(), assetIssueCapsuleV2);
} else {
  assetIssueV2Store.put(assetIssueCapsuleV2.createDbV2Key(), assetIssueCapsuleV2);
}
```

The asset creator can legitimately set `precision` up to `PRECISION_DECIMAL` (6), validated at: [2](#0-1) 

The stored records are then exposed through separate, unprivileged public read paths that pick different stores depending on the query used and the `AllowSameTokenName` mode:

- `Wallet.getAssetIssueByName()` reads from the **V1** store (`assetIssueStore`, precision as set by the user) when `AllowSameTokenName == 0`: [3](#0-2) 

- `Wallet.getAssetIssueById()` always reads from the **V2** store (`assetIssueV2Store`, precision forced to 0): [4](#0-3) 

Both of these are exposed to any unauthenticated client via HTTP and gRPC: [5](#0-4) [6](#0-5) [7](#0-6) 

The unit test explicitly confirms and hard-codes this divergence as expected behavior — V1 keeps `precision = 6` while V2 is forced to `precision = 0` for the identical token: [8](#0-7) 

This is structurally the same defect class as the reported ZCToken issue: the same underlying asset is represented with two different, inconsistent decimals values across code paths/token representations, and the raw balance amounts (which are always stored in undivided integer units, unaffected by `precision`) don't change — only the decimals metadata used by clients to render human-readable amounts diverges.

### Impact Explanation
`precision` is the token's decimals field used by wallets/exchanges/explorers to convert the raw integer balance into a human-displayed amount (analogous to ERC20 `decimals()`/ZCToken decimals). Because `GetAssetIssueByName` and `GetAssetIssueById` return different `precision` values (e.g., 6 vs. 0) for the exact same token when `AllowSameTokenName == 0`, any downstream consumer (wallet UI, exchange, DApp) that queries one endpoint vs. the other will compute the displayed balance/value incorrectly by a factor of up to 10^6 for the same raw on-chain amount. This is a state-divergence bug reachable by any unprivileged asset issuer and observable by any unprivileged API caller — it does not require special permissions, and directly causes divergent representations of on-chain state analogous to the reported finding's "users may think they received 1e18/1e6 times less than expected."

### Likelihood Explanation
Any unprivileged account can trigger this by issuing an asset with `AllowSameTokenName == 0` (the legacy/default mode) and a non-zero `precision` via `AssetIssueContract`/`createassetissue`. Any unprivileged client can then observe the divergence simply by calling `GetAssetIssueByName` vs. `GetAssetIssueById` (or the equivalent HTTP servlets) — both are publicly exposed, unauthenticated read endpoints. No race condition or special timing is required; the divergence is persisted permanently in the two separate LevelDB/RocksDB-backed stores.

### Recommendation
Ensure `precision` metadata is consistent between the V1 (`AssetIssueStore`) and V2 (`AssetIssueV2Store`) representations of the same asset. Either:
1. Do not force `precision = 0` on the V2 capsule in `AssetIssueActuator.execute()` — preserve the user-specified precision consistently across both stores, or
2. If V1-mode assets are intentionally meant to have precision 0 semantics, make all read paths (`getAssetIssueByName`, `getAssetIssueById`, and any others) consistently reflect that same semantic for a given `AllowSameTokenName` mode, rather than returning divergent values depending on which lookup API is used.
Add regression tests asserting that `GetAssetIssueByName` and `GetAssetIssueById` return identical `precision` for the same asset ID/name, across both `AllowSameTokenName` modes.

### Proof of Concept
1. With `AllowSameTokenName == 0` (default legacy mode), submit an `AssetIssueContract` transaction with `precision = 6` (max allowed) via `createassetissue`.
2. Query the asset via `GetAssetIssueByName` (`/wallet/getassetissuebyname`) — observe `precision: 6` (from V1 store, unmodified), matching test expectation at [9](#0-8) .
3. Query the same asset via `GetAssetIssueById` (`/wallet/getassetissuebyid`) using the ID returned in the issuance receipt — observe `precision: 0` (from V2 store, forcibly zeroed), matching test expectation at [10](#0-9) .
4. A client relying on `GetAssetIssueById`'s precision will render the identical raw balance as 10^6 times larger than a client relying on `GetAssetIssueByName`'s precision, for the exact same token and account balance.

  public AssetIssueContract getAssetIssueById(String assetId) {

      return null;
    }
    AssetIssueCapsule assetIssueCapsule = chainBaseManager.getAssetIssueV2Store()
        .get(ByteArray.fromString(assetId));
    if (assetIssueCapsule != null) {
      BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
      processor.updateUsage(assetIssueCapsule);

      return assetIssueCapsule.getInstance();
    } else {
      return null;
