### Title
Missing Chain-Specific Domain Separator in `DelegateAction` Signature Hash Enables Cross-Chain Replay of Meta Transactions — (`File: core/primitives/src/action/delegate.rs`, `core/primitives/src/signable_message.rs`)

---

### Summary

The `DelegateAction` (NEP-366 meta transaction) and `DelegateActionV2` (NEP-611 gas key) signed payload hashes are computed without any chain-specific identifier. The `SignableMessage` wrapper used to produce the NEP-461 hash contains only a fixed protocol-level `MessageDiscriminant` constant and the message body — no `chain_id`, genesis hash, or block hash. Because the same constant is used on every NEAR network (mainnet, testnet, any fork), a `SignedDelegateAction` signed by a user on one network can be submitted by any relayer on a different network where the same account and key exist, causing the user's actions to execute without their consent on the target chain.

---

### Finding Description

`DelegateAction::get_nep461_hash()` computes the signed hash as:

```rust
// core/primitives/src/action/delegate.rs:353-357
pub fn get_nep461_hash(&self) -> CryptoHash {
    let signable = SignableMessage::new(&self, SignableMessageType::DelegateAction);
    let bytes = borsh::to_vec(&signable).expect("Failed to deserialize");
    hash(&bytes)
}
```

`SignableMessage` is defined as:

```rust
// core/primitives/src/signable_message.rs:62-65
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}
```

The `discriminant` is a fixed constant derived from the NEP number (`1 << 30 + 366` for `DelegateAction`, `1 << 30 + 611` for `DelegateActionV2`). It is identical on every NEAR network. The signed payload therefore contains only:

- `discriminant` — a fixed u32 constant, same on all networks
- `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key` — all user-supplied fields

No `chain_id`, genesis hash, or block hash is included in the signed payload. The same applies to `VersionedDelegateActionPayload::get_nep461_hash()` for `DelegateActionV2`.

The outer `SignedTransaction` that wraps the `DelegateAction` does include a `block_hash` field that is chain-specific and validated by `check_transaction_validity_period`. However, this only binds the outer relayer's transaction to a specific chain. The inner `SignedDelegateAction` signature is not bound to any chain. A malicious relayer on a different network can construct a new outer `SignedTransaction` with a valid block hash from that network, wrapping the original `SignedDelegateAction` that was signed for a different network.

The runtime's `apply_delegate_action` verifies the signature and nonce but has no mechanism to detect cross-chain reuse:

```rust
// runtime/runtime/src/actions.rs:430-433
if !signed_delegate_action.verify() {
    result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
    return Ok(());
}
```

The `verify()` call only checks the signature against the chain-agnostic hash.

---

### Impact Explanation

An attacker (any party who obtains a `SignedDelegateAction`) can submit it on a different NEAR network where the same account and key exist. The inner actions execute with `sender_id` as the predecessor, meaning:

- Token transfers execute, draining the user's balance on the target chain
- Function calls execute on behalf of the user on the target chain
- Key additions or deletions execute on the user's account on the target chain

The user's funds and account state on the target chain are modified without their authorization. This is a direct unauthorized transaction and fund loss.

---

### Likelihood Explanation

The attack requires:

1. The same account ID to exist on both networks — highly likely for named accounts (e.g., `alice.near` on mainnet and `alice.testnet` are different, but NEAR implicit accounts are derived from the public key and are identical across all networks by construction)
2. The same public key to be registered as an access key on both networks — common for developers and users who reuse keys across mainnet and testnet
3. The nonce on the target chain to be lower than the nonce used in the signed `DelegateAction` — likely if the user is more active on mainnet than testnet
4. The `max_block_height` to not have been exceeded on the target chain — controllable by the attacker by acting promptly

NEAR implicit accounts (40-byte hex addresses derived from the public key) are particularly vulnerable because the same key produces the same account ID on every NEAR network, and the account is automatically created upon first funding.

---

### Recommendation

Include a chain-specific identifier in the `SignableMessage` payload. The most direct fix is to add the genesis hash (or chain ID string) to the signed data:

```rust
pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub chain_id: String,   // e.g., "mainnet", "testnet", or genesis hash bytes
    pub msg: &'a T,
}
```

Alternatively, include the genesis `CryptoHash` (available at runtime via `ApplyState`) in the `DelegateAction` struct itself, analogous to how `block_hash` is included in `Transaction`. This would be a protocol-level change requiring a new protocol version gate.

---

### Proof of Concept

1. Alice has account `alice.near` on mainnet and testnet with the same ED25519 key pair.
2. Alice signs a `DelegateAction` on mainnet to transfer 100 NEAR to Bob, with `nonce = 5` and `max_block_height = 200_000_000`.
3. The relayer submits it on mainnet. The action executes.
4. An attacker who observed the `SignedDelegateAction` (e.g., from the mainnet transaction) constructs a new outer `SignedTransaction` on testnet with a valid testnet `block_hash`, wrapping the same `SignedDelegateAction`.
5. On testnet, `apply_delegate_action` calls `signed_delegate_action.verify()`. The hash is `SHA256(discriminant_bytes || borsh(delegate_action))` — identical to the mainnet hash because neither the discriminant nor the `DelegateAction` fields contain any chain identifier.
6. Signature verification passes. The nonce check passes if testnet `ak_nonce < 5`. The `max_block_height` check passes if testnet height < 200_000_000.
7. Alice's testnet funds are transferred to Bob without Alice's consent.

The root cause is in `DelegateAction::get_nep461_hash()` at [1](#0-0)  and `VersionedDelegateActionPayload::get_nep461_hash()` at [2](#0-1) , both of which delegate to `SignableMessage` at [3](#0-2)  which contains no chain-specific field. The `MessageDiscriminant` is a fixed constant derived only from the NEP number [4](#0-3)  and is identical across all NEAR networks. The `DelegateAction` struct itself contains no chain identifier [5](#0-4) . The runtime verifier at [6](#0-5)  performs no cross-chain check. The outer transaction's `block_hash` binding [7](#0-6)  does not protect the inner delegate action signature.
