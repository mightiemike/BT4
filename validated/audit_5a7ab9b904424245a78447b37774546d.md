### Title
Historical `ledger_version` account queries derive the stateless-account fallback from current on-chain feature-flag state instead of the state at the requested version - (File: `api/src/accounts.rs`)

### Summary
`Account::account` in `api/src/accounts.rs` correctly fetches the `AccountResource` state value at the caller-supplied `self.ledger_version` [1](#0-0) , but when that lookup returns `None`, it decides whether to synthesize a stateless `AccountResource::new_stateless(...)` (sequence_number 0, address-derived key) by calling `self.context.feature_enabled(FeatureFlag::DEFAULT_ACCOUNT_RESOURCE)` with no version argument at all [2](#0-1) .

### Finding Description
`Account::new` resolves and stores `self.ledger_version` from the caller's `ledger_version` query parameter via `get_latest_ledger_info_and_verify_lookup_version` [3](#0-2) . Every other piece of account data in this struct (resource lookup, balance lookup, module lookup) is fetched at that pinned `self.ledger_version` [4](#0-3) . The stateless-account fallback path is the one exception: `feature_enabled` is invoked without passing `self.ledger_version`, so it necessarily reflects the current/latest on-chain `Features` resource rather than the `Features` resource as of the requested historical version. This means the branch that decides between "return `account_not_found`" and "synthesize a fake `AccountData`" is evaluated against a different point in history than the one the caller asked about.

### Impact Explanation
For a query pinned to a `ledger_version` prior to the activation of `DEFAULT_ACCOUNT_RESOURCE`, if the flag is enabled at the current/latest state, the endpoint will fabricate an `AccountData` (sequence_number 0, address-derived key) for an address that had no committed `AccountResource` at that historical version, instead of the correct `account_not_found`. This misbinds the authenticated response to the wrong point-in-time state: the API claims a specific `ledger_version`'s data, but the existence determination for that address is derived from the latest chain state, not that version.

This is scoped to the read/query path only — it does not corrupt the JMT, accumulator, transaction proofs, or write sets, and does not create validator-to-validator divergence (all synced full nodes see the same current feature-flag value and would behave identically), so there is no hard-fork-only divergence and no proof-material corruption. It falls under the narrower "authenticated API output bound to the wrong version" category rather than a committed-state or proof-integrity break.

### Likelihood Explanation
High likelihood of triggering under normal, unprivileged usage: any external caller can request `/accounts/{address}?ledger_version=N` with an address that never had a committed `AccountResource`, and the mismatch is deterministic once `DEFAULT_ACCOUNT_RESOURCE` is active. No special privileges are required.

### Recommendation
Evaluate `DEFAULT_ACCOUNT_RESOURCE`'s enabled/disabled status against the state at `self.ledger_version` (i.e., read the `Features` resource via a versioned state view at `self.ledger_version`) rather than via a version-agnostic `feature_enabled` call, so the stateless-account fallback decision is consistent with the same historical version used for the primary resource lookup.

### Proof of Concept
1. Pick an address with no committed `0x1::account::Account` resource at any point in its history.
2. Choose `ledger_version = N`, a version prior to the on-chain activation of `DEFAULT_ACCOUNT_RESOURCE`.
3. Ensure the feature is currently enabled at the latest ledger version (post-activation).
4. Call `GET /accounts/{address}?ledger_version=N`.
5. Observe that instead of `404 account_not_found` (the correct historical answer), the endpoint returns a synthesized `AccountData{sequence_number: 0, authentication_key: address}` because `feature_enabled` reflects the *current* flag state, not the flag state at version `N`.

Note: I was unable to inspect the implementation of `Context::feature_enabled` in `api/src/context.rs` (ran out of tool iterations), so I could not 100% confirm whether it internally uses latest state only or has some hidden version-awareness. The call site in `api/src/accounts.rs` takes no version parameter and is called separately from the properly-versioned `get_account_resource()`/`get_state_value_poem(..., self.ledger_version, ...)` calls elsewhere in the same file, which is strong circumstantial evidence for the described mismatch.
