### Title
Chain halt via panic in `receipt_filter_fn` when a stale `GlobalContractDistribution` receipt's `target_shard` cannot be resolved after multiple reshardings - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::pop` filters delayed receipts by shard using `receipt_filter_fn`, which calls `receiver_shard_id(&shard_layout).unwrap()` on every popped receipt [1](#0-0)  . For a `GlobalContractDistribution` receipt, `receiver_shard_id` returns `Err(EpochError::ShardingError(...))` when the receipt's `target_shard` no longer exists in the current shard layout *or* in its split history [2](#0-1)  . This is exactly the CVE's bug class: an entry with a "resource" that doesn't fully exist any more (the CXL region with no allocated address space) is not skipped/handled defensively during an ordering/filtering pass — instead the code assumes it can always be resolved and `unwrap()`s.

### Finding Description
A `GlobalContractDistribution` receipt records the `target_shard` it is heading to and travels shard-by-shard, being pushed to the delayed-receipt queue when its shard is congested [3](#0-2)  . If the receipt sits in the delayed queue across a resharding event, `receiver_shard_id` falls back to `shard_layout.resolve_to_current_shard(target_shard)` to remap the stale shard id to a current descendant [4](#0-3)  . This remap depends on the shard layout carrying full split-history metadata. The repository's own regression test documents that this remap is only reliable for V3 (dynamic-resharding) shard layouts — "With static resharding, the shard layout doesn't maintain a full split history" — and specifically exercises a receipt surviving *two* resharding generations to try to trigger the unwrap panic in `receipt_filter_fn` [5](#0-4)  . When `resolve_to_current_shard` returns `None`, `receiver_shard_id` returns an `Err`, and the unconditional `.unwrap()` inside `receipt_filter_fn` panics [6](#0-5)  .

The path is fully reachable by an ordinary account: any account can submit a `DeployGlobalContract` transaction to originate the distribution receipt [7](#0-6)  . Whether the receipt becomes delayed (congested shard) and survives across resharding boundaries is largely a timing/scheduling matter, not something requiring special privileges — a chunk producer or attacker can help engineer this by congesting the target shard and by timing deploys around scheduled resharding epochs.

### Impact Explanation
Because the delayed-receipt queue is popped deterministically by every validator applying the same chunk, a panic here is not a single-node crash but a **protocol-wide deterministic panic**: every honest node that reaches the same block height with the same delayed-receipt state will hit the same `.unwrap()` and crash, producing a chain halt (denial of service) rather than a benign single-node fault. This matches the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Triggering requires: (1) a `GlobalContractDistribution` receipt that becomes delayed on a shard, and (2) that shard undergoing resharding at least once (twice for the static-layout gap documented in the test) before the receipt is popped. This is a narrow but non-privileged, purely protocol-driven timing condition — no malicious validator, network, or operator behavior is required, only an ordinary global-contract deployment combined with the network's own resharding schedule.

### Recommendation
Change `receipt_filter_fn` to propagate the `Result` from `receiver_shard_id` instead of unwrapping, treating an unresolved target shard as inconsistent state (as is already done elsewhere for similar lookups, e.g. `StorageError::StorageInconsistentState`), or ensure static shard layouts also retain full split-history metadata so `resolve_to_current_shard` never returns `None` for any receipt that could plausibly still be delayed.

### Proof of Concept
The existing test `test_stale_global_contract_distribution_after_double_resharding` is itself a proof-of-concept repro path: it force-splits two shards sequentially so that a `GlobalContractDistribution` receipt's `target_shard` becomes unresolvable, then drains the delayed queue and asserts the chain does not stall [8](#0-7) [5](#0-4)  . The test is explicitly gated to only run without the `protocol_feature_spice` and explicitly notes it "only works with V3 shard layouts," implying the underlying `.unwrap()` in `receipt_filter_fn` remains a live hazard for static (non-V3) shard layouts, which are still the configuration path used by default/mainnet-style setups.

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}

fn forward_distribution_next_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    epoch_info_provider: &dyn EpochInfoProvider,
    state_update: &mut TrieUpdate,

) -> Result<(), RuntimeError> {
    let shard_layout = epoch_info_provider.shard_layout(&apply_state.epoch_id)?;
    let already_delivered_shards = BTreeSet::from_iter(
        global_contract_data
            .already_delivered_shards()
            .iter()
            .cloned()
            .chain(std::iter::once(apply_state.shard_id)),
    );
    let Some(next_shard) = shard_layout
        .shard_ids()
        .filter(|shard_id| !already_delivered_shards.contains(&shard_id))
        .next()

        return Ok(());
    };
    let already_delivered_shards = Vec::from_iter(already_delivered_shards);

    let next_receipt = global_contract_data.forward(next_shard, already_delivered_shards);
    let mut next_receipt = Receipt::new_global_contract_distribution(predecessor_id, next_receipt);
    let receipt_id = apply_state.create_receipt_id(receipt.receipt_id(), 0);
    next_receipt.set_receipt_id(receipt_id);
