Based on the investigation, java-tron's exchange actuators show a **split protection pattern** that maps directly to the reported bug class.

### Title
Missing slippage protection in `ExchangeWithdrawActuator` allows front-run loss of expected payout — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeTransactionActuator` (the TRON analog of a swap) already implements the exact mitigation the external report recommends: an `expected` minimum-output field checked against the computed output before executing the trade. [1](#0-0) [2](#0-1) 

However, `ExchangeWithdrawContract`/`ExchangeWithdrawActuator` — which converts a pool-share `quant` into a proportional amount of the "other" token based on the *live* pool ratio at execution time — has no equivalent `expected`/minimum field in its protobuf message or validation logic. [3](#0-2) [4](#0-3) 

### Finding Description
`ExchangeWithdrawActuator.execute` computes `anotherTokenQuant` from the exchange's current `firstTokenBalance`/`secondTokenBalance` at the moment the transaction is processed, using a simple proportional ratio (`bigSecondTokenBalance * bigTokenQuant / bigFirstTokenBalance`, or the inverse), not a value the caller pinned when they signed the transaction. [5](#0-4) 
`doValidate()` re-derives the same ratio-based `anotherTokenQuant` and only checks for pool-balance sufficiency and a fixed 0.0001 rounding-precision tolerance ("Not precise enough") — never a caller-supplied minimum acceptable amount. [6](#0-5) 

Because the ratio (`firstTokenBalance`/`secondTokenBalance`) is mutated by any `ExchangeTransactionContract` broadcast against the same `exchange_id` (an action open to any unprivileged account with sufficient balance/assets), an attacker can submit a large `ExchangeTransactionContract` trade immediately before the withdraw transaction is packed into a block, skewing the ratio unfavorably, then optionally reverse it afterward. The withdraw actuator has no way to detect or reject this — it simply accepts whatever ratio exists when it executes. This is the same root cause as the reported issue: a value-dependent settlement (a "swap"-like conversion) executed with no caller-specified minimum output, exposed to front-running/sandwiching by any anonymous broadcaster.

### Impact Explanation
The account that owns/created the exchange (`exchangeCapsule.getCreatorAddress()`, checked at line 181-183) can receive materially less of the counter-token than intended when withdrawing, with no recourse — an on-chain, irreversible loss of expected asset value once the transaction is confirmed. This is exchange/market-math accounting corruption of the type described in the report (loss of `payoutAmount`/expected proceeds due to missing slippage bound), even though only the exchange creator can call withdraw — the attacker triggering the front-run/sandwich is an unprivileged, anonymous account able to broadcast an ordinary `ExchangeTransactionContract`. [7](#0-6) 

### Likelihood Explanation
Exploitation only requires broadcasting a standard, unprivileged `ExchangeTransactionContract` against the target `exchange_id` timed shortly before the victim's withdraw is included in a block — no special permissions, no bugs in signature/permission checks needed, and TRON's public transaction pool/broadcast visibility gives attackers the needed timing window (analogous to standard front-running/MEV on any block-ordered chain).

### Recommendation
Add an `expected`-style minimum-output field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the withdrawal if the computed `anotherTokenQuant` falls below the caller-specified minimum, exactly as already done for `ExchangeTransactionActuator`. [2](#0-1) 

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` for `exchange_id = X`, `token_id = A`, `quant = Q` in the broadcast network.
2. Attacker submits an `ExchangeTransactionContract` on the same `exchange_id = X` that shifts the `firstTokenBalance`/`secondTokenBalance` ratio unfavorably for the withdrawer, and ensures it lands in an earlier block/position.
3. The victim's withdraw executes in `ExchangeWithdrawActuator.execute`, computing `anotherTokenQuant` from the now-skewed ratio (lines 79-89), yielding materially less of the counter-token than the victim expected when signing — with no `expected` field to prevent this, unlike `ExchangeTransactionActuator`. [5](#0-4)

      if (allowHarden) {
        BigDecimal remainder = bigSecondTokenBalance.multiply(bigTokenQuant)
            .divide(bigFirstTokenBalance, 4, RoundingMode.HALF_UP)
            .subtract(BigDecimal.valueOf(anotherTokenQuant));
        if (remainder.compareTo(

          throw new ContractValidateException("Not precise enough");
        }
      } else {
        double remainder = bigSecondTokenBalance.multiply(bigTokenQuant)
            .divide(bigFirstTokenBalance, 4, BigDecimal.ROUND_HALF_UP).doubleValue()

          throw new ContractValidateException("Not precise enough");
