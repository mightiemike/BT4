## Title
Replay-verify path silently accepts a locally-recomputed state root that diverges from the authenticated `TransactionInfo` - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by all "verify local re-execution against trusted chain data" call sites (chunk executor replay, `db-tool replay_on_archive`, the CLI's local transaction replay, and the Aptos debugger), only checks `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash` against the target `TransactionInfo`. It never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is the exact analog of the reported bug: a validation routine that checks *some* of the fields tying a result to its true binding context, but omits the field that actually proves the committed/replayed state is the correct one, letting divergent state pass verification.

### Finding Description
`ensure_match_transaction_info` is the single comparator used everywhere re-executed output is checked against an authenticated `TransactionInfo` (obtained from a signed `LedgerInfo`-backed accumulator proof, e.g. during backup/restore replay-verify or chunk-executor `verify_execution`): [1](#0-0) 

It explicitly checks `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event-root hash, but the trailing comment states the gap outright: [2](#0-1) 

The `TransactionInfoV1` (and V0) structures carry `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, all of which are part of the authenticated, accumulator-committed record for the transaction: [3](#0-2) 

These checkpoint hashes are the actual state-tree roots produced by `DoLedgerUpdate::assemble_transaction_infos` from separately computed state/hot-state/position checkpoints: [4](#0-3) 

Callers rely on `ensure_match_transaction_info` as the sole cross-check between locally re-executed output and the trusted target `TransactionInfo` in exactly the flows meant to catch commit/replay divergence:
- `execution/executor/src/chunk_executor/mod.rs` `verify_execution` (re-executes transactions from a chunk and validates against given `transaction_infos`/`write_sets`/`event_vecs`): [5](#0-4) 
- `storage/db-tool/src/replay_on_archive.rs`, which is specifically designed to replay historical chain data and flag divergence: [6](#0-5) 
- `aptos-move/cli/src/commands.rs` local transaction replay/verification: [7](#0-6) 

None of these call sites independently verify the checkpoint hashes; they all rely on `ensure_match_transaction_info`.

### Impact Explanation
This falls under "Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Authenticated API or state-view output bound to the wrong version, object, or proof context" from the state-integrity gate. If the VM/executor produces a state tree (regular Merkle state, hot state, or the new native "position" state introduced by `compute_trading_native_state_roots`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that diverges from the authenticated on-chain root — whether from a VM bug, non-determinism, or a malicious backup/replay data source supplying tampered checkpoint hashes bundled with correct write-sets/events — the verification tooling built specifically to catch this divergence (`replay_on_archive`, chunk-executor `verify_execution`, CLI replay) will report success. That silently masks a wrong committed state root reaching operators/auditors who depend on these tools to detect a hard fork or state-divergence bug before it propagates, which is a high-impact defect in the state-integrity verification chain itself.

### Likelihood Explanation
The gap is deterministic and always present (not a race or edge case): any invocation of `ensure_match_transaction_info` skips the three checkpoint-hash fields unconditionally, as evidenced by the code and its own TODO comment referencing the specific state-divergence scenario it fails to catch. Because these are exactly the code paths that exist to catch such divergences (replay-verify / restore-verify tooling), the practical likelihood of the check silently passing when it should fail is high whenever a checkpoint-hash-affecting bug exists — which is precisely the class of bug this tooling is meant to guard against.

### Recommendation
Extend `ensure_match_transaction_info` (or add a parallel check invoked at every call site) to compare the locally computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against the corresponding fields of the target `TransactionInfo`, sourcing the locally computed values from the same checkpoint pipeline used in `DoLedgerUpdate::assemble_transaction_infos`. This should be a required check before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, per the existing TODO.

### Proof of Concept
Not directly exploitable as a standalone PoC without a state-divergence-inducing VM bug already present; the demonstration would be:
1. Introduce (or trigger) any VM/executor bug that alters computed `state_checkpoint_hash` for a given transaction while `write_set`/`events`/`status`/`gas_used` remain unchanged (e.g. a bug in the position/native-state tree update).
2. Run `db-tool replay_on_archive` (or `chunk_executor::verify_execution`, or CLI replay) against archived on-chain data for that transaction.
3. Observe that verification reports success (`ensure_match_transaction_info` passes) despite the recomputed state root diverging from the authenticated chain state, because the checkpoint-hash fields are never compared.

I was unable to fully trace whether `verify_execution`'s output is also cross-checked elsewhere in the chunk-executor apply-to-ledger pipeline (e.g., a separate root-hash comparison during `commit`) before persisting to local storage, due to iteration limits on reading the surrounding `chunk_executor/mod.rs` code; this would affect whether the impact is "detection-tooling blind spot" only or also "wrong state actually persisted to local DB." I recommend a Devin session review that code path to confirm the full commit-time impact.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn assemble_transaction_infos(
        to_commit: &TransactionsWithOutput,
        transaction_info_v1: bool,
        state_checkpoint_hashes: &[Option<HashValue>],
        hot_state_checkpoint_hashes: Option<&[Option<HashValue>]>,
        position_state_checkpoint_hashes: Option<&[Option<HashValue>]>,
    ) -> (Vec<TransactionInfo>, Vec<HashValue>) {
        let _timer = OTHER_TIMERS.timer_with(&["assemble_transaction_infos"]);

        (0..to_commit.len())
            .into_par_iter()
            .with_min_len(optimal_min_len(to_commit.len(), 64))
            .map(|i| {
                let txn = &to_commit.transactions[i];
                let txn_output = &to_commit.transaction_outputs[i];
                let persisted_auxiliary_info = &to_commit.persisted_auxiliary_infos[i];
                // Use the auxiliary info hash directly from the persisted info
                let auxiliary_info_hash = match persisted_auxiliary_info {
                    PersistedAuxiliaryInfo::None => None,
                    PersistedAuxiliaryInfo::V1 { .. } => {
                        Some(CryptoHash::hash(persisted_auxiliary_info))
                    },
                    PersistedAuxiliaryInfo::TimestampNotYetAssignedV1 { .. } => None,
                };
                let state_checkpoint_hash = state_checkpoint_hashes[i];
                let event_hashes = txn_output
                    .events()
                    .iter()
                    .map(CryptoHash::hash)
                    .collect::<Vec<_>>();
                let event_root_hash =
                    InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash();
                let write_set_hash = CryptoHash::hash(txn_output.write_set());
                let status = txn_output
                    .status()
                    .as_kept_status()
                    .expect("Already sorted.");
                let txn_info = if transaction_info_v1 {
                    TransactionInfo::builder_v1()
                        .transaction_hash(txn.committed_hash())
                        .state_change_hash(write_set_hash)
                        .event_root_hash(event_root_hash)
                        .maybe_state_checkpoint_hash(state_checkpoint_hash)
                        .maybe_hot_state_checkpoint_hash(
                            hot_state_checkpoint_hashes.and_then(|hot| hot[i]),
                        )
                        .gas_used(txn_output.gas_used())
                        .status(status)
                        .maybe_auxiliary_info_hash(auxiliary_info_hash)
                        .maybe_position_state_checkpoint_hash(
                            position_state_checkpoint_hashes.and_then(|p| p[i]),
                        )
                        .build()
                } else {
                    TransactionInfo::builder_v0()
                        .transaction_hash(txn.committed_hash())
                        .state_change_hash(write_set_hash)
                        .event_root_hash(event_root_hash)
                        .maybe_state_checkpoint_hash(state_checkpoint_hash)
                        .gas_used(txn_output.gas_used())
                        .status(status)
                        .maybe_auxiliary_info_hash(auxiliary_info_hash)
                        .build()
                };
