### Title
Sequencer permanently removes failed Bitcoin deposits from the mempool without crediting cBTC, breaking the deposit↔mint binding - (File: `crates/sequencer/src/runner.rs`)

### Summary
The sequencer's L2 block production pipeline fetches a batch of pending Bitcoin deposits, attempts to apply each one as a system transaction, but then unconditionally removes the *entire original batch* from the deposit mempool after block production — even for deposits whose system transaction reverted and was therefore excluded from the produced block. This mirrors the ZetaChain M-23 bug class: an operation is marked "processed/refunded/complete" regardless of whether the underlying value-moving action actually succeeded, resulting in silent loss of user funds with no way to retry.

### Finding Description
`produce_l2_block_inner` fetches a fixed set of pending deposits from the mempool before block production: [1](#0-0) 

This same `deposit_data` slice is passed into system transaction processing. Inside `process_sys_txs`, each deposit is applied as a system transaction inside a revertable checkpoint; if the transaction fails with `EvmSystemTransactionNotSuccessful` (i.e., the on-chain `Bridge.deposit()` call reverted), the working set is rolled back, the nonce is decremented, and the loop simply `continue`s — the failed deposit is **not** added to `all_txs` and is therefore never included in the produced L2 block: [2](#0-1) 

Despite this, after the block is finalized and saved, the sequencer calls `remove_deposits(&deposit_data)` using the **original, unfiltered** `deposit_data` fetched before dry-run/production — not the subset that actually succeeded and was included in `all_txs`: [3](#0-2) 

`remove_deposits` simply deletes every entry whose txid is in the passed list from `accepted_deposit_txs`/`pending_deposits`, with no cross-check against which deposits were actually minted in the block: [4](#0-3) 

On the Bitcoin/L1 side, the deposit is real: the user locked BTC in the N-of-N-controlled UTXO and the `moveTx` was included in a Bitcoin block, i.e., `Bridge.LIGHT_CLIENT` will (eventually) attest to its inclusion. On the Citrea side, `Bridge.deposit()` can legitimately revert for reasons that do not reflect the deposit's invalidity, e.g., the contract being paused (`whenNotPaused` modifier) via the `pause()`/`unpause()` operator controls, or a duplicate submission racing with a previous successful process of the same txId (`require(!processedTxIds[txId], ...)`): [5](#0-4) 

In all such cases, once `process_sys_txs` reverts the failed deposit's system transaction and moves on, the sequencer nonetheless treats that deposit as "handled" by purging it from the deposit mempool in the unconditional `remove_deposits(&deposit_data)` call. There is no retry path shown in this code: once purged from `accepted_deposit_txs`, the deposit is gone from the mempool's bookkeeping, and no subsequent `fetch_deposits` call will ever offer it again. This breaks the fundamental rollup binding: cBTC credited on Citrea must equal the set of genuine BTC deposits that occurred on L1. Here, a genuine L1 deposit is dropped from consideration forever while never being minted.

### Impact Explanation
This is a Critical-class binding violation per the scan's own rubric: "cBTC minted, credited or moved without a matching Bitcoin-side deposit" — the inverse direction also applies and is captured by the same underlying invariant break: a Bitcoin-side deposit occurs but is never credited and can never be resubmitted, because the bookkeeping incorrectly marks it as processed. This is a permanent loss-of-funds condition for the affected depositor with no admin-level recovery mechanism evident in this code path (unlike ZetaChain's `MsgRefundAbort`, there is no equivalent "retry deposit" RPC shown operating on mempool-purged deposits).

### Likelihood Explanation
This requires no attacker action — it is triggered by ordinary operational conditions reachable by an unprivileged depositor: e.g., the operator briefly pausing the Bridge contract (a normal, documented operational control) while deposits are in-flight in the sequencer's mempool, or a race between deposit resubmission and a prior successful application of the same txId. Given the mempool-fetch/apply/remove flow processes deposits in batches every block, any deposit whose system tx fails for a transient reason during the exact block it's picked up is unconditionally and silently dropped.

### Recommendation
Track which deposits were actually included/succeeded (e.g., the `all_txs` set derived from successful `is_deposit` events with their originating `Deposit` value) and pass only that successfully-applied subset to `remove_deposits`. Deposits whose system transaction reverted should remain in the mempool (or be explicitly requeued/flagged) so they can be retried in a future block, mirroring the fix pattern from the referenced report: only mark/remove state as "processed" when the underlying credit actually succeeded.

### Proof of Concept
1. A user submits a valid Bitcoin deposit; the `moveTx` is relayed and queued in the sequencer's `DepositDataMempool`.
2. Before the sequencer applies it, the Bridge operator calls `pause()` on `Bridge.sol` (a normal operational action, not requiring the depositor's or an attacker's cooperation) — see the `whenNotPaused` modifier on `deposit()`: [6](#0-5) 
3. `produce_l2_block_inner` fetches this deposit via `fetch_deposits` and attempts to apply it in `process_sys_txs`; the call reverts with `EvmSystemTransactionNotSuccessful` because the contract is paused, so the working set is reverted and the loop `continue`s, excluding the deposit from the block: [7](#0-6) 
4. After block production, `remove_deposits(&deposit_data)` is called with the full original fetched list (including the failed deposit), purging it from the mempool: [3](#0-2) 
5. The user's BTC remains locked on L1 (moveTx confirmed), but the deposit record is gone from the sequencer's mempool and is never retried — cBTC is never minted for a Bitcoin deposit that genuinely occurred.

    #[instrument(level = "trace", skip_all, ret)]
    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }
