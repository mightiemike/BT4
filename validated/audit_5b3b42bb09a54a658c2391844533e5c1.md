Confirmed vulnerability path: `socialize-debt` in the vault contracts writes down `lindex` directly (a non-time-based mutation of the value that `market.clar`'s `index-cache` is supposed to memoize), and `market.clar`'s `liquidate` explicitly refreshes its cache for that one call site — but no other code path that reads `index-cache` within the same transaction/block is guaranteed to see the refreshed value if it read the cache *before* the write-down.

### Title
Stale `index-cache` liquidity index used for price/notional resolution after `socialize-debt` write-down within the same block - ([File: local-testing/contracts/market/market.clar])

### Summary
`market.clar` memoizes each vault's `{index, lindex}` per `{timestamp: stacks-block-time, aid}` in `index-cache` to save cross-contract calls [1](#0-0) . This cache is documented as being invalidated purely by block-timestamp change, on the assumption that `index`/`lindex` only move with time [2](#0-1) . That assumption is false: `socialize-debt` in every vault contract writes down `lindex` immediately and non-time-proportionally as soon as bad debt is socialized [3](#0-2) . `market.clar`'s own `socialize-debt-asset` helper is aware of this and manually re-primes the cache immediately after calling `vault-socialize-debt` [4](#0-3) , which proves the source can move mid-block/mid-transaction and that the general per-timestamp cache-invalidation model is insufficient — the fix is applied at exactly one call site.

### Finding Description
1. `accrue-and-cache` is a `map-get?`-then-`map-set` memoization keyed by `{timestamp: stacks-block-time, aid}` [1](#0-0) .
2. `resolve-ztoken`, used for all zToken price resolution (collateral valuation), reads this cache via `get-cached-indexes` and trusts it without re-checking the vault [5](#0-4) .
3. `liquidate` populates the cache once at the start (`accrue-user-debts`/`accrue-user-collateral`) and then reuses that cached snapshot for the whole rest of the function to compute LTV, liquidation amounts, and — later — the `remaining-debt-to-repay` calc, which itself calls `get-cached-indexes debt-aid` again [6](#0-5) .
4. Only if the liquidation zeroes out the borrower's collateral does `liquidate` invoke `socialize-debt-asset`, which calls `vault-socialize-debt` and then manually `map-set`s the refreshed indexes back into `index-cache` [7](#0-6) .
5. `liquidate-multi` folds `call-liquidate` over a list of positions in one atomic transaction, all sharing `stacks-block-time` [8](#0-7)  (approx). If liquidation #1 for debt-asset `X` triggers `socialize-debt-asset` (bad debt), `lindex` for `X` is written down and the cache entry for `{timestamp, X}` is correctly refreshed for that key at that moment. But any other in-flight state — e.g. `get-cached-indexes` values already destructured into local `let` bindings earlier in a *still-executing* `liquidate` call for a different borrower sharing debt-asset `X` — retain the pre-writedown value for the remainder of that call, since Clarity evaluates `let` bindings once at entry and does not re-read `map-get?` sources later in the same function body unless explicitly coded to (as `socialize-debt-asset` does for its own call, but callers "above" it in the same `let` do not).
6. More generally, the whole caching contract is: "index only changes with the timestamp." `socialize-debt` breaks that contract for `lindex` by mutating it outside of time-based accrual. Every read site of `index-cache`/`get-cached-indexes` other than the one inside `socialize-debt-asset` implicitly relies on the broken assumption.

### Impact Explanation
If a subsequent zToken-collateral valuation or liquidation math within the same block/transaction reads a not-yet-invalidated `lindex` (pre-writedown, i.e., too high) for an asset that just had bad debt socialized against it, that stale higher liquidity index causes zToken collateral to be over-valued in USD terms for other users' health/liquidation calculations evaluated in the same block. Over-valued collateral can let an actually-liquidatable position with zToken collateral evade `liquidate`'s health check (`ERR-HEALTHY`), or let a borrower with zToken collateral borrow beyond what true collateral value supports before the index catches up next block — this stalls proper liquidation and risks protocol insolvency / permanently frozen unclaimed yield for lenders. This lands on the in-scope Critical/High impact classes (protocol insolvency, temporary freezing of funds) rather than a purely academic issue, because `lindex` is directly consumed for zToken pricing via `resolve-ztoken`.

### Likelihood Explanation
This requires: (a) a position with zero remaining collateral against a specific debt asset getting liquidated (triggering `socialize-debt-asset`) in the same transaction/block as (b) another operation valuing zToken collateral backed by the same vault. `liquidate-multi` makes (a)+(b) trivially composable by a single caller in one atomic batch, and any other transaction landing in the same block (same `stacks-block-time`) as a bad-debt liquidation is a second, less-controllable avenue. Given `liquidate-multi` is explicitly designed to batch heterogeneous positions/assets in one call, the likelihood of hitting this ordering is moderate — it is a realistic sequencing bug, not purely theoretical, though it needs a bad-debt event to actually occur.

### Recommendation
Do not treat `index-cache` as valid based on timestamp alone. Either (a) invalidate/re-fetch the cache entry for an asset immediately whenever `socialize-debt` is invoked and force every subsequent `let`-bound consumer within the same call graph to re-read via `get-cached-indexes` rather than carrying forward already-destructured values, or (b) make `lindex` write-downs from `socialize-debt` also bump a per-asset "epoch"/version counter that is included in the cache key, so any stale in-memory reference from before the write-down is provably distinguishable from the fresh one, or (c) simplest: in `liquidate-multi`/`liquidate`, disallow subsequent zToken valuation reads of an asset's cache within the same transaction after any `socialize-debt-asset` call touches that asset — i.e., recompute notional values for all remaining positions in the batch after any bad-debt socialization event rather than relying on values computed earlier in the same fold.

### Proof of Concept
1. Set up two borrowers, Alice and Bob, each borrowing debt-asset `USDC` (aid `USDC`), with Alice's position backed by zSTX collateral and Bob's position backed entirely by `USDC`-vault-adjacent collateral that will be fully liquidated to zero.
2. Craft a `liquidate-multi` call with two entries: position 1 = Bob (whose liquidation results in `no-collateral-left = true`, triggering `socialize-debt-asset` for `USDC`, writing down `lindex` for the `USDC` vault) and position 2 = Alice's zSTX-collateralized position valued via `resolve-ztoken` against a zSTX vault that itself borrowed liquidity partly represented via the `USDC` lindex chain (or, more directly, any borrower whose collateral is `zUSDC`, i.e., a zToken directly wrapping the `USDC` vault).
3. Order the fold so Bob's liquidation (which stales the cache going stale->fresh via socialize) happens first, but structure Alice's liquidation call such that her collateral valuation (`resolve-ztoken` for `zUSDC`) was already computed/cached in `accrue-and-cache` for `{timestamp, USDC}` earlier in Alice's own `let` bindings before Bob's socialize-debt executes in the same `liquidate-multi` fold pass — this requires calling `liquidate` for Alice's position ordering ahead of, or interleaved by prior accrual calls with, Bob's in the same block/tx via two separate calls sharing `stacks-block-time` (e.g. Alice's collateral-add or borrow call executed as part of a broader multi-call transaction, immediately followed inside the same block by Bob's liquidation via a different transaction from the same block, both hitting the same `{timestamp, USDC}` cache key).
4. Verify (in `local-testing`) that Alice's zUSDC collateral valuation used in her own health check reflects the pre-writedown `lindex`, i.e., her collateral is valued higher than the vault's post-socialization NAV would justify, letting her either avoid liquidation she should be subject to, or borrow more than truly-backed collateral allows, within that same block.

Note: fully exercising this PoC end-to-end (constructing the exact block-timestamp collision and vault balances to reproduce measurable stale-cache pricing) requires running the `local-testing` Clarinet/Clarigen test harness, which I could not execute in this read-only analysis; the code-level root cause (cache invalidation contract violated by `socialize-debt`'s non-time-based `lindex` write-down, with only one of several read sites patched) is confirmed directly from source at the cited locations.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)

            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))

            (unwrap! (contract-call? .market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
