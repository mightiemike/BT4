### Title
`ExchangeTransactionActuator` trusts `ExchangeCapsule.transaction()` result without validating resulting balances in the default (non-hardened) path - (`chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The externally reported bug is a class of issue where a state-changing helper function can return a value under an edge condition (e.g. "no items left") without reverting, and the caller (`mintFromFixedPriceSale`) unconditionally treats the return as success and moves funds/state anyway. The closest analog in java-tron is `ExchangeCapsule.transaction()`, which is called by both `ExchangeTransactionActuator.doValidate()` and `ExchangeTransactionActuator.execute()` [1](#0-0) [2](#0-1) . This function computes an exchanged quantity and mutates the pool balances, but only validates the resulting balances for non-negativity when the "hardened" calculation path is used; the default (legacy) path silently accepts whatever the bonding-curve math produces.

### Finding Description
`ExchangeCapsule.transaction()` computes `buyTokenQuant` via a `Processor` (either the legacy `ExchangeProcessor` or, when `hardenedCalc` is true, `SafeExchangeProcessor.INSTANCE`), then updates `newFirstTokenBalance`/`newSecondTokenBalance` and commits them into the capsule [3](#0-2) . Critically, the negative-balance sanity check is gated behind `hardenedCalc`:

```
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [4](#0-3) 

In the default (non-hardened) mode — i.e. whenever `allowHarden()`/`AllowHardenExchangeCalculation` is not enabled — this guard never executes, so `transaction()` will return a `buyTokenQuant` and commit updated balances even if the legacy `ExchangeProcessor` bancor-style math produces a quantity that drives a pool balance negative or otherwise inconsistent with actual reserves. Both `ExchangeTransactionActuator.doValidate()` [5](#0-4)  and `execute()` [6](#0-5)  only check `anotherTokenQuant < tokenExpected` (i.e., the trader receives at least what they expect) — they never check that the exchange's underlying reserve can actually cover `anotherTokenQuant`, relying entirely on `transaction()` to enforce that invariant. Since the enforcement is conditional on `hardenedCalc`, the default code path is exactly the "helper returns without reverting on an invalid/edge condition, and caller blindly proceeds to move funds" pattern described in the report.

### Impact Explanation
If the legacy `ExchangeProcessor` math (bancor/relay-token formula) can, for certain balance/quantity edge cases (e.g., extreme quant relative to pool balance, or near-exhausted reserves — analogous to "the last token has been minted"), yield a `buyTokenQuant` that exceeds the true available reserve, `execute()` will still call `accountCapsule.addAssetAmountV2(anotherTokenID, anotherTokenQuant, ...)` and commit the exchange capsule with a negative or corrupted balance, effectively minting/crediting tokens the exchange doesn't own. This is an asset/accounting corruption vector in exchange market math, reachable by any user broadcasting an `ExchangeTransactionContract` transaction — no privileged actor needed.

### Likelihood Explanation
Moderate/uncertain. Reachability is confirmed (any account can create an `ExchangeTransactionContract`), and the code path (default, non-hardened calculation) is the standard path unless the `AllowHardenExchangeCalculation` proposal is active on the network. However, I was not able to fully inspect `ExchangeProcessor.exchange()`'s exact math within the available tool budget to confirm a concrete input that produces a negative resulting balance under the legacy formula (double-based bancor curve) — this would require deeper analysis or fuzzing of `ExchangeProcessor` to construct a concrete PoC transaction.

### Recommendation
Move the non-negative balance check in `ExchangeCapsule.transaction()` out of the `hardenedCalc`-only branch so it applies unconditionally, and add an explicit check in `ExchangeTransactionActuator` that `anotherTokenQuant` does not exceed the current reserve balance of `anotherTokenID` before committing the trade, regardless of which calculation mode is active.

### Proof of Concept
Not fully constructed — a concrete PoC requires finding specific `firstTokenBalance`/`secondTokenBalance`/`sellTokenQuant` inputs for which `ExchangeProcessor.exchange()` returns a `buyTokenQuant` large enough to drive the opposing balance negative under the legacy (non-hardened) formula; this needs further numerical analysis of `ExchangeProcessor.java`, which could not be completed within the available investigation.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();
