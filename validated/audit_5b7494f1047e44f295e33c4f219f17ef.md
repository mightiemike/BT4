## Analog Found

### Title
Panic-inducing `.unwrap()` on stale cross-shard receipt resolution causes a transaction-triggered chunk/chain halt - (`runtime/runtime/src/congestion_control.rs`)

### Summary
The Convex report's root cause is a hard assumption ("every reward token has `totalSupply()`") that fails for one class of input (stash tokens) and reverts the whole batch instead of degrading gracefully. The nearcore analog is `DelayedReceiptQueueWrapper::receipt_filter_fn`, which assumes every delayed `GlobalContractDistribution` receipt's `target_shard` is always resolvable in the current shard layout and calls `.unwrap()` on that assumption. When the assumption fails — a receipt has been delayed across shard-layout changes whose split history is not fully retained (legacy V0/V1/V2 static-resharding layouts, explicitly documented as unfixed) — the `.unwrap()` panics while draining the delayed-receipt queue for an entire chunk, rather than failing just that one receipt.

### Finding Description
`receipt_filter_fn` unconditionally unwraps the result of `receiver_shard_id`: [1](#0-0) 

`receiver_shard_id` for a `GlobalContractDistribution` receipt returns `Err(EpochError::ShardingError(...))` if the receipt's `target_shard` cannot be resolved forward to a shard in the current layout: [2](#0-1) 

Resolution is delegated to `ShardLayout::resolve_to_current_shard`, which is only fully cumulative (walks the entire split history) for `ShardLayoutV3`; for `V0`/`V1`/`V2` it only looks one generation back via `get_children_shards_ids`: [3](#0-2) 

The V3 implementation is fully recursive over the accumulated `shards_split_map` and was specifically hardened/tested for two-generation resharding: [4](#0-3) 

A dedicated regression test acknowledges this fix is scoped to V3 only and explicitly states the pre-V3/static path is unprotected: [5](#0-4) [6](#0-5) 

So the same bug class as the Convex report exists structurally: a per-item check inside a batch (`DelayedReceiptQueueWrapper::pop`, draining the shard's delayed receipt queue) assumes a property (shard resolvability) universally holds, and reverts/panics the whole operation when it does not — for exactly the code path (legacy static shard-layout history) the codebase's own comments admit is not covered by the fix.

### Impact Explanation
`receipt_filter_fn` executes inside `DelayedReceiptQueueWrapper::pop`, which is called every chunk while draining the delayed-receipt backlog: [7](#0-6) 

A panic there aborts `Runtime::apply` for the shard, which every honest validator executes identically for the same input — this is a transaction/receipt-triggered halt of chunk application (not a peer-only, sync-only, or malicious-validator-only condition), matching the accepted "transaction-triggered halt" impact class.

### Likelihood Explanation
`GlobalContractDistribution` receipts are created by an ordinary, unprivileged `DeployGlobalContract` action available to any signer; any user submitting such a transaction seeds a receipt whose `target_shard` is a plain field forwarded shard-by-shard. If that receipt is delayed (e.g., via congestion, which any user can also help induce by submitting enough load) across shard-layout transitions that do not retain full split history (legacy static V0/V1/V2 shard-layout epochs, which remain part of the supported protocol-version bootstrap/upgrade path), `resolve_to_current_shard` returns `None`, `receiver_shard_id` returns `Err`, and the `.unwrap()` in `receipt_filter_fn` panics. This requires no validator/network compromise — only an ordinary transaction plus the chain's own scheduled resharding history, consistent with the rules' allowed threat model (unprivileged transaction signer / RPC-reachable action).

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` with graceful error propagation (return `Result` from `pop`/the iterator instead of panicking), and extend `ShardLayout::resolve_to_current_shard` for `V0`/`V1`/`V2` layouts to walk the full historical split chain (or reject/garbage-collect genuinely orphaned `GlobalContractDistribution` receipts) instead of assuming a single-generation lookup always succeeds — mirroring the fix already applied for `ShardLayoutV3`.

### Proof of Concept
1. Bootstrap (or replay) a chain that undergoes two static shard-layout transitions (pre-`DynamicResharding`, i.e., `V0`/`V1`/`V2` layouts) such that a shard's `target_shard` ancestry spans both transitions.
2. Any user submits a `DeployGlobalContract` transaction from an account on the shard being split first; this creates a `GlobalContractDistribution` receipt with `target_shard` = the shard about to be split.
3. Induce enough congestion/backlog (ordinary large receipts/transactions any user can submit) so the receipt sits in the delayed queue across the second shard split.
4. When the delayed queue is drained (`DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn`), `receiver_shard_id` cannot resolve the doubly-stale `target_shard` for the legacy layout (`resolve_to_current_shard` only checks one generation), returns `Err`, and the `.unwrap()` panics, aborting `apply` for every validator processing that chunk — halting the shard.

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    /// For V3 layouts this uses the complete `shards_split_map`.
    /// For older layouts it falls back to `get_children_shards_ids` (single generation only).
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {

            Self::V0(_) | Self::V1(_) | Self::V2(_) => {
                self.get_children_shards_ids(shard_id).map(|c| c[0])

            Self::V3(v3) => v3.resolve_to_current_shard(shard_id),
        }
    }

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }
