### Title
Transfers to a `0u` Universal Account whose `UniversalStateInit` preimage is unknown or unreachable permanently freeze the deposited balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
NEAR's `UniversalAccount` (`0u...`) scheme lets a `Transfer` action create an uninitialized account at an address derived as SHA3‑256 of an arbitrary `RawStateInit` byte string, before any `UniversalStateInitAction` is ever submitted. Once such an account exists in the `Uninitialized` state, the *only* actions the runtime accepts on it are further `Transfer`s and a `UniversalStateInitAction` whose `derive_universal_account_id(state_init)` exactly matches the account id. If nobody ever submits (or can ever reconstruct) the exact raw bytes that hash to that id, the account can never transition to `Initialized`, and the balance sent to it is permanently unrecoverable — the same class of stuck-funds bug as the original `depositFor(address(0))` report, but reachable purely through NEAR's own account-derivation/transfer semantics.

### Finding Description
`action_implicit_account_creation_transfer` creates a bare, uninitialized `Account::new_uninitialized` for any `UniversalAccount`-typed id the moment it receives a `Transfer`, without requiring a matching `UniversalStateInit` to exist yet: [1](#0-0) 

`check_account_existence` explicitly allows this creation-by-transfer (`implicit_creation_allowed` returns `true` unconditionally for `AccountType::UniversalAccount`, without even requiring the transfer to be the receipt's only action): [2](#0-1) 

Once created and uninitialized, every action other than `Transfer` and `UniversalStateInit`/`DeterministicStateInit` is rejected with `AccountNotInitialized`: [3](#0-2) 

The only path to `Initialized` is `UniversalStateInitAction`, whose receiver must equal the SHA3‑256-derived id of the *exact raw bytes supplied on-chain*: [4](#0-3) [5](#0-4) 

The host-function documentation itself states the consequence plainly: any byte string maps to some `0u` id, and "a string that is not a well-formed state init maps to an account that can never be initialized": [6](#0-5) 

This is a real, protocol-verified scenario, not merely a hypothetical: an integration test funds the canonical all-zero-hash id `0u000...0` (for which, by construction, no `UniversalStateInit` preimage is realistically obtainable) and documents that "the account can never leave the uninitialized state": [7](#0-6) 

Critically, the id derivation is over the *exact raw bytes*, not the logical/decoded value: two producers who intend to write the "same" `UniversalStateInit` (e.g., differing only in `BTreeMap` iteration order across differing client/library serializers) derive two different `0u` ids, and a `Transfer` sent to the id computed from one encoding cannot ever be initialized by state-init bytes that hash to the other: [8](#0-7) [9](#0-8) 

### Impact Explanation
Any transaction signer, relayer, or contract using `Promise`-batch actions can send a `Transfer` to a `0u` account id for which the corresponding `RawStateInit` is unknown, lost, or was computed with a different (non-canonical) serialization than what will ever be submitted on-chain. The funds land in a real, chain-recorded account balance that is provably unrecoverable: no key exists to sign from it, no contract exists to call from it, and no other action is permitted until an exact-byte-matching `UniversalStateInitAction` arrives — which by SHA3-256 preimage resistance (for garbage/mistyped ids) or serialization mismatch (for legitimate but non-canonical producers) will never happen. This is a concrete "permanently frozen funds" outcome directly reachable from an unprivileged transaction/RPC path.

### Likelihood Explanation
Likelihood is realistic rather than purely theoretical:
- A user or wallet can mistype/misconstruct a `0u` address, or copy a stale/corrupted `RawStateInit` byte blob, and fund the wrong derived id — analogous to fat-fingering `address(0)` in the original report, but here the "zero address" equivalent (`0u000...0` and any other id lacking a known preimage) is a first-class, protocol-legal account type.
- Different SDKs/relayers/contracts serializing "the same" `UniversalStateInit` non-canonically (proven possible by `test_derive_universal_account_id_is_over_raw_bytes`) will derive different ids from what another party expects, so a `Transfer` sent based on one party's derivation can be permanently orphaned relative to the `UniversalStateInitAction` the other party later submits.
- The runtime performs no sanity check (e.g., no minimum "escrow" period, no way to reclaim via `DeleteAccount`, no fallback ownerless-account sweep) before permanently locking a `Transfer`'s deposit into an uninitialized universal account.

### Recommendation
Consider one or more of:
- Require that a `Transfer` targeting a not-yet-existing `UniversalAccount` id be accompanied (in the same receipt/batch, similar to the `is_the_only_action` gate used for other implicit kinds) by a `UniversalStateInitAction` whose derived id matches, so that an account is never created purely speculatively without its state init being simultaneously proven reachable.
- Alternatively, add an explicit, cheap on-chain/off-chain verification/warning path (e.g., a view-only "is this UAID derivable from data you hold" check surfaced prominently in wallets/SDKs) and/or a protocol-level timeout/refund-to-sender mechanism for `Transfer`-only funded, never-initialized `0u` accounts after some grace period, so mistakenly or non-canonically funded ids are not perpetually and irrecoverably locked.
- Standardize and enforce canonical serialization for `RawStateInit` at the SDK level shared across all first-party tooling to eliminate the "same logical state init, different id" class entirely.

### Proof of Concept
1. An attacker or well-meaning-but-buggy relayer computes (or fabricates) a `RawStateInit` byte string whose SHA3-256 hash encodes to some `0u...` id, e.g. the canonical all-zero-hash `0u0000000000000000000000000000000000000000000000000000` (see `core/primitives-core/src/universal_account_id.rs` KATS, all-zero vector).
2. A `Transfer` (e.g., via `SignedTransaction::send_money`) is sent to that id. `check_account_existence`/`implicit_creation_allowed` permit the transfer to create the account uninitialized (`runtime/runtime/src/actions.rs:936-946`, `276-282`).
3. The account now holds the deposited balance in `AccountState::Uninitialized`, exactly as demonstrated by `test_dump_state_with_uninitialized_universal_account` (`integration-tests/src/tests/tools/state_dump.rs:589-623`), whose own comment states the account "can never leave the uninitialized state."
4. No `UniversalStateInitAction` whose raw bytes hash to that specific id can realistically be produced (preimage resistance for the zero/garbage case, or a serialization mismatch for the "same logical value, different bytes" case per `test_derive_universal_account_id_is_over_raw_bytes`).
5. `check_account_existence` continues to reject every other action (`AddKey`, `DeployContract`, `FunctionCall`, `DeleteAccount`, etc.) with `AccountNotInitialized` (`runtime/runtime/src/actions.rs:857-889`), so the deposited balance is permanently stuck with no path to withdrawal.

/// A state init whose borsh is valid but is not what the typed form would write:
/// the storage entries are in descending key order, which borsh accepts and
/// re-sorts on decode. Hand-assembled, since the typed API cannot express it.
fn non_canonical_state_init(public_key: &PublicKey) -> RawStateInit {
    let mut bytes = vec![
        0, // V1
        0, // code: None
    ];
    bytes.extend_from_slice(&2u32.to_le_bytes()); // data: 2 entries, descending
    for (key, value) in [(b"b", b"2"), (b"a", b"1")] {
        bytes.extend_from_slice(&1u32.to_le_bytes());
        bytes.extend_from_slice(key);
        bytes.extend_from_slice(&1u32.to_le_bytes());
        bytes.extend_from_slice(value);
    }
    bytes.extend_from_slice(&1u32.to_le_bytes()); // access_keys: 1
    let handle = PublicKeyHandle::from(public_key.clone());
    bytes.extend_from_slice(&borsh::to_vec(&handle).expect("borsh must not fail"));
    RawStateInit(bytes)
}

/// The account created is the one derived from the bytes the sender serialized,
/// not from re-encoding the struct they decode to. Two encodings of the same
/// logical state init are two different accounts, which is what lets a producer
/// whose serializer does not sort `BTree*` containers still address its account.
#[test]
fn test_universal_state_init_derives_from_supplied_bytes() {
    init_test_logger();
    let mut env = Env::setup();

    let public_key = SecretKey::from_seed(KeyType::ED25519, "uaid-non-canonical").public_key();
    let raw = non_canonical_state_init(&public_key);

    // Without this the test proves nothing: it has to be an encoding the typed
    // form would not have written.
    let decoded = UniversalStateInit::from_raw(&raw).expect("fixture must be valid borsh");
    assert_ne!(decoded.to_raw().0, raw.0, "fixture must be non-canonical");

    let from_supplied = derive_universal_account_id(&raw);
    let from_re_encoding = decoded.derive_account_id();
    assert_ne!(from_supplied, from_re_encoding, "the two encodings must derive different ids");

    env.create_universal_account(raw, &from_supplied, Balance::from_near(1));

    // The account exists at the id derived from the bytes that were sent...
    let view = env.view_account(&from_supplied);
    assert!(view.storage_usage > 0, "the supplied bytes should have created the account");
    let access_key = env.env.rpc_node().view_access_key_query(&from_supplied, &public_key).unwrap();
    assert!(
        matches!(access_key.permission, AccessKeyPermissionView::FullAccess),
        "installed key must be full access, got {:?}",
        access_key.permission
    );

    // ...and nothing exists at the id their re-encoding would have derived.
    assert!(
        env.try_view_account(&from_re_encoding).is_err(),
        "re-encoding the decoded state init must not be what the id follows"
    );
}
