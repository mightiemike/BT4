### Title
Silent floating-point division-by-zero / overflow in default (non-hardened) `ExchangeProcessor` corrupts AMM exchange accounting - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The Cosmos SDK Groups bug (ASA-2025-003) is a case where a malicious, unprivileged actor drives a governance/module computation into a division-by-zero, and the resulting unhandled arithmetic condition corrupts state / halts the chain, even though a fix already exists but must be adopted. java-tron has an almost identical situation in its TRX/TRC10 Exchange (AMM) module: the legacy, still-default `ExchangeProcessor` used by `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` performs unchecked floating point division that can hit a zero/near-zero denominator, and the hardened, safe replacement (`SafeExchangeProcessor`, gated by `ALLOW_HARDEN_EXCHANGE_CALCULATION`) is opt-in via governance and disabled by default.

### Finding Description
`ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` compute ratios with primitive `double` arithmetic: [1](#0-0) 

- `exchangeToSupply`: `newBalance = balance + quant` then divides `quant / newBalance`.
- `exchangeFromSupply`: `supply -= supplyQuant` then divides `supplyQuant / supply`.

Both of these are ordinary Java `double` divisions, not `BigDecimal`/`BigInteger` operations, so a zero (or negative, wrapped) denominator does **not** throw `ArithmeticException` — it silently yields `Infinity`/`NaN`, which is then cast back to `long` (`(long) issuedSupply`), producing `Long.MAX_VALUE`/`Long.MIN_VALUE` or nonsensical values rather than failing loudly.

This computation is reached directly from unprivileged, anonymous broadcast transactions through `ExchangeCapsule.transaction`: [2](#0-1) 

which is invoked from `ExchangeTransactionActuator.execute`/`doValidate`: [3](#0-2) 

The repository's own maintainers clearly recognized this exact bug class: they introduced `SafeExchangeProcessor`, which performs the same computation with `BigDecimal` so that a zero denominator throws a catchable `ArithmeticException` instead of silently producing `Infinity`: [4](#0-3) 

Test code even documents the div-by-zero characteristic explicitly for the hardened path: [5](#0-4) 

But this hardened path is **not the default**. It is only activated by the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter, which must be approved by a super-representative proposal (the same "protocol didn't update" pattern as ASA-2025-003): [6](#0-5) [7](#0-6) 

Until that proposal passes, `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` all fall back to the unsafe `ExchangeProcessor`/raw-`long` arithmetic path (`allowHarden()` returns `false` by default): [8](#0-7) 

### Impact Explanation
Unlike the Cosmos Groups bug (which throws an uncaught panic and halts consensus), this java-tron analog does not crash the node with an exception — Java `double` division by zero does not raise `ArithmeticException`. Instead it silently returns `Infinity`/`NaN`, which is cast to a `long`. This is arguably a *worse* outcome in terms of exploitability: an unprivileged, ordinary user submitting an `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` that drives one side of a pool balance toward zero (or that overflows `long` addition in `balance + quant`) can obtain a wildly incorrect (`Long.MAX_VALUE`-class) `anotherTokenQuant`, resulting in direct asset/accounting corruption — draining the exchange pool or minting an unbounded amount of the counter-asset to the attacker's account. This falls squarely within the accepted impact categories ("asset or accounting corruption").

### Likelihood Explanation
The vulnerable, non-hardened `ExchangeProcessor` remains the network default because `ALLOW_HARDEN_EXCHANGE_CALCULATION` defaults to `0` and requires a super-representative governance proposal to enable — mirroring exactly the ASA-2025-003 scenario where "the fix exists but the protocol didn't update." Any account with sufficient balance/asset holdings can broadcast an `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` unprivileged, so the reachable surface is the full validator/full-node transaction-processing pipeline (`Manager`/actuators), not a privileged or leaked-key path. Some existing input validation (`firstTokenBalance == 0 || secondTokenBalance == 0` checks) reduces triviality, but the boundary/overflow conditions in `balance + quant` (long overflow) and near-zero `supply` after repeated `supply -= supplyQuant` are not fully excluded by current validation, given `supply` is a running local variable across repeated trades within a single exchange rather than a persisted, bounds-checked value.

### Recommendation
Make the `SafeExchangeProcessor` (BigDecimal-based, exception-on-zero-denominator) the mandatory path for all exchange actuators regardless of the `ALLOW_HARDEN_EXCHANGE_CALCULATION` flag, or at minimum add explicit zero/overflow guards directly in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` before performing the division, and treat this as a chain-critical default rather than an opt-in governance parameter.

### Proof of Concept
Not independently reproducible from the indexed code alone — a concrete PoC would require modeling the exact sequence of `ExchangeInject`/`ExchangeTransaction` calls needed to drive `firstTokenBalance + tokenQuant` (in `ExchangeProcessor.exchangeToSupply`) or the running `supply` value (in `exchangeFromSupply`) to zero/overflow within the `long`/`double` precision boundaries; this requires runtime experimentation (e.g., a Devin session with the local test harness) rather than static analysis, since the existing `ExchangeProcessorTest` demonstrates the div-by-zero property only against `SafeExchangeProcessor`, not the default `ExchangeProcessor`.     logger.debug("balance: " + balance);
    long newBalance = balance + quant;

    long out = (long) issuedSupply;

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
