### Title
Rescue-funds outbound trusts attacker-supplied `prc20` from `RescueFundsOnSourceChain` log without cross-checking it against the original inbound's asset - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`AttachRescueOutboundFromReceipt` builds a `RESCUE_FUNDS` outbound purely from the `prc20` field decoded out of the `RescueFundsOnSourceChain` EVM log, without ever verifying that this token matches the PRC20/asset that was actually associated with the original stuck `UniversalTx`. The eligibility gate only checks the *status* of the original UTX (deposit failed for CEA, or `INBOUND_REVERT` reverted for non-CEA) — it never checks that `event.PRC20` corresponds to `originalUtx.InboundTx.AssetAddr`/its PRC20 mapping. This is the same missing-linkage bug class as the reported TON issue: a receiver/asset field supplied on an "escape hatch" (multihop shortcut / rescue) path is trusted for routing value without validating it is the same asset that was actually locked.

### Finding Description
`AttachRescueOutboundFromReceipt` [1](#0-0)  decodes a `RescueFundsOnSourceChain` log emitted by `UniversalGatewayPC`, extracts `event.PRC20` (an indexed, caller-supplied address on the emitting EVM call) via `DecodeRescueFundsOnSourceChainFromLog` [2](#0-1) , and only checks that the *original* UTX is in an eligible stuck state (CEA deposit `FAILED`, or non-CEA `INBOUND_REVERT` reached `REVERTED`) [3](#0-2) .

It then resolves `event.PRC20` to an `ExternalAssetAddr` via `GetTokenConfigByPRC20(sourceChain, event.PRC20)` and builds the rescue outbound using `originalUtx.InboundTx.Amount` (the amount from the *original*, unrelated inbound) combined with the attacker-chosen `Prc20AssetAddr`/`ExternalAssetAddr`: [4](#0-3) 

Nowhere is `event.PRC20` checked against the PRC20 that corresponds to `originalUtx.InboundTx.AssetAddr` (the actual token from the original inbound). This mirrors the TON finding precisely: the shortcut path used a receiver-address match without validating the *asset* attached to that receiver matched what was actually held; here, the rescue path uses a UTX-eligibility match without validating the *token* attached to the rescue call matches what was actually part of that UTX.

### Impact Explanation
If the on-chain `UniversalGatewayPC`/vault contract does not independently enforce that `prc20` matches the token originally associated with `universalTxId` (a cross-repo Solidity component not present in this node repo), a caller could trigger `rescueFunds` specifying an arbitrary registered PRC20 while pointing at any other UTX that is merely in the eligible stuck state. The keeper would then build and eventually broadcast (after UV/TSS observation) an outbound that pays out `originalUtx.InboundTx.Amount` denominated in a completely different, potentially far more valuable, token/chain pairing than the one that was actually deposited or locked for that UTX — i.e. minting/paying an unauthorized asset amount, corrupting `Prc20AssetAddr`/`ExternalAssetAddr`/`Amount` semantics of a canonical `UniversalTx`. This falls squarely within "corruption of PRC20 or native asset accounting ... token mapping ... unauthorized refund of protocol-controlled funds."

### Likelihood Explanation
The gate is state-based, not authorization-based: any account whose inbound previously entered `PC_EXECUTED_FAILED` (CEA) or has a `REVERTED` `INBOUND_REVERT` (non-CEA, e.g. after a TSS/UV outage or destination-chain revert) can retry rescue and is completely free to choose which registered PRC20 the module keeper treats as the rescued asset, since the keeper performs no independent comparison against `originalUtx.InboundTx.AssetAddr`. Whether this is fully exploitable end-to-end depends on Solidity-side validation in `UniversalGatewayPC.rescueFunds` (not included in this repository), but the Go-side keeper — which is the authoritative recorder of `UniversalTx` state — provides no defense-in-depth check, which is the same class of gap flagged in the reference report ("missing validation ... add a check that the jetton wallet used in the swap is also the expected wallet").

### Recommendation
In `AttachRescueOutboundFromReceipt`, before building the rescue outbound, resolve the PRC20 that corresponds to `originalUtx.InboundTx.AssetAddr` for `originalUtx.InboundTx.SourceChain` and assert it equals `event.PRC20`; reject the event (return an error / skip) otherwise. This closes the loop entirely on the Go/keeper side regardless of what the Solidity contract does, consistent with the recommended short-term fix in the referenced report (validate the asset used in the escape-hatch path is the one actually expected, not just that a receiver/UTX-state condition matches).

### Proof of Concept
1. Attacker's own non-CEA `FUNDS` inbound for token `X` (say, a low-liquidity/cheap token) with amount `A` gets stuck: its `INBOUND_REVERT` outbound reaches `Status_REVERTED` (e.g., relayer/TSS failure on the source chain) — a state reachable without any privileged actor, purely via normal protocol operation on an ordinary user deposit.
2. Attacker calls the gateway's `rescueFunds`-style entry point on Push Chain, referencing this UTX's `universalTxId`, but supplies `prc20` = the PRC20 address of a high-value token `Y` (any token registered in `uregistry` for that source chain — registration itself isn't attacker-controlled, but which registered token is referenced in this call is).
3. `AttachRescueOutboundFromReceipt` sees the eligible `REVERTED` state [5](#0-4) , resolves `Y`'s `ExternalAssetAddr` via `GetTokenConfigByPRC20` [6](#0-5) , and creates a `RESCUE_FUNDS` outbound with `Amount = A` (original token-`X` amount) but `Prc20AssetAddr`/`ExternalAssetAddr` for token `Y` [7](#0-6) .
4. Once UVs observe/sign this outbound, the attacker receives amount `A` of token `Y` on the destination chain despite never having deposited or locked token `Y`.

// AttachRescueOutboundFromReceipt scans the receipt for RescueFundsOnSourceChain events
// emitted by UniversalGatewayPC and, for each one found, attaches a RESCUE_FUNDS outbound
// to the original UTX referenced by the event's universalTxId.
//
// Unlike normal outbounds (which create a new UTX), rescue outbounds are appended to the
// already-existing UTX whose funds are stuck on the source chain.
func (k Keeper) AttachRescueOutboundFromReceipt(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	pcTx types.PCTx,
) error {
	universalGatewayPC := strings.ToLower(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_GATEWAY_PC"].Address)

	evmChainID, err := utils.ExtractEvmChainID(ctx.ChainID())
	if err != nil {
		return fmt.Errorf("rescue: failed to extract EVM chain ID: %w", err)
	}
	pushChainCaip := fmt.Sprintf("eip155:%s", evmChainID)

	for _, lg := range receipt.Logs {
		if lg.Removed {
			continue
		}
		if strings.ToLower(lg.Address) != universalGatewayPC {
			continue
		}
		if len(lg.Topics) == 0 {
			continue
		}
		if strings.ToLower(lg.Topics[0]) != strings.ToLower(types.RescueFundsOnSourceChainEventSig) {
			continue
		}

		event, err := types.DecodeRescueFundsOnSourceChainFromLog(lg)
		if err != nil {
			return fmt.Errorf("failed to decode RescueFundsOnSourceChain: %w", err)
		}

		// The universalTxId in the event is a 0x-prefixed bytes32 matching our UTX key.
		originalUtxId := strings.TrimPrefix(event.UniversalTxId, "0x")

		originalUtx, found, err := k.GetUniversalTx(ctx, originalUtxId)
		if err != nil {
			return fmt.Errorf("rescue: failed to fetch UTX %s: %w", originalUtxId, err)
		}
		if !found {
			return fmt.Errorf("rescue: original UTX %s not found", originalUtxId)
		}
		if originalUtx.InboundTx == nil {
			return fmt.Errorf("rescue: UTX %s has no inbound tx", originalUtxId)
		}

func DecodeRescueFundsOnSourceChainFromLog(log *evmtypes.Log) (*RescueFundsOnSourceChainEvent, error) {
	if len(log.Topics) < 4 {
		return nil, fmt.Errorf("RescueFundsOnSourceChain: need 4 topics, got %d", len(log.Topics))
	}
	if strings.ToLower(log.Topics[0]) != strings.ToLower(RescueFundsOnSourceChainEventSig) {
		return nil, fmt.Errorf("not a RescueFundsOnSourceChain event")
	}

	event := &RescueFundsOnSourceChainEvent{
		UniversalTxId: log.Topics[1], // bytes32 as 0x-prefixed hex
		PRC20:         common.HexToAddress(log.Topics[2]).Hex(),
		Sender:        common.HexToAddress(log.Topics[3]).Hex(),
	}
