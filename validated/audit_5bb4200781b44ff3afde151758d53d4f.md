### Title
Malicious NEP-141 token / registrar contract can permanently brick the NEAR wallet-contract via callback gas exhaustion, freezing the account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the NEAR "eth-wallet" account-abstraction contract) uses a single in-flight-transaction guard, `has_in_flight_tx`, to serialize execution of Ethereum-emulated transactions. The flag is set to `true` in one receipt (`rlp_execute`) and is only reset to `false` inside a later, separate callback receipt (`address_check_callback` / `nep_141_storage_balance_callback` / `rlp_execute_callback`). Because NEAR rolls back *all* state writes of a failed receipt, if the callback receipt itself fails (e.g. runs out of its fixed, hard-coded gas budget while deserializing an attacker-controlled cross-contract response), the `has_in_flight_tx = false` write never lands on-chain, and the flag remains stuck at `true` forever. This mirrors the ERC777-callback report: an external, attacker-influenced contract (the ERC20-like token or address registrar that the wallet calls back into) can use its callback surface to permanently block further operations of the victim contract — here, freezing the entire wallet-contract account instead of blocking a liquidation.

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` and returns a `Promise` chain, committing that state in its own receipt: [1](#0-0) 

For ERC20 emulation, the wallet contract calls out to an externally-controlled `token_id` (the `target` account supplied via the RLP-encoded action) with a fixed, hard-coded gas budget for the follow-up callback: [2](#0-1) 

The callback gas constants are small and fixed at compile time, independent of what the external token contract actually returns: [3](#0-2) 

The callback resets the guard as its very first statement, then deserializes the attacker-controlled `storage_balance_of` response: [4](#0-3) 

Because a malicious/compromised token contract fully controls the size and shape of the `PromiseResult::Successful(value)` payload (up to the protocol's max returned-data size), it can return a payload whose `serde_json::from_slice` deserialization, combined with the rest of the callback logic, exceeds the fixed `callback_gas` budget. When that happens, the callback receipt fails with an out-of-gas error, and the entire receipt — including the `self.has_in_flight_tx = false;` write that already executed in memory — is rolled back, per the runtime's per-receipt commit/rollback semantics: [5](#0-4) 

The same pattern applies to `address_check_callback`, which is invoked after calling out to the (also externally reachable) address registrar: [6](#0-5) 

Once `has_in_flight_tx` is stuck `true`, every future call to `rlp_execute` on this account is unconditionally rejected: [7](#0-6) 

There is no other public method that resets `has_in_flight_tx` back to `false` except the callbacks themselves (and `ban_relayer`, which only runs on the separate relayer-error path taken at the *original* `rlp_execute` call, not after a stuck callback) — the guard's own doc comment states it must stay `true` for the whole promise chain, but provides no recovery path if the final callback never successfully executes: [8](#0-7) 

### Impact Explanation
This is directly analogous to the reported ERC777-callback issue: an externally-controlled contract's callback behavior is used to permanently deny a critical state transition (there: liquidation; here: any future transaction on the wallet-contract account). Once triggered, the affected NEAR account can never submit another Ethereum-emulated transaction through this contract again — the account's assets and its ability to use the eth-emulation surface at all become permanently frozen, since `rlp_execute` will forever short-circuit with "transaction already in progress." This satisfies the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
The trigger requires only an ordinary, unprivileged transaction: any relayer/account owner constructing an RLP-encoded ERC20 transfer whose `to` address resolves to a token contract that the attacker controls (or a compromised/malicious token that a user is lured into interacting with, a very common pattern in token-approval/transfer phishing). The attacker-controlled token merely needs to return an oversized or otherwise gas-expensive `storage_balance_of` response — no validator, network, or privileged access is needed, and the callback gas budgets are small, fixed constants (5 Tgas order) that are easy to exceed with a moderately sized payload.

### Recommendation
- Reset `has_in_flight_tx` (and persist it) *before* making the externally-controlled cross-contract call, or use a design where the guard's release does not depend on the successful completion of a receipt whose gas/failure is influenced by an untrusted external contract.
- Bound/validate the size of data returned by `storage_balance_of`/registrar `lookup` before attempting to deserialize it, and ensure the callback has enough gas headroom to handle worst-case (max-sized) payloads or fail cheaply.
- Provide an explicit recovery/unlock path (e.g., a timeout-based reset or an owner-only "clear stuck flag" mechanism) so a failed callback cannot permanently brick the contract.

### Proof of Concept
1. Attacker deploys (or compromises) a NEP-141-like contract `evil_token` whose `storage_balance_of` method returns a payload sized/structured to maximize JSON-deserialization cost (up to the protocol's max return-data size).
2. Victim (or a relayer on the victim's behalf) submits an RLP-encoded Ethereum "ERC20 transfer" transaction through `WalletContract::rlp_execute` with `target = evil_token`.
3. `rlp_execute` sets `has_in_flight_tx = true` and schedules `Promise::new(evil_token).function_call("storage_balance_of", ...).then(ext.nep_141_storage_balance_callback(...))` with a fixed `callback_gas` (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS + action.gas()`), per `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:433-458`.
4. `evil_token::storage_balance_of` returns its crafted large payload; `nep_141_storage_balance_callback` starts, sets `has_in_flight_tx = false` in memory, then runs out of gas while processing the oversized `serde_json::from_slice(&value)` call.
5. The callback receipt fails and is rolled back in its entirety (per the runtime's commit/rollback semantics for failed receipts), so `has_in_flight_tx` remains `true` in the persisted contract state.
6. Any subsequent call to `rlp_execute` on this account immediately returns `"Error: transaction already in progress, please try again later."` forever, permanently freezing the wallet-contract account.
