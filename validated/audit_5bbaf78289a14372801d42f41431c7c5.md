### Title
Uncaught exception in `sanitizeHost()` from `atob()`/`URL` parsing failures on malformed-but-regex-valid base64 host param - (File: packages/apps/shopify-api/lib/utils/shop-validator.ts)

### Summary
`sanitizeHost()` validates the `host` query parameter only with a loose base64 character-set regex before calling `atob()` (via `decodeHost`) and immediately feeding the decoded bytes into `new URL()`, with no `try/catch`. Because both `atob()` and the `URL` constructor can throw on inputs that still satisfy the character-set regex, an attacker can make `sanitizeHost()` throw an uncaught exception instead of returning `null`, breaking its documented `throwOnInvalid`/null-return contract.

### Finding Description
`sanitizeHost()` in `packages/apps/shopify-api/lib/utils/shop-validator.ts:52-91` only checks the base64 alphabet with `/^[0-9a-zA-Z+/]+={0,2}$/` [1](#0-0) . This regex does not enforce a valid base64 length (a multiple of 4). A string like a single character `"a"` (length ≡ 1 mod 4) satisfies the regex but is not a legally-decodable base64 sequence; per the WHATWG/Node `atob` forgiving-base64 algorithm, such input triggers an exception at `decodeHost()` (`atob(host)`) [2](#0-1) .

Separately, even for length-valid base64, the decoded bytes are directly interpolated into a URL string and parsed with `new URL()` at line 58, with no error handling: `const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);` [3](#0-2) . Decoded bytes containing characters invalid in a URL authority (e.g. `<`, control characters, unmatched brackets) cause the `URL` constructor to throw `TypeError: Invalid URL`, which is not caught anywhere in the function.

Both failure modes bypass the function's intended contract: return `sanitizedHost` (string) or `null`, and only throw `InvalidHostError` when `throwOnInvalid` is explicitly `true` (line 85-87) [4](#0-3) . Callers rely on this contract without wrapping calls in their own try/catch, e.g. `validateShopAndHostParams()` in both the Remix and React Router adapters call `api.utils.sanitizeHost(...)` directly and only check for a falsy return value [5](#0-4) , and the Express middleware `redirectToShopifyOrAppRoot` calls `api.utils.sanitizeHost(req.query.host as string)!` with a non-null assertion, again with no local try/catch [6](#0-5) . This function is reached pre-authentication: `validateShopAndHostParams` runs before any session token/HMAC verification in the document-request path of `authenticateAdmin` [7](#0-6) .

Note: In the Remix/React Router `authenticateAdmin()` flow, an outer `try { ... } catch (errorOrResponse) { ...; throw errorOrResponse; }` block wraps the call [8](#0-7) , so a thrown `TypeError` there is re-thrown to the surrounding framework request handler rather than crashing the Node process — the practical effect there is an unhandled 500 error instead of the intended graceful redirect to the login/exit-iframe path. The Express `redirectToShopifyOrAppRoot` middleware has no such wrapper, so an uncaught throw there propagates to Express's default error handling for that request.

### Impact Explanation
This is a functional/availability defect: a single malformed `host` value causes an unhandled exception at a pre-authentication validation point instead of the intended "return null → redirect to login" behavior. Impact is limited to a per-request failure (raw 500 / unhandled request-level error) rather than a full-service crash, since JS exceptions in async request handlers are caught by the surrounding framework/try-catch layers in the reviewed call sites. This corresponds to a low-severity availability/robustness issue (single-request DoS/error-page disclosure at most), not a session-forgery, token-theft, or cross-tenant compromise — no authentication or authorization check is bypassed as a result.

### Likelihood Explanation
Trivial to trigger: no authentication, secrets, or preconditions are required — an anonymous client sends `GET /?shop=x.myshopify.com&host=<crafted string>` where `host` is a base64-alphabet string with invalid length or that decodes to characters invalid in a URL authority. This is fully attacker-controlled and repeatable on every request to any embedded-app route protected by `validateShopAndHostParams` or by `redirectToShopifyOrAppRoot`.

### Recommendation
Wrap the `atob`/`URL` construction in `sanitizeHost()` in a `try/catch`, treating any decode/parse failure as an invalid host (return `null`, or throw `InvalidHostError` only if `throwOnInvalid` is true), matching the function's documented contract:
```ts
let sanitizedHost = base64regex.test(host) ? host : null;
if (sanitizedHost) {
  try {
    const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);
    // ... existing regex validation of hostname
  } catch {
    sanitizedHost = null;
  }
}
```
Additionally, tighten the base64 validation to also assert the length is a multiple of 4 (or use padding-aware validation) to reject strings like `"a"` before calling `atob`.

### Proof of Concept
```ts
// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts
import {shopifyApi} from '../..';
import {testConfig} from '../../__tests__/test-config';

test('sanitizeHost should not throw on malformed base64 length', () => {
  const shopify = shopifyApi(testConfig());
  // 'a' matches /^[0-9a-zA-Z+/]+={0,2}$/ but is invalid base64 (length % 4 === 1)
  expect(() => shopify.utils.sanitizeHost('a')).not.toThrow();
  expect(shopify.utils.sanitizeHost('a')).toBeNull();
});

test('sanitizeHost should not throw when decoded bytes are not a valid URL authority', () => {
  const shopify = shopifyApi(testConfig());
  // base64 for "<" (0x3C) -> decodes into "https://<", invalid per WHATWG URL parser
  const maliciousHost = Buffer.from('<').toString('base64'); // "PA=="
  expect(() => shopify.utils.sanitizeHost(maliciousHost)).not.toThrow();
  expect(shopify.utils.sanitizeHost(maliciousHost)).toBeNull();
});
```
Both assertions currently fail (the calls throw an uncaught `TypeError`/`DOMException` instead of returning `null`), demonstrating the bug against the current implementation at [9](#0-8) .

```typescript
export function sanitizeHost(config: ConfigInterface) {
  return (host: string, throwOnInvalid = false): string | null => {
    const base64regex = /^[0-9a-zA-Z+/]+={0,2}$/;

    let sanitizedHost = base64regex.test(host) ? host : null;
    if (sanitizedHost) {
      const {hostname} = new URL(`https://${decodeHost(sanitizedHost)}`);

      const originsRegex = [
        'myshopify\\.com',
        'shopify\\.com',
        'myshopify\\.io',
        'spin\\.dev',
        'shop\\.dev',
      ];

      if (config.domainTransformations) {
        const hostTransformationDomains = config.domainTransformations
          .filter((t) => t.includeHost !== false)
          .flatMap((t) =>
            getTransformationDomains({
              ...config,
              domainTransformations: [t],
            }),
          );
        originsRegex.push(...hostTransformationDomains);
      }

      const hostRegex = new RegExp(`\\.(${originsRegex.join('|')})$`);
      if (!hostRegex.test(hostname)) {
        sanitizedHost = null;
      }
    }
    if (!sanitizedHost && throwOnInvalid) {
      throw new InvalidHostError('Received invalid host argument');
    }

    return sanitizedHost;
  };
}
```
