### No vulnerability found for this question.

Both checks operate on the same immutable field, not on independently-resolved "current parent" state, so the claimed race is not possible.

**Details:**

In `append_block`, the parent used for the burn-total check and the parent used for the VRF-seed check are the exact same value: `block.header.parent_block_id`, a field baked into the immutable `NakamotoBlock` struct passed into the function. [1](#0-0) 

`Self::get_expected_burns(burn_dbconn, chainstate_tx, block)` resolves the parent's burn total either via the tenure-change tx's `burn_view_consensus_hash` or, when there's no new tenure, directly via `block.header.parent_block_id`: [2](#0-1) 

`check_block_commit_vrf_seed` → `validate_vrf_seed` → `get_parent_vrf_proof` also uses `self.header.parent_block_id` directly (the same block struct field, not a re-resolved "current tip"): [3](#0-2) [4](#0-3) 

There is no "resolution" step subject to a race — both call sites read the same already-parsed, immutable `NakamotoBlock` field. Additionally, `append_block` takes `chainstate_tx: &mut ChainstateTx` and threads it through both calls sequentially; Rust's ownership model prevents any concurrent mutation of `chainstate_tx` during this single call, and block processing is serialized through the chainstate's single-writer transaction, so no interleaved chain-tip update can occur mid-function as the question hypothesizes. [5](#0-4) 

The premise — that `expected_burn_opt`'s parent and the VRF check's parent could diverge due to concurrent tip resolution — does not hold: both are derived from the same single-valued, already-fixed `block.header.parent_block_id`, and the enclosing function holds exclusive mutable access to the chainstate transaction throughout. No divergent parent references, no non-reproducible MARF root, and no accept/reject inconsistency is reachable through this path.
