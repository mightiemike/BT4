### Title
Legacy (non-hardened) `ExchangeProcessor` uses unchecked double-precision math whose overflow/precision loss silently corrupts exchange balances - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The reported bug class ("`get_reserve` returns a value computed in `f64` that is silently clamped when cast back to a fixed-width integer, producing incorrect and exploitable seat prices") has a direct analog in java-tron's `ExchangeProcessor`, which computes bancor-style exchange amounts entirely in `double` arithmetic and truncates the result to `long` with an unchecked `(long)` cast.

### Finding Description
`ExchangeProcessor.exchangeFromSupply` computes:
```java
double exchangeBalance = balance
    * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
return (long) exchangeBalance;
``` [1](#0-0) 
and `exchangeToSupply` similarly casts a `double` result to `long`: [2](#0-1) 

Because the exponent `2000.0` is applied to a ratio that can be pushed close to or above 1 by an attacker-chosen `sellTokenQuant`, `Maths.pow(...)` can return values whose magnitude, once multiplied by `balance`, exceeds `Long.MAX_VALUE` (or loses significant precision) while still fitting in the 53-bit mantissa error margin of `double`. The subsequent narrowing `(long)` cast either silently clamps to `Long.MAX_VALUE`/`Long.MIN_VALUE` or truncates to an incorrect value — exactly the class of bug described in the report, where an `f64`-based price/reserve computation is cast back into a bounded integer type without any overflow or precision check.

This unhardened path is reached from `ExchangeCapsule.transaction`, which selects `ExchangeProcessor` unless `hardenedCalc` is `true`: [3](#0-2) 
and `hardenedCalc`/`useStrictMath` are gated behind the chain parameters `allowHardenExchangeCalculation()` and `allowStrictMath()`, which are set via `AbstractExchangeActuator.allowHarden()` and passed by every exchange actuator (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`): [4](#0-3) [5](#0-4) 

The codebase already contains a corrected implementation, `SafeExchangeProcessor`, which performs the same math in `BigDecimal`/`BigInteger` and uses `longValueExact()` (which throws `ArithmeticException` on overflow instead of silently clamping): [6](#0-5) 
This mirrors the upstream Deriverse fix ("convert to i64 only after computing the precise result"), confirming the bug class is real and was already recognized as needing a hardened replacement — but the hardened path is only used when the `allowHardenExchangeCalculation` committee proposal has been activated. Until that proposal is activated on a given network, every `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` broadcast by an anonymous account is processed through the vulnerable double-precision `ExchangeProcessor` path.

### Impact Explanation
An attacker who controls the `sellTokenQuant` in an `ExchangeTransactionContract`/`ExchangeInjectContract` can drive the `pow(base, 2000.0)` computation into a regime where double-precision error or overflow causes the computed `buyTokenQuant` (or the injected/withdrawn amount) to be silently wrong — either far larger than the actual reserve (draining the counterparty side of the pool / other users' funds) or clamped/truncated to an incorrect small value (causing users to receive far less than they should when selling). Because `ExchangeCapsule.transaction` then directly mutates `firstTokenBalance`/`secondTokenBalance` in `Exchange` proto state and the actuator credits/debits real TRX/TRC10 asset balances based on this corrupted value, this can produce direct economic loss and/or an extractable arbitrage/drain vector, matching the "opportunities for an attacker to extract value" impact in the original report.

### Likelihood Explanation
Reachability requires only a normal, unprivileged broadcast transaction (`ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract`) — no privileged role, leaked key, or malicious peer is needed. The precondition is that `allowHardenExchangeCalculation` has not yet been activated via committee proposal on the target chain/network; the presence of the flag and `SafeExchangeProcessor` in this exact codebase indicates the maintainers are aware of the issue and have already built (but not unconditionally enabled) the fix, which is consistent with a real, previously-unpatched-by-default precision/overflow defect in a resource/exchange math path.

### Recommendation
- Make the `SafeExchangeProcessor` (`BigDecimal`/exact-value) path the unconditional implementation for `ExchangeProcessor.exchange`, removing the double-precision fallback rather than gating it behind a proposal, or ensure the hardening proposal is activated by default on all networks.
- In the interim (non-hardened) path, validate that intermediate `double` values remain within `Long.MIN_VALUE`/`Long.MAX_VALUE` before casting, and reject/throw instead of silently truncating, mirroring the `longValueExact()` semantics already used in `SafeExchangeProcessor`.
- Apply the same review to `usageToBalance`/`calculateGlobalEnergyLimit` in `RepositoryImpl.java` and `EnergyProcessor.java`, which have analogous unchecked `(long) (double ...)` casts still reachable when `hardenResourceCalculation()`/`hardenCalculation()` is disabled. [7](#0-6) [8](#0-7) 

### Proof of Concept
1. Create an exchange pool (`ExchangeCreateActuator`) with a small `secondTokenBalance` relative to the internal `supply` constant (`1_000_000_000_000_000_000L`), e.g. `firstTokenBalance = 1`, `secondTokenBalance = 1`, on a network where `allowHardenExchangeCalculation` is not yet activated (default legacy behavior), as exercised in `ExchangeProcessorTest.testHardenedLargeQuant`/`testStrictMath`, which already demonstrate divergence between `ExchangeProcessor` and `SafeExchangeProcessor` for the same inputs: [9](#0-8) 
2. Submit an `ExchangeTransactionContract` (or `ExchangeInjectContract`) with a `sellTokenQuant` chosen so `1.0 + supplyQuant/supply` raised to the `2000.0` power in `exchangeFromSupply` produces a `double` whose value, once multiplied by `balance`, exceeds `Long.MAX_VALUE` or loses precision at the relevant magnitude.
3. Observe that `ExchangeCapsule.transaction` returns/commits an incorrect `buyTokenQuant`/`anotherTokenBalance` (clamped or truncated), while `SafeExchangeProcessor.INSTANCE.exchange` on the same inputs would either throw `ArithmeticException` (as shown in `testHardenedOverflowDetection`) or return the mathematically correct bounded value — demonstrating the discrepancy and resulting balance corruption in the non-hardened default path.   private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
