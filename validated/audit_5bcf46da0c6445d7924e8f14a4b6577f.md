### Title
`ValidateMultiSign`/`BatchValidateSign` TVM precompiles build signatures with no chain-id or verifying-contract domain separation, enabling cross-fork/cross-chain signature replay - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract (address `0x...0a`) lets any deployed smart contract verify off-chain signatures against an account's on-chain `Permission` structure. The message that a user must sign is built purely from `address || permissionId || data`, with no chain identifier and no binding to the calling/verifying contract's address. This mirrors exactly the `_checkSig` bug class described in the report: a signature scheme intended to authorize an action tied to one specific deployment can be legally replayed against any other deployment (a chain fork, a test network sharing the same account/permission state, or another dApp that reuses the same `(address, permissionId, data)` triple) because nothing in the signed payload commits to the environment in which the signature is meant to be valid.

### Finding Description
`ValidateMultiSign.execute` computes the digest to be checked as: [1](#0-0) 

i.e. `hash = SHA256(address || permissionId || data)`. `BatchValidateSign` is similar but takes the caller-supplied `hash` directly and iterates ecrecover against it: [2](#0-1) 

Neither construction includes:
- A chain identifier (there is no `CHAINID`-derived value folded into the hash, unlike the CHAINID opcode which is derived from the genesis block hash and is chain-specific — see `IstanbulTest.istanbulSelfBalanceChainIdTest`), and
- The address of the verifying/calling contract (the precompile is reachable from `msg.sender` context of any TVM contract via `CALL`, but the digest never binds to that contract's address).

This is the same missing-domain-separation pattern flagged in the external report for `_checkSig`: the signed payload commits only to data that is meaningful within a single logical application instance (`address`, `permissionId`, `data`), but the same payload/signature pair remains valid:
- Across a hard fork of the java-tron chain that preserves account/permission state (an attacker-controlled fork, or a private testnet cloned from mainnet state),
- Across any two contracts on the same chain that both choose to call `validatemultisign`/`batchvalidatesign` with the same `(address, permissionId, data)` triple for semantically different actions (e.g. a "permit" style authorization reused by an unrelated dApp),

because the precompile itself provides no enforcement that the signature is scoped to "this contract, this chain".

### Impact Explanation
Any dApp author relying on `ValidateMultiSign`/`BatchValidateSign` as a signature-based authorization primitive (a common EIP-712/permit-style pattern) inherits a replay vulnerability unless they manually add chain/contract binding into `data` themselves — the precompile gives them no such guarantee and the semantics look deceptively similar to a general-purpose ecrecover-based check-weight helper used elsewhere in the codebase (`TransactionCapsule.checkWeight`), where replay protection is provided incidentally by the enclosing transaction's `ref_block`/`expiration` fields, not by this primitive. An attacker who can get a victim to sign a message for use on one contract/chain (e.g. a "testnet" or "sidechain" fork) can replay that exact signature to satisfy the permission-weight check on another contract or chain instance where the same address/permission/data triple recurs, resulting in unauthorized account operations being authorized (e.g. approving fund movement, multisig thresholds being satisfied) that the signer never intended for that context.

### Likelihood Explanation
Exploitation requires a scenario where the same signer address, permission ID, and payload are meaningful across two distinct deployments/forks/dApps — this is a realistic occurrence for testnets forked from mainnet state, privately operated java-tron-based chains, and third-party dApps that adopt copy-pasted integration patterns for this precompile (as seen in the "reuse this exact `(address, permissionId, data)` construction" pattern used consistently in the test helpers). The precompile is reachable from any smart contract via ordinary `CALL`, requiring no privileged access — any contract deployed by anyone can invoke it, and the exploit only needs a previously-observed valid signature, matching the "signature re-use/front-run to bypass authentication" pattern in the report.

### Recommendation
Add mandatory domain separation to the signed digest computed inside `ValidateMultiSign` (and document the same requirement for callers of `BatchValidateSign`, which accepts a caller-supplied hash): fold in the chain ID (as already exposed via the `CHAINID` opcode) and the verifying contract's address (`msg.sender`/precompile caller) into the hash before it is used for `ecrecover`-based weight checks, e.g. `hash = SHA256(chainId || callerContractAddress || address || permissionId || data)`. This ensures a signature produced for one chain/contract cannot satisfy the permission-weight check on another fork or another contract. Long term, treat any newly introduced on-chain, ecrecover-style authorization primitive as requiring EIP-712-style domain separation by default rather than leaving it to individual dApp authors to add ad hoc.

### Proof of Concept
1. On chain A (e.g. java-tron mainnet), account `Alice` has an `active` permission (id=2, threshold=2, keys = {`K1`,`K2`}).
2. Alice's co-signers sign `toSign = SHA256(Alice_address || 2 || data)` off-chain, intending to authorize a specific action on dApp `X` deployed on chain A, and the resulting signatures are submitted through `validatemultisign(Alice_address, 2, data, [sig1, sig2])`, as exercised in `ValidateMultiSignContractTest.testDifferentCase` (`framework/src/test/java/org/tron/common/runtime/vm/ValidateMultiSignContractTest.java:104-125`).
3. An attacker who operates or forks a second java-tron-based chain B (or a second dApp `Y` on chain A) that preserves/reproduces the same `Alice_address`/permission-id/`data` state replays the identical `[sig1, sig2]` against `validatemultisign` on chain B/dApp `Y`.
4. Because the digest never included a chain id or the verifying contract's address, the precompile returns success (`DataWord.ONE()`), and the unrelated chain/dApp treats the replayed signatures as a valid authorization from Alice's co-signers, even though they never intended to authorize anything on chain B/dApp `Y`.
