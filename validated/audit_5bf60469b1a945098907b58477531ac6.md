### Title
Underflow panic in `Stakes::sub_delegated_stake` when a stake account's recomputed effective stake exceeds its previously cached delegated amount - (File: `runtime/src/stakes.rs`)

### Summary
`runtime/src/stakes.rs` maintains a `delegated_stakes: ImblHashMap<Pubkey, u64>` accumulator that is supposed to always equal the sum of the *currently cached* effective stake delegated to each vote account. `sub_delegated_stake` unconditionally assumes the accumulator can never be smaller than the amount being subtracted, and uses `.expect()` to enforce it, which panics instead of returning an error. This is the same bug class as the external report: code assumes a running "total" (there, rebase-token supply; here, per-validator delegated stake) will never decrease relative to what a later computation expects to subtract, and when that assumption is violated the result is not a graceful error but an unrecoverable failure.

### Finding Description
`sub_delegated_stake` is:
```rust
fn sub_delegated_stake(&mut self, voter_pubkey: &Pubkey, stake: u64) {
    if stake == 0 { return; }
    let current_stake = self.delegated_stakes.get_mut(voter_pubkey)
        .expect("subtraction from missing delegated stake");
    *current_stake = current_stake.checked_sub(stake)
        .expect("subtraction value exceeds delegated stake");
    ...
}
``` [1](#0-0) 

It is called from `upsert_stake_delegation`, which recomputes the *old* delegation's effective stake (`old_stake`) from the delegation stored in the previous version of the account, using the current epoch and `stake_history`, and then subtracts that freshly recomputed value from the cached accumulator:
```rust
Some(old_stake_account) => {
    let old_delegation = old_stake_account.delegation();
    let old_voter_pubkey = old_delegation.voter_pubkey;
    let old_stake = delegation_effective_stake(old_delegation, self.epoch, &self.stake_history, ...);
    if voter_pubkey != old_voter_pubkey || stake != old_stake {
        self.sub_delegated_stake(&old_voter_pubkey, old_stake);
        ...
    }
}
``` [2](#0-1) 

`upsert_stake_delegation` is reached through `StakesCache::check_and_store`, which is invoked whenever an account owned by the stake program is stored/updated: [3](#0-2) 

This means any ordinary stake-program instruction that mutates a `StakeStateV2` account (`DelegateStake`, `Deactivate`, `Split`, `Merge`, `Redelegate`, `MoveStake`, etc.) drives this code path through normal bank transaction processing — it is not an operator-only or validator-internal path, matching the required "ordinary client transaction" reachability.

The critical, unverified assumption is that `old_stake` recomputed on the *new* write will always equal what was actually accumulated into `delegated_stakes` on the *previous* write for that account. Because `delegation_effective_stake` depends on warm-up/cool-down rates, `self.epoch`, and `stake_history` (all of which are external, time-varying, and feature-gated — note `use_fixed_point_stake_math`), any divergence between the value used at insertion time and the value recomputed at a later mutation (e.g., due to differing code paths, floating-point vs fixed-point math transitions, or a mutation racing an epoch-boundary `refresh_delegated_stakes`) causes the recomputed `old_stake` to exceed the live accumulator, triggering the `expect()` panic. This exactly mirrors the reported class 2 issue in the report ("assumption that a tracked total will not decrease" causing an underflow that halts a rebasing/accounting update), except here it is validator-runtime stake accounting rather than an on-chain rebase-token vault.

### Impact Explanation
If the underflow assertion is triggered, this is an unconditional Rust panic on the hot bank-transaction-processing path used to keep the stakes cache in sync during normal block replay. Because `StakesCache::check_and_store` runs during every validator's transaction commit/replay of the same block, a panic here is deterministic across the whole cluster for the offending slot, i.e., a cluster-halting panic — the most severe accepted impact category for this scope.

### Likelihood Explanation
I was not able to fully construct a concrete reproducing transaction sequence within the available time/tooling; doing so requires tracing `delegation_effective_stake`, the warmup/cooldown rate computation, and the interaction with the `use_fixed_point_stake_math` feature gate and epoch-boundary `refresh_delegated_stakes()` in detail, which was not completed. The likelihood therefore depends on whether there exists a legitimate stake-account mutation sequence (e.g., interleaving instructions across a feature-activation boundary, or split/merge/redelegate sequences) that causes the effective-stake recomputation for the "old" delegation to diverge upward from what was cached at insertion. This is plausible given the surrounding code explicitly guards a similar recomputation-consistency risk in `upsert_stake_delegation` (`stake != old_stake` check) but does not defensively saturate/guard `sub_delegated_stake` itself.

### Recommendation
Replace the panicking `.expect()` calls in `sub_delegated_stake` (and the corresponding lookup in the same function) with saturating arithmetic (e.g., `current_stake.saturating_sub(stake)`) or with an explicit, loggable error/recovery path rather than an unconditional panic, so that any latent inconsistency between the cached accumulator and a freshly recomputed effective stake degrades gracefully instead of crashing the validator. This mirrors the report's own recommendation of "an explicit error, a try/catch structure, or a redesign of this flow" rather than allowing an unguarded underflow to abort processing. [1](#0-0) 

### Proof of Concept
Not fully constructed. I confirmed the reachable call chain (`check_and_store` → `upsert_stake_delegation` → `sub_delegated_stake`) from ordinary stake-program instructions, but did not complete tracing `delegation_effective_stake`'s warmup/cooldown/feature-gate logic far enough to produce a concrete transaction sequence proving the underflow is triggerable by an unprivileged client. This is stated explicitly as unverified; confirming or ruling this out would require deeper analysis of `stake_delegation.rs::delegation_effective_stake`, `Stakes::activate_epoch`/`refresh_delegated_stakes`, and the `use_fixed_point_stake_math` feature transition, which exceeded the available investigation budget.
