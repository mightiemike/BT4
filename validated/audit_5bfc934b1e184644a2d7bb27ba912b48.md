### Title
Unprivileged attacker can flood the network with free, forced EVM-execution work via gasless `MsgExecutePayload` against any deployed UEA - ([File: app/txpolicy/gasless.go], [File: app/ante/account_init_decorator.go], [File: x/uexecutor/keeper/msg_execute_payload.go])

### Summary
The reported SEDA issue is a "push model" bug class: an attacker forces the protocol to do costly work (processing a request) for free, by making the compensating step (fee transfer) revert, so the requester pays nothing while the network/solver absorbs the cost. Push Chain's gasless admission path for `MsgExecutePayload` reproduces the same invariant break in a different subsystem: any unprivileged account — created for free via the `AccountInitDecorator` gasless bootstrap — can force a full `DerivedEVMCall` execution attempt against any already-deployed UEA, paying no Cosmos fee at all, and the message legitimately reverts only *inside* the EVM call (signature check in the UEA contract), after the node has already spent compute dispatching and metering the EVM transaction.

### Finding Description
`MsgExecutePayload` is in the gasless allowlist (`app/txpolicy/gasless.go:14-25`), and the module documentation confirms "any account may submit the message" without enforcing `Signer == EVM(Owner)` — the cryptographic check happens only inside the UEA contract's `executeUniversalTx` [1](#0-0) .

For any gasless tx, `MinGasPriceDecorator` and `DeductFeeDecorator` skip fee/min-gas-price checks entirely [2](#0-1) [3](#0-2) , and `AccountInitDecorator` will create a brand-new on-chain account mid-pipeline for a never-seen signer, requiring only a self-consistent signature over `account_number=0, sequence=0` — no funding, no prior existence needed [4](#0-3) . This decorator is not restricted to UV-only messages; it applies to any tx composed entirely of gasless message types, which includes `MsgExecutePayload`.

Once past the ante pipeline, `ExecutePayload` resolves the UEA address and, if it is already deployed (true for any UEA a legitimate user has ever used), proceeds directly to `CallUEAExecutePayload`, which performs a real, `commit=true` `DerivedEVMCall` using the attacker-supplied `universal_payload.GasLimit` [5](#0-4) . The cryptographic authorization check is deferred entirely to the EVM call itself (ECDSA/Ed25519 verification inside the UEA contract) [6](#0-5) , meaning the chain has already dispatched and metered the EVM transaction — consuming real node compute/EVM gas-processing resources — before determining the request is bogus and reverting it.

Because the tx is fee-free and the signer account can be freshly minted at zero cost each time, an attacker can generate an effectively unlimited stream of disposable Cosmos keys, each submitting one `MsgExecutePayload` with garbage `VerificationData` targeting any known deployed UEA, forcing repeated real EVM-execution attempts network-wide with no economic cost and no per-signer rate limit.

### Impact Explanation
This breaks the "gasless allowlisting ... must not turn attacker input into accepted authorization" invariant and the "denial of service ... reachable without privileged control" scope item: an unprivileged actor can force honest full nodes/validators to repeatedly perform costly, forced EVM-execution work (dispatch + gas metering + revert) for zero cost, with no fee-based friction and no need to hold a funded account, potentially degrading node/validator performance chain-wide — the same "flood the network with cheap requests to force uncompensated work" pattern as the referenced SEDA finding, just relocated from solver fee payouts to validator/full-node compute.

### Likelihood Explanation
High reachability: the attack requires no privileged role, no validator/TSS/UV status, and no prior funding — only knowledge of one already-deployed UEA address (these are deterministic and discoverable) and the ability to generate ECDSA keypairs and sign a Cosmos tx, both trivially automatable. The only friction is the SDK block-gas budget per block (a `gas` value must still be specified within block limits), but since it carries no fee, an attacker can submit many such transactions across many blocks/mempools at effectively zero marginal cost.

### Recommendation
- Require a minimal, non-gasless economic cost (fee, deposit, or stake) for `MsgExecutePayload`, or at least remove it from the pure-gasless allowlist for third-party/non-owner submissions.
- Perform a cheap, node-local pre-check (e.g., signature/verification-data format validation, or a lightweight local recovery/verify) before dispatching the costly `DerivedEVMCall`, so invalid submissions fail before consuming EVM execution resources.
- Rate-limit or require minimum account age/history for gasless-tx account auto-creation via `AccountInitDecorator`, or restrict its use to the UV/TSS message set it was originally designed for, since generalizing it to `MsgExecutePayload` allows unlimited free sybil account creation.

### Proof of Concept
1. Generate a new ECDSA keypair (Cosmos account never seen on-chain).
2. Query/derive a known, already-deployed UEA address `ueaAddr` for any active user (UEA addresses are deterministically derivable via the factory).
3. Construct `MsgExecutePayload{Signer: <new key's addr>, UniversalAccountId: <victim's UEA id>, UniversalPayload: {..., GasLimit: <large>}, VerificationData: <garbage>}`.
4. Sign the tx with `account_number=0, sequence=0` and submit as a gasless tx (no fee coins).
5. `AccountInitDecorator` creates the new account and lets the tx through the rest of the ante pipeline with zero fee (`app/ante/account_init_decorator.go:52-75`, `app/ante/fee.go:59-64`).
6. `ExecutePayload` dispatches a full `DerivedEVMCall` to the UEA (`x/uexecutor/keeper/msg_execute_payload.go:87`), which reverts on signature check inside the contract, but only after the chain paid the compute cost of executing it.
7. Repeat with a new disposable key for each transaction — no fee, no funding required — to flood the network with forced EVM-execution attempts at zero attacker cost.

Note: I could not verify whether `MsgExecutePayload`/`UniversalPayload.GasLimit` has an upper bound enforced in `ValidateBasic` (the relevant file `x/uexecutor/types/universal_payload.go` / `msg_execute_payload.go` validation logic was not fully retrievable from the index within the available iterations), which would affect how large a single forced EVM call can be. This should be confirmed directly in the repository before finalizing severity.

```markdown
### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.

#### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**
```
