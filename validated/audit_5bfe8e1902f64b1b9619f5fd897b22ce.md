### Title
`ensure_match_transaction_info()` skips validating state/hot-state checkpoint hashes, allowing replay-verify to accept a divergent computed state root — ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the authenticated-comparison routine used by replay/verification tooling to check that a freshly-executed `TransactionOutput` matches the archived, ledger-committed `TransactionInfo`. The function checks status, gas used, write-set hash, and event root hash, but explicitly and admittedly skips the `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash` fields, per its own `TODO` comment.

### Finding Description
In `types/src/transaction/mod.rs`, `ensure_match_transaction_info()` validates several fields of the freshly-computed `TransactionOutput` against the archived `TransactionInfo`, but the code itself documents the gap: [1](#0-0) 

Specifically:
- `status` is checked [2](#0-1) 
- `gas_used` is checked [3](#0-2) 
- `write_set_hash` (`state_change_hash`) is checked [4](#0-3) 
- `event_root_hash` is checked [5](#0-4) 
- but `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that bind the committed ledger state root to the transaction — are never compared, as the inline `TODO(trading-native)` comment states: "this comparator ignores the checkpoint hashes ... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." [6](#0-5) 

This function is consumed directly by `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which re-executes archived transactions with the VM and calls `ensure_match_transaction_info` to decide whether the replay matches the historically committed ledger: [7](#0-6) 

Because the comparator omits the checkpoint-hash fields, replay-verify will report success (`Ok(())`) for a transaction chunk even if the locally recomputed state (Sparse-Merkle/Jellyfish state root, and now the "position" state root introduced alongside `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is different from what was actually committed and authenticated on-chain by validator signatures. This mirrors the external report's bug class exactly: a state/asset-integrity check that exists in a sibling function (write-set/event/gas/status match) but is missing for one specific, security-critical field (the checkpoint/state root), silently allowing a stale/incorrect value to pass verification.

### Impact Explanation
Replay-verify (`db-tool replay-on-archive`, and `aptos-debugger`/CLI paths that call the same function per the earlier `grep_search` hits in `aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`) is the primary mechanism operators and auditors use to confirm that archived history is consistent with actual VM execution, i.e., that the committed ledger state is correct. Because the state-checkpoint-hash comparison is missing, this tool can give a false "successful replay" verdict even though the locally computed state root diverges from the one that was signed off by validators and stored in the durable `TransactionInfo`/accumulator. This can mask state-divergence bugs (including hard-fork-causing divergence) during audits, backup verification, and data-integrity checks — exactly the "authenticated state-view output bound to the wrong version/root" and "hard-fork-only divergence during replay/verification" impact classes called out in the task's Required Impacts.

### Likelihood Explanation
The code path is real and reachable today: `execute_and_verify` in `replay_on_archive.rs` unconditionally calls `ensure_match_transaction_info` with the freshly executed output, and the comparator's omission is not conditioned on any feature flag being enabled — it is unconditional in the current code. The author's own `TODO` comment confirms the gap is intentional-but-unresolved and explicitly names the exact downstream consumer (`replay_on_archive`) that is affected, which is strong internal corroboration that this is a genuine, not-yet-mitigated verification gap rather than a false positive.

### Recommendation
Add checks in `ensure_match_transaction_info()` comparing `self`'s recomputed `state_checkpoint_hash` (and `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` when applicable) against `txn_info.state_checkpoint_hash()` (and friends), following the same `ensure!` pattern used for `write_set_hash` and `event_root_hash`, before any feature that relies on trading-native/position state roots is enabled — as the comment itself recommends.

### Proof of Concept
1. Take an archived block backup and modify (or induce via a hypothetical divergent VM execution) the resulting state root computed for a transaction, while keeping write set, events, gas, and status identical to the archived `TransactionInfo`.
2. Run `db-tool replay-on-archive` (which calls `execute_and_verify` → `ensure_match_transaction_info`) over that version range: [8](#0-7) 
3. Because `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are never compared in `ensure_match_transaction_info`, the call returns `Ok(())` and the divergence is never surfaced, even though the actual ledger state root differs from the one authenticated by validator signatures on the `LedgerInfo`.

*Note: I was unable to fully trace the exact conditions under which `position_state_checkpoint_hash`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` is populated versus `None` in production configurations (index size limits prevented me from reading the full `aptosdb_reader.rs`/`aptosdb_writer.rs` usages), so the precise scope of when this divergence would be non-trivially exploitable (vs. always `None` today) is not fully confirmed locally.*
