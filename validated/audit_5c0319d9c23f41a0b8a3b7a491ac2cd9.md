### Title
Unauthenticated first-caller can seize ownership of the UEA Factory proxy by front-running `initialize` - (File: `x/uexecutor/keeper/genesis.go`, `x/uexecutor/types/abi.go`)

### Summary
Push Chain's `x/uexecutor` module deploys the UEA Factory (proxy + implementation + proxy admin) at genesis via `deployFactoryEA` in `x/uexecutor/keeper/genesis.go`, but the genesis path only writes bytecode and storage slots for the proxy/admin — it never invokes the Factory's `initialize(address initialOwner)` function [1](#0-0) . The Factory ABI exposes `initialize(address initialOwner)` as a public, unauthenticated function [2](#0-1) , matching the exact bug class in the reference report: an initializer with no access control that can be invoked by any unprivileged caller. Because no operator/deployer transaction is coupled atomically to genesis to claim ownership, any external, unprivileged account can call `initialize` on the Factory proxy before the legitimate operator does and become `owner`.

### Finding Description
`deployFactoryEA` performs three raw EVM state-writes at genesis — the implementation, the `ProxyAdmin`, and the `TransparentUpgradeableProxy`-style Factory proxy — using `SetAccount`/`SetCode`/`SetState` directly against `evmKeeper`, bypassing any constructor or initializer logic [3](#0-2) [4](#0-3) . Unlike `deployProxyAdminContract`, which explicitly seeds the `ProxyAdmin`'s owner storage slot at genesis (`SetState(..., common.Hash{}, owner...)`) [5](#0-4) , the Factory contract's owner is never set this way. Instead, the Factory relies on an explicit `initialize(address initialOwner)` call to establish ownership — exactly the pattern the test-harness helper `setupFactoryContract` performs manually against a pre-selected owner account [6](#0-5) .

In production, `InitGenesis` calls `deployFactoryEA` unconditionally on fresh genesis, then returns — with no corresponding call to `initialize` anywhere in the keeper [7](#0-6) . This leaves the deployed Factory proxy in an "un-initialized owner" state (`owner() == address(0)`) as soon as the chain starts producing blocks. `initialize(address initialOwner)` carries no `onlyOwner`/`onlyGovernance` gate in the ABI signature and only OpenZeppelin's `initializer` modifier would prevent *re-initialization*, not a *first* call by an arbitrary address — this mirrors the exact `SwapImpl::initialize` pattern from the reference report, where "lacks access control and can be called... allowing arbitrary reinitialization/initialization of the proxy."

Because the Factory `owner()` subsequently gates `registerNewChain`, `registerUEA`, and — critically — `setUEAProxyImplementation` (all present in `FactoryV1ABI`) [8](#0-7) , whoever wins the race to call `initialize` first gains full control over:
- which bytecode implementation every future UEA (`UEA_EVM`/`UEA_SVM`) proxy points to via `setUEAProxyImplementation`,
- which chains/VMs are registered (`registerNewChain`), and
- which implementation gets bound to a given chain/VM pair (`registerUEA`).

`x/uexecutor` deploys every user's Universal Executor Account through this same Factory (`CallFactoryToDeployUEA` / `DeployUEAV2`) [9](#0-8) , and inbound execution auto-deploys UEAs and deposits PRC20/native funds into them [10](#0-9) . An attacker who becomes Factory owner can point `UEA_PROXY_IMPLEMENTATION` at a malicious implementation that ignores the ECDSA/Ed25519 owner-signature check normally enforced inside `executeUniversalTx` (per the authorization model documented in `x/uexecutor/README.md`) [11](#0-10) , allowing the attacker to drain funds deposited into any newly-deployed UEA, or redirect `depositPRC20`/execution flows to an attacker-controlled destination.

### Impact Explanation
This breaks the "unauthorized UEA execution / unauthorized module-originated EVM execution" invariant explicitly in scope: a malicious, unprivileged actor gains sole administrative control (`owner`) of the system contract responsible for minting/deploying every user's Universal Executor Account, and can then substitute a malicious UEA implementation that bypasses signature verification, enabling theft of funds deposited by any ordinary user through the standard inbound/deposit path. This is a high-impact, protocol-wide compromise, not limited to a single user.

### Likelihood Explanation
Likelihood is high assuming the deployment/operational flow does not couple `initialize` to genesis atomically (e.g., an operator submitting the `initialize` transaction as the very first Push Chain transaction). Because block 1+ is open to ordinary transactions and `initialize` is a plain, un-gated EVM call reachable by any account with minimal gas, an attacker (or a bot watching for freshly-launched Push Chain networks) can trivially win the race by submitting the call before the operator's initialization transaction lands, especially in networks with any mempool visibility or if the operator's init tx is delayed.

Note: I was unable to fully verify from the indexed code whether some out-of-repo genesis/deployment tooling calls `initialize` synchronously within the same genesis block/transaction bundle before the chain accepts any other transaction (e.g., as part of `gentx`/module init flow) — if such a mechanism exists it would close the race window, but no such call was found within `x/uexecutor/keeper/genesis.go`, `InitGenesis`, or any non-test production code path searched.

### Recommendation
- Have `deployFactoryEA` (or `InitGenesis`) atomically initialize the Factory's owner via direct storage write (the same pattern already used for `ProxyAdmin`'s owner slot in `deployProxyAdminContract`), rather than relying on a follow-up `initialize` transaction.
- Alternatively/additionally, gate `initialize` so it can only be invoked once by a known, protocol-controlled sender (e.g., checked against the `uexecutor` module account or an authorized deployer address) and revert for any other caller, matching the recommended `AlreadyInitialized`/owner-not-zero guard pattern cited in the reference report.
- Add an invariant test asserting that immediately after genesis (before any user transaction is processed), `Factory.owner()` is already non-zero and matches the intended operator/module address.

### Proof of Concept
1. Launch a Push Chain network from genesis; `InitGenesis` runs `deployFactoryEA`, deploying the Factory proxy/impl/admin but leaving `owner() == address(0)` [1](#0-0) .
2. Before the legitimate operator's `initialize(operatorAddr)` transaction is included, an attacker submits an EVM transaction calling `initialize(attackerAddr)` on `FACTORY_PROXY_ADDRESS_HEX` using the `FactoryV1ABI` signature [2](#0-1) .
3. The attacker's transaction lands first; `owner()` now returns `attackerAddr` (as demonstrated by the equivalent flow in `setupFactoryContract`, which shows `initialize` immediately setting `owner`) [12](#0-11) .
4. Attacker calls `setUEAProxyImplementation(maliciousImpl)`, redirecting all subsequently deployed UEAs to attacker-controlled bytecode that skips the owner-signature check.
5. Any user's inbound deposit auto-deploys a UEA through this poisoned Factory and funds are stolen when routed through the malicious implementation.

func deployFactoryProxy(ctx context.Context, evmKeeper types.EVMKeeper) {
	sdkCtx := sdk.UnwrapSDKContext(ctx)
	proxyAddress := common.HexToAddress(types.FACTORY_PROXY_ADDRESS_HEX)
	proxyAdminOwner := common.HexToAddress(types.PROXY_ADMIN_ADDRESS_HEX)
	factoryImplAddress := common.HexToAddress(types.FACTORY_IMPL_ADDRESS_HEX)

	// Compute the code hash from the runtime bytecode
	codeHash := crypto.Keccak256(types.ProxyRuntimeBytecode)

	// Create the EVM account object
	evmAccount := statedb.Account{
		Nonce:    1,             // to prevent tx nonce=0 conflicts
		Balance:  new(uint256.Int), // zero balance by default
		CodeHash: codeHash,      // link to deployed code
	}

	// Set the EVM account with the factory proxy contract
	err := evmKeeper.SetAccount(sdkCtx, proxyAddress, evmAccount)
	if err != nil {
		panic("failed to set factory proxy contract account: " + err.Error())
	}

	// Store the runtime bytecode linked to the code hash
	evmKeeper.SetCode(sdkCtx, codeHash, types.ProxyRuntimeBytecode)

	// Update proxyAdmin Slot with the proxyAdmin owner address (left padded to 32 bytes)
	evmKeeper.SetState(sdkCtx, proxyAddress, types.PROXY_ADMIN_SLOT, common.LeftPadBytes(proxyAdminOwner.Bytes(), 32))

	// Update proxyImplementation Slot with the factory implementation address (left padded to 32 bytes)
	evmKeeper.SetState(sdkCtx, proxyAddress, types.PROXY_IMPLEMENTATION_SLOT, common.LeftPadBytes(factoryImplAddress.Bytes(), 32))
}

#### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**
