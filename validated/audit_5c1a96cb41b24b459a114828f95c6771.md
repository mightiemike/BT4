### Title
UnDelegateResourceProcessor (TVM path) prematurely deletes shared V2 delegation index while a locked delegation still exists - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java])

### Finding Description
The claim in the prompt — that `DelegateResourceProcessor`, `FreezeBalanceActuator`, and `DelegateResourceActuator` write *different physical index keys* for the same logical owner/receiver relationship — does not hold. All V2 delegation paths (`DelegateResourceProcessor.delegateResource` [1](#0-0) , `DelegateResourceActuator.delegateResource` via `delegatedResourceAccountIndexStore.delegateV2` [2](#0-1) , and `DelegatedResourceAccountIndexStore.delegateV2`/`unDelegateV2` [3](#0-2) ) derive the exact same physical keys: `V2_FROM_PREFIX + owner + receiver` and `V2_TO_PREFIX + receiver + owner`. `FreezeBalanceActuator` uses a separate, intentionally distinct legacy V1 index (`FROM_PREFIX`/`TO_PREFIX` or `add*` list-based index) tied to the legacy freeze mechanism [4](#0-3) , which is by design a different feature/store key (`DelegatedResourceCapsule.createDbKey` vs `createDbKeyV2`), not a "differently keyed" duplicate of the same relationship.

However, investigating the actual clearing logic between the TVM and wallet unDelegate paths reveals a real asymmetry. `UnDelegateResourceActuator.execute` (wallet path) only deletes the shared V2 index when **both** the locked and unlocked `DelegatedResourceCapsule` entries for the pair are absent: [5](#0-4) 

`UnDelegateResourceProcessor.execute` (TVM path, reachable via `Program.unDelegateResource`, i.e. the `unDelegateResource` opcode/precompile) only checks the **unlocked** `DelegatedResourceCapsule` (`createDbKeyV2(owner, receiver, false)`) before deleting the same shared V2 index keys — it never inspects the locked (`lock=true`) resource entry: [6](#0-5) 

Because the V2 index is shared between locked and unlocked delegations for the same owner/receiver pair (both are indexed only by `owner`+`receiver`, with no lock discriminator), an attacker can create both a locked delegation (via `DelegateResourceActuator` with `lock=true`, a normal wallet call) and an unlocked delegation to the same receiver, then invoke the TVM `unDelegateResource` precompile to fully unDelegate just the unlocked portion. `UnDelegateResourceProcessor` will delete the V2 index entries even though the locked `DelegatedResourceCapsule` (with real, non-zero frozen balance) still exists, producing a state where `DelegatedResourceStore` still contains an active locked delegation but the `DelegatedResourceAccountIndexStore` (V2) has no record linking owner and receiver.

### Impact Explanation
This causes the V2 delegation index (`getV2Index`, exposed via `wallet.getDelegatedResourceAccountIndexV2`) to become inconsistent with the underlying `DelegatedResourceStore`: a locked delegation with real economic value continues to exist and continues to grant the receiver acquired resources, but is no longer discoverable via the standard index used by wallets/explorers to enumerate delegation relationships. This is a state-consistency/invariant-violation bug (silent loss of index entry for an active delegation) rather than a fund-theft bug, since balances/accounting for the locked resource itself are untouched. It affects any consumer relying on the index to discover open delegations (UIs, monitoring, later re-delegation/lock-period validation logic in `DelegateResourceActuator.validate` that reads `DelegatedResourceStore` directly by lock key, not the index, so core protocol accounting is not directly broken, but the public index API becomes wrong).

### Likelihood Explanation
Fully triggerable by an unprivileged account: (1) freeze V2 balance, (2) call `DelegateResourceContract` with `lock=true` to the receiver, (3) delegate additional unlocked balance to the same receiver (via wallet or a TVM contract), (4) deploy/call a contract that invokes the `unDelegateResource` precompile to fully unDelegate the unlocked amount. All steps are ordinary, permissionless transactions/contract calls; no race condition or non-deterministic ordering between nodes is required — this is a deterministic logic bug in `UnDelegateResourceProcessor`, so it reproduces identically on every honest node (no consensus divergence, just a wrong-but-consistent state).

### Recommendation
In `UnDelegateResourceProcessor.execute`, before clearing the V2 index, also fetch and check the locked `DelegatedResourceCapsule` (`createDbKeyV2(ownerAddress, receiverAddress, true)`) exactly as `UnDelegateResourceActuator` does, and only delete the index when both locked and unlocked entries are absent/zero.

### Proof of Concept
Java integration test plan (JUnit, extending existing `UnDelegateResourceActuatorTest`/`FreezeV2Test` fixtures):
1. Freeze V2 bandwidth/energy for `OWNER_ADDRESS`.
2. Call `DelegateResourceActuator` with `lock=true` to delegate part of the balance to `RECEIVER_ADDRESS` (creates `DelegatedResourceCapsule` at `createDbKeyV2(owner, receiver, true)`).
3. Call `DelegateResourceProcessor.execute` (simulating TVM `unDelegateResource`'s sibling call, or directly via `Program.delegateResource`) to delegate an additional unlocked amount to the same receiver (creates `createDbKeyV2(owner, receiver, false)` and populates the shared V2 index).
4. Invoke `UnDelegateResourceProcessor.execute` (simulating the TVM `unDelegateResource` opcode) to fully unDelegate the unlocked amount.
5. Assert:
   - `dbManager.getDelegatedResourceStore().get(createDbKeyV2(owner, receiver, true))` is still non-null with the locked balance intact.
   - `dbManager.getDelegatedResourceAccountIndexStore().getV2Index(owner)` no longer lists `receiver` in `toAccountsList` (bug: index wrongly empty).
   - Compare against the wallet path: repeat steps 2–4 but use `UnDelegateResourceActuator.execute` for step 4 instead, and assert the index **still** lists `receiver` (correct behavior), demonstrating the divergence between the two code paths for equivalent state.

  public void delegateV2(byte[] from, byte[] to, long time) {
    byte[] fromKey = Bytes.concat(V2_FROM_PREFIX, from, to);
    DelegatedResourceAccountIndexCapsule toIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(to));
    toIndexCapsule.setTimestamp(time);
    this.put(fromKey, toIndexCapsule);

    byte[] toKey = Bytes.concat(V2_TO_PREFIX, to, from);
    DelegatedResourceAccountIndexCapsule fromIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(from));
    fromIndexCapsule.setTimestamp(time);
    this.put(toKey, fromIndexCapsule);
  }

  public void unDelegate(byte[] from, byte[] to) {
    byte[] fromKey = Bytes.concat(FROM_PREFIX, from, to);
    this.delete(fromKey);
    byte[] toKey = Bytes.concat(TO_PREFIX, to, from);
    this.delete(toKey);
  }


  public void unDelegateV2(byte[] from, byte[] to) {
    byte[] fromKey = Bytes.concat(V2_FROM_PREFIX, from, to);
    this.delete(fromKey);
    byte[] toKey = Bytes.concat(V2_TO_PREFIX, to, from);
    this.delete(toKey);
  }
