## Title
Missing Validation That `shop` Parameter Matches Session Token's `dest` Claim in Token Exchange - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Summary
The library's `tokenExchange` function decodes and cryptographically verifies a Shopify session token (JWT) but never checks that the token's authenticated `dest` (destination shop) claim matches the separately supplied, caller-controlled `shop` argument. The verified JWT and the untrusted `shop` string are two independent pieces of data that are never cross-checked before the resulting access token is requested and a `Session` is created and stored under the caller-supplied shop.

### Finding Description
`tokenExchange` in [1](#0-0)  calls `decodeSessionToken(config)(sessionToken)` only to validate the JWT signature, expiry and audience (`aud`/API key) — see [2](#0-1) . The decoded `payload` (which contains the shop-identifying `dest`/`iss` claims) is discarded; it is never compared against the `shop` parameter that is passed in independently. The function then sanitizes `shop` and uses it directly to build the target URL (`https://${cleanShop}/admin/oauth/access_token`) and to construct the returned `Session` (`shop: cleanShop`) — see [3](#0-2) .

This is the same bug class as the reported LineaRollup issue: a value that should be checked against data that was actually verified (there: `finalBlockNumber` vs. the last block of submitted/proven data; here: the caller-supplied `shop` vs. the shop embedded in the verified session token) is instead accepted unchecked from an untrusted source, and the mismatch check is silently delegated entirely to a downstream system (there: the prover; here: Shopify's `/admin/oauth/access_token` endpoint).

By contrast, other higher-level integrations in this same repo are careful to always derive `shop` from the verified token's `dest` claim rather than trust a separate parameter, e.g. `getSessionTokenContext` in shopify-app-remix/shopify-app-react-router explicitly does `const dest = new URL(payload.dest); const shop = dest.hostname;` [4](#0-3)  before ever calling `tokenExchange`. However, the public, documented API `shopify.auth.tokenExchange` explicitly instructs developers building non-Remix/non-React-Router apps to source `shop` directly from `req.query.shop` — an attacker-controlled value — independently of the `sessionToken`: [5](#0-4) . The library itself performs no defense-in-depth check that these two values agree before using the untrusted `shop` to build the request and to label the resulting session.

### Impact Explanation
If Shopify's backend token-exchange endpoint does not itself strictly enforce that the JWT's `dest`/`iss` matches the domain used in the token-exchange request, an app that follows the documented usage pattern could exchange a session token issued for one shop against a `shop` value supplied by an unauthenticated request path, resulting in a `Session` object being created/stored under an attacker-chosen shop identifier with an access token from a mismatched context — i.e., cross-tenant session/storage confusion. Even if Shopify's backend independently rejects such mismatches (which cannot be verified from this repository), the shopify-api library's own logic still lacks the local safety check the report's remediation pattern recommends, meaning correctness/security depends entirely on an external service rather than provable local validation.

### Likelihood Explanation
Exploitability strictly depends on how developers wire `shop` into `tokenExchange`. Apps using the built-in `shopify-app-remix`/`shopify-app-react-router` strategies are not affected because they always derive `shop` from the verified `payload.dest` before calling the function [4](#0-3) . Apps that call `shopify.auth.tokenExchange` directly per the documented non-Remix pattern, taking `shop` from an untrusted query parameter, are exposed to this gap, and whether it is exploitable further depends on unverifiable Shopify-side enforcement.

### Recommendation
In `tokenExchange` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), use the `payload` returned by `decodeSessionToken` and verify that the sanitized `shop` matches the hostname derived from `payload.dest` (and/or `payload.iss`) before proceeding, throwing an `InvalidJwtError`/`InvalidShopError` on mismatch — analogous to how `oauth.ts`'s `validQuery` cross-checks `state` against the cookie value [6](#0-5) .

### Proof of Concept
1. An app built with `shopify-app-express` (or any custom integration) calls `shopify.auth.tokenExchange({ shop: req.query.shop, sessionToken, requestedTokenType })`, following the documented pattern in `tokenExchange.md`.
2. An attacker sends a request with a valid session token for `attacker-shop.myshopify.com` (which they legitimately control/install the app on) but sets `shop=victim-shop.myshopify.com` in the query string.
3. `tokenExchange` decodes/verifies the JWT (valid signature, valid `aud`), but never checks `payload.dest` against `shop`; it proceeds to call `https://victim-shop.myshopify.com/admin/oauth/access_token` with the attacker's `subject_token`, and — if that call is accepted, since local library logic performs no mismatch guard — constructs and returns/stores a `Session` labeled with `shop: "victim-shop.myshopify.com"` [7](#0-6) .

export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
