### Title
Stale cached liquidity index used across borrow/repay/liquidation within the same block cache window - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` caches vault liquidity/borrow indexes keyed only by `{ timestamp: stacks-block-time, aid }` via `accrue-and-cache` [1](#0-0) . Multiple public entry points (e.g. `liquidate`, `liquidate-multi`) later read this cache directly with `get-cached-indexes` under an `unwrap-panic`, trusting it reflects the current, correct index for the asset [2](#0-1) . However, the cache is never invalidated when the underlying vault's index actually changes mid-transaction (e.g., via `vault-system-borrow`/`vault-system-repay`/`vault-socialize-debt`, which call into vault contracts directly, not through `accrue-and-cache`) [3](#0-2) .

### Finding Description
`accrue-and-cache` is a per-timestamp memoization: the first call for a given `aid` within a block calls `vault-accrue` and stores the result in `index-cache`; every subsequent call in the same block (same `stacks-block-time`) for that `aid` returns the stale stored value without re-querying the vault [1](#0-0) . This is explicitly documented as a gas optimization to avoid repeated cross-contract calls within one block [4](#0-3) .

The bound value (cached `index`/`lindex`) is invalidated only by a new `stacks-block-time` — never by an intervening state-changing vault call within the same call graph. Functions such as `liquidate`/`liquidate-multi` perform debt repayment and collateral seizure that route through `vault-system-repay`/`vault-socialize-debt` (which internally accrue and mutate the vault's real index/state) and *afterwards* still consult `get-cached-indexes` for computations like `other-borrow-idx` used to size `other-debt-repayable` [2](#0-1) . Because the cache key is timestamp+aid only, any operation that mutates vault index state without going through `accrue-and-cache` (the `vault-system-*`/`vault-socialize-debt` paths bypass it entirely) leaves the market's cached view permanently stale for the rest of the block, for every subsequent transaction/call that hits the cache within that same `stacks-block-time` window.

This matches the "cached value not invalidated when its source moves" analog: the value (`index-cache` entry) is bound once, the source (vault's real index) moves via a direct vault mutation, and the later use (`get-cached-indexes` in liquidation math) still consumes the pre-move value.

### Impact Explanation
Using a stale index for `other-borrow-idx`/`other-debt-repayable` sizing in `liquidate` can under- or over-state how much additional debt is repayable/seizable, causing incorrect bad-debt socialization amounts or incorrect collateral seizure sizing during liquidation — leading to protocol insolvency risk (bad debt not properly socialized) or temporary freezing/misallocation of collateral value, both of which map to the in-scope impact classes.

### Likelihood Explanation
This requires a specific interleaving within a single block: an accrual happening for asset `aid` (caching indexes), followed by a vault-mutating operation (`system-borrow`/`system-repay`/`socialize-debt`) on the same `aid` that changes the real index without refreshing the cache, followed by a `liquidate` call in the same block relying on `get-cached-indexes`. Given `stacks-block-time` only changes per block (not per transaction), and multiple market operations (deposit, borrow, repay, liquidate) can occur in sequence within one block, this is plausible under normal usage/MEV-style bundling rather than requiring any privileged access.

### Recommendation
Invalidate or refresh the `index-cache` entry for an `aid` whenever any vault-mutating call (`vault-system-borrow`, `vault-system-repay`, `vault-socialize-debt`, `vault-deposit`, `vault-redeem`) is made for that asset, or route all such mutations through `accrue-and-cache` first and re-cache the post-mutation index, so `get-cached-indexes` can never be consumed after the source has moved within the same block.

### Proof of Concept
Not independently verifiable from static review alone — a concrete PoC would require simulating a multi-call block (accrue → vault-mutating call on the same `aid` → `liquidate`) in the Clarinet/Clarity test harness under `local-testing/`, which was not run as part of this analysis. I was unable to fully trace whether `vault-system-repay`/`socialize-debt` internally call something equivalent to `vault-accrue` and update `index-cache` implicitly, since the vault contract internals under `mainnet/contracts/vault/` were not retrieved before the iteration limit was reached — this should be confirmed before treating the finding as conclusively exploitable.

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))

## Index Caching in Market

The market contract caches vault indexes per timestamp to avoid redundant vault calls within the same block:

```clarity
;; In market.clar
(define-map index-cache- 
  { timestamp: uint, aid: uint }
  { index: uint, lindex: uint })

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid }))
    ;; Check cache first, accrue vault if needed
    (match (map-get? index-cache- cache-key)
      existing existing
      (let ((fresh (vault-accrue aid)))
        (map-set index-cache- cache-key fresh)
        fresh))))
```

**Benefits:**
- Multiple operations on same vault in one block use cached index
- Reduces cross-contract calls significantly
- Lower gas costs for complex transactions
- Cache automatically invalidates next block (timestamp changes)
