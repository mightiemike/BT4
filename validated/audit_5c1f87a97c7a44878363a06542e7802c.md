### Title
Permanent DoS of the Shielded (zk-SNARK) pool via exhaustion of the 32-bit Sapling Merkle-tree leaf index - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `VerifyMintProof` and `VerifyTransferProof` precompiled contracts (backing the shielded TRC-20 pool used by any smart contract or transaction that calls the shielding precompiles) validate the note-commitment tree position with a hard `TREE_WIDTH` (2^32) bound check on `leafCount`, mirroring exactly the Hats-protocol bug class: a fixed, unprivileged-mintable ID/position space that becomes permanently unusable once exhausted.

### Finding Description
`VerifyMintProof.execute()` reads `leafCount` from caller-supplied ABI data and rejects it only if `leafCount >= TREE_WIDTH`: [1](#0-0) 
Likewise `VerifyTransferProof` bounds-checks `leafCount >= TREE_WIDTH - 1`: [2](#0-1) 
Tests explicitly document that the valid leaf-count domain is `[0, 2^32 - 1]` and that `1L << 32` (and `-1`) are rejected as "wrong leafcount": [3](#0-2) [4](#0-3) 

`leafCount` is the running, monotonically-incrementing position counter of the shielded pool's Incremental Merkle Tree (Sapling depth-32 tree), which every successful mint/transfer into the shielded pool advances by one via `insertLeaves()`: [5](#0-4) [6](#0-5) 

This is functionally identical to the Hats `mintTopHat()` issue: an anonymous, unprivileged caller can drive the same fixed-size counter (top 32 bits / `TREE_WIDTH = 2^32` leaf slots) toward exhaustion by repeatedly minting shielded notes, since minting a shielded note requires no fee gate other than the transparent value being shielded and standard TRX bandwidth/energy — there is no deposit or throttling fee tied to leaf-space consumption itself.

The parallel, non-shielded, mint-like actuators in java-tron (`AssetIssueActuator`'s `tokenIdNum`, `ExchangeCreateActuator`'s `latestExchangeNum`, `ProposalCreateActuator`'s `latestProposalNum`) do **not** share this bug class because their counters are unbounded 64-bit `long`s (via `DynamicPropertiesStore`), e.g.: [7](#0-6) 
so exhausting them is computationally infeasible — only the shielded pool's Sapling-derived 32-bit tree width reproduces the Hats-style fixed, exhaustible identifier space.

### Impact Explanation
If the on-chain shielded note commitment tree's leaf count ever reaches `2^32`, every subsequent `VerifyMintProof` and `VerifyTransferProof` call (and therefore `ShieldedTransferActuator.executeShielded()`, which calls `merkleContainer.saveCmIntoMerkleTree`) would be rejected by the bounds check, permanently freezing the entire shielded TRC-20/TRC-10 pool — no new shielded notes could be minted or transferred, and existing shielded funds could become effectively stuck (spends still require valid Merkle paths/anchors generated against a growable tree). This is a protocol-level DoS of a core privacy feature, not limited to a single actor's assets.

### Likelihood Explanation
Exhausting 2^32 (~4.3 billion) leaf slots requires an enormous number of on-chain shielded mint transactions, each consuming TRX for bandwidth/energy and the `VerifyMintProof` precompile's fixed 150,000 energy cost: [8](#0-7) 
On Ethereum-mainnet-equivalent gas/fee economics this is likely cost-prohibitive, similar to the original Hats report's assessment for ETH mainnet; however, java-tron is deployed as a permissionless public chain where transaction cost is comparatively low and could theoretically be reduced further via config, so the underlying design flaw (a hard, unprivileged-fillable 32-bit position bound with no proportional anti-exhaustion fee) is a real, unmitigated structural risk analogous to the reported bug class, even though full exploitation is currently expensive.

### Recommendation
- Track the shielded pool leaf/position counter as part of consensus-critical state and reject transactions once the tree nears capacity with a clear, permanent error rather than silently returning `Pair.of(true, DataWord.ZERO().getData())` (indistinguishable from a proof-verification failure).
- Consider charging a leaf-consumption fee (in addition to the standard shielded transaction fee) scaled to the finite 2^32 slot budget, so exhausting the tree is economically infeasible, mirroring the report's recommended non-refundable deposit mitigation.
- Add monitoring/alerting on `leafCount` growth rate, and plan a forward migration path (e.g., a new tree/versioned pool) before the tree approaches exhaustion, since `TREE_WIDTH` is fixed by the Sapling protocol's 32-level tree design and cannot be changed without a hard fork.

### Proof of Concept
1. An attacker repeatedly calls the shielded mint precompile/actuator path (`ShieldedTransferActuator` → `VerifyMintProof.execute()`), each time supplying the current `leafCount` and a valid mint proof, incrementing the tree's leaf count by one per call via `insertLeaves()`.
2. Because `leafCount` is only rejected once `leafCount >= TREE_WIDTH` (2^32), an attacker with sufficient TRX to pay bandwidth/energy for ~4.29 billion mint transactions can drive the shielded pool's Merkle tree to full capacity.
3. Once `leafCount == TREE_WIDTH`, every future call to `VerifyMintProof` or `VerifyTransferProof` for the shielded pool returns a failure result (as verified by the `verifyMintWrongLeafcount`/`verifyTransferWrongLeafcount` tests using `leafCount = 1L << 32`), permanently disabling shielding and shielded transfers protocol-wide without a hard fork to redesign the tree.

        int offset = 0;
