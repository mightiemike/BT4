### Title
`ensure_match_transaction_info` skips state/hot-state checkpoint hash validation, allowing replay-verify to accept a divergent committed state root - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-record comparator used by `db-tool`'s `replay_on_archive` (and the debugger/CLI replay paths) to verify that a freshly re-executed transaction output matches the transaction info that was actually signed and committed to the ledger (from a backup/archive). The function only compares `status`, `gas_used`, `state_change_hash` (write-set hash) and `event_root_hash`. It explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the Merkle roots that summarize the actual world-state after the transaction.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates the kept status, gas used, write-set hash, and event root hash, but the function's own comment acknowledges the gap: [2](#0-1) 

Because the state/hot-state checkpoint hash (and the new `position_state_checkpoint_hash` field on `TransactionInfoV1`) is never re-derived from the locally-computed post-state Sparse Merkle Tree and compared against the value in the authenticated `TransactionInfo` pulled from the backup, `replay_on_archive::Verifier::execute_and_verify` — the only caller that performs an unprivileged, standalone verification of archived ledger history against local VM re-execution — will report success even when the locally-recomputed world state differs from the one whose root was originally signed by validators. See the call site: [3](#0-2) .

`TransactionInfoV0`/`V1` carry the `state_checkpoint_hash` field specifically to bind a `TransactionInfo` (and therefore the value fed into the transaction accumulator and eventually into `LedgerInfo`) to one exact state-tree root: [4](#0-3) . Skipping this comparison breaks the "authenticated response/proof must stay bound to the right ledger version and root" invariant for this verification tool: a write-set hash and event root can match while the resulting state tree (and thus the checkpoint root) is wrong, e.g. due to a bug in state-value metadata handling, hot-state/position-state merge logic, or a divergent state-key encoding that produces the same serialized write-set bytes hash but writes to a different logical state slot.

### Impact Explanation
`replay-verify` / `replay_on_archive` is the mechanism used to detect state divergence between a re-executed history and the historically-committed (validator-signed) ledger — it is the last line of defense for catching state-corrupting bugs (including hard-fork-only divergences) after the fact. Because the state-checkpoint-hash fields are excluded from the comparison, this tool can silently pass even though the recomputed state tree diverges from the authenticated one, hiding exactly the class of bug the gate is concerned with ("committed state that differs from the correct VM result" / "hard-fork-only divergence during commit, replay ... verification"). This does not directly corrupt consensus-committed state on mainnet (the normal execution/commit path is separate and still authenticates the checkpoint hash through the accumulator/`LedgerInfo` signature), but it removes the only automated backstop for detecting such corruption during replay/audit, which is a high-severity gap in the proof/storage integrity tooling.

### Likelihood Explanation
The gap is unconditionally present in every call to `ensure_match_transaction_info`, including the `db-tool replay-verify` production path used to audit mainnet archives, `aptos-debugger`, and the `aptos` CLI replay command. No feature flag needs to be enabled for the comparator itself to skip checkpoint-hash validation — the code comment ties it to enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, but the check is already absent today regardless of that flag's state, so any bug producing a matching write-set/event hash while corrupting the derived state tree would go undetected right now.

### Recommendation
In `ensure_match_transaction_info`, recompute the local post-state checkpoint hash (and hot-state / position-state checkpoint hash when present) and assert equality against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` whenever those fields are `Some` in the expected `TransactionInfo`, mirroring the existing `write_set_hash` / `event_root_hash` checks, rather than deferring this to a future feature flag.

### Proof of Concept
1. Run `db-tool replay-verify` (`replay_on_archive.rs`) against a backup range containing a transaction whose re-execution produces write ops that serialize (and hash) identically for `state_change_hash`/events but land on a different `StateKey`/resource-group slot than the originally committed values (e.g., a bug in resource-group tag mapping or state-value-metadata handling that changes *where* a value is written without changing the write-set's own hash contribution).
2. `execute_and_verify` calls `ensure_match_transaction_info` at [5](#0-4) , which checks status/gas/write_set_hash/event_root_hash only.
3. Because `state_checkpoint_hash` is never recomputed/compared, the verifier returns `Ok(None)` (no error) for this chunk even though the local Sparse Merkle Tree root would not match the checkpoint hash embedded in the authenticated `TransactionInfo`, i.e., the divergence is silently accepted as "verified."

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
