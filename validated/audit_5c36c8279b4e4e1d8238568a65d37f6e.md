### Title
Misconfigured/too-low `BouncerConfig.block_max_capacity` constants permanently reject legitimate transactions and L1 messages, causing frozen L1→L2 messages and unconfirmable transactions - ([File: crates/blockifier/src/bouncer.rs], [File: crates/blockifier/src/transaction/transaction_execution.rs])

### Summary
The reported bug is that a protocol parameter (`maxGas`) that bounds the resource consumption of a certain operation, if set too low by governance/config, makes the corresponding action unconditionally and permanently fail. The sequencer has a structurally identical parameter: `BouncerConfig.block_max_capacity` (a `BouncerWeights` struct with `l1_gas`, `sierra_gas`, `proving_gas`, `message_segment_length`, `n_events`, `state_diff_size`, `receipt_l2_gas`, `n_txs`), which is set from `VersionedConstants`/node configuration, not from the transaction sender. Any single transaction (or L1→L2 message) whose intrinsic resource footprint exceeds this fixed constant can never be included in *any* block, regardless of resubmission, fee bump, or which block builder processes it.

### Finding Description
Every transaction executed via `Transaction::execute_raw` is checked with `verify_tx_weights_within_max_capacity`, which in turn calls `BouncerConfig::within_max_capacity_or_err`: [1](#0-0) [2](#0-1) 

This check compares the transaction's own resource weights against the constant `block_max_capacity` (an absolute, per-block ceiling defined by governance/versioned constants) - not against the bouncer's remaining room in the currently-building block: [3](#0-2) 

If the check fails, the caller (`TransactionExecutor::execute`) aborts the transactional state and returns a hard `TransactionExecutionError::TransactionTooLarge`, distinct from the transient `BlockFull` case: [4](#0-3) [5](#0-4) 

Because the comparison is against the fixed `block_max_capacity` constant (analogous to `maxGas`), and not against "room left in the current block," a transaction that is intrinsically too large relative to this constant will fail identically on every retry, in every block, forever - there is no way for the sender to fix this by increasing fees or resource bounds, since the failure is driven by governance-set capacity constants, not by the sender's own resource-bound parameters.

This is most severe for `L1Handler` transactions (messages bridged from L1), which are mandatory, non-optional, and must be processed exactly once by the Starknet OS. If `block_max_capacity` is configured too low relative to a legitimate L1→L2 message's resource footprint (e.g., due to a governance misconfiguration or a change in `VersionedConstants` that shrinks the effective capacity), that L1Handler message becomes permanently unprocessable, blocking the L1→L2 message queue and freezing any funds/state transition tied to that message.

### Impact Explanation
- A class of legitimate account transactions can become permanently un-confirmable network-wide (matches the "network unable to confirm new transactions" impact criterion), since the rejection is deterministic and identical for every proposer/validator (all use the same `VersionedConstants`/`BouncerConfig`).
- For L1Handler transactions specifically, this can produce permanent freezing of funds: an L1→L2 bridge message that is inherently too large relative to a misconfigured `block_max_capacity` can never be executed by any sequencer, and since L1 handler messages must be processed in order, this can also block all subsequent L1 handler messages from that L1 contract, freezing bridged assets indefinitely.
- This is a configuration/versioned-constants risk analogous to the reported `maxGas` issue: a single miscalibrated constant (too low relative to real-world transaction/class resource costs) silently converts "the block is momentarily full" into "this transaction/message can never be included."

### Likelihood Explanation
Reachable by any unprivileged transaction sender or L1 message emitter: they simply need to submit a transaction (or trigger an L1→L2 message) whose intrinsic resource weights (events, calldata/state-diff size, sierra/proving gas) exceed `block_max_capacity`. No special privileges are required to trigger the failure path itself; the only precondition is that governance/protocol constants have set `block_max_capacity` too low relative to realistic transaction/message sizes - the same precondition the external report flags for `maxGas`. Given that `block_max_capacity` is derived from evolving `VersionedConstants` (as seen across protocol versions, e.g. `blockifier_versioned_constants_0_14_3.json`), the risk of a mismatched/too-tight configuration recurring across upgrades is non-trivial.

### Recommendation
- Distinguish "transaction cannot fit in an empty block" (`TransactionTooLarge`, computed against `block_max_capacity` alone) from "no room left in current block" (`BlockFull`) more rigorously in monitoring/alerting, and add CI/governance-time validation that runs realistic worst-case transactions (especially L1Handler messages with maximal legitimate calldata/event counts) against every new `BouncerConfig`/`VersionedConstants` release to guarantee no legitimate transaction class becomes permanently unfit.
- For L1Handler transactions in particular, consider enforcing a floor on `block_max_capacity` fields derived from `l1_handler_max_amount_bounds` (already present in `VersionedConstants`, e.g. `l1_handler_max_amount_bounds.l2_gas`) so a message that passes L1-side bounds checks can never subsequently fail the bouncer's block-capacity check.
- Apply the same governance safeguards Morpho committed to in the referenced report (e.g., a time-locked change window and mandatory testing against real transaction/message size distributions) before any `BouncerConfig`/`VersionedConstants` update that touches `block_max_capacity`.

### Proof of Concept
Existing tests already demonstrate the exact failure mode when `block_max_capacity` is set too tight relative to a transaction's weights: [6](#0-5) [7](#0-6) 

In both, setting a capacity field too low unconditionally causes `TransactionExecutionError::TransactionTooLarge` ("Transaction size exceeds the maximum block capacity") - the same transaction would fail this way in any block, on any sequencer, for as long as the configuration stands, exactly mirroring the analog `maxGas`-too-low failure mode described in the external report, with the added severity that for `L1Handler` transactions this failure is permanent and unavoidable by the message's origin (freezing the corresponding L1→L2 flow).

    pub fn within_max_capacity_or_err(
        &self,
        weights: BouncerWeights,
    ) -> TransactionExecutionResult<()> {
        if self.block_max_capacity.has_room(weights) {
            Ok(())
        } else {
            Err(TransactionExecutionError::TransactionTooLarge {
                max_capacity: Box::new(self.block_max_capacity),
                tx_size: Box::new(weights),
            })
        }

#[rstest]
fn test_transaction_too_large_sierra_gas_based(block_context: BlockContext) {
    let mut state = test_state(&block_context.chain_info, Fee(0), &[]);
    let mut transactional_state = TransactionalState::create_transactional(&mut state);
    let block_max_capacity = BouncerWeights { sierra_gas: GasAmount(20), ..Default::default() };
    let bouncer_config = BouncerConfig { block_max_capacity, ..Default::default() };

    // Use gas amount > block_max_capacity's.
    let exceeding_gas = GasAmount(30);
    let execution_summary = ExecutionSummary::default();
    let builtin_counters = CairoPrimitiveCounterMap::default();
    let tx_resources = TransactionResources {
        computation: ComputationResources { sierra_gas: exceeding_gas, ..Default::default() },
        ..Default::default()
    };
    let tx_state_changes_keys = transactional_state.to_state_diff().unwrap().state_maps.keys();

    let result = verify_tx_weights_within_max_capacity(
        &transactional_state,
        &execution_summary,
        &builtin_counters,
        &tx_resources,
        &tx_state_changes_keys,
        &bouncer_config,
        &block_context.versioned_constants,
        GasAmount::ZERO,
    )
    .map_err(TransactionExecutorError::TransactionExecutionError);

    let expected_weights = BouncerWeights {
        sierra_gas: exceeding_gas,
        n_txs: 1,
        proving_gas: exceeding_gas,
        ..BouncerWeights::empty()
    };

    assert_matches!(result, Err(
        TransactionExecutorError::TransactionExecutionError(
            TransactionExecutionError::TransactionTooLarge { max_capacity, tx_size }
        )
    )  if *max_capacity == bouncer_config.block_max_capacity && *tx_size == expected_weights);
}

/// Verifies that a transaction is rejected when the bouncer config has tight capacity limits.
///
/// Sets `n_txs: 0` so that any transaction exceeds the block capacity, and asserts that
/// execution returns `TransactionExecutionError` with a "Transaction size exceeds" message.
#[rstest]
#[ignore] // Requires RPC access
fn test_execute_rejected_by_tight_bouncer_limits(
    rpc_virtual_block_executor: RpcVirtualBlockExecutor,
) {
    // Override the bouncer config with zero capacity so any transaction is too large.
    let mut executor = rpc_virtual_block_executor;
    let mut bouncer_config = BouncerConfig::max();
    bouncer_config.block_max_capacity.n_txs = 0;
    executor.config.bouncer_config = bouncer_config;

    let (tx, tx_hash) = construct_balance_of_invoke();
    let contract_class_manager = ContractClassManager::start(ContractClassManagerConfig::default());

    let error = match executor.execute(
        BlockId::Number(BlockNumber(TEST_BLOCK_NUMBER)),
        contract_class_manager,
        vec![(tx, tx_hash)],
    ) {
        Err(error) => error,
        Ok(_) => panic!("Execution should fail when bouncer capacity is zero"),
    };

    assert_matches!(
        error,
        VirtualBlockExecutorError::TransactionExecutionError(msg)
            if msg.contains("Transaction size exceeds the maximum block capacity")
    );
}
