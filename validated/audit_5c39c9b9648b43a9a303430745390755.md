### Title
Fragmentation-unaware integer division in `many_ref_accounts_can_be_moved` allows multi-ref accounts to be packed into a target slot below their current slot - ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
`AccountsDb::many_ref_accounts_can_be_moved` estimates how many packed target slots are needed for multi-ref ("many_refs_newest") accounts using a simple `alive_bytes / ideal_storage_size + 1` division, but the actual bin-packer `PackedAncientStorage::pack` can fragment those same bytes into *more* storages than this estimate when individual account sizes prevent perfect packing. This mismatch lets `combine_ancient_slots_packed_internal` assign a multi-ref account to a target slot lower than the slot it currently lives in, violating the documented invariant that such accounts "must be moved a slot >= each account's current slot."

### Finding Description
`many_ref_accounts_can_be_moved` computes:
```rust
let required_ideal_packed = (alive_bytes as u64 / tuning.ideal_storage_size + 1) as usize;
...
let highest_slot = target_slots_sorted[i_last];
many_refs_newest.iter().all(|many| many.slot <= highest_slot)
``` [1](#0-0) 

This assumes the total `alive_bytes` of the multi-ref accounts will fit into `ceil(alive_bytes / ideal_storage_size)` packed storages (the "top" `required_ideal_packed` entries of `target_slots_sorted`), and it only requires that all `many_refs_newest` slots be `<=` the smallest of those top slots.

However, the actual packer `PackedAncientStorage::pack` greedily fills one storage at a time and, when adding the next account would exceed `ideal_size`, it stops early and starts a *new* storage rather than splitting the account — this is by design since accounts cannot be split across storages:
```rust
if new_size > ideal_size && bytes_total > 0 {
    full = true;
    break;
}
``` [2](#0-1) 

If the `many_refs_newest` entries are sized (e.g., each entry's account(s) just over half of `ideal_storage_size`) such that pairs cannot share a storage, the packer produces one storage per entry — i.e. more storages than `ceil(alive_bytes / ideal_storage_size)`. `combine_ancient_slots_packed_internal` places `many_refs_newest` first in the packing iterator (so it consumes the *first* chunks of `pack`), and `write_packed_storages` assigns those first chunks to the *highest* target slots in `target_slots_sorted` in order:
```rust
let packer = accounts_to_combine.target_slots_sorted.iter().rev().zip(packed_contents)...
``` [3](#0-2) 

Because the check only validated that `highest_slot` (computed from the *underestimated* `required_ideal_packed`) is `>=` all `many_refs_newest` slots, but the actual bin-packer consumes more target slots than `required_ideal_packed`, later (lower-priority) multi-ref chunks get assigned to target slots *below* the estimate's `highest_slot` — potentially below the account's own current slot. `write_one_packed_storage`/`write_ancient_accounts` write the account to whatever `target_slot` they are handed with no runtime check that `target_slot >= account.slot`:
```rust
fn write_one_packed_storage<'a, 'b: 'a>(&'b self, packed: &'a PackedAncientStorage<'a>, target_slot: Slot, ...) {
    let accounts_to_write = StorableAccountsBySlot::new(target_slot, accounts_to_write, self);
    ...
    self.write_ancient_accounts(*bytes_total, accounts_to_write, write_ancient_accounts)
}
``` [4](#0-3) 

No other guard (the later `pack.len() > accounts_to_combine.target_slots_sorted.len()` check) catches this, because it only checks the *total* number of storages against the *total* number of available target slots, not that specifically the multi-ref data lands at or above its required slot floor.

### Impact Explanation
This causes an alive, ref_count>1 account (one whose current index entry is the "newest" live version) to be rewritten into a packed ancient append vec at a slot lower than its true current slot. This breaks the core AccountsDb invariant that "the highest slot # where an account exists defines the most recent account" (explicitly called out in the surrounding code comments at accounts-db/src/ancient_append_vecs.rs lines 879-885), which can cause the wrong (stale) account version to be treated as newest at a given fork slot, leading to bank hash / capitalization divergence after ancient packing. This maps to the "silent balance change / hash divergence from account version changing without a transaction" bounty category.

### Likelihood Explanation
Triggering this requires an attacker to arrange multiple ancient-eligible slots where the same pubkey is alive with `ref_count > 1` (achievable by repeatedly rewriting the same account across enough distinct slots without triggering a `clean` that reduces it to `ref_count == 1`), sized so that the `many_refs_newest` alive-byte total causes bin-packing fragmentation relative to the dynamically computed `tuning.ideal_storage_size` (`ancient_slot_infos.total_alive_bytes * 2 / max_ancient_slots`, itself influenced by attacker-controlled account counts/sizes). This is a self-contained AccountsDB background pathway reachable purely by an unprivileged accounts owner controlling account keys, sizes and write frequency, with no validator/leader/staked privileges required. It requires some precision in sizing to reliably reproduce (to make `required_ideal_packed`'s floor-division underestimate the actual number of `pack()` storages), but is deterministic and repeatable once the size/slot layout is found via the same formulas present in the code.

### Recommendation
Make `many_ref_accounts_can_be_moved`'s estimate match (or bound) the actual number of storages `PackedAncientStorage::pack` will produce for the `many_refs_newest` set specifically — e.g., by running (or simulating) `PackedAncientStorage::pack` on just the `many_refs_newest` accounts first to get an exact/worst-case storage count, rather than a coarse `total_bytes / ideal_size` division that assumes perfect packing efficiency. Alternatively, add an explicit post-hoc assertion/guard in `write_packed_storages` (or right after `PackedAncientStorage::pack`) that verifies, for every multi-ref account chunk, the assigned `target_slot >= account_original_slot`, and abort/skip the packing round (as is already done for the `many_ref_accounts_can_be_moved` failure case) if violated, instead of silently writing to storage.

### Proof of Concept
Add a targeted unit test exercising `PackedAncientStorage::pack` fragmentation vs. `many_ref_accounts_can_be_moved`'s estimate, and a broader invariant test around `combine_ancient_slots_packed_for_tests`:

```rust
#[test]
fn test_many_ref_accounts_can_be_moved_fragmentation_underestimate() {
    let ideal_size = 1000u64;
    let tuning = PackedAncientStorageTuning {
        ideal_storage_size: NonZeroU64::new(ideal_size).unwrap(),
        ..default_tuning()
    };

    // 3 multi-ref "slots" each with a single ~600-byte account: pairs can't share
    // a 1000-byte storage, so PackedAncientStorage::pack needs 3 storages,
    // but many_ref_accounts_can_be_moved's floor(1800/1000)+1 = 2.
    let many_refs_newest = vec![
        AliveAccounts { bytes: 600, slot: 9, accounts: /* one 600-byte AccountFromStorage */ vec![] },
        AliveAccounts { bytes: 600, slot: 7, accounts: vec![] },
        AliveAccounts { bytes: 600, slot: 5, accounts: vec![] },
    ];
    // target slots: two "safe" high slots (20, 30) above all many_refs_newest.slot,
    // plus several lower slots (1..4) that must NOT receive slot-5's data.
    let target_slots_sorted = vec![1, 2, 3, 4, 20, 30];

    // Estimate says it's safe:
    assert!(AccountsDb::many_ref_accounts_can_be_moved(
        &many_refs_newest, &target_slots_sorted, &tuning
    ));

    // But actual packing needs 3 storages for many_refs_newest alone:
    let pack = PackedAncientStorage::pack(many_refs_newest.iter(), tuning.ideal_storage_size);
    assert!(pack.len() >= 3);

    // Simulate write_packed_storages' assignment: target_slots_sorted.rev() zipped with pack.
    let assigned: Vec<Slot> = target_slots_sorted.iter().rev().take(pack.len()).cloned().collect();
    // The 3rd chunk (containing slot-5's account) is assigned target_slots_sorted[3] == 4,
    // which is LESS than the account's own current slot (5) -> invariant violated.
    assert!(assigned[2] < many_refs_newest[2].slot, "invariant violated: assigned {} < original slot {}", assigned[2], many_refs_newest[2].slot);
}
```

A broader property/fuzz test should build randomized many-ref pubkey configurations sized near `ideal_storage_size` boundaries across several ancient slots, call `combine_ancient_slots_packed_for_tests`, and assert (as `test_shrink_packed_ancient`/`compare_all_accounts` already do for the non-adversarial case) that `get_all_accounts` before and after matches exactly, and additionally assert no account's post-pack storage slot is lower than its pre-pack slot list slot.
