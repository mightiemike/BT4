### Title
Committee governance can toggle `UNFREEZE_DELAY_DAYS` to block already-vested `WithdrawExpireUnfreezeContract` withdrawals - (File: `framework/src/main/java/org/tron/core/consensus/ProposalService.java`)

### Summary
`WithdrawExpireUnfreezeActuator.validate()` gates withdrawal of already-expired unfrozen TRX behind `dynamicStore.supportUnfreezeDelay()`, a dynamic-property flag that is set by committee (witness) governance proposals through `ProposalService.process`. Unlike most other "enable-once" feature flags in that same switch statement, the `UNFREEZE_DELAY_DAYS` case has no one-way guard, so the value (and therefore the derived support flag) can be changed at any time by a passing proposal — including being set back to a value that makes `supportUnfreezeDelay()` return `false`. This mirrors the Rocket Pool bug class: a withdrawal that a user is otherwise entitled to (funds already past their unfreeze-expiration time, principal already computed and waiting in `unfrozenV2List`) can be blocked purely by a governance-side state change, breaking the invariant that a legitimately unlockable balance can always be withdrawn.

### Finding Description
The withdrawal path works as follows:
- `UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor` place funds into `accountCapsule`'s `unfrozenV2List` with an `unfreezeExpireTime` [1](#0-0) .
- To actually move that already-expired amount into spendable `balance`, the user must submit a `WithdrawExpireUnfreezeContract`, processed by `WithdrawExpireUnfreezeActuator.execute`/`validate` [2](#0-1) .
- `validate()` unconditionally requires `dynamicStore.supportUnfreezeDelay()` to be true, otherwise it throws `ContractValidateException("Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee")` [3](#0-2) .

This gate is controlled by the `UNFREEZE_DELAY_DAYS` proposal type, processed in `ProposalService.process`: [4](#0-3) 

Compare this to other feature-toggle cases in the very same switch statement (e.g. `ALLOW_CANCEL_ALL_UNFREEZE_V2`, `ALLOW_MULTI_SIGN`, `ALLOW_ADAPTIVE_ENERGY`), which are guarded with `if (get...() == 0) { save...(entry.getValue()); }` — an explicit one-way/irreversible-enable pattern [5](#0-4) [6](#0-5) . The `UNFREEZE_DELAY_DAYS` case has no such guard and unconditionally overwrites the stored value on every successful proposal, meaning the underlying delay/support value used to gate `WithdrawExpireUnfreezeContract` can be flipped at will by a future proposal, including being reduced or reset in a way that causes `supportUnfreezeDelay()` to evaluate to `false` after having previously been `true`.

Once that happens, any user whose principal has already legitimately reached its `unfreezeExpireTime` (i.e., they are contractually entitled to withdraw per the previously-agreed unfreeze schedule) will have `WithdrawExpireUnfreezeActuator.validate()` reject their transaction, even though `execute()` itself would have succeeded and correctly moved the exact funds into `balance` [7](#0-6) . This is analogous to the Rocket Pool finding where a governance-controlled contract (`RocketMinipoolManager`) could be altered to block a withdrawal that should always succeed once a user is eligible — here the "network contract" is the dynamic-parameter store controlled by committee proposals, and the withdrawal-blocking mechanism is the `validate()` precondition rather than a call-failure, but the resulting invariant break is the same: funds that are already unlocked per protocol rules become permanently stuck pending another governance action.

### Impact Explanation
If the flag is toggled off after having been on, users with expired `UnFreezeV2` entries cannot submit a successful `WithdrawExpireUnfreezeContract` to realize their already-due principal; their TRX remains locked in `unfrozenV2List` indefinitely, purely due to a governance-controlled dynamic parameter, not due to any fault or action of the user. This is a settlement/accounting-availability impact: previously agreed, already-expired unlock amounts become non-withdrawable.

### Likelihood Explanation
This requires a successful witness-committee proposal (2/3+ super-majority of active witnesses) to change `UNFREEZE_DELAY_DAYS` after it has already been enabled — the same threshold as any other network parameter proposal in java-tron. This is not a single-actor attack but is reachable through ordinary, sanctioned governance flow, without needing a malicious contract upgrade, unlike the Rocket Pool scenario, which lowers the barrier compared to Rocket Pool's requirement of a full contract replacement.

### Recommendation
Do not gate `WithdrawExpireUnfreezeContract.validate()` on a governance flag that can be toggled at will after having been enabled once. Treat `UNFREEZE_DELAY_DAYS`/`supportUnfreezeDelay` the same as the other one-way feature switches in `ProposalService.process` (guard with `if (get...() == 0)`), or entirely decouple withdrawal eligibility for already-expired `UnFreezeV2` entries from any governance-mutable flag so that once funds are past their `unfreezeExpireTime`, their withdrawal cannot be blocked by a later proposal.

### Proof of Concept
1. Committee passes a proposal enabling `UNFREEZE_DELAY_DAYS` (nonzero), enabling `FreezeBalanceV2Contract`/`UnfreezeBalanceV2Contract`/`WithdrawExpireUnfreezeContract` per `ProposalService.process` [4](#0-3) .
2. Alice freezes and later unfreezes via `UnfreezeBalanceV2Actuator`, placing her balance into `unfrozenV2List` with expiry `now + unfreezeDelayDays * FROZEN_PERIOD` [1](#0-0) .
3. Time passes; her entry's `unfreezeExpireTime` is now in the past — she is entitled to withdraw via `WithdrawExpireUnfreezeContract`.
4. Before she submits the withdrawal, committee passes another `UNFREEZE_DELAY_DAYS` proposal (e.g., value causing `supportUnfreezeDelay()` to become false) — processed unconditionally by the same code path with no reversibility guard [4](#0-3) .
5. Alice submits `WithdrawExpireUnfreezeContract`; `validate()` now throws `ContractValidateException("Not support WithdrawExpireUnfreeze transaction, need to be opened by the committee")` [3](#0-2) , even though her funds already satisfy the expiry condition checked inside `execute()`. Her already-due principal is stuck.

**Note on confidence**: I could not directly retrieve the body of `DynamicPropertiesStore.supportUnfreezeDelay()` due to indexing/tool limits in this session, so the exact boolean condition it checks (e.g., `getUnfreezeDelayDays() != 0` vs. some other stored flag) is inferred from naming convention and the way it's paired with `getUnfreezeDelayDays()`/`saveUnfreezeDelayDays()` in the same file. I recommend a Devin session with full repository access to confirm this implementation before treating this as conclusively exploitable.

      withdrawExpireUnfreezeContract = any.unpack(WithdrawExpireUnfreezeContract.class);

        withdrawExpireUnfreezeContract.getOwnerAddress().toByteArray());
