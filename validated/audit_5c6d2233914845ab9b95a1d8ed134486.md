This confirms `create_account` requires the `to` address to sign only during allocate/assign (the atomic creation step), but that signature requirement does **not** carry over to a later, separate `InitializeNonceAccount` instruction, since `initialize_nonce_account` only checks `is_writable()`, never `is_signer()`.

### Title
Front-runnable `InitializeNonceAccount` allows an attacker to seize nonce authority and drain the account - (File: programs/system/src/system_instruction.rs)

### Summary
The System Program's `InitializeNonceAccount` instruction sets the nonce account's `authority` field to whatever pubkey is passed in the instruction data, and it only requires the target nonce account to be **writable** — it never requires the nonce account (or any pre-existing owner-designated key) to **sign**. This mirrors the TRST-H-2 pattern: a state-defining "initialize" call is permissionless and can be front-run by anyone observing the pending transaction, letting an attacker set the critical parameter (here, the `nonce_authority`) before the legitimate creator's initialize transaction lands, and the account subsequently rejects any correction because it is no longer `Uninitialized`.

### Finding Description
`initialize_nonce_account` only validates writability of the account and that its current state is `State::Uninitialized`; it does not check that the account itself, or any specific caller, has signed: [1](#0-0) 

The dispatcher in `system_processor.rs` likewise requires only 1 instruction account (the nonce account) plus the recent-blockhashes and rent sysvars — no signer check on the nonce account itself: [2](#0-1) 

By contrast, `System::CreateAccount` *does* require the new account to sign in the same transaction (via `allocate`/`assign`'s `address.is_signer(signers)` check): [3](#0-2) 

This asymmetry means: once an account has been created (system-owned, empty/zeroed data — i.e., deserializes as `State::Uninitialized`) but before it has been initialized as a nonce account, **anyone** can submit a standalone `InitializeNonceAccount` instruction naming that account and any `authority` pubkey they choose. Because the state machine only allows the transition `Uninitialized -> Initialized` once (a second call on an already-`Initialized` account returns `InstructionError::InvalidAccountData`, as covered by `initialize_inx_initialized_account_fail`) the legitimate creator's subsequent `InitializeNonceAccount` call will fail, permanently leaving the attacker as the `authority`: [4](#0-3) 

Once the attacker controls `authority`, they control `AdvanceNonceAccount`, `AuthorizeNonceAccount`, and critically `WithdrawNonceAccount`, which lets the authority holder drain the account's lamports entirely once the nonce is stale relative to the current blockhash (no additional signature from the original funder is required): [5](#0-4) 

The safe/expected usage path bundles `CreateAccount` + `InitializeNonceAccount` atomically in a single transaction, as done by `solana_system_interface::instruction::create_nonce_account` and consumed by the CLI's nonce-creation flow: [6](#0-5) 
However, nothing in the runtime or the instruction itself enforces this atomicity — any wallet, program, or multi-step workflow (e.g., pre-funding a nonce account address ahead of time and initializing it later, a pattern explicitly supported by `create_account_with_seed`/`create_nonce_account_with_seed`) is exposed to front-running of the initialize step.

### Impact Explanation
This is a concrete theft-of-funds vector: an attacker who front-runs `InitializeNonceAccount` becomes the sole `authority` over the target account and can subsequently withdraw all of its lamports via `WithdrawNonceAccount`, at the victim's expense, with no signature from the victim required after the fact. This affects any ordinary client using a two-step (non-atomic) nonce-account setup, which is a documented and used pattern (`create_nonce_account_with_seed` in the CLI separates creation planning from submission in the offline-signing flow).

### Likelihood Explanation
Exploitability requires only observing a pending `InitializeNonceAccount`-eligible account (a system-owned, zero-data, non-zero-lamport account) — either from mempool/gossip observation of the victim's `CreateAccount` transaction, or simply by scanning on-chain state for such accounts (e.g., pre-funded but not-yet-initialized nonce accounts, which are a normal reachable state) — and racing a single cheap `InitializeNonceAccount` transaction ahead of the legitimate one. No special privilege, CPI, or program deployment is needed; it is reachable directly from an ordinary client transaction against the builtin System Program.

### Recommendation
Require that `InitializeNonceAccount` additionally checks that the nonce account (or a designated creation-time authority) is a transaction signer, mirroring the `CreateAccount` signer requirement, so that only the party who created/funded the account (or an authority they nominate at creation) can perform the first initialization. Alternatively/additionally, document and enforce (at the instruction-builder level for all first-party tooling) that `CreateAccount` and `InitializeNonceAccount` must always be composed atomically in one transaction, and consider adding a runtime-level warning/guard for standalone `InitializeNonceAccount` instructions targeting accounts with no prior transaction history tying them to the fee payer.

### Proof of Concept
1. Victim's wallet submits transaction T1: `SystemInstruction::CreateAccount { lamports: rent_exempt_min, space: nonce::State::size(), owner: system_program::id() }` for a freshly generated nonce keypair `N`, intending to send a follow-up transaction T2: `SystemInstruction::InitializeNonceAccount(victim_authority)`.
2. Attacker observes T1 land (or observes address `N` in mempool/gossip) and immediately submits transaction T_evil: `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` targeting the same account `N`, needing no signature from `N` or the victim — only writability, per `initialize_nonce_account` (programs/system/src/system_instruction.rs:169-176).
3. T_evil lands first; `N`'s state becomes `State::Initialized(Data { authority: attacker_pubkey, ... })`.
4. Victim's T2 now fails with `InstructionError::InvalidAccountData` since the account is no longer `Uninitialized` (programs/system/src/system_instruction.rs:202-209, verified in test `initialize_inx_initialized_account_fail`).
5. Attacker submits `SystemInstruction::WithdrawNonceAccount(full_balance)` signed by `attacker_pubkey`, draining all lamports the victim deposited into `N`.

pub(crate) fn withdraw_nonce_account(
    from_account_index: IndexOfAccount,
    lamports: u64,
    to_account_index: IndexOfAccount,
    rent: &Rent,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.is_writable() {
        ic_msg!(
            invoke_context,
            "Withdraw nonce account: Account {} must be writeable",
            from.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    let check_signer = |signer: &Pubkey| {
        if !signers.contains(signer) {
            ic_msg!(
                invoke_context,
                "Withdraw nonce account: Account {} must sign",
                signer
            );
            return Err(InstructionError::MissingRequiredSignature);
        }
        Ok(())
    };

    let state: Versions = from.get_state()?;
    match state.state() {
        State::Uninitialized => {
            if lamports > from.get_lamports() {
                ic_msg!(
                    invoke_context,
                    "Withdraw nonce account: insufficient lamports {}, need {}",
                    from.get_lamports(),
                    lamports,
                );
                return Err(InstructionError::InsufficientFunds);
            }
            check_signer(from.get_key())?;
        }
        State::Initialized(data) => {
            if lamports == from.get_lamports() {
                let durable_nonce =
                    DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
                if data.durable_nonce == durable_nonce {
                    ic_msg!(
                        invoke_context,
                        "Withdraw nonce account: nonce can only advance once per slot"
                    );
                    return Err(SystemError::NonceBlockhashNotExpired.into());
                }
                check_signer(&data.authority)?;
                from.set_state(&Versions::new(State::Uninitialized))?;
            } else {
                let min_balance = rent.minimum_balance(from.get_data().len());
                let amount = checked_add(lamports, min_balance)?;
                if amount > from.get_lamports() {
                    ic_msg!(
                        invoke_context,
                        "Withdraw nonce account: insufficient lamports {}, need {}",
                        from.get_lamports(),
                        amount,
                    );
                    return Err(InstructionError::InsufficientFunds);
                }
                check_signer(&data.authority)?;
            }
        }
    };

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;

    Ok(())
}

        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());

                ic_msg!(
                    invoke_context,

                    account.get_lamports(),

                );

                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);

            account.set_state(&Versions::new(state))
        }

                invoke_context,
                "Initialize nonce account: Account {} state is invalid",

            );
            Err(InstructionError::InvalidAccountData)
        }
    }
