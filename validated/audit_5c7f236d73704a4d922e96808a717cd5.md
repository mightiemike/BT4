### Title
Global contract identity persists after account deletion, allowing takeover of `GlobalByAccount` contracts by a re-registered account name - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`DeployGlobalContract` with `deploy_mode: AccountId` publishes shared WASM code under a permanent trie key keyed only by the *string* `AccountId`, not by any fixed owner credential or the account's lifetime. When the publishing account is deleted, `remove_account` cleans up the account record, access keys, local contract code, and contract data — but never touches the `GlobalContractCode`/`GlobalContractNonce` entries keyed by that account name. Because sufficiently long top-level account names can be created by *anyone* (not just a registrar), an unrelated party can recreate the deleted name and redeploy new code to the same `GlobalContractIdentifier::AccountId(name)` slot, silently hijacking the WASM code executed by every other account that had opted in via `UseGlobalContract`.

### Finding Description
- `action_delete_account` calls `remove_account`, which removes `TrieKey::Account`, `TrieKey::ContractCode`, all access/gas keys, and `TrieKey::ContractData` for the deleted account: [1](#0-0) [2](#0-1) . It never enumerates or removes `TrieKey::GlobalContractCode`/`TrieKey::GlobalContractNonce`, which are entirely separate trie columns (`col::GLOBAL_CONTRACT_CODE = 18`, `col::GLOBAL_CONTRACT_NONCE = 19`) not included in `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` handling done by `remove_account`: [3](#0-2) .
- When `DeployGlobalContract{ deploy_mode: AccountId }` is executed, the runtime derives the global-contract identifier purely from the deploying account's name: `GlobalContractIdentifier::AccountId(account_id.clone())`, increments a nonce keyed by that identifier, and stores the code at `TrieKey::GlobalContractCode { identifier }`: [4](#0-3) [5](#0-4) . There is no binding to a specific key, account-creation nonce, or long-lived owner identity — only the current holder of the account name at deploy time.
- Other accounts opt in via `UseGlobalContract`, storing `AccountContract::GlobalByAccount(account_id)` on themselves, so every future `FunctionCall` on them resolves code by looking up the current value at `GlobalContractCode{identifier: AccountId(account_id)}`: [6](#0-5) [7](#0-6) .
- Top-level account names at or above `min_allowed_top_level_account_length` may be created by *any* predecessor, not only the registrar: [8](#0-7) . Thus once the original publisher deletes its account, the exact same name is freely reclaimable by anyone.
- Because the `GlobalContractCode`/`GlobalContractNonce` rows survive account deletion and are addressed only by the account-name string, the new "owner" of the recreated name can call `DeployGlobalContract{AccountId}` again and overwrite the shared code — with no relationship to, or permission granted by, the original publisher or by the accounts that use it via `GlobalByAccount`. This mirrors the CVE-2025-66467 bug class: a resource-scoped permission/artifact ("bucket policy" ↔ "global-contract-by-account slot") is not invalidated when the underlying named resource is deleted, so reuse of the name by a different principal grants that principal unintended control/access over state other parties still trust.

### Impact Explanation
Every account that executed `UseGlobalContract(AccountId(name))` continues to trust code addressed by that name indefinitely, with no re-confirmation. If the name is deleted and reclaimed by an attacker, the attacker can deploy arbitrary WASM that will subsequently execute as the "shared" contract code for all such accounts on every `FunctionCall` receipt — enabling unauthorized value movement (draining balances/deposits reachable via those accounts' contract logic), corrupting their persisted state, and enabling forged outcomes. This is a state-transition/authorization bypass reachable purely through ordinary transactions (`DeleteAccount`, `CreateAccount`, `DeployGlobalContract`), fitting the "unauthorized value movement" / "invalid state transition acceptance" impact categories.

### Likelihood Explanation
The attack requires: (1) a `GlobalByAccount` publisher account whose name is long enough to bypass registrar restrictions and is later deleted (voluntarily, e.g., after decommissioning, or because its balance was drained and it self-deletes to reclaim storage-stake); (2) at least one consumer account still referencing that name via `GlobalByAccount`; and (3) an attacker submitting ordinary `CreateAccount` + `DeployGlobalContract` transactions to reclaim the name. All steps are achievable by an unprivileged transaction sender with no special network position, so likelihood is moderate — it depends on real-world usage patterns of `GlobalContractDeployMode::AccountId` combined with eventual deletion/reuse of the publisher account, but requires no validator or protocol-level cooperation.

### Recommendation
On `action_delete_account`, also purge (or otherwise invalidate) any `TrieKey::GlobalContractCode`/`TrieKey::GlobalContractNonce` entries keyed by `GlobalContractIdentifier::AccountId(account_id)` for the account being deleted, or make the `AccountId`-mode global-contract identifier immutable/non-reclaimable once an account name is deleted (e.g., by tombstoning the name or binding the identifier to an account-creation nonce rather than the raw string). Alternatively, require `UseGlobalContract(AccountId(...))` consumers to periodically re-validate/pin a specific code hash rather than trusting a mutable name-based pointer indefinitely.

### Proof of Concept
1. Attacker A controls `sharedlib.near` (length ≥ `min_allowed_top_level_account_length`, so no registrar restriction applies).
2. A sends `DeployGlobalContract{ code: honest_code, deploy_mode: AccountId }` from `sharedlib.near` → stores code at `GlobalContractCode{ AccountId("sharedlib.near") }`, nonce = 1 (`runtime/runtime/src/global_contracts.rs:143-171,191-227`).
3. Victim accounts `v1.near`, `v2.near`, ... send `UseGlobalContract(GlobalContractIdentifier::AccountId("sharedlib.near"))`, setting `AccountContract::GlobalByAccount("sharedlib.near")` on themselves (`global_contracts.rs:76-108`).
4. `sharedlib.near` sends `DeleteAccount{ beneficiary_id: ... }`. `remove_account` wipes its `Account`/keys/`ContractCode`/`ContractData`, but leaves `GlobalContractCode{ AccountId("sharedlib.near") }` and its nonce untouched (`core/store/src/utils/mod.rs:504-575`).
5. Attacker E, an unrelated principal, sends `CreateAccount` for `sharedlib.near` (allowed for anyone since it's a sufficiently long top-level name, `actions.rs:175-200`), obtaining a fresh key for that name.
6. E sends `DeployGlobalContract{ code: malicious_code, deploy_mode: AccountId }` from the new `sharedlib.near` — this increments the nonce and overwrites `GlobalContractCode{ AccountId("sharedlib.near") }` with `malicious_code` (`global_contracts.rs:143-171,191-227`).
7. On the next `FunctionCall` receipt to `v1.near`/`v2.near`, the runtime resolves their contract via `GlobalContractIdentifier::AccountId("sharedlib.near")` and executes E's `malicious_code` as if it were the originally-trusted shared contract, with no action or consent from `v1.near`/`v2.near`.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
}
