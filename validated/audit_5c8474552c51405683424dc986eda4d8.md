### Title
Unescaped exception messages are concatenated directly into JSON API responses, enabling JSON/response injection - ([File: framework/src/main/java/org/tron/core/services/http/GetBrokerageServlet.java])

### Summary
Several HTTP API servlets build their JSON error response by string-concatenating the raw `Throwable.getMessage()` into a JSON literal instead of using a JSON serializer that performs proper escaping. This is the same bug class as the reported issue — untrusted/derived text is dropped verbatim into a structured output channel that a client (wallet UI or automated caller) trusts as well-formed, uncontrolled data. If the exception message contains characters such as `"`, `\`, or control characters, the resulting response is no longer valid, predictable JSON, and additional fields/values can be smuggled into the document.

### Finding Description
`GetBrokerageServlet.doGet` and `GetRewardServlet.doGet` catch `DecoderException`/`IllegalArgumentException` raised while decoding the user-supplied `address` parameter and write the exception message directly into a hand-built JSON string: [1](#0-0) [2](#0-1) 

This pattern differs from the rest of the codebase, where responses are constructed via `JSONObject.put(...).toJSONString()` (which escapes special characters) or via `Util.printErrorMsg(e)` — e.g. `GetNodeInfoServlet`, `GetPendingSizeServlet`, `GetBurnTrxServlet` all route exceptions through `Util.printErrorMsg`: [3](#0-2) 

The unescaped path is reachable directly from an anonymous HTTP request (`GET /wallet/getbrokerageinfo?address=...` and `GET /wallet/getReward?address=...`), because `Util.getAddress(request)` parses the raw request parameter and the resulting decode failures ultimately surface as `e.getMessage()`. Because Base58Check/Hex decoding libraries frequently echo the offending or partially-decoded input in their exception text, an attacker can craft an `address` value whose decode-failure message contains a literal `"` (double quote) or newline, which — once concatenated unescaped — terminates the intended JSON string early and lets the attacker append arbitrary additional JSON key/value pairs to the response body.

This mirrors exactly the pattern called out in the reference report: uncontrolled/derived error text injected into a structured user-facing/consumer-facing channel without context-aware encoding, allowing message forgery.

### Impact Explanation
A malformed/attacker-influenced address parameter can corrupt the shape of what is otherwise supposed to be a fixed two-field JSON object (`result`, `message`/`Error`). Any client (wallet frontend, monitoring tool, exchange integration) that parses this endpoint's JSON and trusts additional fields could be misled into acting on attacker-injected data (e.g., a spoofed extra field), or simply suffer a parse failure/DoS on that call path. This falls squarely within the allowed scope of "HTTP/gRPC/JSON-RPC handlers," since the injection point is a public read-only RPC-API endpoint reachable without authentication.

### Likelihood Explanation
Likelihood is moderate: exploitation depends on the specific decode-failure message text actually containing an unescaped `"` or control character, which is dependent on the underlying Bouncy Castle / Tron `DecodeUtil` implementation's exception messages rather than fully attacker-chosen text. No further investigation of those library messages was completed in this session, so the exact injectable character set could not be confirmed with certainty from the index alone.

### Recommendation
Replace manual string concatenation with `JSONObject`/a JSON library for all error responses (as already done in most other servlets), ensuring proper escaping of quotes, backslashes, and control characters. Where verbose internal exception text isn't required by the API contract, prefer fixed error codes/messages and log the raw exception server-side only, consistent with the "short term" recommendation in the source report.

### Proof of Concept
1. Send `GET /wallet/getbrokerageinfo?address=<value that causes the decoder to throw a message containing a literal double-quote character>`.
2. Observe the response body: `{"Error": "INVALID address, <injected content>"}` — if `<injected content>` contains an unescaped `"`, the JSON structure is broken and attacker-controlled key/value pairs can be appended after the closing brace boundary is prematurely reached.
3. Repeat against `GET /wallet/getReward?address=...`, which has the identical unescaped concatenation pattern. [4](#0-3) [5](#0-4)
