### Title
Unbounded `PendingInbounds` scan on every inbound ballot finalization enables gas-exhaustion DoS of inbound processing - ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
Analogous to TRST-H-4 (an unbounded loop over all gauges inside `updatePeriod()` that could exceed block gas limits and permanently revert weekly emissions), Push Chain's `afterInboundBallotTerminal` hook performs a full linear `Walk` over the entire `PendingInbounds` collection every single time *any* inbound ballot reaches a terminal state (PASSED/REJECTED/EXPIRED). Because `PendingInbounds` grows with ordinary, unprivileged user activity (every unique source-chain deposit event creates an entry), the cost of this walk scales with total in-flight inbound volume and is paid on the hot path of `MsgVoteInbound` — a gasless message.

### Finding Description
`x/uvalidator`'s generic ballot machine calls `BallotHooks.AfterBallotTerminal` synchronously whenever a ballot transitions to a terminal state [1](#0-0) . For `INBOUND_TX` ballots this dispatches to `afterInboundBallotTerminal`, which — because "ballot IDs are one-way canonical digests" — locates the owning `PendingInboundEntry` by iterating over the *entire* `PendingInbounds` collection and scanning each entry's variants for a matching `BallotId`: [2](#0-1) 

Critically, on the common "ballot PASSED" path, the entry has already been removed from `PendingInbounds` by `VoteInbound` **before** the hook fires (`RemovePendingInbound` at step 6 of `VoteInbound` happens prior to `ExecuteInbound`, and the hook fires as part of `VoteOnInboundBallot`/`CheckIfFinalizingVote` inside the ballot machine). This means the `found` flag will be `false` and the `Walk` cannot short-circuit — it is forced to scan **every remaining entry in `PendingInbounds`** on every single finalizing `MsgVoteInbound` call, regardless of the outcome.

`PendingInbounds` entries are created by the **first** validator vote on any inbound and are keyed by `sha256(sourceChain:txHash:logIndex)` [3](#0-2) . Growth of this collection is driven entirely by ordinary source-chain deposit activity — no privilege is required to trigger a new inbound: any unprivileged user can send funds/payload through the gateway on any supported external chain, causing honest Universal Validators to observe the event and submit `MsgVoteInbound` for it (this is the base user-facing deposit flow of the protocol, not a validator-privileged action). Because `MsgVoteInbound` is itself gasless [4](#0-3) , an attacker can cheaply cause a very large number of concurrent inbound events to be in flight (e.g., many trivial/dust deposits across multiple external chains within the same block-time window), inflating `PendingInbounds` size, while UVs continue to submit legitimate `MsgVoteInbound` votes for all of them and each other's finalizations.

Once `PendingInbounds` is large enough, the mandatory O(n) `Walk` performed inside every single finalizing `MsgVoteInbound` execution can push that transaction's gas consumption past the tx gas limit (or, in the worst case, the block gas limit), causing the finalizing vote to fail/revert. Since `MarkBallotFinalized` (and thus the ballot state transition to `PASSED`/`REJECTED`) is committed transactionally together with the hook call inside the same message handling flow, a reverted transaction means the ballot never finalizes and the corresponding inbound is never minted/executed on Push Chain — directly analogous to `updatePeriod()` reverting and freezing emissions distribution in the original report.

### Impact Explanation
This breaks the "Honest-validator finalization path" invariant explicitly listed in scope: "user-created source events, payloads, and chain interactions must not let honest UVs converge on the wrong ballot ... or wrong outbound" — here they cannot converge/finalize *at all* once the walk becomes too expensive. It also falls under "denial of service only when it is not network-level and is reachable without privileged control," since:
- The trigger (creating many pending inbounds via cheap/dust external-chain deposits) requires no privileged role — any unprivileged external attacker can do this.
- The affected path (`MsgVoteInbound` finalization → inbound execution → PRC20 mint / UEA payload execution) is a core, user-reachable universal execution flow, not just a query.
- The consequence is a stall of inbound crediting and universal execution for the whole protocol once `PendingInbounds` accumulates enough entries, degrading (and at a large enough scale, halting) legitimate deposit processing — a systemic protocol-wide DoS, not merely griefing a single user's transaction.

### Likelihood Explanation
Medium-to-High. The Walk executes unconditionally on *every* terminal inbound-ballot transition regardless of PASS/REJECT/EXPIRE outcome, and in the common PASSED path it always scans the full collection without early exit (since `found` is always `false` there). It does not require any esoteric edge case — only that a meaningful number of inbound events be concurrently in flight, which any unprivileged actor can force by submitting many low-value deposits across the supported external chains within the ballot's `expiryAfterBlocks` window, at a cost bounded only by source-chain gas fees (cheap on most EVM L2s) plus zero Push Chain fees since the vote message is gasless.

### Recommendation
Avoid the reverse lookup entirely by indexing `PendingInbounds` by `ballotID` (or storing a `ballotID → utxKey` secondary index) so the hook can do an O(1)/O(log n) lookup instead of a full collection walk. Alternatively, bound `PendingInbounds` size (e.g., cap concurrent pending inbound entries per source chain, or require ballots to carry their owning `utxKey` so the hook is passed the key directly instead of having to search for it) and enforce ballot-count/gas budgeting so a single finalizing vote can never be forced to pay for the entire pending set.

### Proof of Concept
Conceptual PoC (cannot be executed without a running testnet/devnet with an EVM gateway and Universal Validators):
1. Deploy/observe a supported external chain (e.g., a devnet Sepolia gateway) with `IsInboundEnabled = true`.
2. From an unprivileged EOA, submit a large number (N) of distinct low-value `addFunds`/gateway transactions with unique tx hashes/log indices in rapid succession, faster than the ballot voting threshold can be reached for each (e.g., have UVs delayed or intentionally target chains with slower confirmation), so that N `PendingInboundEntry` records accumulate simultaneously in `x/uexecutor`'s `PendingInbounds` collection.
3. As UVs continue to submit `MsgVoteInbound` for these and other legitimate inbounds, each finalizing vote invokes `afterInboundBallotTerminal`, which performs `h.k.PendingInbounds.Walk(ctx, nil, ...)` over all N entries [5](#0-4) .
4. Measure/instrument gas consumption of `MsgVoteInbound` as N grows; demonstrate that for sufficiently large N the finalizing vote's gas usage approaches or exceeds `MaxTxGasWanted`/block gas limit, causing the tx to fail and the corresponding inbound(s) to never finalize/mint, stalling universal execution for those (and subsequently attempted) transactions.

Note: I was not able to execute this against a live node within this session; the finding is based on static analysis of the referenced source and README documentation confirming `PendingInbounds` growth semantics and the unconditional full-collection `Walk` in the terminal-ballot hook.

) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
