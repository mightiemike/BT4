### Title
`many_ref_accounts_can_be_moved` underestimates required packed storages due to non-optimal bin-packing in `PackedAncientStorage::pack`, allowing a many-ref account to be moved to a slot lower than its true last-write slot - ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
`many_ref_accounts_can_be_moved` estimates the number of packed ancient storages required for "many-ref newest" accounts using a simple `ceil(total_bytes / ideal_storage_size)` formula [1](#0-0) , but the actual packer, `PackedAncientStorage::pack`, uses a greedy "next-fit"-style bin packing algorithm that can require strictly more storages than this estimate whenever account sizes are chosen adversarially [2](#0-1) . Because the only post-pack safety check is a global count comparison (`pack.len() > target_slots_sorted.len()`) and not a per-account slot-vs-target-slot check, this mismatch lets a many-ref account be written to a target slot lower than its true highest live slot, violating the fundamental invariant that "the highest slot # where an account exists defines the most recent account" [3](#0-2) .

### Finding Description
`combine_ancient_slots_packed_internal` collects `many_refs_newest` (accounts with ref_count > 1 whose current record is the newest/highest-slot record for that pubkey), sorts them by slot descending, and validates that they can be safely packed via `many_ref_accounts_can_be_moved` before calling `PackedAncientStorage::pack` [4](#0-3) .

`many_ref_accounts_can_be_moved` computes:
```
required_ideal_packed = (alive_bytes / ideal_storage_size) + 1
highest_slot = target_slots_sorted[len - required_ideal_packed]
```
and only asserts `many.slot <= highest_slot` for every group [5](#0-4) . This assumes the actual packer will need at most `required_ideal_packed` storages to hold `alive_bytes` of many-ref data, so that any many-ref account whose slot is `<= highest_slot` will be placed at or above its own original slot.

`PackedAncientStorage::pack`, however, is a "next-fit" packer: for each candidate storage it keeps adding whole `AliveAccounts` groups (or individual accounts, when a group must be split) only while the running total stays within `ideal_size`; once an addition would exceed `ideal_size` it seals the current storage and starts a new one, without going back to fill left-over space in earlier storages [6](#0-5) . This is a classic next-fit bin-packing algorithm, which is known to require up to roughly `2×` the number of bins that an optimal/ceiling-based packing would use when item sizes are chosen just above half the bin capacity (e.g., repeated groups sized ~0.6×`ideal_storage_size` each force a fresh storage per group, since two of them never fit together). Consequently the number of storages `pack.len()` actually consumed by the many-ref data can exceed `required_ideal_packed`.

Storages are then mapped to target slots in `write_packed_storages` by zipping `target_slots_sorted.iter().rev()` (highest slot first) with the `pack` results in order, so `pack[0]` (highest-slot many-ref data) gets the highest target slot, `pack[1]` the next highest, etc. [7](#0-6) . If the packer needs `P > required_ideal_packed` storages to hold the many-ref data, storages at index `>= required_ideal_packed` still contain many-ref-newest accounts, but they are zipped to target slots **below** `highest_slot` — the exact value that `many_ref_accounts_can_be_moved` used to certify safety for accounts with `slot <= highest_slot`. An account whose original slot equals (or is close to) `highest_slot` can thus be assigned a target slot below its true slot.

The only other check before writing is a coarse total-count comparison: `if pack.len() > accounts_to_combine.target_slots_sorted.len() { return; }` [8](#0-7) . This does not verify per-account slot-vs-target-slot alignment, so it does not catch the scenario above as long as there are enough total target slots overall (e.g., because there is also plenty of one-ref data to consume the remaining slots). There is no other assertion in the write path (`write_one_packed_storage`, `write_ancient_accounts`) that verifies an account is not moved below its live slot.

### Impact Explanation
This is a `LOAD_FRESHNESS` violation: a many-ref account can be silently packed into a lower ancient slot than the slot containing its true latest write. Because AccountsDB determines "the current value of an account" by the account entry at the account's highest known slot, moving the newest-alive record to a lower slot means a stale/older account state (or metadata pointing at now-emptied storage) is presented as authoritative on replay/reads for that pubkey, effectively changing an account's observed balance/data without a corresponding transaction. This matches the "silent balance change from stale/duplicate/resurrected account state across ancient-append-vec packing" bounty category referenced in the audit scope.

### Likelihood Explanation
Exploitability requires:
- An attacker-controlled pubkey that has been written across several distinct ancient slots (ref_count > 1), reachable by any unprivileged user simply by repeatedly writing to the same account across slots that later become "ancient" and get root/aged into the ancient range — fully within normal permissionless capability (create/rewrite/close/reopen accounts, control data length hence `stored_size`).
- Precisely engineered account sizes (e.g., several `AliveAccounts` groups sized just over half of `ideal_storage_size`) to trigger next-fit's worst-case bin inflation, combined with slot values placed at/just under the boundary computed by `required_ideal_packed`, so the `many_ref_accounts_can_be_moved` check passes while the real packer needs more storages.
- Triggering `combine_ancient_slots_packed`/ancient shrink/clean to run with the crafted set of ancient slots (this runs automatically as part of validator background maintenance, not requiring special privilege to invoke — only requiring the attacker's slots to become eligible ancient candidates).

This requires careful crafting of account data sizes and slot distribution but no elevated privilege, and is reproducible deterministically once discovered, since `PackedAncientStorage::pack` and `many_ref_accounts_can_be_moved` are both pure/deterministic functions over caller-supplied `AliveAccounts`.

### Recommendation
Make `many_ref_accounts_can_be_moved`'s slot-safety property enforced structurally rather than by an approximate byte-count formula:
- After running `PackedAncientStorage::pack`, walk the resulting `pack` list against `target_slots_sorted.iter().rev()` and assert, for every account included in each `PackedAncientStorage`, that its original slot (`AliveAccounts.slot`) is `<=` the target slot it will actually be written to. Abort/skip packing (like the existing `pack.len() > target_slots_sorted.len()` bail-out) if this per-account invariant is violated, instead of relying solely on the pre-check estimate.
- Alternatively, replace the `required_ideal_packed` estimate with an exact reproduction of the packer's behavior (or a provably conservative upper bound account for next-fit's worst case, e.g., `2 * ceil(alive_bytes / ideal_storage_size)`), so the pre-check can never underestimate the number of storages the real packer will use.

### Proof of Concept
Add a unit test in `accounts-db/src/ancient_append_vecs.rs` alongside `test_many_ref_accounts_can_be_moved` that:
1. Constructs several `AliveAccounts` `many_refs_newest` groups (distinct slots, sorted descending) whose individual account sizes are deliberately set to just over half of `ideal_storage_size` (e.g., `0.6 * ideal_storage_size` each, split across multiple `AccountFromStorage` entries within a group so the packer's per-account split logic is exercised), so that `PackedAncientStorage::pack` provably needs more bins than `ceil(total_bytes / ideal_storage_size)`.
2. Calls `many_ref_accounts_can_be_moved(&many_refs_newest, &target_slots_sorted, &tuning)` and shows it returns `true`.
3. Calls `PackedAncientStorage::pack(many_refs_newest.iter(), tuning.ideal_storage_size)` and asserts `pack.len() > required_ideal_packed` (i.e., more bins were actually used than the check assumed).
4. Simulates the zip in `write_packed_storages` (`target_slots_sorted.iter().rev().zip(pack)`) and asserts that for at least one `(target_slot, packed)` pair, some account's original `slot` (recovered from `packed.accounts`) is `> target_slot` — demonstrating a concrete violation of "assigned target slot must be >= original slot" even though `many_ref_accounts_can_be_moved` returned `true`.

    fn pack(
        mut accounts_to_combine: impl Iterator<Item = &'a AliveAccounts<'a>>,
        ideal_size: NonZeroU64,
    ) -> Vec<PackedAncientStorage<'a>> {
        let mut result = Vec::default();
        let ideal_size: u64 = ideal_size.into();
        let ideal_size = ideal_size as usize;
        let mut current_alive_accounts = accounts_to_combine.next();
        // starting at first entry in current_alive_accounts
        let mut partial_inner_index = 0;
        // 0 bytes written so far from the current set of accounts
        let mut partial_bytes_written = Saturating(0);
        // pack a new storage each iteration of this outer loop
        loop {
            let mut bytes_total = 0usize;
            let mut accounts_to_write = Vec::default();

            // walk through each set of alive accounts to pack the current new storage up to ideal_size
            let mut full = false;
            while !full && current_alive_accounts.is_some() {
                let alive_accounts = current_alive_accounts.unwrap();
                if partial_inner_index >= alive_accounts.accounts.len() {
                    // current_alive_accounts have all been written, so advance to next set from accounts_to_combine
                    current_alive_accounts = accounts_to_combine.next();
                    // reset partial progress since we're starting over with a new set of alive accounts
                    partial_inner_index = 0;
                    partial_bytes_written = Saturating(0);
                    continue;
                }
                let bytes_remaining_this_slot =
                    alive_accounts.bytes.saturating_sub(partial_bytes_written.0);
                let bytes_total_with_this_slot =
                    bytes_total.saturating_add(bytes_remaining_this_slot);
                let mut partial_inner_index_max_exclusive;
                if bytes_total_with_this_slot <= ideal_size {
                    partial_inner_index_max_exclusive = alive_accounts.accounts.len();
                    bytes_total = bytes_total_with_this_slot;
                } else {
                    partial_inner_index_max_exclusive = partial_inner_index;
                    // adding all the alive accounts in this storage would exceed the ideal size, so we have to break these accounts up
                    // look at each account and stop when we exceed the ideal size
                    while partial_inner_index_max_exclusive < alive_accounts.accounts.len() {
                        let account = alive_accounts.accounts[partial_inner_index_max_exclusive];
                        let account_size = account.stored_size();
                        let new_size = bytes_total.saturating_add(account_size);
                        if new_size > ideal_size && bytes_total > 0 {
                            full = true;
                            // partial_inner_index_max_exclusive is the index of the first account that puts us over the ideal size
                            // so, save it for next time
                            break;
                        }
                        // this account fits
                        partial_bytes_written += account_size;
                        bytes_total = new_size;
                        partial_inner_index_max_exclusive += 1;
                    }
                }

                if partial_inner_index < partial_inner_index_max_exclusive {
                    // these accounts belong in the current packed storage we're working on
                    accounts_to_write.push((
                        alive_accounts.slot,
                        // maybe all alive accounts from the current or could be partial
                        &alive_accounts.accounts
                            [partial_inner_index..partial_inner_index_max_exclusive],
                    ));
                }
                // start next storage with the account we ended with
                // this could be the end of the current alive accounts or could be anywhere within that vec
                partial_inner_index = partial_inner_index_max_exclusive;
            }
            if accounts_to_write.is_empty() {
                // if we returned without any accounts to write, then we have exhausted source data and have packaged all the storages we need
                break;
            }
            // we know the full contents of this packed storage now
            result.push(PackedAncientStorage {
                bytes: bytes_total as u64,
                accounts: accounts_to_write,
            });
        }
        result
    }
