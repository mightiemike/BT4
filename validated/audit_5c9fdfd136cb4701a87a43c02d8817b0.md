### Title
Unprivileged front-running of TRC10 `ExchangeTransactionContract` slippage check causes DoS on legitimate exchange trades - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeTransactionActuator` implements TRC10's built-in AMM ("bancor-style") exchange trade. A trader specifies a minimum acceptable output (`tokenExpected`) and the actuator computes the actual output at execution time from the exchange pool's live balances, reverting the whole transaction if the computed output is below the caller's expectation. Because the pool balances (`firstTokenBalance` / `secondTokenBalance`) are shared, globally-mutable state that any unprivileged account can alter (via its own `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` against the same `exchange_id`), an attacker can front-run a victim's pending trade with a tiny trade of their own to shift the pool ratio just enough to push the victim's computed output below `tokenExpected`, causing the victim's transaction to revert. This mirrors the WiseLending finding's root cause: a threshold check computed against shared, attacker-influenceable state at validation/execution time, which reverts the whole transaction rather than gracefully adjusting, enabling a cheap, repeatable DoS by an unprivileged party.

### Finding Description
In `ExchangeTransactionActuator.doValidate()`, the amount of `anotherTokenQuant` the trader will receive is computed live from the exchange pool state: [1](#0-0) 

```

218|        dynamicStore.allowStrictMath(), allowHarden());
219|    if (anotherTokenQuant < tokenExpected) {
220|      throw new ContractValidateException("token required must greater than expected");

```

`exchangeCapsule.transaction()` computes the output using the pool's current `firstTokenBalance`/`secondTokenBalance` (a constant-product/bancor style curve), which are read from the shared `ExchangeCapsule` for the given `exchange_id`: [2](#0-1) 

This same pool state is mutated by every trade against that exchange, including `ExchangeInjectActuator` (adds proportional liquidity, shifting the ratio) and `ExchangeWithdrawActuator` (removes proportional liquidity), and by other traders' `ExchangeTransactionActuator` calls: [3](#0-2) [4](#0-3) 

Since any unprivileged account can submit an `ExchangeTransactionContract` (or `ExchangeInjectContract`) trading against the same `exchange_id`, and Java-TRON orders/validates transactions in block/pending-pool order, an attacker can insert a small transaction immediately before a victim's larger trade to shift `firstTokenBalance`/`secondTokenBalance` just enough that the victim's `anotherTokenQuant` computed at validation time falls below the victim's specified `tokenExpected`. The actuator then throws `ContractValidateException("token required must greater than expected")` and the whole transaction fails, exactly as the WiseLending `checkMaxShares()` reverts on `TooManyShares()` when a borrower front-runs the liquidator's repayment share count. In both cases: (1) the validation threshold is computed against externally-mutable shared state at execution time, (2) any unprivileged actor can nudge that shared state, and (3) the response to exceeding the threshold is a hard revert of the entire transaction rather than a partial/adjusted execution.

### Impact Explanation
An unprivileged attacker can repeatedly and cheaply grief specific traders (or all traders) on a chosen TRC10 exchange pool by submitting minimal-cost trades/injections immediately ahead of target transactions, causing the target's `ExchangeTransactionContract` to revert due to the slippage check. This wastes the victim's bandwidth/energy fee, delays execution of time-sensitive trades in a market where price is moving, and can be sustained indefinitely at low cost since TRC10 exchanges have no minimum trade size floor beyond `> 0`. This is a concrete DoS on market/exchange functionality reachable by any unprivileged account, matching the class of issue in the report (judged Medium severity by the original audit due to it being an "annoying" but not fund-stealing DoS).

### Likelihood Explanation
Likelihood is high for any account wishing to grief a specific counterparty or degrade UX/liquidity-taking on a TRC10 exchange pool: the attacker only needs read access to the mempool/pending transactions (or simply monitor recent trades against a given `exchange_id` and react quickly) and enough TRX/asset balance to submit a minimal trade. No special permission, admin role, or high capital is required — this is a pure unprivileged-user griefing vector inherent to the exchange design's front-runnable slippage check.

### Recommendation
Consider one or more of the following, mirroring the WiseLending fix direction (adjust rather than hard-revert, or reduce front-runnability):
- Allow `ExchangeTransactionActuator` to execute with a partially-filled/adjusted output when the computed `anotherTokenQuant` is close to but below `tokenExpected` only within an acceptable tolerance configured by the trader, rather than an unconditional revert, OR clearly document that TRC10 exchange trades are subject to slippage/front-running as an accepted trade-off (as with `vonMangoldt`'s dismissal in the original report, this may be judged Low/Informational rather than fixed).
- Consider rate-limiting or minimum-liquidity-change thresholds for `ExchangeInjectContract`/`ExchangeWithdrawContract` per block to reduce the ability to make surgical last-moment ratio shifts.
- Recommend wallets/clients set a sensible slippage tolerance (`tokenExpected`) rather than an exact-expected value to reduce false-revert sensitivity to minor pool-state changes.

### Proof of Concept
1. Attacker observes a pending `ExchangeTransactionContract` from Victim trading `tokenQuant` of `tokenID` against `exchange_id` with `tokenExpected` set tightly (e.g., minimal acceptable slippage).
2. Attacker submits their own `ExchangeTransactionContract` (or a minimal `ExchangeInjectContract`) against the same `exchange_id`, trading in the same direction as the victim, with a low fee so it is prioritized/ordered before the victim's transaction.
3. This shifts `firstTokenBalance`/`secondTokenBalance` in the shared `ExchangeCapsule` as computed in `ExchangeTransactionActuator.execute()`/`ExchangeInjectActuator.execute()`.
4. When the victim's transaction is validated (`ExchangeTransactionActuator.doValidate()` line 217-221), `exchangeCapsule.transaction()` now returns a lower `anotherTokenQuant` computed from the shifted pool state, which falls below the victim's `tokenExpected`, causing `ContractValidateException("token required must greater than expected")` and the victim's transaction to fail, consuming the victim's bandwidth/energy for a failed operation.
5. Attacker can repeat this ahead of every subsequent retry by the victim, as long as they can consistently front-run, achieving a sustained DoS on that exchange pool for the targeted victim(s).

Note: I was unable to fully trace `ExchangeCapsule.transaction()`'s exact bancor/constant-product math implementation within the available index (only its signature location was found), so the precise numeric magnitude of ratio shift needed per attack iteration is not verified here; a Devin session with full repository access would be needed to compute exact minimal griefing trade sizes.
