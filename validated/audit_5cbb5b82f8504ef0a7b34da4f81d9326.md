### Title
`block_direct_execute_call` protection can be bypassed via `library_call` syscall, allowing spoofed direct execution of `__execute__` - (File: `crates/blockifier/src/execution/syscalls/hint_processor.rs`, `crates/blockifier/src/execution/native/syscall_handler.rs`, `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`)

### Summary
The external report describes a `FloodPlain` "magic value" selector check (`SELECTOR_EXTENSION`) that is only enforced on one calling interface (`sourceConsiderations`) but not on an equivalent alternate interface (`sourceConsideration`), letting an attacker spoof a privileged callback through the unguarded path. The sequencer contains a structurally identical pattern: `call_contract` explicitly checks the target selector against `EXECUTE_ENTRY_POINT_NAME` (via `maybe_block_direct_execute_call`) to forbid directly invoking a contract's `__execute__` entry point, but the `library_call` syscall — an equally reachable calling interface — performs no equivalent selector check.

### Finding Description
`call_contract` in both the current and deprecated syscall handlers guards against directly invoking `__execute__`: [1](#0-0) 
This is invoked from `call_contract` in `SyscallHintProcessor` and the deprecated handler: [2](#0-1) [3](#0-2) 

However, the `library_call` implementations — in the current VM handler, the Native handler, and the deprecated handler — build the same `CallEntryPoint` (with `entry_point_selector` fully attacker-controlled from calldata) but never call `maybe_block_direct_execute_call` or perform any equivalent selector check: [4](#0-3) [5](#0-4) [6](#0-5) 

The same asymmetry exists in the Starknet OS Cairo re-execution code: `execute_deprecated_syscalls`'s `CALL_CONTRACT_SELECTOR` branch explicitly asserts `call_contract_syscall.request.selector != EXECUTE_ENTRY_POINT_SELECTOR`, but the `LIBRARY_CALL_SELECTOR` branch performs no such assertion: [7](#0-6) 
Similarly in the current OS execution path, `execute_call_contract` checks `request.selector == EXECUTE_ENTRY_POINT_SELECTOR` and rejects it, while `execute_library_call` has no such check: [8](#0-7) 

This is the same bug class as the report: a selector/interface-based guard that is meant to block invocation of a privileged entry point is applied to only one of several functionally-equivalent call paths (`call_contract` vs `library_call`), leaving the other path fully open to the exact call it was designed to prevent. `library_call` delegates execution with `CallType::Delegate` while preserving `storage_address`/`caller_address` from the caller, meaning a contract can invoke its own (or another class's) `__execute__` code path in the context of the calling contract, exactly what `block_direct_execute_call` is meant to prevent for `call_contract`.

### Impact Explanation
`__execute__` is the account-abstraction entry point that Starknet's protocol invariants rely on being invoked only once per transaction, in a specific caller context (`caller_address == 0`), following successful `__validate__`. The `block_direct_execute_call` protection exists specifically to prevent contracts from re-entering/directly invoking `__execute__` outside of that protocol-controlled path (bypassing the "caller must be zero" assumption depended upon by many deployed accounts, and preventing arbitrary contracts from executing an account's transaction logic under attacker-chosen conditions). Since `library_call` bypasses this guard entirely while allowing an attacker-controlled contract to specify any class hash and selector (including `__execute__`) with `call_type = Delegate`, any contract's `__execute__` logic can be invoked outside the intended transaction-processing flow. Where accounts rely on `block_direct_execute_call` (or on the `caller_address == 0` invariant enforced elsewhere) as a security boundary, this creates a path to unauthorized account-action execution.

### Likelihood Explanation
This is trivially reachable by any unprivileged contract via a single `library_call_syscall`/`library_call` invocation from ordinary Cairo1 or Cairo0 code, requiring no special privileges, deployment coordination, or off-chain assumptions — matching the "unprivileged sender reaching blockifier execution/syscalls" criterion. The gap is present in all handler variants (VM `SyscallHintProcessor`, `native::syscall_handler`, and the deprecated Cairo0 handler) as well as mirrored in the Starknet OS Cairo re-execution logic, so it is a systemic omission rather than an isolated code path, increasing the likelihood that it is exploitable end-to-end and reproduced consistently by the OS during re-execution (avoiding divergence detection).

### Recommendation
Apply the same `maybe_block_direct_execute_call` (or equivalent selector check) in `library_call` across all three Rust syscall handlers (`SyscallHintProcessor::library_call`, native `syscall_handler::library_call`, and the deprecated `execute_library_call`), and add the matching `assert_not_equal(request.selector, EXECUTE_ENTRY_POINT_SELECTOR)` guard to the `LIBRARY_CALL_SELECTOR` branch in `deprecated_execute_syscalls.cairo` and to `execute_library_call` in `syscall_impls.cairo`, so that the OS and blockifier remain consistent and no calling interface can bypass the direct-execute-call restriction.

### Proof of Concept
1. Deploy an account/contract `Victim` whose `__execute__` performs security-relevant logic guarded only by the assumption that it is invoked through the standard transaction flow (e.g., relies on `block_direct_execute_call` being enforced, or performs actions predicated on being called only once per validated transaction).
2. Deploy an `Attacker` contract with a function that issues `library_call_syscall(class_hash=Victim's class hash, function_selector=selector!("__execute__"), calldata=...)`.
3. Submit an ordinary `INVOKE` transaction that calls `Attacker`'s function.
4. Observe that, unlike an equivalent `call_contract_syscall` targeting `__execute__` (which reverts with `Invalid argument` per `test_direct_execute_call` in `crates/blockifier/src/execution/syscalls/syscall_tests/call_contract.rs`), the `library_call_syscall` path succeeds and executes `Victim`'s `__execute__` code with `storage_address`/`caller_address` inherited from `Attacker`, demonstrating the bypass of the `block_direct_execute_call` protection reachable from an ordinary transaction.

        &mut self,
        selector: EntryPointSelector,

        let versioned_constants = &self.context.tx_context.block_context.versioned_constants;
        if versioned_constants.block_direct_execute_call

        {
            return Err(SyscallExecutionError::Revert { error_data: vec![INVALID_ARGUMENT_FELT] });
        }
        Ok(())

                request.function_selector,

        })?;

pub fn execute_library_call(
    syscall_handler: &mut DeprecatedSyscallHintProcessor<'_>,
    vm: &mut VirtualMachine,
    class_hash: ClassHash,
    code_address: Option<ContractAddress>,
    call_to_external: bool,
    entry_point_selector: EntryPointSelector,
    calldata: Calldata,
) -> DeprecatedSyscallResult<ReadOnlySegment> {
    let entry_point_type =
        if call_to_external { EntryPointType::External } else { EntryPointType::L1Handler };
    let entry_point = CallEntryPoint {
        class_hash: Some(class_hash),
        code_address,
        entry_point_type,
        entry_point_selector,
        calldata,
        // The call context remains the same in a library call.
        storage_address: syscall_handler.storage_address,
        caller_address: syscall_handler.caller_address,
        call_type: CallType::Delegate,
        initial_gas: syscall_handler.context.gas_costs().base.default_initial_gas_cost,
    };

    execute_inner_call(entry_point, vm, syscall_handler).map_err(|error| {
        error.as_lib_call_execution_error(
            class_hash,
            syscall_handler.storage_address,
            entry_point_selector,
        )
    })
}
