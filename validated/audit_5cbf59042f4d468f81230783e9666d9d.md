### Title
Denial of Service via unhandled `atob()` exception in `sanitizeHost`/`decodeHost` on malformed `host` query parameter - (File: packages/apps/shopify-api/lib/utils/shop-validator.ts)

### Summary
`sanitizeHost()` validates the `host` query parameter using only a loose regex (`/^[0-9a-zA-Z+/]+={0,2}$/`) that accepts any base64-alphabet string regardless of length, then immediately decodes it with `decodeHost()` (a thin wrapper around `atob()`) and feeds the result into `new URL()`, all without a try/catch. Because the regex does not enforce a length that is a valid base64 encoding, an attacker-supplied `host` value that matches the regex but is not valid base64 (e.g., a single character with no padding) causes `atob()` to throw an uncaught `DOMException`/`Error`. This propagates out of `sanitizeHost`, `decodeHost`, `getEmbeddedAppUrl`, and any caller that does not explicitly wrap the call in a try/catch.

### Finding Description
`sanitizeHost` in [1](#0-0)  performs:
1. A permissive base64-charset regex test (no length/padding validation).
2. `new URL(`https://${decodeHost(sanitizedHost)}`)`, where `decodeHost` is [2](#0-1) , a direct call to `atob(host)`.

`atob()` implements the WHATWG "forgiving-base64" decode algorithm, which throws when the (whitespace-stripped) input length is not congruent to a valid base64 length (e.g., length ≡ 1 mod 4, or non-canonical padding). The regex used by `sanitizeHost` does not enforce this constraint — it only restricts the character set and allows 0–2 trailing `=`. A string like `"A"`, `"AB"`, or other malformed-but-regex-matching values will pass the regex check and then cause `atob()` to throw synchronously, with **no surrounding try/catch** in `sanitizeHost` itself.

This is structurally analogous to the reported `nimiq-keys` bug: input passes a coarse validity gate (byte length in the advisory; base64 charset here) but is not actually well-formed for the decoding routine it's handed to, and the decoding call is not defensively wrapped, so a crafted-but-superficially-valid input reaches an unguarded panic/throw path.

The `host` parameter is fully attacker/anonymous-controlled: it is read straight from the request query string in multiple auth-adjacent entry points reachable pre-authentication:
- `getEmbeddedAppUrl` → `buildEmbeddedAppUrl` → `sanitizeHost(host, true)` [3](#0-2) 
- `validateShopAndHostParams` in both `shopify-app-remix` and `shopify-app-react-router`, called at the very start of `authenticate.admin` before any session/shop validation succeeds [4](#0-3) 
- `redirectToShopifyOrAppRoot` (Remix/React Router/Express variants), which reads `url.searchParams.get('host')!` directly into `sanitizeHost` [5](#0-4) 
- `redirect-to-auth.ts`'s `clientSideRedirect`, called from Express `ensureInstalledOnShop`/`redirectToAuth` for embedded requests, calls `sanitizeHost` with **no try/catch** at all [6](#0-5) 

Notably, `embedAppIntoShopify` in `ensure-installed-on-shop.ts` explicitly wraps `api.auth.getEmbeddedAppUrl(...)` (which reaches `sanitizeHost`) in a try/catch specifically to guard against this kind of throw [7](#0-6) , but `clientSideRedirect` and `redirectToShopifyOrAppRoot` do not have equivalent protection, confirming the throw path is real and was only partially mitigated.

### Impact Explanation
Where `sanitizeHost`/`decodeHost` is invoked from a synchronous Express middleware handler without a surrounding try/catch (e.g., `redirect-to-shopify-or-app-root.ts` and `redirect-to-auth.ts`'s `clientSideRedirect`), an uncaught throw inside an `async` Express 4 middleware becomes an unhandled promise rejection, since Express 4 does not automatically forward async errors to `next(err)`. Depending on the app's Node.js version and process-level `unhandledRejection` configuration, this can terminate the entire Node process, taking down the app for all merchants — a denial of service triggered by a single anonymous/unauthenticated HTTP request. In React Router/Remix loader contexts the same throw is more likely caught by the framework's error boundary and rendered as a 500, which is a more limited (but still real) DoS of the specific request/auth handler.

### Likelihood Explanation
High reachability: the `host` query parameter is read from unauthenticated, anonymous HTTP requests at the very entry of the admin authentication flow, before shop/session validation, in every framework binding (`shopify-app-express`, `shopify-app-remix`, `shopify-app-react-router`). No secret or prior authentication is required — an attacker only needs to send a GET request with a crafted `host=` value (e.g., `host=A`) matching the loose base64-charset regex but not a validly padded base64 string.

### Recommendation
- In `decodeHost` (`packages/apps/shopify-api/lib/auth/decode-host.ts`), wrap `atob(host)` in a try/catch and surface a controlled `InvalidHostError` instead of letting the underlying `DOMException`/`Error` propagate.
- In `sanitizeHost` (`packages/apps/shopify-api/lib/utils/shop-validator.ts`), tighten the regex to only accept properly-padded, length-valid base64 strings (length a multiple of 4) or explicitly try/catch the `decodeHost`/`new URL` call and return `null` (or throw `InvalidHostError` when `throwOnInvalid`) on failure, matching the function's documented contract.
- Audit and add try/catch (or `next(err)`) around every call site that invokes `sanitizeHost`/`getEmbeddedAppUrl` outside of an already-guarded context, notably `redirect-to-auth.ts`'s `clientSideRedirect` and the various `redirect-to-shopify-or-app-root.ts` implementations.

### Proof of Concept
1. Send `GET /?shop=test-shop.myshopify.com&host=A` (or any single-character/invalidly-padded base64-charset string) to an embedded app route that triggers `authenticate.admin` (Remix/React Router) or `ensureInstalledOnShop`/`redirectToAuth` (Express) before a valid session exists.
2. `validateShopAndHostParams`/`clientSideRedirect` calls `api.utils.sanitizeHost('A')`.
3. `base64regex.test('A')` returns `true` (character set matches, no length constraint).
4. `decodeHost('A')` calls `atob('A')`, which throws because `'A'` is not a validly-padded base64 string.
5. The exception propagates unguarded out of `sanitizeHost`; in an Express async middleware with no try/catch (e.g., `clientSideRedirect`/`redirectToShopifyOrAppRoot`), this produces an unhandled promise rejection which, depending on Node configuration, crashes the process — a single anonymous request causing denial of service for the whole app.

  params: BasicParams,
  responseHeaders?: Headers,
): Promise<never> {
  const {api} = params;
  const url = new URL(request.url);

  const host = api.utils.sanitizeHost(url.searchParams.get('host')!)!;
  const shop = api.utils.sanitizeShop(url.searchParams.get('shop')!)!;

  const redirectUrl = api.config.isEmbeddedApp
    ? await api.auth.getEmbeddedAppUrl({rawRequest: request})
    : `/?shop=${shop}&host=${encodeURIComponent(host)}`;

}
