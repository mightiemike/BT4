### Title
`TransactionOutput::ensure_match_transaction_info()` never validates the state checkpoint root hash, letting replay-verify silently accept a corrupted state root - (`File: types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info()` is the sole equality gate used by replay/verify tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger`, `aptos-move/cli`) to compare a locally re-executed `TransactionOutput` against an authenticated, accumulator-proven `TransactionInfo` fetched from backup/archive storage. The function checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but never compares `state_checkpoint_hash` (or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) against anything derived from local re-execution — the code's own comment acknowledges this gap.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates only four fields:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` vs `txn_info.state_change_hash()`
- `event_root_hash` vs `txn_info.event_root_hash()`

It never reads or compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` to any locally computed Sparse-Merkle/JMT root. The function's own trailing comment documents this: [2](#0-1)  states the comparator "ignores the checkpoint hashes... so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution."

This is the sole comparison call used by the authenticated-replay path:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify` calls `executed_outputs[idx].ensure_match_transaction_info(...)` per transaction after VM re-execution against a live/archive DB [3](#0-2) , and treats absence of an `Err` as full agreement, driving process exit codes used by `testsuite/replay-verify` (mainnet/testnet replay-verify CI/monitoring).
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs` similarly call this function as their sole re-execution correctness check.

None of these paths independently re-derive and compare the state (or hot-state/position) checkpoint root against `txn_info`'s corresponding hash anywhere else; the state root/Merkle root fields, which are the exact commitment that a Merkle/state proof binds to, are simply skipped.

### Impact Explanation
`state_checkpoint_hash` is the authenticated root that binds the on-chain `TransactionInfo` (and therefore the transaction accumulator / ledger info) to the actual world state at that version. Because the verification function never checks it, a divergence between the archived/authenticated `TransactionInfo.state_checkpoint_hash` and the state root that local re-execution would actually produce is silently accepted as a passing replay. This defeats the entire purpose of replay-verify (detecting non-determinism, storage corruption, or a bug that produces a different state root than what was actually committed to the chain) for the state-commitment dimension specifically — exactly the "Hard-fork-only divergence during commit, replay, restore, or proof verification" impact category, since a wrong state root would only manifest as a hard-fork-class disagreement between validators if ever exploited, and this is the tool relied upon to catch such divergences before they reach production.

### Likelihood Explanation
This is not a hypothetical: the gap is on every call path of the function today, unconditionally (not gated behind any not-yet-enabled feature flag — the missing check applies to the plain `state_checkpoint_hash` field present in `TransactionInfoV0`/`V1` since inception, not just the newer hot-state/position fields the code comment calls out). Any bug in checkpoint-hash computation (e.g., in `do_state_checkpoint.rs`, JMT batch update, or hot-state changes) that alters the true state root but leaves gas/status/write-set/event hashes unchanged would go completely undetected by `replay_on_archive`, `aptos-debugger`, and the CLI replay tooling used to validate historical mainnet data.

### Recommendation
Extend `ensure_match_transaction_info` to also compute or accept an expected state-checkpoint root (and hot-state/position-state root when applicable) for checkpoint transactions and assert equality against `txn_info.state_checkpoint_hash()` (and the V1 counterparts), mirroring the existing pattern used for `write_set_hash` and `event_root_hash`. This must be wired through so all three call sites (`replay_on_archive`, `aptos-debugger`, CLI) supply/require the locally-computed checkpoint hash whenever a transaction is a checkpoint.

### Proof of Concept
1. Take any version `v` that is a state-checkpoint boundary and has a valid `TransactionInfo` with `state_checkpoint_hash = H`.
2. Construct an archive/backup entry (or a local `AptosDB`) where the recorded `TransactionInfo` at `v` has a `state_checkpoint_hash` different from `H'`, the actual root produced by re-executing the same write sets from genesis (e.g., inject an off-by-one corruption in a stored `state_checkpoint_hash` while keeping `state_change_hash`/`event_root_hash`/`gas_used`/`status` correct).
3. Run `storage/db-tool/src/replay_on_archive.rs`'s replay-verify over that range: `execute_and_verify` re-executes the transactions and calls `ensure_match_transaction_info` [3](#0-2) .
4. Observe that no error is raised and the chunk is reported as verified, despite the corrupted `state_checkpoint_hash`, because `ensure_match_transaction_info` at [1](#0-0)  never reads or checks that field.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
