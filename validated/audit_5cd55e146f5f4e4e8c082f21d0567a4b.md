### Title
Starknet OS `execute_replace_class` accepts an undeclared/zero class hash while Blockifier rejects it, causing state-root divergence - ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The `replace_class` syscall handler in the Starknet OS (Cairo re-execution program) writes any attacker-supplied `class_hash` — including `0` or a never-declared hash — directly into `contract_state_changes` without checking that the class was actually declared. The equivalent Rust Blockifier implementation explicitly performs this check and reverts the call if the class is undeclared. Any contract can invoke `replace_class` from an ordinary transaction, so this is reachable by an unprivileged sender, and the divergent validation between the sequencer's Blockifier execution and the OS's re-execution can produce different state commitments/roots for the same block.

### Finding Description
`execute_replace_class` in the OS explicitly documents the missing check with a `TODO`: [1](#0-0) 

It reads `request.class_hash`, and — with only a `TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.` comment — immediately writes a new `StateEntry` with that class hash into `contract_state_changes` and logs it to the revert log, with no validation that the class is declared or non-zero. The same unchecked pattern exists in the deprecated syscall path: [2](#0-1) 

By contrast, the Rust Blockifier — which is what the sequencer actually runs to build blocks — enforces the check before mutating state: [3](#0-2) 

`get_compiled_class` fails (and the syscall reverts) if `class_hash` is `0` or otherwise undeclared, and additionally Blockifier enforces the class must be Cairo1 (`is_cairo1`). The deprecated Blockifier syscall handler performs an analogous declared-class check: [4](#0-3) 

I reviewed the state-commitment pipeline (`state.cairo`, `squash_class_changes`) that consumes `contract_class_changes`/`contract_state_changes`, and found no re-validation there that a class hash written by `replace_class` was actually declared — the squash/commitment logic simply commits whatever class hash values were recorded during execution.

### Impact Explanation
Because the sequencer's block-building path (Blockifier) rejects `replace_class(0)` / `replace_class(<undeclared>)` as a reverted call, while the OS's re-execution (used for proving / verifying the same block, e.g. in `starknet_os` re-execution flows) would silently accept it and commit the new (possibly zero) class hash to the contract's state entry, the two execution engines can produce different final state roots and thus different block hashes for the exact same block of transactions. This is a canonical "honest-node divergence" / "wrong committed root" bug class: if the OS is the consensus-relevant re-execution used to attest to state validity, a discrepancy here could make the network compute two different valid-looking state commitments for the same transaction set, or make an honestly-produced block fail OS re-execution verification (denial of block confirmation), or — if OS is instead treated as authoritative — silently corrupt a contract by resetting its class pointer to `0`/an undeclared hash even though Blockifier would have reverted that specific call.

### Likelihood Explanation
The `replace_class` syscall is a normal, permissionless Starknet syscall available to any deployed contract executing an ordinary transaction (invoke, or via account `__execute__`) — no admin/operator privilege is required. Triggering the divergence only requires a contract that calls `replace_class_syscall` with a class hash equal to `0` or one that has not been declared. This makes the bug trivially reachable from a single submitted transaction.

### Recommendation
Add the declared-class-hash check in `execute_replace_class` in both `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo` (i.e., verify `class_hash != 0` and that the class was actually declared/exists in `contract_class_changes`/committed class tree) prior to writing the new `StateEntry`, mirroring the check already performed in Blockifier's `syscall_base.rs::replace_class` (`get_compiled_class` + `is_cairo1`). This keeps OS and Blockifier semantics consistent and prevents accepting invalid class replacements during OS re-execution.

### Proof of Concept
1. Deploy any Cairo1 contract that exposes a callable entry point invoking `replace_class_syscall(class_hash)` with an attacker-controlled `class_hash` (e.g. the existing `test_replace_class` test helper: [5](#0-4) ).
2. Submit an ordinary invoke transaction calling this entry point with `class_hash = 0` (or any hash for a class never declared on-chain).
3. In Blockifier (sequencer execution): `self.state.get_compiled_class(class_hash)` fails, and `replace_class` returns a `SyscallExecutionError`, causing the inner call to revert (verified by the existing test `undeclared_class_hash` at [6](#0-5)  which asserts the error contains "is not declared").
4. In the Starknet OS re-execution of the identical transaction, `execute_replace_class` (`syscall_impls.cairo:881-920`) performs no such check and unconditionally updates `contract_state_changes` with the new (invalid) class hash, meaning the OS computes a different final state for the contract's class entry than Blockifier did for the same transaction — a concrete state-root/behavior divergence between the two independently-maintained execution engines.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
