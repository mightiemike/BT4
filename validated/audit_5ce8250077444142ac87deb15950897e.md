### Title
Unbounded iteration over attacker-inflated `VotesStore` in `Wallet.getPaginatedNowWitnessList` causes RPC/HTTP DoS - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`Wallet.getPaginatedNowWitnessList` is exposed via an anonymous, unauthenticated RPC/HTTP endpoint and internally calls a private `countVote` helper that performs a full, unbounded scan of the entire `VotesStore` on every single invocation. Because `VotesStore` entries are created and persisted per-voter-address by the `VoteWitnessContract` actuator (and by the TVM native `VoteWitnessProcessor`) and are only cleared once per maintenance epoch, an attacker can cheaply inflate the size of this store by generating many new addresses and broadcasting minimal-value vote transactions, directly mirroring the "PAIR-2 | DoS Dividends" bug class (unbounded loop whose iteration count is attacker-controlled via cheap address/entry creation).

### Finding Description
`countVoteAccount` in `VoteWitnessActuator.java` [1](#0-0)  and `VoteWitnessProcessor.execute` (TVM native `voteWitness`) [2](#0-1)  both write one `VotesCapsule` entry per unique owner address into `VotesStore` whenever that address casts (or re-casts) a vote. Any account can be created for the cost of a broadcast transaction and can vote with as little as 1 TRX-equivalent tron power, so the number of distinct entries in `VotesStore` is effectively bounded only by how many cheap vote transactions an attacker is willing to broadcast within a single maintenance epoch.

These entries persist in `VotesStore` until the next `doMaintenance()` cycle, at which point `MaintenanceManager.countVote` iterates and deletes every entry [3](#0-2) . However, before that cyclical cleanup happens, the RPC-facing method `Wallet.getPaginatedNowWitnessList` re-implements the exact same full-store scan on every call via its own private `countVote` helper: [4](#0-3) [5](#0-4) 

This method is exposed to anonymous, unauthenticated callers through the gRPC/HTTP API (`framework/src/main/java/org/tron/core/services/http/GetPaginatedNowWitnessListServlet.java` and `RpcApiService.java`, both of which reference `getPaginatedNowWitnessList`). Every request to this endpoint triggers a full `Iterator<Entry<byte[], VotesCapsule>>` walk over the entire `VotesStore`, regardless of the `offset`/`limit` pagination parameters requested by the caller — pagination is only applied *after* the full unbounded scan and subsequent full-list sort (`WitnessStore.sortWitnesses`).

### Impact Explanation
Because the cost of the scan is O(number of `VotesStore` entries) and that entry count is fully attacker-controlled (cheap to grow via many cheap vote transactions from many funded addresses), a malicious actor can:
1. Inflate `VotesStore` within a single epoch by broadcasting a large number of low-cost `VoteWitnessContract` transactions from many addresses.
2. Repeatedly call the public `getPaginatedNowWitnessList` RPC/HTTP endpoint (even asking for `limit=1`), each call forcing the node to perform the full O(n) scan, map operations, and a full sort of all witnesses.

This can degrade or exhaust node CPU/latency resources servicing this public API, denying service to legitimate API consumers on that node (RPC/HTTP-API DoS), and — since the same unbounded-scan pattern is duplicated in the consensus-critical `MaintenanceManager.countVote` — could also slow down maintenance-period processing at scale.

### Likelihood Explanation
Medium-High. No special privileges are required: any user with the ability to create accounts and broadcast the cheap `VoteWitnessContract` (or invoke the TVM `voteWitness` precompiled-style opcode) can inflate the `VotesStore`, and the vulnerable RPC/HTTP endpoint is unauthenticated and callable by anyone. The main constraint is the TRX cost of funding many voter accounts and broadcast bandwidth/energy fees, which raises the cost of the attack but does not prevent it.

### Recommendation
- Avoid re-scanning the entire `VotesStore` per API call in `Wallet.getPaginatedNowWitnessList`; cache/precompute vote deltas once per block or per maintenance window instead of on every request.
- Apply the requested `offset`/`limit` before performing expensive aggregation where possible, or bound the maximum number of entries processed per call.
- Consider capping or rate-limiting the number of distinct new voter entries a single address/IP can create within an epoch, or moving to an accumulator/point-based reward-and-vote-count design (similar to the "pointsPerShare" pattern referenced in the original report) that avoids needing to iterate all voters at query time.

### Proof of Concept
1. Create N funded accounts (each requiring only minimal TRX/bandwidth).
2. From each account, broadcast a `VoteWitnessContract` transaction with a very small vote count, populating N entries in `VotesStore` via `VoteWitnessActuator.countVoteAccount` [6](#0-5) .
3. Before the next maintenance cycle clears `VotesStore`, repeatedly call the public `getPaginatedNowWitnessList` gRPC/HTTP endpoint.
4. Observe that each call triggers `Wallet.countVote`'s full unbounded iteration over all N entries [7](#0-6) , causing increasing latency/CPU cost proportional to N, independent of the requested `limit`.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }
