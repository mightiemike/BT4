## Analog Found

### Title
Stale-session overwrite in `performTokenExchange` invalidates a concurrently-obtained valid access token - ([File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts])

### Summary
`performTokenExchange` snapshots the currently stored session (`sessionToInvalidate`) *before* performing the (slow, network-bound) token-exchange call, and later — on a 401 error from that exchange — unconditionally persists that stale snapshot back to session storage with its `accessToken` cleared. If a concurrent request for the same session id has, in the interim, completed a successful token exchange and stored a fresh valid session, this error path silently overwrites and destroys that valid, freshly obtained access token, mirroring the reported bug class of "overwriting current state with a stale value without accounting for changes made in between."

### Finding Description
In [1](#0-0) , `sessionToInvalidate` is captured from `config.sessionStorage.loadSession(sessionId)` at the very start of the handler. The function then performs one or two awaited network calls to Shopify (`exchangeToken`) at [2](#0-1) . If any of these later fail with an HTTP 401, the `catch` block runs [3](#0-2) , calling `invalidateAccessToken(sessionToInvalidate, config)`.

`invalidateAccessToken` simply clears `accessToken` on the object it is given and calls `storeSession` again: [4](#0-3) . Because `sessionToInvalidate` is the object loaded at the *beginning* of the request (not re-read at error time), any session update that another concurrent request wrote to the same `sessionId` in the intervening time (e.g. a parallel App Bridge fetch that raced ahead and already completed the exchange and stored a fresh, valid `offlineSession`/`onlineSession` via [5](#0-4) ) gets blindly clobbered by this late `storeSession(sessionToInvalidate)` call.

This is directly analogous to the reported Solidity bug: a value that should reflect "current, most up-to-date state" gets forcibly reset/overwritten from a stale snapshot taken earlier in the flow, destroying legitimate accrued state (there: rewards; here: a validly re-issued access token) belonging to the same principal.

### Impact Explanation
The `sessionId` is derived deterministically from `shop`/`sub` (`api.session.getOfflineId(shop)` or `getJwtSessionId(shop, sub)`), so any two concurrent requests bearing session tokens for the same shop/user resolve to the same storage key. Embedded Shopify apps routinely fire multiple concurrent authenticated fetches from App Bridge on page load, all of which can hit `performTokenExchange` simultaneously when no active session exists yet. A transient 401 on just one of these concurrent exchanges (e.g. brief Shopify-side hiccup, clock skew, or an attacker deliberately racing a bad/expired session token against a legitimate one) causes the just-established valid offline/online access token to be wiped from storage. This forces the merchant's app into a re-authentication/bounce loop, effectively a denial-of-service against the app's authenticated session for that shop.

### Likelihood Explanation
This requires no privileged access — any client capable of sending concurrent requests with session tokens for the same shop (which App Bridge does naturally, and which an unauthenticated network attacker or malicious script could deliberately trigger by replaying/racing an invalid session token alongside a valid one) can hit this race. The window is the duration of the `api.auth.tokenExchange` network round trip, which is non-trivial and gives a realistic race window.

### Recommendation
Do not persist a stale in-memory snapshot on the error path. Re-load the current session from storage immediately before invalidating (or use a storage-level conditional/atomic update, e.g. only clear `accessToken` if it still matches the token that caused the 401), so a concurrently-stored valid session is never overwritten by an older one.

### Proof of Concept
1. Request A (no active session) and Request B (same shop) both hit `performTokenExchange` concurrently; both load the same stale/absent session and set `sessionToInvalidate`.
2. Request B's `exchangeToken` succeeds first and stores a fresh valid `offlineSession` via `config.sessionStorage.storeSession(offlineSession)`.
3. Request A's `exchangeToken` call then fails with a 401 (e.g. transient Shopify error or a raced expired token).
4. Request A's catch block runs `invalidateAccessToken(sessionToInvalidate, config)`, which persists the old (pre-exchange) session object with `accessToken = undefined` under the same `sessionId`, overwriting Request B's freshly stored valid token.
5. Subsequent legitimate requests using the session B obtained now find `accessToken` cleared, are forced to redo the auth/bounce flow — a self-inflicted DoS of the auth handler for that shop.

import {Session} from '@shopify/shopify-api';

import {AppConfigInterface} from '../config-types';

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
}
