### Title
L1Handler transactions bypass all calldata-size validation, letting a single L1 message permanently exceed block bouncer capacity and become unincludable - ([File: crates/blockifier/src/transaction/l1_handler_transaction.rs])

### Summary
Starknet's `RpcTransaction` stateless validator enforces `max_calldata_length` only for `DeployAccount` and `Invoke` transactions, explicitly skipping the check for `Declare` and never even seeing `L1Handler` transactions at all, since `L1Handler` never enters the RPC gateway - it is produced directly from scraped L1 events by `apollo_l1_events`/`TransactionManager` and injected into block building via `ProposeTransactionProvider`/`ValidateTransactionProvider`. Consequently, the size of an `L1Handler` transaction's `calldata` (the L1→L2 message payload) is bounded only by whatever limits exist on the *L1* side (the sending chain's tx-size/gas limits), which can be far larger than the sequencer's own block resource budget.

### Finding Description
The stateless RPC validator (`StatelessTransactionValidator::validate`) calls `validate_tx_extended_calldata_size`, which computes calldata length only for `DeployAccount`/`Invoke` and unconditionally returns `Ok(())` for `Declare` [1](#0-0) . `L1HandlerTransaction` is not even a variant of `RpcTransaction`, so it never passes through `StatelessTransactionValidator::validate` at all [2](#0-1) .

`L1Handler` transactions are instead created purely from scraped L1 events and staged for proposal by `TransactionManager::get_txs`, with no calldata/payload size check anywhere in that path [3](#0-2) . The payload size (`calldata.len() - 1`, excluding the `from_address` field) directly feeds into the block's `message_segment_length` bouncer weight via `get_message_segment_length`, which adds `L1_TO_L2_MSG_HEADER_SIZE + payload_size` unconditionally to the segment length [4](#0-3) , and this size is derived straight from `L1HandlerTransaction::payload_size()` [5](#0-4) .

After executing any transaction, `Transaction::execute_raw` calls `verify_tx_weights_within_max_capacity`, which computes the transaction's own bouncer weights and checks them against `bouncer_config.block_max_capacity` via `within_max_capacity_or_err` [6](#0-5) . If a transaction's weights alone exceed the configured max (default `message_segment_length: 3700`) it returns `TransactionExecutionError::TransactionTooLarge` [7](#0-6) , and this error is *permanent* per-transaction - it does not depend on how full the current block is; it fires even against an empty bouncer/block, as confirmed by the dedicated regression test `test_transaction_too_large_sierra_gas_based` which shows a transaction whose own resource usage exceeds `block_max_capacity` fails unconditionally, regardless of block state [8](#0-7) .

Because `L1HandlerTransaction::execute_raw` builds its receipt (and therefore its message-segment/bouncer weight) directly from `self.payload_size()` with no upstream length cap [9](#0-8) , a message sent from L1 with a sufficiently large payload will always fail `TransactionTooLarge` on every attempt to include it in any block - it can never be executed, never consumed, and never removed from `TransactionManager`'s proposable index, since removal only happens on consumption/cancellation events observed from L1 [10](#0-9) .

This is the same root-cause pattern as the referenced ZKsync report: an unprivileged party (there, a governance proposer; here, an L1 message sender) submits data whose length is checked (or not checked at all) at one processing stage but is used unbounded at a later, resource-constrained stage, so that stage can never succeed for that data — permanently defeating a downstream mechanism (there, guardian veto; here, sequencer block inclusion of the L1 message).

### Impact Explanation
Any L1 contract can call the L1 bridge/StarknetCore-equivalent `sendMessageToL2` with an arbitrarily large payload (limited only by L1's own gas/tx-size limits, which can be substantially larger than the sequencer's `message_segment_length` cap of 3700). The resulting `L1Handler` transaction can never fit into any block's bouncer budget and is therefore permanently unexecutable by the sequencer — i.e., the network becomes unable to confirm this L1-originated transaction. If the L1 message carries value/deposit semantics (as is standard for L1→L2 bridging messages), funds associated with that message can become permanently stuck on L2 inclusion, and legitimate cancellation on L1 (if available) is a separate, out-of-scope mitigation that does not fix the sequencer-side inability to process appropriately-sized-but-still-oversized messages. This matches the "network unable to confirm new transactions" / "permanent freezing of funds" criteria.

### Likelihood Explanation
Likelihood is high: triggering this requires only calling the standard L1→L2 messaging entry point with a large payload — no special privileges, no reliance on validator/proposer misbehavior, and no dependency on mocked-only code paths. The gap is structural: `L1Handler` transactions are categorically excluded from the gateway's stateless size validation (`RpcTransaction` has no `L1Handler` variant), and no other size cap exists between L1 event scraping and block-building bouncer checks.

### Recommendation
Enforce an explicit maximum payload/calldata length for `L1HandlerTransaction` at the earliest possible point — ideally when scraping/ingesting the L1 event in `apollo_l1_events` (rejecting or flagging oversized messages before they ever reach `TransactionManager`'s proposable index) — sized so that `get_message_segment_length` combined with existing message-segment-length usage from L2-to-L1 messages can never exceed `BouncerWeights::message_segment_length`'s configured `block_max_capacity` in the worst case. Additionally, consider validating this bound defensively in `L1HandlerTransaction::execute_raw` / `TransactionReceipt::from_l1_handler` so an oversized message is deterministically rejected/handled (e.g., marked non-proposable) rather than silently becoming permanently stuck.

### Proof of Concept
1. From L1, call the standard L1→L2 messaging function (`sendMessageToL2`-equivalent) targeting some L2 contract, with a payload whose length, once run through `get_message_segment_length` (`L1_TO_L2_MSG_HEADER_SIZE + payload_size`), exceeds the sequencer's configured `bouncer_config.block_max_capacity.message_segment_length` (default 3700) [11](#0-10) .
2. `apollo_l1_events` scrapes the `LogMessageToL2` event and stores it as a pending `L1HandlerTransaction` in `TransactionManager` with no size check [3](#0-2) .
3. On the next proposal round, `ProposeTransactionProvider` fetches it via `get_l1_handler_txs` and feeds it to the blockifier `TransactionExecutor` [12](#0-11) .
4. `L1HandlerTransaction::execute_raw` executes normally, but `Transaction::execute_raw`'s subsequent `verify_tx_weights_within_max_capacity` call computes `message_segment_length` from the oversized payload and returns `TransactionExecutionError::TransactionTooLarge` [13](#0-12) [14](#0-13) .
5. This failure is deterministic and independent of block fullness (confirmed by `test_transaction_too_large_sierra_gas_based` showing the same class of failure against an empty bouncer) [8](#0-7) , so every future attempt to propose/validate a block containing this transaction fails identically, and the transaction remains in `TransactionManager`'s pending/proposable state indefinitely.

pub fn get_message_segment_length(
    l2_to_l1_payload_lengths: &[usize],
    l1_handler_payload_size: Option<usize>,
) -> usize {
    // Add L2-to-L1 message segment length; for each message, the OS outputs the following:
    // to_address, from_address, payload_size, payload.
    let mut message_segment_length = l2_to_l1_payload_lengths
        .iter()
        .map(|payload_length| constants::L2_TO_L1_MSG_HEADER_SIZE + payload_length)
        .fold(0, |accumulator, length| {
            usize::checked_add(accumulator, length).expect(
                "Sending a message to L1 costs gas proportional to payload, so total cannot \
                 exceed usize.",
            )
        });

    if let Some(payload_size) = l1_handler_payload_size {
        // The corresponding transaction is of type L1 handler; add the length of the L1-to-L2
        // message sent by the sequencer (that will be outputted by the OS), which is of the
        // following format: from_address=calldata[0], to_address=contract_address,
        // nonce, selector, payload_size, payload=calldata[1:].
        message_segment_length += constants::L1_TO_L2_MSG_HEADER_SIZE + payload_size;
    }

    message_segment_length
}

fn test_transaction_too_large_sierra_gas_based(block_context: BlockContext) {
    let mut state = test_state(&block_context.chain_info, Fee(0), &[]);
    let mut transactional_state = TransactionalState::create_transactional(&mut state);
    let block_max_capacity = BouncerWeights { sierra_gas: GasAmount(20), ..Default::default() };
    let bouncer_config = BouncerConfig { block_max_capacity, ..Default::default() };

    // Use gas amount > block_max_capacity's.
    let exceeding_gas = GasAmount(30);
    let execution_summary = ExecutionSummary::default();
    let builtin_counters = CairoPrimitiveCounterMap::default();
    let tx_resources = TransactionResources {
        computation: ComputationResources { sierra_gas: exceeding_gas, ..Default::default() },
        ..Default::default()
    };
    let tx_state_changes_keys = transactional_state.to_state_diff().unwrap().state_maps.keys();

    let result = verify_tx_weights_within_max_capacity(
        &transactional_state,
        &execution_summary,
        &builtin_counters,
        &tx_resources,
        &tx_state_changes_keys,
        &bouncer_config,
        &block_context.versioned_constants,
        GasAmount::ZERO,
    )
    .map_err(TransactionExecutorError::TransactionExecutionError);

    let expected_weights = BouncerWeights {
        sierra_gas: exceeding_gas,
        n_txs: 1,
        proving_gas: exceeding_gas,

        TransactionExecutorError::TransactionExecutionError(
            TransactionExecutionError::TransactionTooLarge { max_capacity, tx_size }
        )
    )  if *max_capacity == bouncer_config.block_max_capacity && *tx_size == expected_weights);
}
