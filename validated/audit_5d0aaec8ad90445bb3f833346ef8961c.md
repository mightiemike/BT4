### Title
ETH-implicit accounts can receive funds permanently locked when the referenced global Wallet Contract is not deployed - (File: runtime/runtime/src/actions.rs)

### Summary
Any unprivileged sender can create an ETH-implicit account by sending a plain `Transfer` action to a 42-character `0x...` account id. `action_implicit_account_creation_transfer` unconditionally assigns the account `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))`, i.e. a hard-coded reference to a global contract identified only by hash [1](#0-0) . This hash is *not* guaranteed to correspond to an already-deployed global contract on that chain — deployment happens independently via a separate `DeployGlobalContract` action [2](#0-1) . If nobody has deployed that global contract yet (e.g. a fresh localnet/testnet-like chain, or any chain id whose expected wallet code hasn't been published as a global contract), the account is created and funded but has no runnable code.

### Finding Description
Per the design docs, once created, "An ETH-implicit account can only be used by calling the methods of the Wallet Contract. It cannot be deleted, nor can a full access key be added" [3](#0-2) . This is confirmed by `test_transaction_from_eth_implicit_account_fail`, which shows that without an access key, every avenue to control the account — sending money, deleting the account, adding an access key, or redeploying — is rejected with `AccessKeyNotFound`, because ETH-implicit accounts never receive an access key from a `Transfer` [4](#0-3) .

The only way to operate on the account's balance is by invoking `rlp_execute` on the Wallet Contract code that is supposed to be resolved via `RuntimeContractIdentifier::resolve`, which looks up the account's `AccountContract::Global` hash [5](#0-4) . If that global contract hash was never deployed on-chain, any `FunctionCall` (including `rlp_execute`) directed at that account fails with `GlobalContractDoesNotExist` — there is no fallback, no owner override, and (per the docs) no way to delete the account or attach a full-access key to reclaim the deposited balance. Since the account cannot be deleted and has no usable code, the deposited NEAR is stranded with no code path to move it out.

This mirrors the reported bug class: an account/contract that accumulates value through normal deposit/transfer flow, but that is missing any privileged or public "withdraw"/"recover" exit once the intended operational path (contract logic) is unavailable — here, unavailable because the referenced global contract code doesn't exist yet.

### Impact Explanation
This is a "permanently frozen funds" scenario, matching the rules' accepted-impact category. Any unprivileged transaction signer — a relayer, or literally anyone who sends a `Transfer` to a syntactically valid ETH-implicit account id (`0x` + 40 hex chars) before/without that chain's wallet global contract being deployed — can create an account whose balance becomes unreachable, since no key exists to authorize deletion, key-add, or redeploy actions, and the only intended operational entrypoint (`rlp_execute` via the global Wallet Contract) cannot resolve to real code.

### Likelihood Explanation
Likelihood is high on any network where the wallet global contract has not yet been deployed under the exact hash referenced by `eth_wallet_global_contract_hash(chain_id)` for that `chain_id` — for instance a new/custom chain id that falls into the `_ => *LOCALNET.read_contract().hash()` branch [6](#0-5) , or any deployment sequencing where users/relayers can send funds to derived ETH-implicit addresses before an operator deploys the corresponding global contract. Since account creation via `Transfer` requires no permission and is a normal, everyday operation (this is literally how these accounts are meant to be created), the vulnerable window is trivially reachable by a single unprivileged transaction.

### Recommendation
- Reject (or hold in a recoverable pending state) `Transfer`-based creation of ETH-implicit accounts whose target global contract hash is not currently deployed, rather than silently creating an account with an unresolvable `AccountContract::Global` reference.
- Alternatively, provide an explicit, permissionless recovery/refund path (e.g., automatically refund the transfer to the sender, or allow deletion/beneficiary payout) when the referenced global contract does not exist at account-creation time or at first use.
- Add protocol-level invariant checks/tests that assert every `eth_wallet_global_contract_hash(chain_id)` used for account creation is deployed before the feature/chain goes live, and monitoring to catch any newly supported `chain_id` for which this precondition is not met.

### Proof of Concept
1. Start (or point at) a NEAR-compatible chain/chain_id for which the global contract at `eth_wallet_global_contract_hash(chain_id)` (see `runtime/near-wallet-contract/src/lib.rs:89-104`) has not been deployed via `DeployGlobalContract`.
2. From any unprivileged account, submit `SignedTransaction::send_money` (or any `Transfer` action) to a derived ETH-implicit account id (`0x` + 40 lowercase hex chars), analogous to the flow tested in `test_eth_implicit_account_creation` [7](#0-6) , but skip the `DeployGlobalContract` step that the real test performs beforehand [8](#0-7) .
3. This creates the account with `AccountContract::Global(hash)` and the deposited balance, per `action_implicit_account_creation_transfer` [1](#0-0) .
4. Attempt to call `rlp_execute` on the account (the only intended way to move funds out) — the call fails with `GlobalContractDoesNotExist` because the code was never deployed.
5. Attempt to delete the account or add a full-access key using any signature — both fail with `AccessKeyNotFound`, exactly as demonstrated in `test_transaction_from_eth_implicit_account_fail` [9](#0-8) , since the account never received an access key.
6. The deposited balance is now permanently unreachable — there is no signer, key, or governance action defined in this codebase that can move it.

**Caveat / uncertainty:** I could not fully verify from the indexed code whether there is a governance-level or genesis-config mechanism elsewhere in nearcore that guarantees the relevant global contract is always deployed before a `chain_id` is activated for ETH-implicit accounts (e.g., via genesis state records), which would mitigate this in practice for mainnet/testnet specifically. The vulnerability as coded has no in-protocol safeguard against this sequencing issue for arbitrary/new chain ids, but I recommend a Devin session with full repo/genesis access to confirm whether any deployment-ordering guarantee exists outside the runtime code reviewed here.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

    pub(crate) fn resolve(
        account_id: &AccountId,
        account_contract: AccountContract,
        state_update: &TrieUpdate,
        chain_id: &str,
        access: AccessOptions,
    ) -> Result<Self, StorageError> {
        let local_hash = match GlobalContractIdentifier::try_from(account_contract) {
            Ok(gci) => {
                let code_hash = gci.clone().hash(state_update, access)?;
                return Ok(RuntimeContractIdentifier::Global { code_hash, identifier: gci });
            }
            Err(ContractIsLocalError::NotDeployed) => return Ok(RuntimeContractIdentifier::None),
            Err(ContractIsLocalError::Deployed(local_hash)) => local_hash,
        };

        if account_id.get_account_type() == AccountType::EthImplicitAccount {
            // Accounts that look like eth implicit accounts and have existed prior to the
            // eth-implicit accounts protocol change (these accounts are discussed in the
            // description of #11606) may have something else deployed to them. Only return
            // something here if the accounts have a wallet contract hash. Otherwise use the
            // regular path to grab the deployed contract.
            if LegacyEthWallet::resolve(local_hash).is_some() {
                // ETH implicit wallet accounts use global contracts, including
                // those created in old protocol versions.
                let global_hash = eth_wallet_global_contract_hash(chain_id);
                return Ok(RuntimeContractIdentifier::Global {
                    code_hash: global_hash,
                    identifier: GlobalContractIdentifier::CodeHash(global_hash),
                });
            }
        }

        Ok(RuntimeContractIdentifier::AccountLocal {
            code_hash: local_hash,
            account_id: account_id.clone(),
        })
    }
