Based on the investigation, I found a strong analog to the reported bug class in the batch prover's JSON-RPC surface.

### Title
Unauthenticated `citrea_setCommitments` RPC allows overriding sequencer commitments without DA validation - (File: `crates/batch-prover/src/rpc.rs`)

### Summary
The batch prover exposes a JSON-RPC method `set_commitments` (`citrea_setCommitments`) that directly writes attacker-supplied `SequencerCommitment` records into the ledger DB — bypassing every validation step (merkle-root verification against actual L2 blocks, strict index/height ordering, DA-inclusion checks) that the node's normal commitment ingestion path (`process_sequencer_commitment` in `crates/fullnode/src/da_block_handler.rs`) enforces. [1](#0-0)  This mirrors the reported `update()` bug class: a state-mutating entry point that relies on an implicit trust assumption (only privileged flows should ever call it) but has no access-control check enforcing that assumption in code.

### Finding Description
`BatchProverRpcServerImpl::set_commitments` takes a list of `SequencerCommitmentRpcParam`, converts each into a `SequencerCommitment`, logs "Overriding sequencer commitment", and unconditionally calls `put_commitment_by_index`, `put_commitment_index_by_l1`, and `put_prover_pending_commitment` on the ledger DB. [1](#0-0)  There is no signature check against the sequencer's DA public key, no cross-check against the actual merkle root of synced L2 blocks, and no ordering/height validation — all of which are present in the honest commitment-processing path used by full nodes: `process_sequencer_commitment` requires the merkle root to match the actual L2 block hashes and enforces strictly increasing height/index before it will accept and store a commitment. [2](#0-1) 

Because the prover uses `put_prover_pending_commitment` entries to select which commitment ranges to generate batch proofs for, and `SequencerCommitmentAccessor` state that gets read by the light-client circuit's `verify_batch_proof_seq_comm_relation` is populated from these same commitment records, an attacker-supplied fake commitment injected via this RPC can be used to drive proof generation over a merkle root/L2 range that a sequencer never actually posted to L1. [3](#0-2) 

### Impact Explanation
This breaks the binding that a batch proof's claimed sequencer-commitment set must equal the commitment set the sequencer actually posted to the DA layer. An unauthenticated caller reaching this RPC can plant an arbitrary commitment (wrong merkle root / wrong L2 range) directly into prover state, which the prover then treats as canonical input for proof generation — matching the "Critical: a false state transition proved... or an unauthorized sequencer commitment" impact category, since it lets state that was never authorized by the sequencer/DA enter the proving pipeline as if it were authentic.

### Likelihood Explanation
Any party capable of sending a JSON-RPC request to the batch prover's RPC endpoint can invoke `citrea_setCommitments` — no cryptographic proof of sequencer identity, no DA inclusion check, and no caller-identity check are performed in the handler itself. [4](#0-3) 

### Recommendation
Restrict `set_commitments` so it can only be invoked by a trusted/internal caller (e.g., gate it behind the same DA-validation logic used in `process_sequencer_commitment`, or remove it from the externally reachable RPC surface and make it an internal-only/test-only API), and require the same merkle-root and ordering checks before any commitment is persisted as canonical.

### Proof of Concept
1. Call `citrea_setCommitments` with a list containing one `SequencerCommitmentRpcParam` whose `merkle_root`/`l2_end_block_number` do not correspond to any commitment actually posted by the sequencer to Bitcoin DA.
2. Observe that `put_commitment_by_index`, `put_commitment_index_by_l1`, and `put_prover_pending_commitment` are called unconditionally, persisting the forged commitment. [5](#0-4) 
3. The prover subsequently treats this forged commitment as a `prover_pending_commitment` and may generate/attempt a batch proof over the bogus range, which the light-client circuit's `verify_batch_proof_seq_comm_relation` would accept as long as the JMT-stored commitment (also forged by the same RPC path) matches.

Note: I was unable to fully verify, within the available tool budget, whether an external authentication/authorization middleware wraps this RPC method in the deployed node configuration (the citation shows the handler itself performs no such check). If such middleware exists elsewhere in the RPC server setup, this may not be exploitable by a fully unprivileged network caller — a follow-up review of the RPC server construction/module registration would confirm this.

    Vm: Zkvm + 'static,
{
    async fn set_commitments(
        &self,
        commitments: Vec<SequencerCommitmentRpcParam>,
    ) -> RpcResult<()> {
        for commitment in commitments {
            let l1_height = commitment.l1_height.to::<u64>();
            let commitment = SequencerCommitment {
                merkle_root: commitment.merkle_root,
                index: commitment.index.to::<u32>(),
                l2_end_block_number: commitment.l2_end_block_number.to::<u64>(),
            };

            info!(
                "Overriding sequencer commitment, index={} merkle_root={} l2_end_height={} l1_height={}",
                commitment.index,
                hex::encode(commitment.merkle_root),
                commitment.l2_end_block_number,
                l1_height,
            );

            self.context
                .ledger_db
                .put_commitment_by_index(&commitment)
                .map_err(internal_rpc_error)?;
            // This might cause some duplicate commitment indices appear in l1 -> index table which is ok
            self.context
                .ledger_db
                .put_commitment_index_by_l1(SlotNumber(l1_height), commitment.index)
                .map_err(internal_rpc_error)?;
            self.context
                .ledger_db
                .put_prover_pending_commitment(commitment.index)
                .map_err(internal_rpc_error)?;
        }

        Ok(())
    }
