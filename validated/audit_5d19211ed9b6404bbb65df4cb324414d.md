### Title
Unbounded full-store iteration in `AssetIssueStore.getAllAssetIssues()` (inherited by `AssetIssueV2Store`) enables RPC-API DoS amplification - (File: `chainbase/src/main/java/org/tron/core/store/AssetIssueV2Store.java`)

### Summary
`AssetIssueV2Store` has no overrides and inherits `getAllAssetIssues()` from `AssetIssueStore`, which performs a full unbounded iteration over the entire `asset-issue-v2` column family on every call via `Streams.stream(iterator())`. Several unauthenticated, unpaginated RPC/HTTP endpoints (`GetAssetIssueList`, `GetAssetIssueByAccount`, `GetAssetIssueByName`, `GetAssetIssueListByName`, and their Solidity/PBFT-node variants) invoke this method directly, so the per-request cost of these free read queries scales linearly with the total number of assets ever issued on the network.

### Finding Description
`AssetIssueV2Store extends AssetIssueStore` and adds no methods of its own [1](#0-0) . Its inherited primary read method, `getAllAssetIssues()`, iterates every key in the underlying store with no bound or pagination: [2](#0-1) 

This method is reachable from multiple RPC/HTTP query paths that take no offset/limit and are exposed to anonymous callers:
- `Wallet.getAssetIssueList()` calls `getAllAssetIssues()` with no bound and is used by the unpaginated `GetAssetIssueList` HTTP/gRPC handler. [3](#0-2) 
- `Wallet.getAssetIssueByAccount()` fetches the entire list via `getAllAssetIssues()` and filters in memory. [4](#0-3) 
- `Wallet.getAssetIssueByName()` and `Wallet.getAssetIssueListByName()` similarly call `getAllAssetIssues()` on the V2 store for every request. [5](#0-4) [6](#0-5) 

The store is grown by an unprivileged attacker through `AssetIssueActuator`, which is reachable by any funded account broadcasting an `AssetIssueContract` transaction. Growth is gated only by a fee check and a "one asset per account" rule — not by a cap on total assets in the store: [7](#0-6) 

None of the checks listed in the rules (`validateSignature`, permission weights, `DecodeUtil.addressValid`, fork gates, energy/bandwidth accounting) bound the *query* side: read-only RPC/HTTP calls to `GetAssetIssueList`/`GetAssetIssueByAccount`/`GetAssetIssueByName` are not transactions, so they consume no bandwidth or energy and are essentially free to repeat, while the underlying scan cost is O(n) in the total number of assets across the whole network.

### Impact Explanation
Each unauthenticated query to the affected endpoints forces the node to enumerate and deserialize every `AssetIssueCapsule` in the `asset-issue-v2` (and `asset-issue`) column family. As the store grows (via normal, allowed asset issuance by any account paying `getAssetIssueFee()`), the per-query cost grows linearly and can be triggered repeatedly for free by any unprivileged caller, degrading node responsiveness — this matches the "DoS via RPC-API" impact class. The impact is bounded by the total asset count on the network rather than by any single attacker action, and it affects a shared read path used by multiple wallet/API endpoints.

### Likelihood Explanation
No privileged role, leaked key, or non-default configuration is required. An attacker (or many colluding low-cost accounts) pays the standard `AssetIssueContract` fee (`getAssetIssueFee()`, defaulting to 1024 TRX per new asset per account) to increase the number of stored assets, then issues unlimited free `GetAssetIssueList`/`GetAssetIssueByAccount`/`GetAssetIssueByName` RPC/HTTP calls to repeatedly trigger full-store scans. This is fully reproducible and requires no race conditions; the only cost is the one-time linear fee to grow the dataset, after which the amplification is free and repeatable indefinitely.

### Recommendation
Add pagination/limits to `getAllAssetIssues()`-backed public endpoints (`GetAssetIssueList`, `GetAssetIssueByAccount`, `GetAssetIssueByName`, `GetAssetIssueListByName`) similar to the already-existing `getAssetIssuesPaginated(offset, limit)` path, or cap the number of records scanned/returned per unauthenticated call, and consider indexing lookups by name/owner instead of full-table scan-and-filter.

```java
// JUnit-style PoC illustrating unbounded scan growth in AssetIssueV2Store.getAllAssetIssues()
@Test
public void testGetAllAssetIssuesScanGrowsWithSeededKeys() {
  int[] sizes = {100, 1000, 10000};
  for (int n : sizes) {
    for (int i = 0; i < n; i++) {
      AssetIssueCapsule cap = new AssetIssueCapsule(
          AssetIssueContractOuterClass.AssetIssueContract.newBuilder()
              .setName(ByteString.copyFromUtf8("tok" + i))
              .build());
      cap.setId(String.valueOf(i));
      assetIssueV2Store.put(cap.createDbV2Key(), cap);
    }
    long start = System.nanoTime();
    List<AssetIssueCapsule> all = assetIssueV2Store.getAllAssetIssues(); // full iterator scan, no limit
    long elapsed = System.nanoTime() - start;
    // elapsed grows ~linearly with n, demonstrating unbounded per-request cost
    System.out.println("n=" + n + " scanned=" + all.size() + " elapsedNs=" + elapsed);
  }
}
```
Request-level reproduction: repeatedly call the `GetAssetIssueList` HTTP/gRPC endpoint (no offset/limit) against a node whose `asset-issue-v2` store has been grown via many `AssetIssueContract` transactions; observe request latency/CPU scale with total asset count, confirming the invariant "iteration bounded independent of key count" is violated.
