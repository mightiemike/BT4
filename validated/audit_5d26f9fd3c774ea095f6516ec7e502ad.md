### Title
Unbounded `prefixQuery` in `DelegatedResourceAccountIndexStore.getV2Index` causes attacker-controlled RPC-API DoS - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Finding Description
`getV2Index`/`getWithPrefix` (`DelegatedResourceAccountIndexStore.java:114-138`) performs two `prefixQuery` calls over `V2_FROM_PREFIX+address` and `V2_TO_PREFIX+address`, then sorts and materializes **every** matching entry into a `DelegatedResourceAccountIndexCapsule`, with no limit, cap, or pagination on the number of entries returned. [1](#0-0) 

The number of index entries under a given owner/receiver prefix is directly controlled by an unprivileged caller: `Program.delegateResource`/`Program.unDelegateResource` (reachable from any deployed contract when `VMConfig.allowTvmFreezeV2` is enabled) drive `DelegateResourceProcessor`/`UnDelegateResourceProcessor.execute`, which write V2 index keys via `repo.updateDelegatedResourceAccountIndex`. Critically, when a delegation is fully undone, `UnDelegateResourceProcessor.execute` does **not** call `unDelegateV2` (which deletes the key); it instead writes an *empty* `DelegatedResourceAccountIndexCapsule(new byte[0])` at both the `fromKey` and `toKey`. [2](#0-1) 

Whether that empty-value write behaves as a true delete (removed from `prefixQuery` results) depends on the underlying `revokingDB`/`Chainbase.prefixQuery` semantics, which filter out `null` values but not necessarily zero-length values written explicitly; this needs verification, but even in the best case (empty writes act as deletes), an attacker can simply avoid ever calling unDelegate and instead perform many small `delegateResource` calls (minimum amount, e.g. 1 TRX/1 sun-scale) to thousands of distinct freshly-generated receiver addresses, each creating one live `V2_FROM_PREFIX`/`V2_TO_PREFIX` entry under the attacker's own owner address. This state growth is entirely paid for and controlled by the attacker and is never pruned automatically.

On the read side, `Wallet.getDelegatedResourceAccountIndexV2` calls `getV2Index`, which is reached unauthenticated via HTTP (`GetDelegatedResourceAccountIndexServlet`/`GetDelegatedResourceAccountIndexV2Servlet`) and gRPC (`RpcApiService`), and via the Solidity/PBFT read-only mirror servlets. The only protection at the servlet layer is `RateLimiterServlet`, which applies a generic QPS/IP-based limiter independent of the size of the underlying prefix range being scanned. [3](#0-2) [4](#0-3) 

There is no per-request cost tied to the number of index entries scanned: the rate limiter permits N QPS regardless of whether each query costs O(1) or O(entries), so an attacker who has inflated their own index to tens/hundreds of thousands of entries can issue repeated cheap unauthenticated queries, each of which forces the node to execute an expensive `prefixQuery` + sort + object materialization over the whole attacker-inflated range, consuming disproportionate CPU/IO on every call.

### Impact Explanation
This is a Denial-of-Service vector against the RPC-API: an attacker-controlled amount of on-chain state (bounded only by what the attacker is willing to pay in transaction fees to create) directly determines the cost of every subsequent unauthenticated read request against that address. Repeated invocation can degrade node responsiveness for the `getDelegatedResourceAccountIndex(V2)` interface and consume shared node resources (CPU/IO), matching the "DoS via RPC-API" impact class. It does not corrupt consensus state, steal funds, or leak secrets — impact is availability/performance degradation of the queried node(s), scoped to nodes that serve this API.

### Likelihood Explanation
Preconditions are attacker-affordable and require no privileged role: `VMConfig.allowTvmFreezeV2` must be enabled (default TVM freezing-v2 behavior on networks that support it), and the attacker needs enough TRX to fund many minimal delegations plus the energy/bandwidth for each contract call. Building up N=100k entries requires N transactions, each individually cheap, so cost scales roughly linearly with N but is entirely attacker-financed and repeatable; there is no protocol-level cap on the number of distinct delegation relationships per owner address. The exploitation of the read side is free/unauthenticated and repeatable at will, limited only by the generic QPS rate limiter, which is not adaptive to the cost of the specific query.

### Recommendation
- Bound `getWithPrefix`/`prefixQuery` result size (e.g., enforce a hard cap on returned entries, or require pagination/cursor parameters on `getDelegatedResourceAccountIndex(V2)`).
- Consider cost-based or state-size-aware rate limiting for this endpoint instead of flat QPS.
- Ensure `unDelegateResource` actually removes (not merely blanks) fully-undelegated index entries so unused index growth is naturally pruned, and audit whether zero-length capsule writes are filtered by `prefixQuery`/iterator logic as intended.
- Consider imposing a maximum number of concurrent delegation relationships per owner/receiver pair enforced at `validate()` time in `DelegateResourceProcessor`.

public void testUnboundedGetV2IndexGrowth() {
  byte[] owner = randomAddress();
  int n = 100_000;
  for (int i = 0; i < n; i++) {
    byte[] receiver = randomAddress();
    delegatedResourceAccountIndexStore.delegateV2(owner, receiver, i);

  DelegatedResourceAccountIndexCapsule result =
      delegatedResourceAccountIndexStore.getV2Index(owner);
  long elapsed = System.nanoTime() - start;

  // elapsed grows roughly linearly with n; repeat with n=1000 and n=100000
  // and compare wall-clock to demonstrate unbounded per-request cost.
}

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
