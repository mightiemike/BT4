## Finding

### Title
Sharded execution's total-supply patch only fixes `TOTAL_SUPPLY_STATE_KEY`, leaving other write-set locations that embed the same aggregator value with a stale, shard-local override — ([File: aptos-move/aptos-vm/src/sharded_block_executor/aggr_overridden_state_view.rs])

### Summary
During sharded block execution, each shard's `AggregatorOverriddenStateView` fakes the value at `TOTAL_SUPPLY_STATE_KEY` as a fixed constant `TOTAL_SUPPLY_AGGR_BASE_VAL` (`u128::MAX >> 1`) so that shards can execute independently and deterministically without knowing the true, globally-aggregated total supply. [1](#0-0)  After all shards finish, `aggregate_and_update_total_supply` computes the true delta and calls `TransactionOutput::update_total_supply`, which patches **only** the raw `TOTAL_SUPPLY_STATE_KEY` entry directly inside the write set bytes. [2](#0-1) [3](#0-2) 

### Finding Description
Aptos' delayed-field mechanism is specifically designed so that when Move code reads an aggregator value (e.g. `coin::supply()` / `optional_aggregator::read`) and stores the result into any other resource, resource-group entry, or table entry, that embedded copy is tracked via a `DelayedFieldID` placeholder and later resolved consistently everywhere it was embedded, through `replace_ids_with_values`/`map_id_to_values_in_write_set`/`map_id_to_values_in_group_writes` at commit-time materialization. [4](#0-3) [5](#0-4) 

However, this materialization happens **per-shard**, inside each shard's own independent `BlockSTM` execution, using the shard-local `AggregatorOverriddenStateView` as the base for the total-supply delayed field. That means any user resource/table/resource-group entry that legitimately embeds the coin-supply value gets patched with a value derived from `TOTAL_SUPPLY_AGGR_BASE_VAL` plus only that shard's local delta — not the real cross-shard aggregated value. [6](#0-5) 

The subsequent coordinator-level correction step, `aggregate_and_update_total_supply`, computes the correct global delta but applies it **only** to the single `TOTAL_SUPPLY_STATE_KEY` entry via `txn_output.update_total_supply(...)` → `WriteSet::update_total_supply`, which does a direct BTreeMap `insert` keyed by `TOTAL_SUPPLY_STATE_KEY` and asserts an existing entry was replaced. [7](#0-6) [3](#0-2)  It has no knowledge of, and does not touch, any other location in the write set where the same (now-materialized, stale) aggregator value was embedded by the normal delayed-field mechanism.

This gap is implicitly acknowledged in the code's own comment: "TODO: Remove this when we have aggregated total supply implementation for remote sharding. For now we need this because after all the txns are executed, the proof checker expects the total_supply to read/written to the tree." [8](#0-7) 

### Impact Explanation
If a transaction stores the observed total-supply/aggregator value into a resource-group entry or table entry (e.g., a custom accounting/audit resource that snapshots `coin::supply()`), the committed write set for that block will contain two mutually inconsistent representations of total supply: the canonical `TOTAL_SUPPLY_STATE_KEY` entry (correctly patched to the true global value) and the derived resource-group/table entry (left with the shard-local, `TOTAL_SUPPLY_AGGR_BASE_VAL`-based stale value). This is a genuine state-commitment inconsistency baked into the JMT/committed ledger state, not merely a display issue — any consumer trusting the derived resource's embedded supply value would observe an incorrect total supply that differs from the canonical aggregator state.

### Likelihood Explanation
This bug is only reachable when the block is executed through the sharded/remote execution path (`execute_block_sharded`), which is wired into the executor (`do_get_execution_output.rs`) and is a real, non-test production code path, but is not the default consensus execution engine for a standard mainnet validator — it requires the sharding/remote-executor configuration to be active. [9](#0-8)  If enabled, triggering the divergence requires only an ordinary, unprivileged Move call that reads `coin::supply()` (or another delayed-field-backed aggregator) and stores the result into a resource-group/table entry — no special privileges are needed.

### Recommendation
Either (a) extend `aggregate_and_update_total_supply` to re-run the delayed-field "replace identifiers with values" / re-patch logic across the entire write set (not just `TOTAL_SUPPLY_STATE_KEY`) for every location that embedded the total-supply delayed field, or (b) disable/guard the delayed-field materialization of the total-supply aggregator inside per-shard execution until the true cross-shard value is known, deferring embedding into other resources until after the coordinator-level correction. Complete the TODO referenced in `aggr_overridden_state_view.rs` before enabling sharded execution for consensus-relevant state.

### Proof of Concept
1. Deploy a Move module with a function `record_supply()` that calls `coin::supply<AptosCoin>()` and stores the returned `u128` into a table entry or a resource placed in a resource group (e.g., via `table::upsert` or a custom `#[resource_group_member]` struct).
2. Submit a transaction from any unprivileged account calling `record_supply()`, and run it under a validator/executor configured with `execute_block_sharded` (sharded/remote executor enabled, ≥2 shards).
3. After block commit, read back the canonical value at `TOTAL_SUPPLY_STATE_KEY` and compare it to the value stored in the table/resource-group entry written by `record_supply()`.
4. Observe the two values diverge: `TOTAL_SUPPLY_STATE_KEY` reflects the correctly aggregated global supply (patched by `aggregate_and_update_total_supply`), while the table/resource-group entry reflects the stale, shard-local `TOTAL_SUPPLY_AGGR_BASE_VAL`-derived value materialized during that shard's independent execution.

    let aggr_total_supply_delta_ref = &aggr_total_supply_delta;
    // Runtime is O(num_txns), hence parallelized at the shard level and at the txns level.
    executor_thread_pool.scope(|_| {
        sharded_output
            .par_iter_mut()
            .enumerate()

// For each delayed field in resource write set, replace the identifiers with values
// (ignoring other writes). Currently also checks the keys are unique.
fn map_id_to_values_in_write_set<T: Transaction, M: Materializer<T>>(
    resource_write_set: Vec<(T::Key, ValueWithLayout<T::Value>)>,
    materializer: &M,
) -> Result<Vec<(T::Key, T::Value)>, PanicError> {
    resource_write_set
        .into_iter()
        .map(|(key, value)| match value {
            ValueWithLayout::Exchanged(write_op, Some(layout)) => Ok((
                key,
                replace_ids_with_values(&write_op, &layout, materializer)?,
            )),
            ValueWithLayout::Exchanged(_, None) | ValueWithLayout::RawFromStorage(_) => Err(
                code_invariant_error("Resource write to materialize must have a layout"),
            ),
        })
        .collect()
}
