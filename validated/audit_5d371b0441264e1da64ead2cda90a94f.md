### Title
Silent session-storage write failure treated as success in OAuth callback lets a merchant be permanently locked out of the app - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/auth-code-flow.ts])

### Summary
The `SessionStorage` interface explicitly signals persistence failures via a `Promise<boolean>` return value rather than by throwing [1](#0-0) . Every OAuth callback handler in the app packages calls `storeSession()` and awaits it, but never checks the returned boolean, treating any non-throwing call as success and immediately proceeding to set the auth-complete cookie, register webhooks, run the `afterAuth` hook, and redirect the merchant into the app.

### Finding Description
This is the same bug class as the referenced report: an operation whose success is only knowable through a return value (ERC-20 `transfer` returning `false` / ERC-4626 `redeem` returning fewer shares than requested) is invoked and its result is discarded, so the caller proceeds under the false assumption that the operation succeeded.

- The core library's OAuth `callback()` unconditionally signs and sets the session cookie for the newly-created session id before the app ever attempts to persist the session: [2](#0-1) 
- `shopify-app-remix`'s `AuthCodeFlowStrategy.handleAuthCallbackRequest` then calls `config.sessionStorage!.storeSession(session)` and ignores its boolean result before registering webhooks, running the `afterAuth` hook, and redirecting into the app: [3](#0-2) 
- `shopify-app-express`'s `authCallback()` does exactly the same thing — `await config.sessionStorage.storeSession(callbackResponse.session);` with no check of the returned boolean before proceeding to webhook registration, `afterAuth`, and marking the request authenticated: [4](#0-3) 
- The custom-storage implementation guide the library itself ships even documents that `storeSession` can legitimately return `false` on a write error rather than throwing: [5](#0-4) 
- The library's own v5→v6 migration example is the only place that actually checks this return value (`if ((await sqliteSessionStorage.storeSession(...)) == false) { console.log(...) }`), confirming the return value is meant to be checked — it just isn't checked in the shipped app packages: [6](#0-5) 

If a `storeSession` implementation fails and returns `false` (e.g., transient DB/connection error, quota limit, duplicate-key conflict swallowed by the adapter, etc.) instead of throwing, the app has already signed the session cookie / considers OAuth complete, but no session record exists in storage. On the merchant's very next request, `loadSession(sessionId)` returns `undefined` [7](#0-6) , so `ensureInstalledOnShop`/`validateAuthenticatedSession`/`authenticateAdmin` treat the shop as not installed and redirect back into OAuth again [8](#0-7) , repeating the same failure-prone `storeSession` call indefinitely.

### Impact Explanation
This is a DoS of the authentication handler for the affected shop/merchant: the merchant can be stuck in an OAuth redirect loop and never reach an authenticated state, effectively locking them out of the app in a way indistinguishable from the referenced report's "funds locked" scenario — an operation silently fails, its failure is not surfaced, and the caller commits to a state (signed cookie / webhook registration / afterAuth side effects) predicated on success that never happened. Unlike the on-chain report, no funds are at risk here, but access/availability for a legitimate, unprivileged merchant is broken by a single OAuth flow, matching the "DoS of an auth handler" acceptance criterion.

### Likelihood Explanation
Triggering requires only a transient failure of the configured `SessionStorage` backend during `storeSession` (network blip to Redis/Mongo/Postgres/MySQL, KV/DynamoDB throttling, connection pool exhaustion, etc.) that the specific storage adapter surfaces as a `false` return rather than a thrown exception — which the interface contract explicitly allows. This does not require a privileged actor, leaked secret, or MITM; it can occur during any normal OAuth callback for any shop, and is more likely at scale (many concurrent installs) or against less-robust custom `SessionStorage` implementations that apps are encouraged to write themselves per `implementing-session-storage.md`.

### Recommendation
Check the boolean returned by `storeSession()` in `auth-callback.ts` (shopify-app-express), `auth-code-flow.ts` (shopify-app-remix and shopify-app-react-router), and `perform-token-exchange.ts`/`token-exchange.ts` call sites. On `false`, do not proceed to set the session cookie/return an authenticated context; instead, log the failure and return a 500 or retry, so the client is not told (via cookie/redirect) that OAuth succeeded when the session was never durably persisted.

### Proof of Concept
1. Implement (or use) a `SessionStorage` whose `storeSession` returns `false` on a simulated transient failure (per the documented contract in `implementing-session-storage.md`) instead of throwing.
2. Complete OAuth: `shopify.auth.callback()` succeeds and signs `SESSION_COOKIE_NAME` for the new session id (`oauth.ts` lines 219-230); `authCallback`/`handleAuthCallbackRequest` calls `storeSession(session)`, which returns `false`, but the code ignores it and proceeds to `afterAuth`/redirect.
3. Make a subsequent request as the merchant with the signed session cookie; `loadSession(sessionId)` returns `undefined` because nothing was ever stored, causing `ensureInstalledOnShop`/`authenticateAdmin` to redirect back to `/auth`, which repeats step 2 indefinitely if the storage failure persists — the merchant can never reach an authenticated app view.

  public async storeSession(session: Session): Promise<boolean> {
    try {
      const lines = this.readLines();

      let found = false;

      // process each line
      for (let i = 0; i < lines.length; i++) {
        // split the line by comma into columns
        const columns = lines[i].split(',');
        // check if the id column matches (second column is value of 'id')
        if (columns[1] === session.id) {
          // if the session id already exists, update the line
          lines[i] = session.toPropertyArray().join(',');
          found = true;
          break;
        }
      }

      if (!found) {
        // if the session id does not exist, add a new line
        lines.push(session.toPropertyArray().join(','));
      }

      try {
        this.writeLines(lines);
        return true;
      } catch (err) {
        // error on write
        return false;
      }
    } catch (err) {
      // error on read
      return false;
    }
