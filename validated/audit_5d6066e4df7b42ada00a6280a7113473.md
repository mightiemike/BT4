### Title
Exchange balance corruption via unchecked integer arithmetic when `allowHardenExchangeCalculation` is disabled - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
This is analogous to the reported Futureswap `Exchange`/`ExchangeFactory` bug class — an AMM-style pool that tracks token balances and computes trade outputs — but mapped onto java-tron's built-in `Exchange`/`ExchangeCreate`/`ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction` actuators, which implement a Bancor-style TRX/TRC10 liquidity pool reachable directly from a broadcast transaction.

### Finding Description
`ExchangeCapsule.transaction()` updates the pool's `firstTokenBalance`/`secondTokenBalance` after every trade [1](#0-0) . Whether the update uses overflow-checked arithmetic (`StrictMathWrapper.addExact/subtractExact`) and a post-condition check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) depends entirely on the `hardenedCalc` flag, which is derived from `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()` in `AbstractExchangeActuator.allowHarden()` [2](#0-1) . When this dynamic property is `0` (its default/unenabled state, changed only via a network parameter proposal), the balance updates use plain `+`/`-` with no overflow check and no negative-balance guard: `firstTokenBalance + sellTokenQuant` / `secondTokenBalance - buyTokenQuant`, etc. [3](#0-2) . `ExchangeTransactionActuator.execute()` calls this method directly and persists the resulting (potentially wrapped/negative) balances back into `ExchangeV2Store` unconditionally [4](#0-3) .

### Impact Explanation
If the non-hardened path can be driven to overflow `long` (e.g., via repeated large injects raising the balance close to `Long.MAX_VALUE`, then a trade that pushes the sum past the boundary) or to underflow below zero, the AMM invariant is silently corrupted. A corrupted (wrapped-negative or wrapped-huge) pool balance changes subsequent price computation (`ExchangeProcessor.exchange`), allowing a trader to withdraw the pool's assets for disproportionately little value or making pool balances inconsistent with actual token custody in the `AccountStore`, i.e., asset/accounting corruption in an on-chain financial primitive.

### Likelihood Explanation
Exploitability depends on being able to grow token balances near `Long.MAX_VALUE` or force underflow, which is constrained by `ExchangeCreateActuator`/`ExchangeInjectActuator`/`ExchangeTransactionActuator` validation (`ContractValidateException` on non-sufficient balances, `getExchangeBalanceLimit()` check in `ExchangeTransactionActuator.doValidate()` at lines 199–205) [5](#0-4) . I could not fully verify whether `getExchangeBalanceLimit()`'s configured value and other validation paths (e.g. `ExchangeInjectActuator`, `ExchangeWithdrawActuator`) are sufficient in all network configurations to prevent balances from reaching overflow-triggering magnitudes, nor whether `allowHardenExchangeCalculation` is enabled by default on mainnet — this determines whether the vulnerable code path is actually reachable today. The existence of a dedicated "hardened" fix path and test (`hardenedSuccessExchangeCreate`) strongly suggests the overflow issue in the legacy path was a known concern that was patched behind a feature flag rather than removed outright.

### Recommendation
Confirm the current mainnet/testnet value of `allowHardenExchangeCalculation` and the enforced `getExchangeBalanceLimit()`. If the property is not universally enabled, backport the overflow-checked/`hardenedCalc` semantics as the only code path (removing the legacy unchecked branch), or lower/enforce `exchangeBalanceLimit` such that overflow of `long` arithmetic during `addExact`/`subtractExact`-equivalent operations is provably unreachable in the legacy path.

### Proof of Concept
Not constructed — reaching an actual overflow would require chaining many `ExchangeInjectContract`/`ExchangeTransactionContract` transactions to push a pool's `firstTokenBalance`/`secondTokenBalance` near `Long.MAX_VALUE` while `allowHardenExchangeCalculation()==0`, subject to `getExchangeBalanceLimit()` enforcement whose configured value I was unable to confirm within the available context.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
