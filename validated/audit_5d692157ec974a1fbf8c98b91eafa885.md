### Title
Delegate-Action Nested `WithdrawFromGasKey` Bypasses Pending Transaction Queue Balance Accounting - (File: `chain/client/src/pending_transaction_queue.rs`, `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/verifier.rs`)

### Summary
The external report describes a Vault whose unguarded `withdraw()` can be called by any attacker to drain the native-token balance the contract relies on to pay for future messaging, causing subsequent operations to fail (DoS via balance starvation). The reachable nearcore analog is the gas-key balance accounting used for meta-transaction admission: the `PendingTransactionQueue` only inspects *top-level* actions of a submitted transaction to track pending `WithdrawFromGasKey` amounts, but `WithdrawFromGasKey` can also be nested inside a `Delegate` action. A nested withdrawal silently drains a gas key's balance without the admission-time queue accounting for it, so the queue continues to treat the gas key as "funded" for other pending transactions it has already admitted.

### Finding Description
Gas keys are sub-balances attached to an access key, funded via `TransferToGasKey` and drained via `WithdrawFromGasKey` (`runtime/runtime/src/access_keys.rs:257-335`). When a transaction is admitted for execution, `verify_and_charge_gas_key_tx_ephemeral` (`runtime/runtime/src/verifier.rs:524-594`) checks the gas key's balance minus `pending.paid_from_gas_key`, a value maintained by the client-side `PendingTransactionQueue` that is supposed to reflect gas costs and withdrawals from *already admitted but not-yet-applied* transactions signed with the same gas key.

The protocol version comment for `RejectWithdrawFromGasKeyInDelegate` makes the root cause explicit: [1](#0-0) 

That is: `WithdrawFromGasKey` can be embedded as an *inner* action of a `Delegate`/meta-transaction (`Action::Delegate(SignedDelegateAction)`), where the outer transaction's top-level action list contains only the `Delegate` action itself. Because the `PendingTransactionQueue` scans only the outer transaction's actions to compute `paid_from_gas_key`, this nested withdrawal is invisible to the admission-time balance bookkeeping, even though it executes at the receiver shard and moves real balance out of the gas key (`runtime/runtime/src/access_keys.rs:290-335`, dispatched from `apply_action` at `runtime/runtime/src/lib.rs:812-821`).

The fix that closes this hole is `validate_delegate_action`, which rejects any `WithdrawFromGasKey` nested in a delegate action — but only once `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` is enabled: [2](#0-1) 

The test that documents and exercises the pre-fix behavior confirms that, before the protocol upgrade, a delegate-wrapped `WithdrawFromGasKey` is admitted and executes successfully, draining the gas key balance: [3](#0-2) 

Based on the enum ordering in `core/primitives-core/src/version.rs` (`RejectWithdrawFromGasKeyInDelegate` sits alongside/after other features such as `FixContractLoadingError` and `ReceiptPromiseInputSizeLimit` that the accompanying architecture spec explicitly states are **not yet active** at the current stable protocol version, `STABLE_PROTOCOL_VERSION = 86`), this mitigating gate appears to still be nightly-only and not yet activated on the live network at the reviewed revision. I could not fully confirm the exact numeric protocol version assigned to `RejectWithdrawFromGasKeyInDelegate` from the excerpts retrieved, so this should be independently verified against `protocol_version()` in `core/primitives-core/src/version.rs` before treating it as currently exploitable in production.

### Impact Explanation
If `RejectWithdrawFromGasKeyInDelegate` is not yet active, any account holder (or a relayer colluding with/impersonating a sender, since the delegate is signed by the sender's own access key) can submit a sequence of gas-key transactions that the `PendingTransactionQueue` optimistically admits as "funded," then submit a delegate-wrapped `WithdrawFromGasKey` that drains the gas key out from under those already-admitted transactions. This is directly analogous to the reported Vault bug: a value store that other operations depend on for continued functioning is drained by an actor who is authorized to touch the store but exploits an accounting gap to disrupt already-scheduled, chain-trusted assumptions (admitted-but-unexecuted transactions). Concretely, this can cause previously admitted gas-key transactions to fail execution due to insufficient balance despite having passed admission checks — a form of invalid-state-transition-adjacent inconsistency between the client's optimistic admission bookkeeping and actual on-chain balance, and a transaction-processing correctness bug reachable purely by an ordinary transaction signer using standard meta-transaction (`Delegate`) and gas-key primitives.

### Likelihood Explanation
High, if the mitigating protocol feature is not yet active on the target network: the attack requires nothing more than a normal account with a gas key, standard `AddKeyAction`/`TransferToGasKeyAction` setup, and crafting a `SignedDelegateAction` whose inner actions include `WithdrawFromGasKeyAction` — all standard, unprivileged transaction-construction primitives exercised directly by the existing test `test_reject_delegated_gas_key_withdraw_protocol_upgrade`.

### Recommendation
Confirm the exact `protocol_version()` mapped to `ProtocolFeature::RejectWithdrawFromGasKeyInDelegate` in `core/primitives-core/src/version.rs` and whether it is active at the deployed `STABLE_PROTOCOL_VERSION`. If not yet active, treat the rollout of this feature as time-sensitive and ensure the `PendingTransactionQueue` (`chain/client/src/pending_transaction_queue.rs`) either (a) recursively inspects delegate-action inner actions for `WithdrawFromGasKey` when computing `paid_from_gas_key`, or (b) the validation-time rejection (`validate_delegate_action`) is activated as early as possible, consistent with the approach already implemented for `NewReceipt` mode.

### Proof of Concept
Reference: `test-loop-tests/src/tests/reject_delegated_gas_key_withdraw.rs:26-137` demonstrates the exploit path pre-upgrade:
1. Sender adds a gas key (`AddKeyAction` with `AccessKey::gas_key_full_access`) and funds it via `TransferToGasKeyAction`.
2. Sender signs a `DelegateAction` (with their own full-access key) whose single inner action is `WithdrawFromGasKeyAction` targeting the gas key, wrapped as `Action::Delegate` in an outer transaction whose top-level action list therefore does not literally contain `WithdrawFromGasKey`.
3. Submit via a relayer; the `PendingTransactionQueue` admits the transaction and any concurrently pending gas-key transactions without accounting for the nested withdrawal.
4. On execution, the gas key balance is drained (`balance_after == balance_before - WITHDRAW_AMOUNT`), demonstrating the hidden balance movement bypassing admission-time accounting. [4](#0-3)
