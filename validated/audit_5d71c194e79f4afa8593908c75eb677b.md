### Title
OAuth callback HMAC validation uses a different `shop` query-parameter value than the one used to redeem the access token - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
In `shopify.auth.callback`, when the incoming callback URL contains a duplicated `shop` query parameter, the code uses **two different mechanisms** to read that value for two different purposes: HMAC/state verification uses the *last* occurrence, while the actual token-exchange request and resulting session use the *first* occurrence. This mirrors the reported bug class ("multiple inputs/outputs, ambiguous choice of which one is authoritative") applied to an unauthenticated, Shopify-facing HTTP endpoint (the OAuth callback).

### Finding Description
`callback()` parses the callback URL's query string with `URLSearchParams` and reads `shop` twice, in two incompatible ways: [1](#0-0) 

```
const query = new URL(request.url, ...).searchParams;
const shop = query.get('shop')!;
```
`URLSearchParams.get()` always returns the **first** value for a repeated key.

Later, the HMAC/state check is performed against an object built with `Object.fromEntries(query.entries())`: [2](#0-1) 

For a duplicated key, `Object.fromEntries` keeps the **last** value, because each subsequent entry overwrites the previous key in the resulting object. So `validQuery()`/`validateHmac()` (in `packages/apps/shopify-api/lib/utils/hmac-validator.ts`, `generateLocalHmac`/`stringifyQueryForAdmin`) validate the HMAC and `state` cookie against the *last* `shop` value.

Immediately after the HMAC check succeeds, the code re-reads `query.get('shop')` (the *first* value again) to build the shop used for the actual token exchange and the resulting session: [3](#0-2) 

```
const cleanShop = sanitizeShop(config)(query.get('shop')!, true)!;
const postResponse = await fetchRequestFactory(config)(
  `https://${cleanShop}/admin/oauth/access_token`, ...);
const session: Session = createSession({..., shop: cleanShop, ...});
```

The net effect: the request's *integrity* (HMAC + anti-CSRF `state`) is proven for one `shop` value, but the code exchange and session creation are executed against a **different** `shop` value taken from the same request — exactly the "which input is the receiver, which output is the onramp" ambiguity described in the source report, applied to shop/tenant selection instead of BTC UTXOs.

Root-cause file/function support: [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker who has completed (or can trigger) a legitimate OAuth authorization flow for a shop they control can append a second, attacker-chosen `shop=<victim-domain>` parameter to Shopify's genuine callback redirect before it reaches the app. The HMAC/state check still validates successfully (it uses the attacker's real, last `shop=` value, matching Shopify's real signature), while the app then attempts to redeem the authorization `code` and create/store a session keyed to the *first* (attacker-chosen, arbitrary) `shop` value. This is a validated-request/action mismatch: the shop that "passed verification" is not the shop the app subsequently acts on, undermining the invariant that a verified Shopify callback corresponds 1:1 to the shop being installed/authenticated.

The severity in practice depends on whether Shopify's own `/admin/oauth/access_token` endpoint independently rejects a `code` that was not issued for the target shop (which is expected server-side behavior, but I could not verify this from the repository alone since that endpoint lives in Shopify's backend, not this codebase). If Shopify's token endpoint does bind codes to their issuing shop, the outward exploit is blocked at that layer; however, the library-level parameter-confusion bug (verify against one value, act on a different value from the same duplicated field) is a real defect independent of that external mitigation, and any other client-side consumer (logging, error messages, cookie path derivation via `config.cookiePath(session)`, `afterAuth` hooks, etc.) built on top of the mismatched `shop`/`cleanShop` pair inherits this ambiguity.

### Likelihood Explanation
Reaching this code path requires only an anonymous HTTP request to the app's public OAuth callback URL with a crafted, duplicated `shop` query parameter alongside a legitimately-obtained `hmac`/`state`/`code` set (obtainable by any actor who can install the app on their own store). No privileged access or secret leakage is required to reach the internal inconsistency; only the downstream consequence (a successful cross-shop token exchange) depends on Shopify's own server-side code-binding behavior, which is outside this repository and could not be verified here.

### Recommendation
Read the `shop` parameter exactly once from a single, canonical source and use that same value consistently for: state/HMAC validation, the token-exchange request, and session creation. Reject (or explicitly canonicalize, e.g. always take the first or always reject duplicates) any request containing a repeated `shop` parameter before performing HMAC/state verification, similar to the existing hardening already applied to App Proxy requests (`APP_PROXY_SINGLE_VALUE_PARAMS` in `packages/apps/shopify-api/lib/utils/hmac-validator.ts`) — that same duplicate-parameter rejection should be extended to the OAuth `callback()` flow's `shop` (and ideally `code`, `state`, `timestamp`) parameters.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, initiating `shopify.auth.begin`, and receives Shopify's genuine callback redirect: `GET /auth/callback?shop=attacker-shop.myshopify.com&code=...&state=...&timestamp=...&hmac=...`.
2. Attacker intercepts this redirect in their own browser (they fully control it, no MITM required) and modifies the query string to prepend a second `shop` parameter: `?shop=victim-shop.myshopify.com&shop=attacker-shop.myshopify.com&code=...&state=...&timestamp=...&hmac=...`.
3. The app's `callback()` handler:
   - Computes `authQuery.shop = "attacker-shop.myshopify.com"` (last value) for HMAC/state validation — passes, since this matches Shopify's real signature.
   - Computes `cleanShop = "victim-shop.myshopify.com"` (first value via `query.get('shop')`) and issues `POST https://victim-shop.myshopify.com/admin/oauth/access_token` with the attacker's `code`, then creates a `Session` with `shop: "victim-shop.myshopify.com"`.
4. Whether this results in an actual cross-tenant session depends on Shopify's backend rejecting the shop/code mismatch (unverified here), but the library-level shop-selection inconsistency itself is demonstrated purely via request crafting against `packages/apps/shopify-api/lib/auth/oauth/oauth.ts` lines 143-217.

export function callback(config: ConfigInterface): OAuthCallback {
  return async function callback<T = AdapterHeaders>({
    expiring,
    ...adapterArgs
  }: CallbackParams): Promise<CallbackResponse<T>> {
    throwIfCustomStoreApp(
      config.isCustomStoreApp,
      'Cannot perform OAuth for private apps',
    );

    const log = logger(config);

    const request = await abstractConvertRequest(adapterArgs);

    const query = new URL(
      request.url,
      `${config.hostScheme}://${config.hostName}`,
    ).searchParams;
    const shop = query.get('shop')!;

    const response = {} as NormalizedResponse;
    let userAgent = request.headers['User-Agent'];
    if (Array.isArray(userAgent)) {
      userAgent = userAgent[0];
    }
    if (isbot(userAgent)) {
      logForBot({request, log, func: 'callback'});
      throw new ShopifyErrors.BotActivityDetected(
        'Invalid OAuth callback initiated by bot',
      );
    }

    log.info('Completing OAuth', {shop});

    const cookies = new Cookies(request, response, {
      keys: [config.apiSecretKey],
      secure: true,
    });

    const stateFromCookie = await cookies.getAndVerify(STATE_COOKIE_NAME);
    cookies.deleteCookie(STATE_COOKIE_NAME);
    if (!stateFromCookie) {
      log.error('Could not find OAuth cookie', {shop});

      throw new ShopifyErrors.CookieNotFound(
        `Cannot complete OAuth process. Could not find an OAuth cookie for shop url: ${shop}`,
      );
    }

    const authQuery: AuthQuery = Object.fromEntries(query.entries());
    if (!(await validQuery({config, query: authQuery, stateFromCookie}))) {
      log.error('Invalid OAuth callback', {shop, stateFromCookie});

      throw new ShopifyErrors.InvalidOAuthError('Invalid OAuth callback.');
    }

    log.debug('OAuth request is valid, requesting access token', {shop});

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      code: query.get('code'),
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(query.get('shop')!, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    const session: Session = createSession({
      accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
      shop: cleanShop,
      state: stateFromCookie,
      config,
    });

function stringifyQueryForAdmin(query: AuthQuery): string {
  const processedQuery = new ProcessedQuery();
  Object.keys(query)
    .sort((val1, val2) => val1.localeCompare(val2))
    .forEach((key: string) => processedQuery.put(key, query[key]));

  return processedQuery.stringify(true);
}

function stringifyQueryForAppProxy(query: AuthQuery): string {
  return Object.entries(query)
    .sort(([val1], [val2]) => val1.localeCompare(val2))
    .reduce((acc, [key, value]) => {
      return `${acc}${key}=${Array.isArray(value) ? value.join(',') : value}`;
    }, '');
}

export function generateLocalHmac(config: ConfigInterface) {
  return async (
    params: AuthQuery,
    signator: HMACSignator = 'admin',
  ): Promise<string> => {
    const {hmac: _hmac, signature: _signature, ...query} = params;

    const queryString =
      signator === 'admin'
        ? stringifyQueryForAdmin(query)
        : stringifyQueryForAppProxy(query);

    return createSHA256HMAC(config.apiSecretKey, queryString, HashFormat.Hex);
  };
}
