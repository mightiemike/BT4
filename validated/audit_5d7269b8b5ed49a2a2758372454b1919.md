### Title
Unauthenticated `citrea_haltCommitments` / `citrea_resumeCommitments` RPC methods can mutate sequencer state without any API key - ([File: crates/common/src/rpc/auth.rs])

### Summary
The RPC `Auth` middleware only requires the configured `api_key` for three hard-coded methods (`backup_create`, `backup_validate`, `backup_info`). All other JSON-RPC methods, including sequencer-control methods that halt or resume L1 commitment production, are dispatched to the underlying service with no authentication check at all, analogous to the Lighthouse VC bug where only GET requests enforced the Authorization header while state-mutating POST/PATCH requests did not.

### Finding Description
The `Auth` middleware in `crates/common/src/rpc/auth.rs` gates access with a static allow-list: [1](#0-0) 

Any method name not in `PROTECTED_METHODS` bypasses the API-key check entirely and is forwarded directly to `service.call(req)`. This middleware is the only authentication layer installed on the RPC server: [2](#0-1) 

The sequencer exposes `citrea_haltCommitments` and `citrea_resumeCommitments`, which send control messages directly to the sequencer's block-production/commitment loop with no additional authorization inside the handlers: [3](#0-2) 

Because these method names are absent from `PROTECTED_METHODS`, any client that can reach the sequencer's RPC endpoint — which by default also has a permissive CORS layer allowing any origin and any headers — can invoke them without ever supplying `api_key`: [4](#0-3) 

The `RpcMessage::HaltCommitments` / `ResumeCommitments` are consumed by the sequencer's main run loop and toggle whether the sequencer continues to submit sequencer commitments to L1: [5](#0-4) 

This is the same class of bug as CL-2021-44: the authorization boundary is enforced inconsistently across an allow-list of methods rather than uniformly across all methods that mutate node/protocol-relevant state, so an unprivileged caller can trigger a state-mutating action the operator intended to be protected by `api_key`.

### Impact Explanation
An unauthenticated network client can call `citrea_haltCommitments` to make the sequencer stop submitting commitments to the DA layer indefinitely, or call `citrea_resumeCommitments` to restart it, without presenting the operator-configured `api_key`. This is an unauthenticated JSON-RPC call that mutates node state, matching the High-impact category defined for this scan ("an unauthenticated JSON-RPC call that mutates node state or bypasses Auth"). Halting commitments can stall the rollup's finality/proof pipeline that depends on sequencer commitments being posted to L1.

### Likelihood Explanation
Likelihood is high wherever the sequencer's JSON-RPC endpoint is network-reachable: no credential, session, or role is required — only knowledge of the method name, which is public (it's part of the `SequencerRpc` trait defined in the same crate). No sequencer, prover, or council privilege is needed by the caller; the caller only needs the ability to send an HTTP JSON-RPC POST to the port, which the code doesn't gate for these two methods.

### Recommendation
Add `citrea_haltCommitments` and `citrea_resumeCommitments` (and any other sequencer/administrative RPC methods that mutate node behavior) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`, or refactor the middleware to use an explicit allow-list of *public* read-only methods and require the API key by default for everything else, rather than an allow-list of protected methods.

### Proof of Concept
1. Start a sequencer node with `rpc.api_key` configured.
2. From an unauthenticated client (no `api_key` parameter), call:
```json
{"jsonrpc":"2.0","id":1,"method":"citrea_haltCommitments","params":[]}
```
3. Observe the call succeeds (`Auth::call` in `crates/common/src/rpc/auth.rs` forwards it because `"citrea_haltCommitments"` is not in `PROTECTED_METHODS`), and the sequencer stops posting commitments as confirmed by the `SequencerRpcMessage::HaltCommitments` branch in `crates/sequencer/src/runner.rs`.

const PROTECTED_METHODS: [&str; 3] = ["backup_create", "backup_validate", "backup_info"];

#[derive(Debug, Clone)]
pub struct Auth<S> {
    service: S,
    api_key: Option<String>,
}

impl<S> Auth<S> {
    pub fn new(service: S, api_key: Option<String>) -> Self {
        Self { service, api_key }
    }
}

impl<'a, S> RpcServiceT<'a> for Auth<S>
where
    S: RpcServiceT<'a> + Send + Sync + Clone + 'a,
{
    type Future = BoxFuture<'a, MethodResponse>;

    fn call(&self, req: Request<'a>) -> Self::Future {
        let method = req.method_name();
        let service = self.service.clone();
        let api_key = self.api_key.clone().map(Value::from);

        if !PROTECTED_METHODS.contains(&method) {
            return Box::pin(service.call(req));
        }
