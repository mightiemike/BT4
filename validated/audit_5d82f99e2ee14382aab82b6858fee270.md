## Title
Missing PubKey-to-Address Binding Check in `AccountInitDecorator` Allows Forged Signer Authorization for Gasless Txs - (File: `app/ante/account_init_decorator.go`)

### Summary
`AccountInitDecorator.AnteHandle` and its helper `verifySignatureForNewAccount` treat a gasless transaction's declared signer address (`signers[0]`, taken from `sigTx.GetSigners()`) as authenticated the moment *any* valid signature is found for *any* supplied public key — without ever checking that the supplied `pubKey` actually hashes to `newAccAddr`. This breaks the fundamental Cosmos SDK invariant (normally enforced by `ante.NewSetPubKeyDecorator`) that an address must be the hash of the public key that signed for it.

### Finding Description [1](#0-0) 

When a gasless tx (`txpolicy.IsGaslessTx`) targets an address with no existing account, the decorator:
1. Takes `newAccAddr := signers[0]` — this is derived purely from the message content (the proto `cosmos.msg.v1.signer` field value), not cryptographically bound to any key.
2. Calls `verifySignatureForNewAccount`, which builds `signerData.Address = newAccAddr.String()` and verifies the signature bytes against the attacker-supplied `pubKey`: [2](#0-1) 
3. If `authsigning.VerifySignature` succeeds (i.e., the signer produced a valid signature over sign-bytes that embed `newAccAddr`, which they trivially can since they choose both the message content and the private key used to sign), the decorator immediately calls `aid.ak.NewAccountWithAddress(ctx, newAccAddr)`, sets sequence to `1`, stores the account, and returns `ctx, nil` — **skipping the rest of the ante chain entirely for this tx**, including `ante.NewSetPubKeyDecorator`, `NewValidateSigCountDecorator`, `NewSigGasConsumeDecorator`, and `NewSigVerificationDecorator`: [3](#0-2) 

Because `signerData.Address` is populated from `newAccAddr` (attacker-chosen) rather than derived from `pubKey`, an attacker can:
- Craft a gasless message (e.g. `MsgExecutePayload` or `MsgMigrateUEA`, both in the gasless allowlist) whose signer field is set to an arbitrary, not-yet-initialized address `V` (a victim's counterfactual UEA/CEA address, or any address of interest).
- Sign it with their own keypair `K_attacker` (not `V`'s key).
- Submit it as a gasless tx.

`verifySignatureForNewAccount` verifies successfully because the sign-bytes it reconstructs use `Address: V` and `pubKey: K_attacker`'s pubkey — an internally consistent (but semantically meaningless) pair, since nothing checks `sdk.AccAddress(pubKey.Address()) == V`. The tx is accepted as if `V` authorized it, an account for `V` is created with `sequence = 1`, and — critically — since `next(ctx, tx, simulate)` is never invoked, message execution proceeds directly with `GetSigners() == [V]`, meaning downstream message handlers see `V` as the cryptographically-authenticated signer of the message despite `V`'s real key never having been used.

### Impact Explanation
This directly matches the in-scope impact "unauthorized UEA or CEA execution" / "unauthorized state transitions in universal execution flows." The ante pipeline's signer-authentication guarantee — that `msg.Signer == X` implies the caller holds `X`'s private key — is broken for any address that has not yet been initialized on-chain. Any module logic (e.g. `x/uexecutor` handlers for `MsgExecutePayload`, `MsgMigrateUEA`) that trusts `msg.Signer`/`GetSigners()` as proof of authorization (as Cosmos SDK ante/msg-server design assumes) can be tricked into executing on behalf of an address the attacker does not control. It also independently allows account-squatting/nonce-corruption: an attacker can pre-create any uninitialized address with `sequence = 1`, interfering with that address's legitimate first transaction (nonce mismatch), which corresponds to the in-scope "corruption of ... nonce progression" impact.

I was not able to fully verify, within the available context, whether `x/uexecutor`'s `MsgExecutePayload`/`MsgMigrateUEA` handlers rely solely on `msg.Signer` for authorization or additionally require an independent, payload-embedded cryptographic authorization (e.g., via the `usigverifier` precompile) that is separately checked inside the module logic. If such an independent check exists, the practical severity is reduced to account-squatting/nonce-DoS; if it does not, the ante-level flaw directly enables unauthorized UEA/CEA payload execution/migration as an arbitrary victim address.

### Likelihood Explanation
High. This is reachable by any unprivileged external user simply by submitting a normal gasless transaction with a self-controlled keypair and an attacker-chosen signer/address field — no special privileges, validator, or relayer collusion required.

### Recommendation
In `verifySignatureForNewAccount` (or before calling it), explicitly verify that `sdk.AccAddress(pubKey.Address())` equals `newAccAddr` before accepting the signature as valid for that address — mirroring the check performed by the standard `ante.NewSetPubKeyDecorator`. Reject the tx with `sdkerrors.ErrInvalidPubKey` if they do not match.

### Proof of Concept
1. Choose a target address `V` that has no account on-chain (e.g., a not-yet-registered UEA/CEA address).
2. Build a `MsgExecutePayload` (or `MsgMigrateUEA`) whose signer field is set to `V`.
3. Sign the transaction using an attacker-owned keypair `K_attacker` (unrelated to `V`).
4. Submit as a gasless tx. `AccountInitDecorator.verifySignatureForNewAccount` reconstructs `signerData.Address = V` and verifies the signature against `K_attacker`'s pubkey — this succeeds because no code checks `pubKey.Address() == V`.
5. Observe: an account for `V` is created with `sequence = 1`, and the `MsgExecutePayload`/`MsgMigrateUEA` message executes with `GetSigners() == [V]`, despite `V`'s real private key never being used.

A Go unit test analogous to the existing `account_init_decorator_test.go` cases, but supplying a `pubKey`/signature pair for a different keypair than the address encoded in the message's signer field, should assert this is rejected — currently it is not.
