### Title
Reorg-permit re-validation trusts sortition *existence* rather than *canonical descent*, letting a signer double-sign conflicting tenures - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`reorg_permit_stands` re-validates a previously recorded "reorg permit" purely by checking that the permitting sortition's burn hash still resolves (`Ok(_) => true`) via the node's `/v3/sortitions/burn/:hash` endpoint, without re-verifying that this sortition is still the one whose reorg-timing decision actually applies to the current signing attempt. This mirrors the Kyverno class of bug: a state that was meant to be a narrow, one-time exemption (a resource `pending deletion`; here, a `tenure marked superseded`) is trusted indefinitely as long as a shallow existence check passes, letting an attacker keep the exemption alive and use it to bypass the equivocation guard that is supposed to stop a signer from placing two conflicting signatures.

### Finding Description
When a miner proposes a tenure that does not build on the prior sortition, `SortitionData::check_parent_tenure_choice` [1](#0-0)  may sanction the reorg under the "reorg-timing rules" (first-proposal-to-burn-block timing). When sanctioned, every reorged tenure is recorded via `SignerDb::mark_tenure_superseded`, tagging the *permitting* sortition's burn hash [2](#0-1) .

Later, when a *different, conflicting* block reaches the pre-commit signing threshold, `get_signed_conflicts` returns the older, already-signed block annotated with this `superseded_by_*` record [3](#0-2) . The equivocation guard in `handle_block_pre_commit` is supposed to refuse to sign a new block while a fresh, live conflicting signature exists [4](#0-3) , but it *excludes* the conflict outright when `reorg_permit_stands` returns true:

```
fn reorg_permit_stands(...) -> bool {
    let Some(superseded_by) = &conflict.superseded_by else { return false; };
    match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
        Ok(_) => true,
        Err(NOT_FOUND) => false,
        Err(_) => false,
    }
}
``` [5](#0-4) 

The check only asks "does a sortition still exist at this burn hash", not "is that sortition still the head of the canonical fork that actually caused this specific reorg decision to remain valid for the block currently being signed." Because the record is keyed only by burn hash and is replaced wholesale on any newer permit (`INSERT OR REPLACE`, "a re-permit by a different tenure replaces the record" [6](#0-5) ), and because the permit was originally granted based on a timing heuristic evaluated once at proposal time rather than re-derived at signing time, the standing-permit state functions exactly like Kyverno's `deletionTimestamp` exemption: a legitimately narrow, one-shot bypass condition that persists and can be leaned on far outside the window it was designed for, as long as the shallow existence check keeps returning `Ok`.

### Impact Explanation
If the permit is treated as standing for longer than the single legitimate reorg it was granted for, the equivocation guard is defeated: this signer will sign a *second* conflicting block at the same or higher height in a different tenure, on top of a signature it already gave to a still-live block [7](#0-6) . Aggregated across enough signers doing the same (each independently fooled by the same permit-persistence gap), this produces two competing signer-certified blocks at the same height — a minority-triggerable tip disagreement / temporary fork, matching the "High" impact bucket (minority-triggerable divergence, temporary tip disagreement) defined in scope.

### Likelihood Explanation
Triggering requires only that: (1) an attacker's tenure gets a reorg-timing permit recorded once (achievable by any miner proposing a block just after a Bitcoin block transition — the specific "poorly timed" case the rule already handles as normal, not adversarial, behavior — see `checked_proposal_timing` logic [8](#0-7) ), and (2) the permitting burn hash keeps resolving via `/v3/sortitions/burn/:hash` afterward, which it will for as long as the node retains that sortition record — the check never asks whether that sortition is still the *canonical tip*'s ancestor for the *current* fork the signer is being asked to sign into. No majority stake or privileged access is needed; this is purely a client-facing signer/miner interaction.

### Recommendation
`reorg_permit_stands` should re-derive canonical-descent, not mere existence: verify that the permitting sortition is on the node's current canonical burn-chain fork *and* still the ancestor relationship that justified the specific tenure being replaced (e.g., re-run the same reorg-timing/forking-info check used in `check_parent_tenure_choice`, or bind the permit's validity window to the same freshness/height bounds used elsewhere for conflicts in `conflict_still_blocks`). At minimum, add a canonical-tip comparison analogous to the 404-vs-tip-height guard already used in `conflict_still_blocks` sortition checks, rather than trusting any non-404 response.

### Proof of Concept
1. Miner A's tenure 1 block is signed and locally accepted by signer S (fresh, live signature).
2. Miner B proposes tenure 2 shortly after the Bitcoin block transition, triggering `check_parent_tenure_choice`'s timing rule to sanction tenure 2 replacing tenure 1; `mark_tenure_superseded` records tenure 2's sortition burn hash as the permit.
3. S signs tenure 2's block because `reorg_permit_stands` reports the permit stands (test coverage confirms this exact path: `standing_reorg_permit_clears_conflict` [9](#0-8) ).
4. Before the permit record is superseded or pruned, and while tenure 2's sortition burn hash still resolves at the node (it does, indefinitely, as long as the node retains history — `prune_superseded_tenures` is the only expiry, and is time/height based, not descent-based), a *third* conflicting proposal at the same height in yet another tenure can be pushed through the same "permit stands" branch by any signer that independently received the same superseded-tenure record, without the guard ever re-checking that tenure 2's sortition is actually the fork the signer is currently building toward.
5. Result: signers end up split across the two forks with valid signature sets each, producing the reproduced-by-test double-sign scenario, generalized to a case where the "permit" outlives its intended single-use window.

**Uncertainty:** I could not fully trace `get_sortition_by_burn_hash`'s exact semantics (whether the stacks-node endpoint itself enforces "canonical tip" filtering server-side, which would partially mitigate this) since `stacks_client.rs`'s implementation body was not retrieved in this session — this should be verified before treating the finding as conclusively exploitable.

            excluded_signer_signature_hash.to_string(),

        // A pre-commit may be superseded by a competing proposal at the same height (e.g. a
        // re-proposed tenure-start block after the first failed to reach consensus), but a
        // signature must not be superseded while it's still "fresh". A signed block at the
        // same or higher height in ANY tenure is a conflict: two blocks at the same height are
        // siblings no matter which tenure they belong to (e.g. the next tenure's tenure-start
        // block conflicts with the current tenure's block at the same height). Blocks in
        // tenures whose reorg we sanctioned under the reorg-timing rules are excluded, but
        // only while the sortition the permit was granted to is still canonical
        // (`check_parent_tenure_choice` records the permit, `reorg_permit_stands` re-derives
        // its validity from the node); every other question about whether a conflict is
        // still live is derived from the node in `conflict_still_blocks`.
        //
        // Unlike the chainstate check above, a refusal here is "for now" rather than a
        // broadcast rejection: a later pre-commit re-evaluation may still sign the block once
        // the conflicting signature has gone stale.
        let conflicts = match self
            .signer_db
            .get_signed_conflicts(block_info.block.header.chain_length, &block_hash)
        {
            Ok(conflicts) => conflicts,
            Err(e) => {
                warn!("{self}: Failed to query the signed blocks. Refusing to sign block {block_hash}: {e:?}");
                return;
            }
        };
        let freshness_cutoff = get_epoch_time_secs().saturating_sub(
            self.proposal_config
                .tenure_last_block_proposal_timeout
                .as_secs(),
        );
        // A fresh signature only blocks while the block it covers could still be part of the
        // chain: see `conflict_still_blocks`, which asks the node whether it is. Check
        // freshness first: it is a local timestamp comparison, while `reorg_permit_stands`
        // and `conflict_still_blocks` each query the node, so stale conflicts cost no
        // round-trips.
        if let Some(conflict) = conflicts.iter().find(|conflict| {
            conflict.last_endorsed > freshness_cutoff
                && !self.reorg_permit_stands(stacks_client, conflict)
                && self.conflict_still_blocks(
                    stacks_client,
                    conflict,
                    block_info.block.header.chain_length,
                )
        }) {
            warn!(
                "{self}: Reached the pre-commit threshold for a block, but we have recently signed or accepted a different block at the same or higher height. Refusing to sign.";
                "signer_signature_hash" => %block_hash,
                "block_height" => block_info.block.header.chain_length,
                "conflicting_signer_signature_hash" => %conflict.signer_signature_hash,
                "conflicting_block_height" => conflict.stacks_height,
                "conflicting_consensus_hash" => %conflict.consensus_hash,
            );
            return;
        }
