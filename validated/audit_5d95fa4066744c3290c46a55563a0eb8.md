### Title
Meta-transaction (`DelegateAction`/`DelegateActionV2`) signature hash omits any chain/network identifier, enabling cross-chain signature replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
The NEP-461/NEP-366 "signable message" scheme used to authorize meta-transactions (`SignedDelegateAction` / `VersionedSignedDelegateAction`) hashes only a NEP-number-derived discriminant plus the `DelegateAction` payload itself. Unlike the base `Transaction`, which at least references a recent `block_hash`, the delegate-action hash contains no chain/genesis/network identifier at all. This is the same bug class as the reported Opera-Bridge issue: a signed authorization message lacking a domain separator (chain id / contract address) can be replayed on any other deployment/chain that shares the same account and nonce state.

### Finding Description
`SignedDelegateAction::verify()` and `VersionedSignedDelegateAction::verify()` compute the signed hash purely from `SignableMessage{ discriminant, msg: &delegate_action }`, where `discriminant` only encodes the NEP number (366 or 611) via `MessageDiscriminant::new_on_chain`: [1](#0-0) [2](#0-1) 

The discriminant construction has no chain id, genesis hash, or network id component—only a NEP number bucketed into an on-chain/off-chain range: [3](#0-2) [4](#0-3) 

The signed payload (`DelegateAction`/`DelegateActionV2`) itself only contains `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`—again, nothing that ties the signature to a specific chain instance: [5](#0-4) [6](#0-5) 

Replay protection for a `SignedDelegateAction` therefore relies entirely on the target chain's on-chain access-key nonce state matching between the signing context and the chain where it's submitted — there is no cryptographic binding to a specific chain/genesis. This is corroborated by `tools/mirror`, which must explicitly re-sign every `DelegateAction`/`DelegateActionV2` when replaying transactions from a source chain onto a differently-keyed target chain, precisely because the signature carries no chain-specific information and would otherwise remain "valid" bytes wherever the same account/nonce state exists: [7](#0-6) [8](#0-7) 

Any relayer (an ordinary, unprivileged transaction submitter — the same role as the report's "signature relayer") can take a previously observed `SignedDelegateAction` byte-for-byte and wrap it into a fresh outer transaction addressed at any NEAR-protocol-compatible chain where the same `sender_id`/`public_key`/nonce state exists (e.g., a network forked/cloned from a shared genesis snapshot, or a chain split resulting from a contentious upgrade), and the runtime will accept it exactly as it would on the original chain, since `apply_delegate_action` only checks `verify()`, the account's live access-key nonce, and `max_block_height` — none of which are chain-specific.

### Impact Explanation
If two NEAR-protocol chains ever exist with overlapping account/access-key/nonce state (a hard fork, a state-cloned staging/shadow network, or any scenario where genesis or a snapshot is shared), a single previously-signed meta-transaction can be independently executed on both chains by any relayer, without the original signer's renewed consent. Since `DelegateAction` inner actions can include transfers, `FunctionCall`s with deposits, staking, and key/account management, this constitutes concrete unauthorized/duplicated value movement and state-transition execution across the two chains from one signature.

### Likelihood Explanation
Exploitation requires two chains sharing account/nonce state (fork or clone scenario) plus an attacker/relayer capturing a valid `SignedDelegateAction`. This is not achievable against a single, never-forked mainline chain in isolation, but the precondition (chain fork/clone with preserved state) is realistic for NEAR-protocol-derived networks and is exactly the scenario the existing `tools/mirror` re-signing logic was built to guard against for its own migration use case — showing the underlying signature scheme genuinely lacks that protection natively. Given the medium precondition bar and trivial exploitation once met (no privileged access needed, just resubmission), this is rated Medium.

### Recommendation
Bind the NEP-461/NEP-366 signable-message discriminant (or the `DelegateAction`/`DelegateActionV2` payload) to a chain-specific value—e.g., the network's genesis hash or a protocol-defined chain id—so that `get_nep461_hash()` differs across any two independently-genesis'd or forked chains. This mirrors adding `block.chainid`/`address(this)` in the referenced report, adapted to NEAR's domain: incorporate `genesis_hash`/`chain_id` into the hashed `SignableMessage` for delegate actions.

### Proof of Concept
1. Chain A and Chain B are launched from an identical genesis/state snapshot (e.g., a migrated/cloned network, or a chain that later forks into A and B at a common block), such that `alice.near`'s access key and nonce are identical on both.
2. Alice signs a `DelegateAction` (e.g., transferring funds to Bob) per `SignedDelegateAction::sign` / `VersionedSignedDelegateAction::sign` — this hash contains no chain identifier: [9](#0-8) 
3. A relayer submits the resulting `Action::Delegate`/`Action::DelegateV2` wrapped in an outer transaction on Chain A; `apply_delegate_action` validates `verify()` and the nonce and executes it, incrementing Alice's nonce on Chain A only.
4. The same relayer (or anyone who observed the transaction) submits the identical `SignedDelegateAction` bytes wrapped in a fresh outer transaction on Chain B. Since Chain B's copy of Alice's account/nonce is still unmodified (state divergence began independently), `verify()` and nonce checks pass again, and the transfer executes a second time — on a different chain — from one signature.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}
