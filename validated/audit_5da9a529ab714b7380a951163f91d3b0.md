### Title
`ForbidTransferToContract` restriction is bypassable via `ParticipateAssetIssueContract`, allowing blind TRX transfers to smart contracts - (File: `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
The `ForbidTransferToContract` dynamic property was introduced specifically to stop plain TRX/TRC10 transfers from landing on smart-contract accounts outside of `TriggerSmartContract` execution. `TransferActuator` and `TransferAssetActuator` enforce this check, but `ParticipateAssetIssueActuator`, which also moves raw TRX balance to an arbitrary `toAddress`, never checks it — mirroring the TITN bug class where an admin-set transfer restriction is enforced on one value-moving code path but silently skipped on another.

### Finding Description
`TransferActuator.validate()` explicitly blocks sending TRX to a `Contract`-type account once `ForbidTransferToContract` is enabled: [1](#0-0) 

`TransferAssetActuator.validate()` mirrors this for TRC10 assets: [2](#0-1) 

However, `ParticipateAssetIssueActuator` moves the caller's TRX balance (`cost`) directly to the asset issuer's account (`toAddress`) — which can be any account, including a `Contract`-type account that issued a TRC10 token — and never checks `getForbidTransferToContract()`: [3](#0-2) 

Its `validate()` method also has no such guard, only checking address validity, balance sufficiency, asset ownership match, and time window — no contract-type restriction: [4](#0-3) 

A confirmed grep across the codebase shows `getForbidTransferToContract()` is referenced only in `TransferActuator` and `TransferAssetActuator` (plus the dynamic-properties store/config plumbing) — no other value-moving actuator honors it:


This is structurally identical to the TITN report: the primary invariant ("no blind TRX/TRC10 delivery to smart-contract accounts outside of `TriggerSmartContract`") is enforced on the "obvious" transfer path but not on an alternate value-moving actuator that ultimately performs the same balance mutation (`toAccount.setBalance(addExact(...))`), just as TITN's `_validateTransfer` guarded `transfer`/`transferFrom` but not the `mint`/`burn` paths used by `send`.

### Impact Explanation
Any account that has issued a TRC10 asset (an `AssetIssueContract` with `Contract`-type `ownerAddress`, i.e. an on-chain smart contract acting as an asset issuer/owner) can receive plain TRX from any user via `ParticipateAssetIssueContract`, completely bypassing the intended `ForbidTransferToContract` protection. This undermines a protocol-level, committee-controlled safety proposal meant to prevent forwarding TRX to contracts that cannot process it via fallback logic (since `ParticipateAssetIssueActuator` performs no code execution on the contract, unlike `TriggerSmartContract`). Funds sent this way can be stranded or misrouted depending on the receiving contract's expectations, and it defeats a governance-approved chain invariant, which is the closest unprivileged-actor analog to the TITN transfer-restriction bypass (broken invariant via an alternate code path, without any admin/privileged action needed to trigger it — only an unprivileged asset-issuance + participate flow).

### Likelihood Explanation
Likelihood is straightforward: any unprivileged user can issue a TRC10 asset from a smart-contract address (via `AssetIssueContract` where `owner_address` is a deployed contract, or by having a contract self-deploy and issue an asset) and any other unprivileged user can call `ParticipateAssetIssueContract` targeting that asset. No special permissions, timing, or race conditions are required — only that `allowForbidTransferToContract` (the committee proposal) is active on the network, which is a normal deployed configuration.

### Recommendation
Add the same `ForbidTransferToContract`/`AllowTvmCompatibleEvm` checks used in `TransferActuator.validate()` and `TransferAssetActuator.validate()` to `ParticipateAssetIssueActuator.validate()` (and audit other actuators such as `ExchangeTransactionActuator`, `WithdrawBalanceActuator`/`MortgageService`, and any others that call `AccountCapsule.setBalance`/`addExact` on an arbitrary `toAddress`) to ensure the invariant is uniformly enforced across every code path capable of moving TRX/TRC10 balance to a `Contract`-type account, rather than only the two "obvious" transfer actuators.

### Proof of Concept
1. Deploy a smart contract `C` with no payable fallback logic requirements.
2. From `C`, issue a TRC10 asset via `AssetIssueContract` (owner address = `C`).
3. Enable `ForbidTransferToContract` (as is standard on mainnet).
4. From an unrelated EOA `user1`, attempt `TransferContract` to `C` directly → fails with "Cannot transfer TRX to a smartContract." (per `TransferActuator.validate()`).
5. From `user1`, call `ParticipateAssetIssueContract` targeting `C`'s asset with `amount = X` TRX.
6. `ParticipateAssetIssueActuator.execute()` credits `X` TRX to `C`'s balance (`toAccount.setBalance(addExact(toAccount.getBalance(), cost))`), succeeding despite `ForbidTransferToContract` being enabled — demonstrating the same class of restriction bypass reported in the TITN bridge finding.
