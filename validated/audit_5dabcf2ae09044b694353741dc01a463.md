### Title
`SnosHintProcessor` always uses `VersionedConstants::latest_constants()` instead of the block's own protocol-version constants, causing OS/blockifier divergence in versioned-constants-gated syscall behavior - (File: `crates/starknet_os/src/hint_processor/snos_syscall_executor.rs`)

### Summary
This is the same bug class as the C4 Gondi finding: a value that should be sourced from a per-object stored/pinned configuration (there, `Loan.protocolFee`; here, the block's pinned `starknet_version`-specific `VersionedConstants`) is instead read from a "current"/global source (`protocolFee.fraction` in Gondi; `VersionedConstants::latest_constants()` here). `SnosHintProcessor::versioned_constants()` hardcodes the latest constants set regardless of which protocol version the block being re-executed by the Starknet OS actually belongs to.

### Finding Description
`SyscallExecutor for SnosHintProcessor` implements `versioned_constants()` as: [1](#0-0) 
This hard-codes `VersionedConstants::latest_constants()`, ignoring the actual `starknet_version` of the block being re-executed. In every other execution path in the sequencer (`blockifier`), `versioned_constants()` is derived from `BlockContext`, which is built with the constants matching the specific block's `starknet_version` (e.g. `VersionedConstants::get(&starknet_version)` as used in `apollo_rpc_execution` and in `virtual_block_executor.rs`): [2](#0-1) [3](#0-2) 

This `os_constants` value returned by `versioned_constants()` directly gates unprivileged, transaction-sender-controlled syscall semantics inside `get_execution_info`, such as whether L1 data gas is excluded from `TxInfo` and whether the transaction's reported version is rewritten to `1` for "v1-bound" accounts: [4](#0-3) 

The equivalent gating logic in the blockifier's normal execution path correctly consults the block-context-bound `versioned_constants`, not a global "latest" singleton: [5](#0-4) 

`data_gas_accounts`, `v1_bound_accounts_cairo1`, and `v1_bound_accounts_max_tip` are all versioned-constants fields that differ across protocol versions (confirmed by the presence of per-version JSON resource files and version diff regression files, e.g. `blockifier_versioned_constants_0_13_x.json` / `0_14_x.json` and `versioned_constants_diff_regression/0.13.0_0.13.1.txt`). If the block being re-executed by the Starknet OS is not on the very latest protocol version, `SnosHintProcessor` will evaluate `should_exclude_l1_data_gas` / `should_replace_to_v1` against the wrong (newer) constants set than the blockifier used when the block was originally produced.

### Impact Explanation
Because `get_execution_info`'s returned `TxInfo` (specifically whether L1 data gas fields are stripped, and whether `version` is rewritten to `1`) is directly observable by contract code (including account contracts controlled by an unprivileged transaction sender), any divergence between the constants set used by the block-producing sequencer/blockifier and the constants set used by the Starknet OS re-execution will make the OS compute different `CallInfo`/execution results (retdata, internal calls, potentially different fee/gas accounting) than what was actually committed on-chain for that block. This causes the Starknet OS re-execution to diverge from the honest block execution result for any block not on the OS's hardcoded "latest" version — i.e., an honest-node/OS divergence, which can result in state-root/commitment mismatches or rejection/failure of valid, previously-confirmed blocks during proving/re-execution, undermining the ability to produce a correct proof for the actual committed state.

### Likelihood Explanation
This is triggered simply by including the affected class hash (one that is present in the version-specific `data_gas_accounts` or `v1_bound_accounts_cairo1` sets) among the transactions being re-executed and having the block's protocol version differ from `VersionedConstants::LATEST` — a condition that is unprivileged, reachable from an ordinary transaction sender's account contract implementation, and will recur for every historical block once a new protocol version becomes `LATEST` while old blocks with different `data_gas_accounts`/`v1_bound_accounts_*` sets still need OS re-execution.

### Recommendation
Change `SnosHintProcessor`'s `versioned_constants()` (in `crates/starknet_os/src/hint_processor/snos_syscall_executor.rs:363-365`) to resolve constants from the block's own `starknet_version`/os block input (analogous to `VersionedConstants::get(&starknet_version)` used elsewhere), rather than unconditionally returning `VersionedConstants::latest_constants()`, so `data_gas_accounts`, `v1_bound_accounts_cairo1`, `v1_bound_accounts_max_tip`, and other version-gated fields match what was used at original block-execution time.

### Proof of Concept
1. A block `B` is produced under protocol version `V_old`, whose `VersionedConstants` (`V_old`) has `data_gas_accounts = {}` (class hash `C` not present) or a different `v1_bound_accounts_cairo1` set than `V_latest`.
2. An unprivileged sender deploys/uses account contract with class hash `C`, and its `__validate__`/`__execute__` invokes `get_execution_info()` syscall.
3. During block `B`'s original execution, blockifier's `versioned_constants()` returns `V_old` constants, so `should_exclude_l1_data_gas`/`should_replace_to_v1` evaluate one way, producing a specific `TxInfo` view and resulting `CallInfo`.
4. Later, the Starknet OS re-executes block `B` for proving via `SnosHintProcessor`, whose `versioned_constants()` (`crates/starknet_os/src/hint_processor/snos_syscall_executor.rs:363-365`) unconditionally returns `VersionedConstants::latest_constants()` (`V_latest`, where `C` is now in `data_gas_accounts` or the v1-bound set changed).
5. `get_execution_info` in the OS path computes `should_exclude_l1_data_gas`/`should_replace_to_v1` differently than the original execution, producing a different `TxInfo` view to the contract than what was actually used on-chain, causing the OS's execution trace/output for block `B` to diverge from the committed result.     fn get_execution_info(
        _request: GetExecutionInfoRequest,
        vm: &mut VirtualMachine,
        syscall_handler: &mut Self,
        _remaining_gas: &mut u64,
    ) -> Result<GetExecutionInfoResponse, Self::Error> {
        let call_info_tracker = syscall_handler.get_current_call_info_tracker()?;
        let original_execution_info_ptr = call_info_tracker.execution_info_ptr;
        let class_hash =
            call_info_tracker.call_info.call.class_hash.expect("No class hash was set.");
        let tx_version =
            syscall_handler.get_execution_info_nested_field_value(&["tx_info", "version"], vm)?;

        let os_constants = &syscall_handler.versioned_constants().os_constants;
        // Check if we should exclude L1 data gas for this class hash.
        let should_exclude_l1_data_gas = tx_version == TransactionVersion::THREE.0
            && os_constants.data_gas_accounts.contains(&class_hash);
        // Check if we should return version = 1.
        let tip = syscall_handler.get_execution_info_nested_field_value(&["tx_info", "tip"], vm)?;
        let should_replace_to_v1 = tx_version == TransactionVersion::THREE.0
            && os_constants.v1_bound_accounts_cairo1.contains(&class_hash)
            && tip <= Felt::from(os_constants.v1_bound_accounts_max_tip.0);

        // Allocate or return the original execution info segment.
        let execution_info_ptr = allocate_or_return_execution_info_segment(
            original_execution_info_ptr,
            should_exclude_l1_data_gas,
            should_replace_to_v1,
            vm,
            syscall_handler.program,
        )?;
        Ok(GetExecutionInfoResponse { execution_info_ptr })
    }

    /// Return whether the L1 data gas should be excluded for the `get_execution_info` syscall.
    pub fn should_exclude_l1_data_gas(&self) -> bool {
        let class_hash = self.call.class_hash;
        let versioned_constants = &self.context.tx_context.block_context.versioned_constants;
        versioned_constants.os_constants.data_gas_accounts.contains(&class_hash)
            && self.context.tx_context.tx_info.version() == TransactionVersion::THREE
    }
