Analysis supporting this conclusion:

The binding claimed broken is: `processedTxIds[txId]` insertions == number of distinct Bitcoin move transactions actually broadcast/included. The premise requires two distinct `moveTx` payloads (different `witness`/`shaScriptPubkeys`) that hash to the same `txId` via `ValidateSPV.calculateTxId(moveTx.version, moveTx.vin, moveTx.vout, moveTx.locktime)`, which by design (BIP141) excludes witness data — this is a legitimate, intentional Bitcoin property, not a bug. [1](#0-0) 

However, for two such transactions to differ only in witness while sharing identical `version`/`vin`/`vout`/`locktime`, they must spend the exact same UTXO (`vin` is part of the hashed fields). On the real Bitcoin blockchain only one such conflicting transaction can ever be confirmed — the second is a double-spend and cannot be mined without majority hashrate/reorg control, which is explicitly out of scope for this audit. [2](#0-1) 

Critically, `deposit()` does not accept the `moveTx` on trust — it requires `LIGHT_CLIENT.verifyInclusion(proof.blockHeight, wtxId, proof.intermediateNodes, proof.index)` where `wtxId` is the *witness-included* hash, checked against the real Bitcoin witness Merkle root committed via `BitcoinLightClientContract::setBlockInfo`, which is populated from actual finalized L1 block headers by the sequencer/DA layer. [3](#0-2)  An attacker cannot forge a valid Merkle inclusion proof for a `wtxId` that was never actually mined, so a second, non-broadcast variant with a colliding `txId` but forged witness cannot pass this check. Additionally, `deposit()` independently reconstructs and verifies the BIP-341 Taproot Schnorr signature via `verifySigInTx` over the actual witness/script — this check was specifically added after a documented prior vulnerability to prevent exactly this class of "different witness, same effective tx" forgery. [4](#0-3) [5](#0-4) 

At the RPC/sequencer layer, `citrea_sendRawDepositTransaction` also simulates the call via `evm.get_call` before accepting the deposit into the pool, and separately deduplicates by a `calc_tx_id` derived from `version`/`vin`/`vout`/`locktime` before the deposit even reaches the chain. [6](#0-5) [7](#0-6) 

Since exploiting this requires either a SHA256 hash collision on the txId hashing (computationally infeasible, purely theoretical) or a real Bitcoin double-spend/reorg (majority hashrate, explicitly excluded), and the on-chain `deposit()` logic independently re-verifies both Merkle inclusion of the witness-inclusive `wtxId` and the Schnorr signature over the actual witness, the claimed binding violation cannot be demonstrated by an unprivileged attacker within scope.

    fn calc_tx_id(req: &Deposit) -> anyhow::Result<[u8; 32]> {
        let call = BridgeContract::depositCall::abi_decode_raw(req, true)
            .map_err(|e| anyhow::anyhow!("Could not decode DepositCall ABI: {e:?}"))?;

        let tx = call.moveTx;

        let mut data = Vec::new();

        data.extend_from_slice(&tx.version.0);
        data.extend_from_slice(&tx.vin.0);
        data.extend_from_slice(&tx.vout.0);
        data.extend_from_slice(&tx.locktime.0);

        let hasher = Sha256::hash(&data);

        let second = Sha256::hash(&hasher);

        Ok(second)
    }
