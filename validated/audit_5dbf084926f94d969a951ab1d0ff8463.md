### Title
Chainlink exchange-rate oracle applies only static absolute bounds with no outlier/deviation filtering - (File: `crates/apollo_l1_gas_price/src/rate_bounds.rs`)

### Summary
The sequencer's `ChainlinkOracleClient` accepts any oracle answer that falls within wide, statically-configured absolute bounds, with no check on the rate's deviation from recently accepted values. This mirrors the reported bug class: a price feed consumer that filters obviously-broken values (zero, decimals-mismatch, stale/future timestamps) but has no defense against a plausible-but-manipulated or poisoned price, letting a single volatile/compromised read flow directly into consensus-critical fee computation.

### Finding Description
`read_feed` in `crates/apollo_l1_gas_price/src/chainlink_oracle/feed_read.rs` performs decimals validation, a zero-answer check, and staleness/future-timestamp checks, then calls `check_rate_bounds` as the only sanity filter on the numeric value itself: [1](#0-0) 

`check_rate_bounds` only compares the rate against fixed `minimum_rate`/`maximum_rate` config values, with no relation to the previously accepted rate or a rolling median — exactly the missing mitigation (median/threshold tracking) called out in the external report: [2](#0-1) 

The developers' own comment documents that the bounds are wide enough to admit a "plausible but manipulated" answer, and explicitly flags the missing relative-to-previous-block check as unimplemented: [3](#0-2) 

Production config confirms the width of the accepted band: STRK/USD accepts $0.0001–$10 (a 100,000× range) and ETH/USD accepts $20–$50,000: [4](#0-3) 

This oracle rate feeds directly into the L2 fee-market target computation reachable on every block build/validate: `resolve_fee_target` calls `get_strk_to_usd_rate`, and `compute_fee_target` converts it directly into `SNIP35_FEE_TARGET_FRI`/the fee target without any additional outlier check: [5](#0-4) [6](#0-5) 

The client itself also documents that reads are not deterministic across validators (`call_contract` executes against each node's own latest committed state), so the same block timestamp can resolve to different Chainlink rounds on different nodes, and this is only saved from causing disagreement because Chainlink's deviation threshold is assumed to sit "far inside" the `l1_gas_price_margin_percent` tolerance validators compare against: [7](#0-6) 

### Impact Explanation
The fee target that is derived from the unfiltered rate is clamped into a bounded band around `fee_actual` by `compute_fee_proposal`/`fee_proposal_bounds` before publication, which limits — but does not eliminate — the effect of a single bad read: sustained manipulation or misconfiguration of the feed (or of its Starknet-side aggregator contract) can still walk the L2 gas price target toward one edge of a 100,000×-wide range over successive blocks, since nothing checks the new rate against recent history. This can materially overcharge or undercharge every user's L2 gas fee network-wide (a form of user economic loss via manipulated fee accounting), and in the worst case interacts with the assumed-but-unenforced "deviation is inside the margin" invariant to produce validator disagreement (honest-node divergence) if that assumption is violated.

### Likelihood Explanation
Exploitation requires influencing (or exploiting a misconfiguration/attack of) the Chainlink aggregator contract's `latest_round_data`/`decimals` view responses read by the batcher — a feed anyone can call the view functions of, but which is normally only writable by the feed's authorized reporters. The developers already flag this as a known, unaddressed gap ("TODO(Asaf): bound the rate's change against the previous block's implied rate"), indicating the absolute bounds alone are known-insufficient. Likelihood is therefore tied to feed compromise/misconfiguration rather than a trivial single-transaction exploit, but the missing mitigation is concrete and already acknowledged in-repo.

### Recommendation
Add a relative/rate-of-change check anchored to the block header (not node-local history) so every validator rejects/accepts the same values deterministically — e.g., bound each accepted rate to within a threshold of the last committed block's implied rate or a short rolling median, as the external report recommends, rather than relying solely on wide static absolute bounds.

### Proof of Concept
Not applicable as a standalone runnable PoC: the finding is a code-level gap (absence of a deviation/outlier check), demonstrated by the current implementation and tests in `rate_bounds_test.rs`, which only verify the static min/max edges are enforced and contain no test for rejecting a rate that jumps far from the previously accepted one: [8](#0-7)

//! The absolute sanity bounds every exchange rate must fall in, whichever source reports it.

use apollo_l1_gas_price_config::config::RateBounds;
use apollo_l1_gas_price_types::errors::ExchangeRateOracleClientError;
use apollo_l1_gas_price_types::ExchangeRate;

#[cfg(test)]
#[path = "rate_bounds_test.rs"]
mod rate_bounds_test;

// TODO(Asaf): bound the rate's change against the previous block's implied rate. The absolute
// bounds below are wide enough to pass a manipulated but plausible answer, the STRK/USD pair alone
// accepting anything from $0.0001 to $10, which only a bound relative to the last accepted rate
// catches. It must be anchored to the block header rather than to node-local history, so that every
// validator accepts and rejects the same values.
/// Absolute bounds are the only defense against a feed wired to the wrong asset or a
/// plausible-but-poisoned answer: consensus checks that validators agree with each other, never
/// that the agreed value is sane, and every node reads the same chain state.
pub(crate) fn check_rate_bounds(
    rate: ExchangeRate,
    bounds: RateBounds,
) -> Result<(), ExchangeRateOracleClientError> {
    if rate < bounds.minimum_rate || rate > bounds.maximum_rate {
        return Err(ExchangeRateOracleClientError::RateOutOfBoundsError {
            pair: bounds.pair,
            rate,
            min_rate: bounds.minimum_rate,
            max_rate: bounds.maximum_rate,
        });
    }
    Ok(())
}

pub fn compute_fee_target(
    target_atto_usd_per_l2_gas: u128,
    strk_usd_rate: u128,
) -> Option<GasPrice> {
    if strk_usd_rate == 0 {
        return None;
    }
    // floor_fri = target_atto_usd_per_l2_gas * 10^18 / strk_usd_rate
    let numerator = U256::from(target_atto_usd_per_l2_gas) * U256::from(FRI_DECIMALS_SCALE);
    let floor = numerator / U256::from(strk_usd_rate);
    Some(GasPrice(u128::try_from(floor).unwrap_or(u128::MAX)))
}

///
/// Consensus calls `fetch_rate` on every proposal build and validate, so the call must not block on

#[rstest]
fn a_rate_exactly_on_either_bound_is_accepted(
    #[values(CurrencyPair::EthUsd, CurrencyPair::StrkUsd, CurrencyPair::EthStrk)]
    pair: CurrencyPair,
) {
    let bounds = default_bounds(pair);
    for rate in [bounds.minimum_rate, bounds.maximum_rate] {
        check_rate_bounds(rate, bounds).unwrap();
    }
}

/// One unit at `EXCHANGE_RATE_DECIMALS` outside either bound is rejected, so the accepted band is
/// exactly the configured one.
#[rstest]
fn a_rate_one_unit_outside_either_bound_is_rejected(
    #[values(CurrencyPair::EthUsd, CurrencyPair::StrkUsd, CurrencyPair::EthStrk)]
    pair: CurrencyPair,
) {
    let bounds = default_bounds(pair);
    for rate in [bounds.minimum_rate - 1, bounds.maximum_rate + 1] {
        assert_matches!(
            check_rate_bounds(rate, bounds),
            Err(ExchangeRateOracleClientError::RateOutOfBoundsError { pair: error_pair, .. })
                if error_pair == pair
        );
    }
}
