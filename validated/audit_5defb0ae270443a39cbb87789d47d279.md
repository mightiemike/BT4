### Title
Per-builtin proving-gas cost derivation (`induced_gas_costs`) truncates to zero, letting a transaction's builtin usage bypass bouncer accounting - (File: `crates/blockifier/src/bouncer.rs`)

### Summary
`BuiltinInstanceLimits::induced_gas_costs` computes each Cairo builtin/opcode's per-instance proving-gas cost as `floor(proving_gas / limit)`, exactly the same "amount * scale / total_shares" integer-division pattern flagged in the referenced report. With the configured default limits (e.g. `range_check96: 33_519_553`, `add_mod: 3_000_000`, `mul_mod: 3_000_000`) and a `proving_gas` block budget on the order of `5_000_000_000`, division still yields a small non-zero cost today, but the derivation has no floor/guard, so any operator/versioned-constants configuration where `limit > proving_gas` (or where `proving_gas` is temporarily reduced, e.g. via `BouncerConfig::max()`'s comment "Keep proving_gas at the default value") drives a builtin's per-instance cost to `0`.

### Finding Description
`BuiltinInstanceLimits::induced_gas_costs` derives per-primitive proving-gas cost with plain integer division and no rounding-up or minimum-of-one enforcement: [1](#0-0) 

This is structurally identical to the reported bug class: an accumulator/weight contribution computed as `numerator / denominator` that can floor to zero when the denominator (here, the configured instance limit) is large relative to the numerator (`proving_gas`, the block-wide budget). The resulting `BuiltinGasCosts` feeds directly into the bouncer's per-transaction weight computation (`get_tx_weights` → `TxWeights.bouncer_weights.proving_gas`), which gates whether a transaction fits in the current block: [2](#0-1) 

If any Cairo primitive's induced cost rounds to `0`, then every execution of that builtin/opcode contributes zero to `proving_gas`, so a transaction (or sequence of transactions from an unprivileged sender) can invoke that builtin arbitrarily many times without ever counting against the bouncer's `proving_gas` capacity check in `has_room`/`within_max_capacity_or_err`.

### Impact Explanation
The bouncer's `proving_gas` weight exists specifically to bound the total proving cost per block so the sequencer/prover can process and prove each block within resource/time budgets. If a builtin's derived cost silently truncates to zero, an attacker-crafted transaction (or set of transactions from a single submitted call) can accumulate unbounded real proving work for that builtin while `proving_gas` accounting reports it as free, defeating the bouncer's purpose. This can push actual per-block proving/execution resource consumption far beyond the intended cap, which under the finding's threat categories corresponds to blockifier execution/bouncer weight miscalculation — a resource-accounting bypass reachable from a single unprivileged transaction, not merely a "resource-only" nuisance since it can make committed blocks economically/computationally larger than the bounded capacity the bouncer is designed to enforce (risking downstream inability to prove/process blocks within budget).

### Likelihood Explanation
Likelihood depends entirely on configuration: with the shipped `BuiltinInstanceLimits::default()` values and `BouncerWeights::default().proving_gas = 5_000_000_000`, all default derived costs remain ≥ 1 (I verified this is not currently triggered under the shown default JSON constants and Rust defaults). However, the function itself performs no validation that `proving_gas >= limit`, and callers such as `BouncerConfig::max()` explicitly reduce/pin `proving_gas` to the default while other tests already construct scenarios with much smaller `proving_gas` budgets. Any deployment, configuration change, or versioned-constants update that raises a `BuiltinInstanceLimits` value close to or above the block's `proving_gas` capacity (a governance/config action, not requiring exploitation of user funds) would silently zero out that builtin's cost. This is a real but configuration-contingent risk, not a bug exploitable purely from a malicious transaction's calldata under current shipped defaults.

### Recommendation
Change `induced_gas_costs` to use ceiling division with a minimum floor of 1 (mirroring the `Fee::checked_div_ceil` pattern already used elsewhere in this codebase for gas/fee conversions), e.g. `derive(limit) = max(1, proving_gas.0.div_ceil(limit.get()))`, or explicitly assert/reject configurations where `limit >= proving_gas` at construction/deserialization time so a zero-cost builtin can never silently enter production.

### Proof of Concept
Not concretely exploitable against shipped defaults (verified: `5_000_000_000 / 33_519_553 ≈ 149`, `/ 3_000_000 ≈ 1666`, both non-zero). The vulnerability is latent in the arithmetic itself: for any `BuiltinInstanceLimits` value `L` and `proving_gas` budget `P` where `L > P` (achievable via versioned-constants/config changes, e.g. lowering `proving_gas` in `BouncerWeights` or raising a builtin's instance limit), `derive(L) = P / L = 0`: [3](#0-2) 
Under such a configuration, a transaction invoking that builtin `N` times (for arbitrarily large `N`) would add `0 * N = 0` to the block's accumulated `proving_gas` weight, letting it bypass `BouncerConfig::has_room`/`within_max_capacity_or_err` checks entirely while consuming real proving resources.

impl BuiltinInstanceLimits {
    /// Induces the per-instance proving-gas cost of each Cairo primitive from its per-block
    /// instance limit: `cost = floor(proving_gas / limit)`.
    pub fn induced_gas_costs(&self, proving_gas: GasAmount) -> BuiltinGasCosts {
        let derive = |limit: NonZeroU64| -> u64 { proving_gas.0 / limit.get() };
        BuiltinGasCosts {
            pedersen: derive(self.pedersen),
            range_check: derive(self.range_check),
            range_check96: derive(self.range_check96),
            poseidon: derive(self.poseidon),
            ecdsa: derive(self.ecdsa),
            ecop: derive(self.ecop),
            bitwise: derive(self.bitwise),
            keccak: derive(self.keccak),
            add_mod: derive(self.add_mod),
            mul_mod: derive(self.mul_mod),
            blake: derive(self.blake),
        }
    }
