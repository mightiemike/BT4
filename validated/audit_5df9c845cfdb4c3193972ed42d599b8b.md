Based on my analysis, I found a valid native analog to the reported bug class (unsafe/unescaped string concatenation causing context-boundary confusion).

### Title
Unescaped colon-delimited key construction allows UTX/outbound-ID collision across distinct inbound events - (File: `x/uexecutor/types/keys.go`)

### Summary
`GetInboundUniversalTxKey`, `GetPcUniversalTxKey`, `GetOutboundRevertId`, and `GetRescueFundsOutboundId` build their sha256 preimage by naive `fmt.Sprintf("%s:%s:%s", ...)` concatenation of `sourceChain`, `txHash`, and `logIndex` (or similar tuples), exactly the "unescaped delimiter" bug class described in the report: fields are joined with a raw separator that is never escaped or length-prefixed within the field itself. This is the same root cause as `escapeUnsafeCharacters` — a delimiter character embedded in one field can shift the apparent field boundary and make two different logical tuples serialize to an identical string (and thus identical hash/key).

### Finding Description
Compare the two key-construction strategies in the same file:
- `hashFields` (used for `GetInboundBallotKey` / `GetOutboundBallotKey`) explicitly documents and implements per-field hashing specifically *because* naive concatenation is unsafe: "Per-field hashing makes it injective — a sub-hash can't contain ':', so no field value can shift a boundary and collide with a different tuple." [1](#0-0) 
- `GetInboundUniversalTxKey`, `GetPcUniversalTxKey`, `GetOutboundRevertId`, and `GetRescueFundsOutboundId` do **not** use `hashFields` — they concatenate raw fields with `:` directly before hashing: [2](#0-1) [3](#0-2) [4](#0-3) 

`ValidateBasic()` for `Inbound` only checks that `TxHash` and `LogIndex` are non-empty after `TrimSpace` — it does **not** restrict their character set (no hex/base58-only enforcement, no rejection of `:`), and `Canonicalize()` only applies a *lenient* canonicalization that falls back to the raw trimmed string whenever the value doesn't parse as a valid chain-specific hash. [5](#0-4) [6](#0-5) [7](#0-6) 

For non-EVM/non-Solana namespaces (`CanonicalizeTxHashByNamespace`'s `default` branch), any string passes through unchanged — `txHash`/`fundRecipient`-style fields for such chains are never restricted at all. [8](#0-7) 

This means an attacker who controls (or can spoof, from an unsupported/loosely-validated chain namespace) a `TxHash` or `LogIndex` value containing a literal `:` character could craft two distinct `(sourceChain, txHash, logIndex)` tuples that serialize to the identical `"chain:txHash:logIndex"` string, e.g.:
- Tuple A: `chain="x:1", txHash="abc", logIndex="0"` → `"x:1:abc:0"`
- Tuple B: `chain="x", txHash="1:abc", logIndex="0"` → `"x:1:abc:0"`

producing the same `sha256` UTX key / outbound ID for two logically different events.

### Impact Explanation
`GetInboundUniversalTxKey` is the canonical UTX identity used to reject duplicate inbound votes (`k.HasUniversalTx(ctx, universalTxKey)` in `VoteInbound`) [9](#0-8)  and is documented as the canonical `UniversalTx.id` [10](#0-9) . `GetOutboundRevertId` / `GetRescueFundsOutboundId` are described as also serving as the **subTxId used for replay protection on the source-chain gateway call** [4](#0-3) . A collision in these IDs, if reachable with attacker-controlled field content on a namespace whose txHash isn't hex/base58-restricted, could cause an inbound from one source event to be mistaken (keyed identically) for another, or could theoretically undermine the "unique per inbound event" replay-protection guarantee that revert/rescue subTxIds rely on — this maps to the in-scope impact of "forged, replayed, mismatched, or cross-linked inbound/outbound state accepted through user-reachable flows."

### Likelihood Explanation
Likelihood is **low-to-uncertain** in practice for the currently supported namespaces: `eip155` enforces strict 32-byte-hex `CanonicalizeEVMHash` and `solana` enforces base58/hex-only validation via `canonicalizeSolanaTxHash`, both of which would reject a `:`-containing txHash and fall back only to a trimmed-but-uncanonicalized string in the *lenient* path — meaning the raw, unrestricted value is only used verbatim for chains outside these two namespaces, or when validators intentionally submit malformed data. `LogIndex` itself is attacker/observer-supplied free text with no format check beyond non-empty, which is a more directly reachable vector for boundary-shifting since it's less likely to be format-checked downstream. I could not fully verify from the available code index whether any additional chain-type-specific validation exists in `universalClient/chains/*` that would prevent a UV or event source from ever emitting a colon-containing `TxHash`/`LogIndex` before it reaches `VoteInbound`; this repo index does not show a global allowlist of characters for those fields at the message level.

### Recommendation
Apply the same injective `hashFields` per-field-hashing approach already used for `GetInboundBallotKey`/`GetOutboundBallotKey` to `GetInboundUniversalTxKey`, `GetPcUniversalTxKey`, `GetOutboundRevertId`, and `GetRescueFundsOutboundId`, instead of raw `fmt.Sprintf` colon-concatenation, so that no field's contents can shift the delimiter boundary regardless of source-chain namespace or validation gaps.

### Proof of Concept
Given the code in `x/uexecutor/types/keys.go`:
```go
func GetInboundUniversalTxKey(inbound Inbound) string {
	chain := strings.TrimSpace(inbound.SourceChain)
	txHash := utils.LenientCanonicalizeTxHash(chain, inbound.TxHash)
	logIndex := strings.TrimSpace(inbound.LogIndex)
	data := fmt.Sprintf("%s:%s:%s", chain, txHash, logIndex)
	hash := sha256.Sum256([]byte(data))
	return hex.EncodeToString(hash[:])
}
```
For a namespace outside `eip155`/`solana` (default passthrough in `CanonicalizeTxHashByNamespace`), submitting:
- Inbound₁: `SourceChain="custom:1", TxHash="X", LogIndex="0"` → preimage `"custom:1:X:0"`
- Inbound₂: `SourceChain="custom", TxHash="1:X", LogIndex="0"` → preimage `"custom:1:X:0"`

both produce the identical `sha256` digest and thus the identical `UniversalTx` ID / `PendingInboundEntry` key, despite representing two distinct source-chain events — this could not be reproduced against a running node within this analysis; it is derived from static code review of the key-construction and validation logic cited above.

```go
// hashFields = sha256( hex(sha256(domain)) : hex(sha256(f0)) : ... ). Per-field
// hashing makes it injective — a sub-hash can't contain ':', so no field value
// can shift a boundary and collide with a different tuple.
func hashFields(domain collections.Prefix, parts ...string) string {
	hashed := make([]string, 0, len(parts)+1)
	d := sha256.Sum256(domain.Bytes())
	hashed = append(hashed, hex.EncodeToString(d[:]))
	for _, p := range parts {
		sum := sha256.Sum256([]byte(p))
		hashed = append(hashed, hex.EncodeToString(sum[:]))
	}
	final := sha256.Sum256([]byte(strings.Join(hashed, ":")))
	return hex.EncodeToString(final[:])
}
```

```go
// CanonicalizeTxHashByNamespace canonicalizes a transaction hash/signature
// for the given CAIP-2 chain. Empty input passes through (e.g. failed
// outbound observations carry no hash).
func CanonicalizeTxHashByNamespace(chain, txHash string) (string, error) {
	txHash = strings.TrimSpace(txHash)
	if txHash == "" {
		return "", nil
	}
	switch CAIP2Namespace(chain) {
	case namespaceEVM:
		return CanonicalizeEVMHash(txHash)
	case namespaceSolana:
		return canonicalizeSolanaTxHash(txHash)
	default:
		return txHash, nil
	}
}
```

```go
// LenientCanonicalizeTxHash canonicalizes txHash for chain, falling back to
```
