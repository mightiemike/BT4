### Title
Bootstrap-declare bypass lets any unprivileged sender declare a class without `__validate_declare__` or fee payment - ([File: crates/starknet_api/src/executable_transaction.rs])

### Summary
`DeclareTransaction::is_bootstrap_declare` grants a completely unauthenticated, fee-free, validate-free declare path whenever a V3 declare transaction has `sender_address == bootstrap_address()`, `nonce == 0`, and the *execution-flag* `charge_fee == false`. The bootstrap address is a hard-coded, publicly known constant (`ContractAddress::from(0x424f4f545354524150)`, the ASCII encoding of `"BOOTSTRAP"`), and `charge_fee` is derived purely from the transaction's own resource bounds via `enforce_fee()` (zero bounds ⇒ `enforce_fee() == false`). This mirrors the reported `AccessTokenContract` bug class: two logically-parallel code paths (normal `Declare` vs. "bootstrap" `Declare`) that should be equally privileged but are gated only by attacker-controllable, publicly-known values (sender address constant + zero resource bounds), letting an unprivileged caller pick the more favorable path.

### Finding Description
`is_bootstrap_declare` is defined as: [1](#0-0) 

The condition it checks is: `sender_address == bootstrap_address() && nonce == Nonce(Felt::ZERO) && !charge_fee`. `bootstrap_address()` is a fixed, compile-time constant — not a privileged/verified system account, not gated by any signature check, and not restricted to a genesis/bootstrap phase at the state-transition level.

This flag is consumed in `AccountTransaction::execute_raw`: [2](#0-1) 

When `tx.is_bootstrap_declare(self.execution_flags.charge_fee)` is true, the transaction **completely skips** `perform_pre_validation_stage` (fee-bound checks, balance checks) and skips execution of the `__validate_declare__` entry point — it goes straight to declaring the class via `run_execute`, and returns a default (empty) `TransactionExecutionInfo` (no validate call info, no fee transfer, no nonce increment).

The `charge_fee` execution flag that gates this is not a protocol-enforced constant — it is computed from `enforce_fee()`, which itself depends on the transaction's own resource bounds: [3](#0-2) [4](#0-3) 

So a transaction sender who sets `sender_address = bootstrap_address()`, `nonce = 0`, and zero resource bounds (all `max_amount`/`max_price_per_unit` = 0, which is how `enforce_fee()` returns `false`) causes `charge_fee` to evaluate to `false` through the normal, generic fee-enforcement mechanism — with no special-case gate preventing an arbitrary caller from using the constant bootstrap sender address. Since the "BOOTSTRAP" address has (by design) never been deployed, its on-chain nonce defaults to `0`, so the ordinary nonce check in `handle_nonce` (called from `perform_pre_validation_stage`, itself skipped in the bootstrap branch) is trivially satisfiable, and no signature or `__validate_declare__` invocation is required at all in the bootstrap branch — there is no account contract behind that address to validate anything.

This is structurally identical to the reported bug: `paidMint` (normal path, real privilege check + fee) vs. `referralMint` (alternate path with a different, weaker/attacker-chosen privilege level, gated only by public, attacker-suppliable data). Here, "normal Declare" (fee + validate) vs. "bootstrap Declare" (no fee + no validate) are gated only by a hardcoded public constant address and self-reported zero resource bounds, both of which the transaction sender fully controls.

### Impact Explanation
If reachable in production (i.e., if nothing upstream of the blockifier — gateway/mempool — permanently blocks transactions whose `sender_address == bootstrap_address()` outside of a genesis/bootstrap phase), an unprivileged sender could declare arbitrary classes without paying any fee and without passing any account validation, at any point after genesis. This is an unauthorized-account-action / fee-bypass vulnerability with direct on-chain state effects (class declarations written to `contract_class_changes`) obtained without proving control of any real account. It also produces an execution result inconsistent with what the honest protocol expects for a normal `Declare` transaction (no validate call, no fee transfer, no nonce increment), which is a form of state/behavior divergence from the intended fee/validation invariants enforced for every other account transaction.

### Likelihood Explanation
The `is_bootstrap_declare` check itself is purely a function of transaction fields the sender fully controls (`sender_address`, `nonce`, `resource_bounds` via `charge_fee`/`enforce_fee`). The comment at the call site notes this "flow is used for the sequencer to bootstrap a new system," implying it is intended to be exercised only during genesis, but the guard enforcing that restriction, if any, must live outside the code cited here (e.g., gateway/mempool acceptance policy, or a block-number/genesis check) — no such restriction is visible in `is_bootstrap_declare` or in `execute_raw`. Given the uncertainty about whether an out-of-band restriction exists elsewhere in the gateway/mempool that prevents non-genesis bootstrap-declare transactions from being admitted, I could not fully confirm end-to-end reachability from the RPC/gateway ingress path within the available context — this would need to be verified against the gateway's stateless/stateful validators and the mempool's admission logic to see if they special-case or explicitly reject `sender_address == bootstrap_address()` post-genesis.

### Recommendation
Restrict the bootstrap-declare bypass so it cannot be exercised by an arbitrary transaction sender after genesis:
- Gate the bypass on an explicit, sequencer-controlled/protocol state flag (e.g., "genesis not yet complete" / block number == 0) rather than solely on transaction-supplied fields (`sender_address`, `nonce`, self-reported zero resource bounds).
- Reject any `Declare` transaction with `sender_address == bootstrap_address()` at the gateway/mempool level once the chain is past genesis, rather than relying on nonce/fee heuristics that a normal caller can satisfy.
- Ensure `charge_fee` cannot be forced to `false` by the sender alone for security-relevant special-cased branches; decouple the "is this a bootstrap tx" decision from `enforce_fee()`, which is meant purely for fee-charging semantics, not for authorization decisions.

### Proof of Concept
1. Craft a `DeclareTransaction::V3` with `sender_address = DeclareTransaction::bootstrap_address()` (`0x424f4f545354524150`), `nonce = Nonce(Felt::ZERO)`, and `resource_bounds` set to all-zero (`AllResourceBounds::default()`/`create_for_testing_no_fee_enforcement()`), yielding `enforce_fee() == false` and hence `charge_fee == false` (see test at [5](#0-4)  which the codebase's own `test_bootstrap_declare` exercises with exactly this construction).
2. Submit this transaction as any unprivileged party (no signature required, since `bootstrap_address()` corresponds to no deployed account contract).
3. Observe (per `execute_raw`, lines 899-912 of `account_transaction.rs`) that `is_bootstrap_declare` returns `true`, `perform_pre_validation_stage` and `__validate_declare__` are entirely skipped, and the class is declared for free: `state.set_compiled_class_hash` succeeds with `assert_eq!(res, TransactionExecutionInfo::default())` and only the class-declaration/compiled-class-hash change occurs in the state diff — exactly as validated by the existing unit test `test_bootstrap_declare` in `account_transactions_test.rs:945-991`, which the codebase's own test suite confirms produces a successful declare with zero fees, zero validation, and no nonce bump.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }

        // Do not run validate or perform any account-related actions for declare transactions that
        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {
            if tx.is_bootstrap_declare(self.execution_flags.charge_fee) {
                let mut context = EntryPointExecutionContext::new_invoke(
                    tx_context.clone(),
                    self.execution_flags.charge_fee,
                    SierraGasRevertTracker::new(GasAmount::default()),
                );
                let mut remaining_gas = 0;
                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());
            }
        }
