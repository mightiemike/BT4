### Title
Replay-verify tooling accepts mismatched state/position checkpoint (Merkle) roots as valid - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole comparator used by both replay-verify code paths to authenticate locally re-executed transaction outputs against a trusted, signature-backed `TransactionInfo` sequence pulled from backup storage. It never compares `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, so a state root divergence between local re-execution and the authenticated chain is silently accepted as a "successful replay."

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  asserts equality of transaction status, gas used, write-set hash, and event-root hash, then returns `Ok(())` without ever inspecting the checkpoint-hash fields carried by `TransactionInfo`. The gap is acknowledged directly in the source: [2](#0-1) .

This function is used as the pass/fail oracle for two distinct verification tools:
- `execution/executor/src/chunk_executor/mod.rs::verify_execution`, invoked from `remove_and_replay_epoch` whenever `verify_execution_mode.should_verify()` is set [3](#0-2) . This is the code path used by `storage/db-tool/src/replay_verify.rs`, the `aptos db-tool replay-verify` subcommand that downloads an epoch history/backup and re-executes it to authenticate the archive.
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, which performs the equivalent check against `expected_txn_info` pulled straight from a backup handler [4](#0-3) .

Both call sites pass `expected_txn_info`/`txn_info` objects whose `state_checkpoint_hash` (root of the world-state Sparse/Jellyfish Merkle Tree at that version), `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` fields are simply never checked against the locally recomputed state. `TransactionInfoV0`/`V1` carry these fields specifically to authenticate the state root [5](#0-4) , and elsewhere in the codebase (e.g. `execute_and_commit`/`assert_committed_write_set_version` test helper) only `state_change_hash` (write-set hash) is checked as well, reinforcing that the state-checkpoint root is generally not independently authenticated by these tools.

### Impact Explanation
The state-checkpoint hash is the authenticated binding between a `TransactionInfo` (covered by validator signatures via the accumulator/`LedgerInfo`) and the actual Sparse/Jellyfish Merkle root of the world state at that version — this is exactly the "wrong accumulator root / state proof accepted as valid" class of issue the state-integrity gate calls out. Because `ensure_match_transaction_info` omits this comparison, both `replay-verify` and `replay-on-archive` — the tools operators and auditors use to confirm that a downloaded backup/archive reproduces the exact authenticated ledger state — can report success even when the locally computed state root, hot-state root, or (once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/trading-native position state is enabled) the position-state root diverges from the version actually committed and signed by validators. A backup/archive whose write-set/event data hash correctly but whose actual persisted state values differ (e.g. due to a corrupted state-merklization bug, a backup provider bit-flip, or a divergent commit path) would pass verification undetected, defeating the entire purpose of replay-verify as an integrity check on ledger data and durable storage. This is a high-severity gap in a proof/state-integrity verification tool, though it does not itself corrupt consensus-committed state — it silently disables detection of such corruption.

### Likelihood Explanation
This is not a hypothetical: the gap is deterministic and unconditional — every call to `ensure_match_transaction_info` in both replay tools skips the check, currently gated behind a TODO rather than an actual validation. Any legitimate operator running `db-tool replay-verify` or `replay-on-archive` against a backup with corrupted or divergent state data (independent of write-set/event content) will get a false "verified" result. No adversarial timing or privileged access is required — this triggers on ordinary use of the shipped tooling.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (when enabled) `position_state_checkpoint_hash` against the recomputed roots produced by `DoStateCheckpoint`, and thread those computed hashes into both `chunk_executor::verify_execution` and `replay_on_archive::execute_and_verify` before allowing `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state features to ship, exactly as the existing TODO comment already recommends.

### Proof of Concept
1. Take any historical backup/archive with authenticated `TransactionInfo`s (correct `transaction_hash`, `event_root_hash`, `state_change_hash`, and correct signed `LedgerInfo`), but modify the persisted state values referenced by the write-set to a functionally different but hash-colliding-irrelevant path — or, more directly, simulate a state-merklization bug in local execution that computes wrong `state_checkpoint_hash` while `write_set`/`events` output remains identical.
2. Run `aptos db-tool replay-verify` against this backup or run `replay-on-archive`.
3. Observe that `ensure_match_transaction_info` returns `Ok(())` because it never reads `txn_info.state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` — see [6](#0-5)  for the full set of fields actually compared, none of which include the checkpoint hashes present on `TransactionInfoV0`/`V1` [5](#0-4) .
4. The tool reports success despite the state root being wrong, confirming the detection gap.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
