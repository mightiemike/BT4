### Title
NEP-366/NEP-611 meta-transaction (`SignedDelegateAction`) signature digest lacks chain/network domain separation - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
`SignedDelegateAction` and `VersionedSignedDelegateAction` (NEP-366/NEP-611 meta-transactions) are authorized by signing a hash built from `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`, prefixed only by a NEP-number `MessageDiscriminant`. Nothing in the signed payload ties the signature to a specific network/chain (no `chain_id`, `genesis_hash`, or similar). Any nearcore-derived chain that shares account state with another chain (e.g. via nearcore's own `fork-network` tool, or any project that boots a new network from a copy of another network's genesis/state export) can have a validly-signed `SignedDelegateAction` from chain A replayed on chain B, exactly as in the reported Uniswap/PancakeSwap KEM-hook digest issue: sender/receiver/action fields match, but no domain separator prevents cross-instance reuse.

### Finding Description
`DelegateAction::get_nep461_hash` and `VersionedDelegateActionPayload::get_nep461_hash` compute the signed hash as: [1](#0-0) [2](#0-1) 

which is fed into `SignableMessage`, whose only tag is a NEP-number discriminant, not any chain identifier: [3](#0-2) [4](#0-3) 

Verification (`SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify`) only re-derives this same chain-agnostic hash and checks the ed25519/secp256k1 signature against it: [5](#0-4) [6](#0-5) 

The only real replay protections are the access-key nonce and `max_block_height`, both enforced in `validate_delegate_action_key`: [7](#0-6) 

Both checks are **local to the executing chain's own state** — nonce is compared to whatever nonce is currently stored for that `(sender_id, public_key)` on that chain, and `max_block_height` is compared to that chain's own block height counter. Neither of these encodes which network the signer intended the delegate action for. This is structurally identical to the reported bug: the signed tuple binds direction/amount/counterparty (there: pool key, direction, price; here: sender, receiver, actions, nonce, height) but omits any binding to chain identity (there: chain ID/deployment salt; here: `chain_id`/`genesis_hash`).

Unlike ordinary `SignedTransaction`s, which include a recent `block_hash` from the signer's own chain (making a valid signed transaction chain-specific in practice because block hashes are chain-unique), the meta-transaction's `DelegateAction`/`DelegateActionV2` carries only a plain `BlockHeight` integer, not a hash — this is not chain-specific data at all, so it does not provide domain separation by itself. Confirmed the wallet-contract's RLP-execute path *does* explicitly check `tx.chain_id != Some(CHAIN_ID)` and bans a relayer on mismatch [8](#0-7)  — showing nearcore engineers are aware domain separation on chain id is needed for signed cross-chain-replayable messages elsewhere in the codebase, but the equivalent protection was never added to the core NEP-366/611 `SignableMessage`/`DelegateAction` scheme.

### Impact Explanation
If any two nearcore-based networks (mainnet/testnet, or — more concretely — a network produced by nearcore's own `tools/fork-network` state-forking utility, or any custom chain bootstrapped from an export of another chain's genesis/state) share the same account_id → public_key → nonce state at the time of fork/genesis, a `SignedDelegateAction` signed by a user for use on chain A remains valid and executable on chain B as long as the nonce on chain B has not advanced past the signed nonce and the block height is still below `max_block_height`. Because delegate actions can carry arbitrary inner actions (transfers, function calls, key management, etc.) up to the sender's access-key permissions, this allows unauthorized value movement / unintended state transitions on the "wrong" network using a signature the user only intended for one specific chain — a concrete cross-chain replay of an authorization, matching the "unauthorized value movement" acceptance criterion.

### Likelihood Explanation
Exploitation requires a scenario where two live nearcore-derived networks share overlapping account/key/nonce state, which is not the default mainnet/testnet relationship (they have independently bootstrapped genesis and diverging nonce histories) but is a realistic and directly supported nearcore feature via `tools/fork-network`, which is designed to fork network state for creating new environments while preserving accounts, access keys, and their nonces. Any deployment that treats a forked network as a live, user-facing chain (e.g., testing/staging chains that still accept relayed meta-transactions from users, or enterprise/appchain forks) is exposed. This is Medium likelihood: it needs a specific but supported operational pattern (state-sharing fork) rather than being universally exploitable across arbitrary unrelated nearcore chains.

### Recommendation
Add a chain-specific domain separator to the NEP-366/NEP-611 signed payload — e.g. fold the genesis hash or a chain-specific identifier into `SignableMessage`/`DelegateAction`/`DelegateActionV2` (analogous to `chain_id` in the wallet-contract's RLP path) — so that `get_nep461_hash` commits to the network the action is intended for, and `verify()` rejects delegate actions signed for a different chain. This should be considered for the next revision of NEP-461/NEP-366 message tagging.

### Proof of Concept
1. Stand up chain A (e.g. mainnet) and let account `alice.near` create/use access key `K` with nonce `N`.
2. Use `tools/fork-network` (or any equivalent state-copy bootstrap) to create chain B from chain A's state at a point where `alice.near`'s access key `K` still has nonce `≤ N`.
3. On chain A, Alice signs a `SignedDelegateAction` (via `SignedDelegateAction::sign`/`DelegateAction::get_nep461_hash`) authorizing some sensitive action (e.g. transfer, function call) with `nonce = N+1` and a generous `max_block_height`, intended for use only on chain A through a specific relayer.
4. A malicious relayer (or the intended relayer acting maliciously) submits the identical `SignedDelegateAction` bytes as the `Action::Delegate`/`Action::DelegateV2` payload of a transaction on chain B instead.
5. `validate_delegate_action_key` on chain B finds `alice.near`'s access key `K` with nonce `≤ N`, `delegate_nonce.nonce() > current_nonce` passes, `max_block_height` bound passes, and `SignedDelegateAction::verify()` succeeds because the hash never encoded which chain it was for — the action executes on chain B against Alice's will.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
