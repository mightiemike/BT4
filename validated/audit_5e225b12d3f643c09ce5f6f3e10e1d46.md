## Title
Underpriced Signature Verification in `BatchValidateSign`/`ValidateMultiSign` Precompiles: Energy Charged Is Decoupled From Actual Work Performed - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The external report's core theme is that a fixed/mis-estimated fee formula fails to track the actual, attacker-influenced cost of work performed by a callback, allowing users to pay less than the true computational cost and causing unpredictable/underpriced execution. The closest concrete analog in java-tron is the energy pricing of the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts, where `getEnergyForData()` derives the signature count purely from the raw calldata byte length using a fixed ABI-shape assumption, while `execute()`/`doExecute()` derives the *actual* number of signatures to recover from a completely independent, attacker-controlled ABI offset/length field embedded inside that same calldata.

### Finding Description
`ValidateMultiSign.getEnergyForData()` computes the number of signatures purely as a function of total calldata length: [1](#0-0) 

`BatchValidateSign.getEnergyForData()` does the same: [2](#0-1) 

However, the actual number of signatures processed by `execute()`/`doExecute()` is read from a dynamic ABI offset word (`words[3]` for `ValidateMultiSign`, `words[1]`/`words[2]` for `BatchValidateSign`) that points to an arbitrary location inside the calldata and whose "array length" field is itself attacker-controlled: [3](#0-2) [4](#0-3) 

`extractBytesArray`/`extractSigArray` walk this attacker-supplied offset/length structure, and because ABI-style offsets can overlap or be reused, a crafted (small) calldata blob can encode an offset table that repeatedly points back into the same short region, producing up to `MAX_SIZE` (5 for `ValidateMultiSign`, 16 for `BatchValidateSign`) *distinct* signature-recovery iterations while the raw `data.length`-based formula in `getEnergyForData()` charges for far fewer (or zero) "words": [5](#0-4) 

Each iteration of the signature loop performs a full ECDSA `recoverAddrBySign` (equivalent in cost to `ECRecover`, which itself is separately priced at 3000 energy): [6](#0-5) [7](#0-6) 

This mirrors the report's Finding #2 (inaccurate gas-cost estimation because the fee model does not track the actual cost of attacker-supplied input/callback complexity): the energy pricing function and the actual execution cost are computed from two independent, unlinked interpretations of the same untrusted byte string.

Some mitigation exists: `isValidAbiEncoding()` (only enforced when `VMConfig.allowTvmOsaka()` is active, i.e. TIP-854) rejects calldata whose overall length is not the fixed `header + N*item` shape: [8](#0-7) 
This check constrains the *outer* shape of the calldata (word alignment and header/item multiple), but it does not constrain the *inner* dynamic offset/length fields that `extractBytesArray`/`extractSigArray` use to determine how many signature-recovery operations actually run, nor does it re-derive `getEnergyForData()`'s count from those same fields. The two code paths remain independent.

### Impact Explanation
If the discrepancy between the `getEnergyForData()`-derived count and the loop-driven actual recovery count can be made asymmetric (fewer energy-formula "words" than actual `signatures.length` iterations), a caller can obtain more ECDSA recover cycles than the energy charged accounts for. This is the java-tron analog of "underpriced public work": network validators/full nodes perform CPU-bound cryptographic verification work (batched, up to `MAX_SIZE` parallel ECDSA recoveries per call in `BatchValidateSign`) that is not proportionally metered by the energy fee actually deducted from the caller's account, creating a resource-exhaustion/DoS surface if repeated across many transactions, and a fee-model integrity issue (accounting) since the deducted energy does not reflect consumed node resources.

### Likelihood Explanation
Exploitability depends on whether ABI offset/length words can be crafted to make `words.length`-total-byte-count small while the referenced array-length fields (dictated by `words[offset]` in `extractBytesArray`) report up to `MAX_SIZE` items with overlapping/short encodings — this requires careful crafting but no privileged role; it is reachable by any unprivileged account issuing a `TriggerSmartContract` transaction that calls the `ValidateMultiSign`/`BatchValidateSign` precompile addresses (guarded only by `VMConfig.allowTvmSolidity059()`, a chain-parameter feature flag, not an access-control check). I was not able to fully verify, within tool constraints, an exact byte-level payload that maximizes iteration count while minimizing `data.length`-derived energy cost (this needs deeper analysis of `DataWord.parseArray`/`intValueSafe` bounds handling and how the fixed `MAX_SIZE` cap interacts with the divergence) — this uncertainty should be resolved with a fuller live/constructed PoC before treating this as immediately exploitable at scale.

### Recommendation
- Derive the energy charge for `ValidateMultiSign`/`BatchValidateSign` from the same dynamic array-length fields used in `execute()`/`doExecute()` (i.e., `signatures.length`/`addresses.length` after `extractSigArray`/`extractBytesArray`), rather than from a purely length-based formula, so pricing and execution are computed from the same trusted source of truth.
- Extend `isValidAbiEncoding()` (or add a new validation step) to also verify that the referenced dynamic array offsets/lengths lie within bounds and do not permit overlapping/aliased reads that inflate iteration count relative to `data.length`.
- Apply the same fix regardless of `allowTvmOsaka()`/`allowTvmSelfdestructRestriction()` activation state, since the underlying `getEnergyForData()` formula is unconditional.

### Proof of Concept
Not independently constructed/validated due to tool-access constraints (this task provides only read-only code-search access to the repository, not the ability to compile/run java-tron or craft and submit a live `TriggerSmartContract` transaction against `ValidateMultiSign`/`BatchValidateSign`). A concrete PoC would require: (1) building calldata for `batchvalidatesign(bytes32,bytes[],address[])` where the outer word count is minimized (to minimize `(data.length/32 - 5)/6` in `getEnergyForData`) while the `words[1]`/`words[2]` offsets and their pointed-to length words are crafted so that `extractSigArray`/`extractBytesArray` yield `signatures.length` close to `MAX_SIZE=16`; (2) submitting this via `TriggerSmartContract` on a node with `allowTvmSolidity059` (and optionally `allowTvmSelfdestructRestriction`) enabled and comparing energy billed (`getEnergyForData` output) against actual ECDSA recover operations executed in `doExecute`. I recommend a background Devin session with compiler/test access to construct and validate this payload against `BatchValidateSignContractTest`/`ValidateMultiSignContractTest` harnesses already present in the repo.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
