### Title
Deposit Refund Misattribution in `apply_delegate_action` Allows Sender to Drain Relayer's Attached Deposit on Failure — (File: `runtime/runtime/src/actions.rs`)

### Summary

When a relayer submits a meta transaction (`DelegateAction`), the relayer's balance is debited for any deposit attached to the inner actions. However, when the inner receipt fails, the deposit refund is sent to the **sender** (`delegate_action.sender_id`, i.e., Alice), not to the relayer who actually paid it. An unprivileged sender can deliberately craft a `DelegateAction` with a large deposit that is guaranteed to fail on the receiver's shard, causing the relayer to permanently lose the deposit to the sender.

---

### Finding Description

**Step 1 — Relayer pays the deposit at transaction conversion.**

In `runtime/runtime/src/config.rs`, `total_deposit` recurses into `DelegateAction` inner actions and charges the full deposit to the relayer's account:

```rust
// Note, here Relayer pays the deposit but if actions fail, the deposit is
// refunded to Sender of DelegateAction
let actions = delegate_action.get_actions();
action_balance = total_deposit(&actions)?;
``` [1](#0-0) 

**Step 2 — Inner receipt's `predecessor_id` is set to the sender (Alice), not the relayer.**

In `apply_delegate_action`, the new receipt spawned from the `DelegateAction` has `predecessor_id = sender_id` (Alice):

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // ← Alice, not the relayer
    receiver_id: delegate_action.receiver_id().clone(),
    ...
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(), // ← relayer
        ...
    }),
});
``` [2](#0-1) 

**Step 3 — On failure, deposit refund is sent to `balance_refund_receiver()` = `predecessor_id` = Alice.**

In `refund_unspent_gas_and_deposits`:

```rust
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(),
        deposit_refund,
    ));
}
``` [3](#0-2) 

`balance_refund_receiver()` returns `refund_to` if set, otherwise `predecessor_id`:

```rust
pub fn balance_refund_receiver(&self) -> &AccountId {
    self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
}
``` [4](#0-3) 

For the inner receipt created by `apply_delegate_action`, `refund_to` is `None` (it uses `ReceiptEnum::Action`, not `ActionV2`) and `predecessor_id` is Alice. So the full deposit goes to Alice. [5](#0-4) 

**Step 4 — Gas refund correctly goes to the relayer (signer), but deposit refund does not.**

```rust
result.new_receipts.push(Receipt::new_gas_refund(
    &action_receipt.signer_id(),   // ← relayer (correct)
    gas_balance_refund,
    action_receipt.signer_public_key().clone(),
));
``` [6](#0-5) 

Gas refunds go to `signer_id` (relayer) — correct. Deposit refunds go to `predecessor_id` of the inner receipt (Alice) — incorrect from the relayer's perspective.

The nearcore documentation explicitly acknowledges this asymmetry:

> "If an inner action requires an attached balance (for example a transfer action) then this balance is taken from the relayer. … But what if the transaction fails execution on Bob's shard? At this point, the predecessor is Alice and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a **financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard**." [7](#0-6) 

---

### Impact Explanation

The relayer loses the full attached deposit to Alice. Alice can craft a `DelegateAction` with an arbitrarily large deposit (e.g., 1000 NEAR) targeting a call that is guaranteed to fail (non-existent method, insufficient storage, etc.). The relayer, after verifying the action content off-chain, submits it and pays the deposit. The inner receipt fails on the receiver's shard, and the entire deposit is refunded to Alice. The relayer's balance is permanently reduced by the deposit amount.

This is a direct analog to the NonUSTStrategy bug: the party paying the cost (relayer / depositor) does not receive the benefit or refund — instead it flows to a third party (Alice / LP holders) who can deliberately engineer the situation.

---

### Likelihood Explanation

Any account that can sign a `DelegateAction` (i.e., any NEAR account with a valid key) can exploit this against any relayer that processes meta transactions with non-zero deposits. The attack requires no special privileges. The only external requirement is finding a relayer willing to submit the crafted action, which is the normal operating model for meta transactions. Likelihood is **medium**: it requires a relayer to be in use, but the financial incentive is clear and the attack is trivially constructable.

---

### Recommendation

The inner receipt created in `apply_delegate_action` should use `ReceiptEnum::ActionV2` with `refund_to` set to the relayer's account ID (`action_receipt.signer_id()`), so that deposit refunds on failure are returned to the party who paid them:

```rust
let new_action_receipt = ActionReceiptV2 {
    signer_id: action_receipt.signer_id().clone(),
    signer_public_key: action_receipt.signer_public_key().clone(),
    refund_to: Some(action_receipt.signer_id().clone()), // ← relayer gets deposit refund
    gas_price: action_receipt.gas_price(),
    ...
};
```

This mirrors the existing `promise_set_refund_to` host function mechanism already present in the runtime. [8](#0-7) 

---

### Proof of Concept

1. Alice creates a `DelegateAction` targeting `receiver = contract.near`, with inner action `FunctionCall { method_name: "nonexistent", deposit: 1000 NEAR, gas: 30 TGas }`.
2. Alice signs the `DelegateAction` with her key and sends it off-chain to a relayer.
3. The relayer verifies the action content, wraps it in a transaction (`signer = relayer`), and submits it. At transaction conversion, `total_deposit` charges 1000 NEAR from the relayer's account.
4. The outer receipt executes on Alice's shard: `apply_delegate_action` creates an inner receipt with `predecessor_id = alice.near`, `signer_id = relayer.near`.
5. The inner receipt executes on `contract.near`'s shard: the function call fails (`MethodNotFound`).
6. `refund_unspent_gas_and_deposits` issues a deposit refund to `balance_refund_receiver()` = `predecessor_id` = `alice.near`.
7. Alice receives 1000 NEAR. The relayer has lost 1000 NEAR.

## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
