### Title
Ignored `storeSession` success flag causes silent session-persistence failures treated as successful authentication - (File: `packages/apps/shopify-app-express/src/auth/auth-callback.ts`, `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts`, `packages/apps/shopify-app-react-router/src/server/authenticate/admin/strategies/token-exchange.ts`)

### Summary
The `SessionStorage.storeSession()` contract explicitly returns `Promise<boolean>` to signal whether the session was actually persisted, but every OAuth callback and token-exchange code path in `shopify-app-express`, `shopify-app-remix`, and `shopify-app-react-router` calls this method and discards the boolean result, then unconditionally proceeds as if the session was durably stored.

### Finding Description
The `SessionStorage` interface is documented as returning `true`/`false` to indicate storage success or failure: [1](#0-0)  and the implementation guide confirms this contract: [2](#0-1) .

Despite this, none of the authentication entrypoints check the returned boolean:

- In the classic OAuth callback flow, `storeSession` is awaited and ignored, then the code immediately registers webhooks, redirects to online OAuth, sets `res.locals.shopify.session`, and fires the `afterAuth` hook as if persistence succeeded: [3](#0-2) .
- In the Express token-exchange middleware, both the offline and online `storeSession` calls are unchecked before the request is marked authenticated and `next()` is invoked: [4](#0-3) .
- The same unchecked pattern exists in the Remix token-exchange strategy: [5](#0-4) .
- And in the React Router equivalent: [6](#0-5) .

This mirrors the report's core issue: a call whose return value communicates success/failure is invoked but its result is never inspected, so the caller can silently treat a failed operation as if it succeeded.

### Impact Explanation
If `storeSession` returns `false` (e.g. due to a transient DB/connection error, a validation failure in a custom `SessionStorage` implementation, or a write conflict such as those explicitly handled in `PrismaSessionStorage`: [7](#0-6) ), the current request still proceeds as authenticated: the response marks the session as valid, webhooks may be registered, and the `afterAuth` hook fires — all based on an access token that was never durably persisted. Subsequent requests for that shop will fail to load the session, forcing repeated OAuth/token-exchange cycles (an availability degradation for the merchant) and potentially inconsistent app state (e.g., webhooks registered without a way to look up the session that owns them).

### Likelihood Explanation
This code path executes on every OAuth callback and every token-exchange request — both reachable by a merchant completing normal app installation/embedding flows, so the ignored-boolean condition is exercised on every request, but the failure trigger (an actual storage failure) depends on the underlying storage backend's transient error conditions, making the failure likelihood dependent on the storage backend rather than trivially attacker-controlled.

### Recommendation
Check the boolean returned by `storeSession` at each call site and treat a `false` result as a persistence failure: log/alert and return an error response (e.g. 500) instead of proceeding to mark the request as authenticated, fire `afterAuth`, or register webhooks.

### Proof of Concept
Not applicable as a forged-request PoC; this is a control-flow defect verifiable by code inspection — mock any `SessionStorage.storeSession` implementation to return `false` and observe that `auth-callback.ts`, `perform-token-exchange.ts`, and both `token-exchange.ts` strategies still complete the request as a successful authentication.

  public async storeSession(session: Session): Promise<boolean> {
    await this.ensureReady();
    const data = this.sessionToRow(session);

    try {
      await this.getSessionTable().upsert({
        where: {id: session.id},
        update: data,
        create: data,
      });
    } catch (error) {
      if (
        error instanceof Prisma.PrismaClientKnownRequestError &&
        error.code === UNIQUE_KEY_CONSTRAINT_ERROR_CODE
      ) {
        console.log(
          'Caught PrismaClientKnownRequestError P2002 - Unique Key Key Constraint, retrying upsert.',
        );
        await this.getSessionTable().upsert({
          where: {id: session.id},
          update: data,
          create: data,
        });
        return true;
      }
      throw error;
    }

    return true;
  }
