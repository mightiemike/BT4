### Title
`ValidateMultiSign` precompile lets malformed calldata throw a `RuntimeException` out of `callToPrecompiledAddress`, aborting the entire outer call/transaction instead of failing gracefully like a normal `CALL` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Sherlock report describes a case where a contract's low-level `try/catch` around an external call cannot swallow the failure because the callee reverts in a way that is not "catchable" at the call site, forcing the whole transaction to revert instead of letting the caller continue gracefully. The analogous java-tron path is the TVM's own "call to precompiled contract" mechanism: `Program.callToPrecompiledAddress` is supposed to behave like a normal EVM `CALL` — on failure it should push `0` on the stack and let the calling contract's bytecode decide what to do next (its own try/catch equivalent). Before the TIP-854 hardening (`VMConfig.allowTvmOsaka()`), `ValidateMultiSign.execute` decodes raw calldata with `DataWord.parseArray(rawData)` with no bounds/format validation, so malformed calldata throws inside the decoder rather than returning `Pair.of(false, ...)`.

### Finding Description
`Program.callToPrecompiledAddress` calls the precompile and expects a `Pair<Boolean, byte[]>` result to decide the CALL outcome: [1](#0-0) 

If `contract.execute(data)` throws instead of returning `Pair.of(false, ...)`, the exception propagates out of `callToPrecompiledAddress` entirely, bypassing the intended "push 0 and continue" semantics, and is only caught much higher up (`VM.play`'s outer `catch (RuntimeException e)`), which halts VM execution and reverts the whole transaction: [2](#0-1) 

`ValidateMultiSign.execute` (address `0x66`, used for TVM multi-sig permission validation) parses calldata unconditionally via `DataWord.parseArray(rawData)` and indexes `words[0]`..`words[3]` before any length/shape validation, only gating on `VMConfig.allowTvmOsaka()`: [3](#0-2) 

This is confirmed by the project's own regression test, which documents that pre-activation, malformed calldata is expected to throw a `RuntimeException` out of `execute` rather than being handled gracefully — exactly the "no outer catch" failure mode being fixed by TIP-854: [4](#0-3) 

And the fix is explicitly scoped to `VMConfig.allowTvmOsaka()` activation, with a companion test (`testTip854OuterFrameContainment`) asserting that only after the TIP-854/Osaka feature gate is enabled does a malformed `CALL` to `ValidateMultiSign`/`BatchValidateSign` correctly push `0` and leave the outer frame free of a propagated exception: [5](#0-4) 

The parallel `BatchValidateSign` precompile was hardened differently: it wraps its whole body in `try { return doExecute(data); } catch (Throwable t) { ... return Pair.of(true, new byte[WORD_SIZE]); }`, unconditionally catching any decode-time exception regardless of the Osaka flag: [6](#0-5) 

`ValidateMultiSign`, however, only wraps the post-decode business logic (signature-weight computation) in a `try/catch`, not the initial `DataWord.parseArray`/`words[...]` decoding that happens before it: [7](#0-6) 

So, whenever `VMConfig.allowTvmOsaka()` is not yet active on the running network, any smart contract that does `address(0x66).call{gas: X}(malformedData)` and expects a graceful `false` return (the Solidity analog of `try/catch` swallowing a failed sub-call) will instead have the *entire outer transaction* aborted — this mirrors the `repayLoanCallback` bug class where the intended graceful-failure path (`try/catch` at the caller) is bypassed because the actual failure mode isn't a normal, catchable revert.

### Impact Explanation
Any contract logic built to defensively call `ValidateMultiSign` (address `0x66`) and treat a `false`/`0` return as "signature validation failed, continue" is instead forced into an unconditional revert of the entire transaction whenever it (or an attacker who controls part of the calldata construction, e.g., via a proxy or wrapper contract forwarding user-supplied signature arrays) supplies malformed-length calldata. This breaks the caller's expected fail-soft contract semantics and can be weaponized by a malicious counterparty to force reverts/DoS specific transaction flows (e.g., multi-sig-gated payment/settlement contracts) that rely on `ValidateMultiSign` failing gracefully rather than aborting. This is a DoS of protocol-implementation semantics reachable via ordinary broadcast transactions/contract calls — no privileged actor is required.

### Likelihood Explanation
Likelihood is conditional: the vulnerable path only exists while `VMConfig.allowTvmOsaka()` is not activated on the network (pre-hardfork). Given the fix (TIP-854) exists specifically to correct this, the un-patched behavior is the live, default behavior until the corresponding hardfork/proposal is activated on the chain running this code. Reaching it only requires an ordinary `CALL`/`STATICCALL`/`DELEGATECALL` from any contract to precompile address `0x66` with calldata shaped to fail the `DataWord.parseArray` bounds checks (e.g., too few 32-byte words, causing an `ArrayIndexOutOfBoundsException` inside decoding) — trivially reachable from any broadcast `TriggerSmartContract`.

### Recommendation
Apply the same unconditional defensive wrapping used in `BatchValidateSign` to `ValidateMultiSign.execute`: validate/guard calldata shape (or wrap the entire method body, including `DataWord.parseArray` and the array indexing, in a `try/catch`) regardless of the `VMConfig.allowTvmOsaka()` flag, so that malformed calldata always results in `Pair.of(false, EMPTY_BYTE_ARRAY)` (or `Pair.of(true, DATA_FALSE)` consistent with prior semantics) rather than an uncaught exception propagating through `Program.callToPrecompiledAddress` and aborting the caller's transaction.

### Proof of Concept
1. On a java-tron network where `VMConfig.allowTvmOsaka()` is not yet enabled, deploy a contract that calls `address(0x66).call(shortMalformedCalldata)` where `shortMalformedCalldata` has fewer than the 5 header words `ValidateMultiSign` expects (e.g., `new byte[64]`, i.e., 2 words).
2. `Program.callToPrecompiledAddress` invokes `ValidateMultiSign.execute(data)`.
3. `DataWord.parseArray(rawData)` / subsequent `words[0]`, `words[1]`, `words[2]`, `words[3]` accesses throw (e.g., `ArrayIndexOutOfBoundsException`), matching the documented pre-activation behavior in `testTip854PreActivationNoOp`.
4. The exception is not caught inside `execute`, propagates out of `callToPrecompiledAddress`, and is only caught by `VM.play`'s outer handler, which spends all remaining energy and halts/reverts the entire transaction — even though the calling contract intended to treat a failed multi-sig validation as a recoverable `false` result.
