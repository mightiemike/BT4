### Title
`cost_model::calculate_cost` account-data allocation accounting is bypassed via CPI-based allocation - (File: cost-model/src/cost_model.rs)

### Summary
`CostModel::calculate_allocated_accounts_data_size` in `cost-model/src/cost_model.rs` only inspects top-level, statically-compiled instructions returned by `transaction.program_instructions_iter()` and only recognizes an allocation when the instruction's `program_id` is literally `system_program::id()`. [1](#0-0)  A transaction that instead invokes an attacker-deployed SBF program at the top level, which then internally CPIs into the system program to `CreateAccount`/`Allocate`, produces `allocated_accounts_data_size == 0` in the estimate because the top-level `program_id` is not `system_program::id()` and inner/CPI instructions are never inspected. [2](#0-1) 

### Finding Description
`calculate_cost` computes `allocated_accounts_data_size` via `calculate_transaction_cost` → `calculate_allocated_accounts_data_size`, which iterates only `instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>` sourced from `transaction.program_instructions_iter()` (the transaction message's top-level compiled instructions). [3](#0-2)  For each instruction it checks `program_id == system_program::id()` and only then deserializes the instruction data to detect `CreateAccount`, `CreateAccountWithSeed`, `CreateAccountAllowPrefund`, `Allocate`, or `AllocateWithSeed`. [4](#0-3)  This mechanism cannot see instructions issued via CPI, because CPI-invoked instructions are constructed and dispatched at runtime by the program itself (through `invoke`/`invoke_signed`, i.e. `program-runtime/src/cpi.rs`) and never appear in the transaction's top-level `program_instructions_iter()`.

The same static, top-level-only method is also reused for the "actual executed" cost path: `calculate_cost_for_executed_transaction` calls `calculate_transaction_cost` with the identical `transaction.program_instructions_iter()`, so even post-execution cost accounting for `allocated_accounts_data_size` does not use any information about what was actually allocated during execution (unlike `loaded_accounts_data_size_cost`, which does receive an `actual_loaded_accounts_data_size_bytes` argument). [5](#0-4) 

Exploit flow:
1. Attacker deploys an SBF program that, when invoked, performs `invoke(&system_instruction::create_account(...))` or `invoke(&system_instruction::allocate(...))` against a PDA/keypair it controls.
2. Attacker submits a top-level transaction whose only instruction targets their own program (not `system_program::id()`).
3. `calculate_account_data_size_on_instruction` returns `SystemProgramAccountAllocation::None` for that top-level instruction since `program_id != system_program::id()`, so `calculate_allocated_accounts_data_size` sums to `0`. [2](#0-1) 
4. `TransactionCost.allocated_accounts_data_size` is `0`, which `QosService`/`CostTracker::try_add` uses to check the block-level `allocated_data_size` budget (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA = 100_000_000` bytes). [6](#0-5) [7](#0-6) 
5. Because the estimate is `0`, this block-level throttle never fires for CPI-based allocations, regardless of how much real account data the transaction actually allocates during execution.

The per-transaction real allocation is still bounded by `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION = MAX_ACCOUNT_DATA_LEN * 2` (~20 MiB) enforced in `transaction-context/src/transaction_accounts.rs::can_data_be_resized`, which is independent of the cost model and not bypassable by CPI. [8](#0-7) [9](#0-8)  This per-transaction cap means the exploit does not grant unbounded per-transaction allocation, but it does mean an attacker can pack many transactions, each allocating up to ~20 MiB of real account data via CPI, into a block while the `CostTracker`'s `allocated_accounts_data_size` block-level admission counter stays at `0` for all of them, letting real accounts-data growth for the slot exceed the intended `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100 MB) QoS budget that block-packing/admission relies on.

### Impact Explanation
This breaks the specific invariant the question targets ("all account data allocation in a transaction is charged, including allocations made through CPI") for the block-level accounts-data-growth QoS limit only. The CU cost of the CPI'd system-program call is still charged through `programs_execution_cost`/compute budget metering — this is purely an `allocated_accounts_data_size` (bytes) accounting gap, not a compute-cost bypass. The concrete effect is that the leader's block-builder/QoS layer (`QosService`/`CostTracker`) can under-provision for real per-slot account-data growth, admitting more real state growth per block than the 100 MB `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` budget intends. Repeated abuse across many slots by unprivileged actors could increase per-slot state growth/IO beyond the value the cost model is designed to bound, potentially degrading validator/replay performance — consistent with a Liveness/Loss-of-Availability class finding, though it is a throughput-degradation vector bounded by the still-enforced per-transaction `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` cap rather than an unbounded resource-exhaustion or consensus-halting bug.

### Likelihood Explanation
Fully reachable by an unprivileged attacker: deploying an SBF program and invoking CPI to the system program is a normal, permissionless capability, and the top-level `program_instructions_iter()` scoping of `calculate_allocated_accounts_data_size` is a straightforward, deterministic code property, not a probabilistic race. The cost to the attacker is only normal transaction/compute-unit fees and program deployment rent; the exploit is trivially repeatable across transactions and slots.

### Recommendation
The cost model cannot statically know what a top-level SBF program will do via CPI (this is a known, general limitation of static-instruction-only cost estimation and is explicitly called out in the code comment "eventually, potentially determine account data size of all writable accounts / at the moment, calculate account data size of account creation"). [10](#0-9)  Fixing the *post-execution* accounting is straightforward and directly analogous to how `loaded_accounts_data_size_cost` is already computed with the actual value: change `calculate_cost_for_executed_transaction` to accept and use the *actual* accounts-data-size delta observed during execution (e.g., from the transaction's resize-delta / accounts_data_size tracking, `transaction-context/src/transaction_accounts.rs::update_accounts_resize_delta`) instead of recomputing from `program_instructions_iter()`, and feed that corrected actual value back into `CostTracker::update_execution_cost`/`try_add`/`remove` so the block-level `allocated_accounts_data_size` budget reflects reality even when allocation happens through CPI. The pre-execution estimate used for initial QoS admission can remain a conservative static approximation, since it is inherently only an estimate, but the tracker's committed/accumulated state should be reconciled with actual execution results.

### Proof of Concept
1. Deploy a minimal SBF test program that, on invocation, issues `invoke(&system_instruction::create_account(payer, new_account, lamports, space, owner), accounts)` for an attacker-chosen `space` (e.g. near `MAX_PERMITTED_DATA_LENGTH`).
2. Build a transaction whose single top-level instruction invokes this program (program_id ≠ `system_program::id()`), with `new_account` as a writable, signer account.
3. Call `CostModel::calculate_cost(&tx, &feature_set)` and assert `tx_cost.allocated_accounts_data_size() == 0`.
4. Execute the transaction against a `Bank`/SVM harness and read the actual accounts-data-size delta produced (e.g., via `bank.load_accounts_data_size_delta()` as used in `runtime/src/bank/tests.rs::test_update_accounts_data_size`), asserting it is `> 0` and equal to the CPI'd `space`. [11](#0-10) 
5. Assert failure of the invariant: `calculate_cost`'s `allocated_accounts_data_size` (0) is strictly less than the actual measured allocation, demonstrating the estimate is not an upper bound as required by the "Fast validation" criterion in the question.
6. Optionally, feed the same `tx_cost` into `CostTracker::try_add` in a loop to show the `allocated_accounts_data_size` block-level counter never increases despite repeated real CPI-based allocations, contrasting with `cost-model/src/cost_tracker.rs::test_cost_tracker_reach_data_block_limit`, which shows the tracker does correctly throttle when `allocated_accounts_data_size` is set directly (i.e., only the top-level system-program path is covered). [12](#0-11)

    fn calculate_account_data_size_on_deserialized_system_instruction(
        instruction: SystemInstruction,
        feature_set: &FeatureSet,
    ) -> SystemProgramAccountAllocation {
        let validate_space = |space: u64| {
            if space > MAX_PERMITTED_DATA_LENGTH {
                SystemProgramAccountAllocation::Failed
            } else {
                SystemProgramAccountAllocation::Some(space)
            }
        };

        match instruction {
            SystemInstruction::CreateAccount { space, .. }
            | SystemInstruction::CreateAccountWithSeed { space, .. }
            | SystemInstruction::Allocate { space }
            | SystemInstruction::AllocateWithSeed { space, .. } => validate_space(space),
            SystemInstruction::CreateAccountAllowPrefund { space, .. } => {
                if !feature_set.snapshot().create_account_allow_prefund {
                    return SystemProgramAccountAllocation::Failed;
                }
                validate_space(space)
            }
            // DEVELOPER WARNING: New allocating instructions MUST return `Failed`
            // until activated by a feature gate
            SystemInstruction::Assign { .. }
            | SystemInstruction::Transfer { .. }
            | SystemInstruction::AdvanceNonceAccount
            | SystemInstruction::WithdrawNonceAccount(..)
            | SystemInstruction::InitializeNonceAccount(..)
            | SystemInstruction::AuthorizeNonceAccount(..)
            | SystemInstruction::UpgradeNonceAccount
            | SystemInstruction::AssignWithSeed { .. }
            | SystemInstruction::TransferWithSeed { .. } => SystemProgramAccountAllocation::None,
            // DEVELOPER WARNING: New non-allocating instructions MUST return `Failed`
            // until activated by a feature gate
        } // Do not add wildcard pattern (_)
    }

    fn calculate_account_data_size_on_instruction(
        program_id: &Pubkey,
        instruction: SVMInstruction,
        feature_set: &FeatureSet,
    ) -> SystemProgramAccountAllocation {
        if program_id == &system_program::id() {
            if let Ok(instruction) =
                limited_deserialize(instruction.data, solana_packet::PACKET_DATA_SIZE as u64)
            {
                Self::calculate_account_data_size_on_deserialized_system_instruction(
                    instruction,
                    feature_set,
                )
            } else {
                SystemProgramAccountAllocation::Failed
            }
        } else {
            SystemProgramAccountAllocation::None
        }
    }

    /// eventually, potentially determine account data size of all writable accounts
    /// at the moment, calculate account data size of account creation
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }
