### Title
Panic in `receipt_filter_fn` on unresolvable `GlobalContractDistribution.target_shard` after resharding permanently halts delayed-receipt draining, causing a transaction-triggered chain halt - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DeployGlobalContract` is a normal, unprivileged action any account can submit. It creates a `GlobalContractDistribution` receipt that is walked shard-by-shard and can sit in the persistent, FIFO **delayed receipts queue** across many chunks while it "hops" through the shard layout. If the shard layout changes (resharding) while such a receipt is delayed, its `target_shard` field can become stale relative to the current layout. When the delayed queue is drained, `receipt_filter_fn` computes `receiver_shard_id()` and unconditionally `.unwrap()`s the result — if the shard id cannot be resolved, this panics. Because the delayed queue is FIFO and always drained from the head (exactly analogous to the Y2K Carousel rollover queue always processed from `index=0`), a single corrupted/unresolvable entry stuck at the front of the backlog will cause **every subsequent chunk application on that shard to panic**, permanently halting that shard (and effectively the chain) until a hard intervention/hotfix is deployed.

### Finding Description
- `Receipt::receiver_shard_id` (`core/primitives/src/receipt.rs:437-467`) resolves the destination shard for a `GlobalContractDistribution` receipt via `shard_layout.resolve_to_current_shard(target_shard)`, returning `Err(EpochError::ShardingError(...))` when the target shard "does not exist in the shard layout or its split history." [1](#0-0) 
- The delayed-receipt queue wrapper's filter, used every time a receipt is popped off the head of the persistent FIFO delayed queue during `process_delayed_receipts`, calls this function and immediately `.unwrap()`s it: [2](#0-1) 
- This filter runs on every `pop()` from the `DelayedReceiptQueue`, which is drained strictly FIFO from the front, exactly like the Sherlock Y2K `rolloverQueue`/`mintRollovers` pattern that always starts at `index=0` — a single bad head-of-queue entry blocks all subsequent progress because there is no way to skip past it. [3](#0-2) 
- `GlobalContractDistribution` receipts are created by any account calling the `DeployGlobalContract` action (`action_deploy_global_contract`, `runtime/runtime/src/global_contracts.rs:25-63`), which any unprivileged signer can submit, and then repeatedly forwarded shard-by-shard via `forward_distribution_next_shard` until it has visited every shard in the (then-current) shard layout: [4](#0-3) 
- The project's own test-loop regression test explicitly documents this exact failure mode and demonstrates it is only guarded for **two** resharding generations: `test_stale_global_contract_distribution_after_double_resharding` deliberately forces two sequential dynamic shard splits while a `GlobalContractDistribution` receipt for `deploy_user` is still in flight/delayed, then asserts the chain does *not* stall: [5](#0-4) 
  The test's own comment states: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations."* [6](#0-5) 

While the two-generation case is now covered by `resolve_to_current_shard`'s split-history map (`ShardsSplitMapV3`, `core/primitives/src/shard_layout/v3.rs:10-26`), the fundamental design is still `.unwrap()`-based and only as robust as the retained split-history/ancestor mapping. Any scenario where the split-history lookup cannot resolve the shard (e.g., additional resharding generations beyond what is tested, GC of retired shard-layout history, or any other edge case not covered by the two-split regression test) reproduces the panic — with no bound on how many resharding events can occur while a `GlobalContractDistribution` receipt is delayed in the queue, since delay time is driven by chunk gas/compute limits and congestion, not by a hard cap on elapsed resharding epochs.

### Impact Explanation
If `receiver_shard_id()` returns `Err` for an entry sitting anywhere in a shard's delayed-receipts queue, `receipt_filter_fn`'s `.unwrap()` panics every single time `process_delayed_receipts`/`DelayedReceiptQueueWrapper::pop` attempts to drain the queue — which happens unconditionally near the start of every chunk application for that shard. Because the delayed queue is a persistent FIFO trie-backed structure drained strictly from the head, and the panicking entry cannot be skipped or removed without special intervention, this results in **an unrecoverable, transaction/action-triggered chain halt** for the affected shard: every validator applying chunks for that shard crashes deterministically, which is exactly the "transaction-triggered halt" outcome called out as an acceptance criterion. This is functionally identical to the Y2K Carousel bug: a self-inflicted, permanently-DOS'd FIFO queue processed from the head that can never make forward progress once a malformed entry reaches the front.

### Likelihood Explanation
Reaching this requires: (1) a `DeployGlobalContract` action from any account (`GlobalContractDeployMode` is fully user-selectable, no special permission needed) whose resulting `GlobalContractDistribution` receipt takes multiple chunks/epochs to finish visiting all shards (achievable under congestion or simply due to the shard-by-shard hop design), and (2) enough resharding events occurring while that receipt is in flight to exceed whatever split-history depth `resolve_to_current_shard` can track. Dynamic resharding is triggered by state/memory growth thresholds rather than being purely validator-discretionary, and an attacker can accelerate shard memory growth via ordinary transactions to hasten splits. The existence of a dedicated regression test for the "double resharding" case strongly indicates this was a real, previously-triggerable bug class that engineering is aware of and has only partially hardened (bounded to two known-good split generations); the underlying `.unwrap()` in `receipt_filter_fn` remains a single point of failure for any unresolved case.

### Recommendation
- Replace the `.unwrap()` in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:876`) with a graceful, deterministic fallback rather than a panic — e.g., treat an unresolvable `target_shard` as belonging to the current shard (never dropping/losing the receipt) or explicitly re-route/re-target it, and surface a recoverable `RuntimeError`/`StorageInconsistentState` instead of an unconditional panic that halts the whole shard.
- Bound the lifetime of `GlobalContractDistribution` receipts against the shard-layout split-history retention window, or persist a canonical shard mapping snapshot with the receipt so historical resharding depth cannot exceed what `resolve_to_current_shard` can resolve.
- Add fuzz/property tests that resharding an arbitrary number of times (not just two) while any receipt kind is delayed never produces an unresolvable `target_shard`/`receiver_shard_id`, matching the Y2K-style remediation of never trusting a queue-invariant that a single previous state transition (here, resharding; there, unlisted enlist calls) can silently violate.

### Proof of Concept
1. Submit a `DeployGlobalContract` action from any account on shard S0 (unprivileged, single transaction) — `action_deploy_global_contract` (`runtime/runtime/src/global_contracts.rs:25`) creates a `GlobalContractDistribution` receipt targeting the deployer's own shard first.
2. While the receipt is still being forwarded (`forward_distribution_next_shard`, `global_contracts.rs:288-332`) — or delayed under chunk gas pressure — trigger enough shard splits (via ordinary state growth transactions that push shard memory past the `DynamicReshardingConfig` thresholds, as exercised in the existing test) so that the receipt's `target_shard` becomes several resharding generations stale.
3. Once splits exceed whatever depth `resolve_to_current_shard`'s split-history map can resolve (the current regression test only proves 2 generations are safe), `receiver_shard_id()` in `core/primitives/src/receipt.rs:447-463` returns `Err`.
4. On the next `process_delayed_receipts` call, `DelayedReceiptQueueWrapper::pop` invokes `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874-878`), which `.unwrap()`s the `Err` and panics.
5. Because the delayed queue is FIFO and this entry sits at (or reaches) the head, every subsequent attempt by any validator to apply a chunk for that shard repeats the same panic — a permanent, transaction-triggered chain halt, mirroring the existing test `test_stale_global_contract_distribution_after_double_resharding` (`test-loop-tests/src/tests/global_contracts_distribution.rs:30-187`), which was written specifically to catch this exact failure mode for the two-generation case.

    state_update: &mut TrieUpdate,

    let shard_layout = epoch_info_provider.shard_layout(&apply_state.epoch_id)?;
    let already_delivered_shards = BTreeSet::from_iter(

            .iter()
            .cloned()
            .chain(std::iter::once(apply_state.shard_id)),
    );
    let Some(next_shard) = shard_layout
        .shard_ids()

        return Ok(());

    let mut next_receipt = Receipt::new_global_contract_distribution(predecessor_id, next_receipt);
    let receipt_id = apply_state.create_receipt_id(receipt.receipt_id(), 0);
    next_receipt.set_receipt_id(receipt_id);

                shard_id: apply_state.shard_id,
