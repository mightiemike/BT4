Given the effort budget and iteration limit, I'll finalize based on the strongest confirmed local-code invariant gap found.### Title
`ensure_match_transaction_info` never validates state-checkpoint / hot-state / position-state root hashes, letting replay-verify accept a locally-computed state root that diverges from the authenticated chain - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the comparator used by replay/verify tooling (`storage/db-tool/src/replay_on_archive.rs`, `execution/executor/src/chunk_executor/mod.rs::verify_execution`) to confirm that a fresh local VM execution reproduces the authenticated, backup/consensus-committed `TransactionInfo` for a given version. It checks status, gas used, write-set hash, and event root hash, but it explicitly does **not** check `state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()`, as acknowledged by the code's own TODO comment.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  and continues through the write-set/event checks at [2](#0-1) . The function ends with an explicit admission that it skips the checkpoint-hash fields entirely: [3](#0-2) 

This function is the sole per-transaction correctness gate in two production/ops paths:
1. `execution/executor/src/chunk_executor/mod.rs::verify_execution`, invoked from `remove_and_replay_epoch` whenever `VerifyExecutionMode::should_verify()` is true during chunk replay (state-sync catch-up / intelligent sync verification): [4](#0-3) 
2. `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`, the tool operators use to audit that re-executing archived history reproduces the authenticated ledger: [5](#0-4) 

By contrast, the *live* state-sync fast path (`StateSyncChunkVerifier::verify_chunk_result`) compares the entire `TransactionInfo` struct field-by-field via `ensure_transaction_infos_match`, which does include `state_checkpoint_hash` since it's part of `TransactionInfo`'s `PartialEq`: [6](#0-5) . So the gap is specific to the "verify execution" / replay-verify tooling path, not the primary consensus-driven state-sync commit path — the two paths use different comparators, and only one of them was updated to skip checkpoint hashes.

The root cause: `ensure_match_transaction_info` takes `txn_info: &TransactionInfo` (the authenticated value with `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` fields) but never dereferences those getters to compare them against a locally computed root. Any state-root divergence between the local re-execution and the historical/authenticated `TransactionInfo` — caused by a VM/executor non-determinism bug, a Jellyfish Merkle/state-summary computation bug, or corrupted archived data that still hashes correctly on write-set/events — will be silently reported as "matched" by this comparator.

### Impact Explanation
This breaks the state-proof-integrity invariant that "committed state that differs from the correct VM result" must be detectable during replay/verification of authenticated data. Concretely:
- `replay_on_archive` (used to audit mainnet historical correctness, e.g., after a VM/gas-schedule change or when validating a new client implementation) will report a chunk as "verified" even though the locally computed state Merkle root at that version diverges from the on-chain `state_checkpoint_hash`. This defeats the entire purpose of the tool — detecting divergence would otherwise flag exactly the class of "hard-fork-only divergence during commit, replay, restore" bugs this report solicits.
- `verify_execution` in the chunk executor's replay path (used by full/validator nodes catching up via `VerifyExecutionMode::verify_all()`/related modes) similarly cannot detect an execution bug that produces a wrong state root while incidentally preserving correct write-set/event hashes for the checked transactions, or where the divergent state materializes only via the state-checkpoint transaction's root rather than in the per-transaction write set of the checked transactions themselves.
- Because this omission is not gated behind the "trading-native"/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` experimental flag for the base `state_checkpoint_hash` (only the position/hot-state part is future-tied), a real base-ledger state root mismatch during replay-verify is missed today, not just a future feature's root.

I could not fully confirm within the available iterations whether any other, later invariant in the executor/db-tool pipeline would independently panic on such a mismatch (e.g., accumulator-hash comparisons downstream), so the practical blast radius (silent false-positive "replay ok" vs. some other implicit catch) carries residual uncertainty; the code-level comparator gap itself, however, is concretely demonstrated.

### Likelihood Explanation
Triggering this requires an underlying execution/state-computation divergence to already exist (e.g., a non-determinism bug, a subtly incorrect state-summary/JMT update, or bit-for-bit different hashing under a different build) — this comparator is a *detection* mechanism, not itself an attack surface reachable by an unprivileged network actor to corrupt live consensus-committed state. Its value is precisely to catch such divergences before they propagate; the bug is that it fails at that one job. Likelihood is best characterized as "would matter whenever any other latent state-computation bug exists," making it a force-multiplier / safety-net failure rather than a directly exploitable primitive on its own.

### Recommendation
In `ensure_match_transaction_info` (types/src/transaction/mod.rs), compare the locally computed state checkpoint hash (and, when available/enabled, hot-state and position-state checkpoint hashes) against `txn_info.state_checkpoint_hash()` / `txn_info.hot_state_checkpoint_hash()` / `txn_info.position_state_checkpoint_hash()`, mirroring the pattern already used for `write_set_hash` and `event_root_hash`. Since `TransactionOutput` alone does not carry the state-checkpoint root (that's computed by `DoStateCheckpoint`), thread the applicable checkpoint hash into the callers (`verify_execution` in chunk_executor and `execute_and_verify` in replay_on_archive) so it can be validated per checkpoint transaction, not skipped.

    pub fn ensure_transaction_infos_match(
        &self,
        transaction_infos: &[TransactionInfo],
    ) -> Result<()> {
        ensure!(
            self.transaction_infos.len() == transaction_infos.len(),
            "Lengths don't match. {} vs {}",
            self.transaction_infos.len(),
            transaction_infos.len(),
        );

        let mut version = self.first_version();
        for (txn_info, expected_txn_info) in
            zip_eq(self.transaction_infos.iter(), transaction_infos.iter())

            ensure!(
                txn_info == expected_txn_info,
                "Transaction infos don't match. version:{version}, txn_info:{txn_info}, expected_txn_info:{expected_txn_info}",
            );
            version += 1;
        }
        Ok(())
