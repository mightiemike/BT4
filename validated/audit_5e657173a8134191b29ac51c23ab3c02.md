### Title
Attacker-controlled `RevertInstructions.FundRecipient` set to the zero address causes permanent burn of bridged/refund funds - (File: x/uexecutor/keeper/outbound.go, x/uexecutor/keeper/build_revert_outbound.go, x/uexecutor/types/inbound.go)

### Summary
The `Inbound.RevertInstructions.FundRecipient` field is fully attacker-controlled (it comes from the source-chain gateway event data submitted by the bridging user) and is never validated to be non-zero/non-empty anywhere in the inbound validation pipeline. When a bridged inbound later fails and must be reverted, or an outbound fails and funds must be re-minted, the protocol calls `CallPRC20Deposit` directly to this attacker-supplied address. If the attacker sets it to the EVM zero address, the protocol permanently mints/re-mints the bridged PRC20 tokens to `0x0`, burning them irrecoverably — mirroring the ERC721Votes bug class where an unchecked "destination" parameter allows an asymmetric, irreversible accounting operation (subtract/burn with no valid recipient).

### Finding Description
`Inbound.Canonicalize()` only lenient-canonicalizes `RevertInstructions.FundRecipient`; it does not reject the zero address: [1](#0-0) 

`ValidateForExecution()` validates `Amount`, `AssetAddr`, `Recipient`, and payload fields, but has no check at all on `RevertInstructions.FundRecipient`: [2](#0-1) 

The value is used verbatim to build the revert outbound recipient: [3](#0-2) 

And again when an already-created outbound fails and bridged funds must be re-minted back to the user: [4](#0-3) 

`CallPRC20Deposit` performs a real, committed `DerivedEVMCall` that mints PRC20 tokens to whatever `to` address is supplied, with no zero-address guard on the Go side: [5](#0-4) 

The same unguarded recipient pattern also affects the excess-gas refund path (`applyGasRefund`), which similarly falls back to `outbound.RevertInstructions.FundRecipient`: [6](#0-5) 

This matches the bug class in the external report: an unchecked "destination" parameter (delegate target in the original, fund-recipient here) lets a state-changing operation perform a one-sided, irreversible accounting action (subtract-only checkpoint / mint-to-void) with no way to recover the value, because zero address is never rejected as a valid destination.

### Impact Explanation
Any external, unprivileged bridging user can cause their own (or, in a more damaging cross-user variant, whoever they name in `RevertInstructions`) bridged/refunded PRC20 balance to be permanently and irrecoverably minted to the zero address instead of returned. This is an unauthorized/permanent burn of protocol-escrowed bridged value with no admin or validator misbehavior involved — it fires purely from validator-honest finalization of an attacker-crafted inbound event, matching the in-scope impact "permanent loss ... of user or protocol-controlled funds" / "unauthorized burn."

### Likelihood Explanation
High reachability: any user calling the source-chain gateway's `addFunds`-style method controls the raw event payload that becomes `Inbound.RevertInstructions.FundRecipient` server-side, decoded from `raw_payload`. No privileged role is needed, and honest Universal Validators will vote normally on the observed event since nothing about a zero-address `FundRecipient` is invalid at the ballot layer. The failure/refund path (deposit failure, chain-config removal race, outbound failure, excess-gas refund) is a normal, frequently-exercised branch in production (see the extensive revert/refund test suite), not an edge case.

### Recommendation
Reject empty/zero-address `FundRecipient` in `Inbound.ValidateForExecution()` (and the equivalent check on `OutboundTx.RevertInstructions` before `handleFailedOutbound`/`applyGasRefund` mint calls), falling back to `Sender` (as already done when `RevertInstructions` is `nil`) whenever `FundRecipient` is the zero address instead of trusting it verbatim.

### Proof of Concept
1. Attacker bridges funds via the source-chain gateway `addFunds` call, encoding `RevertInstructions.FundRecipient = 0x0000000000000000000000000000000000000000` in the raw payload, and deliberately arranges for the inbound to fail post-quorum (e.g., unregistered/removed token config, as already exercised in `test/integration/uexecutor/vote_inbound_validation_test.go:312-364` and `rescue_funds_test.go`).
2. Validators vote and finalize the ballot honestly; `ValidateForExecution` passes (no check on `FundRecipient`).
3. `buildRevertOutbound` sets `Recipient = "0x000...000"` per `x/uexecutor/keeper/build_revert_outbound.go:10-14`.
4. When the revert outbound resolves (or in the direct `handleFailedOutbound` path for a failed outbound), `CallPRC20Deposit` mints the bridged PRC20 amount to the zero address, permanently destroying it — verifiable by asserting `ob.Recipient == types.EvmZeroAddress` and observing the PRC20 balance of `0x0` increase instead of the user's.

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

	return nil
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
