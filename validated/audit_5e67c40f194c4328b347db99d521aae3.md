This confirms a genuine java-tron analog of the reported bug class: fabricated/stale log events surviving a failed transaction because the failure path fails to clear them before they are persisted and consumed by downstream log-processing code that never re-checks the transaction's failed status.

### Title
Log events from exceptionally-failed TVM executions are not cleared before being persisted and processed as valid logs - (`actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`VMActuator.execute()` clears `ProgramResult.logInfoList`/`deleteAccounts` unconditionally only when `result.getException() != null || result.isRevert()` is detected on the *normal* return path from `VM.play()`. [1](#0-0)  However, when `VM.play()` itself throws (`JVMStackOverFlowException`, `OutOfTimeException`, or any other `Throwable`), the corresponding `catch` blocks call `clearExceptionResult(result)`, which only clears the accumulated logs/delete-accounts **if the `allowTvmOsaka` hard-fork flag is enabled**: [2](#0-1) 

```java
private void clearExceptionResult(ProgramResult result) {
  if (VMConfig.allowTvmOsaka()) {
    result.getDeleteAccounts().clear();
    result.getLogInfoList().clear();
  }
}
``` [3](#0-2) 

`allowTvmOsaka` is a chain-parameter-gated hard-fork flag (`VMConfig.allowTvmOsaka()`/`initAllowTvmOsaka`) like every other TVM feature switch, defaulting to disabled until activated by chain governance. [4](#0-3)  On any chain where this flag is not yet active, a transaction that throws a stack-overflow or timeout exception mid-execution still keeps whatever `LogInfo` entries were appended to `ProgramResult.logInfoList` before the exception fired.

The transaction is nonetheless marked as failed downstream: `TransactionUtil.buildTransactionInfoInstance` sets `TransactionInfo.result = FAILED` based on `trace.getRuntimeError()`/exception, but unconditionally copies **all** of `programResult.getLogInfoList()` into the persisted `TransactionInfo.log` field regardless of that failure status: [5](#0-4) 

### Finding Description
This is the direct analog of the Phoenix SDK bug: an event/log collection loop that fails to check the transaction's `is_err`/failed status before trusting the parsed log data. In java-tron:
- `LogMatch.matchBlock` iterates `TransactionInfo.getLogList()` for every `TransactionInfo` in a block to build `eth_getLogs` results, with no check of `TransactionInfo.getResult()` (`SUCESS`/`FAILED`). [6](#0-5) 
- `BlockEventGet.parseLogs` builds `ContractTrigger`/event-plugin triggers from `txInfo.getLogList()` unconditionally. [7](#0-6) 
- `TransactionReceipt` (JSON-RPC `eth_getTransactionReceipt`/block receipts) copies `txInfo.getLogList()` into the receipt logs array, deriving `status` from `receipt.getResultValue()` (a separate `contractResult` enum) rather than from `TransactionInfo.code` FAILED/SUCESS, and without gating log inclusion on that status. [8](#0-7) 

Because logs are only guaranteed to be purged on the exception path when `allowTvmOsaka` is on, any chain instance running with this flag still disabled (the default state for a not-yet-activated hard fork) will persist and later expose logs generated by a transaction that ultimately errored out via a JVM-level exception (stack overflow / timeout / other `Throwable`) — as opposed to a normal VM-detected revert/exception, which is already correctly cleared unconditionally.

### Impact Explanation
An attacker-controlled contract that deliberately triggers deep recursion (JVM `StackOverflowError` → `JVMStackOverFlowException`) or a CPU-time exhaustion (`OutOfTimeException`) after having already emitted one or more `LOG0`-`LOG4` events can cause those emitted events to survive into the persisted `TransactionInfo` even though the transaction is recorded as `FAILED` and its state changes/internal transactions are rejected. Any consumer that trusts `TransactionInfo.log`/`eth_getLogs`/`eth_getTransactionReceipt` output without independently re-validating `TransactionInfo.result` (which mirrors the exact SDK flaw in the report) will process spoofed events for a transaction that never actually completed successfully — potentially misleading off-chain indexers, bridges, or exchanges (e.g., crediting a deposit event that never truly occurred) and providing a DoS/confusion vector for downstream SDK/event-plugin consumers of java-tron's log/event APIs.

### Likelihood Explanation
Reachable by any unprivileged user who can submit a `TriggerSmartContract`/`CreateSmartContract` transaction that deploys or calls a contract designed to emit logs and then recurse deeply enough to hit the JVM stack limit, or to run long enough to trip the CPU/timeout guard — both of which are ordinary, permissionless TVM execution paths, not privileged operations. The condition is gated purely on whether the `allowTvmOsaka` hard-fork parameter has been activated on the target chain; on any deployment where it has not yet been turned on, the vulnerable code path is the active, default behavior.

### Recommendation
Make `clearExceptionResult` unconditional (remove the `VMConfig.allowTvmOsaka()` gate) so that logs and delete-account lists are always cleared for `JVMStackOverFlowException`, `OutOfTimeException`, and generic `Throwable` paths, consistent with the existing unconditional clearing at the `result.getException() != null || result.isRevert()` check. As defense in depth, all downstream log consumers (`LogMatch`, `BlockEventGet`, `TransactionReceipt`, event-plugin trigger builders) should also explicitly verify `TransactionInfo.getResult() == code.SUCESS` before treating `TransactionInfo.log` entries as valid.

### Proof of Concept
1. Deploy a contract whose fallback/entry function first executes `LOG1`/`emit Event(...)`, then recurses into itself (or another contract) until the JVM call stack overflows, triggering `Program.JVMStackOverFlowException` inside `VM.play()`.
2. Broadcast a `TriggerSmartContract` transaction invoking this function on a java-tron node where `allowTvmOsaka` has not been activated.
3. Execution reaches `VMActuator.execute()`'s `catch (JVMStackOverFlowException e)` block; `clearExceptionResult(result)` is called but performs no clearing since `VMConfig.allowTvmOsaka()` is `false`. [9](#0-8) 
4. `TransactionUtil.buildTransactionInfoInstance` marks the resulting `TransactionInfo.result = FAILED` but still copies the pre-overflow `LogInfo` entries into `TransactionInfo.log`. [5](#0-4) 
5. Query `eth_getLogs`/`eth_getTransactionReceipt` or the event plugin for that transaction hash; the fabricated log entry is returned even though the transaction failed and its side effects were rolled back.

  public static List<LogFilterElement> matchBlock(LogFilter logFilter, long blockNum,
      String blockHash, List<TransactionInfo> transactionInfoList, boolean removed) {

    int txCount = transactionInfoList.size();
    List<LogFilterElement> matchedLog = new ArrayList<>();
    int logIndexInBlock = 0;

    for (int i = 0; i < txCount; i++) {
      TransactionInfo transactionInfo = transactionInfoList.get(i);
      int logCount = transactionInfo.getLogCount();

      for (int j = 0; j < logCount; j++) {
        Log log = transactionInfo.getLog(j);

        if (logFilter.matchesExactly(log)) {
          List<DataWord> topicList = new ArrayList<>();
          for (ByteString topic : log.getTopicsList()) {
            topicList.add(new DataWord(topic.toByteArray()));
          }

          LogFilterElement logFilterElement = new LogFilterElement(blockHash,
              blockNum,
              ByteArray.toHexString(transactionInfo.getId().toByteArray()),
              i,
              ByteArray.toHexString(log.getAddress().toByteArray()),
              topicList,
              ByteArray.toHexString(log.getData().toByteArray()),
              logIndexInBlock,
              removed,
              transactionInfo.getBlockTimeStamp()
          );
          matchedLog.add(logFilterElement);
        }

        logIndexInBlock += 1;
      }
    }

    return matchedLog;
  }
