## Title
Rounding/precision divergence between `validate()` and `execute()` in `ExchangeWithdrawActuator` causes validated withdrawals to fail on-chain - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` computes `anotherTokenQuant` (the counterpart amount returned to a TRC10 exchange withdrawer) twice with two **different rounding strategies**: `doValidate()` truncates the ratio with `BigDecimal.divideToIntegralValue` and tolerates up to 0.01% imprecision, while `execute()` recomputes the same ratio with `BigDecimal.divide()` (no rounding mode) and requires the result to be **exactly** divisible via `.longValueExact()`. This mirrors the Tapioca `MagnetarHelper.getFractionForAmount` vs `Singularity._removeAsset` bug class: two code paths computing the same derived value with inconsistent rounding, so a value accepted by the "estimator"/validation path is rejected by the actual state-mutating path.

### Finding Description
In `doValidate()`, the ratio is computed by truncation and only checked against a tolerance band: [1](#0-0) 

In `execute()`, the *same* ratio is recomputed but with `BigDecimal.divide()` (no scale/rounding mode supplied), which throws `ArithmeticException` unless the division is exact: [2](#0-1) 

Because `doValidate()` accepts any `tokenQuant` whose implied `anotherTokenQuant` is within 0.01% of the truncated (rounded-down) value, a transaction can pass validation for a `tokenQuant` where `secondTokenBalance * tokenQuant` is **not evenly divisible** by `firstTokenBalance`. When such a transaction reaches `execute()`, the strict `.divide()` call throws `ArithmeticException`, which is caught and converted into a `FAILED` status / `ContractExeException`: [3](#0-2) [4](#0-3) 

This is the direct java-tron analog of the reported bug class: an "estimation"/pre-check computation (`doValidate`, analogous to `MagnetarHelper.getFractionForAmount`) and the actual settlement computation (`execute`, analogous to `Singularity._removeAsset`) disagree because they round differently on the same math, causing a value that the pre-check accepts to be rejected (or, in the Tapioca case, mis-valued) by the real execution path.

### Impact Explanation
Any unprivileged TRC10 exchange creator (the `ExchangeWithdrawContract.owner_address` must equal `exchange.creator_address`, but this is a normal user role, not a privileged chain role) can trigger a withdrawal that passes `validate()` yet unconditionally fails at `execute()` for a broad, easily-computable set of `tokenQuant` values — specifically whenever `secondTokenBalance * tokenQuant` is not exactly divisible by `firstTokenBalance` but the truncated ratio still falls inside the 0.01% tolerance window. This is a concrete validate/execute state divergence: transactions that are broadcast, included in a block, and consume bandwidth/energy resources are guaranteed to revert to `FAILED`, wasting resources and making a class of legitimate exchange-withdraw amounts systematically unusable, even though the protocol's own validation logic deems them acceptable.

### Likelihood Explanation
High. This is not a rare edge case — any non-exact ratio (which is the overwhelming majority of `(firstTokenBalance, secondTokenBalance, tokenQuant)` triples for real-world pool balances) can produce a truncated value that satisfies the 0.01% tolerance check in `doValidate()` yet is not an exact `BigDecimal.divide()` quotient in `execute()`. No special privileges, timing, or MEV race is required — an ordinary exchange creator can hit this deterministically by choosing a `tokenQuant` derived from the pool's current balances.

### Recommendation
Make `execute()` use the same rounding as `doValidate()` (i.e., `divideToIntegralValue`/explicit rounding mode instead of a strict exact `.divide()`), or conversely tighten `doValidate()` to only accept exact ratios, so the validation and settlement computations agree. Centralize the ratio computation into a single shared helper used by both `doValidate()` and `execute()` to eliminate the possibility of divergent rounding.

### Proof of Concept
1. Create/observe a TRC10 exchange with `firstTokenBalance` and `secondTokenBalance` such that `gcd(secondTokenBalance, firstTokenBalance) < firstTokenBalance` (i.e., not every `tokenQuant` yields an integer ratio) — true for essentially any live pool.
2. As the exchange creator, submit `ExchangeWithdrawContract` with a `tokenQuant` (of `firstTokenID`) such that `secondTokenBalance * tokenQuant / firstTokenBalance` truncates to a value within 0.01% of the exact ratio but is not an exact integer division.
3. `validate()` (`doValidate()` at [1](#0-0) ) succeeds because the remainder is within tolerance.
4. `execute()` ( [2](#0-1) ) throws `ArithmeticException` from `.longValueExact()` on a non-exact `.divide()`, caught at [4](#0-3) , yielding a `FAILED` transaction result despite passing validation.
