### Title
Nakamoto block-proposal validation hardcodes `DEFAULT_MAX_TENURE_BYTES` while mining uses a configurable `max_tenure_bytes`, causing a miner/validator tenure-size divergence - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
`NakamotoBlockBuilder`'s tenure-size accounting (the analog of Optimism's calldata-derived gas floor) is computed from two different sources depending on the code path. During mining, the byte budget for a tenure is taken from the node's own configurable setting, `settings.max_tenure_bytes`, passed into `NakamotoBlockBuilder::new` in `build_nakamoto_block`. During block-proposal validation (the function signers/other nodes call to accept or reject a mined block before it is signed), the builder is instead constructed with the hardcoded constant `DEFAULT_MAX_TENURE_BYTES`, ignoring whatever value the validating node (or the miner) actually configured. This mirrors the EIP-7623 bug class: two code paths compute the "same" size-derived budget with two different formulas/inputs, so a value considered valid on one side can be rejected (or vice versa) on the other.

### Finding Description
The miner path constructs the builder with the configured tenure byte budget: [1](#0-0) 

That budget is enforced per-transaction in `try_mine_tx_with_len`, which accumulates `total_tenure_size` and rejects further transactions with `Error::TenureTooBigError` once it reaches `self.max_tenure_bytes`: [2](#0-1) 

In contrast, `NakamotoBlockProposal::validate` (the entry point used to statically/re-execute a proposed block before it is signed) and its internal `validate_replay` helper both construct their own `NakamotoBlockBuilder` with the **hardcoded** `u64::from(DEFAULT_MAX_TENURE_BYTES)`, not the value the node has configured or the value the miner used: [3](#0-2) [4](#0-3) 

Because `try_mine_tx_with_len` is re-invoked during replay validation with this independently-sourced `max_tenure_bytes`, the tenure-size equality that must hold between "what the miner allowed itself to build" and "what a validating node will accept" is not guaranteed: it holds only when a node's configured `max_tenure_bytes` happens to equal `DEFAULT_MAX_TENURE_BYTES`. If a miner (an unprivileged, minority actor — only the current sortition winner controls their own node's config) raises its own `max_tenure_bytes` above the default and builds a tenure whose total size falls between `DEFAULT_MAX_TENURE_BYTES` and its own configured value, the tenure is valid by the miner's own construction rules, but `postblock_proposal::validate`/`validate_replay` on any signer or peer will hit `Error::TenureTooBigError` partway through replay (see the tenure-size check at `nakamoto/mod.rs`, guarded by the same constant during block append) and reject the proposal or misclassify the replay set, producing a static-validation verdict that diverges from the block actually produced.

### Impact Explanation
This is a minority-triggerable (single mining node) static-validation divergence: a tenure that is internally consistent from the miner's perspective can be rejected by the independent validation path solely because that path uses a different, hardcoded byte-budget constant instead of mirroring the value actually used to build the block. This falls into the "High" impact category of a minority-triggerable static-validation divergence causing temporary tip/proposal disagreement (rejected valid proposals, stalled tenures) rather than an outright chain split, since block-proposal validation failures block signing rather than causing already-committed states to disagree.

### Likelihood Explanation
Triggering requires no privileged access beyond controlling one's own miner configuration (`max_tenure_bytes` is a node-local setting used by `BlockBuilderSettings`), which any miner already possesses when it wins sortition. No majority coordination or another party's key is needed; the divergence is purely a consequence of hardcoding a constant on one code path and reading a configurable field on the other.

### Recommendation
Thread the same `max_tenure_bytes` value (sourced from node configuration, not the hardcoded `DEFAULT_MAX_TENURE_BYTES`) into every `NakamotoBlockBuilder::new` call used for proposal validation and replay (`postblock_proposal.rs` lines ~713-724 and ~921-932), so the byte-budget check performed during validation is guaranteed to be identical to the one enforced by the block's producer.

### Proof of Concept
1. Configure a mining node with `miner.max_tenure_bytes` set above `DEFAULT_MAX_TENURE_BYTES` (a supported config knob feeding `BlockBuilderSettings.max_tenure_bytes`, consumed at `stackslib/src/chainstate/nakamoto/miner.rs:688`).
2. Win sortition and mine a tenure whose accumulated `total_tenure_size` exceeds `DEFAULT_MAX_TENURE_BYTES` but stays under the miner's configured `max_tenure_bytes`; the miner's own `try_mine_tx_with_len` check (`nakamoto/miner.rs:826-838`) allows this.
3. Submit the resulting block as a proposal; a signer/validator invokes `NakamotoBlockProposal::validate`, which rebuilds the tenure via `NakamotoBlockBuilder::new(..., u64::from(DEFAULT_MAX_TENURE_BYTES))` (`postblock_proposal.rs:713-724`) and replays the transactions.
4. Replay hits the smaller, hardcoded budget and raises `Error::TenureTooBigError` (or otherwise diverges in the replay-set accounting in `validate_replay`, `postblock_proposal.rs:921-1051`), causing the proposal to be rejected even though it was valid per the miner's own rules — a static-validation verdict directly attributable to the mismatched constant vs. configured value.

Note: the exact numeric value of `DEFAULT_MAX_TENURE_BYTES` and the full validation/bounds-checking logic for the `max_tenure_bytes` config field in `stackslib/src/config/mod.rs` could not be retrieved in the available search budget; the core claim — that `postblock_proposal.rs` hardcodes `DEFAULT_MAX_TENURE_BYTES` while `nakamoto/miner.rs` uses the configurable `settings.max_tenure_bytes` — is directly supported by the cited lines.
