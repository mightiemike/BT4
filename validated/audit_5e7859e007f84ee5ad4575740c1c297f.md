### Title
Chain sunset after outbound creation permanently strands already-burned funds in `PendingOutbounds` with no signing or refund path - (File: `universalClient/tss/coordinator/coordinator.go`, `x/uexecutor/keeper/create_outbound.go`)

### Summary
An admin can disable a chain's outbound flag (`ChainConfig.Enabled.IsOutboundEnabled = false`) or fully sunset the chain at any time via `x/uregistry`'s `MsgUpdateChainConfig`. If an `OutboundTx` for that destination chain was already created and indexed in `PendingOutbounds` *before* the disable took effect, the funds backing it (already burned/committed on Push Chain to emit the `UniversalTxOutbound` event) become permanently unrecoverable: the coordinator refuses to ever sign it again, and the chain's on-chain lifecycle explicitly forbids any automatic refund of a `PendingOutbounds` entry.

### Finding Description
Outbound creation happens synchronously in `BuildOutboundsFromReceipt`/`attachOutboundsToUtx` at the moment a `UniversalTxOutbound` event is observed in an EVM receipt, and the `OutboundTx` is written into `PendingOutbounds` before any TSS signing occurs [4](#0-3) . At creation time the only outbound-enabled check performed is inside `BuildOutboundsFromReceipt` itself [3](#0-2) , so a chain that is enabled at creation time but subsequently sunset by the admin leaves a "PENDING" entry in `PendingOutbounds` that was never blocked.

On the universalClient side, the coordinator that drives TSS signing for `EventTypeSignOutbound` events explicitly re-checks `IsChainOutboundEnabled` on *every poll* and permanently skips signing for any event whose destination chain is currently disabled [5](#0-4) . There is no expiry, retry-after-re-enable acknowledgment, or alternate path back to the user for that specific event once disabled — it is simply logged and `continue`d forever while the chain remains disabled.

On the Push Chain state-machine side, `x/uexecutor`'s own documentation confirms `PendingOutbounds` is intentionally never auto-removed except by validator consensus reaching `PASSED`; ballot/TSS-signing expiry does **not** remove the entry, and no automatic refund/compensation mechanism exists for a stuck `PendingOutbounds` record [6](#0-5) . Combined with the coordinator's permanent skip for disabled chains, an outbound whose destination chain is later sunset has no code path to (a) get signed/broadcast, or (b) get reverted/refunded — the user's already-burned funds are stuck in the "PENDING" `OutboundTx`/`PendingOutbounds` state indefinitely, exactly analogous to the reported `PositionManager` bug where queued redemptions against a sunset collateral get stuck because `redemptionCooldownPeriod` is never zeroed to unblock recovery.

### Impact Explanation
This is a High-impact, unprivileged-triggerable fund-freezing condition: any ordinary user whose crosschain transfer created a `PendingOutbounds` entry to a chain that is later disabled (a routine, expected admin/ops action documented in the codebase) has their bridged/burned funds permanently locked with no on-chain recovery path — matching the "permanent freezing of user funds" allowed-impact category.

### Likelihood Explanation
Likelihood is Low-to-Medium and not attacker-controlled per se — it requires the ordinary combination of (1) a normal user transaction creating a pending outbound and (2) a subsequent admin chain-disable action (a legitimate, expected operational event, e.g. during incident response or deprecating a chain), which is explicitly anticipated by the codebase's own "chain sunset" comments and tests (`test/integration/uexecutor/evm_hooks_and_outbound_test.go`, `universalClient/chains/chains_test.go`). No malicious actor is required; a routine admin action combined with in-flight user traffic is sufficient to trigger permanent loss for the affected users.

### Recommendation
When a chain transitions to `IsOutboundEnabled = false` (or fully sunset), the `x/uexecutor` keeper should proactively resolve any existing `PendingOutbounds` entries whose `DestinationChain` matches — either by triggering the same revert/refund path used for `INBOUND_REVERT`/rescue outbounds (minting the bridged amount back to the sender/`FundRecipient`), or by exposing an explicit admin-gated "cancel and refund pending outbound" message analogous to `RevertStuckInbound`, so operators have a guaranteed on-chain path to make affected users whole once a chain is sunset. This should be paired with either removing the coordinator's indefinite skip in favor of a timeout-driven expiry+refund vote, or ensuring the admin refund path is exercised whenever a chain is disabled while outbounds are still in flight.

### Proof of Concept
1. User submits a crosschain transfer that emits `UniversalTxOutbound` targeting chain `eip155:11155111`, which is currently `IsOutboundEnabled: true` — Push Chain burns/locks the corresponding PRC20 and creates an `OutboundTx` (`Status_PENDING`) plus a `PendingOutbounds` entry (`x/uexecutor/keeper/create_outbound.go`).
2. Before TSS signing completes, the admin submits `MsgUpdateChainConfig` on `x/uregistry` setting `Enabled.IsOutboundEnabled = false` for `eip155:11155111` (a supported, documented operation; see `test/integration/uexecutor/evm_hooks_and_outbound_test.go:576-627` demonstrating the disabled-check).
3. On the next and all subsequent coordinator poll ticks, `processConfirmedEvents` hits `!c.chains.IsChainOutboundEnabled(chain)` and skips the event indefinitely (`universalClient/tss/coordinator/coordinator.go:420-426`) — no signing, no broadcast, ever, while the chain stays disabled.
4. Per `x/uexecutor/README.md`'s documented invariants, nothing on Push Chain automatically times out, reverts, or refunds this `PendingOutbounds` entry — it persists as `PENDING` forever, and the user's already-debited funds are unrecoverable without a bespoke governance/admin intervention that does not currently exist in the codebase.

func (k Keeper) attachOutboundsToUtx(
	ctx sdk.Context,
	utxId string,
	outbounds []*types.OutboundTx,
	revertMsg string, // revert msg if the outbound is for a inbound revert
) error {

	if len(outbounds) == 0 {
		return nil
	}
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {

		for _, outbound := range outbounds {

			utx.OutboundTx = append(utx.OutboundTx, outbound)

			// Compute signature expiry deadline for the destination chain.
			var signingDeadline int64
			if chainCfg, err := k.uregistryKeeper.GetChainConfig(ctx, outbound.DestinationChain); err == nil {
				if chainCfg.TssSigningDeadline != nil && *chainCfg.TssSigningDeadline > 0 {
					signingDeadline = ctx.BlockTime().Unix() + int64(chainCfg.TssSigningDeadline.Seconds())
				}
			}

			// Write to pending outbounds index (inside UpdateUniversalTx closure for atomicity)
			if err := k.PendingOutbounds.Set(ctx, outbound.Id, types.PendingOutboundEntry{
				OutboundId:      outbound.Id,
				UniversalTxId:   utxId,
				CreatedAt:       ctx.BlockHeight(),
				SigningDeadline: signingDeadline,
			}); err != nil {
				return fmt.Errorf("failed to set pending outbound index for %s: %w", outbound.Id, err)
			}
