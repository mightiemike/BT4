OAuth login CSRF via shared `shopify_app_state`/`shopify_app_session` cookie path causes cross-shop session fixation - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
The Shopify OAuth `begin`/`callback` flow stores the anti-CSRF nonce (`shopify_app_state`) and, for non-embedded apps, the resulting session id (`shopify_app_session`) as browser cookies keyed only by a fixed `path` value that is **not scoped per shop**. Because the same browser cookie jar is shared by every shop a victim visits through the same app, an attacker who owns/controls their own shop can force an OAuth flow for their shop into a victim's browser and overwrite the victim's state/session cookie, fixing the victim's browser into the attacker's shop session — a classic OAuth login-CSRF / session-fixation bug. This mirrors the report's root cause: a value keyed by a shared "slot" (here, cookie path) that gets silently reset/overwritten by an unrelated entity (here, another shop), producing state confusion between the original holder and the new one.

### Finding Description
In `begin()`, the OAuth nonce cookie is always set with a path equal to the app's fixed `callbackPath` (e.g. `/auth/callback`), which is identical for every shop using the app — there is no shop-specific scoping: [1](#0-0) 

In `callback()`, the resulting session id cookie (`SESSION_COOKIE_NAME`) is written for non-embedded apps using `config.cookiePath ?? '/'`, i.e. it defaults to path `/` unless the app developer explicitly opts in to a shop-specific `cookiePath` function: [2](#0-1) 

The `cookiePath` option is documented as new and opt-in — "Static path (default behaviour, unchanged)" is `'/'` — confirming this collision is the pre-existing, still-default behavior, not fully mitigated for apps that don't set it: [3](#0-2) 

Because `Set-Cookie` from the app's own `begin()` response is applied by the browser regardless of whether the follow-on redirect to Shopify is fully completed by the user, an attacker can cause this response to be loaded in a victim's browser (e.g. via an `<iframe>`), setting `shopify_app_state` in the victim's cookie jar for the *attacker's* OAuth flow. If the app is already authorized on the attacker's own shop (a normal state for an app the attacker installed on their own store), Shopify's `/admin/oauth/authorize` endpoint silently re-approves and redirects back to the callback URL without requiring any user interaction, all while still running inside the victim's browser/iframe. The callback then validates successfully (`stateFromCookie` and `query.state` both originate from the very same flow instance) via: [4](#0-3) 

and the resulting `shopify_app_session` cookie — scoped to shop-independent path `/` by default — is written into the victim's browser, silently overwriting whatever session (their own shop's, if any) previously existed there.

### Impact Explanation
The victim's browser session for the non-embedded app becomes fixed to the attacker's shop without any consent click from the victim. Any subsequent data the victim enters into the app (forms, settings, uploaded content) is now associated with the attacker's shop, and any admin/staff actions performed by the browser while this cookie is active are executed against the attacker's shop's session rather than the shop the victim believes they are using. This is a cross-tenant session-fixation/login-CSRF vulnerability directly enabled by the shared cookie key without shop-specific scoping being applied by default.

### Likelihood Explanation
Any unauthenticated external attacker who can install/register their own Shopify shop (trivial, free, and self-service) can mount this attack purely by getting a victim to load a page containing a hidden iframe pointing at the target app's own `begin()`/OAuth start endpoint for the attacker's shop. No credentials, no MITM, and no privileged access to the victim's account are required — only default (non-`cookiePath`-configured), non-embedded app deployments are needed, which the CHANGELOG confirms is still the default behavior.

### Recommendation
Make cookie-path (or another shop-discriminating mechanism) scoping mandatory rather than opt-in for both `STATE_COOKIE_NAME` and `SESSION_COOKIE_NAME`, e.g., always derive the cookie path (or cookie name) from the shop parameter of the current OAuth flow instead of defaulting to `/` or a fixed `callbackPath`. Alternatively, bind the state cookie to the specific `shop` value being authorized and verify that binding in `callback()` (in addition to the current HMAC/state checks), so a nonce generated for one shop cannot be validated for a callback claiming a different shop.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` normally, so the app already holds a valid offline/online grant for that shop (subsequent OAuth authorize calls for it will auto-approve without a consent screen).
2. Attacker hosts a page containing `<iframe src="https://victim-app.example.com/auth?shop=attacker.myshopify.com">` (the app's `begin()` route) and lures the victim (who has no relationship to `attacker.myshopify.com`) to visit it.
3. The victim's browser receives and stores the `shopify_app_state` cookie from `begin()` (`packages/apps/shopify-api/lib/auth/oauth/oauth.ts` lines 93-100), then follows the redirect to Shopify's `/admin/oauth/authorize`, which silently re-approves (already granted) and redirects back to the app's callback URL — all inside the iframe, in the victim's browser.
4. `callback()` validates HMAC and state successfully (lines 242-255) because both derive from the same flow instance running in the victim's browser, exchanges the code for a token, and sets `shopify_app_session` at the default path `/` (lines 219-230), overwriting any prior session cookie the victim's browser held for this app.
5. The victim's browser is now fixed to `attacker.myshopify.com`'s app session for all further non-embedded app requests, without ever seeing or approving an installation prompt themselves.

```markdown
- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
```
