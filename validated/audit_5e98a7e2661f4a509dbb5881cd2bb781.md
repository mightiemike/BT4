### Title
Module-account nonce divergence between `ModuleAccountNonce` manual counter and real on-chain EVM nonce during UEA deployment - (File: `x/uexecutor/keeper/deploy_uea.go`, `x/uexecutor/keeper/evm.go`)

### Summary
`x/uexecutor` issues EVM transactions on behalf of its own module account (`ueModuleAccAddress`) through `DerivedEVMCall`. Almost every call site pre-increments a manually tracked, off-chain nonce counter (`ModuleAccountNonce`, collection index `4`) and passes it as `manualNonce`, explicitly to avoid nonce collisions between multiple derived calls issued by the module within the same block/transaction. However, `DeployUEAV2`/`CallFactoryToDeployUEA` — which is invoked from the very same inbound-execution flows, using the same `ueModuleAccAddress` as sender — passes `manualNonce = nil` and `isModuleSender = false`, causing that specific call to consume the nonce read directly from EVM state instead of the tracked counter.

### Finding Description
Per `DERIVED_TRANSACTIONS.md` and `x/uexecutor/keeper/keeper.go`, the module explicitly states:

> "Only one collection in the whole codebase should ever increment `ModuleAccountNonce`. ... The current design has only `x/uexecutor` doing this, so the invariant holds trivially." [1](#0-0) 

This claim is contradicted by the code. `GetModuleAccountNonce`/`IncrementModuleAccountNonce` maintain a KV-stored counter used by `CallPRC20Deposit`, `CallPRC20DepositAutoSwap`, `CallUniversalCoreSetChainMeta`, `CallUniversalCoreRefundUnusedGas`, and `CallExecuteUniversalTx` — all with `isModuleSender=true` and an explicit `&nonce`: [2](#0-1) [3](#0-2) 

But `CallFactoryToDeployUEA`, called from `DeployUEAV2` with `evmFrom = ueModuleAccAddress` (the same module sender address), passes `isModuleSender=false` and `manualNonce=nil`: [4](#0-3) [5](#0-4) 

`ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` call `DeployUEAV2(ctx, ueModuleAccAddress, ...)` when a UEA has not yet been deployed for a given inbound sender, and then immediately go on to call `depositPRC20`/`CallExecuteUniversalTx`/other module-sender derived calls for the *same* UTX in the same message handler: [6](#0-5) 

Per the fork's own documented semantics, `manualNonce=nil` causes the nonce to be "read from state like a normal user" (i.e., the real EVM state nonce of `ueModuleAccAddress` at call time), while `isModuleSender=true` + `&nonce` calls use the independently tracked `ModuleAccountNonce` collection value, which the docs say is "the caller's responsibility" and is "trusted verbatim" by the fork: [7](#0-6) [8](#0-7) 

Because `DeployUEAV2`'s state-nonce-consuming call is never reflected back into the `ModuleAccountNonce` collection (there is no call to `SetModuleAccountNonce` anywhere outside genesis/migration paths), the two nonce sources for the identical sender address (`ueModuleAccAddress`) can silently diverge: after a UEA deployment consumes the real on-chain nonce N (advancing state nonce to N+1), the `ModuleAccountNonce` counter used by subsequent manual-nonce derived calls in the same or a later block may still be at a value ≤ N, causing it to submit a stale/already-consumed nonce for the same sender address.

This is exactly the structural pattern behind the referenced Nibiru finding [M-07]: two different code paths manage the nonce for the same effective signer inconsistently (one auto-managed/state-derived, one manually tracked), and the manually tracked value is not kept in sync with nonce consumption that occurs through the other path.

### Impact Explanation
Depending on how the `pushchain/evm` fork's `DerivedEVMCall` actually resolves a stale/lower-than-current `manualNonce` for a module sender (this exact behavior lives in the external `github.com/pushchain/evm` fork and could not be directly verified from this repository's index), the impact ranges from:
- **Denial of service on legitimate inbound execution**: the derived call is rejected/reverted because the supplied `manualNonce` no longer matches the account's real state nonce, causing deposits/refunds/chain-meta updates for otherwise-valid inbounds to fail non-deterministically (depends on block ordering of concurrent inbound votes), corrupting the `UniversalTx` PCTx audit trail with spurious `FAILED` entries.
- **Nonce/state corruption**: if the fork trusts `manualNonce` "verbatim" and force-sets it via `SetNonce`-style logic (as the analog Nibiru `ApplyEvmMsg` code did for contract-creation), a stale, lower manual nonce could roll back the module account's on-chain nonce, potentially enabling a previously-executed derived call's nonce slot to be reused for a *different* payload, corrupting canonical `UniversalTx`/PRC20 accounting state for the module account.

This directly touches the required impact categories of "unauthorized module-originated EVM execution" and "corruption of ... canonical UniversalTx state," triggered purely by ordinary user activity (submitting a first-time cross-chain deposit that requires UEA deployment, timed/interleaved with other inbound votes landing in the same block) — no privileged actor is required.

### Likelihood Explanation
Reaching this condition requires two module-originated derived-call code paths for the same `ueModuleAccAddress` sender to interleave: one going through `DeployUEAV2` (state-nonce path) and another going through the `ModuleAccountNonce`-tracked path (`CallPRC20Deposit`, `CallExecuteUniversalTx`, etc.), without the collection being resynced after the deploy. Since `x/uexecutor` has no `BeginBlocker`/`EndBlocker` and processes `MsgVoteInbound` for multiple UTXs synchronously as validator votes arrive, an attacker with control over multiple source-chain inbound events (which any user submitting bridge transactions can create) can engineer this interleaving by causing a first-time-UEA-deploy inbound and other module-derived-call inbounds to finalize within the same or adjacent Push Chain blocks. Actual triggerability is bounded by validator vote timing rather than direct attacker control, so I assess likelihood as **plausible but not deterministically forceable** by an attacker without further confirmation of the fork's exact nonce-enforcement semantics.

### Recommendation
- Route `DeployUEAV2`/`CallFactoryToDeployUEA` through the same `ModuleAccountNonce` collection (pass `isModuleSender=true` and an explicit `&nonce` obtained via `GetModuleAccountNonce`/`IncrementModuleAccountNonce`) so that every EVM transaction sent as `ueModuleAccAddress` shares a single, consistently incremented nonce source.
- Alternatively, if `DeployUEAV2` must read the state nonce directly, resynchronize `ModuleAccountNonce` from the real on-chain nonce of `ueModuleAccAddress` immediately after every such call succeeds.
- Add an invariant check/test asserting `ModuleAccountNonce` always equals the module account's actual EVM state nonce after each block, to catch any other future call sites that bypass the manual counter.

### Proof of Concept
Full confirmation requires the `pushchain/evm` fork's `DerivedEVMCall` nonce-enforcement source, which is not present in this repository's index (it is pinned via `replace` in `go.mod` to `github.com/pushchain/evm`), so the following describes the reachable code-level divergence rather than an exploited end-to-end transaction:

1. A user (Sender A) triggers a first-time cross-chain deposit whose UEA is not yet deployed. Validators vote `MsgVoteInbound`; on finalization `ExecuteInboundFundsAndPayload` calls `DeployUEAV2(ctx, ueModuleAccAddress, ...)`, which calls `CallFactoryToDeployUEA` with `manualNonce=nil` — consuming the real on-chain nonce N of `ueModuleAccAddress` (state nonce becomes N+1) without touching `ModuleAccountNonce`. [9](#0-8) 
2. In the same or a subsequent block, another inbound (Sender B, or even a later step of Sender A's own inbound) triggers `depositPRC20`/`CallExecuteUniversalTx`, which reads `ModuleAccountNonce` (still ≤ N, since it was never updated by step 1) and submits it as `manualNonce` for the same `ueModuleAccAddress` sender. [10](#0-9) 
3. The module account's two nonce views (`ModuleAccountNonce` collection vs. actual EVM state nonce) are now inconsistent, and the second derived call either fails (stalling legitimate deposit/refund execution and corrupting the `UniversalTx.PcTx` audit trail with a bogus `FAILED` entry) or — depending on fork enforcement — is accepted with a stale nonce that Push Chain's own documentation says is "trusted verbatim," undermining the "single source of truth" invariant the module explicitly relies on.

**Note on limitations:** the precise runtime consequence (hard failure vs. silent nonce overwrite) depends on `DerivedEVMCall`'s implementation in the external `pushchain/evm` fork repository, which is outside this repo's indexed contents. I recommend a Devin session with access to `github.com/pushchain/evm` source to confirm whether a stale/lower `manualNonce` for an existing account is rejected or force-applied, which determines whether the concrete impact is "DoS on inbound execution" or "nonce/state corruption enabling replay."

```markdown
## Caveats

- **`isModuleSender=true` requires the synthetic signer logic in the fork.** If the upstream cosmos-evm version is bumped, that signer path must remain intact, otherwise module-originated derived calls will fail validation.
- **`manualNonce` is the caller's responsibility.** The fork trusts the supplied value verbatim. Two callers stomping each other's nonce will cause receipt collisions and confusing replays.
- **Pre-increment, never post-increment.** If you increment after the call and the call panics or errors mid-execution, you've now reused a nonce. Always increment first; treat skipped nonces as a non-issue (EVM allows nonce gaps for module accounts since no transaction sequencing depends on them).
```

```go
func (k Keeper) CallFactoryToDeployUEA(
	ctx sdk.Context,
	from, factoryAddr common.Address,
	universalAccount *types.UniversalAccountId,
) (*evmtypes.MsgEthereumTxResponse, error) {
	k.Logger().Debug("EVM call: deployUEA",
		"factory", factoryAddr.Hex(),
		"chain_namespace", universalAccount.ChainNamespace,
		"chain_id", universalAccount.ChainId,
		"owner", universalAccount.Owner,
	)

	abi, err := types.ParseFactoryABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse factory ABI")
	}

	abiUniversalAccount, err := types.NewAbiUniversalAccountId(universalAccount)
	if err != nil {
		return nil, errors.Wrapf(err, "failed to create universal account")
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		from,        // who is sending the transaction
		factoryAddr, // destination: FactoryV1 contract
		big.NewInt(0),
		nil,
		true,  // commit = true (real tx, not simulation)
		false, // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		false, // not a module sender
		nil,
		"deployUEA",
		abiUniversalAccount,
	)
}
```

```go
func (k Keeper) CallUniversalCoreRefundUnusedGas(
	ctx sdk.Context,
	gasToken common.Address,
	amount *big.Int,
	recipient common.Address,
	withSwap bool,
	fee *big.Int,
	minPCOut *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse UniversalCore ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	// fee is uint24 in Solidity — pass as *big.Int (go-ethereum ABI packs non-standard widths as *big.Int)
	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress,
		handlerAddr,
		big.NewInt(0),
		nil,
		true,
		false,
		true,
		&nonce,
		"refundUnusedGas",
		gasToken,
		amount,
		recipient,
		withSwap,
		fee,
		minPCOut,
	)
}
```

```go
func (k Keeper) DeployUEAV2(ctx context.Context, evmFrom common.Address, universalAccountId *types.UniversalAccountId) (*evmtypes.MsgEthereumTxResponse, error) {

	k.Logger().Debug("deploying UEA",
		"chain_namespace", universalAccountId.ChainNamespace,
		"chain_id", universalAccountId.ChainId,
		"owner", universalAccountId.Owner,
		"from", evmFrom.Hex(),
	)

	// EVM Call arguments
	factoryAddress := common.HexToAddress(types.FACTORY_PROXY_ADDRESS_HEX)

	// Use your keeper CallEVM directly
	receipt, err := k.CallFactoryToDeployUEA(
		sdkCtx,
		evmFrom,
		factoryAddress,
		universalAccountId,
	)
	if err != nil {
		return nil, err
	}

	k.Logger().Info("UEA deployed",
		"chain_namespace", universalAccountId.ChainNamespace,
		"chain_id", universalAccountId.ChainId,
		"owner", universalAccountId.Owner,
		"tx_hash", receipt.Hash,
		"gas_used", receipt.GasUsed,
	)

	return receipt, nil
}
```

```go
// GetModuleAccountNonce returns the current module account nonce.
// If not set yet, it safely defaults to 0.
func (k Keeper) GetModuleAccountNonce(ctx sdk.Context) (uint64, error) {
	nonce, err := k.ModuleAccountNonce.Get(ctx)
	if err != nil {
		// If the key is missing, return 0 instead of error
		if errors.Is(err, collections.ErrNotFound) {
			return 0, nil
		}
		return 0, err
	}
	return nonce, nil
}

// IncrementModuleAccountNonce increases the nonce by 1 and stores it back.
func (k Keeper) IncrementModuleAccountNonce(ctx sdk.Context) (uint64, error) {
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return 0, err
	}
	newNonce := nonce + 1
	if err := k.ModuleAccountNonce.Set(ctx, newNonce); err != nil {
		return 0, err
	}
	return newNonce, nil
}
```
