### Title
`liquidate-multi` swallows failed liquidations via `map`, permanently persisting the debt-repay/collateral-seize side effects of a `liquidate()` call whose later bad-debt-socialization step reverts - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` batches liquidations by directly invoking the public `liquidate` function (not via `contract-call?`) inside a `map`, and always returns `(ok (list ...))` regardless of whether individual entries succeeded. `liquidate` itself performs its state-mutating calls (`vault-system-repay`, `debt-remove-scaled`, `collateral-remove`) *before* the later bad-debt-socialization fold that can abort with `ERR-BAD-DEBT-SOCIALIZATION-FAILED`. Because those mutating steps are executed as separate `contract-call?`s that individually succeed and commit, and because the enclosing `liquidate-multi` transaction never itself returns an error, a late failure inside one batched liquidation does not undo the debt repayment/collateral seizure that already happened for that position - it is only reported as an `err` entry in the returned list.

### Finding Description
`liquidate-multi` is defined as: [1](#0-0) 

It maps `call-liquidate` (a private wrapper that calls the public `liquidate` directly, as a same-contract function call, not `contract-call?`) over the batch and always wraps the result in `(ok ...)`: [2](#0-1) 

Inside `liquidate`, all health/slippage guards (`ERR-LIQUIDATION-PAUSED`, `ERR-SLIPPAGE`, etc.) are evaluated first, and only afterward does the function perform its mutating cross-contract calls: [3](#0-2) 

However, later in the same function, if the borrower's collateral is fully exhausted, a bad-debt write-down is attempted via a `fold` over `socialize-debt-asset`, guarded by an `asserts!` that can still fail *after* the debt repay/removal and collateral removal above have already executed and committed: [4](#0-3) 

`socialize-debt-asset` is itself a fold that can `unwrap!` into a failed accumulator if the underlying vault call fails: [5](#0-4) 

Because `liquidate` is invoked as a plain in-contract function call (not `contract-call?`) from `call-liquidate`, and because `liquidate-multi` (the top-level transaction entry point) unconditionally returns `ok`, the transaction as a whole commits. The nested `contract-call?`s that already succeeded (`vault-system-repay`, `.v0-market-vault debt-remove-scaled`, `.v0-market-vault collateral-remove`) keep their committed state even though `liquidate`'s own execution for that position later returns an error via the bad-debt-socialization assert. The caller only observes this as an `err` entry inside the response list produced by `liquidate-multi`, with no on-chain indication that debt/collateral were already moved for that "failed" entry.

### Impact Explanation
When bad-debt socialization fails after collateral has already been fully seized and debt already marked repaid/removed for that asset, the position is left with residual, unsocialized bad debt that can no longer be liquidated (no collateral remains) and was never properly written down in the vault's `total-borrowed`/index accounting. This permanently distorts vault accounting (overstated outstanding debt with no backing collateral), which manifests as protocol insolvency risk and permanent freezing/mis-distribution of supplier yield, since the vault's interest/index computations will never reconcile the phantom debt.

### Likelihood Explanation
Exploitation requires no privileged access - any liquidator batching liquidations through `liquidate-multi` against a borrower whose last collateral asset is fully seized in the same call can trigger the code path where bad-debt socialization is attempted, and any transient failure in `vault-socialize-debt`/`vault-accrue` for that debt asset (e.g., an edge case in `calc-principal-ratio-reduction`, a zero-debt division edge case, or `debt-remove-scaled` interaction) surfaces only as a swallowed error, not a batch-level revert. The likelihood is not fully proven experimentally here (I did not trace every arithmetic edge case that reliably triggers the assert), but the structural weakness - the `map`-based batch entry point combined with mutation-before-final-guard ordering inside `liquidate` - is directly demonstrated in the code.

### Recommendation
Ensure `liquidate-multi` treats each batched liquidation atomically per-entry: either invoke `liquidate` via `contract-call?` (so a failure inside one entry actually rolls back that entry's nested state changes per Clarity's per-`contract-call?` savepoint semantics) instead of a plain in-contract function call, or restructure `liquidate` so the bad-debt-socialization step is validated for feasibility *before* performing `vault-system-repay`/`debt-remove-scaled`/`collateral-remove`, guaranteeing all-or-nothing execution for a single liquidation regardless of how it is invoked.

### Proof of Concept
1. Borrower has a single collateral asset and outstanding debt such that liquidating in full consumes 100% of the collateral (`no-collateral-left` path).
2. Liquidator calls `liquidate-multi` with this position included in the batch.
3. Inside `liquidate` (invoked as a plain call by `call-liquidate`), the guards pass, then `vault-system-repay`, `debt-remove-scaled`, and `collateral-remove` execute via `contract-call?` and commit successfully.
4. The subsequent `fold socialize-debt-asset` fails (e.g., due to a vault-side edge case in `vault-socialize-debt`/`vault-accrue`), causing the `asserts! ... ERR-BAD-DEBT-SOCIALIZATION-FAILED` at [6](#0-5)  to trigger, making `liquidate` return `err`.
5. `call-liquidate` returns this `err` response, `map` collects it into the results list, and `liquidate-multi` still returns `(ok (list ... err-entry ...))`, so the whole transaction commits.
6. On-chain state now shows: borrower's debt for that asset removed/repaid, collateral fully seized/transferred - but the vault's bad-debt write-down never happened, leaving vault accounting permanently out of sync.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation

                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))

;; Liquidates multiple positions atomically
;; Each position can have different: borrower, collateral asset, debt asset, and debt amount
;; Prevents front-running attacks that prevent bad debt socialization
;; Note: price-feeds not supported in batch - update prices separately or use individual liquidate()
;; Returns list of responses - one per position (ok/err)
;; Failed liquidations return error codes but don't revert entire batch
(define-public (liquidate-multi
                (positions (list 64 { borrower: principal,
                                      collateral-ft: <ft-trait>,
                                      debt-ft: <ft-trait>,
                                      debt-amount: uint,
                                      min-collateral-expected: uint })))
  (ok (map call-liquidate positions)))
