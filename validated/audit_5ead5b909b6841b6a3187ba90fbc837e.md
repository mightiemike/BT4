### Title
Fork-dependent poison-microblock report divergence causes `assert_eq!` panic in `inner_insert_matured_miner_reward` for a shared ancestor reward key - (File: `stackslib/src/chainstate/stacks/db/accounts.rs`)

### Summary
`inner_insert_matured_miner_reward` assumes that any two Stacks forks that mature a reward for the same `(parent_block_id, child_block_id)` key must compute an identical `MinerReward`, and treats any mismatch as a fatal `assert_eq!`. Because the poison-microblock report used in `calculate_miner_reward` is looked up from the *processing fork's* Clarity state at a fixed height rather than being fixed at the moment the reported block was mined, a poison-microblock report transaction that is included on only one of two sibling forks (both of which share the reported ancestor block) can make the two forks compute two different `MinerReward` values for the identical key, hitting the fatal assertion.

### Finding Description
The equality the code relies on is:
`stored_matured_reward_for_(parent_block_id, child_block_id)` == `newly_computed_reward_for_(parent_block_id, child_block_id)` for every fork that ever matures that pair. [1](#0-0) 

The reward is computed in `find_mature_miner_rewards`, which looks up the poison-microblock reporter for the ancestor block being matured via `get_poison_microblock_report(clarity_tx, reward_height)` — a lookup against the *current fork's* Clarity DB state, keyed only by absolute block height, not by the specific `(parent_block_id, child_block_id)` pair or by any fork-invariant commitment fixed at the time the ancestor block was produced. [2](#0-1) 

`calculate_miner_reward` branches materially on whether `poison_reporter_opt` is `Some`: the coinbase (and possibly anchored/streamed fees) are redirected to the poison reporter and the miner is "punished," producing a `MinerReward` with a different `address`/`recipient`/`coinbase` than the un-poisoned case. [3](#0-2) 

`inner_insert_matured_miner_reward`'s comment explicitly acknowledges that two forks may independently attempt to store a reward for the same ancestor pair, and treats that as safe *only* under the unstated assumption that the recomputed reward will always be identical:
```
// the only time it's okay to re-insert the same reward is if there are two Stacks forks
// trying to store the same matured rewards for a common ancestor block.
```
followed by `assert_eq!(rw, reward, "FATAL: tried to insert multiple distinct matured parent block reward records")`. [4](#0-3) 

The attacker's exact input: a valid `TransactionPayload::PoisonMicroblock` transaction proving a microblock fork committed by some miner's key at a given sequence — a transaction any unprivileged participant can construct once two conflicting, validly-signed microblocks at the same sequence number exist (e.g., from a miner's own equivocating microblock stream, or one leaked/observed on the network). The attacker gets this transaction mined into a block on fork A only (e.g., by relaying it only to the miner producing fork A, or timing its broadcast so it lands only in one of two competing sibling tenures), while fork B's blocks — which still reference the exact same ancestor block being rewarded — never include it.

Exploit flow:
1. Both forks A and B share a common ancestor block `C` with parent `P`, i.e., both forks will eventually mature the reward keyed by `(P_id, C_id)`.
2. Fork A includes a `PoisonMicroblock` tx (about `C`'s microblock stream) in one of its later blocks; fork B does not include it (or includes a different reporter / omits it).
3. When a node processes fork A far enough that `C`'s reward matures, `get_poison_microblock_report` returns `Some(reporter_A)` on fork A's Clarity state, producing a `MinerReward` crediting `reporter_A` and zeroing/reducing the miner's coinbase.
4. The node later reorgs to (or additionally processes, e.g. during a race/reorg window) fork B and matures the same `(P_id, C_id)` pair; `get_poison_microblock_report` on fork B's state returns `None` (no report), producing a different `MinerReward` crediting the original miner in full.
5. `inner_insert_matured_miner_reward` finds the existing row for `(P_id, C_id)`, compares `rw` (from fork A) against the freshly computed `reward` (from fork B), and hits `assert_eq!(rw, reward, ...)`, which panics and crashes the node process.

None of the existing guards prevent this: there is no fork-invariant/deterministic binding between the poison report and the specific `(parent_block_id, child_block_id)` pair other than "same block height," and `calculate_miner_reward`/`find_mature_miner_rewards` never checks that the poison report itself is part of the shared, pre-fork history versus fork-specific inclusion. `check_tenure_tx`, `verify_signer_signatures`, VRF/sortition validation, and MARF hashing operate on separate concerns (tenure/consensus validity, not the reward bookkeeping table) and do not constrain this.

### Impact Explanation
Any node that processes both forks (which is the normal, expected behavior during a reorg — nodes routinely process a competing branch before orphaning it) hits a Rust `assert_eq!` panic and crashes. Because this is deterministic given the same two forks, **every** node that ever processes both forks in this order will crash identically, which is a chain-processing halt reachable from ordinary reorg handling rather than a contrived corruption. This matches the "Critical: permanent node crash / consensus halt across all nodes that replay the fork pair" category, since it is a within-repo defect in miner-reward bookkeeping triggered by a legitimate fork + poison-report combination, not a generic resource-exhaustion DoS.

### Likelihood Explanation
Preconditions: the attacker needs (a) the ability to produce or observe a valid poison-microblock proof (any microblock-stream equivocation, achievable by a single miner slot or by observing one), and (b) the ability to get that transaction included in one branch's blocks but not the sibling branch — feasible for an unprivileged participant with a minority miner slot or simply by relaying the tx asymmetrically to competing miners during a natural fork/reorg. No majority stake, no signer collusion, and no privileged role is required. The scenario requires a live reorg where both forks are processed by the same node, which is common infrastructure behavior, not a rare edge case.

### Recommendation
Make the reward computed for a shared ancestor `(parent_block_id, child_block_id)` fork-invariant, e.g., resolve/store the poison-microblock report as part of the immutable historical record of the ancestor block itself (committed at the point the ancestor block was mined) rather than re-deriving it from the current fork's live Clarity state at maturation time. Alternatively, change `inner_insert_matured_miner_reward` to not crash on mismatch: detect the divergent-reward case, log it, and either keep the first-seen value deterministically (e.g., via a canonical tie-break) or defer/skip the conflicting insert instead of using a fatal `assert_eq!`.

### Proof of Concept
Rust integration test plan (two-fork harness on one `StacksChainState`):
1. Build a common ancestor chain up to block `C` (parent `P`), including a microblock stream produced by miner `M`.
2. Construct two conflicting, validly-signed microblocks at the same sequence number for `M`'s stream (poison evidence).
3. Fork A: mine subsequent blocks that include a `PoisonMicroblock` transaction reporting `M`'s equivocation for `C`'s stream, submitted by reporter `R`. Advance fork A until `C`'s reward matures; call `find_mature_miner_rewards` + `insert_matured_child_miner_reward` for `(P_id, C_id)` — assert the stored `MinerReward.recipient == R.to_account_principal()` and `coinbase` reflects the poison-commission calculation.
4. Fork B: from the same ancestor `P`/`C`, mine an alternate chain of the same length that does *not* include the `PoisonMicroblock` transaction. Advance fork B until `C`'s reward matures on this branch, and call `insert_matured_child_miner_reward` for the same `(P_id, C_id)` key.
5. Assertion under test: the second call must NOT panic via `assert_eq!(rw, reward, ...)` — i.e., either the two computed `MinerReward` values for `(P_id, C_id)` must be equal (proving no divergence), or the code must handle the mismatch gracefully (no fatal assertion). As written today, step 5 is expected to panic, demonstrating the bug: `rw.recipient == R` (poison reporter) while `reward.recipient == M` (original miner), with differing `coinbase`, hitting `assert_eq!` at `stackslib/src/chainstate/stacks/db/accounts.rs:515`.
