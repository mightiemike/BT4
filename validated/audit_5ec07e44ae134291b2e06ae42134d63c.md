### Title
Unbounded, Linearly-Scanned `reverse_index` Vec in SPL-Token Secondary Index Enables Attacker-Driven Quadratic CPU Cost - (File: accounts-db/src/accounts_index/secondary.rs)

### Summary
The `SecondaryIndex::insert()` function used by the SPL-Token-Owner and SPL-Token-Mint secondary indexes maintains a `reverse_index[inner_key] = Vec<Pubkey>` that is unbounded and is linearly scanned (`outer_keys.contains(key)`) on every single insert. Because `inner_key` is the token-account pubkey and `key` is the token account's *owner* field (attacker-controlled, decoded straight from account data), an unprivileged user who repeatedly changes their own token account's owner authority to fresh pubkeys causes this vector to grow without bound, and the `contains()` check performed on every insert turns the update cost into O(n) per write, i.e. O(n²) total for n writes to the same account — closely analogous to the reported unbounded-array/linear-scan gas-DoS pattern.

### Finding Description
`SecondaryIndex::insert()` pushes `key` (owner or mint) onto `reverse_index[inner_key]` only after checking that it isn't already present, but that presence check itself is a linear scan of the same unbounded vector: [1](#0-0) 

The comment above the type declaration acknowledges the vector is expected to stay small ("this is rare"), but nothing enforces that assumption: [2](#0-1) 

`inner_key`/`key` come directly from `update_spl_token_secondary_indexes`, where `pubkey` (the token account) is the `inner_key` and the decoded owner/mint field from the account's raw data is the outer `key`: [3](#0-2) 

`owner_key` is fully attacker-controlled: it is whatever the SPL Token program's `AccountOwner`/authority field currently is, and any token account holder can change it (e.g. via repeated `SetAuthority` calls) in as many separate slots/transactions as they like. Each such change is a distinct account write, and `update_secondary_indexes` is invoked on every account update when secondary indexes are enabled: [4](#0-3) 

Because each new owner value is essentially unique, `outer_keys.contains(key)` will almost always return `false`, so the vector keeps growing on every insert, and the cost of the `contains()` scan grows linearly with the number of prior owner changes for that specific account — yielding quadratic total CPU cost for a single attacker-controlled token account.

Cleanup of the same structure (`remove_by_inner_key_if`, invoked from `handle_dead_keys`/`purge_secondary_indexes_by_inner_key_if` when the account is finally removed from the primary index) also has to `drain(..)` the entire accumulated vector in one lock-held pass: [5](#0-4) 

This mirrors the reported bug class precisely: an attacker-growable, unbounded per-key array whose removal/insert costs scale with the (attacker-inflated) array size, run under a single lock/loop with no cap.

### Impact Explanation
This is only reachable when the validator/RPC node is configured with `--account-index spl-token-owner` and/or `spl-token-mint` (a common configuration on RPC nodes serving `getTokenAccountsByOwner`/`getTokenAccountsByMint`). Once enabled, any unprivileged user can, for a single token account they control, drive `reverse_index[pubkey]` to unbounded size and make each subsequent secondary-index update (which happens on the account-update hot path during flush) progressively more expensive due to the linear `contains()` scan, and make the eventual cleanup pass (`remove_by_inner_key_if`) proportionally more expensive as well. This causes disproportionate CPU and memory cost on the affected node relative to the (cheap) cost the attacker incurs to trigger it, degrading that node's account-update and index-cleanup performance.

### Likelihood Explanation
Likelihood is limited by the fact that this only affects nodes that opt into SPL-token secondary indexes (a config choice, common for RPC infrastructure but not for validators generally). Given that precondition, the attack itself requires no special privilege — just repeated `SetAuthority` (or equivalent owner-field-mutating) transactions against a single token account across many slots, which is inexpensive and fully within a normal user's capability.

### Recommendation
Bound the growth of `reverse_index` entries, e.g. by capping the number of distinct outer keys tracked per inner key (falling back to a "too many, drop tracking precision" sentinel), and/or replace the linear `Vec::contains` check with a `HashSet` (or small-set structure) so insert cost stays O(1) regardless of how many distinct owner/mint values have been observed for that account. Alternatively, only retain the most recent outer key per inner key if index precision for historical values is not required, since only the reader accessing the current owner appears to be relevant in practice.

### Proof of Concept
1. Start a validator/RPC node with `--account-index spl-token-owner`.
2. As an unprivileged user, create an SPL Token account `A`.
3. Repeatedly submit `SetAuthority(AccountOwner, new_random_pubkey)` on `A`, each in a separate slot, for N iterations.
4. Observe that `accounts_index.spl_token_owner_index.reverse_index[A]`'s vector length grows to N (per `update_spl_token_secondary_indexes` → `SecondaryIndex::insert`), and that each subsequent `insert()` call's `outer_keys.contains(key)` scan cost grows linearly with N, making the cumulative cost of N owner changes quadratic in N. Eventually closing/removing `A` triggers `remove_by_inner_key_if`, which must drain all N entries under a single lock.

    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);

        // removed (e.g. it was concurrently re-added), leave its mapping in place.

        // remove its entry from the reverse-index.
        reverse_index_entry.remove();
