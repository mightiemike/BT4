### Title
Hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` in the ETH Wallet Contract can permanently brick base-token transfers requiring an address check - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (the on-chain contract deployed to ETH-implicit accounts to let Ethereum-style transactions execute NEAR actions, per NEP-518) resolves the "address registrar" contract from a hardcoded, compile-time constant rather than a governance-controlled or verifiable parameter. This is structurally the same bug pattern as the Sherlock report: a security-critical cross-contract dependency address is baked in as a constant instead of being configurable/validated, and if it is wrong (or the referenced contract is redeployed/changed), the dependent code path reverts/fails permanently, blocking users from completing an action needed to move funds.

### Finding Description
`ADDRESS_REGISTRAR_ACCOUNT_ID` is embedded into the wallet-contract WASM at compile time via `include_str!` of a plain text file whose only content is `address-map.near`: [1](#0-0) [2](#0-1) 

This constant is used inside `inner_rlp_execute`, on the path handling `EOABaseTokenTransfer` with `address_check: Some(address)` — i.e. when the wallet contract must verify (via a cross-contract call to the registrar) that the transfer target address is not already claimed by a named account before it forwards the emulated Ethereum base-token transfer: [3](#0-2) 

The account ID is parsed at call time with only a syntactic validation (`.parse()`), which panics if the string is not a syntactically valid `AccountId`, but does **not** validate that the account exists or hosts a compatible `AddressRegistrar` contract: [4](#0-3) 

If `ADDRESS_REGISTRAR_ACCOUNT_ID` does not point to a live, correctly-implemented `AddressRegistrar` contract (e.g. wrong/stale address baked in at build time, or the registrar being redeployed/migrated to a new account without a corresponding rebuild+redeploy of the wallet contract), the cross-contract `lookup` call will fail. This surfaces in `address_check_callback` as `PromiseResult::Failed`, which is handled by simply returning a failure response, `has_in_flight_tx` is reset to `false`: [5](#0-4) 

Critically, on this path the transaction's nonce is deliberately **not** incremented — deferred until the registrar lookup succeeds and returns `None` — as documented in `inner_rlp_execute`: [6](#0-5) 

Because the registrar address is a fixed constant baked into the deployed wasm (the same binary used for all ETH-implicit accounts on a chain, referenced globally via `eth_wallet_global_contract_hash`), this is a single point of failure analogous to `RollerUtils`' hardcoded `DIVIDER`: if it is wrong, every wallet-contract instance on that chain is affected, not just one account.

### Impact Explanation
If the hardcoded registrar address is incorrect or becomes stale relative to the actually-deployed `AddressRegistrar` contract, then **every** relayed Ethereum-style base-token transfer that requires an address check will deterministically fail at the `lookup` cross-contract call. Since the nonce is never incremented on this failure branch, the user's signed Ethereum transaction can be retried indefinitely with the same nonce yet will never succeed, and the only observable effect for the user is a stuck/failed transfer — there is no alternate, permissionless code path in this contract to bypass the registrar check for that same transaction shape. This mirrors the "brick" impact in the report: users relying on ETH-style tooling to move base-token funds through their ETH-implicit account can be locked out of that specific transfer type. Because the wallet contract is deployed as a shared **Global** contract used by all ETH-implicit accounts (see `EthImplicitGlobalContract` / `eth_wallet_global_contract_hash`), a bad hardcoded value affects the entire population of ETH-implicit accounts on the network, not a single user.

### Likelihood Explanation
This is a build/deploy-time correctness issue rather than an issue directly triggerable by an attacker choosing arbitrary input — similarly to the original Sherlock finding, the trigger condition is "the hardcoded dependency address is wrong for the environment it's deployed to" (e.g. copy-paste from a different network, or the registrar being redeployed to a new account without a corresponding rebuild of the wallet contract binary that embeds `ADDRESS_REGISTRAR_ACCOUNT_ID`). Given the value is committed directly in source (`address-map.near`) with no update mechanism from governance/admin and no runtime validation that the target account actually implements `AddressRegistrar`, any mismatch is silent until an `EOABaseTokenTransfer` with `address_check: Some(..)` is attempted by a normal user through a relayer — a fully permissionless, single-transaction trigger.

### Recommendation
- Do not hardcode the address-registrar account ID as a compile-time constant baked into a shared global contract binary used by every ETH-implicit account. Instead, make it a configurable/immutable value set at controlled deployment/initialization time (analogous to passing `DIVIDER` via constructor in the referenced fix), so that the correct chain-specific registrar can be enforced without silently drifting.
- Add defensive handling in `address_check_callback` (and/or `inner_rlp_execute`) for the case where the registrar call fails, to avoid a state where the intended action can never complete (e.g., a bounded retry/fallback path, or clearer failure semantics that let the relayer/user recover instead of an unconditional dead end).
- Validate at build/release time (and ideally with an on-chain/CI check) that `ADDRESS_REGISTRAR_ACCOUNT_ID` matches an actually-deployed `AddressRegistrar` contract for each target chain (mainnet/testnet/localnet), the same way `wallet_contract_magic_bytes`/`eth_wallet_global_contract_hash` are chain-gated in `runtime/near-wallet-contract/src/lib.rs`.

### Proof of Concept
1. Build the wallet-contract WASM with `ADDRESS_REGISTRAR_ACCOUNT_ID` = `address-map.near` (as currently committed) and deploy it as the global wallet contract for ETH-implicit accounts on a chain where `address-map.near` is not a valid, deployed `AddressRegistrar` contract (e.g., the account doesn't exist, or has been redeployed/migrated elsewhere without updating this constant).
2. An ETH-implicit account (created via a `Transfer` action per `docs/DataStructures/Account.md`) attempts a base-token transfer requiring an address check — i.e., the relayer submits an RLP-encoded Ethereum transaction to `rlp_execute` producing `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), .. })`.
3. `inner_rlp_execute` reaches `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:419-424`, builds a promise to `address-map.near::lookup`, and does not increment the nonce (`lib.rs:358-365`).
4. Because `address-map.near` is not a valid/functioning registrar, the promise fails; `address_check_callback` (`lib.rs:140-148`) returns a failure `ExecuteResponse` without banning the relayer and without advancing the nonce.
5. The user/relayer retries with the same nonce and encounters the identical failure indefinitely — this specific transfer flow is permanently unusable for every ETH-implicit account using this wallet-contract build, until the contract is redeployed with a corrected registrar reference.
