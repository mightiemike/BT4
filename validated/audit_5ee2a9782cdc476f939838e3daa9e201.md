### Title
Unhandled exception in `sanitizeHost` from malformed base64 `host` param crashes async Express/Remix redirect handlers - (File: `packages/apps/shopify-api/lib/utils/shop-validator.ts`)

### Summary
`sanitizeHost` calls `new URL(https://${decodeHost(sanitizedHost)})` with no try/catch, so any base64-valid `host` value that `atob` decodes into a string that is not a syntactically valid URL authority (e.g. containing whitespace, control characters, or other characters illegal in a URL host) causes `new URL()` to throw a synchronous `TypeError`. Several pre-auth callers (`getEmbeddedAppUrl`, Express's `redirectToShopifyOrAppRoot`, Remix's `redirectToShopifyOrAppRoot`/`validateShopAndHostParams`) invoke `sanitizeHost`/`buildEmbeddedAppUrl` inside `async` functions without wrapping the call in try/catch, turning the thrown error into an unhandled promise rejection.

### Finding Description
`sanitizeHost` in `packages/apps/shopify-api/lib/utils/shop-validator.ts` first checks the raw `host` string against `base64regex = /^[0-9a-zA-Z+/]+={0,2}$/` [1](#0-0) , which only constrains the *encoded* characters, not what the base64 payload decodes to. It then immediately does `const {hostname} = new URL(\`https://${decodeHost(sanitizedHost)}\`)` with no try/catch around the `new URL()` call [2](#0-1) . `decodeHost` is a thin wrapper over `atob` [3](#0-2) , which will happily decode any base64 string into arbitrary bytes, including spaces, tabs, control characters, or other bytes that are not permitted in a URL authority component. When such bytes are substituted into the `https://<decoded>` template, `new URL()` throws a `TypeError: Invalid URL` synchronously.

This function is reached pre-authentication from multiple entry points that take an untrusted `host` query parameter and call `sanitizeHost`/`buildEmbeddedAppUrl` without their own try/catch:
- `getEmbeddedAppUrl` reads `host` directly from `url.searchParams.get('host')` and passes it to `buildEmbeddedAppUrl`, which calls `sanitizeHost(config)(host, true)` unguarded [4](#0-3) .
- Express's `redirectToShopifyOrAppRoot` middleware calls `api.utils.sanitizeHost(req.query.host as string)!` synchronously inside an `async function`, with no try/catch [5](#0-4) .
- Remix's `redirectToShopifyOrAppRoot` and `validateShopAndHostParams` similarly call `api.utils.sanitizeHost(...)` unguarded inside async/sync functions that are invoked from the OAuth/admin-authentication flow [6](#0-5) [7](#0-6) .

Because these calls happen inside `async` function bodies, a synchronous throw becomes a rejected Promise. Express 4's routing layer does not `await`/catch rejected promises returned by route/middleware handlers by default, so this becomes an unhandled promise rejection. Since Node.js 15+, the default `--unhandled-rejections` mode is `throw`, meaning an uncaught rejection terminates the Node process by default. This turns a single crafted, unauthenticated HTTP request into a process-level denial of service against the host application's auth-adjacent redirect handlers.

Regarding the specific bypass hypotheses in the question (userinfo `@` tricks, `myshopify.com.attacker.com` suffix tricks): these do **not** bypass the allowlist, because `new URL().hostname` correctly strips userinfo/port/path/fragment before the `hostRegex = /\.(domain1|domain2|...)$/` check is applied [8](#0-7) , and the regex anchors on a literal `.` before the allowed suffix, so `attacker.commyshopify.com` and `myshopify.com.attacker.com` are correctly rejected. The genuine, exploitable issue is the missing error handling around `new URL()`, not an allowlist bypass.

### Impact Explanation
An unauthenticated attacker can send a single GET/POST request with a crafted `host` query parameter (valid base64 that decodes to characters illegal in a URL, e.g. a space) to any endpoint that invokes `sanitizeHost`/`buildEmbeddedAppUrl` pre-authentication (e.g., the app's OAuth redirect/root route). This throws an unhandled exception; in Express-based host apps this becomes an unhandled promise rejection, which under default Node.js 15+ behavior terminates the process — a full denial of service reachable without any credentials, matching Shopify's "DoS in an authentication handler" bounty impact class.

### Likelihood Explanation
No preconditions beyond the ability to send an HTTP request with a `host` query parameter — this is the default entry point for any embedded Shopify app using `shopify-api`/`shopify-app-express`/`shopify-app-remix`. Crafting a payload is trivial (any base64 string decoding to a space or control character, e.g. `Buffer.from(' ').toString('base64')` = `"IA=="`) and is 100% repeatable.

### Recommendation
Wrap the `new URL(...)` call in `sanitizeHost` in a try/catch, treating any thrown error as an invalid host (returning `null` or throwing `InvalidHostError` consistently), so malformed decoded values can never propagate an unhandled exception into caller code. Additionally, callers such as `redirectToShopifyOrAppRoot` (Express/Remix) and `getEmbeddedAppUrl` should not use non-null assertions (`!`) on `sanitizeHost` results and should handle invalid host values by returning an error response rather than relying on the function never throwing.

```ts
// packages/apps/shopify-api/lib/utils/__tests__/shop-validator.test.ts

test('sanitizeHost throws unhandled TypeError on malformed decoded host', () => {
  const shopify = shopifyApi(testConfig());

  // "IA==" is valid base64, decodes to a single space " ",
  // which is not a legal URL host and makes `new URL` throw.
  const malformedBase64Host = Buffer.from(' ').toString('base64'); // "IA=="

  expect(() => shopify.utils.sanitizeHost(malformedBase64Host)).toThrow(TypeError);
  // Expected (secure) behavior: should return null or throw InvalidHostError,
  // not an unhandled TypeError from `new URL()`.
});
```

Expected (buggy) behavior: the async middleware throws inside `sanitizeHost`, producing an unhandled promise rejection; under default Node 15+ semantics this crashes the process instead of returning a 400 response.
