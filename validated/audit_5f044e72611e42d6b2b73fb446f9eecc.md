### Title
Stale-Read TOCTOU on Session Storage Causes One Failing Concurrent Request to Overwrite Another Request's Freshly-Obtained Access Token - ([File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts])

### Summary
`performTokenExchange` reads the current session from `sessionStorage` once at the top of the handler and holds onto that snapshot (`sessionToInvalidate`). If the subsequent Shopify token-exchange call fails with an HTTP 401 later in the same request, the handler blindly nulls out the access token on that stale snapshot and writes it back to shared session storage, without re-reading the session immediately before the write. In a concurrent-request scenario, this stale write can clobber a valid, freshly-obtained access token that another concurrent request for the *same shop/session id* stored in the interim — the classic "last writer wins on a shared mutable resource, computed from a stale read" pattern described in the vault bug class.

### Finding Description
`perform-token-exchange.ts` captures the current session near the start of the handler: [1](#0-0) 

That snapshot is retained purely for later error handling ("Hoisted so the outer catch can invalidate a stale access token if needed"). [2](#0-1) 

Later, after the (possibly slow) network calls to `api.auth.tokenExchange` for offline/online tokens have taken place, if a 401 is received the handler invalidates the access token using the *original* stale snapshot object rather than re-loading the current session state from storage: [3](#0-2) 

`invalidateAccessToken` unconditionally overwrites the stored session with the stale in-memory object (with `accessToken` set to `undefined`): [4](#0-3) 

There is no optimistic-concurrency check (e.g., comparing token/timestamp before writing) and no re-fetch of the session right before the invalidating write. All session-storage implementations examined (`MemorySessionStorage`, `PostgreSQL`, `DynamoDB`) perform a simple upsert/put that fully replaces the row for a given session id, with no version or CAS semantics: [5](#0-4) [6](#0-5) 

This is the same class of bug as the vault report: a shared piece of state (Vault balance / SessionStorage row keyed by shop+session id) is mutated based on data read at an earlier point in time, and the final write silently discards work done by another actor in between — the "last writer" (the request that reaches the invalidation branch last) overwrites the outcome for everyone sharing that resource (the shop's offline/online session).

### Impact Explanation
Because `sessionId` is derived deterministically from `shop` (and `sub` for online tokens), multiple concurrent requests hitting the same app instance for the same shop/user (e.g., multiple embedded-admin tabs, or concurrent webhook/app-proxy driven authenticate calls) share the same session-storage key. If Request A's token-exchange transiently fails with a 401 (e.g. Shopify-side transient error, rate limiting, or an in-flight token revoked-and-reissued race) while Request B concurrently completes a token exchange and stores a fresh, valid `accessToken` for the same session id, Request A's delayed invalidation branch will overwrite Request B's freshly stored session, wiping out its valid access token. All subsequent requests for that shop then see `accessToken: undefined`/inactive session and are forced into full re-authentication (`respondToInvalidSessionToken`), effectively causing a denial-of-service of the authenticated request path for that shop until OAuth/token-exchange is repeated. This impacts every merchant/session sharing the app process at the time of the race, not just the requester who hit the transient 401.

### Likelihood Explanation
The trigger for the race is a transient 401 from `api.auth.tokenExchange`, which is plausible in production (network blips, Shopify-side throttling, revoked/rotated tokens, or races inherent to `expiringOfflineAccessTokens` refresh flow) rather than a contrived edge case. Any app that receives concurrent requests for the same shop (very common for embedded apps with multiple browser tabs, background jobs, or webhook-triggered authenticate calls) is exposed. No privileged access or secret leakage is needed — it's purely a timing condition triggerable by an unauthenticated/normal merchant browsing flow that happens to overlap with any 401 response from Shopify's token endpoint.

### Recommendation
Before writing the invalidated session, re-load the current session from `sessionStorage` (or perform the invalidation conditionally, e.g., only clear the access token if it still matches the token/timestamp that was active when the 401 occurred) instead of relying on the `sessionToInvalidate` snapshot captured at the start of the request. Session-storage adapters should support optimistic concurrency (e.g., a version/updatedAt column with a conditional update) so that a stale write cannot silently clobber a newer session record. Apply the same fix to the equivalent logic in `packages/apps/shopify-app-remix/src/server/authenticate/admin/strategies/token-exchange.ts` and `packages/apps/shopify-app-react-router/src/server/authenticate/admin/strategies/token-exchange.ts`, which share the same `invalidateAccessToken`-on-401 pattern.

### Proof of Concept
1. App is configured with the default in-memory/Postgres session storage and `useOnlineTokens`/offline session for shop `test.myshopify.com`.
2. Two concurrent requests (`A` and `B`) hit an endpoint protected by `performTokenExchange` for the same shop at roughly the same time, both finding no active session and both calling `exchangeToken` for `OfflineAccessToken`.
3. Request `B`'s token exchange succeeds and calls `config.sessionStorage.storeSession(offlineSession)` with a valid `accessToken`, completing successfully and returning `next()`.
4. Request `A`'s token exchange call to `api.auth.tokenExchange` returns an `HttpResponseError` with `code === 401` (simulate via a mocked failing/transient response), causing the `catch` block to run: [3](#0-2) 
5. Since `sessionToInvalidate` was captured before either exchange occurred (a pre-exchange, inactive/absent session snapshot), `invalidateAccessToken` stores that stale session object (with `accessToken: undefined`) back into `sessionStorage`, overwriting the valid session `B` just stored.
6. Any subsequent request for `test.myshopify.com` now finds `session.accessToken === undefined` / `isActive()` false, and is forced to re-authenticate — denial of service for the shop caused entirely by request `A`'s failure clobbering request `B`'s success.

**Note on verification limits:** I was not able to execute this concurrency scenario against a live/test harness (no execution environment available in this analysis mode); the finding is based on static code-path analysis of the read-then-late-write pattern shown above, which is directly reachable from the standard `authenticate`/token-exchange middleware without any privileged access.

```typescript
import {Session} from '@shopify/shopify-api';

import {AppConfigInterface} from '../config-types';

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
}
```
