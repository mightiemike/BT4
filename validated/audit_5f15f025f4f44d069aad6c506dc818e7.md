## Title
Wallet Contract fails to refund the caller's attached deposit when the intermediate `storage_balance_of` / registrar lookup promise fails, permanently locking user funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

## Summary
The external report shows a contract that blindly assumes an ERC-20-like external call will always return in the expected format/succeed in the expected way, and when it doesn't (USDT), the operation just breaks. The nearcore analog is the NEAR Wallet Contract's Ethereum-emulation flow, which assumes its intermediate cross-contract calls (`storage_balance_of`, address-registrar `lookup`) always resolve so that the final callback can perform the deposit refund. When those intermediate calls fail, the caller's attached deposit is silently dropped instead of refunded, unlike the final `rlp_execute_callback`, which explicitly refunds on failure.

## Finding Description
`CallerDeposit` tracks a non-self caller's attached NEAR deposit so it can be refunded if the cross-contract action ultimately fails [1](#0-0) .

The final step of a normal action flow, `rlp_execute_callback`, correctly implements this refund when the underlying promise fails: [2](#0-1) 

However, for ERC-20 emulated transfers, the wallet contract first calls `storage_balance_of` on the NEP-141 token, then in `nep_141_storage_balance_callback` decides whether a `storage_deposit` is required before doing the actual `ft_transfer`: [3](#0-2) 

If that `storage_balance_of` promise fails (e.g. the target token does not implement NEP-145 storage management, is paused, runs out of gas, or otherwise reverts — directly analogous to USDT not conforming to the expected ERC-20 ABI), the callback simply returns an error response without refunding `caller_deposit`, even though `caller_deposit` is passed into the function precisely for this purpose: [4](#0-3) 

The same pattern exists in `address_check_callback`, used for EOA base-token transfers that require an address-registrar lookup. When the registrar promise fails, the caller's deposit is again dropped without refund: [5](#0-4) 

The relevant transaction-kind branches that create these intermediate promises (and thus can strand a `caller_deposit`) are in `inner_rlp_execute`: [6](#0-5) 

Because `has_in_flight_tx` is reset to `false` at the start of each callback (line 202, line 140) before deciding the outcome, and no refund promise is scheduled on the failure branch, the yoctoNEAR value in `attached_deposit` for that receipt is simply absorbed by the wallet contract's own balance — there is no code path that ever returns it to `caller_deposit.account_id`.

## Impact Explanation
Any relayer/caller who submits an RLP-encoded ERC-20 `transfer` (with a non-zero `fee`, causing `CallerDeposit::new` to populate) or an EOA base-token transfer with an `address_check`, and attaches a NEAR deposit as part of that call, permanently loses that deposit if the intermediate cross-contract call (`storage_balance_of` on the target NEP-141 token or `lookup` on the address registrar) fails for any reason — including interacting with a non-standard/incompatible token contract, exactly mirroring the "non-standard token breaks the standard flow" root cause from the report, but here resulting in permanently frozen funds rather than merely a revert.

## Likelihood Explanation
This is reachable by any ordinary transaction signer/relayer calling `rlp_execute` with an attached deposit on an ERC-20 emulated transfer targeting a NEP-141 token that does not fully implement NEP-145's `storage_balance_of` (or where that call otherwise fails), or when the address registrar lookup fails. No privileged access is required — a single crafted or unlucky transaction triggers the loss.

## Recommendation
Add the same deposit-refund logic used in `rlp_execute_callback` to the `PromiseResult::Failed` branches of both `address_check_callback` and `nep_141_storage_balance_callback`, i.e. schedule a `promise_batch_create` + `promise_batch_action_transfer` back to `caller_deposit.account_id` before returning the failure `ExecuteResponse`.

## Proof of Concept
1. A relayer submits an RLP transaction encoding an `ERC20_TRANSFER_SELECTOR` call targeting a NEP-141 token account that does not implement `storage_balance_of` (or where that call is made to fail, e.g. by targeting a non-existent/incompatible account), attaching a non-zero deposit and setting a non-zero `fee` so `CallerDeposit::new` populates.
2. `inner_rlp_execute` creates the `storage_balance_of` promise chained to `nep_141_storage_balance_callback` per [7](#0-6) .
3. The `storage_balance_of` call fails (`PromiseResult::Failed`).
4. `nep_141_storage_balance_callback` returns `ExecuteResponse{success: false, ...}` without issuing any refund promise, per [8](#0-7) .
5. The relayer's attached deposit remains in the wallet contract's balance permanently, with no mechanism to reclaim it.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
