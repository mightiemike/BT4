### Title
AddressRegistrar `register()` Permanently Locks Excess Attached Deposit on Successful Registration - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar::register` method, part of the NEAR Wallet Contract implementation, only validates that the attached deposit is *at least* the required storage cost, but on the success path (a new address→account mapping) it never refunds the excess over `required_deposit`. The collision path, by contrast, explicitly refunds the caller's *entire* deposit. This asymmetry means any caller who attaches more than the exact required amount when successfully registering a new address permanently loses the difference, with no withdrawal mechanism in the contract to recover it.

### Finding Description
`register()` computes `required_deposit` from the byte cost of storing the 20-byte address plus the account id, and panics if `given_deposit < required_deposit` [1](#0-0) . It never checks the upper bound. When the entry is `Vacant` (first-time, successful registration), the code inserts the mapping and returns without transferring back any surplus of `given_deposit` over `required_deposit` [2](#0-1) . By contrast, the `Occupied` (collision) branch explicitly creates a transfer promise refunding the *entire* `given_deposit` back to `env::predecessor_account_id()` since no storage was consumed [3](#0-2) .

This is structurally the same class of bug as the reported `nft_revoke` issue: a fund-movement/refund step that should be conditioned on the actual amount owed (here, `given_deposit - required_deposit`) is simply missing on one code path, while a sibling path shows the refund is understood to be the correct behavior. There is no `withdraw` or owner-recovery function anywhere in this contract [4](#0-3) , so any surplus becomes unrecoverable once accepted.

The contract is reachable directly by any unprivileged account via a plain `FunctionCall` transaction with an attached deposit (`#[payable]`), and is also invoked indirectly from `WalletContract::rlp_execute`/`inner_rlp_execute` when emulating Ethereum EOA transfers to eth-implicit addresses [5](#0-4) , so both direct RPC callers and relayers submitting Ethereum-emulated transactions can trigger this loss of funds path.

### Impact Explanation
Any account attaching more NEAR than the exact computed `required_deposit` on a successful (non-colliding) `register()` call permanently loses the excess amount: it is retained by the `AddressRegistrar` contract with no code path to withdraw or refund it. This satisfies the "permanently frozen funds" impact category, since the deposited value is irrecoverably locked from the perspective of the depositor.

### Likelihood Explanation
This is highly likely to be triggered accidentally in normal usage rather than requiring an attacker: any relayer or user who attaches a slightly generous or round-number deposit (a common practice to guarantee sufficient storage cost, since the exact byte cost calculation depends on account-id length) will overpay and lose the difference on every successful registration. No special privileges, timing, or race conditions are required — a single, ordinary transaction is sufficient.

### Recommendation
Compute the surplus (`given_deposit - required_deposit`) in the `Vacant` branch and issue a transfer promise refunding that surplus back to `env::predecessor_account_id()`, mirroring the refund logic already present in the `Occupied` branch, so only the exact storage cost is retained by the contract.

### Proof of Concept
1. Deploy the `AddressRegistrar` contract as done in the wallet contract test harness.
2. Call `register(account_id)` attaching a deposit noticeably larger than `storage_byte_cost() * (20 + account_id.len())` (e.g., a round number like 0.01 NEAR versus the few-hundred-yoctoNEAR-per-byte requirement).
3. Observe that the call succeeds (`Some(address)` returned) and the mapping is inserted, but the caller's account balance is decreased by the full attached deposit rather than just the computed `required_deposit` — confirmed by inspecting `register()`'s `Vacant` arm, which never emits any transfer promise back to the caller [2](#0-1) .
4. Contrast with calling `register()` a second time with a different `account_id` that hashes to the same address (collision) and the same excess deposit: here the *entire* deposit is refunded via `promise_batch_action_transfer`, confirming the intended refund behavior exists but is absent from the success path [6](#0-5) .

#[near_bindgen]
#[derive(PanicOnDefault, BorshDeserialize, BorshSerialize)]
#[borsh(crate = "near_sdk::borsh")]
pub struct AddressRegistrar {
    pub addresses: LookupMap<Address, AccountId>,
}

#[near_bindgen]
impl AddressRegistrar {
    #[init]
    pub fn new() -> Self {
        Self { addresses: LookupMap::new(StorageKey::Addresses) }
    }

    /// Computes the address associated with the given `account_id` and
    /// attempts to store the mapping `address -> account_id`. If there is
    /// a collision where the given `account_id` has the same address as a
    /// previously registered one then the mapping is NOT updated and `None`
    /// is returned. Otherwise, the mapping is stored and the address is
    /// returned as a hex-encoded string with `0x` prefix.
    #[payable]
    pub fn register(&mut self, account_id: AccountId) -> Option<String> {
        // It is not allowed to register eth-implicit accounts because the purpose
        // of the registry is to allow looking up the named account associated with
        // an address obtained via hashing, but eth-implicit accounts are already
        // parsable as addresses.
        if is_eth_implicit(&account_id) {
            let log_message = format!("Refuse to register eth-implicit account {account_id}");
            env::log_str(&log_message);
            return None;
        }

        // Must store the address and the account id
        let bytes_to_store = 20 + (account_id.len() as u128);
        let required_deposit =
            NearToken::from_yoctonear(env::storage_byte_cost().as_yoctonear() * bytes_to_store);
        let given_deposit = env::attached_deposit();
        // The caller must pay for the storage cost of registering.
        if given_deposit < required_deposit {
            let message = format!(
                "Insufficient deposit to cover storage cost. Given={} Expected={}",
                given_deposit.as_yoctonear(),
                required_deposit.as_yoctonear(),
            );
            env::panic_str(&message);
        }

        let address = account_id_to_address(&account_id);

        match self.addresses.entry(address) {
            Entry::Vacant(entry) => {
                let address = format!("0x{}", hex::encode(address));
                let log_message = format!("Added entry {} -> {}", address, account_id);
                entry.insert(account_id);
                env::log_str(&log_message);
                Some(address)
            }
            Entry::Occupied(entry) => {
                let log_message = format!(
                    "Address collision between {} and {}. Keeping the former.",
                    entry.get(),
                    account_id
                );
                env::log_str(&log_message);
                // Transfer the deposit back to the caller since no storage was updated.
                let refund_promise = env::promise_batch_create(&env::predecessor_account_id());
                env::promise_batch_action_transfer(refund_promise, given_deposit);
                None
            }
        }
    }

    /// Attempt to look up the account ID associated with the given address.
    /// If an entry for that address is found then the associated account id
    /// is returned, otherwise `None` is returned. Use the `register` method
    /// to add entries to the map.
    /// This function will panic if the given address is not the hex-encoding
    /// of a 20-byte array. The `0x` prefix is optional.
    pub fn lookup(&self, address: String) -> Option<AccountId> {
        let address = {
            let mut buf = [0u8; 20];
            hex::decode_to_slice(address.strip_prefix("0x").unwrap_or(&address), &mut buf)
                .unwrap_or_else(|_| env::panic_str("Invalid hex encoding"));
            buf
        };
        self.addresses.get(&address).cloned()
    }

    /// Computes the address associated with the given `account_id` and
    /// returns it as a hex-encoded string with `0x` prefix. This function
    /// does not update the mapping stored in this contract. If you want
    /// to register an account ID use the `register` method.
    pub fn get_address(&self, account_id: AccountId) -> String {
        let address = account_id_to_address(&account_id);
        format!("0x{}", hex::encode(address))
    }
}
