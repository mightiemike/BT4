No vulnerability found for this exploit question.

**Reasoning:**

The proposed attack chain does not hold up under inspection of the actual code paths:

1. **Per-version isolation of `EventAccumulatorSchema`.** Each version's event accumulator is built independently from scratch: `EventDb::put_events` calls `MerkleAccumulator::<EmptyReader, EventAccumulatorHasher>::append(&EmptyReader, 0, &event_hashes)` — i.e., `num_existing_leaves = 0` every time, with no cross-version reader. [1](#0-0)  The schema key is `(Version, Position)` encoded with `BigEndian` on the version first, so entries are strictly partitioned by version in key-space. [2](#0-1)  `EventStorePruner::prune_event_accumulator` only iterates and deletes rows where the version falls in `[begin, end)`, stopping as soon as it encounters a version `>= end`. [3](#0-2)  There is no mechanism for a crafted hash value to make the pruner touch a different version's rows, since the loop bound is purely the version field of the key, not any hash content.

2. **`ContractEvent::hash()` is a standard collision-resistant hash**, not an attacker-controlled value that can be "chosen" to collide with another version's accumulator node hash in any exploitable way; even a genuine collision would need to also collide with the SHA3-based `EventAccumulatorHasher` internal node hashing used by the Merkle accumulator, which is outside any realistic capability for "unprivileged input."

3. **Critically, the committed `event_root_hash` in `TransactionInfo` is never read back from `EventAccumulatorSchema`.** It is computed once at execution/commit time via `InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash()` and baked immutably into the `TransactionInfo` struct, which is itself hashed and included in the transaction accumulator (the ledger's authenticated Merkle tree). [4](#0-3)  All downstream verification of `event_root_hash` (e.g. `TransactionWithProof::verify`, `TransactionOutput::ensure_match_transaction_info`, `verify_events_against_root_hash`) independently recomputes the root from the raw `ContractEvent` list using `InMemoryEventAccumulator::from_leaves`, never by reading `EventAccumulatorSchema`. [5](#0-4) [6](#0-5) [7](#0-6) 

Since `EventAccumulatorSchema` is merely an on-disk cache used to serve individual-event inclusion proofs within a version (via `EventHashReader`) [8](#0-7) , and it is strictly partitioned per-version with no cross-version dependency, pruning an adjacent version range cannot corrupt a live version's accumulator entries, and even a hypothetical corruption of that cache would not change the already-committed, independently-verifiable `event_root_hash` baked into the transaction accumulator. The described exploit path is not realizable.

type Key = (Version, Position);

impl KeyCodec<EventAccumulatorSchema> for Key {
    fn encode_key(&self) -> Result<Vec<u8>> {
        let (version, position) = self;

        let mut encoded_key = Vec::with_capacity(size_of::<Version>() + size_of::<u64>());
        encoded_key.write_u64::<BigEndian>(*version)?;
        encoded_key.write_u64::<BigEndian>(position.to_inorder_index())?;
        Ok(encoded_key)
    }

    fn decode_key(data: &[u8]) -> Result<Self> {
        ensure_slice_len_eq(data, size_of::<Self>())?;

        let version_size = size_of::<Version>();

        let version = (&data[..version_size]).read_u64::<BigEndian>()?;
        let position = (&data[version_size..]).read_u64::<BigEndian>()?;
        Ok((version, Position::from_inorder_index(position)))
    }
