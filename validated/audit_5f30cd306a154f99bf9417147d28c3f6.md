### Title
Unhandled `EpochError` in `receipt_filter_fn` panics on stale `GlobalContractDistribution` receipt after static-resharding shard-layout changes - (File: runtime/runtime/src/congestion_control.rs)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` calls `.unwrap()` on the `Result` returned by `Receipt::receiver_shard_id`. For `GlobalContractDistribution` receipts, `receiver_shard_id` returns `Err(EpochError::ShardingError(...))` whenever the receipt's `target_shard` cannot be mapped forward into the current shard layout. `ShardLayout::resolve_to_current_shard` (the remapping function) only walks a *complete* split history for `ShardLayoutV3` (dynamic resharding); for legacy `V0/V1/V2` (static/protocol-version-driven resharding, still the default on most networks) it only checks one generation of children. This is a NULL/Option-analog to CVE-2020-35507's unguarded pointer dereference in untrusted-input parsing: unvalidated/attacker-influenced input (a delayed cross-shard receipt whose target shard has aged out) reaches an `.unwrap()` that the code base itself documents as capable of panicking.

### Finding Description
Any account can submit a `DeployGlobalContract` action, which produces a `GlobalContractDistribution` receipt carrying a fixed `target_shard` id: [1](#0-0) 

That receipt is routed by `Receipt::receiver_shard_id`, which for `GlobalContractDistribution` tries to remap an out-of-layout `target_shard` via `shard_layout.resolve_to_current_shard(target_shard)` and returns `Err(EpochError::ShardingError(..))` if no descendant shard exists in the current layout or its split history: [2](#0-1) 

That `Result` is consumed unguarded in `DelayedReceiptQueueWrapper::receipt_filter_fn`, used while popping receipts out of the delayed-receipt queue during `Runtime::apply`/`process_delayed_receipts`: [3](#0-2) 

```rust
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
```

The remapping helper `ShardLayout::resolve_to_current_shard` only has full multi-generation history for the newer `V3` layout format used by *dynamic* resharding: [4](#0-3) [5](#0-4) 

For legacy `V0/V1/V2` layouts (the "static resharding" model, driven purely by protocol-version upgrades — this is the model that has actually been used in production so far, and is the default absent an explicitly configured `ShardLayoutConfig::Dynamic`), `resolve_to_current_shard` falls back to `get_children_shards_ids`, which only walks **one** generation of splits:
```rust
Self::V0(_) | Self::V1(_) | Self::V2(_) => {
    self.get_children_shards_ids(shard_id).map(|c| c[0])
}
``` [6](#0-5) 

Consequently, if a `GlobalContractDistribution` receipt is delayed (kept in the on-chain delayed-receipt queue) across **two or more** legacy resharding events, its `target_shard` can no longer be resolved by either the current layout or a single-generation lookup, so `resolve_to_current_shard` returns `None`, `receiver_shard_id` returns `Err`, and `receipt_filter_fn`'s `.unwrap()` panics — crashing chunk application for every validator on that shard.

The codebase itself acknowledges this exact failure mode in a regression test, but the test is explicitly scoped to skip the assertion unless `DynamicResharding`/`V3` layouts are active, precisely because the fix (`resolve_to_current_shard`'s full split-history walk) "only works with V3 shard layouts. With static resharding, the shard layout doesn't maintain a full split history": [7](#0-6) [8](#0-7) 

The comment inside the test states directly: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in receipt_filter_fn() when receiver_shard_id() fails to remap the old target_shard after two resharding generations." This confirms the bug class is known, but the guard/fix has only been validated (and possibly only applies) under the V3/dynamic-resharding code path, leaving the legacy static-resharding path unverified/unpatched against the same panic.

### Impact Explanation
A panic inside `Runtime::apply` (via `process_delayed_receipts` → `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn`) is not caught as a soft error — it aborts the chunk-application thread deterministically on every honest validator processing that shard, because it happens inside the state-transition function itself. This is a transaction-triggered halt: an ordinary `DeployGlobalContract` transaction, combined with the receipt being stuck in the delayed queue while two protocol-version-driven shard splits occur on its target shard, causes every validator to crash while applying that shard's chunks, i.e., the chain for that shard stops making progress. This matches the required impact bar (a transaction-triggered halt of chunk application) and is directly analogous to the referenced CVE's unguarded-input-parsing crash.

### Likelihood Explanation
Reachability requires: (1) any account submitting a `DeployGlobalContract`/`UseGlobalContract` transaction (fully unprivileged), and (2) the resulting `GlobalContractDistribution` receipt being kept in the delayed-receipt queue (e.g. by congesting/saturating the target shard's compute budget, itself reachable by unprivileged senders as shown in the test harness) across two subsequent shard-layout changes on the legacy (non-V3) resharding path. Because static resharding is triggered automatically at protocol-version boundaries rather than by validator/operator action, and shard splits recur naturally over the life of the network, this is not merely a theoretical corner case — it is exactly the scenario the project's own regression test was written to catch, just left unverified for the non-dynamic-resharding code path.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` with proper error propagation (`Result`-returning filter used from a fallible `pop`), and extend `ShardLayout::resolve_to_current_shard` (or `receiver_shard_id`) to walk the full historical split chain for `V0/V1/V2` layouts as well — e.g. by threading in `get_shard_layout_history` the same way `ShardLayoutV3::derive_with_layout_history` already does for bootstrapping — so a `GlobalContractDistribution` receipt surviving multiple legacy resharding events resolves to a valid descendant shard instead of failing. Extend `test_stale_global_contract_distribution_after_double_resharding` to also run (and assert no panic) against the static/legacy resharding path.

### Proof of Concept
1. Configure a network using legacy static resharding (`ShardLayoutConfig::Static`, i.e. `V1/V2` shard layouts driven by protocol-version upgrades) — the default absent explicit dynamic-resharding configuration.
2. From an unprivileged account, submit a `DeployGlobalContract` transaction targeting an account on shard `S_A`, generating a `GlobalContractDistribution` receipt with `target_shard = S_A`.
3. Saturate the compute budget of shard `S_A` every block (as done in `test_stale_global_contract_distribution_after_double_resharding`, using ordinary `FunctionCall`/gas-burning transactions) so the distribution receipt is pushed into, and stays in, the delayed-receipt queue.
4. Trigger two successive protocol-version-driven shard splits that both affect `S_A` (or its descendant), matching the "two resharding generations" scenario described in the test.
5. Stop saturating and let the delayed queue drain; `process_delayed_receipts` pops the stale receipt, `receipt_filter_fn` calls `receiver_shard_id` → `resolve_to_current_shard` on the legacy layout, which cannot resolve past one generation, returns `Err`, and the `.unwrap()` in `congestion_control.rs:876` panics, halting chunk application on all validators tracking that shard.

*(Note: full end-to-end reproduction under the legacy/static resharding path specifically was not directly executed here; the existing test in the repo demonstrates the identical crash scenario is guarded against only for `V3`/dynamic resharding, and explicitly documents that the underlying remap primitive lacks full split history for `V0/V1/V2`, which is the basis for this finding.)*

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }
