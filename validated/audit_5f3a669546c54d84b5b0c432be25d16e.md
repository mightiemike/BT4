### Title
OAuth callback shop-parameter desync allows HMAC-validated query to differ from the query value actually used for the token exchange - ([File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts])

### Summary
In the OAuth `callback` handler, the `shop` query parameter is read twice using two different semantics on the same underlying multi-valued `URLSearchParams` object: once collapsed via `Object.fromEntries()` (which keeps the **last** occurrence of a duplicated key) for HMAC/state validation, and once via `URLSearchParams.get()` (which returns the **first** occurrence) for building the actual OAuth token-exchange request and the resulting session's `shop`. This mirrors the reported bug class — untrusted extra data appended alongside a validly-signed value is not rejected by a sanity check, and is silently consumed by a different code path than the one that validated the request.

### Finding Description
`callback()` parses the incoming query string into a `URLSearchParams` object: [1](#0-0) 

It then converts the params to a plain object for HMAC/state validation: [2](#0-1) 

`Object.fromEntries(query.entries())` silently collapses a repeated `shop` (or any repeated) key, keeping only the **last** value — there is no check that rejects duplicate/extra query parameters here (unlike the `appProxy` signator path, which explicitly rejects duplicates via `APP_PROXY_SINGLE_VALUE_PARAMS`): [3](#0-2) 

`validQuery` then validates HMAC and OAuth `state` strictly against this collapsed (last-value) object: [4](#0-3) 

However, immediately after validation succeeds, the code re-reads `shop` directly from the original `URLSearchParams` using `.get()`, which returns the **first** occurrence of a duplicated key — a different value than the one that was actually cryptographically validated: [5](#0-4) [6](#0-5) 

This value is used to build the access-token exchange URL and to construct the resulting `Session.shop`: [7](#0-6) 

Just as the RLP parser in the referenced report failed to verify that all input bytes were consumed — allowing attacker-appended bytes to ride along with a validly-signed transaction — this code fails to verify that the query string contains no extra/duplicate `shop` occurrences before using it, allowing an attacker-appended `shop=...` parameter to be smuggled past HMAC validation (which only "sees" the last value) while a different downstream consumer (`.get()`, which reads the first value) acts on the attacker-controlled value.

### Impact Explanation
An attacker who can influence or replay an OAuth callback URL for their own store's legitimate authorization redirect (e.g., a merchant/developer performing OAuth for their own shop, or observing a valid callback in transit/logs on a non-HTTPS or shared network) can insert an extra `shop` query parameter ahead of the genuine one. HMAC and `state` checks continue to pass because they operate on the same (last-value) `shop` that Shopify actually signed, while `cleanShop` — used to pick the shop domain that the resulting `Session` is attributed to and to build the `/admin/oauth/access_token` request URL — is taken from the first (attacker-controlled) value. This value confusion can misattribute which shop a session record is created/keyed for, or route the token-exchange POST to an attacker-chosen host, depending on how the OAuth authorization `code` behaves for a mismatched shop domain on Shopify's side. At minimum it represents a validation/consumption desync in an unprivileged, internet-reachable authentication handler.

### Likelihood Explanation
Exploitation requires the attacker to control or tamper with the OAuth callback URL for a legitimately-signed request (e.g., via a redirect they influence, a proxy, browser history/log leakage, or their own OAuth flow on their own shop) and to correctly craft a duplicate `shop` parameter that still lands as the "last" value expected by the HMAC check. This is a real gap (no duplicate-parameter rejection on the admin/OAuth path, only present for `appProxy`), but the practical severity depends on how Shopify's `/admin/oauth/access_token` endpoint validates the authorization `code` against the shop passed in the request — this callchain could reject a shop/code mismatch, limiting full impact to failed exchanges (DoS/error) rather than always a full account/session takeover. This nuance could not be fully confirmed from the codebase alone since token-code binding is enforced server-side by Shopify's OAuth service, outside of this repository.

### Recommendation
- Reject any query containing duplicate/repeated single-value parameters (`shop`, `hmac`, `code`, `state`, `timestamp`) in the admin OAuth `callback` path, the same way `APP_PROXY_SINGLE_VALUE_PARAMS` is already enforced for `appProxy` in `normalizeQuery` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts`).
- Ensure a single canonical parsing of the query (e.g., always `Object.fromEntries(query.entries())`) is used consistently everywhere `shop`, `code`, and `state` are read in `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`, instead of mixing `URLSearchParams.get()` (first-value semantics) with `Object.fromEntries()` (last-value semantics).

### Proof of Concept
Conceptual (not fully verified end-to-end against Shopify's OAuth server, per Likelihood note above):
1. Obtain/observe a legitimately Shopify-signed OAuth callback URL for `victim-shop.myshopify.com`: `.../callback?shop=victim-shop.myshopify.com&code=<code>&state=<state>&timestamp=<ts>&hmac=<valid-hmac>`.
2. Craft: `.../callback?shop=attacker-shop.myshopify.com&shop=victim-shop.myshopify.com&code=<code>&state=<state>&timestamp=<ts>&hmac=<valid-hmac>`.
3. `Object.fromEntries(query.entries())` collapses `shop` to `victim-shop.myshopify.com` (last value) → HMAC/state validation passes (`validQuery` in `oauth.ts` lines 242-255).
4. `query.get('shop')` returns `attacker-shop.myshopify.com` (first value) → used for `cleanShop`, the token-exchange URL, and the resulting `Session.shop` (`oauth.ts` lines 194-217), diverging from the value that was actually validated.

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }
