## Finding: Replay-verify comparator silently ignores state-checkpoint root hashes [1](#0-0) 

### Title
Replay-verify / backup-verify skips state-checkpoint (Merkle root) comparison, allowing a diverged state tree to be reported as verified - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` — the comparator used by chunk-executor replay verification and CLI/backup verify tooling — checks only `status`, `gas_used`, the write-set hash, and the event-root hash against the recorded `TransactionInfo`. It does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [2](#0-1) , even though these fields represent the JMT/state Merkle roots that are supposed to be authenticated inside `TransactionInfo` and bound into the transaction accumulator/ledger info. The code contains a self-admitted TODO acknowledging exactly this: "this comparator ignores the checkpoint hashes ... so replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution" [3](#0-2) .

### Finding Description
`ensure_match_transaction_info` is invoked by `ChunkExecutorInner::verify_execution`, which is the real verification step used when replaying transactions from a backup/chunk during restore (`remove_and_replay_epoch` → `verify_execution`) [4](#0-3) , as well as by CLI replay tooling [5](#0-4)  and the debugger's mismatch printer [6](#0-5) .

This comparator is meant to guarantee that locally re-executed transactions reproduce the exact `TransactionInfo` that was cryptographically committed to the ledger (i.e., whose hash is a leaf in the transaction accumulator secured by validator signatures). However, since the function skips the `state_checkpoint_hash` (and hot/position variants) fields, any divergence in the *state Merkle root* computed by local re-execution vs. the authenticated `TransactionInfo` goes completely undetected — as long as gas, status, write-set bytes, and events happen to match. This can occur if:
- A backup/restore data source supplies a `TransactionInfo` whose `state_checkpoint_hash` doesn't actually correspond to the state written into the target DB's Jellyfish Merkle Tree (e.g., truncated/corrupted snapshot, or state store bug in `do_state_checkpoint.rs`).
- Bugs in state-checkpoint/JMT root computation (`execution/executor/src/workflow/do_state_checkpoint.rs`) cause a silently wrong root to be computed and persisted, since replay-verify — the safety net meant to catch this class of bug — does not check it.

### Impact Explanation
The state-checkpoint hash is the authenticated binding between a `TransactionInfo` (proven via the accumulator/ledger-info signatures) and the actual state Merkle tree persisted to storage. If replay-verify tooling omits this check, a restored/replayed node can end up with a state tree that is internally consistent for write-set/events/gas but has a Merkle root that diverges from what was actually authenticated on-chain, while the tool reports success. This falls squarely in the "Proof And Storage Pivots" category: restore/replay paths must not let committed data be reinterpreted into a different ledger state, and the position/hot-state root proof binding must be preserved. A node bootstrapped or verified this way could serve state proofs, `get_state_value_with_proof_by_version` responses, or a locally-served merkle root that is wrong for that version yet passes all available integrity tooling, which is a high-impact state-integrity gap.

### Likelihood Explanation
This is not an attacker-triggered exploit in the traditional sense (no privileged assumptions needed) — it's a structural gap in a security-critical verification tool. Any bug or divergence in the underlying JMT/state-checkpoint computation, or any backup source that is not perfectly trustworthy, will not be caught by `verify_execution`/`ensure_match_transaction_info`. The gap is explicitly documented in-code by the developers as an unresolved TODO, confirming both the existence and the awareness of the broken invariant, but it remains unfixed at HEAD.

### Recommendation
Extend `TransactionOutput::ensure_match_transaction_info` (or the state-checkpoint-aware caller) to also validate `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` against the values actually produced by `DoStateCheckpoint` for the corresponding version(s), before treating a replayed/restored chunk as verified. At minimum, `ChunkExecutorInner::verify_execution` should be updated to pass in and check the locally computed checkpoint hashes rather than relying solely on `ensure_match_transaction_info`'s narrower comparison.

### Proof of Concept
1. Take (or construct) a backup/chunk whose `TransactionInfo.state_checkpoint_hash` does not match the actual Merkle root that would result from applying its `write_set` to the target DB's Jellyfish Merkle Tree (e.g., due to a JMT computation bug, or an adversarial/corrupted backup source), while keeping `gas_used`, `status`, write-set bytes, and events self-consistent.
2. Feed this chunk through `TransactionRestoreBatchController`/`ChunkExecutorInner::remove_and_replay_epoch` with `VerifyExecutionMode::should_verify() == true`.
3. `verify_execution` calls `ensure_match_transaction_info`, which only compares status/gas/write-set-hash/event-root, all of which match — so verification succeeds despite the state Merkle root divergence [7](#0-6) .
4. The chunk is committed as "verified," leaving the local state tree's root diverged from the authenticated on-chain root for that version, with no verification-time detection.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

    fn verify_execution(
        &self,
        transactions: &[Transaction],
        persisted_aux_info: &[PersistedAuxiliaryInfo],
        transaction_infos: &[TransactionInfo],
        write_sets: &[WriteSet],
        event_vecs: &[Vec<ContractEvent>],
        begin_version: Version,
        end_version: Version,
        verify_execution_mode: &VerifyExecutionMode,
    ) -> Result<Version> {
        // Execute transactions.
        let parent_state = self.commit_queue.lock().latest_state().clone();
        let state_view = self.state_view(parent_state.latest())?;
        let txns = transactions
            .iter()
            .take((end_version - begin_version) as usize)
            .cloned()
            .map(|t| t.into())
            .collect::<Vec<SignatureVerifiedTransaction>>();

        let auxiliary_info = persisted_aux_info
            .iter()
            .take((end_version - begin_version) as usize)
            .map(|persisted_aux_info| AuxiliaryInfo::new(*persisted_aux_info, None))
            .collect::<Vec<_>>();
        let onchain_config = chunk_onchain_config(&state_view)?;
        let execution_output = DoGetExecutionOutput::by_transaction_execution::<V>(
            &V::new(),
            txns.into(),
            auxiliary_info,
            &parent_state,
            state_view,
            onchain_config,
            TransactionSliceMetadata::chunk(begin_version, end_version),
        )?;
        // not `zip_eq`, deliberately
        for (version, txn_out, txn_info, write_set, events) in multizip((
            begin_version..end_version,
            &execution_output.to_commit.transaction_outputs,
            transaction_infos.iter(),
            write_sets.iter(),
            event_vecs.iter(),
        )) {
            if let Err(err) = txn_out.ensure_match_transaction_info(
                version,
                txn_info,
                Some(write_set),
                Some(events),
            ) {
                return if verify_execution_mode.is_lazy_quit() {
                    error!("(Not quitting right away.) {}", err);
                    verify_execution_mode.mark_seen_error();
                    Ok(version + 1)
                } else {
                    Err(err)
                };
            }
        }
        Ok(end_version)
    }
