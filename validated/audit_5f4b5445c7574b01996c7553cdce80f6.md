### Title
Unchecked non-existent `beneficiary_id` on `DeleteAccountAction` permanently burns the deleted account's balance - (File: runtime/runtime/src/actions.rs)

### Summary
The external report's bug class is "a privileged/critical address-like parameter is accepted without existence/zero-value validation, causing accidental and irreversible loss of value." The closest reachable analog in nearcore is `DeleteAccountAction::beneficiary_id`: the runtime only checks that the id is *syntactically* a valid `AccountId`, never that the beneficiary account *exists*. Any unprivileged transaction signer who deletes their own account with a mistyped, stale, or otherwise non-existent (but syntactically valid) `beneficiary_id` causes the account's entire remaining balance to be irreversibly burned rather than refunded to anyone.

### Finding Description
`action_delete_account` in `runtime/runtime/src/actions.rs` unconditionally builds a balance-refund receipt addressed to `delete_account.beneficiary_id` whenever the account being deleted has a non-zero balance, then removes the account and clears its state — with no check that the beneficiary account exists: [1](#0-0) 

The only validation performed on `beneficiary_id` anywhere in the pipeline is that it is a syntactically valid `AccountId` string (documented in the actions spec as returning `InvalidAccountId` only for malformed ids): [2](#0-1) 

The refund receipt created by `Receipt::new_balance_refund` is a system-predecessor "refund" receipt. Per the runtime-execution spec, refund receipts are free (no gas charged) — and critically, **if a refund receipt fails (e.g., because the target account does not exist), its deposit is burned into `other_burnt_amount` instead of being returned to anyone**: [3](#0-2) 

This is confirmed by the test `refund_may_not_create_universal_account`, which explicitly demonstrates that a balance-refund receipt targeting a nonexistent account fails with `AccountDoesNotExist` and does **not** create the account or return the funds anywhere — the deposit is simply lost: [4](#0-3) 

A companion test (`delete_after_init_removes_account`) explicitly notes in its own comments that the beneficiary "has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" — i.e., the test authors are aware that a nonexistent beneficiary silently destroys the funds, and they work around it by pre-creating the beneficiary account rather than the runtime rejecting the action: [5](#0-4) 

This exactly mirrors the reported bug class: a privileged/critical target parameter (`beneficiary_id`, analogous to `_userAddress`) is accepted with only superficial format validation and no "does this target actually exist / is this the intended value" check, so a user error (typo, stale wallet-cached account id, front-end omission/defaulting) leads to unrecoverable loss of value instead of a revert.

### Impact Explanation
Any transaction signer who submits a `DeleteAccountAction` with a `beneficiary_id` that is syntactically valid but does not correspond to an existing account permanently and silently burns their entire remaining account balance — this is a real, transaction-triggered loss of funds for the unprivileged signer who called the action, with no recourse. Because `DeleteAccountAction` is reachable by any full-access-key holder for their own account, and no simulation/dry-run mechanism forces beneficiary-existence checking before submission, ordinary user error (e.g., copy-pasting a wrong account id, a relayer/front-end supplying an unvalidated or default value, or targeting an account that was deleted between when the UI fetched it and when the transaction executed) results in concrete, permanent value destruction. This satisfies the "permanently frozen/lost funds" impact criterion.

### Likelihood Explanation
Likelihood is meaningfully high for a client-side/human error scenario: `beneficiary_id` is a plain user-supplied `AccountId` string, and nothing in transaction construction, wallet UX, or the runtime validation path cross-checks its existence before the delete is finalized. Since the delete itself succeeds and only the *refund* silently fails and burns, the signer receives no explicit "beneficiary invalid" error to catch the mistake pre-submission (contrast with `InvalidAccountId` which *is* caught for malformed strings). This is analogous to the reported Solidity issue where a missing-address transaction is technically well-formed but semantically wrong, and succeeds while destroying value.

### Recommendation
Before creating the refund receipt in `action_delete_account`, verify that `delete_account.beneficiary_id` actually exists in state (not merely that it's a syntactically valid `AccountId`), and reject the `DeleteAccount` action (e.g. with a new `ActionErrorKind::BeneficiaryAccountDoesNotExist`) if it does not. Alternatively, disallow refund receipts from silently burning value on `AccountDoesNotExist` and instead route unspendable refunds to a well-defined fallback (e.g., back to the deleting account's predecessor/actor, or to the protocol treasury) rather than `other_burnt_amount`.

### Proof of Concept
1. Create account `alice.near` with a nonzero balance and a full-access key.
2. Submit a transaction from `alice.near` containing a single `DeleteAccountAction { beneficiary_id: "nonexistent999.near" }`, where `nonexistent999.near` is syntactically valid but was never created.
3. `action_delete_account` (`runtime/runtime/src/actions.rs:380-386`) creates a `Receipt::new_balance_refund` for `alice.near`'s full balance addressed to `nonexistent999.near`, then deletes `alice.near`.
4. The refund receipt executes against `nonexistent999.near`; per `refund_may_not_create_universal_account` (`runtime/runtime/src/tests/apply.rs:6882-6926`), a refund to a missing account fails with `AccountDoesNotExist` and does not create the account.
5. Per the runtime-execution spec (`protocol-model/spec/runtime-execution.md:66-69`), the failed refund's deposit is burned into `other_burnt_amount` instead of being returned to `alice.near` or anyone else — the entire balance is permanently lost.
