This confirms the analog: NEAR's deterministic accounts (NEP-616) are documented as having "fixed code" bound into their address derivation, but when `DeterministicAccountStateInitV1.code` uses `GlobalContractIdentifier::AccountId(id)` (the "AccountId" deploy mode), the actual bytecode is a mutable pointer controlled by whoever owns `id` — analogous to `UXDController.setRedeemable`, where the "fixed" reference (redeemable token) can silently be swapped by a party the depositor doesn't control, endangering already-deposited funds.

### Title
Deterministic accounts using `GlobalContractIdentifier::AccountId` code reference lose their "fixed code" guarantee, letting the global-contract owner rewrite code and steal deposited funds - (File: `runtime/runtime/src/global_contracts.rs`, `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
A deterministic account's id is derived by hashing its `DeterministicAccountStateInit` (code + initial data), which is advertised as giving the account "fixed code and fixed initial state" [1](#0-0) . However, when the `code` field is a `GlobalContractIdentifier::AccountId(id)` rather than `CodeHash`, the commitment only binds to the *identifier* (the owning account id), not to the bytecode itself. The bytecode behind an `AccountId`-mode global contract is explicitly mutable by its owner at any time via a new `DeployGlobalContractAction`, and the docs state this plainly: `AccountId` mode "allows the owner to update the contract for all its users" [2](#0-1) .

### Finding Description
`action_deploy_global_contract` lets any account owning `deploy_account_id` overwrite the code stored at `TrieKey::GlobalContractCode { identifier: GlobalContractIdentifier::AccountId(...) }` [3](#0-2) . Any account (including a deterministic account) that references that identifier resolves its executable code dynamically at call time through `RuntimeContractIdentifier::resolve`, which looks up the current global contract code rather than a fixed hash pinned at account-creation time [4](#0-3) .

A deterministic account is created via `DeterministicStateInitAction`, whose validation only checks that the receiver id equals `derive_near_deterministic_account_id(state_init)` — a hash over the borsh-encoded `DeterministicAccountStateInit`, which for `AccountId` mode encodes only the owner account id, not the actual code bytes [5](#0-4) [6](#0-5) . `deploy_deterministic_account` calls `use_global_contract`, which sets `AccountContract::GlobalByAccount(id)` on the account — a live pointer, not a snapshot [5](#0-4) [7](#0-6) .

This mirrors the `setRedeemable` pattern: a value that participants trust to be immutable (the redeemable token / the deterministic account's code) is actually re-pointable post-hoc by a privileged-but-unrelated third party (the contract owner / the global-contract deployer), and users who deposited funds into the entity relying on that reference have no recourse.

### Impact Explanation
A user can inspect the code referenced by a `GlobalContractIdentifier::AccountId` at the time they compute/derive a deterministic account id, verify it is safe (e.g., an escrow/vesting contract that only allows withdrawal by a specific key), and deposit funds into that deterministic account. After the deposit, the account that owns the referenced global contract identifier can call `DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` again to replace the code with malicious logic (e.g., code that transfers the account's own balance to an attacker-controlled address on any function call). Since the deterministic account's contract execution now runs under the new, arbitrary code with full authority over that account's own balance and storage, this results in a concrete unauthorized value movement/loss of the deposited funds — the deterministic account's promised "fixed code" invariant is violated in a way that is directly reachable by ordinary transactions from any two unprivileged accounts (the global-contract deployer and the depositor), without any protocol-level warning that the code can change post hoc.

### Likelihood Explanation
Likelihood is high in any deployment where a deterministic account is created referencing an `AccountId`-mode global contract that the depositor does not themselves control (e.g., a shared/third-party utility contract advertised as a deterministic-account "factory" template). The mutation path (`DeployGlobalContractAction`) is a normal, unprivileged transaction action available to any account, requiring only enough balance to pay for the new code's storage [8](#0-7) , and no additional confirmation or timelock gates a redeploy that affects all already-created deterministic (or regular) accounts using that identifier — this is demonstrated intentionally in `test_global_contract_update`, where redeploying an `AccountId`-mode contract changes behavior for all existing "using" accounts [9](#0-8) .

### Recommendation
For deterministic accounts (and more generally for any account relying on an immutability guarantee derived from a hash commitment), require `DeterministicAccountStateInitV1.code` to be restricted to `GlobalContractIdentifier::CodeHash` only, rejecting `AccountId`-mode references at `DeterministicStateInitAction` validation time. If `AccountId` mode must remain supported for deterministic accounts, the derived account id must additionally commit to the current code hash resolved at creation time (pinning it as `CodeHash` internally), or the protocol must clearly document and enforce that deterministic accounts built on `AccountId`-mode contracts are not, in fact, tamper-proof, and provide a way for depositors to detect/react to a subsequent contract-owner redeploy before funds are placed at risk.

### Proof of Concept
1. Account `owner.near` deploys a global contract in `AccountId` mode containing benign escrow logic via `DeployGlobalContractAction { deploy_mode: AccountId }` (see `test_global_contract_update` setup) [10](#0-9) .
2. `alice.near` computes `state_init = DeterministicAccountStateInitV1 { code: GlobalContractIdentifier::AccountId("owner.near"), data: {...} }`, derives `det_account = derive_near_deterministic_account_id(state_init)`, and sends `DeterministicStateInitAction` with a deposit to create/fund `det_account`, as shown in the test helper `new_deterministic_account_with_data` [11](#0-10) .
3. After `det_account` has accumulated balance, `owner.near` issues another `DeployGlobalContractAction { deploy_mode: AccountId }` overwriting the code stored under `owner.near`'s global-contract identifier with malicious code that transfers the caller's own balance to an attacker address on function call, per `action_deploy_global_contract`/`initiate_distribution` semantics [3](#0-2) .
4. Any subsequent `FunctionCall` receipt into `det_account` resolves via `RuntimeContractIdentifier::resolve` to the newly deployed malicious code (since resolution is dynamic, not pinned) [4](#0-3) , executing with `det_account`'s balance and draining the funds `alice.near` deposited, despite `det_account`'s id having been derived to supposedly commit to fixed, verified code.

    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {

            account_id: account_id.clone(),

        .into());
        return Ok(());

        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}

    pub(crate) fn resolve(
        account_id: &AccountId,
        account_contract: AccountContract,
        state_update: &TrieUpdate,

            }
            Err(ContractIsLocalError::NotDeployed) => return Ok(RuntimeContractIdentifier::None),

            // Accounts that look like eth implicit accounts and have existed prior to the
            // eth-implicit accounts protocol change (these accounts are discussed in the
            // description of #11606) may have something else deployed to them. Only return
            // something here if the accounts have a wallet contract hash. Otherwise use the
            // regular path to grab the deployed contract.
            if LegacyEthWallet::resolve(local_hash).is_some() {
                // ETH implicit wallet accounts use global contracts, including
                // those created in old protocol versions.
                let global_hash = eth_wallet_global_contract_hash(chain_id);
                return Ok(RuntimeContractIdentifier::Global {
                    code_hash: global_hash,
                    identifier: GlobalContractIdentifier::CodeHash(global_hash),
                });
            }
        }

        Ok(RuntimeContractIdentifier::AccountLocal {
            code_hash: local_hash,
            account_id: account_id.clone(),
