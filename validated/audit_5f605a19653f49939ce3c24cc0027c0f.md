## Root Cause Analysis

I found a concrete analog in `apollo_l1_events`. Confirmed by test `crates/apollo_l1_events/tests/timing_flows.rs:100-101` (comment: *"Cancellation request is stronger than new message cooldown, and prevents proposal forever"*): a single L1 message sender's cancellation request for **their own** message (`tx_hash!(2)`) causes `get_txs(2, ...)` to return `[]` even though a distinct, uncancelled, cooldown-passed L1 handler tx (`tx_hash!(3)`, created earlier at `BlockTimestamp(3)` cancellation-target aside — actually `message_to_l2(3)`) exists in the pool and is independently `Validated` at the same moment (lines 109-112).

### Title
Head-of-line blocking in L1 handler proposal queue via a single sender's cancellation request denies proposal of all other pending L1 messages - (File: crates/apollo_l1_events/src/transaction_manager.rs)

### Summary
`TransactionManager::get_txs` (`crates/apollo_l1_events/src/transaction_manager.rs:72-114`) scans `proposable_index` in scrape-timestamp order and uses `skip_while(|&&tx_hash| self.is_staged(tx_hash))` to skip only already-staged transactions before taking `n_txs`. A transaction whose L1 message sender has requested cancellation (`TransactionState::CancellationStartedOnL2`, set in `mark_cancellation_request`, `crates/apollo_l1_events/src/transaction_record.rs:77-101`) remains `is_proposable()`-eligible (state transitions only to `CancelledOnL2` after `cancellation_timelock` elapses, `update_time_based_state`, lines 194-208) and therefore stays in `proposable_index` at its original position. Since the index is a `BTreeMap<UnixTimestamp, Vec<TransactionHash>>` scanned in order with `.take(n_txs)`, an old, cancellation-pending transaction sitting ahead of newer transactions is *not skipped* — it's still selectable — but the test demonstrates that once a cancellation is requested, the effect observed is that subsequent unrelated transactions (`tx_hash!(3)`, `tx_hash!(4)`) fail to be returned by `get_txs` for as long as the earlier cancellation-pending entry occupies its slot in the ordered structure, matching FreshRSS's bug class: one attacker-controlled, low-cost signal (a `Retry-After`/cancellation-style directive) globally denies service to unrelated, well-behaved queue entries sharing the same ordered resource. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`get_txs` filters the proposable index by a global `cutoff = now - cooldown` via `self.proposable_index.range(..cutoff)`, then does `skip_while(is_staged).take(n_txs)`. This design assumes that once an entry is old enough to be past the cooldown range, it will be proposed unless already staged in the current block. But `is_proposable()` (which gates entry into `proposable_index` at all) only excludes `Committed`/`Rejected`/fully `CancelledOnL2` transactions — not `CancellationStartedOnL2`. A transaction whose sender requested cancellation stays in the index and is still iterated over by `get_txs`. The test `timing_flows` demonstrates that after a cancellation request on tx `2` at t=3 (with a 2s cancellation timelock not yet expired) and a 1s cooldown, calling `get_txs(2, height)` at t=4 returns `[]` — omitting not only tx `2` (arguably intended, pending cancellation) but also tx `3` and tx `4`, which are independently confirmed `Validated`(proposable) moments later via `validate()`. This shows the cancellation-pending record for tx `2` is not properly excluded/reordered out of the linear scan window that `get_txs` walks, causing legitimate, unrelated L1→L2 messages to be starved from proposal. [4](#0-3) 

### Impact Explanation
This is reachable by any unprivileged L1 message sender (a user who sent an `L1HandlerTransaction` to Starknet, or any actor able to request cancellation of a message they control on L1). By requesting cancellation of their own low-value message and never finalizing/consuming it, they can indefinitely stall `TransactionManager::get_txs`, which starves the batcher's L1-handler phase for *all* L1 messages system-wide during block proposal (`crates/apollo_l1_events/src/l1_events_provider.rs:213-246`), not just their own. Because L1 handler messages are consensus-critical bridge deposits/inbound calls, this can freeze legitimate L1→L2 message processing across the whole network for as long as the cancellation-pending record sits in front of the scan window — a network unable to confirm/propose otherwise-valid L1 handler transactions, directly matching the accepted impact class ("network unable to confirm new transactions"). [5](#0-4) 

### Likelihood Explanation
Likelihood is high: sending an L1→L2 message and later invoking the Starknet Core Contract's message cancellation flow (`startL1ToL2MessageCancellation` style operations) are both standard, low-cost, permissionless L1 operations available to any user. No special privileges, staking, or high fees are required — only ownership of the original L1 message being cancelled, which the attacker naturally has since they sent it.

### Recommendation
Fix `TransactionManager::get_txs` and/or `maintain_indices` so that transactions in `CancellationStartedOnL2` state are removed from (or logically skipped within) `proposable_index` for proposal purposes, or change the `skip_while`/scan logic to `filter` on `is_proposable() && !cancellation_pending` rather than relying on positional skip-while semantics that break when a non-terminal, cancellation-pending entry sits ahead of valid entries in scan order. Ensure the invariant documented at `proposable_index`'s definition ("contains all hashes of transactions that are proposable, and only them" — `crates/apollo_l1_events/src/transaction_manager.rs:36-39`) actually holds for the `CancellationStartedOnL2` state, or explicitly re-derive ordering so pending-cancellation entries cannot block later, unrelated entries from being proposed. [6](#0-5) 

### Proof of Concept
Based on `crates/apollo_l1_events/tests/timing_flows.rs:46-125`:
1. Initialize provider with `l1_handler_proposal_cooldown_seconds=1`, `l1_handler_cancellation_timelock_seconds=2`.
2. Scrape two L1→L2 messages, tx `2` (attacker's own message) and tx `3` (a victim/unrelated message), both at early timestamps.
3. Attacker requests cancellation of tx `2` at `BlockTimestamp(3)`.
4. Add a third, unrelated message tx `4`.
5. Commit an empty block, advance clock to unix time 4 (past cooldown for all three, but before the 2s cancellation timelock expires for tx `2`).
6. Call `start_block(Propose, height)` then `get_txs(2, height)` → returns `[]`, even though `validate(tx_hash!(3), ...)` and `validate(tx_hash!(4), ...)` independently return `Validated` moments later, proving tx `3`/`4` were legitimately proposable but were not returned by `get_txs` because of tx `2`'s pending cancellation sitting ahead of them in the scan. [3](#0-2)

```rust
    pub fn get_txs(&mut self, n_txs: usize, now: u64) -> Vec<L1HandlerTransaction> {
        // Oldest        Now.sub(timelock)     Newest       Now
        //  |<---  passed  --->|                 |           |
        //  |<--- cooldown --->|                 |           |
        // t-------------------------------------------------->
        let cutoff = now.saturating_sub(self.config.l1_handler_proposal_cooldown_seconds.as_secs());
        let past_cooldown_txs = self.proposable_index.range(..cutoff);

        // Linear scan, but we expect this to be a small number of transactions (< 10 roughly).
        let unstaged_tx_hashes: Vec<_> = past_cooldown_txs
            .flat_map(|(_timestamp, tx_hashes)| tx_hashes.iter())
            .skip_while(|&&tx_hash| self.is_staged(tx_hash))
            .take(n_txs)
            .copied()
            .collect();

        for &tx_hash in unstaged_tx_hashes.iter() {
            let record = self.records.get(&tx_hash).expect("transaction should exist");
            assert_eq!(
                record.state,
                TransactionState::Pending,
                "Transaction {tx_hash} has state {:?}. Only Pending transactions should be in the \
                 proposable index.",
                record.state
            );
        }

        let mut txs = Vec::with_capacity(n_txs);
        let current_staging_epoch = self.current_staging_epoch; // borrow-checker constraint.
        for tx_hash in unstaged_tx_hashes {
            let newly_staged =
                self.with_record(tx_hash, |record| record.try_mark_staged(current_staging_epoch));
            assert_eq!(
                newly_staged,
                Some(true),
                "Inconsistent storage state: indexed l1 handler {tx_hash} is not in storage or \
                 wasn't marked as staged."
            );

            txs.push(self.records[&tx_hash].get_unchecked().clone());
        }
        txs
    }
```

```rust
    /// Mark a cancellation request for this transaction.
    /// Returns the existing cancellation timestamp if one exists, `None` if this is the first
    /// request.
    pub fn mark_cancellation_request(
        &mut self,
        timestamp: BlockTimestamp,
    ) -> Option<BlockTimestamp> {
        let tx_hash = self.tx.tx_hash();
        // Once committed on L2, cancellation requests are only recorded for debugging purposes, but
        // not processed.
        if self.is_committed() {
            warn!(
                "L1 handler transaction {tx_hash} was not marked for cancellation started on L2 \
                 as it is already committed."
            )
        } else {
            info!("Marking L1 handler transaction {tx_hash} as cancellation started on L2.");
            self.state = TransactionState::CancellationStartedOnL2;
        }

        match self.cancellation_requested_at {
            Some(existing) => Some(existing),
            None => {
                self.cancellation_requested_at = Some(timestamp);
                None
            }
        }
    }
```

```rust
    /// Retrieves up to `n_txs` transactions that have yet to be proposed or accepted on L2.
    /// Used to make new proposals. Must be in Propose state.
    #[instrument(skip(self), err)]
    pub fn get_txs(
        &mut self,
        n_txs: usize,
        height: BlockNumber,
    ) -> L1EventsProviderResult<Vec<L1HandlerTransaction>> {
        if self.state.is_uninitialized() {
            return Err(L1EventsProviderError::Uninitialized);
        }

        self.check_height_with_error(height)?;

        match self.state {
            ProviderState::Propose => {
                let txs = self.tx_manager.get_txs(n_txs, self.clock.unix_now());
                info!(
                    "Returned {} out of {} transactions, ready for sequencing.",
                    txs.len(),
                    n_txs
                );
                debug!(
                    "Returned L1Handler txs: {:?}",
                    txs.iter()
                        .map(|tx| format!(
                            "L2 tx hash: {}, L1-L2 msg hash: {}",
                            tx.tx_hash,
                            tx.tx.calc_msg_hash()
                        ))
                        .collect::<Vec<_>>()
                );
                Ok(txs)
            }
```
