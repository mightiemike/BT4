### Title
Legacy (default) TRC10 Exchange bancor math uses floating-point `Math.pow`, causing rounding-corrupted token accounting on `ExchangeTransactionContract` - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The default (non-hardened) TRC10 Exchange price computation in `ExchangeProcessor` performs the bancor-formula relay/exchange math using `double`-precision `Math.pow`/`Maths.pow`, instead of the exact `BigDecimal` arithmetic used by `SafeExchangeProcessor`. This mirrors the AaveV3 `supplyTokenTo()` bug class: a division/rounding step produces a credited amount that is not exactly reconcilable with the true proportional value, so users transferring in tokens can receive a mis-rounded amount of the counter-token, and the pool balances used for the next trade's ratio drift away from the exact invariant.

### Finding Description
`ExchangeCapsule.transaction()` selects the arithmetic engine based on the `hardenedCalc` flag: `SafeExchangeProcessor.INSTANCE` when true, or a plain `ExchangeProcessor` otherwise [1](#0-0) . `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` gate the "hardened"/exact path behind `dynamicStore.allowHardenExchangeCalculation()`, exposed via `AbstractExchangeActuator.allowHarden()` [2](#0-1) , which is a committee-controlled proposal parameter (default state cannot be confirmed from the index, but the codebase explicitly retains a "legacy vs hardened" code path and test suite for it) [3](#0-2) .

The legacy `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute `-supply * (1.0 - Math.pow(1 + quant/newBalance, 0.0005))` and `balance * (Math.pow(1 + supplyQuant/supply, 2000.0) - 1.0)` entirely in `double` precision, then truncate to `long` via a direct cast [4](#0-3) . `SafeExchangeProcessor` performs the same formula with `BigDecimal` at 18-digit scale and `RoundingMode.HALF_UP`, and the project's own test explicitly proves the two engines diverge: `Assert.assertNotEquals(anotherTokenQuant, result)` for the legacy vs. strict-math variant, while the safe/BigDecimal variant is asserted equal to the strict one [5](#0-4) . This confirms that the default double-precision engine's rounding does not match the mathematically-correct value that the codebase itself defines as canonical.

This is the direct analog of the AaveV3 finding: a division/rounding step (there, `_tokenToShares`/`_sharesToToken`; here, the bancor power-function division) determines how much of a counter-asset a user is credited with relative to what they deposited, and the rounding error is not reconciled back into the amount actually taken/given, unlike the mitigation pattern the AaveV3 fix applied (`_depositAmount = _sharesToToken(_shares)`).

### Impact Explanation
Any user calling `ExchangeTransactionContract` (broadcastable by any account, unprivileged) against a legacy-mode exchange pool receives a `buyTokenQuant` computed via imprecise floating-point math instead of the exact bancor-curve output. Because the reserve-balance updates (`exchangeCapsule.setBalance(...)`) are derived from this same imprecise value [6](#0-5) , repeated trades accumulate rounding drift in the pool's `firstTokenBalance`/`secondTokenBalance` versus the true bancor invariant, which can be leveraged over many transactions to extract value from the pool (or conversely cause traders to receive systematically less than owed), corrupting on-chain TRC10 exchange accounting. This falls under "exchange/market math" corruption.

### Likelihood Explanation
Reachable directly from an unprivileged, unauthenticated broadcast transaction (`ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`) with no special permissions required — only an existing TRC10 exchange pool and token balance are needed. Exploitability depends on the `allowHardenExchangeCalculation` dynamic parameter remaining disabled (legacy path active), which the code and tests indicate is a real, currently-supported runtime state rather than a deprecated one.

### Recommendation
Make `SafeExchangeProcessor` (exact `BigDecimal` bancor math) the sole/default processor for all exchange actuators, removing dependency on the `allowHardenExchangeCalculation` toggle, or ensure the toggle defaults to enabled network-wide via a mandatory hard fork rather than an optional proposal. Additionally, audit `ExchangeInjectActuator`/`ExchangeWithdrawActuator` proportional-quant calculations for the same "amount debited ≠ amount reconstructable from credited quant" pattern the AaveV3 fix addressed, and reconcile any residual rounding into the transferred amount rather than allowing balances to silently drift.

### Proof of Concept
Using the project's own regression test as evidence of the divergence: for input `{4732214L, 2202692725330L, 29218L}` (and 46 other data rows), `ExchangeProcessorTest.testStrictMath` shows `ExchangeProcessor` (double math) and `SafeExchangeProcessor`/`BigDecimal`-strict math produce different results for the identical trade [7](#0-6) . Any `ExchangeTransactionContract` executed while `allowHardenExchangeCalculation` is off will use the double-precision engine, producing a `buyTokenQuant`/reserve update inconsistent with the exact bancor curve, exactly as demonstrated by this test.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
