### Title
MAX_RESULT check in `getPossibleBlock` occurs only after all bloom-section I/O and BitSet work is done - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java])

### Summary
`LogBlockQuery.getPossibleBlock()` performs the full section-by-section bloom filter matching (via `subMatch`/`partialMatch`, which reads every relevant bit-index bitmap from `SectionBloomStore` through `sectionExecutor`) and builds the complete `blockNumBitSet`/`blockNumList` before checking whether the result size exceeds `MAX_RESULT`. Because the size check is the very last statement in the method, an attacker's over-limit query still causes the node to pay the full I/O/CPU cost of the query and only then receives a `JsonRpcTooManyResultException`.

### Finding Description
In `getPossibleBlock()` <cite repo="Oyahkilomeikhide/java-tron--006" path="framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java" start="63,70,72,73,74,77,78,79,82,83,84,85,86,87,88,89,90,91,93,94,95,96,98" end="63,70,72,73,74,77,78,79,82,83,84,85,86,87,88,89,90,91,93,94,95,96,98" />, the method:
1. Computes `allConditionsIndex` from the filter's addresses/topics via `getConditions()`.
2. Allocates a `BitSet` of capacity `(maxSection - minSection + 1) * BLOCK_PER_SECTION` and initializes all bits to 1.
3. For each condition, calls `subMatch(conditionsIndex)`, which in turn calls `partialMatch(bitIndexes, section)` for every section between `minSection` and `maxSection`. `partialMatch` submits concurrent `sectionBloomStore.get(section, bitIndex)` calls to `sectionExecutor` (disk reads) and performs `BitSet.and`/`or` operations for every unique bit index <cite repo="Oyahkilomeikhide/java-tron--006" path="framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogBlockQuery.java" start="140,151,152,153,154,155,156,159,160,161,162,163,164,165" end="140,151,152,153,154,155,156,159,160,161,162,163,164,165" />.
4. After all sections/conditions are processed, it iterates the resulting `blockNumBitSet` to build `blockNumList`.
5. **Only then**, at line 93, does it check `if (blockNumList.size() >= MAX_RESULT)` and throw `JsonRpcTooManyResultException`.

There is no upfront bound on the number of sections (`maxSection - minSection`) or an early abort inside `subMatch`/`partialMatch` when the running result count already exceeds `MAX_RESULT`. A public API caller (e.g. `eth_getLogs`/`eth_newFilter` style query reachable through `LogFilterWrapper`) can specify a wide `fromBlock`/`toBlock` range (or `Long.MAX_VALUE` which resolves to `currentMaxBlockNum`) with no address/topic filters, guaranteeing many matching blocks and thus `blockNumList.size() >= MAX_RESULT`. This forces the node to execute every section read and BitSet computation across the whole requested block range before rejecting the request. `LogMatch.matchBlockOneByOne()` has a similar after-the-fact check <cite repo="Oyahkilomeikhide/java-tron--006" path="framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogMatch.java" start="98,99,100,101,102" end="98,99,100,101,102" /> but that occurs progressively per matched block (interleaved), whereas `LogBlockQuery.getPossibleBlock` has no interleaving—work is fully completed up front for the whole range.

### Impact Explanation
An unprivileged JSON-RPC client can repeatedly submit broad `eth_getLogs`-style filter queries (wide block range, empty address/topics) that are guaranteed to produce more than `MAX_RESULT` (10000) matching blocks. Each such call forces the node to perform full bloom-section disk reads and BitSet computation across the entire section range before throwing an exception, while the attacker pays only the cost of one HTTP/RPC request. This is a classic underpriced-public-work / amplification pattern: repeated calls can consume disproportionate node I/O/CPU resources relative to the attacker's cost, degrading node/API responsiveness for legitimate users (DoS/resource exhaustion), though it does not lead to fund theft, replay, or state divergence.

### Likelihood Explanation
The precondition is minimal: an attacker only needs access to the public JSON-RPC log query endpoint and knowledge that a wide block range without narrow topic/address filters will exceed `MAX_RESULT`. No special privileges, contracts, or state manipulation are required, and the query can be repeated indefinitely at negligible client cost, making this straightforward and highly repeatable.

### Recommendation
Add an early-exit check inside `subMatch`/`partialMatch` (or in `getPossibleBlock`'s block-collection loop) so the number of matched blocks is checked against `MAX_RESULT` as it accumulates, aborting scanning of further sections as soon as the threshold is exceeded, rather than only after the entire range has been scanned. Additionally, consider bounding `maxSection - minSection` (i.e., the requested block range) upfront based on a maximum allowed span before beginning any bloom store reads, so obviously oversized ranges are rejected immediately without any I/O.

### Proof of Concept
Integration test outline (JUnit, using the existing `SectionBloomStoreTest`/`LogBlockQueryTest` infrastructure):
```java
// Setup: populate SectionBloomStore with enough sections/blocks so that
// a filter with no address/topic restriction and a wide fromBlock..toBlock
// range matches > LogBlockQuery.MAX_RESULT (10000) blocks.

@Test
public void testMaxResultCheckedAfterFullScan() {
  AtomicInteger sectionReadCount = new AtomicInteger();
  SectionBloomStore countingStore = Mockito.spy(sectionBloomStore);
  // wrap get() to increment sectionReadCount before delegating
  Mockito.doAnswer(inv -> {
    sectionReadCount.incrementAndGet();
    return inv.callRealMethod();
  }).when(countingStore).get(Mockito.anyInt(), Mockito.anyInt());

  LogFilterWrapper wideFilter = new LogFilterWrapper(
      new LogFilter(0L, currentMaxBlockNum, null, new byte[0][][])); // no address/topics
  LogBlockQuery query = new LogBlockQuery(wideFilter, countingStore, currentMaxBlockNum, executor);

  Assert.assertThrows(JsonRpcTooManyResultException.class, query::getPossibleBlock);

  // Assert that sectionBloomStore.get() was invoked for every section in
  // [minSection, maxSection] (i.e., full scan happened) rather than stopping early
  int expectedSections = (maxSection - minSection + 1);
  Assert.assertTrue(sectionReadCount.get() > 0);
  Assert.assertEquals(expectedSections, sectionsActuallyScanned); // confirms no early exit
}
```
Expected result: the test shows `sectionBloomStore.get()`/BitSet operations are invoked for the full section range before the `JsonRpcTooManyResultException` is thrown, confirming the missing upfront cost bound.
