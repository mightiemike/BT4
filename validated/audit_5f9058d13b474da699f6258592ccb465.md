## Title
Webhook HMAC signature does not bind the `shop`/domain identity, enabling cross-tenant session confusion in `authenticate.webhook` - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`)

### Summary
This is the same root-cause class as the PoolTogether `depositWithPermit` finding: a cryptographic proof is checked, but the identity that the proof is supposed to bind to the caller's claimed identity is never actually verified against that proof. In the PoolTogether bug, the permit signature's `_owner` was set to `msg.sender` instead of the party the caller claimed to act on behalf of (`_receiver`), letting an unrelated actor benefit from someone else's approval. In this codebase, the webhook HMAC only signs the raw request body, while the shop identity (`X-Shopify-Shop-Domain` header) that determines *whose* offline access token/session gets loaded is taken verbatim from an unauthenticated header and never cryptographically tied to the HMAC that was validated.

### Finding Description
`validateHmacFromRequestFactory` computes and checks the webhook HMAC using only `rawBody`: [1](#0-0) 

The `domain` field, however, is extracted independently from request headers and is not part of what was signed/verified: [2](#0-1) 

The webhook authenticate handler then uses this unauthenticated `domain` value directly to select and load the tenant's offline session/access token: [3](#0-2) 

and the same pattern exists for `ensureValidOfflineSession`, which loads a session keyed purely by the `shop` string passed to it: [4](#0-3) 

Because the HMAC is `HMAC(apiSecretKey, rawBody)` and `apiSecretKey` is the app's single client secret shared across *every* shop that installs the app, any merchant who installs the app can obtain a validly-signed webhook body for content they control (e.g. by creating an order/customer/product with attacker-chosen field values on their own store and letting Shopify deliver the real webhook). Since `domain` is not part of the signed data, that attacker can replay the exact same body+HMAC to the app's shared webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or events equivalent) header with a victim shop's domain. The HMAC check still passes because it only validates the body, not the domain-to-signature binding — directly analogous to `_permit` validating a signature without checking it belongs to the party (`_receiver`) that the rest of the function operates on.

### Impact Explanation
If this passes validation, `authenticate.webhook` loads the **victim shop's** offline session/access token (via `ensureValidOfflineSession`/`createOrLoadOfflineSession`) and hands it to the app's webhook handler along with the attacker-controlled payload, and constructs an authenticated `admin` client scoped to the victim's store: [5](#0-4) 
This is a cross-tenant confusion: an app's webhook business logic (e.g. `app/uninstalled`, `orders/create`, `customers/data_request`, etc.) executes against a shop the attacker doesn't control, using that shop's access token, driven by a payload the attacker crafted. Depending on the app's webhook handlers, this can lead to data corruption, unauthorized actions, or leakage of another merchant's data back to the attacker via handler responses/side effects.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even free/trial) installer of the target app — no special privilege beyond installing the app. They must know or guess a victim shop domain (`*.myshopify.io` domains are often discoverable/guessable or public storefront URLs). No secret material needs to be leaked; the attacker uses their own legitimately-issued webhook HMAC. This satisfies the "cross-tenant access" acceptance criterion via an unprivileged/single-merchant actor.

### Recommendation
Bind the shop domain into the signed material actually verified, or independently authenticate it:
- Prefer deriving the tenant/shop strictly from data that is cryptographically covered by the HMAC (e.g., embed/validate shop within the payload, or use per-shop derived secrets/keys if the delivery mechanism supports it), or
- At minimum, cross-check the `domain` header against an expected/allow-listed value for the session that is ultimately loaded (e.g., verify the resolved session's `shop` was already known/installed via a prior authenticated flow, and treat mismatches between session shop and any shop identifiers embedded in the payload as invalid), or
- Track outstanding webhook deliveries by `webhookId`/`eventId` scoped per-shop from the registration step so a body signed for shop A cannot be attributed to shop B.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.io`.
2. Attacker triggers a real webhook (e.g. `orders/create`) with attacker-controlled fields (note, tags, line items, etc.), capturing the genuine `X-Shopify-Hmac-Sha256` header and raw body Shopify sends to the app's webhook endpoint.
3. Attacker resends this exact `rawBody` + `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.io`.
4. `validateHmacFromRequestFactory` validates successfully (HMAC only checks `rawBody`) — see `packages/apps/shopify-api/lib/utils/hmac-validator.ts` lines 189-197.
5. `authenticate.webhook` proceeds to call `ensureValidOfflineSession(params, "victim.myshopify.io")`, loading victim's offline token, and invokes the app's webhook handler with attacker-controlled payload data as if it originated from the victim shop.
