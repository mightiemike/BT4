### Title
Zero-Balance-Account 1-yoctoNEAR promise subsidy mints unbacked tokens if `subsidized_amount` is not fully subtracted from burnt/total-supply accounting - ([File: runtime/near-vm-runner/src/wasmtime_runner/logic.rs])

### Summary
The external report describes `NovaExchange`'s `rewardHolders` function, an unrestricted mint reachable by any caller that credits balance out of thin air. The closest reachable analog in nearcore is the NEP-448 "zero-balance account" 1-yoctoNEAR promise subsidy: when a zero-balance contract attaches exactly 1 yoctoNEAR to a promise `FunctionCall` (or `yield_create_with_id`), the runtime *skips deducting* that yoctoNEAR from the sender and instead records it in `subsidized_amount`, while the deposit is still credited to the receiver's balance via `action_transfer`/`action_function_call`. This is an intentional design (to let deterministic/zero-balance accounts call things like `ft_transfer_call`), but it is a genuine, protocol-tracked token-creation path whose correctness depends entirely on `subsidized_amount` being subtracted from burnt totals everywhere total supply is derived.

### Finding Description
`promise_batch_action_function_call_weight` and `promise_yield_create_with_id` skip the balance deduction whenever `amount == 1 yoctoNEAR`, `one_yocto_on_promise` is enabled (stable since PV 85), and `current_account_balance.is_zero()`: [1](#0-0) 
The skipped amount is only bookkept as `subsidized_amount` on `ExecutionResultState`, never actually removed from anywhere: [2](#0-1) 
Downstream, the deposit still flows to the receiver as a normal credited balance (via the `FunctionCall`/`Transfer` action executing the promise), and the sender's balance is never reduced for that yoctoNEAR — this is confirmed by the end-to-end test showing the zero-balance account's balance after the call equals exactly its (unreduced) drained balance plus reward, i.e. the 1 yoctoNEAR shows up on the receiver side with no debit anywhere: [3](#0-2) 
The field's own doc comment states the invariant the whole mechanism relies on: `subsidized_amount` "is effectively minted" and "must be subtracted from total_balance_burnt to keep total supply correct": [4](#0-3) 
This is architecturally identical to the `NOVAToken.rewardHolders` bug class: a caller-triggered code path creates value that is credited to an account without a corresponding, guaranteed debit — correctness depends solely on a *separate* bookkeeping subtraction happening consistently at every point total supply is computed (block-level supply update, RPC/view total-supply reporting, cross-shard/chunk aggregation). I was not able to fully verify, within the available index, that every consumer of burnt/total-supply totals (in particular `core/primitives/src/block.rs`'s `new_total_supply = prev.total_supply + minted − balance_burnt` described in the economics spec) actually reads and subtracts `stats.balance.subsidized_amount`; my searches for `subsidized_amount` combined with `balance_burnt`/`total_supply` in `runtime/runtime/src/lib.rs` and `chain/chain/src/runtime/mod.rs` returned matches whose exact wiring (whether the subtraction is applied per-chunk before it reaches `new_total_supply`) I could not confirm with certainty from the indexed content.

### Impact Explanation
If the subtraction of `subsidized_amount` from `total_balance_burnt` is missing or incomplete along any aggregation path (e.g., a code path that reads `tx_burnt_amount`/`other_burnt_amount` for supply purposes without also reading `subsidized_amount`), every zero-balance-account promise call that hits the exemption unconditionally mints 1 yoctoNEAR of unbacked supply. While the per-call amount is tiny (1 yoctoNEAR), this is a transaction-triggered, permissionless, unlimited-repetition path (any account can drive its balance to zero — trivially achievable for a fresh zero-balance/deterministic account — and repeatedly invoke `promise_batch_action_function_call_weight`/`promise_yield_create_with_id` with amount=1). Repeated calls accumulate real, spendable balance credited to the receiver with no matching debit, which is a state-transition/total-supply-divergence class bug if the reconciliation is broken — matching the "supply inflation" acceptance criterion.

### Likelihood Explanation
The mechanism is reachable purely via a signed transaction/contract call — no privileged role required — and is stabilized in mainnet configuration (`one_yocto_on_promise` flips to `true` at PV 85, `core/parameters/res/runtime_configs/85.yaml:1`). The trigger conditions (zero balance + exactly 1 yoctoNEAR attached + one_yocto_on_promise enabled) are simple to construct via a `DeployGlobalContract`/`UseGlobalContract` ZBA pattern as shown in the existing test harness. However, likelihood of an actual exploitable bug depends entirely on whether the accounting subtraction is correctly and universally wired; the existence of dedicated tests (`test_one_yocto_subsidy_tracked_in_stats`) asserting `stats.balance.subsidized_amount` is populated suggests the developers are aware of and actively guarding this invariant, which lowers (but does not eliminate, given the multiple aggregation call sites) the likelihood of a live gap.

### Recommendation
Audit every code path that computes total supply, burnt-amount totals, or cross-chunk/cross-shard supply reconciliation (`core/primitives/src/block.rs::new_total_supply`, any RPC/view total-supply endpoint, and validator/consensus-side supply verification) to confirm each one subtracts `BalanceStatsV1::subsidized_amount` from `balance_burnt` before it is used, and add an integration/invariant test that runs many zero-balance accounts through the 1-yoctoNEAR subsidy path across multiple chunks/epochs and asserts the on-chain total supply matches genesis supply plus/minus the tracked inflation/burn exactly (accounting for the subsidy), rather than only unit-testing that `subsidized_amount` is incremented in isolation.

### Proof of Concept
1. Deploy a global contract exposing `call_promise`/`yield_create_with_id`-style host-function wrappers, as done in `setup_zba_global_contract` (`integration-tests/src/tests/runtime/test_yield_resume.rs:651`), and reference it from a small (`UseGlobalContract`) account so it qualifies as a Zero Balance Account (storage_usage ≤ 770 bytes).
2. From within the contract call, drain the account's entire balance via a `Transfer` promise to `current_account_balance == 0`.
3. In the same call, invoke `promise_batch_action_function_call_weight` (or `promise_yield_create_with_id`) attaching exactly `1` yoctoNEAR to a promise targeting any receiver — this hits the `skip_deduct` branch in `runtime/near-vm-runner/src/wasmtime_runner/logic.rs:3451-3462`, crediting the receiver with 1 yoctoNEAR while the sender's balance is not reduced for it.
4. Repeat steps 2–3 across many transactions/chunks (each zero-balance account can be reused or many such accounts created cheaply) to accumulate an arbitrarily large amount of "subsidized" tokens credited to receiver accounts.
5. Compare the sum of all account balances (or `total_supply` reported via RPC) against genesis supply plus recorded epoch inflation minus recorded burnt fees; a discrepancy equal to the accumulated `subsidized_amount` not reflected in the burnt-total reconciliation would confirm unbacked supply inflation. (Full confirmation requires tracing every `total_supply`/`balance_burnt` consumer to verify the subtraction is applied everywhere; this could not be fully completed with the available index and would need to be validated by a Devin agent with full repository/build access.)

    // Allow attaching exactly 1 yoctoNEAR to a promise function call
    // when the contract has zero balance. This lets deterministic accounts
    // call functions like ft_transfer_call that require an attached deposit
    // without needing to be seeded with balance first.
    let skip_deduct = amount == Balance::from_yoctonear(1)
        && ctx.config.one_yocto_on_promise
        && ctx.result_state.current_account_balance.is_zero();
    if skip_deduct {
        ctx.result_state.subsidized_amount = ctx
            .result_state
            .subsidized_amount
            .checked_add(amount)
            .expect("subsidized_amount overflow");
    } else {
        ctx.result_state.deduct_balance(amount)?;
    }

#[test]
fn create_with_id_one_yocto_exemption_on_drained_zba() {
    use testlib::runtime_utils::alice_account;
    let (node, zba_id) = setup_zba_global_contract();
    let alice_id = alice_account();
    let balance_before = node.user().view_account(&zba_id).unwrap().amount;
    let subsidized_before = node.client.read().cumulative_subsidized;

    // Sign as alice (not zba) so that the gas reservation comes out of alice's
    // balance — keeping zba's balance untouched until the wasm runs. The gas
    // reward still goes to the receiver (zba).
    let args = drain_then_yield_args(&alice_id, balance_before, &[20u8; 32], &[6u8; 16], 1);
    let args_len = args.len() as u64;
    let res = node
        .user()
        .function_call(alice_id, zba_id.clone(), "call_promise", args, MAX_GAS, Balance::ZERO)
        .unwrap();

    assert_eq!(
        res.status,
        FinalExecutionStatus::SuccessValue(vec![]),
        "drain + 1-yocto via the exemption should succeed on a ZBA; got {res:?}",
    );

    // The exemption fires exactly once — confirm the runtime tracked it.
    let subsidized_after = node.client.read().cumulative_subsidized;
    let subsidy = subsidized_after.checked_sub(subsidized_before).unwrap();
    assert_eq!(
        subsidy,
        Balance::from_yoctonear(1),
        "expected exactly 1 yoctoNEAR of subsidy (the exemption), got {} yoctoNEAR",
        subsidy.as_yoctonear(),
    );

    // The wasm drains the entire account_balance, then the 1-yocto deduction is
    // skipped via the exemption — leaving the VM's account balance at 0. The runtime
    // sets account.amount = 0, the ZBA check lets that stand, and finally the
    // receiver gas reward is credited on top, so balance_after = reward exactly.
    let reward = contract_function_call_reward(&fee_helper(&node), &res, "call_promise", args_len);
    let view = node.user().view_account(&zba_id).unwrap();
    assert_eq!(
        view.amount, reward,
        "expected zba balance to equal exactly the gas reward (drained + subsidized + reward)",
    );
    assert!(
        view.storage_usage <= 770,
        "zba should still qualify as a ZBA after the call: storage_usage = {}",
        view.storage_usage,
    );
}
