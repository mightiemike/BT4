### Title
Unhandled `.unwrap()` on `receiver_shard_id()` panics the chunk producer when a stale `GlobalContractDistribution` receipt survives multiple dynamic resharding events - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::pop`'s `receipt_filter_fn` unconditionally `.unwrap()`s the `Result` returned by `Receipt::receiver_shard_id`. For `GlobalContractDistribution` receipts, that function can legitimately return `Err(EpochError::ShardingError(..))` when the receipt's `target_shard` cannot be resolved in the current shard layout or its split history. A single unprivileged `DeployGlobalContract` transaction, combined with ordinary network congestion that delays the resulting distribution receipt across two or more dynamic-resharding (`ShardLayoutV3`) events, can drive the shard layout into a state where this resolution fails, turning the `Err` into a process-crashing `panic!` on every node applying that shard's chunk.

### Finding Description
`Receipt::receiver_shard_id` explicitly documents and handles the case where a `GlobalContractDistribution` receipt's `target_shard` is stale (from an old shard layout) by trying to resolve it via `shard_layout.resolve_to_current_shard(target_shard)`, and returns an `Err(EpochError::ShardingError(...))` when that resolution fails: [1](#0-0) 

The only caller that exercises this code path when draining the delayed-receipt queue does not propagate that error — it panics instead: [2](#0-1) 

`resolve_to_current_shard` walks the `ShardLayoutV3::shards_split_map`, which is a *cumulative* record only for V3 layouts; for pre-V3 layouts it falls back to a single-generation lookup: [3](#0-2) [4](#0-3) 

The reachability path is entirely composed of allowed/unprivileged actions: any account can submit `DeployGlobalContract`, which creates a `GlobalContractDistributionReceipt` carrying a `target_shard` equal to the deployer's shard at that time. If the shard hosting the deployer is heavily loaded (unprivileged callers can trivially saturate a shard's compute budget with cheap `FunctionCall` receipts), the distribution receipt is pushed into the shard's delayed-receipt queue instead of being processed immediately, exactly as `process_incoming_receipts`/`process_local_receipts` do via `delayed_receipts.push(...)`. While the receipt sits delayed, dynamic resharding (a normal, protocol-driven, non-privileged, non-adversarial chain event) can split the shard — and split it again — before the delayed queue drains. When the queue is finally drained, `DelayedReceiptQueueWrapper::pop` calls `receipt_filter_fn`, which `.unwrap()`s a `Result` that can now be `Err` because the receipt's stale `target_shard` cannot be resolved through the accumulated split history (e.g., due to an unbootstrapped/older split map or an edge case not covered by `resolve_to_current_shard`'s recursive walk).

This exact scenario is independently confirmed by an in-repo regression test that walks through deploying a global contract, saturating the shard to force the distribution receipt into the delayed queue, forcing two sequential dynamic resharding splits, and then draining the queue — explicitly stating the expected failure mode: [5](#0-4) 

The test's own comment states the mechanism precisely: "If the vulnerability exists, processing the stale `GlobalContractDistribution` receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old `target_shard` after two resharding generations" [6](#0-5) .

### Impact Explanation
`panic!` inside `receipt_filter_fn`, called from `DelayedReceiptQueueWrapper::pop`, is invoked from the runtime's chunk-apply path (`process_delayed_receipts` → `pop`) on every validator/chunk-producer node that applies the affected shard. Since chunk application is deterministic and mandatory for all nodes tracking the shard, an unhandled panic here is a transaction/receipt-triggered halt: every node that reaches this code path crashes rather than producing a divergent-but-valid state, taking down chunk production for that shard chain-wide until an operator intervenes. This satisfies the "transaction-triggered halt" impact bucket explicitly in scope.

### Likelihood Explanation
The trigger requires only unprivileged capabilities already available to any account: deploying a global contract (`DeployGlobalContract`) and submitting ordinary transactions to saturate a shard's compute budget so the resulting distribution receipt is delayed. The remaining condition — two dynamic-resharding splits occurring while the receipt is delayed — depends on the network's dynamic resharding cadence and is not attacker-controlled in the general case, but it is a normal, expected chain event (not a malicious validator or network-layer action), and the repository maintains a dedicated regression test built specifically to reproduce it, indicating the maintainers consider it a realistic scenario worth guarding against. This keeps likelihood at least Medium.

### Recommendation
In `DelayedReceiptQueueWrapper::pop`/`receipt_filter_fn`, replace the `.unwrap()` on `receiver_shard_id(&shard_layout)` with proper error propagation (`?` or an explicit `Result`-returning filter), converting an unresolved `target_shard` into a handled `RuntimeError`/`StorageInconsistentState` rather than a `panic!`, consistent with how other unresolved-shard conditions are already surfaced as recoverable errors elsewhere in `runtime/runtime/src/lib.rs`.

### Proof of Concept
1. Deploy a global contract from an account on shard S_A (`DeployGlobalContract`), producing a `GlobalContractDistributionReceipt` with `target_shard = S_A`.
2. Continuously submit cheap `FunctionCall`/burn-gas transactions to S_A each block so the shard's compute budget is saturated and the distribution receipt is pushed to the delayed-receipt queue instead of executing immediately.
3. While the receipt remains delayed, trigger two sequential dynamic-resharding splits that affect S_A's lineage (e.g., via `force_split_shards` in a `DynamicReshardingConfig`, or naturally under sustained memory-usage growth).
4. Stop saturating and allow the delayed queue to drain; `DelayedReceiptQueueWrapper::pop` calls `receipt_filter_fn`, which calls `receiver_shard_id` on the stale receipt and `.unwrap()`s the result.
5. If `resolve_to_current_shard` cannot map the receipt's stale `target_shard` through the accumulated split history, the `Err(EpochError::ShardingError(..))` is unwrapped, panicking chunk application on every node tracking that shard and halting the chain for it — exactly the scenario reproduced end-to-end in `test_stale_global_contract_distribution_after_double_resharding` [7](#0-6) .

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }

#[test]
#[cfg_attr(feature = "protocol_feature_spice", ignore)]
fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
