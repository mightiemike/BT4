There is a reachable division-by-zero pattern in java-tron's energy-limit accounting that mirrors the reported bug class: a denominator (`totalEnergyWeight`) is only defensively checked under one code path, while the actual divide-by-it happens in a separate hardened branch that is guarded solely by a Java `assert` statement — which is a no-op in production JVMs (assertions are disabled by default) — so the zero-denominator condition is not actually enforced at runtime.

### Title
Division by zero in `calculateGlobalEnergyLimit` due to unenforced `assert` on `totalEnergyWeight` - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit()` and its TVM-repository twin `RepositoryImpl.calculateGlobalEnergyLimit()` both guard the zero-denominator case for `totalEnergyWeight` using a bare `assert` statement instead of an explicit runtime check, then (when the "harden resource calculation" flag is on) perform a `BigInteger` division by that same value. Since Java assertions are disabled by default in production (`-ea` not set), if `totalEnergyWeight` is 0 and `allowNewReward()` is false, execution falls through the assert and performs `BigInteger.valueOf(...).divide(BigInteger.valueOf(0))`, throwing an uncaught `ArithmeticException`.

### Finding Description
In `EnergyProcessor.calculateGlobalEnergyLimit`:
```java
long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
if (hardenCalculation()) {
  return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
}
``` [1](#0-0) 

The zero check on `totalEnergyWeight` only takes effect when `allowNewReward()` is true. Otherwise, the code relies on `assert totalEnergyWeight > 0`, which does nothing in a production JVM (assertions are off by default), so a zero value silently passes through into `calculateGlobalLimitV1`, which performs an unguarded `BigInteger` divide:
```java
protected long calculateGlobalLimitV1(long frozeBalance, long totalLimit, long totalWeight) {
  long weight = frozeBalance / TRX_PRECISION;
  return BigInteger.valueOf(weight)
      .multiply(BigInteger.valueOf(totalLimit))
      .divide(BigInteger.valueOf(totalWeight))
      .longValueExact();
}
``` [2](#0-1) 

`BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException: BigInteger divide by zero`. This is the exact division-by-zero shape described in the report: one flag-gated check protects against zero in only one branch, while the value used in the actual division is not independently validated before use.

The same pattern exists in the TVM-facing `RepositoryImpl.calculateGlobalEnergyLimit`, used directly during smart-contract execution's energy accounting:
```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
assert totalEnergyWeight > 0;
if (hardenResourceCalculation()) {
  return BigInteger.valueOf(energyWeight)
      .multiply(BigInteger.valueOf(totalEnergyLimit))
      .divide(BigInteger.valueOf(totalEnergyWeight))
      .longValueExact();
}
``` [3](#0-2) 

This method is invoked from `VMActuator.getAccountEnergyLimitWithFloatRatio()` while computing the caller's available energy for a triggered contract call — a path reachable by any anonymous, unprivileged `TriggerSmartContract` broadcast transaction:
```java
long totalEnergyFromFreeze = rootRepository.calculateGlobalEnergyLimit(account);
``` [4](#0-3) 

`getUsage`/`calculateGlobalLimit*` helper functions elsewhere in the same classes correctly guard against a zero denominator with early returns (e.g. `EnergyProcessor.calculateGlobalEnergyLimitV2` checks `if (totalEnergyWeight == 0) return 0;` explicitly) [5](#0-4) , confirming that the V1/`assert`-based path is the outlier that omits this defensive check in a way enforceable at runtime.

### Impact Explanation
`totalEnergyWeight` is a dynamic property tracking the network-wide sum of frozen balances for energy; it can legitimately be zero on fresh chains/private networks before any account freezes TRX for energy, or transiently if the fork controlling `allowNewReward` is not active while all energy freezes are unwound. When it is zero and this code path is hit (non-`allowNewReward`, hardened calculation enabled), any unprivileged transaction that triggers TVM execution or an unfreeze/undelegate operation that recomputes account energy limits throws an unhandled `ArithmeticException` instead of a controlled `ContractValidateException`/`ContractExeException`. Depending on where in transaction processing/block application this exception surfaces, it can abort transaction execution unexpectedly or, if unhandled higher up, disrupt block processing — a denial-of-service vector triggerable by an anonymous account with no special privileges.

### Likelihood Explanation
Exploitability depends on the network being in (or being driven into) a state where `totalEnergyWeight == 0` while `allowNewReward` is disabled and `allowHardenResourceCalculation` is enabled — a state most plausible on newly bootstrapped or private/test java-tron networks rather than an established mainnet with existing frozen balances. However, since Java assertions are disabled by default in essentially all production JVM deployments, the `assert` provides no actual runtime protection, making this a real latent bug rather than a defense-in-depth safety net.

### Recommendation
Replace the bare `assert totalEnergyWeight > 0;` checks in `EnergyProcessor.calculateGlobalEnergyLimit` and `RepositoryImpl.calculateGlobalEnergyLimit` with explicit runtime guards (e.g., `if (totalEnergyWeight <= 0) { return 0; }`) executed unconditionally — not gated behind `allowNewReward()` — before entering either the hardened `BigInteger` division path or the legacy double-division path, mirroring the safe pattern already used in `calculateGlobalEnergyLimitV2`.

### Proof of Concept
1. Configure/bootstrap a java-tron node with `allowHardenResourceCalculation=1` and `allowNewReward=0` (achievable pre-fork or on a private chain), and ensure no account currently has frozen energy balance so `getTotalEnergyWeight()` returns 0 [6](#0-5) .
2. Broadcast any `TriggerSmartContract` transaction from an unprivileged account against an existing contract, causing `VMActuator` to compute the caller's energy limit via `getAccountEnergyLimitWithFloatRatio` → `RepositoryImpl.calculateGlobalEnergyLimit` [3](#0-2) .
3. Observe `BigInteger.valueOf(...).divide(BigInteger.valueOf(0))` throw `ArithmeticException`, propagating out of the normal `ContractValidateException`/`ContractExeException` handling path used elsewhere in the actuator flow.
