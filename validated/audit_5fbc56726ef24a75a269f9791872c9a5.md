### Title
Cross-network replay of council-signed `BatchProofMethodId` upgrade between Nightly and TestNetworkWithForks due to identical `chain_id` (5665) and identical default DA public keys - (File: crates/light-client-prover/src/circuit/mod.rs, crates/light-client-prover/src/circuit/initial_values.rs)

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the same value `5665`, and when the `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_{1..5}` env vars are unset, `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` and `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` default to byte-identical pubkeys. Consequently, a `BatchProofMethodId` blob genuinely signed and broadcast by the Nightly security council is verified as valid, byte-for-byte, when replayed onto a TestNetworkWithForks light-client-prover instance built without the env overrides.

### Finding Description
The claimed binding was: `citrea_network_to_chain_id(Network::Nightly) != citrea_network_to_chain_id(Network::TestNetworkWithForks)`. Tracing the code shows this is false — both evaluate to `5665` at [2](#0-1) .

In `run_l1_block`, the `DataOnDa::BatchProofMethodId` branch enforces two checks before accepting an upgrade: the activation height must exceed the last one, and `circuit_chain_id != batch_proof_method_id.body.chain_id` must not hold, i.e. `citrea_network_to_chain_id(network) == body.chain_id` [3](#0-2) . Because both networks compute chain_id `5665`, a body signed with `chain_id = 5665` (originally intended for Nightly) passes this check unmodified when the same raw blob is replayed against a TestNetworkWithForks node.

The second guard, `verify_method_id_security_council`, checks ECDSA signatures against `method_id_upgrade_authority_da_public_keys` [4](#0-3) . These keys come from `InitialValueProvider::method_id_upgrade_authority_da_public_keys`, which for `Network::Nightly` and `Network::TestNetworkWithForks` resolve to `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` and `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` respectively [5](#0-4) . Both constant arrays default to identical hex pubkeys (`0313c4ff...`, `03b15df9...`, `03fb89fd...`, `037d415a...`, `022fad51...`) when the corresponding env vars are unset at compile time [6](#0-5) [7](#0-6) . Since the signed message (`body.serialize()`) and signatures are attacker-observable and copyable bytes, and the keys plus chain_id used to verify them are identical across the two networks under this default-build precondition, no existing guard rejects the replay: neither `blob.sender()` checks (not used for this data type), nor `Auth`, nor any node-identity check distinguishes "this blob was intended for Nightly" from "this blob was intended for TestNetworkWithForks."

### Impact Explanation
If both networks are ever run with the default (unset env var) build — e.g., a devnet/nightly deployment operator forgetting to inject distinct `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_*` values for `TestNetworkWithForks` — an attacker can take a real, council-authorized Nightly method-id-upgrade inscription and rebroadcast the identical raw Bitcoin transaction bytes on the DA the TestNetworkWithForks light-client-prover watches. The TestNetworkWithForks light-client-prover will accept it as a validly authorized `BatchProofMethodId` upgrade, updating `BatchProofMethodIdAccessor` state with a method ID that was never separately authorized by (or even intended for) TestNetworkWithForks's operators. This causes a batch proof method-id upgrade to be accepted that was never independently authorized for that network — matching the Critical impact category ("a sequencer commitment or method-id upgrade accepted that was never authorised"). The attack is repeatable for every future Nightly method-id upgrade transaction as long as both networks keep the shared default keys and shared chain_id.

### Likelihood Explanation
Likelihood is entirely conditional on operational practice, not a code-inherent guarantee: it requires (1) a real deployment running TestNetworkWithForks with the default/unset `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_*` env vars (same for Nightly), and (2) that Nightly's council actually broadcasts a real upgrade transaction that an attacker can observe on Bitcoin/DA and re-inscribe. The `chain_id` collision (`5665`) is a hard compile-time constant, not configuration-dependent — this part is unconditionally true today, and it is the root cause the question is trying to isolate. The attacker's only cost is the Bitcoin inscription fee to rebroadcast the captured bytes; no keys are needed since the signatures are copied verbatim. This is fully within the unprivileged attacker model (anyone who can inscribe a Bitcoin transaction).

### Recommendation
Assign `Network::Nightly` and `Network::TestNetworkWithForks` distinct chain_id constants in `citrea_network_to_chain_id` (e.g. do not reuse `5665`), and/or ensure `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` and `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` default to distinct compiled-in pubkeys rather than identical ones, so that operators who forget to set the env-var overrides are not silently exposed to cross-network replay.

pub fn verify_method_id_security_council(
    initial_da_pubkeys: [[u8; SECURITY_COUNCIL_COMPRESSED_PUBKEY_SIZE];
        SECURITY_COUNCIL_MEMBER_COUNT],
    msg: &[u8],
    signatures_with_idx: &[([u8; SECURITY_COUNCIL_SIGNATURE_SIZE], u8);
         SECURITY_COUNCIL_SIGNATURE_THRESHOLD],
) -> bool {
    // EIP-191 prefix + keccak256 → 32-byte prehash
    let prehash = eip191_hash_message(msg);

    // Check that signature indices are within bounds
    for &(_, index) in signatures_with_idx {
        if index >= 5 {
            log!("Invalid signature index: {}", index);
            return false;
        }
    }

    // Make sure the indexes are in ascending order to prevent duplicates
    for i in 0..signatures_with_idx.len() - 1 {
        if signatures_with_idx[i].1 >= signatures_with_idx[i + 1].1 {
            log!(
                "Signature indices are not in ascending order, failing indices: {}, {}",
                signatures_with_idx[i].1,
                signatures_with_idx[i + 1].1
            );
            return false;
        }
    }

    for signature_with_idx in signatures_with_idx.iter() {
        let signature = signature_with_idx.0;
        let pubkey_idx = signature_with_idx.1;
        let const_pubkey = initial_da_pubkeys[pubkey_idx as usize];

        // ensure the inscription pubkey matches the expected constant (compressed 33B)
        let verifying_key = VerifyingKey::from_sec1_bytes(const_pubkey.as_slice())
            .expect("Initial DA pubkeys must be parsable to k256 VerifyingKey form sec1 bytes");

        let Ok(parsed_sig) = Signature::from_bytes(&signature.into()) else {
            log!("Invalid signature format");
            return false; // invalid signature format, fail
        };

        // verify prehash with the matching verifying key
        if verifying_key
            .verify_prehash(prehash.as_slice(), &parsed_sig)
            .is_err()
        {
            log!("Signature verification failed for index: {}", pubkey_idx);
            return false;
        }
    }

    true
