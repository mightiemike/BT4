### Title
Unchecked `.unwrap()` on `receiver_shard_id()` in `receipt_filter_fn` causes a transaction-triggered chunk-processing panic on stale `GlobalContractDistribution` receipts - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` force-unwraps the `Result` returned by `Receipt::receiver_shard_id()` when popping delayed receipts. `receiver_shard_id()` legitimately returns `Err(EpochError::ShardingError(..))` for a `GlobalContractDistribution` receipt whose `target_shard` cannot be resolved to a shard in the current layout (or its recorded split history). Any signer can trigger this by deploying a global contract shortly before a shard hosting the pending distribution receipt is split/retired in a way that leaves the split history unable to map the stale `target_shard`, causing every node applying that chunk to panic identically.

### Finding Description
`receiver_shard_id()` ( [1](#0-0) ) explicitly documents that a `GlobalContractDistribution` receipt's `target_shard` can be "from an arbitrarily old layout" if the receipt was delayed across multiple resharding events, and it now returns an `Err` (instead of panicking) when `shard_layout.resolve_to_current_shard(target_shard)` cannot resolve the id:
```
let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard) else {
    return Err(EpochError::ShardingError(...));
};
```
However, the only caller inside the delayed-receipt draining path does not treat this as a recoverable condition. `receipt_filter_fn`, used by `DelayedReceiptQueueWrapper::pop` to filter out receipts left over from a shard split, unwraps both the shard-layout lookup and the `receiver_shard_id()` result: [2](#0-1) 

This is structurally the same bug class as the referenced CVE: a value that can legitimately become unresolvable/missing (the removed/split shard, analogous to the removed USB port's hub) is dereferenced (`.unwrap()`) without a guard, based on an implicit assumption ("this can't happen") that a concurrent state change (resharding) violates. `resolve_to_current_shard` for `ShardLayoutV3` walks the cumulative split map recursively and returns `None` "only if the shard ID is absent from both the current layout and the split history" ( [3](#0-2) ). Such absence is reachable in practice: when the network migrates from V1/V2 static resharding to V3 dynamic resharding, the split map is seeded only from `build_shard_split_map(layout_history)`, i.e., from whatever historical layouts are available at migration time ( [4](#0-3) ). A `GlobalContractDistributionReceipt` created and delayed before that migration, targeting a shard from a layout not included in the reconstructed history, would fail to resolve after migration, and the queue-draining code panics.

A test in the repository, `test_stale_global_contract_distribution_after_double_resharding`, was written specifically to pin the "receiver_shard_id() fails to remap the old target_shard" scenario and asserts the chain does not stall while draining such a stale receipt ( [5](#0-4) ). That test exercises the case where `resolve_to_current_shard` *does* successfully resolve (two splits fully covered by the V3 split map), so it passes — but it does not cover the unresolvable case (e.g. crossing the V2→V3 migration boundary, or a chain of splits exceeding whatever history was captured), where `receiver_shard_id()` still returns `Err` and `receipt_filter_fn`'s `.unwrap()` will panic.

### Impact Explanation
A panic inside `receipt_filter_fn`/`pop()` occurs while every validator/RPC node tracking the shard is draining the delayed-receipt queue during ordinary chunk application — this is deterministic and identical across all honest nodes applying the same chunk, so it manifests as a chain-wide halt (liveness failure) for the affected shard(s) rather than a state-root fork. Any account holder can trigger the precondition merely by deploying a global contract (`DeployGlobalContract`/`UseGlobalContract` actions), which unconditionally produces a `GlobalContractDistributionReceipt` that gets queued and forwarded shard-by-shard ( [6](#0-5) ); no special privilege beyond submitting an ordinary transaction is required.

### Likelihood Explanation
Triggering requires a specific but realistic sequencing: submit a global-contract deployment, then have the shard undergo resharding events such that the recorded split history in the (possibly freshly-migrated) `ShardLayoutV3` cannot resolve the receipt's stale `target_shard` before the delayed receipt is drained. This is most plausible around the V2→V3 dynamic-resharding migration boundary, where `derive_with_layout_history`/`build_shard_split_map` only reconstructs history from the layouts it is given ( [7](#0-6) ). The repository's own regression test demonstrates the surrounding scenario is a live concern that the team is actively testing for, which supports plausibility, though I could not fully verify from the index whether every migration path guarantees complete split history (this would need to be confirmed by running/extending the existing test against the migration boundary rather than the pure-V3 double-split case).

### Recommendation
Change `receipt_filter_fn` to propagate the `Result` instead of `.unwrap()`-ing it (mirror the handling already used in `filter_incoming_receipts_for_shard` and `forward_from_buffer_to_shard`, which use `?`). Update `pop()`'s signature/call sites to handle the `Err` case as a graceful, well-defined outcome (e.g., treat an unresolvable stale `GlobalContractDistribution` receipt as consumed/dropped with a logged warning, or route it through `resolve_to_current_shard`'s ancestor-walk equivalent before filtering) rather than allowing a `RuntimeError`-worthy condition to become a raw panic during chunk application.

### Proof of Concept
1. Deploy a global contract from an account on shard S (produces a `GlobalContractDistributionReceipt` with `target_shard = S`).
2. Ensure the receipt is delayed (e.g., saturate compute on S) so it remains in the delayed-receipt queue while resharding occurs — as done in `test_stale_global_contract_distribution_after_double_resharding` ( [8](#0-7) ).
3. Trigger enough resharding (or a V2→V3 dynamic-resharding migration) that the split history retained by the resulting `ShardLayoutV3` does not contain an entry mapping `S` (or its descendants) forward — `resolve_to_current_shard` then returns `None`.
4. When the delayed queue drains and `pop()` calls `receipt_filter_fn` on the stale receipt, `receiver_shard_id()` returns `Err(EpochError::ShardingError)`, the `.unwrap()` at `runtime/runtime/src/congestion_control.rs:876` panics, and every node applying that chunk crashes identically, halting the shard.

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

///
/// Assumes that layouts are ordered from newest to oldest, and that there are no duplicates.
/// Ignores layouts with `version()` lower than `VERSION` (this is **not** the struct version).
pub fn build_shard_split_map(layout_history: &[ShardLayout]) -> ShardsSplitMapV3 {
    let mut split_history = ShardsSplitMapV3::new();

    for window in layout_history.windows(2) {
        let current_layout = &window[0];
        let prev_layout = &window[1];

        if current_layout.version() < VERSION || prev_layout.version() < VERSION {
            break;
        }

        debug_assert_ne!(current_layout, prev_layout);

        for shard_id in current_layout.shard_ids() {
            match current_layout.try_get_parent_shard_id(shard_id).expect("invalid shard_id") {
                Some(parent_id) if parent_id != shard_id => {
                    split_history.entry(parent_id).or_default().push(shard_id);
                }
                _ => continue,
            }
        }
    }

    split_history
}

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }

fn forward_distribution_next_shard(
    receipt: &Receipt,
    global_contract_data: &GlobalContractDistributionReceipt,
    apply_state: &ApplyState,
    epoch_info_provider: &dyn EpochInfoProvider,
    state_update: &mut TrieUpdate,
    receipt_sink: &mut ReceiptSink,
    receipt_to_tx: &mut Vec<(CryptoHash, ReceiptToTxInfo)>,
) -> Result<(), RuntimeError> {
    let shard_layout = epoch_info_provider.shard_layout(&apply_state.epoch_id)?;
    let already_delivered_shards = BTreeSet::from_iter(
        global_contract_data
            .already_delivered_shards()
            .iter()
            .cloned()
            .chain(std::iter::once(apply_state.shard_id)),
    );
    let Some(next_shard) = shard_layout
        .shard_ids()
        .filter(|shard_id| !already_delivered_shards.contains(&shard_id))
        .next()
    else {
        return Ok(());
    };
    let already_delivered_shards = Vec::from_iter(already_delivered_shards);
    let predecessor_id = receipt.predecessor_id().clone();
    let next_receipt = global_contract_data.forward(next_shard, already_delivered_shards);
    let mut next_receipt = Receipt::new_global_contract_distribution(predecessor_id, next_receipt);
    let receipt_id = apply_state.create_receipt_id(receipt.receipt_id(), 0);
    next_receipt.set_receipt_id(receipt_id);
    if apply_state.save_receipt_to_tx {
        receipt_to_tx.push((
            receipt_id,
            ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: *receipt.receipt_id(),
                    parent_predecessor_id: receipt.predecessor_id().clone(),
                }),
                receiver_account_id: next_receipt.receiver_id().clone(),
                shard_id: apply_state.shard_id,
            }),
        ));
    }
    receipt_sink.forward_or_buffer_receipt(next_receipt, apply_state, state_update)?;
    Ok(())
}
