### Title
Unbounded slippage/deadline-less AMM swap quoting in gas-abstraction auto-swap and gas-refund flows allows MEV extraction from user deposits and refunds - ([File: x/uexecutor/keeper/execute_inbound_gas.go], [File: x/uexecutor/keeper/outbound.go])

### Summary
The bug class in the external report is that a spot-price-derived fee/quote can be manipulated between the time a user's transaction is composed and the time it lands on-chain, since the value used for computing an economic parameter (fee, in the original report; a swap quote, here) is read at execution time rather than bound to what the user actually agreed to. In Push Chain's `x/uexecutor` module, the gas-abstraction "deposit + auto-swap" path (`ExecuteInboundGas` → `CallPRC20DepositAutoSwap`) and the outbound gas-refund path (`applyGasRefund` → `CallUniversalCoreRefundUnusedGas`) both derive a `minPCOut` slippage bound from a spot quote (`GetSwapQuote`) fetched via `evmKeeper.CallEVM` at the moment the module-originated transaction executes, using a fixed 5% tolerance computed in Go, not chosen or signed by the depositing user.

### Finding Description
In `ExecuteInboundGas` (x/uexecutor/keeper/execute_inbound_gas.go:104-153), after a user's cross-chain deposit is finalized by validators, the module:
1. Fetches `quoterAddr`/`wpcAddr`/`fee` from `UniversalCore` [1](#0-0) 
2. Calls `k.GetSwapQuote(sdkCtx, quoterAddr, prc20AddressHex, wpcAddr, fee, amount)` to get a spot-derived quote for the deposited amount [2](#0-1) 
3. Computes `minPCOut = quote * 95 / 100` (a hardcoded 5% slippage tolerance) and immediately calls `CallPRC20DepositAutoSwap` [3](#0-2) 

The same pattern repeats in `applyGasRefund` (x/uexecutor/keeper/outbound.go:214-234), where `getSwapQuoteForRefund` computes a spot quote and the same fixed 5% tolerance is applied before calling `CallUniversalCoreRefundUnusedGas` with `withSwap=true` [4](#0-3) .

Because this whole flow is module-originated (`DerivedEVMCall`, not a user-signed EVM transaction), the user has no ability to specify their own slippage tolerance or a quote deadline — the quote is fetched and consumed in the same block/transaction by the module using the pool's live spot state. If the AMM pool referenced by `quoterAddr`/`wpcAddr` reflects a spot price that can be moved within the same block (e.g., via a preceding swap in the same block from an unprivileged actor interacting with the underlying Uniswap-style pool the `UniversalCore` contract routes through), an attacker can sandwich the module's auto-swap: push the pool price unfavorably immediately before the module's `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas` executes (still satisfying the loose 5% band), extract the difference, then restore price afterward. This directly reduces the amount of PC the depositing/refunded user actually receives versus what a correctly-quoted amount would have yielded — a mechanical analog of the reported issue, where an economic parameter computed from live reserves is used without binding it to what the affected party intended, enabling value extraction by a party who can influence ordering/reserves around the transaction.

### Impact Explanation
This corrupts the "amount of PC user actually receives" invariant for the gasless/gas-abstraction deposit-and-swap flow and the outbound gas-refund flow. An unprivileged actor able to move the referenced AMM pool's price within the tolerance window can siphon value from every affected inbound deposit or outbound refund that goes through the swap path, at the expense of ordinary users — a loss of user funds through legitimate, validator-agreed code paths (not requiring any dishonest validator, TSS participant, or admin). This matches the "stealing ... loss ... of user or protocol-controlled funds" and "corruption of ... refund accounting ... UniversalTx state" impact categories in scope.

### Likelihood Explanation
Likelihood depends on whether the pool backing `quoterAddr`/`wpcAddr` is thin/spot-based and whether an attacker can reliably influence the pool's reserves in the same block as the module's derived EVM call (e.g. by submitting an ordinary EVM swap transaction against the same pool ahead of the module transaction, within builder/validator-controlled but non-privileged mempool ordering). Because the tolerance is a flat 5% rather than a TWAP-based or user-committed bound, and the quote is fetched and consumed atomically without any deadline or user-supplied minOut, the window for manipulation is bounded only by pool depth and the fixed 5% band — plausible for lower-liquidity gas-token pools, which is the most likely scenario for less common source-chain gas tokens.

### Recommendation
- For `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas`, derive `minPCOut` from a manipulation-resistant reference (e.g., a TWAP over multiple blocks, or the previously-recorded chain-meta/oracle price) rather than a spot quote read at execution time, or tighten/validate the deviation between spot and a trusted reference before proceeding.
- Consider allowing the amount to be split/deferred, or fail-closed (fall back to the no-swap PRC20 deposit/refund path already present as a fallback) whenever the spot price deviates materially from a recent reference price, rather than only falling back on outright call failure.
- Verify whether `quoterAddr`/`wpcAddr`/pool liquidity is sufficiently deep/protected in Push Chain's own production `UniversalCore` deployment; if the underlying pool is exclusively provisioned/controlled by the protocol with no external LPs or swappers able to move price, this reduces to a low/no-impact finding, but that guarantee is not established in scoped Go code and should be confirmed against the `UniversalCore` Solidity contract's access model, which is outside the indexed Go code available here.

### Proof of Concept
Conceptual attack (exact PoC requires the `UniversalCore`/Quoter Solidity contract, which is not in the indexed code shown):
1. Attacker monitors the mempool/inbound-ballot-finalization for pending `ExecuteInboundGas` deposits (or pending outbound refunds) with sizable `amount`.
2. Immediately before the module's derived EVM call executes, attacker submits an ordinary swap against the same PRC20/WPC pool used by `quoterAddr`, moving the spot price down (or up, depending on direction) by close to the tolerance band.
3. The module computes `quote` from the now-skewed pool state and derives `minPCOut = quote*95/100`, then executes the swap on behalf of the user/refund recipient at the manipulated price via `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas` [3](#0-2) .
4. Attacker reverses their initial swap, capturing the price impact as profit, while the user/refund recipient receives less PC than an honest spot price would have yielded.
