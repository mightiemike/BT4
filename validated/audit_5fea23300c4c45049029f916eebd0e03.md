## Finding

The premise in the question (double-credit / minting via self-match) is not what the code actually does — but there **is** a genuine lost-update bug in this exact call chain, in the opposite direction: it *destroys* value rather than duplicating it.

### Title
Self-match lost-update destroys maker-side proceeds when taker address equals resting maker order's owner - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
When an account crosses a `MarketSellAssetContract` order against its **own** resting order (taker address == maker order owner address), `matchSingleOrder` credits the maker leg by independently fetching a fresh `AccountCapsule` from `accountStore`, mutating it, and immediately calling `accountStore.put()` [1](#0-0) . That fresh fetch reflects the pre-transaction committed state, not the in-memory `accountCapsule` object that `execute()` has already been mutating (fee debit, sell-token debit, buy-token credit). At the end of `execute()`, the single stale in-memory `accountCapsule` is written back with `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` [2](#0-1) , which fully overwrites the account record and silently discards the maker-leg credit that was already persisted moments earlier.

### Finding Description
- `execute()` fetches `accountCapsule` once via `accountStore.get(...)` and reuses that same in-memory instance across `transferBalanceOrToken`, `createAndSaveOrder`, and `matchOrder` [3](#0-2) .
- Inside `matchSingleOrder`, the taker leg is credited directly onto that shared in-memory object via `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)` [4](#0-3) , but the maker leg uses the overloaded `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` which does its own `accountStore.get(...)` / `accountStore.put(...)` round trip [5](#0-4) [1](#0-0) .
- When taker == maker (self-match), both code paths operate on the same DB key but through two different `AccountCapsule` object instances. The maker-path `put()` happens first (inside `matchOrder`), and the final taker-path `put()` at line 148 happens last, fully overwriting the record — so the maker-leg credit is lost.
- `validate()` contains no check preventing an owner from crossing against their own resting order — there is no self-trade restriction in the validation logic [6](#0-5) .
- Order-book bookkeeping (`orderStore`, `marketAccountStore`, `ret.addOrderDetails`) correctly records the maker order as filled/INACTIVE and the fill in the transaction result, but the actual persisted account balance does not reflect the maker-side proceeds, so the on-chain order-fill history diverges from the actual balance.

### Impact Explanation
An unprivileged account that self-crosses its own resting order permanently loses the maker-side proceeds (the returned/credited `sellTokenID` amount) while the fee is still charged and the sell-side debit still applies. This is a value-destruction bug rather than the double-credit/mint hypothesized in the question — the account ends up worse off than either a normal trade or a no-op, and the persisted account state diverges from the order-fill records shown in `ret`/order store. This is a real invariant violation (conservation of value / balance reconciliation) reachable by any account, not the "double-credit/mint" impact originally hypothesized.

### Likelihood Explanation
Fully feasible and repeatable with normal, unprivileged transactions: place a resting sell order for owner X (any `MarketSellAssetContract`), then broadcast a second `MarketSellAssetContract` from the same owner X with a price that crosses the resting order. No special permissions, timing races across blocks, or off-chain assumptions are required — everything happens within one `execute()` call.

### Recommendation
In `matchSingleOrder` / `addTrxOrToken`, detect when the maker order's owner address equals the taker's account address and route the maker-leg credit through the same in-memory `takerAccountCapsule` object instead of doing an independent `accountStore.get`/`put` round trip. More generally, defer all `accountStore.put()` calls for a given address to a single point per transaction (e.g., maintain a per-address cache of loaded `AccountCapsule` objects within `matchOrder`/`matchSingleOrder`) so that the same address is never read-modified-written through two divergent object instances within one execution.

### Proof of Concept
Java integration test outline (add to `framework/src/test/java/org/tron/core/actuator/MarketSellAssetActuatorTest.java`):
```java
@Test
public void selfMatchLosesMakerProceeds() throws Exception {
  InitAsset();
  byte[] owner = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);

  // give owner TOKEN_ONE to sell
  AccountCapsule acc = dbManager.getAccountStore().get(owner);
  acc.addAssetAmountV2(TOKEN_ID_ONE.getBytes(), 1000L,
      dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
  dbManager.getAccountStore().put(owner, acc);

  // 1) place resting order: sell TOKEN_TWO, buy TOKEN_ONE (owner already has TOKEN_TWO from InitAsset)
  addOrder(TOKEN_ID_TWO, 100L, TOKEN_ID_ONE, 100L, OWNER_ADDRESS_FIRST);

  long token1Before = dbManager.getAccountStore().get(owner)
      .getAssetV2MapForTest().getOrDefault(TOKEN_ID_ONE, 0L);
  long token2Before = dbManager.getAccountStore().get(owner)
      .getAssetV2MapForTest().getOrDefault(TOKEN_ID_TWO, 0L);

  // 2) broadcast crossing order from SAME owner: sell TOKEN_ONE, buy TOKEN_TWO
  MarketSellAssetActuator actuator = new MarketSellAssetActuator();
  actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
      OWNER_ADDRESS_FIRST, TOKEN_ID_ONE, 100L, TOKEN_ID_TWO, 100L));
  TransactionResultCapsule ret = new TransactionResultCapsule();
  actuator.validate();
  actuator.execute(ret);

  AccountCapsule after = dbManager.getAccountStore().get(owner);
  long token1After = after.getAssetV2MapForTest().getOrDefault(TOKEN_ID_ONE, 0L);
  long token2After = after.getAssetV2MapForTest().getOrDefault(TOKEN_ID_TWO, 0L);

  // Expected (conservation, if fully fixed): token1 net -0 (sold then bought back),
  // token2 net -0 (sold in resting order, then bought back), minus fees only.
  // Actual (bug): TOKEN_TWO maker-leg credit is lost -> token2After < expected reconciled value,
  // proving the maker-side proceeds vanished.
  Assert.assertNotEquals("maker-leg credit unexpectedly lost due to lost-update overwrite",
      token2Before + 100L, token2After);
}
```
Expected result on current code: the assertion demonstrates that the maker-side credit written inside `matchOrder` is overwritten and absent from the final persisted `AccountCapsule`, confirming the lost-update / value-destruction bug.

  private void addTrxOrToken(MarketOrderCapsule orderCapsule, long num) {
    AccountCapsule accountCapsule = accountStore
        .get(orderCapsule.getOwnerAddress().toByteArray());

    byte[] buyTokenId = orderCapsule.getBuyTokenId();
    if (Arrays.equals(buyTokenId, "_".getBytes())) {
      accountCapsule.setBalance(addExact(accountCapsule.getBalance(), num));
    } else {
      accountCapsule
          .addAssetAmountV2(buyTokenId, num, dynamicStore, assetIssueStore);
    }
    accountStore.put(orderCapsule.getOwnerAddress().toByteArray(), accountCapsule);
  }
