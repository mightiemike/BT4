## Title
Active-permission holders can rewrite an account's Owner permission via `AccountPermissionUpdateContract`, enabling persistent privilege self-escalation - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

## Summary
java-tron's multi-sig permission model has an analogous "role hierarchy" structure: `Owner` (top-level, like `SUPER_ADMIN_ROLE`), `Witness`, and `Active` (delegated, like `ROLE_MANAGER_ROLE`) permissions [1](#0-0) . Just as the reported Solidity bug lets a `ROLE_MANAGER_ROLE` assign `ROLE_MANAGER_ROLE` to itself/others without restriction, java-tron's `AccountPermissionUpdateActuator` and the transaction-signature validation path in `TransactionCapsule` do not prevent an `Active`-type permission from being authorized (via its `operations` bitmap) to execute `AccountPermissionUpdateContract` itself. Once such an `Active` permission is granted this capability, its key holder can sign a valid permission-update transaction using only `Active`-level authority and completely rewrite the account's `Owner` permission (add itself as an owner key, remove other owner keys, change threshold), achieving persistent Owner-level control and defeating any attempt by the real account owner to revoke that Active permission.

## Finding Description
The `Permission` message defines a hierarchy of `Owner`, `Witness`, and `Active` types, where `Active` permissions carry an `operations` bitmap restricting which contract types they may authorize [1](#0-0) .

When validating a transaction's signature, `TransactionCapsule.checkPermission` only enforces that a non-owner (`permissionId != 0`) signer holds an `Active`-type permission and that the contract type bit is set in that permission's `operations` — it does not special-case `AccountPermissionUpdateContract`: [2](#0-1) 

`AccountPermissionUpdateActuator.checkPermission` validates a submitted `Active` permission's `operations` bitmap only against `dynamicStore.getAvailableContractType()`, which — unlike the default operations bitmap — does include `AccountPermissionUpdateContract` as a "valid" bit: [3](#0-2) 

This is confirmed by the codebase's own tests: `getAvailableContractType()` includes `AccountPermissionUpdateContract`, while `getActiveDefaultOperations()` explicitly excludes it by default: [4](#0-3) [5](#0-4) 

This shows the developers intended `AccountPermissionUpdateContract` to be excluded from an `Active` permission's capabilities by default, but no code path actually enforces this exclusion when an owner (or a compromised owner key, or a wallet/exchange configuring custom multi-sig policies) grants a broader custom `operations` bitmap to an `Active` permission. Once an `Active` permission has this bit set, `AccountPermissionUpdateActuator.execute` applies the update unconditionally via `account.updatePermissions(...)`, replacing the `owner_permission`, `witness_permission`, and `active_permission` fields with whatever the caller submits, with no check that the new content preserves any relationship to the signer's original authority level: [6](#0-5) 

## Impact Explanation
An `Active`-permission holder who is (deliberately or inadvertently) authorized to invoke `AccountPermissionUpdateContract` can rewrite the account's `Owner` permission to grant themselves (or a colluding address) full Owner-level control, entirely bypassing the intended lower-privilege scope of an `Active` key. This mirrors the reported bug class exactly: a delegated/manager-tier role escalates or entrenches itself at the top tier. Because permission changes take effect immediately on `execute`, this also enables a front-running scenario identical to the one in the report — if the true account owner submits a transaction to revoke the compromised `Active` permission, the holder of that permission can race to submit their own `AccountPermissionUpdateContract` transaction first, rewriting `owner_permission` to retain (or gain) control before the revocation is processed. This constitutes unauthorized account operation / persistent account takeover for any account whose active-permission bitmap includes this contract type.

## Likelihood Explanation
Likelihood is Low-to-Medium: exploitation requires that some `Active` permission on the account already carries the `AccountPermissionUpdateContract` bit in its `operations` field — which is not the default (`getActiveDefaultOperations()` excludes it) — but there is no chain-level guard preventing an owner from setting this bit via `AccountPermissionUpdateActuator.checkPermission`'s validation against `getAvailableContractType()`, which does allow it. This can occur through misconfiguration, third-party wallet/custody tooling that grants broad Active permissions, or social engineering of an account owner into granting this specific permission.

## Recommendation
In `AccountPermissionUpdateActuator.checkPermission` (and/or `TransactionCapsule.checkPermission` / `WalletUtil.checkPermissionOperations`), explicitly forbid the `AccountPermissionUpdateContract` type bit from being set/honored within an `Active` permission's `operations` bitmap, mirroring how `SUPER_ADMIN_ROLE` is reserved in the referenced report. This should be enforced both when validating a new `Active` permission at update time and when validating a signer's authority to submit an `AccountPermissionUpdateContract` transaction, ensuring only the `Owner` permission (permissionId == 0) can ever modify account permissions.

## Proof of Concept
1. Account owner creates a custom `Active` permission whose `operations` bitmap sets the bit corresponding to `ContractType.AccountPermissionUpdateContract` (allowed today because `checkPermission` only validates against `getAvailableContractType()`, which includes this type) and submits it via `AccountPermissionUpdateContract`; `AccountPermissionUpdateActuator.validate()`/`execute()` accept it [3](#0-2) .
2. The holder of that `Active` permission crafts a new `AccountPermissionUpdateContract` transaction with `permission_id` set to their Active permission id, containing a new `owner_permission` that includes their own address with sufficient weight/threshold.
3. `TransactionCapsule.validateSignature`/`checkPermission` accepts the signature because `permission.getType() == Active` and the operations bit for `AccountPermissionUpdateContract` is set [2](#0-1) .
4. `AccountPermissionUpdateActuator.execute` applies `account.updatePermissions(...)`, replacing the account's `owner_permission` with the attacker-controlled one [7](#0-6) .
5. The attacker now holds Owner-level control; if the legitimate owner races to revoke the Active permission, the attacker's front-run transaction (step 2-4) can complete first and entrench control.
