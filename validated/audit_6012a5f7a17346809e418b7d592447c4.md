### Title
Super Representatives can set voter-reward brokerage to 100% at any time, letting them confiscate voters' entire staking reward - ([File: actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java])

### Summary
The external report describes an auction platform where the owner can change the platform fee at any time, including to 100%, leaving the auction creator with nothing. The analogous unprivileged-reachable pattern in java-tron is the Super Representative (witness) "brokerage" ratio: any account can become a witness and any TRX holder can vote for it expecting a reward split, but the witness can unilaterally reset the brokerage ratio to 100% at any time via a normal broadcast transaction, taking the voters' entire share of future rewards with no notice, timelock, or voter consent mechanism.

### Finding Description
`UpdateBrokerageActuator.execute()` lets any witness account (a role any TRX holder can acquire by registering as a witness — this is not an owner/root-only role, and voting for a witness is available to any TRX holder) freely rewrite its own brokerage percentage at any time: [1](#0-0) 

The only bound enforced in `validate()` is `0 <= brokerage <= 100`: [2](#0-1) [3](#0-2) 

That value is stored as the "pending" brokerage (`cycle = -1`) via `DelegationStore.setBrokerage(byte[] address, int brokerage)`: [4](#0-3) 

At every maintenance/cycle transition, `MaintenanceManager.doMaintenance()` copies this pending value into the next reward cycle's brokerage slot for every witness, with no check on whether it changed since voters cast their votes for that SR: [5](#0-4) 

When rewards are actually paid, `MortgageService.payReward()` looks up the brokerage for the *current* cycle and deducts that percentage of the block/transaction-fee reward for the witness before crediting the remainder to the shared voter reward pool used by `withdrawReward()`/`computeReward()`: [6](#0-5) 

Because a witness can broadcast an `UpdateBrokerageContract` transaction at any point during a cycle, they can set `brokerage = 100` right before/at the start of a new cycle in which many delegators have already voted for them (based on an earlier, lower brokerage), diverting the entire reward for that cycle to the witness's own allowance and leaving voters with 0, exactly mirroring the auction-house bug class where the fee-taking party can retroactively/unilaterally set the fee to 100% after the counterpart has already committed value (auction bid / vote-stake).

### Impact Explanation
Voters who freeze TRX and vote for a witness expecting a given reward split have no on-chain guarantee that the brokerage ratio will remain stable for the cycle(s) in which their vote is already locked in. A malicious or compromised witness operator can drain the entire voter-reward share for a cycle by setting brokerage to 100%, causing direct, unauthorized loss of staking rewards for third-party TRX holders — an accounting/reward-distribution corruption reachable purely through an ordinary broadcast transaction from an account that anyone can become (witness registration is permissionless, subject only to stake/vote thresholds), not a privileged system admin.

### Likelihood Explanation
Likely: witnesses are numerous, permissionless to become (`ApplyForWitness`), and the `UpdateBrokerageContract` transaction has no cooldown, no maximum-change-per-period restriction, and no requirement of prior voter consent — only the trivial `0-100` range check. Any witness (including one that starts with attractive low brokerage to attract votes, and later maximizes it) can perform this at will each cycle boundary.

### Recommendation
Introduce a delay/lock-in for brokerage changes analogous to fixing the auction fee at creation time — e.g., require the new brokerage to take effect only after N+1 (or more) cycles from submission (rather than the immediate next maintenance cycle), cap the maximum delta allowed per update, and/or emit an on-chain event sufficiently in advance so that voters can react (unvote) before the new rate is applied to reward computation in `MortgageService.payReward`.

### Proof of Concept
1. Witness `W` registers and sets brokerage low (e.g., 10%) to attract voters via `UpdateBrokerageContract` (`UpdateBrokerageActuator`).
2. Multiple TRX holders vote for `W`, expecting a 90/10 reward split, recorded in `AccountCapsule` votes / `DelegationStore` vote records.
3. Right before or during the cycle in which votes take effect, `W` broadcasts another `UpdateBrokerageContract` transaction setting `brokerage = 100` (allowed since `100 <= ActuatorConstant.ONE_HUNDRED`).
4. At the next `MaintenanceManager.doMaintenance()` call, this value is copied into the active cycle's brokerage entry via `delegationStore.setBrokerage(nextCycle, ...)`.
5. `MortgageService.payReward()` then computes `brokerageAmount = 100% * value`, so `value -= brokerageAmount` leaves `0` for the shared voter reward pool; voters calling `withdrawReward`/`queryReward` receive nothing for that cycle despite having voted in good faith.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
