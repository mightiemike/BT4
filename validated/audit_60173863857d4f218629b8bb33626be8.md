### Title
`LiquidityCap` on `uregistry.TokenConfig` is validated but never enforced during PRC20 minting, allowing unbounded per-token PRC20 supply inflation - (File: x/uexecutor/keeper/handler.go, x/uexecutor/keeper/evm.go)

### Summary
The Push Chain registry (`x/uregistry`) stores a `liquidity_cap` field per `TokenConfig`, described as "max supply cap for this token." [1](#0-0)  The field is required to be non-empty at registration time [2](#0-1) , mirroring the BetExpress report's pattern of a capacity limit that exists in schema/docs but is not actually enforced at the point where value is created. Every code path that mints PRC20 supply (`depositPRC20`, `CallPRC20Deposit`, `handleFailedOutbound`'s re-mint) reads only the token's PRC20 contract address and amount from `TokenConfig`/`Inbound`, and never reads or checks `LiquidityCap` against the token's current or resulting total supply.

### Finding Description
`TokenConfig.LiquidityCap` is defined as the "max supply cap for this token" [3](#0-2)  and is validated to be a non-empty string on registration/update [2](#0-1) . However, a repository-wide search of the keeper packages (`x/uregistry/keeper`, `x/uexecutor/keeper`) shows no reference to `LiquidityCap` anywhere outside of type definitions, proto marshal/unmarshal code, and tests. In particular:

- `depositPRC20` (called from `ExecuteInboundFunds`, CEA/GAS_AND_PAYLOAD paths, and `handleFailedOutbound`) looks up `TokenConfig` only to resolve the `NativeRepresentation.ContractAddress` (the PRC20 address), then calls `CallPRC20Deposit` with the attacker/validator-observed `Amount` from the `Inbound` — no cap check against `LiquidityCap` occurs. [4](#0-3) 
- `CallPRC20Deposit` mints PRC20 tokens on the `UNIVERSAL_CORE` handler contract for whatever `amount` is passed, with no supply-cap parameter or check performed by the Cosmos-side keeper before invoking the EVM call. [5](#0-4) 
- The re-mint path on a failed/reverted outbound (`handleFailedOutbound`) similarly calls `CallPRC20Deposit` directly with the outbound's `Amount`, again without any liquidity-cap check. [6](#0-5) 

Because inbound amounts and asset addresses ultimately originate from unprivileged external-chain events that Universal Validators vote on and honest UVs relay faithfully (the report is scoped to honest validators/nodes), a user who can generate a large or repeated set of inbound deposit events on a supported external chain for a specific whitelisted token can cause the Push Chain module to mint an amount of PRC20 supply for that token that has no relationship to the `LiquidityCap` the registry admin configured. This is the direct structural analog of the audited BetExpress bug: a numeric ceiling exists in configuration/schema (`reinforcementAbility` in the original report, `LiquidityCap` here) but the code path that actually creates/locks value (bet placement locking LP liquidity vs. inbound-triggered PRC20 minting) does not consult it.

### Impact Explanation
If unenforced, `LiquidityCap` provides no real limit on how much PRC20 supply can be minted for a given whitelisted token via legitimate (non-privileged) inbound deposit flows. This directly corrupts PRC20 accounting invariants (the "PRC20 or native asset accounting" invariant in the impact gate): the on-chain PRC20 supply for a token can grow unbounded relative to the registry's intended cap, potentially exceeding real backing liquidity on the source chain/vault and creating a mismatch that could be exploited when swapping/withdrawing PRC20 back to native assets (e.g., via `CallPRC20DepositAutoSwap` or outbound flows), effectively enabling unauthorized minting of value beyond the configured/intended ceiling.

### Likelihood Explanation
Likelihood is high relative to the original report's low likelihood, because no attacker capital lockup, precise timing window, or coordinated cross-condition exploitation is required — an ordinary unprivileged user can simply cause repeated or large inbound deposit events (subject only to real funds held on the source chain and gateway/vault mechanics there) for a token whose registry entry has a `liquidity_cap` intended to bound supply. The condition is reachable through the standard `MsgVoteInbound` → ballot finalization → `ExecuteInboundFunds`/`depositPRC20` path with entirely honest validators and honest nodes.

### Recommendation
Enforce `TokenConfig.LiquidityCap` at the point where PRC20 supply is minted. Concretely:
- Before calling `CallPRC20Deposit` (in `depositPRC20`, `x/uexecutor/keeper/handler.go`, and in `handleFailedOutbound`, `x/uexecutor/keeper/outbound.go`), query the PRC20 contract's current total supply (or track it in module state) and reject/queue the deposit if `currentSupply + amount > LiquidityCap`.
- Alternatively, enforce the cap inside the `UNIVERSAL_CORE`/PRC20 handler contract itself (`depositPRC20Token`) so it is impossible to bypass regardless of which Cosmos-side caller invokes it, mirroring the recommendation from the original report to bind the limit at the point of value creation rather than leaving it as an advisory configuration value.
- Add integration tests analogous to `token_config_test.go` but that actually exercise the deposit path and assert failure/rejection once `LiquidityCap` is exceeded.

### Proof of Concept
Conceptual PoC (cannot be executed without live devnet access):
1. Registry admin adds a `TokenConfig` for `USDC` on `eip155:11155111` with `liquidity_cap = "1000000000000000000000000"` (1,000,000 * 10^18), as done in the test fixtures. [7](#0-6) 
2. An unprivileged user deposits real USDC into the gateway contract on Ethereum Sepolia in amounts that, cumulatively across many inbound events (each individually valid), sum to well beyond `1,000,000,000,000,000,000,000,000` units.
3. Universal Validators (honest, following protocol) observe and vote `MsgVoteInbound` for each deposit; quorum is reached each time via the generic ballot machine.
4. `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints the corresponding PRC20 amount every time, as shown in `x/uexecutor/keeper/handler.go:12-46` and `evm.go:262-303`, with no check against `LiquidityCap`.
5. Total minted PRC20 supply for the token exceeds the configured `liquidity_cap`, with no error, revert, or rejection anywhere in the flow — confirmed by the absence of any `LiquidityCap` reference in `x/uexecutor/keeper/*.go` or `x/uregistry/keeper/*.go`.

Note: due to index size limits, some file contents (e.g., full `x/uregistry/keeper/keeper.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `execute_inbound_funds_and_payload.go`) were only partially visible; a full manual/dynamic verification with terminal access to the repository and a running devnet would give higher confidence that no cap check exists elsewhere (e.g., inside the Solidity `UNIVERSAL_CORE`/PRC20 contracts, which are outside this Go codebase's scope and not indexed here).

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}

// handleFailedOutbound mints back the bridged tokens to the revert recipient,
// then attempts to refund any excess gas (gasFee - gasFeeUsed) just like a
// successful outbound would. Both operations are recorded on the outbound.
func (k Keeper) handleFailedOutbound(ctx sdk.Context, utxId string, outbound types.OutboundTx, obs *types.OutboundObservation) error {
	// Only revert bridged funds for funds-related tx types
	if outbound.TxType == types.TxType_FUNDS || outbound.TxType == types.TxType_GAS_AND_PAYLOAD ||
		outbound.TxType == types.TxType_FUNDS_AND_PAYLOAD {

		// Decide revert recipient safely
		recipient := outbound.Sender
		if outbound.RevertInstructions != nil &&
			outbound.RevertInstructions.FundRecipient != "" {
			recipient = outbound.RevertInstructions.FundRecipient
		}

		amount := new(big.Int)
		amount, ok := amount.SetString(outbound.Amount, 10)
		if !ok {
			return fmt.Errorf("invalid amount: %s", outbound.Amount)
		}
		receipt, err := k.CallPRC20Deposit(ctx, common.HexToAddress(outbound.Prc20AssetAddr), common.HexToAddress(recipient), amount)

		pcTx := types.PCTx{
			Sender:      outbound.Sender,
			BlockHeight: uint64(ctx.BlockHeight()),
		}
		// Capture tx hash from receipt even on EVM revert for debugging.
		if receipt != nil {
			pcTx.TxHash = receipt.Hash
			pcTx.GasUsed = receipt.GasUsed
		}
		if err != nil {
			pcTx.Status = "FAILED"
			pcTx.ErrorMsg = err.Error()
			outbound.PcRevertExecution = &pcTx
			// Re-mint failed — mark as ABORTED for manual intervention
			return k.AbortOutbound(ctx, utxId, outbound,
				fmt.Sprintf("failed to re-mint tokens for revert: %s", err.Error()))
		}
		pcTx.TxHash = receipt.Hash
		pcTx.GasUsed = receipt.GasUsed
		pcTx.Status = "SUCCESS"
		outbound.PcRevertExecution = &pcTx
		k.Logger().Info("outbound failed: funds re-minted for revert",
			"utx_id", utxId,
			"outbound_id", outbound.Id,
			"tx_hash", receipt.Hash,
		)
	}
