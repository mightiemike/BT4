### Title
Delegate action (NEP-366/NEP-611 meta-transaction) signatures lack chain/network binding, enabling cross-network signature replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
The signing scheme used for meta-transactions (`SignedDelegateAction`/`VersionedSignedDelegateAction`, NEP-366/NEP-611) hashes only the delegate action's fields plus a NEP-number discriminant — it never binds the signature to a specific chain, genesis, or network identifier. Because NEAR-implicit accounts are pure deterministic functions of the signer's public key, the *same* account id and full-access key are reproducible on any independent nearcore-based network. A `SignedDelegateAction` produced for use on one network can therefore be replayed verbatim on a different nearcore-based network (e.g. testnet vs. another independently operated nearcore chain, or any two networks sharing the scheme), causing the delegated actions to execute there without the user's intent — this is the same missing-chain-ID signature-replay bug class described in the report.

### Finding Description
The delegate-action signature hash is computed by `SignableMessage::sign`/`DelegateAction::get_nep461_hash`: [1](#0-0) 

The `MessageDiscriminant` only encodes the NEP number (366 or 611), not any network/genesis identifier: [2](#0-1) 

The hashed payload (`DelegateAction`) contains only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key` — no chain/genesis id: [3](#0-2) 

`SignedDelegateAction::verify()` and the V2/gas-key variant `VersionedSignedDelegateAction::verify()` only check this hash against the signature and public key — again with no chain binding: [4](#0-3) 

At apply time, `apply_delegate_action` verifies the signature, checks `max_block_height` against the *local* chain's current block height, matches `sender_id`, and validates the access-key nonce — but never checks any chain/genesis identifier: [5](#0-4) 

This is unlike ordinary `SignedTransaction`s, which embed a `block_hash` referencing an actual recent block of the specific chain they were built for, making cross-chain replay of ordinary transactions practically infeasible (the block hash from one independent network essentially never matches an actual block on another network). `DelegateAction.max_block_height`, in contrast, is a bare integer with no relationship to any specific chain's block history, so it provides no chain-binding at all.

Compounding this, NEAR-implicit accounts are fully deterministic from the public key (`account_id = hex(public_key)`), so the identical account id and full-access key are guaranteed to exist wherever the same key is used to create an implicit account on any nearcore-based network: [6](#0-5) [7](#0-6) 

### Impact Explanation
An attacker who observes a `SignedDelegateAction`/`VersionedSignedDelegateAction` intended for one nearcore-based network (e.g., a relayer's inbox, testnet, or any independently operated nearcore deployment) can resubmit the identical bytes as the `Action::Delegate`/`Action::DelegateV2` payload of a transaction on a different nearcore-based network. If the target account (deterministically the same for NEAR-implicit accounts, or coincidentally provisioned the same way on both networks) has a matching access-key nonce and the `max_block_height` has not yet been exceeded on that network, the relayer on that network will unwittingly execute the exact same delegated actions (transfers, `AddKey`, function calls, etc.) that the user only authorized for the original network. This results in unauthorized execution/value movement on a network the signer never intended to interact with, without requiring any additional secret or interaction from the victim — satisfying the "unauthorized value movement" impact bar.

### Likelihood Explanation
Exploitation only requires capturing one valid `SignedDelegateAction` (these are routinely passed to/through relayers, sometimes over public RPC, and are explicitly designed to be relayed by a third party) and resubmitting it as-is on another nearcore-based network where the corresponding account/key/nonce state matches. No cryptographic break or privileged access is needed — a single unprivileged transaction resubmission by any relayer/RPC caller suffices, and NEAR's protocol explicitly supports many independent networks (testnet, mainnet, and any custom nearcore deployment) running the identical signing/verification code.

### Recommendation
Bind the NEP-366/NEP-611 signable message to the target chain, e.g. by including the network's `genesis_id`/chain identifier (analogous to how `SignedTransaction.block_hash` binds ordinary transactions to a specific chain's history) inside `SignableMessage`/`DelegateAction`/`DelegateActionV2`, and enforce that bound value against the runtime's own genesis/chain id in `apply_delegate_action` before honoring the delegate action.

### Proof of Concept
1. On Network A, Alice (holder of ED25519 keypair `K`) creates the NEAR-implicit account `hex(K.public)` via a transfer (per `action_implicit_account_creation_transfer`), giving it a full-access key with nonce `N`.
2. On Network B (a separate nearcore-based deployment), an attacker also funds the implicit account `hex(K.public)` via a transfer, which likewise creates a full-access key with nonce `N` for the same public key (per the same deterministic derivation).
3. Alice signs a `DelegateAction{sender_id: hex(K.public), receiver_id: victim, actions: [Transfer{deposit}], nonce: N+1, max_block_height: H}` intended for a relayer on Network A only, per `DelegateAction::get_nep461_hash`/`SignedDelegateAction::sign` (`core/primitives/src/action/delegate.rs:92-95`).
4. The attacker, who observed this `SignedDelegateAction` (e.g., as the relayer or via public mempool/RPC), wraps the identical bytes into an `Action::Delegate` in a transaction submitted to Network B before block height `H`.
5. `apply_delegate_action` on Network B (`runtime/runtime/src/actions.rs:453-497`) verifies the signature successfully (no chain check exists), confirms `max_block_height` and nonce match, and executes the `Transfer` action on Network B — moving funds Alice never authorized to be moved on Network B.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

impl VersionedSignedDelegateAction {

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }
