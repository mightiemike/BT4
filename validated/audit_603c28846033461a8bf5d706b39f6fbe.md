## Findings Summary

I traced the external report's core invariant — "a value that is supposed to authenticate a specific committed object can silently validate against a different, attacker-relevant object" — to Aptos's replay/state-commitment verification path, specifically `TransactionOutput::ensure_match_transaction_info` in `types/src/transaction/mod.rs`.

### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash checks, letting a state root divergent from VM output pass replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`ensure_match_transaction_info` is the authenticated-equality check used by `db-tool`'s `replay_on_archive` verifier and `aptos-debugger` to confirm a freshly re-executed `TransactionOutput` matches the historically committed `TransactionInfo` fetched from backup/archive data. [1](#0-0) [2](#0-1) 

### Finding Description
The function validates status, gas used, write-set hash (`state_change_hash`), and event root hash, but its own inline comment admits it intentionally omits the state checkpoint hash comparisons: [3](#0-2) 
This means the actual resulting state root (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) recorded in the archived `TransactionInfo` is never checked against the state root the re-executed VM output would have produced. The comment explicitly notes that this allows `db-tool`'s `replay_on_archive` (line 392 call site) to "report a successful replay even when the authenticated position state root diverges from local execution."

### Impact Explanation
`state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are the fields that bind a `TransactionInfo` (and therefore the accumulator leaf that is Merkle-proven against a `LedgerInfo`) to the actual post-execution state tree root. Because the comparator only checks write-set hash, gas, status, and event root, an archive/backup dataset whose write set matches but whose recorded state root was corrupted (e.g. due to a storage bug, a malicious archive provider, or a bit-flip in a Merkle root field) would pass `replay_on_archive` verification undetected. Given this task's "Proof And Storage Pivots" (accumulators, JMT structures, restore paths must preserve deterministic proof binding; replay paths must not reinterpret committed data into a different ledger state), this is a real gap in the tooling meant to catch exactly that class of divergence.

### Likelihood Explanation
This is a real, currently-shipped gap (not hypothetical): the code comment itself documents the exact scenario and names the tool (`replay_on_archive`) and the exact preconditions (enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`). It requires no privileged access to trigger — only an archive/backup source with correct write-set/event data but a mismatched state root, which is plausible under storage corruption, partial data loss, or backup tampering scenarios that `replay_on_archive` is specifically meant to detect.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s locally computed state checkpoint hash(es) against `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, and `position_state_checkpoint_hash()` before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, as the TODO already prescribes, and gate any related replay-verify success reporting on this check.

### Proof of Concept
Not independently constructible from the index alone — confirming an end-to-end trigger would require assembling an archive/backup file with a valid write set/events but a corrupted `state_checkpoint_hash`, and running it through `replay_on_archive`.

**Caveat / uncertainty:** I could not fully verify from the indexed code whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently enabled on mainnet, or whether some other layer (e.g. `state_checkpoint_output.rs`, `execution_output.rs`) independently enforces this state-root binding during normal (non-replay-tool) commit/consensus execution — that would materially change the severity, since this gap may only affect the offline `db-tool` verification path and not the live commit path itself. Given index size limits, some file contents (e.g. full `execution_output.rs`, `state_checkpoint_output.rs`, and consensus commit call sites) were not fully inspected; a Devin session with full repo access would be needed to confirm whether this gap is confined to the replay-verify tool or also reachable in the live state-sync/commit path.
