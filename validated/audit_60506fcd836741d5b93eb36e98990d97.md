Based on my investigation, I found a concrete analog of the "insufficient boundary/delimiter validation" bug class from the external report.

### Title
Unhardened colon-delimited concatenation in `GetInboundUniversalTxKey`/`GetPcUniversalTxKey`/`GetOutboundRevertId` allows UTX-identity boundary-shift collisions - (File: `x/uexecutor/types/keys.go`)

### Summary
The external report's core lesson is that concatenating variable-length, attacker-influenced fields with a fixed delimiter (`"bh="`, `:`) without per-field length/hash-boundary protection lets one field's content "shift" where the parser thinks the next field starts, causing two logically different inputs to be treated as the same (or vice versa). The same class of bug exists in Push Chain's UTX-identity key derivation.

### Finding Description
`x/uexecutor/types/keys.go` defines two different concatenation strategies for deriving keys from `Inbound`/`Outbound` fields:

- `hashFields` — used for `GetInboundBallotKey` and `GetOutboundBallotKey` — explicitly hashes each field individually before joining with `:`, with an inline comment stating the exact rationale from the external report's bug class: [1](#0-0) 

- In contrast, `GetInboundUniversalTxKey` (the canonical UTX-identity key — the single source of truth for "has this inbound already been processed") builds its digest via naive, un-hashed field concatenation: [2](#0-1) 

The same naive pattern (`fmt.Sprintf("%s:%s:...")` over raw, un-hashed fields) is reused in `GetPcUniversalTxKey`, `GetOutboundRevertId`, and `GetRescueFundsOutboundId`: [3](#0-2) [4](#0-3) 

This key is the sole gate against double-processing: `VoteInbound` checks `HasUniversalTx(ctx, universalTxKey)` before finalizing, and rejects the inbound if the key already exists: [5](#0-4) 

If `TxHash` or `LogIndex` could ever contain a `:` character, two distinct `(chain, txHash, logIndex)` tuples could produce the identical concatenated string and thus the identical UTX key — exactly the "boundary shift" collision the report describes for `"bh="`/DKIM-header parsing, and exactly the collision `hashFields` was purpose-built to prevent elsewhere in this same file.

### Impact Explanation
If exploitable, a second genuine inbound event could be silently treated as "already exists" and dropped (permanent loss/freezing of a user's bridged funds since no UTX would be created for it), or conversely a legitimate first inbound could be blocked/overwritten by a colliding key from unrelated data. Under the "Push Chain Allowed Impact Gate," this maps to "permanent loss/freezing of user funds" and "corruption of canonical UniversalTx state," both in scope.

### Likelihood Explanation
I could **not confirm actual exploitability** within the time available. `TxHash` and `LogIndex` are populated from real on-chain data (EVM tx hashes are fixed-format 0x-hex, Solana signatures are base58, log indices are typically decimal integers formatted by the event-parsing code in `universalClient/chains/evm/event_parser.go` / `universalClient/chains/svm/event_parser.go`), none of which naturally contain `:`. I was not able to fully trace every code path that populates `Inbound.TxHash`/`Inbound.LogIndex` (including the raw/CEA paths) to rule out a case where these strings could be attacker-influenced free-form text containing `:`. `ValidateBasic()` for `Inbound` only checks non-emptiness of `LogIndex`/`TxHash`, not character set: [6](#0-5) 

Given this uncertainty, I cannot assert a concrete unprivileged trigger with full confidence — this should be verified by checking whether any attacker-influenced value can inject a `:` into `TxHash` or `LogIndex` before reaching `GetInboundUniversalTxKey`.

### Recommendation
Regardless of current exploitability, harden `GetInboundUniversalTxKey`, `GetPcUniversalTxKey`, `GetOutboundRevertId`, and `GetRescueFundsOutboundId` to use the same `hashFields`-style per-field hashing already used for ballot keys, so the UTX-identity derivation is injective by construction rather than relying on the implicit assumption that `TxHash`/`LogIndex` never contain the delimiter character. This mirrors recommendation I/II from the external report: don't rely on "this can't happen given upstream format," make the boundary-safety local and structural.

### Proof of Concept
Not executable without confirming a code path that can inject `:` into `Inbound.TxHash` or `Inbound.LogIndex`. Conceptually: if `TxHash = "0xabc:1"`, `LogIndex = ""` produces the same concatenated string `"chain:0xabc:1:"` as `TxHash = "0xabc"`, `LogIndex = "1:"` (note trailing behavior needs exact reproduction), the two would hash to the same `universalTxKey`, and `HasUniversalTx` would reject the second as a duplicate.

```go
// GetInboundUniversalTxKey: UTX identity from canonical (source_chain, tx_hash,
// log_index). Canonicalizes locals; caller's inbound is not mutated.
func GetInboundUniversalTxKey(inbound Inbound) string {
	chain := strings.TrimSpace(inbound.SourceChain)
	txHash := utils.LenientCanonicalizeTxHash(chain, inbound.TxHash)
	logIndex := strings.TrimSpace(inbound.LogIndex)
	data := fmt.Sprintf("%s:%s:%s", chain, txHash, logIndex)
	hash := sha256.Sum256([]byte(data))
	return hex.EncodeToString(hash[:]) // hash[:] converts [32]byte → []byte
}
```

```go
// hashFields = sha256( hex(sha256(domain)) : hex(sha256(f0)) : ... ). Per-field
// hashing makes it injective — a sub-hash can't contain ':', so no field value
// can shift a boundary and collide with a different tuple.
func hashFields(domain collections.Prefix, parts ...string) string {
	hashed := make([]string, 0, len(parts)+1)
	d := sha256.Sum256(domain.Bytes())
	hashed = append(hashed, hex.EncodeToString(d[:]))
	for _, p := range parts {
		sum := sha256.Sum256([]byte(p))
		hashed = append(hashed, hex.EncodeToString(sum[:]))
	}
	final := sha256.Sum256([]byte(strings.Join(hashed, ":")))
	return hex.EncodeToString(final[:])
}
```

```go
// GetOutboundRevertId generates a deterministic outbound ID for an inbound-revert
// outbound. sourceChain is the CAIP-2 identifier of the chain the inbound came from
// (e.g. "eip155:1"); logIndex disambiguates multiple bridge events in the same
// source tx. This ID is also used as the subTxId on the source-chain gateway call,
// providing replay protection — so it must be unique per inbound event.
func GetOutboundRevertId(sourceChain, inboundTxHash, logIndex string) string {
	data := fmt.Sprintf("%s:%s:%s:REVERT", sourceChain, inboundTxHash, logIndex)
	hash := sha256.Sum256([]byte(data))
	return hex.EncodeToString(hash[:])
}

// GetRescueFundsOutboundId generates a deterministic outbound ID for a rescue-funds
// outbound. pushChainCaip is the CAIP-2 identifier of Push Chain (e.g. "eip155:2240"),
// mirroring the convention used by GetPcUniversalTxKey. This ID is also used as the
// subTxId on the source-chain gateway call, providing replay protection.
func GetRescueFundsOutboundId(pushChainCaip string, pcTxHash string, logIndex string) string {
	data := fmt.Sprintf("%s:%s:%s:RESCUE", pushChainCaip, pcTxHash, logIndex)
	hash := sha256.Sum256([]byte(data))

}
```
