### Title
Open Redirect via Unauthenticated `exitIframe` Parameter Bypassing Domain Whitelist Check - ([File: packages/apps/shopify-app-remix/src/server/authenticate/admin/helpers/validate-redirect-url.ts])

### Summary
The Curve report flags that user-supplied oracle addresses are trusted without any whitelist, letting attacker-controlled values silently override the intended trust boundary. The exact same class of bug exists in the `sanitizeRedirectUrl` helper used by `shopify-app-remix` and `shopify-app-react-router`: it is meant to restrict redirects to the app's own domain, but because it resolves the untrusted value with `new URL(redirectUrl, domain)`, an attacker-supplied **absolute** URL completely overrides the "whitelisted" `domain` argument, defeating the intended restriction.

### Finding Description
`sanitizeRedirectUrl` is supposed to act as a whitelist gate: callers pass the app's own base domain plus a candidate redirect target, expecting the function to reject anything outside that domain. [1](#0-0) 

The check only validates that the URL is not a `file:` URI, has no whitespace, has no doubled path separators, and uses `http:`/`https:` (optionally forcing `https:` when `requireSSL` is set). It never verifies that the resulting `url.hostname`/`url.origin` matches the `domain` argument. Per the WHATWG URL spec, `new URL(absoluteUrl, base)` returns `absoluteUrl` untouched whenever `absoluteUrl` is itself absolute — the `base`/`domain` parameter is silently ignored. So `sanitizeRedirectUrl(config.appUrl, 'https://attacker.example/')` returns `https://attacker.example/` successfully, passing every check (correct protocol, no file scheme, no whitespace, HTTPS satisfies `requireSSL`).

This function is invoked with attacker-reachable, unauthenticated input in `renderAppBridge`: [2](#0-1) 

`renderAppBridge` is called from the exit-iframe handler inside `authStrategyFactory`, which reads the `exitIframe` query parameter directly off the request URL, with no signature or session check at all, and this handler runs before any shop/host validation or authentication in the request-handling pipeline: [3](#0-2) [4](#0-3) 

The `respondToExitIframeRequest` check fires purely on `url.pathname === config.auth.exitIframePath`, with no HMAC, session-token, or origin verification of the `exitIframe` value before it is handed to `renderAppBridge` → `sanitizeRedirectUrl`. The identical pattern (same `validate-redirect-url.ts`, same `render-app-bridge.ts` structure) exists in `@shopify/shopify-app-react-router`.

### Impact Explanation
Any unauthenticated actor can send a GET request such as `GET /auth/exit-iframe?exitIframe=https://attacker.example&shop=<any-shop>.myshopify.com` to a Shopify embedded app built on `shopify-app-remix`/`shopify-app-react-router`. The server responds with HTML containing `<script>window.open("https://attacker.example/", "_top")</script>`, breaking the merchant out of the Shopify Admin iframe and top-level-navigating their browser to an attacker-controlled domain. This is a classic open-redirect, useful for phishing (fake OAuth/consent pages that mimic Shopify's install flow), which can be chained with social engineering to steal merchant credentials or trick a merchant into re-authorizing a malicious OAuth client.

### Likelihood Explanation
This is trivially reachable with a single crafted URL, requires no authentication, no valid session, and no secret knowledge — only knowledge of the app's exit-iframe path (a well-known, standardized Shopify app-bridge convention: `config.auth.exitIframePath`). The existing test suite only validates rejection of `file:///...` URIs and relative-path edge cases; it never asserts that `sanitizeRedirectUrl` rejects a same-protocol absolute URL pointing to a different host, confirming this gap was not caught by tests.

### Recommendation
Enforce an actual origin whitelist in `isSafe`/`sanitizeRedirectUrl`: after constructing `url = new URL(redirectUrl, domain)`, explicitly compare `url.origin` (or `url.hostname`) against the parsed `domain`'s origin/hostname (and any other origins the app is intentionally willing to redirect to, e.g., `myshopify.com` admin domains) and reject the URL if it does not match. Do not rely on the base-URL parameter of the `URL` constructor as an implicit trust boundary, since absolute inputs bypass it entirely.

### Proof of Concept
1. Deploy any embedded app using `@shopify/shopify-app-remix` (or `shopify-app-react-router`) with default config (`config.auth.exitIframePath` defaulting to `/auth/exit-iframe`).
2. As an unauthenticated client, request:
   `GET https://<app-host>/auth/exit-iframe?exitIframe=https%3A%2F%2Fattacker.example&shop=example.myshopify.com`
3. Observe the HTTP 200 response contains:
   `<script>window.open("https://attacker.example/", "_top")</script>`
4. If loaded inside the Shopify Admin iframe context (or shared as a direct link), the victim's top-level browsing context is navigated to `https://attacker.example`, completing the open redirect.

function isSafe(
  domain: string,
  redirectUrl: unknown,
  requireSSL: boolean | undefined = true,
): redirectUrl is string {
  if (typeof redirectUrl !== 'string') {
    return false;
  }

  if (
    FILE_URI_MATCH.test(redirectUrl) ||
    WHITESPACE_CHARACTER.test(redirectUrl)
  ) {
    return false;
  }

  let url: URL;

  try {
    url = new URL(redirectUrl, domain);
  } catch (_error) {
    return false;
  }

  if (INVALID_RELATIVE_URL.test(url.pathname)) {
    return false;
  }

  if (!VALID_PROTOCOLS.includes(url.protocol)) {
    return false;
  }

  if (requireSSL && url.protocol !== 'https:') {
    return false;
  }

  return true;
}
