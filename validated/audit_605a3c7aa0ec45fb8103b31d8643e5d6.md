### Title
CREATE2 front-running enables deterministic-address squatting and unrecoverable DoS against legitimate contract deployment - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
The Morpho report's root cause is generic: a create-style operation derives a deterministic identifier from attacker/creator-controllable inputs, and the creation path reverts unconditionally if that identifier is "already taken," letting an attacker who can predict the identifier front-run and permanently block/hijack the legitimate creation. `java-tron`'s TVM `CREATE2` opcode exhibits the same structural pattern: the target address is fully deterministic from `(sender, salt, init-code)` and can be computed off-chain before the transaction lands, and `createContractImpl` treats an "already existing" address as an unrecoverable failure of that specific deployment attempt.

### Finding Description
`CREATE2` computes the new contract's address deterministically via `WalletUtil.generateContractAddress2(senderAddress, salt, programCode)` and passes it into `createContractImpl`: [1](#0-0) 

Inside `createContractImpl`, the engine checks whether an account/contract already exists at that address, and — post-Constantinople — only blocks the deployment if the existing account is itself a contract (`isContractExist`): [2](#0-1) 

If `contractAlreadyExists` is `true`, the create call unconditionally fails with a hard exception instead of allowing the legitimate deployer any alternative path: [3](#0-2) 

Because the salt, sender (factory) address, and init code are all known/predictable ahead of time (the test suite explicitly demonstrates address prediction with `getCreate2Addr` mirroring the exact TRON CREATE2 formula), any third party can precompute the resulting address before the legitimate creator's transaction is mined: [4](#0-3) 

An attacker who observes a pending `CREATE2` deployment (e.g., in the mempool, or simply by knowing the deterministic parameters used by a well-known factory) can front-run it by deploying **any** contract code to that exact address first. Once a contract genuinely occupies the address, `isContractExist` returns true and the legitimate deployer's `CREATE2` call permanently fails for that `(sender, salt)` pair — the victim cannot simply "retry," since the salt/address are fixed by design (this is the entire point of CREATE2-based counterfactual deployment patterns, e.g., deterministic multisig/wallet factories, deterministic escrow/vault addresses used by exchanges and DeFi integrations on TRON).

This mirrors the Morpho bug class precisely: a deterministic, front-runnable identifier (market id / contract address) plus an "already exists → revert" guard that an attacker can trigger first to grief the legitimate actor.

### Impact Explanation
Impact is protocol/dApp-level griefing rather than direct fund theft in the base case: legitimate deterministic-deployment flows (counterfactual wallets, CREATE2-based escrow/vault factories, deterministic pool/market contracts that many TRON DeFi and exchange integrations rely on) can be permanently DoS'd for a specific `(factory, salt)` combination once an attacker occupies the predicted address with junk bytecode. Because the address is deterministic, this is not a transient failure — the deployer cannot recover that exact address, breaking any off-chain agreements or precomputed addresses that depended on it (e.g., counterfactual multisig deployment, layer-2 bridge escrow addresses, or account-abstraction wallets referenced before deployment). If integrators fund the predicted address before deployment (a common CREATE2 pattern), the attacker's squatting contract could also intercept/trap those funds depending on its bytecode, escalating to fund-loss scenarios in specific integrations.

### Likelihood Explanation
Likelihood is medium: exploitation requires the attacker to learn the `(sender, salt, init-code)` triple before the legitimate deployment transaction confirms — via mempool observation, off-chain leakage of a precomputed deterministic address, or simply knowing a public factory's deterministic salt scheme (a very common on-chain pattern for wallets/escrows). No special privilege is needed; any account can submit the front-running `CREATE`/`CREATE2` at the target address once it is known, exactly as the Morpho attacker needed only to predict the oracle contract's nonce-derived address.

### Recommendation
This is inherent to standard `CREATE2` semantics (matches Ethereum's own behavior) and is not necessarily a bug unique to this codebase, but consumers/integrators of `CREATE2` in TRON contracts (and TRON tooling/documentation) should be warned about the front-running risk and encouraged to:
- Avoid relying on deterministic addresses that are computable by third parties before deployment, or
- Bind the salt to values only the legitimate deployer can produce/reveal atomically with the deployment (e.g., commit-reveal schemes), or
- Add application-level ownership/initialization checks after deployment (rather than relying solely on "address didn't exist yet") so that a griefing contract at the predicted address cannot silently absorb value or be treated as legitimate.
Since `createContractImpl`'s existence check is standard EVM/TVM behavior, no core-protocol code change is strictly required; the actionable recommendation is developer guidance/hardening for `CREATE2`-dependent TRON dApps.

### Proof of Concept
1. A factory contract computes `predictedAddr = CREATE2(factory, salt, initCodeHash)` off-chain (as shown in the repo's own `FreezeTest.sol` `getCreate2Addr` helper) and a legitimate deployer intends to deploy their contract there.
2. An attacker monitoring pending transactions (or who otherwise learns `salt`/`initCodeHash`, e.g. a public/well-known factory pattern) submits their own transaction that performs `CREATE`/`CREATE2` producing bytecode at that same `predictedAddr` first.
3. On confirmation, `getContractState().getAccount(newAddress)` returns a non-null, contract-typed account, so `isContractExist` returns `true` for the legitimate deployer's later transaction. [2](#0-1) 
4. The legitimate deployer's `CREATE2` call then executes the `contractAlreadyExists` branch and fails with `"Trying to create a contract with existing contract address: 0x..."`. [5](#0-4) 
5. Because the salt and factory address are fixed, the legitimate deployer cannot retry with the same parameters — the deployment is permanently blocked at that address, analogous to the Morpho market being permanently "already created" by a front-runner.

*Note:* The `contractAlreadyExists` check depends on `VMConfig.allowTvmConstantinople()`/`isContractExist` gating — I could not fully trace `isContractExist`'s implementation body within the available index (only its two call sites in `Program.java` were found), so the exact conditions under which a non-contract account at the address does or does not block re-use could not be fully confirmed from the indexed code. A Devin session with full repository access would be needed to inspect `isContractExist` in full and confirm edge cases (e.g., whether a plain TRX-funded EOA-like account at the predicted address also blocks deployment pre-code, which would lower the bar for the griefing attack even further).

```text
    // selector: 0xbb63e785
    // Predict CREATE2 address without deploying
    //
    // TRON CREATE2 formula (differs from standard EVM):
    //   address = keccak256(prefix ++ sender[20] ++ salt[32] ++ keccak256(code)[32])[12:]
    //
    // - Standard EVM uses 0xff as prefix (magic byte)
    // - TRON replaces it with the address prefix byte (0x41 for mainnet, 0xa0 for testnet)
    // - This value is hardcoded at compile time by tron-solc
    //
    function getCreate2Addr(uint256 salt) public view returns (address) {
        bytes memory bytecode = type(FreezeContract).creationCode;
        bytes32 hash = keccak256(
            abi.encodePacked(
                bytes1(0x41),       // TRON mainnet address prefix
                address(this),      // 20-byte factory address
                salt,               // 32-byte salt
                keccak256(bytecode) // 32-byte code hash
            )
        );
        return address(uint160(uint256(hash)));
    }
```
