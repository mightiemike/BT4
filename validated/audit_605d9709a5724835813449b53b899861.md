### Title
Signature-malleable duplicate microblock headers with identical content bypass PoisonMicroblock fork-identity check - ([File: stacks-codec/src/transaction.rs])

### Summary
`TransactionPayload::consensus_deserialize` for `PoisonMicroblock` only requires that the two headers differ in *some* field (`h1 == h2` on the full struct, including the `signature` field) and that they share either `sequence` or `prev_block`. It never verifies that the headers actually diverge in `tx_merkle_root` (i.e., represent genuinely different microblock content). Because ECDSA signatures are malleable ((r,s) → (r, n-s) with adjusted recovery id, computable by anyone from a single observed signature, with no private key needed), a second header can be produced with identical `sequence`, `prev_block`, `tx_merkle_root`, `version`, and `timestamp`, differing only in signature bytes, and still recover to the same miner pubkey hash.

### Finding Description
The broken equality is: **"two headers accepted as PoisonMicroblock evidence" should imply "two headers with divergent `tx_merkle_root`/content signed by the same key"**, but the code only enforces "two headers structurally unequal AND sharing sequence-or-prev_block."

At `stacks-codec/src/transaction.rs:2905-2925`: [1](#0-0) 
the checks performed are:
1. `h1 == h2` (derived `PartialEq` over the *entire* header struct, including `signature`) — rejects only bit-for-bit identical headers.
2. `h1.sequence != h2.sequence && h1.prev_block != h2.prev_block` — rejects only if **both** sequence and prev_block differ.

Neither check inspects `tx_merkle_root`. If an attacker takes a single genuine, already-broadcast microblock header `h1` (sequence N, prev_block P, tx_merkle_root R, signature `sig1`), they can compute a malleated signature `sig2` from `sig1` alone (public transformation, no private key required) and construct `h2` identical to `h1` in every field except `signature`. This passes both checks: `h1 != h2` (signature differs) and `h1.sequence == h2.sequence` (satisfies the OR, since the rejection requires both mismatches). The resulting `TransactionPayload::PoisonMicroblock(h1, h2)` is accepted by the codec even though `h1` and `h2` describe the exact same microblock content — there was no equivocation by the miner, only a resigned/malleated duplicate.

Downstream, the pubkey-recovery equality check (`check_recover_pubkey`) used by mempool admission and by the poison-handling logic in `stackslib/src/chainstate/stacks/db/transactions.rs` and `stackslib/src/chainstate/stacks/db/blocks.rs` verifies only that both headers recover to the same miner pubkey hash — which they do, since the malleated signature is valid for the identical message under the same key. I was unable to confirm within the available tool budget whether the downstream poison-processing routine additionally re-checks `tx_merkle_root` divergence before paying out/penalizing; based on the code visible in the codec layer, the *only* gate against this case is the struct-level `h1 == h2` check, which a signature-malleable duplicate trivially evades.

### Impact Explanation
If the downstream handler does not independently re-verify content divergence (`tx_merkle_root` difference), this allows a non-equivocating miner to be falsely reported as having produced two conflicting microblocks, resulting in a reward mis-payment: the reporter collects a poison-microblock bounty and the honest miner is penalized for a fork that never occurred. Per the stated severity rubric this is a "poison or reward mis-payment bounded to fees" (High), since the PoisonMicroblock payout is a bounty/penalty mechanism bounded by the microblock/tenure reward rather than a full double-spend of the entire block reward.

### Likelihood Explanation
The attacker needs only to observe one already-broadcast, validly-signed microblock header from any miner (public information) and perform a purely arithmetic ECDSA signature malleation — no private key, no stake, no privileged role, and no majority position is required. This is repeatable against any miner's microblock stream the moment a single header is public. The only uncertainty is whether an additional check further down the validation pipeline (outside the file/lines in scope) independently enforces `tx_merkle_root` divergence, which I could not fully confirm due to tool-call limits.

### Recommendation
In `TransactionPayload::consensus_deserialize` (`stacks-codec/src/transaction.rs`, PoisonMicroblock branch), explicitly require that `h1.tx_merkle_root != h2.tx_merkle_root` (or otherwise assert genuine content divergence) in addition to — not merely instead of — the sequence/prev_block OR-check, so that two headers differing only in signature bytes over an identical message are rejected as non-evidence of equivocation.
