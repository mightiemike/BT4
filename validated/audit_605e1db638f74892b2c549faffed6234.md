## Title
Wallet Contract pays the relayer fee and hard-codes the NEP-141 storage deposit amount before the underlying cross-contract transfer is confirmed to succeed, permitting fee payment / nonce consumption for a transfer that reverts - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Aurora-style `WalletContract::rlp_execute` entry point (reachable by any transaction that calls the deployed wallet contract, exactly like the Sherlock report's user-facing `_settleClaim`) fires the relayer-fee transfer as an independent promise *before* the outcome of the emulated ERC-20/base-token transfer is known, and separately hard-codes the amount attached to the NEP-141 `storage_deposit` call instead of querying the target token's real `storage_balance_bounds`. If that hard-coded value is insufficient for a token with non-standard bounds, the inner transfer fails, yet the relayer has already been paid and the nonce has already been advanced - the same "value movement finalized on one leg while the paired cross-contract transfer silently fails" pattern as the Connext `xcall` zero-slippage bug.

### Finding Description
In `inner_rlp_execute` [1](#0-0) , when the parsed transaction is an `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, a **separate, unchained** promise batch transferring `fee` to the relayer is created immediately, decoupled from whether the actual transfer action succeeds. The nonce is also incremented up-front for `ERC20Transfer` (and for `EOABaseTokenTransfer` without an address check) at lines 358-365, before the real cross-contract call is even dispatched.

Separately, for `ERC20Transfer`, if the receiver is not yet registered with the token, `nep_141_storage_balance_callback` issues a `storage_deposit` call using a **hard-coded** constant instead of the token's actual bounds: [2](#0-1) [3](#0-2) 

This is structurally identical to the reported bug class: a hard-coded parameter (there, `0` slippage; here, a fixed `1_250 * MICRO_NEAR` storage-deposit amount) is supplied to a cross-contract/cross-domain transfer step without validating it against the real, dynamic requirement of the destination contract, so the transfer step can revert while an economically significant, unconditional side-effect (the relayer fee payment, and the nonce consumption) has already been committed and is not tied to, or reverted by, the failure of the paired action.

If `storage_deposit` fails because the real bound exceeds the hard-coded constant (any custom/non-standard NEP-141 implementation, e.g. one that charges higher storage per-account, which the comment itself acknowledges is an assumption "essentially all tokens" but not all tokens follow), the chained `.then(ext.rlp_execute_callback(...))` reports `PromiseResult::Failed`. `rlp_execute_callback` only refunds the `caller_deposit` (the deposit attached to the wallet call itself, used for storage cost accounting) - it has no knowledge of, and cannot undo, the already-dispatched relayer-fee promise from `inner_rlp_execute`: [4](#0-3) 

### Impact Explanation
This results in unauthorized/unconditional value movement: the wallet-contract owner's tokens (the `fee`) are transferred to the relayer even though the intended ERC-20 transfer to the receiver never executes, and the nonce is consumed so the transaction cannot be resubmitted. This is a genuine fund-loss condition reachable purely by submitting a normal `rlp_execute` transaction/RPC call against an eth-implicit account backed by this wallet contract, matching the required "concrete unauthorized value movement" / "permanently frozen funds" bar.

### Likelihood Explanation
Triggering it only requires a target NEP-141 token whose real `storage_balance_bounds().min` exceeds the hard-coded `NEP_141_STORAGE_DEPOSIT_AMOUNT` constant (1250 micro-NEAR) - plausible for any token contract that is not the exact reference NEP-141/NEP-145 implementation, and does not require a malicious relayer or validator, only an ordinary user/relayer interacting with a non-conforming token contract.

### Recommendation
Chain the relayer-fee transfer to the resolution of the main action (e.g. include it as part of the same promise batch or in a callback conditioned on `PromiseResult::Successful`) instead of dispatching it unconditionally and independently; and replace the hard-coded `NEP_141_STORAGE_DEPOSIT_AMOUNT` with a value derived from an on-chain `storage_balance_bounds` query (or otherwise ensure fee/nonce state changes are only committed once the paired cross-contract transfer is confirmed successful).

### Proof of Concept
1. Deploy (or use) a NEP-141 token whose `storage_deposit` requires more than `1_250 * 10^18` yoctoNEAR to register a new account (a valid, standards-adjacent but non-default bound).
2. A user signs an RLP `ERC20Transfer` Ethereum-style transaction through their `WalletContract`, specifying a non-zero relayer `fee` and a `receiver_id` that is not yet registered with that token.
3. A relayer calls `rlp_execute` with this transaction. `inner_rlp_execute` immediately creates and sends the `fee` transfer to the relayer (lines 374-385) and increments the nonce (lines 358-365).
4. The wallet contract queries `storage_balance_of`, finds the receiver unregistered, and issues `storage_deposit` with the hard-coded amount (line 259) followed by `ft_transfer`. Because the token requires more than the hard-coded amount, `storage_deposit` fails, the whole promise resolves as `PromiseResult::Failed`, and `ft_transfer` never executes.
5. Result: the relayer has already received `fee`, the nonce has advanced, but the receiver never got the tokens - a definite, unrecoverable loss for the wallet owner.

    #[private]
    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
