### Title
Inconsistent withdraw-cooldown validation between wallet-API and TVM withdrawReward paths - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawRewardProcessor.java])

### Summary
Analogous to the Perpetual bug where `withdraw` and `withdrawFor` implement two different validation strengths for the same conceptual action, java-tron has two independent code paths that both withdraw a witness's accumulated `allowance` reward into balance, but they enforce different sets of preconditions: `WithdrawBalanceActuator` (the wallet/RPC `WithdrawBalanceContract`) and `WithdrawRewardProcessor` (the TVM `WITHDRAWREWARD` opcode, reachable from any smart contract). Only the former enforces the intended 24-hour withdrawal cooldown and the "must have a reward" check.

### Finding Description
`WithdrawBalanceActuator.validate()` enforces three checks before allowing a withdraw of `allowance`/reward into `balance`:
- rejects guard representatives,
- enforces a 24‑hour cooldown via `witnessAllowanceFrozenTime`,
- requires `allowance > 0 || queryReward(...) > 0`. [1](#0-0) 

The functionally equivalent TVM-reachable path, `WithdrawRewardProcessor.validate()` (invoked from `Program.withdrawReward()` via the `WITHDRAWREWARD` opcode when `allowTvmVote` is active), only rejects guard representatives — it does **not** check `latestWithdrawTime`/cooldown, nor does it require a positive reward before proceeding: [2](#0-1) 

The TVM opcode is wired up as a public, unprivileged operation gated only by the `allowTvmVote` feature flag: [3](#0-2) [4](#0-3) 

This is structurally the same class of bug as the Perpetual report: two entry points that should share the same state/precondition invariant (only the "properly cooled-down / has-reward" state should allow withdraw) diverge, with the TVM-reachable path being the permissive one — analogous to `withdraw()` in Perpetual only checking `!SETTLING` while `withdrawFor()` correctly checked `== NORMAL`.

### Impact Explanation
Any account (via a smart contract call using the `WITHDRAWREWARD` opcode) can bypass the intended 24-hour withdrawal rate limit that is enforced for the same operation through the wallet/API `WithdrawBalanceContract` path. This is an invalid-state/divergence issue: the same logical state transition (settle `allowance` into `balance`, reset `latestWithdrawTime`) is reachable from two code paths with materially different guard conditions, meaning the protocol-level restriction ("no more than once per 24h") is not actually enforced universally, only enforced for one entry point. It does not appear to enable a direct fund-theft or double-spend (the amount withdrawn is still bounded by the actual accrued `allowance`/reward at time of the call, computed via `VoteRewardUtil.withdrawReward`), so the practical severity is limited to bypassing a rate-limiting/anti-spam mechanism rather than causing loss of funds.

### Likelihood Explanation
The `WITHDRAWREWARD` opcode is reachable by any account through a deployed contract once `allowTvmVote` is enabled on the network (this is an already-activated proposal feature, as also exercised in `VoteTest`). No special privilege is required — likelihood of exploitation (as a rate-limit bypass) is high whenever the feature is active, though the resulting benefit to an attacker is limited since it does not increase the amount withdrawable.

### Recommendation
Align the precondition checks in `WithdrawRewardProcessor.validate()` with `WithdrawBalanceActuator.validate()`: add the same 24-hour cooldown check (based on `AccountCapsule.getLatestWithdrawTime()` and `DynamicPropertiesStore.getWitnessAllowanceFrozenTime()`), and/or explicitly document why the TVM path is intentionally exempt from this cooldown if that is a deliberate design decision.

### Proof of Concept
1. Enable `allowTvmVote` on a test network (already required for `WITHDRAWREWARD` to be active).
2. Deploy a contract implementing `function withdrawReward() external returns (uint) { return withdrawreward(); }` as shown in `VoteTest`. [5](#0-4) 
3. From a witness account that has recently withdrawn (i.e., `now - latestWithdrawTime < witnessAllowanceFrozenTime`), call this contract's `withdrawReward()` repeatedly. Each call succeeds through `Program.withdrawReward()` → `WithdrawRewardProcessor.validate()`/`execute()` because there is no cooldown check, whereas an equivalent `WithdrawBalanceContract` transaction submitted in the same window through `WithdrawBalanceActuator.validate()` would fail with `"The last withdraw time is ..., less than 24 hours"`. [6](#0-5)

  public void validate(WithdrawRewardParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();

    boolean isGP = CommonParameter.getInstance()
        .getGenesisBlock().getWitnesses().stream().anyMatch(witness ->
            Arrays.equals(ownerAddress, witness.getAddress()));
    if (isGP) {
      throw new ContractValidateException(
          ACCOUNT_EXCEPTION_STR + StringUtil.encode58Check(ownerAddress)
              + "] is a guard representative and is not allowed to withdraw Balance");
    }
  }

  public long withdrawReward() {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner, 0, null,
        "withdrawReward", nonce, null);

    WithdrawRewardParam param = new WithdrawRewardParam();
    param.setOwnerAddress(owner);
    param.setNowInMs(getTimestamp().longValue() * 1000);
    try {
      WithdrawRewardProcessor processor = new WithdrawRewardProcessor();
      processor.validate(param, repository);
      long allowance = processor.execute(param, repository);
      repository.commit();
      if (internalTx != null) {
        internalTx.setValue(allowance);
      }
      return allowance;
    } catch (ContractValidateException e) {
      logger.warn("TVM WithdrawReward: validate failure. Reason: {}", e.getMessage());
    } catch (ContractExeException e) {
      logger.warn("TVM WithdrawReward: execute failure. Reason: {}", e.getMessage());
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return 0;
  }
