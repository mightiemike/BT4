### Title
Out-of-bounds panic / index divergence in `decompress` due to missing bucket-offset consistency check - (File: crates/starknet_os/src/hints/hint_implementation/stateless_compression/utils.rs)

### Summary
The Cairo implementation of stateless-compression decompression (`compression.cairo`) is provably safe: `reconstruct_data` tracks per-bucket read offsets in a Cairo dict and, after reconstructing all `data_len` elements, asserts (via `dict_update`/`dict_squash`) that every bucket's final offset equals its declared length. This proves no read of `all_values` ever went past the declared bucket boundaries. The Rust port of the same algorithm, `decompress()` in `utils.rs:545-617`, reimplements the offset-tracking with a plain `Vec<usize>` (`bucket_offset_trackers`) and **never performs the equivalent final-consistency check**. It reads `all_values[*offset]` at line 612 using offsets derived purely from `bucket_index_per_elm`/header lengths taken from attacker/prover-controlled compressed felt data, with no bound proof. [1](#0-0) 

### Finding Description
`decompress` parses, from an iterator of `Felt`s:
- a header containing `data_len` and per-bucket `unique_value_bucket_lengths` and `n_repeating_values` [2](#0-1) 
- `bucket_index_per_elm`, an array of `data_len` bucket indices in `[0, TOTAL_N_BUCKETS)` [3](#0-2) 

It then computes `bucket_offsets` from the *declared* bucket lengths and, for each of `data_len` entries, indexes `all_values[*offset]` and increments the tracker for that bucket [4](#0-3) .

Nothing enforces that the number of times a given bucket index appears in `bucket_index_per_elm` is bounded by that bucket's declared length. If a bucket's index is repeated more often than its declared length, `offset` for that bucket keeps incrementing past its allotted slice and starts reading into (or past) the next bucket's region of `all_values`, or past the end of the vector entirely (`all_values[*offset]` in the Vec — for small overrun this yields wrong values silently reinterpreted as different state-diff fields; for large overrun it panics with an out-of-bounds index). This is the direct analog of the nginx JS heap-overflow class: attacker-controlled length/index fields feeding a buffer access without the bounds validation that the "safe" reference implementation performs.

This code path is reachable by any party submitting/publishing a state diff that is later decoded through `PartialOsStateDiff::try_from_output_iter`, which calls `decompress` directly on the (decrypted) OS-output felt stream [5](#0-4) . Since the header/bucket-index data ultimately originates from state-diff compression that is guessed/proven off-chain, a malicious prover/publisher (or any consumer parsing untrusted state-diff bytes with this Rust utility) can construct a compressed stream whose `bucket_index_per_elm` violates the implicit invariant that Cairo's `dict_squash` enforces, causing this Rust decoder to panic (indexing past `all_values`) or return a state diff that misattributes storage/class updates.

### Impact Explanation
If this Rust `decompress` path is used by any sequencer/full-node component to interpret a state diff (any place that constructs a `PartialOsStateDiff` from output felts, e.g. verifying or displaying L2 state diffs), a crafted/malicious compressed payload can crash that component (panic on out-of-bounds `Vec` index -> node/service DoS) or, in the non-panicking overrun case, cause the decoded state diff's field/values to diverge from what the Cairo OS execution actually proved, producing an honest-node divergence between what is displayed/ingested vs. what was actually committed. This maps to the "no consistency proof on attacker-controlled buffer offsets" bug class of the nginx `js_fetch_proxy` CVE (heap buffer read past intended bounds under attacker-controlled length data).

### Likelihood Explanation
Medium: the vulnerable Rust `decompress` is not the code path used for state-transition validity (that's enforced by the Cairo VM/`dict_squash`), so it doesn't directly corrupt the committed state root. Its exploitability depends on whether/where `PartialOsStateDiff::try_from_output_iter` is invoked on untrusted, unverified felt streams (rather than post-STARK-verified output) in production nodes. I was not able to fully trace every caller of `TryFromOutputIter`/`PartialOsStateDiff` to confirm whether it is always used only after Cairo-level proof verification (in which case the compressed data is already known-consistent) or whether it can be reached on raw/unverified state-diff bytes.

### Recommendation
Add an explicit final-offset validation in `decompress()` mirroring the Cairo `dict_squash` check: after processing all `data_len` entries, assert that each `bucket_offset_trackers[i]` equals the expected cumulative bucket boundary (`bucket_offsets[i+1]` or `all_values.len()` for the last bucket), returning a proper `Result`/`OsHintError` instead of allowing unchecked indexing, and use `.get()`-based checked indexing for `all_values[*offset]` to fail gracefully instead of panicking.

### Proof of Concept
Construct a compressed felt stream where:
- header declares `unique_value_bucket_lengths = [1, 0, 0, 0, 0, 0]` (one 252-bit unique value) and `n_repeating_values = 0`, `data_len = 3`.
- `bucket_index_per_elm = [0, 0, 0]` (claims the single unique-value bucket is read 3 times).

Feeding this to `decompress` causes `bucket_offset_trackers[0]` to be incremented from 0→1→2→3 while `all_values` has only 1 element, so the second iteration's `all_values[*offset]` (offset=1) already reads out of the unique-values slice; with a larger crafted `data_len` the offset exceeds `all_values.len()` entirely, causing a Rust `Vec` index-out-of-bounds panic in [6](#0-5) , unlike the Cairo version which would fail the `dict_squash` proof for the same crafted input.
