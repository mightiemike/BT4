### Title
`AccountCreateContract` transactions targeting a specific account address can be front-run and permanently blocked - (File: actuator/src/main/java/org/tron/core/actuator/CreateAccountActuator.java)

### Summary
`CreateAccountActuator` allows any funded account to create a new account at an arbitrary `accountAddress` chosen by the caller, gated only by an existence check on that address. Because that address is fully attacker-controlled and observable in the mempool before confirmation, an attacker can front-run any pending `AccountCreateContract` transaction by broadcasting their own transaction with the identical `accountAddress`, causing the legitimate transaction to permanently fail validation — the same "flag already set, so the real call reverts" bug class described in the external report for `DKIMRecoverySigValidator`.

### Finding Description
`CreateAccountActuator.validate()` unpacks the `AccountCreateContract`, reads the caller-supplied `accountAddress`, and rejects the transaction only if that address already exists in the `AccountStore`: [1](#0-0) 

`execute()` then unconditionally writes an `AccountCapsule` at that same `accountAddress` and deducts the account-creation fee from the paying `ownerAddress`: [2](#0-1) 

There is no binding between the `ownerAddress` (fee payer/signer) and the `accountAddress` being created — any account can pay to instantiate any not-yet-existing address. Because `AccountCreateContract` transactions are broadcast to the public mempool before being included in a block, the target `accountAddress` is visible to anyone watching pending transactions, exactly like the `identifier` argument in the reported `validateSig` front-running scenario. An attacker can observe a pending `AccountCreateContract` for address `X` and immediately broadcast their own `AccountCreateContract` with `accountAddress = X` (paying the trivial creation fee themselves). If the attacker's transaction confirms first, the account at `X` now exists, so the original transaction's `validate()` call hits the `"Account has existed"` check and fails — this is functionally identical to the reported `require(!recoveries[identifier], 'recovery already done')` front-running block, just applied to account-existence state instead of a recovery-completion flag.

### Impact Explanation
The victim's intended account-creation transaction for a specific address is permanently blocked, since the address becomes irreversibly occupied by the attacker's transaction. This can be used to grief users or services that rely on creating a specific, pre-determined account address (e.g., addresses tied to off-chain infrastructure, vanity addresses, or deterministic addresses referenced by other systems), denying them the ability to ever register that address as intended.

### Likelihood Explanation
Likelihood is high: there are no preconditions beyond having a funded account able to pay the (typically small) account-creation fee, no special permissions are required, and the target `accountAddress` is fully visible in any pending `AccountCreateContract` transaction prior to confirmation, making the attack trivially and cheaply repeatable for any observed transaction of this type.

### Recommendation
Remove the attacker-controlled binding between fee payer and target address, or add a mechanism that prevents an unrelated third party from claiming an address that another party is actively trying to create (e.g., only allow `ownerAddress == accountAddress`-style self-registration flows, or require some commitment/reveal scheme so the target address cannot be read from the pending transaction before it is mined).

### Proof of Concept
1. User A broadcasts `AccountCreateContract{ownerAddress: A, accountAddress: X}` intending to create account `X`.
2. Attacker observes this pending transaction in the mempool and immediately broadcasts `AccountCreateContract{ownerAddress: Attacker, accountAddress: X}`, paying the account-creation fee from their own balance.
3. If the attacker's transaction is confirmed first, `AccountStore.has(X)` becomes `true`.
4. User A's original transaction then fails `CreateAccountActuator.validate()` with `"Account has existed"` [3](#0-2) , permanently preventing User A from ever creating account `X` as intended.
