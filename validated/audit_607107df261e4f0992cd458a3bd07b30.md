### Title
Event V2→V1 translator reads `latest_state_checkpoint_view()` instead of the version-pinned state, corrupting persisted sequence numbers for translated events - (File: `storage/indexer/src/event_v2_translator.rs`)

### Summary
`EventV2TranslationEngine::get_state_value_bytes_for_resource` and `get_state_value_bytes_for_object_group_resource` always read the resource from `main_db_reader.latest_state_checkpoint_view()` [1](#0-0) , rather than from the state as of the specific transaction/version whose event is being translated. `CreateCollectionTranslator` (and every other `EventV2Translator` impl) uses the `count()` field read from that resource as the `default` sequence number passed into `get_next_sequence_number` [2](#0-1) .

### Finding Description
`get_next_sequence_number` prefers the in-memory `event_sequence_number_cache` (returns `cached + 1`) and only falls back to the persisted `EventSequenceNumberSchema` entry or the supplied `default` when there is no cache entry [3](#0-2) .

`DBIndexer::process_a_batch` iterates transactions from `start_version` to `end_version` (a whole `batch_size` worth of already-committed transactions) sequentially, translating each `ContractEventV2` in order and updating the cache immediately after each translation via `cache_sequence_number` [4](#0-3) .

Because `latest_state_checkpoint_view()` returns the *current tip* state — which, at the time a historical/batched version is being translated, already reflects **all** later transactions in the batch (and possibly beyond) — the `count()` value read for the very first `CreateCollection` event in the batch is not "count after this event" but "count after the whole batch". If the same creator submits multiple `CreateCollection` transactions that land in the same indexing batch (a normal occurrence during node startup/backfill/catch-up, or whenever `batch_size` spans more than one block), the first translated event in that batch is assigned a sequence number that already accounts for all subsequent same-batch events, and every following event derives from `cached + 1` off that inflated value. The result is a set of `ContractEventV1` sequence numbers that do not correspond to the true chronological/on-chain order of the events, and the mapping between transaction version and assigned sequence number becomes dependent on indexing batch boundaries rather than being a pure function of committed state.

This is written durably into `TranslatedV1EventSchema`, `EventByKeySchema`, `EventByVersionSchema`, and `EventSequenceNumberSchema` [5](#0-4) , and served directly to the authenticated event-query API via `DBIndexer::get_events_by_event_key`, which trusts the persisted `EventByKeySchema`/`EventByVersionSchema` ordering and cross-checks only that consecutive lookups are index-continuous, not that they reflect the true emission order [6](#0-5) .

I was not able to fully verify, within the tool budget available, whether the specific scenario in the question (an attacker *actively decreasing* a resource's own event count between two of their own transactions to force a repeated/lower sequence number for the *same* `EventKey`) is achievable. That would require a legitimate Move-framework path that resets an account's GUID-derived `EventKey`/counter while keeping the same key — GUID creation numbers on Aptos accounts are monotonic and are not reset by resource deletion/recreation, so I could not confirm a way to make `count()` go backward for the exact same `EventKey`. What I could concretely confirm is the batch/backfill non-determinism described above, which arises purely from ordinary (non-malicious) multi-transaction usage landing in the same indexing batch, and produces sequence numbers that are wrong relative to true on-chain order (though still locally monotonic per batch due to the cache).

### Impact Explanation
This corrupts durable indexer-DB records that back the authenticated event-query API: returned `ContractEventV1.sequence_number` values for translated (module/V2) events no longer correspond to true emission order and can be non-deterministic depending on indexing batch size / catch-up timing, i.e., two nodes indexing the same chain history with different `batch_size` settings (or one live-indexing vs. one backfilling) can persist different `sequence_number` values for the same underlying V2 event. This is an "authenticated API output bound to the wrong version/object" class issue as scoped, though it is confined to the auxiliary internal indexer DB (not core consensus state, accumulator, or proof material), so it does not create a hard-fork-only divergence or corrupt the actual ledger/accumulator.

### Likelihood Explanation
High for the batch/non-determinism variant: any node backfilling `enable_event_v2_translation` over existing history, or any node whose indexer batch_size spans more than one block, will hit this whenever the same creator emits 2+ token/collection events within one batch — a purely benign, unprivileged usage pattern (no adversarial manipulation required). Likelihood for the specific "attacker forces a repeated/duplicate sequence number for the same key" variant described in the question is unconfirmed/likely low, since it appears to require breaking GUID monotonicity, which I found no evidence supports.

### Recommendation
Have `EventV2TranslationEngine::get_state_value_bytes_for_resource` / `get_state_value_bytes_for_object_group_resource` read the resource at the specific transaction `Version` being translated (e.g., via `main_db_reader.state_view_at_version(version)` or an equivalent versioned state view) instead of `latest_state_checkpoint_view()`, so translated sequence numbers are a deterministic function of the event's own committed version rather than of indexing batch boundaries.

### Proof of Concept
Not independently constructed/verified — recommend a Devin session to write an integration test that: (1) sets `internal_indexer_db_config.batch_size` > 1, (2) has one account submit two `create_collection` transactions in the same batch window, (3) runs `DBIndexer::process_a_batch` covering both versions in one call, and (4) asserts whether the two translated `ContractEventV1` sequence numbers match what a single-transaction-per-batch run would produce (they should be `0`/`1` or similar low, in-order values but will instead reflect the inflated post-batch `count()`).

    pub fn get_events_by_event_key(
        &self,
        event_key: &EventKey,
        start_seq_num: u64,
        order: Order,
        limit: u64,
        ledger_version: Version,
    ) -> Result<Vec<EventWithVersion>> {
        self.indexer_db
            .ensure_cover_ledger_version(ledger_version)?;
        error_if_too_many_requested(limit, MAX_REQUEST_LIMIT)?;
        let get_latest = order == Order::Descending && start_seq_num == u64::MAX;

        let cursor = if get_latest {
            // Caller wants the latest, figure out the latest seq_num.
            // In the case of no events on that path, use 0 and expect empty result below.
            self.indexer_db
                .get_latest_sequence_number(ledger_version, event_key)?
                .unwrap_or(0)
        } else {
            start_seq_num
        };

        // Convert requested range and order to a range in ascending order.
        let (first_seq, real_limit) = get_first_seq_num_and_limit(order, cursor, limit)?;

        // Query the index.
        let mut event_indices = self.indexer_db.lookup_events_by_key(
            event_key,
            first_seq,
            real_limit,
            ledger_version,
        )?;

        // When descending, it's possible that user is asking for something beyond the latest
        // sequence number, in which case we will consider it a bad request and return an empty
        // list.
        // For example, if the latest sequence number is 100, and the caller is asking for 110 to
        // 90, we will get 90 to 100 from the index lookup above. Seeing that the last item
        // is 100 instead of 110 tells us 110 is out of bound.
        if order == Order::Descending {
            if let Some((seq_num, _, _)) = event_indices.last() {
                if *seq_num < cursor {
                    event_indices = Vec::new();
                }
            }
        }

        let mut events_with_version = event_indices
            .into_iter()
            .map(|(seq, ver, idx)| {
                let event = match self
                    .main_db_reader
                    .get_event_by_version_and_index(ver, idx)?
                {
                    event @ ContractEvent::V1(_) => event,
                    ContractEvent::V2(_) => ContractEvent::V1(
                        self.indexer_db
                            .get_translated_v1_event_by_version_and_index(ver, idx)?,
                    ),
                };
                let v0 = match &event {
                    ContractEvent::V1(event) => event,
                    ContractEvent::V2(_) => bail!("Unexpected module event"),
                };
                ensure!(
                    seq == v0.sequence_number(),
                    "Index broken, expected seq:{}, actual:{}",
                    seq,
                    v0.sequence_number()
                );

                Ok(EventWithVersion::new(ver, event))
            })
            .collect::<Result<Vec<_>>>()?;
        if order == Order::Descending {
            events_with_version.reverse();
        }

        Ok(events_with_version)
