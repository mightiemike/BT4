This is a documented, exact analog of the Wings bug class: a single check performed once on a receipt (against `max_receipt_size`), followed by unbounded mutation of that same receipt (`output_data_receivers` appended *after* the size check), which can push it arbitrarily over the limit — exactly the "check once, then unbounded growth" pattern from the Wings CVE.

### Title
Post-validation mutation of `output_data_receivers` allows receipts to exceed `max_receipt_size`, bypassing state-witness size limits - ([File: runtime/runtime/src/lib.rs])

### Summary
`validate_receipt` in `runtime/runtime/src/verifier.rs` checks a newly created receipt's borsh-encoded size against `limit_config.max_receipt_size` exactly once, at creation time, in `ValidateReceiptMode::NewReceipt` mode [1](#0-0) . This check runs in `apply_action_receipt` immediately after each action executes and produces `new_result.new_receipts` [2](#0-1) . However, after this size check passes, the runtime unconditionally mutates that same receipt by appending the *outer* receipt's `output_data_receivers` onto it via `extend_from_slice`, with no re-validation or bound on the resulting size [3](#0-2) . A contract-controlled promise/callback DAG can therefore produce a receipt that is validated at (or just under) `max_receipt_size` and then grown past it by this post-validation append, exactly mirroring the "check once using a stale/point-in-time value, then unbounded write" pattern in the Wings SFTP bug.

### Finding Description
The size gate is a boolean, one-shot check taken *before* the mutation that can enlarge the object: `validate_receipt` computes `borsh::object_length(receipt)` and compares against `max_receipt_size`, but only for freshly created receipts (`ValidateReceiptMode::NewReceipt`) [4](#0-3) . This validation happens per new receipt right after `apply_action` returns, before the outer receipt-processing logic appends `output_data_receivers` [5](#0-4) . When a `FunctionCall` action returns `ReturnData::ReceiptIndex`, the runtime looks up that specific already-validated new receipt and extends its `output_data_receivers` with the *current* receipt's own `output_data_receivers`, with no subsequent size check [3](#0-2) . This is a known, unfixed bug tracked as near/nearcore#12606, explicitly documented in the codebase itself: the `ValidateReceiptMode::ExistingReceipt` doc comment states "There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed" [6](#0-5) , and `try_forward` contains an explicit workaround clamping oversized receipt sizes to `max_receipt_size` for congestion-control accounting purposes, citing the same issue [7](#0-6) . Two dedicated regression tests confirm the receipt is accepted and processed above the configured `max_receipt_size` after the promise-return / value-return mutation path [8](#0-7) [9](#0-8) .

### Impact Explanation
`max_receipt_size` (4 MiB) is one of the load-bearing components of the `ChunkStateWitness` size budget: the design doc states the whole 21 MiB witness budget is built by summing `max_transaction_size + ... + max_receipt_size + ...`, explicitly relying on `max_receipt_size` being enforced [10](#0-9) . A contract-controlled receipt that is allowed to exceed this bound inflates witness size beyond the assumed budget, and also bypasses the `outgoing_receipts_usual_size_limit`/`outgoing_receipts_big_size_limit` bandwidth-forwarding admission logic which relies on receipts being at most `max_receipt_size` (the clamp in `try_forward` is only an accounting workaround, not a size reduction of the actual receipt content) [11](#0-10) . Repeated exploitation by an unprivileged contract deployer/caller (any account can deploy the pattern shown in the PoC test) can be used to push outsized receipts through cross-shard forwarding and into chunk witnesses beyond the sizes chunk producers/validators are designed to budget for, which is a resource-exhaustion / stateless-validation risk on the honest-node witness pipeline rather than a benign under-limit scenario.

### Likelihood Explanation
This requires only a standard `FunctionCall` action deploying a normal contract and calling a method that creates a promise DAG with `output_data_receivers`/`promise_return`, fully reachable by any unprivileged transaction signer/contract deployer — no validator or node-level privilege is needed. The bug is already reproduced and confirmed by two shipped tests in the repository (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`), so likelihood of triggering it is effectively certain given deliberate construction of the input sizes [12](#0-11) .

### Recommendation
Re-validate (or re-clamp) receipt size against `max_receipt_size` after the `output_data_receivers` extension in `apply_action_receipt`, immediately following the mutation at `runtime/runtime/src/lib.rs:1152-1170`, failing the action/receipt with `ReceiptSizeExceeded` if the post-mutation size exceeds the limit, closing near/nearcore#12606 at the root cause rather than only working around it in `congestion_control.rs`.

### Proof of Concept
Use the existing repository test `test_max_receipt_size_promise_return` (or `test_max_receipt_size_value_return`) as the PoC: deploy `near_test_contracts::rs_contract()`, call a method that builds a promise DAG `A -> then -> B` where `A` creates a third promise `C` and does `promise_return`, sized so `C`'s receipt is exactly `max_receipt_size` before output-data-receiver attachment; after attachment the receipt exceeds `max_receipt_size` yet is still accepted and appears on-chain as an oversized incoming receipt, as asserted by `assert_oversized_receipt_occurred` [13](#0-12) .

**File:** docs/misc/state_witness_size_limits.md (L16-40)
```markdown
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
* `max_receipt_total_input_size - 4 MiB + 640 B`
  * Hard limit on the combined size of a receipt's resolved promise inputs (the `ReceivedData` referenced by its `input_data_ids`). Receipts which exceed it fail with `TotalPromiseInputSizeExceeded` without executing their actions.
  * These inputs are read before `per_receipt_storage_proof_size_limit` starts counting, so without this limit a single receipt could pull `max_number_input_data_dependencies * max_receipt_size` (128 * 4 MiB) into the witness.
  * The limit is `max_length_returned_data` (4 MiB) plus the worst-case per-input framing overhead (128 * 5 bytes), so 4 MiB of input data always fits no matter how it's split across data receipts.
* `combined_transactions_size_limit - 4 MiB`
  * Hard limit on total size of transactions from this and previous chunk. `ChunkStateWitness` contains transactions from two chunks, this limit applies to the sum of their sizes.
* `new_transactions_validation_state_size_soft_limit - 500 KiB`
  * Validating new transactions generates storage proof (recorded trie nodes), which has to be limited. Once transaction validation generates more storage proof than this limit, the chunk producer stops adding new transactions to the chunk.
* `per_receipt_storage_proof_size_limit - 4 MB`
  * Executing a receipt generates storage proof. A single receipt is allowed to generate at most 4MB of storage proof. This is a hard limit, receipts which generate more than that will fail.
* `main_storage_proof_size_soft_limit - 4 MB`
  * This is a limit on the total size of storage proof generated by receipts in one chunk. Once receipts generate more storage proof than this limit, the chunk producer stops processing receipts and moves the rest to the delayed queue.
  * It's a soft limit, which means that the total size of storage proof could reach 8 MB (3.99MB + one receipt which generates 4MB of storage proof)
  * Due to implementation details it's hard to find the exact amount of storage proof generated by a receipt, so an upper bound estimation is used instead. This upper bound assumes that every removal generates additional 2000 bytes of storage proof, so receipts which perform a lot of trie removals might be limited more than theoretically applicable.
* `outgoing_receipts_usual_size_limit - 100 KiB`
  * Limit on the size of outgoing receipts to another shard. Needed to keep the size of `source_receipt_proofs` small.
  * On most block heights a shard isn't allowed to send receipts larger than 100 KiB to another shard.
* `outgoing_receipts_big_size_limit - 4.5 MiB`
  * On every block height there's one special "allowed shard" which is allowed to send larger receipts, up to 4.5 MiB in total.
  * A receiving shard will receive receipts from `num_shards - 1` shards using the usual limit and one shard using the big limit.

In total that gives 4 MiB + 500 KiB + 8MB + 4 MiB + 5*100 KiB + 4.5 MiB ~= 21 MiB of maximum witness size. Possibly a little more on missing chunks.
```
