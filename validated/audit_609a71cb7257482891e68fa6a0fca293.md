Based on my research, `max_length_returned_data` is up to 4,194,304 bytes (4 MiB) per mainnet parameters, confirming a target contract can legally return data at that scale. This confirms the analog is technically feasible: a callback with a small hard-coded static gas budget can be starved by a large, attacker-controlled return value, causing an out-of-gas failure that rolls back the `has_in_flight_tx` reset — mirroring the Sherlock report's "hard-coded/fixed gas stipend causes DOS/frozen funds" pattern.

### Title
Hard-coded static gas for Wallet Contract promise callbacks can be exhausted by an attacker-controlled return value, permanently freezing the wallet - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract (NEP-518, used by ETH-implicit accounts) guards against concurrent execution with a `has_in_flight_tx` boolean that is reset to `false` at the very top of every promise callback. However, the gas attached to these callbacks (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, all fixed at 5–10 Tgas) is a hard-coded static budget, independent of the size of the data the callback must process from the resolved promise. This is directly analogous to Solidity's `payable.transfer`/`.send()` 2300-gas stipend: a fixed, non-configurable gas allowance that can become insufficient depending on runtime conditions the caller does not control, causing the operation to fail.

### Finding Description
`WalletContract::rlp_execute` refuses to start a new transaction while `has_in_flight_tx` is `true`: [1](#0-0) 

Every callback that is chained with `.then(...)` unconditionally sets `has_in_flight_tx = false` as its first statement, e.g. `rlp_execute_callback`: [2](#0-1) 

and `address_check_callback` / `nep_141_storage_balance_callback` do the same at their start: [3](#0-2) [4](#0-3) 

The static gas allocated to these callbacks is a fixed constant, not scaled with the size of the value the inner promise can return: [5](#0-4) 

`rlp_execute_callback` copies the entire `PromiseResult::Successful(value)` byte buffer into the response: [6](#0-5) 

The protocol allows a target contract's return value (and thus the resolved `DataReceipt`) to be as large as `max_length_returned_data` (4 MiB on mainnet), enforced only by `validate_data_receipt`: [7](#0-6) [8](#0-7) 

Because the runtime treats a receipt whose execution fails (including WASM out-of-gas panics) as fully atomic — rolling back *all* state changes performed during that receipt, including the `has_in_flight_tx = false` write that already executed at function entry — a callback that runs out of its fixed static gas budget while copying/serializing an oversized value never commits the unlock: [9](#0-8) 

If the `FunctionCall` action's target contract (chosen by the wallet owner when they sign their Ethereum-style transaction, or reachable in the ERC-20/base-token emulation flow via `nep_141_storage_balance_callback`/`address_check_callback` against any externally provided token/registrar contract) returns a value close to the 4 MiB cap, the fixed 5–10 Tgas callback budget can be exhausted purely by the cost of reading/copying that data before the callback ever executes its own logic (the reset already happened, but the receipt as a whole is discarded on panic). Since `has_in_flight_tx` remains `true` in the persisted state, every subsequent call to `rlp_execute` for that account is permanently rejected with "transaction already in progress."

### Impact Explanation
This produces a permanent denial-of-service / freezing-of-funds condition on the affected ETH-implicit account's Wallet Contract: `rlp_execute` — the sole entry point for moving funds or acting on behalf of that account — will unconditionally refuse to proceed for that account forever, since there is no recovery/reset method exposed in the contract (`ban_relayer`, the only other state-mutating branch, also requires successfully executing a promise and does not reset a stuck flag if it can never be invoked). The account's balance and any assets controlled exclusively through this Wallet Contract become permanently unreachable, matching "permanently frozen funds" from the accepted-impact list.

### Likelihood Explanation
Reachable from a single relayer-submitted NEAR transaction calling `rlp_execute` on an ETH-implicit account, where the RLP-encoded Ethereum transaction's target is a contract (attacker-controlled or merely "return a large payload") that returns data sized close to the 4 MiB `max_length_returned_data` limit. No validator, network, or protocol-privileged access is required — only a standard `FunctionCall` action whose value response the wallet's own callback then has to copy under an unscaled, fixed gas budget. The precondition (target returns large payload) is fully controlled by whichever contract the signed transaction targets, which for ERC-20/NEP-141 emulation paths (`nep_141_storage_balance_callback`) or address-registrar paths (`address_check_callback`) is an externally-supplied account the user does not need to fully trust for this griefing to occur.

### Recommendation
Scale the static gas attached to `rlp_execute_callback`, `address_check_callback`, and `nep_141_storage_balance_callback` proportionally to `max_length_returned_data` (or otherwise bound/truncate the amount of promise-result data copied in these callbacks) so that out-of-gas failures in the callback cannot occur purely due to attacker-controlled return-value size. Alternatively, persist the "unlock" (`has_in_flight_tx = false`) via a mechanism that survives receipt failure (e.g., a follow-up unconditional cleanup receipt), or add an owner-only escape hatch to manually clear a stuck `has_in_flight_tx` flag.

### Proof of Concept
1. Deploy the Wallet Contract as a global contract for ETH-implicit accounts (as in `test_wallet_contract_interaction`), and fund an ETH-implicit account.
2. Sign an Ethereum-style transaction (via `rlp_execute`) whose target is a NEP-141-style token contract, or any account whose called method returns a value near `max_length_returned_data` (4 MiB) bytes on success.
3. Submit the transaction through the relayer to `rlp_execute`; the inner `FunctionCall`/`nep_141_storage_balance_callback`/`rlp_execute_callback` chain resolves successfully at the target, but the wallet's own callback — bounded by the fixed `RLP_EXECUTE_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` constant — runs out of gas while handling the oversized `PromiseResult::Successful(value)`.
4. Observe the receipt fails and is rolled back in its entirety (per `runtime/runtime/src/lib.rs` receipt atomicity), so the earlier `self.has_in_flight_tx = false` write is discarded and the persisted flag remains `true`.
5. Any subsequent call to `rlp_execute` for this account now returns `"Error: transaction already in progress, please try again later."` indefinitely, as demonstrated by the existing `test_simultaneous_transactions` test which shows this exact error path being taken when `has_in_flight_tx` is `true`: [10](#0-9)

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

/// Validates given data receipt. Checks validity of the length of the returned data.
fn validate_data_receipt(
    limit_config: &LimitConfig,
    receipt: &DataReceipt,
) -> Result<(), ReceiptValidationError> {
    let data_len = receipt.data.as_ref().map(|data| data.len()).unwrap_or(0);
    if data_len as u64 > limit_config.max_length_returned_data {
        return Err(ReceiptValidationError::ReturnedValueLengthExceeded {
            length: data_len as u64,
            limit: limit_config.max_length_returned_data,
        });
    }
    Ok(())
}

- **Failed receipt atomicity**: a receipt whose result is `Err` triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting (`runtime/runtime/src/lib.rs:967`). `set_error` additionally clears queued receipts, proposals, and burnt/subsidized amounts (`runtime/runtime/src/lib.rs:487`).
- **Staking invariant**: `update_validator_accounts` returns a fatal `StorageInconsistentState` if `locked < max_of_stakes` (`runtime/runtime/src/lib.rs:1617`).

/// Only one transaction can be in flight at a time.
#[tokio::test]
async fn test_simultaneous_transactions() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let receiver_account = worker.root_account().unwrap();

    let initial_receiver_balance = receiver_account.view_account().await.unwrap().balance;

    let receiver_id = receiver_account.id().as_str().into();
    let action = Action::Transfer { receiver_id, yocto_near: 1 };
    let signed_transaction =
        utils::create_signed_transaction(0, receiver_account.id(), Wei::zero(), action, &wallet_sk);
    let wallet_method_call_1 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));
    let wallet_method_call_2 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));

    let near_transaction = wallet_contract
        .inner
        .as_account()
        .batch(wallet_contract.inner.id())
        .call(wallet_method_call_1)
        .call(wallet_method_call_2)
        .transact()
        .await?;

    let result: ExecuteResponse = near_transaction.json()?;

    // The second transaction in the batch fails and this is returned as the
    // result of the Near transaction. But the first transaction in the batch
    // spawns promises that resolve, so the transfer was will successful.
    assert!(!result.success);
    assert!(result.error.unwrap().contains("transaction already in progress"));

    let final_receiver_balance = receiver_account.view_account().await.unwrap().balance;
    assert_eq!(final_receiver_balance.as_yoctonear() - initial_receiver_balance.as_yoctonear(), 1,);

    Ok(())
}
