## Title
Unbounded `unfrozenV2List` iteration in `CancelAllUnfreezeV2Actuator` / `WithdrawExpireUnfreezeActuator` enables a zero-fee Denial-of-Service - ([File: actuator/src/main/java/org/tron/core/actuator/CancelAllUnfreezeV2Actuator.java])

### Summary
The bug class described in the report—unbounded iteration over a growable, attacker-controlled set/list with no proportional cost—has a concrete analog in java-tron's stake/unfreeze accounting. `UnfreezeBalanceV2Actuator` limits only the count of *unexpired* unfreeze entries (`UNFREEZE_MAX_TIMES = 32`), not the total size of `unfrozenV2List` on an account. Once an unfreeze entry expires it no longer counts against the cap yet remains in the account's protobuf-backed list until it is explicitly consumed by `WithdrawExpireUnfreezeActuator` or `CancelAllUnfreezeV2Actuator`. Both of these actuators fully iterate the entire list in `execute()`, and both charge zero fee (`calcFee()` returns `0`), so the cost of processing an arbitrarily large list is not gas/bandwidth-metered.

### Finding Description
`AccountCapsule.getUnfreezingV2Count(long now)` only counts entries whose `expireTime > now`: [1](#0-0) 

`UnfreezeBalanceV2Actuator.validate()` uses this count to enforce `UNFREEZE_MAX_TIMES` (32), but this only bounds *pending* (not-yet-expired) unfreeze requests: [2](#0-1) [3](#0-2) 

Because a freeze/unfreeze/wait-for-expiry cycle can be repeated indefinitely (freeze a minimal amount, unfreeze it, let the delay period pass, refreeze, repeat), an account can accumulate an unbounded number of *expired* `UnFreezeV2` entries in `account.unfrozenV2List` — each cycle adds a new entry that never gets removed unless the owner separately calls `WithdrawExpireUnfreezeContract` or `CancelAllUnfreezeV2Contract`.

Both cleanup actuators then unconditionally iterate the **entire** list:
- `CancelAllUnfreezeV2Actuator.execute()` iterates `unfrozenV2List` in full with no size limit: [4](#0-3) 
- `WithdrawExpireUnfreezeActuator.execute()` similarly processes the full list via `getTotalWithdrawUnfreeze` / `getRemainWithdrawList`: [5](#0-4) 

Both actuators return a zero fee, meaning the cost of this O(n) processing (list copy, iteration, protobuf rebuild, `AccountStore.put`) is not paid for in bandwidth/energy proportional to n: [6](#0-5) 

This mirrors the reported bug class exactly: an unbounded set is grown by ordinary user actions, and a single state-changing operation must fully iterate it, with no gas/fee scaling to the set size — the same root cause as `HookManager.sol`'s `runExecutionHooks`/`runValidationHooks` iterating `EnumerableSet.values()`.

### Impact Explanation
Any account can grow its own `unfrozenV2List` to an arbitrarily large size over time at negligible cost (each freeze/unfreeze cycle costs only ordinary bandwidth/energy for the transaction itself; the actuators that create the entries — `UnfreezeBalanceV2Actuator` — do not charge for storage growth, and `calcFee()` for the eventual cleanup calls is `0`). When a block later includes a `CancelAllUnfreezeV2Contract` or `WithdrawExpireUnfreezeContract` transaction against such an account, every full node must execute the same unbounded loop (`Triple`/`AtomicLong` accounting, list copy/filter, protobuf rebuild) during block application, consuming CPU/memory disproportionate to the fee paid. Because this same computation is repeated by every validating node, a sufficiently bloated list can materially slow block processing/validation for the network, and in extreme cases could stall processing of that specific transaction/block — a state-processing DoS vector, distinct from a simple self-harm scenario since it must be re-executed by every node that validates the chain.

### Likelihood Explanation
Reaching this state requires only unprivileged, permissionless actions (`FreezeBalanceV2Contract` and `UnfreezeBalanceV2Contract`) repeated over many delay-period cycles; no special privilege or contract interaction is needed. The only friction is time (each cycle needs to wait out the unfreeze delay, governed by `supportUnfreezeDelay`/`saveUnfreezeDelayDays`) and the ordinary per-transaction bandwidth/energy cost, making this a low-cost, high-patience attack rather than a one-shot exploit. This lowers likelihood compared to an instant DoS, but the attack is entirely feasible for a determined actor and the resulting cleanup transaction is a normal, unprivileged operation that other nodes are forced to execute.

### Recommendation
- Track and cap the *total* size of `unfrozenV2List` (not just the count of currently-unexpired entries), rejecting further `UnfreezeBalanceV2Contract` calls once the account's list exceeds a hard limit until the owner withdraws/cancels expired entries.
- Alternatively/additionally, charge `calcFee()` in `CancelAllUnfreezeV2Actuator` and `WithdrawExpireUnfreezeActuator` proportional to the number of entries processed (similar to how bandwidth/energy is charged elsewhere), so the cost of the O(n) work is borne by the account generating it.
- Consider bounding the number of items processed per call (batch/paginate cleanup) so a single transaction cannot force unbounded work in one block.

### Proof of Concept
1. Enable `supportUnfreezeDelay` (as done in `CancelAllUnfreezeV2ActuatorTest.setUp()`).
2. Repeatedly: `FreezeBalanceV2Contract` a small amount → `UnfreezeBalanceV2Contract` it (adds one `UnFreezeV2` entry via `AccountCapsule.addUnfrozenV2List`) → wait until `unfreezeExpireTime` passes so the entry no longer counts toward `UNFREEZE_MAX_TIMES` (see `getUnfreezingV2Count`) → repeat. Each cycle adds a permanent entry to `unfrozenV2List` that is never removed unless a cleanup call is issued.
3. After N cycles (N arbitrarily large, limited only by attacker patience/time), submit a single `CancelAllUnfreezeV2Contract` (or `WithdrawExpireUnfreezeContract`). Both actuators iterate the full N-sized list in `execute()` (see the cited `for (UnFreezeV2 unFreezeV2 : unfrozenV2List)` loop and `getTotalWithdrawUnfreeze`/`getRemainWithdrawList`), with `calcFee() == 0`, demonstrating unpriced O(n) work performed by every node validating the block.
