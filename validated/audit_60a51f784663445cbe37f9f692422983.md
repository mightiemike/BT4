### Title
`TransactionOutput::ensure_match_transaction_info` skips validation of `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single integrity gate that compares a locally-executed `TransactionOutput` against an authenticated `TransactionInfo` (the object actually committed to the transaction accumulator and signed by validators). It explicitly checks status, gas used, write-set hash, and event root hash, but the code contains an explicit acknowledged gap: it does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the recomputed values. [1](#0-0) 

### Finding Description
The function's own comment documents the gap: [2](#0-1) 

It states that the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)," and that this allows "replay-verify tooling (e.g. db-tool's `replay_on_archive`) [to] report a successful replay even when the authenticated position state root diverges from local execution."

This function is the sole state-integrity check used by chunk-executor's `verify_execution` when validating restored/replayed transaction chunks against previously-persisted, authenticated `TransactionInfo`s (analogous to the GMX case where a "slippage" check was expected on every path but silently skipped on one branch): [3](#0-2) 

The same function is also used by `aptos-debugger`, `cli/src/commands.rs`, and `storage/db-tool/src/replay_on_archive.rs` for offline replay verification against archived state. In all of these callers, `ensure_match_transaction_info` is treated as the authority for "does my local execution match the authenticated ledger record," yet it silently omits comparing the state root/checkpoint hash fields that are actually part of `TransactionInfo` (`state_checkpoint_hash()`, and — per the newer `TransactionInfoV1` — `hot_state_checkpoint_hash()` and `position_state_checkpoint_hash()`).

Because the write-set hash (`state_change_hash`) only commits to the *raw write operations emitted by this transaction* and not to the resulting Merkle/JMT state root, a divergence in how those writes are folded into the state tree (e.g. a bug in the state-summary/state-checkpoint computation path in `do_state_checkpoint.rs`, or in the newer position-state tree used for `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) would produce a wrong `state_checkpoint_hash` that this function would never flag.

### Impact Explanation
This breaks the "committed state must match the correct VM result" invariant for the checkpoint/state-root class of authenticated data. If the JMT/state-summary root computed during checkpointing diverges from what should have been committed (due to a bug, a race, or an inconsistent restore), `ensure_match_transaction_info` — the very function designed to catch exactly this kind of divergence during chunk-executor's `verify_execution` and offline replay-verify tooling — will report success anyway. This means:
- State-sync/backup-restore verification (`VerifyExecutionMode`) can silently accept a chunk whose recomputed state checkpoint root does not match the previously-committed/authenticated one.
- `replay_on_archive` (used to validate historical state correctness against archived data, including for potential fork/hard-fork investigations) can report a clean replay despite an actual state-root mismatch.

This matches the required "Wrong ... state proof accepted as valid" / "Hard-fork-only divergence during commit, replay ... verification" impact class, since the affected checks are specifically the replay/restore verification paths, not consensus-time execution itself.

### Likelihood Explanation
The gap is unconditional in the current code — it is not behind a feature flag for the base `state_checkpoint_hash`/`hot_state_checkpoint_hash` fields (only the position-state part is additionally gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`); the comparator simply never reads or compares these fields at all. It requires no attacker action to trigger — any real bug or inconsistency in state-checkpoint computation (in `do_state_checkpoint.rs`'s hashing/merging logic, which is nontrivial and actively being extended, e.g. hot-state and position-state summaries) would go undetected by this specific verification path. However, exploitation still requires an underlying primary bug that produces a diverging state root; this weakness is a "verification gap" that removes the safety net rather than a directly triggerable primitive by itself.

### Recommendation
Extend `ensure_match_transaction_info` to compare the recomputed `state_checkpoint_hash` (and, where applicable, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) against the values in `txn_info`, mirroring how `state_change_hash` and `event_root_hash` are already checked, before this function is relied upon by chunk-executor's `verify_execution` and by `replay_on_archive`/`aptos-debugger` replay tooling.

### Proof of Concept
1. In `execution/executor/src/chunk_executor/mod.rs::verify_execution`, or in `storage/db-tool/src/replay_on_archive.rs`, feed a transaction chunk whose replayed execution correctly reproduces the write set and events (so `state_change_hash` and `event_root_hash` match) but whose downstream state-checkpoint/JMT root diverges from the persisted `TransactionInfo.state_checkpoint_hash` (e.g., by simulating a bug in `DoStateCheckpoint::get_state_checkpoint_hashes` in `execution/executor/src/workflow/do_state_checkpoint.rs`).
2. Call `ensure_match_transaction_info` with this mismatched state — it returns `Ok(())` because the function never reads `state_checkpoint_hash()`/`hot_state_checkpoint_hash()`/`position_state_checkpoint_hash()` from either side.
3. Observe that chunk verification/replay-verify tooling reports success despite the mismatched, authenticated state root — exactly the scenario the code's own TODO comment describes.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
