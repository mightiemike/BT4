### Title
Deterministic account initialization can silently bind pre-funded balance to attacker-controlled code via mutable `GlobalContractIdentifier::AccountId` — ([File: runtime/runtime/src/deterministic_account_id.rs])

### Summary
`DeterministicStateInitAction` derives an account's identity from a `DeterministicAccountStateInit` that references its code only by a `GlobalContractIdentifier`, which may be the mutable `AccountId` variant. Because the deterministic account id commits to the *identifier*, not the *resolved bytecode*, and because a `Transfer` may fund the not-yet-initialized deterministic account before the state-init action runs, an attacker who controls (or races to redeploy) the referenced global-by-account contract can cause the eventual initialization to bind a victim's already-deposited funds to different, attacker-chosen code — mirroring the reported `placeBid()` "auction restarted" class where a stable identifier is used against a resource whose underlying content silently changed between intent formation and execution, without any pin/version check.

### Finding Description
`DeterministicAccountStateInitV1` stores `code: GlobalContractIdentifier`, which can be either `CodeHash` (immutable) or `AccountId` (explicitly documented as mutable — "This allows the owner to update the contract for all its users") [1](#0-0) . The deterministic account id is derived by borsh-hashing the whole `DeterministicAccountStateInit` value, which only encodes the `GlobalContractIdentifier`, not the code it currently resolves to [2](#0-1) .

Per the docs, users may pre-fund a not-yet-initialized deterministic account via a plain `Transfer` before the `DeterministicStateInitAction` ever executes: "A `Transfer` can also deposit a balance before the `DeterministicStateInitAction`. The account will not be usable, however, until the `DeterministicStateInitAction` is also executed." [3](#0-2) . `check_account_existence` explicitly allows `DeterministicStateInit` on either an existing or non-existing account [4](#0-3) , and initialization is idempotent/lazy by design — "if the account was already created before: do nothing" [5](#0-4) .

The actual code-binding happens in `deploy_deterministic_account`, which calls `use_global_contract` with `state_init.code()` — i.e. it resolves whatever code the `GlobalContractIdentifier::AccountId` currently points to *at execution time*, not at the time the id was derived or funds were sent [6](#0-5) . Since `DeterministicStateInitAction` can be submitted by anyone who reproduces the same `state_init` value (there is no owner/creator restriction other than the id-derivation check), and since the global-by-account contract owner can redeploy at any time via `DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId` [7](#0-6) , the code that ultimately takes control of the account (and any funds already sitting there from an earlier `Transfer`) can differ from what the depositor observed/intended when the id was computed and funds were sent — exactly the "resource restarted before intent is executed" pattern from the report, just applied to account code instead of an auction's parameters.

This class of issue was partially recognized by the codebase itself: a related exploit involving delegated `DeterministicStateInit` and mismatched receiver ids was already found and fixed (`FixDelegatedDeterministicStateInit`, tested by `try_meta_tx_deterministic_receiver_exploit`) [8](#0-7) , but that fix only pins the *receiver id* to the derived id — it does not pin the *resolved code* referenced through `GlobalContractIdentifier::AccountId` to a specific version at deposit time.

### Impact Explanation
Unprivileged users regularly reference `GlobalContractIdentifier::AccountId` in `DeterministicAccountStateInit` (the test helper `sharded_contract_id()` explicitly supports this identifier for the deterministic-account pattern) [9](#0-8) . Any depositor who sends NEAR to a deterministic account address before it is initialized is trusting that the eventual `DeterministicStateInitAction` will install the code they reviewed. If the global contract owner redeploys before initialization runs (or an attacker intentionally races the initializing transaction after redeploying), the account ends up running different code than what the depositor's mental model assumed, while already holding the depositor's balance — resulting in unauthorized value movement (funds effectively delivered to logic the depositor never approved). This satisfies the "concrete unauthorized value movement" bar via a completely unprivileged single-transaction path (a `Transfer` to a not-yet-existing `0s…` address, followed later by any account's `DeterministicStateInitAction`).

### Likelihood Explanation
Likelihood is moderate: it requires (1) a depositor pre-funding a deterministic account referencing an `AccountId`-mode global contract, and (2) the global contract being redeployed (by its legitimate owner, or because the owner's key/process is compromised) before the account is initialized, or an attacker deliberately timing their own `DeterministicStateInitAction` submission after such a redeploy. This mirrors the report's core "identifier stays fixed, underlying resource state changes before execution" mechanics, but here the redeploy is gated behind control of the global-contract owner account rather than being open to every observer — narrowing but not eliminating exploitability, especially in flows encouraging users to pre-fund deterministic addresses computed off-chain.

### Recommendation
Do not allow `DeterministicAccountStateInitV1.code` to reference the mutable `GlobalContractIdentifier::AccountId` variant when the resulting id is meant to guarantee "fixed code" semantics — restrict deterministic-account state-init to `GlobalContractIdentifier::CodeHash` only, or otherwise pin/verify the resolved code hash at both funding time and initialization time so that `DeterministicStateInitAction` fails (rather than silently succeeding with different code) if the referenced `AccountId` contract has been redeployed since the `state_init` was constructed/funds were sent.

### Proof of Concept
1. Global contract owner `G` deploys contract `A` via `DeployGlobalContractAction { deploy_mode: AccountId }`.
2. User `U` builds `state_init = DeterministicAccountStateInit::V1 { code: GlobalContractIdentifier::AccountId(G), data }`, derives `det_account = derive_near_deterministic_account_id(&state_init)`, and sends a `Transfer` of funds to `det_account` (allowed pre-init per docs).
3. Before anyone submits `DeterministicStateInitAction` for `det_account`, `G` redeploys global contract to malicious code `A'` via another `DeployGlobalContractAction { deploy_mode: AccountId }` (same account id `G`, new bytecode).
4. Anyone (attacker or unwitting relayer) submits `DeterministicStateInitAction` with the same `state_init` (same `code: AccountId(G)`) — `deploy_deterministic_account` resolves `use_global_contract` against the now-different code `A'` and installs it on `det_account`, which already holds `U`'s funds [6](#0-5) .
5. `det_account` is now controlled by `A'`'s logic while holding `U`'s deposit, with no protocol-level check that the code matches what `U` intended when funding the address.

### Deterministic account ID

The account ID is derived from a `DeterministicAccountStateInit` instance.

To derive the deterministic account id, borsh-encode the `DeterministicAccountStateInit` enum instance into raw
bytes. Then use the following formula: `'0s' + keccak256(bytes)[12:32].hex()`.

    protocol_version: ProtocolVersion,

    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    assert_ne!(det_account_a, det_account_b);

    // Deploy det_account_b and add a full-access key so it can act as meta_tx_sender.

    let deploy_tx = SignedTransaction::deterministic_state_init(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        env.get_tx_block_hash(),
        state_init_b.clone(),
        storage_balance,
    );
    env.run_tx(deploy_tx);

    let meta_tx_sender_signer = create_user_test_signer(&det_account_b);
    let pk_base64 = near_primitives_core::serialize::to_base64(
        &borsh::to_vec(&meta_tx_sender_signer.public_key()).unwrap(),
    );
    let add_key_args = serde_json::json!([
        { "batch_create": { "account_id": det_account_b.as_str() }, "id": 0 },
        {
            "action_add_key_with_full_access": {
                "promise_index": 0,
                "public_key": pk_base64,
                "nonce": 0
            },
            "id": 0,
            "return": true
        }
    ]);
    let add_key_tx = SignedTransaction::call(
        env.next_nonce(),
        env.user_account(),
        det_account_b.clone(),
        &user_signer,
        Balance::from_near(2),
        "call_promise".to_owned(),
        serde_json::to_vec(&add_key_args).unwrap(),
        Gas::from_teragas(300),
        env.get_tx_block_hash(),
    );
    env.run_tx(add_key_tx);

    // Craft the exploit: outer_tx.receiver = det_account_b = derive(state_init_b).
    // Old check: det_account_b == derive(state_init_b) passes.
    // The delegate action targets det_account_a, which is the wrong account.
    // In no protocol version can this ever be allowed to be executed successfully.
    let relayer = env.independent_account();
    let relayer_signer = create_user_test_signer(&relayer);
    let inner_action = Action::DeterministicStateInit(Box::new(DeterministicStateInitAction {
        state_init: state_init_b,
        deposit: Balance::ZERO,
    }));
    let delegate_nonce = env.next_nonce_for(&det_account_b);
    let delegate_action = DelegateAction {
        sender_id: det_account_b.clone(),
        receiver_id: det_account_a,
        actions: vec![NonDelegateAction::try_from(inner_action).unwrap()],
        nonce: delegate_nonce,
        max_block_height: 1_000_000,
        public_key: meta_tx_sender_signer.public_key(),
    };
    let signed_delegate_action =
        SignedDelegateAction::sign(&meta_tx_sender_signer, delegate_action);
    let tx = SignedTransaction::from_actions(
        env.next_nonce(),
        relayer,
        det_account_b,
        &relayer_signer,
        vec![Action::Delegate(Box::new(signed_delegate_action))],
        env.get_tx_block_hash(),
    );
    env.try_execute_tx(tx)
}
