### Title
Uncontrolled recursion in `Chain::get_recursive_transaction_results` allows an RPC-triggered native stack overflow / node crash - ([File: chain/chain/src/chain.rs])

### Summary
`Chain::get_recursive_transaction_results` walks the DAG of receipts produced by a transaction using genuine (non-tail) Rust function recursion, with no depth limit, no cycle guard, and no iterative/stack-based rewrite (unlike other traversal code in the codebase which was deliberately rewritten to be non-recursive to avoid exactly this class of bug). It is reachable from the public `tx` / `EXPERIMENTAL_tx_status` JSON-RPC methods via `get_final_transaction_result`, i.e. from any unauthenticated RPC caller who knows a transaction hash.

### Finding Description
`get_recursive_transaction_results` recurses once per receipt in the outcome chain: [1](#0-0) 

It is invoked from `get_final_transaction_result`, the function backing the `tx` RPC method (via `ViewClientActor` / `TxStatus`): [2](#0-1) 

Each level of recursion adds a native stack frame; there is no explicit maximum-depth check comparable to the one added elsewhere in the codebase for the same conceptual problem (`ReceiptToTx`'s `MAX_DEPTH=1000` guard, tested in `test_receipt_to_tx_depth_exceeded`): [3](#0-2) 

The elsewhere-explicit `MAX_DEPTH` cap and the explicit iterative rewrite of trie/subtree traversal to "avoid any potential stack overflows" (`core/store/src/trie/trie_recording.rs`) show that the project is generally aware of, and defends against, this bug class — but this particular RPC-facing recursive walk was not converted: [4](#0-3) 

An attacker-controlled transaction can generate a long chain of dependent receipts (cross-contract self-calls, as demonstrated by the `max_self_recursion_delay` test contract method used precisely to build long receipt chains): [5](#0-4) 

and the existing test confirms achievable receipt-chain depths in the hundreds are already realistic (56–221 hops) purely from a single transaction's prepaid gas budget: [6](#0-5) 

Because `outcomes.receipt_ids` for a node can also fan out (multiple output receipts, data receipts, yield/resume follow-ups) across many chunks and blocks over the lifetime of the chain, an attacker is not limited to a single chunk's gas budget: receipts can be spread out over many transactions/epochs (e.g., via yield/resume, or by chaining many independently-funded transactions whose receipts reference each other through `receipt_ids`), allowing the DAG depth walked by `get_recursive_transaction_results` to grow arbitrarily large over time, independent of any single gas limit.

In Rust, stack overflow from unbounded recursion is not a catchable panic: the runtime installs a guard page and, upon overflow, prints "thread ... has overflowed its stack" and calls `abort()`, which terminates the entire process — not just the offending actor/thread. Since `ViewClientActor` runs in the same process as the rest of the node, an RPC-triggered stack overflow in this code path can crash the whole node process.

### Impact Explanation
A single RPC-reachable read call (`tx` / `EXPERIMENTAL_tx_status`) that walks an attacker-shaped, sufficiently deep receipt DAG can trigger unbounded native recursion and a process-level stack overflow, aborting the entire node process. Because RPC endpoints are typically served on the same process as chain/view logic, this is a transaction-triggered denial-of-service / halt against any node (validator, RPC node, or indexer) that receives the malicious `tx` query, not merely a resource-metering nuisance — it directly matches the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
Constructing a deep receipt chain requires only standard, permission-less capabilities: deploying a self-recursive contract (as already demonstrated in-repo by `max_self_recursion_delay`/`recurse`) and submitting one or more transactions to build a long chain of receipts, then querying `tx` for the originating transaction hash. No validator, peer, or privileged access is required — only a wallet, a small amount of NEAR for gas/storage, and the ability to submit transactions and issue a JSON-RPC query, both of which are explicitly in-scope, unprivileged capabilities. The main uncertainty is the exact number of stack frames needed to overflow a real deployment's configured stack size (default OS thread stack is typically several MiB, and this frame is only moderately sized), and whether a single transaction's gas budget alone (currently capped at a few hundred hops per the existing test) is sufficient, or whether cross-block/yield-resume chaining is needed to reach the required depth — this makes exploitability plausible but not fully proven without further measurement.

### Recommendation
Rewrite `get_recursive_transaction_results` as an iterative, explicit-stack (or worklist/queue-based) traversal, mirroring the pattern already used in `trie_recording.rs`'s `get_subtree_size` and the `traverse_all_nodes` function in `state_parts.rs`. Additionally, apply an explicit maximum node/depth cap (analogous to the `ReceiptToTx` `MAX_DEPTH = 1000` guard) and return a well-defined error (e.g. `DepthExceeded`) instead of unbounded recursion, and add a cycle/duplicate-visit guard to protect against malformed or adversarially crafted receipt graphs.

### Proof of Concept
1. Deploy a contract exposing a self-recursive cross-contract-call method (equivalent to the in-repo `max_self_recursion_delay`/`recurse` test methods) that, on each hop, creates a new outgoing receipt back to itself.
2. Submit a transaction (or a sequence of transactions using yield/resume or chained follow-up transactions) that produces a receipt DAG whose chain of `outcome.receipt_ids` is deep enough to overflow the RPC-serving process's native call stack.
3. Call the `tx` (or `EXPERIMENTAL_tx_status`) JSON-RPC method with the originating transaction hash, `wait_until` sufficient for outcomes to be recorded, so that `ViewClientActor` invokes `Chain::get_final_transaction_result` → `get_recursive_transaction_results` over the full depth of the DAG.
4. Observe the node process abort with a stack-overflow error, terminating all node services (RPC, chain processing) served by that process, rather than returning a normal `FinalExecutionOutcomeView` or bounded error.

    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);
    let amount = 1u128;
    let gas_fixed = 0;
    let gas_weight = 1;
    let argument_bytes = recursion.saturating_add(1).to_be_bytes();
    promise_batch_action_function_call_weight(
        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );
    promise_return(promise_idx);
}
