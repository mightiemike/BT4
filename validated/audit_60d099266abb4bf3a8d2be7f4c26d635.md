### Title
Replay-verify path never checks `state_checkpoint_hash`, allowing a corrupted or divergent state root to pass verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single comparator used by every "replay and verify" code path (chunk-executor state-sync replay, backup restore-and-replay, and `db-tool replay_on_archive`) to confirm that locally re-executed transactions match the authenticated `TransactionInfo` recorded on-chain. It checks status, gas, the write-set hash (`state_change_hash`), and the event root hash, but it never compares `TransactionInfo::state_checkpoint_hash()` (the JMT/state root committed per transaction) against the state root actually produced by local re-execution.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) . It validates `status`, `gas_used`, `write_set_hash` vs `state_change_hash`, and `event_root_hash`, but the function ends with a comment acknowledging the gap without any check: [2](#0-1) . Critically, this comment only mentions the newer trading-native/hot-state/position roots — but the function never validates the base `state_checkpoint_hash` field either, and there is no feature flag gating that omission; it is unconditional.

This comparator is relied upon as the sole per-transaction integrity check in three separate flows:
- Chunk-executor replay verification during long-range state sync / backup replay: [3](#0-2) 
- The `db-tool replay_on_archive` verification tool, which is explicitly meant to catch divergence between historical committed data and freshly re-executed VM output: [4](#0-3) 

Meanwhile, the actual `state_checkpoint_hash` recorded into the ledger's `TransactionInfo` is computed once, at initial execution time, from the state-checkpoint output: [5](#0-4) . During replay, the write set is re-derived and checked against `state_change_hash`, but the resulting state tree root produced by replaying that write set is never independently re-derived and compared to the `state_checkpoint_hash` stored in the (backup-provided or previously persisted) `TransactionInfo`.

### Impact Explanation
`state_checkpoint_hash` is the field that ultimately feeds the transaction accumulator root, which is signed by validators in `LedgerInfo`. It is the primary state-commitment value that authenticates "this is the correct state after executing this transaction." Because replay-verify tooling only re-derives and checks the write-set hash and event hash — not the state root — a transaction whose write set superficially hashes correctly, or a backup/replay source that supplies a `TransactionInfo` with a `state_checkpoint_hash` that does not correspond to the actual resulting global state (e.g., due to a JMT/state-store bug, sharded commit inconsistency, or corrupted/tampered backup artifact), will be reported as "verified" by `replay_on_archive` and accepted by chunk-executor replay, even though the locally recomputed ledger state diverges from what is claimed to be authenticated. This directly matches the "committed state that differs from the correct VM result" and "hard-fork-only divergence during commit, replay, restore" impact categories — a real state-integrity divergence could go completely undetected by the tooling specifically designed to detect it.

### Likelihood Explanation
This is a genuine, currently-existing gap in the comparator used by every replay/restore verification code path, not merely a defect reachable through a rare or privileged condition — it applies unconditionally to all V0 and V1 `TransactionInfo`s, not just the yet-to-be-enabled `COMPUTE_TRADING_NATIVE_STATE_ROOTS` fields the code comment calls out. However, exploiting this for a mainnet consensus-affecting bug still requires an underlying execution/state-store divergence to exist in the first place (this check is a detection/verification safety net, not itself a state-mutation bug); the finding's severity is about loss of a critical detection mechanism for state-root corruption, rather than a directly attacker-triggerable state corruption. I was not able to fully verify whether some other, independent code path (outside this comparator and its three callers) also cross-checks the state root during replay, which would mitigate the impact — this needs further verification with full repository access.

### Recommendation
Extend `ensure_match_transaction_info` to recompute the actual post-transaction state root during replay (or accept it as a parameter alongside `expected_write_set`/`expected_events`) and assert it equals `txn_info.state_checkpoint_hash()` (and, once enabled, the hot-state and position checkpoint hashes too), causing replay-verify tooling and chunk-executor replay to fail loudly on any state-root divergence rather than silently reporting success.

### Proof of Concept
Not independently exploitable via a runnable PoC from static analysis alone: the gap is a missing assertion in `ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2203`). Conceptually: construct a `TransactionInfo` (e.g. from a backup manifest or replay input) whose `write_set`/`events` hash correctly against `state_change_hash`/`event_root_hash`, but whose `state_checkpoint_hash` does not match the real state root produced by applying that write set on top of the correct parent state (simulating a state-store bug or a tampered backup artifact). Feed it through `db-tool replay_on_archive verify` or chunk-executor replay; both will report success because `ensure_match_transaction_info` never inspects `state_checkpoint_hash`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
