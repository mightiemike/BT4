## Finding

### Title
Exchange balance arithmetic silently uses unprotected `+`/`-` (no SafeMath-equivalent) unless a disabled feature flag is enabled - (File: actuator/src/main/java/org/tron/core/actuator/AbstractExchangeActuator.java)

### Summary
The `LibEnumerableMap` report flags unprotected `-`, `+`, `/` operators that should use SafeMath-equivalent checked arithmetic. The analogous pattern exists in java-tron's exchange (AMM-style) accounting: the helper methods that are *named* like safe-math wrappers (`addExact`/`subtractExact`) only perform overflow-checked arithmetic when a dynamic chain parameter is enabled; otherwise they fall back to raw `x + y` / `x - y`.

### Finding Description
`AbstractExchangeActuator.addExact`/`subtractExact` gate the use of `StrictMathWrapper` (overflow-checked) math behind `allowHarden()`, which reads `dynamicPropertiesStore.allowHardenExchangeCalculation()`: [1](#0-0) 

These wrappers are used throughout `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` to update account balances and exchange pool balances from an anonymous, broadcast `ExchangeInjectContract` / `ExchangeWithdrawContract` / `ExchangeTransactionContract`: [2](#0-1) 

The actual token-swap math resides in `ExchangeCapsule.transaction`, which likewise only uses checked `StrictMathWrapper.addExact/subtractExact` when `hardenedCalc` (again sourced from `allowHardenExchangeCalculation`) is `true`; otherwise it performs plain `firstTokenBalance + sellTokenQuant` / `secondTokenBalance - buyTokenQuant`: [3](#0-2) 

The non-hardened `ExchangeProcessor` implementation computes the swap result using plain `double` arithmetic and casts the result to `long` with `(long) issuedSupply` / `(long) exchangeBalance`, with no overflow or precision-loss guard: [4](#0-3) 

By contrast, a hardened, BigDecimal-based `SafeExchangeProcessor` exists but is only invoked when `hardenedCalc == true`: [5](#0-4) 

Critically, `doValidate()` in `ExchangeTransactionActuator` only bounds-checks the *sell*-side balance against `getExchangeBalanceLimit()` via `addExact` (itself only checked when hardened): [6](#0-5) 
The resulting `buyTokenQuant`/`anotherTokenQuant` on the *other* side of the pool is never independently validated against `balanceLimit` in this actuator, so the correctness of the pool state after the swap depends entirely on the (potentially unchecked) processor math.

This mirrors exactly the reported bug class: math operations that look protected (or are protected in principle) but execute unprotected arithmetic on attacker-influenced values (`tokenQuant`, pool balances) under the actual default runtime configuration.

### Impact Explanation
If `allowHardenExchangeCalculation` is not enabled on a given network (this is a dynamic/committee-controlled chain parameter, not necessarily on by default), every `ExchangeInjectContract`, `ExchangeWithdrawContract`, and `ExchangeTransactionContract` broadcast by any account is processed with raw `+`/`-`/`double`-cast arithmetic on the exchange pool's token balances. This can produce silently wrapped/overflowed or precision-corrupted `firstTokenBalance`/`secondTokenBalance` values, corrupting the AMM's token-balance accounting (asset/accounting corruption) — e.g., pool balances going negative/wrapping to large positive numbers, or the received/paid quantities being computed incorrectly due to `double` truncation — without an `ArithmeticException` being thrown to block the transaction.

### Likelihood Explanation
Reachability is high in principle: the vulnerable code executes on every ordinary `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transaction from any account as long as the `allowHardenExchangeCalculation` proposal has not been activated by the witness committee on that network. I was unable to determine from the indexed code whether this parameter is `1` (enabled) by default on current java-tron mainnet/testnet genesis configuration — the default value assignment for `allowHardenExchangeCalculation` was not found in the excerpts retrieved, so this could not be conclusively confirmed as currently-exploitable on a live, fully-hardened network. Practically triggering a genuine overflow additionally requires driving `firstTokenBalance`/`secondTokenBalance`/`tokenQuant` values close to `Long.MAX_VALUE`, which is constrained (but not fully, on the buy side) by `getExchangeBalanceLimit()`.

### Recommendation
- Remove the feature-flag gating and always use overflow-checked arithmetic (`Math.addExact`/`Math.subtractExact` or `StrictMathWrapper`) for all exchange balance updates in `AbstractExchangeActuator`, `ExchangeCapsule.transaction`, and `ExchangeProcessor`, rather than making SafeMath-equivalent protection opt-in via `allowHardenExchangeCalculation`.
- Replace `ExchangeProcessor`'s `double`-based math with the `BigDecimal`/`SafeExchangeProcessor` implementation unconditionally.
- In `ExchangeTransactionActuator.doValidate`, validate the resulting `anotherTokenQuant`/buy-side balance against `getExchangeBalanceLimit()` as well, not only the sell-side balance.

### Proof of Concept
Not independently reproducible from static review alone because it depends on the live value of the `allowHardenExchangeCalculation` dynamic chain parameter (not confirmed via the indexed code) and requires crafting `tokenQuant`/pool-balance values near `Long.MAX_VALUE` bounds; a concrete PoC transaction sequence would need to be validated against a running node/testnet to confirm actual overflow triggering and resulting corrupted balances.

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
