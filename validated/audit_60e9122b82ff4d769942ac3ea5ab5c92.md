### Title
Unvalidated `dest` claim from session token trusted for shop identity and outbound OAuth token-exchange URL construction - ([File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts])

### Summary
Similar to the Knox oracle finding, where externally supplied data (Chainlink price feeds) was consumed without validating its content or format before being used in downstream calculations, this codebase takes the `dest` claim out of a decoded session-token JWT and feeds it directly into `new URL()` and into shop/session-id construction and outbound token-exchange requests, without ever passing it through the library's own `sanitizeShop` validator.

### Finding Description
`decodeSessionToken` in `packages/apps/shopify-api/lib/session/decode-session-token.ts` verifies the JWT signature, expiry (`exp`/`nbf`), and optionally the `aud` claim, but never validates the *format* or *content* of the `dest` claim itself. [1](#0-0) 

That unvalidated `dest` value is then trusted directly as a shop identity in multiple call sites, without ever calling `sanitizeShop` (the function the library uses everywhere else — e.g. `oauth.ts`, `login.ts`, `validate-shop-and-host-params.ts` — to validate that a shop string matches a genuine `*.myshopify.com`/`*.myshopify.io`/`shop.dev` domain):

- `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`: [2](#0-1) 
Here `shop` is derived from `new URL(payload.dest).hostname` and used to build the session id (`getJwtSessionId`/`getOfflineId` — note these internally do call `sanitizeShop`, but only after the value has already been used to load/query session storage keyed by an untrusted string) and is passed to `exchangeToken`, which in turn calls Shopify's `/admin/oauth/access_token` endpoint using that shop value as the request host — an outbound API URL constructed from unvalidated data.

- `packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts` and the equivalent react-router file both do `const dest = new URL(payload.dest); const shop = dest.hostname;` and pass this `shop` onward to build session identifiers and downstream client requests, without an explicit `sanitizeShop` check on `dest`. [3](#0-2) 

- `packages/apps/shopify-app-express/src/middlewares/validate-authenticated-session.ts` does the same pattern (`payload.dest.replace('https://', '')`) to determine `shop` for redirect construction. [4](#0-3) 

This mirrors the Knox root cause precisely: data returned from an external source (there, an oracle; here, a signed-but-content-unchecked JWT claim) is consumed by downstream logic (URL construction, session lookup, outbound HTTP request to Shopify) without validating that its *value* conforms to the expected shape, only that the *token itself* was cryptographically valid.

### Impact Explanation
Because `dest` is not validated for a well-formed Shopify domain before `new URL(payload.dest)` is called, a malformed or unexpected `dest` value (e.g. missing scheme in some contexts, or crafted by any Shopify-hosted surface that issues session tokens for this app with a `dest` value that doesn't match the expected shop-domain pattern) would throw an uncaught `TypeError: Invalid URL` inside these auth-handling code paths in `perform-token-exchange.ts` and `authenticate.ts`, which is not wrapped in the same broad `try/catch` used for the outer `decodeSessionToken` errors in some of these files — resulting in a 500 error / disruption of the authentication handler (a DoS of the auth handler), analogous to the "division by zero" disruption described in the Knox report. Additionally, since the shop value used for session-storage keys and for the outbound token-exchange request host is not canonicalized/validated at the point of use (only later, inside `getOfflineId`/`getJwtSessionId`), there is a window where an unsanitized string is used to build the URL sent to `/admin/oauth/access_token`.

### Likelihood Explanation
Exploitability is constrained by the fact that `dest` sits inside a JWT signed with the app's own secret key, so an external attacker cannot forge a `dest` value without already possessing `apiSecretKey`. The most plausible trigger is therefore not attacker-forged content but unexpected/malformed `dest` formatting from legitimate Shopify-issued tokens in edge surfaces (checkout/POS/customer-account extension tokens, which tests confirm can omit the protocol, e.g. `dest: 'test-shop.myshopify.com'`), which increases the chance that some caller path hits `new URL()` on a value that isn't a full URL and throws unexpectedly. I could not fully verify (due to reaching the tool-call limit) whether each of these five call sites is wrapped in a try/catch that gracefully handles a `new URL()` throw, so likelihood of the DoS impact specifically is **uncertain** and should be verified by directly tracing exception handling around each `new URL(payload.dest)` call.

### Recommendation
- Validate `dest` (and any other externally influenced claims used for shop identity) through `sanitizeShop`/hostname-format validation immediately after decoding the session token and before using it in `new URL()`, session-id derivation, or outbound request construction.
- Wrap `new URL(payload.dest)` parsing in explicit error handling that returns a clean 400/401 response rather than allowing an uncaught exception to propagate out of the auth handler.
- Ensure `decodeSessionToken` itself optionally validates that `dest`/`iss` match the expected Shopify domain regex, consistent with how `sanitizeShop`/`sanitizeHost` are already used for other user-supplied shop/host values elsewhere in the codebase.

### Proof of Concept
Not independently reproducible with certainty from static review alone — the concrete trigger depends on confirming (1) whether any legitimate Shopify-issued session token surface can produce a `dest` value that fails `new URL()` parsing, and (2) whether the specific call sites lack a catch handler for that throw. Recommend a background Devin session to: (a) grep all five `new URL(payload.dest)` call sites for enclosing try/catch scope, and (b) write a unit test supplying a JWT with a malformed `dest` (e.g. `dest: 'not a url'`) through `shopify.authenticate.admin`, `shopify.validateAuthenticatedSession()` (express), and `performTokenExchange` to observe whether an unhandled exception/500 results instead of a controlled 400/401.

```typescript
export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
```

```typescript
async function setShopFromSessionOrToken(
  api: Shopify,
  session: Session | undefined,
  token: string,
): Promise<string | undefined> {
  let shop: string | undefined;

  if (session) {
    shop = session.shop;
  } else if (api.config.isEmbeddedApp) {
    const payload = await api.session.decodeSessionToken(token);
    shop = payload.dest.replace('https://', '');
  }
  return shop;
}
```
