### Title
`shop` parameter used for token exchange is never cross-checked against the verified session token's embedded shop (`dest`) - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Summary
This is the same bug class as the Beedle `buyLoan` finding: an operation combines two independent identifiers — a caller-supplied identifier (`poolId` in Beedle, `shop` here) and an identifier implicitly carried by an authenticated credential (`loan.collateralToken`/`loan.loanToken` in Beedle, the session token's `dest` claim here) — without verifying that the two actually refer to the same entity. In `shopify-app-js`, `tokenExchange()` accepts a `shop` string and a `sessionToken`, decodes the token (verifying signature and `aud`) but never checks that the shop embedded in the token matches the `shop` argument before using it to build the OAuth token-exchange request and to key the resulting session.

### Finding Description
`tokenExchange()` decodes and cryptographically validates `sessionToken` but only checks `payload.aud === config.apiKey`; it never compares `payload.dest`/shop to the `shop` parameter it was called with: [1](#0-0) 

`decodeSessionToken()` itself only validates signature, expiry and `aud`, and returns the raw payload without asserting any shop binding: [2](#0-1) 

The `shop` value that reaches `tokenExchange()` in the Remix strategy is not derived from the verified token at all — it comes straight from an unauthenticated request query parameter: [3](#0-2) 

That `shop` is then passed alongside `sessionToken` into `exchangeToken()`/`api.auth.tokenExchange()`: [4](#0-3) 

Notably, the Express implementation of the same feature avoids this exact issue by deriving `shop` from the verified `payload.dest` rather than from request input: [5](#0-4) 

This confirms the root cause is a missing consistency check inside the shared `tokenExchange()` function in `shopify-api` itself (not just a caller mistake) — the function should reject or ignore a `shop` argument that does not match the token's own shop claim, but it doesn't. Any consumer that (like the Remix strategy) sources `shop` from unauthenticated request state rather than from the verified token inherits the vulnerability.

### Impact Explanation
If a caller path supplies a `shop` value that isn't cross-validated against the session token's actual shop, the library will issue a token-exchange request to `https://${shop}/admin/oauth/access_token` using a `subject_token` bound to a different shop, and will store/key the resulting session under the caller-supplied `shop`. This mirrors the `buyLoan` root cause: trusting a caller-supplied identifier to associate with a resource without checking it against the identifier embedded in the authenticated credential — enabling potential cross-tenant session confusion (wrong shop's session data being requested/stored) if the target Shopify endpoint's own validation is bypassed or if the mismatch value is trusted for local session storage keys.

### Likelihood Explanation
Exploitability ultimately depends on whether Shopify's real `/admin/oauth/access_token` endpoint independently rejects a `subject_token` whose `dest` doesn't match the request host — this external enforcement could not be verified from the codebase. What is verifiable, and is the actual code defect, is that the shopify-app-js library performs no such check itself, and that the Remix authentication path can be reached by any unauthenticated caller (`shop` from `?shop=` query string) supplying a session token for a different store, which is precisely the "unprivileged actor, single request" reachability required.

### Recommendation
In `tokenExchange()` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), after decoding the session token, assert that the shop derived from `payload.dest` matches the `shop` parameter passed to the function (throwing `InvalidJwtError`/similar on mismatch) before constructing the outbound request or session — matching the safer pattern already used in `shopify-app-express/src/middlewares/perform-token-exchange.ts`, which derives `shop` exclusively from the verified token.

### Proof of Concept
Not independently reproduced against a live Shopify OAuth server (which may or may not itself reject the mismatched `dest`); the concrete, verifiable defect is the absence of a `payload.dest === shop` check in `tokenExchange()`/`decodeSessionToken()`, demonstrated by direct code inspection of the cited files, contrasted with the Express implementation's stricter derivation of `shop` from the token itself.

export function decodeSessionToken(config: ConfigInterface) {
  return async (
    token: string,
    {checkAudience = true}: DecodeSessionTokenOptions = {},
  ): Promise<JwtPayload> => {
    let payload: JwtPayload;
    try {
      payload = (
        await jose.jwtVerify(token, getHMACKey(config.apiSecretKey), {
          algorithms: ['HS256'],
          clockTolerance: JWT_PERMITTED_CLOCK_TOLERANCE,
        })
      ).payload as unknown as JwtPayload;
    } catch (error) {
      throw new ShopifyErrors.InvalidJwtError(
        `Failed to parse session token '${token}': ${error.message}`,
      );
    }

    // The exp and nbf fields are validated by the JWT library

    if (checkAudience && payload.aud !== config.apiKey) {
      throw new ShopifyErrors.InvalidJwtError(
        'Session token had invalid API key',
      );
    }

    return payload;
  };
