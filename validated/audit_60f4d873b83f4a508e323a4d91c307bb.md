Move's execution model on the VM is atomic per transaction: any `abort` anywhere in this call chain (e.g., a malformed/empty `code` vector triggering a bytecode-verification failure in the native `request_publish`, or a BCS deserialization mismatch in `util::from_bytes` for a crafted `metadata_serialized`) causes the entire transaction, including the `PackageRegistry` mutation via `borrow_global_mut` writes and the `move_to(code_signer, ManagingRefs {...})`, to be rolled back before the VM produces a write set. The executor never commits partial resource writes for an aborted transaction — `PackageRegistry` and `ManagingRefs` are written or not written together, never inconsistently, because the abort occurs before the VM session's mutations are converted into a `ChangeSet`/write set at all.
