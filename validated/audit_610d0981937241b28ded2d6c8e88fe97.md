### Title
`TransactionOutput::ensure_match_transaction_info` skips state-checkpoint hash validation, allowing state-root divergence to go undetected during replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative check used by chunk replay and state-sync verification paths to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded in the transaction accumulator. The function validates status, gas used, write-set hash, and event root hash, but explicitly and admittedly skips validating `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that actually commit to the JMT/state-Merkle root produced by execution. [1](#0-0) 

### Finding Description
`ensure_match_transaction_info` is meant to be the integrity gate that proves a replayed/re-executed transaction output is consistent with what was actually committed to the ledger (analogous to verifying an invariant that should cover *all* relevant state, not a subset). It checks:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- write-set hash vs `txn_info.state_change_hash()`
- event root hash vs `txn_info.event_root_hash()` [2](#0-1) 

But it does not check the state-checkpoint-hash fields carried in `TransactionInfo` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`), which are the fields that bind the transaction info to the actual root of the state Merkle tree(s) after execution. The code contains an explicit acknowledgement of this gap: [3](#0-2) 

This is structurally the same class of bug as the stableswap report: a commitment/invariant check that is supposed to cover the full state (all tokens in the pool / all committed fields of the transaction) but is instead computed/verified over only a strict subset (offer/ask tokens / write-set+events+gas+status), silently ignoring other components (the third token / the checkpoint hashes) that are part of the true invariant.

This function is used by exactly the code paths responsible for detecting execution/replay divergence:
- `execution/executor/src/chunk_executor/mod.rs` (chunk replay/verify-execution path used by state sync and fast sync)
- `storage/db-tool/src/replay_on_archive.rs` (the tool explicitly designed to replay historical transactions from an archive and flag divergence from committed history)
- `aptos-move/cli/src/commands.rs` [4](#0-3) 

### Impact Explanation
Since the checkpoint-hash fields are omitted from the comparison, a node whose locally computed state root (state Merkle tree, hot-state tree, or the new position/native-orderbook state tree) diverges from the authenticated `TransactionInfo.state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` will still pass `ensure_match_transaction_info` as long as the write set, events, gas, and status match. Because write-set/event/gas/status equality does not imply state-root equality (the state root is derived by *applying* the write set into a Merkle tree, a step this check does not re-verify), replay-verify and chunk-verification tooling can report a "successful" replay even though the actual authenticated state commitment has silently diverged from local execution. That undermines the core state-integrity guarantee these tools exist to provide: that committed durable ledger state matches the correct VM result, and it also means proof/verification tooling built on top of `TransactionInfo` fields it doesn't cross-check (position-state proofs, hot-state proofs) has no independent verification against replay in this code path.

### Likelihood Explanation
The comment in the code is explicit that this is a known, intentional gap ("TODO(trading-native): ... Validate the checkpoint hashes here before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`"), which confirms this is not a hypothetical trigger — it is the current, shipped behavior of `ensure_match_transaction_info` and is reachable any time chunk replay/verification or `replay_on_archive` runs against transactions that contain a state-checkpoint transaction (i.e., end of block/epoch), which happens on every block boundary. I could not fully verify within available context whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently enabled on mainnet (this feature flag reference appears in `types/src/on_chain_config/aptos_features.rs`, `aptos-move/aptos-release-builder/src/components/feature_flags.rs`, and `storage/aptosdb/src/db/aptosdb_reader.rs`, but I was not able to inspect their contents in this session due to tool-call limits) — if that feature is not yet active, then the `position_state_checkpoint_hash`/hot-state gap may currently be a no-op divergence source, but the `state_checkpoint_hash` skip for the classic state-Merkle-tree root is unconditional and always in scope regardless of that flag.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the locally computed state-checkpoint hash(es) (state Merkle root, hot-state root, and position-state root when applicable) against the corresponding fields on `txn_info`, failing the check (as with the other fields) on mismatch, before this function is relied upon by chunk executor verification, `replay_on_archive`, or any other divergence-detection tooling.

### Proof of Concept
Not independently exploitable as a standalone PoC without further access to `COMPUTE_TRADING_NATIVE_STATE_ROOTS` gating logic and the exact call sites in `chunk_executor/mod.rs` / `replay_on_archive.rs`, which I was unable to fully read in the remaining budget. The root-cause evidence is the code itself: `ensure_match_transaction_info` at `types/src/transaction/mod.rs` lines 2139-2203 checks status/gas/write-set-hash/event-root-hash but never compares `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` against any locally recomputed value, and the surrounding comment confirms this omission is known and unresolved. A concrete exploit/PoC (e.g., constructing a chunk whose replayed state root differs but write set/events/gas/status match) would require executing the chunk-executor/replay-on-archive code paths, which is beyond the scope of static analysis here.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
