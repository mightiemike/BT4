### Title
FunctionCall access-key allowance is not tracked in `PendingConstraints`, allowing concurrent pending chunks to exceed the key's allowance cap - ([File: runtime/runtime/src/verifier.rs])

### Summary
`PendingConstraints` (used to prevent double-spending across not-yet-certified chunks) tracks `paid_from_balance`, `paid_from_gas_key`, `max_nonce`, and `max_bootstrap_nonce`, but has no field for allowance already consumed by a `FunctionCall` access key in other pending, uncertified chunks. The allowance check in `check_and_compute_new_allowance` reads the access key's on-trie `allowance` value directly, with no adjustment for pending consumption, unlike the balance check which explicitly subtracts `pending.paid_from_balance`.

### Finding Description
`verify_and_charge_tx_ephemeral` (`runtime/runtime/src/verifier.rs:312-404`) computes `available_balance = account.amount().saturating_sub(pending.paid_from_balance)` and checks it against `total_cost` [1](#0-0) . This correctly prevents two concurrently-pending chunks from independently succeeding a balance check against the same stale account balance, since the pending amount already committed by earlier uncertified chunks is subtracted first.

By contrast, the allowance check is performed by `check_and_compute_new_allowance`, which reads `access_key.permission.function_call_permission().allowance` straight from the (stale, not-yet-applied) access key state and subtracts only `total_cost` of the current transaction [2](#0-1) . It receives no `pending` parameter and never consults `pending.paid_from_balance` or any allowance-specific pending counter [3](#0-2) .

The `AccessKey`'s allowance is only actually decremented in the trie when a chunk is certified via `VerificationResult::apply` (`runtime/runtime/src/lib.rs:337-376`), which writes `permission.allowance = Some(*a)` [4](#0-3) . Until certification, every subsequent chunk-preparation pass (or RPC-time verification via `validate_verify_and_charge_transaction`, `runtime/runtime/src/verifier.rs:1071-1130`) re-reads the same stale, not-yet-decremented allowance from state and re-validates a fresh transaction against the *full* original allowance rather than the allowance remaining after other uncertified, in-flight spending is accounted for.

This is architecturally identical to the CVE-2025-7954 Shopware bug class: a check-then-act race on a usage/spend cap where the "act" (decrement) is deferred (here: deferred until certification) but the "check" is repeated against the stale un-decremented value for each new concurrent request, permitting the cap to be exceeded by the sum of multiple concurrently-pending uses.

`PendingConstraints`'s design elsewhere (see `paid_from_balance`, `paid_from_gas_key` in `chain/client/src/pending_transaction_queue.rs:405-468, 553-593`) demonstrates the nearcore authors are aware that pending/uncertified spend must be tracked to prevent exactly this kind of double-spend; the allowance path was not given the equivalent tracking.

### Impact Explanation
A `FunctionCall` access key's `allowance` is specifically designed as a hard spending cap independent of, and typically much smaller than, the full account balance — it exists to bound the blast radius of a limited-permission key used by an app/contract integration (e.g. a key intended to spend at most 1 NEAR on gas over its lifetime, on an account holding much larger reserves). If the allowance check does not account for other uncertified, already-admitted-but-not-yet-applied spending against the same key, an attacker holding such a restricted key can submit multiple transactions in quick succession so that they land in separate, concurrently pending (uncertified) chunks. Each verification pass reads the same stale full allowance and each independently succeeds, so the aggregate spend against that key can exceed its configured allowance — a fee/spend-cap bypass, i.e., unauthorized value movement beyond the explicitly authorized limit for that key. This maps to the report's accepted impact categories ("fee or gas bypass" / "concrete unauthorized value movement").

### Likelihood Explanation
This does not require a malicious validator, peer, or any privileged role — it can be triggered purely by an unprivileged holder of a `FunctionCall` access key submitting ordinary transactions through standard RPC in quick succession, relying on normal, non-adversarial multi-chunk pipelining (several chunks can be produced/included before the earlier one is certified/applied). No node or protocol-layer manipulation is needed; it only requires that more than one chunk touching the same access key be in flight (uncertified) at once, which is a routine occurrence in the existing pending-transaction-queue design that this file's own comments/tests assume for balance and nonce tracking.

### Recommendation
Add allowance tracking to `PendingConstraints` (or an equivalent per-access-key pending-allowance ledger in `PendingTransactionQueue`/`PendingTxSession`), mirroring `paid_from_balance`/`paid_from_gas_key`. `check_and_compute_new_allowance` should be extended to accept and subtract the pending, not-yet-certified allowance consumption for the given `(account_id, public_key)` before validating `total_cost` against the remaining allowance, exactly as `verify_and_charge_tx_ephemeral` already does for `pending.paid_from_balance` against `account.amount()`.

### Proof of Concept
1. Create an account with a `FunctionCall` access key whose `FunctionCallPermission.allowance = Some(X)` and a large overall account balance (`>> X`), targeting a fixed `receiver_id`/method.
2. Craft two (or more) valid transactions signed by this key, each with `total_cost` close to `X` (e.g. `0.9 * X`), with sequential nonces.
3. Submit them so they are picked up by chunk production/prepared for two different, concurrently outstanding (uncertified) chunks before the first is applied/certified — e.g. via `prepare_transactions_extra` invoked for successive un-certified blocks, or via `validate_verify_and_charge_transaction`/RPC submission timed against the pending-transaction-queue window described in `chain/client/src/pending_transaction_queue.rs`.
4. Because `verify_and_charge_tx_ephemeral` → `check_and_compute_new_allowance` (`runtime/runtime/src/verifier.rs:282-303, 365-373`) reads the on-trie allowance directly and ignores `pending`, both transactions independently pass `NotEnoughAllowance`, even though their combined cost (`~1.8 * X`) exceeds the key's configured allowance `X`.
5. Once both chunks are eventually certified/applied, the access key's `allowance` field (decremented sequentially, `runtime/runtime/src/lib.rs:349-359`) underflows/saturates or the total spend against the key's cap ends up exceeding `X` — the intended cap was bypassed by the concurrency window, analogous to exceeding Shopware's voucher usage cap via concurrent requests.

fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
