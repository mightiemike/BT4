## Title
Excess attached deposit sent to the NEAR Wallet Contract's `rlp_execute` is never refunded on success — funds get permanently stranded - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit "Wallet Contract" (`rlp_execute` entry point) accepts an `attached_deposit` from an external caller and stores the *entire* amount as `CallerDeposit` so it can be refunded if the resulting cross-contract call/promise fails. However, the actual value forwarded in the generated action is computed independently from the signed Ethereum transaction's `value`/`yocto_near` fields, not from `attached_deposit`. If the caller attaches more NEAR than the action actually needs and the call **succeeds**, the surplus is never refunded — `CallerDeposit` is only consulted on the `Failed` branch of the callback. This mirrors the reported Solidity bug pattern of accepting `msg.value` without refunding the excess.

### Finding Description
`CallerDeposit::new` captures the full `attached_deposit` of an external (non-self) caller of `rlp_execute`: [1](#0-0) 

The amount actually attached to the outgoing promise/action is computed from the signed RLP Ethereum transaction's `value` field and the small `yocto_near` (`u32`) field embedded in the ABI-decoded action — a value that is completely independent of what the relayer chooses to attach as `attached_deposit` on the Near transaction: [2](#0-1) [3](#0-2) 

`inner_rlp_execute` builds the promise from this independently-derived `action` deposit, while separately tracking `caller_deposit = CallerDeposit::new(&context)` based on the full `attached_deposit`: [4](#0-3) 

The refund of `caller_deposit` only happens in the `Failed` branch of `rlp_execute_callback`; on success, nothing checks whether the promise's actual deposit matched the caller's `attached_deposit`, and no refund of any surplus occurs: [5](#0-4) 

The project's own test acknowledges this behavior explicitly by asserting that on success the caller loses at least the full attached amount ("does not get a refund when their tokens are spent"), without verifying that the amount lost matches only what was actually required by the action: [6](#0-5) 

Because `attached_deposit` (what the Near transaction actually transfers into the wallet-contract account) and the eth-tx-derived `deposit` used for the outbound promise (`additional_value.saturating_add(yocto_near)`) are two unrelated numbers, any caller/relayer that attaches more NEAR than the action needs will see the excess permanently retained by the wallet-contract account with no code path to reclaim it once the inner promise succeeds.

### Impact Explanation
This is a fund-loss / frozen-funds bug reachable by any unprivileged external account calling `rlp_execute` on a NEAR Wallet Contract (eth-implicit account) with `attached_deposit` greater than what the embedded, signed Ethereum transaction's value dictates. On success, the surplus NEAR becomes stuck in the wallet-contract account's balance — it is not credited to the intended receiver, not returned to the caller, and not accounted for by any other logic in the contract. Depending on caller behavior (e.g. a relayer overestimating required funds, or a buggy/careless integration attaching a round/fixed deposit regardless of the actual `tx.value`), this can silently and repeatedly strand user or relayer funds.

### Likelihood Explanation
Likelihood is moderate: nothing in the protocol enforces that `attached_deposit` on the Near-level call matches the value encoded in the RLP transaction. Any relayer or integrator that is not extremely careful to attach *exactly* the derived deposit (`additional_value + yocto_near`, itself a nontrivial derived value involving `MAX_YOCTO_NEAR` scaling and `VALUE_MAX` clamping) will overpay and lose the difference on success. Because relayers are third-party software integrating with the wallet contract, mismatches are plausible in practice, not merely theoretical.

### Recommendation
On the success path in `rlp_execute_callback` (and correspondingly in `inner_rlp_execute`/`CallerDeposit`), compute the excess as `attached_deposit - action_deposit_actually_forwarded` and refund that difference back to the external caller (`predecessor_account_id`), mirroring the deposit-refund logic already used for the `Failed` case, rather than only ever refunding the entire attached deposit or nothing at all.

### Proof of Concept
1. An external account (not the wallet contract's own owner) calls `rlp_execute` on an eth-implicit wallet-contract account, signing a valid RLP transaction whose ABI-decoded action deposit (`additional_value.saturating_add(yocto_near)`) is `X` yoctoNEAR.
2. The caller attaches `attached_deposit = X + Δ` (Δ > 0) to the Near `FunctionCall` invoking `rlp_execute`.
3. `CallerDeposit::new` records `X + Δ` as the amount to refund only if the resulting promise fails.
4. `inner_rlp_execute`/`action_to_promise` builds and dispatches the action using only `X` (derived from the RLP tx), which succeeds.
5. `rlp_execute_callback` hits the `PromiseResult::Successful` branch, which does not reference `caller_deposit` at all — `Δ` is neither forwarded to the receiver nor refunded to the caller, permanently increasing the wallet-contract account's balance without any accounting path to release it back to its rightful owner.
