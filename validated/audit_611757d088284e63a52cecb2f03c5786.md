### Title
Lenient hex-string decoding in `ByteArray.fromHexString()` may silently accept malformed/mis-sized addresses in HTTP API servlets - (File: `common/src/main/java/org/tron/common/utils/ByteArray.java`)

### Summary
`ByteArray.fromHexString()` mirrors the bug class described in the external report: it silently "fixes up" malformed hex input (odd length gets a `0` prepended) rather than rejecting it, and it performs no length validation against the caller's expected size (e.g., 21-byte TRON address). This function is used directly, unchecked, by numerous HTTP API servlets to parse the `address` request parameter.

### Finding Description
`ByteArray.fromHexString()`:
```java
public static byte[] fromHexString(String data) {
  if (data == null) {
    return EMPTY_BYTE_ARRAY;
  }
  if (data.startsWith("0x")) {
    data = data.substring(2);
  }
  if (data.length() % 2 != 0) {
    data = "0" + data;
  }
  return Hex.decode(data);
}
``` [1](#0-0) 

Compare this to the ENS `HexUtils.hexStringToBytes32()` bug: no rejection of odd-length input, no rejection of over/under-length input relative to what the caller expects it to represent. Here, an odd-length string is padded rather than rejected, and there is no upper/lower bound check on the decoded length at all — the caller (many HTTP servlets) is expected to enforce a fixed length but often does not.

Several HTTP servlets call this directly on the raw user-supplied `address` parameter without any length check before constructing a `ByteString`/using it as a lookup key, e.g.:
```java
String address = request.getParameter("address");
if (visible) {
  address = Util.getHexAddress(address);
}
fillResponse(visible, ByteString.copyFrom(ByteArray.fromHexString(address)), response);
``` [2](#0-1) 

The same unchecked pattern appears in `GetAccountResourceServlet`, `GetAssetIssueByAccountServlet`, `GetAvailableUnfreezeCountServlet`, `GetCanDelegatedMaxSizeServlet`, `GetDelegatedResourceAccountIndexServlet`, `GetDelegatedResourceAccountIndexV2Servlet`, `GetDelegatedResourceServlet`, `GetDelegatedResourceV2Servlet`, `GetMarketOrderByAccountServlet`, and `ScanShieldedTRC20NotesByIvkServlet`. [3](#0-2) 

By contrast, the newer JSON-RPC layer (`JsonRpcApiUtil`) has already been hardened with explicit length checks and regex validation for addresses, hashes, and topics before calling `ByteArray.fromHexString`, including code comments noting "oversized input rejected before fromHexString":
```java
public static byte[] addressCompatibleToByteArray(String hexAddress)
    throws JsonRpcInvalidParamsException {
  if (hexAddress == null || hexAddress.length() > DecodeUtil.ADDRESS_SIZE + 2) {
    throw new JsonRpcInvalidParamsException("invalid address");
  }
  ...
``` [4](#0-3) 

This asymmetry suggests the JSON-RPC surface was already patched against exactly this bug class, while the legacy HTTP wallet servlets were not.

### Impact Explanation
I was unable to fully confirm within the available tool budget whether an unvalidated, wrong-length address reaching `wallet.getAccountNet()`, `wallet.getDelegatedResource()`, etc. leads to anything beyond a benign "account not found" response (i.e., a wrong-length key simply fails to match any store key). I could not verify whether any of these decoded byte arrays are used in a context where a mis-sized/zero-padded value could cause: (a) a DoS via unhandled exception, (b) incorrect address-prefix coercion enabling cross-account key collisions, or (c) any state-mutating actuator path (as opposed to these read-only `Get*Servlet`s). All servlets found in this search were read-only query endpoints, not transaction/actuator state-transition paths, which limits the concrete impact I can substantiate.

### Likelihood Explanation
The endpoints are reachable via anonymous HTTP requests (no authentication), and the lenient parsing is trivially triggerable by supplying an odd-length or wrong-length `address` parameter. However, likelihood of a *security-relevant* outcome (beyond a malformed lookup returning empty/null) is unconfirmed.

### Recommendation
Given the confirmed asymmetry (JSON-RPC layer hardened, legacy HTTP servlets not), the recommendation is to apply the same validation used in `JsonRpcApiUtil.addressCompatibleToByteArray`/`hashToByteArray` (length bounds + regex before decode) uniformly to the HTTP `Get*Servlet` address/hash parsing paths that currently call `ByteArray.fromHexString()` directly on unchecked user input, and to make `ByteArray.fromHexString()` itself reject odd-length input rather than silently padding it, unless callers explicitly opt into lenient parsing (as already partially modeled by the `HexMode.STRICT`/`LENIENT` distinction introduced in `JsonRpcApiUtil`). [5](#0-4)

  public static byte[] addressCompatibleToByteArray(String hexAddress)
      throws JsonRpcInvalidParamsException {
    // ADDRESS_SIZE (42) is the hex length of a 21-byte address; +2 leaves room for the optional
    // "0x" prefix, so a 0x-prefixed 21-byte address (0x41..., 44 chars) is still accepted.
    if (hexAddress == null || hexAddress.length() > DecodeUtil.ADDRESS_SIZE + 2) {
      throw new JsonRpcInvalidParamsException("invalid address");
    }
    byte[] addressByte;
    try {
      addressByte = ByteArray.fromHexString(hexAddress);
      if (addressByte.length != DecodeUtil.ADDRESS_SIZE / 2
          && addressByte.length != DecodeUtil.ADDRESS_SIZE / 2 - 1) {
        throw new JsonRpcInvalidParamsException("invalid address");
      }

      if (addressByte.length == DecodeUtil.ADDRESS_SIZE / 2 - 1) {
        addressByte = ByteUtil.merge(new byte[] {DecodeUtil.addressPreFixByte}, addressByte);
      } else if (addressByte[0] != ByteArray.fromHexString(DecodeUtil.addressPreFixString)[0]) {
        // addressByte.length == DecodeUtil.ADDRESS_SIZE / 2
        throw new JsonRpcInvalidParamsException("invalid address");
      }
    } catch (Exception e) {
      throw new JsonRpcInvalidParamsException(e.getMessage());
    }
    return addressByte;
  }

  /**
   * Validation mode for {@link #requireValidHex}.
   */
  public enum HexMode {
    /**
     * Execution-apis BYTES schema: requires {@code 0x} prefix and
     * even total length; {@code ""} is accepted as empty bytes per
     * geth's {@code hexutil.Bytes.UnmarshalText}.
     */
    STRICT,
    /**
     * {@link ByteArray#fromHexString}'s lenient parsing: accepts bare
     * hex and odd-length input. Kept for backward compatibility.
     */
    LENIENT
  }

  /**
   * Throws if {@code value} is not parseable hex under the given
   * {@code mode}. {@code null} is treated as absent and returns
   * silently. {@code fieldName} is used only in error messages.
   */
  public static void requireValidHex(String fieldName, String value, HexMode mode)
      throws JsonRpcInvalidParamsException {
    if (value == null) {
      return;
    }
    if (mode == HexMode.STRICT) {
      if (value.isEmpty()) {
        return;
      }
      if (!value.startsWith("0x") || value.length() % 2 != 0) {
        throw new JsonRpcInvalidParamsException(
            "invalid hex string for \"" + fieldName + "\"");
      }
    }
    try {
      ByteArray.fromHexString(value);
    } catch (Exception e) {
      throw new JsonRpcInvalidParamsException(
          "invalid hex string for \"" + fieldName + "\"");
    }
  }
