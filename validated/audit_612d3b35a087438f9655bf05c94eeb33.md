### Title
Reverted/exception TVM execution skips `resetAccountUsage`, causing `payEnergyBill`'s `EnergyProcessor.useEnergy` to settle on top of the un-rolled-back pre-charge reservation from `getAccountEnergyLimitWithFixRatio` - ([File: chainbase/src/main/java/org/tron/core/db/TransactionTrace.java])

### Summary
Under `allowTvmFreezeV2`/`supportUnfreezeDelay`, `VMActuator.getAccountEnergyLimitWithFixRatio` pre-charges (merges) up to `min(leftFrozenEnergy, energyFromFeeLimit)` worth of energy usage into the caller's (and possibly origin's) persisted `AccountCapsule` before execution. `TransactionTrace.pay()` is supposed to "un-merge" this reservation via `resetAccountUsage` before the real bill is applied by `ReceiptCapsule.payEnergyBill` → `EnergyProcessor.useEnergy`, but that reset is only performed when `getRuntimeResult().getException() == null && !getRuntimeResult().isRevert()`. On any reverted or exception-terminated execution, the reset is skipped while `payEnergyBill` still unconditionally calls `useEnergy`, which additively increases usage on top of the still-inflated (un-reset) baseline.

### Finding Description
`VMActuator.getAccountEnergyLimitWithFixRatio` (lines 583-601) pre-charges energy into the account's persisted window and commits it via `rootRepository.updateAccount`: [1](#0-0) 

At the end of the transaction, `TransactionTrace.pay()` conditionally calls `resetAccountUsage` to strip this reservation back out, but **only** if execution succeeded without exception or revert: [2](#0-1) 

`resetAccountUsage` computes `newUsage` by explicitly "dropping the pre consumed frozen energy" (`mergedUsage`) and substituting the real usage (`usage`): [3](#0-2) 

Regardless of whether the reset ran, `receipt.payEnergyBill(...)` executes unconditionally right after: [4](#0-3) 

`ReceiptCapsule.payEnergyBill` then calls `EnergyProcessor.useEnergy(account, usage, now)` with the real gas usage (`receipt.getEnergyUsageTotal()`, set from `ProgramResult.getEnergyUsed()` regardless of revert), which is additive on top of `account.getEnergyUsage()`: [5](#0-4) [6](#0-5) 

So the sequence is:
1. Pre-charge merges up to `min(leftFrozenEnergy, energyFromFeeLimit)` into the caller's/origin's window and persists it (`VMActuator.java:589-600`).
2. Execution reverts or throws (attacker-controlled — any `REVERT`, `OUT_OF_ENERGY`, or similar failure path sets `ProgramResult.revert`/`exception`) — `chainbase/src/main/java/org/tron/common/runtime/ProgramResult.java:74-80,119-125`.
3. `TransactionTrace.pay()`'s reset condition (`TransactionTrace.java:261-262`) evaluates false, so `resetAccountUsage` is skipped — the reservation is never rolled back.
4. `payEnergyBill`/`useEnergy` still runs and adds the real energy usage on top of the still-inflated window, permanently inflating the account's `EnergyUsage`/window beyond what was actually consumed for this single logical transaction.

This matches the "executes against a different baseline, causing the account to be … permanently double-charged" branch of the question, though not the "settlement never executes" branch — `payEnergyBill` always runs; the divergence is that it runs against a stale, un-reset baseline.

### Impact Explanation
When `caller != origin` (a normal user calling someone else's deployed contract with a `consumeUserResourcePercent < 100`), the origin (contract owner)'s reset is likewise skipped on revert. An attacker who is merely the caller — with no special privilege — can force reverts (e.g., a `require()`/`revert` early in the callee) to permanently inflate the origin's persisted energy usage window beyond real consumption, without cost to the attacker beyond a possibly small fee-limit-bounded reservation. Repeated over a block window this degrades/exhausts the frozen energy allowance available to a victim contract for its legitimate future callers, a griefing/DoS effect on the victim's resource ledger, and constitutes a real double-accounting/invalid-state divergence in the persisted `AccountCapsule.EnergyUsage`.

### Likelihood Explanation
Preconditions are mainnet-realistic: `allowTvmFreezeV2` + `supportUnfreezeDelay` (Stake 2.0) enabled, which is the current mainnet configuration. Triggering a revert is trivial and fully attacker-controlled (any `TriggerSmartContract` call to a contract that reverts, e.g. via a failing `require`). No special timing or race condition is needed — this happens on every reverted TVM call under freeze v2, making it highly repeatable.

### Recommendation
Remove the exception/revert exclusion from the reset condition in `TransactionTrace.pay()` (`chainbase/src/main/java/org/tron/core/db/TransactionTrace.java:261-262`), or otherwise ensure `resetAccountUsage`/`resetAccountUsageV2` always runs before `payEnergyBill` regardless of `getException()`/`isRevert()`, so the pre-charge reservation is always trimmed back to the real recorded usage (`receipt.getEnergyUsageTotal()`) prior to final billing, for both origin and caller accounts.

### Proof of Concept
Integration test plan (extending `RuntimeImplTest`/`EnergyProcessorTest` patterns already in the repo):
1. Enable `allowTvmFreezeV2` and `supportUnfreezeDelay` via `DynamicPropertiesStore` (as done in `framework/src/test/java/org/tron/common/runtime/vm/VMConfigIsolationTest.java`).
2. Deploy a contract owned by `origin`, with `consumeUserResourcePercent < 100`, and freeze enough energy for `origin`.
3. Freeze energy for `caller` (a distinct account) sufficient to pass `getAccountEnergyLimitWithFixRatio`'s pre-charge.
4. Craft a `TriggerSmartContract` call to a callee function that unconditionally `revert()`s after consuming some energy.
5. Execute via `RuntimeImpl.execute` + `TransactionTrace.exec()`/`finalization()` (mirroring `RuntimeImplTest`), capturing `origin`'s `AccountCapsule.getEnergyUsage()`/window before and after.
6. Assert: after the single reverted transaction, `origin.getEnergyUsage()` equals only the real `receipt.getEnergyUsageTotal()`-derived origin share (correct behavior) — the test should currently **fail**, showing `origin.getEnergyUsage()` also includes the un-rolled-back pre-charge reservation from step 1 (i.e., inflated beyond one billing pass), demonstrating the double-accounting.

  private void resetAccountUsage(AccountCapsule accountCap,
      long usage, long size, long mergedUsage, long mergedSize, long size2) {
    if (dynamicPropertiesStore.supportAllowCancelAllUnfreezeV2()) {
      resetAccountUsageV2(accountCap, usage, size, mergedUsage, mergedSize, size2);
      return;
    }
    long currentSize = accountCap.getWindowSize(ENERGY);
    long currentUsage = accountCap.getEnergyUsage();
    // Drop the pre consumed frozen energy
    long newArea = currentUsage * currentSize
        - (mergedUsage * mergedSize - usage * size);
    // If area merging happened during suicide, use the current window size
    long newSize = mergedSize == currentSize ? size : currentSize;
    // Calc new usage by fixed x-axes
    long newUsage = max(0, newArea / newSize, dynamicPropertiesStore.disableJavaLangMath());
    // Reset account usage and window size
    accountCap.setEnergyUsage(newUsage);
    accountCap.setNewWindowSize(ENERGY, newUsage == 0 ? 0L : newSize);
  }

  public boolean useEnergy(AccountCapsule accountCapsule, long energy, long now) {

    long energyUsage = accountCapsule.getEnergyUsage();
    long latestConsumeTime = accountCapsule.getAccountResource().getLatestConsumeTimeForEnergy();
    long energyLimit = calculateGlobalEnergyLimit(accountCapsule);
    long newEnergyUsage;
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newEnergyUsage = increase(energyUsage, 0, latestConsumeTime, now);
    } else {
      // only participate in the calculation as a temporary variable, without disk flushing
      newEnergyUsage = recovery(accountCapsule, ENERGY, energyUsage,
          latestConsumeTime, now);
    }

    if (energy > (energyLimit - newEnergyUsage)
        && dynamicPropertiesStore.getAllowTvmFreeze() == 0
        && !dynamicPropertiesStore.supportUnfreezeDelay()) {
      return false;
    }

    long latestOperationTime = dynamicPropertiesStore.getLatestBlockHeaderTimestamp();
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newEnergyUsage = increase(newEnergyUsage, energy, now, now);
    } else {
      // Participate in calculation and flush disk persistence
      newEnergyUsage = increase(accountCapsule, ENERGY, energyUsage, energy,
          latestConsumeTime, now);
    }

    accountCapsule.setEnergyUsage(newEnergyUsage);
