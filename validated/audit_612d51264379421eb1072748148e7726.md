I found a strong analog. The Near Wallet Contract (`runtime/near-wallet-contract`) uses cross-contract promise callbacks as its equivalent of "try/catch": each callback inspects `env::promise_result(0)` and must decide whether to refund the caller's attached deposit on failure. The final callback (`rlp_execute_callback`) does this correctly, but the two intermediate callbacks do not.Confirmed. The bug is clear: `address_check_callback` and `nep_141_storage_balance_callback` both swallow `PromiseResult::Failed` (and JSON parse failures) of the *intermediate* lookup call by returning an `ExecuteResponse{success:false}` directly — without ever forwarding `caller_deposit` to a refund promise. Only the final `rlp_execute_callback` contains the refund-on-failure logic. This is functionally the same "ineffective try/catch swallows failure silently" bug class as the source report, but here it results in permanently stuck user funds rather than an incorrect authorization decrease.

### Title
Wallet-contract intermediate promise callbacks silently swallow failure and permanently strand the caller's attached deposit - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point attaches an external caller's deposit (`CallerDeposit`) to the transaction and forwards it through a chain of cross-contract-call callbacks that act as this codebase's equivalent of try/catch around external calls. The final callback, `rlp_execute_callback`, correctly refunds `caller_deposit` when the underlying promise fails. However, the two "gatekeeper" callbacks that run *before* it — `address_check_callback` (for eth-implicit-target base-token transfers) and `nep_141_storage_balance_callback` (for emulated ERC-20 transfers) — do not: when their own preceding promise (`address_registrar.lookup(...)` or `token.storage_balance_of(...)`) fails or returns unparsable JSON, they immediately return `PromiseOrValue::Value(ExecuteResponse{success:false, ...})` without creating any refund promise for `caller_deposit`.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-473`) computes `caller_deposit` via `CallerDeposit::new(&context)` [1](#0-0)  whenever the transaction's predecessor (relayer/caller) is not the wallet-contract's own account, tracking the attached NEAR deposit so it can later be refunded if the emulated action fails.

For two transaction kinds, this deposit is threaded through an intermediate promise before the final action executes:

- `EOABaseTokenTransfer { address_check: Some(address), .. }` calls the address registrar first, then `.then(ext.address_check_callback(target, action, caller_deposit))` [2](#0-1) 
- `ERC20Transfer { receiver_id, .. }` calls `storage_balance_of` first, then `.then(ext.nep_141_storage_balance_callback(token_id, receiver_id, action, caller_deposit))` [3](#0-2) 

Both callbacks match on `env::promise_result(0)` — the direct analog of a try/catch around the external call:

`address_check_callback`:
```rust
PromiseResult::Failed => {
    return PromiseOrValue::Value(ExecuteResponse {
        success: false, success_value: None,
        error: Some("Call to Address Registrar contract failed".into()),
    });
}
``` [4](#0-3) 

`nep_141_storage_balance_callback`:
```rust
PromiseResult::Failed => {
    return PromiseOrValue::Value(ExecuteResponse {
        success: false, success_value: None,
        error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
    });
}
``` [5](#0-4) 

In both branches `caller_deposit` (already captured as a function parameter, still `Some(...)` whenever an external caller attached NEAR) is simply dropped — no `promise_batch_create` / `promise_batch_action_transfer` refund is issued.

Compare this to the only callback that *does* handle the equivalent failure correctly, `rlp_execute_callback`:
```rust
PromiseResult::Failed => {
    if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
        let refund_promise = env::promise_batch_create(&account_id);
        env::promise_batch_action_transfer(refund_promise, NearToken::from_yoctonear(yocto_near.into()));
    }
    ExecuteResponse { success: false, success_value: None, error: Some("Failed Near promise".into()) }
}
``` [6](#0-5) 

The existing regression test `test_caller_refunds` only exercises the path where the final action-execution promise fails (`fake.near` receiver) [7](#0-6) ; it never drives a failure of the *address-registrar* or *storage_balance_of* pre-check, so the missing refund in `address_check_callback` / `nep_141_storage_balance_callback` is untested and unnoticed.

### Impact Explanation
Because `attached_deposit` on the `#[payable] rlp_execute` call is already transferred into the wallet contract's own NEAR balance at the moment the transaction is submitted (this is how NEAR payable methods work), any external caller (a relayer or any account submitting an RLP-encoded transaction on behalf of an eth-implicit-account owner) whose deposit is not refunded on this failure path has their NEAR permanently absorbed into the wallet contract's balance with no accounting or code path that ever returns it. `has_in_flight_tx` is reset to `false` [8](#0-7)  so the contract accepts new transactions normally, giving no on-chain indication that a deposit was stranded. This is a concrete, transaction-triggered loss of user funds ("permanently frozen funds") reachable by any account calling `rlp_execute` with attached deposit on a base-token transfer to an eth-implicit target, or an ERC-20 transfer.

### Likelihood Explanation
Both failing preconditions are easily and legitimately triggerable without any malicious validator/node behavior:
- The address registrar cross-contract call can fail for mundane reasons — the registrar account is out of gas, temporarily unavailable, deleted, or returns a payload that fails `serde_json::from_slice` — any of which lands in the swallowed branches.
- `storage_balance_of` on an NEP-141 token contract can likewise fail if the token contract panics, is paused, lacks that method, or returns malformed JSON.

Given relayers routinely batch/automate calls to `rlp_execute` with attached deposits for base-token and ERC-20 transfers, and any single dependency hiccup on the registrar or token contract's side triggers deposit loss, likelihood is medium-to-high in practice, not merely theoretical.

### Recommendation
In both `address_check_callback` and `nep_141_storage_balance_callback`, mirror `rlp_execute_callback`'s handling: on `PromiseResult::Failed` (and on JSON-decoding failure) issue a refund promise for `caller_deposit` before returning the failure `ExecuteResponse`, exactly as already done for the final-action failure path.

### Proof of Concept
1. Deploy the wallet contract to an eth-implicit account `addr.near`.
2. As an external relayer account `relayer.near`, call `rlp_execute` with `target` set to another eth-implicit account and an attached deposit of `N` NEAR, where the RLP-decoded transaction is an `EOABaseTokenTransfer` with `address_check: Some(address)` (i.e. `target` is an eth-implicit account, triggering the registrar-lookup path) — see the promise construction at `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:412-432`.
3. Arrange for the address-registrar cross-contract call to fail (e.g., point `ADDRESS_REGISTRAR_ACCOUNT_ID` at an account that is deleted/out of gas/returns malformed JSON, as is done in the sanity tests' `address_registrar` mock but forced to error).
4. Observe that `address_check_callback` returns `ExecuteResponse{success:false, error:Some("Call to Address Registrar contract failed")}` at `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:141-148`, and that `relayer.near`'s `N` NEAR deposit is never refunded — the wallet contract's own account balance permanently retains it, unlike the `test_caller_refunds` scenario (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs:170-229`) where a final-action failure does correctly refund the caller.
