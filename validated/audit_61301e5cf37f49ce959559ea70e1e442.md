### Title
Missing UnregisterLOOP on job-service-creation failure paths leaks LoopRegistry entries — ([File: core/services/ocr2/delegate.go])

### Summary
`newServicesGenericPlugin` in `core/services/ocr2/delegate.go` calls `d.cfg.RegisterLOOP` (which reserves a port and a `RegisteredLoop` map entry via `plugins.NewCmdFactory`/`LoopRegistry.Register`) but, unlike `validateGenericPluginSpec` in `core/services/ocr2/validate/validate.go`, never sets up a corresponding `UnregisterLOOP` call for its own error paths. Any downstream failure after the successful `RegisterLOOP` call in this function leaks the registry entry and its reserved TCP port permanently.

### Finding Description
`plugins.NewCmdFactory` immediately calls `register(lcfg.ID)` (i.e. `LoopRegistry.Register`) which allocates a free port and inserts a `RegisteredLoop` into `LoopRegistry.registry`, and only *later*, when the returned closure is invoked, does it build the `exec.Cmd`: [1](#0-0) 

`RegistrarConfig.RegisterLOOP` is a thin wrapper over this: [2](#0-1) 

In `core/services/ocr2/validate/validate.go`, `validateGenericPluginSpec` correctly pairs `RegisterLOOP` with an immediate `defer rc.UnregisterLOOP(loopID)`: [3](#0-2) 

However, `Delegate.newServicesGenericPlugin` in `core/services/ocr2/delegate.go` — invoked when the job's services are actually instantiated (`job.Spawner.StartService` → `delegate.ServicesForSpec`) — calls `RegisterLOOP` and then has **no** `defer d.cfg.UnregisterLOOP(...)`: [4](#0-3) 

After this point the function has many `return nil, err` exits (provider-server setup failure, JSON marshal failure, `libocr2.NewOracle` failure, `OnchainSigningStrategy` key-bundle lookup failure for multi-chain signing, etc.): [5](#0-4) [6](#0-5) [7](#0-6) 

Every one of these error returns leaves the just-created `RegisteredLoop` entry (and its allocated port from `freeport.Take`) in the registry forever, since `LoopRegistry.Unregister` is the only code path that calls `freeport.Return` and deletes the map entry: [8](#0-7) 

On the caller side, `job.spawner.StartService` treats a `ServicesForSpec` error as a hard failure and simply returns without any compensating cleanup of partially-registered LOOP resources — it only knows about `ServiceCtx` objects that were successfully appended to `aj.services`, and a `RegisteredLoop` registered inside `newServicesGenericPlugin` is never represented as a `ServiceCtx`, so `stopService`'s reverse-order `Close()` loop can never reach it: [9](#0-8) [10](#0-9) 

An attacker who can submit OCR2 generic-plugin job specs (per the question's stated precondition) can craft a spec whose `Command` points at a real, `exec.LookPath`-resolvable binary that passes `validateGenericPluginSpec` (which does properly unregister after validation) but is engineered to make one of the later steps in `newServicesGenericPlugin` fail deterministically (e.g. a bad `OnchainSigningStrategy` multi-chain key-bundle reference causing `KeyBundleID`/`d.ks.Get` to error, or a provider/oracle construction failure). Each such job-creation attempt permanently consumes one `LoopRegistry` slot and one OS port.

### Impact Explanation
Repeated submission of job specs engineered to fail during `newServicesGenericPlugin` after `RegisterLOOP` succeeds causes an unbounded, monotonically growing leak of `LoopRegistry` entries and reserved OS ports. Given a finite ephemeral port range, this leads to `freeport.Take` eventually failing for all future LOOP registrations (`Register` returns "failed to get free port"), denying subsequent OCR2 generic-plugin, StarkNet/Cosmos/Aptos/TON/Sui/Stellar LOOPP relayer, EVM LOOPP relayer, and standard-capabilities LOOPP creation node-wide — a resource-exhaustion/denial-of-service of the plugin subsystem, matching a "gradual node resource exhaustion / denial of a key node function" bounty category.

### Likelihood Explanation
Feasible and fully repeatable: the attacker only needs the ability to submit job specs (an explicitly allowed precondition per the question and audit rules), a binary resolvable by `exec.LookPath` (satisfying `validateGenericPluginSpec`), and a spec crafted so a later step in `newServicesGenericPlugin` fails deterministically (e.g. malformed `OnchainSigningStrategy` multi-chain config). Each submission leaks exactly one registry entry/port with no rate limiting or automatic reclamation, so the leak scales linearly with attacker-submitted job creation attempts.

### Recommendation
In `core/services/ocr2/delegate.go`'s `newServicesGenericPlugin`, immediately after a successful `d.cfg.RegisterLOOP` call, register a cleanup (e.g. `defer` guarded by a `success` flag cleared only on the final successful return, or explicit `d.cfg.UnregisterLOOP(loopID)` calls on every subsequent error path) so that any failure between `RegisterLOOP` and the point the LOOP-backed service is safely handed off to the job spawner's `ServiceCtx` list results in immediate unregistration. Additionally, `job.spawner.StartService` should ensure that any resources registered by a delegate during a failed `ServicesForSpec` call are rolled back, e.g. by having delegates return partially-created resources for cleanup or by requiring delegates to guarantee this invariant internally, consistent with the pattern already used in `validateGenericPluginSpec`.

### Proof of Concept
Unit test in `core/services/ocr2` (or a new test file) simulating the leak:
1. Construct a `Delegate` with a `RegisterLOOP`/`UnregisterLOOP` pair backed by a real `plugins.LoopRegistry` (e.g. `plugins.NewTestLoopRegistry`).
2. Build a minimal OCR2 job spec with `PluginType: types.LLO` or a generic plugin config whose `OnchainSigningStrategy` is a multi-chain strategy referencing a key bundle ID that does not exist in the keystore (`d.ks.Get(kbID)` will error at line ~1387-1390), or otherwise engineer any of the other post-`RegisterLOOP` error branches to trigger.
3. Call `d.newServicesGenericPlugin(...)` (or `d.ServicesForSpec` via the public API) and assert it returns an error.
4. Assert `reg.List()` (or `LoopRegistry.registry` size) still contains the loop ID / has not returned to baseline size, and that the previously allocated Prometheus port is not returned to `freeport`.
5. Repeat the cycle N times and assert the registry size grows by N, demonstrating unbounded leak, in contrast to `validateGenericPluginSpec`, where an equivalent test would show the registry returning to baseline after each cycle due to its `defer rc.UnregisterLOOP(loopID)`.

```go
// Unregister remove a loop from the registry
// Safe for concurrent use.
func (m *LoopRegistry) Unregister(id string) {
	m.mu.Lock()
	defer m.mu.Unlock()

	loop, exists := m.registry[id]
	if !exists {
		m.lggr.Debugf("Trying to unregistered a loop that is not registered %q", id)
		return
	}

	freeport.Return([]int{loop.EnvCfg.PrometheusPort})
	delete(m.registry, id)
	m.lggr.Debugf("Unregistered loopp %q", id)
}
```

```go
// stopService removes the job from memory and stop the services.
// It will always delete the job from memory even if closing the services fail.
func (js *spawner) stopService(jobID int32) {
	lggr := js.lggr.With("jobID", jobID)
	js.activeJobsMu.Lock()
	aj := js.activeJobs[jobID]
	delete(js.activeJobs, jobID)
	js.activeJobsMu.Unlock()

	for i := len(aj.services) - 1; i >= 0; i-- {
		service := aj.services[i]
		sLggr := lggr.With("subservice", i, "serviceType", reflect.TypeOf(service))
		if c, ok := service.(services.HealthReporter); ok {
			if err := js.checker.Unregister(c.Name()); err != nil {
				sLggr.Warnw("Failed to unregister service from health checker", "err", err)
			}
		}
		if err := service.Close(); err != nil {
			sLggr.Criticalw("Error stopping job service", "err", err)
			js.SvcErrBuffer.Append(pkgerrors.Wrap(err, "error stopping job service"))
		}
	}
}
```
