### Title
Panicking (non-graceful) accounting underflow in `OutgoingMetadatas`/`ReceiptGroupsQueue` can halt chunk application if push/pop receipt size or gas values ever desync - (File: core/store/src/trie/outgoing_metadata.rs)

### Summary
The reported `FeeDistributor` bug is a class of vulnerability where an "accounted" running total is only ever incremented and is decremented later using a value that is assumed — but not guaranteed — to match what was originally added; any desync causes an underflow that aborts a shared code path used by multiple unrelated features. The closest reachable analog in nearcore is `ReceiptGroupsQueue`/`OutgoingMetadatas`, the per-shard outgoing-buffer accounting structure that backs the bandwidth-scheduler request generation. Unlike the sibling `CongestionInfo` accounting (which uses `checked_sub`/`checked_add` and returns `RuntimeError::UnexpectedIntegerOverflow` on mismatch, core/primitives/src/congestion_info.rs:256-321), `ReceiptGroupsQueue`'s totals are decremented with `.expect()`-based helpers that **panic** the process instead of returning an error.

### Finding Description
`OutgoingMetadatas::update_on_receipt_pushed` (core/store/src/trie/outgoing_metadata.rs:49-64) adds a receipt's `size`/`gas` to a per-receiver-shard `ReceiptGroupsQueue` when a receipt is buffered for cross-shard forwarding (called from `ReceiptSinkV2::buffer_receipt`, runtime/runtime/src/congestion_control.rs:486-495). Later, when the receipt is popped off the buffer to be forwarded, `OutgoingMetadatas::update_on_receipt_popped` (outgoing_metadata.rs:68-80) is called with a size/gas value that is **recomputed at pop time** rather than read back verbatim from what was recorded at push time (see `forward_from_buffer_to_shard`, runtime/runtime/src/congestion_control.rs:338-393, which calls `receipt_congestion_gas(&receipt, &apply_state.config)` and `receipt_size(&receipt)` on the popped receipt using the *current* `apply_state.config`).

The subtraction helpers underlying `update_on_receipt_popped` are:
```
fn subtract_size_checked(total: &mut u64, delta: ByteSize) {
    *total = total.checked_sub(delta.as_u64())
        .expect("subtract_size_checked - Underflow! Negative size!");
}
fn subtract_gas_checked(total: &mut u128, delta: Gas) {
    *total = total.checked_sub(delta.as_gas().into())
        .expect("subtract_gas_checked - Underflow! Negative gas!")
}
```
(outgoing_metadata.rs:401-417), and `total_receipts_num` is decremented with `.checked_sub(1).expect("Underflow! - More receipts were popped than pushed!")` (outgoing_metadata.rs:325-329). All three are `.expect()`-based panics, not `Result`-returning checks like the parallel `CongestionInfo::remove_receipt_bytes`/`remove_buffered_receipt_gas` (congestion_info.rs:256-321), which explicitly document "Congestion accounting cannot underflow" via `checked_add`/`checked_sub` returning `RuntimeError`.

This mirrors the `FeeDistributor` bug exactly: an accounted total (`ReceiptGroupsQueueDataV0.total_size`/`total_gas`/`total_receipts_num`) is credited once at buffering time and is assumed to be debited later with an identical amount, but the debit value is independently recomputed from a mutable input (`apply_state.config`, i.e. `RuntimeConfig`/fee parameters) rather than stored alongside the buffered receipt in the general (non-`StateStoredReceipt`) code path. If the fee/gas parameters used to compute `receipt_congestion_gas`/`receipt_size` for a given receipt ever differ between the time it is buffered and the time it is later popped (e.g., because the runtime config changes between those two points while the receipt is sitting congested in the outgoing buffer — buffered receipts can persist across many chunks/epochs while a shard is congested), the recomputed pop-time value will not equal the push-time value, and the subtraction underflows, hitting the `.expect()` panic.

### Impact Explanation
`update_on_receipt_popped`/the `subtract_*_checked` helpers run inside `Runtime::apply` (chunk application), on the hot path used by `ReceiptSinkV2WithInfo::forward_from_buffer` every chunk that drains a shard's outgoing receipt buffer (runtime/runtime/src/congestion_control.rs:233-287, :338-395). A panic there aborts chunk application for that shard on every node that reaches this code path with the mismatched data, which is a **transaction/receipt-triggered halt**: any account can cause receipts to accumulate in a shard's outgoing buffer (by sending transactions whose receipts route to a congested/slow-draining shard) and once such receipts are eventually forwarded under different fee parameters than when they were buffered, the shard chunk-apply panics for all honest nodes applying that chunk — a consensus-wide, non-recoverable failure mode rather than a rejected single transaction.

### Likelihood Explanation
This is presented as an architectural class-match to the external report rather than a proven, currently-triggerable exploit: I was not able to fully confirm within the available context whether `use_state_stored_receipt` (which stores precomputed `StateStoredReceiptMetadata{ congestion_gas, congestion_size }` alongside the buffered receipt so it is read back rather than recomputed, per `protocol-model/spec/cross-shard-congestion.md:78-84`) is unconditionally active on the current stable protocol version, which would close this specific desync path by construction. If `use_state_stored_receipt` is always `true` at the current protocol version, this specific underflow is currently unreachable in production and only a residual defense-in-depth concern (the `.expect()` still means any yet-undiscovered accounting bug anywhere in the push/pop pairing turns into a chain halt instead of a graceful error, unlike `CongestionInfo`'s equivalent counters). I could not verify this within the remaining tool budget.

### Recommendation
1. Change `subtract_size_checked`, `subtract_gas_checked`, and the `total_receipts_num` decrement in `core/store/src/trie/outgoing_metadata.rs` to return `Result<(), StorageError>`/propagate an error (consistent with `CongestionInfo::remove_receipt_bytes`/`remove_buffered_receipt_gas`) instead of panicking via `.expect()`, so any accounting desync degrades to a handled error rather than an unrecoverable chunk-apply panic.
2. Verify and, if necessary, enforce that `receipt_size`/`receipt_congestion_gas` used at pop-time in `forward_from_buffer_to_shard` are always sourced from the same precomputed value stored at push time (i.e., always via `StateStoredReceiptMetadata`, never recomputed from a potentially-changed `RuntimeConfig`), for every protocol version where buffered receipts can survive a config-changing upgrade.
3. Add a regression/fuzz test that buffers a receipt under one `RuntimeConfig` (fee schedule) and pops it after simulating a config change, asserting the totals never underflow and match exactly regardless of intervening config changes.

### Proof of Concept
Conceptual reproduction (could not be fully validated against the live protocol-version gating in the time available):
1. An attacker keeps a target shard heavily congested (sending many cheap transactions whose receipts route there) so that some of the attacker's own receipts remain parked in that shard's outgoing buffer (`ShardsOutgoingReceiptBuffer`) for an extended period spanning a protocol-version upgrade that changes `RuntimeConfig` fee parameters relevant to `compute_receipt_congestion_gas`/`compute_receipt_size` for that receipt's actions.
2. If the buffered receipt representation does not carry forward the exact `size`/`gas` recorded at push time (i.e., `use_state_stored_receipt` is not unconditionally in effect, or some other future code path recomputes rather than reuses the stored metadata), then when `ReceiptSinkV2WithInfo::forward_from_buffer_to_shard` (runtime/runtime/src/congestion_control.rs:338-393) finally pops and forwards the receipt, it recomputes `gas`/`size` under the new config and calls `OutgoingMetadatas::update_on_receipt_popped` with these new values.
3. `subtract_size_checked`/`subtract_gas_checked` (core/store/src/trie/outgoing_metadata.rs:401-417) then underflow against the smaller push-time-recorded total and `.expect()`-panic, aborting `Runtime::apply` for every honest node applying that chunk — a chain halt for the affected shard.
