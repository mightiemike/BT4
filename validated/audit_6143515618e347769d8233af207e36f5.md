### Title
Replay/Restore Verification Skips State-Checkpoint Hash, Allowing a Wrong State Root to Be Accepted as "Verified" - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info`, the function used by transaction-replay and backup-restore verification paths to confirm that a locally re-executed transaction reproduces the historical, trusted `TransactionInfo`, checks status, gas, write-set hash, and event-root hash — but never checks `state_checkpoint_hash` (or `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`). A transaction whose write set, events, gas, and status match but whose resulting Jellyfish Merkle / hot-state root diverges from the authenticated value will pass verification, silently letting a corrupted or buggy execution be accepted as a faithful replay.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0) . It compares `status`, `gas_used`, the write-set hash against `state_change_hash`, and the event root hash against `event_root_hash`, but the function's own comment admits the gap: [2](#0-1) 

This comparator ignores the checkpoint hashes entirely — there is no comparison of the locally-computed state-checkpoint/hot-state/position-state root against `txn_info.state_checkpoint_hash()` (or the V1 equivalents).

This function is the sole correctness gate in at least three real replay/restore code paths:
- Chunk-executor replay verification, used when replaying historical transactions (e.g., during backup restore) to confirm the locally re-executed output matches the trusted `TransactionInfo` supplied by the chunk/backup source: [3](#0-2) 
- `db-tool`'s `replay_on_archive`, whose entire purpose is to detect execution-correctness divergence against archived state before a hard fork can occur: [4](#0-3) 
- The Move CLI's replay/verification of on-chain transactions: [5](#0-4) 

In all these flows, the state root actually written to durable storage after a chunk/backup replay is the **locally recomputed** one (produced by `DoStateCheckpoint`/`DoLedgerUpdate` from the replayed execution), not an externally supplied authoritative root — the externally supplied `TransactionInfo` is only used as an oracle to *validate* that local execution is correct. Because the state-checkpoint hash is excluded from that validation, any divergence in JMT/hot-state root computation (from a VM bug, an execution-path bug, a corrupted intermediate state, or a mismatched feature-flag configuration such as `hot_state_root_in_txn_info`/`compute_trading_native_state_roots`) will not be caught. The replay/restore pipeline will report success and commit a Merkle root that differs from the one the rest of the network — and any future proof verification, API state responses, or accumulator computation building on that restored DB — considers authoritative.

This breaks the "Storage schemas, replay paths, and restore helpers must not reinterpret committed data into a different ledger state" and "state-commitment... integrity" invariants: a corrupted state-commitment root can be committed and treated as validated, with no independent gate catching it.

### Impact Explanation
A wrong `state_checkpoint_hash` accepted through replay/restore verification directly corrupts durable ledger state: the restored/replayed node's JMT and hot-state roots diverge from the correct value while its own tooling reports the replay as verified. Since `replay_on_archive` and chunk-replay verification are the primary mechanisms operators and Aptos Labs use to catch execution-determinism regressions *before* they can cause a chain split/hard fork, this gap defeats that safety net: a state-root-affecting bug could ship silently, be "verified" as correct by this exact tooling, and only manifest as consensus divergence once broadly deployed. It also directly corrupts a restored full node's local database (wrong Merkle roots persisted), which would then serve incorrect proofs/state via the authenticated API and reject/accept future state proofs against the wrong root.

### Likelihood Explanation
No malicious actor is required — this is a latent gap in a correctness-checking function reachable any time replay/backup-restore verification runs (routine operator/CI workflows), and any real execution bug that affects only the Merkle-root computation path (not write-set/events/gas/status) will be missed automatically. The comment in the code itself confirms the aptos-core team is aware the gap exists but has left it unaddressed for the trading-native checkpoint hashes and, by the same logic, `state_checkpoint_hash` generally.

### Recommendation
Extend `ensure_match_transaction_info` to compare `self`'s locally computed state-checkpoint hash (and hot-state/position-state checkpoint hashes when the corresponding feature flags are enabled) against `txn_info.state_checkpoint_hash()` (and V1 equivalents), returning an error on mismatch just as is done for `state_change_hash` and `event_root_hash`. This requires threading the locally computed checkpoint hash(es) into `TransactionOutput` (or passing them alongside, as `expected_write_set`/`expected_events` already are) at each call site (`chunk_executor::verify_execution`, `replay_on_archive::execute_and_verify`, `aptos-move/cli`).

### Proof of Concept
1. Construct (or trigger via a genuine execution-path bug) a transaction whose write set, events, gas, and status are byte-identical to the historical record, but whose resulting state tree differs (e.g., a bug in hot-state root computation, or in an optional trading-native root computation gated by a feature flag).
2. Feed this transaction/output pair through `replay_on_archive`'s `execute_and_verify` ( [6](#0-5) ) or `chunk_executor::verify_execution` ( [7](#0-6) ).
3. Observe `ensure_match_transaction_info` returns `Ok(())` because it never inspects `state_checkpoint_hash`, even though the locally computed Merkle/hot-state root differs from the trusted `TransactionInfo`'s checkpoint hash — the corrupted state root is committed and the replay is reported as verified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
