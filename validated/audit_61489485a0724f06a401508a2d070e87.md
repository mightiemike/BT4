### Title
Unbounded-allocation Borsh decode of attacker-controlled `SignedTransaction` bytes on the JSON-RPC transaction-submission path - ([File: chain/jsonrpc/src/api/transactions.rs])

### Summary
`decode_signed_transaction` in `chain/jsonrpc/src/api/transactions.rs` base64-decodes the caller-supplied `signed_tx_base64` and immediately calls `SignedTransaction::try_from_slice(&bytes)` with no upper bound on `bytes.len()` and no pre-check of the Borsh length-prefixed fields inside it before allocation. [1](#0-0) 

This is the exact bug class in the external report: a size/length value taken from untrusted input is used to drive a memory allocation before that value is checked against any sane maximum, allowing a caller to force a large allocation attempt (`CWE-770`, uncontrolled resource consumption) purely from the length-prefix bytes, independent of how much actual data was supplied.

### Finding Description
Every `Vec<T>`-shaped field on `Transaction`/`SignedTransaction` (e.g. `actions: Vec<Action>`, nested `DelegateAction.actions`, method-name/argument byte vectors, etc.) is Borsh-decoded by reading a `u32` length prefix and then materializing a buffer/vector sized by that prefix. The codebase is well aware that this is dangerous for peer-supplied data: the P2P network layer explicitly added a guard specifically to stop this attack:

```
/// Upper bound on the Borsh-encoded size of a peer-supplied transaction body,
/// enforced before the body is deserialized to mitigate maliciously inflated
/// transactions exhausting node memory at decode time.
const MAX_TRANSACTION_SIZE_BYTES: usize = 16 * MIB as usize;
``` [2](#0-1) 

and a generic helper used across the P2P decode paths:

```rust
/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(...);
    }
    T::try_from_slice(bytes)
}
``` [3](#0-2) 

The JSON-RPC transaction-submission path (`broadcast_tx_async`, `broadcast_tx_commit`, and the `tx` status lookup, all reachable by any unauthenticated RPC caller) does not use this helper or any equivalent gate:

```rust
fn decode_signed_transaction(value: String) -> Result<SignedTransaction, RpcParseError> {
    let bytes = near_primitives::serialize::from_base64(&value)
        .map_err(|err| RpcParseError(format!("Failed to decode transaction: {}", err)))?;
    SignedTransaction::try_from_slice(&bytes)
        .map_err(|err| RpcParseError(format!("Failed to decode transaction: {}", err)))
}
``` [1](#0-0) 

The same unguarded pattern exists in the `serde::Deserialize` impl of `SignedTransaction` itself, used by `RpcSendTransactionRequest`/`TransactionInfo::Transaction` for the `signed_tx_base64` field:

```rust
impl<'de> serde::Deserialize<'de> for SignedTransaction {
    fn deserialize<D>(deserializer: D) -> Result<Self, D::Error> {
        let signed_tx_base64 = <String as serde::Deserialize>::deserialize(deserializer)?;
        let signed_tx_borsh = from_base64(&signed_tx_base64)...?;
        borsh::from_slice::<Self>(&signed_tx_borsh)...
    }
}
``` [4](#0-3) 

Any real size validation (`max_transaction_size`, `validate_transaction`) only happens later in `runtime/runtime/src/verifier.rs`, *after* the Borsh decode has already run and any oversized nested `Vec` allocation attempt has already occurred: [5](#0-4) 

Because the JSON-RPC endpoint accepts an arbitrary-length base64 string in the request body with (per this investigation) no found application-level cap on request/payload size in the `near-jsonrpc` crate (searches for `max_payload_size`/`content_length_limit`/`PayloadConfig` returned no hits), an attacker can:
1. Send a `signed_tx_base64` string that decodes to a small number of Borsh-encoded bytes.
2. Craft one of the length-prefix fields inside the encoded `Transaction`/`Action` structure (e.g., an `actions: Vec<Action>` count, a `DelegateAction`'s inner action vector, or a byte-vector length like `method_name`/`args`) to an attacker-chosen large `u32` value.
3. Trigger a `Vec`/buffer allocation sized to that value before the actual data backing it is checked against the buffer bounds, and well before `max_transaction_size`/`max_actions_per_receipt` are ever consulted.

### Impact Explanation
This maps to "transaction-triggered halt" / uncontrolled resource consumption from a single, unauthenticated RPC call. A validator or RPC node's `broadcast_tx_async`/`broadcast_tx_commit`/`tx` JSON-RPC handlers can be driven to attempt large memory allocations purely from the wire-format length metadata of a submitted (not necessarily validly-signed, since decode happens before signature/size verification) transaction blob. Repeated or parallel submissions of such payloads can exhaust node memory, causing the RPC/validator process to OOM-crash or become unresponsive — a resource-exhaustion DoS reachable by any RPC caller, matching the ImageMagick "policy bypass triggers OOM" bug class (missing max-allocation check before an allocation driven by attacker-controlled size).

### Likelihood Explanation
High likelihood of reachability: `broadcast_tx_async`/`broadcast_tx_commit`/`tx` are public, unauthenticated JSON-RPC methods exposed by every RPC/validator node by default. No signature check, nonce check, or `max_transaction_size` check occurs before the Borsh decode. The fact that the network (P2P) layer of the same codebase explicitly patched this exact class of bug for peer-supplied transactions (`MAX_TRANSACTION_SIZE_BYTES`, `try_from_slice_with_limit`) but the JSON-RPC ingress path was not confirmed to have the same protection is strong internal evidence that this specific decode path is the gap.

### Recommendation
Apply the same pre-decode size gate used in the network layer to the JSON-RPC transaction ingestion paths: enforce an upper bound (e.g., `MAX_TRANSACTION_SIZE_BYTES`, consistent with `max_transaction_size`) on the base64-decoded byte length in `decode_signed_transaction` (`chain/jsonrpc/src/api/transactions.rs`) and in `SignedTransaction`'s `serde::Deserialize` impl (`core/primitives/src/transaction.rs`) *before* calling `try_from_slice`/`borsh::from_slice`, mirroring `try_from_slice_with_limit` from `chain/network/src/network_protocol/proto_conv/util.rs`. Additionally confirm the JSON-RPC HTTP server enforces a reasonable maximum request-body size independent of this fix.

### Proof of Concept
Not independently executed (no runtime access in this investigation); the concrete PoC construction would be:
1. Build a minimal Borsh byte sequence representing a `SignedTransaction { transaction: Transaction { ..., actions: Vec<Action> }, signature, ... }` where the 4-byte length prefix for `actions` (or a nested `DelegateAction`'s action vector, or a `FunctionCallAction.args`/`method_name` byte vector) is set to a very large `u32` (e.g., `0xFFFFFFFE`) while the remainder of the buffer is truncated/short.
2. Base64-encode this short byte sequence and submit it via `broadcast_tx_async`("<base64>") or `broadcast_tx_commit`("<base64>") to a node's JSON-RPC endpoint.
3. Observe memory allocation attempt/behavior in `SignedTransaction::try_from_slice` inside `decode_signed_transaction`, before any `max_transaction_size`/`validate_transaction` check runs.

This last point (exact allocation-before-bounds-check behavior of the specific Borsh version pinned in this repo, and confirmation of no HTTP body-size cap on the JSON-RPC server) was not fully verified within the available search budget — the Borsh version used and any framework-level (actix/axum) request-size limits could not be conclusively confirmed here and are flagged as open verification items for a full session.

/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time. Use this for any peer-supplied borsh blob whose
/// decoded form can be much larger than its wire size; `limit` must sit above
/// the largest legitimate encoding of `T` and well below the peer-frame cap.
/// Returns `io::Error` so it composes with the borsh-based proto decode sites.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!("encoded size {} exceeds the limit of {limit} bytes", bytes.len()),
        ));
    }
    T::try_from_slice(bytes)
}
