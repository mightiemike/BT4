### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` lists in the legacy (non-optimized) delegation index path - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java)

### Summary
When the `AllowDelegateOptimization` chain parameter is not yet enabled (its legacy default), `FreezeBalanceActuator` and `UnfreezeBalanceActuator` maintain per-account address arrays (`toAccounts`/`fromAccounts`) inside a single `DelegatedResourceAccountIndexCapsule` protobuf value. Every new distinct delegatee/delegator address is appended to this array with no upper bound, and the whole array is read, rebuilt, and rewritten on every subsequent freeze/unfreeze/delegate operation — the same anti-pattern flagged in the external report (`allFNUHolders`-style growing array with `addAddress`/`removeAddress` loops).

### Finding Description
`FreezeBalanceActuator.delegateResource()` fetches the owner's and receiver's `DelegatedResourceAccountIndexCapsule`, checks `List.contains()` on the full list, and appends the new address with `addToAccount`/`addFromAccount` when the legacy path is active: [1](#0-0) 

This is gated by `!dynamicPropertiesStore.supportAllowDelegateOptimization()`, meaning it is the active code path whenever the `AllowDelegateOptimization` proposal has not been passed by the committee (i.e., a legacy/default state on many java-tron based chains): [2](#0-1) 

`DelegatedResourceAccountIndexCapsule.addToAccount`/`addFromAccount` simply append to the protobuf repeated field with no size cap: [3](#0-2) 

On unfreeze, the corresponding entry is removed by copying the *entire* list into an `ArrayList`, calling `List.remove`, and rebuilding the whole protobuf object — an O(n) operation on the full historical list of delegatees for that account, mirroring the report's `removeAddress` loop over an ever-growing array: [4](#0-3) 

Critically, `FreezeBalanceActuator.calcFee()` returns a fixed `0`, so delegating resources to a large number of distinct receiver addresses costs no additional actuator-level fee proportional to the resulting index-list size: [5](#0-4) 

Any account can repeatedly freeze a minimal amount of TRX and delegate bandwidth/energy to a large number of unique, attacker-controlled receiver addresses. Each delegation is a cheap, unprivileged transaction, yet it permanently grows the `toAccounts` array stored under the delegator's key (and the `fromAccounts` array under each receiver's key). Every future freeze/unfreeze/delegate/undelegate operation touching that account must deserialize, scan (`contains`), and re-serialize the whole growing list, and node operators must persist and read this growing blob indefinitely — with no compaction or pruning mechanism visible in `DelegatedResourceAccountIndexStore`/`DelegatedResourceAccountIndexCapsule`.

### Impact Explanation
This is analogous to the reported "unbounded loops" bug class: unpriced, attacker-controlled growth of a per-account array that is fully read and rewritten (an implicit "loop" over the whole list on `contains`/`remove`/serialization) on every subsequent state-changing operation involving that address. The consequences are:
- Increasing CPU/storage/serialization cost for validators processing any subsequent `FreezeBalanceContract`/`UnfreezeBalanceContract` touching the polluted account, since `get()`/`put()` on `DelegatedResourceAccountIndexStore` moves the full growing blob.
- Degraded performance for legitimate users who freeze/delegate to or receive delegation from a "polluted" account, since their own index updates require reading/rewriting a large list.
- No fee scales with the size of this growth (`calcFee()==0`), so the attack is essentially free besides minimal frozen TRX (which can be re-frozen/unfrozen and reused across many receivers), making this an underpriced-public-work / storage-growth DoS vector against nodes running with the legacy (non-optimized) delegation index model.

### Likelihood Explanation
The vulnerable path is only active while `AllowDelegateOptimization` has not been enabled via governance proposal — this is a runtime/configuration-dependent condition, not a universal mainnet condition today (Tron mainnet may already have this proposal enabled). Since I could not verify the current on-chain/default value of this parameter for the specific deployment(s) this repo targets (I did not find the parameter's default initialization value in the accessible portion of `DynamicPropertiesStore.java`), likelihood is **uncertain and environment-dependent**: on any java-tron based chain (private chain, testnet, or a mainnet fork) that has not executed the `AllowDelegateOptimization` proposal, this is fully reachable by any unprivileged account issuing ordinary `FreezeBalanceContract` transactions with a receiver address.

### Recommendation
- Cap the number of distinct delegatee/delegator entries tracked per account in the legacy index path, or migrate all deployments to the optimized per-pair-key model (`delegate`/`unDelegate` with prefixed keys) and disable/remove the legacy list-based path entirely.
- Alternatively, charge a fee proportional to the current size of the `toAccounts`/`fromAccounts` list on each append, to disincentivize unbounded growth while the legacy path remains active.
- Ensure the `convert()` migration path (which itself loops over `toList`/`fromList`) is bounded or invoked incrementally rather than reading an unbounded list at once when the optimization proposal activates.

### Proof of Concept
Conceptual sequence (legacy path, `AllowDelegateOptimization == 0`):
1. Attacker account `A` freezes a small amount of TRX with `FreezeBalanceContract.receiver_address = R1`, `resource = BANDWIDTH`. This appends `R1` to `A`'s `toAccounts` list via `FreezeBalanceActuator.delegateResource` and pays `calcFee() == 0`.
2. Attacker unfreezes (or lets it remain) and repeats step 1 with `R2, R3, ..., Rn` for a large `n`, each a freshly generated address.
3. `A`'s `DelegatedResourceAccountIndexCapsule.toAccounts` grows to size `n` with no bound, stored under `A`'s key in `DelegatedResourceAccountIndexStore`.
4. Any subsequent `FreezeBalanceContract`/`UnfreezeBalanceContract` involving `A` (by `A` or any of `R1..Rn`) must fetch, `contains()`-scan, and rewrite this size-`n` list (see `FreezeBalanceActuator.java:328-332` and `UnfreezeBalanceActuator.java:162-182`), imposing growing CPU/storage cost on every node validating these transactions, disproportionate to the fixed transaction fee paid.

Note: I was unable to confirm within the indexed portion of the repo whether `AllowDelegateOptimization` is enabled by default for the target deployment(s), which is the key precondition for this path being reachable; this should be verified against the specific network/genesis configuration in use.

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

        .clearToAccounts()

        .build();
