Confirmed: the malleability gap traces directly into `PrecompiledContracts.ValidateMultiSign`, where per-signer weight is accumulated using a dedup check that can be defeated by ECDSA signature malleability.

### Title
ECDSA signature malleability in `ValidateMultiSign` allows weight double-counting to bypass multisig threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
Java-tron's `ECDSASignature.validateComponents` (used by the `ECRecover`, `BatchValidateSign`, and `ValidateMultiSign` TVM precompiles) never enforces the canonical low-`s` rule, so for any valid signature `(r, s, v)` the mutated pair `(r, N-s, v')` also recovers to the same signer address — the same malleability class the external report flags for compact ECDSA signatures. The `ValidateMultiSign` precompile (address `0x…0a`, reachable from any Solidity/TVM contract) accumulates signer `weight` while deduplicating "already-seen" signers by comparing the *exact signature bytes* rather than only the recovered address. A malleable variant of an already-counted signature is treated as a "new" entry and its weight is added again, letting an attacker inflate `totalWeight` past a multisig `permission.getThreshold()` using fewer distinct real signers than the permission requires.

### Finding Description
`ECDSASignature.validateComponents` only checks `1 <= r,s < SECP256K1N` and `v ∈ {27,28}` — it never enforces `s <= HALF_CURVE_ORDER`, even though `HALF_CURVE_ORDER` and `toCanonicalised()` exist in the same class and are used only on the *signing* path (`doSign`), never on the *verification* path. [1](#0-0) [2](#0-1) 

Because of this, given any valid `(r,s,v)` signature for a message hash, `(r, CURVE.getN().subtract(s), flipped_v)` is also accepted as valid by `recoverAddrBySign`/`SignUtils.signatureToAddress`, recovering to the exact same address — this is the generic ECDSA "compact signature" malleability the report describes. [3](#0-2) 

The `ValidateMultiSign` precompile uses this address-recovery routine while iterating over caller-supplied signatures and summing weight:
```java
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  if (weight == 0) {
    return Pair.of(true, DATA_FALSE);
  }
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
``` [4](#0-3) 

The inner de-duplication check compares `merge(recoveredAddr, sign)` (address concatenated with the raw signature bytes), not the address alone. When the same signer's address is already present but the caller supplies a *malleable variant* of that signer's signature (`r, N-s, v'`), the merged byte string differs from the previously stored one, so `matrixContains(executedSignList, sign)` is `false`. Execution falls through the `continue`, and `totalWeight += weight` runs again for the same signer — effectively double-counting that signer's weight using a signature the attacker can derive purely by arithmetic (`N - s`), with no need for the private key.

### Impact Explanation
`ValidateMultiSign` implements TRON's on-chain multisig weight/threshold check exposed to arbitrary TVM contracts (address `0x…0a`), analogous to `TransactionCapsule.checkWeight` used for account permissions. A contract (e.g. a custodial wallet, DAO treasury, or any DApp gating fund transfers on `permission.getThreshold()`) that calls this precompile to authorize an action can be tricked into approving an action with less real signer weight than the permission's threshold requires: an attacker who already possesses (or has observed) just one valid signature from each of `k` distinct co-signers, but not enough weight to hit the threshold, can craft one or more malleable variants per signature to inflate `totalWeight` and cross the threshold — a direct accounting/authorization-bypass impact (funds/action approved without the required number of independent signers).

### Likelihood Explanation
The precompile is a public TVM primitive reachable by any deployed smart contract without special privilege; the malleable variant requires only modular subtraction (`N - s`) and flipping `v`, no private key or special access. The barrier is only that the attacker must already hold at least one valid signature per signer they want to "duplicate" (e.g. via a leaked/partial approval, a previous on-chain use, or a cooperating-but-insufficient signer), which is a realistic scenario for any k-of-n multisig where fewer than the full `n` signers are colluding or where a single signature is exposed (e.g., posted to reach quorum, then reused with a malleable twin to inflate weight).

### Recommendation
Enforce canonical low-`s` (`s <= HALF_CURVE_ORDER`) in `ECDSASignature.validateComponents` (and the SM2 equivalent) so malleable variants are rejected outright, and/or change `ValidateMultiSign`'s de-duplication key in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java` (lines ~1085-1106) to dedupe strictly by `recoveredAddr`, counting each signer's weight at most once regardless of how many distinct signature encodings recover to that address.

### Proof of Concept
1. Signer `A` produces one valid canonical signature `(r, s, v)` over `hash = sha256(address‖permissionId‖data)` that recovers to `A`'s address via `recoverAddrBySign`. [5](#0-4) 
2. Attacker computes a second signature `(r, N-s, v')` (`N = CURVE.getN()`, `v'` = the other recovery id), which `SignUtils.fromComponents`/`validateComponents` accepts because no canonical-`s` check exists. [1](#0-0) 
3. Attacker calls `ValidateMultiSign` with the signature array `[sig1, sig2]` where both recover to `A`. On the first iteration `executedSignList` is empty, so `A`'s weight is added; on the second iteration `matrixContains(executedSignList, recoveredAddr)` is true (address `A` present) but `matrixContains(executedSignList, sign)` is false (different raw bytes), so the `continue` is skipped and `A`'s weight is added a second time. [4](#0-3) 
4. `totalWeight` now reflects `2 × weight(A)` from a single real signer, potentially reaching `permission.getThreshold()` and returning `dataOne()` (approved) even though only one distinct signer actually authorized the action.
