## Title
`replay_on_archive` verification silently ignores state-checkpoint root mismatches - (File: `types/src/transaction/mod.rs`)

### Summary
The external report's root cause is a check that exists in name but does not enforce the invariant it claims to protect (`_protected()` checked a lock that was never set). The Aptos analog is `TransactionOutput::ensure_match_transaction_info` in [1](#0-0) , which is the sole state-integrity check used by the archive replay-verification tool, yet it deliberately skips comparing the state-checkpoint root hashes that are the actual commitment to post-execution ledger state.

### Finding Description
`ensure_match_transaction_info` validates that a locally re-executed `TransactionOutput` matches a trusted, proof-anchored `TransactionInfo`. It checks status, gas used, write-set hash, and event root hash: [2](#0-1) 

But it explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that commit to the Sparse Merkle Tree root of world state after the transaction. This is called out directly in the code: [3](#0-2) 

This function is the exact and only correctness gate used by `storage/db-tool`'s `replay_on_archive` verifier, which is a tool run to validate that locally-executed VM output matches the archived, ledger-info-proven history: [4](#0-3) 

The `expected_txn_infos[idx]` passed in comes from the archived, proof-verified `TransactionInfo` (anchored via the transaction accumulator to a signed `LedgerInfo`), so it authentically carries the correct `state_checkpoint_hash` for that version. Because `ensure_match_transaction_info` never compares it against the locally recomputed state root, a VM or state-checkpoint computation bug that produces a wrong post-state (but coincidentally correct write set, events, gas, and status) will pass replay verification undetected.

### Impact Explanation
This breaks the "committed state that differs from correct VM result... accepted as valid" invariant described in the State-Integrity Gate. `replay_on_archive`/`replay-verify` is the primary tool used (including in CI, per `testsuite/replay-verify/main.py`) to catch state-divergence bugs across historical chain data before/after protocol or VM changes — exactly the hard-fork-relevant class of bug this tool exists to catch. A state-root-corrupting bug (e.g., in state checkpoint hashing, hot-state/position-state root computation, or SMT update logic) would silently pass this verification step even though the produced state root diverges from the authenticated on-chain root, defeating the tool's core purpose and allowing a wrong ledger-state divergence to go undetected until it manifests as a live consensus fork.

### Likelihood Explanation
The gap is deterministic and always present for every replayed transaction — it's not probabilistic. Any bug that affects state root computation while leaving the write set/events/gas/status accidentally correct (a plausible failure mode for TrustedState/hot-state/JMT-root-specific regressions) is guaranteed to bypass detection. The comment in the source confirms this is a known, currently-unaddressed gap (guarded behind an unimplemented `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature check that is never invoked from this comparator).

### Recommendation
In `ensure_match_transaction_info`, add explicit comparison of the locally computed state checkpoint hash(es) (state, hot-state, position-state) against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()` whenever the corresponding state is available to the caller (e.g., `replay_on_archive` has access to the post-execution state view and can independently compute state roots). Until this is implemented, `replay_on_archive` output should not be treated as validating state-root correctness, and this limitation should be surfaced prominently rather than left to an internal TODO.

### Proof of Concept
1. Introduce (hypothetically, e.g., via a bug in JMT/hot-state root computation) a change that computes an incorrect `state_checkpoint_hash` while leaving `write_set`, `events`, `gas_used`, and `status` unchanged for some transaction.
2. Run `db-tool replay-on-archive` against archived history containing that transaction.
3. `execute_and_verify` calls `ensure_match_transaction_info`, which only checks status/gas/write-set-hash/event-root-hash [2](#0-1)  — the call returns `Ok(())` despite the state root being wrong, and the tool reports the transaction as successfully replay-verified.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
