### Title
Missing G2 Subgroup Check in `decode_g2` Allows Non-Prime-Order Points in `alt_bn128_pairing_check` — (`runtime/near-vm-runner/src/logic/alt_bn128.rs`)

---

### Summary

`decode_g2` validates G2 inputs only for curve membership via `bn::AffineG2::new`, but performs no prime-order subgroup (r-torsion) check. A point on the twist curve E'(Fq2) but outside G2 passes decoding and is fed directly to `bn::pairing_batch`. The Ate pairing is only bilinear and correct on G1 × G2; for Q ∉ G2 the Miller loop + final exponentiation produces an element of GT that is not the mathematically correct pairing value. Any contract using `alt_bn128_pairing_check` for ZK-proof or BLS-signature verification is therefore reachable by an unprivileged user who submits a transaction with crafted G2 bytes.

---

### Finding Description

`decode_g2` at lines 131–142 decodes a G2 point by parsing two Fq2 coordinates and calling `bn::AffineG2::new(x, y)`: [1](#0-0) 

`bn::AffineG2::new` (from the `bn`/`substrate-bn` crate) checks only that the point satisfies the twist curve equation y² = x³ + b/ξ over Fq2. It does **not** multiply the candidate point by the group order r and verify the result is the point at infinity. Consequently, any point on E'(Fq2) whose order is a multiple of the cofactor h₂ (but not purely r) passes this gate.

The decoded point is then passed directly to `bn::pairing_batch`: [2](#0-1) 

The host function `alt_bn128_pairing_check` in `logic.rs` documents that "point is not in the subgroup … returns `AltBn128InvalidInput`", but the implementation never enforces this: [3](#0-2) 

The same gap exists in the wasmtime runner path: [4](#0-3) 

For contrast, the BLS12-381 pairing implementation in the same codebase explicitly calls `blst_p2_affine_in_g2` before proceeding: [5](#0-4) 

No equivalent guard exists for alt_bn128 G2 inputs.

---

### Impact Explanation

The Ate pairing on BN256 is bilinear and non-degenerate only on G1 × G2. For Q ∉ G2, the Miller loop still produces a value in F_{p¹²}*, and the final exponentiation maps it into GT, but the result is not the correct pairing value. This means:

- **False positive**: an attacker can supply a crafted non-G2 point Q such that `bn::pairing_batch` returns `Gt::one()` even though the mathematically correct pairing check (with the G2 projection of Q) would return false. Any contract using this host function to gate state changes (ZK proof verifier, BLS aggregation verifier, etc.) would accept an invalid proof.
- **False negative**: a non-G2 point can cause a legitimately valid pairing to evaluate to non-one, breaking correct contract logic.

Impact class: **cryptographic flaw reachable from user-submitted transactions** and **contract execution flow breakage**.

---

### Likelihood Explanation

- The attack requires no privileges: any account can submit a transaction calling a contract that invokes `alt_bn128_pairing_check`.
- Constructing a point on E'(Fq2) outside G2 is trivial: sample a random point on the twist curve and verify `[r]Q ≠ O` (the cofactor h₂ of BN256's twist is large, so a random curve point is almost certainly outside G2).
- The EIP-197 specification (which NEAR's host function is modelled on) explicitly mandates subgroup checks; go-ethereum enforces them. The gap is a known vulnerability class in pairing-based cryptography.
- The note in the question that this is a "cofactor-2 point" is mathematically imprecise — the twist cofactor h₂ for BN256 is a large integer, not 2 — but this does not affect the validity of the vulnerability; any non-G2 curve point suffices.

---

### Recommendation

Add an explicit r-torsion check inside `decode_g2` after `bn::AffineG2::new` succeeds:

```rust
// After bn::AffineG2::new(x, y) succeeds, verify subgroup membership:
let pt: bn::G2 = bn::G2::from(affine);
if pt * bn::Fr::from_slice(&R_BYTES).unwrap() != bn::G2::zero() {
    return Err(InvalidInput::new("g2 point not in subgroup", raw));
}
```

where `R_BYTES` is the little-endian encoding of the BN256 group order r. Alternatively, use a crate version that exposes a dedicated `is_in_subgroup` check, or adopt cofactor clearing (multiply by h₂) before the pairing, which is equivalent for BN curves.

```rust
// 1. Find a point on E'(Fq2) outside G2:
//    Take generator G2_gen of E'(Fq2); compute Q = G2_gen (order = h2*r, not in G2).
//    Verify: [r]Q != O  =>  Q is not in G2.
// 2. Encode Q as 128 bytes (two Fq2 elements, little-endian u256 each).
// 3. Pair with any G1 point P:
//    input = encode(P) ++ encode(Q)   // 192 bytes
// 4. Call alt_bn128_pairing_check(input).
//    decode_g2 accepts Q (curve check passes).
//    bn::pairing_batch computes e(P, Q) for Q ∉ G2.
//    Result may equal Gt::one() even though the correct pairing e(P, Q_r) != 1,
//    or vice versa — demonstrating the invariant violation.
```

The host function's own documentation at line 1137 of `logic.rs` promises rejection of non-subgroup points; the code at lines 131–142 of `alt_bn128.rs` never enforces it.

```rust
fn decode_g2(raw: &[u8; 2 * POINT_SIZE]) -> Result<bn::G2, InvalidInput> {
    let (x, y) = stdx::split_array(raw);
    let x = decode_fq2(x)?;
    let y = decode_fq2(y)?;
    if x.is_zero() && y.is_zero() {
        Ok(bn::G2::zero())
    } else {
        bn::AffineG2::new(x, y)
            .map_err(|_err| InvalidInput::new("invalid g2", raw))
            .map(bn::G2::from)
    }
}
```
