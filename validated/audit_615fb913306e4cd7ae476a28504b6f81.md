### Title
Unbounded native-stack recursion in transaction-status resolution allows RPC-triggered node crash - (File: `chain/chain/src/chain.rs`)

### Summary
`Chain::get_recursive_transaction_results` walks the receipt DAG produced by an executed transaction using genuine Rust call-stack recursion, with **no depth limit and no cycle/size guard**, unlike the newer, hardened `EXPERIMENTAL_receipt_to_tx` walker which explicitly bounds its walk with `RECEIPT_TO_TX_MAX_DEPTH`. This is reachable by any RPC caller (or any node serving `tx`/`EXPERIMENTAL_tx_status`) querying the final outcome of a transaction that produced a deep receipt/callback chain, and is the closest reachable analog to the reported `dv_compare` DoS: a crafted/attacker-shaped input drives an unbounded internal traversal that can exhaust process resources (stack) and crash the serving node — a transaction-triggered halt of the RPC/view service.

### Finding Description
`get_recursive_transaction_results` recurses once per receipt in the outcome tree, with no maximum depth check and no protection against pathologically long chains: [1](#0-0) 

It is invoked directly from `get_final_transaction_result`, which is the backing implementation for the standard transaction-status JSON-RPC/view-client APIs: [2](#0-1) 

The duplicate implementation used by the test/runtime user harness has the identical unbounded-recursion pattern: [3](#0-2) 

Contrast this with the codebase's own newer receipt-ancestry walker, `handle_receipt_to_tx`, which was deliberately built with an explicit, bounded iterative loop (`for _ in 0..RECEIPT_TO_TX_MAX_DEPTH`) precisely to avoid unbounded walks/stack growth, and which has dedicated regression tests proving the `DepthExceeded` guard fires at exactly 1000 hops: [4](#0-3) [5](#0-4) [6](#0-5) 

That the team specifically engineered a depth cap for one receipt-walking RPC path, but left the older, still-serving `get_final_transaction_result`/`get_recursive_transaction_results` path with recursion of unbounded depth over attacker-influenced receipt-chain length, is the structural weakness: a contract deployer can craft a transaction whose execution creates a long chain of cross-contract callback receipts (each `then`-chained promise creates one more receipt hanging off the last), and then any RPC caller (including the attacker) querying that transaction's final result forces the serving node to recurse to a depth proportional to the receipt chain length, with no ceiling.

### Impact Explanation
Unbounded native recursion driven by attacker-controlled data is a classic stack-exhaustion DoS: once the call stack for the servicing thread is exhausted, the OS delivers SIGSEGV/stack overflow, which in Rust is not a catchable panic and aborts the process. Because view/RPC handlers typically run on shared executors/thread pools, this can take down the RPC service for a node (validator's own view-client thread, or dedicated RPC nodes), a transaction-triggered halt of node functionality, matching the "resource-only/DoS via crafted input" bug class of the referenced CVE, adapted to nearcore's actually-reachable RPC surface.

### Likelihood Explanation
Constructing a very deep single-transaction receipt chain requires each hop to be paid for out of the same transaction's prepaid gas, which does bound the achievable depth to some degree (each function-call action receipt has a nonzero base/creation cost), so a single transaction alone may only achieve on the order of tens to low hundreds of chained receipts before gas is exhausted — likely insufficient by itself to overflow a multi-MB thread stack given typical per-frame stack costs of this function. However, I could not fully verify the exact minimum action-receipt creation cost, the RPC/view-client thread's stack size, or whether promise-yield/resume and cross-block continuation mechanisms (which decouple gas payment from wall-clock/RPC-observed chain length) could be combined to grow the effectively-recursed chain far beyond what a single transaction's gas budget would suggest. Given this uncertainty, likelihood is assessed as **medium**: the missing bound is a clear, concrete code defect (confirmed by the presence of an equivalent, deliberately-added cap elsewhere in the same codebase), but full proof that it is exploitable to an actual stack-overflow crash under mainnet gas/stack parameters was not completed within available context.

### Recommendation
Convert `get_recursive_transaction_results` (and the duplicate in `integration-tests/src/user/runtime_user.rs`) from recursive calls to an explicit iterative worklist/queue traversal, and add a hard cap on the number of outcomes/receipts visited (mirroring `RECEIPT_TO_TX_MAX_DEPTH`/`DepthExceeded` used by `handle_receipt_to_tx`), returning a bounded error instead of recursing indefinitely.

### Proof of Concept
Conceptual, not fully executable given the identified gas-cost uncertainty:
1. Deploy a contract whose method, when called, issues a `Promise::then` callback to itself, and recursively repeats this chaining as many times as the attached prepaid gas allows.
2. Submit one transaction invoking this contract with maximum prepaid gas, producing the longest receipt chain the gas budget allows.
3. Call the `tx`/`EXPERIMENTAL_tx_status` RPC (backed by `Chain::get_final_transaction_result` → `get_recursive_transaction_results`) for that transaction's hash once all receipts have executed.
4. Observe recursive stack growth proportional to the receipt-chain length with no depth cap enforced by the code, in contrast to the capped `EXPERIMENTAL_receipt_to_tx` path in the same codebase.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,
            receipt_ids[i].as_ref(),
            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
                origin: ReceiptOrigin::FromReceipt(ReceiptOriginReceipt {
                    parent_receipt_id: receipt_ids[i + 1],
                    parent_predecessor_id: "system".parse().unwrap(),
                }),
                receiver_account_id: "receiver".parse().unwrap(),
                shard_id: ShardId::new(0),
            }),
        );
    }

    store_update.commit();

    // Query receipt_0 — needs 1001 hops, exceeds MAX_DEPTH=1000.
    let handle = env.node_datas[0].view_client_sender.actor_handle();
    let view_client: &mut near_client::ViewClientActor = env.test_loop.data.get_mut(&handle);
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[0]));

    match result {
        Err(GetReceiptToTxError::DepthExceeded { receipt_id, limit }) => {
            assert_eq!(receipt_id, receipt_ids[0], "error reports originally queried receipt");
            assert_eq!(limit, 1000, "limit == MAX_DEPTH=1000");
        }
        other => panic!("expected DepthExceeded error, got: {other:?}"),
    }

    // Sanity: receipt_2 (999 FromReceipt + 1 terminal = 1000 iter) succeeds
    // — exactly at limit.
    let result = view_client.handle(receipt_to_tx_req(receipt_ids[2]));
    assert!(result.is_ok(), "1000 hops succeed, got: {result:?}");
    let response = result.unwrap();
    assert_eq!(response.transaction_hash, CryptoHash::hash_bytes(b"tx"));
    assert_eq!(response.sender_account_id.as_str(), "sender");
}
