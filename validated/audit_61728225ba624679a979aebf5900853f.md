### Title
Bootstrap Declare Transaction Bypasses Fee, Nonce, and Signature Authorization for Class Declaration - (File: crates/blockifier/src/transaction/account_transaction.rs)

### Summary
The sequencer implements a special "bootstrap declare" code path intended only for initializing a brand-new Starknet system with its first classes before any account exists. This path is triggered purely by client-supplied transaction fields (`sender_address == 'BOOTSTRAP'`, `nonce == 0`, `version == 3`, zero fee/resource bounds) and, when triggered, completely skips `__validate_declare__` signature verification, fee charging, and nonce incrementation — both in the Rust blockifier and in the Starknet OS Cairo re-execution. No genesis-only gate (e.g. "only if no blocks exist yet") is enforced at this layer, so any unprivileged transaction sender can construct such a transaction at any point after genesis to declare classes for free without ever proving control of the `BOOTSTRAP` address (which is not a real deployed account with a public key).

### Finding Description
`DeclareTransaction::is_bootstrap_declare` treats a transaction as a "bootstrap declare" solely based on attacker-controlled transaction fields: [1](#0-0) 

In `AccountTransaction::execute_raw`, when this predicate is true, the code short-circuits before `perform_pre_validation_stage` (nonce/fee checks) and before running `__validate_declare__`, directly executing the declare and returning: [2](#0-1) 

Crucially, this same bypass is hit not only during block execution but also during the **gateway's own stateful validation**, which is the code path that decides whether to admit a transaction into the mempool. `StatefulValidator::perform_validations` always fully *executes* Declare (and DeployAccount) transactions rather than merely calling `__validate__`: [3](#0-2) 

That `execute(tx)` call re-enters `AccountTransaction::execute_raw`, hitting the same `is_bootstrap_declare` bypass — meaning the gateway will admit a bootstrap-declare transaction with no signature check and no fee at all, as confirmed by the fact that `charge_fee` for such a tx is fully attacker-controlled through `enforce_fee`, which is derived only from resource bounds present in the request: [4](#0-3) 

The equivalent Starknet OS re-execution path (used for proof generation / re-execution) mirrors this bypass identically, checking only `sender_address == 'BOOTSTRAP'`, `nonce == 0`, `version == 3`, and `max_possible_fee == 0`, and — critically — never incrementing the nonce for this path: [5](#0-4) 

Because the `BOOTSTRAP` sender's nonce is never incremented (also explicitly called out in an integration test comment as expected behavior), and the only per-class protection is that the *same* class hash cannot be declared twice (`prev_value=0` guard on the class-hash dictionary), an attacker can resubmit fresh bootstrap-declare transactions (each with a new/undeclared `class_hash`) indefinitely, at any block height — not only at genesis: [6](#0-5) 

I searched for a production-level gate restricting this behavior to true genesis (e.g., a check on `allow_bootstrap_txs` or block number) in the gateway/mempool/blockifier crates, and only found the `allow_bootstrap_txs` flag inside test-harness code (`apollo_integration_tests`), not inside the actual gateway/mempool/blockifier validation logic: [7](#0-6) 
The only state-reader-level distinction found is that `GenesisStateReader` is used when no blocks exist yet, but this does not, by itself, prevent an attacker's transaction from being routed through the same `AccountTransaction::execute_raw`/`is_bootstrap_declare` code path once real blocks exist, since the predicate that triggers the bypass is checked on the transaction's own fields, not on chain state.

### Impact Explanation
This mirrors the reported bug class exactly: a specific execution path (bootstrap declare) skips the authorization checks (signature validation via `__validate_declare__`, and fee enforcement) that all normal Declare transactions must pass through, based only on attacker-supplied fields rather than any genuine authorization proof. The practical effect is that any unprivileged transaction sender can:
- Declare arbitrary new Sierra/Cairo classes on the network completely free of charge (bypassing the protocol's fee-based economic authorization for state-changing operations), and
- Repeat this indefinitely (once per distinct, not-yet-declared class hash), since the sender's nonce never advances.

This is a resource-exhaustion / free-computation vector (declaring and compiling classes consumes sequencer/CASM-compilation resources without payment) and an authorization bypass of the fee/signature gate that is otherwise mandatory for all Declare transactions, matching the Medium severity class of the reported analog (authenticated/unprivileged actor performing a privileged, normally-fee-gated state mutation without the required authorization check).

### Likelihood Explanation
The trigger requires only crafting a standard `DeclareTransactionV3` RPC payload with `sender_address` set to the fixed constant `bootstrap_address()` (`0x424f4f545354524150`), `nonce = 0`, zero resource bounds, and a valid Sierra class + matching `compiled_class_hash`. No special network position, staking, or privileged role is needed — this is directly reachable from a single submitted transaction through the public gateway `add_tx` HTTP endpoint, matching the "unprivileged transaction sender" reachability required by the task's scope.

### Recommendation
Restrict the bootstrap-declare bypass so it can only be exercised during genuine genesis bootstrapping (e.g., gate it on the actual absence of any committed blocks/state, verified server-side against chain state rather than trusting the transaction's `sender_address`/`nonce`/`version` fields alone), and/or disable acceptance of such transactions entirely once the chain has left genesis. Apply the corresponding restriction consistently in `AccountTransaction::execute_raw`, `StatefulValidator::perform_validations` (gateway admission path), and the Starknet OS Cairo `execute_declare_transaction` re-execution path, since all three currently rely solely on client-supplied transaction fields to decide whether to skip authorization.

### Proof of Concept
1. Construct a `DeclareTransactionV3` (or `InternalRpcDeclareTransactionV3`) with:
   - `sender_address = DeclareTransaction::bootstrap_address()` (the constant `'BOOTSTRAP'` address)
   - `nonce = Nonce(Felt::ZERO)`
   - `resource_bounds` set so that `max_possible_fee == 0` (e.g. `ValidResourceBounds::create_for_testing_no_fee_enforcement()`), as used in `generate_bootstrap_declare`: [8](#0-7) 
   - `class_hash`/`compiled_class_hash` for an arbitrary attacker-chosen class, with an empty or garbage `signature` (never checked).
2. Submit this transaction via the gateway's `add_tx` HTTP endpoint like any normal user transaction.
3. The gateway's `StatefulValidator::perform_validations` executes the tx via `self.execute(tx)`, which reaches `AccountTransaction::execute_raw`'s `is_bootstrap_declare` branch and succeeds without validating any signature or charging any fee.
4. The transaction is admitted into the mempool, later batched, and executed by the batcher via the same bypass, permanently declaring the attacker's class on-chain at zero cost.
5. Repeat with a new `class_hash` each time (nonce never increments for the `BOOTSTRAP` sender), enabling unlimited free class declarations.

    // Returns whether the declare transaction is for bootstrapping.
    // In this case, no account-related actions should be made besides the declaration.
    pub fn is_bootstrap_declare(&self, charge_fee: bool) -> bool {
        if let crate::transaction::DeclareTransaction::V3(tx) = &self.tx {
            return tx.sender_address == Self::bootstrap_address()
                && tx.nonce == Nonce(Felt::ZERO)
                && !charge_fee;
        }
        false
    }

    /// Returns the address of the bootstrap contract.
    /// Declare transactions can be sent from this contract with no validation, fee or nonce
    /// change. This is used for starting a new Starknet system.
    pub fn bootstrap_address() -> ContractAddress {
        // A felt representation of the string 'BOOTSTRAP'.
        ContractAddress::from(0x424f4f545354524150_u128)
    }

        // Do not run validate or perform any account-related actions for declare transactions that
        // meet the following conditions.
        // This flow is used for the sequencer to bootstrap a new system.
        // Note: The absence of any account-related action leads to some unintuitive but expected
        // behavior:
        // - After the transaction is executed successfully, the batcher does not notify the mempool
        //   about its inclusion in a block. As a result, the transaction remains in the mempool.
        // - When the next block is produced, the mempool will propose the same transaction again.
        // - This time, execution will fail because the contract has already been declared.
        // - The transaction will then be marked as rejected, the mempool will be notified, and the
        //   transaction will be removed from the mempool.
        if let Transaction::Declare(tx) = &self.tx {
            if tx.is_bootstrap_declare(self.execution_flags.charge_fee) {
                let mut context = EntryPointExecutionContext::new_invoke(
                    tx_context.clone(),
                    self.execution_flags.charge_fee,
                    SierraGasRevertTracker::new(GasAmount::default()),
                );
                let mut remaining_gas = 0;
                let res = tx.run_execute(state, &mut context, &mut remaining_gas)?;
                assert!(res.is_none(), "Declare execute should not result in a CallInfo.");

                return Ok(TransactionExecutionInfo::default());
            }
        }

    pub fn perform_validations(&mut self, tx: AccountTransaction) -> StatefulValidatorResult<()> {
        // Deploy account transaction should be fully executed, since the constructor must run
        // before `__validate_deploy__`. The execution already includes all necessary validations,
        // so they are skipped here.
        // Declare transaction should also be fully executed - otherwise, if we only go through
        // the validate phase, we would miss the check that the class was not declared before.
        match tx.tx {
            ApiTransaction::DeployAccount(_) | ApiTransaction::Declare(_) => self.execute(tx),
            ApiTransaction::Invoke(_) => {
                let tx_context = Arc::new(self.tx_executor.block_context.to_tx_context(&tx));
                tx.perform_pre_validation_stage(self.state(), &tx_context)?;
                if !tx.execution_flags.validate {
                    return Ok(());
                }

                // `__validate__` call.
                let (_optional_call_info, actual_cost) = self.validate(&tx, tx_context.clone())?;

                // Post validations.
                PostValidationReport::verify(
                    &tx_context,
                    &actual_cost,
                    tx.execution_flags.charge_fee,
                )?;

                Ok(())
            }
        }
    }
