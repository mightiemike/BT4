### Title
Divergent "available delegatable resource" calculations between the TVM query precompile and the actual delegation enforcement path allow state/logic divergence - ([File: actuator/src/main/java/org/tron/core/vm/utils/FreezeV2Util.java])

### Summary
The Yearn report describes two functions (`_creditAvailable` and `_debtOutstanding`) that are meant to represent the same underlying quantity but use different inputs/formulas, producing divergent answers about how much credit/debt a strategy actually holds. The same bug class exists in java-tron's FreezeV2 resource-delegation subsystem: the value returned by the read-only TVM query `FreezeV2Util.queryDelegatableResource` (exposed to any smart contract via a precompiled contract) is computed with a materially different formula than the value actually enforced by `DelegateResourceActuator.validate()` / `DelegateResourceProcessor.validate()` when a delegation is executed.

### Finding Description
`queryDelegatableResource` computes the "available to delegate" amount as: [1](#0-0) 
using `Repository.getAccountNetUsageBalanceAndRestoreSeconds`, which recovers usage via a local `recover()` calculation without mutating the account, and converts the recovered usage to a TRX-denominated value with `usageToBalance()`: [2](#0-1) [3](#0-2) 

By contrast, the actual enforcement path in `DelegateResourceActuator.validate()` (regular transaction) and `DelegateResourceProcessor.validate()` (TVM-triggered delegate) computes the "available" quantity differently: it first mutates the account's usage via `processor.updateUsageForDelegated(ownerCapsule)` (or `EnergyProcessor.updateUsage`), then reads the raw (now-updated) `getNetUsage()`/`getEnergyUsage()` field and re-derives a TRX-equivalent usage inline using `totalNetWeight`/`totalNetLimit` ratios and `getV2NetUsage`/`getV2EnergyUsage`, rather than the `recover()`/`usageToBalance()` path used by the query function: [4](#0-3) [5](#0-4) 

These two code paths — one advisory/query-facing (reachable by any contract through the TVM precompile), one enforcement-facing (used at actual delegation time) — compute the same conceptual value ("frozen V2 balance minus currently consumed usage, i.e., how much this account can still delegate") using different usage-recovery semantics (mutating vs. non-mutating `recover`), different total-limit fields, and different scaling paths. This is structurally the same root cause as the Yearn bug: two functions meant to agree on a resource/credit availability figure diverge because they read/derive state differently.

### Impact Explanation
Any contract (unprivileged caller) that queries `queryDelegatableResource` on-chain to decide how much resource it can delegate can receive a value that does not match what `DelegateResourceActuator`/`DelegateResourceProcessor` will actually allow at execution time. This can cause:
- Composability breakage/halt: a contract computing a delegate amount based on the query value can have its subsequent `DelegateResourceContract` (or TVM-triggered delegate) reverted because the enforced check disagrees with the queried "available" figure — an invalid-state/divergence outcome for automated on-chain flows built on top of this precompile.
- Under- or over-estimation of delegatable capacity, undermining any accounting logic (e.g., resource-rental marketplaces or automated resource managers) that treats the query result as authoritative.

Unlike the Yearn case, I could not confirm a direct fund-extraction/loss-avoidance exploit path within the scope investigated (i.e., I did not find code that lets an attacker directly siphon TRX from this divergence), so the concrete impact substantiated here is limited to state-divergence/halt for on-chain consumers of the query function, not a proven balance-drain.

### Likelihood Explanation
The `queryDelegatableResource` function is reachable by any smart contract without special privilege via the TVM precompiled contract layer referenced in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`, and the divergence is deterministic whenever an account has non-zero, decaying resource usage (i.e., it has consumed bandwidth/energy recently) — a very common condition. Because the divergence is state/time dependent (based on `recover()` decay vs. mutated usage timing), it will not always manifest identically, but it is easily triggerable by any account with recent resource usage, making it a moderate-likelihood, low-effort-to-trigger condition for contracts that rely on the query result.

### Recommendation
Unify the "available delegatable resource" calculation into a single shared function used both by `FreezeV2Util.queryDelegatableResource` and by `DelegateResourceActuator.validate()` / `DelegateResourceProcessor.validate()`, ensuring both consult the same usage-recovery method (`recover()` vs. `updateUsageForDelegated`) and the same total-limit fields (`getTotalNetLimit()` vs. `getTotalNetCurrentLimit()`), so that a value returned by the read-only query is guaranteed to match what will be enforced when the delegation is actually attempted. Document the guaranteed invariant explicitly (e.g., "queryDelegatableResource() always equals the maximum acceptable `delegateBalance` for a subsequent DelegateResourceContract in the same block").

### Proof of Concept
Not fully constructable from static analysis alone — a concrete PoC would require driving an account into a state where `latestConsumeTimeForEnergy`/`latestConsumeTime` and `windowSize` cause `RepositoryImpl.recover()` (non-mutating) to differ from the mutated usage produced by `BandwidthProcessor.updateUsageForDelegated`/`EnergyProcessor.updateUsage` (e.g., by having usage measured across a period boundary or with pending window-size changes), then comparing the return value of `queryDelegatableResource` against the actual maximum `delegateBalance` accepted by `DelegateResourceActuator.validate()`/`DelegateResourceProcessor.validate()` in the same block. I was not able to execute this scenario in the current investigation and flag this as unverified beyond the static code-path comparison shown above.

  public Pair<Long, Long> getAccountNetUsageBalanceAndRestoreSeconds(AccountCapsule accountCapsule) {
    long now = getHeadSlot();

    long netUsage = accountCapsule.getNetUsage();
    long latestConsumeTime = accountCapsule.getLatestConsumeTime();
    long accountWindowSize = accountCapsule.getWindowSize(Common.ResourceCode.BANDWIDTH);

    if (now >= latestConsumeTime + accountWindowSize) {
      return Pair.of(0L, 0L);
    }

    long restoreSlots = latestConsumeTime + accountWindowSize - now;

    long newNetUsage = recover(netUsage, latestConsumeTime, now, accountWindowSize);

    long totalNetLimit = getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = getTotalNetWeight();

    long balance = usageToBalance(newNetUsage, totalNetWeight, totalNetLimit);

    return Pair.of(balance, restoreSlots * BLOCK_PRODUCED_INTERVAL / 1_000);

  private long usageToBalance(long usage, long totalWeight, long totalLimit) {
    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(usage)
          .multiply(BigInteger.valueOf(totalWeight))
          .multiply(BigInteger.valueOf(TRX_PRECISION))
          .divide(BigInteger.valueOf(totalLimit))
          .longValueExact();
    }
    return (long) ((double) usage * totalWeight / totalLimit * TRX_PRECISION);
  }
