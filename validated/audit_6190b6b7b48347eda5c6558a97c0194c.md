### Title
Unbounded `PendingInbounds` scan on every inbound ballot terminal transition — attacker-inflatable O(n) hot-path scan analogous to the Casper blacklist-vector DoS - (File: x/uexecutor/keeper/ballot_hooks.go)

### Summary
The reported Casper bug is a class of "unbounded collection that keeps growing, then gets linearly scanned on every core operation, degrading core functionality over time." Push Chain's `x/uexecutor` module has a structurally identical pattern: `PendingInbounds` is a `collections.Map[string, types.PendingInboundEntry]` keyed by `utx_key`, but the `AfterBallotTerminal` hook cannot use that key directly (ballot IDs are one-way digests) and instead performs a full `Walk` over the *entire* `PendingInbounds` collection on every single inbound ballot's terminal transition (PASSED/REJECTED/EXPIRED) to find the matching entry.

### Finding Description
`x/uexecutor/keeper/ballot_hooks.go`'s `afterInboundBallotTerminal` is wired as the `x/uvalidator` `BallotHooks.AfterBallotTerminal` callback and fires every time any inbound ballot reaches a terminal state (this happens routinely — essentially once per processed cross-chain inbound event): [1](#0-0) 

The relevant scan:
```go
err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
    for _, v := range e.Variants {
        if v.BallotId == ballotID {
            utxKey, entry, found = key, e, true
            return true, nil
        }
    }
    return false, nil
})
``` [2](#0-1) 

`PendingInbounds` is created and grown by `RecordInboundVote`, invoked from `VoteInbound` on the *first* vote for any inbound observation — before UTX existence, before finalization, before any spam/liquidity/rate control other than the bonded-UV-only gate on submitting `MsgVoteInbound`: [3](#0-2) 

The unbounded-growth trigger is unprivileged and external: anyone can generate arbitrarily many cheap/dust gateway events on any registered source chain (e.g. tiny/zero-value deposits, or transactions crafted to differ just enough to create distinct `Inbound` payload bytes and thus distinct ballot variants). Honest, non-malicious Universal Validators will observe and vote on all of these exactly as designed — no validator misbehavior is required. Each such event creates or extends a `PendingInboundEntry` in `PendingInbounds`, and the entry is only removed once *all* its variants reach a terminal ballot state (`x/uexecutor/README.md:244-260`). By flooding the source chain with events whose payload never reaches quorum before ballot expiry (or by simply creating a very large steady-state backlog), an attacker can grow `PendingInbounds` without bound and without spending anything on Push Chain itself (`MsgVoteInbound` is a gasless message type per `app/txpolicy/gasless.go`).

Once inflated, **every subsequent terminal transition for every other inbound in the system** — triggered by completely unrelated, legitimate users' cross-chain transfers — pays the cost of a full linear `Walk` over the bloated map before it can even locate its own entry. This is the direct functional analog of the Casper report's `is_blacklisted_util`/`blacklist_pubkey` pattern: an ever-growing collection with no secondary/direct index, linearly scanned inside a core transaction-processing hot path (there, `transfer`/`mint`/`burn`; here, inbound ballot finalization which gates minting PRC20s and executing the user's UEA payload).

### Impact Explanation
As `PendingInbounds` grows, the per-inbound cost of `afterInboundBallotTerminal` grows linearly with the total number of unresolved inbound entries system-wide, not with the size of the specific inbound being processed. This degrades — and at sufficient scale can starve — the core universal-execution finalization path (PRC20 minting, UEA payload execution, outbound creation) for all users, not just the attacker, exactly mirroring the "excessive fees for core functionality" impact described in the source report. Because `MsgVoteInbound` is gasless, the attacker incurs essentially zero on-chain cost on Push Chain to inflate the collection (only whatever trivial cost exists on the external source chain to emit a gateway event), while the cost is paid by the validator set's compute time processing every subsequent inbound. This is a scoped, in-repo root cause (missing reverse index / unbounded collection scanned in a hot path) rather than a network-level or purely off-chain issue.

### Likelihood Explanation
Medium-to-high. No privileged role is required — an ordinary user interacting with any registered gateway on any external chain can create `Inbound` events cheaply and repeatedly. The comment in the code itself acknowledges the walk is a stopgap ("the pending set is small and transient, and this hook only fires on terminal transitions") — an assumption that does not hold under adversarial pressure, since nothing bounds how many inbound observations can be outstanding simultaneously, and variant-fragmentation (the same underlying event producing multiple `InboundVariant`s due to encoding differences) can further multiply entries even without new source-chain transactions, though the existing convergence normalization mitigates the classic encoding-variant fragmentation case.

### Recommendation
Mirror the exact remediation used in the referenced Casper fix (replace unbounded linear scan with a direct/dictionary-style index):
- Add a secondary index `BallotIDToUtxKey: collections.Map[string, string]` (or use `collections.IndexedMap`) populated in `RecordInboundVote` whenever a new `InboundVariant` is created, mapping `ballotID -> utxKey`.
- In `afterInboundBallotTerminal`, replace the `PendingInbounds.Walk(...)` full scan with a direct `BallotIDToUtxKey.Get(ctx, ballotID)` lookup, followed by a direct `PendingInbounds.Get(ctx, utxKey)`.
- Remove the index entry when the owning `PendingInboundEntry` is removed (on all-variants-terminal cleanup) to avoid unbounded growth of the new index itself.
- Consider adding an explicit cap or expiry-driven eviction on `PendingInbounds` size independent of ballot expiry, to bound worst-case memory/storage even before the O(1) fix lands.

### Proof of Concept
Conceptual (cannot be executed without a running devnet/testnet in this environment, but derivable directly from the code paths cited above):
1. Register (or use an already-registered) external chain with inbound enabled.
2. Have a set of honest Universal Validators run normally.
3. As an unprivileged actor, submit N distinct low/zero-value transactions to the chain's gateway contract in a way that yields distinct `Inbound.TxHash`/`LogIndex` values (trivial and cheap on most EVM testnets/mainnets), causing N `MsgVoteInbound` submissions from honest UVs and N entries accumulating in `PendingInbounds` (analogous to the Casper PoC's loop pushing 1230 blacklist entries).
4. Measure the wall-clock/compute cost of `afterInboundBallotTerminal` (or equivalently the total inbound-finalization latency) for a legitimate, unrelated inbound both before and after the flood — the existing test suite's `TestQueryAllPendingInbounds`/`pending_inbound_audit_trail_test.go` scaffolding (`RecordInboundVote`, `PendingInbounds.Get`) can be adapted into a benchmark that inserts a large number of unrelated entries and then times `AfterBallotTerminal` for a distinct ballot ID, directly demonstrating the linear-in-N cost predicted above.

func (h BallotHooks) afterInboundBallotTerminal(
	ctx context.Context,
	ballotID string,
	status uvalidatortypes.BallotStatus,
) error {
	// Ballot IDs are one-way canonical digests (not reversible), so locate
	// the owning audit-trail entry by scanning PendingInbounds for the
	// variant carrying this ballot ID. The pending set is small and
	// transient, and this hook only fires on terminal transitions.
	var (
		utxKey string
		entry  types.PendingInboundEntry
		found  bool
	)
	err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
		for _, v := range e.Variants {
			if v.BallotId == ballotID {
				utxKey, entry, found = key, e, true
				return true, nil
			}
		}
		return false, nil
	})
	if err != nil {
		return err
	}
	if !found {
		// Entry was already cleared (e.g. the consensus-success path in
		// VoteInbound already removed it before this hook fires), or the
		// ballot does not belong to a tracked inbound. Nothing to do.
		return nil
	}
```
