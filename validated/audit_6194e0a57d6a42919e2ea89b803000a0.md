### Title
Unenforced `LiquidityCap` on PRC20 inbound minting allows unbounded synthetic-asset issuance beyond configured limits - (File: `x/uexecutor/keeper/handler.go`, `x/uexecutor/keeper/evm.go`, `x/uregistry/types/token_config.go`)

### Summary
`TokenConfig.LiquidityCap` is required and validated as a non-empty numeric string on every registered token, and is documented (`x/uregistry/README.md`) as "the liquidity cap" governing per-token exposure. However, no code path in `x/uexecutor` (the inbound execution flow that mints PRC20 tokens via `depositPRC20` → `CallPRC20Deposit`) ever reads `TokenConfig.LiquidityCap` or compares it against cumulative minted supply. The field is checked for well-formedness at config-write time and then never consulted again — structurally identical to the `QVSimpleStrategy` bug where `maxVoiceCreditsPerAllocator` was checked against `allocator.voiceCredits`, but `voiceCredits` was never incremented, silently nullifying the cap.

### Finding Description
`ValidateBasic` on `TokenConfig` (`x/uregistry/types/token_config.go:56-58`) enforces `liquidity_cap` is non-empty when an admin registers or updates a token via `MsgAddTokenConfig`/`MsgUpdateTokenConfig`. This creates the on-chain and operator expectation that PRC20 issuance for that token is bounded by `LiquidityCap`.

The actual mint path is:
1. `VoteInbound` finalizes an honest-validator-observed inbound (`x/uexecutor/keeper/msg_vote_inbound.go`).
2. `ExecuteInboundFunds` (`x/uexecutor/keeper/execute_inbound_funds.go:24-30`) calls `k.depositPRC20(...)`.
3. `depositPRC20` (`x/uexecutor/keeper/handler.go:12-46`) fetches `TokenConfig` only to resolve `NativeRepresentation.ContractAddress` — it reads `tokenConfig.LiquidityCap` nowhere — then calls `CallPRC20Deposit`.
4. `CallPRC20Deposit` (`x/uexecutor/keeper/evm.go:262-303`) issues a module-sender `DerivedEVMCall` to `depositPRC20Token` for the full inbound `Amount`, with no cap check, no running-total lookup, and no rejection path if a hypothetical total is exceeded.

Because every unprivileged external-chain user can trigger an inbound (subject only to honest-validator quorum on the *observation*, not on the *amount*), a stream of legitimate-looking inbound deposits for the same token can mint PRC20 far beyond any configured `LiquidityCap`, with the chain never noticing the field exists at runtime.

### Impact Explanation
This breaks the "PRC20 asset accounting must not misroute or over-issue value" invariant explicitly called out in the allowed-impact scope (registry and accounting path: "PRC20/native representation ... must not misroute value or attach the wrong asset semantics"). An unenforced liquidity cap means PRC20 supply for a token can grow unbounded relative to the real collateral locked on the source chain's gateway/vault, which is a form of unauthorized/uncapped mint relative to the protocol's own declared backing limit — directly analogous in class to "every allocator has an unlimited number of votes" in the original report (here: "every token has unlimited mintable liquidity, regardless of the configured cap").

### Likelihood Explanation
High likelihood of being reachable: any user who can get a real (or replayed-format, but honestly-observed) inbound deposit through the standard gateway-observation → ballot → finalize path repeatedly exercises this same code, and nothing in the hot path differentiates "first deposit" from "deposit number one million" for the same token. No privileged actor or malicious validator is required — this is purely a missing runtime check against an existing, validated, but functionally decorative config field.

### Recommendation
Track cumulative minted/outstanding PRC20 supply per token (e.g., a new `MintedSupply` collection keyed by `chain:address`, updated atomically alongside `CallPRC20Deposit`), and enforce `mintedSupply + amount <= LiquidityCap` inside `depositPRC20` before issuing the `DerivedEVMCall`. Reject (and route to the existing revert/refund flow) deposits that would exceed the cap, mirroring how `QVSimpleStrategy._allocate` was fixed by actually updating and checking `allocator.voiceCredits` before allowing further allocation.

### Proof of Concept
1. Admin registers a token via `MsgAddTokenConfig` with `LiquidityCap = "1000000"` (validated as non-empty per `token_config.go`).
2. An external user deposits an inbound of amount `1000000` on the source chain; honest Universal Validators observe and vote it through `VoteInbound` → ballot passes → `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints `1000000` PRC20. Cap reached.
3. The same (or a different) user deposits another inbound of amount `1000000` for the *same token*. The flow is identical — `depositPRC20` never reads or checks `LiquidityCap` — and another `1000000` PRC20 is minted, for a cumulative `2000000`, double the configured cap.
4. Repeat indefinitely: PRC20 supply for the token grows without bound, regardless of `LiquidityCap`, because the field is never consulted at runtime — only at config write-time for string non-emptiness.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
