### Title
Missing address validation on `RevertInstructions.FundRecipient` allows attacker-controlled refunds/re-mints to be silently coerced to an unintended (including zero) address - ([File: x/uexecutor/keeper/outbound.go], [File: x/uexecutor/keeper/build_revert_outbound.go], [File: x/uexecutor/types/inbound.go])

### Summary
The external report's bug class is "unvalidated address parameters can be set to `address(0)`, breaking contract functionality / causing fund loss." The native analog in Push Chain is the `RevertInstructions.fund_recipient` field on an `Inbound`/`OutboundTx`: unlike the primary `Recipient` field, it is never format- or zero-checked before being converted with `common.HexToAddress` and used as the destination of a PRC20 re-mint or gas refund.

### Finding Description
`Inbound.ValidateForExecution` strictly validates the primary `Recipient` field for `FUNDS`/`GAS` types with `utils.IsValidAddress(p.Recipient, utils.HEX)` [1](#0-0) , but there is no equivalent `ValidateBasic`/`ValidateForExecution` check anywhere for `RevertInstructions.FundRecipient` — a `grep` for a validator on `RevertInstructions` returns no matches, and the proto message itself carries no invariant beyond being a plain string [2](#0-1) .

`Inbound.Canonicalize()` only *lenient*-canonicalizes `FundRecipient` — malformed values are trimmed and passed through unchanged, never rejected, by design ("lenient... never rejected... execution-level validation rejects malformed inbounds later") [3](#0-2) . But no such "execution-level validation" exists for `FundRecipient` — it is used as-is at every revert/refund call site:

- `buildRevertOutbound` copies `RevertInstructions.FundRecipient` directly into `outbound.Recipient` with only an empty-string check (fallback to `Sender`), no format check [4](#0-3) .
- `handleFailedOutbound` picks the same field and calls `common.HexToAddress(recipient)` directly to re-mint bridged tokens via `CallPRC20Deposit` [5](#0-4) .
- `applyGasRefund` does the same for the gas-refund recipient before calling `CallUniversalCoreRefundUnusedGas` [6](#0-5) .

`common.HexToAddress` in go-ethereum never errors: it hex-decodes the input (ignoring/erroring silently on non-hex content, which `common.FromHex` maps to an empty byte slice) and then left-pads/truncates to 20 bytes with `BytesToAddress`. Any non-empty but malformed string — e.g., truncated hex, a value with non-hex characters, or a base58/Solana-style string appearing on an EVM destination — deterministically resolves to the Ethereum zero address `0x0000...0000` or to a wrong/truncated 20-byte value, rather than failing loudly. Because `FundRecipient` skips both `IsValidAddress`/`CanonicalizeEVMAddress` (strict) and any pre-mint format check, a value that passes the trivial `!= ""` guard can still coerce to the burn address.

### Impact Explanation
Since `RevertInstructions` is attacker-influenced input carried on the `Inbound` record from an unprivileged user's deposit/gateway call, and it survives all the way to the fund-re-mint path (`CallPRC20Deposit`) and gas-refund path (`CallUniversalCoreRefundUnusedGas`) unchecked, a malformed but non-empty `FundRecipient` causes the protocol to mint PRC20 tokens or refund gas to the EVM zero address (or another unintended 20-byte value) instead of reverting the operation or falling back to `Sender`. This is a permanent, unrecoverable loss of the bridged principal or excess-gas refund — the same "unchecked zero address → fund loss" invariant break identified in the external report, just manifesting on the revert/refund path instead of a constructor. It does not let an attacker steal *another* user's funds, but it does allow reachable, unprivileged-triggered permanent loss of user/protocol-controlled value, matching the in-scope impact category.

### Likelihood Explanation
Medium. Triggering requires an inbound whose `RevertInstructions.FundRecipient` is a non-empty but invalid/malformed address, combined with a downstream revert/refund actually firing (e.g., failed outbound, insufficient swap liquidity, admin `RevertStuckInbound`). The primary `Recipient` field is well-guarded, so exploitation is confined specifically to the revert/refund side-path, which is less scrutinized and only exercised on failure paths — making it easy to miss in testing but straightforward for anyone submitting a crafted inbound/gateway event to reach.

### Recommendation
Add a `ValidateBasic`/format check for `RevertInstructions.FundRecipient` mirroring the existing `Recipient` check (`utils.IsValidAddress(fundRecipient, utils.HEX)`), rejecting execution (failing the PCTx/creating a normal revert to `Sender`) whenever the field is non-empty but not a well-formed 20-byte hex address, and explicitly reject the literal zero address unless it is an intentional sentinel. Apply the same guard uniformly at `buildRevertOutbound`, `handleFailedOutbound`, and `applyGasRefund` before calling `common.HexToAddress`.

### Proof of Concept
Not independently executed against a live node — verification is based on static code tracing of `x/uexecutor/types/inbound.go`, `x/uexecutor/keeper/build_revert_outbound.go`, and `x/uexecutor/keeper/outbound.go`. A concrete PoC would:
1. Submit/vote an `Inbound` (`TxType_FUNDS`) with a valid `Recipient` but `RevertInstructions.FundRecipient = "0xZZ"` (non-hex, non-empty).
2. Force the outbound/swap to fail (e.g., insufficient liquidity), triggering `handleFailedOutbound`.
3. Observe `CallPRC20Deposit` executing against `common.HexToAddress("0xZZ")` (resolves to `0x000...0`), permanently burning the re-minted principal instead of returning it to `Sender`.

I was not able to execute this against a running chain instance, so the exact silent-failure behavior of `common.HexToAddress`/`common.FromHex` for various malformed inputs (which characters short-circuit to zero vs. truncate) should be confirmed empirically before filing a high-confidence report.

// Canonicalize normalizes encoding-variant fields in place (per source-chain
// namespace) so the same event from any observer is byte-identical across
// ballot keys, UTX keys and registry lookups. Lenient (unparseable values are
// kept trimmed, never rejected) because the vote path must always record a
// UTX — execution-level validation rejects malformed inbounds later.
func (p *Inbound) Canonicalize() {
	p.SourceChain = strings.TrimSpace(p.SourceChain)
	p.TxHash = utils.LenientCanonicalizeTxHash(p.SourceChain, p.TxHash)
	p.Sender = utils.LenientCanonicalizeAddress(p.SourceChain, p.Sender)
	p.AssetAddr = utils.LenientCanonicalizeAddress(p.SourceChain, p.AssetAddr)
	// Recipient lives on Push Chain (EVM) regardless of source chain.
	p.Recipient = utils.LenientCanonicalizeEVMAddress(p.Recipient)
	p.LogIndex = strings.TrimSpace(p.LogIndex)
	p.Amount = strings.TrimSpace(p.Amount)
	p.RawPayload = utils.CanonicalizeHexBlob(p.RawPayload)
	p.VerificationData = utils.CanonicalizeHexBlob(p.VerificationData)
	if p.RevertInstructions != nil {
		// Refunds return to the source chain.
		p.RevertInstructions.FundRecipient = utils.LenientCanonicalizeAddress(p.SourceChain, p.RevertInstructions.FundRecipient)
	}
