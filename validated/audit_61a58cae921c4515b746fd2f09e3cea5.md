### Title
Transfer causing account-balance overflow triggers a `StorageInconsistentState` panic that halts the shard, rather than a recoverable transaction failure - (File: `runtime/runtime/src/lib.rs`, `chain/chain/src/runtime/mod.rs`)

### Summary
The external report is about a cross-chain `_credit` call that reverts (instead of failing gracefully) when a credited amount pushes total supply over a cap, permanently locking user funds. The closest reachable analog in this nearcore tree is the `Transfer` action's balance-overflow check: when a receipt's `deposit` combined with the receiver's existing balance would exceed `u128::MAX`, the runtime does not fail the receipt with an ordinary `ActionError` (which would trigger the refund/rollback machinery) but instead returns `StorageError::StorageInconsistentState("Account balance integer overflow...")`. Any single crafted or naturally-occurring transaction/receipt that causes this condition converts what should be a per-receipt failure into a **fatal error that panics the whole shard's chunk application**.

### Finding Description
Any account balance mutation in the runtime (`Transfer` action, gas-key balance credit, function-call deposit credit) that would overflow `u128` is guarded with `checked_add`, but on failure the code returns `StorageError::StorageInconsistentState("Account balance integer overflow...")` [1](#0-0)  instead of an ordinary `ActionErrorKind` that would go through the normal failed-receipt path (deposit/gas refund, `state_update.rollback()`).

The same overflow-guard pattern recurs at multiple credit sites: the gas-key balance credit uses `checked_add` and maps failure to `StorageError::StorageInconsistentState("gas key balance integer overflow")` [2](#0-1) , and the function-call deposit path performs the same check before executing the call [3](#0-2) .

Crucially, `StorageInconsistentState` is not treated as a recoverable per-transaction/per-receipt error at the top of the apply pipeline. `Runtime::apply_chunk` explicitly re-panics on any `StorageError` other than `FlatStorageBlockNotSupported`/`MissingTrieValue`: [4](#0-3) 

This is confirmed by an existing regression test that documents the invariant "an inconsistent-state error would be a failed chunk" and explicitly asserts that hitting `StorageInconsistentState` for owed validator balances is expected to make `apply()` return an `Err(RuntimeError::StorageError(StorageError::StorageInconsistentState(_)))`, which the production `apply_chunk` wrapper turns into a `panic!` [5](#0-4) . The doc comment on `VerificationResult::apply` explicitly states the concern: "a panic there stops the node instead of the transaction" [6](#0-5) .

Contrast this with how the runtime normally handles a receipt that cannot be completed (e.g. insufficient balance for storage staking): it uses `ActionErrorKind::LackBalanceForState`, a normal failed-receipt outcome that triggers `refund_unspent_gas_and_deposits` and `state_update.rollback()` [7](#0-6) , exactly the kind of graceful failure/rollback mechanism the external report recommends for the cap-exceeded case. The balance-overflow path skips this mechanism entirely and instead aborts the whole shard.

### Impact Explanation
Where the external bug merely locks funds on one chain requiring admin intervention (medium severity), this nearcore analog is more severe: reaching an account-balance `u128` overflow via a `Transfer` (or a gas-key credit, or a function-call deposit credit) does not just fail one receipt — it panics the node process applying that chunk. Because `checked_add` failures at these sites are converted to `StorageError::StorageInconsistentState` and `apply_chunk` re-panics on such errors, a single transaction/receipt that manages to push an account's balance past `u128::MAX` can bring down chunk production for the shard hosting that account, i.e. a transaction-triggered halt of block/chunk production, one of the explicitly in-scope severe outcomes for this scan.

### Likelihood Explanation
Reaching `u128::MAX` for a real account balance via normal transfers is astronomically unlikely under today's token supply, so this is primarily a **defense-in-depth defect** rather than an easily triggerable exploit under current economic parameters — the guard exists specifically because the overflow is only theoretically possible, and today it is caught with `checked_add`. The likelihood classification here should reflect that this requires an attacker to actually get an account balance close to `u128::MAX` (not realistically achievable purely by an unprivileged transaction signer under current supply/mint limits), which is why this is flagged as an analog worth documenting but with acknowledged low practical likelihood given current NEAR token economics; the code path itself, however, is confirmed and directly analogous to the reported bug class (cap-exceeding value causing an unrecoverable failure instead of a graceful rejection/rollback).

### Recommendation
Treat account-balance-overflow conditions at all credit sites (`Transfer` action, gas-key balance credit, function-call deposit credit) as ordinary `ActionErrorKind` failures rather than `StorageError::StorageInconsistentState`, so that the normal failed-receipt refund/rollback machinery (`refund_unspent_gas_and_deposits`, `state_update.rollback()`) handles them without ever reaching the `panic!` in `apply_chunk`. This mirrors the external report's recommendation of "implementing a rollback mechanism for transactions that exceed the cap" by ensuring any credit that would exceed a hard numeric limit fails the specific receipt (with a refund) instead of aborting shard-wide chunk processing.

### Proof of Concept
Conceptual PoC (not independently executed, based on code paths read):
1. Construct an account whose balance is at or extremely near `u128::MAX` (theoretical precondition; not achievable under current mainnet economics, but the code path is unconditionally reachable given such a state).
2. Submit a `Transfer` (or any action crediting balance) receipt targeting that account with a nonzero `deposit`.
3. The `checked_add` on `account.amount()` fails, and the runtime returns `StorageError::StorageInconsistentState("Account balance integer overflow...")` instead of a normal `ActionError` [1](#0-0) , [3](#0-2) .
4. This error propagates out of `Runtime::apply` as `Err(RuntimeError::StorageError(StorageError::StorageInconsistentState(_)))`.
5. `apply_chunk` in `chain/chain/src/runtime/mod.rs` matches on `Error::StorageError` and calls `panic!("{err}")` for anything other than `FlatStorageBlockNotSupported`/`MissingTrieValue` [4](#0-3) , halting the node instead of merely failing the offending receipt.
6. The existing test `test_apply_validator_update_uninitialized_account` demonstrates the same "inconsistent-state ⇒ failed chunk" pattern for a related overflow-adjacent invariant, confirming that this error class is designed to fail the whole `apply()` call rather than a single receipt [8](#0-7) .
