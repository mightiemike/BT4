## Title
Receiver gas-reward priced at a different gas-price scale than the burnt-amount accumulator causes a deterministic `checked_sub().unwrap()` panic (chain halt) - ([File: runtime/runtime/src/lib.rs])

### Summary
In the pre-`AccountCostIncrease` code path of `Runtime::apply_action_receipt`, the receiver's function-call gas reward is priced using the receipt's original **gas-purchase price**, while the burnt-amount accumulator it is subtracted from is priced using the **current block's gas price**. When these two prices diverge enough (a legitimate, protocol-allowed situation for delayed/congested receipts), the reward can exceed the accumulator, and the unconditional `.unwrap()` on the subtraction panics every validator applying the chunk — a deterministic, transaction-triggered chain halt. This is the same bug class as the Astaria `WithdrawProxy.claim()` finding: a value is computed in one fixed “scale” (there, `1e18`/token-decimals; here, gas-purchase price vs. gas-burn price) and then subtracted from an accumulator expressed in a different scale, causing an unhandled underflow that reverts/halts and can permanently jam the affected pathway.

### Finding Description
`Runtime::apply_action_receipt` computes two independent price bases for the same receipt: [1](#0-0) 

```
let gas_burn_price =
    if ProtocolFeature::AccountCostIncrease.enabled(apply_state.current_protocol_version) {
        // should always be <= gas_purchase_price, otherwise receiver_reward might underflow
        // or mint new tokens.
        std::cmp::min(gas_purchase_price, apply_state.gas_price)
    } else {
        apply_state.gas_price
    };
```

The comment explicitly documents the risk: `gas_burn_price` must be `<= gas_purchase_price`, otherwise the receiver reward can underflow. The `min()` guard, however, is only applied when `AccountCostIncrease` is enabled (protocol version 85+). Pre‑85, `gas_burn_price` is simply `apply_state.gas_price` — the *current block's* price, unrelated to `gas_purchase_price` (the price recorded on the receipt when it was created/purchased, potentially much earlier if the receipt was delayed by congestion): [2](#0-1) 

The burnt-amount accumulator is priced with `gas_burn_price`: [3](#0-2) 

```
let mut tx_burnt_amount = safe_gas_to_balance(gas_burn_price, gas_burnt)?
    .checked_sub(gas_refund_result.price_deficit)
    .unwrap();
...
let tokens_burnt = tx_burnt_amount;
```

But the receiver's function-call reward, in the pre-`AccountCostIncrease` branch, is priced with `gas_purchase_price` instead of `gas_burn_price`: [4](#0-3) 

```
let receiver_gas_reward = result
    .gas_burnt_for_function_call
    .checked_mul(*apply_state.config.fees.burnt_gas_reward.numer() as u64)
    .unwrap()
    .checked_div(*apply_state.config.fees.burnt_gas_reward.denom() as u64)
    .unwrap();
let receiver_reward =
    if ProtocolFeature::AccountCostIncrease.enabled(apply_state.current_protocol_version) {
        safe_gas_to_balance(gas_burn_price, receiver_gas_reward)?
    } else {
        // Post NEP-536/pre AccountCostIncrease: We are not refunding gas price differences...
        safe_gas_to_balance(gas_purchase_price, receiver_gas_reward)?
    };
```

That reward is then subtracted from `tx_burnt_amount` unconditionally: [5](#0-4) 

```
if receiver_reward > Balance::ZERO {
    let mut account = get_account(state_update, account_id)?;
    if let Some(ref mut account) = account {
        tx_burnt_amount = tx_burnt_amount.checked_sub(receiver_reward).unwrap();
        ...
```

`receiver_reward` is `burnt_gas_reward` (mainnet fraction ≈ 3/10) of `gas_burnt_for_function_call`, priced at `gas_purchase_price`, while `tx_burnt_amount` is (essentially) all of `gas_burnt` priced at `gas_burn_price = apply_state.gas_price`. Because gas price is bounded to a `[min, min*20]` range and moves block-to-block toward load (`compute_next_gas_price_checked`), a receipt purchased near the max price and executed (after being delayed by congestion, or by input-data dependency, or simply many blocks later) once the block price has fallen can have `gas_purchase_price` several multiples of `apply_state.gas_price`. Once `gas_purchase_price / gas_burn_price` exceeds roughly `gas_burnt / (burnt_gas_reward_fraction * gas_burnt_for_function_call)` (≈`1/0.3 ≈ 3.33` when the function call dominates the receipt's gas), `receiver_reward` exceeds `tx_burnt_amount`, and the `.unwrap()` panics.

### Impact Explanation
This computation runs inside `Runtime::apply_action_receipt`, which is executed identically and deterministically by every validator/node that applies the chunk containing the receipt. A panic here is not a graceful `RuntimeError` return; it is an unhandled `.unwrap()` on a `checked_sub`, which per nearcore's arithmetic-overflow policy aborts the process. Since every node hits the same underflow on the same receipt, this crashes the entire validator set simultaneously — a transaction-triggered chain halt, not merely a single-node crash or a resource-exhaustion issue.

### Likelihood Explanation
The trigger requires only: (1) the chain running a protocol version below `AccountCostIncrease` activation (PV 85) — a state the pre-85 code path is still compiled and reachable for, per `MIN_SUPPORTED_PROTOCOL_VERSION = 83`; and (2) an attacker submitting a `FunctionCall` action receipt that gets purchased at a high gas price and executed later (e.g., delayed via congestion control, cross-shard forwarding, or a postponed/data-dependent receipt) once the block gas price has dropped substantially, with most of the receipt's gas spent inside the function call itself (maximizing `gas_burnt_for_function_call` relative to `gas_burnt`). Both congestion (which naturally raises the purchase price and delays receipts) and gas-price mean-reversion (which lowers it again) are normal, attacker-influenceable network conditions, so no privileged access is needed — any account able to submit a `FunctionCall` transaction can attempt to engineer this timing.

### Recommendation
Price `receiver_reward` consistently with `tx_burnt_amount` in the pre-`AccountCostIncrease` branch too (i.e., always use the same price basis, `gas_burn_price`, for both the accumulator and the amount subtracted from it), or replace the unconditional `.unwrap()` at line 1132 with a `checked_sub` that saturates/caps `receiver_reward` at `tx_burnt_amount` and returns a `RuntimeError`/logs an inconsistency rather than panicking, mirroring the `min(gas_purchase_price, apply_state.gas_price)` guard already used for `gas_burn_price` itself.

### Proof of Concept
1. Submit a `FunctionCall` transaction whose receipt is purchased while the block gas price is near `max_gas_price` (e.g., during sustained >50% chunk utilization) and whose actions cause the receipt to be delayed (congestion, postponed via `input_data_ids`, or simply queued behind other receipts) until the block gas price has dropped toward `min_gas_price` (utilization consistently below 50% for several blocks) — a ~20x price ratio is achievable given `MAX_GAS_MULTIPLIER = 20`.
2. Ensure the function call consumes most of its attached gas in WASM execution (`gas_burnt_for_function_call ≈ gas_burnt`), maximizing `receiver_gas_reward = burnt_gas_reward_fraction * gas_burnt_for_function_call` relative to `gas_burnt`.
3. When the receipt is finally applied at the lower block price (pre-`AccountCostIncrease`), `receiver_reward = gas_purchase_price * receiver_gas_reward` (high price) can exceed `tx_burnt_amount = gas_burn_price * gas_burnt` (low price), triggering `tx_burnt_amount.checked_sub(receiver_reward).unwrap()` to panic at [6](#0-5) , crashing every node applying the chunk.
