### Title
Node key-export API endpoints allow creation of unencrypted/trivially-weak key backups (empty or arbitrary `newpassword`, no complexity enforcement) - ([File: core/web/eth_keys_controller.go])

### Summary
Every `/v2/keys/<type>/export/:ID` endpoint (ETH, EVM, CSA, OCR, OCR2, P2P, VRF, Solana, Cosmos, StarkNet, Aptos, Stellar, Tron, Sui, TON) reads the encryption password for the exported key file directly from an HTTP query parameter (`newpassword`) and forwards it unchanged into the keystore's `Export`/`ToEncryptedJSON` call. Unlike the CLI and the master-keystore unlock flow, none of these HTTP export paths invoke `utils.VerifyPasswordComplexity`, so an admin can request (or a script/automation/CI job can silently request) an export with `newpassword=""` or a single-character password. The resulting scrypt-encrypted JSON keyfile is then trivially/immediately crackable, and yet it is treated by operators as a "backed up, encrypted key" artifact — mirroring the reported bug class where users are permitted to create "encrypted" backups with no real protection.

### Finding Description
- The router wires `POST /v2/keys/eth/export/:address`, `/v2/keys/evm/export/:address`, `/v2/keys/csa/export/:ID`, `/v2/keys/ocr/export/:ID`, `/v2/keys/ocr2/export/:ID`, `/v2/keys/p2p/export/:ID`, `/v2/keys/vrf/export/:keyID`, and the generic per-chain export routes to controller `Export` handlers, gated only by `auth.RequiresAdminRole` [4](#0-3) .
- Each handler reads `newPassword := c.Query("newpassword")` and passes it straight to the keystore, e.g. `ekc.app.GetKeyStore().Eth().Export(c.Request.Context(), id, newPassword)` [1](#0-0) , and the generic controller does the same: `bytes, err := kc.ks.Export(keyID, newPassword)` [5](#0-4) .
- The keystore `Export` methods (`eth.go`, `p2p.go`, `vrf.go`, `stellar.go`, `sui.go`, `ton.go`, `aptos.go`, `cosmos.go`, `solana.go`) all call `key.ToEncryptedJSON(password, ks.scryptParams)` with whatever password was supplied, without any minimum-length or complexity check [6](#0-5) .
- This is inconsistent with the local/CLI authentication flow, which does enforce `MinRequiredLen = 16` and rejects leading/trailing whitespace via `VerifyPasswordComplexity` when creating a *new* keystore password [7](#0-6) [3](#0-2) . No equivalent guard exists on the export/backup path.

### Impact Explanation
Any principal with admin-role API access (which is also required to just read/manage keys) can generate a "backed up" key file that is effectively unencrypted (empty password) or trivially brute-forceable (1–2 character password), then store/transmit it as if it were a properly protected credential export. If that exported file is later exfiltrated (e.g., through a misconfigured backup destination, shared storage, log capture, or a compromised downstream system that only checked for "file exists" and not "password strength"), the attacker gains immediate access to the raw ETH/OCR/CSA/VRF/etc. private key material — a direct secret-disclosure / node-compromise path, analogous to the reported "skip password / unencrypted backup" issue.

### Likelihood Explanation
Requires an already-authenticated admin-role API caller, so this is not remotely exploitable by an unauthenticated attacker. However, it is easy to trigger accidentally (e.g., automation scripts, key-rotation tooling, or an attacker who has obtained admin API credentials through another vector) since there is no server-side guard preventing `newpassword=` (empty) or weak values, and the UI/CLI equivalents enforce complexity elsewhere in the codebase, creating an inconsistent, easily-missed security boundary.

### Recommendation
Enforce `utils.VerifyPasswordComplexity` (or an equivalent minimum-strength check) on the `newpassword` parameter inside every key controller's `Export` handler (or centrally inside the keystore `Export`/`ToEncryptedJSON` call paths) before encrypting and returning the key file, rejecting empty or sub-minimum-length passwords with a 400 error, consistent with the complexity requirements already enforced for the master keystore password.

### Proof of Concept
1. Authenticate as an admin-role API user (session cookie or API token).
2. `POST /v2/keys/eth/export/<address>?newpassword=` (empty) or `?newpassword=a`.
3. The server responds `200 OK` with a scrypt-encrypted JSON keyfile encrypted under the empty/weak password (`core/web/eth_keys_controller.go:240-258` → `core/services/keystore/eth.go:235-246`), which can be decrypted almost instantly offline, exposing the raw private key.

func VerifyPasswordComplexity(password string, disallowedStrings ...string) (merr error) {
	errMsg := ErrMsgHeader
	var stringErrs []string

	if LeadingWhitespace.MatchString(password) || TrailingWhitespace.MatchString(password) {
		stringErrs = append(stringErrs, ErrWhitespace.Error())
	}

	if len(password) < MinRequiredLen {
		stringErrs = append(stringErrs, fmt.Sprintf("password is less than %d characters long", MinRequiredLen))
	}

	for _, s := range disallowedStrings {
		if strings.Contains(strings.ToLower(password), strings.ToLower(s)) {
			stringErrs = append(stringErrs, fmt.Sprintf("password may not contain: %q", s))
		}
	}

func (ks *eth) Export(ctx context.Context, id string, password string) ([]byte, error) {
	ks.lock.RLock()
	defer ks.lock.RUnlock()
	if ks.isLocked() {
		return nil, ErrLocked
	}
	key, err := ks.getByID(id)
	if err != nil {
		return nil, err
	}
	return key.ToEncryptedJSON(password, ks.scryptParams)
}
