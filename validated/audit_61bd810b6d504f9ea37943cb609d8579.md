## Title
INBOUND_REVERT / RESCUE_FUNDS outbounds are created without the outbound-enabled gate, permanently stranding refund funds once the destination chain's outbound stays disabled - (File: `x/uexecutor/keeper/build_revert_outbound.go`)

### Summary
The Fractional report describes funds getting permanently stuck because some functions checked the shared resource's *state* inconsistently across code paths (leaving pending contributions unguarded relative to the path that actually mutated the shared vault state). Push Chain has the same class of bug: `x/uexecutor` enforces `IsChainOutboundEnabled` when building outbounds from a payload's EVM logs (`BuildOutboundsFromReceipt`), but the parallel code path that creates `INBOUND_REVERT` and `RESCUE_FUNDS` outbounds (`buildRevertOutbound` / `attachOutboundsToUtx`) never performs that check. Once a chain's outbound is disabled — a normal, non-privileged-abuse operational state (chain paused/deprecated, or the required precondition for `x/utss` fund migration) — user-triggered inbound failures still queue refund outbounds for that chain, and those outbounds can never be signed/broadcast because the TSS signing layer *does* enforce the same gate at sign time. The refund is created but can never leave `PENDING`, permanently stranding the user's already-deposited external-chain funds.

### Finding Description
Normal outbound creation explicitly checks and rejects when a destination chain's outbound is disabled: [1](#0-0) 

But the sibling outbound-creation helper used for refunding failed inbounds does not perform any such check: [2](#0-1) 

and the generic attach routine that both paths eventually funnel into also has no gate — it unconditionally appends the outbound and indexes it in `PendingOutbounds`: [3](#0-2) 

This ungated `buildRevertOutbound` + `attachOutboundsToUtx` combination is reached from every failed-inbound path that is triggerable by an ordinary depositor whose inbound fails validation or deposit for reasons unrelated to outbound-enablement (e.g. unregistered token config, empty recipient, invalid amount): [4](#0-3) [5](#0-4) 

Meanwhile, the off-chain TSS signing layer *does* gate on `IsChainOutboundEnabled` at sign time, confirmed by the session manager's dedicated rejection path/test: [6](#0-5) 

So the invariant "an outbound for a disabled-outbound chain must never exist / must never be attempted" is enforced only on one side (broadcasting) and only sporadically on the creation side (payload-triggered outbounds are blocked, revert/rescue outbounds are not). This directly mirrors the external report's root cause: some functions check the shared resource's live state, others that mutate/queue against the same resource do not, and a legitimate, non-malicious state transition (outbound disabled — analogous to a buyout starting) leaves already-committed positions (a pending revert refund — analogous to a migration contribution) with no way out.

### Impact Explanation
When a chain's outbound is disabled — whether for ordinary operational reasons (chain paused/deprecated by `MsgUpdateChainConfig`) or because it is the required precondition for `x/utss.InitiateFundMigration` (`k.uregistryKeeper.IsChainOutboundEnabled` must be false, see `x/utss/keeper/msg_initiate_fund_migration.go`), any ordinary user inbound that later fails validation/deposit for that chain still produces a `PENDING` `INBOUND_REVERT` outbound. This outbound is indexed in `PendingOutbounds` for UV pickup, but the session manager will refuse to ever sign it while outbound stays disabled. The user's original externally-deposited funds — which the revert path exists specifically to return — become permanently unrecoverable, with no admin or protocol escape hatch analogous to `RevertStuckInbound`/`RescueFunds` covering this specific stuck-outbound state (rescue itself requires a *REVERTED* inbound-revert outbound to already exist, which this permanently-PENDING outbound can never reach). This is a permanent freezing of protocol/user-controlled funds triggerable without any privileged or malicious actor.

### Likelihood Explanation
This requires no validator or admin misbehavior. An attacker (or any ordinary user) only needs to submit a deposit on a source chain whose outbound has been disabled (a state an admin sets routinely for chain maintenance/deprecation or as a mandatory precursor to TSS key migration) using conditions that make the deposit fail validation (e.g., an asset address without a registered `TokenConfig`, an empty recipient for a `FUNDS` inbound, etc. — all of which are exercised by existing integration tests as ordinary failure paths). Honest Universal Validators faithfully observe and vote in the real external-chain event, so the ballot finalizes normally and the vulnerable code path executes deterministically.

### Recommendation
Add the same `IsChainOutboundEnabled` check used in `BuildOutboundsFromReceipt` to `buildRevertOutbound` / `attachOutboundsToUtx` (or to each call site that constructs an `INBOUND_REVERT` / `RESCUE_FUNDS` outbound) before queuing it into `PendingOutbounds`. If the destination chain's outbound is disabled at refund-creation time, either (a) defer/queue the revert creation until outbound is re-enabled with a durable retry mechanism, or (b) surface a first-class on-chain record (similar to `ExpiredInbounds`) that an admin escape hatch can act on once the chain is re-enabled, instead of silently creating an outbound that can never be signed.

### Proof of Concept
1. Admin disables outbound for chain `eip155:X` via `MsgUpdateChainConfig` (ordinary maintenance, or as the mandatory step before `MsgInitiateFundMigration`).
2. A user deposits on `eip155:X` using an asset address that has no registered `TokenConfig` on Push Chain (see `test/integration/uexecutor/vote_inbound_validation_test.go` "non-isCEA FUNDS inbound deposit failure DOES create revert outbound" for the exact mechanics).
3. Honest UVs observe and vote the inbound via `MsgVoteInbound`; deposit fails; `handleFailedInboundValidation`/`ExecuteInboundFunds` calls `buildRevertOutbound` and `attachOutboundsToUtx` — no outbound-enabled check is performed, so a `PENDING` `INBOUND_REVERT` outbound is created and indexed in `PendingOutbounds`.
4. The Universal Client's `SessionManager` (per `TestVerifySigningRequest_OutboundDisabled`) refuses to build/sign this outbound because `IsChainOutboundEnabled("eip155:X") == false`.
5. The outbound remains `PENDING` indefinitely; as long as outbound for `eip155:X` is not re-enabled, the user's original deposit is permanently unrecoverable — with no completion path since `RESCUE_FUNDS` requires a `REVERTED` (not `PENDING`) inbound-revert outbound.

func (k Keeper) attachOutboundsToUtx(
	ctx sdk.Context,
	utxId string,
	outbounds []*types.OutboundTx,
	revertMsg string, // revert msg if the outbound is for a inbound revert
) error {

	if len(outbounds) == 0 {
		return nil
	}
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {

		for _, outbound := range outbounds {

			utx.OutboundTx = append(utx.OutboundTx, outbound)

			// Compute signature expiry deadline for the destination chain.
			var signingDeadline int64
			if chainCfg, err := k.uregistryKeeper.GetChainConfig(ctx, outbound.DestinationChain); err == nil {
				if chainCfg.TssSigningDeadline != nil && *chainCfg.TssSigningDeadline > 0 {
					signingDeadline = ctx.BlockTime().Unix() + int64(chainCfg.TssSigningDeadline.Seconds())
				}
			}

			// Write to pending outbounds index (inside UpdateUniversalTx closure for atomicity)
			if err := k.PendingOutbounds.Set(ctx, outbound.Id, types.PendingOutboundEntry{
				OutboundId:      outbound.Id,
				UniversalTxId:   utxId,
				CreatedAt:       ctx.BlockHeight(),
				SigningDeadline: signingDeadline,
			}); err != nil {
				return fmt.Errorf("failed to set pending outbound index for %s: %w", outbound.Id, err)
			}

// from the UniversalCore contract via getOutboundTxGasAndFees.
func (k Keeper) buildRevertOutbound(sdkCtx sdk.Context, inbound *types.Inbound) *types.OutboundTx {
	recipient := inbound.Sender
	if inbound.RevertInstructions != nil && inbound.RevertInstructions.FundRecipient != "" {
		recipient = inbound.RevertInstructions.FundRecipient
	}

	outbound := &types.OutboundTx{
		DestinationChain:  inbound.SourceChain,
		Recipient:         recipient,
		Amount:            inbound.Amount,
		ExternalAssetAddr: inbound.AssetAddr,
		Sender:            inbound.Sender,
		TxType:            types.TxType_INBOUND_REVERT,
		OutboundStatus:    types.Status_PENDING,
		Id:                types.GetOutboundRevertId(inbound.SourceChain, inbound.TxHash, inbound.LogIndex),
	}
