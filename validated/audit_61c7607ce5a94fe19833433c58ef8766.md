### Title
Signer v1/v2 use different "already-signed-in-tenure" predicates for the tenure-change duplicate check, causing mixed-version signer sets to disagree on whether the same tenure-change block is valid - ([File: stacks-signer/src/chainstate/v1.rs], [File: stacks-signer/src/chainstate/v2.rs])

### Summary
The GMX report's root cause is that two code paths that are supposed to enforce the *same* rule (block-range validity for order execution) instead enforce *different* rules per order type, letting an attacker use the resulting information/ordering asymmetry to get a guaranteed-favorable outcome. The structurally closest analog I could locate in this repo is that the signer's tenure-change duplicate-block check is implemented with two different predicates depending on signer protocol version: `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` calls `signer_db.get_last_globally_accepted_block(...)`, while the same-named function in `stacks-signer/src/chainstate/v2.rs` calls `signer_db.get_last_signed_block(...)` (locally-or-globally accepted) [1](#0-0) [2](#0-1) . The project's own documentation calls this out explicitly: "v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)" [3](#0-2) .

### Finding Description
Both `v1::validate_tenure_change_payload` and `v2::validate_tenure_change_payload` are meant to enforce the same consensus-relevant equality: "does this tenure-change block try to start a new tenure while we (the signer) have already accepted a block within the tenure it claims to be superseding?" If so, the proposal must be rejected as `RejectReason::DuplicateBlockFound` [1](#0-0) [4](#0-3) .

The two implementations, however, source their "have we already accepted a block in this tenure" answer from different predicates:
- v1 uses `get_last_globally_accepted_block`, i.e., only a block that has crossed the network-wide signature threshold counts.
- v2 uses `get_last_signed_block`, i.e., a block that this signer merely locally signed (but which has not necessarily reached the global signature threshold) also counts.

This means a proposal that reorgs a block that is *locally signed but not yet globally accepted* will be treated as a duplicate/invalid by v2 signers but accepted by v1 signers evaluating the exact same block and exact same local state. A miner (or any actor observing the mixed signer set) that knows the version split of the signer pool can craft a tenure-change proposal timed against a block that has only been locally (not yet globally) signed, and predict in advance which subset of signers will accept vs. reject it - the same "free look into the future" structural weakness as the GMX bug, where the attacker exploits the fact that two logically-parallel validation paths don't apply the same timing/finality rule.

### Impact Explanation
If a mixed-version signer set (v1 and v2 signers coexisting, e.g., during a rolling upgrade) is asked to vote on a tenure-change proposal that reorgs a locally-signed-but-not-globally-accepted block, v1 and v2 signers will produce different verdicts for the identical proposal. This is a validation-verdict divergence among honest, non-colluding signers driven purely by protocol-version skew rather than by any signer acting maliciously, resulting in a temporary tip/consensus disagreement (vote splitting, delayed finality, or a stalled tenure) until the weight of one version dominates. This matches the "High - temporary tip disagreement" / "validation verdict two nodes disagree on" category rather than a full chain split, since eventual convergence should occur once weight tips to one side.

### Likelihood Explanation
This requires only that the signer network is running mixed v1/v2 chainstate logic (a normal, expected condition during a protocol upgrade window), and that a proposer submits a tenure-change confirming a block that is locally-signed but not globally accepted — a scenario that is not attacker-privileged (any proposer/miner can trigger it opportunistically by submitting the tenure-change close to when only a local, sub-threshold signature exists). No signer collusion or majority control is needed to *trigger* the divergence; only the natural version skew during rollout is needed.

### Recommendation
Ensure `validate_tenure_change_payload` in v1 and v2 use an identical predicate for "already accepted a block in this tenure" (both should require the same finality condition — either both require global acceptance, or both accept a well-defined "locally signed" state) so that all signers apply congruent rules to tenure-change proposals regardless of protocol version, closing the same-input/different-verdict window during mixed-version operation.

### Proof of Concept
Not independently reproduced in this pass; the divergence is evidenced directly by comparing the two implementations, which is why this analysis is based on their source and the project's own documentation of the exact behavioral difference: [5](#0-4) [6](#0-5) [7](#0-6) 

Note: I was unable to fully trace `get_last_signed_block` / `get_last_globally_accepted_block` implementations in `stacks-signer/src/signerdb.rs` in this pass (tool budget exhausted before reading that file), so the precise timing window in which a block is "locally signed but not globally accepted" (and thus how exploitable/likely the divergence is in practice) is not fully verified. A follow-up review of `signerdb.rs`'s definitions of those two predicates, plus a live/integration test with a mixed v1/v2 signer set proposing a tenure-change against a sub-threshold-signed block, is recommended to confirm exploitability before treating this as fully confirmed.

    /// in tenure changes, we need to check:
    /// (1) if the tenure change confirms the expected parent block (i.e.,
    /// the last globally accepted block in the parent tenure)
    /// (2) if the parent tenure was a valid choice
    fn validate_tenure_change_payload(
        &self,
        proposed_by: &ProposedBy,
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the sortition's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        let parent_tenure_id = &proposed_by.state().data.parent_tenure_id;
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            self.config.tenure_last_block_proposal_timeout,
            self.config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // now, we have to check if the parent tenure was a valid choice.
        let is_valid_parent_tenure = proposed_by.state().data.check_parent_tenure_choice(
            signer_db,
            client,
            &self.config.first_proposal_burn_block_timing,
        )?;
        if !is_valid_parent_tenure {
            return Err(RejectReason::ReorgNotAllowed);
        }
        let last_in_current_tenure = signer_db
            .get_last_globally_accepted_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
    }

A failed check becomes a different rejection depending on who asked.
`check_block_against_signer_db_state` returns `SortitionViewMismatch`, or
`ConnectivityIssues` when the lookup itself errored rather than answering; the v2
`check_proposal` path returns `InvalidParentBlock`.

Two things belong to the proposal path only and are **not** re-run at validate-ok
or at signing:

- `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we
  have already accepted a block in the tenure a tenure-change block is starting.
  v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1
  counts only globally accepted ones (`get_last_globally_accepted_block`).
- the v2 `check_proposal` wrapper checks miner pubkey hash, consensus hash, the
  pox bitvec, and tenure-extend rules before delegating here.

Because the duplicate check never runs again, a block that crosses the pre-commit
threshold long after it was proposed relies on section 5's own-tenure conflict
guard to cover the same ground.

The same `get_tenure_last_block_info` also feeds the state machine's
parent-tenure view (section 8), which is why its semantics are
consensus-visible.

> Anchors: `check_latest_block_in_tenure`,

> `validate_tenure_change_payload` (chainstate/v1.rs, v2.rs);
> `check_block_against_signer_db_state` (signer.rs); `get_last_signed_block`,
> `get_last_globally_accepted_block`, `get_last_accepted_block` (signerdb.rs)
