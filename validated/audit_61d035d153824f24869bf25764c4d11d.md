## Finding

### Title
`GlobalStateView::check_proposal` (v2 signer chainstate) omits the reorg-legitimacy check `check_parent_tenure_choice`, allowing a minority of global-state-protocol signers to accept a tenure-change block whose parent tenure choice is an unpermitted reorg - ([File: stacks-signer/src/chainstate/v2.rs])

### Summary
The v1 signer chainstate validates every tenure-change proposal's parent-tenure choice via `SortitionData::check_parent_tenure_choice`, which enforces the rule that a miner may only build on something other than the immediately-prior sortition if the reorged tenures are provably "safe" to replace (zero or a single, poorly-timed block). The v2 (`GlobalStateView`) `check_proposal`/`validate_tenure_change_payload` path, used by signers running the newer global-state protocol, never calls this function at all.

### Finding Description
`stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload` explicitly performs this check: [1](#0-0) 
calling `proposed_by.state().data.check_parent_tenure_choice(...)` and rejecting with `RejectReason::ReorgNotAllowed` if it returns `false`.

`stacks-signer/src/chainstate/v2.rs::validate_tenure_change_payload` performs the parent-tenure-confirmation check and the duplicate-block check, but has **no call** to `check_parent_tenure_choice` anywhere in the file: [2](#0-1) 
A repo-wide search confirms `check_parent_tenure_choice` is referenced only in `chainstate/mod.rs` (definition), `chainstate/v1.rs` (call site), `v0/signer.rs`, and its own tests — never in `chainstate/v2.rs`, the file that implements `check_proposal` for `GlobalStateView`.

The v2 code contains a comment suggesting this check happened earlier ("We already confirmed in check miner activity that the current tenure is valid..."), but no function named anything like `check_miner_activity` exists in the repo, and no other v2 code path invokes `check_parent_tenure_choice` before or during block-proposal evaluation. `check_parent_tenure_choice`'s doc-comment states its actual purpose is to gate whether a *reorg of the parent tenure* is legitimate — a materially different question from whether "the current tenure is valid" (miner activity/timeout), which is handled by the unrelated `SortitionState::is_timed_out`/`is_tenure_valid` machinery.

This means: for signers running the v2/global-state protocol, a miner can propose (and get signed) a `BlockFound` tenure-change whose `prev_tenure_consensus_hash` points to a tenure other than the immediately-preceding sortition — i.e., an unpermitted reorg — as long as it passes `check_tenure_change_confirms_parent` (which only checks that the block confirms the *reported* parent tenure's last signed block, not whether choosing that parent over the more recent sortition was legitimate) and the `DuplicateBlockFound`/`get_last_signed_block` checks (which only look at the *target* tenure, not at tenures being reorged away).

### Impact Explanation
This breaks the equality the report's bug-class targets: "a tenure not descending from its sortition." v1 and v2 signers, evaluating the exact same tenure-change proposal, can reach different verdicts — v1 signers reject an illegitimate reorg with `ReorgNotAllowed`, while v2 signers have no code path that can produce that rejection, since the underlying function is never invoked. In a mixed-version signer set (explicitly a supported, real-world scenario since v1/v2 coexist behind `determine_active_signer_protocol_version` and `uses_global_state()`), this is a **minority-triggerable validation-verdict divergence**: v2 signers can be induced to sign a tenure-change block that v1 signers would reject as an unsanctioned reorg. If v2 signers reach the acceptance threshold, this results in a temporarily accepted competing tenure that overrides recently-signed blocks in a way the protocol's reorg-safety rule (bounded to "0 blocks or 1 poorly-timed block") was designed to prevent, i.e., blocks that should be protected from reorg can be discarded/overridden without the safety gate — a tip disagreement / potential reorg of otherwise-final blocks bounded by the signer set split.

### Likelihood Explanation
Reachable without a majority: it only requires v2-protocol signers (or a v2-only signer set) to receive a crafted tenure-change proposal whose parent tenure is not the prior sortition. `check_proposal` in v2 is the sole gate for these signers (`stacks-signer/src/chainstate/v2.rs:113-300`), and since it never calls `check_parent_tenure_choice`, no configuration of `SortitionData` or `SignerDb` state on the v2 path can produce a `ReorgNotAllowed` rejection. A miner attempting this needs no signer keys or admin privileges — the attempt is purely a matter of what tenure-change payload it proposes, i.e., unprivileged and minority-triggerable in a mixed v1/v2 environment.

### Recommendation
Add an explicit call to `SortitionData::check_parent_tenure_choice` inside `stacks-signer/src/chainstate/v2.rs::validate_tenure_change_payload`, mirroring the v1 implementation, and return `RejectReason::ReorgNotAllowed` when it returns `false`. Confirm (and if necessary, add tests to `stacks-signer/src/chainstate/tests/v2.rs`) that a reorg-inducing tenure-change proposal is rejected identically under both v1 and v2 protocol paths, and audit the misleading comment about "check miner activity" to identify whether a real, equivalent check was intended but never wired in.

### Proof of Concept
Conceptual PoC (no live network needed to demonstrate the code-path divergence):
1. Construct a `SortitionData`/`GlobalStateView` scenario where `parent_tenure_id != prior_sortition` (a reorg attempt) and the reorged tenure has >1 globally-accepted blocks recorded in `SignerDb` — a case that `check_parent_tenure_choice` would reject (`stacks-signer/src/chainstate/mod.rs:210-223`).
2. Run this `TenureChangePayload`/`NakamotoBlock` through `stacks-signer/src/chainstate/v1.rs::validate_tenure_change_payload`: observe it returns `Err(RejectReason::ReorgNotAllowed)`.
3. Run the identical payload through `stacks-signer/src/chainstate/v2.rs::validate_tenure_change_payload` (via `GlobalStateView::check_proposal`): observe it returns `Ok(())` (assuming `check_tenure_change_confirms_parent` and the duplicate check pass), because no equivalent call exists in this file.
4. This divergence is directly verifiable by inspecting that `check_parent_tenure_choice` has zero call sites in `stacks-signer/src/chainstate/v2.rs`, contrasted with its single call site (with `ReorgNotAllowed` handling) in `stacks-signer/src/chainstate/v1.rs:497-504`.

*Note: due to index size limits, I was not able to fully trace whether some other code path outside `chainstate/v2.rs` (e.g., inside `signer_state.rs`'s miner-state-machine computation) independently re-derives an equivalent reorg-safety guarantee for v2 before a block reaches `check_proposal`. I searched for `check_miner_activity` (referenced in the v2 source comment) and found no such function in the indexed codebase. If such logic exists elsewhere and was simply renamed/refactored, it would need to be located and confirmed to actually enforce the same tenure-reorg constraint before this finding can be considered dispositive; I recommend a Devin session with full repository access to verify this precisely.*

    /// in tenure changes, we need to check:
    /// if the tenure change confirms the expected parent block (i.e.,
    /// the last globally accepted block in the parent tenure)
    fn validate_tenure_change_payload(
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        parent_tenure_id: &ConsensusHash,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        config: &ProposalEvalConfig,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the signer's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            config.tenure_last_block_proposal_timeout,
            config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // We already confirmed in check miner activity that the current tenure is valid. So check we are not
        // reorging the tenure blocks. Only blocks we have signed (locally or globally accepted) count
        // here: a block we have merely pre-committed to carries no signature from us, so it is safe to
        // accept a competing tenure-start block in its place if it failed to reach consensus.
        let last_in_current_tenure = signer_db
            .get_last_signed_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
    }
