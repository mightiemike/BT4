### Title
`ensure_match_transaction_info` skips state-checkpoint hash comparison, allowing replay-verify tooling to accept a corrupted state root as valid - (File: types/src/transaction/mod.rs)

### Summary
`TransactionOutput::ensure_match_transaction_info` in [1](#0-0)  is the authenticated-comparison function used by db-tool's `replay-on-archive`/`replay-verify` and `aptos-move/cli` transaction replay to check a locally re-executed `TransactionOutput` against the `TransactionInfo` recorded/committed on-chain. It checks status, gas used, write-set hash (`state_change_hash`) and event root hash, but explicitly does **not** compare the recomputed state-checkpoint hash (SMT/state root) against `TransactionInfo::state_checkpoint_hash()` (nor the hot-state or position-state checkpoint hashes), as documented by the function's own trailing TODO comment.

### Finding Description
`ensure_match_transaction_info` is called from two independent tools that do not go through the chunk-executor's checkpoint-hash cross-check:
- `storage/db-tool/src/replay_on_archive.rs::execute_and_verify` [2](#0-1)  re-executes archived transactions with `AptosVMBlockExecutor::execute_block` and calls `ensure_match_transaction_info` directly on the resulting `TransactionOutput`, with no separate state-checkpoint verification step.
- `aptos-move/cli/src/commands.rs` calls the same method after materializing a VM output for a single replayed transaction [3](#0-2) .

By contrast, the normal chunk-executor path (`execution/executor/src/chunk_executor/mod.rs::update_ledger`) does validate checkpoint hashes, by explicitly threading `known_state_checkpoints`/`known_hot_state_checkpoints`/`known_position_state_checkpoints` into `DoStateCheckpoint::run()` [4](#0-3) . The `replay_on_archive` tool's direct-execution path bypasses this checkpoint-validating machinery entirely, relying solely on `ensure_match_transaction_info`, which is the function that explicitly skips the check:

The broken invariant: `state_change_hash` (the hash of *this single transaction's* write set) is a different, narrower value than `state_checkpoint_hash` (the global SMT/JMT state root after applying the write set on top of all prior state). A correctness bug anywhere in the durable state-commit path (e.g., stale-index handling, JMT/SMT node construction, hot-state merge, or the position/trading-native state tree noted in the comment) can produce a wrong global state root while each individual transaction's own write-set hash still matches. Because `ensure_match_transaction_info` never compares `state_checkpoint_hash`, such divergence is invisible to the two authenticated replay-verification call sites above.

### Impact Explanation
Replay-verify tooling (`db-tool replay-on-archive`, and by extension any operational or audit process relying on it) is one of the primary mechanisms for detecting silent state-commitment corruption from backup archives. This gap means a state-computation bug that corrupts the committed Merkle/state root — while leaving the per-transaction write-set hash intact — would be reported as "replay succeeded" even though the authenticated global ledger state diverges from what was actually computed and committed on mainnet. This falls squarely within the state-integrity gate: "Committed state that differs from the correct VM result... Hard-fork-only divergence during commit, replay, restore, or proof verification," since the state root is precisely the proof-bearing/authenticated value that downstream state/Merkle proofs are built on.

### Likelihood Explanation
This is not a directly externally triggerable exploit by an unprivileged attacker in the traditional sense — it does not corrupt consensus-committed state by itself. Its severity comes from being a detection blind spot: any other latent bug in state-commit/restore logic (several of which are explicitly called out by the code's own comments in this repo, e.g. the "trading-native"/position state root) would go undetected by this specific verification tool path, undermining the safety net that operators rely on to catch state-root divergence before/after it becomes consensus-committed. The code's own TODO comment confirms this is a known, currently-unmitigated gap rather than a hypothetical one.

### Recommendation
Extend `ensure_match_transaction_info` to also compare the recomputed state-checkpoint hash (and, where applicable, hot-state and position-state checkpoint hashes) against `txn_info.state_checkpoint_hash()` / `hot_state_checkpoint_hash()` / `position_state_checkpoint_hash()`, or otherwise ensure that all replay-verify call sites (`replay_on_archive.rs`, `aptos-move/cli`) route through the checkpoint-validating `DoStateCheckpoint` machinery used by the chunk executor before treating a replay as successful.

### Proof of Concept
Not applicable as a runnable PoC — this is a code-audit finding based on a self-documented gap. To construct a concrete demonstration: (1) inject a state-commit bug that alters the computed state-checkpoint hash without changing any individual transaction's write-set bytes (e.g., a stale-index or JMT construction bug affecting the global root only), (2) run `db-tool replay-on-archive` or `aptos-move/cli` replay across the affected version range, and (3) observe that `ensure_match_transaction_info` reports success because it never inspects `state_checkpoint_hash`.

**Note on verification limits:** I could not fully trace whether `storage/backup/backup-cli/src/coordinators/replay_verify.rs::ReplayVerifyCoordinator` (used by `db-tool replay-verify`, distinct from `replay-on-archive`) routes through the chunk-executor's checkpoint-validating `update_ledger`/`DoStateCheckpoint` path or also relies solely on `ensure_match_transaction_info`; confirming this would require deeper tracing of `TransactionRestoreBatchController`'s replay path, which the index did not fully surface.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
