### Title
Attacker-controlled `UniversalPayload.GasLimit` can OOG-panic `MsgVoteInbound`, wiping recorded votes and permanently blocking ballot finalization for that inbound - (File: `x/uexecutor/keeper/msg_vote_inbound.go`)

### Summary
An external, unprivileged actor who initiates a cross-chain deposit event (source-chain sender) fully controls the `UniversalPayload` embedded in that event, including `GasLimit` and `Data`. Honest Universal Validators (UVs) observe this event verbatim and submit it via `MsgVoteInbound`. There is no upper bound on `GasLimit`, and it is passed directly as the explicit EVM `gasLimit` to `DerivedEVMCall`/`CallUEAExecutePayload`. If a crafted, gas-heavy payload consumes more gas than the SDK `GasWanted` on the UV's vote transaction, the Cosmos SDK gas meter panics with out-of-gas *after* the vote and ballot state were already written via `commit()` earlier in the same handler — but because all writes for a `DeliverTx` share one outer `CacheMultiStore`, the panic discards the entire transaction, including the just-recorded vote. This is the same class of bug as the LayerZero report: a large, attacker-tunable gas sink positioned just before critical state-persisting logic, such that exhausting gas mid-flow blocks/erases the very bookkeeping meant to record failure or progress, rather than gracefully failing into the designed fallback path.

### Finding Description
`VoteInbound` records the vote and finalizes the ballot inside a `CacheContext`, calls `commit()`, and only then proceeds to create the `UniversalTx` and execute it: [3](#0-2) . Execution failures from validation (`ValidateForExecution`) are turned into a graceful `handleFailedInboundValidation` path with a FAILED `PCTx` and revert outbound, guaranteeing a `UniversalTx` is always created per the function's own documented invariant: [4](#0-3)  and [5](#0-4) .

However, `ValidateForExecution` never bounds `GasLimit` — it only calls `UniversalPayload.ValidateBasic()`, which merely checks it parses as a non-negative integer string: [6](#0-5)  and [1](#0-0) . `ExecuteInbound` dispatches to `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload`, which call `ExecutePayloadV2` → `CallUEAExecutePayload`, using the attacker-supplied `GasLimit` verbatim as the explicit gas parameter: [7](#0-6) , [2](#0-1) .

If this attacker-chosen `GasLimit` (combined with EVM execution against arbitrary `Data`/`To`) consumes more of the outer Cosmos SDK gas meter than the vote transaction's declared `GasWanted`, the SDK gas meter panics with `ErrorOutOfGas` mid-execution — after `RecordInboundVote`/`VoteOnInboundBallot` already ran `commit()` into the local `tmpCtx`, but this write is not truly durable: it lives in the same outer `DeliverTx` cache that BaseApp discards entirely when it recovers a panic and returns an error for that message. The net effect: the honest UV's vote, and the ballot-finalization side effects, are wiped, and no `UniversalTx` or failed-PCTx safety net is ever written for that inbound — contradicting the module's own stated invariant that a UTX is *always* created after ballot finalization.

Since `MsgVoteInbound` is a gasless message type (only fee deduction is skipped, per `app/txpolicy/gasless.go`, not gas-meter enforcement: [8](#0-7)  and [9](#0-8) ), each UV that revotes on this same crafted inbound is subject to the identical OOG panic, since the offending `GasLimit`/`Data` are part of the canonicalized `Inbound` payload that every honest observer reproduces identically. This can repeatedly nullify votes on that specific inbound across UVs, preventing the ballot from ever reaching a terminal (PASSED/EXPIRED/REJECTED) state and from ever producing the UTX record — funds observed as bridged on the source chain can never be reflected, refunded, or reverted on Push Chain for that inbound.

### Impact Explanation
This breaks the "honest-validator finalization path" and "universal execution path" invariants: an unprivileged, external-chain sender can craft a source-chain event whose attacker-controlled `UniversalPayload.GasLimit`/`Data` causes the corresponding `MsgVoteInbound` to abort via out-of-gas panic on every UV that attempts to vote/finalize it, permanently preventing the ballot from finalizing and the `UniversalTx` safety-net record (deposit/refund) from ever being created — a denial-of-service specific to that bridged transaction that is reachable purely through a default deposit-with-payload transaction on the source chain, with honest nodes and honest validators. Depending on gas cost relative to typical UV `GasWanted` settings for vote transactions, this could also manifest as a permanent freeze of the bridged funds tied to that inbound (never reverted, never delivered), which the report's allowed-impact gate explicitly lists as in scope ("permanent freezing... of user or protocol-controlled funds").

### Likelihood Explanation
Likelihood is Medium: it requires the attacker's chosen `GasLimit`/payload complexity to exceed whatever `GasWanted` UVs typically set for `MsgVoteInbound` transactions (an off-chain/config detail not verifiable from this repository alone), and it depends on the actual gas semantics of `DerivedEVMCall`'s explicit-gasLimit sub-call versus the parent SDK gas meter (i.e., whether the sub-call's gas is drawn from and can exhaust the same meter that wraps the whole message handler, causing a panic rather than a contained EVM revert). I could not fully confirm from the indexed code how `DerivedEVMCall`'s gas accounting interacts with the outer Cosmos SDK gas meter (this logic lives in the pinned `github.com/pushchain/evm` fork referenced by `DERIVED_TRANSACTIONS.md`, whose implementation is outside this repository's index). This uncertainty should be resolved by a Devin session with full repository/dependency access before treating this as confirmed exploitable.

### Recommendation
Enforce an explicit upper bound on `UniversalPayload.GasLimit` in `ValidateForExecution` (e.g., capped well below typical UV vote-tx `GasWanted`, similar to how the LZ report recommends bounding the attacker-controlled array size). Additionally, wrap the execution dispatch (`ExecuteInbound`/`ExecutePayloadV2`) in a `recover()`-guarded boundary within `VoteInbound` so that any residual out-of-gas or panic condition during payload execution degrades to the existing `handleFailedInboundValidation`/failed-PCTx path instead of unwinding and erasing the already-finalized vote and ballot state.

### Proof of Concept
Not independently reproduced against a running node; derived from static analysis of the call chain: `VoteInbound` → `ExecuteInbound` → `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` → `ExecutePayloadV2` → `CallUEAExecutePayload` → `DerivedEVMCall(gasLimit=UniversalPayload.GasLimit)`, where `GasLimit` is attacker-supplied and unbounded per `UniversalPayload.ValidateBasic()`. A concrete PoC would require running the full node stack (including the `github.com/pushchain/evm` fork) with a crafted deposit event whose payload `GasLimit`/`Data` are tuned to exceed a UV's vote-tx gas budget, then observing whether the resulting SDK panic causes the entire `MsgVoteInbound` (including the vote/ballot writes) to be discarded rather than degrading into the failed-PCTx/revert path — this exceeds what is verifiable via static code search alone.
