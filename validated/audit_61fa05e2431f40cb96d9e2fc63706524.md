### Title
`accrue()` pause pass-through returns stale index/lindex without reverting, corrupting `system-borrow`/`system-repay`/`deposit`/`redeem` accounting and market-side index cache - (File: `local-testing/contracts/vault/vault-sbtc.clar` and equivalent per-vault contracts)

### Summary
Every vault contract's `accrue` function, when the `accrue` pause flag is set, returns `(ok { index: idx, lindex: lidx })` with the *stale* pre-accrual values instead of reverting or refusing the call. Every state-changing vault entry point (`deposit`, `redeem`, `system-borrow`, `system-repay`, `socialize-debt`, etc.) calls `(try! (accrue))` first and treats its `ok` result as fresh, correctly-updated indexes.

### Finding Description
In `vault-sbtc.clar` (and identically in `vault-stx.clar`, `vault-usdc.clar`, `vault-usdh.clar`, `vault-ststx.clar`, `vault-ststxbtc.clar`, and their mainnet `v0-vault-*` counterparts): [1](#0-0) 

```clarity
(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          (let ((next (next-index)) ...)
            ...
            (ok { index: next, lindex: nliq })))))
```

When the DAO (or whoever controls pause-states) pauses `accrue` for a vault, `accrue()` **succeeds** (`ok`) but returns the *old* index/lindex pair, silently skipping the interest-accrual update, instead of returning an error. Every caller treats a successful `try!` as "indexes are now current": [2](#0-1) 
- `deposit` calls `(u (try! (accrue)))` and then computes `convert-to-shares-preview amount` using whatever index is in storage — unaffected by the pause flag being consulted or not, because `try!` never sees a failure. [3](#0-2) 
- `system-borrow` and `system-repay` likewise call `(try! (accrue))`, then read `(var-get index)` directly afterward for scaling debt — since the pause branch never updates `last-update`, `index`, or `lindex`, the debt/liquidity indexes silently stop advancing while the vault continues to accept borrows/repays/deposits/redemptions and mint interest-implied shares, and market-side callers assume the returned tuple reflects "now."

Critically, `market.clar`'s own caching layer explicitly documents an expectation that `accrue`/`vault-accrue` returns *fresh* interest-adjusted indexes for the current `stacks-block-time`, and caches that value for the rest of the transaction: [4](#0-3) 
```clarity
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

Because `vault-accrue` (the vault's `accrue`) never signals failure when paused, `market.clar` caches the *stale* index for the block and uses it for every health check, notional valuation, debt-scaling and liquidation computation (`convert-to-scaled-debt`, `resolve-ztoken`, `scale-debt-for-liquidation`, etc.) that runs later in the same or subsequent transactions until the pause is lifted — the pass-through masquerades as a legitimate accrual result rather than reverting the caller, which is exactly the "pause that passes through instead of reverting" analog class.

### Impact Explanation
While `accrue` is paused, interest that should accrue on outstanding debt (`borrow-index`) and to depositors (`lindex`/liquidity index) stops being reflected, yet the vault keeps processing `deposit`, `redeem`, `system-borrow`, and `system-repay` using the frozen index as if it were live. This means:
- New depositors receive shares priced off a stale liquidity index while real yield/interest continues to be owed conceptually, understating or overstating share value relative to what would have accrued.
- Debt taken out or repaid during the pause is scaled with the frozen `index`, permanently losing the interest that should have accrued for depositors during that window — a temporary/permanent freezing of unclaimed yield for liquidity providers, matching the in-scope "temporary freezing of funds"/"theft of unclaimed yield" impact classes, since that interest is never retroactively applied once accrual resumes (the pre-pause index becomes the new baseline and interest for the paused period is simply lost rather than caught up).
- Because `try!` never observes an error, no caller (market, liquidator, depositor) has any on-chain signal that the returned indexes are stale; the pause is completely invisible downstream.

### Likelihood Explanation
This requires the DAO/pause-authority to actually set the `accrue` pause flag via `set-pause-states` on a vault, which is a normal operational lever (e.g., during an incident response or upgrade), not an attacker-controlled or malicious action. It is not a privileged-key compromise in the sense of "leaked keys" — it is the intended pause mechanism failing to behave safely for its stated purpose (pause = stop the vault from behaving as if things are current), and the resulting fund/yield discrepancy is a direct code-logic defect independent of any single malicious actor, occurring naturally any time this admin lever is used.

### Recommendation
Have the paused branch of `accrue` return an error (e.g., `ERR-PAUSED`) instead of `(ok { index: idx, lindex: lidx })`, or have every caller of `accrue` explicitly check `(get accrue states)` and revert with `ERR-PAUSED` before treating the accrual result as current — consistent with how `deposit`/`redeem`/`system-borrow`/`system-repay` already assert `(not (get X states)) ERR-PAUSED)` for their own action flags. Alternatively, if pausing `accrue` while still allowing deposits/borrows is an intentional design choice, ensure the market-side `index-cache` and downstream health/liquidation logic explicitly account for the possibility of stale indexes rather than assuming any `ok` accrual result is fresh.

### Proof of Concept
1. DAO calls `set-pause-states` on `vault-sbtc` (or any vault) with `{ accrue: true, deposit: false, borrow: false, repay: false, redeem: false }` (a legitimate partial-pause configuration since each flag is independent). [5](#0-4) 
2. A user calls `system-borrow` on the vault. `(try! (accrue))` at line 870 hits the `PAUSED` branch and returns `(ok { index: idx, lindex: lidx })` with the last-stored (stale) `index`/`lindex`, without updating `last-update`. [6](#0-5) 
3. `system-borrow` proceeds normally — `idx` (stale) is used to compute `scaled-amount`, funds are sent, and the loan is scaled at the outdated index, even though real elapsed time (and thus real interest) has passed.
4. Concurrently, `market.clar`'s `accrue-and-cache` caches this same stale `{index, lindex}` tuple for `stacks-block-time`, and every collateral valuation / debt notional / liquidation computation for that block uses the frozen values. [4](#0-3) 
5. When the pause is lifted, `next-index`/`next-liquidity-index` computation resumes from the old `last-update` timestamp, but the interest that should have compounded for depositors during the paused interval is never separately recovered — depositors have permanently lost yield relative to a correctly-functioning (or correctly-reverting) accrual path.
