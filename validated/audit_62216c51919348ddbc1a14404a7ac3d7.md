### Title
Non-differential total resource weight update in `FreezeBalanceProcessor` desyncs global bandwidth/energy accounting from actual frozen funds - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java`)

### Summary
The external report describes a vault where the accounting value used for `totalAssets()` can diverge from where the funds actually are, corrupting deposit/mint/redeem share-price math. The closest reachable analog in java-tron is the resource-staking subsystem: `DynamicPropertiesStore`'s `TotalNetWeight`/`TotalEnergyWeight` act as the "total assets" denominator used to compute the bandwidth/energy price (`totalNetLimit / TotalNetWeight`) for every account, while the real backing "funds" are each account's frozen-TRX fields (`AccountCapsule` frozen balances). `FreezeBalanceProcessor`, invoked from the TVM `freeze()` opcode (`Program.java:1916`), updates the global weight with a plain, non-differential addition instead of the old/new-diff pattern used everywhere else in the codebase, which can desynchronize the global counter from the real per-account frozen balances.

### Finding Description
Every other freeze/unfreeze code path in the codebase (actuator and native contract) computes the account's own weight before and after the state change and applies only the *difference* to the global counter, explicitly to absorb integer-division truncation from `TRX_PRECISION`: [1](#0-0) [2](#0-1) [3](#0-2) 

`FreezeBalanceProcessor.execute()` (the V1 freeze path reachable via the TVM native `freeze()` instruction) instead directly adds the newly frozen amount divided by `TRX_PRECISION` to the global weight, without computing an old/new diff of the account's total frozen balance: [4](#0-3) 

Because Java integer division truncates, an account's locally-tracked frozen balance is priced in whole `TRX_PRECISION` units via floor division (e.g. `accountCapsule.getFrozenBalance() / TRX_PRECISION`), while the global counter here is incremented by `frozenBalance / TRX_PRECISION` computed from the newly added delta alone. When an account already holds a sub-`TRX_PRECISION` remainder from a previous freeze (which contributed 0 to its own weight due to truncation), a subsequent small freeze that pushes the total across a `TRX_PRECISION` boundary is not reflected correctly in the global total, because the increment is derived from the delta, not from `(newTotalWeight - oldTotalWeight)` for that account. Repeated micro-freezes/unfreezes through this native-contract path (attacker-controlled amounts, freely invocable by any TVM contract) can therefore make `TotalNetWeight`/`TotalEnergyWeight` drift out of sync with the sum of the real per-account frozen weights that back it — analogous to the reported bug where the ledger used for the "total assets" calculation no longer matches where the real funds actually sit.

A similar comment left in the sibling `UnfreezeBalanceProcessor.java` ("adjust total resource, used to be a bug here") confirms this exact class of desynchronization has been a recurring problem area in this subsystem: [5](#0-4) 

### Impact Explanation
`TotalNetWeight`/`TotalEnergyWeight` are chain-wide denominators used to compute every account's bandwidth/energy allowance from `getTotalNetLimit()`/`getTotalEnergyCurrentLimit()`. A permanent drift in this global counter (relative to the true aggregate of per-account frozen weights) systematically mis-prices free resources for all accounts network-wide — some accounts get more bandwidth/energy than their stake entitles them to, others get less. This is a resource/reward accounting corruption analogous to the reported "share price" corruption, reachable purely through repeated TVM contract calls (no privileged actor required).

### Likelihood Explanation
Likelihood is Low, matching the original report's rating: the drift only manifests when an account's cumulative frozen balance crosses a `TRX_PRECISION` (1,000,000 sun) boundary via many small `freeze()` calls through the V1 TVM native-contract freeze path specifically (not the V2 or actuator paths, which use the correct diff pattern), and each single drift unit is at most 1 weight unit (1 TRX) — requiring sustained, deliberate exploitation to accumulate a materially significant deviation.

### Recommendation
Change `FreezeBalanceProcessor.execute()` to use the same old/new differential pattern already used in `FreezeBalanceV2Processor`/`UnfreezeBalanceV2Processor`/`FreezeBalanceActuator` — compute `accountCapsule.getFrozenBalance()/TRX_PRECISION` before and after applying the frozen-balance change, and add only the difference to `TotalNetWeight`/`TotalEnergyWeight`, instead of adding `frozenBalance / TRX_PRECISION` directly.
