### Title
Relayer fee is paid unconditionally before the emulated transfer/action's success is known, letting a relayer drain a wallet-contract's NEAR balance via repeated failing transactions - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` → `inner_rlp_execute` computes a relayer `fee` for `EOABaseTokenTransfer` and `ERC20Transfer` emulation kinds and fires an independent `Transfer` promise to the `predecessor_account_id` (the relayer) *before* the promise that performs the actual requested action (base token transfer or NEP-141 `ft_transfer`) is created and *without ever checking the result of that action*. The fee-payment promise is not chained (`.then()`) to the outcome of the underlying transfer/ERC-20 action, so it always executes and always succeeds independently of whether the user's intended transfer/action succeeds or fails.

### Finding Description
In `inner_rlp_execute`: [1](#0-0) 

the code does:
```rust
if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
    env::promise_batch_action_transfer(refund_promise, *fee);
}
```
This creates a brand-new, independent batch promise that transfers `fee` yoctoNEAR out of the wallet contract's own balance to the relayer (`predecessor_account_id`). This happens unconditionally right after successfully *parsing* the RLP transaction, before the promise for the actual action (`action_to_promise` / the NEP-141 `storage_balance_of` → `storage_deposit` → `ft_transfer` chain) is even constructed: [2](#0-1) 

Crucially, unlike the caller's own attached deposit (tracked via `CallerDeposit` and refunded on failure in `rlp_execute_callback`, see the `PromiseResult::Failed` branch): [3](#0-2) 

the relayer fee transfer has no such safeguard. There is no result check tying the fee payment to the success of the emulated transfer. The comment in `internal.rs` documents the intent ("Relayers should also verify the fee before sending...") but this is only advisory, not enforced on-chain: [4](#0-3) 

This is the direct analog of the reported Solidity issue: an external value transfer (here, the fee `Transfer` action) is dispatched without checking/gating on the success of the associated operation it is supposed to compensate for (the base-token transfer or `ft_transfer`), enabling silent loss of the account owner's funds.

### Impact Explanation
A relayer (an unprivileged party that merely needs to be able to submit transactions/receipts calling `rlp_execute`, i.e., a "meta-transaction sender"/RPC caller — not a validator or node) can repeatedly submit RLP transactions that are guaranteed or designed to fail the underlying action (e.g., an `ERC20Transfer` to a receiver where `ft_transfer` will revert due to insufficient token balance, or a base-token `Transfer` to a target that does not satisfy `check_account_existence`) while still collecting the `fee` on every attempt, since the fee-payment promise executes and succeeds independently of the failing action. Each failed attempt still increments the nonce (nonce increments happen at parse time for these emulation kinds, before knowing whether the downstream promise succeeds), so a malicious relayer can drain the wallet-contract account's real NEAR balance one `fee` at a time with transactions that do nothing useful for the user. This is unauthorized value movement out of the user's account balance triggered by a submitted transaction, matching the required "concrete unauthorized value movement" impact criterion.

### Likelihood Explanation
This is trivially reachable: any account controlling (or colluding with) the relayer role can invoke `rlp_execute` with a target/receiver_id that is engineered to make `ft_transfer` or the base-token transfer fail deterministically (e.g., zero token balance on the wallet for the `ERC20Transfer` path, or an account that fails `check_account_existence`), and the fee is still paid every single call as shown by the fee-refund construction preceding the actual action's promise. No validator, node, or network-layer compromise is required — only the ability to submit `rlp_execute` calls as (or via) a relayer, which is the wallet contract's normal operating model.

### Recommendation
Chain the relayer fee payment to the outcome of the underlying action instead of firing it independently — e.g., only issue the fee `Transfer` from within/after `rlp_execute_callback` conditioned on `PromiseResult::Successful`, or make the fee transfer part of the same batch/receipt as the action so that a failure of the main action also fails (and thus refunds) the fee transfer.

### Proof of Concept
1. Deploy a wallet contract and fund it with NEAR.
2. Mint some NEP-141 token to the wallet's account but leave the balance below what is needed for repeated `ERC20Transfer` emulations to a receiver, or simply target a receiver_id engineered so `ft_transfer` will fail (e.g., insufficient token balance, since `ft_transfer` calls with amount greater than balance fail).
3. As the relayer (predecessor), repeatedly call `rlp_execute` with an `ERC20Transfer` (or `EOABaseTokenTransfer`) transaction carrying a non-zero `max_fee_per_gas * gas_limit`-derived `fee` (see `internal::parse_rlp_tx_to_action`, lines 54-64 of `internal.rs`) and a target/transfer designed to fail.
4. Observe that on every call the wallet's NEAR balance decreases by `fee` (paid to the relayer) as shown by test `test_base_token_transfer_with_relayer_refund` and `test_erc20_emulation` demonstrating the unconditional relayer-refund transfer, even though in this crafted scenario the underlying action always fails and `rlp_execute_callback` reports `success: false`. // Relayers are paid for base token transfers.
#[tokio::test]
async fn test_base_token_transfer_with_relayer_refund() -> anyhow::Result<()> {
    const TRANSFER_AMOUNT: NearToken = NearToken::from_near(2);
    const RELAYER_REFUND: NearToken = NearToken::from_millinear(1);
    const GAS_LIMIT: u64 = 100_000;

    let TestContext { worker, wallet_contract, wallet_sk, wallet_contract_bytes, .. } =
        TestContext::new().await?;

    let relayer = worker.root_account()?;

    let (other_wallet, other_address) =
        TestContext::deploy_wallet(&worker, &wallet_contract_bytes).await?;

    let initial_relayer_balance = relayer.view_account().await?.balance;
    let initial_wallet_balance = wallet_contract.inner.as_account().view_account().await?.balance;
    let initial_other_balance = other_wallet.inner.as_account().view_account().await?.balance;

    let transaction = aurora_engine_transactions::eip_2930::Transaction2930 {
        nonce: 0.into(),
        gas_price: (RELAYER_REFUND.as_yoctonear()
            / ((GAS_LIMIT as u128) * (MAX_YOCTO_NEAR as u128)))
            .into(),
        gas_limit: GAS_LIMIT.into(),
        to: Some(Address::new(other_address)),
        value: Wei::new_u128(TRANSFER_AMOUNT.as_yoctonear() / u128::from(MAX_YOCTO_NEAR)),
        data: Vec::new(),
        chain_id: CHAIN_ID,
        access_list: Vec::new(),
    };
    let signed_transaction = crypto::sign_transaction(transaction, &wallet_sk);

    let result = wallet_contract
        .rlp_execute_from(
            &relayer,
            other_wallet.inner.id().as_str(),
            &signed_transaction,
            NearToken::from_yoctonear(0),
        )
        .await?;

    assert!(result.success);

    let final_relayer_balance = relayer.view_account().await?.balance;
    let final_wallet_balance = wallet_contract.inner.as_account().view_account().await?.balance;
    let final_other_balance = other_wallet.inner.as_account().view_account().await?.balance;

    // Receiver balance increases
    assert_eq!(
        final_other_balance.as_yoctonear(),
        initial_other_balance.as_yoctonear() + TRANSFER_AMOUNT.as_yoctonear()
    );

    // Wallet balance decreases (round to milliNEAR to account for funds
    // received for calling the contract).
    assert_eq!(
        final_wallet_balance.as_millinear(),
        initial_wallet_balance.as_millinear()
            - TRANSFER_AMOUNT.as_millinear()
            - RELAYER_REFUND.as_millinear()
    );

    // Relayer balance stays the same (rounded to the nearest milliNEAR) since the
    // wallet refunded the relayer approximately equal to the transaction gas cost.
    assert_eq!(final_relayer_balance.as_millinear(), initial_relayer_balance.as_millinear());

    Ok(())
}
