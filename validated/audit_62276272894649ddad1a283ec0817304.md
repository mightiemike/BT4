### Title
Failed re-mint during outbound revert permanently freezes user funds with no recovery path - (File: x/uexecutor/keeper/outbound.go)

### Summary
When an outbound fails and the module attempts to revert bridged funds by re-minting PRC20 tokens to the original sender/recipient, a failure of that re-mint call causes the outbound to be marked `ABORTED` with no automated or user-reachable path to ever recover the funds, mirroring the reported bug class of funds becoming inaccessible once a particular state (here, `ABORTED`) is reached instead of a recoverable one (`REVERTED`).

### Finding Description
In `handleFailedOutbound`, when an outbound of type `FUNDS`, `GAS_AND_PAYLOAD`, or `FUNDS_AND_PAYLOAD` fails on the destination chain, the keeper tries to re-mint the bridged PRC20 tokens back to the revert recipient via `CallPRC20Deposit`: [1](#0-0) 

If that re-mint call errors, the outbound is marked `ABORTED` via `AbortOutbound` rather than `REVERTED`: [2](#0-1) 

`AbortOutbound` sets `Status_ABORTED`, records the reason, removes the entry from `PendingOutbounds`, and only emits a monitoring event — it does not create any UTX mutation that could be retried automatically: [3](#0-2) 

The only automated fund-recovery mechanism in this module is `AttachRescueOutboundFromReceipt`, which explicitly requires either (a) a CEA inbound whose first `PcTx` (deposit) `Status == "FAILED"`, or (b) a non-CEA inbound with an `INBOUND_REVERT` outbound whose `OutboundStatus == types.Status_REVERTED`: [4](#0-3) 

An `ABORTED` outbound satisfies neither condition — it is not `REVERTED`, so `hasRevertedAutoRevert` stays `false` and rescue is rejected with `"rescue: UTX %s has no reverted inbound-revert outbound"`. The `AbortOutbound` doc comment itself confirms the state is a dead end: "This signals that automatic processing has failed and manual intervention is needed," and the `Status` table in the README labels `ABORTED` as needing "manual intervention" with no protocol-level retry path documented or implemented: [5](#0-4) 

The same unrecoverable pattern also exists in `applyGasRefund`: if both the swap-based and no-swap fallback calls to `CallUniversalCoreRefundUnusedGas` fail, `refundPcTx.Status` is simply set to `"FAILED"` and stored in `outbound.PcRefundExecution`, with no retry mechanism or rescue eligibility tied to a failed gas refund: [6](#0-5) 

This mirrors the external report's core issue: funds are conceptually meant to be recoverable (paid out via a rescue/payout-like mechanism), but the actual code path that would trigger recovery (`RESCUE_FUNDS` eligibility) checks for a specific narrow state (`REVERTED`) that the failure path (`ABORTED`) never reaches — leaving user funds permanently stuck exactly like the `PayoutManager` funds that were never sent and could only be withdrawn in a narrow window.

### Impact Explanation
Funds that fail to re-mint during a revert (e.g., a transient EVM/PRC20 call failure, gas estimation issue, or any transactional error inside `CallPRC20Deposit`) become permanently frozen — no user, validator, or admin-facing message in the reachable module surface can move the `ABORTED` outbound back into a recoverable state, and rescue funds logic strictly excludes `ABORTED`. This constitutes permanent freezing of protocol/user-controlled funds, matching the "High Impact" classification in the source report.

### Likelihood Explanation
Likelihood is High because the trigger condition (a `CallPRC20Deposit` re-mint call failing) is on the ordinary failed-outbound path that any external chain's outbound execution failure can hit — it requires no privileged actor, just an outbound that both fails destination-chain execution AND fails its automatic PC-side re-mint (e.g., due to insufficient gas token liquidity in module account, a reverted contract call, or any evm.go error surfaced through `DerivedEVMCall`). This is fully reachable from ordinary, unprivileged user deposit/withdrawal flows.

### Recommendation
Extend rescue eligibility in `AttachRescueOutboundFromReceipt` to also accept outbounds in `Status_ABORTED` (in addition to `Status_REVERTED`) so that funds stuck due to a failed re-mint attempt can still be recovered via the `RESCUE_FUNDS` flow. Alternatively, introduce an explicit governance- or admin-gated (but scoped) retry message that re-attempts the `CallPRC20Deposit` re-mint for `ABORTED` outbounds, transitioning them to `REVERTED` on success so the standard rescue path becomes available. The same fix should be applied for `PcRefundExecution.Status == "FAILED"` gas-refund cases, since they currently have no analogous rescue path at all.

### Proof of Concept
1. A `FUNDS` inbound completes and triggers an outbound to a destination chain.
2. UVs vote `MsgVoteOutbound` with `success = false`, driving `FinalizeOutbound` → `handleFailedOutbound`.
3. Simulate `CallPRC20Deposit` failing (e.g., insufficient PRC20 balance/allowance in module account, or a reverted precompile call) — the outbound is marked `Status_ABORTED` with `AbortReason = "failed to re-mint tokens for revert: ..."`.
4. Attempt to call `AttachRescueOutboundFromReceipt` for this UTX with a valid `RescueFundsOnSourceChain` event/log; observe it returns `"rescue: UTX %s has no reverted inbound-revert outbound"` because the outbound is `ABORTED`, not `REVERTED`.
5. Confirm there is no other reachable message/keeper method that transitions an `ABORTED` outbound to any recoverable state — the funds (never re-minted on Push Chain, and already consumed/failed on the destination side) are permanently unrecoverable through any user- or validator-facing flow.

// AbortOutbound marks an outbound as ABORTED with a reason.
// This signals that automatic processing has failed and manual intervention is needed.
func (k Keeper) AbortOutbound(ctx context.Context, utxId string, outbound types.OutboundTx, reason string) error {
	sdkCtx := sdk.UnwrapSDKContext(ctx)

	outbound.OutboundStatus = types.Status_ABORTED
	outbound.AbortReason = reason

	if err := k.UpdateOutbound(ctx, utxId, outbound); err != nil {
		return err
	}

	// Defensively remove from pending index (may already be removed by caller)
	_ = k.PendingOutbounds.Remove(ctx, outbound.Id)

	// Emit event for monitoring/alerting
	sdkCtx.EventManager().EmitEvent(sdk.NewEvent(
		"outbound_aborted",
		sdk.NewAttribute("utx_id", utxId),
		sdk.NewAttribute("outbound_id", outbound.Id),
		sdk.NewAttribute("abort_reason", reason),
	))

	return nil
}
