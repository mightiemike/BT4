Based on my investigation, I found a genuine, code-documented integrity gap in the replay-verification path, distinct from (but analogous in spirit to) the ERC-6909 bug: a verification function that is supposed to attest an output matches a "trusted" record silently skips the most important field.

### Title
`TransactionOutput::ensure_match_transaction_info` never verifies the state-root (checkpoint) hash, letting replay-verify tools accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function that replay/debugging tools use to confirm a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on an archive/ledger. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that actually commit to the global state Merkle root.

### Finding Description
`ensure_match_transaction_info` computes and compares `write_set_hash` against `txn_info.state_change_hash()` and `event_root_hash` against `txn_info.event_root_hash()`, but there is no comparison at all for `txn_info.state_checkpoint_hash()` (or the hot-state/position variants): [1](#0-0) 

This is acknowledged directly in the source as a TODO: [2](#0-1) 

`state_checkpoint_hash` is the Jellyfish Merkle Tree root committing to the entire post-transaction global state — the single most security-critical value in a `TransactionInfo` besides the write-set hash. Skipping it means a mismatch between the locally-computed state root and the archived, ledger-info-anchored root is undetectable by this comparator.

This function is called directly by tooling whose entire purpose is proof/replay integrity checking:
- `storage/db-tool/src/replay_on_archive.rs`
- `aptos-move/cli/src/commands.rs`
- `aptos-move/aptos-debugger/src/aptos_debugger.rs`
- `execution/executor/src/chunk_executor/mod.rs`

By contrast, the primary chunk-executor consensus/state-sync commit path additionally validates via `ensure_transaction_infos_match`, which operates on full `TransactionInfo` hashes (and therefore does implicitly cover the checkpoint hash) — see the accumulator-anchored check used in `StateSyncChunkVerifier::verify_chunk_result`: [3](#0-2) 

So the gap is scoped specifically to standalone callers of `ensure_match_transaction_info` (debugger/replay-verify/CLI paths), not the core consensus commit path.

### Impact Explanation
Tools like `db-tool replay_on_archive` and `aptos-debugger` exist specifically so operators/auditors can replay historical transactions against an archive and detect any divergence from the authenticated on-chain execution result (e.g., after a VM/storage upgrade, to catch a hard-fork-only non-determinism bug before it reaches mainnet consensus). Because the state-root/checkpoint hash is never compared, a state-computation bug that produces the *correct* write set and events but a *wrong* Merkle state root (e.g., due to a JMT computation bug, a hot-state or the new "trading native"/position-state root bug) would be reported as a **successful, matching replay**, even though the state root is corrupted. This directly undermines a proof/commitment-integrity guarantee the tool is supposed to provide, and is explicitly the scenario called out for the new `COMPUTE_TRADING_NATIVE_STATE_ROOTS` position-state root, but the same reasoning applies to the long-standing `state_checkpoint_hash` and `hot_state_checkpoint_hash`, which are also unchecked.

### Likelihood Explanation
This is not a bug that occurs by chance — it is a deterministic code omission (confirmed by the developer's own TODO). It fires whenever any caller relies on `ensure_match_transaction_info` for an end-to-end correctness assertion, and any of the four call sites listed above do exactly that. The exposure is currently limited to offline/replay/debugging tooling rather than the live consensus commit path (which is separately protected by the accumulator-hash comparison in `ensure_transaction_infos_match`), so it is not an on-chain-exploitable divergence by itself, but it does defeat the safety net meant to catch a hard-fork-causing state-root divergence before/while it happens.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled) `position_state_checkpoint_hash` against the corresponding fields on the locally-computed side, erroring out on any mismatch, exactly as is already done for `state_change_hash` and `event_root_hash`.

### Proof of Concept
Not applicable as an on-chain exploit PoC — this is a tooling/verification-logic gap rather than a state-corruption primitive reachable by an unprivileged transaction. The "proof" is the source code itself: compare the fields checked in `ensure_match_transaction_info` (lines 2168–2195) against the fields defined on `TransactionInfo` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash`) and the TODO comment (lines 2197–2202) which explicitly states the checkpoint hashes are ignored, together with confirming the four production call sites (`replay_on_archive.rs`, `commands.rs`, `aptos_debugger.rs`, `chunk_executor/mod.rs`) that rely on this function for correctness verification.

**Caveat / uncertainty:** I was not able to fully trace, within the available tool budget, exactly how `chunk_executor/mod.rs`'s call to `ensure_match_transaction_info` interacts with the earlier accumulator-based `ensure_transaction_infos_match` check in the same commit flow (i.e., whether the latter runs first and would already catch the divergence, making the former redundant-but-incomplete rather than a standalone gap in that specific path). This should be verified with a Devin session that can trace the full call graph and, ideally, add a unit test that deliberately corrupts a state-checkpoint hash and confirms whether `replay_on_archive`/`aptos-debugger` currently fail to detect it.

impl ChunkResultVerifier for StateSyncChunkVerifier {
    fn verify_chunk_result(
        &self,
        parent_accumulator: &InMemoryTransactionAccumulator,
        ledger_update_output: &LedgerUpdateOutput,
    ) -> Result<()> {
        // In consensus-only mode, we cannot verify the proof against the executed output,
        // because the proof returned by the remote peer is an empty one.
        if cfg!(feature = "consensus-only-perf-test") {
            return Ok(());
        }

        THREAD_MANAGER.get_exe_cpu_pool().install(|| {
            let first_version = parent_accumulator.num_leaves();

            // Verify the chunk extends the parent accumulator.
            let parent_root_hash = parent_accumulator.root_hash();
            let num_overlap = self.txn_infos_with_proof.verify_extends_ledger(
                first_version,
                parent_root_hash,
                Some(first_version),
            )?;
            assert_eq!(num_overlap, 0, "overlapped chunks");

            // Verify transaction infos match
            ledger_update_output
                .ensure_transaction_infos_match(&self.txn_infos_with_proof.transaction_infos)?;

            Ok(())
        })
    }
