### Title
Missing Slippage Protection in `ExchangeInjectActuator` / `ExchangeWithdrawActuator` Enables Front-Running/Sandwich Attacks on TRON's Built-in Bancor-style Exchange - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
TRON's native token exchange (`ExchangeInjectContract` / `ExchangeWithdrawContract`) lets any account inject or withdraw liquidity from a bonding-curve pool. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced at execution time, the inject/withdraw contracts provide **no minimum/maximum bound on the counter-token amount**. The counter-token amount is computed from the pool ratio that exists *at the moment the transaction executes on-chain*, not the ratio the user observed when signing. This is the same class of bug as the reported issue: a swap/liquidity operation is executed against a live pool ratio with no caller-supplied slippage bound, letting a third party manipulate the ratio immediately before the victim's transaction lands (front-running/sandwiching) to force the victim to give up more value than intended.

### Finding Description
`ExchangeInjectActuator.execute()` computes `anotherTokenQuant` purely from the current on-chain pool balances at execution time: [1](#0-0) 

There is no field in the contract or validation logic constraining `anotherTokenQuant` to a value the user pre-approved — the proto message only carries `owner_address`, `exchange_id`, `token_id`, and `quant`: [2](#0-1) 

The same pattern exists in `ExchangeWithdrawActuator.execute()`, where `anotherTokenQuant` (the amount the withdrawer receives back) is likewise derived from the live pool ratio with no user-specified minimum-out: [3](#0-2) [4](#0-3) 

By contrast, `ExchangeTransactionActuator` (the actual swap function) *does* enforce a user-supplied `expected` value and reverts if the pool state moved unfavorably: [5](#0-4) 

This shows the codebase already recognizes the need for slippage protection for swaps, but omitted the equivalent protection for inject/withdraw, which is exactly the "slippage mishandling" bug class described in the report: an operation whose realized exchange rate is determined at execution time with no bound the caller can enforce.

Any account can permissionlessly move the pool ratio via a broadcast `ExchangeTransactionContract` immediately before a victim's pending `ExchangeInjectContract`/`ExchangeWithdrawContract` is packed into a block (front-running via mempool observation or same-block ordering by the block producer), then reverse the trade afterward (back-run) to restore the ratio and pocket the difference — a classic sandwich attack against liquidity providers.

### Impact Explanation
- For `ExchangeInjectActuator`: the victim can be forced to give up a manipulated (larger) amount of the counter-token than the ratio they observed, while `firstTokenBalance`/`secondTokenBalance` used for the actual balance debit are recomputed at execution time from the attacker-manipulated ratio. [6](#0-5) 
- For `ExchangeWithdrawActuator`: the victim can receive a manipulated (smaller) amount of the counter-token back than expected when the ratio has been artificially skewed just before execution. [7](#0-6) 

This is direct, quantifiable asset loss for depositors/liquidity providers in the built-in exchange, reachable by any address broadcasting an ordinary transaction — no privileged role required.

### Likelihood Explanation
The TRON native Exchange (Bancor-formula AMM) is a long-standing, still-present, unprivileged feature reachable by any account via `wallet/exchangeinject`, `wallet/exchangewithdraw`, and `wallet/exchangetransaction` HTTP/gRPC endpoints and broadcast transactions. Executing a front-run/back-run against a pending transaction only requires observing the mempool or being (or colluding with) the block producer packing the block — a realistic capability on any live network. Because there is zero on-chain slippage check for inject/withdraw, the attack is deterministic once the attacker can order their transactions around the victim's.

### Recommendation
Add a caller-specified minimum (`expected_another_token_quant` for inject/withdraw) analogous to the `expected` field already used in `ExchangeTransactionContract`, and validate it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` before mutating balances — reverting the transaction if the computed `anotherTokenQuant` violates the user's bound, exactly mirroring the check in `ExchangeTransactionActuator`: [5](#0-4) 

### Proof of Concept
1. Exchange pool holds `firstTokenBalance = 1,000,000 A`, `secondTokenBalance = 1,000,000 B`.
2. Victim signs `ExchangeInjectContract{token_id=A, quant=10,000}` expecting to inject roughly `10,000 B` as the counter-token, based on the ratio they observed off-chain.
3. Attacker front-runs with an `ExchangeTransactionContract` swap that shifts the pool ratio drastically (e.g., dumps B into the pool, or the reverse), so that by the time the victim's inject executes, `anotherTokenQuant = secondTokenBalance * quant / firstTokenBalance` (computed in `ExchangeInjectActuator.execute()`) resolves to a much larger `B` amount than the victim intended. [8](#0-7) 
4. The victim's account is debited this larger, attacker-manipulated `anotherTokenQuant` with no revert path, since no `expected`/minimum bound exists in the contract or actuator logic.
5. Attacker back-runs to restore the original ratio, extracting the value the victim was forced to overpay. The identical mechanism applies in reverse for `ExchangeWithdrawActuator`, where the victim can be made to receive less `anotherTokenQuant` than the pre-attack ratio implied.
