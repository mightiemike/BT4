## Title
Integer-division truncation in `grow_index` can leave AccountsIndex on-disk bucket capacity effectively frozen, causing repeated failed reindex attempts / CPU burn under growth pressure - (File: bucket_map/src/bucket.rs)

### Summary
`grow_index` in `bucket_map/src/bucket.rs` computes the new bucket capacity as `(current_capacity * 110 / 100).max(anticipated_size)` [1](#0-0)  to decide how much to grow an accounts-index on-disk bucket by. Because this is done with integer arithmetic, for any `current_capacity` where `current_capacity < 10`, `current_capacity * 110 / 100` truncates back down to exactly `current_capacity` (e.g. `9 * 110 / 100 == 9`). This mirrors the report's bug class: a ratio/multiplier applied via integer division that, for small operand values, truncates to a no-op result instead of the intended proportional increase.

### Finding Description
`grow_index` is only entered when `self.index.contents.capacity() == current_capacity`, i.e. it is specifically invoked because an insert failed due to insufficient index-bucket capacity [2](#0-1) . The intent of the `* 110 / 100` factor is to guarantee the new capacity is materially larger than the old one so that the subsequent reindex ("rehash all existing entries into the new bucket") succeeds and future growth converges quickly. `DEFAULT_CAPACITY_POW2` is `5` (i.e. an initial capacity of `32`) [3](#0-2) , so the very first several grow attempts from a small starting capacity are safe. However, once a bucket has been reduced to a smaller size (e.g. via reallocation, restart-time restore, or a deliberately small anticipated size), or when `anticipated_size` (via `set_anticipated_count`) is `0` or very small, the loop can compute `new_capacity == current_capacity`:

```
let anticipated_size = self.anticipated_size * 140 / 100;
loop {
    let new_capacity = (current_capacity * 110 / 100).max(anticipated_size);
    ...
    current_capacity = index.capacity(); // if allocator gives back exactly what was requested, unchanged
    ...
    if new_ix.is_err() { valid = false; break; } // reindex fails again because capacity did not grow
}
``` [4](#0-3) 

If the allocator returns a bucket with capacity equal to what was requested (which is the common case since `Capacity::Actual` is only bumped up to fill a page boundary, and small element counts routinely fit within a single page without being rounded up further) [5](#0-4) , then `current_capacity` after the failed attempt is unchanged from before, and the next loop iteration recomputes the exact same (truncated) `new_capacity`. The loop has no upper bound on `count` and no fallback strategy (e.g. `current_capacity + 1`, or rounding up on multiplication) to guarantee forward progress; it will spin indefinitely, burning CPU inside a lock/measurement scope (`Measure::start("grow_index")`), while any thread waiting on that bucket's write lock is blocked.

This directly parallels the reported bug class: a proportional/interest-like growth calculation performed via truncating integer division silently collapses to "no change" for small magnitudes, defeating the intended monotonic progression and enabling a degenerate, exploitable state.

### Impact Explanation
This lives in the AccountsDb on-disk `AccountsIndex` bucket-map growth path (`bucket_map/src/bucket.rs`), which is explicitly in scope (bucket map, part of AccountsDB storage and index). If `grow_index` becomes stuck, any validator using disk-backed index (`IndexLimit::Minimal`/`Threshold`) processing accounts that hash into the affected bin experiences unbounded CPU consumption on that thread while holding the bucket's write lock (acquired by the caller before invoking `grow`), which can stall account inserts/lookups against that bin and produce disproportionate CPU cost — one of the explicitly accepted impact categories.

### Likelihood Explanation
Triggering requires the disk index to reach a state where a bucket's capacity is small and the anticipated-size hint is also small/zero when a resize is attempted — this is possible on validators configured with `--accounts-index-memory-limit-mb`/disk-backed index modes under normal operation (not a malicious-snapshot or bootstrap-only scenario), since bucket capacities can shrink relative to bins after restart-config reuse (`load_on_restart`) and `anticipated_size` defaults to `0` unless explicitly set via `set_anticipated_count`. Because the trigger depends on internal allocator rounding behavior (whether `Capacity::Actual` returns exactly the requested count), it is not fully deterministic from the outside, which is why this should be treated with caution rather than certainty.

### Recommendation
Guarantee forward progress in the growth calculation, independent of `current_capacity`'s magnitude:
```rust
let new_capacity = current_capacity
    .saturating_add((current_capacity / 10).max(1))
    .max(current_capacity + 1)
    .max(anticipated_size);
```
i.e. always add at least 1 (or better, round the `* 110 / 100` up rather than truncating down), and additionally bound the retry loop / assert that `new_capacity > current_capacity` before proceeding, to fail fast (panic/log) rather than spin forever if the allocator ever returns a bucket that isn't actually larger.

### Proof of Concept
Not runnable in this environment; the following demonstrates the truncation defect purely arithmetically, mirroring the reported PToken bug:
```rust
for current_capacity in 1u64..10 {
    let anticipated_size = 0u64; // e.g. set_anticipated_count never called with a nonzero value
    let new_capacity = (current_capacity * 110 / 100).max(anticipated_size);
    assert_eq!(new_capacity, current_capacity); // "growth" that grows nothing
}
```
This shows that for `current_capacity` in `1..=9`, the "10% growth" factor used in `bucket_map/src/bucket.rs:696` truncates to the original value, so `grow_index`'s reindex-and-retry loop can be entered with a `new_capacity` identical to the capacity that already failed to hold the index, precisely analogous to the reported `principal * ratio == principal` truncation.
