### Title
Unbounded, unde-duplicated growth of the per-shop session-id list in `KVSessionStorage` enables storage-quota/DoS griefing - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.storeSession` unconditionally appends the session id to a per-shop index list on every call, with no de-duplication and no pruning, unlike the sibling `RedisSessionStorage` implementation which explicitly checks for an existing entry before appending.

### Finding Description
`storeSession` calls `addShopIds(session.shop, [session.id])` on every store, and `addShopIds` blindly concatenates the new id(s) onto whatever is already stored, with no check for whether that id is already present: [1](#0-0) [2](#0-1) 

Compare this to `RedisSessionStorage.addKeyToShopList`, which explicitly guards against duplicate insertion (`if (!idKeysArray.includes(idKey))`) before pushing: [3](#0-2) 

Because `storeSession` is re-invoked every time a session is re-persisted — for example each time an app re-derives/refreshes an offline or online token via `tokenExchange` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`) and the resulting session is written back through `sessionStorage.storeSession` in the remix/react-router `token-exchange` strategy and `ensure-offline-token-is-not-expired` helper — the *same* session id (e.g., the deterministic offline session id `offline_<shop>`) is pushed into the shop's KV list again and again. Nothing in `addShopIds` removes duplicates or old/expired ids; the array is read (`namespace.get`), concatenated, and rewritten (`namespace.put`) in full on every single `storeSession` call.

This mirrors the report's structural bug class exactly: an unconditional, append-only record generated by an ordinary, repeatable action (session persistence via token exchange) that is never pruned or deduplicated, causing the per-key payload — and the cost of reading/parsing/rewriting it — to grow monotonically with every legitimate request cycle.

### Impact Explanation
Every `storeSession` call for a shop must fetch the full historical id list, JSON-parse it, append, JSON-stringify, and write it back — an O(n) cost that grows without bound as the list accumulates duplicate entries from repeated token-exchange/session-refresh cycles. This:
- increases per-request latency and KV read/write costs (write-amplification griefing) for every authenticated request to that shop, and
- risks exceeding the KV value-size limit for the shop's session-index key over time, at which point `storeSession`/`findSessionsByShop` for that shop begins failing, denying the app the ability to persist or discover sessions for the affected shop (an availability failure of the session-storage layer that the OAuth/token-exchange path depends on).

Unlike the Redis implementation (which dedupes), the KV backend has no such safeguard, so any app relying on `@shopify/shopify-app-session-storage-kv` in a normal, non-malicious usage pattern (repeated token exchange on token expiry, which happens automatically per Shopify's recommended embedded-app auth flow) will see this index grow unbounded purely from legitimate traffic, and a malicious/automated caller that intentionally forces repeated re-authentication/token-exchange cycles for a shop can accelerate this growth to a griefing/DoS outcome.

### Likelihood Explanation
High for organic accumulation (every token-exchange refresh reproduces the bug without any attacker action) and readily triggerable at will by any actor who can cause repeated token-exchange calls for a given shop (e.g., a merchant/app installer script hitting endpoints that route through `authenticate.admin` with token exchange enabled), since no privileged access or secret is required — it only depends on the ordinary, unprivileged session-token exchange flow.

### Recommendation
In `KVSessionStorage.addShopIds`, de-duplicate before writing (mirroring `RedisSessionStorage.addKeyToShopList`'s `includes` check), and additionally prune stale/replaced ids for the same logical session slot (e.g., detect and replace rather than append when the id being stored already represents that shop/user's offline or online session) so the per-shop index does not grow with each token-exchange cycle.

### Proof of Concept
Not executed against a live KV namespace, but the code path is directly demonstrable by reading the source:
1. `storeSession(session)` is called for the same `session.id` repeatedly (e.g. once per token-exchange/session-refresh cycle) — see call site in `token-exchange.ts` (`createSession` result is persisted via `sessionStorage.storeSession`).
2. Each call reaches `addShopIds(shop, [session.id])` which does `JSON.stringify([...shopIds, ...ids])` unconditionally — no membership check exists at `kv.ts:75-79`, contrasted with the guarded implementation at `redis.ts:159` (`if (!idKeysArray.includes(idKey))`).
3. Repeating step 1 N times for the same shop/session id yields an id list of length N (all duplicates of the same id) rather than length 1, growing the KV value size linearly with the number of token-exchange calls, with no pruning mechanism anywhere in the class.

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
