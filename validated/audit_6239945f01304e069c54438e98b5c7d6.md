## Title
Governance Proposal Quorum Can Be Trivially Bypassed Due to Integer Truncation and Floating Witness-Set Size - (File: `chainbase/src/main/java/org/tron/core/capsule/ProposalCapsule.java`)

### Summary
Analogous to the RocketDAO issue where proposal acceptance quorum was not tied to a fixed minimum viable membership, java-tron's on-chain governance (`ProposalCapsule`/`ProposalController`) computes the required quorum as a *relative* percentage of the **current** active witness set size rather than an absolute floor. Because the calculation uses integer division, a shrinking active-witness set causes the effective quorum requirement to degrade below the intended 70% threshold, and collapses to **zero approvals required** when the active set is very small.

### Finding Description
The quorum check lives in `ProposalCapsule.hasMostApprovals`: [1](#0-0) 

```java
public boolean hasMostApprovals(List<ByteString> activeWitnesses) {
    long count = this.proposal.getApprovalsList().stream()
        .filter(witness -> activeWitnesses.contains(witness)).count();
    ...
    return count >= activeWitnesses.size() * 7 / 10;
}
```

This is invoked from `ProposalController.processProposal`, which is run periodically during maintenance and decides whether a pending governance proposal (which changes dynamic chain parameters via `ProposalService.process`) becomes `APPROVED` or `DISAPPROVED`: [2](#0-1) 

The `activeWitnesses` list used for the check is **not** fixed at proposal-creation time — it is read fresh from `WitnessScheduleStore` at processing time, and it is populated by `DposService.updateWitness`, which sets the active-witness list to simply be *all* registered witnesses whenever the total witness count is `<= MAX_ACTIVE_WITNESS_NUM` (27): [3](#0-2) 

The root cause is twofold, both mirroring the RocketDAO bug class ("no minimum participation quorum" / quorum computed relative to a membership count that can shrink):

1. **Integer truncation of the 70% threshold.** `activeWitnesses.size() * 7 / 10` uses integer division. For `size = 1`, this evaluates to `0`, meaning `count >= 0` is always true — a proposal is approved with **zero approvals**. For `size = 2`, the threshold truncates to `1` instead of the intended ceiling of `2` (70% of 2 rounds up to 2), silently lowering the real requirement to 50%.
2. **No absolute minimum quorum floor.** Exactly like the RocketDAO defect, there is no check that the active-witness/member set itself meets a minimum viable size before proposals can be processed and take effect — the quorum is purely relative to whatever the current active set happens to be, which can shrink (e.g. on smaller/private/consortium java-tron networks, or during early bootstrap before the full 27-SR set is reached).

The unit test in the repo actually demonstrates the intended 70%-of-27 (=18) approvals path, but never exercises small active-witness-set sizes where the truncation degenerates the quorum: [4](#0-3) 

### Impact Explanation
Any deployment of java-tron (private/consortium chain, testnet, or a mainnet-like chain during early bootstrap) that runs with fewer than the full complement of active witnesses is exposed to a governance-quorum defect: dynamic parameter-change proposals (`ProposalService.process`, invoked from `ProposalController.processProposal`) can be silently approved with far fewer approvals than the documented 70% supermajority — and with **zero** approvals when only a single witness is active. This is a state/accounting-integrity impact: chain-wide dynamic parameters (fees, resource limits, protocol switches, etc.) could be altered without the intended supermajority consensus, directly paralleling the RocketDAO concern that proposals could pass without a real minimum participation quorum.

### Likelihood Explanation
This is deterministic, not probabilistic: it depends solely on the size of the active witness set at proposal-processing time, which is entirely a function of chain configuration/registration count, not of any privileged internal-only condition. Any java-tron-based network configured with a small witness count (common for private/consortium/testing deployments, and structurally true during early genesis bootstrap before 27 witnesses are registered) will always hit truncated or zero quorum thresholds. No special privilege beyond being one of the (few) active witnesses is required to trigger the degenerate case.

### Recommendation
- Replace the truncating relative quorum calculation with a rounded-up computation (e.g., `Math.ceil(activeWitnesses.size() * 0.7)`) so the required approval count never falls below the intended supermajority percentage.
- Enforce an absolute minimum active-witness count (a "minimum viable quorum size") before `ProposalController.processProposal` is allowed to approve/execute proposals, refusing to process (or deferring) proposals if the active witness set falls below that floor — directly addressing the RocketDAO-style recommendation to not accept/execute proposals when membership drops below a minimum threshold.

### Proof of Concept
1. Configure/run a java-tron network (e.g., private/consortium mode) that ends up with a single active witness (`activeWitnesses.size() == 1`), a scenario reachable via genesis config or witness attrition, per `DposService.updateWitness` logic which sets the active set to all registered witnesses when total `<= MAX_ACTIVE_WITNESS_NUM`.
2. Submit a `ProposalCreateContract` to create a governance proposal changing a dynamic parameter (via `ProposalCreateActuator`).
3. Do **not** submit any `ProposalApproveContract` for it.
4. Wait for the maintenance cycle to invoke `ProposalController.processProposals` → `processProposal`, which calls `proposalCapsule.hasMostApprovals(activeWitnesses)`.
5. Because `activeWitnesses.size() == 1`, `1 * 7 / 10 == 0`, so `count (0) >= 0` evaluates `true`; the proposal is marked `APPROVED` and `ProposalService.process` applies the parameter change with zero recorded approvals, confirming the quorum bypass described in `chainbase/src/main/java/org/tron/core/capsule/ProposalCapsule.java:156-168`.

  public boolean hasMostApprovals(List<ByteString> activeWitnesses) {
    long count = this.proposal.getApprovalsList().stream()
        .filter(witness -> activeWitnesses.contains(witness)).count();
    if (count != this.proposal.getApprovalsCount()) {
      List<ByteString> InvalidApprovalList = this.proposal.getApprovalsList().stream()
          .filter(witness -> !activeWitnesses.contains(witness)).collect(Collectors.toList());
      logger.info("InvalidApprovalList:" + getAddressStringList(InvalidApprovalList));
    }
    if (activeWitnesses.size() != MAX_ACTIVE_WITNESS_NUM) {
      logger.info("activeWitnesses size = {}", activeWitnesses.size());
    }
    return count >= activeWitnesses.size() * 7 / 10;
  }

      setDynamicParameters(proposalCapsule);

  @Test
  public void testHasMostApprovals() {
    ProposalCapsule proposalCapsule = new ProposalCapsule(
        Proposal.newBuilder().build());
    proposalCapsule.setState(State.APPROVED);
    proposalCapsule.setID(1);

    List<ByteString> activeWitnesses = Lists.newArrayList();
    for (int i = 0; i < 27; i++) {
      activeWitnesses.add(ByteString.copyFrom(new byte[] {(byte) i}));
    }
    for (int i = 0; i < 18; i++) {
      proposalCapsule.addApproval(ByteString.copyFrom(new byte[] {(byte) i}));
    }

    Assert.assertTrue(proposalCapsule.hasMostApprovals(activeWitnesses));

    proposalCapsule.clearApproval();
    for (int i = 1; i < 18; i++) {
      proposalCapsule.addApproval(ByteString.copyFrom(new byte[] {(byte) i}));
    }

    activeWitnesses.clear();
    for (int i = 0; i < 5; i++) {
      activeWitnesses.add(ByteString.copyFrom(new byte[] {(byte) i}));
    }
    proposalCapsule.clearApproval();
    for (int i = 0; i < 3; i++) {
      proposalCapsule.addApproval(ByteString.copyFrom(new byte[] {(byte) i}));
    }
    Assert.assertTrue(proposalCapsule.hasMostApprovals(activeWitnesses));
  }
