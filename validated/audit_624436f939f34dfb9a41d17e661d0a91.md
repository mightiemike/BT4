### Title
Unchecked `-1` sentinel from `JsonRpcApiUtil.parseEnergyFee()` propagates as a bogus `gasPrice`/`energyUnitPrice` in JSON-RPC transaction receipts and event-plugin triggers - (File: `framework/src/main/java/org/tron/core/services/event/BlockEventGet.java`)

### Summary
`JsonRpcApiUtil.parseEnergyFee(timestamp, energyPriceHistory)` returns a sentinel value of `-1` when it cannot find a matching entry for the given timestamp, analogous to how the referenced Reserve Protocol `price()` function returns a sentinel (`FIX_MAX`) when pricing data is unavailable. Just as `collateralShortfall()` failed to validate that sentinel before using it in arithmetic, `BlockEventGet.getEnergyPrice()` calls `parseEnergyFee` directly and returns the raw result — including `-1` — without any validation or fallback, unlike the only other caller of the same parser, `Wallet.getEnergyFee(long timestamp)`, which explicitly checks `if (energyFee == -1) { energyFee = getEnergyFee(); }`.

### Finding Description
`JsonRpcApiUtil.parseEnergyFee` returns `-1` if no history entry satisfies `timestamp > time` for any entry in the `energyPriceHistory` string: [1](#0-0) 

`Wallet.getEnergyFee(long timestamp)` — used by all JSON-RPC receipt/transaction endpoints (`getTransactionByHash`, `getTransactionReceipt`, `getBlockReceipts`, `BlockResult`) — correctly detects and replaces this sentinel: [2](#0-1) 

However, `BlockEventGet.getEnergyPrice(long blockTime)`, used by the event-plugin trigger pipeline (`getTransactionLogTrigger`), calls the same parser but performs **no validation** of the `-1` sentinel: [3](#0-2) 

The unchecked result is then fed directly into `TransactionLogTriggerCapsule` as `energyUnitPrice` for every transaction in the block: [4](#0-3) 

and stored verbatim into the published event via `setEnergyUnitPrice(energyUnitPrice)`: [5](#0-4) 

Under normal operation the `DEFAULT_ENERGY_PRICE_HISTORY` seed value starts at time `0`, so a well-formed history with `blockTime > 0` should always match an entry. The sentinel is only reachable in corner cases such as: a corrupted/reset `ENERGY_PRICE_HISTORY` dynamic property (e.g., manually reset via a lower-level DB write, migration, or bug in `EnergyPriceHistoryLoader`/`ProposalService` appending malformed entries), or a `blockTime` of `0` or negative (e.g., genesis block, `time <= 0` edge in `parseEnergyFee`'s `timestamp > time` check). This mirrors the acknowledged Reserve Protocol scenario where the sentinel is reachable only in an edge/corner case, but is still a real correctness defect because the consuming code performs no defensive check on the returned value before persisting/broadcasting it.

### Impact Explanation
If reached, downstream consumers of the event-plugin (e.g., off-chain indexers, exchanges computing effective gas cost using `TransactionLogTrigger.energyUnitPrice`) will receive `-1` as the reported energy price for every transaction in the affected block, corrupting fee/accounting data derived from the trigger stream. This is a data-integrity/accounting issue in the node's externally consumed event data rather than a fund-loss vulnerability, and it is limited to the event-plugin trigger pipeline (`BlockEventGet`), not the JSON-RPC-facing `Wallet.getEnergyFee` path, which already guards against it.

### Likelihood Explanation
Low likelihood under normal chain operation, since `ENERGY_PRICE_HISTORY` is seeded with `DEFAULT_ENERGY_PRICE_HISTORY` starting at time `0` and only grows via `ENERGY_FEE` proposals; matching for any positive `blockTime` should normally succeed. It becomes reachable if the stored history string is ever malformed/reset, or for edge-case timestamps, similarly to the corner-case scenario judged Medium severity in the original report.

### Recommendation
In `BlockEventGet.getEnergyPrice(long blockTime)`, mirror the defensive check already present in `Wallet.getEnergyFee(long timestamp)`: if `parseEnergyFee` returns `-1`, fall back to `manager.getDynamicPropertiesStore().getEnergyFee()` (the current base energy fee) instead of propagating the sentinel into `TransactionLogTriggerCapsule`.

### Proof of Concept
1. Force `getDynamicPropertiesStore().getEnergyPriceHistory()` into a state where no entry satisfies `timestamp > time` for the block's timestamp being processed (e.g., corrupt/reset the stored history, or process a block with `timeStamp <= 0`).
2. Call `BlockEventGet.getTransactionLogTrigger(block, solidNum)`, which invokes `getEnergyPrice(block.getTimeStamp())` → `JsonRpcApiUtil.parseEnergyFee(...)` returning `-1`.
3. Observe `TransactionLogTriggerCapsule` is constructed with `energyUnitPrice = -1`, and `TransactionLogTrigger.setEnergyUnitPrice(-1)` is published to any subscribed event plugin/consumer, corrupting reported gas price data — contrast with `Wallet.getEnergyFee(timestamp)` which would never emit `-1` in the equivalent situation.   public static long parseEnergyFee(long timestamp, String energyPriceHistory) {
```java
    String[] priceList = energyPriceHistory.split(",");

    for (int i = priceList.length - 1; i >= 0; i--) {
      String[] priceArray = priceList[i].split(":");
      long time = Long.parseLong(priceArray[0]);
      long price = Long.parseLong(priceArray[1]);
      if (timestamp > time) {
        return price;
      }
    }

    return -1;
  }
```
