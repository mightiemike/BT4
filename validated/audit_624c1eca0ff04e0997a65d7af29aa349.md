## Analysis: DeleteAccountAction beneficiary validation gap (analog to missing `recovery != 0` check)

The external report's core pattern — a user-supplied "destination" address parameter that is syntax-checked but not existence/reachability-checked, so a legitimate but bad value causes permanent, protocol-level fund loss — has a direct analog in nearcore's `DeleteAccountAction`.

### Title
Unvalidated `DeleteAccountAction.beneficiary_id` allows a signer's remaining balance to be permanently burned instead of refunded - (File: `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`DeleteAccountAction` only validates that `beneficiary_id` is a syntactically well-formed `AccountId`; it never checks that the beneficiary account actually exists or can receive the refund. When the beneficiary doesn't exist (or is the very account being deleted), the resulting balance-refund receipt fails and the funds are permanently burned rather than returned to anyone — mirroring the reported bug class of an unchecked "recipient" parameter causing funds to be sent to a black hole.

### Finding Description
`validate_delete_action` performs the only sanity check on `beneficiary_id`, restricted to account-id syntax: [1](#0-0) 

During execution, `action_delete_account` unconditionally emits a system balance-refund receipt to whatever `beneficiary_id` the signer supplied, with no existence or reachability check: [2](#0-1) 

That refund receipt is a system-predecessor receipt. If executed against a non-existent (or uninitialized) beneficiary account, it fails, and the runtime's refund-failure path burns the deposit rather than returning it to anyone: [3](#0-2) 

This is confirmed by an existing regression test showing that a refund to a nonexistent account fails with `AccountDoesNotExist` and does **not** create the account (i.e., the transfer is dropped/burned, not delivered): [4](#0-3) 

The documented invariant makes the burn explicit: "a failed refund burns its deposit into `other_burnt_amount`": [5](#0-4) 

Because `beneficiary_id` is never checked for existence (analogous to the missing `recovery != 0` / `agent != 0` checks in the reported bridge bug), a signer can set `beneficiary_id` to:
- a syntactically valid but never-created `AccountId`, or
- the account being deleted itself (self-beneficiary), which is deleted (`*account = None`) before the refund receipt executes, so the refund now targets a just-deleted account,

and in either case the entire remaining account balance is irrevocably burned instead of transferred anywhere.

### Impact Explanation
This results in permanently frozen/burnt funds — an accepted impact category. Unlike a simple user mistake with no protocol consequence, this is a supply-affecting event: the balance is moved from `tokens_burnt`/`other_burnt_amount` accounting rather than being preserved for any account, permanently reducing that user's/account's realizable NEAR with no recovery path once the delete-account receipt is committed. Since `DeleteAccountAction` requires `predecessor_id == receiver_id`, this cannot be forced onto a third party without their signature, but it is a real, unrecoverable value-loss bug directly reachable by any single account-holder's own transaction or by a contract batching a self-delete via the Promise API (`promise_batch_action_delete_account`), same as the reported "if recovery==0, funds are sent to 0 address" and "if agent==0, funds are locked forever" scenarios, which also stem from unchecked user-supplied destination parameters.

### Likelihood Explanation
High reachability: the vulnerable code path is exercised by a single `DeleteAccountAction` inside an ordinary `SignedTransaction` or via `promise_batch_action_delete_account` from a WASM contract — no privileged access, validator status, or multi-party coordination is required. The only prerequisite is supplying a `beneficiary_id` that is syntactically valid but does not correspond to an initialized, existing account (trivial to trigger, intentionally or accidentally).

### Recommendation
Extend `validate_delete_action` (or `action_delete_account`) to require that `beneficiary_id`:
- is not equal to `account_id` (no self-beneficiary), and
- corresponds to an existing, initialized account, returning an explicit action error (e.g., `DeleteAccountBeneficiaryDoesNotExist`) instead of silently deleting the account and later burning the refund.

Alternatively, since checking existence at validation time requires a trie lookup, the check can be performed in `action_delete_account` itself before removing the account and generating the refund receipt, refusing the delete (rather than burning funds) if the beneficiary account does not exist or is uninitialized.

### Proof of Concept
1. Account `alice.near` holds a balance and has no locked stake.
2. `alice.near` submits a `SignedTransaction` (or a contract issues a receipt via `promise_batch_action_delete_account`) with a single `DeleteAccountAction { beneficiary_id: "never-created.near" }` (or `beneficiary_id: "alice.near"` itself).
3. `validate_delete_action` accepts this because `"never-created.near"`/`"alice.near"` is a syntactically valid `AccountId`.
4. `action_delete_account` removes `alice.near`'s account and pushes `Receipt::new_balance_refund("never-created.near", account_balance)`.
5. This refund receipt, executed with `predecessor_id == "system"`, fails with `AccountDoesNotExist` (as demonstrated by the `refund_may_not_create_universal_account` test), and per the refund-failure path the entire `account_balance` is added to `stats.balance.other_burnt_amount` — permanently destroyed rather than delivered to `alice.near`, `never-created.near`, or any other account. pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
