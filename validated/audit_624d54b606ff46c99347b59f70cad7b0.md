### Title
Relayer fee paid unconditionally before the emulated transfer's outcome is checked - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Lido `WstETH.sol` bug is that `transfer`/`transferFrom` return values are not checked, so the contract proceeds as if the token movement succeeded even when it actually failed. The closest reachable analog in nearcore is in the NEAR Wallet Contract's `inner_rlp_execute`, where the relayer's fee transfer is scheduled and paid out **before** the wallet's underlying action (an emulated ERC-20 `ft_transfer` or a base-token `Transfer`) has actually been executed or its result checked.

### Finding Description
`inner_rlp_execute` parses a relayed Ethereum-style transaction into a NEAR `Action` plus a `TransactionKind`. For `EOABaseTokenTransfer` and `ERC20Transfer` kinds with a non-zero `fee`, the contract immediately creates and dispatches a `Transfer` promise to the relayer: [1](#0-0) 

This fee-refund promise is created unconditionally, *before* the promise for the real action (`action_to_promise(...)` / the `ft_transfer` cross-contract call chain) is even constructed, and independent of whether that action promise ultimately succeeds. The actual action's outcome is only checked afterwards, in `rlp_execute_callback`, via `env::promise_result(0)`: [2](#0-1) 

Because both the fee-transfer receipt and the action receipt(s) are dispatched from the same function call without any dependency between them (the fee transfer is not chained via `.then()` on the action's success), the relayer is paid the fee regardless of whether the `ft_transfer` (which can fail for reasons such as insufficient balance, the token contract panicking, or `storage_deposit` failing) or the native `Transfer` action succeeds. The code never gates the fee payment on the "return value" (i.e., the promise result / success) of the transfer it is compensating the relayer for — structurally the same class of bug as not checking `transfer`/`transferFrom`'s boolean return value before treating the operation as successful.

### Impact Explanation
A malicious or just unlucky relayer can submit a wallet-contract transaction whose emulated ERC-20 transfer is designed to fail (e.g., the user/wallet does not actually hold sufficient token balance, or the token contract reverts) while still collecting the `fee` amount of $NEAR that was supposed to compensate them only for successfully relaying a valid transfer. This is unauthorized value movement: the wallet owner's $NEAR is transferred out even though the intended action did not happen, with no automatic refund of the fee back to the wallet. This directly affects fund custody of eth-implicit accounts backed by the Wallet Contract, a component reachable by any signer/relayer sending a `rlp_execute` transaction.

### Likelihood Explanation
Reachable by any account that can call `rlp_execute` (the relayer role is explicitly untrusted per the code's own comments about "faulty relayer" and access-key revocation), and it requires only crafting/relaying a transaction whose emulated action is set up to fail on-chain (e.g., insufficient token balance) while a non-zero `fee` is specified. No special privileges beyond being a relayer with a function-call access key (a normal, expected role in this system) are required.

### Recommendation
Chain the fee-refund transfer so it only executes after the main action's promise result is confirmed successful (e.g., attach it inside `rlp_execute_callback` on the `PromiseResult::Successful` branch, or use `promise_batch_then`/`.then()` so the fee payment promise depends on the action's outcome), instead of dispatching it eagerly and unconditionally in `inner_rlp_execute`.

### Proof of Concept
1. Deploy the Wallet Contract for an eth-implicit account and fund it with some NEP-141 tokens and $NEAR.
2. As the relayer, craft an RLP `ERC20Transfer` transaction with a non-zero `fee` value but with a `value`/transfer amount that will cause `ft_transfer` to fail (e.g., set the transfer amount higher than the wallet's token balance, or target a token contract that always panics on transfer).
3. Submit via `rlp_execute`. Observe in `inner_rlp_execute` that the fee-transfer promise to the relayer's account is created and sent immediately, per [3](#0-2) , before the `ft_transfer` promise chain (which will fail) is even created.
4. Confirm the relayer's account balance increases by `fee` even though `ExecuteResponse.success == false` for the failed `ft_transfer`, as returned by `rlp_execute_callback`'s `PromiseResult::Failed` branch [4](#0-3) .
