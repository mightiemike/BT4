### Title
Non-injective `citrea_network_to_chain_id` allows a `BatchProofMethodId` upgrade signed/broadcast for `Network::Nightly` to be replayed on `Network::TestNetworkWithForks` (and vice-versa) - (File: crates/light-client-prover/src/circuit/mod.rs)

### Summary
`citrea_network_to_chain_id` maps `Network::Nightly` and `Network::TestNetworkWithForks` to the identical numeric chain id `5665`, and the `DataOnDa::BatchProofMethodId` handler in the light-client circuit only checks `circuit_chain_id != batch_proof_method_id.body.chain_id`, never the actual `Network` variant. Combined with the fact that the default/env-derived method-id-upgrade authority keys for these two networks are configured identically, a publicly observed, validly-signed method-id-upgrade blob for one of these networks can be copied byte-for-byte and inscribed on the other network's Bitcoin DA, and will pass both the chain-id check and the signature check.

### Finding Description
The binding the light-client circuit is supposed to enforce is:
`citrea_network_to_chain_id(deployment_network) == batch_proof_method_id.body.chain_id` ⟺ `deployment_network == authorised_network`.

This binding is broken because `citrea_network_to_chain_id` is not injective: `Network::Nightly → 5665` and `Network::TestNetworkWithForks → 5665` (see `crates/light-client-prover/src/circuit/mod.rs:763-771`). The circuit code path in `crates/light-client-prover/src/circuit/mod.rs:529-565` processes `DataOnDa::BatchProofMethodId` blobs by: (1) checking `activation_l2_height` is monotonically increasing, (2) checking `circuit_chain_id != batch_proof_method_id.body.chain_id` and skipping otherwise, (3) verifying the 3-of-5 security-council signature over `body.serialize()` via `verify_method_id_security_council`, then (4) calling `BatchProofMethodIdAccessor::insert`. None of these steps reference the actual `Network` enum variant — only the numeric chain id, which collides for two variants.

An attacker (unprivileged, per the threat model) who observes a legitimately-authorised `BatchProofMethodId` reveal transaction posted on the `Nightly` Bitcoin DA network (all on-chain data is public) can copy the exact `borsh(DataOnDa::BatchProofMethodId(...))` bytes — body (`method_id`, `activation_l2_height`, `chain_id=5665`) plus the 3 valid signatures — and inscribe an identical reveal transaction on the `TestNetworkWithForks` Bitcoin DA network (or vice versa). Because the two networks' default method-id-upgrade authority keys are provisioned from the same env-var names/fallback constants (`crates/light-client-prover/src/circuit/initial_values.rs:500-646`), the signatures verify successfully there too, and because `citrea_network_to_chain_id(TestNetworkWithForks) == 5665 == body.chain_id`, the chain-id guard also passes. The existing unit test `test_wrong_network_method_id_update_should_fail` only exercises the `Mainnet` vs `Nightly` case (chain ids 4114 vs 5665, which correctly differ) and never exercises the `Nightly`/`TestNetworkWithForks` collision, so this gap is untested.

### Impact Explanation
This lets a method-id-upgrade record be inserted via `BatchProofMethodIdAccessor::insert` on a network for which the security council never separately authorised an upgrade with that specific `activation_l2_height`/`method_id` — it is a cross-network replay of an authorisation intended for a different deployment. This matches the Critical category "a sequencer commitment or method-id upgrade accepted that was never authorised." It is repeatable for every future method-id-upgrade broadcast on either of the two colliding networks, and it affects any light-client prover/full node tracking the `TestNetworkWithForks` (or `Nightly`) network, causing them to accept a batch-proof method id switch that was not independently authorised for that specific network configuration.

### Likelihood Explanation
Both `Network::Nightly` and `Network::TestNetworkWithForks` are non-production/testing network configurations (`TestNetworkWithForks` is explicitly documented as "used for testing purposes only"), so the practical blast radius is limited to these test/QA deployments rather than `Mainnet`, `Testnet`, or `Devnet`, which have distinct, non-colliding chain ids. Exploitation requires only observing a real method-id-upgrade inscription on one of the two networks and paying Bitcoin fees to replay the identical bytes onto the other network's chain — no private keys, no privileged role, and no live authority cooperation needed.

### Recommendation
Change `citrea_network_to_chain_id` to return a distinct value per `Network` variant (or better, bind the check directly to the `Network` enum discriminant/name rather than a derived numeric id), and add an exhaustive injectivity test over all `Network` variants so future additions cannot silently collide.

use std::collections::HashSet;
use sov_rollup_interface::Network;

#[test]
fn citrea_network_to_chain_id_is_injective() {
    let variants = [
        Network::Mainnet,
        Network::Testnet,
        Network::Devnet,
        Network::Nightly,
        Network::TestNetworkWithForks,
    ];
    let mut seen = HashSet::new();
    for v in variants {
        let id = citrea_network_to_chain_id(v);
        assert!(seen.insert(id), "chain id {id} collides for variant {v:?}");
    }
    // Currently fails: Nightly and TestNetworkWithForks both map to 5665
}

/// These are chain ids for the citrea networks
/// This function is mainly used to check the chain id of the
/// method id upgrade transactions and to prevent cross network replay attacks
/// The method id upgrade identifiers are not strictly tied to chain ids
/// but for simplicity we use the same values
pub fn citrea_network_to_chain_id(network: sov_rollup_interface::Network) -> u64 {
    match network {
        sov_rollup_interface::Network::Mainnet => 4114,
        sov_rollup_interface::Network::Testnet => 5115,
        sov_rollup_interface::Network::Devnet => 62298,
        sov_rollup_interface::Network::Nightly => 5665,
        sov_rollup_interface::Network::TestNetworkWithForks => 5665,
    }
}
