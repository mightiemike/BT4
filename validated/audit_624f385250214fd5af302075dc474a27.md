### Title
`replace_class` syscall in the Starknet OS Cairo implementation does not verify class-hash existence before rebinding a contract's class — ([File: crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo])

### Summary
The Rust blockifier's `replace_class` syscall handler explicitly checks that the target `class_hash` is declared (and is Cairo1) before rewriting a contract's class binding, but the Starknet OS (SNOS) Cairo re-implementation of the same syscall — used for re-execution/proving of blocks — has an explicit `TODO` marking that this existence check is *not* performed, mirroring the `addPlugin` bug class of trusting an unvalidated external reference before it is consumed by dependent logic.

### Finding Description
The blockifier's syscall implementation for `replace_class` reads the compiled class to confirm it is declared before allowing the state update: [1](#0-0) 

The deprecated (Cairo0) syscall handler enforces the same invariant: [2](#0-1) 

However, the equivalent logic in the Starknet OS Cairo program — which independently re-executes transactions to build/verify the state diff and commitment for proving — updates `contract_state_changes` with the new `class_hash` without first verifying that a compiled class is actually declared for that hash: [3](#0-2) 

The comment at line 902, `// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.`, is a direct acknowledgment that this validation is missing. The Cairo0 (deprecated) OS syscall handler has the identical gap: [4](#0-3) 

This is structurally analogous to the reported `addPlugin` issue: an external reference (a plugin address / here, a class hash) is accepted and bound into critical state without validating that the referenced entity actually exists, relying entirely on a different code path (the Rust blockifier) to have already performed that check.

### Impact Explanation
Under the current architecture, the Rust blockifier is what actually executes transactions when building a block, and it does enforce the "class must be declared" check, so a transaction that fails this check would revert and never be included with the state-mutating `replace_class` in the block. The Starknet OS is meant to independently re-derive the same result from the block's transactions for proving. Because the OS's `replace_class` lacks the analogous check, the OS is not an independently correct/complete implementation of the state-transition function: it will silently accept and commit a class-hash rebinding that the Rust reference implementation would have rejected. This is a genuine implementation divergence between the two "sequencer path" components explicitly named in scope (blockifier execution vs. Starknet OS re-execution), and if any other logic path can cause an undeclared-class `replace_class` to reach OS re-execution (e.g., differences in when/how the check is bypassed, version-specific gaps, or future changes that rely on the OS being the source of truth), it can produce a wrong committed state root / class-hash-to-contract binding, since the OS would treat the operation as succeeding without verifying it references a real, provably-declared class.

### Likelihood Explanation
Likelihood is currently constrained because the Rust blockifier's check acts as a gate before transactions are ever included in a block, so a normal single transaction cannot trivially force the invalid `replace_class` state change to reach OS re-execution through the standard sequencer pipeline today. However, the presence of the explicit unresolved `TODO` shows this is a known, unpatched gap in the OS reference implementation rather than a hypothetical concern, and it represents a genuine correctness gap between the two independently-maintained state-transition implementations (Rust blockifier vs. Cairo OS) that are required to agree bit-for-bit for the system's soundness guarantees to hold.

### Recommendation
Add the missing declared-class check to the OS's `execute_replace_class` implementations (both the Cairo1 path in `syscall_impls.cairo` and the deprecated Cairo0 path in `deprecated_execute_syscalls.cairo`), mirroring the blockifier's check via `get_compiled_class`/`contract_class_changes` lookups, and also verify the class version (V1) consistency as the Rust implementation does (`ForbiddenClassReplacement` for V0), to keep the two implementations in lockstep and remove reliance on an external component to enforce this invariant.

### Proof of Concept
Not independently reproducible as a standalone unprivileged-transaction exploit against the current sequencer pipeline, because the Rust blockifier's `replace_class` handler at [1](#0-0)  already rejects `replace_class` calls with undeclared class hashes before they can be included in a block, which is confirmed by the existing test asserting `"is not declared"` error: [5](#0-4) . The gap is confirmed purely at the source level in the OS Cairo program via the explicit TODO comment and absence of any equivalent check in `execute_replace_class`: [6](#0-5) . Confirming whether any other reachable path (e.g., alternate transaction versions, future code changes removing the blockifier-side check, or bugs in how the OS's declared-classes dictionary is initialized/aliased) could allow this gap to be exploited by a single external transaction would require deeper analysis of the OS's block-building/committment pipeline that was not completed within the available investigation.

    pub fn replace_class(&mut self, class_hash: ClassHash) -> SyscallResult<()> {
        // Ensure the class is declared (by reading it), and of type V1.
        let compiled_class = self.state.get_compiled_class(class_hash)?;

        if !is_cairo1(&compiled_class) {
            return Err(SyscallExecutionError::ForbiddenClassReplacement { class_hash });
        }
        self.state.set_class_hash_at(self.call.storage_address, class_hash)?;
        Ok(())
    }
