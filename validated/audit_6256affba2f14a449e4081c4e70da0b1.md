### Title
Deposit rounds shares-minted to zero for small amounts while still consuming the depositor's underlying, permanently transferring the deposit to existing shareholders - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`)

### Summary
The `deposit` function in every v0 vault contract computes `inkind` (shares to mint) via `convert-to-shares-preview`, which performs `mul-div-down amount ts ta` — integer division that truncates toward zero. [1](#0-0)  The `deposit` function only asserts `amount > 0` (`ERR-AMOUNT-ZERO`) but never asserts that the computed `inkind` (shares) is greater than zero, unlike `redeem`, which explicitly checks `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`. [2](#0-1) [3](#0-2)  Consequently a depositor can transfer real underlying tokens into the vault, have them added to `assets`, and receive zero `zft` shares in return, permanently losing their principal to the benefit of existing shareholders.

### Finding Description
`deposit` computes `inkind` before any assertion related to it:
```
(inkind (convert-to-shares-preview amount))
...
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
``` [4](#0-3) 

`convert-to-shares-preview` rounds down: `(mul-div-down amount ts ta)`. [1](#0-0)  If `ts` (total shares) and `ta` (total assets, including accrued interest) have diverged such that `ta > ts` (which happens naturally as interest accrues and shares appreciate in value), any `amount` for which `amount * ts < ta` truncates to `inkind = u0`.

Because `min-out` defaults to `u0` in typical integrator usage (a caller not anticipating rounding will pass `0` for “no minimum”), the slippage check `(>= inkind min-out)` — i.e. `(>= 0 0)` — passes vacuously. There is no `ERR-OUTPUT-ZERO`-style check on the mint side (contrast with `redeem`, which has one). The function then proceeds to:
1. `receive-underlying amount account` — pulling the user's real tokens into the contract.
2. `ft-mint? zft inkind recipient` — minting `u0` shares to the depositor.
3. `var-set assets (+ current-assets amount)` — crediting the deposited amount to the vault's total assets, which backs the *existing* shareholders' redemption value.

The depositor's underlying asset is absorbed into the vault's `assets`, increasing the redeemable value of every other holder of `zft`, while the depositor holds no claim (`inkind = 0`) on any of it. The deposited value is irreversibly redistributed to other shareholders in a single transaction/single call — the same "assign zero tokens to sender" defect flagged for `DSTContract.sol`'s fallback in the external report, and analogous to `redeem`'s explicit `ERR-OUTPUT-ZERO` guard that `deposit` conspicuously lacks.

### Impact Explanation
The depositor's principal is not merely delayed or temporarily locked — it is permanently and irreversibly transferred to the rest of the shareholder pool because zero shares are minted back to them and there is no shares-based claim to later redeem. This is direct theft of user funds at rest (the depositor's underlying moves into the shared asset pool with no corresponding claim), satisfying the Critical impact bar.

### Likelihood Explanation
The trigger condition only requires that `total-assets-preview / total-supply-preview` (the share price) exceeds `1` by enough that a given deposit amount rounds to zero shares, which is the ordinary state of any vault after interest has accrued for a while (shares appreciate above 1:1). Any user submitting a sufficiently small deposit — whether accidentally (dust deposit, UI rounding, script default) or as a griefing/self-harm action — while relying on the common convention of `min-out = 0` will trigger this without any special privileges or timing requirements.

### Recommendation
Add an explicit zero-output guard on the deposit path, mirroring the existing `redeem` check, e.g.:
```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed immediately after `inkind` is computed in `deposit`, across all v0 vault contracts (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`).

### Proof of Concept
1. Vault has accrued interest so that `total-assets-preview() = ta` and `total-supply-preview() = ts` with `ta > ts` (share price > 1 unit of underlying per share).
2. Depositor calls `deposit(amount, 0, recipient)` where `amount` is small enough that `amount * ts / ta` truncates to `0` (e.g., `amount = 1` base unit when `ta/ts` ratio is large enough). [5](#0-4) 
3. `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` passes since `amount = 1`.
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes since both are `0`. [6](#0-5) 
5. `receive-underlying amount account` transfers the depositor's 1 unit of underlying into the vault. [7](#0-6) 
6. `ft-mint? zft inkind recipient` mints `0` shares to the depositor. [8](#0-7) 
7. `var-set assets (+ current-assets amount)` increases vault assets backing all other shareholders by the depositor's contribution. [9](#0-8) 
8. The depositor now holds `0` `zft` shares and has no way to reclaim the transferred underlying; the value has been permanently redistributed to existing shareholders.

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```
