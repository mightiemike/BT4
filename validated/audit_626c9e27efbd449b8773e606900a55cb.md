### Title
Non-deterministic floating-point `Math.pow()` used for bonding-curve exchange rate calculation, when strict-math/hardened-math is not enabled - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The reported bug class ("`exp()` inaccurate when `x/g` is not small" causing fee mis-calculation from a bounded polynomial approximation) maps in java-tron to `ExchangeProcessor`'s use of a raw double-precision `pow()` transcendental function to evaluate the Bancor-style bonding-curve TRC10 exchange formula. Like the Solidity `exp()`, this is a floating-point approximation of a transcendental function feeding directly into on-chain asset accounting, and it is reachable from an anonymous broadcast transaction (`ExchangeTransactionContract` / `ExchangeInjectContract` / `ExchangeWithdrawContract`).

### Finding Description
`ExchangeProcessor.exchangeToSupply()` / `exchangeFromSupply()` compute the TRC10 relay-supply bonding curve using `Maths.pow(base, exponent, useStrictMath)`, which — depending on the `useStrictMath` flag — dispatches to either `StrictMathWrapper.pow` (`StrictMath.pow`) or `MathWrapper.pow` (plain `Math.pow`): [1](#0-0) 

`Math.pow` is explicitly documented by the JDK as not guaranteed to be bit-for-bit reproducible across platforms/JIT implementations, unlike `StrictMath.pow`. The codebase itself acknowledges this danger by shipping platform-specific `MathWrapper` implementations (`platform/x86` and `platform/arm`) and a hard-coded historical lookup table of known-divergent `(a, b) -> result` triples that had to be patched in after the fact: [2](#0-1) [3](#0-2) 

This is the exact same bug class as the Solidity report: a numerical approximation of an exponential/power function, embedded directly in on-chain financial accounting, whose imprecision (here, cross-platform non-determinism rather than Taylor-series truncation) can corrupt results. The `Maths` class itself is marked `@Deprecated` with a comment recommending `StrictMathWrapper` "for cross-platform consistency," confirming project awareness of the risk: [4](#0-3) 

The vulnerable path is reachable directly from a broadcast `ExchangeTransactionContract`, which invokes `ExchangeCapsule.transaction(...)` → `ExchangeProcessor.exchange(...)` using the `dynamicStore.allowStrictMath()` governance flag: [5](#0-4) [6](#0-5) 

A hardened, deterministic `BigDecimal`-based implementation (`SafeExchangeProcessor`) and an `allowHardenExchangeCalculation` governance switch already exist to remediate this exact issue: [7](#0-6) 

### Impact Explanation
If `allowStrictMath` / `allowHardenExchangeCalculation` are not enabled (e.g., on a private/consortium/test chain, or a chain that has not yet activated the corresponding hard-fork proposal), nodes running different JVM/CPU architectures (x86 vs ARM, as evidenced by the dual `MathWrapper` implementations) can compute different `Math.pow` results for the same `(base, exponent)` inputs on a broadcast `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`. Since the resulting relay-supply and exchanged-token amounts are written directly into account balances and exchange pool balances, this can produce state divergence between nodes (chain fork / consensus divergence) or, on a single node, incorrect asset accounting favoring one party in the trade — an accounting corruption class impact, analogous to the "sigmoid()/fee miscalculation" impact in the original report.

### Likelihood Explanation
Likelihood is moderated by the fact that this exact issue has already been recognized by the maintainers, who introduced `StrictMathWrapper`, the deprecation warning on `Maths`, the platform-specific correction tables, `allowStrictMath`, `allowHardenExchangeCalculation`, and `SafeExchangeProcessor` as mitigations/hard-fork switches (visible in `ProposalUtil.java`, `DynamicPropertiesStore.java`). On networks (e.g. mainnet) where these proposals are activated, the deterministic/hardened path is used and the risk is closed. The residual risk applies to chains/environments where these flags remain at their default/legacy value and mixed-architecture validator sets are used — this could not be fully confirmed from the index due to not locating the exact default value for `allowStrictMath`/`allowHardenExchangeCalculation` in `reference.conf` or the genesis defaults.

### Recommendation
- Confirm the default/activation state of `ALLOW_STRICT_MATH` and `ALLOW_HARDEN_EXCHANGE_CALCULATION` on all supported networks, and ensure `SafeExchangeProcessor` (BigDecimal-based, deterministic) is the only path used once these proposals activate, deprecating the legacy `Math.pow`-based path entirely rather than keeping it selectable.
- Remove reliance on `java.lang.Math` (non-strict) transcendental functions anywhere account/asset balances are computed; standardize on `StrictMath` or integer/BigDecimal fixed-point arithmetic to guarantee bit-for-bit determinism across all supported CPU architectures.
- Retire the historical `MathWrapper` correction-table hack once the hardened path is universally active, since its existence is itself evidence that non-determinism previously caused observable divergence in production.

### Proof of Concept
1. Deploy two java-tron nodes on different CPU architectures (x86 and ARM) without `allowStrictMath`/`allowHardenExchangeCalculation` activated.
2. Broadcast an `ExchangeCreateContract` to create a TRC10 exchange pool, then broadcast an `ExchangeTransactionContract` calling into `ExchangeCapsule.transaction(...)` with `useStrictMath=false, hardenedCalc=false`, which routes to `ExchangeProcessor.exchangeToSupply/exchangeFromSupply` using `Math.pow`.
3. Compare the resulting `anotherTokenQuant` / relay supply computed on each node; due to `Math.pow`'s platform-dependent, non-strictly-specified rounding, the two nodes can compute different results for the same inputs, as previously observed and hard-coded around in `MathWrapper`'s `addPowData` correction table (see the block-numbered entries referencing specific historical mismatches).   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

package org.tron.common.math;

/**
 * This class is deprecated and should not be used in new code,
 * for cross-platform consistency, please use {@link StrictMathWrapper} instead,
 * especially for floating-point calculations.
 */
@Deprecated
public class Maths {

  /**
   * Returns the value of the first argument raised to the power of the second argument.
   * @param a the base.
   * @param b the exponent.
   * @return the value {@code a}<sup>{@code b}</sup>.
   */
  public static double pow(double a, double b, boolean useStrictMath) {
    return useStrictMath ? StrictMathWrapper.pow(a, b) : MathWrapper.pow(a, b);
  }

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
