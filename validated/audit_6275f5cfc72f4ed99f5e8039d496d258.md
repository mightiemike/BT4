### Title
`totalNetWeight`/`totalEnergyWeight` global cache can be permanently inflated by legacy TVM `unfreezeBalance()` native contract, corrupting network-wide bandwidth/energy pricing - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java])

### Summary
`DynamicPropertiesStore.getTotalNetWeight()`/`getTotalEnergyWeight()` are global cached aggregates, analogous to the reported `_cachedTotalUnderlying`, that are supposed to always equal the sum of every account's `frozenBalance / TRX_PRECISION`. Just like the report's `_cachedTotalUnderlying` being updated from an assumed withdrawn amount instead of the true post-withdraw state, the TVM native `unfreezeBalance()` path (`UnfreezeBalanceProcessor`) decrements this cache using `-unfreezeBalance / TRX_PRECISION` (the raw amount just unfrozen) instead of computing the delta between the account's rounded weight before and after unfreezing, as the equivalent non-TVM `UnfreezeBalanceActuator` correctly does. This produces a persistent, network-wide accounting drift in the global weight cache.

### Finding Description
`FreezeBalanceActuator.addTotalWeight()` and `UnfreezeBalanceActuator.execute()` both maintain `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT` by computing the account's *rounded* weight before and after the operation and adding only the *delta*: [1](#0-0) 
This technique (`newNetWeight - oldNetWeight`, both `floor(frozenBalance/TRX_PRECISION)`) is loss-less with respect to the true rounded sum, because it mirrors exactly how the weight was added when the balance was frozen in `FreezeBalanceActuator`: [2](#0-1) 

However, `UnfreezeBalanceProcessor` — the equivalent logic invoked from the TVM native `unfreezeBalance()` precompiled function reachable from any smart contract — decrements the cache directly from the just-withdrawn amount instead of the rounded delta: [3](#0-2) 
The comment `// adjust total resource, used to be a bug here` at that exact line indicates this code path has historically been the source of drift bugs.

Because `TRX_PRECISION` is 1,000,000, and an account's bandwidth-frozen balance can be an accumulation of multiple `Frozen` entries (each frozen at different times, each contributing a floor-rounded weight when added), unfreezing a subset of those entries via `unfreezeBalance += next.getFrozenBalance()` and then floor-dividing the *sum of unfrozen entries alone* — rather than `floor(totalBefore/TRX_PRECISION) - floor(totalAfter/TRX_PRECISION)` — can differ from the correct delta by up to several TRX_PRECISION units whenever the remaining (not-yet-expired) frozen balance is not itself an exact multiple of `TRX_PRECISION`. This mismatch accumulates over many unfreeze operations network-wide, permanently drifting `totalNetWeight`/`totalEnergyWeight` away from the true rounded sum of all account weights, exactly mirroring how `_cachedTotalUnderlying` in the reported bug becomes systematically wrong relative to reality.

### Impact Explanation
`totalNetWeight`/`totalEnergyWeight` directly determine every account's bandwidth/energy limit via `BandwidthProcessor.calculateGlobalNetLimit()`/`calculateGlobalNetLimitV2()` and `ResourceProcessor.calculateGlobalLimitV2()`: [4](#0-3) 
An inflated (or deflated) global weight cache skews the `(long)(netWeight * (totalLimit/totalWeight))` computation for *every* account on the network, meaning honest accounts get systematically wrong resource limits — either denial-of-service (limits too low) or resource over-allocation (limits too high, enabling spam/DoS against the network's finite bandwidth/energy pool). This is a resource-accounting corruption reachable purely through normal contract execution.

### Likelihood Explanation
The native `unfreezeBalance()` TVM contract is callable by any account via a deployed/triggered smart contract — no privileged role is required. `Program.withdrawReward`/related native contract wiring shows these processors are invoked directly from TVM opcode execution, so any user broadcasting a contract-triggering transaction that calls unfreeze on a multi-entry frozen balance can trigger the miscalculation. The drift per call is bounded (at most a few `TRX_PRECISION` units), but it is directional and cumulative across the whole chain's lifetime, so likelihood of eventual measurable divergence is high, though the magnitude of any single transaction's effect is small.

### Recommendation
Change `UnfreezeBalanceProcessor.execute()` to compute the weight delta the same way `UnfreezeBalanceActuator` does: capture `oldWeight = floor(accountBalanceBeforeUnfreeze / TRX_PRECISION)` and `newWeight = floor(accountBalanceAfterUnfreeze / TRX_PRECISION)`, and call `repo.addTotalNetWeight(newWeight - oldWeight)` / `addTotalEnergyWeight(newWeight - oldWeight)` instead of `-unfreezeBalance / TRX_PRECISION`, ensuring consistency between the freeze and unfreeze accounting paths (both TVM-native and actuator).

### Proof of Concept
Not independently executed; reasoning is based on static code comparison between `FreezeBalanceActuator`/`UnfreezeBalanceActuator` (correct delta-based accounting) and `UnfreezeBalanceProcessor` (raw-amount-based accounting). A concrete PoC would: (1) freeze bandwidth for an account in two separate `FreezeBalance` calls so the account's `frozenBalance` accumulates non-`TRX_PRECISION`-aligned amounts across two `Frozen` entries; (2) wait for one entry to expire; (3) call the native `unfreezeBalance()` via a TVM contract to unfreeze only the expired entry; (4) compare `dynamicStore.getTotalNetWeight()` before/after against the value produced by an equivalent sequence performed via `UnfreezeBalanceActuator` — the two paths would diverge by the described rounding delta. This part is **unconfirmed by test execution** due to lack of runtime access in this analysis; the divergence is inferred from the algorithmic difference between the two code paths.
