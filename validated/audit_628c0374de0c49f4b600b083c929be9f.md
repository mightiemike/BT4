### Title
`remove_account()` leaves orphaned PromiseYield / postponed-receipt state, allowing a stale parked receipt to be replayed against a re-created account - (File: `core/store/src/utils/mod.rs`)

### Summary
The Linux kernel bug frees a parent NFS state object (open stateid) without freeing/unlinking the dependent child state (copynotify stateid) that references it, leaving a dangling reference that a later timer-driven cleanup path (`laundromat`) walks and corrupts. The analogous pattern in `nearcore` is `remove_account()` (`core/store/src/utils/mod.rs:504-575`), which is the single place that tears down account state on `DeleteAccount`. It removes the `Account`, `ContractCode`, all `AccessKey`/gas-key rows, and `ContractData` rows, but it does **not** remove any `PromiseYieldReceipt`, `PromiseYieldStatus`, postponed-receipt (`PostponedReceiptId`/`PendingDataCount`), or `ReceivedData` entries keyed by that `account_id`. These are all separate trie-key namespaces (`core/primitives/src/trie_key.rs:244-247` etc.) that are not iterated or cleaned by `remove_account`. [1](#0-0) 

### Finding Description
A contract can create a `PromiseYield` receipt via `promise_yield_create`, which is stored keyed by `(receiver_id, data_id)` in `PromiseYieldReceipt`, together with a `PromiseYieldTimeout` entry in a global per-shard FIFO queue ordered by `expires_at` (`core/primitives/src/receipt.rs:1082-1091`, `core/store/src/utils/mod.rs:181-212`). If the same account is deleted via `action_delete_account` (`runtime/runtime/src/actions.rs:330-406`) before the yield is resumed or timed out, `remove_account` is called to tear down the account's state: [2](#0-1) 

`remove_account` only walks and removes `AccessKey`/gas-key and `ContractData` prefixes plus the `Account`/`ContractCode` rows — it never touches `PromiseYieldReceipt`, `PromiseYieldStatus`, or postponed-receipt bookkeeping for that account: [1](#0-0) 

The global `PromiseYieldTimeout` queue entry that was created for this account/`data_id` is untouched by account deletion (it lives outside any account-keyed prefix). When `resolve_promise_yield_timeouts` later processes the queue and the `expires_at` height is reached, it only checks `contains_key(promise_yield_key)` to decide whether to synthesize a `PromiseResume`: [3](#0-2) 

Because `remove_account` never removed the `PromiseYieldReceipt` row, `contains_key` is still `true` even though the owning account was deleted. If the same `account_id` is subsequently re-created (e.g. funded again by a transfer, or re-deployed), the stale yield receipt is still resolvable: the synthesized `PromiseResume` will find the old `yield_receipt` via `get_promise_yield_receipt`, remove it, and execute it with `apply_action_receipt` against whatever account state now exists at that `account_id`: [4](#0-3) 

This is state that a caller believes is dead (the account was deleted) suddenly re-animating and running arbitrary actions/output-data callbacks that were signed off by the *old* incarnation of the account, against the *new* incarnation's balance/keys/contract.

### Impact Explanation
This produces an invalid state transition / unauthorized action execution:
- A previously-committed `PromiseYield` action receipt (which can carry arbitrary follow-up actions and output-data callbacks, including transfers or function calls with `deposit`) is replayed on a re-created account that never explicitly re-authorized it, causing unexpected balance movement or contract calls attributable to the wrong "generation" of the account.
- Because the yield/timeout resolution path runs deterministically inside `resolve_promise_yield_timeouts` during normal chunk application (not a validator-only or malicious-peer path), this is reachable by any account owner via ordinary transactions (yield creation via a `FunctionCall`, delete via `DeleteAccount`, re-creation via a plain `Transfer`), and it affects consensus-critical state (state root) identically on all honest nodes — so it is not itself a state-root divergence, but it is an invalid state transition being *accepted* by protocol rules that were not designed to allow it.
- Depending on what actions the stale yield receipt performs, this can range from unexpected funds transfer/spend on the recreated account to invoking privileged contract-internal callbacks (`output_data_receivers`) that assume the yield they resolve is contemporaneous, undermining application-level invariants (e.g., escrow/cross-contract-call patterns relying on "no dangling promise after account deletion").

### Likelihood Explanation
Reaching this requires: (1) a contract that calls `promise_yield_create`/`promise_yield_create_with_id` and is not resumed before (2) the same signer/account issuing a `DeleteAccount` action, and (3) the account being re-created before the `PromiseYieldTimeout` fires (the timeout window is a configurable, typically multi-block-height parameter, giving an attacker-controlled account owner ample time to delete-and-recreate within that window). All three steps are ordinary, unprivileged transactions any account holder can submit against their own account; no validator or network-level cooperation is needed. This makes it a straightforward attacker-controlled sequence rather than a rare race, though it does require deliberate misuse of promise-yield + delete/recreate rather than being triggered by benign usage alone.

### Recommendation
When `action_delete_account` / `remove_account` tears down an account, also enumerate and remove any `PromiseYieldReceipt`, `PromiseYieldStatus`, postponed-receipt (`PostponedReceiptId`/`PendingDataCount`), and `ReceivedData` rows keyed by that `account_id`, mirroring how access keys and contract data are already prefix-scanned and removed. Alternatively (or additionally), have `resolve_promise_yield_timeouts` and the `PromiseResume` handling path verify that the *account* referenced by the stale yield still corresponds to the same account "generation" that created it (e.g. by checking account existence/initialization state or a generation counter) before executing/resuming it, and drop stale timeout entries whose target account was deleted since creation.

### Proof of Concept
1. Account `A` deploys a contract and calls a method that invokes `promise_yield_create(callback_method, timeout_blocks)`, producing a `PromiseYieldReceipt` for `(A, data_id)` and a `PromiseYieldTimeout` entry with `expires_at = h0 + timeout_blocks`.
2. Before `expires_at`, `A` submits a batched `DeleteAccount` (beneficiary = attacker-controlled account). `action_delete_account` → `remove_account` runs; the `PromiseYieldReceipt`/`PromiseYieldTimeout` rows for `A` are left in the trie.
3. Some other account transfers funds to `A`, or `A` is otherwise re-created (e.g., via `CreateAccount`) before `expires_at`.
4. At block height `expires_at`, `resolve_promise_yield_timeouts` finds the queue entry, checks `contains_key(PromiseYieldReceipt{A, data_id})` → true (never cleaned up), and forwards a synthetic `PromiseResume`.
5. The runtime's `PromiseResume` handling (`runtime/runtime/src/lib.rs:1568-1616`) fetches the stale `yield_receipt` and calls `apply_action_receipt` on it — executing the old receipt's actions/callback against account `A`'s new state, even though `A` was deleted and re-created in between.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
