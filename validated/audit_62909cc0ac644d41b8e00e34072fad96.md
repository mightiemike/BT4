### Title
Rejected L1 handler transactions remain validatable, allowing a previously-rejected L1 message to be re-included in a proposed block - (File: `crates/apollo_l1_events/src/transaction_manager.rs`)

### Summary
`TransactionRecord::is_validatable()` in the L1 events transaction manager only excludes transactions in `Committed`, `CancelledOnL2`, or `Consumed` states, but does not exclude `Rejected` transactions. This is analogous to the reported audit issue where `_distribute` failed to check a status field (`Accepted`) before performing a state-changing action — here `validate_tx` fails to check the `Rejected` status before treating an L1 handler transaction as re-validatable for inclusion in a block. [1](#0-0) 

### Finding Description
`TransactionRecord::mark_rejected` transitions a transaction into `TransactionState::Rejected` and additionally sets a `rejected` metadata flag, explicitly documenting that "double reject not currently checked": [2](#0-1) 

However, `is_validatable()` — the gate used by `validate_tx` to decide whether an L1 handler transaction may be accepted into a proposed/validated block — only checks `!is_committed() && !is_cancelled() && !is_consumed()`: [1](#0-0) 

It never checks `state == TransactionState::Rejected`. Consequently, in `TransactionManager::validate_tx`, the match arm that maps invalid states to specific `InvalidValidationStatus` variants (`AlreadyIncludedOnL2`, `CancelledOnL2`, `ConsumedOnL1`) has no arm for `Rejected` and relies on `is_validatable()` to have filtered it out; since it doesn't, a `Rejected` record falls through to the `else` branch and is treated as valid for staging/inclusion: [3](#0-2) 

This mirrors the audit-report bug class exactly: a state machine defines a terminal/negative status (`Rejected` / `REJECTED`) but a downstream state-changing function (`validate_tx` / `_distribute`) omits the corresponding guard, allowing the item to be processed again as if it were still pending/valid.

### Impact Explanation
`validate_tx` is the function honest sequencer nodes use to independently verify that an L1 handler transaction proposed by the block proposer is legitimate for inclusion. If a transaction was already rejected in a prior block (e.g., due to nonce/fee failure), it is not excluded from `is_validatable()`, so a proposer could re-propose the same L1 handler transaction and honest validating nodes would locally mark it `Validated` rather than rejecting it with a clear `InvalidValidationStatus`. Because `commit_txs` distinguishes committed vs. rejected transactions and calls `mark_rejected`/`mark_committed` accordingly, and `mark_committed`/`mark_rejected` both assert against double-transitions (`assert!(!self.committed, ...)` / `assert!(!self.committed, ...)`), re-validating and re-attempting to commit an already-`Rejected` L1 handler message risks committing/consuming an L1 message a second time or causing panics/asserts across nodes that reached different states, undermining L1-message exactly-once processing guarantees and potentially causing honest-node divergence in accepting the block.

### Likelihood Explanation
This path is reachable purely from the normal transaction/L1-message lifecycle without any privileged or malicious-operator assumption: any L1 handler message that gets rejected once in the ordinary course of block building can subsequently be re-included by a proposer and independently re-validated as OK by all nodes running `validate_tx`, since the check omission is unconditional and not dependent on adversarial timing.

### Recommendation
Update `is_validatable()` to also exclude the `Rejected` state (and/or add an explicit `TransactionState::Rejected` match arm in `validate_tx` mapping to a dedicated `InvalidValidationStatus`, e.g. `AlreadyRejected`), consistent with how `Committed`, `CancelledOnL2`, and `Consumed` are already excluded:
```rust
pub fn is_validatable(&self) -> bool {
    !self.is_committed() && !self.is_cancelled() && !self.is_consumed() && !self.is_rejected()
}
```
and add the corresponding `is_rejected()` helper plus a match arm in `validate_tx`.

### Proof of Concept
1. An L1 handler transaction `tx_hash` is scraped and added via `add_tx`, entering `Pending` state. [4](#0-3) 
2. A block is built and committed such that `tx_hash` ends up in `rejected_txs`; `commit_txs` calls `mark_rejected`, setting `state = Rejected`. [5](#0-4) 
3. A subsequent (possibly malicious or buggy) proposer includes `tx_hash` again in a new proposal.
4. An honest validating node calls `validate_tx(tx_hash, now)`; since `record.state == Rejected`, `is_validatable()` returns `true` (only `Committed`/`CancelledOnL2`/`Consumed` are excluded), so the function proceeds to `try_mark_staged` and returns `ValidationStatus::Validated` instead of rejecting the tx. [6](#0-5) 
5. This allows a previously rejected L1 message to be accepted again into the pipeline, contrary to the intended one-shot rejection semantics documented in `mark_rejected`'s "double reject not currently checked" comment. [2](#0-1)

    pub fn validate_tx(&mut self, tx_hash: TransactionHash, unix_now: u64) -> ValidationStatus {
        let current_staging_epoch_cloned = self.current_staging_epoch;

        let policy = TransactionRecordPolicy {
            cancellation_timelock: self.config.l1_handler_cancellation_timelock_seconds,
        };

        let validation_status = self.with_record(tx_hash, |record| {
            // If the current time affects the state, update state now.
            record.update_time_based_state(unix_now, policy);
            if !record.is_validatable() {
                match record.state {
                    TransactionState::Committed => {
                        InvalidValidationStatus::AlreadyIncludedOnL2.into()
                    }
                    TransactionState::CancelledOnL2 => {
                        InvalidValidationStatus::CancelledOnL2.into()
                    }
                    TransactionState::Consumed => InvalidValidationStatus::ConsumedOnL1.into(),
                    _ => unreachable!(),
                }
            } else if record.try_mark_staged(current_staging_epoch_cloned) {
                ValidationStatus::Validated
            } else {
                InvalidValidationStatus::AlreadyIncludedInProposedBlock.into()
            }
        });

        validation_status.unwrap_or(InvalidValidationStatus::NotFound.into())
    }

    pub fn commit_txs(
        &mut self,
        committed_txs: &[TransactionHash],
        rejected_txs: &[TransactionHash],
    ) {
        self.rollback_staging();

        for &tx_hash in committed_txs {
            self.create_record_if_not_exist(tx_hash);
            self.with_record(tx_hash, |r| r.mark_committed()).unwrap();
        }
        for &tx_hash in rejected_txs {
            self.with_record(tx_hash, |r| r.mark_rejected()).expect(
                "Rejected L1 handler tx has no record. Unreachable: all L1 handler txs in a \
                 committed block were validated as known (validation rejects unknown hashes), \
                 sync commits with empty rejected_txs, and records are only removed via L1 \
                 cancellation/consumption, which can't race a block.",
            );
        }
    }

    pub fn add_tx(
        &mut self,
        tx: L1HandlerTransaction,
        block_timestamp: BlockTimestamp,
        scrape_timestamp: UnixTimestamp,
    ) {
        let tx_hash = tx.tx_hash;
        // If exists, return false and do nothing. If not, create the record as a HashOnly payload.
        let is_new_record = self.create_record_if_not_exist(tx_hash);
        // Replace a HashOnly payload with a Full payload. Do not update a Full payload.
        // A hash only payload can come from catching up from state sync, and then updated by
        // add_events from the scraper. However, if we get the same full tx twice (from the scraper)
        // it could indicate a double-scrape, and may cause the tx to be re-added to the proposable
        // index.
        self.with_record(tx_hash, move |record| match &record.tx {
            TransactionPayload::HashOnly(_) => {
                if !is_new_record {
                    info!(
                        "Transaction {tx_hash} already exists as a HashOnly payload. It was \
                         probably gotten via state sync component, and is now updated with a Full \
                         payload."
                    );
                }
                record.tx.set(tx, block_timestamp, scrape_timestamp);
                // Counts the HashOnly -> Full transition, regardless of whether the HashOnly
                // was just created here or pre-existed from state sync.
                L1_MESSAGE_SCRAPER_L1_HANDLER_TX_COUNT.increment(1);
            }
            TransactionPayload::Full { tx: _, created_at_block_timestamp: _, scrape_timestamp } => {
                warn!(
                    "Transaction {tx_hash} already exists as a Full payload, scraped at \
                     {scrape_timestamp}. This could indicate a double scrape. Ignoring the new \
                     transaction."
                );
            }
        });
    }
