### Title
Shared `last-update` timestamp is advanced by borrow-index rounding even when the liquidity index does not move, permanently erasing unclaimed LP yield - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent `v0-vault-*.clar` vaults)

### Summary
`accrue()` computes two independent accumulators — the borrow index (`index`) and the liquidity index (`lindex`) — from the *same* `last-update` timestamp, but only persists a *new* `last-update` if **either** index changed. Because the borrow index is rounded **up** (`mul-div-up`) while the liquidity index is rounded **down** (`mul-div-down`) using a strictly smaller rate, the borrow index will tick on almost every call while the liquidity index can round to exactly zero. When that happens, `last-update` is still advanced (because the borrow index changed), discarding the time window the liquidity index needed to accrue, permanently starving depositors of yield.

### Finding Description
`next-index` computes the borrow-side multiplier with round-up division: [1](#0-0) 

`next-liquidity-index` computes the liquidity-side multiplier with round-down division, using `liquidity-rate`, which is derived from the borrow rate scaled down by utilization and the reserve factor and is therefore always ≤ the borrow rate: [2](#0-1) [3](#0-2) 

`calc-multiplier-delta` is the shared math: for `round-up=true` (borrow index) any nonzero remainder from `rate * time-delta * INDEX-PRECISION / SECONDS-PER-YEAR-BPS` still increments the multiplier; for `round-up=false` (liquidity index) any remainder is discarded and the multiplier can equal `INDEX-PRECISION` exactly (no growth) when the numerator is smaller than the divisor: [4](#0-3) 

`accrue()` reads both `next` (borrow) and `nliq` (liquidity) from the current `last-update`, updates each `data-var` independently, but resets the shared clock if *either* one moved: [5](#0-4) 

Sequence of events:
1. `last-update = T0`. Utilization and/or reserve-factor make `liquidity-rate` a fraction of `interest-rate` (e.g., 50% utilization, 10% reserve fee → `liquidity-rate` ≈ 45% of borrow rate).
2. Any user calls a state-changing entry point (`deposit`, `system-borrow`, `system-repay`, `redeem`, or `accrue` itself) at `T0 + Δt`, where `Δt` is small enough that `liquidity-rate * Δt * INDEX-PRECISION / SECONDS-PER-YEAR-BPS < SECONDS-PER-YEAR-BPS` remainder-wise, i.e. rounds to `0`, so `nliq == lidx` (no growth), while `interest-rate * Δt` rounded **up** is enough to move `next` by at least `1`, so `next != idx`.
3. In `accrue()`, `(is-eq idx next)` is `false` → `index` is updated. `(is-eq lidx nliq)` is `true` → `lindex` is left untouched, correctly reflecting that no liquidity interest accrued *yet*.
4. Because `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))` is `true` (borrow index moved), `last-update` is unconditionally set to `stacks-block-time` (i.e., `T0 + Δt`).
5. The unaccrued liquidity-side time window `[T0, T0+Δt]` is lost forever: the next `next-liquidity-index` call computes `time-delta` from the new `last-update`, not from `T0`. The fractional liquidity yield for that whole window can never be recovered.
6. Because `accrue()` is a public, unauthenticated entry point invoked as part of every `deposit`/`borrow`/`repay`/`redeem`, any high-frequency user activity (or a user simply repeatedly interacting with the vault, or an attacker deliberately spamming small transactions each block) keeps `Δt` small on every call, causing the liquidity index to be reset over and over while never accumulating the rounding remainder — the classic "clock advances on any change, not specifically on the value it should be gating" analog from the referenced report, except here two accumulators race for one shared clock and the more rounding-sensitive one (round-up borrow index) perpetually invalidates the other's window.

This differs from the original report's exact mechanism (which required the same accumulator to both round to zero AND advance its own clock); here the vulnerability is that a *shared* clock is gated by the change of a *different, more coarsely-quantized* accumulator, so the liquidity index's clock is stolen out from under it whenever the borrow index (which almost always changes due to round-up) ticks first.

### Impact Explanation
Lenders'/depositors' accrued interest (`lindex`, which underlies `total-assets`/`total-assets-preview` and ultimately the `zft` share price via `total-supply-preview`) can be permanently starved: the time windows lost to this rounding race are never recovered because `last-update` has already moved past them. This is a temporary/permanent freezing (loss) of unclaimed yield owed to LPs, funneled instead to borrowers who pay a full borrow-index accrual while depositors receive less than their fair share of it, since the treasury/LP fee split (`treasury-lp`) is computed off the borrow-side `debt-delta`, decoupled from whether `lindex` grew at all in that window.

### Likelihood Explanation
This requires no special privileges — `accrue()` is a public entry point invoked implicitly on every deposit, borrow, repay, and redeem. Any vault with realistic utilization below 100% and/or a nonzero `fee-reserve` will have `liquidity-rate < interest-rate`, satisfying the rounding asymmetry. Any user (or the natural transaction flow of the protocol on a fast L2/Stacks block cadence) repeatedly interacting with the vault keeps `Δt` small, which is the normal condition, making this occur naturally and frequently rather than requiring a contrived attack.

### Recommendation
Do not share a single `last-update` timestamp for two accumulators whose rounding characteristics differ. Either:
- Maintain independent `last-update-index` and `last-update-lindex` timestamps, each advanced only when its own respective accumulator changes; or
- Only advance the shared `last-update` when **both** `index` and `lindex` fail to change (i.e., keep accruing until both accumulators actually move), so that no fractional time is discarded for either accumulator.

### Proof of Concept
1. Deploy/observe a vault (e.g., `v0-vault-stx.clar`) with utilization ≈ 50% and `fee-reserve` > 0, so `liquidity-rate` is meaningfully smaller than `interest-rate`.
2. At `T0`, call any entry point that triggers `accrue()` (e.g., a `1`-unit `deposit`) so `last-update = T0`.
3. Immediately after (`Δt` = a few seconds, or one Stacks block), call another small `deposit`/`system-repay` to trigger `accrue()` again.
4. Compute off-chain: `mul-div-up(interest-rate, Δt * INDEX-PRECISION, SECONDS-PER-YEAR-BPS)` is nonzero (borrow index moves) while `mul-div-down(liquidity-rate, Δt * INDEX-PRECISION, SECONDS-PER-YEAR-BPS)` is zero (liquidity index does not move).
5. Observe in `accrue()`'s logic at [6](#0-5)  that `last-update` is nonetheless advanced to the new block time because `index` changed.
6. Repeat step 3 every block/transaction; `lindex` never accumulates the lost `Δt` windows even though the underlying debt (and hence real yield) is compounding on the borrow side, permanently reducing LP payout relative to the true interest paid by borrowers.
