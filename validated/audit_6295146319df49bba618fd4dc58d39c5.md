### Title
Unsafe `BigInteger.longValue()` Truncation in DEX Order Matching Overflow Fallback - (File: `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java`)

### Summary
`MarketUtils.multiplyAndDivide()` computes `a * b / c` for TRON's on-chain DEX (`MarketSellAssetActuator`). When the intermediate multiplication overflows a Java `long`, the code falls back to `BigInteger` arithmetic but converts the final result back to `long` using the non-validating `BigInteger.longValue()` instead of `longValueExact()`. This mirrors the reported bug class: a wide integer result is downcast to a narrower type without checking that it actually fits, silently truncating/wrapping instead of failing safely.

### Finding Description
`multiplyAndDivide` first tries `multiplyExact`/`floorDiv` (which throw on overflow), and only on `ArithmeticException` falls back to `BigInteger`: [1](#0-0) 

Unlike every other overflow-hardened path in the codebase (e.g. `RepositoryImpl.usageToBalance`/`getUsage`/`calculateGlobalEnergyLimit`, which use `longValueExact()` and intentionally throw when the value doesn't fit — see `RepositoryImpl.java:256-265,940-985`), this fallback uses plain `longValue()`, which truncates to the low 64 bits and can silently produce a wrapped/negative `long` if `a*b/c` exceeds `Long.MAX_VALUE`.

This function is called directly by `MarketSellAssetActuator.matchSingleOrder()` to compute the exact quantities exchanged between taker and maker orders in the on-chain order book: [2](#0-1) [3](#0-2) [4](#0-3) 

The only bound placed on `sellTokenQuantity`/`buyTokenQuantity` is the configurable `dynamicStore.getMarketQuantityLimit()`, enforced in `validate()`: [5](#0-4) 

Both the taker's and maker's quantities (each independently bounded only by this single per-field limit, not by their product) feed into `a*b/c`. If `a` and `b` are both close to the limit and `c` is small (e.g., `1`), `a*b/c` can exceed `Long.MAX_VALUE` even though each individual quantity passed validation. In that case the `multiplyExact` overflow check correctly throws, the code falls into the `BigInteger` path, computes the true (huge) result, and then `longValue()` truncates it to an essentially arbitrary/wrapped (possibly negative) `long` — with no exception, no revalidation, and no bounds check before this value is fed straight into account balance/asset accounting via `addTrxOrToken`/`accountCapsule.setBalance` and `addAssetAmountV2`.

### Impact Explanation
The truncated/wrapped value is used directly as the amount of TRX or TRC-10 tokens credited to accounts in `matchSingleOrder` (`addTrxOrToken`, `setSellTokenQuantityRemain`, etc.). A silently wrapped result (which can even be negative) can corrupt on-chain account balances/asset amounts, causing incorrect settlement amounts, potential creation or destruction of value in the DEX, and state divergence between what the order intended and what was actually settled — a concrete accounting/settlement impact reachable by any unprivileged user simply placing market orders.

### Likelihood Explanation
Exploitability depends on the concrete value of `dynamicStore.getMarketQuantityLimit()` at runtime, which I was not able to confirm within this session (index/tooling budget exhausted before locating the default/genesis-configured value). If the configured limit is large enough that two limit-sized quantities can multiply to exceed `Long.MAX_VALUE` while a legitimately-created maker order can have a very small `buyTokenQuantity` (the validate check only requires `> 0`), the overflow path is trivially reachable by any user through normal `MarketSellAssetContract` transactions — no privileged role is required. This is a real, code-verified defect (missing `longValueExact()`), but I could not fully confirm the exact numeric threshold needed to trigger it without further investigation of `DynamicPropertiesStore.getMarketQuantityLimit()`'s configured value, which should be verified before treating this as confirmed exploitable in production.

### Recommendation
Change `MarketUtils.multiplyAndDivide` to use `longValueExact()` instead of `longValue()` for the `BigInteger` fallback path, and have `MarketSellAssetActuator`/`matchSingleOrder` catch the resulting `ArithmeticException` and fail the trade (or actuator execution) safely rather than allowing the transaction to proceed with a silently corrupted quantity. Additionally, consider bounding the product `sellTokenQuantity * buyTokenQuantity` explicitly in `validate()`, not just each operand individually.

### Proof of Concept
1. User A creates a `MarketSellAssetContract` maker order selling `sellTokenQuantity = quantityLimit` of token X for `buyTokenQuantity = 1` of token Y (passes validation since both are `> 0` and `<= quantityLimit`); order rests in the book via `saveRemainOrder`.
2. User B submits a taker `MarketSellAssetContract` with `sellTokenQuantityRemain` also near `quantityLimit` for token Y against token X.
3. `matchSingleOrder` invokes `MarketUtils.multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity=1, ...)` — i.e., `a*b/1` with `a,b` near `quantityLimit`; if `quantityLimit^2 > Long.MAX_VALUE`, `multiplyExact` throws, the `BigInteger` fallback computes the true huge value, and `longValue()` silently truncates it into an arbitrary (possibly negative) `long`.
4. That corrupted value is passed to `addTrxOrToken`, directly mutating account balances/asset amounts, producing incorrect settlement without any exception or validation.

(Confirming exploitability requires knowing the exact configured `MarketQuantityLimit`, which was not verified in this session.)

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
