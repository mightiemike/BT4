### Title
KVSessionStorage `findSessionsByShop` unbounded shop-session-index growth causes DoS of `APP_UNINSTALLED` webhook handler and `ensureInstalledOnShop` auth middleware - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
`KVSessionStorage.storeSession()` appends the stored session's id to a per-shop index list (`shop:{shop}`) on every call, without checking whether the id is already present, unlike the equivalent Redis implementation. Because this index is read entirely and iterated by `findSessionsByShop()`, repeated legitimate session-store operations for the same shop cause the index array to grow without bound, eventually causing timeouts/failures in code paths that depend on `findSessionsByShop`, including the `APP_UNINSTALLED` webhook handler and the `ensureInstalledOnShop` auth middleware.

### Finding Description
`storeSession` unconditionally calls `addShopIds`, which reads the current array and concatenates the new id(s) without deduplication: [1](#0-0) [2](#0-1) 

Compare this to the Redis implementation, which explicitly guards against duplicates before pushing to the per-shop list: [3](#0-2) 

Any operation that re-invokes `storeSession` for a shop — including normal OAuth re-authentication, token refresh flows, or repeated online-token issuance (where non-embedded apps mint a new random session id via `crypto.randomUUID()` on every OAuth completion) — appends another entry to the KV list, even when the underlying session id is unchanged or superseded. Nothing in `KVSessionStorage` caps, dedups, or prunes this list. `findSessionsByShop` then reads the full array and performs a KV `get` for every id in it, sequentially inflating latency/costs proportional to the (attacker- or merchant-triggerable) index size: [4](#0-3) 

This is directly consumed by `AppInstallations.includes()`/`.delete()`, which require `findSessionsByShop` and `deleteSessions` to be implemented: [5](#0-4) 

`AppInstallations.delete()` is invoked directly from the `APP_UNINSTALLED` webhook handler, an unauthenticated-but-HMAC-verified request-authentication code path that a single merchant can trigger repeatedly (e.g., by reinstalling/uninstalling the app): [6](#0-5) [7](#0-6) 

The same `AppInstallations` object is also consulted (via `findSessionsByShop`) from install-check code paths, and `deleteSessions` on `KVSessionStorage` iterates ids one at a time: [8](#0-7) 

This is the same bug class as the referenced FeeSplitter finding: an unbounded, attacker/merchant-growable list is iterated in full by a critical function (`_sendFees()` ↔ `findSessionsByShop()`/`deleteSessions()`), with no cap on the list size, causing denial of service in downstream consumers that must complete the iteration (fund-withdrawal functions ↔ webhook uninstall handling and install-check middleware).

### Impact Explanation
Once the per-shop id list grows large (from repeated re-auth/reinstalls for a single shop), `findSessionsByShop` performs one KV read per stale id sequentially, and `deleteSessions` performs one KV delete per id sequentially. This degrades or times out the `APP_UNINSTALLED` webhook processing (so a shop can never be cleanly uninstalled/cleaned up, and Shopify's webhook retry/backoff may eventually stop retrying, leaving stale data) and can also degrade any consumer relying on `findSessionsByShop` for install checks in `shopify-app-express`. This is a denial-of-service on request-authentication/session-management infrastructure for the affected shop, scoped to KV-backed deployments (e.g., Cloudflare Workers KV).

### Likelihood Explanation
No malicious intent beyond ordinary app usage is strictly required — repeated legitimate flows (reinstall/uninstall cycles, or repeated online-token OAuth completions for non-embedded apps, which mint a fresh random session id each time) will unconditionally grow the list. A single merchant/attacker can trivially accelerate this by repeatedly reinstalling the app or repeating the OAuth flow, with no rate limiting or cap in `KVSessionStorage`.

### Recommendation
In `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`, mirror the Redis adapter's deduplication logic in `addShopIds` (only push the id if not already present), and/or switch the per-shop index to a `Set`-like structure keyed by id (e.g., store one KV key per `shop:{shop}:{id}` and use `list()` to enumerate) so stale/duplicate entries cannot accumulate. Additionally, prune ids from the index whenever `deleteSession`/`deleteSessions` runs (already attempted via `removeShopIds`, but this only removes ids explicitly deleted — it does not fix duplicate accumulation from repeated `storeSession` calls with the same id) and consider bounding the maximum index size with eviction of stale/expired sessions.

### Proof of Concept
1. Configure an app to use `KVSessionStorage` in a non-embedded, online-token OAuth flow (or any flow where `storeSession` may be called repeatedly for a shop).
2. Trigger repeated OAuth completions or app reinstalls for the same shop (e.g., a merchant clicking install/uninstall several thousand times, or repeated online token issuance which uses `crypto.randomUUID()` per completion, per `create-session.ts`).
3. Each call to `storeSession` appends to `shop:{shop}` in KV without checking for existing entries (`kv.ts` lines 75-79), so the array length grows linearly with the number of store operations, with no cap.
4. Trigger `APP_UNINSTALLED` webhook (or any code calling `findSessionsByShop`/`deleteSessions`); observe that the handler must sequentially read/delete every accumulated id, which measurably increases latency and can time out or fail entirely on the underlying request-authentication/session-cleanup handler as the shop's index grows large.

      {type: 'json'},
    );

  private async addShopIds(shop: string, ids: string[]) {
    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
  }
