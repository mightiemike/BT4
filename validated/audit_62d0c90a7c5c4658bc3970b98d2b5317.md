### Title
Permanent token loss when `DeleteAccount`'s `beneficiary_id` does not exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` unconditionally emits a `Receipt::new_balance_refund` to the caller-supplied `beneficiary_id` without verifying the beneficiary account exists. Because balance-refund receipts are refund receipts (`predecessor_id == "system"`), they can never implicitly create an account (`implicit_creation_allowed` returns `false` whenever `is_refund` is `true`). If `beneficiary_id` does not exist, the refund's `Transfer` action fails with `AccountDoesNotExist`, and per the documented refund semantics ("If the execution of a refund fails, the refund amount is burnt"), the account's entire remaining balance is permanently destroyed.

### Finding Description
When an account is deleted, `action_delete_account` pays out the account's current balance to `beneficiary_id` via a refund receipt: [1](#0-0) 

The only validation ever performed on `beneficiary_id` is a syntax check, not an existence check: [2](#0-1) 

Because the resulting receipt is a system/refund receipt, `check_account_existence`'s `implicit_creation_allowed` helper unconditionally refuses to create the destination account for it: [3](#0-2) 

And the runtime's documented behavior for a failed refund is that the funds are burnt rather than returned to anyone: [4](#0-3) [5](#0-4) 

This is also acknowledged directly in the test suite, which deliberately pre-creates the beneficiary account and notes why: "The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" (and that refund would then fail and burn): [6](#0-5) 
There is also an explicit regression test proving a refund can never create even a "universal" implicit account: [7](#0-6) 

### Impact Explanation
Any account owner (or any contract issuing a self-delete via a promise batch, or a relayer executing a meta-transaction) who submits `DeleteAccount { beneficiary_id }` with a `beneficiary_id` that does not exist on-chain (a typo, a deleted/never-created sub-account, etc.) causes the entire remaining NEAR balance of the deleted account to be irrecoverably burnt instead of transferred. This is a direct, transaction-triggered, permanent loss of user funds — no attacker cooperation from a third party is required, and there is no way to recover the burnt tokens. This matches the reported bug class (funds permanently lost because the chosen recipient cannot receive them) but manifests here as protocol-level token burning rather than tokens being stuck in a contract.

### Likelihood Explanation
This is trivially reachable by any single unprivileged account: constructing a `DeleteAccount` action with an accidental or intentionally wrong `beneficiary_id` requires nothing more than including that action in a normal transaction, a meta-transaction (`Delegate`), or a promise generated from a `FunctionCall` (`append_action_delete_account`). No special permissions, timing, or coordination are needed, and the failure mode (silent burn rather than a hard error surfaced to the end user in an obviously actionable way) makes accidental fund loss realistic, e.g. a typo'd beneficiary account ID.

### Recommendation
Before generating the balance-refund receipt in `action_delete_account`, verify that `beneficiary_id` refers to an existing account (or reject the action up front in `validate_delete_action`/at execution time and leave the account undeleted, similar to how `DeleteAccountWithLargeState` or `GasKeyBalanceTooHigh` currently reject and leave the account unchanged). Alternatively, allow the refund receipt to implicitly create the beneficiary account when it doesn't exist, rather than unconditionally burning the balance.

### Proof of Concept
1. Create account `victim.near` with a non-zero balance and no locked stake.
2. From `victim.near` (or via a promise/meta-transaction targeting it), submit a transaction with a single, final `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "does-not-exist.near" })`, where `does-not-exist.near` has never been created.
3. `action_delete_account` (`runtime/runtime/src/actions.rs:380-386`) pushes a `Receipt::new_balance_refund(&"does-not-exist.near", account_balance)` and deletes `victim.near`.
4. When the resulting refund receipt is applied, `check_account_existence` sees `Action::Transfer` targeting a nonexistent account with `is_refund = true`, so `implicit_creation_allowed` returns `false`, producing `ActionErrorKind::AccountDoesNotExist`.
5. Per `runtime/runtime/src/lib.rs:1047-1055`, since the failing receipt's `predecessor_id` is `"system"`, its full deposit (`victim.near`'s entire balance) is added to `other_burnt_amount` — the funds are gone forever, credited to no account.
