## Title
Divide-before-multiply precision loss in legacy vote reward computation causes systematic underpayment/loss of staking rewards - (`chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The Sherlock report flags `claim_batch()` for dividing before multiplying (`amount_per_claim = amount * rate / PRECISION` then `* number_of_claims`), which truncates the intermediate result and can zero out or shrink the final payout. Java-tron's legacy (pre-Vi-algorithm) vote reward computation in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` has the same structural flaw: it computes `voteRate = (double) userVote / totalVote` first, then multiplies by `totalReward`, using floating point instead of integer/BigInteger math, truncating to `long` on every cycle iteration.

### Finding Description
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a super representative's reward for one cycle as:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
``` [1](#0-0) 

This divides `userVote / totalVote` first (losing precision immediately when `userVote << totalVote`), then multiplies by `totalReward`, and the assignment `reward += ...` implicitly narrows the `double` result to `long`, truncating any fractional reward on every cycle. This is invoked in a loop, once per cycle, from `getOldReward`:
```java
private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
}
``` [2](#0-1) 

which is only bypassed when the `allowOldRewardOpt` committee parameter is enabled — otherwise this divide-then-multiply/truncate-per-cycle path is the one actually executed for every cycle prior to `newRewardAlgorithmEffectiveCycle`: [3](#0-2) 

The reachable, unprivileged entry point is the ordinary `WithdrawBalanceContract` transaction, processed by `WithdrawBalanceActuator.execute`, which calls `mortgageService.withdrawReward(...)` directly, with no privileged-actor requirement: [4](#0-3) 

By contrast, the newer reward algorithm (`RewardViCalService` / `MortgageService.computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)`) correctly multiplies before dividing, using `BigInteger`:
```java
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
``` [5](#0-4) 

confirming that the legacy `computeReward(long cycle, ...)` path is the analog of the reported flaw: it is the divide-first implementation that the fixed/hardened code elsewhere in the same class deliberately avoids.

### Impact Explanation
When `userVote` is small relative to `totalVote` (a very common case for small voters on any super representative with a large total vote), `(double) userVote / totalVote` can produce a very small double that, multiplied by `totalReward` and truncated to `long` each cycle, rounds down to zero or a smaller integer than the mathematically correct proportional share. Because this happens per-cycle inside a loop (`for (long cycle = begin; cycle < end; cycle++) reward += computeReward(cycle, votes);`), the truncation error accumulates across every affected cycle, permanently and systematically underpaying voters their staking rewards — i.e., partial loss of funds, exactly the impact class described in the report ("loss of precision, and in the worst case may not be possible to retrieve the funds").

### Likelihood Explanation
This path executes whenever `allowOldRewardOpt` is not enabled and reward cycles fall before `newRewardAlgorithmEffectiveCycle` — this is the default/legacy path for any chain (including private/consortium deployments built from this codebase, or historical unclaimed reward ranges) that has not turned the optimization on via committee proposal. It requires no privileged access: any account holder with unclaimed legacy-cycle voting rewards triggers it merely by broadcasting a standard `WithdrawBalanceContract` transaction.

### Recommendation
Replace the double-based `voteRate * totalReward` computation with integer/BigInteger arithmetic that multiplies before dividing, mirroring the approach already used in the newer Vi-based algorithm:
```java
reward += BigInteger.valueOf(totalReward)
    .multiply(BigInteger.valueOf(userVote))
    .divide(BigInteger.valueOf(totalVote))
    .longValue();
```
This avoids the early precision loss from floating-point division and per-cycle truncation to `long`.

### Proof of Concept
1. Configure a chain (or use a private/consortium java-tron network) where `allowOldRewardOpt` is disabled (default, unless explicitly enabled via committee proposal) and rewards exist in cycles before `newRewardAlgorithmEffectiveCycle`.
2. A witness `srAddress` receives `totalReward` in cycle `c`, with `totalVote` for that cycle being large (e.g., 100,000,000) while a particular voter's `userVote` is small (e.g., 1).
3. Call `MortgageService.withdrawReward(voterAddress)` (triggered via a normal `WithdrawBalanceContract` transaction) which internally calls `getOldReward` → `computeReward(cycle, votes)`:
   - `voteRate = (double) 1 / 100000000 = 1e-8`
   - `reward += voteRate * totalReward` — if `totalReward` is small enough (e.g., below 1e8), the product truncates to `0` after narrowing to `long`, even though the voter is mathematically entitled to a nonzero (if tiny) share; across many cycles the cumulative loss is not compensated because each cycle's contribution is independently truncated to zero or rounded down.
4. Compare against the multiply-then-divide integer approach, which would correctly compute the fractional share via `BigInteger`, showing the accumulated payout differs (is lower) under the legacy floating-point implementation, confirming the precision-loss impact described in the referenced report.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
