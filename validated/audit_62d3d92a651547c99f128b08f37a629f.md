### Title
Executable-account rent-exemption check in `set_executable` is not re-validated after subsequent `set_data_length`/`checked_sub_lamports`, allowing a permanently non-rent-exempt executable account - ([File: transaction-context/src/instruction_accounts.rs])

### Summary
`BorrowedInstructionAccount::set_executable` only validates rent exemption against the account's data length *at the moment it is called*, using `self.get_data().len()`. Because `set_data_length` and `checked_sub_lamports`/`set_lamports` never re-check rent exemption against `executable` status, a program can shrink an account's data, mark it executable against the shrunk size, restore (or exceed) the original data length, and/or drain lamports afterward — leaving an executable account whose balance no longer covers the rent-exempt minimum for its actual size.

### Finding Description
`set_executable` (transaction-context/src/instruction_accounts.rs:286-311) performs:
```
if !self.transaction_context.rent.is_exempt(self.get_lamports(), self.get_data().len()) {
    return Err(InstructionError::ExecutableAccountNotRentExempt);
}
```
This is a one-time, point-in-time check. `set_data_length` (lines 197-207) and `extend_from_slice`/`set_data_from_slice` never consult rent exemption at all — they only enforce `can_data_be_resized` (delta/limits) via `transaction_accounts::can_data_be_resized`. Likewise `set_lamports`/`checked_sub_lamports`/`checked_add_lamports` (lines 120-161) never check rent exemption against the `executable` flag or current data length; they only enforce signer/owner/writability constraints on lamport movement.

Consequently a program owning account A can, within one instruction (or a CPI chain within one transaction):
1. `set_data_length(small_len)` — shrink data, lowering the effective rent-exempt minimum.
2. `set_executable(true)` — passes because it is validated only against `small_len`.
3. `set_data_length(large_len)` — grow the data back up (or larger), which does not re-check rent exemption for the now-executable account.
4. `checked_sub_lamports(x)` — remove lamports; also does not check the executable/rent invariant.

None of the individual checks catch this because each function only validates its own local precondition (writability, ownership, data growth limits, or rent-exemption *at call time*), and there is no cross-cutting invariant re-validated after each mutation that says "if this account is executable, verify it remains rent-exempt after this call." I attempted to locate any post-transaction or post-instruction-level global invariant check (e.g., in `transaction.rs`, `transaction_accounts.rs`, or bank-level `verify_account_changes`) that would catch a non-rent-exempt executable account at commit time, but I could not confirm the existence of such a re-validation step within the available index for this repo; this is a gap in what I could verify from the indexed files.

### Impact Explanation
If unenforced end-to-end, this would let an account become `executable=true` while permanently under-funded relative to its rent-exempt minimum, breaking rent-accounting invariants assumed elsewhere in the runtime (e.g., code that assumes any executable account is rent-exempt and thus never subject to rent collection/garbage collection). This maps to a "rent/lamport accounting corruption" class finding under Solana's runtime-invariant bounty categories, distinct from direct theft of funds — it does not enable inflation or fund theft by itself, but corrupts an invariant relied upon by downstream logic.

### Likelihood Explanation
This requires only an unprivileged attacker deploying and invoking their own SBF program that owns the target account and issues `set_data_length` → `set_executable` → `set_data_length` → `checked_sub_lamports` (or equivalent CPI sequence) in one instruction. No special permissions are needed beyond normal ownership of the account by the attacker's own program, which is trivially satisfiable. However, I was not able to confirm (given index limitations) whether a bank-level/whole-transaction rent-exemption re-check exists that would reject the transaction at commit time — if such a check exists, this finding is not exploitable end-to-end, and the report would need to be downgraded to invalid.

### Recommendation
- Add a post-mutation invariant so that any time an account's `executable` flag is `true`, subsequent `set_data_length`/`extend_from_slice`/`set_data_from_slice`/`set_lamports` calls re-validate rent exemption against the account's current lamports and (possibly changed) length, rejecting the mutation (or requiring closing/rent top-up) if it would leave an executable account non-rent-exempt.
- Alternatively/additionally, enforce a transaction-wide post-execution check (if not already present) that any account marked `executable` is rent-exempt before the transaction is allowed to commit.

### Proof of Concept
Add an SVM/bank integration test:
1. Create account A owned by a test program P, funded to be rent-exempt for a small size `S_small` and non-rent-exempt for the intended final size `S_large`.
2. In one instruction to P:
   - `set_data_length(S_small)`
   - `set_executable(true)` — expect success since validated against `S_small`.
   - `set_data_length(S_large)`
   - `checked_sub_lamports(k)` for some `k` making lamports below `Rent::minimum_balance(S_large)`.
3. Commit the transaction and assert it succeeds (i.e., is not rejected).
4. Assert on the resulting account state: `account.executable() == true` and `Rent::default().is_exempt(account.lamports(), account.data().len()) == false`, demonstrating the invariant violation.

If step 3 instead fails (transaction rejected) due to some existing invariant enforcement not visible in the indexed files, the finding should be treated as not reproducible/invalid.
