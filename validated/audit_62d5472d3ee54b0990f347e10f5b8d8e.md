### Title
Missing length validation on `PedersenHash` content before native `librustzcashMerkleHash` call reachable from `IncrementalMerkleVoucherContainer.append` - (File: `chainbase/src/main/java/org/tron/common/zksnark/IncrementalMerkleVoucherContainer.java`)

### Summary
`IncrementalMerkleVoucherContainer.append` forwards a `PedersenHash` (a protobuf message with an unconstrained `bytes content` field) into `IncrementalMerkleTreeContainer.append`, which under the "both left and right present" branch calls `PedersenHashCapsule.combine`, which calls `JLibrustzcash.librustzcashMerkleHash` directly on `a.getContent().toByteArray()` / `b.getContent().toByteArray()` with no length check. This is inconsistent with other JNI wrapper methods in the same class that explicitly validate fixed 32-byte lengths before calling into native code.

### Finding Description
`IncrementalMerkleVoucherContainer.append` (`chainbase/src/main/java/org/tron/common/zksnark/IncrementalMerkleVoucherContainer.java:38-67`) delegates directly to `IncrementalMerkleTreeContainer.append` for both the cursor path and the non-cursor path (lines 41, 63). Neither method performs any length/size validation on the incoming `PedersenHash obj` before use.

Inside `IncrementalMerkleTreeContainer.append` (`chainbase/src/main/java/org/tron/common/zksnark/IncrementalMerkleTreeContainer.java:92-124`), once both `left` and `right` are populated, the code calls: [1](#0-0) 
which invokes `PedersenHashCapsule.combine(treeCapsule.getLeft(), treeCapsule.getRight(), 0)`.

`PedersenHashCapsule.combine` passes the raw content bytes straight to the native call with no size check: [2](#0-1) 

`JLibrustzcash.librustzcashMerkleHash` itself performs no validation either, in contrast with sibling methods in the same class (e.g. `librustzcashAskToAk`, `librustzcashToScalar`, `librustzcashTreeUncommitted`) which explicitly call `LibrustzcashParam.valid32Params(...)` / `validParamLength(...)` before invoking the native `INSTANCE` methods: [3](#0-2) [4](#0-3) 

The `PedersenHash.content` field is a protobuf `bytes` field with no length constraint enforced at the proto level, and its origin (e.g. a shielded output's note commitment) is attacker-supplied data inside a shielded transaction. If the byte array is not exactly 32 bytes, it is passed unchecked to `librustzcashMerkleHash`, whose underlying Rust/JNI implementation is expected to operate on fixed 32-byte buffers; a shorter/longer array can result in out-of-bounds native memory access when the native side copies or dereferences the buffer without checking the JNI array's actual length.

I was unable to fully trace, within the available tool budget, whether the shielded-transfer actuator's `validate()` step enforces a 32-byte length on note-commitment bytes *before* they reach this append/combine path (i.e., whether SNARK proof verification always precedes the merkle-tree append in execution order). This uncertainty affects exact reachability but the core defect — missing length validation in the append→combine→native call chain — is confirmed by direct code reading.

### Impact Explanation
If reachable with unvalidated commitment length, this could cause an out-of-bounds native memory read/write in the JNI boundary, crashing the node process (DoS) or, depending on the native implementation's memory-safety handling, potentially worse memory corruption — matching "Node RCE / crash (Fatal/Advanced)".

### Likelihood Explanation
Exploitability depends entirely on whether an attacker can get an unvalidated, non-32-byte `PedersenHash.content` value into the merkle tree append path via a shielded transaction before any other validation (e.g., zk-SNARK proof checks with their own `valid32Params` gating) rejects it. Without confirming that ordering, I cannot assert this is a fully unmitigated, end-to-end reachable path from an unprivileged attacker's transaction — only that the `append`/`combine`/`librustzcashMerkleHash` code itself lacks the invariant "validates all lengths before native call" that other JLibrustzcash wrapper methods enforce.

### Recommendation
Add explicit length validation (`LibrustzcashParam.valid32Params(...)`) on both operands in `PedersenHashCapsule.combine` before calling `JLibrustzcash.librustzcashMerkleHash`, and/or validate `PedersenHash.getContent()` size (== 32 bytes) at the point of ingestion from transaction data (e.g., in the shielded-transfer actuator's `validate()`) before any commitment is appended to `IncrementalMerkleVoucherContainer`/`IncrementalMerkleTreeContainer`.

### Proof of Concept
```java
// JUnit sketch demonstrating the missing pre-call length validation
@Test
public void appendMalformedLengthPedersenHash() throws Exception {
  IncrementalMerkleTreeContainer tree =
      new IncrementalMerkleTreeContainer(new IncrementalMerkleTreeCapsule());

  // valid 32-byte first leaf
  PedersenHash valid = PedersenHash.newBuilder()
      .setContent(ByteString.copyFrom(new byte[32]))
      .build();
  tree.append(valid);

  // malformed second leaf: e.g. 1 byte instead of 32
  PedersenHash malformed = PedersenHash.newBuilder()
      .setContent(ByteString.copyFrom(new byte[1]))
      .build();

  // Expectation: append() should reject malformed length BEFORE reaching
  // PedersenHashCapsule.combine -> JLibrustzcash.librustzcashMerkleHash.
  // Currently no such check exists, so this proceeds to the native call
  // with a mismatched-length buffer.
  tree.append(malformed); // triggers combine() -> native call with 1-byte array
}
```
Currently, no `ZksnarkException` (or equivalent) is thrown for the malformed length prior to the native call, confirming the missing invariant described in the question.
