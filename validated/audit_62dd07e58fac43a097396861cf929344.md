### Title
Uncontrolled Resource Consumption via Oversized Action Receipts Bypassing `max_receipt_size` (issue #12606) - (File: `runtime/runtime/src/lib.rs`)

### Summary
An unprivileged contract deployer/caller can trigger creation of action or data receipts that exceed the protocol's `max_receipt_size` hard limit by using `promise_return`/`value_return` in a receipt that also has `output_data_receivers`. The size check in `validate_receipt` runs before `output_data_receivers` is appended to the already-validated new receipt, so the final persisted/broadcast receipt can be larger than the configured hard limit intended to bound `ChunkStateWitness` size and cross-shard transfer size. This is the exact bug class of the reference advisory (CWE-400/770, uncontrolled resource consumption): a single untrusted input causes memory/bandwidth/storage consumption beyond the system's declared bound.

### Finding Description
`Runtime::process_action_receipt` extends `output_data_receivers` onto an already-created new receipt *after* it has passed size validation: [1](#0-0) 

This is done for the `ReturnData::ReceiptIndex` case — when a contract's execution returns a promise index (via `promise_return`) instead of a value, and the calling receipt has `output_data_receivers`, the runtime mutates the *new* receipt in place, growing its serialized size with each `DataReceiver` entry, without re-checking `max_receipt_size`.

The size check itself only fires at `ValidateReceiptMode::NewReceipt` time, immediately after receipt construction and before this mutation: [2](#0-1) 

The codebase explicitly acknowledges this is a known, unresolved bug — a separate, more tolerant validation mode (`ExistingReceipt`) was added specifically to keep the runtime from crashing when it encounters receipts that violate `max_receipt_size`: [3](#0-2) 

Test coverage in the repository directly demonstrates the exploit: a `promise_return` used together with `output_data_receivers` produces a receipt whose size exceeds `max_receipt_size`, and the runtime does not reject it: [4](#0-3) [5](#0-4) 

A separate root cause path exists for `value_return`: the returned value is checked only against `max_length_returned_data` (independent of the full data-receipt/`max_receipt_size` framing), and the data receipt built from it can subsequently exceed `max_receipt_size` once wrapped: [6](#0-5) 

`docs/misc/state_witness_size_limits.md` documents that the entire `ChunkStateWitness` size budget (~21 MiB) is built on the assumption that individual receipts stay under `max_receipt_size` (4 MiB); an oversized receipt directly undermines that budget: [7](#0-6) 

Partial mitigation exists in cross-shard forwarding: `try_forward`/bandwidth-request generation clamp oversized receipts to `max_receipt_size` for admission accounting purposes so they are not permanently stuck, but this is only a workaround for forwarding logic, not a fix to the root size-validation gap: [8](#0-7) [9](#0-8) 

### Impact Explanation
Any account that deploys and calls a contract (fully unprivileged, reachable via a single signed transaction) can produce receipts that exceed `max_receipt_size` by up to the size of `max_length_returned_data`/`output_data_receivers` overhead. Because `max_receipt_size` is a load-bearing invariant for:
- Bounding `ChunkStateWitness` size (used by all chunk validators),
- Bounding storage-proof/state generated during application,
- Bounding bandwidth-scheduler and congestion-control accounting (`compute_receipt_size`),

an oversized receipt can inflate resource consumption (memory, network bandwidth for witness distribution, storage) beyond the limits the protocol was designed to guarantee, matching the "uncontrolled resource consumption" class in the reference CVE. It does not by itself cause fund loss or a state-root fork (the oversized receipt is still applied consistently by all nodes, and the workaround clamps forwarding accounting), but it is a concrete, reachable violation of a hard, documented size invariant that other subsystems rely on for resource bounding — this is the direct analog of the Artemis "uncontrolled resource consumption via unbounded message size" bug class.

### Likelihood Explanation
High reachability: no special privileges are required — deploying and calling a WASM contract that issues `promise_create`/`promise_then`/`promise_return` with `output_data_receivers`, or that returns a large value near `max_length_returned_data`, is sufficient. The bug is already reproduced by first-party tests in this exact repository state (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`), confirming the code path is live and unresolved on this branch.

### Recommendation
Re-validate receipt size (`validate_receipt` with `ValidateReceiptMode::NewReceipt`) after `output_data_receivers` is appended in `Runtime::process_action_receipt` (around `lib.rs:1152-1170`), and reject/refund the transaction with `ReceiptSizeExceeded` if the post-mutation size exceeds `max_receipt_size`, rather than allowing an oversized receipt to be persisted and only tolerated later via `ValidateReceiptMode::ExistingReceipt`. Additionally, tighten `value_return`'s check to account for the full data-receipt framing overhead per receiver, not just `max_length_returned_data`, mirroring the approach already taken for `max_receipt_total_input_size`.

### Proof of Concept
1. Deploy `near_test_contracts::rs_contract()` (or any contract using the promise API) to an account.
2. Call a method that: creates promise `A`, then `A.then(B)`, and inside `A`'s execution creates a further promise `C` via `promise_create`, then calls `promise_return(C)` — this is exactly what `max_receipt_size_promise_return_method1`/`method2` in the test contract do (see `runtime/near-test-contracts/test-contract-rs/src/lib.rs:1988-2018`).
3. Size the padding/args of `C`'s receipt so that, before `output_data_receivers` is appended, it is exactly at `max_receipt_size` (4 MiB) as computed in the test: [10](#0-9) 
4. Because `A` has an `output_data_receivers` entry (from the `.then(B)` link) and returns `ReturnData::ReceiptIndex` for `C`, the runtime appends `A`'s `output_data_receivers` onto `C`'s already-validated receipt (`lib.rs:1152-1170`), pushing `C` above `max_receipt_size` without any subsequent validation.
5. `assert_oversized_receipt_occurred` in the test suite confirms the runtime accepts and processes the oversized receipt rather than rejecting the transaction — reproducible today via `cargo test -p test-loop-tests test_max_receipt_size_promise_return`.

/// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }
