This confirms the key mechanic: standard Cosmos SDK ante handler semantics commit ante-branch state changes (fee deduction, sequence increment, and here, new account creation) independently of whether `runMsgs` later succeeds — that's exactly why sequence numbers increment even on failed messages. `AccountInitDecorator` sits in this ante chain [1](#0-0) , and unconditionally creates and persists a brand-new on-chain account for any address that (a) signs a tx whose messages are all in the gasless whitelist and (b) doesn't already have an account — with no bond, funding, or validator-membership check at that point [2](#0-1) . The gasless whitelist itself only checks message *type URLs*, not any relationship between signer and the actual business authorization (e.g., `MsgVoteInbound`/`MsgVoteTssKeyProcess` require a bonded Universal Validator, but that check happens deep inside the msg-server handler, long after the account has already been created and committed) [3](#0-2) [4](#0-3) .

### Title
Unbounded free account creation via gasless AccountInitDecorator leads to persistent on-chain state-bloat DoS - (File: app/ante/account_init_decorator.go)

### Summary
The external report's core issue is that unauthenticated network participants can force a validator to accept and persist unbounded, low-cost resource records (fake peer entries) with no gate other than a signature check and no cap on total resource growth. The scoped Push Chain analog is `AccountInitDecorator`, which persists a brand-new on-chain `BaseAccount` record for **any** self-generated keypair, at zero fee, as long as the surrounding transaction's message types are on the gasless whitelist — regardless of whether the underlying gasless message will ultimately be authorized to do anything.

### Finding Description
`NewCosmosAnteHandler` chains `NewAccountInitDecorator` before signature/fee decorators [5](#0-4) . Its `AnteHandle` logic is:

1. If the tx is gasless (`IsGaslessTx`) and the sole signer has no account yet, verify a signature over `account_number=0, sequence=0`, then call `aid.ak.NewAccountWithAddress` + `SetAccount` and short-circuit the rest of the chain [2](#0-1) .
2. `IsGaslessTx` only inspects message *type URLs* against a static allowlist (`MsgExecutePayload`, `MsgVoteInbound`, `MsgVoteOutbound`, `MsgVoteChainMeta`, `MsgVoteTssKeyProcess`, `MsgVoteFundMigration`, `MsgMigrateUEA`) — it does not check whether the signer is actually a bonded Universal Validator or otherwise authorized [3](#0-2) .
3. An attacker only needs to generate a fresh keypair locally, sign a syntactically valid `MsgVoteInbound` (or any other whitelisted message) with that keypair, and broadcast it. `DeductFeeDecorator` skips fee deduction and `MinGasPriceDecorator` skips the minimum-fee check for gasless txs, so this costs the attacker nothing economically [6](#0-5) .
4. The actual authorization check (`IsBondedUniversalValidator`) happens later, in the msg server, after the ante chain (including account creation) has already run and been committed [7](#0-6) . Standard Cosmos SDK `runTx` semantics commit ante-branch state independently of `runMsgs` outcome — this is the same mechanism by which sequence numbers persist on failed message execution, and it applies identically here: the new account record survives even though the wrapped `MsgVoteInbound`/`MsgVoteTssKeyProcess` call will subsequently fail with "not bonded."

The net effect: any unprivileged party can, at negligible cost (one keypair generation + broadcast, no fee, no stake, no bond), cause every full node to permanently persist a new account entry in the `auth` module's KV store. This is directly analogous to the peer-list report's core defect — an unauthenticated actor can force acceptance of attacker-controlled, low-verification-cost resource records with no size limit on the resulting resource pool — except here the "peer list" is Push Chain's canonical account store, and the "peer" is a throwaway keypair.

### Impact Explanation
This is a state-growth denial-of-service vector, not a network-level packet flood: each accepted tx permanently and irreversibly grows the `auth` module's account store on **every** node in the network (full nodes and validators alike must apply the same state transition to stay in consensus). Because account records are never pruned, this is a persistent disk/memory cost imposed on all validators and full nodes, degrading state-store performance, snapshot/IAVL tree size, and sync times over time — with the attacker paying essentially nothing per unit of imposed cost. This falls within the "denial of service only when it is not network-level and is reachable without privileged control" allowed-impact category, since the trigger requires no validator/relayer/TSS privilege — just a self-generated keypair and network access to broadcast a tx.

### Likelihood Explanation
High. No special permissions, funds, or validator/UV bonding are required. An attacker can script generation of arbitrary numbers of keypairs and broadcast gasless `MsgVoteInbound`/`MsgVoteOutbound`/`MsgVoteChainMeta`/`MsgVoteTssKeyProcess`/`MsgVoteFundMigration`/`MsgExecutePayload` transactions continuously; each is accepted into a block as long as it passes ante checks (which it will, since it only needs a self-consistent signature over sequence 0), even though the wrapped business message subsequently fails authorization deep in the corresponding msg server.

### Recommendation
Mirror the audit report's own recommendation of bounding resource growth for unauthenticated/low-cost interactions:
- Perform (or at minimum pre-check) the message-specific authorization gate (e.g., `IsBondedUniversalValidator` for TSS/vote messages, valid `UniversalAccountId` binding for `MsgExecutePayload`) inside `AccountInitDecorator` (or a preceding decorator) *before* creating and persisting the new account, so unauthorized signers cannot trigger permanent state writes.
- Alternatively/additionally, impose a minimum tiny bond, rate limit, or per-block/per-signer cap on gasless-triggered new-account creation, and/or expire/garbage-collect never-used accounts created this way.

### Proof of Concept
1. Generate a fresh secp256k1/ed25519 keypair (`newAddr`) that has never held an account on Push Chain.
2. Construct a `MsgVoteInbound` (or any gasless-whitelisted message) with `Signer = newAddr`, sign it with `account_number=0, sequence=0` per `AccountInitDecorator.verifySignatureForNewAccount`.
3. Broadcast the tx. `IsGaslessTx` passes (message type is whitelisted), `MinGasPriceDecorator`/`DeductFeeDecorator` skip fee checks, `AccountInitDecorator` creates and commits a new `BaseAccount` for `newAddr` with `sequence=1`.
4. The subsequent `VoteTssKeyProcess`/`VoteInbound` msg-server call fails with "not bonded" — the tx as a whole is a `DeliverTx` failure — but the account creation from step 3 persists on-chain regardless (identical to how sequence increments survive failed messages under standard `runTx`/ante-branch-commit semantics).
5. Repeat steps 1–4 with a new keypair each time, at zero fee, to grow the `auth` module store without bound.

// IsGaslessTx checks if a transaction contains only allowed gasless message types
// Returns true if all messages in the transaction are in the allowed gasless message types
func IsGaslessTx(tx sdk.Tx) bool {
	var (
		// GaslessMsgTypes defines the message types that are allowed in gasless transactions
		GaslessMsgTypes = []string{
			sdk.MsgTypeURL(&uexecutortypes.MsgMigrateUEA{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgExecutePayload{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteInbound{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteOutbound{}),
			sdk.MsgTypeURL(&utsstypes.MsgVoteTssKeyProcess{}),
			sdk.MsgTypeURL(&utsstypes.MsgVoteFundMigration{}),
			sdk.MsgTypeURL(&uexecutortypes.MsgVoteChainMeta{}),
		}
	)

	msgs := tx.GetMsgs()
	if len(msgs) == 0 {
		return false
	}

	for _, msg := range msgs {
		switch m := msg.(type) {
		case *authz.MsgExec:
			// Only gasless if ALL inner messages are allowed
			for _, innerMsg := range m.Msgs {
				if !slices.Contains(GaslessMsgTypes, innerMsg.TypeUrl) {
					return false
				}
			}
		default:
			if !slices.Contains(GaslessMsgTypes, sdk.MsgTypeURL(msg)) {
				return false
			}
		}
	}
	return true
}
