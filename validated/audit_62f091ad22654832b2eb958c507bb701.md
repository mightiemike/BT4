Confirmed: the webhook HMAC in `validate.ts`/`hmac-validator.ts` is computed only over `rawBody`, and the `domain` header (shop identity, used later to load the offline session) is read separately via `checkWebhookHeaders`/`checkWebhooksHeaders` without ever being included in the signed material, and without cross-checking it against anything derived from the signature.### Title
Webhook `X-Shopify-Shop-Domain` header is unauthenticated, allowing cross-tenant impersonation in webhook processing - (File: packages/apps/shopify-api/lib/utils/hmac-validator.ts)

### Summary
`validateHmacFromRequestFactory` verifies only that the **raw body** of an incoming webhook was signed with the app's shared client secret. It never binds the `X-Shopify-Shop-Domain` (or events `Domain`) header, the topic, or the webhook ID to that signature. `validateFactory` in `webhooks/validate.ts` then trusts the unauthenticated `domain` header verbatim and returns it as the shop identity for the webhook, which downstream code (`authenticateWebhookFactory` in the Remix/React Router packages) uses to load the offline session and construct authenticated Admin/Storefront API clients for that shop.

### Finding Description
`validateHmacFromRequestFactory` computes the expected HMAC from `rawBody` alone: [1](#0-0) 

The header carrying the shop identity (`domain`) is read completely independently, after HMAC success, with no cross-check against the signed payload: [2](#0-1) [3](#0-2) 

That unauthenticated `domain` value is passed straight to `ensureValidOfflineSession(params, check.domain)`, and the resulting session (with its access token) is attached to the request context: [4](#0-3) 

Because the app's `apiSecretKey` is a single shared secret for the whole app across **all** installed shops (not per-shop), this is analogous to the referenced H-12 pattern: the code validates that "some legitimate party signed this" (the app's own secret over the body — comparable to checking only the lender's signature) but never validates that the party is authorized to act as the specific shop named in the header (comparable to missing the borrower-authorization check). Any merchant who has installed the app (an unprivileged, low-trust actor relative to other tenants) can trigger genuine webhooks for their own store and obtain valid `(rawBody, hmac)` pairs signed with the same app secret used for every other merchant. Since the domain header is not part of the signed material, that same valid `(rawBody, hmac)` pair can be replayed with an arbitrary forged `X-Shopify-Shop-Domain` header claiming to be a victim's shop, and the HMAC check will still pass.

### Impact Explanation
If the forged domain matches an existing offline session, the webhook handler executes with that victim shop's session/Admin API client and attacker-controlled body content (topic, payload) — a cross-tenant impersonation/confusion. This can trigger business logic (e.g., `app/uninstalled`, order/product handlers, custom app hooks) for a shop the attacker does not control, using data the attacker fabricated (subject to matching the topic's normal payload shape, since only the raw body bytes need to match a previously-obtained valid signature, or the attacker can request Shopify's server to sign arbitrary content for their own shop and just swap the header). This maps to the "cross-tenant access" / "accepted forged Shopify request" categories.

### Likelihood Explanation
Reachable from a single merchant/customer-controlled webhook delivery (unprivileged actor) with no additional secrets: the attacker only needs to install the app on any shop (or already have it installed) to obtain valid signed bodies, then POST to the app's webhook endpoint with a swapped `X-Shopify-Shop-Domain` header. This is a documented characteristic of Shopify's own webhook HMAC scheme (HMAC over body only), so it is a systemic design gap rather than an implementation typo, but it is squarely inside `shopify-app-js`'s webhook validation/authentication code path (`validate.ts`, `hmac-validator.ts`, `authenticate.ts`), which is what actually decides which shop's session to load and expose to app code.

### Recommendation
- Bind the shop domain (and ideally topic/webhook ID) into the value that's authenticated, or independently verify that the `X-Shopify-Shop-Domain` header corresponds to a shop that actually has this exact `webhookId` registered/pending (Shopify assigns a unique `webhookId` per delivery per shop; cross-checking it, e.g. via idempotency/dedup storage keyed by shop, would catch replays across shops).
- At minimum, document/enforce that consumers must treat the `domain` header as attacker-influenceable and not implicitly trust it for authorization decisions beyond session lookup, and add server-side webhook ID deduplication scoped per shop to prevent replay-based cross-tenant reuse.
- Consider verifying that the offline session's own stored shop matches an out-of-band signal (e.g., only proceed if a session for that domain was created via this app's real OAuth/install flow shortly before, or track subscription IDs returned at webhook registration time).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`. The app is granted access and Shopify begins delivering webhooks (e.g. `orders/create`) signed with `HMAC-SHA256(rawBody, apiSecretKey)` in `X-Shopify-Hmac-Sha256`.
2. Attacker captures a legitimate `(rawBody, hmac)` pair from one of these deliveries (or crafts an order on their own store whose serialized body has the shape needed to be processed as a webhook for another shop's topic).
3. Attacker sends `POST /webhooks` directly to the merchant app's webhook endpoint with:
   - the captured `rawBody` and `X-Shopify-Hmac-Sha256` unchanged,
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged),
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-API-Version` set to plausible values.
4. `validateHmacFromRequestFactory` validates the HMAC successfully (it only checks `rawBody` against the shared `apiSecretKey`) as shown in `packages/apps/shopify-api/lib/utils/hmac-validator.ts:168-197`.
5. `checkWebhooksHeaders` extracts `domain = 'victim-shop.myshopify.com'` from the (forged, unauthenticated) header without any check against the signature, per `packages/apps/shopify-api/lib/webhooks/validate.ts:99-134`.
6. `authenticateWebhookFactory` calls `ensureValidOfflineSession(params, check.domain)` for `victim-shop.myshopify.com`, and if that shop's session exists in storage, the returned context includes a working `admin` client authenticated as the victim shop plus attacker-controlled `payload`/`topic`, as shown in `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts:35-102`.

I was not able to fully verify within the available tool budget whether any additional per-shop webhook subscription/ID validation exists elsewhere in the stack (e.g., in `shopify-app-session-storage` or app-level webhook registries) that might mitigate this at a higher layer; the core `shopify-api` webhook validation code itself performs no such binding.

export function validateFactory(config: ConfigInterface) {
  return async function validate({
    rawBody,
    ...adapterArgs
  }: WebhookValidateParams): Promise<WebhookValidation> {
    const request: NormalizedRequest =
      await abstractConvertRequest(adapterArgs);

    const webhookType = detectWebhookType(request.headers);

    const validHmacResult = await validateHmacFromRequestFactory(config)({
      type: HmacValidationType.Webhook,
      rawBody,
      webhookType,
      ...adapterArgs,
    });

    if (!validHmacResult.valid) {
      if (validHmacResult.reason === ValidationErrorReason.InvalidHmac) {
        const log = logger(config);

        );
      }
      return validHmacResult;
    }
