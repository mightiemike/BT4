### Title
Non-embedded OAuth session cookie shares a single identifier across shops by default, causing cross-tenant session collision - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
For non-embedded apps, the `SESSION_COOKIE_NAME` cookie set at OAuth callback is written with `path: config.cookiePath ?? '/'`, which defaults to the domain-wide root path. Because the cookie is keyed only by name/path and not by shop, when a user (e.g. an agency managing multiple merchant stores, or any user with two tabs) completes OAuth for shop B while a session cookie already exists for shop A in the same browser, shop B's session id silently overwrites shop A's cookie. This is the same bug class as the external report: one identifier (there, an `apmNamehash`; here, the session cookie) is reused across two logically distinct resources (two different shop sessions), so the runtime cannot tell which entity the identifier actually refers to, and code that trusts the identifier ends up operating on the wrong one.

### Finding Description
`begin()`/`callback()` in `packages/apps/shopify-api/lib/auth/oauth/oauth.ts` set the offline session id into a single cookie name (`SESSION_COOKIE_NAME`) with a shop-agnostic default path: [1](#0-0) 

The `cookiePath` config option (added specifically to address this) documents the exact collision and states the default remains insecure for multi-shop scenarios unless the developer opts in: [2](#0-1) 

Downstream, when a request carries no explicit `shop` query param (a normal document/browser request), the offline session id is derived purely from the cookie via `getCurrentId`, and the resolved session's `shop` field is then trusted to determine which shop the request belongs to: [3](#0-2) [4](#0-3) 

Because the cookie carries no shop-scoping by default, `getCurrentId` (`packages/apps/shopify-api/lib/session/session-utils.ts:28-83`) returns whatever session id was most recently written by any shop's OAuth callback: [5](#0-4) 

The changelog confirms the maintainers identified this exact collision and added `cookiePath` as an **opt-in** mitigation, leaving the default (`path: '/'`) unchanged for backward compatibility: [6](#0-5) 

### Impact Explanation
When two shops are authenticated against the same non-embedded app in the same browser (a common scenario for agencies/support staff managing multiple merchant stores, or simply two tabs open during onboarding), the second OAuth callback silently overwrites the first shop's session cookie. A subsequent same-browser request that relies on the cookie (no explicit `shop` param) will resolve to the wrong shop's offline session id, and code such as `ensureInstalledOnShop`/`getOfflineSession` will treat that browser context as belonging to the other shop's session — effectively a cross-tenant session mix-up analogous to the original report's "cannot tell which application is actually deployed" collision.

### Likelihood Explanation
This requires no attacker-controlled forgery — it triggers under normal, foreseeable usage (any user or shared browser handling OAuth for more than one shop) whenever `cookiePath` is left at its default. The maintainers' own changelog and inline documentation acknowledge this is a real, previously observed collision, and the fix is opt-in rather than the default, so all apps that have not explicitly set `cookiePath` remain exposed.

### Recommendation
Change the default `cookiePath` behavior to scope the cookie per shop automatically (e.g., derive a shop-specific path or embed the shop in the cookie name) rather than requiring library consumers to opt in, or emit a runtime warning when a non-embedded app has no `cookiePath` configured and multiple distinct shop sessions have been observed. At minimum, downstream consumers (`shopify-app-remix`, `shopify-app-react-router`, `shopify-app-express`) should validate that the cookie-derived session's `shop` matches any independently known shop context before trusting it, rather than assuming cookie-derived identity is authoritative.

### Proof of Concept
1. Deploy the app as non-embedded with default config (no `cookiePath` set).
2. In Browser Tab 1, complete OAuth install for `shop-a.myshopify.com`; the `shopify_app_session` cookie is set with `path=/` containing `offline_shop-a.myshopify.com`.
3. In Browser Tab 2 (same browser/profile), complete OAuth install for `shop-b.myshopify.com`; the callback in `oauth.ts` (`callback.setAndSign(SESSION_COOKIE_NAME, session.id, {path: '/'})`) overwrites the same cookie with `offline_shop-b.myshopify.com`.
4. Return to Tab 1 and make a request without a `shop` query parameter; `getOfflineSessionId`/`getCurrentId` reads the (now shop-b) cookie, loads shop B's offline session, and the app proceeds as if operating on shop B's tenant context inside what the user believes is shop A's tab.

   * By default the cookie is written with `path: '/'`, making it domain-wide.

export function getCurrentSessionId(config: ConfigInterface) {
  return async function getCurrentSessionId({
    isOnline,
    ...adapterArgs
  }: GetCurrentSessionIdParams): Promise<string | undefined> {
    const request = await abstractConvertRequest(adapterArgs);

    const log = logger(config);

    if (config.isEmbeddedApp) {
      log.debug('App is embedded, looking for session id in JWT payload', {
        isOnline,
      });

      const authHeader = request.headers.Authorization;
      if (authHeader) {
        const matches = (
          typeof authHeader === 'string' ? authHeader : authHeader[0]
        ).match(/^Bearer (.+)$/);
        if (!matches) {
          log.error('Missing Bearer token in authorization header', {isOnline});

          throw new ShopifyErrors.MissingJwtTokenError(
            'Missing Bearer token in authorization header',
          );
        }

        const jwtPayload = await decodeSessionToken(config)(matches[1]);
        const shop = jwtPayload.dest.replace(/^https:\/\//, '');

        log.debug('Found valid JWT payload', {shop, isOnline});

        if (isOnline) {
          return getJwtSessionId(config)(shop, jwtPayload.sub);
        } else {
          return getOfflineId(config)(shop);
        }
      } else {
        log.error(
          'Missing Authorization header review App Bridge configuration',
          {isOnline},
        );
      }
    } else {
      log.debug('App is not embedded, looking for session id in cookies', {
        isOnline,
      });

      const cookies = new Cookies(request, {} as NormalizedResponse, {
        keys: [config.apiSecretKey],
      });
      return cookies.getAndVerify(SESSION_COOKIE_NAME);
    }

- c439dab: Add `cookiePath` config option for multi-shop non-embedded apps

  Non-embedded apps that need to support multiple shops simultaneously in
  separate browser tabs were affected by a cookie collision: all shops shared
  a single `shopify_app_session` cookie at `path=/`, so authenticating a new
  shop would silently overwrite the previous shop's session.

  The new optional `cookiePath` config option lets you scope the session
  cookie to a shop-specific URL prefix, so each shop's cookie coexists
  independently in the browser.

  ```ts
  // Static path (default behaviour, unchanged)
  cookiePath: '/';

  // Factory function — recommended for multi-shop apps
  cookiePath: (session) => `/shops/${session.shop}/`;
  ```

  **Requirement:** the configured path must match your app's URL structure.
  Each shop must be served under a distinct URL prefix for the browser to
  deliver the correct cookie per request.
