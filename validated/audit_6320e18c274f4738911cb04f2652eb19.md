### Title
`ensure_match_transaction_info` skips authenticated checkpoint-hash validation, allowing committed state roots to diverge from re-executed VM output - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authenticated-response invariant that binds a freshly-computed VM output to a trusted, accumulator-proven `TransactionInfo` (e.g. during chunk-executor replay and `replay_on_archive` verification). It checks status, gas, write-set hash, and event-root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that bind a transaction to the committed state/hot-state/position Merkle roots.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates status, gas, and write-set hash against the trusted `TransactionInfo`, but the function's own comment documents that it deliberately ignores the checkpoint hashes: [2](#0-1) 

This matters because `state_checkpoint_hash` (and, under the newer trading-native feature, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) is the field that binds a `TransactionInfo` leaf — and therefore the whole transaction accumulator / ledger-info root — to the actual state Merkle root produced by execution. The write-set hash proves the *diff* was applied correctly, but it says nothing about whether the *resulting Merkle root* (state root, hot-state root, or position-state root) is correct. This function is the sole "does what I computed match what's committed" gate used by:
- `execution/executor/src/chunk_executor/mod.rs` (chunk replay during state sync / fast sync)
- `storage/db-tool/src/replay_on_archive.rs` (operator/auditor tool that replays archived history and is meant to catch divergence)
- `aptos-move/aptos-debugger/src/aptos_debugger.rs` and `aptos-move/cli/src/commands.rs`

Because the `compute_trading_native_state_roots` feature computes a `position_state_checkpoint_hash`/state root as a new, less-audited code path [3](#0-2) , any bug in that computation (or a corrupted/malicious upstream `TransactionInfo`) would not be caught by this match check.

### Impact Explanation
If the locally recomputed state/hot-state/position-state root diverges from what is embedded in the trusted `TransactionInfo` (obtained e.g. from an accumulator-proven chunk during fast sync, or from archived history being replayed for audit), `ensure_match_transaction_info` will still report a match. This means:
- During chunk-executor replay/fast-sync, a node can accept and commit a state tree that differs from the one implied by its own re-execution, without any error being raised at this authentication boundary.
- `replay_on_archive`, whose entire purpose is to detect exactly this class of divergence for audit/hard-fork-safety purposes, is blind to state/hot-state/position root mismatches — silently reporting successful replay even when the authenticated state root has diverged.

This falls squarely under the specified impact class: "Committed state that differs from the correct VM result or corrupts durable ledger data" and "Hard-fork-only divergence during commit, replay, restore, or proof verification."

### Likelihood Explanation
The gap is unconditional — it applies on every call to `ensure_match_transaction_info`, not just an edge case, and is explicitly flagged as a known, intentional omission in the code's own comment (the comment says it should be validated "before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"). Because `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is gated behind an on-chain feature flag [4](#0-3) , the concrete exploitability today depends on whether that flag is active. Regardless of the flag, the pre-existing `state_checkpoint_hash` field is also excluded from the check even without the new feature, so the audit/replay-verification gap for the base state root is live independent of any feature flag.

### Recommendation
Extend `ensure_match_transaction_info` to compare the locally computed `state_checkpoint_hash` (and, when applicable, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) against the corresponding fields on the trusted `TransactionInfo`, failing loudly on mismatch, exactly as is already done for `write_set_hash` and `event_root_hash`. This should be done before `compute_trading_native_state_roots`/hot-state checkpointing are relied upon in production, and ideally gated so that `replay_on_archive` cannot report success while silently skipping root-level verification.

### Proof of Concept
Not applicable/available from static review alone — reproducing requires driving a divergent state/hot-state/position-state root through chunk-executor replay or `replay_on_archive` (e.g., a build with a subtly incorrect state-checkpoint computation, or a crafted/corrupted upstream `TransactionInfo` supplied during fast sync) and observing that `ensure_match_transaction_info` still returns `Ok(())`. This was not executed; the finding is based on the function's logic and its own documenting comment at [2](#0-1) .

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
