## Analog Found

### Title
ETH-implicit account creation binds to the wallet global contract without verifying it exists, permanently freezing any deposited funds - (File: runtime/runtime/src/actions.rs)

### Summary
The Sherlock report flags `MeritDutchAuction.setNFT` for permanently wiring in an immutable dependency (`MeritNFT`) without first checking the precondition the code comments claim ("must have MINTER_ROLE") — if false, the contract is bricked and unrecoverable. The analogous nearcore pattern is `action_implicit_account_creation_transfer` for ETH-implicit accounts: it unconditionally sets the new account's contract to `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))` without checking that this global contract code actually exists in state on the receiving shard — unlike the sibling `use_global_contract` path, which explicitly performs that existence check before committing.

### Finding Description
When funds are transferred to an ETH-implicit address (`0x...`) for the first time, `action_implicit_account_creation_transfer` creates the account and, for the `EthImplicitAccount` branch, directly assigns: [1](#0-0) 
```
AccountType::EthImplicitAccount => {
    let chain_id = epoch_info_provider.chain_id();
    let global_contract_hash = eth_wallet_global_contract_hash(&chain_id);
    ...
    *account = Some(Account::new(
        deposit,
        Balance::ZERO,
        AccountContract::Global(global_contract_hash),
        storage_usage,
    ));
}
```
There is no `contains_key(TrieKey::GlobalContractCode{..})` check here. Compare this to `use_global_contract`, the function used when an *existing* account voluntarily opts into a global contract, which does perform this check and rejects the action with `GlobalContractDoesNotExist` if the code isn't present: [2](#0-1) 

This asymmetry means the invariant "the wallet global contract is already deployed on this shard" is *assumed*, not verified, on the implicit-account-creation path — exactly the same bug class as `MeritDutchAuction.setNFT` assuming (but not checking) that `MINTER_ROLE` was already granted.

Per the account-model documentation, once created this way an ETH-implicit account is permanently locked into using only the Wallet Contract: it cannot have a `DeployContract`, cannot `AddKey`, and cannot be deleted, because `check_actor_permissions` requires `actor_id == account_id` for all of these actions, and an ETH-implicit account has no access key of its own — the only way to act as itself is through a successful `FunctionCall` (e.g. `rlp_execute`) into its own wallet-contract code: [3](#0-2) 

If the referenced global contract hash was never actually deployed/distributed to the account's shard (global contracts propagate "shard by shard" and can take time, or may simply never have been deployed on a given chain/fork), any `FunctionCall` against this account resolves to `RuntimeContractIdentifier::Global` pointing at nonexistent code, and fails. With no code to execute and no access key to sign with directly, the account becomes permanently unusable — any balance sent to it (via the same `Transfer` that created it, or subsequent transfers) is frozen with no path to recovery, matching the "Auction contract rendered useless" impact of the original report, but here manifesting as **permanently frozen funds** rather than merely a redeployment inconvenience.

### Impact Explanation
Any unprivileged account can trigger this by simply sending a `Transfer` to an arbitrary ETH-implicit (`0x...`) address before the corresponding wallet global contract has been deployed/propagated on that shard/chain. The resulting account is created pointing at nonexistent global code, and by protocol design (no key, no `DeployContract`, no `AddKey`, no `DeleteAccount` permitted against it) there is no way to ever authorize any action from or on that account again. Funds sent to it — including the triggering transfer itself and any later deposits — are permanently frozen, satisfying the "permanently frozen funds" acceptance criterion.

### Likelihood Explanation
This is reachable by any single, ordinary `Transfer` transaction from any signer — no special privilege is required. The only precondition is that the wallet global contract has not yet been deployed/propagated to the target shard at the time of the transfer, which can occur during rollout of `EthImplicitGlobalContract`, on new/forked chains that have not performed the initial governance deploy, or transiently while global-contract distribution is still propagating shard-by-shard (the docs explicitly note this can "take a while to propagate to all shards"). The lack of an existence check on this specific path (vs. the checked `use_global_contract` path) means the runtime provides no defense-in-depth against this race/misconfiguration window.

### Recommendation
Before creating an ETH-implicit account bound to `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))`, verify the global contract code actually exists in trie state for the account's shard, mirroring the check already performed in `use_global_contract`/`action_use_global_contract` (`runtime/runtime/src/global_contracts.rs:84`). If absent, reject the implicit-account-creation transfer (refund the deposit) instead of silently committing an unusable account, or defer account materialization until the global contract is confirmed present.

### Proof of Concept
1. On a chain/shard where the ETH wallet global contract (identified by `eth_wallet_global_contract_hash(chain_id)`) has **not** yet been deployed via `DeployGlobalContract`/distributed to the target shard.
2. Any signer submits `SignedTransaction::send_money(..., eth_implicit_account_id, deposit, ...)` to a fresh `0x...` address.
3. `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:255-269`) creates the account with `AccountContract::Global(hash)` unconditionally — no existence check is performed, unlike `use_global_contract` (`runtime/runtime/src/global_contracts.rs:84`).
4. Any subsequent `FunctionCall` (e.g. `rlp_execute`) to this account fails because the referenced global code does not exist on this shard.
5. Because `check_actor_permissions` (`runtime/runtime/src/actions.rs:755-801`) requires `actor_id == account_id` for `DeployContract`/`AddKey`/`DeleteAccount`, and the account has no access key and no way to execute code as itself, no future transaction can ever change or recover the account.
6. The deposited balance, and any further transfers to this address, are permanently frozen.

```rust
pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) | Action::UniversalStateInit(_) => (),
    };
    Ok(())
}
```

```rust
pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
```
