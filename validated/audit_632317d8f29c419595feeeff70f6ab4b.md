### Title
Fork-dependent PoisonMicroblock report causes divergent `MinerReward` for the same `(parent_block_id, child_block_id)`, triggering a FATAL `assert_eq!` panic on reorg - ([File: stackslib/src/chainstate/stacks/db/accounts.rs])

### Summary
`inner_insert_matured_miner_reward` assumes that the `MinerReward` computed for a given `(parent_block_id, child_block_id)` pair is always identical, no matter which Stacks fork re-derives it, and therefore treats a second, differing computation as `FATAL` and panics. That assumption is false: `find_mature_miner_rewards` queries the *current fork's* Clarity/MARF state for a `PoisonMicroblock` report (`get_poison_microblock_report`) rather than data pinned to the matured block itself, so the same ancestor pair can legitimately compute a "punished" reward on one fork and an "unpunished" reward on a sibling fork. A single miner (attacker) can trigger this by equivocating their own microblock stream and having the resulting `PoisonMicroblock` report land in only one of two forks that later reconverge (reorg) on the same node.

### Finding Description
The broken equality the code assumes is:
`reward_computed_on_fork_A(parent_block_id, child_block_id) == reward_computed_on_fork_B(parent_block_id, child_block_id)`

`inner_insert_matured_miner_reward` enforces this with a hard panic: [1](#0-0) 

But the reward is not a pure function of the two block hashes. `find_mature_miner_rewards` looks up whether the block being rewarded was "punished" for a poison-microblock by querying `get_poison_microblock_report` against the *currently processing* `clarity_tx` (i.e., the current fork's tip state), not against state committed by the matured block itself: [2](#0-1) 

`get_poison_microblock_report` reads a Clarity DB key populated only when a `PoisonMicroblock` transaction has actually been mined somewhere in the calling fork's history: [3](#0-2) 

`calculate_miner_reward` then uses `poison_reporter_opt` to zero/reduce the child miner's `coinbase`, `tx_fees_anchored`, and `tx_fees_streamed_confirmed` when `punished == true`: [4](#0-3) 

Because `payments`/`matured_rewards` rows are stored keyed only by block-hash identifiers (not purged on reorg — this is explicitly acknowledged by the comment "the only time it's okay to re-insert the same reward is if there are two Stacks forks trying to store the same matured rewards for a common ancestor block"), a node that processes fork A to maturity (storing a punished reward for ancestor block `H`) and then reorgs to fork B (which shares block `H` as a common ancestor but has no poison report in its own history) will recompute an unpunished reward for the identical `(parent_block_id, child_block_id)` pair. `inner_get_matured_miner_payments` finds the previously-stored (punished) row, `assert_eq!` fails, and the process panics.

**Exploit flow (attacker input):** An attacker who is a single miner (or has a single miner slot) intentionally equivocates their own microblock stream (mines two conflicting microblocks at the same sequence signed with their own key — this requires no privilege). Anyone can then submit a valid `PoisonMicroblock` report transaction citing the equivocation. The attacker (or simply network/reorg timing) ensures that report transaction is confirmed in fork A but not in fork B, where both forks share the equivocating tenure/block as a common ancestor and both eventually mature that block's reward.

**Why existing guards don't help:** `check_tenure_tx`, `validate_vrf_seed`, `common_validate_against_burnchain`, and MARF hashing validate block/tenure structure and burnchain linkage, not the historical presence of a `PoisonMicroblock` report transaction in an *unrelated fork*. Nothing prevents the same `matured_rewards` key from being computed with different `poison_recipient_opt` values across forks, and the maturation window (`MINER_REWARD_MATURITY`) only delays when the divergence surfaces — it doesn't prevent it.

### Impact Explanation
When the assert fires, the affected node's chain-processing thread panics (Rust `panic!` via `assert_eq!`), which halts that node's ability to advance its Stacks tip on that fork (and, since the stored row is permanent DB state, re-processing the same reorg on restart reproduces the same panic — a persistent halt for that node). A second node that never observed both forks converging in the same order (e.g., it only ever followed fork B, or pruned/never received fork A before maturity) computes and stores the reward once and advances normally. This produces exactly the asymmetric outcome the question describes: node A halts, node B proceeds — a node-liveness divergence rooted in consensus-adjacent (poison-microblock/reward) logic, not privileged behavior. This falls in the "temporary tip disagreement" / node-halting category, with a credible path toward a broader liveness incident if the affected node is a widely-relied-upon miner or API node.

### Likelihood Explanation
Preconditions: the attacker needs to be a miner able to equivocate their own microblock stream (a routine, permissionless operation entirely within their own key), and needs a natural or attacker-timed reorg where the poison report lands in only one candidate fork before the `MINER_REWARD_MATURITY` window elapses for the common ancestor. This requires no majority stake, no signer collusion, and no other party's key — only a single miner slot and the ability to broadcast microblocks/transactions, matching the unprivileged-attacker model. It is repeatable each time the attacker equivocates and a reorg straddles the maturity boundary.

### Recommendation
Make the poison-microblock determination deterministic with respect to the matured block's own identity rather than the querying fork's tip state — e.g., store/attach the poison-report decision (reporter, sequence) as part of the matured block's own committed data at the time it was first processed, or key `get_microblock_poison_report` lookups off the ancestor block's own chain state at the moment of maturity rather than the current tip's accumulated Clarity DB. Alternatively, replace the `assert_eq!` FATAL panic with a resolution policy (e.g., only trust the first computed reward for a given `(parent_block_id, child_block_id)` and log a warning on subsequent divergent computations, or fall back to a fork-independent reward derivation) so a legitimate divergence cannot crash the node.

### Proof of Concept
Rust integration test plan (using `TestPeer` harness akin to existing tests in `stackslib/src/chainstate/stacks/tests/block_construction.rs` and `accounting.rs`):
1. Build a common tenure at height `H` where miner `M` produces a microblock stream containing an equivocation (two microblocks at the same sequence, signed by `M`), matching the pattern in `test_poison_microblock_same_block`/`test_poison_microblock_multiple_same_block` (`stackslib/src/chainstate/stacks/db/transactions.rs`).
2. From common ancestor at height `H+1`, build fork A: within `MINER_REWARD_MATURITY` blocks, include a `PoisonMicroblock` transaction reporting `M`'s equivocation, so `insert_microblock_poison` records it in fork A's Clarity DB.
3. From the same ancestor at height `H+1`, build fork B with the same block count but no `PoisonMicroblock` transaction anywhere in its history.
4. On "node A" (`peer.process_stacks_epoch_at_tip_checked`): process fork A through maturity; call `StacksChainState::get_matured_miner_payment(parent_block_id_H, child_block_id_H)` and assert it reflects a punished (reduced) `coinbase`/`tx_fees_anchored`/`tx_fees_streamed_confirmed`.
5. Still on node A, reorg to fork B (feed fork B's burn ops so it wins) and continue processing fork B past the same maturity height for block `H`. Assert that this call sequence panics with message containing `"FATAL: tried to insert multiple distinct matured parent block reward records"` (wrap in `std::panic::catch_unwind` to assert panic occurred).
6. On a fresh "node B" chainstate, process only fork B end-to-end (never fork A) through the same maturity height; assert `get_matured_miner_payment(parent_block_id_H, child_block_id_H)` returns the unpunished reward successfully and the node's tip advances with no panic — demonstrating `node_A.halted == true` while `node_B.halted == false` for the same underlying fork pair.

    /// Returns None if there are no forks.
    pub fn get_poison_microblock_report<T: ClarityConnection>(
        clarity_tx: &mut T,
        height: u64,
    ) -> Result<Option<(StacksAddress, u16)>, Error> {
        let principal_seq_opt = clarity_tx
            .with_clarity_db_readonly(|ref mut db| db.get_microblock_poison_report(height as u32))
            .map_err(|e| Error::ClarityError(e.into()))?;

        Ok(principal_seq_opt.map(|(principal, seq)| (principal.into(), seq)))
    }
