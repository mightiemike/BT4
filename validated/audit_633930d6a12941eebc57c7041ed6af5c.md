### Title
Poison-microblock reward can be stolen by submitting non-conflicting header pairs with a spoofed lower sequence number - (File: `stackslib/src/chainstate/stacks/db/transactions.rs`)

### Summary
`handle_poison_microblock` only checks that `mblock_header_1` and `mblock_header_2` were signed by the same microblock key (`check_microblock_header_signer`), and never verifies that the two headers actually collide (same `sequence`, same `prev_block`, different hash). A second reporter can therefore submit *any* two legitimately-published, non-forking microblock headers from the same stream, with `mblock_header_1.sequence` set arbitrarily low, and `insert_microblock_poison` will overwrite the correct first reporter's record, redirecting the commission to the colluding address.

### Finding Description
The claimed equality is: *exactly one valid report — from the FIRST genuine double-signature discovered — receives the commission, and no report may be overwritten unless it proves a strictly earlier real fork point.*

In `handle_poison_microblock` (stackslib/src/chainstate/stacks/db/transactions.rs:722-856), the only cross-validation performed is: [1](#0-0) 
which calls `check_microblock_header_signer`: [2](#0-1) 
That function *only* checks that both headers recover to the same public-key hash — it never checks `mblock_header_1.sequence == mblock_header_2.sequence`, nor `prev_block` equality, nor that the hashes differ. Those structural "do the headers actually conflict" checks exist only in the **mempool** admission path (`MemPoolRejection`), which is not consensus-enforced: [3](#0-2) 

Since every microblock in a stream is signed by the *same* miner key, ANY two legitimately-published, non-conflicting microblocks (e.g., seq=2 and seq=10, both part of the single canonical, non-forked stream) will pass `check_microblock_header_signer` trivially — they were signed by the same key by construction, with no fork involved at all.

The sequence-comparison branch then blindly trusts `mblock_header_1.sequence` as the "better" (earlier) fork point and overwrites the existing report: [4](#0-3) 

Exploit flow: Reporter A finds the real equivocation (two conflicting headers at sequence S) and submits a valid poison tx, recorded via `insert_microblock_poison(height, A, S)`. A colluding address B — who needs no privileged access, only the ability to observe two arbitrary already-published microblocks signed by the same miner key at any two positions in the (real, non-forked) stream, e.g., sequences 2 and 10 — crafts `TransactionPayload::PoisonMicroblock(header_at_seq_2, header_at_seq_10)` and includes it either via mempool bypass (attacker holds a miner slot per the threat model, so mempool `MemPoolRejection` checks are irrelevant to block-inclusion) or via a node that doesn't re-validate the payload semantics before consensus execution. Since `2 < S`, `handle_poison_microblock` accepts it as a "better" report and reassigns the commission to B, even though positions 2 and 10 do not represent any equivocation at all.

Existing guards fail because: `check_tenure_tx`, `verify_signer_signatures`, VRF/static validators, and MARF hashing operate on unrelated invariants; the only guard that could catch this (mempool's structural fork-equality check in blocks.rs) is not re-applied inside `handle_poison_microblock` at the consensus/Clarity execution layer, so a transaction admitted directly into a block (rather than via mempool broadcast) skips it entirely.

### Impact Explanation
This causes block-reward/commission re-assignment (theft) from the legitimate first reporter A to colluding party B — a reward mis-payment. Because the check that is bypassed is a mempool-only, non-consensus-enforced check, different nodes' local mempools may also reject/accept this tx inconsistently depending on their own submission path (RPC vs. direct block inclusion), which additionally risks state divergence on report bookkeeping between nodes that validated the tx via mempool rules vs. those that only ran block-level consensus validation. This matches "poison or reward mis-payment bounded to fees" (High) at minimum, with the fund-redirection component pushing toward Critical-adjacent impact since a real reporter's rightful commission is stolen.

### Likelihood Explanation
Preconditions: an existing valid report at (pubkh, height, seq=S) from a real equivocation, and an attacker holding or colluding with an account that can submit a subsequent `PoisonMicroblock` transaction and, per the threat model, can get transactions into blocks (a single miner slot suffices, since mempool-only checks can be bypassed via direct block construction). No majority stake, no signer key, no node compromise is required — the attacker only needs to observe two already-public, same-key-signed, non-conflicting microblock headers, which are trivially available from the same stream that produced the real fork. This is fully repeatable for every future poison-microblock incident.

### Recommendation
Move the structural equivocation checks currently only enforced in the mempool (`blocks.rs` ~6844-6861: `sequence` equality, `prev_block` equality, `version` equality, and header inequality/differing hash) into `check_microblock_header_signer` or directly into `handle_poison_microblock`, so that consensus-level processing rejects any `PoisonMicroblock` payload whose two headers do not actually represent a genuine equivocation (same sequence, same parent, differing block hash) regardless of how the transaction reached block inclusion.

### Proof of Concept
Rust integration test plan (in `stackslib/src/chainstate/stacks/db/transactions.rs` test module, alongside existing poison-microblock tests):
1. Set up chainstate, insert a microblock pubkey hash at height 1 (`insert_microblock_pubkey_hash`).
2. Construct a genuine equivocation: two microblocks with the SAME sequence S and SAME `prev_block` but different content/hash, signed by the miner key. Build and process `tx_poison_A` from reporter A referencing these headers.
3. Assert `get_poison_microblock_report(height) == (A_addr, S)`.
4. Construct two microblocks that are NOT forking (different, non-equal `prev_block`/sequence, e.g., legitimate sequential headers at sequence 2 and 10, both signed by the same miner key, no collision). Build `tx_poison_B` from colluding address B with `PoisonMicroblock(header_seq_2, header_seq_10)`.
5. Process `tx_poison_B` directly via `StacksChainState::process_transaction` (bypassing mempool `MemPoolRejection`, simulating direct block inclusion by a miner-slot attacker).
6. Assert the transaction is rejected OR, if it currently succeeds (demonstrating the bug), assert `get_poison_microblock_report(height)` still equals `(A_addr, S)` and NOT `(B_addr, 2)`. Currently, per the traced code, the second assertion will FAIL — `insert_microblock_poison` overwrites the record to `(B_addr, 2)`, proving the vulnerability.

        mblock_hdr_1: &StacksMicroblockHeader,
        mblock_hdr_2: &StacksMicroblockHeader,
    ) -> Result<Hash160, Error> {
        let pkh1 = mblock_hdr_1.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        let pkh2 = mblock_hdr_2.check_recover_pubkey().map_err(|e| {
            Error::InvalidStacksTransaction(
                format!("Failed to recover public key: {:?}", &e),
                false,
            )
        })?;

        if pkh1 != pkh2 {
            let msg = format!(
                "Invalid PoisonMicroblock transaction -- signature pubkey hash {} != {}",
                &pkh1, &pkh2
            );
            warn!("{}", &msg);
            return Err(Error::InvalidStacksTransaction(msg, false));
        }
        Ok(pkh1)
    }
