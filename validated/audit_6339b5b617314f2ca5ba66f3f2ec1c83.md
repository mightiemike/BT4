### Title
Session-token/shop binding is not enforced in `shopify.auth.tokenExchange()`, allowing a caller-supplied `shop` to be exchanged against a mismatched session token - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Summary
The `split()` bug's root cause is that a privileged operation (minting a new token worth most of the value) is driven by a caller-supplied identifier (`tokenId`) that is never checked for correspondence with the caller's actual ownership — only structural/format checks (`fraction` bounds, `frozen`) are performed. The closest unprivileged analog in this codebase is `tokenExchange()`: it accepts a caller-supplied `shop` string and a `sessionToken`, but only validates that the `sessionToken` is a validly-signed, non-expired JWT — it never checks that the token's own `dest`/`aud` claim actually corresponds to the `shop` argument being used to build the outbound request and to key the resulting session.

### Finding Description
`tokenExchange()` in [1](#0-0)  takes `shop` and `sessionToken` as independent parameters. It calls `decodeSessionToken(config)(sessionToken)` purely to validate the JWT signature/expiry, discards the returned payload, and then uses the caller-supplied `shop` (only lightly normalized via `sanitizeShop`) to construct the outbound request URL `https://${cleanShop}/admin/oauth/access_token` and to key the resulting `Session` object (`createSession({..., shop: cleanShop, ...})`, see [2](#0-1) ). Nowhere in this function is `payload.dest` (the shop the token was actually issued for) compared against the `shop` argument.

Most call sites are safe because they derive `shop` from the same trusted token they pass in — e.g. `performTokenExchange` in express derives `shop` from `payload.dest` after decoding the very token it forwards ( [3](#0-2) ), and the remix `getSessionTokenContext` also derives `shop` from `payload.dest` for embedded apps ( [4](#0-3) ).

However, the react-router package's `getSessionTokenContext` diverges: for apps configured with `AppDistribution.ShopifyAdmin`, it **skips** session-token validation/shop-derivation entirely and instead takes `shop` straight from the raw, unauthenticated URL query string: [5](#0-4) 
That untrusted `shop` value is then passed, together with the (separately-obtained, validly-signed) `sessionToken`, into `TokenExchangeStrategy.authenticate()` → `exchangeToken()` → `api.auth.tokenExchange({sessionToken, shop, ...})` ( [6](#0-5) ). Because `tokenExchange()` never cross-checks `shop` against the token's `dest` claim, the library will happily issue a POST request to `https://{attacker-influenced-shop}/admin/oauth/access_token` carrying a legitimately-signed but unrelated session token as the subject, and will store the resulting session keyed to the attacker-supplied `shop` if Shopify's OAuth server were to accept the mismatched pair.

This mirrors the `split()` flaw precisely: an identifier that determines who receives value/access (`tokenId` in the NFT case, `shop` here) is trusted from the caller instead of being derived from/verified against the authenticated principal (`msg.sender` in the NFT case, the JWT payload here).

### Impact Explanation
If exploitable, this could let an attacker who controls only the URL's `shop` query parameter (trivial to manipulate via a crafted link/iframe reload, since it is not part of the signed `host` param or the session token) redirect a victim's legitimate token-exchange flow toward a different shop domain, and/or cause the resulting offline/online session to be persisted under an attacker-chosen shop key in the app's session storage — a form of session-storage/cross-tenant confusion. Whether the exchange actually succeeds ultimately depends on Shopify's own OAuth token-exchange endpoint enforcing that `subject_token`'s destination matches the shop being called; the shopify-app-js library itself performs no such enforcement, so any assurance is entirely external to this code.

### Likelihood Explanation
Reachable by any single merchant/browser session without special privileges: `shop` is read unauthenticated from `request.url` for `AppDistribution.ShopifyAdmin` apps, and only this class of app skips the "derive shop from the validated JWT payload" logic that protects the other distribution types and the remix package. Exploitability is bounded by whether Shopify's backend independently validates token/shop correspondence, which could not be verified from this repository alone.

### Recommendation
In `tokenExchange()` (`packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts`), decode the session token and use/verify its `dest` claim as the source of truth for the shop used to build the outbound request and the resulting session — reject the call (or ignore the caller-supplied `shop`) if it does not match `payload.dest`. Additionally, align `getSessionTokenContext` in `shopify-app-react-router/src/server/authenticate/admin/authenticate.ts` with the remix package's behavior so that for embedded/token-exchange-capable configurations, `shop` is always derived from the validated session token rather than from the raw URL query string.

### Proof of Concept
Not independently reproducible from static analysis alone: constructing a working exploit requires confirming (1) that a victim's real App Bridge session token can be combined server-side with an attacker-chosen `shop` query parameter under `AppDistribution.ShopifyAdmin`, and (2) that Shopify's live `/admin/oauth/access_token` endpoint does not itself reject a `subject_token` whose `dest` differs from the requested shop domain. Point (2) cannot be verified from the repository and was not testable in this environment; the code-level PoC is the absence of any `payload.dest === shop` assertion in `tokenExchange()`, shown at [7](#0-6) , combined with the unauthenticated `shop` extraction at [8](#0-7) .
