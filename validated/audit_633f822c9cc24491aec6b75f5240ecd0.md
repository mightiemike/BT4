### Title
Unbounded-length borsh transaction decode on JSON-RPC ingest lacks the pre-decode size gate applied on the P2P path - ([File: chain/jsonrpc/src/api/transactions.rs])

### Summary
`libid3tag`'s CVE-2017-11551 is a classic "trust the length field before validating the data" bug: `id3_field_parse` reads an attacker-controlled length prefix and allocates/consumes memory for it before confirming the input actually contains that much data, letting a small crafted file trigger an out-of-memory condition. nearcore's own P2P ingestion path treats untrusted Borsh-encoded blobs (including `SignedTransaction`) with the identical threat model in mind and has added an explicit pre-decode size gate to defend against it, but the JSON-RPC transaction-submission endpoint, which is directly reachable by any unprivileged caller, decodes the same `SignedTransaction` type without that gate.

### Finding Description
On the network (peer) ingestion path, nearcore explicitly documents and guards against "maliciously inflated" Borsh payloads forcing large allocations at decode time: [1](#0-0) 

and enforces it via a pre-decode length check before any Borsh field (including nested `Vec<u8>`/`Vec<Action>` fields such as `DeployContractAction::code`, `FunctionCallAction::args`, or `DelegateAction`) is materialized: [2](#0-1) 

The peer-message tests explicitly state the intent: "an oversized body is rejected before it is Borsh-decoded, so the inflated nested-action `Vec` is never materialized at decode time." [3](#0-2) 

In contrast, the JSON-RPC entry point that decodes a caller-supplied, base64-encoded `SignedTransaction` for `broadcast_tx_async`/`broadcast_tx_commit`/`tx` calls `SignedTransaction::try_from_slice(&bytes)` directly, with **no size check on `bytes` before Borsh decoding**: [4](#0-3) 

`RpcSendTransactionRequest::parse` and `RpcTransactionStatusRequest::parse` both funnel into this same `decode_signed_transaction` helper: [5](#0-4) 

The only length check that exists on transactions (`max_transaction_size`) is performed by `ValidatedTransaction::check_valid_for_config`, which runs **after** the transaction has already been fully Borsh-decoded into memory: [6](#0-5) 

Because Borsh's `Vec<T>` deserialization reads a 4-byte little-endian length prefix and then allocates/reads that many elements before any application-level size check runs, a request whose JSON body need not itself be large can still declare an inflated length (e.g., a `Vec<u8>` field claiming close to `u32::MAX` elements) that the decoder attempts to materialize before the code ever reaches `check_valid_for_config`'s `max_transaction_size` gate — exactly the "read length, allocate/consume before validating actual data present" pattern behind CVE-2017-11551. This is the same class of bug the nearcore authors clearly recognized and patched specifically for the P2P transaction path (`MAX_TRANSACTION_SIZE_BYTES` gate in `peer_message.rs`), but the JSON-RPC path — which any unprivileged RPC caller can hit directly, with no peer-frame size cap in front of it — was left unguarded.

### Impact Explanation
A successful trigger causes large, attacker-controlled memory allocation(s) on the RPC node processing the request, which can exhaust process memory and crash or stall the node's JSON-RPC service (and potentially the whole validator/RPC process, depending on allocator/OOM-killer behavior). This is a transaction-triggered denial-of-service reachable from a single unauthenticated RPC call — no signature validity, balance, or nonce checks are required to reach the vulnerable decode path, since decoding happens strictly before any of that validation. Because RPC nodes are often collocated with or trusted by validators/chunk producers, this can degrade transaction ingestion availability for a shard.

### Likelihood Explanation
High likelihood of reachability: `send_tx`, `send_tx_async`, `broadcast_tx_commit`, and `tx`/`EXPERIMENTAL_tx_status` are all standard public JSON-RPC methods that accept a base64 `signed_tx_base64` string and immediately hit `decode_signed_transaction`. No special privileges, prior state, or account existence is needed — the caller doesn't even need to be a valid signer, since verification happens after decode. The main uncertainty is the magnitude of the practical impact, which depends on how the specific Borsh crate version used allocates for oversized `Vec` length prefixes (whether it pre-allocates full capacity vs. grows incrementally) — this could not be fully confirmed from the indexed sources, but the codebase's own defensive comments and tests on the P2P path treat this exact scenario as a real, worth-mitigating threat.

### Recommendation
Add the same pre-decode size gate used on the P2P path (`try_from_slice_with_limit`, or an equivalent length check against `max_transaction_size`/a small constant upper bound) to `decode_signed_transaction` in `chain/jsonrpc/src/api/transactions.rs`, rejecting any base64-decoded payload larger than the protocol's `max_transaction_size` (or a safety margin above it) before calling `SignedTransaction::try_from_slice`. Apply the same treatment to any other JSON-RPC/Rosetta-RPC entry points that Borsh-decode caller-supplied bytes directly (e.g., `chain/rosetta-rpc/src/utils.rs`'s `BorshInHexString::deserialize`), for consistency with the network layer's threat model.

### Proof of Concept
1. Submit a JSON-RPC `broadcast_tx_async` (or `send_tx`) request whose `signed_tx_base64` value decodes to a short, hand-crafted Borsh buffer that begins with a valid-looking `Transaction`/`TransactionV0` prefix (`signer_id`, `public_key`, `nonce`, `receiver_id`, `block_hash`) followed by an `actions: Vec<Action>` (or a `FunctionCallAction::args: Vec<u8>` / `DeployContractAction::code: Vec<u8>`) length prefix set to a large value (close to `u32::MAX`), with the actual trailing bytes truncated/omitted.
2. Send this to the target node's `send_tx`/`broadcast_tx_async` RPC endpoint.
3. `decode_signed_transaction` (`chain/jsonrpc/src/api/transactions.rs:71-76`) calls `SignedTransaction::try_from_slice` directly on the attacker-controlled bytes with no size gate, before `ValidatedTransaction::check_valid_for_config`'s `max_transaction_size` check (`core/primitives/src/transaction.rs:377-384`) ever runs.
4. Repeated/parallel requests of this shape can be used to force repeated large allocation attempts on the RPC node, exhausting memory before any single request is rejected for being malformed or oversized.

/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time. Use this for any peer-supplied borsh blob whose
/// decoded form can be much larger than its wire size; `limit` must sit above
/// the largest legitimate encoding of `T` and well below the peer-frame cap.
/// Returns `io::Error` so it composes with the borsh-based proto decode sites.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!("encoded size {} exceeds the limit of {limit} bytes", bytes.len()),
        ));
    }
    T::try_from_slice(bytes)
}

fn decode_signed_transaction(value: String) -> Result<SignedTransaction, RpcParseError> {
    let bytes = near_primitives::serialize::from_base64(&value)
        .map_err(|err| RpcParseError(format!("Failed to decode transaction: {}", err)))?;

        .map_err(|err| RpcParseError(format!("Failed to decode transaction: {}", err)))
}
