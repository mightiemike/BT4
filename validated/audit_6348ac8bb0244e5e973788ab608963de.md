## Title
Wallet Contract's `has_in_flight_tx` re-entrancy guard can become permanently stuck at `true`, permanently freezing the wallet — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract`'s `rlp_execute` entry point uses a boolean guard `has_in_flight_tx` to prevent more than one Ethereum-emulated transaction from being processed concurrently, analogous to a Solidity `nonReentrant` guard. This is directly analogous to the reported `Basket.sol#mint()` bug class: a re-entrancy-style guard whose state-management is flawed such that a legitimate call path can never reset the guard, permanently blocking every future call to the guarded function.

### Finding Description
`WalletContract` stores the guard flag and documents its intended invariant: [1](#0-0) 

`rlp_execute` checks the flag, and if free, sets it to `true` and returns a `Promise` — this state change (`self.has_in_flight_tx = true`) is committed as part of that function call's receipt, independent of whatever happens to the promise/callback chain afterward: [2](#0-1) 

The flag is only reset to `false` at the very start of each of the follow-up callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`): [3](#0-2) [4](#0-3) 

Because NEAR receipts each commit their own state transition independently, `has_in_flight_tx = true` is durably persisted the moment `rlp_execute` schedules its promise. If the corresponding callback receipt fails to execute successfully as a function call at all (e.g. it runs out of gas and traps, hitting `HostError::GasExceeded`/`GasLimitExceeded` as shown in the runtime's gas-accounting logic) rather than returning normally, none of its state mutations — including the `self.has_in_flight_tx = false` reset — are applied: [5](#0-4) 

The callback gas budgets in the wallet contract are hard-coded, small static constants (`RLP_EXECUTE_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, etc.) added on top of `action.gas()` taken from the user-supplied Ethereum transaction: [6](#0-5) [7](#0-6) 

If a submitted transaction's gas parameters/action complexity cause a downstream callback receipt to exceed its allotted gas (for example under network congestion causing gas price changes, or an attached-gas value that is inconsistent with the deeper multi-hop `storage_balance_of` → `storage_deposit` → `ft_transfer` → `rlp_execute_callback` chain for ERC-20 emulation), that callback receipt fails outright and the `has_in_flight_tx` reset never lands on chain. The contract's own test `test_simultaneous_transactions` confirms the guard's blocking behavior — a second `rlp_execute` call while the flag is `true` is unconditionally rejected with "transaction already in progress": [8](#0-7) 

There is no code path anywhere in `lib.rs` that force-resets `has_in_flight_tx` outside of the callback functions, so once stuck at `true`, every subsequent `rlp_execute` call — from any unprivileged caller/relayer — is rejected forever.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, the wallet contract instance can never process another Ethereum-emulated transaction. Since this contract is meant to give an Ethereum-style externally-owned account control over a NEAR account's funds and contract interactions, this is a transaction-triggered, permanent denial-of-service of that account's wallet functionality — effectively freezing all further fund movement and contract calls routed through the wallet contract, matching the "permanently frozen funds" / "protocol availability impacted" impact class from the referenced report.

### Likelihood Explanation
Any unprivileged caller who can submit a signed Ethereum-style transaction (or any relayer forwarding one) through `rlp_execute` can trigger a callback receipt whose gas need exceeds the hard-coded static gas budget, especially for the multi-hop ERC-20 emulation path (`nep_141_storage_balance_callback` → `storage_deposit` + `ft_transfer` → `rlp_execute_callback`). No validator, node operator, or privileged role is required — a normal user or relayer transaction is sufficient to reach this path.

### Recommendation
- Ensure `has_in_flight_tx` is reset even when a scheduled callback fails to execute, e.g. by not relying solely on the callback's own state mutation to clear the flag (for instance, clear the flag preemptively for external observers via a timeout, or use `#[private]` callback signatures guaranteed to be invoked with `PromiseResult` handling that cannot itself run out of gas before the reset statement executes).
- Audit and increase the static gas budgets (`RLP_EXECUTE_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`) to include sufficient safety margin so that legitimate callback executions cannot run out of gas.
- Add a recovery mechanism (e.g., an owner/self-callable method, or a time-based expiry) that allows `has_in_flight_tx` to be cleared if a promise chain never resolves.

### Proof of Concept
1. Deploy a `WalletContract` and sign an Ethereum ERC-20 `transfer` transaction (`EthEmulationKind::ERC20Transfer`) to an unregistered receiver, so `inner_rlp_execute` schedules `nep_141_storage_balance_callback` with `NEP_141_STORAGE_BALANCE_CALLBACK_GAS + action.gas()`.
2. Craft `action.gas()` and the deposit/gas parameters of the outer NEAR transaction such that the amount of gas actually forwarded to the multi-action `storage_deposit` + `ft_transfer` + `rlp_execute_callback` chain is insufficient (this is controllable by the caller's transaction `gas` field and by network gas price fluctuations affecting the effective budget at execution time).
3. Observe that `nep_141_storage_balance_callback` sets `self.has_in_flight_tx = true` and schedules further actions, but the final `rlp_execute_callback` receipt runs out of gas and fails without executing its body (per `runtime/near-vm-runner/src/logic/gas_counter.rs` `burn_gas`), so `has_in_flight_tx` is never reset to `false`.
4. Call `rlp_execute` again with any valid transaction — it is rejected with `"Error: transaction already in progress, please try again later."` as demonstrated by `test_simultaneous_transactions`, and this rejection persists indefinitely since there is no other code path resetting the flag.

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

/// Only one transaction can be in flight at a time.
#[tokio::test]
async fn test_simultaneous_transactions() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let receiver_account = worker.root_account().unwrap();

    let initial_receiver_balance = receiver_account.view_account().await.unwrap().balance;

    let receiver_id = receiver_account.id().as_str().into();
    let action = Action::Transfer { receiver_id, yocto_near: 1 };
    let signed_transaction =
        utils::create_signed_transaction(0, receiver_account.id(), Wei::zero(), action, &wallet_sk);
    let wallet_method_call_1 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));
    let wallet_method_call_2 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));

    let near_transaction = wallet_contract
        .inner
        .as_account()
        .batch(wallet_contract.inner.id())
        .call(wallet_method_call_1)
        .call(wallet_method_call_2)
        .transact()
        .await?;

    let result: ExecuteResponse = near_transaction.json()?;

    // The second transaction in the batch fails and this is returned as the
    // result of the Near transaction. But the first transaction in the batch
    // spawns promises that resolve, so the transfer was will successful.
    assert!(!result.success);
    assert!(result.error.unwrap().contains("transaction already in progress"));

    let final_receiver_balance = receiver_account.view_account().await.unwrap().balance;
    assert_eq!(final_receiver_balance.as_yoctonear() - initial_receiver_balance.as_yoctonear(), 1,);

    Ok(())
}
