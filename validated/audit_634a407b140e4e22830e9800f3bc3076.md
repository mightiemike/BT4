### Title
Receipt size limit is enforced before mutation, allowing creation of oversized receipts that bypass `max_receipt_size` and inflate `ChunkStateWitness` beyond its designed bound - (File: `runtime/runtime/src/verifier.rs`)

### Summary
The `WT_CLOSE_SESSION` advisory is a "size check happens too late / is missing" bug class: a field is buffered into memory before any bound is enforced. nearcore has a directly analogous, currently-acknowledged bug in receipt-size validation: `max_receipt_size` is checked, but the checked receipt can subsequently be mutated (by appending `output_data_receivers`, or by wrapping an oversized returned value into a `DataReceipt`) after the size check has already passed, producing receipts that exceed `max_receipt_size` without being rejected.

### Finding Description
`validate_receipt`/`validate_action_receipt` in `runtime/runtime/src/verifier.rs` enforces `limit_config.max_receipt_size` against the receipt as constructed at validation time [1](#0-0) . However, the runtime already documents a known bypass: an `ExistingReceipt` validation mode exists specifically because receipts above the size limit can be created and the runtime "has to handle them gracefully until the receipt size limit bug is fixed," referencing tracked issue near/nearcore#12606 [2](#0-1) .

The in-repo regression tests for this exact scenario confirm two concrete unpatched paths, both reachable from an ordinary contract call:
1. `test_max_receipt_size_promise_return` — a receipt is built at exactly `max_receipt_size`, passes validation, and then `output_data_receivers` is appended afterward, pushing the receipt above the limit without being rejected [3](#0-2) .
2. `test_max_receipt_size_value_return` — a contract returns a value as large as `max_receipt_size`; that value is wrapped into a `DataReceipt` after the size check, so the resulting `DataReceipt` exceeds `max_receipt_size` and is not rejected [4](#0-3) .

`validate_data_receipt` only checks `max_length_returned_data` on the raw returned value, not the size of the resulting serialized `DataReceipt`, so wrapping/framing overhead and any subsequent mutation are not accounted for [5](#0-4) . This is the same root cause class as the CVE: the size guard is evaluated against an intermediate/partial state of the object rather than the final buffered/stored form.

`max_receipt_size` exists specifically to bound the size of `ChunkStateWitness` — the design doc states the goal is to keep total witness size under ~21MiB, with `max_receipt_size` (4MiB) as one of the hard limits contributing to that budget [6](#0-5) .

### Impact Explanation
An unprivileged contract deployer/caller can, via a single transaction calling their own deployed contract (using `promise_return`/promise callback chaining, or by returning an oversized value from a function call), produce a receipt whose serialized size exceeds the protocol-mandated `max_receipt_size`. Because this receipt still gets included in `ChunkStateWitness`, it inflates the witness beyond the size budget the limits doc assumes, undermining the invariant that witnesses stay bounded (~21MiB) — the same "unbounded memory/size consumption due to missing enforcement" pattern as the CVE, but here affecting chunk producers/validators processing witnesses and node memory during distribution/validation, rather than remote peers. The runtime test suite explicitly asserts these oversized receipts occur (`assert_oversized_receipt_occurred`) and that the runtime must not die when processing them, which itself confirms the bypass is real and currently only mitigated by defensive handling, not prevented at admission [7](#0-6) .

### Likelihood Explanation
High reachability: any account that can deploy and call a contract can trigger either path with ordinary `FunctionCall` actions and promise chaining — no special privileges, validator role, or network position are required. The bug is already tracked and reproduced by first-party tests in this exact revision, confirming it is not merely theoretical.

### Recommendation
Re-validate the fully mutated receipt (after `output_data_receivers` are attached and after return-value wrapping into `DataReceipt`) against `max_receipt_size` before it is committed to the outgoing receipt set / included in the witness, rather than checking size only at an earlier, pre-mutation point. Alternatively, account for the maximum possible post-mutation overhead (e.g., `output_data_receivers` framing, `DataReceipt` framing) in the size check performed in `validate_action_receipt`/`validate_data_receipt` in `runtime/runtime/src/verifier.rs`, matching how `max_receipt_total_input_size` already reserves worst-case framing overhead.

### Proof of Concept
Already present in-repo as regression tests demonstrating the bypass: [8](#0-7) 
- `test_max_receipt_size_promise_return`: deploys a contract, calls a method that creates a promise DAG `A -> B`, where executing `A` issues `promise_return` to a promise `C` whose base receipt is sized to exactly `max_receipt_size`; attaching `output_data_receivers` afterward pushes `C`'s receipt above the limit, yet the test only asserts `assert_oversized_receipt_occurred` (not rejection).
- `test_max_receipt_size_value_return`: deploys a contract, calls `max_receipt_size_value_return_method` with `value_size = max_receipt_size`; the returned value is wrapped into a `DataReceipt` that ends up larger than `max_receipt_size`, again only asserted via `assert_oversized_receipt_occurred` rather than being rejected by `validate_data_receipt`.

/// Validates given data receipt. Checks validity of the length of the returned data.
fn validate_data_receipt(
    limit_config: &LimitConfig,
    receipt: &DataReceipt,
) -> Result<(), ReceiptValidationError> {
    let data_len = receipt.data.as_ref().map(|data| data.len()).unwrap_or(0);
    if data_len as u64 > limit_config.max_length_returned_data {
        return Err(ReceiptValidationError::ReturnedValueLengthExceeded {
            length: data_len as u64,
            limit: limit_config.max_length_returned_data,
        });
    }
    Ok(())
}

fn test_max_receipt_size() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);

        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // We can't test receipt limit by submitting large transactions because we hit the transaction size limit

        env.rpc_node().head().last_block_hash,

    assert_matches!(large_tx_exec_res, Err(InvalidTxError::TransactionSizeExceeded { .. }));

    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,

        env.rpc_node().head().last_block_hash,
    );

    // 3MB is still under the limit, so this should succeed.
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),

        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Generating a receipt that is 5 MB should fail, it's above the receipt size limit.
    let too_large_receipt_tx = SignedTransaction::call(
        103,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,

        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    let too_large_receipt_tx_exec_res =

    match too_large_receipt_tx_exec_res.status {
        FinalExecutionStatus::Failure(TxExecutionError::ActionError(action_error)) => {
            match action_error.kind {
                ActionErrorKind::NewReceiptValidationError(
                    ReceiptValidationError::ReceiptSizeExceeded { .. },
                ) => {
                    // Ok, got the expected error
                }
                _ => panic!("Expected ReceiptSizeExceeded error, got: {:?}", action_error),

        _ => panic!(

            too_large_receipt_tx_exec_res

    );
    let sum_4_res = env.rpc_runner().run_tx(sum_4_tx, Duration::seconds(5));
    assert_eq!(sum_4_res, 10u64.to_le_bytes().to_vec());

    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}

## State witness size limits

Some limits were introduced to keep the size of `ChunkStateWitness` reasonable.
`ChunkStateWitness` contains all the incoming transactions and receipts that will be processed during chunk application and in theory a single receipt could be tens of megabytes in size. Distributing a `ChunkStateWitness` this large would be troublesome, so we limit the size and number of transactions, receipts, etc. The limits aim to keep the total uncompressed size of `ChunkStateWitness` under 21MiB.

There are two types of size limits:

* Hard limit - the size must be below this limit, anything else is considered invalid
* Soft limit - things are added until the limit is exceeded, after that things stop being added. The last added thing is allowed to slightly exceed the limit.

The limits are:

* `max_transaction_size = 1.5 MiB`
  * All transactions must be below 1.5 MiB, otherwise they'll be considered invalid and rejected.
  * Previously was 4MiB, now reduced to 1.5MiB
* `max_receipt_size - 4 MiB`:
  * All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected.
  * Previously there was no limit on receipt size. Set to 4MiB, might be reduced to 1.5MiB in the future to match the transaction limit.
