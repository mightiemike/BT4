Based on my investigation, I found a self-documented integrity gap in the transaction-output/transaction-info comparator used by replay-verify and chunk-verification tooling.

### Title
`ensure_match_transaction_info` silently skips state/position checkpoint-hash verification, allowing authenticated ledger state to diverge undetected during replay-verify - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the comparator used to confirm that a locally re-executed transaction matches the `TransactionInfo` already committed to (and accumulator-proven against) the ledger. It checks status, gas used, write-set hash, and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` against the freshly computed values, as the code itself documents in a TODO.

### Finding Description [1](#0-0) 

The function verifies transaction status, gas, the write-set hash (`state_change_hash`) and the event root hash against `txn_info`, then returns `Ok(())` without ever comparing `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()`, or `position_state_checkpoint_hash()` to values computed from the actual re-executed ledger state. The code comment makes this explicit: [2](#0-1) 

This comparator is invoked by the chunk-executor's replay-verify path, `verify_execution`, which re-executes a chunk of transactions and checks the freshly produced `TransactionOutput`s against the `TransactionInfo`s taken from the chunk/backup being verified — without ever calling `DoStateCheckpoint` in this path, so no independent check of the state/hot-state/position-state roots happens at all in this flow: [3](#0-2) 

Compare this to the normal block-commit path (`DoStateCheckpoint`), where the analogous root hashes actually are checked against `known_state_checkpoints`: [4](#0-3) 

That check only runs during normal chunk commit (`update_ledger`), which does pass `known_position_state_checkpoints` derived from `txn_infos` — but it is gated by `compute_trading_native_state_roots`. In the dedicated `verify_execution`/replay-verify code path used by tools such as `db-tool replay_on_archive`, this state-checkpoint validation is skipped entirely and relies solely on `ensure_match_transaction_info`, which the TODO says intentionally ignores these checkpoint hashes.

### Impact Explanation
If the position-state or hot-state root computed during local re-execution diverges from what is embedded in the (accumulator-proven, validator-signed) `TransactionInfo` — due to a determinism bug, storage corruption, or an incorrect restore/replay of position-state data — `ensure_match_transaction_info` will still return `Ok(())`. Replay-verify tooling built on this comparator (explicitly called out for `db-tool`'s `replay_on_archive`) will report a successful, matching replay even though the authenticated state root bound to that ledger version has silently diverged from the correct VM result. This breaks the "authenticated API/state-view output must stay bound to the right version, object, and proof" invariant for any consumer relying on replay-verify to detect ledger corruption or non-determinism in these newer state trees.

### Likelihood Explanation
This is a self-admitted incompleteness in the verification path (not a subtle logic bug), gated behind the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature flag mentioned in the TODO. That means the checkpoint types affected (hot-state and position-state) are tied to functionality still being rolled out, which limits — but does not eliminate — current mainnet relevance: any code path that already sets `hot_state_root_in_txn_info` or `compute_trading_native_state_roots` true and relies on `verify_execution`/replay-verify for integrity assurance would silently accept divergent state today.

### Recommendation
Extend `ensure_match_transaction_info` to accept and check the computed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when applicable) against `txn_info`'s corresponding fields, or ensure the `verify_execution` replay path always runs `DoStateCheckpoint` and validates its output against `txn_infos` before considering a chunk successfully replayed.

### Proof of Concept
Not independently exploitable without also corrupting the underlying position/hot-state computation; the finding is the code-documented absence of a checkpoint-hash comparison in `ensure_match_transaction_info` (lines 2139–2204) combined with `verify_execution` (lines 648–707 in `chunk_executor/mod.rs`) never invoking `DoStateCheckpoint`, which is the only place in the codebase that performs this comparison.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
