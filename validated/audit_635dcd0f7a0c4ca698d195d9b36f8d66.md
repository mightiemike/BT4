Based on my investigation, I found a concrete analog of this bug class in java-tron's `ExchangeTransactionActuator`.

### Title
`ExchangeTransactionActuator` validates the exchange balance-limit cap using the *sell-side* requested quantity while the actual balance mutation occurs on the *buy-side* computed amount, allowing the enforced `exchangeBalanceLimit` cap to be silently exceeded - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
Similar to the Sherlock finding where `currentStakeLimit` is decremented using the requested `stakeAmount` instead of the actual amount later returned by `_stake()`, `ExchangeTransactionActuator.doValidate()` enforces the `ExchangeBalanceLimit` guard against the token being sold (using the caller-supplied `tokenQuant`), but the actual pool-state mutation that happens in `execute()` applies to *both* tokens in the pair, via the bancor-formula-computed `anotherTokenQuant`, which is never checked against the limit.

### Finding Description
In `doValidate()`, the balance-limit check only validates the side of the pair matching the input `tokenID`: [1](#0-0) 

The check computes `tokenBalance = tokenBalance + tokenQuant` and compares it to `balanceLimit`, but it never computes or validates the resulting balance on the *other* side of the pair after the trade. The actual "other" token quantity, `anotherTokenQuant`, is only computed afterward via the bancor-relay formula in `exchangeCapsule.transaction()`, and it is used solely to check the `tokenExpected` slippage bound: [2](#0-1) 

In `execute()`, the actual pool balances are mutated using this same `anotherTokenQuant`, exactly mirroring the update in `ExchangeCapsule.transaction()`: [3](#0-2) 

Because the growth of the "sell" side (via `tokenQuant`) is what's capped, and not the shrink/growth of the "buy" side (`anotherTokenQuant`), a resulting `secondTokenBalance` (or `firstTokenBalance`) can end up smaller than intended, or - in `ExchangeInjectActuator`'s analogous flow - can grow past `getExchangeBalanceLimit()` on the un-validated side, since `ExchangeInjectActuator` never checks `newAnotherTokenBalance` against `balanceLimit` at all (only `ExchangeTransactionActuator` even attempts a check, and only for one side): [4](#0-3) 

This is the same root-cause pattern as the Sherlock report: a protective accounting/limit check is performed using the caller-supplied "requested" amount, while the actual state mutation is driven by a derived/computed amount that can diverge from the value that was checked, letting the derived amount escape the intended cap.

### Impact Explanation
An unprivileged user can call `ExchangeTransactionContract` (or `ExchangeInjectContract`) with an input `tokenQuant` chosen so that the sell-side check passes (`tokenBalance <= balanceLimit`), while the actual buy-side change (`anotherTokenQuant`), computed by the bancor-relay curve, pushes the un-checked side of the AMM pool's balance beyond the protocol's intended `ExchangeBalanceLimit` invariant. This is an invalid-state/accounting-divergence issue: the on-chain `ExchangeCapsule` balances can diverge from the safety bound the validator is meant to enforce, undermining the purpose of `getExchangeBalanceLimit()` as an overflow/manipulation safeguard for the TRX/TRC10 bancor exchange pools.

### Likelihood Explanation
This is reachable by any unprivileged account holding TRX or the relevant TRC10 asset issuing a standard `ExchangeTransactionContract`/`ExchangeInjectContract` transaction - no special privilege is required, and the condition (checking only one side of the pair) is a straightforward, deterministic flaw in the validator logic rather than a probabilistic race.

### Recommendation
After computing `anotherTokenQuant` (in `ExchangeTransactionActuator.doValidate()`) and `newAnotherTokenBalance` (already computed in `ExchangeInjectActuator.doValidate()`), validate the resulting balance on the "other" token side against `balanceLimit` as well, mirroring the check already applied to the input `tokenQuant` side, so that both sides of the pair are bounded consistently by `getExchangeBalanceLimit()`.

### Proof of Concept
1. Create/observe an exchange pair near `ExchangeBalanceLimit` on one side (e.g., `secondTokenBalance` close to the limit).
2. An attacker submits `ExchangeTransactionContract` selling `firstTokenID` with a `tokenQuant` small enough that `firstTokenBalance + tokenQuant <= balanceLimit` (passes the check in [1](#0-0) ).
3. Due to the bancor-relay math in `exchangeCapsule.transaction()` [3](#0-2) , the resulting `anotherTokenQuant` decrement (or, on the inject side, increment) pushes `secondTokenBalance` outside the intended safety bound, since that side is never checked against `balanceLimit`.
4. The transaction succeeds and commits the out-of-bound exchange state via `Commons.putExchangeCapsule`, permanently diverging pool balances from the protocol's configured `ExchangeBalanceLimit` invariant.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
