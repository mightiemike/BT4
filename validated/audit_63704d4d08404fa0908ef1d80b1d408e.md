### Title
Unbounded `condvar.wait` in `ReceiptPreparationPipeline::get_contract` Allows Indefinite Main-Thread Block if Background Compilation Hangs or Panics — (`runtime/runtime/src/pipelining.rs`)

### Summary

`ReceiptPreparationPipeline::get_contract` calls `task.condvar.wait(&mut status_guard)` with **no timeout** when the background compilation thread holds `PrepareTaskStatus::Working`. If the background thread never calls `notify_all()` — because compilation hangs, panics (e.g., OOM), or otherwise fails to complete — the main chunk-application thread blocks indefinitely, stalling block processing.

### Finding Description

When a `FunctionCall` receipt is submitted to the pipeline, a background task is spawned on `contract_compilation_pool()`. The closure atomically sets the task status to `Working` before calling `prepare_function_call`: [1](#0-0) 

`notify_all()` is only called **after** `prepare_function_call` returns successfully. There is no panic handler or deferred `notify_all()` in the closure.

When `get_contract` is called on the main thread and finds `PrepareTaskStatus::Working`, it enters an unbounded wait: [2](#0-1) 

`parking_lot::Condvar::wait` blocks without any timeout. If the background thread:
- panics (e.g., due to OOM during Wasmtime/Winch compilation), or
- hangs indefinitely on a pathological WASM input,

then `notify_all()` is never called, the status remains `Working`, and the main thread waits forever. There is no timeout, no fallback, and no panic-recovery path in the background closure.

The thread pool's `run_worker` does not catch panics from `job()`: [3](#0-2) 

A panicking job simply terminates the worker thread. The `PrepareTask` condvar is never signaled.

The Wasmtime engine is configured with Winch (single-pass) on x86_64 and Cranelift with `OptLevel::None` + `SinglePass` regalloc elsewhere: [4](#0-3) 

These settings reduce but do not eliminate the risk of superlinear compilation time or OOM on adversarially crafted WASM. No compilation timeout is configured in the Wasmtime engine, and no `wait_timeout` is used in the pipelining condvar.

### Impact Explanation

If triggered, the main chunk-application thread blocks indefinitely inside `get_contract`. No further receipts in the chunk are processed, no new chunks are produced, and the node stops finalizing blocks. This is a non-network-level DoS: it affects the node's liveness without requiring network-level access, and it is fixable without a hardfork (by adding a `wait_timeout` and a fallback compilation path).

### Likelihood Explanation

An unprivileged attacker can deploy a WASM contract and submit a `FunctionCall` receipt targeting it — both are standard protocol operations. The practical difficulty lies in crafting WASM that causes the Winch/Cranelift compiler to hang or OOM after passing NEAR's preparation limits (function count, local count, function body size). Winch's single-pass design makes hangs unlikely on x86_64 production, but OOM during compilation remains plausible for large, limit-saturating WASM. The structural bug (unbounded wait, no panic recovery) is unconditional.

### Recommendation

1. Replace `task.condvar.wait(&mut status_guard)` with `task.condvar.wait_for(&mut status_guard, COMPILATION_TIMEOUT)` and handle the timeout case by falling back to main-thread compilation (discarding the background result).
2. Wrap the background closure body in `std::panic::catch_unwind` and call `task.condvar.notify_all()` in the panic handler after setting the status to a terminal error state.
3. Consider adding a Wasmtime compilation timeout via a dedicated thread with a kill signal, or by using Wasmtime's `Engine::increment_epoch` / epoch-based interruption.
