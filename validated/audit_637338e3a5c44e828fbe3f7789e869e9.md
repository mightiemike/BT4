### Title
Missing AccountId validation for `output_data_receivers` / `signer_id` in `validate_action_receipt` — ([File: runtime/runtime/src/verifier.rs])

### Summary
`validate_receipt`/`validate_action_receipt` in `runtime/runtime/src/verifier.rs` strictly re-validates `receipt.predecessor_id()` and `receipt.receiver_id()` with `AccountId::validate`, explicitly because the VM host function `read_and_parse_account_id` (in `near-vm-runner/src/wasmtime_runner/logic.rs`) performs only a lenient parse when a contract supplies an account id via `promise_batch_create`/`promise_batch_then`. However, the same strict `AccountId::validate` check is never applied to the `receiver_id` field of each `DataReceiver` inside `output_data_receivers`, nor to `signer_id` of the `ActionReceipt`, even though dedicated error variants `ReceiptValidationError::InvalidDataReceiverId` and `InvalidSignerId` exist in `core/primitives/src/errors.rs` for exactly this purpose and are otherwise unused.

### Finding Description
`validate_action_receipt` at [1](#0-0)  only checks:
- `input_data_ids().len()` against a limit,
- `refund_to()` via `AccountId::validate`,
- recurses into `validate_actions_with_mode` for the action list.

It does **not** call `AccountId::validate` on `output_data_receivers()[i].receiver_id` or on `signer_id()`. Compare this to `validate_receipt` itself at [2](#0-1)  which explicitly re-validates `predecessor_id` and `receiver_id` with a comment stating this is needed "to maintain backwards compatibility with AccountId validation since we illegally parse an AccountId in near-vm-runner/src/wasmtime_runner/logic.rs#fn(read_and_parse_account_id)".

The `DataReceiver.receiver_id` value in `output_data_receivers` is populated directly from a contract-supplied account-id string parsed the same lenient way, e.g. in `ReceiptManager::create_action_receipt` at [3](#0-2)  and from `promise_batch_create`'s `read_and_parse_account_id` call at [4](#0-3) . The two error kinds `InvalidDataReceiverId` and `InvalidSignerId` are declared in `ReceiptValidationError` at [5](#0-4)  but no call site in the codebase that I could find actually constructs `InvalidDataReceiverId` or `InvalidSignerId` — they appear to be dead validation paths, mirroring the `_hooks`-vs-`_interactions` pattern in the report: one parallel input path (`predecessor_id`/`receiver_id`) is validated while a structurally identical path (`output_data_receivers` receiver ids, `signer_id`) that originates from the same untrusted, leniently-parsed source is skipped.

### Impact Explanation
A malformed `AccountId` string surviving into `output_data_receivers[i].receiver_id` of a persisted `ActionReceipt`/`ActionReceiptV2` would later be used to route the resulting `DataReceipt` to a destination account/shard. Because shard assignment and trie-key derivation for accounts depend on well-formed `AccountId`s, an invalid id reaching this stage could cause divergent behavior between nodes if any downstream logic assumes validity (e.g., shard routing, account lookups, or receipt matching), or could be rejected inconsistently depending on where the second-line-of-defense checks are ultimately located — since here that second line of defense (`validate_action_receipt`) does not perform the check at all for this field. This falls under state-root divergence / invalid state transition risk, which is why the report's underlying bug class (asymmetric validation between "twin" fields) is a valid, medium-severity analog rather than a purely cosmetic gap.

### Likelihood Explanation
Reachable directly by any contract call using `promise_batch_then`/`promise_batch_create` plus attaching output data receivers — no privileged access needed, just a `FunctionCall` action from an ordinary transaction signer. Whether this is currently exploitable end-to-end depends on how strict `read_and_parse_account_id` actually is and whether any other layer (e.g., shard/tries code) independently validates the id before it can cause divergence; I was not able to fully trace every downstream consumer of `output_data_receivers[i].receiver_id` in the time available, so the ultimate blast radius (crash vs. silent inconsistency vs. no effect) is not fully confirmed and should be verified with a targeted PoC.

### Recommendation
Add `AccountId::validate` checks for every `DataReceiver.receiver_id` in `output_data_receivers()` and for `signer_id()` inside `validate_action_receipt` (returning `ReceiptValidationError::InvalidDataReceiverId` / `InvalidSignerId` respectively), matching the strictness already applied to `predecessor_id`/`receiver_id`/`refund_to` in the same function, for both `ValidateReceiptMode::NewReceipt` and, at minimum, tolerant handling for `ExistingReceipt` consistent with existing backward-compatibility patterns in that file.

### Proof of Concept
Not independently reproduced against a running node in this session (index-only investigation); the concrete PoC would be: from an ordinary account, submit a `FunctionCall` action to a contract that calls `promise_batch_create` targeting a nearly-valid account id string accepted by the lenient `read_and_parse_account_id` parser, then `promise_batch_then`/attach an output data receiver pointing at that id, and observe that the resulting `ActionReceipt`'s `output_data_receivers` entry passes `validate_action_receipt` unchecked while an equivalently malformed `receiver_id`/`predecessor_id` on the receipt itself would be rejected by `validate_receipt`. This last step (confirming the lenient parser actually lets an invalid id through, and tracing what breaks downstream) needs to be executed in a live Devin session with full repo/test access to confirm exploitability.

/// Validates a given receipt. Checks validity of the Action or Data receipt.
pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }
    }

    // We retain these checks here as to maintain backwards compatibility
    // with AccountId validation since we illegally parse an AccountId
    // in near-vm-runner/src/wasmtime_runner/logic.rs#fn(read_and_parse_account_id)
    AccountId::validate(receipt.predecessor_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidPredecessorId {
            account_id: receipt.predecessor_id().to_string(),
        }
    })?;
    AccountId::validate(receipt.receiver_id().as_ref()).map_err(|_| {
        ReceiptValidationError::InvalidReceiverId { account_id: receipt.receiver_id().to_string() }
    })?;

fn validate_action_receipt(
    limit_config: &LimitConfig,
    receipt: VersionedActionReceipt,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if receipt.input_data_ids().len() as u64 > limit_config.max_number_input_data_dependencies {
        return Err(ReceiptValidationError::NumberInputDataDependenciesExceeded {
            number_of_input_data_dependencies: receipt.input_data_ids().len() as u64,
            limit: limit_config.max_number_input_data_dependencies,
        });
    }

    if let Some(account_id) = receipt.refund_to() {
        AccountId::validate(account_id.as_ref()).map_err(|_| {
            ReceiptValidationError::InvalidRefundTo { account_id: account_id.to_string() }
        })?;
    }

    validate_actions_with_mode(
        limit_config,
        receipt.actions(),
        receiver,
        current_protocol_version,
        mode,
    )
    .map_err(ReceiptValidationError::ActionsValidation)
}

    /// The `receiver_id` of a Receipt is not valid.
    InvalidReceiverId { account_id: String } = 1,
