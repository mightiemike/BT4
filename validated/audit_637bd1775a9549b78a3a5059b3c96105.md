### Title
Unchecked `long` accumulation of global resource weights (`TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight`) causes silent overflow corruption of network-wide resource pricing - ([File: chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java])

### Summary
`DynamicPropertiesStore.addTotalEnergyWeight`/`addTotalTronPowerWeight` (and the analogous `addTotalNetWeight`) accumulate every account's freeze/unfreeze/delegate operations into a single global `long` counter using plain `+=` with no overflow check, exactly analogous to the Nibbl `_updateTwav()` bug where `cumulativeValuation` is a monotonically-updated accumulator that can overflow. Instead of reverting (as in Solidity ≥0.8), Java `long` overflow silently wraps to a negative/garbage value, permanently corrupting the network-wide global resource limit calculation used by every account's `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`.

### Finding Description
`DynamicPropertiesStore.addTotalEnergyWeight` and `addTotalTronPowerWeight` read the current cumulative weight, add the caller-supplied delta, and persist it with no bounds/overflow checking: [1](#0-0) 

These are called on every `FreezeBalanceActuator`/`FreezeBalanceV2Actuator`/`UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`/`DelegateResourceActuator`/`UnDelegateResourceActuator`/`CancelAllUnfreezeV2Actuator` execution, driven directly by anonymous broadcast transactions: [2](#0-1) [3](#0-2) 

This global counter is subsequently used, unguarded against overflow/negative values, as the divisor in the network-wide resource-limit formula that every account's bandwidth/energy allowance derives from: [4](#0-3) [5](#0-4) 

This mirrors the report's root cause precisely: a value that's expected to be a "monotonic/interesting-delta" accumulator (`cumulativeValuation` in Twav vs. `TotalEnergyWeight`/`TotalNetWeight`/`TotalTronPowerWeight` in java-tron) is updated with checked/unchecked arithmetic inconsistently across the codebase. Notably, java-tron *does* have a hardened, overflow-checked code path (`RepositoryImpl.calculateGlobalEnergyLimit` using `BigInteger`/`StrictMathWrapper`, gated by `allowHardenResourceCalculation`/`allowHardenExchangeCalculation`), proving the team is aware that these long-lived accumulators can overflow — but the *write* path (`addTotalEnergyWeight`/`addTotalTronPowerWeight`/`addTotalNetWeight`) that produces the stored total was never hardened with the same `addExact`/`BigInteger` treatment applied elsewhere (e.g. `ExchangeInjectActuator`, `AssetIssueActuator`'s FrozenSupply-expire-time check).

### Impact Explanation
If `TotalEnergyWeight`/`TotalNetWeight`/`TotalTronPowerWeight` overflows `Long.MAX_VALUE` (or is driven negative through the `newWeight - oldWeight` delta patterns used throughout freeze/unfreeze/delegate actuators), it silently wraps rather than reverting. Because this is a single global, persisted `DynamicPropertiesStore` value shared by the whole network:
- Every account's `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` (division by this corrupted value) is permanently broken chain-wide, not just for one user — this is a stronger, network-wide DoS/asset-accounting corruption compared to the original single-pool Nibbl bug.
- A negative or garbage divisor can produce negative/nonsensical bandwidth and energy limits for all accounts, effectively freezing or unfairly restricting/inflating everyone's free resource allotment (consensus-relevant state corruption, since this value is part of `DynamicPropertiesStore` and flows into transaction processing determinism across all full nodes).
- Because the corruption is silent (no exception, no revert), unlike the original Solidity report, it is strictly worse: it doesn't just "stop working," it computes incorrect values that could be exploited for free/near-free resource usage or wrongful resource exhaustion of legitimate accounts.

### Likelihood Explanation
Reaching `Long.MAX_VALUE` in `TotalEnergyWeight`/`TotalNetWeight` via legitimate freeze operations at TRX-precision-scaled weight units requires an enormous, unrealistic amount of frozen TRX/resource delegation across the whole network (similar caveat as the original report, where the judge downgraded severity because there's no concrete PoC of reaching the overflow threshold in practice). It is unclear from static analysis alone whether any single-account or coordinated multi-account attack path (e.g., repeated delegate/undelegate leaving stale deltas, or exploiting `oldWeight - newWeight` sign errors in delegation/undelegation flows) could drive the counter toward overflow faster than proportional to total frozen TRX supply. This would require dynamic testing/fuzzing of the freeze/unfreeze/delegate delta arithmetic to confirm feasibility, which is beyond what the indexed code excerpts can prove.

### Recommendation
Apply the same hardening already used elsewhere in the codebase (`StrictMathWrapper.addExact`/`BigInteger`, as seen in `AbstractExchangeActuator`, `AssetIssueActuator`'s expire-time check, and the harden variants of `RepositoryImpl`/`EnergyProcessor`/`BandwidthProcessor`) to the *write* paths that mutate `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight`:
- Use `Math.addExact`/`StrictMathWrapper.addExact` in `DynamicPropertiesStore.addTotalEnergyWeight`/`addTotalTronPowerWeight`/`addTotalNetWeight` and their `RepositoryImpl` counterparts, throwing/rejecting the triggering transaction via `ContractValidateException`/`ContractExeException` instead of allowing silent wraparound.
- Add sanity bounds checks (e.g., reject deltas that would push the total below 0 or above a sane chain-parameter ceiling) consistent with the already-present `max(0, totalEnergyWeight, ...)` clamping for the new-reward-algorithm path.

### Proof of Concept
Static PoC (cannot be dynamically executed here, but demonstrable via unit test pattern already present in the repo's own `CalculateGlobalLimitHardenTest`):
1. Set `dynamicPropertiesStore.saveTotalEnergyWeight(Long.MAX_VALUE - 1)` directly (or via a sequence of `FreezeBalanceV2Contract` transactions that increment `oldEnergyWeight`→`newEnergyWeight` deltas summing close to `Long.MAX_VALUE`).
2. Submit one more `FreezeBalanceV2Contract` transaction that calls `FreezeBalanceV2Actuator.execute` → `dynamicStore.addTotalEnergyWeight(newEnergyWeight - oldEnergyWeight)` with a positive delta, causing the internal `totalEnergyWeight += amount` in `DynamicPropertiesStore.addTotalEnergyWeight` (lines 2282–2293) to wrap to a negative value.
3. Observe that `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` (lines 145–179) now divides by a negative/corrupted `totalEnergyWeight`, producing incorrect (potentially negative or grossly wrong) `energyLimit` for every account network-wide, with no exception thrown (in the non-hardened default path) — unlike the hardened path which the repo's own tests (`testGlobalEnergyLimitOverflowDetectedWithHardening`) show throws `ArithmeticException` only when `allowHardenResourceCalculation` is enabled.

  private void addTotalWeight(ResourceCode resourceCode, DynamicPropertiesStore dynamicStore,
                              long frozenBalance, long increment) {
    long weight = dynamicStore.allowNewReward() ? increment : frozenBalance / TRX_PRECISION;
    switch (resourceCode) {
      case BANDWIDTH:
        dynamicStore.addTotalNetWeight(weight);
        break;
      case ENERGY:
        dynamicStore.addTotalEnergyWeight(weight);
        break;
      case TRON_POWER:
        dynamicStore.addTotalTronPowerWeight(weight);
        break;
      default:
        logger.debug("Resource Code Error.");
    }
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
