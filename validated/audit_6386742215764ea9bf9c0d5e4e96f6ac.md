## Analysis

The reported bug class — a `payable`/deposit‑accepting entry point that fails to return the attached value on error paths, causing funds to become permanently stuck — has a direct analog in the NEAR Wallet Contract's `rlp_execute` method.

### Title
`WalletContract::rlp_execute` retains the caller's attached NEAR deposit on synchronous error paths, permanently freezing external‑caller funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`rlp_execute` is a `#[payable]` entry point that an external caller can invoke with an attached NEAR deposit intended to cover gas/fees for the emulated Ethereum transaction it executes on behalf of an eth-implicit account. That deposit is only refunded to the caller in one specific place — inside the async callback `rlp_execute_callback`, and only when the underlying cross-contract promise later fails. Every synchronous error path inside `rlp_execute`/`inner_rlp_execute` returns a normal `PromiseOrValue::Value(...)` (not a panic), so the runtime treats the receipt as a successful execution and never issues an automatic deposit refund. The attached deposit therefore remains stuck in the `WalletContract` account balance.

### Finding Description
`rlp_execute` is marked `#[payable]` and forwards to `inner_rlp_execute`, which builds an `ExecutionContext` from `env::attached_deposit()` and derives `CallerDeposit` only for external (non-self) callers: [1](#0-0) [2](#0-1) 

The only refund of `caller_deposit` happens deep inside the async chain, in `rlp_execute_callback`, and only on `PromiseResult::Failed`: [3](#0-2) 

However several code paths return an `ExecuteResponse` with `success: false` synchronously (i.e. as a normal WASM return value, not a panic) *before* any promise/refund logic is set up:
- The "transaction already in progress" guard at the very top of `rlp_execute` runs before `attached_deposit`/`CallerDeposit` is even inspected: [4](#0-3) 
- Any `Err(e)` bubbled up from `inner_rlp_execute` (e.g. `AccountNonceExhausted`, malformed RLP transaction / `Error::User`, unsupported action, or an `ExecutionContext::new` failure) is converted directly to a value response with no refund: [5](#0-4) [6](#0-5) 

Crucially, the protocol-level automatic deposit refund only fires when the *action receipt itself* fails (i.e., when `result.result.is_err()` at the runtime level, generally caused by a panic/trap), not when a contract method completes successfully but reports a logical/business failure via its return value: [7](#0-6) [8](#0-7) 

Since `rlp_execute` never panics on these paths — it deliberately catches errors and returns a normal `ExecuteResponse` — the runtime records the receipt as successful, `deposit_refund` is `Balance::ZERO`, and no `Receipt::new_balance_refund` is ever generated. The attached NEAR is already credited to the `WalletContract` account balance (attached deposits are deposited into the receiver's balance before execution starts, per the Economics API model) and stays there permanently, with no contract-level mechanism to reclaim it on these paths.

### Impact Explanation
Any external, unprivileged caller (e.g., a relayer or dApp submitting a transaction on behalf of an eth-implicit account owner) that attaches a NEAR deposit to `rlp_execute` and hits any of the synchronous failure conditions — a concurrently in-flight transaction, an exhausted nonce, a malformed/invalid RLP-encoded transaction, or an unsupported action — permanently loses that attached deposit. This is a direct, transaction-triggered, unauthorized retention of caller funds with no recovery path, matching "permanently frozen funds" impact criteria.

### Likelihood Explanation
Likelihood is high: no privileged role is needed, the caller only needs to submit a single `FunctionCall` to `rlp_execute` with a non-zero deposit while the target account's `has_in_flight_tx` is true (trivially achievable by any relayer racing itself or by a normal user retry) or while submitting a transaction that fails RLP parsing/validation (e.g., malformed data, replayed/invalid nonce). These are all conditions reachable directly from a single submitted transaction/RPC call.

### Recommendation
Ensure the attached deposit is always accounted for and refunded on every path in `rlp_execute`/`inner_rlp_execute` that returns a synchronous `ExecuteResponse` without spawning the deposit-bearing promise. Concretely:
- Compute `caller_deposit` (or the raw `attached_deposit`) before any early return, and explicitly issue a `Promise::new(predecessor_account_id).transfer(attached_deposit)` (or attach it back onto the response) whenever the method resolves synchronously with `success: false`.
- Audit every `return PromiseOrValue::Value(...)` / `Err(...)` branch in `inner_rlp_execute` and `rlp_execute` to guarantee the deposit is either consumed by a spawned promise or explicitly refunded.

### Proof of Concept
1. An external caller (not the eth-implicit account itself) calls `rlp_execute(target, tx_bytes_b64)` twice in the same block/receipt window with a non-zero attached deposit, or with a nonce that is already `u64::MAX`, or with `tx_bytes_b64` that fails RLP decoding.
2. `rlp_execute` returns `PromiseOrValue::Value(ExecuteResponse { success: false, .. })` synchronously (lines 97-105 or 116-128 of `lib.rs`), without spawning any promise and without invoking `rlp_execute_callback`.
3. Because this is a normal (non-panicking) WASM return, `apply_action_receipt`/`refund_unspent_gas_and_deposits` sees `result.result.is_ok()` and sets `deposit_refund = Balance::ZERO` (`runtime/runtime/src/lib.rs:1303`), so no balance-refund receipt is created.
4. The caller's attached deposit remains credited to the `WalletContract` account's balance indefinitely, with no method in the contract able to withdraw it back to the caller.

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }
