## Title
`ensure_match_transaction_info` skips state-checkpoint hash comparison, allowing a corrupted/divergent state root to pass replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole invariant check used by the chunk-executor's replay-verification path (`execution/executor/src/chunk_executor/mod.rs::verify_execution`) to confirm that locally re-executed transaction output matches the authenticated `TransactionInfo` persisted/retrieved from storage. The function explicitly does **not** compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the very fields that commit the Merkle state root into the accumulator-proof-bearing `TransactionInfo`. This mirrors the external report's root cause pattern: a value that should gate/commit only after a correctness check is instead accepted/propagated with an unchecked, premature or divergent linkage — here, a state root is treated as "verified" while the one proof-relevant value that actually binds execution to committed state is never checked.

### Finding Description
`TransactionInfo` is the object stored in and authenticated by the transaction accumulator; its `state_checkpoint_hash()` is the on-chain root binding a `Version` to a specific `JellyfishMerkleTree`/state root [1](#0-0) .

`ensure_match_transaction_info` verifies status, gas used, write-set hash (`state_change_hash`), and event root hash against the target `TransactionInfo`, but explicitly skips the checkpoint hashes with a self-documenting TODO admitting the gap: [2](#0-1) 

This function is the only correctness gate invoked in the chunk-executor's `verify_execution` routine, which drives `db-tool`'s `replay_on_archive`/`replay-verify` tooling used to validate that re-executed history matches an authenticated backup/archive: it iterates locally-computed `execution_output.to_commit.transaction_outputs` against persisted `transaction_infos` and calls `ensure_match_transaction_info` per version [3](#0-2) .

Because the state/hot-state/position checkpoint hashes are excluded from the comparison, a mismatch between the locally-recomputed state root and the state root recorded in the (supposedly authenticated) `TransactionInfo` will not be detected by this check. If the "trading-native" state root computation (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, referenced directly in the same TODO) diverges from the actual persisted state — whether from a bug in state-root computation, storage corruption, or a maliciously/incorrectly produced backup/replay input — `replay_on_archive` and any other consumer of `ensure_match_transaction_info` (also used from `aptos-move/cli/src/commands.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs`) will report a "successful" replay even though the state root is wrong.

### Impact Explanation
This breaks the proof-binding invariant that replay/restore tooling is supposed to guarantee: that recomputed execution state matches the authenticated ledger state at a given version. On mainnet-adjacent operational flows (chunk executor replay-verification, `db-tool replay-verify`, debugger-driven re-execution against archived data), this allows a divergent or corrupted state root to be silently accepted as validated, which can mask hard-fork-only state divergence, corrupt/incorrect archive data, or compute-path bugs in the state-checkpoint computation. Since `state_checkpoint_hash` is exactly the value bound into `TransactionInfo` and hashed into the transaction accumulator (used for proof verification, e.g., `TransactionInfoListWithProof::verify`), an integrity checker that skips it defeats the purpose of the check for the state-root portion of the commitment, even though transaction hash/write-set/event-root are still checked.

### Likelihood Explanation
This is not a hypothetical timing race like the external report; it's a standing, self-acknowledged gap in the codebase (explicit TODO), triggered on every invocation of `verify_execution`/`ensure_match_transaction_info` in existing replay/verify/debugger tooling. The gap is guarded behind future enablement of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, meaning it is a known, unresolved TODO rather than already-mitigated. Whether this constitutes a currently *exploitable* mainnet path depends on whether/when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` and the "trading-native" state-root path are enabled in production, which I could not fully verify from the available index — the feature flag's exact current on-chain enablement was not confirmed in this pass. I could not find any compensating verification of `state_checkpoint_hash` elsewhere in the `verify_execution` call chain, but I was not able to check every downstream consumer of `execution_output.to_commit` (`aptos-move/cli/src/commands.rs` and other checks might separately assert on the checkpoint hash).

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on both sides) before returning `Ok(())`, instead of leaving this TODO unresolved. If `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently disabled and the state root is always locally computed/verified elsewhere before this function is called, that compensating check should be made explicit and enforced at this call site (or a debug_assert/hard failure added) rather than relying on an implicit assumption documented only in a comment.

### Proof of Concept
No runnable PoC was constructed because reproducing the divergence requires driving `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-gated state-root computation to diverge from persisted `TransactionInfo.state_checkpoint_hash`, which requires environment/feature-flag state not confirmed available in this codebase snapshot. The structural proof is the code itself: [4](#0-3)  shows the comparator omitting the checkpoint-hash fields, and [5](#0-4)  shows this is the sole gate used by replay verification.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
