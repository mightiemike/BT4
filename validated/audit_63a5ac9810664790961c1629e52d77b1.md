### Title
Unbounded recursion in `get_recursive_transaction_results` allows a stack-overflow DoS via a crafted transaction's receipt chain — ([File: chain/chain/src/chain.rs])

### Summary
The recursive receipt-chain walk used to answer transaction-status RPC queries has no depth limit. A crafted transaction that causes a long chain (or fan-out) of downstream receipts (e.g., a self-recursive cross-contract call pattern, similar to the `max_self_recursion_delay`/`internal_recurse` patterns already used in nearcore's own evil-contract tests) will produce a correspondingly deep chain of `ExecutionOutcome`s linked by `receipt_ids`. When any RPC caller subsequently queries the transaction/receipt status, the node walks this chain with unbounded native-stack recursion and can crash with a stack overflow.

### Finding Description
`get_recursive_transaction_results` recurses once per `receipt_id` found in each outcome's `receipt_ids` list, with no depth counter, no iterative/worklist rewrite, and no cap tied to protocol limits: [1](#0-0) 

It is invoked directly from `get_final_transaction_result`, the function that builds the `FinalExecutionOutcomeView` returned by JSON-RPC transaction-status calls: [2](#0-1) 

This is structurally the same bug class as CVE-2024-47072: XStream's `BinaryStreamDriver` recursively parsed nested elements from an attacker-controlled binary stream with no depth guard, letting a native stack overflow crash the process. Here, the "input stream" is the chain of receipts produced by a transaction the attacker fully controls (via nested cross-contract Promise calls / self-calls), and the "parser" is `get_recursive_transaction_results`, which walks that receipt DAG with native Rust recursion instead of an explicit stack.

Unlike the WASM contract-side recursion (bounded by gas and caught by `test_evil_deep_recursion`), this recursion runs in the **host/RPC-serving process itself**, so a stack overflow here does not fail a single contract call — it can abort the node process that is serving the RPC request. Both `runtime_user.rs`'s test-only analogue (`get_recursive_transaction_results` in `integration-tests/src/user/runtime_user.rs:221-243`) and the production `chain.rs` version share this same unbounded-recursion structure, confirming the pattern is systemic rather than a one-off.

An attacker able to submit transactions can drive very deep receipt chains cheaply: each hop is a cross-contract `FunctionCall` promise (a few Tgas), and nearcore's own contract test harness demonstrates depths of 100,000+ are achievable within gas/test parameters (`test_evil_deep_recursion`, using values up to 1,000,000). A similarly deep receipt-outcome chain, once persisted in the chain/receipt store, is later walked recursively by `get_recursive_transaction_results` whenever any node (validator or RPC node) is asked for that transaction's final status — an operation any unprivileged RPC caller can trigger.

### Impact Explanation
A successful stack overflow in `get_recursive_transaction_results` aborts the process (`SIGSEGV`/`SIGABRT` from stack guard page violation), which is not a recoverable Rust panic. Because `get_final_transaction_result` runs inside the chain/view-client serving path for `tx` / `EXPERIMENTAL_tx_status`-style RPC calls, this directly halts the RPC node process handling the request. If this code path also executes on validator nodes serving such queries (view client actor / chain object shared with the client actor), it can cause a validator crash — a transaction-triggered halt, which the validation rules for this scan explicitly treat as in-scope, high-impact (denial of service / consensus-node crash), matching the CVSS `A:H` (availability-high) rating of the upstream XStream advisory.

### Likelihood Explanation
Likelihood is high for the RPC-node crash: any account holder can submit a transaction chaining enough cross-contract calls/receipts (well within existing gas and action limits demonstrated by nearcore's own recursion test contracts) to build a receipt-outcome chain deep enough to overflow a typical 8MB thread stack, then simply query that transaction's status via public RPC — no special privileges, validator status, or race condition needed.

### Recommendation
Rewrite `get_recursive_transaction_results` (and its `integration-tests` analogue) to use an explicit iterative worklist (`Vec`/`VecDeque`-based BFS/DFS) instead of native recursion, mirroring the pattern already used elsewhere in the codebase for untrusted recursive structures (e.g. `traverse_all_nodes` in `core/store/src/trie/state_parts.rs:644-714`, `get_subtree_size` in `core/store/src/trie/trie_recording.rs:297-372`, and `flatten_nodes` in `core/store/src/trie/trie_storage_update.rs:162-252`, all of which explicitly convert recursive trie walks into stack-based loops "to avoid any potential stack overflows"). Additionally, cap the number of chained outcomes/receipts collected per query to a sane bound and return a partial/error result rather than fully expanding an attacker-inflated chain.

### Proof of Concept
1. Submit a transaction whose `FunctionCall` action invokes a contract method that recursively issues further cross-contract `FunctionCall` promises to itself (the same self-recursive pattern nearcore already exercises in `runtime/near-test-contracts/test-contract-rs/src/lib.rs` via `max_self_recursion_delay`/`internal_recurse`), producing a chain of N receipts each referencing the next via `receipt_ids`, for N large enough to exceed the RPC/chain process's stack size (empirically demonstrated at N≈100,000+ recursion depth in `test_evil_deep_recursion`, `integration-tests/src/tests/runtime/test_evil_contracts.rs:133-156`).
2. Wait for the chain to execute all receipts across the necessary blocks.
3. Call the transaction-status RPC (`tx` / equivalent) for the originating transaction hash, which invokes `Chain::get_final_transaction_result` → `get_recursive_transaction_results`.
4. The recursive walk over the N-deep `receipt_ids` chain exhausts the native call stack and crashes the serving node process — a transaction-triggered denial of service.

    /// Collect all the execution outcomes existing at the current moment
    /// Fails if there are non executed receipts, and require_all_outcomes == true
    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

    /// Waits for the end of the execution of all corresponding receipts
    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,

        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);

        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }
