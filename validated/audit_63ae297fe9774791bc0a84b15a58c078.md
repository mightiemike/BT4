Based on my investigation, I found a native analog of the "no validation of address parameter" bug class in the inbound revert/refund flow.

### Title
Unvalidated `RevertInstructions.FundRecipient` address can permanently freeze refunded user funds - (File: `x/uexecutor/keeper/build_revert_outbound.go`)

### Summary
The external report flags that `BaseStrategy`'s `vault` address parameter is accepted into the constructor without validation, which can break the contract if the value is malformed. The Push Chain analog is `RevertInstructions.FundRecipient` on an `Inbound` — a string address supplied entirely by the depositing user on the *source* chain (part of the gateway `addFunds`-style call) — which is threaded straight through to become the `Recipient` of a refund/revert `OutboundTx` without ever being canonicalized or format-validated for the destination chain namespace.

### Finding Description
`RevertInstructions` is a thin proto wrapper around a single string field with no `ValidateBasic`: [1](#0-0) 

It is populated directly from attacker-controlled source-chain event data on the `Inbound` message: [2](#0-1) 

When an inbound fails post-quorum validation, or is stuck and later force-reverted by admin, `buildRevertOutbound` uses `inbound.RevertInstructions.FundRecipient` verbatim as the outbound `Recipient` with no address-format check — only an empty-string fallback to `Sender`: [3](#0-2) 

This is inconsistent with how every other externally-supplied address field in the registry is treated: `TokenConfig.Address` and `NativeRepresentation.ContractAddress` are both run through `utils.CanonicalizeAddressByNamespace` / `utils.CanonicalizeEVMAddress` before being accepted, specifically to guarantee a parseable, canonical address: [4](#0-3) [5](#0-4) 

By contrast, `Inbound`/`RevertInstructions` validation (as far as I could confirm) only checks that `Recipient` is non-empty for `FUNDS`-type inbounds — I found no equivalent canonicalization check for `RevertInstructions.FundRecipient`: [6](#0-5) 

The admin escape-hatch path (`RevertStuckInbound` → `MsgRevertStuckInbound`) reuses the exact same `buildRevertOutbound` helper and the exact same unvalidated `FundRecipient`, so even the manual recovery path cannot correct a malformed value once the inbound has already been ballot-finalized: [7](#0-6) 

### Impact Explanation
If an unprivileged user submits a source-chain deposit with a malformed/garbage `revertRecipient` (not a parseable address for the destination chain's VM type — e.g. wrong length, non-hex garbage for EVM, invalid base58 for SVM), and the deposit later fails execution or expires (triggering the revert/refund path), the resulting `OutboundTx.Recipient` carries the invalid value into the TSS signing/broadcast pipeline. Depending on downstream TSS tx-builder behavior, this can produce an outbound that can never be validly signed or broadcast to the destination chain, leaving the refund permanently stuck `PENDING` — i.e., permanent freezing of the user's own bridged funds, with no code path shown that re-validates or falls back to `Sender` for this specific failure mode (fallback to `Sender` only fires when the field is empty, not when it's malformed).

### Likelihood Explanation
Likelihood is high for reachability (any unprivileged depositor fully controls this field via their own deposit tx) but the practical severity depends on whether the downstream TSS/outbound tx-builder itself performs a hard validation pass. I could not fully verify, given index coverage limits, whether `Inbound.ValidateBasic()` (in `x/uexecutor/types/inbound.go`) or a later TSS-signing stage independently rejects malformed `FundRecipient` values before they reach `PendingOutbounds`. This is the key uncertainty in this finding.

### Recommendation
Add a `ValidateBasic`/canonicalization check on `RevertInstructions.FundRecipient` (mirroring `utils.CanonicalizeAddressByNamespace` used for `TokenConfig.Address`) at inbound ingestion/vote time, keyed on the destination chain's VM type, and reject or fall back to `Sender` when the field is non-empty but not a parseable address for that chain.

### Proof of Concept
Not exploitable/verifiable purely by static review — would require constructing an `Inbound` with `RevertInstructions.FundRecipient` set to a malformed string for the source chain's namespace, driving it through 2/3 quorum via `MsgVoteInbound` (as in `test/integration/uexecutor/vote_inbound_validation_test.go`) to a failure state, and observing whether the resulting `OutboundTx.Recipient` is ever rejected before being placed in `PendingOutbounds`, or whether it persists there indefinitely.

func (k Keeper) buildRevertOutbound(sdkCtx sdk.Context, inbound *types.Inbound) *types.OutboundTx {
	recipient := inbound.Sender
	if inbound.RevertInstructions != nil && inbound.RevertInstructions.FundRecipient != "" {
		recipient = inbound.RevertInstructions.FundRecipient
	}

	outbound := &types.OutboundTx{
		DestinationChain:  inbound.SourceChain,
		Recipient:         recipient,
		Amount:            inbound.Amount,
		ExternalAssetAddr: inbound.AssetAddr,
		Sender:            inbound.Sender,
		TxType:            types.TxType_INBOUND_REVERT,
		OutboundStatus:    types.Status_PENDING,
		Id:                types.GetOutboundRevertId(inbound.SourceChain, inbound.TxHash, inbound.LogIndex),
	}
