### Title
Approve/Cancel spec status checks are non-atomic (TOCTOU), allowing a cancelled job proposal spec to still be approved and deployed - (File: core/services/feeds/service.go, core/services/feeds/orm.go)

### Summary
`ApproveSpec` and `CancelSpec` in the feeds service each perform a "read current status → validate → act" sequence, but the validation and the eventual `UPDATE` are not performed atomically against the same status predicate. The underlying SQL `UPDATE` statements in `orm.ApproveSpec` and `orm.CancelSpec` update rows by `id` alone, without a `WHERE status = <expected>` guard, so a concurrent status transition between the initial read and the final write is not detected. This mirrors the reported bug class where a cancellation flag/state is checked once but not re-validated at execution time, letting a "cancelled" action still complete.

### Finding Description
`service.ApproveSpec` reads the spec/proposal state up front and validates it via `isApprovable`, which is based on the `spec.Status`/`proposal.Status` retrieved before the transaction begins: [1](#0-0) 

The actual approval mutation happens later, inside a DB transaction, by directly calling `tx.orm.ApproveSpec(ctx, id, j.ExternalJobID)`: [2](#0-1) 

The ORM-level `ApproveSpec` implementation issues an `UPDATE job_proposal_specs ... WHERE id = $2` with no status predicate, so it will unconditionally flip the spec/proposal status to `Approved` regardless of any status change that occurred between the initial read (in `isApprovable`) and this write: [3](#0-2) 

Symmetrically, `service.CancelSpec` checks `spec.Status != SpecStatusApproved` using a value fetched before its own transaction, then calls `tx.orm.CancelSpec`, whose `UPDATE` also only filters `WHERE id = $2` with no status guard: [4](#0-3) [5](#0-4) 

Because neither write is conditioned on the status value that was validated, two concurrent requests (e.g., one admin/API caller invoking `ApproveSpec` while another invokes `CancelSpec` on the same spec ID) can race: the "cancel" check passes based on stale data, and the "approve" transaction — which does its own multi-step work (creating the job, calling `s.jobSpawner.CreateJob`, calling FMS `ApprovedJob`) — completes and persists an `Approved` status even though the spec was concurrently cancelled (or vice versa). This is directly analogous to the reported Vader issue: the cancellation path updates one piece of state (`mapPID_votes` / here, the initial in-memory read) but the finalization/execution path (`finaliseProposal` / here, the ORM `UPDATE ... WHERE id = $2`) does not re-check the cancellation flag before proceeding, so the cancelled action still executes.

### Impact Explanation
A successful race results in a job spec that was intended to be cancelled still being materialized as a live Chainlink job (via `s.jobSpawner.CreateJob`) and reported to the Feeds Manager as `ApprovedJob`, or a legitimately approved job being silently cancelled/deleted (`s.jobSpawner.DeleteJob`) despite the approval having already been validated. This is an unsafe workflow/job execution issue: an operator's explicit cancellation intent can be bypassed, causing an unintended job (potentially an old/rejected on-chain job spec) to run on the node, or causing a validly approved production job to be torn down unexpectedly.

### Likelihood Explanation
This requires two administrative actions (approve and cancel) on the same spec ID racing in a narrow window between the initial `GetSpec`/`isApprovable` check and the final transactional `UPDATE`. This is only exploitable by parties with access to the Feeds Manager job-proposal approve/cancel GraphQL mutations (`ApproveJobProposalSpec`/`CancelJobProposalSpec` resolvers), so likelihood is limited to operators/automation with that access, but no special privilege escalation is needed beyond normal feeds-admin usage — an automated approval/cancellation pipeline (e.g., CI or FMS-driven bulk operations) could trigger this without malicious intent.

### Recommendation
Make the status transition atomic: add the expected current status to the `WHERE` clause of the `UPDATE` in `orm.ApproveSpec` and `orm.CancelSpec` (e.g., `WHERE id = $2 AND status = 'pending'`), and check `rowsAffected == 0` to return a conflict/error when the row's status has already changed. This closes the TOCTOU window analogous to fixing `finaliseProposal` to check a cancellation flag before executing.

### Proof of Concept
1. Create and get a spec into `SpecStatusApproved` (pending) state.
2. Concurrently issue: (a) `CancelSpec(ctx, specID)` and (b) `ApproveSpec(ctx, specID, force)`.
3. Both requests read the spec status before either transaction commits, so both pass their respective validation (`spec.Status != SpecStatusApproved` fails to catch it for cancel, and `isApprovable` still sees the pre-cancel status for approve).
4. Whichever `UPDATE ... WHERE id = $2` (no status predicate) commits last wins, silently overriding the other operation's intended final state — e.g., `ApproveSpec`'s transaction finishes after `CancelSpec`'s, leaving the job created and reported as `Approved` even though it was concurrently cancelled.

func (s *service) ApproveSpec(ctx context.Context, id int64, force bool) error {
	spec, err := s.orm.GetSpec(ctx, id)

		return errors.Wrap(err, "orm: job proposal")

		return err
	}

func (s *service) CancelSpec(ctx context.Context, id int64) error {
	spec, err := s.orm.GetSpec(ctx, id)
	if err != nil {
		return errors.Wrap(err, "orm: job proposal spec")
	}

	if spec.Status != SpecStatusApproved {
		return errors.New("must be an approved job proposal spec")
	}

	jp, err := s.orm.GetJobProposal(ctx, spec.JobProposalID)
	if err != nil {
		return errors.Wrap(err, "orm: job proposal")

	)

		var txerr error

// CancelSpec cancels the spec and removes the external job id from the associated job proposal. It
// sets the status of the spec and the proposal to cancelled, except in the case of deleted

func (o *orm) CancelSpec(ctx context.Context, id int64) error {
	// Update the status of the approval
	stmt := `
UPDATE job_proposal_specs
SET status = $1,
	status_updated_at = NOW(),
	updated_at = NOW()
WHERE id = $2
RETURNING job_proposal_id;
`

	o.lggr.Infow("cancelling job proposal spec", "specID", id)
	var jpID int64
	if err := o.ds.GetContext(ctx, &jpID, stmt, SpecStatusCancelled, id); err != nil {
