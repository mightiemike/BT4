Based on my research, I found a viable analog in the vault interest-accrual pause mechanism, not in the market-side index cache (which I found is correctly refreshed after `socialize-debt`, closing that avenue).

### Title
Frozen liquidity index during an `accrue` pause lets depositors front-run the retroactive interest catch-up and extract other suppliers' realized yield - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent per-asset vault contracts)

### Summary
Each vault's `pause-states` record exposes independent pause flags for `deposit`, `redeem`, `borrow`, `repay`, and `accrue` [1](#0-0) [2](#0-1) . When only `accrue` is paused, the `accrue` function short-circuits and returns the *current* (frozen) `index`/`lindex` instead of computing and applying interest, explicitly documented as a pass-through: [3](#0-2) . Because `deposit` and `redeem` have their own separate pause flags and are unaffected by the `accrue` flag, both remain callable while `accrue` is paused, and both still route through `accrue()` first, receiving the frozen index/price [4](#0-3) [5](#0-4) .

### Finding Description
`last-update` is only advanced when the computed `index`/`lindex` actually changes: [6](#0-5) . While `accrue` is paused, `next-index`/`next-liquidity-index` short-circuit and return the unchanged current value [7](#0-6) , so `last-update` is never bumped for the whole pause duration. When the DAO/guardian later unpauses `accrue`, the very next `accrue()` call computes `time-delta = stacks-block-time - last-update`, which now spans the *entire* pause window, and applies the corresponding compounded interest to `index`/`lindex` in a single lump-sum jump [8](#0-7) .

Because the interest rate curve (`interest-rate()`, driven by public utilization) and the pause/unpause timing are both observable on-chain, the size of this pending lump-sum index jump is fully predictable in advance, exactly as the referenced Derby bug describes for `exchangeRate`. An attacker can:
1. Observe that `accrue` is paused for a vault (public `pause-states`), while `deposit`/`redeem` remain enabled.
2. Deposit right before the unpause transaction/first post-unpause `accrue()` call, minting zTokens at the stale, pre-jump `lindex` (share price) via `convert-to-shares-preview` inside `deposit` [9](#0-8) .
3. Wait for (or trigger) the first `accrue()` after unpause, which retroactively compounds the whole frozen interval into `lindex` at once.
4. Immediately `redeem` at the new, jumped `lindex`, capturing interest that was economically earned by lenders who supplied liquidity throughout the pause window, without having borne any of that exposure.

This mirrors the report's root cause precisely: a value (`lindex`/share price) is bound at the time of `deposit`/`redeem`, its true economic source (accumulated borrower interest) moves independently of that bound value while accrual is paused, and the later use (the lump-sum catch-up on unpause) is exploitable because deposit/redeem are not tied to the same event that invalidates the frozen index.

### Impact Explanation
This allows theft of unclaimed yield from existing suppliers: the interest that should be distributed proportionally over time to depositors who held zTokens throughout the pause is instead captured disproportionately by an attacker who deposits only immediately before the catch-up and withdraws immediately after. This falls under the in-scope "High - theft of unclaimed yield" impact category.

### Likelihood Explanation
Likelihood depends on the `accrue` pause flag actually being toggled off while `deposit`/`redeem` are enabled, and on the pause lasting long enough / utilization being high enough for the retroactive jump to exceed gas/slippage costs. Pause/unpause is a DAO/guardian-controlled action, so the attacker cannot force the pause but can monitor for it and race the unpause transaction or the first accrue-triggering call afterward; this is a realistic and repeatable MEV-style opportunity rather than a one-off edge case, similar to the original Derby finding's threat model.

### Recommendation
When resuming from an `accrue` pause, either (a) reset `last-update` to the pause-start timestamp so no interest is retroactively compounded for the paused interval, or (b) disable `deposit`/`redeem` automatically whenever `accrue` is paused so users cannot mint/burn shares at a stale index, or (c) apply the interest catch-up gradually rather than in a single lump sum.

### Proof of Concept
1. DAO pauses `accrue` for `vault-usdc` (sets `accrue` bit in `pause-states`) while leaving `deposit`/`redeem` unpaused.
2. Time passes; borrower interest accrues economically (via utilization) but `index`/`lindex`/`last-update` remain frozen because `accrue()` returns early [3](#0-2) .
3. Attacker observes the pending unpause (public governance action) and calls `deposit(amount, min-out, attacker)` just before it, minting zUSDC at the stale `lindex`.
4. DAO unpauses `accrue`; the next `accrue()` call (attacker's own follow-up tx, or any other user's tx) computes the full pause-duration `time-delta` and jumps `lindex` up in one step [8](#0-7) .
5. Attacker calls `redeem(shares, min-out, attacker)` immediately, receiving the post-jump underlying value — capturing the whole pause-period's interest despite having deposited for only two transactions.

Note: I could not fully confirm within the remaining iterations whether `deposit`/`redeem` pause flags are ever automatically linked to the `accrue` flag at the protocol-config level (e.g., a DAO proposal that always pauses all four together); if such a coupling exists in the deployed configuration, this specific window would be closed in practice even though the contract code itself does not enforce it. This would need to be verified against the actual DAO pause proposals, which are outside the scoped contract logic reviewed here.
