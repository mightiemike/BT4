### Title
Non-atomic check-then-act on `eventFilter2ResultFull`/`eventFilter2ResultSolidity` allows concurrent `eth_newFilter` calls to bypass `maxLogFilterNum` limit - (File: framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java)

### Summary
`TronJsonRpcImpl.newFilter(FilterRequest)` enforces a filter-count cap by reading `ConcurrentHashMap.size()` and comparing it to `maxLogFilterNum`, then later calling `put(filterID, ...)` on the same map. Because the size check and the subsequent insertion are two separate, non-synchronized operations, concurrent unprivileged callers can race past the intended cap and register more `LogFilterAndResult` entries than `maxLogFilterNum` permits.

### Finding Description
`ConcurrentHashMap` guarantees atomicity for individual operations (`size()`, `put()`) but provides no atomicity across a read-then-write sequence spanning two calls. The guard `if (maxLogFilterNum > 0 && eventFilter2Result.size() >= maxLogFilterNum) { throw ... }` followed later by `eventFilter2Result.put(filterID, filterAndResult)` is a classic TOCTOU (time-of-check-to-time-of-use) race: many threads can each observe a size below the threshold before any of them commits its `put`, letting all of them proceed and insert, so the map ends up holding more entries than `maxLogFilterNum` allows. Each entry retains a `LogFilterAndResult`/`LogFilterWrapper` with its own accumulating result list, so overshoot beyond the configured cap increases retained memory. This is reachable by any unauthenticated JSON-RPC client calling `eth_newFilter`, since filter creation requires no authentication, signature, or fee — it is a pure RPC-layer resource-registration call.

### Impact Explanation
Exceeding the intended `maxLogFilterNum` bound allows more concurrently-held log filters (and their retained result buffers) than the operator configured, which is a control-bypass on the node's own resource-limiting safeguard for the JSON-RPC subsystem. This falls under DoS via RPC-API in the sense that the node's designed memory/connection-count safeguard can be exceeded, though the excess is bounded by the number of concurrently racing threads/requests within the race window (not literally unbounded growth per single call) — the impact is a limited multiplicative overshoot per burst of concurrent requests, not an unlimited-per-request amplification.

### Likelihood Explanation
Exploitability requires only network access to the JSON-RPC endpoint (default enabled on many node configurations) and the ability to fire many concurrent `eth_newFilter` requests — no cost, no signature, no fees, fully repeatable. The race window is small (between `size()` check and `put()`), so the overshoot per attack burst is proportional to attacker concurrency and network/thread scheduling, requiring sustained high-concurrency bursts to meaningfully exceed the cap by a significant margin.

### Recommendation
Make the check-and-insert atomic, e.g. use `ConcurrentHashMap.computeIfAbsent`/a custom `compute` that atomically checks size before insertion, or guard the check-and-put sequence with an explicit lock (e.g., `synchronized` block or `ReentrantLock`) around both the size check and the put, or use an `AtomicInteger` counter incremented via `compareAndSet` before performing the map insertion, decrementing on filter expiry/uninstall.

```java
@Test
public void testConcurrentNewFilterRace() throws InterruptedException {
    int threads = 50;
    ExecutorService pool = Executors.newFixedThreadPool(threads);
    CountDownLatch latch = new CountDownLatch(threads);
    for (int i = 0; i < threads; i++) {
        pool.submit(() -> {
            try {
                tronJsonRpc.newFilter(someFilterRequest());
            } catch (Exception ignored) {
            } finally {
                latch.countDown();
            }
        });
    }
    latch.await();
    // Expected (correct behavior): map size <= maxLogFilterNum
    // Actual (vulnerable behavior): map size can exceed maxLogFilterNum
    assertTrue(eventFilter2ResultFieldSize() <= maxLogFilterNum);
}
```
