### Title
Method-ID upgrade cross-network replay between `Nightly` and `TestNetworkWithForks` due to identical `chain_id` and identical default council public keys - ([File: crates/light-client-prover/src/circuit/initial_values.rs])

### Summary
`citrea_network_to_chain_id` maps both `Network::Nightly` and `Network::TestNetworkWithForks` to the same value (`5665`), and the corresponding `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` / `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` constants are populated from the exact same environment-variable names with byte-identical default hex-encoded public keys. Both networks are also wired to the same compiled light-client guest program (`LIGHT_CLIENT_LATEST_BITCOIN_GUESTS`), whose `NETWORK` constant is fixed at build time via `CITREA_NETWORK`/default `Network::Nightly`. This means a `BatchProofMethodId` body signed for one of these two network labels will pass both the `chain_id` check and the `verify_method_id_security_council` signature check on a deployment configured/compiled for the other label, unless an operator deliberately supplies different override env vars per build.

### Finding Description
The binding claimed by the question is: `citrea_network_to_chain_id(Network::Nightly) == citrea_network_to_chain_id(Network::TestNetworkWithForks)` (both `5665`) AND `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS == TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS`.

- `citrea_network_to_chain_id` returns `5665` for both `Network::Nightly` and `Network::TestNetworkWithForks`: [1](#0-0) .
- `run_l1_block`'s `DataOnDa::BatchProofMethodId` branch checks `circuit_chain_id != batch_proof_method_id.body.chain_id` and then calls `verify_method_id_security_council(*method_id_upgrade_authority_da_public_keys, ...)`, where `method_id_upgrade_authority_da_public_keys` is whichever network's constant array was passed in by the caller: [2](#0-1) .
- `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` and `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` are both built from `option_env!("METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_1..5")` — the **same** environment variable names — with identical hard-coded default hex values (private keys `...D9077`..`...D9073`): [3](#0-2) .
- The guest binary that actually implements the light client circuit selects its `NETWORK` constant (and therefore which of the two identical arrays gets compiled in) purely from the `CITREA_NETWORK` build-time env var, defaulting to `Network::Nightly`: [4](#0-3) , and the pubkeys are selected via the same `match NETWORK` pattern: [5](#0-4) .
- On the node/host side, `Network::Nightly` and `Network::TestNetworkWithForks` are both routed to `LIGHT_CLIENT_LATEST_BITCOIN_GUESTS` for both the ELF and the code commitment used for proof verification: [6](#0-5) [7](#0-6) .
- Native-side, `InitialValueProvider<BitcoinSpec>::method_id_upgrade_authority_da_public_keys` still does a `match self { Network::Nightly => NIGHTLY_..., Network::TestNetworkWithForks => TEST_NETWORK_WITH_FORKS_... }`, so which constant gets used is determined by whichever `Network` value the host process was launched with: [8](#0-7) .

Because both networks (a) collide on `chain_id`, (b) use the same guest ELF/code-commitment, and (c) default to identical override-able public keys via identically-named env vars, a `BatchProofMethodId` DA transaction that is validly signed by the 3-of-5 council for one of these networks (e.g., a `TestNetworkWithForks` test/staging deployment) will also pass `chain_id` matching and `verify_method_id_security_council` on a deployment running with `Network::Nightly` (or vice versa), as long as the deploying operator did not override the default `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_1..5` env vars differently between the two builds. An unprivileged attacker who observes the (public) inscribed Bitcoin transaction carrying the valid `BatchProofMethodId` blob for one network can copy its exact bytes and re-inscribe them as a new transaction targeting the DA/network the attacker wants to attack; `run_l1_block` performs no binding of the message to a specific Bitcoin network's DA beyond the `chain_id` field inside the signed body, which collides.

### Impact Explanation
If the two deployments actually run with default (unmodified) public keys, this allows a replayed `BatchProofMethodId` message to update the accepted future batch-proof method ID on the "victim" network's light client proof state without that network's own council having authorized it for that network — this falls into the Critical category "a sequencer commitment or method-id upgrade accepted that was never authorised." Because `BatchProofMethodIdAccessor::insert` persists into the LCP JMT state that is proved and consumed transitively by Clementine's bridge proof (per `docs/light-client-circuit.md`), a forged/foreign method ID acceptance can affect which batch-proof method ID is trusted going forward on the "wrong" network, potentially enabling acceptance of a batch proof for a state transition that did not happen there. This is repeatable for every future council-authorized method-id upgrade issued on either colliding network, as long as the key material stays identical across the two.

### Likelihood Explanation
This is conditioned entirely on operational configuration, which could not be fully confirmed from the repository: the default (`option_env!`-absent) values for `NIGHTLY_...` and `TEST_NETWORK_WITH_FORKS_...` public keys are byte-identical in source, and `Network::TestNetworkWithForks` is explicitly documented as "used for testing purposes only," suggesting it may run on a separate DA network/signet from the "real" Nightly deployment, and operators plausibly override the env vars per deployment. Whether real production/nightly infrastructure sets distinct `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_1..5` per network at build time is a deployment/CI detail not visible in this repository — I could not verify actual CI/build pipeline configuration to confirm or refute divergence. Given the audit rules require exact confirmation of identical key material to rate Critical, and the only concrete evidence found is that the *source-code defaults* are identical (not necessarily what is deployed), this should be treated as a latent, configuration-dependent finding rather than a confirmed, end-to-end exploitable Critical bug against a live deployment.

### Recommendation
- Use genuinely distinct `chain_id` values for `Network::Nightly` and `Network::TestNetworkWithForks` in `citrea_network_to_chain_id` instead of both mapping to `5665`.
- Ensure the default (non-overridden) `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` and `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` constants are never identical, and use distinctly named environment variables (not the shared `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_1..5`) per network so that a single build/CI environment cannot accidentally produce identical council key sets for two different network labels.
- Add a compile-time or startup assertion that the resolved chain_id and public key set for the running `Network` differ from those of any other network sharing the same guest ELF.

```rust
#[test]
fn nightly_and_test_network_with_forks_method_id_keys_should_differ() {
    use crate::circuit::initial_values::bitcoinda::{
        NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS,
        TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS,
    };
    use sov_rollup_interface::Network;
    use crate::circuit::citrea_network_to_chain_id;

    // Binding 1: chain ids collide
    assert_eq!(
        citrea_network_to_chain_id(Network::Nightly),
        citrea_network_to_chain_id(Network::TestNetworkWithForks)
    );

    // Binding 2: default public keys must NOT be identical for the
    // chain_id-collision to be safe. This currently fails with default
    // (unset) env vars, proving the replay is exploitable under default config.
    assert_ne!(
        NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS,
        TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS,
        "Nightly and TestNetworkWithForks method-id upgrade council keys are identical \
         while their chain_ids also collide -> method-id upgrade replay across networks is possible"
    );
}
```
Running this test with no `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_*` env vars set (the default CI/build condition) is expected to fail on the `assert_ne!`, confirming the identical-key-material precondition the question's severity gating depends on. A full end-to-end reproduction additionally requires building two guest ELFs with `CITREA_NETWORK=nightly` and `CITREA_NETWORK=testnetworkwithforks` respectively, feeding one's validly-signed `BatchProofMethodId` DA blob to the other's `run_circuit`, and observing `verify_method_id_security_council` return `true`; this end-to-end part could not be executed in this environment, so actual production key divergence at deploy time remains unverified.
