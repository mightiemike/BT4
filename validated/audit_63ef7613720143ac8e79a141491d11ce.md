### Title
`DeleteAccountAction` does not validate that `beneficiary_id` is a reachable/existing account, permanently burning the deleted account's balance - (File: `runtime/runtime/src/actions.rs`)

### Summary
The Sherlock finding describes `Vault.transferOwnership` accepting an unchecked destination address, so a caller can point a critical, irreversible operation at an address that can never receive/use it, rendering funds/permissions permanently unusable. The analogous nearcore path is `DeleteAccountAction`, whose `beneficiary_id` field is only syntax-checked, never existence/reachability-checked, before the runtime irreversibly deletes the account and dispatches its balance to that address.

### Finding Description
`validate_delete_action` only verifies that `beneficiary_id` is a syntactically valid `AccountId`; it never checks that the account exists or is capable of receiving a refund: [1](#0-0) 

`action_delete_account` then unconditionally deletes the account and creates a balance-refund receipt to whatever `beneficiary_id` was supplied, with no existence check: [2](#0-1) 

When that refund receipt is later processed, `check_account_existence` explicitly forbids **any** implicit/deterministic/universal account type from being implicitly created by a refund receipt (`is_refund: true` always returns `false` from `implicit_creation_allowed`): [3](#0-2) [4](#0-3) 

If the refund's target account does not exist (a typo'd name, a never-created implicit/deterministic id, or any other account that is absent at execution time), the `Transfer` action in the refund receipt fails with `AccountDoesNotExist`, and the runtime's refund-failure path burns the deposit outright rather than returning it anywhere: [5](#0-4) 

This is confirmed by an existing unit test showing exactly this outcome — a refund to a non-existent id fails with `AccountDoesNotExist` and the account is never created, i.e. the value is lost rather than delivered: [6](#0-5) 

The runtime's own documentation even acknowledges the sharp edge without treating it as an error to reject at validation time — "The beneficiary has to exist, otherwise the balance transfer the delete sends it would come straight back as a refund" — but this is only handled ad hoc in individual test setups, not enforced by the protocol: [7](#0-6) 

### Impact Explanation
This mirrors the "transferOwnership does not check zero address" bug class: a single unprivileged, self-authorized action (`DeleteAccountAction`, submittable by any signer via a standard transaction) accepts an unchecked destination for an irreversible transfer of the account's entire remaining balance. If the caller supplies (accidentally or via a compromised/buggy client, e.g. any tool constructing `beneficiary_id` programmatically, as seen in `tools/mirror`) a `beneficiary_id` that does not exist and cannot be implicitly created by a refund (any implicit/ETH-implicit/deterministic/universal account not yet instantiated, or a plain typo'd named account), the account's whole balance is irrecoverably burnt instead of transferred. This is a concrete, protocol-level, transaction-triggered permanent loss of funds — not a low-severity or cosmetic issue — matching the "permanently frozen/lost funds" acceptance criterion.

### Likelihood Explanation
Likelihood is realistic: `DeleteAccountAction` is a normal, commonly-used action reachable by any account holder deleting their own account, and `beneficiary_id` is fully attacker/user-controlled input with no protocol-level existence check at validation or execution time. Off-by-one typos in account names, stale/rotated relayer or tooling configuration (e.g., automated account-cleanup scripts), or targeting an implicit account id that was never funded are all realistic ways to trigger this without any special privilege.

### Recommendation
Add an existence (and refund-eligibility) check for `beneficiary_id` either at action validation time (reject `DeleteAccountAction` whose beneficiary cannot be resolved/created) or make the runtime refuse to burn on refund failure for delete-account payouts — e.g., require the beneficiary account to already exist, or explicitly disallow deleting an account when `beneficiary_id` is unreachable, analogous to requiring `_newOwner != address(0)` in the original report.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance.
2. Submit `DeleteAccountAction { beneficiary_id: "nonexistent.near" }` (or any implicit/deterministic account id that has never been created) signed by `alice.near`.
3. `validate_delete_action` accepts the action because `nonexistent.near`/the implicit id is syntactically valid (`runtime/runtime/src/action_validation.rs:447-451`).
4. `action_delete_account` deletes `alice.near` and queues `Receipt::new_balance_refund(beneficiary_id, account_balance)` (`runtime/runtime/src/actions.rs:380-386`).
5. When the refund receipt executes, `check_account_existence` rejects the `Transfer` because the beneficiary account does not exist and is not an eligible implicit-creation refund target (`runtime/runtime/src/actions.rs:842-850`, `2590-2597`).
6. The refund fails, and per `runtime/runtime/src/lib.rs:1047-1054` the entire deposit (the deleted account's whole former balance) is added to `other_burnt_amount` — permanently destroyed, matching the behavior already asserted by the existing test `refund_may_not_create_universal_account` (`runtime/runtime/src/tests/apply.rs:6880-6926`).

    /// The other half of the old gate, untouched by the relaxation: refunds are
    /// free, so they must not create an account, a `0u` one included.
    #[test]
    fn refund_may_not_create_universal_account() {
        init_test_logger();
        let key = SecretKey::from_seed(KeyType::ED25519, "refund-target").public_key();
        let account_id = derive_universal_account_id(&state_init_for(&[key]).to_raw());
        let (runtime, tries, root, apply_state, _signers, epoch) = setup_runtime(
            vec![alice_account()],
            Balance::from_near(100),
            Balance::ZERO,
            Gas::from_teragas(1000),
        );

        let result = runtime
            .apply(
                tries.get_trie_for_shard(ShardUId::single_shard(), root),
                &None,
                &apply_state,
                from_ref(&Receipt::new_balance_refund(&account_id, funding())),
                SignedValidPeriodTransactions::empty(),
                &epoch,
                Default::default(),
            )
            .unwrap();
        let mut store_update = tries.store_update();
        let new_root =
            tries.apply_all(&result.trie_changes, ShardUId::single_shard(), &mut store_update);
        store_update.commit();

        // Assert on the reason, not just the absence: without this the test would
        // also pass if the refund receipt were dropped instead of refused.
        let [outcome] = &result.outcomes[..] else {
            panic!("the refund receipt must produce exactly one outcome, got {:?}", result.outcomes)
        };
        assert_matches!(
            &outcome.outcome.status,
            ExecutionStatus::Failure(TxExecutionError::ActionError(err))
                if matches!(err.kind, ActionErrorKind::AccountDoesNotExist { .. }),
            "a refund to a missing `0u` id must fail with AccountDoesNotExist",
        );
        let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
        assert!(
            get_account(&state, &account_id).unwrap().is_none(),
            "a refund must not bring a `0u` account into existence",
        );
    }
