This is a genuine indexer state-integrity bug in the V2→V1 event translation path, reachable by any unprivileged user's token transactions and manifesting deterministically during indexer catch-up/backfill (which is the normal cold-start path for every fullnode).

### Title
Event V2→V1 translator derives sequence numbers from the chain-head state instead of the emitting transaction's version, corrupting indexed `ContractEventV1` sequence numbers - (`storage/indexer/src/event_v2_translator.rs`)

### Summary
`EventV2TranslationEngine::get_state_value_bytes_for_resource` (and its object-group counterpart) always reads the `TokenStore`/`CoinStore`/etc. resource via `main_db_reader.latest_state_checkpoint_view()` — i.e., the *current chain-head* state — regardless of which historical transaction version is actually being translated. [1](#0-0) 

The `TokenWithdrawTranslator` (and the analogous `TokenDeposit`/`Burn`/`MutatePropertyMap`/`Offer` translators) uses this resource's event-handle counter as the `default` sequence number the very first time a given `EventKey` is encountered: [2](#0-1) 

```
pub fn get_next_sequence_number(&self, event_key: &EventKey, default: u64) -> Result<u64> {
    if let Some(seq) = self.get_cached_sequence_number(event_key) {
        Ok(seq + 1)
    } else {
        let seq = self.internal_indexer_db.get::<EventSequenceNumberSchema>(event_key)?
            .map_or(default, |seq| seq + 1);
        Ok(seq)
    }
}
``` [3](#0-2) 

### Finding Description
The bootstrap `default` is only correct if the resource state being read reflects the state exactly as of the transaction that emitted the event (i.e., the handle's counter immediately after that specific withdraw). Instead, `latest_state_checkpoint_view()` returns the DB's *current* checkpoint — which, during the `DBIndexer`'s normal tail-following operation, is the main DB's synced head, not the version being iterated.

`DBIndexer::process`/`process_a_batch` iterates historical transactions/events/write-sets from `start_version` up to `end_version` (which can span the entire backlog on node bootstrap, resync, or catch-up after downtime), while for every V2 event it calls `translate_event_v2_to_v1`, which in turn reads the resource via the *always-latest* state view: [4](#0-3) [5](#0-4) 

Because the same event handle's counter keeps incrementing with every subsequent withdrawal made by the account before the indexer catches up, the very first time a given `withdraw_events` `EventKey` is translated (no in-memory cache entry, no persisted `EventSequenceNumberSchema` entry), the code binds `sequence_number = default`, where `default` is the resource's *final* counter value as of the chain head — not the counter value as of the emitting transaction's version. All subsequent occurrences of the same key simply increment this wrong baseline (`cached + 1`), so the error propagates deterministically through the entire historical sequence for that account/token.

This directly violates the required "authenticated API/state-view output bound to the correct version" invariant: the persisted `TranslatedV1EventSchema`, `EventByKeySchema`, and `EventByVersionSchema` records — which are the sole basis for the JSON REST API's legacy V1 event queries — are permanently populated with sequence numbers that do not correspond to the true historical ledger state at the time each event was emitted. [6](#0-5) 

### Impact Explanation
Any unprivileged account performing standard `0x3::token` withdraw/deposit/burn/etc. operations is affected once its event-handle key is first observed by the indexer while the indexer is behind the chain head (the default cold-start condition for every node, and also true after any indexer restart following the loss of its in-memory cache combined with catch-up beyond a single transaction). The resulting persisted index entries carry incorrect sequence numbers that permanently diverge from the true, contiguous 0-based V1 event numbering, corrupting durable secondary-index state and misleading any authenticated API consumer relying on `EventKey`+`sequence_number` semantics (e.g., "find event N for this account", pagination by sequence number, or any client cross-checking event counts against historical resource state).

### Likelihood Explanation
High. This does not require any special timing or race — it occurs deterministically any time the internal indexer processes a historical batch of transactions for an account that has more than one withdraw/deposit/etc. event by the time the batch is processed, which is guaranteed during the initial indexer bootstrap of every full node (processing from version 0 up to the current head) and after any extended indexer downtime/catch-up.

### Recommendation
`EventV2TranslationEngine::get_state_value_bytes_for_resource`/`get_state_value_bytes_for_object_group_resource` should read the resource at the specific version being translated (e.g., via `DbStateViewAtVersion`/`state_view_at_version(Some(version))`, or by using the write-set/state associated with that transaction) instead of `latest_state_checkpoint_view()`, so the event-handle counter used as the bootstrap default reflects the ledger state as of the emitting transaction, not the chain head. [7](#0-6) 

### Proof of Concept
1. Fresh-bootstrap (or restart) an internal indexer with `enable_event_v2_translation` on a chain history where account `A` has already performed two sequential `TokenWithdraw` events at versions `V1 < V2` within the backlog to be processed.
2. Let `DBIndexer::process` iterate `[V1, V2+1)` in one pass (normal batch behavior). When translating the withdraw event at `V1`, `TokenWithdrawTranslator` calls `engine.get_state_value_bytes_for_resource` which reads the `TokenStore` resource via `latest_state_checkpoint_view()` — by this point the resource already reflects the withdrawal at `V2` too, so `withdraw_events().count()` equals the count *after* both withdrawals, e.g. `2`, instead of `0` (the correct sequence number for the first-ever withdraw event).
3. Compare the `sequence_number` stored in `TranslatedV1EventSchema`/`EventByKeySchema` for the `V1` event against the value that would be obtained by reading the `TokenStore` resource's counter at the state checkpoint of version `V1` specifically — they differ, confirming the sequence number is bound to a state snapshot inconsistent with the event's actual emitting version.

```markdown
### Event V2→V1 translation (`event_v2_translator.rs`)

Module events (`ContractEventV2`) carry no event key or sequence number, but old API queries are keyed on them. `EventV2TranslationEngine` holds a registry of per-`TypeTag` `EventV2Translator` impls (coin deposit/withdraw, token/collection events, etc.). Each translator reconstructs the V1 `EventKey` and sequence number by reading the corresponding on-chain resource's event handle from the main DB's latest state checkpoint view, then the result is stored in `TranslatedV1EventSchema` and mirrored into the event-by-key/version indices.

- Sequence numbers are tracked in an in-memory `DashMap` cache backed by `EventSequenceNumberSchema`; `get_next_sequence_number` falls back to the on-chain handle count.
- Translation failure is non-fatal: the event is skipped (`Ok(None)`) with a warning. "Resource not found" for Mint/Burn is expected and silently ignored (ConcurrentSupply collections have no V1-style supply resource).
