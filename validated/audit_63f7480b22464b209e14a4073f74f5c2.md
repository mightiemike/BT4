### Title
Precision loss in standby-witness / voter reward distribution due to divide-then-multiply (rate) truncation causes systemic reward underpayment - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
The reported esMETA bug is a classic "compute a rate via division, then multiply back" precision-loss pattern (`unstakeRate = amount / timeToExit`, later `unstakeRate * elapsed`), which systematically shortchanges users because the rate is rounded down before it is ever multiplied. The same architectural pattern exists in java-tron's standby-witness reward payout and legacy voter reward computation, where a per-unit reward rate is first computed by division and then multiplied per recipient, causing rounding dust to be silently lost instead of paid out.

### Finding Description
In `MortgageService.payStandbyWitness()` [1](#0-0) , a single "rate" (`eachVotePay`) is computed once via division of `totalPay` by `voteSum`, and then this pre-rounded/pre-truncated rate is multiplied by each witness's vote count and cast down to a `long`:
```
double eachVotePay = (double) totalPay / voteSum;
long pay = (long) (w.getVoteCount() * eachVotePay);
```
Because `eachVotePay` is a `double` computed once and then reused for every standby witness, the sum of all `pay` values distributed is generally less than `totalPay` — the loop never verifies or redistributes the residual "dust" left in the reward pool. This is structurally identical to the reported bug: an amount/time (here amount/voteSum) ratio computed once, then multiplied per unit, with each multiplication independently truncated.

The same divide-then-multiply-then-truncate pattern recurs in the legacy voter reward path `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` [2](#0-1) :
```
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```
and in `IncentiveManager.reward()` [3](#0-2) :
```
long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay / voteSum));
```
`payStandbyWitness()` is invoked unconditionally from `Manager.payReward()` on every produced block when `allowChangeDelegation()` is enabled (the current mainnet reward model) [4](#0-3) , making this an actively executed, unprivileged (block-production-triggered) accounting path, not a dormant legacy branch.

### Impact Explanation
Each block, the sum of rewards actually credited to standby witnesses is less than the intended `witness127PayPerBlock` budget, and the shortfall is not tracked or redistributed — it is permanently lost from circulation relative to the intended reward schedule. Because this runs on every single block, the aggregate discrepancy accumulates over the life of the chain, similar to how the esMETA report describes accumulated imbalance between META and esMETA from per-unstake rounding. It is a resource/reward accounting correctness issue rather than a fund-theft primitive, so severity is bounded, but it represents a genuine and continuous violation of the intended reward-distribution invariant.

### Likelihood Explanation
High and deterministic: the code path executes on every block via normal, unprivileged block production/reward payout (`Manager.payReward` → `MortgageService.payStandbyWitness`), and `totalPay`/`voteSum` will essentially never divide evenly, so the loss occurs virtually every time this function runs.

### Recommendation
Avoid pre-computing an independently-rounded per-unit rate that is reused across multiple recipients. Instead:
- Compute each recipient's pay with multiply-before-divide semantics using integer/BigInteger math: `pay = voteCount * totalPay / voteSum` (single division at the end, not a separately rounded intermediate rate), matching the spirit of the report's fix (scale up before dividing, and divide back only once at the very end).
- Track and redistribute (or explicitly log/burn in a controlled, accounted way) any residual dust so `sum(pay) == totalPay` is preserved, similarly to how `DelegationStore`/`RewardViCalService` already use `BigInteger` and `DECIMAL_OF_VI_REWARD` scaling for the "new" reward algorithm [5](#0-4) .
- Apply the same fix to `MortgageService.computeReward(cycle, votes)` and `IncentiveManager.reward()`, which exhibit the identical `double`-rate-then-multiply truncation pattern.

### Proof of Concept
Given `totalPay = 10` and three standby witnesses each with `voteCount = 1` (`voteSum = 3`):
```
eachVotePay = 10.0 / 3 = 3.3333333333333335
pay (per witness) = (long)(1 * 3.3333333333333335) = 3
total distributed = 3 * 3 = 9
```
`1` unit (10% of the block's standby reward budget) is never distributed to any account and is lost every time this ratio doesn't divide evenly — which is the common case on a live network with constantly changing vote totals — directly mirroring the esMETA report's "users will always get less amount than expected... errors accumulated" scenario.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
