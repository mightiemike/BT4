Based on my investigation, this VRF listener logic contains an analog of the reported bug class: individual per-item balance checks against a shared balance figure without decrementing that figure as items are approved within the same processing pass.

### Title
Insufficient Balance Check Allows Over-Committing VRF Subscription Funds Across a Batch of Fulfillments - (File: core/services/vrf/v2/listener_v2_log_processor.go)

### Summary
`processRequestsPerSubHelper` in `core/services/vrf/v2/listener_v2_log_processor.go` iterates over a subscription's ready VRF requests (in chunks) and, for each pending fulfillment, checks whether `startBalanceNoReserved` covers that single request's cost before enqueueing a fulfillment transaction. [1](#0-0) [2](#0-1) 

### Finding Description
The function's own doc comment states that `startBalanceNoReserved` represents "the balance of the subscription minus any pending requests that have already been processed and not yet fulfilled onchain" — i.e., it is meant to reflect funds remaining after reservations. [3](#0-2) 

However, within the inner loop over `pipelines` (one iteration per ready VRF request in the current chunk), the code twice compares `startBalanceNoReserved` against a single request's cost (`p.fundsNeeded` at line 765, `p.maxFee` at line 786) and, if sufficient, proceeds to enqueue a fulfillment transaction via `TxManager().CreateTransaction`. [4](#0-3) 

Critically, there is no visible decrement/subtraction of `startBalanceNoReserved` after a request passes this check and is enqueued for fulfillment within the loop — the same balance value is reused for every subsequent request in the chunk (and across chunks, since `startBalanceNoReserved` is a shared `*big.Int` pointer parameter). This mirrors the reported `validateMetaTxList` flaw: checking each item's cost individually against total available balance without accounting for the cumulative cost of items already approved in the same pass. As a result, if a subscription has just enough balance for one large fulfillment but a chunk contains several ready requests whose costs each individually fit under the current balance, all of them can pass the check and get enqueued as pending transactions even though the subscription cannot actually fund all of them combined.

### Impact Explanation
This can cause the node to enqueue multiple VRF fulfillment transactions for a subscription that only has funds for one (or some) of them. When these are eventually broadcast/mined, only the transactions that still succeed on-chain (subject to the coordinator's own balance check) will complete; the rest will revert or be retried, consuming node resources (gas estimation, pipeline runs, DB writes, retries) and delaying processing of legitimately fulfillable requests — a resource-exhaustion / DoS-style condition on the VRF node's request-processing pipeline, analogous to the original txpool sponsorship DoS where an attacker fills the pool with only-partially-fundable transactions.

### Likelihood Explanation
Requires a subscription owner (or an attacker funding a subscription just above a single request's threshold) to submit multiple VRF requests in the same processing window/chunk so they are evaluated together before any of them is confirmed on-chain and the subscription balance is refreshed. This is a normal usage pattern (multiple requests to a subscription in short succession) rather than requiring privileged access, making it reachable by any unprivileged consumer contract calling `requestRandomWords` multiple times against a thinly-funded subscription.

### Recommendation
Track a running/local copy of the remaining balance as fulfillments are approved within `processRequestsPerSubHelper` (and across the chunk loop), decrementing it by each accepted request's `maxFee`/`fundsNeeded` immediately after the request is queued for fulfillment, rather than repeatedly comparing against the same starting balance snapshot for every request in the batch.
