### Title
Missing `TokenConfig.Enabled` check on the inbound deposit path allows minting PRC20 for a disabled/de-listed token — ([File: x/uexecutor/keeper/handler.go])

### Summary
`x/uregistry` defines a `TokenConfig.Enabled` field intended to gate whether a registered token is currently allowed for minting/bridging (`bool enabled = 6; // Whether this token is enabled for minting/bridging` — [1](#0-0) ). However, in the entire inbound-fund execution path in `x/uexecutor`, every lookup of a `TokenConfig` (`GetTokenConfig` / `GetTokenConfigByPRC20`) only checks that the config *exists* and that `NativeRepresentation` is non-nil — mirroring the exact anti-pattern flagged in the Gearbox report (checking existence of a mapping entry instead of validating the value that actually gates the operation). The `Enabled` flag is never read or enforced anywhere in `x/uexecutor` [2](#0-1) .

### Finding Description
`depositPRC20`, the function that actually credits PRC20 balance for an inbound deposit, resolves the token configuration and only validates presence of `NativeRepresentation`:

```go
tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
if err != nil {
    return nil, err
}
if tokenConfig.NativeRepresentation == nil {
    return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
}
``` [3](#0-2) 

This is the sole gate before `CallPRC20Deposit` mints/credits the PRC20 to the recipient. There is no check of `tokenConfig.Enabled`.

The gating logic that Push Chain does enforce before processing an inbound is `ChainConfig.Enabled.IsInboundEnabled` (a *chain-level* flag), checked in `VoteInbound`:
```go
enabled, err := k.uregistryKeeper.IsChainInboundEnabled(ctx, inbound.SourceChain)
...
if !enabled {
    return fmt.Errorf("inbound is disabled for chain %s", inbound.SourceChain)
}
``` [4](#0-3) 

That check only covers the chain as a whole; it says nothing about whether an individual *token* on that chain has been disabled. Grepping the entire `x/uexecutor` package for any reference to `TokenConfig.Enabled` (as opposed to `ChainConfig.Enabled`) returns zero hits — the flag is set at registration time via `MsgAddTokenConfig`/`MsgUpdateTokenConfig` but is dead weight everywhere execution actually happens (`create_outbound.go`, `build_revert_outbound.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`, `handler.go` — all of which call `GetTokenConfig`/`GetTokenConfigByPRC20` but only check for existence/`NativeRepresentation`, never `Enabled`).

`ValidateForExecution` (`x/uexecutor/types/inbound.go`) — the function that gates whether an inbound is even processed — likewise checks only that `AssetAddr` is non-empty; it does not resolve the `TokenConfig` at all, so a de-listed token's `Enabled=false` state never surfaces as a rejection reason [5](#0-4) .

Consequence: if an admin ever "disables" a token (sets `Enabled=false`, e.g. in response to a hack, a delisting, a liquidity-cap breach, or any other governance decision) without also fully removing the `TokenConfig`/`NativeRepresentation`, unprivileged users can still submit inbound deposits for that asset from the source chain and have honest validators vote them through — the ballot, `ValidateForExecution`, and `depositPRC20` all succeed because none of them consult `Enabled`.

### Impact Explanation
This breaks the token-registry invariant that `Enabled=false` prevents minting/bridging of a token. An unprivileged attacker (or any ordinary user with legitimate on-chain funds of the disabled token) can force honest validators to mint PRC20 for a token the protocol has explicitly deauthorized, resulting in unauthorized mint of PRC20/native asset representation and corruption of the token-registry accounting invariant that `Enabled` gates issuance. This falls squarely within the "Registry and accounting path" and "unauthorized mint" impact categories in scope, is triggerable purely from a default user-deposit flow, and requires no privileged or malicious-validator assumption — only that an admin action ("disable this token") is not being enforced.

### Likelihood Explanation
Likelihood depends on operational practice: this is exploitable only in the window where an admin has set `Enabled=false` on a `TokenConfig` but has not (or cannot, since there is no dedicated pause-mint-only primitive) fully removed the config/`NativeRepresentation`. Given `MsgRemoveTokenConfig` exists as a separate, heavier operation (and `Enabled` is documented as the intended lighter-weight "pause minting/bridging" lever), it is reasonable to expect operators will use `Enabled=false` as the primary disable mechanism, making this a realistic, not merely theoretical, gap. It requires no adversarial validator collusion — any user depositing funds for the disabled asset after the admin toggles the flag will trigger it.

### Recommendation
Enforce `TokenConfig.Enabled` at the same point `ChainConfig.Enabled.IsInboundEnabled` is checked (or immediately in `depositPRC20`/`ValidateForExecution`), rejecting inbound processing (with the existing failed-PCTx + revert-outbound machinery) when the resolved `TokenConfig.Enabled` is `false`, analogous to the existing chain-level enable/disable gate:
```go
tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
if err != nil {
    return nil, err
}
if !tokenConfig.Enabled {
    return nil, fmt.Errorf("token %s on chain %s is disabled", assetAddr, sourceChain)
}
if tokenConfig.NativeRepresentation == nil {
    return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
}
```
Apply the same check consistently everywhere `GetTokenConfig`/`GetTokenConfigByPRC20` is used to gate a mint/deposit/rescue/refund path (`create_outbound.go`, `build_revert_outbound.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`).

### Proof of Concept
1. Admin registers `TokenConfig{Chain: "eip155:11155111", Address: "0xUSDC...", Enabled: true, NativeRepresentation: {ContractAddress: prc20USDC}}` via `MsgAddTokenConfig`.
2. Later, admin sets `Enabled: false` via `MsgUpdateTokenConfig` (e.g., to pause the asset), while leaving `NativeRepresentation` intact (the natural, lower-blast-radius action compared to fully removing the config).
3. An ordinary unprivileged user deposits the underlying token into the source-chain gateway as normal (see the test pattern in `test/integration/uexecutor/inbound_zero_amount_test.go` for the vote/finalize flow).
4. Honest validators vote via `VoteInbound` → `IsChainInboundEnabled` passes (chain still enabled) → `ValidateForExecution` passes (doesn't check token `Enabled`) → `ExecuteInboundFunds` → `depositPRC20` passes (only checks `NativeRepresentation != nil`) → PRC20 is minted to the recipient despite the token being administratively disabled [6](#0-5) [3](#0-2) .
