## Title
Secondary-index full-set materialization in `SecondaryIndex::get`/`get_index_key_pubkeys` allows disproportionate CPU/memory cost from a single indexed `getProgramAccounts`-style RPC call - (File: `accounts-db/src/accounts_index/secondary.rs`, `accounts-db/src/accounts_index.rs`, `accounts-db/src/accounts_db.rs`)

### Summary
The reported GovNFT bug is a class of "unbounded registry getter" issue: a single-call accessor that materializes an ever-growing collection in one shot, with no pagination, so it degrades/fails as the underlying set grows. Agave's account secondary index (`SplTokenMint`, `SplTokenOwner`, `ProgramId`) has the same shape: a single query key can map to an unbounded (and attacker/user-influenced) number of inner pubkeys, and the accessor used to serve indexed scans collects *all* of them into a `Vec` up front, with no limit applied until after the (potentially huge) collection and subsequent per-account loads have already happened.

### Finding Description
`SecondaryIndex::get` returns every pubkey registered under a key by cloning the entire in-memory `HashSet` into a `Vec`, unconditionally: [1](#0-0) 

This is invoked, without any size cap, by `AccountsIndex::get_index_key_pubkeys`: [2](#0-1) 

`AccountsDb::index_scan_accounts` calls it to obtain the complete pubkey list *before* iterating and loading each account: [3](#0-2) 

The only mitigation is a `byte_limit_for_scan` check applied *inside* the per-account callback in `Accounts::load_by_index_key_with_filter`, which aborts the scan only after accumulated result bytes exceed the configured limit: [4](#0-3) 

This is reachable from a single, ordinary RPC call. `JsonRpcRequestProcessor::get_filtered_indexed_accounts` (used by `getTokenAccountsByOwner`/`getTokenAccountsByMint`/`getProgramAccounts` when secondary indexes are enabled) forwards straight through to `Bank::get_filtered_indexed_accounts` → `Accounts::load_by_index_key_with_filter` → `AccountsDb::index_scan_accounts`: [5](#0-4) [6](#0-5) 

Because the config abort flag (`ScanConfig`) is only checked/set by the *result-size* accumulator, not before the initial key-set materialization, a hot inner key (e.g., a widely-used SPL token mint, a heavily-used token-owner such as an exchange wallet, or a very popular program id like the SPL Token program itself) forces the validator to:
1. Clone an entire `HashSet<Pubkey>` of unbounded size into a fresh `Vec` (`SecondaryIndex::get`), and
2. Call `do_load` (a full account load from storage/cache) for every one of those pubkeys, one at a time, before the byte-limit abort can even trigger, since the abort is only evaluated for elements that pass the caller-supplied filter and get accumulated.

If the filter passed by the RPC layer (e.g., token-account-state + mint-offset memcmp) matches many/most entries, the byte-limit abort may trigger relatively early; but if the caller's filter is permissive or rejects most accounts (so nothing accumulates against the byte limit), the loop in `index_scan_accounts` will walk the *entire* unbounded pubkey set with no early exit, since `config.is_aborted()` is never set. This mirrors the GovNFT registry getter bug exactly: an internal, ever-growing set with a single, non-paginated accessor that a caller cannot iterate incrementally.

### Impact Explanation
A single RPC call against a secondary-indexed key with a large and growing inner-key set (a realistic condition for popular SPL Token mints/owners or program ids on mainnet) causes the node to allocate and clone an unbounded `Vec<Pubkey>` and then perform an unbounded number of `do_load` account fetches in one synchronous scan, causing disproportionate CPU and memory cost on the responding validator/RPC node relative to the cost of issuing the request. This matches the "disproportionate storage and CPU cost" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires the operator to have enabled `--account-index spl-token-owner|spl-token-mint|program-id`, and requires a query key whose associated inner-key set has grown large (a very plausible steady-state condition, not a crafted edge case) combined with a filter that does not quickly hit `scan_results_limit_bytes`. No malicious snapshot or multiple-client coordination is required, and it is a single-call trigger, so it falls inside scope as a legitimate indexed-getProgramAccounts DoS (excluded only is the *unfiltered*, non-indexed variant).

### Recommendation
Bound `SecondaryIndex::get`/`get_index_key_pubkeys` themselves (not just the post-load result size), e.g., by supporting a cursor/offset-based iteration analogous to `AccountsIndexPubkeyIterator`, or by checking `ScanConfig::is_aborted()`/an item-count cap while collecting keys rather than after loading each account. At minimum, apply a configurable maximum on the number of inner keys returned by `SecondaryIndex::get` (or stream them via an iterator) so a single query cannot force materialization and per-account loading of an unbounded, ever-growing set.

### Proof of Concept
1. Start a validator/RPC node with `--account-index spl-token-owner` (or `spl-token-mint`/`program-id`).
2. Populate (or wait for organic growth of) a very large number of SPL token accounts under one owner/mint key, or use the built-in program-id index which is populated for every account whose owner is indexed.
3. Issue a single `getTokenAccountsByOwner` (or equivalent) RPC call for that hot key with a filter/encoding combination unlikely to accumulate quickly against `scan_results_limit_bytes` (e.g., request only accounts matching a rare `dataSlice`/`memcmp` condition that most stored accounts fail).
4. Observe that `AccountsDb::index_scan_accounts` (`accounts-db/src/accounts_db.rs:3358`) must first materialize the full `Vec<Pubkey>` from `SecondaryIndex::get` (`accounts-db/src/accounts_index/secondary.rs:252`) and then perform `do_load` for every entry in that vector before the scan can complete, since `config.is_aborted()` is never set by a non-accumulating filter.

        &self,

        bank_id: BankId,
        index_key: &IndexKey,
        filter: F,
        byte_limit_for_scan: Option<usize>,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let sum = AtomicUsize::default();
        let config = ScanConfig::default().recreate_with_abort();
        let mut collector = Vec::new();
        let result = self
            .accounts_db
            .index_scan_accounts(
                ancestors,
                bank_id,
                *index_key,
                |some_account_tuple| {
                    Self::load_while_filtering(&mut collector, some_account_tuple, |account| {
                        let use_account = filter(account);
                        if use_account
                            && Self::accumulate_and_check_scan_result_size(
                                &sum,
                                account,
                                &byte_limit_for_scan,
                            )
                        {
                            // total size of results exceeds size limit, so abort scan
                            config.abort();
                        }
                        use_account
                    });
                },
                &config,
            )
            .map(|_| collector);
        Self::maybe_abort_scan(result, &config)
    }

    pub async fn get_filtered_indexed_accounts(
        &self,
        bank: &Arc<Bank>,
        index_key: &IndexKey,
        program_id: &Pubkey,
        filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(
                    &index_key,
                    |account| {
                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)
                            && filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                    },
                    byte_limit_for_scans,
                )
            })
            .await
            .expect("Failed to spawn blocking task")?;
        if sort_results {
            // Avoid copying pubkeys (using Ord::cmp(a, b) silences clippy::unnecessary_sort_by).
            accounts.sort_unstable_by(|(addr_a, _), (addr_b, _)| Ord::cmp(addr_a, addr_b));
        }
        Ok(accounts)
    }
