## Title
Replay-verify's transaction-info comparator silently ignores state-checkpoint root hashes, masking state divergence — (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness check used by db-tool's `replay_on_archive` (and other debugger/replay tooling) to validate that locally re-executed transactions match the authenticated `TransactionInfo` pulled from a backup/archive. The function verifies status, gas used, write-set hash, and event root hash, but explicitly skips comparing `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` — the fields that authenticate the JMT state root, hot-state root, and native-position tree root respectively. As a result, a local execution that diverges from the authenticated chain state (i.e., computes a different Merkle state root while still producing the same write set/events/gas/status) is reported by replay-verify as a successful, matching replay.

### Finding Description
`ensure_match_transaction_info` is defined at [1](#0-0)  and checks status, gas, write-set hash, and event root hash against the supplied `txn_info`. The trailing comment makes the gap explicit: [2](#0-1) , stating that the comparator ignores the checkpoint hashes so "replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution."

This function is the terminal verification step in `storage/db-tool/src/replay_on_archive.rs`'s `Verifier::execute_and_verify`, which re-executes transactions from a backup and calls it as the only pass/fail gate: [3](#0-2) . The `expected_txn_info` values fed in come directly from the backup/archive (the authenticated ledger data being verified), so this is precisely the code path responsible for detecting state-commitment divergence between a node's VM/storage stack and the historical, consensus-committed ledger.

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class fields [4](#0-3) , and these are populated by the executor when assembling transaction infos at commit time [5](#0-4) . These fields are exactly the state-commitment bindings that `state-integrity` checks are supposed to protect (state Merkle root, hot-state root, and the new native-position/trading state root gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`). Because `ensure_match_transaction_info` never re-derives or compares these hashes against what local execution computed, any bug (or malicious archive/state-view/replay-path bug) that causes local execution to land on a different state root — while write set, events, gas and status happen to match — passes verification silently.

### Impact Explanation
Replay-verify (`db-tool replay-on-archive`) and the aptos-debugger replay path exist specifically to catch state divergence, including hard-fork-only bugs where consensus data (write set/events/status) matches but the derived state root differs due to a state-application, restore, or replay bug. Because the comparator omits the checkpoint-hash fields, such divergence is invisible to the tool: it will report "replay successful" for versions where the actual committed state root (and thus the durable ledger state derived by that node) is wrong. This directly undermines the "authenticated API / state-view output bound to the wrong version, object, or proof context" and "hard-fork-only divergence during commit, replay, restore" integrity guarantees called out as in-scope impacts, since an operator relying on replay-verify to detect a state-corrupting bug (e.g., in JMT restore, position-tree computation, or state application) would get a false-positive "match" and miss a real ledger-state corruption.

### Likelihood Explanation
This is not a hypothetical: the code contains an explicit TODO acknowledging the exact gap and naming `db-tool`'s `replay_on_archive` as an affected consumer [2](#0-1) . The gap is unconditionally present today (not feature-gated), and becomes acutely relevant as `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` roll out, since those new state roots are precisely the values this comparator was supposed to authenticate but does not.

### Recommendation
Extend `ensure_match_transaction_info` to compare locally recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present in `txn_info`) against the corresponding values produced by local execution/state-checkpoint computation, and fail verification on mismatch — as already flagged by the code's own TODO before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is enabled in production.

### Proof of Concept
Not directly exploitable by an external attacker without a separate root-cause bug (e.g., in JMT restore or the native-position tree merge logic) that causes local state-root computation to diverge from the authenticated committed root while leaving write set/events/gas/status unchanged. Given such a divergence, `Verifier::execute_and_verify` in `storage/db-tool/src/replay_on_archive.rs` (lines 392–405) would call `ensure_match_transaction_info` and receive `Ok(())` despite the state roots differing, because the function never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` (`types/src/transaction/mod.rs`, lines 2139–2203).

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );
