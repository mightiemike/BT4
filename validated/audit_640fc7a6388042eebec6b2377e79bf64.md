### Title
Off-by-One Boundary in `DelegateAction` Expiry Allows 1-Block Window of Unauthorized Execution — (`File: runtime/runtime/src/actions.rs`)

### Summary

`apply_delegate_action` checks expiry with a strict `>` comparison, but the field description and the `Actions.md` specification both state the action should expire when `block_height >= max_block_height`. This creates a 1-block overlap where a `DelegateAction` the user believes has expired can still be executed by a relayer.

### Finding Description

`DelegateAction.max_block_height` is documented as:

> "The maximal height of the block in the blockchain **below which** the given DelegateAction is valid."

`docs/RuntimeSpec/Actions.md` states:

> "If the current block is **equal or greater than** `max_block_height`" → `DelegateActionExpired`

The runtime check in `apply_delegate_action` is:

```rust
if apply_state.block_height > delegate_action.max_block_height() {
    result.result = Err(ActionErrorKind::DelegateActionExpired.into());
    return Ok(());
}
``` [1](#0-0) 

The condition `block_height > max_block_height` means the action is **still valid** when `block_height == max_block_height`. The specification and field description both require expiry at `block_height >= max_block_height`.

The field definition: [2](#0-1) 

The spec documentation: [3](#0-2) 

### Impact Explanation

A user who signs a `DelegateAction` with `max_block_height = N` — following the documented semantics that the action is valid only for blocks **below** N — believes the action is expired at block N. A relayer who holds the signed action can submit it at exactly block N. The runtime accepts it because `N > N` is false. The action executes one block past the user's intended deadline.

If the `DelegateAction` contains a `Transfer`, `AddKey`, or any other fund-affecting action, this 1-block window allows a malicious relayer to execute an action the user believed was already expired, constituting an unauthorized transaction and potential fund loss or unauthorized key addition.

### Likelihood Explanation

Low-to-medium. The relayer must hold the signed `DelegateAction` and submit it at exactly the boundary block. This is a deliberate, targeted attack by a malicious relayer. However, the attack requires no privileged access beyond being the designated relayer, and the 1-block window is deterministic and predictable on NEAR's fixed-slot block schedule.

### Recommendation

Change the expiry check from strict greater-than to greater-than-or-equal, matching the documented semantics:

```rust
// Before
if apply_state.block_height > delegate_action.max_block_height() {

// After
if apply_state.block_height >= delegate_action.max_block_height() {
``` [4](#0-3) 

This aligns the code with the field description ("below which the action is valid") and the `Actions.md` specification ("equal or greater than `max_block_height`" triggers expiry).

### Proof of Concept

1. Alice signs a `DelegateAction` with `max_block_height = N` containing `Action::Transfer { deposit: 100 NEAR }` to Bob.
2. Alice submits it to relayer Carol.
3. At block `N-1`, Alice believes the action expires at block N (per documentation) and considers the delegation safe to let expire.
4. Carol (malicious relayer) waits until block N and submits the transaction.
5. The runtime evaluates `apply_state.block_height (N) > max_block_height (N)` → `false` → action is **not** expired.
6. The transfer executes at block N, one block past Alice's intended expiry.
7. Alice loses 100 NEAR to an execution she believed was no longer possible.

The existing test `test_delegate_action_max_height` confirms the off-by-one: it only tests `max_block_height + 1` as the failing case, leaving `max_block_height` itself untested as a boundary: [5](#0-4)
