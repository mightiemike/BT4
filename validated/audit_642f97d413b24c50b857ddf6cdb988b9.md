## Title
Guard Representative (genesis witness) block rewards become permanently unwithdrawable - (File: `actuator/src/main/java/org/tron/core/actuator/WithdrawBalanceActuator.java`)

### Summary
Genesis witnesses ("Guard Representatives", or "GR") can actively produce blocks and accrue witness/standby rewards just like any other Super Representative, since nothing in the reward-accrual path excludes them. However, both public reward-withdrawal entry points — the `WithdrawBalanceContract` actuator and the TVM `withdrawReward` native contract — unconditionally reject withdrawal requests from any address matching a genesis witness. This mirrors the reported Golom bug class: value is legitimately credited to an account/entity, but the payout mechanism categorically refuses to release it to that same entity, permanently trapping the funds in on-chain state with no recovery path.

### Finding Description
Block and standby-witness rewards are accrued for whichever address produced the block or is otherwise voted in, without excluding GR addresses: [1](#0-0) 

Reward accrual is booked into the account's `allowance` field via `MortgageService.payReward`/`adjustAllowance`, again with no GR exclusion: [2](#0-1) 

That GRs remain capable of holding vote weight and being active/paid witnesses unless a separate committee proposal explicitly zeroes their votes confirms rewards can legitimately accumulate for GR addresses under normal operation: [3](#0-2) 

Despite this, the only two ways to convert `allowance` into spendable `balance` both explicitly forbid GR addresses:

`WithdrawBalanceActuator.validate()`: [4](#0-3) 

`WithdrawRewardProcessor.validate()` (used by the TVM `WITHDRAWREWARD` opcode): [5](#0-4) 

There is no clawback, redirection to a treasury/blackhole address, or any other mechanism to reclaim the locked allowance — it simply remains in the `AccountCapsule.allowance` field forever, unreachable by any transaction path, exactly analogous to reward tokens becoming stuck once an NFT owner is set to `address(0)` and the OZ ERC20 transfer path refuses to send there.

### Impact Explanation
Any TRX value credited as `allowance` to a genesis witness address (block rewards, transaction-fee-pool rewards, or standby-witness rewards) is permanently locked and unspendable, since the actuator and native contract both hard-block the only withdrawal path for that specific address class. This is a concrete, provable accounting/state defect: funds are recorded as owed but the mechanism to realize them into spendable balance is categorically closed off, which is the same underlying bug pattern as the referenced report (a legitimate reward recipient whose payout path unconditionally reverts).

### Likelihood Explanation
Genesis witnesses retain their genesis vote weight by default (`tryRemoveThePowerOfTheGr` only strips it when a committee proposal explicitly enables `removeThePowerOfTheGr`), so under default/unconfigured conditions GR addresses can remain active witnesses, produce blocks, and accrue `allowance` indefinitely while being permanently barred from withdrawing it. No privileged or malicious action is required to trigger the lock — it is a natural consequence of normal block production and reward accrual under the existing validation logic.

### Recommendation
Either (a) prevent GR addresses from accruing `allowance` in the first place (skip `payReward`/`adjustAllowance` for GR addresses), or (b) if GR addresses are permitted to earn rewards, allow them to withdraw via a clawback/redirect path (e.g., transfer to the blackhole/treasury address instead of reverting) rather than unconditionally rejecting the withdrawal transaction. The current combination — reward accrual allowed, withdrawal categorically forbidden — should be resolved so accrued funds are never permanently unreachable.

### Proof of Concept
1. A genesis witness address (listed in `genesis.block.witnesses`, e.g. `GR1` in `config.conf`) retains sufficient vote weight to be selected as an active Super Representative (default config, `removeThePowerOfTheGr` not enabled).
2. It produces blocks; `Manager.payReward` → `MortgageService.payBlockReward`/`payStandbyWitness` credits `allowance` on its `AccountCapsule` over many cycles.
3. The GR address (or anyone) submits a `WithdrawBalanceContract` transaction, or the GR's associated smart contract calls TVM's `WITHDRAWREWARD` opcode.
4. `WithdrawBalanceActuator.validate()` / `WithdrawRewardProcessor.validate()` detects the address matches a genesis witness and throws `ContractValidateException("... is a guard representative and is not allowed to withdraw Balance")`, confirmed by the existing test `WithdrawBalanceActuatorTest.isGR()`: [6](#0-5) 
5. The accrued `allowance` remains on the account forever with no alternative path to convert it to spendable balance.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }

  @Test
  public void isGR() {
    Witness w = Args.getInstance().getGenesisBlock().getWitnesses().get(0);
    byte[] address = w.getAddress();
    AccountCapsule grCapsule = new AccountCapsule(ByteString.copyFromUtf8("gr"),
        ByteString.copyFrom(address), AccountType.Normal, initBalance);
    dbManager.getAccountStore().put(grCapsule.createDbKey(), grCapsule);
    long now = System.currentTimeMillis();
    dbManager.getDynamicPropertiesStore().saveLatestBlockHeaderTimestamp(now);

    try {
      dbManager.getMortgageService()
          .adjustAllowance(dbManager.getAccountStore(), address, allowance);
    } catch (BalanceInsufficientException e) {
      fail("BalanceInsufficientException");
    }
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(address);
    Assert.assertEquals(accountCapsule.getAllowance(), allowance);

    WitnessCapsule witnessCapsule = new WitnessCapsule(ByteString.copyFrom(address), 100,
        "http://google.com");

    dbManager.getAccountStore().put(address, accountCapsule);
    dbManager.getWitnessStore().put(address, witnessCapsule);

    WithdrawBalanceActuator actuator = new WithdrawBalanceActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager())
        .setAny(getContract(ByteArray.toHexString(address)));

    TransactionResultCapsule ret = new TransactionResultCapsule();
    Assert.assertTrue(dbManager.getWitnessStore().has(address));

    try {
      actuator.validate();
      actuator.execute(ret);
      fail("cannot run here.");

    } catch (ContractValidateException e) {
      String readableOwnerAddress = StringUtil.createReadableString(address);
      Assert.assertTrue(e instanceof ContractValidateException);
      Assert.assertEquals("Account[" + readableOwnerAddress
          + "] is a guard representative and is not allowed to withdraw Balance", e.getMessage());
    } catch (ContractExeException e) {
      Assert.assertFalse(e instanceof ContractExeException);
    }
  }
