## Title
Excess attached deposit is permanently retained (never refunded) by `AddressRegistrar::register()` - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
`AddressRegistrar::register()` is a `#[payable]` method that requires callers to attach enough deposit to cover the storage cost of the new `address -> account_id` mapping, but it only refunds the attached deposit in the "collision" (`Entry::Occupied`) branch. When registration succeeds (`Entry::Vacant`), any amount attached beyond the exact `required_deposit` is silently kept by the contract with no accounting, no partial refund, and no withdrawal mechanism — mirroring the reported Solidity bug class of a `payable` function that accepts value it has no way to return.

### Finding Description
`register()` computes the exact required deposit from the byte cost of storing the address/account mapping, and only checks that `given_deposit >= required_deposit`: [1](#0-0) 

On the success path (`Entry::Vacant`), the full `given_deposit` remains part of the contract's account balance — only the mapping insertion happens, with no logic to compute or refund `given_deposit - required_deposit`: [2](#0-1) 

By contrast, the collision path (`Entry::Occupied`) explicitly refunds the *entire* deposit via a `Transfer` promise back to the predecessor, showing the developers recognized the need to return unused deposits — but only implemented it for one of the two branches: [3](#0-2) 

There is no other method on `AddressRegistrar` (`lookup`, `get_address`) that can move balance out of the contract, and no owner/admin withdrawal function exists at all: [4](#0-3) 

Since NEAR does not auto-refund unused attached deposits for successful function calls (unlike unused *gas*, which the runtime refunds via `refund_unspent_gas_and_deposits`), any deposit accepted by a contract but not explicitly transferred back stays on that contract's balance forever unless the contract code deliberately returns it.

### Impact Explanation
Any unprivileged account calling `register()` with more than the exact required deposit (e.g., padding for safety margin, or miscalculating `account_id` byte length) permanently loses the excess NEAR into the `AddressRegistrar` contract's balance, with no code path to reclaim it. This is a direct, contract-triggered permanent loss of user funds reachable from a single `FunctionCall` transaction/receipt, matching the "permanently frozen funds" criterion.

### Likelihood Explanation
`register()` is a normal, expected entry point for the eth-implicit-account address registration flow used by the NEAR Wallet Contract ecosystem (`ADDRESS_REGISTRAR_ACCOUNT_ID` is referenced directly from `wallet-contract`), so it is called routinely by ordinary users/relayers. Any caller who attaches a deposit larger than the exact required storage cost — which is easy to do since the required amount depends on `account_id.len()` and must be computed off-chain — triggers the loss on every successful (non-colliding) registration.

### Recommendation
In the `Entry::Vacant` success branch of `register()`, compute `given_deposit.saturating_sub(required_deposit)` and, if non-zero, issue a `Transfer` promise refunding the excess to `env::predecessor_account_id()`, mirroring the refund logic already present in the `Entry::Occupied` branch.

### Proof of Concept
1. Call `AddressRegistrar::register("alice.near")` attaching a deposit of, e.g., `2 * required_deposit` yoctoNEAR (`required_deposit` computed as `storage_byte_cost * (20 + len(account_id))`).
2. The address is not previously registered, so the `Entry::Vacant` branch executes, inserting the mapping and returning the hex address.
3. Observe that the `AddressRegistrar` contract's account balance increased by the full `2 * required_deposit`, while only `required_deposit` was actually needed; the caller has no way to retrieve the extra `required_deposit` that was attached.

    /// Attempt to look up the account ID associated with the given address.
    /// If an entry for that address is found then the associated account id
    /// is returned, otherwise `None` is returned. Use the `register` method
    /// to add entries to the map.
    /// This function will panic if the given address is not the hex-encoding
    /// of a 20-byte array. The `0x` prefix is optional.
    pub fn lookup(&self, address: String) -> Option<AccountId> {
        let address = {
            let mut buf = [0u8; 20];
            hex::decode_to_slice(address.strip_prefix("0x").unwrap_or(&address), &mut buf)
                .unwrap_or_else(|_| env::panic_str("Invalid hex encoding"));
            buf
        };
        self.addresses.get(&address).cloned()
    }

    /// Computes the address associated with the given `account_id` and
    /// returns it as a hex-encoded string with `0x` prefix. This function
    /// does not update the mapping stored in this contract. If you want
    /// to register an account ID use the `register` method.
    pub fn get_address(&self, account_id: AccountId) -> String {
        let address = account_id_to_address(&account_id);
        format!("0x{}", hex::encode(address))
    }
}
