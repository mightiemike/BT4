## Analog Vulnerability Found

### Title
OAuth callback HMAC validation and access-token exchange parse the `shop` query parameter with inconsistent semantics, allowing HTTP Parameter Pollution to desynchronize the verified value from the value acted upon - (File: `packages/apps/shopify-api/lib/auth/oauth/oauth.ts`)

### Summary
The Vader report's root cause is that a security-critical value (which recipient gets the redeemed funds) is decoupled from the step that validated/authorized the operation, so an attacker can substitute their own value between the two steps. The `callback()` handler in `oauth.ts` has the same class of bug: the `shop` parameter used to compute/verify the request's HMAC signature is extracted differently from the `shop` parameter used to actually perform the privileged action (requesting an access token and minting a session), so a request with a duplicated `shop` query parameter can pass HMAC validation using one value while the app acts on a different, attacker-supplied value.

### Finding Description
In `callback()`: [1](#0-0) 
`shop` is taken via `query.get('shop')`, which returns the **first** occurrence of a repeated query parameter.

For HMAC validation, the query is instead flattened via: [2](#0-1) 
`Object.fromEntries(query.entries())` overwrites duplicate keys, keeping the **last** occurrence. This `authQuery` object is what actually gets HMAC-verified via `validQuery` → `validateHmac` → `generateLocalHmac` → `stringifyQueryForAdmin`, none of which reject repeated `shop`/`hmac`/`timestamp` parameters for the `admin` signator (that protection only exists for `signator: 'appProxy'`): [3](#0-2) 

Then, when actually requesting the access token, the code re-reads `query.get('shop')` (first occurrence again) to build `cleanShop`, which is used both as the OAuth token-exchange domain and as the `shop` stored on the resulting `Session`: [4](#0-3) 

So the value that is cryptographically checked (last `shop` occurrence) is not the same value that is used to exchange the code and build the session (first `shop` occurrence). This is a classic HTTP Parameter Pollution (HPP) split, the same underlying flaw as the Vader case: the "authorization" step and the "action" step read different, independently-controllable representations of the same identifier, so a caller can make the verification pass on a value they don't intend to act on, while the acted-upon value is a different one they choose.

### Impact Explanation
An attacker who legitimately completes OAuth for their own shop (getting a Shopify-issued, HMAC-valid callback URL for `shop=attacker.myshopify.com`) can freely edit that callback URL - it's just a browser GET request they control - and add a duplicate `shop` parameter before the legitimate one. `authQuery.shop` (last) still equals `attacker.myshopify.com`, so `validateHmac` still succeeds against the real Shopify-signed HMAC. But `cleanShop` (first occurrence) becomes an attacker-chosen shop domain of the attacker's choosing (subject only to `sanitizeShop`'s domain-format check). This causes the app to POST the app's `client_id`/`client_secret` and the attacker's authorization `code` to `https://{attacker-chosen-shop}/admin/oauth/access_token`, and, on any success, to persist a `Session` keyed to that attacker-chosen shop rather than the shop that was actually HMAC-verified. In practice the token exchange itself will fail against a shop that never issued that `code`, so full session hijacking via this exact path is bounded by that check; however, it still constitutes an HMAC-verification bypass on the trusted `shop` binding, discloses the app's `client_secret` to an arbitrary Shopify-domain-shaped endpoint the attacker controls, and represents a request-authentication logic flaw reachable from an anonymous/unprivileged actor (any user able to reach the app's public `/auth/callback`).

### Likelihood Explanation
High reachability: this is a public, unauthenticated HTTP endpoint (`shopify.auth.callback` / the app's OAuth callback route) that only requires crafting a URL with a duplicated `shop` query parameter - no MITM, no leaked secret, and no privileged role are required. The only constraint is that the attacker must complete a real OAuth authorize step for some shop they control to obtain a validly-signed `hmac`/`code`, which is trivial for any merchant/developer running the app on a test or otherwise-controlled store.

### Recommendation
Use a single, consistent parsing strategy for the entire callback: derive `shop` (and every other security-relevant field) from the same normalized/deduplicated query object that is HMAC-validated (`authQuery`), and reject requests containing repeated `shop`, `hmac`, `code`, `state`, or `timestamp` parameters for the `admin` signator, mirroring the protection already implemented for `appProxy` in `normalizeQuery`/`APP_PROXY_SINGLE_VALUE_PARAMS`. Concretely: extend the repeated-security-parameter rejection in `packages/apps/shopify-api/lib/utils/hmac-validator.ts` to the `admin` signator, and change `oauth.ts` to compute `shop`/`cleanShop` from `authQuery.shop` (post-validation, deduplicated) instead of a second, independent `query.get('shop')` call.

### Proof of Concept
1. Attacker installs the app normally on `attacker.myshopify.com`, obtaining a Shopify redirect to `GET /auth/callback?shop=attacker.myshopify.com&code=XYZ&timestamp=T&hmac=H&state=S` with a valid Shopify-issued `hmac=H`.
2. Attacker rewrites this URL before hitting the app server, inserting a duplicate `shop` param first: `GET /auth/callback?shop=other-valid-shop.myshopify.com&shop=attacker.myshopify.com&code=XYZ&timestamp=T&hmac=H&state=S`.
3. In `callback()`, `query.get('shop')` → `other-valid-shop.myshopify.com` (first), while `Object.fromEntries(query.entries())` → `authQuery.shop = attacker.myshopify.com` (last), matching the real `hmac` from step 1, so `validQuery` returns `true`.
4. The app calls `POST https://other-valid-shop.myshopify.com/admin/oauth/access_token` with the app's `client_secret` and the attacker's `code`, and would persist any resulting session under `other-valid-shop.myshopify.com` - demonstrating the verified identity and the acted-upon identity have been desynchronized via parameter pollution.

Note: I was not able to run this against a live instance to confirm the exact HTTP-level behavior of duplicate query parameters through every possible adapter/runtime (`abstractConvertRequest`), since that depends on the specific framework/runtime adapter in use; the core logic mismatch (`query.get()` vs `Object.fromEntries(query.entries())`) is confirmed directly from source, but real-world exploitability may vary slightly by adapter's URL-parsing behavior.

function normalizeQuery(query: HmacQuery, signator: HMACSignator): AuthQuery {
  if (!(query instanceof URLSearchParams)) {
    if (signator === 'appProxy') {
      for (const key of APP_PROXY_SINGLE_VALUE_PARAMS) {
        if (Array.isArray(query[key])) {
          throw new ShopifyErrors.InvalidHmacError(
            `Query parameter "${key}" must not appear more than once.`,
          );
        }
      }
    }

    return query;
  }

  const normalizedQuery = Object.create(null) as AuthQuery;
  for (const [key, value] of query.entries()) {
    const existingValue = normalizedQuery[key];
    if (existingValue === undefined) {
      normalizedQuery[key] = value;
    } else if (
      signator === 'appProxy' &&
      APP_PROXY_SINGLE_VALUE_PARAMS.has(key)
    ) {
      throw new ShopifyErrors.InvalidHmacError(
        `Query parameter "${key}" must not appear more than once.`,
      );
    } else {
      normalizedQuery[key] = `${existingValue},${value}`;
    }
  }

  return normalizedQuery;
}
