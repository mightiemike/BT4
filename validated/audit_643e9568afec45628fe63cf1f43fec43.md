### Title
Missing verification that the caller-supplied `shop` matches the session token's `dest` claim in `tokenExchange` - ([File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts])

### Summary
`tokenExchange()` decodes and cryptographically validates the session token's signature/expiry, but it discards the decoded payload and never checks that the payload's `dest` (the shop the token was actually issued for) matches the separately supplied `shop` parameter used to build the outbound OAuth request URL and the resulting `Session`.

### Finding Description
In `tokenExchange`, the session token is decoded only to validate signature/exp/nbf/aud; the returned payload is never compared to the `shop` argument: [1](#0-0) 

```
export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({shop, sessionToken, requestedTokenType, expiring}) => {
    await decodeSessionToken(config)(sessionToken);   // payload discarded
    ...
    const cleanShop = sanitizeShop(config)(shop, true)!;   // caller-controlled, unrelated to token
    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`, ...
``` [2](#0-1) 

The library's own documentation instructs app developers to source `shop` independently from the request (e.g. a query/search param), not from the verified JWT `dest` claim: [3](#0-2) 

Compare this to how `decode-session-token.ts` and other authenticate flows *do* derive `shop` strictly from the verified `dest` claim (e.g. `getSessionTokenContext` in the Remix/React Router packages uses `new URL(payload.dest).hostname` as the shop, never trusting an independent `shop` value): [4](#0-3) 

Because `tokenExchange` accepts `shop` and `sessionToken` as two independently supplied parameters with no cross-check, any caller who follows the documented API (or any endpoint that lets an authenticated app-embedded user influence the `shop` query parameter, e.g. via `req.query.shop`) can submit a valid session token for shop A together with a `shop` value for shop B. The resulting outbound HTTP request — including `client_id` and `client_secret` — is sent to `https://{attacker-chosen shop}/admin/oauth/access_token`, and if a response is returned, a `Session` object is created and keyed under `cleanShop` (the attacker-supplied shop), not the shop the token actually belonged to.

### Impact Explanation
This is directly analogous to the ExecuteSwap bug class: a "missing check" between two logically-linked inputs (`_tokenFrom` vs. `msg.value` in the original report; `shop` vs. the JWT `dest` here) allows the two values to diverge, letting an attacker substitute an untrusted value for a step downstream that assumes consistency. Here the consequence is a confused-deputy/cross-tenant condition: the app's client secret and a legitimate session token can be paired with an attacker-chosen shop domain to drive a token-exchange request and session creation for a shop that never actually authorized/issued that token. Depending on how the consuming app wires `shop`, this can lead to session-storage entries being created/overwritten under the wrong shop key (cross-tenant session confusion) or leaking token-exchange requests to a shop the caller does not control.

### Likelihood Explanation
Exploitability depends on the app-layer caller passing an independently-sourced `shop` (e.g., from `req.query.shop`) rather than deriving it from the verified token's `dest`, which is exactly what the SDK's own reference documentation instructs developers to do. Some framework integrations in this repo (Remix, React Router `authenticate.admin`) already correctly derive `shop` from `payload.dest`, mitigating risk there, but the underlying `shopify-api` primitive itself performs no defense-in-depth check, and any app built directly on `shopify.auth.tokenExchange` per the documented pattern is exposed. This requires only an unprivileged/single merchant able to control the `shop` query parameter alongside a session token (e.g. their own valid token) to attempt cross-tenant misuse.

### Recommendation
In `tokenExchange` (and ideally in `decodeSessionToken`'s callers generally), capture the decoded payload and assert that `new URL(payload.dest).hostname` equals the sanitized `shop` argument before constructing the outbound request; reject the exchange (throw an `InvalidJwtError` or similar) on mismatch, mirroring the pattern already used in the Remix/React Router `getSessionTokenContext` helpers.

### Proof of Concept
1. Obtain (or forge/hold) a valid, signed session token whose `dest` is `attacker-owned-shop.myshopify.com` (e.g. issued via normal App Bridge flow for a shop the caller controls).
2. Call `shopify.auth.tokenExchange({ shop: 'victim-shop.myshopify.com', sessionToken, requestedTokenType })` — following the documented pattern where `shop` is read from `req.query.shop` rather than the token payload.
3. Observe that `tokenExchange` never compares `sessionToken`'s `dest` to `shop`: [5](#0-4) 
4. The request is sent to `https://victim-shop.myshopify.com/admin/oauth/access_token` with the app's `client_secret` and the mismatched `subject_token`; any resulting `Session` is created with `shop: cleanShop` (`victim-shop.myshopify.com`), independent of the token's true origin — demonstrating the missing shop/token consistency check.

export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );
