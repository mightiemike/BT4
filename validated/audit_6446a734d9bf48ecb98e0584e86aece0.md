### Title
`ensure_match_transaction_info` skips state-checkpoint hash verification, letting replay-verify accept a divergent state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole correctness check used by the `db-tool replay-on-archive` verifier (and other replay/verify call sites) to confirm that locally re-executed transactions match the transaction infos committed to the accumulator. The function checks status, gas used, write-set hash, and event-root hash, but explicitly does not check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` — the fields that bind a transaction info to the actual state (Merkle/JMT) root. A local bug in state-checkpoint/root computation would therefore be silently accepted by the replay-verify tool.

### Finding Description
`ensure_match_transaction_info` computes and compares only three of the fields inside `TransactionInfo`: [1](#0-0) 

It hashes the write set and compares against `txn_info.state_change_hash()`, and it recomputes the event accumulator root and compares against `txn_info.event_root_hash()`, but it never recomputes or compares `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. The code contains an explicit acknowledgment of the gap: [2](#0-1) 

This is the exact function used by `storage/db-tool`'s archive replay-verifier to certify that re-executing a range of historical mainnet transactions reproduces the committed `TransactionInfo`s: [3](#0-2) 

`TransactionInfo` (both V0 and V1) carries `state_checkpoint_hash`, and V1 additionally carries `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, all of which are part of the accumulator leaf hash and therefore part of what an honest validator is attesting to when it signs a `LedgerInfo`: [4](#0-3) 

Because `ensure_match_transaction_info` never recomputes these checkpoint hashes from the locally re-executed state, `replay_on_archive` (and any other caller relying on this function as its correctness oracle) will report a *successful* replay even if the state root produced by local re-execution diverges from the state root that was actually committed and signed by validators. The state-checkpoint root is precisely the value that is supposed to prove "committed state == correct VM result"; skipping it removes the one check that would catch a JMT/SMT computation bug, a hot-state root bug, or (per the TODO) a `position_state_checkpoint_hash` divergence introduced by the trading-native state root feature.

### Impact Explanation
Replay-verify tooling is the mechanism operators and auditors use to gain confidence that a historical/archived database (or a new client re-executing the whole chain) reproduces the exact chain state that was voted on and signed by validators. By omitting the state/hot-state/position-state checkpoint hash comparisons, this tool provides a false sense of assurance: any bug elsewhere in the codebase that corrupts the JMT/SMT root computation, hot-state root computation, or (once enabled) the native-position state root, would pass `replay_on_archive` silently. This directly undermines the state-commitment integrity guarantee the tool exists to provide, and could mask a hard-fork-causing state divergence rather than surface it, which is exactly the class of impact this scan is meant to catch (the local root cause is confirmed in-repo via the TODO comment and the exact set of fields the function omits).

### Likelihood Explanation
The gap is deterministic and 100% reproducible — it is not a race condition or edge case, it is a structural omission in the verification function that is exercised on every call. Any state-root-computation bug (in the JMT restore code, `do_state_checkpoint.rs`, hot-state summary, or the still-experimental trading-native position state root) would be missed every single time replay-verify is run, until such a bug is discovered by some other means (e.g., a live chain halt).

### Recommendation
Extend `ensure_match_transaction_info` (or add a companion check invoked alongside it in `replay_on_archive.rs` / `chunk_executor`) to recompute the state-checkpoint hash (and, when applicable, `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`) from the locally re-executed state and assert equality with the corresponding fields of the expected `TransactionInfo`, exactly as is already done for `state_change_hash` and `event_root_hash`. This requires threading the relevant state-summary/root value computed during execution into the comparison, mirroring how `do_state_checkpoint.rs` derives `state_checkpoint_hashes` from `execution_output`.

### Proof of Concept
1. Introduce (hypothetically) a bug in the JMT/SMT root computation path (e.g., `execution/executor/src/workflow/do_state_checkpoint.rs`) that produces an incorrect `state_checkpoint_hash` for a given version, while all write sets/events/gas/status remain correct.
2. Run `db-tool replay-on-archive` over the affected version range against the archived transaction infos.
3. `execute_and_verify` calls `ensure_match_transaction_info` per transaction: [3](#0-2) 
4. Because the function never recomputes/compares `state_checkpoint_hash`, the call returns `Ok(())` and the tool reports the range as successfully verified, even though the state root diverges from the one signed in the archived `LedgerInfo`.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );
