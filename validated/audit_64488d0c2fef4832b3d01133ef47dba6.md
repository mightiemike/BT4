## Verification of recursion depth in `get_recursive_transaction_results`

This function recurses once per receipt in the outcome tree, with **no depth limit and no cycle/duplicate-visit check**, unlike the sibling `handle_receipt_to_tx` path in `chain/client/src/view_client_actor.rs` which explicitly bounds hops at `RECEIPT_TO_TX_MAX_DEPTH = 1000` [1](#0-0) . By contrast, `get_recursive_transaction_results` walks `outcome.receipt_ids` recursively for every receipt id with unbounded depth [2](#0-1) , and is invoked from `get_final_transaction_result`, the function backing transaction-status queries [3](#0-2) .

An attacker who is an ordinary transaction signer can trigger deep receipt chains cheaply: NEAR's cross-contract call/promise mechanism lets a single transaction spawn a chain of dependent receipts (as demonstrated by the `max_self_recursion_delay` test contract, which recursively re-invokes itself via `promise_batch_create`/`promise_batch_action_function_call_weight` until gas runs low) [4](#0-3) , achieving depths in the range of 56–221 receipts per test observation [5](#0-4) . Each `promise_then`/self-recursive call produces a new dependent receipt id chained to the prior one, and this pattern can be repeated across multiple transactions/blocks (each hop consuming gas but not blocked from being re-chained by follow-up transactions) to build outcome chains that are `receipt_ids`-linked far beyond what a native stack frame budget can traverse when a subsequent `tx` RPC query (or indexer / view call) walks `get_final_transaction_result` → `get_recursive_transaction_results` on the resulting transaction hash.

This matches the HtmlUnit bug class precisely: **unbounded/unrestricted recursion triggered by attacker-controlled structurally nested input**, reachable from a single externally-submitted transaction plus a subsequent unprivileged JSON-RPC `tx`/`EXPERIMENTAL_tx_status` query, causing a stack overflow that crashes (or hangs) the serving node process — a transaction/RPC-triggered node crash. I was not able to fully trace whether an even simpler single-transaction path (e.g. via delayed/local receipt chaining without needing multiple blocks) can produce thousands of chained receipt ids in one go, nor could I confirm the exact native stack depth nearcore's server threads reserve — those would need empirical stack-depth testing on the target binary, which is outside what static code search can settle.

### Title
Unbounded recursion in `get_recursive_transaction_results` allows RPC-triggered stack-overflow / node crash - ([File: chain/chain/src/chain.rs])

### Summary
`get_recursive_transaction_results`, used by the `tx` / `EXPERIMENTAL_tx_status` JSON-RPC handlers via `get_final_transaction_result`, recursively walks a transaction's receipt-outcome tree with no depth limit, unlike the analogous `handle_receipt_to_tx` path which explicitly caps hops at `RECEIPT_TO_TX_MAX_DEPTH`. An attacker who submits a transaction that spawns a long chain of dependent cross-contract-call receipts can cause any node serving a subsequent status query for that transaction hash to recurse until it overflows its stack.

### Finding Description
`get_recursive_transaction_results` recurses once per receipt id found in each outcome's `receipt_ids`, with no maximum-depth guard and no cycle detection [2](#0-1) . It is called by `get_final_transaction_result`, which backs transaction-status views returned by JSON-RPC/view-client queries [3](#0-2) .

By contrast, the newer `handle_receipt_to_tx` handler for a structurally similar "walk parent-receipt chain" operation explicitly enforces `RECEIPT_TO_TX_MAX_DEPTH = 1000` and returns `DepthExceeded` rather than recursing unboundedly, and it is implemented iteratively (bounded `for _ in 0..RECEIPT_TO_TX_MAX_DEPTH` loop) rather than via native recursion [6](#0-5) [7](#0-6) . This shows the project is aware of, and has previously mitigated, this exact bug class elsewhere — but `get_recursive_transaction_results` was left unguarded.

A single unprivileged transaction signer can create arbitrarily deep receipt chains cheaply using self cross-contract calls, as shown by the `max_self_recursion_delay` test contract, which repeatedly issues `promise_batch_create` + `promise_batch_action_function_call_weight` + `promise_return` to itself until gas is nearly exhausted [8](#0-7) , empirically producing depths of 56–221 receipts per call chain in existing tests [9](#0-8) . Because outcomes/receipts persist in chain storage and later status queries recurse over the *entire* stored receipt tree (not bounded by gas remaining at query time), an attacker can chain such transactions or otherwise construct a receipt tree deep enough that `get_recursive_transaction_results`'s native call-stack recursion exceeds the thread's stack size when any client subsequently queries transaction status for the resulting hash.

### Impact Explanation
Because `get_final_transaction_result` is invoked from the transaction-status RPC/view-client code path, an attacker-controlled receipt tree depth directly determines native recursion depth on any node servicing a `tx`-status query for that transaction. Exceeding the thread's stack budget causes a stack overflow, which in Rust aborts/crashes the process (undefined behavior/hard fault, not a catchable panic) — a transaction-triggered halt of the querying node's process. This satisfies the "transaction-triggered halt" acceptance criterion.

### Likelihood Explanation
The attacker only needs to submit ordinary `FunctionCall` transactions that recursively invoke themselves via promises — a capability every account holder already has (as demonstrated by the shipped test contract). No privileged role, validator status, or malicious peer/node is required; the second step (an RPC/view query for `tx` status on the resulting hash) is a completely standard, unprivileged client operation. The chain-store-only iterative depth cap used in the sibling `handle_receipt_to_tx` implementation indicates the depth (thousands) needed to overflow a thread stack is well within reach through normal receipt chaining or several chained transactions.

### Recommendation
Rewrite `get_recursive_transaction_results` to use an explicit iterative worklist/stack (as already done in `handle_receipt_to_tx` and in `TrieRecordingStorage::get_subtree_size`'s non-recursive BFS, which explicitly comments "Non recursive approach to avoid any potential stack overflows" [10](#0-9) ), and/or enforce a maximum traversal depth/outcome count analogous to `RECEIPT_TO_TX_MAX_DEPTH`, returning an error instead of recursing further when exceeded.

### Proof of Concept
1. Deploy/use a contract exposing the equivalent of `max_self_recursion_delay` (self cross-contract recursive promise chaining) [4](#0-3) .
2. Submit a transaction invoking this method with maximum gas so it recurses through as many self-calls as gas allows (test observed 56–221 hops per call under `MAX_GAS`) [11](#0-10) ; repeat/chain multiple such transactions targeting the same lineage to compound depth across blocks if a single call's depth is insufficient to overflow the stack.
3. Once the resulting receipt tree is committed to chain storage, call the `tx` (or `EXPERIMENTAL_tx_status`) JSON-RPC method with the originating transaction hash on a node that has this data.
4. The RPC/view-client handler invokes `get_final_transaction_result` → `get_recursive_transaction_results`, which recurses natively over every receipt in the tree; sufficiently deep trees overflow the serving thread's stack and crash the node process.

    pub fn get_final_transaction_result(
        &self,
        transaction_hash: &CryptoHash,
    ) -> Result<FinalExecutionOutcomeView, Error> {
        let mut outcomes = Vec::new();
        self.get_recursive_transaction_results(&mut outcomes, transaction_hash, true)?;
        let status = self.get_execution_status(&outcomes, transaction_hash);
        let receipts_outcome = outcomes.split_off(1);
        let transaction = self.chain_store.get_transaction(transaction_hash).ok_or_else(|| {
            Error::DBNotFoundErr(format!("Transaction {} is not found", transaction_hash))
        })?;
        let transaction = SignedTransactionView::from(Arc::unwrap_or_clone(transaction));
        let transaction_outcome = outcomes.pop().unwrap();
        Ok(FinalExecutionOutcomeView { status, transaction, transaction_outcome, receipts_outcome })
    }

/// Delay completion of the receipt for as long as possible through self cross-contract calls.
///
/// This contract keeps the recursion depth and returns it when less than 5Tgas remains, which is
/// most likely is no longer sufficient for another cross-contract call.
///
/// This is a stable alternative to yield/resume proposal at the time of writing.
#[unsafe(no_mangle)]
pub unsafe fn max_self_recursion_delay() {
    input(0);
    let mut bytes = [0u8; 4];
    read_register(0, bytes.as_mut_ptr());
    let recursion = u32::from_be_bytes(bytes);
    let available_gas = prepaid_gas() - used_gas();
    if available_gas < 5_000_000_000_000 {
        return value_return(4, bytes.as_ptr() as u64);
    }
    current_account_id(1);
    let method_name = "max_self_recursion_delay";
    let promise_idx = promise_batch_create(u64::MAX, 1);
    let amount = 1u128;
    let gas_fixed = 0;
    let gas_weight = 1;
    let argument_bytes = recursion.saturating_add(1).to_be_bytes();
    promise_batch_action_function_call_weight(
        promise_idx,
        method_name.len() as u64,
        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,
        &amount as *const u128 as u64,
        gas_fixed,
        gas_weight,
    );
    promise_return(promise_idx);
}

    // to avoid having separate cases for every possible combination of features.
