This confirms the analog: `DefaultExpiryAfterBlocks = 100_000_000` [1](#0-0)  — expiry is effectively disabled ("~19 years at 6s blocks"), meaning inbound/outbound/TSS ballots almost never age out of `ActiveBallotIDs`. Every unique inbound/outbound observation created by ordinary bridge usage becomes a permanent entry in `ActiveBallotIDs` until finalized, and `CreateBallot` unconditionally re-walks the *entire* `ActiveBallotIDs` set on every single new ballot creation via `ExpireBallotsBeforeHeight` [2](#0-1) .

### Title
Unbounded `ActiveBallotIDs` walk on every ballot creation causes quadratic gas growth and validator-vote DoS - (File: `x/uvalidator/keeper/ballot.go`)

### Summary
`CreateBallot` calls `ExpireBallotsBeforeHeight`, which does a full iteration (plus a `Ballots.Get` per entry) over the entire `ActiveBallotIDs` collection, on every single new ballot creation [3](#0-2) . Because `DefaultExpiryAfterBlocks` is set to 100,000,000 blocks (effectively disabled) [1](#0-0) , ballots created from ordinary, unprivileged bridge activity (inbound deposits, outbound observations, TSS/fund-migration events) never expire and accumulate indefinitely in `ActiveBallotIDs`. Every subsequent vote that creates a new ballot (`VoteOnInboundBallot`, `VoteOnOutboundBallot`, `VoteOnTssBallot`, `VoteOnFundMigrationBallot` → `VoteOnBallot` → `GetOrCreateBallot` → `CreateBallot`) [4](#0-3)  re-scans the whole (ever-growing) active set, making per-vote cost grow linearly with total historical ballot volume and aggregate cost grow quadratically — the exact "unbounded array length" gas-overflow class described in the external report, but here the growth is driven by ordinary, unprivileged user activity (deposits/inbound events) rather than admin actions like `massUpdatePools()`.

### Finding Description
`x/uvalidator`'s ballot machine is the single voting primitive used by `x/uexecutor` (inbound/outbound) and `x/utss` (TSS key/fund migration) [5](#0-4) . Ballot IDs are derived deterministically from the observation content — e.g. `GetInboundBallotKey` hashes source chain, tx hash, sender, amount, asset, raw payload, etc. [6](#0-5)  — so every distinct real-world bridge deposit an ordinary, unprivileged user makes on any enabled source chain produces a brand-new ballot ID.

`CreateBallot` always calls `ExpireBallotsBeforeHeight(ctx, blockHeight)` before persisting the new ballot: [2](#0-1) 

`ExpireBallotsBeforeHeight` performs a two-phase, full walk of `ActiveBallotIDs`, fetching each `Ballot` record individually to check its expiry height: [3](#0-2) 

Because `DefaultExpiryAfterBlocks = 100_000_000` is used for inbound and outbound ballots [7](#0-6) [8](#0-7) , and fund-migration ballots use a similarly huge `fundMigrationExpiryBlocks = 100_000_000` [9](#0-8) , essentially no ballot from ordinary chain operation ever ages out of `ActiveBallotIDs` within realistic timeframes. Every unprivileged user deposit that reaches a source-chain gateway generates a unique inbound observation and, once a universal validator votes on it, a new ballot entry that lives in `ActiveBallotIDs` indefinitely (until manually/governance-purged, as evidenced by the dedicated `purge-expired-outbounds` upgrade handler that had to be written specifically to clean up this backlog [10](#0-9) ).

This means the cost of the `ExpireBallotsBeforeHeight` walk inside `CreateBallot` grows monotonically with the total number of ballots ever created and not yet finalized — an attacker-influenced, unbounded quantity, directly analogous to `pool.length` in the reported `massUpdatePools()` bug. Since this walk executes synchronously inside the message-handling path for `MsgVoteInbound`/`MsgVoteOutbound`/TSS vote messages (i.e., inside a state-transition that is metered by block gas), sustained ordinary bridge usage (or a burst of low-cost deposits on any enabled external chain) drives the active-ballot count up, increasing the gas cost of every subsequent vote transaction that creates a new ballot.

### Impact Explanation
As `ActiveBallotIDs` grows unbounded, per-vote gas cost for creating a new ballot increases linearly with the current active count, and aggregate cost across N created ballots is quadratic. In the worst case, gas cost for a single vote transaction that triggers ballot creation could approach or exceed the block gas limit, causing:
- Universal-validator vote transactions (`MsgVoteInbound`/`MsgVoteOutbound`/TSS votes) to fail with out-of-gas, preventing new ballots (and therefore new inbound/outbound finalizations) from being created — a denial of service on the crosschain execution pipeline reachable purely by accumulated ordinary user deposit volume, not by any privileged actor.
- Because ballots effectively never expire (100M block expiry), this degradation is one-directional and worsens over the life of the chain unless manually remediated (as the `purge-expired-outbounds` upgrade had to do).

This falls within the allowed "denial of service ... reachable without privileged control" impact category, since it can stall genuine user deposits/withdrawals from ever finalizing once the active-ballot backlog is large enough.

### Likelihood Explanation
Likelihood is proportional to organic or attacker-inflated bridge/deposit volume over time. Since `ActiveBallotIDs` never prunes on its own within realistic timeframes (100M-block expiry), and this project already required a manual upgrade handler (`purge-expired-outbounds`) to work around this same accumulation for outbound ballots [11](#0-10) , the underlying growth pattern is confirmed to be a real, already-observed operational issue rather than a purely theoretical one. An attacker does not need special privileges — merely submitting many low-value cross-chain deposits (paid for on the external source chain, not Push Chain) is sufficient to inflate the backlog and degrade the `CreateBallot` path for everyone. The concrete point at which this becomes a hard DoS (gas limit exceeded) depends on chain-specific gas parameters and active-ballot count at the time, which was not independently benchmarked here.

### Recommendation
- Bound the per-call cost of `ExpireBallotsBeforeHeight`: process expirations in fixed-size batches (e.g., iterate at most K entries per call, using a cursor/offset persisted across calls) rather than a full walk on every `CreateBallot`.
- Alternatively, decouple expiry checking from the hot ballot-creation path entirely — run it in a bounded `EndBlocker`/`BeginBlocker` job (`x/uvalidator` already has a `BeginBlocker` for UV reward boosting [12](#0-11) ) that processes a capped number of expirations per block.
- Reconsider the `DefaultExpiryAfterBlocks = 100_000_000` setting; a realistic expiry (or an active pruning/archival mechanism keyed by height) would keep `ActiveBallotIDs` bounded by design rather than relying on ad-hoc upgrade-handler cleanups like `purge-expired-outbounds`.
- Add index-based secondary structures (e.g., an expiry-height-ordered index) so expired ballots can be found and removed in O(expired count) instead of O(total active count).

### Proof of Concept
1. Enable a source chain with cheap/low-value deposits allowed by `x/uregistry` chain config.
2. Repeatedly submit distinct inbound bridge deposits (varying tx hash/sender/amount — trivially producible by any unprivileged external user) so that universal validators cast `MsgVoteInbound` votes that each create a new, distinct ballot via `VoteOnInboundBallot` → `VoteOnBallot` → `GetOrCreateBallot` → `CreateBallot` [13](#0-12) .
3. Because `DefaultExpiryAfterBlocks` is 100,000,000, none of these ballots expire and all remain in `ActiveBallotIDs`.
4. Observe that each subsequent `CreateBallot` call re-walks the growing `ActiveBallotIDs` set via `ExpireBallotsBeforeHeight` [3](#0-2) , with gas consumption for vote transactions rising proportionally to the accumulated active-ballot count, eventually threatening to exceed the block gas limit for the vote transaction that triggers ballot creation.

// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}

### Generic Ballot Machine

Every crosschain observation (in `x/uexecutor` and `x/utss`) is voted through this single mechanism:

```go
ballot, finalized, isNew, err := k.VoteOnBallot(
    ctx,
    ballotId,           // canonical hash of the observation
    ballotType,         // INBOUND | OUTBOUND | CHAIN_META | TSS_EVENT | FUND_MIGRATION
    voter,              // signer's bech32 address
    voteResult,         // SUCCESS | FAILURE
    eligibleVoters,     // snapshot of UVs at ballot creation
    votesNeeded,        // threshold (caller decides 2/3, 100%, simple majority, ...)
    expiryAfterBlocks,  // ballot auto-expires after this many blocks
)
```

A ballot is created lazily on the first vote, indexed in `ActiveBallotIDs`, and finalizes the moment either:
- `yesVotes >= votingThreshold` -> `BALLOT_STATUS_PASSED`
- `eligibleVoters - noVotes < votingThreshold` (the threshold is now mathematically unreachable) -> `BALLOT_STATUS_REJECTED`

On finalization, the ballot is moved from `ActiveBallotIDs` -> `FinalizedBallotIDs`. Expired ballots that never reached threshold are moved to `ExpiredBallotIDs`.

The ballot type is opaque — `x/uvalidator` doesn't care what's being voted on. The ballot ID is a `sha256` of the canonical observation, so two validators voting on the same observation hit the same ballot deterministically.

// GetInboundBallotKey: versioned canonical digest over every execution-
// relevant field (so quorum implies agreement on the outcome), excluding
// universal_payload (recomputed on-chain from raw_payload). Self-canonicalizes,
// so any caller gets one ballot per logical event.
func GetInboundBallotKey(inbound Inbound) (string, error) {
	chain := strings.TrimSpace(inbound.SourceChain)

	// nil RevertInstructions and an empty FundRecipient are semantically
	// identical (revert falls back to sender) — digest them identically.
	fundRecipient := ""
	if inbound.RevertInstructions != nil {
		fundRecipient = utils.LenientCanonicalizeAddress(chain, inbound.RevertInstructions.FundRecipient)
	}

	return hashFields(
		InboundBallotDomain,
		chain,
		utils.LenientCanonicalizeTxHash(chain, inbound.TxHash),
		strings.TrimSpace(inbound.LogIndex),
		utils.LenientCanonicalizeAddress(chain, inbound.Sender),
		// Recipient lives on Push Chain (EVM) regardless of source chain.
		utils.LenientCanonicalizeEVMAddress(inbound.Recipient),
		strings.TrimSpace(inbound.Amount),
		utils.LenientCanonicalizeAddress(chain, inbound.AssetAddr),
		fmt.Sprintf("%d", inbound.TxType),
		utils.CanonicalizeHexBlob(inbound.VerificationData),
		fundRecipient,
		fmt.Sprintf("%t", inbound.IsCEA),
		utils.CanonicalizeHexBlob(inbound.RawPayload),
		// universal_payload intentionally excluded (derived, ignored on-chain).
	), nil
}

func (k Keeper) VoteOnInboundBallot(
	ctx context.Context,
	universalValidator sdk.ValAddress,
	inbound types.Inbound,
) (isFinalized bool,
	isNew bool,
	err error) {
	ballotKey, err := types.GetInboundBallotKey(inbound)
	if err != nil {
		return false, false, err
	}

	universalValidatorSet, err := k.uvalidatorKeeper.GetEligibleVoters(ctx)
	if err != nil {
		return false, false, err
	}

	// number of validators
	totalValidators := len(universalValidatorSet)

	// votesNeeded = ceil(2/3 * totalValidators)
	// >2/3 quorum similar to tendermint
	votesNeeded := (types.VotesThresholdNumerator*totalValidators)/types.VotesThresholdDenominator + 1

	k.Logger().Debug("voting on inbound ballot",
		"ballot_key", ballotKey,
		"validator", universalValidator.String(),
		"total_validators", totalValidators,
		"votes_needed", votesNeeded,
	)

	// Convert []sdk.ValAddress → []string
	universalValidatorSetStrs := make([]string, len(universalValidatorSet))
	for i, v := range universalValidatorSet {
		universalValidatorSetStrs[i] = v.IdentifyInfo.CoreValidatorAddress
	}

	// Step 2: Call VoteOnBallot for this inbound synthetic
	_, isFinalized, isNew, err = k.uvalidatorKeeper.VoteOnBallot(
		ctx,
		ballotKey,
		uvalidatortypes.BallotObservationType_BALLOT_OBSERVATION_TYPE_INBOUND_TX,
		universalValidator.String(),
		uvalidatortypes.VoteResult_VOTE_RESULT_SUCCESS,
		universalValidatorSetStrs,
		int64(votesNeeded),
		int64(types.DefaultExpiryAfterBlocks),
	)
	if err != nil {
		return false, false, err
	}

	if isNew {
		k.Logger().Debug("inbound ballot created", "ballot_key", ballotKey)
	}
	if isFinalized {
		k.Logger().Info("inbound ballot finalized", "ballot_key", ballotKey, "source_chain", inbound.SourceChain)
	}

	return isFinalized, isNew, nil
}
