### Title
Unbounded memory allocation from attacker-controlled array length in deprecated (Cairo0) syscall calldata parsing - ([File: crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs])

### Summary
The Cairo0 ("deprecated") syscall request parser `read_felt_array` reads an array length felt directly from VM memory and converts it into a `usize` allocation size **without validating it against the amount of memory actually available/remaining**, before that size is used to read/allocate a range of felts. This mirrors the CVE-2020-27827 bug class (a length/TLV field from untrusted input drives an allocation without a sanity bound, causing memory exhaustion). A contract deployer/invoker who deploys or triggers execution of a Cairo0 contract can set this length field to an enormous value and force the sequencer to attempt a huge allocation while parsing a `CALL_CONTRACT`, `DELEGATE_CALL`, `LIBRARY_CALL`, or `DEPLOY` syscall request.

### Finding Description
`read_felt_array` in the deprecated (Cairo0) syscalls module: [1](#0-0) 

reads a raw `array_size` felt from VM memory, converts it straight to a `usize`, and forwards it to `felt_range_from_ptr`, which calls `vm.get_integer_range(ptr, size)`: [2](#0-1) 

Unlike the pointer-difference-based length computation used in the newer (Cairo1) syscall reader: [3](#0-2) 

the deprecated path takes the length **directly as a raw felt value** with no bound check against the actual amount of data present in the segment before it is used to drive an allocation. This is the exact analog of the `apollo_cairo_utils` fix, where the team explicitly added a check to "validate before allocating to prevent a contract-controlled length felt from triggering an unbounded `Vec::with_capacity`": [4](#0-3) 

That mitigation was applied to `Retdata`/`CairoArray` deserialization, but the same unvalidated pattern remains in `read_felt_array` in `deprecated_syscalls/hint_processor.rs`, which is used by `read_calldata`/`read_call_params` for `CallContractRequest`, `DelegateCallRequest`, `LibraryCallRequest` (implicitly via `read_call_params`) and `DeployRequest`: [5](#0-4) 

This request-parsing path is reached during blockifier execution any time a Cairo0 ("deprecated") contract executes one of these syscalls — the length field is written into VM memory by the contract's own bytecode/hints, i.e., it is fully attacker-controlled by whoever deploys and invokes that legacy-class contract.

### Impact Explanation
An unprivileged transaction sender can deploy a Cairo0 contract (or reuse an already-declared Cairo0 class hash) and invoke it so that it issues a crafted `call_contract`/`delegate_call`/`library_call`/`deploy` syscall with an artificially large `array_size` felt for the calldata array. This value flows unchecked into `usize::try_from(...)` and then into `vm.get_integer_range(ptr, size)`, which pre-allocates a buffer sized by the attacker-chosen value before validating that the memory segment actually contains that many populated cells. A sufficiently large value can force the executing sequencer/validator node to attempt a very large allocation during transaction execution, causing memory exhaustion or an abort of the execution process. Because this happens deep in blockifier's transaction-execution path (used by every sequencer that must execute/validate the transaction, including full/validator nodes performing re-execution), this can degrade or halt block production/validation — a network-availability impact consistent with "network unable to confirm new transactions."

### Likelihood Explanation
Reachability requires only a standard, unprivileged deploy + invoke sequence targeting a Cairo0 ("deprecated") class — no special privileges, staking, or node-operator access are needed. Cairo0 support and its syscall parsing code remain present and reachable in the current codebase (`deprecated_syscalls` module actively wired into blockifier's execution flow), and any already-declared or newly declared legacy class can be deployed and invoked by any account. The main mitigating uncertainty is the actual runtime behavior of `cairo_vm::VirtualMachine::get_integer_range` for very large `size` values (this function lives in the external `cairo-vm` crate, not in this repository, so its exact allocation strategy — e.g., whether it pre-allocates the full `Vec::with_capacity(size)` before validating cell presence — could not be directly confirmed from this codebase). If `get_integer_range` performs an early bounds check against segment length before allocating, the practical impact would be reduced to an early error rather than an OOM; this should be verified in the `cairo-vm` dependency source before treating this as fully proven.

### Recommendation
Apply the same defensive pattern already used in `apollo_cairo_utils::CairoArray::try_from` (validating a declared length against a hard/computable upper bound derived from actually-available data before allocating) to `read_felt_array` in `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs`. Concretely: before calling `felt_range_from_ptr`, verify that `array_size` does not exceed some configured maximum syscall array length (mirroring `max_calldata_length` validation already present in the gateway for RPC transactions) and/or verify that the target segment's current used size covers the claimed range, returning a `DeprecatedSyscallExecutorBaseError` instead of proceeding to allocate.

### Proof of Concept
1. Declare (or reuse) a Cairo0 class whose bytecode, upon invocation, manually writes a `CallContractRequest`-shaped syscall frame into its own VM memory segment where the `calldata` array's length felt (`array_size`) is set to a very large value (e.g., close to `usize::MAX` or a large multiple of the segment's actual populated size), while the corresponding `calldata` data pointer is left in a small/otherwise-normal segment.
2. Deploy this class via a standard `DEPLOY`/`DEPLOY_ACCOUNT` or `deploy` syscall from another contract, then send an `INVOKE` transaction that causes the contract to execute the crafted `CALL_CONTRACT` (or `DELEGATE_CALL`/`LIBRARY_CALL`/`DEPLOY`) syscall.
3. During execution, `CallContractRequest::read` → `read_call_params` → `read_calldata` → `read_felt_array` (`crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:931-950`) reads the crafted `array_size`, converts it to `usize`, and passes it to `felt_range_from_ptr`/`vm.get_integer_range`, attempting an allocation sized by the attacker-controlled value — observe elevated memory usage / process abort on the executing/validating node.

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError>
        + From<VirtualMachineError>
        + From<MemoryError>
        + From<MathError>
        + From<TryFromBigIntError<BigUint>>,
{
    let array_size = felt_from_ptr(vm, ptr)?;
    // An empty array's data pointer may be a felt-zero null (`cast(0, felt*)`) rather than a real
    // segment.
    if array_size == Felt::ZERO {
        *ptr = (*ptr + 1)?;
        return Ok(vec![]);
    }
    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, usize::try_from(array_size.to_biguint())?)?)
}

    vm: &VirtualMachine,
    ptr: Relocatable,
    size: usize,
) -> Result<Vec<Felt>, VirtualMachineError> {
    let values = vm.get_integer_range(ptr, size)?;

pub fn read_felt_array<TErr>(vm: &VirtualMachine, ptr: &mut Relocatable) -> Result<Vec<Felt>, TErr>
where
    TErr: From<StarknetApiError> + From<VirtualMachineError> + From<MemoryError> + From<MathError>,
{
    // If the start and end pointers are the same, the array is empty.
    // This check is necessary to handle the case where both pointers are zero, and thus are not
    // relocatable values.
    let array_start = vm.get_maybe(&*ptr);
    if array_start.is_some() && array_start == vm.get_maybe(&(*ptr + 1_usize)?) {
        *ptr = (*ptr + 2)?;
        return Ok(vec![]);
    }

    let array_data_start_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_data_end_ptr = vm.get_relocatable(*ptr)?;
    *ptr = (*ptr + 1)?;
    let array_size = (array_data_end_ptr - array_data_start_ptr)?;

    Ok(felt_range_from_ptr(vm, array_data_start_ptr, array_size)?)
}
