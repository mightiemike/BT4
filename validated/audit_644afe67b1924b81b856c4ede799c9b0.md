### Title
`ensure_match_transaction_info` skips state-checkpoint hash comparison during replay-verify, allowing an authenticated state root divergence to go undetected - (File: types/src/transaction/mod.rs)

### Summary
`replay_on_archive`'s replay-verify tool uses `TransactionOutput::ensure_match_transaction_info` as its sole correctness check between locally re-executed VM output and the authenticated, on-chain-committed `TransactionInfo` fetched from the archive. The function explicitly omits comparing `state_checkpoint_hash` / `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`, meaning a discrepancy between the locally-computed post-txn state root and the authenticated root can pass verification silently.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates a re-executed `TransactionOutput` against an authenticated `TransactionInfo` by checking status, gas used, write-set hash (`state_change_hash`), and event root hash. It deliberately does **not** validate the state checkpoint hash fields, as the code comment states directly: [2](#0-1) 

This is the only consistency check performed by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes chunks of transactions against a state view built from local storage and compares the result to `expected_txn_infos` pulled from a (potentially untrusted or divergent) backup/archive source: [3](#0-2) 

`TransactionInfo` (both `V0` and `V1`) carries `state_checkpoint_hash`, and `V1` additionally carries `hot_state_checkpoint_hash` and `position_state_checkpoint_hash`, all committed into the transaction accumulator and thus part of the authenticated ledger state: [4](#0-3) 

Because `ensure_match_transaction_info` skips these fields, if the locally computed Sparse-Merkle/Jellyfish state root (or hot-state/position-state root) diverges from what's authenticated in the accumulator-backed `TransactionInfo` — due to a state-computation bug, storage corruption, non-determinism, or a malicious/corrupted backup source feeding `expected_txn_infos` — replay-verify will still report success as long as write-set bytes and events match. The write-set hash check (`state_change_hash`) only proves the *raw write operations* match; it does not prove that applying them produces the same resulting state root, which is exactly what `state_checkpoint_hash` is meant to authenticate.

### Impact Explanation
Replay-verify (`replay_on_archive`) is a tool explicitly used to detect divergence between local execution/storage and the authenticated chain history — its entire purpose is state-integrity auditing. A gap that lets an authenticated state-root mismatch pass unnoticed defeats this purpose: a hard-fork-only or storage-corruption divergence in the state root would not be flagged, undermining confidence that "replay succeeded" implies the local state tree is correct. This matches the specified impact category ("Hard-fork-only divergence during commit, replay, restore, or proof verification" and "Committed state that differs from the correct VM result"). Impact is Medium-High: it does not itself corrupt state, but it silently masks state-root corruption/divergence that this exact tool exists to catch, and the code comment acknowledges the gap is intentional pending future work.

### Likelihood Explanation
Likelihood is Medium: the gap is triggered any time replay-verify is run against a chunk where state-checkpoint hashes would legitimately differ (e.g. due to a bug in state-tree computation, an inconsistent local state store, or corrupted backup metadata) while the write-set/events still match byte-for-byte. This is plausible in real operational scenarios (partial DB restore, hot-state feature rollout referenced in the TODO, resharding, or replay against archives from a different code version), and the comment itself flags this as a known, not-yet-addressed gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS").

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash` (and, when present, `hot_state_checkpoint_hash` / `position_state_checkpoint_hash`) between the locally computed state and `txn_info`, failing the check (as it does for `state_change_hash`/`event_root_hash`) on mismatch. If a full local recomputation of the checkpoint hash isn't available at the call site in `replay_on_archive`, thread it through similarly to how `expected_write_set`/`expected_events` are threaded, and compute/compare it before treating a chunk replay as verified.

### Proof of Concept
1. Run `replay_on_archive` against a version range where the write set and events produced by local re-execution exactly match the archived `TransactionInfo`'s `state_change_hash`/`event_root_hash`, but the local state tree (fed by `state_view_at_version`) has a stale/incorrect prior state root (e.g., due to a partial restore or a state-computation bug elsewhere), so that applying the matching write set atop the divergent base state yields a different resulting state root than the authenticated `state_checkpoint_hash`.
2. Observe `execute_and_verify` → `ensure_match_transaction_info` at [5](#0-4)  returns `Ok(())` because only `status`, `gas_used`, `state_change_hash`, and `event_root_hash` are checked in [6](#0-5) .
3. The tool reports the chunk as successfully replay-verified even though the resulting state root diverges from the authenticated ledger state — the exact scenario the code's own TODO comment warns about.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
