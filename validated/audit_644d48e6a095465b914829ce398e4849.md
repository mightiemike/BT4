## Title
Replay-verify accepts a divergent authenticated state root because `TransactionOutput::ensure_match_transaction_info` never compares the state/hot-state/position checkpoint hashes - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by both the chunk-executor's `verify_execution` path and `db-tool`'s `replay_on_archive` to confirm that locally re-executed transactions produce the same result as the authenticated, backed-up `TransactionInfo`. The function checks status, gas used, write-set hash, and event root hash, but it never recomputes or compares the `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` fields against the (proof-authenticated) expected `TransactionInfo`. As a result, a locally computed state root that diverges from the canonical, Merkle-accumulator-proven chain will still pass this "verification," silently masking a state-commitment bug during replay/verify tooling.

### Finding Description
`ensure_match_transaction_info` explicitly skips the checkpoint-hash comparisons, and this is acknowledged in the code itself: [1](#0-0) 

The function checks `status`, `gas_used`, `write_set_hash`, and `event_root_hash` [2](#0-1)  but its trailing comment admits: "this comparator ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`), so replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution" [3](#0-2) .

This function is the sole correctness gate in two places that are specifically meant to catch state divergence between local re-execution and the canonical, proof-authenticated ledger:

1. `ChunkExecutor::verify_execution`, which drives `VerifyExecutionMode` (state-sync/backup replay-verify): [4](#0-3) 
2. `db-tool`'s `replay_on_archive::execute_and_verify`, which re-executes archived transactions and compares against `expected_txn_info` pulled from a backup/archive that is itself only authenticated via the transaction accumulator proof (not per-field checked here): [5](#0-4) 

The state/hot-state/position checkpoint hashes are precisely the fields that bind a `TransactionInfo` to the actual Jellyfish Merkle / sparse-Merkle state root at that version — they are computed in `DoStateCheckpoint::run` and folded into `assemble_transaction_infos` when building the canonical `TransactionInfo` for commit: [6](#0-5) . On the actual state-sync commit path these checkpoint hashes ARE checked, but only because `LedgerUpdateOutput::ensure_transaction_infos_match` does full `TransactionInfo` struct equality (`txn_info == expected_txn_info`) rather than calling the field-by-field `ensure_match_transaction_info`: [7](#0-6) . So the gap is isolated to the two replay/verify-only call sites above, but those are exactly the tools operators and auditors rely on to detect state-commitment divergence (e.g. `db-tool replay-on-archive`, or `--verify-execution-mode` during fast/backup restore) — the "restore/replay/proof-verification" invariant called out in scope.

### Impact Explanation
If the local execution of a transaction (e.g. due to a bug in the newly introduced trading-native/position-state computation gated by `compute_trading_native_state_roots`, or any other divergence in checkpoint-hash computation) produces a different state, hot-state, or position-state root than the one actually committed and signed into the canonical chain, `ensure_match_transaction_info` will not detect it. Both `verify_execution` (used by chunk executor state-sync verify mode) and the db-tool's `replay_on_archive` verify command will report success even though the locally materialized ledger state has silently diverged from the authenticated one. This is exactly the "hard-fork-only divergence during ... replay ... or proof verification" impact category: a corrupted committed value (state/hot-state/position checkpoint root) is accepted as matching valid when it is not, undermining the primary safety mechanism meant to catch such divergence before it propagates.

### Likelihood Explanation
This requires an actual divergence to already exist between local re-execution and the canonical result (e.g. a bug in the new trading-native/position-state root computation logic, which is a large new code path added around `DoStateCheckpoint::compute_position_checkpoint`). The verification gap does not itself create a divergence, but it removes the detection mechanism that would otherwise catch such a divergence — meaning any latent bug in the newly added checkpoint-hash computation paths (state/hot-state/position) can go undetected by replay-verify indefinitely.

### Recommendation
In `ensure_match_transaction_info`, recompute (or accept as parameters) the expected `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` and compare them against `txn_info`'s corresponding fields whenever they are `Some` on the expected `TransactionInfo`, mirroring the strict equality check already performed by `LedgerUpdateOutput::ensure_transaction_infos_match`. This should be done before (or as a prerequisite for) fully enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, as the existing TODO comment itself states.

### Proof of Concept
Not directly exploitable as a standalone PoC without a concrete state-computation bug; the finding is a verification-logic gap. To demonstrate: construct a `TransactionOutput` whose `write_set()`/`events()` hash match the expected `TransactionInfo` but for which the (separately, out-of-band) locally computed state-checkpoint root would differ from `txn_info.state_checkpoint_hash()` (e.g. by feeding a mutated position-state summary through `DoStateCheckpoint::compute_position_checkpoint`). Calling `ensure_match_transaction_info` with this data returns `Ok(())` because the function at [8](#0-7)  never inspects `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash`, so both `verify_execution` and `replay_on_archive::execute_and_verify` report a clean replay despite the diverging root.

    pub fn ensure_transaction_infos_match(
        &self,
        transaction_infos: &[TransactionInfo],
    ) -> Result<()> {
        ensure!(
            self.transaction_infos.len() == transaction_infos.len(),
            "Lengths don't match. {} vs {}",
            self.transaction_infos.len(),
            transaction_infos.len(),
        );

        let mut version = self.first_version();
        for (txn_info, expected_txn_info) in
            zip_eq(self.transaction_infos.iter(), transaction_infos.iter())
        {
            ensure!(
                txn_info == expected_txn_info,
                "Transaction infos don't match. version:{version}, txn_info:{txn_info}, expected_txn_info:{expected_txn_info}",
            );
            version += 1;
        }
        Ok(())
