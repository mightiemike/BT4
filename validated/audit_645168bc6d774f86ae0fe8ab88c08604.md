Based on my research, I found a genuine, self-documented integrity gap, but I need to be clear about its verification status before reporting it.

### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash verification, letting corrupted/divergent state roots pass replay-verify - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  is the authenticated-equality check used by replay/verification tooling (`db-tool`'s `replay_on_archive`, the CLI's transaction-info verification, and `aptos-debugger`) to confirm a locally re-executed `TransactionOutput` matches the `TransactionInfo` committed on-chain. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [2](#0-1) .

### Finding Description
The function's own comment acknowledges the gap:
```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution.
``` [3](#0-2) 

The state-checkpoint hash is the Sparse-Merkle-Tree root committing the entire world state at a checkpoint boundary, distinct from the per-transaction write-set hash. Since `ensure_match_transaction_info` is the sole comparator wired into replay-verify call sites (`aptos-move/cli/src/commands.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `execution/executor/src/chunk_executor/mod.rs`, `storage/db-tool/src/replay_on_archive.rs`), any divergence in the state root at a checkpoint — whether from a VM bug, storage corruption, or (per the comment) trading-native/position-state root computation — is invisible to this check.

### Impact Explanation
This directly matches the "Proof And Storage Pivots" scope: an authenticated state-commitment value (the checkpoint/state root bound into `TransactionInfo`, and ultimately into the ledger's accumulator/`LedgerInfo`) can silently diverge from the value locally computed by the VM/executor without replay tooling detecting it. If accepted as valid, replay-verify would falsely certify a backup/archive/restore or historical execution as correct even though the durable state root differs from the true VM result — a state-integrity failure that could mask corruption in restore or fast-sync pipelines that rely on this comparator as their correctness oracle.

### Likelihood Explanation
**I cannot confirm this is currently exploitable on mainnet**, which is why I'm flagging significant uncertainty rather than asserting a concrete exploit path:
- I could not confirm within available search results whether `state_checkpoint_hash` (the currently-active field, as opposed to the newer `hot_state_checkpoint_hash`/`position_state_checkpoint_hash`) is validated by some *other* mechanism in the commit/replay pipeline (e.g., inside `do_state_checkpoint.rs` or accumulator-root verification against `LedgerInfo`) that would make this particular comparator's gap non-exploitable in practice.
- The comment ties the gap specifically to `COMPUTE_TRADING_NATIVE_STATE_ROOTS`, a feature flag defined in `types/src/on_chain_config/aptos_features.rs`, implying the `position_state_checkpoint_hash` divergence scenario is only reachable once that feature is enabled — I was not able to determine its current activation status on mainnet within the available tool budget.
- I was unable to fully trace whether accumulator-level or `LedgerInfo`-level checks elsewhere in the commit path independently catch a state-root mismatch even if this specific function does not, which would reduce the practical severity.

Given this unresolved uncertainty about whether an independent state-root check exists elsewhere in the pipeline, and that the divergence path called out in the code is explicitly gated behind an as-yet-unconfirmed feature flag, I do not have sufficient local proof to assert a concrete, currently-exploitable state-commitment corruption with certainty.

### Recommendation
Have a background engineer verify: (1) whether `state_checkpoint_hash`/`hot_state_checkpoint_hash`/`position_state_checkpoint_hash` are independently checked elsewhere in the executor/replay pipeline (e.g., against locally recomputed SMT roots) such that skipping them here is redundant rather than a gap; (2) the current mainnet activation status of `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. If no independent check exists, extend `ensure_match_transaction_info` to compare all checkpoint-hash fields present in `txn_info` against locally computed equivalents before this comparator is relied upon by replay/restore verification tooling.
