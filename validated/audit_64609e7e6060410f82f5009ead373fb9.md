## Finding: Stale global class cache lets an undeclared Cairo0 class remain executable after a block revert — no revalidation for `V0` classes (unlike Cairo1)

### Title
Undeclared Cairo0 (V0) class remains served from `ContractClassManager` cache after block revert, without re-validation - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
The Unbound "ghost domain names" bug class is: a resolver caches delegation/validity data and, when that data is later revoked, keeps serving the stale cached data because the code path that consumes it never re-checks current authoritative state. The sequencer has a direct analog in its global compiled-class cache: `ContractClassManager` caches `RunnableCompiledClass` entries keyed by `ClassHash` across the process lifetime and across blocks, but the code that revalidates a cache hit against the *current* declared-class state only does so for Cairo1 classes, not for Cairo0 (`V0`) classes.

### Finding Description
`get_compiled_from_class_manager` explicitly acknowledges that a cache hit does not guarantee the class is still declared "since existence in the cache does not guarantee that (it might contain a declared class from a reverted block, for example)" — but it only performs the `is_declared` re-check for non-`V0` variants: [1](#0-0) 

For `RunnableCompiledClass::V0(_)` the `match` arm is empty — the cached class is returned as-is with no verification that it is still declared in the authoritative state (`state_reader.is_declared`).

Meanwhile, the current production revert path used by the batcher (`Batcher::revert_block`, which drives `apollo_reverts::revert_block` on storage) never clears the shared `ContractClassManager` cache: [2](#0-1) 

This is in contrast to the legacy `native_blockifier` path, which explicitly clears the cache on revert specifically to avoid this class of bug: [3](#0-2) 

Storage-level revert does correctly remove the deprecated (Cairo0) class declaration record, e.g. `delete_deprecated_declared_classes_block` / `delete_deprecated_declared_classes`, confirmed by the round-trip test `declare_revert_declare_scenario`: [4](#0-3) [5](#0-4) 

So storage correctly reflects "undeclared" after a revert, but the in-memory `ContractClassManager` (`RawClassCache` / `GlobalContractCache`) does not get invalidated for `V0` entries, and the consuming code path (`get_compiled_from_class_manager`) skips the compensating live-state check that Cairo1 classes get. The result: a `ClassHash` that is undeclared in the current state, but was declared and cached (as `V0`) prior to a block revert, is still served as a valid, executable compiled class by any node whose local cache is still "warm" from having previously executed/built the reverted block.

### Impact Explanation
This produces exactly the "ghost" persistence pattern from the CVE analog — data that should have been invalidated by a revocation event (block revert / undeclare) keeps being treated as authoritative because the consuming code trusts the cache without re-checking current declared state (for `V0` only).

The practical consequence in this sequencer is honest-node divergence:
- A node that itself built/executed the block containing the Cairo0 `declare` (and thus has the class cached) will, after that block is reverted (e.g. via `Batcher::revert_block`), continue to treat a subsequent `invoke`/`deploy` referencing that class hash as valid (`StateReader::get_compiled_class` succeeds via the warm `V0` cache entry).
- A different honest node that did not previously cache the class (e.g., it joined later, or its cache was cold) will correctly reject the same transaction with `StateError::UndeclaredClassHash`, per the intended "must be declared" semantics that Cairo1 explicitly enforces.

Different honest sequencer nodes therefore reach different execution results/state for the same transaction sequence, which can lead to differing committed state roots/block hashes among otherwise-honest validators, i.e. consensus/state divergence — a Medium-severity concrete impact matching the accepted categories (honest-node divergence / wrong committed root).

### Likelihood Explanation
Reaching this requires:
1. An unprivileged sender submits a `DECLARE` for a Cairo0 (deprecated) class — a standard, permitted action for a class declarer.
2. The block containing that declaration is later reverted by the sequencer's own revert flow (`Batcher::revert_block` → `apollo_reverts::revert_block`), which is a normal, non-malicious operational path (used e.g. for consensus recovery from partially-committed heights), not requiring a malicious peer/operator.
3. Any subsequent transaction referencing that class hash is then handled differently depending on whether the local node's `ContractClassManager` cache is warm or cold for that class hash — a difference in incidental process history rather than attacker action, so it is only probabilistically triggered, but it is a genuine, reachable code-path asymmetry (the `V0` branch's missing re-check is a direct, provable gap versus the `V1`/`V1Native` branch).

### Recommendation
Apply the same `is_declared` revalidation to the `V0` branch in `get_compiled_from_class_manager` that is already applied to Cairo1 classes, so a cache hit for a deprecated class is confirmed against current state before being trusted: [6](#0-5) 

Alternatively/additionally, ensure `Batcher::revert_block` clears (or selectively invalidates) the shared `ContractClassManager` cache on revert, matching the pattern already used in `native_blockifier::PyBlockExecutor::revert_block`: [7](#0-6) 

### Proof of Concept
1. Node A submits/executes a block `N` containing `DECLARE` of Cairo0 class `C` (declared via `deprecated_declared_classes`), which populates the local `ContractClassManager`'s `class_cache` with `CompiledClasses::V0(C)` (see `set_and_compile`/`get_runnable` in `crates/blockifier/src/state/native_class_manager.rs` / `contract_class_manager.rs`).
2. Block `N` is reverted via `Batcher::revert_block` (`crates/apollo_batcher/src/batcher.rs:1428`), which calls `apollo_reverts::revert_block`, correctly removing `C`'s declaration from storage (`delete_deprecated_declared_classes_block`), but never calls `contract_class_manager.clear()`.
3. A transaction (e.g. `invoke` or `deploy_account`) referencing class hash `C` is submitted and executed on Node A: `StateReaderAndContractManager::get_compiled_class(C)` → `get_compiled_from_class_manager` hits the cache, matches `RunnableCompiledClass::V0(_)`, takes the empty match arm, and returns the cached class as valid — despite `C` being undeclared in current storage.
4. The same transaction executed on Node B (cold cache) fails with `StateError::UndeclaredClassHash(C)`, because its `get_compiled_from_class_manager` falls through to `self.state_reader.get_compiled_classes(C)`, which reads current (post-revert) declared-class storage and returns an error.
5. Nodes A and B diverge on the validity/effects of the same transaction — honest-node state divergence.

    // This function will panic if there is a storage failure to revert the block.
    pub async fn revert_block(&mut self, input: RevertBlockInput) -> BatcherResult<()> {
        info!("Reverting block at height {}.", input.height);
        let height = self.get_height_from_storage()?.prev().ok_or(
            BatcherError::StorageHeightMarkerMismatch {
                marker_height: BlockNumber(0),
                requested_height: input.height,
            },
        )?;

        if height != input.height {
            return Err(BatcherError::StorageHeightMarkerMismatch {
                marker_height: height.unchecked_next(),
                requested_height: input.height,
            });
        }

        if let Some(height) = self.active_height {
            info!("Aborting all work on height {} due to a revert request.", height);
            self.abort_active_height().await;
        }

        // Wait for the revert commitment to be completed before reverting the storage.
        self.revert_commitment(height).await;

        self.storage_writer.revert_block(height);
        BUILDING_HEIGHT.decrement(1);
        GLOBAL_ROOT_HEIGHT.decrement(1);
        REVERTED_BLOCKS.increment(1);
        Ok(())
    }
