### Title
Witness reward allowance can become permanently unwithdrawable for genesis-witness ("GP") addresses, with no admin recovery path - ([File: actuator/src/main/java/org/tron/core/actuator/WithdrawBalanceActuator.java])

### Summary
The reward/allowance accounting model in java-tron accrues voting/block rewards into an account's `allowance` field through fully permissionless, vote-driven processes, but the *only* two mechanisms that convert `allowance` into spendable `balance` — `WithdrawBalanceActuator` and the TVM native `withdrawreward` opcode (`WithdrawRewardProcessor`) — unconditionally reject any address that matches a genesis-block witness. There is no expiry, override, or emergency sweep function to release this value, mirroring the "funds locked indefinitely because the only withdrawal path is gated behind a condition that can never be satisfied" pattern described in the external NukeFund report.

### Finding Description
Reward accrual (`payReward`, `payStandbyWitness`, `adjustAllowance`) in `MortgageService.payReward` is triggered purely by the public, permissionless vote/consensus process — any address that receives votes and is elected/standby witness accumulates `allowance` regardless of who controls it: [1](#0-0) 

The only two code paths that move `allowance` into spendable `balance` both perform an unconditional, permanent check against the genesis witness list and reject the operation entirely if it matches, with no alternate mitigation:

- `WithdrawBalanceActuator.validate()`: [2](#0-1) 

- `WithdrawRewardProcessor.validate()` (invoked from the TVM `withdrawreward` opcode via `Program.withdrawReward()`): [3](#0-2) 

Both checks compare the address unconditionally against `CommonParameter.getInstance().getGenesisBlock().getWitnesses()` — a static, unchangeable list baked into genesis config — with no time bound, no admin override, and no alternative accounting path for a plain externally-owned account. The only other code path that moves `allowance` to `balance` without this check is `Program.withdrawRewardAndCancelVote`, but that is reachable only via smart-contract `SUICIDE`/self-destruct, which is inapplicable to a normal account: [4](#0-3) 

Consequently, if a genesis-witness address continues to (or later) receives votes and is elected as an active/standby witness — a process driven entirely by unprivileged voter behavior, not by the genesis witness itself — block/standby rewards keep accumulating into its `allowance` field forever, but there is no code path in the entire codebase to ever realize that value as spendable balance.

### Impact Explanation
This is a permanent, protocol-level fund lock affecting witness reward accounting: TRX that is credited via the reward-distribution mechanism (funded from network issuance/transaction fees) accrues in `AccountCapsule.allowance` for the affected address but can never be converted to `balance` and thus never spent, transferred, or recovered — through either the normal `WithdrawBalanceContract` transaction type or the TVM `withdrawreward` precompiled operation. Because the check is hardcoded against the genesis witness address set with no owner/admin override anywhere in the actuator or native-contract layer, the locked value is unrecoverable for the lifetime of the chain, constituting indefinite loss/corruption of witness reward accounting for that class of address.

### Likelihood Explanation
This does not require any privileged action or vulnerable configuration beyond an account address coinciding with a genesis witness continuing to participate in (or being voted into) the witness/standby-witness election, which is a normal, permissionless voting outcome. Because reward accrual (`payReward`) has no exemption for genesis-witness addresses while withdrawal is unconditionally blocked for them, the stuck-fund condition triggers automatically and deterministically whenever such an address earns any reward, with no additional attacker action needed.

### Recommendation
Add either: (a) a bounded, admin-gated emergency-sweep/redirect function for allowance accrued to guard-representative addresses, or (b) prevent `payReward`/`payStandbyWitness`/`adjustAllowance` from crediting `allowance` to genesis-witness addresses in the first place (mirroring the withdrawal-side restriction), so that value is never accrued somewhere it can never be released. Alternatively, allow withdrawal for genesis-witness addresses once they are demonstrably no longer part of the "GR" restricted set, or add an expiry/override mechanism consistent with the rest of the withdrawal-restriction logic (e.g., the 24-hour `witnessAllowanceFrozenTime` check already present for standard accounts).

### Proof of Concept
1. A genesis witness address `G` (present in `CommonParameter.getInstance().getGenesisBlock().getWitnesses()`) is voted in as an active or standby witness by unprivileged voters in a later cycle.
2. The block-producing/maintenance logic calls `MortgageService.payBlockReward`/`payStandbyWitness` → `payReward(G, value)`, which calls `adjustAllowance(G, brokerageAmount)`, incrementing `G.allowance` in `AccountStore`. [1](#0-0) 
3. Any attempt by `G` to broadcast a `WithdrawBalanceContract` transaction or call the TVM `withdrawreward` opcode fails validation with "is a guard representative and is not allowed to withdraw Balance", every single time, forever. [2](#0-1) [5](#0-4) 
4. `G.allowance` keeps growing across cycles with no code path anywhere in the repository capable of ever converting it to spendable `balance`, since `G` is not a contract and cannot trigger `SUICIDE`-based withdrawal. The value is permanently locked.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }

  public void validate(WithdrawRewardParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();

    boolean isGP = CommonParameter.getInstance()
        .getGenesisBlock().getWitnesses().stream().anyMatch(witness ->
            Arrays.equals(ownerAddress, witness.getAddress()));
    if (isGP) {
      throw new ContractValidateException(
          ACCOUNT_EXCEPTION_STR + StringUtil.encode58Check(ownerAddress)
              + "] is a guard representative and is not allowed to withdraw Balance");

  private void withdrawRewardAndCancelVote(byte[] owner, Repository repo) {
    VoteRewardUtil.withdrawReward(owner, repo);

    AccountCapsule ownerCapsule = repo.getAccount(owner);
    if (!ownerCapsule.getVotesList().isEmpty()) {
      VotesCapsule votesCapsule = repo.getVotes(owner);
      if (votesCapsule == null) {
        votesCapsule = new VotesCapsule(ByteString.copyFrom(owner),
            ownerCapsule.getVotesList());
      } else {
        votesCapsule.clearNewVotes();
      }
      ownerCapsule.clearVotes();
      ownerCapsule.setOldTronPower(0);
      repo.updateVotes(owner, votesCapsule);
    }
    try {
      long balance = ownerCapsule.getBalance();
      long allowance = ownerCapsule.getAllowance();
      ownerCapsule.setInstance(ownerCapsule.getInstance().toBuilder()
          .setBalance(addExact(balance, allowance, VMConfig.disableJavaLangMath()))
          .setAllowance(0)
          .setLatestWithdrawTime(getTimestamp().longValue() * 1000)
          .build());
      repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);
    } catch (ArithmeticException e) {
      throw new BytecodeExecutionException("Suicide: balance and allowance out of long range.");
    }
  }
