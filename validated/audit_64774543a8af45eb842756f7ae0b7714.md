The symbol `vm_status_of_result` referenced in the question does not exist anywhere in this repository — searches for that exact name and close variants (`status_of_result`, `fn vm_status_of_result`) return no matches. The actual analogous logic lives in `VMError::into_vm_status` in `third_party/move/move-binary-format/src/errors.rs`, which converts a `VMError` (major status code + sub-status + location) into a `VMStatus`.

Examining that function's logic:

- `VMStatus::Executed` is only produced when `major_status == StatusCode::EXECUTED` [1](#0-0) . `StatusCode::EXECUTED` is not a code that any error-construction path (`PartialVMError::new(...)`, native function failures, verifier failures, etc.) uses — it's reserved for the success sentinel and is never attacker-reachable via bytecode, transaction payloads, or Move abort codes.
- All genuine error paths (`ABORTED`, `Execution` status-type codes, and the fallback arm) map deterministically to `VMStatus::MoveAbort`, `VMStatus::ExecutionFailure`, or `VMStatus::Error` — never to `Executed` [2](#0-1) .
- Downstream, `VMStatus::keep_or_discard` further classifies these into `Keep`/`Discard`, and it only returns `KeptVMStatus::Executed` for the literal `VMStatus::Executed` variant; every other `StatusType` (`Validation`, `InvariantViolation`, `Unknown`) is explicitly discarded, and `Verification`/`Deserialization`/`Execution` types are kept as `MiscellaneousError` or `ExecutionFailure`, not `Executed` [3](#0-2) .
- `TransactionStatus::from_vm_status` in `types/src/transaction/mod.rs` mirrors this mapping and cannot mistakenly produce `Keep(ExecutionStatus::Success)` from a genuine error — that requires `vm_status == VMStatus::Executed` exactly, enforced by `from_executed_vm_status`'s explicit panic guard [4](#0-3) .

There is no code path by which an attacker-crafted transaction can produce a `VMError`/`VMResult::Err` that gets misclassified as `Executed`/success, because the `EXECUTED` status code is never assigned along any error construction path, and every genuine error status type is explicitly and exhaustively handled to either `Discard` or a non-success `Keep(ExecutionStatus::...)` variant.
