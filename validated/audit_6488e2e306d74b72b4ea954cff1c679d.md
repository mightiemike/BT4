## Title
`promise_batch_action_add_key_with_function_call` silently converts an explicit zero allowance into unlimited allowance - ([File: runtime/near-vm-runner/src/wasmtime_runner/logic.rs])

### Summary
The host function that lets a contract create a `FunctionCall`-permission access key via a promise batch action converts an explicitly-supplied allowance of `0` into `None`, which the protocol defines as **unlimited** allowance, instead of a maximally-restrictive (zero-spend) key. This mirrors the reported `MarginTrading.sol` pattern where the contract "defaults to approve `type(uint256).max`" regardless of the caller's intended, tighter amount.

### Finding Description
`FunctionCallPermission.allowance: Option<Balance>` is documented as: `None` means unlimited allowance, `Some(x)` is a hard balance/gas spending cap for that key [1](#0-0) . The verifier decrements this allowance in lockstep with the account balance and errors with `NotEnoughAllowance` once it is exhausted [2](#0-1) ; i.e. `Some(0)` should mean "this key can spend nothing" — a distinctly different, far more restrictive permission than `None` (unlimited).

However, the WASM host function that any contract can invoke to append an `AddKey` action with `FunctionCall` permission collapses these two very different states:

```rust
let allowance = Balance::from_yoctonear(get_u128(..., allowance_ptr)?);
let allowance = if allowance > Balance::ZERO { Some(allowance) } else { None };
``` [3](#0-2) 

Any contract call (reachable directly from a signed transaction executing a `FunctionCall` action) that passes `allowance = 0` when adding a function-call access key ends up creating a key with `allowance: None`, i.e. **unlimited** — the exact opposite of what a `0` value should represent. This value then flows into `append_action_add_key_with_function_call`, which stores whatever `Option<Balance>` it is given verbatim into the new access key's `FunctionCallPermission` [4](#0-3) , with no re-validation or re-interpretation at that layer.

This is a real, reachable behavior gap: a contract author (or a wrapper contract acting on behalf of users, analogous to `MarginTrading.sol`'s `_approveToken`) who intends to add a "dormant"/zero-spend function-call key — for example to register a key now and fund/enable it later, or to explicitly cap spending at zero as a safety default — instead grants that key unrestricted spending power over the account's entire balance for calls to the specified receiver/method set, silently and with no way for the caller to detect the substitution at call time.

### Impact Explanation
This breaks the intended access-control invariant of function-call access keys: a caller-specified "no spending" cap (`0`) is turned into "no spending limit" (`None`). Any account/contract that programmatically adds function-call keys with an allowance value that can be (or default to) `0` — including from untrusted or partially-trusted input — unintentionally grants a key unbounded ability to drain the account's $NEAR balance for gas/fees on transactions to the permitted `receiver_id`. This is an unauthorized-value-movement class bug: it does not require any malicious validator/peer, only a normal contract call constructing an `AddKey` promise action, which matches the required "concrete unauthorized value movement" / "invalid state transition acceptance" bar (an access key is created with permissions strictly broader than what was requested, and the affected account's balance can then be drained by that key's holder).

### Likelihood Explanation
High reachability: this is a single WASM host-function call available to any deployed contract, triggerable by a single transaction/contract call with no special privileges. The bug is deterministic (not timing- or state-dependent) — passing exactly `0` as the allowance parameter always produces this result. The main constraint on exploitability is that a contract must pass `0` as the allowance somewhere in its own logic (e.g., a default value, an uninitialized/zeroed buffer, or a case meant to represent "no allowance yet"), which is a plausible and common pattern for wrapper/relayer contracts managing access keys on behalf of users (directly analogous to the wallet-contract style code inspected in this repo, e.g. `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:488-495`, which itself performs the same `0 → Unlimited` collapse via `Allowance::limited(...).unwrap_or(Allowance::Unlimited)`).

### Recommendation
Do not conflate `allowance == 0` with `allowance == None` (unlimited) in `promise_batch_action_add_key_with_function_call`. Preserve the caller's explicit `Some(0)` as a truly zero-spend cap, and only produce `None` (unlimited) when the caller uses a distinct, unambiguous sentinel (e.g. a documented "no allowance parameter provided" convention rather than the numeric value `0`), matching the semantics already documented for `FunctionCallPermission::allowance`. Any SDK-level helper built on top of this host call (e.g. `Allowance::limited`) should be reviewed for the same 0→Unlimited coercion.

### Proof of Concept
1. Deploy a contract `Vulnerable` on account `V`.
2. `Vulnerable` exposes a method `add_key(pubkey, allowance_yocto: u128, receiver: AccountId)` that calls the promise-batch host function:
   `promise_batch_action_add_key_with_function_call(promise_idx, pubkey_len, pubkey_ptr, nonce, allowance_ptr, receiver_len, receiver_ptr, method_names_len, method_names_ptr)` with the `u128` at `allowance_ptr` set to `0` [5](#0-4) .
3. Any caller invokes `V.add_key(attacker_pubkey, 0, V)` intending to grant `attacker_pubkey` a function-call key with zero spending allowance on `V`.
4. Because of the `if allowance > Balance::ZERO { Some(allowance) } else { None }` conversion, the resulting `AccessKey` on `V` is created with `FunctionCallPermission.allowance = None` (unlimited) rather than `Some(0)`.
5. Query the access key via RPC (`view_access_key`) — it will show `allowance: null`, i.e. unlimited, confirming the substitution. `attacker_pubkey` can now sign transactions from `V` to `V` with gas/fees drawn without any cap from `V`'s balance, until `V`'s balance is exhausted — a direct, unauthorized value-movement outcome from a single contract call.

**Uncertainty**: I could not find the wasmer/near-vm-runner (non-wasmtime) implementation of the same host function in the indexed portion of the codebase to confirm whether it has the identical conversion or was already fixed there; a full audit should check all VM backends (`near-vm-runner` wasmer2/wasmtime) for the same pattern before remediation.

fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}
