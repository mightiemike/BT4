Confirmed the root-cause chain: `validateHmacFromRequestFactory` (`packages/apps/shopify-api/lib/utils/hmac-validator.ts`) computes the webhook HMAC over `rawBody` only, never over the `X-Shopify-Shop-Domain` header. The shop identity used everywhere downstream (`ensureValidOfflineSession(params, check.domain)` in `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts` and `packages/apps/shopify-app-react-router/.../webhooks/authenticate.ts`, plus `webhookCheck.domain` passed straight to app handlers in `packages/apps/shopify-api/lib/webhooks/process.ts`) is taken straight from the unauthenticated header, so a valid HMAC for one shop's payload can be replayed with a spoofed domain header to pull a different shop's offline session — this is the same "index/identifier decoupled from the authenticity check" root cause as the Coinbase `removeOwnerAtIndex` bug.

### Title
Webhook shop identity (`X-Shopify-Shop-Domain`) is not covered by the HMAC, allowing signed webhook payloads to be replayed against a different shop's offline session - (File: `packages/apps/shopify-api/lib/utils/hmac-validator.ts`, `packages/apps/shopify-api/lib/webhooks/validate.ts`, `packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts`)

### Summary
Shopify webhook authenticity is verified solely via `validateHmacFromRequestFactory`, which HMACs `rawBody` with the app's shared `apiSecretKey` and compares it to the `X-Shopify-Hmac-Sha256` header [1](#0-0) . The shop identifier (`X-Shopify-Shop-Domain`) used to select which merchant's session to act on is read separately from headers in `checkWebhooksHeaders`/`checkEventsHeaders` and is never part of the HMAC input [2](#0-1) . Because the app's `apiSecretKey` is shared across all shops that install the app, any merchant can capture a legitimate webhook (valid `hmac` + `rawBody` pair) delivered to their own store and replay it with the `domain` header changed to a victim shop.

### Finding Description
The HMAC only binds `rawBody`; nothing binds `domain`, `topic`, or `webhookId` to that signature. `checkWebhooksHeaders` simply extracts `domain` from the header and returns it as part of the "valid" result once the HMAC over the body checks out [2](#0-1) . Downstream consumers trust `check.domain`/`webhookCheck.domain` unconditionally:
- `authenticateWebhookFactory` (remix/react-router) calls `ensureValidOfflineSession(params, check.domain)` to fetch the offline session and attach an authenticated `admin` client for that shop [3](#0-2) .
- The low-level `process()` handler in `shopify-api` passes `webhookCheck.domain` straight into the app-registered callback as the shop parameter [4](#0-3) .

Since `apiSecretKey` is the same secret for every shop that installs a given app (it's the app's client secret, not a per-shop secret), a malicious merchant who has installed the app can:
1. Receive (or trigger, e.g. by updating a product) a legitimate webhook, capturing a valid `(rawBody, hmac)` pair.
2. Replay the exact same request to the app's webhook endpoint, only substituting `X-Shopify-Shop-Domain` with a victim shop's domain (and optionally other headers like `X-Shopify-Webhook-Id`/`X-Shopify-Topic`, which are also unauthenticated).
3. The HMAC check still passes (it only re-hashes `rawBody`), so the request is treated as "valid" for the victim shop.
4. `ensureValidOfflineSession`/`process()` loads and hands the victim shop's offline `Session` (with a real Admin API access token) to the app's webhook handler, which then executes business logic (e.g. `APP_UNINSTALLED` cleanup, order/fulfillment processing, inventory updates) using attacker-controlled body content but the victim's authenticated session.

This mirrors the Coinbase Smart Wallet bug's root cause: an unauthenticated "index"/identifier (there, the owner index; here, the shop domain header) is decoupled from the cryptographic proof, so a validly-signed action can be replayed to target a different, unintended entity.

### Impact Explanation
Depending on which webhook topics the app subscribes to, this enables cross-tenant impact against any shop that has installed the same app: an attacker-controlled webhook body is processed as if it legitimately originated from the victim shop, with the victim's offline access token available to the handler (e.g. via `admin` client in the webhook context). This can lead to unauthorized data mutations, spurious `APP_UNINSTALLED`/billing-related side effects, or corrupted app state for the victim shop, without the victim doing anything and without the attacker needing the app's secret key.

### Likelihood Explanation
Any shop can install a public app to obtain a valid `(body, hmac)` pair signed with the app's shared secret, since `apiSecretKey` is common to all installs. No privileged access or secret leakage is required — the attacker only needs their own (or any) legitimate app installation and the ability to send an arbitrary HTTP POST with modified headers.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the authenticity check rather than trusting the raw header value: e.g. incorporate `X-Shopify-Shop-Domain` into the HMAC-verified input (as Shopify's newer "Events" style headers begin to do via `eventId`), or independently verify that the resolved shop actually has an active, matching installation/session before trusting `check.domain`/`webhookCheck.domain` for session lookup, and reject any mismatch between the expected shop context (if known) and the header-supplied domain.

### Proof of Concept
1. Merchant A installs the target app; Shopify (or the merchant, via a triggered event) sends a webhook to the app's endpoint with a body `B`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, and `X-Shopify-Hmac-Sha256: HMAC(apiSecretKey, B)`.
2. Attacker (Merchant A) intercepts/records this exact `(B, hmac)` pair.
3. Attacker sends a new POST to the same webhook endpoint with identical body `B` and `hmac`, but `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
4. `validateHmacFromRequestFactory` recomputes `HMAC(apiSecretKey, B)` and it matches, so `checkWebhooksHeaders` returns `valid: true` with `domain: 'shop-victim.myshopify.com'` [5](#0-4) .
5. `authenticateWebhookFactory` loads `shop-victim`'s offline session via `ensureValidOfflineSession(params, 'shop-victim.myshopify.com')` and invokes the app's webhook handler with that session, processing attacker-controlled body `B` under the victim's identity [6](#0-5) .
