### Title
Exchange pool negative-balance invariant check is skipped unless `hardenedCalc`/`allowHarden` is enabled - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
`ExchangeCapsule.transaction()` computes new pool balances (`newFirstTokenBalance`/`newSecondTokenBalance`) after a trade, but only validates that these results are non-negative when `hardenedCalc` (aka `allowHarden`) is `true`: [2](#0-1) 

When `hardenedCalc` is `false` (the legacy/default path used whenever `allowHarden()` returns false, i.e. before the corresponding proposal is activated on-chain, or whenever callers don't pass `true`), the identical negative-balance corruption check is completely absent — mirroring the report's pattern where a critical post-operation invariant check is placed only inside one conditional branch and skipped for the other.

### Finding Description
This method is invoked from `ExchangeTransactionActuator.doValidate()` and `ExchangeWithdrawActuator`/`ExchangeInjectActuator` execution paths, which pass `dynamicStore.allowStrictMath()` and `allowHarden()` as parameters: [3](#0-2) 

`allowHarden()` is gated by a chain parameter/proposal (`AllowHardenExchangeCalculation`), so on any network where that proposal has not been passed (or for any legacy transaction path that calls `transaction(sellTokenID, sellTokenQuant, useStrictMath)` without the hardened flag, which defaults `hardenedCalc` to `false`), the balance-underflow check at line 160 never executes: [4](#0-3) 

In the legacy branch, `newFirstTokenBalance`/`newSecondTokenBalance` are computed with plain `long` arithmetic (no `addExact`/`subtractExact` overflow checks and no negative-balance validation), so a corrupted or extreme pool state (e.g., via repeated small trades that exploit integer-division rounding, or a state reached through another code path) can drive one side of the exchange pool balance negative and persist it via `Commons.putExchangeCapsule(...)`, corrupting the on-chain TRC10 exchange pool used by `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`.

### Impact Explanation
A negative pool balance breaks the AMM invariant relied upon by all subsequent exchange operations (trade, inject, withdraw), potentially enabling further exploitation (e.g., additional trades computed against a corrupted balance) or causing incorrect token accounting/asset issuance on TRC10 tokens and TRX held in the exchange contract. This is reachable directly from broadcast transactions (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) without any privileged role, since `ExchangeTransactionActuator.validate()` calls `exchangeCapsule.transaction(...)` and persists results unconditionally when the hardened check doesn't fire.

### Likelihood Explanation
Likelihood depends on whether `AllowHardenExchangeCalculation`/`allowHarden()` has been activated on the target network and whether any legacy call site invokes `transaction(...)` without `hardenedCalc=true`. On networks/paths where the hardened flag is not set, the invariant check is unconditionally bypassed, matching the reported bug class precisely. I could not fully confirm within the available context whether `allowHarden()` is unconditionally `true` on the current mainnet/testnet default (this needs runtime configuration verification), so the exploitability is contingent on that chain parameter's state — this is the primary uncertainty in this finding.

### Recommendation
Move the non-negative balance invariant check (and ideally overflow-safe arithmetic) outside the `hardenedCalc` conditional so it is enforced unconditionally for both the legacy and hardened calculation paths in `ExchangeCapsule.transaction()`.

### Proof of Concept
1. Ensure the network has not activated `AllowHardenExchangeCalculation` (or invoke a code path that calls the 3-argument `transaction(sellTokenID, sellTokenQuant, useStrictMath)` overload, which defaults `hardenedCalc` to `false`). [4](#0-3) 
2. Broadcast repeated `ExchangeTransactionContract`/`ExchangeWithdrawContract` transactions engineered (via rounding in `Processor.exchange`) to drive one side of the pool balance toward/below zero.
3. Because `hardenedCalc` is `false`, the check at line 160 is skipped, and the corrupted balances are persisted via `Commons.putExchangeCapsule(...)`, verifiable by reading back the exchange pool's `getFirstTokenBalance()`/`getSecondTokenBalance()` and observing a negative value.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
