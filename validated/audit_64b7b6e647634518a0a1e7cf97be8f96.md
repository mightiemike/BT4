Missing slippage/minimum-output protection in `ExchangeWithdrawActuator` allows LP withdrawers to receive fewer counter-asset tokens than expected - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` (TRON's on-chain bancor-style AMM "Exchange" withdraw operation) computes the counter-asset amount (`anotherTokenQuant`) purely from the exchange's live pool ratio at execution time, with no user-supplied minimum-acceptable-amount parameter, unlike its sibling actuator for swaps.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum field [1](#0-0) . Contrast this with `ExchangeTransactionContract`, the swap contract, which explicitly includes an `expected` field for slippage protection [2](#0-1) .

In `ExchangeWithdrawActuator.execute`, the counter-asset amount `anotherTokenQuant` is derived on-the-fly from the current `firstTokenBalance`/`secondTokenBalance` ratio of the exchange pool and immediately paid out to the withdrawer, with no comparison against any user-specified floor: [3](#0-2) 

`doValidate()` similarly recomputes `anotherTokenQuant` from the live pool balances and only checks that it is `> 0` and that the pool has sufficient balance — it never checks it against a user-defined minimum: [4](#0-3) 

Because Tron's `Exchange` object is a bancor-relay AMM whose `firstTokenBalance`/`secondTokenBalance` ratio moves with every `ExchangeTransactionContract` swap that gets included in prior transactions of the same block/preceding blocks, a withdrawer's expected payout ratio can shift between the moment they broadcast `ExchangeWithdrawContract` and the moment it is actually packed into a block and executed — exactly the class of issue flagged in the referenced report for `withdraw_liquidity`.

### Impact Explanation
A withdrawer submitting an `ExchangeWithdrawContract` has no way to bound the amount of the counter asset (`anotherTokenQuant`) they are willing to accept. If the pool ratio moves unfavorably before the transaction executes — whether due to organic trading activity or a block producer/validator sandwiching the withdrawal with swap transactions they control — the user can receive materially less value than anticipated with no recourse (the transaction still succeeds because the only floor check is `anotherTokenQuant > 0` and sufficient pool balance). This is an accounting/economic-loss issue for LPs of Tron's built-in `Exchange` (TRC10 bancor pools), not a consensus-breaking bug, and is unprivileged/reachable by any account holding exchange balance via a normal broadcast transaction.

### Likelihood Explanation
Likelihood is bounded by two factors: (1) usage of the legacy on-chain `Exchange`/bancor market feature is limited in practice compared to TRC20 DEX contracts running in the TVM, and (2) exploiting it for maximal effect (sandwiching) requires an actor able to order transactions favorably (e.g., an SR/block producer), which is a stronger assumption than a purely permissionless attacker, though ordinary market volatility alone can also trigger the loss for any user without any attacker at all — this matches the "low severity, common good-practice gap" characterization given to the analogous Mantra DEX finding.

### Recommendation
Add an optional minimum-expected-amount field to `ExchangeWithdrawContract` (mirroring the existing `expected` field already present in `ExchangeTransactionContract`), and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the withdrawal (`ContractValidateException`) if the computed `anotherTokenQuant` is below the caller-supplied minimum. Users who want unconditional withdrawal can simply set the minimum to `0`.

### Proof of Concept
1. User A holds an `Exchange` (id=1) with `firstTokenBalance` = 100,000,000 and `secondTokenBalance` = 200,000,000, and is its `creator_address` (only the creator can withdraw, per [5](#0-4) ).
2. User A broadcasts `ExchangeWithdrawContract{exchange_id=1, token_id=firstTokenID, quant=1,000,000}`, expecting to receive `secondTokenBalance * quant / firstTokenBalance` = 2,000,000 of the second token.
3. Before this transaction is packed, a block producer (or any actor) inserts `ExchangeTransactionContract` swaps against the same exchange that shift the ratio (e.g., dumps `firstToken` into the pool), reducing `secondTokenBalance` relative to `firstTokenBalance`.
4. When the withdrawal executes, `anotherTokenQuant` in `ExchangeWithdrawActuator.execute` (lines 79-80) is recomputed against the now-worse ratio and paid out — potentially far below the 2,000,000 the user expected — and the transaction still succeeds because there is no minimum-output check, only the `anotherTokenQuant > 0` guard in `doValidate()` (lines 225-227).

**Uncertainty note:** I was unable to fully confirm from the index whether `ExchangeTransactionActuator.java`'s use of the `expected` field is enforced with a strict comparison operator (my last grep for "expected" in that file returned no matches, likely due to index truncation of that file's contents); this doesn't affect the core finding on `ExchangeWithdrawActuator`/`ExchangeWithdrawContract`, which is directly confirmed to lack any such field or check, but a full review of `ExchangeTransactionActuator`'s enforcement logic would benefit from a Devin session with full file access if deeper comparison is needed.
