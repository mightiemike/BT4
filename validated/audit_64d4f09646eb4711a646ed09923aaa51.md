### Title
DoS via unauthenticated `triggerconstantcontract` calls exhausting the `rpc-full-executor` thread pool through calibrated CPU-bound contract execution - ([File: framework/src/main/java/org/tron/core/services/RpcApiService.java])

### Summary
`triggerconstantcontract` is an unauthenticated, feeless RPC entry point that runs arbitrary attacker-supplied bytecode inside `VMActuator.execute` on a pooled `rpc-full-executor` gRPC thread, with a per-call CPU deadline set by `VMActuator.calculateCpuLimitInUs` (`constantCallTimeoutMs` if configured, otherwise the network's `maxCpuTimeOfOneTx`). An attacker can craft a contract whose loop runs for close to that deadline and fire many concurrent calls to occupy every thread in the fixed-size RPC executor pool, starving other gRPC calls served by the same server/pool.

### Finding Description
The call chain is: gRPC `WalletApi`/`WalletSolidityApi`.`triggerConstantContract` → `RpcApiService.callContract(..., isConstant=true)` → `Wallet.triggerConstantContract` → `Wallet.callConstantContract` → `VMActuator.validate/execute` [1](#0-0) [2](#0-1) [3](#0-2) . This path requires no signature/permission checks (no `validateSignature` or owner-permission enforcement is invoked for constant calls) and no fee is charged since it's not broadcast — it only requires that the target contract exist. Deployment of a new attacker contract is also reachable in-line through this same API when `contractAddress` is empty (in-place "deploy and call" for constant execution), so the attacker doesn't even need a prior committed transaction [4](#0-3) .

Inside VM execution, the per-call CPU deadline is computed by `VMActuator.calculateCpuLimitInUs`: for constant calls it uses `constantCallTimeoutMs` (config value) if configured (>0) verbatim, otherwise falls back to `maxCpuTimeOfOneTx * cpuLimitInUsRatio` (the same deadline used for block-processing transactions) [5](#0-4) . This deadline is computed identically for both the `create()` and `call()` code paths and fed into `ProgramInvokeFactory.createProgramInvoke` as `vmShouldEndInUs` [6](#0-5) [7](#0-6) . Because `constantCallTimeoutMs` (or the fallback `maxCpuTimeOfOneTx`) is a fixed, publicly-known value, an attacker can calibrate a contract loop (e.g., a tight SSTORE/hashing loop) to run right up to — but not exceed — that deadline on every invocation, guaranteeing each call occupies the executing thread for close to the maximum allowed time without erroring out as `OutOfTimeException`.

Since the gRPC server executor (`rpc-full-executor`) is a plain fixed-size thread pool sized by `rpcThreadNum` [8](#0-7) , and this same executor and gRPC server also serve unrelated RPC calls (e.g., `getNowBlock`, other wallet queries), saturating it with N ≥ `rpcThreadNum` concurrent long-running constant calls will starve legitimate, unrelated RPC traffic for the duration of the deadline, repeatedly, at effectively zero cost — no fee, no energy consumption is charged for constant calls, and existing checks (`validateSignature`, actuator `validate()`, energy accounting) do not gate this path since constant calls bypass broadcast/consensus economics by design (`callConstantContract` only calls `vmActuator.validate/execute`, no fee deduction) [9](#0-8) .

Rate limiting exists (`RateLimiterInterceptor`), but it is a request-rate limiter, not a CPU-time/concurrency budget; it does not inherently prevent an attacker from opening `rpcThreadNum` concurrent slow-executing connections within the allowed request rate, especially if the limiter is per-IP/per-method count-based rather than time-weighted. There is no visible mechanism in this code path that caps aggregate constant-call CPU time across concurrent requests or isolates constant-call execution onto a separate, smaller-impact thread pool from the one serving all other gRPC APIs (`databaseApi`, `walletApi`, `walletSolidityApi`, `monitorApi` all share the same `serverBuilder.executor(this.executorService)` per `RpcService.initServerBuilder`) [10](#0-9) [11](#0-10) .

### Impact Explanation
This matches the "DoS via RPC-API" bounty impact class: a node's gRPC service (used for block/transaction queries and broadcast by wallets, exchanges, and other infrastructure) can be stalled or made unresponsive for legitimate callers while an unprivileged attacker pays nothing (constant calls are feeless/energy-free by design). This does not corrupt consensus state or steal funds; it is a node-level availability degradation, scoped to whichever fullnode/solidity node exposes the RPC/gRPC API to the attacker.

### Likelihood Explanation
Preconditions: `supportConstant` must be enabled on the target node (this is the documented purpose of the constant-call feature and commonly enabled on public/community fullnodes to support dApp read calls) [12](#0-11) . The attacker needs no funded account with resources beyond what's needed to open gRPC connections and pass `Util`/`DecodeUtil` basic format validation; no fee is charged for constant calls. Calibrating a loop to approach the timeout (whether the default `maxCpuTimeOfOneTx`-derived value or an operator-configured `constantCallTimeoutMs`) is straightforward via local testing against the same TVM implementation (open source), and the attack is fully repeatable — each request can be reissued indefinitely at no cost. The only variable is the size of `rpcThreadNum`/`maxConcurrentCallsPerConnection`, which bounds how many concurrent connections are needed, but does not prevent the attack, only affects its cost in number of connections.

### Recommendation
- Enforce a hard cap on constant-call CPU deadline independent of `maxCpuTimeOfOneTx`/`constantCallTimeoutMs`, e.g., a short fixed ceiling regardless of operator config, and validate `constantCallTimeoutMs` against a conservative maximum at config load (`VmConfig.postProcess`) rather than only checking it's non-negative and within `Long.MAX_VALUE/1000`.
- Route constant-call execution (`triggerconstantcontract`, `estimateenergy`, `eth_call`, `eth_estimateGas`) through a separate, bounded-size executor/thread pool distinct from the one serving block/query gRPC methods, so saturating it cannot starve unrelated API calls.
- Add a global/per-IP concurrency limiter (in-flight constant-call count) in addition to the existing rate limiter, since the existing `RateLimiterInterceptor` is request-count based and does not account for CPU-time-weighted load.
- Consider requiring a lightweight cost/priority mechanism (e.g., queuing with timeout, or per-connection concurrent constant-call limit) for constant calls given they are explicitly fee-free.

### Proof of Concept
1. Deploy a contract (via `triggerconstantcontract` deploy-and-call or a prior `CreateSmartContract`) with a function containing a tight loop tuned to consume close to the node's constant-call CPU deadline, e.g.:
```solidity
function burn() public view returns (uint256) {
    uint256 x = 0;
    for (uint256 i = 0; i < N; i++) { x += i; } // N calibrated via binary search against target deadline
    return x;
}
```
2. Locally calibrate `N` by repeatedly calling `triggerconstantcontract` against the target's `burn()` and measuring `energy_used`/latency until the call reliably finishes just under the deadline without triggering `OutOfTimeException` (visible as `CONTRACT_EXE_ERROR`/`Program$OutOfTimeException` in the response, per `Wallet.callConstantContract`) [13](#0-12) .
3. Launch `N_conn > rpcThreadNum` concurrent gRPC clients, each repeatedly invoking `triggerconstantcontract(burn())` in a tight loop.
4. Concurrently issue `getNowBlock` (or other unrelated) gRPC calls and measure response latency/timeouts.
5. Expected result: while the attack is running, `getNowBlock` and other RPC calls queue behind the exhausted `rpc-full-executor` pool, showing significantly increased latency or client-side timeouts, demonstrating pool-wide starvation caused entirely by fee-free constant calls.

      Builder builder, Return.Builder retBuilder, boolean isEstimating)
      throws ContractValidateException, ContractExeException, HeaderNotFound, VMIllegalException {

    if (!Args.getInstance().isSupportConstant()) {
      throw new ContractValidateException("this node does not support constant");
    }

    Block headBlock;
    List<BlockCapsule> blockCapsuleList = chainBaseManager.getBlockStore()
        .getBlockByLatestNum(1);
    if (CollectionUtils.isEmpty(blockCapsuleList)) {
      throw new HeaderNotFound("latest block not found");
    } else {
      headBlock = blockCapsuleList.get(0).getInstance();
    }

    BlockCapsule headBlockCapsule = new BlockCapsule(headBlock);
    TransactionContext context = new TransactionContext(headBlockCapsule, trxCap,
        StoreFactory.getInstance(), true, false);
    VMActuator vmActuator = new VMActuator(true);

    try {
      vmActuator.validate(context);
      vmActuator.execute(context);
    } finally {
      // constant call runs on a pooled RPC worker; drop its thread-local VM config view so it
      // can never leak into a later (block/broadcast) execution on the same thread.
      VMConfig.clearLocalSnapshot();
    }

  static long calculateCpuLimitInUs(boolean isConstantCall, long maxCpuTimeOfOneTxMs,
      double cpuLimitInUsRatio, long constantCallTimeoutMs) {
    if (isConstantCall && constantCallTimeoutMs > 0L) {
      return constantCallTimeoutMs * VMConstant.ONE_THOUSAND;
    }
    return (long) (maxCpuTimeOfOneTxMs * VMConstant.ONE_THOUSAND * cpuLimitInUsRatio);
  }
