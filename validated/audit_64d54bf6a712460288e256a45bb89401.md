### Title
BURN_TRX_AMOUNT/blackhole balance divergence via TVM SUICIDE redirect to black-hole address - ([File: chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java])

### Summary
When `ALLOW_BLACKHOLE_OPTIMIZATION` is enabled, all TRX-fee/burn paths in actuators (`TransferActuator`, `TransferAssetActuator`, `CreateAccountActuator`, `ResourceProcessor`, memo/multisign fee handling, `ReceiptCapsule`) are gated with `dynamicStore.supportBlackHoleOptimization()` and route burnt value through `DynamicPropertiesStore.burnTrx()`/`saveBurnTrx()` instead of crediting the black-hole account's balance. However, the TVM `SUICIDE` implementation in `Program.suicide()` always credits the black-hole (or any obtainer) address's real balance directly via `getContractState().addBalance(...)`/`MUtil.transfer(...)`, with no check of `supportBlackHoleOptimization()` at all.

### Finding Description
`Program.suicide()` has two code paths that can route contract value to the black-hole address:
1. Self-destruct-to-self case: `getContractState().addBalance(blackHoleAddress, balance)` (only when `VMConfig.allowTvmTransferTrc10()`), used for TRC10 transfer, but note the base `balance` deduction from owner is unconditional zeroing.
2. Explicit obtainer case: when the attacker sets `obtainer` to the black-hole address explicitly (a normal, unprivileged CALL argument to `SUICIDE`), `MUtil.transfer(getContractState(), owner, obtainer, balance)` is invoked, which is a pure `addBalance`/`addBalance(-amount)` pair with **no burn accounting whatsoever**. Compare this to every other burn-fee path in the codebase, which is consistently gated: [3](#0-2) [4](#0-3) 

And the accounting primitive itself: [5](#0-4) 

Because `SUICIDE`'s value transfer to the black hole never calls `burnTrx()`, an unprivileged attacker can deploy and fund a contract, then execute `SUICIDE(blackHoleAddress)` — an entirely public, self-triggered opcode requiring no special permission — and the black-hole account's actual on-chain balance will increase by the contract's balance while `BURN_TRX_AMOUNT` (queried via `getBurnTrxAmount()`/exposed through `/wallet/getburntrx`, gRPC `getBurnTrxCommon`, and on-chain-callable via `GetBurnTrxServlet`) remains unchanged for that amount. [6](#0-5) 

This is a genuine invariant violation: with `ALLOW_BLACKHOLE_OPTIMIZATION` enabled, the intended invariant is that black-hole balance stays fixed at the point optimization was activated and all further burns are tracked exclusively via `BURN_TRX_AMOUNT`; total burnt supply is meant to be computed as `blackhole_balance_at_activation + getBurnTrxAmount()`. `SUICIDE`'s direct balance credit breaks this by causing the black-hole balance to keep growing post-activation while `BURN_TRX_AMOUNT` does not reflect that growth, causing `BURN_TRX_AMOUNT` to systematically under-report actual cumulative burn whenever contracts self-destruct to the black hole.

The `FreezeV2Test.testSuicideToBlackHole` test (line 570-580) exercises exactly this call path (`suicide(owner, contract, contract)`) but, based on the visible helper implementations, does not appear to assert equality between `getBurnTrxAmount()` delta and black-hole balance delta — it only validates freeze/resource bookkeeping, not the burn-supply invariant. I was not able to locate the body of the shared `suicide(...)` helper used by that test within the available index, so I cannot confirm with certainty whether any burn-amount assertion already exists there; this should be verified directly in the repository.

### Impact Explanation
Any downstream logic that computes circulating/total supply as `TOTAL_SUPPLY - getBurnTrxAmount()` (rather than directly re-deriving from the black-hole account balance) will overstate true circulating supply by the amount routed through `SUICIDE` to the black hole after `ALLOW_BLACKHOLE_OPTIMIZATION` was enabled. Conversely, if any logic assumes black-hole balance reflects only `BURN_TRX_AMOUNT`-independent legacy burns, the divergence corrupts that assumption too. This is purely an accounting/state-divergence issue (matches the "invalid state/divergence" acceptance criterion), not a direct value-theft or fund-freeze bug — no attacker gains extra TRX; the black hole still correctly receives and permanently locks the burnt value. The impact is limited to the accuracy of the on-chain `BURN_TRX_AMOUNT` counter and any service/API/computation relying on it.

### Likelihood Explanation
- Precondition: `ALLOW_BLACKHOLE_OPTIMIZATION` must be enabled via committee proposal (`ProposalService.process`, case `ALLOW_BLACKHOLE_OPTIMIZATION`) — this is a governance action, not attacker-controlled, but is an explicitly stated precondition of the question and is a real, already-supported network feature.
- Once enabled, exploitation requires only unprivileged, standard actions: deploy a contract, fund it with a `TransferContract`/deployment value, and call a function that executes `SUICIDE` with the black-hole address as the target — fully reachable by any account, at any time, deterministically and repeatably, matching the exact call sequence in `FreezeV2Test.testSuicideToBlackHole`.
- The divergence is 100% reproducible every time `SUICIDE`-to-blackhole is invoked while the optimization is active.

### Recommendation
In `Program.suicide()` (and the analogous `suicide2()` if it ever permits blackhole obtainer), branch on `getContractState().getDynamicPropertiesStore().supportBlackHoleOptimization()` when the resolved obtainer/inheritor address equals the black-hole address: instead of `MUtil.transfer(...)` / direct `addBalance(blackHoleAddress, ...)`, deduct the balance from the owner and call `dynamicPropertiesStore.burnTrx(balance)` so that `BURN_TRX_AMOUNT` and black-hole balance remain consistent, mirroring the pattern already used in `TransferActuator`, `TransferAssetActuator`, `ResourceProcessor`, and `ReceiptCapsule`.

### Proof of Concept
```java
// Integration test, mirroring FreezeV2Test.suicide() pattern
@Test
public void testSuicideToBlackHoleBurnAccountingDivergence() throws Exception {
  dbManager.getDynamicPropertiesStore().saveAllowBlackHoleOptimization(1L);

  byte[] blackHole = dbManager.getAccountStore().getBlackhole().getAddress().toByteArray();
  long blackHoleBalanceBefore = dbManager.getAccountStore().getBlackhole().getBalance();
  long burnAmountBefore = dbManager.getDynamicPropertiesStore().getBurnTrxAmount();

  byte[] contract = deployContract("TestFreezeV2", FREEZE_V2_CODE);
  long fundedValue = 1_000_000_000L;
  // fund the contract with `fundedValue` TRX via TransferContract or constructor value

  // trigger SUICIDE(blackHole) from within the contract
  suicide(owner, contract, blackHole);

  long blackHoleBalanceAfter = dbManager.getAccountStore().getBlackhole().getBalance();
  long burnAmountAfter = dbManager.getDynamicPropertiesStore().getBurnTrxAmount();

  long blackHoleDelta = blackHoleBalanceAfter - blackHoleBalanceBefore;
  long burnDelta = burnAmountAfter - burnAmountBefore;

  // Invariant expected: burnDelta should equal blackHoleDelta (all value irrevocably
  // sent to black hole should be reflected in BURN_TRX_AMOUNT once optimization is on)
  Assert.assertEquals("BURN_TRX_AMOUNT must track all value sent to black hole",
      blackHoleDelta, burnDelta);
  // Actual observed behavior: blackHoleDelta == fundedValue, burnDelta == 0,
  // demonstrating the divergence.
}
```
