### Title
Pre-existing account state (votes, self-frozen TRON Power/resources) is not cleared when `HistoryBlockHashUtil.deploy()` converts a normal account into the TIP-2935 system contract at a predictable address - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
`HistoryBlockHashUtil.deploy()` upgrades a pre-existing normal account at the fixed, publicly-known address `HISTORY_STORAGE_ADDRESS` into a contract account, but only calls `account.updateAccountType(Contract)` and `account.clearDelegatedResource()` [1](#0-0)  before persisting it. It never clears votes (`clearVotes()`), self-frozen V1 balances (`clearOwnerFreeze`-style reset), or FreezeV2 state (`clearFrozenV2`), unlike other code paths in the codebase that explicitly perform all of these resets together when an account's resource/voting state must be invalidated (e.g. `Program.suicide2` calling `withdrawRewardAndCancelVote`, `clearOwnerFreeze`, `clearOwnerFreezeV2`) [2](#0-1) .

### Finding Description
`HISTORY_STORAGE_ADDRESS` is a fixed, deterministic 21-byte address known to everyone in advance (`410000f90827f1c53a10cb7a02335b175320002935`) [3](#0-2) , exactly like the address-prediction primitive exploited in the Astaria report (CREATE-derived addresses are computable before the contract is deployed). Before the TIP-2935 proposal activates, this address is a completely ordinary account — anyone can send it TRX (creating an implicit normal account) and, crucially, anyone can perform account operations that only require the address to already *exist as a normal account*, such as delegating frozen resources to it (`DelegateResourceContract`/old `FreezeBalanceContract` "for other"), or by having others cast votes toward it (once it becomes a witness) or accumulating a votes list state, or freezing V2 resources tied to it via delegation.

When the proposal activates, `deploy()` detects the pre-existing account and "upgrades" it in place to preserve balance/asset state, exactly mirroring the CREATE2 collision-handling branch in `Program.createContractImpl` [4](#0-3) . However it copies only the narrower `clearDelegatedResource()` call and omits:
- `accountCapsule.clearVotes()` — leaving any votes list associated with the now-contract account inconsistent with `VotesStore`, the same class of "stale accounting counter" bug as Astaria's un-updated `liensOpenForEpoch`.
- FreezeV2 state cleanup (`clearFrozenV2`, `clearUnfrozenV2`, usage counters) — a delegator who delegated FreezeV2 resources to the address before activation may end up with un-reclaimable or double-counted TRON Power/resource accounting once the address becomes a contract, because the resource/energy/bandwidth accounting invariants for contract accounts differ from normal accounts.
- Self-frozen V1 balance (bandwidth/energy) — if the address had frozen balance for itself, it is preserved without being reconciled against contract-account resource semantics.

This is the direct java-tron analog of the Astaria vulnerability: state (accounting counters tied to a resource/lien system) that is set up against a predictable address *before* that address becomes a privileged/contract account is not reset/reconciled at contract-creation time, allowing corrupted downstream accounting (unfreeze/undelegate failures, vote-count desynchronization between `AccountCapsule` and `VotesStore`) once the address is finalized as a contract.

### Impact Explanation
If exploited, the delegator of resources/votes toward `HISTORY_STORAGE_ADDRESS` could end up in a state where:
- Their delegated/self-frozen resources cannot be cleanly withdrawn (`UnDelegateResourceActuator`/`UnfreezeBalanceV2Actuator` operate on assumptions that don't hold for a freshly-converted contract account), potentially locking user funds/resources — a direct asset/accounting corruption and DoS on the affected user's ability to reclaim frozen TRX.
- `VotesStore` and `AccountCapsule.votesList` can diverge for the address, corrupting on-chain vote tallying used in consensus/SR election bookkeeping.

Because `HISTORY_STORAGE_ADDRESS` is a single fixed system address activated once at proposal time, the blast radius is limited to whoever interacts with that specific address before activation, but the accounting corruption is a genuine and permanent (until manually reconciled) chain-state defect once triggered.

### Likelihood Explanation
Reaching this address requires no privileged access — any account can send a `DelegateResourceContract`/legacy `FreezeBalanceContract` "for other" transaction naming `HISTORY_STORAGE_ADDRESS` as recipient, or otherwise interact with it as a normal account, at any point before the TIP-2935 proposal is activated (`deploy()` is only invoked once at proposal-activation maintenance time, per the class's own documentation) [5](#0-4) . The address and the activation mechanism are public knowledge, so the pre-condition (someone interacting with the address in advance) is trivially satisfiable by any unprivileged user, making likelihood moderate-to-high assuming the proposal is expected to activate on a live network with public knowledge of the target address in advance.

### Recommendation
In `HistoryBlockHashUtil.deploy()`, when `accountExisting` is true, fully reconcile all resource/voting state before flipping the account to `Contract` type, not just delegated-resource fields:
- Clear `votesList` and synchronize/clear the corresponding `VotesStore` entry.
- Clear FreezeV2 state (`clearFrozenV2`, `clearUnfrozenV2`, usage/window counters) in addition to `clearDelegatedResource()`.
- Consider rejecting/deferring the upgrade (similar to the foreign-code check already done for `CodeStore`/`ContractStore`) if the pre-existing account has any non-trivial resource/vote state that cannot be safely reconciled, rather than silently converting it while leaving stale accounting fields in place.

### Proof of Concept
1. Before the TIP-2935 proposal is activated, an unprivileged user submits a `DelegateResourceContract` (or a legacy "freeze for other") transaction delegating bandwidth/energy resources to `HISTORY_STORAGE_ADDRESS` (`410000f90827f1c53a10cb7a02335b175320002935`), creating an implicit normal `AccountCapsule` at that address with populated delegated-resource/vote-related fields.
2. The committee/maintenance process activates the TIP-2935 proposal, triggering `HistoryBlockHashUtil.deploy(manager)` [6](#0-5) .
3. `deploy()` finds `accountExisting == true`, calls only `updateAccountType(Contract)` and `clearDelegatedResource()`, and persists the account — any votes list or FreezeV2 state on the account is left untouched.
4. The original user who delegated resources/votes to the address attempts to reclaim them via `UnDelegateResourceActuator`/`UnfreezeBalanceV2Actuator`; because the target account is now a `Contract`-type account with inconsistent leftover accounting fields, the reclaim path can fail or behave inconsistently with the account's true state, mirroring the Astaria scenario where the borrower could not repay/reclaim due to un-reset accounting counters at a preemptively-funded predictable address.

      logger.warn("TIP-2935: foreign state at {}, skipping deploy",
          Hex.toHexString(HISTORY_STORAGE_ADDRESS));

    manager.getCodeStore().put(HISTORY_STORAGE_ADDRESS,
        new CodeCapsule(HISTORY_STORAGE_CODE));

        new ContractCapsule(HISTORY_STORAGE_CONTRACT));

    AccountCapsule account = manager.getAccountStore().get(HISTORY_STORAGE_ADDRESS);
    boolean accountExisting = account != null;
    if (!accountExisting) {
      account = new AccountCapsule(HISTORY_STORAGE_ACCOUNT);
    } else {
      account.updateAccountType(Protocol.AccountType.Contract);
      account.clearDelegatedResource();
    }
    manager.getAccountStore().put(HISTORY_STORAGE_ADDRESS, account);
