### Title
`UnfreezeBalanceProcessor.execute` decrements `TotalNetWeight`/`TotalEnergyWeight` inconsistently with how they are credited, corrupting the network-wide resource-weight accounting - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java)

### Summary
`org.tron.core.store.DynamicPropertiesStore.getTotalNetWeight()`/`getTotalEnergyWeight()` are global aggregates that are supposed to equal the sum of every account's individual frozen-balance-derived weight, exactly like ZeroLend's `totalSupply.supplyShares` is supposed to equal the sum of every position's `balances.supplyShares`. Just as ZeroLend's `PoolLogic::executeMintToTreasury` decremented the global `supplyShares` using an assumption ("shares were minted") that was never reflected in any account balance, java-tron's TVM native `UnfreezeBalanceProcessor.execute` decrements the global weight using a formula (`unfreezeBalance / TRX_PRECISION`) that does not match the formula used everywhere else in the codebase to credit/debit this same aggregate (`newWeight - oldWeight`, gated by `dynamicStore.allowNewReward()`), causing the aggregate to diverge from the true sum of per-account weights.

### Finding Description
`DynamicPropertiesStore.addTotalNetWeight`/`addTotalEnergyWeight` are the single choke points that mutate the global weight counters: [1](#0-0) 

Every other actuator that changes an account's frozen balance computes the delta consistently as `newWeight - oldWeight` derived from the account's actual frozen balance, and (when `allowNewReward()` is enabled) feeds that exact delta into `addTotalNetWeight`/`addTotalEnergyWeight`:
- `FreezeBalanceActuator.addTotalWeight` uses `increment` (the real `newNetWeight - oldNetWeight`) when `allowNewReward()`: [2](#0-1) 
- `UnfreezeBalanceActuator` computes `decrease = newNetWeight - oldNetWeight` and only falls back to `-unfreezeBalance / TRX_PRECISION` when `allowNewReward()` is false: [3](#0-2) 
- `FreezeBalanceV2Actuator` / `UnfreezeBalanceV2Actuator` / `FreezeBalanceV2Processor` / `UnfreezeBalanceV2Processor` / `CancelAllUnfreezeV2Actuator` all uniformly use `newWeight - oldWeight`: [4](#0-3) 

However, `UnfreezeBalanceProcessor` — the TVM native-contract processor that executes an `unfreezeBalance()` operation triggered from inside a smart contract (reachable from any contract-calling transaction) — unconditionally subtracts `unfreezeBalance / TRX_PRECISION` from the global weight, ignoring `allowNewReward()` entirely, even though its own comment flags this exact spot as a past bug source: [5](#0-4) 

This is the same root cause pattern as the ZeroLend finding: a global aggregate (`TotalNetWeight`/`TotalEnergyWeight`, standing in for `supplyShares`) is mutated by a code path whose delta computation does not match the invariant maintained by every sibling code path that also mutates that aggregate together with the underlying per-account state. When `allowNewReward()` is active, the sibling actuators (freeze/unfreeze v1 and v2) increment/decrement the global weight strictly by the account's actual weight delta, but this native-contract path still uses the old, pre-`allowNewReward()` formula. Any account that freezes/unfreezes resources partly via normal transactions and partly by calling the native `unfreezeBalance` opcode from a smart contract will cause `TotalNetWeight`/`TotalEnergyWeight` to drift away from the true sum of `frozenBalance/TRX_PRECISION` across all accounts.

### Impact Explanation
`TotalNetWeight`/`TotalEnergyWeight` are consensus-critical values used to compute every account's bandwidth/energy allowance (`accountNetUsage`, price of resources, adaptive resource limits). If the aggregate is decremented too much relative to the real sum of account weights (analogous to the ZeroLend underflow), `addTotalEnergyWeight`/`addTotalNetWeight` will clamp it to `0` via `max(0, totalEnergyWeight, ...)` when `allowNewReward()` is on, silently destroying real weight and permanently under/over-crediting all frozen-balance holders' share of network resources going forward — a chain-wide resource/reward accounting corruption reachable simply by any account calling a smart contract that invokes the native "unfreeze balance" operation (no privileged actor required). Because this is a state-transition function executed identically by every full node, the drift is deterministic and reproducible across the network (not a consensus split by itself, but a genuine on-chain accounting bug affecting every account's bandwidth/energy pricing).

### Likelihood Explanation
Reachable by any user: deploy or call a contract that triggers the "unfreeze balance" TVM native contract (present since the TVM voting/freezing native-contract feature was enabled), combined with normal `FreezeBalanceContract`/`UnfreezeBalanceV2Contract` broadcast transactions on the same account while `allowNewReward()` is active. No special privileges, keys, or trusted roles are needed — only a standard contract call from an anonymous transaction sender.

### Recommendation
Make `UnfreezeBalanceProcessor.execute`'s total-weight adjustment consistent with the invariant used elsewhere: compute `oldWeight`/`newWeight` from the account's frozen balance before and after the mutation and add `newWeight - oldWeight` when `dynamicStore.allowNewReward()` is true, falling back to `-unfreezeBalance / TRX_PRECISION` only when it is false — mirroring exactly the pattern already implemented in `UnfreezeBalanceActuator` and `UnfreezeBalanceV2Actuator`.

### Proof of Concept
Not independently reproduced in this analysis (no test harness run); the analog is derived purely from static comparison of `UnfreezeBalanceProcessor.execute` (lines 190-201) against the `allowNewReward()`-gated delta logic consistently used in `FreezeBalanceActuator`, `UnfreezeBalanceActuator`, `FreezeBalanceV2Actuator/Processor`, and `UnfreezeBalanceV2Actuator/Processor`. A concrete PoC would require: (1) enabling `allowNewReward()`, (2) freezing balance via `FreezeBalanceV2Actuator` (weight added via `newWeight - oldWeight`), (3) triggering `unfreezeBalance()` through the legacy TVM native contract path on the same account, and (4) comparing `DynamicPropertiesStore.getTotalNetWeight()`/`getTotalEnergyWeight()` against the actual sum of all accounts' `getFrozenBalance()/TRX_PRECISION` to demonstrate the drift.

  private void addTotalWeight(ResourceCode resourceCode, DynamicPropertiesStore dynamicStore,

    switch (resourceCode) {
      case BANDWIDTH:
        dynamicStore.addTotalNetWeight(weight);
        break;

        break;
