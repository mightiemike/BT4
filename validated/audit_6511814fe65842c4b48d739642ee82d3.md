Based on my investigation, I found a concrete analog in java-tron's CREATE2 implementation that mirrors the root cause of the zkSync CREATE3 report: an on-chain address-computation formula that diverges from the formula developers (and even TRON's own compiler-generated Solidity, per code comments in the test suite) assume is used, breaking any contract that pre-computes a CREATE2 address.

### Title
On-chain CREATE2 address derivation omits the EVM `0xff` create2 discriminator, causing predicted vs. actual deployment address divergence for ported factory/CREATE2 patterns - (File: chainbase/src/main/java/org/tron/common/utils/WalletUtil.java)

### Summary
The actual TVM `CREATE2` opcode handler computes the new contract address as `keccak256(sender ++ salt ++ keccak256(initcode))[12:]`, with no leading discriminator byte at all. Standard EVM (and, per the project's own test fixtures, TRON's compiler-emitted address-prediction helper code) documents/assumes the formula `keccak256(prefix ++ sender ++ salt ++ keccak256(initcode))`, using `0xff` on Ethereum or the TRON address-prefix byte (`0x41`) as commented in the codebase. Because the real on-chain computation has no prefix byte whatsoever, any contract ported from Ethereum (or written assuming the documented TRON formula) that predicts a CREATE2 address in Solidity will compute an address that does not match the address actually produced by the VM.

### Finding Description
The CREATE2 opcode handler dispatches to `createContract2`, which derives the new contract's address via `WalletUtil.generateContractAddress2`: [1](#0-0) 

```java
byte[] contractAddress = WalletUtil
    .generateContractAddress2(senderAddress, salt.getData(), programCode);
```

`generateContractAddress2` implements: [2](#0-1) 

```java
public static byte[] generateContractAddress2(byte[] address, byte[] salt, byte[] code) {
    byte[] mergedData = ByteUtil.merge(address, salt, Hash.sha3(code));
    return Hash.sha3omit12(mergedData);
}
```

This is `keccak256(sender ++ salt ++ keccak256(initcode))[12:]` — no `0xff` prefix (as in Ethereum) and no TRON address-prefix byte. However, the project's own reconstructed test contract explicitly documents (and a developer would reasonably rely on) a *different* formula requiring a prefix byte: [3](#0-2) 

```solidity
// TRON CREATE2 formula (differs from standard EVM):
//   address = keccak256(prefix ++ sender[20] ++ salt[32] ++ keccak256(code)[32])[12:]
// - Standard EVM uses 0xff as prefix (magic byte)
// - TRON replaces it with the address prefix byte (0x41 for mainnet, 0xa0 for testnet)
function getCreate2Addr(uint256 salt) public view returns (address) {
    bytes32 hash = keccak256(
        abi.encodePacked(bytes1(0x41), address(this), salt, keccak256(bytecode))
    );
    return address(uint160(uint256(hash)));
}
```

A commented-out unit test in `Create2Test.java` confirms this divergence was already observed and explicitly flagged as a known bug that was intentionally left unresolved ("bug here, but we should keep it so that we can check consistences before istanbul — should be factory address rather than address"): [4](#0-3) 

This is directly analogous to the reported M-15 issue: in the zkSync report, a library (Solady's CREATE3) assumed the standard Ethereum CREATE2 address-derivation formula to precompute deployment addresses, but zkSync Era's actual on-chain formula differs, so the precomputed address never matches the real deployed address, breaking `Registry.generateAnchor`. Here, any Solidity factory/registry contract ported to TVM that uses the standard (or even the documented TRON) CREATE2 prediction formula in `abi.encodePacked(...)` to precompute an address will get a value that does not match what the TVM `CREATE2` opcode actually deploys to, because the real VM implementation uses neither prefix.

### Impact Explanation
Any protocol pattern that depends on CREATE2 address prediction — factory contracts that register/whitelist a pool, vault, or account at a precomputed address before deployment; deterministic proxy/wallet factories; CREATE3-style deploy-then-verify patterns — will break when ported to TVM without modification. The predicted address computed in Solidity will not equal the actual deployed contract address, causing registration/verification logic to operate on the wrong (non-existent or unrelated) address. This mirrors the "breaks core contract functionality, rendering deployment on this VM useless" standard applied in the source report for Medium severity, since it is a systemic, silent VM-level divergence rather than an isolated contract bug — every ported CREATE2-address-prediction pattern is affected, with no funds-loss precondition but with functional breakage of any such contract's core address-registration logic.

### Likelihood Explanation
High likelihood of being triggered unintentionally: any team porting an existing EVM-based CREATE2 factory/registry contract to TRON (a common practice, since TRON explicitly markets EVM/Solidity compatibility) will hit this without any special conditions — it doesn't require an attacker, only normal deployment of an existing, unmodified EVM-derived contract that predicts CREATE2 addresses.

### Recommendation
Either (a) align the on-chain `CREATE2` address derivation in `WalletUtil.generateContractAddress2` with the documented/expected formula (including the address-prefix byte, matching the comment in `FreezeTest.sol`) so that Solidity-level prediction using the documented TRON formula matches the real VM behavior, or (b) clearly and prominently document the exact TVM CREATE2 formula (no prefix byte) in official TVM developer docs, and provide a canonical Solidity helper library for correct address prediction on TRON, so ported EVM contracts do not silently miscompute addresses.

### Proof of Concept
1. Deploy a factory contract with a Solidity CREATE2 address-prediction helper using the standard/documented formula, e.g. `keccak256(abi.encodePacked(bytes1(0x41), address(this), salt, keccak256(bytecode)))` as shown in `FreezeTest.sol` `getCreate2Addr`, per [5](#0-4) .
2. Deploy the same `bytecode` via `CREATE2` (TVM opcode `0xf5`), which internally calls `WalletUtil.generateContractAddress2` with no prefix byte, per [2](#0-1) .
3. Compare the Solidity-predicted address against the actual deployed contract address returned by the `CREATE2` opcode — they differ, exactly as flagged by the disabled test assertion in `Create2Test.java` ("bug here... should be factory address rather than address"), per [4](#0-3) .
