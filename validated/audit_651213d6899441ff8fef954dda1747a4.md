This confirms the mechanism: for non-embedded apps, `getCurrentSessionId` in `session-utils.ts` returns whatever session ID is stored in the single, domain-wide `shopify_app_session` cookie — with no check that the ID corresponds to the shop in the current request's URL/context. This is the same bug class as the report: a single shared key (here, one cookie at `path=/'`) is used across what should be independent per-tenant entries (per-shop sessions), so creating/authenticating a new entry (a new shop's OAuth callback) silently overwrites the earlier entry (a different shop's session cookie).

### Title
Non-embedded multi-shop apps default to a single domain-wide session cookie, letting authentication of one shop silently overwrite another shop's session - (File: packages/apps/shopify-api/lib/auth/oauth/oauth.ts)

### Summary
For non-embedded apps, the OAuth callback writes the offline/online session id into a single cookie, `shopify_app_session`, at `path: '/'` by default. Because the cookie name and path are not scoped per shop, a browser can only hold one such cookie for the whole app domain. Completing OAuth for shop B overwrites the cookie previously set for shop A, and any subsequent read via `getCurrentSessionId` for shop A's tab will silently resolve to shop B's session id.

### Finding Description
In `begin()`/`callback()` ( [1](#0-0) ), the offline/online session id is signed and stored under `SESSION_COOKIE_NAME` with `path: cookiePath ?? '/'`. The default value of `cookiePath` is `'/'` ( [2](#0-1) ), so the cookie is domain-wide and not bound to a specific shop.

When the current session is later looked up, `getCurrentSessionId()` simply reads and verifies whatever id is present in that single cookie, without any check that the id actually corresponds to the shop the current request is for: [3](#0-2) 

Because the cookie is a single global "slot" (analogous to `oracles[foreignAsset]` in the referenced report being a single slot per asset regardless of which pair uses it), authenticating a second shop (adding a new "entry") overwrites the first shop's stored session pointer (the earlier "entry"), exactly mirroring the reported bug class of "adding a new mapping unexpectedly replaces an existing one that shares the same key."

This exact defect and its consequence ("all tabs use the most-recently-authenticated shop") is explicitly documented by the maintainers themselves in the changelog and in the `cookiePath` doc comment: [4](#0-3) .

### Impact Explanation
In a multi-shop, non-embedded deployment (e.g., an agency or user managing several Shopify stores from separate browser tabs on the same app domain), completing OAuth for shop B causes the previously-authenticated tab for shop A to silently start operating with shop B's session id. Since `getCurrentSessionId` performs no shop-consistency check, actions taken in shop A's tab could be executed against shop B's stored session/access token (cross-tenant session confusion) if the calling code trusts the cookie-derived session id without cross-referencing the shop parameter from the request. This is a data-integrity/cross-tenant risk rather than a remotely-exploitable attacker-controlled takeover, since it requires the same browser/user context to interact with two shops — but it is a genuine session-storage overwrite matching the report's bug class, and the impact (wrong shop's session used) is security relevant for merchants or staff managing multiple stores.

### Likelihood Explanation
This triggers under normal, expected usage — no attacker interaction is required, only a legitimate non-embedded app operator authenticating more than one shop in parallel tabs on the same domain, which the maintainers acknowledge as a real, previously-existing scenario (hence adding `cookiePath` as a fix). The default configuration (`cookiePath` unset) remains vulnerable to this collision; the fix is strictly opt-in.

### Recommendation
Bind the OAuth session cookie to the specific shop instead of using one domain-wide slot: either derive `cookiePath` from the shop by default (rather than requiring the app operator to opt in), or key the cookie name itself by shop (e.g., `shopify_app_session_${shop}`), and have `getCurrentSessionId` validate that the loaded session's `shop` matches the shop indicated by the current request before trusting it — mirroring the recommended mitigation of binding the map key to the more specific identifier instead of a shared one.

### Proof of Concept
1. Configure a non-embedded app without setting `cookiePath` (default `'/'`).
2. In Tab 1, complete OAuth for `shop-a.myshopify.com`; the browser stores `shopify_app_session=offline_shop-a...` at `path=/`.
3. In Tab 2 (same browser/domain), complete OAuth for `shop-b.myshopify.com`; per `callback()` ( [1](#0-0) ), this overwrites the same `shopify_app_session` cookie with `offline_shop-b...`.
4. Return to Tab 1 and make a request; `getCurrentSessionId` ( [3](#0-2) ) reads the now-overwritten cookie and returns `offline_shop-b...`, causing Tab 1 to operate using shop B's session instead of shop A's.
