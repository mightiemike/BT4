## Title
Permanently frozen caller deposit in NEAR Wallet Contract when intermediate ETH-emulation callbacks fail before reaching `rlp_execute_callback` - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The `WalletContract` (NEP-518 ETH-implicit account wallet) tracks an external caller's attached deposit in a `CallerDeposit` struct so it can be refunded if the emulated cross-contract call ultimately fails. This refund is implemented only inside the final `rlp_execute_callback`. Two intermediate callbacks used for multi-step ETH-emulation flows — `address_check_callback` (address-registrar lookup for transfers between eth-implicit accounts) and `nep_141_storage_balance_callback` (NEP-141/ERC-20 storage-registration check) — return error `ExecuteResponse`s in several branches without ever creating the refund promise, causing the caller's attached NEAR deposit to remain stuck in the `WalletContract` account.

### Finding Description
`CallerDeposit::new` records the predecessor's `attached_deposit` whenever an external (non-self) account calls the `#[payable]` `rlp_execute` method: [1](#0-0) 

The only place this deposit is refunded is in `rlp_execute_callback`, and only on the `PromiseResult::Failed` branch of the *final* promise in the chain: [2](#0-1) 

However, `caller_deposit` is threaded through two earlier, intermediate callbacks that are used for more complex ETH-emulation flows (transfer between eth-implicit accounts requiring an address-registrar lookup, and ERC-20/NEP-141 transfers requiring a `storage_balance_of` check): [3](#0-2) [4](#0-3) 

Every early-return `PromiseOrValue::Value(...)` branch inside these two callbacks (registrar call failed, unexpected registrar response, invalid target detected, malformed action for a NEP-141 transfer, or `action_to_promise` error) drops `caller_deposit` on the floor instead of issuing the same `env::promise_batch_create` + `promise_batch_action_transfer` refund pattern used in `rlp_execute_callback`. For example the "invalid target" branch and the `Err(e)` branch both terminate execution without a refund: [5](#0-4) 

This mirrors the root cause identified in the external report: a value-transfer/payer mechanism (there, `RFTPayer`; here, the `CallerDeposit` refund flow) is only wired into one code path, while other reachable failure paths never invoke it, so funds attached by the caller become permanently stuck in the intermediate contract (`NFTManager` there, `WalletContract` here).

### Impact Explanation
Any external account (a relayer, or the eth-implicit-account owner calling directly) that attaches a NEAR deposit to `rlp_execute` for a transfer to another eth-implicit account (triggering the address-registrar check) or an ERC-20/NEP-141 transfer (triggering the storage-balance check) loses that deposit permanently if the intermediate check fails or returns an unexpected/invalid result. The funds sit in the `WalletContract` account balance with no code path to recover them (there is no generic sweep/withdraw method visible in this contract). This is a concrete, unauthorized-value-loss / permanently-frozen-funds bug reachable from a single external call, matching the required "permanently frozen funds" impact category.

### Likelihood Explanation
The vulnerable branches are reached whenever:
- a relayer/caller attaches a deposit while calling `rlp_execute` for a base-token transfer between two eth-implicit accounts where the target account turns out to already be a registered named account (`address_check_callback`'s "invalid target" branch), or
- a NEP-141/ERC-20 transfer's `storage_balance_of` lookup returns malformed data, fails, or the decoded action isn't a `FunctionCall` as expected.

These are ordinary error conditions in the ETH-emulation flow (a faulty/malicious relayer supplying an already-registered target, or an NEP-141 token contract returning unexpected data), not requiring any privileged access — any signer of the underlying Ethereum-style transaction routed through the wallet contract can trigger this by construction of the transaction/target, making it a Medium-likelihood issue given it depends on attaching a nonzero deposit alongside one of these specific emulation paths.

### Recommendation
In every early-return error branch of `address_check_callback` and `nep_141_storage_balance_callback` (registrar call failure, malformed registrar response, invalid target, malformed transfer action, promise-construction errors), issue the same `CallerDeposit` refund promise that `rlp_execute_callback` performs on `PromiseResult::Failed`, ideally by factoring the refund logic into a shared helper invoked from all failure branches across the callback chain.

### Proof of Concept
1. Deploy a `WalletContract` instance for eth-implicit account `A`, and a second wallet-contract instance for eth-implicit account `B` that is later registered as a named account via the address registrar.
2. A relayer (external predecessor, distinct from `current_account_id`) calls `A.rlp_execute(target=B, tx_bytes_b64=<signed EOA transfer to B>)` attaching a nonzero deposit (e.g., 1 NEAR) — `CallerDeposit::new` records this deposit since `predecessor_account_id != current_account_id`.
3. Because the transfer target is another eth-implicit account, `inner_rlp_execute` schedules the registrar lookup and `address_check_callback` with `caller_deposit = Some(relayer, 1 NEAR)`.
4. Since `B` is registered as a named account and the transaction signer is not the current account (a genuinely faulty-relayer condition), the callback hits the branch at lines 168–172, returning `ExecuteResponse{success:false, ...}` directly — no refund promise is created.
5. Verify via `view_account` that the relayer's attached 1 NEAR deposit is not returned, and instead remains part of `A`'s (the `WalletContract`'s) account balance indefinitely.

    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
