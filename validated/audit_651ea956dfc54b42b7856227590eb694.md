### Title
Missing zero-output check in vault `deposit()` allows crediting 0 shares for a real underlying deposit, permanently losing the depositor's principal - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and all other `v0-vault-*.clar` contracts)

### Summary
Every vault contract implements a matched pair of entry points, `deposit` and `redeem`, both computing a preview amount (`inkind`) and checking it against a caller-supplied `min-out` for slippage protection. `redeem` additionally guards against the computed output being zero with `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`, but `deposit` has no equivalent check on its own output (`inkind`, the shares to mint). If `inkind` rounds down to `0` for a valid, non-zero `amount`, and the caller supplies `min-out u0` (the natural default when no slippage protection is configured), the deposit proceeds: real underlying tokens are pulled from the depositor and added to vault `assets`, but zero shares are minted to the recipient. This is exactly the reported bug class — an unchecked, possibly-zero "amount out" that lets a state-changing transfer execute with no corresponding output — just found on the deposit path instead of a swap/liquidation path.

### Finding Description
`deposit` computes `inkind` via `convert-to-shares-preview`: [1](#0-0) 

which floors `mul-div-down amount ts ta` when the vault's share price (`ta`/`ts`) has risen above 1 due to accrued interest, so small `amount` values map to `inkind = u0`. `deposit` then only checks: [2](#0-1) 

Note there is no `(asserts! (> inkind u0) ...)` guard — only `(asserts! (>= inkind min-out) ERR-SLIPPAGE)`, which trivially passes when `min-out` is `u0`. Compare this to `redeem` in the very same contract, which does carry the guard: [3](#0-2) 

The same asymmetry (guarded `redeem`, unguarded `deposit`) is present identically across `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, and `v0-vault-usdh.clar`. [4](#0-3) 

### Impact Explanation
When `inkind` floors to `0`, `receive-underlying amount account` still pulls the depositor's real tokens into the vault and `(var-set assets (+ current-assets amount))` credits those tokens to the shared asset pool, while `(ft-mint? zft inkind recipient)` mints `0` zTokens. The depositor's principal is transferred out of their wallet with no corresponding claim on the vault — an irrecoverable, direct loss of the depositor's funds that is absorbed pro-rata into the value of all other existing shareholders. This is direct theft/permanent loss of user funds at rest, matching the Critical impact class.

### Likelihood Explanation
The share price `ta/ts` naturally rises above `1` as the vault accrues borrower interest over time (via `accrue`/`next-index`), so the window in which small deposit amounts round to zero shares widens as the vault matures — it does not require any privileged or malicious setup, only a sufficiently small `amount` relative to the current share price, combined with the common case of `min-out = u0`.

### Recommendation
Add the same guard that `redeem` already has to `deposit`, e.g. `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`, in all six `v0-vault-*.clar` contracts (and their `local-testing` counterparts) before any external transfer/mint side effects are executed.

### Proof of Concept
1. Let the vault accrue enough interest so that `total-assets-preview() / total-supply-preview()` (share price) exceeds `1` (normal operation over time).
2. Depositor calls `deposit(amount, min-out: u0, recipient)` with `amount` small enough that `convert-to-shares-preview(amount)` computes `mul-div-down(amount, ts, ta) = 0` due to integer floor division. [2](#0-1) 
3. All `asserts!` in `deposit` pass: `amount > 0` ✔, `inkind (u0) >= min-out (u0)` ✔, cap check ✔.
4. `receive-underlying` transfers `amount` of real tokens from the depositor into the vault; `ft-mint? zft u0 recipient` mints zero shares; `assets` is increased by `amount`.
5. The depositor has permanently lost `amount` of underlying tokens with zero shares to redeem them back.
