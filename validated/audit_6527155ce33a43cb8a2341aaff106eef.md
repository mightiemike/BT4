### Title
Exchange trades resolve by a bare sequential `exchangeId` with no creator/content binding, allowing a re-org to swap the underlying pool an honest trade executes against - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
`ExchangeCreateActuator` assigns each new bancor-style exchange pool a purely sequential ID (`dynamicStore.getLatestExchangeNum() + 1`) and stores it under that numeric key. `ExchangeTransactionActuator` later resolves trades solely by that numeric `exchangeId`, with no check that the pool at that ID is the one the trader originally observed/intended (e.g., no creator address check, no token-pair/content hash pinned at offer time). This mirrors the reported Royco `RecipeKernel.sol` issue where markets are referenced only by an incrementing `numMarkets` counter with no re-org-safety hash check.

### Finding Description
`ExchangeCreateActuator.execute()` computes the new exchange's ID as a simple counter and persists it: [1](#0-0) 

`ExchangeTransactionActuator.execute()`/`doValidate()` then look the pool up purely by that numeric ID: [2](#0-1) [3](#0-2) 

The only validation performed on the fetched `ExchangeCapsule` is that the trader's `tokenID` matches one of the pool's two stored token IDs (`firstTokenID`/`secondTokenID`) — line 182 in `doValidate()`. There is no check that this exchange was created by a specific account, nor any hash/content commitment binding the `exchangeId` referenced in the `ExchangeTransactionContract` to the exact pool state (tokens, balances, creator) the trader intended to interact with when they broadcast the transaction.

java-tron, like any DPoS/PBFT chain, can undergo local chain re-organizations (fork switching) before a block is solidified. If an `ExchangeCreateContract` transaction that created exchange `id = N` is reverted by a re-org, an attacker can race to submit their own `ExchangeCreateContract` so that the next assigned ID is again `N` (since `LatestExchangeNum` is deterministically derived from the counter, whoever's create transaction lands first after the reorg gets that ID), but with a different token pair (as long as one side still matches what victims are expected to trade) or heavily skewed balances. An honest, already-signed/broadcast `ExchangeTransactionContract` referencing `exchangeId = N` will still pass validation (its `tokenID` may still equal the malicious pool's `firstTokenID`), but `execute()` will use the attacker-controlled `exchangeCapsule.transaction(...)` pricing/balances to compute `anotherTokenQuant`, letting the attacker's replacement pool define the exchange rate.

### Impact Explanation
A victim's trade, intended for a specific, known token pair and pricing curve, can be silently redirected post-reorg to an attacker-controlled pool with manipulated balances/token pairing, resulting in the victim receiving far less value than expected (or a worthless second token) while the attacker's pool absorbs the victim's TRX/token — direct fund loss / accounting corruption via the `ExchangeTransactionContract` path, analogous to the "malicious deposit recipe" theft in the original report. It also creates an incentive for intentionally forcing re-orgs around lucrative pending exchange trades.

### Likelihood Explanation
This requires a chain re-org (fork switch) to occur exactly around the block(s) containing the `ExchangeCreateContract` and the pending `ExchangeTransactionContract`, and requires the attacker to win the race to re-create an exchange at the same numeric ID with an exploitable token pairing. This is a non-trivial, timing-dependent, race-condition style attack — feasible during natural fork-switch events on java-tron's DPoS consensus, but not trivially triggerable at will by an unprivileged actor absent an actual reorg. Likelihood is therefore moderate rather than high, but the reachable path (any account can call `ExchangeCreateContract`, exchanges are referenced by ID only) is unprivileged and directly analogous to the reported bug class.

### Recommendation
Do not resolve exchange trades solely by the mutable sequential `exchangeId`. Instead:
- Bind the `ExchangeTransactionContract` to a content commitment of the pool at offer-creation time (e.g., a hash of `{ownerAddress, firstTokenId, secondTokenId, createTime}` or requiring the trader to also assert expected creator/token pair, matching stored state), rejecting the transaction if the current pool's identity/content doesn't match what the trader committed to; or
- Require re-validation at broadcast-time against the finalized (solidified) block state only, rather than allowing trades to be constructed against not-yet-solidified exchange creations, reducing the reorg window; or
- At minimum, add a creator-address check similar to `ParticipateAssetIssueActuator`'s `toAddress` == asset owner check (`actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java` lines 171-174), so that trades can pin the expected exchange creator and fail closed if a reorg substitutes a different pool owner at the same ID.

### Proof of Concept
1. Actor A submits `ExchangeCreateContract` creating exchange with `firstTokenId = TRX`, `secondTokenId = TokenX`, balanced 1:1000 → assigned `id = N` via `ExchangeCreateActuator.execute()` (`getLatestExchangeNum()+1`). [4](#0-3) 
2. Victim V observes exchange `N`, signs and broadcasts an `ExchangeTransactionContract` with `exchangeId = N`, `tokenID = TRX`, expecting to receive ~1000×`amount` of `TokenX`.
3. Before V's transaction is included/solidified, a local re-org reverts the block containing A's `ExchangeCreateContract`.
4. Attacker M immediately submits its own `ExchangeCreateContract`, again landing at `id = N` (since `LatestExchangeNum` deterministically increments from the current chain head), with `firstTokenId = TRX`, `secondTokenId = WorthlessTokenY`, heavily imbalanced (e.g., 1:1 ratio favoring M).
5. V's already-signed `ExchangeTransactionContract` (`exchangeId=N`, `tokenID=TRX`) still passes `doValidate()`'s check (`tokenID` still equals `firstTokenID`) and executes against M's malicious pool via `exchangeCapsule.transaction(...)` in `ExchangeTransactionActuator.execute()`, sending V's TRX into M's pool and returning worthless `TokenY` instead of the expected `TokenX`.
