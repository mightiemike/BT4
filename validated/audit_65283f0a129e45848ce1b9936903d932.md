## Title
Deterministic hashCode/address tie-break in witness sorting lets a grinded address always win reward/active-set ties - (File: `chainbase/src/main/java/org/tron/core/store/WitnessStore.java`)

### Summary
`WitnessStore.sortWitnesses()` and `WitnessStore.sortWitness()` sort candidate witnesses primarily by vote count, but break ties using a deterministic function of the witness's own address — either `Object.hashCode()` of the raw address bytes or the reversed hex string of the address — both of which an attacker fully controls by grinding their own TRON keypair before registering as a witness. [1](#0-0) 

### Finding Description
This is analogous to the SEDA `FilterAndTally` bug: reveals/proxies were sorted in ascending order by a self-selected public key, so whichever pubkey sorted first was always prioritized when gas/rewards ran out for the remaining participants.

In java-tron, `sortWitnesses(List<WitnessCapsule>, boolean isSortOpt)` sorts by `Comparator.comparingLong(WitnessCapsule::getVoteCount).reversed()` and then a secondary tie-break comparator:
- if `isSortOpt` (i.e. `allowWitnessSortOptimization`) is disabled: `Comparator.comparingInt((WitnessCapsule w) -> w.getAddress().hashCode()).reversed()`
- if enabled: `Comparator.comparing(WitnessCapsule::createReadableString).reversed()`, where `createReadableString()` is just the hex string of the address. [2](#0-1) [3](#0-2) 

A witness's address is `computeAddress(pubKey)`, derived from an arbitrary account keypair that anyone can generate offline before ever registering a witness (`WitnessCapsule(ByteString pubKey, String url)`), so the address — and therefore the tie-break outcome — is fully attacker-chosen (vanity-address grinding). [4](#0-3) 

This sorted/truncated order is used in two reward/consensus-relevant paths:

1. **Active witness selection** — `DposService.updateWitness()` calls `consensusDelegate.sortWitness(list)` (which delegates to `WitnessStore.sortWitness`, same tie-break logic) and then truncates to the top `MAX_ACTIVE_WITNESS_NUM` (27) to become the active block-producing set: [5](#0-4) [6](#0-5) 

2. **Standby witness reward payout** — `WitnessStore.getWitnessStandby()` calls the same `sortWitnesses()` and truncates to `WITNESS_STANDBY_LENGTH` (127), then `MortgageService.payStandbyWitness()` distributes `WITNESS_127_PAY_PER_BLOCK` proportionally only to those in the truncated list: [7](#0-6) [8](#0-7) 

When two or more candidates are tied on vote count at the exact 27th/127th cutoff boundary — which is common since votes are integer counts and many witnesses can share identical totals (e.g. all-zero, or coordinated vote amounts) — the candidate whose address hashCode (or hex string) sorts "larger" under the reversed comparator always wins the slot, deterministically and repeatably every maintenance cycle. This is the same root-cause pattern as the SEDA report: a self-chosen identifier used as a stable tie-break for reward/gas allocation, without any per-cycle randomization or vote-based-only ranking, that lets an attacker with a chosen address always beat a rival with numerically-identical stake/support.

### Impact Explanation
An attacker (or colluding group) can grind an account address ahead of time such that, whenever their vote count ties with a legitimate competitor at the boundary of the active-witness set or the top-127 standby set, they will always be the one selected to produce blocks (and thus receive block rewards) or receive standby-witness pay — displacing an equally-supported competitor every single cycle. This is a reward/resource-accounting fairness violation reachable by any unprivileged actor who can create an account and register as a witness (no special privileges required), matching the "unfair distribution of rewards" impact class from the SEDA report, applied here to TRON's DPoS active-set selection and standby reward accounting.

### Likelihood Explanation
Generating a vanity keypair whose address hashes/sorts favorably is computationally cheap (grinding a hashCode or a few leading hex characters is trivial with modern hardware) and requires no special access — any external party can create such an address via ordinary account/witness creation. Exact vote-count ties are plausible in practice, especially near the standby-127 or active-27 cutoff where marginal witnesses often cluster at low or zero vote counts. Overall likelihood is moderate: it does not guarantee an attacker beats *every* witness, but it guarantees a deterministic, gameable advantage in every tie situation, which recurs every maintenance cycle.

### Recommendation
Do not use an attacker-controllable value (address hashCode or hex string) as the tie-break key. Replace the secondary comparator with a value the attacker cannot pre-select and grind against, e.g. a per-cycle unpredictable seed (such as the block hash or a VRF-derived value) combined with the address, so tie ordering is randomized per cycle instead of being a stable function of the witness's own address.

### Proof of Concept
1. Generate many candidate keypairs offline and compute `computeAddress(pubKey)` for each until one is found whose `hashCode()` (or hex string, if `allowWitnessSortOptimization` is enabled) is numerically larger than that of a target rival witness address.
2. Register this address as a witness and obtain the same vote count as the rival (e.g., 0 votes, or coordinate identical vote totals).
3. Observe that in every `MaintenanceManager.doMaintenance()` cycle, `sortWitnesses`/`sortWitness` places the grinded address ahead of the rival, so it consistently occupies the 27th active-witness slot (`DposService.updateWitness`) or the 127th standby slot (`WitnessStore.getWitnessStandby`), receiving block-production/standby rewards the rival never gets despite equal support.     List<WitnessCapsule> ret;
    List<WitnessCapsule> all = getAllWitnesses();
    sortWitnesses(all, isSortOpt);

    ret.removeIf(w -> w.getVoteCount() < 1);
    return ret;
  }

  public static void sortWitnesses(List<WitnessCapsule> witnesses, boolean isSortOpt) {
    witnesses.sort(Comparator.comparingLong(WitnessCapsule::getVoteCount).reversed()
        .thenComparing(isSortOpt
            ? Comparator.comparing(WitnessCapsule::createReadableString).reversed()
            : Comparator.comparingInt((WitnessCapsule w) -> w.getAddress().hashCode()).reversed()));
  }

  public void sortWitness(List<ByteString> list, boolean isSortOpt) {
    list.sort(Comparator.comparingLong((ByteString b) -> get(b.toByteArray()).getVoteCount())
        .reversed().thenComparing(isSortOpt
            ? Comparator.comparing(
                (ByteString b) -> ByteArray.toHexString(b.toByteArray())).reversed()
            : Comparator.comparingInt(ByteString::hashCode).reversed()));
  }

  public void payStandbyWitness() {
    List<WitnessCapsule> witnessStandbys = witnessStore.getWitnessStandby(
        dynamicPropertiesStore.allowWitnessSortOptimization());
    long voteSum = witnessStandbys.stream().mapToLong(WitnessCapsule::getVoteCount).sum();
    if (voteSum < 1) {
      return;
    }
    long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
    double eachVotePay = (double) totalPay / voteSum;
    for (WitnessCapsule w : witnessStandbys) {
      long pay = (long) (w.getVoteCount() * eachVotePay);
      payReward(w.getAddress().toByteArray(), pay);
      logger.debug("Pay {} stand reward {}.", Hex.toHexString(w.getAddress().toByteArray()), pay);
    }
  }
