## Title
Historical transaction write-set changes and resource JSON responses are decoded using the *latest* Move type layout instead of the layout at the transaction's own version - ([File: api/types/src/convert.rs])

## Summary
The FairSide report's underlying bug class is "state that was fixed at creation time is silently reinterpreted using parameters/state that changed later, producing a result inconsistent with the correct, current-context computation." The Aptos-native analog is in the REST API's transaction/resource JSON rendering path: when historical transactions or resources are converted to JSON, the Move struct/resource layouts used to decode BCS-encoded write-set values and resource bytes are resolved from the **latest** state view, not from a state view pinned to the **version at which the data was actually written**. This is called out as an unresolved `TODO` directly in the code.

## Finding Description
`Context::render_transactions_non_sequential` builds a single `MoveConverter` from `self.latest_state_view_poem(ledger_info)` and reuses it for every historical transaction in the batch, regardless of each transaction's own version: [1](#0-0) 

That converter's `into_transaction_info` builds the `changes` field of the API's `TransactionInfo` by resolving write-set values through `self.try_into_write_set_changes`, which in turn deserializes Move values using struct layouts obtained from the converter's `self.inner` (the state resolver bound to the *latest* checkpoint), with an explicit acknowledgment of the problem: [2](#0-1) 

The same pattern exists for resource endpoints: `AccountsApi::resources` and `StateApi::resource` build the `MoveConverter` from `latest_state_view_poem` / `state_view` and call `try_into_resource`/`try_into_resources`, which internally look up the struct's field layout from module bytecode fetched via the *same, single* state view used for the whole request: [3](#0-2) 

If a Move module's struct definition changes across versions (e.g., a field is added, removed, reordered, or its type changes — something the Aptos VM permits via module upgrades, since struct-layout changes are only restricted for resources with existing storage, not universally forbidden across all upgrade paths), then decoding a write-set value or resource byte blob that was serialized under the *old* layout with the *new* layout will silently produce a corrupted deserialization: field names, types, or values in the JSON response no longer correspond to what was actually written to the ledger at that version. This is the direct analog of the FairSide bug: state committed under one "governance context" (module layout at write time) is blindly reinterpreted under a later, changed context (module layout at query time) instead of being recomputed under the correct historical context.

## Impact Explanation
This breaks the invariant required by the state-integrity gate that "Authenticated API or state-view output bound to the wrong version, object, or proof context" must not occur. The JSON representation of a committed `write_set` change or `resource` value returned by the REST API can silently misrepresent the actual on-chain, provably-committed data for a historical version — while claiming to represent that exact version (the response is still bound to the correct `TransactionInfo.version` / accumulator root, but the *field-level content* is decoded with the wrong-version type layout). Consumers relying on the JSON API (explorers, indexers, wallets, compliance/audit tooling) for historical correctness receive misleading values without any indication of the mismatch; in the worst case a byte sequence that decodes successfully under the new layout but yields a semantically different value (e.g., a `u64` field misaligned with a different `u64` field due to reordering, or an added `Option<T>` field consuming bytes meant for the next field) can produce plausible but wrong data, which is worse than an outright decode failure. BCS-encoded raw bytes returned via `AcceptType::Bcs` are unaffected (they bypass layout resolution), limiting the impact to the JSON encoding path, which the code's own comment concedes is a real, live gap ("must be fixed before we allow module updates").

## Likelihood Explanation
Any Move module upgrade that changes the layout of a struct with pre-existing on-chain data anywhere in its history (and any account/resource-group query for a historical version, or a `changes` field in a historical transaction, that references that struct) triggers the issue. Since module upgrades (including layout-affecting ones under Aptos's upgrade policies) are a routine occurrence, and the code path is unauthenticated/public read-only API traffic (no special privilege needed to trigger — merely querying an old transaction or resource of an address whose module type layout has since evolved), the likelihood of this manifesting in production is high given enough time and any layout-changing upgrade in the wild. It does not corrupt durable ledger data or accumulator roots (limiting it below "wrong root/proof accepted"), which keeps it below Critical but keeps it a real, high-likelihood integrity defect in "authenticated API ... output bound to the wrong ... object context."

## Recommendation
When converting historical `TransactionOnChainData` or resources at a specific version, construct the `MoveConverter`'s state resolver from a `DbStateView` pinned to that transaction's/resource's own version (or the version immediately preceding it, per module resolution semantics) instead of the process-wide latest state checkpoint. This mirrors the fix pattern recommended in the FairSide report: stop applying a later, changed context to data that was fixed under an earlier context; instead, recompute using the parameters (here, struct layouts) that were actually in effect at the time the data was produced.

## Proof of Concept
1. Deploy module `M` with `struct S { a: u64 }`; publish a resource of type `S` at address `X`, and execute a transaction that writes `S { a: 42 }` into `X`'s account state at version `V1`.
2. Upgrade module `M` (a compatible-per-VM-rules but layout-changing upgrade, e.g. `struct S { b: address, a: u64 }` via a resource-group/new-field addition path permitted by the VM) at a later version `V2 > V1`.
3. Query `GET /v1/accounts/X/resource/M::S` (JSON) — hits `StateApi::resource`, which builds `MoveConverter` from `self.context.state_view(ledger_version)` (latest by default) and calls `try_into_resource(&tag, &bytes)` on the byte blob that was actually written under the *old* layout at `V1`.
4. Alternatively, query `GET /v1/transactions?start=<V1 tx version>` — hits `render_transactions_non_sequential`, which builds one converter off `latest_state_view_poem` for the whole batch and decodes the `changes` write-set entries for the `V1` transaction using the *new* (`V2`) layout of `S`.
5. Observe: the JSON `data` field for the `S` resource/write-op is decoded using the post-upgrade field layout, producing values that do not correspond to the actual bytes committed at `V1` (e.g., misinterpreted field boundaries/types), while the response still claims to be for version `V1`/that transaction's committed `TransactionInfo`.

Note: I was not able to execute this end-to-end in a live environment from the index alone (would need a running node + module upgrade to observe the exact malformed JSON output), so step 5's exact malformed values are inferred from the deserialization logic and the code's own acknowledged `TODO`, not from an executed trace.

    pub fn render_transactions_non_sequential<E: InternalError>(
        &self,
        ledger_info: &LedgerInfo,
        data: Vec<TransactionOnChainData>,
    ) -> Result<Vec<aptos_api_types::Transaction>, E> {
        if data.is_empty() {
            return Ok(vec![]);
        }

        let state_view = self.latest_state_view_poem(ledger_info)?;
        let converter = state_view.as_converter(self.db.clone(), self.indexer_reader.clone());
        let txns: Vec<aptos_api_types::Transaction> = data
            .into_iter()
            .map(|t| {
                let timestamp = self.db.get_block_timestamp(t.version)?;
                let txn = converter.try_into_onchain_transaction(timestamp, t)?;
                Ok(txn)
            })
            .collect::<Result<_, anyhow::Error>>()
