### Title
TRC10 `ExchangeProcessor` uses floating-point math for the Bancor invariant, enabling profit-extracting back-and-forth `ExchangeTransactionContract` trades - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
java-tron's TRC10 "Exchange" feature is an AMM-style bonding-curve market (analogous to the reported `AMM.exchange()`), where `ExchangeCapsule.transaction()` calls a `Processor.exchange()` implementation to compute the counter-token amount for a trade. [1](#0-0)  By default this delegates to `ExchangeProcessor`, which implements the Bancor-style invariant using native `double` arithmetic and `Math.pow`, rather than exact/rounded `BigDecimal` math. [2](#0-1)  A hardened, `BigDecimal`-based alternative (`SafeExchangeProcessor`) exists but is only used when the `allowHardenExchangeCalculation` dynamic property/proposal is enabled, which is off unless a super-representative proposal explicitly turns it on. [3](#0-2) 

### Finding Description
The reported bug class is that an AMM's invariant computation loses precision when computing swap fees/output amounts, allowing an attacker to execute repeated back-and-forth swaps that each yield a tiny arithmetic surplus, which compounds into a real profit when repeated many times cheaply.

java-tron's TRC10 Exchange is structurally the same primitive: a constant-relationship market maker where users submit `ExchangeTransactionContract` transactions and the chain computes the output amount via `ExchangeCapsule.transaction()` → `Processor.exchange()`. [4](#0-3)  The default processor, `ExchangeProcessor`, computes the "relay" and output amounts using `double` and `Math.pow` with a hardcoded exponent (`0.0005` for one leg, `2000.0` for the other, which are the inverse of each other and encode the maker/AMM "fee" curve), then truncates via a cast to `long`: [5](#0-4) 

Because this arithmetic is performed with IEEE-754 double precision rather than exact decimal math, repeated composition of `exchangeToSupply`/`exchangeFromSupply` accumulates rounding error in the same way the external report describes for `AMM.exchange()`. The project's own tests demonstrate this is a live discrepancy: `testStrictMath` explicitly asserts that the `false`-mode (`useStrictMath=false`, plain `double` ops) processor and the `true`-mode (`StrictMath`) processor produce *different* results for the same inputs, while the exact `SafeExchangeProcessor` (`BigDecimal`) is treated as the "safe"/ground-truth baseline that the strict-math variant must match. [6](#0-5)  This confirms that the default, unhardened code path (`ExchangeProcessor` with `useStrictMath=false`, and `hardenedCalc=false` since `allowHardenExchangeCalculation` defaults off) produces numerically different (and by construction, less precise) results than the exact calculation, exactly the "inaccuracies in calculating the invariant" condition described in the external report.

Unlike the external Curve report, java-tron's Exchange has no adjustable low/zero "AMM fee" parameter — the fee is baked into the fixed `0.0005`/`2000` weight exponents — so the specific "set minimum AMM fee ≥ 1,000,000" mitigation does not directly translate. What does translate is the root cause: floating-point invariant math instead of exact decimal/rational math, on the default execution path, is the mechanism by which repeated back-and-forth trades can extract net value from the pool via accumulated rounding bias, before the corrective `SafeExchangeProcessor` path (gated behind `allowHardenExchangeCalculation`, itself gated behind a committee proposal in `ProposalUtil`/`ProposalService`) is enabled. [7](#0-6) 

### Impact Explanation
If the floating-point rounding in `ExchangeProcessor` is systematically biased in the attacker's favor for some parameter ranges (as the external report demonstrates for the analogous Curve bug class), an attacker can repeatedly call `ExchangeTransactionContract` (or the same effect through `ExchangeInjectContract`/`ExchangeWithdrawActuator`, which also use non-exact math on the default, non-hardened path) back-and-forth within one or many transactions to siphon TRX/TRC10 token balance out of an Exchange pool without providing equivalent value, corrupting pool accounting and potentially draining liquidity providers'/pool token holders' funds. This is reachable by any account via an ordinary broadcast transaction — no privileged role required.

### Likelihood Explanation
Exploitability depends on whether the specific floating-point error introduced by `Math.pow`/`double` truncation in `exchangeToSupply`/`exchangeFromSupply` is directionally biased toward attacker profit for realistic pool sizes/trade sizes — this requires numerical analysis of the exact formula which I was not able to complete with the available read-only tools (I could not execute code to empirically test round-trip profitability across a parameter sweep as the external report's PoC did for Curve). The `testSellAndBuy`/`testSellAndBuy2` unit tests in `ExchangeCapsuleTest`/`ExchangeProcessorTest` show round-trips returning slightly less than the input (a loss, not a profit) for the sampled inputs, which does not by itself confirm the vulnerability is exploitable in java-tron's formula — it only confirms the non-exact, double-based arithmetic path is live and diverges from the exact `BigDecimal` path.

### Recommendation
- Empirically fuzz `ExchangeProcessor.exchange()` round-trips (buy-then-sell / sell-then-buy) across a wide range of pool balances and trade sizes to determine whether there exist input ranges where the round-trip yields a net-positive `buyTokenQuant` for the attacker (i.e., a "negative fee").
- If such ranges exist, either enable `allowHardenExchangeCalculation` (routing all Exchange operations through the exact `BigDecimal`-based `SafeExchangeProcessor`) by default/permanently, or replace `ExchangeProcessor`'s `double`/`Math.pow` computation with the same exact decimal arithmetic used in `SafeExchangeProcessor` unconditionally, removing the floating-point path entirely.
- Add balance-invariant assertions after every trade (as already done in the hardened path via `newFirstTokenBalance < 0` checks) that also verify the constant-product/Bancor invariant does not increase beyond the intended fee margin, rejecting the transaction otherwise.

### Proof of Concept
Not independently reproduced; a concrete PoC requires running `ExchangeProcessor.exchange()` in a numeric harness across a parameter sweep of `(sellTokenBalance, buyTokenBalance, sellTokenQuant)` doing repeated buy/sell round-trips and checking for any input where `result_after_roundtrip > sellTokenQuant`, analogous to the external report's Curve PoC. The existing `ExchangeProcessorTest.testSellAndBuy`/`testSellAndBuy2` scaffolding ( [8](#0-7) ) is the natural place to extend such a fuzz test, but I was unable to execute code to confirm a profitable input range within this session.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
