### Title
Uncontrolled recursion during untrusted declare-transaction JSON deserialization enables gateway node crash (stack overflow DoS) - (File: `crates/apollo_http_server/src/http_server.rs`, `crates/starknet_api/src/deprecated_contract_class.rs`)

### Summary
The `add_rpc_transaction` and `add_transaction` HTTP endpoints deserialize an attacker-controlled request body directly into Rust structs using `serde_json`/`axum::Json` before any depth or structural validation runs. For deprecated (Cairo0) declare transactions, the target struct (`starknet_api::deprecated_contract_class::Program`) contains multiple `serde_json::Value` fields (`attributes`, `debug_info`, `hints`, `identifiers`, `reference_manager`, `data`), which are parsed by `serde_json`'s inherently recursive descent parser with no depth limit. This is the same bug class as CVE-2025-4565 (protobuf-python unbounded recursive parsing, CWE-674) but the Rust manifestation is more severe: unlike Python (which raises a catchable `RecursionError`), an unbounded recursion in Rust exhausts the native call stack and aborts the entire process — it cannot be caught with `Result`/`panic!`.

### Finding Description
The HTTP server exposes two POST endpoints that accept transactions from any unauthenticated caller: [1](#0-0) 

For `add_tx` (`/gateway/add_transaction`), the raw string body is deserialized with `serde_json::from_str(&tx)` into `DeprecatedGatewayTransactionV3` *before* any structural or size validation is applied: [2](#0-1) 

The declare-transaction path carries a `DeprecatedGatewaySierraContractClass`/`DeprecatedContractClass`, whose `program: Program` field contains several untyped, arbitrarily-nested `serde_json::Value` fields: [3](#0-2) 

`serde_json::Value`'s `Deserialize` implementation recurses once per nesting level of the input JSON array/object (e.g. `[[[[[...]]]]]`) with no configured recursion limit. A payload consisting of a few hundred thousand nested brackets is only a few hundred KB (well under typical `max_request_body_size` / `max_contract_class_object_size` limits, which are enforced only *after* successful deserialization in `validate_class_length`): [4](#0-3) 

Because the size/structure checks in `StatelessTransactionValidator::validate_declare_tx` / `validate_class_length` run only *after* the JSON has already been fully parsed into `Program`/`ContractClass`, they cannot prevent the crash — the stack overflow occurs during the `Json<T>` extraction or `serde_json::from_str` call itself, before any application code executes. A Rust stack overflow triggers `SIGSEGV`/an unrecoverable abort of the process (there is no `unwind`-based recovery from stack overflow), taking down the entire gateway node handling the request.

### Impact Explanation
A single unauthenticated HTTP request with a small, deeply-nested JSON payload can crash the gateway process of any sequencer node that exposes `/gateway/add_transaction`. Since gateway availability is required to admit new transactions, this can render an affected node (and, if replicated across peers via the deprecated gateway ingestion path, potentially several nodes) unable to confirm new transactions — a network availability/DoS impact, consistent with the "network unable to confirm new transactions" acceptance criterion. Because process abort in Rust cannot be caught, this is not a graceful `Result::Err` — the whole service (and any co-located components in the same process) goes down, requiring an external restart.

### Likelihood Explanation
High. The attack requires no authentication, no fees, no valid signature, and no special privileges — it is a raw HTTP POST to a public gateway endpoint with a crafted, small payload. `serde_json::Value` recursion depth needed to overflow a typical thread stack is on the order of tens of thousands of nesting levels, trivially producible and small in byte size (a repeated `[` character), so it easily bypasses byte-size based request limits (`RequestBodyLimitLayer`, `DefaultBodyLimit`) that are configured generously for legitimate large Sierra programs.

### Recommendation
- Impose an explicit recursion/nesting-depth limit before or during JSON parsing of any untrusted transaction/class payload (e.g., use a depth-limited deserializer, or a pre-parse structural scan that rejects JSON exceeding a safe nesting depth, similar to mitigations added for CVE-2025-4565).
- Specifically bound recursion for the `serde_json::Value` fields in `Program` (`attributes`, `debug_info`, `hints`, `identifiers`, `reference_manager`, `data`) and any other place where fully-untyped `serde_json::Value` is deserialized directly from network-supplied bytes (e.g., `apollo_rpc::decompress_program`, `starknet_os` `CairoContractDefinition`).
- Alternatively/additionally, run untrusted JSON deserialization for legacy/declare transactions inside a bounded worker thread with a small, fixed stack size and `catch_unwind`-independent guard (e.g., `std::thread::Builder::stack_size` + external timeout/kill), so a stack overflow only kills a worker instead of the whole process — mirroring the existing pattern already used for Cairo Native execution stack isolation in `crates/blockifier/src/blockifier/transaction_executor.rs` (`execute_txs_sequentially`).
- Add negative tests submitting deeply nested (but byte-size-small) JSON declare/ deploy transactions to confirm the endpoint rejects them with a normal error instead of crashing.

### Proof of Concept
1. Construct a small JSON string for the `add_transaction` (deprecated gateway) declare transaction where `contract_class.program.debug_info` (or `attributes`/`hints`/`identifiers`) is replaced by a deeply nested array, e.g. `"debug_info": "[" * 200000 + "]" * 200000` embedded as valid JSON syntax (a chain of 200,000 nested empty arrays `[[[...[]...]]]`).
2. POST this payload to `/gateway/add_transaction` (or the equivalent RPC declare transaction to `/gateway/add_rpc_transaction`, targeting any `serde_json::Value` nested field reachable pre-validation).
3. Observe that the HTTP server process crashes with a stack overflow before `StatelessTransactionValidator::validate` or `validate_class_length` executes, since the crash occurs inside `serde_json::from_str`/`Json<T>` extraction in `crates/apollo_http_server/src/http_server.rs` lines 196-210 / 167-181.

*Note: I could not execute this PoC in a live environment (no runtime/build access here); the finding is based on static analysis of the deserialization call graph, `Program`'s untyped recursive `serde_json::Value` fields, and validation ordering in `stateless_transaction_validator.rs`. A background Devin session with build/runtime access would be needed to empirically confirm the exact nesting depth required to trigger the overflow on the deployed stack size.*
