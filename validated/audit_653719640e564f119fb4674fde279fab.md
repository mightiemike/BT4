### Title
Unbounded array allocation from attacker-controlled length word in TVM precompiled-contract input parsing - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The reported bug class is "improper input validation of a length/size field taken from untrusted input, which is used to drive an unbounded allocation/copy, causing CPU/memory exhaustion and DoS." In java-tron's TVM precompiled-contract layer, the helper functions `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a `len` value straight out of attacker-supplied call data (a `DataWord`) and immediately allocate a Java array sized by that value, with no check that `len` is consistent with the actual size of the input or with any sane upper bound.

### Finding Description
`extractBytes32Array` takes `len` directly from `words[offset].intValueSafe()` and allocates `new byte[len][]` with no bound check at all: [1](#0-0) 

`extractBytesArray` performs a check that `offset` is within the `words` array, but still allocates `new byte[len][]` using an unbounded `len = words[offset].intValueSafe()` before any per-element bounds validation happens (the per-element `extractBytes` calls happen afterward, inside the loop, once the array is already allocated): [2](#0-1) 

`extractSigArray` has the identical pattern: [3](#0-2) 

These `DataWord` values are 32-byte words taken from the raw contract call `data`, which is fully attacker-controlled ABI-encoded input to a precompiled contract (e.g. the multi-signature validation precompiles named in the codebase test files `BatchValidateSignContractTest.java` / `ValidateMultiSignContractTest.java`). `DataWord.intValueSafe()` clamps to a valid `int` range but a small calldata payload can still set an arbitrary word to a large value (up to `Integer.MAX_VALUE`), so an attacker can submit a very small transaction whose call data encodes a huge `len` for one of these array-length words. This is structurally the same root cause as the Shardeum report: a `length`-like field taken from attacker data is passed to an array/typed-array allocation routine (`new byte[len][]` here vs `Uint8Array.from({length})` there) without validating that `len` actually corresponds to real, correspondingly-sized payload data.

Unlike the RLP decoder (`RLP.calcLength`/`verifyLength`, `framework/.../RLP.java`) and `ContractEventParser.subBytes` (`framework/.../ContractEventParser.java`), which explicitly bound decoded lengths against the remaining payload size before allocating, these `PrecompiledContracts` helpers perform no such `verifyLength`-style check prior to allocation. [4](#0-3) [5](#0-4) 

### Impact Explanation
A crafted `TriggerSmartContract` transaction (or a call from another contract) invoking a precompiled contract that internally uses `extractBytes32Array`/`extractBytesArray`/`extractSigArray` with a large `len` word triggers allocation of a huge array (e.g. `len` near `Integer.MAX_VALUE` implies an object array of billions of null references, several GB of heap). This can cause an `OutOfMemoryError`/severe GC pressure on every full node and witness/SR node that executes the transaction during block validation, i.e. every node in the network processing that block — a direct denial-of-service vector reachable purely through TVM execution triggered by an unprivileged, signed transaction. Because energy/gas for these precompiled contracts is computed from the size of the raw call `data` (as seen generally in this file, e.g. `getEnergyForData` implementations keyed off `data.length`), and not from the attacker-controlled `len` value extracted from inside that data, the resource cost of the allocation is not properly gas-metered — a small, cheap transaction can trigger disproportionately large memory/CPU consumption, matching the "improper input validation leading to DoS" bug class exactly.

### Likelihood Explanation
Likelihood is high for triggering the code path (any account can send a `TriggerSmartContract` transaction calling into these precompiled contracts), but I could not fully confirm within the available tool budget: (1) the exact addresses/opcodes of the precompiled contracts that call `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, (2) whether an outer caller (before these functions) already bounds `len`/`spendCount`/`receiveCount`-style values in all call sites the way the Sapling-related code at lines 1492-1499 of the same file explicitly bounds `spendCount`/`receiveCount` to small constants. Only some of the precompiled-contract call sites in this file were confirmed to have such upstream bounds; `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` themselves have none. This uncertainty should be resolved by tracing every caller of these three helper methods before remediation.

### Recommendation
Add explicit bounds checks in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (mirroring `RLP.verifyLength`) so that `len` is validated against the actual remaining size of `data`/`words` (and against a reasonable hard maximum) before any array is allocated. Additionally, ensure gas/energy costs charged for the corresponding precompiled contracts account for the actual amount of memory/work implied by `len`, not merely the raw call-data length, so an attacker cannot decouple declared vs. real payload size to under-pay for resource consumption.

### Proof of Concept
Concept (not fully validated against the actual entry-point contract call convention due to tool-call limits): construct a `TriggerSmartContract` transaction whose call data, when parsed into `DataWord[]` for the target precompiled contract, places at the expected "array length" offset a large 32-byte integer value (e.g. `0x7FFFFFFF`) while keeping the overall call data short. When the precompiled contract's `execute` method invokes `extractBytes32Array`/`extractBytesArray`/`extractSigArray` with this offset, `new byte[len][]` is allocated with `len ≈ Integer.MAX_VALUE`, causing multi-gigabyte allocation attempts on every node executing this transaction during consensus, independent of the small gas fee paid for the transaction's raw data size.
