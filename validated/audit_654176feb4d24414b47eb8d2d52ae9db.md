### Title
Unbounded duplicate session-ID accumulation in `KVSessionStorage` shop index - (File: packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts)

### Summary
`KVSessionStorage.addShopIds` appends a session ID to the per-shop index list on every `storeSession` call without checking whether that ID is already present, unlike the equivalent `RedisSessionStorage.addKeyToShopList`, which explicitly deduplicates. Because `storeSession` for the same session ID is invoked repeatedly during normal, unauthenticated-triggerable flows (offline access-token refresh on every request via `ensureOfflineTokenIsNotExpired`), the shop's session-ID array in KV storage grows without bound and contains many duplicate entries for what is logically a single session — directly analogous to the reported `users` list duplication bug where an address could re-enter a list multiple times and cause the list-consuming logic (`distributeDividends`) to process the same entity multiple times.

### Finding Description
`KVSessionStorage.storeSession` calls `addShopIds(session.shop, [session.id])` on every store, and `addShopIds` simply concatenates the new ID onto the existing array with no `includes`/dedup check: [1](#0-0) 

Compare this to `RedisSessionStorage.addKeyToShopList`, which guards against duplicates with `if (!idKeysArray.includes(idKey))` before pushing: [2](#0-1) 

`storeSession` is not a one-time, install-only operation — it is re-invoked for the *same* session ID whenever an offline access token is refreshed. This refresh path is triggered transparently on ordinary authenticated requests (and other flows) whenever `expiringOfflineAccessTokens` is enabled: [3](#0-2) [4](#0-3) 

Every such refresh re-stores the same `session.id` for the shop, and each call to `addShopIds` appends another duplicate copy of that ID into the KV list — the list is never deduplicated or pruned except on `deleteSession`. `findSessionsByShop` then maps over the entire (duplicated) ID array and loads/returns the session once per duplicate entry: [5](#0-4) 

### Impact Explanation
Consumers of `findSessionsByShop` treat the result as a list of distinct sessions and iterate it to perform per-session side effects. For example, `AppInstallations.delete` (used by shopify-app-express during app uninstall) fetches all sessions for a shop and passes their IDs to `deleteSessions`: [6](#0-5) 

With a duplicated shop-ID index, this produces a list containing the same session ID many times over (potentially thousands of entries after enough refresh cycles over an app's lifetime), causing:
- Repeated per-session processing (redundant KV reads, redundant deletes) for logic that assumes uniqueness — the analog of "multiple dividends" being paid for one entrant.
- Unbounded growth of the shop's index value in KV storage, since nothing ever removes duplicate IDs except a full `deleteSession`, which only strips the exact ID once via `filter` regardless of how many duplicate copies exist: [7](#0-6) 
  (Note `filter((id) => !ids.includes(id))` removes *all* matching duplicates on delete, so the practical persistent-storage-bloat/DoS risk is bounded to the period before a session is deleted, but during that window the list can grow indefinitely as refreshes accumulate.)
- Because `findSessionsByShop` returns duplicated `Session[]`, any downstream code that treats list length as "number of sessions" or iterates expecting one-decision-per-session gets skewed/duplicated results.

### Likelihood Explanation
This requires no privileged actor and no secret compromise: it is triggered purely by normal traffic to any embedded/offline-token app that has `expiringOfflineAccessTokens` enabled and uses `KVSessionStorage`, since ordinary authenticated requests from merchants naturally cause repeated `storeSession` calls for the same offline session ID as its token nears expiry. No malicious input is even needed — it is a straightforward logic bug reachable by legitimate app usage over time, making it highly likely to manifest in any long-running KV-backed deployment.

### Recommendation
In `KVSessionStorage.addShopIds`, deduplicate before writing, mirroring the Redis implementation:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```

### Proof of Concept
1. Configure an app with `KVSessionStorage` and `future.expiringOfflineAccessTokens: true`.
2. Complete OAuth for `shop-a.myshopify.com`, producing offline session `offline_shop-a.myshopify.com`, which is stored once (index = `[id]`).
3. Let the token approach expiry and make an authenticated request; `validateAuthenticatedSession` → `ensureOfflineTokenIsNotExpired` refreshes the token and calls `config.sessionStorage.storeSession(offlineSession)` again with the *same* `session.id`. [8](#0-7) 
4. `addShopIds` appends the ID again without checking membership, so `namespace.get(shopKey)` now returns `[id, id]`.
5. Repeat step 3 across N refresh cycles; the shop key’s array grows to `[id, id, ..., id]` (N copies).
6. Call `findSessionsByShop('shop-a.myshopify.com')` — it returns N duplicate `Session` objects for the same session. Any caller (e.g., `AppInstallations.delete`) then processes the same session N times instead of once.

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
