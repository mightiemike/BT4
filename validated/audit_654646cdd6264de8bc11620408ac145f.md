### Title
Unbounded gzip decompression of user-supplied Cairo0 program in RPC execution path enables memory-exhaustion DoS - ([File: crates/apollo_rpc/src/v0_8/api/mod.rs])

### Summary
The Starknet RPC node exposes a code path that decompresses a user-supplied, base64-encoded gzip payload (`compressed_program`) with **no size limit and no explicit `Read` cap**, unlike every other decompression path in the codebase, which is a direct analog of the tar-split/gzip-bomb weakness (CVE-2017-14992, GHSA-hqwh-8xv9-42hw): a small compressed input can decompress into an enormous buffer, exhausting node memory.

### Finding Description
`decompress_program` in `crates/apollo_rpc/src/v0_8/api/mod.rs` base64-decodes attacker-controlled input and pipes it through a `flate2::read::GzDecoder`, calling `read_to_end` with an unbounded `Vec<u8>`: [1](#0-0) 

The comment on the function itself acknowledges the gap: `// TODO(dan): add time and size limits.` This function is invoked from `user_deprecated_contract_class_to_sn_api`, which is used when converting a `BroadcastedDeclareV1Transaction` (a `DECLARE_TXN_V1`-style RPC request containing a raw Cairo-0 `DeprecatedContractClass` with a `compressed_program` string field) into an `ExecutableTransactionInput` for local blockifier execution (used by RPC methods such as fee-estimation/simulation flows that accept broadcasted transactions): [2](#0-1) 

This is the *only* decompression call site in the reachable transaction/class-handling code that lacks a size bound. Every other analogous path in the repository was hardened against exactly this bug class:
- `starknet_api::compression_utils::decode_and_decompress_with_size_limit` bounds the decompressed output using `.take(max_size + 1)` before checking against the limit: [3](#0-2) 
- The HTTP gateway's deprecated-transaction conversion path enforces this limit for Sierra programs: [4](#0-3) 
- Protobuf-based Cairo0 program deserialization (P2P sync) enforces a hard `MAX_CAIRO0_PROGRAM_SIZE` cap: [5](#0-4) 
- Gateway-side Sierra bytecode/class-object size validation enforces `max_contract_bytecode_size`/`max_contract_class_object_size` before/around decompression-sensitive paths: [6](#0-5) 

`decompress_program` bypasses all of these protections because it operates on the RPC-node's own broadcasted-transaction execution path rather than the gateway's declare-transaction validation path, so none of the gateway's `max_contract_bytecode_size`/`max_sierra_program_size` checks apply to it.

### Impact Explanation
An unprivileged client can submit a `BroadcastedDeclareV1Transaction` (Cairo-0 declare) with a `contract_class.program` field containing a crafted gzip "bomb" (e.g., a small compressed payload that expands to gigabytes). Because `decode_reader`/`decompress_program` decompresses into an unbounded `Vec<u8>` with no `.take()` limit and no post-check, the node will attempt to allocate memory proportional to the (attacker-chosen) decompressed size. This can exhaust node memory and crash or severely degrade the RPC/execution node — a Denial-of-Service that can render the node unable to process further requests (an execution/simulation service outage), matching the "network unable to confirm new transactions" / availability-loss impact class for the reachable component.

### Likelihood Explanation
Likelihood is high for any deployment that exposes the affected RPC execution flow to untrusted callers: the attack requires only a single, cheaply-constructed base64 gzip payload; no special privileges, prior state, or protocol-level knowledge beyond the RPC schema are needed. The bug is a straightforward oversight (explicitly flagged by the developers' own TODO) rather than requiring complex conditions.

### Recommendation
Route `decompress_program` (and `user_deprecated_contract_class_to_sn_api`) through the same size-bounded decompression utility already used elsewhere in the codebase, e.g. `starknet_api::compression_utils::decode_and_decompress_with_size_limit`, or wrap the `GzDecoder` read with `.take(MAX_SIZE)` and reject payloads whose decompressed length exceeds a configured maximum (consistent with `max_sierra_program_size`/`MAX_CAIRO0_PROGRAM_SIZE` patterns used elsewhere), returning an RPC error instead of allocating unbounded memory. Additionally, add a decompression time budget as noted in the existing TODO.

### Proof of Concept
1. Craft a gzip payload that decompresses to a very large size (a "zip bomb"), e.g. repeatedly appending zero bytes and compressing (gzip achieves very high compression ratios on repetitive data), producing a compressed size of a few KB that expands to multiple GB.
2. Base64-encode the compressed bytes and place them into the `program` field of a `DeprecatedContractClass` used in a `BroadcastedDeclareV1Transaction`.
3. Submit this transaction body to the affected RPC method that accepts broadcasted transactions for execution/fee-estimation (the code path that converts `BroadcastedDeclareTransaction::V1` into `ExecutableTransactionInput::DeclareV1` via `user_deprecated_contract_class_to_sn_api` → `decompress_program`).
4. Observe the node attempt to allocate and populate a multi-gigabyte `Vec<u8>` in `decompress_program`'s `read_to_end` call, leading to memory exhaustion / OOM kill of the node process.

/// Decompresses the provided data with size limits.
fn decompress_with_size_limit(
    decoded_data: Vec<u8>,
    max_size: usize,
) -> Result<Vec<u8>, CompressionError> {
    let decompressor = flate2::read::GzDecoder::new(&decoded_data[..]);
    let mut decompressed_data = Vec::new();
    decompressor
        .take((max_size + 1).try_into().expect("max_size should be less than usize::MAX"))
        .read_to_end(&mut decompressed_data)?;
    if decompressed_data.len() > max_size {
        return Err(CompressionError::SizeLimitExceeded { limit: max_size });
    }
    Ok(decompressed_data)
}
