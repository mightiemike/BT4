### Title
Wallet Contract's compile-time hardcoded `CHAIN_ID` enables cross-fork replay of signed Ethereum-style meta-transactions - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The NEAR Wallet Contract validates Ethereum-style (EIP-2930/legacy) RLP transactions submitted through `rlp_execute` by comparing the transaction's `chain_id` field against a constant `CHAIN_ID` that is baked into the compiled WASM binary at build time, exactly one value per network type (mainnet/testnet/localnet). This mirrors the reported `BoostV2.vy` flaw: a domain-separating identifier (there, EIP-712 `chain.id`; here, the emulated EVM `chain_id`) is fixed once at "initialization" (there, contract deploy; here, contract compilation) rather than derived from the live chain's actual, fork-aware identity.

### Finding Description
`CHAIN_ID` is read from a static file and compiled into the contract: [1](#0-0) 

The build process assigns exactly one fixed `CHAIN_ID` per network category (397 for mainnet, 398 for testnet, 399 for localnet) at build time, with no per-genesis or per-fork differentiation: [2](#0-1) 

The only replay-relevant check performed on the incoming Ethereum-style transaction is that its `chain_id` matches this hardcoded constant: [3](#0-2) 

There is no reference anywhere in the Wallet Contract to the live network's actual chain/genesis identity (e.g. a genesis hash, protocol version, or any value that changes across a chain split). The only other replay defense is a per-account `nonce` stored in contract state, which is identical on both sides of a fork immediately after the split point: [4](#0-3) 

If NEAR mainnet (or testnet) ever undergoes a contentious hard fork that produces two independently live networks (both still using the same `wallet_contract_mainnet.wasm` artifact, hence the same hardcoded `CHAIN_ID = 397`), a user's previously signed EVM-style transaction remains fully valid on both forked chains: the `tx.chain_id != Some(CHAIN_ID)` check in `validate_tx_relayer_data` cannot distinguish between the two forks, exactly as described in the original EIP-712 finding where an immutable `DOMAIN_SEPARATOR` computed once at `__init__` cannot reflect a post-fork chain ID change.

### Impact Explanation
Because Wallet Contract state (deployed contract code, nonce, and account balances) is byte-for-byte identical on both sides of the fork at the split block, a valid signed transaction (e.g. a base-token transfer, ERC-20-style transfer, or arbitrary NEAR `Action` encoded via EVM ABI selectors) that a user intended to submit only on one fork can be relayed and executed on the sibling fork as well. This causes unauthorized/duplicate value movement: the same signed intent (e.g., "transfer N tokens to X") executes independently on both chains, effectively doubling the transfer relative to what the signer authorized on the network they believed they were interacting with.

### Likelihood Explanation
This requires a NEAR chain split/hard fork event to materialize the two candidate chains, which is a low-frequency but not implausible event for a live blockchain. Once such a split exists, exploitation is essentially free: any previously observed signed RLP transaction (which are broadcast/relayed and therefore public) can be resubmitted verbatim via `rlp_execute` on the sibling chain by anyone, with no additional signature or privileged access required — the "attacker" is simply any transaction relayer/observer, matching the reachable, unprivileged-signer threat model.

### Recommendation
Do not rely solely on a compile-time constant `CHAIN_ID` to distinguish live networks. Bind the Wallet Contract's accepted `chain_id` (or an additional domain-separation value) to something that necessarily diverges across a hard fork — for example, incorporate the NEAR genesis hash / protocol version, or make the accepted chain id and any other domain-separating parameters queryable/updatable via governance rather than frozen at compile time, analogous to OpenZeppelin's `EIP712` pattern of recomputing the domain separator dynamically instead of caching it as an `immutable`.

### Proof of Concept
1. Wallet Contract is deployed identically (with `CHAIN_ID = 397`) as part of the genesis state on NEAR mainnet.
2. Mainnet undergoes a hard fork, producing chain A and chain B, both still running the identical Wallet Contract WASM with `CHAIN_ID = 397`, and identical account/nonce state at the fork point (see `nonce` field and `get_nonce` in [4](#0-3) ).
3. A user signs an EIP-2930 transaction (as constructed in the test helper) transferring value to another wallet on chain A, using `chain_id: CHAIN_ID` per [5](#0-4) .
4. Any relayer submits this exact signed transaction bytes via `rlp_execute` to the Wallet Contract instance on chain A — it succeeds, since `tx.chain_id == CHAIN_ID` per [6](#0-5) .
5. The same relayer resubmits the identical signed bytes to the Wallet Contract instance on chain B; the check again passes because `CHAIN_ID` is identical on both forks, and the pre-fork nonce state is identical, so the transfer executes a second time on chain B — a replay the user never separately authorized for chain B.
