### Title
`NakamotoChainState::check_sortition_exists` accepts a `pox_valid = 0` (invalidated) sortition when validating a Nakamoto block's burn view - (File: stackslib/src/chainstate/nakamoto/tenure.rs)

### Summary
This is a structural analog of the `OPFaultVerifier` bug: a verifier consumes an authoritative record (a "dispute game" there, a sortition `BlockSnapshot` here) without checking the flag that marks that record as having been invalidated after being found to not correspond to the canonical/valid history. In `OptimismPortal`, `disputeGameBlacklist` marks games that "resolve incorrectly"; in the Stacks sortition DB, `pox_valid` marks snapshots that no longer belong to the canonical PoX fork after a PoX-reorg/anchor-block invalidation [1](#0-0) .

### Finding Description
`check_sortition_exists` looks up the burn header hash for a block's `consensus_hash`, then fetches the corresponding `BlockSnapshot` and only checks that `snapshot.consensus_hash == block_consensus_hash`; it never checks `snapshot.pox_valid`: [2](#0-1) 

By contrast, every other snapshot-consumer in the same codebase that reads a `BlockSnapshot` by consensus hash explicitly rejects it when `pox_valid` is false:
- `get_stacks_header_hashes` in `sortdb.rs` explicitly errors with `InvalidPoxSortition` when `!tip_snapshot.pox_valid` [3](#0-2) .
- `get_block_commit_for_stacks_block` explicitly errors on `!sn.pox_valid` [4](#0-3) .
- `validate_consensus_hash_reward_cycle_start` in the p2p layer explicitly NACKs when `!base_snapshot.pox_valid` [5](#0-4) .
- `PeerNetwork::get_tip_sortition_snapshot`/`get_ancestor_sortition_snapshot`/`get_peer_sortition_snapshot` all explicitly return `StaleView` on `!sn.pox_valid` [6](#0-5) .
- Even the Nakamoto push-block handler in `relay.rs` explicitly skips a block whose sortition snapshot has `!sn.pox_valid` [7](#0-6) .

The invalidation mechanism itself is `invalidate_descendants_with_closures`, which sets `pox_valid = 0` on all snapshots descending from a burn block whose PoX fork history is superseded (e.g., after a hidden/late-disclosed anchor block causes `process_new_pox_anchor` to call `invalidate_descendants_of`) [1](#0-0) [8](#0-7) . A `pox_valid = 0` snapshot means the consensus hash's sortition is no longer considered part of the canonical PoX-fork history, exactly like a blacklisted OP dispute game is no longer trustworthy for verification even though its on-chain record still physically exists.

`check_sortition_exists` is invoked from the Nakamoto block-processing/validation path to confirm a block's asserted burn view is a real, processed sortition before the block is accepted (used by `NakamotoChainState` in `mod.rs`, per the single reference found). Because it omits the `pox_valid` check that every sibling function performs, a block whose `consensus_hash` maps to a snapshot that has since been invalidated (via a PoX reorg / hidden anchor-block disclosure) can still pass this "sortition exists" check and have its burn-view treated as valid, even though the sortition DB itself has marked that consensus hash's fork-history entry as no longer canonical.

### Impact Explanation
This breaks the equality "a tenure's burn view must be drawn from the canonical, currently-valid PoX-fork sortition history." If a stale/invalidated snapshot is accepted as a legitimate burn view during block validation while other code paths (peer networking, header-hash retrieval, block-commit lookups) all correctly reject the same snapshot as `InvalidPoxSortition`/`StaleView`, nodes can diverge on whether a given Nakamoto block/tenure is valid — one code path (chainstate validation) says "sortition exists, proceed" while every other subsystem treats the same consensus hash as invalid. This is the class of "a tenure not descending from its sortition" / "a validation verdict two nodes disagree on" divergence: it can manifest as a temporarily accepted block that should have been rejected once PoX history is unwound, producing state-root/tip disagreement between nodes that have and have not yet processed the reorg.

### Likelihood Explanation
Triggering requires a PoX anchor-block disclosure/reorg scenario (`process_new_pox_anchor` → `invalidate_descendants_of`) which is a normal, unprivileged, minority-triggerable consensus event (a previously "missing" anchor block being revealed causes retroactive invalidation of descendant sortitions) — not an admin action or majority attack. Any block whose `consensus_hash` corresponds to a sortition later invalidated by such a reorg would hit this codepath.

### Recommendation
Add a `pox_valid` check to `check_sortition_exists`, mirroring the checks already present in `sortdb.rs::get_block_commit_for_stacks_block`, `net/chat.rs::validate_consensus_hash_reward_cycle_start`, and `net/relay.rs`'s push-block handling — i.e., reject (`ChainstateError::NoSuchBlockError` or equivalent) if `snapshot.pox_valid` is false.

### Proof of Concept
1. Node processes burn blocks and sortitions normally; a Nakamoto block references `consensus_hash = CH1` whose snapshot is stored with `pox_valid = 1`.
2. A previously-missing PoX anchor block is later revealed/disclosed, causing the coordinator to call `process_new_pox_anchor` → `SortitionDB::invalidate_descendants_of`, which runs `invalidate_descendants_with_closures` and sets `pox_valid = 0` for all snapshots descending from the reorg point, including the snapshot for `CH1` [8](#0-7) [1](#0-0) .
3. A Nakamoto block (or a re-processing attempt) referencing `CH1` as its burn view is validated via `check_sortition_exists`, which only checks `snapshot.consensus_hash == block_consensus_hash` and does not check `pox_valid` [9](#0-8) ; the function returns `Ok(snapshot)` despite the snapshot being marked invalid.
4. Meanwhile, other subsystems (peer inventory sync, block-commit lookup, header-hash retrieval) correctly refuse to serve/trust this same `consensus_hash` because of the `pox_valid` check, creating inconsistent acceptance of the tenure across the codebase/nodes.

    pub(crate) fn check_sortition_exists(
        burn_dbconn: &SortitionHandleConn,
        block_consensus_hash: &ConsensusHash,
    ) -> Result<BlockSnapshot, ChainstateError> {
        // check that the burnchain block that this block is associated with has been processed.
        // N.B. we must first get its hash, and then verify that it's in the same Bitcoin fork as
        // our `burn_dbconn` indicates.
        let burn_header_hash =
            SortitionDB::get_burnchain_header_hash_by_consensus(burn_dbconn, block_consensus_hash)?
                .ok_or_else(|| {
                    warn!(
                        "Unrecognized consensus hash";
                        "consensus_hash" => %block_consensus_hash,
                    );
                    ChainstateError::NoSuchBlockError
                })?;

        let snapshot = burn_dbconn
            .get_block_snapshot(&burn_header_hash)?
            .ok_or_else(|| {
                warn!(
                    "Tried to process Nakamoto block before its burn view was processed";
                    "burn_header_hash" => %burn_header_hash,
                );
                ChainstateError::NoSuchBlockError
            })?;

        if snapshot.consensus_hash != *block_consensus_hash {
            // should be unreachable, but check defensively
            warn!(
                "Snapshot for {} is not the same as the one for {}",
                &burn_header_hash, block_consensus_hash
            );
            return Err(ChainstateError::NoSuchBlockError);
        }

        Ok(snapshot)
    }

    fn get_tip_sortition_snapshot(&self, sortdb: &SortitionDB) -> Result<BlockSnapshot, net_error> {
        match SortitionDB::get_block_snapshot(sortdb.conn(), &self.tip_sort_id)? {
            Some(sn) => {
                if !sn.pox_valid {
                    // our sortition ID tip got invalidated
                    return Err(net_error::StaleView);
                }
                Ok(sn)
            }
            None => Err(net_error::StaleView),
        }
    }

    /// Get an ancestor snapshot, accounting for PoX invalidation
    pub fn get_ancestor_sortition_snapshot(
        &self,
        sortdb: &SortitionDB,
        height: u64,
    ) -> Result<BlockSnapshot, net_error> {
        let sn = self.get_tip_sortition_snapshot(sortdb)?;
        if sn.block_height < height {
            debug!(
                "Tip sortition snapshot is at {} < {}",
                sn.block_height, height
            );
            return Err(net_error::NotFoundError);
        }

        let ic = sortdb.index_conn();
        match SortitionDB::get_ancestor_snapshot(&ic, height, &sn.sortition_id)? {

                    // our sortition ID tip got invalidated
                    return Err(net_error::StaleView);
                }
                Ok(sn)
            }
            None => Err(net_error::StaleView),
        }
    }
