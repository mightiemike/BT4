### Title
Non-atomic execute() in AccountPermissionUpdateActuator commits permission mutation before fee deduction, allowing fee-free permission changes on reported FAILED transactions - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)` and persists it via `accountStore.put(ownerAddress, account)` **before** calling `adjustBalance(accountStore, ownerAddress, -fee)`, which can throw `BalanceInsufficientException`. When the fee deduction fails, the catch block only sets the transaction result to `FAILED` and rethrows `ContractExeException`, but the already-committed permission mutation is never rolled back.

### Finding Description
The relevant code: [1](#0-0) 

Execution order:
1. `account.updatePermissions(...)` mutates the in-memory `AccountCapsule`.
2. `accountStore.put(ownerAddress, account)` immediately persists the new permission to the account store (line 52).
3. `adjustBalance(accountStore, ownerAddress, -fee)` (line 54) re-reads the account and attempts to subtract the fee; if the balance is insufficient it throws `BalanceInsufficientException` *before* mutating/persisting the balance.
4. The catch block (lines 62-66) sets `result.setStatus(fee, code.FAILED)` and throws `ContractExeException`.

Because `accountStore` writes (a `TronStoreWithRevoking`-backed store) are not scoped to an atomic per-transaction session — they only revert on a whole-block `Session` rollback, not on a caught exception inside a single actuator's `execute()` — the permission write from step 2 remains committed in the store even though the transaction is reported as `FAILED` and the fee was never actually charged. This breaks the implicit all-or-nothing invariant expected of `execute()`: on exception, either nothing should be persisted, or (consistent with TRON's normal fee semantics) at least the fee should still be charged for the attempted state change. Here, neither is guaranteed — the mutation lands for free.

`validate()` does not check balance sufficiency against `getUpdateAccountPermissionFee()` at all — it only checks permission structure, `getAllowMultiSign()`, key counts/weights, etc. [2](#0-1) 
So a transaction with insufficient balance for the fee still passes `validate()` and reaches `execute()`, guaranteeing the vulnerable ordering is reachable through the normal actuator pipeline.

### Impact Explanation
An account owner (self-signed transaction, no privileged role required) can intentionally send an `AccountPermissionUpdateContract` while holding a balance below `getUpdateAccountPermissionFee()`. The permission update is committed to `accountStore` and becomes the account's active permission state, while the transaction result code is `FAILED` and the required fee is never actually deducted. This is a state/exception-consistency bug: it allows fee evasion for permission updates, and it creates a misleading on-chain result — any consumer (light client, exchange, wallet) that trusts `code.FAILED` to mean "no state change occurred" will have an incorrect view of the account's actual permission configuration. This falls into the "unauthorized/uncosted state change" and "accounting/fee-bypass" impact class rather than direct theft of third-party assets, since only the signer's own account permission is affected.

### Likelihood Explanation
The precondition (balance strictly less than `getUpdateAccountPermissionFee()` but a valid, well-formed permission contract) is trivial and entirely attacker-controlled — any ordinary account can arrange its own balance to be in this range and broadcast a normal, signed `AccountPermissionUpdateContract`. No special privileges, timing races, or non-default configuration are needed, and the bug is deterministically reproducible every time this exact balance condition is met.

### Recommendation
Reorder the actuator so that the fee is validated/deducted (or at minimum computed and its sufficiency checked) before any permission mutation is written to `accountStore`, i.e. call `adjustBalance(accountStore, ownerAddress, -fee)` first, and only call `account.updatePermissions(...)` / `accountStore.put(...)` after the fee deduction succeeds. Alternatively/also, add an explicit balance-sufficiency check in `validate()` against `calcFee()`, consistent with how other fee-charging actuators validate balance upfront.

### Proof of Concept
```java
@Test
public void permissionAppliedDespiteFeeFailure() throws Exception {
  byte[] owner = ByteArray.fromHexString(OWNER_ADDRESS);
  AccountCapsule account = dbManager.getAccountStore().get(owner);
  long fee = dbManager.getDynamicPropertiesStore().getUpdateAccountPermissionFee();
  account.setBalance(fee - 1); // insufficient for fee, but > 0
  dbManager.getAccountStore().put(owner, account);

  AccountPermissionUpdateActuator actuator = new AccountPermissionUpdateActuator();
  actuator.setChainBaseManager(dbManager.getChainBaseManager())
      .setAny(getValidPermissionUpdateContract(OWNER_ADDRESS)); // well-formed permissions

  actuator.validate(); // passes: no balance check here

  TransactionResultCapsule ret = new TransactionResultCapsule();
  try {
    actuator.execute(ret);
    fail("expected ContractExeException");
  } catch (ContractExeException e) {
    Assert.assertEquals(code.FAILED, ret.getInstance().getRet());
  }

  // Permission mutation persisted despite FAILED status and no fee charged
  AccountCapsule after = dbManager.getAccountStore().get(owner);
  Assert.assertEquals(newOwnerPermission, after.getInstance().getOwnerPermission());
  Assert.assertEquals(fee - 1, after.getBalance()); // fee not actually deducted
}
```
Expected result: the assertion confirms the new `getOwnerPermission()` is already applied and persisted in `accountStore` even though the actuator threw `ContractExeException` and the transaction result is `FAILED`, and the fee balance was never actually subtracted.

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }
