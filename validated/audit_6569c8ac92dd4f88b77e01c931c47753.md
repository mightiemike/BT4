## Finding: `handleFailedInboundValidation` creates a PENDING revert outbound without checking `IsChainOutboundEnabled`, permanently stranding reverted funds

### Summary
`buildRevertOutbound` / `attachOutboundsToUtx` — used by `handleFailedInboundValidation` and every other revert path — creates an `INBOUND_REVERT` `OutboundTx` with `OutboundStatus_PENDING` and inserts it into `PendingOutbounds` without ever checking whether outbound processing is enabled for the destination chain (which is the inbound's `SourceChain`). This is inconsistent with `BuildOutboundsFromReceipt`, which explicitly calls `k.uregistryKeeper.IsChainOutboundEnabled` and refuses to create the outbound if disabled. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`x/uregistry` models chain enablement as two independent flags, `IsInboundEnabled` and `IsOutboundEnabled` [4](#0-3) , and this asymmetric state is a normal, expected operational condition — not a contrived edge case. In particular, `x/utss`'s `InitiateFundMigration` (TSS key rotation for a chain) explicitly *requires* outbound to already be disabled for the chain, while doing nothing to disable inbound: [5](#0-4) 

So during a routine, honest TSS-migration window, a chain can legitimately be `inbound=true, outbound=false`. While inbound is still enabled, an ordinary unprivileged user's inbound deposit that fails `ValidateForExecution` (e.g. malformed payload, unsupported asset config, oversized amount, etc.) drives the code into `handleFailedInboundValidation`, which calls `buildRevertOutbound` and `attachOutboundsToUtx` unconditionally for non-CEA inbounds: [6](#0-5) 

Unlike `BuildOutboundsFromReceipt` — the analogous path for normal (non-revert) outbound creation — neither `buildRevertOutbound` nor `attachOutboundsToUtx` checks `IsChainOutboundEnabled` before setting `OutboundStatus_PENDING` and writing the `PendingOutbounds` index entry: [7](#0-6) 

The same unguarded call pattern exists in every other revert-creation site (`execute_inbound_funds.go`, `execute_inbound_funds_and_payload.go`, `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`, `admin_revert.go`), confirming the gap is systemic to the revert path rather than a one-off oversight.

Once created, this `PENDING` outbound is never picked up by honest universal validators: the off-chain client explicitly refuses to sign or broadcast it while outbound is disabled for the destination chain, at multiple layers —
- TSS coordinator: [8](#0-7) 
- session manager signing verification: [9](#0-8) 
- broadcaster: [10](#0-9) 

The module's own documentation confirms `PendingOutbounds` entries are never auto-cleaned and require governance/operator intervention: "Ballot expiry does NOT remove the entry ... Auto-refund risks double-pay ... resolution is governance-driven, not chain-driven." [11](#0-10) 

### Impact Explanation
The user's original funds are locked on the source chain (the gateway contract never released them, since the inbound never executed) awaiting the revert outbound to instruct TSS to send them back. Because the revert outbound was created despite outbound being disabled, it can never be signed or broadcast by honest UVs while that chain state persists, so the user's funds remain frozen on the source chain indefinitely with no relayer/validator path to unstick them — this is a real, unprivileged-user-reachable "permanent freezing of user ... funds," and it also corrupts the intended `PENDING`-outbound invariant (a `PENDING` entry should always be eventually actionable by honest validators, mirroring the guard already present in `BuildOutboundsFromReceipt`). It additionally undermines the "no pending outbounds" precondition that `InitiateFundMigration` deliberately enforces before rotating TSS keys, since a new pending outbound can be created for a chain mid-migration through this ungated path.

### Likelihood Explanation
The triggering precondition — `inbound enabled, outbound disabled` — is a normal, admin-driven, honest operational state (explicitly required by `InitiateFundMigration`), not a contrived or malicious one. Any unprivileged user submitting a deposit that fails `ValidateForExecution` during that window (which can be deliberately engineered by the attacker via a malformed/edge-case inbound payload) triggers the bug deterministically. No malicious validators, admins, or TSS participants are required — only that this legitimate config state exists at the same time as an ordinary user transaction.

### Recommendation
Before calling `attachOutboundsToUtx` for a revert outbound (in `buildRevertOutbound`/its callers, including `handleFailedInboundValidation`, `execute_inbound_funds*.go`, `execute_inbound_gas*.go`, and `admin_revert.go`), check `k.uregistryKeeper.IsChainOutboundEnabled(ctx, inbound.SourceChain)` the same way `BuildOutboundsFromReceipt` does. If outbound is disabled, either defer creation of the revert outbound until it is re-enabled (e.g., queue it separately) or mark the `UniversalTx`/outbound state explicitly (e.g. `ABORTED`) with a clear operator-actionable error instead of silently leaving a `PENDING` entry that can never be honestly serviced.

### Proof of Concept
1. As chain admin (or during a routine TSS migration flow), disable outbound for chain `eip155:X` while leaving inbound enabled (`InitiateFundMigration` requires exactly this state).
2. As an unprivileged user, submit an inbound deposit from `eip155:X` whose payload/amount causes `inbound.ValidateForExecution()` to fail after ballot finalization (e.g., an invalid/unsupported universal payload).
3. Observe `VoteInbound` → `handleFailedInboundValidation` → `buildRevertOutbound` → `attachOutboundsToUtx` create an `OutboundTx` with `TxType_INBOUND_REVERT`, `OutboundStatus_PENDING`, indexed in `PendingOutbounds`, with no error and no check against `IsChainOutboundEnabled`.
4. Confirm via `universalClient` code paths (`coordinator.go`, `sessionmanager.go`, `broadcaster.go`) that this outbound will never be signed/broadcast while outbound remains disabled for `eip155:X`, leaving it permanently `PENDING` and the user's source-chain funds permanently frozen.

func (k Keeper) attachOutboundsToUtx(
	ctx sdk.Context,
	utxId string,
	outbounds []*types.OutboundTx,
	revertMsg string, // revert msg if the outbound is for a inbound revert
) error {

	if len(outbounds) == 0 {
		return nil
	}
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {

		for _, outbound := range outbounds {

			utx.OutboundTx = append(utx.OutboundTx, outbound)

			// Compute signature expiry deadline for the destination chain.
			var signingDeadline int64
			if chainCfg, err := k.uregistryKeeper.GetChainConfig(ctx, outbound.DestinationChain); err == nil {
				if chainCfg.TssSigningDeadline != nil && *chainCfg.TssSigningDeadline > 0 {
					signingDeadline = ctx.BlockTime().Unix() + int64(chainCfg.TssSigningDeadline.Seconds())
				}
			}

			// Write to pending outbounds index (inside UpdateUniversalTx closure for atomicity)
			if err := k.PendingOutbounds.Set(ctx, outbound.Id, types.PendingOutboundEntry{
				OutboundId:      outbound.Id,
				UniversalTxId:   utxId,
				CreatedAt:       ctx.BlockHeight(),
				SigningDeadline: signingDeadline,
			}); err != nil {
				return fmt.Errorf("failed to set pending outbound index for %s: %w", outbound.Id, err)
			}

// buildRevertOutbound creates an INBOUND_REVERT outbound with gas fields populated
// from the UniversalCore contract via getOutboundTxGasAndFees.
func (k Keeper) buildRevertOutbound(sdkCtx sdk.Context, inbound *types.Inbound) *types.OutboundTx {
	recipient := inbound.Sender
	if inbound.RevertInstructions != nil && inbound.RevertInstructions.FundRecipient != "" {
		recipient = inbound.RevertInstructions.FundRecipient
	}

	outbound := &types.OutboundTx{
		DestinationChain:  inbound.SourceChain,
		Recipient:         recipient,
		Amount:            inbound.Amount,
		ExternalAssetAddr: inbound.AssetAddr,
		Sender:            inbound.Sender,
		TxType:            types.TxType_INBOUND_REVERT,
		OutboundStatus:    types.Status_PENDING,
		Id:                types.GetOutboundRevertId(inbound.SourceChain, inbound.TxHash, inbound.LogIndex),
	}
