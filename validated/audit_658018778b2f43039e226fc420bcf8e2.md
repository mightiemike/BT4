## Analysis: Unbounded `UniversalPayload.Data` combined with fee-free, funding-free `MsgExecutePayload` admission enables free-of-cost compute DoS

The C4 report's root cause — user-controlled data with no length bound that gets repeatedly processed downstream, letting an attacker impose large gas/compute costs relative to what they pay — has a structural analog in Push Chain's `x/uexecutor` module around `MsgExecutePayload`.

### Key facts

`UniversalPayload.ValidateBasic()` validates hex-formatting and that numeric string fields parse as unsigned integers, but never bounds the length of `Data`: [1](#0-0) 

`MsgExecutePayload.ValidateBasic()` likewise only checks presence/format of fields, never payload size: [2](#0-1) 

`MsgExecutePayload` is in the gasless allowlist — the signer pays **no Cosmos fee**, and per the module README, "Any account may submit the message": [3](#0-2) [4](#0-3) 

`DeductFeeDecorator` and `MinGasPriceDecorator` both explicitly skip all fee checks for gasless txs: [5](#0-4) [6](#0-5) 

`AccountInitDecorator` additionally lets a brand-new, **unfunded** account submit a gasless tx — it auto-creates the account mid-pipeline and bypasses the rest of signature/gas verification: [7](#0-6) 

`ExecutePayload` resolves the UEA address via a real EVM call to the factory, then — if the target UEA is already deployed — proceeds directly into `CallUEAExecutePayload`, which sends the full (unbounded) payload as EVM calldata. Fee is only deducted *after* execution completes/reverts: [8](#0-7) 

### Why this matters

Combining these facts: an unprivileged attacker can spin up unlimited fresh, unfunded accounts (via `AccountInitDecorator`), and submit `MsgExecutePayload` messages — targeting any real, already-deployed UEA address (publicly observable) — carrying an arbitrarily large `UniversalPayload.Data` blob and a bogus `VerificationData`. Each submission is free (no Cosmos fee, no funding requirement), yet forces the node to perform real work: ABI encoding/validation, a factory EVM call to resolve the UEA, and EVM execution of the oversized calldata up to the point the contract-level signature check reverts — all before any fee deduction is attempted. Because there is no length cap on `Data` and no privileged gate on who may submit `MsgExecutePayload`, this asymmetric-cost pattern (cheap/free for the attacker, expensive for the network to process) is the direct structural analog of the CultureIndex `createPiece` issue, where unbounded user-supplied data size let an attacker impose disproportionate downstream costs.

I did not find any repository-side cap on `UniversalPayload.Data` length, nor evidence that `CallUEAExecutePayload`/`CallFactoryToGetUEAAddressForOrigin` short-circuit before processing the full calldata for unfunded/undeployed targets when the target UEA *is* already deployed. I could not verify CometBFT-level `max_tx_bytes`/mempool size configuration in this repository (that's typically node `config.toml`, not part of this codebase), so the practical per-tx size ceiling and thus the real severity of the amplification depend on deployment-level config not visible here.

### Title
Unbounded `UniversalPayload.Data` in gasless, funding-free `MsgExecutePayload` enables free compute-DoS against Push Chain nodes - (File: `x/uexecutor/types/universal_payload.go`)

### Summary
`UniversalPayload.ValidateBasic()` and `MsgExecutePayload.ValidateBasic()` never bound the size of the `Data` field. `MsgExecutePayload` is a gasless, unprivileged message type that any account — including a freshly-created, unfunded one (via `AccountInitDecorator`) — may submit. Processing happens (factory EVM call + `CallUEAExecutePayload`) before any fee is deducted, so an attacker can force real node compute against an arbitrarily large payload at zero cost.

### Finding Description
See analysis above; the chain of `ValidateBasic` checks (`x/uexecutor/types/universal_payload.go` lines 24-39, `x/uexecutor/types/msg_execute_payload.go` lines 48-83) never validates `Data` length. The gasless allowlist (`app/txpolicy/gasless.go`) includes `MsgExecutePayload`, and the ante pipeline (`app/ante/fee.go`, `app/cosmos/min_gas_price.go`, `app/ante/account_init_decorator.go`) skips fee/funding requirements for such txs. `ExecutePayload` (`x/uexecutor/keeper/msg_execute_payload.go`) performs a factory EVM call and `CallUEAExecutePayload` execution against an attacker-chosen, already-deployed UEA before fee deduction is attempted.

### Impact Explanation
An unprivileged, unfunded attacker can repeatedly submit large-payload `MsgExecutePayload` transactions at zero Cosmos fee cost, forcing nodes/validators to expend CPU on ABI decoding and EVM setup/execution disproportionate to what the attacker pays — a denial-of-service vector reachable without any privileged role, consistent with the allowed "gasless admission" and "non-network-level DoS" impact categories.

### Likelihood Explanation
Medium: requires only creating unfunded accounts (trivial, free) and targeting a publicly-known deployed UEA address; no validator or admin collusion needed. Actual severity depends on external CometBFT-level tx/mempool size limits not present in this repository's scope, which I could not verify here.

### Recommendation
Add an explicit maximum length check on `UniversalPayload.Data` (and other variable-length fields) in `UniversalPayload.ValidateBasic()`, and consider requiring minimal balance/funding or rate-limiting for `MsgExecutePayload` submissions from newly-initialized accounts before allowing expensive EVM-call resolution/execution.

### Proof of Concept
Not independently executed; derived from static review of `ValidateBasic` implementations, the gasless allowlist, and the ante-handler decorator chain referenced above. A live PoC would submit repeated `MsgExecutePayload` txs from freshly-created unfunded accounts against a known deployed UEA, each carrying a maximal-size `Data` field and bogus `VerificationData`, and measure per-tx node CPU/time versus the zero fee paid.

// ValidateBasic does a sanity check on the provided data.
func (msg *MsgExecutePayload) ValidateBasic() error {
	// Validate signer
	if _, err := sdk.AccAddressFromBech32(msg.Signer); err != nil {
		return errors.Wrap(err, "invalid signer address")
	}

	// Validate universalAccountId
	if msg.UniversalAccountId == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal account cannot be nil")
	}

	// Validate universal payload
	if msg.UniversalPayload == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "universal payload cannot be nil")
	}

	// Validate verificationData
	if len(msg.VerificationData) == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "verificationData cannot be empty")
	}
	if _, err := hex.DecodeString(strings.TrimPrefix(msg.VerificationData, "0x")); err != nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "invalid verificationData hex")
	}

	// Validate universalAccountId structure
	if err := msg.UniversalAccountId.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universalAccountId")
	}

	// Validate universal payload structure
	if err := msg.UniversalPayload.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid universal payload")
	}

	return nil

```markdown
### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
```
