### Title
Unbounded per-request O(N) work in non-paginated asset-issue RPC-API endpoints enables sustained CPU DoS - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getAssetIssueList()` and `Wallet.getAssetIssueByAccount(ByteString)` (and similarly `getAssetIssueListByName`) fetch the *entire* `AssetIssueStore`/`AssetIssueV2Store` via `getAllAssetIssues()` and run a `BandwidthProcessor.updateUsage(AssetIssueCapsule)` call plus a protobuf serialization for every single asset issue on every call, with no pagination and no per-item cost charged to the caller. An attacker who inflates the number of asset issues can make each subsequent call to the corresponding HTTP/gRPC endpoints do O(N) work, while the endpoints are only protected by a flat QPS-style rate limiter (default `qps=1000` / `global.api.qps`) that does not scale down with the cost of the underlying request.

### Finding Description
`Wallet.getAssetIssueList()` [1](#0-0)  and `Wallet.getAssetIssueByAccount(ByteString)` [2](#0-1)  both call `getAssetIssueStoreFinal(...).getAllAssetIssues()`, which iterates the whole underlying LevelDB/RocksDB store and materializes every `AssetIssueCapsule` into a `List` [3](#0-2) . For every element, a fresh `BandwidthProcessor` is invoked via `processor.updateUsage(issueCapsule)`, which does arithmetic and time-based recovery calculations [4](#0-3) , and the capsule is serialized into the response builder.

These methods are directly reachable, unauthenticated, from:
- HTTP `GetAssetIssueListServlet.doGet/doPost` → `wallet.getAssetIssueList()` [5](#0-4) 
- gRPC `WalletSolidityApi.getAssetIssueList` / full-node `Wallet` service → `wallet.getAssetIssueList()` [6](#0-5) 
- Analogous non-paginated `getAssetIssueByAccount` / `getAssetIssueListByName` code paths [7](#0-6) 

A paginated overload exists (`getAssetIssueList(offset, limit)` bounded by `ASSET_ISSUE_COUNT_LIMIT_MAX` [8](#0-7) ), but the *default*, most commonly used endpoint (`getassetissuelist`, gRPC `GetAssetIssueList`) is the unbounded one, and `getAssetIssueByAccount`/`getAssetIssueListByName` have no paginated counterpart at all.

The only gate present is the generic HTTP/gRPC rate limiter (`RateLimiterServlet`), which defaults to a flat QPS cap (`DEFAULT_QPS_PARAM` from `global.api.qps`, default 1000) [9](#0-8) [10](#0-9) . This rate limiter counts *requests*, not *work per request*, so it does not mitigate a scenario where each permitted request costs O(N) instead of O(1).

Growing N (the AssetIssueStore size) requires broadcasting `AssetIssueContract` transactions. `AssetIssueActuator.validate()` enforces a real TRX fee (`calcFee()` = `dynamicStore.getAssetIssueFee()`) and restricts issuance to accounts that have not already issued an asset (`accountCapsule.getAssetIssuedName().isEmpty()`) [11](#0-10) . This means the attacker cannot grow the store for free from a single account — each new asset issue requires a distinct, funded account and payment of the configured asset-issue fee, which is real chain economics friction rather than a hard technical bound on N.

### Impact Explanation
This matches the "DoS via RPC-API" impact class: an attacker can cause disproportionate CPU consumption on any node's public/solidity/PBFT RPC and HTTP endpoints via unauthenticated, repeatable calls to `GetAssetIssueList`/`getassetissuelist` and `GetAssetIssueByAccount` once the AssetIssueStore is inflated. Every permitted call re-walks the full store and re-runs bandwidth-usage math per entry, producing latency/CPU cost proportional to N rather than to the request itself. Because the mutation in `updateUsage(AssetIssueCapsule)` is applied only to the in-memory capsule object returned from the store getter and is not written back to the store in these query paths, there is no accounting/state-corruption impact — the exploitable impact is limited to increased latency/CPU load (DoS), not double-spend, asset corruption, or consensus divergence.

### Likelihood Explanation
Feasibility depends on how large N can practically get. Each unit of growth costs the attacker: (a) a distinct account (unprivileged, self-funded — trivial to generate many key pairs and fund them with small transfers), and (b) the configured `getAssetIssueFee()` TRX cost per asset issued, plus normal bandwidth/fee for broadcasting the transaction. This is a real, non-trivial but bounded cost, not a free amplification; on public mainnet with a meaningful fee this limits the practical N an attacker can cheaply create, though on a low-fee private/test network or over time with modest capital, N can still be pushed into the tens/hundreds of thousands, at which point the linear-scan cost per RPC call becomes noticeable. Once N is elevated, exploiting the read side is trivial and free/cheap (no transaction, just repeated read-only RPC/HTTP calls up to the flat QPS ceiling), and is fully repeatable indefinitely since assets cannot be deleted from the store by design.

### Recommendation
- Make the paginated method (`getAssetIssueList(offset, limit)`, already bounded by `ASSET_ISSUE_COUNT_LIMIT_MAX`) the only supported form for public/solidity/PBFT endpoints, or enforce a hard maximum page size on the non-paginated `getAssetIssueList()`/`getAssetIssueByAccount()`/`getAssetIssueListByName()` before iterating.
- Add pagination (offset/limit) to `getAssetIssueByAccount` and `getAssetIssueListByName`, since these currently have no bounded alternative at all.
- Consider a rate-limiting strategy that accounts for response/result size or store size, not just request count, for these specific endpoints (e.g., a stricter dedicated QPS/permit strategy configured in `rate.limiter.http`/`rate.limiter.rpc` for these servlets/methods).
- Avoid calling a full `BandwidthProcessor.updateUsage` pass over every asset issue on every query call if the mutated bandwidth-usage figures are not being persisted/read back meaningfully in this context.

```java
// JUnit-style PoC (framework/src/test/java/org/tron/core/WalletTest.java style)
@Test
public void testAssetIssueListLinearScaling() {
  int[] sizes = {1_000, 10_000, 50_000};
  for (int n : sizes) {
    for (int i = 0; i < n; i++) {
      AssetIssueContract c = AssetIssueContract.newBuilder()
          .setOwnerAddress(ByteString.copyFrom(randomAddress()))
          .setName(ByteString.copyFromUtf8("token" + i))
          .setId(Long.toString(i))
          .setTotalSupply(1)
          .setTrxNum(1)
          .setNum(1)
          .setStartTime(1)
          .setEndTime(Long.MAX_VALUE)
          .build();
      AssetIssueCapsule capsule = new AssetIssueCapsule(c);
      chainBaseManager.getAssetIssueStore().put(capsule.createDbKey(), capsule);
      chainBaseManager.getAssetIssueV2Store().put(capsule.createDbV2Key(), capsule);
    }
    long start = System.nanoTime();
    for (int call = 0; call < 20; call++) {
      wallet.getAssetIssueList(); // non-paginated, unauthenticated-reachable endpoint
    }
    long elapsed = System.nanoTime() - start;
    System.out.println("N=" + n + " elapsed(ns)=" + elapsed);
    // assert elapsed grows roughly linearly with n, confirming O(N) per-call cost
  }
}
```
Expected result: per-call latency scales linearly with the number of stored asset issues, confirming that repeated calls to `/wallet/getassetissuelist` or gRPC `GetAssetIssueList` cost the node CPU proportional to attacker-inflated global state, bounded only by the flat request-count rate limiter rather than by request cost.

```java
  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
```
