## Analysis

The external report's core bug class is: **nested/nested-scale iteration over an attacker-growable collection performed inside a message-processing hot path, with no bound on the collection size, letting an unprivileged actor make each subsequent operation more expensive (up to a DoS).** The closest reachable analog in Push Chain's scoped code is in `x/uvalidator`'s generic ballot machine, specifically `CreateBallot`'s unconditional call to `ExpireBallotsBeforeHeight`.

Every new ballot — created for every uniquely-keyed inbound observation, outbound observation, TSS event, or migration event — triggers a full walk of **all currently active ballots** in the store: [1](#0-0) 

That walk is implemented as an unbounded two-phase scan over `ActiveBallotIDs`, fetching every ballot record from the KV store to check its expiry height: [2](#0-1) 

Ballot IDs for inbound observations are derived deterministically from the observed `Inbound` payload bytes (`source_chain:tx_hash:log_index`, etc.), which are effectively attacker-influenceable because an unprivileged user can generate many cheap, distinct source-chain transactions/log indices (e.g., dust deposits on a low-fee source chain) that validators will observe and vote on, each producing a brand-new, unique ballot via `VoteOnInboundBallot` → `k.uvalidatorKeeper.VoteOnBallot` → `GetOrCreateBallot`/`CreateBallot`: [3](#0-2) 

Within a single ballot expiry window (`DefaultExpiryAfterBlocks`), each such attacker-triggered event adds one more entry to `ActiveBallotIDs` that is never pruned until it naturally expires. Since `ExpireBallotsBeforeHeight` is invoked synchronously on *every* new ballot creation and scans the *entire* active set each time, the cost of processing the N-th distinct inbound observation in the window is O(N), and the cumulative cost of N such attacker-generated events within one window is O(N²) — the same superlinear blow-up pattern the external report calls out, just manifesting as validator/consensus-processing cost growth (store reads inside `VoteInbound`/`VoteOutbound` message handling) rather than EVM gas.

This differs from the `farm-manager` `claim` case in mechanism (Cosmos SDK message handling vs. CosmWasm gas metering) but is the same root cause: an unbounded loop over a collection whose size is driven by ordinary, unprivileged user activity, executed inside a commonly-hit write path. Related evidence that pending-ballot/entry sets are known to grow unboundedly and require manual/upgrade-handler cleanup is visible in the `purge-expired-outbounds` upgrade handler and the `PendingOutbounds`/`PendingInbounds` design notes, which explicitly acknowledge that entries are not always promptly pruned: [4](#0-3) 

I did not find an existing cap on `ActiveBallotIDs` size, rate limit on inbound-vote submission, or a decoupling of ballot creation from the expiry-sweep — the scan runs inline, synchronously, on every `CreateBallot` call.

### Title
Unbounded per-call active-ballot scan in `CreateBallot` enables attacker-driven superlinear DoS in validator vote processing - (File: x/uvalidator/keeper/ballot.go)

### Summary
`CreateBallot` unconditionally invokes `ExpireBallotsBeforeHeight`, which performs a full linear scan of `ActiveBallotIDs` (fetching every active ballot record) on every single new ballot creation. Because ballot creation is triggered by ordinary, unprivileged deposit/observation activity (each uniquely-keyed inbound or outbound event produces its own ballot), an attacker can cheaply grow `ActiveBallotIDs` and force every subsequent vote-processing call in the same expiry window to pay an increasing, unbounded cost.

### Finding Description
`x/uvalidator/keeper/ballot.go`'s `CreateBallot` calls `k.ExpireBallotsBeforeHeight(ctx, blockHeight)` before creating any new ballot [1](#0-0) . `ExpireBallotsBeforeHeight` iterates the entire `ActiveBallotIDs` collection, doing a `k.Ballots.Get` for each one, to find candidates past their expiry height [2](#0-1) .

Ballot creation for `INBOUND_TX` ballots happens via `VoteOnInboundBallot`/`VoteOnBallot`/`GetOrCreateBallot` every time a validator votes on a *new* logical inbound event, keyed by the marshaled `Inbound` bytes (which include attacker-observable `source_chain`, `tx_hash`, `log_index`) [5](#0-4) . Because an unprivileged user can submit many distinct cheap transactions on an external source chain (each with a unique tx hash/log index), validators will observe and vote on each as a separate inbound event, and the chain will create a new ballot for each via `CreateBallot`.

Within a single ballot expiry window (`DefaultExpiryAfterBlocks`), ballots that have not yet reached their expiry height remain in `ActiveBallotIDs`. Every additional attacker-triggered event therefore both (a) adds to the active set and (b) forces the *next* `CreateBallot` call (for the next event, from any validator, for any purpose — inbound, outbound, TSS, migration) to re-scan the now-larger active set. This produces O(N) work per new ballot and O(N²) aggregate work for N events generated inside one window, growing unbounded with attacker-supplied event volume, with no cap on `ActiveBallotIDs` size or decoupling of the sweep from the hot path.

This mirrors the `farm-manager` `claim` report's root cause: an iteration whose bound is controlled by accumulated, attacker-reachable state rather than a fixed protocol constant, executed inside common message-processing logic.

### Impact Explanation
This falls under the allowed "denial of service only when it is not network-level and is reachable without privileged control" impact. As the active-ballot set grows, processing time (store reads) for `MsgVoteInbound`/`MsgVoteOutbound`/TSS/migration vote messages from honest validators increases proportionally, degrading validator throughput and, in the worst case (very large attacker-generated backlog within one expiry window), materially slowing block processing for the entire node set — without requiring any validator, admin, or key compromise. It does not directly steal funds, but it degrades the universal-execution vote/finalization pipeline that all inbound settlement and finality depend on.

### Likelihood Explanation
Likelihood is moderate: triggering it requires generating a sustained volume of distinct, votable inbound (or outbound) events within a single ballot expiry window, which costs only the (typically low) fee of unrelated cheap source-chain transactions rather than any Push Chain resource, and requires no elevated permission on Push Chain. The severity scales with how cheap it is to produce distinct observable events on supported source chains and with the default `expiryAfterBlocks`/`DefaultExpiryAfterBlocks` window size.

### Recommendation
- Decouple ballot expiry sweeping from the ballot-creation hot path: run it periodically (e.g., in `EndBlocker`/a scheduled sweep) rather than synchronously inside every `CreateBallot` call, or bound the number of ballots scanned per call.
- Maintain a height-indexed (e.g., sorted-by-expiry) secondary index for active ballots so expired entries can be located and removed in O(log N) or O(1) amortized time instead of a full O(N) scan.
- Consider rate-limiting or batching how many new ballots a single validator vote can create within a short window, or applying per-source-chain quotas on new inbound ballot creation.

### Proof of Concept
1. An attacker submits many (e.g., thousands) of distinct low-value transactions to the gateway contract on a cheap source chain within a short time window, each with a unique `tx_hash`/`log_index`.
2. Universal Validators observe each as a distinct `Inbound` and call `VoteInbound` → `VoteOnInboundBallot` → `k.uvalidatorKeeper.VoteOnBallot` → `GetOrCreateBallot` → `CreateBallot` for each unique event.
3. Each `CreateBallot` call invokes `ExpireBallotsBeforeHeight`, which iterates the full, growing `ActiveBallotIDs` set (`x/uvalidator/keeper/ballot.go:320-347`), fetching every active ballot from the KV store.
4. As the attacker keeps submitting events faster than the expiry window clears them, the cost of each subsequent `CreateBallot` call — and therefore of processing each subsequent validator vote message across the whole set of validators — grows linearly with the number of outstanding events, yielding aggregate quadratic cost for the batch and measurable degradation of vote-processing throughput.

```go
// ExpireBallotsBeforeHeight checks active ballots and marks expired ones.
// It uses a two-phase approach: first collect IDs to expire, then mutate,
// to avoid modifying the ActiveBallotIDs collection during iteration.
func (k Keeper) ExpireBallotsBeforeHeight(ctx context.Context, currentHeight int64) error {
	iter, err := k.ActiveBallotIDs.Iterate(ctx, nil)
	if err != nil {
		return err
	}

	// Phase 1: collect IDs to expire
	var toExpire []string
	for ; iter.Valid(); iter.Next() {
		id, err := iter.Key()
		if err != nil {
			iter.Close()
			return err
		}

		ballot, err := k.Ballots.Get(ctx, id)
		if err != nil {
			iter.Close()
			return err
		}

		if ballot.BlockHeightExpiry <= currentHeight {
			toExpire = append(toExpire, id)
		}
	}
```
