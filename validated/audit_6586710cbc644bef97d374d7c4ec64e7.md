Based on my investigation, I found a real, self-documented gap in transaction-info verification, but I need to be precise about its actual severity, since the code comments already acknowledge it and gate it behind an unreleased feature.

### Title
`ensure_match_transaction_info` skips state/hot-state/position checkpoint hash validation during chunk replay verification - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` [1](#0-0)  is the function used by state-sync/backup replay verification to confirm that locally re-executed transaction output matches the authenticated `TransactionInfo` fetched (with proof) from a peer or archive. It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` [2](#0-1) .

### Finding Description
This function is invoked in `ChunkExecutor::verify_execution` during chunk replay verification (`db-tool replay-verify` / `replay_on_archive`), comparing freshly executed `TransactionOutput`s against `TransactionInfo`s obtained from an already-trusted/proof-verified source [3](#0-2) . It is also directly used by `aptos-move/cli` transaction replay tooling to validate replayed system/user transactions against on-chain `TransactionInfo` [4](#0-3) .

`TransactionInfoV1` carries `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` as first-class fields that are part of its BCS-hashed representation and thus part of what the accumulator commits to [5](#0-4) . These roots summarize the entire state tree (including the newer "hot state" and "native position" trading-related state) after the transaction — a materially different and much larger surface than the write-set hash already checked.

Because the comparator only hashes the write set and events, a re-executed transaction that produces an identical write set and events but a *different resulting state tree* (e.g., due to a divergent state-merkle assembly, hot-state eviction/promotion bug, or a native-position bug affecting `WriteSetV1`'s side-channel `Extension::NativePosition` data [6](#0-5) ) would still pass `ensure_match_transaction_info`. The code comment confirms this is a known, currently-open gap: *"replay-verify tooling ... can report a successful replay even when the authenticated position state root diverges from local execution"* [7](#0-6) .

### Impact Explanation
If exploited (or triggered by an independent bug elsewhere in state-checkpoint/hot-state/position computation), replay-verification and archive-replay tooling would falsely report state-root correctness while the actual computed state root diverges from the authenticated chain state — a proof-integrity blind spot matching the "authenticated response bound to wrong ledger version/root" impact class. However, this gap is explicitly gated: the comment states it must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`" [8](#0-7) , implying the feature that would make this a live mainnet issue is not yet turned on. I could not confirm from the index whether `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/hot-state-root-in-txn-info is currently active on mainnet or gated off; this materially affects whether the gap is presently exploitable versus a documented pre-launch TODO.

### Likelihood Explanation
Low-to-moderate as currently deployed, because this check is only reached in replay-verification/debugging tooling paths, not in the core consensus/commit path (which independently verifies via full-accumulator/`TransactionInfo` hash matching in `ChunkResultVerifier`/`verify_extends_ledger`, not via this comparator) [9](#0-8) . The gap only matters for tooling that relies on `ensure_match_transaction_info` as its sole correctness signal, and only becomes a genuine ledger-integrity risk once the trading-native/hot-state root features it references are enabled.

### Recommendation
Extend `ensure_match_transaction_info` to also compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present on the `TransactionInfo` variant) against locally recomputed values, before any dependent feature (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`) is enabled on mainnet.

### Proof of Concept
Not independently reproducible from the indexed code alone — the gap is a static, self-documented comparator omission rather than a demonstrated live exploit path; a full PoC would require constructing a divergent hot-state/position write and confirming it currently reaches `ensure_match_transaction_info` in a mainnet-relevant path (e.g., `replay-verify`), which I could not fully trace given tool-call limits.

**Caveat:** Given this is a self-acknowledged TODO in the code rather than a silently broken invariant, and I was unable to confirm the on-chain activation status of the associated feature flag, confidence in this being a currently-exploitable high/critical mainnet issue (as opposed to a known pre-launch gap) is limited.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }

impl ChunkResultVerifier for StateSyncChunkVerifier {
    fn verify_chunk_result(
        &self,
        parent_accumulator: &InMemoryTransactionAccumulator,
        ledger_update_output: &LedgerUpdateOutput,
    ) -> Result<()> {
        // In consensus-only mode, we cannot verify the proof against the executed output,
        // because the proof returned by the remote peer is an empty one.
        if cfg!(feature = "consensus-only-perf-test") {
            return Ok(());
        }

        THREAD_MANAGER.get_exe_cpu_pool().install(|| {
            let first_version = parent_accumulator.num_leaves();

            // Verify the chunk extends the parent accumulator.
            let parent_root_hash = parent_accumulator.root_hash();
            let num_overlap = self.txn_infos_with_proof.verify_extends_ledger(
                first_version,
                parent_root_hash,
                Some(first_version),
            )?;
            assert_eq!(num_overlap, 0, "overlapped chunks");

            // Verify transaction infos match
            ledger_update_output
                .ensure_transaction_infos_match(&self.txn_infos_with_proof.transaction_infos)?;

            Ok(())
        })
    }
