## Title
`EpochHistory::verify_ledger_info` silently accepts unverified `LedgerInfoWithSignatures` when the epoch is "too new" — signature/proof verification bypass during backup restore - ([File: storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs])

### Summary
`EpochHistory::verify_ledger_info` (`storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs:276-312`) is the function used by the transaction-restore and state-snapshot-restore pipelines to authenticate the `LedgerInfoWithSignatures` bound to backup chunks/manifests. When the epoch encoded in the supplied `LedgerInfoWithSignatures` exceeds the size of the locally known `epoch_endings` history, the function does not verify the validator signatures at all — it logs a warning and returns `Ok(())` unconditionally. Since the backup blob (manifest + proof files) is fully attacker/host-controlled input during restore, a malicious or compromised backup storage provider can supply an arbitrary, self-signed (or garbage-signed) `LedgerInfoWithSignatures` with an inflated epoch number to skip verification entirely, then use that unverified ledger info as the trusted root for verifying transaction-accumulator/state-snapshot proofs, letting it inject arbitrary fabricated write sets, transaction infos, or state roots into the restored ledger. [1](#0-0) 

### Finding Description
`EpochHistory` is built by restoring epoch-ending backups (validated against a genesis LedgerInfo / trusted waypoints and epoch-to-epoch validator-set chaining) and exposes `verify_ledger_info` for other restore controllers to authenticate ledger infos they encounter:

This is precisely the same "invalid validation" class as the external report: a required check that should always gate acceptance (verify a signature/whitelist condition) is instead bypassed under attacker-controlled input (an out-of-range index/epoch), returning success instead of rejecting. The comment itself ("won't be able to start if this data is malicious") acknowledges the check is deferred to an "upper level" that in fact does not exist for this call — it merely returns `Ok(())`.

`verify_ledger_info` is called directly by both:
- `TransactionRestoreController`/`LoadedChunk::load`, which uses the loaded `LedgerInfoWithSignatures` as the trust root to verify the `TransactionAccumulatorRangeProof` binding `WriteSet`s/`TransactionInfo`s/events to a root hash: [2](#0-1) 
- `StateSnapshotRestoreController::run_impl`, which uses it to authenticate the `TransactionInfoWithProof` whose `state_checkpoint_hash` becomes the trusted Jellyfish-Merkle root for restoring the entire state snapshot: [3](#0-2) 

In both flows, the `LedgerInfoWithSignatures`, the accompanying proof, and the raw data (transactions/write-sets or state chunks) all come from the same untrusted backup storage (`Arc<dyn BackupStorage>`). If that storage is malicious or compromised, the attacker can:
1. Control (or truncate) the epoch-ending backup so that `epoch_endings.len()` is smaller than the epoch it wants to forge.
2. Craft a `LedgerInfoWithSignatures` for the transaction/state-snapshot manifest whose `epoch()` is set beyond `epoch_endings.len()`, with an arbitrary/garbage `AggregateSignature` and an arbitrary root hash.
3. Because `verify_ledger_info` returns `Ok(())` without checking the signature or waypoint at all, this forged ledger info is accepted as trusted.
4. The attacker then builds internally-consistent (but entirely fabricated) `TransactionAccumulatorRangeProof`/`SparseMerkleRangeProof` values against their own forged root hash (since they fully control both the "proof" and the root), causing the restore process to durably commit fabricated write sets, transaction infos, or state values without ever having been endorsed by real validator signatures.

This breaks the fundamental proof/commitment invariant that all durable ledger data reaching storage via restore must be transitively anchored to genesine/validator-set-endorsed `LedgerInfo`s.

### Impact Explanation
This is a high-impact state-integrity issue: it allows unauthenticated, attacker-supplied backup data to be accepted as canonical ledger state during restore (transactions, write sets, events, and/or the entire state-tree snapshot), corrupting durable ledger data with values that never went through consensus/validator signing. Any node or service relying on `aptos-db-restore` against an untrusted or compromised storage backend (S3 bucket, GCS, custom `BackupStorage` implementation, or an on-path attacker able to swap backup contents) can be made to accept a forged chain history/state without detection, since no signature check occurs on the "too new" path.

### Likelihood Explanation
The likelihood is significant in any restore-from-remote-backup scenario since `BackupStorage` is inherently the attacker's point of control (it's the entire content the restore consumes) and the only defense against a malicious epoch value here is this exact check that is bypassed. No privileged access, governance, or admin assumption is needed — a party that can influence backup contents (e.g., through a compromised/malicious storage endpoint) triggers this directly. It requires the restoring node to not already have a wider trusted epoch history bounding the attacker's crafted epoch, which is naturally the case for any epoch beyond what the (attacker-provided) epoch-ending backup contains.

### Recommendation
Do not treat an epoch that exceeds `epoch_endings.len()` as "unverifiable-but-accepted." Instead:
- Reject (`bail!`) when `epoch > self.epoch_endings.len()` unless the caller explicitly indicates that a wider/complete epoch history proof will be verified at a strictly later stage (and only in a manner that cannot be short-circuited to `Ok(())`).
- Alternatively, require that `EpochHistory` be constructed so it always spans up to at least the target restore version/epoch before beginning transaction/state-snapshot restore, and turn the current "too new" branch into a hard error.

### Proof of Concept
1. Set up a `BackupStorage` implementation (or intercept an existing one) that serves:
   - An `EpochEndingBackup` manifest covering epochs `[0, N]` only (attacker fully controls/truncates this).
   - A `TransactionBackup` (or `StateSnapshotBackup`) manifest whose `proof` file contains a forged `(TransactionAccumulatorRangeProof, LedgerInfoWithSignatures)` where `LedgerInfoWithSignatures.ledger_info().epoch() == N+1` (or any epoch beyond `N`) and `signatures` is an arbitrary/empty `AggregateSignature`, and whose root hash is self-consistent with attacker-chosen fake `TransactionInfo`s/write sets.
2. Run `TransactionRestoreController`/`StateSnapshotRestoreController` against this storage with `epoch_history` built from the truncated `EpochEndingBackup`.
3. Observe that `LoadedChunk::load` (or `run_impl` in `state_snapshot/restore.rs`) calls `epoch_history.verify_ledger_info(&ledger_info)`, which hits the `epoch > self.epoch_endings.len()` branch and returns `Ok(())` without checking `signatures`.
4. Observe that `txn_list_with_proof.verify(...)` (or `txn_info_with_proof.verify(...)`) subsequently succeeds because the proof is self-consistent with the attacker's own forged root hash, and the fabricated transactions/state values are committed to the restored `AptosDB`.
