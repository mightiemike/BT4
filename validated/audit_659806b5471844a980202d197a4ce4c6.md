### Title
`ensure_match_transaction_info` in replay/verify tooling silently skips checkpoint-hash validation — hard-fork divergence in state/hot-state/position roots is not detected - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the sole comparator used by `db-tool replay-on-archive`, `aptos-debugger`, and `aptos-move/cli` replay/verify commands to confirm that a freshly re-executed transaction matches the transaction info that is authenticated (via the transaction accumulator) by validator signatures. The function checks status, gas, write-set hash, and event-root hash, but explicitly and admittedly does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. A replay run can therefore report full success even when the locally recomputed state/hot-state/position Merkle root diverges from the authenticated one in the backup/archive.

### Finding Description
`ensure_match_transaction_info` [1](#0-0)  validates:
- `status` vs `txn_info.status()`
- `gas_used` vs `txn_info.gas_used()`
- `write_set_hash` (`CryptoHash::hash(self.write_set())`) vs `txn_info.state_change_hash()`
- recomputed event-root hash vs `txn_info.event_root_hash()`

It never touches `txn_info.state_checkpoint_hash()`, `txn_info.hot_state_checkpoint_hash()`, or `txn_info.position_state_checkpoint_hash()`. The function's own trailing comment documents this gap: [2](#0-1) 

These checkpoint hashes are exactly the roots produced by `DoStateCheckpoint::run`, which computes the state-tree root, the hot-state root (gated by `hot_state_root_in_txn_info`), and — when the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature is on — the "position" (trading-native) state root [3](#0-2) . These per-transaction checkpoint hashes are folded into `TransactionInfoV1` and are part of what is ultimately committed to the transaction accumulator and signed by validators [4](#0-3) .

`ensure_match_transaction_info` is invoked directly by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes transactions from an on-disk backup/DB and compares the result to the `expected_txn_info` read from the archive [5](#0-4) . If the mismatch is detected, the tool treats the range as failed; if not, it reports the range as verified. Because the comparator never inspects the checkpoint-hash fields, a divergence confined to state/hot-state/position root computation (e.g., a bug in `DoStateCheckpoint`, the Jellyfish Merkle update path, or the trading-native position tree) is invisible to this check, even though the write set, events, gas, and status all match.

### Impact Explanation
This falls squarely in the "Hard-fork-only divergence during commit, replay, restore, or proof verification" bucket. `replay-on-archive`, `aptos-debugger`, and the `aptos-move` CLI replay/verify subcommands are the tools operators and auditors use to confirm that a node (or a proposed VM/execution change) reproduces byte-for-byte the authenticated ledger state. Because the checkpoint-hash fields are excluded from the comparison, these tools can report "verified"/"match" for a chunk of transactions whose locally recomputed state root, hot-state root, or position (trading-native) root actually diverges from the one the network signed off on. This masks exactly the class of bug that would otherwise be caught before it becomes an in-production consensus/state divergence (a chain split or a corrupted local DB state that downstream consumers trust as replayed/verified). The `position_state_checkpoint_hash` path is particularly exposed since it is a newer, feature-gated ("trading native") state root whose correctness has comparatively less test coverage.

### Likelihood Explanation
The gap is unconditionally present — every call to `ensure_match_transaction_info` skips the same three fields regardless of configuration — so any real state/hot-state/position-root computation bug introduced elsewhere in the executor (e.g., in `DoStateCheckpoint::compute_position_checkpoint` or the state summary update logic) is guaranteed to escape detection by this tool, rather than merely being a low-probability edge case. However, actual *exploitation impact* is contingent on such an upstream root-computation bug existing; this finding is a detection/verification blind spot rather than a directly state-corrupting primitive by itself, which somewhat lowers direct severity even though the code openly documents this as a known outstanding correctness gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS").

### Recommendation
Extend `ensure_match_transaction_info` to also assert equality of `self`'s recomputed `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` (when present/expected) against `txn_info`'s corresponding fields, mirroring the existing `write_set_hash`/`event_root_hash` pattern, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS` (and any other checkpoint-hash-bearing feature) is enabled on mainnet. This closes the blind spot in `replay_on_archive`, `aptos-debugger`, and CLI replay tooling.

### Proof of Concept
1. Take an archive/backup chunk of transactions whose `TransactionInfoV1` entries carry `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` values (i.e., produced with `hot_state_root_in_txn_info`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS` enabled).
2. Introduce (or trigger via an actual executor bug) a divergence solely in the hot-state or position-state root computation in `DoStateCheckpoint`, leaving write set, events, gas, and status identical to the authenticated info.
3. Run `db-tool replay-on-archive` (or `aptos-debugger`/`aptos-move cli` replay) over that range.
4. Observe that `execute_and_verify` → `ensure_match_transaction_info` [6](#0-5)  reports no error for the affected transactions, because the comparator at [7](#0-6)  never compares the checkpoint-hash fields, despite the recomputed ledger state actually diverging from the authenticated one.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
