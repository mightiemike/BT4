## Title
Relayer Fee Refund Sent Unconditionally Even When the User's Requested Transfer Action Fails - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`inner_rlp_execute` fires the relayer fee refund as an independent, unconditional promise before it schedules (and without any dependency on the success of) the promise that actually performs the user's requested value transfer. This is the structural analog of the reported "missing return-value check" class of bug: a value-moving operation (fee payment to the relayer) is performed as if the underlying operation (the user's `EOABaseTokenTransfer`/`ERC20Transfer`) succeeded, without verifying that it actually did.

### Finding Description
For `EOABaseTokenTransfer` and `ERC20Transfer` transaction kinds with a non-zero `fee`, `inner_rlp_execute` builds the refund promise directly and independently: [1](#0-0) 

```rust
if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { fee, .. })
| TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) =
    &transaction_kind
{
    if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
        let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
        env::promise_batch_action_transfer(refund_promise, *fee);
    }
}
```

This `refund_promise` is created via `env::promise_batch_create` and dispatched right away as its own top-level promise/receipt — it is never chained with `.then()` onto the promise that actually performs the requested transfer/`ft_transfer`. The promise that performs the real work is built afterward, separately, in the `match transaction_kind` block below (e.g. `action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))`), and its success/failure is only checked later in `rlp_execute_callback`: [2](#0-1) 

Critically, `rlp_execute_callback`'s failure branch only refunds `caller_deposit` (the attached deposit for storage/registrar flows) — it does **not** attempt to reclaim or avoid the relayer fee that was already sent out in a separate, already-broadcast receipt: [3](#0-2) 

Because the fee-refund receipt and the "do the real transfer" receipt are two independent receipts dispatched from the same function call, both are guaranteed to execute regardless of whether the token/NEAR transfer itself succeeds. If the actual transfer action fails (e.g. `ft_transfer` panics on insufficient token balance, the receiver account doesn't exist, or the `Action::Transfer` fails due to insufficient wallet NEAR balance), the relayer still unconditionally receives `fee` from the wallet — this mirrors exactly the reported ERC20 bug class: assuming a value-moving call succeeded and acting on that assumption (paying out) without checking the actual outcome.

### Impact Explanation
This allows unauthorized value movement out of the user's eth-wallet-contract account: the relayer is paid `fee` yoctoNEAR even for transactions that ultimately fail to move the user's intended funds/tokens. A malicious or compromised relayer could deliberately submit RLP transactions that are guaranteed to fail the underlying transfer (e.g. targeting an unregistered/invalid NEP-141 receiver in a way that bypasses the storage-deposit flow, or with a bogus target) purely to repeatedly collect the `fee` refund while the user's principal transfer never executes — effectively draining a fee from the wallet each time without providing the paid-for service, since nonce management independently allows retries. Users have no reliable way to know the fee has already been debited even though the desired transfer did not occur.

### Likelihood Explanation
The condition is straightforward to trigger: a relayer only needs to submit a valid, correctly-nonce'd, correctly-fee'd RLP transaction whose target action is guaranteed or made to fail after fee dispatch. Since the fee-refund promise is created unconditionally as soon as `fee` is non-zero and predecessor differs from the wallet itself, and it is not gated on the outcome of the value transfer, this can be reliably exploited by any relayer interacting with the wallet contract — no special privileges beyond being the transaction's predecessor (any account can act as relayer per the wallet-contract design) are required.

### Recommendation
Chain the fee-refund transfer onto the outcome of the actual value-transfer promise (e.g. via `.then()`), or move the refund logic into `rlp_execute_callback` so it is only executed after confirming `PromiseResult::Successful` for the underlying action. Alternatively, hold the fee amount in an escrow-like promise and only release it to the relayer once the primary action's result is confirmed successful, refunding it back to the user/wallet on failure.

### Proof of Concept
1. Deploy a `WalletContract` (eth-wallet) funded with NEAR, associated with a NEP-141 token balance.
2. Have the wallet's owner sign an RLP transaction representing an `ERC20Transfer` (or `EOABaseTokenTransfer`) with a non-zero relayer `fee`, targeting a receiver/token configuration guaranteed to make the underlying `ft_transfer`/`Transfer` action fail (e.g., insufficient token balance causing `ft_transfer` to panic, or a target that cannot receive the transfer).
3. Submit this transaction via `rlp_execute` from a relayer account (`predecessor_account_id` = relayer, differing from `current_account_id`).
4. Observe: `inner_rlp_execute` immediately dispatches the fee-refund `Transfer` receipt to the relayer at lines 382–384; the primary transfer/`ft_transfer` receipt subsequently fails and `rlp_execute_callback` reports `success: false`.
5. Confirm on-chain that the relayer's balance increased by `fee` even though `ExecuteResponse.success == false` and no token/NEAR value was actually delivered to the intended receiver — demonstrating unauthorized value movement to the relayer for a failed operation.
