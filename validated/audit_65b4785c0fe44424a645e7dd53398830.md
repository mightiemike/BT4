### Title
Global (non-namespaced) `requestID` map lets any authorized workflow caller squat another workflow's request ID and cause its HTTP trigger execution to fail — ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`HandleUserTriggerRequest` in the Gateway's HTTP trigger handler registers each incoming user request in a single, gateway-wide map keyed only by the caller-supplied JSON-RPC `id` (`requestID`), with no scoping to workflow, owner, or authorized key. Any authorized caller who is able to submit a request with the same `requestID` before another caller's request arrives will cause the second (legitimate) request to be rejected with `ErrConflict`. This mirrors the reported bug class: a user-chosen identifier is checked for prior existence and the first submission wins, allowing a griefing party to block a victim's action by "racing" the identifier.

### Finding Description
`HandleUserTriggerRequest` validates auth (`authorizeRequest`), checks rate limits, then calls `setupCallback`: [1](#0-0) 

`setupCallback` stores the request under `h.callbacks[requestID]`, a single map shared across the entire `httpTriggerHandler` instance for the DON — it is **not** keyed by workflow ID, workflow owner, or authorized key: [2](#0-1) 

If an entry for that `requestID` already exists, the function immediately returns a conflict error and rejects the request rather than allowing it to proceed: [3](#0-2) 

Reaching `setupCallback` only requires: (1) a syntactically valid trigger request, (2) a valid JWT signed by a key that is registered as an "authorized key" for *some* workflow (`authorizeRequest` → `WorkflowMetadataHandler.Authorize`), and (3) passing the per-workflow rate limiter: [4](#0-3) 

Because authorization is validated per-workflow but the `callbacks` map key space (`requestID`) is global across all workflows/owners on the DON, an attacker who is merely an authorized caller for their *own* unrelated workflow can pick (or predict/guess) the same `requestID` string that a victim is about to use for a *different* workflow, and race to register it first. The victim's subsequent request with the identical `requestID` will hit the existing-key branch and be rejected with `jsonrpc.ErrConflict`, exactly analogous to the `AccountAlreadyCreated` revert in the reported bug — a first-come-first-served, unscoped ID namespace with no way to distinguish legitimate collisions from hostile ones.

Additionally, this handler is directly reachable from the externally-facing Gateway entry point with no additional access control, confirming unprivileged-user reachability: [5](#0-4) 

The existing unit test only validates same-caller duplicate submission, not the cross-workflow/cross-owner collision scenario, so this specific griefing path is not covered by tests: [6](#0-5) 

### Impact Explanation
This is a griefing/DoS vector against the workflow HTTP trigger capability of the CRE Gateway. An attacker with no special privileges beyond being an authorized signer for any workflow (their own) can prevent other workflows' HTTP-triggered executions from starting by squatting shared `requestID` values, causing legitimate `workflows.execute` requests to fail with a conflict error instead of being dispatched to the DON. There is no direct fund loss or state corruption, but it denies availability of the trigger capability to victim workflows/users — matching the "Griefing" impact category in the reported analog (no profit motive, but damage to users/protocol).

### Likelihood Explanation
Exploitability depends on the attacker being able to predict or observe a victim's chosen `requestID` before the victim's request reaches the gateway, since these are HTTP JSON-RPC requests rather than public mempool transactions. This is a meaningful difference from the on-chain frontrunning report where all pending transactions are publicly visible. Likelihood is therefore lower than the on-chain analog and is highest in scenarios where: (a) client libraries or integrations use predictable/sequential/timestamp-based `requestID`s, (b) an attacker specifically targets a known workflow/client whose request pattern is observable through other side channels, or (c) an attacker simply floods the namespace with many likely/common ID values to increase collision probability against arbitrary victims. I could not verify from the available code whether SDKs/clients generate requestIDs with sufficient entropy to make guessing infeasible in practice — this would need to be confirmed by inspecting client-side ID generation, which is outside this repo's scanned surface.

### Recommendation
Scope the `callbacks` map key by a combination that includes caller identity, e.g. `(workflowID, authorizedKey/publicKey, requestID)` rather than `requestID` alone, so that one workflow's/owner's request namespace cannot collide with another's. Alternatively, generate/prefix the internal tracking key server-side (e.g., `workflowID + "/" + requestID`) before insertion into `h.callbacks`, while still returning the original `requestID` to the caller in responses.

### Proof of Concept
Conceptual PoC (illustrating the collision, following the same call path as the existing "duplicate request ID" test):
1. Victim (owner of `workflowA`, authorized key `K_A`) prepares an HTTP trigger request with `id = "req-123"` for `workflowA`.
2. Attacker (owner of an unrelated `workflowB`, authorized key `K_B`, which the attacker legitimately controls) sends a JSON-RPC request with the same `id = "req-123"` for `workflowB` first. `authorizeRequest` succeeds (valid JWT for `workflowB`/`K_B`), and `setupCallback` inserts `h.callbacks["req-123"]`.
3. Victim's request for `workflowA` with `id = "req-123"` arrives and hits the `found` branch in `setupCallback`: [3](#0-2) 
   The victim's request is rejected with `ErrConflict`, even though the two requests belong to entirely different workflows/owners — demonstrating that the `requestID` namespace is not isolated per workflow/caller, matching the account-ID-squatting bug class in the reference report.

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
