### Title
Redirecting balance refunds via `promise_set_refund_to()` permanently burns funds instead of returning them - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`, `core/primitives/src/receipt.rs`)

### Summary
The host function `promise_set_refund_to()` lets a contract redirect the balance refund of a receipt it creates to an arbitrary account instead of the default predecessor. Unlike the checks performed for a normal `Transfer` action, the `refund_to` account id is only syntactically validated (`AccountId::validate`) — there is no existence check, and no implicit-account-creation fallback, when the redirected refund is actually delivered. Because refund receipts are treated as "free" system receipts, a failed refund (e.g., because the `refund_to` account does not exist) does not retry or fall back to the predecessor: the deposit is burned into `other_burnt_amount` and permanently lost. A contract developer who calls the low-level `promise_set_refund_to` API directly (analogous to calling `createRetryableTicketNoRefundAliasRewrite()` instead of the safer `depositEth()` in the Arbitrum report) can therefore lose end-user funds with no recourse, exactly the "developers calling contracts directly may make mistakes and lose tokens" class described in the source report.

### Finding Description
`ActionReceiptV2::refund_to` stores an optional override for where a balance refund should be sent, exposed to contracts through `promise_set_refund_to()`: [1](#0-0) 

At receipt-validation time, `refund_to` is checked only for well-formedness, not existence or reachability: [2](#0-1) 

`Receipt::balance_refund_receiver()` simply returns the `refund_to` id if set, otherwise the predecessor: [3](#0-2) 

When the runtime actually executes the resulting refund receipt (predecessor = `system`), the account-existence check for a plain `Transfer` action only allows implicit account creation under specific narrow conditions (`is_refund` and the transfer being the receipt's sole action) captured by `ReceiptShape`/`implicit_creation_allowed`: [4](#0-3) 

If the redirected account does not exist and does not qualify for implicit creation (e.g., it is a *named*, non-implicit account, or a `0s…` universal/deterministic account with no matching state-init), the refund action fails with `AccountDoesNotExist`. This is confirmed by an existing regression test for the related "must not create a `0u`/universal account via refund" case: [5](#0-4) 

Because refund receipts are system-predecessor receipts, the runtime doc/spec states that they are free to execute and, crucially, on failure the burnt deposit is **not returned to anyone** — it is folded into `other_burnt_amount` rather than being refunded again (refunds of refunds are not generated): [6](#0-5) 

So the sequence a contract author can trigger is:
1. Contract A calls `promise_batch_create`/`promise_batch_action_*` to create a promise to some receiver, attaching a deposit.
2. Contract A calls `promise_set_refund_to(promise_idx, account_id)` pointing at an account it controls or expects to be valid, but which turns out not to exist on-chain (e.g., a typo, a not-yet-created sub-account, or a named account the caller assumed already existed).
3. The downstream call fails or leaves unspent gas/deposit, generating a system refund receipt whose receiver is the `refund_to` account.
4. The `Transfer` action in that refund receipt fails `check_account_existence` (`AccountDoesNotExist`), because the target is not implicit and doesn't exist.
5. Per the refund-handling semantics, this failed refund is not itself re-refunded; the deposit is burned as `other_burnt_amount`, permanently removing the tokens from circulation.

This mirrors the reported Arbitrum issue precisely: a lower-level primitive (`promise_set_refund_to`, analogous to `createRetryableTicketNoRefundAliasRewrite()`) skips the safety semantics that the "default" path (`refund_to == predecessor_id`, analogous to `depositEth()`) implicitly guarantees (the predecessor account is known to exist, since it is the very account that created the receipt), letting careless or buggy contract code cause an irreversible loss of user funds.

### Impact Explanation
This is a real value-loss bug reachable by any contract deployer/dApp developer who uses the `promise_set_refund_to` host function (available to any account via a `FunctionCall` action), without any privileged access. A misconfigured or attacker-supplied `refund_to` target causes attached deposits to be burned rather than refunded to the rightful predecessor, resulting in permanent, unauthorized loss of user funds. This satisfies the "permanently frozen/lost funds" acceptance criterion.

### Likelihood Explanation
Medium likelihood: it requires a contract to actively use `promise_set_refund_to` with an account id that turns out not to exist at execution time (which is a very plausible and easy-to-make developer mistake, especially since NEAR account creation is not enforced at redirect-set time and can race with account deletion or simply be mistyped/mis-derived). This does not require any protocol-level exploit, malicious validator, or special privilege — it is triggerable purely through normal contract logic and a single transaction chain.

### Recommendation
- Validate that a `refund_to` target either already exists, or is guaranteed to be creatable via the normal implicit-account-creation rules, at the time `promise_set_refund_to` is called (or at receipt-validation time), rather than deferring the failure to refund-execution time where the deposit is silently burned.
- Alternatively, on a failed refund whose receiver was redirected via `refund_to`, fall back to refunding the original receipt's predecessor instead of burning the deposit, preserving the safety guarantee that funds are never irrecoverably lost due to a redirect mistake.
- Document prominently (in the host-function docs and NEP) that `promise_set_refund_to` bypasses the implicit safety of predecessor-based refunds and that developers must ensure the target account is guaranteed to exist, similar to warning callers of `depositEth()`-style low-level primitives in other ecosystems.

### Proof of Concept
Not independently reproduced in this pass (no sandbox/terminal access), but the existing regression test demonstrates the failure branch and its "does not create the account" / `AccountDoesNotExist` outcome for a refund receipt targeting a non-existent account: [5](#0-4) 

A full PoC would extend `test_refund_to` (`runtime/runtime/tests/test_async_calls.rs:1204-1297`, which already demonstrates successful refund redirection to an existing account "near_3") by pointing `set_refund_to`'s `beneficiary_id` at a syntactically valid but non-existent, non-implicit account id, then asserting: (a) the refund action fails with `ActionErrorKind::AccountDoesNotExist`, and (b) the deposit does not appear in any subsequent receipt or account balance, confirming it was burned via `other_burnt_amount` rather than returned to the original predecessor. pub(crate) fn check_account_existence(
    action: &Action,
    account: &Option<Account>,
    account_id: &AccountId,
    config: &RuntimeConfig,
    receipt_shape: ReceiptShape,
) -> Result<(), ActionError> {
    match action {
        Action::CreateAccount(_) => {
            if account.is_some() {
                return Err(ActionErrorKind::AccountAlreadyExists {
                    account_id: account_id.clone(),
                }
                .into());
            }
            if get_account_type(account_id, config).is_implicit() {
                // Implicit accounts can only be created implicitly.
                // `CreateAccount` claims `actor_id` for the new account, which
                // would let the rest of the receipt add an access key to an id
                // whose private key the sender does not hold. Rejecting the action
                // is the simplest way to close that.
                // See https://github.com/nearprotocol/NEPs/pull/71
                return Err(ActionErrorKind::OnlyImplicitAccountCreationAllowed {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::Transfer(_) => {
            let account_type = get_account_type(account_id, config);
            if account.is_none() && !implicit_creation_allowed(account_type, receipt_shape) {
                return Err(ActionErrorKind::AccountDoesNotExist {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }

#[test]
fn test_refund_to() {
    let group = RuntimeGroup::new(4, 4, near_test_contracts::rs_contract());

    let signer_sender = group.signers[0].clone();
    let signer_receiver = group.signers[1].clone();
    let deposit = Balance::from_yoctonear(1000);

    let data = serde_json::json!([
        {
            "batch_create": {
                "account_id": "near_2",
            },
            "id": 0
        },
        {
            "action_function_call": {
                "promise_index": 0,
                "method_name": "non_existing_function",
                "arguments": [],
                "amount": deposit,
                "gas": GAS_2,
            },
            "id": 0
        },
        {
            "set_refund_to": {
                "promise_index": 0,
                "beneficiary_id": "near_3"
            }, "id": 0
        }
    ]);

    let signed_transaction = SignedTransaction::from_actions(
        1,
        signer_sender.get_account_id(),
        signer_receiver.get_account_id(),
        &signer_sender,
        vec![Action::FunctionCall(Box::new(FunctionCallAction {
            method_name: "call_promise".to_string(),
            args: serde_json::to_vec(&data).unwrap(),
            gas: GAS_1,
            deposit,
        }))],
        CryptoHash::default(),
    );

    let handles = RuntimeGroup::start_runtimes(group.clone(), vec![signed_transaction.clone()]);
    for h in handles {
        h.join().unwrap();
    }

    println!("{:?}", group.executed_receipts);

    use near_primitives::transaction::*;
    let [r0] = &*assert_receipts!(group, signed_transaction) else {
        panic!("Incorrect number of produced receipts")
    };

    let receipts = &*assert_receipts!(group, "near_0" => r0 @ "near_1",
        ReceiptEnum::Action(ActionReceipt{actions, ..}) | ReceiptEnum::ActionV2(ActionReceiptV2{actions, ..}),
        {},
        actions,
        a0, Action::FunctionCall(function_call_action), {
            assert_eq!(function_call_action.gas, GAS_1);
            assert_eq!(function_call_action.deposit, deposit);
            assert_eq!(function_call_action.method_name, "call_promise");
        }
    );
    let [r1, refunds @ ..] = &receipts else { panic!("Incorrect number of produced receipts") };
    group.assert_gas_refunds(&refunds[..]);

    let receipts = &*assert_receipts!(group, "near_1" => r1 @ "near_2",

    // This is the redirected refund
    assert_refund!(group, deposit_refund @ "near_3");
