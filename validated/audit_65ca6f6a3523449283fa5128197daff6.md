### Title
Wrong Receiver ID Used in `validate_delegate_action` Renders `DeterministicStateInit` via Meta-Transactions Inaccessible — (`runtime/runtime/src/action_validation.rs`)

---

### Summary

`validate_delegate_action` in `runtime/runtime/src/action_validation.rs` passes the **outer transaction's receiver** (`receiver`) to `validate_actions_with_mode` instead of the **delegate action's own receiver** (`delegate_action.receiver_id()`). For `DeterministicStateInit` inner actions, `validate_deterministic_state_init` then compares the cryptographically derived account ID against the wrong account ID, causing every legitimate `DeterministicStateInit` wrapped inside a `DelegateAction` (meta-transaction) to be rejected at transaction validation. The entire feature path is inaccessible via meta-transactions on protocol versions below 85.

---

### Finding Description

`validate_delegate_action` is called from `validate_action_with_mode` when the outer action is `Action::Delegate` or `Action::DelegateV2`. It receives two receiver IDs:

- `receiver` — the outer transaction's `receiver_id` (the account that holds the `DelegateAction`)
- `delegate_action.receiver_id()` — the inner delegate's `receiver_id` (the account the inner actions will actually execute on)

Before `ProtocolFeature::FixDelegatedDeterministicStateInit` (protocol version 85), the function unconditionally uses `receiver` (the outer one) as `inner_receiver` when recursively calling `validate_actions_with_mode`:

```rust
// runtime/runtime/src/action_validation.rs:190-201
let inner_receiver =
    if ProtocolFeature::FixDelegatedDeterministicStateInit.enabled(current_protocol_version) {
        delegate_action.receiver_id()   // correct
    } else {
        receiver                        // BUG: outer tx receiver, not delegate's receiver
    };
validate_actions_with_mode(limit_config, &actions, inner_receiver, ...)?;
```

`validate_deterministic_state_init` then checks:

```rust
// runtime/runtime/src/action_validation.rs:431-438
let derived_id = derive_near_deterministic_account_id(&action.state_init);
if derived_id != *receiver_id {
    return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver { ... });
}
```

Because `receiver_id` is the outer transaction's receiver (e.g., `det_account_b`) rather than the delegate's receiver (e.g., `det_account_a`), the derived ID check compares against the wrong account. A legitimate meta-transaction that wraps a `DeterministicStateInit` targeting the correct deterministic account fails at transaction validation with `InvalidDeterministicStateInitReceiver`, because the outer receiver does not match the state-init's derived ID.

The codebase's own test confirms this behavior:

```
// test-loop-tests/src/tests/deterministic_account_id.rs:141-156
let outcome = try_meta_tx_deterministic_receiver_exploit(fix_version - 1)
    .expect("without the fix, exploit tx passes initial tx validation");
// outcome.status == Failure(NewReceiptValidationError(InvalidDeterministicStateInitReceiver))
```

The test also confirms that an attacker who crafts a tx where the outer receiver happens to match the state-init's derived ID (so tx validation passes) is still blocked at receipt validation — so no unauthorized execution or fund theft is possible. The sole impact is that the legitimate feature path is completely broken.

---

### Impact Explanation

Any unprivileged user who attempts to initialize a deterministic account via a meta-transaction (`DelegateAction` wrapping `DeterministicStateInit`) on protocol versions < 85 receives `InvalidTxError::ActionsValidation(InvalidDeterministicStateInitReceiver)` at transaction submission. The feature is entirely inaccessible via the meta-transaction path. This is a **contract execution flow breakage**: a protocol-defined action type that is supposed to be usable inside `DelegateAction` cannot be used at all.

---

### Likelihood Explanation

Any user who attempts to use `DeterministicStateInit` inside a meta-transaction on a node running protocol version < 85 triggers the bug. No special privileges, no malicious intent, and no specific timing are required. The trigger is a standard JSON-RPC `broadcast_tx_async` or `broadcast_tx_commit` call with a well-formed `DelegateAction` containing a `DeterministicStateInit` inner action.

---

### Recommendation

The fix is already present and gated behind `ProtocolFeature::FixDelegatedDeterministicStateInit` (protocol version 85). The pre-fix branch should be removed once protocol version 85 is universally active, to eliminate the dead code path and prevent any future regression:

```rust
// runtime/runtime/src/action_validation.rs
fn validate_delegate_action(...) {
    let actions = delegate_action.get_actions();
    // Remove the version gate; always use the correct receiver:
    let inner_receiver = delegate_action.receiver_id();
    validate_actions_with_mode(limit_config, &actions, inner_receiver, ...)?;
    Ok(())
}
```

### Proof of Concept

The nearcore test suite already encodes the exact exploit scenario: [1](#0-0) 

The root cause is at: [2](#0-1) 

The wrong-receiver comparison that rejects the legitimate action: [3](#0-2) 

The protocol-version gate that activates the fix at version 85: [4](#0-3) 

**Step-by-step trigger (protocol version < 85):**

1. User deploys a global contract and derives two deterministic account IDs: `det_account_a` and `det_account_b` from two different `DeterministicAccountStateInit` payloads.
2. User deploys `det_account_b` and adds a full-access key to it so it can act as a meta-transaction sender.
3. User constructs a `DelegateAction` with `sender_id = det_account_b`, `receiver_id = det_account_a`, and inner action `DeterministicStateInit { state_init: state_init_b, ... }`.
4. User wraps this in an outer transaction with `receiver_id = det_account_b` (which matches `derive(state_init_b)`).
5. At tx validation, `validate_delegate_action` uses `receiver = det_account_b` as `inner_receiver`. `validate_deterministic_state_init` computes `derived_id = derive(state_init_b) = det_account_b` and checks `det_account_b == det_account_b` — this passes.
6. The tx is accepted and converted to a receipt targeting `det_account_a`.
7. At receipt validation (`validate_receipt(..., NewReceipt)`), `validate_deterministic_state_init` now uses the correct receiver `det_account_a` and checks `derive(state_init_b) = det_account_b != det_account_a` — this fails with `InvalidDeterministicStateInitReceiver`.

For the **legitimate use case** (user wants to do `DeterministicStateInit` on `det_account_a` via meta-tx with outer receiver also `det_account_a`): tx validation uses `receiver = det_account_a` as `inner_receiver`, checks `derive(state_init_a) = det_account_a == det_account_a` — this passes. But the delegate's `receiver_id` is also `det_account_a`, so in this specific case the bug does not block the action. The bug blocks the case where the outer receiver differs from the delegate's receiver, which is the normal meta-transaction pattern where a relayer (outer receiver) forwards the action to the target (delegate receiver). [5](#0-4)

fn validate_delegate_action(
    limit_config: &LimitConfig,
    delegate_action: VersionedDelegateActionRef<'_>,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ActionsValidationError> {
    let actions = delegate_action.get_actions();
    let inner_receiver =
        if ProtocolFeature::FixDelegatedDeterministicStateInit.enabled(current_protocol_version) {
            // This is the correct receiver id to use for the check.
            delegate_action.receiver_id()
        } else {
            // This is a bug fixed with `FixDelegatedDeterministicStateInit` that
            // validated against the wrong id. This makes it impossible to
            // initialize deterministic accounts from meta transactions.
            // The bug cannot be abused, if someone crafts a state init that passes
            // validation here, it will fail when it is checked as incoming receipt.
            receiver
        };
    validate_actions_with_mode(
        limit_config,
        &actions,
        inner_receiver,
        current_protocol_version,
        mode,
    )?;
    Ok(())
}
