### Title
Malformed signer-key buffer silently collapses to the all-zero public key in `RawRewardSetEntry::from_pox_4_tuple`, aggregating unrelated stackers' weight onto a shared phantom signer identity - (File: `stackslib/src/chainstate/nakamoto/signer_set.rs`)

### Summary
`RawRewardSetEntry::from_pox_4_tuple` reads the `signer` field returned from the `pox-4` contract as a `(buff 33)` Clarity value and, if the buffer's length is not exactly `SIGNERS_PK_LEN` (33), silently substitutes an all-zero 33-byte array instead of rejecting the entry, analogous to `LibOwnable._setAdmin` silently accepting `address(0)` instead of reverting.

### Finding Description
In `stackslib/src/chainstate/nakamoto/signer_set.rs`, `from_pox_4_tuple` extracts the `signer` buffer with `expect_buff(SIGNERS_PK_LEN)`, which (per the inline comment) "only enforces max size, not min size." [1](#0-0) 
When `signer.len() != SIGNERS_PK_LEN`, the code does not return an error; it substitutes `[0; SIGNERS_PK_LEN]` — the all-zero public key — and wraps it in `Some(pk_bytes)` as if it were a valid signing key.

This zero-key value is then aggregated by public key in `make_signer_set` (`stackslib/src/chainstate/stacks/boot/mod.rs`), where entries with the same `signing_key` are summed: [2](#0-1) 
Any stacker (whether through their own Clarity call or PoX bug) that produces a signer buffer shorter than 33 bytes gets folded into the same all-zero-key bucket as every other malformed entry, rather than being rejected outright. Because `weight == 0` is the only filter applied, a zero-key entry with nonzero stacked amount is not dropped and becomes a legitimate-looking `NakamotoSignerEntry` with a fixed, publicly-known signing key of all zeros.

This differs from the reported LibOwnable bug in one important way that must be validated: whether the substitution is reachable from an unprivileged, minority-triggerable path (i.e., whether `pox-4.clar`/`pox-5.clar` can be made to return a `signer` buffer whose length is provably less than 33 bytes through ordinary Clarity contract calls). I was unable to confirm within the available tool budget that `pox-4.clar`'s `stack-stx`/`stack-extend`/`stack-aggregation-commit` functions accept a `signer-key` argument shorter than 33 bytes without an explicit length assertion — the grep for length-enforcing assertions on `signer-key` in `pox-4.clar` returned no direct match, but I could not fully inspect the `(buff 33)` typed parameter declarations and their call sites to confirm whether Clarity's type-checker or the contract's own logic guarantees exactly 33 bytes on every path that ultimately produces the `signer` tuple field read here.

### Impact Explanation
Because all nodes execute the identical Rust code deterministically, the zero-key substitution itself does not cause a state-root divergence between honest nodes — every node computes the same (incorrect) reward set. The primary risk, if the buffer-length gap is reachable, is that:
- multiple unrelated stackers with malformed/short signer keys get their weight silently merged onto a single "zero-key" signer identity in the reward set, which is consensus-critical data written into the `.signers` contract and used later for block-signing weight/threshold checks (`verify_signer_signatures` in `stackslib/src/chainstate/nakamoto/mod.rs`), and
- anyone in possession of (or able to derive) the zero-key entry benefits from aggregated voting weight they did not individually earn, without a majority coalition — a single malicious stacker just needs to submit a malformed signer-key.

This would fall under a "reward mis-payment/weight mis-attribution bounded to a subset of stackers" rather than a chain split, since it is fully deterministic and reproducible by all nodes running the same code — it does not, by itself, break cross-node equality of the state root. Its severity is bounded because it requires the very unusual condition of a malformed (not-33-byte) signer-key buffer coming out of the PoX-4 contract, which I could not confirm is achievable without contract-level validation blocking it.

### Likelihood Explanation
Low-to-uncertain. The comment in the code ("(buff 33) only enforces max size, not min size, so we need to do a len check") suggests the author was aware short buffers are theoretically possible from the Clarity type system's perspective, which is why the length check exists at all. However, whether `pox-4.clar`/`pox-5.clar` contract logic can actually be coerced into storing/returning a signer buffer shorter than 33 bytes for a real stacking transaction was not confirmed. Without a concrete unprivileged, minority-triggerable Clarity call path that manufactures a short `signer` buffer, this cannot be treated as validated with confidence.

### Recommendation
If a length mismatch is possible, `from_pox_4_tuple` should return `Err(ChainstateError::Expects(...))` when `signer.len() != SIGNERS_PK_LEN` instead of silently defaulting to the all-zero key, mirroring the recommendation in the original report to explicitly reject the invalid/degenerate value rather than silently accepting a sentinel value that carries real consensus meaning.

### Proof of Concept
Not constructed — a concrete PoC requires confirming a live Clarity call path (through `pox-4.clar`/`pox-5.clar`) that yields a `signer` buffer whose length is provably not 33 bytes, which I was unable to verify with the available tool calls. This should be checked directly against `stackslib/src/chainstate/stacks/boot/pox-4.clar`'s `stack-stx`, `stack-extend`, `stack-aggregation-commit`, and `delegate-stack-stx` (or equivalent) definitions and their `signer-key` parameter typing/validation before treating this as a confirmed, exploitable finding.
