## Analysis

The strongest analog to CVE-2023-28867 (stack consumption from unbounded, attacker-controlled recursion) in this codebase is the recursive bytecode-hash computation used for CASM compiled-class hashing.

### Title
Unbounded native recursion in compiled-class bytecode hashing allows stack-overflow DoS from a crafted DECLARE transaction - (File: `crates/starknet_api/src/contract_class/compiled_class_hash.rs`)

### Summary
`bytecode_hash_node` recursively walks the `bytecode_segment_lengths` tree (`NestedIntList`) produced by the Sierra→CASM compiler for an attacker-submitted contract class, with no recursion-depth limit, and it is invoked directly on the sequencer's real call stack outside of the resource-limited compilation subprocess.

### Finding Description
`SierraCompiler::compile` runs the untrusted Sierra program through the CASM compiler as a resource-limited (CPU-time/memory-bounded) *subprocess* [1](#0-0) , but immediately afterward computes the compiled-class hash of the result *in the parent process*, unprotected by that sandbox: [2](#0-1) 

That call chains into `hash_inner` → `bytecode_hash` → `bytecode_hash_node`, a plain Rust function that recurses once per nesting level of the `bytecode_segment_lengths` structure with no depth bound and no iterative fallback: [3](#0-2) 

The nesting structure being recursed over (`NestedIntList`) is produced by the compiler based on the function/branch structure of the attacker's own Sierra code (see test fixtures showing arbitrary nesting of `NestedIntList::Node`/`Leaf`) [4](#0-3) . Only the total bytecode *size* is bounded (`max_bytecode_size`, default 80 KiB / 80×1024 felts) [5](#0-4) ; nothing bounds the *nesting depth* of that structure. A contract crafted with many deeply nested branch/function scopes (well within the 80K-felt bytecode budget) can therefore produce a segment tree tens of thousands of levels deep, and `bytecode_hash_node` will recurse that deep on the real machine stack, each frame doing a `Vec` allocation via `collect_vec()`.

This same recursive hashing function is not confined to the gateway: it implements the generic `HashableCompiledClass` trait used wherever a compiled-class hash must be independently recomputed, e.g. by `CompiledClassV1` in the blockifier [6](#0-5) . Every honest node that needs to verify/recompute a declared class's hash (gateway ingestion, block building, state-sync validation, re-execution) runs the identical unguarded recursion over attacker-supplied data.

This is a direct structural analog to CVE-2023-28867: an attacker-controlled, deeply-nested input structure drives unbounded native recursion with no depth guard, in contrast to other recursion points in this codebase (e.g. entry-point call recursion) which are explicitly protected by `RecursionDepthGuard` [7](#0-6)  or bounded by Cairo-VM-simulated (heap) stacks rather than the real stack [8](#0-7) .

### Impact Explanation
A stack overflow in `bytecode_hash_node` crashes the process computing it. Because this function is reached during DECLARE transaction ingestion at the gateway (`SierraCompiler::compile`) and by any node that must recompute a compiled-class hash while validating or re-executing the block containing the malicious class, a single submitted DECLARE transaction can crash sequencer/gateway processes network-wide and prevent honest nodes from confirming/syncing past that class — a network-wide denial of service triggered by an unprivileged declarer, without needing operator or peer collusion.

### Likelihood Explanation
Reachable by any account with a single DECLARE transaction: the attacker only needs to write a Sierra contract whose control-flow structure (nested function/branch scoping) causes the CASM compiler to emit a deeply nested `bytecode_segment_lengths` tree, while staying under the size-only `max_bytecode_size` limit. No special privileges, no cooperation from operators/provers/peers is required, and the vulnerable code path executes unconditionally as part of standard DECLARE processing.

### Recommendation
- Convert `bytecode_hash_node` (and the analogous `bytecode_hash_node` recursion in `crates/apollo_starknet_os_program/.../poseidon_compiled_class_hash.cairo` / `blake_compiled_class_hash.cairo`, which mirror the structure in Cairo) to an iterative, explicit-stack-based traversal, or impose and enforce a maximum nesting depth on `bytecode_segment_lengths` consistent with what a legitimate compiler emits for `max_bytecode_size`-bounded programs.
- Alternatively/additionally, run the compiled-class hash computation inside the same resource-isolated (stack-size-bounded, crash-contained) subprocess/thread used for the raw Sierra→CASM compilation step, so a crash there does not take down the whole component.
- Add a fuzz/regression test that declares a class engineered to produce a maximally deep `bytecode_segment_lengths` tree within the size limit, verifying the hash computation degrades gracefully (error) instead of crashing.

### Proof of Concept
1. Craft a Cairo1 contract whose body is composed of ~40,000 deeply nested single-felt-returning branches/functions (e.g., a chain of nested `if`/`match` scopes or nested function calls each with a trivial body), keeping total CASM bytecode length under the default `max_bytecode_size` (81920 felts) so the compiler accepts it.
2. Submit it as the `contract_class` of a DECLARE v3 transaction to the gateway.
3. `stateless_tx_validator` only checks total bytecode/object size, not segment nesting depth [9](#0-8) , so the transaction passes to `SierraCompiler::compile`.
4. The subprocess compiles the class successfully (small enough bytecode) and returns a `CasmContractClass` whose `bytecode_segment_lengths` is deeply nested.
5. `executable_class.hash(&HashVersion::V2)` is invoked in the parent process [10](#0-9) , recursing through `bytecode_hash_node` once per nesting level until the process's real stack is exhausted, crashing the gateway/sierra-compiler process handling the DECLARE transaction.

/// Computes the hash of a bytecode segment. See the documentation of `bytecode_hash_node` in
/// the Starknet OS.
/// Returns the length of the processed segment and its hash.
fn bytecode_hash_node<H, NL>(iter: &mut impl Iterator<Item = Felt>, node: &NL) -> (usize, Felt)
where
    H: StarkHash,
    NL: HashableNestedIntList,
{
    if node.is_leaf() {
        let len = node.get_segment_length();
        let data = iter.take(len).collect_vec();
        assert_eq!(data.len(), len);
        (len, H::hash_array(&data))
    } else {
        // Compute `1 + poseidon(len0, hash0, len1, hash1, ...)`.
        let inner_nodes = node
            .iter_children()
            .map(|child| bytecode_hash_node::<H, NL>(iter, child))
            .collect_vec();
        let hash = H::hash_array(
            &inner_nodes.iter().flat_map(|(len, hash)| [Felt::from(*len), *hash]).collect_vec(),
        ) + Felt::ONE;
        (inner_nodes.iter().map(|(len, _)| len).sum(), hash)
    }
}

// Ensure that the recursion depth does not exceed the maximum allowed depth.
struct RecursionDepthGuard {
    current_depth: Arc<RefCell<usize>>,
    max_depth: usize,
}

impl RecursionDepthGuard {
    fn new(current_depth: Arc<RefCell<usize>>, max_depth: usize) -> Self {
        Self { current_depth, max_depth }
    }

    // Tries to increment the current recursion depth and returns an error if the maximum depth
    // would be exceeded.
    fn try_increment_and_check_depth(&mut self) -> Result<(), EntryPointExecutionError> {
        *self.current_depth.borrow_mut() += 1;
        if *self.current_depth.borrow() > self.max_depth {
            return Err(EntryPointExecutionError::RecursionDepthExceeded);
        }
        Ok(())
    }
}
