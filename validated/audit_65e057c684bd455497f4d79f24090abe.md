## Title
Session-token replay race allows an unprivileged merchant/customer request to clobber a freshly exchanged offline access token, causing shop-wide auth DoS - (File: `packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts`)

## Summary
`performTokenExchange()` reads the current offline session, and — only if it is *not* currently active — performs a token exchange and stores whatever session it obtains. If that exchange later fails with an HTTP 401, the handler "invalidates" the access token it captured *before* the exchange by force-overwriting storage with the stale, token-less session object. Because `storeSession()` is an unconditional last-write-wins upsert keyed by the deterministic id `offline_${shop}` [1](#0-0) , a second (or third) concurrent request carrying the very same still-valid session token can race a first request that already completed a successful exchange, and end up wiping out the just-stored, working offline access token for the entire shop.

## Finding Description
The handler captures the pre-exchange session for later invalidation, then performs the exchange asynchronously: [2](#0-1) 

If the exchange call throws an `HttpResponseError` with `code === 401` (any cause other than the specifically-handled `invalid_subject_token` 400 case), the code unconditionally persists the *stale* pre-exchange session object with its access token cleared: [3](#0-2) 

The actual write happens in `invalidateAccessToken`, which performs no version check or compare-and-swap — it simply calls `storeSession` again on the id-keyed record: [4](#0-3) 

Every backing `SessionStorage` implementation performs a blind upsert by `session.id` with no optimistic locking (e.g. Postgres `ON CONFLICT (id) DO UPDATE`, in-memory `this.sessions[session.id] = session`), so whichever write lands last wins regardless of which request's data is fresher: [5](#0-4) [6](#0-5) 

Because the offline session id is derived only from the shop domain (`offline_${shop}`), it is a single shared resource for the entire store — not scoped to the individual staff member/session token that triggered the exchange [7](#0-6) . This mirrors the analog bug class: a stale-read-then-unconditional-write pattern lets one request's outcome be silently reverted by a racing sibling request, with the "victim" being every other consumer of that shared record (in the original report, the lienee who cannot withdraw; here, every user/background job of the shop that depends on the offline access token).

## Impact Explanation
If triggered, the shop's offline access token is wiped (`accessToken = undefined`) even though a concurrent request had just legitimately obtained and stored a working token. Every subsequent authenticated request, webhook-triggered background job, or billing check for that shop that depends on the offline session will fail until a fresh OAuth/token-exchange cycle repairs it — a shop-wide denial of service caused by nothing more than ordinary concurrent traffic (e.g. two browser tabs, or a user rapidly reloading the embedded app) hitting `validateAuthenticatedSession()`/`performTokenExchange` at the same time. No secrets are leaked and no cross-tenant read/write of another shop's data occurs, but availability of the auth handler and everything gated behind it is degraded, exactly analogous to the "pure grief, no economic benefit" classification in the source report.

## Likelihood Explanation
No forged or stolen credentials are required — only ordinary concurrent use of a still-valid session token by the same authenticated context (e.g. two tabs, background fetch retries, or a merchant deliberately double-firing requests) is needed to enter the race window between `loadSession` and the eventual `storeSession` write in `invalidateAccessToken`. It requires: (1) the offline session being momentarily inactive/expired so the exchange path is entered, and (2) the exchange for one of the racing requests returning an `HttpResponseError` with code 401 from Shopify's token endpoint. Condition (2) is plausible under real network/API conditions (e.g., token endpoint rejecting an already-consumed or momentarily-invalid subject token differently than the explicitly-handled 400 `invalid_subject_token` case), but is not proven against Shopify's live endpoint behavior in this analysis, so likelihood is assessed as low-to-moderate.

## Recommendation
- Do not perform a blind overwrite in `invalidateAccessToken`; re-load the current session immediately before invalidating and only clear the token if it still matches the exact token/version that failed, or use a conditional/optimistic update (e.g. compare-and-swap on an update timestamp or the previous access token value) in `SessionStorage.storeSession`.
- Alternatively, gate the exchange with a per-shop mutex/idempotency key (similar to the existing `idempotentPromiseHandler` used for `afterAuth`) so only one in-flight exchange per shop can write to the shared offline session id at a time.

## Proof of Concept
1. Ensure the shop's stored offline session is inactive/expired (e.g. `session.accessToken` unset or `expires` in the past), matching the "no valid session found" branch in `performTokenExchange` [8](#0-7) .
2. Fire two concurrent requests to an endpoint behind `shopify.validateAuthenticatedSession()` using the same still-valid session token.
3. Request A completes its token exchange first and calls `config.sessionStorage.storeSession(offlineSession)` with a fresh, valid access token.
4. Request B, which read the same stale pre-exchange session at `sessionToInvalidate` before A's write, has its own `exchangeToken` call fail with an `HttpResponseError` (code 401).
5. Request B's catch block calls `invalidateAccessToken(sessionToInvalidate, config)`, which persists the stale session (with `accessToken = undefined`) to the same `offline_${shop}` record, clobbering A's freshly stored valid token [3](#0-2) .
6. Any subsequent request for the shop now fails authentication until a new OAuth/token-exchange cycle repairs the offline session, demonstrating the DoS.

export async function invalidateAccessToken(
  session: Session,
  config: AppConfigInterface,
): Promise<void> {
  config.logger.debug('Invalidating stale access token', {shop: session.shop});
  session.accessToken = undefined;
  await config.sessionStorage.storeSession(session);
