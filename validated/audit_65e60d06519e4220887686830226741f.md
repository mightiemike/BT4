Based on my research, I found a concrete precision/rounding mismatch analog in the signer weight threshold logic that mirrors the reported bug class (fixed-precision integer division causing an equality check to diverge from its "true" value, with a consensus-relevant outcome).

### Title
Inconsistent rounding between signer global-state agreement threshold and Nakamoto block approval threshold - ([File: libsigner/src/v0/signer_state.rs])

### Summary
The `GlobalStateEvaluator::reached_agreement` / `reached_disagreement` functions in `libsigner/src/v0/signer_state.rs` compute a 70%/30% weight threshold using **floor** integer division (`total_weight * 7 / 10`), whereas the consensus-critical block-approval threshold, `NakamotoBlockHeader::compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs`, computes the same nominal 70% cutoff using **ceiling** division (adding 1 whenever there is a remainder). [1](#0-0) [2](#0-1) 

### Finding Description
`compute_voting_weight_threshold` is the actual on-chain rule used by `verify_signer_signatures` to decide whether a Nakamoto block has been signed by enough weight to be accepted network-wide:
```rust
let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
u32::try_from((total_weight * threshold) / 10 + ceil)...
``` [3](#0-2) 

By contrast, the signer-side `GlobalStateEvaluator` (used to decide whether the *signer set* itself has reached agreement on global state, e.g. tx-replay sets) computes:
```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight) >= u64::from(self.total_weight).strict_mul(7) / 10
}
``` [4](#0-3) 

For any `total_weight` not evenly divisible by 10, the chain-level threshold rounds *up* while the signer-level threshold rounds *down*. Example: `total_weight = 511` (whose test the repo itself has for `compute_voting_weight_threshold`) gives a chain threshold of `358` (ceil of `357.7`) [5](#0-4) , while the signer-side floor-division threshold for the same 511 total weight would be `357` — one weight unit lower. A vote weight of exactly `357` satisfies `reached_agreement` (signer's view: consensus reached) but does **not** satisfy the higher, ceiling-based `compute_voting_weight_threshold` used on-chain for block signature verification. This is exactly the class of bug described in the report: a fixed-precision integer-division formula that is "close enough" in most cases but silently diverges from the value another, more precise/differently-rounded computation produces, at specific boundary inputs.

### Impact Explanation
This divergence does not itself corrupt block signatures (those still use the correctly-ceiling-rounded `compute_voting_weight_threshold`), but the signer-side `GlobalStateEvaluator` threshold governs whether signers believe the *signer set* has reached agreement on shared state (e.g., the global transaction-replay set consulted before signing, per `get_global_tx_replay_set`) [6](#0-5) . Because this threshold is one unit lower than the analogous on-chain block-approval threshold at boundary weights, a coalition just below the true 70% supermajority can cause the signer state machine to treat global state as agreed (and, e.g., adopt a tx-replay set) at a weight that a strict-majority observer computing with the on-chain formula would reject. This can lead two honest signer processes — or two versions of the software with these two formulas — to disagree on whether a given weight has "reached agreement," a minority-triggerable divergence bounded to temporary tip/state disagreement among signers, not outright fund loss.

### Likelihood Explanation
The trigger only requires `total_weight % 10 != 0` and a coalition holding a weight exactly at the floor-rounded threshold but below the ceil-rounded threshold — an unprivileged combination of signer weights that occurs naturally whenever the reward-cycle signer weight distribution isn't a multiple of 10 (i.e., essentially always). No majority collusion is needed; it is a deterministic rounding gap present in every reward cycle whose total weight isn't divisible by 10.

### Recommendation
Make `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` use the same ceiling-based rounding convention as `NakamotoBlockHeader::compute_voting_weight_threshold` (or, better, factor both through one shared helper), so that "70% agreement" always means the identical integer threshold regardless of which subsystem evaluates it.

### Proof of Concept
Using `total_weight = 511`:
- `NakamotoBlockHeader::compute_voting_weight_threshold(511) == 358` (verified by existing test) [5](#0-4) 
- `GlobalStateEvaluator::reached_agreement` with `vote_weight = 357`: `357 >= 511*7/10 = 357` → `true` (agreement reached per signer state machine)
- The same `357` weight fed into the chain's rule would be `357 < 358` → **not** enough for block approval.

Thus a weight of `357` is judged sufficient by the signer global-state agreement check but insufficient by the chain's own approval-threshold check for the same nominal 70% supermajority — a concrete equality divergence between two "70% of total_weight" computations in the same codebase.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
