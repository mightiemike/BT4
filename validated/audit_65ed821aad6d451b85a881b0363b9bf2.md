### Title
Replay/restore verification silently accepts a divergent native-position state root - (File: types/src/transaction/mod.rs)

### Summary
The Aptos "trading-native" feature adds a `position_state_checkpoint_hash` field to `TransactionInfoV1`, authenticated by the transaction accumulator/proof exactly like `state_checkpoint_hash`. However, the shared verification routine used by replay, backup-restore-verify, and archive-replay tooling (`TransactionOutput::ensure_match_transaction_info`) never compares this field against the locally computed position root, even though it does compare every other authenticated field (status, gas, write-set hash, event root).

### Finding Description
`TransactionInfoV1` carries `position_state_checkpoint_hash: Option<HashValue>` alongside `state_checkpoint_hash` and `hot_state_checkpoint_hash`: [1](#0-0) 

This field is populated during execution from a separate Merkle structure (`PositionDb`/`ProvablePositionStateSummary`), extended per-chunk in `DoStateCheckpoint::compute_position_checkpoint`, and folded into `TransactionInfoV1` in `assemble_transaction_infos`: [2](#0-1) [3](#0-2) 

Because `position_state_checkpoint_hash` is part of `TransactionInfo`, it is covered by the same accumulator/BCS hash that anchors `TransactionInfoListWithProof::verify` and `TransactionAccumulatorProof::verify` — i.e., it is a proof-bearing, authenticated field exactly like `state_checkpoint_hash`.

Yet `TransactionOutput::ensure_match_transaction_info`, the function used to cross-check a locally-produced `TransactionOutput` against a trusted, proof-verified `TransactionInfo` during replay/restore, only checks `status`, `gas_used`, `write_set` hash (`state_change_hash`), and `event_root_hash`. It explicitly skips the checkpoint hashes, with an inline TODO acknowledging the gap: [4](#0-3) 

```
// TODO(trading-native): this comparator ignores the checkpoint hashes
// (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
// tooling (e.g. db-tool's `replay_on_archive`) can report a successful
// replay even when the authenticated position state root diverges from
// local execution. Validate the checkpoint hashes here before enabling
// COMPUTE_TRADING_NATIVE_STATE_ROOTS.
```

This function is the sole per-transaction check used by the restore/replay path in `storage/backup/backup-cli/src/backup_types/transaction/restore.rs` (`TransactionListWithProofV2::verify` covers structural hash-chain-to-ledger-info binding, but the *content* match between a replayed `TransactionOutput` and the trusted `TransactionInfo` goes through `ensure_match_transaction_info`). The same routine backs `db-tool`'s `replay_on_archive` and other replay-verification tools mentioned in the TODO itself.

### Impact Explanation
If replayed/local execution of transactions on the "native position" (perp trading) sub-state diverges from the previously committed, ledger-info-anchored `position_state_checkpoint_hash` (due to a bug in `NativeStateCommitter`, `PositionDb`, the sharded Merkle-tree extend logic, or any node/version-specific non-determinism in that new subsystem), the divergence is **not detected** by replay verification. A node or tool running `replay_on_archive`/backup restore-verify would report success and consider a corrupted position sub-state (wrong committed native positions, wrong PnL/liquidation-relevant data) as validated, even though it doesn't match the authenticated on-chain root. This breaks the "committed state that differs from correct VM result... treated as verified" invariant, and undermines auditability/restore-integrity for the position sub-ledger, which is state-commitment/proof-integrity-relevant per the task's scope (replay/restore-path divergence not caught by verification).

### Likelihood Explanation
The check is unconditionally skipped for every `TransactionInfoV1` with `position_state_checkpoint_hash` set — it doesn't require any attacker action; it is a straightforward comparator omission acknowledged in-code via the TODO. The feature is currently gated behind `compute_trading_native_state_roots`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, so exploitability requires that flag to be active; the TODO itself states this must be fixed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," implying the gap is real but the feature may not yet be turned on in production. If/when enabled, the gap applies deterministically to every replay/restore-verify pass, so likelihood of the corruption escaping detection (once the underlying state diverges) is high.

### Recommendation
Extend `ensure_match_transaction_info` to compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` against locally recomputed values (or explicitly document/require that callers verify these separately before use), and gate `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/replay-verify tooling on this fix as the existing TODO already recommends.

### Proof of Concept
Not applicable as a runtime exploit — this is a code-level verification gap, provable by inspection: `TransactionInfoV1::position_state_checkpoint_hash` is a proof-covered field (`types/src/transaction/mod.rs:2442-2461`, hashed via `CryptoHash`/`BCSCryptoHash` on `TransactionInfo` and checked by `TransactionAccumulatorProof`/`TransactionInfoListWithProof::verify`), but `ensure_match_transaction_info` (`types/src/transaction/mod.rs:2139-2204`) never reads or compares it, as the inline TODO comment confirms. Any test that (a) constructs a `TransactionOutput` whose write set differs only in `native_position` entries from the state that produced the trusted `TransactionInfo`'s `position_state_checkpoint_hash`, while keeping status/gas/write_set-hash/events/state_checkpoint_hash unchanged, and (b) calls `ensure_match_transaction_info`, would return `Ok(())` despite the position-state mismatch.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
