### Title
Hardcoded 5% slippage tolerance on protocol-forced Uniswap V3 auto-swaps enables value extraction from user deposits - (File: `x/uexecutor/keeper/execute_inbound_gas.go`, `x/uexecutor/keeper/execute_inbound_gas_and_payload.go`, `x/uexecutor/keeper/outbound.go`)

### Summary
The Sturdy `UNISWAP_FEE` finding is about a hardcoded routing/fee parameter that ignores real market conditions and causes value loss versus optimal execution. Push Chain's `uexecutor` keeper has a directly analogous hardcoded parameter: every protocol-initiated Uniswap V3 swap (gas-token auto-swap on inbound GAS/GAS_AND_PAYLOAD processing, and gas-refund auto-swap on outbound completion) uses a fixed `minPCOut = quote * 95 / 100` slippage tolerance, regardless of trade size, pool depth, or token volatility.

### Finding Description
`ExecuteInboundGas` [1](#0-0) , `gasAndPayloadDepositAutoSwap` [2](#0-1) , and `applyGasRefund` [3](#0-2)  all follow the same pattern: fetch the current fee tier via `GetDefaultFeeTierForToken`, fetch a spot quote via `GetSwapQuote` (which calls Uniswap V3 `QuoterV2.quoteExactInputSingle`) [4](#0-3) , and then unconditionally apply a hardcoded 95% floor before calling `CallPRC20DepositAutoSwap` / `CallUniversalCoreRefundUnusedGas`. There is no dynamic slippage model based on trade size relative to pool liquidity, no circuit breaker for large trades against thin PRC20/WPC pools, and no protection such as a TWAP-based reference price to detect if the current spot price has been manipulated immediately before the swap executes.

Because inbound processing is deterministic and reproducible (validators independently vote and finalize the same UniversalTx), an attacker who can predict or influence the ordering of transactions within the block/ordering window that triggers `ExecuteInboundGas`/`ExecuteInboundGasAndPayload`/outbound finalization can move the pool price against the pending swap (e.g. buy WPC before the deposit-driven swap lands, sell after), extracting up to the full 5% slippage buffer from the user's/protocol's swapped value. Because the tolerance is a flat 5% regardless of notional size, this is worst for larger deposits/refunds and thin pools — mirroring the Sturdy report's core complaint that a fixed, unconditional parameter (there: fee tier; here: slippage tolerance) creates a persistent, exploitable gap between "optimal" execution and what the protocol actually settles for.

### Impact Explanation
This falls under "corruption of PRC20 or native asset accounting… refund accounting" and "unauthorized… state transitions in universal execution flows" per the allowed-impact gate: an unprivileged attacker can cause the protocol to execute a worse-than-market swap on a user's inbound deposit or on the automatic gas refund, resulting in real, measurable value loss to the depositor/receiver (up to 5% of the swapped notional) with no compensating benefit and no way for the affected user to opt out, since the swap and its slippage bound are entirely protocol-controlled.

### Likelihood Explanation
Likelihood is moderate: it does not require any privileged role, malicious validator, or malicious relayer — only an ordinary market participant capable of trading against the same PRC20/WPC Uniswap V3 pool the protocol uses, timed around the (predictable, deterministic) block in which the inbound/outbound is processed. Thinly-liquidity PRC20 pairs (newly listed tokens) are the most exposed, and the fixed 5% is large enough on modest pools to be profitable after gas costs.

### Recommendation
Replace the flat 95%/5% constant with a slippage bound derived from trade size vs. current pool liquidity (e.g., cap price impact rather than a fixed percentage), and/or use a TWAP-based reference price from the pool's oracle to detect and reject swaps where the spot price has deviated abnormally from the recent average immediately before execution. Consider making the tolerance configurable per token/pool via `x/uregistry` token config rather than hardcoding it in three separate keeper call sites.

### Proof of Concept
1. Observe a pending inbound deposit (or completed outbound triggering a gas refund) for a PRC20 token paired against WPC in a low-liquidity Uniswap V3 pool on Push Chain.
2. Before the block in which `ExecuteInboundGas`/`ExecuteInboundGasAndPayload`/`handleSuccessfulOutbound` executes the auto-swap, submit a trade that moves the pool price against the pending swap direction.
3. The protocol computes `minPCOut = quote * 95 / 100` off the now-manipulated spot price at `GetSwapQuote` time [5](#0-4)  and executes `CallPRC20DepositAutoSwap`/`CallUniversalCoreRefundUnusedGas` at that degraded price.
4. Reverse the initial trade after the protocol swap lands, capturing the spread up to the 5% tolerance at the expense of the depositor's/refund recipient's proceeds.

// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
