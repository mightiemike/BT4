## Analog identified

This maps to the same bug class as the Lavarage H-01 finding: two pieces of state that are supposed to travel together (in Lavarage, `position_account` in `borrow_collateral` vs. `repay_sol`; here, the `universalTxId` used for eligibility checks vs. the `PRC20` used to determine the actual payout asset) are accepted from independently-controlled fields without cross-validation, letting an attacker splice a legitimate authorization (a real stuck UTX) onto attacker-chosen payout data.

### Title
Rescue-outbound asset confusion — attacker-supplied `PRC20` is never bound to the original inbound's locked asset - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`AttachRescueOutboundFromReceipt` builds a `RESCUE_FUNDS` outbound by combining two independently-sourced pieces of data from a user-triggered `RescueFundsOnSourceChain` event: the `universalTxId` (used only to check *eligibility* — was the original deposit's PCTx `FAILED`, or is there a `REVERTED` `INBOUND_REVERT`) and `PRC20` (used to resolve the actual `ExternalAssetAddr`/token config that becomes the destination-chain payout asset). Nothing ties `PRC20` back to `originalUtx.InboundTx.AssetAddr`, the asset that was actually associated with that UTX.

### Finding Description [1](#0-0) 
walks the log, decodes `universalTxId` and `PRC20` from the event, and uses `universalTxId` solely to fetch `originalUtx` and check the CEA-failed / revert-reverted eligibility conditions. It never checks that `event.PRC20` corresponds to `originalUtx.InboundTx.AssetAddr`. [2](#0-1) 
then resolves `tokenCfg` purely from `event.PRC20` (attacker-controlled, independent of the UTX's real asset) and sets `outbound.ExternalAssetAddr = tokenCfg.Address` while `outbound.Amount = originalUtx.InboundTx.Amount` — i.e., the raw numeric amount from the *original* asset is carried over unchanged and reattached to a completely different asset address chosen via `PRC20`. `Recipient` is safely pinned to the original inbound's sender/RevertInstructions (so this isn't a direct fund-redirection-to-attacker bug), but the *asset* of the resulting outbound is fully attacker-selectable as long as any `PRC20`→token-config mapping exists for the source chain.

This directly mirrors the Lavarage pattern: the code validates one linking ID (`position_account` / `universalTxId`) but a second value used by the privileged action (`repay_sol`'s position / `PRC20`'s resulting asset) is taken from an unrelated, attacker-controlled input instead of being derived from or checked against the same authorized state.

### Impact Explanation
Once a UV quorum observes the resulting `RESCUE_FUNDS` outbound (an honest-validator TSS signing/broadcast, since observation just confirms whatever asset/amount was recorded in the `PendingOutbounds`/UTX entry — see `attachOutboundsToUtx` at [3](#0-2) ), the source-chain gateway/escrow will release `originalUtx.InboundTx.Amount` units of whatever token `tokenCfg.Address` maps to — a token that was never actually locked by that UTX. This is an unauthorized-release / asset-accounting corruption: it can be used to drain escrowed balances of any registered token on the source chain by attaching an inflated- or arbitrary-token payout to any UTX that happens to satisfy the (cheap-to-reach) eligibility conditions — e.g. a deliberately-caused CEA deposit failure (unregistered/invalid asset triggers `PcTx[0].Status = "FAILED"`, as shown in the test's own `setupRescueFundsTest` at [4](#0-3) ) with a small original `Amount`, then rescuing with `PRC20` pointed at a high-value token to exfiltrate a mismatched amount/asset pair.

### Likelihood Explanation
The precondition (a UTX with a FAILED first PCTx, or a REVERTED auto-revert) is attacker-reachable without any privileged role — a user can trivially manufacture a failed CEA deposit (e.g. sending to an unregistered asset address, exactly as the repo's own test fixture does) and then call the source-chain `rescue_funds` entry point with an arbitrary `PRC20` parameter. No validator, node, or admin misbehavior is required — only honest UV observation of whatever the receipt/event says, since the Go-side keeper is the one failing to cross-validate the asset before ever creating the pending outbound.

### Recommendation
In `AttachRescueOutboundFromReceipt`, after loading `originalUtx`, require that `event.PRC20` resolves to the *same* token config as `originalUtx.InboundTx.AssetAddr` (or, equivalently, look up `tokenCfg` from `originalUtx.InboundTx.AssetAddr` directly instead of trusting `event.PRC20`), rejecting the rescue if they diverge — analogous to the report's fix of replacing multiple independently-checked keys with a single check tying the payout instruction back to the authorized record's own identifier.

### Proof of Concept
Not independently executable here (would require standing up the EVM `UniversalGatewayPC` contract and a real inbound/outbound integration harness), but the existing test suite already demonstrates the missing linkage: `test/integration/uexecutor/rescue_funds_test.go`'s `buildRescueFundsLog` helper lets the caller pass `prc20Addr` completely independently of the `utxId`/original inbound's `AssetAddr` (see [5](#0-4)  and the call sites at lines 155-184), and no test asserts that the chosen `prc20Addr` must match the original UTX's asset — confirming the keeper accepts any `PRC20` value for the eligibility-checked UTX.

func (k Keeper) attachOutboundsToUtx(
	ctx sdk.Context,
	utxId string,
	outbounds []*types.OutboundTx,
	revertMsg string, // revert msg if the outbound is for a inbound revert
) error {

	if len(outbounds) == 0 {
		return nil
	}
	return k.UpdateUniversalTx(ctx, utxId, func(utx *types.UniversalTx) error {

		for _, outbound := range outbounds {

			utx.OutboundTx = append(utx.OutboundTx, outbound)

			// Compute signature expiry deadline for the destination chain.
			var signingDeadline int64
			if chainCfg, err := k.uregistryKeeper.GetChainConfig(ctx, outbound.DestinationChain); err == nil {
				if chainCfg.TssSigningDeadline != nil && *chainCfg.TssSigningDeadline > 0 {
					signingDeadline = ctx.BlockTime().Unix() + int64(chainCfg.TssSigningDeadline.Seconds())
				}
			}

			// Write to pending outbounds index (inside UpdateUniversalTx closure for atomicity)
			if err := k.PendingOutbounds.Set(ctx, outbound.Id, types.PendingOutboundEntry{
				OutboundId:      outbound.Id,
				UniversalTxId:   utxId,
				CreatedAt:       ctx.BlockHeight(),
				SigningDeadline: signingDeadline,
			}); err != nil {
				return fmt.Errorf("failed to set pending outbound index for %s: %w", outbound.Id, err)
			}

func buildRescueFundsLog(
	t *testing.T,
	utxId string, // UTX key (64-char hex, no 0x prefix)
	prc20Addr common.Address,
	senderAddr common.Address,
	chainNamespace string,
	gasFee, gasPrice, gasLimit *big.Int,
) *evmtypes.Log {
	t.Helper()

	stringType, _ := abi.NewType("string", "", nil)
	uint8Type, _ := abi.NewType("uint8", "", nil)
	uint256Type, _ := abi.NewType("uint256", "", nil)

	args := abi.Arguments{
		{Type: stringType},  // chainNamespace
		{Type: uint8Type},   // txType (RESCUE_FUNDS = 4)
		{Type: uint256Type}, // gasFee
		{Type: uint256Type}, // gasPrice
		{Type: uint256Type}, // gasLimit
	}
	data, err := args.Pack(chainNamespace, uint8(4), gasFee, gasPrice, gasLimit)
	require.NoError(t, err)

	// UTX ID is stored as a bytes32 topic: "0x" + the 64-char hex UTX key.
	utxIdTopic := "0x" + utxId

	gwPCAddr := utils.GetDefaultAddresses().UniversalGatewayPCAddr

	return &evmtypes.Log{
		Address: gwPCAddr.Hex(),
		Topics: []string{
			uexecutortypes.RescueFundsOnSourceChainEventSig,
			utxIdTopic,
			common.BytesToHash(prc20Addr.Bytes()).Hex(),  // indexed prc20
			common.BytesToHash(senderAddr.Bytes()).Hex(), // indexed sender
		},
		Data:    data,
		Removed: false,
	}
}
