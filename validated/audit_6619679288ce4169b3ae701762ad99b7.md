### Title
Empty PBFT signature list bypasses quorum check, allowing unauthenticated SR/block commit data acceptance - (File: framework/src/main/java/org/tron/core/net/messagehandler/PbftDataSyncHandler.java)

### Summary
`validPbftSign()` in `PbftDataSyncHandler` is meant to enforce that a `PbftCommitMessage` carries at least `2/3+1` valid SR signatures before its committed data (block finality proof or SR-list finality proof) is persisted. However, the entire quorum/signature-verification logic is nested inside `if (srSignList.size() != 0) { ... }`. If a peer sends a `PbftCommitMessage` whose signature list is empty, the check is skipped entirely and the function falls through to `return true`, exactly mirroring the reported Chainlink bug where `transmit()`/`verifyTransmitSigners()` never verified that the submitted signature count actually met quorum, letting an empty signature array pass.

### Finding Description
`processPBFTCommitMessage` parses the PBFT commit `Raw` payload and gates persistence of the result on `validPbftSign`: [1](#0-0) 

`validPbftSign` is supposed to require that the number of *distinct* SR signatures meets `Param.getInstance().getAgreeNodeCount()` (2/3+1 of the SR set) and that every signature recovers to a legitimate SR address: [2](#0-1) 

The quorum-size check (`srSignSet.size() < Param.getInstance().getAgreeNodeCount()`), the per-signature ECDSA recovery/whitelist check, and the "all signatures consumed" check are all inside the `if (srSignList.size() != 0)` block. When `srSignList` is empty (`size() == 0`), none of this logic executes, and the method returns `true` unconditionally — the same class of defect as `verifyTransmitSigners()` returning success for zero submitted signatures because the number of signatures was never checked against the required signer/quorum count.

Because `PbftCommitMessage` is a message that is received directly from the p2p network (see `processMessage`, which caches `pbftCommitMessage` keyed by `raw.getViewN()` before any signature validation occurs) and later replayed through `processPBFTCommitData` → `processPBFTCommitMessage`, an attacker-controlled or malicious peer can craft a `PbftCommitMessage` containing a well-formed `Raw` (arbitrary `DataType.BLOCK`/`DataType.SRL`, `viewN`, `epoch`) with an **empty signature list**. `validPbftSign` will return `true`, and the payload will be written into `PbftSignDataStore` via `putBlockSignData`/`putSrSignData` as if it were legitimately signed by 2/3+1 SRs.

### Impact Explanation
`PbftSignDataStore` persists node-local PBFT finality attestations for blocks and for the SR list (used by PBFT-dependent consumers such as light-client/solidity finality verification and SR-list epoch tracking, as evidenced by `ChainBaseManager`/`TronNetDelegate` wiring). Accepting an unsigned (zero-signature) commit record means a peer can inject fabricated "PBFT-confirmed" state into a node's local store without any of the 2/3+1 SR signatures the protocol is supposed to require. This breaks the core trust assumption of PBFT finality data in this codebase: a single malicious/lying peer, with no cryptographic proof of consensus at all, can cause a victim node to record a false finality attestation for a given block or SR-list epoch, corrupting a security-critical accounting/consensus-state store and potentially misleading any logic or external client that trusts `PbftSignDataStore` contents as evidence of committee agreement.

### Likelihood Explanation
The vulnerable code path is reachable by any connected peer sending a normal `PbftCommitMessage` over the p2p network — no privileged role, on-chain permission, or special account is required, since `processMessage`/`processPBFTCommitMessage` handle raw network messages, and `allowPBFT()` merely gates whether PBFT is enabled at all (a chain-wide config toggle, not an authorization check on the sender). Constructing a `Raw` payload with a chosen `viewN`/`epoch`/`dataType` and attaching zero signatures is trivial for any client speaking the protocol.

### Recommendation
Move the quorum-size and signature-count enforcement outside of the `if (srSignList.size() != 0)` guard so that an empty (or otherwise under-quorum) signature list is explicitly rejected, e.g.:

```java
private boolean validPbftSign(Raw raw, List<ByteString> srSignList,
    List<ByteString> currentSrList) {
  Set<ByteString> srSignSet = new ConcurrentSet();
  srSignSet.addAll(srSignList);
  if (srSignSet.size() < Param.getInstance().getAgreeNodeCount()) {
    logger.error("sr sign count {} < sr count * 2/3 + 1 == {}", srSignSet.size(),
        Param.getInstance().getAgreeNodeCount());
    return false;
  }
  // ... rest of existing per-signature verification, unconditionally executed
}
```
This ensures the quorum check always runs regardless of `srSignList` being empty, closing the bypass.

### Proof of Concept
1. A malicious/compromised peer connects to a victim node and enables PBFT is on (`allowPBFT()` true, typical default for the network).
2. The peer sends a `PbftCommitMessage` whose `PBFTCommitResult.data` is a valid `Raw` protobuf (`dataType = BLOCK`, arbitrary `viewN`) but whose `PBFTCommitResult.signature` list is empty.
3. `processMessage` caches this message keyed by `viewN` without validation.
4. When the victim later processes the corresponding block via `processPBFTCommitData`, it calls `processPBFTCommitMessage`, which calls `validPbftSign(raw, emptyList, srList)`.
5. Because `srSignList.size() == 0`, the `if` block in `validPbftSign` is skipped and the method returns `true`.
6. `pbftSignDataStore.putBlockSignData(raw.getViewN(), pbftCommitMessage.getPbftSignCapsule())` is executed, persisting an attacker-supplied, completely unsigned "PBFT commit" record as if it were validated by 2/3+1 SRs.

Note: I could not fully trace every downstream consumer of `PbftSignDataStore` records (e.g., whether any RPC/light-client/cross-chain component treats this store as an authoritative finality proof) within the indexed portion of the codebase; a Devin session with full repository access would be needed to enumerate all such consumers and precisely bound the blast radius of the forged records.

      PbftSignDataStore pbftSignDataStore = chainBaseManager.getPbftSignDataStore();

        pbftSignDataStore.putSrSignData(raw.getEpoch(), pbftCommitMessage.getPbftSignCapsule());

      }

      logger.error("", e);
    }

  private boolean validPbftSign(Raw raw, List<ByteString> srSignList,
      List<ByteString> currentSrList) {
    //valid sr list
    if (srSignList.size() != 0) {
      Set<ByteString> srSignSet = new ConcurrentSet();
      srSignSet.addAll(srSignList);
      if (srSignSet.size() < Param.getInstance().getAgreeNodeCount()) {
        logger.error("sr sign count {} < sr count * 2/3 + 1 == {}", srSignSet.size(),
            Param.getInstance().getAgreeNodeCount());
        return false;
      }
      byte[] dataHash = Sha256Hash.hash(true, raw.toByteArray());
      Set<ByteString> srSet = Sets.newHashSet(currentSrList);
      List<Future<Boolean>> futureList = new ArrayList<>();
      for (ByteString sign : srSignList) {
        futureList.add(executorService.submit(
            new ValidPbftSignTask(raw.getViewN(), srSignSet, dataHash, srSet, sign)));
      }
      for (Future<Boolean> future : futureList) {
        try {
          if (!future.get()) {
            return false;
          }
        } catch (Exception e) {
          logger.error("", e);
        }
      }
      if (srSignSet.size() != 0) {
        return false;
      }
    }
    return true;
  }
