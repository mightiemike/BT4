### Title
Collateral ledger amount mutated before receive-tokens confirms actual transfer, and unverified against actual token receipt - (File: mainnet/contracts/market/v0-market-vault.clar)

### Summary
`collateral-add` in `v0-market-vault.clar` records the caller-supplied `amount` into the user's collateral ledger via `add-user-collateral` before the token transfer (`receive-tokens`) actually executes, and the ledger is never reconciled against the amount actually received by the contract. If the collateral `ft` is a fee-on-transfer or otherwise non-1:1 SIP-010 token, the vault credits the user with more collateral than it actually took custody of — the exact "wrong stake amount is stored" bug class from the external report (amount recorded before/without accounting for a transfer-time deduction).

### Finding Description
In `collateral-add`: [1](#0-0) 

```
(define-public (collateral-add (account principal) (amount uint) (ft <ft-trait>) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve-or-create account))
        (user-id (get id entry))
        (mask (get mask entry))
        (updated-mask (mask-update mask asset-id true true))
        (updated-entry (merge entry (refresh updated-mask)))
        (result (add-user-collateral user-id asset-id amount)))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-add states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-tokens ft amount account))

    (insert updated-entry)
    ...
    (ok result)))
```

`add-user-collateral` writes `amount` into the user's collateral map as part of the `let`-binding evaluation, i.e., before `receive-tokens` (the actual `ft transfer` call that moves tokens into the vault) runs. The ledger update uses the caller-declared `amount`, not any value returned by, or verified against, the actual transfer outcome. There is no post-transfer check comparing the vault's token balance delta to `amount`.

This mirrors the audited "wrong stake amount is stored" bug: a value (`stake.amount` / here, the collateral ledger entry) is bound/stored using the nominal input amount rather than the amount actually received after any fee or discrepancy is applied by the underlying asset's transfer logic. Because `collateral-add` accepts an arbitrary `<ft-trait>` implementation supplied by the caller (any asset registered via `get-asset`/DAO asset list, not a hardcoded, trusted token), the ledger is only as correct as the assumption that `transfer amount` always moves exactly `amount` tokens — an assumption that does not hold for tokens with transfer fees, rebasing behavior, or other non-standard SIP-010 implementations.

### Impact Explanation
If the actual number of tokens received by the vault is less than `amount` (e.g., a transfer fee deducted by the token contract), the user's recorded collateral (`add-user-collateral ... amount`) exceeds the tokens actually custodied by the protocol. This inflates the user's borrowing capacity relative to real backing assets, and on withdrawal (`collateral-remove` → `send-tokens`) other users' collateral/assets are used to make up the shortfall — a direct path to insolvency/undercollateralization: theft of funds at rest (other depositors' backing assets) once the affected position borrows against the inflated collateral. This lands in the Critical impact category (protocol insolvency / theft of user funds at rest).

### Likelihood Explanation
Exploitability depends entirely on whether an asset with non-standard transfer semantics (fee-on-transfer, rebasing, etc.) can be listed as a collateral asset. Since `get-asset`/asset registration is DAO-governed, whether such an asset could reach `collateral-add` is a listing/governance decision, which lowers likelihood under normal operation but the code itself contains no defensive check (e.g., balance-before/balance-after reconciliation) to prevent it if such an asset were ever listed, or if a listed token's behavior changes post-listing (e.g., a token upgrade introducing a fee).

### Recommendation
Measure the vault's actual balance of `ft` before and after calling `receive-tokens`, and use the actual received delta (not the caller-supplied `amount`) when calling `add-user-collateral`. Alternatively, require and enforce that `receive-tokens` returns the actual number of tokens received, and use that value for the ledger update, mirroring the "store `staked-amount` in `stake.amount`" fix pattern.

### Proof of Concept
1. DAO/registry lists (or an already-listed token contract is upgraded/behaves as) a fee-on-transfer SIP-010 `ft` as a supported collateral asset for `asset-id`.
2. User calls `market.collateral-add` (or the underlying `market-vault.collateral-add`) with `amount = 1000`.
3. During evaluation, `add-user-collateral user-id asset-id amount` runs with `amount = 1000`, so the collateral ledger for `user-id`/`asset-id` becomes `1000`.
4. `receive-tokens ft amount account` executes `ft transfer 1000 account current-contract`; if `ft`'s transfer logic deducts a 2% fee, the vault contract actually receives only `980` tokens.
5. The transaction succeeds (no revert), and `insert updated-entry` persists the updated mask; the ledger now shows `1000` collateral while the vault holds only `980` tokens of that asset.
6. The user's position is valued off the ledger's `1000` for LTV/health checks, letting them borrow against 1000 units of collateral value while only 980 backs it — a shortfall that is socialized onto the rest of the pool when withdrawal/liquidation later fails to fully back all claims. [2](#0-1)
