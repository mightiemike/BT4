### Title
Payload-Triggered Outbound Silently Lost When Attachment Fails After Successful EVM Execution — No Automatic Or Admin-Triggered Recovery Path ([File: x/uexecutor/keeper/execute_inbound_funds_and_payload.go])

### Summary
In `CyanPeerPlan.revive()`, a plan could be marked `COMPLETED` while the underlying NFT stayed locked, with no automatic unlock and only a manual admin fallback. Push Chain's `ExecuteInboundFundsAndPayload` has the same shape of bug: a UEA payload can execute successfully (real funds are moved/burned on the EVM side via `ExecutePayloadV2`), but if `AttachOutboundsToExistingUniversalTx` then fails to record the resulting outbound on the `UniversalTx`, the funds movement that the outbound was supposed to represent is never queued for TSS signing/broadcast — and unlike the `RescueFunds` escape hatch, there is no remediation path for this specific case.

### Finding Description
The deposit + payload flow in `ExecuteInboundFundsAndPayload` runs the UEA payload directly against `sdkCtx` (not inside a `CacheContext`), so any state change performed by the payload (e.g., a call that burns/locks PRC20 for a destination-chain release) commits unconditionally: [1](#0-0) 

When `receipt` is non-nil and `payloadErr == nil`, the code calls `AttachOutboundsToExistingUniversalTx` to turn the payload's emitted outbound intent into a real `OutboundTx` entry (which is what drives TSS signing/broadcast to the destination chain). If that attach call fails, the only remediation is:

```go
if attachErr := k.AttachOutboundsToExistingUniversalTx(sdkCtx, receipt, utx); attachErr != nil {
    if storeErr := k.UpdateUniversalTx(sdkCtx, universalTxKey, func(u *types.UniversalTx) error {
        u.RevertError = attachErr.Error()
        return nil
    }); storeErr != nil {
        return storeErr
    }
}
``` [2](#0-1) 

This mirrors the same pattern found in `execute_inbound_funds.go`, `execute_inbound_gas_and_payload.go`, and `handle_failed_inbound_validation.go`: an EVM-side action commits, then a downstream book-keeping step can fail and is only recorded as an inert `RevertError` string field on the `UniversalTx` proto, not an actionable state: [3](#0-2) 

Unlike a genuinely failed deposit — which `RescueFunds` explicitly supports rescuing — `AttachRescueOutboundFromReceipt` is intentionally gated to require that the deposit **failed**: [4](#0-3) 

This means: for the case where deposit succeeded and the payload also succeeded (i.e., real fund-moving side effects occurred), but the resulting outbound record failed to attach, there is no rescue/re-attach/retry message exposed anywhere in `x/uexecutor` — the `RevertError` field is set and the flow silently stops, exactly analogous to `CyanPeerPlan.revive()` completing the plan while leaving the NFT locked with no automatic unlock.

### Impact Explanation
If the attach step fails after a payload has already produced a real, on-chain-committed effect meant to trigger a destination-chain release (i.e., the "plan is completed" analog), the corresponding outbound is never created, never entered into `PendingOutbounds`, and never signed/broadcast by UVs. The recipient never receives the released funds on the destination chain, and there is no message or automatic mechanism in the module to regenerate the missing outbound from the `RevertError`-flagged `UniversalTx` — a genuine unauthorized-permanent-loss/freezing condition matching the "permanent freezing ... of user or protocol-controlled funds" impact category.

### Likelihood Explanation
Likelihood depends on how often `AttachOutboundsToExistingUniversalTx` can fail post-execution (e.g., transient token-config lookup errors, gas-fee-info lookup failures, or duplicate outbound IDs) — the exact failure surface of that function was not directly inspected in this pass. It is not attacker-forced in the classic sense, but any legitimate, correctly signed inbound with a payload that triggers an outbound is exposed to this gap whenever the attach step errors, and no unprivileged or admin action exists to recover the exact scenario (only the "deposit failed" rescue path is wired up).

### Recommendation
Add a remediation/rescue path (or automatic retry) for the case where a payload executed successfully but the resulting outbound failed to attach — either by re-attempting `AttachOutboundsToExistingUniversalTx` from `RevertError`-flagged `UniversalTx` entries, or by exposing an explicit rescue message analogous to `RescueFunds` that does not require the deposit itself to have failed, so successfully executed payload effects are never left with no path to completion.

### Proof of Concept
Not independently exploited in this pass; this is a static code-path analysis. Confirming exploitability requires demonstrating a concrete failure trigger inside `AttachOutboundsToExistingUniversalTx` (e.g., a `GetTokenConfig`/gas-fee lookup error) occurring after a state-changing `ExecutePayloadV2` call, which should be validated in a Devin session with full repository/test access.
