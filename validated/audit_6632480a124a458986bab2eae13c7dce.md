**Analysis:** The exploit premise assumes `get_state_value_bytes_for_object_group_resource` extracts a byte slice from a fixed-offset packed blob, where an oversized `CollectionResource` could misalign subsequent entries. That's not how it works.

`ObjectGroupResource` is deserialized via `bcs::from_bytes(state_value.bytes())` into a proper `BTreeMap<StructTag, Vec<u8>>` [1](#0-0) . BCS's `BTreeMap`/`Vec<u8>` encoding is length-prefixed per entry (each value is preceded by its own ULEB128 length), and the struct definition is a real map, not a byte-offset table [2](#0-1) . After deserialization, the lookup is `object_group_resource.group.get(struct_tag)`, a keyed BTreeMap lookup by `StructTag`, not an index/offset computation [3](#0-2) .

`CollectionResource` itself is a plain variable-length struct (`AccountAddress`, three `String`s, an `EventHandle`) with no fixed-size assumption anywhere in its serialization or in the group packing code [4](#0-3) . Its size making it "larger" than expected has no bearing on how neighboring entries in the `BTreeMap<StructTag, Vec<u8>>` are parsed — BCS correctly consumes exactly the length-prefixed bytes for each map value regardless of value size, so there is no mechanism for cross-contamination between group members such as `0x4::collection::Collection` and any other tag (e.g. `FixedSupply`, `UnlimitedSupply`) in the same group [5](#0-4) .

Since the "packing" is a standard length-prefixed BCS map (not fixed-offset packing), there is no unprivileged input (however large the `CollectionResource` fields are) that can cause the extracted `Bytes` for one struct tag to be attributed to a different key — this would require a bug in the BCS decoder itself, not in application logic. No corruption of committed state, proof material, or authenticated response results from this code path.
