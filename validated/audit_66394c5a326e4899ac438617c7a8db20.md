### Title
`meta_tx_v0` syscall produces a nonce-less, fully deterministic transaction hash, enabling replay of signed meta-transactions - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/transaction_hash/transaction_hash.cairo`)

### Summary
The `meta_tx_v0` syscall lets any contract invoke another contract's `__execute__` entry point while injecting an attacker/caller-supplied `signature` and a synthetic `TxInfo` whose `transaction_hash` is computed by `compute_meta_tx_v0_hash`. Unlike every other Starknet transaction hash, this hash intentionally omits the `nonce` field (it is hard-coded to `0` and not folded into the hash), so the exact same `(contract_address, entry_point_selector, calldata, chain_id)` tuple always produces the identical `meta_tx_hash`/signature pair, with nothing at the protocol layer preventing that same call from being re-executed any number of times, in the same or later blocks. This mirrors the reported bug class: a signed authorization message that is expected to be single-use (because Starknet transaction hashes conventionally embed a nonce "to prevent re-execution of transactions", as documented at line 48-50 of the same file) is left without any replay-prevention field, shifting all replay-protection burden onto each callee contract's own bookkeeping — exactly the situation criticized in the referenced report, where lack of a "has this signature already been used" check allowed reuse of a previously valid signed authorization.

### Finding Description
`execute_meta_tx_v0` in `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo` (lines 290-367) builds a synthetic `TxInfo` for the inner call with `nonce=0` unconditionally: [1](#0-0) 

The hash itself, `compute_meta_tx_v0_hash`, is computed over only `contract_address`, `entry_point_selector`, `calldata`, and `chain_id` — with `additional_data_size=0`, i.e., no nonce or any other uniqueness-inducing value is folded in: [2](#0-1) 

By contrast, the file's own documentation of `CommonTxFields.nonce` explicitly states the nonce exists to "prevent re-execution of transactions": [3](#0-2) 

The Rust-side (blockifier) implementation of the same syscall mirrors this: `meta_tx_v0` in `syscall_base.rs` computes `transaction_hash` via `InvokeTransactionV0::calculate_transaction_hash`, again with `nonce: Nonce(0.into())` and no per-call uniqueness value, and passes the caller-supplied `signature` straight through unchanged into the fabricated `TransactionInfo`: [4](#0-3) 

Any account-like contract that is designed to be called via `meta_tx_v0` and that verifies the caller's authority by checking a signature against `tx_info.transaction_hash` (the standard, conventional pattern used throughout the codebase — see `account_with_real_validate.cairo`'s `check_ecdsa_signature(message_hash: tx_info.transaction_hash, ...)`) has no way to distinguish a fresh invocation from a replay, because the hash and signature supplied to it are bit-for-bit identical across calls: [5](#0-4) 

This is directly analogous to the reported EIP-712 replay bug: a signed authorization payload/hash is treated as reusable proof of intent by target logic, yet the underlying signing/hashing scheme (here, a core Starknet syscall/protocol primitive rather than a bespoke marketplace contract) has no nonce or "already consumed" tracking, so the same signed message can be validly resubmitted.

### Impact Explanation
Any unprivileged transaction sender can trigger `execute_meta_tx_v0`/`meta_tx_v0` (it is only rejected in `Validate` mode, per `reject_syscall_in_validate_mode`) as part of an ordinary `INVOKE` transaction's execution, with fully attacker-chosen `contract_address`, `entry_point_selector` (constrained to `EXECUTE_ENTRY_POINT_SELECTOR`/`__execute__`), `calldata`, and `signature`. Because the resulting `transaction_hash` given to the target contract is deterministic and nonce-free, a previously captured/observed valid `(calldata, signature)` pair for a meta-tx call can be resubmitted arbitrarily many times by any actor able to invoke the syscall — including the original account itself, or a malicious relayer that intercepts and rebroadcasts the call — resulting in unauthorized repeated execution of account actions that were intended to be authorized once (e.g., replaying a one-time delegated authorization, permit-like approval, or "execute once" signed action) on any contract that relies on `tx_info.transaction_hash`/signature freshness rather than maintaining its own separate nonce/idempotency storage.

### Likelihood Explanation
The behavior is deterministic and always reproducible — it requires no race condition, no validator collusion, and no privileged access. Any contract built to accept `meta_tx_v0`-style calls and verify authorization via signature-over-`transaction_hash` (the idiomatic pattern demonstrated elsewhere in this very codebase) is affected as soon as one valid signed payload is observed on-chain (which is inherent, since the calldata/signature must be submitted in a public transaction to be executed the first time). Likelihood of exploitation is therefore high for any contract adopting the conventional signature-verification idiom against `meta_tx_v0`'s synthetic `TxInfo`.

### Recommendation
Fold a genuine uniqueness value into the meta-tx hash and enforce single-use at the protocol layer, mirroring how normal transactions bind `nonce` into their hash specifically "to prevent re-execution." Concretely: (1) require callers of `meta_tx_v0` to supply a nonce/expiration that becomes part of `compute_meta_tx_v0_hash`'s hashed data (instead of hard-coding `nonce=0` and `additional_data_size=0`), and (2) track consumed meta-tx hashes (e.g., per target contract, analogous to Foundation's `privateSaleInvalidated` mapping fix) so a given signed meta-transaction cannot be executed more than once, either within the OS's `execute_meta_tx_v0` (Cairo) or within blockifier's `SyscallHandlerBase::meta_tx_v0` (Rust) — keeping both implementations consistent, since they must produce identical hashes for OS/blockifier equivalence.

### Proof of Concept
1. Deploy a target account-like contract `T` whose `__execute__` (or an entry point it calls) verifies `check_ecdsa_signature(message_hash: tx_info.transaction_hash, public_key: K, signature_r: sig0, signature_s: sig1)` before performing a privileged action (e.g., transferring an allowance, marking a coupon as redeemed, granting a role) — this exactly matches the pattern shown in `account_with_real_validate.cairo`.
2. The key holder for `K` signs one meta-transaction authorizing a single action: computes `meta_tx_hash = compute_meta_tx_v0_hash(contract_address=T, entry_point_selector=EXECUTE_ENTRY_POINT_SELECTOR, calldata=<action data>, chain_id=CHAIN_ID)` off-chain and produces `(sig0, sig1)` over that hash.
3. Any account submits an `INVOKE` transaction that calls a wrapper contract's `meta_tx_v0_syscall(address=T, entry_point_selector=EXECUTE_ENTRY_POINT_SELECTOR, calldata=<action data>, signature=[sig0, sig1])`, per the syscall path exercised in `crates/blockifier/src/execution/syscalls/syscall_tests/meta_tx.rs`.
4. `T.__execute__` verifies the signature against `tx_info.transaction_hash == meta_tx_hash` successfully and performs the privileged action.
5. Any actor (the original caller, an observer who copies the calldata from the first transaction, or the account itself) submits another, independent `INVOKE` transaction repeating step 3 with the identical `(calldata, signature)`. Because `meta_tx_hash` and the signature are unchanged (no nonce was consumed or hashed), `T.__execute__` verifies successfully again and re-performs the privileged action — demonstrating unauthorized replay of what was intended to be a single authorized action.
