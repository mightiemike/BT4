### Title
Per-transaction O(n) clone of the block-cumulative executed-class-hash set in `Bouncer::try_update` causes quadratic blowup in block building - ([File: crates/blockifier/src/bouncer.rs])

### Summary
`Bouncer::try_update`, called once per candidate transaction while building a block, computes the marginal set of newly-executed class hashes by cloning the *entire* cumulative set of class hashes executed so far in the block via `get_executed_class_hashes()`. Because this cumulative set grows with every transaction that touches a previously-unseen class, and the clone/collect happens on every subsequent transaction, the total cost of building a block is quadratic in the number of distinct classes touched, rather than linear as the surrounding code explicitly intends.

### Finding Description
`Bouncer::get_executed_class_hashes` reconstructs a fresh `HashSet<ClassHash>` by cloning every key currently stored in the block-wide accumulated CASM-hash-computation map: [1](#0-0) 

This function is invoked inside `try_update`, which runs once for every transaction the sequencer attempts to add to the block: [2](#0-1) 

The comment directly above this code states the intended invariant explicitly: "The countings here should be linear in the transactional state changes and execution info rather than the cumulative state attributes." [3](#0-2)  Yet `marginal_executed_class_hashes` is computed against `self.get_executed_class_hashes()`, which is derived from the *cumulative* `accumulated_weights.casm_hash_computation_data_sierra_gas` map — i.e., it clones and rebuilds a set whose size is the total number of distinct classes executed in the block so far, on every single transaction.

This is inconsistent with the pattern used for the analogous `visited_storage_entries` field a few lines later, which is stored directly as a `HashSet` on the `Bouncer` struct and is diffed without cloning the whole cumulative side (the `HashSet::difference` call there iterates only over the smaller, per-tx side): [4](#0-3) 

`executed_class_hashes`, by contrast, is not tracked incrementally as its own field but is recomputed from the accumulated CASM-hash-computation map on every call, which forces an O(cumulative-size) clone each time.

An unprivileged transaction sender fully controls this cost: by submitting many transactions in a block that each touch a distinct, previously-unseen class hash (e.g., invoking many different already-declared contracts, or triggering execution of many distinct declared classes), the sender causes the accumulated map's size `n` to grow linearly with the number of such transactions. Since `get_executed_class_hashes()` is called on every transaction attempt (including transactions ultimately rejected for block-fullness, per the `try_update`/`BlockFull` path), the cumulative work across the whole block becomes O(n²) instead of O(n).

### Impact Explanation
This does not cause loss of funds or state corruption, but it does directly parallel the reported bug class: an adversary-controlled, ever-growing collection is redundantly iterated/cloned on every subsequent operation, degrading performance as a function of the square of the input size. In a sequencer under block-time constraints, an attacker able to fill a block with many transactions touching distinct classes can materially slow down block building (proposer/sequencer node), pushing block-production time toward or past the block deadline. Depending on how severe the slowdown becomes relative to the sequencer's block-time budget, this can manifest as missed/delayed blocks — a performance-based denial-of-service on the block-building path, which is the same failure mode (unbounded/growing loop cost triggerable by an ordinary caller) as the referenced Vault report, just realized as algorithmic-complexity degradation rather than an outright gas-limit revert.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker (or organic block composition) to include a large number of transactions in a single block that each touch previously-unseen class hashes, which is achievable since transaction senders freely choose which contracts/classes to invoke and there is no bound on the *number of distinct classes* touched within a block (only per-transaction resource bounds and an overall `n_txs`/gas cap exist). The larger the configured block capacity (`n_txs`, `sierra_gas`, `proving_gas` limits), the more pronounced the quadratic effect becomes.

### Recommendation
Track `executed_class_hashes` as an incrementally-maintained `HashSet<ClassHash>` field on `Bouncer` (analogous to `visited_storage_entries`), updated via `extend` in `Bouncer::update`, instead of deriving it by cloning all keys out of `accumulated_weights.casm_hash_computation_data_sierra_gas` on every `try_update` call. This restores the linear-per-transaction cost that the surrounding comment already declares as the intended design.

### Proof of Concept
1. Deploy/declare `N` distinct contract classes (each with a unique class hash) ahead of time.
2. In a single block-building pass, submit `N` invoke transactions, each targeting a different one of the `N` classes so that each transaction introduces a new key into `accumulated_weights.casm_hash_computation_data_sierra_gas`.
3. Each call to `bouncer.try_update` for transaction `i` triggers `get_executed_class_hashes()`, which clones a set of size `O(i)` (the classes touched by all prior transactions in the block).
4. Total cost across the block is `Σ_{i=1}^{N} O(i) = O(N²)`, versus the intended `O(N)` behavior described in the code comment at [3](#0-2) , demonstrating the quadratic blowup an unprivileged transaction sender can trigger purely by choosing which classes their transactions touch.
