### Title
Deposits removed from mempool unconditionally on block success, even if their `BridgeContract::depositCall` system tx reverted - (File: crates/sequencer/src/runner.rs)

### Summary
`produce_l2_block_inner` fetches deposit blobs via `fetch_deposits` (which does not remove them) and unconditionally calls `remove_deposits` on the entire fetched `deposit_data` set once the L2 block is saved, without checking the per-transaction receipt status of the corresponding system deposit calls. If a deposit's `depositCall` reverts during actual execution (e.g., `verifyInclusion` fails because the light client hasn't caught up to the referenced Bitcoin block, despite an earlier `eth_call` simulation succeeding), that deposit is permanently evicted from `pending_deposits` with no path back in.

### Finding Description
The binding that should hold: for every deposit blob `d` with `txid = calc_tx_id(d)`, `d` is removed from `pending_deposits`/`accepted_deposit_txs` **if and only if** its system deposit call executed successfully (i.e., produced a successful receipt crediting cBTC). Before block production and after, this binding must still hold — a deposit blob should remain re-submittable until it actually succeeds.

Tracing the code:
- `fetch_deposits` [1](#0-0)  only reads `accepted_deposit_txs`, it does not remove or mark them, by design (confirmed by `test_fetch_deposits_does_not_remove` [2](#0-1) ).
- In `produce_l2_block_inner`, `deposit_data` is fetched [3](#0-2) , passed into `dry_run_transactions` [4](#0-3) , and the actual block is applied via `instrumented_apply_l2_block_txs` [5](#0-4) , producing `receipts` [6](#0-5) .
- After the block is saved, `remove_deposits` is invoked solely gated on `!deposit_data.is_empty()` — **not** on whether the corresponding system-tx receipts indicate success: [7](#0-6) .
- `remove_deposits` itself simply computes `calc_tx_id` for every blob in the passed set and removes matching entries from both `accepted_deposit_txs` and `pending_deposits` [8](#0-7) . It has no concept of execution success/failure — it only operates on the blob set it's given.
- Once removed from `pending_deposits`, the guard in `add_deposit_tx` (`self.pending_deposits.insert(txid.to_vec())`) allows the exact same blob to be inserted again [9](#0-8) , so in principle re-submission is only blocked as long as the depositor manages to resubmit — but nothing in the visible mempool/runner code re-queues a failed deposit automatically, and there is no signal fed back from `receipts` to the mempool identifying which deposits failed.

There is no per-tx check anywhere in the traced code between "system tx receipt status" and "removal from `pending_deposits`". A revert of a Solidity call (as opposed to a protocol-level panic on malformed system-tx encoding) produces a failed EVM receipt but does not abort STF execution, so block production completes normally and `remove_deposits` runs over the full fetched set regardless of individual outcomes.

I was not able to fully verify within the available tool budget whether `hooks.rs`/`apply_l2_block_txs` treats a reverted `depositCall` as a normal failed-receipt EVM transaction (supporting the claim) versus causing a hard panic/abort that would prevent block finalization entirely (which would contradict the claim, since `remove_deposits` would never be reached). Grepping `crates/evm/src/hooks.rs` showed deposit/system-tx handling present but I did not confirm the exact control flow for revert vs. panic paths before running out of iterations. This is the primary remaining uncertainty.

### Impact Explanation
If the revert-not-panic assumption holds, a legitimate depositor whose Bitcoin move-to-vault transaction is real and correctly presigned by Clementine can have their deposit blob permanently evicted from the sequencer's mempool due to a timing race with light-client state, with no automatic retry mechanism visible in this code path. That is a permanent freeze of legitimate cBTC issuance for that depositor — matching the Critical "funds permanently frozen" category. The blast radius is scoped to individual deposits hitting this specific race, not systemic, but each occurrence is a permanent, unrecoverable loss of mint eligibility unless the depositor (or an operator) notices and manually re-submits via `citrea_sendRawDepositTransaction` before base-layer state changes make it invalid again.

### Likelihood Explanation
This requires a race between the light client's view at `eth_call` simulation time (`BlockId::pending()`) and its view at actual dry-run/execution time for a later L2 height — a naturally occurring condition when Bitcoin blocks are being processed asynchronously relative to L2 block production, not an artificial one the attacker needs to engineer via privileged access. It costs the attacker (or an honest but unlucky depositor) nothing extra beyond a normal deposit attempt and standard Bitcoin fees; the "attack" is really just a legitimate depositor being unlucky with timing, or an adversary trying to submit deposits right as light client state transitions to increase odds of the race per the question's framing. It is repeatable per deposit blob, bounded by how often such races occur.

### Recommendation
Only call `remove_deposits` for deposits whose corresponding system-tx receipt in `receipts` indicates success; retain (do not evict from `pending_deposits`) any deposit whose `depositCall` execution reverted so it can be retried in a subsequent block once the light client has caught up. This requires correlating each entry in `deposit_data` with its corresponding receipt in `receipts` (e.g., via transaction index or committed tx hash) at [7](#0-6)  before calling `remove_deposits`.

    // receipt for `deposit`'s system tx was a revert, and add_deposit_tx(deposit)

    pub fn remove_deposits(&mut self, deposits_to_remove: &[Deposit]) -> usize {
        let mut removed_count = 0;

        // Calculate txids for the deposits to remove
        let mut txids_to_remove = HashSet::new();
        for deposit in deposits_to_remove {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            txids_to_remove.insert(txid.to_vec());
        }

        // Retain only deposits that are not in the removal set
        self.accepted_deposit_txs.retain(|deposit| {
            let txid = Self::calc_tx_id(deposit)
                .expect("calc_tx_id should never be called on non-deposit");
            if txids_to_remove.contains(txid.as_slice()) {
                // Remove from pending set
                self.pending_deposits.remove(txid.as_slice());
                removed_count += 1;
                return false;
            }
            true
        });

        // Update metrics
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        debug!("Removed {} deposits from mempool", removed_count);
        removed_count
    }

    pub fn add_deposit_tx(&mut self, req: Deposit) -> anyhow::Result<bool> {
        let txid = Self::calc_tx_id(&req)?;

        debug!("Adding deposit with tx: {}", hex::encode(txid));

        // Check if deposit is already pending
        if !self.pending_deposits.insert(txid.to_vec()) {
            tracing::debug!("Deposit already pending in mempool");
            return Ok(false);
        }

        self.accepted_deposit_txs.push_back(req);
        SM.deposit_data_mempool_txs_inc.increment(1);
        SM.deposit_data_mempool_txs
            .set(self.accepted_deposit_txs.len() as f64);

        Ok(true)
    }

    #[test]
    fn test_fetch_deposits_does_not_remove() {
        let mut mempool = DepositDataMempool::new();
        let deposit1 = hex::decode(DEPOSIT1).unwrap();
        let deposit2 = hex::decode(DEPOSIT2).unwrap();
        let deposit3 = hex::decode(DEPOSIT3).unwrap();

        // Add deposits
        assert!(mempool.add_deposit_tx(deposit1.clone()).unwrap());
        assert!(mempool.add_deposit_tx(deposit2.clone()).unwrap());
        assert!(mempool.add_deposit_tx(deposit3.clone()).unwrap());
        assert_eq!(mempool.pending_deposits.len(), 3);
        assert_eq!(mempool.accepted_deposit_txs.len(), 3);

        // Fetch 2 deposits
        let fetched = mempool.fetch_deposits(2);
        assert_eq!(fetched.len(), 2);
        assert_eq!(fetched[0], deposit1);
        assert_eq!(fetched[1], deposit2);

        // Check that fetched deposits are NOT removed
        assert_eq!(mempool.pending_deposits.len(), 3);
        assert_eq!(mempool.accepted_deposit_txs.len(), 3);

        // Cannot add same deposits again as they're still pending
        assert!(!mempool.add_deposit_tx(deposit1.clone()).unwrap());
        assert!(!mempool.add_deposit_tx(deposit2.clone()).unwrap());

        // Fetch again should return the same deposits
        let fetched_again = mempool.fetch_deposits(2);
        assert_eq!(fetched_again.len(), 2);
        assert_eq!(fetched_again[0], deposit1);
        assert_eq!(fetched_again[1], deposit2);
    }
