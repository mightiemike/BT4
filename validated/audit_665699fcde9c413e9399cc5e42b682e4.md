### Title
Unauthenticated `citrea_haltCommitments` / `citrea_resumeCommitments` RPC methods bypass the `Auth` middleware and let anyone stop sequencer commitment production - (File: `crates/common/src/rpc/auth.rs`)

### Summary
The sequencer exposes `citrea_haltCommitments` and `citrea_resumeCommitments` on the same public JSON-RPC port as all other unauthenticated methods (`eth_*`, etc.), yet these two methods toggle a control-plane flag that stops/resumes the `CommitmentService` from submitting sequencer commitments to the DA layer. The node's `Auth` RPC middleware only requires an API key for three explicitly listed methods and passes every other method through untouched, so these state-mutating operator controls are reachable by any network caller with no authentication whatsoever.

### Finding Description
The RPC server wraps all registered methods with the `Auth` middleware, but that middleware's allow-list of protected methods is hardcoded to backup-related calls only: [1](#0-0) 

Every other method, including `citrea_haltCommitments` and `citrea_resumeCommitments`, falls into the `if !PROTECTED_METHODS.contains(&method)` branch and is forwarded to the underlying service with no credential check at all: [2](#0-1) 

The handlers simply forward a message to the sequencer runner over an internal channel: [3](#0-2) 

which the runner loop consumes to flip the halt flag on the commitment service without any further authorization check: [4](#0-3) 

The `CommitmentService` itself simply stops calling `self.commit(...)` on the "should_run" toggle: [5](#0-4) 

This mirrors the report's bug class exactly: a state-mutating operation that should require privileged/authenticated access (analogous to a `USER OPERATION` in the CoinMate report) is served to unauthenticated callers because the authentication gate is an incomplete allow-list rather than a default-deny policy. The `Auth` middleware is the correct mechanism to enforce this (it already exists for `backup_create`/`backup_validate`/`backup_info`), but `citrea_haltCommitments`/`citrea_resumeCommitments` were never added to `PROTECTED_METHODS`.

### Impact Explanation
Anyone with network access to the sequencer's RPC endpoint can call `citrea_haltCommitments` to indefinitely stop the sequencer from submitting new commitments to L1, and later cannot be forced to resume unless the true operator issues `citrea_resumeCommitments`. Since sequencer commitments are the binding that lets provers/full nodes discover and prove new L2 state, an attacker can unilaterally suspend the rollup's L1 commitment pipeline without holding the sequencer's signing key or any credential — breaking the authority boundary that commitment control is supposed to be restricted to the sequencer operator (an "unauthenticated JSON-RPC call that mutates node state or bypasses `Auth`").

### Likelihood Explanation
The sequencer's JSON-RPC endpoint is the same publicly served port used for standard `eth_*` calls (registered into the same `RpcModule` passed to `start_rpc_server`, wrapped by the single `Auth` layer), so no special network position or credentials are required — a single unauthenticated JSON-RPC POST is sufficient. The only "protection" — the hardcoded `PROTECTED_METHODS` allow-list — omits these methods entirely, so the bug triggers on every call, not intermittently.

### Recommendation
Add `citrea_haltCommitments` and `citrea_resumeCommitments` (and audit for any other operator/control-plane RPC methods) to `PROTECTED_METHODS` in `crates/common/src/rpc/auth.rs`, or switch the `Auth` middleware to a default-deny/allow-list-for-public-methods model instead of a deny-list for protected ones, so newly added privileged methods are secure by default.

### Proof of Concept
1. Start a sequencer node with the standard configuration (RPC bound and reachable, `api_key` optionally set or unset).
2. As an unauthenticated remote client, send:
```json
{"jsonrpc":"2.0","id":1,"method":"citrea_haltCommitments","params":[]}
```
3. Observe (as in the existing test `test_sequencer_halt_resume_commitments`) that no new commitments are published to the DA layer, confirming the call succeeded without any credential: [6](#0-5) 
4. No `api_key` parameter or header was supplied, unlike the required flow for `backup_create`/`backup_validate`/`backup_info`, which reject unauthenticated calls with a 401 error.
