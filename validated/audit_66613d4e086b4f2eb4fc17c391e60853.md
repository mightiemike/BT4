### Title
Sandwich attack on native bancor-style Exchange trades allows value extraction due to reserve-only slippage check - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
java-tron's on-chain TRC10 `Exchange` (a bancor-formula AMM) is traded via `ExchangeTransactionContract`/`ExchangeTransactionActuator`. The only manipulation protection is a slippage floor (`tokenExpected`) computed against the exchange's current reserve balances at validation time. Because block producers order transactions and any account can broadcast `ExchangeTransactionContract`, an attacker can sandwich a victim's trade by moving the pool reserves immediately before the victim's transaction and reverting them immediately after, extracting value from the victim while still satisfying the victim's minimum-output check — mirroring the reported AMM sandwich pattern where a liquidity/price check against a shared, freely-mutable pool state is validated but not protected from adversarial reordering.

### Finding Description
`ExchangeTransactionActuator.doValidate()` reads the exchange's current reserves and computes the expected output purely from that instantaneous state: [1](#0-0) 

The relevant checks are: [2](#0-1) 

The actual AMM math is done in `ExchangeCapsule.transaction()`, which mutates `firstTokenBalance`/`secondTokenBalance` in place based on the bancor relay-token formula, with no other protection against reserve manipulation between transactions: [3](#0-2) 

The only "safety" check enforced is `tokenExpected`, a pure slippage floor: [4](#0-3) 

Because any account can submit an `ExchangeTransactionContract` and transaction ordering within a block is controlled by whoever assembles/orders transactions (including MEV-aware relayers or SRs), an attacker can:
1. Front-run the victim's trade with a large trade on the same exchange ID/tokenID to shift `firstTokenBalance`/`secondTokenBalance` unfavorably against the victim.
2. Let the victim's trade execute at the worse price (which still clears the victim's `tokenExpected` floor if that floor was set loosely, or forces the victim to fail with `"token required must greater than expected"` if set tightly — a DoS on that specific trade).
3. Back-run with an opposite trade to restore the pool and capture the price difference as profit, exactly the classic AMM sandwich pattern referenced in the source report ("liquidity/price validated against current pool state, which is freely mutable by unprivileged third parties via front-run/back-run transactions").

This is structurally identical to the reported root cause: a market/liquidity validation (`validateVariablePoolHasEnoughLiquidity` in the report vs. the `tokenExpected` reserve check here) is performed against a shared, externally-mutable balance instead of against a value that is locked/reserved for the specific transaction, leaving normal users exposed to sandwiching by any unprivileged party who can submit transactions.

### Impact Explanation
Any TRC10 holder or TRX holder trading through the native `Exchange` can have value extracted from their trade by an unprivileged attacker who only needs to submit two ordinary `ExchangeTransactionContract` transactions around the victim's transaction. This is an exchange/market math accounting issue reachable from anonymous broadcast transactions with no elevated privilege, and it can also be used to grief victims into reverted trades (wasted fee/bandwidth) by pushing the price outside their configured `tokenExpected` floor.

### Likelihood Explanation
Likelihood is high: the `Exchange` feature is a native, permissionless AMM; any account can submit trades of arbitrary size limited only by `getExchangeBalanceLimit()`, and transaction ordering around a victim's pending trade is not otherwise constrained at the protocol layer.

### Recommendation
Since fully preventing reordering/sandwiching on-chain is not generally possible (as acknowledged in the referenced report for Uniswap-style AMMs), the mitigation is to ensure the slippage protection (`tokenExpected`) is the primary, clearly documented safeguard for users, and to consider adding trade-size-relative price-impact limits or minimum time/last-price deviation guards on `ExchangeTransactionActuator`/`ExchangeCapsule.transaction()` so a single trade cannot move reserves beyond a bounded percentage, reducing the profitability of sandwiching the native `Exchange`.

### Proof of Concept
1. Attacker observes a pending `ExchangeTransactionContract` from a victim specifying `exchangeId`, `tokenId`, `quant`, and `expected` (a loose slippage floor).
2. Attacker submits a large `ExchangeTransactionContract` trade on the same `exchangeId` in the opposite direction just before the victim's transaction is packed, shifting `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()` at `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:124-169`.
3. Victim's trade executes at `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java:64-99`, receiving a worse `anotherTokenQuant` that still satisfies `tokenExpected` (or fails with `"token required must greater than expected"` at line 220 if the floor is tight, causing wasted fee/DoS on that trade).
4. Attacker submits a reverse trade right after to restore reserves and capture the spread as profit.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
