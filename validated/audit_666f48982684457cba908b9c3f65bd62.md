### Title
Wallet Contract trusts non-standard NEP-141 token promise success without validating actual transfer outcome, causing caller deposit loss - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Near Wallet Contract's ERC-20 emulation path determines whether an emulated `ft_transfer` succeeded purely from the cross-contract call's `PromiseResult` (`Successful`/`Failed`), never inspecting whether the token actually moved. A non-standard NEP-141 implementation that returns normally (does not panic) even when it silently fails to transfer tokens will be reported as a success by the Wallet Contract, and per its own refund logic the caller's attached NEAR deposit will *not* be refunded because the call is classified as successful. This is the direct structural analog of the reported USDT issue, where a non-standard ERC20 that doesn't revert/return the expected success signal fools downstream logic that assumes standard-compliant token behavior.

### Finding Description
`inner_rlp_execute` handles `EthEmulationKind::ERC20Transfer` by chaining a `storage_balance_of` check to `nep_141_storage_balance_callback`, which in turn schedules the `ft_transfer` (or `storage_deposit` + `ft_transfer`) call and chains it to `rlp_execute_callback`: [1](#0-0) 

`rlp_execute_callback` decides success solely from the promise result, without checking whether the token contract's return value actually indicates that funds moved: [2](#0-1) 

The NEP-141 standard requires a compliant `ft_transfer` implementation to panic on failure (insufficient balance, etc.), so a `PromiseResult::Successful` is normally a reliable signal. But nothing in the Wallet Contract enforces or verifies that the `target` account is a standards-compliant NEP-141 contract — `target` is attacker/relayer-controlled input to `rlp_execute`. A non-standard or malicious FT contract can implement `ft_transfer` to return normally (e.g. return `false`/no-op) instead of panicking when the transfer cannot be completed, exactly mirroring USDT's non-standard `transferFrom` behavior that doesn't produce the expected failure signal relied upon by calling code.

Combined with the caller-deposit accounting, this creates a fund-loss condition. `CallerDeposit` is constructed to track the yoctoNEAR an external, non-self caller attaches to `rlp_execute`, and is only refunded on `PromiseResult::Failed`: [3](#0-2) 

The project's own test explicitly documents that once a call is classified as successful, the caller's deposit is *not* refunded ("External caller does not get a refund when their tokens are spent"): [4](#0-3) 

So, if `target` in a `rlp_execute` call is set to a non-standard NEP-141 contract that returns success without moving tokens, the Wallet Contract will (a) report `ExecuteResponse{success:true}` even though the emulated ERC-20 transfer never happened, and (b) permanently keep the caller's attached NEAR deposit instead of refunding it, because the failure path is only reached on an actual promise `Failed`.

### Impact Explanation
An external caller (any account, not necessarily the wallet owner) invoking `rlp_execute` and attaching a NEAR deposit to cover an emulated ERC-20 transfer's relayer fee/gas can have that deposit permanently and unrecoverably consumed by the Wallet Contract while the underlying token transfer silently fails, since no refund path exists for a "successful-looking" promise that did not actually move funds. Users/relayers relying on `ExecuteResponse.success` to confirm that the intended ERC-20 transfer executed will be misled, and any application logic gating further on-chain/off-chain actions on that success flag (e.g. releasing goods, settling a trade) can be exploited by pointing the wallet at an attacker-deployed non-standard token. This is a direct unauthorized loss of the caller's deposited value combined with an invalid state-transition acceptance (a failed transfer accepted/reported as successful).

### Likelihood Explanation
Reachable via a single, ordinary `rlp_execute` function call from any account (transaction signer or relayer with a function-call access key) — no privileged access required. The attacker only needs to control or point `target` at a non-standard NEP-141 contract, which is entirely within an unprivileged caller's ability to deploy and specify.

### Recommendation
Do not treat `PromiseResult::Successful` alone as proof that an emulated ERC-20/NEP-141 transfer succeeded. Either (a) require an explicit balance check before/after the transfer (e.g. via `ft_balance_of`) to confirm the expected delta occurred before finalizing `ExecuteResponse.success` and releasing/keeping the caller deposit, or (b) maintain an allow-list of vetted NEP-141 token contracts usable in ERC-20 emulation, and refuse the caller-deposit consumption path for unverified tokens.

### Proof of Concept
1. Deploy a NEP-141-like contract `evil_token` whose `ft_transfer` method returns normally (no panic) but does not actually adjust balances (i.e., a no-op "always succeeds" transfer).
2. As any external account, call the Wallet Contract's `rlp_execute` with an RLP-encoded ERC-20 `transfer` transaction targeting `evil_token`, attaching a NEAR deposit (`attached_deposit`) intended to cover the relayer fee, per `CallerDeposit::new`.
3. Observe the flow: `nep_141_storage_balance_callback` schedules the `ft_transfer` call on `evil_token`; that call resolves as `PromiseResult::Successful`; `rlp_execute_callback` returns `ExecuteResponse{success:true}`.
4. Verify via `ft_balance_of` that no tokens actually moved on `evil_token`.
5. Verify that the caller's attached NEAR deposit was not refunded (as demonstrated by the existing `test_caller_refunds` test's "successful" branch), confirming the deposit is permanently lost despite the underlying transfer not occurring.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
