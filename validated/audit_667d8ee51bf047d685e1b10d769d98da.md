### Title
Meta-Transaction `SignedDelegateAction` Front-Running Allows Nonce Griefing of Relayers — (`File: runtime/runtime/src/actions.rs`)

---

### Summary

The nearcore meta-transaction system (NEP-366) allows any unprivileged account to wrap and submit a `SignedDelegateAction` that was created by a user for a specific relayer. Because `apply_delegate_action` places no restriction on who the outer-transaction signer is, an attacker who observes a pending meta-transaction in the mempool can extract the `SignedDelegateAction`, wrap it in their own outer transaction, and submit it first. This consumes the user's access-key nonce, causing the original relayer's transaction to fail with `DelegateActionInvalidNonce`. The attack is a direct nearcore-runtime analog of the EIP-2612 permit front-running class.

---

### Finding Description

**Structural parallel to the seed report**

EIP-2612 `permit()` is a user-signed off-chain authorization that any caller can submit on-chain. The vulnerability arises when a function calls `permit()` unconditionally: an attacker can extract the signature from the mempool and call `permit()` directly first, consuming the nonce and causing the original caller's transaction to revert.

In nearcore, `SignedDelegateAction` is the exact structural analog:

- A user (Alice) creates and signs a `DelegateAction` off-chain and hands it to a relayer.
- The relayer wraps it in an outer `SignedTransaction` and submits it.
- The `SignedDelegateAction` is fully self-contained and cryptographically valid regardless of who submits the outer transaction.
- `apply_delegate_action` does **not** check that the outer transaction's signer is any particular relayer. [1](#0-0) 

**The vulnerable execution path**

`apply_delegate_action` in `runtime/runtime/src/actions.rs` performs these checks in order:

1. Signature validity (`signed_delegate_action.verify()`)
2. Expiry (`block_height > max_block_height`)
3. Sender match (`delegate_action.sender_id == account_id` of the outer receipt's receiver)
4. Nonce validity and **nonce write** via `validate_delegate_action_key` [2](#0-1) 

None of these checks restrict which account may be the outer-transaction signer. The nonce is written to state unconditionally on success: [3](#0-2) 

**Attack steps**

1. Alice signs a `DelegateAction` (nonce = N, `max_block_height` = H) and sends it off-chain to relayer R.
2. R wraps it in `SignedTransaction { signer=R, receiver=alice, actions=[Delegate(signed_delegate_action)] }` and submits it.
3. Attacker observes the pending transaction (via RPC, validator node, or sequencer access) and extracts the `SignedDelegateAction`.
4. Attacker creates `SignedTransaction { signer=attacker, receiver=alice, actions=[Delegate(same_signed_delegate_action)] }` and submits it with equal or higher priority.
5. Attacker's transaction executes first on Alice's shard: nonce N is consumed, inner actions execute.
6. R's transaction arrives: `validate_delegate_action_key` finds `delegate_nonce (N) <= current_nonce (N)` and returns `DelegateActionInvalidNonce`. [4](#0-3) 

The failed receipt triggers `state_update.rollback()`, but the nonce write from step 5 is already committed and cannot be undone. [5](#0-4) 

**No existing guard**

The nearcore documentation explicitly acknowledges that the `SignedDelegateAction` is self-contained and that any account can act as a relayer: [6](#0-5) 

There is no `relayer_id` field in `DelegateAction`, no allowlist check in `apply_delegate_action`, and no protocol-level mechanism to bind a `SignedDelegateAction` to a specific submitter.

---

### Impact Explanation

- **Relayer gas loss**: The original relayer's outer transaction fails; the relayer burns gas with no receipt produced and no compensation.
- **Service disruption**: An attacker can systematically front-run every meta-transaction submitted by a target relayer, making the relayer's service non-functional.
- **Compounded attack**: If the attacker additionally drains Alice's fungible-token balance before submitting the `SignedDelegateAction`, the inner actions fail too. Alice's nonce N is permanently consumed; she must sign a new `DelegateAction` with nonce > N. This is a long-term DoS on Alice's meta-transaction capability with no fallback path (unlike the EIP-2612 case where a direct `approve()` exists).
- **Attacker cost**: The attacker pays gas for the outer transaction and the inner actions. This is a griefing attack with no financial gain for the attacker.

This matches the allowed impact: **denial of service that is not network-level and could be fixed without a hardfork**.

---

### Likelihood Explanation

- **Trigger**: Any account with NEAR tokens sufficient to pay gas can perform this attack. No privileged role is required.
- **Observability**: NEAR transactions are forwarded to validators via the P2P network and are queryable via the JSON-RPC `broadcast_tx_async` / `tx` endpoints before finalization. A validator node or an RPC-connected attacker can observe pending transactions.
- **Repeatability**: The attack can be automated to target every meta-transaction from a specific relayer, making it a sustained DoS.
- **Window**: Bounded by `max_block_height` in the `DelegateAction`, but the attacker only needs to act within the same block or a few blocks.

---

### Recommendation

Add a `relayer_id: Option<AccountId>` field to `DelegateAction` (covered by the existing NEP-461 signature). In `apply_delegate_action`, if `relayer_id` is `Some(id)`, verify that the outer receipt's `signer_id` (the relayer) equals `id` before proceeding. This binds the `SignedDelegateAction` to a specific submitter, eliminating the front-running surface without breaking backward compatibility (existing `DelegateAction`s with `relayer_id = None` retain current behavior).

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }

**File:** docs/architecture/how/meta-tx.md (L40-52)
```markdown
With meta transactions, Alice can create a `DelegateAction`, which is very
similar to a transaction. It also contains a list of actions to execute and a
single receiver for those actions. She signs the `DelegateAction` and forwards
it (off-chain) to a relayer. The relayer wraps it in a transaction, of which the
relayer is the signer and therefore pays the gas costs. If the inner actions
have an attached token balance, this is also paid for by the relayer.

On chain, the `SignedDelegateAction` inside the transaction is converted to an
action receipt with the same `SignedDelegateAction` on the relayer's shard. The
receipt is forwarded to the account from `Alice`, which will unpacked the
`SignedDelegateAction` and verify that it is signed by Alice with a valid Nonce
etc. If all checks are successful, a new action receipt with the inner actions
as body is sent to `FT`. There, the `ft_transfer` call finally executes.
```
