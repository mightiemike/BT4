Based on my research, I found a genuine analog in nearcore's `DeleteAccount` action handling that mirrors the "reference to external state that can vanish, causing irrecoverable loss of value" pattern from the Sherlock report.

### Title
DeleteAccount refund to a nonexistent/vanished beneficiary permanently burns account funds instead of returning them - (File: runtime/runtime/src/actions.rs)

### Summary
`action_delete_account` unconditionally creates a balance-refund receipt to the caller-supplied `beneficiary_id` without ever validating that this account currently exists or will still exist by the time the refund receipt lands (potentially on another shard). If the beneficiary account does not exist, the refund receipt fails validation and, being a system-predecessor ("refund") receipt, is not allowed to implicitly create the account — the deposit is silently burned instead of being credited anywhere, exactly like the audited contract's `_restoreLiquidity` blindly trusting an NFT `tokenId` reference that the counterparty can destroy.

### Finding Description
`action_delete_account` reads the account's current balance and pushes an unconditional `Receipt::new_balance_refund` to `delete_account.beneficiary_id`, with no check that this account exists: [1](#0-0) 

The only pre-execution validation on `DeleteAccountAction.beneficiary_id` is that it is a syntactically valid account id — there is no existence check, as documented: [2](#0-1) 

When the resulting refund receipt is later processed (possibly on a different shard, after cross-shard latency), `check_account_existence` is invoked for the `Transfer` action embedded in the refund. Because it's a refund receipt, `implicit_creation_allowed` explicitly disallows creating the destination account: [3](#0-2) [4](#0-3) 

So if `beneficiary_id` does not exist at the time the refund is applied — whether it never existed, was never created, or was concurrently deleted by its own owner between the time the `DeleteAccount` action executes and the time the refund receipt is delivered — the refund action fails with `AccountDoesNotExist`. Per the documented apply-loop behavior, a failed refund receipt does not retry or reroute funds: it burns its deposit into `other_burnt_amount` instead of returning it to anyone: [5](#0-4) [6](#0-5) 

This is structurally identical to the audited bug class: a settlement/repayment path (`DeleteAccount`'s beneficiary payout) is built on an unchecked reference (`beneficiary_id` existence) to external mutable state that a party (the beneficiary itself, or simply an unlucky timing window) can invalidate, and when that happens, the funds are neither delivered nor returned to the original owner — they are irrecoverably destroyed.

### Impact Explanation
Any account holder submitting a single `DeleteAccountAction` transaction with a `beneficiary_id` that does not exist by refund-delivery time causes their own remaining balance to be permanently burned rather than transferred or returned. Because there is no existence check at submission time and the refund crosses shards asynchronously, this is a race an ordinary user can trigger unintentionally (or a malicious relayer/meta-transaction sender could steer a victim into) — the affected account's balance is unrecoverably destroyed, matching the "permanently frozen/destroyed funds" impact category.

### Likelihood Explanation
Reachable directly by any unprivileged transaction signer via a plain `DeleteAccountAction` (or via a `Delegate`/meta-transaction wrapping it) — no validator or node compromise required. The only precondition is a `beneficiary_id` that is absent or gets deleted before the cross-shard refund receipt executes, which is plausible in practice (mistyped id, or the beneficiary account being deleted independently in the same time window).

### Recommendation
Validate `beneficiary_id` existence before allowing `DeleteAccount` to proceed (fail the action instead of deferring to an unrecoverable refund), or make refund receipts capable of returning to the deleting account / a fallback treasury instead of unconditionally burning on failure.

### Proof of Concept
1. Create account `victim.near` with balance and account `ghost.near`.
2. Delete `ghost.near` (or simply reference an id that was never created) in the same or an adjacent block.
3. `victim.near` submits `DeleteAccountAction { beneficiary_id: ghost.near }`.
4. `action_delete_account` unconditionally emits `Receipt::new_balance_refund(ghost.near, balance)` [7](#0-6) .
5. When this refund receipt executes, `check_account_existence` rejects it (`AccountDoesNotExist`) because `ghost.near` doesn't exist and refunds cannot implicitly create accounts [3](#0-2) .
6. Per the documented apply loop, the failed refund's deposit is burned into `other_burnt_amount` rather than returned to `victim.near` [5](#0-4)  — `victim.near`'s funds are permanently lost.
