### Title
Poison-microblock validation accepts two headers that differ only by ECDSA signature malleation, not by actual conflicting content, causing wrongful "equivocation" poison reports and reward mis-payment - (File: `stackslib/src/chainstate/stacks/db/transactions.rs`)

### Summary
`check_microblock_header_signer` and the transaction-admission check in `blocks.rs` only verify that both poison-microblock headers recover to the *same* signer public key hash; they never verify that the headers actually encode *different signed content* (i.e., a genuine `tx_merkle_root` fork). Combined with `check_recover_pubkey` hashing the header with the signature field zeroed out and using `recover_to_pubkey_without_validating_low_s` (no low-S enforcement), an attacker can take a single, legitimately-published microblock header and its signature, apply pure ECDSA signature malleation (negate `s`, flip the recovery bit — computable without the private key), and submit the original header plus the malleated copy as `mblock_header_1`/`mblock_header_2`. Both recover to the identical pubkey hash and pass every existing structural check, even though only one signing act by the miner ever occurred.

### Finding Description
The broken equality is:
`poison_report_valid == two_distinct_valid_signing_acts_by_the_miner_at_conflicting_content`

In practice the code only enforces:
`poison_report_valid == (pkh(header_1) == pkh(header_2)) && version/sequence/prev_block match`

- `StacksMicroblockHeader::check_recover_pubkey` (stacks-codec/src/transaction.rs:2598-2616) computes the digest over `serialize(&mut bytes, true)` — i.e. with the signature field zeroed — so the digest depends only on `version, sequence, prev_block, tx_merkle_root`, not on the signature bytes themselves. It recovers the key via `StacksPublicKey::recover_to_pubkey_without_validating_low_s` (stacks-common/src/util/secp256k1/native.rs:200-205), which explicitly skips low-S normalization.
- `check_microblock_header_signer` (stackslib/src/chainstate/stacks/db/transactions.rs:686-713) calls `check_recover_pubkey` on both headers and only checks `pkh1 == pkh2`. It never compares `mblock_header_1` and `mblock_header_2` for content differences (e.g. differing `tx_merkle_root`).
- `handle_poison_microblock` (stackslib/src/chainstate/stacks/db/transactions.rs:722-856) calls only `check_microblock_header_signer`, then proceeds straight to recording a poison report and commission based on `mblock_header_1.sequence`, with no further requirement that the two headers represent genuinely distinct signed content.
- The mempool-admission check in `stackslib/src/chainstate/stacks/db/blocks.rs:6844-6868` similarly only checks `version/sequence/prev_block` equality and `pkh1 == pkh2`; it never checks that `tx_merkle_root` differs or that the two header structs (including signature) are non-identical.

Because ECDSA signatures are inherently malleable (for any valid `(r, s)` over a message, `(r, n-s)` with the recovery bit flipped is also valid and recoverable to the same public key, and this transformation requires no knowledge of the private key), an attacker can:
1. Observe any legitimately broadcast, signed `StacksMicroblockHeader` (`header_1`) from any miner.
2. Compute the malleated signature `sig_2 = (r, n-s)` with adjusted recovery id, and construct `header_2` identical to `header_1` in every field except `signature`.
3. Submit `PoisonMicroblock(header_1, header_2)`. Both `check_recover_pubkey` calls hash the same digest (signature is zeroed for hashing) and each recovers to the same key, so `pkh1 == pkh2` trivially holds even though the *content* (`tx_merkle_root`) is identical and no second microblock was ever produced by the miner.

No existing guard (`check_tenure_tx`, `verify_signer_signatures`, VRF/static validators, MARF hashing) is on this path — these guard different subsystems (Nakamoto blocks/signers), not classic microblock poison reports, which rely solely on `check_microblock_header_signer` and the `blocks.rs` mempool admission check, neither of which verifies content divergence between the two headers.

### Impact Explanation
This lets an unprivileged attacker fabricate a "poison" report against any miner who has ever produced a microblock, without that miner ever having signed two conflicting microblocks. `handle_poison_microblock` records the attacker as `reporter_principal` and grants them commission eligibility over the (falsely) slashed miner's block reward, and it marks the miner's microblock public key hash as poisoned for the maturity window. This is a reward-mis-payment / miner-punishment integrity issue bounded to a single miner's commission — matching the "High: poison or reward mis-payment bounded to fees" category. It does not cause a chain split or double global reward payment across the network, but it wrongfully redirects/forfeits a specific miner's commission to an attacker who performed no genuine equivocation detection.

### Likelihood Explanation
- Preconditions: attacker needs only to observe one legitimately broadcast, signed microblock header (public data) from any miner using the classic microblock path (`prev_block`-based, non-Nakamoto tenure). No BTC spend, no stake, no privileged role, and no majority position is required.
- The malleation computation (negate `s` mod curve order `n`, flip recovery id) is standard, cheap, and requires no cryptographic secret.
- Fully repeatable against any miner/microblock header the attacker can observe, at any time within the `MINER_REWARD_MATURITY` window enforced in `handle_poison_microblock` (stackslib/src/chainstate/stacks/db/transactions.rs:770-803).

### Recommendation
- In `check_microblock_header_signer` / `handle_poison_microblock`, additionally require that `mblock_header_1 != mblock_header_2` in a semantically meaningful way — specifically, require `tx_merkle_root` (or the full header sans signature) to differ between the two headers, so the poison proof demonstrates genuinely conflicting signed content rather than merely two byte-different encodings of the same content.
- Enforce low-S signature normalization (use `recover_to_pubkey` instead of `recover_to_pubkey_without_validating_low_s`) wherever poison-microblock headers are validated, closing the malleation vector at the signature-recovery layer as a defense-in-depth measure.
- Apply the same "content must differ" check consistently in the mempool admission path (`stackslib/src/chainstate/stacks/db/blocks.rs:6844-6868`).

### Proof of Concept
Rust integration test plan (in `stackslib/src/chainstate/stacks/db/transactions.rs` test module or similar):
1. Generate a `StacksPrivateKey` for a "miner", build a `StacksMicroblockHeader` (`header_1`) with fixed `version/sequence/prev_block/tx_merkle_root`, and sign it (`header_1.sign(&privk)`).
2. Compute the malleated signature: parse `header_1.signature` into `(r, s, recid)`, compute `s' = n - s`, flip `recid`, and construct `sig_2`.
3. Build `header_2 = header_1.clone()` but with `signature = sig_2`. Assert `header_1 != header_2` (structs differ) while `header_1.tx_merkle_root == header_2.tx_merkle_root` (no actual second microblock content).
4. Call `StacksChainState::check_microblock_header_signer(&header_1, &header_2)` and assert it returns `Ok(pkh)` — i.e., the equality `pkh(header_1) == pkh(header_2)` holds despite there being only one real signing act.
5. Call `handle_poison_microblock(env, invoke_ctx, &header_1, &header_2)` in a test Clarity environment where the miner's pubkey hash height is already registered, and assert it returns `Ok(..)`, recording a poison report/commission for the calling `sender_principal`, even though `header_2` is not an independently-published microblock.
6. Contrast with a negative control: attempt the same with `header_2.tx_merkle_root` unchanged and `header_2` fully byte-identical to `header_1` (including signature) — confirm this is rejected at the wire/codec layer (`consensus_deserialize`'s "microblock headers match" check) — demonstrating that the codec-level anti-duplicate check does not catch the signature-malleated variant, which is the actual exploit path.
