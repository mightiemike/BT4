### Title
Malformed (non-multiple-of-4-length) base64 `host` query parameter causes `atob()` to throw an uncaught `DOMException`, crashing the process via unhandled promise rejection in the unauthenticated `/auth` (embedded) route - ([File: packages/apps/shopify-api/lib/utils/shop-validator.ts])

### Summary
`sanitizeHost` validates the `host` parameter with a regex that only checks the base64 *character set*, not that the string length is a multiple of 4, before unconditionally calling `decodeHost` (which wraps the global `atob`). A base64-alphabet string whose length mod 4 equals 1 (e.g. a single character `"A"`) causes `atob` to throw a `DOMException`/`InvalidCharacterError` that is never caught, propagating out of `sanitizeHost` regardless of the `throwOnInvalid` flag.

### Finding Description
In [1](#0-0) , the check `base64regex.test(host)` only validates the character set (`[0-9a-zA-Z+/]+={0,2}`), not that the (unpadded) length satisfies the base64 length invariant. When the regex passes, `decodeHost(sanitizedHost)` is called unconditionally — even when the caller passed `throwOnInvalid = false` (the default) — because the throw-on-invalid logic only governs the later `InvalidHostError`, not the `decodeHost` call itself: [2](#0-1) 

`decodeHost` is a thin wrapper around the global `atob`, with no try/catch. Per the WHATWG "forgiving-base64" decode algorithm that Node's `atob` implements, a string whose length (after removing `=` padding) is congruent to 1 mod 4 is invalid and causes `atob` to throw a `DOMException` (`InvalidCharacterError`). A single character such as `"A"` satisfies the regex (`[0-9a-zA-Z+/]+={0,2}`, zero or more `=`) but has length 1 mod 4 == 1, so `atob("A")` throws.

This propagates to the reachable, unauthenticated entry point [3](#0-2) , which calls `api.utils.sanitizeHost(req.query.host as string)` with no try/catch, when `req.query.embedded === '1'`. `clientSideRedirect` is invoked from `redirectToAuth`, which is invoked directly (unwrapped) from the `begin()` route handler: [4](#0-3) 

Because `begin()` is an `async` Express route handler whose returned promise is never awaited or `.catch()`-handled by Express (Express 4 does not await handler promises), a synchronous throw deep inside (`atob`) rejects that promise with no rejection handler attached anywhere in the call chain — this becomes an unhandled promise rejection. Since Node.js 15+, unhandled promise rejections terminate the process by default, unless the host application has globally overridden this behavior (not part of this library, and not guaranteed).

This is distinct from `authCallback`, whose logic *is* wrapped in a try/catch [5](#0-4) ; the vulnerable path is only the `auth.begin()` route (`GET /auth`), which has no such guard.

### Impact Explanation
An anonymous, unauthenticated attacker can send a single crafted GET request to the app's `/auth` route with `embedded=1` and a malformed `host` value to trigger an unhandled exception that (by default Node.js behavior) crashes the entire application process — a denial-of-service impacting all merchants/tenants served by that process, not just the attacker's request. This matches the "DoS in an authentication handler" impact class called out in scope.

### Likelihood Explanation
This requires only default configuration and a single unauthenticated HTTP GET request with attacker-controlled `shop` and `host` query parameters; no secrets, cookies, or prior authentication are needed. The trigger condition (`host` string length mod 4 == 1, valid base64 alphabet) is trivial to construct (e.g. `host=A`), making this reliably repeatable.

### Recommendation
- Wrap the `decodeHost` call inside `sanitizeHost` in a try/catch, treating any decode failure as an invalid host (return `null`, or throw `InvalidHostError` only when `throwOnInvalid` is true), instead of letting the raw `DOMException` propagate.
- Additionally tighten the base64 validation regex to also enforce correct length (e.g. require length % 4 === 0 after accounting for padding, or use a stricter base64 pattern) before calling `atob`.
- Wrap `redirectToAuth`/`begin()` route handling in try/catch (or use an async-error-forwarding wrapper) so any unexpected exception results in a controlled error response instead of an unhandled promise rejection.

```ts
test('sanitizeHost does not throw on malformed base64 length', () => {
  const shopify = shopifyApi(testConfig());

  // 'A' passes the base64 charset regex but has invalid length (1 mod 4)
  expect(() => shopify.utils.sanitizeHost('A')).not.toThrow();
  expect(shopify.utils.sanitizeHost('A')).toBeNull();
});
```

Request-level PoC against an Express app built with `shopify-app-express`:
```
GET /auth?shop=test-shop.myshopify.com&embedded=1&host=A HTTP/1.1
Host: app.example.com
```
Expected (secure) behavior: HTTP 500 with a clean "No host provided" message from `clientSideRedirect`. Actual (current) behavior: `atob('A')` throws `DOMException [InvalidCharacterError]`, which is unhandled inside the `begin()` async route handler, producing an unhandled promise rejection that can crash the Node.js process.
