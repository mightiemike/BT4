## Title
Attached deposits are permanently trapped in the Wallet Contract when the `address_check_callback` or `nep_141_storage_balance_callback` cross-contract calls fail - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `rlp_execute` entry point accepts an attached NEAR deposit (`env::attached_deposit()`) from *any* external caller and tracks it via `CallerDeposit` so it can be refunded if the resulting cross-contract call fails. However, this refund logic is only implemented in the `Failed` branch of `rlp_execute_callback`. Two other callback functions on the same execution path — `address_check_callback` and `nep_141_storage_balance_callback` — have their own early-return failure branches that drop `caller_deposit` without ever creating a refund promise, permanently trapping the caller's attached NEAR in the contract.

### Finding Description
`rlp_execute` is `#[payable]` and forwards `env::attached_deposit()` into `inner_rlp_execute`, which builds a `CallerDeposit` whenever the caller is not the wallet itself: [1](#0-0)  and [2](#0-1) .

For certain transaction kinds, `inner_rlp_execute` does not go straight to `rlp_execute_callback`; it first schedules an intermediate cross-contract call and callback:
- `EOABaseTokenTransfer { address_check: Some(_), .. }` → calls the address registrar, then `address_check_callback` [3](#0-2) 
- `ERC20Transfer { .. }` → calls `storage_balance_of` on the token contract, then `nep_141_storage_balance_callback` [4](#0-3) 

Both intermediate callbacks receive `caller_deposit` as a parameter but only forward it into the *next* promise chain (which eventually reaches `rlp_execute_callback`) when the intermediate call succeeds. If the intermediate call itself fails or returns an unparseable value, they return an error `ExecuteResponse` directly, discarding `caller_deposit` without refunding it:

- `address_check_callback` failure branches: [5](#0-4) 
- `nep_141_storage_balance_callback` failure branches: [6](#0-5) 

By contrast, the only place that actually issues a refund transfer for `caller_deposit` is inside `rlp_execute_callback`'s `Failed` arm: [7](#0-6) . This mirrors the external report's pattern exactly: the contract has exactly one narrow code path (`heal()` in the report, `rlp_execute_callback`'s `Failed` arm here) that performs the refund, and any value that reaches the contract through a different route (here, a deposit whose flow is diverted through `address_check_callback`/`nep_141_storage_balance_callback` on failure) has no mechanism to be recovered. The contract's own tests confirm the intended invariant — that external callers get refunded on failure — for the direct path only: [8](#0-7) , but no equivalent test or code exists for the address-check or NEP-141-storage-balance intermediate-failure cases.

### Impact Explanation
Any unprivileged account (no access key on the wallet needed — confirmed by `test_caller_refunds` using `worker.root_account()` as an arbitrary external caller) can attach NEAR to a `rlp_execute` call whose decoded Ethereum transaction is either an `EOABaseTokenTransfer` requiring an address-registrar lookup, or an `ERC20Transfer`. If the intermediate cross-contract call (`AddressRegistrar::lookup` or the token's `storage_balance_of`) fails — e.g., the token/registrar contract is not deployed, panics, runs out of gas, or returns malformed data — the attached deposit is silently absorbed into the Wallet Contract's balance with no code path capable of returning it. This is a permanent loss of funds for the caller and an unintended, un-withdrawable accumulation of NEAR in the wallet contract account, matching "permanently frozen funds" in the accepted impact categories.

### Likelihood Explanation
This is trivially triggerable by any account with no privileges: attach a deposit, target an ERC20 token contract or address requiring registrar lookup, and cause that specific intermediate call to fail (e.g., point at a non-existent/non-token account, or a token contract that panics on `storage_balance_of`, or supply insufficient gas for the lookup). No validator or relayer collusion is required — a single transaction from any signer against the wallet contract's public `rlp_execute` method is sufficient.

### Recommendation
Ensure `caller_deposit` is refunded in every failure/early-return branch of `address_check_callback` and `nep_141_storage_balance_callback`, not just in `rlp_execute_callback`. The simplest fix is to route all early failure returns through the same refund logic used in `rlp_execute_callback` (e.g., by refactoring the refund-on-failure code into a shared helper invoked whenever `caller_deposit` is dropped without being forwarded to a subsequent promise).

### Proof of Concept
1. Deploy the Wallet Contract for an eth-implicit account and fund it, as in `test_context::TestContext::new`.
2. As an arbitrary external account (not the wallet's owner, no access key — as done for `caller` in `test_caller_refunds`), call `rlp_execute(target, tx_bytes_b64)` with an attached deposit (e.g., 3 NEAR), where `tx_bytes_b64` decodes to an `ERC20Transfer` (`ERC20_TRANSFER_SELECTOR`) targeting a `target` account that either doesn't implement NEP-141 or panics on `storage_balance_of`.
3. Observe: `nep_141_storage_balance_callback`'s `PromiseResult::Failed` branch returns `ExecuteResponse { success: false, .. }` without any refund promise being created for `caller_deposit`.
4. Query the caller's account balance before/after — it is not restored, and there is no other method on `WalletContract` capable of returning it. [9](#0-8) [10](#0-9)

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
