### Title
Loss of accrued staking/voting rewards when a Super Representative has zero recorded votes in a cycle - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
java-tron's DPoS vote-reward accounting has the same structural flaw as the reported `claimStakingIncentives`/`calculateStakingIncentives` bug: when the "total weight" for a distribution period is zero, the incentive that was already allocated for that period is silently dropped instead of being returned anywhere. In java-tron, block/transaction-fee rewards are earmarked per witness per cycle in `DelegationStore` and later distributed to voters proportional to `userVote / totalVote`. If `totalVote` (the witness's recorded vote count for that cycle) is `0`, the reward-splitting loop simply `continue`s, meaning the entire reward pool credited to that witness for that cycle is never paid to anyone and is never refunded/burned/reallocated — it is permanently orphaned in the store.

### Finding Description
Every block/tx-fee reward paid to a witness is split into a brokerage share (paid immediately to the witness) and a remainder that is recorded per-cycle for voters to later claim: [1](#0-0) 

That remainder is stored via `DelegationStore.addReward(cycle, address, value)` and later read back with `getReward(cycle, address)`: [2](#0-1) 

When a voter withdraws/queries their reward, `MortgageService.computeReward(cycle, votes)` (the "old algorithm" path) reads the witness's total recorded vote for that cycle via `getWitnessVote(cycle, srAddress)`. If that value is `0` (or the sentinel `REMARK`), the whole per-cycle reward is skipped with `continue` — it is never added to any voter's `reward`, and the money sitting under that cycle/address key in `DelegationStore` is never read again by any other code path: [3](#0-2) 

This is invoked from `queryReward`/`withdrawReward`'s cycle-by-cycle accumulation: [4](#0-3) 

The "new algorithm" (Vi-based) path has the identical gap: `accumulateWitnessVi` explicitly skips accumulating any delta-Vi for a cycle whenever `voteCount == 0`, meaning the reward minted for that witness in that cycle never enters the Vi ledger that voters draw from: [5](#0-4) [6](#0-5) 

The TVM-exposed `VoteRewardUtil` (used for contract-owned voting) shares the same `computeReward` pattern and is equally affected: [7](#0-6) 

In none of these paths is the orphaned per-cycle reward amount returned to any pool, redistributed, or accounted as burned — it simply remains an unreachable entry in `DelegationStore`, exactly mirroring the reported Solidity bug where `stakingDiff`/`availableStakingAmount` is silently zeroed out instead of refunded to `tokenomics` when `totalWeightSum == 0`.

### Impact Explanation
A witness can have a recorded vote count of `0` for a given cycle in realistic conditions — e.g., a witness that is part of the active/standby set (because there are fewer registered witnesses than slots, common on private/consortium/test networks built on java-tron, or transiently on mainnet if voters fully reallocate/unfreeze their votes) while still producing blocks and receiving block/tx-fee rewards during that maintenance cycle, since `MaintenanceManager.doMaintenance` records `getVoteCount()` at cycle boundaries and can be `0`. Any block reward or transaction fee reward attributed to that witness for that cycle becomes permanently unclaimable: it is not paid to voters (skipped due to zero-vote division context) and not paid to anyone else, and there is no compensating decrement anywhere in supply accounting — a silent accounting divergence between minted rewards and actually distributable/claimable rewards. This matches the Medium severity classification of the original finding: no direct theft of user funds, but a systemic loss/deduction from the reward ledger.

### Likelihood Explanation
This requires no privileged role — any witness/voter interaction (freezing/voting, then later fully unvoting or a witness simply having low/zero votes while still active) can trigger the zero-vote-count condition for a cycle. It is most easily reproducible on private or low-participation java-tron-based networks (where the number of registered SRs is ≤ the number of active slots, so 0-vote witnesses are still elected), but is also possible transiently on any network. The result is deterministic given the described `getWitnessVote(...) == 0` condition, matching the original PoC's mechanism precisely.

### Recommendation
Track cycles where a witness's total recorded vote is zero and, when the corresponding `getReward(cycle, address)` entry is skipped in `computeReward`/`accumulateWitnessVi`, explicitly reclaim that amount — either credit it back to the witness (as with brokerage) or route it into a documented sink (burn / reserve) instead of leaving it as an unreachable ledger entry. Ensure the reclaim happens exactly once per zero-vote cycle to avoid double-counting.

### Proof of Concept
1. Deploy/operate a java-tron network where the number of registered witnesses is ≤ the active/standby witness count (or arrange for a witness's votes to be fully withdrawn), so a witness `W` is elected/active with `voteCount == 0` for cycle `C`.
2. Let `W` produce blocks and collect transaction fees during cycle `C`; `MortgageService.payBlockReward`/`payTransactionFeeReward` call `payReward`, which calls `delegationStore.addReward(C, W, value)` for the non-brokerage remainder.
3. At the end of the maintenance period, `MaintenanceManager.doMaintenance` records `delegationStore.setWitnessVote(C+1, W, 0)` reflecting the zero vote count.
4. Any voter who previously voted for `W` (or a new voter) calls `withdrawReward`/`queryReward`. `MortgageService.computeReward(C, votes)` reads `getWitnessVote(C, W) == 0` and `continue`s, so the reward recorded in step 2 is never added to any account's allowance.
5. Inspect `DelegationStore` at key `buildRewardKey(C, W)` — the value remains equal to the amount credited in step 2, proving it was never paid out, refunded, or burned, and is permanently orphaned.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
