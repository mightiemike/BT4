### Title
Unauthenticated `CreateShieldedTransactionServlet` allows CPU-expensive zk-SNARK spend proof generation with fabricated (non-existent) anchors before any fee is charged - ([File: framework/src/main/java/org/tron/core/services/http/CreateShieldedTransactionServlet.java])

### Summary
`Wallet.createShieldedTransaction` builds and proves shielded spends via `ZenTransactionBuilder.addSpend`/`build`/`generateSpendProof` without ever checking that the caller-supplied anchor (`voucher.getRt()`) corresponds to a real historical merkle root. The `merkleRootExist` check only exists in `ShieldedTransferActuator.validate`, which runs at broadcast time, so an attacker can force full nodes to run the expensive `librustzcashSaplingSpendProof` computation for arbitrary numbers of fabricated notes/anchors with no fee and only request-rate throttling.

### Finding Description
`CreateShieldedTransactionServlet.doPost` is a `@Component` HTTP servlet that extends `RateLimiterServlet` and requires no authentication; it directly forwards the parsed `PrivateParameters` to `wallet.createShieldedTransaction(...)`. [1](#0-0) 

Inside `Wallet.createShieldedTransaction`, each `SpendNote` from the request is turned into a `SpendDescriptionInfo` by decoding the client-supplied voucher and anchor bytes directly (`spendNote.getVoucher().getRt().toByteArray()`), with no lookup against the chain's stored merkle roots: [2](#0-1) 

`ZenTransactionBuilder.addSpend` simply stores the anchor bytes in a `SpendDescriptionInfo` without validation: [3](#0-2) 

`ZenTransactionBuilder.build` then unconditionally calls `generateSpendProof` for every spend, which invokes the native, computationally expensive `JLibrustzcash.librustzcashSaplingSpendProof` (Groth16 proving) using the client-controlled `spend.anchor` as a proof input — a self-consistent fabricated merkle path/anchor pair (e.g. built from a locally-constructed `IncrementalMerkleTreeContainer`) is sufficient for the proof to succeed, since the proof does not reference chain state: [4](#0-3) [5](#0-4) 

`grep`-confirmed: `merkleRootExist` is referenced only in `MerkleContainer` (definition) and `ShieldedTransferActuator` — never in `Wallet.java` or `ZenTransactionBuilder.java`. The only place the anchor is actually checked against chain state is `ShieldedTransferActuator.validate`, which runs on broadcast, after the proof has already been generated: [6](#0-5) 

`RateLimiterServlet.service` only enforces QPS/permit-based rate limiting (per-endpoint and global), which is agnostic to the CPU cost of the underlying work being requested: [7](#0-6) 

The existing test suite corroborates that `generateSpendProof` succeeds for spends whose anchor was never registered via `putMerkleTreeIntoStore`, and that "Rt is invalid." is raised only later, during actuator validation: [8](#0-7) [9](#0-8) 

### Impact Explanation
Every call to this public, unauthenticated endpoint with a self-consistent fake spend note forces the node to perform a full Groth16 spend-proof computation (`librustzcashSaplingSpendProof`), which is CPU-intensive relative to typical HTTP request handling, before any fee-bearing transaction is broadcast or validated on-chain. Because gating is limited to `RateLimiterServlet`'s QPS-style limiter (not proof-cost-aware), an attacker can sustain proof generation up to the configured QPS ceiling indefinitely, at zero cost, degrading node responsiveness/CPU availability for a full node exposing this HTTP API (a classic underpriced-work / resource-exhaustion condition scoped to nodes serving the shielded wallet HTTP API).

### Likelihood Explanation
- Precondition: the node must have `allowShieldedTransactionApi` enabled (a config flag checked by `checkAllowShieldedTransactionApi()` at the top of `createShieldedTransaction`) so the endpoint functions; this is an operator-controlled build/runtime setting, not attacker-controlled, but is commonly enabled on nodes offering the shielded wallet API.
- Given that precondition, the attack requires no special privileges: any unauthenticated HTTP client can construct a self-referential fake note/merkle voucher (as already demonstrated by existing test helpers such as `createSimpleMerkleVoucherContainer`) and repeatedly POST to `CreateShieldedTransactionServlet`.
- The only constraint is `RateLimiterServlet`'s configured QPS, which limits request throughput but does not scale with the CPU cost of the requested proof, so the achievable CPU-drain per unit time is fixed and reproducible.

### Recommendation
Add a `chainBaseManager.getMerkleContainer().merkleRootExist(anchor)` check inside `Wallet.createShieldedTransaction`/`createShieldedTransactionWithoutSpendAuthSig` (or in `ZenTransactionBuilder.addSpend`) before proof generation, rejecting spends whose anchor does not correspond to a real historical merkle root, mirroring the check already performed in `ShieldedTransferActuator.validate`. Additionally, consider adding a dedicated, stricter rate limit (or proof-generation quota) specifically for shielded proof-generation endpoints, independent of the generic QPS-based `RateLimiterServlet`.

```java
// In a test extending BaseTest with zk params initialized:
@Test
public void testCreateShieldedTransactionAcceptsFakeAnchor() throws Exception {
    // 1. Build a self-consistent but NOT chain-registered merkle tree/voucher for a fake note
    SpendingKey sk = SpendingKey.random();
    ExpandedSpendingKey expsk = sk.expandedSpendingKey();
    PaymentAddress address = sk.defaultAddress();
    Note note = new Note(address, 100_000_000L);
    IncrementalMerkleTreeContainer tree =
        new IncrementalMerkleTreeContainer(new IncrementalMerkleTreeCapsule());
    PedersenHashCapsule cmCapsule = new PedersenHashCapsule();
    cmCapsule.setContent(ByteString.copyFrom(note.cm()));
    tree.append(cmCapsule.getInstance());
    IncrementalMerkleVoucherContainer voucher = tree.toVoucher();
    byte[] fakeAnchor = voucher.root().getContent().toByteArray();
    // NOTE: fakeAnchor is intentionally NOT put into
    // chainBaseManager.getMerkleContainer() via putMerkleTreeIntoStore(...)

    // 2. Build PrivateParameters request as CreateShieldedTransactionServlet would parse it,
    //    with SpendNote.voucher.rt = fakeAnchor and voucher path from `voucher`.

    long start = System.nanoTime();
    // 3. Call wallet.createShieldedTransaction(request) directly (equivalent to servlet path)
    TransactionCapsule txCapsule = wallet.createShieldedTransaction(request); // should NOT throw
    long elapsed = System.nanoTime() - start;

    // Assert: proof generation succeeded locally despite non-existent anchor
    Assert.assertNotNull(txCapsule);
    System.out.println("Proof generation time (ns): " + elapsed);

    // 4. Confirm the SAME anchor is rejected only later, at actuator validate() time
    Contract contract = txCapsule.getInstance().getRawData().getContract(0);
    ShieldedTransferActuator actuator = new ShieldedTransferActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager())
        .setContract(contract).setTx(txCapsule);
    try {
        actuator.validate();
        Assert.fail("expected Rt is invalid.");
    } catch (ContractValidateException e) {
        Assert.assertEquals("Rt is invalid.", e.getMessage());
    }
}
```
Expected result: step 3 succeeds (proof generation completes, consuming measurable CPU time via `librustzcashSaplingSpendProof`) even though the anchor was never stored via `putMerkleTreeIntoStore`; step 4 confirms the same fabricated-anchor transaction is rejected only at broadcast-time validation, confirming the gap between free/unchecked proof generation and paid/checked broadcast.

  public SpendDescriptionCapsule generateSpendProof(SpendDescriptionInfo spend,
      long ctx) throws ZksnarkException {

    byte[] cm = spend.note.cm();

    // check if ak exists
    byte[] ak;
    byte[] nf;
    byte[] nsk;
    if (!ArrayUtils.isEmpty(spend.ak)) {
      ak = spend.ak;
      nf = spend.note.nullifier(ak, JLibrustzcash.librustzcashNskToNk(spend.nsk),
          spend.voucher.position());
      nsk = spend.nsk;
    } else {
      ak = spend.expsk.fullViewingKey().getAk();
      nf = spend.note.nullifier(spend.expsk.fullViewingKey(), spend.voucher.position());
      nsk = spend.expsk.getNsk();
    }

    if (ByteArray.isEmpty(cm) || ByteArray.isEmpty(nf)) {
      throw new ZksnarkException("Spend is invalid");
    }

    byte[] voucherPath = spend.voucher.path().encode();

    byte[] cv = new byte[32];
    byte[] rk = new byte[32];
    byte[] zkproof = new byte[192];
    if (!JLibrustzcash.librustzcashSaplingSpendProof(
        new SpendProofParams(ctx,
            ak,
            nsk,
            spend.note.getD().getData(),
            spend.note.getRcm(),
            spend.alpha,
            spend.note.getValue(),
            spend.anchor,
            voucherPath,
            cv,
            rk,
            zkproof))) {
      throw new ZksnarkException("Spend proof failed");
    }

    // Check per-endpoint first to avoid consuming global IP/QPS quota for requests
    // that would be rejected by the per-endpoint limiter anyway. acquirePermit()
    // chooses blocking or non-blocking semantics based on rate.limiter.apiNonBlocking.
    boolean perEndpointAcquired = rateLimiter == null || rateLimiter.acquirePermit(runtimeData);
    boolean acquireResource = perEndpointAcquired && GlobalRateLimiter.acquirePermit(runtimeData);

    String contextPath = req.getContextPath();
    String url = Strings.isNullOrEmpty(req.getServletPath())
        ? MetricLabels.UNDEFINED : contextPath + req.getServletPath();
    // int64_as_string is honored only on GET requests (URL query). POST is intentionally
    // unsupported because reading the body here would consume request.getReader() and
    // break downstream servlets that read it themselves.
    if ("GET".equalsIgnoreCase(req.getMethod())) {
      JsonFormat.setInt64AsString(Util.getInt64AsString(req));
    }

      resp.setContentType("application/json; charset=utf-8");

      if (acquireResource) {
        Histogram.Timer requestTimer = Metrics.histogramStartTimer(
            MetricKeys.Histogram.HTTP_SERVICE_LATENCY, url);
        super.service(req, resp);
        Metrics.histogramObserve(requestTimer);
      } else {
        resp.getWriter()
