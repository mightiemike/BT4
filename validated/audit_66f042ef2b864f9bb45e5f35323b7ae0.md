### Title
`TransactionOutput::ensure_match_transaction_info` fails to validate state/hot-state/position checkpoint hashes during replay, letting divergent committed state pass verification - ([File: types/src/transaction/mod.rs])

### Summary
`TransactionOutput::ensure_match_transaction_info` is the shared post-execution equality check used by chunk replay (`execution/executor/src/chunk_executor/mod.rs`) and archive replay-verification (`storage/db-tool/src/replay_on_archive.rs`) to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on-chain. The function checks status, gas, write-set hash, and event root hash, but — by its own inline TODO — does **not** check `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` carried by `TransactionInfoV1`.

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  compares only:
- `status()` vs `txn_info.status()`
- `gas_used()` vs `txn_info.gas_used()`
- `hash(write_set)` vs `txn_info.state_change_hash()`
- event accumulator root vs `txn_info.event_root_hash()`

It explicitly documents the gap: [2](#0-1) 

`TransactionInfoV1` (assembled when `TRANSACTION_INFO_V1` is enabled, per [3](#0-2) ) carries `state_checkpoint_hash`, `hot_state_checkpoint_hash` (gated by `HOT_STATE_ROOT_IN_TXN_INFO`), and `position_state_checkpoint_hash` (gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS`), all of which get committed into the transaction accumulator and thus become part of the authenticated ledger root — see the feature-flag wiring in [4](#0-3)  and [5](#0-4) . These checkpoint hashes are never independently re-derived and compared by `ensure_match_transaction_info`, so a local execution result whose state-checkpoint/hot-state/position root diverges from what is on the authenticated ledger will still be reported as "matching" by any caller relying solely on this function.

### Impact Explanation
Both consumers of this function — `execution/executor/src/chunk_executor/mod.rs` (used during chunk-based state sync/replay of an already-committed authenticated chunk) and `storage/db-tool/src/replay_on_archive.rs` (the tool operators use to verify archived history against a fully-synced/authenticated chain) — treat a passing `ensure_match_transaction_info` as proof that local execution reproduces the authenticated ledger state for that transaction. Since the position/hot-state checkpoint roots (bound into the accumulator via `TransactionInfoV1`) are silently excluded from this comparison, replay-verify can report success even though the locally computed state (specifically the native-position/trading state root, or hot-state root) diverges from the value actually committed and proven by consensus. This is exactly the "authenticated ledger data replayed/verified incorrectly, masking a real divergence" class of state-integrity issue: a wrong commitment can go undetected by the very tooling meant to catch it, defeating a hard-fork/consistency safety net for `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO`.

### Likelihood Explanation
The code itself is currently guarded by the fact that `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is off by default and requires both `TRANSACTION_INFO_V1` and `HOTNESS_IN_EPILOGUE` (per [6](#0-5) ). The TODO comment is explicit that this gap must be closed "before enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`," which indicates the maintainers are aware this is not yet safe for production activation. The bug is not exploitable by an external unprivileged actor today (feature flags are off), but it is a genuine, code-documented broken invariant in state-integrity/replay-verification tooling that would silently mask divergence the moment those features are turned on — which is the exact "hard-fork-only divergence during commit, replay ... proof verification" category called out as in-scope.

### Recommendation
Extend `ensure_match_transaction_info` to also compare, when present on `TransactionInfoV1`:
- `state_checkpoint_hash` against the locally computed state-checkpoint root for that version,
- `hot_state_checkpoint_hash` against the locally computed hot-state root (when `HOT_STATE_ROOT_IN_TXN_INFO` is set),
- `position_state_checkpoint_hash` against the locally computed native-position root (when `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is set),

and fail loudly (as the other `ensure!` checks do) on mismatch, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are ever enabled on mainnet.

### Proof of Concept
Not applicable as an exploit against current mainnet behavior — the relevant feature flags (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`) are off by default, so `TransactionInfoV0`/early `V1` paths don't yet rely on these unchecked fields for consensus. The concrete local proof is the source code itself: `ensure_match_transaction_info` (types/src/transaction/mod.rs:2139-2204) omits comparisons for `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash`, and its own inline comment (lines 2197-2202) confirms replay-verify tooling (`storage/db-tool/src/replay_on_archive.rs`, `execution/executor/src/chunk_executor/mod.rs`) can report success despite a diverging authenticated position/hot-state root. I was not able to fully trace how `replay_on_archive.rs` and `chunk_executor/mod.rs` use the return value of this function (e.g., whether they additionally re-verify checkpoint hashes elsewhere) within the available search iterations — confirming that would require reading the full call sites, which I could not do given the remaining budget. If those call sites do perform independent checkpoint-hash verification elsewhere, this finding's severity would be reduced to a defense-in-depth gap rather than a full detection bypass.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
