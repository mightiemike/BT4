### Title
Unbounded secondary-index growth allows any user to inflate `AccountsIndex` per-key pubkey lists, causing disproportionate CPU/memory cost on a single indexed RPC scan - (File: accounts-db/src/accounts_index/secondary.rs)

### Summary
The reported bug's root cause is that an unprivileged actor can append entries to an owner-keyed collection with no access control or cap, so that a single, otherwise-cheap query that must iterate that collection (`redeemRewards`) becomes computationally infeasible. The same pattern exists in Agave's accounts-index secondary indexes (`--account-index program-id|spl-token-mint|spl-token-owner`): any account creator can insert into `SecondaryIndex::index` keyed by an arbitrary program-id/mint/owner pubkey, with no check that the inserter is authorized by, or related to, that key's real owner, and no upper bound on the number of inner keys per outer key.

### Finding Description
`SecondaryIndex::insert` unconditionally adds `inner_key` to the set stored under `key`, and there is no limit on the size of that set: [1](#0-0) 

The insertion is driven purely by data the account creator controls. `update_secondary_indexes` inserts into `program_id_index` for any account whose `owner` field matches a target program id, and `update_spl_token_secondary_indexes` inserts into `spl_token_mint_index`/`spl_token_owner_index` based on bytes unpacked directly from the account's own data, with no verification that the account has any real relationship to that mint/owner beyond matching the SPL token layout: [2](#0-1) [3](#0-2) 

`SecondaryIndex::get` (used by `AccountsIndex::get_index_key_pubkeys`) eagerly clones the entire set of inner keys into a `Vec<Pubkey>` regardless of size: [4](#0-3) [5](#0-4) 

`AccountsDb::index_scan_accounts` then iterates that full vector and performs a storage `do_load` for every returned pubkey before any abort/size-limit check can take effect for entries already collected: [6](#0-5) 

This is reachable from a single RPC call (`getProgramAccounts` with `--account-index program-id`, or `getTokenAccountsByOwner`/`getTokenAccountsByMint` style queries) via `Accounts::load_by_index_key_with_filter` and `rpc.rs::get_filtered_program_accounts`: [7](#0-6) [8](#0-7) 

Just as the Solidity report's `vaults[owner]` array can be inflated by anyone deploying a vault naming an arbitrary `owner`, here anyone can create SPL token accounts (or accounts owned by any program) referencing an arbitrary, popular mint/owner/program pubkey, inflating that key's `SecondaryIndex` entry without the consent of whoever actually controls/uses that mint or program. There is no analog to "only the factory may register" — no caller is authorized to gate these insertions.

### Impact Explanation
On any validator/RPC node that enables a secondary index (`--account-index program-id|spl-token-mint|spl-token-owner`), an unprivileged party can cheaply mass-create trivial token accounts (or program-owned accounts) all referencing the same popular mint/owner/program id. Because insertion is unbounded and unauthenticated, the corresponding `SecondaryIndex` bucket grows without limit. Subsequent single-call indexed queries against that key (`get_index_key_pubkeys` + per-pubkey `do_load`) then incur CPU, memory, and I/O costs proportional to the attacker-inflated set size, i.e., disproportionate cost from one RPC call, degrading that node's availability/performance for legitimate users of a popular mint/program. This matches the "disproportionate storage and CPU cost" acceptance criterion and is a real, previously-observed operational hazard of the secondary-index feature (large mints/programs causing outsized memory/CPU use), not merely theoretical.

### Likelihood Explanation
The feature is opt-in (`--account-index`), but when enabled it is directly reachable by any unprivileged network participant: creating accounts with arbitrary owner/data content is a normal, permissionless operation, and no authorization from the targeted mint/owner/program is required to be indexed under it. No special privileges, timing, or multiple coordinated calls beyond ordinary account creation are needed to grow the index; only a single subsequent RPC call is needed to trigger the disproportionate cost.

### Recommendation
Add per-key bounds (or a global/per-key eviction/backpressure policy) to `SecondaryIndex::insert`, similar to the fix in the original report (restrict who/what can register entries, or cap the number of `inner_key`s tracked per outer `key`), and make `get_index_key_pubkeys`/`index_scan_accounts` apply the scan's byte/size limit before eagerly materializing and iterating the full pubkey set, not only afterward while accumulating results.

### Proof of Concept
1. Run a node with `--account-index spl-token-mint` (or `program-id`) enabled.
2. Repeatedly submit transactions creating new SPL token accounts whose data layout matches `spl_generic_token::token::Account`, all initialized against the same target mint pubkey `M` (a popular, legitimate mint the attacker does not control), e.g. as done in the test setup pattern in [9](#0-8) .
3. Each such account causes `update_spl_token_secondary_indexes` to insert into `spl_token_mint_index.get(M)`'s entry set, per [10](#0-9) ; the set has no upper bound.
4. Issue a single `getTokenAccountsByMint`/indexed query for `M`; `get_index_key_pubkeys` clones the now-huge set ( [4](#0-3) ), and `index_scan_accounts` performs a `do_load` for every entry ( [6](#0-5) ), producing CPU/I/O cost proportional to the attacker-inserted entry count from one RPC call.

    /// Inserts `inner_key` into `key`'s map.
    pub fn insert(&self, key: &Pubkey, inner_key: &Pubkey) {
        // Note: Always lock the reverse index first, so we synchronize with remove().
        // Pre-size to 1 to avoid push() over-allocating an empty Vec to capacity 4.
        let reverse_index_entry = self
            .reverse_index
            .entry(*inner_key)
            .or_insert_with(|| RwLock::new(Vec::with_capacity(1)));
        let mut outer_keys = reverse_index_entry.write().unwrap();

        // Now insert into the index.
        // Note, we do this get()-then-unwrap instead of calling entry() directly, because
        // get() is a read lock whereas entry() is a write lock.  We assume `key` already has
        // a map created, so optimize for the common case and only take a read lock.
        self.index
            .get(key)
            .unwrap_or_else(|| self.index.entry(*key).or_default().downgrade())
            .insert_if_not_exists(inner_key, &self.stats.num_inner_keys);

        if !outer_keys.contains(key) {
            outer_keys.push(*key);
        }

            .accounts_db
