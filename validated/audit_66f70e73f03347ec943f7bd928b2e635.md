### Title
Unbounded secondary-index growth via repeated Assign owner changes on a single live account - ([File: accounts-db/src/accounts_index/secondary.rs])

### Summary
When secondary indexes (`--account-index program-id`, etc.) are enabled, an attacker can repeatedly `Assign`/`AssignWithSeed` a single account they control to a series of distinct owner pubkeys. Each owner change adds a new outer-key mapping to `SecondaryIndex::insert` (`reverse_index` entry grows by one, plus a new `index` DashMap entry per distinct owner) at the cost of a flat, cheap system-program instruction, and none of the stale owner mappings are reclaimed as long as the account itself stays alive (non-zero lamports).

### Finding Description
`system_processor::assign` (`programs/system/src/system_processor.rs:117-135`) lets the account owner sign an `Assign`/`AssignWithSeed` to change `owner` for `DEFAULT_COMPUTE_UNITS = 150` [1](#0-0)  — a fixed, tiny cost regardless of index effects. Every time the account is subsequently flushed/stored, `AccountsDb::update_index_for_flush` (and the cache-only path `update_secondary_index_cached_accounts`) call `AccountsIndex::update_secondary_indexes`, which unconditionally does `self.program_id_index.insert(account_owner, pubkey)` for the *current* owner [2](#0-1) .

`SecondaryIndex::insert` (`accounts-db/src/accounts_index/secondary.rs:132-171`) appends the new owner key to the account's `reverse_index` Vec (`outer_keys.push(*key)`) if not already present, and creates a brand-new `index` DashMap entry for that owner pubkey if one doesn't already exist [3](#0-2) .

Critically, none of this is cleaned up when the owner changes to a new value: stale owner mappings are removed only via `purge_secondary_indexes_by_inner_key_if` / `remove_by_inner_key_if`, which is invoked exclusively when the *account key itself* dies (i.e., its primary-index slot list becomes empty because the account went to zero lamports and was cleaned) [4](#0-3) [5](#0-4) . There is no mechanism that removes a *previous* owner's mapping just because the account was reassigned to a new owner while remaining alive. This is explicitly confirmed by existing tests/comments:
- `test_get_filtered_indexed_accounts`: "Even though the account is re-stored in the bank (and the index) under a new program id, it is still present in the index under the original program id as well." [6](#0-5) 
- `run_test_secondary_indexes_same_slot_and_forks`: "even though the account with secondary_key1 was outdated by the update in the later slot, the primary account key is still alive, so both secondary keys will still be kept alive." [7](#0-6) 

So the sequence `CreateAccount -> Assign(owner_1) -> Assign(owner_2) -> ... -> Assign(owner_N)` (each in a separate rooted slot, keeping the account non-zero-lamport throughout) causes:
- N distinct entries added to `reverse_index[pubkey]` (a `Vec<Pubkey>`), and
- N distinct `index` DashMap keys (one per unique owner value chosen by the attacker), each holding a `RwLockSecondaryIndexEntry` with the account key.

None of these N mappings are ever removed while the attacker keeps the account alive (simply never zeroing lamports/closing it), so the index (used by `getProgramAccounts` with the `program-id` secondary index enabled) grows linearly and permanently in memory/lookup cost, driven entirely by attacker-chosen instructions each costing a flat 150 CU + one signature fee, with no cost or bound tied to the number of distinct owners the attacker chooses to churn through.

### Impact Explanation
This is an uncosted, disproportionate storage/CPU growth in `AccountsIndex` secondary structures (`program_id_index`/similarly `spl_token_owner_index`/`spl_token_mint_index` for token accounts) relative to the flat per-instruction fee paid. On any RPC node that enables account secondary indexes (a documented, common configuration to support unfiltered/fast `getProgramAccounts`), an attacker can cheaply grow `reverse_index` Vec length and the number of `index` DashMap entries without bound, since cleanup only triggers on full account death (zero-lamport + `clean_accounts`), not on owner reassignment. This falls into the "disproportionate storage and CPU cost" / index-maintenance-cost-vs-fee category described in the question's scoped impact.

### Likelihood Explanation
Fully reachable by an unprivileged attacker: they only need to own an account (fee payer + account keypair) and repeatedly sign `Assign`/`AssignWithSeed` instructions to different owner pubkeys across separate slots/roots, never bringing the account to zero lamports. No validator/operator privilege is required beyond the target node having secondary indexes enabled (an opt-in but standard RPC configuration explicitly referenced by the question). The attack is fully repeatable and scales linearly with the number of transactions sent, each of which is cheap (150 CU, one signature).

### Recommendation
When updating the secondary index for an account whose owner has changed, remove the mapping for the account's *previous* owner (not just wait for full account death), e.g. track the last-indexed owner per account (or diff against the current single mapping) in `update_secondary_indexes`/`update_index_for_flush` and call `remove_index_entries`/`remove_by_inner_key_if`-equivalent logic for the old owner when a new owner value is observed, so `program_id_index` never accumulates more than one live outer-key mapping per account.

```rust
#[test]
fn test_program_id_secondary_index_unbounded_owner_churn() {
    let db = AccountsDb {
        account_indexes: program_id_index_enabled(),
        ..AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG)
    };
    let pubkey = Pubkey::new_unique();
    let mut lamports = 1;
    for slot in 1..=1000u64 {
        let owner = Pubkey::new_unique(); // distinct owner each iteration
        let account = AccountSharedData::new(lamports, 0, &owner);
        db.store_for_tests((slot, &[(&pubkey, &account)][..]));
        db.add_root(slot);
        db.flush_accounts_cache_slot_for_tests(slot);
        db.clean_accounts_for_tests(); // account stays alive (non-zero lamports)
        lamports += 1;
    }
    // Assert: reverse_index for `pubkey` has ~1000 entries and the program_id_index
    // has ~1000 distinct outer keys attributable to this single account, despite
    // each Assign costing a flat, tiny fee (150 CU + 1 signature).
    let reverse_len = db.accounts_index.get_reverse_index_len(&AccountIndex::ProgramId, &pubkey); // hypothetical accessor
    assert!(reverse_len >= 900, "expected near-linear unbounded growth, got {reverse_len}");
}
```
Expected assertion: `reverse_index[pubkey].len()` (and corresponding `program_id_index.index` entry count attributable to `pubkey`) grows proportionally to N while total fees paid remain O(N) at a fixed per-tx rate with no additional index-maintenance surcharge — i.e., cost-per-index-entry is effectively free beyond the base instruction fee, and cleanup does not occur until the account is zeroed and cleaned.

```rust
            .entry(*inner_key)
```
