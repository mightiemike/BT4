### Title
Missing `supportUnfreezeDelay()` feature-gate check in `DelegateResourceProcessor.validate` allows TVM contracts to bypass committee-controlled delegate-resource gate - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java])

### Summary
`DelegateResourceActuator.validate` (direct transaction path) requires both `dynamicStore.supportDR()` and `dynamicStore.supportUnfreezeDelay()` to be true before allowing resource delegation. `DelegateResourceProcessor.validate` (used by the TVM `delegateResource` native/precompiled contract path invoked from smart contracts) only checks `supportDR()` and omits the `supportUnfreezeDelay()` check entirely, creating divergent feature-gate enforcement between the two entry points.

### Finding Description
`DelegateResourceActuator.validate()` enforces two separate committee-controlled proposal flags before permitting a `DelegateResourceContract` broadcast directly by a user: [1](#0-0) 

In contrast, `DelegateResourceProcessor.validate()`, which is invoked when a smart contract triggers the `delegateResource` TVM opcode, only checks `supportDR()`: [2](#0-1) 

`supportDR()` and `supportUnfreezeDelay()` are backed by distinct dynamic properties/committee proposals (found referenced separately in `DynamicPropertiesStore.java` and `ProposalUtil.java`), meaning they can be toggled independently by the committee via separate proposals. If the committee enables `ALLOW_DELEGATE_RESOURCE` (making `supportDR()` true) before enabling the unfreeze-delay-related proposal (`supportUnfreezeDelay()` false), the two validate paths diverge: the direct transaction path correctly rejects delegation with `"Not support Delegate resource transaction, need to be opened by the committee"`, while the TVM contract path (`DelegateResourceProcessor.validate`) has no equivalent check and will accept the same logical operation.

An attacker (any unprivileged account) can deploy or call a smart contract that invokes the `delegateResource` precompiled/native contract from Solidity. During the described window (`supportDR()==true`, `supportUnfreezeDelay()==false`), that contract call reaches `DelegateResourceProcessor.execute` and mutates account/delegated-resource state that the committee had not yet intended to allow, producing state changes inconsistent with what the direct actuator path permits under identical global fork-parameter state — a case of non-deterministic feature-gate enforcement based on entry path rather than a state-dependent invariant.

### Impact Explanation
This is a functional/business-logic bug rather than a memory-safety or fund-theft bug: it lets a committee-gated feature be exercised through the contract path in a chain-state window that the transaction-path validator explicitly disallows. The impact is limited to inconsistent enforcement of an intended safety rollout gate (feature exposed early, only through contracts) rather than causing asset loss, unauthorized transfers between third parties' accounts, or node crashes, because resource delegation still requires legitimate frozen balance ownership and correct target/receiver addresses (both processors enforce ownership, balance sufficiency, and receiver validity identically). It matches a "logic error / unintended feature exposure due to inconsistent validation" bounty class rather than a critical fund-security class; it does not constitute a global consensus divergence across nodes (all nodes execute the same code deterministically), but it does represent an inconsistency between two code paths that should enforce the same committee-controlled gate.

### Likelihood Explanation
Exploitability strictly depends on the on-chain state actually being in the window `supportDR()==true && supportUnfreezeDelay()==false`. Whether this window can occur in practice depends on the order in which the corresponding proposals are activated by the committee; I was unable to fully confirm within the available tool budget whether the two proposals are activated together atomically in genesis/config or can be sequenced independently by governance in this codebase (the definitions live in `DynamicPropertiesStore.java` / `ProposalUtil.java`, which I identified but did not fully trace for interdependency enforcement). If they can be set independently (which the separate gating in the actuator code strongly suggests was the intent), the cost to the attacker is only the gas/energy cost of a contract call once such a window opens — no privileged access is required.

### Recommendation
Add the same `supportUnfreezeDelay()` check to `DelegateResourceProcessor.validate` that exists in `DelegateResourceActuator.validate`, so both code paths enforce identical committee feature gates:
```java
if (!dynamicStore.supportUnfreezeDelay()) {
  throw new ContractValidateException("Not support Delegate resource transaction,"
      + " need to be opened by the committee");
}
```
placed immediately after the existing `supportDR()` check in `DelegateResourceProcessor.java`.

### Proof of Concept
```java
// Differential JUnit test (conceptual) — place in actuator or nativecontract test module
@Test
public void testFeatureGateDivergence() throws Exception {
  // Arrange: force fork state supportDR=true, supportUnfreezeDelay=false
  dynamicPropertiesStore.saveAllowDelegateResource(1);      // supportDR() == true
  dynamicPropertiesStore.saveAllowTvmFreezeV2UnfreezeDelay(0); // supportUnfreezeDelay() == false (name illustrative)

  // Act 1: direct actuator path
  DelegateResourceActuator actuator = new DelegateResourceActuator();
  actuator.setChainBaseManager(chainBaseManager);
  actuator.setAny(buildDelegateResourceContractAny(...));
  ContractValidateException actuatorEx = assertThrows(ContractValidateException.class,
      actuator::validate);
  assertTrue(actuatorEx.getMessage().contains("need to be opened by the committee"));

  // Act 2: TVM native contract path
  DelegateResourceProcessor processor = new DelegateResourceProcessor();
  DelegateResourceParam param = buildDelegateResourceParam(...); // same owner/receiver/balance
  // Expected (per invariant): should also throw, but currently PASSES:
  processor.validate(param, repository); // no exception thrown -> divergence proven
}
```
Expected (fixed) behavior: both `actuator.validate()` and `processor.validate()` throw `ContractValidateException` identically when `supportUnfreezeDelay()==false`, regardless of entry path.
