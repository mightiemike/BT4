### Title
Single invalid outbound event in a multi-withdraw payload silently drops **all** outbound records for that transaction, permanently stranding already-moved funds - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`BuildOutboundsFromReceipt` iterates over every `UniversalTxOutbound` (withdraw) log emitted by `UniversalGatewayPC` in a single EVM receipt and turns each into a Cosmos-side `OutboundTx` record. If any one of the outbound events fails registry validation (unsupported/disabled destination chain, or unregistered PRC20 token), the function returns `nil, err` for the **entire receipt**, discarding the `OutboundTx` records already built for the other, valid withdraw events in the same transaction — even though the underlying PRC20 burns/locks for all of those withdrawals already happened atomically on the EVM side.

### Finding Description
`BuildOutboundsFromReceipt` builds an `outbounds` slice by looping over `receipt.Logs` [1](#0-0) . For each valid `UniversalTxOutbound` log it performs two registry checks — `IsChainOutboundEnabled` and `GetTokenConfigByPRC20` — and on failure of either, it immediately `return`s `nil, err`, discarding everything accumulated so far in `outbounds` [2](#0-1) .

This function is invoked from `AttachOutboundsToExistingUniversalTx`, which is called after a `MsgExecutePayload`-driven payload has already successfully executed on the EVM (i.e. after the UEA/UniversalGatewayPC contract calls that burn/lock the PRC20 tokens for withdrawal have already been committed as part of that same atomic EVM transaction) [3](#0-2) . The caller only records the returned error as a free-text `RevertError` string on the UTX and does **not** create any compensating outbound, revert, or refund for the events that had already succeeded [4](#0-3) .

Because a single payload execution can trigger the UniversalGatewayPC withdraw path multiple times (e.g. a payload whose target contract logic issues several cross-chain withdrawals in one call), an attacker who controls the payload can arrange for one of the withdraw events to reference a destination chain that is outbound-disabled, or a token/PRC20 pair with no registered `TokenConfig`. Both conditions are checked only against Cosmos-side registry state and are trivially attacker-triggerable by choosing arbitrary/legitimate-looking parameters for one leg of a multi-withdraw payload while the others are valid.

The result: none of the withdraw events in that receipt get an `OutboundTx` record, `PendingOutbounds` entry, or `OutboundCreatedEvent`, so no TSS signing/broadcast will ever be initiated for the successfully burned/escrowed funds from the other, perfectly valid legs. This is the direct analog of the `forceDeployOnAddresses` bug: an aggregate operation that already externally committed value for multiple items aborts the whole batch on the first item's failure, and the already-spent value for the earlier successful items is never accounted for or recoverable through any user-reachable flow.

### Impact Explanation
This causes permanent loss of user or protocol-controlled funds with no recovery path in the normal (non-privileged) flow: the PRC20 tokens are already burned/moved on the EVM side as part of the executed payload, but the Cosmos module never learns about them as pending outbounds, so they are never delivered to the destination chain, never refunded, and never reflected as `REVERTED`/`ABORTED` for manual rescue. This matches the in-scope impact "unauthorized burn ... or permanent loss of user or protocol-controlled funds" and "corruption of ... canonical UniversalTx state" under the Universal execution / registry pivots.

### Likelihood Explanation
The trigger only requires an unprivileged user to submit a `MsgExecutePayload` (gasless, permissionless per the module's authorization model) whose target contract logic performs multiple cross-chain withdrawals in one EVM transaction, with at least one leg pointing at a chain that is outbound-disabled or a token pair lacking `TokenConfig`. No validator, relayer, or admin collusion is required; this is reachable purely through ordinary payload construction and registry state that a user can probe via read-only queries beforehand.

### Recommendation
Change `BuildOutboundsFromReceipt` to skip/record a failure for the individual invalid outbound event (attaching a revert/rescue-eligible marker for that specific withdrawal) rather than aborting and discarding the entire batch. Successfully-validated outbound events in the same receipt should still be attached and their normal TSS/outbound lifecycle should proceed, while the invalid one is either rejected before the EVM burn (defense at the gateway contract) or funneled into the existing `RESCUE_FUNDS`/revert mechanism instead of being silently dropped.

### Proof of Concept
1. Attacker deploys/uses a contract reachable from their UEA's `executeUniversalTx` payload that, within a single EVM call, invokes `UniversalGatewayPC`'s withdraw path twice: once for a valid, registered `(destChain, PRC20)` pair, and once for a destination chain that is outbound-disabled (or a PRC20 with no `TokenConfig` entry for that source/dest pairing).
2. Attacker submits `MsgExecutePayload` with this payload; the payload executes successfully on the EVM, burning/escrowing PRC20 for both withdrawals and emitting two `UniversalTxOutbound` logs.
3. `ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` calls `AttachOutboundsToExistingUniversalTx` → `BuildOutboundsFromReceipt`, which processes the first (valid) log successfully, appending it to `outbounds`, then hits the second log, fails `IsChainOutboundEnabled`/`GetTokenConfigByPRC20`, and returns `nil, err` — losing the first, valid outbound too.
4. The UTX ends up with an empty `OutboundTx` list and only a `RevertError` string; no TSS signing ever occurs for the first withdrawal despite its tokens already having been burned/escrowed on Push Chain.

func (k Keeper) AttachOutboundsToExistingUniversalTx(
	ctx sdk.Context,
	receipt *evmtypes.MsgEthereumTxResponse,
	utx types.UniversalTx,
) error {
	outbounds, err := k.BuildOutboundsFromReceipt(ctx, utx.Id, receipt)
	if err != nil {
		return err
	}

	return k.attachOutboundsToUtx(ctx, utx.Id, outbounds, "")
}
