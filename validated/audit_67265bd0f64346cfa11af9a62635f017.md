## Title
Missing zero-address check on transfer destinations allows irrecoverable loss of TRX/TRC10 tokens - (`actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`)

### Summary
Similar to the Foundation `FETH.withdrawFrom` bug (funds silently lost when `to == address(0)`), java-tron's `TransferActuator` (and analogously `TransferAssetActuator`) never checks whether the transaction's destination address is the "zero address" (the address consisting of the chain prefix byte followed by all-zero bytes). Because the only address check performed, `DecodeUtil.addressValid`, validates only length and prefix byte and not the semantic validity of the address, a user can broadcast a normal `TransferContract` transaction whose `to_address` is the all-zero address, and the actuator will happily execute the transfer, permanently locking the TRX (or TRC10 asset) at an address with no known private key.

### Finding Description
`TransferActuator.validate()` only validates address format: [1](#0-0) 

`DecodeUtil.addressValid` merely checks that the address is 21 bytes long and starts with the correct chain prefix byte — it performs no check that the remaining 20 bytes are non-zero: [2](#0-1) 

As a result, the all-zero address (`0x41` followed by 20 zero bytes on mainnet) is a "valid" address per this check, even though it is a canonical burn/unspendable address (no known private key controls it — analogous to `address(0)` in Solidity). `TransferActuator.execute()` then unconditionally creates the account (if it doesn't exist) and credits the amount to it: [3](#0-2) 

The same missing check exists in `TransferAssetActuator.validate()`, which validates `toAddress` only via `DecodeUtil.addressValid` before crediting the TRC10 asset balance: [4](#0-3) 

Notably, both actuators already implement an analogous defensive check preventing self-transfers (`Cannot transfer TRX/asset to yourself`), demonstrating the team's awareness of the need to sanity-check the destination address, but the zero-address case was not covered: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any TRX or TRC10 asset sent to the zero address is permanently and irrecoverably lost, since no private key exists to sign a transaction from that address. This is real accounting/value loss reachable directly via a normal, anonymously broadcast `TransferContract`/`TransferAssetContract` transaction — no privileged role is required. While root cause is user/client error (e.g., a wallet bug that zero-fills an unset recipient field, or a user mis-encoding an address to all zeros), the same bug class was judged Medium severity in the original Foundation report because it silently destroys user funds without any error being raised.

### Likelihood Explanation
Likelihood of accidental triggering is plausible in real-world usage (e.g., client-side bugs, malformed address decoding, copy-paste errors producing all-zero bytes) since the zero address passes all existing validation (`DecodeUtil.addressValid`) and the explicit self-transfer guard does not catch it (owner address is never all-zero). No node cooperation or special privileges are needed to trigger the loss.

### Recommendation
Add an explicit check in `TransferActuator.validate()` and `TransferAssetActuator.validate()` (and any other actuators that accept a caller-supplied destination such as `DelegateResourceActuator`/`UnDelegateResourceActuator`/`FreezeBalanceActuator` receiver addresses) rejecting the canonical zero address, e.g.:
```java
byte[] zeroAddress = new byte[]{DecodeUtil.addressPreFixByte}; // padded with 20 zero bytes
if (Arrays.equals(toAddress, zeroAddressBytes)) {
  throw new ContractValidateException("Cannot transfer TRX to the zero address.");
}
```
This mirrors the fix Foundation applied to `FETH.withdrawFrom` (rejecting `to == address(0)`).

### Proof of Concept
1. Construct a `TransferContract` with `owner_address` = a funded account and `to_address` = `0x41` followed by 20 zero bytes (a 21-byte array that passes `DecodeUtil.addressValid`).
2. Broadcast the transaction via the public gRPC/HTTP API.
3. `TransferActuator.validate()` passes (address format valid, not equal to owner address), and `execute()` creates the zero-address account and credits it with the transferred amount.
4. The TRX is now held by an address with no corresponding private key — permanently unspendable/lost. The same PoC applies to `TransferAssetActuator` for TRC10 tokens.
