## Title
Unrecoverable chunk-processing panic on stale `GlobalContractDistribution` receipts after repeated resharding - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs:874-878` calls `.unwrap()` on the result of `Receipt::receiver_shard_id`, which is fallible and returns `Err(EpochError::ShardingError(...))` for `GlobalContractDistribution` receipts whose `target_shard` no longer exists in the current shard layout or its recorded split history. A delayed `GlobalContractDistribution` receipt that outlives two (or more) resharding generations before it is dequeued will trigger this `Err` path and cause an `.unwrap()` panic while applying a chunk, i.e. a full node crash / chunk-processing halt — the same bug class as CVE-2025-45333 (unguarded dereference/unwrap of a value that can be absent, causing a crash), but here reachable by any account that deploys a global contract, not by a malicious peer or validator. [1](#0-0) 

### Finding Description
`Receipt::receiver_shard_id` explicitly documents and implements the failure mode: for a `GlobalContractDistribution` receipt whose `target_shard` is not part of the current `ShardLayout`, it tries `shard_layout.resolve_to_current_shard(target_shard)`, and if that returns `None` (the shard is not resolvable in the current layout's split history) it returns `Err(EpochError::ShardingError(...))` rather than panicking itself: [2](#0-1) 

However, every caller inside `DelayedReceiptQueueWrapper` that needs to decide whether a delayed receipt belongs to the current shard calls this fallible function and immediately `.unwrap()`s it:
```
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
``` [1](#0-0) 

This filter is invoked from `pop` (used every time the runtime drains the delayed-receipt backlog during `Runtime::apply`) and from `peek_iter` (used for contract-preparation lookahead scheduling): [3](#0-2) 

The runtime's own comment on the wrapper explicitly acknowledges that after a `ReshardingV3` split the delayed queue can contain receipts belonging to a sibling shard, and that this discrepancy can persist ("With ReshardingV3, it's possible for a chunk to have delayed receipts that technically belong to the sibling shard before a resharding event"): [4](#0-3) 

`resolve_to_current_shard` can only walk a bounded split history; if a `GlobalContractDistribution` receipt sits in the delayed queue long enough to span two or more resharding generations (chunk saturated so the receipt is repeatedly pushed to the delayed queue instead of processed), the `target_shard` it carries may fall outside what `resolve_to_current_shard` can map, producing `Err`, which the unwrap in `receipt_filter_fn` turns into a panic during `Runtime::apply`. There is a dedicated regression test in the repository that documents this exact scenario and asserts the chain does not stall: [5](#0-4) 

The overall apply flow that reaches this code is: `Runtime::apply` → `process_receipts` → `process_delayed_receipts` → `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn`: [6](#0-5) 

### Impact Explanation
An `.unwrap()` panic inside `Runtime::apply` aborts chunk application for every honest node that reaches this delayed receipt at the same logical point, causing a transaction/receipt-triggered chunk-processing halt across the network (denial of service). Because `GlobalContractDistribution` receipts are generated automatically whenever any account deploys a global contract (`DeployGlobalContract` action) and are then queued/forwarded across shards, an unprivileged contract deployer can create the receipt whose eventual delay (via ordinary chunk/gas saturation across resharding boundaries) triggers this panic — matching the rules' accepted impact of "a transaction-triggered halt."

### Likelihood Explanation
Triggering this requires: (1) submitting a `DeployGlobalContract`/global-contract transaction so a `GlobalContractDistribution` receipt is created and targets a shard that is about to be resharded, and (2) keeping that receipt stuck in the delayed queue (e.g. by saturating chunk compute/gas) across at least two resharding events before it is dequeued. This depends on resharding actually occurring on the network within the receipt's lifetime, which reduces likelihood on networks that reshard rarely, but the repository's own test (`test_global_contract_distribution_survives_multiple_reshardings`-style test) demonstrates this is a concretely reachable sequence using only normal user transactions (contract deploy + gas-burning transactions to saturate chunks), not any validator/operator/network-level privilege.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` (and any other caller of `receiver_shard_id` in the delayed/incoming receipt paths) with proper error propagation, e.g. treat an unresolvable `target_shard` as `StorageError::StorageInconsistentState` (as is already done elsewhere for corrupted delayed receipts) or extend `resolve_to_current_shard` / the shard-layout split history so multi-generation resharding chains remain resolvable indefinitely, then propagate the `Result` out of `receipt_filter_fn`, `pop`, and `peek_iter` instead of unwrapping.

### Proof of Concept
Concrete PoC steps, matching the existing regression test scaffold in the repo:
1. Deploy a global contract from an account located in a shard that will be split by an upcoming dynamic resharding event, generating a `GlobalContractDistribution` receipt targeting that shard.
2. Continuously submit gas-heavy transactions to saturate chunk compute so the distribution receipt is repeatedly pushed into the delayed-receipt queue instead of being processed.
3. Allow two full resharding generations (shard splits) to occur while the receipt remains delayed, so its `target_shard` becomes unresolvable by `resolve_to_current_shard`.
4. Stop saturating and let the delayed queue drain; when the stale receipt is popped, `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn` → `Receipt::receiver_shard_id` returns `Err`, and the `.unwrap()` panics inside `Runtime::apply`, halting chunk production/application.

This scenario is exactly what is exercised (and asserted against) by the existing test: [7](#0-6) 

**Note on uncertainty**: I could not fully retrieve the implementation of `ShardLayout::resolve_to_current_shard` (in `core/primitives/src/shard_layout/mod.rs` / `v3.rs`) within the available tool budget, so I cannot confirm with certainty whether the split-history it tracks is bounded to a fixed depth (making this reachable) or unbounded/self-healing (making the `Err` path effectively dead code that a fix may have already closed off). The presence of a dedicated regression test explicitly describing this exact panic scenario, however, strongly suggests the `Err`/panic path is a real, previously-identified concern in this codebase. Confirming the exact bound would require reading those files directly, which the wiki index did not return content for in this session.

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }
