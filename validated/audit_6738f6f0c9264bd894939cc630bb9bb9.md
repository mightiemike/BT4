### Title
Starknet OS `execute_replace_class` skips the "class must be declared" check performed by Blockifier, causing OS/Blockifier execution divergence - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The Starknet OS Cairo implementation of the `replace_class` syscall writes an attacker-supplied `class_hash` directly into `contract_state_changes` without verifying that a contract class with that hash has actually been declared. The Rust `blockifier` execution engine, which is the reference implementation whose results the OS is meant to faithfully re-execute and prove, performs this check and rejects the call when the class is undeclared. This mirrors the reported bug class: a security-critical identity/existence check ("is this address/hash backed by a real, registered entity") is enforced in one code path but silently skipped in an analogous path that is reachable from an ordinary transaction.

### Finding Description
In the Starknet OS Cairo program, `execute_replace_class` explicitly documents the missing check and proceeds to update state regardless: [1](#0-0) 

Note the comment `// TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.` immediately followed by an unconditional `dict_update` that installs `class_hash` as the contract's new class, with no lookup against the declared-classes table.

By contrast, the blockifier's Rust implementation of the same syscall enforces the check by attempting to read the compiled class for the requested hash, which fails with `StateError::UndeclaredClassHash` if the class was never declared: [2](#0-1) 

The non-deprecated syscall path also delegates to a base implementation (`syscall_handler.base.replace_class`) which performs the same declared-class verification: [3](#0-2) 

This is corroborated by the blockifier's own tests, which assert that replacing with an undeclared class hash fails with "is not declared": [4](#0-3) [5](#0-4) 

Any contract can invoke this syscall directly (e.g. via `replace_class_syscall` in Cairo), meaning the divergent code path is reachable from a single, unprivileged transaction: [6](#0-5) 

### Impact Explanation
The Starknet OS program is executed to re-derive/verify the state transition that the sequencer (blockifier) already computed, and its trace underlies the STARK proof of block validity as well as OS-based re-execution/validation flows. If a transaction calls `replace_class` with an **undeclared** class hash:
- Blockifier (the sequencer's actual execution engine) rejects the call (`UndeclaredClassHash`), causing the call/transaction to revert or fail as appropriate.
- The Starknet OS, lacking the equivalent check, will accept the same call and commit a state diff that sets the contract's class hash to an undeclared value.

This produces a genuine execution divergence between the sequencer's real block execution and the OS's re-execution of that same block, which can result in an incorrect state root/commitment being produced by the OS path, or an OS-generated proof that does not actually correspond to a valid state transition (since a class hash with no matching declared class is not verifiable/executable, e.g. by state readers such as `get_compiled_class`, which explicitly error on undeclared classes: [7](#0-6) ). This falls under "wrong committed root or block hash" / "honest-node divergence" categories.

### Likelihood Explanation
The path is trivially reachable: any account or contract can call `replace_class_syscall(class_hash)` with an arbitrary felt as `class_hash` in a single, ordinary transaction — no special privileges, staking, or operator/proposer role required. The only precondition is that the supplied hash is not an actually-declared class, which is fully attacker-controlled.

### Recommendation
Implement the check in the Starknet OS Cairo `execute_replace_class` (and the analogous deprecated syscall path in `deprecated_execute_syscalls.cairo`) to mirror blockifier: before updating `contract_state_changes`, verify that `class_hash` corresponds to a class that has actually been declared (e.g., via the same declared-classes lookup used elsewhere in the OS, consistent with the `GetContractAddressStateEntry`/state-entry hint infrastructure already used in this function), and fail/abort execution analogously to blockifier's `UndeclaredClassHash` error when it is not. This closes the TODO already flagged in the code and eliminates the OS/blockifier divergence.

### Proof of Concept
1. Deploy any contract exposing a function that calls `replace_class_syscall(class_hash)` with a caller-supplied `class_hash` (e.g. the test contract's `test_replace_class`, as used in blockifier tests: [8](#0-7) ).
2. Submit an invoke transaction calling this function with an arbitrary, never-declared `class_hash` (e.g. `felt!(1234_u16)`, as used in the existing negative test).
3. Observe that when the sequencer executes the transaction via blockifier, the call fails with `UndeclaredClassHash`/"is not declared".
4. Feed the same block/transaction into the Starknet OS re-execution path (`execute_replace_class` in `syscall_impls.cairo`); because the declared-class check is absent (per the TODO at line 902), the OS will accept the syscall and write the undeclared `class_hash` into `contract_state_changes`, diverging from blockifier's actual (failing) execution result.
