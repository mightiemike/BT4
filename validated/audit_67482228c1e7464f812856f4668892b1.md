### Title
Relayer Deposit Stolen via Crafted Failing Meta-Transaction DelegateAction — (`runtime/runtime/src/actions.rs`)

### Summary

In NEAR's meta-transaction (NEP-366) flow, the relayer pays all attached deposits for inner actions. However, when the inner receipt fails on the receiver's shard, the deposit refund is sent to the `predecessor_id` of the inner receipt — which is the **sender** (Alice), not the relayer who actually funded it. A malicious user can deliberately craft a `DelegateAction` with a large attached deposit targeting a call that will fail, causing the relayer to lose the full deposit amount to Alice.

### Finding Description

`apply_delegate_action` in `runtime/runtime/src/actions.rs` constructs the inner receipt as:

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // Alice
    receiver_id: delegate_action.receiver_id().clone(),
    ...
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(), // Relayer
        ...
    }),
});
``` [1](#0-0) 

When this inner receipt fails on the receiver's shard, `refund_unspent_gas_and_deposits` is called. The deposit refund is sent to `receipt.balance_refund_receiver()`, which resolves to `receipt.predecessor_id()` — Alice — because the inner receipt is a `ReceiptEnum::Action` (V1), which has no `refund_to` field:

```rust
pub fn balance_refund_receiver(&self) -> &AccountId {
    self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
}
``` [2](#0-1) 

The deposit refund receipt is then pushed:

```rust
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(),
        deposit_refund,
    ));
}
``` [3](#0-2) 

The relayer's balance was debited for the deposit at transaction-processing time (it is the transaction signer), but the refund flows to Alice. The gas refund correctly goes to the relayer (via `action_receipt.signer_id()`), but the deposit refund does not. [4](#0-3) 

The nearcore documentation explicitly acknowledges this asymmetry:

> "If an inner action requires an attached balance (for example a transfer action) then this balance is taken from the relayer. But what if the transaction fails execution on Bob's shard? At this point, the predecessor is Alice and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard." [5](#0-4) 

The comment in `apply_delegate_action` also acknowledges this:

> "If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction." [6](#0-5) 

### Impact Explanation

A malicious user (Alice) can steal an arbitrary amount of NEAR tokens from any relayer by:
1. Crafting a `DelegateAction` with a `FunctionCall` action carrying a large `deposit` targeting a call that will deterministically fail (e.g., calling a non-existent method on a contract, or a contract that always panics).
2. Submitting the `SignedDelegateAction` to a relayer.
3. The relayer submits the transaction, paying the deposit from its own balance.
4. The inner receipt fails on the receiver's shard.
5. The full deposit is refunded to Alice, not the relayer.

The stolen amount equals the `deposit` field in the inner `FunctionCallAction`, which Alice controls. There is no protocol-level cap on this amount beyond the relayer's balance.

### Likelihood Explanation

Any unprivileged user can construct a `DelegateAction` with an arbitrarily large deposit. Relayers are a standard, documented use case for NEAR meta-transactions. The attack requires no special permissions, no validator access, and no network-level capabilities — only the ability to submit a signed `DelegateAction` to a relayer. The financial incentive is direct and proportional to the deposit size.

### Recommendation

The inner receipt created in `apply_delegate_action` should use `ReceiptEnum::ActionV2(ActionReceiptV2 { refund_to: Some(relayer_id), ... })` so that deposit refunds are directed back to the relayer (the actual payer), not to the sender. The `refund_to` field exists precisely for this purpose in `ActionReceiptV2`. [7](#0-6) 

Alternatively, the protocol could validate that a `DelegateAction`'s inner `FunctionCall` deposit does not exceed what the sender (Alice) can cover from her own balance, preventing the relayer from being exposed to deposit loss.

### Proof of Concept

1. Alice has zero NEAR balance. Relayer has 100 NEAR.
2. Alice crafts a `DelegateAction` with `receiver_id = "some_contract"`, inner action = `FunctionCall { method_name: "nonexistent", deposit: 50 NEAR, gas: 10 TGas }`.
3. Alice signs the `DelegateAction` and sends it to the relayer off-chain.
4. Relayer wraps it in a transaction (relayer is signer), submitting it on-chain. The relayer's balance is debited 50 NEAR (deposit) + gas costs.
5. The inner receipt reaches `some_contract`'s shard. The function call fails (method does not exist).
6. `refund_unspent_gas_and_deposits` fires: `deposit_refund = 50 NEAR`, sent to `receipt.balance_refund_receiver()` = `receipt.predecessor_id()` = Alice.
7. Alice's balance: +50 NEAR. Relayer's balance: −50 NEAR − gas costs.

The relayer loses 50 NEAR to Alice with no recourse at the protocol level.
