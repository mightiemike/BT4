**Analysis:**

The theorized attack relies on `Weak::upgrade()` in `PerInstructionCache::Call` failing non-deterministically due to `Rc` drop timing. This doesn't hold up because:

1. **The strong `Rc` is held for the entire single-threaded execution.** `InterpreterFunctionCaches` is created once per top-level function execution in `MoveVM::execute_loaded_function_with_tracing` at [1](#0-0)  and passed by mutable reference through the entire interpreter loop. Its internal `HashMap<FunctionPtr, Rc<RefCell<FrameTypeCache>>>` retains the strong `Rc` for every function encountered, for the full lifetime of that execution [2](#0-1) .

2. **`PerInstructionCache::Call`/`CallGeneric` only ever store `Weak` copies of that same strong `Rc`**, explicitly to avoid reference cycles for recursive functions (a frame's cache holding a strong ref to itself would leak), as documented in the code comment [3](#0-2) .

3. **There is no code path that removes entries from `function_instruction_caches`/`generic_function_instruction_caches` mid-execution**, and no concurrency: the interpreter is explicitly documented and implemented as single-threaded (`Rc`/`RefCell`, not `Arc`/`Mutex`) [4](#0-3) . Rust's `Rc` drop timing is deterministic based on scope exit, not a race condition — there is no thread or async boundary in this loop where "timing" could vary between runs of identical bytecode with identical inputs.

4. Since the same `FunctionPtr` key is reused for recursive calls to the same function, every recursive call retrieves the same `Rc<RefCell<FrameTypeCache>>` from the map (`get_or_create_frame_cache_non_generic`/`_generic`) [5](#0-4) , so the strong reference backing the `Weak` in `PerInstructionCache::Call` is guaranteed to still be alive whenever `upgrade()` is called during that same execution — the `upgrade()` failure path (`PartialVMError::new_invariant_violation("Frame cache is dropped during interpreter execution")`) at [6](#0-5)  is a defensive invariant check, not a code path reachable via any unprivileged/deterministic bytecode execution pattern.

Because the strong owner (`InterpreterFunctionCaches`) is scoped to outlive the entire single-threaded interpretation of one execution, and Rust drop order is deterministic (not timing/race-dependent) in this synchronous, single-threaded context, there is no mechanism by which identical bytecode under identical inputs could non-deterministically hit the cached vs. non-cached path, and thus no possible divergence in write sets.

use std::{cell::RefCell, collections::HashMap, rc::Rc};

/// Interpreter-level caches for function data (single-threaded)
pub struct InterpreterFunctionCaches {
    function_instruction_caches: HashMap<FunctionPtr, Rc<RefCell<FrameTypeCache>>>,
    generic_function_instruction_caches: HashMap<GenericFunctionPtr, Rc<RefCell<FrameTypeCache>>>,
}

impl InterpreterFunctionCaches {
    pub fn new() -> Self {
        Self {
            function_instruction_caches: HashMap::new(),
            generic_function_instruction_caches: HashMap::new(),
        }
    }

    pub(crate) fn get_or_create_frame_cache(
        &mut self,
        function: &LoadedFunction,
    ) -> Rc<RefCell<FrameTypeCache>> {
        if function.ty_args.is_empty() {
            self.get_or_create_frame_cache_non_generic(function)
        } else {
            self.get_or_create_frame_cache_generic(function)
        }
    }

    /// Returns existing cache, or creates a new one for a non-generic function.
    pub(crate) fn get_or_create_frame_cache_non_generic(
        &mut self,
        function: &LoadedFunction,
    ) -> Rc<RefCell<FrameTypeCache>> {
        debug_assert!(function.ty_args().is_empty());

        let ptr = FunctionPtr::from_loaded_function(function);
        self.function_instruction_caches
            .entry(ptr)
            .or_insert_with(|| FrameTypeCache::make_rc_for_function(function))
            .clone()
    }
