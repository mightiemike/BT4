### Title
Unbounded duplicate-ID growth in `KVSessionStorage` shop index due to missing uniqueness check - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
The `@shopify/shopify-app-session-storage-kv` adapter's `addShopIds()` helper appends a session ID to the shop's session-index array on every call to `storeSession()` without checking whether that ID is already present in the array. Because session IDs for a given shop (offline sessions) or shop+user (online sessions) are deterministic and get re-stored repeatedly during normal token-exchange/refresh flows, the per-shop index array grows with duplicate entries indefinitely. This mirrors the reported bug class: a collection that should contain unique entries is mutated by unconditional appends, distorting/degrading the data structure that depends on it (here, an unbounded storage-growth/DoS condition instead of a distorted median).

### Finding Description
`addShopIds` unconditionally concatenates new IDs into the existing array read from KV, with no de-duplication: [1](#0-0) 

This is called from `storeSession` on every store, with no check for whether the session already exists in the shop's list: [2](#0-1) 

For comparison, the sibling `RedisSessionStorage` adapter explicitly guards against this by checking `includes()` before pushing: [3](#0-2) 

Session IDs are deterministic, not random, for both offline and (embedded) online sessions: [4](#0-3) 

`storeSession` on the *same deterministic ID* is re-invoked from the unauthenticated/merchant-triggered token-exchange authentication path whenever the cached session is missing or nearing expiry (a routine occurrence, since online tokens are short-lived and re-authentication happens on essentially every embedded-admin page load): [5](#0-4) [6](#0-5) 

Each such call re-adds the same ID to the KV shop index without checking for duplicates, so the array for that shop key grows monotonically over the life of the installation.

### Impact Explanation
Over the app's lifetime, a given shop's index key in Workers KV accumulates an ever-growing list of duplicate session IDs (bounded only by KV's per-value size limit). This causes:
- Unbounded growth of the stored JSON array for `findSessionsByShop`, degrading performance of that lookup (each call to `findSessionsByShop` does a `Promise.all` over every listed ID, including duplicates).
- Eventually this can hit KV per-key value size limits, resulting in write failures / storage exhaustion for that shop — effectively a Denial of Service condition against the session-storage/lookup path for that tenant.
- No cross-tenant leakage occurs since IDs stay scoped by shop, but the affected shop's session storage degrades or fails over time, purely from routine, unauthenticated re-authentication traffic (anyone triggering the app's normal token-exchange flow repeatedly, e.g., a merchant reloading the embedded app, drives this).

### Likelihood Explanation
High, in the sense that it requires no attacker action beyond normal usage: every time an offline or online session for a shop needs to be (re-)stored via the standard token-exchange authenticate path (which is the default/only flow for embedded apps with token exchange enabled), the same deterministic session ID is appended again. This is a routine, automatically-triggered code path, not one requiring privileged access, so it will occur naturally on any production app using the KV session storage adapter.

### Recommendation
In `KVSessionStorage.addShopIds` (`packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`), de-duplicate before writing, mirroring the Redis adapter's approach — e.g. merge the new IDs into a `Set` (or check `includes()`) before serializing and storing the array, so repeated `storeSession` calls for the same session ID do not keep appending duplicate entries.

### Proof of Concept
1. Configure an embedded app with `@shopify/shopify-app-session-storage-kv` as `sessionStorage` and token exchange enabled.
2. As a merchant, reload the embedded admin app (or otherwise trigger session re-authentication) multiple times after the online/offline session becomes inactive/near-expiry (this happens routinely, e.g. every online-token expiry cycle).
3. Each reload runs `authenticate()` in `token-exchange.ts`, which calls `config.sessionStorage.storeSession(offlineSession)` (and `onlineSession` if online tokens are used) using the same deterministic session ID for that shop/user.
4. Inspect the KV value at `shop:<shop-domain>` (`getShopSessionIdsKey`) — it will contain the same session ID repeated once per re-authentication, growing without bound as usage continues, since `addShopIds` never checks for existing entries before appending.

    const key = this.getShopSessionIdsKey(shop);
    const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
    await this.namespace.put(key, JSON.stringify([...shopIds, ...ids]));
