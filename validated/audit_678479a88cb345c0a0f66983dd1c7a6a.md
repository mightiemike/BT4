### Title
Missing `TokenConfig.Enabled` check in `depositPRC20` allows minting of disabled/restricted PRC20 tokens - (File: x/uexecutor/keeper/handler.go)

### Summary
`TokenConfig` has an `Enabled` field explicitly documented as "Whether this token is enabled for minting/bridging" [1](#0-0) , mirroring the two-flag restriction model in the Neutrl bug (`SOFT_RESTRICTED` vs `FULL_RESTRICTED`). However, `depositPRC20` — the function that mints PRC20 into a recipient for every inbound and CEA execution path — only calls `GetTokenConfig` to fetch the `NativeRepresentation.ContractAddress`, and never inspects `tokenConfig.Enabled` before calling `CallPRC20Deposit`.

### Finding Description
`depositPRC20` in `x/uexecutor/keeper/handler.go` fetches the token config and immediately proceeds to mint, with no gate on the `Enabled` field: [2](#0-1) 

This function is the single deposit chokepoint used by every inbound execution flow — standard inbound (`ExecuteInboundFundsAndPayload`), the CEA UEA path, the CEA non-UEA/smart-contract path, and the gas-and-payload variant — all of which call `k.depositPRC20(...)` directly with attacker/validator-observed `SourceChain`/`AssetAddr`/`Amount` fields [3](#0-2) .

If an admin ever disables a token (e.g., after discovering a compromised bridge asset, a token needing to be paused, or a token exceeding risk limits) by only flipping `Enabled=false` on the `TokenConfig` (rather than deleting/removing the whole config via `MsgRemoveTokenConfig`), inbound deposits for that token continue to succeed and mint PRC20 unabated, because the only enforced condition is chain-level `IsInboundEnabled`/`IsOutboundEnabled` [4](#0-3) , not token-level `Enabled`.

### Impact Explanation
This corrupts intended token-accounting invariants: a token flagged `Enabled=false` should not be mintable/bridgeable per the field's own documented semantics, yet the deposit path silently ignores it. In line with the Push Chain allowed-impact gate, this could result in "unauthorized mint" of PRC20/native asset accounting for an asset the registry has explicitly marked as disabled.

### Likelihood Explanation
I could not verify from the indexed code whether the admin's operational practice is to always use `MsgRemoveTokenConfig` instead of toggling `Enabled=false`, nor whether some other validation step (in `ValidateForExecution`, `MsgAddTokenConfig`/`MsgUpdateTokenConfig` validation, or ballot finalization) independently blocks disabled tokens before `depositPRC20` is reached. My searches did not surface any such check (`grep_search` for `.Enabled` inside `x/uexecutor/**` only matched unrelated `ChainEnabled` usages in `msg_execute_payload.go` and `msg_migrate_uea.go`), but the index has size limits and full call-graph verification requires reading the complete file contents of `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`, and `x/uregistry/keeper/keeper.go` in full, which I could not do within the remaining iterations. This is also an admin-driven precondition (the token must first be disabled) rather than a fully unprivileged attacker path, which weakens strict alignment with the "unprivileged attacker" framing.

### Recommendation
Add an explicit `tokenConfig.Enabled` check in `depositPRC20` (and any other PRC20-minting call sites that read `TokenConfig`) that fails the deposit (routing to the existing FAILED-PCTx/revert path) when the token is disabled, mirroring the existing `IsChainInboundEnabled` gate pattern already used in `VoteInbound`.

### Proof of Concept
Not independently reproduced against a running node — this would require: (1) registering a chain + token config with `Enabled=true`, (2) admin flips `Enabled=false` via `MsgUpdateTokenConfig`, (3) submitting a normal `MsgVoteInbound` quorum for that same `AssetAddr`, and (4) observing that `depositPRC20`/`CallPRC20Deposit` still mints PRC20 to the recipient despite `Enabled=false`. I was not able to execute this against the test harness (`test/integration/uexecutor/*`) within this session; the closest existing test (`execute_inbound_gas_test.go` "GAS inbound with missing token config records FAILED PCTx") only tests the *missing*-config case, not the *disabled*-config case, which supports the absence of an existing guard but does not by itself confirm the vulnerable code path end-to-end.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
