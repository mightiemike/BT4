### Title
Meta-transaction (delegate action) deposit refunds route to the malicious sender instead of the relayer who funded them - (File: `runtime/runtime/src/actions.rs`)

### Summary
Meta transactions (NEP-366) let a relayer submit a `DelegateAction`/`DelegateActionV2` signed by another account ("sender") and pay all gas and attached deposits on its behalf. When the inner action receipt is spawned by `apply_delegate_action`, the new receipt's `predecessor_id` is set to the *sender's* account, not the relayer. If that inner receipt later fails, the protocol's default deposit-refund rule sends the refunded balance to the receipt's `predecessor_id` — i.e. to the sender, even though the relayer actually paid the deposit. This is structurally the same bug class as the ZetaChain finding: the party credited on failure/refund is the wrong principal (the party that merely "triggered"/signed the action) rather than the party that actually supplied the funds (the relayer/intermediary), enabling value theft from the funder.

### Impact Explanation
Any unprivileged account can act as the "sender" in a meta transaction: it crafts a `DelegateAction`/`SignedDelegateAction` whose inner actions carry a deposit that the relayer is expected to pay, targeting an inner action/receiver that the sender knows (or can force) will fail on the receiver's shard (e.g. targeting a non-existent method, a contract that will reject the call, or a receiver near its storage-staking limit). Because the resulting action receipt's `predecessor_id` equals the sender (not the relayer), the entire attached deposit — funded by the relayer — is refunded back to the sender rather than to the relayer that paid for it. This is a direct, unauthorized value transfer from the relayer to the meta-transaction signer: concrete theft of funds satisfying the "unauthorized value movement" acceptance criterion. Any relayer service (a common, expected component of the meta-transaction ecosystem) is a victim reachable purely through a single submitted transaction/signed delegate action from an ordinary account — no privileged, validator, or network-level position is required.

### Likelihood Explanation
High. No special privileges, timing races, or validator collusion are needed — a normal user account only needs to sign a `DelegateAction` whose inner action is guaranteed (or highly likely) to fail on the receiver's shard while carrying an attached deposit. Relayers that offer generic transaction sponsorship for arbitrary actions (rather than tightly whitelisting deposit-bearing calls) are directly exposed, and the docs themselves flag this as a known incentive problem, i.e. this is not a hypothetical edge case but an accepted architectural gap that any relayer operator must currently defend against purely through off-chain trust/whitelisting.

### Recommendation
- When spawning the inner receipt from a `DelegateAction`, set `refund_to` (via `ActionReceiptV2`) to the relayer's account id (the actual predecessor/signer of the outer transaction that paid the deposit), so `balance_refund_receiver()` returns the relayer instead of defaulting to `sender_id`.
- Alternatively/additionally, require relayers to explicitly opt into deposit-bearing delegate actions or reject inner actions carrying deposits by default, closing the gap without a protocol change, until the `refund_to` fix ships.
- Update `docs/architecture/how/meta-tx.md` accordingly once the protocol-level fix is in place, since it currently documents this as expected relayer-side risk rather than a defect to be fixed.

### Proof of Concept
1. Deploy a relayer service that accepts arbitrary `SignedDelegateAction`s from users and forwards them in a transaction it signs (paying gas + deposit), as shown in the meta-tx test harness.
2. As "Alice" (any unprivileged account), craft a `DelegateAction` with `sender_id = Alice`, `receiver_id = Bob`, and an inner action (e.g. `FunctionCall` with a `deposit` and a `method_name` that does not exist on `Bob`, or any action guaranteed to fail after the deposit action_receipt is created) — see the pattern in [6](#0-5)  for how a failing function call with a deposit is constructed.
3. Sign it and hand it to the relayer, which wraps it in a transaction it signs and submits (paying the deposit).
4. On `Bob`'s shard, the inner action fails. Runtime's `refund_unspent_gas_and_deposits` calls `Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund)`, and since the receipt created in `apply_delegate_action` has `predecessor_id = Alice` and no `refund_to` override, the deposit is refunded to Alice — not to the relayer that actually funded the deposit.
5. Alice's balance increases by the deposit amount the relayer paid for, while the relayer's balance is permanently reduced by that amount: unauthorized value transfer from relayer to sender.

    pub fn refund_to(&self) -> &Option<AccountId> {
        match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseResume(_)
            | ReceiptEnum::GlobalContractDistribution(_) => &None,
            ReceiptEnum::ActionV2(action_receipt_v2)
            | ReceiptEnum::PromiseYieldV2(action_receipt_v2) => &action_receipt_v2.refund_to,
        }
    }

    pub fn balance_refund_receiver(&self) -> &AccountId {
        self.refund_to().as_ref().unwrap_or_else(|| self.predecessor_id())
    }

```markdown
## Balance refunds in meta transactions

Unlike gas refunds, the protocol sends balance refunds to the predecessor
(a.k.a. sender) of the receipt. This makes sense, as we deposit the attached
balance to the receiver, who has to explicitly reattach a new balance to new
receipts they might spawn.

In the world of meta transactions, this assumption is also challenged. If an
inner action requires an attached balance (for example a transfer action) then
this balance is taken from the relayer.

The relayer can see what the cost will be before submitting the meta transaction
and agrees to pay for it, so nothing wrong so far. But what if the transaction
fails execution on Bob's shard? At this point, the predecessor is `Alice` and
therefore she receives the token balance refunded, not the relayer. This is
something relayer implementations must be aware of since there is a financial
incentive for Alice to submit meta transactions that have high balances attached
but will fail on Bob's shard.
```
