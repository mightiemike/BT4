### Title
`VerifyTransferProof.execute` ignores `countDownLatch.await()` timeout result and still blocks on `future.get()`, bypassing the CPU-time budget enforced elsewhere - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
In `VerifyTransferProof.execute`, the code computes `withNoTimeout = countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS)` but never checks the result before unconditionally calling `future.get()` on every submitted sapling-verification task. This is inconsistent with the sibling precompile `BatchValidateSign.doExecute`, which explicitly throws `Program.Exception.notEnoughTime(...)` when `withNoTimeout` is `false` before touching any future.

### Finding Description
`getCPUTimeLeftInNanoSecond()` (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:481-488`) returns the remaining CPU-time budget for the current call, throwing `Program.Exception.notEnoughTime` if it is already exhausted. `VerifyTransferProof.execute` (lines ~1559-1611) submits up to 5 native `librustzcash` verification tasks (`SaplingCheckSpendTask`, `SaplingCheckOutputTask`, `SaplingCheckBingdingSig`) to a thread pool, then does:

```java
boolean withNoTimeout = countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS);
boolean checkResult = true;
for (Future<Boolean> future : futures) {
  boolean eachTaskResult = future.get();
  checkResult = checkResult && eachTaskResult;
}
``` [1](#0-0) 

The `withNoTimeout` boolean is computed but never used to gate execution. If the latch times out (the sapling native verification hasn't finished within the CPU budget allotted by `vmShouldEndInUs`), the loop still calls `future.get()` on each pending future, which blocks until the underlying task actually completes — with no bound related to the CPU-time budget. This is a design regression compared to `BatchValidateSign.doExecute`, which correctly aborts via `Program.Exception.notEnoughTime` when its own `withNoTimeout` is `false`: [2](#0-1) 

The remaining catch blocks in `execute` only catch `InterruptedException` and generic `Throwable` for logging, and never re-raise a "not enough time" style exception derived from the ignored `withNoTimeout` flag. [3](#0-2) 

Attacker path: any unprivileged account can submit a shielded-TRC20 transfer transaction that reaches this precompile (`VerifyTransferProof.execute`) through the TVM shielded-contract call path, since `getEnergyForData` charges a flat 200000 energy regardless of the number of spends/outputs (`spendCount`/`receiveCount` up to 2 each) — there is no cost differentiation based on actual verification cost, and no code path stops execution once the CPU deadline passes mid-`future.get()`.

### Impact Explanation
Because the timeout check result is discarded, an attacker can craft `VerifyTransferProof` calls (via shielded transfer transactions) issued when the CPU budget for the call is nearly exhausted (e.g., due to prior heavy operations in the same transaction/block, or naturally slow verification on a loaded/slower node) so that `countDownLatch.await()` returns `false`, yet the code proceeds to `future.get()` and blocks until the native zk-SNARK checks actually finish — potentially well beyond the CPU time the VM/consensus scheduling intended to allot to that call. This breaks the CPU-time governance mechanism that is otherwise consistently enforced elsewhere (e.g. `MUtil.checkCPUTime`, `BatchValidateSign`), and can cause a node to spend more wall-clock/CPU time processing a block than intended, risking block-processing/liveness degradation under load, particularly if repeated across many shielded transactions in a block.

### Likelihood Explanation
The precondition is simply constructing a valid shielded-transfer TVM call (any account can call the `VerifyTransferProof` precompile through a shielded TRC20 contract) at a point where the remaining CPU budget for that call is small. This is fully reachable by an unprivileged attacker with normal transaction/contract construction — no admin, governance, or off-chain access is required. However, the actual verification result (`checkResult`) is a deterministic pure function of the input bytes via `librustzcash`, so this bug does not by itself cause consensus divergence in the boolean outcome; the practical effect is a latent, un-enforced CPU-time budget for this specific precompile, i.e., a potential CPU-time/DoS amplification vector rather than value theft or state corruption.

### Recommendation
Mirror the pattern used in `BatchValidateSign.doExecute`: check `withNoTimeout` immediately after `countDownLatch.await(...)` and, if `false`, throw `Program.Exception.notEnoughTime("call VerifyTransferProof precompile method")` before iterating over `futures`, instead of unconditionally calling `future.get()`.

### Proof of Concept
```java
// framework/src/test/java/org/tron/common/runtime/vm/PrecompiledContractsVerifyProofTest.java
@Test
public void verifyTransferProofTimeoutIsEnforced() throws Exception {
  VerifyTransferProof transferContract = new VerifyTransferProof();
  // Build a valid-size transfer proof input (see abiEncodeForTransfer helpers in this test file)
  byte[] inputData = abiEncodeForTransfer(/* ... valid params ... */);

  // Simulate an almost-exhausted CPU budget: set vmShouldEndInUs so that
  // getVmShouldEndInUs() * 1000 - System.nanoTime() is a tiny positive number,
  // e.g. a few microseconds, guaranteeing countDownLatch.await() times out
  // before the native librustzcash verification tasks complete.
  transferContract.setVmShouldEndInUs((System.nanoTime() / 1000) + 1); // ~1us left

  long start = System.nanoTime();
  Pair<Boolean, byte[]> result = transferContract.execute(inputData);
  long elapsed = System.nanoTime() - start;

  // Expected (fixed) behavior: execute() should throw Program.Exception.notEnoughTime
  // or otherwise abort quickly, bounded roughly by the CPU budget granted.
  // Current (buggy) behavior: execute() blocks via future.get() until the native
  // verification finishes, so elapsed time can be orders of magnitude larger
  // than the CPU budget that was configured.
  Assert.assertTrue("execution exceeded CPU budget without aborting",
      elapsed < TimeUnit.MILLISECONDS.toNanos(50)); // fails today, demonstrating the bug
}
```
This test asserts that verification either fails deterministically (throws a timeout exception) or completes within the configured CPU budget; today it fails because `execute()` silently ignores `withNoTimeout=false` and blocks on `future.get()` regardless.
