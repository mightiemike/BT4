### Title
Nonce account full-withdrawal path uses an exact-equality balance check that any actor can grief via donation, causing a DoS on `WithdrawNonceAccount` - (File: programs/system/src/system_instruction.rs)

### Summary
`withdraw_nonce_account` decides between a "full close" path and a "partial withdrawal" path solely by comparing the requested `lamports` against the account's *current* lamport balance with strict equality (`lamports == from.get_lamports()`). Because any unprivileged actor can increase a nonce account's lamport balance via an ordinary system transfer (nonce accounts are owned by the System Program and accept lamports from anyone), an attacker can break this equality just before a legitimate "close and withdraw all" transaction lands, forcing the instruction into the partial-withdrawal branch, which then requires leaving the full rent-exempt minimum behind — causing the honest withdrawal to fail with `InsufficientFunds`.

### Finding Description
In `programs/system/src/system_instruction.rs`, the `Initialized` branch of `withdraw_nonce_account` is: [1](#0-0) 

If the caller's requested `lamports` exactly equals `from.get_lamports()`, the code treats this as a full-close (allowing the account to be fully drained and set to `Uninitialized`), skipping any rent-exempt minimum requirement. Otherwise (the `else` branch), it treats the request as a partial withdrawal and enforces that `lamports + rent.minimum_balance(...)` must not exceed the current balance — i.e., the rent-exempt minimum must remain.

A nonce account is owned by the system program and, like any system account, can receive lamports from an ordinary `system_instruction::transfer` sent by anyone, without requiring the nonce authority's signature. An attacker who observes (or predicts) a pending `WithdrawNonceAccount` instruction requesting the account's full current balance can front-run it with a tiny donation (e.g., 1 lamport) to the nonce account. This changes `from.get_lamports()` so it no longer equals the `lamports` value baked into the honest transaction, causing execution to fall into the `else` branch. There, the check `lamports + min_balance > from.get_lamports()` will now virtually always fail (since `min_balance` for a nonce account, sized for `NonceState`, is much larger than the 1-lamport donation), yielding `InstructionError::InsufficientFunds` and reverting the withdrawal/close.

This is precisely the reported bug class ("weak condition"/`Comparison.EQUAL` on a token/asset balance that can be trivially manipulated by any actor for a DoS): the security-relevant branch decision hinges on an externally-influenceable exact balance value rather than a range/threshold comparison.

### Impact Explanation
An attacker can repeatedly and cheaply (1 lamport + fee per attempt) block any user's attempt to fully close/drain their nonce account via `WithdrawNonceAccount`, forcing the transaction to fail every time it is retried with the same "withdraw exact current balance" amount. This is a persistent, low-cost griefing/DoS vector against normal wallet and CLI flows that close nonce accounts (e.g., `solana authorize-nonce-account`/`withdraw-from-nonce-account` closing flows), since the client typically fetches the current balance and submits a withdrawal for that exact figure between when it reads the balance and when the transaction lands — an attack window the adversary can always win with a front-run.

### Likelihood Explanation
High likelihood: the precondition (attacker being able to send an arbitrary system transfer to any public nonce account address) requires no special privilege, and nonce account addresses/pending withdraw amounts are observable on-chain or via mempool/RPC. The attack is cheap (dust transfer), repeatable, and does not require the attacker to interact with the nonce authority at all.

### Recommendation
Do not use exact equality between the requested amount and the current balance to select the full-close vs. partial-withdraw path. Instead:
- Determine "full close" based on whether the resulting balance after withdrawal would be zero (`from.get_lamports().checked_sub(lamports) == Some(0)`), or
- Always compute the effective minimum required to remain (0 if fully closing, else rent-exempt minimum) based on the *post-withdrawal* balance rather than pre-withdrawal equality, so that incidental balance inflation by third parties does not change which branch — and which minimum-balance requirement — applies.

### Proof of Concept
1. Client A creates and funds a nonce account with balance `B` and later wants to fully withdraw/close it by submitting `SystemInstruction::WithdrawNonceAccount` with `lamports = B` (as read from RPC).
2. Attacker observes the nonce account address (public) and, before A's transaction lands, submits an ordinary `system_instruction::transfer` sending 1 lamport to the nonce account, making its balance `B + 1`.
3. A's transaction executes: in `withdraw_nonce_account`, `lamports (B) == from.get_lamports() (B + 1)` is `false`, so execution falls into the `else` branch at [2](#0-1) .
4. `amount = B + min_balance > B + 1` (since `min_balance` for `NonceState::size()` far exceeds 1 lamport), so the instruction returns `InstructionError::InsufficientFunds`, and A's intended full-withdrawal/close fails despite A having sufficient funds prior to the attacker's donation.
