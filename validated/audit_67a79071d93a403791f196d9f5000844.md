**Analysis:**

The behavior described is intentional, not exploitable state corruption.

In `native_public_key_validate`, wrong-length keys either abort with `E_WRONG_PUBKEY_SIZE` or return `Ok(false)`, depending on whether the `ED25519_PUBKEY_VALIDATE_RETURN_FALSE_WRONG_LENGTH` feature flag is enabled — this is a deliberate, versioned behavior change gated by a governance-controlled feature flag, not an attacker-controlled toggle. [1](#0-0) 

A key that has the correct length (32 bytes) but fails to decompress (i.e., is not a valid curve point) always returns `Ok(smallvec![Value::bool(false)])`, never an abort. [2](#0-1) 

These two code paths are functionally distinct by design: one is a length-validation error (structurally malformed input, independent of point math) and the other is a valid-length-but-invalid-point error. The Move caller, `new_validated_public_key_from_bytes`, only interprets the boolean return value (`false` → `option::none`); an abort short-circuits the transaction with a distinct `MoveAbort` status instead. [3](#0-2) 

This divergence is:
1. **Deterministic across all validators** — every node executes the identical native code against the identical, network-wide-activated feature flag state, so there is no possibility of two honest nodes computing different `TransactionInfo` status values for the same input and flag configuration. It is not a hard-fork risk introduced by unprivileged input; it's consensus-consistent behavior.
2. **Already documented/intended** — the feature flag `ED25519_PUBKEY_VALIDATE_RETURN_FALSE_WRONG_LENGTH` exists precisely to control this abort-vs-false behavior across a network upgrade, meaning the "inconsistency" is a known, versioned API behavior rather than a bug that corrupts committed state, proofs, or authenticated responses.
3. **Not a proof/storage integrity issue** — the resulting `MoveAbort` or `Executed` status is exactly what the VM legitimately produces for that input; it gets committed to the transaction info correctly and consistently, so there's no misbinding of write sets, proofs, roots, or versions.

Since an unprivileged caller cannot force disagreement between honest validators, cannot corrupt proof material, and cannot misbind any authenticated response — and the differing statuses are the documented, feature-flag-gated design rather than an unintended divergence — this does not meet the state-integrity/proof-integrity bar required for acceptance.
