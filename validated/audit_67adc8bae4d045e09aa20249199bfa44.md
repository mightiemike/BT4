## Title
Proof-manager `set_proof`/`contains_proof` trust an unauthenticated, attacker-supplied `proof_facts` hash as an integrity root, letting a resubmitted `proof_facts` skip cryptographic proof verification - ([File: crates/apollo_transaction_converter/src/transaction_converter.rs])

### Summary
The circular-trust root cause in the nginx-ui advisory — integrity of attacker-controlled content is checked against metadata that is itself derived from that same attacker-controlled content, so re-verification is skipped once a matching entry "already exists" — has a structural analog in the sequencer's client-side-proving flow. `TransactionConverter::run_proof_verification` decides whether to cryptographically verify a submitted `(proof_facts, proof)` pair purely by asking the proof manager "does an entry already exist for `proof_facts.hash()`?" If yes, verification is skipped entirely, and the proof manager's `set_proof`/`contains_proof` never check that the specific `proof` bytes supplied by the current sender actually match/verify against `proof_facts` — existence of *any* prior entry under that hash is treated as sufficient attestation.

### Finding Description
`ProofFacts::hash()` is computed from attacker-supplied public inputs and is used as the sole key for the proof store (`FsProofStorage`, keyed by `facts_hash`) [1](#0-0) .

`ProofManager::set_proof` short-circuits and returns `Ok(())` without writing/overwriting anything if `contains_proof` is already true for that `facts_hash` — it never compares the newly submitted `proof` bytes to whatever is already stored: [2](#0-1) 

`TransactionConverter::run_proof_verification`, which is the sole gate deciding whether `starknet_proof_verifier::verify_proof` is ever invoked for a gateway-submitted transaction, uses exactly this same existence check to skip cryptographic verification of the proof that accompanies the current transaction: [3](#0-2) 

This is invoked from both the gateway path (`spawn_proof_verification`) and the consensus path (`spawn_verify_and_store_proof`): [4](#0-3) 

The pattern mirrors the nginx-ui bug precisely: instead of an independent, per-request cryptographic check of the attacker-supplied artifact, the system treats "an entry already exists under a hash the attacker controls" as proof of validity, and never verifies that the *currently supplied* content is the one that was actually verified. An unprivileged transaction sender fully controls both `proof_facts` and `proof` in an RPC Invoke V3 transaction, so this is directly reachable from the gateway's `add_tx` path with no special privileges — `check_declare_permissions`/`stateless_tx_validator.validate` do not perform proof verification; that happens later in `convert_rpc_tx_to_internal_and_executable_txs` → `spawn_proof_verification` → `run_proof_verification` [5](#0-4) .

### Impact Explanation
If an attacker can cause an entry to exist under a `proof_facts` hash (e.g., by first submitting a transaction with valid proof_facts/proof that gets legitimately verified and stored, or through any race/duplicate-submission path), any subsequent transaction reusing that same `proof_facts` hash together with a *different, unverified/bogus* `proof` will skip cryptographic verification entirely (`contains_proof == true` → `Ok(false)` → verification never runs), yet the transaction still proceeds through the gateway/converter flow as if the proof had been validated. Since `proof_facts` encode consensus-relevant claims (proof version, virtual-OS program hash, block hash/number, config hash — see `validate_proof_facts` in blockifier) that downstream code trusts as pre-validated once a `VerificationHandle` returns `Ok`, this can let an unprivileged sender get a transaction admitted to the mempool/executed as if it carried a valid client-side proof when it does not, i.e., an unauthorized bypass of the cryptographic proof-verification gate that the whole client-side-proving mechanism depends on for correctness. This is a state-integrity/unauthorized-action class issue analogous to the reported CWE-347/CWE-354 (improper verification of cryptographic signature/integrity check).

### Likelihood Explanation
Reachable by a single unprivileged RPC transaction sender with no special permissions: the only precondition is that a `proof_facts` hash collide with (or reuse) an entry that already exists in the proof store. Because `ProofFacts::hash()` is a value the attacker fully controls (it's derived only from attacker-supplied felts), and because the store's "already contains" check is the entire gate for skipping verification with no secondary equality/authenticity check on `proof`, exploitability depends only on being able to produce/observe a `proof_facts` value whose hash is already present (trivial if the attacker submitted the original verified proof themselves, or if `proof_facts` values are ever reused/observable across transactions, e.g., via mempool broadcast, GCS proof archive object names `proofs/{facts_hash}`, or simply resubmitting their own previously-accepted `proof_facts`).

### Recommendation
- Do not use "entry exists" as a substitute for verifying the exact proof supplied in the current request. `set_proof`/`run_proof_verification` should verify equality of the newly supplied `proof` against the stored value (or always re-verify) rather than trusting presence alone.
- Bind the proof-store key to a hash that includes both `proof_facts` and a commitment to the verified `proof`, so a different `proof` cannot silently reuse the stored acceptance state of a prior verification.
- Consider always performing `verify_proof` for gateway-submitted transactions rather than skipping based on `contains_proof`, reserving the cache/dedup optimization only for identical `(proof_facts, proof)` pairs verified via content hash, not `proof_facts` hash alone.

### Proof of Concept
1. Submit a valid Invoke V3 transaction with `proof_facts = F` and a genuine `proof = P` that passes `starknet_proof_verifier::verify_proof`. The gateway calls `run_proof_verification`, which sees `contains_proof(F) == false`, verifies `P` against `F`, and then `store_proof_and_spawn_archiving` stores `(F, P)` via `ProofManager::set_proof`.
2. Submit a second Invoke V3 transaction with the same `proof_facts = F` but an arbitrary/forged `proof = P'` (never cryptographically verified).
3. In `run_proof_verification`, `contains_proof(F)` now returns `true`, so the function returns `Ok(false)` immediately — `starknet_proof_verifier::verify_proof` is never called on `P'`.
4. The gateway proceeds to treat the transaction as having a validly verified client-side proof (per `run_proof_verification`'s early return path) [6](#0-5) , and `ProofManager::set_proof(F, P')` also no-ops due to the existence check [7](#0-6) , so the tampering is silently absorbed without ever validating `P'`.

**Uncertainty**: I could not fully trace whether `proof_facts` values are cryptographically bound elsewhere (e.g., tied to `tx_hash` or signature) in a way that would prevent an attacker from ever reusing another sender's `proof_facts`, nor could I confirm from the indexed code whether `ProofFacts::hash()` includes any sender-specific salt. If `proof_facts` are effectively single-use/sender-bound by construction elsewhere in the stack, the practical exploitability would be reduced to the case where the *same* sender resubmits their own previously-verified `proof_facts` with a different `proof` — still a verification-bypass but with lower blast radius. A full assessment would benefit from reviewing `ProofFacts::hash()`'s implementation and any binding between `proof_facts` and transaction signature/sender that I was unable to locate within the indexed snippets.

    async fn run_proof_verification(
        proof_facts: ProofFacts,
        proof: Proof,
        proof_manager_client: SharedProofManagerClient,
    ) -> Result<bool, TransactionConverterError> {
        let contains_proof = proof_manager_client.contains_proof(proof_facts.clone()).await?;

        if contains_proof {
            return Ok(false);
        }

        let proof_facts_hash = proof_facts.hash();
        let verify_start = Instant::now();
        tokio::task::spawn_blocking(move || {
            starknet_proof_verifier::verify_proof(proof_facts, proof)
        })
        .await
        .expect("proof verification task panicked")?;
        let verify_duration = verify_start.elapsed();
        PROOF_VERIFICATION_LATENCY.record(verify_duration.as_secs_f64());
        info!(
            "Proof verification took: {verify_duration:?} for proof facts hash: \
             {proof_facts_hash:?}"
        );

        Ok(true)
    }

    /// Spawns a verification-only task. Used by the gateway flow, which stores the proof
    /// separately after all validations pass.
    fn spawn_proof_verification(
        &self,
        proof_facts: ProofFacts,
        proof: Proof,
    ) -> TransactionConverterResult<VerificationHandle> {
        let pmc = self.proof_manager_client.clone();
        let task_proof_facts = proof_facts.clone();
        let task_proof = proof.clone();
        let verification_task = tokio::spawn(async move {
            Self::run_proof_verification(task_proof_facts, task_proof, pmc).await?;
            Ok(())
        });
        Ok(VerificationHandle { proof_facts, proof, verification_task })
    }

    /// Spawns a single task that verifies the proof and then stores it in the proof manager.
    /// Used by the consensus flow, where tasks run concurrently with batcher execution and
    /// are awaited at fin.
    fn spawn_verify_and_store_proof(
        &self,
        proof_facts: ProofFacts,
        proof: Proof,
    ) -> VerifyAndStoreProofTask {
        let pmc = self.proof_manager_client.clone();
        let proof_facts_hash = proof_facts.hash();
        tokio::spawn(async move {
            let verified =
                Self::run_proof_verification(proof_facts.clone(), proof.clone(), pmc.clone())
                    .await?;

            if !verified {
                return Ok(());
            }

            let start = Instant::now();
            pmc.set_proof(proof_facts, proof).await?;
            let duration = start.elapsed();
            CONSENSUS_PROOF_MANAGER_STORE_LATENCY.record(duration.as_secs_f64());
            info!(
                "Proof manager store took: {duration:?} for proof facts hash: {proof_facts_hash:?}"
            );
            Ok(())
        })
    }
