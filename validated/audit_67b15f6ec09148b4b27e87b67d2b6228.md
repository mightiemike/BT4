### Title
Denial of Service via Assertion Panic on Bytecode Segment Structures with Segmentation Depth > 1 - (File: `crates/blockifier/src/execution/contract_class.rs`)

### Summary
`NestedFeltCounts::new_inner`, used to build the felt-size bookkeeping structure for a compiled class's bytecode, contains a hard `assert!` that limits nesting depth to at most 1 level. Any `CasmContractClass` whose `bytecode_segment_lengths` (a `NestedIntList`) has nesting depth greater than 1 will cause this assertion to fail and panic the process, instead of returning a recoverable error.

### Finding Description
`NestedFeltCounts::new` and its recursive helper `new_inner` walk the `NestedIntList` describing how a contract's bytecode is segmented (an artifact produced by Sierra-to-CASM compilation, `bytecode_segment_lengths`), matching it against the raw bytecode felts: [1](#0-0) 

The check `assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.")` at line 168 unconditionally panics whenever the segment tree nests more than one level deep (i.e., a `Node` containing another `Node`). This function is invoked from the production `TryFrom<VersionedCasm> for CompiledClassV1` conversion: [2](#0-1) 

That `TryFrom` conversion is the code path used across multiple state-reader implementations (`apollo_gateway/src/sync_state_reader.rs`, `apollo_state_reader/src/apollo_state.rs`, `apollo_rpc_execution/src/state_reader.rs`, `apollo_rpc_execution/src/execution_utils.rs`) to turn a stored/compiled `VersionedCasm` into an executable `CompiledClassV1`. This conversion happens whenever a class is loaded for execution — i.e., on any transaction (invoke, or a declare followed by invocation, or a declared class's constructor call during deploy) that causes the sequencer to load and run that class's compiled representation.

Elsewhere in the codebase it is demonstrated that `NestedIntList`/segment structures with depth greater than 1 are valid and expected in general: the Starknet OS bytecode-segment-structure builder (`create_bytecode_segment_structure_inner`) and its tests explicitly construct and process multi-level nested segments (depth 2+): [3](#0-2) [4](#0-3) 

This confirms that the Sierra-to-CASM bytecode segmentation model is *not* inherently limited to a single nesting level — a contract with sufficiently structured/nested Cairo functions can legitimately produce (via the real `cairo-lang` compiler) a `bytecode_segment_lengths` tree deeper than 1, which will always crash `blockifier`'s `NestedFeltCounts::new` when that class is subsequently loaded for execution/hash estimation, because the blockifier's implementation only supports depth ≤ 1 by design/assumption, unlike the OS's general-purpose structure builder.

### Impact Explanation
A panic in a `TryFrom` conversion invoked on the class-loading path used by execution nodes/full nodes is a crash, not a recoverable `Result::Err`. Since class loading for execution happens for every transaction that calls into the affected class, an attacker who declares (or otherwise gets included) a contract class whose compiled bytecode segmentation naturally nests beyond depth 1 can cause every node that attempts to load and execute that class to panic. Depending on how panics are handled at the calling layer (thread abort vs. process abort), this can crash sequencer/full-node processes handling transaction execution, block building, or RPC execution — a network-wide denial-of-service / inability to process transactions touching that class, which matches the class of "network unable to confirm new transactions" impact.

### Likelihood Explanation
Reachability requires only a normal, unprivileged declare transaction for a contract whose compiled CASM segmentation naturally exceeds a single level of nesting (plausible for contracts with several levels of nested function/branch structure, which the real compiler's segmentation algorithm can produce), followed by any call into that contract. No special privileges, malicious operator, or protocol-level tricks are needed — a single crafted (but otherwise valid) Cairo/Sierra source is sufficient to trigger the panic during normal execution/class-loading.

### Recommendation
Replace the `assert!(segmentation_depth <= 1, …)` in `NestedFeltCounts::new_inner` with either:
- Support for arbitrary segmentation depth (mirroring the OS's `create_bytecode_segment_structure_inner`, which handles nested `Node`s recursively without a depth cap), or
- If depth truly must be bounded for this specific feature, validate the depth constraint at declare-time in the gateway/compilation-validation stage and reject the class with a proper `Result::Err` (rejecting the declare transaction) rather than panicking deep inside the execution/class-loading path.

### Proof of Concept
1. Author a Cairo 1 contract with sufficiently nested function/branch structure such that the Sierra-to-CASM compiler ("cairo-lang") emits a `bytecode_segment_lengths` (`NestedIntList`) tree with nesting depth ≥ 2 (a `Node` containing a `Node`), as demonstrated to be a valid/expected shape in `create_bytecode_segment_structure_inner`'s own test cases:
   `NestedIntList::Node(vec![NestedIntList::Node(vec![NestedIntList::Leaf(3)])])` (see `crates/starknet_os/src/hints/hint_implementation/compiled_class/utils_test.rs:19`).
2. Submit a Declare transaction for this class as an unprivileged sender.
3. Trigger any invocation of the declared class (or any node operation that loads it via `TryFrom<VersionedCasm> for CompiledClassV1`, e.g. `apollo_gateway::sync_state_reader`, `apollo_state_reader::apollo_state`, or RPC execution state readers).
4. The call into `NestedFeltCounts::new` → `new_inner` panics at the `assert!(segmentation_depth <= 1, ...)` check, crashing the process handling the request instead of returning a graceful error.

impl NestedFeltCounts {
    /// Builds a nested structure matching `layout`, consuming values from `bytecode`.
    #[allow(unused)]
    pub fn new(bytecode_segment_lengths: &NestedIntList, bytecode: &[BigUintAsHex]) -> Self {
        let (base_node, consumed_felts) = Self::new_inner(bytecode_segment_lengths, bytecode, 0);
        assert_eq!(consumed_felts, bytecode.len());
        base_node
    }

    /// Recursively builds the nested structure and returns it with the number of items consumed.
    fn new_inner(
        bytecode_segment_lengths: &NestedIntList,
        bytecode: &[BigUintAsHex],
        segmentation_depth: usize,
    ) -> (Self, usize) {
        assert!(segmentation_depth <= 1, "Only supported for segmentation depth at most 1.");

        match bytecode_segment_lengths {
            NestedIntList::Leaf(len) => {
                let felt_size_groups = FeltSizeCount::from(&bytecode[..*len]);
                (NestedFeltCounts::Leaf(*len, felt_size_groups), *len)
            }
            NestedIntList::Node(segments_vec) => {
                let mut total_felt_count = 0;
                let mut segments = Vec::with_capacity(segments_vec.len());

                for segment in segments_vec {
                    // Recurse into the segment layout.
                    let (segment, felt_count) = Self::new_inner(
                        segment,
                        &bytecode[total_felt_count..],
                        segmentation_depth + 1,
                    );
                    // Accumulate the count from the segment`s subtree.
                    total_felt_count += felt_count;
                    segments.push(segment);
                }

                (NestedFeltCounts::Node(segments), total_felt_count)
            }
        }
    }

pub(crate) fn create_bytecode_segment_structure_inner(
    bytecode: &[Felt],
    bytecode_segment_lengths: NestedIntList,
    bytecode_offset: usize,
) -> (BytecodeSegmentNode, usize) {
    match bytecode_segment_lengths {
        NestedIntList::Leaf(length) => {
            let segment_end = bytecode_offset + length;
            let bytecode_segment = bytecode[bytecode_offset..segment_end].to_vec();

            (BytecodeSegmentNode::Leaf(BytecodeSegmentLeaf { data: bytecode_segment }), length)
        }
        NestedIntList::Node(lengths) => {
            let mut segments = vec![];
            let mut total_len = 0;
            let mut bytecode_offset = bytecode_offset;

            for item in lengths {
                let (current_structure, item_len) =
                    create_bytecode_segment_structure_inner(bytecode, item, bytecode_offset);

                segments.push(BytecodeSegment { length: item_len, node: current_structure });

                bytecode_offset += item_len;
                total_len += item_len;
            }

            (BytecodeSegmentNode::InnerNode(BytecodeSegmentInnerNode { segments }), total_len)
        }
    }
