### Title
Floating-point precision loss in `UnDelegateResourceProcessor.execute()` can push receiver's `NetUsage`/`EnergyUsage` negative, corrupting bandwidth/energy accounting - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java)

### Summary
`UnDelegateResourceProcessor.execute()`, invoked from the TVM `unDelegateResource` opcode (an unprivileged, contract-callable native contract), computes `transferUsage` — the portion of the receiver's consumed bandwidth/energy to claw back — using `double` arithmetic on `long` values, then unconditionally subtracts it from the receiver's `NetUsage`/`EnergyUsage` with no floor/clamp to zero. This mirrors the YaxisVaultAdapter pattern: a derived amount is computed via a lossy conversion (double ratio vs. exact integer share math) and then used to perform a state mutation sized for the *ideal* mathematically-bounded value, without re-validating against the *actual* available/consistent value at the point of use.

### Finding Description
In `UnDelegateResourceProcessor.execute()`: [1](#0-0) 

```java
} else {
  // calculate usage
  long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
      * dynamicStore.getTotalNetLimit() / repo.getTotalNetWeight());
  transferUsage = (long) (receiverCapsule.getNetUsage()
      * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
  transferUsage = min(unDelegateMaxUsage, transferUsage, VMConfig.disableJavaLangMath());

  receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForBandwidth(-unDelegateBalance);
}

long newNetUsage = receiverCapsule.getNetUsage() - transferUsage;
receiverCapsule.setNetUsage(newNetUsage);
```

Mathematically, `unDelegateBalance / getAllFrozenBalanceForBandwidth() <= 1` (since `unDelegateBalance` is validated against `delegatedResourceCapsule.getFrozenBalanceForBandwidth()`, a subset of `getAllFrozenBalanceForBandwidth()` in `UnDelegateResourceProcessor.validate()`), so `transferUsage` should never exceed `receiverCapsule.getNetUsage()`. However, this ratio is computed with IEEE-754 `double` division/multiplication on `long` values that can exceed `2^53` (TRX balances routinely reach `10^15`+ SUN), which loses precision and can push the computed ratio above the exact mathematical value, causing `transferUsage > receiverCapsule.getNetUsage()`. Since `newNetUsage` is a `long` computed as a plain subtraction with no `max(0, ...)` clamp (unlike the analogous helper `FreezeV2Util.getV2NetUsage`, which explicitly does `max(0, v2NetUsage, ...)`), the result can wrap to a large positive number via long underflow if it goes sufficiently negative, or store negative usage values.

The identical unguarded pattern is repeated for `ENERGY`: [2](#0-1) 

This directly parallels the report's root cause: an amount is derived via a precision-lossy conversion, and the *converted* amount is trusted for a subsequent state mutation (subtracting bandwidth/energy usage) rather than being bounded by the actually-consistent value at the mutation site.

### Impact Explanation
`NetUsage`/`EnergyUsage` are core resource-accounting fields used to compute how much free bandwidth/energy an account has left (`BandwidthProcessor`/`EnergyProcessor`). If this value becomes corrupted (negative, or wraps to a huge positive `long` via underflow), it directly affects resource consumption accounting for the receiver account, potentially allowing that account to bypass bandwidth/energy limits (free/near-infinite resource usage) or, in the wrap-around case, get artificially throttled/DoS'd. This is a consensus-relevant state-accounting bug reachable from unprivileged TVM contract execution (`unDelegateResource` Solidity precompile call), affecting resource and reward accounting.

### Likelihood Explanation
Triggering requires: (1) `supportDR()` and `allowTvmFreezeV2`/undelegate feature enabled (already live on mainnet in current java-tron), (2) the delegated/frozen balances and net-usage values large enough (TRX amounts routinely in the 10^9–10^15 SUN range) that double-precision rounding at the `2^53` boundary produces a visible discrepancy, and (3) crafting the exact `unDelegateBalance` vs `getNetUsage()`/`getAllFrozenBalanceForBandwidth()` ratio so the rounding pushes `transferUsage` over `getNetUsage()`. This is achievable by any account with a large frozen/delegated resource position calling the exposed TVM opcode with attacker-controlled parameters — it does not require a privileged actor, leaked key, or malicious peer. Reliably engineering the exact rounding edge case requires care, similar to how the original report noted "unless pps==1e18" — i.e., it is a `precision`/edge-case bug, not guaranteed on every call, but deterministically reproducible given the right inputs.

### Recommendation
Clamp `newNetUsage`/`newEnergyUsage` to zero (as already done via `FreezeV2Util.getV2NetUsage`/`getV2EnergyUsage` elsewhere in the codebase), e.g.:
```java
long newNetUsage = Math.max(0, receiverCapsule.getNetUsage() - transferUsage);
```
and similarly for `newEnergyUsage`. Additionally, cap `transferUsage` itself to `receiverCapsule.getNetUsage()` (and `getEnergyUsage()`) before subtraction, and consider replacing the `double`-based ratio calculations with `BigInteger`/`Math.multiplyHigh`-based exact integer arithmetic to eliminate the precision-loss source entirely, consistent with the hardened `SafeExchangeProcessor`/`StrictMathWrapper` patterns already present in the codebase for other financial calculations.

### Proof of Concept
Not independently executable from the index alone (would require constructing account state with `NetUsage`, `getAllFrozenBalanceForBandwidth()`, and `unDelegateBalance` combinations near the `2^53` double-precision boundary to force the rounding error, then invoking `unDelegateResource` via a deployed contract). This is consistent with the source-level analysis above: [3](#0-2) [4](#0-3)
