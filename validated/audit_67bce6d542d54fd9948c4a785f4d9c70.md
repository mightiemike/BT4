Based on my research, I found a strong analog to the leverage-limit bug: `TokenConfig.LiquidityCap` in `x/uregistry` is required and validated at config-registration time (`ValidateBasic` requires it to be a non-empty string), but the actual PRC20 minting path (`depositPRC20` → `CallPRC20Deposit` → `DerivedEVMCall("depositPRC20Token", ...)`) in `x/uexecutor/keeper/handler.go` and `x/uexecutor/keeper/evm.go` never reads or enforces `LiquidityCap` against the cumulative minted supply before minting. This mirrors the report's core flaw exactly: a protocol-defined risk ceiling exists in config/state, is validated only at the "set" boundary, but is never checked at the value-creating execution boundary. ### Title
Unenforced `LiquidityCap` Allows Unbounded PRC20 Minting Beyond Admin-Set Risk Ceiling - (File: x/uexecutor/keeper/handler.go)

### Summary
`x/uregistry.TokenConfig.LiquidityCap` is documented and required as "max supply cap for this token," and the admin can set/lower it via `MsgAddTokenConfig` / `MsgUpdateTokenConfig`. However, the inbound-triggered PRC20 minting path (`depositPRC20` → `CallPRC20Deposit`) never reads `LiquidityCap` or compares it to the token's current/prospective minted supply. Just as the GTE perps report found that `maxOpenLeverage` reductions are bypassed because the position-opening path never re-validates leverage against the current cap, Push Chain's liquidity cap is bypassed because the minting path never validates against it at all.

### Finding Description
An unprivileged, external-chain user can trigger `MsgVoteInbound`-driven mint flows (`TxType_FUNDS`, `FUNDS_AND_PAYLOAD`, `GAS`, `GAS_AND_PAYLOAD`) for any registered token, and each successful ballot finalization calls `k.depositPRC20(...)` → `k.CallPRC20Deposit(...)` → `DerivedEVMCall("depositPRC20Token", prc20Address, amount, to)`. [5](#0-4) 

`depositPRC20` only resolves the token's PRC20 contract address from `TokenConfig.NativeRepresentation`; it performs no supply check whatsoever against `TokenConfig.LiquidityCap` before minting the user-controlled `Amount` from the vote-finalized `Inbound`. [6](#0-5) 

Because the `Amount` field of an `Inbound` is attacker-influenced (it originates from a source-chain deposit event observed and voted by honest UVs, but the deposit itself, and therefore the amount, is fully controlled by the depositing user on the external chain), a user can simply deposit (and have validators honestly observe/vote) amounts that, cumulatively, vastly exceed the `LiquidityCap` the admin configured as the token's risk ceiling — with zero on-chain enforcement. If the admin later lowers `LiquidityCap` in response to a de-peg or exploit risk on a bridged asset (analogous to lowering `maxOpenLeverage` during volatility), that reduction has no operative effect: new inbound deposits continue to mint without any cap check, exactly as legacy leverage continued to be honored in the GTE report.

### Impact Explanation
`LiquidityCap` is designed as the protocol's primary defense against unbounded PRC20 issuance for a bridged asset — e.g., to bound the module's exposure/backing risk for a given token. Since it is never enforced, an attacker (or just organic volume) can mint PRC20 supply for any token far beyond the admin-intended ceiling, defeating a documented risk control with no privileged action required. This can result in an unbacked/under-collateralized PRC20 supply relative to the value actually locked or intended, i.e., unauthorized mint beyond protocol-sanctioned bounds — directly matching the "unauthorized mint" allowed-impact category.

### Likelihood Explanation
High. No special conditions are needed beyond normal, honest bridging usage: any user depositing on a supported source chain and having their inbound observed/voted by honest UVs (the standard, non-privileged flow) will have PRC20 minted without any cap check. The bug is triggered by default transaction submission paths alone, not by any validator or admin misbehavior.

### Recommendation
In `depositPRC20` (`x/uexecutor/keeper/handler.go`) or in `CallPRC20Deposit` (`x/uexecutor/keeper/evm.go`), before calling `DerivedEVMCall("depositPRC20Token", ...)`, query the PRC20 contract's current `totalSupply()` (or maintain an on-chain running total per token) and reject (or clamp) the mint if `currentSupply + amount > TokenConfig.LiquidityCap`. Re-validate against the *current* `LiquidityCap` value on every mint, not only at token-config registration time, so that admin-driven cap reductions take effect immediately for all subsequent inbound executions.

### Proof of Concept
1. Admin registers a `TokenConfig` for `eip155:11155111` USDC with `LiquidityCap = "1000000000000000000000000"` (1,000,000 tokens at 18 decimals), as done in `test/integration/uexecutor/inbound_synthetic_bridge_test.go`.
2. A user deposits an amount on the source chain far exceeding `LiquidityCap` (or repeats deposits over time to exceed it in aggregate).
3. Honest UVs observe and vote `MsgVoteInbound` for each deposit; quorum is reached exactly as in `TestInboundSyntheticBridge` ("quorum reached executes inbound and prc20 gets minted successfully").
4. `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` mints the full requested amount with no check against `LiquidityCap`; `balanceOf(recipient)` equals the full minted amount regardless of the configured cap.
5. Repeating step 2–4 lets total PRC20 supply for the token grow unbounded, even after the admin lowers `LiquidityCap` to mitigate risk — the reduced cap is never consulted by the minting path.

// ValidateBasic performs sanity checks on the TokenConfig
func (p TokenConfig) ValidateBasic() error {
	if strings.TrimSpace(p.Chain) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "chain cannot be empty")
	}

	if strings.TrimSpace(p.Address) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token contract address cannot be empty")
	}

	// Enforce a parseable address for the chain's namespace (e.g. 20-byte hex
	// for eip155, base58 for solana) so every registration lands on the
	// canonical storage key.
	if _, err := utils.CanonicalizeAddressByNamespace(p.Chain, p.Address); err != nil {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token address for chain %s: %s", p.Chain, err)
	}

	if strings.TrimSpace(p.Name) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token name cannot be empty")
	}

	if strings.TrimSpace(p.Symbol) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "token symbol cannot be empty")
	}

	if p.Decimals == 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "decimals must be greater than zero")
	}

	// Validate token_type is within known enum range
	if _, ok := TokenType_name[int32(p.TokenType)]; !ok {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "invalid token_type: %v", p.TokenType)
	}

	if strings.TrimSpace(p.LiquidityCap) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "liquidity_cap cannot be empty")
	}

	if p.NativeRepresentation == nil {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "native_representation is required")
	}
	if err := p.NativeRepresentation.ValidateBasic(); err != nil {
		return errors.Wrap(err, "invalid native representation")
	}

	return nil
}

import (
	"fmt"

	vmtypes "github.com/cosmos/evm/x/vm/types"
	"github.com/ethereum/go-ethereum/common"

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

// Calls Handler Contract to deposit prc20 tokens
func (k Keeper) CallPRC20Deposit(
	ctx sdk.Context,
	prc20Address, to common.Address,
	amount *big.Int,
) (*evmtypes.MsgEthereumTxResponse, error) {
	handlerAddr := common.HexToAddress(uregistrytypes.SYSTEM_CONTRACTS["UNIVERSAL_CORE"].Address)

	abi, err := types.ParseUniversalCoreABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse Handler Contract ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	// Before sending an EVM tx from module
	nonce, err := k.GetModuleAccountNonce(ctx)
	if err != nil {
		return nil, err
	}

	// increment first (safe for internal modules)
	if _, err := k.IncrementModuleAccountNonce(ctx); err != nil {
		return nil, err
	}

	return k.evmKeeper.DerivedEVMCall(
		ctx,
		abi,
		ueModuleAccAddress, // sender: module account
		handlerAddr,        // destination
		big.NewInt(0),
		nil,
		true,   // commit = true (real tx, not simulation)
		false,  // gasless = false (@dev: we need gas to be emitted in the tx receipt)
		true,   // module sender = true
		&nonce, // manual nonce of module
		"depositPRC20Token",
		prc20Address,
		amount,
		to,
	)
}
