### Title
Unhandled offline-token-refresh failure aborts webhook authentication and denies webhook processing for the shop - (File: packages/apps/shopify-app-remix/src/server/authenticate/webhooks/authenticate.ts)

### Summary
The Chainlink oracle report describes a pattern where a single failing/reverting data source, when not defensively handled, aborts an entire multi-source read and causes a denial of service. The analogous pattern in `shopify-app-js` is in the webhook authentication path: `ensureValidOfflineSession` is invoked without any error handling, so if the (optional) offline-token-refresh step throws, the whole webhook authenticate call throws unhandled — instead of degrading gracefully like the equivalent Express code path does.

### Finding Description
`authenticateWebhookFactory` in `shopify-app-remix` (and the equivalent code in `shopify-app-react-router`) calls: [1](#0-0) 

```ts
const session = await ensureValidOfflineSession(params, check.domain);
```

with no surrounding `try/catch`. This helper chains `createOrLoadOfflineSession` → `ensureOfflineTokenIsNotExpired` → `refreshToken`: [2](#0-1) [3](#0-2) 

When `config.future.expiringOfflineAccessTokens` is enabled and the stored offline session is near/at expiry, `refreshToken()` is called, and on any failure it rethrows either the original `InvalidJwtError`/`invalid_subject_token` error, or a generic `Response(500)`: [4](#0-3) 

Because `authenticateWebhookFactory` does not catch this, the thrown error/response propagates out of the entire webhook handler — even though the webhook payload was already HMAC-validated and does not strictly need a session to be returned (the code already supports `session: undefined` as a valid, non-fatal outcome when no session exists, per lines 88-90 of the same file). This is exactly the "one oracle reverts, so the whole read reverts" pattern from the report: a secondary/optional step (token refresh) that fails causes the primary function (webhook authentication) to fail entirely, instead of returning the webhook context without a session/admin client as it already does when no session exists at all.

Contrast this with the Express (non-Remix/react-router) implementation, `validateWithAuthCodeFlow`, which wraps the equivalent call in `try/catch` and logs the failure instead of failing the whole session-validation flow: [5](#0-4) 

### Impact Explanation
Shopify's webhook infrastructure delivers webhooks to the app's public webhook endpoint automatically and retries on failure. If the offline access/refresh token has been revoked (e.g., merchant reduced scopes or reinstalled the app) or the token endpoint returns a transient error, every subsequent webhook delivery for that shop will throw during `ensureValidOfflineSession`, causing the handler to return 500 for every webhook topic registered for that shop — a denial of service of the webhook auth handler that is unrelated to the specific topic being delivered. Persistent 500s can also lead Shopify to disable/unsubscribe webhook topics for the shop after repeated delivery failures, compounding the availability impact. This qualifies as a "DoS of an auth handler" reachable by a normal (non-privileged) HTTP delivery to a public endpoint.

### Likelihood Explanation
This requires the `expiringOfflineAccessTokens` future flag to be enabled and a scenario where the stored offline session's refresh token is invalid, expired, or the Shopify OAuth token endpoint is briefly unavailable — a realistic operational condition (analogous to a stale/zero-timestamp oracle round in the original report), not an attacker-crafted exploit. It does not require the webhook body/HMAC to be forged; the trigger is an internal auxiliary token-refresh failure surfacing on the main authentication path.

### Recommendation
Wrap the `ensureValidOfflineSession` call in `authenticateWebhookFactory` (and the react-router equivalent) in a `try/catch`, log the failure, and fall back to returning the webhook context with `session: undefined`/`admin: undefined` (as already supported by the existing code when no session is found), rather than letting the refresh failure abort the whole handler. Apply the same defensive pattern used in `shopify-app-express`'s `validateWithAuthCodeFlow`.

### Proof of Concept
1. Enable `future.expiringOfflineAccessTokens` and register a webhook handler.
2. Store an offline session for a shop whose `refreshToken` value is no longer valid (revoked/expired) and whose `expires` is within `WITHIN_MILLISECONDS_OF_EXPIRY` (5 minutes) of now.
3. Have Shopify (or a test harness) deliver any correctly HMAC-signed webhook for that shop to the app's webhook endpoint.
4. `authenticateWebhookFactory` calls `ensureValidOfflineSession` → `ensureOfflineTokenIsNotExpired` → `refreshToken`, which throws (`InvalidJwtError` or a 500 `Response`) because the refresh token is invalid.
5. The thrown error propagates unhandled out of `authenticate()`, causing the webhook route to return a 500 (or crash the handler) for every webhook delivered to that shop until the offline session is manually corrected — even though the webhook itself was legitimate and did not need write/admin access.

import {createOrLoadOfflineSession} from './create-or-load-offline-session';
import {ensureOfflineTokenIsNotExpired} from './ensure-offline-token-is-not-expired';

export async function ensureValidOfflineSession(
  params: BasicParams,
  shop: string,
) {
  const session = await createOrLoadOfflineSession(params, shop);

  if (!session) return undefined;

  return ensureOfflineTokenIsNotExpired(session, params, shop);
}

export async function ensureOfflineTokenIsNotExpired(
  session: Session,
  params: BasicParams,
  shop: string,
) {
  const {config} = params;
  if (
    config.future?.expiringOfflineAccessTokens &&
    session.isExpired(WITHIN_MILLISECONDS_OF_EXPIRY) &&
    config.distribution !== AppDistribution.ShopifyAdmin &&
    session.refreshToken
  ) {
    const offlineSession = await refreshToken(
      params,
      shop,
      session.refreshToken,
    );

    await config.sessionStorage!.storeSession(offlineSession);
    return offlineSession;
  }
  return session;
}
