### Title
Energy charged for `ValidateMultiSign`/`BatchValidateSign` precompiles is derived from raw calldata length, not from the actual number of signatures processed, allowing under-priced CPU-expensive ECDSA recovery work - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The external report's core theme is that a party who controls part of the input to a costed operation (a delegator choosing an enforcer/signature-validation callee) can decouple "gas charged" from "work actually performed," letting them grief or steal execution resources. In java-tron's TVM, the `ValidateMultiSign` and `BatchValidateSign` precompiled contracts price their execution using a formula based purely on the *byte length* of the call data, while the actual work executed in `execute()`/`doExecute()` iterates over a signature array whose size is decoded from calldata content (an ABI-style header) rather than being strictly tied to that same length formula.

### Finding Description
`ValidateMultiSign.getEnergyForData` computes energy as: [1](#0-0) 

i.e. `cnt = (data.length / 32 - 5) / 5` signatures, charged at `1500` energy each. This is a static function of `data.length` alone.

The actual `execute()` method, however, derives the signature array from decoded words (`words[3]`, `words[...]` array-size markers) via `extractSigArray`/`extractBytesArray`, and then loops over `signatures`, performing an ECDSA public-key recovery (`recoverAddrBySign`) per entry: [2](#0-1) 

Because the loop's iteration count is driven by the *decoded* array size embedded in the calldata rather than being provably equal to the `cnt` computed purely from `data.length`, a mismatch between the two is architecturally possible unless the decoder rejects any calldata shape that doesn't match the exact ABI layout the pricing formula assumes. The code contains a guarded fix (`TIP-854`, gated by `VMConfig.allowTvmOsaka()`) that adds `isValidAbiEncoding` checks specifically to reject malformed calldata shapes for this reason: [3](#0-2) 

This strongly indicates that, prior to (and whenever) that feature flag is inactive, calldata could be crafted so the declared/consumed signature-array length is inconsistent with the length-based pricing formula, letting the CPU-expensive per-signature ECDSA recovery loop run more times than the energy charged accounts for — the direct analogue of the report's "gas guzzling"/"gas stealing" abuse via a party-controlled sub-call whose real cost isn't bounded by the fee charged. The same pattern is repeated in `BatchValidateSign`, which additionally offloads recovery to a thread pool sized by attacker-controlled `cnt`: [4](#0-3) [5](#0-4) 

This is reachable directly from a broadcast `TriggerSmartContract` transaction (any contract can `CALL` the `validateMultiSignAddr` / `batchValidateSignAddr` precompiled addresses) and thus from an anonymous RPC client submitting a transaction, matching the "contract call" trigger class in scope.

### Impact Explanation
If the length-derived energy estimate under-counts the true number of ECDSA recoveries actually executed, a malicious contract can pay for `N` "declared" signatures while forcing the node to execute a CPU-bound recovery loop for `M > N` entries, consuming more validating-node CPU/wall-clock time per unit of paid energy than the metering model assumes. At scale (crafted transactions broadcast repeatedly), this is a resource-exhaustion/DoS vector against block-producing and full nodes executing the TVM, and — for `BatchValidateSign` — also spins up thread-pool tasks (`workers.submit(...)`) proportional to the attacker-controlled count, amplifying CPU/thread pressure beyond the metered energy.

### Likelihood Explanation
The fact that the codebase already ships a targeted guard (`isValidAbiEncoding`, gated behind `allowTvmOsaka`/TIP-854) that explicitly rejects "malformed calldata whose byte length is incompatible with the (words-5)/5 shape the per-call energy formula already assumes" is direct evidence that this exact class of mismatch was identified and is only mitigated when that hard fork feature is active. Any network/version where `allowTvmOsaka` is not yet enabled remains exposed to the un-priced-CPU-work condition, and the vulnerability requires only a normal `TriggerSmartContract` transaction from any account — no privileged actor, leaked key, or malicious peer is needed.

### Recommendation
- Ensure the ABI-shape validation (`isValidAbiEncoding`) is unconditionally enforced for `ValidateMultiSign` and `BatchValidateSign`, not only when `allowTvmOsaka` is active, so the length-derived energy formula and the actual iterated array size can never diverge.
- Add an explicit invariant check immediately after array extraction that `signatures.length` (and, for `BatchValidateSign`, `addresses.length`) exactly equals the `cnt` used by `getEnergyForData`, and fail closed (charge full/available energy, return `false`) otherwise.
- For `BatchValidateSign`, additionally bound the thread-pool submission count independently of calldata-derived values before dispatching work, and confirm the `MAX_SIZE` bound is checked before any recovery work begins, not only after selective decoding paths.

### Proof of Concept
Conceptual (no live-network execution performed, derived from static code analysis only):
1. Deploy/trigger a contract that performs a `CALL` (or `STATICCALL`) to the fixed precompiled address `batchValidateSignAddr`/`validateMultiSignAddr`.
2. Craft `data` such that the byte length yields a small `cnt` per `getEnergyForData` (e.g., `(data.length/32 - 5)/5` = 1), but the header word(s) that determine the actual array size decoded by `extractSigArray`/`extractBytesArray` point to a larger embedded array (achievable if the decoder does not strictly bind array bounds to `data.length` under the given ABI header/item word constants when the TIP‑854 guard is inactive).
3. Submit the transaction with the minimal `feeLimit`/energy corresponding to the small `cnt`.
4. Observe (in a controlled test harness such as `ValidateMultiSignContractTest`/`BatchValidateSignContractTest`) that the executor performs recovery operations (and, for the batch variant, thread-pool submissions) for more entries than the energy charge assumed, before the TIP‑854 guard rejects it — confirming the charge/work divergence exists in the un-guarded code path.   @Test
  public void testTip854RejectsMalformedCalldata() {
    VMConfig.initAllowTvmOsaka(1);
    try {
      // Bucket 1: 32-aligned head + sub-word trailing bytes (r=1, r=31).
      for (int r : new int[]{1, 31}) {
        byte[] data = new byte[(5 + 5) * 32 + r];
        Pair<Boolean, byte[]> ret = contract.execute(data);
        Assert.assertFalse("non-32-aligned len=" + data.length, ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Bucket 2: fewer than the static head's 5 words.
      for (int bytes : new int[]{0, 32, 64, 96, 128}) {
        Pair<Boolean, byte[]> ret = contract.execute(new byte[bytes]);
        Assert.assertFalse("len=" + bytes + " < 5 words", ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Bucket 3: 32-aligned but tail not a multiple of I=5 words (k = 1..4).
      for (int k = 1; k <= 4; k++) {
        byte[] data = new byte[(5 + k) * 32];
        Pair<Boolean, byte[]> ret = contract.execute(data);
        Assert.assertFalse("aligned bad-tail k=" + k, ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Null calldata: explicit spec clause.
      Pair<Boolean, byte[]> ret = contract.execute(null);
      Assert.assertFalse("null calldata", ret.getLeft());
      Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
    } finally {
      VMConfig.initAllowTvmOsaka(0);
    }
  }
