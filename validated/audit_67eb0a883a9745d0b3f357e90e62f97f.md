### Title
Governance feature-flag activations (`ProposalUtil`/`DynamicPropertiesStore`) can be turned on but never turned off, leaving no pause/kill-switch for risky protocol features - ([File: actuator/src/main/java/org/tron/core/utils/ProposalUtil.java])

### Summary
The Frankencoin finding centers on the absence of any mechanism to remove or pause a governance-approved but risky component (a minter) once the initial objection window has passed. java-tron has a structurally analogous gap: nearly all consensus/TVM/resource-model feature flags approved through the on-chain proposal mechanism (`ProposalCreateContract` → `ProposalApproveActuator` → `ProposalController`) are validated in `ProposalUtil.validator` with a hard `value != 1` (or equivalent "has been valid, no need to propose again") check, meaning that once a feature is switched on, there is no governance path defined to switch it back off.

### Finding Description
`ProposalUtil.validator` enumerates the accepted values for every chain parameter proposal. For the overwhelming majority of feature toggles - e.g. `ALLOW_CREATION_OF_CONTRACTS`, `ALLOW_TVM_CONSTANTINOPLE`, `ALLOW_TVM_SOLIDITY_059`, `ALLOW_MARKET_TRANSACTION`, `ALLOW_NEW_RESOURCE_MODEL`, `ALLOW_TVM_FREEZE`, `ALLOW_TVM_LONDON`, `ALLOW_TVM_CANCUN`, `ALLOW_TVM_BLOB`, `ALLOW_TVM_SELFDESTRUCT_RESTRICTION`, `ALLOW_TVM_OSAKA`, `ALLOW_TVM_PRAGUE`, `ALLOW_HARDEN_RESOURCE_CALCULATION`, `ALLOW_ENERGY_ADJUSTMENT`, `ALLOW_STRICT_MATH`, `CONSENSUS_LOGIC_OPTIMIZATION` - the validator throws `ContractValidateException` unless `value == 1`, and several additionally guard against re-proposing once active via checks like `dynamicPropertiesStore.getAllowTvmBlob() == 1` → `"has been valid, no need to propose again"`. [1](#0-0) [2](#0-1) [3](#0-2) 

This is a one-way switch by construction: only `ProposalType` cases such as `ALLOW_PROTO_FILTER_NUM`, `ALLOW_ACCOUNT_STATE_ROOT`, `ALLOW_CHANGE_DELEGATION`, `ALLOW_SHIELDED_TRC20_TRANSACTION`, `ALLOW_TRANSACTION_FEE_POOL`, `ALLOW_BLACKHOLE_OPTIMIZATION`, and `ALLOW_HARDEN_EXCHANGE_CALCULATION` accept `value != 1 && value != 0` (i.e. permit toggling back to 0); every other listed feature flag has no code path that ever accepts `0` again once set to `1`. [4](#0-3) 

Once an approved proposal reaches quorum, `ProposalController.processProposal` calls `setDynamicParameters`, which invokes `ProposalService.process` to durably persist the new dynamic property and mark the proposal `APPROVED` - there is no complementary "disable" or "revert" actuator for these parameters analogous to `denyMinter`/`suggestMinter` pairing in Frankencoin. [5](#0-4) 

Just as the Frankencoin report notes that `MintingHub`'s novel auction mechanism carries extra systemic risk with no way to shut it off, several of these irreversible java-tron flags gate genuinely novel/experimental subsystems - e.g. `ALLOW_MARKET_TRANSACTION` (the on-chain TRC10 exchange/market engine) and `ALLOW_NEW_RESOURCE_MODEL` (a new resource accounting model) - both of which, once enabled network-wide, cannot be disabled if a bug is later discovered.

### Impact Explanation
If a bug is later discovered in one of these irreversible features (e.g. a TVM opcode semantics flaw, the market/exchange sell/cancel logic, or a resource-accounting model), the super-representative committee has no on-chain governance mechanism to disable or pause it - the feature remains permanently active for every unprivileged user interacting with contracts, the market/exchange, or resource delegation on the network. This mirrors the core risk identified in the source report: an approved, potentially flawed mechanism cannot be removed or paused, forcing the entire user base to bear ongoing exposure to a known defect until a hard fork is coordinated.

### Likelihood Explanation
Feature activation via these proposal types is a normal, expected part of java-tron's governance/upgrade lifecycle (it has occurred repeatedly across many hard forks per the version gates in `ProposalUtil`), so the precondition ("feature X has been turned on") is routinely met. The missing "off" path is not a hypothetical edge case; it is the default behavior for essentially every feature flag defined in this file, so any bug discovered post-activation in TVM opcodes, market logic, or resource accounting is guaranteed to be irrevocable through governance.

### Recommendation
Introduce disable/rollback support for security- or economically-sensitive feature flags (particularly `ALLOW_MARKET_TRANSACTION`, `ALLOW_NEW_RESOURCE_MODEL`, and TVM opcode-set flags) by allowing `value == 0` proposals symmetric to how `ALLOW_HARDEN_EXCHANGE_CALCULATION` and `ALLOW_CHANGE_DELEGATION` already support toggling. Where a clean disable is unsafe due to state migration concerns, consider adding an independent emergency-pause dynamic property that gates the corresponding actuators/opcodes without requiring a full state rollback, giving the committee a genuine kill-switch analogous to the "pause" capability recommended in the source report.

### Proof of Concept
1. Committee proposes and approves `ALLOW_MARKET_TRANSACTION = 1` via `ProposalCreateActuator`/`ProposalApproveActuator`; `ProposalUtil.validator` accepts only `value == 1`. [2](#0-1) 
2. `ProposalController.processProposal` sets `State.APPROVED` and calls `ProposalService.process`, persisting `AllowMarketTransaction = 1` in `DynamicPropertiesStore`. [6](#0-5) 
3. A bug is later found in the market/exchange matching logic exploitable by unprivileged users placing orders.
4. Committee attempts to submit a new proposal with `ALLOW_MARKET_TRANSACTION = 0` to disable the feature; `ProposalUtil.validator`'s `case ALLOW_MARKET_TRANSACTION` unconditionally rejects any value other than `1`, so the proposal fails validation and the feature cannot be turned off on-chain. [2](#0-1)
