### Title
Contract owner can front-run TriggerSmartContract calls with `UpdateSettingContract` to grief callers who rely on contract-subsidized energy - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java`)

### Summary
Similar to Perennial-V2's `maxFee` griefing bug (where the order owner can front-run a keeper's execution transaction and lower `maxFee` to zero, denying the keeper's earned compensation), a TRON smart contract owner can front-run a caller's `TriggerSmartContract` transaction with an `UpdateSettingContract` transaction that raises `consumeUserResourcePercent` to 100, shifting the entire energy cost of the pending call onto the caller with no floor/limit protection and no timelock.

### Finding Description
When a caller triggers a smart contract, `VMActuator` calculates how much energy the caller vs. the contract's creator/origin will pay based on `consumeUserResourcePercent`, which is read live from the `ContractStore` at execution time: [2](#0-1) [3](#0-2) 

`consumeUserResourcePercent` is a mutable value that the contract's owner can change at any time via `UpdateSettingContractActuator`, with essentially no restriction other than being in `[0, 100]` and being the contract's origin address — there is no minimum guaranteed subsidy, no timelock, and no cooldown between updates: [4](#0-3) 

This is confirmed by the existing test showing the setting can be changed repeatedly, back-to-back, with immediate effect: [5](#0-4) 

Because the actual `consumeUserResourcePercent` (and, analogously, `originEnergyLimit` via `UpdateEnergyLimitContractActuator`) used for a `TriggerSmartContract` is read at block-inclusion/execution time rather than snapshotted at the time the caller decides to submit their transaction, an unprivileged caller (e.g. a relayer/bot that computed a `fee_limit` assuming the contract subsidizes X% of energy) has no guarantee that the subsidy percentage they observed off-chain still applies when their transaction actually executes. The contract owner can observe the pending `TriggerSmartContract` transaction in the mempool and submit an `UpdateSettingContract`/`UpdateEnergyLimitContract` transaction (with a higher fee/priority) that lowers or removes the subsidy just before the caller's call is processed — exactly the "griefing via front-run of a mutable fee/cost-sharing parameter" root cause identified in the Perennial-V2 report, where `maxFee` is read live at settlement instead of being fixed when the keeper committed to the work.

### Impact Explanation
An unprivileged caller relying on a contract's advertised `consumeUserResourcePercent`/`originEnergyLimit` to estimate their expected energy cost can have that assumption invalidated between transaction submission and execution. This can cause the caller's transaction to run out of energy mid-execution (consuming and charging the energy actually used up to that point) or to pay substantially more TRX in energy fees than anticipated, with no minimum-compensation or floor mechanism to protect them — mirroring the underpriced/griefed-worker impact class from the original report.

### Likelihood Explanation
This requires only an unprivileged action from the contract owner (a normal account operation, not a privileged/committee role) and standard blockchain front-running (submitting a competing transaction with the same or later ordering before the caller's tx is included). No special permissions beyond being the contract's origin address are needed, and the setting change takes effect immediately with no delay, making the attack straightforward to execute against any caller whose cost estimate depends on the current subsidy percentage.

### Recommendation
Consider adding a minimum guaranteed `consumeUserResourcePercent`/`originEnergyLimit` bound (or a timelock/cooldown before an `UpdateSettingContract`/`UpdateEnergyLimitContract` change takes effect) so that resource-sharing parameters cannot be altered atomically/immediately before a pending caller transaction is processed, preventing griefing of callers who priced their `fee_limit` against the previously observed subsidy.

### Proof of Concept
1. Contract `C` is deployed with `consumeUserResourcePercent = 10` (owner subsidizes 90% of energy for callers).
2. A relayer/bot observes this and submits a `TriggerSmartContract` transaction against `C` with `fee_limit` sized for only 10% of the expected energy cost.
3. Before that transaction is included, `C`'s owner submits an `UpdateSettingContract` transaction (as validated/executed in `UpdateSettingContractActuator.execute`/`validate`) setting `consumeUserResourcePercent = 100`.
4. When the relayer's transaction executes, `VMActuator.getTotalEnergyLimitWithFixRatio`/`WithFloatRatio` computes the caller's available energy using the new 100% value, causing the relayer's call to run out of energy or fail, while the relayer is still charged for the energy consumed — losing value they expected the contract owner to cover.

  @Override
  public boolean validate() throws ContractValidateException {
    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }
    if (chainBaseManager == null) {
      throw new ContractValidateException("No account store or contract store!");
    }
    AccountStore accountStore = chainBaseManager.getAccountStore();
    ContractStore contractStore = chainBaseManager.getContractStore();
    if (!this.any.is(UpdateSettingContract.class)) {
      throw new ContractValidateException("contract type error, expected type "
          + "[UpdateSettingContract], real type[" + any.getClass() + "]");
    }
    final UpdateSettingContract contract;
    try {
      contract = this.any.unpack(UpdateSettingContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    if (!DecodeUtil.addressValid(contract.getOwnerAddress().toByteArray())) {
      throw new ContractValidateException("Invalid address");
    }
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    String readableOwnerAddress = StringUtil.createReadableString(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException(
          ACCOUNT_EXCEPTION_STR + readableOwnerAddress + "] does not exist");
    }

    long newPercent = contract.getConsumeUserResourcePercent();
    if (newPercent > ActuatorConstant.ONE_HUNDRED || newPercent < 0) {
      throw new ContractValidateException(
          "percent not in [0, 100]");
    }

    byte[] contractAddress = contract.getContractAddress().toByteArray();
    ContractCapsule deployedContract = contractStore.get(contractAddress);

    if (deployedContract == null) {
      throw new ContractValidateException(
          "Contract does not exist");
    }

    byte[] deployedContractOwnerAddress = deployedContract.getInstance().getOriginAddress()
        .toByteArray();

    if (!Arrays.equals(ownerAddress, deployedContractOwnerAddress)) {
      throw new ContractValidateException(
          ACCOUNT_EXCEPTION_STR + readableOwnerAddress + "] is not the owner of the contract");
    }

    return true;
  }

  private long getTotalEnergyLimitWithFloatRatio(AccountCapsule creator, AccountCapsule caller,
      TriggerSmartContract contract, long feeLimit, long callValue) {

    long callerEnergyLimit = getAccountEnergyLimitWithFloatRatio(caller, feeLimit, callValue);
    if (Arrays.equals(creator.getAddress().toByteArray(), caller.getAddress().toByteArray())) {
      return callerEnergyLimit;
    }

    // creatorEnergyFromFreeze
    long creatorEnergyLimit = rootRepository.getAccountLeftEnergyFromFreeze(creator);

    ContractCapsule contractCapsule = rootRepository
        .getContract(contract.getContractAddress().toByteArray());
    long consumeUserResourcePercent = contractCapsule.getConsumeUserResourcePercent(
        VMConfig.disableJavaLangMath());

    if (creatorEnergyLimit * consumeUserResourcePercent
        > (VMConstant.ONE_HUNDRED - consumeUserResourcePercent) * callerEnergyLimit) {
      return floorDiv(
          callerEnergyLimit * VMConstant.ONE_HUNDRED, consumeUserResourcePercent,
          VMConfig.disableJavaLangMath());
    } else {
      return addExact(callerEnergyLimit, creatorEnergyLimit,
          VMConfig.disableJavaLangMath());
    }
  }
