### Title
Proof-of-execution replay via unbound proof_facts caching in TransactionConverter/ProofManager - (File: crates/apollo_transaction_converter/src/transaction_converter.rs)

### Summary
The Starknet sequencer supports "client-side proving" invoke transactions, where an `Invoke` transaction carries `proof_facts` and an accompanying `Proof` (a client-generated proof of correct off-chain execution) [1](#0-0) . Verification of this proof is memoized purely by the hash of `proof_facts`, and once a hash is marked as verified/stored, any subsequent transaction reusing the same `proof_facts` skips proof (re-)verification entirely — mirroring the "prove one leaf multiple times" bug class where a proof is checked for existence but never bound/invalidated per consuming action.

### Finding Description
`TransactionConverter::run_proof_verification` looks up `contains_proof(proof_facts)` in the `ProofManager`, and if true, immediately returns `Ok(false)` (verification skipped) without ever re-verifying the proof against the transaction currently being processed [2](#0-1) . The `ProofManager` (`contains_proof`, `set_proof`, `get_proof`) keys all storage and lookups solely by `proof_facts.hash()` — never by the transaction hash or any other transaction-specific binding (sender, nonce, calldata) [3](#0-2) . The persistent backing store (`FsProofStorage`) is likewise indexed only by `facts_hash` [4](#0-3) .

Critically, the invoke-transaction hash computation treats `calldata`, `sender_address`, `nonce`, and `account_deployment_data` as fields hashed *independently* of `proof_facts` — `proof_facts` is only folded in as an additional, separate hash chain element when non-empty [5](#0-4) . This means the sequencer's dedup/skip-verification logic has no guarantee that the cached `proof_facts` commit to the specific execution content of the *new* transaction reusing them — the gateway/consensus path only checks "have we seen this `proof_facts` hash before," not "does this proof, bound to these exact transaction semantics, apply here."

In `convert_internal_rpc_tx_to_rpc_tx`, when reconstructing an RPC transaction, the previously stored `Proof` is fetched from the manager purely by `proof_facts` and reattached, with an explicit comment: "We expect the proof to be available here because it has already been verified and stored by the proof manager in the gateway" [6](#0-5) . Combined with `spawn_verify_and_store_proof`'s pattern of "verify once, `set_proof` once, then always skip on future sightings" [7](#0-6) , this is functionally the same anti-pattern as the reported `MerkleReserveMinter` bug: successful verification for one instance is treated as permanent, transferable proof for any future use of the same underlying artifact, without any consumption/invalidation tracking scoped to the specific transaction it accompanies.

### Impact Explanation
If `proof_facts` do not fully and uniquely commit to all safety-critical fields of the invoke transaction it is attached to (which is architecturally plausible given that `calldata`, `sender_address`, and `nonce` are hashed as independent, non-proof-facts-derived components of the transaction hash), an attacker could submit one transaction to get a `proof_facts` hash verified and cached, then submit different subsequent transactions reusing the same `proof_facts` value to bypass proof verification (`contains_proof` short-circuits to `Ok(false)`/no re-verify) while pairing it with different calldata/sender/nonce. This could let the account executor accept an invoke transaction as "client-side proven" when the actual execution it purports to certify was never proven, resulting in unauthorized account action being admitted into a block.

### Likelihood Explanation
Reachable directly from an unprivileged RPC/gateway submission of an `InvokeV3WithProof`/`RpcInvokeTransactionV3` transaction containing non-empty `proof_facts` [8](#0-7) ; no special privileges, node compromise, or p2p manipulation is required — only crafting two transactions that reuse identical `proof_facts`.

### Recommendation
Bind proof verification/caching to the full transaction context (e.g., key the proof cache and the "skip verification" decision by transaction hash, or ensure `ProofFacts` cryptographically commits to every field of the transaction that materially affects execution — sender, nonce, calldata, account_deployment_data) rather than solely by an independently-hashable `proof_facts` blob. Alternatively, always re-verify the proof against the specific transaction under consideration rather than treating a prior `contains_proof` hit as sufficient.

### Proof of Concept
Conceptual (exact `ProofFacts` contents were not fully inspectable within the available index, so this cannot be fully confirmed as end-to-end exploitable without further review of `starknet_api::transaction::fields::ProofFacts`):
1. Attacker submits Invoke tx A with `proof_facts = F`, `calldata = C1`, valid `proof = P` attesting to `F`. Gateway verifies `P` against `F`, then `ProofManager::set_proof(F, P)` is stored keyed only by `hash(F)` [9](#0-8) .
2. Attacker submits Invoke tx B with the same `proof_facts = F` but different `calldata = C2`/`sender`/`nonce`.
3. `run_proof_verification` calls `contains_proof(F)` → `true` → returns `Ok(false)`, skipping any re-verification of `P` against tx B's actual content [10](#0-9) .
4. Tx B is accepted into consensus/executed as though it carries a valid client-side proof for its own execution, despite `P` only ever having proven the semantics tied to tx A.

    async fn run_proof_verification(
        proof_facts: ProofFacts,
        proof: Proof,
        proof_manager_client: SharedProofManagerClient,
    ) -> Result<bool, TransactionConverterError> {
        let contains_proof = proof_manager_client.contains_proof(proof_facts.clone()).await?;

        if contains_proof {
            return Ok(false);
        }

        let proof_facts_hash = proof_facts.hash();
        let verify_start = Instant::now();
        tokio::task::spawn_blocking(move || {
            starknet_proof_verifier::verify_proof(proof_facts, proof)
        })
        .await
        .expect("proof verification task panicked")?;
        let verify_duration = verify_start.elapsed();
        PROOF_VERIFICATION_LATENCY.record(verify_duration.as_secs_f64());
        info!(
            "Proof verification took: {verify_duration:?} for proof facts hash: \
             {proof_facts_hash:?}"
        );

        Ok(true)
    }

    pub async fn set_proof(
        &self,
        proof_facts: ProofFacts,
        proof: Proof,
    ) -> Result<(), FsProofStorageError> {
        if self.contains_proof(proof_facts.clone()).await? {
            return Ok(());
        }
        let facts_hash = proof_facts.hash();
        self.proof_storage.set_proof(facts_hash, proof.clone()).await?;
        self.cache.insert(facts_hash, proof);
        Ok(())
    }

    pub async fn get_proof(
        &self,
        proof_facts: ProofFacts,
    ) -> Result<Option<Proof>, FsProofStorageError> {
        let facts_hash = proof_facts.hash();
        // Check cache first.
        if let Some(proof) = self.cache.get(&facts_hash) {
            return Ok(Some(proof));
        }
        // Fallback to filesystem.
        let proof = self.proof_storage.get_proof(facts_hash).await?;
        if let Some(proof) = &proof {
            self.cache.insert(facts_hash, proof.clone());
        }
        Ok(proof)
    }

    pub async fn contains_proof(
        &self,
        proof_facts: ProofFacts,
    ) -> Result<bool, FsProofStorageError> {
        let facts_hash = proof_facts.hash();
        // Check cache first.
        if self.cache.contains(&facts_hash) {
            return Ok(true);
        }
        // Fallback to filesystem.
        self.proof_storage.contains_proof(facts_hash).await
    }
}

#[async_trait::async_trait]
impl ProofStorage for FsProofStorage {
    type Error = FsProofStorageError;

    async fn set_proof(&self, facts_hash: Felt, proof: Proof) -> Result<(), Self::Error> {
        self.write_proof_atomically(facts_hash, proof).await
    }

    async fn get_proof(&self, facts_hash: Felt) -> Result<Option<Proof>, Self::Error> {
        if !self.contains_proof(facts_hash).await? {
            return Ok(None);
        }

        match self.read_proof_from_file(facts_hash).await {
            Ok(proof) => Ok(Some(proof)),
            Err(FsProofStorageError::IoError(e)) if e.kind() == std::io::ErrorKind::NotFound => {
                Ok(None)
            }
            Err(e) => Err(e),
        }
    }

    async fn contains_proof(&self, facts_hash: Felt) -> Result<bool, Self::Error> {
        Ok(tokio::fs::try_exists(self.get_persistent_dir(facts_hash)).await?)
    }
}
