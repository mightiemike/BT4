This confirms the analog: `KVSessionStorage.storeSession` is invoked repeatedly for the *same* session id via normal, unprivileged flows — every offline token refresh (`ensureOfflineTokenIsNotExpired` when `expiringOfflineAccessTokens` is on, triggered automatically near token expiry) and every token-exchange re-authentication (`performTokenExchange`/`token-exchange.ts` strategies, triggered whenever the online/offline session becomes inactive) — and each call unconditionally appends the id to the per-shop KV array without de-duplication, unlike the Redis adapter's equivalent method.

### Title
Unbounded, non-deduplicated growth of the per-shop session-id array in `KVSessionStorage` leads to storage/DoS of session persistence and lookup - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.addShopIds` appends the session id to the shop's index array on every `storeSession` call without checking whether the id is already present, unlike the sibling `RedisSessionStorage.addKeyToShopList`, which explicitly guards against duplicates before pushing.

### Finding Description
`storeSession` unconditionally calls `addShopIds(session.shop, [session.id])` on every store: [1](#0-0) 

`addShopIds` reads the existing `shopIds` array and appends the new id(s) with no deduplication check: [2](#0-1) 

Compare to `RedisSessionStorage.addKeyToShopList`, which explicitly checks `if (!idKeysArray.includes(idKey))` before pushing: [3](#0-2) 

Session ids in this library are deterministic and stable for a given shop/user pair (e.g. `${shop}_${userId}` for online sessions, `offline_${shop}` for offline sessions), so re-storing the *same* session id is a normal, unprivileged, and frequent event, not an edge case: [4](#0-3) 

Two unprivileged/anonymous-adjacent flows repeatedly re-store the *same* offline/online session id:
1. Automatic offline-token refresh, which stores the (same-id) refreshed session every time it is within 5 minutes of expiry — an event automatically retried on every subsequent request until the app is used again: [5](#0-4) 
2. Token-exchange re-authentication, triggered any time a request's session is inactive/expired, which re-stores the offline (and optionally online) session with the same deterministic id: [6](#0-5) [7](#0-6) 

Because `addShopIds` never checks for existing entries, every one of these re-store events adds another duplicate copy of the same id string to the `shop:${shop}` KV value. Over the life of an installed app (which routinely refreshes/re-derives its offline token, especially with `future.expiringOfflineAccessTokens` enabled) this array grows without bound, exactly mirroring the audit's structural root cause: an index/sequence structure that is only ever appended to, with no compaction on the equivalent "remove" or "no-op" path (`deleteSession`'s `removeShopIds` does filter properly, but that only helps on explicit deletion, not on the far more frequent re-store path).

### Impact Explanation
`findSessionsByShop` reads this exact array and performs one KV `get` per entry: [8](#0-7) 
As the shop-index array accumulates duplicate ids indefinitely, `findSessionsByShop` incurs growing, redundant KV read amplification (used by app-installation checks, uninstall/GDPR webhook handlers, and app-level session enumeration), degrading and eventually threatening the availability of these operations for that shop. Separately, `storeSession`/`addShopIds` serializes the entire growing array and writes it back as a single KV value on every store; unbounded growth risks approaching Cloudflare KV per-value size limits, at which point every subsequent `storeSession` call for that shop (i.e. every OAuth/token-exchange re-authentication) would fail, denying the shop the ability to re-authenticate — a DoS of the auth/session-refresh handler for that tenant.

### Likelihood Explanation
This requires no privileged actor and no malicious input: it is triggered purely by normal use of standard, documented features (offline-token refresh via `future.expiringOfflineAccessTokens`, or plain token-exchange re-authentication whenever a session is expired/inactive), both of which occur automatically and repeatedly for every merchant using `KVSessionStorage`. The longer an app using this adapter runs in production, the worse the effect, matching the audit's "temporal fund/DoS freeze that grows over time" framing.

### Recommendation
Update `addShopIds` in `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts` to deduplicate before writing, mirroring the Redis adapter's guard, e.g.:
```ts
private async addShopIds(shop: string, ids: string[]) {
  const key = this.getShopSessionIdsKey(shop);
  const shopIds = (await this.namespace.get<string[]>(key, 'json')) ?? [];
  const merged = Array.from(new Set([...shopIds, ...ids]));
  await this.namespace.put(key, JSON.stringify(merged));
}
```

### Proof of Concept
1. Configure an app with `KVSessionStorage` and `future.expiringOfflineAccessTokens: true` (React Router/Remix) or plain token-exchange (Express/any adapter).
2. Install the app on a shop; note the offline session id is deterministic (`offline_${shop}`).
3. Let the offline token approach expiry repeatedly (or simulate repeated calls to `ensureOfflineTokenIsNotExpired`/`performTokenExchange` with the same session id) across many requests/days.
4. Inspect the KV value at key `shop:${shop}` after each cycle — its JSON array grows by one duplicate `offline_${shop}` entry per refresh cycle, with no bound, while `moneyMarkets`-equivalent real state (the single actual offline session) never changes.
5. Call `findSessionsByShop(shop)`; observe an ever-increasing number of redundant `namespace.get` calls proportional to the array's unbounded length, degrading over time toward failure/DoS as the array size approaches KV value limits.
