### Title
Cross-transaction replay of identical ReceiveDescription (cv/cm/epk/zkproof/c_out) causes duplicate incoming-note counting in `scanNoteByOvk`/`scanShieldedTRC20NotesByOvk` - ([File: framework/src/main/java/org/tron/core/zen/note/OutgoingPlaintext.java])

### Summary
`OutgoingPlaintext.decrypt` is a pure, stateless cryptographic function bound only to `(ovk, cv, cm, epk, c_out)` with no reference to the enclosing transaction's spend descriptions, nullifiers, or txid. Because the chain's shielded-transfer validation only rejects duplicate `cm` values *within a single transaction*'s `receiveDescriptionList` (not across transactions/blocks), and because Sapling output proofs (`checkOutput`) are self-contained relations over `(cv, cm, epk, zkproof)` independent of transaction context, an attacker can copy a full `ReceiveDescription` byte-for-byte into a second, independently-funded `ShieldedTransferContract` and have it validate successfully, causing wallet-facing OVK scanning tools to report the same underlying note as two separate incoming payments.

### Finding Description
`OutgoingPlaintext.decrypt(ciphertext, ovk, cv, cm, epk)` in `framework/src/main/java/org/tron/core/zen/note/OutgoingPlaintext.java:35-44` derives `ock = PRF(ovk, cv, cm, epk)` and decrypts `c_out` with it — this is a deterministic function of only these five values, with no dependence on the transaction ID, nullifiers, or spend descriptions of the enclosing transaction. It is called identically from `Wallet.scanNoteByOvk` (`framework/src/main/java/org/tron/core/Wallet.java:3504-3509`) and `Wallet.getNoteTxFromLogListByOvk` (`framework/src/main/java/org/tron/core/Wallet.java:4052-4053`), both of which loop over on-chain `ReceiveDescription`/log records and, on a successful decrypt, append an entry to the returned note list keyed only by `(txid, index)` — never checking whether the underlying `(cv, cm, epk, c_out)` tuple has already been counted in a prior on-chain event.

On the consensus/actuator side, `ShieldedTransferActuator.validate()` (`actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java:250-256`) only guards against duplicate `cm` **within the same transaction's `receiveDescriptionList`** ("duplicate cm in receive_description"). There is no chain-wide/global uniqueness check on `cm` (or on `cv`/`epk`/`c_out`) across different transactions. `MerkleContainer.saveCmIntoMerkleTree` (`chainbase/src/main/java/org/tron/common/zksnark/MerkleContainer.java:83-89`) unconditionally appends the given `cm` to the tree with no existence check. `ShieldedTransferActuator.checkProof` (`actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java:308-322`) validates `librustzcashSaplingCheckOutput(cv, cm, epk, zkproof)` — a pure cryptographic relation that holds regardless of which transaction it appears in, so a proof generated for one transaction remains valid if pasted verbatim into another. Consequently, an attacker who captures a public `ReceiveDescription` from a settled transaction can embed the identical bytes into a new `ShieldedTransferContract` (supplying independent, validly-funded `SpendDescription`s/nullifiers and a matching binding signature for the new transaction's `valueBalance`), and this second transaction will pass `validate()`/`checkProof()`/`execute()` without error.

Once both transactions are on-chain, a wallet or exchange-style service holding the corresponding `ovk` and calling `scanNoteByOvk`/`scanShieldedTRC20NotesByOvk`/`getNoteTxFromLogListByOvk` will successfully decrypt the `c_out` for both occurrences (since decryption is stateless per the reasoning above) and emit two separate `NoteTx` entries — one per `(txid, index)` — even though they represent the same underlying note payload. Nothing in the OVK-scanning code path or in consensus enforces "one settlement per unique note event," so downstream tooling summing `NoteTx.getNote().getValue()` per emitted entry will double-count the incoming value.

### Impact Explanation
Wallet/exchange-facing tooling that uses `scanNoteByOvk`, `scanShieldedTRC20NotesByOvk`, or `getNoteTxFromLogListByOvk` to compute a depositor's incoming shielded balance for deposit-crediting or spend-eligibility decisions will over-count the credited amount, because the same commitment/ciphertext tuple is reported once per occurrence on-chain rather than once per logical note. This can lead to incorrect balance displays and potentially incorrect downstream spend/withdrawal decisions if such tooling trusts the scan output as an authoritative ledger of received value.

### Likelihood Explanation
The precondition is that an attacker can fund `fromAmount` twice (once per transaction) and reuse a previously observed public `ReceiveDescription`'s bytes verbatim in a second transaction with fresh spend inputs; both `SpendDescription` and `ReceiveDescription` fields are fully attacker-controlled/public information (broadcast on-chain), and no code path in `ShieldedTransferActuator` or `MerkleContainer` rejects a repeated `cm`/`cv`/`epk`/`zkproof`/`c_out` combination across different transactions. The only obstacle is the attacker's own funding cost for the duplicate transaction, which is a cost, not a technical barrier — the check is completely absent rather than merely weak.

### Recommendation
Add a chain-wide duplicate-commitment guard: maintain a persistent index (or leverage the note-commitment tree) to reject `ReceiveDescription`s whose `noteCommitment` (or the full `(cv, cm, epk, c_out)` tuple) has already been included in any previously accepted transaction, not just within the current transaction's `receiveDescriptionList`. Alternatively/additionally, have `scanNoteByOvk`/`scanShieldedTRC20NotesByOvk`/`getNoteTxFromLogListByOvk` deduplicate on the underlying `(cv, cm, epk, c_out)` tuple (or `cm` alone) rather than solely relying on `(txid, index)`, so replayed ReceiveDescriptions are not double-reported to wallet consumers.
