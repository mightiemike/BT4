### Title
Permanent lock of ETH-implicit Wallet Contract via unresettable `has_in_flight_tx` mutual-exclusion flag - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The reported Basis Finance bug is a "conflicting exclusive-authorization" pattern: two legitimate callers each require exclusive control of a resource, but the resource can only grant that exclusivity to one of them, so the other caller's calls permanently fail. The closest reachable analog in this nearcore snapshot is the `WalletContract`'s `has_in_flight_tx` mutual-exclusion invariant, which plays the same "single exclusive gate" role as `onlyController`: it must be set to `true` whenever a promise is outstanding and reset to `false` by the corresponding callback. If any callback panics (host error, out-of-gas, deserialization failure of an untrusted response) before reaching the `self.has_in_flight_tx = false` reset, the flag is never cleared, and the account becomes permanently unable to execute any further `rlp_execute` calls.

### Finding Description
`WalletContract` holds a single boolean, `has_in_flight_tx`, documented as an invariant: it must be `true` whenever a mutable method returns a `Promise` and `false` otherwise [1](#0-0) .

`rlp_execute` is gated by this flag: if it is `true`, every call is rejected outright with "transaction already in progress" [2](#0-1) .

The flag is only cleared inside the follow-up callback functions (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), each of which starts by unconditionally setting `self.has_in_flight_tx = false` before doing any other work [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) .

`nep_141_storage_balance_callback` deserializes an *untrusted* JSON response coming back from an arbitrary NEP-141 token account (`token_id`) that is itself specified inside the RLP-encoded, user/relayer-supplied Ethereum transaction being emulated [7](#0-6) . The static gas budget attached to this callback is fixed and relatively small (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, composed of a few 5 Tgas increments) [8](#0-7) .

Because `self.has_in_flight_tx = false` is the *first* statement in the callback, any state mutation performed by that method — including the reset — is applied only if the callback's execution completes without a runtime-level failure (host error, WASM trap, or running out of the allotted static gas). If execution of the callback function itself fails at the runtime level before completing the deserialization / promise-chaining logic (e.g., the WASM contract traps or exceeds its gas limit while parsing an oversized/malicious response), the entire receipt fails and none of the contract's state writes for that receipt — including the `has_in_flight_tx = false` write — are applied, because state changes within a single receipt/function-call execution are all-or-nothing. Since `token_id` is attacker-influenceable (the "target"/token contract referenced by the emulated Ethereum transaction can be any account, including one deployed and controlled by an attacker), an attacker can deploy a malicious NEP-141-like contract that responds to `storage_balance_of` with a payload engineered to make deserialization/processing in `nep_141_storage_balance_callback` exceed the assigned static gas or otherwise trap, causing the wallet's callback receipt to fail outright.

There is no other public method in `WalletContract` that can reset `has_in_flight_tx` back to `false` once it is stuck at `true` — every reset path lives inside a callback that is only reachable by first successfully executing the original promise chain that got stuck.

### Impact Explanation
Once `has_in_flight_tx` is permanently stuck at `true`, `rlp_execute` unconditionally rejects every future call for that ETH-implicit account, regardless of who signs it (owner or any registered relayer key) [9](#0-8) . Since ETH-implicit accounts can *only* be used by calling Wallet Contract methods (they have no full access key and cannot be deleted) [10](#0-9) , this permanently freezes the account and any $NEAR/NEP-141 balance it holds — no transfer, function call, or key management action can ever be executed by the account's rightful owner again. This matches the "permanently frozen funds" impact category.

### Likelihood Explanation
Reachability requires only a single transaction/RLP-encoded Ethereum transaction routed through `rlp_execute`, targeting an ERC-20/NEP-141 transfer whose token contract is attacker-controlled (a token contract the attacker deploys themselves, which is trivial for anyone to do). The attacker does not need any special privilege, validator status, or network position — this is purely a user-to-contract call. The exact gas/response-size threshold needed to trigger an out-of-gas panic inside the callback is implementation-specific and was not empirically measured against the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget in this review; confirming the exact bound requires running the contract with a crafted oversized `storage_balance_of` response and checking whether it exceeds the ~15 Tgas static allocation. This is the main uncertainty in this finding.

### Recommendation
- Ensure the `has_in_flight_tx` reset is unconditionally guaranteed regardless of what happens later in the callback, e.g., structure each callback so the very first action performed writes `has_in_flight_tx = false` to storage directly (flush storage write before doing any further computation that could panic), or split "clear the in-flight flag" into its own minimal-gas leading receipt/action that cannot fail.
- Bound/limit the amount of untrusted data that is deserialized from external contract responses (`storage_balance_of`) before it is processed, and fail gracefully (returning an `ExecuteResponse` with `success: false`) rather than trapping, for any oversized or malformed payload.
- Add an explicit, permissionless "unstick" mechanism (e.g., a timeout-based self-callback, similar to yield/resume timeouts elsewhere in the runtime) that can clear `has_in_flight_tx` if a promise chain never completes within an expected window, preventing indefinite account freezing.
- Add fuzz/adversarial tests that make the downstream token contract return oversized or gas-exhausting responses to confirm the callback cannot fail mid-way without clearing the flag.

### Proof of Concept
1. Attacker deploys a malicious NEP-141-style contract `evil_token.near` whose `storage_balance_of` method returns an extremely large/deeply nested JSON payload (or otherwise induces expensive computation on the receiving side).
2. Attacker (or unwitting relayer on behalf of a real user) submits an RLP-encoded Ethereum "ERC20 transfer" transaction through `rlp_execute(target: eth_implicit_account, tx_bytes_b64)` where the transfer's token is `evil_token.near` and the receiver is unregistered, forcing the code path through `nep_141_storage_balance_callback` [7](#0-6) .
3. `rlp_execute` sets `has_in_flight_tx = true` and schedules the promise chain [11](#0-10) .
4. `evil_token.near::storage_balance_of` returns its crafted payload; the follow-up `nep_141_storage_balance_callback` execution traps/exceeds gas while processing it, before it can persist `has_in_flight_tx = false`.
5. Because the callback's receipt failed, no state changes (including the flag reset) are committed; `has_in_flight_tx` remains `true` in the account's persisted state.
6. Any subsequent call to `rlp_execute` for this account — from the owner or any relayer — immediately returns `"Error: transaction already in progress, please try again later."` forever, since nothing in the contract can ever clear the flag again [9](#0-8) .

*(Note: the precise gas/payload size needed to reliably trigger an OOG trap inside `nep_141_storage_balance_callback` was not verified by execution in this review; this is the primary open question for confirming exploitability with certainty.)*

                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();

            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)

                let promise = create_ban_relayer_promise(current_account_id);

                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
