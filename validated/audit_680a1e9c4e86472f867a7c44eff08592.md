This confirms the flow: `authenticate.webhook(request)` loads the victim shop's real offline session (with its access token) and constructs an `admin` client bound to it, purely based on the unsigned `domain`/`shopify-shop-domain` header, since `validateHmacFromRequestFactory` only ever hashes `rawBody` — never the shop domain, topic, or `webhookType`.

### Title
Webhook `domain` (shop identity) is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: packages/apps/shopify-api/lib/webhooks/validate.ts])

### Summary
Shopify webhook requests are authenticated by comparing an HMAC computed over the raw request body against the `X-Shopify-Hmac-Sha256` / `shopify-hmac-sha256` header, using the app's single, shop-independent `apiSecretKey`. However, the value that binds the webhook to a specific merchant — the `domain` header (`X-Shopify-Shop-Domain` / `shopify-shop-domain`) — and the `webhookType` discriminator are never included in the signed data. This is the same class of bug as the "nlrType not signed" report: a discriminator/identity field that downstream code uses to select behavior is not covered by the cryptographic signature that is supposed to make the whole request trustworthy.

### Finding Description
`validateHmacFromRequestFactory` computes the local HMAC solely from `rawBody` and the app's secret, and compares it to the `hmac` header value: [1](#0-0) 

`detectWebhookType` and `checkWebhooksHeaders`/`checkEventsHeaders` then read the `domain`, `topic`, `webhookId`, etc. straight out of the (unsigned) request headers and return them as `valid: true` fields, with no cryptographic linkage to the body that was actually verified: [2](#0-1) [3](#0-2) 

Both `shopify-app-remix` and `shopify-app-react-router`'s `authenticateWebhookFactory` then trust `check.domain` as-is to load the tenant's offline session and admin client: [4](#0-3) 

`ensureValidOfflineSession` uses that shop string to fetch the real, stored offline access token for that shop: [5](#0-4) [6](#0-5) 

Because the app's `apiSecretKey` is shared across every shop that installs the app (it is not per-tenant), any merchant who installs the app on their own store can:
1. Trigger a real webhook delivery to their own endpoint (e.g. by creating/updating a resource that fires a subscribed topic), obtaining a body + a valid HMAC computed with the shared app secret.
2. Replay that exact `(rawBody, hmac)` pair to the app's webhook endpoint, but with the `domain` header changed to a victim shop that also has the app installed.
3. `validateHmacFromRequestFactory` accepts it (the HMAC only ever depended on `rawBody` and the shared secret, which are unchanged), and `checkWebhooksHeaders`/`checkEventsHeaders` happily report `domain: <victim shop>`.
4. `authenticate.webhook` loads the victim's real offline session/admin client and hands attacker-controlled payload data to the app's webhook handler, attributed to the victim shop.

### Impact Explanation
This allows an unprivileged single-merchant attacker to forge a webhook "from" any other shop that has the app installed, causing the app's webhook handler logic to run against the victim shop's real offline session/admin API access token with attacker-supplied body content. Depending on what the app's webhook handlers do (write to the victim's database records keyed by shop, call the Admin API on the victim's behalf, trigger billing/state transitions, etc.), this is a cross-tenant data integrity/confidentiality issue and a form of forged-request acceptance, matching the "accepted forged Shopify request / cross-tenant access" class explicitly called out in scope.

### Likelihood Explanation
No secrets need to be leaked and no MITM is required — the attacker only needs to be a legitimate merchant who installs the app on their own store (a normal, unprivileged action), which is enough to obtain a validly-HMAC-signed `(body, hmac)` pair they can then replay with a spoofed `domain` header against the shared webhook endpoint. The `webhooks.validate` API design (HMAC over body only, identity carried in unsigned headers) is present in both `shopify-app-remix` and `shopify-app-react-router` webhook authentication paths, and in `shopify-app-express`'s `processWebhooks` flow as well.

### Recommendation
Bind the request's claimed identity fields (`domain`/shop, `webhookType`, `topic`) to the cryptographic check rather than trusting them from unsigned headers alone. Concretely: after HMAC validation succeeds, cross-check the resolved `domain` against an expected/allow-listed value tied to the session or connection context where possible, and/or extend the HMAC canonicalization to include the header-derived identity fields (analogous to the recommended fix of packing the discriminator into the signed leaf in the original report) so that a body signed for one shop cannot be replayed under a different shop's identity.
