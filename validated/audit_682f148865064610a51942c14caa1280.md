### Title
Hardcoded, non-configurable 5% swap slippage tolerance in gas-abstraction and gas-refund swaps enables sandwich extraction of user/protocol funds - ([File: x/uexecutor/keeper/execute_inbound_gas.go], [File: x/uexecutor/keeper/outbound.go])

### Summary
The external report's "royalty/fee percentage hardcoded" bug class maps directly onto Push Chain's gas-abstraction and gas-refund swap logic. Instead of a fee percentage, the analog here is a hardcoded slippage-tolerance constant (`95/100`, i.e. 5%) used to compute `minPCOut` for on-chain Uniswap V3 swaps executed by the `uexecutor` module on behalf of users. It is not configurable by governance/admin and is applied uniformly regardless of pool liquidity, swap size, or volatility.

### Finding Description
Two independent flows compute `minPCOut` identically:

- `ExecuteInboundGas` (gas-abstraction swap on inbound): [1](#0-0) 

- `applyGasRefund` (unused-gas refund swap on outbound): [2](#0-1) 

In both cases the module:
1. Fetches a spot quote via `GetSwapQuote`, which calls Uniswap V3 `QuoterV2.quoteExactInputSingle` — a spot-price read against current pool reserves, not a TWAP or manipulation-resistant price source: [3](#0-2) 
2. Computes `minPCOut = quote * 95 / 100` — a hardcoded 5% tolerance with no way to tighten/loosen it per pool, per amount, or via params/governance.
3. Immediately executes the real swap on-chain via `CallPRC20DepositAutoSwap` / `CallUniversalCoreRefundUnusedGas`, both using `DerivedEVMCall` (module-originated EVM execution): [4](#0-3)  and [5](#0-4) .

Because the triggering transactions (`MsgVoteInbound`/`MsgVoteOutbound` finalizing the ballot that causes this deterministic swap to execute) are ordinary, publicly-broadcast transactions visible pre-inclusion, an unprivileged attacker who can see them (mempool, gossip, or predict from ordinary user deposit activity) can sandwich the pool: push the spot price down immediately before the module's swap executes (in an earlier position in the same block) and push it back up immediately after. Since `minPCOut` is derived from the same manipulated spot price the attacker created, the check always passes, and the module still executes the swap—suffering up to the full 5% loss on the swap notional, which the attacker captures.

### Impact Explanation
This directly corrupts refund/gas-abstraction accounting: users receive materially less PC than the honest market rate would yield, and the difference (up to 5% of swap notional per finalized inbound/outbound) is extracted by the attacker. This is a fund-loss vector reachable purely by an unprivileged external actor observing normal user cross-chain deposits/outbound settlements, matching the "corruption of PRC20 or native asset accounting, gas fee accounting, refund accounting" and "unauthorized ... unauthorized refund of user or protocol-controlled funds" impact categories. Because the constant is hardcoded and cannot be adjusted (e.g., tightened for low-liquidity pools or governed dynamically), this is a systemic, unpatchable-without-upgrade weakness — the exact analog of the "royalty hardcoded" finding: the fix pattern (make the parameter admin/governance-updatable) is the same recommended remediation.

### Likelihood Explanation
Likelihood is high on any PRC20/pool with moderate-to-low liquidity relative to swap size, since 5% is a large, static tolerance band regardless of trade size. Every gas-abstraction inbound and every outbound with excess-gas refund triggers this code path, so the attack surface recurs continuously and is fully mempool-observable, requiring no privileged access — only capital to front-run/back-run the pool.

### Recommendation
Replace the hardcoded `95/100` divisor with a governance/admin-configurable parameter (e.g., in `uexecutor` module params), and/or replace the spot-price `QuoterV2` read with a TWAP-based or otherwise manipulation-resistant price source before computing `minPCOut`. Consider bounding slippage per swap size/pool liquidity rather than using one fixed constant for both the gas-abstraction and refund-swap code paths.

### Proof of Concept
1. Attacker monitors the mempool/block for an inbound deposit or outbound-refund event about to be finalized by validator votes (`MsgVoteInbound`/`MsgVoteOutbound`), which will trigger `ExecuteInboundGas` or `applyGasRefund`.
2. Attacker submits a large swap against the same PRC20/WPC pool with a higher gas price to land immediately before the module's deterministic swap in the same block, moving the spot price against the module's forthcoming swap.
3. The module calls `GetSwapQuote` → `quoteExactInputSingle`, which reads the now-manipulated spot price, and computes `minPCOut = quote*95/100` based on that skewed price: [6](#0-5) .
4. The module's swap executes at the bad price but still satisfies `minPCOut` (since both were derived from the manipulated state), so no revert occurs.
5. Attacker submits a back-run trade restoring the price, capturing the ~5% spread as profit at the expense of the user's/protocol's refunded or swapped PC amount.

Note: I was not able to fully verify block-ordering guarantees (whether validators/proposers could reorder transactions within a block to prevent adjacent front/back-run placement) from the indexed code alone; this would require deeper review of block proposal / mempool ordering logic outside `x/uexecutor`, which may not be fully present in the indexed snippets. If precise confirmation of MEV-orderability guarantees is needed, a full Devin session with repository access would be required to trace the mempool/proposer logic exhaustively.

```go
// GetSwapQuote calls QuoterV2.quoteExactInputSingle (commit=false) to get the expected
// output amount for swapping prc20 → wpc.
func (k Keeper) GetSwapQuote(
	ctx sdk.Context,
	quoterAddr, prc20Address, wpcAddress common.Address,
	fee, amount *big.Int,
) (*big.Int, error) {
	quoterABI, err := types.ParseUniswapQuoterV2ABI()
	if err != nil {
		return nil, errors.Wrap(err, "failed to parse QuoterV2 ABI")
	}

	ueModuleAccAddress, _ := k.GetUeModuleAddress(ctx)

	params := types.AbiQuoteExactInputSingleParams{
		TokenIn:           prc20Address,
		TokenOut:          wpcAddress,
		AmountIn:          amount,
		Fee:               fee,
		SqrtPriceLimitX96: big.NewInt(0),
	}

	receipt, err := k.evmKeeper.CallEVM(ctx, quoterABI, ueModuleAccAddress, quoterAddr, false, nil, "quoteExactInputSingle", params)
	if err != nil {
		return nil, errors.Wrap(err, "QuoterV2 quoteExactInputSingle failed")
	}

	results, err := quoterABI.Methods["quoteExactInputSingle"].Outputs.Unpack(receipt.Ret)
	if err != nil {
		return nil, errors.Wrap(err, "failed to unpack quoteExactInputSingle result")
	}

	amountOut, ok := results[0].(*big.Int)
	if !ok {
		return nil, fmt.Errorf("unexpected type for amountOut: %T", results[0])
	}

	return amountOut, nil
```
