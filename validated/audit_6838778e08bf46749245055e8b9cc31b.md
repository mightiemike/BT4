### Title
Deleting an account with a nonexistent or invalid beneficiary permanently burns the account's entire balance - (File: runtime/runtime/src/actions.rs)

### Summary
`action_delete_account` sends the deleted account's full balance to `beneficiary_id` via a system-generated balance-refund receipt with no validation that `beneficiary_id` refers to an existing (or creatable) account. If it does not, the refund receipt fails and the funds are irrecoverably burned rather than returned to the account owner or the transaction failing atomically.

### Finding Description
Any account owner (an unprivileged transaction signer) can submit a `DeleteAccount` action specifying an arbitrary `beneficiary_id`. In `action_delete_account` (`runtime/runtime/src/actions.rs:330-407`), the account's current balance is unconditionally scheduled to be moved to the beneficiary via `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` (`runtime/runtime/src/actions.rs:382-386`), and the account itself is deleted immediately (`remove_account`, `*account = None`) in the same receipt — the delete is irreversible once this action executes.

The generated refund receipt is a system-predecessor `ActionReceipt` containing a single `Transfer` action (`docs/RuntimeSpec/Refunds.md:13`). When this receipt is later processed against `beneficiary_id`, `check_account_existence` (`runtime/runtime/src/actions.rs:814-850`) calls `implicit_creation_allowed` (`runtime/runtime/src/actions.rs:928-947`), which explicitly returns `false` whenever `is_refund` is true ("Refund can never create an account", line 932) — confirmed for every account type by the unit test `test_implicit_creation_allowed` (`runtime/runtime/src/actions.rs:2578-2622`, "Refunds are free, and account deletion with a beneficiary makes one, so no kind may be created by one however lonely the transfer is"). Thus if `beneficiary_id` is a named account that has never been created, or any implicit/deterministic/universal account ID that has not been separately created, the refund transfer fails with `ActionErrorKind::AccountDoesNotExist`.

Per `docs/RuntimeSpec/Refunds.md:12`: "If the execution of a refund fails, the refund amount is burnt." This is implemented in `runtime/runtime/src/lib.rs:1047-1054`: for a receipt whose `predecessor_id().is_system()` (i.e., a refund), a failed result adds `total_deposit(&action_receipt.actions())` to `stats.balance.other_burnt_amount` — permanently removing the tokens from circulation with no path to recovery, no error surfaced back to the original `DeleteAccount` signer (whose transaction already succeeded and whose account is already gone), and no rescue mechanism.

This is the direct analog of the reported "accidentally received ERC20 token can be lost forever" class: user error (a typo'd or unregistered `beneficiary_id`) leads to permanent, unrecoverable loss of the entire account balance, and the protocol provides no rescue/refund-to-sender fallback — the funds are simply burned.

### Impact Explanation
Any account holder who deletes their own account (a routine, permissionless, self-service operation, e.g., account cleanup, migration, or via a dApp/wallet UI) with a mistyped, unregistered, or not-yet-existing `beneficiary_id` permanently and irrecoverably loses their entire account balance (`amount`) to burn. There is no confirmation, no dry-run existence check at signing time, and once the `DeleteAccount` action executes, the source account is deleted immediately in the same receipt — there is no way to retry or redirect the refund. Because the amount lost equals the account's entire NEAR balance (potentially large sums), this is a concrete unauthorized/irrecoverable value destruction ("permanently frozen funds" — in this case funds are worse than frozen, they are destroyed) reachable by any ordinary transaction signer with no privileged access.

### Likelihood Explanation
This requires only a single, ordinary `DeleteAccount` transaction from any account owner specifying a beneficiary account ID that does not exist (e.g., a typo, or an account intended to be created later but not yet created, or an implicit account ID computed incorrectly). No cross-shard timing, malicious peer, or validator collusion is needed — it is entirely self-triggered by an unprivileged signer through the standard transaction path (`DeleteAccountAction`, `docs/RuntimeSpec/Actions.md:278-318`), which validates only that `beneficiary_id` is a syntactically valid account ID, not that it exists.

### Recommendation
Before deleting the account and issuing the balance-refund receipt, verify that `beneficiary_id` exists (or is implicitly-creatable through a non-refund path), and reject the `DeleteAccount` action (analogous to `DeleteAccountStaking`) if it does not, so the whole action fails atomically and the account/balance are preserved. Alternatively, disallow refund receipts from silently burning on failure for the delete-account beneficiary path specifically — e.g., fall back to refunding the original account (if not yet removed) or to a well-known treasury/DAO-recoverable account rather than `other_burnt_amount`, and surface this failure back into the `DeleteAccount` action's own execution outcome instead of a separate, silently-burned refund receipt.

### Proof of Concept
1. Account `alice.near` holds `N` NEAR and has no locked stake.
2. `alice.near` signs and submits `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: "nonexistent123.near" })` where `nonexistent123.near` has never been created (a realistic case of a typo or an account meant to be created in a later, separate transaction).
3. `action_delete_account` (`runtime/runtime/src/actions.rs:330-407`) succeeds: `alice.near` is removed from state (`remove_account`), and a `Receipt::new_balance_refund("nonexistent123.near", N)` is queued.
4. When this refund receipt is later processed, `check_account_existence` → `implicit_creation_allowed` returns `false` (refund receipts never create accounts), producing `ActionErrorKind::AccountDoesNotExist`.
5. Because the receipt's `predecessor_id` is `"system"`, `runtime/runtime/src/lib.rs:1047-1054` adds the full deposit `N` to `stats.balance.other_burnt_amount`.
6. Result: `alice.near`'s account and its entire balance `N` are gone; `nonexistent123.near` never received anything; `N` is permanently burned with no recovery path for `alice.near` or anyone else. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

/// Whether a transfer to an account that does not exist yet may create it.
fn implicit_creation_allowed(account_type: AccountType, receipt_shape: ReceiptShape) -> bool {
    let ReceiptShape { is_refund, is_the_only_action } = receipt_shape;
    if is_refund {
        return false; // Refund can never create an account
    }

    match account_type {
        // Named accounts can never be implicitly created by transfer
        AccountType::NamedAccount => false,
        // Near-implicit, Eth-implicit, and deterministic accounts can only be created
        // if transfer is the only action, to avoid account hijacking.
        AccountType::NearImplicitAccount
        | AccountType::EthImplicitAccount
        | AccountType::NearDeterministicAccount => is_the_only_action,
        // Universal account creation does NOT require transfer to be the only action.
        // It cannot be hijacked by other actions batched with the transfer.
        AccountType::UniversalAccount => true,
    }
}
