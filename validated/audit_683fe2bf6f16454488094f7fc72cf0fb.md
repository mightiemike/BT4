Confirmed: `totalNetWeight`/`totalEnergyWeight` accumulation everywhere (FreezeBalanceV2Actuator/Processor, UnfreezeBalanceV2, CancelAllUnfreezeV2) is always computed as **floored** `frozenBalance / TRX_PRECISION` deltas [1](#0-0) , while `calculateGlobalLimitV2`/`calculateGlobalNetLimitV2`/`calculateGlobalEnergyLimitV2` deliberately preserve **fractional** (non-floored) weight in the per-account share numerator [2](#0-1) . This is exactly the Convergence bug class: two different truncation/order-of-operations paths compute what should be the same proportional share of a globally tracked total, so per-account claimable shares are no longer consistent with the denominator that was accumulated using the other (floored) convention.

### Title
Inconsistent truncation between `totalNetWeight`/`totalEnergyWeight` accumulation and `calculateGlobalNetLimitV2`/`calculateGlobalEnergyLimitV2` fractional-weight share calculation - ([File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java])

### Summary
`TotalNetWeight` and `TotalEnergyWeight` are accumulated network-wide as the sum of every account's **floored** `frozenBalance / TRX_PRECISION` (integer weight units), applied consistently across `FreezeBalanceV2Actuator`, `UnfreezeBalanceV2Actuator`, `CancelAllUnfreezeV2Actuator`, and their native-contract processor equivalents. However, when computing an individual account's bandwidth/energy limit share under the delayed-unfreeze (V2) resource model, `calculateGlobalNetLimitV2`/`calculateGlobalEnergyLimitV2` intentionally use the account's **exact fractional** weight (`frozeBalance` divided by `TRX_PRECISION` without flooring, multiplication deferred to `calculateGlobalLimitV2`) rather than the floored integer weight used to build the denominator `totalWeight`. This mirrors the Sherlock/Convergence `ysTotal` root cause: one code path truncates before multiplying (building the tracked total), the other truncates after multiplying (computing the individual claim), against the same conceptual quantity.

### Finding Description
- Per-account weight contributed to the global denominator is always `frozenBalance / TRX_PRECISION` (integer floor), summed via `addTotalNetWeight`/`addTotalEnergyWeight` on freeze [3](#0-2) , unfreeze [4](#0-3) , and cancel-unfreeze [5](#0-4) .
- `calculateGlobalLimitV1` reproduces this floored-weight convention (`weight = frozeBalance / TRX_PRECISION` then multiply/divide) [6](#0-5) , so V1 individual shares are self-consistent with the floored-weight-summed `totalWeight`.
- `calculateGlobalLimitV2`, used whenever `supportUnfreezeDelay()` is enabled via `calculateGlobalNetLimitV2`/`calculateGlobalEnergyLimitV2` [7](#0-6) [8](#0-7) , explicitly avoids flooring the numerator weight and truncates only at the very end: `(frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)` [2](#0-1) .
- The documentation comment for `calculateGlobalLimitV2` itself states this divergence is intentional ("fractional weight ... is preserved through the multiplication and only truncated at the final divide, so small balances yield the same proportional result as the double-arithmetic path") [9](#0-8) , and this is validated as intended parity with the legacy double formula by `CalculateGlobalLimitHardenTest.testV1FlooredWeightVsV2FractionalWeight`, which explicitly asserts the V1 (floored, 25) and V2 (fractional, 37) results diverge for the same `frozeBalance` [10](#0-9) .
- Because `totalNetWeight`/`totalEnergyWeight` is *always* accumulated with the floored convention (there is no separate "fractional total weight" tracked anywhere in the codebase), every account whose `frozenBalance` is not an exact multiple of `TRX_PRECISION` (1 TRX) receives a bandwidth/energy limit computed from a numerator strictly larger than what was counted into the shared denominator. Summed across all accounts, the aggregate of individually-granted `netLimit`/`energyLimit` shares can exceed `totalNetLimit`/`totalEnergyCurrentLimit`, i.e., the network can allocate more free bandwidth/energy capacity in total than the global limit intends.

### Impact Explanation
This breaks the invariant that per-account resource limit shares sum to (at most) the network-wide `totalNetLimit`/`totalEnergyCurrentLimit`. In the original Convergence bug this type of divergence caused reward-share overallocation and DoS on last claimers; here the resource-limit analog means the aggregate granted free bandwidth/energy can exceed the intended global cap, silently degrading the fairness/scarcity guarantee of TRON's resource model (over-granted "free" resource is not itself a fund-drain, but it is a resource-accounting/consensus-determinism concern since it's part of validated state transitions run by every full node).

### Likelihood Explanation
Every account with a `frozenBalance` (in TRX_PRECISION=1,000,000 sun units) that is not an exact multiple of `TRX_PRECISION` triggers this divergence whenever `supportUnfreezeDelay()`/hardened V2 path is active — this is the default freeze-v2 path for any account with frozen balance below 1 TRX in fractional remainder, which is common in practice (any `FreezeBalanceV2Contract` amount not a whole multiple of 1,000,000 sun).

### Recommendation
Make the individual-share formula use the same truncation convention as the accumulated `totalNetWeight`/`totalEnergyWeight` (i.e., floor the per-account weight to `frozeBalance / TRX_PRECISION` before use in V2 as well), or, if fractional weight is genuinely desired, track a parallel fractional-precision total weight and use it consistently as the denominator in the V2 calculation so that per-account shares remain conservative with respect to the tracked total.

### Proof of Concept
1. Two accounts each freeze 1,500,000 sun (1.5 TRX) for bandwidth via `FreezeBalanceV2Contract`.
2. `totalNetWeight` increases by `1,500,000/1,000,000 = 1` (floored) per account, i.e., `totalNetWeight += 1` twice → `totalNetWeight = 2`.
3. `calculateGlobalNetLimitV2` for each account computes share using fractional weight `1.5`, e.g. with `totalNetLimit=43,200,000,000`, `totalNetWeight=2`: each account gets `1.5 * 43,200,000,000/2 ≈ 32,400,000,000`, so both accounts together are entitled to `~64,800,000,000`, i.e., `1.5x` the `totalNetLimit` denominator would suggest (`2 * (43,200,000,000/2)=43,200,000,000` if using floored weight consistently) — demonstrating the aggregate over-allocation exactly analogous to `CalculateGlobalLimitHardenTest.testV1FlooredWeightVsV2FractionalWeight`'s 25 (V1) vs 37 (V2) divergence for the same input [10](#0-9) .

   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.

      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForBandwidth();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalNetLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }

  public void testV1FlooredWeightVsV2FractionalWeight() {
    dbManager.getDynamicPropertiesStore().saveTotalEnergyCurrentLimit(50_000_000_000L);
    dbManager.getDynamicPropertiesStore().saveTotalEnergyWeight(2_000_000_000L);
    long frozeBalance = 1_500_000L; // 1.5 x TRX_PRECISION

    dbManager.getDynamicPropertiesStore().saveAllowHardenResourceCalculation(1);

    // V1 path
    dbManager.getDynamicPropertiesStore().saveUnfreezeDelayDays(0);
    ownerCapsule.setFrozenForEnergy(frozeBalance, 0L);
    dbManager.getAccountStore().put(ownerCapsule.getAddress().toByteArray(), ownerCapsule);
    long v1New = energyProcessor.calculateGlobalEnergyLimit(ownerCapsule);

    // Legacy V1 expectation: floor(1.5) * 25.0 = 1 * 25 = 25
    Assert.assertEquals(25L, v1New);

    // V2 path with the same balance keeps the fractional weight
    long v2New = energyProcessor.calculateGlobalEnergyLimitV2(frozeBalance);
    // Legacy V2 expectation: 1.5 * 25.0 = 37.5 -> 37
    Assert.assertEquals(37L, v2New);

    // And both must match their respective legacy doubles
    dbManager.getDynamicPropertiesStore().saveAllowHardenResourceCalculation(0);
    long v1Old = energyProcessor.calculateGlobalEnergyLimit(ownerCapsule);
    long v2Old = energyProcessor.calculateGlobalEnergyLimitV2(frozeBalance);
    Assert.assertEquals(v1Old, v1New);
    Assert.assertEquals(v2Old, v2New);
  }
