## Analysis

The report's bug class is: *a function performs a state-changing external call, then keeps using values captured **before** that call to update its own state, producing a stale-vs-actual mismatch*. I looked for this pattern in the pox-5 signer/staking boot contract, which is in scope (`stackslib/src/chainstate/stacks/boot/pox-5.clar`), and found a concrete analog.

### Title
`stake-update` omits the reentrancy guard present in `stake`/`register-signer`, letting an untrusted `signer-manager-validate-stake` call reenter and desynchronize `staker-info` from `signer-shares-staked-for-cycle` — (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`stake-update` computes `current-info`, `prev-unlock-cycle`, and `new-lock-amount` from the caller's *existing* `staker-info` entry, then invokes an attacker-controlled trait call, `signer-manager-validate-stake`, before it uses those pre-computed values to remove/re-add the staker's cycle shares and overwrite `staker-info`. Unlike `stake` [1](#0-0)  and `register-signer` [1](#0-0) , `stake-update` never calls `validate-no-reentrancy` [2](#0-1) .

### Finding Description
`stake-update`'s `let` block snapshots the caller's current lock state:

```
(current-info (unwrap! (get-staker-info tx-sender) ERR_NOT_STAKING))
(prev-unlock-cycle (+ (get first-reward-cycle current-info) (get num-cycles current-info)))
(unlock-cycle (+ prev-unlock-cycle cycles-to-extend))
(new-lock-amount (+ (get amount-ustx current-info) amount-increase))
``` [3](#0-2) 

It then calls the caller-supplied `signer-manager` trait implementation via `signer-manager-validate-stake` [4](#0-3) . This is an arbitrary external contract call — the same class of call that `stake` and `register-signer` explicitly guard against reentrancy for, via `(try! (validate-no-reentrancy))` [1](#0-0)  and [5](#0-4) .

After this untrusted call returns, `stake-update` performs the state mutation using the *stale* pre-call values:

```
(try! (remove-staker-from-cycles tx-sender (+ u1 current-cycle) (- prev-unlock-cycle current-cycle u1) true))
(try! (add-staker-to-signer-cycles tx-sender signer (+ u1 current-cycle) num-cycles new-lock-amount true))
(map-set staker-info tx-sender { amount-ustx: new-lock-amount, first-reward-cycle: (get first-reward-cycle current-info), num-cycles: (+ (get num-cycles current-info) cycles-to-extend), signer: signer })
``` [6](#0-5) 

If the caller's supplied `signer-manager` contract, during its `validate-stake` callback, itself calls back into `pox-5` (e.g., a second `stake-update`, `unstake`, or `register-for-bond` call on the same principal) and mutates `staker-info`/`signer-shares-staked-for-cycle`/`total-shares-staked-for-cycle` in between, the outer call's `remove-staker-from-cycles` and final `map-set staker-info` overwrite that intermediate state using the values captured at entry — exactly the "swap-then-use-stale-balance" pattern from the report, but here applied to signer stake-share accounting instead of a Uniswap pool balance. This can desynchronize `signer-shares-staked-for-cycle` / `total-shares-staked-for-cycle` totals from the staker's actual final lock, which feeds directly into signer-weight computation used elsewhere in the codebase (e.g., `pox_5_make_signer_set` apportions signer weight from these staked totals [7](#0-6) ).

### Impact Explanation
This is a minority-triggerable, unprivileged bug: any single staker can deploy a signer-manager contract they control and call `stake-update` on themselves. The corrupted cycle-share bookkeeping can cause a signer's staked/weighted totals to diverge from the true locked amount, mis-crediting or mis-computing signer weight/reward shares for the affected reward cycle(s) — a reward mis-payment bounded to the staking/reward-sharing mechanism, consistent with the "High" impact category (signer weight/stake divergence, reward mis-payment).

### Likelihood Explanation
Medium-to-High: the only precondition is calling `stake-update` with a caller-authored `signer-manager` contract implementing the `signer-manager-trait`'s `validate-stake` entry point to reenter `pox-5`. No privileged role, majority, or other party's key is required. The asymmetry with `stake`/`register-signer` (which do guard) strongly suggests this is an unintentional omission rather than a deliberate design choice.

### Recommendation
Add `(try! (validate-no-reentrancy))` at the start of `stake-update`, matching `stake` and `register-signer`, before any external trait call is made, and/or re-fetch `current-info`/recompute the cycle-mutation quantities from fresh state immediately before the `map-set`/`remove-staker-from-cycles`/`add-staker-to-signer-cycles` calls rather than relying on values captured prior to the `signer-manager-validate-stake` callback.

### Proof of Concept
1. Attacker stakes normally via `stake`, becoming a member of some signer's cycle-share totals.
2. Attacker deploys a contract implementing `signer-manager-trait` whose `validate-stake` function, upon being invoked, issues a nested `contract-call?` back into `pox-5`'s `stake-update` (or another mutating entry point) for the same `tx-sender`, changing `staker-info`/cycle shares.
3. Attacker calls the outer `stake-update` using this malicious contract as `signer-manager`.
4. `stake-update` snapshots `current-info` at entry, calls into the malicious contract (which reenters and mutates state), then finishes by overwriting `staker-info` and the per-cycle share maps using the stale snapshot values, leaving `total-shares-staked-for-cycle` / `signer-shares-staked-for-cycle` inconsistent with the staker's true final position.

*Note: I was not able to inspect the full body of `validate-no-reentrancy` or confirm the exact downstream Clarity runtime semantics of same-transaction contract-call reentrancy in this repo (e.g., whether some other global guard implicitly blocks it); this should be verified against the `validate-no-reentrancy` implementation and existing reentrancy tests before treating this as confirmed exploitable, but the structural asymmetry between `stake-update` and its sibling guarded functions is concrete and directly supports the finding.*

    where
        I: Iterator<Item = Result<RawPox5Entry, PoxEntryParsingError>>,
    {
        let mut signer_set = HashMap::new();
        let mut total_ustx_locked = 0u128;
        for entry_res in entries {
            let entry = match entry_res {
                Ok(x) => x,
                Err(PoxEntryParsingError::Skip(err_str)) => {
                    warn!(
                        "Error while iterating PoX-5 entries, impacting a single entry. Dropping entry from signer set";
                        "error" => err_str
                    );
                    continue;
                }
                Err(PoxEntryParsingError::Abort(err_str)) => {
                    error!(
                        "Abort-triggering error while iterating PoX-5 entries";
                        "error" => err_str
                    );
                    return Err(ChainstateError::PoxNoRewardCycle);
                }
            };

            total_ustx_locked += entry.amount_ustx;

            signer_set
                .entry(entry.signer_key)
                .and_modify(|existing_entry| *existing_entry += entry.amount_ustx)
                .or_insert_with(|| entry.amount_ustx);
        }
