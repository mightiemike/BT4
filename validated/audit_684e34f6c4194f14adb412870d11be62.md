### Title
Ancient-slot squash silently drops carry-forward tombstones, permanently losing zero-lamport deletion markers and allowing stale, non-zero-lamport account state to reappear in snapshots - (File: accounts-db/src/ancient_append_vecs.rs)

### Summary
`AccountsDb::shrink_collect` produces `tombstones_to_carry_forward`: zero-lamport, index-removed accounts whose bytes must be kept in storage so a later incremental snapshot can still observe and propagate the deletion, as long as the slot is newer than `latest_full_snapshot_slot` [1](#0-0) . Normal shrink correctly rewrites these tombstones into the new storage via `store_tombstones` [2](#0-1) . However, the ancient-squash path (`finish_combine_ancient_slots_packed_internal`) has no tombstone-writing logic at all, and only guards the invariant with a `debug_assert!`, which is compiled out in release builds [3](#0-2) .

### Finding Description
`shrink_collect` decides whether a zero-lamport, single-ref account must be carried forward as a tombstone based solely on `can_purge_zero_lamport_single_ref_after_shrink(slot)`, which compares the slot being shrunk against `latest_full_snapshot_slot` [4](#0-3) . This same `shrink_collect` function is shared code used both by normal per-slot shrink (`shrink_storage`) and by ancient-slot combining/packing (`get_unique_accounts_from_storage_for_combining_ancient_slots` → `shrink_collect`) [5](#0-4) .

In the normal shrink path, any non-empty `tombstones_to_carry_forward` is explicitly rewritten to the new storage and tracked [6](#0-5) . In the ancient-squash path (`combine_ancient_slots_packed_internal` → `write_packed_storages` → `finish_combine_ancient_slots_packed_internal`), there is no equivalent call: the code only asserts that `tombstones_to_carry_forward` is empty, with an explicit comment acknowledging that "the squash write path has no tombstone handling, so a non-empty list here would be silently lost" [7](#0-6) .

The safety of this design relies entirely on the assumption (stated in the same comment) that "ancient squash only runs on slots far older than the latest full snapshot, where tombstones are purgeable." That assumption is enforced only by a `debug_assert!`, not a hard runtime check, and is not otherwise validated at the call site: `combine_ancient_slots_packed_internal` selects ancient slots via `get_sorted_potential_ancient_slots`/`collect_sort_filter_ancient_slots`, which filter by age relative to `oldest_non_ancient_slot` (derived from `max_root` and `ancient_append_vec_offset`/epoch schedule), not by any direct comparison to `latest_full_snapshot_slot` [8](#0-7) [9](#0-8) . `latest_full_snapshot_slot` and the ancient-offset/epoch-schedule-derived boundary are independent, separately-driven values (one tracks snapshot-taking cadence, the other tracks epoch/slot age); there is no code path that ties them together to guarantee the "ancient slot ⇒ older than latest full snapshot" invariant holds in all configurations (e.g., custom `--accounts-db-ancient-offset`, delayed/slow full snapshotting, or bootstrap/backfill scenarios where a full snapshot has not yet advanced far enough).

If that invariant is ever violated — an "ancient" slot is squashed while it is still not older than `latest_full_snapshot_slot` — `shrink_collect` will populate `tombstones_to_carry_forward`, and in a release build the `debug_assert!` does nothing: the tombstone bytes are simply dropped as the ancient storage is rewritten, and the pubkey's zero-lamport marker (already removed from the accounts index by this same shrink) disappears without a trace in the new packed storage.

### Impact Explanation
This mirrors the reported bug class exactly: a piece of state (the tombstone bytes / deletion marker) that exists specifically to prevent replay/resurrection of stale funded state is deleted as a side effect of a maintenance operation (ancient squash), with only a debug-only safety net. The concrete consequence documented by the accompanying test suite for the analogous (correctly-handled) shrink path is: without the tombstone, "the rebuild would resurrect Account1 from the full snapshot" [10](#0-9) . If ancient squash drops a tombstone, a subsequent incremental snapshot taken after the ancient combine will not see the zero-lamport update for that pubkey, while the full snapshot still contains the older non-zero balance. Restoring from full+incremental snapshots (e.g., after a validator restart) would then silently resurrect the account with its old, non-zero lamport balance — a silent balance change / stale-account-load and a bank-hash divergence between honest nodes that took the snapshot at different times relative to the ancient-squash event.

### Likelihood Explanation
Ancient-slot combining is a routine, automatic background maintenance operation on all validators (`shrink_ancient_slots`, invoked continuously as slots age past the ancient offset). The precondition ("ancient slot" implies "older than `latest_full_snapshot_slot`") depends on two independently-configured/derived quantities (`ancient_append_vec_offset` + `EpochSchedule`, versus full-snapshot cadence/timing), and the only enforcement is a `debug_assert!`, which does not run in production/release builds. This makes the safety net non-functional exactly in the deployment configuration (release binaries) where the bug would matter. Whether the invariant can concretely be violated in a stock, default-configured mainnet validator was not fully verified within the scope of this investigation — determining that requires tracing all call sites that set `latest_full_snapshot_slot` relative to the ancient-slot boundary computation, which was not completed here.

### Recommendation
- Replace the `debug_assert!` in `finish_combine_ancient_slots_packed_internal` with a real runtime check (or, better, implement tombstone carry-forward for the ancient-squash write path, mirroring `store_tombstones` used in normal shrink), so the invariant is enforced (or satisfied) in release builds too.
- Alternatively/additionally, make ancient-slot selection explicitly exclude slots not yet older than `latest_full_snapshot_slot`, so the precondition is structurally guaranteed rather than assumed.

### Proof of Concept
Not independently reproduced against a running validator; based on static code analysis:
1. Configure a validator/test harness so an "ancient" slot (per `ancient_append_vec_offset`/epoch schedule) still contains a zero-lamport, single-ref account whose most recent non-zero version is captured in the current `latest_full_snapshot_slot` (i.e., `latest_full_snapshot_slot` has not yet advanced past that ancient slot).
2. Trigger `shrink_ancient_slots`/`combine_ancient_slots_packed`, causing `shrink_collect` on that ancient storage to populate `tombstones_to_carry_forward` (analogous to `test_shrink_collect_carries_forward_existing_tombstones` [11](#0-10)  but reached via the ancient path instead of normal shrink).
3. In a release build, `finish_combine_ancient_slots_packed_internal`'s `debug_assert!` is a no-op, so the tombstone is dropped and not written to the packed ancient storage [12](#0-11) .
4. Take an incremental snapshot; restore from full + incremental snapshots (as in `test_incremental_snapshots_handle_tombstones` [13](#0-12) ) and observe the account reappearing with its stale non-zero balance from the full snapshot.

#[test]
fn test_shrink_collect_carries_forward_existing_tombstones() {
    let accounts_db = AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG);
    let slot = 2;
    // Latest full snapshot older than `slot`: tombstones are not yet purgeable.
    accounts_db.set_latest_full_snapshot_slot(slot - 1);

    let alive_pubkey = Pubkey::new_unique();
    let tombstone_pubkey = Pubkey::new_unique();
    let alive_account = AccountSharedData::new(1, 0, &Pubkey::default());
    let zero_lamport_account = AccountSharedData::new(0, 0, &Pubkey::default());

    let (_temp_dirs, paths) = get_temp_accounts_paths(1).unwrap();
    let storage = Arc::new(AccountStorageEntry::new(
        &paths[0],
        slot,
        100,
        DEFAULT_FILE_SIZE,
        accounts_db.accounts_file_provider,
    ));
    // An ordinary alive account, present in the index.
    append_single_account_with_default_hash(
        &storage,
        &alive_pubkey,
        &alive_account,
        true,
        Some(&accounts_db.accounts_index),
    );
    // A zero-lamport account physically in the storage but NOT in the index: i.e. a tombstone
    // carried forward by a prior shrink of an even-older storage.
    append_single_account_with_default_hash(
        &storage,
        &tombstone_pubkey,
        &zero_lamport_account,
        true,
        None,
    );
    accounts_db.storage.insert(Arc::clone(&storage));
    accounts_db.add_root(slot);

    // Record the tombstone account's offset on the storage's tombstone list, as a prior shrink
    // would have.
    let mut tombstone_offset = None;
    storage
        .accounts
        .scan_accounts_without_data(|offset, account| {
            if account.pubkey == &tombstone_pubkey {
                tombstone_offset = Some(offset);
            }
        })
        .unwrap();
    storage.batch_insert_tombstone_offsets([tombstone_offset.unwrap()]);
    assert_eq!(storage.num_zero_lamport_single_ref_accounts(), 1);

    // Newer than the latest full snapshot: the tombstone must be carried forward, not dropped and
    // not mis-routed into the alive set.
    let mut unique_accounts =
        accounts_db.get_unique_accounts_from_storage_for_shrink(&storage, &ShrinkStats::default());
    let shrink_collect = accounts_db.shrink_collect::<AliveAccounts<'_>>(
        &storage,
        &mut unique_accounts,
        &ShrinkStats::default(),
    );
    assert_eq!(shrink_collect.tombstones_to_carry_forward.len(), 1);
    assert!(shrink_collect.tombstones_total_bytes > 0);
    assert_eq!(
        shrink_collect
            .alive_accounts
            .accounts
            .iter()
            .map(|account| *account.pubkey())
            .collect::<Vec<_>>(),
        vec![alive_pubkey],
    );

    // Once the full snapshot advances to `slot`, the tombstone is purgeable and must be dropped
    // rather than carried forward.
    accounts_db.set_latest_full_snapshot_slot(slot);
    let mut unique_accounts =
        accounts_db.get_unique_accounts_from_storage_for_shrink(&storage, &ShrinkStats::default());
    let shrink_collect = accounts_db.shrink_collect::<AliveAccounts<'_>>(
        &storage,
        &mut unique_accounts,
        &ShrinkStats::default(),
    );
    assert!(shrink_collect.tombstones_to_carry_forward.is_empty());
    assert_eq!(shrink_collect.tombstones_total_bytes, 0);
}
