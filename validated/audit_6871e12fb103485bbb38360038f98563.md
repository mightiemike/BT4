### Title
Missing Declared-Class Validation in `execute_replace_class` in the Starknet OS Diverges from Blockifier's Enforced Check - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/syscall_impls.cairo`)

### Summary
The `replace_class` syscall lets a contract change its own class hash. In the blockifier (the component that actually executes transactions when sequencing a block), `replace_class` is guarded by a check that the target class hash was actually declared before the state is updated. In the Starknet OS Cairo program (the component that re-executes the same block to produce the committed state diff / block hash for proving), the analogous `execute_replace_class` function performs **no such check** — it is explicitly marked with an unresolved `TODO`. This mirrors the "Code Update Operation Has No Validation" bug class from the external report: a privileged state-mutating operation (class/code replacement) is executed without validating that the new target is legitimate, creating a path for divergence between the two execution engines that must agree on the resulting state.

### Finding Description
The blockifier's syscall handler for `ReplaceClass` explicitly reads the compiled class before mutating the state, causing the syscall to fail if the class hash was never declared: [1](#0-0) 

The Cairo-native OS implementation of the very same syscall, `execute_replace_class`, updates `contract_state_changes` directly and never validates that `request.class_hash` corresponds to a declared class — the check is called out as a known gap via an open `TODO`: [2](#0-1) 

The deprecated-syscall variant of the same function in the OS program has the identical omission (no declared-class check before the `dict_update`): [3](#0-2) 

Both the deprecated and non-deprecated `ReplaceClass` selectors in the OS dispatcher route directly into these unchecked implementations: [4](#0-3) [5](#0-4) 

The blockifier's `DeprecatedSyscallExecutor` dispatch confirms `ReplaceClass` is a normal, unprivileged, contract-reachable syscall (any Cairo contract can invoke it from its own execution context): [6](#0-5) 

Because the block-building/sequencing path (blockifier) enforces the "class must be declared" invariant while the block re-execution/proving path (Starknet OS) does not, the two execution engines are not provably equivalent with respect to this syscall. If any code path ever allows the OS to independently accept/execute a `ReplaceClass` request that the blockifier would have rejected (e.g. a future rollback of the blockifier-side check, a different invocation of the OS not preceded by blockifier validation, or a divergent PC/trace on revert semantics), the OS could commit a state change (setting a contract's `class_hash` to an undeclared/arbitrary value) that the reference execution never actually accepted. This breaks the fundamental assumption that "OS re-execution == blockifier execution", which underlies the correctness of the STARK proof and the committed state root.

### Impact Explanation
`class_hash` is a first-class part of `StateEntry`/`ContractState`, which is committed into the state Patricia tree and therefore into the block's state root. An unchecked class-hash write in the OS re-execution path — the exact component responsible for producing the values that get committed into the proof and the state root — is the same bug class as "no validation on a privileged storage/code mutation": absent the declared-class check, the OS accepts and commits a `class_hash` value with no proof that a corresponding compiled class exists anywhere in state. If this divergence is ever exercised (i.e., the class-declared invariant is not otherwise perfectly enforced identically on both engines), it results in a wrong committed root / honest-node divergence between the sequencer's actual execution and the OS's re-execution, which is exactly the "wrong committed root or block hash" / "honest-node divergence" impact class.

### Likelihood Explanation
Today the check exists on the blockifier side, so under normal operation the OS TODO is latent rather than immediately exploitable in isolation — an attacker's `ReplaceClass` request would already be rejected by the blockifier before it is included in a block, so the OS would only ever see already-validated class hashes. However, the missing check is an explicitly acknowledged TODO in the current codebase (dated for 2026-01-01), meaning the developers themselves recognize the invariant is not enforced at the OS layer. Any change that decouples the two execution paths, any bug in the blockifier-side check, or any consumer of the OS that re-executes transactions independent of prior blockifier validation would immediately turn this into an exploitable state-root divergence, with no additional privilege required beyond submitting an ordinary contract call that triggers the `replace_class` syscall.

### Recommendation
Remove the `TODO` and add the same declared-class validation to `execute_replace_class` in both `syscall_impls.cairo` and `deprecated_execute_syscalls.cairo` that already exists in the blockifier (`hint_processor.rs`): before performing the `dict_update` on `contract_state_changes`, assert that `contract_class_changes` (or the class-hash lookup table) contains an entry for `request.class_hash`, mirroring `state.get_compiled_class(request.class_hash)?` in the blockifier. This restores parity between the block-building and re-execution/proving paths and removes reliance on an implicit, undocumented invariant that the OS currently only receives pre-validated inputs.

### Proof of Concept
Not applicable as a live exploit against the current code, because the blockifier-side check in `crates/blockifier/src/execution/deprecated_syscalls/hint_processor.rs:800-804` currently prevents an undeclared class hash from ever reaching the OS. The vulnerability is a structural validation gap in `crates/apollo_starknet_os_program/.../syscall_impls.cairo:881-920` and `.../deprecated_execute_syscalls.cairo:307-329` (both marked with an open `TODO` acknowledging the missing check), which would become directly exploitable by any contract calling `replace_class(undeclared_class_hash)` the moment the two execution engines' validation logic diverges.

// Replaces the class.
func execute_replace_class{
    range_check_ptr,
    syscall_ptr: felt*,
    contract_state_changes: DictAccess*,
    revert_log: RevertLogEntry*,
}(contract_address: felt) {
    alloc_locals;
    let request = cast(syscall_ptr + RequestHeader.SIZE, ReplaceClassRequest*);

    // Reduce gas.
    let success = reduce_syscall_gas_and_write_response_header(
        total_gas_cost=REPLACE_CLASS_GAS_COST, request_struct_size=ReplaceClassRequest.SIZE
    );
    if (success == FALSE) {
        // Not enough gas to execute the syscall.
        return ();
    }

    let class_hash = request.class_hash;

    // TODO(Yoni, 1/1/2026): Check that there is a declared contract class with the given hash.
    local state_entry: StateEntry*;
    %{ GetContractAddressStateEntry %}

    tempvar new_state_entry = new StateEntry(
        class_hash=class_hash, storage_ptr=state_entry.storage_ptr, nonce=state_entry.nonce
    );

    dict_update{dict_ptr=contract_state_changes}(
        key=contract_address,
        prev_value=cast(state_entry, felt),
        new_value=cast(new_state_entry, felt),
    );

    assert [revert_log] = RevertLogEntry(selector=CHANGE_CLASS_ENTRY, value=state_entry.class_hash);
    let revert_log = &revert_log[1];

    return ();
}
