**Analysis:**

The current implementation of `sigma_protocol_representation_vec.move` fully closes this attack path. The `RepresentationVec` struct's `v` field has no visibility modifier (private by Move's default rules), and the module declares an explicit, fixed `friend` list restricting all constructors/mutators to a whitelisted set of trusted modules: `sigma_protocol_homomorphism`, `sigma_protocol`, `sigma_protocol_registration`, `sigma_protocol_withdraw`, `sigma_protocol_transfer`, `sigma_protocol_key_rotation`, plus `#[test_only]` friends for test modules [1](#0-0) . Every function that can construct or mutate a `RepresentationVec` — `new_representation_vec`, `get_representations`, `length`, `for_each_ref`, `map_ref`, `scale_all`, `scale_each` — is declared `public(friend)`, meaning none of them are callable from a public/unprivileged context outside that whitelist [2](#0-1) .

Two points make the hypothesized attack infeasible even in the "future refactor" framing posed by the question:

1. **`friend` declarations are compile-time, module-author-controlled metadata baked into the published bytecode.** There is no unprivileged transaction, entry function, script, or API input that can add itself to a module's friend list or alter struct field visibility at runtime. Any such change requires a source-level modification and republishing of the `aptos_framework` module — i.e., a governed framework upgrade, not something reachable "from unprivileged transaction, package, API, view, bytecode, or proof input" as required by the Scope Rules.

2. **The Move bytecode verifier enforces struct field privacy and friend visibility independently of the source module's intent.** Even if a hypothetical accidental `#[test_only]` friend leak occurred, `#[test_only]` items and modules are stripped from/unreachable in a production (non-test) build; they cannot be invoked by mainnet transactions. A genuine bypass would require a `public` (non-friend) constructor to be added to `sigma_protocol_representation_vec.move` itself and republished — a hypothetical developer error in future source code, which the Decision Standard explicitly excludes ("Reject anything that depends on trusted operator mistakes alone").

All current call sites of `new_representation_vec` (in `sigma_protocol_registration.move`, `sigma_protocol_withdraw.move`, `sigma_protocol_transfer.move`, `sigma_protocol_key_rotation.move`, and the test-only example modules) are internal `psi`/`f` implementations gated by their own `public(friend) fun assert_verifies` entry points, which are themselves only reachable through `confidential_asset`'s privileged transaction handlers [3](#0-2) . There is no reachable path from unprivileged input, in the current committed code, that constructs an arbitrary/crafted `RepresentationVec` and feeds it into `sigma_protocol::verify`, so no state-commitment, proof-integrity, or write-set corruption is possible today.
