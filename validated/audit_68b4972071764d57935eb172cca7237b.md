### Title
Paused vault accrual silently freezes the liquidity/borrow index instead of reverting, letting stale index values flow into oracle-cached ztoken pricing and debt accrual - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vaults `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`)

### Summary
Each vault's `accrue` function has an independent `pause-states.accrue` flag. When set, `accrue` does not revert and does not advance the interest index — it silently returns the last-known `{index, lindex}` as if it were the fresh, current value, with no signal to the caller that the result is stale.

### Finding Description
`accrue()` in `mainnet/contracts/vault/v0-vault-stx.clar` (and the identical logic repeated in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) is structured as: [1](#0-0) 
```
(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          ;; PAUSED: Pass-through without reverting
          (ok { index: idx, lindex: lidx })
          ;; NOT PAUSED: Normal accrual logic
          ...
```
When `accrue` is paused, the function returns `(ok {index, lindex})` using the currently stored (last-accrued) values, without any error and without any indication to callers that time has actually elapsed since the last real accrual. Unlike deposit/redeem/borrow/repay pauses (which use `ERR-PAUSED` to hard-stop the caller), the accrue pause is a pass-through that fabricates a successful, fresh-looking result out of a stale value.

This stale `{index, lindex}` is then consumed by `market.clar`'s caching layer: [2](#0-1) 
```
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)
      (let ((indexes (try! (vault-accrue aid))))
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
and by the oracle callcode transform for ztoken pricing: [3](#0-2) 
```
(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))
```
`resolve-ztoken` is the pricing path used for every ztoken accepted as collateral (zSTX, zsBTC, zstSTX, zUSDC, zUSDH, zstSTXbtc) during LTV/health checks in borrow, withdraw, and liquidation. Since `market.clar` treats the value returned by `vault-accrue` as authoritative and caches it without any freshness/staleness marker distinguishing "real accrual" from "paused pass-through," a stale `lindex` is silently baked into the price used for collateral valuation and into debt scaling for that entire block, and remains the on-chain state used until accrual is unpaused — with no revert, no event flagging staleness, and no fallback distinguishing this state from a normal healthy accrual. This mirrors the reported analog exactly: a value is bound (the index/price), the event that should invalidate it (elapsed time / pause) occurs, but the code path that should revert on inability to produce a fresh value instead passes the old value through as if valid.

### Impact Explanation
Because `deposit`, `redeem`, `system-borrow`, and `system-repay` are not gated by the `accrue` pause flag (only their own independent flags are), and because ztoken collateral pricing/health checks depend on `resolve-ztoken`'s `lindex`, users can continue to borrow against, withdraw, and be liquidated against collateral priced with an index that is not tracking real accrued yield while `accrue` is paused. This can misprice collateral (temporarily freezing the true redemption value's growth from the user's perspective, or allowing borrowing against a value that doesn't reflect the real underlying growth), leading to temporary freezing of user's unclaimed yield/interest and to incorrect health/liquidation outcomes during the pause window — a temporary freezing of funds / unclaimed yield impact.

### Likelihood Explanation
This requires the DAO/operator to have paused `accrue` for a given vault (an available, reachable admin control) while leaving dependent operations (deposit, borrow, redeem, liquidation) active; no attacker collusion or Sybil is needed once that state exists — any ordinary user interacting with the vault during that window is affected. Likelihood is contingent on this specific pause configuration occurring, but the code path admits it without any additional safeguard.

### Recommendation
Make `accrue`'s paused branch either (a) revert with a dedicated error so dependent operations relying on freshness cannot silently proceed with fabricated "fresh" results, or (b) tag the returned `{index, lindex}` with an explicit staleness marker that `market.clar`'s `accrue-and-cache`/`resolve-ztoken` check and reject (mirroring the recommended Chainlink L2 sequencer pattern of reverting rather than silently reusing stale data), and additionally gate dependent state-changing operations (deposit/borrow/redeem/liquidate) on the same `accrue` pause flag so a paused accrual cannot be bypassed through other entry points.

### Proof of Concept
1. DAO/operator sets `pause-states.accrue = true` on `v0-vault-stx.clar` (or another vault) via the governance-gated setter, while leaving `borrow`/`deposit`/`redeem` unpaused.
2. Time passes (multiple blocks), so the real liquidity/borrow index should have advanced, but `accrue()` keeps returning the old `{index, lindex}` per [1](#0-0) .
3. A user calls `market.clar`'s borrow/withdraw flow, which calls `vault-accrue`→`accrue-and-cache`, caching the stale `{index, lindex}` keyed by the current block timestamp per [2](#0-1) .
4. `resolve-ztoken` uses this stale `lindex` to price the user's zSTX collateral for the LTV/health check per [3](#0-2) , so the collateral valuation and resulting borrow/liquidation decision is computed against an index frozen since the pause began, not the true post-pause economic value.
5. No revert occurs anywhere in this path — the transaction succeeds using stale data end-to-end.
