Based on my research, I found a concrete analog to the reported bug class within java-tron's permission/signature validation logic, which is duplicated across at least four call sites.

### Title
Missing permission-type/operations-scope check in `ValidateMultiSign` precompile allows Owner/Witness keys to satisfy checks intended to be scoped to Active permissions - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
java-tron implements the "does this signature set satisfy an account's permission threshold" logic in multiple independent places: `TransactionCapsule.validateSignature`/`checkPermission` [1](#0-0) , `TransactionUtil.getTransactionSignWeight` [2](#0-1) , `Wallet.getTransactionApprovedList` [3](#0-2) , and the TVM precompiled contract `ValidateMultiSign` [4](#0-3) . Three of the four sites enforce that, for any non-owner `permissionId`, the referenced `Permission` must be of type `Active` and must pass `checkPermissionOperations` (i.e. be scoped to only the contract types it was granted). The fourth site — the TVM precompile reachable from any smart-contract call — only checks that the recovered signer addresses' summed weight meets the permission's threshold; it never checks `permission.getType()` nor calls `checkPermissionOperations`.

### Finding Description
`ValidateMultiSign` fetches `Permission permission = account.getPermissionById(permissionId)` and then only verifies that the computed `totalWeight >= permission.getThreshold()` [5](#0-4) . Unlike `TransactionCapsule.checkPermission`, which rejects a `permissionId != 0` whose `permission.getType() != PermissionType.Active` and enforces the 32-byte operations bitmask restricting which contract types the permission may authorize [1](#0-0) , the precompile accepts any `permissionId` value — including `0` (Owner) or `1` (Witness) — with no type or scope restriction. This mirrors the reported bug class exactly: the same "is this key/permission properly scoped and enabled to authorize this action" check is duplicated in several places, and one reachable path (here, the TVM precompile invoked directly by contract bytecode) omits it.

### Impact Explanation
Any smart contract deployed on java-tron can call this precompile (address `0x000...66` equivalent, mapped via `PrecompiledContracts`) as a general-purpose "check if this account's permission was satisfied by these signatures" primitive. If a downstream dApp built on top of it assumes that satisfying the precompile implies the caller holds a properly-scoped, restricted Active-type key (the same guarantee the core transaction-signing paths enforce), that assumption is false: an Owner-key holder (unrestricted, full account control) or Witness-key holder can also satisfy checks that were meant to be limited to a scoped `Active` permission with restricted operations. This weakens the security boundary that the operations bitmask in `AccountPermissionUpdateActuator.checkPermission` [6](#0-5)  is designed to enforce (i.e. limiting a delegated key to specific contract types).

### Likelihood Explanation
The precompile is directly reachable from any TVM contract call triggered by a broadcast `TriggerSmartContract` transaction, requiring no special privilege — an anonymous actor can deploy or call a contract that invokes it. There is an existing dedicated test suite (`ValidateMultiSignContractTest.java`) confirming this precompile is a live, exercised feature.

### Recommendation
Align the precompile's validation with the transaction-level checks: reject `permissionId` values whose `Permission.getType() != PermissionType.Active` (except where `permissionId == 0` is intentionally allowed for Owner-only use cases), and consider surfacing/checking the operations bitmask when the precompile is used to gate contract-type-specific authorization, matching the logic in `TransactionCapsule.checkPermission` and `TransactionUtil.getTransactionSignWeight`.

### Proof of Concept
Not independently verified with a running node — this assessment is based on static code comparison across the four call sites. I could not confirm from the indexed code alone whether this discrepancy is an intentional design choice (the precompile may be documented as a generic "verify signature against any permission" utility rather than a transaction-authorization gate) or an overlooked omission; a Devin session with full repo/test access and TRON documentation would be needed to confirm original design intent before treating this as a confirmed vulnerability rather than a design inconsistency.

    if (permission.getKeysCount() == 0) {
      throw new ContractValidateException("key's count should be greater than 0");

      throw new ContractValidateException("Witness permission's key count should be 1");

      throw new ContractValidateException("permission's threshold should be greater than 0");
    }

      throw new ContractValidateException("permission's name is too long");
    }

    if (permission.getParentId() != 0) {
      throw new ContractValidateException("permission's parent should be owner");

        .stream()

        .distinct()
        .collect(toList());

        throw new ContractValidateException("key's weight should be greater than 0");

        throw new ContractValidateException(e.getMessage());

      if (!operations.isEmpty()) {
