### Title
Unbounded growth of `IdempotentPromiseHandler.identifiers` map enables memory-exhaustion DoS during token exchange - (File: `packages/apps/shopify-app-remix/src/server/authenticate/helpers/idempotent-promise-handler.ts`)

### Summary
`IdempotentPromiseHandler` deduplicates `afterAuth` hook invocations during OAuth token-exchange by storing every unique `identifier` (the raw `sessionToken` JWT) in an in-memory `Map`, with no upper bound on the number of entries. This is structurally the same defect class as the reported `activeWorkerIds` issue: an unbounded, attacker-influenced collection that grows with each distinct value supplied by a caller, is only pruned lazily/opportunistically, and is walked in full on every operation — creating a path to unbounded memory growth and increasing per-request work over time.

### Finding Description
`IdempotentPromiseHandler` (duplicated identically in `shopify-app-remix`, `shopify-app-react-router`, and `shopify-app-express`) keeps a `Map<string, number>` of identifiers with insertion timestamps: [1](#0-0) 

Cleanup only happens as a side effect of `handlePromise`, and only removes entries whose age exceeds a fixed 60-second TTL: [2](#0-1) 

There is no cap on the total number of entries the map can hold. If many distinct identifiers are inserted within the same 60-second window (faster than they age out), the map grows without limit for the duration of the burst.

This map is populated during the token-exchange authentication path with `identifier: sessionToken` — a value derived directly from the request-supplied JWT session token, i.e., effectively caller-controlled and unique per request: [3](#0-2) [4](#0-3) 

Each request that needs a fresh offline/online access token (i.e., whenever no active session exists yet, or the session has expired) exercises `handleAfterAuthHook`/`callAfterAuthHook`, inserting a brand-new entry keyed by that request's session token. Because App Bridge/session tokens are short-lived and unique per issuance, a client capable of driving many token-exchange calls within a short window (e.g., a single merchant/staff member scripting repeated calls to the token-exchange endpoint with distinct freshly obtained session tokens, or replaying the flow before any given session is marked active) can insert entries faster than the TTL-based sweep removes them, growing the map's memory footprint for the process lifetime of that burst.

### Impact Explanation
This is analogous to the reported issue: an unbounded collection populated by low-cost, attacker-influenced input, with no maximum-size enforcement, only time-based eventual cleanup. In the worst case, sustained bursts cause increasing memory consumption in the app server process. Because the map is walked in full (`.forEach`) on every single `handlePromise` invocation, the per-request cost of the cleanup step also increases as the map grows, so this can additionally degrade auth-handler latency under load, mirroring the "excessive gas costs for other users" dynamic of the original report (excessive CPU/memory costs for the shared server process, not just the requester). Impact is bounded by process memory rather than a hard-blocking gas limit, so it manifests as gradual degradation/OOM risk under sustained abuse rather than immediate outage from a single transaction.

### Likelihood Explanation
Low-to-moderate. Exploitation requires the attacker to be able to drive the token-exchange path repeatedly with distinct valid-enough session tokens within a 60-second window — this is achievable by a single authenticated merchant/staff member (or an app embedded context they control) scripting calls rather than by a fully anonymous, unauthenticated party, since `api.auth.tokenExchange` still validates the JWT against Shopify. This matches the "single merchant/customer" actor class called out in scope, but the requirement to obtain many distinct valid session tokens in a short window limits ease of exploitation compared to a fully anonymous vector.

### Recommendation
- Enforce a maximum size on `IdempotentPromiseHandler.identifiers` (e.g., LRU eviction or reject/short-circuit inserts beyond a cap) rather than relying solely on time-based cleanup.
- Perform cleanup on a fixed interval/timer independent of request volume, instead of only as a side effect of `handlePromise`, so cleanup work doesn't scale with (and lag behind) request bursts.
- Consider hashing the `sessionToken` (or deriving a smaller idempotency key, e.g., shop+jti) instead of storing the full raw token string as the map key, to bound per-entry memory cost.

### Proof of Concept
Conceptual PoC (not proven against a live deployment, since this requires the full token-exchange flow and Shopify-side JWT issuance):
1. As an authenticated merchant/staff user of an embedded app using `future: { tokenExchange: true }` (or the `shopify-app-express` token-exchange middleware), repeatedly obtain fresh App Bridge session tokens (each has a distinct `jti`/expiry) and issue concurrent requests to the app's authenticated routes before any resulting offline/online session is marked "active" (e.g., by forcing session expiry/invalidation between calls, or hitting the endpoint from multiple contexts in parallel).
2. Each such request causes `TokenExchangeStrategy.authenticate` (or `performTokenExchange`) to call `handleAfterAuthHook`/`callAfterAuthHook` with a new, unique `sessionToken` identifier. [5](#0-4) 
3. If requests arrive faster than the 60-second TTL sweep can remove aged entries, `IdempotentPromiseHandler.identifiers` grows unbounded for the duration of the burst, since there is no maximum-size check in `isPromiseRunnable`/`clearStaleIdentifiers`. [6](#0-5)

```typescript
const IDENTIFIER_TTL_MS = 60000;

export class IdempotentPromiseHandler {
  protected identifiers: Map<string, number>;

  constructor() {
    this.identifiers = new Map<string, number>();
  }

  async handlePromise({
    promiseFunction,
    identifier,
  }: IdempotentHandlePromiseParams): Promise<any> {
    try {
      if (this.isPromiseRunnable(identifier)) {
        await promiseFunction();
      }
    } finally {
      this.clearStaleIdentifiers();
    }

    return Promise.resolve();
  }

  private isPromiseRunnable(identifier: string) {
    if (!this.identifiers.has(identifier)) {
      this.identifiers.set(identifier, Date.now());
      return true;
    }
    return false;
  }
```

```typescript
  private async clearStaleIdentifiers() {
    this.identifiers.forEach((date, identifier, map) => {

        map.delete(identifier);
      }
    });
```
