### Title
`ensure_match_transaction_info` skips state-checkpoint hash verification, letting replay-verify accept a diverged state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the authoritative comparator used by replay/verification tooling to confirm that a locally re-executed `TransactionOutput` matches the authenticated `TransactionInfo` recorded on-chain (i.e., committed under the ledger accumulator and thus under quorum-certified `LedgerInfo`). It checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but explicitly and admittedly does **not** check `state_checkpoint_hash` (covering state root / hot-state root / `position_state_checkpoint_hash`). [1](#0-0) 

### Finding Description
The function's own comment states the gap outright: [2](#0-1) 

`TransactionInfo::state_checkpoint_hash()` is the field that authenticates the post-execution state (and, per the comment, the "trading-native" position state) at that version, and it is one of the leaf fields hashed into the transaction accumulator (alongside `state_change_hash`, `event_root_hash`, `gas_used`, and `status`), which in turn is what `LedgerInfo`/quorum certificates sign over. The write-set hash check only confirms the *delta* (write set) matches, not that applying that write set to the prior state actually produces the state root that was accepted as canonical. If the state-checkpoint hash differs between local re-execution and the recorded `TransactionInfo`, that divergence is currently invisible to any caller of `ensure_match_transaction_info`.

This routine is used by three real integrity-sensitive call sites:
- `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which re-executes archived transactions and calls `ensure_match_transaction_info` to decide pass/fail for the entire replay-verify tool. [3](#0-2) 

- `execution/executor/src/chunk_executor/mod.rs` and `aptos-move/aptos-debugger/src/aptos_debugger.rs` / `aptos-move/cli/src/commands.rs`, which use the same comparator for chunk-replay and CLI-based transaction verification.

Because the check is missing, a corrupted, buggy, or maliciously altered state-computation path (e.g., a bug in state-checkpoint/state-root computation, or in the "trading-native"/hot-state root logic gated by the `COMPUTE_TRADING_NATIVE_STATE_ROOTS` feature referenced in the TODO) can produce a `TransactionOutput` whose write set matches but whose resulting state root does not match the authenticated `TransactionInfo.state_checkpoint_hash`. `ensure_match_transaction_info` will still return `Ok(())`, so replay-verify and chunk-executor verification will both falsely report success. [4](#0-3) 

### Impact Explanation
This breaks the state-commitment/proof-integrity invariant the task specifically calls out: "Committed state that differs from the correct VM result... must not be accepted as verified," and "replay paths... must not reinterpret committed data into a different ledger state." A silent divergence between the locally-computed state root and the authenticated on-chain `state_checkpoint_hash` would let a fork, storage-schema bug, or state-computation regression pass replay-verify undetected, undermining the primary safety net used to catch exactly this class of hard-fork/divergence bug before it reaches production or before archived/backed-up data is trusted for restore. Given replay-verify and chunk-executor verification are relied on as the last line of defense against exactly this failure mode, a false-positive here is a high-severity integrity gap even though it requires a *separate* root-cause bug (in state computation) to actually produce divergent output.

### Likelihood Explanation
Likelihood of the comparator gap itself is certain — it's present in the shipped code and explicitly acknowledged by its own TODO, which conditions fixing it on enabling `COMPUTE_TRADING_NATIVE_STATE_ROOTS`. The likelihood of *triggering* real state divergence depends on there being a separate, latent state-computation bug (e.g., in hot-state/position-state-checkpoint hashing) that this comparator was supposed to catch; I was not able to independently confirm such a state-computation bug exists elsewhere in this snapshot, only that the guard designed to detect it is absent.

### Recommendation
Add `state_checkpoint_hash` (including hot-state and `position_state_checkpoint_hash` components) comparison to `ensure_match_transaction_info`, matching the pattern already used for `state_change_hash` and `event_root_hash`, before any code path (including `COMPUTE_TRADING_NATIVE_STATE_ROOTS`-gated state roots) relies on this function as a correctness gate for replay or chunk verification.

### Proof of Concept
Conceptual PoC (cannot be executed without a live devnet/testnet and a state-computation bug to trigger divergence):
1. Take an archived transaction range with a known `TransactionInfo.state_checkpoint_hash`.
2. Re-execute it locally with a state-computation implementation that produces a different, incorrect state root (e.g., a hypothetical bug in hot-state root aggregation) but the same write set (same `state_change_hash`).
3. Call `TransactionOutput::ensure_match_transaction_info` (as done in `storage/db-tool/src/replay_on_archive.rs::execute_and_verify`) — because state-checkpoint hash is never compared, this call returns `Ok(())`, and the replay-verify tool reports success despite the state root being wrong.     pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
