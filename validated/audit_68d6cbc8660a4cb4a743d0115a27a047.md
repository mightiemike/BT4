### Title
Intermediate multiplication overflow in `ExchangeInjectActuator.execute()` causes valid injections to unnecessarily fail - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes the "another token" quantity twice using two different arithmetic strategies: `doValidate()` uses unbounded `BigInteger` multiplication/division, while `execute()` uses bounded `long` arithmetic via `multiplyExact()`/`floorDiv()`. When the intermediate product `balance * tokenQuant` exceeds `Long.MAX_VALUE`, the `BigInteger` path in validation never overflows and can legitimately pass, but the `long` path in execution throws `ArithmeticException`, aborting an otherwise valid transaction. This mirrors the `_getSpotPrice()` bug class: a phantom overflow in an intermediate multiplication step (rather than a proper `mulDiv`-style computation) causes an avoidable failure even though the final, post-division result is small and valid.

### Finding Description
In `doValidate()`, the exchange-inject ratio is computed with `BigInteger`, which cannot overflow: [1](#0-0) 

In `execute()`, the identical computation is instead performed with native `long` multiplication guarded only by `multiplyExact` (which throws instead of silently overflowing), followed by `floorDiv`: [2](#0-1) 

Because `Commons.Actuator.validate()` is invoked before `execute()` for every broadcast transaction, and because the two code paths use different arithmetic domains, it is possible for `doValidate()` to succeed (since `BigInteger` never overflows and the resulting `anotherTokenQuant` is small and within `getExchangeBalanceLimit()`), while `execute()` subsequently throws `ArithmeticException` from `multiplyExact(secondTokenBalance, tokenQuant)` or `multiplyExact(firstTokenBalance, tokenQuant)` whenever that specific intermediate product exceeds `Long.MAX_VALUE` (~9.22e18), even though `secondTokenBalance`, `firstTokenBalance`, and `tokenQuant` are each individually reasonable and well below any balance limit. The exception is caught and converted into `ContractExeException`, marking the transaction `FAILED`: [3](#0-2) 

This is the same root cause as the reported issue: an intermediate multiplication (`priceX192 * 1e18` in the original report; `balance * tokenQuant` here) is performed with a bounded arithmetic type without first widening (e.g., to `BigInteger`/`mulDiv`-style unbounded computation) even though the final, divided result would fit comfortably. The validate path already correctly avoids this using `BigInteger`, confirming the developers recognize the overflow risk, but the fix was not consistently applied to the execute path.

### Impact Explanation
For any long-lived, popular Exchange pool where token balances have grown large (bounded only by the tunable `exchangeBalanceLimit` dynamic parameter, which can be raised by committee/witness governance to support real liquidity), a modest, entirely legitimate `ExchangeInjectContract` (only callable by the pool creator) can pass validation but then deterministically fail during execution, wasting the transaction fee and preventing legitimate liquidity injections. This is a denial-of-service on a normal actuator state transition, not requiring any privileged actor — the exchange creator is an ordinary account exercising an ordinary DEX operation.

### Likelihood Explanation
Likelihood is Low-to-Medium: the overflow requires `balance * tokenQuant` to exceed `Long.MAX_VALUE` (~9.22 × 10^18), which requires either a very large existing pool balance combined with a modest injected quantity, or a token with high decimal precision. This is plausible for high-value TRC10 pools that have accumulated large balances over time, but is not trivially reachable in small/typical pools.

### Recommendation
Make `execute()` use the same overflow-safe computation as `doValidate()` (i.e., compute `anotherTokenQuant` via `BigInteger` multiply/divide, or a `mulDiv`-equivalent helper that widens before dividing) instead of `multiplyExact`/`floorDiv` on raw `long`s. This ensures execution never fails for a transaction that already passed validation with the same inputs, eliminating the phantom-overflow-induced DoS.

### Proof of Concept
1. Create/grow an `ExchangeCapsule` pool such that, e.g., `secondTokenBalance = 1_000_000_000_000_000L` (1e15, near a raised `exchangeBalanceLimit`).
2. As the pool creator, submit `ExchangeInjectContract` with `tokenId = firstTokenID` and `tokenQuant = 10_000L`.
3. `doValidate()` computes `anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)` via `BigInteger` — no overflow, passes all balance-limit checks (`newAnotherTokenBalance` stays under limit).
4. `execute()` computes `multiplyExact(secondTokenBalance, tokenQuant)` = `1_000_000_000_000_000L * 10_000L` = `1e19`, which exceeds `Long.MAX_VALUE` (~9.22e18) and throws `ArithmeticException`.
5. The exception is caught in `execute()`, the transaction result is set to `FAILED`, and `ContractExeException` is thrown — despite `validate()` having accepted the same transaction as legitimate.
