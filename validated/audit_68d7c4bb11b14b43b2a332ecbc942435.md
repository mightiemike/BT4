### Title
Nightly and TestNetworkWithForks share chain_id=5665 and (by default) identical council/sequencer/prover DA keys, enabling cross-network replay of method-id upgrades - (File: crates/light-client-prover/src/circuit/mod.rs)

### Summary
`citrea_network_to_chain_id` intentionally maps `Network::Nightly` and `Network::TestNetworkWithForks` to the same value (5665), and the default initial values for both networks' method-id-upgrade council public keys, batch prover key and sequencer key are the same hard-coded constants. This means a genuinely council-signed `DataOnDa::BatchProofMethodId` body produced for one of these networks is structurally indistinguishable from - and passes all checks for - the other network's deployment.

### Finding Description
In `run_l1_block`, the binding intended is `citrea_network_to_chain_id(network) == body.chain_id` uniquely identifying the network the council authorized the upgrade for: [2](#0-1) 
Because `citrea_network_to_chain_id(Nightly) == citrea_network_to_chain_id(TestNetworkWithForks) == 5665`, this check does not distinguish the two networks. The signature check `verify_method_id_security_council` only verifies against `method_id_upgrade_authority_da_public_keys` passed in by the caller, which for both networks defaults (absent env var overrides) to the identical constants `NIGHTLY_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` and `TEST_NETWORK_WITH_FORKS_METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEYS` (same hex-encoded keys), and the batch-prover/sequencer keys are also identical by default. `BatchProofMethodIdBody::serialize()` (the signed message) contains only `method_id`, `activation_l2_height`, and `chain_id` - it never encodes which `Network` variant the council intended, so a signature valid for Nightly is bit-identical and verifies as valid for TestNetworkWithForks (and vice versa), since the pubkeys used for verification are also identical by default.

### Impact Explanation
If a real deployment runs `TestNetworkWithForks` and reuses the default keys (i.e., does not override the `METHOD_ID_UPGRADE_AUTHORITY_DA_PUBLIC_KEY_*` env vars), a batch-proof method-id upgrade transaction inscribed on the shared Bitcoin DA for the Nightly network will also be accepted as authorized on a TestNetworkWithForks node, and vice versa - this is exactly the enumerated Critical category "a method-id upgrade accepted that was never authorised [for that network]." This is repeatable for every future council upgrade as long as the default keys/chain-id mapping remain unchanged.

### Likelihood Explanation
This is not exploitable by an unprivileged attacker without cooperation of the council: the attacker cannot forge the ECDSA signatures over `BatchProofMethodIdBody` (needs 3-of-5 valid signatures from `SECURITY_COUNCIL` keys), which requires either genuine council action or key compromise (explicitly out of scope). The realistic exploit path requires only that a real council-authorized message for one of these two networks exist and be observed on the shared Bitcoin DA; an attacker with no privileges beyond broadcasting Bitcoin transactions could then simply re-inscribe/relay that already-published blob to be picked up by the other network's light-client provers (both scan the same DA). This is contingent on: (a) both networks being deployed concurrently with default (non-overridden) keys, and (b) both scanning the same underlying Bitcoin chain. Given `TestNetworkWithForks` is documented as "used for testing purposes only" (per `crates/sovereign-sdk/rollup-interface/src/network.rs`), this is unlikely to hold real bridged BTC value, but the code path itself and the identical-by-default keys/chain-id are real and unconditional.

### Recommendation
Give `TestNetworkWithForks` and `Nightly` distinct chain_id values in `citrea_network_to_chain_id`, and ensure their default method-id-upgrade authority keys, sequencer key, and batch prover key differ (or require explicit distinct env-var configuration with no shared fallback) so that a signed body for one network can never verify under the other's initial values.
