### Title
PoX-5 activation-height validation is skipped when `pox_5_activation_height != epoch_4_0.start_height`, allowing tip-keyed and cycle-keyed PoX-contract dispatch to disagree - (File: stackslib/src/core/mod.rs)

### Summary
The Obol report's core lesson is that a fee/split mechanism that assumes "all value flows through one recipient path" breaks when an unanticipated configuration (a non-ETH token) routes value through a different, unchecked path. The stacks-core analog is the PoX-5 "waterfall" activation-boundary guard: it assumes `pox_5_activation_height` is always equal to `epoch_4_0.start_height`, and only validates the boundary safety property under that assumption. When the two heights differ, the validation is skipped entirely, letting the exact ambiguous-boundary condition the code was built to prevent slip through, so different call sites can select different PoX contracts (and therefore different reward/signer sets) for the same reward cycle.

### Finding Description
`Burnchain::first_pox_waterfall_block` derives the boundary between classic PoX (PoX-4) and PoX-5 "waterfall" block-commit rules by floor-dividing `pox_5_activation_height` into a reward cycle and taking the *next* cycle as the first waterfall cycle: [1](#0-0) 

Two different predicates consume this boundary:
- `active_pox_contract` — a tip-height-keyed predicate (used by RPC/`getpoxinfo`, `chainstate/coordinator/mod.rs`, `chainstate/stacks/db/blocks.rs`, `chainstate/nakamoto/mod.rs`, `net/api/getstackers.rs`).
- `active_pox_contract_for_cycle` — a cycle-keyed predicate explicitly introduced because the tip-keyed predicate "genuinely disagrees across the prepare phase" when the activation height lands inside the prepare phase that sets up the first PoX-5 cycle (used by `chainstate/nakamoto/signer_set.rs` and `chainstate/stacks/boot/mod.rs`): [2](#0-1) [3](#0-2) 

To prevent this disagreement in practice, `stackslib/src/core/mod.rs` asserts that `pox_5_activation_height` must fall inside a reward phase (not a prepare phase) and not on a reward-cycle boundary offset (0 or 1). However, this assertion block is gated by an early return that only executes the checks **when `pox_5_activation_height == epoch_4_0.start_height`**: [4](#0-3) 

`pox_5_activation_height` and `epoch_4_0.start_height` are independent configuration fields; nothing in `PoxConstants` or the epoch schedule forces them to be equal. If they differ (e.g., PoX-5 activates in a later reward cycle than the one in which Epoch 4.0 starts, which is otherwise a plausible/valid configuration), the guard function returns immediately and the ambiguous-boundary safety checks are never run for the actual `pox_5_activation_height` in use. The exact hazard the checks exist to prevent — `pox_5_activation_height` landing inside a prepare phase or on a cycle-boundary offset — can then occur unguarded, and the tip-keyed vs. cycle-keyed predicates will diverge for burn heights in that window, exactly as demonstrated in the project's own tests: [5](#0-4) 

Because the tip-keyed predicate is used along paths that resolve the current reward set / PoX-payout information (`chainstate/coordinator/mod.rs`, `chainstate/stacks/db/blocks.rs`), while the cycle-keyed predicate is used to resolve the Nakamoto signer set for the same reward cycle (`chainstate/nakamoto/signer_set.rs`), an unguarded activation-height misconfiguration lets these two subsystems settle on different PoX contract versions for the same reward cycle. That breaks the equality that "the reward set validated for a sortition's block-commit and the signer set that must have produced/signed the corresponding tenure both come from the same PoX contract version."

### Impact Explanation
If nodes (or two logically distinct code paths within the same node/build) resolve different PoX contracts for the same reward cycle because of this activation-boundary ambiguity, the reward-set resolution used by `pick_recipients`/`check_pox` (`stackslib/src/chainstate/burn/db/sortdb.rs`, `stackslib/src/chainstate/burn/operations/leader_block_commit.rs`) can disagree with the signer set used to validate/produce the corresponding Nakamoto tenure. This falls under the High-severity class: a minority-triggerable static-validation/reward-resolution divergence bounded to a specific configuration window, potentially producing temporary tip disagreement or PoX reward mis-payment for the affected reward cycle.

### Likelihood Explanation
This requires only a specific (but plausible and unprivileged from the protocol's perspective) `PoxConstants`/epoch configuration — setting `pox_5_activation_height` to a value different from `epoch_4_0.start_height` such that it lands on a prepare-phase block or reward-cycle boundary offset. No attacker transaction or majority collusion is needed; it is a latent configuration-validation gap, not a validated invariant, so it is reachable by any deployment (mainnet/testnet parameter choice) that does not happen to set the two heights equal.

### Recommendation
Remove the `if pox_5_activation != epoch_4_0_start { return; }` early-return in `stackslib/src/core/mod.rs`, and instead always validate the general invariant — that `pox_5_activation_height` must not fall within a prepare phase and must not sit at reward-cycle offset 0 or 1 — regardless of its relationship to `epoch_4_0.start_height`. Additionally, add a direct invariant test (or a runtime assertion) that `active_pox_contract(h) == active_pox_contract_for_cycle(first_block_height, reward_cycle_of(h))` for every `h` in the vicinity of `pox_5_activation_height`, so any future boundary predicate can't silently diverge again.

### Proof of Concept
1. Configure a `Burnchain`/`PoxConstants` such that `pox_5_activation_height` is set independently of `epoch_4_0.start_height` (e.g., configure Epoch 4.0 to start well before `pox_5_activation_height`), and choose `pox_5_activation_height` to fall on a prepare-phase block (as in `cycle_predicate_is_stable_across_prepare_phase_for_first_pox5_cycle`).
2. Call `validate_nakamoto_transition_schedule`/the boundary check in `stackslib/src/core/mod.rs`; observe it returns early (`pox_5_activation != epoch_4_0_start`) without running the prepare-phase/offset assertions.
3. As in `stackslib/src/burnchains/tests/cycle_dispatch.rs::cycle_predicate_is_stable_across_prepare_phase_for_first_pox5_cycle`, show `active_pox_contract(prepare_start) == POX_4_NAME` while `active_pox_contract(prepare_end) == POX_5_NAME` for blocks in the very same reward cycle that `active_pox_contract_for_cycle` treats as uniformly PoX-4 or PoX-5.
4. Any code path keyed off `active_pox_contract` (reward-set resolution) versus `active_pox_contract_for_cycle` (signer-set resolution) for that reward cycle will now disagree on which PoX contract governs it. [3](#0-2)

#[test]
fn cycle_predicate_is_stable_across_prepare_phase_for_first_pox5_cycle() {
    // Place activation deep inside the prepare phase that sets up the
    // first PoX-5 cycle. Tip-keyed `active_pox_contract` would return
    // POX_4 for some blocks and POX_5 for others; the cycle-keyed
    // predicate must answer consistently for the cycle as a whole.
    let first = 100u64;
    // offset 9 of cycle 3 = a prepare-phase block of cycle 3 (mod-9).
    let activation = first + 3 * 10 + 9;
    let c = pox_constants_with_pox_5_at(activation as u32);

    // Tip-keyed dispatch genuinely disagrees across the prepare phase:
    // mod-8 of cycle 3 returns POX_4 (burn_height < activation), but
    // mod-0 of cycle 4 returns POX_5 (burn_height > activation).
    let prepare_start = first + 3 * 10 + 8;
    let prepare_end = first + 4 * 10; // mod-0 of cycle 4
    assert_eq!(c.active_pox_contract(prepare_start), POX_4_NAME);
    assert_eq!(c.active_pox_contract(prepare_end), POX_5_NAME);

    // The cycle-keyed predicate is the single source of truth.
    // first_pox_waterfall_block puts cycle 3 as the last classic cycle
    // (it contains the activation height), so cycle 4 is first PoX-5.
    assert_eq!(c.active_pox_contract_for_cycle(first, 3), POX_4_NAME);
    assert_eq!(c.active_pox_contract_for_cycle(first, 4), POX_5_NAME);
}
