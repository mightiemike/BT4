### Title
Raw internal error strings (storage/ORM/listener errors) are leaked to external callers via SecretsListResponse/SecretsSetResponse.ErrorMessage and HeartbeatResponse.InternalError - ([File: core/services/functions/connector_handler.go])

### Summary
`functionsConnectorHandler` embeds the raw `error.Error()` string from `s4.Storage` operations and from `FunctionsListener.HandleOffchainRequest` directly into response fields (`ErrorMessage`, `InternalError`) that are signed and sent back to the requesting external client via `SendToGateway`. This can expose internal implementation details (e.g. ORM/DB error text) to any address that passes the allowlist/rate-limit checks.

### Finding Description
In `handleSecretsList`, a storage failure is formatted verbatim into the response: `response.ErrorMessage = fmt.Sprintf("Failed to list secrets: %v", err)` [1](#0-0) . Similarly in `handleSecretsSet`, both unmarshalling errors and `storage.Put` errors are placed raw into `response.ErrorMessage` [2](#0-1) . In the heartbeat/offchain-request path, `handleOffchainRequest` stores `state.InternalError = err.Error()` from `h.listener.HandleOffchainRequest(ctx, request)` directly, and this cached state is later returned as-is to the caller through `handleHeartbeat` → `sendResponseAndLog` [3](#0-2) , [4](#0-3) .

None of these paths sanitize or generalize the error text before it is JSON-marshalled and dispatched through `sendResponse`/`SendToGateway` [5](#0-4) . The existing checks — `allowlist.Allow(fromAddr)` and `rateLimiter.Allow(body.Sender)` in `HandleGatewayMessage` [6](#0-5)  — gate *who* can send a request, but do nothing to prevent *what* internal error detail is echoed back once a request is accepted. Any allowlisted subscription owner (an ordinary, non-privileged DON user, not a node operator) can send malformed `SecretsSetRequest` payloads (e.g., colliding `SlotID`/`Version`, oversized payloads, invalid signatures that pass unmarshalling but fail deeper storage constraints) or heartbeat/offchain requests that fail deep in `listener.HandleOffchainRequest`, and receive the raw underlying Go error string back in the JSON response. Test code in `connector_handler_test.go` confirms this behavior explicitly returns a literal error like `"boom"` from the mock storage layer straight into the wire-format response: `{"success":false,"error_message":"Failed to list secrets: boom"}` and `{"success":false,"error_message":"Failed to set secret: boom"}` [7](#0-6) , [8](#0-7) .

### Impact Explanation
This is an information-disclosure issue: real production error strings from the S4 storage backend (SQL/ORM layer) or from the Functions listener's offchain execution path could contain DB schema/table names, driver error text, or other backend implementation details. While it does not directly cause fund loss or unauthorized transactions, it broadens the attack surface for a follow-on attacker by revealing infrastructure internals, consistent with an information-disclosure class finding.

### Likelihood Explanation
Any address that passes the on-chain allowlist and subscription-balance check for `secrets_set`, or is on `allowedHeartbeatInitiators` for heartbeat, can trigger this repeatedly and deterministically — this is not a rare race condition, it is the standard error branch of `handleSecretsList`, `handleSecretsSet`, and `handleOffchainRequest`, exercised directly by the repo's own unit tests. The barrier is the allowlist/subscription check (a normal DON participant precondition), not a security boundary against error-detail leakage.

### Recommendation
Replace raw `err.Error()`/`fmt.Sprintf("...: %v", err)` interpolation in `handleSecretsList`, `handleSecretsSet`, and `handleOffchainRequest`/`internalErrorResponse` with a generic, sanitized message (e.g., `"internal error processing request"`), and log the detailed error only server-side via `h.lggr.Errorw` (which already happens in some paths). Consider mapping known error types (e.g., validation errors) to specific safe user-facing messages while defaulting everything else to a generic message.

### Proof of Concept
Extend `connector_handler_test.go`:
1. Mock `storage.List`/`storage.Put` to return an error containing a synthetic "internal" string, e.g. `errors.New("pq: relation \"s4_secrets\" violates constraint")`.
2. Call `handler.HandleGatewayMessage` with a valid allowlisted sender for `secrets_list`/`secrets_set`.
3. Assert on the `SendToGateway` payload that `ErrorMessage` does NOT contain the raw driver/ORM string (currently it will, since the existing tests literally assert `error_message` equals `"Failed to list secrets: boom"`/`"Failed to set secret: boom"`).
4. Similarly, mock `listener.HandleOffchainRequest` to return an error with internal detail and assert the `HeartbeatResponse.InternalError` field returned via a subsequent heartbeat poll does not leak that raw string.

func (h *functionsConnectorHandler) sendResponse(ctx context.Context, gatewayId string, requestBody *api.MessageBody, payload any) error {
	payloadJson, err := json.Marshal(payload)
	if err != nil {
		return err
	}

	msg := &api.Message{
		Body: api.MessageBody{
			MessageId: requestBody.MessageId,
			DonId:     requestBody.DonId,
			Method:    requestBody.Method,
			Receiver:  requestBody.Sender,
			Payload:   payloadJson,
		},
	}
	if err = msg.SignKS(ctx, h.keystore, h.signAddr); err != nil {
		return err
	}

	resp, err := hc.ValidatedResponseFromMessage(msg)
	if err != nil {
		return err
	}

	return h.connector.SendToGateway(ctx, gatewayId, resp)
}
