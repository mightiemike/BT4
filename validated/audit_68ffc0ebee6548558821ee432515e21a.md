### Title
Missing slippage protection in `ExchangeWithdrawActuator` allows sandwich-attack loss when removing liquidity from a Bancor-style exchange pool - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawContract` lets an exchange creator remove liquidity from a TRON Bancor-style token-pair pool by specifying only the amount of one token to withdraw (`quant`). Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced during validation to protect against price movement, `ExchangeWithdrawContract` has no minimum-output/slippage field at all, so the amount of the "other" token returned (`anotherTokenQuant`) is computed purely from the pool's current on-chain balances at execution time with no user-specified floor.

### Finding Description
`ExchangeWithdrawActuator.execute` computes the counter-asset amount to return using the live pool balances at the moment the transaction is processed: [1](#0-0) 

This calculation is repeated in `doValidate`, but the only checks performed are that the pool has sufficient balance and that the resulting value is non-zero and "precise enough" versus a recomputed value — there is no comparison against any caller-supplied minimum: [2](#0-1) 

Contrast this with `ExchangeTransactionActuator`, which explicitly reads an `expected` (minimum) value from the contract and rejects the transaction if the computed output falls below it: [3](#0-2) 

The protobuf definition of `ExchangeWithdrawContract` confirms it has no analogous minimum-amount field — only `owner_address`, `exchange_id`, `token_id`, and `quant`: [4](#0-3) 

This exactly parallels the reported `AuraSpell#closePositionFarm` bug: when exiting the pool, the amount received is determined solely by the current pool state, with no way for the caller to bound their acceptable execution price. Because the pool balances (`firstTokenBalance`/`secondTokenBalance`) can be manipulated by preceding `ExchangeTransactionContract` trades within the same block window/mempool, an attacker can front-run the withdraw with a transaction that skews the pool ratio, let the victim's withdraw execute at the skewed rate, then back-run to restore/profit — a classic sandwich attack against liquidity withdrawal, with no on-chain guard to stop it.

### Impact Explanation
An exchange creator who withdraws liquidity via `ExchangeWithdrawContract` has no way to protect themselves from adverse price movement between transaction construction and execution. A miner/attacker who observes the pending withdraw transaction (visible in the mempool before block inclusion) can sandwich it: manipulate the pool balances via preceding trade(s), let the victim's withdraw settle at the manipulated exchange rate, then reverse the manipulation, extracting value from the victim's withdrawn counter-asset. This causes direct, quantifiable asset loss to the withdrawing account, consistent with an accounting/asset-loss impact.

### Likelihood Explanation
Any account that created a Bancor-style exchange (`ExchangeCreateContract`) can call `ExchangeWithdrawContract` at will, and this is a normal, expected operation reachable via ordinary broadcast transactions — no privileged system role is required beyond being the pool's own creator, which is the same actor role the original bug targets (the position/pool owner performing a routine exit). Because `ExchangeTransactionContract` (trades against the same pool) is also freely callable by any account and settles at the instantaneous pool ratio, front-running/back-running the withdraw is straightforward for anyone monitoring the transaction pool, making exploitation practical whenever a withdraw of meaningful size is submitted against a shallow-liquidity pool.

### Recommendation
Add an optional minimum-output field (or a pair of min amounts for both tokens) to `ExchangeWithdrawContract`, and enforce it in `ExchangeWithdrawActuator.doValidate`/`execute` analogous to the `expected` check already present in `ExchangeTransactionActuator`, so a withdrawing account can bound the acceptable counter-asset amount and safely reject execution if the pool has moved unfavorably.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` transaction from the pool creator, withdrawing `quant` of `firstTokenID`.
2. Attacker submits an `ExchangeTransactionContract` trade that shifts the pool ratio (e.g., sells a large amount of `secondTokenID` into the pool, inflating `firstTokenBalance` relative to `secondTokenBalance`), executed just before the victim's transaction in the same block via `ExchangeTransactionActuator.execute`: [5](#0-4) 
3. Victim's `ExchangeWithdrawContract` executes next; `anotherTokenQuant` is computed from the now-skewed `firstTokenBalance`/`secondTokenBalance` ratio, as shown in the withdraw calculation: [6](#0-5)  — the victim receives less `anotherTokenQuant` than they would have at the pre-manipulation ratio, with no `expected`/minimum check available to reject this.
4. Attacker submits a reversing trade to restore the pool and realize profit from the price impact absorbed by the victim's withdraw.
