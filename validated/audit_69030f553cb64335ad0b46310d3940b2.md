### Title
Signature malleability in `ECKey.ECDSASignature.validateComponents` allows weight double-counting in the `ValidateMultiSign` TVM precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `recover`/`validateComponents` logic that java-tron's TVM precompiled contracts rely on for ECDSA signature recovery only restricts `v` to `{27,28}` and checks that `r,s` are in `[1, n)`, but does **not** enforce the canonical low-`s` form (`s <= n/2`). This is the same signature-malleability class described in the external report (recover allows both `s` and `n-s`). In `PrecompiledContracts.ValidateMultiSign.execute`, the code tracks "already-used" signatures with a raw-signature-derived dedup key (`merge(recoveredAddr, sign)`) instead of deduplicating strictly by recovered address, so a malleable second signature from the *same* key is treated as a "different" signature and its weight is added a second time.

### Finding Description
`ECKey.ECDSASignature.validateComponents` only checks: [1](#0-0) 
i.e. `v` in `{27,28}` and `0 < r,s < SECP256K1N`. It never checks that `s <= SECP256K1N/2`, so for any valid signature `(r, s, v)` the malleable pair `(r, n-s, v')` (with the recovery id flipped) is also accepted as valid and recovers to the exact same address, per `ECKey.recoverPubBytesFromSignature`: [2](#0-1) 

This shared `recover`/`validateComponents` code is used by the `ValidateMultiSign` TVM precompiled contract, which is reachable from any on-chain contract call (analogous to an "anonymous RPC/contract call" entry point): [3](#0-2) 

The dedup logic keys on `recoveredAddr` **and** the raw merged signature bytes:
```
byte[] recoveredAddr = recoverAddrBySign(sign, hash);
sign = merge(recoveredAddr, sign);
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;               // only skipped if byte-identical signature repeats
  }
  MUtil.checkCPUTime();      // otherwise just a CPU-time guard, NOT a skip
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;        // weight is added again for the SAME address
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
``` [4](#0-3) 

Because two malleable encodings of the same key's signature over the same hash produce different raw signature bytes but recover to the same address, this "same signature already counted" branch is bypassed, and `totalWeight` is incremented twice for what is really a single signing key.

### Impact Explanation
This breaks the permission/threshold model that `ValidateMultiSign` is supposed to enforce for on-chain multisig authorization. An attacker who controls a single key with weight `w < threshold` in a target account's permission can compute a malleable variant of their own signature and submit both variants as the `signatures` array argument to the precompile (address used for `validatemultisign`). The precompile will report `totalWeight = 2w`, which can incorrectly reach/exceed the configured `threshold`, causing the calling contract logic to treat an unauthorized/insufficiently-weighted signer set as authorized. This is an unauthorized-account-operation / accounting-corruption class issue directly analogous to the ERC865 signature-malleability report (using a signature, rather than a canonicalized hash/address, as the uniqueness key for an operation).

### Likelihood Explanation
Exploitation requires only: (1) knowledge of one's own private key and a signature over the attacker-chosen hash (trivial, since the attacker signs it themselves), and (2) the ability to derive the standard secp256k1 malleable variant `(r, n-s, flip v)`, which is a well-known, mechanical transformation. No privileged access, leaked keys, or peer/node compromise is needed — any contract caller can trigger `ValidateMultiSign` via a transaction. This makes the likelihood high for any dApp/contract that relies on this precompile for multisig-weighted authorization decisions.

### Recommendation
- Enforce canonical low-`s` signatures in `ECKey.ECDSASignature.validateComponents` (reject `s > SECP256K1N/2`), consistent with EIP-2 / Ethereum's canonical signature form, closing the malleability at the source used by all TVM signature-recovery precompiles (`ECRecover`, `ValidateMultiSign`, `BatchValidateSign`).
- Additionally/alternatively, fix `ValidateMultiSign.execute` to deduplicate strictly by `recoveredAddr` (skip/continue whenever the address has already contributed weight), rather than keying on the raw signature bytes, so weight can never be counted more than once per address regardless of signature malleability.

### Proof of Concept
1. Key `K` has weight `w` in `permission`, with `threshold > w` and no other signer supplied.
2. Attacker signs `hash` with `K` producing `(r, s, v)`.
3. Attacker computes the malleable pair `(r, n-s, v ^ 1)` (standard secp256k1 malleability transform), which recovers to the same address as `K`.
4. Attacker (or any contract) calls the TVM opcode/precompile backing `ValidateMultiSign` with `signatures = [sig1, sig1_malleable]` for `address`/`permissionId`.
5. In `ValidateMultiSign.execute`, iteration 1 adds `weight=w` for `recoveredAddr`; iteration 2 recognizes `recoveredAddr` is already present but the merged signature bytes differ, so it does not `continue` and adds `weight=w` again, yielding `totalWeight = 2w`.
6. If `2w >= threshold`, the precompile returns success (`dataOne()`), granting authorization that should have required additional independent signers. [5](#0-4)

  public static byte[] recoverPubBytesFromSignature(int recId,
      ECDSASignature sig, byte[] messageHash) {
    check(recId >= 0, "recId must be positive");
    check(sig.r.signum() >= 0, "r must be positive");
    check(sig.s.signum() >= 0, "s must be positive");
    check(messageHash != null, "messageHash must not be null");
    // 1.0 For j from 0 to h   (h == recId here and the loop is outside
    // this function)
    //   1.1 Let x = r + jn
    BigInteger n = CURVE.getN();  // Curve order.
    BigInteger i = BigInteger.valueOf((long) recId / 2);
    BigInteger x = sig.r.add(i.multiply(n));
    //   1.2. Convert the integer x to an octet string X of length mlen
    // using the conversion routine
    //        specified in Section 2.3.7, where mlen = ⌈(log2 p)/8⌉ or
    // mlen = ⌈m/8⌉.
    //   1.3. Convert the octet string (16 set binary digits)||X to an
    // elliptic curve point R using the
    //        conversion routine specified in Section 2.3.4. If this
    // conversion routine outputs “invalid”, then
    //        do another iteration of Step 1.
    //
    // More concisely, what these points mean is to use X as a compressed
    // public key.
    ECCurve.Fp curve = (ECCurve.Fp) CURVE.getCurve();
    BigInteger prime = curve.getQ();  // Bouncy Castle is not consistent
    // about the letter it uses for the prime.
    if (x.compareTo(prime) >= 0) {
      // Cannot have point co-ordinates larger than this as everything
      // takes place modulo Q.
      return null;
    }
    // Compressed allKeys require you to know an extra bit of data about the
    // y-coord as there are two possibilities.
    // So it's encoded in the recId.
    ECPoint R = decompressKey(x, (recId & 1) == 1);
    //   1.4. If nR != point at infinity, then do another iteration of
    // Step 1 (callers responsibility).
    if (!R.multiply(n).isInfinity()) {
      return null;
    }
    //   1.5. Compute e from M using Steps 2 and 3 of ECDSA signature
    // verification.
    BigInteger e = new BigInteger(1, messageHash);
    //   1.6. For k from 1 to 2 do the following.   (loop is outside this
    // function via iterating recId)
    //   1.6.1. Compute a candidate public key as:
    //               Q = mi(r) * (sR - eG)
    //
    // Where mi(x) is the modular multiplicative inverse. We transform
    // this into the following:
    //               Q = (mi(r) * s ** R) + (mi(r) * -e ** G)
    // Where -e is the modular additive inverse of e, that is z such that
    // z + e = 0 (mod n). In the above equation
    // ** is point multiplication and + is point addition (the EC group
    // operator).
    //
    // We can find the additive inverse by subtracting e from zero then
    // taking the mod. For example the additive
    // inverse of 3 modulo 11 is 8 because 3 + 8 mod 11 = 0, and -3 mod
    // 11 = 8.
    BigInteger eInv = BigInteger.ZERO.subtract(e).mod(n);
    BigInteger rInv = sig.r.modInverse(n);
    BigInteger srInv = rInv.multiply(sig.s).mod(n);
    BigInteger eInvrInv = rInv.multiply(eInv).mod(n);
    ECPoint.Fp q = (ECPoint.Fp) ECAlgorithms.sumOfTwoMultiplies(CURVE
        .getG(), eInvrInv, R, srInv);
    return q.getEncoded(/* compressed */ false);
  }

        byte v) {

      if (v != 27 && v != 28) {
        return false;
      }

        return false;
      }
      if (BIUtil.isLessThan(s, BigInteger.ONE)) {
        return false;
      }

      if (!BIUtil.isLessThan(r, SECP256K1N)) {
        return false;
      }
