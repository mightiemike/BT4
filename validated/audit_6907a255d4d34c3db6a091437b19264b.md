Based on my investigation, I found a strong analog to the reported Solidity DoS bug in the Wallet Contract's callback/state-persistence design.

### Title
Callback-Reset Flag Can Be Permanently Stuck Due to Out-of-Gas Rollback in Wallet Contract - (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the NEAR wallet-contract used as a persistent per-user "controller" over an eth-implicit account) guards against concurrent execution using a `has_in_flight_tx` boolean that is set to `true` at the start of an operation and is supposed to be reset to `false` inside a private callback once the operation resolves [1](#0-0) . Just like the reported Solidity bug where an unmetered external call could consume all gas and revert the whole transaction (undoing the state cleanup that was supposed to happen before the external call), the NEAR runtime's failure model rolls back **all** state mutations of a failed receipt as a single atomic unit — including flag resets performed earlier in the same function execution — if that receipt later fails (e.g., runs out of its allotted gas).

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` and creates a promise chain ending in one of several `#[private]` callbacks (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`) [2](#0-1) . Each callback's very first statement resets `self.has_in_flight_tx = false` before inspecting the promise result and doing further work [3](#0-2) .

The callbacks are scheduled with small, fixed static gas budgets (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, etc.) [4](#0-3) , while `target` (the account that is called, and whose response value is later processed in the callback) is fully attacker-controlled — it can be any account, including one implementing a malicious contract, as demonstrated by `action_to_promise`'s generic `FunctionCall` path [5](#0-4) . If the target contract returns a value whose processing (copying via `promise_result`, JSON/borsh (de)serialization, and re-emission via `value_return`) costs more gas than the fixed callback budget, the callback's WASM execution traps with `GasExceeded`.

Per nearcore's runtime execution model, a receipt whose execution result is `Err` (including `GasExceeded`) causes the **entire** state update for that receipt to be rolled back: "a receipt whose result is `Err` triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting" [6](#0-5) . Concretely, `near-sdk`'s generated wrapper only persists the contract's Borsh state (`STATE` key) once the method body returns successfully; a mid-execution trap means the state write never happens, so the `has_in_flight_tx = false` write performed at the top of the callback is never committed — exactly mirroring the Solidity bug where a state change made before a gas-unbounded external call is rolled back together with the reverted call.

Since `has_in_flight_tx` can only ever be cleared inside these same callbacks, and there is no other method available to reset it, a single successfully-triggered `GasExceeded` failure inside a callback permanently freezes the contract: every subsequent `rlp_execute` call is rejected up front with "transaction already in progress" [7](#0-6) .

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, the wallet-contract account (which represents a user's eth-emulated NEAR account and controls its funds/tokens) can never again execute `rlp_execute`, permanently freezing the user's ability to transfer NEAR, transfer NEP-141 tokens, add/delete access keys, or perform any other action through this wallet. This matches the "permanently frozen funds" impact criterion: it is a concrete, transaction-triggered denial of service on user funds reachable by any unprivileged caller who can get the wallet to invoke an attacker-influenced/attacker-controlled `target` contract (which is the entire purpose of the contract — relaying arbitrary Ethereum-style transactions to arbitrary NEAR targets).

### Likelihood Explanation
The `target` account and the size/shape of its response are attacker-influenced input in every one of the supported flows (`FunctionCall`, ERC-20 emulation via NEP-141, base-token transfer with address-check) [8](#0-7) . The callback gas budgets are small, fixed constants unrelated to the size of data the target may return, making it plausible for a malicious or compromised target contract (or a malicious relayer picking `target`) to return an oversized payload that exceeds the callback's gas allowance, tripping `GasExceeded` and losing the `has_in_flight_tx` reset.

### Recommendation
- Ensure the flag reset that unblocks future transactions is committed independently of the potentially gas-exhausting work that follows it in the same receipt — e.g., perform the reset in a separate low-risk receipt/callback stage, or cap/validate the size of values copied from `promise_result` before doing further processing, so a large or malicious response cannot cause the same receipt (and thus the flag reset) to be rolled back.
- Alternatively, add a recovery path (e.g., a privileged or time-locked "unstick" method) that can reset `has_in_flight_tx` if it is ever found `true` without a genuinely in-flight promise, so a single malicious response cannot permanently brick the wallet.
- Bound `RLP_EXECUTE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` generously relative to the maximum possible size of any cross-contract return value the callback might need to process, or explicitly truncate/limit the value size before this processing.

### Proof of Concept
1. Deploy a malicious NEAR contract `M` whose method, when called, returns a very large byte string/JSON value (sized so that copying it through `promise_result`/`read_register` and re-serializing it via `value_return` inside the wallet's callback exceeds the fixed `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) budget, but the outer `rlp_execute` transaction itself is given ample total gas so the panic is scoped to the inner callback receipt, not the whole chunk).
2. From the wallet contract (owned by victim), submit an RLP-encoded Ethereum transaction whose `to`/`target` is `M`, via `rlp_execute(target=M, tx_bytes_b64=...)`, as exercised by the existing integration test harness in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs` (`test_function_call_action_success`, `test_caller_refunds`) [9](#0-8) .
3. `rlp_execute` sets `has_in_flight_tx = true`, invokes `M`, then chains to `rlp_execute_callback`; `M`'s successful (but oversized) return triggers `GasExceeded` inside `rlp_execute_callback` after `self.has_in_flight_tx = false` was already executed in-memory but before the method returns and its state is persisted.
4. Verify (analogous to `test_simultaneous_transactions` [10](#0-9) ) that any subsequent `rlp_execute` call now unconditionally returns `"Error: transaction already in progress, please try again later."` indefinitely, with no way to reset the flag, thereby permanently freezing the wallet.

    pub fn rlp_execute(
        &mut self,
        target: AccountId,
        tx_bytes_b64: String,
    ) -> PromiseOrValue<ExecuteResponse> {
        // To ensure user actions are executed in the desired order,
        // having multiple transactions in flight at the same time is
        // not allowed.
        if self.has_in_flight_tx {
            return PromiseOrValue::Value(ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(
                    "Error: transaction already in progress, please try again later.".into(),
                ),
            });
        }
        let current_account_id = env::current_account_id();
        let predecessor_account_id = env::predecessor_account_id();
        let result = inner_rlp_execute(
            current_account_id.clone(),
            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

        match result {
            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(Error::Relayer(_)) if env::signer_account_id() == current_account_id => {
                let promise = create_ban_relayer_promise(current_account_id);
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

/// Only one transaction can be in flight at a time.
#[tokio::test]
async fn test_simultaneous_transactions() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let receiver_account = worker.root_account().unwrap();

    let initial_receiver_balance = receiver_account.view_account().await.unwrap().balance;

    let receiver_id = receiver_account.id().as_str().into();
    let action = Action::Transfer { receiver_id, yocto_near: 1 };
    let signed_transaction =
        utils::create_signed_transaction(0, receiver_account.id(), Wei::zero(), action, &wallet_sk);
    let wallet_method_call_1 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));
    let wallet_method_call_2 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));

    let near_transaction = wallet_contract
        .inner
        .as_account()
        .batch(wallet_contract.inner.id())
        .call(wallet_method_call_1)
        .call(wallet_method_call_2)
        .transact()
        .await?;

    let result: ExecuteResponse = near_transaction.json()?;

    // The second transaction in the batch fails and this is returned as the
    // result of the Near transaction. But the first transaction in the batch
    // spawns promises that resolve, so the transfer was will successful.
    assert!(!result.success);
    assert!(result.error.unwrap().contains("transaction already in progress"));

    let final_receiver_balance = receiver_account.view_account().await.unwrap().balance;
    assert_eq!(final_receiver_balance.as_yoctonear() - initial_receiver_balance.as_yoctonear(), 1,);

    Ok(())
}
