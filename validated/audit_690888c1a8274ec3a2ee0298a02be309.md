### Title
Unbounded per-shop session-id array in `KVSessionStorage` causes denial-of-service of session storage/auth flow - (File: `packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`)

### Summary
`KVSessionStorage.addShopIds` appends session ids to a shop's index array on every `storeSession` call without checking for duplicates, unlike the equivalent Redis implementation. Because `storeSession` is invoked repeatedly with the *same* deterministic offline-session id every time an app re-authenticates via token exchange, the per-shop id array grows without bound, eventually breaking `findSessionsByShop`/`storeSession` for that shop (a denial of service in the request-authentication path), mirroring the "unbonded array" DoS pattern from the referenced report.

### Finding Description
`KVSessionStorage.storeSession` unconditionally calls `addShopIds`, which reads the existing `shop:<shop>` array and writes back the concatenation with no de-duplication: [1](#0-0) [2](#0-1) 

Compare this to the Redis adapter, which explicitly checks `idKeysArray.includes(idKey)` before pushing: [3](#0-2) 

Offline session ids are deterministic per shop (`offline_<shop>`), so every re-exchange of the same offline token calls `storeSession` with an identical id. This happens automatically in the token-exchange authentication path, whenever the stored session is missing or no longer active: [4](#0-3) 

The same pattern exists in the Remix/React-Router equivalents: [5](#0-4) 

Each such call appends a duplicate `offline_<shop>` (and, if `useOnlineTokens` is enabled, `<shop>_<userId>`) entry to the `shop:<shop>` KV array with no cap and no cleanup, since `removeShopIds` is only invoked on `deleteSession`, not on `storeSession`.

`findSessionsByShop` then loads every id in that array on each call: [6](#0-5) 

This is used by `AppInstallations.includes`/`delete`, invoked from unauthenticated OAuth-begin/installation-check paths: [7](#0-6) 

### Impact Explanation
As the shop-level id array grows unbounded, two DoS effects occur:
1. `findSessionsByShop` performs increasingly many redundant `loadSession` calls (one per array entry, including all stale duplicates), degrading and eventually timing out authentication/installation checks for that shop.
2. Cloudflare Workers KV enforces a per-value size limit; once the JSON-serialized id array exceeds that limit, `namespace.put` in `addShopIds`/`storeSession` fails, permanently breaking `storeSession` for the shop — meaning no new offline/online session can ever be persisted again, which blocks all subsequent authentication (OAuth callback and token-exchange) for that shop.

This is a DoS of the app's session-storage and request-authentication mechanism, analogous to the reported unbounded `orgHash` array causing failures in `getOrgBySafe`/`removeOrg`/`getOrgHashBySafe`.

### Likelihood Explanation
The growth is triggered by completely ordinary, unauthenticated-adjacent traffic: any customer/merchant session whose short-lived App Bridge session token or expiring offline access token needs renewal causes another `storeSession` call with the same id. A malicious single merchant (or anyone able to force repeated invalid/expired session-token retries against their own installed app, e.g. by scripting requests against `/api/auth` or triggering repeated 401/retry-session-token cycles) can accelerate this indefinitely, since there is no rate limit or de-duplication safeguard in `addShopIds`. Apps using `@shopify/shopify-app-session-storage-kv` with the `expiringOfflineAccessTokens` future flag or `useOnlineTokens` are most exposed, since these cause frequent, ongoing re-exchange.

### Recommendation
In `addShopIds` (and the parallel `removeShopIds`), de-duplicate the id list before writing back to KV (e.g. use a `Set`), matching the behavior already implemented in `shopify-app-session-storage-redis`'s `addKeyToShopList`. Consider also capping the array size or storing shop→session mapping via a scheme that doesn't require growing a single JSON blob (e.g. one KV key per session id with shop as part of the key prefix, listed via `namespace.list({prefix})`), which avoids both duplicate growth and the KV per-value size ceiling entirely.

### Proof of Concept
1. Deploy an app using `KVSessionStorage` (`packages/apps/session-storage/shopify-app-session-storage-kv/src/kv.ts`) with `future.expiringOfflineAccessTokens` or `useOnlineTokens` enabled, using the token-exchange strategy.
2. As an installed merchant, repeatedly send requests with an expired/invalid session token to a route protected by `validateAuthenticatedSession`/`authenticate.admin`, forcing `performTokenExchange`/`token-exchange.ts` to run `exchangeToken` + `storeSession(offlineSession)` on each request.
3. Observe (via KV admin API or logs) that the `shop:<shop>` key's JSON array keeps appending the same `offline_<shop>` id with each call, since `addShopIds` (`kv.ts:75-79`) never deduplicates.
4. Continue until the array's serialized size approaches the KV per-value limit; subsequent `namespace.put` calls in `storeSession`/`addShopIds` begin failing, causing `storeSession` to throw and breaking authentication for that shop, and/or `findSessionsByShop` (`kv.ts:56-69`) becoming increasingly slow as it re-loads a large number of duplicate ids.

      this.getShopSessionIdsKey(shop),
      {type: 'json'},
    );

    if (!sessionIds) {
      return [];
    }

    return Promise.all(
      sessionIds.map(async (id) => (await this.loadSession(id))!),
    );

  private async addKeyToShopList(session: Session) {
    const shopKey = session.shop;
    const idKey = this.client.generateFullKey(session.id);
    const idKeysArrayString = await this.client.get(shopKey);

    if (idKeysArrayString) {
      const idKeysArray = JSON.parse(idKeysArrayString);

      if (!idKeysArray.includes(idKey)) {
        idKeysArray.push(idKey);
        await this.client.set(shopKey, JSON.stringify(idKeysArray));
      }
    } else {
      await this.client.set(shopKey, JSON.stringify([idKey]));
    }
  }
