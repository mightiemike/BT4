### Title
On-chain deposit/mint path never checks `TokenConfig.Enabled`, letting a disabled (blocked) token continue to mint PRC20/native funds - (File: `x/uexecutor/keeper/handler.go`)

### Summary
Push Chain's `x/uregistry` module exposes a `TokenConfig.Enabled` flag that operators use to disable a token (e.g., after discovering a compromised/malicious token contract, a broken bridge integration, or a liquidity-cap bypass on the source chain) [1](#0-0) . This is conceptually the same "kill switch" primitive as the `ratio = 0` blocking mechanism in the original report. However, exactly like the "neutral adapter" bypass, the on-chain deposit/mint execution path (`depositPRC20`, called from `ExecuteInboundFunds` and the gas/payload execution paths) never reads or enforces `TokenConfig.Enabled` — it only checks that a `TokenConfig` and its `NativeRepresentation` exist, then unconditionally mints PRC20 into the recipient's UEA.

### Finding Description
`depositPRC20` fetches the token config and immediately proceeds to mint, with no branch on `Enabled`: [2](#0-1) 

The inbound validation pipeline that runs before this call — `ValidateForExecution` — validates amount, asset address format, recipient format, and payload shape, but has no check for whether the asset's `TokenConfig.Enabled` is `true`: [3](#0-2) 

`GetTokenConfig`/`GetTokenConfigByPRC20` in `x/uregistry` simply return the stored config without gating on `Enabled`: [4](#0-3) 

A repo-wide search confirms `TokenConfig.Enabled` is read only by the off-chain `universalClient` relayer components (`universalClient/chains/chains.go`, `universalClient/chains/evm/client.go`, `universalClient/chains/svm/client.go`) — i.e., it is used only to decide whether *validators observe/relay* events for a token — and is never dereferenced anywhere in the on-chain `x/uexecutor` execution/minting code path (`handler.go`, `execute_inbound_gas.go`, `execute_inbound_gas_and_payload.go`, `execute_inbound_funds.go`). This means `Enabled=false` only stops *new* honest relayer observations from being generated; it does nothing to stop the chain from executing an inbound that is nonetheless voted through (e.g., an inbound tx that was in flight before disablement, or one submitted by any validator that still relays it — honest validators are assumed, so this isn't a malicious-validator scenario, it's simply that the on-chain guard doesn't exist).

This is the direct analog of the reported bug: the "block" flag (`ratio=0` / `Enabled=false`) is honored by the primary code path (normal adapters / relayer observation gating) but is silently bypassed by a secondary path that still moves funds (the neutral adapter / the on-chain `depositPRC20` minting call), because the blocking check was implemented in the wrong layer.

### Impact Explanation
If operators disable a token via `Enabled=false` in response to a discovered issue (e.g., an external chain contract compromise, unbounded mint bug, or liquidity-cap circumvention on the source chain), the expectation is that Push Chain stops minting the corresponding PRC20/native representation. Because the on-chain execution path never checks this flag, deposits for the disabled token continue to be executed and PRC20 minted into UEAs (unauthorized mint of PRC20/native asset), undermining the only chain-level control meant to stop the exploit and directly enabling continued unauthorized minting / accounting corruption of the PRC20/native representation. `LiquidityCap` is likewise unreferenced by any on-chain enforcement point found in this pass, compounding the exposure.

### Likelihood Explanation
Once a `TokenConfig` is disabled, any inbound event for that token that still reaches quorum (already-in-flight source-chain transactions, or any observation an honest validator set continues to relay because the relayer's own gating is separately timed/raced against the chain-side disablement) will still be minted, since the code contains no `Enabled` gate. No malicious validator or admin action is required to trigger the mint — this is a straightforward missing invariant enforcement in the deposit path, reachable via the ordinary `VoteInbound` → `ExecuteInboundFunds` flow.

### Recommendation
Add an explicit `TokenConfig.Enabled` check (and ideally a `LiquidityCap` check) inside `ValidateForExecution` and/or directly inside `depositPRC20` (and the equivalent gas/payload deposit call sites) before invoking `CallPRC20Deposit`/`CallPRC20DepositAutoSwap`. If the token is disabled, treat the inbound the same way a missing/invalid token config is already treated — mark the PCTx `FAILED` and, for non-isCEA inbounds, schedule the standard `INBOUND_REVERT` outbound path used elsewhere (`handleFailedInboundValidation`, `buildRevertOutbound`).

### Proof of Concept
1. Register `ChainConfig` and `TokenConfig` (with `Enabled: true`) for `eip155:X` / `USDC`, as done in the integration test setup (`setupInboundValidationTest`/`setupInboundCEAPayloadTest`).
2. Submit/observe a valid `FUNDS` inbound and get 3 validator votes to reach quorum — confirm `ExecuteInboundFunds` mints PRC20 successfully.
3. Flip `TokenConfig.Enabled` to `false` (simulating an incident response disablement) via the existing `AddTokenConfig`/update path used in `test/integration/uregistry` tests.
4. Submit a new inbound for the same disabled token/chain and drive it to quorum via `utils.ExecVoteInbound` exactly as in `test/integration/uexecutor/vote_inbound_validation_test.go`.
5. Observe that `ExecuteInboundFunds` → `depositPRC20` → `CallPRC20Deposit` still succeeds and mints PRC20 into the recipient UEA (verifiable via `balanceOf` as in `inbound_cea_payload_test.go`), because no code path reads `TokenConfig.Enabled`.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}

func (p Inbound) ValidateForExecution() error {
	// Validate amount as uint256
	if strings.TrimSpace(p.Amount) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount cannot be empty")
	}
	bi, ok := new(big.Int).SetString(p.Amount, 10)
	if !ok || bi.Sign() < 0 {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be a valid non-negative uint256")
	}
	// Only GAS_AND_PAYLOAD and FUNDS_AND_PAYLOAD allow zero amount (skip deposit, still execute payload)
	if bi.Sign() == 0 && p.TxType != TxType_GAS_AND_PAYLOAD && p.TxType != TxType_FUNDS_AND_PAYLOAD {
		return errors.Wrap(sdkerrors.ErrInvalidRequest, "amount must be positive for this tx type")
	}

	// Validate asset_addr
	if strings.TrimSpace(p.AssetAddr) == "" {
		return errors.Wrap(sdkerrors.ErrInvalidAddress, "asset_addr cannot be empty")
	}

	// isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD
	if p.IsCEA && p.TxType != TxType_FUNDS && p.TxType != TxType_FUNDS_AND_PAYLOAD && p.TxType != TxType_GAS_AND_PAYLOAD {
		return errors.Wrapf(sdkerrors.ErrInvalidRequest, "isCEA is only supported for FUNDS, FUNDS_AND_PAYLOAD, and GAS_AND_PAYLOAD tx types, got: %v", p.TxType)
	}

	// Validate fields required per tx_type
	switch p.TxType {
	case TxType_FUNDS_AND_PAYLOAD, TxType_GAS_AND_PAYLOAD:
		if p.UniversalPayload == nil {
			return errors.Wrap(sdkerrors.ErrInvalidRequest, "payload is required for payload tx types")
		}
		if p.IsCEA && strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty when isCEA is true")
		}
		if p.IsCEA && !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address when isCEA is true: %s", p.Recipient)
		}
		if err := p.UniversalPayload.ValidateBasic(); err != nil {
			return errors.Wrap(err, "invalid payload")
		}
	case TxType_FUNDS, TxType_GAS:
		if strings.TrimSpace(p.Recipient) == "" {
			return errors.Wrap(sdkerrors.ErrInvalidAddress, "recipient cannot be empty")
		}
		if !utils.IsValidAddress(p.Recipient, utils.HEX) {
			return errors.Wrapf(sdkerrors.ErrInvalidAddress, "invalid recipient address: %s", p.Recipient)
		}
	}

	return nil
}

func (k Keeper) GetTokenConfig(ctx context.Context, chain, address string) (types.TokenConfig, error) {
	storageKey := types.GetTokenConfigsStorageKey(chain, address)
	config, err := k.TokenConfigs.Get(ctx, storageKey)
	if err != nil {
		return types.TokenConfig{}, err
	}
	return config, nil
}
