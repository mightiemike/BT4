### Title
`TransactionOutput::ensure_match_transaction_info` skips checkpoint-hash verification, letting replay/state-root divergence pass authenticated checks - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the function used by chunk-executor and `db-tool`'s `replay_on_archive` to authenticate a freshly re-executed `TransactionOutput` against the persisted, ledger-info-proven `TransactionInfo`. It explicitly checks status, gas, write-set hash, and event root hash, but by its own in-code admission it does **not** check `state_checkpoint_hash` or `hot_state_checkpoint_hash`/`position_state_checkpoint_hash` carried in `TransactionInfo`.

### Finding Description
The function ends with: [1](#0-0) 
which is a direct comment admitting the comparator "ignores the checkpoint hashes (state/hot-state and `position_state_checkpoint_hash`)", meaning replay-verify tooling "can report a successful replay even when the authenticated position state root diverges from local execution." The function only validates `status`, `gas_used`, write-set hash (`state_change_hash`), and `event_root_hash`: [2](#0-1) 

This mirrors the external report's bug class: a condition that is supposed to gate acceptance of a value as "matching/trusted" is weaker than intended, so a state that should be rejected (diverging state-checkpoint root) is instead accepted as valid. Here, instead of a wrong `&&`/`||`, the gap is a validation short-circuit by omission — the state-checkpoint root fields exist on `TransactionInfo` (`state_checkpoint_hash`, `hot_state_checkpoint_hash`, `position_state_checkpoint_hash` per `TransactionInfoV0`/`V1`) but are never compared to the locally recomputed state after execution in this authenticated-comparison path.

This function is consumed by `storage/db-tool/src/replay_on_archive.rs`'s `execute_and_verify`, which is the tool operators use to authenticate historical/archived transaction execution against ledger-info-proven `TransactionInfo`: [3](#0-2) 

Because `ensure_match_transaction_info` never recomputes/compares the state (or hot-state) checkpoint hash, a local execution that produces a different state root than the one committed/proven in the archive will still pass this authenticated check, as long as write-set bytes, events, gas and status happen to match.

### Impact Explanation
This breaks the "committed state must match VM result, and proof-bound roots must be authenticated" invariant called out in the state-integrity gate: an authenticated verification path (replay-verify / chunk-executor's transaction-info matching) can silently accept a divergent state-checkpoint root without raising an error. In a hard-fork/consensus-bug scenario, or in the presence of storage corruption on the read path, this specific verification gate would fail to detect the divergence, undermining the replay/restore integrity guarantee that this exact function is meant to provide.

### Likelihood Explanation
The gap is unconditionally present in the standard code path — it requires no special adversarial state and is triggered any time a state-checkpoint hash mismatch exists but write-set/events/gas/status happen to agree (e.g. divergence limited to trading-native/hot-state/position-state components, or accumulator/JMT construction bugs on the state-tree side that don't change the write set itself). The code's own TODO comment corroborates this is a known, currently-unaddressed gap rather than a false positive, though it is explicitly flagged as intentional pending future enablement (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`), which somewhat limits confidence that this represents an active, unprotected mainnet path versus a documented staged rollout gap. I could not fully verify within available context whether `state_checkpoint_hash` is authenticated elsewhere (e.g. `do_state_checkpoint.rs`) in the same call chain before/after `ensure_match_transaction_info`, so it's uncertain whether this specific comparator is the sole authentication point for state-checkpoint roots in the replay/chunk-executor flow.

### Recommendation
Extend `ensure_match_transaction_info` to recompute (or accept as a parameter) the resulting state-checkpoint hash (and hot-state/position-state checkpoint hash where applicable) from local execution and assert equality against `txn_info.state_checkpoint_hash()` / `txn_info.hot_state_checkpoint_hash()` / `txn_info.position_state_checkpoint_hash()`, mirroring the existing `ensure!` pattern already used for write-set and event root hashes, before enabling any feature (e.g. `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) that relies on this function for full authentication.

### Proof of Concept
Conceptual (no exploit code available from static review): run `db-tool replay-on-archive` against a chunk where local execution mutates account state in a way that (a) doesn't change the underlying write-set bytes/order in a way affecting `state_change_hash`, or where a bug/divergence exists purely in state-tree construction (JMT insertion, hot-state promotion) rather than write-set contents, while events/gas/status stay identical to the archived `TransactionInfo`. `ensure_match_transaction_info` at `types/src/transaction/mod.rs:2139-2203` will return `Ok(())` even though the resulting authenticated state root diverges, because `state_checkpoint_hash`/`hot_state_checkpoint_hash` are never compared.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
