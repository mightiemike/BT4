## Title
Reachable panic in `receipt_filter_fn` on stale delayed receipts after resharding causes a chunk-application halt - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
The Cronos report's bug class is "unguarded panics in on-chain logic reachable from ordinary contract/transaction flow, which must instead return a gas-charged error." The nearcore analog is `DelayedReceiptQueueWrapper::receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs:874-878`, which calls `.unwrap()` on `receiver_shard_id(&shard_layout)` while draining the delayed-receipt queue during ordinary chunk `apply()`. This code path is reachable purely by submitting transactions that create receipts and cause the delayed-receipt queue to retain entries across a resharding event — no validator or operator privilege required.

### Finding Description
`receipt_filter_fn` is used by `pop()` (`runtime/runtime/src/congestion_control.rs:880-910`, called from `runtime/runtime/src/lib.rs` during delayed-receipt processing) and `peek_iter()` (`runtime/runtime/src/congestion_control.rs:912-920`) to decide whether a delayed receipt still belongs to the local shard after a resharding split: [1](#0-0) 

`receiver_shard_id` computes the receipt's destination shard from the *current* `ShardLayout`. If a receipt is enqueued and stalls in the delayed queue across **two consecutive resharding generations** (its originally recorded target shard no longer exists in the shard layout by the time it is dequeued), `receiver_shard_id` can fail to remap it, and the `.unwrap()` on the `Result` panics. This same helper backs `pop()` (the mainline path invoked every chunk application while there are delayed receipts) and the bandwidth/peek path — both driven purely by normal, unprivileged transaction/receipt traffic (any account sending receipts that end up delayed due to compute/gas exhaustion, e.g. `GlobalContractDistribution` or ordinary action receipts).

A dedicated regression test in the repository, `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs:32-186`, exists specifically to exercise this scenario: it deploys a global contract (creating a `GlobalContractDistributionReceipt`), then saturates chunk compute with ordinary `burn_gas_raw` function calls submitted by an unprivileged account so the receipt sits in the delayed queue through two forced resharding splits, and asserts the chain does not stall: [2](#0-1) 

The test's own comments explicitly describe the failure mode: *"If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old `target_shard` after two resharding generations."* This confirms the class of bug is known and reachable, matching exactly the Cronos pattern of "unguarded logic panicking instead of gracefully erroring" — except here the trigger is dynamic resharding + normal receipt backlog rather than IBC/ICA message handling.

### Impact Explanation
`apply()` runs as part of chunk production/validation on every honest node processing the shard. A panic inside `receipt_filter_fn`, reached from `pop()` during `process_delayed_receipts` (invoked unconditionally from `runtime/runtime/src/lib.rs:2787-2821` `process_receipts`), aborts the runtime thread and halts chunk application for that shard on every validator that reaches the code path — a transaction/receipt-triggered chain halt, not merely a resource-exhaustion DoS. This falls squarely within the accepted impact class ("a transaction-triggered halt" / "invalid state transition acceptance" via crash rather than error).

### Likelihood Explanation
Triggering requires: (1) dynamic resharding enabled (`ProtocolFeature::DynamicResharding`), (2) at least two resharding splits occurring while a receipt remains stuck in the delayed queue (achievable by any account submitting enough compute-heavy but otherwise ordinary transactions to keep a shard's compute budget saturated across epoch boundaries), and (3) the specific split sequence such that the receipt's originally recorded target shard is fully retired by the second split. This is not attacker-trivial to force resharding timing/config (which is protocol/operator-configured), but the trigger itself — submitting many ordinary function calls to keep compute saturated — is fully within reach of an unprivileged transaction signer once dynamic resharding is active and its parameters make double-splitting plausible within the receipt's dwell time in the queue.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:875-876`) with a guarded fallback: if `receiver_shard_id` cannot resolve the receipt's shard under the current layout, treat the receipt as belonging to the local shard (or reroute/re-derive it via the historical parent/child shard-split mapping) instead of panicking, mirroring the resilient "return calculated value instead of panic" pattern from the referenced Cronos fix. Add an explicit unit/regression test asserting `apply()` returns an `Err`/graceful outcome (never panics) for a receipt whose recorded target shard is absent after multiple resharding generations, extending the existing `test_stale_global_contract_distribution_after_double_resharding` coverage to non-global-contract receipt kinds as well.

### Proof of Concept
1. Enable a `DynamicResharding` epoch config with two scheduled forced shard splits, as configured in `test-loop-tests/src/tests/global_contracts_distribution.rs:59-92`.
2. As an unprivileged account, submit a receipt-generating transaction whose receipt targets the shard that will be split first (e.g., `DeployGlobalContract` from that shard, per lines 105-114).
3. As an unprivileged account, continuously submit ordinary heavy `FunctionCall` transactions (e.g., `burn_gas_raw`) to saturate the shard's per-chunk compute budget every block (lines 116-151), forcing the pending receipt to be pushed into and retained in the delayed-receipt queue.
4. Let both resharding splits complete (lines 152-163).
5. Stop saturating and let the delayed queue drain (lines 165-174): once the stale receipt is popped via `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn`, `receiver_shard_id` cannot map the retired original target shard under the twice-updated `ShardLayout`, and the `.unwrap()` panics, halting chunk application on the processing node(s).
