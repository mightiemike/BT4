### Title
Proof verification is skipped based on an unauthenticated `proof_facts` cache hit, allowing reuse of another transaction's proof to bypass privacy-proof verification - (File: crates/apollo_transaction_converter/src/transaction_converter.rs)

### Summary
The gateway's proof-verification path for "private" `RpcInvokeTransactionV3` transactions (those carrying non-empty `proof_facts`/`proof`) skips cryptographic verification of the submitted proof whenever the `proof_manager_client` already contains an entry for the supplied `proof_facts` value. Because `proof_facts` on an inbound transaction is fully attacker-controlled and is not cryptographically bound to the rest of that transaction (sender, calldata, nonce), an attacker can copy a `proof_facts` value observed in any previously verified, unrelated transaction and attach it to a new, otherwise-unverified transaction. The gateway will treat the new transaction as already proof-verified and admit it to the mempool without ever invoking the actual proof-verification circuit on the attacker's transaction. This mirrors the SPDM analog: a verification result established for one "session" (one proof/fact pair) is silently reused to authenticate a different, unrelated request, because the code path that shortcuts verification never re-checks that the current request's cryptographic material corresponds to what was actually proven.

### Finding Description
`TransactionConverter::run_proof_verification` is the shared logic used by both the gateway (`spawn_proof_verification`) and consensus (`spawn_verify_and_store_proof`) flows: [1](#0-0) 

```
async fn run_proof_verification(proof_facts, proof, proof_manager_client) -> Result<bool, ...> {
    let contains_proof = proof_manager_client.contains_proof(proof_facts.clone()).await?;
    if contains_proof {
        return Ok(false);
    }
    ...
    starknet_proof_verifier::verify_proof(proof_facts, proof) // only reached if NOT already cached
    ...
}
```

If `contains_proof(proof_facts)` returns `true`, the function returns immediately with `Ok(false)` — the supplied `proof` bytes are never passed to `verify_proof` at all for this call. The gateway path (`spawn_proof_verification`) then reports the `VerificationHandle` as successful, and `await_verification_task_and_extract_proof_data` in the gateway happily returns `Some((proof_facts, proof))` as validated proof data: [2](#0-1) 

The `proof_facts` value that keys this cache is a plain user-supplied field on the RPC transaction (`RpcInvokeTransactionV3.proof_facts`), copied verbatim from the incoming request in `convert_rpc_tx_to_internal`: [3](#0-2) 

There is no check anywhere in this path that ties the specific `proof_facts` value to the sender address, calldata, or nonce of *this* transaction — `proof_facts` is only used as a lookup key into the proof-manager cache (`proof_manager_client.contains_proof(proof_facts.clone())`) and as the payload hashed for storage (`proof_facts.hash()`), as seen in `get_proof`/`store_proof_in_proof_manager`: [4](#0-3) 

Once one legitimate private transaction with `proof_facts = F` has been verified and stored (`proof_manager_client.set_proof`), `F` is a public/observable value (it appears in gateway/mempool broadcast, and is stored server-side). Any subsequent, completely unrelated transaction from any sender that reuses `proof_facts = F` (with an arbitrary, non-empty `proof` byte string, since only `proof.is_empty()` is checked before the cache-hit short-circuit — see `verify_proof`'s early `EmptyProof` guard which is bypassed entirely by the cache hit) will be accepted by `run_proof_verification` as "already verified," without the proof-verification circuit (`privacy_circuit_verify_v1::verify_recursive_circuit`) ever running against the actual proof bytes submitted with that transaction.

This is the direct structural analog of CVE-2023-31127: the responder (gateway) trusts that reaching a "finish" state (proof-manager cache hit) implies the full authentication/verification transcript was actually checked for *this* request, when in fact the cache hit only proves *some* transaction with matching `proof_facts` was verified previously — the binding between the verified artifact and the current request is missing.

### Impact Explanation
Any single unprivileged transaction sender able to observe a previously broadcast/verified private invoke transaction's `proof_facts` value can craft their own transaction reusing that value to have the gateway accept it as proof-verified without ever validating a proof against it. Depending on what invariant `proof_facts`/`Proof` are meant to enforce for these "private transactions" (the mechanism attests to program output produced off-chain, gating what the transaction is permitted to claim/execute), this allows an attacker to get a transaction admitted to the mempool (and consequently into blocks) that carries a completely unverified, attacker-chosen "proof" payload. This is a verification-bypass of the intended trust boundary for private transactions, directly reachable from a single submitted transaction with no special privileges — matching the "gateway validation" and "unauthorized account action" categories in scope.

I was not able to fully trace, within the available iterations, exactly which fields of `ProofFacts`/`Proof` are subsequently trusted at Blockifier execution time (i.e., whether the bypassed verification directly authorizes state changes, fee exemptions, or hidden calldata correctness), so I cannot conclusively quantify the downstream monetary/state impact beyond the demonstrated verification-skip itself. This should be confirmed by tracing how `proof_facts`/execution consumes this data during `convert_internal_rpc_tx_to_executable_tx` and blockifier execution.

### Likelihood Explanation
High likelihood of exploitability for the verification-bypass primitive itself: it requires only (a) observing one publicly-verified private transaction's `proof_facts` value (trivially obtainable, since it's included in the transaction and later returned via `convert_internal_rpc_tx_to_rpc_tx`/broadcast), and (b) submitting a new transaction with that `proof_facts` value and arbitrary non-empty `proof` bytes. No special privileges, timing races, or cryptographic breaks are required.

### Recommendation
- Cryptographically bind `proof_facts` to the specific transaction it accompanies (e.g., include the transaction hash, sender address, or a nonce/calldata commitment inside the values that are proven, or require `proof_facts` to be re-derived/re-verified per transaction hash rather than cached by raw content).
- Do not treat a `proof_manager` cache hit as sufficient proof that *this* transaction's submitted proof is valid; either always run `verify_proof` for the submitted `(proof_facts, proof)` pair, or verify that the cached entry was stored for a request with an equivalent binding to the current transaction context.
- Add regression tests asserting that submitting a valid `proof_facts` value from transaction A alongside an invalid/garbage `proof` inside transaction B (different sender/calldata) is rejected.

### Proof of Concept
1. Submit a legitimate private `Invoke` V3 transaction `tx_A` with `proof_facts = F` and a valid `proof = P` to the gateway; it passes `verify_proof` and `proof_manager_client.set_proof(F, P)` stores it (`store_proof_and_spawn_archiving` in `crates/apollo_gateway/src/gateway.rs`).
2. Craft a new, unrelated `Invoke` V3 transaction `tx_B` (different `sender_address`, `calldata`, `nonce`, own valid signature over `tx_B`), setting `proof_facts = F` (copied from `tx_A`) and `proof = <arbitrary non-empty bytes>`.
3. Submit `tx_B` to the gateway. In `TransactionConverter::run_proof_verification`, `proof_manager_client.contains_proof(F)` returns `true` (from step 1), so the function returns `Ok(false)` immediately — `verify_proof(F, <arbitrary bytes>)` is never called.
4. `tx_B` is reported as verified (`VerificationHandle`/`await_verification_task_and_extract_proof_data` returns success) and proceeds through stateful validation and into the mempool, despite carrying an unverified/garbage `proof`.

```rust
    async fn run_proof_verification(
        proof_facts: ProofFacts,
        proof: Proof,
        proof_manager_client: SharedProofManagerClient,
    ) -> Result<bool, TransactionConverterError> {
        let contains_proof = proof_manager_client.contains_proof(proof_facts.clone()).await?;

        if contains_proof {
            return Ok(false);
        }

        let proof_facts_hash = proof_facts.hash();
        let verify_start = Instant::now();
        tokio::task::spawn_blocking(move || {
            starknet_proof_verifier::verify_proof(proof_facts, proof)
        })
        .await
        .expect("proof verification task panicked")?;
        let verify_duration = verify_start.elapsed();
        PROOF_VERIFICATION_LATENCY.record(verify_duration.as_secs_f64());
        info!(
            "Proof verification took: {verify_duration:?} for proof facts hash: \
             {proof_facts_hash:?}"
        );

        Ok(true)
    }
```

```rust
    async fn await_verification_task_and_extract_proof_data(
        &self,
        verification_handle: Option<VerificationHandle>,
        tx_signature: &TransactionSignature,
    ) -> Result<Option<(ProofFacts, Proof)>, StarknetError> {
        let Some(handle) = verification_handle else {
            return Ok(None);
        };

        handle
            .verification_task
            .await
            .map_err(|e| {
                warn!("Proof verification task panicked: {}", e);
                StarknetError::internal_with_logging("Proof verification task panicked:", &e)
            })?
            .map_err(|e| {
                warn!("Proof verification failed: {}", e);
                transaction_converter_err_to_deprecated_gw_err(tx_signature, e)
            })?;

        Ok(Some((handle.proof_facts, handle.proof)))
    }
```
