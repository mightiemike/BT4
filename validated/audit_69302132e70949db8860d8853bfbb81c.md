This confirms a concrete, reachable griefing analog. `DeductGasFeesFromReceipt` bills the recipient (the UEA) for `receipt.GasUsed` whenever the EVM call produced any receipt at all, regardless of whether the call ultimately reverted [1](#0-0) , and `ExecutePayload` explicitly deducts fees "regardless of success/failure" before even checking `execErr` [2](#0-1) . Combined with the fact that `MsgExecutePayload` can be submitted gaslessly by any `Signer`, not just the UEA owner [3](#0-2) , and that the Go keeper never checks `UniversalPayload.Deadline` against current time before dispatching the call — that freshness check lives only inside the external UEA Solidity contract [4](#0-3)  — this is a solid, in-scope analog of the ULTI bug class.

### Title
Unprivileged replay of an owner-signed but expired `UniversalPayload` repeatedly drains UEA gas balance via unconditional fee deduction - (File: `x/uexecutor/keeper/msg_execute_payload.go`)

### Summary
The ULTI report's root cause is that a time-bound parameter (`deadline`) is never checked for staleness before the chain spends resources on it, letting an attacker force wasted, unrecoverable work. Push Chain's `MsgExecutePayload` path has the same missing check: the Cosmos/Go keeper layer never validates `UniversalPayload.Deadline` against `ctx.BlockTime()` before calling `CallUEAExecutePayload` and unconditionally billing gas to the target UEA.

### Finding Description
`ExecutePayload` in `x/uexecutor/keeper/msg_execute_payload.go` performs no deadline freshness check on the incoming `UniversalPayload` before dispatching the EVM call [2](#0-1) . The `UniversalPayload.ValidateBasic()` only checks that `Deadline` parses as a valid non-negative uint256 — it never compares it to the current time [5](#0-4) .

`MsgExecutePayload` is designed so that `Signer` (who pays no Cosmos fee, since the message is gasless) can be any account, distinct from the UEA `Owner` — third-party relaying of the owner's pre-signed payload is an intentional feature [6](#0-5) . The actual deadline/freshness enforcement happens only inside the external UEA contract's `executeUniversalTx`, which is out of this repository's scope [7](#0-6) .

Regardless of whether that contract-side check causes a revert, `DeductGasFeesFromReceipt` bills the UEA for `receipt.GasUsed` as long as a receipt exists with nonzero gas used — it does not gate on success [1](#0-0) , and `ExecutePayload` calls it unconditionally before inspecting `execErr` [2](#0-1) . Because the contract-side deadline revert happens *inside* the EVM call (after `nonce`/signature checks consume gas), and because the nonce is not consumed on revert, the exact same expired, previously leaked/observed `VerificationData` + `UniversalPayload` pair can be resubmitted via `MsgExecutePayload` an unbounded number of times by any unprivileged party — each submission burns real `upc` gas fees from the victim UEA's balance for a call that is guaranteed to fail.

### Impact Explanation
This is a repeatable, unprivileged griefing vector against unwitting UEA owners: any already-signed payload that becomes stale (deadline passes before it's ever submitted, or after a first failed submission) can be replayed indefinitely to drain the victim's on-chain `upc` balance in small increments, with no way for the victim to stop it once the signed payload has leaked (e.g., observed by any relaying party, mempool watcher, or the original `Signer`). This is a direct unauthorized loss of protocol/user-controlled funds analogous to the ULTI LP-griefing bug, though the specific mechanism (per-call metered gas loss vs. one-time frozen LP position) differs, and the amounts drained per replay are bounded by `receipt.GasUsed`.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the attacker to have obtained a validly-signed but not-yet-expired-or-newly-expired `UniversalPayload` + `VerificationData` pair (e.g., by monitoring gasless mempool traffic, or if the original relayer/`Signer` fails to deliver it before the deadline), and requires the underlying contract's deadline check to occur only after some gas-consuming logic (nonce lookup, storage reads) inside `executeUniversalTx`.

### Recommendation
Add an explicit deadline check in the Go keeper (`ExecutePayload` / `ExecutePayloadV2` in `x/uexecutor/keeper/msg_execute_payload.go` and `execute_payload.go`) that compares `UniversalPayload.Deadline` against `sdkCtx.BlockTime().Unix()` and rejects the message before any EVM dispatch or fee deduction if the deadline has already passed. This mirrors the ULTI fix (`revert when block.timestamp > deadline`) and prevents wasted, unrecoverable gas billing on the victim UEA for calls that are certain to fail.

### Proof of Concept
1. Owner signs a `UniversalPayload` with `Deadline = T` and a valid `VerificationData` (Ed25519/ECDSA signature) intended for delivery by a relayer within the deadline window.
2. The relayer (or any observer who intercepts the gasless tx before/after inclusion) fails to deliver it in time, or deliberately withholds it until `T` passes.
3. Any unprivileged attacker submits `MsgExecutePayload` with the exact same `UniversalAccountId`, `UniversalPayload`, and `VerificationData` after `T`. Because `Signer` need not equal `Owner`, this succeeds at the Cosmos layer's authorization check [8](#0-7) .
4. `k.CallUEAExecutePayload` reaches the UEA contract, which reverts on the expired deadline — but only after consuming some gas for signature/nonce checks.
5. `DeductGasFeesFromReceipt` still bills the UEA owner's balance for `receipt.GasUsed` [1](#0-0) , because nonce was never incremented on revert.
6. Steps 3–5 can be repeated indefinitely by the same or different attackers, since the leaked payload remains "valid" cryptographically (signature checks out) even though it's expired — draining the victim's UEA balance in a griefing loop with zero cost to the attacker (the outer `MsgExecutePayload` is itself gasless for the `Signer`) [9](#0-8) .

**Uncertainty note:** I was unable to confirm from the indexed code exactly how much gas the UEA Solidity contract's `executeUniversalTx` consumes before hitting its deadline check (that contract lives in the separate `push-chain-core-contracts` repository, outside this repo's index), so the precise per-replay drain amount and whether the deadline check happens before or after nonce consumption cannot be fully verified here. A Devin session with access to that contract's source would be needed to confirm the exact gas-consumption ordering and quantify the drain.

```markdown
### Authorization model for `MsgExecutePayload` (contract-only binding)

`MsgExecutePayload` follows a **contract-only binding** authorization model. The Cosmos signer of the message and the owner of the target Universal Account are intentionally distinct roles:

- **`Signer`** identifies the Cosmos transaction signer — the party that delivers the owner's pre-authorized payload to Push Chain. `MsgExecutePayload` is a gasless message type (see `app/txpolicy/gasless.go`), so the signer pays no Cosmos transaction fee. Any account may submit the message.
- **`UniversalAccountId.Owner`** identifies the UEA whose pre-authorized payload is being executed. The actual EVM execution gas is deducted from this UEA;s balance (`DeductGasFeesFromReceipt`), not from the signer.

**The chain module deliberately does not enforce `Signer == EVM(Owner)`.** If it did, third-party delivery of owner-signed payloads would be impossible — every owner would have to submit their own Cosmos transactions even though the chain charges them no Cosmos fee for doing so, defeating the cross-chain UX promise of letting an external account act on Push Chain through delivered payloads.
```

```markdown
#### Where authorization actually lives

The cryptographic binding is enforced inside the UEA contract's `executeUniversalTx` (see [`UEA_EVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_EVM.sol#L145) and [`UEA_SVM.sol`](https://github.com/pushchain/push-chain-core-contracts/blob/86e20e2d26819e7cc885549f08c66895221dfab0/src/uea/UEA_SVM.sol)):

1. The contract holds the owner's public key as **immutable bytes** set at UEA deployment via `initialize(_id, _factory)`. There is no code path that mutates this after init.
2. `executeUniversalTx(payload, signature)` verifies the `signature` (passed in as `MsgExecutePayload.VerificationData`) against this stored owner — ECDSA recovery for EVM-origin owners, the Ed25519 precompile (`0x00…00ca`) for SVM-origin owners.
3. The signed payload hash includes a contract-tracked `nonce` (monotonic per UEA) and optional `deadline`, providing replay and freshness protection.
4. If signature verification fails, the contract reverts. The revert propagates as `execErr` from `CallUEAExecutePayload`; the keeper returns the error from `ExecutePayload`; the entire Cosmos transaction (including any partial gas-fee deduction) rolls back atomically. **No state changes survive a failed signature check.**
```

```markdown
#### Why this is safe under `Signer ≠ Owner`

An attacker submitting `MsgExecutePayload` with their own `Signer` and a victim's `UniversalAccountId` produces no exploitable outcome:

- The factory resolves the victim's UEA address from the embedded `UniversalAccountId` — correct.
- `evmFrom` (derived from `Signer`) becomes the EVM-level `msg.sender` of the call to the UEA. Since `evmFrom != UNIVERSAL_EXECUTOR_MODULE` (`0x14191Ea54B4c176fCf86f51b0FAc7CB1E71Df7d7`), the contract enforces the signature check.
- The attacker cannot forge `VerificationData` that recovers to the victim's owner key.
- The contract reverts → the keeper returns an error → the Cosmos transaction reverts in full.
- Net effect: zero state change. No EVM gas is charged to the victim UEA (the deduction is rolled back with the rest of the transaction). The submission costs the attacker nothing on chain (gasless), but also achieves nothing.
```
