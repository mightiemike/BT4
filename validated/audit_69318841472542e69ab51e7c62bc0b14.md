### Title
Missing tenure-identity binding for `TenureChangeCause::Extended` allows a new sortition winner's first block to be misfiled as an extension of a different miner's tenure - (File: stackslib/src/chainstate/nakamoto/tenure.rs)

### Summary
`NakamotoChainState::check_nakamoto_tenure` validates the `BlockFound` cause by cross-checking `parent_tenure.tenure_id_consensus_hash != tenure_payload.prev_tenure_consensus_hash`, but the parallel branch for `Extended` (and its sibling extend-causes) only checks internal self-consistency (`tenure_consensus_hash == prev_tenure_consensus_hash`) and never compares this against the parent block's actual tenure (`parent_tenure.tenure_id_consensus_hash`). This lets a genuinely new sortition winner submit their first block tagged `Extended`, pointing at the prior (different) miner's tenure tip, and be accepted as a continuation of that prior tenure.

### Finding Description
The claimed equality is: `declared_cause(block) == actual_context(sortition_winner_changed | same_miner_continuing)`.

The relevant code path is `NakamotoChainState::check_nakamoto_tenure` [1](#0-0) .

For `TenureChangeCause::BlockFound`, tenure continuity with the parent block's real tenure is explicitly enforced: [2](#0-1) 

For `TenureChangeCause::Extended` (and the other extend variants), the code only checks the payload's own self-consistency and never re-derives/compares against `parent_tenure.tenure_id_consensus_hash`: [3](#0-2) 

The earlier snapshot-level checks for the non-first-tenure case are also self-referential when `tenure_consensus_hash == prev_tenure_consensus_hash` (as is required/true for `Extended`), so `prev_sn.consensus_hash != tenure_sn.consensus_hash` is trivially satisfied and provides no cross-tenure binding: [4](#0-3) 

`get_ongoing_tenure(headers_conn, &block_header.parent_block_id)` is fetched purely to compute `previous_tenure_blocks`/continuity for `BlockFound`, but for `Extended` its `tenure_id_consensus_hash` is never compared to the payload's declared `tenure_consensus_hash`: [5](#0-4) 

Separately, `NakamotoBlock::check_tenure_tx` in `mod.rs` only verifies that the payload's `pubkey_hash` matches the block signer and that `tenure_consensus_hash` matches the block header's own consensus hash — it performs no cross-check against the sortition winner's registered leader key for that consensus hash: [6](#0-5) 

That winner-identity binding normally only happens via the coinbase VRF-proof check (`check_normal_coinbase_tx`/`validate_vrf_seed`), which is exclusively gated on the presence of a coinbase transaction — and a coinbase transaction is only permitted/required when the cause `expects_sortition()` (i.e., `BlockFound`): [7](#0-6) [8](#0-7) 

**Attack flow**: A new miner wins sortition `Y` following prior miner's tenure `X`. Instead of submitting a `BlockFound`+coinbase block (which would trigger the VRF/leader-key check tying the miner's identity to `Y`'s winner), the attacker crafts a tenure-change-only block with:
- `tenure_consensus_hash = prev_tenure_consensus_hash = Y` (self-consistent, satisfies line 797's check)
- `previous_tenure_end = parent_block_id` = the tip of tenure `X` (a different miner's tenure)
- `previous_tenure_blocks` = the actual block count of tenure `X` (public info, trivially satisfies the `tenure_len` check at lines 812-824)
- `cause = TenureChangeCause::Extended`, no coinbase tx

`check_nakamoto_tenure` returns `Ok(Some(parent_tenure))` (`parent_tenure` being `X`'s record) because the `Extended` branch never asserts `tenure_consensus_hash == parent_tenure.tenure_id_consensus_hash`. The block is accepted as a "continuation" of tenure `X`, even though it is really the first block of the distinct, sortition-authorized tenure `Y`.

### Impact Explanation
This is a deterministic validation gap in `check_nakamoto_tenure`, so every honest node applies the same (incorrect) acceptance logic — an invalid block is accepted network-wide, matching the Critical category. Consequences include: the new miner inherits `X`'s tenure block-count budget (`previous_tenure_blocks`/`coinbase_height` does not advance per `advance_nakamoto_tenure`'s `Extended` branch, since `coinbase_height` stays at `parent_coinbase_height`), and the new miner's block bypasses the VRF/leader-key check that `BlockFound` blocks are subject to, since no coinbase is required for `Extended`. This corrupts the tenure/coinbase-height accounting used for reward and read/write budget bookkeeping and lets a miner who did not follow the sortition-authorized `BlockFound` path masquerade as extending someone else's tenure. [9](#0-8) 

### Likelihood Explanation
The only precondition is that the attacker legitimately wins a Bitcoin sortition (achievable with their own BTC and a single miner slot, no majority stake needed) and then crafts the tenure-change payload fields as described instead of the expected `BlockFound`+coinbase payload. No signer collusion, majority stake, or privileged role is required — this is fully within the stated "unprivileged, single miner slot" threat model, and is repeatable every time a new miner wins a sortition following a different miner's tenure.

### Recommendation
In the `Extended`/extend-cause branch of `check_nakamoto_tenure`, add an explicit check that `tenure_payload.tenure_consensus_hash == parent_tenure.tenure_id_consensus_hash` (mirroring the `BlockFound` branch's check against `prev_tenure_consensus_hash`), ensuring an extend can only be filed against the tenure that the parent block actually belongs to, and rejecting any extend payload whose declared tenure differs from the parent's real ongoing tenure.

### Proof of Concept
Rust integration test plan (in `stackslib/src/chainstate/nakamoto/tests/node.rs` or `stacks-node/src/tests/signer/v0/tenure_extend.rs` style):
1. Boot two miners to Nakamoto; Miner 1 wins tenure `X`, submits a normal `BlockFound` block, signers accept, tip advances.
2. Advance the burnchain so Miner 2 wins the next sortition `Y` (`ensure_commit_miner_2`, mine BTC block).
3. Instead of using the standard `mine_bitcoin_block_and_tenure_change_tx(..., TenureChangeCause::BlockFound, ...)` path, construct a `TenureChangePayload` with `cause = TenureChangeCause::Extended`, `tenure_consensus_hash = prev_tenure_consensus_hash = Y`, `previous_tenure_end = <tip of tenure X>`, `previous_tenure_blocks = <actual block count of X>`, `pubkey_hash = Miner2's pkh`, and no coinbase tx, then submit this as Miner 2's block.
4. Call `NakamotoChainState::check_nakamoto_tenure(&mut headers_conn, &mut sort_handle, &block.header, &payload)` directly and assert on both sides of the equality:
   - `payload.tenure_consensus_hash` (`Y`) vs `parent_tenure.tenure_id_consensus_hash` (`X`) — assert they differ.
   - Assert the function currently returns `Ok(Some(_))` (accepting the mismatched extend) instead of the expected `Ok(None)` rejection.
5. Fix validation to add the missing equality check, re-run, and assert `check_nakamoto_tenure` now returns `Ok(None)`, with a `TENURE_REWARD`/`SORTITION` rejection log analogous to the `BlockFound` branch's warning.

    pub(crate) fn check_tenure_tx(&self) -> Result<(), ChainstateError> {
        // If this block has a tenure-change, then verify that the miner public key is the same as
        // the leader key.  This is required for all tenure-change causes.
        let Some(tc_payload) = self.get_tenure_tx_payload() else {
            return Ok(());
        };

        // in all cases, the miner public key must match that of the tenure change
        let recovered_miner_hash160 = self.recover_miner_pubkh()?;
        if tc_payload.pubkey_hash != recovered_miner_hash160 {
            warn!(
                "Invalid tenure-change transaction -- bad miner pubkey hash160";
                "consensus_hash" => %self.header.consensus_hash,
                "stacks_block_hash" => %self.header.block_hash(),
                "stacks_block_id" => %self.header.block_id(),
                "pubkey_hash" => %tc_payload.pubkey_hash,
                "recovered_miner_hash160" => %recovered_miner_hash160
            );
            return Err(ChainstateError::InvalidStacksBlock(
                "Invalid tenure change -- bad miner pubkey hash160".into(),
            ));
        }

        // in all cases, the tenure change's consensus hash must match the block's consensus
        // hash
        if tc_payload.tenure_consensus_hash != self.header.consensus_hash {
            warn!(
                "Invalid tenure-change transaction -- bad consensus hash";
                "consensus_hash" => %self.header.consensus_hash,
                "stacks_block_hash" => %self.header.block_hash(),
                "stacks_block_id" => %self.header.block_id(),
                "tc_payload.tenure_consensus_hash" => %tc_payload.tenure_consensus_hash
            );
            return Err(ChainstateError::InvalidStacksBlock(
                "Invalid tenure change -- bad consensus hash".into(),
            ));
        }

        Ok(())
    }
