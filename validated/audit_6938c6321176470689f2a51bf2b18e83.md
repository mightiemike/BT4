### Title
Missing `block_direct_execute_call` Guard in `library_call` Syscall Allows Bypass of `__execute__` Direct-Call Protection - (File: `crates/blockifier/src/execution/syscalls/hint_processor.rs`)

### Summary
The `call_contract` syscall handler explicitly blocks any attempt to invoke the reserved `__execute__` selector directly (outside of the sequencer's own validated top-level transaction flow) via `maybe_block_direct_execute_call`. This guard, however, is not applied on the `library_call` syscall path, which executes arbitrary declared class code under the *caller's own storage/caller context* (delegate-call semantics). This asymmetry is directly analogous to the reported Vader issue where `BasePool.swap()` lacked the `onlyRouter` modifier that its sibling implementation enforced, allowing callers to reach privileged logic while skipping the validation normally performed by the trusted entry path.

### Finding Description
Blockifier deliberately forbids contracts from calling another contract's `__execute__` entry point directly via `call_contract`, because `__execute__` is meant to run only as the terminal step of a transaction that has already passed `__validate__`, nonce, and fee-resource checks performed by the sequencer/OS. This protection is implemented uniformly across the VM and Native syscall handlers and the deprecated syscall handler: [1](#0-0) [2](#0-1) [3](#0-2) 

The actual check lives in a shared helper: [4](#0-3) 

`library_call`, however, executes the target class's bytecode while keeping the *calling contract's* `storage_address`/`caller_address` (true delegate-call semantics) rather than the callee's identity, and its implementation builds the `CallEntryPoint` without ever invoking `maybe_block_direct_execute_call` on the requested `entry_point_selector`: [5](#0-4) 

Because `library_call` accepts an arbitrary `class_hash` and `entry_point_selector`, any contract can supply the class hash of a declared account contract together with `selector!("__execute__")` and reach the account's `__execute__` logic — the exact call path that `call_contract`'s guard was built to close — without tripping `block_direct_execute_call`.

### Impact Explanation
This is directly analogous to the external report's `BasePool.swap()` finding: one entry path (`call_contract`) enforces the intended restriction, while a functionally equivalent path (`library_call`) does not, letting an unprivileged caller reach code that was designed to be reachable only through the validated top-level transaction flow. Any Starknet account/contract deployed on-chain whose `__execute__` implementation does not itself independently re-verify `get_caller_address() == 0` (the check is convention, not syscall-enforced) can have its `__execute__` logic executed via `library_call` under an attacker-controlled contract's storage/caller context, letting the attacker perform sub-calls that appear to originate from the account's code path without having gone through `__validate__`, nonce increment, or fee charging for that execution — an unauthorized account action bypassing the resource/validation accounting the direct-call block was designed to guarantee.

### Likelihood Explanation
Reachable from a single, ordinary transaction: any contract call can invoke `library_call` with attacker-chosen `class_hash` and `entry_point_selector`, requiring no special privileges, staking, or network position — matching the required "unprivileged transaction sender / contract call" reachability bar.

### Recommendation
Apply the same `maybe_block_direct_execute_call(selector)` check inside the `library_call` handlers (VM, Native, and deprecated syscall executor) that is already applied in the corresponding `call_contract` handlers, so that the `EXECUTE_ENTRY_POINT_NAME` selector is rejected regardless of whether it is reached via `call_contract` or `library_call`.

### Proof of Concept
1. Declare/observe any account class whose `__execute__` does not (or cannot, given delegate-call semantics) reliably re-check the true origin of the call.
2. From an arbitrary attacker contract, invoke the `library_call` syscall with `class_hash` = the account class hash and `entry_point_selector` = `selector!("__execute__")`, passing attacker-chosen inner `contract_address`/`selector`/`calldata`.
3. Observe that, unlike an equivalent attempt through `call_contract` (which is rejected per `crates/blockifier/src/execution/syscalls/syscall_tests/call_contract.rs:297-344`), the `library_call` path proceeds because `maybe_block_direct_execute_call` is never invoked in `crates/blockifier/src/execution/syscalls/hint_processor.rs:631-648`.

    pub(crate) fn maybe_block_direct_execute_call(
        &mut self,
        selector: EntryPointSelector,
    ) -> SyscallResult<()> {
        let versioned_constants = &self.context.tx_context.block_context.versioned_constants;
        if versioned_constants.block_direct_execute_call
            && selector == selector_from_name(EXECUTE_ENTRY_POINT_NAME)
        {
            return Err(SyscallExecutionError::Revert { error_data: vec![INVALID_ARGUMENT_FELT] });
        }
        Ok(())
    }
