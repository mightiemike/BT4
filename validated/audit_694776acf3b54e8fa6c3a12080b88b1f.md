### Title
Unbounded Growth of Per-Pubkey Secondary-Index Reverse-Mapping Vec Causes Linear-Scan CPU Blowup on Insert/Remove - (File: accounts-db/src/accounts_index/secondary.rs)

### Summary
`SecondaryIndex::insert()` and `SecondaryIndex::remove_by_inner_key_if()` maintain a reverse mapping from an account pubkey (`inner_key`) to the set of outer keys (e.g. SPL-token mint/owner or program-id values) it has ever been indexed under, stored as `SecondaryReverseIndexEntry = RwLock<Vec<Pubkey>>` [1](#0-0) . This mirrors the reported bug class: an unbounded, user-influenceable array that is linearly scanned on every mutation and drained on removal, so cost grows with the number of entries a single key has accumulated rather than being bounded.

### Finding Description
On every `insert(key, inner_key)` call, the code takes a write lock on the reverse-index entry for `inner_key` and performs a linear `outer_keys.contains(key)` scan before conditionally pushing:
```
let mut outer_keys = reverse_index_entry.write().unwrap();
...
if !outer_keys.contains(key) {
    outer_keys.push(*key);
}
``` [2](#0-1) 

The code comment explicitly acknowledges the Vec is expected to stay small ("the only case an inner key should map to a different outer key is if the account had different indexed data across different slots... this is rare") [1](#0-0) , but nothing enforces a bound. The indexed value for `AccountIndex::SplTokenMint` / `SplTokenOwner` is read directly from attacker-controlled account data (the mint/owner field of an SPL-token-shaped account), so a wallet can repeatedly rewrite its own account's mint/owner bytes across many slots. Each distinct value observed for the same pubkey appends a new outer_key to that pubkey's reverse-index Vec, since `insert()` never deduplicates or evicts old outer keys unless they are explicitly removed via `remove_by_inner_key_if`.

When the Vec grows to size `n`:
- Every subsequent `insert()` for that same pubkey costs O(n) due to the `contains()` scan, so `n` repeated mutations cost O(n²) total.
- `remove_by_inner_key_if()` drains the entire Vec and calls `remove_index_entries()` (an O(1) DashMap lookup per element, but with `panic!` on any invariant violation) once per outer key, so removal cost scales with `n` too [3](#0-2) .

This is directly analogous to the reported Solidity bug: an attacker-controlled operation grows an unbounded array tied to a single key, and the "cleanup"/removal path (here, `remove_by_inner_key_if`, invoked from `AccountsDb::purge_secondary_indexes_for_dead_keys` during clean/purge) must do work proportional to that array's size [4](#0-3) .

### Impact Explanation
Secondary indexes (`--account-index program-id/spl-token-mint/spl-token-owner`) are opt-in RPC-serving features, but on validators that enable them, this allows a single attacker-controlled pubkey to force disproportionate CPU cost onto the validator's account clean/purge/insert path each time that account is touched, since every insert into the reverse-index Vec becomes O(n) and every eventual removal is O(n) as well. Because the growth is entirely driven by data the attacker writes into their own account across ordinary transactions, no privileged role is needed. This matches the "disproportionate storage and CPU cost" category explicitly listed as in-scope.

### Likelihood Explanation
Requires the target validator to run with a secondary account index enabled (`--account-index`), which is a common RPC-node configuration, not the validator's core/default path. The attacker only needs to submit transactions that repeatedly change the SPL-token mint/owner field of an account they control across distinct slots, which is entirely within normal, unprivileged user capability — no special permissions, consensus role, or malicious snapshot needed.

### Recommendation
Bound the reverse-index Vec size per inner_key (e.g. cap the number of distinct outer keys tracked, or replace the Vec with a `HashSet`/small-set structure with an enforced maximum, evicting the oldest entry when the cap is exceeded), and consider making `insert()` amortized O(1) (e.g., dedupe via a hash set) rather than relying on the "rare" assumption. Metrics/alerts (`num_reverse_index_keys`, `num_inner_keys` already emitted) could also be used to detect and rate-limit degenerate reverse-index growth.

### Proof of Concept
1. Start a validator/RPC node with `--account-index spl-token-mint` (or `spl-token-owner`) enabled.
2. As an unprivileged user, create an SPL-token-account-shaped account for pubkey `P` with mint field `M1`; this calls `SecondaryIndex::insert(M1, P)`, creating `reverse_index[P] = [M1]`.
3. Repeatedly rewrite the same account's data across N distinct slots, each time setting a distinct mint value `M2, M3, ..., MN` (all valid 32-byte pubkey-shaped values chosen by the attacker) before the account is rooted/cleaned so each version is indexed via `insert()`.
4. Each `insert()` call for pubkey `P` performs an O(current length) `contains()` scan over `reverse_index[P]`, so the N insertions cost O(N²) total, and the corresponding entry is never pruned until `remove_by_inner_key_if(P, ...)` is invoked (e.g., during clean when the account becomes zero-lamport/dead), at which point that single removal drains and processes all N outer-key mappings in one call, referenced at [3](#0-2) .
5. Measure clean/insert wall-clock time growth as N increases to demonstrate the quadratic/linear blowup tied to a single attacker-controlled pubkey.

    fn purge_secondary_indexes_for_dead_keys<'a>(
        &self,
        removed_keys: impl IntoIterator<Item = &'a Pubkey>,
    ) {
        if self.account_indexes.is_empty() {
            return;
        }
        for key in removed_keys {
            // Purging secondary entries for a key that is still alive in the primary index
            // would leave a live account invisible to secondary-index scans
            debug_assert!(
                !self.accounts_index.contains(key),
                "key removed from the primary index must not be present: {key}"
            );
            self.accounts_index.purge_secondary_indexes_by_inner_key_if(
                key,
                &self.account_indexes,
                || !self.accounts_cache.contains_pubkey(key),
            );
        }
    }
