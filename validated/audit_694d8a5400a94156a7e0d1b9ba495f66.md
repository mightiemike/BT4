### Title
Rescue outbound trusts attacker-supplied `PRC20` from `RescueFundsOnSourceChain` event without binding it to the original inbound's deposited token - (File: `x/uexecutor/keeper/create_outbound.go`)

### Summary
`AttachRescueOutboundFromReceipt` resolves the `ExternalAssetAddr` for a rescue outbound purely from the `PRC20` field of a `RescueFundsOnSourceChain` event, without ever comparing it to the token that was actually part of the original, stuck inbound.

### Finding Description
`AttachRescueOutboundFromReceipt` runs inside the EVM post-processing hook, which is invoked for every EVM transaction receipt on Push Chain [1](#0-0) . For any log emitted by the `UNIVERSAL_GATEWAY_PC` system contract matching the `RescueFundsOnSourceChain` signature, the keeper decodes the event and extracts `event.PRC20` directly from the caller-controlled log topics [2](#0-1) .

The keeper then looks up the original UTX by `event.UniversalTxId`, checks rescue eligibility (CEA-failed deposit or reverted auto-revert), and checks for duplicate active rescues [3](#0-2) . None of these checks validate that `event.PRC20` corresponds to the PRC20/token that was actually part of the original inbound deposit tied to `originalUtx`. The code then resolves the external asset directly from the attacker-supplied `event.PRC20`: [4](#0-3) 

The resulting outbound carries `ExternalAssetAddr: tokenCfg.Address` (derived from the attacker-chosen `event.PRC20`) but `Amount: originalUtx.InboundTx.Amount` (the amount that was actually deposited/locked using the *original* token). If the source chain has multiple PRC20-registered tokens, a caller can invoke the gateway's rescue path referencing their own stuck `universalTxId` (for token A) while supplying a different, also-registered PRC20 (token B) in the same call, causing the outbound record to instruct release of token B's external asset address for an amount that was never actually escrowed in token B.

### Impact Explanation
Because the outbound record (destination chain, asset address, amount) is the canonical state that honest universal validators subsequently vote on and TSS eventually signs/executes, a mismatched `ExternalAssetAddr`/`Amount` pairing corrupts token mapping and accounting for the source-chain escrow: honest validators would converge on and finalize an outbound event that misroutes value to the wrong external asset, resulting in unauthorized release of a token that was never the one actually locked. This falls under "corruption of PRC20 ... asset accounting ... token mapping" and "unauthorized release ... of user or protocol-controlled funds" in the impact gate.

### Likelihood Explanation
The rescue path is reachable purely through an unprivileged user's own transactions: (1) create a normal inbound deposit that becomes eligible for rescue (CEA failed deposit, or non-CEA with reverted auto-revert), then (2) call the gateway contract's rescue-initiation function on Push Chain, supplying a different, also-registered PRC20 address than the one used in the original deposit. No malicious validator, relayer, or admin involvement is required to reach the vulnerable keeper code — only honest finalization of the (already-corrupted) outbound record. The main caveat is that I could not locate the Solidity source for `UniversalGatewayPC` in this repo to confirm whether the on-chain contract itself constrains the `prc20` parameter passed by the caller (e.g., by deriving it from stored per-UTX state instead of accepting free-form input); that contract logic is outside the indexed scope of the Go repository, so this could be partially mitigated at the Solidity layer, but the Go keeper code reviewed here performs no such validation independently.

### Recommendation
In `AttachRescueOutboundFromReceipt`, validate that `event.PRC20` matches the PRC20/token actually associated with `originalUtx.InboundTx` (e.g., store the deposited PRC20 address on the inbound record and compare it against `event.PRC20` before resolving `tokenCfg`), rejecting the rescue attach if they diverge instead of trusting the event field unconditionally.

### Proof of Concept
1. Attacker submits an inbound deposit using PRC20 token A on source chain `eip155:X`; the deposit fails (CEA) or its auto-revert is later marked `REVERTED` (non-CEA), making the UTX rescue-eligible.
2. Both token A and token B are registered `TokenConfig`s for `eip155:X` (`GetTokenConfigByPRC20` resolves both) [5](#0-4) .
3. Attacker triggers a Push Chain transaction that causes `UniversalGatewayPC` to emit `RescueFundsOnSourceChain(universalTxId=<UTX for token A>, prc20=<token B address>, ...)`.
4. `AttachRescueOutboundFromReceipt` fetches `originalUtx` (token A's UTX), passes eligibility checks, and calls `GetTokenConfigByPRC20(ctx, sourceChain, tokenB)`, attaching an outbound with `ExternalAssetAddr = tokenB.Address` and `Amount = originalUtx.InboundTx.Amount` (token A's amount) [6](#0-5) .
5. No check exists anywhere in the function comparing `event.PRC20` to the token actually used in the original inbound, so this outbound is attached and enters the normal voting/finalization pipeline with mismatched token semantics.
