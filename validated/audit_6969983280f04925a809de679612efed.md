Based on my investigation, I found a genuine analog of the Yieldy bug class (a value is clamped for a limit check, but the original/actual value is then used for the state-mutation accounting that follows), reachable from a transaction/receipt on nearcore.

### Title
Receipt size clamped for admission check but full (unclamped) size decremented from destination shard's bandwidth budget, corrupting `OutgoingLimit.size` accounting - (File: runtime/runtime/src/congestion_control.rs)

### Summary
`ReceiptSinkV2::try_forward` deliberately clamps an oversized receipt's `size` to `max_receipt_size` before comparing it against the destination shard's `forward_limit.size`, as a workaround for issue #12606 (oversized receipts existing due to a prior bug), but the same *clamped* variable is then used to decrement the shard's remaining bandwidth budget, rather than the receipt's true size.

### Finding Description
In `try_forward` (`runtime/runtime/src/congestion_control.rs:403-463`), the mutable local `size` parameter is silently rewritten:

```rust
let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
if size > max_receipt_size {
    ...
    size = max_receipt_size;
}
...
if forward_limit.gas >= admission_gas && forward_limit.size >= size {
    outgoing_receipts.push(receipt);
    forward_limit.gas = forward_limit.gas.saturating_sub(gas);
    forward_limit.size -= size;   // <-- uses the CLAMPED size, not the receipt's real size
    ...
}
``` [1](#0-0) [2](#0-1) 

This is structurally identical to the Yieldy bug: an over-limit quantity (`_profit` / here, receipt `size`) is clamped for the purpose of a bound check, but the *clamped* value rather than the *actual excess-corrected* value is propagated into the downstream accounting state (`_storeRebase(... , _profit)` / here, `forward_limit.size -= size`). In Yieldy the unused excess of `_profit` silently vanished from `rebasePercent`; here, the unused excess of the receipt's real size (`real_size - max_receipt_size`) silently vanishes from the shard's bandwidth-budget bookkeeping — the shard is only charged `max_receipt_size` bytes even though it actually forwards a much larger receipt.

Similarly, `own_congestion_info`/outgoing-buffer bookkeeping in the neighboring `buffer_receipt` path uses the caller-supplied `size`/`gas` which is computed once via `compute_receipt_size`/`compute_receipt_congestion_gas` for the whole flow — the spec confirms this clamping is meant only as "pretend all receipts are at most `max_receipt_size`", i.e., a deliberate divergence between the accounted size and the wire size of what is actually sent [3](#0-2) .

### Impact Explanation
Because `forward_limit.size` is decremented by the clamped (smaller) amount while the *actual*, larger receipt is pushed into `outgoing_receipts`, a single oversized receipt lets the sending shard forward materially more real bytes to the destination shard than the bandwidth scheduler granted it (`OutgoingLimit.size` was supposed to bound bytes sent this height). This under-accounts consumption of the receiver's bandwidth grant, degrading the congestion-control/bandwidth-scheduler backpressure mechanism (NEP-539) that is meant to bound per-shard memory growth from cross-shard receipts. Because this logic runs identically and deterministically on every validating node from the same state (all nodes see the same oversized receipt and the same `max_receipt_size` config), it does not itself cause a state-root divergence between honest nodes — the accounting error is a protocol-consistent under-counting of the bandwidth budget, not a nondeterministic bug. This weakens (but given the deterministic clamp on all nodes, does not fully break) the availability/memory-DoS protection that congestion control provides for oversized receipts specifically flowing from the pre-existing #12606 bug class.

### Likelihood Explanation
Triggering this path requires an existing oversized receipt (`size > max_receipt_size`) to exist in a shard's outgoing buffer in the first place — which the code comment itself says stems from a distinct, already-acknowledged bug (#12606) that allows receipts above the size limit to be created. So while the code path is reachable by any receipt-producing transaction/contract call once an oversized receipt has been created, it is not by itself the primary vulnerability; it is a compensating workaround with a residual accounting flaw. Likelihood of exploitation at scale is Medium: an attacker able to reliably construct receipts exceeding `max_receipt_size` (via the #12606 mechanism) could repeatedly under-report bandwidth consumption to inflate real cross-shard byte throughput beyond the scheduler's intended per-link grant.

### Recommendation
Track and charge the *real* receipt size for `forward_limit.size` (and any other bandwidth-budget bookkeeping) while only using the clamped value for the admission comparison, mirroring the Yieldy fix pattern: perform the bound check with the clamped value, but subtract/account for the true consumed resource (or subtract `forward_limit.size = forward_limit.size.saturating_sub(size)` using the real size and treat any shortfall as fully consuming the remaining budget), so the shard's outgoing bandwidth budget is never under-debited relative to what is actually transmitted.

### Proof of Concept
1. Via the pre-existing #12606 mechanism, an attacker gets a receipt with `receipt.size() > max_receipt_size` (e.g., `2 * max_receipt_size`) buffered for shard `S`.
2. On a subsequent chunk, the bandwidth scheduler grants shard `S` a size budget of, say, `max_receipt_size` bytes for the link from the sender shard (`OutgoingLimit.size = max_receipt_size`).
3. `forward_from_buffer`/`try_forward` is called with the oversized receipt: `size` (real) `= 2 * max_receipt_size` is clamped to `max_receipt_size` at `congestion_control.rs:426`.
4. The check `forward_limit.size >= size` (`max_receipt_size >= max_receipt_size`) passes, and the oversized receipt (its true, unclamped bytes) is pushed to `outgoing_receipts` at `congestion_control.rs:453`.
5. `forward_limit.size -= size` at `congestion_control.rs:455` subtracts only `max_receipt_size`, leaving the shard's remaining budget at `0` — but `2 * max_receipt_size` real bytes were actually sent, i.e., double the granted bandwidth for that link this height, exactly analogous to Yieldy calling `_storeRebase` with the full unclamped `_profit` after the total supply was silently capped.
