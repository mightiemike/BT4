Based on my research, I found a strong analog in nearcore matching the CVE-2024-42117 bug class: a "find index/shard by id" lookup that can fail to find a match, and instead of the caller handling the failure gracefully, the caller `.unwrap()`s the `Result`, causing a panic (the Rust equivalent of hitting an invalid array index / failed ASSERT that continues executing).

### Title
Unhandled `unwrap()` panic on receiver-shard resolution for delayed `GlobalContractDistribution` receipts across multiple reshardings - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`Receipt::receiver_shard_id` can return `Err` when a `GlobalContractDistribution` receipt's `target_shard` no longer exists in the current shard layout and `ShardLayout::resolve_to_current_shard` fails to remap it to a live descendant shard (this can happen once the receipt has survived more than one resharding generation while sitting in the delayed-receipt queue). The runtime's delayed-queue filter, `receipt_filter_fn`, calls `.unwrap()` on this `Result` instead of propagating the error, so hitting this condition panics the node while applying a chunk.

### Finding Description
`Receipt::receiver_shard_id` computes the receiving shard for a receipt. For ordinary action/data receipts it uses `account_id_to_shard_id`, but for `ReceiptEnum::GlobalContractDistribution` it must instead remap a `target_shard`, and falls back to `shard_layout.resolve_to_current_shard(target_shard)` when the target shard is no longer part of the current layout, returning an `EpochError::ShardingError` if that remap fails: [1](#0-0) 

This `Result`-returning function is consumed inside the congestion-control delayed-receipt queue's filter, which discards the `Result` via `.unwrap()`: [2](#0-1) 

`receipt_filter_fn` is invoked from `pop()`, which is on the hot path of draining the shard's delayed-receipt queue during every chunk application: [3](#0-2) 

A dedicated regression test in the repository explicitly documents and probes this exact failure mode — a `GlobalContractDistribution` receipt that is delayed across two resharding events, whose stale `target_shard` cannot be remapped, causing `receiver_shard_id()` to return `Err` and the subsequent `.unwrap()` in `receipt_filter_fn()` to panic: [4](#0-3) 

This mirrors the kernel CVE's bug class precisely: a "find index/shard by id" helper legitimately returns a not-found sentinel (`Err`/`-1`), but the caller does not validate it and instead crashes on an invalid value (`.unwrap()`/using `-1` as an array index).

### Impact Explanation
Any account can trigger a `DeployGlobalContract`-style action that produces a `GlobalContractDistribution` receipt targeted at a specific shard. If that receipt becomes delayed (e.g. due to congestion) and survives across two or more resharding events before being processed, `receiver_shard_id()` fails to resolve it to a live shard and every validator applying that shard's chunk hits the `.unwrap()` panic in `receipt_filter_fn`. Because chunk application is deterministic and mandatory, this is not a crash isolated to a malicious/faulty node — every honest validator attempting to apply that shard's chunk panics, which constitutes a transaction-triggered chain halt for that shard.

### Likelihood Explanation
Triggering the bug requires: (1) an unprivileged account submitting a global-contract deployment transaction whose resulting `GlobalContractDistribution` receipt gets delayed in the target shard's queue, and (2) at least two resharding events occurring before that receipt is processed. This is a multi-step but entirely externally-triggerable scenario (no validator/operator privilege required), and the presence of a purpose-built regression test in the codebase strongly suggests this was identified as a genuine, reachable failure mode tied to the resharding roadmap.

### Recommendation
`receipt_filter_fn` (and any other caller of `receiver_shard_id`) should propagate the `Result` instead of `.unwrap()`ing it, surfacing it through the fallible `pop()`/`RuntimeError` path so an unresolvable receipt is handled as a recoverable error (e.g., logged and retried/dropped through a defined protocol path) rather than causing a process panic. Additionally, `resolve_to_current_shard` should be validated/hardened to correctly walk shard ancestry across an arbitrary number of resharding generations, not just one.

### Proof of Concept
1. Deploy a global contract via `DeployGlobalContract`, producing a `GlobalContractDistribution` receipt targeting shard `S`.
2. Ensure the receipt is delayed in the queue for shard `S` (e.g. via congestion).
3. Trigger two shard-splitting resharding events before the receipt is processed, such that `S` no longer exists in the current shard layout and cannot be resolved via `resolve_to_current_shard`.
4. When the runtime later attempts to drain the delayed queue and calls `receipt_filter_fn` → `receiver_shard_id().unwrap()`, the node panics while applying the chunk, as reproduced by the existing test `test-loop-tests/src/tests/global_contracts_distribution.rs`.
