### Title
Token Exchange session-reuse check omits scope validation, unlike the Auth Code Flow — ([File: packages/apps/shopify-app-express/src/middlewares/perform-token-exchange.ts])

### Summary
This mirrors the GoGoPool `maxDeposit`/`maxMint` vs `maxWithdraw`/`maxRedeem` inconsistency: two sibling code paths implement the "same" ERC4626-style contract (here, "is this stored session still valid enough to reuse"), but only one of them performs the full check. The Auth Code Flow validates session validity with `session.isActive(api.config.scopes)`, explicitly checking that the stored access token still covers the app's configured scopes. The Token Exchange strategy — meant to be functionally equivalent for embedded apps — validates with `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)`, passing `undefined` for scopes and thus skipping scope validation entirely.

### Finding Description
`Session.isActive(scopes, withinMillisecondsOfExpiry)` treats a session as active only if it has an access token, is not expired, and — if `scopes` is provided — the stored `session.scope` still includes the required scopes (via `isScopeChanged`/`isScopeIncluded`): [1](#0-0) 

If `scopes` is `undefined`, `isScopeChanged` unconditionally returns `false`, so scope mismatches are never detected: [2](#0-1) 

The Auth Code Flow middleware correctly passes the app's configured scopes when deciding whether to reuse a stored session, matching the documented behavior that scope changes should force reauthentication: [3](#0-2) 

But the Token Exchange path (used instead of the Auth Code Flow when the `tokenExchange` future flag is enabled for embedded apps) calls `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)`, omitting the scopes argument: [4](#0-3) 

The same pattern (`session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)`) is duplicated in the `shopify-app-remix` and `shopify-app-react-router` `TokenExchangeStrategy`: [5](#0-4) [6](#0-5) 

The dispatcher in `shopify-app-express` explicitly documents that the two flows ("Auth Code Flow" vs "Token Exchange") are meant to be functionally parallel, independent implementations of the same contract: [7](#0-6) 

### Impact Explanation
If a merchant updates the app's requested access scopes (e.g., the developer adds new required scopes and bumps `config.scopes`), the Auth Code Flow correctly detects that a previously stored offline/online session's `scope` no longer satisfies the new required scopes and forces re-authentication via `redirectToAuth`. In the Token Exchange path, the same stale session (with insufficient/outdated scopes) is treated as still "active" and is reused indefinitely (as long as it's not expired), because the scope check is bypassed entirely. This can let a request proceed and hit the Admin/Storefront API with an access token whose granted scopes don't match what the app now requires, meaning the app operates on stale authorization state without prompting merchants to re-consent — a functional deviation from the OAuth/session-validity contract this library is meant to guarantee, directly analogous to the reported "standard broken" ERC4626 inconsistency (Medium severity was assigned in the original report specifically because it broke the standard's contract, even without direct fund loss).

### Likelihood Explanation
Any embedded app using the `tokenExchange` future flag is affected without any special preconditions — this is the default flow for token-exchange-enabled apps. Likelihood of the code path being reached is very high (every authenticated request evaluates this check); the triggering condition (the app's configured scopes changing while an old session persists in storage) is a normal, foreseeable operational event (app updates scope requirements) rather than a rare edge case.

### Recommendation
Update `performTokenExchange` (and the equivalent `TokenExchangeStrategy.authenticate` in `shopify-app-remix` and `shopify-app-react-router`) to pass the configured scopes into `isActive`, consistent with the Auth Code Flow:
```ts
session.isActive(api.config.scopes, WITHIN_MILLISECONDS_OF_EXPIRY)
```
so that scope changes correctly invalidate stale sessions and trigger a fresh token exchange, exactly as they trigger a fresh OAuth redirect in the Auth Code Flow.

### Proof of Concept
1. Configure an app with `future.tokenExchange = true` and initial `scopes = ['read_products']`; a merchant installs and a valid offline session with `scope: 'read_products'` is stored.
2. Developer updates the app config to `scopes = ['read_products', 'write_products']` and redeploys (no forced reinstall).
3. A subsequent authenticated request from the same shop hits `performTokenExchange`; `session.isActive(undefined, WITHIN_MILLISECONDS_OF_EXPIRY)` returns `true` because scopes aren't checked [4](#0-3) , so the stale session (still lacking `write_products`) is reused and `next()` is called without any re-authentication.
4. Compare to the Auth Code Flow: the same scenario there calls `session.isActive(api.config.scopes)` [8](#0-7) , which returns `false` due to `isScopeChanged`, correctly forcing `redirectToAuth`.

  public isActive(
    scopes: AuthScopes | string | string[] | undefined,
    withinMillisecondsOfExpiry = 500,
  ): boolean {
    const hasAccessToken = Boolean(this.accessToken);
    const isTokenNotExpired = !this.isExpired(withinMillisecondsOfExpiry);
    const isScopeChanged = this.isScopeChanged(scopes);
    return !isScopeChanged && hasAccessToken && isTokenNotExpired;
  }

  /**
   * Whether the access token includes the given scopes if they are provided.
   */
  public isScopeChanged(
    scopes: AuthScopes | string | string[] | undefined,
  ): boolean {
    if (typeof scopes === 'undefined') {
      return false;
    }

    return !this.isScopeIncluded(scopes);
  }
