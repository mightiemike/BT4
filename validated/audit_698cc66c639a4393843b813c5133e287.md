### Title
Non-atomic spend/receive settlement in `ShieldedTransferActuator.executeShielded` permanently burns spent notes on merkle-append failure - (File: `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
`executeShielded` writes every spend's nullifier to `nullifierStore` in a first loop, then separately runs `currentMerkle.wfcheck()` and inserts receive commitments (`merkleContainer.saveCmIntoMerkleTree`) in a second loop. If the second phase throws `ZksnarkException` (wrapped into `ContractExeException`), the method aborts without undoing the nullifier writes already committed in the first loop, since there is no local rollback and the store write is direct.

### Finding Description
In `ShieldedTransferActuator.executeShielded`: [1](#0-0) 

The spend loop calls `nullifierStore.put(...)` for every `SpendDescription` unconditionally as long as the nullifier is not already present. Only *after* all spends are persisted does the method call `currentMerkle.wfcheck()` and then loop over receives calling `merkleContainer.saveCmIntoMerkleTree`. Either of these can throw `ZksnarkException` (e.g., tree at `DEPTH=32` capacity or a non-canonical parent hash), which is caught and converted into a `ContractExeException`, aborting `executeShielded` and propagating up through `ShieldedTransferActuator.execute` → the actuator loop in `RuntimeImpl.execute`: [2](#0-1) 

Non-VM actuators (the `default` branch, which includes `ShieldedTransferContract`) are invoked directly with no per-actuator DB session/rollback wrapper — unlike VM contract calls, which are isolated through a dedicated `Repository`/`Program` commit-on-success model. `ActuatorFactory` and `RuntimeImpl` create and run the actuator with no compensating transaction logic: [3](#0-2) 

Since `NullifierStore.put` writes directly into the chain-base store (backed by whatever revoking-store session is currently open for the surrounding block/transaction context, not a per-actuator scope), a mid-`executeShielded` `ContractExeException` does not undo the earlier `nullifierStore.put` calls. `validate()` cannot catch this beforehand because the zk-SNARK proof checks and merkle-root existence checks in `validate()` (checking `merkleRootExist` against the spend's `anchor`) do not simulate the eventual write path of the *new* commitments being appended (`wfcheck`/`append` correctness for the current tree state at execution time), so a legitimately-proof-valid transaction can still fail at the merkle-append step during `execute()`.

### Impact Explanation
An attacker (or even an honest user hitting an edge condition) who submits a transaction with a valid spend but a receive description that causes the merkle tree append/`wfcheck` to fail causes: the spend's nullifier to be permanently recorded as spent (`nullifierStore.has()` true forever), the corresponding note-commitment never inserted into the tree (fund's destination note effectively never created), and the transaction result marked FAILED. This burns the input note's funds with no compensating output — a fund-freezing/loss bug breaking the intended atomicity invariant of one-spend-with-one-receive settlement.

### Likelihood Explanation
Requires an attacker to control a note eligible to spend and to make the shared shielded merkle tree state such that `wfcheck()`/`append()` throws for the receive commitment (e.g., forcing tree exhaustion at `DEPTH=32`, or crafting a non-canonical commitment triggering `ZksnarkException`). This is a naturally-occurring failure mode near tree capacity limits, not requiring any privileged access — any unprivileged broadcaster of a `ShieldedTransferContract` can trigger it once the tree nears capacity, and the described spend/receive ordering guarantees the exposure whenever it happens.

### Recommendation
Make the spend and receive phases atomic within `executeShielded`: perform the merkle `wfcheck()`/append validity checks for all receive commitments (or a dry-run/simulate the entire commitment insertion) before writing any nullifier, or buffer the nullifier writes in memory and only flush to `nullifierStore` after all receive commitments have been successfully appended and `merkleContainer.setCurrentMerkle` has succeeded. Alternatively wrap the whole `executeShielded` body in a dedicated session/checkpoint that is rolled back on any `ContractExeException` before rethrowing.

```java
// framework/src/test/java/org/tron/core/actuator/ShieldedTransferActuatorTest.java
@Test
public void spendNotAtomicWithFailedReceive() throws Exception {
  dbManager.getDynamicPropertiesStore().saveAllowShieldedTransaction(1);
  dbManager.getDynamicPropertiesStore().saveTotalShieldedPoolValue(AMOUNT);

  // 1. Build a valid spend + receive shielded transaction as usual (see shieldAddressToPublic()).
  ZenTransactionBuilder builder = new ZenTransactionBuilder(wallet);
  SpendingKey sk = SpendingKey.random();
  ExpandedSpendingKey expsk = sk.expandedSpendingKey();
  PaymentAddress address = sk.defaultAddress();
  Note note = new Note(address, AMOUNT);
  IncrementalMerkleVoucherContainer voucher = createSimpleMerkleVoucherContainer(note.cm());
  byte[] anchor = voucher.root().getContent().toByteArray();
  dbManager.getMerkleContainer().putMerkleTreeIntoStore(anchor, voucher.getVoucherCapsule().getTree());
  builder.addSpend(expsk, note, anchor, voucher);
  addZeroValueOutputNote(builder); // produces one ReceiveDescription
  TransactionCapsule transactionCap = builder.build();

  Contract contract = transactionCap.getInstance().toBuilder()
      .getRawDataBuilder().getContract(0);
  ShieldedTransferActuator actuator = new ShieldedTransferActuator();
  actuator.setChainBaseManager(dbManager.getChainBaseManager())
      .setContract(contract).setTx(transactionCap);
  TransactionResultCapsule ret = new TransactionResultCapsule();

  // 2. Force the merkle append to fail on the receive side, e.g. by pre-corrupting
  //    the shared "currentMerkle" so wfcheck()/append() throws ZksnarkException
  //    (e.g., fill IncrementalMerkleTreeContainer to DEPTH=32 or inject a
  //    non-canonical parent hash into merkleContainer.getCurrentMerkle()).
  corruptCurrentMerkleToForceAppendFailure(dbManager.getMerkleContainer());

  byte[] nullifier = extractNullifierFromTx(transactionCap);

  actuator.validate(); // passes: proof checks + anchor existence do not detect the corrupted tree state
  try {
    actuator.execute(ret);
    Assert.fail("expected ContractExeException");
  } catch (ContractExeException e) {
    // 3. Assert the bug: nullifier is now permanently marked spent
    Assert.assertTrue(dbManager.getNullifierStore()
        .has(nullifier));
    // 4. Assert the note commitment was never inserted (receiver gets nothing)
    Assert.assertFalse(commitmentPresentInTree(
        dbManager.getMerkleContainer().getCurrentMerkle(), receiveCm));
    // 5. Transaction is FAILED
    Assert.assertEquals(code.FAILED, ret.getInstance().getRet());
  }
}
```
Expected result confirming the bug: `nullifierStore.has(nullifier)` returns `true` and the output commitment is absent from the tree, while `ret` shows `FAILED` — proving the spend was permanently and irreversibly consumed without its paired receive ever landing, with no compensating rollback at `ShieldedTransferActuator`, `TransactionTrace`, or `Manager` level.
