### Title
Method-ID Upgrade Chain ID Collision Between `Nightly` and `TestNetworkWithForks` Networks Enables Cross-Network Replay - (File: crates/light-client-prover/src/circuit/mod.rs)

### Summary
The light client circuit's cross-network replay protection for `BatchProofMethodId` upgrade transactions relies solely on comparing `batch_proof_method_id.body.chain_id` against `citrea_network_to_chain_id(network)`. However, `citrea_network_to_chain_id` assigns the exact same chain ID (5665) to both `Network::Nightly` and `Network::TestNetworkWithForks`, defeating the very check it exists to enforce between these two networks.

### Finding Description
`citrea_network_to_chain_id` is documented as being used "to check the chain id of the method id upgrade transactions and to prevent cross network replay attacks," yet: [1](#0-0) 

returns `5665` for both `Network::Nightly` and `Network::TestNetworkWithForks`. The circuit's enforcement point only checks this numeric equality: [2](#0-1) 

Because the values are equal, a signed `BatchProofMethodIdBody` (containing `method_id`, `activation_l2_height`, `chain_id`) that was authorized (3-of-5 security council signature) for one of these networks is also structurally valid on the other, provided the activation-height monotonicity check also happens to pass. In addition, both networks default to the identical method-id-upgrade-authority public keys, sequencer public key, and prover public key unless overridden at compile time via distinct environment variables: [3](#0-2) [4](#0-3) 

The `BatchProofMethodIdBody` struct's doc comment states the `chain_id` field exists specifically "to prevent cross network replay attacks": [5](#0-4) 

but with a colliding chain ID and (by default) colliding authority keys, this replay protection provides no actual separation between `Nightly` and `TestNetworkWithForks` deployments.

### Impact Explanation
This breaks the binding "an accepted commitment or method-id upgrade versus what the key holder authorised." A method-id upgrade transaction, signed by the security council and inscribed on DA for one network (e.g., `TestNetworkWithForks`), can be replayed and accepted by a light-client-prover circuit instance running `Nightly` (or vice versa), because the chain-id equality check that is supposed to reject it instead passes. This allows an unauthorized method-id upgrade to be applied on a network the signers did not intend to authorize for that specific activation height/method-id, potentially causing that network's honest nodes/provers to diverge from what was actually authorized for it — an unauthorised method-id upgrade per the impact taxonomy.

### Likelihood Explanation
Exploitability depends on whether `Nightly` and `TestNetworkWithForks` circuits/binaries are ever deployed against DA data streams that could physically overlap (e.g., same regtest/bitcoin-testing chain, or an attacker resubmitting an inscription observed on one network's DA to the other network's DA layer). Since these are both described as testing-purpose networks ("used for testing purposes only"), production/mainnet is unaffected, but the mechanism intended to prevent this exact class of replay is nonetheless non-functional between these two identifiers, and the same functions/logic are shared with `Mainnet`/`Testnet`/`Devnet` which do have unique values — so the flaw is isolated to this one colliding pair but is a genuine logic defect in the replay-protection mechanism itself.

### Recommendation
Assign `Network::TestNetworkWithForks` a distinct chain ID from `Network::Nightly` in `citrea_network_to_chain_id`, and ensure their default method-id-upgrade-authority, sequencer, and prover public keys in `initial_values.rs` are also distinct by default (not relying solely on operators setting different environment variables at build time).

### Proof of Concept
1. Security council signs a `BatchProofMethodIdBody { method_id: X, activation_l2_height: H, chain_id: 5665 }` for `TestNetworkWithForks`, using the shared default authority keys, and it is inscribed on that network's DA. [6](#0-5) 
2. An observer copies this exact inscription's payload/signatures to the DA stream that a `Nightly`-configured light-client-prover reads.
3. In `Nightly`'s circuit run, `citrea_network_to_chain_id(Network::Nightly)` returns `5665`, matching `batch_proof_method_id.body.chain_id`, so the check at `mod.rs` lines 544-548 passes; the security council signature check also passes since the default authority keys are identical for both networks.
4. The method ID upgrade, only ever authorized for `TestNetworkWithForks`, is applied on `Nightly` at the specified activation height.

/// These are chain ids for the citrea networks
/// This function is mainly used to check the chain id of the
/// method id upgrade transactions and to prevent cross network replay attacks
/// The method id upgrade identifiers are not strictly tied to chain ids
/// but for simplicity we use the same values
pub fn citrea_network_to_chain_id(network: sov_rollup_interface::Network) -> u64 {
    match network {
        sov_rollup_interface::Network::Mainnet => 4114,
        sov_rollup_interface::Network::Testnet => 5115,
        sov_rollup_interface::Network::Devnet => 62298,
        sov_rollup_interface::Network::Nightly => 5665,
        sov_rollup_interface::Network::TestNetworkWithForks => 5665,
    }
}

pub(crate) fn create_new_method_id_tx(
    activation_height: u64,
    new_method_id: [u32; 8],
    pub_key: [u8; 32],
    network: Network,
) -> MockBlob {
    let pk_bytes_arr: [[u8; 32]; 5] =
        TEST_PRIVATE_KEYS.map(|s| hex::decode(s).unwrap().try_into().unwrap());

    let msg = borsh::to_vec(&BatchProofMethodIdBody {
        activation_l2_height: activation_height,
        method_id: new_method_id,
        chain_id: citrea_network_to_chain_id(network),
    })
    .unwrap();

    let (_initial_pubkeys, signers) = generate_initial_pub_keys_with_signers_from_pks(pk_bytes_arr);
    let prehash = eip191_hash_message(&msg);
    let signatures_with_index = create_valid_signatures(&signers, &prehash);

    let da_data = DataOnDa::BatchProofMethodId(BatchProofMethodId {
        body: BatchProofMethodIdBody {
            method_id: new_method_id,
            activation_l2_height: activation_height,
            chain_id: citrea_network_to_chain_id(network),
        },
        signatures_with_index,
    });

    let da_data_ser = borsh::to_vec(&da_data).expect("should serialize");

    let blob = MockBlob::new(da_data_ser, MockAddress::new(pub_key), [0u8; 32], [42; 32]);
    blob.full_data();

    blob
}
