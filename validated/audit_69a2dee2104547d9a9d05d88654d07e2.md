### Title
Bouncer-update error other than `BlockFull` causes an unconditional panic in concurrent commit path, allowing a single transaction to crash the block-building worker - ([File: crates/blockifier/src/concurrency/worker_logic.rs])

### Summary
`Bouncer::try_update` propagates `TransactionExecutorError::TransactionExecutionError`/`StateError` variants (via `get_tx_weights`, e.g. through `map_class_hash_to_casm_hash_computation_resources` calling `state_reader.get_compiled_class`, or `CasmHashMigrationData::from_state`) whenever a class hash's compiled class cannot be fetched, not just `BlockFull`. In the concurrent execution commit path, any such non-`BlockFull` error is turned into an unconditional Rust `panic!`, unlike the sequential path (`TransactionExecutor::execute` / `execute_txs_sequentially_inner`), which simply propagates the error as a `Result`.

### Finding Description
`Bouncer::try_update` in `crates/blockifier/src/bouncer.rs:627-695` calls `get_tx_weights(...)?` at line 660, and this function itself can fail with a `TransactionExecutionResult` error (wrapping `StateError`, e.g. class/compiled-class not found) sourced from `map_class_hash_to_casm_hash_computation_resources` (`crates/blockifier/src/bouncer.rs:1029-1040`) and `CasmHashMigrationData::from_state` (`crates/blockifier/src/bouncer.rs:377-400`). Only the block-capacity check (line 671-690) returns `TransactionExecutorError::BlockFull`; any state-lookup failure surfaces as a *different* `TransactionExecutorError` variant.

In `crates/blockifier/src/concurrency/worker_logic.rs:347-365` (`commit_tx`), the bouncer result is matched:
```rust
if let Err(error) = bouncer_result {
    match error {
        TransactionExecutorError::BlockFull => return Ok(CommitResult::NoRoomInBlock),
        _ => {
            // TODO(Avi, 01/07/2024): Consider propagating the error.
            panic!("Bouncer update failed. {error:?}: {error}");
        }
    }
}
```
Any bouncer error other than `BlockFull` unconditionally panics the worker thread performing concurrent commit, instead of gracefully rejecting only the offending transaction. This is directly analogous to the PoolTogether `Claimer._claim` bug class: a loop that processes multiple independent units of work (transactions here, prize claims there) fails to safely contain a failure from a single item, causing the entire batch/loop to abort/crash instead of skipping just the bad item.

By contrast, the non-concurrent commit path (`TransactionExecutor::execute`, `crates/blockifier/src/blockifier/transaction_executor.rs:148-182`) simply returns the `TransactionExecutorError` via `?` without panicking — showing the concurrent path's panic branch is an inconsistency/gap in error handling rather than an intended invariant.

### Impact Explanation
If an unprivileged transaction sender can cause `get_tx_weights` to return a non-`BlockFull` error for their own (or an interleaved) transaction during concurrent block building — e.g., by referencing a class hash whose compiled class becomes unavailable to the state reader at bouncer-update time (a state/class-manager lookup failure), or via a race/edge-case interaction with `CasmHashMigrationData::from_state`'s class lookups — the worker thread executing `commit_tx` panics. Depending on how panics propagate in the sequencer's async/thread pool machinery, this can abort in-flight block building, crash the batcher process, or otherwise render the sequencer unable to produce/commit further blocks in that concurrent-execution round — a denial-of-service against block production reachable from a single submitted transaction.

### Likelihood Explanation
Reaching this precisely requires triggering a `StateError` (not the normal `BlockFull`/execution-revert path) at the specific point `try_update` computes casm-hash-computation and migration resources for executed class hashes, during concurrent (multi-worker) execution. This depends on the class-manager/state-reader's exact failure modes for `get_compiled_class` on a class hash that was successfully executed moments earlier (so under normal correct operation this should not occur), making the concrete trigger uncertain from static review alone — I could not fully verify a concrete, reliable transaction shape that forces `get_compiled_class` to fail after successful execution without deeper knowledge of the class-manager/state-reader implementation and the concurrent scheduler's state-visibility guarantees.

### Recommendation
In `crates/blockifier/src/concurrency/worker_logic.rs::commit_tx`, do not `panic!` on non-`BlockFull` bouncer errors. Instead, propagate the error as a `Result` (as already done in the sequential `TransactionExecutor::execute` path) so that the caller can reject just the offending transaction (mark it rejected/re-execute later) rather than crashing the worker/thread that is processing potentially many unrelated transactions concurrently.

### Proof of Concept
Not independently reproduced; the analysis is based on static code review of `crates/blockifier/src/bouncer.rs` and `crates/blockifier/src/concurrency/worker_logic.rs`. Confirming exploitability requires demonstrating a concrete transaction/class-hash scenario in which `state_reader.get_compiled_class` (called from `map_class_hash_to_casm_hash_computation_resources` or `CasmHashMigrationData::from_state`) fails for a class hash that was just executed successfully during concurrent block building, which was not verified within the scope of this review.
