### Title
Shadow-block signature bypass is gated only by an attacker-settable header bit, not by trusted provenance - ([File: stackslib/src/chainstate/nakamoto/mod.rs], [File: stackslib/src/chainstate/nakamoto/shadow.rs])

### Summary
`NakamotoBlockHeader::verify_signer_signatures` and `NakamotoBlock::check_miner_signature` both short-circuit real cryptographic verification whenever `self.is_shadow_block()` is true. That predicate is nothing more than a single bit check on the attacker-supplied `version` byte of the block header, exactly analogous to the OAuth2 Proxy bug where a cheap, spoofable marker (`User-Agent`) caused the checker to declare success without validating the actual protected request.

### Finding Description
`is_shadow_block()` is defined as: [1](#0-0) 
i.e. `version & 0x80 != 0`. The `version` field is part of the block header that any block producer constructs and controls.

This flag is then used to bypass two independent security-critical checks:

1. Signer-weight verification — instead of tallying real signatures against the 70% threshold, the function returns the full reward-set weight as if every signer had signed, without inspecting `signer_signature` at all: [2](#0-1) 

2. Miner-signature verification — the miner signature check is skipped entirely: [3](#0-2) 

The design intent (per comments) is that shadow blocks are only ever inserted directly into chainstate by an out-of-band, consensus-rule-driven SIP process, and are "not downloaded or broadcast": [4](#0-3) 

However, the trust boundary that is supposed to enforce "only locally/administratively inserted blocks may set this bit" is not present in the predicate itself — `is_shadow_block()` is a pure, stateless function of attacker-controlled bytes. The staging database does track an `obtain_method` column that can distinguish `NakamotoBlockObtainMethod::Shadow` from normally downloaded/relayed blocks: [5](#0-4) 
but `verify_signer_signatures` and `check_miner_signature` — which are the actual consensus-critical equality checks (signed weight ≥ threshold, and recovered pubkey == expected miner) — never consult that provenance information. They rely solely on the self-reported version bit.

### Impact Explanation
If any code path that validates a network-supplied or miner-proposed block (rather than an admin-driven shadow-block insertion path) ends up calling `verify_signer_signatures`/`check_miner_signature` on a header where the submitter simply set `version |= 0x80`, the equality "committed signer weight equals the real threshold-weight of collected signatures" is broken: a block with zero or invalid signer signatures would be reported as fully signed, and a block with no valid miner signature would pass miner-signature verification. This is the same bug class as the advisory: a single spoofable marker causes a validation function to report unconditional success regardless of the actual protected content, which — if reachable from untrusted input — is a critical, minority-triggerable authentication/consensus-equality bypass (invalid block accepted).

### Likelihood Explanation
The predicate itself is trivially triggerable by any block producer (single bit flip), which matches the "minority-triggerable, unprivileged" requirement. What I could **not** fully confirm within the available search budget is whether the standard p2p block-acceptance pipeline (e.g., `stackslib/src/net/relay.rs`, `stackslib/src/net/api/postblock_v3.rs`, `stackslib/src/net/api/postblock_proposal.rs` — all of which reference `is_shadow_block`) contains an additional gate that rejects any externally-downloaded/relayed/proposed block whose header has the shadow bit set *before* these functions are invoked. If such a gate exists and is correctly enforced everywhere `verify_signer_signatures`/`check_miner_signature` can be reached with untrusted data, this reduces to a defense-in-depth concern rather than an exploitable bypass. I was unable to inspect the full contents of those three files within the iteration limit to make a final determination either way.

### Recommendation
- Ensure every call site that validates a block originating from the network (relay, block-proposal endpoint, `postblock_v3`) explicitly rejects any header with the shadow-version bit set unless the block's provenance is independently verified as `NakamotoBlockObtainMethod::Shadow` from the local staging DB (i.e., locally/administratively inserted), before `verify_signer_signatures` or `check_miner_signature` are ever invoked.
- Consider having `verify_signer_signatures`/`check_miner_signature` take an explicit "trusted provenance" parameter rather than trusting `is_shadow_block()` alone, so the bypass cannot be reached purely via attacker-controlled header bytes.

### Proof of Concept
Not independently confirmed end-to-end due to inability to inspect the full network validation call chain (`net/relay.rs`, `postblock_v3.rs`, `postblock_proposal.rs`) in this session. Conceptually: craft a `NakamotoBlock` with `header.version |= 0x80`, an empty or garbage `signer_signature` vector, and no valid miner signature; submit it through whichever path (if any) calls `verify_signer_signatures`/`check_miner_signature` on untrusted, network-received blocks without first checking `obtain_method` — this would cause the block to be treated as fully signed and correctly miner-signed.

**Caveat:** Given the uncertainty about whether the network-facing entry points properly gate this bypass, treat this as a **finding requiring verification of the full call graph** (`net/relay.rs`, `postblock_v3.rs`, `postblock_proposal.rs`) rather than a fully proven end-to-end exploit.
