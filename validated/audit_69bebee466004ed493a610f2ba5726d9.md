### Title
Unbounded single RPC account scan can indefinitely stall `AccountsDb::clean_accounts`/shrink, causing disproportionate storage and CPU growth - ([File: accounts-db/src/accounts_scan.rs])

### Summary
`Bank::get_program_accounts` and related RPC-reachable account-scan paths call `AccountsDb::scan_accounts`, which registers a `ScanGuard` that pins the scan's `max_root` into `ScanTracker::ongoing_scan_roots` for the entire duration of the scan callback. Because `max_clean_root()` clamps every subsequent `clean_accounts()`/cache-flush-with-clean call to the *minimum* ongoing scan root, a single unprivileged RPC client that keeps one scan alive (e.g., by slowly consuming a large `getProgramAccounts` response, or by returning slowly from within the per-account callback) can block `clean_accounts` and shrink from making forward progress for as long as the scan is held open — with no upper bound enforced by the scan-tracking mechanism itself.

### Finding Description
`scan_accounts()` opens a `ScanGuard::try_new()` which locks in the scan's `max_root` and increments its count in `ongoing_scan_roots` for the lifetime of the guard (i.e., for the whole scan call): [1](#0-0) [2](#0-1) 

The tracker only exposes `min_ongoing_scan_root()`, which returns the smallest pinned root across *all* currently active scans: [3](#0-2) 

`AccountsDb::max_clean_root()` clamps any proposed clean root down to this minimum ongoing scan root whenever one exists: [4](#0-3) 

Both the periodic cache-flush-with-clean path and `clean_accounts()` itself apply this clamp: [5](#0-4) [6](#0-5) 

The code comments explicitly acknowledge the tradeoff but do not bound it: "If there is a long running scan going on, this could prevent any cleaning based on updates from slots > `max_clean_root`." There is no timeout, deadline, or forced-abort mechanism tied to scan duration in `ScanGuard`/`ScanTracker` — the only termination path is the scan's own natural completion or the bank being dropped/`ScanError::SlotRemoved`. `max_distance_to_min_scan_slot` is tracked only as a metric (`fetch_max`), not enforced as a limit: [7](#0-6) 

This mirrors the report's second-impact bug class: an unprivileged actor (here, any RPC client, not a validator/operator) can trigger a state-freezing operation (a scan) whose duration is entirely attacker-controlled, and that state freeze silently degrades a background invariant (clean/shrink progress) elsewhere in the system, producing effects disproportionate to the cost of triggering it (one RPC call vs. unbounded accumulation of dirty/uncleaned storage on the node).

### Impact Explanation
While a scan is pinned, `clean_accounts()` cannot reclaim any account versions from slots newer than the pinned scan root, and shrink candidates tied to those slots cannot be shrunk either (shrink depends on clean having marked dead/duplicate data). If an attacker (or even an unintentionally slow/misbehaving client) keeps a scan open for an extended period — by opening a `getProgramAccounts`-style call and reading the streamed response slowly, or by using a query that causes the per-account scan callback to run slowly — the node's `AccountsDb` storage will keep accumulating duplicate/dead account versions across all newly rooted slots during that window, since the newest roots cannot be cleaned. This is disproportionate storage and CPU cost: one long-held RPC connection can suppress cleanup across the whole validator for an arbitrary duration, growing disk usage and later spiking CPU/I/O when the backlog is finally released and clean must process a large `min_dirty_slot` range at once.

### Likelihood Explanation
Likelihood is limited by two factors: (1) whether the RPC surface enforces any timeout on scan-based calls (this could mitigate but was not confirmed within available context — I did not fully trace whether `rpc/src/rpc.rs`'s `get_program_accounts` enforces a hard scan deadline distinct from HTTP-level timeouts), and (2) whether a client can practically stall the scan for a meaningfully long time (e.g., via slow TCP consumption of a large account set, or a costly account filter causing a slow per-account callback). Given the mechanism has no scan-duration cap in `ScanGuard`/`ScanTracker` itself, any external timeout would have to come from the RPC transport layer, which is outside `accounts-db`. This makes the likelihood plausible for a network-facing RPC node under attacker control of the client connection, but I could not fully verify from the indexed code whether an independent RPC-level timeout already mitigates this in practice.

### Recommendation
- Enforce a maximum scan duration/deadline in `ScanGuard`, after which the scan is force-aborted (using the existing `ScanConfig::abort()` mechanism) rather than allowed to hold `ongoing_scan_roots` indefinitely.
- Alternatively/additionally, bound the divergence between the min ongoing scan root and the current max root (the metric already tracked via `max_distance_to_min_scan_slot`) and abort/reject scans that exceed a configurable threshold, so that `clean_accounts` can never be blocked for more than a bounded number of slots/time.
- Ensure RPC-facing account-scan endpoints apply their own hard per-request timeout that is enforced independently of client read speed, and confirm this timeout maps to aborting the underlying `scan_accounts` call (via `ScanConfig::abort`) promptly.

### Proof of Concept
Conceptual (cannot be fully executed without a live RPC/validator harness, but the code path is deterministic):
1. Populate a program's accounts so that `get_program_accounts` scan against that program ID is large/slow, or hold the RPC HTTP response open by reading it slowly from the client side.
2. This triggers `Bank`/`AccountsDb::scan_accounts()` → `ScanGuard::try_new()`, which pins the current `max_root` in `ScanTracker::ongoing_scan_roots` for as long as the scan callback/response consumption takes.
3. Concurrently, keep submitting normal transactions/rooting new slots on the validator.
4. Observe that `AccountsBackgroundService`'s periodic `clean_accounts`/`flush_rooted_accounts_cache_with_clean` (via `max_clean_root()`) cannot advance past the pinned scan root (as demonstrated by the existing unit test `test_scan_flush_accounts_cache_then_clean_drop`, which shows clean/flush being held back by an active scan): [8](#0-7) 
5. Storage/dirty-slot backlog on the node grows for the duration the attacker keeps the scan/connection open, which is entirely attacker-controlled and unbounded by any internal timeout in `ScanGuard`/`ScanTracker`.

        }

impl<'a> ScanGuard<'a> {
    /// Begin a scan: checks the bank hasn't been removed and pins `max_root` in
    /// `ongoing_scan_roots`.
    ///
    /// Returns `None` if the bank has already been removed.
    ///
    /// `max_root_inclusive_fn` is called while holding the `ongoing_scan_roots` write lock.
    pub(crate) fn try_new(
        scan_tracker: &'a ScanTracker,
        scan_bank_id: BankId,
        max_root_inclusive_fn: impl FnOnce() -> Slot,
    ) -> Option<Self> {
        {
            let locked_removed_bank_ids = scan_tracker.removed_bank_ids.lock().unwrap();
            if locked_removed_bank_ids.contains(&scan_bank_id) {
                return None;
            }
        }

        let max_root_inclusive = {
            let mut w_ongoing_scan_roots = scan_tracker
                // This lock is also grabbed by clean_accounts(), so clean
                // has at most cleaned up to the current `max_root` (since
                // clean only happens *after* BankForks::set_root() which sets
                // the `max_root`)
                .ongoing_scan_roots
                .write()
                .unwrap();
            // `max_root()` grabs a lock while
            // the `ongoing_scan_roots` lock is held,
            // make sure inverse doesn't happen to avoid
            // deadlock
            let max_root_inclusive = max_root_inclusive_fn();
            if let Some(min_ongoing_scan_root) =
                ScanTracker::min_ongoing_scan_root_from_btree(&w_ongoing_scan_roots)
                && min_ongoing_scan_root < max_root_inclusive
            {
                let current = max_root_inclusive - min_ongoing_scan_root;
                scan_tracker
                    .max_distance_to_min_scan_slot
                    .fetch_max(current, Ordering::Relaxed);
            }
            *w_ongoing_scan_roots.entry(max_root_inclusive).or_default() += 1;
            max_root_inclusive
        };

        scan_tracker.active_scans.fetch_add(1, Ordering::Relaxed);
        Some(Self {
            scan_tracker,
            max_root: max_root_inclusive,
            scan_bank_id,
        })
    }

#[test]
fn test_scan_flush_accounts_cache_then_clean_drop() {
    let db = Arc::new(AccountsDb::new_for_tests_with_config(
        Vec::new(),
        DEFAULT_ACCOUNTS_DB_CONFIG,
    ));
    let account_key = Pubkey::new_unique();
    let account_key2 = Pubkey::new_unique();
    let slot0_account = AccountSharedData::new(1, 0, AccountSharedData::default().owner());
    let slot1_account = AccountSharedData::new(2, 1, AccountSharedData::default().owner());
    let slot2_account = AccountSharedData::new(3, 1, AccountSharedData::default().owner());

    /*
        Store account into slots 0, 1, 2 where
        root slots are 0, 2, and slot 1 is unrooted.
                                0 (root)
                            /        \
                          1            2 (root)
    */
    db.store_for_tests((0, &[(&account_key, &slot0_account)][..]));
    db.store_for_tests((1, &[(&account_key, &slot1_account)][..]));
    // Fodder for the scan so that the lock on `account_key` is not held
    db.store_for_tests((1, &[(&account_key2, &slot1_account)][..]));
    db.store_for_tests((2, &[(&account_key, &slot2_account)][..]));

    let max_scan_root = 0;
    db.add_root(max_scan_root);
    let scan_ancestors: Arc<Ancestors> = Arc::new(Ancestors::from(vec![0, 1]));
    let bank_id = 0;
    let scan_tracker = setup_scan(db.clone(), scan_ancestors.clone(), bank_id, account_key2);

    // Add a new root 2
    let new_root = 2;
    db.add_root(new_root);

    // Check that the scan is properly set up
    assert_eq!(
        db.scan_tracker.min_ongoing_scan_root().unwrap(),
        max_scan_root
    );

    // If we specify a requested_flush_root == 2, then `slot 2 <= max_flush_slot` will
    // be flushed even though `slot 2 > max_scan_root`. The unrooted slot 1 should
    // remain in the cache
    db.flush_accounts_cache(true, Some(new_root));
    assert_eq!(db.accounts_cache.num_slots(), 1);
    assert!(db.accounts_cache.slot_cache(1).is_some());

    // Intra cache cleaning should not clean the entry for `account_key` from slot 0,
    // even though it was updated in slot `2` because of the ongoing scan
    let account = db
        .get_account_at_slot(&account_key, 0)
        .expect("account should exist");
    assert_eq!(account.lamports(), slot0_account.lamports());

    // Run clean, unrooted slot 1 should not be purged, and still readable from the cache,
    // because we're still doing a scan on it.
    db.clean_accounts_for_tests();
    let account = db
        .get_account_at_slot(&account_key, 1)
        .expect("account should exist");
    assert_eq!(account.lamports(), slot1_account.lamports());

    // When the scan is over, clean should not panic and should not purge something
    // still in the cache.
    scan_tracker.exit().unwrap();
    db.clean_accounts_for_tests();
    let account = db
        .get_account_at_slot(&account_key, 1)
        .expect("account should exist");
    assert_eq!(account.lamports(), slot1_account.lamports());
