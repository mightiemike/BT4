### Title
Batch proof method-id selected by `last_l2_height` instead of range start lets an honest proof spanning a method-id activation boundary be rejected with the wrong circuit id - (File: crates/light-client-prover/src/circuit/mod.rs)

### Summary
The light client circuit picks which registered "batch proof method id" to use when verifying a submitted batch proof by binary-searching the activation-height table with the proof's **last** L2 height, while the batch prover partitions commitments into a single proof/circuit run without any awareness of the light client's independently-tracked method-id activation heights. If a method-id activation height falls strictly inside the L2-height range covered by an in-flight (already-generated) batch proof, the light client will select the *new* method id to verify a proof that was actually produced with the *old* one, causing verification to fail for an otherwise valid proof.

### Finding Description
`BatchProofMethodIdAccessor` stores a list of `(activation_l2_height, method_id)` pairs, updated only by authorized `BatchProofMethodId` DA transactions [1](#0-0) .

When the light client circuit processes a complete batch proof, it selects the method id to verify against using the proof's **last** L2 height only: [2](#0-1)

    {
        Ok(idx) => idx,
        Err(idx) => idx.saturating_sub(1),
    };
    batch_proof_method_ids[idx].1

This mirrors the `RewardThrottle.populateFromPreviousThrottle()` bug class: a single boundary value (the proof's *end* height) is used to select a value from a table that actually needs to be validated against the *whole range* the artifact commits to, without checking that the range doesn't straddle a table transition (the analogous `epoch - _activeEpoch > smoothingPeriod` check that malt was missing).

On the prover side, `partition_commitments()` in `crates/batch-prover/src/prover.rs` only splits a batch-proof partition on commitment index gaps, STF spec/fork changes (`PartitionReason::SpecChange`, driven by `fork_from_block_number`), commitment count limits, and state-diff size — never on the light client's `BatchProofMethodId` activation heights, because the batch prover has no access to that JMT-resident table at all: [3](#0-2) 

Consequently, a single batch proof (produced by one guest binary/circuit, i.e. one true method id) can legitimately cover an L2-height range `[start, end]` where a `BatchProofMethodId` activation height `A` satisfies `start <= A <= end`. The proof was generated with the method id that was current at generation time (correct for the range as a whole, since the prover always uses a single, fixed circuit), but the light client's lookup keys off `end` (`batch_proof_output_last_l2_height`), which is `>= A`, so it selects the *new* method id from the table to call `Z::verify`, even though the artifact was produced with the previous circuit.

### Impact Explanation
`Z::verify(proof, &batch_proof_method_id.into(), ...)` will fail because the cryptographic verification key/method id no longer matches the guest binary that actually generated the proof. The `process_complete_proof` function returns `Err(...)` and the batch proof is silently skipped (only logged) [4](#0-3) . Because the underlying sequencer commitments and their L2-height boundaries are already fixed and immutable in the JMT state, and the batch prover has no mechanism to re-partition or re-derive a compliant proof for that exact range once it straddles the activation boundary, this true, valid state transition can become permanently unprovable to the light client — directly matching the explicitly in-scope Critical impact "a true state transition proved... made unprovable." Since the light client proof is the input trusted by Clementine's bridge proof, this can stall L2-state attestation used for withdrawal validation.

### Likelihood Explanation
This does not require any attacker-controlled malicious input or privileged role compromise to trigger — it is a natural consequence of the documented, authorized method-id upgrade workflow interacting with normal batch-proof partitioning timing. Any legitimate `BatchProofMethodId` upgrade transaction whose `activation_l2_height` lands inside the range of a batch proof that is already being generated (or was generated just prior to the DA transaction being observed) will trigger the mismatch. Given batch proof generation and partitioning can take a long time relative to L1 block times, and partitions can span many L2 blocks, the window in which an activation height can land inside an in-flight proof's range is non-trivial.

### Recommendation
Select (and validate) the method id using the **first** L2 height of the batch proof's range (or equivalently, assert that no activation height in the table falls strictly between `start` and `end`), matching the actual circuit used to generate the whole proof. Additionally, expose the light client's `BatchProofMethodId` activation-height schedule to the batch prover so `partition_commitments` can force a partition boundary at any upcoming/known activation height, guaranteeing no single proof ever straddles an activation boundary — analogous to how `PartitionReason::SpecChange` already prevents partitions from spanning STF fork boundaries.

### Proof of Concept
1. Batch prover begins generating a batch proof for sequencer commitments covering L2 heights `[100, 200]`, using method id `M_old` (the only circuit binary it has).
2. While this proof is being generated, the security council submits a `BatchProofMethodId` DA transaction activating `M_new` at `activation_l2_height = 150` (a legitimate operational upgrade, unrelated to this specific in-flight proof).
3. The light client prover processes this method-id transaction first (or in an earlier/same DA block), updating `BatchProofMethodIdAccessor` to `[(0, M_old), (150, M_new)]` via the code path at [5](#0-4) .
4. The batch prover finishes and submits its proof for `[100, 200]`, generated entirely with `M_old`. Its output's `last_l2_height` is `200`.
5. When the light client circuit processes this proof, `binary_search_by_key(&200, ...)` on `[(0, M_old), (150, M_new)]` selects `M_new` (index 1), not `M_old`.
6. `Z::verify(proof, &M_new, ...)` fails even though the proof is a genuine, correctly-computed state transition proved with `M_old`. The proof is discarded via the `Err` branch in `run_l1_block`, and this exact L2 range can never be verified by any future light client proof since the sequencer commitments are already fixed.

/// Accessor for managing batch proof method ids
///
/// This accessor handles storage and retrieval of batch proof method ids that are
/// activated at different L2 block heights, allowing for upgrades to the proving system.
/// It is a wrapper around working set where key is the prefix
/// and the value is a borsh serialized vector of activation height to method id
pub struct BatchProofMethodIdAccessor<S: Storage> {
    /// Phantom data to make the accessor generic over the storage type
    phantom: core::marker::PhantomData<S>,
}

impl<S: Storage> BatchProofMethodIdAccessor<S> {
    /// Batch proof method ids storage prefix
    const PREFIX: u8 = b'm';

    /// Creates a storage key containing just the prefix
    /// # Returns
    /// A storage key for accessing batch proof method ids
    fn key() -> StorageKey {
        // use `StorageKey::singleton_owned` as a hack to create no serialization key
        let mut key = [0u8; 1]; // 1 prefix

        key[0] = Self::PREFIX;

        let p = Prefix::from_slice(&key);
        StorageKey::singleton_owned(p)
    }

    /// Retrieves the batch proof method ids if they exist
    ///
    /// # Arguments
    /// * `working_set` - Mutable reference to the working set for storage access
    ///
    /// # Returns
    /// The batch proof method IDs if they exist, `None` otherwise
    pub fn get(working_set: &mut WorkingSet<S>) -> Option<BatchProofMethodIds> {
        let key = Self::key();

        working_set.get(&key).map(|v| {
            let bytes: RefCount<[u8]> = v.into();
            borsh::from_slice(&bytes)
                .expect("Batch proof method ids deserialization should not fail")
        })
    }

    /// Inserts a new batch proof method id into the LCP state
    ///
    /// # Arguments
    /// * `activation_l2_height` - The L2 block height at which the method id is activated
    /// * `method_id` - The method id to store
    /// * `working_set` - Mutable reference to the working set for storage access
    pub fn insert(activation_l2_height: u64, method_id: [u32; 8], working_set: &mut WorkingSet<S>) {
        let key = Self::key();
        let mut method_ids = Self::get(working_set).unwrap_or_default();
        method_ids.push((activation_l2_height, method_id));
        let value: StorageValue = borsh::to_vec(&method_ids)
            .expect("Batch proof method ids serialization should not fail")
            .into();
        working_set.set(&key, value);
    }

    /// Partition the commitments into provable chunks.
    /// If partition Mode is OneByOne, each commitment is treated as a separate partition.
    ///
    /// If PartitionMode is Normal:
    /// If there is only one commitment, it will be treated as a single partition.
    /// If there are more than one commitment, the commitments are iterated and following conditions are checked at each iteration:
    /// 0. The state diff is increased at each iteration with the current commitment state diff and reset after each partition to the current commitments state diff.
    /// 1. If other than the first commitment, the index of the current commitment and the previous commitment index is checked,
    ///    if they are not consecutive, a partition is formed with the IndexGap PartitionReason.
    /// 2. If the previous commitment l2 end block number and the current commitment l2 end block number are from different forks,
    ///    a partition is formed with the SpecChange PartitionReason.
    /// 3. If serialized and then compressed cumulative state diff of the (current commitment included) partition exceeds the MAX_TX_BODY_SIZE,
    ///    a partition is formed with the StateDiff PartitionReason.
    /// 4. If there is a remaining commitment after the loop, it is added as a last partition with the Finish PartitionReason.
    ///
    /// # Gotchas:
    /// This function expects contiguous known commitments, so, ensure filtering commitments
    /// with `filter_commitments_with_index_gaps` before calling this function.
    ///
    /// # Arguments
    /// * `commitments` - A slice of sequencer commitments to partition
    /// * `mode` - The partition mode to use for partitioning the commitments
    /// * `max_commitments_per_proof` - Optional maximum number of commitments per proof partition
    fn partition_commitments<'a>(
        &self,
        commitments: &'a [SequencerCommitment],
        mode: PartitionMode,
    ) -> anyhow::Result<Vec<Partition<'a>>> {
        let mut state = PartitionState::new(commitments, self.ledger_db.clone())?;

        if mode == PartitionMode::OneByOne {
            for i in 0..commitments.len() {
                state.add_partition(i, PartitionReason::OneByOne)?;
            }
            return Ok(state.into_inner());
        }

        // Normal partition mode

        let mut cumulative_state_diff = StateDiff::new();
        let mut commitment_start_height = state.next_partition_start_height();
        let mut commitments_in_current_partition = 0usize;

        for (i, commitment) in commitments.iter().enumerate() {
            let commitment_end_height = commitment.l2_end_block_number;

            let commitment_state_diff =
                self.get_state_diff(commitment_start_height, commitment_end_height)?;

            commitment_start_height = commitment_end_height + 1;

            // if first commitment, no need to check any condition
            if i == 0 {
                cumulative_state_diff = commitment_state_diff;
                commitments_in_current_partition = 1;
                continue;
            }

            assert_eq!(
                commitment.index,
                commitments[i - 1].index + 1,
                "Commitments with index gap must be filtered before calling partition"
            );

            // check commitment count limit, before adding the current commitment.
            if let Some(max_count) = self.prover_config.max_commitments_per_proof {
                if commitments_in_current_partition >= max_count {
                    cumulative_state_diff = commitment_state_diff;
                    state.add_partition(i - 1, PartitionReason::CommitmentCount)?;
                    commitments_in_current_partition = 1;
                    continue;
                }
            }

            // check spec change
            let current_spec = fork_from_block_number(commitment_end_height);
            if current_spec != fork_from_block_number(commitments[i - 1].l2_end_block_number) {
                cumulative_state_diff = commitment_state_diff;
                state.add_partition(i - 1, PartitionReason::SpecChange)?;
                commitments_in_current_partition = 1;
                continue;
            }
