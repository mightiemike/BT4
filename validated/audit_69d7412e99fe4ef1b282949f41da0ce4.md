## Title
Backup restore accepts unverified `LedgerInfoWithSignatures` as trusted when its epoch exceeds the loaded epoch history, letting untrusted backup storage inject a state/transaction root without signature verification - (File: `storage/backup/backup-cli/src/backup_types/epoch_ending/restore.rs`)

### Summary
`EpochHistory::verify_ledger_info` is the only gate that cryptographically ties a `LedgerInfoWithSignatures` embedded in a backup chunk to a trusted validator set during restore. When the ledger info's epoch is beyond what `EpochHistory.epoch_endings` currently covers, the function does not verify anything — it logs a warning and returns `Ok(())`, treating the ledger info as valid. Both the transaction-chunk restore path and the state-snapshot restore path rely on this "verified" ledger info to accept the accumulator/state root used to validate the actual payload, so an attacker-controlled backup store can supply a forged `LedgerInfoWithSignatures` (with unchecked/garbage signatures) whose embedded root hash is used to accept arbitrary transaction or state data as if it were authenticated.

### Finding Description
`EpochHistory::verify_ledger_info` is defined as: [1](#0-0) 

Specifically, the early-return branch:
```rust
if epoch > self.epoch_endings.len() as u64 {
    // TODO(aldenhu): fix this from upper level
    warn!(...);
    return Ok(());
}
```
returns success without checking the `LedgerInfoWithSignatures`'s aggregate signature against any validator set. This is the sole authentication step used by two restore call sites:

1. `TransactionRestoreController`'s chunk loader calls it before trusting the `ledger_info` used to verify a transaction range proof: [2](#0-1) 

2. `StateSnapshotRestoreController::run_impl` calls it right after verifying only that a `TransactionInfoWithProof` is internally consistent with the ledger info's accumulator hash (which is a self-consistency check, not a check that the ledger info itself is authentic): [3](#0-2) 

In both flows, `txn_info_with_proof.verify(li.ledger_info(), ...)` / `txn_list_with_proof.verify(ledger_info.ledger_info(), ...)` only proves that the supplied payload hashes into the accumulator root recorded inside the attacker-supplied `LedgerInfo` — it does not prove that `LedgerInfo` itself was produced/signed by real validators. That binding is only established by `EpochHistory::verify_ledger_info`, either via a trusted waypoint or via `epoch_state.verify(li)` (which checks the aggregate BLS signature against a known validator set) at line 309 of the epoch-ending restore file: [4](#0-3) 

If the epoch of the supplied ledger info is larger than `epoch_endings.len()` (i.e., the epoch-ending backup didn't (yet) provide validator-set history that far), the function silently skips this signature check entirely, structurally mirroring the oracle bug's "expired version is stamped with a stale non-zero price and thus reported as `valid = true`" pattern — here, "cannot be verified" is stamped as "verified" (`Ok(())`), and downstream code (`txn_list_with_proof.verify`, `txn_info_with_proof.verify`) treats the accumulator/state root inside that unverified ledger info as ground truth for accepting the restored write set / transaction list.

### Impact Explanation
This breaks the state-commitment integrity of the restore path: a compromised or malicious backup storage backend (which is explicitly the untrusted input restore code is designed to defend against, via waypoints and epoch-history verification) can supply a `LedgerInfoWithSignatures` with an epoch number set higher than the epoch history the restorer has loaded, along with an arbitrary/incorrect accumulator root, transaction list or state chunk. Because signature verification is skipped in this case, the forged root is accepted and used to authorize the corresponding transaction infos / state values being loaded into the durable ledger DB, corrupting durable state with unauthenticated data — exactly the "committed state differs from correct data" and "authenticated response bound to wrong root/version" impact class called out as in-scope.

### Likelihood Explanation
Exploitability requires control over (or compromise of) the backup storage source being restored from, which is the primary trust boundary the epoch-history/waypoint verification machinery exists to protect against — this is not a "malicious peer" DoS or a consensus-level issue, but a restore/backup pipeline that is a documented, first-class local code path (`storage/backup/backup-cli`). The gap is also explicitly flagged by the original author with a `TODO(aldenhu): fix this from upper level` comment, indicating it is a known, unresolved integrity hole rather than an intentionally-safe design decision.

### Recommendation
`EpochHistory::verify_ledger_info` should never return `Ok(())` for an epoch it cannot cryptographically verify. Instead of silently trusting the input, callers that only have a partial epoch-ending history for the target range should either (a) fail closed (return an error) when a chunk's ledger info epoch exceeds the loaded epoch history and no trusted waypoint covers it, or (b) require the caller to supply enough epoch-ending backups up front to cover the full target range so this branch is unreachable, converting the current "warn and accept" behavior into a hard error.

### Proof of Concept
1. Prepare a backup store where the transaction (or state-snapshot) manifest's `proof` file contains a forged `LedgerInfoWithSignatures` whose `epoch()` is set higher than `first_epoch + len(chunks)` of the epoch-ending manifest being restored (or simply omit/limit the epoch-ending manifests supplied via `--skip-epoch-endings` or a short epoch-history selection), and whose signatures are empty/invalid, but whose embedded accumulator/state root corresponds to attacker-chosen transaction infos or state values.
2. Run `TransactionRestoreController`/`StateSnapshotRestoreController` (as used by `aptos-db restore` or `backup-cli`) against this store.
3. Observe that `EpochHistory::verify_ledger_info` hits the `epoch > self.epoch_endings.len()` branch, logs a warning, and returns `Ok(())` without checking signatures.
4. Observe that the subsequent `verify()` calls only check internal consistency against the forged ledger info's own root hash, so the attacker-controlled transactions/state values are accepted and written into the restored `AptosDB`.

impl EpochHistory {
    pub fn verify_ledger_info(&self, li_with_sigs: &LedgerInfoWithSignatures) -> Result<()> {
        let epoch = li_with_sigs.ledger_info().epoch();
        ensure!(!self.epoch_endings.is_empty(), "Empty epoch history.",);
        if epoch > self.epoch_endings.len() as u64 {
            // TODO(aldenhu): fix this from upper level
            warn!(
                epoch = epoch,
                epoch_history_until = self.epoch_endings.len(),
                "Epoch is too new and can't be verified. Previous chunks are verified and node \
                won't be able to start if this data is malicious."
            );
            return Ok(());
        }
        if epoch == 0 {
            ensure!(
                li_with_sigs.ledger_info() == &self.epoch_endings[0],
                "Genesis epoch LedgerInfo info doesn't match.",
            );
        } else if let Some(wp_trusted) = self
            .trusted_waypoints
            .get(&li_with_sigs.ledger_info().version())
        {
            let wp_li = Waypoint::new_any(li_with_sigs.ledger_info());
            ensure!(
                *wp_trusted == wp_li,
                "Waypoints don't match. In backup: {}, trusted: {}",
                wp_li,
                wp_trusted,
            );
        } else {
            self.epoch_endings[epoch as usize - 1]
                .next_epoch_state()
                .ok_or_else(|| anyhow!("Shouldn't contain non- epoch bumping LIs."))?
                .verify(li_with_sigs)?;
        };
        Ok(())
    }
}
