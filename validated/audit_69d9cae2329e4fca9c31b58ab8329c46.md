### Title
Disk-index bucket capacity in `Bucket::grow_index()`/`grow_data()` only ever grows, never shrinks, causing permanent, disproportionate disk-space and rehash-CPU cost - (File: `bucket_map/src/bucket.rs`)

### Summary
The external report's bug class is "excess resource received/allocated is never returned/reclaimed" (excess ETH not refunded). The closest concrete analog in agave's accounts index/bucket-map storage is that the on-disk index and data buckets used by the disk-backed `AccountsIndex` are grown (`grow_index`, `grow_data`) whenever capacity is exceeded, but there is no corresponding shrink/compaction path. Once a bin's index or data bucket file has grown to accommodate a burst of entries, the allocated capacity is permanently retained even after most of those entries are deleted, unlike `accounts_db` shrink/clean which reclaim storage space for account data. This is a "keep, never give back" allocation pattern directly analogous to "excess payment not refunded."

### Finding Description
`Bucket::grow_index()` grows the index's backing mmap file whenever the current capacity is exceeded, sizing the new allocation to `max(current_capacity * 110/100, anticipated_size * 140/100)`: [1](#0-0) 

`grow_data()` performs the analogous power-of-two growth for the per-bucket data storage: [2](#0-1) 

Both `grow_index` and `grow_data` are only ever invoked from `Bucket::grow()`, which is driven by `BucketMapError::{IndexNoSpace, DataNoSpace}` returned on insertion failures, i.e., strictly on-demand growth: [3](#0-2) 

Deletions only free individual slots inside the existing allocation (`delete_key` marks index/data slots free) — they never trigger a re-size to a smaller allocation: [4](#0-3) 

There is no `shrink`/`compact` function anywhere in `bucket_map/src/bucket.rs` or the rest of the `bucket_map` crate (confirmed by search), in contrast to `accounts_db`, which has an explicit shrink/clean/reclaim path for account storage (`shrink_storage`, `remove_old_stores_shrink`, `shrink_candidate_slots`) that actively reduces `AccountStorageEntry` file sizes when the alive-to-total ratio drops: [5](#0-4) [6](#0-5) 

This asymmetry means the disk index bucket storage, once expanded (e.g., during a burst of new-account creation, an epoch with many new stake/vote accounts, or a temporary spike in unique pubkeys touching a bin), permanently retains that "excess" allocated capacity for the lifetime of the validator process, even if the number of live entries later drops back down — directly paralleling the "excess ETH kept, not refunded" pattern, just at the level of disk capacity instead of lamports.

### Impact Explanation
This causes a disproportionate and permanent disk-storage cost: the disk index for `AccountsIndex` (used when disk-index/secondary storage is enabled, e.g., via `--accounts-index-memory-limit-mb` / disk bucket-map config) retains peak capacity indefinitely. This matches the explicitly-accepted impact category "disproportionate storage and CPU cost," since re-growth operations (`copy_contents` on `grow_index`/`grow_data`) and the eventual re-hash cost when re-inserting keys after a grow are non-trivial CPU operations that get paid repeatedly at ever-larger sizes with no corresponding shrink to amortize costs down when load decreases. There is no correctness impact (no stale reads, no hash divergence, no consensus break) — this is purely a resource-retention/never-reclaimed issue, unprivileged in nature since any account-creation churn (which any user can influence via transactions creating many new accounts) can trigger the growth.

### Likelihood Explanation
Likelihood is high in the sense that growth events are routine and expected as part of normal validator operation (account churn naturally triggers `IndexNoSpace`/`DataNoSpace` and thus `grow_index`/`grow_data`). However, since a compensating "shrink" was apparently never implemented as a design decision (no `shrink_index`/`shrink_data`/`compact` exists anywhere in the crate), this is a design gap rather than a bug from a defect introduced by a specific commit; it is a long-standing structural characteristic of the bucket-map disk index and would be classified as a known "excess allocation is retained" issue with low urgency since it's a monotonic-but-bounded (by real usage-peak) memory/disk growth pattern, not runaway.

### Recommendation
Add a shrink/compaction path for `Bucket`'s index and data storages analogous to `accounts_db`'s shrink logic: periodically (e.g., during background cleaning intervals already used for `clean_accounts`/`shrink_candidate_slots`), measure the live-entry ratio of each bucket relative to its allocated capacity and, if sufficiently below a shrink threshold, reallocate the bucket to a smaller capacity (copying only live entries), mirroring `AccountsDb::shrink_storage`'s alive-bytes-vs-capacity comparison used for `AccountStorageEntry`.

### Proof of Concept
1. Enable the disk-backed accounts index (secondary/disk index mode).
2. Drive a burst of unique account creation touching a specific index bin sufficient to trigger several `grow_index`/`grow_data` calls (`bucket_map/src/bucket.rs:685-820`), growing the bucket's backing mmap files to a large capacity.
3. Delete the majority of those accounts (rooted and cleaned), reducing live entries in the bin back to a small fraction of capacity via `delete_key` (`bucket_map/src/bucket.rs:663-679`), which only frees individual slots.
4. Observe (e.g., via `BucketStats.total_file_size`/`max_size`, tracked in `bucket_map/src/bucket_stats.rs:1-45`) that the on-disk allocation size for the bucket's index/data files never decreases, remaining at the peak size indefinitely — confirming the "excess capacity, once acquired, is never returned."

    pub fn grow_data(&self, data_index: u64, current_capacity_pow2: u8) {
        let (new_bucket, _file_name) = BucketStorage::new_resized(
            &self.drives,
            self.index.max_search,
            self.data.get(data_index as usize),
            Capacity::Pow2(std::cmp::max(
                current_capacity_pow2 + 1,
                DEFAULT_CAPACITY_POW2,
            )),
            1 << data_index,
            Self::elem_size(),
            &self.stats.data,
        );
        self.reallocated.add_reallocation();
        let mut items = self.reallocated.items.lock().unwrap();
        items.data = Some((data_index, new_bucket));
    }

    fn shrink_storage(&self, store: Arc<AccountStorageEntry>) {
        let slot = store.slot();
        if self.accounts_cache.contains(slot) {
            // It is not correct to shrink a slot while it is in the write cache until flush is complete and the slot is removed from the write cache.
            // There can exist a window after a slot is made a root and before the write cache flushing for that slot begins and then completes.
            // There can also exist a window after a slot is being flushed from the write cache until the index is updated and the slot is removed from the write cache.
            // During the second window, once an append vec has been created for the slot, it could be possible to try to shrink that slot.
            // Shrink no-ops before this function if there is no store for the slot (notice this function requires 'store' to be passed).
            // So, if we enter this function but the slot is still in the write cache, reasonable behavior is to skip shrinking this slot.
            // Flush will ONLY write alive accounts to the append vec, which is what shrink does anyway.
            // Flush then adds the slot to 'uncleaned_roots', which causes clean to take a look at the slot.
            // Clean causes us to mark accounts as dead, which causes shrink to later take a look at the slot.
            // This could be an assert, but it could lead to intermittency in tests.
            // It is 'correct' to ignore calls to shrink when a slot is still in the write cache.
            return;
        }
        let mut unique_accounts =
            self.get_unique_accounts_from_storage_for_shrink(&store, &self.shrink_stats);
        debug!("do_shrink_slot_store: slot: {slot}");

            &store,
            &mut unique_accounts,
            &self.shrink_stats,
        );

            shrink_collect.alive_total_bytes + shrink_collect.tombstones_total_bytes;

        if Self::should_not_shrink(total_rewrite_bytes as u64, shrink_collect.written_bytes)

    fn select_candidates_by_total_usage(
        &self,
        shrink_slots: &ShrinkCandidates,
        shrink_ratio: f64,
    ) -> (IntMap<Slot, Arc<AccountStorageEntry>>, ShrinkCandidates) {
        struct StoreUsageInfo {
            slot: Slot,
            alive_ratio: f64,
            alive_bytes_after_shrink: u64,
            store: Arc<AccountStorageEntry>,
        }
        let mut store_usages = Vec::with_capacity(shrink_slots.len());
        let mut total_alive_bytes: u64 = 0;
        let mut total_bytes: u64 = 0;
        for slot in shrink_slots {
            let Some(store) = self.storage.get_slot_storage_entry(*slot) else {
                continue;
            };
            let alive_bytes_after_shrink = self.alive_bytes_after_shrink(&store) as u64;
            total_alive_bytes += alive_bytes_after_shrink;
            let written_bytes = store.written_bytes();
            total_bytes += written_bytes;
            debug_assert!(
                written_bytes > 0,
                "shrink candidate has zero written bytes! slot: {slot} id: {}",
                store.id(),
            );
            let alive_ratio = alive_bytes_after_shrink as f64 / written_bytes as f64;
            store_usages.push(StoreUsageInfo {
                slot: *slot,
                alive_ratio,
                alive_bytes_after_shrink,
                store: store.clone(),
            });
        }
        store_usages.sort_by(|a, b| {
            a.alive_ratio
                .partial_cmp(&b.alive_ratio)
                .unwrap_or(std::cmp::Ordering::Equal)
        });

        // Working from the beginning of store_usage which are the most sparse and see when we can stop
        // shrinking while still achieving the overall goals.
        let mut shrink_slots = IntMap::default();
        let mut shrink_slots_next_batch = ShrinkCandidates::default();
        for store_usage in &store_usages {
            let store = &store_usage.store;
            let alive_ratio = (total_alive_bytes as f64) / (total_bytes as f64);
            debug!(
                "alive_ratio: {:?} store_id: {:?}, store_ratio: {:?} requirement: {:?}, \
                 total_bytes: {:?} total_alive_bytes: {:?}",
                alive_ratio,
                store_usage.store.id(),
                store_usage.alive_ratio,
                shrink_ratio,
                total_bytes,
                total_alive_bytes
            );
            if alive_ratio > shrink_ratio {
                // we have reached our goal, stop
                debug!(
                    "Shrinking goal can be achieved at slot {:?}, total_alive_bytes: {:?} \
                     total_bytes: {:?}, alive_ratio: {:}, shrink_ratio: {:?}",
                    store_usage.slot, total_alive_bytes, total_bytes, alive_ratio, shrink_ratio
                );
                if store_usage.alive_ratio < shrink_ratio {
                    shrink_slots_next_batch.insert(store_usage.slot);
                } else {
                    break;
                }
            } else {
                let current_store_size = store.written_bytes();
                let after_shrink_size = store_usage.alive_bytes_after_shrink;
                let bytes_saved = current_store_size.saturating_sub(after_shrink_size);
                total_bytes -= bytes_saved;
                shrink_slots.insert(store_usage.slot, Arc::clone(store));
            }
        }
        (shrink_slots, shrink_slots_next_batch)
    }
