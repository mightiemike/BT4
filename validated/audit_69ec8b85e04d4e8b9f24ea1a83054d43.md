## Title
`ensure_match_transaction_info()` accepts replayed transactions whose authenticated checkpoint/state roots diverge from local execution - (File: `types/src/transaction/mod.rs`)

## Summary
`TransactionOutput::ensure_match_transaction_info()` is the integrity check used by replay/verification tooling (`storage/db-tool/src/replay_on_archive.rs`, `aptos-move/aptos-debugger/src/aptos_debugger.rs`, `aptos-move/cli/src/commands.rs`) to confirm that a locally re-executed transaction output matches the authenticated `TransactionInfo` recorded on-chain. The function checks status, gas used, write-set hash (`state_change_hash`), and event root hash, but by its own documented admission does **not** check `TransactionInfoV1`'s `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` fields.

This is called directly for replay verification: [2](#0-1) .

The commit path itself computes these checkpoint hashes and binds them into `TransactionInfoV1`, which is then accumulated into the authenticated transaction accumulator: [3](#0-2)  and [4](#0-3) . The design explicitly states these roots — particularly `position_state_checkpoint_hash` gated by `COMPUTE_TRADING_NATIVE_STATE_ROOTS` — are meant to be "consensus-verified": [5](#0-4) .

The gap is analogous to the external report's core defect: a validation function that is trusted to bind an output to the correct, authenticated commitment silently omits part of that binding (in the report, the VFS address; here, the checkpoint/state roots), so a value that should fail validation is accepted as matching.

## Impact Explanation
Once `COMPUTE_TRADING_NATIVE_STATE_ROOTS` / `HOT_STATE_ROOT_IN_TXN_INFO` are enabled on-chain (both are marked "permanent" lifetime features intended for mainnet), a locally recomputed `position_state_checkpoint_hash` or `hot_state_checkpoint_hash` that diverges from the authenticated on-chain value would **not** be caught by `ensure_match_transaction_info`. Replay/verification tooling (backup verification, debugger replay, archive replay) that relies on this function as its correctness oracle would report success even though the locally derived Merkle root for the native-position tree (or hot state) does not match what was accepted by consensus. This is a real hard-fork/divergence-detection gap: a state root that differs from the correct result is accepted as valid by the verification path, defeating the purpose of `replay_on_archive` and similar tools for the position/hot-state subsystems.

## Likelihood Explanation
The bug is self-acknowledged in code (`TODO(trading-native)`), confirming the maintainers are aware the check is incomplete but it is currently gated by feature flags (`COMPUTE_TRADING_NATIVE_STATE_ROOTS`, `HOT_STATE_ROOT_IN_TXN_INFO`) not yet fully enabled. It is not exploitable by an external attacker to corrupt consensus state directly — the underlying accumulator/root computation elsewhere (`do_ledger_update.rs`) is unaffected — but it is a genuine proof/verification-integrity gap that would silently mask a real divergence (e.g. a bug in position-tree computation or replay logic) once those features go live, which is exactly the class of hard-fork-only divergence-during-replay/verification issue in scope.

## Recommendation
Extend `ensure_match_transaction_info` to compare `txn_info.state_checkpoint_hash()`, `hot_state_checkpoint_hash()` (if present in `TransactionInfoV1`), and `position_state_checkpoint_hash()` against the corresponding locally computed values whenever those fields are populated, before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled on mainnet, exactly as the existing TODO comment recommends.

## Proof of Concept
Not independently reproducible from static analysis alone since `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are not yet fully active on mainnet and I could not run replay tooling in this environment. The evidence is the code path itself: `ensure_match_transaction_info` never reads `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash` from `txn_info`, while `do_state_checkpoint.rs`/`do_ledger_update.rs` compute and bind exactly those fields into the authenticated `TransactionInfoV1`/accumulator. A local execution producing a diverging position/hot-state root would pass this check unnoticed; verifying this at runtime would require constructing a `TransactionOutput` with a mismatched `position_state_checkpoint_hash` against a `TransactionInfoV1` and confirming `ensure_match_transaction_info` still returns `Ok(())`, which I was not able to execute in this read-only environment.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
