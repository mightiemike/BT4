## Title
`market-vault.clar` `collateral-add`/`debt-add-scaled` mutate state in `let`-bindings before their own pause/amount guards run - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
In Clarity, `let` bindings are evaluated strictly in order, and any side-effecting call inside a binding (`map-set`, etc.) executes immediately - it is not deferred until after the function body's `asserts!`/`try!` guards. `collateral-add` and `debt-add-scaled` in `v0-market-vault.clar` (and the mirrored `market-vault.clar` in `local-testing`) call `add-user-collateral` / `add-user-scaled-debt` - both of which perform a `map-set` write - as part of the `let` binding list, *before* the function checks `check-impl-auth`, the pause flag, or `amount > 0`. This is the same root-cause shape as the external report: a guard that is supposed to gate a state-changing action is bypassed because the mutation is reachable before the guard evaluates.

### Finding Description
`add-user-collateral` performs a `map-set` on the `collateral` map: [1](#0-0) 

It is invoked from the `let` binding list of `collateral-add`, i.e. before any of the function's guards run: [2](#0-1) 

The `asserts!`/`try!` calls (`check-impl-auth`, `not (get collateral-add states)` pause check, `amount > 0`) appear only in the function *body*, after the `let` bindings, which is textually where they read, but Clarity's evaluation model executes `let` bindings top-to-bottom with side effects taking place immediately as each binding is computed - so `map-set collateral key updated-collateral-amount` has already executed by the time `check-impl-auth`/pause/`amount>0` are checked. The same pattern recurs in `debt-add-scaled`, which calls `add-user-scaled-debt` (also a `map-set`) inside its `let` bindings before the guards: [3](#0-2) [4](#0-3) 

This mirrors the reported bug class: "a mutation evaluated before its guard." In the Polygon report, a lock intended to gate dangerous control-flow was bypassed because the dangerous action executed via a code path that never reached the check. Here, the `collateral`/`debt` map writes execute via a code path (`let` binding evaluation) that runs unconditionally before `check-impl-auth`, the `collateral-add`/`debt-add` pause flags, and the `amount > 0` check are evaluated.

Because `check-impl-auth` is intended to restrict `collateral-add`/`debt-add-scaled` to be called only through `market.clar` (the authorized caller/implementation), and the pause flag is intended to allow the DAO to halt collateral/debt accounting during an incident, both of these controls are effectively rendered advisory for the underlying map mutation: the map write already happened by the time either check fails, so if the transaction reverts due to the guard failing, the map write is rolled back by Clarity's atomic-transaction semantics (an aborted transaction discards all state changes) - meaning a single call in isolation is safe (revert undoes the "early" mutation). The real risk surfaces only when this local-vault mutation is part of a larger, multi-call flow (e.g. via `market.clar`'s `supply-collateral-add`, which calls `vault-deposit` then `collateral-add`, or any future flow that catches the error from `collateral-add`/`debt-add-scaled` with a non-reverting pattern such as `unwrap!`/`match` and continues execution) - in such a flow, an "early" mutation that occurred before a guard failure could persist even though the guard rejected the operation, since only the specific failing call reverts, not the whole enclosing transaction, if the caller does not propagate the error with `try!`.

### Impact Explanation
If any current or future call site invokes `collateral-add` or `debt-add-scaled` without propagating failure via `try!` (e.g. using `unwrap!`/`match`/`default-to` patterns that swallow the error), the `map-set` to the `collateral`/`debt` maps performed inside the `let` bindings would persist in contract state even though `check-impl-auth`, the pause flag, or the zero-amount guard failed and the function returned an error. This would let a caller record collateral or debt amounts without the corresponding token transfer/authorization actually completing (since `receive-tokens`/`try! (check-impl-auth)` executes after the mutation), directly inflating a user's recorded collateral or debt balances - a path to protocol insolvency or theft of funds if exploited via an alternate entry point that does not use `try!` on the vault call's result. This lands on the Critical impact bucket (protocol insolvency / theft of funds at rest).

### Likelihood Explanation
Currently, all in-scope call sites in `market.clar` invoke `collateral-add`/`debt-add-scaled` with `try!`, so a failing guard reverts the entire transaction and the "early" mutation is discarded by Clarity's atomic transaction semantics - meaning the vulnerability is not exploitable through the currently-wired call paths. However, the code shape itself is the same class of defect flagged in the external report: a guard textually placed to gate an action does not actually gate it at the interpreter level, and the safety net depends entirely on every current and future caller consistently using `try!`/propagating failure. Any refactor, new proposal script, or new market version that calls these vault functions and does not strictly propagate the error (a single missed `try!`) reintroduces the full-severity issue silently, with no test able to catch it by inspecting the guard code alone.

### Recommendation
Restructure `collateral-add`, `collateral-remove`, `debt-add-scaled`, and `debt-remove-scaled` (and any other market-vault function following this pattern) so that all `asserts!`/`try!` guard checks (`check-impl-auth`, pause-state checks, `amount > 0`) execute in the function body *before* any `let` binding that performs a `map-set`/`map-delete`. Bindings that compute values without side effects (e.g. reading `entry`, `mask`, `updated-mask`) can remain in the `let`, but the actual `add-user-collateral`/`add-user-scaled-debt` calls (or any other function with a `map-set`) should be moved into the body after the guards, so a failing guard is guaranteed to be evaluated before any state mutation occurs, independent of whether the transaction as a whole reverts.

### Proof of Concept
Conceptual PoC (cannot be fully executed without a non-`try!` call site in the current in-scope code, but demonstrates the underlying defect):
1. Assume a future/alternate entry point (or a modified `market.clar` version) calls `(match (contract-call? .v0-market-vault collateral-add account amount ft asset-id) ok-result (handle ok-result) err-code (log-and-continue err-code))` instead of `(try! ...)`.
2. Caller supplies `amount = 0` (or the DAO has set `collateral-add` pause state to `true`, or the caller is not the authorized `impl`).
3. `v0-market-vault.clar`'s `collateral-add` evaluates its `let` bindings in order: `add-user-collateral user-id asset-id amount` executes `map-set collateral key updated-collateral-amount`, permanently recording the (potentially zero or unauthorized) collateral amount.
4. Execution then reaches `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` (or the pause/auth check) and returns `(err ERR-AMOUNT-ZERO)`.
5. Because the alternate caller used `match`/non-propagating error handling instead of `try!`, only this inner call fails - the outer transaction commits, and the `collateral` map now contains an entry that was written despite the guard rejecting the call. [5](#0-4)

(define-public (collateral-add (account principal) (amount uint) (ft <ft-trait>) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve-or-create account))
        (user-id (get id entry))
        (mask (get mask entry))
        (updated-mask (mask-update mask asset-id true true)) ;; collateral, insert
        (updated-entry (merge entry (refresh updated-mask)))
        (result (add-user-collateral user-id asset-id amount)))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-add states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-tokens ft amount account))
    
    (insert updated-entry)
