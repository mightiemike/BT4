Based on the investigation, I found a viable analog in the NEAR Wallet Contract's (`near-wallet-contract`) eth-transaction execution flow, where a fixed gas budget assumption for a callback (analogous to assuming a "standard" bounded token-transfer behavior) can be violated by an external contract's response size, permanently bricking the wallet.

### Title
Fixed callback gas budget in `WalletContract::rlp_execute_callback` can be exhausted by large cross-contract call results, permanently freezing the wallet contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract` gates all mutating entry points behind an `has_in_flight_tx` flag that is only cleared inside the promise callback `rlp_execute_callback` [1](#0-0) . For the generic/default action dispatch branch, the callback promise is scheduled with a **fixed** `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) regardless of the size of data the downstream call may return, unlike the two special-cased eth-emulation branches which add `action.gas()` to their callback budgets [2](#0-1) .

### Finding Description
`rlp_execute` sets `has_in_flight_tx = true` once it successfully schedules a promise, and this is only reset back to `false` as the first statement inside the corresponding callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) [3](#0-2) . Because NEAR contract state changes are only committed if the function call returns without panicking, any panic partway through a callback rolls back *all* state changes made in that receipt — including the reset of `has_in_flight_tx`.

For the default dispatch branch (used for plain Near actions decoded from the RLP transaction, i.e. `Action::FunctionCall`/`Transfer`/`AddKey`/`DeleteKey` targets that are not one of the recognized ERC-20/base-token emulation selectors), the callback is scheduled with a constant gas budget that does not scale with `action.gas()` or with the target's potential response size: [4](#0-3) 

Inside `rlp_execute_callback`, `env::promise_result(0)` is used to read the previous promise's result [5](#0-4) . The underlying host function's gas cost for a successful result is explicitly documented and charged as `base + cost of writing data into a register`, i.e. it scales with the byte-length of the returned promise value [6](#0-5) .

Since `target`/`action` (including the attached gas for the inner call) are attacker/user-controlled fields decoded from the signed RLP Ethereum transaction, an account that is the target of the inner call can return an arbitrarily large payload from the invoked method. When the resulting promise resolves successfully with a payload larger than what fits in the residual gas of the fixed 5 Tgas `RLP_EXECUTE_CALLBACK_GAS` budget (after the runtime's base callback overhead), `env::promise_result` will exhaust gas and cause `rlp_execute_callback` to abort. Because the abort happens before/at the point `self.has_in_flight_tx = false` would otherwise be persisted, the flag remains permanently `true` in committed state.

### Impact Explanation
Once `has_in_flight_tx` is stuck at `true`, every subsequent call to `rlp_execute` immediately returns a hard failure without scheduling any further work [7](#0-6) . This permanently disables the eth-wallet's ability to process any further Ethereum-emulated transactions, effectively freezing any assets/actions that must go through this Wallet Contract (NEAR balance transfers, NEP-141 token transfers, access-key management routed through the wallet), matching the "permanently frozen funds" impact category. This is a direct structural analog to the reported bug class: an assumption about the bounded/standard behavior of a called external contract (there: `bool`-returning `transfer`; here: a small/bounded return payload) that, when violated, makes a state-critical operation (there: `recover()`; here: clearing `has_in_flight_tx`) permanently un-executable.

### Likelihood Explanation
Reachable by a single unprivileged actor: the wallet owner (transaction signer) or a relayer submitting the signed RLP transaction on the owner's behalf chooses the inner action's `target` and `gas`; the target contract only needs to be a valid Near account that returns a sufficiently large successful result for the invoked method (which can be entirely legitimate large state, or a contract purpose-built to return an oversized blob). No validator or node collusion, no malicious peer, and no special privileges are required — a normal transaction/action from the wallet path suffices.

### Recommendation
Scale the default branch's callback gas allocation with `action.gas()` (as already done for the `ERC20Transfer` and `EOABaseTokenTransfer` branches), and/or bound the maximum size of data copied out of `promise_result` in `rlp_execute_callback`, and/or reset `has_in_flight_tx` via a mechanism that is robust to callback failure (e.g., checked before doing any gas-sensitive work, or via a separate always-succeeding cleanup step) so an out-of-gas panic in the callback cannot leave the flag permanently set.

### Proof of Concept
1. Deploy (or reuse) a Near contract `Malicious` whose invoked method returns a payload sized such that copying it via `promise_result` inside a 5 Tgas budget causes an out-of-gas failure.
2. Construct and sign an RLP Ethereum transaction whose decoded Near action is a `FunctionCall` targeting `Malicious`'s large-return method, taking the default dispatch branch (i.e., not one of the ERC-20/base-token emulation selectors) in `dispatch_action`/match block at `lib.rs:412-470`.
3. Submit via `rlp_execute`; the wallet contract sets `has_in_flight_tx = true` and schedules `action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))` with `with_static_gas(RLP_EXECUTE_CALLBACK_GAS)`.
4. When the inner promise resolves successfully with the oversized payload, `rlp_execute_callback` panics on `env::promise_result(0)` due to insufficient gas, rolling back the `has_in_flight_tx = false` write.
5. Any subsequent call to `rlp_execute` on this wallet now always returns `success: false` with "transaction already in progress" — the wallet contract is permanently frozen.

/// # Cost

/// `base + cost of writing data into a register`
pub fn promise_result(
    ctx: &mut Ctx,
    _memory: &mut [u8],
    result_idx: u64,
    register_id: u64,
) -> Result<u64> {
    ctx.result_state.gas_counter.pay_base(base)?;
    if ctx.context.is_view() {
        return Err(
            HostError::ProhibitedInView { method_name: "promise_result".to_string() }.into()
        );
    }
    match ctx
        .context
        .promise_results
        .get(result_idx as usize)
        .ok_or(HostError::InvalidPromiseResultIndex { result_idx })?
    {
        PromiseResult::NotReady => Ok(0),
        PromiseResult::Successful(data) => {
            ctx.registers.set_rc_data(
                &mut ctx.result_state.gas_counter,
                &ctx.config.limit_config,
                register_id,
                Rc::clone(data),
            )?;
            Ok(1)
        }
        PromiseResult::Failed => Ok(2),
    }
