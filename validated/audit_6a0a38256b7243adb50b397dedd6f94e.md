### Title
Process-global class cache skips declaration re-validation for Cairo 0 classes, allowing undeclared-class execution to diverge across nodes - (File: crates/blockifier/src/state/state_reader_and_contract_manager.rs)

### Summary
The Pingora advisory root cause is a cache whose key/validation scheme omits a security-relevant dimension (host), letting one context's cached response be served to another. `StateReaderAndContractManager::get_compiled_from_class_manager` has an analogous validation gap: the process-global `ContractClassManager` class cache is keyed only by `ClassHash` and is **not** scoped to the currently committed chain state. The code itself documents that a cache hit "might contain a declared class from a reverted block", and mitigates this by re-checking `is_declared()` on cache hit — but only for non-V0 (Cairo1/Native) classes. Cairo 0 (`RunnableCompiledClass::V0`) cache hits are returned with no re-validation at all.

### Finding Description
`get_compiled_from_class_manager` in `crates/blockifier/src/state/state_reader_and_contract_manager.rs` reads: [1](#0-0) 

For a cache hit, the match arm explicitly does nothing for `V0` (`RunnableCompiledClass::V0(_) => {}`) while every other variant is required to pass `self.state_reader.is_declared(class_hash)?` before being trusted. The comment on lines 76-78 makes clear the developers are aware that the global cache (`ContractClassManager` / `GlobalContractCache`, keyed only by `ClassHash`, shared across the whole process lifetime — see `crates/starknet_api/src/class_cache.rs` and `crates/blockifier/src/state/global_cache.rs`) can retain entries from a block that was never committed (e.g., a rejected/aborted proposal, a re-executed/discarded speculative run, or a chain revert), yet chose to guard only the Cairo1/Native path: [2](#0-1) 

`FetchCompiledClasses::is_declared` is documented as "Cairo 0 classes always return false," which is presumably *why* the check was skipped for V0 (it cannot distinguish "was declared" from "was never declared" for Cairo 0). This means the safety net that exists for Cairo1/Native is structurally absent for Cairo 0, leaving the exact scenario the code comment warns about unmitigated for that class type — analogous to Pingora's cache key that "excludes critical factors," except here the missing factor is "is this class actually declared in the state I'm currently executing against."

### Impact Explanation
Because the class cache is process-global and outlives any individual block/proposal (populated via `contract_class_manager.set_and_compile` any time a class is successfully fetched, e.g. during speculative execution, validation-only runs, or a proposal that is later dropped), a Cairo 0 class hash that was ever fetched successfully — even in a block/proposal that was subsequently rejected, reverted, or not committed — remains servable indefinitely without re-checking that it is declared in the currently committed state. A transaction that invokes that class hash (as a `DEPLOY`/library-call/CALL target) on a node whose cache is warm from the earlier (uncommitted) execution will succeed and execute real bytecode, while a node with a cold cache (freshly synced, cache evicted by LRU, or restarted) will correctly reject it with `UndeclaredClassHash`. This is a state/consensus divergence between otherwise-honest nodes on the same input, which can lead to disagreement on transaction validity, differing state diffs/roots for the same block, and a chain that cannot reliably confirm the same state across nodes — i.e., wrong committed root / honest-node divergence.

### Likelihood Explanation
Triggering requires a class hash to have been present in a rejected/uncommitted block or discarded speculative execution (a routine occurrence in a sequencer that runs block-building, validation, and simulation concurrently against a long-lived `ContractClassManager`), followed by any transaction referencing that class hash before the LRU cache evicts it. No special privileges are needed by the transaction sender; the only requirement is that some prior, unprivileged path (declare validation, proposal execution, RPC `simulate_transactions`/`call`, mempool validation) caused the Cairo 0 class to be fetched and cached. Given the cache is explicitly called out by the code's own comment as capable of holding stale/uncommitted entries, and the fix pattern (is_declared check) exists but is deliberately not applied to V0, this is a real, reachable gap rather than a theoretical one, though its exact triggering window depends on node-specific timing/cache eviction, which this review could not fully instrument without execution.

### Recommendation
Extend `FetchCompiledClasses::is_declared` (or add a Cairo0-aware variant) so it can positively confirm a Cairo 0 class hash is declared in the *current* committed/pending state, and apply the same re-validation on every class-cache hit regardless of class version — removing the `V0(_) => {}` bypass. Alternatively, invalidate/scope the global `ContractClassManager` cache to committed state (e.g., clear or version-tag entries on block revert/abort of a proposal) so uncommitted classes can never be served after their originating block fails to commit.

### Proof of Concept
1. Node executes (validates or speculatively builds) a block/proposal that declares Cairo 0 class `C` and it gets cached in the shared `ContractClassManager` via `set_and_compile` (`get_compiled_from_class_manager`, cache-miss branch): [3](#0-2) 
2. That block/proposal is not committed (rejected, reverted, or discarded after simulation) — the committed state reader never records `C` as declared, but the process-global cache entry for `class_hash(C)` persists.
3. A subsequent unprivileged transaction invokes `class_hash(C)` (e.g., via `deploy_contract`/library-call/direct call). On this node, `get_compiled_from_class_manager` hits the cache; because the returned `RunnableCompiledClass::V0(_)` skips the `is_declared` check, the class executes successfully.
4. A different honest node without the warm cache entry calls the same transaction and correctly returns `StateError::UndeclaredClassHash`, diverging from the first node's result/state diff for the same input.

pub struct GlobalContractCache<T: Clone>(pub Arc<Mutex<ContractLRUCache<T>>>);

impl<T: Clone> GlobalContractCache<T> {
    /// Locks the cache for atomic access. Although conceptually shared, writing to this cache is
    /// only possible for one writer at a time.
    pub fn lock(&self) -> LockedClassCache<'_, T> {
        self.0.lock().expect("Global contract cache is poisoned.")
    }

    pub fn get(&self, class_hash: &ClassHash) -> Option<T> {
        self.lock().cache_get(class_hash).cloned()
    }

    pub fn set(&self, class_hash: ClassHash, contract_class: T) {
        self.lock().cache_set(class_hash, contract_class);
    }
