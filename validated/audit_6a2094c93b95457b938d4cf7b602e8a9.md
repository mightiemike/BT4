## Title
Metering local credit balance desyncs on overspend, permitting workflow execution beyond the reserved billing limit - (File: `core/services/workflows/metering/metering.go`)

### Summary
The workflow metering `Report.Settle` method tries to refund the difference between an earmarked ("deducted") credit amount and the actual credits spent by capability nodes. When actual spend exceeds the earmarked amount (analogous to the "WETH price increases" scenario in the report, where a natural fluctuation causes a withdrawal to exceed a deposit), the refund becomes negative, `balanceStore.Add` rejects it, and the error is silently logged and discarded. The in-memory credit balance is never decreased by the overspend, so it stays overstated relative to the true remaining reserve, exactly like the `totalDeposited` variable in the report that can never correctly reach zero/negative and desyncs from real pool state.

### Finding Description
`Report.Settle` earmarks credits during `Deduct` via `balanceStore.Minus`, then at settlement time attempts to refund the unused portion: [1](#0-0) 

`step.Deduction` is the amount earmarked for the step; `spentCredits` is the amount actually reported as spent by the capability's nodes (median-aggregated in the loop above). If `spentCredits` exceeds `step.Deduction` — which can happen legitimately, e.g. gas price spikes for a `GAS.*` spend type between deduction and settlement, exactly analogous to the WETH price increase in the external report — `step.Deduction.Sub(spentCredits)` is negative.

That negative value is passed to `balanceStore.Add`, which explicitly rejects negative amounts instead of decreasing the balance further: [2](#0-1) 

Because `Add` returns `ErrInvalidAmount` on a negative delta, the balance is **not modified at all**, and `Settle` only logs the invariant violation without correcting `r.balance`: [3](#0-2) 

The correct behavior on overspend would be to further debit the balance by `spentCredits - step.Deduction` (i.e., call `Minus`), mirroring how the underlying `Deduct`/`Minus` path already guards against going negative: [4](#0-3) 

Instead, the local `balance` value remains stuck at `original - step.Deduction`, i.e. higher than the true remaining credits (`original - spentCredits`). This is the same class of bug as the `totalDeposited` accounting variable: an unsigned/guarded quantity that is supposed to track net consumption but is allowed to silently desync from the real state whenever consumption exceeds the expected earmark, because the code chooses to reject the update rather than correctly account for the deficit.

Note that `AddSpent` still faithfully records the true `spentCredits` for reporting purposes: [5](#0-4) 

so the receipt eventually sent to the billing service (`CreditsConsumed: r.balance.GetSpent().String()`) is accurate: [6](#0-5) 

But the **local, in-execution gating balance** (`r.balance.Get()`), which is used by subsequent `Deduct` calls (`ByResource`, `ByDerivedAvailability`) to decide whether further capability calls are allowed, remains artificially inflated: [7](#0-6) [8](#0-7) 

### Impact Explanation
The `Reserve` call establishes a hard credit ceiling for a workflow execution as returned by the billing service: [9](#0-8) 

The purpose of `r.balance` gating subsequent `Deduct` calls is to enforce that ceiling in real time so a workflow execution cannot authorize more capability calls than it has been billed credits for. Once one step overspends its earmark (e.g. due to a legitimate gas-price fluctuation for an on-chain write capability, directly analogous to the price movement in the external report), the accounting silently fails to reduce the local balance by the deficit. Every subsequent `Deduct` in the same execution then operates against an inflated balance, allowing the workflow to authorize/execute additional paid capability invocations (e.g. more on-chain writes, more compute) that exceed the credit amount the billing service actually reserved for this execution. This is a metering/billing-enforcement bypass — a form of misreporting/uncontrolled resource consumption within the node's own execution engine — even though the final receipt's `CreditsConsumed` figure is separately accurate.

### Likelihood Explanation
This does not require a malicious node/operator; it can be triggered by ordinary conditions already anticipated by the code itself: the `GAS.*` spend-type handling explicitly shifts/rounds values and expects gas price variance between the time credits are earmarked (`Deduct`) and the time the actual spend is reported (`Settle`). Any workflow execution containing a paid capability step whose real cost variably exceeds its `ByDerivedAvailability`/`ByResource` earmark (gas spikes, concurrent-call-derived limits being tight, rounding in `convertToBalance`/`convertFromBalance`) will hit this path. The condition is silently swallowed (only an `Info`-level log line), so it is likely to go unnoticed in production while systematically under-enforcing the credit ceiling.

### Recommendation
In `Report.Settle`, when `spentCredits.GreaterThan(step.Deduction)`, explicitly debit the balance for the excess via `balanceStore.Minus(spentCredits.Sub(step.Deduction))` (and floor the balance at zero rather than erroring/no-op), instead of routing the negative delta through `Add`, which is documented to reject negative values. Alternatively, replace the `Add`/`Minus` split with a single signed adjustment method that always applies `step.Deduction - spentCredits` to the balance regardless of sign, so the local balance can never desynchronize from true consumption.

### Proof of Concept
1. Configure a workflow step using `ByDerivedAvailability` (or `ByResource`) for a `GAS.<chainSelector>` spend type; `Deduct` earmarks `step.Deduction` credits and reduces `r.balance` accordingly via `balanceStore.Minus` (metering.go:375, balance_store.go:130-146).
2. Have the capability's node responses (`metadata.Metering`) report a `SpendValue` for that unit whose converted credit value (`spentCredits`) is greater than `step.Deduction` — trivially true whenever the real gas price at execution time is higher than the gas price used to compute the earmark.
3. In `Settle` (metering.go:511-515), `step.Deduction.Sub(spentCredits)` is negative; `r.balance.Add(...)` returns `ErrInvalidAmount` (balance_store.go:176-178) and is discarded; `r.balance` is left unchanged at `original - step.Deduction`, even though true remaining credits are `original - spentCredits` (a smaller number).
4. A subsequent `Deduct` call in the same workflow execution computes `getMaxSpendForInvocation` off the inflated `r.balance.Get()` (metering.go:796), permitting further capability spend beyond what the billing service actually reserved for this execution — despite the eventual receipt separately reporting the true `spentCredits` via `AddSpent`/`GetSpent` (metering.go:517, 648).

func ByResource(
	spendType, capabilityID string,
	amount decimal.Decimal,
) func(string, *Report) ([]capabilities.SpendLimit, error) {
	return func(ref string, r *Report) ([]capabilities.SpendLimit, error) {
		step := ReportStep{
			CapabilityID:     capabilityID,
			Deduction:        decimal.Zero,
			AggregatedSpends: make(map[string]AggregatedStepDetail),
		}

		defer func() {
			r.steps[ref] = step
		}()

		bal, err := r.balance.ConvertToBalance(spendType, amount)
		if err != nil {
			// Fail open, continue optimistically
			r.switchToMeteringMode(fmt.Errorf("failed to convert to balance [%s]: %w", spendType, err))
		}

		step.Deduction = bal

		// if in metering mode, exit early without modifying local balance
		if r.meteringMode {
			return []capabilities.SpendLimit{}, nil
		}

		return []capabilities.SpendLimit{}, r.balance.Minus(bal)
	}

func (r *Report) getMaxSpendForInvocation(
	userSpendLimit decimal.NullDecimal,
	openConcurrentCallSlots int,
) (decimal.NullDecimal, error) {
	nullCapSpendLimit := decimal.NewNullDecimal(decimal.Zero)
	nullCapSpendLimit.Valid = false

	if openConcurrentCallSlots == 0 {
		// invariant: this should be managed by the consumer (engine)
		return nullCapSpendLimit, ErrNoOpenCalls
	}

	if !r.reserved {
		return nullCapSpendLimit, ErrNoReserve
	}

	if r.meteringMode {
		return nullCapSpendLimit, nil
	}

	// Split the available local balance between the number of concurrent calls that can still be made
	spendLimit := r.balance.Get().Div(decimal.NewFromInt(int64(openConcurrentCallSlots)))

	if userSpendLimit.Valid {
		spendLimit = decimal.Min(spendLimit, userSpendLimit.Decimal)
	}

	return decimal.NewNullDecimal(spendLimit), nil
}

// Minus lowers the current credit balance.
func (bs *balanceStore) Minus(amount decimal.Decimal) error {
	bs.mu.Lock()
	defer bs.mu.Unlock()

	if amount.LessThan(decimal.Zero) {
		return ErrInvalidAmount
	}

	if amount.GreaterThan(bs.balance) {
		return ErrInsufficientBalance
	}

	bs.balance = bs.balance.Sub(amount)

	return nil
}
