### Title
Post-validation mutation of receipts bypasses `max_receipt_size` limit, admitting oversized receipts into cross-shard traffic - (File: `runtime/runtime/src/lib.rs`)

### Summary
In `Runtime::apply_action_receipt`, newly-created receipts are size/shape-validated via `validate_receipt(..., ValidateReceiptMode::NewReceipt)` **before** `output_data_receivers` are appended to them (or before the return value is wrapped into a new `Data` receipt). Because the size check happens too early in the pipeline, a contract call reachable by any unprivileged account can produce a receipt that passes validation at its pre-mutation size and then grows past `max_receipt_size` after the `output_data_receivers`/return-value mutation, with no re-validation afterward.

### Finding Description
`apply_action_receipt` executes each action in the receipt and, immediately after each action, validates any freshly created receipts: [1](#0-0) 

Only after this loop completes does the function mutate the resulting receipt by attaching `output_data_receivers` to it (when the action's `ReturnData` is a `ReceiptIndex`) or by wrapping a large return value into a new `Data` receipt derived from `output_data_receivers`: [2](#0-1) 

Neither branch re-invokes `validate_receipt`/the `max_receipt_size` check after this mutation, so a receipt that was exactly at (or just under) `max_receipt_size` when first validated can be pushed above the limit by the subsequent `output_data_receivers` append or by wrapping an oversized return value, and it is still forwarded/committed as a valid outgoing/local receipt. This is a known, already-tracked defect referenced directly in the test suite comments (`https://github.com/near/nearcore/issues/12606`): [3](#0-2) [4](#0-3) 

The regression tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` construct exactly this scenario (a `promise_return` whose target receipt is sized to be at the limit, or a returned value sized to be at the limit) via a normal, unprivileged `FunctionCall` transaction, and confirm via `assert_oversized_receipt_occurred` that a receipt exceeding `max_receipt_size` is actually persisted as an incoming/outgoing receipt on chain: [5](#0-4) [6](#0-5) 

This directly parallels CVE-2021-32566's bug class ("improper input validation" that lets a maliciously-shaped input evade the size/limit check meant to bound resource consumption) — here the validation is performed on a snapshot of the receipt taken before its final mutation, so the enforced invariant (`size <= max_receipt_size`) that downstream systems (bandwidth scheduler, congestion control, state-witness/storage-proof size accounting, receipt size limits referenced throughout `core/primitives/src/bandwidth_scheduler.rs` and `runtime/runtime/src/congestion_control.rs`) rely on can be silently violated by any account submitting a single transaction.

### Impact Explanation
`max_receipt_size` is a protocol-level invariant consumed by the bandwidth scheduler and congestion control to bound the amount of receipt data shards must buffer/forward/process per chunk, and indirectly bounds state-witness and storage-proof sizes. An unprivileged caller who can get an oversized receipt admitted bypasses this bound, which can inflate per-chunk receipt/storage-proof sizes beyond what the protocol assumes elsewhere, risking excessive resource consumption or divergent behavior between nodes that enforce the limit differently at different code paths (receipt creation vs. later oversized persisted receipt). This matches the "resource exhaustion / limit-bypass DOS" bug class of the CVE, reachable purely through a signed `FunctionCall` transaction from any account — no elevated privilege, validator role, or network-level access is required.

### Likelihood Explanation
High reachability: the trigger is a standard `FunctionCall` transaction from any funded account, requiring only a contract that does a `promise_return` or returns a value sized near `max_receipt_size` — both are directly demonstrated in the existing test contract (`near_test_contracts::rs_contract`) methods `max_receipt_size_promise_return_method1` and `max_receipt_size_value_return_method`, and the bug is already tracked upstream, indicating it reproduces deterministically.

### Recommendation
Re-run `validate_receipt` (specifically the size check) on the mutated receipt after `output_data_receivers` are appended or after wrapping the return value into a `Data` receipt, at `runtime/runtime/src/lib.rs:1031-1069`, and fail the receipt (as `ReceiptValidationError::ReceiptSizeExceeded`) if the post-mutation size exceeds `max_receipt_size`, mirroring the existing check at lines 866-878.

### Proof of Concept
1. Deploy `near_test_contracts::rs_contract()` from any funded account.
2. Call `max_receipt_size_promise_return_method1` (or `max_receipt_size_value_return_method`) with an `args_size`/`value_size` chosen so the resulting receipt is at `max_receipt_size` (4,194,304 bytes) before `output_data_receivers`/return-value wrapping, as done in `test_max_receipt_size_promise_return`/`test_max_receipt_size_value_return`.
3. Observe (as `assert_oversized_receipt_occurred` verifies) that a receipt whose serialized size exceeds `max_receipt_size` is persisted as an incoming/outgoing receipt on chain, i.e. the size limit was bypassed: [6](#0-5)

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
