### Title
Unbounded `ListProposals`/`getProposalList` API endpoint iterates the entire, ever-growing proposal set with no pagination or cap - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`BondAggregator.liveMarketsBy` reverted because it looped over an unbounded, ever-growing `marketCounter` with external calls each iteration, eventually exceeding the block gas limit and permanently breaking the read path. The direct analog in java-tron is `Wallet.getProposalList()`, exposed via the unauthenticated `WalletApi.listProposals` gRPC method and the `ListProposalsServlet` HTTP endpoint, which pulls the **entire** `ProposalStore` into memory and serializes it with no offset/limit/cap, unlike the pagination-safe sibling `getPaginatedProposalList`.

### Finding Description
`getProposalList()` fetches every proposal ever created via `chainBaseManager.getProposalStore().getAllProposals()` and appends all of them to a single response builder, with no bound on the number of items processed or returned: [1](#0-0) 

This is reachable by any unprivileged, unauthenticated caller through two public interfaces:
- gRPC `WalletApi.listProposals` / `WalletSolidityApi/WalletExtension` handlers, which call `wallet.getProposalList()` directly with no offset/limit parameter (`EmptyMessage` request): [2](#0-1) 
- the HTTP `ListProposalsServlet`, which likewise calls `wallet.getProposalList()` unconditionally and serializes the full result to JSON: [3](#0-2) 

Crucially, the codebase already recognizes this exact bug class and has a fixed, bounded sibling API, `getPaginatedProposalList`, which explicitly caps the result with `PROPOSAL_COUNT_LIMIT_MAX` and computes only a bounded key range: [4](#0-3) 

The same unbounded pattern also exists for `getWitnessList()` (fixed analog `getPaginatedNowWitnessList` exists), reinforcing that this is a known-and-partially-fixed anti-pattern the maintainers did not apply consistently across all list endpoints: [5](#0-4) 

Unlike TRON's active witness set (bounded to a small constant, e.g. 27/127), the `ProposalStore` grows monotonically over the life of the chain — every committee proposal ever submitted (including expired/disapproved/canceled ones) remains a permanent entry and is never pruned, since `latestProposalNum` only increases. Therefore `getProposalList()`'s cost (DB reads + protobuf serialization + JSON marshaling in the HTTP case) scales linearly and unboundedly with total historical proposal count, with no way for the caller to cap it.

### Impact Explanation
This is the underpriced-public-work analog of the Sherlock finding: a public, unauthenticated read API endpoint whose resource cost (CPU, memory, response size, network bandwidth) is unbounded and grows forever with global chain state, with no per-request cap enforced by the server. As the number of historical proposals grows (which happens automatically over the life of the network and cannot be prevented), each call to `ListProposals`/`GET /wallet/listproposals` becomes progressively more expensive to serve. This can eventually:
- degrade full-node responsiveness for that request (large iteration + full JSON serialization on every call, called repeatedly by any client),
- amplify DoS potential, since an unauthenticated caller can trigger unlimited full-store scans/serializations at will with a single-line HTTP GET request, at negligible cost to the caller but growing cost to the node,
- diverge in practice from the already-fixed sibling endpoint (`getPaginatedProposalList`) which explicitly caps with `PROPOSAL_COUNT_LIMIT_MAX`, showing the team accepted the risk model but left this endpoint unmitigated.

This does not directly cause consensus divergence (it's a read-only API, not part of block validation/execution), so severity is lower than a consensus-halting bug, but it is a legitimate, concretely reachable resource-exhaustion / DoS vector on the public API surface, matching the "underpriced-public-work" impact class called out in the validation rules.

### Likelihood Explanation
High likelihood of eventual triggering without any attacker action: proposal count monotonically increases as normal chain operation continues (every `ProposalCreateContract` transaction adds an entry that is never removed), so the unbounded cost is guaranteed to grow over time. It is also trivially and repeatedly triggerable by any unauthenticated third party at will via a single HTTP GET or gRPC call, requiring no special permissions, since `ListProposalsServlet`/`listProposals` have no offset/limit and no result cap.

### Recommendation
- Cap `getProposalList()` the same way `getPaginatedProposalList` already does (introduce a `PROPOSAL_COUNT_LIMIT_MAX`-based ceiling, or simply deprecate `getProposalList()`/`ListProposals` in favor of forcing callers to use `GetPaginatedProposalList`).
- Apply the same fix to `getWitnessList()` (used by the unbounded `listWitnesses` RPC/HTTP endpoint), enforcing a bound consistent with `getPaginatedNowWitnessList`.
- More generally, audit all `Wallet.java` "list all X" methods that call an underlying `getAllX()` store method without a `getPaginatedX` cap, since the pattern of "unbounded getAllX() reachable via an unauthenticated grpc/http endpoint that also has a properly bounded paginated sibling" is exactly the anti-pattern that caused the referenced Sherlock finding.

### Proof of Concept
1. Observe `chainBaseManager.getProposalStore().getAllProposals()` has no internal limit (confirmed via `ProposalStore.getAllProposals` reference — not independently re-inspected in this pass, but consumed unconditionally by `getProposalList()`).
2. Over the life of a live TRON network, the committee has already created a monotonically increasing number of proposals; call `GET /wallet/listproposals` (or gRPC `WalletApi.listProposals`) repeatedly.
3. Compare with `GET /wallet/getpaginatedproposallist?offset=0&limit=20`, which returns bounded results due to `PROPOSAL_COUNT_LIMIT_MAX` capping in `getPaginatedProposalList` (`framework/src/main/java/org/tron/core/Wallet.java:3275-3304`), demonstrating the unbounded call has no equivalent safeguard.
4. As the store grows further (an inevitability of chain operation, requiring no attacker cost), the unbounded call's cost (iteration + full serialization) grows without bound, exactly mirroring how `BondAggregator.liveMarketsBy`'s cost grew unboundedly with `marketCounter` until it became unusable.

```java
  public ProposalList getPaginatedProposalList(long offset, long limit) {

    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestProposalNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestProposalNum();
    if (latestProposalNum <= offset) {
      return null;
    }
    limit =
        limit > PROPOSAL_COUNT_LIMIT_MAX ? PROPOSAL_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestProposalNum ? latestProposalNum : end;
    ProposalList.Builder builder = ProposalList.newBuilder();

    ImmutableList<Long> rangeList = ContiguousSet
        .create(Range.openClosed(offset, end), DiscreteDomain.longs())
        .asList();
    rangeList.stream().map(ProposalCapsule::calculateDbKey).map(key -> {
      try {
        return chainBaseManager.getProposalStore().get(key);
      } catch (Exception ex) {
        return null;
      }
    }).filter(Objects::nonNull)
        .forEach(proposalCapsule -> builder
            .addProposals(proposalCapsule.getInstance()));
    return builder.build();
```
