### Title
`SortitionState::V1::validate_tenure_change_payload` Only Checks Globally-Accepted Blocks, Allowing a Duplicate Tenure-Change to Be Signed for a Tenure That Already Has a Locally-Accepted Block - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
The v1 signer chainstate's duplicate-tenure-change guard checks only `get_last_globally_accepted_block`, missing blocks that are `LocallyAccepted` or `PreCommitted` in the same tenure. This mirrors the reported bug class: a state-existence check (`get_last_globally_accepted_block`) is used where a stricter "signed activity" check is required, letting an already-signed-but-not-yet-globally-accepted state be treated as if it doesn't exist, and thereby approving an action that should have been rejected.

### Finding Description
`SortitionState` (v1) validates a proposed tenure-change block via `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs`: [1](#0-0) 

This function only calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` to decide whether a duplicate `BlockFound` tenure-change should be rejected. If a block for that tenure exists in the signer's local DB but is only `LocallyAccepted` or `PreCommitted` (i.e., the signer itself has already signed or pre-committed to a tenure-start block for this consensus hash, but that block has not yet gathered enough signatures to become globally accepted), `get_last_globally_accepted_block` returns `None`, and the duplicate-check silently passes.

The codebase's own v2 implementation demonstrates this is a known, previously-exploitable defect class: `validate_tenure_change_payload` in `v2.rs` was changed to use `get_last_signed_block`, which covers both `LocallyAccepted` and globally accepted states: [2](#0-1) 

And the regression test explicitly documents the root cause and the fix rationale: [3](#0-2) 

The v1 code path was never updated with the equivalent fix — it still relies solely on `get_last_globally_accepted_block`, i.e., the "does this tenure-change/duplicate exist" check and the "has this signer already signed something for this tenure" check are inconsistent, exactly the `auctionExists`/`auctionActive` mismatch pattern from the reference report.

### Impact Explanation
Because a signer running v1 chainstate logic will not detect a locally-accepted (already-signed) block in a tenure when a second, different tenure-start proposal (same consensus hash, different content/miner) is submitted, that signer can sign a second, conflicting tenure-start block for the same tenure. If different subsets of signers each sign a different one of the two competing tenure-start blocks (one via the correctly-guarded path, others via the vulnerable v1 path), no single block can reach the full signing threshold cleanly, or worse, two different blocks could independently gather enough signatures from different signer subsets over time, producing a genuine tip disagreement for that tenure. This falls under the "temporary tip disagreement" / minority-triggerable static-validation divergence category, since it requires only that a signer running v1 (or a miner that is aware v1 signers won't reject the duplicate) submit a second tenure-start proposal — not a majority of signers or an admin action.

### Likelihood Explanation
The v1 chainstate/signer path coexists with v2 in this codebase (`stacks-signer/src/chainstate/mod.rs` retains both `SortitionState::V1` and `V2` variants, and `stacks-node/src/tests/signer/multiversion.rs` exercises mixed v1/v2 signer populations), indicating v1 signers can still be active during a protocol version transition. Any miner (unprivileged) can submit a second `BlockFound` tenure-change block for a tenure once an earlier one was only locally-accepted (not yet globally accepted) by v1 signers, e.g., during periods of network delay or partial signature collection, without needing to compromise a majority of signers.

### Recommendation
Update `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use the same signed-block lookup used by v2 (`get_last_signed_block`, or equivalently check both locally-accepted and globally-accepted states) instead of `get_last_globally_accepted_block` alone, so the "block already exists for this tenure" check consistently covers every state in which this signer (or the network) has already committed a signature.

### Proof of Concept
1. Miner A proposes a `BlockFound` tenure-change block B1 for tenure `CH`. A v1 signer signs/locally-accepts B1 via `mark_locally_accepted`, but B1 fails to gather enough total signatures to become globally accepted (e.g., due to network partition/timeout).
2. Miner A (or a colluding miner) proposes a second, different `BlockFound` tenure-change block B2 for the same tenure `CH`.
3. The v1 signer's `validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(&CH)`, which returns `None` (since B1 was only locally accepted), and the duplicate check at [1](#0-0)  passes, allowing the v1 signer to sign B2 as well.
4. If other signers (v2, correctly patched) reject B2 because they already signed B1, while some v1 signers sign B2, the signer set becomes split across two competing tenure-start blocks for the same tenure, producing a temporary tip disagreement — the exact analog of the referenced report's `auctionExists`/`auctionActive` inconsistency being exploited by an unprivileged actor to force an inconsistent/duplicate state transition.
