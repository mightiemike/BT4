The strongest analog to this bug class in java-tron is the Bancor-formula token exchange module, specifically the `ExchangeWithdrawContract` handled by `ExchangeWithdrawActuator`, which removes liquidity from an exchange pool without allowing the caller to specify a minimum acceptable output — exactly the missing-slippage-control pattern described in the report.

### Title
Missing slippage/minimum-output protection in `ExchangeWithdrawActuator` allows liquidity withdrawals to be sandwiched for reduced proceeds - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` lets an exchange's creator withdraw a chosen `quant` of one token from a bancor-style token pair pool, receiving a proportional amount (`anotherTokenQuant`) of the paired token computed from the pool's *current* balances. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced as a minimum-received check, `ExchangeWithdrawContract` has no equivalent minimum-output/slippage field, so the withdrawer has no way to bound the output amount they are willing to accept.

### Finding Description
`ExchangeWithdrawContract` is defined with only `owner_address`, `exchange_id`, `token_id`, and `quant` — no `expected`/minimum field, in contrast to `ExchangeTransactionContract`, which explicitly adds `expected` for this purpose. [1](#0-0) 

In `ExchangeWithdrawActuator.doValidate()`, `anotherTokenQuant` is derived purely from the pool's live `firstTokenBalance`/`secondTokenBalance` ratio at validation time, with only a "not precise enough" rounding check — never a caller-specified floor: [2](#0-1) 

The same ratio-based computation is repeated in `execute()`, which then mutates the pool balances and credits the account with whatever `anotherTokenQuant` was computed: [3](#0-2) 

Because Tron blocks execute transactions sequentially and pool balances are mutated by any preceding `ExchangeTransactionContract` (buy/sell) in the same block, an attacker can submit a trade that skews `firstTokenBalance`/`secondTokenBalance` immediately before the withdrawer's transaction executes (and optionally reverse it afterward), analogous to a Uniswap V3 sandwich attack against `pool.burn`. Since the withdraw actuator has no `amountMin`-style guard, the withdrawer's `anotherTokenQuant` is computed against the manipulated ratio and can be substantially less than the fair, unmanipulated value.

### Impact Explanation
The exchange creator withdrawing liquidity can receive a materially reduced amount of the paired token if their withdrawal is sandwiched by a preceding/following trade against the same `exchange_id` pool, causing a real, quantifiable loss of value to the withdrawer — the same "impermanent loss via missing slippage check" impact described in the report, mapped onto java-tron's own AMM-style `Exchange`/`ExchangeV2` bancor pools.

### Likelihood Explanation
Exploitation requires only ordinary, unprivileged actions: submitting an `ExchangeTransactionContract` against the target pool timed around the victim's `ExchangeWithdrawContract` within the same block, which any account can do. No special privileges are required beyond being the pool creator to trigger a withdrawal at all, and pool trading is fully public. This mirrors the original report's acknowledgment that the attack is limited to sandwiching a specific action lacking output bounds.

### Recommendation
Add a caller-specified minimum output (e.g., an `expected`/`another_token_min` field) to `ExchangeWithdrawContract`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the transaction if the computed `anotherTokenQuant` falls below that caller-supplied floor, mirroring the existing `expected` check already used in `ExchangeTransactionActuator`.
