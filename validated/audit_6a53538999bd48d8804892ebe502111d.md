### Title
Unbounded Recursion in JSON-RPC Request Deserialization Leads to Stack Overflow and Node Process Crash - (File: chain/jsonrpc/src/lib.rs)

### Summary
The nearcore JSON-RPC server deserializes every incoming request body directly into the `Message` type via `axum::extract::Json<Message>`, where `Message` (and its `Request`/`Notification` variants) embed a `serde_json::Value` for `params`. [1](#0-0) [2](#0-1)  `serde_json::Value` deserialization recurses once per level of JSON array/object nesting with no configurable depth limit, mirroring exactly the Scriban `ObjectRecursionLimit`-unbounded rendering recursion described in the report (CWE-674). The only guard in front of this parser is a byte-size cap (`RequestBodyLimitLayer` using `limits_config.json_payload_max_size`, default 10 MiB), which bounds payload size but not nesting depth. [3](#0-2) [4](#0-3) 

### Finding Description
`rpc_handler()` is the single entry point for every JSON-RPC POST request and takes `Json(request): Json<Message>` as an Axum extractor argument, meaning deserialization happens before any application-level validation or routing logic runs. [1](#0-0)  The `Message` enum is `#[serde(untagged)]` and its `Request`/`Notification`/`Batch` variants carry a raw `serde_json::Value` for `params` (and `Batch` is itself `Vec<Message>`), so the untrusted body is walked by serde_json's native recursive descent parser with no `near`-side depth check. [5](#0-4) [2](#0-1) 

The only defense present is `RequestBodyLimitLayer::new(limits_config.json_payload_max_size)`, wired in `create_jsonrpc_app()`, with a default of `10 * 1024 * 1024` bytes (10 MiB). [3](#0-2) [6](#0-5)  This layer only rejects a request whose total body size exceeds the cap — it does not constrain how many nesting levels the bytes encode. A payload consisting almost entirely of repeated `[` characters (`params: [[[[...]]]]`) costs roughly one byte per nesting level, so a 10 MiB body can encode on the order of several million levels of array nesting, comfortably exceeding the recursion depth needed to exhaust a normal thread stack. Unlike an ordinary Rust panic, stack overflow triggers an unrecoverable process abort (SIGSEGV/SIGABRT via the guard page), which is not caught by any `Result`/`catch_unwind` boundary in the Axum/Tokio handler, taking down the entire node process — validator, RPC, and all — exactly as described for the Scriban `StackOverflowException` analog. This differs from the internal, code-owned recursive structures nearcore already defends against elsewhere (e.g. `ReceiptToTx` chain depth capped at `MAX_DEPTH=1000`, trie `print_recursive_internal` bounded by `max_depth`, borsh `NonDelegateAction` breaking action recursion, and finite-wasm's explicit stack-height instrumentation for contract execution) — none of those bounded-recursion mechanisms apply to the untrusted JSON body parsed at the front door of the JSON-RPC server. [7](#0-6) [8](#0-7) [9](#0-8) 

### Impact Explanation
Any unauthenticated caller able to reach the JSON-RPC HTTP endpoint (port 3030 by default, listed explicitly as an in-scope RPC surface) can send a single crafted POST request to crash the node process with a stack overflow before any request-level authentication, method routing, or business logic executes. [10](#0-9)  Because the crash occurs inside the shared Axum/Tokio process that also drives the validator's block production and networking, a validator running the default RPC configuration (`enable_debug_rpc` aside) can be forced offline by an external, unauthenticated request — a transaction-independent but RPC-triggered halt of node availability, consistent with the "Denial of Service" impact class of the reported advisory.

### Likelihood Explanation
Likelihood is high: the JSON-RPC `/` endpoint is enabled by default with no special feature flag, the default body-size limit (10 MiB) is far larger than what is needed to encode enough nesting to overflow a typical 8 MiB thread stack, and no authentication or rate limiting stands between an external caller and the vulnerable deserialization call. Exploitation requires only crafting and sending one HTTP request.

### Recommendation
- Configure `serde_json`'s deserializer with a bounded recursion/nesting limit (or pre-validate nesting depth of the raw bytes before invoking `serde_json::from_slice`/`Json<Message>` extraction) for all externally-reachable JSON-RPC and Rosetta-RPC entry points in `chain/jsonrpc/src/lib.rs` and `chain/jsonrpc-primitives/src/message.rs`.
- Alternatively/additionally, run body deserialization in a context with a small, explicitly bounded stack and treat overflow as a request-scoped error rather than a process-fatal condition (e.g. via `stacker`/guarded execution), so a malicious payload degrades to a rejected request instead of crashing the whole node.
- Apply the same nesting-depth guard to the Rosetta RPC server's JSON parsing path (`chain/rosetta-rpc`), which shares the same unbounded `serde_json::Value` pattern.

### Proof of Concept
```
POST / HTTP/1.1
Host: <node>:3030
Content-Type: application/json
Content-Length: <~10485760>

{"jsonrpc":"2.0","id":1,"method":"status","params":<N million repetitions of "[">...<matching "]">}
```
Where `N` is chosen so the payload stays under `json_payload_max_size` (default 10 MiB) but the nesting depth (roughly one level per byte of `[`) is far beyond what a normal thread stack can support during `serde_json`'s recursive-descent parse invoked by `Json<Message>` extraction in `rpc_handler()`. [1](#0-0)  This causes an uncatchable stack overflow, aborting the entire node process, before the `"method"` field is ever inspected.

## JSON-RPC Server

### Server Startup

The JSON-RPC server uses **Axum**. Startup happens in `start_http()` in `chain/jsonrpc/src/lib.rs`:

1. Creates an Axum `Router` via `create_jsonrpc_app()` with all routes and middleware.
2. Binds a TCP listener on the configured address (default `0.0.0.0:3030`).
3. Spawns the server asynchronously via `FutureSpawner`.

The socket is bound eagerly (before spawning), so callers can be sure the server is reachable once `start_http()` returns.
