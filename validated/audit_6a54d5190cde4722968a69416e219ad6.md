### Title
Reentrancy through malicious `<ft-trait>` in `collateral-add` lets a stale `insert` overwrite a reentrant `collateral-remove`'s mask update, corrupting the disabled-mask bit and permanently bricking `get-position` for the account - (mainnet/contracts/market/v0-market-vault.clar)

### Summary
`collateral-add` computes `updated-entry` (with the new mask) inside its `let` block, then calls `receive-tokens` (which invokes the caller-supplied `<ft-trait>`'s `transfer`) before finally calling `insert` to persist that pre-computed entry. Because the attacker's own token contract can reenter the protocol during that `transfer` callback and successfully complete a `collateral-remove` (including its own `insert`) on the same account before the outer `insert` runs, the outer call's stale `updated-entry` silently overwrites the reentrant `collateral-remove`'s mask change when it finally commits.

### Finding Description
Sequence for account with an existing registry entry `{id:5, account, mask:M0}` (bit X set for existing collateral, none for Y yet):

1. Attacker's transaction calls the market impl, which calls `collateral-add(account, amount, ft, asset-id=Y)` on `v0-market-vault.clar`.
2. In `collateral-add`'s `let` (lines 375-381): `entry = resolve-or-create(account)` reads `registry`/`reverse` (no write - `create` only builds a struct, see lines 143-157). `mask = M0`. `updated-mask = mask-update(M0, Y, true, true) = M1`. `updated-entry = merge entry (refresh M1)` is bound **now**, capturing `M1` computed from the stale `M0`. `add-user-collateral` writes the `collateral` map immediately (line 198-203).
3. `try! (receive-tokens ft amount account)` (line 387) calls `contract-call? ft transfer ...` (line 257) - `ft` is the attacker's own malicious contract.
4. Inside that `transfer` callback, the attacker reenters via the market impl's withdraw path, which calls `collateral-remove(account, amount=all-of-X, ft-x, asset-id=X, recipient=attacker)` on the vault.
5. `collateral-remove`'s `let` (lines 407-415) reads `entry = resolve(account)` → still `mask=M0` (correct at that instant, since the outer `insert` has not run). `remove-user-collateral` zeroes/deletes the `collateral` map entry for X (lines 205-214). `updated-mask = mask-update(M0, X, true, false) = M2` (clears bit X). `updated-entry = merge entry (refresh M2)`.
6. `insert(updated-entry)` at line 421 commits `map-set registry 5 {mask: M2, ...}` - bit X correctly cleared, bit Y not yet present. `send-tokens` transfers asset X out to the attacker (line 422) and the reentrant call returns `(ok 0)`.
7. Control returns up through `ft.transfer` → `receive-tokens` → the outer `collateral-add`, which now executes `insert(updated-entry)` at line 389, where `updated-entry` still equals the value computed in step 2: `mask = M1 = M0 | bit(Y)`. This `map-set registry 5 {mask: M1, ...}` **overwrites** the reentrant call's `mask=M2`, restoring bit X even though the corresponding `collateral` map entry for X was deleted in step 5.

Root cause: `updated-entry` is bound early in the `let` (before the reentrancy-vulnerable external call at line 387) and is never re-derived from the current on-chain mask after that call returns; `insert` (lines 159-169) performs an unconditional `map-set` with no compare-and-swap/guard against concurrent mutation of the same registry id.

No later check recovers this: `insert` has no versioning/CAS, and the outer transaction does not re-read `registry` after the reentrant call before writing.

### Impact Explanation
After the transaction, the account's registry entry has `mask` bit X set while the corresponding `collateral{id, asset:X}` map entry is deleted. `get-collateral` (line 296-297) is defined as `(unwrap-panic (map-get? collateral {...}))`, so any subsequent call to `lookup-collateral`/`get-position` (lines 299-333) - which any market-impl operation (borrow, health-factor check, withdrawal validation, etc.) depends on to evaluate the account's collateral - will always try to look up the now-deleted asset-X collateral entry and hit `unwrap-panic`, aborting the transaction. This permanently bricks any protocol operation on that account that requires reading its position, effectively freezing the account's remaining collateral (asset Y and any other collateral) behind an unusable position. This meets the in-scope "permanent freezing of funds" category; the question frames it as High, but the practical blast radius (permanently unusable account state via unconditional panic) argues for Critical.

### Likelihood Explanation
Fully attacker-controlled and repeatable: the attacker uses their own account, supplies their own malicious `<ft-trait>` implementation as the collateral asset for `collateral-add`, and uses their own already-registered account with existing collateral in another asset. No privileged role, oracle, or second party is needed - only a normal `collateral-add` call plus a self-authored token contract that reenters via the market impl's withdraw entry point during the `transfer` callback. This is a single transaction, single-user interleaving, fully deterministic given Clarity's evaluation order (the `let` binds `updated-entry` before the `try!` on `receive-tokens`, so the interleaving is guaranteed, not probabilistic).

### Recommendation
Do not compute `updated-entry`/`updated-mask` before external calls that can reenter. Re-read `registry`/`mask` immediately before the final `insert` (right after `receive-tokens`/`send-tokens` returns), or add a reentrancy guard (e.g., a per-account or global lock data-var checked/set at function entry and cleared at exit) around `collateral-add`, `collateral-remove`, `debt-add-scaled`, and `debt-remove-scaled` so that a reentrant call cannot execute while an outer mutating call is still pending its own `insert`.

### Proof of Concept
Clarinet simnet plan:
1. Deploy a malicious `ft-trait` implementation contract `evil-ft` whose `transfer` function, when called with a specific flag/amount, calls back into the market impl's collateral-withdraw entry point for `asset-id=X`, `amount=<full X balance>`, recipient=attacker.
2. As the attacker account, first call `collateral-add` with a legitimate asset X and amount, establishing a registry entry with `mask` bit X set (no reentrancy needed here).
3. Call `collateral-add(account, amount, evil-ft, asset-id=Y)`. Inside `receive-tokens`'s call to `evil-ft.transfer`, trigger the reentrant `collateral-remove(account, full-X-amount, real-ft-x, asset-id=X, recipient=attacker)` through the market impl.
4. After the outer `collateral-add` transaction completes, call `get-position(account, enabled-mask)` (or any market-impl function depending on it) and assert it aborts with a runtime panic (unwrap-panic failure) because `collateral{id, asset:X}` is deleted while `mask` still has bit X set.
5. Confirm via `map-get? registry id` that `mask` includes bit X (stale) and bit Y (from the outer call), demonstrating the reentrant `collateral-remove`'s mask clearing of bit X was discarded by the outer `insert`.
