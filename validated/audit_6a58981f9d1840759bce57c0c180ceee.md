### Title
`ensure_match_transaction_info` silently skips checkpoint-hash verification, letting replay-verify tooling report success while the position/state Merkle root diverges - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the integrity gate used by `storage/db-tool/src/replay_on_archive.rs` (and other replay tools) to confirm that a locally re-executed transaction matches the authenticated `TransactionInfo` pulled from a backup/archive. It checks status, gas, write-set hash, and event-root hash, but — per its own inline `TODO(trading-native)` comment — it never checks `state_checkpoint_hash`, `hot_state_checkpoint_hash`, or `position_state_checkpoint_hash`. This is analogous to the `rescue()` bug: a check that is supposed to gate an operation (accepting a replayed/committed result as valid) has an unguarded bypass path, so a corrupted checkpoint root sails through as "verified."

### Finding Description
`ensure_match_transaction_info` at [1](#0-0)  validates four fields (status, gas_used, write_set hash, event_root hash) but has an explicit acknowledged gap: [2](#0-1) 

This means the checkpoint-hash fields carried in `TransactionInfo` — `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and the newly added `position_state_checkpoint_hash` — are never cross-checked against the locally recomputed roots produced by `DoStateCheckpoint`/`DoLedgerUpdate` (`execution/executor/src/workflow/do_state_checkpoint.rs`, `execution/executor/src/workflow/do_ledger_update.rs`).

`storage/db-tool/src/replay_on_archive.rs::execute_and_verify` calls exactly this function as its sole correctness gate after re-executing a chunk from backup data: [3](#0-2) . If it returns `Ok(())`, the tool advances and reports the chunk as verified.

Because `write_set_hash` only covers the per-transaction write set (not the accumulated Jellyfish Merkle root over all state, which is calculated periodically at checkpoints), a discrepancy in checkpoint/root computation — e.g. a bug in `NativeStateCommitter::apply` (`storage/aptosdb/src/native_state_committer.rs:60-141`), `PositionLedgerStateWithSummary::extend`, or any logic feeding `DoStateCheckpoint::get_position_checkpoint_hashes` (`execution/executor/src/workflow/do_state_checkpoint.rs:98-234`) — would not be caught by replay-verify at all, even though every individual write op matches.

### Impact Explanation
Replay-verify / archive-replay is one of the primary tools operators and auditors use to confirm that historical mainnet data is internally consistent and that no node (or hostile archive provider) has served tampered committed state. Because the checkpoint hash comparison is a no-op, this tool can certify a chain segment as "correctly replayed" even when:
- The position-state Jellyfish Merkle root diverges from what local VM execution would produce (a hard-fork-class divergence in the trading-native subsystem).
- The state or hot-state checkpoint root is wrong.

This directly matches the "Committed state that differs from the correct VM result... accepted as valid" and "Authenticated API or state-view output bound to the wrong version/root" impact categories: a corrupted or maliciously altered checkpoint root state committed to a backup archive is accepted as valid by the verification tool, undermining downstream trust decisions (auditors, node operators using `replay_on_archive` to validate a bootstrap source, or CI-based invariant checks) even though no cryptographic or execution safeguard actually holds.

### Likelihood Explanation
Low-to-moderate. This requires either (a) an existing bug elsewhere in checkpoint-root computation (e.g., in the still-in-development trading-native/position-state feature, which is gated behind `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) or (b) a maliciously supplied archive with tampered `TransactionInfo.position_state_checkpoint_hash`/`state_checkpoint_hash` combined with a normal-looking write set. The code comment itself flags this as a known, deliberate gap ("Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS"), indicating the authors are aware the feature is unsafe to enable as-is. No unprivileged network attacker is required — this is a verification-tool integrity gap, not a consensus-safety bug, so likelihood is bounded by how much replay-verify results are relied upon before the feature is fully wired in.

### Recommendation
Extend `ensure_match_transaction_info` to recompute and compare `state_checkpoint_hash`, `hot_state_checkpoint_hash`, and `position_state_checkpoint_hash` whenever they are present in `txn_info`, mirroring the checks already done for `write_set_hash`/`event_root_hash`. At minimum, gate `COMPUTE_TRADING_NATIVE_STATE_ROOTS` from being enabled until this validation is implemented, as the existing TODO comment recommends.

### Proof of Concept
1. Enable the trading-native position-state feature (`compute_trading_native_state_roots` / `COMPUTE_TRADING_NATIVE_STATE_ROOTS`) so `TransactionInfo` carries a `position_state_checkpoint_hash`.
2. Introduce (or have) a divergence between the recomputed position-state Merkle root and the archived `TransactionInfo.position_state_checkpoint_hash` (e.g., via a bug in `NativeStateCommitter::apply`/`PositionLedgerStateWithSummary::extend`, or by tampering with a backup's serialized `TransactionInfo`).
3. Run `db-tool replay-on-archive` over the affected version range. `execute_and_verify` calls `ensure_match_transaction_info` with the tampered/incorrect `expected_txn_info`; since status/gas/write_set_hash/event_root_hash still match, the function returns `Ok(())` and the tool reports zero failures for that chunk, despite the checkpoint root being wrong.

Note: I could not verify at what stage `COMPUTE_TRADING_NATIVE_STATE_ROOTS` is currently enabled/disabled on mainnet (the feature appears to still be under active development per the surrounding TODOs), so the current exploitability window on production mainnet data is uncertain and should be confirmed before treating this as an immediately live issue.

    pub fn ensure_match_transaction_info(
        &self,
        version: Version,
        txn_info: &TransactionInfo,
        expected_write_set: Option<&WriteSet>,
        expected_events: Option<&[ContractEvent]>,
    ) -> Result<()> {
        const ERR_MSG: &str = "TransactionOutput does not match TransactionInfo";

        let expected_txn_status: TransactionStatus = txn_info.status().clone().into();
        ensure!(
            self.status() == &expected_txn_status,
            "{}: version:{}, status:{:?}, auxiliary data:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.status(),
            self.auxiliary_data(),
            expected_txn_status,
        );

        ensure!(
            self.gas_used() == txn_info.gas_used(),
            "{}: version:{}, gas_used:{:?}, expected:{:?}",
            ERR_MSG,
            version,
            self.gas_used(),
            txn_info.gas_used(),
        );

        let write_set_hash = CryptoHash::hash(self.write_set());
        ensure!(
            write_set_hash == txn_info.state_change_hash(),
            "{}: version:{}, write_set_hash:{:?}, expected:{:?}, write_set: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            write_set_hash,
            txn_info.state_change_hash(),
            self.write_set,
            expected_write_set,
        );

        let event_hashes = self
            .events()
            .iter()
            .map(CryptoHash::hash)
            .collect::<Vec<_>>();
        let event_root_hash = InMemoryEventAccumulator::from_leaves(&event_hashes).root_hash;
        ensure!(
            event_root_hash == txn_info.event_root_hash(),
            "{}: version:{}, event_root_hash:{:?}, expected:{:?}, events: {:?}, expected(if known): {:?}",
            ERR_MSG,
            version,
            event_root_hash,
            txn_info.event_root_hash(),
            self.events(),
            expected_events,
        );

        // TODO(trading-native): this comparator ignores the checkpoint hashes
        // (state/hot-state and `position_state_checkpoint_hash`), so replay-verify
        // tooling (e.g. db-tool's `replay_on_archive`) can report a successful
        // replay even when the authenticated position state root diverges from
        // local execution. Validate the checkpoint hashes here before enabling
        // COMPUTE_TRADING_NATIVE_STATE_ROOTS.
        Ok(())
    }
