### Title
Silent Transaction Drop with False `ValidTx` Response When Pool Is Full — (`File: chain/client/src/rpc_handler.rs`)

---

### Summary

When the transaction pool is at capacity, `process_tx_internal` silently discards a validated transaction but continues execution and returns `ProcessTxResponse::ValidTx` to the caller. The RPC layer interprets this as a successful submission, begins polling for the transaction's on-chain status, and ultimately times out. The transaction is permanently lost with no actionable error returned to the user.

---

### Finding Description

In `chain/client/src/rpc_handler.rs`, `process_tx_internal` handles the result of `pool.insert_transaction` with a `match` block: [1](#0-0) 

The `InsertTransactionResult::NoSpaceLeft` arm emits only a `tracing::trace!` log and **does not return**. Execution falls through to the `active_validator` check: [2](#0-1) 

When the node is an active validator (chunk producer) for the transaction's shard, it returns `Ok(ProcessTxResponse::ValidTx)` even though the transaction was never inserted into the pool.

The pool enforces a hard byte-size ceiling: [3](#0-2) 

Once that ceiling is reached, every subsequent insertion returns `NoSpaceLeft`. The pool does not evict lower-priority transactions; it simply rejects new ones.

The RPC layer in `send_tx` treats `ValidTx` as a successful submission and enters the polling loop: [4](#0-3) 

`tx_status_fetch` polls `ViewClientActor` on every new block until the configured timeout (default 10 s): [5](#0-4) 

Because the transaction was never inserted into the pool it will never appear on chain, so the poll always returns `NotObserved` or `DoesNotTrackShard`, and the call ultimately resolves to `RpcTransactionError::TimeoutError`.

The `send_tx_async` (`broadcast_tx_async`) path is even more opaque: the fire-and-forget send returns the transaction hash immediately with no indication of pool rejection: [6](#0-5) 

---

### Impact Explanation

The broken invariant is: *"a `ValidTx` response guarantees the transaction has been accepted into the mempool and will be scheduled for execution."* When the pool is full this invariant is violated. The transaction is permanently lost — it will not be retried, forwarded, or queued — yet the caller receives a success signal. Any contract interaction, token transfer, or staking action carried by that transaction silently fails to execute. This constitutes **contract execution flow breakage** reachable from ordinary user-submitted transactions.

---

### Likelihood Explanation

The pool size limit is a configurable byte ceiling (`total_transaction_size_limit`). Under sustained high load the pool fills naturally. An adversary can also deliberately saturate the pool by submitting many large, valid transactions from accounts they control, causing victim transactions submitted immediately after to be silently dropped. No privileged access is required; any account with sufficient balance to pay fees can trigger this condition.

---

### Recommendation

1. **Return an explicit error on `NoSpaceLeft`**: The `NoSpaceLeft` arm should return `Ok(ProcessTxResponse::InvalidTx(InvalidTxError::TransactionSizeExceeded))` or a dedicated `PoolFull` variant so the RPC layer can surface a clear, retryable error to the caller instead of a false `ValidTx`.

2. **Eviction policy**: Consider evicting the lowest-fee transaction when the pool is full rather than rejecting the incoming one, to preserve liveness under load.

3. **Async path**: `send_tx_async` should at minimum log a warning at `warn` level (not `trace`) when a transaction is dropped due to pool overflow, so operators can detect the condition.

---

### Proof of Concept

1. Configure a node as a chunk producer with a small `total_transaction_size_limit` (e.g., 1 byte, forcing immediate overflow).
2. Submit any valid `SignedTransaction` via `broadcast_tx_commit` (which calls `send_tx` with `wait_until: ExecutedOptimistic`).
3. `process_tx_internal` reaches `InsertTransactionResult::NoSpaceLeft`, logs at trace level, falls through, and returns `ValidTx`.
4. `send_tx` enters `tx_status_fetch` and polls until the 10-second timeout.
5. The RPC response is `RpcTransactionError::TimeoutError` — not a pool-full error — and the transaction never appears on chain.
6. Repeating the submission with a fresh nonce produces the same result indefinitely as long as the pool remains full.
