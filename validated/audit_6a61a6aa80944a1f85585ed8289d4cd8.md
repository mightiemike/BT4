### Title
Griefing via unweighted per-contract dynamic energy factor allows any caller to spike other users' TVM execution costs - ([File: chainbase/src/main/java/org/tron/core/capsule/ContractStateCapsule.java])

### Summary
The TVM "dynamic energy" congestion-pricing feature raises the per-opcode energy cost multiplier for *all* callers of a smart contract based on a single, unweighted aggregate metric: total energy consumed by *any* caller of that contract in the current cycle. Because this aggregate has no per-caller weighting or cost-proportional counterbalance, any unprivileged account can cheaply spend its own energy invoking a target contract to push the cycle's aggregate usage above `dynamicEnergyThreshold`, causing the contract-wide penalty factor to escalate for every subsequent caller — exactly the "shared aggregate statistic manipulated by one actor to raise a shared price for everyone else" pattern described in the Ajna report (there: `Debt/(LUP*Collateral)` EMA; here: per-contract cycle `energyUsage` vs `dynamicEnergyThreshold`).

### Finding Description
When `allowDynamicEnergy` is enabled, `Program.updateContextContractFactor()` looks up (or creates) a `ContractStateCapsule` keyed by the *target contract address* and calls `catchUpToCycle()`: [1](#0-0) 

`ContractStateCapsule.catchUpToCycle()` compares that contract's aggregate `energyUsage` (summed across all callers in the prior cycle) against a fixed `threshold`, and if exceeded, multiplicatively raises `energyFactor` for the *whole contract*, decaying it only slowly afterward: [2](#0-1) 

The aggregate `energyUsage` is accumulated per execution with no attribution or weighting by caller — `addContextContractUsage()` simply adds the caller's own energy usage to the shared counter for that contract address: [3](#0-2) [4](#0-3) 

Once the contract's `energyFactor` exceeds `DYNAMIC_ENERGY_FACTOR_DECIMAL`, every opcode executed by *any* caller of that contract (not just the attacker) is charged a penalty proportional to the factor, and CALL-type opcodes are further penalized via `getCalculateCallCost()`: [5](#0-4) [6](#0-5) 

This is structurally identical to the Ajna bug: a single, unweighted aggregate (there, EMA of pool-wide `Debt/(LUP*Collateral)`; here, per-contract cycle `energyUsage`) determines a punitive multiplier (there, the interest rate; here, `energyFactor`) that is applied uniformly to *all* participants sharing the resource (borrowers of the pool / callers of the contract), and the metric can be pushed past its threshold by one actor spending resources that are disproportionate to the damage inflicted on everyone else, because the aggregation performs no per-actor cost weighting.

### Impact Explanation
An attacker who is not privileged in any way can repeatedly call a victim's deployed smart contract with energy-heavy but otherwise harmless calls to drive that contract's per-cycle `energyUsage` above `dynamicEnergyThreshold`. Once triggered, `catchUpToCycle()` increases `energyFactor` by `increasePercent = 1 + increaseFactor/precision` per elapsed cycle the usage stays over threshold, while the decrease path decays it by `pow(1 - increaseFactor/(DYNAMIC_ENERGY_DECREASE_DIVISION*precision), cycleCount)` — an intentionally asymmetric ramp where escalation is fast and recovery is slow. Because the increase is applied to the whole contract's opcode pricing, all legitimate users interacting with that contract subsequently pay inflated energy fees (or run out of energy / hit `OutOfEnergyException` in `EnergyCost.getCalculateCallCost`), degrading or effectively disabling normal use of the contract — a direct availability/economic-griefing impact on unprivileged users of that contract, mirroring the pool-disabling impact in the Ajna report.

### Likelihood Explanation
The attack requires only: (1) the chain/committee has enabled `allowDynamicEnergy` (a committee-governed but not caller-privileged feature — see `ProposalService.process` case `ALLOW_DYNAMIC_ENERGY`), and (2) the attacker sends ordinary transactions calling the target contract, paying for their own energy at the standard `SUN_PER_ENERGY` rate. No special role, permission, or large capital is required — only enough TRX/energy to exceed the (committee-configured, potentially low) `dynamicEnergyThreshold` for one contract in one cycle, which is comparable in spirit to Bob's low-cost WBTC deposit in the original report. This is a plausible, reachable, unprivileged-actor griefing vector, though its practical severity depends on the specific values chosen for `dynamicEnergyThreshold` / `dynamicEnergyIncreaseFactor` / `dynamicEnergyMaxFactor`, which I could not fully enumerate from the index (the exact numeric defaults in `common/src/main/java/org/tron/core/Constant.java` were not retrievable within available tool calls).

### Recommendation
Apply the same remediation principle Sherlock recommended for Ajna: stop weighting the congestion metric purely by raw aggregate usage, and instead weight/attribute energy usage by caller (e.g., cap or discount the contribution of any single caller/address to a contract's per-cycle `energyUsage`, or require the penalty to scale with a caller-diversity metric rather than a single unweighted sum) in `ContractStateCapsule.catchUpToCycle()` / `Program.addContextContractUsage()`. This would prevent a single account from unilaterally driving the shared `energyFactor` above levels the actual (diverse) caller population would produce, raising the cost of griefing proportionally to the fraction of legitimate traffic the attacker would need to dominate.

### Proof of Concept
1. Assume `allowDynamicEnergy = 1` is active (committee proposal) with some `dynamicEnergyThreshold = T`.
2. Deploy or select any target contract `C` with normal, low legitimate traffic such that its typical per-cycle `energyUsage` is well below `T`.
3. Attacker repeatedly calls `C` (e.g., via a cheap loop-triggering entrypoint) in a single cycle until cumulative `energyUsage` recorded in `ContractStateCapsule` for `C` exceeds `T` — see accumulation path: `VM.play()` → `program.addContextContractUsage(energyUsage)` → `ContractStateCapsule.addEnergyUsage()`. [7](#0-6) 
4. On the next cycle boundary, any caller's `Program.updateContextContractFactor()` invokes `catchUpToCycle()`, which detects `getEnergyUsage() > threshold` and raises `energyFactor` for contract `C`. [8](#0-7) 
5. All subsequent legitimate callers of `C` in that cycle now pay `energy * factor / DYNAMIC_ENERGY_FACTOR_DECIMAL` per opcode instead of the normal cost, per `VM.play()`'s penalty branch, potentially causing their transactions to run out of energy. [9](#0-8) 
6. The attacker can repeat step 3 with minimal follow-up traffic each cycle to keep `energyUsage` above `T`, sustaining the elevated `energyFactor` indefinitely (since decrease decay is intentionally slower than increase), analogous to Bob leaving a small residual collateral in the Ajna scenario to keep the manipulated rate elevated.

  public long updateContextContractFactor() {
    ContractStateCapsule contractStateCapsule =
        contractState.getContractState(getContextAddress());

    if (contractStateCapsule == null) {
      contractStateCapsule = new ContractStateCapsule(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber());
      contractState.updateContractState(getContextAddress(), contractStateCapsule);
    } else {
      if (contractStateCapsule.catchUpToCycle(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber(),
          VMConfig.getDynamicEnergyThreshold(),
          VMConfig.getDynamicEnergyIncreaseFactor(),
          VMConfig.getDynamicEnergyMaxFactor(),
          VMConfig.allowStrictMath(),
          VMConfig.disableJavaLangMath())) {
        contractState.updateContractState(getContextAddress(), contractStateCapsule
        );
      }
    }
    contextContractFactor = contractStateCapsule.getEnergyFactor()
        + Constant.DYNAMIC_ENERGY_FACTOR_DECIMAL;
    return contextContractFactor;
  }

  public boolean catchUpToCycle(
      long newCycle, long threshold, long increaseFactor, long maxFactor,
      boolean useStrictMath, boolean disableMath
  ) {
    long lastCycle = getUpdateCycle();

    // Updated within this cycle
    if (lastCycle == newCycle) {
      return false;
    }

    // Guard judge and uninitialized state
    if (lastCycle > newCycle || lastCycle == 0L) {
      reset(newCycle);
      return true;
    }

    final long precisionFactor = DYNAMIC_ENERGY_FACTOR_DECIMAL;

    // Increase the last cycle
    // fix the threshold = 0 caused incompatible
    if (getEnergyUsage() > threshold) {
      lastCycle += 1;
      double increasePercent = 1 + (double) increaseFactor / precisionFactor;
      this.contractState = ContractState.newBuilder()
          .setUpdateCycle(lastCycle)
          .setEnergyFactor(min(
              maxFactor,
              (long) ((getEnergyFactor() + precisionFactor) * increasePercent) - precisionFactor,
              disableMath))
          .build();
    }

    // No need to decrease
    long cycleCount = newCycle - lastCycle;
    if (cycleCount <= 0) {
      return true;
    }

    // Calc the decrease percent (decrease factor [75% ~ 100%])
    double decreasePercent = pow(
        1 - (double) increaseFactor / DYNAMIC_ENERGY_DECREASE_DIVISION / precisionFactor,
        cycleCount, useStrictMath
    );

    // Decrease to this cycle
    // (If long time no tx and factor is 100%,
    //  we just calc it again and result factor is still 100%.
    //  That means we merge this special case to normal cases)
    this.contractState = ContractState.newBuilder()
        .setUpdateCycle(newCycle)
        .setEnergyFactor(max(
            0,
            (long) ((getEnergyFactor() + precisionFactor) * decreasePercent) - precisionFactor,
            disableMath))
        .build();

    return true;
  }
