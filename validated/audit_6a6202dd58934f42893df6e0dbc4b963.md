### Title
Unbounded blocking of `server.Receive` on `parallelExecutor.ExecuteTask` while holding `receiveLock` allows a single DON member to serialize/starve the entire ExecutableCapabilityServer - ([File: core/capabilities/remote/executable/server.go])

### Summary
`server.Receive` acquires `r.receiveLock` for the entire duration of message processing, including the synchronous call to `r.parallelExecutor.ExecuteTask`, which blocks until a slot in the fixed-size `taskSemaphore` (`cap = ServerMaxParallelRequests`) becomes free. Because the semaphore is shared across all `CallerDonId`s and never grows, and there is no per-request timeout applied to the blocking `select` inside `ExecuteTask` (the `ctx` passed comes from the long-lived dispatcher receive-loop context, not a per-message deadline), a caller who submits more concurrent unique `MessageId`/payload combinations than `ServerMaxParallelRequests`, each backed by a slow underlying capability call, can keep all semaphore slots occupied and additionally block `Receive` itself on `receiveLock`, starving all other callers (including legitimate DONs) from having their messages processed at all.

### Finding Description
- `server.Receive` (`core/capabilities/remote/executable/server.go:243-321`) takes `r.receiveLock.Lock()` at the top and holds it via `defer` for the whole function body [1](#0-0) .
- Each unique combination of `messageID + hash(payload)` produces a new `requestID` and a new `request.ServerRequest`, so an attacker sending unique message IDs/payloads is not deduplicated [2](#0-1) .
- The call `r.parallelExecutor.ExecuteTask(ctx, ...)` is made synchronously inside `Receive`, still holding `receiveLock` [3](#0-2) .
- `ExecuteTask` blocks in a `select` until a slot is available in `t.taskSemaphore` (capacity fixed at `ServerMaxParallelRequests`, set once at `Start` and never resized), the executor stops, or `ctx` is done [4](#0-3) ; the semaphore is shared globally across all `CallerDonId`s, with no per-DON quota [5](#0-4) .
- The `ctx` passed to `Receive` (and thus to `ExecuteTask`) originates from the dispatcher's long-lived receive-loop context (`d.stopCh.NewCtx()` in `dispatcher.receive`), not a per-request timeout, so `ExecuteTask` will block until a slot frees or the whole dispatcher/service stops — not until any individual request expires.
- Because `Receive` holds `receiveLock` while blocked inside `ExecuteTask`, no further messages (from any DON, including for unrelated/legitimate requests, and including replies that would otherwise let in-flight requests complete) can be processed by this server instance until that call unblocks, and `expireRequests` (`core/capabilities/remote/executable/server.go:223-241`) — which also needs `receiveLock` — cannot run either, so timeout-based cleanup of stuck requests is itself blocked.
- Mitigating factor: messages first pass through `dispatcher.handleMessage`, which applies a per-sender token-bucket rate limit (`PerSenderRPS`/`PerSenderBurst`, default 10 RPS / 50 burst) [6](#0-5) . This limits sustained throughput from a single peer but does not prevent a burst (up to `PerSenderBurst`, default 50) of distinct unique-payload `Execute` messages from occupying all semaphore slots if `ServerMaxParallelRequests` is configured below that burst size, and it does not stop the `receiveLock` from being held for the duration of processing each admitted burst message with a slow underlying capability. The rate limiter is per network sender (peer), and a DON member typically maps to a single peer identity, so this does not fully neutralize the described flooding vector, though it does bound its rate.

### Impact Explanation
If exploited, a single DON member can cause the local node's `ExecutableCapabilityServer` to stop processing `Execute` messages for all callers (legitimate DONs included) for as long as the attacker keeps the semaphore/`receiveLock` occupied with slow underlying-capability calls — effectively a denial-of-service of a shared capability server on the node, not scoped to the attacker's own DON. This matches a "griefing/DoS of a subsystem shared across DONs" impact category rather than fund loss or auth bypass; severity is bounded by the fact that it affects a single node's server instance and is bounded by dispatcher per-sender rate limiting and eventual `RequestTimeout`-based expiry (once `receiveLock` becomes available again).

### Likelihood Explanation
Requires only that the attacker be a legitimate member of a workflow DON registered against the capability (no special privilege beyond DON membership), and that they can trigger the underlying capability to run slowly (or hold up the `fn` passed to `ExecuteTask`). Feasibility is throttled by the dispatcher per-sender rate limiter (default burst 50, 10 RPS refill) and by `ServerMaxParallelRequests`/`RequestTimeout` configuration; if `ServerMaxParallelRequests` is smaller than the sender burst allowance, an attacker can still exhaust the semaphore within a single allowed burst. Full verification of default `ServerMaxParallelRequests` value in this codebase could not be completed within the available searches — this should be confirmed before treating the finding as immediately practical against default configuration.

### Recommendation
- Do not hold `receiveLock` while calling `ExecuteTask`: dispatch/enqueue the task asynchronously (e.g., via a bounded per-request goroutine or worker queue) and release `receiveLock` before or independent of blocking on the semaphore, so message intake/`expireRequests` are never blocked by executor backpressure.
- Bound `ExecuteTask`'s wait with the request's own `RequestTimeout` (derive a per-call context deadline) rather than relying solely on the long-lived dispatcher context, so a full semaphore causes bounded rejection/timeout instead of indefinite blocking.
- Consider per-`CallerDonId` fairness/quotas on `taskSemaphore` (e.g., per-DON sub-limits or weighted fair scheduling) so that no single DON can occupy the entire shared capacity.

### Proof of Concept
Integration test in `core/capabilities/remote/executable`:
1. Construct a `server` with `ServerMaxParallelRequests = 1` (or small N) and `RequestTimeout` set to a short duration, with `underlying.Execute` implemented to block until a test-controlled channel is closed.
2. From `CallerDonId = A`, call `server.Receive` concurrently with `N+1` distinct `MessageId`/payload combinations (unique `messageID+hash(payload)` per call), each triggering the slow `underlying.Execute`.
3. From `CallerDonId = B` (a second, legitimate DON), call `server.Receive` with a normal, fast request after step 2 starts.
4. Assert that DON B's request does not get processed (its `OnMessage`/response callback is never invoked) until well after `RequestTimeout` has elapsed and/or until the attacker's slow calls are released — demonstrating that `receiveLock` contention plus semaphore exhaustion starves an unrelated DON's legitimate request beyond `RequestTimeout`.
5. Additionally assert that `expireRequests` (ticker-driven) does not run/cannot clean up expired requests while `Receive` is blocked inside `ExecuteTask`, confirming the `receiveLock` contention compounds the semaphore exhaustion.

func (t *ParallelExecutor) ExecuteTask(ctx context.Context, fn func(ctx context.Context)) error {
	select {
	case t.taskSemaphore <- struct{}{}:
		t.recordSlotUsage(ctx)
		stopped := !t.IfNotStopped(func() {
			t.wg.Go(func() {
				ctxWithStop, cancel := t.stopChan.Ctx(ctx)
				defer func() {
					<-t.taskSemaphore
					t.recordSlotUsage(ctxWithStop)
					cancel()
				}()
				fn(ctxWithStop)
			})
		})

		if stopped {
			return errors.New("executor stopped")
		}
	case <-t.stopChan:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}

	return nil
}
