### Title
Pausing `accrue` Lets `system-repay` Extinguish Debt Using a Stale Interest Index, Permanently Losing Owed Yield - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The `accrue` pause flag in the Zest lending vaults is implemented as a pass-through instead of a revert: when `accrue` is marked paused, `next-index`/`next-liquidity-index` silently return the *current* (stale) index instead of computing the up-to-date one, and `last-update` is left untouched. [1](#0-0)  Because the `borrow`/`repay` pause flags are independent booleans from `accrue` in the same `pause-states` tuple, `system-repay` keeps operating while `accrue` is paused, computing `debt` from the frozen index. [2](#0-1)  A borrower who fully repays while `accrue` is paused zeroes out `principal-scaled`, so the interest that should have accrued during the paused window is never captured for that position — even though the index is later updated to "catch up," `total-debt = scaled_principal * index` is `0 * anything = 0`, permanently discarding the reserve/LP share of that interest.

### Finding Description
`accrue` is defined to check `pause-states` and, when `accrue` is paused, return `{index: idx, lindex: lidx}` unchanged rather than reverting: [3](#0-2) . The helper functions it depends on, `next-index` and `next-liquidity-index`, implement the same pass-through: if `(get accrue states)` is true they return the stored `idx`/`lidx` directly and skip the `time-delta`/`interest-rate` computation entirely, meaning `last-update` is never advanced either. [1](#0-0) 

`system-repay` calls `(try! (accrue))` first, then reads `idx (var-get index)` and `debt (total-debt)` directly from vars — while `accrue` is paused, both of these reflect the stale, un-accrued index. [4](#0-3)  The `repay` pause flag is a separate boolean from `accrue` in `pause-states`, so an admin/DAO pausing `accrue` alone (e.g., during an oracle/rate-model issue) does not stop `system-repay` from executing. [2](#0-1)  A borrower can then submit a full repayment sized to the stale (understated) `debt`, which reduces `principal-scaled` to zero via `capped-reduction`. [5](#0-4)  Once `principal-scaled` is `0`, no future index update (however large, once `accrue` is later unpaused and the deferred `time-delta` is applied) can recover that borrower's owed interest, because `total-debt` is computed as `principal-scaled * index`, which stays `0`. [6](#0-5)  The same pattern is repeated identically across `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`, and `v0-vault-ststxbtc.clar`.

This mirrors the reported bug class exactly: a "pause" that is meant to gate a sensitive computation instead silently passes stale values through, and a later, independently-gated mutation (`system-repay`) consumes those stale values to permanently close out a position before the deferred effect (the accrued interest) can ever be applied.

### Impact Explanation
Any interest that accrues during a window where `accrue` is paused but `repay` is not is permanently lost for positions that are fully repaid within that window — this interest represents yield owed to depositors/liquidity providers (and the protocol's reserve cut, `fee-reserve`, minted as `treasury-lp`). This is a permanent freezing/loss of unclaimed yield, matching the in-scope "High" impact category (permanent freezing of unclaimed yield).

### Likelihood Explanation
The precondition is that `accrue` is paused while `repay` remains active — a plausible, non-compromised operational state (e.g., pausing accrual during an interest-rate-model migration or an oracle-related maintenance window while still allowing users to repay). Any borrower aware of this state can time a full repayment to avoid interest that accrued (or would accrue) during the pause window; no privileged access or DAO compromise is required, only observing the public `pause-states` and submitting a normal `repay` transaction.

### Recommendation
Make the `accrue`-paused branches of `next-index`/`next-liquidity-index` still account for elapsed time once unpaused only if `last-update` is explicitly frozen and no position can be closed to zero principal in the interim, OR — more robustly — make `system-repay`/`system-borrow`/`flashloan` revert (rather than silently proceed) when `accrue` is paused, since their debt/interest math depends on an up-to-date index. At minimum, disallow `principal-scaled` from being reduced to zero via `system-repay` while `accrue` is paused, or force `repay` to also be paused whenever `accrue` is paused.

### Proof of Concept
1. DAO/admin pauses `accrue` only (e.g., `pause-states.accrue = true`) while leaving `repay` unpaused, for operational reasons (rate model update, oracle issue, etc.).
2. Time passes; real-world interest should be accruing on outstanding debt, but `next-index`/`next-liquidity-index` return the frozen `idx`/`lidx` and `last-update` is not advanced. [1](#0-0) 
3. A borrower with outstanding debt calls `system-repay` (via `market`) for the full amount reported by `total-debt`, which is computed from the stale, pre-pause index. [7](#0-6) 
4. `principal-scaled` for that borrower's position becomes `0`; their debt is fully closed at the pre-pause valuation.
5. `accrue` is later unpaused; `next-index` catches up on the elapsed `time-delta`, but this benefits only positions that still have nonzero `principal-scaled` — the interest owed by the borrower who repaid in step 3 during the paused window is never captured, permanently reducing the yield due to depositors/reserve.
