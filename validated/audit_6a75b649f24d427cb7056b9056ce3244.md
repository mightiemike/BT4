### Title
Unauthenticated CPU-exhaustion DoS via unthrottled concurrent `TriggerConstantContract` calls invoking BN128 pairing precompile - (File: `framework/src/main/java/org/tron/core/services/RpcApiService.java`)

### Summary
`RpcApiService.callContract` handles both mutating and constant (`isConstant=true`) contract calls on the same gRPC service and thread pool (referenced as the shared RPC executor in `RpcApiService.java`). Constant calls are executed synchronously against `Wallet.triggerConstantContract` without consuming the caller's bandwidth/energy, and are only bounded per-call by `maxEnergyLimitForConstant` (configured in `Args`/`VmConfig`/`CommonParameter` and enforced in `VMActuator`), not by any global concurrency or CPU-time throttle.

### Finding Description
`callContract` in `RpcApiService.java` dispatches `TriggerConstantContract` requests to `Wallet.triggerConstantContract`, which runs the EVM/VM synchronously on the calling gRPC executor thread. Because the call is "constant," no transaction is broadcast and no bandwidth/energy is deducted from any account, so the normal per-account resource-throttling mechanism (bandwidth/energy accounting enforced for real transactions) never applies. The only cap on the amount of computation a single call can perform is `maxEnergyLimitForConstant`, a global config value (see `Args.java`, `VmConfig.java`, `CommonParameter.java`) used by `VMActuator` to bound the energy assigned to one constant execution — this is a per-call ceiling, not a global rate limiter or admission-control mechanism.

An unprivileged client needs only a network connection to the gRPC endpoint (no funded account, no signed transaction, no fee) to invoke `TriggerConstantContract` against a contract calling precompile `0x08` (BN128 pairing) with the maximum number of pairs allowed under `maxEnergyLimitForConstant`. Because these calls are processed on the shared gRPC service thread pool, submitting many such calls concurrently occupies worker threads for the full duration of each expensive VM execution. If the number of concurrent expensive calls approaches or exceeds the executor's thread count, other unrelated RPCs (e.g., `GetNowBlock`, `GetTransactionById`) queued on the same pool experience increased latency or are starved entirely.

None of the standard mitigations apply here: `validateSignature`, permission/owner checks, and actuator `validate()` are irrelevant because constant calls never create or broadcast a transaction; bandwidth/energy accounting doesn't apply by design for constant calls; and no rate limiter specific to `TriggerConstantContract` concurrency was found bounding aggregate CPU consumption across simultaneous requests.

### Impact Explanation
Concrete scoped impact is **DoS via RPC-API**: exhaustion of the gRPC/full-node RPC thread pool and degraded/stalled responsiveness for all RPC clients on the node, achievable with zero cost (no fee, no funded account, no signed transaction) by an anonymous network client. This matches the TRON bounty impact class "Node DoS via RPC-API" — availability degradation without any state corruption, fund loss, or key leakage.

### Likelihood Explanation
Preconditions are minimal and default: a publicly reachable gRPC full-node endpoint (default configuration exposes `TriggerConstantContract`), a deployed contract invoking the BN128 pairing precompile sized to the constant-call energy ceiling, and the ability to open many concurrent gRPC streams — all available to an unprivileged attacker at essentially zero monetary cost, and fully repeatable since constant calls leave no on-chain trace and consume no attacker resources.

### Recommendation
Introduce concurrency/rate limiting specific to constant-call execution (e.g., a bounded semaphore or dedicated smaller executor with backpressure/rejection for `TriggerConstantContract`/`TriggerConstantContractSolidity`), separate the constant-call execution pool from the pool serving read-only/administrative RPCs like `GetNowBlock`, and/or apply a wall-clock execution timeout per constant call independent of `maxEnergyLimitForConstant` so a burst of maximal-cost calls cannot monopolize shared worker threads.

### Proof of Concept
Request-level PoC (no JUnit needed, purely load-based):
1. Deploy a contract whose fallback/entry function calls precompile `0x08` (`altbn128_pairing`) with the maximum number of pairs allowed under the configured `maxEnergyLimitForConstant`.
2. Fire N concurrent gRPC `TriggerConstantContract` calls (e.g., N = executor thread pool size or higher) against this contract from an unauthenticated client — no account funding or signing required.
3. Concurrently issue unrelated `GetNowBlock`/`GetTransactionById` RPCs from a separate client and measure p99 latency before and during the load test.
4. Expected result if vulnerable: p99 latency for unrelated RPCs increases sharply (multi-second stalls or timeouts) while the attacker's calls execute, with zero cost/fee to the attacker and no state change recorded on-chain — confirming CPU/thread-pool exhaustion via a free code path.
