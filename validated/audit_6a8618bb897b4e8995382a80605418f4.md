### Title
Default (non-hardened) TRC10 Exchange swap math uses unchecked `long` arithmetic, allowing silent balance underflow/overflow in the Bancor-style AMM pool - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The analog of the reported "swap USD overflow + missing dispensing-account balance check" bug exists in java-tron's TRC10 `Exchange` (on-chain AMM/Bancor-relay) feature. The default code path for `ExchangeTransactionActuator` performs pool-balance updates with plain, unchecked `long` arithmetic and never validates that the payout side of the pool holds enough of the token being dispensed before crediting the trader, mirroring both defects in the report (unchecked arithmetic on the swap amount, and no dispensing-custody sufficiency check).

### Finding Description
`ExchangeTransactionActuator.execute()`/`doValidate()` compute the counter-party amount via `ExchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`. [1](#0-0) 

Whether "hardened" (overflow-checked) math is used is gated by `AbstractExchangeActuator.allowHarden()`, which reads `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()` — a chain parameter that must be turned on via governance proposal and is off (`0`) unless explicitly enabled, as shown by every test in the suite having to call `saveAllowHardenExchangeCalculation(1)` to exercise the safe path. [2](#0-1) 

In the default (`hardenedCalc == false`) branch of `ExchangeCapsule.transaction()`, the new pool balances are computed with plain `+`/`-` on primitive `long`, with no `Math.addExact/subtractExact` and no post-check other than the one guarded by `hardenedCalc`: [3](#0-2) 

The `buyTokenQuant` (the amount to be paid out from the *other* side of the pool — the direct analog of the report's "amount_out"/`dispensing_custody`) is itself produced by `ExchangeProcessor.exchange()`, which uses `double`/`StrictMath.pow` bancor-curve math instead of exact integer arithmetic: [4](#0-3) 

Nowhere in `ExchangeTransactionActuator.doValidate()` is `buyTokenQuant`/`anotherTokenQuant` checked against the *current* balance of the token being paid out before the swap is applied — the only checks present are `tokenQuant > 0`, `tokenExpected > 0`, pool balances `!= 0`, and that the incoming-token balance (not the outgoing one) stays under `balanceLimit`: [5](#0-4) 

Because the pool-balance subtraction (`secondTokenBalance - buyTokenQuant` or `firstTokenBalance - buyTokenQuant`) in the non-hardened path is a raw `long` subtraction with no bound check, if floating-point rounding in the double-based bancor formula (or crafted extreme input, e.g. very large `tokenQuant` relative to pool size) ever yields a `buyTokenQuant` that meets or exceeds the current balance of the dispensing side, the result is a **negative pool balance silently persisted to state** (`Commons.putExchangeCapsule(...)`), i.e. exactly the "insufficient dispensing_custody funds → underflow" scenario from the report — except here it's TVM-adjacent on-chain accounting state, not a crash, so it corrupts the AMM pool invariant going forward (subsequent swaps price off a corrupted/negative balance).

By contrast, `ExchangeInjectActuator` and `ExchangeWithdrawActuator` already use `multiplyExact`/`BigInteger` for their ratio math and `addExact`/`subtractExact` from `AbstractExchangeActuator`, but those exact-math helpers likewise degrade to plain `+`/`-` unless `allowHarden()` is true: [6](#0-5) [7](#0-6) 

The existence of a parallel `SafeExchangeProcessor`/`StrictMathWrapper`-based hardened path confirms this exact bug class was previously identified and partially remediated behind a feature flag, but the flag defaults to disabled, leaving the vulnerable default path live: [8](#0-7) 

### Impact Explanation
If triggerable, an unprivileged user submitting a `TransactionContract`-wrapped `ExchangeTransactionContract` (a plain public transaction type, no privileged role required) could drive a TRC10 exchange pool's tracked balance negative on the default math path. Since `ExchangeCapsule.setBalance` stores whatever `long` results (no floor at zero without hardened mode), this corrupts the on-chain AMM state used by every subsequent `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` against that pool — an accounting/invalid-state impact analogous to the report's underflow concern, and it can propagate mispriced swaps to all future traders of that exchange pair.

### Likelihood Explanation
Likelihood is moderate rather than trivially reproducible: the theoretical Bancor curve guarantees `buyTokenQuant < buyTokenBalance` for well-formed inputs, so triggering an actual crossing requires either (a) floating-point/`double` rounding error accumulating near pool-balance boundaries (`ExchangeProcessor` uses `double` and `(long) issuedSupply` truncation, not exact decimal math) or (b) an extreme/edge-case `tokenQuant` (e.g., very small pool `secondTokenBalance`/`firstTokenBalance` combined with a large sell quant near `balanceLimit`). This requires no privileged access and no mocked environment — it is reachable from any account with sufficient token/TRX balance issuing a normal transaction — but exact numeric conditions to flip the sign were not empirically reproduced in this analysis (no test harness run), so this should be treated as a concrete, code-verified defect whose exact trigger inputs require further numeric fuzzing to pin down precisely.

### Recommendation
1. Make hardened math (`allowHardenExchangeCalculation`) the mandatory default for all `Exchange*Actuator` classes rather than an opt-in governance proposal, or remove the flag and always use `SafeExchangeProcessor`/exact `BigDecimal` arithmetic for the Bancor relay computation in `ExchangeCapsule.transaction()`.
2. Add an explicit pre-execution check in `ExchangeTransactionActuator.doValidate()` (and `execute()`) that `buyTokenQuant`/`anotherTokenQuant` computed by `exchangeCapsule.transaction(...)` does not exceed the pre-swap balance of the token being dispensed, failing validation otherwise — independent of the `allowHarden()` flag.
3. Replace `ExchangeProcessor`'s `double`/`StrictMath.pow` truncation with the already-present `BigDecimal`-based `SafeExchangeProcessor` logic unconditionally, eliminating floating-point rounding as a source of balance-boundary violations.

### Proof of Concept
Not independently executed against a running node in this analysis (ask-only/read-only investigation). The code-level trigger path is:
1. Attacker calls `createExchange`-derived TRC10 pool (or targets an existing low-liquidity pool) where `secondTokenBalance` (or `firstTokenBalance`) is small relative to achievable `tokenQuant` inputs.
2. Attacker sends an `ExchangeTransactionContract` with `tokenQuant` chosen so that `ExchangeProcessor.exchange()`'s double-precision bancor formula returns a `buyTokenQuant` at or exceeding the current opposite-side balance.
3. Because `allowHardenExchangeCalculation` is disabled by default, `ExchangeCapsule.transaction()` takes the unchecked branch (`chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:143-156`) and stores a negative `newSecondTokenBalance`/`newFirstTokenBalance` via `Commons.putExchangeCapsule(...)` in `ExchangeTransactionActuator.execute()` without the actuator or `doValidate()` rejecting it.
This would need to be confirmed with a running node/unit test injecting extreme pool-ratio values to precisely determine the numeric threshold at which the double-precision formula's output crosses the boundary.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
