## Analysis Result

### Title
Unchecked ERC20 `transfer` success return value in fee-charging path allows a transaction to be treated as fee-paid without actual payment - (File: `crates/apollo_starknet_os_program/src/cairo/starkware/starknet/core/os/execution/transaction_impls.cairo`)

### Summary
The audit finding flags `InfiltrationPeriphery.heal()` for calling `IERC20.approve` without checking its boolean return value, so a silent `false` result is treated as success. The same bug class — ignoring an ERC20-style `success` return value from an externally invoked entry point — exists in the Starknet OS `charge_fee` function that every account transaction goes through to pay its fee.

### Finding Description
`charge_fee` builds a `TransferCallData` and invokes the fee-token contract's `transfer` entry point through `non_reverting_select_execute_entry_point_func`, then simply returns without inspecting the call's return data: [1](#0-0) 

This is in stark contrast to `run_validate` in the same OS package, which calls the exact same helper (`non_reverting_select_execute_entry_point_func`) but *does* validate the returned data against the expected `VALIDATED` selector before proceeding: [2](#0-1) 

`non_reverting_select_execute_entry_point_func` itself only asserts that the call did not revert (`assert is_reverted = 0`); it does not and cannot know whether the callee's return payload semantically signals success or failure — that is left to the caller (as `run_validate` correctly does, and `charge_fee` does not): [3](#0-2) 

The standard fee ERC20 (`ERC20.cairo`) happens to always return `TRUE` from `transfer`, and only fails via `assert_not_zero` reverts on insufficient balance, so the bug is currently latent under the reference implementation: [4](#0-3) 

However, the fee token's class hash is read dynamically from state (`fee_state_entry.class_hash`) rather than hardcoded, so `charge_fee` executes whatever code is currently deployed at `fee_token_address`: [5](#0-4) 

The equivalent Rust-side sequencer logic in `blockifier` has the same gap: `execute_fee_transfer` runs the `CallEntryPoint` for `transfer` and only propagates a `TransactionExecutionResult` error if the VM call itself errors/reverts — it never inspects `CallInfo.execution.retdata` to confirm the returned `success` felt is nonzero before treating the fee as collected: [6](#0-5) [7](#0-6) 

### Impact Explanation
Since neither the Starknet OS re-execution path nor the sequencer's `blockifier` execution path verifies the `success` boolean returned by the fee token's `transfer` entry point, a fee-token implementation that returns `FALSE` (or any falsy value) without reverting — a legitimate, ERC20-spec-compliant behavior pattern (e.g., paused/blacklist logic that returns false instead of reverting) — would cause the sequencer to treat the transaction as having successfully paid its fee, include it in the block, and commit the corresponding `fee_transfer_call_info`/receipt, while no actual value was transferred to the sequencer. This is a concrete loss of expected fee revenue and a functional-correctness gap between "fee charged" bookkeeping and "fee actually transferred" reality, reachable by any account whose transaction goes through the standard fee-charging flow.

### Likelihood Explanation
Exploitation requires the fee token contract (whose class hash is read from state, not hardcoded) to implement `transfer` in a way that returns a falsy success value instead of reverting on failure. This is not possible with the current canonical `ERC20.cairo` used in this repo, which always reverts on failure and returns `TRUE` on success, making the issue currently latent rather than actively exploitable against the default fee token. The likelihood is Medium: it depends on the specific fee-token implementation deployed at `fee_token_address`, but the missing defensive check itself is present in both the OS and blockifier code paths for every fee-charging transaction.

### Recommendation
In `charge_fee` (Cairo OS), capture and assert on the `retdata`/`retdata_size` returned by `non_reverting_select_execute_entry_point_func`, mirroring the pattern already used in `run_validate`, to ensure the `success` value is truthy before considering the fee paid. Symmetrically, in `execute_fee_transfer` (blockifier), inspect `CallInfo.execution.retdata` (or equivalent) after executing the fee-transfer call and fail the transaction if the returned success flag is not truthy, rather than relying solely on absence of a VM-level error/revert.

### Proof of Concept
1. Deploy (or have chain governance/admin — in a hypothetical or test network — set) a `fee_token_address` class whose `transfer` function returns `Uint256`/`felt` `0` (false) in some code path (e.g., a paused state or blacklist check) instead of reverting, while other code paths behave like the standard ERC20.
2. Submit a normal V3 invoke transaction with `max_fee`/resource bounds set as usual.
3. During block execution, `charge_fee` calls this fee token's `transfer`; the call returns normally (no revert) with `retdata = [0]` indicating failure.
4. `non_reverting_select_execute_entry_point_func` only checks `is_reverted = 0` and passes; `charge_fee` ignores `retdata` entirely and returns `()`, so the OS proceeds as if the fee was successfully charged.
5. On the blockifier/sequencer side, `execute_fee_transfer` similarly returns `Ok(CallInfo)` without checking `execution.retdata`, so `handle_fee` records the transfer as successful.
6. The block is committed with the transaction's receipt showing `fee_transfer_call_info` as a normal, non-reverted call, while the sequencer's actual token balance was never incremented — a permanent, unrecoverable loss of the expected fee for that transaction.

    fn execute_fee_transfer(
        state: &mut dyn State,
        tx_context: Arc<TransactionContext>,
        actual_fee: Fee,
    ) -> TransactionExecutionResult<CallInfo> {
        // The least significant 128 bits of the amount transferred.
        let lsb_amount = Felt::from(actual_fee.0);
        // The most significant 128 bits of the amount transferred.
        let msb_amount = Felt::ZERO;

        let TransactionContext { block_context, tx_info } = tx_context.as_ref();
        let storage_address = tx_context.fee_token_address();
        // The fee contains the cost of running this transfer, and the token contract is
        // well known to the sequencer, so there is no need to limit its run.
        let mut remaining_gas_for_fee_transfer =
            block_context.versioned_constants.os_constants.gas_costs.base.default_initial_gas_cost;
        let fee_transfer_call = CallEntryPoint {
            class_hash: None,
            code_address: None,
            entry_point_type: EntryPointType::External,
            entry_point_selector: selector_from_name(constants::TRANSFER_ENTRY_POINT_NAME),
            calldata: calldata![
                *block_context.block_info.sequencer_address.0.key(), // Recipient.
                lsb_amount,
                msb_amount
            ],
            storage_address,
            caller_address: tx_info.sender_address(),
            call_type: CallType::Call,

            initial_gas: remaining_gas_for_fee_transfer,
        };
        let mut context = EntryPointExecutionContext::new_invoke(
            tx_context,
            true,
            SierraGasRevertTracker::new(GasAmount(remaining_gas_for_fee_transfer)),
        );

        Ok(fee_transfer_call
            .execute(state, &mut context, &mut remaining_gas_for_fee_transfer)
            .map_err(|error| Box::new(TransactionFeeError::ExecuteFeeTransferError(error)))?)
    }
