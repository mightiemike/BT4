### Title
Unbounded per-cycle reward computation loop can cause excessive resource consumption / stuck withdrawals for long-inactive voters - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.withdrawReward`/`queryReward` (and the TVM analog `VoteRewardUtil.withdrawReward`/`queryReward`) compute rewards between `beginCycle` and `currentCycle` for an account. When `beginCycle` is older than `newRewardAlgorithmEffectiveCycle` (i.e., the voter never withdrew before the new VI-based algorithm was activated), the reward for the old range is computed via `getOldReward`, which iterates a `for (long cycle = begin; cycle < end; cycle++)` loop and inside each iteration calls `computeReward(cycle, votes)`, itself looping over every vote the account holds. [1](#0-0) 

### Finding Description
`computeReward(beginCycle, endCycle, accountCapsule)` splits the reward computation into an "old" range (before `newRewardAlgorithmEffectiveCycle`) and a "new" O(1)-per-vote VI-delta range: [2](#0-1) 

For the old range, `getOldReward` either calls the optimized `RewardViCalService.getNewRewardAlgorithmReward` (O(1) per vote via the precomputed VI store) when `allowOldRewardOpt()` is enabled, or falls back to a manual per-cycle loop when that optimization has not been activated: [1](#0-0) 

This fallback loop iterates once per cycle between `beginCycle` and `min(endCycle, newRewardAlgorithmEffectiveCycle)`, and for each cycle it iterates over every SR the account voted for, doing DB store reads via `delegationStore.getReward`/`getWitnessVote` each time: [3](#0-2) 

This is precisely the reported bug class: a voter who never triggers a reward withdrawal for a very long time accumulates a `beginCycle` that stays far behind `currentCycle`/`newRewardAlgorithmEffectiveCycle`. Cycles in java-tron roll roughly every maintenance period, so "many years" of inactivity translates into thousands of cycles. The number of loop iterations (and DB reads) grows linearly, unbounded, with the number of cycles since the account's last withdrawal, multiplied by the number of SR votes held. There is no cap in the code that would stop the loop or split the work if `currentCycle - beginCycle` (or `newRewardAlgorithmEffectiveCycle - beginCycle`) becomes very large.

The same computation path is directly reachable by any account, not just witnesses, via:
- The TVM opcode/precompile path `VoteRewardUtil.withdrawReward`/`queryReward`, invoked from smart-contract code (e.g., `REWARDBALANCE`/withdraw-reward opcodes), which itself performs the equivalent VI delta loop, but crucially the caller can also route into `computeReward`/`getOldReward` state through the shared `DelegationStore`. [4](#0-3) 
- Ordinary account TRX freeze/vote reward withdrawal, exercised through `MortgageService.withdrawReward`, called during normal account/vote processing.

Since this reward-computation cost is charged as part of transaction execution (bandwidth/energy in the TVM path, or as part of block/withdraw processing in the account path), an attacker-controlled or simply very-old account can force disproportionately large computation for a single call once enough elapsed cycles accumulate.

### Impact Explanation
If the manual old-reward loop path is exercised (i.e., `allowOldRewardOpt()` is not enabled, which is a committee-controlled proposal flag rather than something enabled by default at genesis), a very old, un-withdrawn vote/reward claim can force an unbounded (linear in elapsed cycles × vote count) computation inside a single transaction/contract call. In the account-level path this can slow down block processing or the API call that resolves the reward/withdraw request; in the TVM path (`VoteRewardUtil`) it can cause a call to run out of energy/CPU budget mid-execution, effectively preventing the affected account from ever successfully withdrawing its accumulated reward (denial of service against that specific claim), matching exactly the reported "later claimer might not be able to claim reward" bug class.

### Likelihood Explanation
Likelihood depends on network configuration: the fix path (`RewardViCalService`/`allowOldRewardOpt`) already exists in the codebase and, once activated via governance proposal, computes old rewards in O(1) per vote instead of O(cycles). Whether this proposal is enabled by default or must be explicitly voted on by the committee could not be fully confirmed from the available index (the `DynamicPropertiesStore` default value for `ALLOW_OLD_REWARD_OPT` could not be retrieved due to truncated file content in the index). If the optimization is off by default or not yet activated on a given network, any account that has never withdrawn its cycle-based reward since before `newRewardAlgorithmEffectiveCycle` is reachable through this unbounded loop, making this a moderate-likelihood, environment-dependent issue.

### Recommendation
Cap or chunk the per-cycle loop in `getOldReward` (and equivalently in any other manual per-cycle reward accumulation) so it cannot process more than a bounded number of cycles in a single call; if the reward-computation optimization path is available, it should be the default rather than an opt-in proposal, or the fallback loop should never be reachable in production once the network is live for long enough. Alternatively, ensure `allowOldRewardOpt` (or the equivalent VI-based computation) is always used for old-algorithm cycles rather than allowing the linear fallback to execute for large ranges.

### Proof of Concept
Not independently verified from the index. Conceptually: create an account, vote for many SRs, wait/roll forward through many cycles without withdrawing (increasing `beginCycle`-to-`currentCycle`/`newRewardAlgorithmEffectiveCycle` distance), disable/never-enable `allowOldRewardOpt`, then call `withdrawReward`/`queryReward` (or the TVM `REWARDBALANCE`/withdraw opcode) and observe computation cost scaling linearly with elapsed cycles × number of votes, as demonstrated by the existing benchmark test that specifically measures old vs. new algorithm performance over ~73,000 cycles: [5](#0-4) 

**Note on limitations:** I was unable to retrieve the actual default value of `ALLOW_OLD_REWARD_OPT` in `DynamicPropertiesStore.java` or `reference.conf` due to index truncation, so I cannot definitively confirm whether the vulnerable fallback loop is reachable by default on a freshly-deployed/mainnet-equivalent network versus only when a committee proposal has explicitly disabled the optimization. This should be verified directly in a full checkout before treating this as confirmed-exploitable on any specific live network.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }

  public static void withdrawReward(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmVote()) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long beginCycle = repository.getBeginCycle(address);
    long endCycle = repository.getEndCycle(address);
    long currentCycle = repository.getDynamicPropertiesStore().getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;
      }
      beginCycle += 1;
    }
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      repository.updateBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);
  }
