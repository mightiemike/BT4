### Title
Poison-microblock slashing can be forged from a single honest microblock signature via ECDSA malleability - ([File: stackslib/src/chainstate/stacks/db/transactions.rs])

### Summary
`check_microblock_header_signer` recovers each `StacksMicroblockHeader`'s signer via `check_recover_pubkey`, which calls `StacksPublicKey::recover_to_pubkey_without_validating_low_s`, skipping low-S normalization. Because the digest that is signed/recovered excludes the signature field itself, an attacker can take one honestly-signed microblock header, flip its `s` value (and recovery id) to produce a mathematically valid "malleated" signature over the identical digest — no private key required — and submit it as the second header of a `PoisonMicroblock` transaction, causing the chain state to record a fork/double-sign that never happened.

### Finding Description
The broken equality: **"poison report accepted for pubkey X" == "miner with key X genuinely produced two distinct signed microblocks at the same sequence/prev_block."** This equality is violated.

- `StacksMicroblockHeader::check_recover_pubkey` (`stacks-codec/src/transaction.rs:2598-2616`) computes the digest over `version, sequence, prev_block, tx_merkle_root` with the signature zeroed out (`serialize(&mut bytes, true)`), then recovers the pubkey from `self.signature` using `recover_to_pubkey_without_validating_low_s` (`stacks-common/src/util/secp256k1/native.rs:200-239`), which explicitly skips the low-S check (`verify_low_s=false`).
- ECDSA signature malleability guarantees that for any valid signature `(r, s, v)` over a message `m` recovering to pubkey `Q`, the tuple `(r, n-s, 1-v)` is also a valid signature over the same `m` recovering to the same `Q` — this requires no knowledge of the private key, only public arithmetic on an already-observed signature.
- `check_microblock_header_signer` (`stackslib/src/chainstate/stacks/db/transactions.rs:686-713`) only checks `pkh1 == pkh2`. It does not check that `tx_merkle_root`, `block_hash()`, or the signature encodings actually represent a second independently-signed microblock.
- `handle_poison_microblock` (`transactions.rs:722-856`) relies solely on this check before recording a poison report (`insert_microblock_poison`) and slashing/reassigning commission tied to `pubkh`'s coinbase at `mblock_pubk_height` (`transactions.rs:750-856`).
- The mempool-level pre-check `MemPoolRejection` handling for `PoisonMicroblock` (`stackslib/src/chainstate/stacks/db/blocks.rs:6844-6868`) also only verifies `sequence`, `prev_block`, `version` equality and `pkh1 == pkh2` — it never checks that `tx_merkle_root` differs or that `block_hash()`s differ meaningfully (i.e., that the two headers represent genuinely distinct content beyond a malleated signature encoding).

Exploit flow: attacker observes one broadcast, honestly-signed `StacksMicroblockHeader` (with `version, sequence, prev_block, tx_merkle_root, signature`). Attacker computes the malleated signature `sig' = (r, n-s, 1-v)` (public arithmetic only), forms `header2 = header1` with `signature = sig'`. Because header1's fields other than `signature` are unchanged, `header2 != header1` (Rust `PartialEq` compares the raw signature bytes), satisfying superficial "distinctness," yet `check_recover_pubkey` yields identical `pkh1 == pkh2`, and `sequence`/`prev_block`/`version` are trivially identical. Attacker submits `TransactionPayload::PoisonMicroblock(header1, header2)`. It passes all existing static and mempool checks and is processed by `handle_poison_microblock`, which inserts a poison record and pays the reporter a commission / slashes the miner's coinbase — despite there being only one real microblock ever produced.

Existing guards that fail: `check_microblock_header_signer` (equality on `pkh1==pkh2` only), and the mempool rejection logic — neither compares `tx_merkle_root` or `block_hash()` between the two headers to confirm a genuine, distinct signing event took place.

### Impact Explanation
This does not itself cause a chain split, invalid-block acceptance, or MARF root divergence — the poisoned pubkey/report state is deterministic on all nodes given the same transaction, so no fork results. The concrete harm is a wrongful reward/commission mis-payment: an honest miner's microblock public key is falsely poisoned, and the attacker (as reporter) can claim a commission tied to that miner's coinbase, using only a single genuine, publicly-observed signature — no double-signing ever occurred. Per the stated severity rubric, this is a **poison/reward mis-payment bounded to fees/commission**, i.e., **High** severity, not Critical (no chain split, no invalid block, no state-root divergence is produced).

### Likelihood Explanation
The attacker needs only to observe one broadcast microblock (something any network participant sees) and perform public-key-independent arithmetic (S-negation, recovery-id flip) on the signature — no BTC stake, no majority, no privileged role, and no interaction with any other party's key. This is trivially repeatable against any miner's microblocks that are still within the `MINER_REWARD_MATURITY` window (`transactions.rs:770-803`). It is feasible today given `check_recover_pubkey`'s unconditional use of `recover_to_pubkey_without_validating_low_s`.

### Recommendation
In `check_microblock_header_signer` (and/or `check_recover_pubkey`), reject malleated signature pairs by:
1. Enforcing low-S normalization on both signatures before/at recovery (use `recover_to_pubkey` with low-S validation, or explicitly reject if either signature is not the canonical low-S form), and/or
2. Requiring that the two headers differ in `tx_merkle_root` (or `block_hash()`) — not merely in signature bytes — before treating them as evidence of equivocation, both in the mempool rejection path (`blocks.rs:6844-6868`) and in `handle_poison_microblock`/`check_microblock_header_signer`.

### Proof of Concept
Rust integration test outline (in `stackslib/src/chainstate/stacks/db/transactions.rs` test module, alongside `process_poison_microblock_multiple_same_block`):
1. Generate a `block_privk`/`block_pubkh`, insert via `StacksChainState::insert_microblock_pubkey_hash`.
2. Build one genuinely signed `mblock_1` via `make_signed_microblock(&block_privk, ..., prev_block, seq)`.
3. Extract `mblock_1.header.signature`, decode `(r, s, v)`, compute the malleated `(r, n-s, 1-v)` using `secp256k1`'s `negate_s`, and construct `header2 = mblock_1.header.clone()` with the malleated signature substituted.
4. Assert `header2 != mblock_1.header` (byte-level) but `header2.check_recover_pubkey().unwrap() == mblock_1.header.check_recover_pubkey().unwrap()` (both equal `block_pubkh`), and `header2.tx_merkle_root == mblock_1.header.tx_merkle_root`.
5. Construct `TransactionPayload::PoisonMicroblock(mblock_1.header.clone(), header2)`, sign it as a reporter, and call `StacksChainState::process_transaction`.
6. Assert on both sides of the equality: (a) the transaction is currently **accepted** (`.unwrap()` succeeds, a poison report is inserted via `get_poison_microblock_report`) — demonstrating the vulnerability — versus (b) the expected/fixed behavior, where the equality "one genuine distinct double-signature" should require processing to **reject** with an error (e.g., `PoisonMicroblocksDoNotConflict` or a new "non-distinct content" error), since only one real microblock signature ever existed.
