Confirmed: `DelegateAction` (NEP-366 meta-transactions) is signed as `SignableMessage { discriminant, msg: &delegate_action }`, and the signed payload is `DelegateAction { sender_id, receiver_id, actions, nonce, max_block_height, public_key }` [1](#0-0) . Neither the discriminant nor the `DelegateAction` struct includes a chain identifier or genesis hash — only a NEP number tag, sender/receiver account IDs, an access-key nonce, and a block-height expiry [2](#0-1) .

### Title
Meta-transaction (`DelegateAction`) signatures lack chain-binding, enabling cross-chain replay of NEP-366 authorization tokens - (File: core/primitives/src/action/delegate.rs)

### Summary
`SignedDelegateAction::sign`/`verify` compute the signature over `delegate_action.get_nep461_hash()`, which is `hash(borsh(SignableMessage{discriminant, msg: &DelegateAction}))` [3](#0-2) . The `MessageDiscriminant` only encodes a NEP number (366 for `DelegateAction`, 611 for `DelegateActionV2`) [2](#0-1) , and the signed `DelegateAction` body carries `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key` — no chain ID, genesis hash, or any other network-binding value [1](#0-0) . This is exactly the bug class described in the external report: an authorization token that encodes only an address and a counter (nonce), reusable on any chain where that account/key/nonce state matches.

### Finding Description
When a relayer submits a `SignedDelegateAction` inside a transaction, validation in `validate_delegate_action_key` checks the access key's existence, permission, and that `delegate_action.nonce() > access_key.nonce`, plus that `apply_state.block_height < max_block_height` (via the separate `DelegateActionExpired` check) [4](#0-3) . None of these checks, nor the signature itself, are bound to a specific network/genesis. `nearcore` explicitly supports forking a live chain's state into a new network while preserving accounts, access keys, and their nonces (`tools/fork-network`), and more generally any nearcore-derived chain (testnet-like clones, app-specific forks) can end up with the same `AccountId`/`PublicKey`/nonce state as another chain at some point in time.

Given that, a `SignedDelegateAction` a user signs intending to authorize actions on chain A (e.g. handed to a relayer, or observed in a pending/mempool transaction) remains a fully valid, replayable authorization on chain B as long as: (1) `sender_id`'s access key with the same `public_key` exists there with `nonce < delegate_action.nonce`, and (2) `apply_state.block_height < max_block_height`. Any relayer can independently repackage the identical `SignedDelegateAction` into a new outer `Action::Delegate` on chain B's transaction and have it executed there, causing the user's authorized actions (transfers, function calls, key/permission changes, etc.) to execute on a chain the signer never intended.

### Impact Explanation
Because `DelegateAction` grants a relayer the ability to execute arbitrary `sender_id`-authorized actions (transfers, function calls with deposits, staking, key management — anything the underlying access key permits) [5](#0-4) , replaying an intercepted/leaked meta-transaction on a sibling chain constitutes unauthorized value movement / unauthorized state transition on that other chain: the sender never intended the action to be valid there, yet it will be accepted and applied identically to a legitimately-scoped meta-transaction. This satisfies "concrete unauthorized value movement" / "invalid state transition acceptance" criteria, since it is a state change the honest signer did not consent to for that specific network.

### Likelihood Explanation
This requires (a) two or more nearcore-based networks sharing overlapping account/access-key/nonce state — a scenario `nearcore` itself facilitates via its `fork-network` tooling and is common for testnets/appchains derived from mainnet genesis snapshots — and (b) an attacker or relayer obtaining a signed but not-yet-consumed `SignedDelegateAction` (e.g., by operating as, or colluding with, the relayer that a user handed the meta-transaction to, or by observing it before/while it is included). This is a real, non-trivial-but-plausible operational scenario rather than a theoretical one, since meta-transactions are explicitly designed to be created once and forwarded by a possibly separate relayer party, and the signed payload never expires beyond `max_block_height`/nonce ordering — both of which can independently be satisfied on more than one chain.

### Recommendation
Include a chain-binding value (e.g., genesis hash or a protocol-level equivalent of chain ID) in the `MessageDiscriminant`/`DelegateAction` signed payload, mirroring the fix already applied for the analogous "TermAuth" issue in the referenced report (adding `block.chainid` and destination-contract binding to the signed hash). Concretely, extend `DelegateAction`/`DelegateActionV2` (or the `SignableMessage` wrapper) to include the genesis hash of the chain the action is intended for, and have `validate_delegate_action_key` reject delegate actions whose embedded chain-binding value does not match the current chain's genesis hash.

### Proof of Concept
Conceptual (cannot be executed without two live nearcore networks sharing state):
1. Fork a running nearcore network's state into a second network using `tools/fork-network`, preserving `alice.near`'s account, full-access key, and its current nonce on both networks.
2. On network A, `alice.near` signs a `DelegateAction{ sender_id: alice.near, receiver_id: bob.near, actions: [Transfer{...}], nonce: N+1, max_block_height: H }` and hands the `SignedDelegateAction` to relayer R, intending it to execute only on network A.
3. Before R submits it on A, an operator of network B (or R itself, if also operating on B) wraps the identical `SignedDelegateAction` into an `Action::Delegate` inside a new outer transaction submitted to network B, where `alice.near`'s access key nonce is still `< N+1` and current block height `< H`.
4. `validate_delegate_action_key` on network B accepts the nonce/permission checks (they only reference local state) [4](#0-3) , `SignedDelegateAction::verify` succeeds because the signed hash never referenced network identity [6](#0-5) , and the transfer to `bob.near` executes on network B despite `alice.near` never authorizing it there.

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}
