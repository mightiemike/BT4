### Title
Concurrent `BucketApi::grow` calls from foreground write-through and background index flush can trip the `Reallocated::add_reallocation` "only 1 reallocation" assertion, panicking a validator thread - (File: bucket_map/src/bucket.rs)

### Summary
`Bucket::grow_index` and `Bucket::grow_data` are both invoked through `BucketApi::grow`, which takes only a *read* lock on the bucket's `RwLock`, while normal writes (`try_write`/`insert`) take an exclusive *write* lock. Because two independent code paths - the immediate write-through path (`InMemAccountsIndex::write_through`) and the background flush path (`InMemAccountsIndex::flush_slot_cache`/background thread) - both call the shared `write_to_disk` helper (`try_write` then `grow` on `BucketApi`) against the *same* per-bin `BucketApi`, it is possible for two threads to concurrently hold read locks and both call `Reallocated::add_reallocation`, tripping the `assert_eq!(0, ...)` and panicking the thread.

### Finding Description
`Reallocated::add_reallocation` documents and enforces (via assertion) that only one reallocation can be in flight for a given `Bucket` at a time: [1](#0-0) 

`grow_index` and `grow_data` are the only two callers, and both call `add_reallocation()` without any mutual-exclusion guarantee between themselves: [2](#0-1) [3](#0-2) 

They are dispatched from `Bucket::grow`, called by `BucketApi::grow`, which explicitly documents that it only takes a **read** lock (comment: "grows are special - they get a read lock"): [4](#0-3) 

In contrast, `try_write`/`insert`/`update` take an exclusive **write** lock via `get_write_bucket`, which also calls `handle_delayed_grows()` (clearing `active_reallocations`) each time it is acquired: [5](#0-4) 

Rust's `std::sync::RwLock` allows arbitrarily many concurrent readers. So while `try_write` calls are mutually exclusive with each other, two threads that each *already failed* a `try_write` (and thus already released the write lock) can subsequently call `grow()` concurrently, both taking read locks at the same time.

This race is reachable in production because the exact same helper, `InMemAccountsIndex::write_to_disk` (try_write, then on error call `disk.grow(err)`), is invoked from two independent call sites that both operate on the same per-bin `Arc<BucketApi<(Slot,U)>>`:
- The foreground/inline write-through path (`write_through`, called synchronously from `upsert`/`replace`/`slot_list_mut_with_entry`/`try_write_through` whenever `should_write_through` is enabled and an entry becomes single-slot/single-ref): [6](#0-5) [7](#0-6) 
- The background flush path (`flush_slot_cache`/`background()`), run by dedicated `solIdxFlusherNN` threads, calling the identical `write_to_disk` helper for aged/dirty entries: [8](#0-7) [9](#0-8) 

Exploit flow: an unprivileged attacker who writes/rewrites many accounts that hash into the same accounts-index bin (bin selection is `bin_from_pubkey`, which is deterministic and attacker-observable/pre-computable since it does not use a secret per-run salt the way `Bucket::bucket_index_ix` does) can force that bin's on-disk `Bucket` to be simultaneously near-full on both the index storage and a data storage bucket. If, at nearly the same time, (a) a foreground transaction causes `write_through` to fail a `try_write` with `IndexNoSpace` and call `disk.grow(IndexNoSpace)`, and (b) the background flusher thread (processing a different dirty/aged pubkey in the same bin) fails a `try_write` with `DataNoSpace` and calls `disk.grow(DataNoSpace)` at roughly the same moment, both threads hold concurrent read locks and both invoke `add_reallocation()`. The second caller's `fetch_add` observes `1` (not `0`), and `assert_eq!` panics the calling thread.

None of the existing guards (slot/ancestor checks, zero-lamport checks, ref-count checks, ObsoleteAccount handling) are relevant here - this is a pure concurrency/locking defect in the bucket-map storage layer, unrelated to account content validation.

### Impact Explanation
This is a liveness/availability bug reachable purely by driving unprivileged write patterns (creating/rewriting many accounts that collide into one accounts-index bin, with a mix of new-key insertions to grow the index and larger data to grow the data buckets). A panic in a `solIdxFlusherNN` background thread, or in whatever thread performs the inline write-through (which can be a transaction-processing/replay thread), degrades or halts index flushing/eviction for that bin. Depending on the process's panic-handling configuration (this repo's Cargo profiles do not set `panic = "abort"` anywhere found, so by default a panic on a non-main thread does not itself abort the process, but it does kill that thread; if any code subsequently `.join().unwrap()`s that thread's `JoinHandle`, the panic propagates and can bring down the whole validator). At minimum this is a correctness/availability defect in a shared, always-active subsystem (`AccountsDb`/`AccountsIndex`), matching the "node panic" / disproportionate degradation bounty category.

### Likelihood Explanation
Preconditions: the disk index / `IndexLimit::Threshold` (write-through) mode must be enabled so that `write_through` is invoked on the foreground path (this is a documented, real production configuration - see `IndexLimit::Threshold` and `should_write_through`, and the associated tests in `accounts-db/src/accounts_db/tests/impl.rs`). Given that, the attacker only needs to:
1. Discover or brute-force a pubkey that lands in the same accounts-index bin as their target account(s) (bin routing is `PubkeyBinCalculator`/`bin_from_pubkey`, a fixed deterministic function of the pubkey - not randomized per-validator, so pre-computable offline).
2. Drive a high write rate to that bin with a mix of many small unique new keys (to exhaust the index bucket, `IndexNoSpace`) and growing/enlarged account data (to exhaust a data bucket, `DataNoSpace`), timed so that the foreground write-through and background flush loop overlap.

The race window is narrow (only the gap between the failed `try_write`'s lock release and the subsequent `grow()` call), so this is a low-but-nonzero-probability timing race rather than a deterministically triggerable single-shot bug; it would generally need to be hammered by a fuzz/stress harness or sustained adversarial load to trigger reliably. This is exactly the kind of scenario the question's proof idea calls for (a concurrency fuzz test).

### Recommendation
Make `add_reallocation` (or `grow_index`/`grow_data`) exclusive with respect to *each other*, not just with respect to `handle_delayed_grows`. Options:
- Have `BucketApi::grow` take the same lock discipline as writes for the "check-and-set" portion (e.g., use a dedicated `Mutex` around the compare/insert step of `active_reallocations`, replacing the bare `fetch_add`+`assert` with a `compare_exchange(0, 1)` that returns an error/silently no-ops instead of asserting when a reallocation is already pending), since a second grow request for the same current-capacity condition should just be treated as already-handled (fine, because the newly-set bigger bucket already covers the need) rather than a fatal bug.
- Alternatively, serialize `grow()` calls with a bucket-internal mutex distinct from the outer `RwLock`, so at most one thread can be inside `grow_index`/`grow_data`/`add_reallocation` at a time, regardless of whether the outer `RwLock` is held for reading or writing.

### Proof of Concept
Rust concurrency test to add under `bucket_map/src/bucket.rs` `#[cfg(test)]` (or a new integration test in `bucket_map/tests/`):

```rust
#[test]
fn test_concurrent_grow_index_and_grow_data_can_panic_add_reallocation() {
    use std::{sync::Arc, thread};

    // Construct a Bucket<u64> sized so that both `grow_index` (IndexNoSpace)
    // and `grow_data` (DataNoSpace) conditions can be simulated directly,
    // bypassing BucketApi's write-lock serialization of try_write, and instead
    // calling `Bucket::grow` (immutable ref) from two threads concurrently,
    // mirroring how `BucketApi::grow` only takes a read lock in production.
    let bucket = Arc::new(make_test_bucket_with_capacity(/* small capacity */));

    let b1 = Arc::clone(&bucket);
    let t1 = thread::spawn(move || {
        b1.grow(BucketMapError::IndexNoSpace(b1.index.capacity()));
    });

    let b2 = Arc::clone(&bucket);
    let t2 = thread::spawn(move || {
        b2.grow(BucketMapError::DataNoSpace((0, 0)));
    });

    // Expected (buggy) behavior: one of the joins returns an Err because the
    // spawned thread panicked inside `Reallocated::add_reallocation`'s
    // `assert_eq!(0, ..., "Only 1 reallocation can occur at a time")`.
    let r1 = t1.join();
    let r2 = t2.join();
    assert!(
        r1.is_ok() && r2.is_ok(),
        "a background/foreground thread panicked due to concurrent grow_index/grow_data \
         calling add_reallocation() without mutual exclusion: r1={r1:?} r2={r2:?}"
    );
}
```

A higher-fidelity integration reproduction would use `BucketApi<(Slot, u64)>` directly (as `InMemAccountsIndex` does) and two threads calling `bucket_api.try_write(...)`/`bucket_api.grow(...)` in the `write_to_disk` pattern with interleaved keys engineered (via `#[cfg(test)]` capacity hooks) to fail with `IndexNoSpace` on one thread and `DataNoSpace` on the other in the same time window, asserting the process does not panic. Because the underlying race depends on real thread scheduling, the test should be run under a stress/fuzz loop (e.g., `loom` or repeated iterations with `std::sync::Barrier` to force both threads into `grow()` simultaneously) to reliably reproduce the panic and to validate a fix that replaces the `assert_eq!` with a `compare_exchange`-based idempotent no-op.

    /// Writes `disk_entry` for `pubkey` to `disk`, retrying after a grow if needed.
    /// Returns the total time spent waiting for disk grows, in microseconds.
    fn write_to_disk(
        disk: &BucketApi<(Slot, U)>,
        pubkey: &Pubkey,
        disk_entry: &[(Slot, U)],
    ) -> u64 {
        let mut grow_us = 0u64;
        loop {
            match disk.try_write(pubkey, (disk_entry, 1)) {
                Ok(_) => break,
                Err(err) => {
                    let m = Measure::start("flush_grow");
                    disk.grow(err);
                    grow_us += m.end_as_us();
                }
            }
        }
        grow_us
    }
