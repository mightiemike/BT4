### Title
KV-replay recomputes ledger state without cross-checking it against the already-committed `TransactionInfo` checkpoint hashes - ([File: storage/aptosdb/src/backup/restore_utils.rs])

### Summary
When `kv_replay` is used (`save_transactions_and_replay_kv` → `restore_utils::save_transactions_impl`), the code recomputes the post-transaction ledger state purely from the supplied write sets via `StateStore::calculate_state_and_put_updates`, and persists the result — but it never compares the recomputed state root to the `state_checkpoint_hash` / `hot_state_checkpoint_hash` already recorded in the `TransactionInfo` that was committed to the accumulator/ledger. `TransactionInfoDb::get_transaction_info` is a pure passthrough reader and performs no such cross-check either.

### Finding Description
`save_transactions_impl` unconditionally writes the supplied `txn_infos` to `TransactionInfoDb`: [1](#0-0) 

Then, only if `kv_replay` is set, it re-derives ledger state from the write sets and stores the resulting KV/JMT updates: [2](#0-1) 

`calculate_state_and_put_updates` computes the new `LedgerState` from `current.update_with_db_reader(...)` and simply returns it — there is no `ensure!` comparing `new_state`'s root hash (or the JMT root at checkpoints) to `state_checkpoint_hash()`/`hot_state_checkpoint_hash()` of the corresponding, already-persisted `TransactionInfo`: [3](#0-2) 

`get_transaction_info` itself is a plain read with no verification logic at all: [4](#0-3) 

This gap is corroborated by an explicit TODO in the shared comparator used by replay tooling, which states that checkpoint hashes are deliberately not validated: [5](#0-4) 

`ensure_match_transaction_info` checks `status`, `gas_used`, `state_change_hash` (write-set hash) and `event_root_hash`, but the comment at lines 2197-2202 explicitly documents that state/hot-state checkpoint hashes and `position_state_checkpoint_hash` are ignored, meaning "replay-verify tooling (e.g. db-tool's `replay_on_archive`) can report a successful replay even when the authenticated position state root diverges from local execution." The same gap applies to `calculate_state_and_put_updates` in the `kv_replay` path: it recomputes a JMT/state root incrementally from write sets but never asserts equality against the `state_checkpoint_hash` bound in the corresponding `TransactionInfo` that was authenticated via the accumulator proof at backup/restore time.

### Impact Explanation
If the write-set data fed into `kv_replay` (from a backup manifest or any other untrusted/corrupted source) diverges from what was truly executed on-chain, at consensus-committed checkpoints — but still happens to match the transaction-level `state_change_hash` check for the write set — the state root recomputed via `calculate_state_and_put_updates` can silently diverge from the `state_checkpoint_hash`/`hot_state_checkpoint_hash` already recorded in the ledger's `TransactionInfo`. Nothing in this path raises an error; the wrong `LedgerState` is committed as if it were correct, corrupting the JMT/state root binding for the replayed database going forward (a state-integrity break with hard-fork/divergence potential for any node relying on this replayed DB).

### Likelihood Explanation
This requires the `kv_replay`/`save_transactions_and_replay_kv` code path to be exercised (used by db-restore tooling, state-sync-v2 KV-only restore, and `replay_verify`/db-tool utilities) with write-set data that diverges from the canonical execution result while still passing the narrower checks that are performed (e.g., transaction hash / write-set hash at the single-transaction level, if performed upstream — a step I could not fully confirm in `storage/backup/backup-cli/src/backup_types/transaction/restore.rs` due to index limitations on that file). The TODO comment in `ensure_match_transaction_info` independently confirms that Aptos's own replay-verify tooling is documented as *not* validating checkpoint-hash divergence today, which raises the likelihood that this class of gap is real and currently unaddressed in production replay/restore code, rather than purely theoretical.

### Recommendation
In `calculate_state_and_put_updates` (or immediately after it is called from `save_transactions_impl`'s `kv_replay` branch), add an explicit `ensure!` that compares the recomputed checkpoint/latest state root against the `state_checkpoint_hash` (and `hot_state_checkpoint_hash` where applicable) already stored in the corresponding `TransactionInfo`, failing loudly (returning an `AptosDbError`) on mismatch instead of silently persisting the divergent state. Additionally, resolve the TODO in `TransactionOutput::ensure_match_transaction_info` by validating checkpoint hashes there as well, so that generic replay-verify tooling also catches this class of divergence.

### Proof of Concept
Due to index-size limitations, I was unable to fully load `storage/backup/backup-cli/src/backup_types/transaction/restore.rs` (the file returned as effectively empty/truncated in this environment) to confirm whether an independent write-set-to-`state_change_hash` check exists upstream of `save_transactions_and_replay_kv`. A concrete PoC would be: an integration test that (1) commits a chunk of transactions normally so `TransactionInfo`s with known `state_checkpoint_hash` are persisted, (2) invokes `RestoreHandler::save_transactions_and_replay_kv` with write sets that differ from the originally-executed ones for at least one version in a way that still hashes identically at the single–write-set level check (or where that check does not exist for kv_replay), and (3) asserts that `save_transactions_and_replay_kv`/`calculate_state_and_put_updates` returns `Ok(())` and commits a state root that does **not** equal the stored `TransactionInfo::state_checkpoint_hash()`, demonstrating that the mismatch is never raised as an error. I recommend a Devin session with full repository/file access to write and run this test, since the relevant loading code in `restore.rs` could not be completely inspected here.

```rust
    pub fn calculate_state_and_put_updates(
        &self,
        state_update_refs: &StateUpdateRefs,
        ledger_batch: &mut SchemaBatch,
        sharded_state_kv_batches: &mut ShardedStateKvSchemaBatch,
    ) -> Result<(LedgerState, HotStateUpdates)> {
        let current = self.current_state_locked().ledger_state();
        let (hot_state, persisted) = self.get_persisted_state()?;
        let (new_state, reads, hot_state_updates) = current.update_with_db_reader(
            &persisted,
            hot_state,
            state_update_refs,
            self.state_db.clone(),
        )?;

        self.put_state_updates(
            &new_state,
            &state_update_refs.per_version,
            &reads,
            ledger_batch,
            sharded_state_kv_batches,
        )?;

        Ok((new_state, hot_state_updates))
    }
```
