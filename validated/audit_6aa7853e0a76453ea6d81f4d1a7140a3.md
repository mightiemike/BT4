### Title
Disabled/Deprecated Token Configs Are Still Honored for PRC20 Minting on Inbound — Missing "Enabled" Allowlist Enforcement (File: x/uexecutor/keeper/handler.go)

### Summary
`TokenConfig` in `x/uregistry` carries an `Enabled` flag intended as the on-chain allowlist/kill-switch for which external tokens may be bridged (analogous to the iframe report's recommendation to gate embedding via an explicit trusted-origin allowlist / kill switch). However, the inbound execution path that mints PRC20 tokens (`depositPRC20` in `x/uexecutor/keeper/handler.go`) fetches the `TokenConfig` by `(sourceChain, assetAddr)` and only validates that `NativeRepresentation` is non-nil — it never checks `Enabled`. This means once a token has ever been registered with a native representation, an attacker-controlled inbound event referencing that `AssetAddr` will still successfully mint PRC20, even after the token has been disabled by governance/admin (e.g., in response to a compromise, deprecation, or an accounting bug requiring the mapping to be frozen).

### Finding Description
`Inbound.AssetAddr` is fully attacker/relayer-observation-controlled data that flows from `MsgVoteInbound` through `VoteInbound` → `ExecuteInbound` → `ExecuteInboundFunds`/`ExecuteInboundFundsAndPayload`/`ExecuteInboundGasAndPayload` → `depositPRC20`: [1](#0-0) 

`GetTokenConfig` performs a direct keyed lookup with no filtering on the `Enabled` field: [2](#0-1) 

`ValidateForExecution` on `Inbound`, which is the gate run before execution, only validates that `AssetAddr` is non-empty — it performs no registry/enabled check at all: [3](#0-2) 

Once quorum of honest Universal Validators votes an inbound referencing a since-disabled `TokenConfig.Address`, `depositPRC20` still resolves `NativeRepresentation.ContractAddress` and calls `CallPRC20Deposit`, minting PRC20 to the recipient — with no invocation-time restriction analogous to the CSP `frame-src` allowlist the external report recommends.

### Impact Explanation
If a `TokenConfig` is disabled after initial registration (the chain's only "kill switch" for a bridged asset — e.g., due to a discovered vulnerability in the external token contract, incorrect decimals/liquidity-cap configuration, or a compromised bridge on the source chain), inbound deposits referencing that asset's address continue to mint PRC20 on Push Chain. This is an unauthorized-mint / broken-invariant condition: the `Enabled` flag is supposed to be the authoritative allowlist gate for which assets may be bridged, but it is not enforced at the only code path that actually performs the mint. This can lead to unauthorized PRC20 minting against a token intentionally excluded from the accounting system, corrupting PRC20 supply/accounting invariants.

### Likelihood Explanation
Likelihood is bounded by the precondition that the token must have been registered at some point (an admin action) and then disabled — this is a normal, expected operational sequence for handling deprecated or compromised tokens, not a privileged-attacker scenario. Once that state exists, exploitation only requires an ordinary user/attacker to trigger a source-chain event (e.g., an `addFunds` gateway call) referencing the disabled token's contract address, which honest Universal Validators will observe and vote on as usual — no malicious validator or privileged action is needed on the Push Chain side.

### Recommendation
Add an explicit `Enabled` check in `depositPRC20` (and any other execution path that resolves a `TokenConfig` for value movement, e.g., `ExecuteInboundGasAndPayload`'s auto-swap paths and `AttachRescueOutboundFromReceipt`) immediately after `GetTokenConfig` returns, returning an error (routed through the existing `FAILED` PCTx / revert flow) if `!tokenConfig.Enabled`. This restores `Enabled` as an effective allowlist/kill-switch consistent with its intended purpose, mirroring the external report's recommendation to enforce an explicit allowlist and provide a working kill switch rather than relying on a flag that is set but never read at the enforcement point.

### Proof of Concept
1. Admin registers `TokenConfig{Chain: "eip155:11155111", Address: "0xUSDC", Enabled: true, NativeRepresentation: {ContractAddress: "0xPRC20USDC"}}`.
2. Admin later sets `Enabled: false` via `MsgUpdateTokenConfig` (e.g., after discovering the token contract on Sepolia was compromised), intending to stop further bridging of this asset.
3. Attacker triggers (or replays) a gateway event on `eip155:11155111` referencing `0xUSDC` as `AssetAddr` with some `Amount` and `Recipient`.
4. Honest Universal Validators observe the event and submit `MsgVoteInbound` with `Inbound{AssetAddr: "0xUSDC", ...}` as usual — nothing in `ValidateBasic`/`ValidateForExecution`/`VoteInbound` checks `Enabled`.
5. Once quorum is reached, `ExecuteInboundFunds` → `depositPRC20` looks up the `TokenConfig` (still resolvable by key even though `Enabled=false`), resolves `NativeRepresentation.ContractAddress`, and mints PRC20 to the recipient via `CallPRC20Deposit` — despite the admin's explicit intent to disable the asset.

Note: I could not find any additional guard elsewhere in the codebase (e.g., in `x/uregistry` keeper methods invoked from `x/uexecutor`) that filters on `Enabled` before this point; the search results consistently show `GetTokenConfig`/`GetTokenConfigByPRC20` performing unconditional lookups. If such a check exists in code outside what the index surfaced (e.g., a filter added elsewhere not captured by the search), that would change this conclusion — a full repository clone via a Devin session would be needed to rule this out with certainty.

func (k Keeper) depositPRC20(
	ctx sdk.Context,
	sourceChain string,
	assetAddr string,
	recipient common.Address,
	amountStr string,
) (*vmtypes.MsgEthereumTxResponse, error) {
	// get token config
	tokenConfig, err := k.uregistryKeeper.GetTokenConfig(ctx, sourceChain, assetAddr)
	if err != nil {
		return nil, err
	}

	if tokenConfig.NativeRepresentation == nil {
		return nil, fmt.Errorf("token config for %s:%s has no native representation", sourceChain, assetAddr)
	}
	prc20Address := tokenConfig.NativeRepresentation.ContractAddress
	prc20AddressHex := common.HexToAddress(prc20Address)

	// convert amount
	amount := new(big.Int)
	amount, ok := amount.SetString(amountStr, 10)
	if !ok {
		return nil, fmt.Errorf("invalid amount: %s", amountStr)
	}

	k.Logger().Debug("EVM call: depositPRC20Token",
		"prc20", prc20AddressHex.Hex(),
		"recipient", recipient.Hex(),
		"amount", amountStr,
	)

	// call PRC20 deposit
	return k.CallPRC20Deposit(ctx, prc20AddressHex, recipient, amount)
}
