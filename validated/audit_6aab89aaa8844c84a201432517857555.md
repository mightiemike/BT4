### Title
Missing slippage protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` allows unexpected asset amounts - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
java-tron's Bancor-style `Exchange` mechanism has three contract types: `ExchangeTransactionContract` (swap), `ExchangeInjectContract` (add liquidity), and `ExchangeWithdrawContract` (remove liquidity). Only `ExchangeTransactionContract` carries an `expected` field that is validated against the actual computed output before execution. `ExchangeInjectContract` and `ExchangeWithdrawContract` have no equivalent minimum/maximum bound field, so the ratio-derived counter-token amount computed at execution time is applied unconditionally, with no way for the caller to bound acceptable outcomes.

### Finding Description
The protobuf definitions show the asymmetry directly: `ExchangeTransactionContract` includes `expected`, while `ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `owner_address`, `exchange_id`, `token_id`, and `quant`. [1](#0-0) 

In `ExchangeTransactionActuator.doValidate()`, the actuator recomputes the counter-token amount via `exchangeCapsule.transaction(...)` and rejects the transaction if it falls below `tokenExpected`, which is exactly the slippage-protection pattern the external report recommends: [2](#0-1) 

By contrast, `ExchangeInjectActuator.execute()` computes `anotherTokenQuant` purely from the pool's current ratio (`secondTokenBalance * tokenQuant / firstTokenBalance` or the inverse) and immediately deducts that amount from the caller's balance, with no bound the caller can set: [3](#0-2) 

Likewise, `ExchangeWithdrawActuator.execute()` computes the counter-token amount to pay out from the current ratio and credits whatever that computes to, again with no floor the caller controls: [4](#0-3) 

Because `ExchangeCapsule.getFirstTokenBalance()`/`getSecondTokenBalance()` (and thus the ratio) can be changed by any intervening `ExchangeTransactionContract` swap broadcast and packed into an earlier position in the same or a prior block, the ratio at inject/withdraw execution time can differ materially from the ratio the user observed when constructing and signing their transaction. [5](#0-4) 

### Impact Explanation
A user submitting `ExchangeInjectContract` can be forced to contribute a larger-than-expected amount of the paired token (since `anotherTokenQuant` is deducted unconditionally from their account in `execute()`), and a user submitting `ExchangeWithdrawContract` can receive a smaller-than-expected amount of the paired token, both due to pool-ratio movement between transaction construction and on-chain execution. This is an accounting/asset-loss issue for the affected account, reachable purely through normal, permissionless broadcast transactions.

### Likelihood Explanation
Any user or bot can move the exchange ratio with an ordinary `ExchangeTransactionContract` swap before a pending `ExchangeInject`/`ExchangeWithdraw` transaction executes; TRON's exchange pools are shared, low-liquidity legacy pools, so ratio movement between submission and confirmation is plausible, especially under network delay or intentional front-running/sandwiching by front-running transactions targeting the same exchange id.

### Recommendation
Add a caller-specified bound field (e.g., `expected`/min-out for withdraw, max-in/expected for inject) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` the same way `ExchangeTransactionActuator` validates `expected`, rejecting the contract if the computed counter-token amount is outside the caller's specified tolerance.

### Proof of Concept
1. User A observes `Exchange#1` with `firstTokenBalance=1_000_000`, `secondTokenBalance=1_000_000` and submits `ExchangeWithdrawContract` withdrawing `100_000` of `firstToken`, expecting ~`100_000` of `secondToken` back.
2. Before A's transaction is packed, User B broadcasts a large `ExchangeTransactionContract` swap against the same exchange id, shifting the ratio heavily (e.g., `secondTokenBalance` drops to `500_000`).
3. A's `ExchangeWithdrawContract` executes using the current (post-swap) ratio in `ExchangeWithdrawActuator.execute()` at lines 74-89, paying out far less `secondToken` than A anticipated, with no mechanism in the contract or actuator to reject the transaction for insufficient output — unlike the equivalent check present for `ExchangeTransactionContract` at lines 217-221 of `ExchangeTransactionActuator.java`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
