### Title
Cairo0 class cache in `StateReaderAndContractManager::get_compiled_from_class_manager` is never re-bound to committed declaration state — (File: crates/blockifier/src/state/state_reader_and_contract_manager.rs)

### Summary
The global `ContractClassManager` class cache is keyed only by `ClassHash`. For Cairo1 classes, a cache hit is re-validated against the authoritative state (`is_declared`) to guard against stale entries left by reverted/never-committed executions. For Cairo0 (deprecated) classes, this re-validation is explicitly skipped, so a class hash that was speculatively compiled and cached (e.g. during gateway mempool validation of a Declare transaction that never gets committed) remains permanently servable as "declared" to any later transaction, without ever being bound back to the real, committed declared-classes state.

### Finding Description
`get_compiled_from_class_manager` branches on the cached class variant: [5](#0-4) 
For `RunnableCompiledClass::V0(_)` (Cairo0), the `match` arm is empty — no check is performed. For any Cairo1 variant, `self.state_reader.is_declared(class_hash)?` is called and the class is rejected as `UndeclaredClassHash` if the check fails. The code comment explains the *reason* the Cairo1 check exists: "existence in the cache does not guarantee [declaration], it might contain a declared class from a reverted block." That exact risk applies equally to Cairo0 classes, but there is no analogous binding check, because `FetchCompiledClasses::is_declared` is documented to "always return `false`" for Cairo0 classes [6](#0-5) , so the implementation simply omits verification for that class type entirely rather than using a real Cairo0-aware binding check.

This cache is not scratch/per-block state — it is the same `ContractClassManager` instance shared across the whole gateway process, constructed once and reused by every `StatefulTransactionValidator` instance created per incoming transaction [2](#0-1) . The stateful validator **fully executes** Declare (and DeployAccount) transactions during ordinary mempool admission — not just their `__validate__` entry point — specifically so a not-yet-committed declare can be checked; the side effect is that `set_and_compile` populates the shared cache for the submitted class hash even though the transaction may never be included in any finalized block (mempool eviction, fee competition, nonce race, dropped by consensus, etc.) [7](#0-6) .

Analogous to the Keycloak flaw — where a cross-session verification artifact is keyed by a coarse identifier (`userId`, `idpAlias`) without being (re-)bound to the specific upstream identity actually verified, letting a different account consume it — here the "verification" that a class hash corresponds to a legitimately declared class is keyed only by `ClassHash` in a long-lived shared cache, and for Cairo0 that binding to the authoritative declared-classes state is never re-checked on subsequent uses.

### Impact Explanation
Once a Cairo0 class hash is cached this way, any later transaction referencing that class hash (e.g. a `deploy_syscall`/library call, or another account whose `class_hash_at` happens to reference it) will have `get_compiled_class` succeed and execute the cached bytecode via this node's gateway/validator path, even though the class was never actually committed as declared in the canonical state. Because the cache is process-local and its population depends on which transactions this particular node happened to speculatively execute, different honest sequencer nodes will disagree on whether that class hash is executable/declared at the same logical state — producing honest-node divergence in validation outcomes and, if such a class is used inside a block a node builds, a state transition / state diff that is not reproducible by the Starknet OS re-execution (which reads only committed, authoritative state, without this ephemeral gateway-side cache), resulting in an unprovable or wrong-committed-root block.

### Likelihood Explanation
Reaching the vulnerable code path requires only submitting an ordinary Declare transaction for a Cairo0 class through the public gateway — fully within reach of a single unprivileged transaction sender, no special privileges, no proposer/operator collusion. The class need not ever be finalized on-chain; any rejection after the (successful) full-execution validation step (e.g., mempool eviction due to fee competition, nonce override, or the block containing it not being finalized) leaves the stale cache entry in place indefinitely (subject to LRU eviction), since nothing besides an explicit whole-cache `clear()` on a full storage-level block revert removes it [8](#0-7)  — and that clear path is not wired into the normal live gateway/mempool rejection flow.

### Recommendation
Apply the same authoritative re-validation to Cairo0 cache hits as is done for Cairo1: extend `FetchCompiledClasses::is_declared`/the underlying state reader to report true declaration status for Cairo0 classes as well (rather than hardcoding `false`), and check it unconditionally in `get_compiled_from_class_manager` regardless of `RunnableCompiledClass` variant, so a cache hit is always re-bound to the current authoritative declared-classes state before being trusted.

### Proof of Concept
1. Submit an RPC Declare transaction for a fresh Cairo0 class `C` (class_hash `h`) to the gateway with the account nonce set correctly.
2. The gateway's `StatefulTransactionValidator::run_validate_entry_point` fully executes the Declare transaction (`perform_validations` → `execute`), which calls `get_compiled_class(h)`, causing `set_and_compile(h, ...)` to populate the process-global `ContractClassManager` cache with `RunnableCompiledClass::V0`.
3. Ensure this Declare transaction is never actually committed (e.g., submit a competing higher-fee transaction with the same nonce so the mempool drops it, or let it be evicted before block inclusion).
4. Submit a second transaction (e.g. a `deploy_syscall`/library-call referencing class_hash `h`) through the same node's gateway/validator.
5. Observe that `get_compiled_from_class_manager` returns the cached class for `h` without any `is_declared` check (since it's `V0`), letting the second transaction validate/execute successfully even though `h` was never declared in committed state — producing results at this node that other honest nodes (without the cached entry) would reject as `UndeclaredClassHash`.

        // Deploy account transaction should be fully executed, since the constructor must run
        // before `__validate_deploy__`. The execution already includes all necessary validations,

                    &actual_cost,
