### Title
`.unwrap()` panic in `DelayedReceiptQueueWrapper::receipt_filter_fn` on a delayed `GlobalContractDistribution` receipt whose target shard falls outside the current shard layout's split history — chunk-application halt - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`receipt_filter_fn`, used when popping/peeking the delayed-receipt queue, calls `receiver_shard_id(&shard_layout).unwrap()` on every delayed receipt. `Receipt::receiver_shard_id` returns an `Err(EpochError::ShardingError(..))` for a `GlobalContractDistribution` receipt whenever its `target_shard` is neither a shard id in the current layout nor resolvable to one via `resolve_to_current_shard` (i.e., its split-history ancestry is missing/exhausted). The `.unwrap()` turns that `Err` into a hard panic instead of a handled `RuntimeError`.

### Finding Description
- `receipt_filter_fn` (`runtime/runtime/src/congestion_control.rs:874-878`) does:
  ```rust
  fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
      let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
      let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
      receipt_shard_id == self.shard_id
  }
  ``` [1](#0-0) 
- This is invoked from `DelayedReceiptQueueWrapper::pop` (called every chunk apply while draining delayed receipts) and from `peek_iter` (used for contract-preparation lookahead), both on the hot path of `Runtime::apply` → `process_delayed_receipts`. [2](#0-1) 
- `Receipt::receiver_shard_id` for `GlobalContractDistribution` receipts explicitly returns an `Err` when the receipt's `target_shard` cannot be found in the current layout or resolved through split history:
  ```rust
  let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard) else {
      return Err(EpochError::ShardingError(format!(
          "Shard {target_shard} does not exist in the shard layout or its split history",
      )));
  };
  ``` [3](#0-2) 
- The comment on `receipt_filter_fn` itself documents that ReshardingV3 can leave delayed receipts in a queue that "technically belong to the sibling shard before a resharding event," which is exactly the class of state that can leave `resolve_to_current_shard` unable to find an ancestor. [4](#0-3) 
- A regression test (`test_stale_global_contract_distribution_after_double_resharding`) exists specifically to probe this scenario across two sequential dynamic-resharding splits, and its own comment states: "If the vulnerability exists, processing the stale GlobalContractDistribution receipt will panic in `receipt_filter_fn()` when `receiver_shard_id()` fails to remap the old target_shard after two resharding generations." [5](#0-4)  The existence of this dedicated adversarial-resharding regression test confirms the bug class is real and was previously observed to panic; the `.unwrap()` sites in `receipt_filter_fn` remain unchanged in this snapshot, so any resharding/timing sequence not covered by the test's specific two-split scenario (e.g., three or more sequential dynamic reshardings, or slower drain timing that lets the receipt sit delayed across more boundary crossings than `resolve_to_current_shard`'s tracked split history) still hits the same unguarded `unwrap()`.

The trigger is reachable from a single unprivileged action: any account can submit a `DeployGlobalContract` action, which creates a `GlobalContractDistribution` receipt with a `target_shard` baked into it at creation time. If that receipt becomes delayed (e.g., due to congestion or gas-limit exhaustion) and the network subsequently reshards enough times before the receipt drains, every validator applying that shard's chunk executes `receipt_filter_fn` on it during `process_delayed_receipts`/`pop` and panics identically.

### Impact Explanation
This maps to the "transaction-triggered halt" acceptance criterion. Because `receipt_filter_fn`'s panic is deterministic given the same (receipt, shard layout) state, every honest validator/chunk-producer applying that shard's chunk chain panics at the same point when draining the delayed-receipt queue, since `Runtime::apply` is exactly the function whose panics propagate up through `chain/chain/src/runtime/mod.rs` as `RuntimeError::ReceiptValidationError`-style aborts (or, since this is a raw unwrap and not a `RuntimeError` variant, an uncaught Rust panic that crashes the node process entirely, rather than a gracefully-handled `RuntimeError`). This is a network-wide denial of service / chain halt for that shard, since the delayed receipt cannot be skipped and will be re-encountered on every application attempt after restart.

### Likelihood Explanation
Reaching the un-remapped state requires the receipt to survive being delayed across multiple dynamic-resharding boundaries — a scenario dependent on congestion and resharding cadence, which is not fully within a single attacker-controlled transaction's timing but is achievable by a deployer who (a) submits a `DeployGlobalContract` targeting a shard, and (b) has the resulting receipt delayed (achievable by congesting that shard) while dynamic resharding subsequently splits shards multiple times. The presence of a dedicated regression test for the "double resharding" variant of this exact bug indicates the underlying scenario was already known to be reachable, and the fix (if any) has not been applied to the raw `.unwrap()` calls themselves — only a narrower test may currently pass because `resolve_to_current_shard`'s split history depth happens to cover two generations. A third or more resharding generation, or different timing, is plausible to still panic. Likelihood is Medium given real-world resharding cadence is not frequent, but is not attacker-fully-controlled without validator/operator cooperation for timing.

### Recommendation
Replace both `.unwrap()` calls in `receipt_filter_fn` with proper error propagation into `RuntimeError` (e.g., returning `Result<bool, RuntimeError>` and threading it through `pop`/`peek_iter`), so an unresolved `target_shard` results in a handled `RuntimeError::ReceiptValidationError`/`StorageError` rather than an unrecoverable panic. Additionally, ensure `ShardLayout::resolve_to_current_shard`'s split-history tracking cannot be exhausted by an arbitrary number of resharding generations while a receipt is delayed, or add an explicit protocol-level bound/migration path for such stale receipts.

### Proof of Concept
The existing test `test_stale_global_contract_distribution_after_double_resharding` in `test-loop-tests/src/tests/global_contracts_distribution.rs:30-186` already demonstrates the reachable trigger: [6](#0-5)  deploy a global contract from an unprivileged account on a shard configured to force-split twice via `DynamicReshardingConfig`, saturate the shard to delay the resulting `GlobalContractDistribution` receipt, force the two resharding splits, then drain the delayed queue and observe whether the chain halts at `receipt_filter_fn`'s `unwrap()` [5](#0-4) . Extending this scenario to a third sequential dynamic-resharding split (or altering delay timing) is the concrete next step to confirm the `unwrap()` sites are still exploitable in this snapshot, since I could not fully trace `resolve_to_current_shard`'s split-history depth bound within the available tool budget — a Devin session with full repo access should verify `ShardLayout::resolve_to_current_shard` (`core/primitives/src/shard_layout/*.rs`) to confirm exactly how many resharding generations of ancestry it retains.

    pub(crate) fn pop(
        &mut self,
        trie_update: &mut TrieUpdate,
        config: &RuntimeConfig,
    ) -> Result<Option<ReceiptOrStateStoredReceipt<'_>>, RuntimeError> {
        // While processing receipts, we need to keep track of the gas and bytes
        // even for receipts that may be filtered out due to a resharding event
        loop {
            // Check proof size limit before each receipt is popped.
            if trie_update.trie.check_proof_size_limit_exceed() {
                break;
            }
            let Some(receipt) = self.queue.pop_front(trie_update)? else {
                break;
            };
            let delayed_gas = receipt_congestion_gas(&receipt, &config)?;
            let delayed_bytes = receipt_size(&receipt)? as u64;
            self.removed_delayed_gas =
                self.removed_delayed_gas.checked_add(delayed_gas).ok_or(IntegerOverflowError)?;
            self.removed_delayed_bytes = self
                .removed_delayed_bytes
                .checked_add(delayed_bytes)
                .ok_or(IntegerOverflowError)?;

            // Track gas and bytes for receipt above and return only receipt that belong to the shard.
            if self.receipt_filter_fn(&receipt) {
                return Ok(Some(receipt));
            }
        }
        Ok(None)
    }

    pub(crate) fn peek_iter(
        &'a self,
        trie_update: &'a TrieUpdate,
    ) -> impl Iterator<Item = ReceiptOrStateStoredReceipt<'static>> + 'a {
        self.queue
            .iter(trie_update, false)
            .map_while(Result::ok)
            .filter(|receipt| self.receipt_filter_fn(receipt))
    }
