### Title
Interest index clock freezes at zero utilization, retroactively over-accruing interest across the dormant gap - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Each vault's `accrue`/`next-index`/`next-liquidity-index` logic only advances the `last-update` timestamp when the computed index actually changes value. At zero utilization the interest rate is `0`, so `calc-multiplier-delta` returns a no-op multiplier and `next-index`/`next-liquidity-index` equal the stored `index`/`lindex`. Because the update to `last-update` is itself gated on `(not (is-eq idx next))`, `last-update` never advances during any period where utilization (and therefore the rate) is zero. When utilization later becomes non-zero, the very next `accrue` computes `time-delta` as `stacks-block-time` minus the stale, frozen `last-update`, and applies the *current* interest rate over that entire stale gap — effectively charging interest as if debt/utilization had existed for the whole dormant period, when it did not.

### Finding Description
The mechanism is present identically in every vault contract, e.g. `v0-vault-usdc.clar`: [1](#0-0) 

`next-index` (and symmetrically `next-liquidity-index`) computes the rate from current `utilization`, and applies it via `calc-multiplier-delta` over `time-delta = stacks-block-time - last-update`: [2](#0-1) 

`accrue()` only persists `index`/`lindex`/`last-update` when they differ from the previous value: [3](#0-2) 

Sequence:
1. Vault has zero (or effectively negligible) debt, so `utilization()` = 0 and `interest-rate()` = 0.
2. Every call to `accrue` (via `deposit`, `redeem`, `system-borrow`, etc.) computes `next-index`/`next-liquidity-index` equal to the stored `index`/`lindex` because the rate is 0, so the guarded `var-set last-update stacks-block-time` branch is skipped — `last-update` stays frozen at its old value while real chain time keeps advancing.
3. This dormant period can last arbitrarily long (many blocks/days), during which `last-update` never moves.
4. A borrow finally occurs. At the moment `accrue` runs inside `system-borrow`, utilization is still computed pre-borrow (still 0), so `last-update` still does not advance on that call.
5. On the *next* interaction that calls `accrue` (a subsequent borrow, deposit, or redeem) after debt now exists, `utilization()` is non-zero and `interest-rate()` > 0. `next-index` computes `time-delta = stacks-block-time - last-update`, where `last-update` is still the stale timestamp from before the entire dormant period — not from when the debt was actually created.
6. The non-zero rate is compounded over this stale, oversized `time-delta`, producing an index jump that charges interest as though the debt (and the corresponding non-zero utilization) had existed for the whole dormant interval, which it did not.

This is the same code-shape as the reported bug class: a value (`last-update`, the "clock") is only mutated conditionally ("advanced only on change"), so it silently goes stale while the state it is supposed to timestamp (utilization/rate) moves in the interim, and a later read consumes the stale value as though it were current.

### Impact Explanation
The resulting index jump inflates `total-debt`/`debt-preview` for every borrower in the vault (via `calc-cumulative-debt` using the jumped `index`), and inflates the treasury fee mint (`calc-treasury-lp-preview`) computed from the erroneous `debt-delta`. Borrowers can be charged debt increases disproportionate to the real elapsed time their debt existed, which can push previously healthy positions into unexpected insolvency/liquidation, and can distort `total-assets`/`total-supply` used for share pricing in `deposit`/`redeem`, mispricing shares for depositors. Because this manifests as an incorrect, one-time non-reversible state mutation to `index`/`lindex`/`principal-scaled`/treasury LP shares, it falls under temporary/permanent freezing of user funds (positions unexpectedly liquidatable, redemption share pricing distorted) rather than a simple yield-timing quirk.

### Likelihood Explanation
This does not require any adversarial multi-block coordination, oracle manipulation, or DAO compromise — it is a natural consequence of a vault experiencing a dormant, zero-utilization period (a very plausible condition for a market with fluctuating supply/borrow demand) followed by resumption of borrowing. Any user or protocol keeper triggering `accrue` transitions (via ordinary `deposit`, `borrow`, or `redeem` calls) can trigger the stale-clock catch-up, making this a naturally occurring rather than contrived condition.

### Recommendation
Update `last-update` unconditionally on every `accrue` call (regardless of whether `index`/`lindex` numerically changed), so `time-delta` is always measured against the true last-accrual timestamp rather than the last timestamp at which the index happened to change value.

### Proof of Concept
1. Deploy vault with zero deposits/borrows (utilization = 0); note `last-update = T0`.
2. Let a long period elapse (many blocks) with no debt-creating activity; each `deposit`/`redeem` call triggers `accrue`, but since `interest-rate()=0`, `next-index == index`, so `last-update` remains `T0`.
3. At time `T1 = T0 + large_delta`, a borrower calls `borrow`, creating debt (accrue inside this call still sees old utilization = 0, so `last-update` stays `T0`).
4. At time `T2` shortly after `T1`, a second interaction (e.g., another deposit or borrow) triggers `accrue`. `utilization()` is now non-zero, so `interest-rate() > 0`. `time-delta = T2 - last-update = T2 - T0` (the entire dormant span, not `T2 - T1`), and this large `time-delta` is compounded at the current non-zero rate into `next-index`, producing an outsized one-time debt/index jump attributable to a period when no debt existed at all.
