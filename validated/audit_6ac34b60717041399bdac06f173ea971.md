### Title
Panicking `.unwrap()` on `receiver_shard_id()` in delayed-receipt draining can halt a shard on a single transaction-triggered `GlobalContractDistribution` receipt - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
The external report describes a cross-chain bridge adapter that does not catch exceptions thrown by receiving contracts, so a single failing message can jam the whole message pathway. The closest reachable analog in `nearcore` is in the deterministic receipt-processing/congestion-control pipeline: `DelayedReceiptQueueWrapper::pop`'s `receipt_filter_fn` calls `Receipt::receiver_shard_id(...).unwrap()` while draining the delayed-receipt queue every chunk. If this call ever returns an `Err` (the shard-layout/split-history lookup for a `GlobalContractDistribution` receipt fails to resolve), the `unwrap()` panics and crashes every honest node applying that chunk — a transaction-triggered halt, analogous to the reported "unhandled exception blocks the message queue."

### Finding Description
Any account can submit a `DeployGlobalContractAction`, which is turned into a `GlobalContractDistribution` receipt carrying a `target_shard` [1](#0-0) . This receipt hops shard by shard via `forward_distribution_next_shard`/`ReceiptSink::forward_or_buffer_receipt` [2](#0-1) , and, like any other receipt, can be pushed into the persistent **delayed-receipt queue** if the local shard is out of compute/proof-size budget when it arrives [3](#0-2) .

When the delayed queue is later drained, `DelayedReceiptQueueWrapper::pop` calls a shard filter that computes the receiver shard **and unconditionally unwraps the result**:
```
fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {
    let shard_layout = self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap();
    let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
    receipt_shard_id == self.shard_id
}
``` [4](#0-3) 

For `GlobalContractDistribution` receipts, `receiver_shard_id` does not simply map an account id to a shard; it must resolve a possibly stale `target_shard` (recorded in an old shard layout) to a shard in the *current* layout via `shard_layout.resolve_to_current_shard(target_shard)`, and explicitly returns `Err(EpochError::ShardingError(...))` when the target shard "does not exist in the shard layout or its split history" [5](#0-4) . This resolution depends on the shard's split-history/ancestor map (`ShardsSplitMapV3`/`ShardsAncestorMapV3`), which is built incrementally from a bounded window of prior shard layouts [6](#0-5) . A `GlobalContractDistribution` receipt that stays delayed/buffered across enough resharding generations (or across a layout-history boundary where the ancestor chain is no longer tracked) can therefore end up with a `target_shard` that `resolve_to_current_shard` cannot find, making `receiver_shard_id` return `Err`.

`receipt_filter_fn`'s `.unwrap()` converts that `Err` into a panic during delayed-receipt draining, which happens inside `DelayedReceiptQueueWrapper::pop`, invoked from `process_delayed_receipts`, which is part of `Runtime::apply`'s deterministic state-transition function run by every validating node [7](#0-6) [8](#0-7) . Because every honest node executes the identical apply logic on the identical delayed queue, the panic is fully deterministic and reproducible — it is not a single-node fault but a synchronized crash across the network for the affected shard, i.e. a transaction-triggered halt.

Notably, the engineering team is aware of a related, narrower instance of this exact class of bug: a regression test explicitly documents that a stale `GlobalContractDistribution` receipt surviving **two** resharding generations while stuck in the delayed queue used to panic in `receipt_filter_fn()`, and a partial fix (`resolve_to_current_shard`) was added [9](#0-8) . This shows the failure mode is real and previously observed; the `receipt_filter_fn`'s `.unwrap()` on `receiver_shard_id()`, however, remains an unconditional panic path rather than a handled/recoverable error for any input this fix does not cover (e.g. deeper resharding chains, layout-history truncation, or any other future `receiver_shard_id` error path).

### Impact Explanation
A panic inside `Runtime::apply`'s delayed-receipt draining crashes the client process for every node applying chunks on the affected shard, since panics in the apply path are not caught as soft errors (contrast with `StorageInconsistentState`, which is returned as a typed error rather than panicking, e.g. for invalid delayed receipts on dequeue [10](#0-9) ). This stops block/chunk production for the shard — a concrete, transaction-triggered chain halt reachable from a single unprivileged `DeployGlobalContract` transaction combined with congestion/resharding conditions that delay the resulting distribution receipt long enough for its `target_shard` to become unresolvable.

### Likelihood Explanation
Triggering this requires: (1) submitting a `DeployGlobalContractAction` (trivially available to any account), and (2) keeping the resulting `GlobalContractDistribution` receipt in the delayed/buffered queue across enough shard-layout changes that `resolve_to_current_shard` cannot map the recorded `target_shard`. The existing regression test in the repo demonstrates that two resharding generations were previously sufficient to reproduce a panic here, and only that specific case has a documented fix. Given dynamic/frequent resharding configurations, or any as-yet-unhandled corner case of the split-history bookkeeping, this is a realistic, low-cost DoS vector, matching the "risk accepted, low probability, high impact" characterization of the analogous CCIP report.

### Recommendation
Replace the `.unwrap()` calls in `receipt_filter_fn` (and the `epoch_info_provider.shard_layout(...).unwrap()` alongside it) with proper error propagation, converting `receiver_shard_id` failures into a typed `RuntimeError`/`StorageError::StorageInconsistentState` (consistent with how other delayed-receipt inconsistencies are already handled) rather than allowing them to panic and halt the chain [4](#0-3) . Additionally, audit all other `.unwrap()`/`.expect()` calls on `receiver_shard_id()` and other resharding-aware shard-resolution functions along the receipt-forwarding and delayed-queue-draining paths for the same class of unhandled-error-induced panic.

### Proof of Concept
The repository's own test demonstrates the underlying mechanism: it deploys a global contract from an account whose shard is scheduled to be force-split twice, saturates that shard's compute budget every block so the resulting `GlobalContractDistribution` receipt is pushed to and stays in the delayed queue through both resharding events, and then stops saturating to let the queue drain — checking that the chain does not stall (`"likely panicked processing stale receipt"`) [11](#0-10) . This confirms the exact code path (`receipt_filter_fn` → `receiver_shard_id` → `resolve_to_current_shard`) is reachable and panic-prone from ordinary transactions; the residual risk is that the `.unwrap()` at [4](#0-3)  still converts any unresolved-shard `Err` into an unconditional panic rather than a handled error, for any scenario the current partial fix does not cover.

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

/// A mapping from the parent shard to child shards. It maps shards from the
/// previous shard layout to shards that they split to in this shard layout.
/// Unlike previous versions of `ShardsSplitMap`, this one:
///   * Only includes shards that are actually split.
///   * Includes the full history of shard splits, i.e. split map of the current
///     layout is a superset of the split map of its parent layout.
///
/// For example if a shard layout with shards `[0, 2, 3, 4]` and split map `{1 => [3, 4]}`
/// splits shard 2 into shards [5, 6] the ShardSplitMap in the resulting layout will be:
/// `{1 => [3, 4], 2 => [5, 6]}`.
pub type ShardsSplitMapV3 = BTreeMap<ShardId, Vec<ShardId>>;

/// A mapping from the child shard to all its ancestors. Parent shard is the first
/// element of the ancestors vector, 'grandparent' shard is the second element, etc.
/// IDs of shards which have no ancestors (i.e. were *not* created by a split) are
/// not present in the mapping.
type ShardsAncestorMapV3 = BTreeMap<ShardId, Vec<ShardId>>;

const VERSION: ShardVersion = 3;

fn validate_and_derive_shard_ancestor_map(
    shard_ids: &Vec<ShardId>,
    shards_split_map: &ShardsSplitMapV3,
) -> ShardsAncestorMapV3 {
    let mut shards_parent_map = BTreeMap::new();
    for (&parent_shard_id, child_shard_ids) in shards_split_map {
        assert!(
            !shard_ids.contains(&parent_shard_id),
            "shard that is split should no longer be used"
        );
        assert!(child_shard_ids.len() > 1, "shard must be split into at least two children");
        for &child_shard_id in child_shard_ids {
            let prev = shards_parent_map.insert(child_shard_id, parent_shard_id);
            assert!(prev.is_none(), "no shard should appear in the map twice");
        }
    }

    let mut shards_ancestor_map = ShardsAncestorMapV3::new();
    for shard_id in shard_ids {
        let mut ancestors = vec![];
        let mut current_id = *shard_id;
        while let Some(parent_shard_id) = shards_parent_map.get(&current_id) {
            ancestors.push(*parent_shard_id);
            current_id = *parent_shard_id;
        }
        shards_ancestor_map.insert(*shard_id, ancestors);
    }
    shards_ancestor_map
}

/// Build `ShardsSplitMapV3` from a sequence of previous shard layouts.
///
/// Assumes that layouts are ordered from newest to oldest, and that there are no duplicates.
/// Ignores layouts with `version()` lower than `VERSION` (this is **not** the struct version).
pub fn build_shard_split_map(layout_history: &[ShardLayout]) -> ShardsSplitMapV3 {
    let mut split_history = ShardsSplitMapV3::new();

    for window in layout_history.windows(2) {
        let current_layout = &window[0];
        let prev_layout = &window[1];

        if current_layout.version() < VERSION || prev_layout.version() < VERSION {
            break;
        }

        debug_assert_ne!(current_layout, prev_layout);

        for shard_id in current_layout.shard_ids() {
            match current_layout.try_get_parent_shard_id(shard_id).expect("invalid shard_id") {
                Some(parent_id) if parent_id != shard_id => {
                    split_history.entry(parent_id).or_default().push(shard_id);
                }
