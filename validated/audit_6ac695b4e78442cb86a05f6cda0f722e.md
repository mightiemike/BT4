### Title
Promise-yield timeout can fire and permanently resolve a yield with `None` before a legitimately-submitted `yield_resume` call ever reaches the yielding shard, due to independence from cross-shard congestion delay - (File: runtime/runtime/src/lib.rs)

### Summary
`resolve_promise_yield_timeouts` decides whether a parked `PromiseYield` receipt has "timed out" purely by comparing the persisted `expires_at: BlockHeight` to the current block height on the yielding account's shard. It has no awareness of whether a resume-triggering receipt (e.g. an oracle's callback `FunctionCall`) that will eventually invoke `promise_yield_resume` is already in flight but stuck in a sender shard's outgoing buffer due to congestion control / the bandwidth scheduler. If that cross-shard delay pushes the resume trigger's arrival past `expires_at`, the yield is irreversibly resolved with a timeout (`data: None`) even though the resuming party did nothing wrong and initiated the resume in time.

### Finding Description
A `PromiseYield` receipt is parked on the yielding account's own shard and awaits a `PromiseResume`; it is never itself cross-shard, but the call that ultimately invokes the resume (`promise_yield_resume` host function via `submit_promise_resume_data`) happens as part of executing *some other* receipt that lands on the yielding account. That triggering receipt frequently originates from a different account/shard (e.g., an oracle's callback), and must cross shards to arrive: [1](#0-0) 

`resolve_promise_yield_timeouts` runs at the very end of every chunk's `process_receipts` and only checks `expires_at` against the current `block_height`, plus whether the `PromiseYieldReceipt` is still present in state — it has no way to know that a resume trigger is already en route but delayed: [2](#0-1) 

The code comment explicitly acknowledges an ordering guarantee, but it only covers the case where the real resume was *already created as a receipt this chunk on the same shard*: [3](#0-2) 

That guarantee does not hold if the trigger receipt itself has not yet arrived at the yielding shard because it is sitting in a sender-shard outgoing buffer under NEP-539 congestion control or bandwidth-scheduler throttling — a receipt can legitimately wait there for many blocks: [4](#0-3) 

Once the synthetic timeout `PromiseResume(data: None)` is processed, the parked yield and its `PromiseYieldStatus` are removed and the yielded receipt executes with `None`: [5](#0-4) 

When the genuine, on-time resume trigger finally arrives and executes `promise_yield_resume`, `submit_promise_resume_data` finds neither the yield receipt nor its status in state and silently returns `Ok(false)` — a no-op, with no error surfaced to the caller: [6](#0-5) 

This mirrors the external report's root cause precisely: a deadline (`grace period` / `expires_at`) is enforced against wall-clock/block-height progress while the user-controlled action needed to avoid the penalty (redeem / resume) can be delayed by the system itself (insufficient escrow positions / cross-shard congestion) — and the user is charged the "timeout" outcome despite having acted correctly and in time.

### Impact Explanation
Any dApp relying on yield/resume across shards (e.g., oracle-fed price callbacks, cross-contract confirmation flows) can have its promise silently resolved with `None` instead of the real value purely because of network/shard congestion, with no error and no recourse — the resume call becomes a permanent no-op once the window is missed. This is an invalid state transition from the contract's perspective (it observes a timeout when a valid resume was submitted in time) and can lead to loss of funds/incorrect execution paths in any contract that treats yield timeouts as an error/cancellation branch, or as a signal to release escrowed value. This is reachable purely by a normal transaction/receipt flow under organic or moderately congested shard conditions and requires no malicious validator or network actor.

### Likelihood Explanation
Likelihood is Medium: it requires (a) a yield/resume pattern where the resuming receipt must cross shards to reach the yielding account, and (b) sustained congestion/bandwidth throttling on the sending shard's outgoing link long enough to push arrival past `expires_at`. Both congestion control and bandwidth scheduling are normal, expected mechanisms (not adversarial), and cross-shard oracle-style resume flows are an intended usage pattern for yield/resume, so this can occur under ordinary network load without any malicious actor.

### Recommendation
Track whether a resume has genuinely been *initiated but not yet delivered* at the granularity that matters for the race, i.e., before the triggering (predecessor) receipt has even reached the yielding shard there is no signal to suppress the timeout. Consider either (a) extending `expires_at` semantics to account for the maximum possible cross-shard delivery delay under full congestion, (b) requiring the timeout resolution to defer if there is any indication of pending cross-shard traffic destined for the yield's `data_id` (harder given the receipt hasn't arrived yet), or (c) surfacing an explicit error/distinguishable status from `submit_promise_resume_data` when it discovers the yield was already resolved (instead of a silent `Ok(false)`), so calling contracts can detect and handle the race instead of silently losing the resume.

### Proof of Concept
1. Contract `B` (on shard `S1`) calls `promise_yield_create`, parking a receipt with `expires_at = h0 + timeout_length` on `S1`.
2. Contract `A` (on shard `S2`) is meant to call back into `B` to resume the yield with real data, before `h0 + timeout_length`. `A` submits this well before the deadline.
3. Shard `S2`'s outgoing link to `S1` becomes congested/bandwidth-limited (per NEP-539), so `A`'s callback receipt sits in `S2`'s outgoing buffer for several blocks past `h0 + timeout_length` (`runtime/runtime/src/congestion_control.rs`, `try_forward`/`buffer_receipt`).
4. At block height `h0 + timeout_length`, `S1`'s `resolve_promise_yield_timeouts` (still has spare compute budget locally, since the congestion is on `S2`'s outgoing side, not `S1`'s incoming side) fires the synthetic `PromiseResume(data: None)`, resolving `B`'s yield with a timeout.
5. Later, `A`'s callback finally arrives on `S1` and executes `promise_yield_resume` → `submit_promise_resume_data` finds no parked yield/state and silently returns `Ok(false)`; `B`'s contract already executed its timeout branch and the real data is lost, even though `A` acted before the deadline.

```markdown
### 4. Forwarding vs buffering (congestion + bandwidth admission)

Every outgoing receipt goes through `ReceiptSink::forward_or_buffer_receipt`
(`congestion_control.rs:162` → `:292`). It computes the receipt's receiver shard,
size, and congestion gas, then calls `try_forward` (`:403`):

1. If `size > max_receipt_size`, size is clamped to `max_receipt_size` for the limit
   comparison (bug workaround for oversized receipts, issue #12606, `:417`).
2. The receiver's `OutgoingLimit` is looked up; a missing entry defaults to
   `{ gas: Gas::MAX, size: 0 }` (`:439`) — since the bandwidth scheduler, a shard may
   send **zero** bytes on a link with no grant.
3. Under `ClampOutgoingGasAdmission` (PV 85) the *admission* gas is clamped to
   `allowed_shard_outgoing_gas` (`:443`), so a single very-expensive receipt cannot be
   blocked forever by the gas limit; pre-85 the full receipt gas is used.
4. Forward iff `forward_limit.gas >= admission_gas && forward_limit.size >= size`
   (`:451`); then the receipt is pushed to `outgoing_receipts` and the limit is
   decremented by the *actual* gas and size (`:453`). Otherwise it is returned
   `NotForwarded` and `buffer_receipt` (`:466`) pushes it onto the outgoing buffer for
   that shard, growing `own_congestion_info` by its size and buffered gas (`:486`).
```

```markdown
### 8. Promise yield / resume (parking and timeout)

A `PromiseYield` receipt, when processed, is simply stored keyed by
`(receiver_id, data_id)` and awaits resume (`process_receipt`, `lib.rs:1431-1434`,
`set_promise_yield_receipt`). Yields are **instant receipts** (`is_instant_receipt`,
`receipt.rs:474`) and confined to a single account, so they never cross shard
boundaries and count as zero congestion gas (`congestion_control.rs:696`).

A `PromiseResume` receipt (`lib.rs:1436`) delivers the awaited data. If it is a
*timeout* resume (`data: None`) and the yield status is `ResumeInitiated`, it is
dropped because a real resume already exists (`lib.rs:1441-1444`). Otherwise, if the
parked yield receipt is found, the runtime removes it and its status, stores the
`ReceivedData`, and executes the yield receipt immediately (`lib.rs:1450-1498`); a
second resume for the same `data_id` finds nothing and is ignored (`lib.rs:1499`).
```

```rust
    fn submit_promise_resume_data(
        &mut self,
        data_id: CryptoHash,
        data: Vec<u8>,
    ) -> Result<bool, VMLogicError> {
        let has_yield_receipt_in_state =
            has_promise_yield_receipt(self.trie_update, self.account_id.clone(), data_id)
                .map_err(wrap_storage_error)?;
        let has_yield_status_in_state =
            has_promise_yield_status(self.trie_update, &self.account_id, data_id)
                .map_err(wrap_storage_error)?;

        if has_yield_receipt_in_state || has_yield_status_in_state {
            self.receipt_manager.create_promise_resume_receipt(data_id, data);
            set_promise_yield_status(
                &mut self.trie_update,
                &self.account_id,
                data_id,
                PromiseYieldStatus::ResumeInitiated,
            );
            return Ok(true);
        }

        Ok(false)
    }
```
