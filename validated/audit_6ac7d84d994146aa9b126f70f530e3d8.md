### Title
Truncated base-fee division in `CalculateGasCost` can zero out payload-execution gas fees, letting an attacker's UEA/CEA payload execute EVM state changes for free - (File: `x/uexecutor/keeper/fees.go`)

### Summary
`CalculateGasCost` unwraps the feemarket's `LegacyDec` base fee into a raw integer with `baseFeeBig.Div(baseFeeBig, big.NewInt(1e18))`, truncating any fractional-upc component. When the network base fee decays to a value below 1 upc (a legitimate, attacker-reachable feemarket state, not a privileged action), the truncated `effectiveGasPrice` becomes `0`, so `gasCost = effectiveGasPrice * gasUsed = 0`. `DeductGasFeesFromReceipt` then short-circuits on `gasCost.Sign() <= 0` and returns `nil` — skipping fee deduction entirely — while the EVM call (UEA payload execution, PRC20 transfers, `executeUniversalTx`, etc.) has already been fully committed. This is the same class of bug as the Union `UToken.redeem()` report: an integer-division round-error makes a computed "amount owed" collapse to zero while the underlying value-moving action still executes in full.

### Finding Description
`CalculateGasCost` (`x/uexecutor/keeper/fees.go:47-91`) computes: [1](#0-0) 
This division assumes the real base fee is always a whole number of upc, per its own comment, but the feemarket's dynamically-adjusted `LegacyDec` base fee (`k.feemarketKeeper.GetBaseFee(sdkCtx)`, called in `DeductGasFeesFromReceipt`) is not guaranteed to stay ≥ 1 whole upc — it can decay to a fractional value as blocks run under target gas usage. [2](#0-1) 
When `baseFeeBig` truncates to `0`, `effectiveGasPrice` is `0`, so `gasCost` is `0` regardless of `gasUsed`. `DeductGasFeesFromReceipt` treats `gasCost.Sign() <= 0` as "nothing to deduct" and returns success without ever calling `DeductAndBurnFees`.

This routine is invoked from multiple production, user-reachable execution paths that perform real state changes before the fee check:
- `ExecutePayload` (`x/uexecutor/keeper/msg_execute_payload.go:87-93`) — any account can submit a gasless `MsgExecutePayload` that triggers a UEA's `executeUniversalTx`, then calls `DeductGasFeesFromReceipt` to charge the UEA for the gas the EVM call consumed.
- `ExecuteInboundGasAndPayload`'s smart-contract/CEA branch (`x/uexecutor/keeper/execute_inbound_gas_and_payload.go:216-256`), which wraps the EVM call and fee deduction in a `CacheContext`, but only rolls back if `feeErr != nil` — if `DeductGasFeesFromReceipt` returns `nil` (because `gasCost == 0`), `writeCache()` commits the EVM state unconditionally.

### Impact Explanation
The impact matches "corruption of ... gas fee accounting" in the allowed-impact list. When base fee truncates to zero, all users (and specifically an attacker submitting `MsgExecutePayload` or inbound CEA payloads while base fee is low) get real EVM execution — including PRC20/UEA state mutations that would normally be gated on the recipient having enough `upc` to pay for gas — without being charged. This breaks the module's fee/gas invariant ("the actual EVM execution gas is deducted from this UEA's balance") and lets a recipient/UEA with zero `upc` balance still receive fully executed, committed payloads, defeating `DeductGasFeesFromReceipt`'s only purpose (see the module's own design note in `x/uexecutor/README.md:216` about gas being deducted from the UEA). This is a genuine free-execution / broken-accounting bug, but it does **not** by itself mint, steal, or drain user/protocol asset balances the way the UToken bug drains `assetManager` — it only voids fee collection on the uexecutor module (whose fees are burned, not paid to a specific victim).

### Likelihood Explanation
Reachability depends entirely on whether the feemarket's actual `GetBaseFee()` value can realistically fall under 1 raw upc unit (i.e., under `1e18` in `LegacyDec` internal storage, or under `1.0` when unwrapped). I could not confirm the feemarket's floor/minimum base fee parameter (`MinGasPrice` in `app/cosmos/min_gas_price.go` and `app/ante/validator_tx_fee.go` appeared relevant but I did not get to inspect their exact values/interaction with the EVM feemarket module's base fee floor before running out of iterations). If the network enforces a base fee floor well above 1 upc (which is likely, given `upc` is an extremely fine denomination, 1e18 upc = 1 PC), this bug is very unlikely to be practically triggerable by an ordinary attacker and would only occur in a misconfigured or extreme low-usage scenario. This is the key unresolved uncertainty.

### Recommendation
- In `CalculateGasCost`, do not truncate the base fee before comparison/multiplication. Perform the `effectiveGasPrice * gasUsed` computation while `baseFee` is still a `LegacyDec` (or scale `gasUsed` up before multiplying, then divide at the very end, rounding up rather than down) so a positive fractional-upc base fee never collapses to an integer `0`.
- In `DeductGasFeesFromReceipt`, distinguish "no fee owed because gasUsed == 0" from "fee rounded to zero despite gasUsed > 0" — the latter should still charge a minimum of 1 upc (round up) rather than silently skip deduction, preserving the fee-burn invariant regardless of feemarket precision.
- Verify (this needs confirmation from feemarket module config) whether `GetBaseFee` can ever legitimately return a value whose whole-upc part is `0`; if the feemarket enforces a floor safely above `1e18`, downgrade this from an active vulnerability to a defensive hardening item.

### Proof of Concept
1. Drive the network's EIP-1559 feemarket base fee down (via sustained low block gas usage) until `feemarketKeeper.GetBaseFee(ctx)` returns a `LegacyDec` whose integer (upc) part is `0` (e.g., `0.9`).
2. Submit `MsgExecutePayload` (gasless, callable by any account, see `x/uexecutor/README.md` authorization notes) targeting a UEA whose EVM balance is `0 upc`, with a payload that performs a state-changing call (e.g., an ERC20/PRC20 transfer) and consumes non-zero `gasUsed`.
3. In `ExecutePayload`, `CallUEAExecutePayload` executes and commits the EVM call; `DeductGasFeesFromReceipt` is called afterward: `CalculateGasCost` truncates `baseFeeBig` to `0`, produces `gasCost = 0`, and returns early without deducting/burning anything.
4. Verify on-chain that the payload's state changes persisted while the UEA's `upc` balance remained unchanged (no fee burned) — an attacker with an empty-balance UEA obtained free EVM execution, bypassing the intended gas-fee accounting invariant.
