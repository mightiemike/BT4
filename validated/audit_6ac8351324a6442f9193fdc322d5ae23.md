Confirmed: `get_partial_transaction_result_option` (called from the production `TxStatus` RPC path used by the `tx`/`tx_status`/`EXPERIMENTAL_tx_status`/`broadcast_tx_commit` JSON-RPC methods) calls `Chain::get_recursive_transaction_results`, which is unbounded native Rust recursion with no depth cap.

### Title
Unbounded recursive receipt-outcome traversal reachable via `tx`/`tx_status` RPC causes stack-overflow node crash - (File: chain/chain/src/chain.rs)

### Summary
`Chain::get_recursive_transaction_results` recursively walks the execution-outcome tree of a transaction by following `outcome.receipt_ids` with genuine (non-tail) Rust function calls and no depth limit, analogous to the unbounded recursive de-schedule/re-schedule signaling loop in CVE-2020-29566 that let an external actor drive Xen into a stack overflow.

### Finding Description
`get_recursive_transaction_results` fetches the outcome for an id, pushes it, then for every `receipt_id` in that outcome recurses into itself again: [1](#0-0) 

This function is invoked by both `get_final_transaction_result`: [2](#0-1) 

and, critically, by `get_partial_transaction_result_option`, which is the function the production RPC path uses: [3](#0-2) 

`get_partial_transaction_result_option` is reached from `ViewClientActor::get_tx_status`, which serves the `TxStatus` message backing the JSON-RPC `tx`, `tx_status`, `broadcast_tx_commit`, and `send_tx` (with `wait_until`) endpoints: [4](#0-3) [5](#0-4) [6](#0-5) 

Any unprivileged RPC caller who knows a transaction hash (their own submitted transaction, or any public on-chain transaction hash) can trigger this recursive walk. The recursion depth is bounded only by the depth of the receipt/callback chain the transaction produced, not by any explicit limit. The codebase already recognizes this exact bug class and has fixed it once for a related lookup (`ReceiptToTx`), which enforces `MAX_DEPTH = 1000` and returns `DepthExceeded` instead of recursing unbounded: [7](#0-6) 

No equivalent guard exists for `get_recursive_transaction_results`.

A malicious contract can trivially build an arbitrarily deep receipt/promise chain. The `max_self_recursion_delay` test contract demonstrates self-chaining cross-contract calls purely to maximize the number of hops within a single receipt's gas budget: [8](#0-7) 
and an integration test confirms depths in the tens-to-low-hundreds are achievable from a single call with a single gas budget: [9](#0-8) 
Because each hop's gas budget resets when a fresh receipt/transaction is created (an attacker can keep resubmitting new transactions each carrying a fresh prepaid-gas allotment to extend the same logical promise chain across many blocks), the achievable receipt-outcome tree depth for a single transaction hash is not bounded by a single 300 Tgas budget — it can be grown over many blocks into the thousands, well past what a typical OS thread stack can absorb via non-tail Rust recursion (each frame holds a `Vec<ExecutionOutcomeWithIdView>` index, an inner `for` loop, and error-propagation state).

### Impact Explanation
Because `ViewClientActor` runs as a shared multithread actor serving RPC queries for the node (not sandboxed per request), a stack overflow inside this recursive call aborts the process (Rust has no way to catch a stack overflow — it triggers an abort/SIGSEGV via the guard page), crashing the entire node/validator process that answers RPC queries for that shard. This is a transaction-triggered halt of the affected node: any unprivileged caller who submits or discovers a transaction with a sufficiently deep receipt chain and then queries `tx`/`tx_status`/`broadcast_tx_commit` against a node serving that shard can crash the process, a concrete Denial of Service matching the accepted impact criteria (transaction-triggered halt).

### Likelihood Explanation
The attacker needs only: (1) permission to submit ordinary function-call transactions (any signer), (2) a contract capable of chaining promises to build a deep outcome tree (trivial, demonstrated by existing test contracts), and (3) the ability to call a public JSON-RPC `tx`/`tx_status` endpoint, which is offered by every RPC node by default. No validator, network, or privileged access is required, making this a fully unprivileged, remotely triggerable path.

### Recommendation
Convert `get_recursive_transaction_results` to an iterative traversal using an explicit work queue/stack (as already done elsewhere in the codebase, e.g. `TrieRecordingStorage::get_subtree_size`'s non-recursive `VecDeque` traversal, and the depth-capped `ReceiptToTx` lookup) or add an explicit maximum traversal depth/outcome count that returns a client-facing error (e.g. `DepthExceeded`) instead of continuing to recurse, mirroring the pattern already applied to `GetReceiptToTx`.

### Proof of Concept
1. Deploy a contract exposing a method like `max_self_recursion_delay` (already present in the test contract) that repeatedly issues `promise_batch_create` + `promise_batch_action_function_call_weight` back to itself, and/or chain many separate transactions each re-invoking the pattern with fresh prepaid gas to extend the total callback chain across blocks, producing an execution-outcome tree whose receipt-id chain depth exceeds the thread's stack capacity (tens of thousands of hops, achievable over enough blocks given no depth cap exists on-chain for this pattern).
2. Submit the initiating transaction to a target RPC node that tracks the relevant shard.
3. Call the `tx` or `tx_status` (or `broadcast_tx_commit`) JSON-RPC method with that transaction's hash.
4. `ViewClientActor::get_tx_status` → `Chain::get_partial_transaction_result_option` → `Chain::get_recursive_transaction_results` recurses once per receipt-id hop with no depth check, exhausting the thread stack and crashing the node process — a remotely triggerable Denial of Service, directly analogous to the unbounded recursive re-schedule loop described in CVE-2020-29566.

    fn get_recursive_transaction_results(
        &self,
        outcomes: &mut Vec<ExecutionOutcomeWithIdView>,
        id: &CryptoHash,
        require_all_outcomes: bool,
    ) -> Result<(), Error> {
        let outcome = match self.get_execution_outcome(id) {
            Ok(outcome) => outcome,
            Err(err) => return if require_all_outcomes { Err(err) } else { Ok(()) },
        };
        outcomes.push(ExecutionOutcomeWithIdView::from(outcome));
        let outcome_idx = outcomes.len() - 1;
        for idx in 0..outcomes[outcome_idx].outcome.receipt_ids.len() {
            let id = outcomes[outcome_idx].outcome.receipt_ids[idx];
            self.get_recursive_transaction_results(outcomes, &id, require_all_outcomes)?;
        }
        Ok(())
    }

/// Handler-level: write synthetic ReceiptToTx rows forming chain of 1001
/// FromReceipt entries (exceeds MAX_DEPTH=1000). Verify DepthExceeded
/// returned with originally queried receipt_id.
#[test]
fn test_receipt_to_tx_depth_exceeded() {
    init_test_logger();

    let mut env = TestLoopBuilder::new().epoch_length(EPOCH_LENGTH).track_all_shards().build();

    let store = env.validator().store();
    let mut store_update = store.store_update();

    // Chain of 1002 receipt IDs: receipt_0 → receipt_1 → ... → receipt_1001.
    // receipt_0..receipt_1000 are FromReceipt → next. receipt_1001 is
    // FromTransaction (terminal — never reached).
    let chain_len = 1002usize;
    let receipt_ids: Vec<CryptoHash> =
        (0..chain_len).map(|i| CryptoHash::hash_bytes(&(i as u32).to_le_bytes())).collect();

    // Terminal node: receipt_1001 → tx.
    store_update.insert_ser(
        DBCol::ReceiptToTx,
        receipt_ids[chain_len - 1].as_ref(),
        &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {
            origin: ReceiptOrigin::FromTransaction(ReceiptOriginTransaction {
                tx_hash: CryptoHash::hash_bytes(b"tx"),
                sender_account_id: "sender".parse().unwrap(),
            }),
            receiver_account_id: "receiver".parse().unwrap(),
            shard_id: ShardId::new(0),
        }),
    );

    // Intermediates: receipt_i → receipt_{i+1}.
    for i in 0..chain_len - 1 {
        store_update.insert_ser(
            DBCol::ReceiptToTx,

            &ReceiptToTxInfo::V1(ReceiptToTxInfoV1 {

                    parent_receipt_id: receipt_ids[i + 1],

        method_name.as_ptr() as u64,
        argument_bytes.len() as u64,
        argument_bytes.as_ptr() as u64,

        gas_fixed,
        gas_weight,
    );
