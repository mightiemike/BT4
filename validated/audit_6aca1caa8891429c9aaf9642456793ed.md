### Title
`validate_shadow_parent_burnchain` no-ops when the shadow parent header is not yet in the local staging DB, allowing a crafted block-commit's `parent_vtxindex`/`parent_block_ptr` to bypass shadow-parent consistency checks on nodes lagging in shadow-block awareness - (File: `stackslib/src/chainstate/nakamoto/shadow.rs`)

### Summary
`NakamotoChainState::validate_shadow_parent_burnchain` only enforces the "block-commit `parent_vtxindex` must be 0 and `parent_block_ptr` must equal the shadow parent's sortition height" invariant when the local node's staging DB already contains the parent block's header [1](#0-0) . Since shadow blocks are explicitly inserted post-hoc, per-node, "not consensus-relayed" [2](#0-1) , a node that hasn't yet applied shadow-repair tooling will silently no-op this check for a block whose parent is (unbeknownst to it) a shadow block, while a node that has the shadow block loaded enforces it and rejects the same block+commit pair. Since this check is only run once, at initial `accept_block`/staging-insertion time, and never re-run when the block is later processed, a bad block ingested during the "lagging" window becomes permanently part of that node's canonical history.

### Finding Description
The broken equality is: `validate_shadow_parent_burnchain(node_with_shadow_block, block, commit)` == `validate_shadow_parent_burnchain(node_without_shadow_block, block, commit)`.

Tracing the code:
- `validate_shadow_parent_burnchain` first does `staging_db.get_nakamoto_block_header(&block.header.parent_block_id)`; if `None`, it returns `Ok(())` immediately, before ever checking `is_shadow_block()`, `parent_vtxindex`, or `parent_block_ptr` [1](#0-0) . Only if the header is present and is a shadow block does it enforce `block_commit.parent_vtxindex == 0` and `block_commit.parent_block_ptr == parent_sn.block_height` [3](#0-2) .
- This function is invoked exactly once, from `validate_normal_nakamoto_block_burnchain`, which itself is called only from `NakamotoChainState::accept_block` at the moment a block is first ingested into the staging DB [4](#0-3) [5](#0-4) . It is not re-invoked later when the block is actually appended/processed via `process_next_nakamoto_block`, which only checks Stacks-level header linkage (`parent_block_id` equality), not burnchain block-commit fields [6](#0-5) .
- The underlying burnchain (sortition-level) validation of the commit's `parent_vtxindex`/`parent_block_ptr` (`leader_block_commit.rs`'s `check_block_commit`) is much looser: for a "maybe shadow" commit (`parent_vtxindex == 0`), it only requires *some* sortition snapshot to exist at `parent_block_ptr` — it does not require that height to actually correspond to the real shadow parent tenure [7](#0-6) . This means an attacker-controlled commit with `parent_vtxindex = 0` and `parent_block_ptr` pointing at an arbitrary unrelated past sortition height (not the true shadow-tenure height) can win a sortition on all nodes identically (deterministic burnchain consensus), independent of any node's local Stacks chainstate.
- The Stacks-level block itself must still declare the *true* shadow block as `parent_block_id` to be a valid chain continuation, so `validate_shadow_parent_burnchain` is the only guard that cross-checks the miner's declared burnchain parent pointer against the actual Stacks-level shadow parent. It is gated on local staging-DB knowledge rather than deterministic burnchain state, so its outcome is not guaranteed uniform across honest nodes.

Exploit flow: attacker (a single miner, using their own BTC) crafts a `LeaderBlockCommitOp` with `parent_vtxindex = 0` and `parent_block_ptr` pointing to an arbitrary past sortition (not the real shadow tenure height), wins the sortition, and mines/broadcasts a Nakamoto block whose `parent_block_id` is the real shadow block. Any node that has not yet ingested/loaded that shadow block into its staging DB (i.e., hasn't run the emergency shadow-repair tooling yet) will have `validate_shadow_parent_burnchain` return `Ok(())` as a no-op and will accept/store the block if the rest of validation (signer signatures, etc.) passes. A node that already has the shadow block loaded will reject the same block outright. Because the check runs only at initial ingestion and is never repeated, once the "lagging" node later applies the shadow-repair tooling, the previously-accepted bad block becomes processable and gets appended permanently to that node's canonical chain, without ever being re-validated against the now-known shadow parent.

Existing guards that do *not* prevent this: `check_tenure_tx`/tenure continuity and the "discontinuous Nakamoto Stacks block" check only verify that `parent_block_id` hash-links correctly to a known parent header — they don't inspect the block-commit's `parent_vtxindex`/`parent_block_ptr` fields at all [8](#0-7) . `verify_signer_signatures` only checks that stackers signed the block content, not the commit's burnchain fields. `common_validate_against_burnchain`/`validate_normal_against_burnchain` checks VRF proof/seed and miner-key linkage but is a separate call from `validate_shadow_parent_burnchain` and does not substitute for it.

### Impact Explanation
This is a minority-triggerable static-validation divergence: two honest nodes, differing only in whether they have locally ingested a given shadow block (a purely local, out-of-band, per-node administrative action), reach different accept/reject verdicts for an identical block+commit pair. If the "lagging" node later catches up (applies shadow-repair tooling), the previously accepted bad block is never re-validated and becomes permanently part of its canonical chain — producing a chain split between nodes that consistently enforced the check from the start and any node that had a window of staleness. This matches the "High – minority-triggerable ... static-validation divergence, temporary tip disagreement" category (and could escalate toward Critical if the divergent block becomes permanently canonical on some fraction of the network, since shadow blocks/tenures are, by design, not consensus-relayed and re-sync via block hash/ID rather than via this specific validation).

### Likelihood Explanation
Preconditions: an emergency shadow-chainstate-repair scenario must exist (i.e., there was an empty prepare phase requiring shadow tenures) — this is already an "emergency tooling" code path, not routine operation, and shadow repair is described as manually applied per-node/per-release rather than automatically synchronized. The attacker needs to win a single Bitcoin sortition with a crafted commit (feasible for any miner with sufficient BTC bidding — this fits the "single miner slot" unprivileged-attacker model) and does not need majority stake or signer control; they only need signers to sign a block whose commit's `parent_vtxindex`/`parent_block_ptr` fields they don't independently re-verify. Feasibility depends on catching honest nodes in the "shadow-repair not yet applied" window, which is realistically narrow (repair tooling is meant to be applied promptly/uniformly), reducing but not eliminating repeatability.

### Recommendation
Do not treat "parent header absent from local staging DB" as equivalent to "parent is not a shadow block." Instead, `validate_shadow_parent_burnchain` should determine shadow-parent status from a source of truth that is uniform across nodes (e.g., check the burnchain/sortition DB for whether a Stacks tenure/sortition exists with no corresponding non-shadow block-commit, or defer processing until the parent header is resolvable — mirroring the "no parent; cannot process yet" deferral used elsewhere — rather than silently returning `Ok(())`). Additionally, re-run `validate_shadow_parent_burnchain` (or an equivalent check) at actual block-processing/append time, not only at initial `accept_block` ingestion, so that blocks accepted during a temporary staleness window are re-validated once the true parent becomes known before being appended to the canonical chain.

### Proof of Concept
Rust integration test plan (two `StacksChainState`/`SortitionDB` instances built from the same burnchain/test harness, following the pattern in `stackslib/src/chainstate/nakamoto/tests/node.rs`'s shadow-tenure tests):
1. Build a common chain history up to a shadow tenure using `TestPeer`/`make_shadow_tenure` helpers (as in `stackslib/src/chainstate/nakamoto/tests/node.rs:2517` `make_shadow_tenure`), producing `shadow_block`.
2. Clone the chainstate into two instances, "Node A" and "Node B" (or use two separately-initialized `TestPeer`s fed the identical burnchain/sortition history).
3. On Node A: call `process_shadow_block(&mut chain_state_a, &mut sort_db_a, shadow_block.clone())` so the shadow block is fully ingested and processed (mirroring `stackslib/src/chainstate/nakamoto/shadow.rs:884-954`).
4. On Node B: do *not* call `process_shadow_block`/`add_shadow_block` — leave its staging DB without the shadow header.
5. Craft a `LeaderBlockCommitOp` with `parent_vtxindex = 0` and `parent_block_ptr` set to an arbitrary unrelated valid sortition height (not the true shadow tenure height), and a `NakamotoBlock` whose `header.parent_block_id` equals `shadow_block.block_id()`, signed by the current signer set.
6. On Node A, call `NakamotoChainState::accept_block(...)` (or `validate_shadow_parent_burnchain` directly, as in `stackslib/src/chainstate/nakamoto/tests/node.rs:2349-2407`) with this block+commit; assert it returns `Err(ChainstateError::InvalidStacksBlock(_))`.
7. On Node B, call the same `accept_block`/`validate_shadow_parent_burnchain` with the identical block+commit; assert it returns `Ok(())` and the block is stored in Node B's staging DB.
8. Then apply `process_shadow_block` (or equivalent shadow-repair ingestion) on Node B so its shadow parent becomes known, and drive `process_next_nakamoto_block` to advance Node B's tip.
9. Assert the final equality check: `NakamotoChainState::get_canonical_block_header(chain_state_a.db(), &sort_db_a)` (canonical tip excludes the bad block) != `NakamotoChainState::get_canonical_block_header(chain_state_b.db(), &sort_db_b)` (canonical tip includes the bad block) — demonstrating the two honest nodes have permanently diverged on canonical chain tip from processing the identical block+commit pair.
