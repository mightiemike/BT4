### Title
Stale global class-cache entries for Cairo0 (V0) classes can be served without a declaration check after a block/proposal revert - ([File: crates/blockifier/src/state/state_reader_and_contract_manager.rs])

### Summary
`StateReaderAndContractManager::get_compiled_from_class_manager` verifies that a cached class is still actually declared before serving it from the process-global `ContractClassManager` cache — but only for Cairo1 (non-`V0`) classes. Cairo0 (`V0`) classes are returned straight from the cache with no re-validation, even though the surrounding comment explicitly acknowledges the cache can hold "a declared class from a reverted block."

### Finding Description
`get_compiled_from_class_manager` reads from a node-global, cross-block `ContractClassManager`/`GlobalContractCache` (shared across proposals and blocks, not reset per block) [1](#0-0) . When a class hash is found in this cache, the code branches on class type:

```
match &runnable_class {
    RunnableCompiledClass::V0(_) => {}
    _ => {
        // The Cairo1 class is cached; verify it is declared,
        // since existence in the cache does not guarantee that
        // (it might contain a declared class from a reverted block, for example).
        if !self.state_reader.is_declared(class_hash)? {
            return Err(StateError::UndeclaredClassHash(class_hash));
        }
    }
}
``` [2](#0-1) 

For `V0` (Cairo0/deprecated) classes, no equivalent freshness check is performed. The `FetchCompiledClasses::is_declared` documentation itself states "Cairo 0 classes always return `false`," so the mechanism used to protect Cairo1 classes structurally cannot be reused for Cairo0 classes [3](#0-2) .

This global class cache (`RawClassCache`/`GlobalContractCache`) is populated whenever `get_compiled_classes` is called and `set_and_compile` stores the result, independent of whether the surrounding block/proposal is ultimately committed [4](#0-3) , [5](#0-4) . The batcher/consensus flow builds and aborts proposals frequently (`abort_proposal`, `abort_active_proposal`, `BlockBuilder::abort_block`) without clearing this class cache [6](#0-5) , [7](#0-6) , and the batcher also supports explicit block reverts that roll back committed state and the class-manager marker while the in-memory compiled-class cache is unaffected [8](#0-7) , [9](#0-8) .

As a result, if a Cairo0 `DECLARE` transaction is executed (compiling/caching its class) in a proposal or block that is subsequently aborted or reverted, the compiled V0 class remains resident in the shared cache. A later, unrelated transaction (e.g., a `DEPLOY_ACCOUNT`, `INVOKE`, or `REPLACE_CLASS` referencing that same class hash on a contract address) submitted by any unprivileged sender can trigger `get_compiled_class` and receive the stale V0 compiled class from cache — bypassing the "is this class actually declared in current committed state" check that exists only for Cairo1 classes.

### Impact Explanation
If a class that should be considered undeclared (because its declaration never made it into canonical, committed state) is nonetheless served for execution, a node can successfully execute a transaction that should fail with `UndeclaredClassHash`. This produces execution results, state diffs, and consequently a state root/block hash that differ from what an honest node without the stale cache entry (or a node whose cache was cleared) would produce — a state-committer/consensus divergence, i.e., wrong committed root/block hash or a network unable to agree on the block. It can also let an unprivileged transaction sender effectively deploy/invoke logic under a class hash that the protocol does not (yet, or no longer) consider declared, which is an unauthorized/incorrect account action from the protocol's point of view.

### Likelihood Explanation
The condition requires two independently plausible, unprivileged-transaction-reachable events on the same node process: (1) a Cairo0 `DECLARE` (or a class compiled via `get_compiled_classes` during any block attempt) being cached during a proposal/block build that then gets aborted or reverted, and (2) a subsequent transaction on the same node referencing that class hash before the cache entry is naturally evicted (LRU) or the node restarts. Proposal aborts, validation timeouts, and interrupted proposals are routine occurrences in normal consensus operation (not merely malicious-actor scenarios) [10](#0-9) , so the cache-population precondition is easy to hit; the real gating factor is timing of a second transaction referencing the same class hash before eviction, and this reasoning is my inference from the code comment and cache lifecycle, not a proof of an end-to-end exploit against consensus safety — I was not able to fully trace whether other layers (e.g., `is_declared` calls elsewhere, storage-level `is_declared`/`get_class_hash_at` checks in the caller stack for `V0` deploys) independently prevent using an undeclared V0 class hash for a deploy/invoke path.

### Recommendation
Extend the freshness verification in `get_compiled_from_class_manager` to also cover `RunnableCompiledClass::V0`, using a Cairo0-specific "is this class hash actually deployed/declared in the current committed state" check (e.g., verifying against `get_class_hash_at`/state-diff-derived declaration data rather than relying on `is_declared`, which by design only tracks Cairo1 classes). Alternatively, ensure the global `ContractClassManager` cache is cleared or entries invalidated whenever a proposal is aborted or a block is reverted, so that classes compiled during non-committed execution paths cannot leak into subsequent, unrelated transaction executions.

### Proof of Concept
Not independently reproduced in this review; the sequence to demonstrate would be:
1. Submit/execute (in a proposal or block build that will not be committed) a `DECLARE` transaction for a Cairo0 class `C`, causing `StateReaderAndContractManager::get_compiled_from_class_manager` to call `set_and_compile` and populate the global `ContractClassManager` cache with `RunnableCompiledClass::V0` for `class_hash(C)` [4](#0-3) .
2. Abort/interrupt that proposal (e.g., via `abort_proposal`/`abort_active_proposal`) or revert the block via `revert_block`, so that `C` is not declared in the canonical committed state [6](#0-5) , [8](#0-7) .
3. Submit a new transaction (e.g., `DEPLOY_ACCOUNT` or `INVOKE`) on a contract with `class_hash = class_hash(C)`, causing `get_compiled_class` to hit the cache and return the V0 class without any `is_declared`-equivalent check [2](#0-1) .
4. Compare execution/state-diff results against a node whose cache does not contain `C` (e.g., cold cache) to confirm divergence.

// This function will panic if the storage reader fails to revert.
pub fn revert_block(storage_writer: &mut StorageWriter, target_block_marker: BlockNumber) {
    let txn = storage_writer
        .begin_rw_txn()
        .unwrap()
        .revert_header(target_block_marker)
        .unwrap()
        .0
        .revert_body(target_block_marker)
        .unwrap()
        .0

        .unwrap()
        .0
