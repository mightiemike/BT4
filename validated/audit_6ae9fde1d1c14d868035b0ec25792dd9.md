Based on my investigation, I found a genuine analog to the tx.origin trust-during-initialization bug class in the merchant custom app ("ShopifyAdmin distribution") authentication path.

### Title
Unvalidated `shop` query parameter accepted for cross-tenant session creation in merchant custom app auth strategy - (File: `packages/apps/shopify-app-remix/src/server/authenticate/admin/authenticate.ts`)

### Summary
For apps configured with `AppDistribution.ShopifyAdmin` (merchant custom apps), the normal OAuth/session-token trust chain is disabled — analogous to RocketStorage's `storageInit == false` branch that relaxes validation and trusts an alternate, weaker signal. In this "special mode," the `shop` value that seeds the session is read directly from the URL query string without going through `sanitizeShop`, unlike every other code path in the library.

### Finding Description
In `getSessionTokenContext` [1](#0-0) , when `config.isEmbeddedApp`/`config.distribution !== AppDistribution.ShopifyAdmin`, `shop` is derived from a cryptographically-authenticated session token's `dest` claim (JWT signed with the app's secret): `validateSessionToken` → `dest.hostname` [2](#0-1) .

However, for `AppDistribution.ShopifyAdmin` (the branch taken by merchant custom apps), the code instead does:
```
const url = new URL(request.url);
const shop = url.searchParams.get('shop')!;
```
with **no `sanitizeShop` call and no signature/JWT verification of this value** [3](#0-2) . This unvalidated `shop` is passed straight into `strategy.authenticate()`, which for this distribution is `MerchantCustomAuth.authenticate` [4](#0-3) . That method calls `this.api.session.customAppSession(shop)`, which builds a `Session` object stamped with whatever `shop` string was supplied, paired with the single statically-configured `adminApiAccessToken` for the app [5](#0-4)  (this does call `sanitizeShop` with `throwOnInvalid`, but only *format*-validates that `shop` ends in a Shopify domain suffix — it does not verify that the token was actually issued for, or that the caller actually represents, that shop).

This mirrors the RocketStorage pattern exactly: the "strict" verification path (JWT/session-token validation, analogous to `contract.exists` check) is bypassed in a special mode (`ShopifyAdmin` distribution, analogous to `storageInit == false`), and a weaker, attacker-influenced signal (`tx.origin == guardian`, analogous to a raw unauthenticated `shop` query parameter) is trusted instead.

### Impact Explanation
Because `session.shop` in the resulting `Session` is attacker-controlled (any value from the URL, only regex-validated for being a `*.myshopify.com`-style domain), and the app's single static `adminApiAccessToken` is reused for all `shop` values, any request handler that branches on `session.shop` (e.g., logging, webhook shop association, per-shop data storage keyed off `session.shop`, or app logic that trusts `session.shop` to scope database queries) can be tricked into operating under an attacker-chosen shop identity while still using the real access token. This is a cross-tenant identity confusion vector: an anonymous request with `?shop=victim-or-arbitrary.myshopify.com` produces a `Session` object claiming to belong to that shop, without any proof the request originated from that shop or its App Bridge session.

### Likelihood Explanation
This is only reachable for apps that opt into `AppDistribution.ShopifyAdmin` (merchant custom/admin-created apps), a documented, narrower deployment mode. It requires no privileged actor and no leaked secret — a single anonymous HTTP request with an arbitrary `shop` query parameter is enough to reach `MerchantCustomAuth.authenticate` and mint a `Session` for that shop string, since `respondToOAuthRequests` is a no-op for this strategy [6](#0-5)  and there is no session-token/HMAC check gating this branch before `shop` is read.

### Recommendation
Sanitize/validate `shop` from the query string using `api.utils.sanitizeShop` at the point it is extracted in `getSessionTokenContext` for the `ShopifyAdmin` distribution branch (consistent with every other place `shop` is read from a query string in this codebase, e.g. `validate-shop-and-host-params.ts`). More importantly, document explicitly (short term) that for merchant custom apps, the library does not authenticate the caller's association with `shop` — it is the app developer's responsibility to add their own authentication in front of this route, since `respondToOAuthRequests` and session-token validation are both skipped for this distribution. Long term, consider requiring an explicit, signed proof of shop identity (or restrict `customAppSession` shop selection to a configured allow-list) rather than trusting a raw query parameter.

### Proof of Concept
1. Configure a Shopify app with `distribution: AppDistribution.ShopifyAdmin` and a static `adminApiAccessToken`.
2. As an anonymous client, send `GET /app?shop=any-arbitrary-store.myshopify.com` (no session token, no App Bridge context, no prior OAuth).
3. `authStrategyFactory`'s `authenticateAdmin` reaches `getSessionTokenContext`, takes the `ShopifyAdmin` branch, reads `shop` directly from the query string unsanitized [3](#0-2) , and calls `MerchantCustomAuth.authenticate`, producing `session.shop === "any-arbitrary-store.myshopify.com"` paired with the app's real `adminApiAccessToken` [4](#0-3) .
4. Any downstream app logic that trusts `session.shop` for tenant-scoping (logging, webhooks correlation, per-shop caches) is now operating under an attacker-supplied shop identity.

**Note:** I could not fully verify how `react-router` package variant handles this (it appeared structurally identical based on the earlier search results), nor could I confirm concrete production app code that trusts `session.shop` in a security-sensitive way in this repo itself — the impact depends on downstream consumer app logic outside this library. This limits certainty of the ultimate severity, though the root-cause finding (missing sanitization/validation of an untrusted `shop` parameter that seeds a `Session`) is concretely verified in the code cited above.

async function getSessionTokenContext(
  params: BasicParams,
  request: Request,
): Promise<SessionTokenContext> {
  const {api, config, logger} = params;

  const headerSessionToken = getSessionTokenHeader(request);
  const searchParamSessionToken = getSessionTokenFromUrlParam(request);
  const sessionToken = (headerSessionToken || searchParamSessionToken)!;

  logger.debug('Attempting to authenticate session token', {
    shop: getShopFromRequest(request),
    sessionToken: JSON.stringify({
      header: headerSessionToken,
      search: searchParamSessionToken,
    }),
  });

  if (config.isEmbeddedApp) {
    const payload = await validateSessionToken(params, request, sessionToken);
    const dest = new URL(payload.dest);
    const shop = dest.hostname;

    logger.debug('Session token is valid - authenticated', {shop, payload});
    const sessionId = config.useOnlineTokens
      ? api.session.getJwtSessionId(shop, payload.sub)
      : api.session.getOfflineId(shop);

    return {shop, payload, sessionId, sessionToken};
  }

  const url = new URL(request.url);
  const shop = url.searchParams.get('shop')!;

  const sessionId = await api.session.getCurrentId({
    isOnline: config.useOnlineTokens,
    rawRequest: request,
  });

  return {shop, sessionId, payload: undefined, sessionToken};
