### No vulnerability found for this question.

**Reasoning:** `make_vecs` is only invoked from `Batches::new`, which is called once at scheduler construction time via `SchedulingCommon::new` [1](#0-0) . Its parameters, `num_threads` (bounded by `MAX_THREADS`, asserted at construction [2](#0-1) ) and `target_num_transactions_per_batch`, come from validator configuration set at banking-stage startup, not from any per-transaction instruction/account count or attacker-controlled packet content [3](#0-2) . There is no code path from a submitted transaction's instruction count, account count, or size into `make_vecs`'s arguments — the function only pre-allocates `Vec::with_capacity` for a fixed number of worker threads once at process start, and subsequent per-transaction work (`add_transaction_to_batch`) merely pushes into existing vectors without re-invoking `make_vecs` [4](#0-3) . Since an unprivileged attacker cannot influence `num_threads` or `target_num_transactions_per_batch` through any transaction, the described amplification path does not exist in this code.

impl<Tx> Batches<Tx> {
    pub fn new(num_threads: usize, target_num_transactions_per_batch: usize) -> Self {
        fn make_vecs<T>(
            num_threads: usize,
            target_num_transactions_per_batch: usize,
        ) -> Vec<Vec<T>> {
            (0..num_threads)
                .map(|_| Vec::with_capacity(target_num_transactions_per_batch))
                .collect()
        }

        Self {
            ids: make_vecs(num_threads, target_num_transactions_per_batch),
            transactions: make_vecs(num_threads, target_num_transactions_per_batch),
            max_ages: make_vecs(num_threads, target_num_transactions_per_batch),

            total_cus: vec![0; num_threads],
            entry_bytes: vec![ENTRY_OVERHEAD_BYTES; num_threads],

        }
