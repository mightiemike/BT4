### Title
Shadow-block version bit lets any attacker-forged block bypass signer signature verification - (File: stackslib/src/chainstate/nakamoto/mod.rs)

### Finding Description
`NakamotoBlockHeader::verify_signer_signatures` is the single, generic entry point used to validate signer approval of a Nakamoto block, and it is invoked from the ordinary network block-acceptance/tenure-download paths (`net/relay.rs`, `net/unsolicited.rs`, `net/download/nakamoto/tenure_downloader.rs`, `tenure_downloader_unconfirmed.rs`), not from a shadow-block-specific code path. [1](#0-0) 

Inside this function, before any signature is checked, the header is inspected with `self.is_shadow_block()`, which is a pure syntactic check of a single bit in the untrusted, attacker-controlled `version` byte of the header: [2](#0-1) 

If that bit is set, the function immediately returns `get_shadow_signer_weight`, which sums the weight of *every* signer in the reward set and returns it as the "signing weight," without inspecting `self.signer_signature` at all: [3](#0-2) 

The broken equality is: **on any node whose block-acceptance pipeline calls `verify_signer_signatures` generically (i.e., the standard relay/tenure-download path) == treating an attacker-forged, unsigned block as fully-signed by the entire reward set**, purely because the attacker set one bit in the header version byte. There is no cryptographic or allow-list check tying `is_shadow_block()` to the actual SIP-sanctioned, out-of-band-agreed shadow block set — `is_shadow_block_version` is defined only as `version & 0x80 != 0`. Real shadow blocks are documented as being "inserted directly into the staging blocks DB as part of a schema update" and "neither mined nor relayed," but that is an operational/documentation-level assumption, not a code-enforced gate at the point where `verify_signer_signatures` is called from the network-facing paths. An attacker who wins a single sortition slot (miner, not signer, privilege) can freely choose any header `version` byte for the block it proposes, set the high bit, submit an empty (or garbage) `signer_signature` vector, and have `verify_signer_signatures` unconditionally report "full weight signed" for that block wherever this function is invoked without a preceding, explicit "this exact block/tenure is on the hardcoded shadow-block allow-list" check.

I was unable to conclusively locate, within the code I could inspect, an explicit prior gate (e.g., a check against a hardcoded set of shadow block hashes/consensus hashes, or a check that a block only reaches `verify_signer_signatures`'s shadow branch if it was inserted via the dedicated `insert_shadow_block` internal function rather than received over the wire) that would prevent this. This is a material gap in my verification — I ran out of tool budget before confirming whether `NakamotoChainState::append_block` (the function that actually persists/accepts a block, called by relay.rs/unsolicited.rs) restricts the shadow-block signature bypass to blocks that entered chainstate exclusively through the internal admin/schema-upgrade insertion path, as opposed to blocks parsed from the wire.

### Impact Explanation
If the generic network path indeed reaches this bypass for any wire-supplied block with the shadow bit set, this is Critical: an attacker-controlled block with zero real signer approval would be accepted network-wide as fully signed by 100% of signer weight, directly violating the Nakamoto consensus invariant that blocks require ≥70% signer weight. This could let an attacker-controlled miner (who only needs to win one sortition) inject arbitrary transactions/state transitions without any signer consent, or cause divergent behavior between nodes that do vs. do not treat the shadow bit as trustworthy, producing a chain split.

### Likelihood Explanation
Preconditions: the attacker needs to win exactly one sortition slot (achievable with a minority of BTC, as stated in the threat model) so that they can propose a Nakamoto block for their own tenure, and craft the header with the shadow version bit set and an empty/arbitrary `signer_signature` field. No signer key, majority stake, or node-operator privilege is required. This is repeatable every time the attacker wins a sortition. However, whether this is actually exploitable depends entirely on whether the standard network block-acceptance code path (`append_block`, called from `relay.rs`/`unsolicited.rs`) truly has no additional gate rejecting non-whitelisted shadow-bit blocks before reaching `verify_signer_signatures` — a point I could not fully confirm with the available evidence.

### Recommendation
`verify_signer_signatures`'s shadow-block branch should not be reachable for blocks arriving through the ordinary block-relay/tenure-download path. Concretely:
- Gate the shadow bypass on an explicit, node-hardcoded allow-list of shadow block hashes/consensus hashes shipped with a given software release (matching the SIP process), rather than trusting a self-reported version bit in the header.
- Ensure `NakamotoChainState::append_block` (and any other function that persists blocks received from peers) explicitly rejects any block with `is_shadow_block() == true` unless it is being inserted through the dedicated internal `insert_shadow_block` code path, never through the generic peer-received block path.

### Proof of Concept
1. In a Rust integration test, construct a valid `NakamotoBlockHeader` for a tenure won by a test miner via a real sortition (minority BTC stake).
2. Set `header.version |= 0x80` (shadow bit) and set `signer_signature` to an empty vector (or a garbage signature vector that would fail the normal path).
3. Submit the block via the ordinary block-relay ingestion function used by `net/relay.rs`/`net/unsolicited.rs` (the same path a peer-broadcast block would take).
4. Assert `NakamotoBlockHeader::verify_signer_signatures(&reward_set, epoch_id)` returns `Ok(full_reward_set_weight)` for this block even though `signer_signature` is empty — i.e., assert the SIGNING equality (`distinct valid signer weight >= threshold`) is *falsely* satisfied because `is_shadow_block()` short-circuited real verification.
5. Run this on two node configurations — one that has (hypothetically) a shadow-block allow-list check ahead of `append_block`, one that does not — and show the accept/reject verdict and canonical tip diverge, per the audit's proof idea.

*Note: step 3's feasibility (whether the generic relay path actually permits shadow-bit blocks through to `append_block`/`verify_signer_signatures` without an additional gate) is the exact fact I could not fully confirm given tool-call limits; a Devin session with full repo/test access should verify `NakamotoChainState::append_block` and the `insert_shadow_block` call sites to close this gap before treating this finding as confirmed.*

    /// Get the signing weight of a shadow block
    pub fn get_shadow_signer_weight(&self, reward_set: &RewardSet) -> Result<u32, Error> {
        let Some(signers) = reward_set.signers() else {
            return Err(ChainstateError::InvalidStacksBlock(
                "No signers in the reward set".to_string(),
            ));
        };
        let shadow_weight = signers
            .iter()
            .fold(0u32, |acc, signer| acc.saturating_add(signer.weight));

        Ok(shadow_weight)
    }
