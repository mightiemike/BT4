### Title
`shopify.auth.tokenExchange` does not verify that the decoded session-token `dest` matches the caller-supplied `shop` parameter - (File: packages/apps/shopify-api/lib/auth/oauth/token-exchange.ts)

### Summary

### Finding Description
`tokenExchange()` accepts `shop` and `sessionToken` as two independent parameters. It calls `decodeSessionToken(config)(sessionToken)` purely to validate the token's signature/expiry/audience, but it discards the returned payload and never checks that `payload.dest` (the shop the token was actually issued for) matches the `shop` argument that is used to build the outbound request: [1](#0-0) 

The `shop` value is then used verbatim (after `sanitizeShop`) to build the target host for the token-exchange POST (`https://${cleanShop}/admin/oauth/access_token`), and it is also fed into `createSession()` to become the resulting `Session.shop`: [2](#0-1) 

Critically, the library's own published documentation instructs integrators to derive `shop` from the request's query string (`shopify.utils.sanitizeShop(req.query.shop, true)`), completely independent from the `sessionToken`'s embedded `dest` claim: [3](#0-2) 

This is structurally identical to the SKALE bug class: a value that should be derived from/verified against a trusted, cryptographically-bound source (the session token's `dest`) is instead accepted as a second, independently-controlled input, and the library performs no internal consistency check that ties the two together before performing a sensitive, resource-scoped action (minting an access token / persisting a `Session`).

By contrast, the framework-level integrations (`shopify-app-remix`, `shopify-app-react-router`, `shopify-app-express`) are safe because *they* derive `shop` exclusively from the validated token's `dest` field rather than from any externally supplied parameter: [4](#0-3) [5](#0-4) 

The vulnerable surface is therefore confined to the low-level `@shopify/shopify-api` `auth.tokenExchange` primitive itself, which any app author calling it directly (as shown in its own doc example) can misuse.

### Impact Explanation
If an integrator follows the officially documented pattern and sources `shop` from a query parameter rather than from the token payload, an unprivileged user in possession of *their own* valid session token could invoke the endpoint with an attacker-chosen `shop` value. Because `token-exchange.ts` performs no `payload.dest === shop` check, the library will happily attempt (and, depending on how the resulting `Session` is later consulted/stored by the app, potentially succeed in persisting) a `Session` object keyed to a shop different from the one the token was actually issued for. Any app logic downstream that trusts `session.shop` (e.g., session storage lookups keyed by shop, webhook/session-storage injection, or per-tenant authorization decisions) could be confused into cross-tenant session mix-up. This maps to the accepted class "session-storage injection / cross-tenant access" from a value that should have been derived from a verified, tamper-proof source (the JWT) but instead was accepted as an unrelated parameter — mirroring how `ERC20OnChain.mint` trusted a role-holder to specify an amount that should have been tied to the actual bridged transfer.

### Likelihood Explanation
Likelihood is Medium at most, and highly contingent on integrator behavior:
- It requires a developer building directly against the low-level `@shopify/shopify-api` package (not the higher-level Remix/React Router/Express adapters, which are unaffected) and following the library's own documented example of sourcing `shop` from the request query string.
- Shopify's server-side `/admin/oauth/access_token` token-exchange endpoint may itself reject a `subject_token` whose issuer/`dest` doesn't correspond to the target shop's domain, which would block real-world exploitation — this server-side enforcement is outside this repository and could not be verified from the codebase alone.
- No production integration package in this repo (`shopify-app-remix`, `shopify-app-react-router`, `shopify-app-express`) actually exhibits the unsafe pattern; they all bind `shop` to `payload.dest`.

### Recommendation
In `tokenExchange()`, after decoding the session token, assert that `sanitizeShop(config)(shop, true)` equals the shop derived from `payload.dest`/`payload.iss`, and throw an `InvalidJwtError`/`InvalidOAuthError` on mismatch, rather than trusting the caller-supplied `shop` independently. Update `docs/reference/auth/tokenExchange.md` to stop recommending that `shop` be taken from `req.query.shop` and instead show deriving it from the decoded session token, consistent with how the Remix/React Router/Express adapters already behave.

### Proof of Concept
Not independently verified end-to-end against Shopify's live `/admin/oauth/access_token` endpoint (that server-side behavior is outside this repo and could not be confirmed). Conceptually:
1. Attacker is a legitimate, authenticated user of the app on `shop-a.myshopify.com` and holds a valid session token for that shop.
2. App exposes a custom `/auth` route implemented per the library's documented example, using `shop = sanitizeShop(req.query.shop, true)` independent of the token.
3. Attacker calls `/auth?shop=shop-b.myshopify.com` while attaching their own valid `shop-a` session token.
4. `tokenExchange()` decodes/validates the token (succeeds, since it belongs to a real, currently-installed shop) but never checks `payload.dest` against `shop-b.myshopify.com`, and issues the exchange request scoped to `shop-b`, with the resulting `Session.shop` set to `shop-b`.
5. Whether this ultimately yields a usable cross-tenant `Session` depends on Shopify's own server-side validation of the `subject_token` vs. target domain, which is unverified here.

```typescript
export function tokenExchange(config: ConfigInterface): TokenExchange {
  return async ({
    shop,
    sessionToken,
    requestedTokenType,
    expiring,
  }: TokenExchangeParams) => {
    await decodeSessionToken(config)(sessionToken);

    const body = {
      client_id: config.apiKey,
      client_secret: config.apiSecretKey,
      grant_type: TokenExchangeGrantType,
      subject_token: sessionToken,
      subject_token_type: IdTokenType,
      requested_token_type: requestedTokenType,
      expiring: expiring ? '1' : '0',
    };

    const cleanShop = sanitizeShop(config)(shop, true)!;

    const postResponse = await fetchRequestFactory(config)(
      `https://${cleanShop}/admin/oauth/access_token`,
      {
        method: 'POST',
        body: JSON.stringify(body),
        headers: {
          'Content-Type': DataType.JSON,
          Accept: DataType.JSON,
        },
      },
    );

    if (!postResponse.ok) {
      throwFailedRequest(await postResponse.json(), false, postResponse);
    }

    return {
      session: createSession({
        accessTokenResponse: await postResponse.json<AccessTokenResponse>(),
        shop: cleanShop,
        // We need to keep this as an empty string as our template DB schemas have this required
        state: '',
        config,
      }),
    };
```
