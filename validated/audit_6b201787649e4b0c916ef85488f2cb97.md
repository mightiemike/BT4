### Title
Global signer state-machine agreement uses a floor-rounded threshold while block-signature approval uses a ceiling-rounded threshold, letting sub-quorum weight be treated as "agreement" - (File: `libsigner/src/v0/signer_state.rs`)

### Summary
The external report's root cause is a magic-number division that silently produces the wrong scaled value because two code paths encode the "same" percentage differently. The direct analog in this repo is the divergence between `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` in `libsigner/src/v0/signer_state.rs` and `NakamotoBlockHeader::compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs`, both of which implement the same `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` (70%) supermajority concept but round it differently — one floors, the other explicitly ceils.

### Finding Description
`NakamotoBlockHeader::compute_voting_weight_threshold` computes the minimum weight needed to approve a block by explicitly rounding **up**: [1](#0-0) 

```
let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
u32::try_from((total_weight * threshold) / 10 + ceil)
```

By contrast, `GlobalStateEvaluator::reached_agreement` (and its complement `reached_disagreement`) — used to determine the signer network's consensus view of the current miner, burn-block view, protocol version, and transaction replay set — use the **same** `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD` constant but perform plain integer division with **no ceiling**: [2](#0-1) 

```
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD) / 10
}
```

For any `total_weight` where `total_weight * 7` is not a multiple of 10 (i.e. almost every possible signer-weight total), `reached_agreement`'s floor threshold is exactly **one weight unit lower** than `compute_voting_weight_threshold`'s ceil threshold — this is demonstrated by the project's own test vectors, e.g. `total_weight = 511` yields a real approval threshold of `358`, while the floor formula used in `reached_agreement` would yield `357`: [3](#0-2) 

`GlobalStateEvaluator::determine_global_state`, `determine_latest_supported_signer_protocol_version`, and `determine_global_burn_view` all rely on `reached_agreement` to decide when the signer set has reached global consensus on the canonical miner/burn view/protocol/tx-replay-set: [4](#0-3) [5](#0-4) [6](#0-5) 

Because the threshold used to establish "global agreement" among signers is systematically weaker (by exactly the rounding remainder) than the threshold actually required to produce a block with a valid signer signature bundle (`verify_signer_signatures` → `compute_voting_weight_threshold`), a coalition of signer weight sitting exactly between the floor and the ceil value is treated as having reached quorum by the state-machine evaluator, while that same weight would be rejected as insufficient by block-signature verification: [7](#0-6) 

### Impact Explanation
This breaks the intended equality between "the signer set agrees a quorum threshold was met" and "a block can actually collect a valid supermajority signature." A minority coalition (one weight unit below the true supermajority) can cause the local `GlobalStateEvaluator` to conclude that a specific miner/burn view/protocol version/tx-replay-set has "global agreement," even though it does not meet the real on-chain supermajority bar enforced by `compute_voting_weight_threshold`. Since this evaluator result feeds directly into which miner/tenure a signer treats as canonical, it can cause temporary tip/miner disagreement among honest signers relative to the actual chain-level quorum requirement — matching the "temporary tip disagreement" High-impact category. It does not by itself allow an invalid block to be accepted on-chain, since block signature verification still uses the correct ceiling formula, so the impact is bounded to signer coordination/liveness rather than a state-root or reward-theft issue.

### Likelihood Explanation
The discrepancy is not an edge case — it occurs for essentially all values of `total_weight` (any total_weight where `total_weight * 7 mod 10 != 0`), so it will be triggered under normal, non-adversarial network operation whenever the aggregate signer weight sitting on one side of a decision equals exactly the floor threshold. No majority or admin access is required; a coalition need only reach a weight equal to the floor(70%) value, one unit short of the actual ceil(70%) supermajority, to trip `reached_agreement`/`reached_disagreement` incorrectly relative to the block-approval definition.

### Recommendation
Make `GlobalStateEvaluator::reached_agreement` and `reached_disagreement` use the same rounding rule as `NakamotoBlockHeader::compute_voting_weight_threshold` (i.e., call or replicate the ceiling-based threshold calculation) so that "signer global agreement" and "block signature approval" always agree on the exact weight boundary, eliminating the off-by-one discrepancy between the two consensus-threshold computations.

### Proof of Concept
1. Configure a reward cycle where `total_weight = 511` (a value already used in the codebase's own regression test for `compute_voting_weight_threshold`).
2. The correct/consensus-enforced block approval threshold is `358` per `compute_voting_weight_threshold` (verified by existing test at `stackslib/src/chainstate/nakamoto/tests/mod.rs:4118-4122`).
3. Have a subset of signers accumulate exactly `357` weight units of agreement on a given `current_miner`/burn view/protocol version.
4. `GlobalStateEvaluator::reached_agreement(357)` returns `true` (`357 >= floor(511*7/10) = 357`), so `determine_global_state`/`determine_global_burn_view`/`determine_latest_supported_signer_protocol_version` will report this as the agreed global state.
5. However, a block requiring signatures from that same weight (357) would be rejected by `NakamotoBlockHeader::verify_signer_signatures`, since `357 < 358` (the real ceil threshold) — demonstrating the two "same-concept" threshold checks diverge on identical input.

    /// Compute the threshold for the minimum number of signers (by weight) required
    /// to approve a Nakamoto block.
    pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }

    /// Determine what the maximum signer protocol version that a majority of signers can support
    pub fn determine_latest_supported_signer_protocol_version(&self) -> Option<u64> {
        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
            *entry += weight;
        }
        // find the highest version number supported by a threshold number of signers
        let mut protocol_versions: Vec<_> = protocol_versions.into_iter().collect();
        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }
