### Title
Single invalid/stale L1 message aborts entire block validation, discarding all other valid transactions in the proposal - (File: crates/apollo_batcher/src/transaction_provider.rs)

### Summary
The external report describes a root-cause pattern: a per-item external-availability/validation check that is missing or incomplete causes one failing item inside a loop over many items to abort the *entire* batch operation, instead of being isolated and skipped. The Apollo sequencer analog is in `ValidateTransactionProvider::get_txs`, where a single `InternalConsensusTransaction::L1Handler` transaction in a fetched buffer that fails L1 validation (e.g. because it was already consumed/included on L1 or L2, or cannot be found — states that can legitimately change between proposal time and validation time) causes the whole call to return `Err(TransactionProviderError::L1HandlerTransactionValidationFailed)`, which propagates to `FailOnErrorCause::L1HandlerTransactionValidationFailed` and aborts the *entire* block-building/validation task for that height, discarding every other transaction already staged in the proposal.

### Finding Description
`ValidateTransactionProvider::get_txs` iterates a batch of received transactions and, for each `L1Handler` transaction, calls the L1 events provider's `validate()`: [1](#0-0) 

If the validation status for a *single* L1 handler transaction in the batch comes back `Invalid` (statuses include `AlreadyIncludedInProposedBlock`, `AlreadyIncludedOnL2`, `ConsumedOnL1`, `NotFound`), the function immediately returns an `Err`, even though the remaining transactions in the buffer (which may include perfectly valid `RpcTransaction`s and other L1 handler transactions) are never processed or returned: [2](#0-1) 

This error is consumed in `add_txs_to_executor`, which special-cases only this specific error path and converts it into a hard failure that aborts block validation for the entire height, rather than skipping/dropping just the offending transaction: [3](#0-2) 

The L1 handler transaction's validity state (`AlreadyIncludedOnL2`, `ConsumedOnL1`, `NotFound`) is a property of *external* L1/L2 chain state that can change between the time a proposer builds a proposal (querying the L1 provider) and the time a validator revalidates the same transaction (querying its own, possibly slightly different, L1 provider snapshot due to L1 reorgs, timing races, or a slower/faster L1 sync). Because there is no per-transaction isolation or retry — only a coarse "abort the whole validation" fallback — a single such transient/legitimate mismatch discards the entire batch of transactions collected for that proposal.

### Impact Explanation
When a single L1 handler transaction in a validator's received proposal is judged invalid due to this external, time-dependent L1 state check, the validator aborts the whole block-building task (`abort_block`), rejecting the *entire* proposal instead of merely excluding that transaction. This denies the validator's vote on an otherwise valid block containing many legitimate transactions, forcing a round change / re-proposal. If this condition is systematically reproducible (e.g., an L1 message nearing its consumption/cancellation window, or provider desync near height boundaries), it degrades consensus throughput and liveness of transaction confirmation for the affected height, since correct transactions bundled with the problematic L1 message cannot be confirmed in that round.

### Likelihood Explanation
The trigger requires only an L1-to-L2 message (reachable by any L1 message sender) whose consumption/validity state transitions in a narrow window around block boundaries (e.g. due to a legitimate L1 reorg, near-simultaneous consumption, or provider staleness) — no malicious proposer, peer, or privileged actor is needed. The condition falls squarely within the reachable "external dependency check with no isolation" root cause of the referenced report, though the practical frequency depends on how often L1 state changes occur in the narrow window between proposal and validation for the same height.

### Recommendation
In `ValidateTransactionProvider::get_txs`, do not fail the entire fetch when a single L1 handler transaction is found invalid. Instead, drop/skip the invalid L1 handler transaction (and report it via metrics/logging, similar to how `ProposeTransactionProvider::get_l1_handler_txs` already tolerates provider errors with `.unwrap_or_default()`), and continue returning the remaining valid transactions in the buffer. Reserve the hard abort path only for genuinely unrecoverable provider/communication failures.

### Proof of Concept
1. A proposer builds a proposal for height `H` including transactions `[L1Handler(A), Rpc(B), Rpc(C)]`, where `A` is valid to the proposer's L1 provider snapshot at proposal time.
2. Before validators call `ValidateTransactionProvider::get_txs` on this batch, the state backing `A`'s validity changes on the validator's L1 provider (e.g., `A` becomes `ConsumedOnL1` or `AlreadyIncludedOnL2` due to timing/reorg), causing `l1_events_provider_client.validate` to return `Invalid`. [4](#0-3) 
3. `get_txs` immediately returns `Err(L1HandlerTransactionValidationFailed)` without ever returning `Rpc(B)` and `Rpc(C)`.
4. `add_txs_to_executor` maps this to `FailOnErrorCause::L1HandlerTransactionValidationFailed`, aborting the whole block build/validation for height `H`. [3](#0-2) 
5. Result: transactions `B` and `C`, despite being fully valid, are not confirmed in this round; the validator rejects the entire proposal instead of only the problematic `A`.
