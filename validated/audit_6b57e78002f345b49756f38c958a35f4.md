### Title
Truncated decimal-normalization in TRX-weight-to-resource-limit conversion causes systematic under/over-allocation of bandwidth/energy - (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java, chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java, chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java)

### Summary
The MONT report's root cause is a "quote-then-divide" pattern where a value expressed in one decimal precision (MONT, 18 decimals) is truncated by an early integer division before being combined with a ratio, producing systematic, price-dependent error. The same structural pattern — normalizing a fine-grained SUN balance (6 decimals of TRX) to a coarse "weight" unit via an early truncating division, and only then multiplying by a limit/weight ratio — exists in java-tron's resource accounting code, specifically `BandwidthProcessor.calculateGlobalNetLimit` [1](#0-0) .

### Finding Description
`calculateGlobalNetLimit` computes `netWeight = frozeBalance / TRX_PRECISION` — an integer division that discards the sub-1,000,000-sun (sub-1-TRX) remainder of a user's frozen balance — and only afterward multiplies by the global ratio `totalNetLimit / totalNetWeight` using double arithmetic: [2](#0-1) 
The same early-truncation-then-multiply pattern appears in `calculateGlobalNetLimitV2`, which instead truncates via casting to `double` before multiplying by the ratio when the "hardened" code path is not active: [3](#0-2) 
This mirrors exactly the MONT bug class: `price = quoter.quoteExactInputSingle(..., 1e18, ...)` truncates the fine-grained price to a coarse unit before it's used in `reward = ... / price`, and the resulting error is not proportional to the truncated remainder but compounds through the subsequent multiplication, causing systematic deviation that grows as the truncated quantity (MONT price, or here, frozen-TRX weight) shrinks relative to the precision unit.

Notably, the codebase itself has already flagged this exact defect class: a governance-gated "hardened" replacement path exists (`hardenCalculation()`), which performs the whole computation in `BigInteger` without any intermediate truncation, explicitly to avoid this precision loss: [4](#0-3) 
This confirms the maintainers recognize the un-hardened formula as buggy; until the corresponding proposal is activated network-wide, the legacy truncating formula remains the live, default code path exercised on every `FreezeBalance`/`FreezeBalanceV2` and resource-consuming broadcast transaction.

### Impact Explanation
Because `netWeight`/`frozeBalance` truncation happens before the ratio multiplication, an account's computed bandwidth/energy limit is not proportional to its actual frozen TRX; for small frozen balances or specific balance/ratio combinations the account can receive a bandwidth/energy limit that differs from the mathematically correct value (either less or more, depending on rounding direction of the subsequent double multiplication) — the same class of misallocation described in the MONT report, but affecting on-chain resource accounting rather than a token reward payout. Since bandwidth/energy limits gate transaction admission and fee-free execution, systematic misallocation is a resource/reward accounting integrity issue.

### Likelihood Explanation
This code path executes on every account that has frozen TRX for bandwidth/energy and is exercised through ordinary, unprivileged `FreezeBalance(V2)` and transaction-broadcast flows — no special privilege is required to trigger it, and the flawed arithmetic runs by default whenever `allowHardenResourceCalculation` has not been activated via proposal.

### Recommendation
Activate the existing `ALLOW_HARDEN_RESOURCE_CALCULATION` proposal (or equivalently make the `BigInteger`-based hardened formula in `calculateGlobalLimitV1`/`calculateGlobalLimitV2` the unconditional default) so that `frozeBalance`, `totalNetLimit`/`totalEnergyLimit`, and `totalNetWeight`/`totalEnergyWeight` are combined via a single non-truncating computation (multiply-then-divide in full precision) rather than truncating the balance to whole-TRX units before multiplying by the ratio.

### Proof of Concept
Not independently verified with a live network trace; based on the code paths cited above:
1. Freeze a TRX balance that is not an exact multiple of `TRX_PRECISION` (1,000,000 sun), e.g. `frozeBalance = 1_500_000` sun with `totalNetLimit = 43_200_000_000`, `totalNetWeight = 2_000_000_000`.
2. Non-hardened path: `netWeight = 1_500_000 / 1_000_000 = 1` (truncated), then `limit = 1 * (43_200_000_000.0/2_000_000_000.0) = 21`.
3. Full-precision (hardened) computation: `BigInteger.valueOf(1_500_000).multiply(43_200_000_000) / (1_000_000 * 2_000_000_000) = 32` — a materially different result, demonstrating the same truncate-then-multiply distortion described in the MONT report, confirmed by the project's own regression tests contrasting the legacy and hardened formulas: [5](#0-4)

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForBandwidth();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalNetLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }

  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
