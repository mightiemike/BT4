### Title
Unhandled `receiver_shard_id` error panics chain-wide during delayed-receipt processing — ([File: runtime/runtime/src/congestion_control.rs])

### Summary
`DelayedReceiptQueueWrapper::receipt_filter_fn` in `runtime/runtime/src/congestion_control.rs` calls `.unwrap()` on `Receipt::receiver_shard_id(&shard_layout)`, a `Result`-returning call that can legitimately return `Err` for `GlobalContractDistribution` receipts whose `target_shard` cannot be mapped to any shard in the current layout or its recorded split history. Unlike the Incus bug (a wrong length-guard causing an out-of-bounds panic on a single node), this is a missing error-handling guard (`.unwrap()` instead of propagating the error) on a resharding-related lookup, reachable purely through normal transaction/receipt flow — every validator applying the shard's chunk hits the same panic, turning a single flawed check into a **consensus-wide, transaction-triggered halt** rather than a single-daemon crash.

### Finding Description
`receiver_shard_id` computes the destination shard for a receipt: [1](#0-0) 

For `GlobalContractDistribution` receipts it falls back to `ShardLayout::resolve_to_current_shard(target_shard)` when the literal `target_shard` id is no longer part of the current layout (because of an intervening reshard), and returns `Err(EpochError::ShardingError(...))` if that resolution fails: [2](#0-1) 

`resolve_to_current_shard` recursively walks `shards_split_map` (the recorded split history) and returns `None` if the shard id is absent from both the current layout and that split history: [3](#0-2) 

The consumer of this fallible API in the delayed-receipt drain path does not propagate the error — it unwraps it: [4](#0-3) 

`receipt_filter_fn` is invoked by `pop()` on every delayed receipt popped from the persistent delayed-receipt queue during ordinary chunk application: [5](#0-4) 

This mirrors the Incus bug-class: a validation/bounds-mapping check (`len(slice) >= i-1` there; `resolve_to_current_shard` returning `None`/`Err` here) that is not correctly guarded before it's relied upon, and the flaw sits directly on a path fed by attacker-influenced/normal input (a submitted `DeployGlobalContract` transaction whose resulting receipt can be delayed across shard-layout changes).

### Impact Explanation
Because `receipt_filter_fn` runs identically on every honest validator applying the same chunk (it's part of the deterministic state-transition/apply loop, not a peer-specific or network path), a triggered panic here is not a single-node crash — it is a **transaction-triggered halt**: every node attempting to apply the shard's chunk (both chunk producers/validators generating the state witness and validators re-executing it for stateless validation) panics identically, since the `receiver_shard_id().unwrap()` is deterministic given the receipt and shard layout state. This satisfies the "transaction-triggered halt" / "invalid state transition acceptance via crash-instead-of-apply" impact bar, and is more severe than the original single-daemon-crash bug because there is no way for the network to route around it (the panic reproduces on every honest replica processing that shard).

The existing regression test in the repo, `test_stale_global_contract_distribution_after_double_resharding`, specifically exercises a `GlobalContractDistribution` receipt surviving two sequential dynamic resharding events and asserts the chain does **not** stall — i.e. this exact scenario is a known, previously-identified risk area for this code: [6](#0-5) 

### Likelihood Explanation
Triggering requires: (1) submitting a `DeployGlobalContract` transaction (unprivileged, any signer can do this) whose resulting `GlobalContractDistribution` receipt gets delayed (e.g. due to compute/gas-limit or congestion), and (2) the shard undergoing enough resharding activity that `resolve_to_current_shard` cannot map the receipt's `target_shard` to a shard in the then-current layout's recorded split history. `resolve_to_current_shard`'s recursive walk of `shards_split_map` is intended to cover exactly this, and the currently-present regression test exercises a two-generation-deep case; whether there remain uncovered edge cases (e.g. layout-version transitions where `shards_split_map` history is not fully populated, GC of older layout state, or additional resharding generations beyond what the test covers) could not be conclusively confirmed from static review alone — this would require dynamic/fuzz testing of `resolve_to_current_shard`/`build_shard_split_map` across mixed static/dynamic resharding sequences to fully validate. The root-cause pattern (a fallible shard-resolution call `.unwrap()`ed inside a per-chunk hot loop) is confirmed and exploitable in principle whenever the underlying `Option`/`Result` can legitimately be `None`/`Err`.

### Recommendation
Replace the `.unwrap()` in `receipt_filter_fn` with proper error propagation (`?` returning a `RuntimeError`/`StorageInconsistentState`, consistent with how other delayed-receipt inconsistencies are handled elsewhere in `runtime/runtime/src/lib.rs`, e.g. `StorageError::StorageInconsistentState` for corrupted delayed receipts), and add exhaustive property/fuzz testing of `ShardLayoutV3::resolve_to_current_shard` and `build_shard_split_map` across mixed V1/V2/V3 layout histories, multi-generation resharding, and GC boundaries to ensure `shards_split_map` always contains full ancestry for any receipt that can outlive a resharding event.

### Proof of Concept
Not independently reproduced in this review (no execution environment available). The reachable trigger path, based on static analysis of the cited code, is:
1. Submit a `DeployGlobalContract` transaction from an account near a shard boundary, causing a `GlobalContractDistribution` receipt to be created with `target_shard` set to the then-current shard.
2. Cause the receipt to be delayed (e.g. via congestion / compute-limit exhaustion) and let the shard undergo resharding generations such that `shards_split_map`'s recorded history does not include an entry mapping the receipt's stale `target_shard` forward.
3. When the delayed queue drains and `DelayedReceiptQueueWrapper::pop` → `receipt_filter_fn` is called on this receipt, `receiver_shard_id(...).unwrap()` panics on every validator applying the chunk, halting chunk/block production for that shard.

    pub fn receiver_shard_id(&self, shard_layout: &ShardLayout) -> Result<ShardId, EpochError> {
        let shard_id = match self.receipt() {
            ReceiptEnum::Action(_)
            | ReceiptEnum::ActionV2(_)
            | ReceiptEnum::Data(_)
            | ReceiptEnum::PromiseYield(_)
            | ReceiptEnum::PromiseYieldV2(_)
            | ReceiptEnum::PromiseResume(_) => {
                shard_layout.account_id_to_shard_id(self.receiver_id())
            }
            ReceiptEnum::GlobalContractDistribution(receipt) => {
                let target_shard = receipt.target_shard();
                if shard_layout.shard_ids().contains(&target_shard) {
                    target_shard
                } else {
                    // The target shard may be from an arbitrarily old layout (the receipt could
                    // have been delayed across multiple resharding events). resolve_to_current_shard
                    // will find a shard descendant in the current layout.
                    let Some(current_shard) = shard_layout.resolve_to_current_shard(target_shard)
                    else {
                        return Err(EpochError::ShardingError(format!(
                            "Shard {target_shard} does not exist in the shard layout or its split history",
                        )));
                    };
                    current_shard
                }
            }
        };
        Ok(shard_id)
    }

    /// Resolve any historical shard ID to a current shard by walking the full
    /// split history in `shards_split_map`. Returns the shard itself if it is
    /// current, or follows the first child at each generation until a current
    /// shard is reached. Returns `None` only if the shard ID is absent from
    /// both the current layout and the split history.
    pub fn resolve_to_current_shard(&self, shard_id: ShardId) -> Option<ShardId> {
        if self.shard_ids.contains(&shard_id) {
            return Some(shard_id);
        }
        let children = self.shards_split_map.get(&shard_id)?;
        self.resolve_to_current_shard(children[0])
    }

    // Here, we filter all the receipts that don't belong to the current shard_id.
    //
    // The function follows the guidelines of standard iterator filter function
    // We return true if we should retain the receipt and false if we should filter it.
    fn receipt_filter_fn(&self, receipt: &ReceiptOrStateStoredReceipt) -> bool {

        let receipt_shard_id = receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap();
        receipt_shard_id == self.shard_id
    }
