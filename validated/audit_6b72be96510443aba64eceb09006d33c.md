### Title
Unbounded `PendingInbounds.Walk` scan in ballot-terminal cleanup enables gas-DoS of inbound finalization - ([File: x/uexecutor/keeper/ballot_hooks.go])

### Summary
`BallotHooks.afterInboundBallotTerminal` locates the `PendingInboundEntry` owning a just-finalized ballot by doing a full, unbounded scan of the `PendingInbounds` collection with `k.PendingInbounds.Walk(ctx, nil, ...)`, comparing every stored variant's `BallotId` against the target. This callback fires synchronously, inside the same metered transaction, on every single `MsgVoteInbound` call that causes a ballot to reach a terminal state (`PASSED`/`REJECTED`/`EXPIRED`). Because `PendingInbounds` entries are created permissionlessly by ordinary source-chain deposits (any external-chain transaction that a validator observes and votes on creates or extends an entry via `RecordInboundVote`), an unprivileged attacker can inflate the size of `PendingInbounds` by generating many cheap/dust deposits on any enabled source chain, each producing a distinct `utx_key`. As this collection grows, the gas cost of the mandatory `Walk` scan on every subsequent inbound-ballot finalization grows linearly, eventually causing `MsgVoteInbound` transactions to exceed their gas limit and fail — a state-machine-reachable denial of service on the universal execution finalization path, analogous to the reported `resetAllGates` unbounded-array-iteration flaw.

### Finding Description
`RecordInboundVote` (<cite repo="Thankgoddavid56/push-chain-node--019" path="x/uexecutor/keeper/inbound.go" start="27,42,56" />) creates a new `PendingInboundEntry`/`InboundVariant` for every unique `(source_chain, tx_hash, log_index)` combination the moment the first validator votes on it. `VoteInbound` (<cite repo="Thankgoddavid56/push-chain-node--019" path="x/uexecutor/keeper/msg_vote_inbound.go" start="18,64,70" />) always calls `RecordInboundVote` before voting on the ballot, so every observed source-chain event — including trivially cheap, attacker-generated deposits — grows `PendingInbounds` and stays there until the ballot is fully resolved.

When any inbound ballot finalizes (`PASSED`/`REJECTED`/`EXPIRED`), `x/uvalidator`'s `MarkBallotFinalized`/`MarkBallotExpired` invoke the registered `BallotHooks.AfterBallotTerminal` callback (<cite repo="Thankgoddavid56/push-chain-node--019" path="x/uvalidator/keeper/ballot.go" start="155,187" />, <cite repo="Thankgoddavid56/push-chain-node--019" path="x/uvalidator/keeper/ballot.go" start="191,212" />). For `INBOUND_TX` ballots this dispatches to `afterInboundBallotTerminal`, which does:

```go
err := h.k.PendingInbounds.Walk(ctx, nil, func(key string, e types.PendingInboundEntry) (bool, error) {
    for _, v := range e.Variants {
        if v.BallotId == ballotID {
            utxKey, entry, found = key, e, true
            return true, nil
        }
    }
    return false, nil
})
```

This scans the entire `PendingInbounds` map (no index by ballot ID, no bound on iteration count) every time a single ballot resolves. As documented, "the pending set is small and transient" is only an assumption — nothing enforces it (<cite repo="Thankgoddavid56/push-chain-node--019" path="x/uexecutor/keeper/ballot_hooks.go" start="76,80" />). An attacker who submits many cheap deposits across configured source chains (each a distinct `tx_hash`/`log_index`, requiring no privileged access) causes validators to record correspondingly many `PendingInbounds` entries. Because entries are only removed once *all* their ballot variants reach a terminal state, an attacker can also deliberately keep entries pending (e.g., by using chains/values that make votes slow to reach quorum) to maximize the live-entry count for longer.

Once the collection is large, resolving *any* inbound ballot — including one for a legitimate user's genuine deposit — requires the module to iterate potentially the full set, and this iteration happens inside a real, gas-metered Cosmos transaction (`MsgVoteInbound`), unlike the EVM `resetAllGates` case but with the same root cause: unbounded iteration over attacker-influenced-size state performed synchronously as part of routine execution. As `PendingInbounds` grows without bound, per-vote gas cost grows, degrading and eventually blocking finalization of inbound votes network-wide (validators' `MsgVoteInbound` txs start failing due to out-of-gas), which stalls `UniversalTx` creation for all pending inbound deposits, including honest users' funds.

### Impact Explanation
This is a denial-of-service on the universal execution finalization path (inbound voting → `UniversalTx` creation), reachable without any privileged role — an attacker only needs to trigger enabled-chain deposits, which validators must observe and vote on per protocol design. Severity is Medium: no direct fund loss occurs, but honest users' inbound transactions can be stalled/blocked because validator votes that would finalize their ballots start failing from excessive gas consumption in the mandatory cleanup hook, and the accumulated `PendingInbounds` backlog persists as growing state that keeps degrading every future inbound resolution.

### Likelihood Explanation
Medium. It requires the attacker to fund a moderate number of cheap deposits on one or more enabled source chains and get validators to vote on them (which happens automatically per the module's crosschain-observation design — no admin/validator collusion is needed). This is achievable purely through ordinary user-reachable deposit flows, matching the "reachable without privileged control" DoS class explicitly listed as in-scope.

### Recommendation
- Add a secondary index (e.g., `Map[ballotID -> utxKey]`) so `afterInboundBallotTerminal` can do a direct `Get` instead of a full `Walk` scan.
- Alternatively, bound the number of concurrently-pending `PendingInbounds`/variants (e.g., cap variants per `utx_key`, or rate-limit/age out entries), and enforce ballot expiry aggressively so stale entries can't accumulate indefinitely.
- Consider charging/metering iteration cost proportionally, or moving the terminal-cleanup lookup off the hot vote-finalization path (e.g., batched/async cleanup) so an attacker-inflated collection can't directly degrade the gas cost of every future vote.

### Proof of Concept
1. Attacker performs `N` small deposits on an enabled source chain (e.g., `eip155:11155111`), each with a unique `tx_hash`/`log_index`, at minimal cost.
2. Validators observe and submit `MsgVoteInbound` for each, causing `RecordInboundVote` to create `N` distinct `PendingInboundEntry` records that remain in `PendingInbounds` until their ballots terminate (`GetInboundBallotKey`/`RecordInboundVote` per <cite repo="Thankgoddavid56/push-chain-node--019" path="x/uexecutor/keeper/inbound.go" start="35,56" />).
3. As `N` grows large (e.g., tens of thousands, well within reach of dust-value deposits), every subsequent `MsgVoteInbound` that finalizes any ballot (attacker's or a genuine user's) triggers `PendingInbounds.Walk` over the full `N`-sized collection in `afterInboundBallotTerminal` (<cite repo="Thankgoddavid56/push-chain-node--019" path="x/uexecutor/keeper/ballot_hooks.go" start="86,94" />), consuming gas proportional to `N`.
4. Once the per-tx gas cost of this scan exceeds validators' typical gas limit for `MsgVoteInbound`, votes on inbound ballots begin failing with out-of-gas, halting finalization of pending inbounds — including honest users' deposits awaiting their `UniversalTx`.
