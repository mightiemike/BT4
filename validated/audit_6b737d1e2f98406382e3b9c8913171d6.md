### Title
Deposit Refund Misdirection in `apply_delegate_action` Allows Unprivileged User to Drain Relayer Funds — (`runtime/runtime/src/actions.rs`)

---

### Summary

When a `DelegateAction` (meta transaction) inner receipt fails on the receiver's shard, the attached deposit is refunded to the `predecessor_id` of the inner receipt — the `sender_id` (Alice, the user) — not to the relayer who actually paid the deposit. An unprivileged user can deliberately craft a `DelegateAction` with a large attached deposit that will fail on the receiver's shard, causing the relayer to permanently lose the deposit while the user gains it.

---

### Finding Description

In `apply_delegate_action` (`runtime/runtime/src/actions.rs`), when a new inner receipt is generated from a `DelegateAction`, the `predecessor_id` is set to `sender_id` (Alice, the user):

```rust
let new_receipt = Receipt::V0(ReceiptV0 {
    predecessor_id: sender_id.clone(),   // ← Alice, not the relayer
    receiver_id: delegate_action.receiver_id().clone(),
    receipt: ReceiptEnum::Action(ActionReceipt {
        signer_id: action_receipt.signer_id().clone(),  // ← relayer
        ...
        actions: delegate_action.get_actions(),
    }),
});
``` [1](#0-0) 

The relayer is the `signer_id` of the outer transaction and pays all costs including the attached deposit. However, when the inner receipt fails on the receiver's shard, `refund_unspent_gas_and_deposits` generates a deposit refund to `receipt.balance_refund_receiver()`, which resolves to the `predecessor_id` of the inner receipt — Alice — not the relayer:

```rust
if deposit_refund > Balance::ZERO {
    result.new_receipts.push(Receipt::new_balance_refund(
        receipt.balance_refund_receiver(),   // ← Alice (predecessor_id of inner receipt)
        deposit_refund,
    ));
}
``` [2](#0-1) 

The code comment in `apply_delegate_action` itself acknowledges this asymmetry:

> "Note, Relayer prepaid all fees and all things required by actions: attached deposits and attached gas. If something goes wrong, deposit is refunded to the predecessor, this is sender_id/Sender in DelegateAction. Gas is refunded to the signer, this is Relayer. … Therefore Relayer should verify DelegateAction before submitting it because it spends the attached deposit." [3](#0-2) 

The nearcore architecture documentation explicitly confirms the exploitable invariant:

> "But what if the transaction fails execution on Bob's shard? At this point, the predecessor is `Alice` and therefore she receives the token balance refunded, not the relayer. This is something relayer implementations must be aware of since there is a **financial incentive for Alice to submit meta transactions that have high balances attached but will fail on Bob's shard**." [4](#0-3) 

The protocol provides no on-chain mechanism for a relayer to enforce that a deposit refund returns to itself. The only suggested mitigation is off-chain pre-verification, which cannot be made atomic with on-chain execution.

---

### Impact Explanation

**Invariant broken:** The relayer pays the deposit for inner actions in a meta transaction. If the inner receipt fails, the deposit must be returned to the party who paid it (the relayer/signer). Instead, it is returned to the `predecessor_id` of the inner receipt (the user/sender), breaking the fund-custody invariant.

**Concrete loss:** An unprivileged user can cause the relayer to lose an arbitrarily large NEAR deposit. The user's balance increases by the deposit amount; the relayer's balance decreases by the same amount. This is a direct, unconditional transfer of funds from the relayer to the attacker, triggered entirely by the attacker's off-chain action of crafting a malicious `DelegateAction`.

This maps to the allowed impact categories: **stealing or loss of funds** and **balance manipulation**.

---

### Likelihood Explanation

- **Attacker:** Any unprivileged NEAR account holder. No special role, key, or privilege is required.
- **Trigger:** Alice crafts a `DelegateAction` containing a `FunctionCall` or `Transfer` with a large attached deposit directed at a receiver that will reject or fail the call (e.g., a non-existent method, a contract that panics, or a non-existent account). She sends this off-chain to any relayer.
- **Relayer pre-verification is insufficient:** The relayer can check Alice's current state, but cannot atomically guarantee the inner receipt will succeed. Alice can race the relayer by modifying state (e.g., removing a storage registration) between the relayer's check and the on-chain execution.
- **Repeatability:** The attack can be repeated with fresh nonces as long as the relayer continues to accept `DelegateAction`s from Alice.
- **No protocol-level guard exists:** The `DelegateAction` validation in `apply_delegate_action` checks signature, `max_block_height`, sender identity, and key permissions — but does not and cannot check whether the inner receipt will succeed. [5](#0-4) 

---

### Recommendation

The protocol should redirect deposit refunds from failed inner receipts to the `signer_id` (relayer) rather than the `predecessor_id` (sender). Concretely, `apply_delegate_action` should either:

1. **Set `predecessor_id` to the relayer's account** in the generated inner receipt, so that the standard deposit-refund path (`predecessor_id`) already returns funds to the relayer; or
2. **Override `balance_refund_receiver()`** for receipts spawned by `DelegateAction` to return `signer_id` instead of `predecessor_id`.

A less invasive alternative is to add a protocol-level `max_deposit` field to `DelegateAction` that the relayer can enforce on-chain, capping the deposit the relayer is exposed to.

---

### Proof of Concept

**Setup:**
- `relayer.near` — a meta-transaction relayer with 1000 NEAR
- `alice.near` — an unprivileged user with 0 NEAR
- `victim_contract.near` — a contract that always panics on any call

**Steps:**

1. Alice crafts a `DelegateAction`:
   ```
   DelegateAction {
       sender_id: "alice.near",
       receiver_id: "victim_contract.near",
       actions: [FunctionCall { method: "any", deposit: 500 NEAR, gas: 30 TGas }],
       nonce: <valid>,
       max_block_height: <current + 100>,
       public_key: <alice's key>,
   }
   ```
2. Alice signs it and sends it off-chain to `relayer.near`.
3. `relayer.near` wraps it in a `SignedTransaction` (paying 500 NEAR deposit + gas) and submits it on-chain.
4. On `alice.near`'s shard, `apply_delegate_action` executes: inner receipt is created with `predecessor_id = "alice.near"`, `signer_id = "relayer.near"`.
5. On `victim_contract.near`'s shard, the function call panics. `refund_unspent_gas_and_deposits` fires:
   - Gas refund → `signer_id` = `relayer.near` ✓
   - **Deposit refund (500 NEAR) → `predecessor_id` = `alice.near`** ✗
6. **Result:** `relayer.near` loses 500 NEAR (plus gas). `alice.near` gains 500 NEAR. Alice started with 0 NEAR.

The broken value is the deposit refund receiver: `alice.near` instead of `relayer.near`. The corrupted state is `alice.near`'s balance (increased by 500 NEAR) and `relayer.near`'s balance (decreased by 500 NEAR + gas). [1](#0-0) [2](#0-1) [6](#0-5)
