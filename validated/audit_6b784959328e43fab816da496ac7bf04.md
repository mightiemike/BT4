### Title
Signer's "active miner" identity check (consensus hash / pubkey hash / bitvec) runs only at proposal time and is never re-validated before the signature is placed - (File: stacks-signer/src/chainstate/v2.rs, stacks-signer/src/v0/signer.rs)

### Summary
`GlobalStateView::check_proposal()` validates that a proposed block's `consensus_hash` matches the signer's currently-tracked active-miner `tenure_id`, that the recovered miner pubkey hash matches the winning pubkey hash, and that the bitvec is all-1s. This is the analog of the report's "open price of a stop order" check: a value that determines whether the trade (here, the block/miner) is still legitimate. This check runs exactly once, when the proposal first arrives, but the irrevocable action (placing a signer's cryptographic signature) happens much later, after a two-round pre-commit process that can take minutes. The re-validation performed just before signing (`check_block_against_signer_db_state`) intentionally omits this active-miner identity check.

### Finding Description
Per `docs/signer-flows.md` (section 7, "The chainstate checks (shared)"), the flow is explicit:

> "Two things belong to the proposal path only and are **not** re-run at validate-ok or at signing: ... the v2 `check_proposal` wrapper checks miner pubkey hash, consensus hash, the pox bitvec, and tenure-extend rules before delegating here."

The actual check lives in `GlobalStateView::check_proposal` [1](#0-0) , which compares `block.header.consensus_hash` against the signer's locally-tracked `MinerState::ActiveMiner.tenure_id`, and the recovered pubkey against `current_miner_pkh` [2](#0-1) .

This check is invoked only from `handle_block_proposal` at the time the proposal first arrives (per the flow diagram in `docs/signer-flows.md`, section 3, `CHECK["check_block_against_state ... v1 SortitionsView::check_proposal or v2 GlobalStateView::check_proposal"]`). Downstream, before the signature is actually produced, the code re-runs `check_block_against_signer_db_state` at two points: once when the validate-ok response arrives [3](#0-2) , and again once the pre-commit weight threshold is crossed [4](#0-3) . But `check_block_against_signer_db_state` itself only checks tenure-change-confirms-parent and "is this the latest block in tenure" [5](#0-4)  — it does **not** re-check that the block's `consensus_hash` still matches the signer's *current* active-miner tenure id, nor that the miner pubkey hash is still the *current* winning pubkey hash.

Between the initial proposal check and the final signature, the signer's view of "who is the active miner" (`self.signer_state.current_miner`) can change — a new sortition can arrive, a burn view can advance, or the miner-status state machine can be updated (e.g. `sortition_state.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock` set from a 30% `ReorgNotAllowed` rejection weight, as seen in `store_and_process_block_rejection` [6](#0-5) ). None of that invalidates a pre-commit or block-info record already in flight for the proposal that was checked against the *old* active-miner view, since the pre-commit/signing recheck path does not re-run `check_proposal`'s identity checks.

### Impact Explanation
This is a minority-triggerable divergence in what a "valid" signature means: a signer that received the proposal when it still matched the active miner can end up placing its signature on a block whose `consensus_hash`/pubkey no longer correspond to the miner the rest of the network currently recognizes as active (e.g. after a new sortition or after a `ReorgNotAllowed`-driven invalidation). Because different signers observe state-machine transitions (`current_miner`, `miner_status`) at slightly different wall-clock times, some signers may place signatures based on a now-stale active-miner view while others, evaluating the same block slightly later, would reject it under `check_proposal`. If enough signers straddle this window, the block can gather the 70% signing weight and be pushed to the node even though it no longer satisfies the `ConsensusHashMismatch`/`PubkeyHashMismatch` equality that `check_proposal` is meant to guarantee — a temporary tip/verdict disagreement between signers bounded to at most one sortition's worth of drift. This matches the "High: minority-triggerable... static-validation divergence... temporary tip disagreement" bucket rather than a full chain split, since the stacks-node's own block acceptance still independently re-derives the winning sortition from burn state.

### Likelihood Explanation
The window is real and adversary-controllable: the report's own PoC pattern (a value validated once, then changed, with the dependent check never re-run) maps directly onto the signer's pre-commit round, which the docs describe as deliberately taking "minutes" to reach 70% weight. An attacker (or just network conditions) that causes a new sortition, a tenure-extend, or a 30%-weight `ReorgNotAllowed` rejection to land inside that window can trigger the described divergence without needing majority signer collusion — a single signer or a small minority racing ahead of others is sufficient to manifest disagreement. Likelihood is Medium-to-High for the *divergence* occurring, though turning that divergence into an actually-signed, pushed block still requires enough total weight to reach the 70% threshold before the "conflict" backstops in `handle_block_pre_commit` (fresh signed-conflict/reorg-permit checks) catch it — those backstops target *sibling-block* conflicts, not stale active-miner identity, so they do not close this specific gap.

### Recommendation
Re-run the `consensus_hash`/pubkey-hash/bitvec equality checks from `GlobalStateView::check_proposal` (or the equivalent v1 checks) inside `check_block_against_signer_db_state`, so that both the validate-ok recheck and the pre-commit-threshold recheck re-validate the block against the signer's *current* `current_miner` state, not just tenure-confirmation. This mirrors the C4 mitigation direction ("validate again for the new value before the irreversible action") applied to the signer's active-miner identity rather than to a swap's SL/TP price.

### Proof of Concept
1. Signer S receives a block proposal `B` referencing tenure `T1`; `check_proposal` passes because `self.signer_state.current_miner` is `ActiveMiner { tenure_id: T1, current_miner_pkh: PKH1 }` [7](#0-6) .
2. `B` is submitted for node validation and returns OK; `check_block_against_signer_db_state` is run and passes (it only checks tenure-confirmation, not miner identity) [3](#0-2) ; S sends a pre-commit.
3. Before 70% pre-commit weight is reached, a new sortition lands and S's state machine advances `current_miner` to tenure `T2`/`PKH2` (or 30% of signers vote `ReorgNotAllowed`, setting `miner_status = InvalidatedBeforeFirstBlock` for `T1`'s sortition) [6](#0-5) .
4. Other pre-commits for `B` (from signers that were still slightly behind, or had already locked in before the transition) arrive and cross the 70% weight threshold; `handle_block_pre_commit` reruns `check_block_against_signer_db_state`, which still does not check `consensus_hash`/pubkey against the now-updated `current_miner`, so it passes, and S signs `B` [4](#0-3) .
5. `B` is broadcast as signed even though, under the network's now-current view, it should have failed `ConsensusHashMismatch`/`PubkeyHashMismatch`, producing a signer-set verdict disagreement with signers that evaluated `B` after the transition and rejected it via `check_proposal`.
