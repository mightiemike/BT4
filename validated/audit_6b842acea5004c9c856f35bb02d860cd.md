### Title
`many_ref_accounts_can_be_moved` underestimates storage slots needed by `PackedAncientStorage::pack`, letting multi-ref "newest alive" accounts be repacked into a target slot lower than their true write slot - ([File: accounts-db/src/ancient_append_vecs.rs])

### Summary
`AccountsDb::many_ref_accounts_can_be_moved` reserves target ancient slots for `many_refs_newest` accounts using a purely byte-based estimate (`required_ideal_packed`), but the actual packer `PackedAncientStorage::pack` is a sequential/"next-fit" bin packer that can consume strictly more storage bins than that byte estimate when account sizes don't divide evenly into `ideal_storage_size`. When this fragmentation occurs, `write_packed_storages` (which zips `target_slots_sorted` from highest to lowest against the packed chunks in priority order) can place a multi-ref account's newest-alive data into a target slot lower than the boundary slot verified by `many_ref_accounts_can_be_moved`, and potentially lower than the account's own original slot, violating the documented invariant "accounts in `many_refs_newest` must be moved a slot >= each account's current slot."

### Finding Description
`many_ref_accounts_can_be_moved` (accounts-db/src/ancient_append_vecs.rs:390-415) computes: [1](#0-0) 

`required_ideal_packed = floor(alive_bytes / ideal_storage_size) + 1`, which is always `>= ceil(alive_bytes / ideal_storage_size)` — i.e., it assumes an *optimal* bytes-only packing with at most one bin of rounding slack. It then checks that all `many_refs_newest` account slots are `<= target_slots_sorted[len - required_ideal_packed]`, relying on the assumption that the real packer will place all multi-ref content inside exactly the top `required_ideal_packed` reserved target slots.

The real packer, `PackedAncientStorage::pack` (accounts-db/src/ancient_append_vecs.rs:1012-1094), is a sequential next-fit packer: once adding the next whole account to the current bin would exceed `ideal_size`, it closes the bin (leaving up to `account_size - 1` bytes of slack) and starts a new one: [2](#0-1) 

Because accounts are indivisible units, adversarially-sized accounts can force the packer to waste a bounded fraction of each bin repeatedly. Over many bins this fragmentation accumulates and the actual number of bins consumed by `many_refs_newest` content can exceed the byte-based `required_ideal_packed` estimate by more than the single-bin buffer built into the "+1" rounding.

`combine_ancient_slots_packed_internal` (accounts-db/src/ancient_append_vecs.rs:470-511) uses the boolean result of `many_ref_accounts_can_be_moved` as the *only* gate before calling `PackedAncientStorage::pack` and then `write_packed_storages`: [3](#0-2) 

`write_packed_storages` (accounts-db/src/ancient_append_vecs.rs:646-701) assigns packed chunks to `target_slots_sorted` from highest to lowest, in the same order `pack()` produced them (multi-ref chunks first, since `many_refs_newest` is chained first in the iterator at line 496-502): [4](#0-3) 

The only remaining safety net, `pack.len() > accounts_to_combine.target_slots_sorted.len()` (line 506), only rejects the repack if the *total* number of chunks (multi-ref + one-ref) exceeds the total target-slot count — it does not check that the multi-ref chunks specifically stayed within the reserved high-slot region. So if fragmentation pushes the multi-ref boundary down by more than the "+1" slack while total chunk count still fits, the extra multi-ref chunk lands on a target slot below `highest_slot`, and potentially below that account's own original slot — directly violating the invariant the check exists to enforce.

Since the affected accounts are, by construction, multi-ref (`ref_count > 1`, i.e., the same pubkey has other slot-list entries at older slots), relocating the "newest alive" entry to a slot lower than an *intervening* still-tracked slot-list entry means the accounts index would then resolve that pubkey's slot-list max for many ancestor sets to the older, intervening entry instead of the truly newest data — a stale-read violation.

### Impact Explanation
This matches the "AccountsDB returns stale/wrong-slot account state to execution" category. If exploited, an ancestor-scoped account load could return older account data (wrong owner/lamports/data) than what was actually most recently committed for that fork, which could let a subsequent transaction operate on stale account state (e.g., double-spend logic based on a stale balance, or bypass state transitions that depend on the latest write). It also risks accounts-hash/capitalization divergence between honest nodes if the repack happens non-deterministically relative to timing, and can trigger the `debug_assert!` at `finish_combine_ancient_slots_packed_internal` in adjacent code paths or downstream consistency assertions, causing a node panic in debug builds.

### Likelihood Explanation
This requires an unprivileged attacker to: (1) create many multi-ref accounts (same pubkey written at multiple slots, so ref_count > 1) that are the "newest alive" version, sized so that they poorly bin-pack against `get_ancient_append_vec_capacity()` (128 MiB, accounts-db/src/ancient_append_vecs.rs:1097-1118), and (2) accumulate enough of these ancient-eligible slots/bytes so that the accumulated fragmentation (bounded by `~account_size / ideal_storage_size` per bin, up to ~7.8% given `MAX_ACCOUNT_DATA_LEN` = 10 MiB) exceeds the single-bin buffer in `required_ideal_packed`. This is achievable purely through normal user account create/rewrite operations paid for by the attacker, without validator/leader privileges, but requires substantial storage/rent cost (roughly gigabytes of account data across many slots) and precise timing to land these slots in the same ancient-slot combination batch, making it a real but resource-intensive, non-trivial-to-time attack.

### Recommendation
Make `many_ref_accounts_can_be_moved`'s slot-boundary check track the actual number of bins `PackedAncientStorage::pack` will use for `many_refs_newest` content (e.g., by running a dry-run pack of just `many_refs_newest` first and using its concrete `.len()` instead of the byte-based estimate), or change `write_packed_storages`/`pack` to guarantee multi-ref content never spills past the previously-computed boundary (e.g., pack `many_refs_newest` into its own dedicated set of storages, verify count against target slots, and only then pack one-ref accounts separately into the remaining target slots) instead of chaining them into a single sequential pack pass.

### Proof of Concept
Rust unit test in `accounts-db/src/ancient_append_vecs.rs` test module, building on existing helpers `combine_ancient_slots_packed_for_tests`, `get_sample_storages`, and `PackedAncientStorage::pack`:

```rust
#[test]
fn test_many_ref_pack_fragmentation_violates_slot_order() {
    // ideal_size chosen so items of size just under it force 1-per-bin fragmentation,
    // and required_ideal_packed (byte-based) undercounts actual bins needed.
    let ideal_size = 1000u64;
    // Build >13 AliveAccounts sets (many_refs_newest), each with a single account
    // whose stored size is just over half of ideal_size is not needed; use sizes
    // that leave ~8% waste per bin and accumulate over many bins, e.g. size=130,
    // where floor(1000/130)=7 fits with 90 bytes waste per bin (9%).
    // Construct N sets, each descending slot, each 130 bytes, spanning enough bins
    // that fragmentation waste > 1 extra bin vs required_ideal_packed's "+1" buffer.
    let account_size = 130usize;
    let num_sets = 100; // total bytes = 13000, ideal ceiling = 13 bins
    // many_refs_newest slots descending: 1000, 999, ..., 901
    // target_slots_sorted ascending: enough slots to satisfy required_ideal_packed
    // but fewer than actual bins fragmentation will require.
    //
    // 1. Build many_refs_newest: Vec<AliveAccounts> with `num_sets` entries,
    //    each `bytes = account_size`, slot = 1000 - i.
    // 2. Compute required_ideal_packed per the production formula.
    // 3. Call PackedAncientStorage::pack(many_refs_newest.iter(), ideal_size) alone
    //    and assert result.len() > required_ideal_packed (demonstrates undercount).
    // 4. Then run combine_ancient_slots_packed_for_tests with a real DB where
    //    target_slots_sorted is sized to exactly required_ideal_packed + few one-ref slots,
    //    verify many_ref_accounts_can_be_moved returns true (bug: should reject),
    //    then assert post-pack the multi-ref account with the LOWEST slot in
    //    many_refs_newest ends up written to a target slot < its original slot,
    //    which should be an assertion failure / invariant violation.
}
```

Concretely, the first assertion (`result.len() > required_ideal_packed`) is the core, minimal, deterministic proof that `PackedAncientStorage::pack`'s actual bin count can exceed `many_ref_accounts_can_be_moved`'s reserved bin count, which is the root cause enabling the slot-order violation in the full `combine_ancient_slots_packed_internal` flow.
