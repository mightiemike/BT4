### Title
`ValidateMultiSign` precompiled contract's signed hash is not bound to a caller/contract identity or nonce, enabling cross-contract and repeated replay of the same authorization - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompile (TVM opcode reachable via any smart contract call) recovers signer addresses from a hash computed only as `sha256(address || permissionId || data)`. This hash carries no information about which contract invoked the precompile, no nonce, and no usage-tracking, so a single off-chain signature produced to authorize one specific action in one specific consuming contract can be replayed verbatim — by anyone, in any other contract, and any number of times — as long as that contract also passes the same `(address, permissionId, data)` triple to the precompile. This mirrors the Astaria root cause: a signed "commitment" whose encoding omits the identity of the consuming contract (there, `strategy.vault`), letting the same signature validate successfully in unintended contexts and be reused indefinitely.

Because the recovered signature is checked purely against `TransactionCapsule.getWeight(permission, recoveredAddr)` and a threshold, with no consumption/nonce bookkeeping at the precompile level (analogous to how `TransactionCapsule.checkWeight` for on-chain transactions is safe only because the *entire raw transaction bytes*, including unique reference block/expiration, are hashed — a protection this precompile deliberately does not provide): [4](#0-3) 

any dApp built on top of `validatemultisign`/`batchvalidatesign` to implement an off-chain-authorized, single-use action (loans, vault operations, orders, etc. — exactly the pattern in the Astaria report) inherits full exposure to signature replay unless it independently embeds a nonce and the consuming contract's own address inside `data`/`hash` and manually enforces one-time use. The precompile itself provides no such guarantee, unlike a well-designed EIP-712-style scheme that would bind `chainId`, verifying contract, and a nonce into the signed digest.

### Impact Explanation
Any TVM smart contract relying on `ValidateMultiSign`/`BatchValidateSign` as its sole authorization/anti-replay mechanism for asset-moving or state-changing actions (loan issuance, withdrawal approval, order execution, etc.) is vulnerable to the exact replay class described in the report: a single legitimately-signed authorization can be reused multiple times, or reused by a different, unrelated contract that happens to receive the same `(address, permissionId, data)` triple, resulting in unauthorized repeated asset transfers or accounting corruption for those contracts. This is a genuine gap in a security-primitive precompile that many contracts trust to behave like a safe, one-shot signature check.

### Likelihood Explanation
Exploitation requires an attacker (or a buggy dApp) to reuse a previously observed valid `(address, permissionId, data, signatures)` tuple against the same or another contract that performs the identical precompile call — fully unprivileged and reachable from any deployed TVM contract via a standard triggered/contract-call transaction. No special network position or privileged role is required; the only prerequisite is a consuming contract that does not itself add nonce/context binding, which is common for naive implementations of the multisig-authorization pattern this precompile advertises.

### Recommendation
Document explicitly (and consider enforcing) that `data`/`hash` passed to `ValidateMultiSign`/`BatchValidateSign` MUST include a unique nonce, the target/consuming contract address, and a chain identifier, and/or add a native nonce-tracking mechanism (e.g., an on-chain used-hash set scoped per account/permission) inside the precompile itself so a given signature can only be consumed once, closing the gap regardless of how careful individual dApp authors are.

### Proof of Concept
1. Account `A` signs `hash = sha256(A || permissionId || data)` once, intending to authorize a single action in contract `C1` (e.g., "approve withdrawal of X tokens").
2. Contract `C1` calls the `validatemultisign` precompile with `(A, permissionId, data, [sig])`; it returns `true` and `C1` performs the withdrawal. [5](#0-4) 
3. The same tuple `(A, permissionId, data, [sig])` is submitted again — either to `C1` a second time, or to an unrelated contract `C2` that happens to call the precompile with the same triple — and the precompile again returns `true`, because `hash` is identical and nothing tracked its prior use or bound it to `C1`.
4. `C2` (or `C1` again) treats this as a fresh, valid authorization and performs the action a second time, exactly as in the reported Astaria bug where the same commitment/signature was replayed against a different vault/contract context.
