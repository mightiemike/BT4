### Title
`ensure_match_transaction_info` skips checkpoint-hash comparison, letting replay-verify accept a diverged authenticated state root - (File: `types/src/transaction/mod.rs`)

### Summary
`TransactionOutput::ensure_match_transaction_info` is the single integrity gate used by both the debugger/CLI and `db-tool`'s `replay_on_archive` to confirm that a freshly re-executed transaction output matches the transaction info that was actually committed to the ledger accumulator. The function validates status, gas, write-set hash, and event-root hash, but explicitly does **not** validate the state-checkpoint / hot-state / `position_state_checkpoint_hash` fields of `TransactionInfo`, per its own inline TODO. This mirrors the external report's bug class: a value that is supposed to be checked/accrued through one code path (here, checkpoint-hash verification) can silently diverge because a second path (state/hot-state/position checkpoint commitment) is never compared against the authoritative value.

### Finding Description
`ensure_match_transaction_info` in `types/src/transaction/mod.rs` is the comparator invoked by `storage/db-tool/src/replay_on_archive.rs::Verifier::execute_and_verify` after re-executing a chunk of transactions: [1](#0-0) 

It checks status, gas used, write-set hash against `state_change_hash`, and event root hash: [2](#0-1) 

But it stops there, with an explicit acknowledgment that checkpoint hashes are skipped: [3](#0-2) 

`TransactionInfo` (in the `TransactionInfoV1` variant gated by the `TRANSACTION_INFO_V1` feature) carries a `state_checkpoint_hash` (state + hot-state root) and, for the native trading subsystem, a `position_state_checkpoint_hash`, which becomes consensus-committed and accumulator-bound once `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled: [4](#0-3) 

These checkpoint hashes are computed during execution in `do_state_checkpoint.rs`/`do_ledger_update.rs` and folded into the `TransactionInfo` that is hashed into the transaction accumulator on commit: [5](#0-4) 

Because `ensure_match_transaction_info` is the only comparator used by replay-verify tooling, and it never re-derives or compares the checkpoint hashes it receives against locally re-executed state/hot-state/position roots, any divergence between the locally computed state (state SMT root, hot-state root, or native-position state root) and what was actually committed to the ledger under `TransactionInfoV1` will not be detected by `replay_on_archive`. The tool will report the chunk as successfully verified even though the authenticated checkpoint/state root differs from what local execution would produce.

### Impact Explanation
This breaks the state-proof/replay integrity invariant required by the gate: "committed state that differs from the correct VM result... accepted as valid" and "hard-fork-only divergence during commit, replay, restore, or proof verification." Once `TRANSACTION_INFO_V1`/`COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are turned on (they are feature-gated but designed to be enabled), a bug in state-checkpoint or native-position state-root computation on the committing path (executor, hot-state accumulator, or native-position handling) would be invisible to the primary offline auditing/replay tool. This directly undermines the ability to detect a corrupted or forked ledger state via replay, which is exactly the kind of proof-and-storage pivot the task calls out as high/critical: an authenticated, accumulator-bound root (`state_checkpoint_hash`/`position_state_checkpoint_hash`) can silently diverge from the correct VM result without any tooling catching it.

### Likelihood Explanation
The gap is not hypothetical: it's called out by name in the code (`// TODO(trading-native): ... Validate the checkpoint hashes here before enabling COMPUTE_TRADING_NATIVE_STATE_ROOTS`), meaning the feature is intended to be turned on for the native-trading subsystem while this check is still missing. Anyone using `replay_on_archive`/the debugger/CLI to independently verify chain history after this feature is enabled would get false assurance. Likelihood of triggering requires (a) the feature being enabled and (b) an independent bug in checkpoint-root computation elsewhere — but the point of this finding is that the *detection* mechanism itself is broken, so any such bug would go unnoticed rather than being caught, which is a proof-integrity failure in its own right regardless of whether an unrelated root-computation bug currently exists.

### Recommendation
Extend `ensure_match_transaction_info` to accept and compare the locally-computed state checkpoint hash, hot-state root hash, and (when native trading is enabled) `position_state_checkpoint_hash` against the corresponding fields on the supplied `TransactionInfo`, failing verification (as the other checks do via `ensure!`) on any mismatch. This must be wired up before `COMPUTE_TRADING_NATIVE_STATE_ROOTS`/`HOT_STATE_ROOT_IN_TXN_INFO` are enabled in production, as the TODO itself states.

### Proof of Concept
Not directly exploitable as a standalone PoC since it requires the checkpoint-hash-affecting features to be enabled and a separate root-computation defect to exist; the finding is that the verification code path (`ensure_match_transaction_info`, invoked from `replay_on_archive.rs` line 392) provably omits comparison of `state_checkpoint_hash`/`position_state_checkpoint_hash`/hot-state root fields, per the maintainers' own TODO at `types/src/transaction/mod.rs:2197-2202`, so any such defect would pass replay verification undetected — the code proves the missing invariant directly.
